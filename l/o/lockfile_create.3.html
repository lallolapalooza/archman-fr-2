lockfile_create(3)

Paquet: liblockfile

Licences: GPL

LOCKFILE_CREATE(3) Manuel du programmeur Linux LOCKFILE_CREATE(3)

NOM

lockfile_create, lockfile_remove, lockfile_touch, lockfile_check - gestion des fichiers de verrouillage

SYNTAXE

#include <lockfile.h>

cc [ drapeau ... ] fichier ... -llockfile [ bibliothèque ]

int lockfile_create( const char *fichier_verrou, int tentatives, int drapeaux [, struct lockargs args ] );
int lockfile_remove( const char *fichier_verrou );
int lockfile_touch( const char *fichier_verrou );
int lockfile_check( const char *fichier_verrou, int drapeaux );

DESCRIPTION

Fonctions pour gérer les fichiers de verrouillage de manière sûre pour NFS.

lockfile_create

La fonction lockfile_create crée un fichier de verrouillage de manière sûre pour NFS.

Si le paramètre drapeaux est défini sur L_PID ou L_PPID, lockfile_create vérifiera non seulement l'existence d'un fichier de verrouillage, mais lira également son contenu pour voir s'il contient un identifiant de processus en ASCII. Si c'est le cas, le fichier de verrouillage n'est valide que si ce processus existe toujours. Sinon, un fichier de verrouillage plus ancien que 5 minutes est considéré comme obsolète.

Lors de la création d'un fichier de verrouillage, si L_PID est défini dans drapeaux, l'ID du processus courant sera écrit dans le fichier de verrouillage. Parfois, il peut être utile d'utiliser l'ID du processus parent à la place (par exemple, la commande dotlockfile l'utilise). Dans de tels cas, vous pouvez utiliser le drapeau L_PPID à la place.

lockfile_touch

Si le fichier de verrouillage se trouve sur un système de fichiers partagé, il pourrait avoir été créé par un processus sur une machine distante. La méthode L_PID ou L_PPID pour déterminer si un fichier de verrouillage est encore valide ou obsolète est donc incorrecte et ne doit pas être utilisée. Si vous maintenez un verrouillage pendant plus de 5 minutes, un appel à lockfile_create par un autre processus considérera le verrou comme obsolète et le supprimera. Pour éviter cela, appelez lockfile_touch pour rafraîchir le fichier de verrouillage à intervalles réguliers (toutes les minutes environ).

lockfile_check

Cette fonction vérifie si un fichier de verrouillage valide est déjà présent sans tenter de créer un nouveau fichier de verrouillage.

lockfile_remove

Supprime le fichier de verrouillage.

VALEURS DE RETOUR

lockfile_create renvoie l'un des codes de statut suivants :

   #define L_SUCCESS   0    /* Fichier de verrouillage créé                      */
   #define L_TMPLOCK   2    /* Erreur lors de la création du fichier de verrouillage temporaire           */
   #define L_TMPWRITE  3    /* Impossible d'écrire le pid dans le fichier de verrouillage temporaire      */
   #define L_MAXTRYS   4    /* Échec après le nombre maximal de tentatives  */
   #define L_ERROR     5    /* Erreur inconnue ; vérifier errno            */
   #define L_ORPHANED  7    /* Appel avec L_PPID mais le parent n'existe plus */
   #define L_RMSTALE   8    /* Échec de la suppression du fichier de verrouillage obsolète       */

lockfile_check renvoie 0 si un fichier de verrouillage valide est présent. S'il n'y a pas de fichier de verrouillage ou pas de fichier de verrouillage valide, -1 est renvoyé.

lockfile_touch et lockfile_remove renvoient 0 en cas de succès. En cas d'échec, -1 est renvoyé et errno est défini appropriément. Ce n'est pas une erreur de supprimer un fichier de verrouillage inexistant avec lockfile_remove().

ALGORITHME

L'algorithme utilisé pour créer un fichier de verrouillage de manière atomique, même sur NFS, est le suivant :

1
Un fichier unique est créé. Au format printf, le nom du fichier est .lk%05d%x%s. Le premier argument (%05d) est l'ID du processus courant. Le deuxième argument (%x) est constitué des 4 bits mineurs de la valeur renvoyée par time(2). Le dernier argument est le nom d'hôte du système.
2
Ensuite, le fichier de verrouillage est créé en utilisant link(2). La valeur de retour de link est ignorée.
3
Maintenant, le fichier de verrouillage est interrogé avec stat(). Si stat échoue, on passe à l'étape 6.
4
La valeur de stat du fichier de verrouillage est comparée à celle du fichier temporaire. Si elles sont identiques, nous avons le verrou. Le fichier temporaire est supprimé et une valeur de 0 (succès) est renvoyée à l'appelant.
5
Une vérification est effectuée pour voir si le fichier de verrouillage existant est valide. S'il n'est pas valide, le fichier de verrouillage obsolète est supprimé.
6
Avant de réessayer, on dort pendant n secondes. n est initialement de 5 secondes, mais après chaque tentative, 5 secondes supplémentaires sont ajoutées jusqu'à un maximum de 60 secondes (une augmentation progressive). Ensuite, on retourne à l'étape 2 jusqu'à tentatives fois.

SYSTÈMES DE FICHIERS DISTANTS ET LE CACHE D'ATTRIBUTS DU NOYAU

Ces fonctions ne verrouillent pas un fichier - elles génèrent un fichier de verrouillage. Cependant, dans de nombreux cas, comme les boîtes aux lettres Unix, tous les programmes concernés accédant aux boîtes aux lettres s'accordent sur le fait que la présence de <nom_de_fichier>.lock signifie que <nom_de_fichier> est verrouillé.

Si vous utilisez lockfile_create pour créer un verrou sur un fichier résidant sur un serveur distant, et que vous avez déjà ce fichier ouvert, vous devez vider le cache d'attributs NFS après le verrouillage. Ceci est nécessaire pour éviter le scénario suivant :

o
ouvrir /var/mail/NOM_UTILISATEUR
o
les attributs, tels que la taille, l'inode, etc., sont maintenant mis en cache dans le noyau !
o
pendant ce temps, une autre application distante ajoute des données à /var/mail/NOM_UTILISATEUR
o
acquérir le verrou en utilisant lockfile_create()
o
se positionner à la fin du fichier
o
écrire des données

Maintenant, la fin du fichier n'est plus vraiment la fin du fichier - le noyau a mis en cache les attributs à l'ouverture, et st_size n'est plus la fin du fichier. Donc, après avoir verrouillé le fichier, vous devez dire au noyau de vider le cache d'attributs de fichiers NFS.

La seule façon portable de faire cela est d'utiliser les primitives de verrouillage de fichiers fcntl() POSIX - verrouiller un fichier à l'aide de fcntl() a pour effet secondaire de rendre invalide le cache d'attributs de fichiers NFS du noyau.

lockfile_create() ne peut pas faire cela pour vous pour deux raisons. Premièrement, il crée simplement un fichier de verrouillage - il ne sait pas quel fichier vous essayez réellement de verrouiller ! Deuxièmement, même s'il pouvait déduire le fichier que vous verrouillez à partir du nom de fichier, en l'ouvrant et en le fermant simplement, il rendrait invalides tous les verrous POSIX existants que le programme pourrait déjà avoir sur ce fichier (oui, les sémantiques de verrouillage POSIX sont insensées !).

Donc, fondamentalement, ce que vous devez faire est quelque chose comme ceci :

  fd = open("/var/mail/UTILISATEUR");
  .. code du programme ..
  lockfile_create("/var/mail/UTILISATEUR.lock", x, y);
  /* Rendre invalide le cache d'attributs NFS en utilisant des verrous POSIX */
  if (lockf(fd, F_TLOCK, 0) == 0) lockf(fd, F_ULOCK, 0);

Vous devez faire attention à cela si vous intégrez cela dans un programme existant qui pourrait déjà utiliser le verrouillage fcntl(), flock() ou lockf() - vous pourriez rendre invalides des verrous existants.

Il existe également une méthode non portable. De nombreuses opérations NFS renvoient les attributs mis à jour - et le noyau Linux utilise réellement ceux-ci pour mettre à jour le cache d'attributs. L'une de ces opérations est chmod(2).

Donc, interroger un fichier avec stat() puis le modifier avec chmod() vers st.st_mode ne changera pas réellement le fichier, et n'interférera pas non plus avec les verrous sur le fichier, mais cela rendra invalide le cache d'attributs. L'équivalent à utiliser depuis un script shell serait

  chmod u=u /var/mail/UTILISATEUR

PERMISSIONS

Si vous êtes sur un système où le répertoire de spool de courrier n'est écrivable que par un groupe spécial (généralement "mail"), vous ne pouvez pas créer directement un fichier de verrouillage dans le répertoire de spool de courrier sans permissions spéciales.

Lockfile_create et lockfile_remove vérifient si le fichier de verrouillage se termine par $NOM_UTILISATEUR.lock, et si le répertoire où se trouve le fichier de verrouillage est accessible en écriture par le groupe
