NOM

logind.conf, logind.conf.d — Fichiers de configuration du gestionnaire de connexion

SYNTAXE

/etc/systemd/logind.conf
/run/systemd/logind.conf
/usr/local/lib/systemd/logind.conf
/usr/lib/systemd/logind.conf
/etc/systemd/logind.conf.d/*.conf
/run/systemd/logind.conf.d/*.conf
/usr/local/lib/systemd/logind.conf.d/*.conf
/usr/lib/systemd/logind.conf.d/*.conf

DESCRIPTION

Ces fichiers configurent divers paramètres du gestionnaire de connexion systemd, systemd-logind.service(8). Voir systemd.syntax(7) pour une description générale de la syntaxe.

DIRECTORIES DE CONFIGURATION ET PRÉCÉDENCE

La configuration par défaut est définie lors de la compilation, donc une configuration n'est nécessaire que lorsqu'il est nécessaire de déroger à ces valeurs par défaut. Le fichier de configuration principal est chargé à partir de l'un des répertoires listés par ordre de priorité, seul le premier fichier trouvé est utilisé : /etc/systemd/, /run/systemd/, /usr/local/lib/systemd/ [1], /usr/lib/systemd/. La version du vendeur du fichier contient des entrées commentées montrant les valeurs par défaut comme guide pour l'administrateur. Des remplacements locaux peuvent également être créés en créant des fichiers de surcharge, comme décrit ci-dessous. Le fichier de configuration principal peut également être modifié à cet effet (ou une copie dans /etc/ s'il est livré sous /usr/), cependant l'utilisation de fichiers de surcharge pour la configuration locale est recommandée par rapport aux modifications du fichier de configuration principal.

En plus du fichier de configuration principal, des fragments de configuration de surcharge sont lus à partir de /usr/lib/systemd/*.conf.d/, /usr/local/lib/systemd/*.conf.d/, et /etc/systemd/*.conf.d/. Ces surcharges ont une priorité plus élevée et remplacent le fichier de configuration principal. Les fichiers dans les sous-répertoires de configuration *.conf.d/ sont triés par leur nom de fichier par ordre lexicographique, quelle que soit la sous-répertoire dans laquelle ils résident. Lorsque plusieurs fichiers spécifient la même option, pour les options qui n'acceptent qu'une seule valeur, l'entrée dans le fichier trié en dernier prend la priorité, et pour les options qui acceptent une liste de valeurs, les entrées sont collectées dans l'ordre où elles apparaissent dans les fichiers triés.

Lorsque des paquets ont besoin de personnaliser la configuration, ils peuvent installer des surcharges sous /usr/. Les fichiers dans /etc/ sont réservés à l'administrateur local, qui peut utiliser cette logique pour remplacer les fichiers de configuration installés par les paquets du vendeur. Les surcharges doivent être utilisées pour remplacer les surcharges des paquets, car le fichier de configuration principal a une priorité plus faible. Il est recommandé de préfixer tous les noms de fichiers dans ces sous-répertoires avec un numéro à deux chiffres et un tiret, pour simplifier l'ordre. Cela définit également un concept de priorité des surcharges pour permettre aux vendeurs de systèmes d'exploitation de livrer des surcharges dans une plage spécifique inférieure à la plage utilisée par les utilisateurs. Cela devrait réduire le risque que les surcharges de paquets remplacent accidentellement les surcharges définies par les utilisateurs. Il est recommandé d'utiliser la plage 10-40 pour les surcharges dans /usr/ et la plage 60-90 pour les surcharges dans /etc/ et /run/, afin de s'assurer que les surcharges locales et transitoires prennent la priorité sur les surcharges livrées par le vendeur du système d'exploitation.

Pour désactiver un fichier de configuration fourni par le vendeur, la méthode recommandée est de placer un lien symbolique vers /dev/null dans le répertoire de configuration dans /etc/, avec le même nom de fichier que le fichier de configuration du vendeur.

OPTIONS

Toutes les options sont configurées dans la section [Login] :

NAutoVTs=

Prend un entier positif. Configure le nombre de terminaux virtuels (VT) à allouer par défaut qui, lorsqu'ils sont activés et qu'ils n'ont jamais été utilisés, des services "autovt" sont automatiquement démarrés. Ces services sont instanciés à partir de l'unité modèle autovt@.service pour le nom TTY VT respectif, par exemple, autovt@tty4.service. Par défaut, autovt@.service est lié à getty@.service. En d'autres termes, des invites de connexion sont démarrées dynamiquement lorsque l'utilisateur bascule vers des terminaux virtuels inutilisés. Par conséquent, ce paramètre contrôle combien de "gettys" de connexion sont disponibles sur les VT. Si un VT est déjà utilisé par un autre sous-système (par exemple, une connexion graphique), ce type d'activation ne sera pas tenté. Notez que le VT configuré avec ReserveVT= est toujours soumis à ce type d'activation, même s'il ne fait pas partie des VT configurés avec la directive NAutoVTs=. Par défaut : 6. S'il est défini sur 0, le démarrage automatique des services "autovt" est désactivé.

ReserveVT=

Prend un entier positif. Identifie un terminal virtuel qui sera inconditionnellement réservé pour l'activation de autovt@.service (voir ci-dessus). Le VT sélectionné avec cette option sera marqué comme occupé inconditionnellement, de sorte qu'aucun autre sous-système ne l'allouera. Cette fonctionnalité est utile pour garantir que, quel que soit le nombre de VT alloués par d'autres sous-systèmes, un "getty" de connexion est toujours disponible. Par défaut : 6 (en d'autres termes, il y aura toujours un "getty" disponible sur Alt-F6.). S'il est défini sur 0, la réservation de VT est désactivée.

Ajouté dans la version 190.

KillUserProcesses=

Prend un argument booléen. Configure si les processus d'un utilisateur doivent être tués lorsque l'utilisateur se déconnecte. S'il est défini sur vrai, l'unité de portée correspondant à la session et tous les processus à l'intérieur de cette portée seront terminés. S'il est défini sur faux, la portée est "abandonnée", voir systemd.scope(5), et les processus ne sont pas tués. Par défaut : "non", mais voir les options KillOnlyUsers= et KillExcludeUsers= ci-dessous.

En plus des processus de session, les processus utilisateur peuvent s'exécuter sous l'unité du gestionnaire utilisateur user@.service. Selon les paramètres de "linger", cela peut permettre aux utilisateurs d'exécuter des processus indépendamment de leurs sessions de connexion. Voir la description de enable-linger dans loginctl(1).

Notez que définir KillUserProcesses=oui cassera des outils comme screen(1) et tmux(1), sauf s'ils sont déplacés hors de la portée de la session. Voir l'exemple dans systemd-run(1).

KillOnlyUsers=, KillExcludeUsers=

Ces paramètres prennent des listes d'utilisateurs séparées par des espaces qui remplacent le paramètre KillUserProcesses=. Un nom d'utilisateur peut être ajouté à KillExcludeUsers= pour exclure les processus dans les portées de session de cet utilisateur d'être tués même si KillUserProcesses=oui est défini. Si KillExcludeUsers= n'est pas défini, l'utilisateur "root" est exclu par défaut. KillExcludeUsers= peut être défini sur une valeur vide pour remplacer cette valeur par défaut. Si un utilisateur n'est pas exclu, KillOnlyUsers= est vérifié ensuite. Si ce paramètre est spécifié, seuls les processus dans les portées de session de ces utilisateurs seront tués. Sinon, les utilisateurs sont soumis au paramètre KillUserProcesses=oui.

IdleAction=

Configure l'action à entreprendre lorsque le système est inactif. Prend l'une des valeurs suivantes : "ignore", "poweroff", "reboot", "halt", "kexec", "suspend", "hibernate", "hybrid-sleep", "suspend-then-hibernate", "sleep", et "lock". Par défaut : "ignore".

Notez que cela nécessite que les sessions utilisateur signalent correctement l'état d'inactivité au système. Le système exécutera l'action après que toutes les sessions aient signalé qu'elles sont inactives, qu'aucun verrouillage d'inhibiteur d'inactivité n'est actif, et qu'ensuite, le délai configuré avec IdleActionSec= (voir ci-dessous) a expiré.

Ajouté dans la version 198.

IdleActionSec=

Configure le délai après lequel l'action configurée dans IdleAction= (voir ci-dessus) est effectuée une fois que le système est inactif.

Ajouté dans la version 198.

InhibitDelayMaxSec=

Spécifie le temps maximum pendant lequel un arrêt système ou une demande de mise en veille est retardée en raison d'un verrouillage d'inhibiteur de type "delay" actif, avant que l'inhibiteur ne soit ignoré et que l'opération ne s'exécute de toute façon. Par défaut : 5.

UserStopDelaySec=

Spécifie combien de temps l'enregistrement utilisateur et l'unité de service utilisateur par utilisateur user@.service sont conservés après qu'un utilisateur se soit complètement déconnecté. S'il est défini sur zéro, le service utilisateur est terminé immédiatement lorsque la dernière session de l'utilisateur a pris fin. Si cette option est configurée sur une valeur non nulle, les cycles de déconnexion/connexion rapides sont accélérés, car le gestionnaire de services de l'utilisateur n'est pas constamment redémarré. SleepOperation=

Accepte une liste d'opérations de veille. Les valeurs possibles sont "suspend", "hibernate", "hybrid-sleep", et "suspend-then-hibernate". Contrôle les opérations de veille candidates pour l'action "sleep". Lorsque l'action "sleep" est effectuée, les opérations de veille spécifiées sont vérifiées dans un ordre fixe ("suspend-then-hibernate" → "hybrid-sleep" → "suspend" → "hibernate"), et la première prise en charge par la machine est utilisée pour mettre le système en veille. Par défaut, "suspend-then-hibernate suspend hibernate".

Ajouté dans la version 256.

HandlePowerKey=, HandlePowerKeyLongPress=, HandleRebootKey=, HandleRebootKeyLongPress=, HandleSuspendKey=, HandleSuspendKeyLongPress=, HandleHibernateKey=, HandleHibernateKeyLongPress=, HandleLidSwitch=, HandleLidSwitchExternalPower=, HandleLidSwitchDocked=, HandleSecureAttentionKey=

Contrôle la façon dont logind doit gérer les touches d'alimentation, de redémarrage et de veille du système, ainsi que le commutateur de fermeture du capot pour déclencher des actions telles que l'arrêt du système, le redémarrage ou la suspension. Peut être l'une des valeurs suivantes : "ignore", "poweroff", "reboot", "halt", "kexec", "suspend", "hibernate", "hybrid-sleep", "suspend-then-hibernate", "sleep", "lock", "factory-reset", et "secure-attention-key". Si "ignore", systemd-logind ne gérera jamais ces touches. Si "lock", toutes les sessions en cours seront verrouillées ; sinon, l'action spécifiée sera effectuée pour l'événement respectif. Seuls les périphériques d'entrée portant la balise udev "power-switch" seront surveillés pour les événements de touche/commutateur de capot.

HandlePowerKey= par défaut à "poweroff", HandleRebootKey= par défaut à "reboot", HandleSuspendKey= par défaut à "suspend", HandleHibernateKey= par défaut à "hibernate", HandlePowerKeyLongPress= par défaut à "ignore", HandleRebootKeyLongPress= par défaut à "poweroff", HandleSuspendKeyLongPress= par défaut à "hibernate", HandleHibernateKeyLongPress= par défaut à "ignore". HandleLidSwitch= par défaut à "suspend". HandleLidSwitchExternalPower= est complètement ignoré par défaut (pour la compatibilité ascendante) — une valeur explicite doit être définie avant qu'il ne soit utilisé pour déterminer le comportement. HandleLidSwitchDocked= par défaut à "ignore". Si le système est inséré dans une station d'accueil, ou si plus d'un écran est connecté, l'action spécifiée par HandleLidSwitchDocked= se produit ; si le système est alimenté par courant externe, l'action (le cas échéant) spécifiée par HandleLidSwitchExternalPower= se produit ; sinon, l'action HandleLidSwitch= se produit. HandleSecureAttentionKey= par défaut à "secure-attention-key"

Une application différente peut désactiver la gestion par logind des touches d'alimentation et de veille du système ainsi que du commutateur de capot en prenant un verrou d'inhibiteur de bas niveau ("handle-power-key", "handle-suspend-key", "handle-hibernate-key", "handle-lid-switch", "handle-reboot-key"). Ceci est le plus souvent utilisé par les environnements de bureau graphiques pour reprendre la gestion de la suspension et de la mise en veille prolongée, et pour utiliser leurs propres mécanismes de configuration. Si un verrou d'inhibiteur de bas niveau est pris, logind n'effectuera aucune action lorsque cette touche ou ce commutateur est déclenché et que les paramètres Handle*= sont non pertinents, à l'exception de HandleSecureAttentionKey=, qui est toujours géré depuis son ajout dans la version 257.

Ajouté dans la version 184.

PowerKeyIgnoreInhibited=, SuspendKeyIgnoreInhibited=, HibernateKeyIgnoreInhibited=, LidSwitchIgnoreInhibited=, RebootKeyIgnoreInhibited=

Contrôle si les actions que systemd-logind entreprend lorsque les touches d'alimentation, de redémarrage et de veille, ainsi que le commutateur de capot sont déclenchés, sont soumises à des verrous d'inhibiteur de haut niveau ("shutdown", "reboot", "sleep", "idle"). Les verrous d'inhibiteur de bas niveau ("handle-power-key", "handle-suspend-key", "handle-hibernate-key", "handle-lid-switch", "handle-reboot-key"), sont toujours respectés, quelle que soit cette paramètre.

Ces paramètres acceptent des arguments booléens. Si "no", les verrous d'inhibiteur pris par les applications sont respectés. Si "yes", les verrous d'inhibiteur "shutdown", "reboot" "sleep", et "idle" sont ignorés. PowerKeyIgnoreInhibited=, SuspendKeyIgnoreInhibited=, HibernateKeyIgnoreInhibited= et RebootKeyIgnoreInhibited= par défaut à "no". LidSwitchIgnoreInhibited= par défaut à "yes". Cela signifie que lorsque systemd-logind gère les événements par lui-même (aucun verrou d'inhibiteur de bas niveau n'est pris par une autre application), le commutateur de capot ne respecte pas les bloqueurs de suspension par défaut, mais les touches d'alimentation et de veille le font.

Ajouté dans la version 190.

HoldoffTimeoutSec=

Spécifie une période de temps après le démarrage du système ou la reprise du système pendant laquelle systemd attend avant de réagir aux événements du capot. Ceci est requis pour que le système détecte correctement les périphériques connectés à chaud afin que systemd puisse ignorer les événements du capot si des moniteurs externes ou des stations d'accueil sont connectés. Si défini sur 0, systemd réagira toujours immédiatement, potentiellement avant que le noyau n'ait complètement interrogé tous les périphériques connectés à chaud. Ceci est sûr, tant que vous ne vous souciez pas que systemd tienne compte des périphériques qui ont été branchés ou débranchés pendant que le système était éteint. Par défaut, 30s.

Ajouté dans la version 220.

RuntimeDirectorySize=

Définit la limite de taille du répertoire d'exécution $XDG_RUNTIME_DIR pour chaque utilisateur qui se connecte. Accepte une taille en octets, éventuellement suffixée des suffixes habituels K, G, M et T, à la base 1024 (IEC). Alternativement, un pourcentage numérique suffixé par "%" peut être spécifié, ce qui définit la limite de taille par rapport à la quantité de RAM physique. Par défaut, 10%. Notez qu'il ne s'agit que d'une limite de sécurité. Comme chaque répertoire d'exécution est un système de fichiers tmpfs, il ne consommera que la mémoire nécessaire.

Ajouté dans la version 211.

RuntimeDirectoryInodesMax=

Définit la limite du nombre d'inodes pour le répertoire d'exécution $XDG_RUNTIME_DIR pour chaque utilisateur qui se connecte. Accepte un nombre, éventuellement suffixé des suffixes habituels K, G, M et T, à la base 1024 (IEC). Par défaut, la taille de RuntimeDirectorySize= divisée par 4096. Notez qu'il ne s'agit que d'une limite de sécurité. Comme chaque répertoire d'exécution est un système de fichiers tmpfs, il ne consommera que la mémoire nécessaire.

Ajouté dans la version 246.

InhibitorsMax=

Contrôle le nombre maximum d'inhibiteurs simultanés à autoriser. Par défaut, 8192 (8K).

Ajouté dans la version 230.

SessionsMax=

Contrôle le nombre maximum de sessions utilisateur simultanées à gérer. Par défaut, 8192 (8K). Selon la façon dont le module pam_systemd.so est inclus dans la configuration de la pile PAM, d'autres sessions de connexion seront soit refusées, soit autorisées mais non suivies par systemd-logind.

Ajouté dans la version 230.

RemoveIPC=

Contrôle si les objets IPC System V et POSIX appartenant à l'utilisateur doivent être supprimés lorsque l'utilisateur se déconnecte complètement. Accepte un argument booléen. Si activé, l'utilisateur ne pourra pas consommer de ressources IPC après la fin de la dernière session de l'utilisateur. Cela couvre les sémaphores, la mémoire partagée et les files d'attente de messages System V, ainsi que la mémoire partagée et les files d'attente de messages POSIX. Notez que les objets IPC de l'utilisateur root et des autres utilisateurs système sont exclus de l'effet de ce paramètre. Par défaut, "yes".

Ajouté dans la version 212.

StopIdleSessionSec=

Spécifie un délai en secondes, ou une durée après laquelle systemd-logind vérifie l'état d'inactivité de toutes les sessions. Toute session inactive pendant plus longtemps que le délai d'attente sera arrêtée. Notez que cette option ne s'applique pas aux sessions "greeter" ou "lock-screen". Par défaut, "infinity" (systemd-logind ne vérifie pas l'état d'inactivité des sessions). Pour plus de détails sur la syntaxe des durées, voir systemd.time(7).

Ajouté dans la version 252.

DesignatedMaintenanceTime=

Spécifie un événement de calendrier par défaut pour les arrêts programmés. Ainsi, lorsque vous utilisez par exemple la commande shutdown -r pour redémarrer le système sans spécifier de délai, logind utiliserait l'événement de calendrier configuré à la place. Pour plus de détails sur la syntaxe des événements de calendrier, voir systemd.time(7).

Ajouté dans la version 257.

WallMessages=

Contrôle si les messages wall(1) doivent être envoyés aux terminaux de tous les utilisateurs actuellement connectés lors d'un arrêt ou d'un redémarrage. Par défaut, "yes", et peut être modifié à la volée via les propriétés DBus "EnableWallMessages" et "WallMessagePrefix".

Ajouté dans la version 258.
