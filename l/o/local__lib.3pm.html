local::lib(3) Documentation Perl fournie par l'utilisateur local::lib(3)

NOM

local::lib - crée et utilise une bibliothèque locale (lib/) pour les modules Perl avec PERL5LIB

SYNTAXE

Dans le code -

use local::lib; # configure une bibliothèque locale dans ~/perl5
use local::lib '~/foo'; # idem, mais dans ~/foo
# Ou...
use FindBin;
use local::lib "$FindBin::Bin/../support";  # bibliothèque de support locale à l'application

Depuis le shell -

# Installe LWP et ses dépendances manquantes dans le répertoire '~/perl5'
perl -MCPAN -Mlocal::lib -e 'CPAN::install(LWP)'
# Imprime simplement des commandes shell utiles
$ perl -Mlocal::lib
PERL_MB_OPT='--install_base /home/nom_utilisateur/perl5'; export PERL_MB_OPT;
PERL_MM_OPT='INSTALL_BASE=/home/nom_utilisateur/perl5'; export PERL_MM_OPT;
PERL5LIB="/home/nom_utilisateur/perl5/lib/perl5"; export PERL5LIB;
PATH="/home/nom_utilisateur/perl5/bin:$PATH"; export PATH;
PERL_LOCAL_LIB_ROOT="/home/nom_utilisateur/perl5:$PERL_LOCAL_LIB_ROOT"; export PERL_LOCAL_LIB_ROOT;

Depuis un fichier .bash_profile ou .bashrc -

eval "$(perl -I$HOME/perl5/lib/perl5 -Mlocal::lib)"

La technique d'amorçage

Une méthode typique pour installer local::lib est ce qu'on appelle la technique d'"amorçage". Vous devriez faire cela si votre administrateur système n'a pas déjà installé local::lib. Dans ce cas, vous devrez installer local::lib dans votre répertoire personnel.

Même si vous avez des privilèges administratifs, vous voudrez toujours configurer vos variables d'environnement, comme expliqué à l'étape 4. Sans cela, vous continueriez à installer les modules dans l'installation CPAN du système et vos scripts Perl n'utiliseraient pas le chemin lib/ que vous avez amorcé avec local::lib.

Par défaut, local::lib s'installe lui-même et les modules CPAN dans ~/perl5.

Les utilisateurs Windows doivent également consulter "Différences lors de l'utilisation de ce module sous Win32".

1.
Téléchargez et décompressez l'archive tar de local::lib depuis CPAN (recherchez "Download" sur la page CPAN concernant local::lib). Faites cela en tant qu'utilisateur ordinaire, pas en tant que root ou administrateur. Décompressez le fichier dans votre répertoire personnel ou dans tout autre emplacement pratique.
2.
Exécutez ceci : 
perl Makefile.PL --bootstrap

Si le système vous demande s'il doit configurer automatiquement autant que possible, vous répondriez généralement par oui.

3.
Exécutez ceci : (local::lib suppose que vous avez make installé sur votre système) 
make test && make install
4.
Nous devons maintenant configurer les variables d'environnement appropriées, afin que Perl commence à utiliser notre répertoire lib/ nouvellement généré. Si vous utilisez bash ou tout autre shell Bourne, vous pouvez l'ajouter à votre script de démarrage de shell de cette manière : 
echo 'eval "$(perl -I$HOME/perl5/lib/perl5 -Mlocal::lib)"' >>~/.bashrc

Si vous utilisez le shell C, vous pouvez le faire comme suit :

% echo $SHELL
/bin/csh
$ echo 'eval `perl -I$HOME/perl5/lib/perl5 -Mlocal::lib`' >> ~/.cshrc

Après avoir écrit votre fichier de configuration de shell, assurez-vous de le relire pour intégrer les paramètres modifiés dans l'environnement de votre shell actuel. Les shells Bourne utilisent ". ~/.bashrc" pour cela, tandis que les shells C utilisent "source ~/.cshrc".

Amorçage dans un répertoire alternatif

Afin d'installer local::lib dans un répertoire autre que celui par défaut, vous devez spécifier le nom du répertoire lors de l'appel à bootstrap. Ensuite, lors de la configuration des variables d'environnement, perl et local::lib doivent tous deux connaître l'emplacement du répertoire d'amorçage. Le processus de configuration ressemblerait à ceci :

perl Makefile.PL --bootstrap=~/foo
make test && make install
echo 'eval "$(perl -I$HOME/foo/lib/perl5 -Mlocal::lib=$HOME/foo)"' >>~/.bashrc
. ~/.bashrc

Autres options d'amorçage

Si vous êtes sur une machine lente, ou si vous opérez sous des limitations draconiennes d'espace disque, vous pouvez désactiver la génération automatique des pages de manuel (manpages) à partir de POD lors de l'installation de modules en utilisant l'argument "--no-manpages" lors de l'amorçage :

perl Makefile.PL --bootstrap --no-manpages

Pour éviter de faire plusieurs amorçages pour plusieurs environnements de modules Perl sur le même compte, par exemple si vous l'utilisez pour plusieurs applications déployées indépendamment, vous pouvez utiliser une installation local::lib amorcée pour installer des modules dans différents répertoires directement comme ceci :

cd ~/mondossier1
perl -Mlocal::lib=./
eval $(perl -Mlocal::lib=./)  ### Pour configurer l'environnement pour ce shell uniquement
printenv                      ### Vous verrez que ~/mondossier1 est dans PERL5LIB
perl -MCPAN -e install ...    ### tous les modules que vous voulez
cd ../mondossier2
... RECOMMENCER ...

Si vous utilisez .bashrc pour activer automatiquement un local::lib, le local::lib sera réactivé dans tous les sous-shells utilisés, substituant les ajustements que vous auriez pu faire dans le shell parent. Pour éviter cela, vous pouvez initialiser le local::lib dans .bash_profile plutôt que dans .bashrc, ou protéger l'invocation de local::lib avec une vérification $SHLVL :

[ $SHLVL -eq 1 ] && eval "$(perl -I$HOME/perl5/lib/perl5 -Mlocal::lib)"

Si vous travaillez avec plusieurs environnements "local::lib", vous voudrez peut-être en retirer certains de l'environnement actuel sans perturber les autres. Vous pouvez désactiver un environnement comme ceci (en utilisant sh bourne) :

eval $(perl -Mlocal::lib=--deactivate,~/chemin)

ce qui générera et exécutera les commandes nécessaires pour supprimer "~/chemin" de vos différents chemins de recherche. Quel que soit l'environnement qui a été activé **le plus récemment**, il restera la cible pour l'installation des modules. C'est-à-dire, si vous activez "~/chemin_A" puis que vous activez "~/chemin_B", les nouveaux modules que vous installerez iront dans "~/chemin_B". Si vous désactivez "~/chemin_B", les modules seront installés dans "~/cheminA" -- mais si vous désactivez "~/chemin_A", ils seront toujours installés dans "~/cheminB" car pathB a été activé plus tard.

Vous pouvez également demander à "local::lib" de se retirer complètement de l'environnement du shell actuel avec l'option "--deactivate-all". Pour plusieurs environnements pour plusieurs applications, vous devrez peut-être inclure une version modifiée des instructions "use FindBin" dans l'exemple "Dans le code" ci-dessus. Si vous avez fait quelque chose comme ce qui précède, vous avez un ensemble de modules Perl dans "~/mondossier1/lib". Si vous avez un script dans "~/mondossier1/scripts/monscript.pl", vous devez lui indiquer où trouver les modules que vous avez installés pour lui dans "~/mondossier1/lib".

Dans "~/mondossier1/scripts/monscript.pl" :

use strict;
use warnings;
use local::lib "$FindBin::Bin/..";  ### pointe vers ~/mondossier1 et local::lib trouve lib
use lib "$FindBin::Bin/../lib";     ### pointe vers ~/mondossier1/lib

Mettez ceci avant tout bloc BEGIN { ... } qui requiert les modules que vous avez installés.

Différences lors de l'utilisation de ce module sous Win32

Pour configurer les variables d'environnement appropriées pour votre session actuelle de "CMD.exe", vous pouvez utiliser ceci :

C:\>perl -Mlocal::lib
set PERL_MB_OPT=--install_base C:\DOCUME~1\ADMINI~1\perl5
set PERL_MM_OPT=INSTALL_BASE=C:\DOCUME~1\ADMINI~1\perl5
set PERL5LIB=C:\DOCUME~1\ADMINI~1\perl5\lib\perl5
set PATH=C:\DOCUME~1\ADMINI~1\perl5\bin;%PATH%
### Pour configurer l'environnement pour ce shell uniquement
C:\>perl -Mlocal::lib > %TEMP%\tmp.bat && %TEMP%\tmp.bat && del %TEMP%\tmp.bat
### au lieu de $(perl -Mlocal::lib=./)

Si vous voulez que les entrées d'environnement persistent, vous devrez les ajouter vous-même dans l'applet Système du Panneau de configuration ou utiliser App::local::lib::Win32Helper.

Le "~" est traduit en répertoire de profil de l'utilisateur (le répertoire nommé pour l'utilisateur sous "Documents and Settings" (Windows XP ou antérieur) ou "Users" (Windows Vista ou ultérieur)) à moins que $ENV{HOME} n'existe. Après cela, le répertoire personnel est traduit en nom court (ce qui signifie que le répertoire doit exister) et les sous-répertoires sont créés.

local::lib







NAME


local::lib - self-contained Perl installation base







SYNOPSIS


  use local::lib;
  # Or to activate a specific directory:
  use local::lib '/path/to/installation';
  # Or to activate multiple directories:
  use local::lib '/path/to/installation', '/another/path';
  # Or to activate without creating directories:
  use local::lib no_create => 1;
  # Or to activate a specific directory without creating:
  use local::lib '/path/to/installation', no_create => 1;
  # Or to activate a directory with extra env vars:
  use local::lib '/path/to/installation', extra => {
    PERL_MM_OPT => "-e 'make install DESTDIR=...'";
  };
  # Or to build your own environment variables:
  my $ll = local::lib->new(...);
  # Or to activate directories from an existing object:
  my $ll_activated = $ll->activate('/path/to/installation');
  # Or to get the shell command to set up the environment:
  print $ll->environment_vars_string;








DESCRIPTION


This module allows you to easily install Perl modules into a
    local directory instead of the system's global Perl installation. This is
    useful for Perl installations shared between multiple users, or when you
    don't have write access to the global Perl installation.


When you activate a local::lib installation,
    it modifies @INC,
    PERL5LIB, PATH,
    PERL_MM_OPT, and
    PERL_MB_OPT so that Perl and its associated tools
    will find and use the modules installed in your local directory.




PATH RESOLUTION FUNCTIONS


The local::lib module provides several
    functions to resolve paths. These are usually called internally, but can
    also be called directly.




resolve_empty_path



  
Arguments:
    $path

  

  
Return value:
    $home_or_path

  




If the given path is empty, returns the user's home directory.
    Otherwise, returns the path unchanged.






resolve_home_path



  
Arguments:
    $path

  

  
Return value:
    $home_path

  




Attempts to find the user's home directory. If no definite answer
    is available, throws an exception.






resolve_relative_path



  
Arguments:
    $path

  

  
Return value:
    $absolute_path

  




Translates the given path into an absolute path.






resolve_path



  
Arguments:
    $path

  

  
Return value:
    $absolute_path

  




Calls the following in a pipeline, passing the result from the
    previous to the next, in an attempt to find where to configure the
    environment for a local library installation:
    "resolve_empty_path", "resolve_home_path",
    "resolve_relative_path". Passes the given path argument to
    "resolve_empty_path" which then returns a result that is passed to
    "resolve_home_path", which then has its result passed to
    "resolve_relative_path". The result of this final call is returned
    from "resolve_path".











OBJECT INTERFACE




new



  
Arguments:
    %attributes

  

  
Return value:
    $local_lib

  




Constructs a new "local::lib"
    object, representing the current state of @INC and
    the relevant environment variables.









ATTRIBUTES




roots


An arrayref representing active
    "local::lib" directories.






inc


An arrayref representing @INC.






libs


An arrayref representing the PERL5LIB environment variable.






bins


An arrayref representing the PATH environment variable.






extra


A hashref of extra environment variables (e.g.
    "PERL_MM_OPT" and
    "PERL_MB_OPT")






no_create


If set, "local::lib" will not
    try to create directories when activating them.

clone



  
Arguments:
    %attributes

    $local_lib

activate



  
Arguments:
    $path

A WARNING ABOUT UNINST=1


Be careful about using local::lib in combination with "make
    install UNINST=1". The idea of this feature is that will uninstall an
    old version of a module before installing a new one. However it lacks a
    safety check that the old version and the new version will go in the same
    directory. Used in combination with local::lib, you can potentially delete a
    globally accessible version of a module while installing the new version in
    a local place. Only combine "make install UNINST=1" and local::lib
    if you understand these possible consequences.







LIMITATIONS


    
  
  • Directory names with spaces in them are not well supported by the perl
      toolchain and the programs it uses. Pure-perl distributions should support
      spaces, but problems are more likely with dists that require compilation.
      A workaround you can do is moving your local::lib to a directory with
      spaces after you installed all modules inside your local::lib
      bootstrap. But be aware that you can't update or install CPAN modules
      after the move.
    • 
  
  • Rather basic shell detection. Right now anything with csh in its name is
      assumed to be a C shell or something compatible, and everything else is
      assumed to be Bourne, except on Win32 systems. If the
      "SHELL" environment variable is not set,
      a Bourne-compatible shell is assumed.
    • 
  
  • Kills any existing PERL_MM_OPT or PERL_MB_OPT.
    • 
  
  • Should probably auto-fixup CPAN config if not already done.
    • 
  
  • On VMS and MacOS Classic (pre-OS X), local::lib loads File::Spec. This
      means any File::Spec version installed in the local::lib will be ignored
      by scripts using local::lib. A workaround for this is using
      "use lib
      "$local_lib/lib/perl5";" instead of using
      "local::lib" directly.
    • 
  
  • Conflicts with ExtUtils::MakeMaker's
      "PREFIX" option.
      "local::lib" uses the
      "INSTALL_BASE" option, as it has more
      predictable and sane behavior. If something attempts to use the
      "PREFIX" option when running a
      Makefile.PL, ExtUtils::MakeMaker will refuse to run, as the two
      options conflict. This can be worked around by temporarily unsetting the
      "PERL_MM_OPT" environment variable.
    • 
  
  • Conflicts with Module::Build's
      "--prefix" option. Similar to the
      previous limitation, but any "--prefix"
      option specified will be ignored. This can be worked around by temporarily
      unsetting the "PERL_MB_OPT" environment
      variable.
    • 



Patches very much welcome for any of the above.



  
•

  
On Win32 systems, does not have a way to write the created environment
      variables to the registry, so that they can persist through a reboot.









TROUBLESHOOTING


If you've configured local::lib to install CPAN modules somewhere
    in to your home directory, and at some point later you try to install a
    module with "cpan -i
    Foo::Bar", but it fails with an error like:
    "Warning: You do not have
    permissions to install into
    /usr/lib64/perl5/site_perl/5.8.8/x86_64-linux at
    /usr/lib64/perl5/5.8.8



/Foo/Bar.pm" et enfouie
    dans le journal d'installation se trouve une erreur indiquant
    "'INSTALL_BASE' is not a known MakeMaker parameter
    name", alors vous avez d'une manière ou d'une autre perdu votre module
    ExtUtils::MakeMaker mis à jour.


Pour remédier à cette situation, relancez la procédure d'amorçage
    documentée ci-dessus.


Ensuite, exécutez "rm -r
    ~/.cpan/build/Foo-Bar*"


Enfin, relancez "cpan -i
    Foo::Bar" et cela devrait s'installer sans problème.
