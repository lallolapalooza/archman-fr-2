load(n)

Paquet: tcl

Licences: TCL

load(n) Commandes intégrées Tcl load(n)

NOM

load - Charger du code machine et initialiser de nouvelles commandes

SYNOPSIS

load ?-global? ?-lazy? ?--? nom_fichier
load ?-global? ?-lazy? ?--? nom_fichier préfixe
load ?-global? ?-lazy? ?--? nom_fichier préfixe interpréteur

DESCRIPTION

Cette commande charge du code binaire depuis un fichier dans l'espace d'adressage de l'application et appelle une procédure d'initialisation dans la bibliothèque pour l'intégrer à un interpréteur. nom_fichier est le nom du fichier contenant le code ; sa forme exacte varie d'un système à l'autre, mais sur la plupart des systèmes, il s'agit d'une bibliothèque partagée, telle qu'un fichier .so sous Solaris ou une DLL sous Windows. préfixe est utilisé pour calculer le nom d'une procédure d'initialisation. interpréteur est le nom de chemin de l'interpréteur dans lequel charger la bibliothèque (voir l'entrée du manuel interp pour les détails) ; si interpréteur est omis, il prend par défaut l'interpréteur dans lequel la commande load a été invoquée.

Une fois le fichier chargé dans l'espace d'adressage de l'application, l'une des deux procédures d'initialisation sera appelée dans le nouveau code. Typiquement, la procédure d'initialisation ajoutera de nouvelles commandes à un interpréteur Tcl. Le nom de la procédure d'initialisation est déterminé par préfixe et par le fait que l'interpréteur cible soit sécurisé ou non. Pour les interpréteurs normaux, le nom de la procédure d'initialisation aura la forme pfx_Init, où pfx est identique à préfixe, sauf que la première lettre est convertie en majuscule et toutes les autres lettres en minuscule. Par exemple, si préfixe est foo ou FOo, le nom de la procédure d'initialisation sera Foo_Init.

Si l'interpréteur cible est un interpréteur sécurisé, alors le nom de la procédure d'initialisation sera pfx_SafeInit au lieu de pfx_Init. La fonction pfx_SafeInit doit être écrite avec soin, de manière à initialiser l'interpréteur sécurisé uniquement avec des fonctionnalités partielles fournies par la bibliothèque qui sont sûres à utiliser par du code non fiable. Pour plus d'informations sur Safe-Tcl, voir l'entrée du manuel safe.

La procédure d'initialisation doit correspondre au prototype suivant :

typedef int Tcl_PackageInitProc(
        Tcl_Interp *interp);

L'argument interp identifie l'interpréteur dans lequel la bibliothèque doit être chargée. La procédure d'initialisation doit retourner TCL_OK ou TCL_ERROR pour indiquer si elle s'est terminée avec succès ou non ; en cas d'erreur, elle doit définir le résultat de l'interpréteur pour qu'il pointe vers un message d'erreur. Le résultat de la commande load sera le résultat retourné par la procédure d'initialisation.

Le chargement effectif d'un fichier ne sera effectué qu'une seule fois pour chaque nom_fichier dans une application. Si un nom_fichier donné est chargé dans plusieurs interpréteurs, alors le premier load chargera le code et appellera la procédure d'initialisation ; les appels load suivants appelleront la procédure d'initialisation sans recharger le code. Pour les versions de Tcl antérieures à 8.5, il n'est pas possible de décharger ou recharger une bibliothèque. À partir de la version 8.5 cependant, la commande unload permet de décharger les bibliothèques chargées avec load, pour les bibliothèques qui sont conscientes du mécanisme de déchargement de Tcl.

La commande load prend également en charge les bibliothèques qui sont liées statiquement à l'application, si ces bibliothèques ont été enregistrées en appelant la procédure Tcl_StaticPackage. Si nom_fichier est une chaîne vide, alors préfixe doit être spécifié.

Si préfixe est omis ou spécifié comme une chaîne vide, Tcl essaie de deviner le préfixe. Cela peut être fait différemment selon les plates-formes. La supposition par défaut, utilisée sur la plupart des plates-formes UNIX, consiste à prendre le dernier élément de nom_fichier, à supprimer les trois premiers caractères s'ils sont lib, et à utiliser les caractères alphabétiques et les soulignements suivants, convertis en casse de titre comme préfixe. Par exemple, la commande load libxyz4.2.so utilise le préfixe Xyz et la commande load bin/last.so {} utilise le préfixe Last.

Si nom_fichier est une chaîne vide, alors préfixe doit être spécifié. La commande load recherche d'abord une bibliothèque chargée statiquement (une qui a été enregistrée en appelant la procédure Tcl_StaticPackage) sous ce nom ; si elle en trouve une, elle l'utilise. Sinon, la commande load recherche une bibliothèque chargée dynamiquement sous ce nom, et l'utilise si elle est trouvée. Si plusieurs fichiers différents ont été chargés avec différentes versions de la bibliothèque, Tcl choisit le fichier qui a été chargé en premier.

Si -global est spécifié avant le nom du fichier, tous les symboles trouvés dans la bibliothèque partagée sont exportés pour une utilisation globale par d'autres bibliothèques. L'option -lazy retarde le chargement réel des symboles jusqu'à leur première utilisation effective. Les options peuvent être abrégées. L'option -- indique la fin des options, et doit être utilisée si vous souhaitez utiliser un nom de fichier qui commence par - et que vous fournissez un préfixe à la commande load.

Sur les plates-formes qui ne prennent pas en charge les options -global ou -lazy, les options existent toujours mais n'ont aucun effet. Notez que l'utilisation des options -global ou -lazy peut entraîner des plantages dans votre application plus tard (en cas de conflits de symboles ou de symboles manquants), qui ne peuvent pas être détectés lors du load. Utilisez donc cela uniquement lorsque vous savez ce que vous faites, vous n'obtiendrez pas de message d'erreur agréable lorsque quelque chose ne va pas avec la bibliothèque chargée.

PROBLÈMES DE PORTABILITÉ

Windows     
Lorsqu'un chargement échoue avec une erreur de type "bibliothèque introuvable", il est également possible qu'une bibliothèque dépendante n'ait pas été trouvée. Pour voir les bibliothèques dépendantes, tapez “dumpbin -imports <nom_dll>” dans une console DOS pour voir ce que la bibliothèque doit importer. Lors du chargement d'une DLL dans le répertoire courant, Windows ignorera “./” comme spécificateur de chemin et utilisera une heuristique de recherche pour trouver la DLL à la place. Pour éviter cela, chargez la DLL avec :
load [file join [pwd] ma_lib.DLL]

BOGUES

Si le même fichier est chargé par différents nom_fichier, il sera chargé dans l'espace d'adressage du processus plusieurs fois. Le comportement de ceci varie d'un système à l'autre (certains systèmes peuvent détecter les chargements redondants, d'autres non).

EXEMPLE

L'exemple suivant est une extension minimale :

#include <tcl.h>
#include <stdio.h>
static int fooCmd(void *clientData,
        Tcl_Interp *interp, int objc, Tcl_Obj *const objv[]) {
    printf("appelé avec %d arguments\n", objc);
    return TCL_OK;
}
int Foo_Init(Tcl_Interp *interp) {
    if (Tcl_InitStubs(interp, "8.1", 0) == NULL) {
	return TCL_ERROR;
    }
    printf("création de la commande foo");
    Tcl_CreateObjCommand(interp, "foo", fooCmd, NULL, NULL);
    return TCL_OK;
}

Lorsqu'elle est intégrée dans une bibliothèque partagée/dynamique avec un nom approprié (par exemple, foo.dll sous Windows, libfoo.so sous Solaris et Linux), elle peut ensuite être chargée dans Tcl avec ce qui suit :

# Charger l'extension
switch $tcl_platform(platform) {
    windows {
        load [file join [pwd] foo.dll]
    }
    unix {
        load [file join [pwd] libfoo[info sharedlibextension]]
    }
}
# Exécuter maintenant la commande définie par l'extension
foo
