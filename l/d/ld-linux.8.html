ld.so(8) Manuel de l'administrateur système ld.so(8)

NOM

ld.so, ld-linux.so - editeur de liens/chargeur dynamique

SYNTAXE

L'éditeur de liens dynamique peut être exécuté soit indirectement en lançant un programme ou un objet partagé dynamiquement lié (auquel cas aucune option de ligne de commande ne peut être passée à l'éditeur de liens et, dans le cas ELF, l'éditeur de liens dynamique stocké dans la section .interp du programme est exécuté) soit directement en lançant :

/lib/ld-linux.so.* [OPTIONS] [PROGRAMME [ARGUMENTS]]

DESCRIPTION

Les programmes ld.so et ld-linux.so* trouvent et chargent les objets partagés (bibliothèques partagées) nécessaires à un programme, préparent le programme pour l'exécution, puis le lancent.

Les binaires Linux nécessitent une liaison dynamique (liaison au moment de l'exécution) à moins que l'option -static n'ait été donnée à ld(1) lors de la compilation.

Le programme ld.so gère les binaires a.out, un format binaire utilisé il y a longtemps. Le programme ld-linux.so* (/lib/ld-linux.so.1 pour libc5, /lib/ld-linux.so.2 pour glibc2) gère les binaires au format ELF plus moderne. Les deux programmes ont le même comportement et utilisent les mêmes fichiers et programmes de support (ldd(1), ldconfig(8), et /etc/ld.so.conf).

Lors de la résolution des dépendances des objets partagés, l'éditeur de liens dynamique inspecte d'abord chaque chaîne de dépendance pour voir si elle contient une barre oblique (cela peut se produire si un chemin d'objet partagé contenant des barres obliques a été spécifié au moment de la liaison). Si une barre oblique est trouvée, la chaîne de dépendance est interprétée comme un chemin (relatif ou absolu), et l'objet partagé est chargé en utilisant ce chemin.

Si une dépendance d'objet partagé ne contient pas de barre oblique, elle est recherchée dans l'ordre suivant :

(1)
En utilisant les répertoires spécifiés dans l'attribut de section dynamique DT_RPATH du binaire s'il est présent et que l'attribut DT_RUNPATH n'existe pas.
(2)
En utilisant la variable d'environnement LD_LIBRARY_PATH, à moins que l'exécutable ne soit exécuté en mode sécurisé (voir ci-dessous), auquel cas cette variable est ignorée.
(3)
En utilisant les répertoires spécifiés dans l'attribut de section dynamique DT_RUNPATH du binaire s'il est présent. Ces répertoires ne sont recherchés que pour trouver les objets requis par les entrées DT_NEEDED (dépendances directes) et ne s'appliquent pas aux enfants de ces objets, qui doivent eux- mêmes avoir leurs propres entrées DT_RUNPATH. Ceci est différent de DT_RPATH, qui s'applique à la recherche de tous les enfants dans l'arbre de dépendances.
(4)
À partir du fichier cache /etc/ld.so.cache, qui contient une liste compilée d'objets partagés candidats trouvés précédemment dans le chemin de bibliothèques augmenté. Si, toutefois, le binaire a été lié avec l'option de l'éditeur de liens -z nodefaultlib, les objets partagés dans les chemins par défaut sont ignorés. Les objets partagés installés dans les répertoires de capacités matérielles (voir ci-dessous) sont préférés aux autres objets partagés.
(5)
Dans le chemin par défaut /lib, puis /usr/lib. (Sur certaines architectures 64 bits, les chemins par défaut pour les objets partagés 64 bits sont /lib64, puis /usr/lib64.) Si le binaire a été lié avec l'option de l'éditeur de liens -z nodefaultlib, cette étape est ignorée.

Jetons de chaîne dynamiques

Dans plusieurs endroits, l'éditeur de liens dynamique développe des jetons de chaîne dynamiques :

•
Dans les variables d'environnement LD_LIBRARY_PATH, LD_PRELOAD, et LD_AUDIT,
•
à l'intérieur des valeurs des balises de section dynamique DT_NEEDED, DT_RPATH, DT_RUNPATH, DT_AUDIT, et DT_DEPAUDIT des binaires ELF,
•
dans les arguments des options de ligne de commande de ld.so --audit, --library-path, et --preload (voir ci- dessous), et
•
dans les arguments de nom de fichier des fonctions dlopen(3) et dlmopen(3).

Les jetons substitués sont les suivants :

$ORIGIN (ou équivalent ${ORIGIN})
Ceci se développe en répertorier le répertoire contenant le programme ou l'objet partagé. Ainsi, une application située dans somedir/app peut être compilée avec

gcc -Wl,-rpath,'$ORIGIN/../lib'

pour qu'elle trouve un objet partagé associé dans somedir/lib, peu importe où somedir se trouve dans la hiérarchie des répertoires. Cela facilite la création d'applications "clés en main" qui n'ont pas besoin d'être installées dans des répertoires spéciaux, mais peuvent plutôt être décompressées dans n'importe quel répertoire et trouver toujours leurs propres objets partagés.
$LIB (ou équivalent ${LIB})
Ceci se développe en lib ou lib64 en fonction de l'architecture (par exemple, sur x86-64, il se développe en lib64 et sur x86-32, il se développe en lib).
$PLATFORM (ou équivalent ${PLATFORM})
Ceci se développe en une chaîne correspondant au type de processeur du système hôte (par exemple, "x86_64"). Sur certaines architectures, le noyau Linux ne fournit pas de chaîne de plateforme à l'éditeur de liens dynamique. La valeur de cette chaîne est tirée de la valeur AT_PLATFORM dans le vecteur auxiliaire (voir getauxval(3)).

Notez que les jetons de chaîne dynamiques doivent être correctement entre guillemets lorsqu'ils sont définis à partir d'un shell, afin d'empêcher leur expansion en tant que variables de shell ou d'environnement.

OPTIONS

--argv0 chaîne (depuis glibc 2.33)
Définit argv[0] à la valeur chaîne avant de lancer le programme.
--audit liste
Utilise les objets nommés dans liste comme auditeurs. Les objets de liste sont délimités par des deux-points.
--glibc-hwcaps-mask liste
Ne recherche les sous-répertoires intégrés que si dans liste.
--glibc-hwcaps-prepend liste
Recherche les sous-répertoires glibc-hwcaps dans liste.
--inhibit-cache
N'utilise pas /etc/ld.so.cache.
--library-path chemin
Utilise chemin au lieu du paramètre de la variable d'environnement LD_LIBRARY_PATH (voir ci-dessous). Les noms ORIGIN, LIB, et PLATFORM sont interprétés comme pour la variable d'environnement LD_LIBRARY_PATH.
--inhibit-rpath liste
Ignore les informations RPATH et RUNPATH dans les noms d'objets de la liste. Cette option est ignorée lors de l'exécution en mode sécurisé (voir ci-dessous). Les objets de la liste sont délimités par des deux-points ou des espaces.
--list
Liste toutes les dépendances et comment elles sont résolues.
--list-diagnostics (depuis glibc 2.33)
Affiche des informations de diagnostic système dans un format lisible par machine, telles que certaines variables internes du chargeur, le vecteur auxiliaire (voir getauxval(3)), et les variables d'environnement. Sur certaines architectures, la commande peut afficher des informations supplémentaires (comme les fonctionnalités CPU utilisées dans la sélection indirecte de fonctions GNU sur x86). --list-tunables (depuis glibc 2.33) Affiche les noms et les valeurs de tous les tunables, ainsi que les valeurs minimales et maximales autorisées.
--preload liste (depuis glibc 2.30)
Prélance les objets spécifiés dans liste. Les objets de la liste sont délimités par des deux-points ou des espaces. Les objets sont préchargés comme expliqué dans la description de la variable d'environnement LD_PRELOAD ci-dessous.
Par contraste avec LD_PRELOAD, l'option --preload offre un moyen d'effectuer un préchargement pour un seul exécutable sans affecter le préchargement effectué dans un quelconque processus enfant qui lance un nouveau programme.
--verify
Vérifie que le programme est lié dynamiquement et que cet éditeur de liens dynamique peut le gérer.

ENVIRONNEMENT

Diverses variables d'environnement influencent le fonctionnement du lieur dynamique.

Mode d'exécution sécurisé

Pour des raisons de sécurité, si le lieur dynamique détermine qu'un exécutable doit être exécuté en mode sécurisé, les effets de certaines variables d'environnement sont annulés ou modifiés, et de plus, ces variables d'environnement sont supprimées de l'environnement, de sorte que le programme ne voit même pas les définitions. Certaines de ces variables d'environnement affectent le fonctionnement du lieur dynamique lui-même et sont décrites ci-dessous. D'autres variables d'environnement traitées de cette manière incluent : GCONV_PATH, GETCONF_DIR, HOSTALIASES, LOCALDOMAIN, LD_AUDIT, LD_DEBUG, LD_DEBUG_OUTPUT, LD_DYNAMIC_WEAK, LD_HWCAP_MASK, LD_LIBRARY_PATH, LD_ORIGIN_PATH, LD_PRELOAD, LD_PROFILE, LD_SHOW_AUXV, LOCALDOMAIN, LOCPATH, MALLOC_TRACE, NIS_PATH, NLSPATH, RESOLV_HOST_CONF, RES_OPTIONS, TMPDIR, et TZDIR.

Un exécutable est exécuté en mode sécurisé si l'entrée AT_SECURE dans le vecteur auxiliaire (voir getauxval(3)) a une valeur non nulle. Cette entrée peut avoir une valeur non nulle pour diverses raisons, notamment :

•
Les identifiants utilisateur réel et effectif du processus diffèrent, ou les identifiants de groupe réel et effectif diffèrent. Cela se produit généralement à la suite de l'exécution d'un programme avec les bits set-user-ID ou set-group-ID.
•
Un processus avec un ID utilisateur non root a exécuté un exécutable qui a conféré des capacités au processus.
•
Une valeur non nulle peut avoir été définie par un module de sécurité Linux.

Variables d'environnement

Parmi les variables d'environnement les plus importantes figurent les suivantes :

LD_ASSUME_KERNEL (de glibc 2.2.3 à glibc 2.36)
Chaque objet partagé peut informer le lieur dynamique de la version minimale de l'ABI du noyau dont il a besoin. (Cette exigence est codée dans une section de note ELF visible via readelf -n sous la forme d'une section étiquetée NT_GNU_ABI_TAG.) Lors de l'exécution, le lieur dynamique détermine la version de l'ABI du noyau en cours d'exécution et rejettera le chargement des objets partagés qui spécifient des versions minimales d'ABI dépassant cette version d'ABI.
LD_ASSUME_KERNEL peut être utilisé pour amener le lieur dynamique à supposer qu'il s'exécute sur un système avec une version différente de l'ABI du noyau. Par exemple, la commande suivante amène le lieur dynamique à supposer qu'il s'exécute sous Linux 2.2.5 lors du chargement des objets partagés requis par myprog :

$ LD_ASSUME_KERNEL=2.2.5 ./myprog

Sur les systèmes qui fournissent plusieurs versions d'un objet partagé (dans différents répertoires du chemin de recherche) ayant des exigences de version d'ABI de noyau minimales différentes, LD_ASSUME_KERNEL peut être utilisé pour sélectionner la version de l'objet qui est utilisée (en fonction de l'ordre de recherche des répertoires).
Historiquement, l'utilisation la plus courante de la fonctionnalité LD_ASSUME_KERNEL était de sélectionner manuellement l'ancienne implémentation des threads POSIX LinuxThreads sur les systèmes qui fournissaient à la fois LinuxThreads et NPTL (cette dernière étant généralement par défaut sur ces systèmes) ; voir pthreads(7).
LD_BIND_NOW (depuis glibc 2.1.1)
Si elle est définie sur une chaîne non vide, oblige le lieur dynamique à résoudre tous les symboles au démarrage du programme au lieu de différer la résolution des appels de fonction au moment où ils sont référencés pour la première fois. Ceci est utile lors de l'utilisation d'un débogueur.
LD_LIBRARY_PATH
Une liste de répertoires dans lesquels rechercher les bibliothèques ELF au moment de l'exécution. Les éléments de la liste sont séparés par des deux-points ou des points-virgules, et il n'y a pas de support pour l'échappement de ces séparateurs. Un nom de répertoire de longueur nulle indique le répertoire de travail courant.
Cette variable est ignorée en mode sécurisé.
Dans les chemins spécifiés dans LD_LIBRARY_PATH, le lieur dynamique développe les jetons $ORIGIN, $LIB et $PLATFORM (ou les versions utilisant des accolades autour des noms) comme décrit ci-dessus dans Jetons de chaînes dynamiques. Ainsi, par exemple, la commande suivante amène une bibliothèque à être recherchée dans le sous-répertoire lib ou lib64 sous le répertoire contenant le programme à exécuter :

$ LD_LIBRARY_PATH='$ORIGIN/$LIB' prog

(Notez l'utilisation d'apostrophes, qui empêchent l'expansion de $ORIGIN et $LIB en tant que variables shell !)
LD_PRELOAD
Une liste d'objets partagés ELF supplémentaires, spécifiés par l'utilisateur, à charger avant tous les autres. Cette fonctionnalité peut être utilisée pour remplacer sélectivement des fonctions dans d'autres objets partagés.
Les éléments de la liste peuvent être séparés par des espaces ou des deux-points, et il n'y a pas de support pour l'échappement de ces séparateurs. Les objets sont recherchés en utilisant les règles données sous DESCRIPTION. Les objets sont recherchés et ajoutés à la carte de liens dans l'ordre de gauche à droite spécifié dans la liste.
En mode sécurisé, les noms de chemins contenant des barres obliques sont ignorés. De plus, les objets partagés ne sont préchargés que depuis les répertoires de recherche standard et uniquement s'ils ont le bit de mode set-user-ID activé (ce qui n'est pas typique).
Dans les noms spécifiés dans la liste LD_PRELOAD, le lieur dynamique comprend les jetons $ORIGIN, $LIB et $PLATFORM (ou les versions utilisant des accolades autour des noms) comme décrit ci-dessus dans Jetons de chaînes dynamiques. (Voir également la discussion sur les guillemets sous la description de LD_LIBRARY_PATH.)
Il existe diverses méthodes pour spécifier les bibliothèques à précharger, et celles-ci sont traitées dans l'ordre suivant :
(1)
La variable d'environnement LD_PRELOAD.
(2)
L'option de ligne de commande --preload lors de l'invocation directe du lieur dynamique.
(3)
Le fichier /etc/ld.so.preload (décrit ci-dessous).
LD_TRACE_LOADED_OBJECTS
Si elle est définie (sur n'importe quelle valeur), oblige le programme à lister ses dépendances dynamiques, comme s'il était exécuté par ldd(1), au lieu de s'exécuter normalement.

Ensuite, il existe de nombreuses variables plus ou moins obscures, dont beaucoup sont obsolètes ou destinées à un usage interne.

LD_AUDIT (depuis glibc 2.4)
Une liste d'objets partagés ELF spécifiés par l'utilisateur à charger avant tous les autres dans un espace de noms de lieur séparé (c'est-à-dire un espace qui n'interfère pas avec les liaisons de symboles normales qui se produiraient dans le processus). Ces objets peuvent être utilisés pour auditer le fonctionnement du lieur dynamique. Les éléments de la liste sont séparés par des deux-points, et il n'y a pas de support pour l'échappement du séparateur.
LD_AUDIT est ignoré en mode sécurisé.
Le lieur dynamique notifiera les objets partagés d'audit lors des soi-disant points de contrôle d'audit — par exemple, le chargement d'un nouvel objet partagé, la résolution d'un symbole, ou l'appel d'un symbole d'un autre objet partagé — en appelant une fonction appropriée dans l'objet partagé d'audit. Pour plus de détails, voir rtld-audit(7). L'interface d'audit est largement compatible avec celle fournie sur Solaris, comme décrit dans son Guide du lieur et des bibliothèques, au chapitre Interface d'audit du lieur d'exécution.
Dans les noms spécifiés dans la liste LD_AUDIT, le lieur dynamique comprend les jetons $ORIGIN, $LIB et $PLATFORM (ou les versions utilisant des accolades autour des noms) comme décrit ci-dessus dans Jetons de chaînes dynamiques. (Voir également la discussion sur les guillemets sous la description de LD_LIBRARY_PATH.)
Depuis glibc 2.13, en mode sécurisé, les noms de la liste d'audit contenant des barres obliques sont ignorés, et seuls les objets partagés des répertoires de recherche standard qui ont le bit de mode set-user-ID activé sont chargés.
LD_BIND_NOT (depuis glibc 2.1.95)
Si cette variable d'environnement est définie sur une chaîne non vide, ne mettez pas à jour la GOT (global offset table) et la PLT (procedure linkage table) après avoir résolu un symbole de fonction. En combinant l'utilisation de cette variable avec LD_DEBUG (avec les catégories bindings et symbols), on peut observer toutes les liaisons de fonctions d'exécution.
LD_DEBUG (depuis glibc 2.1)
Affiche des informations de débogage détaillées sur le fonctionnement du lieur dynamique. Le contenu de cette variable est une ou plusieurs des catégories suivantes, séparées par des deux-points, des virgules, ou (si la valeur est entre guillemets) des espaces :
help
Spécifier help dans la valeur de cette variable n'exécute pas le programme spécifié et affiche un message d'aide sur les catégories qui peuvent être spécifiées dans cette variable d'environnement.
all
Affiche toutes les informations de débogage (sauf statistics et unused ; voir ci-dessous).
bindings
Affiche des informations sur la définition à laquelle chaque symbole est lié.
files
Affiche la progression pour chaque fichier d'entrée.
libs
Affiche les chemins de recherche des bibliothèques.
reloc
Affiche le traitement des relocations.
scopes
Affiche les informations de portée.
statistics
Affiche les statistiques de relocation.
symboles
Affiche les chemins de recherche pour chaque recherche de symbole.
non utilisé
Détermine les DSO inutilisés.
versions
Affiche les dépendances de version.
Depuis glibc 2.3.4, LD_DEBUG est ignoré en mode d'exécution sécurisée, sauf si le fichier /etc/suid-debug existe (le contenu du fichier est sans importance).
LD_DEBUG_OUTPUT (depuis glibc 2.1)
Par défaut, la sortie de LD_DEBUG est écrite dans la sortie d'erreur standard. Si LD_DEBUG_OUTPUT est défini, alors la sortie est écrite dans le chemin d'accès spécifié par sa valeur, avec le suffixe « . » (point) suivi de l'ID du processus ajouté au chemin d'accès.
LD_DEBUG_OUTPUT est ignoré en mode d'exécution sécurisée.
LD_DYNAMIC_WEAK (depuis glibc 2.1.91)
Par défaut, lors de la recherche de bibliothèques partagées pour résoudre une référence de symbole, l'éditeur de liens dynamique résoudra la première définition qu'il trouve.
Les anciennes versions de glibc (avant glibc 2.2) avaient un comportement différent : si l'éditeur de liens trouvait un symbole faible, il s'en souvenait et continuait la recherche dans les autres bibliothèques partagées. S'il trouvait ensuite une définition forte du même symbole, il utilisait cette définition à la place. (Si aucun autre symbole n'était trouvé, l'éditeur de liens dynamique utilisait le symbole faible trouvé initialement.)
L'ancien comportement de glibc n'était pas standard. (La pratique standard est que la distinction entre symboles faibles et forts ne devrait avoir d'effet qu'au moment de l'édition des liens statique.) Dans glibc 2.2, l'éditeur de liens dynamique a été modifié pour fournir le comportement actuel (qui était le comportement fourni par la plupart des autres implémentations à cette époque).
Définir la variable d'environnement LD_DYNAMIC_WEAK (avec n'importe quelle valeur) fournit l'ancien comportement non standard de glibc, où un symbole faible dans une bibliothèque partagée peut être remplacé par un symbole fort découvert ultérieurement dans une autre bibliothèque partagée. (Notez que même lorsque cette variable est définie, un symbole fort dans une bibliothèque partagée ne remplacera pas une définition faible du même symbole dans le programme principal.)
Depuis glibc 2.3.4, LD_DYNAMIC_WEAK est ignoré en mode d'exécution sécurisée.
LD_HWCAP_MASK (de glibc 2.1 à glibc 2.38)
Masque pour les capacités matérielles. Depuis glibc 2.26, l'option peut être ignorée si glibc ne prend pas en charge les "tunables".
LD_ORIGIN_PATH (depuis glibc 2.1)
Chemin où le binaire est trouvé.
Depuis glibc 2.4, LD_ORIGIN_PATH est ignoré en mode d'exécution sécurisée.
LD_POINTER_GUARD (de glibc 2.4 à glibc 2.22)
Réglé sur 0 pour désactiver la protection des pointeurs. Toute autre valeur active la protection des pointeurs, ce qui est également le comportement par défaut. La protection des pointeurs est un mécanisme de sécurité par lequel certains pointeurs vers du code stockés dans la mémoire programme inscriptible (adresses de retour sauvegardées par setjmp(3) ou pointeurs de fonction utilisés par divers éléments internes de glibc) sont brouillés de manière semi-aléatoire pour rendre plus difficile pour un attaquant de détourner les pointeurs pour les utiliser en cas de dépassement de tampon ou d'attaque par « stack smashing ». Depuis glibc 2.23, LD_POINTER_GUARD ne peut plus être utilisé pour désactiver la protection des pointeurs, qui est maintenant toujours activée.
LD_PROFILE (depuis glibc 2.1)
Le nom d'un (unique) objet partagé à profiler, spécifié soit comme chemin d'accès, soit comme nom de son. La sortie de profilage est ajoutée au fichier dont le nom est : $LD_PROFILE_OUTPUT/$LD_PROFILE.profile.
Depuis glibc 2.2.5, LD_PROFILE utilise un chemin par défaut différent en mode d'exécution sécurisée.
LD_PROFILE_OUTPUT (depuis glibc 2.1)
Répertoire où la sortie de LD_PROFILE doit être écrite. Si cette variable n'est pas définie, ou est définie comme une chaîne vide, alors le défaut est /var/tmp.
LD_PROFILE_OUTPUT est ignoré en mode d'exécution sécurisée ; à la place, /var/profile est toujours utilisé.
LD_SHOW_AUXV (depuis glibc 2.1)
Si cette variable d'environnement est définie (avec n'importe quelle valeur), affiche le tableau auxiliaire transmis par le noyau (voir aussi getauxval(3)).
Depuis glibc 2.3.4, LD_SHOW_AUXV est ignoré en mode d'exécution sécurisée.
LD_TRACE_PRELINKING (de glibc 2.4 à glibc 2.35)
Si cette variable d'environnement est définie, trace le pré-liaison de l'objet dont le nom est assigné à cette variable d'environnement. (Utilisez ldd(1) pour obtenir une liste des objets qui pourraient être tracés.) Si le nom de l'objet n'est pas reconnu, alors toute l'activité de pré-liaison est tracée.
LD_USE_LOAD_BIAS (de glibc 2.3.3 à glibc 2.35)
Par défaut (c'est-à-dire si cette variable n'est pas définie), les exécutables et les objets partagés pré-liés honoreront les adresses de base de leurs objets partagés dépendants et les exécutables indépendants de position (PIE) et autres objets partagés (non pré-liés) ne les honoreront pas. Si LD_USE_LOAD_BIAS est défini avec la valeur 1, les exécutables et les PIE honoreront les adresses de base. Si LD_USE_LOAD_BIAS est défini avec la valeur 0, ni les exécutables ni les PIE n'honoreront les adresses de base.
Depuis glibc 2.3.3, cette variable est ignorée en mode d'exécution sécurisée.
LD_VERBOSE (depuis glibc 2.1)
Si défini à une chaîne non vide, affiche des informations sur le versionnement des symboles du programme si la variable d'environnement LD_TRACE_LOADED_OBJECTS a été définie.
LD_WARN (depuis glibc 2.1.3)
Si défini à une chaîne non vide, avertit des symboles non résolus.
LD_PREFER_MAP_32BIT_EXEC (x86-64 seulement ; depuis glibc 2.23)
Selon le guide d'optimisation logicielle Intel Silvermont, pour les applications 64 bits, les performances de prédiction de branchement peuvent être affectées négativement lorsque la cible d'une branche est à plus de 4 Go de la branche. Si cette variable d'environnement est définie (à n'importe quelle valeur), l'éditeur de liens dynamique essaiera d'abord de mapper les pages exécutables en utilisant le drapeau mmap(2) MAP_32BIT, et se rabattra sur le mappage sans ce drapeau si cette tentative échoue. NB : MAP_32BIT mapperont dans les 2 Go bas (pas 4 Go) de l'espace d'adressage.
Comme MAP_32BIT réduit la plage d'adresses disponible pour la randomisation de la disposition de l'espace d'adressage (ASLR), LD_PREFER_MAP_32BIT_EXEC est toujours désactivé en mode d'exécution sécurisée.

FICHIERS

/lib/ld.so
Éditeur de liens/chargeur dynamique a.out
/lib/ld-linux.so.{1,2}
Éditeur de liens/chargeur dynamique ELF
/etc/ld.so.cache
Fichier contenant une liste compilée de répertoires dans lesquels rechercher les objets partagés et une liste ordonnée d'objets partagés candidats. Voir ldconfig(8).
/etc/ld.so.preload

NAME

ld.so, ld-linux.so — dynamic linker/loader

SYNOPSIS

ld.so and ld-linux.so are the dynamic linker/loader. This manual page is not intended for direct use by end-users. Refer to ld.so(8) for details.

DESCRIPTION

The dynamic linker/loader, ld.so (or ld-linux.so on Linux), is responsible for loading and linking dynamically linked programs when they are run. It is also used to link shared libraries that are loaded using the dlopen(3) function.

OPTIONS

The dynamic linker/loader accepts a number of command-line options, primarily for debugging purposes. These options are usually passed by the ldconfig(8) program or set via the ld.so(8) environment variables.

-d
Dump information about the dynamic linking process.
-f
Force loading of shared libraries, even if they are considered unsafe.
-h
Print the library search path.
-i
Ignore the default library search path and only use the paths specified on the command line.
-r
Repeat loading of shared libraries, for testing purposes.
-v
Print the version of the dynamic linker/loader.

ENVIRONMENT

The behavior of the dynamic linker/loader can be influenced by several environment variables:

LD_LIBRARY_PATH
A colon-separated list of directories to search for shared libraries. If this variable is not set, the dynamic linker/loader searches the default system directories. This variable should generally not be set by users, as it can lead to security vulnerabilities. It is primarily intended for debugging and development.
LD_PRELOAD
A colon-separated list of shared libraries to be loaded before any other shared libraries. This is often used for overriding existing library functions or for profiling purposes.
LD_BIND_NOW
If set, all symbols are resolved eagerly when the program is started, rather than lazily when they are first used. This can improve performance in some cases, but may also increase startup time.
LD_DEBUG
Controls the amount of debugging information printed by the dynamic linker/loader. Possible values include `all`, `bindings`, `libs`, `reloc`, `symbols`, etc.

FILES

/lib/ld-linux.so.2
The dynamic linker/loader for Linux.
/etc/ld.so.cache
Cache file that contains the results of the last invocation of ldconfig(8). This file speeds up the process of finding shared libraries.
/etc/ld.so.conf
Configuration file that specifies additional directories to search for shared libraries.

NOTES

The dynamic linker/loader plays a crucial role in the execution of dynamically linked programs. Understanding its behavior and the environment variables that influence it is important for system administration and software development.

Hardware capabilities support has the drawback that each new feature added grows the search path exponentially, because it has to be added to every combination of the other existing features.

For instance, on x86 32-bit, if the hardware supports i686 and sse2, the resulting search path will be i686/sse2:i686:sse2:.. A new capability newcap will set the search path to newcap/i686/sse2:newcap/i686:newcap/sse2:newcap:i686/sse2:i686:sse2:.

glibc Hardware capabilities (from glibc 2.33)

glibc 2.33 added a new hardware capability scheme,
where under each CPU architecture, certain levels can be defined, grouping support for certain features or special instructions. Each architecture level has a fixed set of paths that it adds to the dynamic linker search list, depending on the hardware of the machine. Since each new architecture level is not combined with previously existing ones, the new scheme does not have the drawback of growing the dynamic linker search list uncontrollably.

For instance, on x86 64-bit, if the hardware supports x86_64-v3 (for instance Intel Haswell or AMD Excavator), the resulting search path will be glibc-hwcaps/x86-64-v3:glibc-hwcaps/x86-64-v2:. The following paths are currently supported, in priority order.

PowerPC (64-bit little-endian only)
power10, power9
s390 (64-bit only)
z16, z15, z14, z13
x86 (64-bit only)
x86-64-v4, x86-64-v3, x86-64-v2

glibc 2.37 removed support for the legacy hardware capabilities.
