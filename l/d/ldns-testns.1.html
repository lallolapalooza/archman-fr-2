ldns-testns(1) Manuel des commandes générales ldns-testns(1)

NOM

ldns-testns - outil simple de faux serveur de noms

SYNTAXE

ldns-testns [ OPTION ] fichier_de_donnees

DESCRIPTION

ldns-testns peut être utilisé pour fournir des réponses à des requêtes DNS à des fins de test. Les réponses sont pré-établies et peuvent être adaptées aux besoins de test. Les réponses peuvent être totalement invalides ou impossibles à analyser.

Ce programme est une aide au débogage. Il n'est pas efficace, surtout avec un long fichier de configuration, mais il peut donner n'importe quelle réponse à n'importe quelle requête. Cela peut aider le développeur à pré-scriptter les réponses pour les requêtes.

Il écoute par défaut sur IP4 UDP et TCP. Vous pouvez spécifier un enregistrement RR par RR avec des indicateurs d'en-tête à renvoyer.

ldns-testns n'est pas destiné à une utilisation en production.

OPTIONS

-r
Écoute sur un port aléatoire. Le numéro de port est affiché sur la sortie standard.
-p port
Écoute sur le port spécifié.
-f nombre
Fait un fork de ce nombre d'instances supplémentaires qui servent les mêmes ports et le même fichier de données. Elles ne se terminent pas ; il est affiché 'forked pid: <nombre>' et vous devez les tuer vous-même.
-v
Affiche plus d'informations de débogage. Il est possible de donner cette option plusieurs fois pour augmenter le niveau de verbosité.
-6
Se lie à une adresse IP6 au lieu d'une adresse IP4. À utiliser avec -p.
fichier_de_donnees
Le fichier de données est lu au démarrage. Il contient les requêtes et les paquets qui doivent être envoyés en réponse à ces requêtes. Le format du fichier de données est expliqué ci-dessous.

FORMAT DU FICHIER DE DONNÉES

Le format du fichier de données utilise ';' pour indiquer un commentaire. Un certain nombre d'entrées sont traitées de la première à la dernière. La première entrée correspondante est utilisée pour répondre à la requête. C'est un format basé sur les lignes. Les enregistrements de ressources DNS sont saisis au format de fichier de zone.

Vous pouvez utiliser les directives $ORIGIN et $TTL. Les parenthèses '(' et ')' des fichiers de zone pour étendre les lignes sur plusieurs lignes ne sont pas autorisées.

$ORIGIN origine $TTL ttl_par_défaut

BEGIN_ENTREE

; d'abord donner des lignes MATCH, qui disent quelles requêtes sont correspondantes ; par cette entrée. ; 'opcode' fait correspondre la requête à l'opcode de la réponse ; si vous le laissez vide, n'importe quel opcode correspondra à cette entrée. ; 'qtype' fait correspondre la requête au qtype de la réponse ; 'qname' fait correspondre la requête au qname de la réponse ; 'serial=1023' fait correspondre la requête si le numéro de série ixfr est 1023.

MATCH [opcode] [qtype] [qname] [serial=<valeur>] MATCH [UDP|TCP] MATCH ...

; Ensuite, l'en-tête de RÉPONSE est spécifié.

REPLY opcode, rcode ou flags.
(opcode) QUERY IQUERY STATUS NOTIFY UPDATE
(rcode) NOERROR FORMERR SERVFAIL NXDOMAIN NOTIMPL YXDOMAIN
YXRRSET NXRRSET NOTAUTH NOTZONE
(flags) QR AA TC RD CD RA AD

REPLY ...

; toute action supplémentaire à effectuer.

ADJUST copy_id ; 'copy_id' copie l'ID de la requête dans la réponse. ; 'sleep=10' attend 10 secondes avant de donner la réponse (TCP est ouvert)

ADJUST [sleep=<nombre>] ; attend avant de donner une réponse quelconque ADJUST [packet_sleep=<nombre>] ; attend avant ce paquet dans la séquence

SECTION QUESTION <RR, un par ligne> ; le nombre de RR est déterminé automatiquement.

SECTION ANSWER <RR, un par ligne>

SECTION AUTHORITY <RR, un par ligne>

SECTION ADDITIONAL <RR, un par ligne>

HEX_EDNSDATA_BEGIN <Données Hex d'une option EDNS> HEX_EDNSDATA_END

EXTRA_PACKET ; suivre avec SECTION, REPLY pour plus de paquets.
HEX_ANSWER_BEGIN ; suivre avec les données hexadécimales
; cela remplace tout paquet de réponse construit
; avec les mots-clés SECTION (seule SECTION QUERY
; est utilisée pour faire correspondre les requêtes). Si les données ne peuvent pas
; être analysées, les règles ADJUST pour le paquet de réponse
; sont ignorées

HEX_ANSWER_END

FIN_ENTREE
