ldd(1) Manuel des commandes générales ldd(1)

NOM

ldd - affiche les dépendances des objets partagés

SYNTAXE

ldd [option ...] fichier ...

DESCRIPTION

ldd affiche les objets partagés (bibliothèques partagées) requis par chaque programme ou objet partagé spécifié sur la ligne de commande. Un exemple de son utilisation et de sa sortie est le suivant :


$ ldd /bin/ls;
    linux-vdso.so.1 (0x00007ffcc3563000)
    libselinux.so.1 => /lib64/libselinux.so.1 (0x00007f87e5459000)
    libcap.so.2 => /lib64/libcap.so.2 (0x00007f87e5254000)
    libc.so.6 => /lib64/libc.so.6 (0x00007f87e4e92000)
    libpcre.so.1 => /lib64/libpcre.so.1 (0x00007f87e4c22000)
    libdl.so.2 => /lib64/libdl.so.2 (0x00007f87e4a1e000)
    /lib64/ld-linux-x86-64.so.2 (0x00005574bf12e000)
    libattr.so.1 => /lib64/libattr.so.1 (0x00007f87e4817000)
    libpthread.so.0 => /lib64/libpthread.so.0 (0x00007f87e45fa000)

Dans le cas habituel, ldd invoque le lieur dynamique standard (voir ld.so(8)) avec la variable d'environnement LD_TRACE_LOADED_OBJECTS définie à 1. Cela amène le lieur dynamique à inspecter les dépendances de l'objet dynamique du programme, et à trouver (selon les règles décrites dans ld.so(8)) et à charger les objets qui satisfont ces dépendances. Pour chaque dépendance, ldd affiche l'emplacement de l'objet correspondant et l'adresse (hexadécimale) à laquelle il est chargé. (Les dépendances partagées linux-vdso et ld-linux sont spéciales ; voir vdso(7) et ld.so(8).)

Sécurité

Soyez conscient que dans certaines circonstances (par exemple, lorsque le programme spécifie un interpréteur ELF autre que ld-linux.so), certaines versions de ldd peuvent tenter d'obtenir les informations de dépendance en essayant d'exécuter directement le programme, ce qui peut conduire à l'exécution de tout code défini dans l'interpréteur ELF du programme, et potentiellement à l'exécution du programme lui-même. (Avant glibc 2.27, l'implémentation ldd d'origine faisait cela par exemple, bien que la plupart des distributions fournissaient une version modifiée qui ne le faisait pas.)

Par conséquent, vous ne devriez jamais utiliser ldd sur un exécutable non fiable, car cela pourrait entraîner l'exécution de code arbitraire. Une alternative plus sûre lors du traitement d'exécutables non fiables est :


$ objdump -p /chemin/vers/programme | grep NEEDED;

Notez, cependant, que cette alternative n'affiche que les dépendances directes de l'exécutable, tandis que ldd affiche l'arborescence complète des dépendances de l'exécutable.

OPTIONS

--version
Affiche le numéro de version de ldd.
--verbose
-v
Affiche toutes les informations, y compris, par exemple, les informations de versionnement des symboles.
--unused
-u
Affiche les dépendances directes inutilisées. (Depuis glibc 2.3.4.)
--data-relocs
-d
Effectue les relocalisations et signale tout objet manquant (ELF uniquement).
--function-relocs
-r
Effectue les relocalisations pour les objets de données et les fonctions, et signale tout objet ou fonction manquant (ELF uniquement).
--help
Informations d'utilisation.

BOGUES

ldd ne fonctionne pas sur les bibliothèques partagées a.out.

ldd ne fonctionne pas avec certains programmes a.out extrêmement anciens qui ont été compilés avant que le support de ldd ne soit ajouté aux versions du compilateur. Si vous utilisez ldd sur l'un de ces programmes, le programme tentera de s'exécuter avec argc = 0 et les résultats seront imprévisibles.

VOIR AUSSI

pldd(1), sprof(1), ld.so(8), ldconfig(8)
