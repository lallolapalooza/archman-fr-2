LD(1) Outils de développement GNU LD(1)

NOM

ld - L'éditeur de liens GNU

SYNOPSIS

ld [options] fichiers-objets ...

DESCRIPTION

ld combine un certain nombre de fichiers objets et d'archives, relocalise leurs données et résout les références de symboles. Habituellement, la dernière étape de la compilation d'un programme est l'exécution de ld.

ld accepte des fichiers de commandes d'éditeur de liens écrits dans un sur-ensemble de la syntaxe du langage de commande de l'éditeur de liens d'AT&T, afin de fournir un contrôle explicite et total sur le processus d'édition de liens.

Cette page de manuel ne décrit pas le langage de commande ; consultez l'entrée ld dans "info" pour des détails complets sur le langage de commande et sur d'autres aspects de l'éditeur de liens GNU.

Cette version de ld utilise les bibliothèques BFD à usage général pour opérer sur les fichiers objets. Cela permet à ld de lire, combiner et écrire des fichiers objets dans de nombreux formats différents - par exemple, COFF ou "a.out". Différents formats peuvent être liés ensemble pour produire n'importe quel type de fichier objet disponible.

Outre sa flexibilité, l'éditeur de liens GNU est plus utile que les autres éditeurs de liens pour fournir des informations diagnostiques. De nombreux éditeurs de liens abandonnent l'exécution immédiatement à la rencontre d'une erreur ; chaque fois que possible, ld continue l'exécution, vous permettant d'identifier d'autres erreurs (ou, dans certains cas, d'obtenir un fichier de sortie malgré l'erreur).

L'éditeur de liens GNU ld est conçu pour couvrir un large éventail de situations et pour être aussi compatible que possible avec les autres éditeurs de liens. En conséquence, vous avez de nombreux choix pour contrôler son comportement.

OPTIONS

L'éditeur de liens prend en charge une pléthore d'options en ligne de commande, mais en pratique, peu d'entre elles sont utilisées dans un contexte particulier. Par exemple, une utilisation fréquente de ld est de lier des fichiers objets Unix standards sur un système Unix standard et supporté. Sur un tel système, pour lier un fichier "hello.o" :

ld -o <sortie> /lib/crt0.o hello.o -lc

Cela indique à ld de produire un fichier nommé sortie à la suite de la liaison du fichier "/lib/crt0.o" avec "hello.o" et la bibliothèque "libc.a", qui proviendra des répertoires de recherche standards. (Voir la discussion sur l'option -l ci-dessous.)

Certaines des options en ligne de commande de ld peuvent être spécifiées à n'importe quel point de la ligne de commande. Cependant, les options qui se réfèrent à des fichiers, telles que -l ou -T, provoquent la lecture du fichier au point où l'option apparaît dans la ligne de commande, par rapport aux fichiers objets et aux autres options de fichier. La répétition d'options n'ayant pas de référence à un fichier avec un argument différent n'aura soit aucun effet supplémentaire, soit annulera les occurrences précédentes (celles situées plus à gauche sur la ligne de commande) de cette option. Les options qui peuvent être significativement spécifiées plus d'une fois sont notées dans les descriptions ci-dessous.

Les arguments qui ne sont pas des options sont des fichiers objets ou des archives qui doivent être liés ensemble. Ils peuvent suivre, précéder ou être mélangés avec les options de la ligne de commande, à l'exception du fait qu'un argument de fichier objet ne peut pas être placé entre une option et son argument.

Habituellement, l'éditeur de liens est appelé avec au moins un fichier objet, mais vous pouvez spécifier d'autres formes de fichiers d'entrée binaires en utilisant -l, -R, et le langage de script de commande. Si *aucun* fichier d'entrée binaire n'est spécifié, l'éditeur de liens ne produit aucune sortie et affiche le message No input files.

Si l'éditeur de liens ne parvient pas à reconnaître le format d'un fichier objet, il supposera qu'il s'agit d'un script d'éditeur de liens. Un script spécifié de cette manière complète le script d'éditeur de liens principal utilisé pour la liaison (soit le script d'éditeur de liens par défaut, soit celui spécifié à l'aide de -T). Cette fonctionnalité permet à l'éditeur de liens de lier avec un fichier qui semble être un objet ou une archive, mais qui définit en réalité certaines valeurs de symboles, ou utilise "INPUT" ou "GROUP" pour charger d'autres objets. La spécification d'un script de cette manière ne fait que compléter le script d'éditeur de liens principal, avec les commandes supplémentaires placées après le script principal ; utilisez l'option -T pour remplacer entièrement le script d'éditeur de liens par défaut, mais notez l'effet de la commande "INSERT".

Pour les options dont le nom est une seule lettre, les arguments de l'option doivent soit suivre la lettre de l'option sans espace blanc intermédiaire, soit être donnés comme des arguments séparés immédiatement après l'option qui les requiert.

Pour les options dont le nom est composé de plusieurs lettres, un seul ou deux traits peuvent précéder le nom de l'option ; par exemple, -trace-symbol et --trace-symbol sont équivalents. Notez qu'il y a une exception à cette règle. Les options à plusieurs lettres qui commencent par une minuscule 'o' ne peuvent être précédées que de deux traits. Ceci afin de réduire la confusion avec l'option -o. Ainsi, par exemple, -omagic définit le nom du fichier de sortie sur magic, tandis que --omagic définit le drapeau NMAGIC sur la sortie.

Les arguments des options à plusieurs lettres doivent soit être séparés du nom de l'option par un signe égal, soit être donnés comme des arguments séparés immédiatement après l'option qui les requiert. Par exemple, --trace-symbol foo et --trace-symbol=foo sont équivalents. Des abréviations uniques des noms des options à plusieurs lettres sont acceptées.

Notez que si l'éditeur de liens est appelé indirectement, via un pilote de compilateur (par exemple, gcc), alors toutes les options de ligne de commande de l'éditeur de liens doivent être précédées de -Wl, (ou de ce qui est approprié pour le pilote de compilateur particulier), comme suit :

gcc -Wl,--start-group foo.o bar.o -Wl,--end-group

Ceci est important, car sinon le programme pilote de compilateur peut silencieusement ignorer les options de l'éditeur de liens, ce qui entraîne une liaison incorrecte. La confusion peut également survenir lors du passage d'options nécessitant des valeurs par un pilote, car l'utilisation d'un espace entre l'option et l'argument agit comme un séparateur, et fait que le pilote passe uniquement l'option à l'éditeur de liens et l'argument au compilateur. Dans ce cas, il est plus simple d'utiliser les formes jointes des options à une seule et à plusieurs lettres, telles que :

gcc foo.o bar.o -Wl,-eENTRY -Wl,-Map=a.map

--filter=name
When creating an ELF shared object, set the internal DT_FILTER field to the specified name. This tells the dynamic linker that the symbol table of the shared object which is being created should be used as a filter on the symbol table of the shared object name.

If you later link a program against this filter object, then, when you run the program, the dynamic linker will see the DT_FILTER field. Thus the filter object can be used to select a subset of the symbols provided by the object name.

Some older linkers used the -F option throughout a compilation toolchain for specifying object-file format for both input and output object files. The GNU linker will ignore the -F option when not creating an ELF shared object.

--remap-inputs=pattern=filename
--remap-inputs-file=file
These options allow the names of input files to be changed before the linker attempts to open them. The option --remap-inputs=foo.o=bar.o will cause any attempt to load a file called foo.o to instead try to load a file called bar.o. Wildcard patterns are permitted in the first filename, so --remap-inputs=foo*.o=bar.o will rename any input file that matches foo*.o to bar.o.

An alternative form of the option --remap-inputs-file=filename allows the remappings to be read from a file. Each line in the file can contain a single remapping. Blank lines are ignored. Anything from a hash character (#) to the end of a line is considered to be a comment and is also ignored. The mapping pattern can be separated from the filename by whitespace or an equals (=) character.

The options can be specified multiple times. Their contents accumulate. The remappings will be processed in the order in which they occur on the command line, and if they come from a file, in the order in which they occur in the file. If a match is made, no further checking for that filename will be performed.

If the replacement filename is /dev/null or just NUL then the remapping will actually cause the input file to be ignored. This can be a convenient way to experiment with removing input files from a complicated build environment.

Note that this option is position dependent and only affects filenames that come after it on the command line. Thus:

ld foo.o --remap-inputs=foo.o=bar.o

Will have no effect, whereas:

ld --remap-inputs=foo.o=bar.o foo.o

Will rename the input file foo.o to bar.o.

Note - these options also affect files referenced by INPUT statements in linker scripts. But since linker scripts are processed after the entire command line is read, the position of the remap options on the command line is not significant.

If the verbose option is enabled then any mappings that match will be reported, although again the verbose option needs to be enabled on the command line before the remaped filenames appear.

If the -Map or --print-map options are enabled then the remapping list will be included in the map output.

[0x0000000c]                foo = (foo * 0x4)
[0x0000000c]                foo = (foo + 0x8)

Voir Expressions pour plus d'informations sur les expressions dans les scripts de liaison.

  • Comment les propriétés GNU sont fusionnées.

    Lorsque le lieur fusionne les sections .note.gnu.property d'entrée en une section .note.gnu.property de sortie, certaines propriétés sont supprimées ou mises à jour. Ces actions sont rapportées dans la carte de liaison. Par exemple :

    Removed property 0xc0000002 to merge foo.o (0x1) and bar.o (not found)

    Cela indique que la propriété 0xc0000002 est supprimée de la sortie lors de la fusion des propriétés de foo.o, dont la valeur de la propriété 0xc0000002 est 0x1, et de bar.o, qui n'a pas la propriété 0xc0000002.

    Updated property 0xc0010001 (0x1) to merge foo.o (0x1) and bar.o (0x1)

    Cela indique que la valeur de la propriété 0xc0010001 est mise à jour à 0x1 dans la sortie lors de la fusion des propriétés de foo.o, dont la valeur de la propriété 0xc0010001 est 0x1, et de bar.o, dont la valeur de la propriété 0xc0010001 est 0x1.

  • Sur certaines cibles ELF, une liste de corrections insérées par --relax 
    foo.o: Adjusting branch at 0x00000008 towards "far" in section .text

    Cela indique que le branchement à 0x00000008 dans foo.o, ciblant le symbole « far » dans la section .text, a été remplacé par une trampoline.

    -n
    --nmagic
    Désactive l'alignement des sections sur les pages et désactive la liaison avec les bibliothèques partagées. Si le format de sortie prend en charge les nombres magiques de style Unix, marque la sortie comme "NMAGIC".
    -N

    Définit les sections de texte et de données comme lisibles et écrivables. De plus, n'aligne pas le segment de données sur les pages et désactive la liaison avec les bibliothèques partagées. Si le format de sortie prend en charge les nombres magiques de style Unix, marque la sortie comme "OMAGIC". Note : Bien qu'une section de texte écrivable soit autorisée pour les cibles PE-COFF, elle n'est pas conforme à la spécification du format publiée par Microsoft.

    Cette option annule la plupart des effets de l'option -N. Elle rend la section de texte illisible en écriture et force le segment de données à être aligné sur les pages. Note : cette option n'active pas la liaison avec les bibliothèques partagées. Utilisez -Bdynamic pour cela.
    -o sortie
    --output=sortie
    Utilise sortie comme nom pour le programme produit par ld ; si cette option n'est pas spécifiée, le nom a.out est utilisé par défaut. La commande de script "OUTPUT" peut également spécifier le nom du fichier de sortie.

    Note : le lieur supprimera le fichier de sortie avant de commencer à y écrire. Il le fera même s'il s'avère que la liaison ne peut pas être terminée en raison d'erreurs.

    Note : le lieur vérifiera que le nom du fichier de sortie ne correspond pas au nom de l'un des fichiers d'entrée, mais c'est tout. En particulier, il ne se plaindra pas si le fichier de sortie risque d'écraser un fichier source ou un autre fichier important. Par conséquent, dans les systèmes de construction, il est recommandé d'utiliser l'option -o comme dernière option sur la ligne de commande du lieur. Par exemple, considérez :

    ld -o $(EXE) $(OBJS)
ld $(OBJS) -o $(EXE)

    Si la variable EXE n'est pas définie pour une raison quelconque, la première version de la commande du lieur pourrait finir par supprimer l'un des fichiers objet (le premier de la liste OBJS), tandis que la deuxième version de la commande du lieur générera un message d'erreur et ne supprimera rien.

    --dependency-file=depfile
    Écrit un fichier de dépendances dans depfile. Ce fichier contient une règle appropriée pour "make" décrivant le fichier de sortie et tous les fichiers d'entrée qui ont été lus pour le produire. La sortie est similaire à la sortie du compilateur avec -M -MP. Notez qu'il n'y a pas d'option comme le -MM du compilateur, pour exclure les « fichiers système » (ce qui n'est pas un concept bien défini dans le lieur, contrairement aux « en-têtes système » dans le compilateur). Ainsi, la sortie de --dependency-file est toujours spécifique à l'état exact de l'installation où elle a été produite, et ne doit pas être copiée dans les Makefiles distribués sans édition minutieuse.
    -O niveau
    Si niveau est une valeur numérique supérieure à zéro, ld optimise la sortie. Cela peut prendre beaucoup plus de temps et devrait donc probablement n'être activé que pour le binaire final. Pour le moment, cette option n'affecte que la génération des bibliothèques partagées ELF. Les futures versions du lieur pourraient faire plus usage de cette option. De plus, il n'y a actuellement aucune différence dans le comportement du lieur pour différentes valeurs non nulles de cette option. Là encore, cela pourra changer dans les futures versions.
    -plugin nom
    Implique un plugin dans le processus de liaison. Le paramètre nom est le nom de fichier absolu du plugin. Généralement, ce paramètre est ajouté automatiquement par le compilateur, lors de l'utilisation de l'optimisation au moment de la liaison, mais les utilisateurs peuvent également ajouter leurs propres plugins s'ils le souhaitent.

    Notez que l'emplacement des plugins issus du compilateur est différent de l'endroit où les programmes ar, nm et ranlib recherchent leurs plugins. Pour que ces commandes utilisent un plugin basé sur le compilateur, il doit d'abord être copié dans le répertoire ${libdir}/bfd-plugins. Tous les plugins de lieur basés sur gcc sont rétrocompatibles, il suffit donc de copier le plus récent.

    --push-state
    L'option --push-state permet de préserver l'état actuel des drapeaux qui régissent la gestion des fichiers d'entrée afin qu'ils puissent tous être restaurés avec une option correspondante --pop-state.

    Les options couvertes sont : -Bdynamic, -Bstatic, -dn, -dy, -call_shared, -non_shared, -static, -N, -n, --whole-archive, --no-whole-archive, -r, -Ur, --copy-dt-needed-entries, --no-copy-dt-needed-entries, --as-needed, --no-as-needed, et -a.

    Une cible pour cette option sont les spécifications pour pkg-config. Lorsqu'elle est utilisée avec l'option --libs, toutes les bibliothèques potentiellement nécessaires sont listées puis potentiellement liées à chaque fois. Il est préférable de retourner quelque chose comme suit :

    -Wl,--push-state,--as-needed -libone -libtwo -Wl,--pop-state
    --pop-state
    Annule l'effet de --push-state, restaure les valeurs précédentes des drapeaux régissant la gestion des fichiers d'entrée.
    -q
    --emit-relocs
    Laisse les sections de relocalisation et leur contenu dans les exécutables entièrement liés. Les outils d'analyse et d'optimisation post-liaison peuvent avoir besoin de ces informations pour effectuer des modifications correctes des exécutables. Cela entraîne des exécutables plus volumineux.

    Cette option n'est actuellement prise en charge que sur les plateformes ELF.

    --force-dynamic
    Force le fichier de sortie à avoir des sections dynamiques. Cette option est spécifique aux cibles VxWorks.
    -r
    --relocatable
    Génère une sortie relocalisable, c'est-à-dire un fichier de sortie qui peut à son tour servir d'entrée à ld. C'est souvent appelé liaison partielle. En guise d'effet secondaire, dans les environnements qui prennent en charge les nombres magiques Unix standard, cette option définit également le nombre magique du fichier de sortie sur "OMAGIC". Si cette option n'est pas spécifiée, un fichier absolu est produit. Lors de la liaison de programmes C++, cette option ne résoudra pas les références aux constructeurs ; pour ce faire, utilisez -Ur.

    Lorsqu'un fichier d'entrée n'a pas le même format que le fichier de sortie, la liaison partielle n'est prise en charge que si ce fichier d'entrée ne contient aucune relocalisation. Différents formats de sortie peuvent avoir des restrictions supplémentaires ; par exemple, certains formats basés sur "a.out" ne prennent pas en charge la liaison partielle avec des fichiers d'entrée d'autres formats.

    Lorsque la sortie relocalisable contient à la fois du contenu qui nécessite une optimisation au moment de la liaison (LTO) et du contenu qui n'en a pas besoin, une section .gnu_object_only sera créée pour contenir un fichier objet relocalisable, comme si -r était appliqué à toutes les entrées relocalisables qui n'ont pas besoin de LTO. Lors du traitement d'une entrée relocalisable avec une section .gnu_object_only, le lieur extraira la section .gnu_object_only en tant qu'entrée séparée.

    Notez que puisque -r regroupe certaines sections de différents fichiers d'entrée, il peut y avoir des impacts négatifs sur la taille du code et la localité dans l'exécutable final ou la bibliothèque partagée.

    Cette option fait la même chose que -i.

    -R nomfichier
    --just-symbols=nomfichier
    Lit les noms de symboles et leurs adresses à partir de nomfichier, mais ne le relocalise pas ou
    inclure dans la sortie. Cela permet à votre fichier de sortie de référencer symboliquement les emplacements absolus de la mémoire définis dans d'autres programmes. Vous pouvez utiliser cette option plus d'une fois.

    Pour la compatibilité avec d'autres éditeurs de liens ELF, si l'option -R est suivie d'un nom de répertoire, plutôt que d'un nom de fichier, elle est traitée comme l'option -rpath.

    --rosegment
    --no-rosegment
    Tenter de s'assurer qu'un seul segment en lecture seule et non de code est créé. Utile uniquement lorsqu'il est utilisé conjointement avec l'option -z separate-code. Les binaires résultants devraient être plus petits que si -z separate-code est utilisé seul. Sans cette option, ou si --no-rosegment est spécifié, l'option -z separate-code créera deux segments en lecture seule, un avant le segment de code et un après celui-ci.

    Les noms des options sont trompeurs, mais ils ont été choisis pour que l'éditeur de liens soit compatible avec les éditeurs de liens LLD et GOLD.

    Ces options ne sont prises en charge que par les cibles ELF.

    -s
    --strip-all
    Omettre toutes les informations de symbole du fichier de sortie.
    -S
    --strip-debug
    Omettre les informations de symbole de débogage (mais pas tous les symboles) du fichier de sortie.

    Stocker les fichiers intermédiaires "temporaires" du plugin de manière permanente.

    --trace

La sortie -t est utile pour générer une liste de tous les fichiers objets et scripts impliqués dans l'édition de liens, par exemple, lors de l'empaquetage de fichiers pour un rapport de bogue de l'éditeur de liens.

    --script=scriptfile
    Utiliser scriptfile comme script de l'éditeur de liens. Ce script remplace le script de l'éditeur de liens par défaut de ld (plutôt que de s'y ajouter), sauf si le script contient "INSERT", donc commandfile doit spécifier tout ce qui est nécessaire pour décrire le fichier de sortie.

    Si scriptfile n'existe pas dans le répertoire courant, "ld" le recherche dans les répertoires spécifiés par les options -L précédentes.

    Les options de la ligne de commande qui apparaissent avant l'option -T peuvent affecter le script, mais les options de la ligne de commande qui apparaissent après elles n'en affectent pas.

    Il existe d'autres façons de spécifier des scripts d'éditeur de liens. Voir

    -dT scriptfile
    --default-script=scriptfile

Cela permet aux options placées après l'option --default-script sur la ligne de commande d'affecter le comportement du script de l'éditeur de liens, ce qui peut être important lorsque la ligne de commande de l'éditeur de liens ne peut pas être directement contrôlée par l'utilisateur. (par exemple, parce que la ligne de commande est construite par un autre outil, tel que gcc).

    -u symbol
    --undefined=symbol
    Forcer symbol à être entré dans le fichier de sortie en tant que symbole non défini. Cela peut, par exemple, déclencher l'édition de liens de modules supplémentaires à partir des bibliothèques standard. -u peut être répété avec différents arguments d'option pour entrer des symboles non définis supplémentaires. Cette option est équivalente à la commande de script d'éditeur de liens "EXTERN".

    Si cette option est utilisée pour forcer des modules supplémentaires à être inclus dans le lien, et si le symbole est une erreur lorsqu'il reste indéfini, alors l'option --require-defined devrait être utilisée à la place.

    --require-defined=symbol
    Exiger que symbol soit défini dans le fichier de sortie. Cette option est identique à l'option --undefined, sauf que si symbol n'est pas défini dans le fichier de sortie, l'éditeur de liens affichera une erreur et quittera. Le même effet peut être obtenu dans un script d'éditeur de liens en utilisant "EXTERN", "ASSERT" et "DEFINED" ensemble. Cette option peut être utilisée plusieurs fois pour exiger des symboles supplémentaires.
    -Ur
    Pour les programmes qui n'utilisent pas de constructeurs ou de destructeurs, ou pour les systèmes basés sur ELF, cette option est équivalente à -r : elle génère une sortie déplaçable, c'est-à-dire un fichier de sortie qui peut à son tour servir d'entrée à ld. Pour d'autres binaires, cependant, l'option -Ur est similaire à -r mais elle résout également les références aux constructeurs et destructeurs.

    Pour les systèmes où -r et -Ur se comportent différemment, il n'est pas possible d'utiliser -Ur sur des fichiers qui ont eux-mêmes été liés avec -Ur; une fois la table des constructeurs construite, on ne peut plus y ajouter. Utilisez -Ur uniquement pour la dernière liaison partielle, et -r pour les autres.

    --orphan-handling=MODE
    Contrôler la manière dont les sections orphelines sont gérées. Une section orpheline est une section qui n'est pas spécifiquement mentionnée dans un script d'éditeur de liens.

    MODE peut prendre l'une des valeurs suivantes :

    "place"
    Les sections orphelines sont placées dans une section de sortie appropriée en suivant la stratégie décrite dans Sections Orphelines. L'option --unique affecte également la manière dont les sections sont placées.
    "discard"
    Toutes les sections orphelines sont jetées, en les plaçant dans la section /DISCARD/.
    "warn"
    L'éditeur de liens placera la section orpheline comme pour "place" et émettra également un avertissement.
    "error"
    L'éditeur de liens se terminera avec une erreur si une section orpheline est trouvée.

    Par défaut, si --orphan-handling n'est pas donné, la valeur est "place".

    --unique[=SECTION]
    Crée une section de sortie distincte pour chaque section d'entrée correspondant à SECTION, ou si l'argument joker optionnel SECTION est manquant, pour chaque section d'entrée orpheline. Une section orpheline est une section qui n'est pas spécifiquement mentionnée dans un script d'éditeur de liens. Vous pouvez utiliser cette option plusieurs fois sur la ligne de commande ; elle empêche la fusion normale des sections d'entrée portant le même nom, remplaçant les affectations de sections de sortie dans un script d'éditeur de liens.

    --version

    --discard-all

    -X

    -z keyword

    call-nop=prefix-addr
    call-nop=suffix-nop
    call-nop=prefix-byte
    call-nop=suffix-byte
    Spécifie le remplissage NOP de 1 octet lors de la transformation d'un appel indirect vers une fonction définie localement, foo, via son slot GOT. call-nop=prefix-addr génère "0x67 call foo". call-nop=suffix-nop génère "call foo 0x90". call-nop=prefix-byte génère "byte call foo". call-nop=suffix-byte génère "call foo byte".     -( archives -)
    --start-group archives --end-group
    Les archives doivent être une liste de fichiers d'archives. Elles peuvent être soit des noms de fichiers explicites, soit des options -l.

    Les archives spécifiées sont recherchées de manière répétée jusqu'à ce qu'aucune nouvelle référence indéfinie ne soit créée. Normalement, une archive n'est recherchée qu'une seule fois dans l'ordre où elle est spécifiée sur la ligne de commande. Si un symbole dans cette archive est nécessaire pour résoudre un symbole indéfini auquel il est fait référence par un objet dans une archive qui apparaît plus tard sur la ligne de commande, l'éditeur de liens ne pourrait pas résoudre cette référence. En groupant les archives, elles seront toutes recherchées de manière répétée jusqu'à ce que toutes les références possibles soient résolues.

    L'utilisation de cette option a un coût de performance significatif. Il est préférable de l'utiliser uniquement lorsqu'il existe des références circulaires inévitables entre deux archives ou plus.

    --no-accept-unknown-input-arch

Le comportement par défaut à partir de la version 2.14 est de rejeter de tels fichiers d'entrée, et donc l'option --accept-unknown-input-arch a été ajoutée pour rétablir l'ancien comportement.
    --as-needed
    --no-as-needed
    Cette option affecte les balises DT_NEEDED ELF pour les bibliothèques dynamiques mentionnées sur la ligne de commande après l'option --as-needed. Normalement, l'éditeur de liens ajoutera une balise DT_NEEDED pour chaque bibliothèque dynamique mentionnée sur la ligne de commande, indépendamment du fait que la bibliothèque soit réellement nécessaire ou non. --as-needed fait en sorte qu'une balise DT_NEEDED ne soit émise que pour une bibliothèque qui, *à ce stade de la liaison*, satisfait une référence symbole indéfini non faible provenant d'un fichier objet régulier ou, si la bibliothèque n'est pas trouvée dans les listes DT_NEEDED d'autres bibliothèques nécessaires, une référence symbole indéfini non faible d'une autre bibliothèque dynamique nécessaire. Les fichiers objets ou les bibliothèques apparaissant sur la ligne de commande *après* la bibliothèque en question n'affectent pas si la bibliothèque est considérée comme nécessaire. Ceci est similaire aux règles d'extraction des fichiers objets des archives. --no-as-needed rétablit le comportement par défaut.

    Remarque : sur les systèmes basés sur Linux, l'option --as-needed affecte également le comportement des options --rpath et --rpath-link. Voir la description de --rpath-link pour plus de détails.

    --cref
    Produire une table de références croisées. Si un fichier de carte de l'éditeur de liens est généré, la table de références croisées est imprimée dans le fichier de carte. Sinon, elle est imprimée sur la sortie standard.

    Le format de la table est intentionnellement simple, de sorte qu'il puisse être facilement traité par un script si nécessaire. Les symboles sont affichés, triés par nom. Pour chaque symbole, une liste de noms de fichiers est fournie. Si le symbole est défini, le premier fichier listé est l'emplacement de la définition. Si le symbole est défini comme une valeur commune, alors tous les fichiers où cela se produit apparaissent ensuite. Enfin, tous les fichiers qui référencent le symbole sont listés.

    --ctf-variables
    --no-ctf-variables
    Le format d'informations de débogage CTF prend en charge une section qui encode les noms et les types de variables trouvées dans le programme qui n'apparaissent dans aucune table de symboles. Ces variables ne peuvent clairement pas être recherchées par adresse par les débogueurs conventionnels, de sorte que l'espace utilisé pour leurs types et leurs noms est généralement gaspillé : les types sont généralement petits mais les noms ne le sont souvent pas. --ctf-variables provoque la génération d'une telle section. Le comportement par défaut peut être restauré avec --no-ctf-variables.

    share-unconflicted
    Placer tous les types qui n'ont pas de définitions ambiguës dans le dictionnaire partagé, où les débogueurs peuvent facilement y accéder, même s'ils n'apparaissent que dans une seule unité de traduction. C'est le comportement par défaut.
    share-duplicated
    Placer uniquement les types qui apparaissent dans plusieurs unités de traduction dans le dictionnaire partagé : les types ayant une seule définition vont dans des dictionnaires par unité de traduction. Les types ayant des définitions ambiguës dans plusieurs unités de traduction vont toujours dans des dictionnaires par unité de traduction. Cela tend à rendre le CTF plus grand, mais peut réduire la quantité de CTF dans le dictionnaire partagé. Pour de très grands projets, cela peut accélérer l'ouverture du CTF et économiser de la mémoire chez le consommateur CTF à l'exécution.
    --no-define-common
    Cette option inhibe l'attribution d'adresses aux symboles communs. La commande de script "INHIBIT_COMMON_ALLOCATION" a le même effet.

    L'option --no-define-common permet de découpler la décision d'attribuer des adresses aux symboles communs du choix du type de fichier de sortie ; sinon, un type de sortie non relocable force l'attribution d'adresses aux symboles communs. L'utilisation de --no-define-common permet aux symboles communs référencés depuis une bibliothèque partagée de se voir attribuer des adresses uniquement dans le programme principal. Cela élimine l'espace dupliqué inutilisé dans la bibliothèque partagée, et empêche également toute confusion potentielle lors de la résolution vers le mauvais duplicata lorsqu'il y a de nombreux modules dynamiques avec des chemins de recherche spécialisés pour la résolution des symboles à l'exécution.

C'est le comportement par défaut pour une édition de liens finale, mais cette option peut être utilisée pour modifier le comportement d'une édition de liens relocable (-r). La commande de script "FORCE_GROUP_ALLOCATION" a le même effet.
    --defsym=symbole=expression
    Crée un symbole global dans le fichier de sortie, contenant l'adresse absolue donnée par expression. Vous pouvez utiliser cette option autant de fois que nécessaire pour définir plusieurs symboles dans la ligne de commande. Une forme limitée d'arithmétique est prise en charge pour l'expression dans ce contexte : vous pouvez donner une constante hexadécimale ou le nom d'un symbole existant, ou utiliser "+" et "-" pour ajouter ou soustraire des constantes hexadécimales ou des symboles. Si vous avez besoin d'expressions plus élaborées, envisagez d'utiliser le langage de commande de l'éditeur de liens à partir d'un script. Note : il ne doit y avoir aucun espace blanc entre symbole, le signe égal ("=") et expression.

    L'éditeur de liens traite les arguments --defsym et les arguments -T dans l'ordre. Placer --defsym avant -T définira le symbole avant que le script de l'éditeur de liens de -T ne soit traité, tandis que placer --defsym après -T définira le symbole après que le script de l'éditeur de liens ait été traité. Cette différence a des conséquences pour les expressions dans le script de l'éditeur de liens qui utilisent les symboles --defsym ; l'ordre correct dépendra de ce que vous essayez d'accomplir.

    --demangle[=style]
    --no-demangle
    Ces options contrôlent si les noms de symboles doivent être désanguinolisés dans les messages d'erreur et autres sorties. Lorsque l'éditeur de liens est invité à désanguinoliser, il essaie de présenter les noms de symboles de manière lisible : il supprime les traits de soulignement initiaux s'ils sont utilisés par le format du fichier objet, et convertit les noms de symboles C++ mangled en noms lisibles par l'utilisateur. Différents compilateurs ont différents styles de mangling. L'argument optionnel de style de désanguinolisation peut être utilisé pour choisir un style de désanguinolisation approprié pour votre compilateur. L'éditeur de liens désanguinolise par défaut, sauf si la variable d'environnement COLLECT_NO_DEMANGLE est définie. Ces options peuvent être utilisées pour outrepasser le comportement par défaut.
    -Ifichier
    --dynamic-linker=fichier
    Définit le nom de l'éditeur de liens dynamique. Ceci n'est pertinent que lors de la génération d'exécutables ELF liés dynamiquement. L'éditeur de liens dynamique par défaut est normalement correct ; n'utilisez pas ceci sauf si vous savez ce que vous faites.
    --no-dynamic-linker
    Lors de la production d'un fichier exécutable, omettre la demande d'un éditeur de liens dynamique à utiliser au moment du chargement. Ceci n'est pertinent que pour les exécutables ELF qui contiennent des relocations dynamiques, et nécessite généralement un code de point d'entrée capable de traiter ces relocations.
    --embedded-relocs
    Cette option est similaire à l'option --emit-relocs, sauf que les relocations sont stockées dans une section spécifique à la cible. Cette option n'est prise en charge que par les cibles BFIN, CR16 et M68K.
    --disable-multiple-abs-defs
    Ne pas autoriser les définitions multiples avec des symboles inclus dans le nom de fichier invoqué par -R ou --just-symbols
    --fatal-warnings
    --no-fatal-warnings
    Traiter tous les avertissements comme des erreurs. Le comportement par défaut peut être restauré avec l'option --no-fatal-warnings.
    -w
    --no-warnings
    Ne pas afficher de messages d'avertissement ou d'erreur. Cela remplace --fatal-warnings s'il a été activé. Cette option peut être utilisée lorsqu'il est connu que le binaire de sortie ne fonctionnera pas, mais qu'il est toujours nécessaire de le créer.
    --force-exe-suffix
    S'assurer qu'un fichier de sortie a un suffixe .exe.

    Si un fichier de sortie entièrement lié et construit avec succès n'a pas de suffixe ".exe" ou ".dll", cette option force l'éditeur de liens à copier le fichier de sortie vers un fichier du même nom avec un suffixe ".exe". Cette option est utile lors de l'utilisation de makefiles Unix non modifiés sur un hôte Microsoft Windows, car certaines versions de Windows n'exécuteront pas une image sauf si elle se termine par un suffixe ".exe".

    --gc-sections
    --no-gc-sections
    Activer la collecte des déchets des sections d'entrée inutilisées. Elle est ignorée sur les cibles qui ne prennent pas en charge cette option. Le comportement par défaut (ne pas effectuer cette collecte des déchets) peut être restauré en spécifiant --no-gc-sections sur la ligne de commande. Notez que la collecte des déchets pour les cibles au format COFF et PE est prise en charge, mais l'implémentation est actuellement considérée comme expérimentale.

    --gc-sections détermine quelles sections d'entrée sont utilisées en examinant les symboles et les relocations. La section contenant le symbole d'entrée et toutes les sections contenant des symboles indéfinis sur la ligne de commande seront conservées, tout comme les sections contenant des symboles référencés par des objets dynamiques. Notez que lors de la construction de bibliothèques partagées, l'éditeur de liens doit supposer que tout symbole visible est référencé. Une fois cet ensemble initial de sections déterminé, l'éditeur de liens marque récursivement comme utilisées toutes les sections référencées par leurs relocations. Voir --entry, --undefined et --gc-keep-exported.

    Cette option peut être définie lors d'une édition de liens partielle (activée avec l'option -r). Dans ce cas, la racine des symboles conservés doit être explicitement spécifiée soit par l'une des options --entry, --undefined, ou --gc-keep-exported, soit par une commande "ENTRY" dans le script de l'éditeur de liens.

    En tant qu'extension GNU, les sections d'entrée ELF marquées avec le drapeau "SHF_GNU_RETAIN" ne seront pas collectées.

    --print-gc-sections
    --no-print-gc-sections
    Lister toutes les sections supprimées par la collecte des déchets. La liste est imprimée sur stderr. Cette option n'est efficace que si la collecte des déchets a été activée via l'option --gc-sections. Le comportement par défaut (ne pas lister les sections supprimées) peut être restauré en spécifiant --no-print-gc-sections sur la ligne de commande.
    --gc-keep-exported
    Lorsque --gc-sections est activé, cette option empêche la collecte des déchets des sections d'entrée inutilisées qui contiennent des symboles globaux ayant une visibilité par défaut ou protégée. Cette option est destinée à être utilisée pour les exécutables où les sections non référencées seraient autrement collectées indépendamment de la visibilité externe des symboles contenus. Notez que cette option n'a aucun effet lors de la liaison d'objets partagés, car c'est déjà le comportement par défaut. Cette option n'est prise en charge que pour les cibles au format ELF.
    --print-output-format
    Imprimer le nom du format de sortie par défaut (potentiellement influencé par d'autres options de ligne de commande). C'est la chaîne qui apparaîtrait dans une commande de script d'éditeur de liens "OUTPUT_FORMAT".
    --print-memory-usage
    Imprimer la taille utilisée, la taille totale et la taille utilisée des régions mémoire créées avec le
    MEMORY
    Imprimer un résumé de l'utilisation de la mémoire. Ceci est utile sur les cibles embarquées pour avoir une vue rapide de la quantité de mémoire libre. Le format de la sortie comporte une ligne d'en-tête et une ligne par région. Il est à la fois lisible par l'homme et facilement analysable par des outils. Voici un exemple de sortie : 
    Région mémoire       Taille utilisée  Taille région  % utilisée
             ROM :        256 Ko           1 Mo     25.00 %
             RAM :          32 B           2 Go      0.00 %

    Note : si vous souhaitez connaître l'utilisation de la mémoire par l'éditeur de liens lui-même, l'option --stats le fera.

    --help
    Imprimer un résumé des options en ligne de commande sur la sortie standard et quitter.
    --target-help
    Imprimer un résumé de toutes les options spécifiques à la cible sur la sortie standard et quitter.
    -Map=fichier_map
    Imprimer une carte de liaison dans le fichier fichier_map. Voir la description de l'option -M, ci-dessus. Si fichier_map est juste le caractère "-" alors la carte sera écrite sur stdout.

    Spécifier un répertoire comme fichier_map fait que la carte de liaison est écrite dans un fichier à l'intérieur du répertoire. Normalement, le nom du fichier à l'intérieur du répertoire est calculé à partir du nom de base du fichier de sortie avec ".map" ajouté. Si cependant le caractère spécial "%" est utilisé, alors celui-ci sera remplacé par le chemin complet du fichier de sortie. De plus, s'il y a des caractères après le symbole %, alors ".map" ne sera plus ajouté.

    -o foo.exe -Map=bar                  [Crée ./bar]
-o ../dir/foo.exe -Map=bar           [Crée ./bar]
-o foo.exe -Map=../dir               [Crée ../dir/foo.exe.map]
-o ../dir2/foo.exe -Map=../dir       [Crée ../dir/foo.exe.map]
-o foo.exe -Map=%                    [Crée ./foo.exe.map]
-o ../dir/foo.exe -Map=%             [Crée ../dir/foo.exe.map]
-o foo.exe -Map=%.bar                [Crée ./foo.exe.bar]
-o ../dir/foo.exe -Map=%.bar         [Crée ../dir/foo.exe.bar]
-o ../dir2/foo.exe -Map=../dir/%     [Crée ../dir/../dir2/foo.exe.map]
-o ../dir2/foo.exe -Map=../dir/%.bar [Crée ../dir/../dir2/foo.exe.bar]

    Il est erroné de spécifier plus d'un caractère "%".

    Si le fichier carte existe déjà, il sera écrasé par cette opération.

    --no-keep-memory
    Normalement, ld optimise la vitesse au détriment de l'utilisation de la mémoire en mettant en cache les tables de symboles des fichiers d'entrée en mémoire. Cette option indique à ld d'optimiser plutôt l'utilisation de la mémoire, en relisant les tables de symboles si nécessaire. Cela peut être nécessaire si ld manque de mémoire lors de la liaison d'un gros exécutable.
    --no-undefined
    -z defs
    Signaler les références de symboles non résolues provenant des fichiers objets réguliers. Ceci est fait même si l'éditeur de liens crée une bibliothèque partagée non symbolique. Le commutateur --[no-]allow-shlib-undefined contrôle le comportement pour le signalement des références non résolues trouvées dans les bibliothèques partagées en cours de liaison.

    Les effets de cette option peuvent être annulés en utilisant "-z undefs".

    --allow-multiple-definition
    -z muldefs
    Normalement, lorsqu'un symbole est défini plusieurs fois, l'éditeur de liens signale une erreur fatale. Ces options autorisent les définitions multiples et la première définition sera utilisée.
    --allow-shlib-undefined
    --no-allow-shlib-undefined
    Autorise ou interdit les symboles indéfinis dans les bibliothèques partagées. Ce commutateur est similaire à --no-undefined sauf qu'il détermine le comportement lorsque les symboles indéfinis se trouvent dans une bibliothèque partagée plutôt qu'un fichier objet régulier. Il n'affecte pas la manière dont les symboles indéfinis dans les fichiers objets réguliers sont gérés.

    Le comportement par défaut est de signaler les erreurs pour tous les symboles indéfinis référencés dans les bibliothèques partagées si l'éditeur de liens est utilisé pour créer un exécutable, mais de les autoriser si l'éditeur de liens est utilisé pour créer une bibliothèque partagée.

    Les raisons pour lesquelles les références de symboles indéfinis dans les bibliothèques partagées spécifiées au moment de la liaison sont autorisées sont les suivantes :

    • Une bibliothèque partagée spécifiée au moment de la liaison peut ne pas être la même que celle disponible au moment du chargement, donc le symbole pourrait en fait être résoluble au moment du chargement.
    • Il existe certains systèmes d'exploitation, par exemple BeOS et HPPA, où les symboles indéfinis dans les bibliothèques partagées sont normaux.

      Le noyau BeOS, par exemple, patch les bibliothèques partagées au moment du chargement pour sélectionner la fonction la plus appropriée pour l'architecture actuelle. Ceci est utilisé, par exemple, pour sélectionner dynamiquement une fonction memset appropriée.

    --error-handling-script=nom_script
    Si cette option est fournie, l'éditeur de liens invoquera nom_script chaque fois qu'une erreur sera rencontrée. Actuellement cependant, seuls deux types d'erreurs sont pris en charge : symboles manquants et bibliothèques manquantes. Deux arguments seront passés au script : le mot-clé "undefined-symbol" ou `missing-lib" et le nom du symbole indéfini ou de la bibliothèque manquante. L'intention est que le script fournisse des suggestions à l'utilisateur quant à l'endroit où le symbole ou la bibliothèque pourrait être trouvé. Après que le script aura terminé, le message d'erreur normal de l'éditeur de liens sera affiché.

    La disponibilité de cette option est contrôlée par un commutateur de configuration, elle peut donc ne pas être présente dans des implémentations spécifiques.

    --no-undefined-version
    Normalement, lorsqu'un symbole a une version indéfinie, l'éditeur de liens l'ignore. Cette option interdit les symboles avec une version indéfinie et une erreur fatale sera émise à la place.
    --default-symver
    Créer et utiliser une version de symbole par défaut (le soname) pour les symboles exportés non versionnés.
    --default-imported-symver
    Créer et utiliser une version de symbole par défaut (le soname) pour les symboles importés non versionnés.
    --no-warn-mismatch
    Normalement, ld produira une erreur si vous essayez de lier ensemble des fichiers d'entrée qui ne correspondent pas pour une raison quelconque, peut-être parce qu'ils ont été compilés pour des processeurs différents ou pour des architectures différentes (endianness). Cette option indique à ld qu'il doit silencieusement autoriser de telles erreurs potentielles. Cette option ne doit être utilisée qu'avec prudence, dans les cas où vous avez pris des mesures spéciales qui garantissent que les erreurs de l'éditeur de liens sont inappropriées.
    --no-warn-search-mismatch
    Normalement, ld produira un avertissement s'il trouve une bibliothèque incompatible lors d'une recherche de bibliothèque. Cette option supprime l'avertissement.
    --no-whole-archive
    Désactiver l'effet de l'option --whole-archive pour les archives suivantes.
    --noinhibit-exec
    Conserver le fichier de sortie exécutable tant qu'il est utilisable. Normalement, l'éditeur de liens ne produira pas de fichier de sortie s'il rencontre des erreurs pendant le processus de liaison ; il se termine sans écrire de fichier de sortie lorsqu'il émet une erreur quelconque.
    -nostdlib
    Ne rechercher que dans les répertoires de bibliothèques explicitement spécifiés sur la ligne de commande. Les répertoires de bibliothèques spécifiés dans les scripts de l'éditeur de liens (y compris les scripts de l'éditeur de liens spécifiés sur la ligne de commande) sont ignorés.
    --oformat=format_sortie
    ld peut être configuré pour prendre en charge plus d'un type de fichier objet. Si votre ld est configuré de cette manière, vous pouvez utiliser l'option --oformat pour spécifier le format binaire pour le fichier objet de sortie. Même lorsque ld est configuré pour prendre en charge des formats d'objets alternatifs, vous n'avez généralement pas besoin de le spécifier, car ld devrait être configuré pour produire en tant que format de sortie par défaut le format le plus courant sur chaque machine. format_sortie est une chaîne de caractères, le nom d'un format particulier pris en charge par les bibliothèques BFD. (Vous pouvez lister les formats binaires disponibles avec objdump -i.) La commande de script "OUTPUT_FORMAT" peut également spécifier le format de sortie, mais cette option la remplace.
    --out-implib fichier
    Créer une bibliothèque d'importation dans fichier correspondant à l'exécutable que l'éditeur de liens génère (par exemple, une DLL ou un programme ELF). Cette bibliothèque d'importation (qui devrait s'appeler "*.dll.a" ou "*.a" pour les DLL) peut être utilisée pour lier des clients contre l'exécutable généré ; ce comportement permet d'éviter une étape distincte de création de bibliothèque d'importation (par exemple, "dlltool" pour les DLL). Cette option n'est disponible que pour les ports de l'éditeur de liens ciblant i386 PE et ELF.
    -pie
    --pic-executable
    Créer un exécutable indépendant de la position. Ceci n'est actuellement pris en charge que sur les plateformes ELF. Les exécutables indépendants de la position sont relocalisés par l'éditeur de liens dynamique à l'adresse virtuelle que le système d'exploitation choisit pour eux, ce qui peut varier entre les invocations. Ils sont marqués ET_DYN dans l'en-tête du fichier ELF, mais diffèrent des bibliothèques partagées à plusieurs égards. En particulier, les symboles définis dans un PIE par défaut ne peuvent pas être remplacés par un autre objet, comme c'est le cas dans une bibliothèque partagée.
    -no-pie
    Créer un exécutable dépendant de la position. C'est le comportement par défaut.
    -qmagic
    Cette option est ignorée pour la compatibilité Linux.
    -Qy
    Cette option est ignorée pour la compatibilité SVR4.
    --relax
    --no-relax
    Une option avec des effets dépendant de la machine. Cette option n'est prise en charge que sur quelques
    cibles.

    Sur certaines plateformes, l'option --relax effectue des optimisations globales spécifiques à la cible qui deviennent possibles lorsque l'éditeur de liens résout l'adressage dans le programme, telles que la relaxation des modes d'adressage, la synthèse de nouvelles instructions, la sélection d'une version plus courte des instructions actuelles et la combinaison de valeurs constantes.

    Sur certaines plateformes, ces optimisations globales au moment de l'édition des liens peuvent rendre le débogage symbolique de l'exécutable résultant impossible. C'est le cas connu pour la famille de processeurs Matsushita MN10200 et MN10300.

    Sur les plateformes où la fonctionnalité est prise en charge, l'option --no-relax la désactivera.

    Sur les plateformes où la fonctionnalité n'est pas prise en charge, les deux options --relax et --no-relax sont acceptées, mais ignorées.

    --retain-symbols-file=nom_fichier
    Conserve *uniquement* les symboles listés dans le fichier nom_fichier, en supprimant tous les autres. nom_fichier est simplement un fichier plat, avec un nom de symbole par ligne. Cette option est particulièrement utile dans les environnements (tels que VxWorks) où une grande table de symboles globale est accumulée progressivement, afin de conserver la mémoire d'exécution.

    --retain-symbols-file ne supprime *pas* les symboles indéfinis, ni les symboles nécessaires aux relocalisations.

    Vous ne pouvez spécifier --retain-symbols-file qu'une seule fois sur la ligne de commande. Elle remplace -s et -S.

    -rpath=rep
    Ajoute un répertoire au chemin de recherche des bibliothèques d'exécution. Ceci est utilisé lors de la liaison d'un exécutable ELF avec des objets partagés. Tous les arguments -rpath sont concaténés et passés à l'éditeur de liens d'exécution, qui les utilise pour localiser les objets partagés à l'exécution.

    L'option -rpath est également utilisée lors de la localisation des objets partagés requis par des objets partagés inclus explicitement dans la liaison ; voir la description de l'option -rpath-link. La recherche de -rpath de cette manière n'est prise en charge que par les éditeurs de liens natifs et les éditeurs de liens croisés qui ont été configurés avec l'option --with-sysroot.

    Si -rpath n'est pas utilisé lors de la liaison d'un exécutable ELF, le contenu de la variable d'environnement "LD_RUN_PATH" sera utilisé s'il est défini.

    L'option -rpath peut également être utilisée sur SunOS. Par défaut, sur SunOS, l'éditeur de liens formera un chemin de recherche d'exécution à partir de toutes les options -L qui lui sont données. Si une option -rpath est utilisée, le chemin de recherche d'exécution sera formé exclusivement à l'aide des options -rpath, ignorant les options -L. Cela peut être utile lors de l'utilisation de gcc, qui ajoute de nombreuses options -L qui peuvent se trouver sur des systèmes de fichiers montés via NFS.

    Pour la compatibilité avec d'autres éditeurs de liens ELF, si l'option -R est suivie d'un nom de répertoire, plutôt que d'un nom de fichier, elle est traitée comme l'option -rpath.

    -rpath-link=rep
    Lors de l'utilisation d'ELF ou de SunOS, une bibliothèque partagée peut en requérir une autre. Cela se produit lorsqu'une liaison "ld -shared" inclut une bibliothèque partagée comme l'un des fichiers d'entrée.

    Lorsque l'éditeur de liens rencontre une telle dépendance lors d'une liaison non partagée et non déplaçable, il essaiera automatiquement de localiser la bibliothèque partagée requise et de l'inclure dans la liaison, si elle n'est pas incluse explicitement. Dans un tel cas, plusieurs répertoires sont recherchés comme décrit ci-dessous. L'option -rpath-link spécifie le premier ensemble de répertoires à rechercher. Cette option peut spécifier une séquence de noms de répertoires soit en fournissant une liste de noms séparés par des deux-points, soit en apparaissant plusieurs fois.

    Les jetons $ORIGIN et $LIB peuvent apparaître dans ces répertoires de recherche. Ils seront remplacés par le chemin complet du répertoire contenant le programme ou l'objet partagé dans le cas de $ORIGIN et soit lib - pour les binaires 32 bits - soit lib64 - pour les binaires 64 bits - dans le cas de $LIB.

    La forme alternative de ces jetons - ${ORIGIN} et ${LIB} - peut également être utilisée. Le jeton $PLATFORM n'est pas pris en charge.

    L'option --rpath-link doit être utilisée avec prudence car elle remplace le chemin de recherche qui aurait pu être intégré en dur dans une bibliothèque partagée. Dans ce cas, il est possible d'utiliser involontairement un chemin de recherche différent de celui que l'éditeur de liens d'exécution aurait utilisé.

    Lorsque des bibliothèques partagées supplémentaires sont requises, l'éditeur de liens recherche les répertoires dans l'ordre listé ci-dessous afin de les trouver. Notez cependant que cela ne s'applique qu'aux bibliothèques supplémentaires nécessaires pour satisfaire les bibliothèques partagées déjà incluses. Cela ne s'applique *pas* aux bibliothèques qui sont incluses via l'option de ligne de commande -l. Les recherches des bibliothèques -l ne sont effectuées que dans les répertoires spécifiés par l'option -L.

    1.
    Tous les répertoires spécifiés par les options -rpath-link.
    2.
    Tous les répertoires spécifiés par les options -rpath. La différence entre -rpath et -rpath-link est que les répertoires spécifiés par les options -rpath sont inclus dans l'exécutable et utilisés à l'exécution, tandis que l'option -rpath-link n'est efficace qu'au moment de la liaison. La recherche de -rpath de cette manière n'est prise en charge que par les éditeurs de liens natifs et les éditeurs de liens croisés qui ont été configurés avec l'option --with-sysroot.
    3.
    Sur un système ELF, pour les éditeurs de liens natifs, si les options -rpath et -rpath-link n'ont pas été utilisées, recherchez le contenu de la variable d'environnement "LD_RUN_PATH".
    4.
    Sur SunOS, si l'option -rpath n'a pas été utilisée, recherchez tous les répertoires spécifiés à l'aide des options -L.
    5.
    Pour un éditeur de liens natif, recherchez le contenu de la variable d'environnement "LD_LIBRARY_PATH".
    6.
    Pour un éditeur de liens ELF natif, les répertoires dans "DT_RUNPATH" ou "DT_RPATH" d'une bibliothèque partagée sont recherchés pour les bibliothèques partagées dont elle a besoin. Les entrées "DT_RPATH" sont ignorées si les entrées "DT_RUNPATH" existent.
    7.
    Pour un éditeur de liens système Linux, si le fichier /etc/ld.so.conf existe, la liste des répertoires trouvés dans ce fichier. Remarque : le chemin vers ce fichier est préfixé par la valeur "sysroot", si elle est définie, puis par toute chaîne "prefix" si l'éditeur de liens a été configuré avec l'option --prefix=<chemin>.
    8.
    Pour un éditeur de liens natif sur un système FreeBSD, tous les répertoires spécifiés par la macro "_PATH_ELF_HINTS" définie dans le fichier d'en-tête elf-hints.h.
    9.
    Tous les répertoires spécifiés par une commande "SEARCH_DIR" dans un script d'éditeur de liens donné sur la ligne de commande, y compris les scripts spécifiés par -T (mais pas -dT).
    10.
    Les répertoires par défaut, normalement /lib et /usr/lib.
    11.
    Tous les répertoires spécifiés par un plugin LDPT_SET_EXTRA_LIBRARY_PATH.
    12.
    Tous les répertoires spécifiés par une commande "SEARCH_DIR" dans un script d'éditeur de liens par défaut.

    Notez cependant sur les systèmes basés sur Linux qu'il existe une mise en garde supplémentaire : si l'option --as-needed est active *et* qu'une bibliothèque partagée est trouvée qui satisferait normalement la recherche *et* que cette bibliothèque n'a pas de tag DT_NEEDED pour libc.so *et* qu'il existe une bibliothèque partagée plus loin dans l'ensemble des répertoires de recherche qui satisfait également la recherche *et* que cette seconde bibliothèque a un tag DT_NEEDED pour libc.so *alors* la seconde bibliothèque sera sélectionnée à la place de la première.

    Si la bibliothèque partagée requise n'est pas trouvée, l'éditeur de liens affichera un avertissement et continuera la liaison.

    --section-ordering-file=script
    Cette option est utilisée pour augmenter le script d'éditeur de liens actuel avec un mappage supplémentaire des sections d'entrée aux sections de sortie. Ce fichier doit utiliser la même syntaxe pour "SECTIONS" que celle utilisée dans les scripts d'éditeur de liens normaux, mais il ne doit rien faire d'autre que placer les sections d'entrée dans les sections de sortie. @pxref{SECTIONS}

    Une deuxième contrainte sur le script d'ordonnancement des sections est qu'il ne peut référencer que des sections de sortie déjà définies par le script d'éditeur de liens actuellement utilisé. (C'est-à-dire le script d'éditeur de liens par défaut ou un script spécifié sur la ligne de commande). L'avantage du script d'ordonnancement des sections est qu'il peut être utilisé pour mapper les sections d'entrée au début des sections de sortie, afin qu'elles puissent assurer l'ordonnancement des sections dans la section de sortie. Par exemple, imaginez que le script d'éditeur de liens par défaut ressemble à ceci :

    SECTIONS {
  .text : { *(.text.hot) ; *(.text .text.*) }
  .data : { *(.data.big) ; *(.data .data.*) }
  }

    Si un fichier d'ordonnancement de sections comme celui-ci est utilisé :

    .text : { *(.text.first) ; *(.text.z*) }
.data : { foo.o(.data.first) ; *(.data.small) }

    Cela serait équivalent à un script d'éditeur de liens comme celui-ci :

    SECTIONS {
  .text : { *(.text.first) ; *(.text.z*) ; *(.text.hot) ; *(.text .text.*) }
  .data : { foo.o(.data.first) ; *(.data.small) ; *(.data.big) ; *(.data .data.*) }
  }

    L'avantage du fichier d'ordonnancement de sections est qu'il peut être utilisé pour ordonner les sections qui importent à l'utilisateur sans avoir à se soucier des autres sections, des régions mémoire, ou de quoi que ce soit d'autre.

    Calcule et affiche des statistiques sur le fonctionnement du lieur, telles que le temps d'exécution et l'utilisation de la mémoire.

    Si l'argument facultatif filename n'est pas fourni, seules des informations de base sont rapportées, et elles sont envoyées au flux de sortie d'erreur standard. Si l'argument filename est fourni, des informations étendues sont écrites dans le fichier nommé. Si filename est défini uniquement sur le symbole -, alors les informations étendues sont envoyées au flux de sortie standard. Si filename commence par +, le fichier est ouvert en mode d'ajout plutôt qu'en mode d'écrasement.

    Si l'option -Map a été activée, les informations sont également enregistrées dans le fichier map. Remarque : si les options --stats et -Map ont toutes deux reçu des arguments filename et qu'ils correspondent, les informations ne seront écrites qu'une seule fois et non deux.

    Si la variable d'environnement "LD_STATS" est définie, cela se comporte comme l'option --stats. Si la valeur de la variable est une chaîne de caractères, elle sera utilisée comme nom d'un fichier dans lequel les informations doivent être enregistrées. Sinon, les informations seront envoyées au flux de sortie standard. L'utilisation de la variable d'environnement permet d'enregistrer des statistiques sans avoir à modifier la ligne de commande du lieur. Remarque : si la variable d'environnement et l'option --stats sont toutes deux utilisées, l'option --stats a la priorité.

De plus, les informations sont également rapportées pour une phase spéciale appelée ALL qui couvre l'ensemble du processus de liaison. Notez que les phases individuelles peuvent contenir ou se chevaucher, il ne faut donc pas supposer que les ressources globales utilisées par le lieur sont la somme des ressources utilisées par les phases individuelles.

    --warn-common
    Avertit lorsqu'un symbole commun est combiné avec un autre symbole commun ou avec une définition de symbole. Les éditeurs de liens Unix autorisent cette pratique quelque peu laxiste, mais les éditeurs de liens sur certains autres systèmes d'exploitation ne le font pas. Cette option vous permet de détecter des problèmes potentiels liés à la combinaison de symboles globaux. Malheureusement, certaines bibliothèques C utilisent cette pratique, vous pourriez donc recevoir des avertissements concernant des symboles dans les bibliothèques ainsi que dans vos programmes.

    Il existe trois types de symboles globaux, illustrés ici par des exemples en C :

    int i = 1;
    Une définition, qui va dans la section des données initialisées du fichier de sortie.
    extern int i;
    Une référence indéfinie, qui n'alloue pas d'espace. Il doit y avoir soit une définition, soit un symbole commun pour la variable quelque part.
    int i;
    Un symbole commun. S'il n'y a que des symboles communs (un ou plusieurs) pour une variable, elle va dans la zone des données non initialisées du fichier de sortie. L'éditeur de liens fusionne plusieurs symboles communs pour la même variable en un seul symbole. S'ils sont de tailles différentes, il choisit la taille la plus grande. L'éditeur de liens transforme un symbole commun en une déclaration, s'il existe une définition de la même variable.

Chaque avertissement se compose d'une paire de lignes : la première décrit le symbole venant d'être rencontré, et la seconde décrit le symbole précédent rencontré avec le même nom. Un ou les deux symboles seront des symboles communs.

    1.
    Transformation d'un symbole commun en une référence, car il existe déjà une définition pour le symbole. 
    <fichier>(<section>): avertissement : commun de `<symbole>'
   écrasé par définition
<fichier>(<section>): avertissement : défini ici
    2.
    Transformation d'un symbole commun en une référence, car une définition ultérieure du symbole est rencontrée. C'est le même cas que le précédent, sauf que les symboles sont rencontrés dans un ordre différent. 
    <fichier>(<section>): avertissement : définition de `<symbole>'
   écrasant le commun
<fichier>(<section>): avertissement : le commun est ici
    3.
    Fusion d'un symbole commun avec un symbole commun précédent de même taille. 
    <fichier>(<section>): avertissement : multiples communs
   de `<symbole>'
<fichier>(<section>): avertissement : le commun précédent est ici
    4.
    Fusion d'un symbole commun avec un symbole commun précédent plus grand. 
    <fichier>(<section>): avertissement : commun de `<symbole>'
   écrasé par un commun plus grand
<fichier>(<section>): avertissement : le commun plus grand est ici
    5.
    Fusion d'un symbole commun avec un symbole commun précédent plus petit. C'est le même cas que le précédent, sauf que les symboles sont rencontrés dans un ordre différent. 
    <fichier>(<section>): avertissement : commun de `<symbole>'

    --warn-execstack
    --warn-execstack-objects
    --no-warn-execstack
    Sur les plateformes ELF, l'éditeur de liens peut générer des messages d'avertissement s'il est invité à créer un fichier de sortie contenant une pile exécutable. Il y a trois états possibles :
    1.
    Ne génère aucun avertissement.
    2.
    Génère toujours des avertissements, même si la pile exécutable est demandée via l'option de ligne de commande -z execstack.
    3.
    Ne génère un avertissement que si un fichier objet demande une pile exécutable, mais pas si l'option -z execstack est utilisée.

    L'état par défaut dépend de la manière dont l'éditeur de liens a été configuré lors de sa construction. L'option --no-warn-execstack met toujours l'éditeur de liens dans l'état "pas d'avertissements". L'option --warn-execstack met l'éditeur de liens dans l'état "avertir toujours". L'option --warn-execstack-objects met l'éditeur de liens dans l'état "avertir uniquement pour les fichiers objets".

Ils peuvent spécifier qu'ils n'ont pas besoin d'une pile exécutable en ayant la même section, mais sans le bit exécutable défini. Si un fichier d'entrée n'a pas de section .note.GNU-stack, le comportement par défaut est spécifique à la cible. Pour certaines cibles, l'absence d'une telle section implique qu'une pile exécutable *est* requise. C'est souvent un problème pour les fichiers assembleur créés manuellement.

    Avertit si plusieurs valeurs de pointeur global sont nécessaires dans le fichier de sortie. Ceci n'est pertinent que pour certains processeurs, comme l'Alpha. Plus précisément, certains processeurs placent les constantes de grande valeur dans une section spéciale. Un registre spécial (le pointeur global) pointe au milieu de cette section, de sorte que les constantes puissent être chargées efficacement via un mode d'adressage relatif à un registre de base. Étant donné que le décalage en mode relatif à un registre de base est fixe et relativement petit (par exemple, 16 bits), cela limite la taille maximale du pool de constantes. Ainsi, dans les grands programmes, il est souvent nécessaire d'utiliser plusieurs valeurs de pointeur global pour pouvoir adresser toutes les constantes possibles. Cette option provoque un avertissement lorsque ce cas se produit.

    --wrap=symbole
    Utiliser une fonction d'encapsulation (wrapper) pour symbole. Toute référence indéfinie à symbole sera résolue en "__wrap_symbole". Toute référence indéfinie à "__real_symbole" sera résolue en symbole.

    Ceci peut être utilisé pour fournir une fonction d'encapsulation pour une fonction système. La fonction d'encapsulation doit être appelée "__wrap_symbole". Si elle souhaite appeler la fonction système, elle doit appeler "__real_symbole".

    Voici un exemple trivial :

    void *
__wrap_malloc (size_t c)
{
  printf ("malloc appelé avec %zu\n", c);
  return __real_malloc (c);
}

    Si vous liez d'autres codes avec ce fichier en utilisant --wrap malloc, tous les appels à "malloc" appelleront la fonction "__wrap_malloc" à la place. L'appel à "__real_malloc" dans "__wrap_malloc" appellera la vraie fonction "malloc".

    Vous pourriez également souhaiter fournir une fonction "__real_malloc", de sorte que les liaisons sans l'option --wrap réussissent. Si vous faites cela, vous ne devez pas placer la définition de "__real_malloc" dans le même fichier que "__wrap_malloc" ; si vous le faites, l'assembleur pourrait résoudre l'appel avant que l'éditeur de liens ait une chance de le rediriger vers "malloc".

    Seules les références indéfinies sont remplacées par l'éditeur de liens. Ainsi, les références internes à l'unité de traduction à symbole ne sont pas résolues en "__wrap_symbole". Dans l'exemple suivant, l'appel à "f" dans "g" n'est pas résolu en "__wrap_f".

    int
f (void)
{
  return 123;
}

int
g (void)
{
  return f();
}

    --compress-debug-sections=zlib
    --compress-debug-sections=zlib-gnu
    --compress-debug-sections=zlib-gabi

    Sur les plateformes ELF, ces options contrôlent la manière dont les sections de débogage DWARF sont compressées à l'aide de zlib.

    --compress-debug-sections=none ne compresse pas les sections de débogage DWARF. --compress-debug-sections=zlib-gnu compresse les sections de débogage DWARF et les renomme en commençant par .zdebug au lieu de .debug. --compress-debug-sections=zlib-gabi compresse également les sections de débogage DWARF, mais au lieu de les renommer, elle définit le drapeau SHF_COMPRESSED dans les en-têtes des sections.

    L'option --compress-debug-sections=zlib est un alias pour --compress-debug-sections=zlib-gabi.

    --compress-debug-sections=zstd compresse les sections de débogage DWARF à l'aide de zstd.

    Le comportement de compression par défaut varie en fonction de la cible impliquée et des options de configuration utilisées pour construire la toolchain. Le défaut peut être déterminé en examinant la sortie de l'option --help de l'éditeur de liens.

    --reduce-memory-overheads
    Cette option réduit les exigences mémoire à l'exécution de ld, au détriment de la vitesse de liaison. Elle a été introduite pour sélectionner l'ancien algorithme O(n^2) pour la génération du fichier de mappage de liaison, plutôt que le nouvel algorithme O(n) qui utilise environ 40% de mémoire en plus pour le stockage des symboles.

    Le commutateur --reduce-memory-overheads peut également être utilisé pour activer d'autres compromis dans les futures versions de l'éditeur de liens.

    The GNU linker

    SYNOPSIS

    ld [option...] [obj-file>...] [-llib>]...

    DESCRIPTION

    The GNU linker, ld, is a program that takes one or more object files and links them together. It may also take libraries of object files in order to resolve references and may produce one of several forms of output.

    The ld program is used as a front end to manage the invocation of the appropriate linker for the target.

    The linker supports several different types of output. The most common is a relocatable output file, which is the input to ld again. The default output format is usually executable.

    A third type of output is a core dump, used for debugging.

    Finally, a fourth type of output is a shared object, which can be linked with other objects to create other executables or shared objects.

    This document describes the options common to all targets, and then the options specific to certain targets.

    I386 PE LINKER

    The i386 PE linker supports the -shared option, which causes the output to be a dynamically linked library (DLL) instead of a normal executable. You should name the output "*.dll" when you use this option. In addition, the linker fully supports the standard "*.def" files, which may be specified on the linker command line like an object file (in fact, it should precede archives it exports symbols from, to ensure that they get linked in, just like a normal object file).

    In addition to the options common to all targets, the i386 PE linker support additional command-line options that are specific to the i386 PE target. Options that take values may be separated from their values by either a space or an equals sign.

    --add-stdcall-alias
    If given, symbols with a stdcall suffix (@nn) will be exported as-is and also with the suffix stripped. [This option is specific to the i386 PE targeted port of the linker]
    --base-file file
    Use file as the name of a file in which to save the base addresses of all the relocations needed for generating DLLs with dlltool. [This is an i386 PE specific option]
    --dll
    Create a DLL instead of a regular executable. You may also use -shared or specify a "LIBRARY" in a given ".def" file. [This option is specific to the i386 PE targeted port of the linker]
    --enable-long-section-names
    --disable-long-section-names
    The PE variants of the COFF object format add an extension that permits the use of section names longer than eight characters, the normal limit for COFF. By default, these names are only allowed in object files, as fully-linked executable images do not carry the COFF string table required to support the longer names. As a GNU extension, it is possible to allow their use in executable images as well, or to (probably pointlessly!) disallow it in object files, by using these two options. Executable images generated with these long section names are slightly non-standard, carrying as they do a string table, and may generate confusing output when examined with non-GNU PE-aware tools, such as file viewers and dumpers. However, GDB relies on the use of PE long section names to find Dwarf-2 debug information sections in an executable image at runtime, and so if neither option is specified on the command-line, ld will enable long section names, overriding the default and technically correct behaviour, when it finds the presence of debug information while linking an executable image and not stripping symbols. [This option is valid for all PE targeted ports of the linker]
    --enable-stdcall-fixup
    --disable-stdcall-fixup
    If the link finds a symbol that it cannot resolve, it will attempt to do "fuzzy linking" by looking for another defined symbol that differs only in the format of the symbol name (cdecl vs stdcall) and will resolve that symbol by linking to the match. For example, the undefined symbol "_foo" might be linked to the function "_foo@12", or the undefined symbol "_bar@16" might be linked to the function "_bar". When the linker does this, it prints a warning, since it normally should have failed to link, but sometimes import libraries generated from third-party dlls may need this feature to be usable. If you specify --enable-stdcall-fixup, this feature is fully enabled and warnings are not printed. If you specify --disable-stdcall-fixup, this feature is disabled and such mismatches are considered to be errors. [This option is specific to the i386 PE targeted port of the linker]

    Remarque : l'utilisation de l'extension « auto-import » rendra la section de texte du fichier image inscriptible. Cela n'est pas conforme à la spécification du format PE-COFF publiée par Microsoft.

    Remarque - l'utilisation de l'extension « auto-import » provoquera également le placement des données en lecture seule, qui seraient normalement placées dans la section .rdata, dans la section .data à la place. Ceci afin de contourner un problème avec les constantes décrit ici : http://www.cygwin.com/ml/cygwin/2004-09/msg01101.html

    L'utilisation de « auto-import » fonctionne généralement « tout simplement » - mais parfois vous pourriez voir ce message :

    "la variable '<var>' ne peut pas être auto-importée. Veuillez lire la documentation de ld pour "--enable-auto-import" pour plus de détails."

    Ce message apparaît lorsque certaines (sous-)expressions accèdent à une adresse donnée par la somme de deux constantes (les tables d'importation Win32 n'en autorisent qu'une). Les instances où cela peut se produire incluent les accès aux champs membres de variables de structure importées d'une DLL, ainsi que l'utilisation d'un index constant dans un tableau importé d'une DLL. Tout variable multi-mots (tableaux, structures, long long, etc.) peut déclencher cette condition d'erreur. Cependant, quel que soit le type de données exact de la variable exportée fautive, ld la détectera toujours, émettra l'avertissement et s'arrêtera.

    Il existe plusieurs façons de résoudre ce problème, quel que soit le type de données de la variable exportée :

    Une façon est d'utiliser le commutateur --enable-runtime-pseudo-reloc. Cela laisse la tâche d'ajuster les références dans votre code client pour l'environnement d'exécution, donc cette méthode ne fonctionne que lorsque l'environnement d'exécution prend en charge cette fonctionnalité.

    Une deuxième solution consiste à forcer l'une des 'constantes' à être une variable - c'est-à-dire, inconnue et non optimisable au moment de la compilation. Pour les tableaux, il existe deux possibilités : a) rendre l'indexé (l'adresse du tableau) variable, ou b) rendre l'index 'constant' variable. Ainsi :

    extern type extern_array[];
extern_array[1] -->
   { volatile type *t=extern_array; t[1] }

    ou

    extern type extern_array[];
extern_array[1] -->
   { volatile int t=1; extern_array[t] }

    Pour les structures (et la plupart des autres types de données multi-mots), la seule option est de rendre la structure elle-même (ou le long long, ou le ...) variable :

    extern struct s extern_struct;
extern_struct.field -->
   { volatile struct s *t=&extern_struct; t->field }

    ou

    extern long long extern_ll;
extern_ll -->
  { volatile long long * local_ll=&extern_ll; *local_ll }

    Une troisième méthode pour traiter cette difficulté est d'abandonner « auto-import » pour le symbole fautif et de le marquer avec "__declspec(dllimport)". Cependant, en pratique, cela nécessite d'utiliser des #defines au moment de la compilation pour indiquer si vous compilez une DLL, si vous compilez du code client qui se liera à la DLL, ou si vous compilez/liez simplement une bibliothèque statique. Lors du choix entre les différentes méthodes de résolution du problème 'adresse directe avec décalage constant', vous devriez considérer l'usage typique dans le monde réel :

    Original :

    --foo.h
extern int arr[];
--foo.c
#include "foo.h"
void main(int argc, char **argv){
  printf("%d\n",arr[1]);
}

    Solution 1 :

    --foo.h
extern int arr[];
--foo.c
#include "foo.h"
void main(int argc, char **argv){
  /* Ce contournement est pour win32 et cygwin; ne pas "optimiser" */
  volatile int *parr = arr;
  printf("%d\n",parr[1]);
}

    Solution 2 :

    --foo.h
/* Remarque: auto-export est supposé (pas de __declspec(dllexport)) */
#if (defined(_WIN32) || defined(__CYGWIN__)) && \
  !(defined(FOO_BUILD_DLL) || defined(FOO_STATIC))
#define FOO_IMPORT __declspec(dllimport)
#else
#define FOO_IMPORT
#endif
extern FOO_IMPORT int arr[];
--foo.c
#include "foo.h"
void main(int argc, char **argv){
  printf("%d\n",arr[1]);
}

    Une quatrième façon d'éviter ce problème est de recoder votre bibliothèque pour utiliser une interface fonctionnelle plutôt qu'une interface de données pour les variables fautives (par exemple, les fonctions d'accès set_foo() et get_foo()).

    DESCRIPTION

    The GNU linker, ld, combines a number of object files and libraries together in order to begin the process of creating an executable or a shared library. It can also be used to produce shared libraries that are not yet linked.

    ld is usually invoked via the compiler driver program (e.g. gcc). Invoking ld directly may lead to unexpected results, as ld relies on the compiler driver to specify the correct linker script and command-line options.

    OPTIONS

    --no-omagic
    Equivalent to --nmagic for pdp11-aout.

    ENVIRONMENT

    You can change the behaviour of ld with the environment variables "GNUTARGET", "LDEMULATION" and "COLLECT_NO_DEMANGLE".

    "GNUTARGET" determines the input-file object format if you don't use -b (or its synonym --format). Its value should be one of the BFD names for an input format. If there is no "GNUTARGET" in the environment, ld uses the natural format of the target. If "GNUTARGET" is set to "default" then BFD attempts to discover the input format by examining binary input files; this method often succeeds, but there are potential ambiguities, since there is no method of ensuring that the magic number used to specify object-file formats is unique. However, the configuration procedure for BFD on each system places the conventional format for that system first in the search-list, so ambiguities are resolved in favor of convention.

    "LDEMULATION" determines the default emulation if you don't use the -m option. The emulation can affect various aspects of linker behaviour, particularly the default linker script. You can list the available emulations with the --verbose or -V options. If the -m option is not used, and the "LDEMULATION" environment variable is not defined, the default emulation depends upon how the linker was configured.

    Normally, the linker will default to demangling symbols. However, if "COLLECT_NO_DEMANGLE" is set in the environment, then it will default to not demangling symbols. This environment variable is used in a similar fashion by the "gcc" linker wrapper program. The default may be overridden by the --demangle and --no-demangle options.

    If the PE/COFF specific --insert-timestamp is active and the SOURCE_DATE_EPOCH environment variable is defined, then the timestamp value in this variable will be inserted into the COFF header instead of the current time.

    If the "LD_STATS" environment variable is defined then linker resource use information will be recorded, just as if the --stats option had been used. If the "LD_STATS" variable has a string value then this will used as the name of a file into which the information should be stored. Otherwise the information will be sent to the standard output stream.

    DESCRIPTION

    L'éditeur de liens GNU, ld, combine un certain nombre de fichiers objets et de bibliothèques pour commencer le processus de création d'un exécutable ou d'une bibliothèque partagée. Il peut également être utilisé pour produire des bibliothèques partagées qui ne sont pas encore liées.

    ld est généralement appelé via le programme pilote du compilateur (par exemple, gcc). L'invocation directe de ld peut conduire à des résultats inattendus, car ld s'appuie sur le pilote du compilateur pour spécifier le script d'édition de liens et les options de ligne de commande corrects.

    OPTIONS

    --no-omagic
    Équivalent à --nmagic pour pdp11-aout.

    ENVIRONNEMENT

    Vous pouvez modifier le comportement de ld avec les variables d'environnement "GNUTARGET", "LDEMULATION" et "COLLECT_NO_DEMANGLE".

    "GNUTARGET" détermine le format objet du fichier d'entrée si vous n'utilisez pas -b (ou son synonyme --format). Sa valeur doit être l'un des noms BFD pour un format d'entrée. S'il n'y a pas de "GNUTARGET" dans l'environnement, ld utilise le format naturel de la cible. Si "GNUTARGET" est défini sur "default", alors BFD tente de découvrir le format d'entrée en examinant les fichiers d'entrée binaires ; cette méthode réussit souvent, mais il existe des ambiguïtés potentielles, car il n'existe aucun moyen de garantir que le nombre magique utilisé pour spécifier les formats de fichiers objets est unique. Cependant, la procédure de configuration pour BFD sur chaque système place le format conventionnel pour ce système en premier dans la liste de recherche, de sorte que les ambiguïtés sont résolues en faveur de la convention.

    "LDEMULATION" détermine l'émulation par défaut si vous n'utilisez pas l'option -m. L'émulation peut affecter divers aspects du comportement de l'éditeur de liens, en particulier le script d'édition de liens par défaut. Vous pouvez lister les émulations disponibles avec les options --verbose ou -V. Si l'option -m n'est pas utilisée et que la variable d'environnement "LDEMULATION" n'est pas définie, l'émulation par défaut dépend de la façon dont l'éditeur de liens a été configuré.

    Normalement, l'éditeur de liens désancrera les symboles par défaut. Cependant, si "COLLECT_NO_DEMANGLE" est défini dans l'environnement, alors il désancre pas les symboles par défaut. Cette variable d'environnement est utilisée de manière similaire par le programme wrapper de l'éditeur de liens "gcc". La valeur par défaut peut être remplacée par les options --demangle et --no-demangle.

    Si le --insert-timestamp spécifique à PE/COFF est actif et que la variable d'environnement SOURCE_DATE_EPOCH est définie, alors la valeur d'horodatage de cette variable sera insérée dans l'en-tête COFF au lieu de l'heure actuelle.

    Si la variable d'environnement "LD_STATS" est définie, alors les informations d'utilisation des ressources de l'éditeur de liens seront enregistrées, comme si l'option --stats avait été utilisée. Si la variable "LD_STATS" a une valeur de chaîne, alors celle-ci sera utilisée comme nom de fichier dans lequel les informations doivent être stockées. Sinon, les informations seront envoyées au flux de sortie standard.
