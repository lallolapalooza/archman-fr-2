LDAP_TABLE(5) Manuel des formats de fichiers LDAP_TABLE(5)

NOM

ldap_table - Configuration du client LDAP de Postfix

SYNTAXE

postmap -q "chaîne" ldap:/etc/postfix/nom_fichier
postmap -q - ldap:/etc/postfix/nom_fichier <fichier_entree

DESCRIPTION


Le système de messagerie Postfix utilise des tables optionnelles pour la réécriture d'adresses ou le routage de courriers. Ces tables sont généralement au format dbm ou db.

Alternativement, les tables de recherche peuvent être spécifiées comme bases de données LDAP.

Pour utiliser les recherches LDAP, définissez une source LDAP comme table de recherche dans main.cf, par exemple :

    alias_maps = ldap:/etc/postfix/ldap-aliases.cf

Le fichier /etc/postfix/ldap-aliases.cf a le même format que le fichier main.cf de Postfix, et peut spécifier les paramètres décrits ci-dessous. Un exemple est donné à la fin de ce manuel.

Cette méthode de configuration est disponible avec la version 2.1 de Postfix et ultérieures. Voir la section « PARAMÈTRES OBSOLÈTES DE MAIN.CF » ci-dessous pour les versions plus anciennes de Postfix.

Pour plus de détails sur SSL et STARTTLS LDAP, voir la section sur SSL et STARTTLS ci-dessous.

MEMBERSHIP DE LISTE

Lors de l'utilisation de LDAP pour stocker des listes telles que $mynetworks, $mydestination, $relay_domains, $local_recipient_maps, etc., il est important de comprendre que la table doit stocker chaque membre de la liste comme une clé séparée. La recherche dans la table vérifie l'*existence* de la clé. Voir « Listes Postfix contre tables » dans le document DATABASE_README pour une discussion.

NE CRÉEZ PAS de tables qui retournent la liste complète des domaines dans $mydestination ou $relay_domains etc., ou des adresses IP dans $mynetworks.

CRÉEZ des tables avec chaque élément correspondant comme clé et une valeur arbitraire. Avec les bases de données LDAP, il n'est pas rare de retourner la clé elle-même.

Par exemple, NE FAITES JAMAIS ceci dans une map définissant $mydestination :

    query_filter = domain=*
    result_attribute = domain

Faites ceci à la place :

    query_filter = domain=%s
    result_attribute = domain

PARAMÈTRES LDAP GÉNÉRAUX

Dans le texte ci-dessous, les valeurs par défaut sont indiquées entre parenthèses. Remarque : n'utilisez pas de guillemets dans ces variables ; au moins, pas tant que les routines de configuration de Postfix ne savent pas comment gérer les chaînes entre guillemets.

server_host (par défaut: localhost)
Le nom de l'hôte exécutant le serveur LDAP, par ex. 
    server_host = ldap.example.com

Selon la bibliothèque cliente LDAP que vous utilisez, il devrait être possible de spécifier plusieurs serveurs ici, la bibliothèque essayant dans l'ordre si le premier échoue. Il devrait également être possible de donner à chaque serveur de la liste un port différent (remplaçant server_port ci-dessous), en les nommant comme suit :

    server_host = ldap.example.com:1444

REMARQUE : ce client se reconnectera immédiatement après un échec unique, et échouera une requête de recherche après un deuxième échec également.

Avec OpenLDAP, une (liste de) URL LDAP peut être utilisée pour spécifier à la fois le(s) nom(s) d'hôte et le(s) port(s) :

    server_host = ldap://ldap.example.com:1444
                ldap://ldap2.example.com:1444

Toutes les URL LDAP acceptées par la bibliothèque OpenLDAP sont prises en charge, y compris les connexions via des sockets de domaine UNIX, et LDAP SSL (ce dernier à condition qu'OpenLDAP ait été compilé avec le support SSL) :

    server_host = ldapi://%2Fsome%2Fpath
                ldaps://ldap.example.com:636
server_port (par défaut: 389)
Le port sur lequel le serveur LDAP écoute, par ex. 
    server_port = 778
timeout (par défaut: 10 secondes)
Le nombre de secondes qu'une recherche peut prendre avant d'expirer, par ex.



timeout = 5

search_base (Pas de valeur par défaut ; vous devez configurer ceci)
Le DN de base RFC2253 sur lequel effectuer la recherche, par ex. 
    search_base = dc=votre, dc=com
Avec Postfix 2.2 et ultérieur, ce paramètre prend en charge les expansions '%' suivantes :
%%
Ceci est remplacé par un caractère '%' littéral.
%s
Ceci est remplacé par la clé d'entrée. Le quoting RFC 2253 est utilisé pour s'assurer que la clé d'entrée n'ajoute pas de métacaractères inattendus.
%u
Lorsque la clé d'entrée est une adresse de la forme utilisateur@domaine, %u est remplacé par la partie locale de l'adresse (citée RFC 2253). Sinon, %u est remplacé par toute la chaîne de recherche. Si la partie locale est vide, la recherche est supprimée et ne retourne aucun résultat.
%d
Lorsque la clé d'entrée est une adresse de la forme utilisateur@domaine, %d est remplacé par la partie domaine de l'adresse (citée RFC 2253). Sinon, la recherche est supprimée et ne retourne aucun résultat.
%[SUD]
Pour le paramètre search_base, les équivalents majuscules des expansions ci-dessus se comportent de manière identique à leurs homologues minuscules. Avec le paramètre result_format (précédemment appelé result_filter, voir la section AUTRES FONCTIONNALITÉS OBSOLÈTES et ci-dessous), ils développent les composants correspondants de la clé d'entrée plutôt que la valeur du résultat.
%[1-9]
Les motifs %1, %2, ... %9 sont remplacés par le composant le plus significatif correspondant du domaine de la clé d'entrée. Si la clé d'entrée est utilisateur@mail.example.com, alors %1 est com, %2 est example et %3 est mail. Si la clé d'entrée n'est pas qualifiée ou n'a pas assez de composants de domaine pour satisfaire tous les motifs spécifiés, la recherche est supprimée et ne retourne aucun résultat.
query_filter (par défaut: mailacceptinggeneralid=%s)
Le filtre RFC2254 utilisé pour rechercher dans le répertoire, où %s est un substitut pour l'adresse que Postfix essaie de résoudre, par ex. 
    query_filter = (&(mail=%s)(paid_up=true))

Ce paramètre prend en charge les expansions '%' suivantes :

%%
Ceci est remplacé par un caractère '%' littéral. (Postfix 2.2 et ultérieur).
%s
Ceci est remplacé par la clé d'entrée. Le quoting RFC 2254 est utilisé pour s'assurer que la clé d'entrée n'ajoute pas de métacaractères inattendus.
%u
Lorsque la clé d'entrée est une adresse de la forme utilisateur@domaine, %u est remplacé par la partie locale de l'adresse (citée RFC 2254). Sinon, %u est remplacé par toute la chaîne de recherche. Si la partie locale est vide, la recherche est supprimée et ne retourne aucun résultat.
%d
Lorsque la clé d'entrée est une adresse de la forme utilisateur@domaine, %d est remplacé par la partie domaine de l'adresse (citée RFC 2254). Sinon, la recherche est supprimée et ne retourne aucun résultat.
%[SUD]
Les équivalents majuscules des expansions ci-dessus se comportent dans le paramètre query_filter de manière identique à leurs homologues minuscules. Avec le paramètre result_format (précédemment appelé result_filter, voir la section AUTRES FONCTIONNALITÉS OBSOLÈTES et ci-dessous), ils développent les composants correspondants de la clé d'entrée plutôt que la valeur du résultat.
Les expansions %S, %U et %D ci-dessus sont disponibles avec Postfix 2.2 et ultérieur.
%[1-9]
Les motifs %1, %2, ... %9 sont remplacés par le composant le plus significatif correspondant du domaine de la clé d'entrée. Si la clé d'entrée est utilisateur@mail.example.com, alors %1 est com, %2 est example et %3 est mail. Si la clé d'entrée n'est pas qualifiée ou n'a pas assez de composants de domaine pour satisfaire tous les motifs spécifiés, la recherche est supprimée et ne retourne aucun résultat.
Les expansions %1, ..., %9 ci-dessus sont disponibles avec Postfix 2.2 et ultérieur.
Le paramètre "domain" décrit ci-dessous limite les clés d'entrée aux adresses dans les domaines correspondants. Lorsque le paramètre "domain" n'est pas vide, les requêtes LDAP pour des adresses non qualifiées ou des adresses dans des domaines non correspondants sont supprimées et ne retournent aucun résultat.

result_format (défaut: %s)
Appelé result_filter dans les versions de Postfix antérieures à 2.2. Modèle de format appliqué aux attributs de résultat. Le plus souvent utilisé pour ajouter (ou préfixer) du texte au résultat. Ce paramètre prend en charge les expansions '%' suivantes :
%%
Ceci est remplacé par un caractère '%' littéral. (Postfix 2.2 et ultérieur).
%s
Ceci est remplacé par la valeur de l'attribut de résultat. Lorsque le résultat est vide, il est ignoré.
%u
Lorsque la valeur de l'attribut de résultat est une adresse de la forme utilisateur@domaine, %u est remplacé par la partie locale de l'adresse. Lorsque la partie locale du résultat est vide, elle est ignorée.
%d
Lorsque la valeur d'un attribut de résultat est une adresse de la forme utilisateur@domaine, %d est remplacé par la partie domaine de la valeur de l'attribut. Lorsque le résultat n'est pas qualifié, il est ignoré.
%[SUD1-9]
Les expansions en majuscules et en chiffres décimaux interpolent les parties de la clé d'entrée plutôt que le résultat. Leur comportement est identique à celui décrit avec query_filter, et en fait, comme la clé d'entrée est connue à l'avance, les recherches dont la clé ne contient pas toutes les informations spécifiées dans le modèle de résultat sont supprimées et ne retournent aucun résultat.
Les expansions %S, %U, %D et %1, ..., %9 ci-dessus sont disponibles avec Postfix 2.2 et ultérieur.
Par exemple, l'utilisation de "result_format = smtp:[%s]" permet d'utiliser un attribut mailHost comme base d'une table transport(5). Après application du format de résultat, plusieurs valeurs sont concaténées sous forme de chaînes séparées par des virgules. Les paramètres expansion_limit et size_limit expliqués ci-dessous permettent de restreindre le nombre de valeurs dans le résultat, ce qui est particulièrement utile pour les maps qui doivent retourner une seule valeur.

La valeur par défaut %s spécifie que chaque valeur d'attribut doit être utilisée telle quelle.

Ce paramètre était appelé result_filter dans les versions de Postfix antérieures à 2.2. Si aucun "result_format" n'est spécifié, la valeur de "result_filter" sera utilisée à la place avant de recourir à la valeur par défaut. Cela assure la compatibilité avec les anciens fichiers de configuration.

NOTE : N'entourez PAS le format de résultat de guillemets !

domain (défaut: pas de liste de domaines)
Il s'agit d'une liste de noms de domaines, de chemins vers des fichiers ou de bases de données "type:table". Lorsqu'il est spécifié, seules les clés de recherche entièrement qualifiées avec une partie locale *non vide* et un domaine correspondant sont éligibles pour la recherche : les recherches de type 'utilisateur', les recherches de domaine nu et les recherches "@domaine" ne sont pas effectuées. Cela peut réduire considérablement la charge de requêtes sur le serveur LDAP. 
    domain = postfix.org, hash:/etc/postfix/searchdomains

Il est préférable de ne pas utiliser LDAP pour stocker les domaines éligibles aux recherches LDAP.

NOTE : Ne définissez PAS ce paramètre pour les alias locaux(8).

Cette fonctionnalité est disponible dans Postfix 1.0 et ultérieur.

result_attribute (défaut: maildrop)
Les attributs que Postfix lira à partir des entrées d'annuaire retournées par la recherche, pour être résolus en une adresse e-mail. 
    result_attribute = mailbox, maildrop

Ne vous fiez pas à la valeur par défaut ("maildrop"). Spécifiez explicitement le result_attribute dans tous les fichiers de configuration de table ldap. Ceci est particulièrement pertinent lorsqu'aucun result_attribute n'est applicable, par exemple dans les cas où leaf_result_attribute et/ou terminal_result_attribute sont utilisés à la place. La valeur par défaut est inoffensive si "maildrop" est également listé comme attribut de résultat feuille ou terminal, mais il est préférable de ne pas laisser cela au hasard.

special_result_attribute (défaut: vide)
Les attributs des entrées d'annuaire qui peuvent contenir des DN ou des URL LDAP RFC 2255. S'ils sont trouvés, une recherche récursive est effectuée pour récupérer l'entrée référencée par le DN, ou les entrées correspondant à la requête URL. 
    special_result_attribute = memberdn

La récursion de DN récupère les mêmes result_attributes que la requête principale, y compris les attributs spéciaux pour une récursion supplémentaire.

Le traitement des URL récupère uniquement les attributs qui sont inclus à la fois dans la définition de l'URL et en tant qu'attributs de résultat (ordinaires, spéciaux, feuille ou terminal) dans la définition de la table Postfix. Si l'URL liste des attributs spéciaux de la table, ceux-ci sont récupérés et utilisés récursivement. Une URL qui ne spécifie aucune sélection d'attributs est équivalente (RFC 2255) à une URL qui sélectionne tous les attributs, auquel cas les attributs sélectionnés seront l'ensemble complet des attributs de résultat dans la table Postfix.

Si un descripteur d'attribut d'URL LDAP ou l'attribut de résultat de table LDAP correspondant (mais pas les deux) utilise des options de sous-type RFC 2255 ("attr;option"), l'attribut demandé au serveur LDAP inclura l'option de sous-type. Dans tous les autres cas, l'attribut de l'URL et l'attribut de la table doivent correspondre exactement. Les attributs avec des options dans l'URL et dans la table Postfix sont demandés uniquement lorsque les options sont identiques. Les options de descripteur d'attribut LDAP sont très rarement utilisées, la plupart des utilisateurs LDAP n'auront pas à se soucier de ce niveau de détail nuancé.

terminal_result_attribute (défaut: vide)
Lorsque un ou plusieurs attributs de résultat terminaux sont trouvés dans une entrée LDAP, tous les autres attributs de résultat sont ignorés et seuls les attributs de résultat terminaux sont retournés. Ceci est utile pour déléguer l'expansion des membres de groupe à un hôte particulier, en utilisant un attribut optionnel "maildrop" sur des groupes sélectionnés pour router le groupe vers un hôte spécifique, où le groupe est développé, éventuellement via un gestionnaire de liste de diffusion ou un autre traitement spécial. 
    result_attribute =
    terminal_result_attribute = maildrop

Lors de l'utilisation d'attributs de résultat terminaux et/ou feuilles, il est préférable de définir result_attribute à une valeur vide lorsqu'il n'est pas utilisé, ou de le définir explicitement à la valeur souhaitée, même s'il s'agit de la valeur par défaut "maildrop".

Cette fonctionnalité est disponible avec Postfix 2.4 ou ultérieur.

leaf_result_attribute (défaut: vide)
Lorsque un ou plusieurs attributs de résultat spéciaux sont trouvés dans une entrée LDAP non terminale (voir ci-dessus), les attributs de résultat feuille sont exclus de l'expansion de cette entrée. Ceci est utile lors de l'expansion de groupes et que les attributs d'adresse e-mail souhaités des objets membres obtenus via la récursion DN ou URI sont également présents dans l'objet groupe. Pour retourner uniquement les valeurs d'attributs des objets feuille et non du groupe contenant, ajoutez l'attribut à la liste leaf_result_attribute, et non à la liste result_attribute, qui est toujours développée. Notez que la valeur par défaut de "result_attribute" n'est pas vide, vous pourriez vouloir la définir explicitement à vide lors de l'utilisation de "leaf_result_attribute" pour développer le groupe en une liste d'adresses DN membres. Si les groupes ont à la fois des références DN membres ET des attributs qui contiennent des chaînes rfc822 multi-valeurs, alors les attributs de chaîne vont dans "result_attribute". Les attributs qui représentent les adresses e-mail des objets référencés via un DN (ou une URI LDAP) vont dans "leaf_result_attribute". 
    result_attribute = memberaddr
    special_result_attribute = memberdn
    terminal_result_attribute = maildrop
    leaf_result_attribute = mail

Lors de l'utilisation d'attributs de résultat terminaux et/ou feuilles, il est préférable de définir result_attribute à une valeur vide lorsqu'il n'est pas utilisé, ou de le définir explicitement à la valeur souhaitée, même s'il s'agit de la valeur par défaut "maildrop".

Cette fonctionnalité est disponible avec Postfix 2.4 ou ultérieur.

scope (défaut: sub)
La portée de recherche LDAP : sub, base ou one. Celles-ci se traduisent par LDAP_SCOPE_SUBTREE, LDAP_SCOPE_BASE et LDAP_SCOPE_ONELEVEL.
bind (défaut: yes)
Si et comment se connecter au serveur LDAP. Les implémentations LDAP plus récentes ne nécessitent pas que les clients se connectent, ce qui permet de gagner du temps. Exemple : 
    # Ne pas se connecter
    bind = no
    # Utiliser la connexion SIMPLE
    bind = yes
    # Utiliser la connexion SASL
    bind = sasl

Les versions de Postfix antérieures à 2.8 ne prennent en charge que "bind = no" ce qui signifie ne pas se connecter, et "bind = yes" ce qui signifie établir une connexion SIMPLE. Postfix 2.8 et ultérieur prend également en charge "bind = SASL" lorsqu'il est compilé avec le support SASL LDAP comme décrit dans LDAP_README, il ajoute également les synonymes "bind = none" et "bind = simple" pour "bind = no" et "bind = yes" respectivement. Voir la section SASL ci-dessous pour les paramètres supplémentaires disponibles avec "bind = sasl".

Si vous avez besoin de vous connecter, vous pourriez envisager de configurer Postfix pour qu'il se connecte à la machine locale sur un port qui est un tunnel SSL vers votre serveur LDAP. Si votre serveur LDAP ne prend pas en charge nativement le SSL, placez un tunnel (wrapper, proxy, peu importe comment vous l'appelez) sur ce système également. Cela devrait empêcher le mot de passe de transiter sur le réseau en clair.

bind_dn (défaut: vide)
Si vous devez vous connecter, faites-le avec ce nom distinctif. Exemple : 
    bind_dn = uid=postfix, dc=your, dc=com
Avec "bind = sasl" (voir ci-dessus), le DN peut être facultatif pour certains mécanismes SASL, ne spécifiez pas de DN si ce n'est pas nécessaire.
bind_pw (défaut: vide)
Le mot de passe pour le nom distinctif ci-dessus. Si vous devez l'utiliser, vous voudrez probablement rendre le fichier de configuration de la map lisible uniquement par l'utilisateur Postfix. Lorsque vous utilisez la syntaxe obsolète ldap:ldapsource, avec des paramètres de map dans main.cf, il n'est pas possible de stocker de manière sécurisée le mot de passe de connexion. Ceci est dû au fait que main.cf doit être lisible par tout le monde pour permettre aux comptes locaux de soumettre du courrier via la commande sendmail. Exemple : 
    bind_pw = postfixpw
Avec "bind = sasl" (voir ci-dessus), le mot de passe peut être facultatif pour certains mécanismes SASL, ne spécifiez pas de mot de passe si ce n'est pas nécessaire.

cache_expiry (IGNORÉ avec un avertissement)
cache_size (IGNORÉ avec un avertissement)
Les paramètres ci-dessus ne sont PLUS PRIS EN CHARGE par Postfix. Le support de cache a été abandonné par OpenLDAP depuis la version 2.1.13.
recursion_limit (par défaut : 1000)
Une limite sur la profondeur d'imbrication de l'évaluation des attributs spéciaux des DN et des URL. La limite doit être un nombre entier positif non nul.
expansion_limit (par défaut : 0)
Une limite sur le nombre total d'éléments de résultat renvoyés (sous forme de liste séparée par des virgules) par une recherche dans la table. Une valeur de zéro désactive la limite. Les recherches échouent avec une erreur temporaire si la limite est dépassée. Définir la limite à 1 garantit que les recherches ne renvoient pas de valeurs multiples.
size_limit (par défaut : $expansion_limit)
Une limite sur le nombre d'entrées LDAP renvoyées par une seule recherche LDAP effectuée dans le cadre de la recherche. Une valeur de 0 désactive la limite. L'expansion des références de DN et d'URL implique des requêtes LDAP imbriquées, chacune étant soumise séparément à cette limite.

Note : même une seule entrée LDAP peut générer plusieurs résultats de recherche, via plusieurs attributs de résultat et/ou des attributs de résultat multivalués. Cette limite plafonne l'utilisation des ressources par recherche sur le serveur LDAP, et non la multiplicité finale du résultat de la recherche. Elle est analogue à l'option "-z" de "ldapsearch".

dereference (par défaut : 0)
Quand faut-il résoudre les alias LDAP. (Notez que cela n'a rien à voir avec les alias Postfix.) Les valeurs autorisées sont celles qui sont légales pour les implémentations LDAP OpenLDAP/UM :
0
jamais
1
lors de la recherche
2
lors de la localisation de l'objet de base pour la recherche
3
toujours
Voir ldap.h ou les pages de manuel ldap_open(3) ou ldapsearch(1) pour plus d'informations. Et si vous utilisez un package LDAP qui a d'autres valeurs possibles, veuillez en informer la liste de diffusion postfix-users@postfix.org.
chase_referrals (par défaut : 0)
Définit (ou efface) LDAP_OPT_REFERRALS (nécessite le support de la version 3 de LDAP).
version (par défaut : 2)
Spécifie la version du protocole LDAP à utiliser.
debuglevel (par défaut : 0)
Le niveau à définir pour le débogage dans les bibliothèques OpenLDAP.

PARAMÈTRES LDAP SASL

Si vous utilisez les bibliothèques OpenLDAP compilées avec le support SASL, Postfix 2.8 et versions ultérieures compilées avec le support SASL LDAP tel que décrit dans LDAP_README peuvent s'authentifier auprès des serveurs LDAP via SASL.

Cela permet l'authentification auprès du serveur LDAP via des mécanismes autres qu'un simple mot de passe. La flexibilité ajoutée a un coût : il n'est plus pratique de définir un délai d'attente explicite pour la durée d'une opération de liaison LDAP. Dans des conditions défavorables, que la liaison SASL expire ou non, la durée du délai d'attente est déterminée par les bibliothèques LDAP et SASL.

Il est préférable d'utiliser des tables qui utilisent des liaisons SASL via proxymap(8), de cette façon le processus demandeur peut temporiser la demande proxymap. Cela vous permet également de configurer l'environnement du processus en remplaçant le paramètre import_environment de proxymap(8) dans master.cf(5). Des paramètres d'environnement spéciaux peuvent être nécessaires pour configurer les caches d'informations d'identification GSSAPI ou d'autres options spécifiques au mécanisme SASL. Les informations d'identification GSSAPI utilisées pour les recherches LDAP peuvent devoir être différentes de celles, par exemple, utilisées par le client SMTP de Postfix pour s'authentifier auprès des serveurs distants.

L'utilisation de mécanismes SASL nécessite la version 3 du protocole LDAP, la version par défaut du protocole est 2 pour des raisons de compatibilité ascendante. Vous devez définir "version = 3" en plus de "bind = sasl".

Les paramètres suivants sont pertinents pour l'utilisation de LDAP avec SASL

sasl_mechs (par défaut : vide)
Liste d'un ou plusieurs mécanismes SASL, séparés par des espaces, à essayer.
sasl_realm (par défaut : vide)
Domaine SASL à utiliser, le cas échéant.
sasl_authz_id (par défaut : vide)
L'identité d'autorisation SASL à affirmer, le cas échéant.
sasl_minssf (par défaut : 0)
Le facteur de sécurité sasl minimum requis pour établir une connexion.

PARAMÈTRES LDAP SSL ET STARTTLS

Si vous utilisez les bibliothèques OpenLDAP compilées avec le support SSL, Postfix peut se connecter aux serveurs LDAP SSL et émettre la commande STARTTLS.

Le service LDAP SSL peut être demandé en utilisant une URL LDAP SSL dans le paramètre server_host :

    server_host = ldaps://ldap.example.com:636

STARTTLS peut être activé avec le paramètre start_tls :

    start_tls = yes

Les deux formes nécessitent la version 3 du protocole LDAP, qui doit être définie explicitement avec :

    version = 3

Si l'un des programmes Postfix interrogeant la table est configuré dans master.cf pour s'exécuter en chroot, tous les certificats et clés impliqués doivent être copiés dans le jail chroot. Bien entendu, les clés privées ne devraient être lisibles que par l'utilisateur "postfix".

Les paramètres suivants sont pertinents pour LDAP SSL et STARTTLS :

start_tls (par défaut : no)
Indique s'il faut émettre STARTTLS lors de la connexion au serveur. Ne le définissez pas avec LDAP SSL (la session SSL est configurée automatiquement lors de l'ouverture de la connexion TCP).
tls_ca_cert_dir (Pas de défaut ; définissez soit ce paramètre, soit tls_ca_cert_file)
Répertoire contenant les certificats d'autorité de certification X509 au format PEM qui doivent être reconnus par le client dans les connexions SSL/TLS. Chaque fichier contient un certificat d'autorité de certification. Les fichiers sont recherchés par la valeur de hachage du nom de sujet de l'autorité de certification, qui doit donc être disponible. S'il existe plusieurs certificats d'autorité de certification avec la même valeur de hachage de nom, l'extension doit être différente (par exemple, 9d66eef0.0, 9d66eef0.1, etc.). La recherche s'effectue dans l'ordre du numéro d'extension, indépendamment des autres propriétés des certificats. Utilisez l'utilitaire c_rehash (de la distribution OpenSSL) pour créer les liens nécessaires.
tls_ca_cert_file (Pas de défaut ; définissez soit ce paramètre, soit tls_ca_cert_dir)
Fichier contenant les certificats d'autorité de certification X509 au format PEM qui doivent être reconnus par le client dans les connexions SSL/TLS. Ce paramètre a la priorité sur tls_ca_cert_dir.
tls_cert (Pas de défaut ; vous devez le définir)
Fichier contenant le certificat X509 du client à utiliser par le client dans les connexions SSL/TLS.
tls_key (Pas de défaut ; vous devez le définir)
Fichier contenant la clé privée correspondant au tls_cert ci-dessus.
tls_require_cert (par défaut : no)
Indique s'il faut demander le certificat X509 du serveur et vérifier sa validité lors de l'établissement des connexions SSL/TLS. Les valeurs prises en charge sont no et yes.

Avec no, la chaîne de confiance du certificat serveur n'est pas vérifiée, mais avec OpenLDAP avant 2.1.13, le nom dans le certificat serveur doit toujours correspondre au nom du serveur LDAP. Avec OpenLDAP 2.0.0 à 2.0.11, le nom du serveur n'est pas nécessairement celui que vous avez spécifié, mais est déterminé (par recherche inverse) à partir de l'adresse IP de la connexion au serveur LDAP. Avec OpenLDAP avant 2.0.13, les extensions subjectAlternativeName dans le certificat du serveur LDAP sont ignorées : le nom du serveur doit correspondre au CommonName du sujet. Le paramètre no correspond à la valeur never de TLS_REQCERT dans les fichiers de configuration du client LDAP.

N'utilisez pas TLS avec OpenLDAP 2.0.x (et surtout avec x <= 11) si vous pouvez l'éviter.

Avec yes, le certificat du serveur doit être émis par une autorité de certification de confiance et ne pas être expiré. Le nom du serveur LDAP doit correspondre à l'un des noms trouvés dans le certificat (voir ci-dessus pour le comportement dépendant de la version de la bibliothèque OpenLDAP). Le paramètre yes correspond à la valeur demand de TLS_REQCERT dans les fichiers de configuration du client LDAP.

Les valeurs "try" et "allow" de TLS_REQCERT n'ont pas d'équivalents ici. Elles ne sont pas disponibles avec OpenLDAP 2.0, et de toute façon ont des propriétés de sécurité discutables. Soit vous voulez des connexions LDAP vérifiées par TLS, soit vous n'en voulez pas.

La valeur yes ne fonctionne correctement qu'avec Postfix 2.5 et versions ultérieures, ou avec OpenLDAP 2.0. Les versions antérieures de Postfix ou les versions ultérieures d'OpenLDAP ne fonctionnent pas ensemble avec ce paramètre. Le support de LDAP sur TLS a été ajouté à Postfix sur la base de l'API OpenLDAP 2.0.

tls_random_file (Pas de défaut)
Chemin d'un fichier pour obtenir des bits aléatoires lorsque /dev/[u]random n'est pas disponible, à utiliser par le client dans les connexions SSL/TLS.
tls_cipher_suite (Pas de défaut)
Suite de chiffrement à utiliser dans les négociations SSL/TLS.

Voici un exemple de base pour utiliser LDAP afin de rechercher des alias locaux(8). Supposons que dans main.cf, vous ayez :

    alias_maps = hash:/etc/aliases,

GENERAL LDAP PARAMETERS

The following parameters are used to control the behavior of the LDAP client. They are available for all lookup table types that use LDAP.

server_host (No default)
The network hostname or IP address of the LDAP server. This parameter can be specified multiple times for multiple servers.
server_port (636 for LDAPS, 389 for others)
The network port number of the LDAP server. For LDAPS connections, the default is port 636. For other connection types, the default is port 389.
search_base (No default)
The base DN for LDAP searches. This parameter is mandatory for lookup tables that require a search operation (e.g., virtual domains, mail aliases, list members).
search_filter (No default)
The search filter template. This parameter is mandatory for lookup tables that require a search operation. It supports the following placeholders:
%s
The lookup key (e.g., the sender address or domain).

For example, a search filter of "(mailRoutingAddress=%s)" would search for entries where the mailRoutingAddress attribute matches the lookup key.

result_format (No default)
The result format template. This parameter is used to specify how to format the result of an LDAP search. It supports the following placeholders:
%s
The entire attribute value.
%1s
The first attribute value.
%[attribute-name]s
The value of the specified attribute.

For example, a result format of "%1s" would return the first value of the attribute being searched for. A result format of "%[mailDrop]%s" would return the value of the mailDrop attribute followed by the entire attribute value.

result_attribute (No default)
The attribute to return from the LDAP search. If this parameter is specified, only the value(s) of this attribute will be returned. If it is not specified, the entire entry will be returned.
result_filter (No default)
For backwards compatibility with the pre 2.2 LDAP clients, result_filter can for now be used instead of result_format, when the latter parameter is not also set. The new name better reflects the function of the parameter. This compatibility interface may be removed in a future release.
domain (No default)
A domain name to append to the lookup key. This is useful for services that require fully qualified domain names.
mandatory_field (No default)
A list of attribute names that must be present in the LDAP entry for it to be considered valid. If any of the specified attributes are missing, the lookup will fail.

LDAP SASL PARAMETERS

The following parameters control the use of Simple Authentication and Security Layer (SASL) for authentication to the LDAP server.

sasl_mech (No default)
The SASL mechanism to use (e.g., PLAIN, LOGIN, CRAM-MD5).
sasl_authcid (No default)
The SASL authentication identity (username).
sasl_passwd (No default)
The SASL password. This should be stored in a secure file and not directly in main.cf.
sasl_realm (No default)
The SASL realm.
sasl_mechanism_filter (No default)
A list of allowed SASL mechanisms, separated by commas. If not specified, all supported mechanisms will be tried.

LDAP SSL AND STARTTLS PARAMETERS

The following parameters control the use of SSL/TLS for secure connections to the LDAP server.

ssl_version (No default)
The SSL/TLS version to use (e.g., TLSv1, TLSv1.1, TLSv1.2).
tls_ca_cert_file (No default)
The file containing the trusted CA certificates for verifying the LDAP server's certificate.
tls_cert_file (No default)
The file containing the client certificate for authentication to the LDAP server.
tls_key_file (No default)
The file containing the private key for the client certificate.
tls_require_cert (Yes)
Whether to require a valid certificate from the LDAP server. Valid values are "Yes", "No", "Demand", "Allow", "Try".

EXAMPLE

The following example shows how to configure Postfix to use an LDAP server for mail alias lookups.

# main.cf
alias_maps = ldap:mail_aliases

# ldap-mail_aliases.cf
server_host = ldap.example.com
search_base = ou=aliases,dc=example,dc=com
search_filter = (&(mailRoutingAddress=%s)(objectClass=mailRecipient))
result_format = %1s

In this example:

  • alias_maps specifies that Postfix should use the ldap:mail_aliases lookup table for mail aliases.

  • The ldap-mail_aliases.cf file defines the parameters for the LDAP lookup.

  • server_host specifies the LDAP server hostname.

  • search_base specifies the base DN for the search.

  • search_filter defines the filter to search for mail aliases. It looks for entries with a mailRoutingAddress attribute matching the lookup key and an objectClass of mailRecipient.

  • result_format specifies that Postfix should use the first value of the matched attribute as the mail alias.

This configuration would allow Postfix to resolve mail aliases stored in an LDAP directory. For instance, if a user sends a message to john.doe@example.com, Postfix would query the LDAP server for an entry matching (&(mailRoutingAddress=john.doe@example.com)(objectClass=mailRecipient)). If a matching entry is found with a mailRoutingAddress attribute set to "jdoe@internal.example.com", Postfix would deliver the message to jdoe@internal.example.com.

Consider another example where the lookup is for recipients whose mailacceptinggeneralid attribute is "ldapuser". The Postfix system would query the LDAP server for entries matching this criteria, read the "maildrop" attributes of those found, and build a list of their maildrops, which will be treated as RFC822 addresses to which the message will be delivered.

OBSOLÈTE PARAMÈTRES MAIN.CF

Pour la compatibilité ascendante avec Postfix version 2.0 et antérieure, les paramètres LDAP peuvent également être définis dans main.cf. Spécifiez comme source LDAP un nom qui ne commence pas par une barre oblique ou un point. Les paramètres LDAP seront alors accessibles sous le nom que vous avez donné à la source dans sa définition, un trait de soulignement, et le nom du paramètre. Par exemple, si la table de correspondance est spécifiée comme "ldap:ldapsource", le paramètre "server_host" ci-dessous serait défini dans main.cf comme "ldapsource_server_host".

Note : avec cette forme, les mots de passe des sources LDAP sont écrits dans main.cf, qui est normalement lisible par tous. Le support de cette forme sera supprimé dans une future version de Postfix.

AUTRES FONCTIONNALITÉS OBSOLÈTES

result_filter (Aucune valeur par défaut)
Pour la compatibilité ascendante avec les clients LDAP pré 2.2, result_filter peut pour l'instant être utilisé à la place de result_format, lorsque ce dernier paramètre n'est pas également défini. Le nouveau nom reflète mieux la fonction du paramètre. Cette interface de compatibilité peut être supprimée dans une future version.
