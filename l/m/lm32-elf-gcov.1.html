DESCRIPTION

gcov est un programme de test de couverture. Utilisez-le en concertation avec GCC pour analyser vos programmes afin de créer du code plus efficace et plus rapide, et pour découvrir les parties non testées de votre programme. Vous pouvez utiliser gcov comme un outil de profilage pour découvrir où vos efforts d'optimisation auront le meilleur impact sur votre code. Vous pouvez également utiliser gcov avec l'autre outil de profilage, gprof, pour évaluer quelles parties de votre code utilisent le plus de temps de calcul.

Les outils de profilage vous aident à analyser les performances de votre code. En utilisant un profileur tel que gcov ou gprof, vous pouvez obtenir des statistiques de performance de base, telles que :

  • la fréquence d'exécution de chaque ligne de code
  • quelles lignes de code sont effectivement exécutées
  • combien de temps de calcul chaque section de code utilise

Une fois que vous connaissez ces informations sur le fonctionnement de votre code lorsqu'il est compilé, vous pouvez examiner chaque module pour voir lesquels doivent être optimisés. gcov vous aide à déterminer où concentrer vos efforts d'optimisation.

Les développeurs de logiciels utilisent également les tests de couverture en concertation avec des suites de tests, pour s'assurer que le logiciel est réellement suffisamment bon pour une publication. Les suites de tests peuvent vérifier qu'un programme fonctionne comme prévu ; un programme de couverture vérifie quelle partie du programme est exercée par la suite de tests. Les développeurs peuvent alors déterminer quels types de cas de test doivent être ajoutés aux suites de tests pour créer à la fois des tests meilleurs et un meilleur produit final.

Vous devriez compiler votre code sans optimisation si vous prévoyez d'utiliser gcov, car l'optimisation, en combinant certaines lignes de code en une seule fonction, peut ne pas vous fournir autant d'informations que vous en avez besoin pour rechercher des "points chauds" où le code utilise une grande quantité de temps de calcul. De même, comme gcov accumule les statistiques ligne par ligne (à la plus basse résolution), il fonctionne mieux avec un style de programmation qui place une seule instruction par ligne. Si vous utilisez des macros complexes qui se développent en boucles ou en autres structures de contrôle, les statistiques sont moins utiles — elles ne rapportent que la ligne où apparaît l'appel de macro. Si vos macros complexes se comportent comme des fonctions, vous pouvez les remplacer par des fonctions inline pour résoudre ce problème.

gcov crée un fichier journal appelé fichier_source.gcov qui indique combien de fois chaque ligne d'un fichier source fichier_source.c a été exécutée. Vous pouvez utiliser ces fichiers journaux avec gprof pour aider à affiner les performances de vos programmes. gprof fournit des informations de chronométrage que vous pouvez utiliser en conjonction avec les informations que vous obtenez de gcov.

gcov ne fonctionne que sur du code compilé avec GCC. Il n'est compatible avec aucun autre mécanisme de profilage ou de test de couverture.

OPTIONS

-a
--all-blocks
Écrit les comptes d'exécution individuels pour chaque bloc de base. Normalement, gcov affiche les comptes d'exécution uniquement pour les blocs principaux d'une ligne. Avec cette option, vous pouvez déterminer si des blocs au sein d'une même ligne ne sont pas exécutés.
-b
--branch-probabilities
Écrit les fréquences des branches dans le fichier de sortie, et écrit le résumé des branches sur la sortie standard. Cette option vous permet de voir à quelle fréquence chaque branche de votre programme a été prise. Les branches inconditionnelles ne seront pas affichées, sauf si l'option -u est donnée.
-c
--branch-counts
Écrit les fréquences des branches sous forme de nombre de branches prises, plutôt que sous forme de pourcentage de branches prises.
-g
--conditions
Écrit la couverture des conditions dans le fichier de sortie, et écrit le résumé des conditions sur la sortie standard. Cette option vous permet de voir si les conditions de votre programme ont eu au moins une fois un effet indépendant sur le résultat de l'expression booléenne (couverture modifiée des décisions/conditions). Cela nécessite que vous compiliez la source avec -fcondition-coverage.
-d
--display-progress
Affiche la progression sur la sortie standard.
-f
--function-summaries
Affiche des résumés pour chaque fonction en plus du résumé au niveau du fichier.
-h
--help
Affiche l'aide sur l'utilisation de gcov (sur la sortie standard), et quitte sans effectuer d'autre traitement.
-j
--json-format
Produit le fichier gcov dans un format JSON intermédiaire facile à analyser, qui ne nécessite pas le code source pour la génération. Le fichier JSON est compressé avec l'algorithme de compression gzip et les fichiers ont l'extension .gcov.json.gz.

La structure du JSON est la suivante :

{
  "current_working_directory": "foo/bar",
  "data_file": "a.out",
  "format_version": "2",
  "gcc_version": "11.1.1 20210510"
  "files": ["$file"]
}

Les champs de l'élément racine ont la sémantique suivante :

  • current_working_directory : répertoire de travail où l'unité de compilation a été compilée
  • data_file : nom du fichier de données (GCDA)
  • format_version : version sémantique du format

    Changements dans la version 2 :

*
calls : des informations sur les appels de fonction sont ajoutées
*
gcc_version : version du compilateur GCC

Chaque file a la forme suivante :

{
  "file": "a.c",
  "functions": ["$function"],
  "lines": ["$line"]
}

Les champs de l'élément file ont la sémantique suivante :

*
file_name : nom du fichier source

Chaque function a la forme suivante :

{
  "blocks": 2,
  "blocks_executed": 2,
  "demangled_name": "foo",
  "end_column": 1,
  "end_line": 4,
  "execution_count": 1,
  "name": "foo",
  "start_column": 5,
  "start_line": 1
}

Les champs de l'élément function ont la sémantique suivante :

  • blocks : nombre de blocs dans la fonction
  • blocks_executed : nombre de blocs exécutés de la fonction
  • demangled_name : nom démêlé de la fonction
  • end_column : colonne dans le fichier source où se termine la fonction
  • end_line : ligne dans le fichier source où se termine la fonction
  • execution_count : nombre d'exécutions de la fonction
  • name : nom de la fonction
  • start_column : colonne dans le fichier source où commence la fonction
  • start_line : ligne dans le fichier source où commence la fonction
-H
--human-readable
Écrit les informations de couverture dans un format plus lisible par l'homme plutôt que dans le format des fichiers .gcov. Cela inclut des résumés de fonctions et des fréquences de branches. Les options -b, -c et -f sont automatiquement activées.
-k
--use-colors
Active l'utilisation des couleurs dans la sortie. Les lignes non exécutées sont imprimées en rouge, les lignes exécutées une fois en jaune et les lignes exécutées plusieurs fois en vert. Cela inclut l'option --hotness-colors.
-l
--long-file-names
Ne supprime pas le préfixe du nom de fichier des noms des fichiers source dans le fichier de sortie. Par défaut, gcov supprime les préfixes de répertoire afin de rendre le nom de fichier plus court.
-m
--demangled-names
Affiche les noms démêlés des fonctions et des méthodes dans le fichier de sortie. Par exemple, la fonction `_ZN7MyClass3fooEi' s'affichera comme `MyClass::foo(int)'.
-n
--no-output
Ne produit aucun fichier de sortie. Ceci est utile pour utiliser gcov avec l'option --json-format ou pour ne pas créer de fichiers .gcov.
-o
--object-directory répertoire|fichier
Spécifie le répertoire ou le fichier où gcov doit rechercher les fichiers d'objets (par exemple, gcc.output/). Lorsque plusieurs fichiers d'objets sont traités, ils peuvent être spécifiés avec plusieurs options -o.
-p
--preserve-paths
Ne supprime pas le préfixe du nom de fichier des noms des fichiers source dans le fichier de sortie. Par défaut, gcov supprime les préfixes de répertoire afin de rendre le nom de fichier plus court.
-q
--use-hotness-colors
Active l'utilisation des couleurs dans la sortie. Les lignes non exécutées sont imprimées en rouge, les lignes exécutées une fois en jaune et les lignes exécutées plusieurs fois en vert. Cela inclut l'option --hotness-colors.
-r
--relative-only
Ne supprime pas le préfixe du nom de fichier des noms des fichiers source dans le fichier de sortie. Par défaut, gcov supprime les préfixes de répertoire afin de rendre le nom de fichier plus court.
-s
--source-prefix répertoire
Supprime le préfixe répertoire des noms de fichiers source dans le fichier de sortie. Par défaut, gcov supprime les préfixes de répertoire afin de rendre le nom de fichier plus court.
-t
--stdout
Écrit la sortie sur la sortie standard plutôt que dans des fichiers .gcov.
-u
--unconditional-branches
Inclut les branches inconditionnelles dans le rapport des fréquences de branches.
-x
--hash-filenames
Donne aux fichiers de sortie des noms basés sur un hachage des noms de fichiers source complets. Cela peut être utile pour éviter les conflits de noms de fichiers lorsque vous traitez de nombreux fichiers source.
-v
--version
Affiche la version de gcov et quitte.

Le fichier source où la fonction commence
  • start_line : ligne dans le fichier source où la fonction commence

    • Notez que les numéros de ligne et de colonne commencent à 1. Dans l'implémentation actuelle, start_line et start_column n'incluent pas les paramètres de modèle et le type de retour qui précède, mais cela est susceptible d'être corrigé à l'avenir.

    Chaque line a le format suivant :

    {
  "block_ids": ["$block_id"],
  "branches": ["$branch"],
  "calls": ["$call"],
  "count": 2,
  "conditions": ["$condition"],
  "line_number": 15,
  "unexecuted_block": false,
  "function_name": "foo",
}

    Les branches et les appels ne sont présents qu'avec l'option -b. Les champs de l'élément line ont la sémantique suivante :

    • block_ids : identifiants des blocs de base appartenant à la ligne
    • count : nombre d'exécutions de la ligne
    • line_number : numéro de ligne
    • unexecuted_block : indicateur si la ligne contient un bloc non exécuté (toutes les instructions de la ligne ne sont pas exécutées)
    • function_name : nom d'une fonction à laquelle cette line appartient (peut ne pas être défini pour une ligne avec des instructions inline)

    Chaque branch a le format suivant :

    {
  "count": 11,
  "destination_block_id": 17,
  "fallthrough": true,
  "source_block_id": 13,
  "throw": false
}

    Les champs de l'élément branch ont la sémantique suivante :

    • count : nombre d'exécutions de la branche
    • fallthrough : vrai lorsque la branche est une branche de continuation
    • throw : vrai lorsque la branche est une branche exceptionnelle
    • isource_block_id : identifiant du bloc de base où cette branche se produit
    • destination_block_id : identifiant du bloc de base vers lequel cette branche saute

    Chaque call a le format suivant :

    {
  "destination_block_id": 1,
  "returned": 11,
  "source_block_id": 13
}

    Les champs de l'élément call ont la sémantique suivante :

    • returned : nombre de fois qu'un appel de fonction est revenu (le nombre d'appels est égal à line::count)
    • isource_block_id : identifiant du bloc de base où cet appel se produit
    • destination_block_id : identifiant du bloc de base où l'exécution continue après le retour

    Chaque condition a le format suivant :

    {
  "count": 4,
  "covered": 2,
  "not_covered_false": [],
  "not_covered_true": [0, 1],
}

    Les champs de l'élément condition ont la sémantique suivante :

    • count : nombre de résultats de condition dans cette expression
    • covered : nombre de résultats de condition couverts dans cette expression
    • not_covered_true : termes, par index, non vus comme vrais dans cette expression
    • not_covered_false : termes, par index, non vus comme faux dans cette expression

    -k

Cela peut être utile si x.h est inclus dans plusieurs fichiers source et que vous souhaitez voir les contributions individuelles. Si vous utilisez l'option -p, les noms des fichiers incluant et inclus seront des chemins complets.
    -m
    --demangled-names
    Afficher les noms de fonctions démanglés dans la sortie. Par défaut, les noms de fonctions manglés sont affichés.

    -o directory|file

Si un fichier est spécifié ici, les fichiers de données portent le nom de ce fichier, sans son extension.

Ceci est utile si les fichiers source se trouvent dans plusieurs répertoires différents.
    -q
    --use-hotness-colors
    Émettre une sortie colorée de type perf pour les lignes chaudes. La légende de l'échelle de couleurs est imprimée tout au début du fichier de sortie.

    --relative-only
    N'émettre des informations que sur les fichiers source avec un nom de chemin relatif (après élision du préfixe source). Les chemins absolus sont généralement des fichiers d'en-tête système et la couverture de toutes les fonctions inline qui y figurent n'est normalement pas intéressante.
    -s directory
    --source-prefix directory
    Un préfixe pour les noms de fichiers source à supprimer lors de la génération des fichiers de couverture de sortie. Cette option est utile lors de la compilation dans un répertoire séparé, et le chemin du répertoire source ne doit pas être inclus lors de la détermination des noms de fichiers de sortie. Notez que cette détection de préfixe est appliquée avant de déterminer si le fichier source est absolu.

    --stdout
    Sortie vers la sortie standard au lieu des fichiers de sortie.
    -u
    --unconditional-branches
    Lorsque les probabilités de branchement sont données, inclure celles des branches inconditionnelles. Les branches inconditionnelles ne sont normalement pas intéressantes.
    -v
    --version
    Afficher le numéro de version de gcov (sur la sortie standard), et quitter sans traitement supplémentaire.
    -w
    --verbose
    Imprimer des informations détaillées relatives aux blocs de base et aux arcs.
    -x
    --hash-filenames
    Lors de l'utilisation de --preserve-paths, gcov utilise le chemin complet des fichiers source pour créer un nom de fichier de sortie. Cela peut conduire à des noms de fichiers longs qui peuvent dépasser les limites du système de fichiers. Cette option crée des noms de la forme source-file##md5.gcov, où le composant source-file est la partie finale du nom de fichier et le composant md5 est calculé à partir du nom manglé complet qui aurait été utilisé autrement. L'option est une alternative à --preserve-paths sur les systèmes qui ont une limite de système de fichiers.

    gcov doit être exécuté avec le répertoire courant identique à celui dans lequel vous avez lancé le compilateur. Sinon, il ne pourra pas localiser les fichiers source. gcov produit des fichiers nommés mangledname.gcov dans le répertoire courant. Ceux-ci contiennent les informations de couverture du fichier source auquel ils correspondent. Un fichier .gcov est produit pour chaque fichier source (ou fichier d'en-tête) contenant du code, qui a été compilé pour produire les fichiers de données. La partie mangledname du nom du fichier de sortie est généralement simplement le nom du fichier source, mais peut être quelque chose de plus complexe si les options -l ou -p sont utilisées. Se référer à ces options pour les détails.

    Si vous invoquez gcov avec plusieurs fichiers d'entrée, les contributions de chaque fichier d'entrée sont additionnées. Typiquement, vous l'invoqueriez avec la même liste de fichiers que pour l'édition des liens finale de votre exécutable.

    Les fichiers .gcov contiennent des champs séparés par des : ainsi que le code source du programme. Le format est

    <execution_count>:<line_number>:<source line text>

    Des informations supplémentaires sur les blocs peuvent suivre chaque ligne, lorsqu'elles sont demandées par une option de ligne de commande. Le execution_count est - pour les lignes ne contenant pas de code. Les lignes non exécutées sont marquées ##### ou =====, selon qu'elles sont accessibles par des chemins non exceptionnels ou seulement par des chemins exceptionnels tels que les gestionnaires d'exceptions C++, respectivement. Étant donné l'option -a, les blocs non exécutés sont marqués $$$$$ ou %%%%%, selon qu'un bloc de base est accessible via des chemins non exceptionnels ou exceptionnels. Les blocs de base exécutés ayant une instruction avec un execution_count nul se terminent par un caractère * et sont colorés en magenta avec l'option -k. Cette fonctionnalité n'est pas prise en charge en Ada.

    Notez que GCC peut complètement supprimer les corps de fonctions qui ne sont pas nécessaires -- par exemple, si elles sont inlinées partout. Ces fonctions sont marquées avec -, ce qui peut être source de confusion. Utilisez l'option -fkeep-inline-func

    ions et les options -fkeep-static-functions pour conserver ces fonctions et permettre à gcov d'afficher correctement leur execution_count.

    Certaines lignes d'informations au début ont un line_number de zéro. Ces lignes d'en-tête sont de la forme

    -:0:<tag>:<value>

    L'ordre et le nombre de ces lignes d'en-tête seront augmentés à mesure que le développement de gcov progresse ; ne vous fiez pas à leur maintien inchangé. Utilisez tag pour localiser une ligne d'en-tête particulière.

    Les informations supplémentaires sur les blocs sont de la forme

    <tag> <information>

    L'information est lisible par l'homme, mais conçue pour être assez simple pour un traitement automatique.

    Lors de l'impression des pourcentages, 0% et 100% ne sont imprimés que lorsque les valeurs sont exactement 0% et 100% respectivement. D'autres valeurs qui seraient conventionnellement arrondies à 0% ou 100% sont plutôt imprimées comme la valeur non limite la plus proche.

    Lorsque vous utilisez gcov, vous devez d'abord compiler votre programme avec une option spéciale de GCC --coverage. Cela indique au compilateur de générer les informations supplémentaires nécessaires à gcov (essentiellement un graphe de flux du programme) et inclut également du code supplémentaire dans les fichiers objet pour générer les informations de profilage supplémentaires nécessaires à gcov. Ces fichiers supplémentaires sont placés dans le répertoire où se trouve le fichier objet.

    L'exécution du programme générera une sortie de profil. Pour chaque fichier source compilé avec -fprofile-arcs, un fichier .gcda accompagnant sera placé dans le répertoire du fichier objet.

    L'exécution de gcov avec les noms de fichiers source de votre programme en tant qu'arguments produira désormais une liste du code ainsi que la fréquence d'exécution de chaque ligne. Par exemple, si votre programme s'appelle tmp.cpp, voici ce que vous voyez lorsque vous utilisez la fonctionnalité de base de gcov:

    $ g++ --coverage tmp.cpp -c
$ g++ --coverage tmp.o
$ a.out
$ gcov tmp.cpp -m
Fichier 'tmp.cpp'
Lignes exécutées : 92.86% sur 14

    Pour chaque fonction, une ligne est imprimée indiquant combien de fois la fonction est appelée, combien de fois elle retourne et quel pourcentage des blocs de la fonction a été exécuté.

    Pour chaque bloc de base, une ligne est imprimée après la dernière ligne du bloc de base décrivant le branchement ou l'appel qui termine le bloc de base. Il peut y avoir plusieurs branches et appels listés pour une seule ligne source s'il existe plusieurs blocs de base qui se terminent sur cette ligne. Dans ce cas, les branches et les appels reçoivent chacun un numéro. Il n'y a pas de moyen simple de faire correspondre ces branches et appels aux constructions sources. En général, cependant, la branche ou l'appel de plus bas numéro correspondra à la construction la plus à gauche sur la ligne source.

    Pour un branchement, s'il a été exécuté au moins une fois, un pourcentage indiquant le nombre de fois où le branchement a été pris par rapport au nombre de fois où le branchement a été exécuté sera imprimé. Sinon, le message "jamais exécuté" sera imprimé.

    Pour un appel, s'il a été exécuté au moins une fois, un pourcentage indiquant le nombre de fois où l'appel a retourné par rapport au nombre de fois où l'appel a été exécuté sera imprimé. Ce sera généralement 100%, mais peut être inférieur pour les fonctions qui appellent "exit" ou "longjmp", et donc peuvent ne pas retourner à chaque fois qu'elles sont appelées.

    Les comptes d'exécution sont cumulatifs. Si le programme d'exemple était exécuté à nouveau sans supprimer le fichier .gcda, le compte du nombre de fois où chaque ligne de la source a été exécutée serait ajouté aux résultats de l'exécution précédente. Ceci est potentiellement utile de plusieurs manières. Par exemple, il pourrait être utilisé pour accumuler des données sur un certain nombre d'exécutions de programmes dans le cadre d'une suite de vérification de tests, ou pour fournir des informations plus précises à long terme sur un grand nombre d'exécutions de programmes.

    Les données des fichiers .gcda sont enregistrées juste avant la sortie du programme. Pour chaque source

    ce file compiled with -fprofile-arcs, the profiling code first attempts to read in an existing .gcda file; if the file doesn't match the executable (differing number of basic block counts) it will ignore the contents of the file. It then adds in the new execution counts and finally writes the data to the file.

    Utilisation de gcov avec l'optimisation GCC

    Si vous prévoyez d'utiliser gcov pour optimiser votre code, vous devez d'abord compiler votre programme avec une option spéciale de GCC --coverage. En dehors de cela, vous pouvez utiliser toutes les autres options de GCC ; mais si vous voulez prouver que chaque ligne de votre programme a été exécutée, vous ne devriez pas compiler avec optimisation en même temps. Sur certaines machines, l'optimiseur peut éliminer certaines lignes de code simples en les combinant avec d'autres lignes. Par exemple, du code comme celui-ci :

    if (a != b)
  c = 1;
else
  c = 0;

    peut être compilé en une seule instruction sur certaines machines. Dans ce cas, il n'y a aucun moyen pour gcov de calculer des comptes d'exécution séparés pour chaque ligne car il n'y a pas de code séparé pour chaque ligne. Par conséquent, la sortie de gcov ressemble à ceci si vous avez compilé le programme avec optimisation :

    100:   12:if (a != b)
100:   13:  c = 1;
100:   14:else
100:   15:  c = 0;

    La sortie montre que ce bloc de code, combiné par l'optimisation, a été exécuté 100 fois. Dans un sens, ce résultat est correct, car il n'y avait qu'une seule instruction représentant ces quatre lignes. Cependant, la sortie n'indique pas combien de fois le résultat était 0 et combien de fois le résultat était 1.

    Les fonctions inline peuvent créer des comptes de ligne inattendus. Les comptes de ligne sont affichés pour le code source de la fonction inline, mais ce qui est affiché dépend de l'endroit où la fonction est inline, ou si elle n'est pas inline du tout.

    Si la fonction n'est pas inline, le compilateur doit émettre une copie hors ligne de la fonction, dans tout fichier objet qui en a besoin. Si fileA.o et fileB.o contiennent tous deux des corps hors ligne d'une fonction inline particulière, ils contiendront également tous deux des comptes de couverture pour cette fonction. Lorsque fileA.o et fileB.o sont liés ensemble, l'éditeur de liens, sur de nombreux systèmes, sélectionnera l'un de ces corps hors ligne pour tous les appels à cette fonction, et supprimera ou ignorera l'autre. Malheureusement, il ne supprimera pas les compteurs de couverture pour le corps de fonction inutilisé. Par conséquent, lorsqu'il est instrumenté, toutes les utilisations de cette fonction, sauf une, afficheront des comptes nuls.

    Si la fonction est inline à plusieurs endroits, la structure du bloc à chaque emplacement peut ne pas être la même. Par exemple, une condition peut maintenant être calculable au moment de la compilation dans certains cas. Étant donné que la couverture de toutes les utilisations de la fonction inline sera affichée pour les mêmes lignes sources, les comptes de ligne eux-mêmes peuvent sembler incohérents.

    Les applications de longue durée peuvent utiliser les installations "__gcov_reset" et "__gcov_dump" pour limiter la collecte de profils à la région du programme d'intérêt. Appeler "__gcov_reset(void)" effacera tous les compteurs de profils d'exécution à zéro, et appeler "__gcov_dump(void)" provoquera le vidage des informations de profil collectées à ce moment-là dans des fichiers de sortie .gcda. Les applications instrumentées utilisent un destructeur statique de priorité 99 pour invoquer la fonction "__gcov_dump". Ainsi, "__gcov_dump" est exécutée après tous les destructeurs statiques définis par l'utilisateur, ainsi que les gestionnaires enregistrés avec "atexit".

    Si un exécutable charge un objet partagé dynamique via la fonctionnalité dlopen, -Wl,--dynamic-list-data est nécessaire pour vider toutes les données de profil.

    La bibliothèque d'exécution de profilage signale diverses erreurs liées à la manipulation et à la sauvegarde des profils. Les erreurs sont imprimées sur la sortie d'erreur standard ou dans le fichier GCOV_ERROR_FILE, si la variable d'environnement est utilisée. Pour terminer immédiatement après une erreur, définissez la variable d'environnement GCOV_EXIT_AT_ERROR. Cela peut aider les utilisateurs à trouver des conflits de profils qui conduisent à un profil trompeur.
