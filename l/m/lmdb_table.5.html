LMDB_TABLE(5) Manuel des formats de fichiers LMDB_TABLE(5)

NOM

lmdb_table - Adaptateur LMDB de Postfix

SYNTAXE

postmap lmdb:/etc/postfix/fichier
postmap -i lmdb:/etc/postfix/fichier <fichier_entree
postmap -d "clef" lmdb:/etc/postfix/fichier
postmap -d - lmdb:/etc/postfix/fichier <fichier_entree
postmap -q "clef" lmdb:/etc/postfix/fichier
postmap -q - lmdb:/etc/postfix/fichier <fichier_entree

DESCRIPTION


L'adaptateur LMDB de Postfix fournit un accès à une base de données persistante clé-valeur mappée en mémoire. La taille de la base de données est limitée uniquement par l'espace d'adressage mémoire (généralement 31 ou 47 bits sur les CPU 32 bits ou 64 bits, respectivement) et par l'espace disponible sur le système de fichiers.

REQUETES

L'adaptateur LMDB prend en charge toutes les opérations de table de consultation de Postfix. Cela rend LMDB adapté à la réécriture d'adresses, au routage, aux politiques d'accès, aux caches, ou à toute information pouvant être stockée sous une clé de consultation fixe.

Lorsqu'une transaction échoue en raison d'une base de données pleine, Postfix redimensionne la base de données et réessaie la transaction.

Les recherches de table Postfix peuvent générer des clés de recherche partielles telles que des noms de domaine sans un ou plusieurs sous-domaines, des adresses réseau sans un ou plusieurs octets les moins significatifs, ou des adresses électroniques sans la partie locale, l'extension d'adresse ou le domaine. Ce comportement se retrouve également avec, par exemple, les tables btree:, hash: ou ldap:.

Les modifications apportées à une base de données LMDB ne déclenchent pas un redémarrage automatique du démon, et ne nécessitent pas de redémarrage avec "postfix reload".

FIABILITE

L'architecture copy-on-write de LMDB assure des mises à jour sûres, au prix d'une utilisation de l'espace plus importante que certaines autres bases de données de fichiers plats. Les opérations de lecture sont mappées en mémoire pour la rapidité. Les opérations d'écriture ne sont pas mappées en mémoire pour éviter une corruption silencieuse due à des bogues de pointeurs errants.

Plusieurs processus peuvent mettre à jour une base de données LMDB en toute sécurité sans sérialiser les requêtes via le service proxymap(8). Cela rend LMDB adapté en tant que cache partagé pour les services verify(8) ou postscreen(8).

SYNCHRONISATION

L'adaptateur LMDB de Postfix n'utilise pas le schéma de verrouillage intégré de LMDB, car cela nécessiterait des fichiers de verrouillage écrivables par tous et violerait le modèle de sécurité de Postfix. Au lieu de cela, Postfix utilise des verrous fcntl(2) avec une granularité de fichier entier. Les programmes qui utilisent le protocole de verrouillage intégré de LMDB corrompraient une base de données LMDB de Postfix ou liraient des données inutiles.

Chaque transaction de lecture ou d'écriture de base de données LMDB de Postfix doit être protégée du début à la fin avec un verrou fcntl(2) partagé ou exclusif. Un écrivain peut rétrograder atomiquement un verrou exclusif en un verrou partagé, mais il doit détenir un verrou exclusif lors de l'ouverture d'une autre transaction d'écriture.

Notez que les verrous fcntl(2) ne protègent pas les transactions au sein du même processus les unes contre les autres. Si un programme ne peut éviter de faire des requêtes de base de données simultanées, il doit protéger ses transactions avec des verrous intra-processus, en plus des verrous fcntl(2) par processus.

PARAMETRES DE CONFIGURATION

Les programmes de courte durée récupèrent automatiquement les modifications de main.cf. Avec les programmes de démon de longue durée, utilisez la commande "postfix reload" après une modification de configuration.

lmdb_map_size (16777216)
La limite de taille initiale de la base de données LMDB d'OpenLDAP en octets.
