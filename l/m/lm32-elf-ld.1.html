LD(1) Outils de développement GNU LD(1)

NOM

ld - L'éditeur de liens GNU

SYNTAXE

ld [options] fichier-objet ...

DESCRIPTION

ld combine un certain nombre de fichiers objets et d'archives, relocalise leurs données et résout les références de symboles. Généralement, la dernière étape de la compilation d'un programme consiste à exécuter ld.

ld accepte des fichiers de langage de commande de l'éditeur de liens écrits dans un sur-ensemble de la syntaxe du langage de commande de l'éditeur de liens d'AT&T, afin de fournir un contrôle explicite et total sur le processus d'édition de liens. L'éditeur de liens GNU ne lit pas les fichiers de commande de l'éditeur de liens par défaut. La commande pour lier le plus couramment utilisée est la commande gcc.

Cette page de manuel ne décrit pas le langage de commande ; voir l'entrée ld dans "info" pour les détails complets sur le langage de commande et sur d'autres aspects de l'éditeur de liens GNU.

Cette version de ld utilise les bibliothèques BFD à usage général pour opérer sur les fichiers objets. Cela permet à ld de lire, combiner et écrire des fichiers objets dans de nombreux formats différents, par exemple COFF ou "a.out". Différents formats peuvent être liés ensemble pour produire n'importe quel type de fichier objet disponible.

Outre sa flexibilité, l'éditeur de liens GNU est plus utile que d'autres éditeurs de liens pour fournir des informations diagnostiques. De nombreux éditeurs de liens abandonnent l'exécution immédiatement à la rencontre d'une erreur ; chaque fois que possible, ld continue son exécution, vous permettant d'identifier d'autres erreurs (ou, dans certains cas, d'obtenir un fichier de sortie malgré l'erreur).

L'éditeur de liens GNU ld est conçu pour couvrir un large éventail de situations et pour être aussi compatible que possible avec d'autres éditeurs de liens. Par conséquent, vous avez de nombreux choix pour contrôler son comportement.

OPTIONS

L'éditeur de liens supporte une pléthore d'options en ligne de commande, mais en pratique, peu d'entre elles sont utilisées dans un contexte particulier. Par exemple, une utilisation fréquente de ld est de lier des fichiers objets Unix standards sur un système Unix standard et supporté. Sur un tel système, pour lier un fichier "hello.o":

ld -o <sortie> /lib/crt0.o hello.o -lc

Ceci indique à ld de produire un fichier appelé sortie comme résultat de la liaison du fichier "/lib/crt0.o" avec "hello.o" et la bibliothèque "libc.a", qui proviendra des répertoires de recherche standards. (Voir la discussion de l'option -l ci-dessous.)

Certaines des options en ligne de commande de ld peuvent être spécifiées à n'importe quel endroit de la ligne de commande. Cependant, les options qui font référence à des fichiers, telles que -l ou -T, provoquent la lecture du fichier à l'endroit où l'option apparaît dans la ligne de commande, par rapport aux fichiers objets et aux autres options de fichier. La répétition d'options non liées à des fichiers avec un argument différent n'aura soit aucun effet supplémentaire, soit remplacera les occurrences précédentes (celles plus à gauche sur la ligne de commande) de cette option. Les options qui peuvent être spécifiées de manière significative plus d'une fois sont indiquées dans les descriptions ci-dessous.

Les arguments non-options sont des fichiers objets ou des archives qui doivent être liés ensemble. Ils peuvent suivre, précéder ou être mélangés avec les options de la ligne de commande, à l'exception qu'un argument de fichier objet ne peut pas être placé entre une option et son argument.

Généralement, l'éditeur de liens est appelé avec au moins un fichier objet, mais vous pouvez spécifier d'autres formes de fichiers d'entrée binaires en utilisant -l, -R, et le langage de commande de script. Si aucun fichier d'entrée binaire n'est spécifié du tout, l'éditeur de liens ne produit aucune sortie et émet le message No input files.

Si l'éditeur de liens ne peut pas reconnaître le format d'un fichier objet, il supposera qu'il s'agit d'un script d'éditeur de liens. Un script spécifié de cette manière augmente le script d'éditeur de liens principal utilisé pour la liaison (soit le script d'éditeur de liens par défaut, soit celui spécifié en utilisant -T). Cette fonctionnalité permet à l'éditeur de liens de se lier à un fichier qui semble être un objet ou une archive, mais qui définit en fait seulement certaines valeurs de symboles, ou utilise "INPUT" ou "GROUP" pour charger d'autres objets. La spécification d'un script de cette manière augmente simplement le script d'éditeur de liens principal, avec les commandes supplémentaires placées après le script principal ; utilisez l'option -T pour remplacer entièrement le script d'éditeur de liens par défaut, mais notez l'effet de la commande "INSERT".

Pour les options dont les noms sont une seule lettre, les arguments d'options doivent soit suivre la lettre d'option sans espace blanc intermédiaire, soit être donnés comme arguments séparés immédiatement après l'option qui les requiert.

Pour les options dont les noms sont plusieurs lettres, un ou deux traits peuvent précéder le nom de l'option ; par exemple, -trace-symbol et --trace-symbol sont équivalents. Notez qu'il y a une exception à cette règle. Les options à plusieurs lettres commençant par un 'o' minuscule ne peuvent être précédées que de deux traits. Ceci afin de réduire la confusion avec l'option -o. Ainsi, par exemple, -omagic définit le nom du fichier de sortie à magic, tandis que --omagic définit le flag NMAGIC sur la sortie.

Les arguments des options à plusieurs lettres doivent soit être séparés du nom de l'option par un signe égal, soit être donnés comme arguments séparés immédiatement après l'option qui les requiert. Par exemple, --trace-symbol foo et --trace-symbol=foo sont équivalents. Des abréviations uniques des noms d'options à plusieurs lettres sont acceptées.

Notez que si l'éditeur de liens est appelé indirectement, via un pilote de compilateur (par exemple, gcc), alors toutes les options en ligne de commande de l'éditeur de liens doivent être préfixées par -Wl, (ou ce qui est approprié pour le pilote de compilateur particulier), comme ceci :

gcc -Wl,--start-group foo.o bar.o -Wl,--end-group

Ceci est important, car sinon le programme pilote de compilateur peut silencieusement ignorer les options de l'éditeur de liens, résultant en une mauvaise liaison. De la confusion peut également survenir lors du passage d'options nécessitant des valeurs à travers un pilote, car l'utilisation d'un espace entre l'option et l'argument agit comme un séparateur, et fait que le pilote passe uniquement l'option à l'éditeur de liens et l'argument au compilateur. Dans ce cas, il est plus simple d'utiliser les formes jointes des options à une et plusieurs lettres, comme ceci :

gcc foo.o bar.o -Wl,-eENTRY -Wl,-Map=a.map

Voici une table des commutateurs génériques acceptés par l'éditeur de liens GNU :

@fichier
Lit les options de ligne de commande depuis fichier. Les options lues sont insérées à la place de l'option @fichier d'origine. Si fichier n'existe pas, ou ne peut pas être lu, alors l'option sera traitée littéralement, et ne sera pas supprimée.

Les options dans fichier sont séparées par des espaces blancs. Un caractère d'espace blanc peut être inclus dans une option en entourant l'option entière de guillemets simples ou doubles. N'importe quel caractère (y compris une barre oblique inverse) peut être inclus en préfixant le caractère à inclure par une barre oblique inverse. Le fichier peut lui-même contenir des options @fichier supplémentaires ; toutes ces options seront traitées récursivement.

-a mot-clé
Cette option est supportée pour la compatibilité HP/UX. L'argument mot-clé doit être l'une des chaînes archive, shared, ou default. -aarchive est fonctionnellement équivalent à -Bstatic, et les deux autres mots-clés sont fonctionnellement équivalents à -Bdynamic. Cette option peut être utilisée un nombre quelconque de fois.
--audit AUDITLIB
Ajoute AUDITLIB à l'entrée "DT_AUDIT" de la section dynamique. AUDITLIB n'est pas vérifié pour son existence, ni n'utilisera le DT_SONAME spécifié dans la bibliothèque. S'il est spécifié plusieurs fois, "DT_AUDIT" contiendra une liste d'interfaces d'audit à utiliser, séparées par des deux-points. Si l'éditeur de liens trouve un objet avec une entrée d'audit lors de la recherche de bibliothèques partagées, il ajoutera une entrée "DT_DEPAUDIT" correspondante dans le fichier de sortie. Cette option n'est significative que sur les plateformes ELF supportant l'interface rtld-audit.
-b format-entrée
--format=format-entrée
ld peut être configuré pour supporter plus d'un type de fichier objet. Si votre ld est configuré de cette manière, vous pouvez utiliser l'option -b pour spécifier le format binaire pour les fichiers objets qui suivent cette option sur la ligne de commande. Même lorsque ld est configuré pour supporter des formats d'objets alternatifs, vous n'avez généralement pas besoin de le spécifier, car ld devrait être configuré pour attendre comme un

Vous pourriez vouloir utiliser cette option si vous liez des fichiers avec un format binaire inhabituel. Vous pouvez également utiliser -b pour basculer explicitement les formats (lors de la liaison de fichiers objets de formats différents), en incluant -b format-entrée avant chaque groupe de fichiers objets d'un format particulier.

Le format par défaut est pris de la variable d'environnement "GNUTARGET".

Vous pouvez également définir le format d'entrée à partir d'un script, en utilisant la commande "TARGET" ;

-c fichier-commande-MRI
--mri-script=fichier-commande-MRI
Pour la compatibilité avec les linkeurs produits par MRI, ld accepte des fichiers scripts écrits dans un langage de commande alternatif et restreint, décrit dans la section Fichiers Scripts Compatibles MRI de la documentation GNU ld. Introduisez les fichiers scripts MRI avec l'option -c ; utilisez l'option -T pour exécuter des scripts de linkage écrits dans le langage de script ld à usage général. Si fichier-commande-MRI n'existe pas, ld le recherche dans les répertoires spécifiés par les options -L.
-d
-dc
-dp
Ces trois options sont équivalentes ; plusieurs formes sont supportées pour la compatibilité avec d'autres linkeurs. Elles allouent de l'espace aux symboles communs même si un fichier de sortie relogeable est spécifié (avec -r). La commande script "FORCE_COMMON_ALLOCATION" a le même effet.
--depaudit BIBLIB
-P BIBLIB
Ajoute BIBLIB à l'entrée "DT_DEPAUDIT" de la section dynamique. BIBLIB n'est pas vérifié pour son existence, et n'utilisera pas le DT_SONAME spécifié dans la bibliothèque. S'il est spécifié plusieurs fois, "DT_DEPAUDIT" contiendra une liste séparée par des deux-points d'interfaces d'audit à utiliser. Cette option n'est significative que sur les plateformes ELF supportant l'interface rtld-audit. L'option -P est fournie pour la compatibilité Solaris.
--enable-linker-version
Active la directive de script de linkage "LINKER_VERSION", décrite dans Données de Section de Sortie. Si cette directive est utilisée dans un script de linkage et que cette option a été activée, alors une chaîne contenant la version du linkage sera insérée au point actuel.

Remarque : l'emplacement de cette option sur la ligne de commande du linker est important. Elle n'affectera que les scripts de linkage qui la suivent sur la ligne de commande, ou qui sont intégrés au linker.

--disable-linker-version
Désactive la directive de script de linkage "LINKER_VERSION", de sorte qu'elle n'insère pas de chaîne de version. C'est le comportement par défaut.
--enable-non-contiguous-regions
Cette option évite de générer une erreur si une section d'entrée ne correspond pas à une section de sortie correspondante. Le linker essaie d'allouer la section d'entrée aux sections de sortie correspondantes suivantes, et ne génère une erreur que si aucune section de sortie n'est assez grande. Ceci est utile lorsque plusieurs régions mémoire non contiguës sont disponibles et que la section d'entrée ne requiert pas une région particulière. L'ordre dans lequel les sections d'entrée sont évaluées ne change pas, par exemple : 
MEMORY {
  MEM1 (rwx) : ORIGIN = 0x1000, LENGTH = 0x14
  MEM2 (rwx) : ORIGIN = 0x1000, LENGTH = 0x40
  MEM3 (rwx) : ORIGIN = 0x2000, LENGTH = 0x40
}
SECTIONS {
  mem1 : { *(.data.*); } > MEM1
  mem2 : { *(.data.*); } > MEM2
  mem3 : { *(.data.*); } > MEM3
}

avec les sections d'entrée :
.data.1: taille 8
.data.2: taille 0x10
.data.3: taille 4

résulte en .data.1 affectée à mem1, et .data.2 et .data.3
affectées à mem2, même si .data.3 rentrerait dans mem3.

Cette option est incompatible avec les instructions INSERT car elle modifie la manière dont les sections d'entrée sont mappées aux sections de sortie.

--enable-non-contiguous-regions-warnings
Cette option active les avertissements lorsque "--enable-non-contiguous-regions" permet des correspondances potentiellement inattendues dans le mappage des sections, pouvant conduire à ignorer silencieusement une section au lieu d'échouer parce qu'elle ne rentre dans aucune région de sortie.
-e point-d-entrée
--entry=point-d-entrée
Utilise point-d-entrée comme symbole explicite pour commencer l'exécution de votre programme, plutôt que le point d'entrée par défaut. S'il n'y a pas de symbole nommé point-d-entrée, le linker essaiera d'interpréter point-d-entrée comme un nombre, et l'utilisera comme adresse d'entrée (le nombre sera interprété en base 10 ; vous pouvez utiliser un préfixe 0x pour la base 16, ou un préfixe 0 pour la base 8).
--exclude-libs bib,bib,...
Spécifie une liste de bibliothèques d'archives à partir desquelles les symboles ne doivent pas être exportés automatiquement. Les noms de bibliothèques peuvent être délimités par des virgules ou des deux-points. Spécifier "--exclude-libs ALL" exclut les symboles de toutes les bibliothèques d'archives de l'exportation automatique. Cette option n'est disponible que pour le port PE i386 de la cible du linker et pour les ports ELF. Pour PE i386, les symboles explicitement listés dans un fichier .def sont toujours exportés, quelle que soit cette option. Pour les ports ELF, les symboles affectés par cette option seront traités comme cachés.
--exclude-modules-for-implib module,module,...
Spécifie une liste de fichiers objets ou de membres d'archive, à partir desquels les symboles ne doivent pas être exportés automatiquement, mais qui doivent être copiés intégralement dans la bibliothèque d'importation générée pendant la liaison. Les noms de modules peuvent être délimités par des virgules ou des deux-points, et doivent correspondre exactement aux noms de fichiers utilisés par ld pour ouvrir les fichiers ; pour les membres d'archive, il s'agit simplement du nom du membre, mais pour les fichiers objets, le nom listé doit inclure et correspondre précisément à tout chemin utilisé pour spécifier le fichier d'entrée sur la ligne de commande du linker. Cette option n'est disponible que pour le port PE i386 du linker. Les symboles explicitement listés dans un fichier .def sont toujours exportés, quelle que soit cette option.
-E
--export-dynamic
--no-export-dynamic
Lors de la création d'un exécutable lié dynamiquement, l'utilisation de l'option -E ou de l'option --export-dynamic provoque l'ajout de tous les symboles à la table des symboles dynamiques. La table des symboles dynamiques est l'ensemble des symboles qui sont visibles depuis les objets dynamiques à l'exécution.

Si vous n'utilisez aucune de ces options (ou utilisez l'option --no-export-dynamic pour rétablir le comportement par défaut), la table des symboles dynamiques contiendra normalement uniquement les symboles qui sont référencés par un objet dynamique mentionné dans la liaison.

Si vous utilisez "dlopen" pour charger un objet dynamique qui doit se référer aux symboles définis par le programme, plutôt qu'à un autre objet dynamique, alors vous devrez probablement utiliser cette option lors de la liaison du programme lui-même.

Vous pouvez également utiliser la liste dynamique pour contrôler quels symboles doivent être ajoutés à la table des symboles dynamiques si le format de sortie le supporte. Voir la description de --dynamic-list.

Notez que cette option est spécifique aux ports ELF. Les cibles PE supportent une fonction similaire pour exporter tous les symboles d'une DLL ou d'un EXE ; voir la description de --export-all-symbols ci-dessous.

--export-dynamic-symbol=glob
Lors de la création d'un exécutable lié dynamiquement, les symboles correspondant à glob seront ajoutés à la table des symboles dynamiques. Lors de la création d'une bibliothèque partagée, les références aux symboles correspondant à glob ne seront pas liées aux définitions dans la bibliothèque partagée. Cette option est inopérante lors de la création d'une bibliothèque partagée et que -Bsymbolic ou --dynamic-list ne sont pas spécifiés. Cette option n'est significative que sur les plateformes ELF qui supportent les bibliothèques partagées.
--export-dynamic-symbol-list=fichier
Spécifie un --export-dynamic-symbol pour chaque motif dans le fichier. Le format du fichier est le même que celui du nœud de version sans portée et nom de nœud. Voir VERSION pour plus d'informations.
-EB
Lier des objets big-endian. Ceci affecte le format de sortie par défaut.
-EL
Lier des objets little-endian. Ceci affecte le format de sortie par défaut.
-f nom
--auxiliary=nom
Lors de la création d'un objet partagé ELF, définit le champ interne DT_AUXILIARY sur le nom spécifié. Ceci indique au linker dynamique que la table des symboles de l'objet partagé doit être utilisée comme filtre auxiliaire sur la table des symboles de l'objet partagé nom.

Si plus tard vous liez un programme contre cet objet filtre, alors, lorsque vous exécuterez le programme, le linker dynamique verra le champ DT_AUXILIARY. Si le linker dynamique résout des symboles depuis l'objet filtre, il vérifiera d'abord s'il existe une définition dans l'objet partagé nom. S'il y en a une, elle sera utilisée à la place de la définition dans l'objet filtre. L'objet partagé nom n'a pas besoin d'exister. Ainsi, l'objet partagé nom peut être utilisé pour fournir une implémentation alternative de certaines fonctions, peut-être pour le débogage ou pour des performances spécifiques à la machine.

Cette option peut être spécifiée plusieurs fois. Les entrées DT_AUXILIARY seront créées dans l'ordre où elles apparaissent sur la ligne de commande.

-F nom
--filter=nom
Lors de la création d'un objet partagé ELF, définit le champ interne DT_FILTER au nom spécifié. Cela indique à l'éditeur de liens dynamique que la table des symboles de l'objet partagé en cours de création doit être utilisée comme filtre sur la table des symboles de l'objet partagé nom.

Si vous liez ultérieurement un programme à cet objet filtre, alors, lors de l'exécution du programme, l'éditeur de liens dynamique verra le champ DT_FILTER. L'éditeur de liens dynamique résoudra les symboles conformément à la table des symboles de l'objet filtre comme d'habitude, mais il se liera en fait aux définitions trouvées dans l'objet partagé nom. Ainsi, l'objet filtre peut être utilisé pour sélectionner un sous-ensemble des symboles fournis par l'objet nom.

Certains éditeurs de liens plus anciens utilisaient l'option -F dans toute la chaîne d'outils de compilation pour spécifier le format du fichier objet pour les fichiers objets d'entrée et de sortie. L'éditeur de liens GNU utilise d'autres mécanismes à cette fin : les options -b, --format, --oformat, la commande "TARGET" dans les scripts de l'éditeur de liens, et la variable d'environnement "GNUTARGET". L'éditeur de liens GNU ignorera l'option -F lorsqu'il ne créera pas d'objet partagé ELF.

-fini=nom
Lors de la création d'un exécutable ou d'un objet partagé ELF, appelle NOM lorsque l'exécutable ou l'objet partagé est déchargé, en définissant DT_FINI à l'adresse de la fonction. Par défaut, l'éditeur de liens utilise "_fini" comme fonction à appeler.
-g
Ignoré. Fourni pour la compatibilité avec d'autres outils.
-G valeur
--gpsize=valeur
Définit la taille maximale des objets à optimiser à l'aide du registre GP à taille. Ceci n'est pertinent que pour les formats de fichiers objets tels que MIPS ELF qui prennent en charge le placement d'objets volumineux et petits dans des sections différentes. Ceci est ignoré pour les autres formats de fichiers objets.
-h nom
-soname=nom
Lors de la création d'un objet partagé ELF, définit le champ interne DT_SONAME au nom spécifié. Lorsqu'un exécutable est lié à un objet partagé qui possède un champ DT_SONAME, alors lorsque l'exécutable est exécuté, l'éditeur de liens dynamique tentera de charger l'objet partagé spécifié par le champ DT_SONAME plutôt que d'utiliser le nom de fichier donné à l'éditeur de liens.
-i
Effectue une liaison incrémentielle (identique à l'option -r).
-init=nom
Lors de la création d'un exécutable ou d'un objet partagé ELF, appelle NOM lorsque l'exécutable ou l'objet partagé est chargé, en définissant DT_INIT à l'adresse de la fonction. Par défaut, l'éditeur de liens utilise "_init" comme fonction à appeler.
-l spécification_nom
--library=spécification_nom
Ajoute l'archive ou le fichier objet spécifié par spécification_nom à la liste des fichiers à lier. Cette option peut être utilisée un nombre quelconque de fois. Si spécification_nom est de la forme :nom_fichier, ld recherchera dans le chemin des bibliothèques un fichier nommé nom_fichier, sinon il recherchera dans le chemin des bibliothèques un fichier nommé libspécification_nom.a.

Sur les systèmes qui prennent en charge les bibliothèques partagées, ld peut également rechercher des fichiers autres que libspécification_nom.a. Spécifiquement, sur les systèmes ELF et SunOS, ld recherchera dans un répertoire une bibliothèque nommée libspécification_nom.so avant d'en rechercher une nommée libspécification_nom.a. (Par convention, une extension ".so" indique une bibliothèque partagée.) Notez que ce comportement ne s'applique pas à :nom_fichier, qui spécifie toujours un fichier nommé nom_fichier.

L'éditeur de liens ne recherchera dans une archive qu'une seule fois, à l'emplacement où elle est spécifiée sur la ligne de commande. Si l'archive définit un symbole qui était indéfini dans un objet apparu avant l'archive sur la ligne de commande, l'éditeur de liens inclura les fichiers appropriés de l'archive. Cependant, un symbole indéfini dans un objet apparaissant plus tard sur la ligne de commande n'entraînera pas l'éditeur de liens à rechercher à nouveau l'archive.

Voir l'option -( pour savoir comment forcer l'éditeur de liens à rechercher les archives plusieurs fois.

Vous pouvez lister la même archive plusieurs fois sur la ligne de commande.

Ce type de recherche d'archives est standard pour les éditeurs de liens Unix. Cependant, si vous utilisez ld sur AIX, notez qu'il est différent du comportement de l'éditeur de liens AIX.

-L répertoire_recherche
--library-path=répertoire_recherche
Ajoute le chemin répertoire_recherche à la liste des chemins que ld recherchera pour les bibliothèques d'archives et les scripts de contrôle de ld. Vous pouvez utiliser cette option un nombre quelconque de fois. Les répertoires sont recherchés dans l'ordre où ils sont spécifiés sur la ligne de commande. Les répertoires spécifiés sur la ligne de commande sont recherchés avant les répertoires par défaut. Toutes les options -L s'appliquent à toutes les options -l, indépendamment de l'ordre dans lequel les options apparaissent. Les options -L n'affectent pas la manière dont ld recherche un script d'éditeur de liens, sauf si l'option -T est spécifiée.

Si répertoire_recherche commence par "=" ou $SYSROOT, alors ce préfixe sera remplacé par le préfixe sysroot, contrôlé par l'option --sysroot, ou spécifié lors de la configuration de l'éditeur de liens.

L'ensemble par défaut de chemins recherchés (sans être spécifié avec -L) dépend du mode d'émulation utilisé par ld, et dans certains cas également de la manière dont il a été configuré.

Les chemins peuvent également être spécifiés dans un script de liaison avec la commande "SEARCH_DIR". Les répertoires spécifiés de cette manière sont recherchés au point où le script de liaison apparaît sur la ligne de commande.

-m émulation
Émule l'éditeur de liens émulation. Vous pouvez lister les émulations disponibles avec les options --verbose ou -V.

Si l'option -m n'est pas utilisée, l'émulation est prise de la variable d'environnement "LDEMULATION", si elle est définie.

Sinon, l'émulation par défaut dépend de la manière dont l'éditeur de liens a été configuré.

--remap-inputs=motif=nom_fichier
--remap-inputs-file=fichier
Ces options permettent de modifier les noms des fichiers d'entrée avant que l'éditeur de liens ne tente de les ouvrir. L'option --remap-inputs=foo.o=bar.o entraînera toute tentative de chargement d'un fichier nommé foo.o à essayer plutôt de charger un fichier nommé bar.o. Les motifs génériques sont autorisés dans le premier nom de fichier, donc --remap-inputs=foo*.o=bar.o renommera tout fichier d'entrée qui correspond à foo*.o en bar.o.

Une forme alternative de l'option --remap-inputs-file=nom_fichier permet de lire les remappages à partir d'un fichier. Chaque ligne du fichier peut contenir un seul remappage. Les lignes vides sont ignorées. Tout ce qui commence par un caractère dièse (#) jusqu'à la fin d'une ligne est considéré comme un commentaire et est également ignoré. Le motif de remappage peut être séparé du nom de fichier par un espace blanc ou un signe égal (=).

Les options peuvent être spécifiées plusieurs fois. Leur contenu s'accumule. Les remappages seront traités dans l'ordre où ils apparaissent sur la ligne de commande, et s'ils proviennent d'un fichier, dans l'ordre où ils apparaissent dans le fichier. Si une correspondance est trouvée, aucune vérification supplémentaire pour ce nom de fichier ne sera effectuée.

Si le nom de fichier de remplacement est /dev/null ou simplement NUL, alors le remappage provoquera en fait l'ignorance du fichier d'entrée. Cela peut être un moyen pratique d'expérimenter la suppression de fichiers d'entrée d'un environnement de construction complexe.

Notez que cette option dépend de la position et n'affecte que les noms de fichiers qui la suivent sur la ligne de commande. Ainsi :

ld foo.o --remap-inputs=foo.o=bar.o

N'aura aucun effet, alors que :

ld --remap-inputs=foo.o=bar.o foo.o

Renommera le fichier d'entrée foo.o en bar.o.

Notez que ces options affectent également les fichiers référencés par les instructions INPUT dans les scripts de l'éditeur de liens. Mais comme les scripts de l'éditeur de liens sont traités après la lecture de la ligne de commande entière, la position des options de remappage sur la ligne de commande n'est pas significative.

Si l'option verbose est activée, tout remappage correspondant sera signalé, bien que, là encore, l'option verbose doive être activée sur la ligne de commande avant l'apparition des noms de fichiers remappés.

Si les options -Map ou --print-map sont activées, la liste des remappages sera incluse dans la sortie de la carte.

-M
--print-map
Imprime une carte de liaison sur la sortie standard. Une carte de liaison fournit des informations sur la liaison, notamment :
  • Où les fichiers objets sont mappés en mémoire.
  • Comment les symboles communs sont alloués.
  • Tous les membres d'archive inclus dans la liaison, avec une mention du symbole qui a causé l'inclusion du membre d'archive.
  • Les valeurs attribuées aux symboles.

    Notez que les symboles dont les valeurs sont calculées par une expression qui implique une référence à une valeur précédente du même symbole peuvent ne pas avoir le résultat correct affiché dans la carte de liaison. Ceci est dû au fait que l'éditeur de liens ignore les résultats intermédiaires et ne conserve que la valeur finale d'une expression. Dans de telles circonstances, l'éditeur de liens affichera la valeur finale entourée de crochets. Ainsi, par exemple, un script de l'éditeur de liens contenant :

    foo = 1
foo = foo * 4
foo = foo + 8

    produira la sortie suivante dans la carte de liaison si l'option -M est utilisée :

    0x00000001                foo = 0x1
[0x0000000c]                foo = (foo * 0x4)
[0x0000000c]                foo = (foo + 0x8)

    OPTIONS

    The following options are recognized by ld(1).

    -as-needed, -a
    Affects ELF DT_NEEDED tags for dynamic libraries mentioned on the command line after the -as-needed option. Normally the linker will add a DT_NEEDED tag for each dynamic library mentioned on the command line, regardless of whether the library is actually needed or not. -as-needed causes a DT_NEEDED tag to only be emitted for a library that at that point in the link satisfies a non-weak undefined symbol reference from a regular object file or, if the library is not found in the DT_NEEDED lists of other needed libraries, a non-weak undefined symbol reference from another needed dynamic library. Object files or libraries appearing on the command line after the library in question do not affect whether the library is seen as needed. This is similar to the rules for extraction of object files from archives. This option is the inverse of -non-needed.
    -Bdynamic
    Link against shared libraries. This is only meaningful on platforms for which shared libraries are supported. This option is normally the default on such platforms. The different variants of this option are for compatibility with various systems. You may use this option multiple times on the command line: it affects library searching for -l options which follow it.
    -Bgroup
    Set the "DF_1_GROUP" flag in the "DT_FLAGS_1" entry in the dynamic section. This causes the runtime linker to handle lookups in this object and its dependencies to be performed only inside the group. --unresolved-symbols=report-all is implied. This option is only meaningful on ELF platforms which support shared libraries.
    -Bsymbolic
    When creating a shared library, bind references to global symbols to the definition within the shared library, if any. Normally, it is possible for a program linked against a shared library to override the definition within the shared library. This option is only relevant when creating shared libraries.
    -Bstatic
    Link against static libraries. This is only meaningful on platforms for which shared libraries are supported. The different variants of this option are for compatibility with various systems. You may use this option multiple times on the command line: it affects library searching for -l options which follow it. This option also implies --unresolved-symbols=report-all. This option can be used with -shared. Doing so means that a shared library is being created but that all of the library's external references must be resolved by pulling in entries from static libraries.
    --copy-dt-needed-entries
    Make copies of the DT_NEEDED entries from dynamic libraries into the output file. This is the default behaviour.
    -cref
    Produce a cross-reference table. This is only supported on platforms that use the COFF object file format.
    -defsym name=value
    Create a symbol named name and set its value to value. This is only supported on platforms that use the COFF object file format.
    --embedded
    Produce an executable image that can be run on an embedded system. This implies that the linker should not create a BSS segment and should not assume that it can use the standard C library.
    --filter-libs list
    Comma separated list of archive names. Archives in the list are not copied into the output file. This option is only valid when creating a shared library. This option is only supported on ELF platforms.
    -gc-sections, -Wl,--gc-sections
    Remove unused sections from the output file. This option is only relevant when creating shared libraries.
    --help
    Print a list of available options on the standard output, and exit.
    -o outfile
    Use outfile for the name of the output file instead of the default name of a.out.
    -N
    This option is ignored for SunOS compatibility.
    -nxcompat
    Set the NX bit in the ELF header. This indicates that the text segment should not be executed.
    -pie
    Create a position independent executable. This option is only relevant when creating an executable file.
    --print-gc-sections
    List the sections that are garbage collected when -gc-sections is used.
    --print-map
    Print a map file describing the layout of the output file. This is equivalent to providing a file name of /dev/stdout to the -Map option.
    -r
    This option is ignored for SunOS compatibility.
    --rpath list
    --runtime-dirs list
    A comma separated list of directories to be searched for shared libraries at runtime. This option is only supported on ELF platforms.
    --rpath-link list
    -L list
    A comma separated list of directories to be searched for shared libraries. This option is only supported on ELF platforms. On Linux based systems this option also affects the behaviour of the -as-needed option.
    -shared
    Create a shared object. This is equivalent to the -Bshareable option. This option is only relevant on platforms that support shared objects.
    --trace
    Print the names of the object files as they are processed. This option is only supported on platforms that use the COFF object file format.
    --trace-symbol=symbol
    Trace access to the specified symbol. This option is only relevant when creating shared libraries.
    --unresolved-symbols={report-all|ignore-all|ignore-in-shared-libs|remove-in-object-files|report-in-object-files}
    Specify how to handle unresolved symbols. The default is report-in-object-files.
    report-all
    Report all unresolved symbols.
    ignore-all
    Ignore all unresolved symbols.
    ignore-in-shared-libs
    Ignore unresolved symbols in shared libraries.
    remove-in-object-files
    Remove unresolved symbols from object files.
    report-in-object-files
    Report unresolved symbols in object files.
    --version
    Print the version number of the linker on the standard output, and exit.
    -V
    Increment the linker's verbosity level. This option is ignored for SunOS compatibility.
    -warn-common
    Warn if any common symbols are used. This option is ignored for SunOS compatibility.
    -Wl,--warn-textrel
    Warn if the linker creates a non-PIC executable that contains relocations in the text segment.
    est-warnings
    Make all warnings into errors. This switch is not supported by all linkers.
    --filter-paths
    --no-filter-paths
    Normally the linker will search for input files in directories specified by the options -L, -I and --sysroot. This option disables this search for directories which are specified by options, but it does not disable search in directories specified on the command line directly.

    The default behaviour can be restored using --filter-paths.

    --gc-sections
    --no-gc-sections
    When creating a shared object or executable, it is sometimes possible to discard unused sections. This option enables this garbage collection. This is done by marking sections that are referenced by other sections, or by symbols, and discarding the others. This may be useful for reducing the size of executables and shared objects. The default can be restored by using --no-gc-sections.
    --impltoc-section=name
    Set the name of the section used for the implementation symbol table. This is only useful when creating shared libraries.
    --incremental
    --no-incremental
    Enable or disable incremental linking. Incremental linking allows the linker to reuse information from a previous link, and hence make subsequent links much faster. This is the default for relocatable links but is not supported for absolute links. The default behaviour can be restored using --no-incremental.
    --just-symbols=file
    Copy symbols from file to the output file. No relocation information is copied. This is the default behavior when linking relocatably (using -r). You can use this option to force the linker to behave as if it were linking relocatably, even when it is not.
    --keep-archive-member-symbols
    --no-keep-archive-member-symbols
    When creating a shared object, the linker normally removes the symbols for archive members. This option prevents that. This is the default behaviour, and it can be restored using --no-keep-archive-member-symbols.
    --link-flavor=flavor
    Use the specified linking flavor. Currently supported flavors are eabi and bfin-eabi. The default flavor is used if this option is not specified.
    --local-undefined=method
    This option controls how the linker deals with undefined symbols that are local to a shared object. The default method is eabi.

    Supported methods are:

    eabi
    Global symbols are not visible in the shared object. This is the default behaviour.
    stub
    A stub symbol is created for each undefined symbol.
    indirect
    A stub symbol is created for each undefined symbol. The stub is used to resolve the symbol.
    --main-path=path
    Set the main path for the linker. This is used when searching for objects and libraries.
    -Map=mapfile

    --no-merge-Moveable

    --no-multiple-final-definition
    This option ensures that only one definition of each symbol is ever final. This is the default behaviour.
    --nmagic
    Disable the "the magic numbers in the object file headers" option. This option is intended for use with old systems that do not understand the magic numbers.
    --no-warn-mismatch
    Do not warn about mismatches between the object file version and the linker script version.
    --no-warn-search-mismatch
    Do not warn about mismatches between the object file search path and the linker search path.
    --no-whole-archive
    --whole-archive
    When creating a shared object, the linker normally only includes archive members that are referenced. This option forces the linker to include all archive members. The default behavior can be restored using --no-whole-archive.
    -ooutfile
    Use outfile as the name of the output file. The linker normally names the output file a.out.
    -p
    This option is obsolete. It used to create a program that could be executed. Use -o instead.
    --print-map
    Print the linker map to standard output. This is the default behavior.
    --relax
    --no-relax
    Enable or disable linker relaxation. Linker relaxation is the process of replacing short branches with longer ones when necessary. This can be used to improve code size and performance. The default behavior can be restored using --no-relax.
    -r
    Create a relocatable output file. This is useful for creating shared libraries, or for linking together multiple object files into a single relocatable object file. The output file is created with the same format as the input files.
    --reloc-section=name

    --shared
    Create a shared object. This is equivalent to using the linker script option -shared.
    --shared-libname=name

    --sort-section=alignment

    --split-stack=size

    -static
    Do not use any shared libraries. Link all functions and data into the executable. This is the default.
    --strip-symbols
    Remove all symbols from the output file. This is useful for reducing the size of executables and shared objects.
    --sysroot=root

    -t

    -Tscript

    --traditional-format

    -v

    --version

    --warn-common-symbol-overwrite

    --warn-constructors

    --warn-multiple-aliasing

    --wrap=symbol

    -w
    --no-warnings

    --force-exe-suffix
    S'assurer qu'un fichier de sortie a le suffixe .exe.

    Si un fichier de sortie entièrement lié et construit avec succès n'a pas de suffixe ".exe" ou ".dll", cette option force l'éditeur de liens à copier le fichier de sortie dans un autre portant le même nom avec un suffixe ".exe". Cette option est utile lors de l'utilisation de makefiles Unix non modifiés sur un hôte Microsoft Windows, car certaines versions de Windows n'exécuteront pas une image si elle ne se termine pas par un suffixe ".exe".

    --gc-sections
    --no-gc-sections
    Activer la collecte de garbage des sections d'entrée inutilisées. Elle est ignorée sur les cibles qui ne prennent pas en charge cette option. Le comportement par défaut (ne pas effectuer cette collecte de garbage) peut être restauré en spécifiant --no-gc-sections sur la ligne de commande. Notez que la collecte de garbage pour les cibles de format COFF et PE est prise en charge, mais l'implémentation est actuellement considérée comme expérimentale.

    --gc-sections décide quelles sections d'entrée sont utilisées en examinant les symboles et les relocations. La section contenant le symbole d'entrée et toutes les sections contenant des symboles indéfinis sur la ligne de commande seront conservées, tout comme les sections contenant des symboles référencés par des objets dynamiques. Notez que lors de la construction de bibliothèques partagées, l'éditeur de liens doit supposer que tout symbole visible est référencé. Une fois cet ensemble initial de sections déterminé, l'éditeur de liens marque récursivement comme utilisées toute section référencée par ses relocations. Voir --entry, --undefined et --gc-keep-exported.

    Cette option peut être définie lors d'une liaison partielle (activée avec l'option -r). Dans ce cas, la racine des symboles conservés doit être explicitement spécifiée soit par l'une des options --entry, --undefined ou --gc-keep-exported, soit par une commande "ENTRY" dans le script de l'éditeur de liens.

    En tant qu'extension GNU, les sections d'entrée ELF marquées avec le drapeau "SHF_GNU_RETAIN" ne seront pas collectées par le garbage.

    --print-gc-sections
    --no-print-gc-sections
    Lister toutes les sections supprimées par la collecte de garbage. La liste est imprimée sur stderr. Cette option n'est efficace que si la collecte de garbage a été activée via l'option --gc-sections. Le comportement par défaut (ne pas lister les sections supprimées) peut être restauré en spécifiant --no-print-gc-sections sur la ligne de commande.
    --gc-keep-exported
    Lorsque --gc-sections est activé, cette option empêche la collecte de garbage des sections d'entrée inutilisées qui contiennent des symboles globaux ayant une visibilité par défaut ou protégée. Cette option est destinée à être utilisée pour les exécutables où les sections non référencées seraient autrement collectées par le garbage, quelle que soit la visibilité externe des symboles contenus. Notez que cette option n'a aucun effet lors de la liaison d'objets partagés, car c'est déjà le comportement par défaut. Cette option n'est prise en charge que pour les cibles au format ELF.
    --print-output-format
    Imprimer le nom du format de sortie par défaut (peut-être influencé par d'autres options de la ligne de commande). C'est la chaîne qui apparaîtrait dans une commande de script d'éditeur de liens "OUTPUT_FORMAT".
    --print-memory-usage
    Imprimer la taille utilisée, la taille totale et la taille utilisée des régions de mémoire créées avec la commande MEMORY. Ceci est utile sur les cibles embarquées pour avoir une vue rapide de la quantité de mémoire libre. Le format de la sortie comporte un titre et une ligne par région. Il est à la fois lisible par l'homme et facilement analysable par des outils. Voici un exemple de sortie : 
    Région mémoire      Taille utilisée  Taille région  % utilisé
             ROM:        256 Ko         1 Mo     25.00%
             RAM:          32 octets      2 Go      0.00%

    Imprimer un résumé des options de la ligne de commande sur la sortie standard et quitter.
    --target-help
    Imprimer un résumé de toutes les options spécifiques à la cible sur la sortie standard et quitter.
    -Map=fichier_map
    Imprimer une carte de liaison dans le fichier fichier_map. Voir la description de l'option -M, ci-dessus. Si fichier_map est juste le caractère "-", la carte sera écrite sur stdout.

    Spécifier un répertoire comme fichier_map fait que la carte de l'éditeur de liens est écrite dans un fichier à l'intérieur du répertoire. Normalement, le nom du fichier à l'intérieur du répertoire est calculé comme le nom de base du fichier de sortie output avec ".map" ajouté. Si cependant le caractère spécial "%" est utilisé, il sera remplacé par le chemin complet du fichier de sortie. De plus, s'il y a des caractères après le symbole %, alors ".map" ne sera plus ajouté.

    -o foo.exe -Map=bar                  [Crée ./bar]
-o ../dir/foo.exe -Map=bar           [Crée ./bar]
-o foo.exe -Map=../dir               [Crée ../dir/foo.exe.map]
-o ../dir2/foo.exe -Map=../dir       [Crée ../dir/foo.exe.map]
-o foo.exe -Map=%                    [Crée ./foo.exe.map]
-o ../dir/foo.exe -Map=%             [Crée ../dir/foo.exe.map]
-o foo.exe -Map=%.bar                [Crée ./foo.exe.bar]
-o ../dir/foo.exe -Map=%.bar         [Crée ../dir/foo.exe.bar]
-o ../dir2/foo.exe -Map=../dir/%     [Crée ../dir/../dir2/foo.exe.map]
-o ../dir2/foo.exe -Map=../dir/%.bar [Crée ../dir/../dir2/foo.exe.bar]

    Il est erroné de spécifier plus d'un caractère "%".

    Si le fichier de carte existe déjà, il sera écrasé par cette opération.

    --no-keep-memory
    ld optimise normalement la vitesse au détriment de l'utilisation de la mémoire en mettant en cache les tables de symboles des fichiers d'entrée en mémoire. Cette option indique à ld d'optimiser à la place l'utilisation de la mémoire, en relisant les tables de symboles si nécessaire. Cela peut être requis si ld manque d'espace mémoire lors de la liaison d'un grand exécutable.
    --no-undefined
    -z defs
    Signaler les références de symboles non résolues provenant de fichiers objets réguliers. Ceci est fait même si l'éditeur de liens crée une bibliothèque partagée non symbolique. Le commutateur --[no-]allow-shlib-undefined contrôle le comportement pour le signalement des références non résolues trouvées dans les bibliothèques partagées en cours de liaison.

    Les effets de cette option peuvent être annulés en utilisant "-z undefs".

    --allow-multiple-definition
    -z muldefs
    Normalement, lorsqu'un symbole est défini plusieurs fois, l'éditeur de liens signale une erreur fatale. Ces options autorisent les définitions multiples et la première définition sera utilisée.
    --allow-shlib-undefined
    --no-allow-shlib-undefined
    Autorise ou interdit les symboles indéfinis dans les bibliothèques partagées. Ce commutateur est similaire à --no-undefined sauf qu'il détermine le comportement lorsque les symboles indéfinis se trouvent dans une bibliothèque partagée plutôt que dans un fichier objet régulier. Il n'affecte pas la manière dont les symboles indéfinis dans les fichiers objets réguliers sont gérés.

    Le comportement par défaut est de signaler les erreurs pour tous les symboles indéfinis référencés dans les bibliothèques partagées si l'éditeur de liens est utilisé pour créer un exécutable, mais de les autoriser si l'éditeur de liens est utilisé pour créer une bibliothèque partagée.

    Les raisons pour lesquelles les références de symboles indéfinis dans les bibliothèques partagées spécifiées au moment de la liaison sont autorisées sont que :

    • Une bibliothèque partagée spécifiée au moment de la liaison peut ne pas être la même que celle disponible au moment du chargement, de sorte que le symbole pourrait en fait être résoluble au moment du chargement.
    • Il existe certains systèmes d'exploitation, par exemple BeOS et HPPA, où les symboles indéfinis dans les bibliothèques partagées sont normaux.

      Le noyau BeOS, par exemple, patch les bibliothèques partagées au moment du chargement pour sélectionner la fonction la plus appropriée à l'architecture actuelle. Ceci est utilisé, par exemple, pour sélectionner dynamiquement une fonction memset appropriée.

    --error-handling-script=nom_script
    Si cette option est fournie, l'éditeur de liens invoquera nom_script chaque fois qu'une erreur est rencontrée. Actuellement, seuls deux types d'erreurs sont pris en charge : symboles manquants et bibliothèques manquantes. Deux arguments seront passés au script : le mot-clé "undefined-symbol" ou `missing-lib" et le nom du symbole indéfini ou de la bibliothèque manquante. L'intention est que le script fournisse des suggestions à l'utilisateur quant à l'endroit où le symbole ou la bibliothèque pourrait être trouvé. Une fois le script terminé, le message d'erreur normal de l'éditeur de liens sera affiché.

    La disponibilité de cette option est contrôlée par un commutateur de configuration, elle peut donc ne pas être présente dans des implémentations spécifiques.

    --no-undefined-version
    Normalement, lorsqu'un symbole a une version indéfinie, l'éditeur de liens l'ignore. Cette option interdit les symboles de version indéfinie et une erreur fatale sera émise à la place.
    --default-symver
    Créer et utiliser une version de symbole par défaut (le soname) pour les symboles exportés non versionnés.
    id="default~3">--default-imported-symver
    Crée et utilise une version de symbole par défaut (le soname) pour les symboles importés non versionnés.
    --no-warn-mismatch
    Normalement, ld générera une erreur si vous essayez de lier des fichiers d'entrée qui sont incompatibles pour une raison quelconque, peut-être parce qu'ils ont été compilés pour des processeurs différents ou pour des endiannesses différentes. Cette option indique à ld qu'il doit autoriser silencieusement de telles erreurs potentielles. Cette option ne doit être utilisée qu'avec précaution, dans les cas où vous avez pris des mesures spéciales pour garantir que les erreurs du lieur sont inappropriées.
    --no-warn-search-mismatch
    Normalement, ld émettra un avertissement s'il trouve une bibliothèque incompatible lors d'une recherche de bibliothèque. Cette option supprime l'avertissement.
    --no-whole-archive
    Désactive l'effet de l'option --whole-archive pour les fichiers d'archive suivants.
    --noinhibit-exec
    Conserve le fichier de sortie exécutable tant qu'il est encore utilisable. Normalement, le lieur ne produira pas de fichier de sortie s'il rencontre des erreurs pendant le processus de liaison ; il se termine sans écrire de fichier de sortie lorsqu'il émet une erreur quelconque.
    -nostdlib
    Ne recherche les répertoires de bibliothèques explicitement spécifiés sur la ligne de commande. Les répertoires de bibliothèques spécifiés dans les scripts de liaison (y compris les scripts de liaison spécifiés sur la ligne de commande) sont ignorés.
    --oformat=format-sortie
    ld peut être configuré pour prendre en charge plus d'un type de fichier objet. Si votre ld est configuré de cette manière, vous pouvez utiliser l'option --oformat pour spécifier le format binaire pour le fichier objet de sortie. Même lorsque ld est configuré pour prendre en charge des formats d'objet alternatifs, vous n'avez généralement pas besoin de le spécifier, car ld doit être configuré pour produire en tant que format de sortie par défaut le format le plus courant sur chaque machine. format-sortie est une chaîne de texte, le nom d'un format particulier pris en charge par les bibliothèques BFD. (Vous pouvez lister les formats binaires disponibles avec objdump -i.) La commande de script "OUTPUT_FORMAT" peut également spécifier le format de sortie, mais cette option la remplace.
    --out-implib fichier
    Crée une bibliothèque d'importation dans fichier correspondant à l'exécutable que le lieur génère (par exemple, une DLL ou un programme ELF). Cette bibliothèque d'importation (qui devrait s'appeler "*.dll.a" ou "*.a" pour les DLL) peut être utilisée pour lier les clients à l'exécutable généré ; ce comportement permet d'éviter une étape de création de bibliothèque d'importation séparée (par exemple, "dlltool" pour les DLL). Cette option n'est disponible que pour les ports du lieur ciblant i386 PE et ELF.
    -pie
    --pic-executable
    Crée un exécutable indépendant de la position. Ceci n'est actuellement pris en charge que sur les plateformes ELF. Les exécutables indépendants de la position sont similaires aux bibliothèques partagées en ce sens qu'ils sont déplacés par le lieur dynamique à l'adresse virtuelle que le système d'exploitation leur attribue (ce qui peut varier entre les invocations). Comme les exécutables liés dynamiquement normaux, ils peuvent être exécutés et les symboles définis dans l'exécutable ne peuvent pas être remplacés par des bibliothèques partagées.
    -no-pie
    Crée un exécutable dépendant de la position. C'est le comportement par défaut.
    -qmagic
    Cette option est ignorée pour la compatibilité Linux.
    -Qy
    Cette option est ignorée pour la compatibilité SVR4.
    --relax
    --no-relax
    Une option avec des effets dépendants de la machine. Cette option n'est prise en charge que sur quelques cibles.

    Sur certaines plateformes, l'option --relax effectue des optimisations globales spécifiques à la cible qui deviennent possibles lorsque le lieur résout l'adressage dans le programme, telles que la relaxation des modes d'adressage, la synthèse de nouvelles instructions, la sélection de versions plus courtes des instructions actuelles et la combinaison de valeurs constantes.

    Sur certaines plateformes, ces optimisations globales au moment de la liaison peuvent rendre le débogage symbolique de l'exécutable résultant impossible. C'est le cas pour les processeurs de la famille Matsushita MN10200 et MN10300.

    Sur les plateformes où la fonctionnalité est prise en charge, l'option --no-relax la désactive.

    Sur les plateformes où la fonctionnalité n'est pas prise en charge, les deux options --relax et --no-relax sont acceptées, mais ignorées.

    --retain-symbols-file=nom-fichier
    Conserve *uniquement* les symboles listés dans le fichier nom-fichier, en supprimant tous les autres. nom-fichier est simplement un fichier plat, avec un nom de symbole par ligne. Cette option est particulièrement utile dans les environnements (comme VxWorks) où une grande table de symboles globale est accumulée progressivement, pour économiser de la mémoire d'exécution.

    --retain-symbols-file ne supprime *pas* les symboles indéfinis, ni les symboles nécessaires aux relocalisations.

    Vous ne pouvez spécifier --retain-symbols-file qu'une seule fois sur la ligne de commande. Elle remplace -s et -S.

    -rpath=rép
    Ajoute un répertoire au chemin de recherche des bibliothèques d'exécution. Ceci est utilisé lors de la liaison d'un exécutable ELF avec des objets partagés. Tous les arguments -rpath sont concaténés et transmis au lieur d'exécution, qui les utilise pour localiser les objets partagés à l'exécution.

    L'option -rpath est également utilisée lors de la localisation des objets partagés requis par les objets partagés explicitement inclus dans la liaison ; voir la description de l'option -rpath-link. La recherche de -rpath de cette manière n'est prise en charge que par les lieurs natifs et les lieurs croisés qui ont été configurés avec l'option --with-sysroot.

    Si -rpath n'est pas utilisé lors de la liaison d'un exécutable ELF, le contenu de la variable d'environnement "LD_RUN_PATH" sera utilisé s'il est défini.

    L'option -rpath peut également être utilisée sur SunOS. Par défaut, sur SunOS, le lieur forme un chemin de recherche d'exécution à partir de toutes les options -L qui lui sont fournies. Si une option -rpath est utilisée, le chemin de recherche d'exécution sera formé exclusivement à l'aide des options -rpath, ignorant les options -L. Cela peut être utile lors de l'utilisation de gcc, qui ajoute de nombreuses options -L qui peuvent se trouver sur des systèmes de fichiers montés NFS.

    Pour la compatibilité avec d'autres lieurs ELF, si l'option -R est suivie d'un nom de répertoire, plutôt que d'un nom de fichier, elle est traitée comme l'option -rpath.

    -rpath-link=rép
    Lors de l'utilisation d'ELF ou de SunOS, une bibliothèque partagée peut en nécessiter une autre. Cela se produit lorsqu'une liaison "ld -shared" inclut une bibliothèque partagée comme l'un des fichiers d'entrée.

    Lorsque le lieur rencontre une telle dépendance lors d'une liaison non partagée et non déplaçable, il essaiera automatiquement de localiser la bibliothèque partagée requise et de l'inclure dans la liaison, si elle n'est pas incluse explicitement. Dans un tel cas, l'option -rpath-link spécifie le premier ensemble de répertoires à rechercher. L'option -rpath-link peut spécifier une séquence de noms de répertoires soit en spécifiant une liste de noms séparés par des deux-points, soit en apparaissant plusieurs fois.

    Les jetons $ORIGIN et $LIB peuvent apparaître dans ces répertoires de recherche. Ils seront remplacés par le chemin complet du répertoire contenant le programme ou l'objet partagé dans le cas de $ORIGIN et soit lib - pour les binaires 32 bits - soit lib64 - pour les binaires 64 bits - dans le cas de $LIB.

    La forme alternative de ces jetons - ${ORIGIN} et ${LIB} peut également être utilisée. Le jeton $PLATFORM n'est pas pris en charge.

    Cette option doit être utilisée avec précaution car elle remplace le chemin de recherche qui aurait pu être codé en dur dans une bibliothèque partagée. Dans un tel cas, il est possible d'utiliser involontairement un chemin de recherche différent de celui que le lieur d'exécution utiliserait.

    Le lieur utilise les chemins de recherche suivants pour localiser les bibliothèques partagées requises :

    1.
    Tous les répertoires spécifiés par les options -rpath-link.
    2.
    Tous les répertoires spécifiés par les options -rpath. La différence entre -rpath et -rpath-link est que les répertoires spécifiés par les options -rpath sont inclus dans l'exécutable et utilisés à l'exécution, tandis que l'option -rpath-link n'est effective qu'au moment de la liaison. La recherche de -rpath de cette manière n'est prise en charge que par les lieurs natifs et les lieurs croisés qui ont été configurés avec l'option --with-sysroot.
    3.
    Sur un système ELF, pour les lieurs natifs, si les options -rpath et -rpath-link n'ont pas été utilisées, recherchez le contenu de la variable d'environnement "LD_RUN_PATH".
    4.
    Sur SunOS, si l'option -rpath n'a pas été utilisée, recherchez tous les répertoires spécifiés à l'aide des options -L.
    5.
    Pour un lieur natif, recherchez le contenu de la variable d'environnement "LD_LIBRARY_PATH".
    6.
    Pour un lieur ELF natif, les répertoires dans "DT_RUNPATH" ou "DT_RPATH" d'une bibliothèque partagée sont recherchés pour les bibliothèques partagées dont elle a besoin. Les entrées "DT_RPATH" sont ignorées si des entrées "DT_RUNPATH" existent.
    7.
    Pour un lieur système Linux, si le fichier /etc/ld.so.conf existe, la liste des répertoires trouvés dans ce fichier. Remarque : le chemin de ce fichier est précédé de la valeur "sysroot", si elle est définie, puis de toute chaîne "prefix" si le lieur a été configuré avec le b
    >--prefix=<chemin>.
    8.
    Pour un éditeur de liens natif sur un système FreeBSD, tous les répertoires spécifiés par la macro "_PATH_ELF_HINTS" définie dans le fichier d'en-tête elf-hints.h.
    9.
    Tous les répertoires spécifiés par une commande "SEARCH_DIR" dans un script d'éditeur de liens donné sur la ligne de commande, y compris les scripts spécifiés par -T (mais pas -dT).
    10.
    Les répertoires par défaut, normalement /lib et /usr/lib.
    11.
    Tous les répertoires spécifiés par un plugin LDPT_SET_EXTRA_LIBRARY_PATH.
    12.
    Tous les répertoires spécifiés par une commande "SEARCH_DIR" dans un script d'éditeur de liens par défaut.

    Notez cependant que sur les systèmes basés sur Linux, il y a une mise en garde supplémentaire : Si l'option --as-needed est active et qu'une bibliothèque partagée est trouvée qui satisferait normalement la recherche et que cette bibliothèque n'a pas de balise DT_NEEDED pour libc.so et qu'il y a une bibliothèque partagée plus loin dans l'ensemble des répertoires de recherche qui satisfait également la recherche et que cette seconde bibliothèque a une balise DT_NEEDED pour libc.so, alors la seconde bibliothèque sera sélectionnée à la place de la première.

    Si la bibliothèque partagée requise n'est pas trouvée, l'éditeur de liens émettra un avertissement et continuera la liaison.

    -shared
    -Bshareable
    Crée une bibliothèque partagée. Ceci n'est actuellement pris en charge que sur les plateformes ELF, XCOFF et SunOS. Sur SunOS, l'éditeur de liens créera automatiquement une bibliothèque partagée si l'option -e n'est pas utilisée et qu'il y a des symboles indéfinis dans la liaison.
    --sort-common
    --sort-common=ascending
    --sort-common=descending
    Cette option indique à ld de trier les symboles communs par alignement dans l'ordre croissant ou décroissant lors de leur placement dans les sections de sortie appropriées. Les alignements de symboles considérés sont de seize octets ou plus, de huit octets, de quatre octets, de deux octets et d'un octet. Ceci afin d'éviter les écarts entre les symboles en raison des contraintes d'alignement. Si aucun ordre de tri n'est spécifié, l'ordre décroissant est supposé.
    --sort-section=name
    Cette option appliquera "SORT_BY_NAME" à tous les modèles de sections génériques dans le script de l'éditeur de liens.
    --sort-section=alignment
    Cette option appliquera "SORT_BY_ALIGNMENT" à tous les modèles de sections génériques dans le script de l'éditeur de liens.
    --spare-dynamic-tags=nombre
    Cette option spécifie le nombre d'emplacements vides à laisser dans la section .dynamic des objets partagés ELF. Des emplacements vides peuvent être nécessaires pour les outils de post-traitement, tels que le pré-éditeur de liens. La valeur par défaut est 5.
    --split-by-file[=taille]
    Similaire à --split-by-reloc mais crée une nouvelle section de sortie pour chaque fichier d'entrée lorsque la taille taille est atteinte. taille vaut par défaut 1 si elle n'est pas donnée.
    --split-by-reloc[=nombre]
    Tente de créer des sections supplémentaires dans le fichier de sortie de sorte qu'aucune section de sortie unique dans le fichier ne contienne plus de nombre relocations. Ceci est utile lors de la génération de fichiers très volumineux relocalisables pour le téléchargement dans certains noyaux temps réel avec le format de fichier objet COFF ; car COFF ne peut pas représenter plus de 65535 relocations dans une seule section. Notez que cela ne fonctionnera pas avec les formats de fichiers objets qui ne prennent pas en charge les sections arbitraires. L'éditeur de liens ne divisera pas les sections d'entrée individuelles pour la redistribution, donc si une seule section d'entrée contient plus de nombre relocations, une section de sortie contiendra ce nombre de relocations. nombre vaut par défaut 32768.
    --stats
    Calcule et affiche des statistiques sur le fonctionnement de l'éditeur de liens, telles que le temps d'exécution et l'utilisation de la mémoire.
    --sysroot=répertoire
    Utilise répertoire comme emplacement du sysroot, remplaçant la valeur par défaut configurée lors de la compilation. Cette option n'est prise en charge que par les éditeurs de liens configurés avec --with-sysroot.
    --task-link
    Ceci est utilisé par les cibles basées sur COFF/PE pour créer un fichier objet lié à une tâche où tous les symboles globaux ont été convertis en statiques.
    --traditional-format
    Pour certaines cibles, la sortie de ld diffère à certains égards de la sortie de certains éditeurs de liens existants. Ce commutateur demande à ld d'utiliser plutôt le format traditionnel.

    Par exemple, sur SunOS, ld combine les entrées dupliquées dans la table des chaînes de symboles. Cela peut réduire la taille d'un fichier de sortie avec des informations de débogage complètes de plus de 30 %. Malheureusement, le programme "dbx" de SunOS ne peut pas lire le programme résultant ("gdb" n'a aucun problème). Le commutateur --traditional-format indique à ld de ne pas combiner les entrées dupliquées.

    --section-start=nomsection=org
    Localise une section dans le fichier de sortie à l'adresse absolue donnée par org. Vous pouvez utiliser cette option autant de fois que nécessaire pour localiser plusieurs sections sur la ligne de commande. org doit être un entier hexadécimal unique ; pour la compatibilité avec d'autres éditeurs de liens, vous pouvez omettre le préfixe 0x généralement associé aux valeurs hexadécimales. Note : il ne doit y avoir aucun espace entre nomsection, le signe égal ("="), et org.
    -Tbss=org
    -Tdata=org
    -Ttext=org
    Identique à --section-start, avec ".bss", ".data" ou ".text" comme nomsection.
    -Ttext-segment=org
    Lors de la création d'un exécutable ELF, il définira l'adresse du premier octet du segment de texte.
    -Trodata-segment=org
    Lors de la création d'un exécutable ELF ou d'un objet partagé pour une cible où les données en lecture seule se trouvent dans leur propre segment, séparé du texte exécutable, il définira l'adresse du premier octet du segment de données en lecture seule.
    -Tldata-segment=org
    Lors de la création d'un exécutable ELF ou d'un objet partagé pour le modèle de mémoire moyenne x86-64, il définira l'adresse du premier octet du segment ldata.
    --unresolved-symbols=méthode
    Détermine comment gérer les symboles non résolus. Il existe quatre valeurs possibles pour méthode :
    ignore-all
    Ne pas signaler de symboles non résolus.
    report-all
    Signaler tous les symboles non résolus. C'est la valeur par défaut.
    ignore-in-object-files
    Signaler les symboles non résolus contenus dans les bibliothèques partagées, mais les ignorer s'ils proviennent de fichiers objets réguliers.
    ignore-in-shared-libs
    Signaler les symboles non résolus provenant de fichiers objets réguliers, mais les ignorer s'ils proviennent de bibliothèques partagées. Cela peut être utile lors de la création d'un binaire dynamique et lorsque l'on sait que toutes les bibliothèques partagées auxquelles il doit faire référence sont incluses sur la ligne de commande de l'éditeur de liens.

    Le comportement pour les bibliothèques partagées seules peut également être contrôlé par l'option --[no-]allow-shlib-undefined.

    Normalement, l'éditeur de liens générera un message d'erreur pour chaque symbole non résolu signalé, mais l'option --warn-unresolved-symbols peut transformer cela en un avertissement.

    --dll-verbose
    --verbose[=NOMBRE]
    Affiche le numéro de version de ld et liste les émulations d'éditeur de liens prises en charge. Affiche quels fichiers d'entrée peuvent être ouverts et lesquels ne le peuvent pas. Affiche le script de l'éditeur de liens utilisé par l'éditeur de liens. Si l'argument facultatif NOMBRE > 1, le statut des symboles des plugins sera également affiché.
    --version-script=fichier-script-version
    Spécifie le nom d'un script de version à l'éditeur de liens. Ceci est généralement utilisé lors de la création de bibliothèques partagées pour spécifier des informations supplémentaires sur la hiérarchie des versions de la bibliothèque en cours de création. Cette option n'est entièrement prise en charge que sur les plateformes ELF qui prennent en charge les bibliothèques partagées ; voir VERSION. Elle est partiellement prise en charge sur les plateformes PE, qui peuvent utiliser des scripts de version pour filtrer la visibilité des symboles en mode d'exportation automatique : tous les symboles marqués comme local dans le script de version ne seront pas exportés.
    --warn-common
    Avertit lorsqu'un symbole commun est combiné avec un autre symbole commun ou avec une définition de symbole. Les éditeurs de liens Unix autorisent cette pratique quelque peu laxiste, mais les éditeurs de liens sur certains autres systèmes d'exploitation ne le font pas. Cette option vous permet de détecter des problèmes potentiels liés à la combinaison de symboles globaux. Malheureusement, certaines bibliothèques C utilisent cette pratique, vous pourriez donc recevoir des avertissements concernant les symboles des bibliothèques ainsi que de vos programmes.

    Il existe trois types de symboles globaux, illustrés ici par des exemples en C :

    int i = 1;
    Une définition, qui va dans la section des données initialisées du fichier de sortie.
    extern int i;
    Une référence indéfinie, qui dne réserve pas d'espace. Il doit y avoir soit une définition, soit un symbole commun pour la variable quelque part.
    int i;
    Un symbole commun. S'il n'y a que (un ou plusieurs) symboles communs pour une variable, elle est placée dans la zone de données non initialisées du fichier de sortie. L'éditeur de liens fusionne plusieurs symboles communs pour la même variable en un seul symbole. S'ils sont de tailles différentes, il choisit la plus grande taille. L'éditeur de liens transforme un symbole commun en une déclaration si une définition de la même variable existe.

    L'option --warn-common peut produire cinq types d'avertissements. Chaque avertissement se compose d'une paire de lignes : la première décrit le symbole qui vient d'être rencontré, et la seconde décrit le symbole précédent rencontré avec le même nom. Un ou les deux symboles seront des symboles communs.

    1.
    Transformation d'un symbole commun en une référence, car il existe déjà une définition pour le symbole. 
    <fichier>(<section>): avertissement : commun de `<symbole>'
   écrasé par définition
<fichier>(<section>): avertissement : défini ici
    2.
    Transformation d'un symbole commun en une référence, car une définition ultérieure du symbole est rencontrée. C'est la même chose que le cas précédent, sauf que les symboles sont rencontrés dans un ordre différent. 
    <fichier>(<section>): avertissement : définition de `<symbole>'
   écrasant commun
<fichier>(<section>): avertissement : commun est ici
    3.
    Fusion d'un symbole commun avec un symbole commun précédent de même taille. 
    <fichier>(<section>): avertissement : plusieurs communs
   de `<symbole>'
<fichier>(<section>): avertissement : commun précédent est ici
    4.
    Fusion d'un symbole commun avec un symbole commun précédent plus grand. 
    <fichier>(<section>): avertissement : commun de `<symbole>'
   écrasé par un commun plus grand
<fichier>(<section>): avertissement : commun plus grand est ici
    5.
    Fusion d'un symbole commun avec un symbole commun précédent plus petit. C'est la même chose que le cas précédent, sauf que les symboles sont rencontrés dans un ordre différent. 
    <fichier>(<section>): avertissement : commun de `<symbole>'
   écrasant un commun plus petit
<fichier>(<section>): avertissement : commun plus petit est ici
    --warn-constructors
    Avertit si des constructeurs globaux sont utilisés. Ceci n'est utile que pour quelques formats de fichiers objets. Pour des formats comme COFF ou ELF, l'éditeur de liens ne peut pas détecter l'utilisation de constructeurs globaux.
    --warn-execstack
    --warn-execstack-objects
    --no-warn-execstack
    Sur les plateformes ELF, l'éditeur de liens peut générer des messages d'avertissement s'il lui est demandé de créer un fichier de sortie contenant une pile exécutable. Il y a trois états possibles :
    1.
    Ne génère aucun avertissement.
    2.
    Génère toujours des avertissements, même si la pile exécutable est demandée via l'option de ligne de commande -z execstack.
    3.
    Génère un avertissement uniquement si un fichier objet demande une pile exécutable, mais pas si l'option -z execstack est utilisée.

    L'état par défaut dépend de la manière dont l'éditeur de liens a été configuré lors de sa construction. L'option --no-warn-execstack place toujours l'éditeur de liens dans l'état sans avertissements. L'option --warn-execstack place l'éditeur de liens dans l'état d'avertissement permanent. L'option --warn-execstack-objects place l'éditeur de liens dans l'état d'avertissement uniquement pour les fichiers objets.

    Note : les fichiers d'entrée au format ELF peuvent spécifier qu'ils nécessitent une pile exécutable en ayant une section .note.GNU-stack avec le bit exécutable défini dans ses drapeaux de section. Ils peuvent spécifier qu'ils n'ont pas besoin d'une pile exécutable en ayant la même section, mais sans le bit exécutable défini. Si un fichier d'entrée n'a pas de section .note.GNU-stack, le comportement par défaut est spécifique à la cible. Pour certaines cibles, l'absence d'une telle section implique qu'une pile exécutable *est* requise. C'est souvent un problème pour les fichiers assembleur conçus à la main.

    --error-execstack
    --no-error-execstack
    Si l'éditeur de liens doit générer un message d'avertissement concernant une pile exécutable, l'option --error-execstack transformera cet avertissement en une erreur. Remarque : cette option ne modifie pas l'état de génération des avertissements d'execstack de l'éditeur de liens. Utilisez --warn-execstack ou --warn-execstack-objects pour définir un état d'avertissement spécifique.

    L'option --no-error-execstack rétablira le comportement par défaut de génération de messages d'avertissement.

    --warn-multiple-gp
    Avertit si plusieurs pointeurs globaux sont requis dans le fichier de sortie. Ceci n'est pertinent que pour certains processeurs, comme l'Alpha. Spécifiquement, certains processeurs placent les constantes de grande valeur dans une section spéciale. Un registre spécial (le pointeur global) pointe vers le milieu de cette section, de sorte que les constantes puissent être chargées efficacement via un mode d'adressage relatif à un registre de base. Comme le décalage en mode relatif à un registre de base est fixe et relativement petit (par exemple, 16 bits), cela limite la taille maximale du pool de constantes. Ainsi, dans les grands programmes, il est souvent nécessaire d'utiliser plusieurs pointeurs globaux afin de pouvoir adresser toutes les constantes possibles. Cette option provoque un avertissement lorsque ce cas se produit.
    --warn-once
    N'émet un avertissement qu'une seule fois pour chaque symbole non défini, plutôt qu'une fois par module qui y fait référence.
    --warn-rwx-segments
    --no-warn-rwx-segments
    Avertit si l'éditeur de liens crée un segment chargeable, de taille non nulle, qui a les trois indicateurs de permission lecture, écriture et exécution définis. Un tel segment représente une vulnérabilité de sécurité potentielle. De plus, des avertissements seront générés si un segment de stockage local de thread est créé avec l'indicateur de permission d'exécution défini, qu'il ait ou non les indicateurs de lecture et/ou d'écriture définis.

    Ces avertissements sont activés par défaut. Ils peuvent être désactivés via l'option --no-warn-rwx-segments et réactivés via l'option --warn-rwx-segments.

    --error-rwx-segments
    --no-error-rwx-segments
    Si l'éditeur de liens doit générer un message d'avertissement concernant un segment exécutable et inscriptible, ou un segment TLS exécutable, alors l'option --error-rwx-segments transformera cet avertissement en erreur. L'option --no-error-rwx-segments rétablira le comportement par défaut de génération d'un simple message d'avertissement.

    Remarque : l'option --error-rwx-segments n'active pas en soi les avertissements concernant ces segments. Ces avertissements sont soit activés par défaut, si l'éditeur de liens a été configuré ainsi, soit via l'option de ligne de commande --warn-rwx-segments.

    --warn-section-align
    Avertit si l'adresse d'une section de sortie est modifiée en raison de l'alignement. Typiquement, l'alignement sera défini par une section d'entrée. L'adresse ne sera modifiée que si elle n'est pas explicitement spécifiée ; c'est-à-dire si la commande "SECTIONS" ne spécifie pas d'adresse de départ pour la section.
    --warn-textrel
    Avertit si l'éditeur de liens ajoute DT_TEXTREL à un exécutable indépendant de la position ou à un objet partagé.
    --warn-alternate-em
    Avertit si un objet a un code machine ELF alternatif.
    --warn-unresolved-symbols
    Si l'éditeur de liens doit signaler un symbole non résolu (voir l'option --unresolved-symbols), il générera normalement une erreur. Cette option fait en sorte qu'il génère un avertissement à la place.
    --error-unresolved-symbols
    Rétablit le comportement par défaut de l'éditeur de liens qui consiste à générer des erreurs lors du signalement de symboles non résolus.
    --whole-archive
    Pour chaque archive mentionnée sur la ligne de commande après l'option --whole-archive, inclure chaque fichier objet de l'archive dans la liaison, plutôt que de rechercher dans l'archive les fichiers objets requis. Ceci est normalement utilisé pour transformer un fichier d'archive en une bibliothèque partagée, forçant l'inclusion de chaque objet dans la bibliothèque partagée résultante. Cette option peut être utilisée plusieurs fois.

    Deux notes lors de l'utilisation de cette option avec gcc : Premièrement, gcc ne connaît pas cette option, vous devez donc utiliser -Wl,-whole-archive. Deuxièmement, n'oubliez pas d'utiliser -Wl,-no-whole-archive après votre liste d'archives, car gcc ajoutera sa propre liste d'archives à votre liaison et vous ne voudrez peut-être pas que ce drapeau affecte également celles-ci.

    --wrap=symbole
    Utilise une fonction enveloppe pour symbole. Toute référence non définie à symbole sera résolue en "__wrap_symbole". Toute référence non définie à "__real_symbole" sera résolue en symbole.

    Ceci peut être utilisé pour fournir une enveloppe pour une fonction système. La fonction enveloppe doit être appelée "__wrap_symbole". Si elle souhaite appeler la fonction système, elle doit appeler "__real_symbole".

    Voici un exemple trivial :

    void *
__wrap_malloc (size_t c)
{
  printf ("malloc appelé avec %zu\n", c);
  return __real_malloc (c);
}

    Si vous liez d'autres codes avec ce fichier en utilisant --wrap malloc, alors tous les appels à "malloc" appelleront la fonction "__wrap_malloc" à la place. L'appel à "__real_malloc" dans "__wrap_malloc" appellera la fonction "malloc" réelle.

    Vous pouvez également souhaiter fournir une fonction "__real_malloc", afin que les liens sans l'option --wrap réussissent. Si vous faites cela, vous ne devez pas mettre la définition de "__real_malloc" dans le même fichier que "__wrap_malloc" ; si vous le faites, l'assembleur peut résoudre l'appel avant que l'éditeur de liens ait la possibilité de le lier à "malloc".

    Seules les références indéfinies sont remplacées par l'éditeur de liens. Ainsi, les références internes à l'unité de traduction à symbole ne sont pas résolues en "__wrap_symbole". Dans l'exemple suivant, l'appel à "f" dans "g" n'est pas résolu en "__wrap_f".

    int
f (void)
{
  return 123;
}

int
g (void)
{
  return f();
}
    --eh-frame-hdr
    --no-eh-frame-hdr
    Demande (--eh-frame-hdr) ou supprime (--no-eh-frame-hdr) la création de la section ".eh_frame_hdr" et du segment d'en-tête ELF "PT_GNU_EH_FRAME".
    --no-ld-generated-unwind-info
    Demande la création d'informations de déroulement ".eh_frame" pour les sections de code générées par l'éditeur de liens, telles que PLT. Cette option est activée par défaut si les informations de déroulement générées par l'éditeur de liens sont prises en charge. Cette option contrôle également la génération d'informations de trace de pile ".sframe" pour les sections de code générées par l'éditeur de liens, telles que PLT.
    --enable-new-dtags
    --disable-new-dtags
    Cet éditeur de liens peut créer les nouvelles balises dynamiques en ELF. Mais les anciens systèmes ELF pourraient ne pas les comprendre. Si vous spécifiez --enable-new-dtags, les nouvelles balises dynamiques seront créées au besoin et les anciennes balises dynamiques seront omises. Si vous spécifiez --disable-new-dtags, aucune nouvelle balise dynamique ne sera créée. Par défaut, les nouvelles balises dynamiques ne sont pas créées. Notez que ces options ne sont disponibles que pour les systèmes ELF.
    --hash-size=nombre
    Définit la taille par défaut des tables de hachage de l'éditeur de liens sur un nombre premier proche de nombre. Augmenter cette valeur peut réduire le temps nécessaire à l'éditeur de liens pour effectuer ses tâches, au détriment d'une augmentation des besoins en mémoire de l'éditeur de liens. De même, réduire cette valeur peut réduire les besoins en mémoire au détriment de la vitesse.
    --hash-style=style
    Définit le type des tables de hachage de l'éditeur de liens. style peut être "sysv" pour la section ELF classique ".hash", "gnu" pour la nouvelle section GNU ".gnu.hash" ou "both" pour les tables de hachage ELF classiques ".hash" et GNU ".gnu.hash". La valeur par défaut dépend de la configuration de l'éditeur de liens, mais pour la plupart des systèmes basés sur Linux, ce sera "both".
    --compress-debug-sections=none
    --compress-debug-sections=zlib
    --compress-debug-sections=zlib-gnu
    --compress-debug-sections=zlib-gabi
    --compress-debug-sections=zstd
    Sur les plateformes ELF, ces options contrôlent comment les sections de débogage DWARF sont compressées à l'aide de zlib.

    --compress-debug-sections=none ne compresse pas les sections de débogage DWARF. --compress-debug-sections=zlib-gnu compresse les sections de débogage DWARF et les renomme pour commencer par .zdebug au lieu de .debug. --compress-debug-sections=zlib-gabi compresse également les sections de débogage DWARF, mais au lieu de les renommer, il définit l'indicateur SHF_COMPRESSED dans les en-têtes des sections.

    L'option --compress-debug-sections=zlib est un alias pour --compress-debug-sections=zlib-gabi.

    --compress-debug-sections=zstd compresse les sections de débogage DWARF à l'aide de zstd.

    Notez que cette option remplace toute compression dans les sections de débogage d'entrée, donc si un binaire est lié avec --compress-debug-sections=none par exemple, toutes les sections de débogage compressées dans les fichiers d'entrée seront décompressées avant d'être copiées dans le binaire de sortie.

    Le comportement de compression par défaut varie en fonction de la cible impliquée et des options de configuration utilisées pour construire la chaîne d'outils. La valeur par défaut peut être déterminée en examinant la sortie de l'option --help de l'éditeur de liens.

    --reduce-memory-overheads
    Cette option réduit les exigences en mémoire au moment de l'exécution de ld, au détriment de la vitesse de liaison. Elle a été introduite pour sélectionner l'ancien algorithme O(n^2) pour la génération du fichier de carte de liens, plutôt que le nouvel algorithme O(n) qui utilise environ 40% de mémoire supplémentaire pour le stockage des symboles.

    Un autre effet de ce commutateur est de définir la taille de table de hachage par défaut sur 1021, ce qui économise de la mémoire au prix d'un temps d'exécution plus long de l'éditeur de liens. Cela n'est cependant pas fait si le commutateur --hash-size a été utilisé.

    Le commutateur --reduce-memory-overheads peut également être utilisé pour activer d'autres compromis dans les futures versions de l'éditeur de liens.

    --max-cache-size=taille
    ld met normalement en cache les informations de relocalisation et les tables de symboles des fichiers d'entrée en mémoire avec une taille illimitée. Cette option définit la taille maximale du cache à taille.
    --build-id
    --build-id=style
    Demande la création d'une section de note ELF ".note.gnu.build-id" ou d'une section COFF ".buildid". Le contenu de la note sont des bits uniques identifiant ce fichier lié. style peut être "uuid" pour utiliser 128 bits aléatoires, "sha1" pour utiliser un hachage SHA1 de 160 bits sur les parties normatives du contenu de sortie, "md5" pour utiliser un hachage MD5 de 128 bits sur les parties normatives du contenu de sortie, ou "0xchaîne_hex" pour utiliser une chaîne de bits choisie spécifiée sous forme de nombre pair de chiffres hexadécimaux (les caractères "-" et ":" entre les paires de chiffres sont ignorés). Si style est omis, "sha1" est utilisé.

    Les styles "md5" et "sha1" produisent un identifiant qui est toujours le même dans un fichier de sortie identique, mais qui sera unique parmi tous les fichiers de sortie non identiques. Il n'est pas destiné à être comparé comme une somme de contrôle du contenu du fichier. Un fichier lié peut être modifié ultérieurement par d'autres outils, mais la chaîne de bits d'identification de construction identifiant le fichier lié d'origine ne change pas.

    Passer "none" pour style désactive le paramètre de toutes les options "--build-id" précédentes sur la ligne de commande.

    --package-metadata=JSON
    Demande la création d'une section de note ELF ".note.package". Le contenu de la note est au format JSON, conformément à la spécification des métadonnées de paquet. Pour plus d'informations, voir : https://systemd.io/ELF_PACKAGE_METADATA/ Si l'argument JSON est manquant/vide, cela désactivera la création de la note de métadonnées, si elle avait été activée par une occurrence antérieure de l'option --package-metadata. Si l'éditeur de liens a été construit avec libjansson, la chaîne JSON sera validée.

    L'éditeur de liens PE i386 prend en charge l'option -shared, qui fait que la sortie est une bibliothèque liée dynamiquement (DLL) au lieu d'un exécutable normal. Vous devriez nommer la sortie "*.dll" lorsque vous utilisez cette option. De plus, l'éditeur de liens prend entièrement en charge les fichiers "*.def" standard, qui peuvent être spécifiés sur la ligne de commande de l'éditeur de liens comme un fichier objet (en fait, il doit précéder les archives dont il exporte les symboles, pour s'assurer qu'ils sont liés, tout comme un fichier objet normal).

    En plus des options communes à toutes les cibles, l'éditeur de liens PE i386 prend en charge des options de ligne de commande supplémentaires spécifiques à la cible PE i386. Les options qui prennent des valeurs peuvent être séparées de leurs valeurs par un espace ou un signe égal.

    --add-stdcall-alias
    Si présent, les symboles avec un suffixe stdcall (@nn) seront exportés tels quels et également avec le suffixe supprimé. [Cette option est spécifique au port ciblé i386 PE de l'éditeur de liens]
    --base-file fichier
    Utilisez fichier comme nom d'un fichier dans lequel enregistrer les adresses de base de toutes les relocalisations nécessaires pour générer des DLL avec dlltool. [Il s'agit d'une option spécifique à i386 PE]
    --dll
    Crée une DLL au lieu d'un exécutable normal. Vous pouvez également utiliser -shared ou spécifier une "LIBRARY" dans un fichier ".def" donné. [Cette option est spécifique au port ciblé i386 PE de l'éditeur de liens]
    --enable-long-section-names
    --disable-long-section-names
    Les variantes PE du format objet COFF ajoutent une extension qui permet l'utilisation de noms de section plus longs que huit caractères, la limite normale pour COFF. Par défaut, ces noms sont uniquement
    autorisé dans les fichiers objets, car les images exécutables entièrement liées ne transportent pas la table de chaînes COFF requise pour prendre en charge les noms plus longs. En tant qu'extension GNU, il est possible de les autoriser également dans les images exécutables, ou de les interdire (probablement inutilement !) dans les fichiers objets, en utilisant ces deux options. Les images exécutables générées avec ces noms de section longs sont légèrement non standard, transportant une table de chaînes, et peuvent générer une sortie confuse lorsqu'elles sont examinées avec des outils non-GNU connaissant le format PE, tels que les visualiseurs et les déchargeurs de fichiers. Cependant, GDB s'appuie sur l'utilisation des noms de section longs PE pour trouver les sections d'informations de débogage Dwarf-2 dans une image exécutable au moment de l'exécution, et donc si aucune des deux options n'est spécifiée sur la ligne de commande, ld activera les noms de section longs, outrepassant le comportement par défaut et techniquement correct, lorsqu'il détectera la présence d'informations de débogage lors de la liaison d'une image exécutable et sans dépouiller les symboles. [Cette option est valide pour tous les ports du linker ciblés sur PE]
    --enable-stdcall-fixup
    --disable-stdcall-fixup
    Si le linker trouve un symbole qu'il ne parvient pas à résoudre, il tentera une « liaison approximative » en recherchant un autre symbole défini qui ne diffère que par le format du nom du symbole (cdecl vs stdcall) et résoudra ce symbole en le liant à la correspondance. Par exemple, le symbole indéfini "_foo" pourrait être lié à la fonction "_foo@12", ou le symbole indéfini "_bar@16" pourrait être lié à la fonction "_bar". Lorsque le linker fait cela, il affiche un avertissement, car normalement il aurait dû échouer à lier, mais parfois les bibliothèques d'importation générées à partir de DLL tierces peuvent nécessiter cette fonctionnalité pour être utilisables. Si vous spécifiez --enable-stdcall-fixup, cette fonctionnalité est entièrement activée et les avertissements ne sont pas imprimés. Si vous spécifiez --disable-stdcall-fixup, cette fonctionnalité est désactivée et de telles incompatibilités sont considérées comme des erreurs. [Cette option est spécifique au port du linker ciblé sur i386 PE]
    --leading-underscore
    --no-leading-underscore
    Pour la plupart des cibles, le préfixe de symbole par défaut est un underscore et est défini dans la description de la cible. Avec cette option, il est possible de désactiver/activer le préfixe de symbole par défaut avec un underscore.
    --export-all-symbols
    Si spécifié, tous les symboles globaux des objets utilisés pour construire une DLL seront exportés par la DLL. Notez que c'est le comportement par défaut s'il n'y aurait autrement aucun symbole exporté. Lorsque des symboles sont explicitement exportés via des fichiers DEF ou implicitement exportés via des attributs de fonction, le défaut est de ne rien exporter d'autre, sauf si cette option est spécifiée. Notez que les symboles "DllMain@12", "DllEntryPoint@0", "DllMainCRTStartup@12" et "impure_ptr" ne seront pas exportés automatiquement. De plus, les symboles importés d'autres DLL ne seront pas réexportés, ni les symboles spécifiant la disposition interne de la DLL tels que ceux commençant par "_head_" ou se terminant par "_iname". En outre, aucun symbole de "libgcc", "libstd++", "libmingw32", ou "crtX.o" ne sera exporté. Les symboles dont les noms commencent par "__rtti_" ou "__builtin_" ne seront pas exportés, pour aider avec les DLL C++. Enfin, il existe une liste étendue de symboles privés à Cygwin qui ne sont pas exportés (évidemment, cela s'applique lors de la construction de DLL pour les cibles Cygwin). Ces exclusions Cygwin sont : "_cygwin_dll_entry@12", "_cygwin_crt0_common@8", "_cygwin_noncygwin_dll_entry@12", "_fmode", "_impure_ptr", "cygwin_attach_dll", "cygwin_premain0", "cygwin_premain1", "cygwin_premain2", "cygwin_premain3", et "environ". [Cette option est spécifique au port du linker ciblé sur i386 PE]
    --exclude-symbols symbole,symbole,...
    Spécifie une liste de symboles qui ne devraient pas être exportés automatiquement. Les noms de symboles peuvent être délimités par des virgules ou des deux-points. [Cette option est spécifique au port du linker ciblé sur i386 PE]
    --exclude-all-symbols
    Spécifie qu'aucun symbole ne doit être exporté automatiquement. [Cette option est spécifique au port du linker ciblé sur i386 PE]
    --file-alignment
    Spécifie l'alignement de fichier. Les sections dans le fichier commenceront toujours à des décalages de fichier qui sont des multiples de ce nombre. La valeur par défaut est 512. [Cette option est spécifique au port du linker ciblé sur i386 PE]
    --heap réserve
    --heap réserve,engagement
    Spécifie le nombre d'octets de mémoire à réserver (et éventuellement à engager) pour être utilisés comme tas pour ce programme. La valeur par défaut est 1 Mo réservé, 4 Ko engagés. [Cette option est spécifique au port du linker ciblé sur i386 PE]
    --image-base valeur
    Utilise valeur comme adresse de base de votre programme ou DLL. C'est le plus bas emplacement mémoire qui sera utilisé lorsque votre programme ou DLL sera chargé. Pour réduire le besoin de relocalisation et améliorer les performances de vos DLL, chacune devrait avoir une adresse de base unique et ne pas chevaucher d'autres DLL. La valeur par défaut est 0x400000 pour les exécutables, et 0x10000000 pour les DLL. [Cette option est spécifique au port du linker ciblé sur i386 PE]
    --kill-at
    Si spécifié, les suffixes stdcall (@nn) seront supprimés des symboles avant leur exportation. [Cette option est spécifique au port du linker ciblé sur i386 PE]
    --large-address-aware
    Si spécifié, le bit approprié dans le champ "Caractéristiques" de l'en-tête COFF est défini pour indiquer que cet exécutable prend en charge des adresses virtuelles supérieures à 2 gigaoctets. Ceci doit être utilisé conjointement avec le commutateur /3GB ou /USERVA=valeur mégaoctets dans la section "[operating systems]" du fichier BOOT.INI. Sinon, ce bit n'a aucun effet. [Cette option est spécifique aux ports du linker ciblés sur PE]
    --disable-large-address-aware
    Annule l'effet d'une option précédente --large-address-aware. Ceci est utile si --large-address-aware est toujours défini par le pilote du compilateur (par exemple, gcc de Cygwin) et que l'exécutable ne prend pas en charge les adresses virtuelles supérieures à 2 gigaoctets. [Cette option est spécifique aux ports du linker ciblés sur PE]
    --major-image-version valeur
    Définit le numéro de la partie majeure de la "version d'image". La valeur par défaut est 1. [Cette option est spécifique au port du linker ciblé sur i386 PE]
    --major-os-version valeur
    Définit le numéro de la partie majeure de la "version de l'OS". La valeur par défaut est 4. [Cette option est spécifique au port du linker ciblé sur i386 PE]
    --major-subsystem-version valeur
    Définit le numéro de la partie majeure de la "version du sous-système". La valeur par défaut est 4. [Cette option est spécifique au port du linker ciblé sur i386 PE]
    --minor-image-version valeur
    Définit le numéro de la partie mineure de la "version d'image". La valeur par défaut est 0. [Cette option est spécifique au port du linker ciblé sur i386 PE]
    --minor-os-version valeur
    Définit le numéro de la partie mineure de la "version de l'OS". La valeur par défaut est 0. [Cette option est spécifique au port du linker ciblé sur i386 PE]
    --minor-subsystem-version valeur
    Définit le numéro de la partie mineure de la "version du sous-système". La valeur par défaut est 0. [Cette option est spécifique au port du linker ciblé sur i386 PE]
    --output-def fichier
    Le linker créera le fichier fichier qui contiendra un fichier DEF correspondant à la DLL que le linker génère. Ce fichier DEF (qui devrait s'appeler "*.def") peut être utilisé pour créer une bibliothèque d'importation avec "dlltool" ou peut être utilisé comme référence pour les symboles exportés automatiquement ou implicitement. [Cette option est spécifique au port du linker ciblé sur i386 PE]
    --enable-auto-image-base
    --enable-auto-image-base=valeur
    Choisit automatiquement la base d'image pour les DLL, éventuellement en commençant par la base valeur, à moins qu'une ne soit spécifiée à l'aide de l'argument "--image-base". En utilisant un hachage généré à partir du nom de la DLL pour créer des bases d'image uniques pour chaque DLL, les collisions en mémoire et les relocalisations qui peuvent retarder l'exécution du programme sont évitées. [Cette option est spécifique au port du linker ciblé sur i386 PE]
    --disable-auto-image-base
    Ne génère pas automatiquement une base d'image unique. S'il n'y a pas de base d'image spécifiée par l'utilisateur ("--image-base"), utilise la valeur par défaut de la plateforme. [Cette option est spécifique au port du linker ciblé sur i386 PE]
    --dll-search-prefix chaîne
    Lors de la liaison dynamique à une DLL sans bibliothèque d'importation, recherche "<chaîne><basename>.dll" de préférence à "lib<basename>.dll". Tson comportement permet de distinguer facilement les DLL compilées pour les différents « sous-plateformes » : native, cygwin, uwin, pw, etc. Par exemple, les DLL Cygwin utilisent typiquement `"--dll-search-prefix=cyg". [Cette option est spécifique au port cible i386 PE de l'éditeur de liens]
    --enable-auto-import
    Effectue une liaison sophistiquée de `"_symbole"` à `"__imp__symbole"` pour les importations de données depuis les DLL, rendant ainsi possible de contourner le mécanisme dllimport du côté de l'utilisateur et de référencer des noms de symboles non obfusqués. [Cette option est spécifique au port cible i386 PE de l'éditeur de liens]

    Les remarques suivantes concernent l'implémentation originale de la fonctionnalité et sont obsolètes de nos jours pour les cibles Cygwin et MinGW.

    Note : L'utilisation de l'extension 'auto-import' rendra la section de texte du fichier image modifiable. Ceci n'est pas conforme à la spécification du format PE-COFF publiée par Microsoft.

    Note - l'utilisation de l'extension 'auto-import' entraînera également le placement des données en lecture seule, qui seraient normalement placées dans la section .rdata, dans la section .data à la place. Ceci afin de contourner un problème avec les constantes qui est décrit ici : http://www.cygwin.com/ml/cygwin/2004-09/msg01101.html

    L'utilisation de 'auto-import' fonctionnera généralement bien — mais parfois, vous pourriez voir ce message :

    "la variable '<var>' ne peut pas être auto-importée. Veuillez lire la documentation de ld pour "--enable-auto-import" pour plus de détails."

    Ce message survient lorsque certaines (sous)expressions accèdent à une adresse résultant de la somme de deux constantes (les tables d'importation Win32 n'en autorisent qu'une). Les cas où cela peut se produire incluent les accès aux champs membres de variables struct importées depuis une DLL, ainsi que l'utilisation d'un index constant dans un tableau importé depuis une DLL. Toute variable multi-mots (tableaux, structures, long long, etc.) peut déclencher cette condition d'erreur. Cependant, quel que soit le type de données exact de la variable exportée fautive, ld la détectera toujours, émettra l'avertissement et s'arrêtera.

    Il existe plusieurs façons de résoudre cette difficulté, quel que soit le type de données de la variable exportée :

    Une façon est d'utiliser le commutateur --enable-runtime-pseudo-reloc. Cela laisse la tâche d'ajuster les références dans votre code client pour l'environnement d'exécution, donc cette méthode ne fonctionne que lorsque l'environnement d'exécution prend en charge cette fonctionnalité.

    Une deuxième solution consiste à forcer l'une des 'constantes' à être une variable — c'est-à-dire, inconnue et non optimisable au moment de la compilation. Pour les tableaux, il y a deux possibilités : a) faire de l'indexé (l'adresse du tableau) une variable, ou b) faire de l'index 'constant' une variable. Ainsi :

    extern type extern_array[];
extern_array[1] -->
   { volatile type *t=extern_array; t[1] }

    ou

    extern type extern_array[];
extern_array[1] -->
   { volatile int t=1; extern_array[t] }

    Pour les structures (et la plupart des autres types de données multi-mots), la seule option est de faire de la structure elle-même (ou du long long, ou du ...) une variable :

    extern struct s extern_struct;
extern_struct.field -->
   { volatile struct s *t=&extern_struct; t->field }

    ou

    extern long long extern_ll;
extern_ll -->
  { volatile long long * local_ll=&extern_ll; *local_ll }

    Une troisième méthode pour traiter cette difficulté est d'abandonner 'auto-import' pour le symbole fautif et de le marquer avec "__declspec(dllimport)". Cependant, en pratique, cela nécessite d'utiliser des #defines au moment de la compilation pour indiquer si vous compilez une DLL, compilez du code client qui se liera à la DLL, ou simplement compilez/liez une bibliothèque statique. En faisant le choix entre les différentes méthodes de résolution du problème 'adresse directe avec décalage constant', vous devriez considérer l'usage typique en monde réel :

    Original :

    --foo.h
extern int arr[];
--foo.c
#include "foo.h"
void main(int argc, char **argv){
  printf("%d\n",arr[1]);
}

    Solution 1 :

    --foo.h
extern int arr[];
--foo.c
#include "foo.h"
void main(int argc, char **argv){
  /* Ce contournement est pour win32 et cygwin; ne pas "optimiser" */
  volatile int *parr = arr;
  printf("%d\n",parr[1]);
}

    Solution 2 :

    --foo.h
/* Note : auto-export est supposé (pas de __declspec(dllexport)) */
#if (defined(_WIN32) || defined(__CYGWIN__)) && \
  !(defined(FOO_BUILD_DLL) || defined(FOO_STATIC))
#define FOO_IMPORT __declspec(dllimport)
#else
#define FOO_IMPORT
#endif
extern FOO_IMPORT int arr[];
--foo.c
#include "foo.h"
void main(int argc, char **argv){
  printf("%d\n",arr[1]);
}

    Une quatrième façon d'éviter ce problème est de recoder votre bibliothèque pour utiliser une interface fonctionnelle plutôt qu'une interface de données pour les variables fautives (par exemple, des fonctions d'accès set_foo() et get_foo()).

    --disable-auto-import
    N'essaie pas d'effectuer une liaison sophistiquée de `"_symbole"` à `"__imp__symbole"` pour les importations de données depuis les DLL. [Cette option est spécifique au port cible i386 PE de l'éditeur de liens]
    --enable-runtime-pseudo-reloc

[Cette option est spécifique au port cible i386 PE de l'éditeur de liens]
    --disable-runtime-pseudo-reloc
    Ne crée pas de relocations pseudo pour les importations de données avec décalage non nul depuis les DLL. [Cette option est spécifique au port cible i386 PE de l'éditeur de liens]
    --enable-extra-pe-debug
    Affiche des informations de débogage supplémentaires relatives au thunking des symboles auto-importés. [Cette option est spécifique au port cible i386 PE de l'éditeur de liens]
    --section-alignment
    Définit l'alignement des sections. Les sections en mémoire commenceront toujours à des adresses qui sont un multiple de ce nombre. La valeur par défaut est 0x1000. [Cette option est spécifique au port cible i386 PE de l'éditeur de liens]
    --stack reserve
    --stack reserve,commit
    Spécifie le nombre d'octets de mémoire à réserver (et éventuellement à allouer) pour être utilisé comme pile pour ce programme. La valeur par défaut est 2 Mo réservés, 4 Ko alloués. [Cette option est spécifique au port cible i386 PE de l'éditeur de liens]

    --subsystem quel:majeur
    --subsystem quel:majeur.mineur

Vous pouvez éventuellement définir également la version du sous-système. Des valeurs numériques sont également acceptées pour quel. [Cette option est spécifique au port cible i386 PE de l'éditeur de liens]

Cette fonctionnalité a été introduite avec MS Windows Vista pour les cibles PE i386. Cette option est activée par défaut mais peut être désactivée via l'option --disable-dynamicbase. Cette option implique également --enable-reloc-section.
    --forceinteg
    --disable-forceinteg
    Les vérifications d'intégrité du code sont appliquées. Cette option est désactivée par défaut.
    --nxcompat
    --disable-nxcompat
    L'image est compatible avec la protection contre l'exécution des données (DEP). Cette fonctionnalité a été introduite avec MS Windows XP SP2 pour les cibles PE i386. L'option est activée par défaut.
    --no-isolation
    --disable-no-isolation
    Bien que l'image comprenne l'isolation, n'isole pas l'image. Cette option est désactivée par défaut.
    --no-seh
    --disable-no-seh
    L'image n'utilise pas SEH. Aucun gestionnaire SE ne peut être appelé depuis cette image. Cette option est désactivée par défaut.
    --no-bind
    --disable-no-bind
    Ne lie pas cette image. Cette option est désactivée par défaut.

    Le pilote utilise le modèle de pilote MS Windows. Cette option est
    désactivé par défaut.
    --tsaware
    --disable-tsaware
    L'image est compatible avec le serveur Terminal. Cette option est désactivée par défaut.
    --insert-timestamp
    --no-insert-timestamp
    Insérer un horodatage réel dans l'image. C'est le comportement par défaut car il correspond au code hérité et signifie que l'image fonctionnera avec d'autres outils propriétaires. Le problème avec ce défaut est qu'il produira des images légèrement différentes à chaque fois que les mêmes sources seront liées. L'option --no-insert-timestamp peut être utilisée pour insérer une valeur zéro pour l'horodatage, garantissant ainsi que les binaires produits à partir de sources identiques seront identiques lors de la comparaison.

    Si --insert-timestamp est actif, l'heure insérée est soit l'heure à laquelle la liaison a lieu, soit, si la variable d'environnement "SOURCE_DATE_EPOCH" est définie, le nombre de secondes depuis l'époque Unix tel que spécifié par cette variable.

    --enable-reloc-section
    --disable-reloc-section
    Créer la table de relocalisation de base, nécessaire si l'image est chargée à une adresse de base différente de celle spécifiée dans l'en-tête PE. Cette option est activée par défaut.

    La cible C6X uClinux utilise un format binaire appelé DSBT pour prendre en charge les bibliothèques partagées. Chaque bibliothèque partagée dans le système doit avoir un index unique ; tous les exécutables utilisent l'index 0.

    --dsbt-size taille
    Cette option définit le nombre d'entrées dans la DSBT de l'exécutable ou de la bibliothèque partagée actuelle à taille. La valeur par défaut est de créer une table avec 64 entrées.
    --dsbt-index index
    Cette option définit l'index DSBT de l'exécutable ou de la bibliothèque partagée actuelle à index. La valeur par défaut est 0, ce qui est approprié pour la génération d'exécutables. Si une bibliothèque partagée est générée avec un index DSBT de 0, les relocations "R_C6000_DSBT_INDEX" sont copiées dans le fichier de sortie.

    L'option --no-merge-exidx-entries désactive la fusion des entrées exidx adjacentes dans les informations de déroulement de pile.

    --branch-stub
    Cette option active la relaxation des branches du lieur en insérant des sections de "branch stub" lorsque nécessaire pour étendre la portée des branches. Cette option n'est généralement pas requise car C-SKY prend en charge les instructions de branchement et d'appel qui peuvent accéder à toute la plage mémoire et la relaxation des branches est normalement gérée par le compilateur ou l'assembleur.
    --stub-group-size=N
    Cette option permet un contrôle plus fin de la création des "stub" de branchement du lieur. Elle définit la taille maximale d'un groupe de sections d'entrée qui peut être géré par une seule section "stub". Une valeur négative de N place les sections "stub" après leurs branches, tandis qu'une valeur positive permet aux sections "stub" d'apparaître avant ou après les branches. Les valeurs 1 ou -1 indiquent que le lieur doit choisir des valeurs par défaut appropriées.

    Les lieurs 68HC11 et 68HC12 prennent en charge des options spécifiques pour contrôler le mappage de commutation de banque mémoire et la génération de code de trampoline.

    --no-trampoline
    Cette option désactive la génération de trampoline. Par défaut, un trampoline est généré pour chaque fonction lointaine qui est appelée à l'aide d'une instruction "jsr" (cela se produit lorsqu'un pointeur vers une fonction lointaine est pris).
    --bank-window nom
    Cette option indique au lieur le nom de la région mémoire dans la spécification MEMORY qui décrit la fenêtre de banque mémoire. La définition d'une telle région est ensuite utilisée par le lieur pour calculer la pagination et les adresses dans la fenêtre mémoire.

    Les options suivantes sont prises en charge pour contrôler la gestion de la génération du GOT lors de la liaison pour les cibles 68K.

    --got=type
    Cette option indique au lieur quel schéma de génération de GOT utiliser. type doit être l'un des suivants : single, negative, multigot ou target. Pour plus d'informations, consultez l'entrée Info de ld.

    Les options suivantes sont prises en charge pour contrôler la génération d'instructions microMIPS et les vérifications de relocalisation de branchement pour les transitions de mode ISA lors de la liaison pour les cibles MIPS.

    --insn32
    --no-insn32
    Ces options contrôlent le choix des instructions microMIPS utilisées dans le code généré par le lieur, comme dans le PLT ou les stub de liaison paresseuse, ou dans la relaxation. Si --insn32 est utilisé, le lieur utilise uniquement des encodages d'instructions de 32 bits. Par défaut ou si --no-insn32 est utilisé, tous les encodages d'instructions sont utilisés, y compris ceux de 16 bits si possible.
    --ignore-branch-isa
    --no-ignore-branch-isa
    Ces options contrôlent les vérifications de relocalisation de branchement pour les transitions de mode ISA invalides. Si --ignore-branch-isa est utilisé, le lieur accepte toutes les relocalisations de branchement et toute transition de mode ISA requise est perdue dans le calcul de relocalisation, à l'exception de certains cas d'instructions "BAL" qui satisfont aux conditions de relaxation et sont converties en instructions "JALX" équivalentes lorsque la relocalisation associée est calculée. Par défaut ou si --no-ignore-branch-isa est utilisé, une vérification est effectuée, entraînant la perte d'une transition de mode ISA et produisant une erreur.
    --compact-branches
    --no-compact-branches
    Ces options contrôlent la génération d'instructions compactes par le lieur dans les entrées PLT pour MIPS R6.

    Pour la cible pdp11-aout, trois variantes du format de sortie peuvent être produites comme sélectionnées par les options suivantes. La variante par défaut pour pdp11-aout est l'option --omagic, tandis que pour les autres cibles, --nmagic est la valeur par défaut. L'option --imagic est définie uniquement pour la cible pdp11-aout, tandis que les autres sont décrites ici telles qu'elles s'appliquent à la cible pdp11-aout.

    -N
    --omagic
    Marquer la sortie comme "OMAGIC" (0407) dans l'en-tête a.out pour indiquer que le segment de texte ne doit pas être protégé en écriture et partagé. Étant donné que les segments de texte et de données sont à la fois lisibles et modifiables, le segment de données est alloué immédiatement après le segment de texte. C'est l'ancien format pour les programmes exécutables PDP11 et c'est la valeur par défaut pour ld sur les systèmes Unix PDP11 depuis le début jusqu'à 2.11BSD.
    -n
    --nmagic
    Marquer la sortie comme "NMAGIC" (0410) dans l'en-tête a.out pour indiquer que lorsque le fichier de sortie est exécuté, la partie texte sera en lecture seule et partageable entre tous les processus exécutant le même fichier. Cela implique de déplacer les zones de données jusqu'à la première frontière de page de 8 Ko possible suivant la fin du texte. Cette option crée un format d'exécutable pur.
    -z
    --imagic
    Marquer la sortie comme "IMAGIC" (0411) dans l'en-tête a.out pour indiquer que lorsque le fichier de sortie est exécuté, les zones de texte et de données du programme seront chargées dans des espaces d'adressage séparés en utilisant la fonction d'instruction et d'espace de données séparés de l'unité de gestion de mémoire dans les modèles plus grands du PDP11. Cela double l'espace d'adressage disponible pour le programme. Le segment de texte est à nouveau pur, protégé en écriture et partageable. La seule différence dans le format de sortie entre cette option et les autres, outre le nombre magique, est que les segments de texte et de données commencent tous deux à l'emplacement 0. L'option -z sélectionnait ce format dans 2.11BSD. Cette option crée un format d'exécutable séparé.
    --no-omagic
    Équivalent à --nmagic pour pdp11-aout.

    ENVIRONNEMENT

    Vous pouvez modifier le comportement de ld avec les variables d'environnement "GNUTARGET", "LDEMULATION" et "COLLECT_NO_DEMANGLE".

    "GNUTARGET" détermine le format de l'objet du fichier d'entrée si vous n'utilisez pas -b (ou son synonyme --format). Sa valeur doit être l'un des noms BFD pour un format d'entrée. S'il n'y a pas de "GNUTARGET" dans l'environnement, ld utilise le format naturel de la cible. Si "GNUTARGET" est défini sur "default", alors BFD tente de découvrir le format d'entrée en examinant les fichiers d'entrée binaires ; cette méthode réussit souvent, mais il existe des ambiguïtés potentielles, car il n'existe aucun moyen de garantir que le nombre magique utilisé pour spécifier les formats de fichiers objets est unique. Cependant, la procédure de configuration de BFD sur chaque système place le format conventionnel pour ce système en premier dans la liste de recherche, de sorte que les ambiguïtés sont résolues en faveur de la convention.

    "LDEMULATION" détermine l'émulation par défaut si vous n'utilisez pas l'option -m. L'émulation peut affecter divers aspects du comportement du lieur, en particulier le script de lieur par défaut. Vous pouvez lister les émulations disponibles avec les options --verbose ou -V. Si l'option -m n'est pas utilisée et que la variable d'environnement "LDEMULATION" n'est pas définie, l'émulation par défaut dépend de la manière dont le lieur a été configuré.

    Normalement, le lieur démêlera les symboles par défaut. Cependant, si "COLLECT_NO_DEMAN

    E" est défini dans l'environnement, alors il sera par défaut de ne pas démangler les symboles. Cette variable d'environnement est utilisée de manière similaire par le programme wrapper de l'éditeur de liens "gcc". La valeur par défaut peut être ignorée par les options --demangle et --no-demangle.
