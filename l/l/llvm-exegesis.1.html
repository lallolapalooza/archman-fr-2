NOM

llvm-exegesis - Banc d'essai d'instructions machine LLVM

SYNOPSIS

llvm-exegesis [options]

DESCRIPTION

llvm-exegesis est un outil de banc d'essai qui utilise les informations disponibles dans LLVM pour mesurer les caractéristiques des instructions de la machine hôte telles que la latence, le débit ou la décomposition des micro-opérations (uops).

Étant donné un nom d'opcode LLVM et un mode de banc d'essai, llvm-exegesis génère un extrait de code qui rend l'exécution aussi sérielle (resp. aussi parallèle) que possible afin que nous puissions mesurer la latence (resp. le débit inverse/la décomposition des uops) de l'instruction. L'extrait de code est compilé à la volée (jitted) et, sauf demande contraire, exécuté sur le sous-objet cible de l'hôte. Le temps pris (resp. l'utilisation des ressources) est mesuré à l'aide de compteurs de performance matériels. Le résultat est imprimé en YAML sur la sortie standard.

L'objectif principal de cet outil est de valider (ou invalider) automatiquement les modèles de planification TableDef de LLVM. À cette fin, nous fournissons également une analyse des résultats.

llvm-exegesis peut également effectuer des bancs d'essai sur des extraits de code arbitraires fournis par l'utilisateur.

PLATEFORMES SUPPORTÉES

llvm-exegesis prend actuellement en charge uniquement X86 (64 bits uniquement), ARM (AArch64 uniquement, génération d'extraits limitée), MIPS, PowerPC (PowerPC64LE uniquement) et RISC-V (RV64I/E et RV32I/E) sous Linux pour les bancs d'essai. Toutes les fonctionnalités de banc d'essai ne sont pas garanties de fonctionner sur toutes les plateformes. llvm-exegesis dispose également d'un mode d'analyse séparé pris en charge sur toutes les plateformes sur lesquelles LLVM est disponible.

Pour activer les bancs d'essai dans llvm-exegesis, LLVM doit être configuré et compilé avec LLVM_ENABLE_LIBPFM activé, car llvm-exegesis dépend de libpfm4 pour accéder aux compteurs de performance. Les bancs d'essai peuvent échouer si le CPU cible n'est pas pris en charge par libpfm. Cela peut être vérifié en définissant les variables d'environnement LIBPFM_VERBOSE et LIBPFM_DEBUG pour activer le mode verbeux ou de débogage pour libpfm. Si libpfm est installé dans un répertoire non standard, LLVM peut être configuré pour localiser la bibliothèque et les fichiers d'en-tête nécessaires en définissant les variables d'environnement LIBRARY_PATH, C_INCLUDE_PATH et CPLUS_INCLUDE_PATH. De plus, LD_LIBRARY_PATH doit être défini afin que llvm-exegesis puisse localiser la bibliothèque libpfm lors de l'exécution.

ANNOTATIONS DES EXTRAITS

llvm-exegesis prend en charge les bancs d'essai d'extraits d'assemblage arbitraires. Cependant, les bancs d'essai de ces extraits nécessitent souvent une configuration pour qu'ils puissent s'exécuter correctement. llvm-exegesis dispose de cinq annotations et de quelques utilitaires supplémentaires pour aider à la configuration afin que les extraits puissent être testés correctement.

  • LLVM-EXEGESIS-DEFREG <nom de registre> - L'ajout de cette annotation à l'extrait d'assemblage texte à tester marque le registre comme nécessitant une définition. Une valeur sera automatiquement fournie, sauf si un deuxième paramètre, une valeur hexadécimale, est passé. Ceci est fait avec le format LLVM-EXEGESIS-DEFREG <nom de registre> <valeur hexadécimale>. <valeur hexadécimale> est un schéma de bits utilisé pour remplir le registre. S'il s'agit d'une valeur inférieure à celle du registre, elle est étendue en signe pour correspondre à la taille du registre.
  • LLVM-EXEGESIS-LIVEIN <nom de registre> - Cette annotation permet de spécifier les registres qui doivent conserver leur valeur au démarrage du banc d'essai. Des valeurs peuvent être passées via des registres depuis la configuration du banc d'essai dans certains cas. Les registres et les valeurs qui leur sont assignées et qui peuvent être utilisés dans le script de banc d'essai avec un LLVM-EXEGESIS-LIVEIN sont les suivants :
•
Registre de mémoire temporaire - Le registre spécifique dans lequel cette valeur est placée dépend de la plateforme (par exemple, c'est le registre RDI sous X86 Linux). Définir ce registre comme live-in garantit qu'un pointeur vers un bloc de mémoire (1 Mo) est placé dans ce registre et peut être utilisé par l'extrait.
  • LLVM-EXEGESIS-MEM-DEF <nom de valeur> <taille> <valeur> - Cette annotation permet de spécifier des définitions de mémoire qui peuvent ensuite être mappées dans le processus d'exécution d'un extrait avec l'annotation LLVM-EXEGESIS-MEM-MAP. Chaque valeur est nommée en utilisant l'argument <nom de valeur> afin qu'elle puisse être référencée plus tard dans une annotation de mappage. La taille est spécifiée en nombre décimal d'octets et la valeur est donnée en hexadécimal. Si la taille de la valeur est inférieure à la taille spécifiée, la valeur sera répétée jusqu'à ce qu'elle remplisse toute la section de mémoire. L'utilisation de cette annotation nécessite le mode d'exécution par sous-processus.
  • LLVM-EXEGESIS-MEM-MAP <nom de valeur> <adresse> - Cette annotation permet de mapper des définitions de mémoire précédemment définies dans le contexte d'exécution d'un processus. Le nom de la valeur fait référence à une définition de mémoire précédemment définie et l'adresse est un nombre décimal spécifiant l'adresse à laquelle la définition de mémoire doit commencer. Notez qu'une seule définition de mémoire peut être mappée plusieurs fois. L'utilisation de cette annotation nécessite le mode d'exécution par sous-processus.
  • LLVM-EXEGESIS-SNIPPET-ADDRESS <adresse> - Cette annotation permet de définir l'adresse où le début de l'extrait à exécuter sera mappé. L'adresse est donnée en hexadécimal. Notez que l'extrait inclut également du code de configuration, de sorte que l'instruction exacte à l'adresse spécifiée ne sera pas la première instruction de l'extrait. L'utilisation de cette annotation nécessite le mode d'exécution par sous-processus. Ceci est utile dans les cas où la mémoire accédée par l'extrait dépend de l'emplacement de l'extrait, comme l'adressage relatif à RIP.
  • LLVM-EXEGESIS-LOOP-REGISTER <nom de registre> - Cette annotation spécifie le registre de boucle à utiliser pour suivre l'itération actuelle lors de l'utilisation du mode de répétition de boucle. llvm-exegesis doit suivre l'itération de boucle actuelle dans le mode de répétition de boucle de manière performante (c'est-à-dire sans accès mémoire), et utilise un registre pour ce faire. Ce registre a une valeur par défaut spécifique à l'architecture (par exemple, R8 sur X86), mais cela pourrait entrer en conflit avec certains extraits. Cette annotation permet de changer le registre pour éviter les interférences entre le registre d'index de boucle et l'extrait.

EXEMPLE 1: TESTER DES INSTRUCTIONS

Supposons que vous ayez une machine X86-64. Pour mesurer la latence d'une seule instruction, exécutez :

$ llvm-exegesis --mode=latency --opcode-name=ADD64rr

Mesurer la décomposition des uops ou le débit inverse d'une instruction fonctionne de manière similaire :

$ llvm-exegesis --mode=uops --opcode-name=ADD64rr
$ llvm-exegesis --mode=inverse_throughput --opcode-name=ADD64rr

La sortie est un document YAML (par défaut, il écrit sur stdout, mais vous pouvez rediriger la sortie vers un fichier en utilisant --benchmarks-file) :

---
key:
  opcode_name:     ADD64rr
  mode:            latency
  config:          ''
cpu_name:        haswell
llvm_triple:     x86_64-unknown-linux-gnu
num_repetitions: 10000
measurements:
  - { key: latency, value: 1.0058, debug_string: '' }
error:           ''
info:            'explicit self cycles, selecting one aliasing configuration.
Snippet:
ADD64rr R8, R8, R10
'
...

Pour mesurer la latence de toutes les instructions pour l'architecture hôte, exécutez :

$ llvm-exegesis --mode=latency --opcode-index=-1

EXEMPLE 2: TESTER UN EXTRAIT DE CODE PERSONNALISÉ

Pour mesurer la latence/les uops d'un morceau de code personnalisé, vous pouvez spécifier l'option snippets-file (- lit depuis l'entrée standard).

$ echo "vzeroupper" | llvm-exegesis --mode=uops --snippets-file=-

Les extraits de code réels dépendent généralement des registres ou de la mémoire. llvm-exegesis vérifie la vivacité des registres (c'est-à-dire que toute utilisation de registre a une définition correspondante ou est un "live in"). Si votre code dépend de la valeur de certains registres, vous devez utiliser les annotations d'extrait pour garantir que la configuration est correctement effectuée.

">Par exemple, l'extrait de code suivant dépend des valeurs de XMM1 (qui sera défini par l'outil) et du tampon mémoire passé dans RDI (en direct).

# LLVM-EXEGESIS-LIVEIN RDI
# LLVM-EXEGESIS-DEFREG XMM1 42
vmulps        (%rdi), %xmm1, %xmm2
vhaddps       %xmm2, %xmm2, %xmm3
addq $0x10, %rdi

EXEMPLE 3: MESURE AVEC ANNOTATIONS MÉMOIRE

Certains extraits nécessitent une configuration mémoire à des endroits spécifiques pour s'exécuter sans planter. La configuration de la mémoire peut être accomplie avec les annotations LLVM-EXEGESIS-MEM-DEF et LLVM-EXEGESIS-MEM-MAP. Pour exécuter l'extrait suivant :

movq $8192, %rax
movq (%rax), %rdi

Nous devons avoir au moins huit octets de mémoire alloués à partir de 0x2000. Nous pouvons créer l'environnement d'exécution nécessaire avec les annotations suivantes ajoutées à l'extrait :

# LLVM-EXEGESIS-MEM-DEF test1 4096 7fffffff
# LLVM-EXEGESIS-MEM-MAP test1 8192
movq $8192, %rax
movq (%rax), %rdi

EXEMPLE 4: ANALYSE

En supposant que vous ayez un ensemble d'instructions mesurées (en latence ou en uops) au format YAML dans le fichier /tmp/benchmarks.yaml, vous pouvez analyser les résultats en utilisant la commande suivante :

  $ llvm-exegesis --mode=analysis \
--benchmarks-file=/tmp/benchmarks.yaml \
--analysis-clusters-output-file=/tmp/clusters.csv \
--analysis-inconsistencies-output-file=/tmp/inconsistencies.html

Cela regroupera les instructions en clusters ayant les mêmes caractéristiques de performance. Les clusters seront écrits dans /tmp/clusters.csv dans le format suivant :

cluster_id,opcode_name,config,sched_class
...
2,ADD32ri8_DB,,WriteALU,1.00
2,ADD32ri_DB,,WriteALU,1.01
2,ADD32rr,,WriteALU,1.01
2,ADD32rr_DB,,WriteALU,1.00
2,ADD32rr_REV,,WriteALU,1.00
2,ADD64i32,,WriteALU,1.01
2,ADD64ri32,,WriteALU,1.01
2,MOVSX64rr32,,BSWAP32r_BSWAP64r_MOVSX64rr32,1.00
2,VPADDQYrr,,VPADDBYrr_VPADDDYrr_VPADDQYrr_VPADDWYrr_VPSUBBYrr_VPSUBDYrr_VPSUBQYrr_VPSUBWYrr,1.02
2,VPSUBQYrr,,VPADDBYrr_VPADDDYrr_VPADDQYrr_VPADDWYrr_VPSUBBYrr_VPSUBDYrr_VPSUBQYrr_VPSUBWYrr,1.01
2,ADD64ri8,,WriteALU,1.00
2,SETBr,,WriteSETCC,1.01
...

llvm-exegesis analysera également les clusters pour signaler les incohérences dans les informations de planification. La sortie est un fichier HTML. Par exemple, /tmp/inconsistencies.html contiendra des messages tels que les suivants : [image]

OPTIONS

--help
Imprimer un résumé des options de ligne de commande.
--opcode-index=<indice d'opcode LLVM>
Spécifier l'opcode à mesurer, par indice. Spécifier -1 entraînera la mesure de chaque opcode existant. Voir l'exemple 1 pour les détails. opcode-index, opcode-name ou snippets-file doivent être définis.
--opcode-name=<nom d'opcode 1>,<nom d'opcode 2>,...
Spécifier l'opcode à mesurer, par nom. Plusieurs opcodes peuvent être spécifiés sous forme de liste séparée par des virgules. Voir l'exemple 1 pour les détails. opcode-index, opcode-name ou snippets-file doivent être définis.
--snippets-file=<nom de fichier>
Spécifier l'extrait de code personnalisé à mesurer. Voir l'exemple 2 pour les détails. opcode-index, opcode-name ou snippets-file doivent être définis.
--mode=[latency|uops|inverse_throughput|analysis]
Spécifier le mode d'exécution. Notez que certains modes ont des exigences et des options supplémentaires.

Le mode latency peut utiliser soit RDTSC, soit LBR. latency[LBR] n'est disponible que sur X86 (au moins depuis Skylake). Pour exécuter en mode latency, une valeur positive doit être spécifiée pour x86-lbr-sample-period et --repetition-mode=loop.

En mode analysis, vous devez également spécifier au moins l'une des options -analysis-clusters-output-file= et -analysis-inconsistencies-output-file=.

--benchmark-phase=[prepare-snippet|prepare-and-assemble-snippet|assemble-measured-code|measure]
Par défaut, lorsque -mode= est spécifié, l'extrait généré sera exécuté et mesuré, ce qui nécessite que nous soyons sur le matériel pour lequel l'extrait a été généré, et qui prend en charge les mesures de performance. Cependant, il est possible de s'arrêter à une certaine étape avant la mesure. Les choix sont : * prepare-snippet: Générer uniquement la séquence d'instructions minimale. * prepare-and-assemble-snippet: Identique à prepare-snippet, mais affiche également un extrait de la séquence (encodé en hexadécimal). * assemble-measured-code: Identique à prepare-and-assemble-snippet, mais crée également la séquence complète qui peut être exportée dans un fichier en utilisant --dump-object-to-disk. * measure: Identique à assemble-measured-code, mais exécute également la mesure.
--x86-lbr-sample-period=<nBranches/sample>
Spécifier la période d'échantillonnage LBR - combien de branches avant de prendre un échantillon. Lorsqu'une valeur positive est spécifiée pour cette option et que le mode est latency, nous utiliserons les LBR pour la mesure. Pour choisir la "bonne" période d'échantillonnage, une petite valeur est préférée, mais un ralentissement pourrait se produire si l'échantillonnage est trop fréquent. Un nombre premier doit être utilisé pour éviter de sauter systématiquement certains blocs.
--x86-disable-upper-sse-registers
L'utilisation des registres xmm supérieurs (xmm8-xmm15) force un encodage d'instruction plus long, ce qui peut exercer une pression plus grande sur les étapes de recherche et de décodage du frontend, réduisant potentiellement le taux de dispatch des instructions vers le backend, en particulier sur le matériel plus ancien. Comparer les résultats de base avec ce mode activé peut aider à déterminer les effets du frontend et peut être utilisé pour améliorer les estimations de latence et de débit.
--repetition-mode=[duplicate|loop|min|middle-half-duplicate|middle-half-loop]
Spécifier le mode de répétition. duplicate créera un bloc de base large et linéaire avec min-instructions instructions (en répétant l'extrait min-instructions/taille de l'extrait fois). loop, éventuellement, dupliquera l'extrait jusqu'à ce que le corps de la boucle contienne au moins loop-body-size instructions, puis encapsulera le résultat dans une boucle qui exécutera min-instructions instructions (donc, encore une fois, en répétant l'extrait min-instructions/taille de l'extrait fois). Le mode loop, en particulier avec le déroulement de boucle, a tendance à mieux masquer les effets du frontend du CPU sur les architectures qui mettent en cache les instructions décodées, mais consomme un registre pour compter les itérations. Si vous effectuez une analyse sur de nombreux opcodes, il peut être préférable d'utiliser le mode min, qui exécutera chaque autre mode et produira le résultat mesuré minimal. Les modes de répétition de la moitié centrale dupliqueront ou exécuteront l'extrait en boucle selon le mode spécifique. Les modes de répétition de la moitié centrale exécuteront deux mesures, l'une deux fois plus longue que la première, puis soustrairont la différence entre les deux pour obtenir des valeurs sans surcharge.
--min-instructions=<Nombre d'instructions>
Spécifier le nombre cible d'instructions exécutées. Notez que le nombre réel de répétitions de l'extrait sera min-instructions/taille de l'extrait. Des valeurs plus élevées conduisent à des mesures plus précises mais allongent la mesure.
--loop-body-size=<Taille préférée du corps de boucle>
Uniquement efficace pour -repetition-mode=[loop|min]. Au lieu de boucler directement sur l'extrait, dupliquez-le d'abord pour que le corps de la boucle contienne au moins ce nombre d'instructions. Cela peut potentiellement conduire à ce que le corps de la boucle soit mis en cache dans le CPU Op Cache / Loop Cache, ce qui permet d'obtenir un débit potentiellement plus élevé que les décodeurs CPU.
--max-configs-per-opcode=<valeur>
Spécifier le nombre maximum de configurations qui peuvent être générées pour chaque opcode. Par défaut, il est de 1, ce qui signifie que nous supposons qu'une seule mesure suffit à caractériser un opcode. Cela peut ne pas être vrai pour toutes les instructions : par exemple, les caractéristiques de performance de l'instruction LEA sur X86 dépendent de la valeur des registres et des immédiats assignés. Définir une valeur de -max-configs-per-opcode supérieure à 1 permet à llvm-exegesis d'explorer plus de configurations pour découvrir si certaines assignations de registres ou d'immédiats entraînent des caractéristiques de performance différentes.
--benchmarks-file=</chemin/vers/fichier>
Fichier pour lire (mode analysis) ou écrire (modes latency/uops/inverse_throughput) les résultats des mesures. "-" utilise stdin/stdout.
--analysis-clusters-output-file=</chemin/vers/fichier>
Si fourni, écrire les clusters d'analyse sous forme de CSV dans ce fichier. "-" imprime sur stdout. Par défaut, cette analyse n'est pas exécutée.

OPTIONS

--analysis-inconsistencies-output-file=</chemin/vers/fichier>
Si non vide, écrit les incohérences trouvées pendant l'analyse dans ce fichier. - imprime sur stdout. Par défaut, cette analyse n'est pas exécutée.
--analysis-filter=[all|reg-only|mem-only]
Par défaut, tous les résultats de benchmark sont analysés, mais il peut être utile parfois de ne regarder que ceux qui n'impliquent pas de mémoire, ou vice versa. Cette option permet soit de conserver tous les benchmarks, soit de filtrer (ignorer) soit tous ceux qui impliquent de la mémoire (impliquent des instructions pouvant lire ou écrire en mémoire), soit l'inverse, de ne conserver que ces benchmarks.
--analysis-clustering=[dbscan,naive]
Spécifie l'algorithme de clustering à utiliser. Par défaut, DBSCAN sera utilisé. L'algorithme de clustering naïf est mieux adapté pour un travail ultérieur sur la sortie de -analysis-inconsistencies-output-file=, il créera un cluster par opcode, et vérifiera que le cluster est stable (tous les points sont voisins).
--analysis-numpoints=<paramètre numPoints de dbscan>
Spécifie le paramètre numPoints à utiliser pour le clustering DBSCAN (mode analysis, DBSCAN uniquement).
--analysis-clustering-epsilon=<paramètre epsilon de dbscan>
Spécifie le paramètre epsilon utilisé pour le clustering des points de benchmark (mode analysis).
--analysis-inconsistency-epsilon=<epsilon>
Spécifie le paramètre epsilon utilisé pour la détection des cas où le cluster est différent des valeurs du profil d'ordonnancement LLVM (mode analysis).
--analysis-display-unstable-clusters
S'il y a plus d'un benchmark pour un opcode, ces benchmarks peuvent ne pas être groupés dans le même cluster si les caractéristiques de performance mesurées sont différentes. Par défaut, tous ces opcodes sont filtrés. Ce drapeau affichera uniquement ces opcodes instables.
--ignore-invalid-sched-class=false
S'il est défini, ignore les instructions qui n'ont pas de classe d'ordonnancement (indice de classe = 0).
--mtriple=<nom du triple>
Triple cible. Voir -version pour les cibles disponibles.
--mcpu=<nom du cpu>
S'il est défini, mesure les caractéristiques du CPU en utilisant les compteurs pour ce CPU. Ceci est utile lors de la création de nouveaux modèles d'ordonnancement (le CPU hôte n'est pas connu de LLVM). (-mcpu=help pour plus de détails)
--analysis-override-benchmark-triple-and-cpu
Par défaut, llvm-exegesis analysera les benchmarks pour le triple/CPU pour lesquels ils ont été mesurés, mais si vous souhaitez les analyser pour une autre combinaison (spécifiée via -mtriple/-mcpu), vous pouvez passer ce drapeau.
--dump-object-to-disk=<nom de fichier>
S'il est défini, llvm-exegesis exportera le code généré dans un fichier temporaire pour permettre l'inspection du code. Désactivé par défaut.
--use-dummy-perf-counters
S'il est défini, llvm-exegesis ne lira aucun compteur de performance réel et renverra une valeur factice à la place. Ceci peut être utilisé pour s'assurer qu'un extrait de code ne plante pas lorsque les compteurs de performance matériels ne sont pas disponibles et pour déboguer llvm-exegesis lui-même.
--execution-mode=[inprocess,subprocess]
Cette option spécifie le mode d'exécution à utiliser. Le mode d'exécution inprocess est le mode par défaut. Le mode d'exécution subprocess permet des fonctionnalités supplémentaires telles que les annotations mémoire, mais est actuellement limité à X86-64 sous Linux.
--benchmark-repeat-count=<nombre de répétitions>
Cette option permet de spécifier le nombre de fois où la mesure doit être répétée lors de la mesure de la latence. Par défaut, llvm-exegesis répétera une mesure de latence suffisamment de fois pour équilibrer le temps d'exécution et la réduction du bruit.
--validation-counter=[instructions-retired,l1d-cache-load-misses,
l1d-cache-store-misses,l1i-cache-load-misses,data-tlb-load-misses,
data-tld-store-misses,instruction-tlb-load-misses]
Cette option permet l'utilisation de compteurs de validation, qui mesurent des événements microarchitecturaux supplémentaires tels que les misses de cache pour valider les conditions d'exécution des extraits. Ces événements sont mesurés à l'aide du sous-système perf dans un groupe avec le compteur de performance utilisé pour mesurer la valeur d'intérêt. Ce drapeau peut être spécifié plusieurs fois pour mesurer plusieurs événements. Le nombre maximum de compteurs de validation dépend de la plateforme.
--benchmark-process-cpu=<ID du CPU>
Cette option spécifie le numéro du CPU qui doit être utilisé pour exécuter le sous-processus de benchmark. Lors du démarrage du sous-processus, llvm-exegesis définira l'affinité du sous-processus pour qu'il n'inclue que le CPU spécifié. Cette option ne fonctionne qu'en mode d'exécution par sous-processus.

STATUT DE SORTIE

llvm-exegesis retourne 0 en cas de succès. Sinon, un message d'erreur est imprimé sur la sortie d'erreur standard, et l'outil retourne une valeur non nulle.
