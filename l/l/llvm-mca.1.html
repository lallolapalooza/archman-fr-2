NOM

llvm-mca - Analyseur de code machine LLVM

SYNOPSIS

llvm-mca [options] [entrée]

DESCRIPTION

llvm-mca est un outil d'analyse de performance qui utilise les informations disponibles dans LLVM (par exemple, les modèles de planification) pour mesurer statiquement la performance du code machine sur un CPU spécifique.

La performance est mesurée en termes de débit ainsi que de consommation des ressources du processeur. L'outil fonctionne actuellement pour les processeurs disposant d'un backend pour lequel un modèle de planification est disponible dans LLVM.

L'objectif principal de cet outil n'est pas seulement de prédire la performance du code lorsqu'il est exécuté sur la cible, mais aussi d'aider à diagnostiquer les problèmes potentiels de performance.

À partir d'une séquence de code assembleur, llvm-mca estime les Instructions Par Cycle (IPC), ainsi que la pression sur les ressources matérielles. Le style d'analyse et de rapport a été inspiré par l'outil IACA d'Intel.

Par exemple, vous pouvez compiler du code avec clang, afficher l'assembleur, et le rediriger directement vers llvm-mca pour analyse :

$ clang foo.c -O2 --target=x86_64 -S -o - | llvm-mca -mcpu=btver2

Ou pour la syntaxe Intel :

$ clang foo.c -O2 --target=x86_64 -masm=intel -S -o - | llvm-mca -mcpu=btver2

(llvm-mca détecte la syntaxe Intel par la présence d'une directive .intel_syntax au début de l'entrée. Par défaut, la syntaxe de sa sortie correspond à celle de son entrée.)

Les modèles de planification ne sont pas seulement utilisés pour calculer les latences et le débit des instructions, mais aussi pour comprendre quelles ressources processeur sont disponibles et comment les simuler.

Par conception, la qualité de l'analyse effectuée par llvm-mca est inévitablement affectée par la qualité des modèles de planification dans LLVM.

Si vous constatez que le rapport de performance n'est pas précis pour un processeur, veuillez signaler un bug https://github.com/llvm/llvm-project/issues contre le backend approprié.

OPTIONS

Si entrée est "-" ou omis, llvm-mca lit depuis l'entrée standard. Sinon, il lira depuis le nom de fichier spécifié.

Si l'option -o est omise, alors llvm-mca enverra sa sortie vers la sortie standard si l'entrée provient de l'entrée standard. Si l'option -o spécifie "-", alors la sortie sera également envoyée vers la sortie standard.

-help
Affiche un résumé des options de ligne de commande.
-o <nom_de_fichier>
Utilise <nom_de_fichier> comme nom de fichier de sortie. Voir le résumé ci-dessus pour plus de détails.
-mtriple=<triple cible>
Spécifie une chaîne de triple cible.
-march=<arch>
Spécifie l'architecture pour laquelle analyser le code. Par défaut, il s'agit de la cible par défaut de l'hôte.
-mcpu=<nom_cpu>
Spécifie le processeur pour lequel analyser le code. Par défaut, le nom du CPU est auto-détecté depuis l'hôte.
-output-asm-variant=<identifiant de variante>
Spécifie la variante d'assembleur de sortie pour le rapport généré par l'outil. Sur x86, les valeurs possibles sont [0, 1]. Une valeur de 0 (resp. 1) pour ce drapeau active le format d'assembleur AT&T (resp. Intel) pour le code imprimé par l'outil dans le rapport d'analyse.
-print-imm-hex
Préférer le format hexadécimal pour les littéraux numériques dans le code assembleur de sortie imprimé dans le cadre du rapport.
-dispatch=<largeur>
Spécifie une largeur de dispatch différente pour le processeur. La largeur de dispatch est par défaut le champ 'IssueWidth' dans le modèle de planification du processeur. Si la largeur est zéro, la largeur de dispatch par défaut est utilisée.
-register-file-size=<taille>
Spécifie la taille du fichier de registres. Lorsqu'il est spécifié, ce drapeau limite le nombre de registres physiques disponibles à des fins de renommage de registres. Une valeur de zéro pour ce drapeau signifie un nombre illimité de registres physiques.
-iterations=<nombre d'itérations>
Spécifie le nombre d'itérations à exécuter. Si ce drapeau est réglé sur 0, l'outil définit le nombre d'itérations à une valeur par défaut (c'est-à-dire 100).
-noalias=<booléen>
S'il est défini, l'outil suppose que les chargements et les stockages n'ont pas d'alias. C'est le comportement par défaut.
-lqueue=<taille de la file d'attente de chargement>
Spécifie la taille de la file d'attente de chargement dans l'unité de chargement/stockage émulée par l'outil. Par défaut, l'outil suppose un nombre illimité d'entrées dans la file d'attente de chargement. Une valeur de zéro pour ce drapeau est ignorée, et la taille de file d'attente de chargement par défaut est utilisée à la place.
-squeue=<taille de la file d'attente de stockage>
Spécifie la taille de la file d'attente de stockage dans l'unité de chargement/stockage émulée par l'outil. Par défaut, l'outil suppose un nombre illimité d'entrées dans la file d'attente de stockage. Une valeur de zéro pour ce drapeau est ignorée, et la taille de file d'attente de stockage par défaut est utilisée à la place.
-timeline
Active la vue chronologique.
-timeline-max-iterations=<itérations>
Limite le nombre d'itérations à imprimer dans la vue chronologique. Par défaut, la vue chronologique imprime des informations pour jusqu'à 10 itérations.
-timeline-max-cycles=<cycles>
Limite le nombre de cycles dans la vue chronologique, ou utilise 0 pour aucune limite. Par défaut, le nombre de cycles est fixé à 80.
-resource-pressure
Active la vue de pression sur les ressources. Ceci est activé par défaut.
-register-file-stats
Active les statistiques d'utilisation du fichier de registres.
-dispatch-stats
Active des statistiques de dispatch supplémentaires. Cette vue collecte et analyse les événements de dispatch d'instructions, ainsi que les événements de blocage de dispatch statiques/dynamiques. Cette vue est désactivée par défaut.
-scheduler-stats
Active des statistiques de planification supplémentaires. Cette vue collecte et analyse les événements d'émission d'instructions. Cette vue est désactivée par défaut.
-retire-stats
Active des statistiques supplémentaires sur l'unité de contrôle de retraite. Cette vue est désactivée par défaut.
-instruction-info
Active la vue d'informations sur les instructions. Ceci est activé par défaut.
-show-encoding
Active l'impression des encodages d'instructions dans
l'info de l'instruction vue.
-show-barriers
Active l'impression des drapeaux LoadBarrier et StoreBarrier dans la vue d'informations des instructions.
-all-stats
Imprime toutes les statistiques matérielles. Ceci active des statistiques supplémentaires liées à la logique de dispatch, aux planificateurs matériels, au(x) registre(s) et à l'unité de contrôle de sortie. Cette option est désactivée par défaut.
-all-views
Active toutes les vues.
-instruction-tables=<level>
Imprime des informations sur la pression des ressources basées sur les informations statiques disponibles à partir du modèle de processeur. Ceci diffère de la vue de pression des ressources car cela ne nécessite pas que le code soit simulé. Il imprime plutôt la distribution uniforme théorique de la pression des ressources pour chaque instruction en séquence.

Le choix de <level> contrôle le nombre d'informations imprimées. <level> peut être none (par défaut), normal, full. Note: Si l'option est utilisée sans <label>, la valeur par défaut est normal (hérité).

Lorsque <level> est full, des informations supplémentaires sont : - <Bypass Latency> : latence lorsqu'un bypass est implémenté entre les opérandes dans les pipelines (voir SchedReadAdvance). - <LLVM Opcode Name> : mnémonique plus identifiant des opérandes. - <Resources units> : unités de ressources utilisées associées à l'Opcode LLVM. - <instruction comment> : rapporte un commentaire s'il y en a dans l'assemblage source.

La syntaxe de <Resources units> peut être : - <Resource Name> : ReleaseAtCycle est 1. - <Resource Name>[<ReleaseAtCycle>] : ReleaseAtCycle est supérieur à 1 et AcquireAtCycle est 0. - <Resource Name>[<AcquireAtCycle>,<ReleaseAtCycle>] : ReleaseAtCycle est supérieur à 1 et AcquireAtCycle est supérieur à 0.

-bottleneck-analysis
Imprime des informations sur les goulets d'étranglement qui affectent le débit. Cette analyse peut être coûteuse et est désactivée par défaut. Les goulets d'étranglement sont mis en évidence dans la vue récapitulative. L'analyse des goulets d'étranglement n'est actuellement pas prise en charge pour les processeurs avec un backend en ordre.
-json
Imprime les vues demandées au format JSON valide. Les instructions et les ressources du processeur sont imprimées en tant que membres d'objets JSON de niveau supérieur spécialisés. Les vues individuelles y font référence par leur index. Cependant, toutes les vues ne sont pas actuellement prises en charge. Par exemple, le rapport de l'analyse des goulets d'étranglement n'est pas imprimé en JSON. Toutes les vues par défaut sont actuellement prises en charge.
-disable-cb
Force l'utilisation des classes génériques CustomBehaviour et InstrPostProcess plutôt que l'utilisation de l'implémentation spécifique à la cible. Les classes génériques ne détectent jamais de dangers personnalisés et n'apportent aucune modification post-traitement aux instructions.
-disable-im
Force l'utilisation du gestionnaire générique InstrumentManager plutôt que l'utilisation de l'implémentation spécifique à la cible. La classe générique crée des Instruments qui ne fournissent aucune information supplémentaire, et InstrumentManager ne remplace jamais la classe de planification par défaut pour une instruction donnée.
-skip-unsupported-instructions=<reason>
Force llvm-mca à continuer en présence d'instructions qui ne peuvent pas être analysées ou qui manquent d'informations de planification clés. Notez que l'analyse résultante est impactée car ces instructions non prises en charge sont ignorées comme si elles n'étaient pas fournies dans l'entrée.

Le choix de <reason> contrôle quand mca signalera une erreur. <reason> peut être none (par défaut), lack-sched, parse-failure, any.

STATUT DE SORTIE

llvm-mca renvoie 0 en cas de succès. Sinon, un message d'erreur est imprimé sur la sortie d'erreur standard et l'outil renvoie 1.

UTILISATION DES MARQUEURS POUR ANALYSER DES BLOCS DE CODE SPÉCIFIQUES

llvm-mca permet l'utilisation facultative de commentaires de code spéciaux pour marquer des régions de code assembleur à analyser. Un commentaire commençant par la sous-chaîne LLVM-MCA-BEGIN marque le début d'une région d'analyse. Un commentaire commençant par la sous-chaîne LLVM-MCA-END marque la fin d'une région. Par exemple :

# LLVM-MCA-BEGIN
  ...
# LLVM-MCA-END

Si aucune région définie par l'utilisateur n'est spécifiée, alors llvm-mca assume une région par défaut qui contient chaque instruction du fichier d'entrée. Chaque région est analysée isolément, et le rapport de performance final est l'union de tous les rapports générés pour chaque région d'analyse.

Les régions d'analyse peuvent avoir des noms. Par exemple :

# LLVM-MCA-BEGIN Un exemple simple
  add %eax, %eax
# LLVM-MCA-END

Le code de l'exemple ci-dessus définit une région nommée "Un exemple simple" avec une seule instruction. Notez que le nom de la région n'a pas besoin d'être répété dans la directive LLVM-MCA-END. En l'absence de régions imbriquées, une directive LLVM-MCA-END anonyme termine toujours la région définie par l'utilisateur actuellement active.

Exemple de régions imbriquées :

# LLVM-MCA-BEGIN foo
  add %eax, %edx
# LLVM-MCA-BEGIN bar
  sub %eax, %edx
# LLVM-MCA-END bar
# LLVM-MCA-END foo

Exemple de régions qui se chevauchent :

# LLVM-MCA-BEGIN foo
  add %eax, %edx
# LLVM-MCA-BEGIN bar
  sub %eax, %edx
# LLVM-MCA-END foo
  add %eax, %edx
# LLVM-MCA-END bar

Notez que plusieurs régions anonymes ne peuvent pas se chevaucher. De plus, les régions qui se chevauchent ne peuvent pas avoir le même nom.

Il n'y a pas de prise en charge pour marquer des régions à partir de code source de haut niveau, comme C ou C++. En solution de contournement, des directives d'assemblage en ligne peuvent être utilisées :

int foo(int a, int b) {
  __asm volatile("# LLVM-MCA-BEGIN foo":::"memory");
  a += 42;
  __asm volatile("# LLVM-MCA-END":::"memory");
  a *= b;
  return a;
}

Cependant, cela interfère avec les optimisations telles que la vectorisation de boucle et peut avoir un impact sur le code généré. En effet, les instructions __asm sont considérées comme du code réel ayant des effets secondaires importants, ce qui limite la manière dont le code environnant peut être transformé. Si les utilisateurs souhaitent utiliser l'assemblage en ligne pour émettre des marqueurs, il est recommandé de toujours vérifier que l'assemblage de sortie est équivalent à l'assemblage généré en l'absence de marqueurs. Les options de Clang pour émettre des rapports d'optimisation https://clang.llvm.org/docs/UsersManual.html#options-to-emit-optimization-reports peuvent également aider à détecter les optimisations manquées.

RÉGIONS D'INSTRUMENTATION

Une InstrumentRegion décrit une région de code assembleur protégée par des directives de commentaires spéciales LLVM-MCA.

# LLVM-MCA-<INSTRUMENT_TYPE> <data>
  ...  ## asm

où INSTRUMENT_TYPE est un type défini par la cible et s'attend à utiliser data.

Un commentaire commençant par la sous-chaîne LLVM-MCA-<INSTRUMENT_TYPE> met des données en portée pour que llvm-mca les utilise dans son analyse pour toutes les instructions suivantes.

Si un commentaire avec le même INSTRUMENT_TYPE est trouvé plus tard dans la liste d'instructions, alors la région d'instrumentation d'origine sera automatiquement terminée, et une nouvelle région d'instrumentation commencera.

S'il y a des commentaires contenant des INSTRUMENT_TYPE différents, alors les deux ensembles de données restent disponibles. Contrairement à une région d'analyse, une région d'instrumentation n'a pas besoin d'un commentaire pour terminer la région.

Les commentaires qui sont préfixés par LLVM-MCA- mais qui ne correspondent pas à un INSTRUMENT_TYPE valide pour la cible entraînent une erreur, à l'exception de BEGIN et END, car ceux-ci correspondent aux régions d'analyse. Les commentaires qui ne commencent pas par LLVM-MCA- sont ignorés par llvm-mca.

Une instruction (un MCInst) est ajoutée à une InstrumentRegion R uniquement si son emplacement se situe dans l'intervalle [R.RangeStart, R.RangeEnd].

Sur les cibles RISCV, les instructions vectorielles ont un comportement différent en fonction du LMUL. Le code peut être instrumenté avec un commentaire qui prend la forme suivante :

# LLVM-MCA-RISCV-LMUL <M1|M2|M4|M8|MF2|MF4|MF8>

Le RISCV InstrumentManager remplacera la classe de planification pour les instructions vectorielles afin d'utiliser le comportement de planification de son pseudo-instruction qui dépend du LMUL. Il est logique de placer les commentaires d'instrumentation RISCV directement après les instructions vset{i}vl{i}, bien qu'ils puissent être placés n'importe où dans le programme.

Exemple de programme sans appel à vset{i}vl{i} :

# LLVM-MCA-RISCV-LMUL M2
vadd.vv v2, v2, v2

Exemple de programme avec un appel à vset{i}vl{i} :

vsetvli zero, a0, e8, m1, tu, mu
# LLVM-MCA-RISCV-LMUL M1
vadd.vv v2, v2, v2

Exemple de programme avec plusieurs appels à vset{i}vl{i} :

vsetvli zero, a0, e8, m1, tu, mu
# LLVM-MCA-RISCV-LMUL M1
vadd.vv v2, v2, v2
vsetvli zero, a0, e8, m8, tu, mu
# LLVM-MCA-RISCV-LMUL M8
vadd.vv v2, v2, v2

Exemple de programme avec un appel à vsetvl :

vsetvl rd, rs1, rs2
# LLVM-MCA-RISCV-LMUL M1
vadd.vv v12, v12, v12
vsetvl rd, rs1, rs2
# LLVM
-MCA-RISCV-LMUL M4 vadd.vv v12, v12, v12

COMMENT LLVM-MCA FONCTIONNE

llvm-mca prend du code d'assemblage en entrée. Le code d'assemblage est analysé en une séquence de MCInst à l'aide des analyseurs d'assemblage de cible LLVM existants. La séquence analysée de MCInst est ensuite analysée par un module Pipeline pour générer un rapport de performance.

Le module Pipeline simule l'exécution de la séquence de code machine dans une boucle d'itérations (par défaut, 100). Au cours de ce processus, le pipeline collecte un certain nombre de statistiques liées à l'exécution. À la fin de ce processus, le pipeline génère et imprime un rapport à partir des statistiques collectées.

Selon ce rapport, le noyau de produit scalaire a été exécuté 300 fois, pour un total de 900 instructions simulées. Le nombre total de micro-opérations simulées (uOps) est également de 900.

Le rapport est structuré en trois sections principales. La première section collecte quelques chiffres de performance; le but de cette section est de donner un aperçu très rapide du débit de performance. Les indicateurs de performance importants sont l'IPC (Instructions Par Cycle), les uOps Per Cycle (micro-opérations Par Cycle), et le Block RThroughput (Débit Réciproque de Bloc).

Le champ DispatchWidth est le nombre maximum de micro-opérations qui sont expédiées vers le backend hors-ordre à chaque cycle simulé. Pour les processeurs avec un backend en ordre, DispatchWidth est le nombre maximum de micro-opérations émises vers le backend à chaque cycle simulé.

L'IPC est calculé en divisant le nombre total d'instructions simulées par le nombre total de cycles.

Le champ Block RThroughput est l'inverse du débit de bloc. Le débit de bloc est une quantité théorique calculée comme le nombre maximum de blocs (c'est-à-dire d'itérations) qui peuvent être exécutés par cycle d'horloge simulé en l'absence de dépendances de boucle. Le débit de bloc est limité supérieurement par le taux de dispatch, et la disponibilité des ressources matérielles.

En l'absence de dépendances de données de boucle, l'IPC observé tend vers un maximum théorique qui peut être calculé en divisant le nombre d'instructions d'une seule itération par le Block RThroughput.

Le champ 'uOps Per Cycle' est calculé en divisant le nombre total de micro-opérations simulées par le nombre total de cycles. Une différence entre Dispatch Width et ce champ est un indicateur d'un problème de performance. En l'absence de dépendances de données de boucle, les 'uOps Per Cycle' observés devraient tendre vers un débit maximal théorique qui peut être calculé en divisant le nombre d'uOps d'une seule itération par le Block RThroughput.

Le champ uOps Per Cycle est borné supérieurement par la largeur de dispatch. Cela est dû au fait que la largeur de dispatch limite la taille maximale d'un groupe de dispatch. L'IPC et les 'uOps Per Cycle' sont limités par la quantité de parallélisme matériel. La disponibilité des ressources matérielles affecte la distribution de la pression sur les ressources, et elle limite le nombre d'instructions qui peuvent être exécutées en parallèle chaque cycle. Une différence entre la largeur de dispatch et le débit théorique maximum d'uOps par cycle (calculé en divisant le nombre d'uOps d'une seule itération par le Block RThroughput) est un indicateur d'un goulot d'étranglement de performance causé par le manque de ressources matérielles. En général, plus le Block RThroughput est bas, mieux c'est.

Dans cet exemple, uOps par itération/Block RThroughput est de 1.50. Comme il n'y a pas de dépendances de boucle, les uOps Per Cycle observés devraient s'approcher de 1.50 lorsque le nombre d'itérations tend vers l'infini. La différence entre la largeur de dispatch (2.00) et le débit théorique maximum d'uOps par cycle (1.50) est un indicateur d'un goulot d'étranglement de performance causé par le manque de ressources matérielles, et la vue Resource pressure peut aider à identifier l'utilisation problématique des ressources.

La deuxième section du rapport est la vue des informations sur les instructions. Elle montre la latence et le débit réciproque de chaque instruction de la séquence. Elle rapporte également des informations supplémentaires liées au nombre de micro-opérations, et aux propriétés des micro-opérations (c'est-à-dire, 'MayLoad', 'MayStore', et 'HasSideEffects').

Le champ RThroughput est l'inverse du débit d'instructions. Le débit est calculé comme le nombre maximum d'instructions du même type qui peuvent être exécutées par cycle d'horloge en l'absence de dépendances d'opérandes. Dans cet exemple, le débit réciproque d'une multiplication flottante vectorielle est de 1 cycle/instruction. C'est parce que le multiplicateur FP JFPM n'est disponible qu'à partir du pipeline JFPU1.

Les encodages d'instructions sont affichés dans la vue des informations sur les instructions lorsque le drapeau -show-encoding est spécifié.

Ci-dessous un exemple de sortie de -show-encoding pour le noyau de produit scalaire :

Instruction Info:

[3]: RThroughput
[4]: MayLoad
[5]: MayStore
[6]: HasSideEffects (U)
[7]: Encoding Size
[1]    [2]    [3]    [4]    [5]    [6]    [7]    Encodings:                    Instructions:

La colonne Encoding Size indique la taille en octets des instructions. La colonne Encodings montre les encodages réels des instructions (séquences d'octets en hexadécimal).

La troisième section est la vue de la pression sur les ressources. Cette vue rapporte le nombre moyen de cycles de ressources consommés par itération par les instructions pour chaque unité de ressource processeur disponible sur la cible. Les informations sont structurées en deux tableaux. Le premier tableau rapporte le nombre de cycles de ressources dépensés en moyenne par itération. Le second tableau corrèle les cycles de ressources à l'instruction machine de la séquence. Par exemple, chaque itération de l'instruction vmulps s'exécute toujours sur l'unité de ressource [6] (JFPU1 - pipeline flottant #1), consommant une moyenne de 1 cycle de ressource par itération. Notez que sur AMD Jaguar, la multiplication flottante vectorielle ne peut être émise que vers le pipeline JFPU1, tandis que les additions flottantes horizontales ne peuvent être émises qu'au pipeline JFPU0.

La vue de la pression sur les ressources aide à identifier les goulots d'étranglement causés par une utilisation élevée de certaines ressources matérielles. Les situations où la pression sur les ressources est principalement concentrée sur quelques ressources devraient, en général, être évitées. Idéalement, la pression devrait être uniformément répartie entre plusieurs ressources.

La vue chronologique est structurée en deux tableaux. Le premier tableau montre les instructions changeant d'état au fil du temps (mesuré en cycles) ; le second tableau (nommé Temps d'attente moyen) rapporte des statistiques temporelles utiles, qui devraient aider à diagnostiquer les goulots d'étranglement de performance causés par de longues dépendances de données et une utilisation sous-optimale des ressources matérielles.

Une instruction dans la vue chronologique est identifiée par une paire d'indices, où le premier indice identifie une itération, et le second indice est l'indice de l'instruction (c'est-à-dire où elle apparaît dans la séquence de code). Puisque cet exemple a été généré en utilisant 3 itérations : -iterations=3, les indices d'itération vont de 0 à 2 inclus.

À l'exclusion de la première et de la dernière colonne, les colonnes restantes sont en cycles. Les cycles sont numérotés séquentiellement à partir de 0.

D'après l'exemple de sortie ci-dessus, nous savons ce qui suit :

  • L'instruction [1,0] a été dépêchée au cycle 1.
  • L'instruction [1,0] a commencé son exécution au cycle 2.
  • L'instruction [1,0] a atteint l'étape d'écriture au cycle 4.
  • L'instruction [1,0] a été retirée au cycle 10.

L'instruction [1,0] (c'est-à-dire vmulps de l'itération #1) n'a pas eu à attendre dans la file d'attente du planificateur pour que les opérandes soient disponibles. Au moment où vmulps est dépêché, les opérandes sont déjà disponibles et le pipeline JFPU1 est prêt à servir une autre instruction. Ainsi, l'instruction peut être immédiatement délivrée sur le pipeline JFPU1. Ceci est démontré par le fait que l'instruction n'a passé que 1 cycle dans la file d'attente du planificateur.

Il y a un écart de 5 cycles entre l'étape d'écriture et l'événement de retrait. C'est parce que les instructions doivent être retirées dans l'ordre du programme, donc [1,0] doit attendre que [0,2] soit retiré en premier (c'est-à-dire qu'elle doit attendre jusqu'au cycle 10).

Dans l'exemple, toutes les instructions sont dans une chaîne de dépendance RAW (Read After Write). Le registre %xmm2 écrit par vmulps est immédiatement utilisé par le premier vhaddps, et le registre %xmm3 écrit par le premier vhaddps est utilisé par le second vhaddps. Les longues dépendances de données ont un impact négatif sur le parallélisme au niveau de l'instruction (ILP).

Dans l'exemple de produit scalaire, il existe des anti-dépendances introduites par des instructions d'itérations différentes. Cependant, ces dépendances peuvent être supprimées à l'étape de renommage de registre (au coût de l'allocation d'alias de registre, et donc de la consommation de registres physiques).

Le tableau Temps d'attente moyen aide à diagnostiquer les problèmes de performance causés par la présence d'instructions à latence longue et de dépendances de données potentiellement longues qui peuvent limiter l'ILP. La dernière ligne, <total>, montre une moyenne globale sur toutes les instructions mesurées. Notez que llvm-mca, par défaut, suppose au moins 1 cycle entre l'événement de dépêche et l'événement de délivrance.

Lorsque la performance est limitée par les dépendances de données et/ou les instructions à latence longue, le nombre de cycles passés à l'état prêt devrait être très faible par rapport au nombre total de cycles passés dans la file d'attente du planificateur. La différence entre les deux compteurs est un bon indicateur de l'impact des dépendances de données sur l'exécution des instructions. Lorsque la performance est principalement limitée par le manque de ressources matérielles, la différence entre les deux compteurs est faible. Cependant, le nombre de cycles passés dans la file d'attente a tendance à être plus élevé (c'est-à-dire plus de 1-3 cycles), en particulier par rapport à d'autres instructions à faible latence.

Utilisation du fichier de registres

Lorsqu'un processeur implémente un jeu d'instructions qui prend en charge à la fois les registres entiers et les registres à virgule flottante, il peut y avoir plusieurs fichiers de registres physiques. Dans le cas d'un processeur avec 32 registres entiers et 32 registres à virgule flottante, cela peut être implémenté comme un seul fichier de registres avec 64 entrées, ou comme deux fichiers de registres distincts : un fichier de registres entiers avec 32 entrées et un fichier de registres à virgule flottante avec 32 entrées.

Dans le premier cas (un fichier de registres unique), les instructions à virgule flottante et les instructions entières utilisent le même pool de registres physiques. La plupart des instructions à virgule flottante sont mappées à des registres à virgule flottante, et la plupart des instructions entières sont mappées à des registres entiers. Cependant, les instructions à virgule flottante peuvent parfois nécessiter d'utiliser des registres entiers, et inversement. La plupart des processeurs modernes implémentent des fichiers de registres physiques dédiés pour les entiers et les registres à virgule flottante.

Le nombre de registres physiques disponibles pour le renommage de registres peut être spécifié par le biais de l'option de commande -register-file-size. Flux des instructions

Cette section décrit le flux des instructions à travers le pipeline par défaut de llvm-mca, ainsi que les unités fonctionnelles impliquées dans le processus.

Le pipeline par défaut implémente la séquence d'étapes suivante pour traiter les instructions.

  • Dispatch (L'instruction est envoyée aux planificateurs).
  • Issue (L'instruction est émise vers les pipelines du processeur).
  • Write Back (L'instruction est exécutée et les résultats sont écrits).
  • Retire (L'instruction est retirée; les écritures sont validées architecturallement).

Le pipeline in-order implémente la séquence d'étapes suivante:

  • InOrderIssue (L'instruction est émise vers les pipelines du processeur).
  • Retire (L'instruction est retirée; les écritures sont validées architecturallement).

llvm-mca suppose que toutes les instructions ont été décodées et placées dans une file d'attente avant le début de la simulation. Par conséquent, les étapes de récupération et de décodage des instructions ne sont pas modélisées. Les goulots d'étranglement des performances dans le frontend ne sont pas diagnostiqués. De plus, llvm-mca ne modélise pas la prédiction de branchement.

Dispatch des instructions

Au cours de l'étape de dispatch, les instructions sont sélectionnées dans l'ordre du programme à partir d'une file d'attente d'instructions déjà décodées, et envoyées par groupes aux planificateurs matériels simulés.

La taille d'un groupe de dispatch dépend de la disponibilité des ressources matérielles simulées. La largeur de dispatch du processeur est par défaut égale à la valeur de IssueWidth dans le modèle de planification de LLVM.

Une instruction peut être envoyée si:

  • La taille du groupe de dispatch est inférieure à la largeur de dispatch du processeur.
  • Il y a suffisamment d'entrées dans le tampon de réordonnancement.
  • Il y a suffisamment de registres physiques pour le renommage de registres.
  • Les planificateurs ne sont pas pleins.

Les modèles de planification peuvent éventuellement spécifier quels fichiers de registres sont disponibles sur le processeur. llvm-mca utilise cette information pour initialiser les descripteurs de fichiers de registres. Les utilisateurs peuvent limiter le nombre de registres physiques globalement disponibles pour le renommage de registres en utilisant l'option de commande -register-file-size. Une valeur de zéro pour cette option signifie illimité. En sachant combien de registres sont disponibles pour le renommage, l'outil peut prédire les blocages de dispatch causés par le manque de registres physiques.

Le nombre d'entrées de tampon de réordonnancement consommées par une instruction dépend du nombre de micro-opérations spécifiées pour cette instruction par le modèle de planification de la cible. Le tampon de réordonnancement est responsable du suivi de la progression des instructions qui sont "en vol", et de leur retrait dans l'ordre du programme. Le nombre d'entrées dans le tampon de réordonnancement est par défaut égal à la valeur spécifiée par le champ MicroOpBufferSize dans le modèle de planification de la cible.

Les instructions qui sont envoyées aux planificateurs consomment des entrées dans le tampon du planificateur. llvm-mca interroge le modèle de planification pour déterminer l'ensemble des ressources tamponnées consommées par une instruction. Les ressources tamponnées sont traitées comme des ressources du planificateur.

Émission des instructions

Chaque planificateur de processeur implémente un tampon d'instructions. Une instruction doit attendre dans le tampon du planificateur jusqu'à ce que les opérandes d'entrée du registre deviennent disponibles. Ce n'est qu'à ce moment-là que l'instruction devient éligible pour l'exécution et peut être émise (potentiellement hors ordre) pour l'exécution. Les latences des instructions sont calculées par llvm-mca avec l'aide du modèle de planification.

Le planificateur de llvm-mca est conçu pour simuler plusieurs planificateurs de processeurs. Le planificateur est responsable du suivi des dépendances de données et de la sélection dynamique des ressources du processeur qui sont consommées par les instructions. Il délègue la gestion des unités de ressources du processeur et des groupes de ressources à un gestionnaire de ressources. Le gestionnaire de ressources est responsable de la sélection des unités de ressources qui sont consommées par les instructions. Par exemple, si une instruction consomme 1 cycle d'un groupe de ressources, le gestionnaire de ressources sélectionne l'une des unités disponibles du groupe; par défaut, le gestionnaire de ressources utilise un sélecteur de type round-robin pour garantir que l'utilisation des ressources est uniformément répartie entre toutes les unités d'un groupe.

Le planificateur de llvm-mca regroupe en interne les instructions en trois ensembles:

  • WaitSet: un ensemble d'instructions dont les opérandes ne sont pas prêts.
  • ReadySet: un ensemble d'instructions prêtes à s'exécuter.
  • IssuedSet: un ensemble d'instructions en cours d'exécution.

En fonction de la disponibilité des opérandes, les instructions qui sont envoyées au planificateur sont soit placées dans le WaitSet, soit dans le ReadySet.

Chaque cycle, le planificateur vérifie si les instructions peuvent être déplacées du WaitSet vers le ReadySet, et si les instructions du ReadySet peuvent être émises vers les pipelines sous-jacents. L'algorithme donne la priorité aux instructions plus anciennes par rapport aux instructions plus récentes.

Étape d'écriture et de retrait

Les instructions émises sont déplacées du ReadySet vers l'IssuedSet. Là, les instructions attendent jusqu'à ce qu'elles atteignent l'étape d'écriture (write-back). À ce moment-là, elles sont retirées de la file d'attente et l'unité de contrôle de retrait est notifiée.

Lorsque les instructions sont exécutées, l'unité de contrôle de retrait marque l'instruction comme "prête à être retirée".

Les instructions sont retirées dans l'ordre du programme. Le fichier de registres est informé du retrait afin qu'il puisse libérer les registres physiques qui ont été alloués à l'instruction lors de l'étape de renommage de registres.

Unité de chargement/stockage et modèle de cohérence mémoire

Pour simuler une exécution hors ordre des opérations mémoire, llvm-mca utilise une unité de chargement/stockage (LSUnit) simulée pour simuler l'exécution spéculative des chargements et des stockages.

Chaque chargement (ou stockage) consomme une entrée dans la file de chargement (ou de stockage). Les utilisateurs peuvent spécifier les options -lqueue et -squeue pour limiter le nombre d'entrées dans les files de chargement et de stockage respectivement. Les files sont illimitées par défaut.

La LSUnit implémente un modèle de cohérence relâché pour les chargements et les stockages mémoire. Les règles sont:

1.
Un chargement plus jeune est autorisé à passer un chargement plus ancien uniquement s'il n'y a pas de stockages ou de barrières entre les deux chargements.
2.
Un chargement plus jeune est autorisé à passer un stockage plus ancien à condition que le chargement n'alias pas le stockage.
3.
Un stockage plus jeune n'est pas autorisé à passer un stockage plus ancien.
4.
Un stockage plus jeune n'est pas autorisé à passer un chargement plus ancien.

Par défaut, la LSUnit suppose de manière optimiste que les chargements n'aliasent pas les opérations de stockage (-noalias=true). Sous cette hypothèse, les chargements plus jeunes sont toujours autorisés à passer les stockages plus anciens. Essentiellement, la LSUnit ne tente pas d'exécuter d'analyse d'alias pour prédire quand les chargements et les stockages n'aliasent pas les uns les autres.

Il est à noter que, dans le cas de la mémoire combinant en écriture (write-combining), la règle 3 pourrait être assouplie pour permettre le réordonnancement des opérations de stockage n'aliasant pas. Cela dit, pour le moment, il n'y a aucun moyen d'assouplir davantage le modèle mémoire (-noalias est la seule option). Essentiellement, il n'y a pas d'option pour spécifier un type de mémoire différent (par exemple, write-back, write-combining, write-through; etc.) et par conséquent pour affaiblir ou renforcer le modèle mémoire.

D'autres limitations sont:

  • La LSUnit ne sait pas quand une transmission de stockage à chargement (store-to-load forwarding) peut se produire.
  • La LSUnit ne sait rien de la hiérarchie des caches et des types de mémoire.
  • La LSUnit ne sait pas comment identifier les opérations de sérialisation et les barrières mémoire.

La LSUnit ne tente pas de prédire si un chargement ou un stockage atteint ou manque le cache L1. Elle sait seulement si une instruction "MayLoad" et/ou "MayStore". Pour les chargements, le modèle de planification fournit une latence de chargement à utilisation "optimiste" (qui correspond généralement à la latence de chargement à utilisation lorsque il y a un succès dans le L1D).

llvm-mca ne connaît pas (en soi) les opérations de sérialisation ou les instructions de type barrière mémoire. La LSUnit utilisait auparavant de manière conservatrice les indicateurs "MayLoad", "MayStore" et les effets secondaires non modélisés d'une instruction pour déterminer si une instruction devait être traitée comme une barrière mémoire. C'était inexact en général et cela a été modifié de sorte que chaque instruction ait maintenant un indicateur IsAStoreBarrier et IsALoadBarrier. Ces indicateurs sont spécifiques à mca et sont faux par défaut pour chaque instruction. Si une instruction doit avoir l'un de ces indicateurs activé, cela doit être fait dans la classe InstrPostProcess de la cible. Pour un exemple, regardez la méthode X86InstrPostProcess::postProcessInstruction dans llvm/lib/Target/X86/MCA/X86CustomBehaviour.cpp.

Une barrière de chargement/stockage consomme une entrée de la file de chargement/stockage. Une barrière de chargement/stockage impose l'ordre des chargements/stockages. Un chargement plus jeune ne peut pas passer une barrière de chargement. De même, un stockage plus jeune ne peut pas passer une barrière de stockage. Un chargement plus jeune doit attendre que la barrière mémoire/de chargement soit exécutée. Une barrière de chargement/stockage est "exécutée" lorsqu'elle devient la plus ancienne entrée dans la (les) file(s) de chargement/stockage. Cela signifie également, par construction, que tous les chargements/stockages plus anciens ont été exécutés.

En conclusion, l'ensemble complet des règles de cohérence de chargement/stockage sont:

1.
Un stockage ne peut pas passer un stockage précédent.
2.
Un stockage ne peut pas passer un chargement précédent (indépendamment de -noalias).
3.
Un stockage doit attendre qu'une barrière de stockage plus ancienne soit entièrement exécutée.
4.
Un chargement peut passer un chargement précédent.
5.
Un chargement ne peut pas passer un stockage précédent à moins que -noalias ne soit activé.
dd>
6.
Une charge doit attendre qu'une barrière de charge plus ancienne soit entièrement exécutée.

Émission et exécution dans l'ordre

Les processeurs dans l'ordre sont modélisés comme une seule étape InOrderIssueStage. Elle contourne les unités Dispatch, Scheduler et Load/Store. Les instructions sont émises dès que leurs registres opérandes sont disponibles et que les exigences de ressources sont satisfaites. Plusieurs instructions peuvent être émises en un cycle selon la valeur du paramètre IssueWidth dans le modèle de planification de LLVM.

Une fois émises, une instruction est déplacée vers l'ensemble IssuedInst jusqu'à ce qu'elle soit prête à être retirée. llvm-mca garantit que les écritures sont validées dans l'ordre. Cependant, une instruction est autorisée à valider les écritures et à se retirer dans le désordre si la propriété RetireOOO est vraie pour au moins une de ses écritures.

Comportement personnalisé

Étant donné que certaines instructions ne sont pas parfaitement exprimées dans leur modèle de planification, llvm-mca ne parvient pas toujours à les simuler parfaitement. Modifier le modèle de planification n'est pas toujours une option viable (peut-être parce que l'instruction est mal modélisée intentionnellement ou que le comportement de l'instruction est assez complexe). La classe CustomBehaviour peut être utilisée dans ces cas pour forcer une modélisation correcte des instructions (souvent en personnalisant les dépendances de données et en détectant les conflits que llvm-mca ne peut pas connaître).

llvm-mca est livré avec une classe CustomBehaviour générique et plusieurs classes spécifiques à la cible. La classe générique sera utilisée si le drapeau -disable-cb est utilisé ou si une classe CustomBehaviour spécifique à la cible n'existe pas pour cette cible. (La classe générique ne fait rien.) Actuellement, la classe CustomBehaviour ne fait partie que du pipeline dans l'ordre, mais il est prévu de l'ajouter au pipeline dans le désordre à l'avenir.

La méthode principale de CustomBehaviour est checkCustomHazard() qui utilise l'instruction actuelle et une liste de toutes les instructions en cours d'exécution dans le pipeline pour déterminer si l'instruction actuelle doit être émise. En sortie, la méthode renvoie un entier représentant le nombre de cycles pendant lesquels l'instruction actuelle doit s'arrêter (cela peut être une sous-estimation si vous ne connaissez pas le nombre exact et une valeur de 0 représente aucun arrêt).

Si vous souhaitez ajouter une classe CustomBehaviour pour une cible qui n'en a pas encore, référez-vous à une implémentation existante pour voir comment la configurer. Les classes sont implémentées dans le backend spécifique à la cible (par exemple, /llvm/lib/Target/AMDGPU/MCA/) afin qu'elles puissent accéder aux symboles du backend.

Gestionnaire d'instruments

Sur certaines architectures, les informations de planification de certaines instructions ne contiennent pas toutes les informations requises pour identifier la classe de planification la plus précise. Par exemple, des données pouvant avoir un impact sur la planification peuvent être stockées dans des registres CSR.

Un exemple est RISCV, où les valeurs dans des registres tels que vtype et vl modifient le comportement de planification des instructions vectorielles. Comme MCA ne suit pas les valeurs des registres, les commentaires d'instruments peuvent être utilisés pour spécifier ces valeurs.

La fonction principale d'InstrumentManager est getSchedClassID() qui a accès à l'MCInst et à tous les instruments actifs pour cet MCInst. Cette fonction peut utiliser les instruments pour remplacer la classe de planification de l'MCInst.

Sur RISCV, les commentaires d'instruments contenant des informations LMUL sont utilisés par getSchedClassID() pour mapper une instruction vectorielle et le LMUL actif à la classe de planification de l'pseudo-instruction qui décrit cette instruction de base et le LMUL actif.

Vues personnalisées

llvm-mca est livré avec plusieurs Vues telles que la Vue Chronologique et la Vue Résumé. Ces Vues sont génériques et peuvent fonctionner avec la plupart (sinon toutes) des cibles. Si vous souhaitez ajouter une nouvelle Vue à llvm-mca et qu'elle ne nécessite aucune fonctionnalité backend qui ne soit pas déjà exposée via les classes de la couche MC (MCSubtargetInfo, MCInstrInfo, etc.), veuillez l'ajouter au répertoire /tools/llvm-mca/View/. Cependant, si votre nouvelle Vue est spécifique à la cible ET nécessite des symboles ou des fonctionnalités backend non exposés, vous pouvez la définir dans le répertoire /lib/Target/<TargetName>/MCA/.

Pour activer cette Vue spécifique à la cible, vous devrez utiliser la classe CustomBehaviour de cette cible pour remplacer les méthodes CustomBehaviour::getViews(). Il existe 3 variantes de ces méthodes en fonction de l'endroit où vous souhaitez que votre Vue apparaisse dans la sortie : getStartViews(), getPostInstrInfoViews(), et getEndViews(). Ces méthodes renvoient un vecteur de Vues, vous voudrez donc renvoyer un vecteur contenant toutes les Vues spécifiques à la cible en question.

Étant donné que ces Vues spécifiques à la cible (et dépendantes du backend) nécessitent les variantes CustomBehaviour::getViews(), ces Vues ne seront pas activées si le drapeau -disable-cb est utilisé.

L'activation de ces Vues personnalisées n'affecte pas les Vues non personnalisées (génériques). Continuez à utiliser les arguments de ligne de commande habituels pour activer / désactiver ces Vues.
