NOM

lloadd - Daemon équilibreur de charge LDAP

SYNTAXE

/usr/lib/lloadd [-4|-6] [-d niveau-débogage] [-f fichier-config-lloadd] [-h URLs] [-n nom-service] [-s niveau-syslog] [-l utilisateur-local-syslog] [-o option[=valeur]] [-r répertoire] [-u utilisateur] [-g groupe]

DESCRIPTION

Lloadd est le démon LDAP autonome. Il écoute les connexions LDAP sur un nombre quelconque de ports (par défaut 389), redirigeant les opérations LDAP qu'il reçoit sur ces connexions pour être traitées par les backends configurés. lloadd est typiquement invoqué au démarrage, généralement à partir de /etc/rc.local. Au démarrage, lloadd se divise en un processus enfant et se détache du tty appelant. S'il est configuré dans le fichier de configuration, le processus lloadd inscrira son ID de processus (voir getpid(2)) dans un fichier .pid, ainsi que les options de la ligne de commande lors de l'invocation dans un fichier .args (voir lloadd.conf(5)). Si l'indicateur -d est fourni, même avec un argument zéro, lloadd ne se divisera pas et ne se détachera pas du terminal appelant.

Voir le « Guide de l'administrateur OpenLDAP » pour plus de détails sur lloadd.

OPTIONS

-4
Écoute uniquement sur les adresses IPv4.
-6
Écoute uniquement sur les adresses IPv6.
-d niveau-débogage
Active le débogage tel que défini par niveau-débogage. Si cette option est spécifiée, même avec un argument zéro, lloadd ne se divisera pas et ne se détachera pas du terminal appelant. Certains messages généraux de fonctionnement et d'état sont affichés pour toute valeur de niveau-débogage. niveau-débogage est considéré comme une chaîne de bits, chaque bit correspondant à un type différent d'informations de débogage. Voir <ldap_log.h> pour les détails. Des tableaux séparés par des virgules de noms conviviaux peuvent être spécifiés pour sélectionner la sortie de débogage des informations de débogage correspondantes. Tous les noms reconnus par la directive loglevel décrite dans lloadd.conf(5) sont pris en charge. Si niveau-débogage est ?, une liste des niveaux de débogage installés est affichée et lloadd se termine.

N'oubliez pas que si vous activez la journalisation des paquets, les paquets contenant des mots de passe de liaison seront affichés. Par conséquent, si vous redirigez le journal vers un fichier journal, ce fichier doit être protégé en lecture.

-s niveau-syslog
Cette option indique à lloadd à quel niveau de débogage les instructions de débogage doivent être journalisées dans le service syslog(8). La valeur niveau-syslog peut être définie sur toute valeur ou combinaison autorisée par le commutateur -d. Lloadd enregistre tous les messages sélectionnés par niveau-syslog au niveau de gravité DEBUG de syslog(3), sur l'unité spécifiée avec -l.
-n nom-service
Spécifie le nom du service pour la journalisation et d'autres usages. Par défaut, le nom de base de argv[0], c'est-à-dire : « lloadd ».
-l utilisateur-local-syslog
Sélectionne l'utilisateur local du service syslog(8). La valeur peut être LOCAL0 à LOCAL7, ainsi que USER et DAEMON. Par défaut, c'est LOCAL4. Cependant, cette option n'est autorisée que sur les systèmes qui prennent en charge les utilisateurs locaux avec le service syslog(8). La journalisation vers syslog(8) se produit au niveau de gravité « DEBUG ».
-f fichier-config-lloadd
Spécifie le fichier de configuration de lloadd. Par défaut, il s'agit de /etc/openldap/lloadd.conf.
-h liste-URLs
lloadd servira par défaut ldap:/// (LDAP sur TCP sur toutes les interfaces au port LDAP par défaut). C'est-à-dire qu'il se liera en utilisant INADDR_ANY et le port 389. L'option -h peut être utilisée pour spécifier des URL LDAP (et d'autres schémas) à servir. Par exemple, si lloadd reçoit -h « ldap://127.0.0.1:9009/ ldaps:/// ldapi:/// », il écoutera sur 127.0.0.1:9009 pour LDAP, 0.0.0.0:636 pour LDAP sur TLS, et LDAP sur IPC (sockets de domaine Unix). L'hôte 0.0.0.0 représente INADDR_ANY (toutes les interfaces). Une liste d'URL séparées par des espaces est attendue. Les URL doivent être des schémas LDAP, PLDAP, LDAPS, PLDAPS ou LDAPI, et généralement sans DN ni autres paramètres optionnels (sauf comme discuté ci-dessous). La prise en charge des trois derniers schémas dépend des options de configuration sélectionnées. Les hôtes peuvent être spécifiés par nom ou par formats d'adresse IPv4 et IPv6. Les ports, s'ils sont spécifiés, doivent être numériques. Le port par défaut pour ldap:// est 389 et le port par défaut pour ldaps:// est 636, idem pour les variantes avec proxy activé.

Les schémas d'URL PLDAP et PLDAPS fournissent la prise en charge de la version 2 du protocole proxy HAProxy, qui permet à un serveur d'équilibrage de charge ou à un serveur proxy de fournir l'adresse IP du client distant à slapd pour être utilisée pour le contrôle d'accès ou la journalisation. Les ports configurés pour PLDAP ou PLDAPS n'accepteront que les connexions qui incluent l'en-tête de protocole proxy nécessaire. Les connexions à ces ports doivent être restreintes au niveau réseau aux seuls équilibreurs de charge ou proxies approuvés pour éviter l'usurpation d'adresses IP de clients par des tiers.

Pour le moment, l'équilibreur de charge n'agit sur aucune adresse enregistrée.

Pour LDAP sur IPC, nom est le nom du socket, et aucun port n'est requis, ni autorisé ; notez que les séparateurs de répertoire doivent être encodés en URL, comme tout autre caractère spécial pour les URL ; ainsi le socket


/usr/local/var/ldapi

doit être spécifié comme


ldapi://%2Fusr%2Flocal%2Fvar%2Fldapi

L'emplacement par défaut pour le socket IPC est /var/lib/openldap/run/ldapi

-r répertoire
Spécifie un répertoire qui deviendra le répertoire racine. lloadd changera le répertoire de travail actuel vers ce répertoire, puis effectuera un chroot(2) vers ce répertoire. Cela est fait après l'ouverture des écoutes mais avant la lecture de tout fichier de configuration ou l'initialisation de tout backend. Lorsqu'il est utilisé comme mécanisme de sécurité, il doit être utilisé conjointement avec les options -u et -g.
-u utilisateur
lloadd exécutera lloadd avec le nom d'utilisateur ou l'ID spécifié, et la liste des groupes supplémentaires de cet utilisateur telle que définie avec initgroups(3). L'ID de groupe est également modifié pour correspondre au gid de cet utilisateur, sauf si l'option -g est utilisée pour outrepasser. Notez que lorsqu'il est utilisé avec -r, lloadd utilisera la base de données des utilisateurs dans l'environnement chroot.
-g groupe
lloadd s'exécutera avec le nom ou l'ID du groupe spécifié. Notez que lorsqu'il est utilisé avec -r, lloadd utilisera la base de données des groupes dans l'environnement chroot.
-o option[=valeur]
Cette option fournit un moyen générique de spécifier des options sans avoir besoin de réserver une lettre distincte pour chacune.

Elle prend en charge les options suivantes :

slp={on|off|slp-attributs}
Lorsque le support SLP est compilé dans lloadd, désactivez-le (off),
activez-le en vous enregistrant auprès des DA SLP sans attributs SLP spécifiques (on), ou avec des attributs SLP spécifiques slp-attributs qui doivent être une définition de liste d'attributs SLP conformément à la norme SLP.

Par exemple, « slp=(tree=production),(server-type=OpenLDAP),(server-version=2.4.15) » s'enregistre auprès des DA SLP avec les trois attributs SLP tree, server-type et server-version qui ont les valeurs indiquées ci-dessus. Cela permet de rechercher spécifiquement auprès des DA SLP les serveurs LDAP détenant l'arbre production en cas de multiples arbres disponibles.

e compilé en tant que module chargeable de slapd. Dans ce cas, il peut être chargé comme suit :

    moduleload path/to/lloadd.la
    backend lload
    listen "listening URLs"

Cela permet à lloadd de fournir des fonctionnalités supplémentaires via le processus hôte slapd, comme l'accès aux statistiques d'exécution dans cn=monitor et à la configuration dynamique de cn=config.

Les sockets d'écoute spécifiés seront sous le contrôle direct de lloadd et doivent être différents des sockets sur lesquels slapd est configuré pour écouter. Les clients se connectant à ceux-ci sont complètement séparés des clients LDAP réguliers se connectant aux sockets slapd habituels - les clients lloadd n'ont aucun accès aux bases de données slapd, de même, le trafic des clients slapd ne se propage en aucun cas aux serveurs backend lloadd.

INTERFACE CN=MONITOR

Dans le cadre de l'interface cn=monitor de lloadd, il est possible de fermer une connexion client gérée en écrivant dans l'entrée correspondante, en remplaçant l'attribut olmConnectionState par la valeur closing. Ceci est soumis aux ACL configurées sur la base de données moniteur. Le serveur enverra un Avis de Déconnexion au client, refusera toute nouvelle opération et, une fois toutes les opérations en attente terminées, fermera la connexion.

Par exemple, pour fermer la connexion numéro 42 :

    dn: cn=connection 42,cn=incoming connections,cn=load balancer,cn=backends,cn=monitor
    changetype: modify
    replace: olmConnectionState
    olmConnectionState: closing

EXEMPLES

Pour démarrer lloadd et lui faire se détacher du terminal et commencer à équilibrer la charge des serveurs LDAP définis dans le fichier de configuration par défaut, tapez simplement :

/usr/lib/lloadd

Pour démarrer lloadd avec un fichier de configuration alternatif, et activer un débogage volumineux qui sera imprimé sur la sortie d'erreur standard, tapez :

/usr/lib/lloadd -f /var/tmp/lloadd.conf -d 255

Pour démarrer lloadd en tant que module à l'intérieur d'un processus slapd écoutant sur ldap://:1389 et ldaps://, mettez ce qui suit dans votre slapd.conf (ou son équivalent dans cn=config) :

    moduleload lloadd.la
    backend lload
    listen "ldap://:1389 ldaps://"
