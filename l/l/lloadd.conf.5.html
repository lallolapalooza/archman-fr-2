LLOADD.CONF(5) Manuel des formats de fichiers LLOADD.CONF(5)

NOM

lloadd.conf - fichier de configuration pour lloadd, le démon LDAP autonome

SYNTAXE

/etc/openldap/lloadd.conf

DESCRIPTION

Le fichier /etc/openldap/lloadd.conf contient des informations de configuration pour le démon lloadd(8).

Le fichier lloadd.conf est constitué d'une série d'options de configuration globales qui s'appliquent à lloadd dans son ensemble (y compris tous les backends), suivies de zéro ou plusieurs définitions de backend qui contiennent des informations spécifiques sur la manière de contacter une instance de backend. Les options de configuration ne sont pas sensibles à la casse ; leur valeur, au cas par cas, peut être sensible à la casse.

Le format général de lloadd.conf est le suivant :

    # commentaire - ces options s'appliquent au serveur dans son ensemble
    <options de configuration globales>
    # première définition de backend
    backend-server <définition du backend 1>
    # définitions de backends subséquentes
    ...

Autant de serveurs de backend que désiré peuvent être configurés.

Si une ligne commence par un espace blanc, elle est considérée comme une continuation de la ligne précédente. Aucune ligne physique ne doit dépasser 2000 octets.

Les lignes vides et les lignes de commentaire commençant par un caractère '#' sont ignorées. Remarque : les lignes de continuation sont déroulées avant que le traitement des commentaires ne soit appliqué.

Les arguments des lignes de configuration sont séparés par des espaces blancs. Si un argument contient des espaces blancs, il doit être entouré de guillemets doubles. Si un argument contient un guillemet double (`"') ou un caractère antislash (`\'), le caractère doit être précédé d'un antislash.

Les options de configuration spécifiques disponibles sont discutées ci-dessous dans les Options de configuration globales et Options générales de backend. Reportez-vous au « OpenLDAP Administrator's Guide » pour plus de détails sur le fichier de configuration de lloadd.

INTÉGRATION SLAPD

Notez que lorsque lloadd est configuré en tant que module slapd, toute option portant le même nom qu'une option dans slapd.conf(5), l'interprétation de slapd prévaut et l'option lloadd mentionnée n'est pas disponible directement via slapd.conf(5), elle devrait plutôt être configurée via un attribut dédié dans cn=config. En particulier, à moins que l'option TLSShareSlapdCTX ne soit définie, lloadd conserve son propre contexte TLS qui ne peut être configuré qu'à travers la configuration dynamique.

Une option supplémentaire est disponible lors de l'exécution en tant que module slapd :

listen <URIs d'écoute>
Les URI sur lesquelles le module Load Balancer doit écouter. Ne doivent pas chevaucher ceux que slapd utilise pour ses propres sockets d'écoute. L'attribut cn=config associé est olcBkLloadListen avec chaque URI fournie comme valeur distincte. Aucune modification de cet attribut après le démarrage du serveur ne prendra effet avant son redémarrage.

OPTIONS DE CONFIGURATION GLOBALE

Les options décrites dans cette section s'appliquent à tous les backends. Les arguments qui doivent être remplacés par du texte réel sont affichés entre crochets <>.

argsfile <nom de fichier>
Le nom (absolu) d'un fichier qui contiendra la ligne de commande du serveur lloadd (nom du programme et options).
concurrency <entier>
Spécifie un niveau de concurrence souhaité. Fourni au système de threads sous-jacent comme indice. Par défaut, aucun indice n'est fourni.
feature <fonctionnalité> [...]
Active des fonctionnalités supplémentaires prises en charge par le Load Balancer LDAP. Les fonctionnalités prises en charge sont :
proxyauthz
lors de la procuration d'une opération, passe l'identité autorisée du client en utilisant le contrôle d'autorisation par procuration (RFC 4370). Aucun contrôle n'est ajouté à l'opération si elle est initiée par un client dont l'identité liée correspond à l'identité configurée dans bindconf (aucune normalisation du DN n'est tentée).

Si des liaisons SASL sont émises par des clients et que cette fonctionnalité est activée, les serveurs backend doivent prendre en charge l'opération étendue LDAP "Who Am I ?" pour que le Load Balancer puisse détecter la bonne identité d'autorisation.

include <nom de fichier>
Lit des informations de configuration supplémentaires à partir du fichier donné avant de continuer avec la ligne suivante du fichier actuel.
io-threads <entier>
Spécifie le nombre de threads à utiliser pour le gestionnaire de connexion. La valeur par défaut est 1 et convient généralement pour jusqu'à 16 cœurs de processeur. La valeur doit être une puissance de 2.

Si modifié après le démarrage du serveur, un changement de cette option ne prendra effet qu'après le redémarrage du serveur.

logfile <nom de fichier>
Spécifie un fichier pour enregistrer les messages de débogage de lloadd. Par défaut, ces messages ne vont qu'à stderr, ne sont enregistrés nulle part ailleurs et sont sans rapport avec les messages exposés par le
logfile-format debug | syslog-utc | syslog-localtime
Spécifie le format du préfixe pour les messages écrits dans le fichier journal. Le format de débogage est le format normal utilisé pour les messages de débogage de slapd, avec une horodatage en hexadécimal, suivi d'un identifiant de thread. Les autres options consistent à utiliser des préfixes de style syslog(3), avec des horodatages en UTC ou dans le fuseau horaire local. Le format par défaut est le format de débogage. Paramètre de configuration loglevel. La spécification d'un fichier journal copie les messages vers stderr et le fichier journal.
logfile-only on | off
Spécifie que les messages de débogage doivent uniquement aller vers le fichier journal configuré, et non vers stderr.
logfile-rotate <max> <Mbytes> <heures>
Spécifie la rotation automatique du fichier journal configuré comme nombre maximal d'anciens fichiers journaux à conserver, une taille maximale en mégaoctets autorisée pour un fichier journal avant rotation, et un âge maximal en heures pour qu'un fichier journal soit utilisé avant rotation. Le nombre maximal doit être compris entre 1 et 99. La définition de Mbytes ou heures à zéro désactive respectivement la vérification de la taille ou de l'âge. Au moins l'un des champs Mbytes ou heures doit être non nul. Par défaut, aucune rotation automatique ne sera effectuée.
loglevel <entier> [...]
Spécifie le niveau auquel les instructions de débogage et les statistiques d'opérations doivent être enregistrées dans syslog (actuellement dans la facilité LOG_LOCAL4 de syslogd(8)). Elles doivent être considérées comme des sous-systèmes plutôt que comme des niveaux de journalisation de plus en plus détaillés. Certains messages de priorité plus élevée sont enregistrés indépendamment du loglevel configuré dès qu'une journalisation est configurée. Les niveaux de journalisation sont additifs, et les niveaux disponibles sont :
1
(0x1 trace) trace des appels de fonction
2
(0x2 packets) débogage de la gestion des paquets
4
(0x4 args) débogage intensif (arguments de fonction)
8
(0x8 conns) gestion des connexions
16
(0x10 BER) affichage des paquets envoyés et reçus
64
(0x40 config) traitement du fichier de configuration
256
(0x100 stats) connexions, opérations LDAP, résultats (recommandé)
512
(0x200 stats2) entrées du journal de statistiques envoyées
32768
(0x8000 none) uniquement les messages qui sont enregistrés quel que soit le niveau de journalisation défini
Le niveau de journalisation souhaité peut être saisi sous forme d'un seul entier combinant les niveaux souhaités (ORés), en notation décimale ou hexadécimale, comme une liste d'entiers (qui sont ORés en interne), ou comme une liste des noms affichés entre parenthèses, tel que 
    loglevel 5

13 loglevel 0x201 loglevel 512 1 loglevel 0x200 0x1 loglevel stats trace

sont équivalents. Le mot-clé any peut être utilisé comme raccourci pour activer la journalisation à tous les niveaux (équivalent à -1). Le mot-clé none, ou sa représentation entière équivalente, provoque l'enregistrement des messages qui sont journalisés quelle que soit la valeur du loglevel configuré. En fait, si le loglevel est défini sur 0, aucune journalisation n'a lieu, donc au moins le niveau none est requis pour que les messages de haute priorité soient journalisés.

Le loglevel est défini par défaut sur stats. Ce niveau doit généralement également être inclus lors de l'utilisation d'autres niveaux de journalisation, afin d'aider à analyser les journaux.

pidfile <nomdefichier>
Le nom (absolu) d'un fichier qui contiendra l'identifiant de processus du serveur lloadd (voir getpid(2)).
sockbuf_max_incoming_client <entier>
Spécifie la taille maximale des PDU LDAP acceptés provenant des clients. La valeur par défaut est 262143.
sockbuf_max_incoming_upstream <entier>
Spécifie la taille maximale des PDU LDAP acceptés provenant des connexions en amont. La valeur par défaut est 4194303.
tcp-buffer [listener=<URL>] [{read|write}=]<taille>
Spécifie la taille du tampon TCP. Une valeur globale pour les tampons TCP de lecture et d'écriture liés à n'importe quel écouteur est définie, sauf si l'écouteur est explicitement spécifié, ou si les qualificateurs read ou write sont utilisés. Voir tcp(7) pour plus de détails. Notez que certains systèmes d'exploitation implémentent un réglage automatique des tampons TCP.
threads <entier>
Spécifie la taille maximale du pool de threads principal. La valeur par défaut est 16 ; la valeur minimale est 2.
threadqueues <entier>
Spécifie le nombre de files d'attente de travail à utiliser pour le pool de threads principal. La valeur par défaut est 1 et elle est généralement adéquate pour jusqu'à 8 cœurs de processeur. La valeur ne doit pas dépasser le nombre de processeurs du système.
max_pdus_per_cycle <entier>
Si défini sur 0, les PDU sont gérés directement par les threads d'E/S, sinon une tâche est mise en file d'attente pour être récupérée par le pool de threads. Cette tâche traitera les PDU de la connexion jusqu'à ce qu'il n'y ait plus de données à lire ou que cette limite soit atteinte, moment auquel le thread d'E/S pourra la reprendre. Des valeurs très élevées peuvent entraîner l'épuisement de certaines connexions dans un environnement à très haut débit. La valeur par défaut est 1000.
client_max_pending <entier>
Fera en sorte que l'équilibreur de charge limite le nombre d'opérations inachevées pour chaque connexion client. La valeur par défaut est 0, illimité.
iotimeout <entier>
Spécifie le nombre de millisecondes à attendre avant de fermer de force une connexion avec une écriture en cours. Cela permet une récupération plus rapide dans diverses conditions de blocage réseau. Un iotimeout de 0 désactive cette fonctionnalité. La valeur par défaut est 10000.
write_coherence <entier>
Spécifie le nombre de secondes après la fin d'une opération d'écriture pendant lequel lloadd dirigera exclusivement les opérations vers le dernier backend sélectionné. Une opération d'écriture est tout ce qui n'est pas traité en interne (certaines exops, abandon), à l'exception des opérations de recherche, de comparaison et de liaison. Les opérations de liaison réinitialisent également cette restriction. La valeur par défaut est 0, les opérations d'écriture ne restreignent pas la sélection. Lorsqu'elle est négative, la restriction n'est pas limitée dans le temps et persiste jusqu'à la prochaine liaison.
restrict_exop <OID> <action>
Indique à lloadd qu'une opération étendue avec un OID donné doit être gérée d'une manière spécifique. L'OID 1.1 est spécial, il définit une valeur par défaut (uniquement pour les opérations non gérées en interne). La signification de l'argument <action> est la même que pour restrict_control ci-dessous.
restrict_control <OID> <action>
Indique à lloadd qu'un contrôle avec un OID donné attaché à une opération quelconque doit être géré d'une manière spécifique selon l'argument <action>. Actuellement, seules les opérations transmises intactes sont inspectées de cette manière, en particulier, les contrôles sur les opérations de liaison et étendues ne sont **pas** vérifiés.

Par ordre de priorité décroissante (l'action avec la priorité la plus élevée l'emporte), voici l'action effectuée :

reject
les opérations qui portent ce contrôle seront rejetées.
connection
une fois qu'un upstream est sélectionné, toutes les opérations futures de ce client seront dirigées vers la même connexion. Utile lorsque l'état est partagé entre le client et l'upstream que l'équilibreur de charge ne suit pas.
backend
comme write, sauf que cela n'expire pas.
write
ceci est traité comme une opération d'écriture (voir write_coherence) ci-dessus.
ignore
n'influence pas les restrictions, utile lors de la modification de la valeur par défaut globale des exops. C'est le traitement par défaut pour les exops/contrôles non gérés en interne par l'équilibreur de charge.

OPTIONS TLS

Si lloadd est compilé avec la prise en charge de la couche de transport sécurisé (TLS), des options supplémentaires peuvent être spécifiées.

TLSShareSlapdCTX { on | off }
Si défini sur non (par défaut), lloadd utilisera son propre contexte TLS (nécessite d'être configuré via cn=config sauf si lloadd est exécuté comme un démon autonome). Si activé, les options pour slapd s'appliquent alors, car le contexte TLS de slapd est utilisé.

Les options suivantes ne sont disponibles que lorsque compilé en tant que démon autonome. Lorsqu'il est compilé en tant que module slapd(8), les équivalents cn=config doivent être utilisés si un contexte TLS distinct pour le module est nécessaire, sinon utilisez l'option TLSShareSlapdCTX.

TLSCipherSuite <spécification-suite-chiffrement>
Permet de configurer les chiffrements qui seront acceptés et leur ordre de préférence. <spécification-suite-chiffrement> doit être une spécification de chiffrement pour la bibliothèque TLS utilisée (OpenSSL, GnuTLS ou Mozilla NSS). Exemple :
OpenSSL:
TLSCipherSuite HIGH:MEDIUM:+SSLv2
GnuTLS:
TLSCiphersuite SECURE256:!AES-128-CBC

Pour vérifier quels chiffrements une spécification donnée sélectionne dans OpenSSL, utilisez :

openssl ciphers -v <spécification-suite-chiffrement>

Avec GnuTLS, les spécifications disponibles peuvent être trouvées dans la page de manuel de gnutls-cli(1) (voir la description de l'option --priority).

Dans les anciennes versions de GnuTLS, où gnutls-cli ne prend pas en charge l'option --priority, vous pouvez obtenir la liste — plus limitée — des chiffrements en appelant :

gnutls-cli -l

Lors de l'utilisation de Mozilla NSS, les spécifications de suite de chiffrement OpenSSL sont utilisées et traduites dans le format utilisé en interne par Mozilla NSS. Il n'y a pas de moyen facile de lister les suites de chiffrement depuis la ligne de commande. La liste faisant autorité se trouve dans le code source de Mozilla NSS dans le fichier

        static const SSLCipherSuiteInfo suiteInfo[]
TLSCACertificateFile <nomdefichier>
Spécifie le fichier qui contient les certificats de toutes les Autorités de Certification que lloadd reconnaîtra. Le certificat de l'AC qui a signé le certificat du serveur doit être inclus parmi ces certificats. Si l'AC signataire n'était pas une AC de niveau supérieur (racine), les certificats pour toute la séquence d'AC, de l'AC signataire à l'AC de niveau supérieur, doivent être présents. Les certificats multiples sont simplement ajoutés au fichier ; l'ordre n'est pas significatif.
TLSCACertificatePath <chemin>
Spécifie le chemin d'un répertoire contenant les certificats d'Autorité de Certification dans des fichiers individuels séparés. Habituellement, un seul de ces deux, ou TLSCACertificateFile, est utilisé. Cette directive n'est pas prise en charge lors de l'utilisation de GnuTLS.

Lors de l'utilisation de Mozilla NSS, <chemin> peut contenir une base de données de certificats/clés Mozilla NSS. Si <chemin> contient une base de données de certificats/clés Mozilla NSS et des fichiers de certificats d'AC, OpenLDAP utilisera la base de données de certificats/clés et ignorera les fichiers de certificats d'AC.

TLSCertificateFile <nomdefichier>
Spécifie le fichier contenant le certificat du serveur lloadd.

Lors de l'utilisation de Mozilla NSS, si une base de données de certificats/clés est utilisée (spécifiée avec TLSCACertificatePath), TLSCertificateFile spécifie le nom du certificat à utiliser :

TLSCertificateFile Certificat-Serveur
Si vous utilisez un jeton autre que le jeton interne intégré, spécifiez d'abord le nom du jeton, suivi d'un deux-points : 
TLSCertificateFile mon_matériel_périphérique:Certificat-Serveur
Utilisez certutil -L pour lister les certificats par nom : 
certutil -d /chemin/vers/certdbdir -L
TLSCertificateKeyFile <nomdefichier>
Spécifie le fichier contenant la clé privée du serveur lloadd qui correspond au certificat stocké dans le fichier TLSCertificateFile. Actuellement, la clé privée ne doit pas être protégée par un mot de passe, il est donc d'une importance capitale qu'elle soit protégée avec soin.

Lors de l'utilisation de Mozilla NSS, TLSCertificateKeyFile spécifie le nom d'un fichier contenant le mot de passe de la clé pour le certificat s

spécifié avec TLSCertificateFile. La commande modutil peut être utilisée pour désactiver la protection par mot de passe de la base de données de certificats/clés. Par exemple, si TLSCACertificatePath spécifie /etc/openldap/certdb comme emplacement de la base de données de certificats/clés, utilisez modutil pour changer le mot de passe en une chaîne vide :

modutil -dbdir /etc/openldap/certdb -changepw 'NSS Certificate DB'
Vous devez posséder l'ancien mot de passe, le cas échéant. Ignorez l'AVERTISSEMENT concernant le navigateur en cours d'exécution. Appuyez sur 'Entrée' pour le nouveau mot de passe.
TLSDHParamFile <nom_fichier>
Cette directive spécifie le fichier contenant les paramètres pour l'échange de clés éphémères Diffie-Hellman. Ceci est requis pour utiliser un certificat DSA sur le serveur, ou un certificat RSA manquant de l'utilisation de clé « chiffrement de clé ». Notez que la définition de cette option peut également activer les échanges de clés Diffie-Hellman anonymes dans certaines suites de chiffrement non par défaut. Les échanges de clés anonymes doivent généralement être évités car ils ne fournissent aucune authentification réelle du client ou du serveur et aucune protection contre les attaques de type « man-in-the-middle ». Vous devriez ajouter « !ADH » à vos suites de chiffrement pour vous assurer que ces suites ne sont pas utilisées. Lors de l'utilisation de Mozilla NSS, ces paramètres sont toujours générés aléatoirement, cette directive est donc ignorée.
TLSECName <nom>
Spécifie le nom d'une courbe à utiliser pour l'échange de clés éphémères Diffie-Hellman sur courbe elliptique. Ceci est requis pour activer les algorithmes ECDHE dans OpenSSL. Cette option n'est pas utilisée avec GnuTLS ; les courbes peuvent être choisies dans la spécification de la suite de chiffrement GnuTLS. Cette option est également ignorée pour Mozilla NSS.
TLSProtocolMin <majeur>[.<mineur>]
Spécifie la version minimale du protocole SSL/TLS qui sera négociée. Si le serveur ne prend pas en charge au moins cette version, le handshake SSL échouera. Pour exiger TLS 1.x ou supérieur, définissez cette option à 3.(x+1), par exemple : 
TLSProtocolMin 3.2

exigerait TLS 1.1. La spécification d'un minimum supérieur à celui pris en charge par l'implémentation OpenLDAP entraînera l'exigence du niveau le plus élevé qu'elle prend en charge. Cette directive est ignorée avec GnuTLS.

TLSRandFile <nom_fichier>
Spécifie le fichier à partir duquel obtenir des bits aléatoires lorsque /dev/[u]random n'est pas disponible. Généralement défini sur le nom de la socket EGD/PRNGD. La variable d'environnement RANDFILE peut également être utilisée pour spécifier le nom du fichier. Cette directive est ignorée avec GnuTLS et Mozilla NSS.
TLSVerifyClient <niveau>
Spécifie quelles vérifications effectuer sur les certificats clients lors d'une session TLS entrante, le cas échéant. Le <niveau> peut être spécifié par l'un des mots-clés suivants :
never
C'est la valeur par défaut. lloadd ne demandera pas de certificat au client.
allow
Le certificat client est demandé. Si aucun certificat n'est fourni, la session se poursuit normalement. Si un certificat invalide est fourni, il sera ignoré et la session se poursuivra normalement.
try
Le certificat client est demandé. Si aucun certificat n'est fourni, la session se poursuit normalement. Si un certificat invalide est fourni, la session est immédiatement terminée.
demand | hard | true
Ces mots-clés sont tous équivalents, pour des raisons de compatibilité. Le certificat client est demandé. Si aucun certificat n'est fourni, ou si un certificat invalide est fourni, la session est immédiatement terminée.
TLSCRLCheck <niveau>
Spécifie si la Liste de Révocation de Certificats (CRL) de l'AC doit être utilisée pour vérifier si les certificats clients n'ont pas été révoqués. Ceci nécessite que le paramètre TLSCACertificatePath soit défini. Cette directive est ignorée avec GnuTLS et Mozilla NSS. <niveau> peut être spécifié par l'un des mots-clés suivants :
none
Aucune vérification de CRL n'est effectuée.
peer
Vérifie la CRL du certificat du pair.
all
Vérifie la CRL pour toute la chaîne de certificats.
TLSCRLFile <nom_fichier>
Spécifie un fichier contenant une Liste de Révocation de Certificats à utiliser pour vérifier que les certificats n'ont pas été révoqués. Cette directive n'est valide que lors de l'utilisation de GnuTLS et Mozilla NSS.

CONFIGURATION DU BACKEND

Les options dans cette section décrivent comment lloadd se connecte et s'authentifie auprès des serveurs backend. Les backends sont organisés en groupes (tiers). Les backends du premier tier sont essayés en premier, si aucun d'eux n'est accessible, le tier suivant est essayé de la même manière. S'il y a un backend dans le tier qui a des connexions appropriées, mais qu'elles sont occupées, aucun tier supplémentaire n'est consulté. Ceci est utile dans les scénarios de haute disponibilité où un groupe de serveurs (par exemple, l'environnement local) devrait être contacté si possible.

Il est supposé que tous les serveurs backend servent les mêmes données. Au démarrage, les connexions configurées sont établies et celles non dédiées à la gestion des requêtes de liaison sont authentifiées auprès du backend en utilisant les informations de l'option bindconf. La configuration d'authentification est partagée entre elles.

bindconf
[bindmethod=simple|sasl] [binddn=<dn>] [saslmech=<mech>] [authcid=<identité>] [authzid=<identité>] [credentials=<motdepasse>] [realm=<realm>] [secprops=<propriétés>] [timeout=<secondes>] [network-timeout=<secondes>] [keepalive=<idle>:<probes>:<interval>] [tcp-user-timeout=<millisecondes>] [tls_cert=<fichier>] [tls_key=<fichier>] [tls_cacert=<fichier>] [tls_cacertdir=<chemin>] [tls_reqcert=never|allow|try|demand] [tls_cipher_suite=<chiffrements>] [tls_crlcheck=none|peer|all] [tls_protocol_min=<majeur>[.<mineur>]]

Spécifie les informations d'identification de liaison que lloadd utilise lors de l'établissement de ses connexions régulières à tous les backends.

Une bindmethod de simple requiert les options binddn et credentials et ne devrait être utilisée que lorsque des services de sécurité adéquats (par exemple, TLS ou IPSEC) sont en place. N'OUBLIEZ PAS : les informations d'identification de liaison simple doivent être en clair ! Une bindmethod de sasl requiert l'option saslmech. Selon le mécanisme, une identité d'authentification et/ou des informations d'identification peuvent être spécifiées en utilisant authcid et credentials. Le paramètre authzid peut être utilisé pour spécifier une identité d'autorisation. Des propriétés de sécurité spécifiques (comme avec le mot-clé sasl-secprops ci-dessus) pour une liaison SASL peuvent être définies avec l'option secprops. Un realm SASL non par défaut peut être défini avec l'option realm.

Le paramètre timeout indique combien de temps une opération peut être en attente d'une réponse (résultat, entrée de recherche, ...) du serveur en secondes. En raison de la manière dont les timeouts sont détectés, le timeout pourrait ne pas être détecté et géré jusqu'à timeout secondes après qu'il se soit produit.

Le paramètre network-timeout définit combien de temps le consommateur attendra pour établir une connexion réseau avec le fournisseur. Une fois qu'une connexion est établie, le paramètre timeout détermine combien de temps le consommateur attendra que la requête Bind initiale s'achève.

Un timeout défini à 0 signifie qu'aucun timeout n'est actif et, par défaut, aucun timeout n'est actif.

Le paramètre keepalive définit les valeurs de idle, probes, et interval utilisées pour vérifier si une socket est active ; idle est le nombre de secondes pendant lesquelles une connexion doit rester inactive avant que TCP ne commence à envoyer des sondes keepalive ; probes est le nombre maximum de sondes keepalive que TCP doit envoyer avant de fermer la connexion ; interval est l'intervalle en secondes entre les sondes keepalive individuelles. Seuls certains systèmes prennent en charge la personnalisation de ces valeurs ; le paramètre keepalive est ignoré sinon et les paramètres globaux du système sont utilisés.

Le paramètre tcp-user-timeout, s'il est non nul, correspond au TCP_USER_TIMEOUT défini sur les connexions ascendantes, remplaçant le paramètre du système d'exploitation. Seuls certains systèmes prennent en charge la personnalisation de ce paramètre ; il est ignoré sinon et les paramètres globaux du système sont utilisés.

OPTIONS DE TIER

tier
<type de tier>

Regroupe les serveurs qui doivent être considérés dans le même essai. Si une connexion viable est trouvée même si elle est occupée, le répartiteur de charge ne passe pas au tier suivant. Le processus de sélection d'une connexion au sein d'un tier dépend du type du tier.


Les types disponibles sont :

roundrobin
Les serveurs sont essayés dans l'ordre et si l'un est sélectionné avec succès, la recherche suivante essaiera à partir de celui qui suit dans la liste.
weighted
Les serveurs backend acceptent une nouvelle option weight=<entier> qui indique à quelle fréquence ils doivent être sélectionnés. Si elle n'est pas spécifiée, le poids est par défaut à 0 et ces backends ont une faible chance d'être sélectionnés même lorsqu'un backend avec un poids non nul est configuré dans le tier. Le processus de sélection est conforme à la RFC2782.
bestof
Comme avec weighted, les backends acceptent l'option weight=<entier>. La latence moyenne multipliée par le weight est mesurée au fil du temps. Le processus de sélection choisit 2 backends au hasard, compare leurs latences pondérées et le backend ayant une meilleure
(plus bas) score est essayé. Si le backend n'est pas disponible (ou est occupé), l'autre backend est essayé, puis les backends sont choisis en ordre circulaire.

Notez que contrairement à weighted, plus le poids est élevé, plus la latence "effective" est élevée et plus la probabilité qu'un backend soit sélectionné est faible.

OPTIONS_BACKEND

backend-server
uri=ldap[s]://<nom_hôte>[:port] [retry=<intervalle_de_réessai_en_ms>] [starttls=yes|critical] [numconns=<connexions>] [bindconns=<connexions>] [max-pending-ops=<opérations>] [conn-max-pending=<opérations>]

Marque le début de la définition d'un backend.

uri spécifie le backend sous forme d'URI LDAP. Si <port> n'est pas fourni, le numéro de port LDAP standard (389 ou 636) est utilisé.

Lloadd tentera de maintenir numconns connexions actives et également bindconns connexions actives dédiées à la gestion des requêtes de liaison client.

Si une erreur se produit sur une connexion fonctionnelle, une nouvelle tentative de connexion est effectuée immédiatement. Si elle se produit lors de l'établissement d'une nouvelle connexion à ce backend, lloadd attendra avant de tenter une nouvelle reconnexion, conformément au paramètre retry (la valeur par défaut est de 5 secondes).

Les opérations seront distribuées entre les connexions du backend (upstreams).

Le paramètre conn-max-pending, sauf s'il est défini sur 0 (la valeur par défaut), limitera le nombre d'opérations non terminées par connexion amont. De même, max-pending-ops limitera le nombre total d'opérations non terminées sur toutes les connexions du backend. 0, la valeur par défaut, signifie qu'aucune limite ne sera imposée pour ce backend.

Le paramètre starttls spécifie l'utilisation de l'opération étendue StartTLS pour établir une session TLS avant de se lier au fournisseur. Si l'argument critical est fourni, la session sera interrompue si la requête StartTLS échoue. Sinon, la session syncrepl se poursuit sans TLS. Le réglage tls_reqcert est défini par défaut sur "demand" et les autres réglages TLS sont définis par défaut de la même manière que les réglages TLS principaux de slapd.

LIMITATIONS

La prise en charge des liaisons SASL en proxy est limitée au mécanisme EXTERNAL (et uniquement pour extraire le DN d'un certificat TLS client s'il est utilisé lors de la dernière renégociation) et aux mécanismes qui ne dépendent ni des métadonnées de connexion (comme Kerberos) ni n'établissent une couche d'intégrité/confidentialité SASL (encore une fois, certains mécanismes Kerberos, DIGEST-MD5 peut négocier cela).
