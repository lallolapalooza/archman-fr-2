LEX(1P) Manuel du programmeur POSIX LEX(1P)

PROLOG

Cette page de manuel fait partie du Manuel du programmeur POSIX. L'implémentation Linux de cette interface peut différer (consultez la page de manuel Linux correspondante pour les détails du comportement sous Linux), ou l'interface peut ne pas être implémentée sous Linux.

NOM

lex — générer des programmes pour des tâches lexicales (DÉVELOPPEMENT)

SYNOPIS

lex [-t] [-n|-v] [fichier...]

DESCRIPTION

L'utilitaire lex générera des programmes C destinés au traitement lexical des entrées caractères, et qui peuvent servir d'interface à yacc. Les programmes C seront générés à partir du code source lex et seront conformes à la norme ISO C, sans dépendre d'un comportement indéfini, non spécifié ou dépendant de l'implémentation, sauf dans les cas où le code est copié directement depuis la source fournie, ou dans des cas documentés par l'implémentation. Habituellement, l'utilitaire lex écrira le programme qu'il génère dans le fichier lex.yy.c ; l'état de ce fichier est indéfini si lex se termine avec un code de sortie non nul. Voir la section DESCRIPTION ÉTENDUE pour une description complète du langage d'entrée lex.

OPTIONS

L'utilitaire lex sera conforme au volume Bases de Définitions de POSIX.1‐2017, Section 12.2, Directives de syntaxe des utilitaires, à l'exception de la Directive 9.

Les options suivantes seront prises en charge :

-n
Supprime le résumé des statistiques habituellement écrit avec l'option -v. Si aucune taille de table n'est spécifiée dans le code source lex et que l'option -v n'est pas spécifiée, alors -n est implicite.
-t
Écrit le programme résultant sur la sortie standard au lieu de lex.yy.c.
-v
Écrit un résumé des statistiques lex sur la sortie standard. (Voir la discussion sur les tailles de table lex dans Définitions dans lex.) Si l'option -t est spécifiée et que -n ne l'est pas, ce rapport sera écrit sur la sortie d'erreur standard. Si des tailles de table sont spécifiées dans le code source lex, et si l'option -n n'est pas spécifiée, l'option -v peut être activée.

OPÉRANDES

L'opérande suivant sera pris en charge :

fichier
Un chemin d'accès à un fichier d'entrée. Si plus d'un de ces opérandes fichier est spécifié, tous les fichiers seront concaténés pour produire un seul programme lex. Si aucun opérande fichier n'est spécifié, ou si un opérande fichier est '-', l'entrée standard sera utilisée.

STDIN

L'entrée standard sera utilisée si aucun opérande fichier n'est spécifié, ou si un opérande fichier est '-'. Voir FICHIERS D'ENTRÉE.

FICHIERS D'ENTRÉE

Les fichiers d'entrée seront des fichiers texte contenant du code source lex, tel que décrit dans la section DESCRIPTION ÉTENDUE.

VARIABLES D'ENVIRONNEMENT

Les variables d'environnement suivantes affecteront l'exécution de lex :

LANG
Fournit une valeur par défaut pour les variables d'internationalisation qui sont non définies ou vides. (Voir le volume Bases de Définitions de POSIX.1‐2017, Section 8.2, Variables d'internationalisation pour la précédence des variables d'internationalisation utilisées pour déterminer les valeurs des catégories de locale.)
LC_ALL
Si définie à une chaîne de caractères non vide, remplace les valeurs de toutes les autres variables d'internationalisation.
LC_COLLATE

Détermine la locale pour le comportement des plages, des classes d'équivalence et des éléments de classement multi-caractères dans les expressions régulières. Si cette variable n'est pas définie à la locale POSIX, les résultats sont indéfinis.
LC_CTYPE
Détermine la locale pour l'interprétation des séquences d'octets de données textuelles comme caractères (par exemple, caractères mono-octet par opposition aux multi-octets dans les arguments et les fichiers d'entrée), et le comportement des classes de caractères dans les expressions régulières. Si cette variable n'est pas définie à la locale POSIX, les résultats sont indéfinis.
LC_MESSAGES

Détermine la locale qui devrait être utilisée pour affecter le format et le contenu des messages de diagnostic écrits sur la sortie d'erreur standard.
NLSPATH
Détermine l'emplacement des catalogues de messages pour le traitement de LC_MESSAGES.

Si l'option -v est spécifiée et que l'option -n ne l'est pas, les statistiques de lex seront également écrites soit sur la sortie standard, soit sur la sortie d'erreur, dans un format dépendant de l'implémentation. Ces statistiques peuvent également être générées si des tailles de table sont spécifiées avec un opérateur '%' dans la section Définitions, tant que l'option -n n'est pas spécifiée.

Un fichier texte contenant du code source C sera écrit dans lex.yy.c, ou sur la sortie standard si l'option -t est présente.

During pattern matching, lex shall search the set of patterns for the single longest possible match. Among rules that match the same number of characters, the rule given first shall be chosen.

The general format of lex source shall be:

Definitions %% Rules %% UserSubroutines

The first "%%" is required to mark the beginning of the rules (regular expressions and actions); the second "%%" is required only if user subroutines follow.

Any line in the Definitions section beginning with a <blank> shall be assumed to be a C program fragment and shall be copied to the external definition area of the lex.yy.c file. Similarly, anything in the Definitions section included between delimiter lines containing only "%{" and "%}" shall also be copied unchanged to the external definition area of the lex.yy.c file.

Any such input (beginning with a <blank> or within "%{" and "%}" delimiter lines) appearing at the beginning of the Rules section before any rules are specified shall be written to lex.yy.c after the declarations of variables for the yylex() function and before the first line of code in yylex(). Thus, user variables local to yylex() can be declared here, as well as application code to execute upon entry to yylex().

The action taken by lex when encountering any input beginning with a <blank> or within "%{" and "%}" delimiter lines appearing in the Rules section but coming after one or more rules is undefined. The presence of such input may result in an erroneous definition of the yylex() function.

C-language code in the input shall not contain C-language trigraphs. The C-language code within "%{" and "%}" delimiter lines shall not contain any lines consisting only of "%}", or only of "%%".

Definitions in lex

Definitions appear before the first "%%" delimiter. Any line in this section not contained between "%{" and "%}" lines and not beginning with a <blank> shall be assumed to define a lex substitution string. The format of these lines shall be:

name substitute

If a name does not meet the requirements for identifiers in the ISO C standard, the result is undefined. The string substitute shall replace the string {name} when it is used in a rule. The name string shall be recognized in this context only when the braces are provided and when it does not appear within a bracket expression or within double-quotes.

In the Definitions section, any line beginning with a <percent-sign> ('%') character and followed by an alphanumeric word beginning with either 's' or 'S' shall define a set of start conditions. Any line beginning with a '%' followed by a word beginning with either 'x' or 'X' shall define a set of exclusive start conditions. When the generated scanner is in a %s state, patterns with no state specified shall be also active; in a %x state, such patterns shall not be active. The rest of the line, after the first word, shall be considered to be one or more <blank>-separated names of start conditions. Start condition names shall be constructed in the same way as definition names. Start conditions can be used to restrict the matching of regular expressions to one or more states as described in Regular Expressions in lex.

Implementations shall accept either of the following two mutually-exclusive declarations in the Definitions section:

%array
Declare the type of yytext to be a null-terminated character array.
%pointer
Declare the type of yytext to be a pointer to a null-terminated character string.

The default type of yytext is implementation-defined. If an application refers to yytext outside of the scanner source file (that is, via an extern), the application shall include the appropriate %array or %pointer declaration in the scanner source file.

Implementations shall accept declarations in the Definitions section for setting certain internal table sizes. The declarations are shown in the following table.


Table: Table Size Declarations in lex

Declaration Description Minimum Value
%p n Number of positions 2500
%n n Number of states 500
%a n Number of transitions 2000
%e n Number of parse tree nodes 1000
%k n Number of packed character classes 1000
%o n Size of the output array 3000

In the table, n represents a positive decimal integer, preceded by one or more <blank> characters. The exact meaning of these table size numbers is implementation-defined. The implementation shall document how these numbers affect the lex utility and how they are related to any output that may be generated by the implementation should limitations be encountered during the execution of lex. It shall be possible to determine from this output which of the table size values needs to be modified to permit lex to successfully generate tables for the input language. The values in the column Minimum Value represent the lowest values conforming implementations shall provide.

Rules in lex

The rules in lex source files are a table in which the left column contains regular expressions and the right column contains actions (C program fragments) to be executed when the expressions are recognized.

ERE action
ERE action
...

The extended regular expression (ERE) portion of a row shall be separated from action by one or more <blank> characters. A regular expression containing <blank> characters shall be recognized under one of the following conditions:

*
The entire expression appears within double-quotes.
*
The <blank> characters appear within double-quotes or square brackets.
*
Each <blank> is preceded by a <backslash> character.

User Subroutines in lex

Anything in the user subroutines section shall be copied to lex.yy.c following yylex().

Regular Expressions in lex

The lex utility shall support the set of extended regular expressions (see the Base Definitions volume of POSIX.1‐2017, Section 9.4, Extended Regular Expressions), with the following additions and exceptions to the syntax:

"..."
Any string enclosed in double-quotes shall represent the characters within the double-quotes as themselves, except that <backslash>-escapes (which appear in the following table) shall be recognized. Any <backslash>-escape sequence shall be terminated by the closing quote. For example, "\01""1" represents a single string: the octal value 1 followed by the character '1'.
<state>r, <state1,state2,...>r

The regular expression r shall be matched only when the program is in one of the start conditions indicated by state, state1, and so on; see Actions in lex. (As an exception to the typographical conventions of the rest of this volume of POSIX.1‐2017, in this case <state> does not represent a metavariable, but the literal angle-bracket characters surrounding a symbol.) The start condition shall be recognized as such only at the beginning of a regular expression.
r/x
The regular expression r shall be matched only if it is followed by an occurrence of regular expression x (x is the instance of trailing context, further defined below). The token returned in yytext shall only match r. If the trailing portion of r matches the beginning of x, the result is unspecified. The r expression cannot include further trailing context or the '$' (match-end-of-line) operator; x cannot include the '^' (match-beginning-of-line) operator, nor trailing context, nor the '$' operator. That is, only one occurrence of trailing context is allowed in a lex regular expression, and the '^' operator only can be used at the beginning of such an expression.
{name}
When name is one of the substitution symbols from the Definitions section, the string, including the enclosing braces, shall be replaced by the substitute val
ue. La valeur de substitution doit être traitée dans l'expression régulière étendue comme si elle était entre parenthèses. Aucune substitution ne se produira si {nom} apparaît dans une expression entre crochets ou entre guillemets doubles.

Dans une ERE, un caractère <backslash> doit être considéré comme le début d'une séquence d'échappement, comme spécifié dans le tableau du volume des Définitions de base de POSIX.1‐2017, Chapitre 5, Notation de format de fichier ('\\', '\a', '\b', '\f', '\n', '\r', '\t', '\v'). De plus, les séquences d'échappement du tableau suivant doivent être reconnues.

Un <nouvelle ligne> littéral ne peut pas apparaître dans une ERE ; la séquence d'échappement '\n' peut être utilisée pour représenter un <nouvelle ligne>. Un <nouvelle ligne> ne sera pas mis en correspondance par un opérateur point.

Les opérateurs d'ancrage ERE '^' et '$' n'apparaissent pas dans le tableau. Avec les expressions régulières lex, ces opérateurs sont limités dans leur utilisation : l'opérateur '^' ne peut être utilisé qu'au début d'une expression régulière entière, et l'opérateur '$' seulement à la fin. Les opérateurs s'appliquent à l'expression régulière entière. Ainsi, par exemple, le modèle "(^abc)|(def$)" est indéfini ; il peut être écrit à la place comme deux règles séparées, l'une avec l'expression régulière "^abc" et l'autre avec "def$", qui partagent une action commune via l'action spéciale '|' (voir ci-dessous). Si le modèle était écrit "^abc|def$", il correspondrait soit à "abc", soit à "def" sur une ligne à part entière.

Contrairement aux règles générales des ERE, l'ancrage embarqué n'est pas autorisé par la plupart des implémentations lex historiques. Un exemple d'ancrage embarqué serait pour des modèles tels que "(^| )foo( |$)" pour mettre en correspondance "foo" lorsqu'il existe comme mot complet. Cette fonctionnalité peut être obtenue en utilisant les fonctionnalités lex existantes :

^foo/[ \n]      |
" foo"/[ \n]    /* Trouvé foo comme mot séparé. */

Notez également que '$' est une forme de contexte final (il est équivalent à "/\n") et en tant que tel ne peut pas être utilisé avec des expressions régulières contenant une autre instance de l'opérateur (voir la discussion précédente sur le contexte final).

L'opérateur supplémentaire d'expressions régulières de contexte final '/' peut être utilisé comme un caractère ordinaire s'il est présenté entre guillemets doubles, "/" ; précédé d'un <backslash>, "\/" ; ou dans une expression entre crochets, "[/]". Les opérateurs de condition de démarrage '<' et '>' seront spéciaux uniquement dans une condition de démarrage au début d'une expression régulière ; ailleurs dans l'expression régulière, ils seront traités comme des caractères ordinaires.

Actions dans lex

L'action à entreprendre lorsqu'une ERE est mise en correspondance peut être un fragment de programme C ou les actions spéciales décrites ci-dessous ; le fragment de programme peut contenir une ou plusieurs instructions C, et peut également inclure des actions spéciales. L'instruction C vide ';' sera une action valide ; toute chaîne dans l'entrée lex.yy.c qui correspond à la partie modèle d'une telle règle est effectivement ignorée ou ignorée. Cependant, l'absence d'action ne sera pas valide, et l'action que lex entreprend dans une telle condition est indéfinie.

La spécification d'une action, y compris les instructions C et les actions spéciales, peut s'étendre sur plusieurs lignes si elle est entourée d'accolades :

ERE <un ou plusieurs espaces> { instruction de programme
                           instruction de programme }

Les instructions de programme ne doivent pas contenir de jetons de prétraitement avec des accolades déséquilibrées.

L'action par défaut lorsqu'une chaîne dans l'entrée d'un programme lex.yy.c n'est mise en correspondance par aucune expression sera de copier la chaîne dans la sortie. Comme le comportement par défaut d'un programme généré par lex est de lire l'entrée et de la copier dans la sortie, un programme source lex minimal qui n'a que "%%" générera un programme C qui copie simplement l'entrée dans la sortie inchangée.

Quatre actions spéciales seront disponibles :

|   ECHO;   REJECT;   BEGIN
|
L'action '|' signifie que l'action pour la règle suivante est l'action pour cette règle. Contrairement aux trois autres actions, '|' ne peut pas être entourée d'accolades ou terminée par un <point-virgule> ; l'application doit s'assurer qu'elle est spécifiée seule, sans autres actions.
ECHO;
Écrit le contenu de la chaîne yytext sur la sortie.
REJECT;
Généralement, une seule expression est mise en correspondance par une chaîne donnée dans l'entrée. REJECT signifie « continuer vers la prochaine expression qui correspond à l'entrée actuelle » et provoquera l'exécution de la règle qui était le deuxième choix après la règle actuelle pour la même entrée. Ainsi, plusieurs règles peuvent être mises en correspondance et exécutées pour une chaîne d'entrée unique ou des chaînes d'entrée qui se chevauchent. Par exemple, étant donné les expressions régulières "xyz" et "xy" et l'entrée "xyz", généralement seule l'expression régulière "xyz" correspondrait. La prochaine tentative de correspondance commencerait après z. Si la dernière action de la règle "xyz" est REJECT, cette règle et la règle "xy" seraient exécutées. L'action REJECT peut être implémentée de telle sorte que le flux de contrôle ne continue pas après elle, comme s'il équivalait à un goto vers une autre partie de yylex(). L'utilisation de REJECT peut entraîner des analyseurs un peu plus volumineux et plus lents.
BEGIN
L'action :
BEGIN newstate;

bascule l'état (condition de démarrage) vers newstate. Si la chaîne newstate n'a pas été déclarée précédemment comme condition de démarrage dans la section Définitions, les résultats sont non spécifiés. L'état initial est indiqué par le chiffre '0' ou le jeton INITIAL.

Les fonctions ou macros décrites ci-dessous sont accessibles au code utilisateur inclus dans l'entrée lex. Il

est non spécifié s'ils apparaissent dans le code C généré par lex, ou s'ils ne sont accessibles que via l'opérande -l l pour c99 (la bibliothèque lex).

int yylex(void)

Effectue l'analyse lexicale de l'entrée ; c'est la fonction principale générée par l'utilitaire lex. La fonction doit renvoyer zéro lorsque la fin de l'entrée est atteinte ; sinon, elle doit renvoyer des valeurs non nulles (jetons) déterminées par les actions sélectionnées.
int yymore(void)

Lorsqu'elle est appelée, indique que lorsque la prochaine chaîne d'entrée sera reconnue, elle sera ajoutée à la valeur actuelle de yytext au lieu de la remplacer ; la valeur dans yyleng sera ajustée en conséquence.
int yyless(int n)

Conserve n caractères initiaux dans yytext, terminés par un NUL, et traite les caractères restants comme s'ils n'avaient pas été lus ; la valeur dans yyleng sera ajustée en conséquence.
int input(void)

Renvoie le caractère suivant de l'entrée, ou zéro en cas de fin de fichier. Elle doit obtenir l'entrée à partir du pointeur de flux yyin, bien que potentiellement via un tampon intermédiaire. Ainsi, une fois l'analyse commencée, l'effet de la modification de la valeur de yyin est indéfini. Le caractère lu doit être retiré du flux d'entrée du scanner sans aucun traitement par le scanner.
int unput(int c)

Remet le caractère 'c' dans l'entrée ; yytext et yyleng sont indéfinis jusqu'à ce que la prochaine expression soit reconnue. Le résultat de l'utilisation de unput() pour plus de caractères que ceux qui ont été lus est non spécifié.

Les fonctions suivantes doivent apparaître uniquement dans la bibliothèque lex accessible via l'opérande -l l ; elles peuvent donc être redéfinies par une application conforme :

int yywrap(void)

Appelée par yylex() en fin de fichier ; le yywrap() par défaut doit toujours renvoyer 1. Si l'application nécessite que yylex() continue le traitement avec une autre source d'entrée, alors l'application peut inclure une fonction yywrap(), qui associe un autre fichier à la variable externe FILE * yyin et doit renvoyer une valeur de zéro.
int main(int argc, char *argv[])

Appelle yylex() pour effectuer l'analyse lexicale, puis quitte. Le code utilisateur peut contenir main() pour effectuer des opérations spécifiques à l'application, en appelant yylex() selon les besoins.

À l'exception de input(), unput() et main(), tous les noms externes et statiques générés par lex doivent commencer par le préfixe yy ou YY.

 0
Achèvement réussi.
>0
Une erreur s'est produite.

USAGE APPLICATIF

Les applications conformes sont averties que dans la section Règles, une ERE sans action n'est pas acceptable, mais ne doit pas nécessairement être détectée comme erronée par lex. Cela peut entraîner des erreurs de compilation ou d'exécution.

Le but de input() est de retirer des caractères du flux d'entrée et de les ignorer pour l'analyse lexicale. Une utilisation courante consiste à ignorer le corps d'un commentaire une fois que le début d'un commentaire est reconnu.

L'utilitaire lex n'est pas entièrement internationalisé dans son traitement des expressions régulières dans le code source lex ou dans l'analyseur lexical généré. Il semblerait souhaitable que l'analyseur lexical interprète les expressions régulières fournies dans le code source lex conformément à l'environnement spécifié lors de l'exécution de l'analyseur lexical, mais ce n'est pas possible avec la technologie lex actuelle. De plus, la nature même des analyseurs lexicaux produits par lex doit être étroitement liée aux exigences lexicales du langage d'entrée décrit, qui est souvent spécifique à la locale de toute façon. (Par exemple, écrire un analyseur utilisé pour le texte français n'est pas automatiquement utile pour traiter d'autres langues.)

EXEMPLES

Ce qui suit est un exemple de programme lex qui implémente un analyseur rudimentaire pour une syntaxe de type Pascal :

%{
/* Nécessaire pour l'appel à atof() ci-dessous. */
#include <math.h>
/* Nécessaire pour printf(), fopen(), et stdin ci-dessous. */
#include <stdio.h>
%}
DIGIT    [0-9]
ID       [a-z][a-z0-9]*
%%
{DIGIT}+ {
    printf("Un entier : %s (%d)\n", yytext,
        atoi(yytext));
    }
{DIGIT}+"."{DIGIT}*        {
    printf("Un flottant : %s (%g)\n", yytext,
        atof(yytext));
    }
if|then|begin|end|procedure|function        {
    printf("Un mot-clé : %s\n", yytext);
    }
{ID}    printf("Un identifiant : %s\n", yytext);
"+"|"-"|"*"|"/"        printf("Un opérateur : %s\n", yytext);
"{"[^}\n]*"}"    /* Ignorer les commentaires sur une seule ligne. */
[ \t\n]+        /* Ignorer les espaces blancs. */
.  printf("Caractère non reconnu : %s\n", yytext);
%%
int main(int argc, char *argv[])
{
    ++argv, --argc;  /* Ignorer le nom du programme. */
    if (argc > 0)
        yyin = fopen(argv[0], "r");
    else
        yyin = stdin;
    yylex();
}

JUSTIFICATION

Même si l'option -c et les références au langage C sont conservées dans cette description, lex peut être généralisé à d'autres langages, comme cela a été fait à une époque pour EFL, l'Extended FORTRAN Language. Comme la spécification d'entrée de lex est essentiellement indépendante du langage, des versions de cet utilitaire pourraient être écrites pour produire du code Ada, Modula-2 ou Pascal, et il existe des implémentations historiques connues qui le font.

La description actuelle de lex contourne le problème du traitement des ERE internationalisées dans le code source lex ou dans l'analyseur lexical généré. S'il suit le modèle utilisé par awk (le code source est supposé être présenté dans la locale POSIX, mais l'entrée et la sortie sont dans la locale spécifiée par les variables d'environnement), alors les tables de l'analyseur lexical produit par lex interpréteraient les ERE spécifiées dans le code source lex en fonction des variables d'environnement spécifiées lors de l'exécution de lex. L'effet désiré serait que l'analyseur lexical interprète les ERE fournies dans le code source lex selon l'environnement spécifié lors de l'exécution de l'analyseur lexical, mais ce n'est pas possible avec la technologie lex actuelle.

La description des séquences d'échappement de chiffres octaux et hexadécimaux correspond à l'utilisation des séquences d'échappement dans la norme ISO C.

Les versions antérieures de cette norme autorisaient des implémentations avec des octets autres que huit bits, mais cela a été modifié dans cette version.

Il n'y a pas de spécification détaillée du format de sortie. Le comportement observé de lex dans quatre implémentations historiques différentes était qu'aucune de ces implémentations ne rapportait de manière cohérente les numéros de ligne pour les messages d'erreur et d'avertissement. De plus, il y avait un désir que lex soit autorisé à émettre des messages de diagnostic supplémentaires. Laisser les formats des messages non spécifiés évite ces questions de formatage et les problèmes d'internationalisation.

Bien que le spécificateur %x pour les conditions de démarrage exclusives ne soit pas une pratique historique, il est considéré comme un changement mineur par rapport aux implémentations historiques et améliore considérablement la convivialité des programmes lex puisqu'il permet à une application d'obtenir la fonctionnalité attendue avec moins d'instructions.

Les déclarations %array et %pointer ont été ajoutées comme un compromis entre les systèmes historiques. Le lex basé sur System V copie le texte reconnu dans un tableau yytext. Le programme flex, pris en charge sur les systèmes BSD et GNU, utilise un pointeur. Dans ce dernier cas, des améliorations significatives de performance sont disponibles pour certains analyseurs. La plupart des programmes historiques ne devraient nécessiter aucun changement lors du portage d'un système à l'autre car la chaîne référencée est terminée par un caractère nul dans les deux cas. (La méthode utilisée par flex dans son cas consiste à terminer le jeton par un caractère nul sur place en mémorisant le caractère qui se trouvait juste après le jeton et en le remplaçant avant de continuer l'analyse suivante.) Les programmes multi-fichiers avec des références externes à yytext en dehors du fichier source de l'analyseur devraient continuer à fonctionner sur leurs systèmes historiques, mais nécessiteraient l'une des nouvelles déclarations pour être considérés comme strictement portables.

La description des ERE évite les répétitions inutiles de détails sur les ERE car leur signification dans une ERE lex est la même que celle des ERE dans ce volume de POSIX.1‐2017.

La raison de la condition indéfinie associée au texte commençant par un <espace> ou à l'intérieur des délimiteurs "%{" et "%}" apparaissant dans la section Règles est une pratique historique. Le lex basé sur BSD et System V copie l'entrée indentée (ou entourée) dans la section Règles (sauf au début) dans des zones inaccessibles de la fonction yylex() (le code est écrit directement après une instruction break). Dans certains cas, le lex de System V génère un message d'erreur ou une erreur de syntaxe, selon la forme de l'entrée indentée.

L'intention de diviser la liste des fonctions en celles qui peuvent apparaître dans lex.yy.c vs celles qui apparaissent uniquement dans libl.a est que seules les fonctions de libl.a peuvent être redéfinies de manière fiable par une application conforme.

Les descriptions de la sortie standard et de l'erreur standard sont quelque peu compliquées car les implémentations historiques de lex ont choisi d'émettre des messa de diagnostic

lex(1p) — Manuel de l’utilisateur Linux

PROLOG

NOM

lex — générateur d'analyseurs lexicaux

SYNOPIS

lex [-c] [-n] [-t] [-v] [fichier...]

DESCRIPTION

Le programme utilitaire lex génère un programme d'analyse lexicale (un analyseur). L'analyseur généré est écrit en langage C et est renvoyé dans un fichier nommé lex.yy.c. Le programme résultant, lorsqu'il est compilé et exécuté, lit l'entrée standard ou les fichiers spécifiés, et classe les entrées en fonction d'une série de règles définies dans le ou les fichiers spécifiés.

Le fichier lex.yy.c contient une fonction nommée yylex() qui effectue l'analyse lexicale. Cette fonction est généralement appelée à partir d'un programme d'analyse syntaxique écrit avec yacc(1). Il est également possible d'appeler yylex() directement dans un programme C autonome.

OPTIONS

Le programme utilitaire lex prendra en charge les options suivantes :

-c
Ceci est le comportement par défaut. Le code C généré est écrit dans le fichier lex.yy.c.
-n
Ne pas écrire le rapport récapitulatif des statistiques sur la sortie standard (uniquement lorsque la sortie C est dans lex.yy.c).
-t
Écrit le code C généré sur la sortie standard au lieu du fichier lex.yy.c. Les statistiques sont toujours écrites sur la sortie standard.
-v
Ne pas écrire le rapport récapitulatif des statistiques sur la sortie standard. Ceci est l'inverse de l'option -v de yacc(1).

OPÉRANDES

Les opérandes suivants sont pris en charge :

fichier
Le nom d'un fichier contenant des spécifications pour l'analyseur lexical. Si aucun fichier n'est spécifié, l'entrée standard est utilisée.

STDIN

L'entrée standard peut être utilisée pour lire les spécifications de l'analyseur lexical, ou pour fournir les données d'entrée à l'analyseur lexical généré si cela est fait via l'option -t.

FICHIERS D'ENTRÉE

Les fichiers spécifiés par les opérandes sont lus séquentiellement pour construire l'analyseur lexical. Les règles, les options et le code C sont lus à partir de ces fichiers. La structure typique d'un fichier d'entrée lex est la suivante :

définitions
%%
règles
%%
code utilisateur C

VARIABLES D'ENVIRONNEMENT

Aucune variable d'environnement n'est utilisée par cette version de lex.

ÉVÉNEMENTS ASYNCHRONES

Non défini.

STDOUT

Par défaut, le code C généré est écrit dans le fichier lex.yy.c. Les statistiques sont écrites sur la sortie standard, sauf si les options -n ou -v sont spécifiées. Si l'option -t est utilisée, le code C est également écrit sur la sortie standard.

STDERR

Les messages d'erreur sont écrits sur la sortie d'erreur standard.

FICHIERS DE SORTIE

Par défaut, lex.yy.c est créé.

DESCRIPTION ÉTENDUE

Le programme utilitaire lex génère un analyseur lexical, un programme qui reconnaît les constructions lexicales dans le texte. Le programme utilitaire lex lit des spécifications qui décrivent les constructions lexicales et une action à effectuer lorsque l'une de ces constructions est reconnue. L'action est généralement une petite fonction C.

Le programme utilitaire lex génère un fichier source C appelé lex.yy.c qui contient une routine nommée yylex() qui effectue le travail d'analyse lexicale.

L'analyseur généré par lex est basé sur une machine à états finis déterministe (DFA).

VALEUR DE RETOUR

Non défini.

CONSÉQUENCES DES ERREURS

Non défini.

UTILISATION PAR APPLICATION

L'utilisation de lex est généralement la suivante :

lex [options] fichier(s)
cc lex.yy.c -ll
./a.out < fichier_entrée

Le programme yacc(1) est souvent utilisé conjointement avec lex pour construire des analyseurs syntaxiques.

EXEMPLES

Les exemples suivants clarifient les différences entre les expressions régulières lex et les expressions régulières apparaissant ailleurs dans ce volume de POSIX.1‐2017. Pour les expressions régulières de la forme « r/x », la chaîne correspondant à r est toujours retournée ; la confusion peut survenir lorsque le début de x correspond à la partie finale de r. Par exemple, étant donné l'expression régulière « a\*b/cc » et l'entrée « aaabcc », yytext contiendrait la chaîne « aaab » lors de cette correspondance. Mais étant donné l'expression régulière « x\*/xy » et l'entrée « xxxy », le jeton xxx, et non xx, est renvoyé par certaines implémentations car xxx correspond à « x\* ».

Dans la règle « ab\*/bc », le « b\* » à la fin de r étend la correspondance de r au début du contexte final, de sorte que le résultat n'est pas spécifié. Si cette règle était « ab/bc », cependant, la règle correspond au texte « ab » lorsqu'il est suivi du texte « bc ». Dans ce dernier cas, la correspondance de r ne peut pas s'étendre au début de x, de sorte que le résultat est spécifié.

RATIONALE

Le comportement par défaut des statistiques de lex était que celles-ci étaient écrites sur la sortie standard (sauf si -t était donné). POSIX.1‐2008 autorise ce comportement, mais laisse une ouverture pour le comportement plus attendu d'utilisation de la sortie d'erreur pour les diagnostics. De plus, le comportement System V d'écriture des statistiques lorsque des tailles de table sont données est autorisé, tandis que les systèmes dérivés de BSD peuvent l'éviter. Le programmeur peut toujours obtenir précisément les résultats souhaités en utilisant les options -t ou -n.

La section OPERANDES ne mentionne pas l'utilisation de - comme synonyme de l'entrée standard ; toutes les implémentations historiques ne prennent pas en charge une telle utilisation pour l'un des opérandes fichier.

Une description de la table de traduction a été supprimée des premières propositions en raison de son utilisation relativement faible dans les applications historiques.

La modification de la définition de la fonction input() qui autorise la mise en mémoire tampon des entrées présente l'opportunité de gains de performances majeurs dans certaines applications.
