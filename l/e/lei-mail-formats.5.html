NOM

lei-mail-formats - description des formats de courrier pris en charge par lei

DESCRIPTION

lei-q(1) prend en charge l'écriture dans plusieurs formats de courrier existants pour l'interopérabilité avec les agents utilisateurs de courrier (MUA) existants ; ci-dessous un aperçu pour aider les utilisateurs à choisir.

Maildir

Le format de sortie par défaut lorsqu'un chemin de système de fichiers est donné, il prend en charge l'accès parallèle en lecture-écriture. Les performances sont acceptables pour les plus petites répertoires, mais se dégradent à mesure que les boîtes aux lettres grossissent. La vitesse et l'évolutivité sont limitées par les performances du noyau et du système de fichiers en raison de l'utilisation de petits fichiers et d'un grand nombre d'appels système.

Voir aussi : https://cr.yp.to/proto/maildir.html et https://wiki2.dovecot.org/MailboxFormat/Maildir

Famille Mbox

La famille mbox comprend plusieurs formats incompatibles. Le verrouillage pour l'accès parallèle est pris en charge, mais peut ne pas être compatible entre les outils. Avec la compression (par exemple gzip(1)), ils nécessitent le moins d'espace tout en offrant de bonnes performances en lecture seule.

Les mises à jour de mots-clés ("Status:" et/ou "X-Status:" en-têtes) nécessitent généralement la réécriture de l'ensemble du mbox.

Voir aussi : https://www.loc.gov/preservation/digital/formats/fdd/fdd000383.shtml, mbox(5)

mboxo

Le format traditionnel BSD. Il met en citation "From " en ">From ", mais les lignes commençant déjà par ">From " ne sont pas mises en citation, donc la réversibilité automatique n'est pas garantie. Les MUA qui privilégient "mboxcl" ou "mboxcl2" peuvent les convertir automatiquement dans leur format préféré.

La troncature est indétectable à moins d'être compressée avec gzip ou similaire.

mboxrd

Une évolution de "mboxo", mais met en citation les lignes "From " préfixées par n'importe quel nombre de caractères ">" et est donc entièrement réversible.

Ce format est émis par PublicInbox::WWW(3pm) avec gzip. Depuis git 2.10, "git am --patch-format=mboxrd" lit ce format. "git log" et "git format-patch --stdout" peuvent également générer ce format avec le commutateur "--pretty=mboxrd".

Comme avec "mboxo" non compressé, mboxrd non compressé est vulnérable à une troncature indétectable.

Il se dégrade gracieusement en étant traité comme "mboxo" par les MUA ignorant le format, car une citation excessive de ">From " est reconnaissable par les humains.

mboxcl

"mboxo" avec un en-tête "Content-Length:", les lignes "From " restent citées pour conserver la lisibilité avec les MUA "mboxo" et "mboxrd". Cependant, il est facile de corrompre ces fichiers lors de l'utilisation d'outils qui ne connaissent pas "Content-Length:" et écrivent des mises à jour en tant que "mboxo".

mutt(1) convertira "mboxo" et "mboxrd" en mboxcl lors de l'ouverture.

Voir aussi : https://www.jwz.org/doc/content-length.html

mboxcl2

Similaire à "mboxcl", mais sans aucune citation de "From ". Il est totalement incompatible avec les MUA qui ne gèrent que "mboxo" et/ou "mboxrd". Ce format est généré par mutt(1) lors de l'écriture dans un nouveau mbox.

MH

Support préliminaire pour les lectures à partir de la version 2.0.0. Les sémantiques de verrouillage diffèrent de manière incompatible entre les écrivains existants : Python et nmh semblent compatibles entre eux, tandis que mutt semble sujet aux courses et inadapté à l'accès parallèle en raison de rename(2) pouvant écraser le fichier ".mh_sequences". Plus d'informations sur d'autres clients sont très appréciées.

Les numéros de séquence peuvent être packés et réutilisés par certains écrivains, donc les utilisateurs de lei pourraient avoir besoin d'exécuter lei-refresh-mail-sync(1) si inotify|kevent a manqué le pack pendant que lei-daemon(8) n'était pas en cours d'exécution.

lei est sûr pour lire les archives mlmmj en tant que MH car mlmmj ne packe ni n'utilise de fichier .mh_sequences pour stocker l'état.

MMDF

Pas encore pris en charge, et il n'est pas clair si l'utilisation/le support actuel rend la peine de le prendre en charge.

IMAP

Selon le logiciel serveur IMAP et sa configuration, les serveurs IMAP peuvent utiliser n'importe lequel (ou une combinaison) des formats susmentionnés ou une base de données non standard. Actuellement, lei utilise Mail::IMAPClient, ce qui offre des performances acceptables sur des liaisons à faible latence. Les performances sur les liaisons à haute latence sont actuellement médiocres.

eml

Un seul fichier de message brut. "eml" n'est pas un format de sortie pour lei, mais est accepté comme un "--input-format" ("-F") pour les commandes en lecture seule telles que lei-tag(1) et lei-import(1).

Depuis que "eml" est le suffixe du type MIME "message/rfc822" (selon le fichier "mime.types"), lei en déduira le type en fonction du suffixe ".eml" si "--input-format" n'est pas spécifié.

".patch" les fichiers suffixés générés par git-format-patch(1) (sans "--stdout") sont des fichiers "eml" avec l'ajout d'un en-tête mbox "From ". lei(1) supprime les lignes "From " pour les traiter comme "eml" lors de la lecture de ceux-ci pour la compatibilité avec "git-am(1)" et des outils similaires.

NOM

lei-mail-formats - Formats de courriels supportés par lei

DESCRIPTION

Cet article de manuel décrit les formats de courrier électronique que le programme lei peut comprendre et manipuler.

Maildir

Le format Maildir est un format moderne de stockage de courrier électronique. Chaque courriel est stocké dans un fichier distinct, et les messages sont organisés dans des sous-répertoires tels que new, cur et tmp.

Famille Mbox

La famille mbox est un format plus ancien et plus simple de stockage de courrier électronique. Les courriels sont généralement stockés dans un seul fichier, avec chaque courriel précédé d'un délimiteur spécifique (par exemple, "From ").

MH

Le format MH (Message Handling) est un système de gestion de messages basé sur des fichiers. Chaque courriel est stocké dans un fichier distinct dans une hiérarchie de répertoires.

MMDF

Le format MMDF (Multi-channel Memorandum Distribution Facility) est un autre système de gestion de courriels qui était populaire dans le passé. Il utilise une structure de fichiers spécifique pour stocker les messages.

IMAP

IMAP (Internet Message Access Protocol) n'est pas un format de stockage local, mais un protocole qui permet d'accéder aux courriels stockés sur un serveur. lei peut interagir avec des serveurs IMAP pour récupérer et gérer les courriels.

eml

Le format .eml est une extension de nom de fichier couramment utilisée pour les fichiers de courrier électronique individuels. Ces fichiers contiennent généralement le contenu d'un courriel unique dans un format standard (souvent basé sur MIME).
