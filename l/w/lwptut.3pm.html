NOM

lwptut -- Un tutoriel LWP

DESCRIPTION

LWP (abréviation de « Library for WWW in Perl ») est un groupe de modules Perl très populaire pour accéder aux données sur le Web. Comme la plupart des distributions de modules Perl, chaque module composant de LWP est fourni avec une documentation qui constitue une référence complète de son interface. Cependant, LWP contient tellement de modules qu'il est difficile de savoir par où commencer pour trouver des informations sur la façon d'effectuer les tâches les plus simples et les plus courantes.

Pour vraiment vous introduire à l'utilisation de LWP, il faudrait un livre entier -- un livre qui existe d'ailleurs, intitulé Perl & LWP. Mais cet article devrait vous donner un aperçu de la façon dont vous pouvez aborder certaines tâches courantes avec LWP.

Obtenir des documents avec LWP::Simple

Si vous voulez simplement obtenir ce qui se trouve à une URL particulière, la façon la plus simple de le faire est d'utiliser les fonctions de LWP::Simple.

Dans un programme Perl, vous pouvez appeler sa fonction get($url). Elle essaiera d'obtenir le contenu de cette URL. Si elle réussit, elle renverra le contenu ; mais s'il y a une erreur, elle renverra undef.

my $url = 'http://www.npr.org/programs/fa/?todayDate=current';
  # Juste un exemple : l'URL de l'émission /Fresh Air/ la plus récente
use LWP::Simple;
my $content = get $url;
die "Impossible d'obtenir $url" unless defined $content;
# Ensuite, faites des choses avec $content, comme ceci :
if($content =~ m/jazz/i) {
  print "Ils parlent de jazz aujourd'hui sur Fresh Air !\n";
}
else {
  print "Fresh Air est apparemment sans jazz aujourd'hui.\n";
}

La variante la plus pratique de "get" est "getprint", qui est utile dans les one-liners Perl. Si elle peut obtenir la page dont vous fournissez l'URL, elle l'envoie à STDOUT ; sinon, elle se plaint à STDERR.

% perl -MLWP::Simple -e "getprint 'http://www.cpan.org/RECENT'"

C'est l'URL d'un fichier texte brut qui liste les nouveaux fichiers sur CPAN au cours des deux dernières semaines. Vous pouvez facilement en faire partie d'une commande shell soignée, comme celle-ci qui vous envoie par e-mail la liste des nouveaux modules "Acme::" :

% perl -MLWP::Simple -e "getprint 'http://www.cpan.org/RECENT'"  \
   | grep "/by-module/Acme" | mail -s "Nouveaux modules Acme ! Joie !" $USER

Il existe d'autres fonctions utiles dans LWP::Simple, notamment une fonction pour exécuter une requête HEAD sur une URL (utile pour vérifier les liens ou obtenir la date de dernière révision d'une URL), et deux fonctions pour enregistrer/miroir une URL dans un fichier local. Consultez la documentation de LWP::Simple pour les détails complets, ou le chapitre 2 de Perl & LWP pour plus d'exemples.

Les bases du modèle de classe LWP

Les fonctions de LWP::Simple sont pratiques pour les cas simples, mais ses fonctions ne supportent pas les cookies ou l'authentification, ne permettent pas de définir des lignes d'en-tête dans la requête HTTP, et ne permettent généralement pas de lire les lignes d'en-tête dans la réponse HTTP (notamment le message d'erreur HTTP complet, en cas d'erreur). Pour accéder à toutes ces fonctionnalités, vous devrez utiliser le modèle de classe complet de LWP.

Bien que LWP soit composé de dizaines de classes, les deux principales que vous devez comprendre sont LWP::UserAgent et HTTP::Response. LWP::UserAgent est une classe pour les « navigateurs virtuels » que vous utilisez pour effectuer des requêtes, et HTTP::Response est une classe pour les réponses (ou messages d'erreur) que vous recevez de ces requêtes.

L'idiome de base est "$response = $browser->get($url)", ou plus illustré :

# Au début de votre programme :

use LWP 5.64; # Charge toutes les classes LWP importantes et s'assure
              # que votre version est raisonnablement récente.
my $browser = LWP::UserAgent->new;

...

# Puis plus tard, quand vous avez besoin de faire une requête get :
my $url = 'http://www.npr.org/programs/fa/?todayDate=current';

my $response = $browser->get( $url );
die "Impossible d'obtenir $url -- ", $response->status_line
 unless $response->is_success;
die "Hé, je m'attendais à du HTML, pas à ", $response->content_type
 unless $response->content_type eq 'text/html';
   # ou quel que soit le type de contenu que vous pouvez traiter
# Sinon, traitez le contenu d'une manière ou d'une autre :

if($response->decoded_content =~ m/jazz/i) {
  print "Ils parlent de jazz aujourd'hui sur Fresh Air !\n";
}
else {
  print "Fresh Air est apparemment sans jazz aujourd'hui.\n";
}

Il y a deux objets impliqués : $browser, qui contient un objet de classe LWP::UserAgent, et ensuite l'objet $response, qui est de classe HTTP::Response. Vous n'avez vraiment besoin que d'un seul objet navigateur par programme ; mais chaque fois que vous effectuez une requête, vous recevez un nouvel objet HTTP::Response, qui aura des attributs intéressants :

  • Un code de statut indiquant le succès ou l'échec (que vous pouvez tester avec "$response->is_success").
  • Une ligne de statut HTTP qui est, espérons-le, informative en cas d'échec (que vous pouvez voir avec "$response->status_line", renvoyant quelque chose comme « 404 Not Found »).
  • Un type de contenu MIME comme « text/html », « image/gif », « application/xml », etc., que vous pouvez voir avec "$response->content_type"
  • Le contenu réel de la réponse, dans "$response->decoded_content". Si la réponse est du HTML, c'est là que se trouvera le code source HTML ; si c'est un GIF, alors "$response->decoded_content" sera les données binaires du GIF.
  • Et des dizaines d'autres méthodes pratiques et plus spécifiques qui sont documentées dans la documentation de HTTP::Response, et de ses superclasses HTTP::Message et HTTP::Headers.

Ajouter d'autres en-têtes de requête HTTP

La syntaxe la plus couramment utilisée pour les requêtes est "$response = $browser->get($url)", mais en vérité, vous pouvez ajouter des lignes d'en-tête HTTP supplémentaires à la requête en ajoutant une liste de paires clé-valeur après l'URL, comme ceci :

$response = $browser->get( $url, $key1, $value1, $key2, $value2, ... );

Par exemple, voici comment envoyer certains en-têtes couramment utilisés, au cas où vous auriez affaire à un site qui rejetterait autrement votre requête :

my @ns_headers = (
 'User-Agent' => 'Mozilla/4.76 [en] (Win98; U)',
 'Accept' => 'image/gif, image/x-xbitmap, image/jpeg, image/pjpeg, image/png, */*',
 'Accept-Charset' => 'iso-8859-1,*,utf-8',
 'Accept-Language' => 'en-US',
);
...

$response = $browser->get($url, @ns_headers);

Si vous ne réutilisiez pas ce tableau, vous pourriez simplement faire ceci :

$response = $browser->get($url,
 'User-Agent' => 'Mozilla/4.76 [en] (Win98; U)',
 'Accept' => 'image/gif, image/x-xbitmap, image/jpeg, image/pjpeg, image/png, */*',
 'Accept-Charset' => 'iso-8859-1,*,utf-8',
 'Accept-Language' => 'en-US',
);

Si vous ne changiez que la ligne 'User-Agent', vous pourriez simplement changer la ligne par défaut de l'objet $browser de « libwww-perl/5.65 » (ou similaire) à ce que vous voulez, en utilisant la méthode "agent" de LWP::UserAgent :

$browser->agent('Mozilla/4.76 [en] (Win98; U)');

Activation des cookies

Un objet LWP::UserAgent par défaut agit comme un navigateur dont le support des cookies est désactivé. Il existe diverses façons de l'activer, en réglant son attribut "cookie_jar". Un « cookie jar » est un objet représentant une petite base de données de tous les cookies HTTP qu'un navigateur connaît. Il peut correspondre à un fichier sur le disque ou à un objet en mémoire qui commence vide, et dont la collection de cookies disparaîtra une fois le programme terminé.

Pour donner à un navigateur un cookie jar en mémoire vide, vous réglez son attribut "cookie_jar" comme ceci :

use HTTP::CookieJar::LWP;
$browser->cookie_jar( HTTP::CookieJar::LWP->new );

Pour enregistrer un cookie jar sur disque, voir « dump_cookies » dans HTTP::CookieJar. Pour charger des cookies depuis le disque dans un jar, voir « load_cookies » dans HTTP::CookieJar.

POSTING FORM DATA

To post form data, you'll want to use the "post" method of an LWP::UserAgent object. The method takes the URL to post to, followed by a list of key/value pairs representing the form data. For example:

$response = $browser->post( $url,
  [
    formkey1 => value1,
    formkey2 => value2,
    ...
  ],
);

Or if you need to send HTTP headers:

$response = $browser->post( $url,
  [
    formkey1 => value1,
    formkey2 => value2,
    ...
  ],
  headerkey1 => value1,
  headerkey2 => value2,
);

For example, the following program makes a search request to AltaVista (by sending some form data via an HTTP POST request), and extracts from the HTML the report of the number of matches:

use strict;
use warnings;
use LWP 5.64;
my $browser = LWP::UserAgent->new;
my $word = 'tarragon';
my $url = 'http://search.yahoo.com/yhs/search';
my $response = $browser->post( $url,
  [ 'q' => $word,  # the Altavista query string
    'fr' => 'altavista', 'pg' => 'q', 'avkw' => 'tgz', 'kl' => 'XX',
  ]
);
die "$url error: ", $response->status_line
 unless $response->is_success;
die "Weird content type at $url -- ", $response->content_type
 unless $response->content_is_html;
if( $response->decoded_content =~ m{([0-9,]+)(?:<.*?>)? results for} ) {
  # The substring will be like "996,000</strong> results for"
  print "$word: $1\n";
}
else {
  print "Couldn't find the match-string in the response\n";
}

Sending GET Form Data

Some HTML forms convey their form data not by sending the data in an HTTP POST request, but by making a normal GET request with the data stuck on the end of the URL. For example, if you went to "www.imdb.com" and ran a search on "Blade Runner", the URL you'd see in your browser window would be:

http://www.imdb.com/find?s=all&q=Blade+Runner

To run the same search with LWP, you'd use this idiom, which involves the URI class:

use URI;
my $url = URI->new( 'http://www.imdb.com/find' );
  # makes an object representing the URL
$url->query_form(  # And here the form data pairs:
  'q' => 'Blade Runner',
  's' => 'all',
);
my $response = $browser->get($url);

See chapter 5 of Perl & LWP for a longer discussion of HTML forms and of form data, and chapters 6 through 9 for a longer discussion of extracting data from HTML.

Absolutizing URLs

The URI class that we just mentioned above provides all sorts of methods for accessing and modifying parts of URLs (such as asking sort of URL it is with "$url->scheme", and asking what host it refers to with "$url->host", and so on, as described in the docs for the URI class. However, the methods of most immediate interest are the "query_form" method seen above, and now the "new_abs" method for taking a probably-relative URL string (like "../foo.html") and getting back an absolute URL (like "http://www.perl.com/stuff/foo.html"), as shown here:

use URI;
$abs = URI->new_abs($maybe_relative, $base);

For example, consider this program that matches URLs in the HTML list of new modules in CPAN:

use strict;
use warnings;
use LWP;
my $browser = LWP::UserAgent->new;

my $url = 'http://www.cpan.org/RECENT.html';
my $response = $browser->get($url);
die "Can't get $url -- ", $response->status_line
 unless $response->is_success;

my $html = $response->decoded_content;
while( $html =~ m/<A HREF=\"(.*?)\"/g ) {
  print "$1\n";
}

When run, it emits output that starts out something like this:

MIRRORING.FROM
RECENT
RECENT.html
authors/00whois.html
authors/01mailrc.txt.gz
authors/id/A/AA/AASSAD/CHECKSUMS
...

However, if you actually want to have those be absolute URLs, you can use the URI module's "new_abs" method, by changing the "while" loop to this:

while( $html =~ m/<A HREF=\"(.*?)\"/g ) {
  print URI->new_abs( $1, $response->base ) ,"\n";
}

(The "$response->base" method from HTTP::Message is for returning what URL should be used for resolving relative URLs -- it's usually just the same as the URL that you requested.)

That program then emits nicely absolute URLs:

http://www.cpan.org/MIRRORING.FROM
http://www.cpan.org/RECENT
http://www.cpan.org/RECENT.html
http://www.cpan.org/authors/00whois.html
http://www.cpan.org/authors/01mailrc.txt.gz
http://www.cpan.org/authors/id/A/AA/AASSAD/CHECKSUMS
...

See chapter 4 of Perl & LWP for a longer discussion of URI objects.

Of course, using a regexp to match hrefs is a bit simplistic, and for more robust programs, you'll probably want to use an HTML-parsing module like HTML::LinkExtor or HTML::TokeParser or even maybe HTML::TreeBuilder.

Other Browser Attributes

LWP::UserAgent objects have many attributes for controlling how they work. Here are a few notable ones:

  • "$browser->timeout(15);"

    This sets this browser object to give up on requests that don't answer within 15 seconds.

  • "$browser->protocols_allowed( [ 'http', 'gopher'] );"

    This sets this browser object to not speak any protocols other than HTTP and gopher. If it tries accessing any other kind of URL (like an "ftp:" or "mailto:" or "news:" URL), then it won't actually try connecting, but instead will immediately return an error code 500, with a message like "Access to 'ftp' URIs has been disabled".

  • "use LWP::ConnCache; $browser->conn_cache(LWP::ConnCache->new());"

    This tells the browser object to try using the HTTP/1.1 "Keep-Alive" feature, which speeds up requests by reusing the same socket connection for multiple requests to the same server.

  • "$browser->agent( 'SomeName/1.23 (more info here maybe)' )"

    This changes how the browser object will identify itself in the default "User-Agent" line is its HTTP requests. By default, it'll send "libwww-perl/versionnumber", like "libwww-perl/5.65". You can change that to something more descriptive like this:

    $browser->agent( 'SomeName/3.14 (contact@robotplexus.int)' );

    Or if need be, you can go in disguise, like this:

    $browser->agent( 'Mozilla/4.0 (compatible; MSIE 5.12; Mac_PowerPC)' );
  • "push @{ $ua->requests_redirectable }, 'POST';"

    This tells this browser to obey redirection responses to POST requests (like most modern interactive browsers), even though the HTTP RFC says that should not normally be done.

For more options and information, see the full documentation for LWP::UserAgent.

Writing Polite Robots

If you want to make sure that your LWP-based program respects robots.txt files and doesn't make too many requests too fast, you can use the LWP::RobotUA class instead of the LWP::UserAgent class.

LWP::RobotUA class is just like LWP::UserAgent, and you can use it like so:

use LWP::RobotUA;
my $browser = LWP::RobotUA->new('YourSuperBot/1.34', 'you@yoursite.com');
  # Your bot's name and your email address
my $response = $browser->get($url);

But HTTP::RobotUA adds these features:

  • If the robots.txt on $url's server forbids you from accessing $url, then the $browser object (assuming it's of class LWP::RobotUA) won't actually request it, but instead will give you back (in $response) a 403 error with a message "Forbidden by robots.txt". That is, if you have this line: 
    die "$url -- ", $response->status_line, "\nAborted"
 unless $response->is_success;

    then the program would die with an error message like this:

    http://whatever.site.int/pith/x.html -- 403 Forbidden by robots.txt
Aborted at whateverprogram.pl line 1234
  • If this $browser object sees that the last time it talked to $url's server was too recently, then it will pause (via "sleep") to avoid making too many requests too often. How long it will pause for, is by default one minute -- but you can control it with the "$browser->delay( minutes )" attribute.

    For example, this code:

    $browser->delay( 7/60 );

    ...means that this browser will pause when it needs to avoid talking to any given server more than once every 7 seconds.

For more options and information, see the full documentation for LWP::RobotUA.

Using Proxies

In some cases, you will want to (or will have to) use proxies for accessing certain sites and/or using certain protocols. This is most commonly the case when your LWP program is running (or could be running) on a machine that is behind a firewall.

To make a browser object use proxies that are defined in the usual environment variables ("HTTP_PROXY", etc.), just call the "env_proxy" on a user-agent object before you go making any requests on it. Specifically:

use LWP::UserAgent;
my $browser = LWP::UserAgent->new;

# And before you go making any requests:
$browser->env_proxy;

For more information on proxy parameters, see the LWP::UserAgent documentation, specifically the "proxy", "env_proxy", and "no_proxy" methods.

HTTP Authentication

Many web sites restrict access to documents by using "HTTP Authentication". This isn't just any form of "enter your password" restrict

NOM

LWP::UserAgent - un agent utilisateur pour le Web

DESCRIPTION

L'authentification HTTP est un mécanisme de sécurité standard qui demande à l'utilisateur de s'authentifier auprès du serveur Web avant de pouvoir accéder à des ressources protégées. Ce n'est pas une redirection, mais un mécanisme spécifique où le serveur HTTP envoie au navigateur un code HTTP qui indique « Ce document fait partie d'un 'domaine' protégé, et vous ne pouvez y accéder que si vous le redemandez en ajoutant des en-têtes d'autorisation spéciaux à votre requête ».

Par exemple, les administrateurs de Unicode.org empêchent les bots de collecte d'adresses e-mail de collecter le contenu de leurs archives de listes de diffusion en les protégeant par l'authentification HTTP, puis en indiquant publiquement le nom d'utilisateur et le mot de passe (à "http://www.unicode.org/mail-arch/") – à savoir le nom d'utilisateur « unicode-ml » et le mot de passe « unicode ».

Par exemple, considérez l'URL suivante, qui fait partie de la zone protégée du site Web :

http://www.unicode.org/mail-arch/unicode-ml/y2002-m08/0067.html

Si vous accédez à cela avec un navigateur, vous obtiendrez une invite comme « Entrez le nom d'utilisateur et le mot de passe pour 'Unicode-MailList-Archives' sur le serveur 'www.unicode.org' ».

Dans LWP, si vous demandez simplement cette URL, comme ceci :

use LWP;
my $browser = LWP::UserAgent->new;
my $url =
 'http://www.unicode.org/mail-arch/unicode-ml/y2002-m08/0067.html';
my $response = $browser->get($url);
die "Erreur: ", $response->header('WWW-Authenticate') || 'Erreur d\'accès',
  #  ('WWW-Authenticate' est le nom du domaine)
  "\n ", $response->status_line, "\n à $url\n Abandon"
 unless $response->is_success;

Alors vous obtiendrez cette erreur :

Erreur: Basic realm="Unicode-MailList-Archives"
 401 Authorization Required
 à http://www.unicode.org/mail-arch/unicode-ml/y2002-m08/0067.html
 Abandon à auth1.pl ligne 9.  [ou ailleurs]

... parce que le $browser ne connaît ni le nom d'utilisateur ni le mot de passe pour ce domaine ("Unicode-MailList-Archives") sur cet hôte ("www.unicode.org"). La manière la plus simple de le faire savoir au navigateur est d'utiliser la méthode "credentials" pour lui indiquer un nom d'utilisateur et un mot de passe qu'il peut essayer d'utiliser pour ce domaine sur cet hôte. La syntaxe est :

$browser->credentials(
  'nom_serveur:num_port',
  'nom_domaine',
 'nom_utilisateur' => 'mot_de_passe'
);

Dans la plupart des cas, le numéro de port est 80, le port TCP/IP par défaut pour HTTP ; et vous appelez généralement la méthode "credentials" avant de faire des requêtes. Par exemple :

$browser->credentials(
  'reports.mybazouki.com:80',
  'web_server_usage_reports',
  'plinky' => 'banjo123'
);

Donc, si nous ajoutons ceci au programme ci-dessus, juste après la ligne "$browser = LWP::UserAgent->new;"...

$browser->credentials(  # ajoutez ceci au "porte-clés" de notre $browser
  'www.unicode.org:80',
  'Unicode-MailList-Archives',
  'unicode-ml' => 'unicode'
);

... alors lorsque nous l'exécutons, la requête réussit, au lieu de provoquer l'appel de la fonction "die".

Accéder aux URL HTTPS

Lorsque vous accédez à une URL HTTPS, cela fonctionnera pour vous de la même manière qu'une URL HTTP – si votre installation LWP dispose d'un support HTTPS (via une bibliothèque Secure Sockets Layer appropriée). Par exemple :

use LWP;
my $url = 'https://www.paypal.com/';   # Oui, HTTPS !
my $browser = LWP::UserAgent->new;
my $response = $browser->get($url);
die "Erreur à $url\n ", $response->status_line, "\n Abandon"
 unless $response->is_success;
print "Youpi, ça a marché ! J'ai obtenu ce document ",
 $response->content_type, " !\n";

Si votre installation LWP n'a pas de support HTTPS configuré, alors la réponse sera infructueuse et vous obtiendrez ce message d'erreur :

Erreur à https://www.paypal.com/
 501 Protocol scheme 'https' is not supported
 Abandon à paypal.pl ligne 7.   [ou le programme et la ligne correspondants]

Si votre installation LWP dispose du support HTTPS installé, alors la réponse devrait être réussie, et vous devriez pouvoir consulter $response comme pour toute réponse HTTP normale.

Pour plus d'informations sur l'installation du support HTTPS pour votre installation LWP, consultez le fichier utile README.SSL fourni avec la distribution libwww-perl.

Obtenir de Grands Documents

Lorsque vous demandez un document volumineux (ou potentiellement volumineux), un problème avec la manière normale d'utiliser les méthodes de requête (comme "$response = $browser->get($url)") est que l'objet réponse en mémoire devra contenir le document entier – en mémoire. Si la réponse est un fichier de trente mégaoctets, cela risque d'être une charge importante pour l'utilisation de la mémoire de ce processus.

Une alternative notable est de demander à LWP de sauvegarder le contenu dans un fichier sur le disque, au lieu de le sauvegarder en mémoire. Voici la syntaxe à utiliser :

$response = $ua->get($url,
                       ':content_file' => $spécification_fichier,
                    );

Par exemple,

$response = $ua->get('http://search.cpan.org/',
                       ':content_file' => '/tmp/sco.html'
                    );

Lorsque vous utilisez cette option ":content_file", le $response contiendra toutes les lignes d'en-tête normales, mais "$response->content" sera vide. Les erreurs d'écriture dans le fichier de contenu (par exemple, en raison d'un refus de permission ou d'un disque plein) seront signalées via les en-têtes de réponse "Client-Aborted" ou "X-Died", et non via la méthode "is_success" :

if ($response->header('Client-Aborted') eq 'die') {
  # gérer l'erreur ...

Notez que cette option ":content_file" n'est pas prise en charge dans les versions plus anciennes de LWP, vous devriez donc envisager d'ajouter "use LWP 5.66;" pour vérifier la version de LWP, si vous pensez que votre programme pourrait s'exécuter sur des systèmes avec des versions plus anciennes.

Si vous avez besoin de compatibilité avec les anciennes versions de LWP, utilisez cette syntaxe, qui fait la même chose :

use HTTP::Request::Common;
$response = $ua->request( GET($url), $spécification_fichier );
