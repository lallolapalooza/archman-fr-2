#define BIO_FLAGS_WRITE 0x02
#define BIO_FLAGS_IO_SPECIAL 0x04
#define BIO_FLAGS_RWS \
(BIO_FLAGS_READ|BIO_FLAGS_WRITE|BIO_FLAGS_IO_SPECIAL)

DESCRIPTION

Ces fonctions déterminent pourquoi un BIO est incapable de lire ou d'écrire des données. Elles sont généralement appelées après un échec de l'appel BIO_read(3) ou BIO_write(3).

BIO_should_retry() renvoie 1 si l'appel qui a produit cette condition doit être retenté ultérieurement, ou 0 si une erreur s'est produite.

BIO_should_read() renvoie 1 si la cause de la condition de réessai est qu'un BIO a besoin de lire des données, ou 0 sinon.

BIO_should_write() renvoie 1 si la cause de la condition de réessai est qu'un BIO a besoin d'écrire des données, ou 0 sinon.

BIO_should_io_special() renvoie 1 si une condition spéciale (c'est-à-dire une raison autre que la lecture ou l'écriture) est la cause de la condition de réessai, ou 0 sinon.

BIO_retry_type() renvoie le OU bit à bit d'un ou plusieurs des indicateurs BIO_FLAGS_READ, BIO_FLAGS_WRITE et BIO_FLAGS_IO_SPECIAL représentant la cause de la condition de réessai actuelle, ou 0 s'il n'y a pas de condition de réessai. Les types de BIO actuels ne définissent qu'un seul des indicateurs à la fois.

BIO_get_retry_BIO() détermine la raison précise de la condition spéciale. Il parcourt la chaîne BIO à partir de bio et renvoie le BIO qui a causé cette condition. S'il n'y a pas de condition spéciale, bio est renvoyé lui-même. Si reason n'est pas un pointeur NULL, *reason est défini à l'un des codes de raison suivants :

0
Il n'y a pas de condition spéciale.
BIO_RR_ACCEPT
accept(2) aurait bloqué. Cela peut se produire pour les BIO créés à partir de BIO_s_accept(3) ou BIO_f_ssl(3).
BIO_RR_CONNECT
connect(2) aurait bloqué. Cela peut se produire pour les BIO créés à partir de BIO_s_connect(3) ou BIO_f_ssl(3).
BIO_RR_SSL_X509_LOOKUP
Une fonction de rappel d'application définie par SSL_CTX_set_client_cert_cb(3) a demandé à être appelée à nouveau. Cela peut se produire pour les BIO créés à partir de BIO_f_ssl(3).

BIO_get_retry_reason() renvoie l'un des codes de raison ci-dessus pour une condition spéciale qui s'est produite dans bio. Elle ne parcourt pas la chaîne et renvoie 0 si aucune condition spéciale ne s'est produite dans bio lui-même.

BIO_set_retry_reason() définit la raison de réessai pour une condition spéciale pour le bio donné. Elle est destinée à être appelée par les fonctions implémentant un type BIO plutôt que par des fonctions utilisant simplement des BIOs.

BIO_should_retry(), BIO_should_read(), BIO_should_write(), BIO_should_io_special() et BIO_retry_type() sont implémentées comme des macros.

Si BIO_should_retry() renvoie false, alors la "condition d'erreur" précise dépend du type de BIO qui l'a causée et du code de retour de l'opération BIO. Par exemple, si un appel à BIO_read(3) sur un BIO de socket renvoie 0 et que BIO_should_retry() est false, alors la cause sera que la connexion est fermée. Une condition similaire sur un BIO de fichier signifiera qu'il a atteint la fin du fichier (EOF). Certains types de BIO peuvent placer des informations supplémentaires dans la file d'erreurs. Pour plus de détails, voir les pages man des types de BIO individuels.

Si la structure d'E/S sous-jacente est en mode bloquant, presque tous les types de BIO actuels ne demanderont pas de réessai, car les appels d'E/S sous-jacents ne le feront pas. Si l'application sait que le type de BIO ne signalera jamais de réessai, elle n'a pas besoin d'appeler BIO_should_retry() après un appel d'E/S BIO échoué. Ceci est généralement fait avec des BIOs de fichier.

Les BIOs SSL sont la seule exception actuelle à cette règle : ils peuvent demander un réessai même si la structure d'E/S sous-jacente est bloquante, si une négociation (handshake) se produit pendant un appel à BIO_read(3). Une application peut retenter l'appel échoué immédiatement ou éviter cette situation en définissant SSL_MODE_AUTO_RETRY sur la structure SSL sous-jacente.

Bien qu'une application puisse retenter un appel non bloquant échoué immédiatement, cela sera probablement très inefficace car l'appel échouera de manière répétée jusqu'à ce que les données puissent être traitées ou soient disponibles. Une application attendra normalement que la condition nécessaire soit satisfaite. La manière dont cela est fait dépend de la structure d'E/S sous-jacente.

Par exemple, si la cause est finalement un socket et que BIO_should_read() est vrai, alors un appel à select(2) peut être effectué pour attendre que des données soient disponibles, puis retenter l'opération BIO. En combinant les conditions de réessai de plusieurs BIOs non bloquants dans un seul appel à select(2), il est possible de servir plusieurs BIOs dans un seul thread, bien que les performances puissent être médiocres si des BIOs SSL sont présents car des délais longs peuvent survenir pendant le processus de négociation initial.

libressl-BIO_should_retry(3) — LibreSSL 4.2.1

NAME

BIO_should_read, BIO_should_write, BIO_should_io_special, BIO_should_retry, BIO_retry_type, BIO_get_retry_BIO, BIO_get_retry_reason, BIO_set_retry_reason - BIO retry and error handling

SYNOPSIS

#include <openssl/bio.h>
int BIO_should_read(BIO *bio);
int BIO_should_write(BIO *bio);
int BIO_should_io_special(BIO *bio);
int BIO_should_retry(BIO *bio);
int BIO_retry_type(BIO *bio);
BIO *BIO_get_retry_BIO(BIO *bio);
int BIO_get_retry_reason(BIO *bio);
void BIO_set_retry_reason(BIO *bio, int reason);

DESCRIPTION

A BIO can block indefinitely if the underlying I/O structure cannot process or return any data. This depends on the behaviour of the platforms I/O functions. This is often not desirable: one solution is to use non-blocking I/O and use a timeout on the select(2) (or equivalent) call.

SEE ALSO

BIO_new(3), BIO_read(3)

HISTORY

BIO_should_read(), BIO_should_write(), BIO_retry_type(), and BIO_should_retry() first appeared in SSLeay 0.6.0. BIO_should_io_special(), BIO_get_retry_BIO(), and BIO_get_retry_reason() first appeared in SSLeay 0.8.0. All these functions have been available since OpenBSD 2.4.

BIO_set_retry_reason() first appeared in OpenSSL 1.1.0 and has been available since OpenBSD 7.1.

BUGS

The OpenSSL ASN.1 functions cannot gracefully deal with non-blocking I/O: they cannot retry after a partial read or write. This is usually worked around by only passing the relevant data to ASN.1 functions when the entire structure can be read or written.

Il est possible qu'un BIO se bloque indéfiniment si la structure d'E/S sous-jacente ne peut pas traiter ou retourner de données. Cela dépend du comportement des fonctions d'E/S des plateformes. Ceci n'est souvent pas souhaitable : une solution consiste à utiliser des E/S non bloquantes et à utiliser un délai d'attente sur l'appel select(2) (ou équivalent).

VOIR AUSSI

BIO_new(3), BIO_read(3)

BIO_should_read(), BIO_should_write(), BIO_retry_type(), et BIO_should_retry() sont apparus pour la première fois dans SSLeay 0.6.0. BIO_set_retry_reason() est apparu pour la première fois dans OpenSSL 1.1.0 et est disponible depuis OpenBSD 7.1.

Les fonctions ASN.1 d'OpenSSL ne peuvent pas gérer gracieusement les E/S non bloquantes : elles ne peuvent pas réessayer après une lecture ou une écriture partielle. Ceci est généralement contourné en ne passant les données pertinentes aux fonctions ASN.1 que lorsque toute la structure peut être lue ou écrite.
