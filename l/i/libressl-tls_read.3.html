TLS_READ(3) Manuel des fonctions de bibliothèque TLS_READ(3)

NOM

tls_read, tls_write, tls_handshake, tls_error, tls_close — utiliser une connexion TLS

SYNOPSIS

bibliothèque “libtls” libssl libcrypto
#include <tls.h>

ssize_t
tls_read(struct tls *ctx, void *buf, size_t buflen);

ssize_t
tls_write(struct tls *ctx, const void *buf, size_t buflen);

int
tls_handshake(struct tls *ctx);

const char *
tls_error(struct tls *ctx);

int
tls_close(struct tls *ctx);

DESCRIPTION

tls_read() lit buflen octets de données depuis le socket dans buf. Il retourne la quantité de données lues.

tls_write() écrit buflen octets de données depuis buf vers le socket. Il retourne la quantité de données écrites.

tls_handshake() effectue explicitement le handshake TLS. Il est seulement nécessaire d'appeler cette fonction si vous avez besoin de garantir que le handshake est terminé, car tls_read() et tls_write() effectuent automatiquement le handshake TLS lorsque nécessaire.

La fonction tls_error() peut être utilisée pour récupérer une chaîne contenant plus d'informations sur la dernière erreur relative à un contexte.

tls_close() ferme une connexion après utilisation. Seule la couche TLS sera arrêtée et l'appelant est responsable de la fermeture des descripteurs de fichiers, à moins que la connexion n'ait été établie en utilisant tls_connect(3) ou tls_connect_servername(3). Après la fermeture de la connexion, ctx peut être passé à tls_free(3).

VALEURS DE RETOUR

tls_read() et tls_write() retournent une taille en cas de succès ou -1 en cas d'erreur.

tls_handshake() et tls_close() retournent 0 en cas de succès ou -1 en cas d'erreur.

Les fonctions tls_read(), tls_write(), tls_handshake(), et tls_close() ont également deux valeurs de retour spéciales :

TLS_WANT_POLLIN
Le descripteur de fichier de lecture sous-jacent doit être lisible pour continuer.
TLS_WANT_POLLOUT
Le descripteur de fichier d'écriture sous-jacent doit être accessible en écriture pour continuer.

Dans le cas de descripteurs de fichiers bloquants, le même appel de fonction doit être répété immédiatement. Dans le cas de descripteurs de fichiers non bloquants, le même appel de fonction doit être répété lorsque la condition requise a été satisfaite.

Les appelants de ces fonctions ne peuvent pas se fier à la valeur de errno globale. Pour éviter une mauvaise gestion des conditions d'erreur, tls_read(), tls_write(), tls_handshake(), et tls_close() effacent explicitement errno.

tls_error() retourne NULL si aucune erreur ne s'est produite avec ctx pendant ou depuis le dernier appel à tls_handshake(), tls_read(), tls_write(), tls_close(), ou tls_reset(3) impliquant ctx, ou si l'allocation mémoire a échoué lors de la tentative de construction de la chaîne décrivant la dernière erreur liée à ctx.

EXEMPLES

L'exemple suivant montre comment gérer les écritures TLS sur un descripteur de fichier bloquant :

...
while (len > 0) {
	ssize_t ret;

	ret = tls_write(ctx, buf, len);
	if (ret == TLS_WANT_POLLIN || ret == TLS_WANT_POLLOUT)
		continue;
	if (ret == -1)
		errx(1, "tls_write: %s", tls_error(ctx));
	buf += ret;
	len -= ret;
}
...

L'exemple suivant montre comment gérer les écritures TLS sur un descripteur de fichier non bloquant en utilisant poll(2) :

...
pfd[0].fd = fd;
pfd[0].events = POLLIN|POLLOUT;
while (len > 0) {
	nready = poll(pfd, 1, 0);
	if (nready == -1)
		err(1, "poll");
	if ((pfd[0].revents & (POLLERR|POLLNVAL)))
		errx(1, "bad fd %d", pfd[0].fd);
	if ((pfd[0].revents & (pfd[0].events|POLLHUP))) {
		ssize_t ret;

		ret = tls_write(ctx, buf, len);
		if (ret == TLS_WANT_POLLIN)
			pfd[0].events = POLLIN;
		else if (ret == TLS_WANT_POLLOUT)
			pfd[0].events = POLLOUT;
		else if (ret == -1)
			errx(1, "tls_write: %s", tls_error(ctx));
		else {
			buf += ret;
			len -= ret;
		}
	}
}
...

HISTORIQUE

tls_read(), tls_write(), tls_error(), et tls_close() sont apparues dans OpenBSD 5.6 et ont reçu leurs noms finaux dans OpenBSD 5.7.

tls_handshake() est apparue dans OpenBSD 5.9.

AVERTISSEMENTS

La fonction tls_error() retourne un pointeur interne. Il ne doit pas être libéré par l'application, sinon une erreur de double libération surviendra. Le pointeur deviendra invalide lors de la prochaine erreur avec ctx. Par conséquent, si l'application peut avoir besoin du message ultérieurement, elle doit copier la chaîne avant d'appeler la prochaine fonction libtls impliquant ctx, ou un défaut de segmentation ou une lecture de données non intentionnelles en sera le résultat probable.
