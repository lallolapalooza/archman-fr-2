CRYPTO_SET_EX_DATA(3) Manuel des fonctions de bibliothèque CRYPTO_SET_EX_DATA(3)

NOM

CRYPTO_get_ex_new_index, CRYPTO_EX_new, CRYPTO_EX_free, CRYPTO_EX_dup, CRYPTO_new_ex_data, CRYPTO_set_ex_data, CRYPTO_get_ex_data, CRYPTO_free_ex_data — fonctions de bas niveau pour les données spécifiques aux applications

SYNTAXE

bibliothèque “libcrypto”
#include <openssl/crypto.h>

int
CRYPTO_get_ex_new_index(int class_index, long argl, void *argp, CRYPTO_EX_new *new_func, CRYPTO_EX_dup *dup_func, CRYPTO_EX_free *free_func);

typedef int
CRYPTO_EX_new(void *parent, void *data, CRYPTO_EX_DATA *ad, int idx, long argl, void *argp);

typedef void
CRYPTO_EX_free(void *parent, void *data, CRYPTO_EX_DATA *ad, int idx, long argl, void *argp);

typedef int
CRYPTO_EX_dup(CRYPTO_EX_DATA *to, const CRYPTO_EX_DATA *from, void *datap, int idx, long argl, void *argp);

int
CRYPTO_new_ex_data(int class_index, void *parent, CRYPTO_EX_DATA *ad);

int
CRYPTO_set_ex_data(CRYPTO_EX_DATA *ad, int idx, void *data);

void *
CRYPTO_get_ex_data(CRYPTO_EX_DATA *ad, int idx);

void
CRYPTO_free_ex_data(int class_index, void *parent, CRYPTO_EX_DATA *ad);

DESCRIPTION

La bibliothèque implémente les fonctions documentées dans la page de manuel RSA_get_ex_new_index(3) et des fonctions similaires pour d'autres types d'objets parents en utilisant les fonctions documentées dans la présente page de manuel. Les programmes d'application n'ont presque jamais besoin d'appeler directement les fonctions documentées ici.

CRYPTO_get_ex_new_index() se comporte de la même manière que RSA_get_ex_new_index(3) sauf que le type d'objet parent pour lequel le nouvel idx est réservé ne fait pas partie du nom de la fonction mais est plutôt spécifié par l'argument supplémentaire class_index recevant l'une des constantes CRYPTO_EX_INDEX_* définies dans <openssl/crypto.h>. La recommandation donnée dans RSA_get_ex_new_index(3) de définir l'argument argl à 0 et les quatre derniers arguments à NULL s'applique. La bibliothèque transmet les arguments argl et argp aux fonctions de rappel pour le idx respectif, mais les ignore par ailleurs.

Si un pointeur de fonction est passé pour l'argument new_func, cette fonction est appelée pour le idx renvoyé chaque fois qu'un nouvel objet parent est alloué avec RSA_new(3) ou une fonction similaire.

Si un pointeur de fonction est passé pour l'argument free_func, cette fonction est appelée pour le idx renvoyé lorsqu'un objet parent est libéré avec RSA_free(3) ou une fonction similaire.

Les arguments de new_func et free_func sont les suivants :

parent
l'objet parent qui contient les data
data
les data précédemment définis par CRYPTO_set_ex_data() à l'idx dans parent
ad
le sous-objet CRYPTO_EX_DATA de l'objet parent
idx
la valeur de retour de CRYPTO_get_ex_new_index() qui a défini ce rappel
argl
l'argl passé à CRYPTO_get_ex_new_index() pour ce idx
argp
l'argp passé à CRYPTO_get_ex_new_index() pour ce idx

Si un pointeur de fonction est passé pour dup_func, cette fonction est censée être appelée pour le idx renvoyé chaque fois qu'un objet parent du type respectif est copié. En fait, les seules fonctions qui le font sont BIO_dup_chain(3), EC_KEY_copy(3), et SSL_dup(3), et la pile réseau TLS 1.3 le fait en interne lors de la duplication d'un objet SSL_SESSION après avoir reçu un message de ticket de session. La plupart des autres types d'objets prenant en charge ex_data ne prennent pas en charge la copie en premier lieu, tandis que DSA_dup_DH(3) et X509_dup(3) ignorent simplement dup_func.

Les arguments de dup_func sont les suivants :

to
le sous-objet CRYPTO_EX_DATA du nouvel objet parent
from
le sous-objet CRYPTO_EX_DATA de l'objet parent original
datap
un pointeur vers une copie du pointeur vers les ex_data originaux
idx
la valeur de retour de CRYPTO_get_ex_new_index() qui a défini ce rappel
argl
l'argl passé à CRYPTO_get_ex_new_index() pour ce idx
argp
l'argp passé à CRYPTO_get_ex_new_index() pour ce idx

À l'intérieur de dup_func, le pointeur data contenu dans l'objet parent original copié peut être accédé en castant et en déréférençant datap, par exemple :

char *orig_data = *(char **)datap;

Si les données originales sont copiées, par exemple d'une manière similaire à

char *new_data;
if ((new_data = strdup(orig_data)) == NULL)
	return 0;

alors le pointeur vers la mémoire nouvellement allouée doit être renvoyé à l'appelant dans l'argument datap, par exemple :

*(char **)datap = new_data;
return 1;

Appeler CRYPTO_set_ex_data(to, idx, new_data) depuis l'intérieur de dup_func n'a aucun effet car le code qui appelle dup_func appelle inconditionnellement CRYPTO_set_ex_data(to, idx, *datap

var>) après dup_func réussit. Par conséquent, si dup_func ne modifie pas *datap, l'objet parent nouvellement créé finit par contenir un pointeur vers la même mémoire que l'objet parent d'origine et toute mémoire allouée dans dup_func est perdue.

Lorsque plusieurs fonctions de rappel sont appelées, elles le sont par ordre croissant de leur valeur idx.

CRYPTO_new_ex_data() est une fonction interne qui initialise le sous-objet ad de l'objet parent, le type de l'objet parent étant spécifié par l'argument class_index. L'initialisation comprend l'appel des fonctions de rappel new_func respectives pour toutes les valeurs idx réservées pour lesquelles de telles fonctions de rappel sont configurées. Malgré son nom, CRYPTO_new_ex_data() ne crée pas un nouvel objet mais exige que ad pointe vers un objet déjà alloué mais encore non initialisé.

CRYPTO_set_ex_data() et CRYPTO_get_ex_data() se comportent de la même manière que RSA_set_ex_data(3) et RSA_get_ex_data(3), respectivement, à la différence qu'ils n'acceptent pas un pointeur vers l'objet parent mais exigent à la place un pointeur vers le sous-objet CRYPTO_EX_DATA de cet objet parent.

CRYPTO_free_ex_data() est une fonction interne qui libère toute mémoire utilisée à l'intérieur du sous-objet ad de l'objet parent, le type de l'objet parent étant spécifié par l'argument class_index. Cela comprend l'appel des fonctions de rappel free_func respectives pour toutes les valeurs idx réservées pour lesquelles de telles fonctions de rappel sont configurées. Malgré son nom, CRYPTO_free_ex_data() ne libère pas ad lui-même.

VALEURS DE RETOUR

CRYPTO_get_ex_new_index() renvoie un nouvel indice égal ou supérieur à 1, ou -1 en cas d'échec d'allocation mémoire.

CRYPTO_EX_new() et CRYPTO_EX_dup() sont censées retourner 1 en cas de succès ou 0 en cas d'échec.

CRYPTO_new_ex_data() et CRYPTO_set_ex_data() retournent 1 en cas de succès ou 0 si l'allocation mémoire échoue.

CRYPTO_get_ex_data() renvoie les données spécifiques à l'application ou NULL si l'objet parent qui contient ad ne contient pas de données spécifiques à l'application à l'idx donné.

ERREURS

Après un échec de CRYPTO_get_ex_new_index(), CRYPTO_new_ex_data(), ou CRYPTO_set_ex_data(), le diagnostic suivant peut être récupéré avec ERR_get_error(3), ERR_GET_REASON(3), et ERR_reason_error_string(3):

ERR_R_MALLOC_FAILURE "échec d'allocation mémoire"
L'allocation mémoire a échoué.

Dans quelques cas d'échec inhabituels, ERR_get_error(3) peut signaler des erreurs différentes causées par OPENSSL_init_crypto(3) ou même aucune.

Même si elle ne peut pas indiquer un échec, CRYPTO_free_ex_data() peut occasionnellement également définir un code d'erreur qui peut être récupéré avec ERR_get_error(3).

CRYPTO_get_ex_data() ne distingue pas le succès de l'échec. Par conséquent, après que CRYPTO_get_ex_data() ait retourné NULL, ERR_get_error(3) retourne 0 à moins qu'il n'y ait encore une erreur antérieure dans la file d'attente.

VOIR AUSSI

BIO_get_ex_new_index(3), DH_get_ex_new_index(3), DSA_get_ex_new_index(3), RSA_get_ex_new_index(3), SSL_CTX_get_ex_new_index(3), SSL_get_ex_new_index(3), SSL_SESSION_get_ex_new_index(3), X509_STORE_CTX_get_ex_new_index(3), X509_STORE_get_ex_new_index(3)

HISTORIQUE

CRYPTO_get_ex_new_index(), CRYPTO_new_ex_data(), CRYPTO_set_ex_data(), CRYPTO_get_ex_data(), et CRYPTO_free_ex_data() sont apparus pour la première fois dans SSLeay 0.9.0 et sont disponibles depuis OpenBSD 2.4.

CRYPTO_EX_new(), CRYPTO_EX_free(), et CRYPTO_EX_dup() sont apparus pour la première fois dans OpenSSL 0.9.5 et sont disponibles depuis OpenBSD 2.7.

POINTS DE VIGILANCE

Si un programme installe des fonctions de rappel, le dernier appel à CRYPTO_get_ex_new_index() installant une fonction d'un certain type pour un class_index donné doit être terminé avant que le premier objet de ce class_index puisse être créé, libéré ou copié, respectivement. Sinon, une initialisation ou une libération incomplète en résultera.

Au moment où new_func est appelé, l'objet parent est seulement partiellement initialisé, donc essayer d'accéder à des données dans cet objet est fortement déconseillé. L'argument data est typiquement NULL dans new_func.

Au moment où free_func est appelé, l'objet parent est déjà largement déconstruit et une partie de son contenu peut avoir été effacée et libérée. Par conséquent, essayer d'accéder à des données dans parent est fortement déconseillé. Selon la documentation de l'API OpenSSL, le code de la bibliothèque appelant free_func serait même autorisé à passer un pointeur NULL pour l'argument parent.

CRYPTO_set_ex_data() et CRYPTO_get_ex_data() ne peuvent raisonnablement pas être utilisés en dehors des fonctions de rappel car aucune fonction d'API ne fournit l'accès à des pointeurs du type CRYPTO_EX_DATA *.

À l'intérieur de new_func, l'appel de CRYPTO_get_ex_data() n'a pas de sens car il retourne toujours NULL, et l'appel de CRYPTO_set_ex_data() n'a pas de sens car new_func n'a pas accès à des données significatives qu'il pourrait stocker, et l'absence de données spécifiques à l'application à un idx donné est déjà suffisamment indiquée par la valeur de retour par défaut NULL de CRYPTO_get_ex_data(), RSA_get_ex_data(3), et fonctions similaires.

À l'intérieur de free_func, l'appel de CRYPTO_get_ex_data() n'a pas de sens car la valeur de retour est déjà disponible dans data, et l'appel de CRYPTO_set_ex_data() n'a pas de sens car l'objet parent, y compris les ex_data qu'il contient, est déjà en cours de déconstruction et n'existera plus lorsque le code de l'application reprendra le contrôle.

À l'intérieur de dup_func, l'appel de CRYPTO_get_ex_data() n'a pas de sens car la valeur de retour pour from est déjà disponible comme *datap, et la valeur de retour pour to est NULL. L'appel de CRYPTO_set_ex_data() n'a pas de sens car la modification de from provoquerait un effet secondaire indésirable dans ce contexte et tenter de modifier to est inefficace comme expliqué ci-dessus.

Par conséquent, le code de l'application ne peut jamais utiliser CRYPTO_set_ex_data() ou CRYPTO_get_ex_data() de manière significative.

Le fait que les fonctions documentées dans la présente page de manuel fassent partie de l'API publique pourrait donner l'impression que les programmes d'application pourraient ajouter le support ex_data à des types d'objets supplémentaires qui ne l'offrent pas par défaut. Cependant, pour les types d'objets intégrés qui n'offrent pas de support ex_, cela n'est pas possible car ces objets ne contiennent pas le sous-objet CRYPTO_EX_DATA requis.

Il est théoriquement possible d'ajouter le support ex_data à un type d'objet défini par l'application en ajoutant un champ CRYPTO_EX_DATA à la déclaration de la structure, un appel à CRYPTO_new_ex_data() au constructeur de l'objet, et un appel à CRYPTO_free_ex_data() au destructeur de l'objet. La documentation OpenSSL mentionne que la constante CRYPTO_EX_INDEX_APP est réservée à cet effet. Cependant, faire cela serait peu utile. Il est beaucoup plus simple d'ajouter tous les champs de données requis à la déclaration de la structure elle-même.

BOGUES

Si new_func ou dup_func échoue, l'échec est ignoré silencieusement par la bibliothèque, entraînant potentiellement un objet initialisé de manière incomplète. Le programme de l'application ne peut pas détecter l'échec.
