CMS_DECRYPT(3) Manuel des fonctions de bibliothèque CMS_DECRYPT(3)

NOM

CMS_decrypt, CMS_decrypt_set1_pkey, CMS_decrypt_set1_key — déchiffrer le contenu d'une structure EnvelopedData CMS

SYNTAXE

bibliothèque « libcrypto »
#include <openssl/cms.h>

int
CMS_decrypt(CMS_ContentInfo *cms, EVP_PKEY *private_key, X509 *certificate, BIO *dcont, BIO *out, unsigned int flags);

int
CMS_decrypt_set1_pkey(CMS_ContentInfo *cms, EVP_PKEY *private_key, X509 *certificate);

int
CMS_decrypt_set1_key(CMS_ContentInfo *cms, unsigned char *symmetric_key, size_t keylen, const unsigned char *id, size_t idlen);

DESCRIPTION

CMS_decrypt() extrait et déchiffre le contenu de la structure CMS EnvelopedData cms en utilisant la private_key et le certificate du destinataire. Il écrit le contenu déchiffré dans out.

Dans le cas rare où le contenu compressé est détaché, passez-le via dcont. Pour une utilisation normale, définissez dcont à NULL.

Bien que le certificate du destinataire ne soit pas nécessaire pour déchiffrer les données, il est nécessaire pour localiser le destinataire approprié (parmi plusieurs possibles) dans la structure CMS.

Si le certificate est défini à NULL, tous les destinataires possibles sont essayés. Ce cas est cependant problématique. Pour contrer l'attaque MMA (attaque de Bleichenbacher sur le remplissage RSA PKCS #1 v1.5), tous les destinataires sont essayés, qu'ils réussissent ou non. Si aucun destinataire ne réussit, une clé symétrique aléatoire est utilisée pour déchiffrer le contenu : cela produira généralement des données incorrectes et pourrait (mais sans garantie) finalement retourner uniquement une erreur de remplissage. Si CMS_decrypt() venait de retourner une erreur lorsque toutes les clés de destinataire chiffrées échouaient à déchiffrer, un attaquant pourrait l'utiliser dans une attaque par timing. Si le drapeau spécial CMS_DEBUG_DECRYPT est défini, le comportement ci-dessus est modifié et une erreur est retournée si aucune clé de destinataire chiffrée ne peut être déchiffrée sans générer une clé de chiffrement de contenu aléatoire. Les applications doivent utiliser ce drapeau avec une extrême prudence, en particulier dans les passerelles automatisées, car il peut les rendre vulnérables aux attaques.

Il est possible de déterminer la clé du destinataire correct par d'autres moyens (par exemple, en la recherchant dans une base de données) et de la définir dans la structure cms à l'avance en utilisant les fonctions utilitaires CMS telles que CMS_decrypt_set1_pkey(). Dans ce cas, les deux certificate et private_key doivent être définis à NULL lors de l'appel ultérieur à CMS_decrypt().

Pour traiter les types KEKRecipientInfo, CMS_decrypt_set1_key() ou CMS_RecipientInfo_set0_key(3) et CMS_RecipientInfo_decrypt(3) doivent être appelées avant CMS_decrypt() et certificate et private_key définis à NULL lors de l'appel ultérieur à CMS_decrypt().

Si le bit CMS_TEXT est défini dans flags, les en-têtes MIME de type text/plain sont supprimés du contenu. Si le contenu n'est pas de type text/plain, une erreur se produit.

VALEURS DE RETOUR

CMS_decrypt(), CMS_decrypt_set1_pkey(), et CMS_decrypt_set1_key() retournent 1 en cas de succès ou 0 en cas d'échec. L'erreur peut être obtenue via ERR_get_error(3).

VOIR AUSSI

CMS_ContentInfo_new(3), CMS_encrypt(3), CMS_get0_RecipientInfos(3)

NORMES

RFC 5652 : Cryptographic Message Syntax (CMS)

  • section 6.1 : Type EnvelopedData
  • section 6.2.3 : Type KEKRecipientInfo

HISTORIQUE

CMS_decrypt(), CMS_decrypt_set1_pkey(), et CMS_decrypt_set1_key() sont apparus pour la première fois dans OpenSSL 0.9.8h et sont disponibles depuis OpenBSD 6.7.

BOGUES

L'absence de traitement en une seule passe et la nécessité de conserver toutes les données en mémoire, comme mentionné dans CMS_verify(3), s'appliquent également à CMS_decrypt().
