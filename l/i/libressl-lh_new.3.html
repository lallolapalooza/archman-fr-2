DESCRIPTION

Cette librairie implémente des tables de hachage dynamiques avec vérification de type. Les entrées de la table de hachage peuvent être des structures arbitraires. Habituellement, elles consistent en des champs clé et valeur.

lh_<type>_new() crée une nouvelle structure LHASH_OF(<type>) pour stocker des entrées de données arbitraires, et fournit les fonctions de rappel (callbacks) de hachage et de comparaison qui seront utilisées pour organiser les entrées de la table. La fonction de rappel de hachage prend un pointeur vers une entrée de la table comme argument et retourne une valeur de hachage unsigned long pour son champ clé. La valeur de hachage est normalement tronquée à une puissance de 2, assurez-vous donc que votre fonction de hachage retourne des bits de faible ordre bien mélangés. La fonction de rappel de comparaison prend deux arguments (pointeurs vers deux entrées de la table de hachage) et retourne 0 si leurs clés sont égales, une valeur non nulle sinon. Si votre table de hachage contiendra des éléments d'un type particulier et que les fonctions de rappel de hachage et de comparaison hachent et comparent ces types, alors les macros DECLARE_LHASH_HASH_FN() et IMPLEMENT_LHASH_COMP_FN() peuvent être utilisées pour créer des wrappers de fonctions de rappel des prototypes requis par lh_<type>_new(). Celles-ci fournissent des casts par variable avant d'appeler les callbacks spécifiques au type écrits par l'auteur de l'application. Ces macros, ainsi que celles utilisées pour les callbacks doall, sont définies comme suit ;

#define	DECLARE_LHASH_HASH_FN(name, o_type) \
	unsigned long name##_LHASH_HASH(const void *);
#define	IMPLEMENT_LHASH_HASH_FN(name, o_type) \
	unsigned long name##_LHASH_HASH(const void *arg) { \
		const o_type *a = arg; \
		return name##_hash(a); }
#define	LHASH_HASH_FN(name) name##_LHASH_HASH

#define	DECLARE_LHASH_COMP_FN(name, o_type) \
	int name##_LHASH_COMP(const void *, const void *);
#define	IMPLEMENT_LHASH_COMP_FN(name, o_type) \
	int name##_LHASH_COMP(const void *arg1, const void *arg2) { \
		const o_type *a = arg1;		    \
		const o_type *b = arg2; \
		return name##_cmp(a,b); }
#define	LHASH_COMP_FN(name) name##_LHASH_COMP

#define	DECLARE_LHASH_DOALL_FN(name, o_type) \
	void name##_LHASH_DOALL(void *);
#define	IMPLEMENT_LHASH_DOALL_FN(name, o_type) \
	void name##_LHASH_DOALL(void *arg) { \
		o_type *a = arg; \
		name##_doall(a); }
#define	LHASH_DOALL_FN(name) name##_LHASH_DOALL

#define	DECLARE_LHASH_DOALL_ARG_FN(name, o_type, a_type) \
	void name##_LHASH_DOALL_ARG(void *, void *);
#define	IMPLEMENT_LHASH_DOALL_ARG_FN(name, o_type, a_type) \
	void name##_LHASH_DOALL_ARG(void *arg1, void *arg2) { \
		o_type *a = arg1; \
		a_type *b = arg2; \
		name##_doall_arg(a, b); }
#define	LHASH_DOALL_ARG_FN(name) name##_LHASH_DOALL_ARG

Un exemple de table de hachage stockant des pointeurs sur des structures de type 'STUFF' pourrait être défini comme suit ;

/* Calculer la valeur de hachage de 'tohash' (implémenté ailleurs) */
unsigned long STUFF_hash(const STUFF *tohash);
/* Ordonner 'arg1' et 'arg2' (implémenté ailleurs) */
int stuff_cmp(const STUFF *arg1, const STUFF *arg2);
/* Créer des fonctions wrapper type-safe pour utilisation dans les internes de LHASH */
static IMPLEMENT_LHASH_HASH_FN(stuff, STUFF);
static IMPLEMENT_LHASH_COMP_FN(stuff, STUFF);
/* ... */
int main(int argc, char *argv[]) {
        /* Créer la nouvelle table de hachage en utilisant les wrappers de hachage/comparaison */
        LHASH_OF(STUFF) *hashtable =
	    lh_STUFF_new(LHASH_HASH_FN(STUFF_hash),
        	LHASH_COMP_FN(STUFF_cmp));
	/* ... */
}

lh_<type>_free() libère la structure LHASH_OF(<type>) table. Les entrées de table de hachage allouées ne seront pas libérées ; envisagez d'utiliser lh_<type>_doall() pour désallouer toutes les entrées restantes dans la table de hachage (voir ci-dessous).

lh_<type>_insert() insère la structure pointée par data dans table. S'il existe déjà une entrée avec la même clé, l'ancienne valeur est remplacée. Notez que lh_<type>_insert() stocke des pointeurs, les données ne sont pas copiées.

lh_<type>_delete() supprime une entrée de table.

lh_<type>_retrieve() recherche une entrée dans table. Normalement, data est une structure avec les champs clé définis ; la fonction retournera un pointeur vers une structure entièrement remplie.

lh_<type>_doall() appellera, pour chaque entrée de la table de hachage, func avec l'élément de données comme paramètre. Pour lh_<type>_doall() et lh_<type>_doall_arg(), les casts de pointeurs de fonction doivent être évités dans les callbacks (voir NOTES) ; utilisez plutôt les macros declare/implement pour créer des wrappers type-safe qui casteront les variables avant d'appeler vos callbacks spécifiques au type. It is used internally by OpenSSL, but it is also available for general use. .PP The functions come in two flavors. There are the generic functions which operate on .I void * pointers, and there are type-specific functions generated by the .B IMPLEMENT_LHASH_..._FN macros. It is strongly recommended to use the type-specific functions for type-safety. .PP The hash table needs two functions to operate correctly: a hash function and a comparison function. The hash function takes a pointer to the data and returns an .Vt unsigned long value. The comparison function takes two pointers to data elements and returns 0 if they are equal, and non-zero otherwise. .PP When creating a hash table, the size of the hash table must be specified. This is a hint to the hash table implementation about how many items to expect. The hash table will grow and shrink automatically as items are inserted and deleted. .PP The .B lh_new() function creates a new hash table with the specified initial size and comparison function. The hash function is implicitly set to .B lh_strhash() for strings. For other data types, the hash function must be provided when the table is created. This is done via the type-specific wrappers, e.g. .BI lh_MYSTRUCT_new(size, compare, hash) would be the way to create a table for .Vt MYSTRUCT *. .PP The .B lh_insert() function inserts an item into the hash table. If an item with the same key already exists, the old item is replaced and the old item is returned. Otherwise, .B NULL is returned. .PP The .B lh_delete() function removes an item from the hash table. The removed item is returned. If the item is not found, .B NULL is returned. .PP The .B lh_retrieve() function retrieves an item from the hash table. The item is returned if found, otherwise .B NULL is returned. .PP .SH "TYPE-SPECIFIC WRAPPERS" .PP To avoid the pitfalls of using .I void * pointers, OpenSSL provides macros to generate type-specific wrapper functions. .PP For example, if you have a structure .Vt STUFF and want to store pointers to it in the hash table, you can use the macros like this: .PP .IP "\fBDECLARE_LHASH_FN(STUFF, STUFF)\fP" .RS .B /* In a header file */ .BI DECLARE_LHASH_FN(STUFF, STUFF) .RE .IP "\fBIMPLEMENT_LHASH_FN(STUFF, STUFF)\fP" .RS .B /* In a source file */ .BI IMPLEMENT_LHASH_FN(STUFF, STUFF) .RE .PP This will declare and implement functions like .BI lh_STUFF_insert(), lh_STUFF_delete(), lh_STUFF_retrieve() and .BI lh_STUFF_doall(), lh_STUFF_doall_arg(). .PP Note that the hash function used must be specified when creating the table. It also, apparently, violates ANSI-C. .PP The LHASH code regards table entries as constant data. As such, it internally represents items inserted via .BI lh_insert() with a .Vt const void * pointer type. This is why callbacks such as those used by .BI lh_doall() and .BI lh_doall_arg() declare their prototypes with "const", even for the parameters that pass back the table items' data pointers — for consistency, user-provided data is "const" at all times as far as the LHASH code is concerned. However, as callers are themselves providing these pointers, they can choose whether they too should be treating all such parameters as constant. .PP As an example, a hash table may be maintained by code that, for reasons of encapsulation, has only "const" access to the data being indexed in the hash table (i.e. it is returned as "const" from elsewhere in their code) — in this case the LHASH prototypes are appropriate as-is. Conversely, if the caller is responsible for the life-time of the data in question, then they may well wish to make modifications to table item passed back in the .BI lh_doall() or .BI lh_doall_arg() callbacks (see the "STUFF_cleanup" example above). If so, the caller can either cast the "const" away (if they're providing the raw callbacks themselves) or use the macros to declare/implement the wrapper functions without "const" types. .PP Callers that only have "const" access to data they are indexing in a table, yet declare callbacks without constant types (or cast the "const" away themselves), are therefore creating their own risks/bugs without being encouraged to do so by the API. On a related note, those auditing code should pay special attention to any instances of DECLARE/IMPLEMENT_LHASH_DOALL_[ARG_]_FN macros that provide types without any "const" qualifiers. .SH INTERNALS .PP The following description is based on the SSLeay documentation: .PP The lhash library implements a hash table described in the .I Communications of the ACM in 1991. What makes this hash table different is that as the table fills, the hash table is increased (or decreased) in size via .BR reallocarray(3) . When a 'resize' is done, instead of all hashes being redistributed over twice as many 'buckets', one bucket is split. So when an 'expand' is done, there is only a minimal cost to redistribute some values. Subsequent inserts will cause more single 'bucket' redistributions but there will never be a sudden large cost due to redistributing all the 'buckets'. .PP The state for a particular hash table is kept in the .Vt LHASH structure. The decision to increase or decrease the hash table size is made depending on the 'load' of the hash table. The load is the number of items in the hash table divided by the size of the hash table. The default values are as follows. If (hash->up_load < load) => expand. If (hash->down_load > load) => contract. The .I up_load has a default value of 1 and .I down_load has a default value of 2. These numbers can be modified by the application by just playing with the .I up_load and .I down_load variables. The 'load' is kept in a form which is multiplied by 256. So hash->up_load=8*256 will cause a load of 8 to be set. .PP If you are interested in performance, the field to watch is .IR num_comp_calls . The hash library keeps track of the 'hash' value for each item so when a lookup is done, the 'hashes' are compared, if there is a match, then a full compare is done, and hash->num_comp_calls is incremented. If num_comp_calls is not equal to num_delete plus num_retrieve, it means that your hash function is generating hashes that are the same for different values. It is probably worth changing your hash function if this is the case because even if your hash table has 10 items in a 'bucket', it can be searched with 10 .Vt unsigned long compares and 10 linked list traverses. This will be much less expensive that 10 calls to your compare function. .PP .BI lh_strhash() is a demo string hashing function. Since the LHASH routines would normally be passed structures, this routine would not normally be passed to .BI lh_new(), rather it would be used in the function passed to .BI lh_new(). .SH SEE ALSO .BR crypto(3) .SH HISTORY .PP .BI lh_new(), lh_free(), lh_insert(), lh_delete(), lh_retrieve(), lh_doall(), and .BI lh_strhash() appeared in SSLeay 0.4 or earlier. .BI lh_doall_arg() first appeared in SSLeay 0.5.1. lh_new, lh_insert, lh_retrieve, lh_delete, lh_free, lh_num, lh_error, lh_stats - Créer, manipuler et détruire une table de hachage libère

SYNOPSIS

#include <openssl/lhash.h>

LHASH_OF(type) *lh_new(unsigned long init_mask, unsigned long id);

int lh_insert(LHASH_OF(type) *lh, void *data);

void *lh_retrieve(LHASH_OF(type) *lh, const void *data);

int lh_delete(LHASH_OF(type) *lh, const void *data);

void lh_free(LHASH_OF(type) *lh);

unsigned long lh_num(const LHASH_OF(type) *lh);

int lh_error(const LHASH_OF(type) *lh);

void lh_stats(const LHASH_OF(type) *lh, FILE *fp);

DESCRIPTION

Les fonctions lh_new(), lh_insert(), lh_retrieve(), lh_delete(), lh_free(), lh_num(), lh_error() et lh_stats() fournissent une implémentation de table de hachage libère.

La macro LHASH_OF(type) est utilisée pour déclarer des pointeurs vers des tables de hachage contenant des éléments de type. Par exemple, LHASH_OF(char) *lh_table; déclare un pointeur vers une table de hachage qui contiendra des chaînes de caractères.

lh_new(init_mask, id) crée une nouvelle table de hachage. init_mask est un masque de bits utilisé pour initialiser la taille de la table de hachage. id est un identifiant unique pour cette table de hachage, utilisé par la fonction de hachage par défaut.

lh_insert(lh, data) insère un élément data dans la table de hachage lh. Elle renvoie 1 en cas de succès, 0 en cas d'échec.

lh_retrieve(lh, data) recherche un élément dans la table de hachage lh qui correspond à data. Elle renvoie un pointeur vers l'élément trouvé, ou NULL s'il n'est pas trouvé.

lh_delete(lh, data) supprime un élément de la table de hachage lh qui correspond à data. Elle renvoie 1 en cas de succès, 0 en cas d'échec.

lh_free(lh) libère toute la mémoire allouée pour la table de hachage lh.

lh_num(lh) renvoie le nombre d'éléments actuellement dans la table de hachage lh.

lh_error(lh) renvoie le code d'erreur de la dernière opération effectuée sur la table de hachage lh. Les valeurs possibles sont 0 (pas d'erreur) et 1 (erreur interne).

lh_stats(lh, fp) imprime des statistiques sur la table de hachage lh dans le fichier fp.

VALEURS DE RETOUR

Voir la description de chaque fonction.

NOTES

Ces fonctions utilisent une implémentation de table de hachage générique. L'utilisateur doit fournir une fonction de hachage appropriée lors de la création de la table.

INTERNES

Non applicable.
