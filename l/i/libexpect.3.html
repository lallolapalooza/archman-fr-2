LIBEXPECT(3) Manuel des fonctions de bibliothèque LIBEXPECT(3)

NOM

libexpect - bibliothèque de dialogue programmé avec des programmes interactifs

DESCRIPTION

Cette bibliothèque contient des fonctions qui permettent d'utiliser Expect comme extension Tcl ou de l'utiliser directement depuis C ou C++ (sans Tcl). L'ajout d'Expect comme extension Tcl est très court et simple, nous allons donc couvrir cela en premier.

SYNTAXE

#include expect_tcl.h
Expect_Init(interp);
cc fichiers... -lexpect5.20 -ltcl7.5 -lm

Note : les versions de la bibliothèque peuvent différer dans la version réelle.

La fonction Expect_Init ajoute des commandes expect à l'interpréteur nommé. Elle évite d'écraser des commandes existantes, cependant des alias commençant par « exp_ » sont toujours créés pour les commandes expect. Ainsi, par exemple, « send » peut être utilisé comme « exp_send ».

En général, vous ne devriez appeler les commandes Expect que via Tcl_Eval. Certaines fonctions auxiliaires peuvent être appelées directement. Elles sont résumées ci-dessous. Elles peuvent être utiles pour construire votre propre `main`. Regardez le fichier `exp_main_exp.c` dans la distribution Expect comme prototype de `main`. Un autre prototype est `tclAppInit.c` dans la distribution source de Tcl. Un prototype pour travailler avec Tk se trouve dans `exp_main_tk.c` dans la distribution Expect.

exp_cmdlinecmds vaut 1 si Expect a été invoqué avec des commandes sur la ligne de commande du programme (en utilisant « -c » par exemple). exp_interactive vaut 1 si Expect a été invoqué avec le drapeau -i ou si aucune commande ou script n'est invoqué. exp_cmdfile est un flux à partir duquel Expect lira les commandes. exp_cmdfilename est le nom d'un fichier qu'Expect ouvrira et à partir duquel il lira les commandes. exp_tcl_debugger_available vaut 1 si le débogueur a été armé.

exp_parse_argv lit la représentation de la ligne de commande. En fonction de ce qui est trouvé, les autres variables listées ici sont initialisées de manière appropriée. exp_interpreter invite interactivement l'utilisateur à entrer des commandes et les évalue. exp_interpret_cmdfile lit le flux donné et évalue toutes les commandes trouvées. exp_interpret_cmdfilename ouvre le fichier nommé et évalue toutes les commandes trouvées. exp_interpret_rcfiles lit et évalue les fichiers .rc. Si my_rc est zéro, alors ~/.expectrc est ignoré. Si sys_rc est zéro, alors le fichier expectrc du système est ignoré. exp_cook renvoie un tampon statique contenant l'argument reproduit avec les sauts de ligne remplacés par des séquences retour chariot-saut de ligne. Le but principal est de permettre la production de messages sans se soucier de savoir si le terminal est en mode brut ou cuit. Si la longueur est zéro, elle est calculée par strlen. exp_error est une fonction de type printf qui écrit le résultat dans interp->result.

DESCRIPTION

exp_spawnl et exp_spawnv créent un nouveau processus par `fork` afin que son entrée standard, sa sortie standard et son erreur standard puissent être lus et écrits par le processus courant. `file` est le nom d'un fichier à exécuter. Les pointeurs `arg` sont des chaînes nulles terminées. Suivant le style de `execve()`, `arg0` (ou `argv[0]`) est généralement un duplicata du nom du fichier.

Quatre interfaces sont disponibles : exp_spawnl est utile lorsque le nombre d'arguments est connu à la compilation. exp_spawnv est utile lorsque le nombre d'arguments n'est pas connu à la compilation. exp_spawnfd est utile lorsqu'un descripteur de fichier ouvert est déjà disponible comme source. exp_popen est expliqué plus loin.

Si le processus est créé avec succès, un descripteur de fichier est retourné, qui correspond à l'entrée standard, la sortie standard et l'erreur standard du processus. Un flux peut être associé au descripteur de fichier en utilisant `fdopen()`. (Cela devrait presque certainement être suivi par `setbuf()` pour désactiver la mise en mémoire tampon des E/S.)

La fermeture du descripteur de fichier sera généralement détectée par le processus comme une EOF. Une fois qu'un tel processus se termine, il doit être attendu (via `wait`) afin de libérer l'espace processus du noyau. (Certains systèmes vous permettent de l'éviter si vous ignorez le signal SIGCHLD).

exp_popen est encore une autre interface, dans le style de `popen()`. Elle prend une ligne de commande du shell Bourne, et retourne un flux qui correspond à l'entrée standard, la sortie standard et l'erreur standard du processus. L'implémentation réelle de exp_popen ci-dessous démontre exp_spawnl.

FILE *
exp_popen(program)
char *program;
{
	FILE *fp;
	int ec;
	if (0 > (ec = exp_spawnl("sh","sh","-c",program,(char *)0)))
		return(0);
	if (NULL == (fp = fdopen(ec,"r+")) return(0);
	setbuf(fp,(char *)0);
	return(fp);
}

Après le lancement d'un processus, la variable exp_pid est définie sur l'ID du processus du nouveau processus. La variable exp_pty_slave_name est définie sur le nom du côté esclave du pty.

Les fonctions de spawn utilisent un pty pour communiquer avec le processus. Par défaut, le pty est initialisé de la même manière que le tty de l'utilisateur (si possible, c'est-à-dire si l'environnement a un terminal de contrôle). Cette initialisation peut être ignorée en définissant `exp_ttycopy` à 0.

Le pty est en outre initialisé à des valeurs par défaut au niveau du système si `exp_ttyinit` est non nul. La valeur par défaut est généralement comparable à « stty sane ».

Les paramètres du tty peuvent être modifiés davantage en définissant la variable exp_stty_init. Cette variable est interprétée dans le style des arguments de `stty`. Par exemple, `exp_stty_init = "sane";` répète l'initialisation par défaut.

Sur certains systèmes, il est possible de rediriger la sortie de la console vers des ptys. Si cela est pris en charge, vous pouvez forcer le prochain spawn à obtenir la sortie de la console en définissant la variable exp_console à 1.

Entre le moment où un processus est lancé et le moment où le nouveau programme prend le contrôle, les fonctions de spawn peuvent nettoyer l'environnement en fermant les descripteurs de fichiers. Par défaut, les seuls descripteurs de fichiers fermés sont ceux internes à Expect et ceux marqués « close-on-exec ».

Si nécessaire, vous pouvez fermer des descripteurs de fichiers supplémentaires en créant une fonction appropriée et en l'assignant à `exp_close_in_child`. La fonction sera appelée après le `fork` et avant le `exec`. (Cela modifie également le comportement de la commande `spawn` dans Expect.)

Si vous utilisez également Tcl, il peut être pratique d'utiliser la fonction `exp_close_tcl_files` qui ferme tous les fichiers entre les descripteurs de fichiers standards par défaut et le descripteur le plus élevé connu de Tcl. (Expect le fait.)

La fonction `exp_child_exec_prelude` est la dernière fonction appelée avant le `exec` réel dans l'enfant. Vous pouvez la redéfinir pour des effets tels que la manipulation de l'uid ou des signaux.

SI VOUS VOULEZ ALLOUER VOTRE PROPRE PTY

extern int exp_autoallocpty;
extern int exp_pty[2];

Les fonctions de spawn utilisent un pty pour communiquer avec le processus. Par défaut, un pty est automatiquement alloué chaque fois qu'un processus est lancé. Si vous souhaitez allouer des ptys vous-même, avant d'appeler l'une des fonctions de spawn, définissez exp_autoallocpty à 0, exp_pty[0] au descripteur de fichier maître du pty et exp_pty[1] au descripteur de fichier esclave du pty. La bibliothèque expect ne fera aucune initialisation de pty (par exemple, `exp_stty_init` ne sera pas utilisé). Le descripteur de fichier esclave du pty sera automatiquement fermé lorsque le processus sera lancé. Après le lancement du processus, toute communication ultérieure se fera avec le descripteur de fichier maître du pty.

TRAITEMENT EXPECT

Bien qu'il soit possible d'utiliser read() pour lire des informations provenant d'un processus lancé par exp_spawnl ou exp_spawnv, des fonctions plus pratiques sont fournies. Ce sont les suivantes :

Les fonctions attendent que la sortie d'un processus corresponde à l'un des modèles, qu'une période spécifiée se soit écoulée, ou qu'un EOF soit rencontré.

Le premier argument de chaque fonction est soit un descripteur de fichier, soit un flux. Les ensembles successifs d'arguments décrivent les modèles et les valeurs entières associées à retourner lorsque le modèle correspond.

L'argument de type est l'une des quatre valeurs. exp_end indique qu'aucun autre modèle n'apparaît. exp_glob indique que le modèle est un modèle de chaîne de style glob. exp_exact indique que le modèle est une chaîne exacte. exp_regexp indique que le modèle est un modèle de chaîne de style regexp. exp_compiled indique que le modèle est un modèle de chaîne de style regexp, et que sa forme compilée est également fournie. exp_null indique que le modèle est un caractère nul (à des fins de débogage, un modèle de chaîne doit également suivre).

Si la forme compilée n'est pas fournie avec les fonctions exp_expectl et exp_fexpectl, toute compilation de modèle effectuée en interne est jetée après le retour de la fonction. Les fonctions exp_expectv et exp_fexpectv compileront automatiquement les modèles et ne les jetteront pas. Au lieu de cela, ils doivent être rejetés par l'utilisateur, en appelant free sur chaque modèle. Il suffit de les rejeter, la dernière fois que les cas sont utilisés.

Les sous-modèles de Regexp correspondant sont stockés dans l'regexp compilé. En supposant que "re" contienne un regexp compilé, la chaîne correspondante se trouve dans re->startp[0]. Les sous-chaînes correspondantes (selon les parenthèses) dans le modèle original se trouvent dans re->startp[1], re->startp[2], et ainsi de suite, jusqu'à re->startp[9]. Les fins de chaîne correspondantes sont re->endp[x] où x est le même index que pour le début de la chaîne.

Le type exp_null correspond si un caractère nul apparaît dans l'entrée. La variable exp_remove_nulls doit être définie sur 0 pour éviter que les caractères nuls ne soient automatiquement supprimés. Par défaut, exp_remove_nulls est défini sur 1 et les caractères nuls sont automatiquement supprimés.

exp_expectv et exp_fexpectv sont utiles lorsque le nombre de modèles n'est pas connu à l'avance. Dans ce cas, les ensembles sont fournis dans un tableau. La fin du tableau est délimitée par une structure exp_case avec le type exp_end. Pour le reste de cette discussion, ces fonctions seront désignées génériquement par expect.

Si un modèle correspond, la valeur entière correspondante est retournée. Les valeurs n'ont pas besoin d'être uniques, cependant elles doivent être positives pour éviter d'être confondues avec EXP_EOF, EXP_TIMEOUT, ou EXP_FULLBUFFER. En cas d'EOF ou de timeout, la valeur EXP_EOF ou EXP_TIMEOUT est retournée. La période de timeout par défaut est de 10 secondes mais peut être modifiée en définissant la variable exp_timeout. Une valeur de -1 désactive le timeout. Une valeur de 0 fait que la fonction expect retourne immédiatement (c'est-à-dire, sonde) après un seul read(). Cependant, elle doit être précédée d'une fonction telle que select, poll, ou un rappel de gestionnaire d'événements pour garantir qu'il y a des données à lire.

Si la variable exp_full_buffer est 1, alors EXP_FULLBUFFER est retournée si exp_buffer se remplit sans qu'aucun modèle n'ait correspondu.

Lorsque la fonction expect retourne, exp_buffer pointe vers le tampon de caractères qui était en cours d'examen pour la correspondance. exp_buffer_end pointe vers le caractère suivant le dernier caractère dans exp_buffer. Si une correspondance a eu lieu, exp_match pointe dans exp_buffer où la correspondance a commencé. exp_match_end pointe vers le caractère suivant où la correspondance s'est terminée.

Chaque fois que de nouvelles entrées arrivent, elles sont comparées à chaque modèle dans l'ordre où elles sont listées. Ainsi, vous pouvez tester l'absence de correspondance en faisant du dernier modèle quelque chose qui apparaîtra certainement, comme une invite. Dans les situations où il n'y a pas d'invite, vous devez vérifier EXP_TIMEOUT (tout comme vous le feriez en interagissant manuellement). Plus de philosophie et de stratégies sur la spécification des modèles expect peuvent être trouvées dans la documentation du programme expect lui-même. Voir VOIR AUSSI ci-dessous.

Les modèles sont les expressions régulières habituelles du style csh. Par exemple, le fragment suivant recherche une connexion réussie, comme lors d'un dialogue telnet.

switch (exp_expectl(
	exp_glob,"connected",CONN,
	exp_glob,"busy",BUSY,
	exp_glob,"failed",ABORT,
	exp_glob,"invalid password",ABORT,
	exp_end)) {
case CONN:	/* logged in successfully */
	break;
case BUSY:	/* couldn't log in at the moment */
	break;
case EXP_TIMEOUT:
case ABORT:	/* can't log in at any moment! */
	break;
default: /* problem with expect */
}

Les astérisques (comme dans l'exemple ci-dessus) sont un raccourci utile pour omettre les caractères de fin de ligne et d'autres détails. Les modèles doivent correspondre à toute la sortie du processus courant (depuis la lecture précédente sur le descripteur ou le flux). Plus de 2000 octets de sortie peuvent forcer les octets précédents à être "oubliés". Ceci peut être modifié en définissant la variable exp_match_max. Notez que des valeurs excessivement grandes peuvent ralentir le moteur de recherche de modèles.

EXECUTION EN ARRIÈRE-PLAN

extern int exp_disconnected;
int exp_disconnect();

Il est possible de déplacer un processus en arrière-plan après qu'il ait commencé à s'exécuter. Une utilisation typique consiste à lire des mots de passe, puis à passer en arrière-plan pour dormir avant d'utiliser les mots de passe pour effectuer un travail réel.

Pour déplacer un processus en arrière-plan, faites un fork, appelez exp_disconnect() dans le processus enfant et exit() dans le processus parent. Ceci dissocie votre processus du terminal de contrôle. Si vous souhaitez déplacer un processus en arrière-plan d'une autre manière, vous devez définir la variable exp_disconnected à 1. Ceci permet aux processus lancés par la suite d'être démarrés correctement.

MULTIPLEXAGE

Par défaut, les fonctions expect bloquent lors d'une lecture sur un unique descripteur de fichier. Si vous souhaitez attendre des modèles provenant de plusieurs descripteurs de fichier, utilisez select, poll, ou un gestionnaire d'événements. Ils vous indiqueront quel descripteur de fichier est prêt à être lu.

Lorsqu'un descripteur de fichier est prêt à être lu, vous pouvez utiliser les fonctions expect pour effectuer une seule lecture en définissant le timeout à 0.

CONTRÔLE DE L'ESCLAVE

void
exp_slave_control(fd,enable)
int fd;
int enable;

Le piégeage des pty est normalement effectué automatiquement par les fonctions expect. Cependant, si vous souhaitez émettre un ioctl, par exemple, directement sur le périphérique esclave, vous devriez désactiver temporairement le piégeage.

Le piégeage des pty peut être contrôlé avec exp_slave_control. Le premier argument est le descripteur de fichier correspondant au processus lancé. Le second argument est 0 si le piégeage doit être désactivé et 1 s'il doit être activé.

ERREURS

Toutes les fonctions signalent les erreurs en retournant -1 et en définissant errno.

Les erreurs qui surviennent après le fork des fonctions spawn (par exemple, tentative de lancer un programme inexistant) sont écrites dans le stderr du processus, et seront lues par le premier expect.

SIGNaux

extern int exp_reading;
extern jmp_buf exp_readenv;

expect utilise alarm() pour le timeout, donc si vous générez des alarmes pendant expect, cela provoquera un timeout prématuré.

En interne, expect appelle read() qui peut être interrompu par des signaux. Si vous définissez des gestionnaires de signaux, vous pouvez choisir de redémarrer ou d'abandonner la lecture interne de expect. La variable, exp_reading, est vraie si (et seulement si) la lecture de expect a été interrompue. longjmp(exp_readenv,EXP_ABORT) abandonnera la lecture. longjmp(exp_readenv,EXP_RESTART) redémarrera la lecture.

JOURNALISATION

extern int exp_loguser;
extern int exp_logfile_all
extern FILE *exp_logfile;

Si exp_loguser est non nul, expect envoie toute sortie du processus lancé vers stdout. Les programmes interactifs ayant tendance à faire écho de leur entrée, cela suffit généralement à montrer les deux côtés de la conversation. Si exp_logfile est également non nul, cette même sortie est écrite dans le flux défini par exp_logfile. Si exp_logfile_all est non nul, exp_logfile est écrit indépendamment de la valeur de exp_loguser.

DÉBOGAGE

Bien que je considère la bibliothèque facile à utiliser, je pense que le programme expect autonome est beaucoup, beaucoup plus facile à utiliser que de travailler avec le compilateur C et son cycle habituel d'édition, de compilation et de débogage. Contrairement aux programmes C typiques, la plupart du débogage ne consiste pas à faire accepter vos programmes par le compilateur C - mais plutôt à obtenir le dialogue correct. De plus, la traduction de scripts d'expect vers C n'est généralement pas nécessaire. Par exemple, la vitesse des dialogues interactifs n'est pratiquement jamais un problème. Veuillez donc essayer d'abord le programme 'expect' autonome. Je soupçonne qu'il s'agit d'une solution plus appropriée pour la plupart des gens que la bibliothèque.

Néanmoins, si vous vous sentez obligé de déboguer en C, voici quelques outils pour vous aider.

DESCRIPTION

            
The spawn functions start a new process.
                exp_spawnp and exp_spawnl are most
                common. exp_spawnp takes a command name and a
                variable number of string arguments, terminated by a NULL pointer.
                exp_spawnl takes a command name and a variable number
                of string arguments, terminated by a NULL pointer.
                exp_spawnv and exp_spawnve take an
                argument vector and environment vector, respectively. The file
                descriptor returned is the standard input file descriptor for the
                spawned process. This is the file descriptor that you will use
                for all subsequent interactions with the process.

            
The expect functions read from the given file
                descriptor (or FILE *) until a pattern is matched. The
                patterns are specified in a format string. The format string
                consists of a sequence of literal strings, glob-style
                wildcards, and POSIX regular expressions. The function returns
                the index of the pattern that was matched.
                exp_expectl and exp_expectp use a
                variable argument list, while exp_expectv takes a
                `va_list'. The `p' versions are equivalent to the `l' versions
                except that they take a variable number of arguments instead of
                a va_list.

            
There are several versions of the expect function,
                corresponding to the type of input stream you are reading from.
                exp_expect* reads from the standard input of the
                current process. exp_fexpect* reads from the given
                FILE *. exp_file_expect* reads from the given
                file descriptor. These functions are generally preferred, as they
                are significantly faster than the FILE * versions.

            
exp_close closes the file descriptor
                returned by exp_spawn*. exp_popen*
                functions are convenient wrappers around exp_spawn*
                and exp_close. exp_close is the
                inverse of exp_spawn.

            
exp_set_log and exp_set_log_file
                cause all subsequent interactions with the spawned process to be
                logged to the specified file or FILE *. If the argument
                is NULL, logging is disabled. exp_set_child_log and
                exp_set_child_log_file do the same for the child
                process's output. Use exp_close_log and
                exp_close_child_log to close the log files.

            
exp_set_modem_ports provides a list of
                modem ports. This is used to enable dial-up connections.

            
exp_set_auto_decoding enables or disables
                automatic character encoding detection. When enabled, the library
                tries to guess the character encoding of the output from the
                spawned process. The default is enabled.

            
exp_set_read_chunk_size sets the size of
                the chunks of data read from the spawned process. The default is
                1024 bytes.

            
exp_set_pty_width and
                exp_set_pty_height set the dimensions of the pseudo-terminal
                (pty) used by the spawned process. exp_get_pty_width
                and exp_get_pty_height retrieve these values. The
                default width is 80 and the default height is 24.

            
exp_set_search_strategy sets the pattern
                matching strategy. The default is to try glob-style patterns
                first, then POSIX regular expressions. Other strategies are
                available (see the full documentation).

            
exp_cooked, exp_hex, and
                exp_expand are utility functions for manipulating
                strings.

            
exp_close_tty closes the controlling
                terminal of the current process.

            
exp_set_output_buffer_size and
                exp_get_output_buffer_size control the size of the
                output buffer used by the library. The default is 1024 bytes.

            
exp_set_input_buffer_size and
                exp_get_input_buffer_size control the size of the
                input buffer used by the library. The default is 1024 bytes.

            
exp_set_force_kterm forces the use of
                kterm, regardless of other settings. Useful for some terminals.

            
exp_set_kterm_timeout and
                exp_get_kterm_timeout set the timeout value for kterm
                operations. The default is 10 seconds.

            
exp_set_keep_stty_local controls whether
                the stty local mode is preserved after spawning a process. The
                default is to unset it.

            
exp_set_pty_os_type and
                exp_get_pty_os_type set and get the operating system
                type for the pseudo-terminal. This can affect how certain
                commands behave.

            
exp_set_autodetect_pty_os and
                exp_get_autodetect_pty_os enable or disable automatic
                detection of the pseudo-terminal's operating system type. The
                default is enabled.

        

        

            
IF YOU WANT TO ALLOCATE YOUR OWN PTY

            
Under normal circumstances, expect manages its
                own pseudo-terminals (ptys). However, if you need to allocate your
                own pty, you can use the exp_open_pty function. This
                function opens a pair of ptys, and returns the slave file
                descriptor and the master file descriptor. You can then use
                exp_spawnve to spawn a process on the slave file
                descriptor, and then use exp_read to read from the master
                file descriptor.

            
int exp_open_pty(int *master, int *slave);

        

        

            
EXPECT PROCESSING

            
The expect functions can be passed a format
                string that describes the patterns to look for. The format string
                can contain literal strings, glob-style wildcards, and POSIX
                regular expressions. The expect function returns the index
                of the pattern that was matched.

            
For example, to match either "hello" or "world", you
                could use:

            
exp_expectl(fd, "hello", "world", NULL);

            
This would return 0 if "hello" was matched, and 1 if
                "world" was matched.

            
You can also use glob-style wildcards:

            
exp_expectl(fd, "user@*", "password:", NULL);

            
This would match "user@" followed by any characters, or
                "password:".

            
POSIX regular expressions can also be used:

            
exp_expectl(fd, "[0-9]+", NULL);

            
This would match one or more digits.

        

        

            
RUNNING IN THE BACKGROUND

            
The expect library is designed for interactive
                use. However, you can use it to run programs in the background.
                Simply use the exp_spawn* functions as usual, and then
                detach the process from the controlling terminal. You can do this
                by forking and having the parent process exit immediately.

        

        

            
MULTIPLEXING

            
The expect library supports multiplexing, which
                allows you to interact with multiple processes simultaneously.
                You can use the exp_select function to wait for activity
                on multiple file descriptors. exp_select takes a
                file descriptor, a timeout, and a set of file descriptors to
                watch. It returns the file descriptor that is ready for reading.

        

        

            
SLAVE CONTROL

            
The expect library provides functions for
                controlling the slave side of the pseudo-terminal. These
                functions are useful for tasks such as setting the terminal
                dimensions, enabling or disabling canonical mode, and controlling
                echoing.

        

        

            
ERRORS

            
The expect functions return -1 on error. The
                specific error can be determined by checking the global variable
                errno.

        

        

            
SIGNALS

            
The expect library installs signal handlers for
                SIGINT, SIGQUIT, and SIGTSTP. These handlers are used to ensure
                that the spawned process is terminated cleanly when the parent
                process receives these signals.

        

        

            
LOGGING

            
The expect library can log all interactions with
                the spawned process to a file or a FILE *. This is useful
                for debugging and for auditing purposes. Use
                exp_set_log or exp_set_log_file to
                specify the log file. Use exp_set_child_log or
                exp_set_child_log_file to log the child's output
                separately. Use exp_close_log and
                exp_close_child_log to close the log files.

        

        

            
DEBUGGING

            
extern int exp_is_debugging;
extern FILE *exp_debugfile;

            
While expect dialogues seem very intuitive, trying to
                codify them in a program can reveal many surprises in a program's
                interface. Therefore a variety of debugging aids are available.
                They are controlled by the above variables, all 0 by default.

            
Debugging information internal to expect is
                sent to stderr when exp_is_debugging is non-zero. The
                debugging information includes every character received, and every
                attempt made to match the current input against the patterns. In
                addition, non-printable characters are translated to a printable
                form. For example, a control-C appears as a caret followed by a C.
                If exp_logfile is non-zero, this information is also
                written to that stream.

            
If exp_debugfile is non-zero, all normal and
                debugging information is written to that stream, regardless of the
                value of exp_is_debugging.

        

        

            
CAVEATS

            
The stream versions of the expect functions are
                much slower than the file descriptor versions because there is no
                way to portably read an unknown number of bytes without the
                potential of timing out. Thus, characters are read one at a time.
                You are therefore strongly encouraged to use the file descriptor
                versions of expect (although, automated versions of
                interactive programs don't usually demand high speed anyway).

            
You can actually get the best of both worlds, writing
                with the usual stream functions and reading with the file
                descriptor versions of expect as long as you don't attempt
                to intermix other stream input functions (e.g., fgetc). To do
                this, pass fileno(stream) as the file descriptor each time.
                Fortunately, there is little reason to use anything but the
                expect functions when reading from interactive programs.

            
There is no matching exp_pclose to exp_popen (unlike
                popen and pclose). It only takes two functions to close down a
                connection (fclose() followed by waiting on the pid), but it is
                not uncommon to separate these two actions by large time
                intervals, so the function seems of little value.

            
If you are running on a Cray running Unicos (all I know
                for sure from experience), you must run your compiled program as
                root or setuid. The problem is that the Cray only allows root
                processes to open ptys. You should observe as much precautions as
                possible: If you don't need permissions, setuid(0) only
                immediately before calling one of the spawn functions and
                immediately set it back afterwards.

            
Normally, spawn takes little time to execute. If
                you notice spawn taking a significant amount of time, it is
                probably encountering ptys that are wedged. A number of tests are
                run on ptys to avoid entanglements with errant processes. (These
                take 10 seconds per wedged pty.) Running expect with the -d
                option will show if expect is encountering many ptys in
                odd states. If you cannot kill the processes to which these ptys
                are attached, your only recourse may be to reboot.

        

        

            
BUGS

            
The exp_fexpect functions don't work at all
                under HP-UX - it appears to be a bug in getc. Follow the advice
                (above) about using the exp_expect functions (which
                doesn't need to call getc). If you fix the problem (before I do -
                please check the latest release) let me know.

        

        

            
SEE ALSO

            
An alternative to this library is the expect
                program. expect interprets scripts written in a high-level
                language which direct the dialogue. In addition, the user can take
                control and interact directly when desired. If it is not
                absolutely necessary to write your own C program, it is much
                easier to use expect to perform the entire interaction. It
                is described further in the following references:

            
"expect: Curing Those Uncontrollable Fits of
                Interactivity" by Don Libes, Proceedings of the Summer
                1990 USENIX Conference, Anaheim, California, June 11-15, 1990.

            
"Using expect to Automate System Administration
                Tasks" by Don Libes, Proceedings of the 1990 USENIX
                Large Installation Systems Administration Conference, Colorado
                Springs, Colorado, October 17-19, 1990.

            
expect(1), alarm(3), read(2), write(2), fdopen(3),
                execve(2), execvp(3), longjmp(3), pty(4).

            
There are several examples C programs in the test
                directory of expect's source distribution which use the
                expect library.
