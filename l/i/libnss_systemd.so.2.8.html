NOM

nss-systemd, libnss_systemd.so.2 - Résolution des noms d'utilisateur et de groupe UNIX pour la recherche d'utilisateurs/groupes via Varlink

SYNTAXE

libnss_systemd.so.2

DESCRIPTION

nss-systemd est un module plug-in pour la fonctionnalité GNU Name Service Switch (NSS) de la bibliothèque GNU C (glibc), fournissant la résolution des noms d'utilisateur et de groupe UNIX pour les services implémentant l'API User/Group Record Lookup API via Varlink[1], tels que le gestionnaire de système et de services systemd(1) (pour sa fonctionnalité DynamicUser=, voir systemd.exec(5) pour plus de détails), systemd-homed.service(8), ou systemd-machined.service(8).

Ce module garantit également que les utilisateurs et groupes root et nobody (c'est-à-dire les utilisateurs/groupes avec les UID/GID 0 et 65534) restent résolubles à tout moment, même s'ils ne sont pas listés dans /etc/passwd ou /etc/group, ou si ces fichiers sont manquants.

Ce module utilise de préférence systemd-userdbd.service(8) pour résoudre les utilisateurs et les groupes, mais fonctionne également sans que le service ne soit en cours d'exécution.

Pour activer le module NSS, ajoutez "systemd" aux lignes commençant par "passwd:", "group:", "shadow:" et "gshadow:" dans /etc/nsswitch.conf.

Il est recommandé de placer "systemd" après l'entrée "files" des lignes /etc/nsswitch.conf afin que les mappages basés sur /etc/passwd, /etc/group, /etc/shadow et /etc/gshadow aient la priorité.

ENREGISTREMENTS STATIQUES JSON UTILISATEUR/GROUPE DROP-IN

Outre les enregistrements d'utilisateurs/groupes acquis via les interfaces IPC Varlink susmentionnées et les comptes racine et nobody synthétisés, ce module rend également disponibles au système les comptes d'utilisateurs et de groupes définis dans des fichiers drop-in statiques dans les répertoires /etc/userdb/, /run/userdb/, /run/host/userdb/ et /usr/lib/userdb/.

C'est un mécanisme simple pour fournir des enregistrements statiques d'utilisateurs et de groupes via des fichiers drop-in JSON. Ces enregistrements d'utilisateurs doivent être définis dans le format décrit par la spécification JSON User Records[2] et être placés dans l'un des répertoires susmentionnés sous un nom de fichier composé du nom d'utilisateur suffixé par .user, avec un mode d'accès lisible par tous. Une liaison symbolique nommée d'après l'UID de l'enregistrement utilisateur formaté en décimal et suffixé par .user, pointant vers le fichier d'enregistrement principal, doit également être créée, afin de permettre les recherches par nom d'utilisateur et par UID. Des données d'enregistrement d'utilisateur privilégié (par exemple, des mots de passe UNIX hachés) peuvent éventuellement être fournies également, dans une paire de fichiers compagnons séparés avec le suffixe .user-privileged. Les données doivent être stockées dans un fichier régulier nommé d'après le nom d'utilisateur, suffixé par .user-privileged, et une liaison symbolique y pointant, nommée d'après l'UID numérique utilisé formaté en décimal avec le même suffixe. Ces fichiers compagnons ne doivent pas être lisibles par quiconque sauf root. Exemple :

-rw-r--r--. 1 root root  723 May 10 foobar.user
-rw-------. 1 root root  123 May 10 foobar.user-privileged
lrwxrwxrwx. 1 root root   19 May 10 4711.user -> foobar.user
lrwxrwxrwx. 1 root root   19 May 10 4711.user-privileged -> foobar.user-privileged

De même, les enregistrements de groupe suivant le format décrit dans JSON Group Record[3] peuvent être définis, en utilisant les suffixes de fichier .group et .group-privileged.

Les fichiers d'enregistrement d'utilisateur/groupe principaux (c'est-à-dire ceux avec les suffixes .user et .group) ne doivent pas contenir la section "privileged" comme décrit dans les spécifications. Les fichiers d'enregistrement d'utilisateur/groupe privilégiés (c'est-à-dire ceux avec les suffixes .user-privileged et .group-privileged) doivent contenir exclusivement cette section.

En plus des deux types de fichiers d'enregistrement d'utilisateur et des deux types de fichiers d'enregistrement de groupe, il existe un cinquième type de fichier qui peut être placé dans les répertoires recherchés : les fichiers qui indiquent l'appartenance d'utilisateurs à des groupes. Spécifiquement, pour chaque paire utilisateur/groupe où l'utilisateur doit être membre d'un groupe, un fichier nommé "nomutilisateur:nomgroupe.membership" doit être créé, c'est-à-dire le nom d'utilisateur UNIX textuel, suivi de deux points, suivi du nom de groupe UNIX textuel, suffixé par ".membership". Le contenu de ces fichiers n'est actuellement pas lu, et les fichiers doivent être créés vides. La simple existence de ces fichiers suffit à affecter l'appartenance d'un utilisateur/groupe. Si un programme fournit des fichiers d'enregistrement d'utilisateur et/ou de groupe dans les répertoires recherchés, il doit toujours également créer de tels fichiers, à la fois pour les appartenances aux groupes principaux et auxiliaires.

Notez que les enregistrements statiques d'utilisateur/groupe ne remplacent généralement pas les enregistrements conflictuels dans /etc/passwd ou /etc/group ou d'autres bases de données de comptes. En fait, avant d'intégrer ces fichiers, il convient de prendre un niveau de précaution raisonnable pour éviter les conflits de noms d'utilisateur/groupe et d'UID/GID.

Le service systemd-userdb-load-credentials.service s'exécute automatiquement au démarrage et installe ces fichiers à partir des enregistrements d'utilisateurs passés via les identifiants système. Voir userdbctl(1) et systemd.system-credentials(7) pour plus de détails.

CONFIGURATION DANS /ETC/NSSWITCH.CONF

Voici un exemple de fichier /etc/nsswitch.conf qui active correctement nss-systemd :

passwd:         files systemd
group:          files [SUCCESS=merge] systemd
shadow:         files systemd
gshadow:        files systemd
hosts:          mymachines resolve [!UNAVAIL=return] files myhostname dns
networks:       files
protocols:      db files
services:       db files
ethers:         db files
rpc:            db files
netgroup:       nis
