NAME

libircclient - Documentation de Libircclient

INTRODUCTION

Introduction

Vue d'ensemble

Libircclient est une bibliothèque petite mais extrêmement puissante qui implémente le protocole client IRC. Elle est conçue pour être petite, rapide, portable et compatible avec les normes RFC ainsi qu'avec des fonctionnalités non standard mais populaires. Elle est parfaite pour construire des clients et des bots IRC.

Caractéristiques

  • API C complète ;
  • Couverture complète du protocole IRC fournissant des fonctions ;
  • Prend en charge plusieurs connexions simultanées à différents serveurs IRC ou même au même serveur ;
  • Prend en charge les connexions IRC en clair et SSL avec vérification optionnelle du certificat ;
  • Prise en charge complète du multithreading, la bibliothèque est thread-safe ;
  • Tout le traitement peut être géré par un seul thread, même si plusieurs connexions sont utilisées ;
  • Interface asynchrone basée sur les événements et non bloquante implémentée avec des callbacks ;
  • Prise en charge supplémentaire pour les applications basées sur des sockets, qui utilisent select();
  • Prise en charge CTCP avec code de réponse intégré en option ;
  • Prend en charge CTCP PING nécessaire pour passer la « vérification d'usurpation » implémentée par la plupart des serveurs IRC ;
  • Prise en charge flexible de DCC, y compris le chat DCC et le transfert de fichiers DCC ;
  • Peut initier et réagir aux DCC initiés ;
  • Peut accepter ou refuser les sessions DCC de manière asynchrone ;
  • Écrit en C pur, taille binaire très petite (environ 30 Ko selon la plateforme) ;
  • Compatible avec tous les clients IRC testés ;
  • Logiciel libre distribué sous licence LGPLv3 ;
  • Prend en charge Linux ainsi que tout Unix conforme à POSIX, Mac OS X et Microsoft Windows ;
  • Prend en charge les architectures 32/64 bits ainsi que les architectures non x86 ;
  • Prise en charge IPv6 (optionnelle, doit être compilée) ;
  • Prise en charge OpenSSL (optionnelle, doit être compilée) ;
  • Interface Cocoa par Nathan Ollerenshaw ;
  • Documentation complète, exemples et FAQ ;

Problèmes connus

Même si cela est possible en utilisant plusieurs sessions, la bibliothèque n'est pas adaptée pour se connecter simultanément à un grand nombre de serveurs IRC. Si vous souhaitez tout de même l'utiliser, vous devrez surmonter les points suivants :

  • Vous ne pouvez pas utiliser la boucle principale dans irc_run() car elle ne prend en charge qu'une seule session. Vous devriez utiliser irc_add_select_descriptors()
  • Vous devrez gérer les reconnexions séparément en traitant les valeurs de retour pertinentes de irc_process_select_descriptors()
  • Si vous souhaitez utiliser poll/epoll() au lieu de select(), vous devrez écrire plus de logique car ce n'est pas directement pris en charge. Voir la FAQ.
  • La bibliothèque n'est pas optimisée pour une faible empreinte mémoire par connexion, chaque connexion non SSL utilise au moins 4 Ko, avec environ 32 Ko par connexion pour le SSL.

INTÉGRATION

Intégration

Exigences

Systèmes d'exploitation et compilateurs pris en charge

La bibliothèque a été largement testée sous Linux x86 et x86_64. Elle a également été testée sur Solaris x86, Linux sur ARM et Linux sur les plates-formes MIPS, sur Mac OS X sur x86 et sur diverses versions de Microsoft Windows.

Compilation

Sur Linux, FreeBSD et Mac OS X, la bibliothèque doit être compilée et installée avant utilisation, sauf si vous utilisez un paquet précompilé fourni par votre distribution de système d'exploitation. S'il est fourni, il est recommandé de l'utiliser, car il serait mis à jour à partir du dépôt central lorsque les bugs sont corrigés.

Sur Microsoft Windows, les binaires officiels de la bibliothèque sont fournis, vous n'avez donc pas besoin de la compiler. Sauf si vous avez de l'expérience dans la compilation avec Cygwin, il est conseillé de ne pas compiler à partir des sources et d'utiliser le binaire officiel.

Bibliothèques requises

La bibliothèque ne dépend que de libc (glibc-devel sous Linux) et gcc, bien que les exemples nécessitent également libstdc++ (libstdc++-devel) et g++. La version minimale prise en charge est glibc 2.2, bien que si IPv6 est demandé, au moins glibc 2.4 est requis.

Si la bibliothèque est compilée avec le support SSL, le paquet de développement openssl (openssl-devel) doit être installé.

Sur Microsoft Windows, Cygwin avec les paquets de développement nécessaires doit être installé (ainsi que openssl-devel).

Compilation

La bibliothèque est configurée et construite de la manière Unix standard :

./configure [--enable-openssl] [--enable-ipv6]
make

Installation

Bien qu'aucune installation ne soit nécessaire pour utiliser les bibliothèques, la cible d'installation est fournie pour plus de commodité et peut être appelée via sudo make install

Liaison

Liez votre application avec libircclient.a ou libircclient.so selon vos besoins. Si vous utilisez la bibliothèque fournie par le système, veuillez lier avec libircclient.so.

Si vous avez compilé la bibliothèque avec le support SSL, vous devrez lier avec les bibliothèques OpenSSL ; ajoutez -lcrypto -lssl à vos LDFLAGS

Sur Microsoft Windows, veuillez lier avec libircclient.lib qui lie implicitement avec libircclient.dll

Programmation

Initialisation

Inclure les en-têtes

Avant d'utiliser la bibliothèque, vous devez inclure l'en-tête de la bibliothèque libircclient.h. Vous voudrez peut-être aussi inclure libirc_rfcnumeric.h qui fournit les codes RFC :

#include "libircclient.h"
#include "libirc_rfcnumeric.h"

Créer des gestionnaires d'événements

Contrairement à la plupart des protocoles réseau comme HTTP ou SMTP, le protocole IRC est basé sur des événements. Les événements proviennent du serveur de manière asynchrone. Certains événements sont déclenchés par votre action (comme rejoindre un canal ou changer de pseudo), certains sont déclenchés par d'autres utilisateurs IRC (comme vous envoyer un message), et certains sont déclenchés par le serveur IRC lui-même (comme envoyer des notes d'opération ou invoquer les services NickServ).

Libircclient aide à gérer ces événements en fournissant la structure de gestion des événements. Elle déclare les événements que vous pouvez définir dans votre application, et lorsqu'un tel événement est reçu du serveur, le callback approprié sera appelé. Le nombre d'événements que vous devez gérer dépend de la complexité de votre client et des fonctionnalités qu'il prend en charge.

En général, seuls deux événements doivent être gérés pour fournir une fonctionnalité minimale : event_connect et event_numeric. Cependant, il est recommandé de créer un vidage d'événements f

unction et utilisez-la pour tous les événements non utilisés afin de vous assurer de ne manquer aucun événement important en attendant le mauvais. Voir la fonction dump_event dans le fichier examples/irctest.c

Initialisation spécifique à Windows

Si vous liez avec la bibliothèque statique sous Microsoft Windows, vous devez initialiser la bibliothèque Winsock2 avant d'appeler les fonctions de la bibliothèque. Cela peut être fait comme suit :

WSADATA wsaData;
if ( WSAStartup ( MAKEWORD (2, 2), &wsaData) != 0 )
    // signaler une erreur

Cependant, si vous liez avec la bibliothèque dynamique (libircclient.dll) qui est celle par défaut si vous utilisez la compilation officielle, ce n'est pas nécessaire car la DLL l'initialise automatiquement lors du chargement.

Créer une session IRC

Pour utiliser la bibliothèque, au moins une session IRC doit être créée. Une session peut être utilisée pour établir une seule connexion à un serveur IRC pour un pseudo donné. Cependant, plusieurs sessions peuvent être créées si nécessaire.

Pour créer une session, appelez la fonction irc_create_session() :

// La structure de callbacks IRC
irc_callbacks_t callbacks;
// L'initialiser
memset ( &callbacks, 0, sizeof(callbacks) );
// Configurer les événements obligatoires
callbacks.event_connect = event_connect;
callbacks.event_numeric = event_numeric;
// Configurer le reste des événements
// Maintenant, créer la session
irc_session_t * session = irc_create_session( &callbacks );
if ( !session )
    // Gérer l'erreur

Ce code peut être répété autant de fois que nécessaire pour créer plusieurs sessions. La même structure de callbacks peut être réutilisée pour plusieurs sessions.

Définir les options

Outre le débogage, il existe deux options que vous pourriez avoir besoin d'utiliser. L'option LIBIRC_OPTION_STRIPNICKS active l'analyse automatique des pseudonymes, et comme il est difficile d'imaginer un cas où elle ne devrait pas être activée, nous l'activons :

irc_option_set( session, LIBIRC_OPTION_STRIPNICKS );

La deuxième option pourrait vous être utile si vous utilisez des connexions SSL et prévoyez de vous connecter à des serveurs qui utilisent des certificats auto-signés. Voir la documentation pour LIBIRC_OPTION_SSL_NO_VERIFY

Se connecter au serveur

Pour initier la connexion au serveur IRC, appelez la fonction irc_connect() :

// Se connecter à un serveur IRC normal
if ( irc_connect (session, "irc.example.com", 6667, 0, "mynick", "myusername", "myrealname" ) )
  // Gérer l'erreur : irc_strerror() et irc_errno()

Pour initier la connexion au serveur IRC via SSL, appelez la fonction irc_connect() et préfixez le nom d'hôte ou l'adresse IP par un symbole dièse (#) :

// Se connecter au serveur SSL ; #192.168.1.1 est aussi possible
if ( irc_connect (session, "#irc.example.com", 6669, 0, "mynick", "myusername", "myrealname" ) )
  // Gérer l'erreur : irc_strerror() et irc_errno()

Cette fonction initie uniquement la connexion, donc lorsqu'elle retourne avec succès, la connexion n'est qu'initiée, mais pas encore établie. Ensuite, l'un des événements suivants se produit après avoir invoqué le gestionnaire réseau :

  • Si la connexion est établie, vous recevrez l'événement event_connect - c'est pourquoi il est important de le gérer
  • Si la connexion a échoué, la fonction de gestion du réseau retournera un échec

Se connecter au serveur IPv6

Pour initier la connexion au serveur IPv6, appelez la fonction irc_connect6() :

if ( irc_connect6 (session, "2001:0db8:85a3:0042:1000:8a2e:0370:7334", 6669, 0, "mynick", "myusername", "myrealname" ) )
  // Gérer l'erreur : irc_strerror() et irc_errno()

Le reste des détails, y compris la valeur de retour et le SSL, sont les mêmes qu'avec la connexion régulière.

Démarrer la boucle réseau

Pour laisser la bibliothèque gérer les événements, il existe deux scénarios. Vous pouvez soit invoquer la boucle réseau intégrée qui gérera le réseau et appellera vos événements, soit écrire votre propre boucle.

Invoquer la boucle réseau intégrée est plus simple mais limité. Comme elle boucle jusqu'à ce que la connexion soit terminée, ce n'est pas une option pour une application graphique (sauf si vous démarrez la boucle dans un thread séparé, ce que vous pouvez faire). Et comme cette boucle ne peut gérer qu'une seule session, il est impossible de l'utiliser si vous souhaitez gérer plusieurs sessions IRC. Dans ces cas, la boucle réseau personnalisée, décrite ci-dessous, doit être utilisée.

Pour démarrer la boucle d'événements, appelez la fonction irc_run() :

if ( irc_run (s) )
  // Soit la connexion au serveur n'a pas pu être établie, soit elle s'est terminée. Voir irc_errno()

N'oubliez pas que l'appel à irc_run() ne retournera pas tant que la connexion au serveur ne sera plus active.

Utiliser la boucle réseau personnalisée

Si vous utilisez plusieurs sessions ou si vous avez votre propre gestionnaire de sockets, vous pouvez utiliser la boucle réseau personnalisée. Dans ce cas, votre application doit être basée sur select() (voir la FAQ si vous souhaitez utiliser d'autres méthodes de polling). Et vous devez exécuter la boucle suivante :

// S'assurer que toutes les sessions IRC sont connectées
if ( !irc_is_connected(session) )
  // reconnecter, ou abandonner
// Créer les structures pour select()
struct timeval tv;
fd_set in_set, out_set;
int maxfd = 0;
// Attendre 0,25 secondes pour les événements - vous pouvez attendre plus longtemps si vous le souhaitez, mais la bibliothèque a des timeouts internes
// donc elle doit être appelée périodiquement même s'il n'y a pas d'événements réseau
tv.tv_usec = 250000;
tv.tv_sec = 0;
// Initialiser les ensembles
FD_ZERO (&in_set);
FD_ZERO (&out_set);
// Ajouter vos propres descripteurs pour lesquels vous devez attendre, le cas échéant
...
// Ajouter les descripteurs de session IRC - appeler irc_add_select_descriptors() pour chaque session active
irc_add_select_descriptors( session, &in_set, &out_set, &maxfd );
// Appeler select()
if ( select (maxfd + 1, &in_set, &out_set, 0, &tv) < 0 )
   // Erreur
// Vous pouvez également vérifier si un descripteur est actif, mais encore une fois, la bibliothèque doit gérer les timeouts internes,
// vous devez donc appeler irc_process_select_descriptors() pour chaque session au moins une fois toutes les quelques secondes
...
// Appeler irc_process_select_descriptors() pour chaque session avec l'ensemble de descripteurs
if ( irc_process_select_descriptors (session, &in_set, &out_set) )
    // La connexion a échoué, ou le serveur s'est déconnecté. Gérez-le.
// Recommencer

Salons et utilisateurs

Avant d'appeler l'une de ces fonctions, assurez-vous d'être connecté au serveur.

Rejoindre et quitter un salon

Pour rejoindre un salon, appelez la fonction irc_cmd_join() avec le nom du salon :

// Rejoindre le salon #linux
if ( irc_cmd_join( session, "#linux", 0 ) )
  // erreur de connexion la plus probable
// Rejoindre le salon $science protégé par la clé secrète *superpassword*
if ( irc_cmd_join( session, "$science", "superpassword" ) )
  // erreur de connexion la plus probable

Vous pouvez rejoindre autant de salons que vous le souhaitez, bien que le serveur puisse restreindre le nombre de salons que vous pouvez rejoindre simultanément.

Si la jonction a réussi, vous recevrez l'événement event_join. Vous devez attendre cet événement avant de pouvoir effectuer des opérations sur le salon (comme envoyer des messages). Cependant, vous n'avez PAS à attendre cet événement pour émettre une deuxième commande JOIN comme montré dans l'exemple ci-dessus.

Si la jonction n'a pas réussi, vous recevrez l'erreur via event_numeric.

Pour quitter un salon, appelez la fonction irc_cmd_part() avec le nom du salon :

// Quitter le salon #linux
if ( irc_cmd_part( session, "#linux" ) )
  // erreur de connexion la plus probable
// Quitter le salon $science
if ( irc_cmd_part( session, "$science" ) )
  // erreur de connexion la plus probable

Envoyer un message à un salon ou à un utilisateur

Après avoir rejoint le salon, vous pouvez envoyer un message au salon en utilisant la fonction irc_cmd_msg() avec le nom du salon :

// Dire "Salut !" à tout le monde dans le salon #linux
if ( irc_cmd_msg( session, "#linux", "Salut !" ) )
  // erreur de connexion la plus probable

Techniquement, le protocole n'exige pas de rejoindre le salon pour envoyer des messages dans le salon. Cependant, la plupart des serveurs définissent par défaut le mode du salon qui empêche les utilisateurs qui n'ont pas rejoint le salon d'envoyer des messages dans le salon.

La même fonction est utilisée pour envoyer un message "privé" à un autre utilisateur. Les messages "privés" ne transitent pas par les salons, mais ils transitent toujours par le serveur IRC (parfois plusieurs serveurs) et peuvent être vus ou même enregistrés par les opérateurs du réseau IRC.

// Dire "Salut !" à l'utilisateur IRC john
if ( irc_cmd_msg( session, "john", "Salut !" ) )
  // erreur de connexion la plus probable

Si le message a été envoyé avec succès, vous ne recevrez aucune confirmation ni aucun événement. Vous ne recevrez l'erreur que via event_numeric si le message n'a pas été envoyé.

Recevoir des messages d'un salon ou d'un utilisateur

Vous recevez les messages du salon

Gestion des messages reçus

Les messages généraux du canal sont gérés en gérant le canal d'event_channel. Chaque fois que quelqu'un dit quelque chose dans le canal, cet événement est appelé.

Vous recevez les messages « privés » d'autres utilisateurs en gérant l'event_privmsg.

Ces gestionnaires d'événements doivent être créés dans votre application et transmis à la bibliothèque lorsque vous *créez une session IRC*.

Envoyer un message d'action

Les messages « action », également appelés messages /me, sont des messages CTCP formatés de manière spéciale. Cependant, la bibliothèque contient une fonction spéciale pour les envoyer, irc_cmd_me(). Les actions envoyées par d'autres personnes sont gérées par l'événement event_ctcp_action.

Comme pour l'envoi de messages, aucune confirmation n'est reçue en cas de succès.

Envoyer une requête CTCP

D'autres requêtes CTCP telles que PING, VERSION, etc. doivent être envoyées en appelant irc_cmd_ctcp_request(). Si la réponse CTCP est reçue, elle est gérée par l'événement event_ctcp_rep.

Gestion du chat DCC

Implémentation du rappel DCC

Que vous prévoyiez d'initier des chats DCC ou d'y répondre, vous devez implémenter le *rappel DCC* :

void dcc_callback (irc_session_t * session, irc_dcc_t id, int status, void * ctx, const char * data, unsigned int length)
{
   if ( status )
   {
       // Si status est LIBIRC_ERR_CLOSED, le chat a été fermé par la partie distante.
       // Sinon, il s'agit d'une erreur ; le CHAT s'est terminé ou n'a pas pu être établi. status est le code d'erreur ; voir irc_strerror(status)
   }
   else if ( length == 0 )
   {
       // La partie distante a accepté la demande de chat, envoyez-lui un "bonjour"
       irc_dcc_text( session, id, "Hello!" );
   }
   else
   {
       // Nous avons reçu le message de chat de la partie distante
       printf ( "La partie distante a dit : %s\n", data );
   }
}

Ce rappel doit être passé soit à la fonction irc_dcc_chat() qui initie la requête, soit à la fonction irc_dcc_accept() qui accepte la requête DCC CHAT initiée par un autre utilisateur.

Initiation du CHAT DCC

Vous pouvez initier un chat DCC avec un autre utilisateur en appelant irc_dcc_chat() :

// L'identifiant de la session de chat DCC sera retourné dans cette variable
irc_dcc_t dccid;
// Initier le chat DCC avec l'utilisateur IRC "john"
if ( irc_dcc_chat( session, 0, "john", dcc_callback, &dccid ) )
  // signaler l'erreur

Vous pouvez maintenant passer à d'autres tâches. Lorsque John accepte ou refuse le chat, dcc_callback() sera appelé, et il sera possible d'utiliser la fonction irc_dcc_text() pour envoyer les messages de chat. Le rappel sera également appelé chaque fois qu'un nouveau message de chat sera reçu, ou lorsque le chat sera terminé ou interrompu en raison d'une erreur réseau.

Répondre aux requêtes CHAT DCC

Pour répondre aux requêtes CHAT DCC, votre application doit implémenter l'événement event_dcc_chat_req. Le rappel pourrait être implémenté comme suit :

void callback_event_dcc_chat( irc_session_t * session, const char * nick, const char * addr, irc_dcc_t dccid )
{
    // L'utilisateur 'nick' de l'adresse IP 'addr' essaie d'initier un chat DCC avec nous.
    // Stockez ces informations dans la file d'attente interne de l'application avec le dccid afin que le rappel puisse retourner
    dcc_queue.store( dccid, "CHAT de " + nick + " Adresse IP : " + addr );
}

et enregistré lors de la création de la session IRC. Si votre application ne gère pas du tout le DCC, vous pouvez simplement appeler la fonction irc_dcc_decline() dans le rappel.

Si elle le fait, nous ne stockons que ces informations dans le rappel, et retournons. En effet, le traitement des événements s'arrêtera jusqu'à ce que le rappel retourne, donc faire apparaître la boîte de dialogue demandant la confirmation de l'utilisateur arrêterait le traitement d'autres événements tels que les messages du canal. Même si votre application est automatique et n'affiche pas de boîtes de dialogue, il est toujours préférable de séparer la logique du chat de la logique du rappel.

Quelque temps plus tard, l'application vérifierait la file d'attente dans le thread GUI, obtiendrait ces informations et afficherait la boîte de dialogue demandant le retour de l'utilisateur. Ensuite, si la demande de chat a été acceptée, l'application appellerait la fonction irc_dcc_accept(), et si elle a été refusée, l'application appellerait la fonction irc_dcc_decline(). Les deux fonctions accepteront le dccid qui identifie cette requête spécifique :

// Quelque part dans le thread GUI
if ( !dcc_queue.empty() )
{
    // Obtenez les informations DCC et affichez la boîte de dialogue à l'utilisateur
    irc_dcc_t dccid = dcc_chat_queue.top().dccid;
    ...
    // Réagissez à l'entrée de l'utilisateur
    if ( dialog.isAccepted() )
        irc_dcc_accept( session, dccid, 0, dcc_callback );
    else
        irc_dcc_decline( session, dccid );
}

Envoyer des messages CHAT

Une fois la session de chat établie, vous pouvez envoyer les messages de chat en utilisant la fonction irc_dcc_text(). Notez que vous devez passer l'identifiant de la session dcc au lieu du pseudo :

irc_dcc_text( session, dccid, "Salut !" );

Gestion du transfert de fichiers DCC

Cette section couvre la gestion de l'envoi et de la réception de fichiers via DCC.

Implémentation du rappel

Que vous prévoyiez d'envoyer ou de recevoir des fichiers via dcc, vous devez implémenter le *rappel DCC*. Bien que le même rappel puisse être utilisé pour l'envoi et la réception, ce n'est pas recommandé car la logique est différente. Par conséquent, l'implémentation suggérée serait d'utiliser des rappels différents comme suggéré :

// Ce rappel est utilisé lorsque nous envoyons un fichier à la partie distante
void callback_dcc_send_file (irc_session_t * session, irc_dcc_t id, int status, void * ctx, const char * data, unsigned int length)
{
   if ( status )
   {
       // Il s'agit d'une erreur ; l'opération d'envoi a été terminée ou la connexion n'a pas pu être établie. status est le code d'erreur ; voir irc_strerror(status)
   }
   else
   {
       // Nous avons envoyé des données à la partie distante, 'length' indique la quantité de données envoyées
       printf ( "Octets envoyés : %d\n", length );
   }
}
// Ce rappel est utilisé lorsque nous recevons un fichier de la partie distante
void callback_dcc_recv_file (irc_session_t * session, irc_dcc_t id, int status, void * ctx, const char * data, unsigned int length)
{
   if ( status )
   {
       // Il s'agit d'une erreur ; l'opération d'envoi a été terminée ou la connexion n'a pas pu être établie. status est le code d'erreur ; voir irc_strerror(status)
   }
   else if ( data == 0 )
   {
       // Le transfert de fichier est terminé
       printf ( "Fichier reçu avec succès\n" );
   }
   else
   {
       // Du contenu de fichier supplémentaire a été reçu. Stockez-le en mémoire, écrivez-le sur disque ou autre
       printf ( "Reçu %d octets de données\n", length );
   }
}

Ce rappel doit être passé soit à la fonction irc_dcc_sendfile() qui initie la requête, soit à la fonction irc_dcc_accept() qui accepte la requête DCC RECVFILE initiée par un autre utilisateur.

Envoi du fichier via DCC

Vous pouvez initier l'envoi d'un fichier via DCC à un autre utilisateur en appelant irc_dcc_sendfile() :

// L'identifiant de la session DCC sera retourné dans cette variable
irc_dcc_t dccid;
// Initier l'envoi du fichier "/etc/passwd" via le chat DCC à l'utilisateur IRC "john"
if ( irc_dcc_sendfile( session, 0, "john", "/etc/passwd", callback_dcc_send_file, &dccid ) )
  // signaler l'erreur

Vous pouvez maintenant passer à d'autres tâches. Lorsque John accepte la requête, le fichier sera envoyé et callback_dcc_send_file() sera appelé chaque fois qu'un morceau de fichier sera envoyé. Le rappel sera également appelé lorsque le fichier aura été envoyé, ou lorsque l'envoi aura été interrompu en raison d'une erreur réseau.

Réception d'un fichier via DCC

Pour recevoir un fichier via DCC, un utilisateur distant doit initier la requête DCC pour vous envoyer un fichier. Pour recevoir cette requête, votre application doit implémenter l'événement event_dcc_send_req. Le rappel pourrait être implémenté comme suit :

void callback_event_dcc_file( irc_session_t * session, const char * nick, const char * addr, const char * filename, unsigned long size, irc_dcc_t dccid )
{

Gestion des couleurs

Suppression des couleurs du message

Si votre bot réagit aux messages texte, vous devez supprimer les couleurs des messages texte avant de les traiter. Sinon, l'utilisateur qui envoie le message coloré n'obtiendra pas la même réaction que l'utilisateur qui n'utilise pas de couleurs, et certains utilisateurs utilisent des couleurs par défaut.

Utilisez la fonction irc_color_strip_from_mirc() pour supprimer les couleurs ANSI du message texte. Elle ne modifie pas les messages qui n'utilisent pas de couleurs.

Conversion des couleurs

La bibliothèque prend en charge la traduction des couleurs et peut convertir les couleurs entre les couleurs ANSI utilisées par les clients IRC et leur représentation textuelle. L'utilisation des couleurs est généralement limitée aux messages et aux raisons spécifiées par l'utilisateur. Vous ne pouvez pas utiliser de couleurs dans le cadre de votre pseudo ou du nom de votre canal.

Utilisez la fonction irc_color_convert_from_mirc() pour convertir les couleurs d'ANSI vers la représentation textuelle de la bibliothèque, et irc_color_convert_to_mirc() pour convertir la représentation textuelle des couleurs de la bibliothèque en ANSI.

N'oubliez pas de libérer() le pointeur retourné une fois qu'il n'est plus utilisé.

Divers

Suivi des pseudos utilisateurs

Si votre application maintient des quotas spécifiques à l'utilisateur, il est important de suivre les changements de pseudos. Étant donné que le pseudo est le seul identifiant disponible pour vous, chaque fois que l'utilisateur change de pseudo, vous devez mettre à jour votre base de données de quotas. Pour ce faire, vous devez intercepter l'événement event_nick. Voir l'exemple examples/censor.c pour plus de détails.

irc_dcc_callback_t

Prototype :

typedef void (*irc_dcc_callback_t) (irc_session_t * session, irc_dcc_t id, int status, void * ctx, const char * data, unsigned int length)

Paramètres :

session La session IRC qui génère un événement (celle retournée par irc_create_session)
id L'ID de la session DCC
status Le statut de la connexion DCC. 0 signifie qu'il n'y a pas d'erreur, sinon contient un code d'erreur
ctx Le contexte fourni par l'utilisateur
data Données reçues (si disponibles), sinon NULL
length Taille des données reçues s'il y a des données

Description :

Ce callback est appelé pour toutes les fonctions DCC lorsqu'un changement d'état se produit.

Pour DCC CHAT, le callback est appelé comme suit :
  • status est LIBIRC_ERR_CLOSED: la connexion est fermée par l'hôte distant. Après le retour du callback, la session DCC est automatiquement détruite
  • status est non nul mais pas LIBIRC_ERR_CLOSED: erreur d'entrée/sortie du socket (erreur de connexion, erreur d'acceptation, erreur de réception, erreur d'envoi). Après le retour du callback, la session DCC est automatiquement détruite
  • status est zéro et length est zéro: le côté distant a accepté la demande de discussion
  • status est zéro et length est non nul: nouveau message de discussion reçu, data contient le message (une chaîne terminée par null), length contient la longueur de la chaîne sans le terminateur null
Pour DCC SEND, pendant l'envoi du fichier, le callback est appelé comme suit :
  • status est non nul: erreur d'entrée/sortie du socket (erreur de connexion, erreur d'acceptation, erreur de réception, erreur d'envoi). Après le retour du callback, la session DCC est automatiquement détruite
  • status est zéro: un autre paquet de données a été envoyé, length contient la quantité totale de données envoyées jusqu'à présent, data est NULL
Pour DCC RECV, pendant l'envoi du fichier, le callback est appelé comme suit :
  • status est non nul: erreur d'entrée/sortie du socket (erreur de connexion, erreur d'acceptation, erreur de réception, erreur d'envoi). Après le retour du callback, la session DCC est automatiquement détruite.
  • status est zéro et data est NULL: le fichier a été reçu avec succès. Après le retour du callback, la session DCC est automatiquement détruite.
  • status est zéro et data n'est pas NULL: nouvelles données reçues, data contient les données reçues, length contient la quantité de données reçues.

irc_cmd_channel_mode

Prototype :

int irc_cmd_channel_mode(irc_session_t *session, const char *channel, const char *mode)

Paramètres :

session Handle de session IRC
channel Nom d'un canal
mode Mode à changer. Si NULL, le mode du canal n'est pas changé mais l'ancien mode est renvoyé.

Description :

Cette fonction est utilisée pour changer ou visualiser les modes du canal. Notez que seuls les opérateurs du canal peuvent changer le mode du canal.

Le mode de canal est représenté par une combinaison de plusieurs lettres. Chaque lettre a sa propre signification dans les modes de canal. La plupart des lettres de mode de canal sont booléennes (c'est-à-dire qu'elles ne peuvent qu'être définies ou réinitialisées), mais quelques lettres de mode de canal acceptent un paramètre. Toutes les options de canal sont définies en ajoutant un signe plus devant la lettre, et réinitialisées en ajoutant un signe moins devant la lettre.

Voici la liste des modes de canal "standard" :

o nickname accorde (+o un surnom) ou retire (-o un surnom) les privilèges d'opérateur de canal à un surnom. Ce mode affecte les utilisateurs dans le canal, pas le canal lui-même. Exemples : "+o tim", "-o watson"
p définit (+p) ou réinitialise (-p) le drapeau de canal privé. Les canaux privés sont affichés dans la liste des canaux comme 'Prv', sans le sujet
s définit (+s) ou réinitialise (-s) le drapeau de canal secret. Les canaux secrets ne sont pas du tout affichés dans la liste des canaux
i définit (+i) ou réinitialise (-i) le drapeau de canal invité uniquement. Lorsque le drapeau est défini, seules les personnes invitées par irc_cmd_invite() peuvent rejoindre ce canal
t permet (+t) ou interdit (-t) la modification du sujet par les utilisateurs qui ne sont pas opérateurs du canal. Lorsque le drapeau est défini, seuls les opérateurs du canal peuvent modifier le sujet du canal
n définit (+n) ou réinitialise (-n) la protection contre les utilisateurs qui n'ont pas rejoint le canal. Lorsque le mode +n est défini, seuls les utilisateurs qui ont rejoint le canal peuvent envoyer des messages au canal
m définit (+m) ou réinitialise (-m) la modération du canal. Lorsque le mode de modération est défini, seuls les opérateurs du canal et les utilisateurs ayant le mode utilisateur +v peuvent parler dans le canal
v nickname accorde (+v pseudo) ou retire (-v pseudo) à l'utilisateur la capacité de parler sur un canal modéré. Exemples : "+v bob", "-v joy"
l number définit (+l 20) ou supprime (-l) la restriction du nombre maximum d'utilisateurs autorisés dans le canal. Lorsque la restriction est définie et qu'il y a un certain nombre d'utilisateurs dans le canal, personne ne peut plus rejoindre le canal
k key définit (+k motdepasse) ou supprime (-k) le mot de passe du canal. Lorsque la restriction est définie, tout utilisateur rejoignant le canal doit fournir une clé de canal
b mask définit (+b !*@.mil) ou supprime (-b !*@.mil) le masque d'interdiction sur un utilisateur pour l'empêcher de rejoindre le canal. Notez que pour supprimer l'interdiction, vous devez spécifier le masque d'interdiction à supprimer, pas juste "-b".

Notez que la liste réelle des modes de canal dépend du serveur IRC, et peut être plus longue. Si vous connaissez des modes de canal populaires qui ne sont pas listés ici, veuillez me contacter.

Le code de retour 0 signifie que la commande a été envoyée au serveur IRC avec succès. Cela ne signifie pas que l'opération a réussi, et vous devez attendre l'événement approprié ou le code d'erreur via l'événement event_numeric.

  • LIBIRC_RFC_RPL_CHANNELMODEIS
  • LIBIRC_RFC_RPL_BANLIST
  • LIBIRC_RFC_RPL_ENDOFBANLIST
Réponses d'erreur possibles pour cette commande selon le RFC1459 :
  • LIBIRC_RFC_ERR_NEEDMOREPARAMS
  • LIBIRC_RFC_ERR_CHANOPRIVSNEEDED
  • LIBIRC_RFC_ERR_NOSUCHNICK
  • LIBIRC_RFC_ERR_NOTONCHANNEL

Le système de couleurs de libircclient est conçu pour être facile à utiliser et portable entre différents clients IRC. Chaque couleur ou option de format est décrite à l'aide de commandes textuelles écrites entre crochets.

Les codes possibles sont :
  • [B] ... [/B] - mode de formatage gras. Tout ce qui se trouve entre [B] et [/B] est écrit en gras.
  • [I] ... [/I] - mode de formatage italique/inverse. Tout ce qui se trouve entre [I] et [/I] est écrit en italique, ou inversé (cependant, comme certains clients sont incapables de rendre le texte en italique, la plupart des clients l'affichent comme du texte normal avec les couleurs de premier plan et d'arrière-plan inversées).
  • [U] ... [/U] - mode de formatage souligné. Tout ce qui se trouve entre [U] et [/U] est écrit souligné.
  • [COLOR=RED] ... [/COLOR] - écrire le texte en utilisant la couleur de premier plan spécifiée. La couleur est définie en utilisant le mot-clé COLOR, un signe égal suivi du code de couleur du texte (voir ci-dessous).
  • [COLOR=RED/BLUE] ... [/COLOR] - écrire le texte en utilisant la couleur de premier plan et d'arrière-plan spécifiée. La couleur est définie en utilisant le mot-clé COLOR, un signe égal suivi du code de couleur du premier plan, un tiret et un code de couleur d'arrière-plan.
Les couleurs suivantes sont supportées :
  • WHITE
  • BLACK
  • DARKBLUE
  • DARKGREEN
  • RED
  • BROWN
  • PURPLE
  • OLIVE
  • YELLOW
  • GREEN
  • TEAL
  • CYAN
  • BLUE
  • MAGENTA
  • DARKGRAY
  • LIGHTGRAY

Exemples de séquences de couleurs :

Hello, [B]Tim[/B].
[U]Arsenal[/U] got a [COLOR=RED]red card[/COLOR]
The tree[U]s[/U] are [COLOR=GREEN/BLACK]green[/COLOR]

Décrit la structure des callbacks d'événements utilisée pour enregistrer les callbacks.

Toute la communication avec le réseau IRC est basée sur des événements. En général, un événement est quelque chose généré par quelqu'un d'autre sur le réseau, ou par le serveur IRC lui-même. "Quelqu'un vous envoie un message", "Quelqu'un a rejoint le canal", "Quelqu'un a quitté IRC" - tous ces messages sont des événements.

Chaque événement a son propre gestionnaire d'événements, qui est appelé lorsque l'événement approprié est reçu. Vous n'avez pas à définir tous les gestionnaires d'événements ; définissez uniquement les gestionnaires pour les événements que vous devez intercepter et mettez les pointeurs des gestionnaires restants à NULL.

event_connect

Cet événement est déclenché lorsque la connexion au serveur IRC est établie avec succès et que le MOTD est reçu. Selon le serveur, il peut aussi être possible d'envoyer des commandes avant cet événement.

Cet événement utilise le callback irc_event_callback_t avec les valeurs suivantes :

origin Inutilisé, défini à NULL
params Inutilisé, défini à NULL
event_nick

Cet événement est déclenché à la réception du message NICK. Il se produit lorsqu'un des utilisateurs (y compris vous) dans l'un des canaux que vous surveillez (auxquels vous avez adhéré) a changé de pseudo.

Changer votre propre pseudo générera également cet événement. Notez que le serveur peut changer votre pseudo indépendamment, vous devez donc suivre cet événement.

Cet événement utilise le callback irc_event_callback_t avec les valeurs suivantes :

origin Le pseudo d'origine (peut être le vôtre !)
params params[0] contient un nouveau pseudo.
event_quit

Cet événement est déclenché à la réception du message QUIT. Il se produit lorsqu'un des utilisateurs dans l'un des canaux que vous surveillez (auxquels vous avez adhéré) s'est déconnecté du serveur IRC.

Cet événement utilise le callback irc_event_callback_t avec les valeurs suivantes :

origin L'utilisateur qui s'est déconnecté
params params[0] est optionnel, contient la raison spécifiée par l'utilisateur pour quitter
event_join

Cet événement est déclenché lors de la réception d'un message JOIN. Il se produit lorsqu'un nouvel utilisateur rejoint le canal que vous surveillez (auquel vous avez adhéré). Il se produit également lorsque vous rejoignez un nouveau canal.

Notez que vous pourriez être "forcé" de rejoindre un canal (et donc de recevoir cet événement) sans émettre la commande JOIN. Un cas typique est lorsque le bot NickServ du serveur est configuré pour vous rejoindre automatiquement à des canaux spécifiques.

Cet événement utilise le callback irc_event_callback_t avec les valeurs suivantes :

origin L'utilisateur qui a rejoint le canal (cela peut être vous !)
params params[0] contient le nom du canal
event_part

Cet événement est déclenché lors de la réception d'un message PART. Il se produit lorsqu'un utilisateur quitte le canal que vous surveillez (auquel vous avez adhéré). Il se produit également lorsque vous quittez un canal.

Cet événement utilise le callback irc_event_callback_t avec les valeurs suivantes :

origin L'utilisateur qui a quitté le canal (cela peut être vous !)
params params[0] contient le nom du canal
d>params[0] contient le nom du canal, params[1] est facultatif et contient la raison spécifiée par l'utilisateur
event_mode

Cet événement est déclenché à la réception d'un message MODE de canal. Il se produit lorsque quelqu'un a modifié le(s) mode(s) du canal que vous surveillez (auquel vous êtes abonné).

Cet événement utilise le rappel irc_event_callback_t avec les valeurs suivantes :

origin L'utilisateur qui a effectué le changement
params params[0] contient le nom du canal, params[1] contient les changements de mode du canal, tels que "+t", "-i", params[2] facultatif, contient l'argument du mode du canal (par exemple, un pseudo pour le mode +o)
event_umode

Cet événement est déclenché à la réception d'un message MODE d'utilisateur. Il se produit lorsque votre mode utilisateur est modifié.

Cet événement utilise le rappel irc_event_callback_t avec les valeurs suivantes :

origin L'utilisateur qui a effectué le changement
params params[0] contient le nom du canal, params[1] contient les changements de mode utilisateur, tels que "+t", "-i"
event_topic

Cet événement est déclenché à la réception d'un message TOPIC. Il se produit lorsque quelqu'un a modifié le sujet du canal que vous surveillez (auquel vous êtes abonné).

Cet événement utilise le rappel irc_event_callback_t avec les valeurs suivantes :

origin L'utilisateur qui a effectué le changement
params params[0] contient le nom du canal, params[1] facultatif, contient le nouveau sujet
event_kick

Cet événement est déclenché à la réception d'un message KICK. Il se produit lorsque quelqu'un (vous y compris) a expulsé quelqu'un (vous y compris) du canal que vous surveillez (auquel vous êtes abonné).

Erreurs

LIBIRC_ERR_OK

(0): Aucune erreur

LIBIRC_ERR_INVAL

(1): Une valeur invalide a été fournie pour l'un des arguments d'une fonction. Par exemple, fournir la valeur NULL comme argument de canal de irc_cmd_join() produit cette erreur.

LIBIRC_ERR_RESOLV

(2): Le nom d'hôte fourni pour la fonction irc_connect() n'a pas pu être résolu en une adresse IP valide.

LIBIRC_ERR_SOCKET

(3): Le nouveau socket n'a pas pu être créé ou rendu non bloquant. Signifie généralement que le serveur manque de ressources, ou (espérons-le pas) un bug dans libircclient. Voir aussi Pourquoi est-ce que j'obtiens une erreur LIBIRC_ERR_SOCKET sous Win32 lorsque j'utilise une bibliothèque statique ?

LIBIRC_ERR_CONNECT

(4): Le socket n'a pas pu se connecter au serveur IRC, ou à la partie DCC de destination. Signifie généralement soit que le serveur IRC est en panne, soit que son adresse est invalide. Pour le DCC, la raison est généralement le pare-feu sur votre ordinateur ou celui de destination, qui refuse le transfert DCC.

LIBIRC_ERR_CLOSED

(5): La connexion IRC a été fermée par le serveur IRC (ce qui pourrait signifier qu'un opérateur IRC vous a banni du serveur - testez votre client avant de vous connecter à un serveur public), ou la connexion DCC a été fermée par le pair distant - par exemple, l'autre côté vient de terminer l'application IRC. Généralement, ce n'est pas une erreur.

LIBIRC_ERR_NOMEM

(6): Il y a deux raisons possibles pour cette erreur. La première est que la mémoire n'a pas pu être allouée pour l'utilisation interne de libircclient, et cette erreur est généralement fatale. La seconde raison est que le tampon de commandes (qui met en file d'attente les commandes prêtes à être envoyées au serveur IRC) est plein, et ne peut pas encore accepter plus de commandes. Dans ce dernier cas, vous devriez simplement attendre et répéter la commande plus tard.

LIBIRC_ERR_ACCEPT

(7): Une connexion DCC chat/send du pair distant n'a pas pu être acceptée. Soit la connexion a été simplement terminée avant d'être acceptée, soit il y a un bug dans libircclient.

LIBIRC_ERR_NODCCSEND

(9): Un nom de fichier fourni à irc_dcc_sendfile() n'a pas pu être envoyé. Soit ce n'est pas un fichier régulier (un répertoire ou un socket, par exemple), soit il n'a pas pu être lu. Voir aussi LIBIRC_ERR_OPENFILE

LIBIRC_ERR_READ

(10): Soit un fichier DCC n'a pas pu être lu (par exemple, a été tronqué pendant l'envoi), soit un socket DCC renvoie une erreur de lecture, ce qui signifie généralement que la connexion réseau est terminée.

LIBIRC_ERR_WRITE

(11): Soit un fichier DCC n'a pas pu être écrit (par exemple, il n'y a pas d'espace disque libre), soit un socket DCC renvoie une erreur d'écriture, ce qui signifie généralement que la connexion réseau est terminée.

LIBIRC_ERR_STATE

(12): La fonction est appelée alors qu'elle ne devrait pas l'être. Par exemple, irc_cmd_join() a été appelé avant que la connexion au serveur IRC ne réussisse, et event_connect est appelé.

LIBIRC_ERR_TIMEOUT

(13): La requête DCC a expiré. Il existe un minuteur pour chaque requête DCC, qui suit les connexions, les acceptations et les requêtes DCC non acceptées/refusées. Pour chaque requête, ce minuteur est actuellement réglé sur 60 secondes. Si la requête DCC n'a pas été connectée, acceptée ou refusée pendant ce temps, elle sera terminée avec cette erreur.

LIBIRC_ERR_OPENFILE

(14): Le fichier spécifié dans irc_dcc_sendfile() n'a pas pu être ouvert.

LIBIRC_ERR_TERMINATED

(15): La connexion au serveur IRC a été terminée.

LIBIRC_ERR_NOIPV6

(16): La fonction qui nécessite le support IPv6 a été appelée, mais le support IPv6 n'a pas été compilé dans l'application.

LIBIRC_ERR_SSL_NOT_SUPPORTED

(17): La connexion SSL était requise mais la bibliothèque n'a pas été compilée avec le support SSL.

LIBIRC_ERR_SSL_INIT_FAILED

(18): La bibliothèque SSL n'a pas pu être initialisée.

LIBIRC_ERR_CONNECT_SSL_FAILED

(19): La négociation SSL a échoué lors de la tentative de connexion au serveur. Généralement, cela signifie que vous essayez d'utiliser SSL mais que vous tentez de vous connecter à un port non SSL.

LIBIRC_ERR_SSL_CERT_VERIFY_FAILED

ANNEXE

Questions fréquemment posées

Pourquoi obtiens-je une erreur LIBIRC_ERR_SOCKET sous Win32 lorsque j'utilise une bibliothèque statique ?

Parce que sous Win32, vous devez initialiser l'API Winsock avant de l'utiliser :

WSADATA wsaData;
if ( WSAStartup ( MAKEWORD (2, 2), &wsaData) != 0 )
    // signaler une erreur
// Vous pouvez maintenant utiliser libircclient

Vous devez le faire UNE FOIS dans votre application, et comme libircclient ne sait pas si vous l'avez déjà initialisé ou non, il ne contient aucun code d'initialisation Winsock.

Que signifie-t-il que le protocole IRC est basé sur les événements ?

Le protocole IRC lui-même est asynchrone et piloté par le serveur. Pour vous, cela signifie ce qui suit :

  • Pour toute commande IRC, il n'est pas possible d'obtenir une réponse immédiate indiquant si la commande a réussi ou non. Au lieu de cela, le serveur enverra la réponse dans un court (ou long) délai.
  • Pour certaines commandes IRC, il n'y a aucune réponse de 'succès'. Par exemple, lorsque vous envoyez un message texte, le serveur IRC n'enverra rien pour confirmer que le message a bien été envoyé.
  • Vous pouvez envoyer plusieurs commandes au serveur IRC, puis recevoir plusieurs réponses concernant chaque commande. L'ordre des réponses que vous recevez est généralement indéfini.
  • Beaucoup d'événements IRC qui vous sont envoyés sont générés par d'autres utilisateurs, ou par le serveur IRC lui-même, et vous sont envoyés dès qu'ils sont générés.
  • Les longues listes (par exemple, les listes de canaux) sont également envoyées sous forme d'événements. De plus, ces événements peuvent être séparés par d'autres événements (messages ou notices). Et il est de votre responsabilité de séparer les données (en utilisant des codes d'événement) et d'utiliser une sorte de structure de données qui les contiendra jusqu'à ce que les données soient complètes. Il n'est pas possible de simplement demander la liste des canaux et de s'attendre à ce que son contenu arrive immédiatement.
  • Vous pouvez envoyer la requête et ne pas recevoir de réponse en cas de succès (comme lorsque vous envoyez un message). Vous pouvez envoyer la requête et elle ne réussira que lorsque vous recevrez une réponse (qui peut arriver après que vous ayez reçu dix autres événements sans rapport). Ou vous pouvez recevoir une réponse sans même envoyer de requête, comme c'est le cas avec JOIN - il est possible que le serveur vous rejoigne implicitement à un canal spécifique.
  • Vous devez vous préparer à vous attendre à l'inattendu de la part du serveur IRC. Par exemple, le serveur peut changer votre pseudo (vu sur la plupart des serveurs qui utilisent l'authentification nickserv. Vous pouvez être "forcé" de rejoindre un canal, de dire quelque chose, de quitter un canal, de changer votre mode utilisateur, etc. Écoutez ce que le serveur IRC vous dit et faites-le.

Pourquoi la fonction irc_cmd_join ne renvoie-t-elle pas d'erreur ?

Un exemple typique est que l'appel irc_cmd_join() retourne toujours succès même lorsque vous tentez de rejoindre un canal protégé par mot de passe. Ensuite, quelque temps plus tard, le serveur IRC renvoie une erreur. C'est parce que les fonctions de la famille irc_cmd retournent succès lorsque la commande est envoyée au serveur IRC. La nature asynchrone de l'IRC rend impossible l'obtention immédiate du résultat de la commande. Veuillez lire la question ci-dessus.

Comment s'enregistrer/s'authentifier auprès de NICKSERV ?

Il n'y a pas de méthode 'standard'. NICKSERV, CHANSERV et autres ne sont pas spécifiés par la RFC. Ce sont des extensions IRC qui se comportent exactement comme les autres utilisateurs IRC mais avec plus de pouvoir. Généralement, leurs messages sont envoyés via des événements Notice, vous pouvez donc utiliser l'algorithme suivant pour gérer l'enregistrement Nickserv :

static void event_notice (irc_session_t * session, const char * event,
                                                 const char * origin, const char ** params, unsigned int count)
{
        char buf[256];
        if ( !origin )
                return;
        if ( strcasecmp (origin, "nickserv") )
                return;
        if ( strstr (params[1], "This nick is not registered") == params[1] )
        {
                sprintf (buf, "REGISTER %s NOMAIL", gCfg.irc_nickserv_password);
                irc_cmd_msg(session, "nickserv", buf);
        }
        else if ( strstr (params[1], "This nickname is registered and protected") == params[1] )
        {
                sprintf (buf, "IDENTIFY %s", gCfg.irc_nickserv_password);
                irc_cmd_msg(session, "nickserv", buf);
        }
        else if ( strstr (params[1], "Password accepted - you are now recognized") == params[1] )
                printf ("Nickserv authentication succeed.");
}

L'idée est d'analyser les messages envoyés par NICKSERV, et s'ils correspondent à des modèles spécifiques, d'y réagir de manière appropriée.

Qu'est-ce que CTCP ?

L'abréviation CTCP signifie "Client-to-Client Protocol" (Protocole Client à Client). Il est utilisé entre les clients IRC pour interroger le client distant pour certaines données, ou pour envoyer des informations - par exemple, les messages /me sont envoyés via CTCP.

Il n'y a pas de liste standard de requêtes CTCP possibles, et différents clients IRC ajoutent souvent leurs propres codes CTCP. Le gestionnaire intégré réagit aux requêtes CTCP TIME, VERSION, PING et FINGER. Si vous avez besoin de réagir à d'autres requêtes, vous devrez écrire votre propre gestionnaire CTCP. Consultez le code source de la fonction libirc_event_ctcp_internal pour avoir une idée de la façon de l'écrire.

Quand on me donne le statut de chanop (+o), pourquoi ne reçois-je pas l'événement umode ?

Devenir opérateur de canal modifie le **mode de canal**, et non le mode utilisateur. Par conséquent, vous recevrez l'**événement_mode** et non **event_umode**.

Si vous recevez l'event_umode avec +o, cela signifie que votre utilisateur est un opérateur du serveur IRC.

Et si mon application utilise epoll ?

La bibliothèque ne prend en charge directement que les boucles basées sur select() pour des raisons historiques, donc epoll et d'autres méthodes de polling ne sont pas directement prises en charge par la bibliothèque. Cependant, si nécessaire, cela pourrait être émulé en convertissant les descripteurs entre select et epoll comme suit :

  • Appelez irc_add_select_descriptors avec un FD_SET vide
  • Extrayez les descripteurs des tableaux fd_set (n'oubliez pas que fd_array est un bitarray, pas un tableau de valeurs). Il peut y avoir plus d'un descripteur dans le cas de sessions DCC.
  • Passez ces descripteurs à poll/epoll en utilisant les événements pertinents (c'est-à-dire utilisez EPOLLIN pour les descripteurs dans in_set)
  • Pour les descripteurs qui ont déclenché les événements, remplissez les structures in_set et out_set pertinentes (encore une fois, rappelez-vous des masques de bits !) et passez-les à irc_process_select_descriptors()

Bien que cela soit fastidieux, les opérations sont très simples (essentiellement des opérations de masques de bits sur une petite structure) et n'ajouteront pas de ralentissement significatif à votre application.
