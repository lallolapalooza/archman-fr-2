STACK_OF(3) Manuel des fonctions de bibliothèque STACK_OF(3)

NOM

STACK_OF — tableaux de taille variable de pointeurs, appelés piles OpenSSL

SYNTAXE

bibliothèque «libcrypto»
#include <openssl/safestack.h>

STACK_OF(type);

DESCRIPTION

L'en-tête <openssl/safestack.h> fournit un système fragile et inhabituellement compliqué de wrappers générés par des macros autour des fonctions décrites dans la page de manuel OPENSSL_sk_new(3). Il est destiné à implémenter des tableaux de pointeurs de taille variable superficiellement sûrs en type, appelés de manière trompeuse «piles» par OpenSSL. En raison du nombre excessif de fonctions d'API, il est impossible de documenter correctement ce système. En particulier, l'appel de man(1) pour l'une des fonctions opérant sur des piles ne peut donner aucun résultat.

Malheureusement, les programmes d'application ne peuvent guère éviter d'utiliser ce concept car plusieurs API OpenSSL importantes s'appuient sur celui-ci ; voir la section VOIR AUSSI pour des exemples. Même si les deux pages sont plus compliquées que toute page de manuel ne devrait l'être, utiliser le concept en toute sécurité nécessite une compréhension complète de tous les détails de cette page de manuel et de OPENSSL_sk_new(3).

La macro STACK_OF() prend un nom de type comme argument, généralement le nom d'un type qui a été défini comme alias pour un type spécifique de struct en utilisant une déclaration typedef. Elle s'étend à un type de struct incomplet destiné à représenter une «pile» d'objets du type donné. Ce type n'existe pas réellement, il n'est donc pas possible de définir, par exemple, une variable automatique ‘STACK_OF(X509) my_certificates’ ; il n'est possible que de définir des pointeurs vers des piles, par exemple ‘STACK_OF(X509) *my_certificates’. La seule façon dont de tels pointeurs peuvent être utilisés est par des fonctions wrapper les convertissant en type _STACK * décrit dans OPENSSL_sk_new(3).

Pour un nombre considérable de types, OpenSSL fournit une fonction wrapper pour chaque fonction décrite dans OPENSSL_sk_new(3). Les noms de ces fonctions wrapper sont généralement construits en insérant le nom du type et un trait de soulignement après le préfixe «sk_» du nom de la fonction. Habituellement, lorsque les fonctions réelles prennent des arguments void *, les wrappers prennent des pointeurs vers le type en question, et lorsque les fonctions réelles prennent des arguments _STACK *, les wrappers prennent des pointeurs vers STACK_OF(type). Il en va de même pour les valeurs de retour. Diverses exceptions à tout cela existent, mais ce qui précède s'applique à tous les types listés ci-dessous.

L'utilisation de ce qui précède peut avoir un sens pour les types suivants car des fonctions d'API publiques existent qui prennent des piles de ces types comme arguments ou les renvoient : ASN1_INTEGER, ASN1_OBJECT, ASN1_UTF8STRING, CMS_RecipientInfo, CMS_SignerInfo, CONF_VALUE, GENERAL_NAMES, GENERAL_SUBTREE, OPENSSL_STRING (qui est juste char *), PKCS12_SAFEBAG, PKCS7, PKCS7_RECIP_INFO, PKCS7_SIGNER_INFO, POLICYQUALINFO, SRTP_PROTECTION_PROFILE, SSL_CIPHER, SSL_COMP, X509, X509_ALGOR, X509_ATTRIBUTE, X509_CRL, X509_EXTENSION, X509_INFO, X509_NAME, X509_OBJECT, X509_POLICY_NODE, X509_REVOKED.

De plus, certaines fonctions d'API publiques utilisent les types suivants qui sont déclarés avec typedef :

STACK_OF(ACCESS_DESCRIPTION) AUTHORITY_INFO_ACCESS
STACK_OF(ASN1_OBJECT) EXTENDED_KEY_USAGE
STACK_OF(ASN1_TYPE) ASN1_SEQUENCE_ANY
STACK_OF(DIST_POINT) CRL_DIST_POINTS
STACK_OF(GENERAL_NAME) GENERAL_NAMES
STACK_OF(IPAddressFamily) IPAddrBlocks
STACK_OF(POLICY_MAPPING) POLICY_MAPPINGS
STACK_OF(POLICYINFO) CERTIFICATEPOLICIES
STACK_OF(X509_ALGOR) X509_ALGORS
STACK_OF(X509_EXTENSION) X509_EXTENSIONS

Bien que les en-têtes OpenSSL déclarent des fonctions wrapper pour de nombreux autres types et même si la documentation OpenSSL indique que les utilisateurs peuvent déclarer leurs propres types de piles, l'utilisation de STACK_OF() avec tout type non listé ici est fortement déconseillée. Pour d'autres types, il peut y avoir des différences subtiles et non documentées en syntaxe et en sémantique, et tenter de déclarer des types de piles personnalisés est très sujet aux erreurs ; utiliser de simples tableaux C de pointeurs vers le type souhaité est beaucoup plus simple et moins dangereux.

EXEMPLES

Le programme suivant crée un objet certificat, y place deux pointeurs sur une pile, et utilise X509_free(3) pour nettoyer correctement :

#include <err.h>
#include <stdio.h>
#include <openssl/x509.h>

int
main(void)
{
	STACK_OF(X509)	*stack;
	X509		*x;

	if ((stack = sk_X509_new_null()) == NULL)
		err(1, NULL);
	if ((x = X509_new()) == NULL)
		err(1, NULL);
	if (sk_X509_push(stack, x) == 0)
		err(1, NULL);
	if (X509_up_ref(x) == 0)
		errx(1, "X509_up_ref failed");
	if (sk_X509_push(stack, x) == 0)
		err(1, NULL);
	printf("%d pointeurs : %p, %p\n", sk_X509_num(stack),
	    sk_X509_value(stack, 0), sk_X509_value(stack, 1));
	sk_X509_pop_free(stack, X509_free);

	return 0;
}

La sortie ressemble à ceci :

2 pointeurs : 0x4693ff24c00, 0x4693ff24c00
