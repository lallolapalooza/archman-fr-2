PEM_READ(3) Manuel des fonctions de bibliothèque PEM_READ(3)

NOM

PEM_write, PEM_write_bio, PEM_read, PEM_read_bio, PEM_get_EVP_CIPHER_INFO, PEM_do_header, PEM_def_callback, pem_password_cb — Routines d'encodage PEM

SYNTAXE

bibliothèque “libcrypto”
#include <openssl/pem.h>

int
PEM_write(FILE *fp, const char *name, const char *header, const unsigned char *data, long len);

int
PEM_write_bio(BIO *bp, const char *name, const char *header, const unsigned char *data, long len);

int
PEM_read(FILE *fp, char **name, char **header, unsigned char **data, long *len);

int
PEM_read_bio(BIO *bp, char **name, char **header, unsigned char **data, long *len);

int
PEM_get_EVP_CIPHER_INFO(char *header, EVP_CIPHER_INFO *cinfo);

int
PEM_do_header(EVP_CIPHER_INFO *cinfo, unsigned char *data, long *len, pem_password_cb *cb, void *userdata);

int
PEM_def_callback(char *password, int size, int verify, void *userdata);

typedef int
pem_password_cb(char *password, int size, int verify, void *userdata);

DESCRIPTION

Ces fonctions lisent et écrivent des objets encodés en PEM, en utilisant le type PEM name, toute information supplémentaire d'header, et les data bruts de longueur len.

PEM est l'encodage binaire du contenu défini pour la première fois dans la RFC 1421 de l'IETF. Le contenu est une série de lignes encodées en base64, entourées de marqueurs de début/fin chacun sur sa propre ligne. Par exemple :

-----BEGIN PRIVATE KEY-----
MIICdg....
... bhTQ==
-----END PRIVATE KEY-----

Des lignes d'en-tête optionnelles peuvent apparaître après la ligne de début, et leur existence dépend du type d'objet écrit ou lu.

PEM_write() écrit dans le fichier fp, tandis que PEM_write_bio() écrit dans le BIO bp. Le name est le nom à utiliser dans le marqueur, l'header est la valeur de l'en-tête ou NULL, et data et len spécifient les données et leur longueur.

Le tampon de data final est typiquement un objet ASN.1 qui peut être décodé avec la fonction d2i_*() appropriée au type name ; voir d2i_X509(3) pour des exemples.

PEM_read() lit depuis le fichier fp, tandis que PEM_read_bio() lit depuis le BIO bp. Les deux ignorent toutes les données non-PEM qui précèdent le début de l'objet PEM suivant. Lorsqu'un objet est récupéré avec succès, le nom du type de la ligne "----BEGIN <type>-----" est renvoyé via l'argument name, les en-têtes d'encapsulation sont renvoyés dans header, et le contenu décodé en base64 et sa longueur sont renvoyés via data et len, respectivement. Les pointeurs name, header, et data doivent être libérés par l'appelant lorsqu'ils ne sont plus nécessaires.

Les fonctions restantes sont dépréciées car le format de chiffrement PEM sous-jacent est obsolète et doit être évité. Il utilise un format de chiffrement avec une fonction de dérivation de clé spécifique à OpenSSL, qui utilise MD5 avec un nombre d'itérations de 1. Au lieu de cela, les clés privées doivent être stockées sous forme PKCS#8, avec un PBE PKCS#5 v2.0 fort ; voir PEM_write_PrivateKey(3) et d2i_PKCS8PrivateKey_bio(3).

PEM_get_EVP_CIPHER_INFO() peut être utilisée pour déterminer si les data renvoyés par PEM_read() ou PEM_read_bio() sont chiffrés et pour récupérer le chiffre et l'IV associés. L'appelant passe un pointeur vers une structure de type EVP_CIPHER_INFO via l'argument cinfo et l'header renvoyé via PEM_read() ou PEM_read_bio(). Si l'appel réussit, 1 est renvoyé et le chiffre et l'IV sont stockés à l'adresse pointée par cinfo. Lorsque l'en-tête est malformé ou non pris en charge, ou lorsque le chiffre est inconnu ou qu'une erreur interne se produit, 0 est renvoyé.

PEM_do_header() peut ensuite être utilisé pour déchiffrer les données si l'en-tête indique un chiffrement. L'argument cinfo est un pointeur vers la structure initialisée par un appel précédent à PEM_get_EVP_CIPHER_INFO(). Si cette structure indique l'absence de chiffrement, PEM_do_header() se termine avec succès sans aucune action. Les arguments data et len sont utilisés à la fois pour passer les données chiffrées qui ont été renvoyées dans les mêmes arguments lors de l'appel précédent à PEM_read() ou PEM_read_bio() et pour passer les données déchiffrées.

La fonction de rappel cb est utilisée pour obtenir le password de chiffrement ; si cb est NULL, PEM_def_callback() est utilisée à la place. Le tampon password doit avoir au moins size octets. Sauf si userdata est NULL, PEM_def_callback() ignore l'argument verify et copie la chaîne d'octets terminée par NUL userdata dans password sans octet NUL de terminaison, tronquant silencieusement la copie à au plus size octets. Si userdata est NULL, PEM_def_callback() demande alors à l'utilisateur le mot de passe en désactivant l'écho en appelant EVP_read_pw_string_min(3) en interne. Dans ce cas, size est silencieusement réduit à au plus BUFSIZ et au plus size - 1 octets sont acceptés de l'utilisateur et copiés dans le tampon de chaîne d'octets password. Une fonction de rappel cb fournie par l'application peut utiliser userdata pour un but différent de celui de PEM_def_callback(), par ex., comme données auxiliaires à utiliser lors de l'obtention du mot de passe. Par exemple, une application graphique pourrait passer un handle de fenêtre. Si le drapeau verify est non nul, l'utilisateur est invité deux fois à entrer le mot de passe pour éviter les fautes de frappe

VALEURS DE RETOUR

PEM_read() et PEM_read_bio() retournent 1 en cas de succès ou 0 en cas d'échec. Ce dernier cas inclut le cas où aucun objet PEM supplémentaire ne reste dans le fichier d'entrée. Pour distinguer la fin du fichier des erreurs plus graves, l'appelant doit examiner la pile d'erreurs et vérifier PEM_R_NO_START_LINE, ce qui indique qu'aucun autre objet PEM n'a été trouvé. Voir ERR_peek_last_error(3) et ERR_GET_REASON(3).

PEM_get_EVP_CIPHER_INFO() et PEM_do_header() retournent 1 en cas de succès ou 0 en cas d'échec. Les données (data) sont probablement sans signification si ces fonctions échouent.

PEM_def_callback() retourne le nombre d'octets stockés dans buf ou une valeur négative en cas d'échec, et cb est censé se comporter de la même manière. Si userdata est NULL, PEM_def_callback() échoue si num est inférieur à 5 ou si une erreur survient lors de la tentative de demander le mot de passe à l'utilisateur. Sinon, il échoue lorsque num est négatif. Les détails des circonstances qui font échouer cb peuvent différer.

HISTORIQUE

PEM_write(), PEM_read(), et PEM_do_header() sont apparus dans SSLeay 0.4 ou antérieur. PEM_get_EVP_CIPHER_INFO() est apparu pour la première fois dans SSLeay 0.5.1. PEM_write_bio() et PEM_read_bio() sont apparus pour la première fois dans SSLeay 0.6.0. Ces fonctions sont disponibles depuis OpenBSD 2.4.

PEM_def_callback() est apparu pour la première fois dans OpenSSL 0.9.7 et est disponible depuis OpenBSD 3.2.
