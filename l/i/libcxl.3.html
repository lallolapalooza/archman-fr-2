LIBCXL(3) Manuel libcxl LIBCXL(3)

NOM

libcxl - Une bibliothèque pour interagir avec les périphériques CXL via les interfaces sysfs(5) et ioctl(2)

SYNTAXE

#include <cxl/libcxl.h>
cc ... -lcxl

DESCRIPTION

libcxl fournit des interfaces pour interagir avec les périphériques CXL sous Linux, en utilisant les interfaces sysfs pour la plupart des interactions avec le noyau, et l'interface ioctl() pour la soumission de commandes.

Le point de départ pour toutes les interfaces de la bibliothèque est un objet cxl_ctx, retourné par linklibcxl:cxl_new[3]. Les périphériques mémoire CXL de Type 3 et les autres objets de périphériques CXL sont descendants de l'objet cxl_ctx, et peuvent être itérés via une API d'itérateur d'objets de la forme cxl_<objet>_foreach(<objet parent>, <itérateur d'objet>).

MEMDEVS

L'objet représentant un extenseur de mémoire CXL (périphérique de Type 3) est struct cxl_memdev. Les interfaces de la bibliothèque relatives à ces périphériques ont le préfixe cxl_memdev_. Ces interfaces sont principalement associées aux interactions sysfs (sauf indication contraire dans leurs sections de documentation respectives). Elles sont typiquement utilisées pour récupérer des données publiées par le noyau, ou pour envoyer des données ou déclencher des opérations du noyau pour un périphérique donné.

Les instances de memdev CXL sont énumérées à partir du contexte global de la bibliothèque struct cxl_ctx. Par défaut, un memdev n'offre qu'un portail pour soumettre des commandes de périphérique mémoire, voir les API de port, décodeur et point d'accès pour déterminer quelles ressources mémoire CXL sont accessibles étant donné un memdev spécifique.

L'hôte d'un memdev est le périphérique point d'accès PCIe qui a enregistré ses capacités CXL auprès du noyau CXL Linux.

Un memdev reçoit un nom de périphérique noyau de la forme "mem%d" où un id (cxl_memdev_get_id()) est alloué dynamiquement lors de la découverte des périphériques. Notez qu'il n'y a aucune garantie que les ids / noms de périphériques noyau pour les memdevs soient stables d'un démarrage à l'autre, les périphériques sont énumérés de manière asynchrone. Si un identifiant stable est nécessaire, utilisez cxl_memdev_get_serial() qui retourne une valeur selon la capacité étendue Numéro de série du périphérique dans la spécification de base PCIe 5.0.

Le nœud de périphérique caractère pour la soumission de commande peut être trouvé par défaut à /dev/cxl/mem%d, ou créé avec un majeur / mineur retourné par cxl_memdev_get_{major,minor}().

Les attributs pmem_size et ram_size retournent l'approvisionnement actuel de DPA (Adresse Physique du Périphérique / capacité locale) dans le périphérique.

cxl_memdev_get_numa_node() retourne le numéro du nœud CPU affinitaire si disponible ou -1 sinon.

cxl_memdev_wait_sanitize() : si une opération de sanitisation est en cours lors de cet appel, le programme se bloquera jusqu'à ce que l'opération de sanitisation soit terminée ou que l'attente expire.

MEMDEV: Contrôle

int cxl_memdev_disable_invalidate(struct cxl_memdev *memdev);
int cxl_memdev_enable(struct cxl_memdev *memdev);

Lorsqu'un périphérique mémoire est désactivé, il désenregistre ses points d'accès associés et potentiellement les ports de commutateur intervenant s'il n'y a pas d'autres memdevs maintenant ce port actif. Cela signifie que tous les objets de port existants que la bibliothèque a précédemment retournés sont invalides et doivent être relus. Les appelants doivent faire attention à récupérer de nouveaux objets de port après un appel à cxl_memdev_disable_invalidate(). Toute utilisation d'un objet de port précédemment obtenu après un appel à cxl_memdev_disable_invalidate() est une erreur de programmation d'utilisation après libération. Il s'ensuit qu'après cxl_memdev_enable(), de nouveaux ports peuvent apparaître dans la topologie qui n'étaient pas précédemment énumérables.


Note

cxl_memdev_disable_invalidate() désactivera de force le memdev
indépendamment du fait que la mémoire fournie par le périphérique soit en cours d'utilisation active par le système d'exploitation. Les appelants assument la responsabilité de s'assurer qu'il est sûr de désactiver le périphérique mémoire. Sinon, cet appel peut être aussi destructeur que de retirer un DIMM d'un système en fonctionnement. Comme tous les autres appels libcxl qui modifient l'état du système ou divulguent des informations sensibles pour la sécurité, cet appel nécessite les privilèges root / CAP_SYS_ADMIN.

Un cxl_cmd est un objet à référence comptée utilisé pour effectuer des commandes Mailbox telles que décrites dans la spécification CXL. Un objet cxl_cmd est lié à un cxl_memdev. Les interfaces de bibliothèque associées ont le préfixe cxl_cmd_. Au sein de cette sous-classe d'interfaces, il y a :

•Les interfaces cxl_cmd_new_*() qui allouent un nouvel objet cxl_cmd pour un type de commande donné ciblant un memdev donné. Dans le cadre du processus d'instanciation de la commande, la bibliothèque valide que la commande est prise en charge par le périphérique mémoire, sinon elle retourne NULL pour indiquer aucune prise en charge. L'ID de commande libcxl est traduit par le noyau en un opcode standard CXL. Voir les ID de commande potentiels dans /usr/include/linux/cxl_mem.h.
•Les interfaces cxl_cmd_<nom>_set_<champ> qui définissent des champs spécifiques dans un cxl_cmd.
•cxl_cmd_submit qui soumet la commande via ioctl().
•Les interfaces cxl_cmd_<nom>_get_<champ> qui récupèrent des champs spécifiques de la réponse de la commande.
•Les interfaces cxl_cmd_get_* pour obtenir des informations générales relatives à la commande.

cxl_cmd_new_raw() prend en charge les commandes dites RAW où l'ID de commande est RAW et il transporte une charge utile de commande de périphérique mémoire CXL non modifiée associée à l'argument opcode. Étant donné que le noyau effectue une validation minimale des entrées sur ces commandes, les commandes brutes ne sont généralement pas prises en charge par le noyau en dehors des scénarios de build de débogage. libcxl est limitée à la prise en charge des commandes qui apparaissent dans la spécification standard publique CXL.

cxl_memdev{read,write,zero}_label() sont des utilitaires pour marshaliser plusieurs commandes d'accès aux étiquettes sur une étendue arbitraire de l'étiquette du périphérique

bel area.

cxl_cmd_partition_set_mode() prend en charge la sélection du mode NEXTBOOT ou IMMEDIATE. Lorsque le mode CXL_SETPART_IMMEDIATE est défini, il est de la responsabilité de l'appelant d'éviter les changements immédiats de partitionnement lorsque l'appareil est en cours d'utilisation. Lorsque le mode CXL_SETPART_NEXTBOOT est défini, la modification du partitionnement deviendra la configuration « suivante », pour devenir active lors du prochain redémarrage de l'appareil.

BUS

L'espace mémoire CXL est cohérent pour le CPU et les périphériques. Les plages d'adresses qui prennent en charge l'accès cohérent sont décrites par le firmware de la plateforme et communiquées au système d'exploitation via un objet racine CXL, struct cxl_bus.

Le nom du fournisseur d'un bus est un nom persistant, indépendant de l'ordre de découverte. Les noms de fournisseur possibles sont ACPI.CXL et cxl_test. Les attributs devname et id, comme les autres objets, sont simplement les noms des périphériques du noyau susceptibles de changer en fonction de l'ordre de découverte.

BUS : Contrôle

int cxl_bus_disable_invalidate(struct cxl_bus *bus);

Une topologie CXL entière peut être démantelée avec cette API. Comme les autres API _invalidate, les appelants doivent supposer que tous les objets de la bibliothèque ont été libérés. Celle-ci va plus loin et libère également l'argument @bus. Cela peut planter le système et n'est utile que dans les scénarios de développement de pilotes de noyau.

PORTS

Les ports CXL suivent la hiérarchie PCIe entre un objet racine CXL du firmware de la plateforme, en passant par les ponts hôtes CXL / PCIe, les ports racine CXL / PCIe, et les ports commutateur CXL / PCIe.

Un objet bus encapsule un objet port CXL. Utilisez cxl_bus_get_port() pour utiliser les API de port génériques sur les objets racine.

Les ports sont hiérarchiques. Tous les ports sauf l'objet racine ont un autre port CXL comme objet parent récupérable via cxl_port_get_parent().

Le port racine d'une hiérarchie peut être récupéré via n'importe quelle instance de port dans cette hiérarchie via cxl_port_get_bus().

L'hôte d'un port est le nom de périphérique correspondant du port racine PCIe, ou du port amont du commutateur avec des capacités CXL.

L'assistant cxl_port_foreach_all() effectue une itération en profondeur de tous les ports sous l'argument de port top.

Le type de port est communiqué via cxl_port_is_<type>(). Un port activé est un port qui a réussi à découvrir les registres de composants CXL dans le périphérique hôte et a énuméré ses ports en aval. Pour qu'un memdev soit activé pour l'opération mémoire CXL, tous les ports CXL de son ascendance doivent également être activés, y compris un port racine, un nombre arbitraire de ports commutateur intermédiaires, et un port terminal point d'extrémité.

cxl_port_hosts_memdev() renvoie vrai si l'hôte du port apparaît dans l'ascendance de la topologie de périphérique de l'hôte du memdev.

DÉCODEURS

Les objets décodeurs sont associés à la « Capacité de décodeur HDM » publiée dans les périphériques de port et les points d'extrémité PCIe compatibles CXL. Le noyau modélise également les plages de mémoire CXL décrites par le firmware de la plateforme (comme le CEDT.CFMWS de l'ACPI) en tant qu'objets décodeurs statiques. Ils acheminent les adresses physiques système (SPA) via une topologie de port vers un décodeur de point d'extrémité qui effectue la traduction finale de SPA en DPA (adresse physique système en adresse physique locale au périphérique).

Le noyau protège l'énumération de la disposition d'adresses physiques du système. Sans CAP_SYS_ADMIN, cxl_decoder_get_resource() renvoie ULLONG_MAX pour indiquer que les informations d'adresse n'ont pas pu être récupérées. Sinon, cxl_decoder_get_resource() renvoie la valeur actuellement programmée de la base de la plage de décodage du décodeur. Un décodeur de taille nulle indique un décodeur désactivé.

Les décodeurs de niveau racine ne prennent en charge qu'un ensemble limité de types de mémoire dans leur plage d'adresses. Les fonctions d'aide cxl_decoder_is_<memtype>_capable() identifient ce qui est pris en charge. Les décodeurs de niveau commutateur, en revanche, sont capables de router tout type de mémoire, c'est-à-dire qu'ils transmettent simplement la prise en charge du type de mémoire de leur port parent. Les décodeurs d'extrémité suivent les capacités de leur périphérique mémoire hôte.

Les capacités d'un décodeur ne doivent pas être confondues avec leur type / mode. Le type dépend finalement de l'extrémité. Par exemple, un accélérateur nécessite que tous les décodeurs de son ascendance soient réglés sur CXL_DECODER_TTYPE_ACCELERATOR, et inversement, les périphériques d'extension de mémoire simples nécessitent CXL_DECODER_TTYPE_EXPANDER.

Le firmware de la plateforme peut configurer la hiérarchie de décodage CXL avant le démarrage du système d'exploitation, et peut supplémentairement exiger que le système d'exploitation ne modifie pas les paramètres de décodage. Cette propriété est indiquée par l'API cxl_decoder_is_locked().

Lorsqu'un décodeur est associé à une région, cxl_decoder_get_region() renvoie cet objet de région. Notez qu'il n'est applicable qu'aux décodeurs de commutateur et d'extrémité, car les décodeurs racines ont une relation 1:N avec les régions. Utilisez cxl_region_foreach() pour une fonctionnalité similaire pour les décodeurs racines.

CIBLES

Un décodeur de niveau racine ou de commutateur prend une SPA (adresse physique système) en entrée et la route vers un port en aval. Le port en aval dépend de la position du port en aval dans l'entrelacement. Un objet struct cxl_target représente les propriétés d'un port en aval donné par rapport à sa configuration d'entrelacement.

La position d'un décodeur ainsi que la granularité de l'entrelacement déterminent quelle adresse dans la plage de ressources du décodeur est mappée à quel port.

L'identifiant de cible est un identifiant que le port CXL utilise pour faire référence à ce port en aval. Pour les ports de commutateur en aval CXL / PCIe, l'identifiant est défini par le champ Numéro de Port de Capacité de Lien PCIe. Pour les décodeurs racines, l'identifiant est spécifié par un mécanisme spécifique au firmware de la plateforme. Pour les ports racines définis par ACPI.CXL, l'identifiant provient du _UID de CEDT.CHBS / ACPI0016.

Le nom du périphérique d'une cible est le nom du périphérique hôte pour le port en aval. Pour les ports CXL / PCIe en aval, le nom du périphérique est le périphérique de commutateur en aval PCI. Pour les ports racines CXL, le nom du périphérique est un objet firmware de plateforme pour le pont hôte, comme une instance de périphérique ACPI0016.

La fonction d'aide cxl_target_maps_memdev() est le compagnon de cxl_decoder_get_target_by_memdev() pour déterminer quels ports en aval / cibles sont capables de mapper quels memdevs.

Certaines implémentations de firmware de plateforme définissent un alias / périphérique compagnon pour représenter la racine d'une hiérarchie de périphériques PCI. La fonction d'aide cxl_target_get_physical_node() renvoie le nom du périphérique de cet objet compagnon dans la hiérarchie PCI.

RÉGIONS

Une région CXL est composée d'une ou plusieurs tranches de memdevs CXL, avec des paramètres d'entrelacement configurables - à la fois le nombre de voies d'entrelacement et la granularité de l'entrelacement. En termes de hiérarchie, elle est enfant d'un décodeur racine CXL. Un décodeur racine (rappelons que cela correspond à une fenêtre CEDT.CFMWS d'ACPI), peut avoir plusieurs régions enfants, mais une région est strictement liée à un seul décodeur racine.

Les tranches qui composent une région sont appelées des mappages. Un mappage est un tuple de memdev, décodeur d'extrémité, et la position.

RÉGION: Énumération

struct cxl_region *cxl_region_get_first(struct cxl_decoder *decoder);
struct cxl_region *cxl_region_get_next(struct cxl_region *region);
#define cxl_region_foreach(decoder, region)                                    \
        for (region = cxl_region_get_first(decoder); region != NULL;           \
             region = cxl_region_get_next(region))
#define cxl_region_foreach_safe(decoder, region, _region)                      \
        for (region = cxl_region_get_first(decoder),                           \
             _region = region ? cxl_region_get_next(region) : NULL;            \
             region != NULL;                                                   \
             region = _region,                                                 \
             _region = _region ? cxl_region_get_next(_region) : NULL)

L'attribut de ressource d'une région est l'adresse physique hôte (Host Physical Address) à laquelle commence l'espace d'adressage de la région. L'espace d'adressage de la région est un sous-ensemble de l'espace d'adressage du décodeur racine parent.

Les voies d'entrelacement correspondent au nombre de memdevs composants participant à la région.

La granularité de l'entrelacement dépend de la granularité du décodeur racine, et doit suivre les règles mathématiques d'entrelacement définies dans la spécification CXL.

Les régions ont une liste de cibles 0..N, qui sont programmées avec le nom d'un décodeur d'extrémité sous chaque memdev participant.

Les attributs decode_commit et decode_reset réservent et libèrent de l'espace DPA sur un memdev donné en allouant un décodeur d'extrémité et en le programmant en fonction de la géométrie d'entrelacement de la région.

Une fois qu'une région est active, elle est attachée soit au sous-système NVDIMM où ses propriétés peuvent être interrogées par ndctl, soit au sous-système DAX où ses propriétés peuvent être interrogées par daxctl. La fonction d'aide cxl_region_get_daxctl_region() renvoie une struct daxctl_region * qui peut être utilisée avec d'autres API libdaxctl.
