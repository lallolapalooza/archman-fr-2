PROLOGUE

Cette page de manuel fait partie du Manuel du programmeur POSIX. L'implémentation Linux de cette interface peut différer (consulter la page de manuel Linux correspondante pour les détails du comportement sous Linux), ou l'interface peut ne pas être implémentée sous Linux.

NOM

limits.h — constantes dépendantes de l'implémentation

SYNOPIS

#include <limits.h>

DESCRIPTION

Une partie de la fonctionnalité décrite sur cette page de référence étend la norme ISO C. Les applications doivent définir la macro de test de fonctionnalité appropriée (voir le volume Interfaces système de POSIX.1‐2017, Section 2.2, L'environnement de compilation) pour activer la visibilité de ces symboles dans cet en-tête.

Beaucoup des symboles listés ici ne sont pas définis par la norme ISO/IEC 9899:1999. De tels symboles ne sont pas indiqués par un ombrage CX, sauf sous la rubrique « Limites numériques ».

L'en-tête <limits.h> doit définir des macros et des constantes symboliques pour diverses limites. Différentes catégories de limites sont décrites ci-dessous, représentant diverses limites sur les ressources que l'implémentation impose aux applications. Toutes les macros et constantes symboliques définies dans cet en-tête doivent être adaptées à une utilisation dans des directives de préprocesseur #if.

Les implémentations peuvent choisir n'importe quelle valeur appropriée pour chaque limite, à condition qu'elle ne soit pas plus restrictive que les Valeurs minimales acceptables listées ci-dessous. Les noms de constantes symboliques commençant par _POSIX peuvent être trouvés dans <unistd.h>.

Les applications ne doivent pas supposer de valeur particulière pour une limite. Pour obtenir une portabilité maximale, une application ne doit pas nécessiter plus de ressources que la quantité de Valeur minimale acceptable. Cependant, une application souhaitant bénéficier de la totalité des ressources disponibles sur une implémentation peut utiliser la valeur donnée dans <limits.h> sur cette implémentation particulière, en utilisant les macros et les constantes symboliques listées ci-dessous. Il convient de noter, cependant, que beaucoup des limites listées ne sont pas invariantes, et à l'exécution, la valeur de la limite peut différer de celles données dans cet en-tête, pour les raisons suivantes :

*
La limite dépend du chemin.
*
La limite diffère entre les machines de compilation et d'exécution.

Pour ces raisons, une application peut utiliser les fonctions fpathconf(), pathconf() et sysconf() pour déterminer la valeur réelle d'une limite à l'exécution.

Les éléments de la liste se terminant par _MIN donnent les valeurs les plus négatives que les types mathématiques sont garantis de pouvoir représenter. Des nombres de valeur plus négative peuvent être pris en charge sur certaines implémentations, comme indiqué par l'en-tête <limits.h> sur l'implémentation, mais les applications nécessitant de tels nombres ne sont pas garanties d'être portables sur toutes les implémentations. Pour les constantes positives se terminant par _MIN, cela indique la valeur minimale acceptable.

Valeurs invariantes à l'exécution (potentiellement indéterminées)

La définition de l'une des constantes symboliques de la liste suivante sera omise de <limits.h> sur des implémentations spécifiques où la valeur correspondante est égale ou supérieure à la valeur minimale spécifiée, mais est non spécifiée.

Cette indétermination pourrait dépendre de la quantité d'espace mémoire disponible sur une instance spécifique d'une implémentation spécifique. La valeur réelle prise en charge par une instance spécifique sera fournie par la fonction sysconf().

LIMITS.H

The <limits.h> header defines the symbolic constants listed below. The values for these constants are either the minimum values that an implementation must support, or the maximum values that an implementation guarantees to support.

The definitions of these symbolic constants are conditionally compiled if certain feature test macros are defined. In addition, the values of constants that are not fixed by the POSIX standard are described as having a minimum acceptable value. If a feature test macro is defined that indicates that a particular feature is supported, the value of the corresponding symbolic constant shall be at least the minimum acceptable value.

The values of some constants may vary between implementations or even between different invocations of the same implementation. The sysconf() function can be used to query the values of these implementation-dependent constants at runtime. Constants whose names end with _MAX or _MIN are typically limits. Constants whose names end with _N, _Ratios, or _XOPEN are typically tunable parameters, or other implementation-defined limits that may vary by implementation.

NAME

limits.h — implementation-defined constants

SYNOPSIS

#include <limits.h>

DESCRIPTION

The header file <limits.h> defines symbolic constants for various implementation-defined limits and configuration options. The following constants are defined:

{_POSIX2_LINE_MAX}

Maximum number of bytes in a line.
Minimum Acceptable Value: 2048
{_POSIX2_RE_DUP_MAX}

Maximum number of repeated occurrences of a Basic Regular Expression subexpression that is allowed by the implementation.
Minimum Acceptable Value: 255
{_POSIX_CHILD_MAX}

Maximum number of processes that may be created per real user ID.
Minimum Acceptable Value: 6
{_POSIX_LINK_MAX}

Maximum number of links that may be created to a file.
Minimum Acceptable Value: 8
{_POSIX_MAX_CANON}

Maximum number of bytes in a canonical input line.
Minimum Acceptable Value: 255
{_POSIX_MAX_INPUT}

Maximum number of bytes that can be typed as input when the underlying terminal driver is in canonical mode.
Minimum Acceptable Value: 255
{_POSIX_NAME_MAX}

Maximum number of bytes in a filename, exclusive of the file suffix.
Minimum Acceptable Value: 14
{_POSIX_NGROUPS_MAX}

Maximum number of real or effective group IDs that a process may possess.
Minimum Acceptable Value: 0 (if the system does not support group sets) or 16.
{_POSIX_OPEN_MAX}

Maximum number of files that a process may have open simultaneously.
Minimum Acceptable Value: 16
{_POSIX_PATH_MAX}

Maximum number of bytes in a pathname, including the length of the filename.
Minimum Acceptable Value: 255
{_POSIX_PIPE_BUF}

Maximum number of bytes that can be written atomically to a pipe.
Minimum Acceptable Value: 512
{_POSIX_SSIZE_MAX}

Maximum value that an object of type ssize_t can hold. This is the size of the largest read (or other stream input function) that can be attempted.
Minimum Acceptable Value: 32767
{_POSIX_SYMLINK_MAX}

Maximum number of bytes a symbolic link may contain.
Minimum Acceptable Value: 1024
{_POSIX_TZNAME_MAX}

Maximum number of characters (excluding the null byte) in any timezone name.
Minimum Acceptable Value: 3
{LOGIN_NAME_MAX}

Maximum length of a login name.
Minimum Acceptable Value: 9
{NL_ARGMAX}

Maximum number of arguments in a format string.
Minimum Acceptable Value: 32767
{NL_SETMAX}

Maximum set number.
Minimum Acceptable Value: 255
{NL_TEXTMAX}

Maximum number of bytes in a message string.
Minimum Acceptable Value: {_POSIX2_LINE_MAX}

Default process priority.
Minimum Acceptable Value: 20

The following sections are informative.

APPLICATION USAGE

None.

RATIONALE

A request was made to reduce the value of {_POSIX_LINK_MAX} from the value of 8 specified for it in the POSIX.1‐1990 standard to 2. The standard developers decided to deny this request for several reasons:

*
They wanted to avoid making any changes to the standard that could break conforming applications, and the requested change could have that effect.
*
The use of multiple hard links to a file cannot always be replaced with use of symbolic links. Symbolic links are semantically different from hard links in that they associate a pathname with another pathname rather than a pathname with a file. This has implications for access control, file permanence, and transparency.
*
The original standard developers had considered the issue of allowing for implementations that did not in general support hard links, and decided that this would reduce consensus on the standard.

Systems that support historical versions of the development option of the ISO POSIX‐2 standard retain the name {_POSIX2_RE_DUP_MAX} as an alias for {_POSIX_RE_DUP_MAX}.

{PATH_MAX}

IEEE PASC Interpretation 1003.1 #15 addressed the inconsistency in the standard with the definition of pathname and the description of {PATH_MAX}, allowing application developers to allocate either {PATH_MAX} or {PATH_MAX}+1 bytes. The inconsistency has been removed by correction to the {PATH_MAX} definition to include the null character. With this change, applications that previously allocated {PATH_MAX} bytes will continue to succeed.
{SYMLINK_MAX}

This symbol refers to space for data that is stored in the file system, as opposed to {PATH_MAX} which is the length of a name that can be passed to a function. In some existing implementations, the pathnames pointed to by symbolic links are stored in the inodes of the links, so it is important that {SYMLINK_MAX} not be constrained to be as large as {PATH_MAX}.
