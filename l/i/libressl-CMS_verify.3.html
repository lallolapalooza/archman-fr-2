libressl-CMS_verify(3)

Paquet: libressl

Licences: ISC, custom:OpenSSL

CMS_VERIFY(3) Manuel des fonctions de bibliothèque CMS_VERIFY(3)

NOM

CMS_verify, CMS_get0_signers — vérifier une structure CMS SignedData

SYNOPHIS

bibliothèque « libcrypto »
#include <openssl/cms.h>

int
CMS_verify(CMS_ContentInfo *cms, STACK_OF(X509) *certs, X509_STORE *store, BIO *indata, BIO *out, unsigned int flags);

STACK_OF(X509) *
CMS_get0_signers(CMS_ContentInfo *cms);

DESCRIPTION

CMS_verify() vérifie la structure CMS SignedData cms. certs est un ensemble de certificats dans lequel rechercher les (les) certificat(s) de signature. store est un magasin de certificats de confiance utilisé pour la vérification de la chaîne. indata est le contenu détaché si le contenu n'est pas présent dans cms. Le contenu est écrit dans out s'il n'est pas NULL.

CMS_get0_signers() récupère le(s) certificat(s) de signature de cms. Il ne peut être appelé qu'après une opération réussie de CMS_verify(). Les signataires doivent être libérés avec sk_X509_free().

Normalement, le processus de vérification se déroule comme suit.

Initialement, quelques vérifications de cohérence sont effectuées sur cms. Il doit y avoir au moins une signature sur les données. Si le contenu est détaché, indata ne peut pas être NULL.

Une tentative est faite pour localiser tous les certificat(s) de signature, en recherchant d'abord dans le paramètre certs (s'il n'est pas NULL) puis en recherchant dans tous les certificats contenus dans la structure cms elle-même. Si un certificat de signature ne peut être localisé, l'opération échoue.

Chaque certificat de signature est vérifié par chaîne en utilisant le but smimesign et le magasin de certificats de confiance fourni store. Tous les certificats internes du message sont utilisés comme CA non fiables. Si la vérification CRL est activée dans store, toutes les CRL internes sont utilisées en plus de la tentative de les rechercher dans store. Si une vérification de chaîne échoue, un code d'erreur est retourné.

Enfin, le contenu signé est lu (et écrit dans out s'il n'est pas NULL) et la signature est vérifiée.

Si toutes les signatures sont vérifiées correctement, la fonction est réussie.

L'un des flags suivants (combinés par OU bit à bit) peut être passé pour modifier le comportement de vérification par défaut :

CMS_NOINTERN
N'utilise pas les certificats du message lui-même lors de la localisation du(des) certificat(s) de signature. Cela signifie que tous les certificats de signature doivent se trouver dans le paramètre certs.
CMS_NOCRL
Si la vérification CRL est activée dans store, alors toutes les CRL présentes dans le message lui-même sont ignorées.
CMS_TEXT
Les en-têtes MIME de type text/plain sont supprimés du contenu. Si le contenu n'est pas de type text/plain, une erreur est retournée.
CMS_NO_SIGNER_CERT_VERIFY
Ne pas vérifier les certificats de signature.
CMS_NO_ATTR_VERIFY
Ne pas vérifier la signature des attributs signés.
CMS_NO_CONTENT_VERIFY
Ne pas vérifier le hachage du contenu.

Une application de CMS_NOINTERN est d'accepter uniquement les messages signés par un petit nombre de certificats. Les certificats acceptables seraient passés dans le paramètre certs. Dans ce cas, si le signataire n'est pas l'un des certificats fournis dans certs, la vérification échouera car le signataire ne peut être trouvé.

Dans certains cas, les techniques standard pour rechercher et valider les certificats ne sont pas appropriées : par exemple, une application peut souhaiter rechercher des certificats dans une base de données ou effectuer une vérification personnalisée. Ceci peut être réalisé en définissant et en vérifiant manuellement les certificats des données signées à l'aide des fonctions utilitaires de données signées.

Il faut prendre soin lors de la modification du comportement de vérification par défaut, par exemple, en réglant CMS_NO_CONTENT_VERIFY désactivera complètement toute vérification du contenu et tout contenu modifié sera considéré comme valide. Cependant, cette combinaison est utile si l'on souhaite simplement écrire le contenu dans out et que sa validité n'est pas considérée comme importante.

La vérification de chaîne devrait idéalement être effectuée en utilisant l'heure de signature plutôt que l'heure actuelle. Cependant, comme l'heure de signature est fournie par le signataire, elle ne peut pas être fiable sans preuve supplémentaire (comme un horodatage fiable).

VALEUR DE RETOUR

CMS_verify() retourne 1 pour une vérification réussie ou 0 si une erreur s'est produite.

CMS_get0_signers() retourne tous les signataires ou NULL si une erreur s'est produite. Les signataires doivent être libérés avec sk_X509_free().

L'erreur peut être obtenue à partir de ERR_get_error(3).

VOIR AUSSI

CMS_ContentInfo_new(3), CMS_get0_SignerInfos(3), CMS_sign(3), CMS_verify_receipt(3)

NORMES

RFC 5652 : Cryptographic Message Syntax (CMS), section 5.1 : Type SignedData

RFC 8419 : Utilisation des signatures Edwards-Curve Digital Signature Algorithm (EdDSA) dans la syntaxe des messages cryptographiques (CMS)

HISTORIQUE

Ces fonctions sont apparues pour la première fois dans OpenSSL 0.9.8h et sont disponibles depuis OpenBSD 6.7.

BOGUES

Le magasin de certificats de confiance n'est pas recherché pour le certificat de signature. Ceci est principalement dû aux lacunes de la fonctionnalité actuelle de X509_STORE.

L'absence de traitement en passe unique signifie que le contenu signé doit être entièrement conservé en mémoire s'il n'est pas détaché.
