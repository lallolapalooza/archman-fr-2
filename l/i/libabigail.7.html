NOM

libabigail - Bibliothèque d'analyse et de comparaison des ABI ELF

APERÇU DU CADRE ABIGAIL

ABIGAIL signifie Application Binary Interface Generic Analysis and Instrumentation Library.

Le type d'incompatibilités d'interface sur lequel se concentre Abigail est lié aux changements apportés aux symboles de fonctions et de variables exportés par ELF, ainsi qu'aux changements de disposition et de taille des types de données des fonctions et variables exportées par les bibliothèques partagées.

Autrement dit, si le type de retour d'une fonction exportée par une bibliothèque partagée change d'une manière incompatible d'une version à l'autre d'une bibliothèque partagée donnée, nous voulons que Abigail aide les gens à le détecter.

En dehors de cette représentation interne, libabigail fournit des outils pour effectuer des comparaisons approfondies de deux ABI. C'est-à-dire qu'elle peut comparer les types de deux ensembles de fonctions ou de variables et représenter le résultat d'une manière qui permet d'émettre des rapports textuels sur les différences.

Cela nous permet d'écrire des outils comme abidiff qui peuvent comparer l'ABI de deux bibliothèques partagées et représenter le résultat d'une manière suffisamment significative pour nous aider à repérer les incompatibilités d'ABI. Il existe plusieurs autres outils construits à l'aide du cadre Abigail.

CONCEPTS

Artefacts d'ABI

L'ensemble des artefacts d'ABI pour un binaire est appelé un Corpus d'ABI.

Les types scalaires ont un nom, une taille et d'autres propriétés scalaires.

Un type agrégé est généralement constitué de sous-types.

Par exemple, les types de classe ou d'union sont une sorte de type agrégé. Ils ont un nom, une taille et des membres. Chaque membre peut être soit

  • un membre de données avec un type représentant un sous-type du type agrégé, un décalage et un nom
  • soit une fonction avec un type représentant un autre sous-type du type agrégé et un nom. Certaines fonctions membres (virtuelles) peuvent également avoir un décalage.

Un autre exemple de type agrégé est un type de fonction, qui est l'union du type de retour et des types de paramètres de la fonction.

Changements d'ABI

Libabigail représente et analyse les changements de types, de fonctions, de variables et de symboles ELF.

Ces différents types de changements d'artefacts d'ABI sont classés en fonction de l'impact qu'ils ont sur la compatibilité de l'ABI.

Les changements d'artefacts d'ABI sont signalés par des outils comme abidiff et abipkgdiff dans des rapports de différences textuels organisés autour des différents types de changements listés ci-dessous.

Veuillez noter que les utilisateurs peuvent demander aux outils d'éviter d'émettre des rapports sur certains changements. Ceci est fait via des spécifications de suppression.

Changements inoffensifs

Un changement dans le rapport de différences est considéré comme inoffensif s'il ne cause pas de problème de compatibilité d'ABI. C'est-à-dire qu'il n'empêche pas une application liée dynamiquement à une version donnée d'une bibliothèque de continuer à fonctionner avec les versions ultérieures modifiées de la même bibliothèque.

Par défaut, abidiff et abipkgdiff filtrent les changements inoffensifs du rapport de différences.

Changements nuisibles

Un changement d'ABI est considéré comme nuisible s'il peut causer des problèmes de compatibilité d'ABI. C'est-à-dire qu'il peut empêcher une application liée dynamiquement à une version donnée d'une bibliothèque de continuer à fonctionner avec les versions ultérieures modifiées de la même bibliothèque.

Autrement dit, un changement nuisible est un changement qui n'est pas inoffensif.

Un changement nuisible doit absolument être revu par un être humain pour savoir s'il cause réellement un problème de compatibilité d'ABI.

Par défaut, abidiff affiche les changements nuisibles pour les fonctions et les variables globales.

Si l'outil émet au moins un changement nuisible, alors le bit ABIDIFF_ABI_CHANGE du champ de bits retourné dans le code de sortie est mis à 1.

Changements incompatibles

Un changement incompatible est un changement nuisible qui cause des problèmes de compatibilité d'ABI. Dans le langage courant des programmeurs, un tel changement est dit casser l'ABI.

Si l'outil abidiff ou abipkgdiff émet au moins un changement incompatible, alors les bits ABIDIFF_ABI_INCOMPATIBLE_CHANGE et ABIDIFF_ABI_CHANGE du champ de bits retourné dans le code de sortie sont mis à 1.

Les changements reconnus comme étant incompatibles avec l'ABI sont les suivants :

  • Changement de SONAME de la bibliothèque partagée
  • Changement de l'architecture d'un binaire
  • Suppression de symboles ELF de fonctions ou de variables globales exportés (pas nécessairement décrits par les informations de débogage)
  • Suppression de fonctions ou de variables globales exportées qui sont décrites par les informations de débogage.
  • Tout changement incompatible dans la disposition du type qui est utilisé comme type d'une variable globale ou comme type de retour ou de paramètre d'une fonction. Ce changement de disposition de type incompatible peut être :
  • une modification de la taille du type
  • ou la suppression d'un membre de données
  • ou une modification du décalage d'un membre de données
  • ou un changement incompatible d'un sous-type du type

Veuillez noter que si un type n'est utilisé ni comme type d'une variable globale, ni comme type de retour ou de paramètre d'une fonction, alors abidiff (ou abipkgdiff) ne considérera pas un changement incompatible de ce type comme un changement d'ABI incompatible. Ce changement sera simplement considéré comme nuisible. Le bit ABIDIFF_ABI_CHANGE du champ de bits retourné dans le code de sortie est mis à 1, ce qui signifie que le changement nécessite une révision humaine. C'est une limitation actuelle du cadre d'analyse libabigail qui pourrait être abordée dans de futurs affinements.

Spécifications de suppression

Définition

Un fichier de spécifications de suppression est un moyen pour un utilisateur d'indiquer à abidiff, abipkgdiff ou tout autre outil libabigail pertinent d'éviter d'émettre des rapports pour les changements impliquant certains artefacts d'ABI.

l'ensemble des artefacts ABI sur lesquels éviter d'émettre des rapports de changement.

Exemples introductifs

Sa syntaxe est basée sur une forme simplifiée et personnalisée de la Syntaxe de Fichier Ini. Par exemple, pour spécifier que les rapports de changement sur un type nommé FooPrivateType doivent être supprimés, on pourrait écrire cette spécification de suppression :

[suppress_type]
  name = FooPrivateType

Si nous voulons nous assurer que seuls les rapports de changement concernant les structures nommées FooPrivateType soient supprimés, nous pourrions écrire :

[suppress_type]
  type_kind = struct
  name = FooPrivateType

Mais nous pourrions aussi vouloir supprimer les rapports de changement concernant les typedefs nommés FooPrivateType. Dans ce cas, nous écririons :

[suppress_type]
  type_kind = typedef
  name = FooPrivateType

Ou, nous pourrions vouloir supprimer les rapports de changement concernant toutes les structures dont les noms se terminent par la chaîne "PrivateType" :

[suppress_type]
  type_kind = struct
  name_regexp = ^.*PrivateType

Examinons maintenant la syntaxe générique des fichiers de spécification de suppression.

Syntaxe

Propriétés

Plus généralement, le format des listes de suppression est organisé autour du concept de propriété. Chaque propriété a un nom et une valeur, délimités par le signe =. Par exemple :

name = value

Les espaces blancs au début et à la fin sont ignorés autour des noms de propriétés et des valeurs.

Expressions régulières

La valeur de certaines propriétés peut être une expression régulière. Dans ce cas, elles doivent être conformes à la syntaxe des expressions régulières étendues POSIX. Notez que Libabigail utilise le moteur d'expressions régulières de la Bibliothèque C GNU.

Échapper un caractère dans une expression régulière

Lorsqu'on essaie de faire correspondre une chaîne qui contient un caractère *, comme dans le type pointeur int*, il faut faire attention car le caractère * est un caractère spécial dans la syntaxe des expressions régulières étendues POSIX. Ce caractère doit donc être échappé pour le moteur d'expressions régulières. Ainsi, l'expression régulière qui correspondrait à la chaîne int* dans un fichier de suppression devrait être :

int\\*

Attendez ; mais pourquoi alors les deux caractères \ ? Eh bien, parce que le caractère \ est un caractère spécial dans la Syntaxe de Fichier Ini utilisée pour spécifier les suppressions. Il doit donc également être échappé, afin que le parseur de Fichier Ini laisse un caractère \ intact dans le flux de données qui est transmis au moteur d'expressions régulières. D'où le \\ destiné au parseur de Fichier Ini.

Donc, en bref, pour échapper un caractère dans une expression régulière, préfixez toujours le caractère avec la séquence \\.

Mode opératoire

Les spécifications de suppression peuvent être appliquées à deux points différents du pipeline de traitement de libabigail.

Dans le mode de fonctionnement par défaut appelé "mode de suppression tardive", les spécifications de suppression sont appliquées au résultat de la comparaison des représentations internes en mémoire de deux ABI. Dans ce mode, si un artefact ABI correspond à une spécification de suppression, ses changements ne sont pas mentionnés dans le rapport de changement ABI. La représentation interne de l'artefact ABI modifié "supprimé" est toujours présente en mémoire ; elle n'est simplement pas mentionnée dans le rapport de changement ABI. Le rapport de changement peut toujours mentionner des statistiques sur le nombre d'artefacts de changement ABI qui ont été supprimés.

C'est le mode d'interprétation par défaut des spécifications de suppression pour la plupart des outils, y compris abidiff et abidw.

Il existe un autre mode de fonctionnement appelé "mode de suppression précoce" où les spécifications de suppression sont appliquées lors de la construction de la représentation interne en mémoire d'un ABI donné. Dans ce mode, si un artefact ABI correspond à une spécification de suppression, aucune représentation interne en mémoire n'est construite pour lui. En conséquence, aucun changement concernant l'artefact ABI correspondant ne sera mentionné dans le rapport de changement ABI et aucune statistique sur le nombre de changements ABI supprimés ne sera disponible. De plus, veuillez noter que comme les artefacts ABI supprimés sont retirés de la représentation interne en mémoire dans ce mode, la quantité de mémoire utilisée par la représentation interne est potentiellement plus faible que la consommation de mémoire en mode de suppression tardive.

Veuillez noter que ce mode supprime des données de la représentation interne construite par libabigail et peut donc entraîner des conséquences inattendues et surprenantes. Par conséquent, ce mode doit être défini explicitement par les utilisateurs, soit en utilisant la propriété drop dans une spécification de suppression, soit en utilisant une option de ligne de commande d'outil spéciale comme abidw --force-early-suppression.

Sections

Les propriétés sont ensuite regroupées en sections nommées arbitrairement qui ne doivent pas être imbriquées. Le nom de la section est sur une ligne séparée et est entouré de crochets, c'est-à-dire :

[nom_section]
nom_propriété1 = valeur_propriété1
nom_propriété2 = valeur_propriété2

Une section peut avoir ou non des propriétés. Les sections qui sont censées avoir des propriétés et qui se trouvent néanmoins vides sont simplement ignorées. Les propriétés qui ne sont pas reconnues par le lecteur sont également ignorées.

Noms de sections

Chaque section différente peut être considérée comme une directive pour supprimer les rapports de changement ABI pour un type particulier d'artefact ABI.

[suppress_file]

Cette directive empêche un outil donné de charger un fichier (binaire ou fichier abixml) si son nom de fichier ou d'autres propriétés correspondent à certaines propriétés. Ainsi, si l'outil est censé comparer les ABI de deux fichiers, et si la directive l'empêche de charger l'un ou l'autre des fichiers, alors aucune comparaison n'est effectuée.

Notez que pour que la directive [suppress_file] fonctionne, au moins une des propriétés suivantes doit être fournie :

file_name_regexp, file_name_not_regexp, soname_regexp, soname_not_regexp.

Si aucune des propriétés ci-dessus n'est fournie, alors la directive [suppress_file] est simplement ignorée.

Les propriétés potentielles de cette section sont listées ci-dessous :

•
file_name_not_regexp

Utilisation :

file_name_not_regexp = <expression-régulière>

Empêche le système de charger le fichier dont le nom ne correspond pas à l'expression régulière spécifiée comme valeur de cette propriété.

•
file_name_regexp

Utilisation :

file_name_regexp = <expression-régulière>

Empêche le système de charger le fichier dont le nom correspond à l'expression régulière spécifiée comme valeur de cette propriété.

•
label
Utilisation :
label = <quelque-valeur>

Définit une étiquette pour la section. Une étiquette est simplement une chaîne informative qui peut être utilisée par l'outil pour faire référence à une suppression de type dans les messages d'erreur. Il peut également y avoir des noms d'étiquettes spéciaux qui font que le système de suppression se comporte d'une certaine manière.

•
soname_regexp

Utilisation :

soname_regexp = <expression-régulière>

Empêche le système de charger le fichier qui contient une propriété SONAME correspondant à l'expression régulière de cette propriété. Notez que cette propriété fonctionne également sur un fichier abixml s'il contient une propriété SONAME.

•
soname_not_regexp

Utilisation :

soname_not_regexp = <expression-régulière>

Empêche le système de charger le fichier qui contient une propriété SONAME qui ne correspond PAS à l'expression régulière de cette propriété. Notez que cette propriété fonctionne également sur un fichier abixml s'il contient une propriété SONAME.

[suppress_type]

Cette directive supprime les messages de rapport sur un changement de type.

Notez que pour que la directive [suppress_type] fonctionne, au moins une des propriétés suivantes doit être fournie :

file_name_regexp, file_name_not_regexp, soname_regexp, soname_not_regexp, name, name_regexp, name_not_regexp, source_location_not_in, source_location_not_regexp, type_kind.

Si aucune des propriétés ci-dessus n'est fournie, alors la directive [suppress_type] est simplement ignorée.

Les propriétés potentielles de cette section sont listées ci-dessous :


•
accessed_through
Utilisation :
accessed_through = <certaines-valeurs-prédéfinies>

Supprime les rapports de changement impliquant un type auquel il est fait référence directement ou par l'intermédiaire d'un pointeur ou d'une référence. Les valeurs potentielles de cette propriété sont les mots-clés prédéfinis ci-dessous :

•
direct

Donc, si [suppress_type] contient la propriété description :

accessed_through = direct

alors les changements concernant un type auquel il est fait référence directement (c'est-à-dire, pas par le biais d'un pointeur ou d'une référence) seront supprimés.

  • pointer

    Si la propriété accessed_through est définie sur la valeur pointer, alors les changements concernant un type auquel il est fait référence par le biais d'un pointeur seront supprimés.

  • reference

    Si la propriété accessed_through est définie sur la valeur reference, alors les changements concernant un type auquel il est fait référence par le biais d'une référence seront supprimés.

  • reference-or-pointer

    Si la propriété accessed_through est définie sur la valeur reference-or-pointer, alors les changements concernant un type auquel il est fait référence par le biais d'une référence ou d'un pointeur seront supprimés.

Pour un exemple complet de l'utilisation de cette propriété, veuillez consulter l'exemple ci-dessous sur la suppression des rapports de changement concernant les types accessibles directement ou par le biais de pointeurs.

•
changed_enumerators

Utilisation :

changed_enumerators = <liste-des-énumérateurs>

Supprime les rapports de changement impliquant des modifications de la valeur des énumérateurs d'un type enum donné. Cette propriété est appliquée si la propriété type_kind est définie sur la valeur enum, au minimum. La valeur de changed_enumerators est une liste d'énumérateurs séparés par des virgules que l'utilisateur s'attend à voir changer. Par exemple :

changed_enumerators = LAST_ENUMERATORS0, LAST_ENUMERATOR1
•
changed_enumerators_regexp

Utilisation :

changed_enumerators_regexp = <liste-des-expressions-régulières-d'énumérateurs>

Supprime les rapports de changement impliquant des modifications de la valeur des énumérateurs d'un type enum donné. Cette propriété est appliquée si la propriété type_kind est définie sur la valeur enum, au minimum. La valeur de la propriété changed_enumerators_regexp est une liste d'expressions régulières séparées par des virgules qui doivent correspondre aux noms des énumérateurs que l'utilisateur s'attend à voir changer. Par exemple :

changed_enumerators_regexp = .*_MAX$, .*_LAST$, .*_NUM$, .*_NBITS$

Dans l'exemple ci-dessus, les rapports de changement sur tout énumérateur dont le nom se termine par _MAX, _LAST, _NUM ou _NBITS seront supprimés.

Notez que pour que cette propriété soit appliquée aux changements d'un type enum, la taille du type enum ne doit PAS avoir changé.


•
drop
Utilisation :
drop = yes | no

Si un type correspond à une spécification de suppression qui contient la propriété "drop" définie sur "yes" (ou "true"), alors le type ne sera même pas représenté dans la représentation interne de l'ABI analysée. Cette propriété fait en sorte que sa spécification de suppression englobante soit appliquée en mode de spécification de suppression précoce. L'effet net est qu'elle réduit potentiellement la quantité de mémoire utilisée pour représenter l'ABI analysée.

Veuillez noter que pour les types struct, class ou enum correspondant à une spécification de suppression avec cette propriété dont la valeur est définie sur "yes" (ou "true"), si la spécification a également une propriété label avec une valeur définie sur libabigail::OPAQUE_TYPE_LABEL, alors le type est transformé en un type opaque, plutôt que d'être simplement ignoré. Cela réduit également la quantité de mémoire utilisée pour représenter l'ABI analysée, mais avec potentiellement moins de perturbations dans la représentation résultante de l'ABI.

Veuillez noter que pour que cette propriété soit efficace, la spécification de suppression englobante doit avoir au moins l'une des propriétés suivantes spécifiées : name_regexp, name, name_regexp, source_location_not_in ou source_location_not_regexp.

•
file_name_not_regexp

Utilisation :

file_name_not_regexp = <expression-régulière>

Supprime les rapports de changement concernant des artefacts ABI définis dans un fichier binaire dont le nom ne correspond pas à l'expression régulière spécifiée comme valeur de cette propriété.

•
file_name_regexp

Utilisation :

file_name_regexp = <expression-régulière>

Supprime les rapports de changement concernant des artefacts ABI définis dans un fichier binaire dont le nom correspond à l'expression régulière spécifiée comme valeur de cette propriété.


•
has_data_member

Utilisation :

has_data_member = <liste-des-noms-de-membres-de-données>

Supprime les rapports de changement impliquant un type qui contient des membres de données dont les noms sont fournis dans la liste de valeurs de cette propriété.

Un exemple d'utilisation de cette propriété serait :

has_data_member = {private_data_member0, private_data_member1}

La propriété ci-dessus correspondrait à tout type qui contient au moins deux membres de données dont les noms sont private_data_member0 et private_data_member1.

Un autre exemple d'utilisation de cette propriété serait :

has_data_member = another_private_data_member

La propriété ci-dessus correspondrait à tout type qui contient un membre de données dont le nom est another_private_data_member0.


•
has_data_member_regexp

Utilisation :

has_data_member_regexp = <une-expression-régulière>

Supprime les rapports de changement impliquant un type qui contient des membres de données dont les noms correspondent à l'expression régulière fournie comme valeur de cette propriété.

Un exemple d'utilisation de cette propriété serait :

has_data_member_regexp = ^private_data_member

La propriété ci-dessus correspondrait à tout type qui contient des membres de données dont les noms correspondent à l'expression régulière ^private_data_member. Autrement dit, elle correspondrait à tout type qui contient des membres de données dont les noms commencent par la chaîne "private_data_member".


•
has_data_member_inserted_at
Utilisation :
has_data_member_inserted_at = <offset-en-bits>

Supprime les rapports de changement impliquant un type qui possède au moins un membre de données inséré à un décalage spécifié par la valeur de propriété offset-en-bits. Veuillez noter que si la taille du type a changé, le changement de type ne sera PAS supprimé par l'évaluation de cette propriété, sauf si la propriété has_size_change est présente et définie sur yes.

La valeur offset-en-bits est soit :

•
une valeur entière, exprimée en bits, qui représente le décalage du point d'insertion du membre de données, à partir du début de la structure ou de la classe concernée.
•
des expressions de sélection de décalage de membre de données, telles que :
  • le mot-clé end qui est une constante nommée dont la valeur est égale au décalage de la fin de la structure ou de la classe.
  • le mot-clé offset_of_flexible_array_data_member qui est une constante nommée qui s'évalue au décalage du membre de données de tableau flexible contenu dans la structure concernée.
  • l'expression d'appel de fonction offset_of(nom-membre-données) où nom-membre-données est le nom d'un membre de données donné de la structure ou de la classe concernée. La valeur de cette expression d'appel de fonction est un entier qui représente le décalage du membre de données désigné par nom-membre-données.
  • l'expression d'appel de fonction offset_after(nom-membre-données) où nom-membre-données est le nom d'un membre de données donné de la structure ou de la classe concernée. La valeur de cette expression d'appel de fonction est un entier qui représente le décalage du point qui suit immédiatement la zone occupée par le membre de données désigné par nom-membre-données.
  • l'expression d'appel de fonction offset_of_first_data_member_regexp(nom-membre-données-regexp) où nom-membre-données-regexp est une expression régulière correspondant à un membre de données. La valeur de cette expression d'appel de fonction est un entier qui représente le décalage du premier membre de données dont le nom correspond à l'argument de l'expression régulière. Si aucun membre de données d'un type de classe donné ne correspond à l'expression régulière, alors le type de classe ne correspondra pas à la directive actuelle.
  • l'expression d'appel de fonction offset_of_last_data_member_regexp(nom-membre-données-regexp) où nom-membre-données-regexp est une expression régulière correspondant à un membre de données. La valeur de cette expression d'appel de fonction est un entier qui représente le décalage du dernier membre de données dont le nom correspond à l'argument de l'expression régulière. Si aucun membre de données d'un type de classe donné ne correspond à l'expression régulière, alors le type de classe ne correspondra pas à la directive actuelle.
•
has_data_member_inserted_between
Utilisation :
has_data_member_inserted_between = {<range-begin>, <range-end>}

Supprime les rapports de modification impliquant un type qui possède au moins un membre de données inséré à un décalage compris dans la plage entre range-begin et range-end. Veuillez noter que chacune des valeurs range-begin et range-end peut être de la même forme que la propriété has_data_member_inserted_at ci-dessus. Veuillez également noter que si la taille du type a changé, alors la modification du type ne sera PAS supprimée par l'évaluation de cette propriété, à moins que la propriété has_size_change ne soit présente et définie sur yes. Notez que les suppressions de membres de données se produisant dans la plage entre range-begin et range-end n'empêcheront pas la modification du type d'être supprimée par l'évaluation de cette propriété si la taille du type ne change pas ou si la propriété has_size_change est présente et définie sur yes.

Exemples d'utilisation de ces propriétés sont :

has_data_member_inserted_between = {8, 64}

ou :

has_data_member_inserted_between = {16, end}

ou :

has_data_member_inserted_between = {offset_after(member1), end}
•
has_data_members_inserted_between
Utilisation :
has_data_members_inserted_between = {<sequence-of-ranges>}

Supprime les rapports de modification impliquant un type qui possède plusieurs membres de données insérés dans diverses plages de décalages. Un exemple d'utilisation de cette propriété est, par exemple :

has_data_members_inserted_between = {{8, 31}, {72, 95}}

Cet exemple d'utilisation supprime les rapports de modification impliquant un type qui a des membres de données insérés dans les plages de décalages binaires [8 31] et [72 95]. La longueur de la séquence de plages ou de cette has_data_members_inserted_between n'est pas limitée ; elle peut être aussi longue que le système peut en gérer. Les valeurs des limites des plages sont du même type que pour la propriété has_data_member_inserted_at ci-dessus. Veuillez également noter que si la taille du type a changé, alors le type ne sera PAS supprimé par l'évaluation de cette propriété, à moins que la propriété has_size_change ne soit présente et définie sur yes. Exemples de code

1.
Suppression des rapports de changement sur les types.

Supposons qu'une bibliothèque nommée libtest1-v0.so contienne ce code très utile :

$ cat -n test1-v0.cc
     1  // Déclaration anticipée d'un type considéré comme opaque pour
     2  // la fonction foo() ci-dessous.
     3  struct opaque_type;
     4
     5  // Cette fonction ne peut pas accéder aux membres de opaque_type.  Par conséquent,
     6  // les changements apportés aux membres de opaque_type ne devraient pas impacter foo, en ce qui concerne
     7  // l'ABI.
     8  void
     9  foo(opaque_type*)
    10  {
    11  }
    12
    13  struct opaque_type
    14  {
    15    int member0;
    16    char member1;
    17  };
$

Changeons la disposition de la structure opaque_type en insérant un membre de données autour de la ligne 15, ce qui conduit à une nouvelle version de la bibliothèque, que nous nommerons libtest1-v1.so :

$ cat -n test1-v1.cc
     1  // Déclaration anticipée d'un type considéré comme opaque pour
     2  // la fonction foo() ci-dessous.
     3  struct opaque_type;
     4
     5  // Cette fonction ne peut pas accéder aux membres de opaque_type ; Par conséquent,
     6  // les changements apportés aux membres de opaque_type ne devraient pas impacter foo, en ce qui concerne
     7  // l'ABI.
     8  void
     9  foo(opaque_type*)
    10  {
    11  }
    12
    13  struct opaque_type
    14  {
    15    char added_member; // <-- un nouveau membre a été ajouté ici maintenant.
    16    int member0;
    17    char member1;
    18  };
$

Compilons les deux exemples. Nous n'oublierons pas de les compiler avec la génération d'informations de débogage activée :

$ g++ -shared -g -Wall -o libtest1-v0.so test1-v0.cc
$ g++ -shared -g -Wall -o libtest1-v1.so test1-v1.cc

Demandons à abidiff quelles différences d'ABI il voit entre libtest1-v0.so et libtest1-v1.so :

$ abidiff libtest1-v0.so libtest1-v1.so
Résumé des changements de fonctions : 0 Supprimées, 1 Modifiée, 0 fonctions ajoutées
Résumé des changements de variables : 0 Supprimées, 0 Modifiées, 0 variables ajoutées
riable 1 fonction avec quelques changements de sous-type indirects : [C]'fonction void foo(opaque_type*)' a quelques changements de sous-type indirects : le paramètre 0 de type 'opaque_type*' a des changements de sous-type : dans le type pointé 'struct opaque_type' : la taille a changé de 64 à 96 bits 1 insertion de membre de données : 'char opaque_type::added_member', à l'offset 0 (en bits) 2 changements de membre de données : 'int opaque_type::member0' l'offset a changé de 0 à 32 'char opaque_type::member1' l'offset a changé de 32 à 64

Ainsi, abidiff rapporte que la disposition de l'opaque_type a changé de manière significative, en ce qui concerne les implications de l'ABI, en théorie. Après tout, un sous-type (struct opaque_type) d'une fonction exportée (foo()) a vu sa disposition changer. Cela pourrait avoir des implications non négligeables sur l'ABI. Mais en pratique ici, le programmeur de la bibliothèque litest1-v0.so sait que le contrat "souple" entre la fonction foo() et le type struct opaque_type est de rester à l'écart des membres de données du type. Les changements de disposition de struct opaque_type ne devraient donc pas impacter foo().

Maintenant, pour apprendre à abidiff ce contrat souple et lui faire éviter d'émettre ce qui revient à de faux positifs dans ce cas, nous écrivons le fichier de spécification de suppression ci-dessous :

$ cat test1.suppr
[suppress_type]
  type_kind = struct
  name = opaque_type

Traduit en langage clair, cette spécification de suppression se lirait : « Ne pas émettre de rapports de changement concernant une structure dont le nom est opaque_type ».

Invoquons maintenant abidiff sur les deux versions de la bibliothèque, mais cette fois avec la spécification de suppression :

$ abidiff --suppressions test1.suppr libtest1-v0.so libtest1-v1.so
Résumé des changements de fonctions : 0 Supprimées, 0 Modifiées (1 filtrée), 0 Fonctions ajoutées
Résumé des changements de variables : 0 Supprimées, 0 Modifiées, 0 Variables ajoutées

Comme vous pouvez le voir, abidiff ne signale plus le changement ; il nous indique qu'il a été filtré à la place.

Supposons que la première version d'une bibliothèque nommée libtest3-v0.so ait le code source suivant :

     gcc -g -Wall -shared -o libtest3-v0.so test3-v0.c

struct S
{
  char member0;
  int member1; /*
                  entre member1 et member2, il y a un certain bourrage,
                  au moins sur certaines plateformes populaires. Sur
                  ces plateformes, l'ajout d'un membre de données assez petit
                  dans cet espace de bourrage ne devrait pas changer
                  l'offset de member1. N'est-ce pas ?
                */
};
int
foo(struct S* s)
{
  return s->member0 + s->member1;
}

Maintenant, supposons que la deuxième version de la bibliothèque nommée libtest3-v1.so ait le code source suivant dans lequel un membre de données a été ajouté dans l'espace de bourrage de struct S et un autre membre de données a été ajouté à sa fin :

/* Compilez ceci avec :
     gcc -g -Wall -shared -o libtest3-v1.so test3-v1.c
 */
struct S
{
  char member0;
  char inserted1; /* <---- Un membre de données a été ajouté ici...  */
  int member1;
  char inserted2; /* <---- ... et un autre a été ajouté ici.  */
};
int
foo(struct S* s)
{
  return s->member0 + s->member1;
}

Mais alors, exécuter abidiff sur ces deux versions de la bibliothèque donne :

$ abidiff libtest3-v0.so libtest3-v1.so

Résumé des changements de variables : 0 Supprimées, 0 Modifiées, 0 Variables ajoutées
1 fonction avec quelques changements de sous-type indirects :

    le paramètre 0 de type 'S*' a des changements de sous-type :

Les lecteurs attentifs remarqueront que le changement apporté à struct widget impacte également la fonction exportée fun1(), qui utilise le type struct widget par le biais d'une référence. Mais abidiff ne nous informe pas de l'impact sur cette fonction fun1() car il a évalué ce changement comme étant redondant avec le changement signalé sur fun0(). La détection et le filtrage de redondance sont bien et utiles pour éviter d'enterrer les informations importantes dans une mer de bruit. Cependant, ils doivent être traités avec soin, par crainte de filtrer par erreur des informations pertinentes et importantes.

Vue d'ensemble

Le dépôt de code source de Libabigail contient plusieurs outils écrits à l'aide de la bibliothèque. Ils sont maintenus et publiés en tant que partie du projet. Tous les outils sont livrés avec un script de complétion bash.

Manuels des outils

abidiff

Cet outil peut également comparer les représentations textuelles de l'ABI de deux binaires ELF (tel que généré par abidw) ou un binaire ELF par rapport à une représentation textuelle d'un autre binaire ELF.

Cet outil utilise la bibliothèque libabigail pour analyser le binaire ainsi que ses informations de débogage associées. Voici son mode de fonctionnement général.

Libabigail a alors la capacité de générer des représentations textuelles des Corpus d'ABI, de les comparer, d'analyser leurs changements et de les rapporter.

Invocation

abidiff [options] <premiere-bibliotheque-partagee> <seconde-bibliotheque-partagee>

Environnement

abidiff charge deux fichiers de spécifications de suppression par défaut, fusionne leur contenu et l'utilise pour filtrer les rapports de changement d'ABI qui pourraient être considérés comme de faux positifs par les utilisateurs.

  • Fichier de spécification système par défaut

    Il est localisé par la variable d'environnement facultative LIBABIGAIL_DEFAULT_SYSTEM_SUPPRESSION_FILE. Si cette variable d'environnement n'est pas définie, alors abidiff essaie de charger le fichier de spécification $libdir/libabigail/libabigail-default.abignore. Si ce fichier n'est pas présent, alors aucun fichier de spécification système par défaut n'est chargé.

  • Fichier de spécification utilisateur par défaut.

    Il est localisé par la variable d'environnement facultative LIBABIGAIL_DEFAULT_USER_SUPPRESSION_FILE. Si cette variable d'environnement n'est pas définie, alors abidiff essaie de charger le fichier de spécification $HOME/.abignore. Si ce fichier n'est pas présent, alors aucune spécification de suppression utilisateur par défaut n'est chargée.

    Ce groupe de corpus d'ABI est ensuite comparé au second groupe de corpus donné en argument à abidiff.

    Valeurs de retour

    Le code de sortie de la commande abidiff est soit 0 si l'ABI des binaires comparés est égale, soit non nul s'ils diffèrent ou si l'outil a rencontré une erreur.

    Dans ce dernier cas, le code de sortie est un champ de bits sur 8 bits dans lequel chaque bit a une signification spécifique.

    Le premier bit, de valeur 1, nommé ABIDIFF_ERROR signifie qu'il y a eu une erreur.

    Le deuxième bit, de valeur 2, nommé ABIDIFF_USAGE_ERROR signifie qu'il y a eu une erreur dans la façon dont l'utilisateur a invoqué l'outil. Il peut être défini, par exemple, si l'utilisateur a invoqué l'outil avec un commutateur de ligne de commande inconnu, avec un nombre ou un argument incorrect, etc. Si ce bit est défini, alors le bit ABIDIFF_ERROR doit également être défini.

    Le troisième bit, de valeur 4, nommé ABIDIFF_ABI_CHANGE signifie que l'ABI des binaires comparés est différent.

    Le quatrième bit, de valeur 8, nommé ABIDIFF_ABI_INCOMPATIBLE_CHANGE signifie que l'ABI des binaires comparés est différent d'une manière incompatible. Si ce bit est défini, alors le bit ABIDIFF_ABI_CHANGE doit également être défini. Si ABIDIFF_ABI_CHANGE est défini et ABIDIFF_INCOMPATIBLE_CHANGE n'est PAS défini, alors cela signifie que les ABI comparés peuvent être compatibles ou non. Dans ce cas, un être humain doit examiner les changements d'ABI pour décider s'ils sont compatibles ou non.

    Notez qu'à l'heure actuelle, il n'existe que quelques types de changements d'ABI qui entraîneraient la définition du drapeau ABIDIFF_ABI_INCOMPATIBLE_CHANGE. Ces changements d'ABI sont soit :

    • la suppression du symbole d'une fonction ou d'une variable qui a été définie et exportée.
    • la modification de l'index d'un membre d'une table de fonctions virtuelles (pour les programmes et bibliothèques C++).

    Avec le temps, lorsque davantage de modèles de changement d'ABI s'avéreront constituer toujours des changements d'ABI incompatibles, nous adapterons le code pour reconnaître ces cas et définir en conséquence ABIDIFF_ABI_INCOMPATIBLE_CHANGE. Donc, si vous trouvez de tels modèles, s'il vous plaît, faites-le nous savoir.

    Les bits restants ne sont pas utilisés pour le moment.

    abipkgdiff

    L'ABI des binaires contenus dans le second ensemble de paquets est comparée à l'ABI des binaires contenus dans le premier ensemble de paquets.

    Cet outil utilise la bibliothèque libabigail pour analyser le binaire ainsi que ses informations de débogage associées. Voici son mode de fonctionnement général.

    Libabigail a ensuite la capacité de générer des représentations textuelles des Corpus d'ABI, de les comparer, d'analyser leurs changements et de les rapporter.

    Invocation

    abipkgdiff [options] <package1> <package2>

    package1 et package2 sont les paquets qui contiennent les binaires à comparer.

    Un style d'invocation alternatif serait :

    abipkgdiff [options] --set1 <pkg1-v1> <pkg2-v1> <pkg3-v1> \
                     --set2 <pkg1-v2> <pkg2-v2> <pkg3-v2>

    où l'ABI des binaires contenus dans le second ensemble de paquets est comparée aux binaires contenus dans le premier ensemble de paquets.

    Environnement

    abipkgdiff charge deux fichiers de spécifications de suppression par défaut, fusionne leur contenu et l'utilise pour filtrer les rapports de changements d'ABI qui pourraient être considérés comme de faux positifs par les utilisateurs.

    • Fichier système de spécifications de suppression par défaut

      Il est situé par la variable d'environnement optionnelle LIBABIGAIL_DEFAULT_SYSTEM_SUPPRESSION_FILE. Si cette variable d'environnement n'est pas définie, alors abipkgdiff essaie de charger le fichier de spécifications $libdir/libabigail/libabigail-default.abignore. Si ce fichier n'est pas présent, alors aucun fichier système de spécifications de suppression par défaut n'est chargé.

    • Fichier utilisateur de spécifications de suppression par défaut.

      Il est situé par la variable d'environnement optionnelle LIBABIGAIL_DEFAULT_USER_SUPPRESSION_FILE. Si cette variable d'environnement n'est pas définie, alors abipkgdiff essaie de charger le fichier de spécifications $HOME/.abignore. Si ce fichier n'est pas présent, alors aucune spécification de suppression utilisateur par défaut n'est chargée.

    En plus de ces fichiers de spécifications de suppression par défaut, abipkgdiff recherchera dans les paquets comparés et s'il trouve un fichier se terminant par l'extension .abignore, il le considérera comme une spécification de suppression et le combinera à la spécification de suppression par défaut qui pourrait déjà être chargée.

    L'utilisateur peut également utiliser l'option --suppressions (documentée plus loin) pour fournir une spécification de suppression.

    Le code de sortie de la commande abipkgdiff est 0 si l'ABI des binaires comparés est identique, ou non nul s'ils diffèrent ou si l'outil a rencontré une erreur.

    kmidiff

    kmidiff compare les interfaces binaires de modules du noyau (Kernel Module Interfaces - KMI) de deux arbres de noyaux Linux. La KMI binaire est l'interface que le noyau Linux expose à ses modules. Les arbres qui nous intéressent ici sont le résultat de la compilation de l'arbre source du noyau Linux.

    Approche générale

    Voici un exemple de la manière de compiler votre noyau si vous souhaitez le comparer à un autre en utilisant kmidiff :

    git clone -b v4.5 git://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git linux/v4.5
cd linux/v4.5
make allyesconfig all

    Ensuite, installez les modules dans un répertoire, par exemple, le sous-répertoire build/modules de votre arbre source de noyau :

    mkdir build/modules
make modules_install INSTALL_MOD_DIR=build/modules

    Construisez ensuite une liste des interfaces exportées par le noyau, que vous souhaitez comparer :

    cat > kmi-whitelist << EOF
[kernel_4.5_kmi_whitelist]
 init_task
 schedule
 dev_queue_xmit
 __kmalloc
 printk
EOF

    Supposons que vous ayez fait quelque chose de similaire pour la branche v4.6 du noyau Linux, vous avez maintenant ces deux répertoires : linux/v4.5 et linux/v4.6. Leurs modules sont présents dans les répertoires linux/v4.5/build/modules et linux/v4.6/build/modules.

    Pour comparer leurs KMI, kmidiff doit savoir où trouver les binaires vmlinux et leurs modules associés. Voici à quoi ressemblerait la ligne de commande :

    kmidiff                                     \
  --kmi-whitelist  linux/v4.6/kmi-whitelist \
  --vmlinux1       linux/v4.5/vmlinux       \
  --vmlinux2       linux/v4.6/vmlinux       \
                   linux/v4.5/build/modules \
                   linux/v4.6/build/modules

    Cet outil utilise la bibliothèque libabigail pour analyser le binaire ainsi que ses informations de débogage associées. Voici son mode de fonctionnement général.

    Libabigail a ensuite la capacité de générer des représentations textuelles des Corpora d'ABI, de les comparer, d'analyser leurs changements et de faire des rapports à leur sujet.

    Invocation

    Plus généralement, kmidiff est invoqué sous la forme :

    kmidiff [options] <premier-repertoire-modules> <second-repertoire-modules>

    Environnement

    Par défaut, kmidiff compare toutes les interfaces (fonctions et variables exportées) entre le noyau et ses modules. En pratique, cependant, certains utilisateurs pourraient vouloir comparer un sous-ensemble de ces interfaces.

    Les utilisateurs peuvent alors définir une "liste blanche" des interfaces à comparer. Une telle liste blanche est simplement un fichier au format "INI" qui ressemble à ceci :

    [kernel_version_x86_64_whitelist]
  function1_name
  function2_name
  global_variable1_name
  ....

    Notez que le nom de la section (le nom entre les deux crochets) de ce fichier INI doit juste se terminer par la chaîne "whitelist". Vous pouvez donc définir le nom que vous souhaitez, par exemple [kernel_46_x86_64_whitelist].

    Ensuite, chaque ligne de ce fichier whitelist est le nom d'une fonction ou d'une variable exportée. Seules ces interfaces, ainsi que les types accessibles depuis leurs signatures, seront comparés par kmidiff récursivement.

    NAME

    abicompat - checks whether an application is ABI compatible with a shared library

    SYNOPSIS

    abicompat [--help | --version] [--list-undefined-symbols | -u] [--show-base-names | -b] [--app-debug-info-dir | --appd <path-to-app-debug-info-directory>] [--lib-debug-info-dir1 | --libd1 <path-to-lib1-debug-info>] [--lib-debug-info-dir2 | --libd2 <path-to-lib1-debug-info>] [--suppressions | --suppr <path-to-suppressions>] [--no-show-locs] [--btf] [--ctf] [--fail-no-debug-info] [--ignore-soname] [--weak-mode] [<application> <shared-library-first-version> <shared-library-second-version>]

    DESCRIPTION

    The abicompat program is a tool that checks whether an application that links against a given shared library is still ABI compatible with a subsequent version of that library. If the new version of the library introduces an ABI incompatibility, then abicompat hints the user at what exactly that incompatibility is.

    When abicompat checks for ABI compatibility, it compares the types of the functions and variables that are exported by the library and consumed by the application. If the types of these functions and variables are different in the second version of the library compared to the first, abicompat emits a diagnostic message. Note that it can only do so if the debug information is available in the libraries.

    The debug information can be provided in various forms:

    • The debug information is embedded in the binaries themselves.
    • The debug information is stored in separate files, using the DWARF format. These files are located in directories specified using the --appd, --libd1, and --libd2 options. These directories are expected to follow the standard layout: the actual debug file is expected to be located at debug-directory/usr/lib/debug/.debug/ binary-basename.debug.gz.
    • The debug information is stored in separate files, using the BTF format. This is specified using the --btf option.
    • The debug information is stored in separate files, using the CTF format. This is specified using the --ctf option.

    In addition to checking ABI compatibility, abicompat can also be used to check the integrity of the debug information itself, and to list the undefined symbols of an application.

    The filenames that are used to represent the shared libraries can be represented in two ways:

    • As a plain filename, like libfoo.so.1.2.3.
    • As a filename that includes the build ID, like libfoo.so.1.2.3/788cdd41a15985bf8e0a48d213a46e07d58822df.xml.

    The intent of including the buildid in the name is so that as a distro is updated with multiple versions of a given shared library, they can be represented nearby but non-conflicting. The SONAME is used in the second-last name component, inspired the behavior of ld.so and ldconfig, which rely on symbolic links to map references from the SONAME to an actual file.

    Example filenames:

    Invocation

    abicompat [options] [<application> <shared-library-first-version> <shared-library-second-version>]

    Options

    • --help

      Display a short help about the command and exit.

    • --version | -v

      Display the version of the program and exit.

    • --list-undefined-symbols | -u

      Display the list of undefined symbols of the application and exit.

    • --show-base-names | -b

      In the resulting report emitted by the tool, this option makes the application and libraries be referred to by their base names only; not by a full absolute name. This can be useful for use in scripts that wants to compare names of the application and libraries independently of what their directory names are.

    • --app-debug-info-dir | --appd <path-to-app-debug-info-directory>

      Set the path to the directory under which the debug information of the application is supposed to be laid out. This is useful for application binaries for which the debug info is in a separate set of files.

    • --lib-debug-info-dir1 | --libd1 <path-to-lib1-debug-info>

      Set the path to the directory under which the debug information of the first version of the shared library is supposed to be laid out. This is useful for shared library binaries for which the debug info is in a separate set of files.

    • --lib-debug-info-dir2 | --libd2 <path-to-lib1-debug-info>

      Set the path to the directory under which the debug information of the second version of the shared library is supposed to be laid out. This is useful for shared library binaries for which the debug info is in a separate set of files.

    • --suppressions | --suppr <path-to-suppressions>

      Use a suppression specification file located at path-to-suppressions. Note that this option can appear multiple times on the command line; all the suppression specification files are then taken into account.

    • --no-show-locs

      Do not show information about where in the second shared library the respective type was changed.

    • --btf

      When comparing binaries, extract ABI information from BTF debug information, if present.

    • --ctf

      When comparing binaries, extract ABI information from CTF debug information, if present.

    • --fail-no-debug-info

      If no debug info was found, then this option makes the program to fail. Otherwise, without this option, the program will attempt to compare properties of the binaries that are not related to debug info, like pure ELF properties.

    • --ignore-soname

      Ignore differences in the SONAME when doing a comparison

    • --weak-mode

      This triggers the weak mode of abicompat. In this mode, only one version of the library is required. That is, abicompat is invoked like this:

    abicompat --weak-mode <the-application> <the-library>

    Note that the --weak-mode option can even be omitted if only one version of the library is given, along with the application; in that case, abicompat automatically switches to operate in weak mode:

    abicompat <the-application> <the-library>

    In this weak mode, the types of functions and variables exported by the library and consumed by the application (as in, the symbols of the these functions and variables are undefined in the application and are defined and exported by the library) are compared to the version of these types as expected by the application. And if these two versions of types are different, abicompat tells the user what the differences are.

    In other words, in this mode, abicompat checks that the types of the functions and variables exported by the library mean the same thing as what the application expects, as far as the ABI is concerned.

    Note that in this mode, abicompat doesn't detect exported functions or variables (symbols) that are expected by the application but that are removed from the library. That is why it is called weak mode.

    Return values

    The exit code of the abicompat command is either 0 if the ABI of the binaries being compared are equal, or non-zero if they differ or if the tool encountered an error.

    In the later case, the exit code is a 8-bits-wide bit field in which each bit has a specific meaning.

    The first bit, of value 1, named ABIDIFF_ERROR means there was an error.

    The second bit, of value 2, named ABIDIFF_USAGE_ERROR means there was an error in the way the user invoked the tool. It might be set, for instance, if the user invoked the tool with an unknown command line switch, with a wrong number or argument, etc. If this bit is set, then the ABIDIFF_ERROR bit must be set as well.

    The third bit, of value 4, named ABIDIFF_ABI_CHANGE means the ABI of the binaries being compared are different.

    The fourth bit, of value 8, named ABIDIFF_ABI_INCOMPATIBLE_CHANGE means the ABI of the binaries compared are different in an incompatible way. If this bit is set, then the ABIDIFF_ABI_CHANGE bit must be set as well. If the ABIDIFF_ABI_CHANGE is set and the ABIDIFF_INCOMPATIBLE_CHANGE is NOT set, then it means that the ABIs being compared might or might not be compatible. In that case, a human being needs to review the ABI changes to decide if they are compatible or not.

    The remaining bits are not used for the moment.

    abilint analyse la représentation XML native d'une ABI telle qu'émise par abidw. Une fois qu'il a analysé la représentation XML de l'ABI, abilint construit un modèle en mémoire à partir de celle-ci. Si cette opération de lecture-écriture réussit, il y a de fortes chances que la représentation XML d'ABI d'entrée soit significative.

      NAME

      fedabipkgdiff — compares ABI of packages for different Fedora releases

      OVERVIEW OF THE ABIGAIL FRAMEWORK

      The Abigail framework provides tools and libraries to help software developers identify interface incompatibilities in libraries and other executable code. The goal of Abigail is to help developers maintain the Application Binary Interface (ABI) stability of their software.

      The framework consists of the following components:

      libabigail
      The core library that represents the debugging information in an intermediate representation format. This library provides an API to access and manipulate the debugging information.
      abidiff
      A tool that compares two versions of a library or executable file and reports the differences in their ABIs.
      abidw
      A tool that dumps the ABI of a library or executable file in a human readable format.
      abidump
      A tool that dumps the ABI of a library or executable file in a machine readable format.
      fedabipkgdiff
      A tool that automates the process of comparing the ABIs of packages across different Fedora releases.

      CONCEPTS

      This section describes the main concepts and terminology used by the fedabipkgdiff tool.

      ABI
      Application Binary Interface. It defines how compiled code should be linked and how libraries communicate with each other at the binary level. Changes in ABI can break compatibility between different versions of a library or program.
      Koji
      The Fedora build system. It is used to build RPM packages for Fedora and its derivatives.
      RPM package
      Red Hat Package Manager. A file format and package management system used by Fedora and other Linux distributions.
      Build
      A specific version and release of an RPM package. It is identified by its package name, version, and release.

      TOOLS

      The fedabipkgdiff tool is a script that automates the process of comparing the ABIs of packages across different Fedora releases. It uses the abidiff tool internally to perform the actual comparison.

      The following options are available:

      • --all-subpackages

        Also compares the ABIs of sub-packages. By default, only the main package is compared.

      • --arch <arch>

        Compare the ABI for a specific architecture arch. If this option is not specified, the tool compares the ABI for all architectures that are supported by the Fedora distribution.

      • --build <build>

        Compare the ABI of the specified build against the baseline specified by option --from. The build value is the name of the package, including its version and release. For example: httpd-2.4.18-2.fc24.

      • --from <distro>
      • --hide-uids

        Do not report differences in UIDs. This is useful when comparing packages that have been rebuilt without changes in the package source, as UIDs might differ between builds.

      • --include-private-symbols

        Include private symbols in the comparison. By default, only public symbols are compared. This option allows comparing the ABI of functions and global variables which symbols are defined and publicly exported in the binaries being compared, even if those types are not defined in public header files available from the packages being compared.

      • --private-dso

        Compare the ABI of shared libraries that are private to the packages. If this option is not provided, shared libraries that are private to the packages being considered are not compared.

      • --server <URL>
      • --show-identical-binaries
      Show the names of the all binaries compared, including the binaries whose ABI compare equal. By default, when this option is not provided, only binaries with ABI changes are mentionned in the output.
      • --suppressions <path-to-suppresions>

        Use a suppression specification file located at path-to-suppressions.

      • --to <distro>
      • --topurl <URL>
      • --traceback

        Show traceback when an exception raised. This is useful for developers of the tool itself to know more exceptional errors.

    Return value

    The exit code of the abipkgdiff command is either 0 if the ABI of the binaries compared are equivalent, or non-zero if they differ or if the tool encountered an error.

    In the later case, the value of the exit code is the same as for the abidiff tool.

    Use cases

    Below are some usage examples currently supported by fedabipkgdiff.

    1.
    Compare the ABI of binaries in a local package against the ABI of the latest stable package in Fedora 23. 
    $ fedabipkgdiff --from fc23 ./httpd-2.4.18-2.fc24.x86_64.rpm
    2.
    Compare the ABI of binaries in two local packages.

    Suppose you have built two versions of package httpd, and you want to see what ABI differences between these two versions of RPM files. The command line invocation would be:

    $ fedabipkgdiff path/to/httpd-2.4.23-3.fc23.x86_64.rpm another/path/to/httpd-2.4.23-4.fc24.x86_64.rpm

    All what fedabipkgdiff does happens on local machine without the need of querying or downloading RPMs from Koji.

    3.
    Compare the ABI of binaries in the latest build of the httpd package in Fedora 23 against the ABI of the binaries in the latest build of the same package in 24.

    In this case, note that neither of the two packages are available locally. The tool is going to talk with the Fedora Build System, determine what the versions and releases of the latest packages are, download them and perform the comparison locally. The command line invocation would be:

    $ fedabipkgdiff httpd-2.8.14.fc23 httpd-2.8.14.fc24

    But if we want to perform the ABI comparison for a specific architecture, say, x86_64, then the command line invocation would be:

    $ fedabipkgdiff httpd-2.8.14.fc23.x86_64 httpd-2.8.14.fc24.x86_64
    5.
    If the use wants to also compare the sub-packages of a given package, she can use the --all-subpackages option. The first command of the previous example would thus look like:
    $ fedabipkgdiff --all-subpackages httpd-2.8.14.fc23 httpd-2.8.14.fc24
