link(2) Manuel des appels système link(2)

NOM

link, linkat - créer un nouveau nom pour un fichier

BIBLIOTHÈQUE

Bibliothèque C standard (libc, -lc)

SYNTAXE

#include <unistd.h>
int link(const char *oldpath, const char *newpath);
#include <fcntl.h>           /* Définition des constantes AT_* */
#include <unistd.h>
int linkat(int olddirfd, const char *oldpath,
           int newdirfd, const char *newpath, int flags);
Exigences des macros de test de fonctionnalités pour glibc (voir feature_test_macros(7)):

linkat():

    Depuis glibc 2.10:
        _POSIX_C_SOURCE >= 200809L
    Avant glibc 2.10:
        _ATFILE_SOURCE

DESCRIPTION

link() crée un nouveau lien (également appelé lien physique) vers un fichier existant.

Si newpath existe, il ne sera pas écrasé.

Ce nouveau nom peut être utilisé exactement comme l'ancien pour toute opération ; les deux noms font référence au même fichier (et ont donc les mêmes permissions et propriétaires) et il est impossible de déterminer quel nom était l'original.

linkat()

L'appel système linkat() fonctionne exactement de la même manière que link(), à l'exception des différences décrites ici.

Si le chemin donné dans oldpath est relatif, il est interprété par rapport au répertoire référencé par le descripteur de fichier olddirfd (plutôt que par rapport au répertoire de travail actuel du processus appelant, comme le fait link() pour un chemin relatif).

Si oldpath est relatif et olddirfd est la valeur spéciale AT_FDCWD, alors oldpath est interprété par rapport au répertoire de travail actuel du processus appelant (comme link()).

Si oldpath est absolu, alors olddirfd est ignoré.

L'interprétation de newpath est la même que pour oldpath, sauf qu'un chemin relatif est interprété par rapport au répertoire référencé par le descripteur de fichier newdirfd.

Les valeurs suivantes peuvent être combinées par un OU bit à bit dans flags :

AT_EMPTY_PATH (depuis Linux 2.6.39)
Si oldpath est une chaîne vide, créez un lien vers le fichier référencé par olddirfd (qui peut avoir été obtenu en utilisant le flag open(2) O_PATH). Dans ce cas, olddirfd peut faire référence à n'importe quel type de fichier, sauf un répertoire. Cela ne fonctionnera généralement pas si le fichier a un nombre de liens de zéro (les fichiers créés avec O_TMPFILE et sans O_EXCL font exception). L'appelant doit posséder la capacité CAP_DAC_READ_SEARCH pour utiliser ce flag. Ce flag est spécifique à Linux ; définissez _GNU_SOURCE pour obtenir sa définition.
AT_SYMLINK_FOLLOW (depuis Linux 2.6.18)
Par défaut, linkat() ne déréférence pas oldpath s'il s'agit d'un lien symbolique (comme link()). Le flag AT_SYMLINK_FOLLOW peut être spécifié dans flags pour provoquer le déréférencement de oldpath s'il s'agit d'un lien symbolique. Si procfs est monté, cela peut être utilisé comme alternative à AT_EMPTY_PATH, comme suit :

linkat(AT_FDCWD, "/proc/self/fd/<fd>", newdirfd,
       newname, AT_SYMLINK_FOLLOW);

Avant Linux 2.6.18, l'argument flags n'était pas utilisé et devait être spécifié comme 0.

Voir openat(2) pour une explication de la nécessité de linkat().

VALEUR RENVOYÉE

En cas de succès, zéro est renvoyé. En cas d'erreur, -1 est renvoyé, et errno est définie pour indiquer l'erreur.

ERREURS

EACCES
L'accès en écriture au répertoire contenant newpath est refusé, ou l'autorisation de recherche est refusée pour l'un des répertoires dans le chemin préfixe de oldpath ou newpath. (Voir aussi path_resolution(7).)
EDQUOT
Le quota de blocs disque de l'utilisateur sur le système de fichiers a été épuisé.
EEXIST
newpath existe déjà.
EFAULT
oldpath ou newpath pointe en dehors de votre espace d'adressage accessible.
EIO
Une erreur d'entrée/sortie s'est produite.
ELOOP
Trop de liens symboliques ont été rencontrés lors de la résolution de oldpath ou newpath.
EMLINK
Le fichier référencé par oldpath a déjà le nombre maximal de liens. Par exemple, sur un système de fichiers ext4(5) qui n'utilise pas la fonctionnalité dir_index, la limite du nombre de liens physiques vers un fichier est de 65 000 ; sur btrfs(5), la limite est de 65 535 liens.
ENAMETOOLONG
oldpath ou newpath était trop long.
ENOENT
Un composant de répertoire dans oldpath ou newpath n'existe pas ou est un lien symbolique dangling.
ENOMEM
Un manque de mémoire noyau disponible s'est produit.
ENOSPC
Le périphérique contenant le fichier n'a pas de place pour la nouvelle entrée de répertoire.
ENOTDIR
Un composant utilisé comme répertoire dans oldpath ou newpath n'est pas, en fait, un répertoire.
EPERM
oldpath est un répertoire.
EPERM
Le système de fichiers contenant oldpath et newpath ne prend pas en charge la création de liens physiques.
EPERM (depuis Linux 3.6)
L'appelant n'a pas la permission de créer un lien physique vers ce fichier (voir la description de /proc/sys/fs/protected_hardlinks dans proc_sys_fs(5)).
EPERM
oldpath est marqué comme immuable ou append-only. (Voir FS_IOC_SETFLAGS(2const).)
EROFS
Le fichier est sur un système de fichiers en lecture seule.
EXDEV
oldpath et newpath ne sont pas sur le même système de fichiers monté. (Linux permet à un système de fichiers d'être monté à plusieurs endroits, mais link() ne fonctionne pas entre différents montages, même si le même système de fichiers est monté sur les deux.)

Les erreurs supplémentaires suivantes peuvent survenir pour linkat :

EBADF
oldpath (newpath) est relatif mais olddirfd (newdirfd) n'est ni AT_FDCWD ni un descripteur de fichier valide.
EINVAL
Une valeur de flag invalide a été spécifiée dans flags.
ENOENT
AT_EMPTY_PATH a été spécifié dans flags, mais l'appelant n'avait pas la capacité CAP_DAC_READ_SEARCH.
ENOENT
Une tentative a été faite pour créer un lien vers le fichier /proc/self/fd/NN correspondant à un descripteur de fichier créé avec

open(path, O_TMPFILE | O_EXCL, mode);

Voir open(2).
ENOENT
Si oldpath est une chaîne vide, olddirfd fait référence à un fichier qui n'existe pas.

VERSIONS

POSIX.1-2001 indique que link() doit déréférencer oldpath s'il s'agit d'un lien symbolique. Cependant, depuis Linux 2.0, Linux ne le fait pas : si oldpath est un lien symbolique, alors newpath est créé comme un lien (physique) vers le même fichier de lien symbolique (c'est-à-dire newpath devient un lien symbolique vers le même fichier auquel oldpath fait référence). D'autres implémentations se comportent de la même manière que Linux. POSIX.1-2008 modifie la spécification de link(), rendant dépendant de l'implémentation si oldpath est déréférencé ou non s'il s'agit d'un lien symbolique. Pour un contrôle précis sur le traitement des liens symboliques lors de la création d'un lien, utilisez linkat().

glibc

Sur les anciens noyaux où linkat() n'est pas disponible, la fonction d'enveloppe glibc utilise link(), sauf si AT_SYMLINK_FOLLOW est spécifié. Lorsque oldpath et newpath sont des chemins relatifs, glibc construit des chemins basés sur les liens symboliques dans /proc/self/fd qui correspondent aux arguments olddirfd et newdirfd.

NORMES

POSIX.1-2024.

HISTORIQUE

link()
SVr4, 4.3BSD, POSIX.1-2001 (mais voir VERSIONS).
linkat()
POSIX.1-2008. Linux 2.6.16, glibc 2.4.

NOTES

Les liens physiques, tels que créés par link(), ne peuvent pas enjamber des systèmes de fichiers. Utilisez symlink(2) si cela est requis.

BOGUES

Sur les systèmes de fichiers NFS, le code de retour peut être erroné si le serveur NFS effectue la création du lien et meurt avant de pouvoir le dire. Utilisez stat(2) pour savoir si le lien a été créé.
