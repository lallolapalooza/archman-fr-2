NOM

libunwind-dynamic -- support de libunwind pour le code généré à l'exécution

INTRODUCTION

Pour que libunwind puisse faire son travail, elle doit être capable de reconstruire l'état de la pile d'appels de chaque trame dans une chaîne d'appels. L'état de la pile d'appels décrit le sous-ensemble de l'état de la machine qui consiste en les registres de trame (typiquement le pointeur d'instruction et le pointeur de pile) et tous les registres sauvegardés par l'appelé (registres préservés). L'état de la trame décrit chaque registre soit en fournissant sa valeur actuelle (pour les registres de trame), soit en fournissant l'emplacement où la valeur actuelle est stockée (registres sauvegardés par l'appelé).

Pour le code généré statiquement, le compilateur s'occupe normalement d'émettre des informations de déroulement qui fournissent le minimum d'informations nécessaires pour reconstruire l'état de la trame pour chaque instruction d'une procédure. Pour le code généré dynamiquement, le générateur de code d'exécution doit utiliser l'interface d'informations de déroulement dynamique fournie par libunwind pour fournir les informations équivalentes. Cette page de manuel décrit le format de ces informations en détail.

Aux fins de cette discussion, une procédure est définie comme une pièce arbitraire de code contigu. Normalement, chaque procédure correspond directement à une fonction dans le langage source, mais ce n'est pas strictement requis. Par exemple, un générateur de code d'exécution pourrait traduire une fonction donnée en deux procédures distinctes (non contiguës) : une pour le code fréquemment exécuté (chaud) et une pour le code rarement exécuté (froid). De même, des fonctions simples du langage source (généralement des fonctions feuilles) peuvent être traduites en code pour lequel les conventions de déroulement par défaut s'appliquent, et pour un tel code, il n'est pas strictement nécessaire d'enregistrer les informations de déroulement dynamiques.

Une procédure est logiquement composée d'une séquence de régions. Les régions sont imbriquées dans le sens où l'état de la trame à la fin d'une région est, par défaut, supposé être l'état de la trame pour la région suivante. Chaque région est considérée comme étant divisée en un prologue, un corps, et un épilogue. Chacun d'eux peut être vide. S'il n'est pas vide, le prologue met en place l'état de la trame pour le corps. Par exemple, le prologue peut devoir allouer de l'espace sur la pile et sauvegarder certains registres sauvegardés par l'appelé. Le corps effectue le travail réel de la procédure mais ne modifie en aucun cas l'état de la trame. S'il n'est pas vide, l'épilogue restaure l'état de la trame précédent et, ce faisant, annule l'effet des prologues. En fait, un seul épilogue peut annuler l'effet des prologues de plusieurs régions (imbriquées).

Nous tenons à souligner que même si le prologue, le corps et l'épilogue sont des entités logiquement distinctes, les générateurs de code optimisants entrelaceront généralement les instructions des trois entités. Pour cette raison, l'interface d'informations de déroulement dynamique de libunwind ne fait aucune distinction quelconque entre le prologue et le corps. De même, l'ensemble exact d'instructions qui composent un épilogue est également sans importance. Le seul point de l'épilogue qui doit être décrit explicitement par les informations de déroulement dynamiques est le point auquel le pointeur de pile est restauré. La raison pour laquelle ce point doit être décrit est qu'une fois que le pointeur de pile est restauré, toutes les valeurs sauvegardées dans la partie désallouée de la trame de pile deviennent invalides et libunwind a donc besoin de le savoir. La partie de l'état de la trame non sauvegardée sur la pile est supposée rester valide jusqu'à la fin de la région. Pour cette raison, il n'est généralement pas nécessaire de décrire les instructions qui restaurent le contenu des registres sauvegardés par l'appelé.

Au sein d'une région, chaque instruction qui affecte l'état de la trame d'une manière ou d'une autre doit être décrite avec un descripteur d'opération. À cette fin, chaque instruction de la région se voit attribuer un index unique. La manière exacte dont cet index est dérivé dépend de l'architecture. Par exemple, sur les architectures de type RISC et EPIC, les instructions ont une taille fixe, il est donc possible de simplement numéroter les instructions. En revanche, la plupart des architectures CISC utilisent des encodages d'instructions de longueur variable, il est donc généralement nécessaire d'utiliser un décalage d'octet comme index. Étant donné l'index de l'instruction, le descripteur d'opération spécifie l'effet de l'instruction de manière abstraite. Par exemple, il peut exprimer que l'instruction stocke le registre sauvegardé par l'appelé r1 au décalage 16 dans la trame de pile.

PROCÉDURES

Le générateur de code d'exécution enregistre les informations de déroulement dynamiques d'une procédure en configurant une structure de type unw_dyn_info_t et en appelant _U_dyn_register(), en passant l'adresse de la structure comme seul argument. Les membres de la structure unw_dyn_info_t sont décrits ci-dessous :

void *next

Privé à libunwind. Ne doit pas être utilisé par l'application.
void *prev

Privé à libunwind. Ne doit pas être utilisé par l'application.
unw_word_t start_ip

L'adresse de début des instructions de la procédure (rappelez-vous : les procédures sont définies comme des morceaux de code contigus, donc une seule plage de code suffit).
unw_word_t end_ip

L'adresse de fin des instructions de la procédure (non inclusive, c'est-à-dire que end_ip-start_ip est la taille de la procédure en octets).
unw_word_t gp

La valeur du pointeur global utilisée pour cette procédure. La signification exacte du pointeur global est spécifique à l'architecture et sur certaines architectures, il n'est pas utilisé du tout.
int32_t format

Le format des informations de déroulement. Ce membre peut être l'un des UNW_INFO_FORMAT_DYNAMIC, UNW_INFO_FORMAT_TABLE, ou UNW_INFO_FORMAT_REMOTE_TABLE.
union u

Cette union contient une sous-structure pour chaque format d'informations de déroulement possible :
unw_dyn_proc_info_t pi

Ce membre est utilisé pour le format UNW_INFO_FORMAT_DYNAMIC.
unw_dyn_table_info_t ti

Ce membre est utilisé pour le format UNW_INFO_FORMAT_TABLE.
unw_dyn_remote_table_info_t rti

Ce membre est utilisé pour le format UNW_INFO_FORMAT_REMOTE_TABLE.

Le format de ces sous-membres est décrit en détail ci-dessous.

FORMAT PROC-INFO

C'est le format préféré pour les informations de déroulement dynamiques et il est généralement celui utilisé par les générateurs de code d'exécution complets. Dans ce format, les détails d'une procédure sont décrits par une structure de type unw_dyn_proc_info_t. Cette structure contient les membres suivants :

unw_word_t name_ptr

L'adresse d'un nom (lisible par l'homme) de la procédure ou 0 si aucun nom de ce type n'est disponible. S'il est non nul, la chaîne stockée à cette adresse doit se terminer par un caractère NUL ASCII. Pour les langages source qui utilisent le renommage de noms (tels que C++ ou Java), la chaîne stockée à cette adresse devrait être la version démanglée du nom.
unw_word_t handler

L'adresse de la routine de personnalité pour cette procédure. Les routines de personnalité sont utilisées conjointement avec la gestion des exceptions. Voir le projet ABI C++ (http://www.codesourcery.com/cxx-abi/) pour un aperçu et une description de la routine de personnalité. Si la procédure n'a pas de routine de personnalité, handler doit être défini à 0.
uint32_t flags

Un masque de bits d'indicateurs. Pour le moment, aucun indicateur n'a été défini et ce membre doit être défini à 0.
unw_dyn_region_info_t *regions

Une liste chaînée de descripteurs de régions se terminant par NULL. Voir la section ``Descripteurs de régions'' ci-dessous pour plus de détails.

unw_word_t table_len

La longueur des informations de déroulement (table_data) comptée en unités de mots (unw_word_t).
unw_word_t table_data

FORMAT DE TABLE INFO À DISTANCE

Le format de table-info à distance a le même objectif de base que le format de table-info régulier. La seule différence est que lorsque libunwind utilise les informations de déroulement, il conservera les données de la table dans l'espace d'adressage cible (qui peut être distant). Par conséquent, le type du membre table_data est unw_word_t plutôt qu'un pointeur. Cela implique que libunwind devra accéder aux données de la table via la fonction de rappel access_mem() de l'espace d'adressage, plutôt que par une référence mémoire directe.

Du point de vue d'un générateur de code d'exécution, le format de table-info à distance n'offre aucun avantage et on s'attend à ce que de tels générateurs décrivent leurs procédures soit avec le format proc-info, soit avec le format table-info normal. La raison principale de l'existence du format de table-info à distance est de permettre au rappel find_proc_info() spécifique à l'espace d'adressage (voir unw_create_addr_space(3libunwind)) de retourner des tables de déroulement dont les données restent en mémoire distante. Cela peut accélérer le déroulement (par exemple, pour un débogueur) car cela réduit la quantité de données qui doivent être chargées depuis la mémoire distante.

DESCRIPTEURS DE RÉGIONS

Un descripteur de région est une structure de longueur variable qui décrit comment chaque instruction de la région affecte l'état de la pile (frame state). Bien sûr, la plupart des instructions d'une région ne modifient pas l'état de la pile et pour celles-ci, rien ne doit être enregistré dans le descripteur de région. Un descripteur de région est une structure de type unw_dyn_region_info_t et possède les membres suivants :

unw_dyn_region_info_t *next

Un pointeur vers la région suivante. Si c'est la dernière région, next est NULL.
int32_t insn_count

La longueur de la région en instructions. Chaque instruction est supposée avoir une taille fixe (voir les sections spécifiques à l'architecture pour plus de détails). La valeur de insn_count peut être négative dans la dernière région d'une procédure (c'est-à-dire qu'elle ne peut être négative que si next est NULL). Une valeur négative indique que la région couvre les N dernières instructions de la procédure, où N est la valeur absolue de insn_count.
uint32_t op_count

La longueur (allouée) du tableau op_count.
unw_dyn_op_t op

Un tableau de directives de déroulement dynamique. Voir la Section « Directives de déroulement dynamique » pour une description des directives.

Un descripteur de région avec une valeur insn_count de zéro est une région vide et de telles régions sont parfaitement légales. En fait, les régions vides peuvent être utiles pour établir un état de pile particulier avant le début d'une autre région.

Une seule liste de régions peut être partagée entre plusieurs procédures à condition que ces procédures partagent un prologue et un épilogue communs (leurs corps peuvent différer, bien sûr). Normalement, de telles procédures consistent en un prologue pré-établi, le corps, et un épilogue pré-établi. Cela pourrait être décrit par deux régions : une couvrant le prologue et une couvrant l'épilogue. Comme la longueur du corps est variable, la dernière région devrait spécifier une valeur négative dans insn_count afin que libunwind sache que la région couvre la fin de la procédure (jusqu'à l'adresse spécifiée par end_ip).

Le descripteur de région est une structure de longueur variable pour rendre possible l'allocation de toute la mémoire nécessaire avec une seule demande d'allocation mémoire. Pour faciliter l'allocation des descripteurs de régions, libunwind fournit une routine d'assistance dont la synopsis est la suivante :

size_t _U_dyn_region_size(int op_count);

Cette routine renvoie le nombre d'octets nécessaires pour contenir un descripteur de région avec de l'espace pour op_count directives de déroulement. Notez que la longueur du tableau op n'a pas besoin de correspondre exactement au nombre de directives dans une région. Au lieu de cela, il suffit que le tableau op contienne au moins autant d'entrées qu'il y a de directives, car la fin des directives peut toujours être indiquée avec la directive UNW_DYN_STOP.

DIRECTIVES DE DÉROULEMENT DYNAMIQUE

Une directive de déroulement dynamique décrit comment l'état de la pile change à un point particulier dans une région. La description est sous forme d'une structure de type unw_dyn_op_t. Cette structure possède les membres suivants :

int8_t tag

L'étiquette de l'opération. Doit être l'une des valeurs unw_dyn_operation_t décrites ci-dessous.
int8_t qp

Le prédicat qualifiant qui contrôle si cette directive est active ou non. Ceci est utile pour les architectures prédiquées telles que IA-64 ou ARM, où le contenu d'un autre registre (préservé par l'appelé) détermine si une instruction est exécutée (prend effet) ou non. Si la directive est toujours active, ce membre doit être défini sur la constante manifeste _U_QP_TRUE (cette constante est définie pour toutes les architectures, prédiquées ou non).
int16_t reg

Le numéro du registre affecté par l'instruction.
int32_t when

Le numéro relatif à la région de l'instruction à laquelle cette directive s'applique. Par exemple, une valeur de 0 signifie que l'effet décrit par cette directive a eu lieu une fois la première instruction de la région exécutée.
unw_word_t val

La valeur à appliquer par l'étiquette de l'opération. La signification exacte de cette valeur varie selon l'étiquette. Voir la Section « Étiquettes d'opération » ci-dessous.

Il est tout à fait légitime de spécifier plusieurs directives de déroulement dynamique avec la même valeur de `when`, si une instruction particulière a un effet complexe sur l'état de la pile.

Les régions vides, par définition, ne contiennent aucune instruction réelle et, en tant que telles, les directives ne sont pas liées à une instruction particulière. Par convention, le membre `when` doit être défini sur 0, cependant.

Il n'est pas nécessaire que les directives de déroulement dynamique apparaissent par ordre croissant de valeurs `when`. Si les directives sont triées dans cet ordre, cela peut entraîner une exécution légèrement plus rapide, mais un générateur de code d'exécution ne devrait pas faire d'efforts supplémentaires juste pour s'assurer que les directives sont triées.

NOTE D'IMPLÉMENTATION : si les implémentations de libunwind pour certaines architectures préfèrent que la liste des directives de déroulement soit triée, il est recommandé que ces implémentations vérifient d'abord si la liste est déjà triée et, si ce n'est pas le cas, trient explicitement les directives avant la première utilisation. Avec cette approche, le surcoût du tri explicite n'est payé que lorsqu'il y a un réel avantage et si le générateur de code d'exécution génère naturellement des listes triées, la pénalité de performance se limite à une simple vérification O(N).

ÉTIQUETTES D'OPÉRATIONS

Les étiquettes d'opération possibles sont définies par le type d'énumération unw_dyn_operation_t qui définit les valeurs suivantes :

UNW_DYN_STOP

Marque la fin de la liste des directives de déroulement dynamique. Toutes les entrées restantes dans le tableau `op` du descripteur de région sont ignorées. Cette étiquette a une valeur garantie de 0.
UNW_DYN_SAVE_REG

Marque une instruction qui sauvegarde le registre `reg` dans le registre `val`.
UNW_DYN_SPILL_FP_REL

Marque une instruction qui "spille" (sauvegarde sur la pile) le registre `reg` vers un emplacement relatif au pointeur de cadre (frame pointer). L'offset relatif au pointeur de cadre est donné par la valeur stockée dans le membre `val`. Voir les sections spécifiques à l'architecture pour une description de la disposition de la pile.
UNW_DYN_SPILL_SP_REL

Marque une instruction qui "spille" (sauvegarde sur la pile) le registre `reg` vers un emplacement relatif au pointeur de pile (stack pointer). L'offset relatif au pointeur de pile est donné par la valeur stockée dans le membre `val`. Voir les sections spécifiques à l'architecture pour une description de la disposition de la pile.
UNW_DYN_ADD

Marque une instruction qui ajoute la valeur constante `val` au registre `reg`. Pour ajouter ou soustraire une valeur constante, stockez le complément à deux de la valeur dans `val`. L'ensemble des registres pouvant être spécifiés pour cette étiquette est décrit dans les sections spécifiques à l'architecture ci-dessous.
