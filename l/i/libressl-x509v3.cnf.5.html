NOM

x509v3.cnf — Format de configuration des extensions X.509 V3 de certificat

DESCRIPTION

Plusieurs utilitaires OpenSSL peuvent ajouter des extensions à un certificat ou à une demande de certificat en fonction du contenu d'un fichier de configuration. Le format du fichier est basé sur le format de openssl.cnf(5).

Généralement, l'application contiendra une option pour pointer vers une section d'extensions. Chaque ligne de la section d'extensions prend la forme :

nom_extension=[critical,] options_extension

Si critical est présent, alors l'extension sera critique.

Le format de options_extension dépend de la valeur de nom_extension.

Il existe quatre types principaux d'extensions : extensions de chaîne de caractères, extensions multi-valeurs, extensions brutes et extensions arbitraires.

Les extensions de chaîne de caractères ont simplement une chaîne de caractères qui contient soit la valeur elle-même, soit comment elle est obtenue. Par exemple :

nsComment="Ceci est un commentaire"

Les extensions multi-valeurs ont une forme courte et une forme longue. La forme courte est une liste de noms et de valeurs :

basicConstraints=critical,CA:true,pathlen:1

La forme longue permet de placer les valeurs dans une section séparée :

basicConstraints=critical,@bs_section

[bs_section]
CA=true
pathlen=1

Les deux formes sont équivalentes.

La syntaxe des extensions brutes est régie par le code de l'extension : elle peut par exemple contenir des données dans plusieurs sections. La syntaxe correcte à utiliser est définie par le code de l'extension lui-même : consultez l'extension des politiques de certificat pour un exemple.

Si un type d'extension n'est pas pris en charge, alors la syntaxe d'extension arbitraire doit être utilisée ; voir la section EXTENSIONS ARBITRAIRES pour plus de détails.

EXTENSIONS STANDARDS

Les sections suivantes décrivent chaque extension prise en charge en détail.

Contraintes de base

Ceci est une extension multi-valeur qui indique si un certificat est un certificat d'AC. Le premier nom (obligatoire) est CA suivi de TRUE ou FALSE. Si CA est TRUE, alors un nom optionnel pathlen suivi d'une valeur non négative peut être inclus. Par exemple :

basicConstraints=CA:TRUE
basicConstraints=CA:FALSE
basicConstraints=critical,CA:TRUE, pathlen:0

Un certificat d'AC doit inclure la valeur basicConstraints avec le champ CA défini sur TRUE. Un certificat d'entité finale doit soit définir CA sur FALSE, soit exclure entièrement l'extension. Certains logiciels peuvent exiger l'inclusion de basicConstraints avec CA défini sur FALSE pour les certificats d'entité finale.

Le paramètre pathlen indique le nombre maximum d'AC qui peuvent apparaître en dessous de celle-ci dans une chaîne. Donc, si vous avez une AC avec un pathlen de zéro, elle ne peut être utilisée que pour signer des certificats d'entité finale et non d'autres AC.

Usage de la clé

L'utilisation de la clé est une extension multi-valeur composée d'une liste de noms des utilisations de clés autorisées.

Les noms pris en charge sont : digitalSignature, nonRepudiation, keyEncipherment, dataEncipherment, keyAgreement, keyCertSign, cRLSign, encipherOnly et decipherOnly. Exemples :

keyUsage=digitalSignature, nonRepudiation
keyUsage=critical, keyCertSign

Usage de la clé étendu

Cette extension consiste en une liste de finalités pour lesquelles la clé publique du certificat peut être utilisée.

Il peut s'agir de noms courts d'objets ou de la forme numérique pointée des OID. Bien que tout OID puisse être utilisé, seules certaines valeurs sont significatives. En particulier, les valeurs PKIX, NS et MS suivantes sont significatives :

valeur signification
serverAuth Authentification de serveur TLS
clientAuth Authentification de client TLS
codeSigning Signature de code
emailProtection Protection d'e-mail (S/MIME)
timeStamping Horodatage de confiance
OCSPSigning Signature OCSP
ipsecIKE Échange de clés Internet IPsec (IKE)
msCodeInd Signature de code individuelle Microsoft (authenticode)
msCodeCom Signature de code commerciale Microsoft (authenticode)
msCTLSign Signature de liste de confiance Microsoft
msEFS Système de fichiers chiffré Microsoft

Exemples :

extendedKeyUsage=critical,codeSigning,1.2.3.4
extendedKeyUsage=serverAuth,clientAuth

Identifiant de la clé du sujet

Ceci est en réalité une extension de chaîne de caractères et peut prendre deux valeurs possibles. Soit le mot hash qui suivra automatiquement les directives du RFC 3280, soit une chaîne hexadécimale donnant la valeur de l'extension à inclure. L'utilisation de la chaîne hexadécimale est fortement déconseillée. Exemple :

subjectKeyIdentifier=hash

Identifiant de la clé de l'autorité

L'extension d'identifiant de clé d'autorité permet deux options, keyid et issuer : les deux peuvent prendre la valeur optionnelle always.

Si l'option keyid est présente, une tentative est faite pour copier l'identifiant de clé du sujet du certificat parent. Si la valeur always est présente, alors une erreur est retournée si l'option échoue.

L'option issuer copie l'émetteur et le numéro de série du certificat de l'émetteur. Cela ne sera fait que si l'option keyid échoue ou n'est pas incluse, sauf si le drapeau always inclura toujours la valeur. Exemple :

authorityKeyIdentifier=keyid,issuer

Nom alternatif du sujet

L'extension de nom alternatif du sujet permet d'inclure diverses valeurs littérales dans le fichier de configuration. Celles-ci incluent email (une adresse e-mail), URI (une uniforme

resource indicator), DNS (un nom de domaine DNS), RID (un identifiant enregistré: OBJECT IDENTIFIER), IP (une adresse IP), dirName (un nom unique) et otherName.

L'option email peut inclure une valeur spéciale copy. Cela inclura automatiquement toutes les adresses e-mail contenues dans le nom du sujet du certificat dans l'extension.

L'adresse IP utilisée dans les options IP peut être au format IPv4 ou IPv6.

La valeur de dirName doit pointer vers une section contenant le nom unique à utiliser comme ensemble de paires nom-valeur. Des AVAs multi-valeurs peuvent être formées en faisant précéder le nom par un caractère ‘+’.

otherName peut inclure des données arbitraires associées à un OID : la valeur doit être l'OID suivi d'un point-virgule et du contenu au format standard ASN1_generate_nconf(3) . Exemples :

subjectAltName=email:copy,email:my@other.address,URI:http://my.url.here/
subjectAltName=IP:192.168.7.1
subjectAltName=IP:13::17
subjectAltName=email:my@other.address,RID:1.2.3.4
subjectAltName=otherName:1.2.3.4;UTF8:some other identifier

subjectAltName=dirName:dir_sect

[dir_sect]
C=UK
O=My Organization
OU=My Unit
CN=My Name

Nom alternatif de l'émetteur

L'option de nom alternatif de l'émetteur prend en charge toutes les options littérales du nom alternatif du sujet. Elle ne prend pas en charge l'option email:copy car cela n'aurait pas de sens. Elle prend en charge une option supplémentaire issuer:copy qui copiera toutes les valeurs du nom alternatif du sujet du certificat de l'émetteur (si possible). Exemple :

issuerAltName = issuer:copy

Informations d'accès de l'autorité

L'extension d'informations d'accès de l'autorité fournit des détails sur la manière d'accéder à certaines informations relatives à l'AC. Sa syntaxe est accessOID; location où location a la même syntaxe que le nom alternatif du sujet (sauf que email:copy n'est pas pris en charge). accessOID peut être n'importe quel OID valide, mais seules certaines valeurs sont significatives, par exemple OCSP et caIssuers. Exemple :

authorityInfoAccess = OCSP;URI:http://ocsp.my.host/
authorityInfoAccess = caIssuers;URI:http://my.ca/ca.html

Points de distribution des listes de révocation

Il s'agit d'une extension multivaluée dont les options peuvent être soit sous forme de paire nom:valeur utilisant la même forme que le nom alternatif du sujet, soit une seule valeur représentant un nom de section contenant tous les champs du point de distribution.

Pour une paire nom:valeur, un nouveau DistributionPoint avec le champ fullName défini sur la valeur donnée, les champs cRLissuer et reasons sont omis dans ce cas.

Dans le cas de l'option unique, la section indiquée contient les valeurs pour chaque champ. Dans cette section :

Si le nom est fullname, le champ valeur doit contenir le nom complet du point de distribution dans le même format que le nom alternatif du sujet.

Si le nom est relativename, alors le champ valeur doit contenir un nom de section dont le contenu représente un fragment de nom unique à placer dans ce champ.

Le nom CRLIssuer, s'il est présent, doit contenir une valeur pour ce champ au format du nom alternatif du sujet.

Si le nom est reasons, le champ valeur doit consister en un champ séparé par des virgules contenant les raisons. Les raisons valides sont : keyCompromise, CACompromise, affiliationChanged, superseded, cessationOfOperation, certificateHold, privilegeWithdrawn, et AACompromise.

Exemples simples :

crlDistributionPoints=URI:http://myhost.com/myca.crl
crlDistributionPoints=URI:http://my.com/my.crl,URI:http://oth.com/my.crl

Exemple complet de point de distribution :

crlDistributionPoints=crldp1_section

[crldp1_section]
fullname=URI:http://myhost.com/myca.crl
CRLissuer=dirName:issuer_sect
reasons=keyCompromise, CACompromise

[issuer_sect]
C=UK
O=Organisation
CN=Some Name

Point de distribution d'émission

Cette extension ne doit apparaître que dans les CRLs. C'est une extension multivaluée dont la syntaxe est similaire à la « section » pointée par l'extension des points de distribution CRL avec quelques différences.

Les noms reasons et CRLissuer ne sont pas reconnus.

Le nom onlysomereasons est accepté, ce qui définit ce champ. La valeur est dans le même format que le champ reasons de l'extension des points de distribution CRL.

Les noms onlyuser, onlyCA, onlyAA, et indirectCRL sont également acceptés. Les valeurs doivent être des valeurs booléennes (TRUE ou FALSE) pour indiquer la valeur du champ correspondant. Exemple :

issuingDistributionPoint=critical, @idp_section

[idp_section]
fullname=URI:http://myhost.com/myca.crl
indirectCRL=TRUE
onlysomereasons=keyCompromise, CACompromise

[issuer_sect]
C=UK
O=Organisation
CN=Some Name

Politiques de certification

Il s'agit d'une extension brute. Tous les champs de cette extension peuvent être définis en utilisant la syntaxe appropriée.

Si vous suivez les recommandations PKIX et n'utilisez qu'un seul OID, vous incluez simplement la valeur de cet OID. Plusieurs OIDs peuvent être définis séparés par des virgules, par exemple :

certificatePolicies= 1.2.4.5, 1.1.3.4

Si vous souhaitez inclure des qualificateurs, l'OID de politique et les qualificateurs doivent être spécifiés dans une section séparée : cela se fait en utilisant la syntaxe @section au lieu d'une valeur OID littérale.

La section référencée doit inclure l'OID de politique en utilisant le nom policyIdentifier. Les qualificateurs CPSuri peuvent être inclus en utilisant la syntaxe :

CPS.nnn=valeur

Les qualificateurs userNotice peuvent être définis en utilisant la syntaxe :

userNotice.nnn=@notice

La valeur du qualificateur userNotice est spécifiée dans la section pertinente. Cette section peut inclure les options explicitText, organization, et noticeNumbers. explicitText et organization sont des chaînes de caractères, et noticeNumbers est une liste de nombres séparés par des virgules. Les options organization et noticeNumbers (si elles sont incluses) doivent toutes deux être présentes. Si vous utilisez l'option userNotice avec IE5, vous avez besoin de l'option ia5org au niveau supérieur pour modifier l'encodage : sinon, il ne sera pas interprété correctement. Exemple :

certificatePolicies=ia5org,1.2.3.4,1.5.6.7.8,@polsect

[polsect]
policyIdentifier = 1.3.5.8
CPS.1="http://my.host.name/"
CPS.2="http://my.your.name/"
userNotice.1=@notice

[notice]
explicitText="Explicit Text Here"
organization="Organisation Name"
noticeNumbers=1,2,3,4

L'option ia5org modifie le type du champ organization. Dans la RFC 2459, il ne peut être que de type DisplayText. Dans la RFC 3280, IA5String est également permissible. Certains logiciels (par exemple, certaines versions de MSIE) peuvent nécessiter ia5org.

Contraintes de politique

Il s'agit d'une extension multivaluée qui consiste en les noms requireExplicitPolicy ou inhibitPolicyMapping et une valeur entière non négative. Au moins un composant doit être présent. Exemple :

policyConstraints = requireExplicitPolicy:3

Inhibition de toute politique

Il s'agit d'une extension de chaîne dont la valeur doit être un entier non négatif. Exemple :

inhibitAnyPolicy = 2

Contraintes de nom

L'extension de contraintes de nom est une extension multivaluée. Le nom doit commencer par le mot permitted ou excluded, suivi d'un point-virgule. Le reste du nom et la valeur suivent la syntaxe de subjectAltName, sauf que email:copy n'est pas pris en charge et la forme IP doit consister en une adresse IP et un masque de sous-réseau séparés par une barre oblique. Exemples :

nameConstraints=permitted;IP:192.168.0.0/255.255.0.0
nameConstraints=permitted;email:.somedomain.com
nameConstraints=excluded;email:.com

OCSP sans vérification

L'extension OCSP sans vérification est une extension de chaîne, mais sa valeur est ignorée. Exemple :

noCheck = ignored

NAME

x509v3.cnf

configuration file for the X509 v3 extension facilities

DESCRIPTION

The X509 v3 extension facilities are configured using the standard OpenSSL configuration file, x509v3.cnf. The location of this file is determined by the openssl.cnf(5) file.

The X509 v3 extensions are specified in the configuration file using the x509v3_extensions section, or for individual certificate requests, using the x509v3_config section.

The configuration directives specify extensions that are added to certificates, certificate requests, or CRLs. The format is generally of the form:

extension_name = [critical,] [optional,] value

If the extension is marked critical then the extension MUST be recognised by the certificate processing application. If it is not recognised the certificate MUST be rejected.

If an extension is not marked critical then it is optional. If an application does not recognise it, it can be ignored.

The value part depends on the extension type. It may be a simple string, a list of values, or a reference to another section in the configuration file.

The following sections describe the supported extensions and their formats.

STANDARD EXTENSIONS

TLS Feature (aka must staple)

This is a multi-valued extension consisting of a list of TLS extension identifiers. Each identifier may be a number in the range from 0 to 65535 or a supported name. When a TLS client sends a listed extension, the TLS server is expected to include that extension in its reply.

The supported names are: status_request and status_request_v2. Example:

tlsfeature = status_request

DEPRECATED EXTENSIONS

The following extensions are non-standard, Netscape specific and largely obsolete. Their use in new applications is discouraged.

Netscape string extensions

Netscape comment (nsComment) is a string extension containing a comment which will be displayed when the certificate is viewed in some browsers. Example:

nsComment = Some Random Comment

Other supported extensions in this category are: nsBaseUrl, nsRevocationUrl, nsCaRevocationUrl, nsRenewalUrl, nsCaPolicyUrl, and nsSslServerName.

Netscape certificate type

This is a multi-valued extensions which consists of a list of flags to be included. It was used to indicate the purposes for which a certificate could be used. The basicConstraints, keyUsage, and extended key usage extensions are now used instead.

Acceptable values for nsCertType are: client, server, email, objsign, reserved, sslCA, emailCA, objCA.

ARBITRARY EXTENSIONS

If an extension is not supported by the OpenSSL code, then it must be encoded using the arbitrary extension format. It is also possible to use the arbitrary format for supported extensions. Extreme care should be taken to ensure that the data is formatted correctly for the given extension type.

There are two ways to encode arbitrary extensions.

The first way is to use the word ASN1 followed by the extension content using the same syntax as ASN1_generate_nconf(3). For example:

1.2.3.4=critical,ASN1:UTF8String:Some random data
1.2.3.4=ASN1:SEQUENCE:seq_sect

[seq_sect]
field1 = UTF8:field1
field2 = UTF8:field2

It is also possible to use the word DER to include the raw encoded data in any extension.

1.2.3.4=critical,DER:01:02:03:04
1.2.3.4=DER:01020304

The value following DER is a hex dump of the DER encoding of the extension. Any extension can be placed in this form to override the default behaviour. For example:

basicConstraints=critical,DER:00:01:02:03

HISTORY

X509v3 extension code was first added to OpenSSL 0.9.2.

CAVEATS

There is no guarantee that a specific implementation will process a given extension. It may therefore sometimes be possible to use certificates for purposes prohibited by their extensions because a specific application does not recognize or honour the values of the relevant extensions.

The DER and ASN1 options should be used with caution. It is possible to create totally invalid extensions if they are not used carefully.

If an extension is multi-value and a field value must contain a comma, the long form must be used. Otherwise the comma would be misinterpreted as a field separator. For example,

subjectAltName=URI:ldap://somehost.com/CN=foo,OU=bar

will produce an error, but the following form is valid:

subjectAltName=@subject_alt_section

[subject_alt_section]
subjectAltName=URI:ldap://somehost.com/CN=foo,OU=bar

Due to the behaviour of the OpenSSL CONF library, the same field name can only occur once in a section. That means that

subjectAltName=@alt_section

[alt_section]
email=steve@here
email=steve@there

will only use the last value. This can be worked around by using the form:

[alt_section]
email.1=steve@here
email.2=steve@there
