NOM

libcurl-tutorial - Tutoriel de programmation libcurl

Objectif

Ce document tente de décrire les principes généraux et quelques approches de base à considérer lors de la programmation avec libcurl. Le texte se concentre sur l'interface C mais devrait s'appliquer assez bien aux bindings dans d'autres langages, car ils suivent généralement l'API C de près.

Ce document désigne par « l'utilisateur » la personne qui écrit le code source utilisant libcurl. Ce pourrait être vous ou quelqu'un dans votre position. Ce qui est généralement appelé « le programme » est l'ensemble du code source que vous écrivez et qui utilise libcurl pour les transferts. Le programme est à l'extérieur de libcurl et libcurl est à l'extérieur du programme.

Pour plus de détails sur toutes les options et fonctions décrites ici, veuillez vous référer à leurs pages man respectives.

Compilation

Il existe de nombreuses façons de compiler des programmes C. Ce chapitre suppose un processus de compilation de style Unix. Si vous utilisez un système de construction différent, vous pouvez toujours lire ceci pour obtenir des informations générales qui peuvent également s'appliquer à votre environnement.

Compilation du Programme
Votre compilateur doit savoir où se trouvent les en-têtes de libcurl. Par conséquent, vous devez définir le chemin d'inclusion de votre compilateur pour pointer vers le répertoire où vous les avez installés. L'outil 'curl-config'[3] peut être utilisé pour obtenir ces informations : 
  $ curl-config --cflags
Liaison du Programme avec libcurl
Une fois le programme compilé, vous devez lier vos fichiers objet pour créer un seul exécutable. Pour que cela réussisse, vous devez lier avec libcurl et éventuellement aussi avec d'autres bibliothèques dont libcurl dépend elle-même. Comme les bibliothèques OpenSSL, mais même certaines bibliothèques système standard peuvent être nécessaires sur la ligne de commande. Pour déterminer les drapeaux à utiliser, une fois de plus, l'outil 'curl-config' vient à la rescousse : 
  $ curl-config --libs
SSL ou Pas
libcurl peut être compilé et personnalisé de nombreuses manières. L'une des choses qui varient entre différentes bibliothèques et compilations est la prise en charge des transferts basés sur SSL, tels que HTTPS et FTPS. Si une bibliothèque SSL prise en charge a été correctement détectée lors de la compilation, libcurl est compilé avec la prise en charge SSL. Pour savoir si une libcurl installée a été compilée avec la prise en charge SSL activée, utilisez curl-config comme suit : 
  $ curl-config --feature

Si SSL est pris en charge, le mot-clé SSL est écrit sur la sortie standard, éventuellement avec d'autres fonctionnalités qui peuvent être activées ou désactivées pour différentes libcurls.

Voir aussi « Fonctionnalités fournies par libcurl » plus loin.

Macro autoconf
Lorsque vous écrivez votre script de configuration pour détecter libcurl et configurer les variables en conséquence, nous proposons une macro qui fait probablement tout ce dont vous avez besoin dans ce domaine. Voir le fichier docs/libcurl/libcurl.m4 - il contient des informations sur son utilisation.

Code Portable dans un Monde Portable

Les personnes derrière libcurl ont déployé des efforts considérables pour faire fonctionner libcurl sur un grand nombre de systèmes d'exploitation et d'environnements différents.

Vous programmez libcurl de la même manière sur toutes les plateformes où libcurl fonctionne. Il n'y a que quelques détails mineurs qui diffèrent. Si vous vous assurez simplement d'écrire votre code de manière suffisamment portable, vous pouvez créer un programme portable. libcurl ne devrait pas vous en empêcher.

Préparation Globale

Le programme doit initialiser une partie de la fonctionnalité de libcurl globalement. Cela signifie que cela doit être fait exactement une fois, peu importe combien de fois vous avez l'intention d'utiliser la bibliothèque. Une fois pour toute la durée de vie de votre programme. Ceci est fait en utilisant

 curl_global_init()

et cela prend un paramètre qui est un masque de bits indiquant à libcurl quoi initialiser. L'utilisation de CURL_GLOBAL_ALL lui fait initialiser tous les sous-modules internes connus, et peut être une bonne option par défaut. Les deux bits actuellement spécifiés sont :

CURL_GLOBAL_WIN32
qui ne fait quelque chose que sur les machines Windows. Lorsqu'il est utilisé sur une machine Windows, il fait initialiser par libcurl les éléments des sockets Win32. Sans avoir correctement initialisé cela, votre programme ne peut pas utiliser correctement les sockets. Vous ne devriez le faire qu'une fois par application, donc si votre programme le fait déjà ou si une autre bibliothèque utilisée le fait, vous ne devriez pas non plus demander à libcurl de le faire.
CURL_GLOBAL_SSL
qui ne fait quelque chose que sur les libcurls compilées et construites avec SSL activé. Sur ces systèmes, cela fait initialiser correctement par libcurl la bibliothèque SSL pour cette application. Cela ne doit être fait qu'une fois par application, donc si votre programme ou une autre bibliothèque le fait déjà, ce bit ne devrait pas être nécessaire.

libcurl possède un mécanisme de protection par défaut qui détecte si curl_global_init(3) n'a pas été appelée au moment où curl_easy_perform(3) est appelée et si tel est le cas, libcurl exécute la fonction elle-même avec un masque de bits deviné. Veuillez noter que ne pas dépendre uniquement de cela n'est ni agréable ni bon.

Lorsque le programme n'utilise plus libcurl, il doit appeler curl_global_cleanup(3), qui est l'inverse de l'appel d'initialisation. Il effectue les opérations inversées pour nettoyer les ressources que l'appel curl_global_init(3) a initialisées.

Les appels répétés à curl_global_init(3) et curl_global_cleanup(3) doivent être évités. Ils ne doivent être appelés qu'une seule fois chacun.

Fonctionnalités fournies par libcurl

Il est considéré comme une bonne pratique de déterminer les fonctionnalités de libcurl au moment de l'exécution plutôt qu'au moment de la compilation (si possible, bien sûr). En appelant curl_version_info(3) et en examinant les détails de la structure renvoyée, votre programme peut déterminer exactement ce que prend en charge la libcurl actuellement en cours d'exécution.

Deux Interfaces

libcurl a d'abord introduit l'interface dite facile (easy). Toutes les opérations de l'interface facile sont préfixées par 'curl_easy'. L'interface facile vous permet d'effectuer des transferts simples avec un appel de fonction synchrone et bloquant.

libcurl propose également une autre interface qui permet des transferts simultanés multiples dans un seul thread, l'interface dite multi. Plus d'informations sur cette interface sont détaillées dans un chapitre séparé plus loin. Vous devez toujours d'abord comprendre l'interface facile, alors continuez à lire pour mieux comprendre.

Gérer l Interface Facile libcurl

Pour utiliser l'interface facile, vous devez d'abord créer votre propre handle facile. Vous avez besoin d'un handle pour chaque session facile que vous souhaitez effectuer. Fondamentalement, vous devriez utiliser un handle pour chaque thread que vous prévoyez d'utiliser pour le transfert. Vous ne devez jamais partager le même handle dans plusieurs threads.

Obtenez un handle facile avec

 handle = curl_easy_init();
Cela renvoie un handle facile. Avec cela, vous passez à l'étape suivante : la configuration de vos actions préférées. Un handle est juste une entité logique pour le transfert à venir ou la série de transferts.

Vous définissez les propriétés et les options pour ce handle en utilisant curl_easy_setopt(3). Elles contrôlent comment le transfert ou les transferts ultérieurs utilisant ce handle sont effectués. Les options restent définies dans le handle jusqu'à ce qu'elles soient à nouveau définies sur quelque chose de différent. Elles sont persistantes. Plusieurs requêtes utilisant le même handle utilisent les mêmes options.

Si à tout moment vous souhaitez effacer toutes les options précédemment définies pour un seul handle facile, vous pouvez appeler curl_easy_reset(3) et vous pouvez également cloner un handle facile (avec toutes ses options définies) en utilisant curl_easy_duphandle(3).

L'une des propriétés les plus élémentaires à définir dans le handle est l'URL. Vous définissez votre URL préférée à transférer avec CURLOPT_URL(3) d'une manière similaire à :

 curl_easy_setopt(handle, CURLOPT_URL, "http://example.com/");

Supposons un instant que vous souhaitiez recevoir des données puisque l'URL identifie une ressource distante que vous souhaitez obtenir ici. Puisque vous écrivez une sorte d'application qui a besoin de ce transfert, je suppose que vous aimeriez que les données vous soient transmises directement au lieu de simplement les envoyer à stdout. Vous écrivez donc votre propre fonction qui correspond à ce prototype :

 size_t write_data(void *buffer, size_t size, size_t nmemb, void *userp);
Vous indiquez à libcurl de passer toutes les données à cette fonction en émettant une fonction similaire à celle-ci : 
 curl_easy_setopt(handle, CURLOPT_WRITEFUNCTION, write_data);
Vous pouvez contrôler quelles données votre fonction de rappel reçoit dans le quatrième argument en définissant une autre propriété : 
 curl_easy_setopt(handle, CURLOPT_WRITEDATA, &internal_struct);
En utilisant cette propriété, vous pouvez facilement passer des données locales entre votre application et la fonction qui est appelée par libcurl. libcurl lui-même ne touche pas aux données que vous passez avec CURLOPT_WRITEDATA(3).

libcurl offre son propre rappel interne par défaut qui s'occupe des données si vous ne définissez pas le rappel avec CURLOPT_WRITEFUNCTION(3). Il affiche simplement les données reçues sur stdout. Vous pouvez faire en sorte que le rappel par défaut écrive les données dans un fichier différent en passant un 'FILE *' vers un fichier ouvert en écriture avec l'option CURLOPT_WRITEDATA(3).

Maintenant, nous devons prendre du recul et prendre une profonde respiration. Voici une de ces rares spécificités dépendantes de la plateforme. L'avez-vous repérée ? Sur certaines plateformes[2], libcurl n'est pas capable d'opérer sur des descripteurs de fichiers ouverts par le programme. Par conséquent, si vous utilisez le rappel par défaut et passez un descripteur de fichier ouvert avec CURLOPT_WRITEDATA(3), libcurl plante. Vous devriez éviter cela pour que votre programme fonctionne correctement pratiquement partout.

(CURLOPT_WRITEDATA(3) était anciennement connu sous le nom de CURLOPT_FILE. Les deux noms fonctionnent toujours et font la même chose).

Si vous utilisez libcurl en tant que DLL Windows, vous DEVEZ utiliser CURLOPT_WRITEFUNCTION(3) si vous définissez CURLOPT_WRITEDATA(3) - sinon vous rencontrerez des plantages.

Il existe bien sûr de nombreuses autres options que vous pouvez définir, et nous y reviendrons plus tard. Continuons plutôt vers le transfert réel :

 success = curl_easy_perform(handle);

curl_easy_perform(3) se connecte au site distant, effectue les commandes nécessaires et effectue le transfert. Chaque fois qu'il reçoit des données, il appelle la fonction de rappel que nous avons définie précédemment. La fonction peut recevoir un octet à la fois, ou elle peut recevoir plusieurs kilo-octets à la fois. libcurl délivre autant que possible aussi souvent que possible. Votre fonction de rappel doit retourner le nombre d'octets dont elle s'est « occupée ». Si ce n'est pas le même nombre d'octets qui lui a été passé, libcurl abandonne l'opération et retourne un code d'erreur.

Lorsque le transfert est terminé, la fonction retourne un code de retour qui vous informe si elle a réussi sa mission ou non. Si un code de retour ne vous suffit pas, vous pouvez utiliser CURLOPT_ERRORBUFFER(3) pour pointer libcurl vers un tampon de votre part où il stocke également un message d'erreur lisible par l'homme.

Si vous souhaitez ensuite transférer un autre fichier, le handle est prêt à être réutilisé. Il est même préférable et encouragé de réutiliser un handle existant si vous avez l'intention de faire un autre transfert. libcurl tente alors de réutiliser une connexion précédente.

Pour certains protocoles, le téléchargement d'un fichier peut impliquer un processus compliqué de connexion, de définition du mode de transfert, de changement de répertoire courant et enfin de transfert des données du fichier. libcurl prend en charge toute cette complexité pour vous. Étant simplement donnée l'URL d'un fichier, libcurl s'occupe de tous les détails nécessaires pour déplacer le fichier d'une machine à une autre.

Problèmes de Multi-threading

libcurl est thread-safe mais il y a quelques exceptions. Référez-vous à libcurl-thread(3) pour plus d'informations.

Lorsque ça ne fonctionne pas

Il arrive que le transfert échoue pour une raison quelconque. Vous pourriez avoir défini la mauvaise option libcurl ou mal compris ce que fait réellement l'option libcurl, ou le serveur distant pourrait renvoyer des réponses non standard qui confondent la bibliothèque, qui confond alors votre programme.

Il y a une règle d'or lorsque ces choses se produisent : définissez l'option CURLOPT_VERBOSE(3) à 1. cela amène la bibliothèque à afficher tous les détails du protocole qu'elle envoie, des informations internes et des données de protocole reçues également (surtout lors de l'utilisation de FTP). Si vous utilisez HTTP, ajouter les en-têtes dans la sortie reçue à étudier est également un moyen intelligent de mieux comprendre pourquoi le serveur se comporte comme il le fait. Incluez les en-têtes dans la sortie du corps normale avec CURLOPT_HEADER(3) défini à 1.

Bien sûr, il reste des bugs. Nous avons besoin de les connaître pour pouvoir les corriger, nous dépendons donc fortement de vos rapports de bugs. Lorsque vous signalez des bugs suspects dans libcurl, veuillez inclure autant de détails que possible : un vidage de protocole que produit CURLOPT_VERBOSE(3), la version de la bibliothèque, autant de votre code que possible qui utilise libcurl, le nom et la version du système d'exploitation, le nom et la version du compilateur, etc.

Si CURLOPT_VERBOSE(3) ne suffit pas, vous augmentez le niveau des données de débogage que votre application reçoit en utilisant CURLOPT_DEBUGFUNCTION(3).

Acquérir des connaissances approfondies sur les protocoles impliqués n'est jamais une mauvaise chose, et si vous essayez de faire des choses amusantes, vous pourriez mieux comprendre libcurl et comment l'utiliser si vous étudiez les documents RFC appropriés au moins brièvement.

Charger des données sur un site distant

libcurl essaie de garder une approche indépendante du protocole pour la plupart des transferts, ainsi le chargement vers un site FTP distant est similaire au chargement de données vers un serveur HTTP avec une requête PUT.

Bien sûr, vous créez d'abord un handle easy ou vous réutilisez un handle existant. Ensuite, vous définissez l'URL sur laquelle opérer, comme auparavant. C'est l'URL distante, sur laquelle nous chargeons maintenant.

Puisque nous écrivons une application, nous voulons très probablement que libcurl obtienne les données de chargement en nous les demandant. Pour y parvenir, nous définissons le rappel de lecture et le pointeur personnalisé que libcurl passe à notre rappel de lecture. Le rappel de lecture doit avoir un prototype similaire à :

 size_t function(char *bufptr, size_t size, size_t nitems, void *userp);
Où bufptr est le pointeur vers un tampon que nous remplissons avec les données à charger et nitems est la taille du tampon et donc la quantité maximale de données que nous pouvons retourner à libcurl dans cet appel. Le pointeur userp est le pointeur personnalisé que nous définissons pour pointer vers une structure de notre part afin de passer des données privées entre l'application et le rappel. 
 curl_easy_setopt(handle, CURLOPT_READFUNCTION, read_function);
 curl_easy_setopt(handle, CURLOPT_READDATA, &filedata);
Indiquez à libcurl que nous voulons charger : 
 curl_easy_setopt(handle, CURLOPT_UPLOAD, 1L);

Certains protocoles ne se comportent pas correctement lorsque les chargements sont effectués sans connaissance préalable de la taille de fichier attendue. Définissez donc la taille du fichier de chargement en utilisant CURLOPT_INFILESIZE_LARGE(3) pour toutes les tailles de fichiers connues comme suit[1] :

 /* dans cet exemple, file_size doit être une variable de type curl_off_t */
 curl_easy_setopt(handle, CURLOPT_INFILESIZE_LARGE, file_size);

Lorsque vous appelez curl_easy_perform(3) cette fois-ci, il effectue toutes les opérations nécessaires et, lorsqu'il a déclenché le chargement, il appelle votre rappel fourni pour obtenir les données à charger. Le programme doit retourner autant de données que possible à chaque appel, car cela rendra probablement le chargement aussi rapide que possible. Le rappel doit retourner le nombre d'octets écrits dans le tampon. Retourner 0 signale la fin du chargement.

Mots de passe

De nombreux protocoles utilisent ou exigent même que le nom d'utilisateur et le mot de passe soient fournis pour pouvoir télécharger ou charger les données de votre choix. libcurl offre plusieurs façons de les spécifier.

La plupart des protocoles permettent de spécifier le nom et le mot de passe dans l'URL elle-même. libcurl le détecte et les utilise en conséquence. Cela s'écrit comme suit :

 protocol://user:password@example.com/path/
Si vous avez besoin de caractères inhabituels dans votre nom d'utilisateur ou mot de passe, vous devez les encoder en URL, sous la forme %XX où XX est un nombre hexadécimal à deux chiffres.

libcurl fournit également des options pour définir divers mots de passe. Le nom d'utilisateur et le mot de passe tels qu'ils apparaissent intégrés dans l'URL peuvent être définis à la place avec l'option CURLOPT_USERPWD(3). L'argument passé à libcurl doit être un char * vers une chaîne au format "user:password". D'une manière comme celle-ci :

 curl_easy_setopt(handle, CURLOPT_USERPWD, "myname:thesecret");

Un autre cas où un nom et un mot de passe peuvent être nécessaires à certains moments est pour les utilisateurs qui doivent s'authentifier auprès d'un proxy qu'ils utilisent. libcurl offre une autre option pour cela, CURLOPT_PROXYUSERPWD(3). Elle est utilisée de manière assez similaire à l'option CURLOPT_USERPWD(3) comme ceci :

 curl_easy_setopt(handle, CURLOPT_PROXYUSERPWD, "myname:thesecret");

Il existe une ancienne méthode Unix « standard » pour stocker les noms d'utilisateur et mots de passe FTP, à savoir dans le fichier $HOME/.netrc (sous Windows, libcurl vérifie également la variable d'environnement %USERPROFILE% si %HOME% n'est pas définie, et essaie "_netrc" comme nom). Le fichier doit être rendu privé afin que seul l'utilisateur puisse le lire (voir également le chapitre « Considérations de sécurité »), car il pourrait contenir le mot de passe en texte brut. libcurl a la capacité d'utiliser ce fichier pour déterminer quel ensemble de nom d'utilisateur et de mot de passe utiliser pour un hôte particulier. En tant qu'extension à la fonction normale

nalité, libcurl supporte également ce fichier pour les protocoles non-FTP comme HTTP. Pour faire en sorte que curl utilise ce fichier, utilisez l'option CURLOPT_NETRC(3) :

 curl_easy_setopt(handle, CURLOPT_NETRC, 1L);

Un exemple basique de ce à quoi un fichier .netrc peut ressembler :

 machine monhost.mondomaine.com
 login monlogin
 password monmotdepasse

Tous ces exemples concernent des cas où le mot de passe est facultatif, ou du moins où vous pouvez le laisser de côté et laisser libcurl tenter de faire son travail sans lui. Il y a des moments où le mot de passe n'est pas facultatif, comme lorsque vous utilisez une clé privée SSL pour des transferts sécurisés.

Pour passer le mot de passe de clé privée connu à libcurl :

 curl_easy_setopt(handle, CURLOPT_KEYPASSWD, "motdepassecle");

Authentification HTTP

Le chapitre précédent a montré comment définir le nom d'utilisateur et le mot de passe pour obtenir des URLs nécessitant une authentification. Lors de l'utilisation du protocole HTTP, il existe de nombreuses manières différentes pour un client de fournir ces informations d'identification au serveur, et vous pouvez contrôler la manière dont libcurl les utilise. La méthode d'authentification HTTP par défaut est appelée 'Basic', qui consiste à envoyer le nom et le mot de passe en texte clair dans la requête HTTP, encodés en base64. C'est non sécurisé.

Au moment de la rédaction, libcurl peut être compilé pour utiliser : Basic, Digest, NTLM, Negotiate (SPNEGO). Vous pouvez indiquer à libcurl lequel utiliser avec CURLOPT_HTTPAUTH(3) comme suit :

 curl_easy_setopt(handle, CURLOPT_HTTPAUTH, CURLAUTH_DIGEST);

Lorsque vous envoyez une authentification à un proxy, vous pouvez également définir le type d'authentification de la même manière mais avec CURLOPT_PROXYAUTH(3) :

 curl_easy_setopt(handle, CURLOPT_PROXYAUTH, CURLAUTH_NTLM);

Ces deux options vous permettent de définir plusieurs types (en les combinant avec un OU logique), pour que libcurl choisisse le plus sécurisé parmi les types que le serveur/proxy prétend supporter. Cette méthode implique cependant un aller-retour supplémentaire car libcurl doit d'abord demander au serveur ce qu'il supporte :

 curl_easy_setopt(handle, CURLOPT_HTTPAUTH, CURLAUTH_DIGEST|CURLAUTH_BASIC);

Pour plus de commodité, vous pouvez utiliser la définition CURLAUTH_ANY (au lieu d'une liste de types spécifiques) qui permet à libcurl d'utiliser la méthode qu'il souhaite.

Lorsqu'il demande plusieurs types, libcurl choisit celui qui est disponible et qu'il considère comme le "meilleur" selon son propre ordre de préférence interne.

Envoi de requêtes POST HTTP

Nous recevons de nombreuses questions sur la manière d'effectuer des requêtes POST HTTP avec libcurl de la bonne manière. Ce chapitre comprend donc des exemples utilisant les différentes versions de requêtes POST HTTP que libcurl supporte.

La première version est le POST simple, la version la plus courante, utilisée par la plupart des pages HTML utilisant la balise <form>. Nous fournissons un pointeur vers les données et indiquons à libcurl de tout poster sur le site distant :

    char *data="nom=daniel&projet=curl";
    curl_easy_setopt(handle, CURLOPT_POSTFIELDS, data);
    curl_easy_setopt(handle, CURLOPT_URL, "http://postici.com/");
    curl_easy_perform(handle); /* envoi ! */

Assez simple, n'est-ce pas ? Étant donné que vous définissez les options POST avec CURLOPT_POSTFIELDS(3), cela bascule automatiquement le handle pour utiliser POST dans la requête à venir.

Et si vous voulez poster des données binaires qui nécessitent également de définir l'en-tête Content-Type: du POST ? Eh bien, les POST binaires empêchent libcurl de pouvoir faire strlen() sur les données pour déterminer la taille. Par conséquent, nous devons indiquer à libcurl la taille des données postées. La définition des en-têtes dans les requêtes libcurl se fait de manière générique, en construisant une liste de nos propres en-têtes puis en passant cette liste à libcurl.

 struct curl_slist *headers=NULL;
 headers = curl_slist_append(headers, "Content-Type: text/xml");
 /* poster des données binaires */
 curl_easy_setopt(handle, CURLOPT_POSTFIELDS, pointeur_binaire);
 /* définir la taille des données postées */
 curl_easy_setopt(handle, CURLOPT_POSTFIELDSIZE, 23L);
 /* passer notre liste d'en-têtes personnalisés */
 curl_easy_setopt(handle, CURLOPT_HTTPHEADER, headers);
 curl_easy_perform(handle); /* envoi ! */
 curl_slist_free_all(headers); /* libérer la liste d'en-têtes */

Bien que les exemples simples ci-dessus couvrent la majorité des cas où des opérations POST HTTP sont nécessaires, ils ne gèrent pas les formposts multipart. Les formposts multipart ont été introduits comme une meilleure façon de poster des données (potentiellement volumineuses) binaires et ont été documentés pour la première fois dans la RFC 1867 (mise à jour dans la RFC 2388). Ils sont appelés multipart car ils sont construits par une chaîne de parties, chaque partie étant une unité de données unique. Chaque partie a son propre nom et contenu. Vous pouvez en fait créer et poster un formpost multipart avec le support POST régulier de libcurl décrit ci-dessus, mais cela exigerait que vous construisiez vous-même un formpost et que vous le fournissiez à libcurl.

Pour faciliter cela, libcurl fournit une API MIME composée de plusieurs fonctions : en les utilisant, vous pouvez créer et remplir un corps multipart. La fonction curl_mime_init(3) crée un corps multipart ; vous pouvez ensuite ajouter de nouvelles parties à un corps multipart en utilisant curl_mime_addpart(3).

Il existe trois sources de données possibles pour une partie : la mémoire à l'aide de curl_mime_data(3), un fichier à l'aide de curl_mime_filedata(3) et des données définies par l'utilisateur lues par une fonction de rappel à l'aide de curl_mime_data_cb(3). curl_mime_name(3) définit le nom d'une partie (c'est-à-dire le champ de formulaire), tandis que curl_mime_filename(3) remplit le nom de fichier distant. Avec curl_mime_type(3), vous pouvez indiquer le type MIME d'une partie, curl_mime_headers(3) permet de définir les en-têtes de la partie. Lorsqu'un corps multipart n'est plus nécessaire, vous pouvez le détruire en utilisant curl_mime_free(3).

L'exemple suivant définit deux parties textuelles simples avec un contenu textuel brut, puis un fichier avec un contenu binaire et télécharge le tout.

 curl_mime *multipart = curl_mime_init(handle);
 curl_mimepart *part = curl_mime_addpart(multipart);
 curl_mime_name(part, "nom");
 curl_mime_data(part, "daniel", CURL_ZERO_TERMINATED);
 part = curl_mime_addpart(multipart);
 curl_mime_name(part, "projet");
 curl_mime_data(part, "curl", CURL_ZERO_TERMINATED);
 part = curl_mime_addpart(multipart);
 curl_mime_name(part, "logotype-image");
 curl_mime_filedata(part, "curl.png");
 /* Définir les informations du formulaire */
 curl_easy_setopt(handle, CURLOPT_MIMEPOST, multipart);
 curl_easy_perform(handle); /* envoi ! */
 /* libérer à nouveau les données postées */
 curl_mime_free(multipart);

Pour poster plusieurs fichiers pour un seul champ de formulaire, vous devez fournir chaque fichier dans une partie séparée, toutes avec le même nom de champ. Bien que la fonction curl_mime_subparts(3) implémente des multipart imbriqués, cette manière de poster plusieurs fichiers est dépréciée par la RFC 7578, section 4.3.

Pour définir la source de données à partir d'un pointeur FILE déjà ouvert, utilisez :

 curl_mime_data_cb(part, taille_fichier, (curl_read_callback) fread,
                   (curl_seek_callback) fseek, NULL, pointeur_fichier);

Une fonction dépréciée curl_formadd(3) est toujours prise en charge dans libcurl. Elle ne devrait cependant plus être utilisée pour de nouvelles conceptions et les programmes qui l'utilisent devraient être convertis à l'API MIME. Elle est cependant décrite ici comme une aide à la conversion.

En utilisant curl_formadd, vous ajoutez des parties au formulaire. Lorsque vous avez terminé d'ajouter des parties, vous postez l'ensemble du formulaire.

L'exemple de l'API MIME ci-dessus est exprimé comme suit en utilisant cette fonction :

 struct curl_httppost *post=NULL;
 struct curl_httppost *last=NULL;
 curl_formadd(&post, &last,
              CURLFORM_COPYNAME, "nom",
              CURLFORM_COPYCONTENTS, "daniel", CURLFORM_END);
 curl_formadd(&post, &last,
              CURLFORM_COPYNAME, "projet",
              CURLFORM_COPYCONTENTS, "curl", CURLFORM_END);
 curl_formadd(&post, &last,
              CURLFORM_COPYNAME, "logotype-image",
              CURLFORM_FILECONTENT, "curl.png", CURLFORM_END);
 /* Définir les informations du formulaire */
 curl_easy_setopt(handle, CURLOPT_HTTPPOST, post);
 curl_easy_perform(handle); /* envoi ! */
 /* libérer à nouveau les données postées */
 curl_formfree(post);

Les formposts multipart sont des chaînes de parties utilisant des séparateurs et des en-têtes de style MIME. Cela signifie que chacune de ces parties séparées reçoit quelques en-têtes qui décrivent le type de contenu, la taille, etc. individuels. Pour permettre à votre application de gérer ce formpost encore plus finement, libcurl vous permet de fournir votre propre ensemble d'en-têtes personnalisés à une partie de formulaire individuelle. Vous pouvez bien sûr fournir des en-têtes à autant de parties que vous le souhaitez, mais ce petit exemple montre comment définir des en-têtes à une partie spécifique lorsque vous l'ajoutez au handle de post :

 struct curl_slist *headers=NULL;
 headers = curl_slist_append(headers, "Content-Type: text/xml");
 curl_formadd(&post, &last,
              CURLFORM_COPYNAME, "logotype-image",
              CURLFORM_FILECONTENT, "curl.xml",
              CURLFORM_CONTENTHEADER, headers,
              CURLFORM_END);
 curl_easy_perform(handle); /* envoi ! */
 curl_formfree(post); /* libérer le post */
 curl_slist_free_all(headers); /* libérer la liste d'en-têtes personnalisés */

Étant donné que toutes les options d'un handle easy sont "collantes", elles restent les mêmes jusqu'à ce qu'elles soient modifiées, même si vous appelez curl_easy_perform(3). Vous pourriez avoir besoin d'indiquer à curl de revenir à une requête GET simple si vous avez l'intention d'en faire une comme prochaine requête. Vous forcez un handle easy à revenir à GET en utilisant l'option CURLOPT_HTTPGET(3) :

 curl_easy_setopt(handle, CURLOPT_HTTPGET, 1L);
Le simple fait de définir CURLOPT_POSTFIELDS(3) sur "" ou NULL n'empêche pas libcurl d'effectuer un POST. Cela fait simplement un POST sans aucune donnée à envoyer !

Conversion de l'API de formulaire dépréciée vers l'API MIME

Quatre règles doivent être respectées lors de la construction du multipart :

- Le handle easy doit être créé avant la construction du multipart.

- Le multipart est toujours créé par un appel à curl_mime_init(handle).

- Chaque partie est créée par un appel à curl_mime_addpart(multipart).

- Une fois terminé, le multipart doit être lié au handle easy en utilisant CURLOPT_MIMEPOST(3) au lieu de CURLOPT_HTTPPOST(3).

Comportements des formulaires dépréciés

Les exemples suivants montrent comment les appels à curl_formadd(3) ont été traduits en opérations de mime.

 curl_formadd(&post, &last,
              CURLFORM_COPYNAME, "id",
              CURLFORM_COPYCONTENTS, "daniel", CURLFORM_END);
              CURLFORM_CONTENTHEADER, headers,
              CURLFORM_END);

devient:

 part = curl_mime_addpart(multipart);
 curl_mime_name(part, "id");
 curl_mime_data(part, "daniel", CURL_ZERO_TERMINATED);
 curl_mime_headers(part, headers, FALSE);

Le réglage du dernier argument de curl_mime_headers(3) à TRUE aurait entraîné la libération automatique des en-têtes lors de la destruction du multipart, économisant ainsi un appel de nettoyage à curl_slist_free_all(3).

 curl_formadd(&post, &last,
              CURLFORM_PTRNAME, "logotype-image",
              CURLFORM_FILECONTENT, "-",
              CURLFORM_END);

devient:

 part = curl_mime_addpart(multipart);
 curl_mime_name(part, "logotype-image");
 curl_mime_data_cb(part, (curl_off_t) -1, fread, fseek, NULL, stdin);

curl_mime_name(3) copie toujours le nom du champ. Le nom de fichier spécial "-" n'est pas pris en charge par curl_mime_filename(3): pour lire un fichier ouvert, utilisez une source de rappel avec fread(). Le transfert sera encodé par morceaux car la taille des données est inconnue.

 curl_formadd(&post, &last,
              CURLFORM_COPYNAME, "datafile[]",
              CURLFORM_FILE, "file1",
              CURLFORM_FILE, "file2",
              CURLFORM_END);

devient:

 part = curl_mime_addpart(multipart);
 curl_mime_name(part, "datafile[]");
 curl_mime_filedata(part, "file1");
 part = curl_mime_addpart(multipart);
 curl_mime_name(part, "datafile[]");
 curl_mime_filedata(part, "file2");

L'implémentation dépréciée de multipart/mixed pour le champ de fichiers multiples est traduite en deux parties distinctes portant le même nom.

 curl_easy_setopt(handle, CURLOPT_READFUNCTION, myreadfunc);
 curl_formadd(&post, &last,
              CURLFORM_COPYNAME, "stream",
              CURLFORM_STREAM, arg,
              CURLFORM_CONTENTLEN, (curl_off_t) datasize,
              CURLFORM_FILENAME, "archive.zip",
              CURLFORM_CONTENTTYPE, "application/zip",
              CURLFORM_END);

devient:

 part = curl_mime_addpart(multipart);
 curl_mime_name(part, "stream");
 curl_mime_data_cb(part, (curl_off_t) datasize,
                   myreadfunc, NULL, NULL, arg);
 curl_mime_filename(part, "archive.zip");
 curl_mime_type(part, "application/zip");

Le rappel CURLOPT_READFUNCTION(3) n'est pas utilisé: il est remplacé en définissant directement la source des données de la partie à partir de la fonction de lecture du rappel.

 curl_formadd(&post, &last,
              CURLFORM_COPYNAME, "memfile",
              CURLFORM_BUFFER, "memfile.bin",
              CURLFORM_BUFFERPTR, databuffer,
              CURLFORM_BUFFERLENGTH, (long) sizeof databuffer,
              CURLFORM_END);

devient:

 part = curl_mime_addpart(multipart);
 curl_mime_name(part, "memfile");
 curl_mime_data(part, databuffer, (curl_off_t) sizeof databuffer);
 curl_mime_filename(part, "memfile.bin");

curl_mime_data(3) copie toujours les données initiales: le tampon de données est donc libre pour une réutilisation immédiate.

 curl_formadd(&post, &last,
              CURLFORM_COPYNAME, "message",
              CURLFORM_FILECONTENT, "msg.txt",
              CURLFORM_END);

devient:

 part = curl_mime_addpart(multipart);
 curl_mime_name(part, "message");
 curl_mime_filedata(part, "msg.txt");
 curl_mime_filename(part, NULL);

L'utilisation de curl_mime_filedata(3) définit le nom de fichier distant comme effet secondaire: il est donc nécessaire de le vider pour l'émulation de *CURLFORM_FILECONTENT*.

Affichage de la progression

Pour des raisons historiques et traditionnelles, libcurl possède un compteur de progression intégré qui peut être activé et qui présente alors un compteur de progression dans votre terminal.

Activez le compteur de progression en réglant, de manière assez étonnante, CURLOPT_NOPROGRESS(3) à zéro. Cette option est réglée à 1 par défaut.

Pour la plupart des applications cependant, le compteur de progression intégré est inutile et ce qui est intéressant à la place est la possibilité de spécifier une fonction de rappel de progression. Le pointeur de fonction que vous passez à libcurl est alors appelé à des intervalles irréguliers avec des informations sur le transfert en cours.

Définissez la fonction de rappel de progression en utilisant CURLOPT_PROGRESSFUNCTION(3). Passez un pointeur vers une fonction qui correspond à ce prototype :

 int progress_callback(void *clientp,
                       double dltotal,
                       double dlnow,
                       double ultotal,
                       double ulnow);

Si l'un des arguments d'entrée est inconnu, une valeur 0 est fournie. Le premier argument, 'clientp', est le pointeur que vous passez à libcurl avec CURLOPT_PROGRESSDATA(3). libcurl ne le touche pas.

Proxys

Ce que "proxy" signifie selon Merriam-Webster : "une personne autorisée à agir pour une autre" mais aussi "l'agence, la fonction ou le bureau d'un député qui agit comme substitut pour une autre".

Les proxys sont extrêmement courants de nos jours. Les entreprises n'offrent souvent un accès Internet aux employés que par leurs proxys. Les clients réseau ou les agents utilisateurs demandent des documents au proxy, le proxy effectue la requête réelle puis les renvoie.

libcurl prend en charge les proxys SOCKS et HTTP. Lorsqu'une URL donnée est demandée, libcurl la demande au proxy au lieu d'essayer de se connecter à l'hôte distant réel identifié dans l'URL.

Si vous utilisez un proxy SOCKS, vous constaterez peut-être que libcurl ne prend pas entièrement en charge toutes les opérations à travers lui.

Pour les proxys HTTP : le fait que le proxy soit un proxy HTTP impose certaines restrictions sur ce qui peut réellement se passer. Une URL demandée qui n'est peut-être pas une URL HTTP est transmise au proxy HTTP pour être renvoyée à libcurl. Cela se fait de manière transparente, et une application peut ne pas avoir besoin de le savoir. Je dis "peut", car parfois il est important de comprendre que toutes les opérations via un proxy HTTP utilisent le protocole HTTP. Par exemple, vous ne pouvez pas invoquer vos propres commandes FTP personnalisées ni même des listages de répertoires FTP appropriés.

Options de proxy
Pour indiquer à libcurl d'utiliser un proxy à un numéro de port donné : 
 curl_easy_setopt(handle, CURLOPT_PROXY, "proxy-host.com:8080");
Certains proxys nécessitent une authentification utilisateur avant d'autoriser une requête, et vous passez ces informations de manière similaire : 
 curl_easy_setopt(handle, CURLOPT_PROXYUSERPWD, "user:password");
Si vous le souhaitez, vous pouvez spécifier uniquement le nom d'hôte dans l'option CURLOPT_PROXY(3), et définir le numéro de port séparément avec CURLOPT_PROXYPORT(3).

Indiquez à libcurl de quel type de proxy il s'agit avec CURLOPT_PROXYTYPE(3) (sinon, il suppose par défaut un proxy HTTP) :

 curl_easy_setopt(handle, CURLOPT_PROXYTYPE, CURLPROXY_SOCKS4);
Variables d'environnement
libcurl vérifie et utilise automatiquement un ensemble de variables d'environnement pour savoir quels proxys utiliser pour certains protocoles. Les noms des variables suivent une vieille tradition et sont construits comme "[protocole]_proxy" (notez la casse minuscule). Cela fait que la variable 'http_proxy' est vérifiée pour le nom d'un proxy à utiliser lorsque l'URL d'entrée est HTTP. Suivant la même règle, la variable nommée 'ftp_proxy' est vérifiée pour les URL FTP. Encore une fois, les proxys sont toujours des proxys HTTP, les noms différents des variables permettent simplement d'utiliser différents proxys HTTP.

Le contenu de la variable d'environnement proxy doit être au format "[protocole://][utilisateur:motdepasse@]machine[:port]". Où la partie protocole:// spécifie le type de proxy et le numéro de port optionnel spécifie sur quel port le proxy opère. Si non spécifié, le numéro de port par défaut interne est utilisé et ce n'est très probablement pas celui que vous voudriez.

Il existe deux variables d'environnement spéciales. 'all_proxy' définit le proxy pour n'importe quelle URL au cas où la variable spécifique au protocole n'aurait pas été définie, et 'no_proxy' définit une liste d'hôtes qui ne devraient pas utiliser de proxy même si une variable l'indique. Si 'no_proxy' est un simple astérisque ("*"), il correspond à tous les hôtes.

Pour désactiver explicitement la vérification par libcurl des variables d'environnement proxy et leur utilisation, définissez le nom du proxy à "" - une chaîne vide - avec CURLOPT_PROXY(3).

SSL et Proxys
SSL concerne les connexions point à point sécurisées. Cela implique un cryptage solide et des choses similaires, ce qui rend en fait impossible pour un proxy d'opérer comme un "homme du milieu" dont c'est la tâche, comme discuté précédemment. Au lieu de cela, la seule façon pour que le SSL fonctionne sur un proxy HTTP est de demander au proxy de tout faire passer sans pouvoir vérifier ou manipuler le trafic.

L'ouverture d'une connexion SSL sur un proxy HTTP est donc une question de demander au proxy une connexion directe à l'hôte cible sur un port spécifié. Cela se fait avec la requête HTTP CONNECT. ("veuillez cher proxy, connectez-moi à cet hôte distant").

En raison de la nature de cette opération, où le proxy n'a aucune idée du type de données qui transite par ce tunnel, cela brise certains des rares avantages qui découlent de l'utilisation d'un proxy, tels que la mise en cache. De nombreuses organisations empêchent ce type de tunneling vers des numéros de port de destination autres que 443 (qui est le numéro de port HTTPS par défaut).

Tunnelisation
Dans le contexte des proxys HTTP, la tunnelisation est utilisée pour les protocoles qui ne sont pas HTTP (ou HTTPS). L'une des utilisations les plus courantes est pour les connexions SSL/TLS vers une destination différente de celle du proxy HTTP.

Lorsque vous demandez une connexion SSL via un proxy HTTP, libcurl envoie une requête HTTP `CONNECT` au proxy. Cette requête demande au proxy de créer un tunnel TCP direct entre lui et le serveur de destination sur le port spécifié. Une fois le tunnel établi, libcurl et le serveur de destination communiquent directement à travers ce tunnel, le proxy ne voyant que les données chiffrées sans pouvoir les inspecter.

Cela est particulièrement important pour HTTPS, où le trafic est chiffré de bout en bout. Le proxy HTTP ne peut pas déchiffrer le trafic SSL/TLS. Par conséquent, la seule façon pour lui de gérer une demande HTTPS est de fournir un tunnel.

Notez que certains pare-feu ou proxys peuvent bloquer ou restreindre les requêtes `CONNECT` vers des ports autres que le port HTTPS standard (443) pour des raisons de sécurité.

="#Tunneling">Tunnelage
Comme expliqué ci-dessus, le tunneling est nécessaire pour que le SSL fonctionne et est souvent même restreint à l'opération prévue pour le SSL ; HTTPS.

Ce n'est cependant pas la seule fois où le tunneling proxy peut vous offrir des avantages à vous ou à votre application.

Comme le tunneling ouvre une connexion directe de votre application à la machine distante, il réintroduit soudainement la possibilité d'effectuer des opérations non-HTTP sur un proxy HTTP. Vous pouvez en fait utiliser des choses comme le téléchargement FTP ou des commandes personnalisées FTP de cette manière.

Encore une fois, cela est souvent empêché par les administrateurs des proxys et est rarement autorisé.

Demandez à libcurl d'utiliser le tunneling proxy comme ceci:

 curl_easy_setopt(handle, CURLOPT_HTTPPROXYTUNNEL, 1L);
En fait, il peut même y avoir des moments où vous souhaitez effectuer des opérations HTTP simples en utilisant un tunnel comme celui-ci, car cela vous permet d'opérer sur le serveur distant au lieu de demander au proxy de le faire. libcurl ne fait pas obstacle à de telles actions innovantes non plus !
Configuration automatique du proxy
Netscape a été le premier à proposer cela. Il s'agit essentiellement d'une page Web (généralement avec une extension .pac) contenant un JavaScript qui, lorsqu'il est exécuté par le navigateur avec l'URL demandée comme entrée, renvoie des informations au navigateur sur la manière de se connecter à l'URL. Les informations renvoyées peuvent être "DIRECT" (ce qui signifie qu'aucun proxy ne doit être utilisé), "PROXY hôte:port" (pour indiquer au navigateur où se trouve le proxy pour cette URL particulière) ou "SOCKS hôte:port" (pour diriger le navigateur vers un proxy SOCKS).

libcurl n'a aucun moyen d'interpréter ou d'évaluer le JavaScript et ne le prend donc pas en charge. Si vous vous retrouvez dans une situation où vous êtes confronté à cette invention désagréable, les conseils suivants ont été mentionnés et utilisés par le passé:

- Selon la complexité du JavaScript, rédigez un script qui le traduit dans une autre langue et exécutez-le.

- Lisez le code JavaScript et réécrivez la même logique dans une autre langue.

- Implémentez un interpréteur JavaScript ; des personnes ont utilisé avec succès le moteur JavaScript de Mozilla par le passé.

- Demandez à vos administrateurs d'arrêter cela, pour une configuration de proxy statique ou similaire.

La persistance est le chemin du bonheur

Recycler plusieurs fois le même descripteur easy lors de requêtes multiples est la solution.

Après chaque opération unique curl_easy_perform(3), libcurl maintient la connexion vivante et ouverte. Une requête ultérieure utilisant le même descripteur easy vers le même hôte pourrait simplement utiliser la connexion déjà ouverte ! Cela réduit considérablement l'impact réseau.

Même si la connexion est perdue, toutes les connexions impliquant du SSL vers le même hôte bénéficient à nouveau du cache d'ID de session de libcurl, ce qui réduit considérablement le temps de reconnexion.

Les connexions FTP qui sont maintenues vivantes font gagner beaucoup de temps, car les allers-retours de commandes-réponses sont évités, et vous ne risquez pas non plus d'être bloqué sans autorisation de vous reconnecter, comme sur de nombreux serveurs FTP qui n'autorisent que N personnes à être connectées en même temps.

libcurl met en cache les résultats de la résolution de noms DNS, ce qui rend les recherches d'un nom précédemment recherché beaucoup plus rapides.

D'autres détails intéressants qui améliorent les performances pour les requêtes ultérieures pourraient également être ajoutés à l'avenir.

Chaque descripteur easy tente de maintenir les quelques dernières connexions actives pendant un certain temps au cas où elles seraient réutilisées. Vous pouvez définir la taille de ce "cache" avec l'option CURLOPT_MAXCONNECTS(3). La valeur par défaut est 5. Il est rarement utile de modifier cette valeur, et si vous pensez à la modifier, c'est souvent juste une question de repenser.

Pour forcer votre prochaine requête à ne pas utiliser une connexion déjà existante, vous pouvez le faire en définissant CURLOPT_FRESH_CONNECT(3) à 1. Dans un esprit similaire, vous pouvez également interdire à la prochaine requête d'"exister" inutilement et éventuellement d'être réutilisée après la requête en définissant CURLOPT_FORBID_REUSE(3) à 1.

Personnalisation des opérations

Il y a un développement continu aujourd'hui où de plus en plus de protocoles sont construits sur HTTP pour le transport. Cela présente des avantages évidents car HTTP est un protocole éprouvé et fiable, largement déployé et doté d'un excellent support proxy.

Lorsque vous utilisez l'un de ces protocoles, et même lorsque vous effectuez d'autres types de programmation, vous pourriez avoir besoin de modifier les manières traditionnelles de HTTP (ou FTP ou...) . Vous pourriez avoir besoin de changer des mots, des en-têtes ou diverses données.

libcurl est aussi votre ami ici.

CURLOPT_CUSTOMREQUEST
Si vous souhaitez simplement modifier le mot-clé de la requête HTTP réelle, comme lorsque GET, HEAD ou POST ne vous suffisent pas, CURLOPT_CUSTOMREQUEST(3) est là pour vous. C'est simple à utiliser : 
curl_easy_setopt(handle, CURLOPT_CUSTOMREQUEST, "MYOWNREQUEST");

Lorsque vous utilisez la requête personnalisée, vous changez le mot-clé de la requête réelle que vous effectuez. Ainsi, par défaut, vous effectuez une requête GET, mais vous pouvez également effectuer une opération POST (comme décrit précédemment) et remplacer ensuite le mot-clé POST si vous le souhaitez. C'est vous le patron.

Modifier les en-têtes
Les protocoles de type HTTP transmettent une série d'en-têtes au serveur lors de la requête, et vous êtes libre de transmettre n'importe quel nombre d'en-têtes supplémentaires qui vous semblent appropriés. L'ajout d'en-têtes est aussi simple que cela : 
struct curl_slist *headers=NULL; /* l'initialisation à NULL est importante */
headers = curl_slist_append(headers, "Hey-server-hey: comment allez-vous ?");
headers = curl_slist_append(headers, "X-silly-content: oui");
/* passez notre liste d'en-têtes personnalisés */
curl_easy_setopt(handle, CURLOPT_HTTPHEADER, headers);
curl_easy_perform(handle); /* transférer http */
curl_slist_free_all(headers); /* libérer la liste d'en-têtes */

... et si vous pensez que certains des en-têtes générés en interne, comme Accept: ou Host:, ne contiennent pas les données que vous souhaitez, vous pouvez les remplacer en les définissant également :

headers = curl_slist_append(headers, "Accept: Agent-007");
headers = curl_slist_append(headers, "Host: munged.host.line");
Supprimer les en-têtes
Si vous remplacez un en-tête existant par un en-tête vide, vous empêchez l'envoi de l'en-tête. Par exemple, si vous souhaitez complètement empêcher l'envoi de l'en-tête "Accept:", vous pouvez le désactiver avec un code similaire à celui-ci :


headers = curl_slist_append(headers, "Accept:");

Le remplacement et l'annulation des en-têtes internes doivent être effectués avec soin et vous devez être conscient que vous pourriez violer le protocole HTTP en le faisant.

Imposer le codage par morceaux
En vous assurant qu'une requête utilise l'en-tête personnalisé "Transfer-Encoding: chunked" lors d'une opération HTTP autre que GET, libcurl passe en mode téléchargement "par morceaux", même si la taille des données à télécharger est connue. Par défaut, libcurl passe généralement en mode téléchargement par morceaux automatiquement si la taille des données à télécharger est inconnue.
Version HTTP
Toutes les requêtes HTTP incluent le numéro de version pour indiquer au serveur quelle version nous prenons en charge. libcurl utilise HTTP 1.1 par défaut. Certains anciens serveurs n'aiment pas recevoir des requêtes 1.1 et lorsque vous traitez des choses anciennes et récalcitrantes comme celles-ci, vous pouvez demander à libcurl d'utiliser 1.0 à la place en faisant quelque chose comme ceci :


curl_easy_setopt(handle, CURLOPT_HTTP_VERSION, CURL_HTTP_VERSION_1_0);

Commandes FTP personnalisées
Tous les protocoles ne sont pas de type HTTP, et donc ce qui précède pourrait ne pas vous aider lorsque vous souhaitez que, par exemple, vos transferts FTP se comportent différemment.

L'envoi de commandes personnalisées à un serveur FTP signifie que vous devez envoyer les commandes exactement comme le serveur FTP s'attend à les recevoir (RFC 959 est un bon guide ici), et vous ne pouvez utiliser que les commandes qui fonctionnent sur le canal de contrôle seul. Toutes les commandes qui nécessitent un échange de données et qui nécessitent donc un canal de données doivent être laissées au jugement de libcurl. Sachez également que libcurl fait de son mieux pour changer de répertoire vers le répertoire cible avant d'effectuer un transfert. Par conséquent, si vous changez de répertoire (avec CWD ou similaire), vous pourriez confondre libcurl et il pourrait alors ne pas tenter de transférer le fichier dans le bon répertoire distant.

Un petit exemple qui supprime un fichier donné avant une opération :

 headers = curl_slist_append(headers, "DELE fichier-a-supprimer");
 /* passez la liste des commandes personnalisées au descripteur */
 curl_easy_setopt(handle, CURLOPT_QUOTE, headers);
 curl_easy_perform(handle); /* transférer les données ftp ! */
 curl_slist_free_all(headers); /* libérer la liste d'en-têtes */

Si vous souhaitiez plutôt que cette opération (ou chaîne d'opérations) se produise _après_ le transfert de données, l'option pour curl_easy_setopt(3) serait plutôt appelée CURLOPT_POSTQUOTE(3) et utilisée exactement de la même manière.

Commandes FTP

Les commandes FTP, comme dans la plupart des protocoles d'envoi de fichiers, peuvent être envoyées avant le transfert réel. Libcurl vous permet de le faire en utilisant l'option CURLOPT_QUOTE(3). Vous fournissez un tableau de chaînes, où chaque chaîne est une commande FTP individuelle à envoyer au serveur. Ces commandes sont envoyées au serveur dans le même ordre où elles sont ajoutées à la liste, et si une commande reçoit un code d'erreur du serveur, aucune autre commande n'est envoyée et libcurl échoue avec un code d'erreur (CURLE_QUOTE_ERROR). Notez que si vous utilisez CURLOPT_QUOTE(3) pour envoyer des commandes avant un transfert, aucun transfert n'a réellement lieu lorsqu'une commande de citation échoue.

Si vous définissez CURLOPT_HEADER(3) à 1, vous indiquez à libcurl d'obtenir des informations sur le fichier cible et de générer des « en-têtes » à son sujet. Les en-têtes sont de style « HTTP », ressemblant à ce qu'ils sont en HTTP.

L'option permettant d'activer les en-têtes ou d'exécuter des commandes FTP personnalisées peut être utile à combiner avec CURLOPT_NOBODY(3). Si cette option est définie, aucun transfert de contenu de fichier réel n'est effectué.

FTP Personnalisé CURLOPT_CUSTOMREQUEST
Si vous souhaitez lister le contenu d'un répertoire FTP en utilisant votre propre commande FTP définie, CURLOPT_CUSTOMREQUEST(3) fait exactement cela. « NLST » est la commande par défaut pour lister les répertoires, mais vous êtes libre de fournir votre propre alternative.

Cookies Sans Pépites de Chocolat

Dans le sens HTTP, un cookie est un nom associé à une valeur. Un serveur envoie le nom et la valeur au client, et s'attend à ce qu'ils soient renvoyés à chaque requête ultérieure vers le serveur qui correspond aux conditions particulières définies. Les conditions incluent que le nom de domaine et le chemin correspondent et que le cookie n'est pas devenu trop ancien.

Dans les cas du monde réel, les serveurs envoient de nouveaux cookies pour remplacer ceux existants afin de les mettre à jour. Les serveurs utilisent les cookies pour « suivre » les utilisateurs et maintenir les « sessions ».

Les cookies sont envoyés du serveur aux clients avec l'en-tête Set-Cookie: et sont envoyés des clients aux serveurs avec l'en-tête Cookie:.

Pour simplement envoyer le cookie de votre choix à un serveur, vous pouvez utiliser CURLOPT_COOKIE(3) pour définir une chaîne de cookie comme ceci :

 curl_easy_setopt(handle, CURLOPT_COOKIE, "name1=var1; name2=var2;");

Dans de nombreux cas, cela ne suffit pas. Vous pourriez vouloir enregistrer dynamiquement tous les cookies que le serveur distant vous transmet, et vous assurer que ces cookies sont ensuite utilisés en conséquence lors des requêtes ultérieures.

Une façon de faire cela est d'enregistrer tous les en-têtes que vous recevez dans un fichier texte brut et, lorsque vous effectuez une requête, vous dites à libcurl de lire les en-têtes précédents pour déterminer quels cookies utiliser. Définissez le fichier d'en-têtes à lire avec CURLOPT_COOKIEFILE(3).

L'option CURLOPT_COOKIEFILE(3) active également automatiquement l'analyseur de cookies dans libcurl. Tant que l'analyseur de cookies n'est pas activé, libcurl n'analyse pas et ne comprend pas les cookies entrants, et ils sont simplement ignorés. Cependant, lorsque l'analyseur est activé, les cookies sont compris, conservés en mémoire et utilisés correctement dans les requêtes ultérieures lorsque le même handle est utilisé. Souvent, cela suffit, et vous n'avez pas besoin d'enregistrer les cookies sur disque. Notez que le fichier que vous spécifiez à CURLOPT_COOKIEFILE(3) n'a pas besoin d'exister pour activer l'analyseur, donc une façon courante d'activer simplement l'analyseur et de ne lire aucun cookie est d'utiliser le nom d'un fichier qui, selon vous, n'existe pas.

Si vous préférez utiliser des cookies existants que vous avez précédemment reçus avec vos navigateurs Netscape ou Mozilla, vous pouvez faire en sorte que libcurl utilise ce fichier de cookies comme entrée. CURLOPT_COOKIEFILE(3) est également utilisé à cette fin, car libcurl détermine automatiquement le type de fichier et agit en conséquence.

Peut-être l'opération de cookies la plus avancée que libcurl propose est l'enregistrement de l'état complet des cookies internes dans un fichier de cookies formaté Netscape/Mozilla. Nous appelons cela le « cookie-jar ». Lorsque vous définissez un nom de fichier avec CURLOPT_COOKIEJAR(3), ce nom de fichier est créé et tous les cookies reçus y sont stockés lorsque curl_easy_cleanup(3) est appelé. Cela permet de passer correctement les cookies entre plusieurs handles sans aucune perte d'informations.

Particularités FTP dont nous avons besoin

Les transferts FTP utilisent une deuxième connexion TCP/IP pour le transfert de données. C'est généralement un fait que vous pouvez oublier et ignorer, mais parfois ce détail revient vous hanter. Libcurl offre plusieurs façons de personnaliser la manière dont la deuxième connexion est établie.

Libcurl peut soit se connecter une deuxième fois au serveur, soit demander au serveur de se reconnecter à lui. La première option est la valeur par défaut et c'est aussi ce qui fonctionne le mieux pour toutes les personnes derrière des pare-feux, des NAT ou des configurations d'IP masquée. Libcurl demande alors au serveur d'ouvrir un nouveau port et d'attendre une deuxième connexion. Par défaut, cela est tenté avec EPSV d'abord, et si cela ne fonctionne pas, il essaie PASV à la place. (EPSV est une extension de la spécification FTP d'origine et n'existe ni ne fonctionne sur tous les serveurs FTP.)

Vous pouvez empêcher libcurl d'essayer d'abord la commande EPSV en définissant CURLOPT_FTP_USE_EPSV(3) à zéro.

Dans certains cas, vous souhaitez que le serveur vous recontacte pour la deuxième connexion. Cela peut être lorsque le serveur est peut-être derrière un pare-feu ou quelque chose de similaire et n'autorise que les connexions sur un seul port. Libcurl informe alors le serveur distant de l'adresse IP et du numéro de port auxquels se connecter. Ceci est fait avec l'option CURLOPT_FTPPORT(3). Si vous la définissez sur « - », libcurl utilise l'« adresse IP par défaut » de votre système. Si vous souhaitez utiliser une IP particulière, vous pouvez définir l'adresse IP complète, un nom d'hôte à résoudre en une adresse IP, voire un nom d'interface réseau local à partir duquel libcurl obtient l'adresse IP.

Lorsqu'il utilise l'approche « PORT », libcurl tente d'utiliser EPRT et LPRT avant d'essayer PORT, car ils fonctionnent avec plus de protocoles. Vous pouvez désactiver ce comportement en définissant CURLOPT_FTP_USE_EPRT(3) à zéro.

API MIME revue pour SMTP et IMAP

En plus de prendre en charge les champs de formulaire multi-parties HTTP, l'API MIME peut être utilisée pour construire des messages électroniques structurés et les envoyer via SMTP ou les ajouter à des répertoires IMAP.

Un message électronique structuré peut contenir plusieurs parties : certaines sont affichées en ligne par le MUA, d'autres sont des pièces jointes. Les parties peuvent également être structurées comme des multi-parties, par exemple pour inclure un autre message électronique ou pour offrir plusieurs alternatives de formats de texte. Cela peut être imbriqué à n'importe quel niveau.

Pour construire un tel message, vous préparez la multi-partie de niveau n, puis vous l'incluez comme source à la multi-partie parente en utilisant la fonction curl_mime_subparts(3). Une fois qu'elle a été liée à sa multi-partie parente, une multi-partie de niveau n lui appartient et ne doit pas être libérée explicitement.

Les données des messages électroniques ne sont pas censées être non-ASCII et la longueur des lignes est limitée : heureusement, certains encodages de transfert sont définis par les normes pour prendre en charge la transmission de données incompatibles. La fonction curl_mime_encoder(3) indique à une partie que ses données source doivent être encodées avant d'être envoyées. Elle génère également l'en-tête correspondant pour cette partie. Si les données de la partie que vous souhaitez envoyer sont déjà encodées selon un tel schéma, n'utilisez pas cette fonction (cela la sur-encoderait), mais définissez explicitement l'en-tête de partie correspondant.

Lors de l'envoi d'un tel message, libcurl le préfixe avec la liste d'en-têtes définie avec CURLOPT_HTTPHEADER(3), comme en-têtes de partie MIME de niveau zéro.

Voici un exemple de construction d'un message électronique avec une alternative texte brut/html en ligne et une pièce jointe codée en base64 :

 curl_mime *message = curl_mime_init(handle);
 /* La partie en ligne est une alternative proposant les versions html et texte
    du courrier électronique. */
 curl_mime *alt = curl_mime_init(handle);
 /* Message HTML. */
 curl_mimepart *part = curl_mime_addpart(alt);
 curl_mime_data(part, "<html><body><p>Ceci est du HTML</p></body></html>",
                      CURL_ZERO_TERMINATED);
 curl_mime_type(part, "text/html");
 /* Message texte. */
 part = curl_mime_addpart(alt);
 curl_mime_data(part, "Ceci est un message en texte brut",
                      CURL_ZERO_TERMINATED);
 /* Créer la partie en ligne. */
 part = curl_mime_addpart(message);
 curl_mime_subparts(part, alt);
 curl_mime_type(part, "multipart/alternative");
 struct curl_slist *headers = curl_slist_append(NULL,
                   "Content-Disposition: inline");
 curl_mime_headers(part, headers, TRUE);
 /* Ajouter la pièce jointe. */
 part = curl_mime_addpart(message);
 curl_mime_filedata(part, "manual.pdf");
 curl_mime_encoder(part, "base64");
 /* Construire les en-têtes du courrier. */
 headers = curl_slist_append(NULL, "From: me@example.com");
 headers = curl_slist_append(headers, "To: you@example.com");
 /* Les définir dans le handle easy. */
 curl_easy_setopt(handle, CURLOPT_HTTPHEADER, headers);
 curl_easy_setopt(handle, CURLOPT_MIMEPOST, mime);

Il convient de noter que l'ajout d'un message à un répertoire IMAP nécessite que la taille du message soit connue avant le téléchargement. Il n'est donc pas possible d'inclure des parties de taille de données inconnue dans ce contexte.

Les en-têtes sont égaux à l'amusement

Certains protocoles fournissent des « en-têtes », des métadonnées séparées des données normales. Ces en-têtes ne sont pas inclus par défaut dans le flux de données normal, mais vous pouvez les faire apparaître dans le flux de données en définissant CURLOPT_HEADER(3) à 1.

Ce qui pourrait être encore plus utile, c'est la capacité de libcurl à séparer les en-têtes des données et ainsi à différencier les callbacks. Vous pouvez par exemple définir un pointeur différent à passer au callback d'écriture ordinaire en définissant CURLOPT_HEADERDATA(3).

Ou, vous pouvez définir une fonction entièrement distincte pour recevoir les en-têtes, en utilisant CURLOPT_HEADERFUNCTION(3).

Les en-têtes sont passés à la fonction de rappel un par un, et vous pouvez vous y fier. Cela vous permet d'ajouter plus facilement des analyseurs d'en-têtes personnalisés, etc.

Les « en-têtes » pour les transferts FTP correspondent à toutes les réponses du serveur FTP. Ce ne sont pas de vrais en-têtes, mais dans ce cas, nous prétendons qu'ils le sont.

L'interface multi

L'interface facile décrite en détail dans ce document est une interface synchrone qui transfère un fichier à la fois et ne retourne pas avant que ce soit fait.

L'interface multi, en revanche, permet à votre programme de transférer plusieurs fichiers dans les deux directions en même temps, sans vous obliger à utiliser plusieurs threads. Le nom pourrait laisser penser que l'interface multi est destinée aux programmes multi-threadés, mais la vérité est presque l'inverse. L'interface multi permet à une application single-threadée d'effectuer les mêmes types de transferts multiples et simultanés que les programmes multi-threadés peuvent effectuer. Elle permet de bénéficier de nombreux avantages des transferts multi-threadés sans la complexité de la gestion et de la synchronisation de nombreux threads.

Pour compliquer un peu plus les choses, il existe même deux versions de l'interface multi. Celle basée sur les événements, également appelée multi_socket, et celle "normale" conçue pour être utilisée avec select(). Voir la page man libcurl-multi.3 pour les détails sur l'API basée sur les événements multi_socket, cette description ici est pour celle orientée select().

Pour utiliser cette interface, il est préférable de comprendre d'abord les bases de l'utilisation de l'interface facile. L'interface multi est simplement une façon de réaliser plusieurs transferts en même temps en ajoutant plusieurs handles faciles dans une "pile multi".

Vous créez les handles faciles que vous souhaitez, un pour chaque transfert concurrent, et vous définissez toutes les options comme vous l'avez appris ci-dessus, puis vous créez un handle multi avec curl_multi_init(3) et ajoutez tous ces handles faciles à ce handle multi avec curl_multi_add_handle(3).

Lorsque vous avez ajouté les handles que vous avez pour le moment (vous pouvez toujours en ajouter de nouveaux à tout moment), vous démarrez les transferts en appelant curl_multi_perform(3).

curl_multi_perform(3) est asynchrone. Il n'effectue que ce qui peut être fait maintenant, puis retourne le contrôle à votre programme. Il est conçu pour ne jamais bloquer. Vous devez continuer à appeler la fonction jusqu'à ce que tous les transferts soient terminés.

La meilleure utilisation de cette interface est lorsque vous faites un select() sur tous les descripteurs de fichiers ou sockets possibles pour savoir quand rappeler libcurl. Cela vous permet également d'attendre et de répondre aux actions sur les sockets/handles de votre propre application. Vous déterminez ce qu'il faut sélectionner() en utilisant curl_multi_fdset(3), qui remplit un ensemble de variables fd_set pour vous avec les descripteurs de fichiers particuliers que libcurl utilise pour le moment.

Lorsque vous appelez ensuite select(), il retourne lorsque l'un des handles de fichiers signale une action et vous appelez alors curl_multi_perform(3) pour permettre à libcurl de faire ce qu'il veut faire. Notez que libcurl dispose également d'un code de délai d'attente, nous vous conseillons donc de ne jamais utiliser de longs délais d'attente sur select() avant de rappeler curl_multi_perform(3). curl_multi_timeout(3) est fourni pour vous aider à obtenir une période de délai d'attente appropriée.

Une autre précaution à prendre : appelez toujours curl_multi_fdset(3) immédiatement avant l'appel à select() car l'ensemble actuel des descripteurs de fichiers peut changer lors de toute invocation de fonction curl.

Si vous souhaitez arrêter le transfert d'un des handles faciles de la pile, vous pouvez utiliser curl_multi_remove_handle(3) pour supprimer des handles faciles individuels. N'oubliez pas que les handles faciles doivent être nettoyés avec curl_easy_cleanup(3).

Lorsqu'un transfert dans la pile multi est terminé, le compteur des transferts en cours (tel que rempli par curl_multi_perform(3)) diminue. Lorsque le nombre atteint zéro, tous les transferts sont terminés.

curl_multi_info_read(3) peut être utilisé pour obtenir des informations sur les transferts terminés. Il retourne alors le CURLcode pour chaque transfert facile, pour vous permettre de déterminer le succès de chaque transfert individuel.

Partage de données entre handles faciles

Vous pouvez partager certaines données entre handles faciles lorsque l'interface facile est utilisée, et certaines données sont partagées automatiquement lorsque vous utilisez l'interface multi.

Lorsque vous ajoutez des handles faciles à un handle multi, ces handles faciles partagent automatiquement une grande partie des données qui seraient sinon conservées sur une base par handle facile lorsque l'interface facile est utilisée.

Le cache DNS est partagé entre les handles au sein d'un handle multi, accélérant la résolution de noms ultérieure, et le pool de connexions qui est maintenu pour mieux permettre les connexions persistantes et la réutilisation des connexions est également partagé. Si vous utilisez l'interface facile, vous pouvez toujours les partager entre des handles faciles spécifiques en utilisant l'interface de partage, voir libcurl-share(3).

Certaines choses ne sont jamais partagées automatiquement, pas même au sein des handles multi, comme par exemple les cookies, donc la seule façon de les partager est avec l'interface de partage.
