NOM

libipq — bibliothèque utilisateur pour la mise en file d'attente des paquets iptables.

SYNTAXE

#include <linux/netfilter.h>
#include <libipq.h>

DESCRIPTION

libipq est une bibliothèque de développement pour la mise en file d'attente des paquets iptables par l'espace utilisateur.

Mise en file d'attente des paquets par l'espace utilisateur

Netfilter fournit un mécanisme pour passer les paquets hors de la pile pour les mettre en file d'attente dans l'espace utilisateur, puis pour recevoir ces paquets de retour dans le noyau avec un verdict spécifiant quoi faire des paquets (comme ACCEPT ou DROP). Ces paquets peuvent également être modifiés dans l'espace utilisateur avant d'être réinjectés dans le noyau.

Pour chaque protocole pris en charge, un module du noyau appelé gestionnaire de file d'attente peut s'enregistrer auprès de Netfilter pour effectuer la mécanique de passage des paquets vers et depuis l'espace utilisateur.

Le gestionnaire de file d'attente standard pour IPv4 est ip_queue. Il est fourni comme module expérimental avec les noyaux 2.4, et utilise un socket Netlink pour la communication noyau/espace utilisateur.

Une fois ip_queue chargé, les paquets IP peuvent être sélectionnés avec iptables et mis en file d'attente pour un traitement par l'espace utilisateur via la cible QUEUE. Par exemple, l'exécution des commandes suivantes :

# modprobe iptable_filter
# modprobe ip_queue
# iptables -A OUTPUT -p icmp -j QUEUE

entraînera l'envoi de tous les paquets ICMP générés localement (par exemple, la sortie ping) au module ip_queue, qui tentera alors de délivrer les paquets à une application utilisateur. S'il n'y a pas d'application utilisateur en attente, les paquets seront ignorés.

Une application peut recevoir et traiter ces paquets via libipq.

Aperçu de Libipq

Libipq fournit une API pour communiquer avec ip_queue. Voici un aperçu de l'utilisation de l'API, consultez les pages de manuel individuelles pour plus de détails sur chaque fonction.

Initialisation
Pour initialiser la bibliothèque, appelez ipq_create_handle(3). Cela tentera de se lier au socket Netlink utilisé par ip_queue et retournera un handle de contexte opaque pour les appels ultérieurs de la bibliothèque.

Définition du mode de file d'attente
ipq_set_mode(3) permet à l'application de spécifier si les métadonnées du paquet, ou les charges utiles des paquets ainsi que les métadonnées, sont copiées vers l'espace utilisateur. Elle est également utilisée pour notifier initialement ip_queue qu'une application est prête à recevoir des messages de file d'attente.

Réception des paquets de la file d'attente
ipq_read(3) attend que les messages de la file d'attente arrivent d'ip_queue et les copie dans un tampon fourni. Les messages de la file d'attente peuvent être des messages de paquet ou des messages d'erreur.

Le type de paquet peut être déterminé avec ipq_message_type(3).

S'il s'agit d'un message de paquet, les métadonnées et la charge utile optionnelle peuvent être récupérées avec ipq_get_packet(3).

Pour récupérer la valeur d'un message d'erreur, utilisez ipq_get_msgerr(3).

Émission de verdicts sur les paquets
Pour émettre un verdict sur un paquet, et éventuellement retourner une version modifiée du paquet au noyau, appelez ipq_set_verdict(3).

Gestion des erreurs
Une chaîne d'erreur correspondant à la valeur interne de la variable d'erreur ipq_errno peut être obtenue avec ipq_errstr(3).

Pour des applications simples, appeler ipq_perror(3) affichera le même message que ipq_errstr(3), ainsi que la chaîne correspondant à la valeur globale errno (si définie) sur stderr.

Nettoyage
Pour libérer le socket Netlink et détruire les ressources associées au handle de contexte, appelez ipq_destroy_handle(3).

RÉSUMÉ

ipq_create_handle(3)
Initialise la bibliothèque, retourne un handle de contexte.
ipq_set_mode(3)
Définit le mode de file d'attente, pour copier soit les métadonnées du paquet, soit les charges utiles ainsi que les métadonnées vers l'espace utilisateur.
ipq_read(3)
Attend qu'un message de file d'attente arrive d'ip_queue et le lit dans un tampon.
ipq_message_type(3)
Détermine le type de message dans le tampon.
ipq_get_packet(3)
Récupère un message de paquet du tampon.
ipq_get_msgerr(3)
Récupère un message d'erreur du tampon.
ipq_set_verdict(3)
Définit un verdict sur un paquet, remplaçant éventuellement son contenu.
ipq_errstr(3)
Retourne un message d'erreur correspondant à la variable interne ipq_errno.
ipq_perror(3)
Fonction d'aide pour afficher les messages d'erreur sur stderr.
ipq_destroy_handle(3)
Détruit le handle de contexte et les ressources associées.

EXEMPLE

Voici un exemple d'application simple qui reçoit des paquets et émet des verdicts NF_ACCEPT sur chaque paquet.

/*
 * Ce code est sous licence GPL.
 */
#include <linux/netfilter.h>
#include <libipq.h>
#include <stdio.h>
#define BUFSIZE 2048
static void die(struct ipq_handle *h)
{
	ipq_perror("passer");
	ipq_destroy_handle(h);
	exit(1);
}
int main(int argc, char **argv)
{
	int status;
	unsigned char buf[BUFSIZE];
	struct ipq_handle *h;

	h = ipq_create_handle(0, NFPROTO_IPV4);
	if (!h)
		die(h);

	status = ipq_set_mode(h, IPQ_COPY_PACKET, BUFSIZE);
	if (status < 0)
		die(h);

	do{
		status = ipq_read(h, buf, BUFSIZE, 0);
		if (status < 0)
			die(h);

		switch (ipq_message_type(buf)) {
			case NLMSG_ERROR:
				fprintf(stderr, "Received error message %d\n",
				        ipq_get_msgerr(buf));
				break;

			case IPQM_PACKET: {
				ipq_packet_msg_t *m = ipq_get_packet(buf);

				status = ipq_set_verdict(h, m->packet_id,
				                         NF_ACCEPT, 0, NULL);
				if (status < 0)
					die(h);
				break;
			}

			default:
				fprintf(stderr, "Unknown message type!\n");
				break;
		}
	} while (1);

	ipq_destroy_handle(h);
	return 0;
}

DIAGNOSTIC

Pour des informations sur la surveillance et l'ajustement d'ip_queue, référez-vous au HOWTO sur le filtrage de paquets de Linux 2.4.

Si une application modifie un paquet, elle doit également mettre à jour les sommes de contrôle du paquet. Généralement, le noyau ignorera silencieusement les paquets modifiés avec des sommes de contrôle invalides.

SÉCURITÉ

Les processus nécessitent la capacité CAP_NET_ADMIN pour accéder au module ip_queue du noyau. De tels processus peuvent potentiellement accéder et modifier tous les paquets IP reçus, générés ou transférés par le noyau.
