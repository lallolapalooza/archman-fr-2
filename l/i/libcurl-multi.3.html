NOM

libcurl-multi - comment utiliser l'interface multi

DESCRIPTION

Ceci est un aperçu de l'utilisation de l'interface multi de libcurl dans vos programmes C. Il existe des pages de manuel spécifiques pour chaque fonction mentionnée ici. Il y a également la page de manuel libcurl-tutorial(3) pour un tutoriel complet sur la programmation avec libcurl et la page de manuel libcurl-easy(3) pour un aperçu de l'interface facile de libcurl.

Toutes les fonctions de l'interface multi sont préfixées par curl_multi.

OBJECTIFS

L'interface multi offre plusieurs capacités que l'interface facile n'a pas. Elles sont principalement :

1. Permettre une interface de type "push". L'application qui utilise libcurl décide où et quand demander à libcurl d'obtenir/envoyer des données.

2. Permettre plusieurs transferts simultanés dans le même thread sans compliquer l'application.

3. Permettre à l'application d'attendre une action sur ses propres descripteurs de fichiers et les descripteurs de fichiers de curl simultanément.

4. Permettre une gestion basée sur les événements et mettre à l'échelle les transferts jusqu'à des milliers de connexions parallèles et au-delà.

UN HANDLE MULTI BEAUCOUP DE HANDLES FACILES

Pour utiliser l'interface multi, vous devez d'abord créer un 'handle multi' avec curl_multi_init(3). Ce handle est ensuite utilisé comme entrée pour toutes les fonctions `curl_multi_*` suivantes.

Avec un handle multi et l'interface multi, vous pouvez effectuer plusieurs transferts simultanés en parallèle. Chaque transfert individuel est construit autour d'un handle facile. Vous créez tous les handles faciles dont vous avez besoin et configurez les options appropriées pour chaque handle facile en utilisant curl_easy_setopt(3).

Il existe deux versions de l'interface multi : celle orientée `select()` et celle basée sur les événements que nous appelons multi_socket. Il est bénéfique de lire la description des deux versions pour comprendre pleinement leur fonctionnement et leurs différences. Nous commençons par la version orientée `select()`.

Lorsqu'un handle facile est configuré et prêt pour le transfert, au lieu d'utiliser curl_easy_perform(3) comme lorsque vous utilisez l'interface facile pour les transferts, vous devez ajouter le handle facile au handle multi avec curl_multi_add_handle(3). Vous pouvez ajouter d'autres handles faciles à un handle multi à tout moment, même si d'autres transferts sont déjà en cours.

Si vous changez d'avis, le handle facile est à nouveau retiré de la pile multi en utilisant curl_multi_remove_handle(3). Une fois retiré du handle multi, vous pouvez à nouveau utiliser d'autres fonctions de l'interface facile comme curl_easy_perform(3) sur le handle ou tout ce que vous jugerez nécessaire. Vous pouvez retirer des handles à tout moment pendant les transferts.

L'ajout du handle facile au handle multi ne démarre pas le transfert. N'oubliez pas que l'une des idées principales de cette interface est de laisser votre application piloter. Vous pilotez les transferts en appelant curl_multi_perform(3). libcurl transfère alors des données s'il y a quelque chose de disponible à transférer. Il utilise les callbacks et tout le reste que vous avez configuré dans les handles faciles individuels. Il transfère des données sur tous les transferts en cours dans la pile multi qui sont prêts à transférer quelque chose. Il peut s'agir de tous, il peut s'agir d'aucun. Lorsqu'il n'y a plus rien à faire pour l'instant, il retourne à l'application appelante.

Votre application extrait des informations de libcurl sur quand elle souhaite être appelée pour transférer des données ou effectuer d'autres travaux. La manière la plus pratique est d'utiliser curl_multi_poll(3) qui vous aide à attendre jusqu'à ce que l'application doive rappeler libcurl. L'ancienne API pour accomplir la même chose est curl_multi_fdset(3) qui extrait des `fd_sets` de libcurl pour les utiliser dans des appels `select()` ou `poll()` afin de savoir quand les transferts dans la pile multi pourraient nécessiter une attention. Ces deux APIs permettent à votre programme d'attendre simultanément des entrées sur vos propres descripteurs de fichiers privés. curl_multi_timeout(3) vous aide également en fournissant une période de délai d'attente appropriée pour vos appels `select()`.

curl_multi_perform(3) stocke le nombre de transferts encore en cours dans l'un de ses arguments d'entrée, et en lisant cela, vous pouvez déterminer quand tous les transferts dans les handles multi sont terminés. 'terminé' ne signifie pas 'réussi'. Un ou plusieurs des transferts peuvent avoir échoué.

Pour obtenir des informations sur les transferts terminés, déterminer le succès ou non, etc., curl_multi_info_read(3) doit être appelé. Il peut retourner un message concernant un transfert en cours ou précédent. Des appels répétés à la fonction permettent d'obtenir plus de messages jusqu'à ce que la file de messages soit vide. Les informations que vous recevez incluent un pointeur de handle facile que vous pouvez utiliser pour identifier à quel handle facile l'information se rapporte.

Lorsqu'un transfert individuel est terminé, le handle facile reste ajouté à la pile multi. Vous devez d'abord retirer le handle facile avec curl_multi_remove_handle(3) puis le nettoyer avec curl_easy_cleanup(3), ou éventuellement lui définir de nouvelles options et le rajouter avec curl_multi_add_handle(3) pour démarrer un autre transfert.

Lorsque tous les transferts dans la pile multi sont terminés, fermez le handle multi avec curl_multi_cleanup(3). Soyez prudent et notez que vous DEVEZ appeler séparément curl_easy_cleanup(3) pour chaque handle facile afin de les nettoyer correctement.

Si vous souhaitez réutiliser un handle facile qui a été ajouté au handle multi pour un transfert, vous devez d'abord le retirer de la pile multi puis le rajouter (éventuellement après avoir modifié certaines options à votre choix).

MULTI_SOCKET

curl_multi_socket_action(3) offre un moyen aux applications de non seulement éviter d'être obligées d'utiliser `select()`, mais aussi d'offrir une API beaucoup plus performante qui fait une différence significative pour les applications utilisant un grand nombre de connexions simultanées.

curl_multi_socket_action(3) est alors utilisé à la place de curl_multi_perform(3).

Lorsque vous utilisez cette API, vous ajoutez des handles faciles au handle multi, tout comme avec l'interface multi normale. Ensuite, vous définissez également deux callbacks avec les options CURLMOPT_SOCKETFUNCTION(3) et CURLMOPT_TIMERFUNCTION(3) à curl_multi_setopt(3). Ce sont deux fonctions de rappel que libcurl appelle avec des informations sur les sockets sur lesquels attendre, pour quelles activités, et quel est le délai d'attente actuel - si celui-ci expire, libcurl doit en être informé.

L'API multi_socket est conçue pour informer votre application des sockets que libcurl utilise actuellement et pour quelles activités (lecture et/ou écriture) sur ces sockets votre application est censée attendre.

Votre application doit s'assurer de recevoir tous les sockets pour lesquels elle est informée dans la fonction de rappel CURLMOPT_SOCKETFUNCTION(3) et doit réagir à l'activité donnée sur eux. Lorsqu'un socket présente l'activité donnée, vous appelez curl_multi_socket_action(3) en spécifiant quel socket et quelle action il y a.

La fonction de rappel CURLMOPT_TIMERFUNCTION(3) est appelée pour définir un délai d'attente. Lorsque ce délai expire, votre application doit appeler la fonction curl_multi_socket_action(3) en indiquant que cela est dû à un délai d'attente.

Cette API est généralement utilisée avec des fonctionnalités sous-jacentes pilotées par événement (comme libevent, libev, kqueue, epoll ou similaire) avec lesquelles l'application s' "abonne" aux changements de socket. Cela permet aux applications et à libcurl de mieux monter en charge et de dépasser des milliers de transferts simultanés sans perdre de performance.

BLOQUANT

Certaines parties du code utilisent encore du code bloquant, même lorsqu'elles sont utilisées à partir de l'interface multi. Bien que nous voulions et ayons l'intention de corriger ces points à l'avenir, vous devez être conscient des restrictions actuelles suivantes :

 - Résolution de noms sauf si les backends c-ares ou threaded-resolver sont utilisés
 - transferts file://
 - transferts TELNET
