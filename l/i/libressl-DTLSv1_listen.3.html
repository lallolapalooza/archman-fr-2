DTLSV1_LISTEN(3) Manuel des fonctions de bibliothèque DTLSV1_LISTEN(3)

NOM

DTLSv1_listen — écoute des connexions DTLS entrantes

SYNOPSIS

bibliothèque «libssl» libcrypto
#include <openssl/ssl.h>

int
DTLSv1_listen(SSL *ssl, struct sockaddr *peer);

DESCRIPTION

DTLSv1_listen() écoute les nouvelles connexions DTLS entrantes. Si un ClientHello est reçu sans cookie, alors DTLSv1_listen() répond avec un HelloVerifyRequest. Si un ClientHello est reçu avec un cookie vérifié, alors le contrôle est retourné au code utilisateur pour permettre l'achèvement de la négociation (par exemple en utilisant SSL_accept(3)).

DTLSv1_listen() est actuellement implémenté comme une macro.

Les protocoles basés sur les datagrammes peuvent être vulnérables aux attaques par déni de service. Un attaquant DTLS pourrait, par exemple, soumettre une série de requêtes d'initiation de négociation qui amènent le serveur à allouer de l'état (et potentiellement effectuer des opérations cryptographiques) consommant ainsi les ressources du serveur. L'attaquant pourrait également (avec UDP) simplement usurper l'adresse IP source dans une telle attaque.

En guise de contre-mesure, DTLS inclut un mécanisme de cookie sans état. L'idée est que lorsqu'un client tente de se connecter à un serveur, il envoie un message ClientHello. Le serveur répond avec un HelloVerifyRequest qui contient un cookie unique. Le client renvoie alors le ClientHello, mais inclut cette fois le cookie dans le message, prouvant ainsi que le client est capable de recevoir les messages envoyés à cette adresse. Tout cela peut être fait par le serveur sans allouer d'état, et donc sans consommer de ressources coûteuses.

OpenSSL implémente cette fonctionnalité via la fonction DTLSv1_listen(). Le paramètre ssl doit être un objet SSL nouvellement alloué avec ses BIOs de lecture et d'écriture définis, de la même manière que pour un appel à SSL_accept(3). Typiquement, le BIO de lecture sera dans un état « non connecté » et donc capable de recevoir des messages de n'importe quel pair.

Lorsqu'un ClientHello contenant un cookie vérifié est reçu, DTLSv1_listen() retournera avec le paramètre ssl mis à jour dans un état où la négociation peut être poursuivie par un appel à (par exemple) SSL_accept(3). De plus, la structure struct sockaddr pointée par peer sera remplie avec les détails du pair qui a envoyé le ClientHello. Il incombe au code appelant de s'assurer que l'emplacement peer est suffisamment grand pour accueillir le schéma d'adressage utilisé. Par exemple, cela peut être fait en allouant de l'espace pour un struct sockaddr_storage et en convertissant le pointeur vers celui-ci en un struct sockaddr * pour l'appel à DTLSv1_listen(). Typiquement, on s'attend à ce que le code utilisateur « connecte » le socket sous-jacent au pair et poursuive la négociation dans un état connecté.

Avant d'appeler DTLSv1_listen(), le code utilisateur doit s'assurer que les rappels de génération et de vérification de cookies ont été configurés à l'aide de SSL_CTX_set_cookie_generate_cb() et SSL_CTX_set_cookie_verify_cb() respectivement.

Comme DTLSv1_listen() fonctionne entièrement sans état lors du traitement des ClientHellos entrants, il ne peut pas traiter les messages fragmentés (car cela nécessiterait l'allocation d'état). Une implication est que DTLSv1_listen() ne prend en charge que les ClientHellos qui tiennent dans un seul datagramme.

VALEUR DE RETOUR

Depuis OpenSSL 1.1.0, une valeur de retour de >= 1 indique le succès. Dans ce cas, la valeur peer sera remplie et l'objet ssl sera prêt pour continuer la négociation.

Une valeur de retour de 0 indique une erreur non fatale. Cela pourrait être dû (par exemple) à une entrée/sortie non bloquante, ou à un message invalide reçu d'un pair. Des erreurs peuvent être placées dans la file d'attente des erreurs OpenSSL avec des informations supplémentaires si nécessaire. Typiquement, on s'attend à ce que le code utilisateur réessaie l'appel à DTLSv1_listen() en cas d'erreur non fatale. Toutes les anciennes erreurs dans la file d'attente des erreurs seront effacées lors de l'appel suivant.

Une valeur de retour de <0 indique une erreur fatale. Cela pourrait être dû (par exemple) à un échec d'allocation de mémoire suffisante pour l'opération.

Avant OpenSSL 1.1.0, les erreurs fatales et non fatales produisaient des codes de retour <= 0 (dans les implémentations typiques, le code utilisateur traite toutes les erreurs comme non fatales), tandis que les codes de retour >0 indiquaient le succès.
