NOM

lit - Testeur Intégré LLVM

SYNOPSIS

lit [options] [tests]

DESCRIPTION

lit est un outil portable pour exécuter des suites de tests de style LLVM et Clang, résumer leurs résultats et indiquer les échecs. lit est conçu pour être un outil de test léger avec une interface utilisateur aussi simple que possible.

lit doit être exécuté avec un ou plusieurs tests spécifiés sur la ligne de commande. Les tests peuvent être des fichiers de test individuels ou des répertoires dans lesquels rechercher des tests (voir DÉCOUVERTE DES TESTS).

Chaque test spécifié sera exécuté (potentiellement simultanément) et une fois que tous les tests auront été exécutés, lit affichera des informations récapitulatives sur le nombre de tests qui ont réussi ou échoué (voir RÉSULTATS DE STATUT DE TEST). Le programme lit s'exécutera avec un code de sortie non nul si des tests échouent.

Par défaut, lit utilisera un affichage de progression succinct et n'affichera des informations récapitulatives que pour les échecs de tests. Voir OPTIONS DE SORTIE pour les options contrôlant l'affichage de la progression et la sortie de lit.

lit inclut également un certain nombre d'options pour contrôler l'exécution des tests (les fonctionnalités spécifiques peuvent dépendre du format de test particulier). Voir OPTIONS D'EXÉCUTION pour plus d'informations.

Enfin, lit prend également en charge des options supplémentaires pour n'exécuter qu'un sous-ensemble des options spécifiées sur la ligne de commande. Voir OPTIONS DE SÉLECTION pour plus d'informations.

lit analyse les options de la variable d'environnement LIT_OPTS après avoir analysé les options de la ligne de commande. LIT_OPTS est principalement utile pour compléter ou remplacer les options de ligne de commande fournies à lit par les cibles check définies par le système de build d'un projet.

lit peut également lire des options à partir de fichiers de réponse spécifiés comme entrées à l'aide de la syntaxe @chemin/vers/fichier.rsp. Les arguments lus à partir d'un fichier doivent être un par ligne et sont traités comme s'ils se trouvaient au même endroit que l'argument référençant le fichier d'origine sur la ligne de commande. Un fichier de réponse peut référencer d'autres fichiers de réponse.

Les utilisateurs intéressés par l'architecture de lit ou par la conception d'une implémentation de test lit devraient consulter INFRASTRUCTURE DE LIT.

OPTIONS GÉNÉRALES

-h, --help
Affiche le message d'aide de lit et quitte.
--version
Affiche le numéro de version de lit et quitte.
-j N, --workers N
Exécute N tests en parallèle. Par défaut, ce nombre est choisi automatiquement pour correspondre au nombre de CPU disponibles détectés.
--config-prefix NOM
Recherche NOM.cfg et NOM.site.cfg lors de la recherche de suites de tests, au lieu de lit.cfg et lit.site.cfg.
-D NOM[=VALEUR], --param NOM[=VALEUR]
Ajoute un paramètre défini par l'utilisateur NOM avec la VALEUR donnée (ou une chaîne vide si non fournie). La signification et l'utilisation de ces paramètres dépendent de la suite de tests.

OPTIONS DE SORTIE

-q, --quiet
Supprime toute sortie, sauf les échecs de tests.
-s, --succinct
Affiche moins de sortie, par exemple n'affiche pas d'informations sur les tests qui réussissent. Affiche également une barre de progression, sauf si --no-progress-bar est spécifié.
-v, --verbose
Affiche plus d'informations sur les échecs de tests, par exemple la sortie complète du test au lieu du seul résultat du test.

Chaque commande est imprimée avant d'être exécutée. Cela peut être utile pour déboguer les échecs de tests, car la dernière commande imprimée est celle qui a échoué. De plus, lit insère 'RUN: à la ligne N' après chaque pipeline de commandes dans la sortie pour vous aider à localiser la ligne source de la commande défaillante.

-vv, --echo-all-commands
Alias obsolète pour -v.
-a, --show-all
Active -v, mais pour tous les tests et pas seulement pour les tests échoués.
-o CHEMIN, --output CHEMIN
Écrit les résultats des tests dans le chemin fourni.
--no-progress-bar
N'utilise pas la barre de progression basée sur curses.
--show-excluded
Affiche les tests exclus.
--show-skipped
Affiche les tests ignorés.
--show-unsupported
Affiche les tests non supportés.
--show-pass
Affiche les tests réussis.
--show-flakypass
Affiche les tests réussis avec réessai.
--show-xfail
Affiche les tests dont l'échec est attendu.

Lorsque cette option est activée, lit fournit également automatiquement une fonctionnalité "valgrind" qui peut être utilisée pour désactiver conditionnellement (ou s'attendre à un échec dans) certains tests.

--vg-leak
Lorsque --vg est utilisé, active les vérifications de fuites de mémoire. Lorsque cette option est activée, lit fournit également automatiquement une fonctionnalité "vg_leak" qui peut être utilisée pour désactiver conditionnellement (ou s'attendre à un échec dans) certains tests.
--vg-arg ARG
Lorsque --vg est utilisé, spécifie un argument supplémentaire à passer à valgrind lui-même.
--no-execute

--xunit-xml-output XUNIT_XML_OUTPUT

--report-failures-only

--run-directives RUN_DIRECTIVES
Spécifie une liste de directives de test à exécuter.
--config CONFIG
Chargez le fichier de configuration spécifié à la place de lit.cfg.
--site SITE
Chargez le fichier de configuration de site spécifié à la place de lit.site.cfg.

EXEMPLES

Exécuter tous les tests dans le répertoire courant et ses sous-répertoires avec la configuration par défaut :

lit .

Exécuter tous les tests du répertoire `test` avec une configuration et une configuration de site spécifiques :

lit -c test --config=my_config.cfg --site=my_site.cfg

Exécuter uniquement les tests qui correspondent à `foo` (et pas à `bar`) dans le répertoire `test`, en utilisant 8 workers :

lit -j 8 test -k foo -k~bar

Exécuter uniquement les tests pour lesquels les commandes du shell sont affichées :

lit -v test

RAPPORTS DE STATUT DE TEST

Les tests peuvent se terminer dans l'un des états suivants.

PASSED

Le test a réussi.

FAILED

Le test a échoué.

XPASS (EXPECTED FAILURE)

Le test était censé échouer, et il a échoué.

XFAIL (EXPECTED SUCCESS)

Le test était censé réussir, mais il a échoué.

UNSUPPORTED

Le test n'est pas supporté par la plateforme actuelle.

UNRESOLVED

Le test n'a pas pu être exécuté.

FLAKYPASS (PASSED AFTER RETRY)

Le test a échoué lors de sa première tentative, mais a réussi lors d'une tentative ultérieure.

SKIPPED

Le test a été explicitement ignoré (par exemple, en utilisant `# RUN: `).

EXCLUDED

Le test a été exclu (par exemple, en utilisant la directive `XFAIL`).

DÉCOUVERTE DES TESTS

lit découvre les tests en parcourant récursivement les répertoires spécifiés sur la ligne de commande. Pour chaque répertoire, il recherche un fichier de configuration lit.cfg ou un fichier de configuration de site lit.site.cfg. Si ces fichiers sont trouvés, ils sont utilisés pour configurer l'environnement de test. Les tests sont généralement nommés `test_*.py` ou `test-*.py`. Les fichiers Python peuvent contenir une directive spéciale RUN: qui spécifie les commandes à exécuter pour le test.

La partie la plus puissante de lit est son architecture, qui permet aux utilisateurs de définir des suites de tests complexes et portables. OPTIONS DE SÉLECTION

Par défaut, lit exécutera d'abord les tests échoués, puis exécutera les tests par ordre décroissant de temps d'exécution pour optimiser la concurrence. L'ordre d'exécution peut être modifié à l'aide de l'option --order.

Les données de temporisation sont stockées dans le test_exec_root dans un fichier nommé .lit_test_times.txt. Si ce fichier n'existe pas, alors lit recherche le fichier dans le test_source_root pour accélérer éventuellement les builds propres.

--max-tests N
Exécute au plus N tests puis termine.
--max-time N
Passe au plus N secondes (approximativement) à exécuter les tests puis termine. Notez que ce n'est pas un alias pour --timeout ; les deux sont des types de maximums différents.
--order {lexical,random,smart}
Définit l'ordre dans lequel les tests sont exécutés. Les valeurs prises en charge sont :
  • lexical - les tests seront exécutés dans l'ordre lexical selon le chemin du fichier de test. Cette option est utile lorsque un ordre de test prévisible est souhaité.
  • random - les tests seront exécutés dans un ordre aléatoire.
  • smart - les tests qui ont échoué précédemment seront exécutés en premier, puis les tests restants, tous par ordre décroissant de temps d'exécution. C'est la valeur par défaut car elle optimise la concurrence.
--shuffle
Exécute les tests dans un ordre aléatoire, et non pas échecs/plus lents en premier. Obsolète, utilisez --order à la place.
-i, --incremental
Exécute les tests échoués en premier (OBSOLÈTE : utilisez --order=smart).
--filter REGEXP
Exécute uniquement les tests dont le nom correspond à l'expression régulière spécifiée dans REGEXP. La variable d'environnement LIT_FILTER peut également être utilisée à la place de cette option, ce qui est particulièrement utile dans les environnements où l'appel à lit est effectué indirectement.
--filter-out REGEXP
Filtre les tests dont le nom correspond à l'expression régulière spécifiée dans REGEXP. La variable d'environnement LIT_FILTER_OUT peut également être utilisée à la place de cette option, ce qui est particulièrement utile dans les environnements où l'appel à lit est effectué indirectement.
--xfail LIST
Traite les tests dont le nom figure dans la liste séparée par des points-virgules LIST comme XFAIL. Cela peut être utile lorsque l'on ne souhaite pas modifier la suite de tests. La variable d'environnement LIT_XFAIL peut également être utilisée à la place de cette option, ce qui est particulièrement utile dans les environnements où l'appel à lit est effectué indirectement.

Un nom de test peut être spécifié comme un nom de fichier relatif au répertoire de la suite de tests. Par exemple :

LIT_XFAIL="affinity/kmp-hw-subset.c;offloading/memory_manager.cpp"

Dans ce cas, tous les tests suivants sont traités comme XFAIL :

libomp :: affinity/kmp-hw-subset.c
libomptarget :: nvptx64-nvidia-cuda :: offloading/memory_manager.cpp
libomptarget :: x86_64-pc-linux-gnu :: offloading/memory_manager.cpp

Alternativement, un nom de test peut être spécifié comme le nom complet du test rapporté dans la sortie LIT. Par exemple, nous pouvons ajuster l'exemple précédent pour ne pas traiter la version nvptx64-nvidia-cuda de offloading/memory_manager.cpp comme XFAIL :

LIT_XFAIL="affinity/kmp-hw-subset.c;libomptarget :: x86_64-pc-linux-gnu :: offloading/memory_manager.cpp"
--xfail-not LIST
Ne pas traiter les tests spécifiés comme XFAIL. La variable d'environnement LIT_XFAIL_NOT peut également être utilisée à la place de cette option. La syntaxe est la même que pour --xfail et LIT_XFAIL. --xfail-not et LIT_XFAIL_NOT remplacent toujours toutes les autres spécifications XFAIL, y compris un --xfail apparaissant plus tard sur la ligne de commande. L'objectif principal est de supprimer un résultat XPASS sans modifier un cas de test qui utilise la directive XFAIL.
--num-shards M
Divise l'ensemble des tests sélectionnés en M sous-ensembles de taille égale ou "shards", et n'en exécute qu'un seul. Doit être utilisé avec l'option --run-shard=N, qui sélectionne le shard à exécuter. La variable d'environnement LIT_NUM_SHARDS peut également être utilisée à la place de cette option. Ces deux options fournissent un mécanisme grossier pour partitionner de grandes suites de tests, pour une exécution parallèle sur des machines séparées (par exemple dans une grande ferme de tests).
--run-shard N
Sélectionne le shard à exécuter, en supposant que l'option --num-shards=M a été fournie. Les deux options doivent être utilisées ensemble, et la valeur de N doit être dans la plage 1..M. La variable d'environnement LIT_RUN_SHARD peut également être utilisée à la place de cette option.

lit se terminera avec un code de sortie de 1 s'il y a des échecs (voir RÉSULTATS DE STATUT DE TEST) et que --ignore-fail n'a pas été passé. Sinon, il se terminera avec le statut 0. INTRODUCTION

This document describes the lit testing tool, a generic testing infrastructure for C, C++, Objective-C, Objective-C++, and other languages. It is widely used by projects such as Clang, LLVM, LLD, and compiler-rt.

The main goal of lit is to provide a flexible, extensible, and portable testing infrastructure. lit is designed to be easily integrated into existing projects, and to allow tests to be written in a natural, readable way.

lit operates by discovering tests and executing them. The way tests are discovered and executed is defined by the project's testing configuration, which is specified in a lit.cfg file. The following sections describe the basic operation of lit, the test statuses it supports, and the infrastructure behind it.

Tests must exist inside some test suite. lit resolves the inputs specified on the command line to test suites by searching upwards from the input path until it finds a lit.cfg or lit.site.cfg file. These files serve as both a marker of test suites and as configuration files which lit loads in order to understand how to find and run the tests inside the test suite.

Once lit has mapped the inputs into test suites it traverses the list of inputs adding tests for individual files and recursively searching for tests in directories.

This behavior makes it easy to specify a subset of tests to run, while still allowing the test suite configuration to control exactly how tests are interpreted. In addition, lit always identifies tests by the test suite they are in, and their relative path inside the test suite. For appropriately configured projects, this allows lit to provide convenient and flexible support for out-of-tree builds.

TEST STATUS RESULTS

Each test ultimately produces one of the following eight results:

PASS

Le test a réussi.

FLAKYPASS

Le test a réussi après avoir été réexécuté plus d'une fois. Ceci ne s'applique qu'aux tests contenant une annotation ALLOW_RETRIES:.

XFAIL

Le test a échoué, mais c'est attendu. Ceci est utilisé pour les formats de test qui permettent de spécifier qu'un test ne fonctionne pas actuellement, mais que l'on souhaite le conserver dans la suite de tests.

XPASS

Le test a réussi, mais il était prévu qu'il échoue. Ceci est utilisé pour les tests qui étaient spécifiés comme devant échouer, mais qui réussissent maintenant (généralement parce que la fonctionnalité qu'ils testent était défectueuse et a été corrigée).

FAIL

Le test a échoué.

UNRESOLVED

Le résultat du test n'a pas pu être déterminé. Par exemple, cela se produit lorsque le test n'a pas pu être exécuté, que le test lui-même est invalide, ou que le test a été interrompu.

UNSUPPORTED

Le test n'est pas supporté dans cet environnement. Ceci est utilisé par les formats de test qui peuvent signaler des tests non supportés.

TIMEOUT

Le test a été exécuté, mais il a expiré avant d'avoir pu se terminer.

Les tests non résolus (UNRESOLVED), expirés (TIMEOUT), échoués (FAIL) et passés de manière inattendue (XPASS) sont considérés comme des échecs.

Selon le format du test, des informations supplémentaires sur son état peuvent être produites (généralement uniquement pour les échecs). Voir la section OPTIONS DE SORTIE pour plus d'informations.

LIT INFRASTRUCTURE

Cette section décrit l'architecture de test lit pour les utilisateurs intéressés par la création d'une nouvelle implémentation de test lit, ou par l'extension d'une existante.

lit proprement dit est principalement une infrastructure pour découvrir et exécuter des tests arbitraires, et pour exposer une interface unique et pratique à ces tests. lit lui-même ne sait pas comment exécuter les tests, plutôt cette logique est définie par les suites de tests.

TEST SUITES

Comme décrit dans DÉCOUVERTE DE TESTS, les tests sont toujours situés à l'intérieur d'une suite de tests. Les suites de tests servent à définir le format des tests qu'elles contiennent, la logique pour trouver ces tests, et toute information supplémentaire pour exécuter les tests.

lit identifie les suites de tests comme des répertoires contenant des fichiers lit.cfg ou lit.site.cfg (voir aussi --config-prefix). Les suites de tests sont découvertes initialement en parcourant récursivement la hiérarchie des répertoires pour tous les fichiers d'entrée passés sur la ligne de commande. Vous pouvez utiliser --show-suites pour afficher les suites de tests découvertes au démarrage.

Une fois qu'une suite de tests est découverte, son fichier de configuration est chargé. Les fichiers de configuration eux-mêmes sont des modules Python qui seront exécutés. Lorsque le fichier de configuration est exécuté, deux variables globales importantes sont prédéfinies :

lit_config

L'objet de configuration global lit (une instance LitConfig), qui définit les formats de test intégrés, les paramètres de configuration globaux et d'autres routines d'aide pour l'implémentation des configurations de test.

config

C'est l'objet de configuration (une instance TestingConfig) pour la suite de tests, que le fichier de configuration est censé peupler. Les variables suivantes sont également disponibles sur l'objet config, dont certaines doivent être définies par la configuration et d'autres sont facultatives ou prédéfinies :

name [obligatoire] Le nom de la suite de tests, pour être utilisé dans les rapports et les diagnostics.

test_format [obligatoire] L'objet de format de test qui sera utilisé pour découvrir et exécuter les tests dans la suite de tests. Généralement, il s'agira d'un format de test intégré disponible dans le module lit.formats.

test_source_root Le chemin du système de fichiers vers la racine de la suite de tests. Pour les compilations hors de l'arbre, c'est le répertoire qui sera analysé pour les tests.

test_exec_root Pour les compilations hors de l'arbre, le chemin vers la racine de la suite de tests à l'intérieur du répertoire d'objet. C'est là que les tests seront exécutés et les fichiers de sortie temporaires placés.

environment Un dictionnaire représentant l'environnement à utiliser lors de l'exécution des tests dans la suite.

standalone_tests Si vrai, marque un répertoire avec des tests attendus pour être exécutés de manière autonome. La découverte de tests est désactivée pour ce répertoire. lit.suffixes et lit.excludes doivent être vides lorsque cette variable est vraie.

suffixes Pour les formats de test lit qui analysent les répertoires à la recherche de tests, cette variable est une liste de suffixes pour identifier les fichiers de test. Utilisé par : ShTest.

substitutions Pour les formats de test lit qui substituent des variables dans un script de test, la liste des substitutions à effectuer. Utilisé par : ShTest.

unsupported Marque un répertoire non supporté, tous les tests à l'intérieur seront signalés comme non supportés. Utilisé par : ShTest.

parent La configuration parente, c'est l'objet de configuration pour le répertoire contenant la suite de tests, ou None.

root La configuration racine. C'est la configuration lit la plus haute dans le projet.

pipefail Normalement, un test utilisant un pipe shell échoue si l'une des commandes du pipe échoue. Si ce n'est pas souhaité, définir cette variable à faux fait échouer le test uniquement si la dernière commande du pipe échoue.

available_features Un ensemble de fonctionnalités qui peuvent être utilisées dans les directives XFAIL, REQUIRES, et UNSUPPORTED.

TEST DISCOVERY

Une fois que les suites de tests sont localisées, lit parcourt récursivement le répertoire source (en suivant test_source_root) à la recherche de tests. Lorsque lit entre dans un sous-répertoire, il vérifie d'abord si une suite de tests imbriquée est définie dans ce répertoire. Si c'est le cas, il charge cette suite de tests récursivement, sinon il instancie une configuration de test locale pour le répertoire (voir FICHIERS DE CONFIGURATION LOCAUX).

Les tests sont identifiés par la suite de tests dans laquelle ils sont contenus, et par le chemin relatif à l'intérieur de cette suite. Notez que le chemin relatif peut ne pas faire référence à un fichier réel sur le disque ; certains formats de test (comme GoogleTest) définissent des "tests virtuels" dont le chemin contient à la fois le chemin vers le fichier de test réel et un sous-chemin pour identifier le test virtuel.

LOCAL CONFIGURATION FILES

Lorsque lit charge un sous-répertoire dans une suite de tests, il instancie une configuration de test locale en clonant la configuration du répertoire parent --- la racine de cette chaîne de configuration sera toujours une suite de tests. Une fois la configuration de test clonée, lit recherche un fichier lit.local.cfg dans le sous-répertoire. S'il est présent, ce fichier sera chargé et pourra être utilisé pour spécialiser la configuration pour chaque répertoire individuel. Cette facilité peut être utilisée pour définir des sous-répertoires de tests optionnels, ou pour modifier d'autres paramètres de configuration --- par exemple, pour modifier le format de test, ou les suffixes qui identifient les fichiers de test.

SUBSTITUTIONS

lit permet de substituer des motifs dans les commandes RUN. Il fournit également l'ensemble de substitutions de base suivant, qui sont définies dans TestRunner.py :

Macro Substitution
%s chemin source (chemin vers le fichier en cours d'exécution)
%S répertoire source (répertoire du fichier en cours d'exécution)
%p identique à %S
%{pathsep} séparateur de chemin
%{fs-src-root} composant racine des chemins du système de fichiers pointant vers le checkout LLVM
%{fs-tmp-root} composant racine des chemins du système de fichiers pointant vers le répertoire temporaire du test
%{fs-sep} séparateur de chemin du système de fichiers
%t nom de fichier temporaire unique au test
%basename_t Le dernier composant de chemin de %t mais sans l'extension .tmp (déprécié, utilisez %{t:stem} à la place)
%T répertoire parent de %t (pas unique, déprécié, n'utilisez pas)

NAME

lit - LLVM Integrated Tester

SYNOPSIS

lit [options] [test-suite-path ...]

DESCRIPTION

lit is a portable test runner. It is designed to be used for testing LLVM tools and libraries, but it is general enough to be used for any testing project.

The test runner can operate in several modes, controlled by command line flags. The primary modes are:

  • Running tests in the specified test suite(s) and printing the results to standard output. This is the default mode.
  • Running tests and printing progress information to standard output.
  • Running tests and printing the test suite structure to standard output.

For more information see the General Options section.

GENERAL OPTIONS

These options control the overall behavior of lit.

-h, --help
Print a summary of options.
-o output_file
Write test results to output_file instead of standard output.
--param NAME=VALUE
Add a test suite parameter. This can be used to pass arbitrary parameters into the test suite. See LIT INFRASTRUCTURE for more information.
-j N, --threads=N
Use N threads to run tests. Defaults to the number of logical cores on the machine. Use 1 for sequential execution.
--no-progress-bar
Disable the dynamic progress bar shown when using the -j option.
--show-suites
Print the test suite structure and exit.
--show-unsupported
Print the list of unsupported tests and exit.
--version
Print the version of lit and exit.

OUTPUT OPTIONS

These options control the format and verbosity of the test output.

-v, --verbose
Produce verbose output. Shows all tests, not just failures.
--quiet
Suppress all output except for errors.
--succinct
Produce succinct output. Only print the test results themselves.
--simplify-output
Simplify the output. Suppresses the test name and progress information. Use this option if you want to parse the test output.
--path- திர VAR
Use VAR to rewrite test paths in the output. See LIT INFRASTRUCTURE for more information.

EXECUTION OPTIONS

These options control how tests are executed.

--run-fail
Run tests that are expected to fail, and vice versa. This is useful for testing that tests are correctly marked.
--max-failures=N
Stop running tests after N failures. Defaults to infinity.
--max-time=N
Stop running tests after N seconds. Defaults to infinity.
--shuffle
Randomly shuffle the tests before running them.
--reorder=file
Reorder tests according to the order given in file.
--resume=file
Resume a previous test run from the specified checkpoint file.
--save-restart=file
Save the current test run state to file for resumption later.

SELECTION OPTIONS

These options select which tests are run.

--filter=REGEX
Only run tests that match the given regular expression.
--not=REGEX
Do not run tests that match the given regular expression.
--exclude=REGEX
Do not run tests that match the given regular expression.
--run-subdir=DIR
Only run tests in the specified subdirectory.
--run-shard=ID/TOTAL
Run only a subset of the tests, specified by shard ID and total number of shards.

ADDITIONAL OPTIONS

These options are used for specific test runner functionalities.

--config-dir=DIR
Directory containing the user's configuration files.
--use-system-libedit
Use the system's libedit instead of the bundled version.
--no-system-libedit
Use the bundled libedit instead of the system's version.
--use-default-config
Use the default configuration file even if a user configuration file is present.
--no-default-config
Do not use the default configuration file.

EXIT STATUS

lit exits with one of the following values:

0
All tests passed.
1
One or more tests failed.
2
An error occurred during test execution (e.g., test command failed).
3
Some tests were unresolvable or unsupported.
4
Timeout occurred.

TEST STATUS RESULTS

The following test status codes are recognized:

PASS
The test passed.
FAIL
The test failed.
XPASS
The test was expected to fail, but passed.
XFAIL
The test was expected to fail and did fail.
UNRESOLVED
The test could not be run (e.g., required tools not found).
UNSUPPORTED
The test is not supported on the current platform.
IMPROVED
The test has improved compared to a previous run.
REGRESSED
The test has regressed compared to a previous run.

lit uses a flexible infrastructure for defining test suites. Test suites are typically defined using a lit.site.cfg or lit.cfg file. These files are Python scripts that are executed by lit.

The following substitutions are available in test suite configuration files:

%H %h but with the backslash replaced by a forward slash
%l The absolute path to the test's log directory.
%L %l but with the backslash replaced by a forward slash
%c The compile directory for the test.

TEST RUN OUTPUT FORMAT

The lit output for a test run conforms to the following schema, in both short and verbose modes (although in short mode no PASS lines will be shown). This schema has been chosen to be relatively easy to reliably parse by a machine (for example in buildbot log scraping), and for other tools to generate.

Each test result is expected to appear on a line that matches:

<result code>: <test name> (<progress info>)

where <result-code> is a standard test result such as PASS, FAIL, XFAIL, XPASS, UNRESOLVED, or UNSUPPORTED. The performance result codes of IMPROVED and REGRESSED are also allowed.

The <test name> field can consist of an arbitrary string containing no newline.

The <progress info> field can be used to report progress information such as (1/300) or can be empty, but even when empty the parentheses are required.

Should a test be allowed retries (see ALLOW_RETRIES: annotation) and it needed more than one attempt to succeed, then <progress info> is extended by this information:

, <num_attempts_made> of <max_allowed_attempts> attempts

Each test result may include additional (multiline) log information in the following format:

<log delineator> TEST '(<test name>)' <trailing delineator>
... log message ...
<log delineator>

where <test name> should be the name of a preceding reported test, <log delineator> is a string of "*" characters at least four characters long (the recommended length is 20), and <trailing delineator> is an arbitrary (unparsed) string.

The following is an example of a test run output which consists of four tests A, B, C, and D, and a log message for the failing test C:

PASS: A (1 of 4)
PASS: B (2 of 4)
FAIL: C (3 of 4)
******************** TEST 'C' FAILED ********************
Test 'C' failed as a result of exit code 1.
********************
PASS: D (4 of 4)

DEFAULT FEATURES

For convenience lit automatically adds available_features for some common use cases.

lit adds a feature based on the operating system being built on, for example: system-darwin, system-linux, etc. lit also automatically adds a feature based on the current architecture, for example target-x86_64, target-aarch64, etc.

When building with sanitizers enabled, lit automatically adds the short name of the sanitizer, for example: asan, tsan, etc.

To see the full list of features that can be added, see llvm/utils/lit/lit/llvm/config.py.
