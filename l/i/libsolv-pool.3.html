NOM

libsolv-pool - Objet pool de Libsolv

ATTRIBUTS PUBLICS

void *appdata

Un pointeur d'usage libre pour l'utilisateur de la bibliothèque. La libération du pool ignore simplement le pointeur.

Stringpool ss

Le pool de chaînes unifiées.

Reldep *rels

Le pool des dépendances de relation unifiées.

int nrels

Nombre de dépendances de relation allouées.

Repo **repos

Le tableau des pointeurs de dépôts, indexés par l'identifiant du dépôt.

int nrepos

Nombre d'éléments alloués dans le tableau des dépôts, c'est-à-dire la taille du tableau repos.

int urepos

Nombre d'éléments utilisés (c'est-à-dire non nuls) dans le tableau des dépôts.

Repo *installed

Pointeur vers le dépôt contenant les paquets installés. Vous pouvez lire cet attribut librement, mais vous devriez utiliser pool_set_installed() si vous souhaitez le modifier.

Solvable *solvables

Le tableau des objets Solvable.

int nsolvables

Nombre d'objets Solvable, c'est-à-dire la taille du tableau solvables. Notez que le tableau peut contenir des solvables libérés, dans ce cas, le pointeur du dépôt du solvable sera nul.

int disttype

Le type de distribution de votre système, par exemple DISTTYPE_DEB. Vous pouvez lire cet attribut librement, mais vous devriez utiliser pool_setdisttype() si vous souhaitez le modifier.

Id *whatprovidesdata

Stockage d'Id multi-usages contenant des tableaux terminés par zéro d'Id. pool_whatprovides() renvoie un décalage dans ces données.

Map *considered

Bitmap optionnel qui peut faire ignorer des solvables par la bibliothèque. Si une bitmap est définie, seuls les solvables dont le bit correspondant à leur Id est défini sont considérés comme utilisables.

int debugmask

Un masque qui définit quels événements de débogage doivent être signalés. pool_setdebuglevel() définit ce masque.

Datapos pos

Un objet stockant une position dans les données du dépôt. Des fonctions comme dataiterator_set_pos() définissent cet objet, l'accès aux données avec un Id de solvable pseudo SOLVID_POS l'utilise.

Queue pooljobs

Une file d'attente où les travaux du solveur fixes peuvent être stockés. Ces travaux sont automatiquement ajoutés lorsque solver_solve() est appelé, ils sont utiles pour stocker des données de configuration comme quels paquets doivent être installés en multiversion.

CRÉATION ET DESTRUCTION

Pool *pool_create();

Crée une nouvelle instance d'un pool.

void pool_free(Pool *pool);

Libère un pool et toutes les données qu'il contient, par exemple les solvables, les dépôts, les chaînes.

Fonctions

void pool_debug(Pool *pool, int type, const char *format, ...);

Signale un message du type type. Vous pouvez filtrer les messages de débogage en définissant un masque de débogage.

void pool_setdebuglevel(Pool *pool, int level);

Définit un masque de débogage prédéfini. Un niveau plus élevé signifie généralement plus de bits définis dans le masque, donc plus de messages sont affichés.

void pool_setdebugmask(Pool *pool, int mask);

Définit le masque de débogage pour filtrer les messages de débogage.

int pool_error(Pool *pool, int ret, const char *format, ...);

Définit la chaîne d'erreur du pool. La valeur ret est simplement utilisée comme valeur de retour de la fonction afin que vous puissiez écrire du code comme return pool_error(...);. Si le masque de débogage contient le bit SOLV_ERROR, pool_debug() est également appelé avec le message et le type SOLV_ERROR.

extern char *pool_errstr(Pool *pool);

Renvoie la chaîne d'erreur actuelle stockée dans le pool. Comme avec la valeur errno de libc, la chaîne n'est significative qu'après qu'une fonction a renvoyé une erreur.

void pool_setdebugcallback(Pool *pool, void (*debugcallback)(Pool *, void *data, int type, const char *str), void *debugcallbackdata);

Définit une fonction de rappel de débogage personnalisée. Au lieu d'écrire sur stdout ou stderr, la fonction de rappel sera appelée.

CONFIGURATION DU POOL

Constantes

DISTTYPE_RPM

Utilisé pour les systèmes qui utilisent rpm comme gestionnaire de paquets de bas niveau.

DISTTYPE_DEB

Utilisé pour les systèmes qui utilisent dpkg comme gestionnaire de paquets de bas niveau.

DISTTYPE_ARCH

Utilisé pour les systèmes qui utilisent le gestionnaire de paquets Arch Linux.

DISTTYPE_HAIKU

Utilisé pour les systèmes qui utilisent des paquets Haiku.

POOL_FLAG_PROMOTEEPOCH

Promeut l'époque de la dépendance fournisseuse à la dépendance demanderesse si elle ne contient pas d'époque. Utilisé à une certaine époque dans les anciennes versions de rpm, les systèmes modernes n'en ont jamais besoin.

POOL_FLAG_FORBIDSELFCONFLICTS

Interdit l'installation de paquets qui entrent en conflit avec eux-mêmes. Debian autorise toujours les paquets qui se auto-conflisent, rpm les interdisait mais a récemment switched pour les autoriser également.

POOL_FLAG_OBSOLETEUSESPROVIDES

Fait correspondre le type de dépendance obsolète avec les fournisseuses au lieu de seulement le nom et la version des paquets. De très anciennes versions de rpm utilisaient le nom/version, puis cela a été changé en fournisseuses et plus tard re-changé en seulement nom/version.

POOL FLAGS

Constants

POOL_FLAG_OBSOLETEONLYPROVIDED

By default, packages obsoleting other packages remove all packages with the same name. rpm-5 switched to also removing packages providing the same name.

POOL_FLAG_OBSOLETEUSESCOLORS

Rpm's multilib implementation (used in RedHat and Fedora) distinguishes between 32bit and 64bit packages (the terminology is that they have a different color). If obsoleteusescolors is set, packages with different colors will not obsolete each other.

POOL_FLAG_IMPLICITOBSOLETEUSESCOLORS

Same as POOL_FLAG_OBSOLETEUSESCOLORS, but used to find out if packages of the same name can be installed in parallel. For current Fedora systems, POOL_FLAG_OBSOLETEUSESCOLORS should be false and POOL_FLAG_IMPLICITOBSOLETEUSESCOLORS should be true (this is the default if FEDORA is defined when libsolv is compiled).

POOL_FLAG_NOINSTALLEDOBSOLETES

New versions of rpm consider the obsoletes of installed packages when checking for dependency, thus you may not install a package that is obsoleted by some other installed package, unless you also erase the other package.

POOL_FLAG_HAVEDISTEPOCH

Mandriva added a new field called distepoch that gets checked in version comparison if the epoch/version/release of two packages are the same.

POOL_FLAG_NOOBSOLETESMULTIVERSION

If a package is installed in multiversionmode, rpm used to ignore both the implicit obsoletes and the obsolete dependency of a package. This was changed to ignoring just the implicit obsoletes, thus you may install multiple versions of the same name, but obsoleted packages still get removed.

POOL_FLAG_ADDFILEPROVIDESFILTERED

Make the addfileprovides method only add files from the standard locations (i.e. the “bin” and “etc” directories). This is useful if you have only few packages that use non-standard file dependencies, but you still want the fast speed that addfileprovides() generates.

Functions

int pool_setdisttype(Pool *pool, int disttype);

Set the package type of your system. The disttype is used for example to define package comparison semantics. Libsolv's default disttype should match the package manager of your system, so you only need to use this function if you want to use the library to solve packaging problems for different systems. The Function returns the old disttype on success, and -1 if the new disttype is not supported. Note that any pool_setarch and pool_setarchpolicy calls need to come after the pool_setdisttype call, as they make use of the noarch/any/all architecture id.

int pool_set_flag(Pool *pool, int flag, int value);

Set a flag to a new value. Returns the old value of the flag.

int pool_get_flag(Pool *pool, int flag);

Get the value of a pool flag. See the constants section about the meaning of the flags.

void pool_set_rootdir(Pool *pool, const char *rootdir);

Set a specific root directory. Some library functions support a flag that tells the function to prepend the rootdir to file and directory names.

const char *pool_get_rootdir(Pool *pool);

Return the current value of the root directory.

char *pool_prepend_rootdir(Pool *pool, const char *dir);

Prepend the root directory to the dir argument string. The returned string has been newly allocated and needs to be freed after use.

char *pool_prepend_rootdir_tmp(Pool *pool, const char *dir);

Same as pool_prepend_rootdir, but uses the pool's temporary space for allocation.

void pool_set_installed(Pool *pool, Repo *repo);

Set which repository should be treated as the "installed" repository, i.e. the one that holds information about the installed packages.

void pool_set_languages(Pool *pool, const char **languages, int nlanguages);

Set the language of your system. The library provides lookup functions that return localized strings, for example for package descriptions. You can set an array of languages to provide a fallback mechanism if one language is not available.

void pool_setarch(Pool *pool, const char *arch);

Set the architecture of your system. The architecture is used to determine which packages are installable and which packages cannot be installed. The arch argument is normally the "machine" value of the "uname" system call.

void pool_setarchpolicy(Pool *, const char *);

Set the architecture policy for your system. This is the general version of pool_setarch (in fact pool_setarch calls pool_setarchpolicy internally). See the section about architecture policies for more information.

void pool_addvendorclass(Pool *pool, const char **vendorclass);

Add a new vendor equivalence class to the system. A vendor equivalence class defines if an installed package of one vendor can be replaced by a package coming from a different vendor. The vendorclass argument must be a NULL terminated array of strings. See the section about vendor policies for more information.

void pool_setvendorclasses(Pool *pool, const char **vendorclasses);

Set all allowed vendor equivalences. The vendorclasses argument must be an NULL terminated array consisting of all allowed classes concatenated. Each class itself must be NULL terminated, thus the last class ends with two NULL elements, one to finish the class and one to finish the list of classes.

void pool_set_custom_vendorcheck(Pool *pool, int (*vendorcheck)(Pool *, Solvable *, Solvable *));

Define a custom vendor check mechanism. You can use this if libsolv's internal vendor equivalence class mechanism does not match your needs.

void pool_setloadcallback(Pool *pool, int (*cb)(Pool *, Repodata *, void *), void *loadcbdata);

Define a callback function that gets called when repository metadata needs to be loaded on demand. See the section about on demand loading in the libsolv-repodata manual.

void pool_setnamespacecallback(Pool *pool, Id (*cb)(Pool *, void *, Id, Id), void *nscbdata);

Define a callback function to implement custom namespace support. See the section about namespace dependencies.

ID POOL MANAGEMENT

Constants

ID_EMPTY

The Id of the empty string, it is always Id 1.

REL_LT

Represents a "<" relation.

REL_EQ

Represents a "=" relation.

REL_GT

Represents a ">" relation. You can use combinations of REL_GT, REL_EQ, and REL_LT or-ed together to create any relation you like.

REL_AND

A boolean AND operation, the "name" and "evr" parts of the relation can be two sub-dependencies. Packages must match both parts of the dependency.

REL_OR

A boolean OR operation, the "name" and "evr" parts of the relation can be two sub-dependencies. Packages can match any part of the dependency.

REL_WITH

Like REL_AND, but packages must match both dependencies simultaneously. See the section about boolean dependencies about more information.

REL_NAMESPACE

A special namespace relation. See the section about namespace dependencies for more information.

REL_ARCH

An architecture filter dependency. The "name" part of the relation is a sub-dependency, the "evr" part is the Id of an architecture that the matching packages must have (note that this is an exact match ignoring architecture policies).

REL_FILECONFLICT

An internal file conflict dependency used to represent file conflicts. See the pool_add_fileconflicts_deps() function.

REL_COND

A conditional dependency, the "name" sub-dependency is only considered if the "evr" sub-dependency is fulfilled. See the section about boolean dependencies about more information.

REL_UNLESS

A conditional dependency, the "name" sub-dependency is only considered if the "evr" sub-dependency is not fulfilled. See the section about boolean dependencies about more information.

REL_COMPAT

A compat dependency used in Haiku to represent version ranges. The "name" part is the actual version, the "evr" part is the backwards compatibility version.

REL_KIND

A pseudo dependency that limits the solvables to a specific kind. The kind is expected to be a prefix of the solvable name, e.g. "patch:foo" would be of kind "patch". "REL_KIND" is only supported in the selection functions.

REL_MULTIARCH

A debian multiarch annotation. The most common value for the "evr" part is "any".

REL_ELSE

The else part of a "REL_COND" or "REL_UNLESS" dependency. See the section about boolean dependencies.

REL_ERROR

An illegal dependency. This is useful to encode dependency parse errors.

Functions

FONCTIONS POOL

Id pool_str2id(Pool *pool, const char *str, int create);

Ajoute une chaîne au pool de chaînes unifiées, retournant l'Id de la chaîne. Si create est zéro, de nouvelles chaînes ne seront pas ajoutées au pool, l'Id 0 sera retourné à la place.

Id pool_strn2id(Pool *pool, const char *str, unsigned int len, int create);

Identique à pool_str2id, mais seuls len caractères de la chaîne sont utilisés. Ceci peut être utilisé pour ajouter des sous-chaînes au pool.

Id pool_rel2id(Pool *pool, Id name, Id evr, int flags, int create);

Crée une dépendance relationnelle à partir d'autres dépendances, name et evr, et un flag. Voir les constantes REL_ pour les flags supportés. Comme avec pool_str2id, create définit si de nouvelles dépendances seront ajoutées ou si l'Id zéro sera retourné à la place.

Id pool_id2langid(Pool *pool, Id id, const char *lang, int create);

Attache un suffixe de langue à un Id de chaîne. Cette fonction peut être utilisée pour créer des Ids de nom de clé linguistiques à partir de noms de clés, elle est fonctionnellement équivalente à la conversion de l'argument id en une chaîne, à l'ajout d'un caractère “:” et de l'argument lang à la chaîne, puis à la reconversion du résultat en un Id.

const char *pool_id2str(const Pool *pool, Id id);

Convertit un Id en une chaîne. Si l'Id est un Id relationnel, la partie “name” sera convertie.

const char *pool_id2rel(const Pool *pool, Id id);

Retourne la chaîne de relation d'un Id relationnel. Retourne une chaîne vide si l'Id passé n'est pas une relation.

const char *pool_id2evr(const Pool *pool, Id id);

Retourne la partie “evr” d'un Id relationnel sous forme de chaîne. Retourne une chaîne vide si l'Id passé n'est pas une relation.

const char *pool_dep2str(Pool *pool, Id id);

Convertit un Id en une chaîne. Si l'Id passé appartient à une relation, une chaîne représentant la relation est retournée. Notez que dans ce cas, la chaîne est allouée dans l'espace temporaire du pool.

void pool_freeidhashes(Pool *pool);

Libère les tables de hachage utilisées pour unifier les chaînes et les relations. Vous pouvez utiliser cette fonction pour économiser de la mémoire si vous savez que vous ne créerez plus de nouvelles chaînes et relations.

FONCTIONS SOLVABLE

Solvable *pool_id2solvable(const Pool *pool, Id p);

Convertit un Id de solvable en un pointeur vers les données du solvable. Notez que le pointeur peut devenir invalide si de nouveaux solvables sont créés ou si d'anciens solvables sont supprimés, car le tableau stockant tous les solvables peut être réalloué.

Id pool_solvable2id(const Pool *pool, Solvable *s);

Convertit un pointeur vers les données du solvable en un Id de solvable.

const char *pool_solvid2str(Pool *pool, Id p);

Retourne une chaîne représentant le solvable avec l'Id p. La chaîne sera une représentation canonique du solvable, généralement une combinaison du nom, de la version et de l'architecture.

const char *pool_solvable2str(Pool *pool, Solvable *s);

Identique à pool_solvid2str, mais au lieu de l'Id, un pointeur vers le solvable est passé.

MATCHING DES DÉPENDANCES

Constantes

EVRCMP_COMPARE

Compare toutes les parties de la version, traite les parties manquantes comme des chaînes vides.

EVRCMP_MATCH_RELEASE

Un mode spécial pour le matching de chaînes de version rpm. Si une version manque une partie de release, elle correspond à toutes les releases. Dans ce cas, les valeurs spéciales “-2” et “2” sont retournées, en fonction de laquelle des deux versions n'avait pas de partie de release.

EVRCMP_MATCH

Un match générique, les parties manquantes correspondent toujours.

EVRCMP_COMPARE_EVONLY

Ne compare que les parties epoch et version, ignore la partie release.

Fonctions

int pool_evrcmp(const Pool *pool, Id evr1id, Id evr2id, int mode);

Compare deux Ids de version, retourne -1 si la première version est inférieure à la deuxième version, 0 si elles sont identiques, et 1 si la première version est supérieure à la deuxième.

int pool_evrcmp_str(const Pool *pool, const char *evr1, const char *evr2, int mode);

Identique à pool_evrcmp(), mais utilise des chaînes au lieu d'Ids.

int pool_evrmatch(const Pool *pool, Id evrid, const char *epoch, const char *version, const char *release);

Fait correspondre un Id de version avec un epoch, une version et une chaîne de release. Passer NULL signifie que la partie doit correspondre à tout.

int pool_match_dep(Pool *pool, Id d1, Id d2);

Retourne “1” si la dépendance d1 (le fournisseur) correspond à la dépendance d2, sinon “0” est retourné. Pour que deux dépendances correspondent, les parties “name” doivent correspondre et la plage de versions décrite par les parties “evr” doit se chevaucher.

int pool_match_nevr(Pool *pool, Solvable *s, Id d);

Similaire à pool_match_dep, mais le fournisseur est la dépendance "auto-fournit" du Solvable s, c'est-à-dire la dépendance “s→name = s→evr”.

int pool_satisfieddep_map(Pool *pool, const Map *map, Id dep);

Retourne “1” si la dépendance dep est satisfaite par les paquets spécifiés dans map, sinon “0” est retourné.

INDEX WHATPROVIDES

void pool_createwhatprovides(Pool *pool);

Crée un index qui mappe les Ids de dépendances à des ensembles de paquets qui fournissent la dépendance.

void pool_freewhatprovides(Pool *pool);

Libère l'index whatprovides pour économiser de la mémoire.

Id pool_whatprovides(Pool *pool, Id d);

Retourne un décalage dans le tableau whatprovidesdata du Pool. Les solvables avec les Ids stockés à partir de ce décalage fournissent la dépendance d. La liste des solvables est terminée par zéro.

Id *pool_whatprovides_ptr(Pool *pool, Id d);

Au lieu de retourner le décalage, retourne le pointeur vers les Ids stockés à ce décalage. Notez que ce pointeur a une durée de validité très limitée, car tout appel qui ajoute de nouvelles valeurs à la zone whatprovidesdata peut réallouer le tableau.

Id pool_queuetowhatprovides(Pool *pool, Queue *q);

Ajoute le contenu de la Queue q à la fin du tableau whatprovidesdata, retournant le décalage dans le tableau.

void pool_addfileprovides(Pool *pool);

Certains gestionnaires de paquets comme rpm permettent les dépendances sur des fichiers contenus dans d'autres paquets. Pour permettre à libsolv de gérer efficacement ces dépendances, vous devez appeler la méthode addfileprovides après avoir créé et lu tous les dépôts. Cette méthode analysera toutes les dépendances de noms de fichiers, puis tous les paquets pour trouver des correspondances de fichiers. Si un nom de fichier a été trouvé, il sera ajouté à la liste des provideurs du paquet correspondant.

void pool_addfileprovides_queue(Pool *pool, Queue *idq, Queue *idqinst);

Identique à pool_addfileprovides, mais les Ids ajoutés sont retournés dans deux Queues, idq pour tous les dépôts sauf celui contenant les paquets "installés", idqinst pour ce dernier. Ces informations peuvent être stockées dans la section méta des dépôts pour accélérer le chargement du dépôt la prochaine fois que addfileprovides est appelée.

void pool_set_whatprovides(pool, Id id, Id offset);

Définit manuellement une entrée dans l'index whatprovides. Vous ne ferez jamais cela pour les dépendances de paquets, car ces entrées sont créées en appelant la fonction pool_createwhatprovides(). Mais cette fonction est utile pour les fournitures d'espaces de noms si vous ne souhaitez pas utiliser un rappel d'espace de noms pour définir les fournitures de manière paresseuse. L'argument offset est un décalage dans le tableau whatprovides, vous pouvez donc utiliser “1” comme fausse valeur et “2” comme vraie valeur.

void pool_flush_namespaceproviders(Pool *pool, Id ns, Id evr);

Efface le cache des fournisseurs pour les dépendances d'espace de noms correspondant à l'espace de noms ns. Si l'argument evr n'est pas nul, la dépendance d'espace de noms pour cette dépendance exacte est effacée, sinon toutes les dépendances d'espace de noms correspondantes sont effacées. Voir la section sur les dépendances d'espace de noms pour plus d'informations.

void pool_add_fileconflicts_deps(Pool *pool, Queue *conflicts);

Certains gestionnaires de paquets comme rpm signalent des conflits lorsqu'une installation de paquet écrase un fichier d'un autre paquet installé avec un contenu différent. Comme les informations sur le contenu des fichiers ne sont pas stockées dans les métadonnées du dépôt, ces conflits ne peuvent être détectés qu'après le téléchargement des paquets. Libsolv fournit une fonction

pour vérifier de tels conflits, pool_findfileconflicts(). Si des conflits sont trouvés, ils peuvent être ajoutés comme spécial REL_FILECONFLICT fournit des dépendances, de sorte que le résolveur sera au courant du conflit lorsqu'il sera réexécuté.

FONCTIONS UTILITAIRES

char *pool_alloctmpspace(Pool *pool, int len);

Alloue de l'espace dans la zone d'espace temporaire du pool. Cet espace a une durée de vie limitée, il sera automatiquement libéré après un nombre fixe (actuellement 16) d'autres appels à pool_alloctmpspace().

void pool_freetmpspace(Pool *pool, const char *space);

Rend l'espace alloué avec pool_alloctmpspace au système. Vous n'êtes pas obligé d'utiliser cette fonction, car l'espace est automatiquement récupéré, mais elle peut être utile pour prolonger la durée de vie d'autres pointeurs vers la zone d'espace temporaire du pool.

const char *pool_bin2hex(Pool *pool, const unsigned char *buf, int len);

Convertit des données binaires en hexadécimal, retournant une chaîne allouée dans la zone d'espace temporaire du pool.

char *pool_tmpjoin(Pool *pool, const char *str1, const char *str2, const char *str3);

Joint trois chaînes et renvoie le résultat dans la zone d'espace temporaire du pool. Vous pouvez utiliser des arguments NULL si vous souhaitez simplement joindre moins de chaînes.

char *pool_tmpappend(Pool *pool, const char *str1, const char *str2, const char *str3);

Comme pool_tmpjoin(), mais si le premier argument est le dernier espace alloué dans la zone d'espace temporaire du pool, il sera remplacé par le résultat de la jointure et aucun nouvel emplacement d'espace temporaire ne sera utilisé. Ainsi, vous pouvez joindre plus de trois chaînes par une combinaison d'un appel à pool_tmpjoin() et de plusieurs appels à pool_tmpappend(). Notez que le pointeur str1 n'est plus utilisable après l'appel.

RECHERCHE DE DONNEES

Constantes

SOLVID_POS

Utilise la position des données stockée dans le pool pour la recherche au lieu de rechercher les données d'un solvable.

SOLVID_META

Utilise les données stockées dans la section méta d'un dépôt (ou zone de données de dépôt) au lieu de rechercher les données d'un solvable. Cette constante ne fonctionne pas pour les fonctions de recherche du pool, utilisez-la pour les fonctions de recherche du dépôt ou de la zone de données de dépôt à la place. Elle est simplement listée pour des raisons de complétude.

Fonctions

const char *pool_lookup_str(Pool *pool, Id solvid, Id keyname);

Renvoie la valeur de chaîne stockée sous l'attribut keyname dans le solvable solvid.

unsigned long long pool_lookup_num(Pool *pool, Id solvid, Id keyname, unsigned long long notfound);

Renvoie le nombre entier non signé de 64 bits stocké sous l'attribut keyname dans le solvable solvid. Si aucun tel nombre n'est trouvé, la valeur de l'argument notfound est renvoyée à la place.

Id pool_lookup_id(Pool *pool, Id solvid, Id keyname);

Renvoie l'Id stocké sous l'attribut keyname dans le solvable solvid.

int pool_lookup_idarray(Pool *pool, Id solvid, Id keyname, Queue *q);

Remplit la file d'attente q avec le contenu du tableau d'Ids stocké sous l'attribut keyname dans le solvable solvid. Renvoie “1” si un tableau a été trouvé, sinon la file d'attente sera vide et “0” sera renvoyé.

int pool_lookup_void(Pool *pool, Id solvid, Id keyname);

Renvoie “1” si une valeur vide est stockée sous l'attribut keyname dans le solvable solvid, sinon “0”.

const char *pool_lookup_checksum(Pool *pool, Id solvid, Id keyname, Id *typep);

Renvoie la somme de contrôle stockée sous l'attribut keyname dans le solvable solvid. Le type de la somme de contrôle sera renvoyé via le pointeur typep. Si aucune somme de contrôle n'est trouvée, NULL sera renvoyé et le type sera mis à zéro. Notez que le résultat est stocké dans la zone d'espace temporaire du Pool.

const unsigned char *pool_lookup_bin_checksum(Pool *pool, Id solvid, Id keyname, Id *typep);

Renvoie la somme de contrôle stockée sous l'attribut keyname dans le solvable solvid. Renvoie la somme de contrôle sous forme de données binaires, vous pouvez utiliser le type renvoyé pour calculer la longueur de la somme de contrôle. Aucune zone d'espace temporaire n'est nécessaire.

const char *pool_lookup_deltalocation(Pool *pool, Id solvid, unsigned int *medianrp);

Ceci est une fonction de recherche utilitaire pour renvoyer l'emplacement du delta pour un rpm delta. Comme les solvables ne peuvent pas stocker de deltas, vous devez utiliser SOLVID_POS comme argument et définir le pointeur datapos du Pool pour qu'il pointe vers des données rpm delta valides.

void pool_search(Pool *pool, Id solvid, Id keyname, const char *match, int flags, int (*callback)(void *cbdata, Solvable *s, Repodata *data, Repokey *key, KeyValue *kv), void *cbdata);

Effectue une recherche sur toutes les données stockées dans le pool. Vous pouvez limiter la zone de recherche en utilisant les arguments solvid et keyname. Les valeurs peuvent éventuellement être comparées à l'argument match, utilisez NULL si vous ne souhaitez pas cette comparaison. Voir la page de manuel de Dataiterator pour connaître les modes de correspondance possibles et l'argument flags. Pour toutes les valeurs (correspondantes), la fonction de rappel est appelée avec l'argument de rappel cbdata et les données décrivant la valeur.

FONCTIONS DE TRAITEMENT ET DE SELECTION

Un traitement consiste en deux Id, how et what. La partie how décrit l'action, les indicateurs du traitement et la méthode de sélection, tandis que la partie what est une entrée pour la sélection. Une sélection est une file d'attente composée de plusieurs traitements (donc le nombre d'éléments dans la file d'attente doit être un multiple de deux). Voir la page de manuel de Solver pour plus d'informations sur les traitements.

const char *pool_job2str(Pool *pool, Id how, Id what, Id flagmask);

Convertit un traitement en chaîne de caractères. Utile à des fins de débogage. Le flagmask peut être utilisé pour masquer les indicateurs du traitement, utilisez “0” si vous ne souhaitez pas voir de tels indicateurs, “-1” pour voir tous les indicateurs, ou une combinaison des indicateurs que vous souhaitez voir.

void pool_job2solvables(Pool *pool, Queue *pkgs, Id how, Id what);

Renvoie une liste de solvables sélectionnés par le traitement spécifié.

int pool_isemptyupdatejob(Pool *pool, Id how, Id what);

Renvoie “1” si le traitement est un traitement de mise à jour qui ne fonctionne avec aucun paquet installé, c'est-à-dire que le traitement est essentiellement une opération nulle. Vous pouvez l'utiliser pour transformer des traitements de mise à jour nuls en traitements d'installation (comme le font les gestionnaires de paquets comme “zypper”).

const char *pool_selection2str(Pool *pool, Queue *selection, Id flagmask);

Convertit une sélection en chaîne de caractères. Utile à des fins de débogage. Voir la fonction pool_job2str() pour l'argument flagmask.

POLITIQUES D'ARCHITECTURE

Une politique d'architecture définit une liste d'architectures qui peuvent être installées sur le système, ainsi que la relation entre elles (c'est-à-dire l'ordre). Les architectures peuvent être délimitées par trois caractères différents :

':'

Aucune relation entre les architectures. Un paquet d'une architecture ne peut pas être remplacé par un paquet d'une autre architecture.

'>'

La première architecture est meilleure que la seconde. Un paquet installé de la seconde architecture peut être remplacé par un paquet de la première architecture et vice versa. Le résolveur sélectionnera la meilleure architecture si les versions sont identiques.

'='

Les deux architectures sont librement échangeables. Utilisé pour définir des alias pour les architectures.

Un exemple serait 'x86_64:i686=athlon>i586'. Cela signifie que les paquets x86_64 ne peuvent être remplacés que par d'autres paquets x86_64, les paquets i686 peuvent être remplacés par des paquets i686 et i586 (mais les paquets i686 seront préférés) et athlon est un autre nom pour l'architecture i686.

Vous pouvez désactiver les vérifications de remplacement d'architecture avec l'indicateur SOLVER_FLAG_ALLOW_ARCHCHANGE du résolveur.

POLITIQUES DE VENDEUR

Différents vendeurs compilent souvent des paquets avec des fonctionnalités différentes, donc Libsolv ne remplace les paquets installés d'un vendeur que par des paquets provenant du même vendeur. De plus, alors que la version d'un paquet est normalement définie par le projet en amont, la partie release de la version est définie par

libsolv-pool.3.fr man page

POLITIQUES DE FOURNISSEUR

Les politiques de fournisseur sont utilisées pour autoriser le remplacement de paquets installés par des paquets de fournisseurs différents dans des conditions définies. Ceci est principalement utilisé pour les distributions, où un paquet de base peut être fourni par différents fournisseurs, par exemple, libsolv gère une politique pour l'libsolv-dev.

La politique de remplacement de fournisseur est configurée en définissant des classes d'équivalence de fournisseurs. Les paquets d'un fournisseur peuvent être remplacés par des paquets de tous les autres fournisseurs appartenant à la même classe d'équivalence.

Les classes d'équivalence de fournisseurs sont définies via SOLVER_ADD_VENDORCLASS. Par défaut, chaque fournisseur a sa propre classe, par conséquent, le remplacement de fournisseur n'est pas autorisé.

Le fournisseur est déterminé par la chaîne SOLVABLE_VENDOR stockée dans chaque solvable. Parfois, un fournisseur change de nom, ou plusieurs fournisseurs forment un groupe qui coordonne la construction de leurs paquets. libsolv offre donc un moyen de définir que des groupes de fournisseurs sont compatibles. Vous le faites en définissant des classes d'équivalence de fournisseurs : les paquets d'un fournisseur d'une classe peuvent être remplacés par des paquets de tous les autres fournisseurs de la classe.

Il peut y avoir plusieurs classes d'équivalence. L'ensemble des changements de fournisseur autorisés pour un paquet installé est calculé en construisant l'union de toutes les classes d'équivalence auxquelles le fournisseur du paquet installé appartient.

Vous pouvez désactiver les vérifications de remplacement de fournisseur avec le drapeau SOLVER_FLAG_ALLOW_VENDORCHANGE du Solver.

DEPENDANCES BOOLEENNES

Les dépendances booléennes permettent de construire des expressions complexes à partir de dépendances simples. Notez qu'en fonction du gestionnaire de paquets, seul un sous-ensemble de celles-ci peut être utile. Par exemple, Debian ne permet actuellement qu'une expression « OU ».

REL_OR

L'expression est vraie si la première ou la seconde dépendance est vraie. Ceci est utile pour les dépendances de paquets comme « Requires », où vous pouvez spécifier qu'un des paquets doit être installé.

REL_AND

L'expression est vraie si les deux dépendances sont vraies. Les paquets satisfaisant les dépendances peuvent être différents, c'est-à-dire « Supplements: perl REL_AND python » est vrai si un paquet fournissant perl et un paquet fournissant python sont installés.

REL_WITH

L'expression est vraie si les deux dépendances sont vraies et sont satisfaites par le même paquet. Ainsi, « Supplements: perl REL_WITH python » ne serait vrai que si un paquet est installé qui fournit les deux dépendances (une sorte d'interpréteur multi-langages).

REL_COND

L'expression est vraie si la première dépendance est vraie ou la seconde dépendance est fausse. « A REL_COND B » est équivalent à « A REL_OR (NON B) » (sauf que libsolv n'expose pas « NON »).

REL_UNLESS

L'expression est vraie si la première dépendance est vraie et la seconde dépendance est fausse. « A REL_UNLESS B » est équivalent à « A REL_AND (NON B) » (sauf que libsolv n'expose pas « NON »).

REL_ELSE

La partie « sinon » d'une dépendance « REL_COND » ou « REL_UNLESS ». Elle doit se trouver directement dans la partie evr de la condition, par exemple « foo REL_COND (bar REL_ELSE baz) ». Pour « REL_COND », ceci est équivalent à écrire « (foo REL_COND bar) REL_AND (bar REL_OR baz) ». Pour « REL_UNLESS », ceci est équivalent à écrire « (foo REL_UNLESS bar) REL_OR (bar REL_AND baz) ».

Chaque sous-dépendance d'une dépendance booléenne peut à son tour être une dépendance booléenne, vous pouvez donc les chaîner pour créer des dépendances complexes.

DEPENDANCES DE NAMESPACE

Les dépendances de namespace peuvent être utilisées pour implémenter des dépendances sur des attributs externes à libsolv. Un exemple serait une dépendance sur la langue définie par l'utilisateur. Ces types de dépendances sont généralement utilisés uniquement pour les dépendances « Conflicts » ou « Supplements », car le gestionnaire de paquets sous-jacent ne sait pas comment les gérer.

Si la bibliothèque a besoin d'évaluer une dépendance de namespace, elle appelle la fonction de rappel de namespace définie dans le pool. La fonction de rappel peut renvoyer un ensemble de paquets qui « fournissent » la dépendance. Si la dépendance est fournie par le système, l'ensemble renvoyé doit se composer uniquement du solvable système (ID de solvable 1).

L'ensemble de paquets renvoyé doit être renvoyé sous forme de décalage dans le tableau whatprovidesdata. Vous pouvez utiliser la fonction pool_queuetowhatprovides pour convertir une file d'attente en un tel décalage. Pour faciliter la programmation de la fonction de rappel, les valeurs de retour « 0 » et « 1 » ne sont pas interprétées comme des décalages. « 0 » signifie qu'aucun paquet ne se trouve dans l'ensemble de retour, « 1 » signifie que seul le solvable système se trouve dans l'ensemble.

L'ensemble renvoyé est mis en cache, de sorte que pour chaque dépendance de namespace, le rappel n'est appelé qu'une seule fois. Si vous avez besoin de vider le cache (peut-être parce que l'utilisateur a sélectionné une autre langue), utilisez la fonction pool_flush_namespaceproviders().
