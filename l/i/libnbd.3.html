NOM

libnbd - bibliothèque cliente du protocole Network Block Device (NBD) en espace utilisateur

SYNOPSIS

#include <libnbd.h>
struct nbd_handle *nbd;
char buf[512];
if ((nbd = nbd_create ()) == NULL ||
    nbd_connect_tcp (nbd, "serveur.example.com", "nbd") == -1 ||
    nbd_pread (nbd, buf, sizeof buf, 0, 0) == -1)
  fprintf (stderr, "%s\n", nbd_get_error ());
  nbd_close (nbd);
  exit (EXIT_FAILURE);
}
nbd_close (nbd);
 cc prog.c -o prog -lnbd
ou :
 cc prog.c -o prog `pkg-config libnbd --cflags --libs`

DESCRIPTION

Network Block Device (NBD) est un protocole réseau permettant d'accéder à des périphériques bloc sur le réseau. Les périphériques bloc sont des disques durs et des éléments qui se comportent comme des disques durs, tels que des images disque et des machines virtuelles.

Libnbd est une bibliothèque cliente pour le protocole NBD qui peut accéder à la plupart des fonctionnalités de NBD tout en étant simple à utiliser et puissante.

Cette page de manuel donne un aperçu de libnbd, en utilisant C comme exemple, mais la bibliothèque est disponible dans d'autres langages de programmation.

HANDLE

Pour utiliser l'API, vous devez d'abord ouvrir un handle en appelant nbd_create(3) (ou son équivalent dans d'autres langages) :

struct nbd_handle *nbd;
nbd = nbd_create ();

Cela crée et renvoie un handle, qui est associé à une connexion à un serveur NBD, initialement non connectée.

Chaque handle est une machine à états complexe qui peut être dans des états tels que créé, connecté à un serveur distant, en phase de négociation, inactif et prêt à émettre des commandes, ou occupé à envoyer ou recevoir des commandes.

Les handles ont un nom utilisé dans les messages de débogage. Le nom est normalement généré ("nbd1", "nbd2", etc.) mais vous pouvez définir un nom convivial avec nbd_set_handle_name(3). Il y a également un champ privé dans le handle pour l'utilisation par l'application, voir nbd_set_private_data(3).

Lorsque vous avez terminé avec le handle, vous devez appeler nbd_close(3) qui ferme le socket sous-jacent (si nécessaire) et libère toutes les ressources associées.

API SYNCHRONE VS ASYNCHRONE

Il existe deux niveaux d'API disponibles. Une API synchrone de haut niveau simple vous permet de donner au handle des instructions de haut niveau comme “connecte-toi au serveur”, “lis un bloc”, “écris un bloc”, etc. Chacune de ces fonctions s'exécute jusqu'à son achèvement, bloquant le thread courant avant de retourner. Une API asynchrone plus compliquée, de bas niveau et non bloquante est également disponible où vous pouvez vous intégrer avec poll(2) ou une autre boucle principale.

Vous pouvez mélanger librement les deux API sur le même handle. Vous pouvez également appeler des API sur un seul handle depuis plusieurs threads. Les appels API uniques sur le handle sont atomiques — ils prennent un verrou sur le handle pendant leur exécution ou sont prudents pour accéder aux champs du handle de manière atomique.

Libnbd ne crée pas ses propres threads.

UTILISATION DE L'API SYNCHRONE (« HAUT NIVEAU »)

C'est la manière la plus simple d'utiliser l'API, avec le inconvénient potentiel que chaque fonction libnbd bloque jusqu'à ce qu'elle soit terminée.

Créez un handle et connectez-vous au serveur :

struct nbd_handle *nbd;
nbd = nbd_create ();
if (!nbd) {
  fprintf (stderr, "%s\n", nbd_get_error ());
  nbd_close (nbd);
  exit (EXIT_FAILURE);
}
if (nbd_connect_tcp (nbd, "serveur.example.com", "nbd") == -1) {
  fprintf (stderr, "%s\n", nbd_get_error ());
  nbd_close (nbd);
  exit (EXIT_FAILURE);
}

Lisez le premier secteur (512 octets) depuis l'export NBD :

char buf[512];
if (nbd_pread (nbd, buf, sizeof buf, 0, 0) == -1) {
  fprintf (stderr, "%s\n", nbd_get_error ());
  nbd_close (nbd);
  exit (EXIT_FAILURE);
}

Fermez le handle :

nbd_close (nbd);

Vous pouvez appeler l'API de haut niveau depuis plusieurs threads, mais chaque appel API libnbd prend un verrou sur le handle et donc les commandes ne s'exécuteront pas en parallèle.

UTILISATION DE L'API ASYNCHRONE (« BAS NIVEAU »)

L'API de bas niveau est utile si vous souhaitez utiliser libnbd dans du code non bloquant ; ou si vous souhaitez émettre des commandes en parallèle depuis plusieurs threads ; ou si vous avez besoin de plus de contrôle, notamment pour avoir plusieurs commandes en cours sur une seule connexion.

Pour utiliser l'API de bas niveau, vous devrez vous intégrer avec poll(2) ou une autre « boucle principale » telle que la boucle d'événements principale de GLib.

Émission de commandes asynchrones

Utilisez les variantes "nbd_aio_*" pour émettre des commandes de manière asynchrone (sans attendre que la commande se termine avant de retourner). Par exemple, la variante asynchrone de nbd_pread(3) est :

int64_t cookie;
cookie = nbd_aio_pread (nbd, buf, sizeof buf,
                        NBD_NULL_COMPLETION, 0);
if (cookie == -1) {
  fprintf (stderr, "%s\n", nbd_get_error ());
  nbd_close (nbd);
  exit (EXIT_FAILURE);
}

Il y a plusieurs points à noter ici :

  • Cela ne fait que démarrer la commande. La commande est (généralement) toujours en cours lorsque l'appel retourne succès, où vous devez vous appuyer sur les appels API ultérieurs pour connaître le résultat final de la commande et déclencher les rappels restants. Cependant, vous devez également être capable de gérer le cas où la charge système permet à la machine à états de progresser suffisamment pour invoquer les rappels avant le retour de l'API asynchrone.
  • Un tampon ("buf") a été attribué pour collecter le résultat de la lecture, mais il n'est pas garanti d'être rempli avec des données tant que la commande n'est pas terminée (voir les exemples ci-dessous). Le tampon ne doit pas être libéré tant que la commande n'a pas fini de s'exécuter.
  • Vous pouvez émettre plusieurs commandes sur le même handle en même temps.
  • Un cookie est retourné qui identifie cette commande dans les appels ultérieurs. Le cookie est unique (par handle libnbd) et ≥ 1.
  • Vous pouvez enregistrer une fonction qui sera appelée lorsque la commande se termine, voir "Callbacks de complétion" ci-dessous. Dans ce cas, nous avons spécifié un callback de complétion nul. Si un callback de complétion est spécifié, il ne sera appelé que si la commande asynchrone a été soumise avec succès (si l'API asynchrone elle-même retourne une erreur, il n'y a rien de plus à compléter).

Socket et direction

Chaque handle libnbd a un socket associé (une fois qu'il a commencé la connexion). Vous pouvez lire le descripteur de fichier du socket en utilisant :

int fd = nbd_aio_get_fd (nbd);

Le socket est non bloquant. Entre les appels à libnbd, il est dans la condition « bloquerait » (would block). Vous pouvez savoir si libnbd attend de lire ou d'écrire sur le socket ensuite en appelant :

int dir = nbd_aio_get_direction (nbd);

qui renvoie l'une des valeurs "LIBNBD_AIO_DIRECTION_READ", "LIBNBD_AIO_DIRECTION_WRITE" ou "

Notifier libnbd quand un événement se produit

Lorsque vous détectez (par exemple, en utilisant poll(2)) qu'un événement de lecture ou d'écriture s'est produit sur le socket, vous devez ensuite en informer libnbd. Vous devez vérifier à nouveau la direction (car elle a pu être modifiée par un autre thread) et notifier libnbd :

int r = 0;
dir = nbd_aio_get_direction (nbd);
if ((dir & LIBNBD_AIO_DIRECTION_READ) &&
                a_read_event_occurred ())
  r = nbd_aio_notify_read (nbd);
else if ((dir & LIBNBD_AIO_DIRECTION_WRITE) &&
                a_write_event_occurred ())
  r = nbd_aio_notify_write (nbd);
if (r == -1) {
  fprintf (stderr, "%s\n", nbd_get_error ());
  // ...
}

Les appels de notification font progresser la machine d'état, lisant et écrivant depuis le socket potentiellement plusieurs fois, jusqu'à ce que le socket bloque à nouveau, moment auquel ils renvoient le contrôle à l'appelant.

Implémentation simple avec nbd_poll(3)

En fait, si vous souhaitez utiliser poll(2) sur une seule poignée, une implémentation simple a déjà été écrite, appelée nbd_poll(3). Il est également utile d'examiner comment cela est implémenté (lib/poll.c dans le code source de libnbd), car cela vous indiquera comment intégrer libnbd avec des boucles principales plus complexes.

Quelques exemples d'utilisation de nbd_poll(3) suivent.

Comme avec l'API de haut niveau, tout commence par la création d'une poignée :

struct nbd_handle *nbd;
nbd = nbd_create ();
if (nbd == NULL) {
  fprintf (stderr, "%s\n", nbd_get_error ());
  nbd_close (nbd);
  exit (EXIT_FAILURE);
}

Pour nous connecter au serveur de manière asynchrone, nous lançons la connexion en utilisant nbd_aio_connect(3), puis nous entrons dans notre boucle principale pour vérifier les événements jusqu'à ce que la connexion soit prête :

int fd;
struct sockaddr_un addr;
socklen_t len;
/* code pour configurer addr,
   puis ... */
if (nbd_aio_connect (nbd, &addr, len) == -1) {
  fprintf (stderr, "%s\n", nbd_get_error ());
  nbd_close (nbd);
  exit (EXIT_FAILURE);
}
while (! nbd_aio_is_ready (nbd)) {
  if (nbd_poll (nbd, -1) == -1) {
    fprintf (stderr, "%s\n", nbd_get_error ());
    nbd_close (nbd);
    exit (EXIT_FAILURE);
  }
}

Pour lire des données de manière asynchrone, lancez une commande de lecture asynchrone, qui renvoie un cookie de commande de 64 bits, et entrez dans la boucle principale jusqu'à ce que la commande soit terminée :

int64_t cookie;
char buf[512];
cookie = nbd_aio_pread (nbd, buf, sizeof buf, offset,
                        NBD_NULL_COMPLETION, 0);
if (cookie == -1) {
  fprintf (stderr, "%s\n", nbd_get_error ());
  nbd_close (nbd);
  exit (EXIT_FAILURE);
}
while (! nbd_aio_command_completed (nbd, cookie)) {
  if (nbd_poll (nbd, -1) == -1) {
    fprintf (stderr, "%s\n", nbd_get_error ());
    nbd_close (nbd);
    exit (EXIT_FAILURE);
  }
}

Pour presque tous les appels synchrones de haut niveau (par exemple, nbd_pread(3)), il existe un équivalent asynchrone de bas niveau (par exemple, nbd_aio_pread(3)) pour démarrer une commande.

GESTION DES ERREURS

Lorsqu'un appel d'API renvoie une erreur (-1 ou "NULL" selon l'API), un message d'erreur et parfois une valeur errno sont disponibles. Vous pouvez récupérer le message d'erreur et/ou l'errno du dernier appel échoué en utilisant nbd_get_error(3) et nbd_get_errno(3). Par exemple :

if (nbd_connect_tcp (nbd, "remote", "nbd") == -1) {
  fprintf (stderr,
           "échec de la connexion au serveur distant : %s (errno = %d)\n",
           nbd_get_error (), nbd_get_errno ());
}

Ces fonctions utilisent le stockage local au thread pour renvoyer l'erreur la plus récente dans le thread courant. C'est pourquoi vous n'avez pas besoin de passer la poignée à ces appels. Elles fonctionnent même si nbd_create(3) renvoie "NULL" lorsqu'il n'y a pas de poignée du tout.

Pour cette raison, vous ne pouvez pas les appeler depuis un autre thread. Vous devriez les appeler immédiatement après l'appel d'API échoué, depuis le même thread. De plus, la chaîne d'erreur renvoyée par nbd_get_error(3) n'est valide que jusqu'au prochain appel d'API libnbd dans le thread courant, donc si vous avez besoin de conserver la chaîne, vous devez la copier (par exemple, en utilisant strdup(3)).

Errno

Pour certaines erreurs, un numéro d'erreur d'appel système (voir errno(3)) est disponible. Vous pouvez trouver le numéro d'erreur en appelant nbd_get_errno(3). Cela fonctionne de la même manière que nbd_get_error(3) en ce qui concerne les threads.

Même lorsqu'un appel renvoie une erreur, nbd_get_errno(3) peut renvoyer 0. Cela ne signifie pas qu'il n'y a pas eu d'erreur. Cela signifie qu'aucune information errno supplémentaire n'est disponible pour cette erreur.

Le numéro d'erreur est souvent l'erreur brute renvoyée par un appel système qui a échoué.

Il peut également être utilisé pour indiquer des conditions spéciales. Les cas les plus courants sont :

"EINVAL"
Paramètres ou état invalides pour l'appel libnbd courant. (Cela peut également indiquer que les requêtes ne sont pas alignées sur les "contraintes de taille de bloc").
"ENOTSUP"
L'appel libnbd n'est pas disponible dans cette compilation de libnbd (par exemple, lors de l'utilisation d'une API TLS si la bibliothèque a été compilée sans prise en charge TLS).
"ENOMEM"
La bibliothèque a manqué de mémoire lors de l'exécution d'une opération.
"ERANGE"
Une requête est trop volumineuse, par exemple si vous essayez de lire trop d'octets dans un seul appel nbd_pread(3).
"EFAULT"
Un paramètre de pointeur était "NULL" alors qu'il aurait dû être non-NULL. Voir la section ci-dessous.

Paramètres Non-NULL

Presque toutes les fonctions libnbd lorsqu'elles sont appelées depuis C prennent un ou plusieurs paramètres de type pointeur qui ne doivent pas être "NULL". Par exemple, le paramètre de poignée, les chaînes et les tampons ne doivent généralement pas être "NULL".

Si un "NULL" est passé comme l'un de ces paramètres, libnbd tente de renvoyer une erreur avec nbd_get_errno(3) renvoyant "EFAULT".

Cependant, cela peut provoquer d'autres avertissements liés au compilateur et même un comportement indéfini, vous devez donc essayer d'éviter cette erreur de programmation.

MESSAGES DE DÉBOGAGE

Libnbd peut afficher de nombreux messages de débogage, utiles si vous rencontrez un problème avec la bibliothèque. Activez le débogage après avoir créé la poignée :

nbd = nbd_create ();
nbd_set_debug (nbd, true);

ou définissez la variable d'environnement "LIBNBD_DEBUG=1", ce qui activera le débogage par défaut sur toutes les nouvelles poignées.

Les messages de débogage sont envoyés à stderr par défaut, mais vous pouvez les rediriger vers un système de journalisation en utilisant nbd_set_debug_callback(3).

CONNEXION À DES SERVEURS NBD LOCAUX OU DISTANTS

Il existe plusieurs façons de se connecter à des serveurs NBD, et vous pouvez même exécuter un serveur à partir de libnbd. Normalement, vous vous connecteriez à un serveur déjà en cours d'exécution, via un socket de domaine Unix local ou une connexion TCP distante. Les appels d'API de haut niveau sont :

nbd_connect_unix (nbd, "socket");
nbd_connect_tcp (nbd, "localhost", "nbd");

Pour nbd_connect_tcp(3), le troisième paramètre est le nom ou le numéro du port, qui peut être un nom de /etc/services ou le numéro de port sous forme de chaîne (par exemple, "10809").

Connexion à une URI NBD

libnbd prend en charge la spécification des URI NBD. Le format des URI est documenté dans nbd_connect_uri(3).

Vous pouvez vous connecter à une URI comme dans ces exemples (en utilisant l'API de haut niveau) :

nbd_connect_uri (nbd, "nbd://example.com/");
nbd_connect_uri (nbd, "nbds+unix:///export?socket=/tmp/nbd.sock");

Cette fonctionnalité est implémentée en appelant d'autres API libnbd pour configurer le nom d'exportation, les paramètres TLS, et enfin se connecter via un socket de domaine Unix ou TCP.

La prise en charge des URI est une fonctionnalité optionnelle de la bibliothèque, nécessitant libxml2 au moment de la compilation. Les appels nbd_connect_uri(3) et nbd_aio_connect_uri(3) généreront une erreur (avec nbd_get_errno(3) renvoyant "ENOTSUP") si elle n'a pas été construite avec cette fonctionnalité, et vous pouvez également la tester explicitement en utilisant nbd_supports_uri(3).

The nbd_connect_uri(3) and nbd_aio_connect_uri(3) calls will raise an error (with nbd_get_errno(3) returning "ENOTSUP") if it was not built with this feature, and you can also test for it explicitly using nbd_supports_uri(3).

Pp">nbd_is_uri(3) utilise une heuristique pour détecter si le paramètre pourrait être une URI NBD ou autre chose (comme un nom de fichier). Cela peut être utile pour les paramètres de programme qui peuvent être une URI ou un fichier.

Connexion a un sous-processus

Certains serveurs NBD — notamment nbdkit(1) avec le paramètre -s, et nbd-server(1) avec le port fixé à 0 — peuvent aussi accepter une seule connexion NBD sur stdin/stdout. Vous pouvez exécuter ces serveurs comme sous-processus de votre programme principal en utilisant nbd_connect_command(3). Cet exemple crée un disque RAM inscriptible de 1G :

char *argv[] = { "nbdkit", "-s", "--exit-with-parent",
                           "memory", "1G", NULL };
nbd_connect_command (nbd, argv);

Lorsque le descripteur est fermé, le sous-processus nbdkit est tué, ce qui dans ce cas signifie que le disque RAM est rejeté. C'est donc utile pour les tests.

Connexion a un sous-processus via l'activation de socket systemd

Certains serveurs NBD — notamment nbdkit(1) et qemu-nbd(1) — supportent l'activation de socket systemd, permettant à libnbd de passer un socket au sous-processus. Cela fonctionne de manière très similaire à nbd_connect_command(3) ci-dessus, mais vous devez utiliser nbd_connect_systemd_socket_activation(3) à la place.

Connexion a n'importe quel socket

Si aucune des autres méthodes nbd_connect* ne convient, vous pouvez créer vous-même un socket connecté et le passer à nbd_connect_socket(3).

L'un des usages est le fuzzing, où nous utilisons socketpair(2) pour créer le socket, puis nous utilisons fork, et le programme de test dans le processus enfant communique avec libnbd via la paire de sockets (voir : https://gitlab.com/nbdkit/libnbd/-/blob/master/fuzzing/libnbd-fuzz-wrapper.c).

Un autre usage est de connecter libnbd à une famille d'adresses qu'il ne supporte pas nativement, comme XDP ou IB.

CONTROLE DE LA NEGOCIATION

Par défaut, lors de l'établissement d'une connexion, libnbd gère toute la négociation avec le serveur, en utilisant uniquement la configuration (par ex. nbd_set_export_name(3) ou nbd_add_meta_context(3)) qui a été demandée avant la tentative de connexion ; cette phase se poursuit jusqu'à ce que nbd_aio_is_connecting(3) ne renvoie plus vrai, au moment où soit les commandes de données sont prêtes à être utilisées, soit la connexion a échoué avec une erreur.

Mais il existe des scénarios dans lesquels il est utile de contrôler également les commandes de poignée de main envoyées pendant la négociation, comme demander au serveur une liste des exports disponibles avant de choisir celui à utiliser. Ceci est réalisé en appelant nbd_set_opt_mode(3) avant de se connecter ; après avoir demandé une connexion, la machine d'états s'arrêtera sur nbd_aio_is_negotiating(3), au moment où l'utilisateur peut décider quelle commande de poignée de main envoyer ensuite. Notez que l'état de négociation n'est accessible qu'aux serveurs de style récent ; les serveurs de style ancien ne peuvent pas négocier et progresseront jusqu'à l'état prêt.

Lorsque l'état de négociation est atteint, vous pouvez initier des commandes d'option telles que nbd_opt_list(3) ou leurs équivalents asynchrones, ainsi que modifier la configuration telle que le nom de l'export qui devait précédemment être défini avant la connexion. Comme le protocole NBD ne permet pas les commandes de négociation parallèles, aucun cookie n'est impliqué, et vous pouvez suivre l'achèvement de chaque commande lorsque l'état n'est plus nbd_aio_is_connecting(3). Si nbd_opt_go(3) échoue mais que la connexion est toujours active, vous reviendrez dans l'état de négociation, où vous pourrez demander un autre nom d'export et réessayer. Quitter l'état de négociation n'est possible qu'avec un nbd_opt_go(3) réussi qui passe à la phase de données, ou nbd_opt_abort(3) qui effectue une fermeture propre de la connexion en sautant la phase de données.

EXPORTS ET FLAGS

Il est possible pour les serveurs NBD de servir différents contenus sur différents “exports”. Pour cela, vous devez passer le bon nom d'export au serveur. Appelez cette API avant de vous connecter :

nbd_set_export_name (nbd, "export");

Notez que certains serveurs (comme nbdkit(1) ≤ 1.14) ignorent ceci, et d'autres serveurs (comme qemu-nbd(8)) l'exigent mais ne peuvent pas servir de contenu différent.

Ces API sont également disponibles après un appel réussi à nbd_opt_info(3) pendant la phase de négociation, si vous avez utilisé nbd_set_opt_mode(3) avant la connexion.

Appels aux flags

Après la connexion, le serveur renverra un ensemble de drapeaux décrivant l'export, comme s'il est inscriptible et s'il peut supporter la mise en cache permanente. Ces drapeaux peuvent être accessibles depuis libnbd en utilisant des API telles que :

int is_read_only = nbd_is_read_only (nbd);
int can_flush = nbd_can_flush (nbd);

Les appels aux drapeaux sont : nbd_can_block_status_payload(3), nbd_can_cache(3), nbd_can_df(3), nbd_can_fast_zero(3), nbd_can_flush(3), nbd_can_fua(3), nbd_can_meta_context(3), nbd_can_multi_conn(3), nbd_can_trim(3), nbd_can_zero(3), nbd_is_read_only(3), nbd_is_rotational(3).

Taille de l'export

Pour obtenir la taille de l'export en octets, utilisez nbd_get_size(3) :

int64_t size = nbd_get_size (nbd);

Contraintes de taille de bloc

Certains serveurs NBD ne peuvent pas traiter les requêtes sur n'importe quelle limite d'octet. Ils peuvent, par exemple, exiger que toutes les requêtes soient alignées sur des secteurs de 512 octets.

De plus, certains serveurs annoncent une taille de bloc préférentielle. Ce n'est pas une exigence, mais c'est la taille de bloc minimale qui peut être accédée efficacement (généralement sans déclencher de cycles coûteux de lecture-modification-écriture internes au serveur).

Ce sont les contraintes de taille de bloc et elles peuvent être interrogées en appelant nbd_get_block_size(3). Portez une attention particulière à la contrainte "LIBNBD_SIZE_MINIMUM" car certains serveurs rejetteront les requêtes plus petites ou non alignées sur cette taille de bloc avec des erreurs "EINVAL" (« Argument invalide »).

Pour des informations du côté serveur, voir ".block_size" dans nbdkit-plugin(3).

Pour des informations définitives sur les contraintes de taille de bloc, lisez la spécification du protocole NBD.

Serveurs newstyle et oldstyle

Libnbd peut se connecter aux deux protocoles NBD plus simples et anciens (avant 2011), désormais appelés "oldstyle", ou aux serveurs modernes "newstyle-fixed". ("newstyle" n'a été disponible que brièvement.) Pour connaître le protocole utilisé par le serveur, appelez nbd_get_protocol(3).

COMMANDES DE DONNEES

Vous pouvez lire et écrire des données depuis le serveur NBD en utilisant nbd_pread(3) et nbd_pwrite(3) ou leurs équivalents asynchrones.

Toutes les commandes de données supportent un argument "flags" (obligatoire en C, mais optionnel dans les langages où il peut prendre 0 par défaut). Pour plus de commodité, la constante "LIBNBD_CMD_FLAG_MASK" est définie avec l'ensemble des drapeaux actuellement reconnus par libnbd, car les futures extensions du protocole NBD peuvent entraîner le support de drapeaux supplémentaires ; mais en général, les commandes de données spécifiques n'acceptent qu'un sous-ensemble des drapeaux connus.

Libnbd effectue par défaut une vérification de la validité côté client dans chacune de ses commandes de données ; par exemple, les tentatives d'écriture sur un serveur qui a annoncé une connexion en lecture seule sont rejetées. Il est possible de modifier certains aspects de cette vérification en utilisant nbd_set_strict_mode(3).

Certains serveurs supportent également :

trim/discard
Si nbd_can_trim(3) renvoie vrai, nbd_trim(3) peut être utilisé pour créer des « trous » dans le stockage sous-jacent du disque sur le serveur. Normalement (bien que pas dans tous les cas), les trous lus reviennent comme des zéros mais ne prennent pas de place.
zeroing
Si nbd_can_zero(3) renvoie vrai, nbd_zero(3) peut être utilisé pour mettre à zéro efficacement des parties du disque sans avoir à envoyer de grandes quantités d'octets zéro sur le réseau (ce qui serait nécessaire en utilisant nbd_pwrite(3)).

Ceci est légèrement différent du trimming car le stockage sous-jacent est toujours alloué. Pour certains types de stockage, cela

écritures futures plus efficaces et/ou moins susceptibles d'échouer en raison d'erreurs d'espace insuffisant.

flushing
Certains serveurs peuvent valider les données dans un stockage permanent et vous informer de manière fiable que cela s'est produit. Deux indicateurs d'exportation sont associés à cela : nbd_can_flush(3) et nbd_can_fua(3).

L'appel nbd_flush(3) (disponible si nbd_can_flush(3) renvoie vrai) vide toutes les écritures en attente sur le disque et ne se termine pas tant que cette opération n'est pas terminée. C'est similaire à l'utilisation de sync(2) sur les systèmes POSIX.

Une façon plus efficace d'y parvenir est de définir l'indicateur "LIBNBD_CMD_FLAG_FUA" sur les appels de type écriture (comme write, trim et zero). Cet indicateur signifie que l'appel ne se terminera pas tant qu'il n'aura pas été validé dans le stockage permanent, mais il n'implique pas le vidage de l'ensemble du disque.

prefetching
Certains serveurs peuvent précharger les données, ce qui accélère les lectures ultérieures. L'appel nbd_cache(3) (disponible si nbd_can_cache(3) renvoie vrai) est utilisé pour le préchargement.
état du bloc
Certains serveurs sont capables de fournir des informations sur les différentes étendues au sein de l'image, via la notion d'un ou plusieurs contextes méta. Le contexte méta le plus courant est "base:allocation" (disponible dans libnbd.h sous "LIBNBD_CONTEXT_BASE_ALLOCATION"), qui peut être utilisé pour savoir quelles portions d'un fichier sont allouées ou lues comme zéro. D'autres contextes peuvent être disponibles ; par exemple, qemu-nbd(8) peut exposer un contexte méta "qemu:dirty-bitmap:NAME" pour suivre quelles portions d'un fichier sont suivies par un bitmap "dirty" qcow2.

Pour utiliser l'état du bloc, le client doit appeler nbd_add_meta_context(3) avant de se connecter, pour chaque contexte méta qui l'intéresse, puis vérifier nbd_can_meta_context(3) après la connexion pour voir quels contextes le serveur prend réellement en charge. Si un contexte est pris en charge, le client peut alors utiliser nbd_block_status_64(3) avec une fonction de rappel qui recevra un tableau de structures décrivant les étendues consécutives au sein d'un contexte. Chaque structure donne la longueur de l'étendue, puis une description par masque de bits de cette étendue (pour le contexte "base:allocation", le masque de bits peut inclure "LIBNBD_STATE_HOLE" pour les portions non allouées du fichier, et/ou "LIBNBD_STATE_ZERO" pour les portions du fichier dont on sait qu'elles se lisent comme zéro).

Il existe un exemple complet de demande de contexte méta et d'utilisation de l'état du bloc disponible à l'adresse https://gitlab.com/nbdkit/libnbd/blob/master/interop/dirty-bitmap.c

PERFORMANCE

Émission de plusieurs requêtes en cours

Les serveurs NBD qui implémentent correctement la spécification peuvent gérer plusieurs requêtes de données simultanément sur la même connexion. Libnbd prend en charge cela lors de l'utilisation de l'API de bas niveau.

Pour l'utiliser, il suffit d'émettre davantage de requêtes selon les besoins (par exemple, en utilisant des appels comme nbd_aio_pread(3), nbd_aio_pwrite(3)) sans attendre que les commandes précédentes soient terminées. Vous devez veiller à ce que les requêtes en cours ne chevauchent pas les décalages disque d'autres commandes d'écriture en cours — une lecture qui se chevauche peut voir des données indéterminées, et une écriture qui se chevauche peut même causer une corruption du disque où le contenu du disque résultant ne correspond à aucune des deux écritures.

Chaque requête est identifiée par un cookie unique de 64 bits (attribué par libnbd), permettant à libnbd et aux appelants de faire correspondre les réponses aux requêtes. Les réponses peuvent arriver dans le désordre. Une requête qui est rejetée côté client pour avoir échoué à une vérification de cohérence (comme tenter d'écrire sur un serveur en lecture seule, voir nbd_set_strict_mode(3)) échouera plutôt que de renvoyer un cookie, bien que le nettoyage de la fermeture soit toujours effectué.

Bien qu'en théorie vous puissiez avoir un nombre indéfini de requêtes en cours en même temps, en pratique, il est conseillé de les limiter à un certain nombre. Libnbd mettra en file d'attente les commandes dans le handle même s'il ne peut pas les écrire sur le serveur, donc cette limite vise principalement à empêcher qu'une file d'attente de commandes ne consomme trop de mémoire. Il est suggéré de commencer avec une limite de 64 requêtes en cours (par connexion NBD) et de mesurer comment l'ajustement de la limite vers le haut et vers le bas affecte les performances pour votre configuration locale.

Il existe un exemple complet utilisant plusieurs requêtes en cours disponible à l'adresse https://gitlab.com/nbdkit/libnbd/blob/master/examples/threaded-reads-and-writes.c

Multi-conn

Certains serveurs NBD annoncent "multi-conn", ce qui signifie qu'il est sûr d'établir plusieurs connexions au serveur et de répartir les commandes entre toutes les connexions.

Pour ce faire, vous devez d'abord ouvrir une seule connexion et tester cette fonctionnalité à l'aide de nbd_can_multi_conn(3). Sans gestion des erreurs, cela ressemblerait à ceci :

struct nbd_handle *nbd[4];
size_t i;
bool supports_multi_conn;
nbd[0] = nbd_create ();
nbd_connect_tcp (nbd[0], "server", "10809");
supports_multi_conn = nbd_can_multi_conn (nbd[0]) > 0;

Si multi-conn est pris en charge, vous pouvez ouvrir d'autres connexions :

if (supports_multi_conn) {
  for (i = 1; i <= 3; ++i) {
    nbd[i] = nbd_create ();
    nbd_connect_tcp (nbd[i], "server", "10809");
  }
}

Si vous émettez plusieurs requêtes en cours (voir ci-dessus) et limitez le nombre, alors la limite doit être appliquée à chaque connexion NBD individuelle.

CHIFFREMENT ET AUTHENTIFICATION

Le protocole NBD et libnbd prennent en charge TLS (parfois appelé à tort "SSL") pour le chiffrement du flux de données et l'authentification des clients et des serveurs. Libnbd désactive TLS par défaut pour une interopérabilité maximale. Pour l'activer sur un handle, vous devez appeler nbd_set_tls(3) avant de vous connecter.

Pour autoriser TLS, mais revenir à un mode non chiffré :

nbd_set_tls (nbd, LIBNBD_TLS_ALLOW);

Utilisez nbd_get_tls_negotiated(3) pour savoir si la négociation TLS a réussi. Évitez "LIBNBD_TLS_ALLOW" si les attaques de type man-in-the-middle sont une préoccupation.

Le mode le plus sécurisé consiste à exiger TLS et à échouer la connexion si le serveur ne le prend pas en charge :

nbd_set_tls (nbd, LIBNBD_TLS_REQUIRE);

Il peut également être nécessaire de vérifier que l'identité du serveur est correcte. Pour certains serveurs, il peut être nécessaire de vérifier auprès du serveur que le client est autorisé à se connecter. Cela peut être fait en utilisant soit des certificats X.509, soit des clés pré-partagées TLS (PSK). Les certificats sont plus sécurisés. Les PSK sont beaucoup plus pratiques, mais vous devez disposer d'un canal sécurisé existant pour distribuer les clés.

Configuration de X.509 à l'aide des autorités de certification système (AC)

C'est le comportement par défaut si vous n'appelez aucune autre fonction "nbd_set_tls_*". Dans ce cas, le serveur doit avoir un certificat public (par exemple, HTTPS) qui peut être vérifié par rapport aux AC enregistrées sur votre système (par exemple, sous /etc/pki).

Pour désactiver la vérification du nom du serveur — ce qui vous expose à une attaque potentielle de l'homme du milieu (MITM) — utilisez :

nbd_set_tls_verify_peer (nbd, false);

Configuration d'une autorité de certification X.509 (AC)

Vous pouvez configurer votre propre AC et y enregistrer des clients et des serveurs, en émettant des certificats clients et serveurs qui authentifieront de manière fiable vos clients et serveurs les uns aux autres.

Cela est décrit en détail dans le manuel nbdkit-tls(1). Les seules différences pour libnbd sont :

  • Les certificats non-root doivent être placés dans "$HOME/.pki/libnbd/" ou "$HOME/.config/pki/libnbd/"
  • Libnbd lit client-cert.pem et client-key.pem (au lieu de server-cert.pem et server-key.pem).

Une fois que vous avez configuré le répertoire contenant les certificats, appelez :

nbd_set_tls_certificates (nbd, "/chemin/vers/le/repertoire");

Configuration des clés pré-partagées (PSK)

Les clés pré-partagées TLS sont une méthode beaucoup plus pratique de configuration de TLS, et plus appropriée pour NBD, mais vous devez disposer d'une méthode sécurisée existante pour distribuer les clés. Elles sont donc idéales si vous souhaitez configurer un service NBD en complément d'une API REST sécurisée existante.

Utilisez psktool(1) pour créer un fichier de paires "nom_utilisateur:clé" :

psktool -u username -p keys.psk

et passez ce chemin à libnbd :

nbd_set_tls_psk_file (nbd, "keys.psk");

Si nécessaire, vous devrez peut-être définir le nom d'utilisateur du client (sinon libnbd utilisera votre nom de connexion) :

nbd_set_tls_username (nbd, "username");

CALLBACKS

Certains appels libnbd prennent des fonctions de rappel (par exemple, nbd_set_debug_callback(3), nbd_aio_pread(3)). Libnbd peut appeler ces fonctions lors du traitement.

Dans l'API C, ces appels libnbd prennent une structure qui contient la foncti on pointeur et un pointeur opaque facultatif "void *user_data" :

nbd_aio_pread (nbd, buf, sizeof buf, offset,
               (nbd_completion_callback) { .callback = my_fn,
                                           .user_data = my_data },
               0);

Pour les rappels facultatifs, si vous ne souhaitez pas de rappel, définissez ".callback" sur "NULL" ou utilisez les macros équivalentes (telles que "NBD_NULL_COMPLETION") définies dans "libnbd.h" :

nbd_aio_pread (nbd, buf, sizeof buf, offset,
               NBD_NULL_COMPLETION, 0);

À partir d'autres langues, la structure et le pointeur opaque ne sont pas nécessaires car vous pouvez utiliser des fermetures (closures) pour obtenir le même effet.

Durées de vie des rappels

Vous pouvez associer une fonction de libération facultative aux rappels. Libnbd appellera cette fonction lorsque le rappel ne sera plus appelé par libnbd, y compris en cas d'échec de l'API.

Cela peut être utilisé pour libérer le "user_data" associé. Par exemple :

void *my_data = malloc (...);
nbd_aio_pread_structured (nbd, buf, sizeof buf, offset,
               (nbd_chunk_callback) { .callback = my_fn,
                                      .user_data = my_data,
                                      .free = free },
               NBD_NULL_COMPLETION,
               0);

appellera free(3) une fois sur "my_data" après que l'on sache que la fonction "chunk.callback = my_fn" ne peut plus être appelée, indépendamment du nombre de fois où "my_fn" a été effectivement appelée. Si un rappel de milieu de commande et un rappel de complétion sont tous deux fournis, les fonctions seront atteintes dans cet ordre : rappels de milieu de commande, rappel de complétion, libération de milieu de commande, et enfin libération de complétion.

La fonction de libération n'est accessible que dans l'API C car elle n'est pas nécessaire dans les langages de programmation à ramasse-miettes.

Rappels avec ".callback=NULL" et ".free!=NULL"

Il est possible d'enregistrer un rappel comme ceci :

...
  (nbd_completion_callback) { .callback = NULL,
                              .user_data = my_data,
                              .free = free },
...

La signification est que le rappel n'est jamais appelé, mais la fonction de libération est toujours appelée après la dernière fois que le rappel aurait dû être appelé. Ceci est utile pour appliquer des actions de libération génériques lorsque les commandes asynchrones sont retirées.

Rappels et verrouillage

Les rappels sont invoqués à un moment où le verrou libnbd est détenu, typiquement lors d'un appel à "nbd_aio_notify_read", "nbd_aio_notify_write", "nbd_aio_poll", ou un autre appel qui peut faire progresser la machine d'état de libnbd. Selon la charge système, il est même possible qu'un rappel soit atteint avant l'achèvement de l'appel "nbd_aio_*" qui a spécifié le rappel. En tant que tel, il est dangereux que le rappel appelle des API "nbd_*" sur le même objet nbd, car cela provoquerait un interblocage.

Rappels de complétion

Toutes les commandes asynchrones ont une fonction de rappel de complétion facultative qui est utilisée si l'appel à l'API asynchrone rapporte un succès. Le rappel de complétion est invoqué lorsque la commande soumise est finalement marquée comme terminée, après que tous les rappels de milieu de commande aient terminé, et avant toutes les fonctions de libération. Le rappel de complétion n'est pas atteint si l'API asynchrone elle-même échoue, tandis que les rappels de libération sont atteints quel que soit le résultat de l'API asynchrone initiale.

Lorsque le rappel de complétion retourne 1, la commande est automatiquement retirée (il n'est pas nécessaire d'appeler nbd_aio_command_completed(3)) ; pour toute autre valeur de retour, la commande doit toujours être retirée manuellement (sinon, la commande immobilisera des ressources jusqu'à ce que nbd_close(3) soit éventuellement atteinte).

Rappels avec le paramètre "int *error"

Certaines commandes de haut niveau (nbd_pread_structured(3), nbd_block_status_64(3)) impliquent l'utilisation d'une fonction de rappel invoquée par la machine d'état aux points appropriés de la réponse du serveur avant que la commande globale ne soit terminée. Ces fonctions de rappel, ainsi que tous les rappels de complétion, incluent un paramètre "error" qui est un pointeur contenant la valeur de toute erreur détectée jusqu'à présent. Si une fonction de rappel échoue et souhaite modifier l'erreur résultante de la commande globale visible plus tard dans la séquence d'API, elle doit réaffecter à "error" et retourner -1 dans l'API C. Les affectations dans "error" sont ignorées pour toute autre valeur de retour ; de même, affecter 0 à "error" n'a aucun effet. Dans d'autres liaisons de langage, le rapport des erreurs de rappel se fait généralement en levant une exception plutôt qu'en retournant une valeur.

Notez qu'un rappel de milieu de commande peut ne jamais être atteint, par exemple si libnbd détecte que la commande était invalide à envoyer (voir nbd_set_strict_mode(3)) ou si le serveur signale un échec qui conclut la commande. Il est sûr pour un rappel de milieu de commande d'ignorer un "error" non nul : tous les autres paramètres du rappel de milieu de commande resteront valides (correspondant à la portion actuelle de la réponse du serveur), et la commande globale échouera toujours (au rappel de complétion ou à nbd_aio_command_completed(3) pour une commande asynchrone, ou en résultat de la commande synchrone globale). Retourner -1 depuis un rappel de milieu de commande n'empêche pas ce rappel d'être atteint à nouveau, si le serveur envoie plus de réponses de milieu de commande qui justifient une nouvelle utilisation de ce rappel. Un rappel de milieu de commande peut être atteint plus de fois que prévu si le serveur n'est pas conforme.

En revanche, si un rappel de complétion est fourni (uniquement possible avec les commandes asynchrones), il ne sera pas appelé si l'appel d'API initial échoue (par exemple, tenter une commande asynchrone dans un état incorrect - il n'y a rien à compléter car la commande n'a pas été mise en file d'attente), mais sera sinon appelé exactement une fois, et le rappel de complétion ne doit pas ignorer la valeur pointée par "error". En particulier, le contenu d'un tampon passé à nbd_aio_pread(3) ou nbd_aio_pread_structured(3) est indéfini si *error est non nul à l'entrée du rappel de complétion. Il est recommandé que si vous choisissez d'utiliser le retrait automatique des commandes (où le rappel de complétion retourne 1 pour éviter d'avoir à appeler nbd_aio_command_completed(3) plus tard), votre fonction de complétion doit retourner 1 sur tous les chemins de contrôle, même lors du traitement des erreurs (notez qu'avec le retrait automatique, l'affectation dans "error" est inutile car il n'y a pas d'API ultérieure pour voir cette valeur).

COMPTEURS DE STATISTIQUES

Libnbd suit plusieurs compteurs de statistiques, utiles pour suivre la quantité de trafic envoyée sur la connexion. Les compteurs suivent le nombre d'octets en clair envoyés et reçus par le protocole NBD (pas nécessairement le nombre d'octets envoyés sur le socket, en particulier lorsque TLS est activé), ainsi que le nombre de blocs de protocole (un groupe d'octets délimité par un nombre magique, et pas le même que le nombre de paquets TCP).

printf ("octets : envoyés=%" PRIu64 " reçus=%" PRIu64,
         nbd_stats_bytes_sent (nbd), nbd_stats_bytes_received (nbd));
printf ("blocs : envoyés=%" PRIu64 " reçus=%" PRIu64,
         nbd_stats_chunks_sent (nbd), nbd_stats_chunks_received (nbd));

SIGNAL

Libnbd n'installe pas de gestionnaires de signaux. Il tente de désactiver "SIGPIPE" lors de l'écriture sur le socket NBD en utilisant le drapeau "MSG_NOSIGNAL" de send(2), ou l'option de socket "SO_NOSIGPIPE", sur les plateformes qui les prennent en charge.

Sur certains vieux systèmes Linux ou les plateformes non-Linux plus récentes, le programme principal peut souhaiter enregistrer un gestionnaire de signaux pour ignorer SIGPIPE :

signal (SIGPIPE, SIG_IGN);

COMPILATION DE VOTRE PROGRAMME

Sur la plupart des systèmes, les programmes C qui utilisent libnbd peuvent être compilés comme ceci :

cc prog.c -o prog -lnbd

Pour détecter si la bibliothèque libnbd et le fichier d'en-tête sont installés, la méthode préférée est d'utiliser pkg-config(1) ou pkgconf(1) :

pkg-config libnbd --exists || fail libnbd est requis

Si la bibliothèque ou le fichier d'en-tête ne sont pas installés dans les emplacements système habituels, vous pouvez compiler votre programme comme suit, en utilisant pkg-config pour détecter l'emplacement approprié de libnbd :

cc prog.c -o prog `pkg-config libnbd --cflags --libs`

Pour compiler un projet externe contre une copie construite de l'arborescence source de libnbd qui n'a pas été installée, consultez le script ./run.

Projets Autoconf

Les projets externes qui utilisent autoconf et doivent vérifier si libnbd est installé doivent utiliser la macro "PKG_CHECK_MODULES" dans configure.ac comme ceci :

PKG_CHECK_MODULES([LIBNBD], [libnbd])

Ceci définira "@LIBNBD_CFLAGS@" et "@LIBNBD_LIBS@" que vous devrez ajouter à votre Makefile.am.

Projets CMake

Pour les projets CMake, utilisez :

find_package(PkgConfig REQUIRED)
pkg_check_modules(LIBNBD REQUIRED libnbd)
target_link_libraries(prog ${LIBNBD_LIBRARIES})
target_include_directories(prog PUBLIC ${LIBNBD_INCLUDE_DIRS})
target_compile_options(prog PUBLIC ${LIBNBD_CFLAGS_OTHER})

Projets Meson

Pour les projets Meson, utilisez :

nbd_dep = dependency('libnbd')
executable('prog', 'prog.c', dependencies : [nbd_dep])
