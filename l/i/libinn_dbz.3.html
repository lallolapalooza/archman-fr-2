NOM

dbz - Routines de base de données pour InterNetNews

SYNOPSIS

#include <inn/dbz.h>
#define DBZMAXKEY              ...
#define DBZ_INTERNAL_HASH_SIZE ...
typedef enum
{
    DBZSTORE_OK,
    DBZSTORE_EXISTS,
    DBZSTORE_ERROR
} DBZSTORE_RESULT;
typedef enum
{
    INCORE_NO,
    INCORE_MEM,
    INCORE_MMAP
} dbz_incore_val;
typedef struct {
    bool writethrough;
    dbz_incore_val pag_incore;
    dbz_incore_val exists_incore;
    bool nonblock;
} dbzoptions;
typedef struct {
    char hash[DBZ_INTERNAL_HASH_SIZE];
} __attribute__((__packed__)) erec;
extern bool dbzinit(const char *name);
extern bool dbzclose(void);
extern bool dbzfresh(const char *name, off_t size);
extern bool dbzagain(const char *name, const char *oldname);
extern bool dbzexists(const HASH key);
extern bool dbzfetch(const HASH key, off_t *value);
extern DBZSTORE_RESULT dbzstore(const HASH key, off_t data);
extern bool dbzsync(void);
extern long dbzsize(off_t contents);
extern void dbzsetoptions(const dbzoptions options);
extern void dbzgetoptions(dbzoptions *options);

DESCRIPTION

Ces fonctions fournissent un système d'indexation pour un accès aléatoire rapide à un fichier texte, ci-après dénommé le fichier de base.

dbz stocke des décalages dans le fichier de base pour une récupération rapide. Toutes les récupérations sont basées sur une valeur de hachage générée par la fonction HashMessageID dans libinn(3).

dbzinit ouvre une base de données, un index vers le fichier de base name, composé des fichiers name.dir, name.index et name.hash qui doivent déjà exister. (Si la base de données est nouvelle, ce devraient être des fichiers de longueur zéro.) Les accès ultérieurs vont à cette base de données jusqu'à ce que dbzclose soit appelée pour fermer la base de données. Lorsque le format de hachage étiqueté est utilisé (si --enable-tagged-hash a été spécifié lors de la configuration), un fichier name.pag est utilisé à la place de .index et .hash.

dbzfetch recherche dans la base de données la key spécifiée, assignant le décalage du fichier de base pour la key correspondante à value, le cas échéant.

dbzstore stocke la paire key-data dans la base de données. Elle renverra "DBZSTORE_EXISTS" pour les doublons (entrées existantes), et "DBZSTORE_OK" en cas de succès. Elle échouera avec "DBZSTORE_ERROR" si les fichiers de la base de données ne sont pas inscriptibles ou pas ouverts, ou si toute autre erreur se produit.

dbzexists vérifie si le hachage donné existe ou non. dbz est optimisé pour cette opération et peut être significativement plus rapide que dbzfetch.

dbzfresh est une variante de dbzinit pour créer une nouvelle base de données avec plus de contrôle sur les détails. Le paramètre size spécifie la taille de la première table de hachage dans la base de données, en nombre de paires clé-valeur. Les performances seront meilleures si le nombre de paires clé-valeur stockées dans la base de données ne dépasse pas environ 2/3 de size, ou 1/2 de size lorsque le format de hachage étiqueté est utilisé. (La fonction dbzsize, étant donné le nombre attendu de paires clé-valeur, suggérera une taille de base de données qui répond à ces critères.) En supposant qu'un décalage fseek est de 4 octets, le fichier .index fera 4 * size octets. Le fichier .hash fera "DBZ_INTERNAL_HASH_SIZE" * size octets (le fichier .dir est minuscule et de taille à peu près constante) jusqu'à ce que le nombre de paires clé-valeur dépasse environ 80% de size. (Rien de catastrophique ne se produira si la base de données dépasse 100% de size, mais les accès ralentiront considérablement et les fichiers .index et .hash grandiront un peu.)

dbz stocke jusqu'à "DBZ_INTERNAL_HASH_SIZE" octets (par défaut, 4 octets si le format de hachage étiqueté est utilisé, 6 sinon) du hachage de l'identifiant de message dans le fichier .hash pour confirmer une correspondance. Cela élimine la nécessité de lire le fichier de base pour gérer les collisions.

Une valeur size de 0 donnée à dbzfresh est synonyme de la valeur par défaut locale ; la valeur par défaut normale convient aux tables d'environ 6 000 000 de paires clé-valeur (ou 500 000 paires clé-valeur lorsque le format de hachage étiqueté est utilisé). Cette valeur par défaut est utilisée par dbzinit.

Lorsque les bases de données sont régénérées périodiquement, comme c'est le cas pour le fichier history, il est plus simple de choisir les paramètres d'une nouvelle base de données en se basant sur l'ancienne. Cela permet également de conserver une mémoire des tailles passées de l'ancienne base de données, de sorte qu'une nouvelle taille de base de données puisse être choisie pour couvrir les fluctuations attendues. dbzagain est une variante de dbzinit pour créer une nouvelle base de données comme une nouvelle génération d'une ancienne base de données. Les fichiers de base de données pour oldname doivent exister. dbzagain est équivalent à appeler dbzfresh avec une size égale au résultat de l'application de dbzsize au nombre maximal d'entrées dans la base de données oldname et ses 10 générations précédentes.

Lorsque de nombreux accès sont effectués par le même programme, dbz est massivement plus rapide si sa première table de hachage est en mémoire. Si le drapeau pag_incore est défini sur "INCORE_MEM", une tentative est faite pour charger la table en mémoire lors de l'ouverture de la base de données, et dbzclose la réécrit sur le disque (si elle a été lue avec succès et modifiée). dbzsetoptions peut être utilisé pour définir les drapeaux pag_incore et exists_incore sur différentes valeurs qui devraient être "INCORE_NO" (lecture depuis le disque), "INCORE_MEM" (lecture depuis la mémoire) ou "INCORE_MMAP" (lecture depuis un fichier mmap'é) pour les fichiers .hash et .index séparément ; cela n'affecte pas l'état d'une base de données déjà ouverte. La valeur par défaut est "INCORE_NO" pour le fichier .index et "INCORE_MMAP" pour le fichier .hash. La tentative de chargement de la table en mémoire peut échouer en raison d'une pénurie de mémoire ; dans ce cas, dbz échoue avec une erreur. Les écritures dans une base de données en mémoire ne sont pas (en général) écrites dans le fichier avant dbzclose ou dbzsync, donc si la robustesse en cas de plantages ou d'accès concurrents est cruciale, les bases de données en mémoire devraient probablement être évitées ou l'option writethrough devrait être définie sur true (indiquant d'écrire systématiquement sur le système de fichiers en plus de mettre à jour la base de données en mémoire).

Si l'option nonblock est vraie, alors les écritures dans les fichiers .hash et .index seront effectuées en utilisant des E/S non bloquantes. Cela peut être significativement plus rapide si votre plate-forme prend en charge les E/S non bloquantes avec les fichiers. Ceci n'est applicable que si vous ne mappez pas la base de données.

dbzsync provoque la purge de tous les tampons, etc., vers les fichiers. Il est généralement utilisé comme mesure de précaution contre les plantages ou les accès concurrents lorsqu'un processus utilisant dbz fonctionnera pendant une longue période. C'est une opération quelque peu coûteuse, surtout pour une base de données en mémoire.

La lecture concurrente des bases de données est relativement sûre, mais il n'y a pas de verrouillage (interne), donc la mise à jour concurrente ne l'est pas.

Une base de données ouverte occupe trois flux stdio et deux descripteurs de fichiers ; la consommation de mémoire est négligeable, à l'exception des bases de données en mémoire (et des tampons stdio).

DIAGNOSTICS

Les fonctions renvoyant des valeurs de type bool renvoient true en cas de succès, false en cas d'échec.

dbzinit tente de définir errno de manière plausible lors du retour, mais sinon, cela n'est pas garanti. Une valeur errno de "EDOM" retournée par dbzinit indique que la base de données ne semblait pas être au format dbz.

Si "DBZTEST" est défini au moment de la compilation, alors une fonction main() sera incluse. Celle-ci effectuera des tests de performance et d'intégrité.

BOGUES

Contrairement à dbm, dbz refusera de dbzstore avec une clé déjà présente dans la base de données. L'utilisateur est responsable d'éviter cela.

Le mappeur de casse RFC5322 implémente seulement une première approximation des règles de casse hideusement complexes de RFC5322.

dbz n'essaie plus d'être compatible avec dbm d'une quelconque manière.

libinn_dbz(3) - Arch Linux

NAME

libinn_dbz — functions for accessing dbz files

SYNOPSIS

#include <inn/dbz.h>

void *
dbz_open(const char *filename, const char *mode, ...);
void
dbz_close(void *dbz_ptr);
int
dbz_store(void *dbz_ptr, const char *key, const char *value);
char *
dbz_fetch(void *dbz_ptr, const char *key);
int
dbz_delete(void *dbz_ptr, const char *key);

DESCRIPTION

The dbz functions provide an interface to a simple database on disk. The database is created using the dbz_open() function. It is a simple hash-table like structure, stored on disk, that can hold key/value pairs. The keys and values are limited to 1024 bytes each.

dbz_open() opens a database file named filename in the specified mode. The supported modes are:

r
Open for reading.
w
Open for writing. If the file exists, it is truncated. If it does not exist, it is created.
a
Open for appending. If the file does not exist, it is created.

The dbz_close() function closes the database file.

dbz_store() stores the value associated with the key. If the key already exists, it will be overwritten.

dbz_fetch() retrieves the value associated with the key. The return value is a pointer to a statically allocated buffer, which will be overwritten by the next call to dbz_fetch() or dbz_delete(). If the key is not found, NULL is returned.

dbz_delete() deletes the entry associated with the key.

DIAGNOSTICS

The dbz functions return negative values on error.

BUGS

The keys and values are limited to 1024 bytes.

HISTORY

This implementation is derived from the C News package. The MD5 code was borrowed from RSA. Extensive reworking was done by Clayton O’Neill <coneill@oneill.net> to remove backward compatibility and add hashing into dbz files. Rewritten into POD by Julien Elie.

SEE ALSO

dbm(3), history(5), libinn(3).

NOM

libinn_dbz — fonctions d'accès aux fichiers dbz

SYNTAXE

#include <inn/dbz.h>

void *
dbz_open(const char *filename, const char *mode, ...);
void
dbz_close(void *dbz_ptr);
int
dbz_store(void *dbz_ptr, const char *key, const char *value);
char *
dbz_fetch(void *dbz_ptr, const char *key);
int
dbz_delete(void *dbz_ptr, const char *key);

DESCRIPTION

Les fonctions dbz fournissent une interface à une base de données simple sur disque. La base de données est créée à l'aide de la fonction dbz_open(). C'est une structure simple ressemblant à une table de hachage, stockée sur disque, qui peut contenir des paires clé/valeur. Les clés et les valeurs sont limitées à 1024 octets chacune.

dbz_open() ouvre un fichier de base de données nommé filename dans le mode spécifié mode. Les modes pris en charge sont :

r
Ouverture en lecture.
w
Ouverture en écriture. Si le fichier existe, il est tronqué. S'il n'existe pas, il est créé.
a
Ouverture en ajout. Si le fichier n'existe pas, il est créé.

La fonction dbz_close() ferme le fichier de base de données.

dbz_store() stocke la valeur associée à la clé. Si la clé existe déjà, elle sera écrasée.

dbz_fetch() récupère la valeur associée à la clé. La valeur de retour est un pointeur vers un tampon alloué statiquement, qui sera écrasé par le prochain appel à dbz_fetch() ou dbz_delete(). Si la clé n'est pas trouvée, NULL est retourné.

dbz_delete() supprime l'entrée associée à la clé.

DIAGNOSTICS

Les fonctions dbz retournent des valeurs négatives en cas d'erreur.

BOGUES

Les clés et les valeurs sont limitées à 1024 octets.

HISTORIQUE

Cette implémentation est dérivée du package C News. Le code MD5 a été emprunté à RSA. Un remaniement approfondi pour supprimer la compatibilité ascendante et ajouter le hachage dans les fichiers dbz a été effectué par Clayton O'Neill <coneill@oneill.net>. Réécrit en POD par Julien Elie.
