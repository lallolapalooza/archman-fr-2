RSA_GET_EX_NEW_INDEX(3) Manuel des fonctions de bibliothèque RSA_GET_EX_NEW_INDEX(3)

NOM

RSA_get_ex_new_index, RSA_set_ex_data, RSA_get_ex_data — ajouter des données spécifiques à l'application aux objets RSA

SYNTAXE

bibliothèque “libcrypto”
#include <openssl/rsa.h>

int
RSA_get_ex_new_index(long argl, void *argp, CRYPTO_EX_new *new_func, CRYPTO_EX_dup *dup_func, CRYPTO_EX_free *free_func);

int
RSA_set_ex_data(RSA *rsa, int idx, void *data);

void *
RSA_get_ex_data(RSA *rsa, int idx);

DESCRIPTION

Les objets parents suivants peuvent avoir des données spécifiques à l'application appelées "ex_data" attachées : BIO, DH, DSA, EC_KEY, RSA, SSL, SSL_CTX, SSL_SESSION, UI, X509, X509_STORE, et X509_STORE_CTX. La page de manuel actuelle documente les fonctions d'API associées prenant le type d'objet RSA en exemple. Les fonctions pour les autres types d'objets fonctionnent exactement de la même manière : remplacez simplement la chaîne "RSA" par le nom du type d'objet respectif dans le reste de cette page de manuel.

Par défaut, chaque objet RSA individuel peut stocker un void * pointant vers des données spécifiques à l'application. Ce pointeur spécifique est identifié par un argument idx de 0.

RSA_get_ex_new_index() réserve le prochain argument idx consécutif, permettant le stockage d'un pointeur void * supplémentaire par objet RSA. Il est généralement appelé au démarrage du programme. Il peut être appelé plus d'une fois si certains objets RSA doivent stocker plus de deux pointeurs spécifiques à l'application. La réservation d'un index supplémentaire pour un type d'objet parent, par exemple pour RSA, ne modifie pas le nombre d'indices pouvant être utilisés avec tout autre type d'objet parent.

Il est fortement recommandé de toujours passer trois pointeurs NULL pour les arguments new_func, dup_func, et free_func. En suivant cette recommandation, les arguments argl et argp sont ignorés ; conventionnellement, passer 0 et NULL est recommandé. Étant donné que leur utilisation est déconseillée, les trois types de fonctions de rappel ne sont documentés que dans la page de manuel de bas niveau CRYPTO_EX_new(3).

RSA_set_ex_data() stocke le pointeur data comme données spécifiques à l'application à l'index idxrsa donné. La signification des données pointées est à la charge de l'application. L'appelant conserve la propriété des data et est responsable de leur libération lorsque ni l'appelant ni l'objet rsa n'en ont plus besoin. Tout autre pointeur précédemment stocké au même idx dans le même objet rsa est silencieusement écrasé. Passer un pointeur NULL pour l'argument data est valide et indique qu'aucune donnée spécifique à l'application ne doit actuellement être stockée à l'index idx donné.

RSA_get_ex_data() récupère le dernier pointeur qui a été stocké à l'aide de RSA_set_ex_data() à l'index idx donné dans l'objet rsa donné.

VALEURS DE RETOUR

RSA_get_ex_new_index() retourne un nouvel index égal ou supérieur à 1, ou -1 en cas d'échec d'allocation de mémoire.

RSA_set_ex_data() retourne 1 en cas de succès ou 0 en cas d'échec d'allocation de mémoire.

RSA_get_ex_data() retourne les données spécifiques à l'application ou NULL si rsa ne contient pas de données spécifiques à l'application à l'index idx donné.

ERREURS

Après un échec de RSA_get_ex_new_index() ou RSA_set_ex_data(), le diagnostic suivant peut être récupéré avec ERR_get_error(3), ERR_GET_REASON(3), et ERR_reason_error_string(3) :

ERR_R_MALLOC_FAILURE "échec d'allocation mémoire"
L'allocation de mémoire a échoué.

Dans quelques rares cas d'échec, ERR_get_error(3) peut signaler d'autres erreurs causées par OPENSSL_init_crypto(3) ou même aucune.

RSA_get_ex_data() ne distingue pas le succès de l'échec. Par conséquent, après que RSA_get_ex_data() retourne NULL, ERR_get_error(3) retourne 0 sauf s'il y a encore une erreur antérieure dans la file d'attente.

VOIR AUSSI

BIO_set_ex_data(3), CRYPTO_set_ex_data(3), DH_set_ex_data(3), DSA_set_ex_data(3), RSA_new(3), SSL_CTX_set_ex_data(3), SSL_SESSION_set_ex_data(3), SSL_set_ex_data(3), X509_STORE_CTX_set_ex_data(3), X509_STORE_set_ex_data(3)

HISTORIQUE

Ces fonctions sont apparues pour la première fois dans SSLeay 0.9.0 et sont disponibles depuis OpenBSD 2.4.

AVERTISSEMENTS

Une minorité relativement faible de programmes d'application tentent de modifier le contrat de l'API de telle sorte que RSA_set_ex_data() transfère la propriété des data à l'objet rsa. Ils le font en fournissant une free_func qui appelle free(3) ou des fonctions *_free() de plus haut niveau sur les data et tentent parfois des actions de nettoyage supplémentaires comme effet secondaire.

Cette pratique est déconseillée pour plusieurs raisons :

  1. En raison d'une erreur de conception majeure dans la fonction d'API de bas niveau CRYPTO_free_ex_data(3), cette pratique crée la possibilité que RSA_free(3) échoue en raison d'un échec d'allocation de mémoire, entraînant une fuite de la mémoire contenant les données spécifiques à l'application et omettant silencieusement tout travail de nettoyage supplémentaire que la free_func était censée effectuer, laissant l'application dans un état incohérent indétectable. On pourrait dire que la fuite de mémoire supplémentaire tout en essayant d'en libérer est des plus malencontreuse, surtout lorsque le programme est déjà à court de mémoire.

Ce site n'est en aucun cas associé à Arch Linux ni affilié à ce projet. Le contenu est uniquement une traduction des pages de manuel d'Arch publiées sur man.archlinux.org.

  • Cette pratique introduit un risque de bogues d'utilisation après libération (use-after-free) et de double libération (double-free) dans le cas où l'objet rsa est détruit alors qu'un appelant de RSA_set_ex_data() ou RSA_get_ex_data() détient encore un pointeur data. Aucun risque de ce type n'existe lorsqu'aucun free_func n'est installé.
  • Tenter un travail de nettoyage supplémentaire dans free_func est une idée encore pire car free_func est incapable de signaler les problèmes qu'il pourrait détecter en effectuant ce travail. Au lieu de cela, si un travail de nettoyage supplémentaire est nécessaire, il est recommandé que le code appelant s'en charge avant d'appeler RSA_free(3).

    • Encore moins de programmes d'application installent un new_func qui alloue de la mémoire et stocke un pointeur vers celle-ci dans l'objet rsa en appelant CRYPTO_set_ex_data(3). Ceci est inutile car new_func n'a pas accès à des informations utiles qu'il pourrait stocker dans une telle mémoire et car la valeur de retour par défaut NULL de RSA_get_ex_data() est suffisante pour indiquer qu'aucune donnée spécifique à l'application n'a encore été stockée. De plus, allouer de la mémoire dans new_func est également déconseillé car cela introduit une responsabilité supplémentaire pour les appelants de RSA_set_ex_data() de toujours appeler RSA_get_ex_data() en premier, même lorsque c'est la première fois que l'application souhaite définir des données spécifiques à l'application dans un objet rsa particulier, et soit de modifier ce que RSA_get_ex_data() retourne, soit de le libérer avant d'appeler RSA_set_ex_data(). Si cela est oublié, une fuite de mémoire en résulte.

    Par conséquent, il est préférable de laisser l'allocation de toute mémoire requise au code de l'application qui appelle RSA_set_ex_data().

    L'installation d'une dup_func est souvent observée en combinaison avec l'installation d'une free_func, pour des raisons évidentes. Elle est rarement utile car pour la plupart des types d'objets parents qui prennent en charge ex_data, y compris pour RSA, la bibliothèque ne fournit pas de fonction API de copie en premier lieu, et même là où des fonctions de copie existent, elles ont tendance à être fragiles et sujettes aux erreurs. Lorsqu'un nouvel objet est nécessaire, il est généralement conseillé de le construire à partir de zéro autant que possible, plutôt que de tenter une opération de copie.

    De plus, si dup_func échoue, par exemple en raison d'un échec d'allocation mémoire, l'échec n'est ni signalé ni détectable de quelque manière que ce soit, laissant le nouvel objet parent avec des données incomplètes et potentiellement dans un état incohérent.

    BUGS

    Si RSA_set_ex_data() échoue, la récupération est très difficile. En particulier, appeler RSA_free(3) sur l'objet parent rsa juste après risque également de rencontrer un échec d'allocation mémoire, laissant échapper toute mémoire allouée en interne par tous les appels précédents de RSA_set_ex_data() sur rsa au lieu de libérer cette mémoire. Afin de récupérer, le programme d'application devrait libérer une quantité suffisante d'autre mémoire avant d'appeler RSA_free(3), ce qui sera rarement réalisable. Par conséquent, après un échec de RSA_set_ex_data(), terminer le programme est probablement la seule option raisonnable.

    Si RSA_set_ex_data() est appelé avec un argument idx supérieur au dernier précédemment retourné par RSA_get_ex_new_index(), il peut toujours réussir, et bien que cela ne soit pas garanti par l'API, récupérer le data à partir d'un idx erroné peut même être possible avec RSA_get_ex_data(), masquant ainsi le bogue dans le programme d'application qui a causé le passage du idx erroné à RSA_set_ex_data() en premier lieu.

    Si l'argument idx erroné est grand, RSA_set_ex_data() peut allouer inutilement une grande quantité de mémoire. Appeler RSA_free(3) sur l'objet parent rsa est le seul moyen de récupérer cette mémoire.

    Si l'argument idx erroné est très grand, RSA_set_ex_data() risque de provoquer un retard important avant d'échouer éventuellement en raison d'une exhaustion de mémoire. Il risque de retourner sans libérer la mémoire déjà allouée, provoquant ainsi l'échec de toute tentative ultérieure d'allocation de mémoire à d'autres fins. Dans cette situation, ce qui a été dit ci-dessus concernant l'échec de RSA_set_ex_data() s'applique, donc terminer le programme est probablement la seule option raisonnable.
