libhavege(3) FONCTIONS BIBLIOTHÈQUE libhavege(3)

NOM

libhavege, havege_create, havege_run, havege_rng, havege_destroy, havege_status, havege_status_dump, havege_version - Générateur de nombres aléatoires Haveged

SYNOPSIS

#include <haveged/havege.h>
H_PARAMS params = {0};
h_status status;
char     status_buf[512];
if (NULL==havege_version(HAVEGE_PREP_VERSION)) exit(1);
H_PTR handle = havege_create(&params);
havege_status(handle, &status);
havege_run(handle);
rc = havege_rng(handle, handle->io_buf, handle->i_readSz/sizeof(H_UINT));
havege_status_dump(handle, H_SD_TOPIC_BUILD, status_buf, sizeof(status_buf));
havege_destroy(handle);

DESCRIPTION

La bibliothèque libhavege fournit le générateur de nombres aléatoires haveged et ses installations de réglage et de test associées dans un sous-paquet de développement. Toutes les fonctionnalités de construction conditionnelle de haveged sont préservées et toutes les options de haveged non directement liées à son interface de démon ou de système de fichiers sont disponibles. Cela signifie que les mêmes composants de réglage et de test de haveged sont présents dans la bibliothèque avec les contrôles équivalents fournis par la commande haveged.

MÉTHODES API

La bibliothèque libhavege utilise la technique de handle opaque pour gérer ses ressources requises. Les erreurs sont retournées dans le membre "error" du handle. La méthode havege_destroy() doit être appelée pour supprimer toutes les ressources réclamées par havege_create().

H_PTR havege_create(H_PARAMS *params);

Crée une ancre. La plupart des membres de l'entrée H_PARAMS pour cet appel correspondent étroitement aux options de ligne de commande de haveged (voir haveged(8) pour les détails). L'appelant doit vérifier une valeur de retour non nulle avec une valeur d'erreur de H_NOERR. Toute valeur de retour non nulle doit être supprimée par un appel à havege_destroy() pour libérer toutes les ressources. Erreurs possibles : H_NOERR, H_NOTESTSPEC, H_NOBUF, H_NOTESTMEM, H_NOINIT

void havege_destroy(H_PTR hptr);

Libère toutes les ressources d'ancre allouées. Si l'option multi-cœur est utilisée, cette méthode doit être appelée depuis un gestionnaire de signaux pour éviter les processus zombies. Si elle est appelée par le processus qui a appelé haveged_create(), hptr sera libéré lorsque tous les processus enfants (le cas échéant) auront terminé. Si elle est appelée par un processus enfant, H_EXIT sera défini et tous les enfants seront réveillés pour quitter.

int havege_rng(H_PTR hptr, H_UINT *buf, H_UINT sz);

Lit des octets aléatoires à partir d'une ancre active. Le RNG doit avoir été préalablement préparé par un appel à havege_run(). La lecture doit avoir lieu dans le buffer alloué, hptr->io_buf. La plage spécifiée est le nombre de H_UINT à lire. Si l'option multi-cœur est utilisée, ce buffer est mappé en mémoire entre les collecteurs. Erreurs possibles : H_NOERR, H_NOTESRUN, H_NOPOST, H_NODONE, H_NORQST, H_NOCOMP, H_EXIT

int havege_run(H_PTR hptr);

Chauffe le RNG et exécute les tests de démarrage. L'opération a réussi si le membre d'erreur du handle est H_NOERR. Un handle échoué doit être supprimé par un appel à havege_destroy(). Erreurs possibles : H_NOERR, H_NOCOLLECT, H_NOWALK, H_NOTESTMEM, H_NOTASK, H_NOTESTTOT, H_NOWAIT, H_NOTIMER, et toute erreur de havege_rng().

void havege_status(H_PTR hptr, H_STATUS hsts);

Remplit la structure h_status avec des informations en lecture seule collectées à partir de la construction du paquet, du réglage à l'exécution et des composants de test.

int havege_status_dump(H_PTR hptr, H_SD_TOPIC topic, char *buf, size_t len);

Appelle havege_status() et formate des présentations standard de l'état de havege dans le buffer fourni. Les formats standard sont :

H_SD_TOPIC_BUILD

ver: %s; arch: %s; vend: %s; build: (%s); collect: %dK

H_SD_TOPIC_TUNE

cpu: (%s); data: %dK (%s); inst: %dK (%s); idx: %d/%d; sz: %d/%d

H_SD_TOPIC_TEST

[tot tests(%s): A:%d/%d B: %d/%d;][tests continus(%s): A:%d/%d B: %d/%d;][dernière estimation entropie %g]

H_SD_TOPIC_SUM

fills: %d, generated: %.4g %c bytes

const char *havege_version(const char *version);

Retourne/vérifie la version de préparation de la bibliothèque. La version de préparation est la version du paquet utilisée pour construire la bibliothèque. Un argument nul retourne la version de préparation inconditionnellement. Utiliser la définition de la chaîne de préparation dans havege.h comme entrée retourne la version de préparation si le fichier d'en-tête est compatible avec la bibliothèque, ou NULL s'il ne l'est pas. Conçu pour être appelé avant de tenter toute initialisation.

NOTES

Les tailles des caches d'instructions et de données de niveau 1 du processeur sont utilisées pour ajuster l'algorithme HAVEGE pour une sensibilité maximale. Si ces tailles ne sont pas spécifiées, haveged tentera de déterminer les tailles dynamiquement à partir du sysfs Linux et/ou de l'instruction cpuid avec un recours à une valeur par défaut compilée si aucune meilleure information n'est disponible.

Le générateur de nombres aléatoires haveged comprend une installation de test d'exécution basée sur la suite de tests définie dans la spécification AIS-31 du Bureau fédéral allemand pour la sécurité de l'information (Bundesamt für Sicherheit in der Informationstechnik). La suite de tests se compose de 11 tests statistiques regroupés en deux suites de tests ("A" et "B"). Les tests peuvent être exécutés à l'initialisation (également appelé test "tot"), ou en continu pour surveiller toutes les sorties. L'échec d'une suite entraînera l'abandon de l'opération, sauf si le comportement est explicitement autorisé dans les options de configuration du test.

La procédure A contient 6 procédures de test conçues pour garantir un comportement statistiquement discret. Le premier test, "test0", vérifie l'injonction de 65k chaînes de six bits. Le reste de la procédure consiste en 257 répétitions des tests FIPS140-1, "test1" à "test4", et un test d'auto-corrélation, "test5". La taille fixe de l'entrée de la procédure A la rend idéale pour une utilisation continue, mais la procédure est lente et gourmande en ressources. En particulier, test5 est plusieurs ordres de grandeur plus lent que tout autre test AIS individuel. Comme alternative pour ceux qui ne peuvent tolérer cette charge, des variantes A<n> de la procédure A sont fournies qui exécutent tous les tests inclus mais exécutent test5 seulement toutes les 2^n répétitions. Même avec cet arrangement, la procédure A est beaucoup plus lente que la procédure B.

La procédure B contient 5 tests, "test6a", "test6b", "test7a", "test7b" et "test8". Les 4 premiers tests vérifient les fréquences attendues pour des échantillons de 100 000 transitions de bits à une étape, deux étapes, trois étapes et quatre étapes. Le dernier test fournit une estimation empirique de l'entropie de l'entrée. L'entrée requise pour compléter ces tests est variable, résultant en un alignement de bits toujours changeant qui protège contre les artefacts de mise en mémoire tampon.

Chaque procédure de test nécessite plus de 1 Mo de données. L'entrée de test est gérée par un index de bits dans le buffer de collecte. Un index indépendant gère l'endroit où la sortie entière est extraite du même buffer. Un remplissage du buffer est déclenché lorsque l'index de sortie indique que toutes les données ont été extraites du buffer. Les tests en ligne ont lieu après que le buffer a été rechargé mais avant que la mise à jour de l'index de sortie ne permette la reprise de la sortie. Si un test en ligne échoue lors du traitement du buffer, le buffer sera rechargé et retraité jusqu'à ce que toute tentative soit terminée et que le buffer ne contienne plus de tests en ligne échoués, ou que la procédure de test en ligne ait échoué et que le générateur de nombres aléatoires soit considéré comme défectueux.

Il est recommandé d'exécuter les deux procédures de test AIS au démarrage pour s'assurer que le générateur de nombres aléatoires est correctement initialisé. Si les ressources sont limitées, omettre la procédure A permettra d'économiser de la mémoire et du temps, avec peu de risque dans les circonstances où la sortie est mélangée avec d'autres sources dans /dev/random ou d'autres csprng. Les tests continus sont également recommandés lorsque la pénalité de débit est acceptable. Une évaluation récente des coûts de performance des tests est présentée ci-dessous.

haveged -n0 -oc | pv > /dev/null
400MiB/s
haveged -n0 -ocb | pv > /dev/null
70MiB/s
haveged -n0 -oca8b | pv > /dev/null
13MiB/s
haveged -n0 -oca8 | pv > /dev/null
8MiB/s
haveged -n0 -oca | pv > /dev/null
100kiB/s

La politique de nouvelle tentative stricte de l'AIS-31 est conçue pour garantir qu'un RNG idéal échouera « presque jamais » à une procédure de test. Une seule nouvelle tentative est obligatoire uniquement pour récupérer d'une tentative précédente qui a connu un échec individuel lors d'un test. L'implémentation haveged enregistre toutes les nouvelles tentatives et se termine en cas d'échec d'une procédure de test, sauf si la procédure a été marquée comme consultative par l'argument « w » (voir --onlinetest dans haveged(8)). Peu de preuves du mécanisme de nouvelle tentative sont visibles, sauf si de grands ensembles de données sont traités. La procédure A est trop lente pour être pratique dans ces situations, donc la procédure B a été la mieux étudiée. Les nouvelles tentatives sont observées au taux approximatif de 0,7 à 0,8 échecs/Go, principalement dans les vérifications multi-étapes de test7.

La probabilité que la procédure B échoue deux fois de suite (auquel cas le programme sera terminé, sauf si l'option w a été spécifiée) est de 4e-7, ce qui devrait se produire à un taux approximatif d'une fois par 3 000 To. Lors de la production de grandes quantités de données de l'ordre de quelques To, il est recommandé d'utiliser l'option -w pour s'assurer que le programme ne se termine pas prématurément en raison d'un échec de nouvelle tentative et d'examiner attentivement la sortie stderr pour tout problème.

Pas de mémoire pour le handle

02 H_NOBUF

Échec de l'allocation du tampon de sortie

04 H_NOCOLLECT

Échec de l'allocation du collecteur

05 H_NOWALK

EXEMPLE

Le programme minimal suivant écrit le contenu de 16 tampons de collecte de données aléatoires sur la sortie standard avec des tests continus.

#include <stdio.h>
#include <haveged/havege.h>
int main(void)
{
H_PTR havege_state;
H_PARAMS havege_parameters = {0};
int i, rc;
if (NULL==havege_version(HAVEGE_PREP_VERSION)) {
  fprintf(stderr, "Incompatible library %s\n", havege_version(NULL));
  return 1;
  }
havege_parameters.testSpec="ta8bcb";
havege_state = havege_create(&havege_parameters);
rc = havege_state==NULL? H_NOHANDLE : havege_state->error;
if (H_NOERR==rc) {
  if (0==havege_run(havege_state)) {
    H_UINT *buf = havege_state->io_buf;
    int size = havege_state->i_readSz /sizeof(H_UINT);
    char info[256];
    for(i=0;i<16;i++) {
        rc = havege_rng(havege_state, buf, size);
        if (rc != size) {
            fprintf(stderr, "RNG read failed %d\n", havege_state->error);
            break;
            }
        rc = fwrite(buf, 1, size*sizeof(H_UINT), stdout);
        if ( rc < size ) {
            fprintf(stderr, "Write failed\n");
            break;
            }
        }
    i = havege_status_dump(havege_state, H_SD_TOPIC_TEST, info, sizeof(info));
    info[i++] = '\n';
    havege_status_dump(havege_state, H_SD_TOPIC_SUM, info+i, sizeof(info)-i);
    fprintf(stderr, "%s\n", info);
    }
  else fprintf(stderr, "Initialize failed %d\n", havege_state->error);
  havege_destroy(havege_state);
  }
else fprintf(stderr, "Create failed %d\n", rc);
return rc;
}

Les valeurs par défaut sont fournies pour toutes les entrées de havege_create() telles que documentées dans havege.h. Dans ce cas, par exemple, (16 * 4 ko = 65 ko) seront écrits sur la sortie standard car la taille par défaut de i_readsz est de 4 ko.
