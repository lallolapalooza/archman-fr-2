DESCRIPTION

BIO_s_bio() retourne la méthode pour une paire BIO. Une paire BIO est une paire de BIOs source/sink où les données écrites dans l'une ou l'autre moitié de la paire sont mises en tampon et peuvent être lues depuis l'autre moitié. Les deux moitiés doivent généralement être gérées par le même thread d'application car aucune synchronisation n'est effectuée sur les structures de données internes.

Les chaînes BIO se terminant généralement par un BIO source/sink, il est possible d'en faire une moitié d'une paire BIO et d'avoir toutes les données traitées par la chaîne sous le contrôle de l'application.

Une utilisation typique des paires BIO est de placer les E/S TLS/SSL sous le contrôle de l'application. Ceci peut être utilisé lorsque l'application souhaite utiliser un transport non standard pour TLS/SSL ou lorsque les routines de socket normales sont inappropriées.

Les appels à BIO_read(3) liron des données depuis le tampon ou demanderont une nouvelle tentative s'il n'y a pas de données disponibles.

Les appels à BIO_write(3) placeront des données dans le tampon ou demanderont une nouvelle tentative si le tampon est plein.

Les appels standard BIO_ctrl_pending(3) et BIO_ctrl_wpending(3) peuvent être utilisés pour déterminer la quantité de données en attente dans le tampon de lecture ou d'écriture.

BIO_reset(3) efface toutes les données du tampon d'écriture.

BIO_make_bio_pair() relie deux BIOs séparés en une paire connectée.

BIO_destroy_pair() détruit l'association entre deux BIOs connectés. La libération de l'une ou l'autre moitié de la paire détruira automatiquement l'association.

BIO_shutdown_wr() est utilisée pour fermer un BIO b. Après cet appel, aucune écriture ultérieure sur le BIO b n'est autorisée ; elles retourneront une erreur. Les lectures sur l'autre moitié de la paire retourneront toutes les données en attente ou EOF une fois que toutes les données en attente auront été lues.

BIO_set_write_buf_size() définit la taille du tampon d'écriture du BIO b à size. Si la taille n'est pas initialisée, une valeur par défaut est utilisée. Elle est actuellement de 17 Ko, suffisante pour un enregistrement TLS de taille maximale. Lorsque une chaîne contenant une paire BIO est copiée avec BIO_dup_chain(3), la taille du tampon d'écriture est automatiquement copiée de l'objet BIO d'origine vers le nouveau.

BIO_get_write_buf_size() retourne la taille du tampon d'écriture.

BIO_new_bio_pair() combine les appels à BIO_new(3), BIO_make_bio_pair() et BIO_set_write_buf_size() pour créer une paire connectée de BIOs bio1 et bio2 avec des tailles de tampon d'écriture writebuf1 et writebuf2. Si l'une des tailles est nulle, alors la taille par défaut est utilisée. BIO_new_bio_pair() ne vérifie pas si bio1 ou bio2 pointe vers un autre BIO ; les valeurs sont écrasées et BIO_free(3) n'est pas appelé.

BIO_get_write_guarantee() et BIO_ctrl_get_write_guarantee() retournent la longueur maximale de données qui peuvent actuellement être écrites dans le BIO. Les écritures dont la taille est supérieure à cette valeur retourneront une valeur de BIO_write(3) inférieure à la quantité demandée ou, si le tampon est plein, demanderont une nouvelle tentative. BIO_ctrl_get_write_guarantee() est une fonction tandis que BIO_get_write_guarantee() est une macro.

BIO_get_read_request() et BIO_ctrl_get_read_request() retournent la quantité de données demandée, ou la taille du tampon si elle est inférieure, si la dernière tentative de lecture de l'autre moitié de la paire BIO a échoué en raison d'un tampon vide. Ceci peut être utilisé pour déterminer combien de données doivent être écrites dans le BIO afin que la prochaine lecture réussisse : ceci est particulièrement utile dans les applications TLS/SSL où la quantité de données lues est généralement significative plutôt qu'une simple taille de tampon. Après une lecture réussie, cet appel retournera zéro. Il retournera également zéro une fois que de nouvelles données auront été écrites, satisfaisant ainsi la demande de lecture (en tout ou en partie). Notez que BIO_get_read_request() ne retourne jamais une quantité supérieure à celle retournée par BIO_get_write_guarantee().

BIO_ctrl_reset_read_request() peut également être utilisé pour réinitialiser la valeur retournée par BIO_get_read_request() à zéro.

Les deux moitiés d'une paire BIO doivent être libérées. Même si une moitié est libérée implicitement à la suite d'un appel à BIO_free_all(3) ou SSL_free(3), l'autre moitié doit toujours être libérée.

Lorsqu'utilisé dans des applications bidirectionnelles (comme TLS/SSL), il faut veiller à vider toute donnée dans le tampon d'écriture. Cela peut être fait en appelant BIO_pending(3) sur l'autre moitié de la paire et, si des données sont en attente, en les lisant et en les envoyant au transport sous-jacent. libressl(7) — OpenSSL BIO pair

NAME

BIO_s_bio, BIO_new_bio_pair, BIO_free_pair, BIO_destroy_bio_pair, BIO_set_write_buf_size, BIO_get_write_buf_size, BIO_get_write_guarantee, BIO_ctrl_get_write_guarantee, BIO_get_read_request, BIO_ctrl_reset_read_request, BIO_shutdown_wr - BIO pair

SYNOPSIS

 #include <openssl/bio.h>

 BIO_METHOD *BIO_s_bio(void);
int BIO_new_bio_pair(BIO **bio1_out, size_t writebuf1, BIO **bio2_out, size_t writebuf2);
void BIO_free_pair(BIO *bio1, BIO *bio2);
void BIO_destroy_bio_pair(BIO *bio1, BIO *bio2);
long BIO_set_write_buf_size(BIO *bio, size_t size);
long BIO_get_write_buf_size(BIO *bio);
long BIO_get_write_guarantee(BIO *bio);
long BIO_ctrl_get_write_guarantee(BIO *bio);
long BIO_get_read_request(BIO *bio);
long BIO_ctrl_reset_read_request(BIO *bio);
long BIO_shutdown_wr(BIO *bio);

DESCRIPTION

A BIO pair is a BIO that simulates a two-way data channel. It is composed of two BIO objects, let's call them bio1 and bio2. Writes to bio1 are read from bio2, and writes to bio2 are read from bio1.

This is useful for testing applications that use the BIO interface, and specifically for applications that use SSL_set_bio(3) to set up BIOs for SSL operations.

The BIO pair is essentially a buffering mechanism. Reads and writes will behave in a non-blocking manner. A write operation will return as soon as the write buffer is full, and a read operation will return as soon as the read buffer is drained. The application is responsible for ensuring that data is moved between the BIOs when necessary. This is typically done using select(2) to wait for data to become available on the underlying transport, and then calling BIO_read(3) and BIO_write(3) to transfer data.

The main difference between BIO_new_bio_pair() and BIO_make_bio_pair() is that BIO_new_bio_pair() creates new, independent BIO pair objects, while BIO_make_bio_pair() links two existing BIO objects together to form a pair.

BIO_free_pair() and BIO_destroy_bio_pair() free the two BIOs that form the pair. BIO_free_pair() leaves the BIO objects themselves intact, while BIO_destroy_bio_pair() frees the BIO objects as well.

BIO_set_write_buf_size() and BIO_get_write_buf_size() can be used to set and get the size of the write buffer for a BIO in the pair. The default size is 4096 bytes.

BIO_get_write_guarantee() and BIO_ctrl_get_write_guarantee() return the number of bytes that are guaranteed to be writeable in the BIO without blocking. This is typically the size of the write buffer minus the amount of data already in the buffer.

BIO_get_read_request() and BIO_ctrl_reset_read_request() are used to manage the number of bytes that must be written to the BIO before an SSL operation can proceed. This is used internally by OpenSSL, for example, during the TLS handshake.

BIO_shutdown_wr() signals that the writing side of the BIO pair is shut down. This means that no more data will be written to this BIO. Reads from the other BIO in the pair will return EOF once any buffered data has been consumed.

BIO_eof(3) is true if no data is in the peer BIO and the peer BIO has been shutdown.

RETURN VALUES

BIO_new_bio_pair() returns 1 on success, with the new BIOs available in bio1 and bio2, or 0 on failure, with NULL pointers stored into the locations for bio1 and bio2. Check the error stack for more information.

When called on a BIO pair BIO object, BIO_method_type(3) returns the constant BIO_TYPE_BIO and BIO_method_name(3) returns a pointer to the static string "BIO pair".

EXAMPLES

The BIO pair can be used to have full control over the network access of an application. The application can call select(2) on the socket as required without having to go through the SSL interface.

BIO *internal_bio, *network_bio;
...
BIO_new_bio_pair(&internal_bio, 0, &network_bio, 0);
SSL_set_bio(ssl, internal_bio, internal_bio);
SSL_operations();  /* e.g. SSL_read() and SSL_write() */
...

application |   TLS-engine
   |        |
   +----------> SSL_operations()
            |     /\    ||
            |     ||    \/
            |   BIO-pair (internal_bio)
            |   BIO-pair (network_bio)
            |     ||     /\
            |     \/     ||
   +-----------< BIO_operations()
   |        |
 socket     |

...
SSL_free(ssl);		/* implicitly frees internal_bio */
BIO_free(network_bio);
...

As the BIO pair will only buffer the data and never directly access the connection, it behaves non-blocking and will return as soon as the write buffer is full or the read buffer is drained. Then the application has to flush the write buffer and/or fill the read buffer.

Use BIO_ctrl_pending(3) to find out whether data is buffered in the BIO and must be transferred to the network. Use BIO_ctrl_get_read_request() to find out how many bytes must be written into the buffer before the SSL operations can successfully be continued.

CAVEATS

As the data is buffered, SSL operations may return with an ERROR_SSL_WANT_READ condition, but there is still data in the write buffer. An application must not rely on the error value of the SSL operation but must assure that the write buffer is always flushed first. Otherwise a deadlock may occur as the peer might be waiting for the data before being able to continue.
