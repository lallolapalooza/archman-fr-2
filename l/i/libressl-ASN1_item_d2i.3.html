DESCRIPTION

Ces fonctions convertissent les valeurs ASN.1 de leur encodage BER en structures C internes (« d2i ») et vice versa (« i2d »). Contrairement aux structures C qui contiennent des pointeurs vers des sous-objets, BER est un encodage sérialisé, adapté au transfert sur le réseau et au stockage dans un fichier.

ASN1_item_d2i() interprète *der_in comme un tableau d'octets encodé en DER ou BER et décode une valeur de type it représentée par jusqu'à length octets. En cas de succès, *der_in est avancé à l'octet suivant les données parsées.

Si le décodage réussit et que val_out ou *val_out est NULL, un nouvel objet est alloué.

Si le décodage réussit et que *val_out n'est pas NULL, il est supposé pointer vers un objet valide et peuplé, et une tentative est faite pour le réutiliser. Il ne doit pas s'agir d'une structure vide telle que celle retournée par ASN1_item_new(3) ou par l'une des fonctions *_new() spécifiques à un type. Cette capacité de « réutilisation » est présente pour assurer la compatibilité ascendante, mais son utilisation est fortement déconseillée ; voir la section ERREURS ci-dessous.

ASN1_item_d2i_bio() et ASN1_item_d2i_fp() sont similaires à ASN1_item_d2i() sauf qu'elles lisent à partir d'un BIO ou d'un FILE, respectivement.

d2i_ASN1_TYPE() est similaire à ASN1_item_d2i() sauf qu'elle ne nécessite pas qu'un type désiré soit spécifié par l'utilisateur, mais retourne au lieu de cela un objet wrapper ASN1_TYPE contenant à la fois le type et la valeur trouvés dans l'entrée.

ASN1_item_i2d() encode l'objet pointé par val_in au format DER.

Si *der_out n'est pas NULL, il écrit les données encodées DER dans le tampon à *der_out et l'incrémente pour pointer après les données qui viennent d'être écrites. Dans ce cas, il incombe à l'utilisateur de s'assurer que le tampon pointé par *der_out est suffisamment long, de sorte qu'aucun débordement de tampon ne puisse se produire.

Si *der_out est NULL, de la mémoire est allouée pour un tampon, et *der_out n'est pas incrémenté, mais pointe vers le début des données qui viennent d'être écrites.

Si der_out est NULL, les octets encodés ne sont écrits nulle part mais sont rejetés. Pour les objets val_inASN1_item_i2d(). Cette technique explicite d'appel double n'est souvent pas nécessaire car la technique d'auto-allocation décrite dans le paragraphe précédent peut être utilisée.

ASN1_item_i2d_bio() et ASN1_item_i2d_fp() sont similaires à ASN1_item_i2d() sauf qu'elles écrivent dans un BIO ou un FILE, respectivement.

i2d_ASN1_TYPE() est similaire à ASN1_item_i2d() sauf que le type et la valeur ne sont pas fournis séparément, mais sous la forme d'un seul objet ASN1_TYPE.

ASN1_item_dup() crée une copie profonde de val_in en appelant ASN1_item_i2d() et ASN1_item_d2i().

VALEURS DE RETOUR

En cas de succès, ASN1_item_d2i(), ASN1_item_d2i_bio(), ASN1_item_d2i_fp(), et d2i_ASN1_TYPE() retournent un pointeur vers la valeur ASN.1 décodée. De plus, si val_out n'est pas NULL, le pointeur est également écrit dans *val_out. Si une erreur se produit, NULL est retourné.

ASN1_item_i2d() et i2d_ASN1_TYPE() retournent le nombre d'octets écrits ou une valeur négative en cas d'erreur.

ASN1_item_i2d_bio() et ASN1_item_i2d_fp() retournent 1 en cas de succès ou 0 en cas d'échec.

ASN1_item_dup() retourne le nouvel objet ASN1_VALUE ou NULL en cas d'erreur.

EXEMPLES

De nombreuses fonctions enveloppantes spécifiques au type existent. L'utilisation de ces enveloppes est recommandée dans le code applicatif car elle rétablit une partie de la sécurité des types dont manquent les interfaces de bas niveau utilisant ASN1_VALUE.

Par exemple, pour allouer un tampon

et écrire le codage DER d'un objet X509 dedans :

X509		*x;
unsigned char	*buf;
int		 len;

buf = NULL;
len = i2d_X509(x, &buf);
if (len < 0)
	/* erreur */

Tentative de décodage d'un tampon :

X509			*x;
unsigned char		*buf;
const unsigned char	*p;
int			 len;

/* Configurer buf et len pour pointer vers le tampon d'entrée. */
p = buf;
x = d2i_X509(NULL, &p, len);
if (x == NULL)
	/* erreur */

Technique équivalente :

X509			*x;
unsigned char		*buf;
const unsigned char	*p;
int			 len;

/* Configurer buf et len pour pointer vers le tampon d'entrée. */
p = buf;
x = NULL;

if (d2i_X509(&x, &p, len) == NULL)
	/* erreur */

HISTORIQUE

d2i_ASN1_TYPE() et i2d_ASN1_TYPE() sont apparus pour la première fois dans SSLeay 0.5.1 et sont disponibles depuis OpenBSD 2.4.

ASN1_item_d2i(), ASN1_item_d2i_bio(), ASN1_item_d2i_fp(), ASN1_item_i2d(), ASN1_item_i2d_bio(), ASN1_item_i2d_fp(), et ASN1_item_dup() sont apparus pour la première fois dans OpenSSL 0.9.7 et sont disponibles depuis OpenBSD 3.2.

ASN1_item_print() est apparu pour la première fois dans OpenSSL 1.0.0 et est disponible depuis OpenBSD 4.9.

MISE EN GARDE

Si le type décrit par it ne correspond pas au type réel de val_in ou *val_out, des dépassements de tampon et des fautes de segmentation sont susceptibles de se produire. Pour plus de détails sur la raison pour laquelle le type ASN1_VALUE constitue une conception d'interface utilisateur dangereuse, voir ASN1_item_new(3).

Les données codées sont sous forme binaire et peuvent contenir des octets NUL intégrés. Les fonctions telles que strlen(3) ne retourneront pas la longueur correcte des données codées.

Bien que la manière dont *der_in et *der_out sont incrémentés après l'opération prenne en charge les modèles d'utilisation typiques de lecture ou d'écriture d'un objet après l'autre, ce comportement peut piéger les imprudents.

L'utilisation d'un pointeur temporaire dans le tampon est obligatoire. Une erreur courante consiste à tenter d'utiliser un tampon directement comme suit :

X509		*x;
unsigned char	*buf;
int		 len;

len = i2d_X509(x, NULL);
buf = malloc(len);
i2d_X509(x, &buf);
/* faire quelque chose avec buf[] */
free(buf);

Ce code entraînera le fait que buf contiendra apparemment des données incorrectes car il a été incrémenté pendant i2d_X509() pour pointer après les données qui viennent d'être écrites. De plus, buf ne contiendra plus le pointeur alloué par malloc(3) et l'appel ultérieur à free(3) risquera de planter.

Un autre piège à éviter est la mauvaise utilisation de l'argument val_out :

X509		*x;

if (d2i_X509(&x, &p, len) == NULL)
	/* erreur */

Cela plantera probablement quelque part dans d2i_X509() car x n'est pas initialisé et une tentative sera faite pour interpréter son contenu invalide comme un objet X509, provoquant généralement une violation de segmentation. Si x est mis à NULL en premier, cela ne se produira pas.

BOGUES

Si la capacité de "réutilisation" est utilisée, un objet valide est passé via *val_out, et une erreur se produit, alors l'objet n'est pas libéré et peut être laissé dans un état invalide ou incohérent.

Dans certaines versions d'OpenSSL, le comportement de "réutilisation" est défectueux, de sorte que certaines parties de l'objet réutilisé peuvent persister si elles ne sont pas présentes dans le nouvel objet.

Dans de nombreuses versions d'OpenSSL, ASN1_item_i2d() ne retournera pas d'erreur si des champs obligatoires ne sont pas initialisés en raison d'une erreur de programmation. Dans ce cas, la structure codée peut contenir des données invalides et certains champs peuvent être entièrement manquants, de sorte que tenter de l'analyser avec ASN1_item_d2i() peut échouer.
