libcurl-security - considérations de sécurité lors de l'utilisation de libcurl

Sécurité

Le projet libcurl prend la sécurité au sérieux. La bibliothèque est écrite avec prudence et des précautions sont prises pour atténuer de nombreux types de risques rencontrés lors de l'opération avec des serveurs potentiellement malveillants sur Internet. C'est cependant une bibliothèque puissante, qui permet aux développeurs d'applications de faire des compromis entre la facilité d'écriture et l'exposition à des opérations potentiellement risquées. Si elle est utilisée correctement, vous pouvez utiliser libcurl pour transférer des données de manière assez sûre.

De nombreuses applications sont utilisées dans des réseaux fermés où les utilisateurs et les serveurs peuvent (éventuellement) être fiables, mais beaucoup d'autres sont utilisées sur des serveurs arbitraires et reçoivent des entrées d'utilisateurs potentiellement non fiables. Ce qui suit est une discussion sur certains risques dans la manière dont les applications utilisent couramment libcurl et les atténuations potentielles de ces risques. Ce n'est pas exhaustif, mais cela montre des classes d'attaques que les applications robustes devraient considérer. Le projet Common Weakness Enumeration sur https://cwe.mitre.org/ est une bonne référence pour bon nombre de ces faiblesses et similaires dont les développeurs d'applications devraient être conscients.

Lignes de commande

Si vous utilisez un outil en ligne de commande (comme curl) qui utilise libcurl, et que vous donnez des options à l'outil en ligne de commande, ces options peuvent être lues par d'autres utilisateurs de votre système lorsqu'ils utilisent ps ou d'autres outils pour lister les processus en cours d'exécution.

Pour éviter ces problèmes, ne fournissez jamais d'éléments sensibles à des programmes utilisant des options en ligne de commande. Écrivez-les dans un fichier protégé et utilisez l'option -K pour éviter cela.

.netrc

Le fichier .netrc est une fonctionnalité pratique qui permet de se connecter rapidement et automatiquement à des sites fréquemment visités. Le fichier contient des mots de passe en texte clair et constitue un risque de sécurité réel. Dans certains cas, votre .netrc est également stocké dans un répertoire personnel monté via NFS ou utilisé sur un autre système de fichiers en réseau, de sorte que le mot de passe en texte clair circule sur votre réseau chaque fois que quelqu'un lit ce fichier.

Pour les applications qui activent l'utilisation de .netrc, un utilisateur qui parvient à définir la bonne URL pourrait alors passer des mots de passe.

Pour éviter ces problèmes, n'utilisez pas les fichiers .netrc et ne stockez jamais de mots de passe en texte clair où que ce soit.

Mots de passe en texte clair

Beaucoup de protocoles que libcurl prend en charge envoient le nom et le mot de passe sans chiffrement en texte clair (authentification HTTP de base, FTP, TELNET etc.). Il est facile pour quiconque sur votre réseau ou un réseau proche du vôtre de lancer un outil d'analyse réseau et d'écouter vos mots de passe. Ne laissez pas le fait que l'authentification HTTP de base utilise des mots de passe encodés en base64 vous tromper. Ils peuvent ne pas paraître lisibles au premier abord, mais ils sont facilement « déchiffrés » par n'importe qui en quelques secondes.

Pour éviter ce problème, utilisez un mécanisme d'authentification ou un autre protocole qui ne permet pas aux espions de voir votre mot de passe : authentification Digest, CRAM-MD5, Kerberos, SPNEGO ou NTLM. Ou encore mieux : utilisez des protocoles authentifiés qui protègent toute la connexion et tout ce qui y est envoyé.

Connexions non authentifiées

Les protocoles qui n'ont aucune forme d'authentification cryptographique ne peuvent pas savoir avec certitude qu'ils communiquent avec le bon serveur distant.

Si votre application utilise un schéma fixe ou un nom d'hôte fixe, ce n'est pas sûr tant que la connexion n'est pas authentifiée. Il peut y avoir une attaque de l'homme du milieu ou en fait le serveur entier pourrait avoir été remplacé par un acteur malveillant.

Les protocoles non authentifiés sont dangereux. Les données qui reviennent à curl peuvent avoir été injectées par un attaquant. Les données que curl envoie peuvent être modifiées avant d'atteindre le serveur prévu. Si elles atteignent même le serveur prévu.

Remèdes :

Restreindre les opérations aux transferts authentifiés
Utilisez des protocoles authentifiés protégés par HTTPS ou SSH.
S'assurer que le certificat du serveur, etc., est vérifié
Ne désactivez jamais la vérification de certificat.

Certificats et connexions de longue durée

La validation des certificats pour les connexions cryptées est effectuée immédiatement après l'établissement d'une connexion. Cette connexion peut être utilisée pour de nombreux transferts ultérieurs, même si le certificat utilisé pour la validation expire ou est révoqué, si le bundle de certificats local est modifié d'une manière qui aurait fait échouer la validation de ce certificat, si le serveur change son certificat pour un autre qui aurait échoué la validation, ou même si un serveur complètement différent est mis en place sous le même nom d'hôte. Cela pourrait se poursuivre pendant de nombreuses heures (voire des années) après qu'un tel changement se produise, ce qui pourrait ne pas être le comportement souhaité pour certaines applications.

Remèdes :

Utilisez l'option CURLOPT_MAXLIFETIME_CONN(3) pour limiter la durée pendant laquelle les connexions sont utilisées après leur validation réussie. Les transferts ultérieurs nécessitent une nouvelle connexion avec une nouvelle validation.

Redirections

L'option CURLOPT_FOLLOWLOCATION(3) suit automatiquement les redirections HTTP envoyées par un serveur distant. Ces redirections peuvent faire référence à n'importe quel type d'URL, pas seulement HTTP. libcurl restreint les protocoles autorisés à être utilisés dans les redirections pour des raisons de sécurité : seuls HTTP, HTTPS, FTP et FTPS sont activés par défaut. Les applications peuvent choisir de restreindre cet ensemble davantage.

Une redirection vers une URL de type file: entraînerait libcurl à lire (ou écrire) des fichiers arbitraires depuis le système de fichiers local. Si l'application renvoie les données à l'utilisateur (comme cela se produirait dans certains types de scripts CGI), un attaquant pourrait en profiter pour lire des données autrement interdites (par exemple, file://localhost/etc/passwd).

Si des identifiants d'authentification sont stockés dans le fichier ~/.netrc, ou si Kerberos est utilisé, tout autre type d'URL (pas seulement file:) nécessitant une authentification est également à risque. Une redirection telle que ftp://serveur-interne/fichier-prive retournerait alors des données même lorsque le serveur est protégé par mot de passe.

De même, si une clé privée SSH non chiffrée a été configurée pour l'utilisateur exécutant l'application libcurl, les URL SCP: ou SFTP: pourraient accéder à des ressources protégées par mot de passe ou clé privée, par exemple sftp://utilisateur@serveur-interne/etc/passwd

Les options CURLOPT_REDIR_PROTOCOLS_STR(3) et CURLOPT_NETRC(3) peuvent être utilisées pour atténuer ce type d'attaque.

Une redirection peut également spécifier un emplacement disponible uniquement sur la machine exécutant libcurl, y compris des serveurs cachés derrière un pare-feu pour l'attaquant. Par exemple http://127.0.0.1/ ou http://intranet/delete-stuff.cgi?delete=all ou tftp://serveur-bootp/données-configuration-pc

Les applications peuvent atténuer cela en désactivant CURLOPT_FOLLOWLOCATION(3) et en gérant elles-mêmes les redirections, en assainissant les URL si nécessaire. Alternativement, une application pourrait laisser CURLOPT_FOLLOWLOCATION(3) activé mais définir CURLOPT_REDIR_PROTOCOLS_STR(3) et installer une fonction de rappel CURLOPT_OPENSOCKETFUNCTION(3) ou CURLOPT_PREREQFUNCTION(3) dans laquelle les adresses sont assainies avant utilisation.

CRLF dans les en-têtes

Pour toutes les options de libcurl qui spécifient des en-têtes, y compris, mais sans s'y limiter, CURLOPT_HTTPHEADER(3), CURLOPT_PROXYHEADER(3), CURLOPT_COOKIE(3), CURLOPT_USERAGENT(3), CURLOPT_REFERER(3) et CURLOPT_RANGE(3), libcurl envoie les en-têtes tels quels et n'applique aucune validation des caractères de retour chariot/nouvelle ligne (CRLF). Les en-têtes HTTP sont sensibles aux CRLF, car un CRLF dans une valeur d'en-tête peut être interprété comme la fin d'un en-tête et le début d'un nouveau. Cela peut être utilisé pour injecter des en-têtes arbitraires.

Remède :

Validez toutes les données que vous fournissez en tant qu'en-têtes ou valeurs d'en-tête pour vous assurer qu'elles ne contiennent pas de CRLF.

Certificats et autres données sensibles

Si libcurl est configuré pour utiliser un grand nombre de certificats client (via CURLOPT_SSLCERT(3)), ou pour stocker des clés privées sensibles ou des informations d'identification de connexion, ces données doivent être protégées. Les applications qui stockent ces données dans des emplacements accessibles en écriture par des utilisateurs non privilégiés ou qui les envoient sur le réseau sans chiffrement courent le risque de les voir compromises.

Remèdes :

Utiliser des méthodes de stockage sécurisées
Les certificats et les clés privées doivent être stockés dans des fichiers dont les permissions sont restreintes aux utilisateurs autorisés. Évitez de stocker des données sensibles dans des fichiers de configuration mondiaux ou dans des emplacements accessibles en écriture par le public.
Chiffrer les données sensibles
Si des données sensibles doivent être transmises, utilisez des protocoles chiffrés comme HTTPS, SFTP ou FTPS. Pour les clés privées, envisagez d'utiliser un chiffrement fort (par exemple, AES-256).
Éviter les données sensibles dans les configurations
Si possible, évitez d'inclure des données sensibles directement dans les fichiers de configuration. Utilisez plutôt des variables d'environnement, des gestionnaires de secrets ou d'autres mécanismes sécurisés pour fournir ces informations à l'application.

DNS et résolution de noms

La résolution de noms DNS est un point critique pour la sécurité. Un attaquant peut compromettre un serveur DNS pour rediriger les requêtes vers de mauvaises adresses IP, ce qui peut conduire à des attaques de l'homme du milieu.

Remèdes :

Utiliser DNSSEC
Si votre environnement le permet, utilisez DNSSEC pour vérifier l'authenticité des réponses DNS.
Utiliser des serveurs DNS de confiance
Configurez vos systèmes pour utiliser des serveurs DNS de confiance et sécurisés.
Penser à la mise en cache DNS
Soyez conscient des implications de la mise en cache DNS. Des enregistrements DNS obsolètes ou malveillants mis en cache peuvent toujours entraîner des connexions à des serveurs non désirés.
Utiliser des noms d'hôte explicites
Dans la mesure du possible, utilisez des noms d'hôte explicites plutôt que des adresses IP, et assurez-vous que la résolution de noms est sécurisée.

Assainissement ou Normalisation

Certaines options de libcurl peuvent accepter des valeurs qui, si elles ne sont pas traitées avec un assainissement ou une normalisation spéciaux, pourraient être utilisées à des fins malveillantes.

Si vous autorisez des entrées utilisateur non fiables dans ces options sans assainir les séquences CRLF, un utilisateur malveillant pourrait être en mesure de modifier la requête d'une manière que vous n'aviez pas prévue, comme l'injection de nouveaux en-têtes.

Ressources Locales

Un utilisateur qui peut contrôler le serveur DNS d'un domaine passé dans une URL peut modifier l'adresse de l'hôte vers une adresse locale et privée qu'une application côté serveur utilisant libcurl pourrait alors utiliser. Par exemple, l'URL anodine http://fuzzybunnies.example.com/ pourrait en fait résoudre l'adresse IP d'un serveur derrière un pare-feu, tel que 127.0.0.1 ou 10.1.2.3. Les applications peuvent atténuer ce risque en définissant une CURLOPT_OPENSOCKETFUNCTION(3) ou une CURLOPT_PREREQFUNCTION(3) et en vérifiant l'adresse avant une connexion.

Tous les scénarios malveillants concernant les URL redirigées s'appliquent tout autant aux URL non redirigées, si l'utilisateur est autorisé à spécifier une URL arbitraire qui pourrait pointer vers une ressource privée. Par exemple, une application Web fournissant un service de traduction pourrait traduire joyeusement file://localhost/etc/passwd et afficher le résultat. Les applications peuvent atténuer ce risque avec l'option CURLOPT_PROTOCOLS_STR(3) ainsi qu'avec des techniques d'atténuation similaires pour les redirections.

Un serveur FTP malveillant pourrait, en réponse à la commande PASV, renvoyer une adresse IP et un numéro de port pour un serveur local à l'application exécutant libcurl mais derrière un pare-feu. Les applications peuvent atténuer ce risque en utilisant l'option CURLOPT_FTP_SKIP_PASV_IP(3) ou CURLOPT_FTPPORT(3).

Les serveurs locaux supposent parfois que l'accès local provient d'amis et d'utilisateurs de confiance. Une application qui attend https://example.com/file_to_read et reçoit à la place http://192.168.0.1/my_router_config pourrait imprimer un fichier qui serait autrement protégé par le pare-feu.

Permettre à votre application de se connecter à des hôtes locaux, que ce soit la même machine qui exécute l'application ou une machine sur le même réseau local, pourrait être exploité par un attaquant qui peut alors peut-être "scanner les ports" des hôtes particuliers - en fonction de la manière dont l'application et les serveurs agissent.

Adresses IPv4

Certains utilisateurs pourraient être tentés de filtrer l'accès aux ressources locales ou similaires en se basant sur les adresses IPv4 numériques utilisées dans les URL. C'est une mauvaise idée et source d'erreurs en raison des nombreuses façons différentes dont une adresse IPv4 numérique peut être spécifiée et que libcurl accepte : un à quatre champs séparés par des points utilisant un ou un mélange d'encodage décimal, octal ou hexadécimal.

Adresses IPv6

libcurl gère les adresses IPv6 de manière transparente et aussi facilement que les adresses IPv4. Cela signifie qu'une fonction d'assainissement qui filtre les adresses comme 127.0.0.1 n'est pas suffisante - les adresses IPv6 équivalentes ::1, ::, 0:00::0:1, ::127.0.0.1 et ::ffff:7f00:1 fournies d'une manière ou d'une autre par un attaquant contourneraient un filtre naïf et pourraient permettre l'accès à des ressources locales indésirables. L'IPv6 possède également des blocs d'adresses spéciaux comme link-local et site-local auxquels une application côté serveur utilisant libcurl ne devrait généralement pas accéder. Un pare-feu mal configuré installé dans un centre de données, une organisation ou sur un serveur peut également être configuré pour limiter les connexions IPv4 mais laisser les connexions IPv6 grandes ouvertes. Dans certains cas, régler CURLOPT_IPRESOLVE(3) sur CURL_IPRESOLVE_V4 peut être utilisé pour limiter les adresses résolues à IPv4 uniquement et contourner ces problèmes.

Téléversements

Lors du téléversement, une redirection peut entraîner l'écrasement d'un fichier local (ou distant). Les applications ne doivent pas autoriser la transmission d'URL non assainies pour les téléversements. De plus, CURLOPT_FOLLOWLOCATION(3) ne doit pas être utilisé pour les téléversements. Les applications devraient plutôt envisager de gérer elles-mêmes les redirections, en assainissant d'abord chaque URL.

Authentification

L'utilisation de CURLOPT_UNRESTRICTED_AUTH(3) pourrait entraîner l'envoi d'informations d'authentification à un second serveur inconnu. Les applications peuvent atténuer ce risque en désactivant CURLOPT_FOLLOWLOCATION(3) et en gérant elles-mêmes les redirections, en assainissant si nécessaire.

L'utilisation de l'option CURLAUTH_ANY pour CURLOPT_HTTPAUTH(3) pourrait entraîner l'envoi du nom d'utilisateur et du mot de passe en texte clair à un serveur HTTP. Utilisez plutôt CURLAUTH_ANYSAFE, qui garantit que le mot de passe est chiffré sur le réseau, ou échoue la requête.

L'utilisation de l'option CURLUSESSL_TRY pour CURLOPT_USE_SSL(3) pourrait entraîner l'envoi du nom d'utilisateur et du mot de passe en texte clair à un serveur FTP. Utilisez plutôt CURLUSESSL_CONTROL pour garantir qu'une connexion chiffrée est utilisée ou échoue la requête.

Cookies

Si les cookies sont activés et mis en cache, un utilisateur pourrait créer une URL qui effectue une action malveillante sur un site dont l'authentification est déjà stockée dans un cookie. Par exemple, http://mail.example.com/delete-stuff.cgi?delete=all. Les applications peuvent atténuer ce risque en désactivant les cookies ou en les effaçant entre les requêtes.

URL SCP dangereuses

Les URL SCP peuvent contenir des commandes brutes dans l'URL scp:, ce qui est un effet secondaire de la conception du protocole SCP. Par exemple :

  scp://user:pass@host/a;date >/tmp/test;

Les applications ne doivent pas autoriser la transmission d'URL SCP non assainies pour les téléchargements.

file://

Par défaut, curl et libcurl prennent en charge les URL file://. Une telle URL est toujours un accès, ou une tentative d'accès, à une ressource locale. Si votre application souhaite éviter cela, gardez le contrôle des URL à utiliser et/ou empêchez curl/libcurl d'utiliser le protocole.

Par défaut, libcurl interdit les redirections vers des URL file://.

Attention : file:// sous Windows

Le système d'exploitation Windows essaie automatiquement, et sans aucun moyen pour les applications de le désactiver, d'établir une connexion à un autre hôte sur le réseau et d'y accéder (via SMB ou d'autres protocoles), rien qu'en accédant au chemin de fichier correct.

Lorsqu'il en a pris conscience, l'équipe de curl a essayé de filtrer de telles tentatives afin de protéger les applications contre des sondes involontaires, par exemple sur les réseaux internes, etc. Cela a entraîné le CVE-2019-15601 et la correction de sécurité associée.

Cependant, nous avons depuis été informés du fait que la correction précédente était loin d'être adéquate, car il existe plusieurs autres façons d'accomplir plus ou moins la même chose : accéder à un hôte distant sur le réseau plutôt qu'au système de fichiers local.

La conclusion à laquelle nous sommes parvenus est qu'il s'agit d'une faiblesse ou d'une fonctionnalité du système d'exploitation Windows lui-même, contre laquelle nous, en tant qu'application, ne pouvons pas protéger les utilisateurs en toute sécurité. Ce serait simplement une course au "whack-a-mole" à laquelle nous ne voulons pas participer. Il existe trop de façons de le faire et il n'y a pas de bouton que nous puissions utiliser pour désactiver cette pratique.

Si vous utilisez curl ou libcurl sous Windows (quelle que soit la version), désactivez l'utilisation du protocole FILE dans curl ou soyez prêt à ce que les accès à une gamme de "chemins magiques" fassent potentiellement accéder votre système à d'autres hôtes de votre réseau. curl ne peut pas vous protéger contre cela.

Et si l'utilisateur peut définir l'URL

Les applications peuvent trouver tentant de laisser les utilisateurs définir l'URL sur laquelle travailler. C'est probablement acceptable, mais cela ouvre la porte à des méfaits et à des astuces que vous, en tant qu'auteur d'application, voudrez peut-être aborder ou prendre des précautions.

Si votre script utilisant curl autorise une URL personnalisée, autorisez-vous également, peut-être involontairement, l'utilisateur à passer d'autres options à la ligne de commande curl si une utilisation créative de caractères spéciaux est appliquée ?

Si l'utilisateur peut définir l'URL, l'utilisateur peut également spécifier la partie schéma pour d'autres protocoles que vous n'aviez pas l'intention que les utilisateurs utilisent et que vous n'aviez peut-être pas envisagés. curl prend en charge plus de 20 schémas d'URL différents. "http://" pourrait être ce que vous pensiez, "ftp://" ou "imap://" pourrait être ce que l'utilisateur donne à votre application. De plus, des opérations inter-protocoles peuvent être effectuées en utilisant un schéma particulier dans l'URL mais en pointant vers un serveur effectuant un protocole différent sur un port non standard.

Remèdes :

Utiliser --proto
Les lignes de commande curl peuvent utiliser --proto pour limiter les schémas d'URL qu'il accepte
Utiliser CURLOPT_PROTOCOLS_STR
Les programmes libcurl peuvent utiliser CURLOPT_PROTOCOLS_STR(3) pour limiter les schémas d'URL qu'il accepte
Envisager de ne pas autoriser l'utilisateur à définir l'URL complète
Peut-être juste laisser l'utilisateur fournir des données pour certaines parties ? Ou peut-être filtrer les entrées pour n'autoriser que des choix spécifiques ?

RFC 3986 vs WHATWG URL

curl prend en charge les URL principalement selon la manière dont elles sont définies dans la RFC 3986, et ce depuis le début.

Les navigateurs Web adhèrent principalement à la spécification URL WHATWG.

Cet écart fait que certaines URL copiées entre navigateurs (ou renvoyées sur HTTP pour une redirection) et curl ne fonctionnent pas de la même manière. Cela peut également causer des problèmes si une application analyse les URL différemment de libcurl et fait des hypothèses différentes sur un lien. Cela peut induire les utilisateurs en erreur en leur faisant obtenir la mauvaise chose, se connecter au mauvais hôte ou autrement ne pas fonctionner de manière identique.

libcurl - security considerations

Security

This document describes potential security issues related to the use of libcurl and the curl command-line tool. It is not exhaustive, and developers should always follow secure coding practices.

libcurl is a client-side library and is thus often used to connect to servers on the internet. This implies that it is a tool that can be used to attack or be attacked. This document tries to outline some of the more common or insidious risks.

It is important to note that the curl command-line tool parses command line arguments and options in a specific way. This man page is intended to describe the security implications of using the libcurl API, but readers should also be aware that the curl tool offers its own set of features and configurations, and these might differ.

For example, the curl command-line tool has built-in support for reading options from a configuration file. The options read from the configuration file are processed in the same way as command-line options, meaning that if you want to use that feature, you should use it in the exact same way as within libcurl itself.

FTP uses two connections

When performing an FTP transfer, two TCP connections are used: one for setting up the transfer and one for the actual data.

FTP is not only unauthenticated, but the setting up of the second transfer is also a weak spot. The second connection to use for data, is either setup with the PORT/EPRT command that makes the server connect back to the client on the given IP+PORT, or with PASV/EPSV that makes the server setup a port to listen to and tells the client to connect to a given IP+PORT.

Again, unauthenticated means that the connection might be meddled with by a man-in-the-middle or that there is a malicious server pretending to be the right one.

A malicious FTP server can respond to PASV commands with the IP+PORT of a totally different machine. Perhaps even a third party host, and when there are many clients trying to connect to that third party, it could create a Distributed Denial-Of-Service attack out of it. If the client makes an upload operation, it can make the client send the data to another site. If the attacker can affect what data the client uploads, it can be made to work as a HTTP request and then the client could be made to issue HTTP requests to third party hosts.

An attacker that manages to control curl's command line options can tell curl to send an FTP PORT command to ask the server to connect to a third party host instead of back to curl.

The fact that FTP uses two connections makes it vulnerable in a way that is hard to avoid.

Active FTP passes on the local IP address

If you use curl/libcurl to do active FTP transfers, curl passes on the address of your local IP to the remote server - even when for example using a SOCKS or HTTP proxy in between curl and the target server.

Denial of Service

A malicious server could cause libcurl to effectively hang by sending data slowly, or even no data at all but just keeping the TCP connection open. This could effectively result in a denial-of-service attack. The CURLOPT_TIMEOUT(3) and/or CURLOPT_LOW_SPEED_LIMIT(3) options can be used to mitigate against this.

A malicious server could cause libcurl to download an infinite amount of data, potentially causing system resources to be exhausted resulting in a system or application crash. Setting the CURLOPT_MAXFILESIZE_LARGE(3) option is not sufficient to guard against this. Instead, applications should monitor the amount of data received within the write or progress callback and abort once the limit is reached.

A malicious HTTP server could cause an infinite redirection loop, causing a denial-of-service. This can be mitigated by using the CURLOPT_MAXREDIRS(3) option.

Arbitrary Headers

User-supplied data must be sanitized when used in options like CURLOPT_USERAGENT(3), CURLOPT_HTTPHEADER(3), CURLOPT_POSTFIELDS(3) and others that are used to generate structured data. Characters like embedded carriage returns or ampersands could allow the user to create additional headers or fields that could cause malicious transactions.

Server-supplied Names

A server can supply data which the application may, in some cases, use as a filename. The curl command-line tool does this with --remote-header-name, using the Content-disposition: header to generate a filename. An application could also use CURLINFO_EFFECTIVE_URL(3) to generate a filename from a server-supplied redirect URL. Special care must be taken to sanitize such names to avoid the possibility of a malicious server supplying one like "/etc/passwd", "autoexec.bat", "prn:" or even ".bashrc".

Server Certificates

A secure application should never use the CURLOPT_SSL_VERIFYPEER(3) option to disable certificate validation. There are numerous attacks that are enabled by applications that fail to properly validate server TLS/SSL certificates, thus enabling a malicious server to spoof a legitimate one. HTTPS without validated certificates is potentially as insecure as a plain HTTP connection.

Showing What You Do

Relatedly, be aware that in situations when you have problems with libcurl and ask someone for help, everything you reveal in order to get best possible help might also impose certain security related risks. Hostnames, usernames, paths, operating system specifics, etc. (not to mention passwords of course) may in fact be used by intruders to gain additional information of a potential target.

Be sure to limit access to application logs if they could hold private or security-related data. Besides the obvious candidates like usernames and passwords, things like URLs, cookies or even filenames could also hold sensitive data.

To avoid this problem, you must of course use your common sense. Often, you can just edit out the sensitive data or just search/replace your true information with faked data.

setuid applications using libcurl

libcurl-using applications that set the 'setuid' bit to run with elevated or modified rights also implicitly give that extra power to libcurl and this should only be done after careful considerations.

Giving setuid powers to the application means that libcurl can save files using those new rights (if for example the SSLKEYLOGFILE environment variable is set). Also: if the application wants these powers to read or manage secrets that the user is otherwise not able to view (like credentials for a login etc), it should be noted that libcurl still might understand proxy environment variables that allow the user to redirect libcurl operations to use a proxy controlled by the user.

File descriptors, fork and NTLM

An application that uses libcurl and invokes fork() gets all file descriptors duplicated in the child process, including the ones libcurl created.

libcurl itself uses fork() and execl() if told to use the CURLAUTH_NTLM_WB authentication method which then invokes the helper command in a child process with file descriptors duplicated. Make sure that only the trusted and reliable helper program is invoked.

This feature was removed from curl in 8.8.0.

Secrets in memory

When applications pass usernames, passwords or other sensitive data to libcurl to be used for upcoming transfers, those secrets are kept around as-is in memory. In many cases they are stored in the heap for as long as the handle itself for which the options are set.

If an attacker can access the heap, like maybe by reading swap space or via a core dump file, such data might be accessible.

Further, when eventually closing a handle and the secrets are no longer needed, libcurl does not explicitly clear memory before freeing it, so credentials may be left in freed data.

Saving files

libcurl cannot protect against attacks where an attacker has write access to the same directory where libcurl is directed to save files.

Cookies

If libcurl is built with PSL (Public Suffix List) support, it detects and discards cookies that are specified for such suffix domains that should not be allowed to have cookies.

if libcurl is not built with PSL support, it has no ability to stop super cookies.

Report Security Problems

Should you detect or just suspect a security problem in libcurl or curl, contact the project curl security team immediately. See https://curl.se/dev/secprocess.html for details.
