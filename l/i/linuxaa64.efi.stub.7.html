DESCRIPTION

systemd-stub (stocké dans des fichiers par architecture linuxx64.efi.stub, linuxia32.efi.stub, linuxaa64.efi.stub sur disque) est un simple stub de démarrage UEFI. Un stub de démarrage UEFI est attaché à une image binaire de noyau Linux, et est un morceau de code qui s'exécute dans l'environnement du firmware UEFI avant de passer à l'environnement du noyau Linux. Le stub de démarrage UEFI assure qu'un noyau Linux est exécutable en tant que binaire UEFI ordinaire, et est capable de diverses préparations avant de basculer le système vers le monde Linux.

Le stub de démarrage UEFI recherche diverses ressources pour l'invocation du noyau dans le binaire PE UEFI lui-même. Ceci permet de combiner diverses ressources dans une seule image binaire PE (une "Unified Kernel Image" ou "UKI" pour faire court), qui peut ensuite être signée via UEFI SecureBoot dans son ensemble, couvrant toutes les ressources individuelles d'un coup. Spécifiquement, il peut inclure les sections PE suivantes :

•Une section ".linux" avec l'image du noyau Linux ELF. Cette section est obligatoire.
•Une section optionnelle ".osrel" avec les informations de sortie du système d'exploitation, c'est-à-dire le contenu du fichier os-release(5) de l'OS auquel appartient le noyau.
•Une section optionnelle ".cmdline" avec la ligne de commande du noyau à passer au noyau invoqué.
•Une section optionnelle ".initrd" avec l'initrd.
•Une section optionnelle ".ucode" avec un initrd contenant le microcode, à remettre au noyau avant tout autre initrd. Cet initrd ne doit pas être compressé.
•Une section optionnelle ".splash" avec une image (au format .BMP de Windows) à afficher à l'écran avant d'invoquer le noyau.
•Une section optionnelle ".dtb" avec un DeviceTree binaire compilé.
•Zéro ou plusieurs sections ".dtbauto". systemd-stub utilisera toujours la première correspondante. La correspondance est effectuée en prenant la première chaîne "compatible" du premier DeviceTree fournie par le firmware dans les tables de configuration et en la comparant avec la première chaîne "compatible" de chacune des sections ".dtbauto". Si le firmware ne fournit pas de DeviceTree, la correspondance est effectuée en utilisant la section ".hwids" à la place. Après avoir sélectionné une section ".hwids" (voir la description ci-dessous), la chaîne "compatible" de cette section sera utilisée pour effectuer la même procédure de correspondance. Si une correspondance est trouvée, cette section ".dtbauto" sera chargée et remplacera ".dtb" s'il est présent.
•Zéro ou plusieurs sections ".efifw" pour l'image du firmware. Cela fonctionne de manière similaire aux sections ".dtbauto". systemd-stub utilisera toujours la première correspondante. La correspondance est effectuée en sélectionnant d'abord l'entrée la plus appropriée dans la section ".hwids" basée sur les identifiants matériels fournis par SMBIOS (voir ci-dessous). Si une entrée adéquate est trouvée, la chaîne "fwid" de cette entrée sera utilisée pour effectuer la procédure de correspondance pour les blobs de firmware dans la section ".efifw". Le premier firmware correspondant sera chargé.
•Zéro ou plusieurs sections ".hwids" avec les identifiants matériels des machines pour faire correspondre les DeviceTrees. systemd-stub utilisera les données SMBIOS pour calculer les identifiants matériels de la machine (conformément à la spécification[1]), puis il essaiera de trouver l'un d'entre eux dans chacune des sections ".hwids". La première section correspondante sera utilisée.
•Une section optionnelle ".uname" avec les informations de version du noyau, c'est-à-dire la sortie de uname -r pour le noyau inclus dans la section ".linux".
•Une section optionnelle ".sbat" avec les métadonnées de révocation de SBAT[2].
•Une section optionnelle ".pcrsig" avec un ensemble de signatures cryptographiques pour les valeurs PCR TPM2 attendues après le démarrage du noyau, au format JSON. Ceci est utile pour implémenter des politiques TPM2 qui lient le chiffrement du disque et similaires aux noyaux qui sont signés par une clé spécifique.
•Une section optionnelle ".pcrpkey" avec une clé publique au format PEM correspondant aux données de signature dans la section ".pcrsig".

Dans un UKI de base, les sections listées ci-dessus apparaissent au plus une fois, à l'exception des sections ".dtbauto" et ".hwids". Dans un UKI multi-profils, plusieurs ensembles de ces sections sont présents dans un seul fichier et forment des "profils", dont l'un peut être sélectionné au démarrage. Pour cela, la section PE ".profile" est définie pour être utilisée comme séparateur entre les ensembles de sections. La section ".profile" elle-même peut contenir des méta-informations sur la section, et suit une structure similaire au contenu de la section ".osrel". Pour plus de détails sur les UKI multi-profils, voir ci-dessous.

Si UEFI SecureBoot est activé et que la section ".cmdline" est présente dans l'image exécutée, toute tentative de remplacer la ligne de commande du noyau en la passant comme paramètres d'invocation au binaire EFI est ignorée. Ainsi, afin de permettre le remplacement de la ligne de commande du noyau, désactivez UEFI SecureBoot, ou n'incluez pas de section PE de ligne de commande du noyau dans le fichier image du noyau. Si une ligne de commande est acceptée via les paramètres d'invocation EFI au binaire EFI, elle est mesurée dans le PCR 12 de TPM (si un TPM est présent).

Si un DeviceTree est intégré dans la section ".dtb", il remplace un DeviceTree existant dans la table de configuration EFI correspondante. systemd-stub demandera au firmware via le protocole "EFI_DT_FIXUP_PROTOCOL" des corrections matérielles spécifiques au DeviceTree.

Le contenu de 11 de ces 12 sections est mesuré dans le PCR 11 du TPM. Il n'est autrement pas utilisé et donc le résultat peut être pré-calculé sans trop d'efforts. La section ".pcrsig" n'est pas incluse dans cette mesure PCR, car elle est censée contenir les signatures pour le résultat de l'opération de mesure, et ne peut donc pas en être également une entrée. Si un UKI contient plusieurs profils, seules les sections PE du profil sélectionné (et celles du profil de base, sauf si remplacées) sont mesurées.

Si le profil numérique sélectionné est non nul, il est mesuré dans le PCR 12.

Lorsque les sections ".pcrsig" et/ou ".pcrpkey" sont présentes dans une image de noyau unifiée, leur contenu est passé au noyau démarré dans une archive initrd cpio synthétique qui les place dans les fichiers /.extra/tpm2-pcr-signature.json et /.extra/tpm2-pcr-public-key.pem. Typiquement, une ligne tmpfiles.d(5) garantit alors leur copie dans /run/systemd/tpm2-pcr-signature.json et /run/systemd/tpm2-pcr-public-key.pem où elles restent accessibles même après que le système soit passé de l'environnement initrd au système de fichiers hôte. Des outils tels que systemd-cryptsetup@.service(8), systemd-cryptenroll(1) et systemd-creds(1) utiliseront automatiquement les fichiers présents sous ces chemins pour déverrouiller des ressources protégées (stockage chiffré ou identifiants) ou lier le chiffrement aux noyaux démarrés.

Pour plus de détails sur le concept UKI, voir la spécification UKI[3].

FICHIERS COMPLEMENTAIRES

Le stub de démarrage UEFI systemd-stub collecte automatiquement trois types de fichiers auxiliaires complémentaires placés éventuellement dans des répertoires de remplacement sur la même partition que le binaire EFI, génère dynamiquement des archives initrd cpio à partir d'eux, et les passe au noyau.

Ce site n'est en aucun cas associé à Arch Linux ni affilié à ce projet. Le contenu est uniquement une traduction des pages de manuel d'Arch publiées sur man.archlinux.org.

Spécifiquement :

•Pour un binaire de noyau appelé foo.efi, il cherchera des fichiers avec le suffixe .cred dans un répertoire nommé foo.efi.extra.d/ à côté de lui. Si le binaire du noyau utilise un compteur dans le but de l'Évaluation Automatique du Démarrage[4], ce compteur sera ignoré. Par exemple, foo+3-0.efi cherchera dans le répertoire foo.efi.extra.d/. Une archive cpio est générée à partir de tous les fichiers trouvés de cette manière, les plaçant dans le répertoire /.extra/credentials/ de la hiérarchie du système de fichiers initrd. Le initrd principal peut alors y accéder dans ce répertoire. Ceci est censé être utilisé pour stocker des identifiants auxiliaires, chiffrés et authentifiés, à utiliser avec LoadCredentialEncrypted dans la partition système UEFI. Voir systemd.exec(5) et systemd-creds(1) pour les détails sur les identifiants chiffrés. L'archive cpio générée est mesurée dans le PCR 12 du TPM (si un TPM est présent).
•De même, les fichiers foo.efi.extra.d/*.sysext.raw sont empaquetés dans une archive cpio et placés dans le répertoire /.extra/sysext/ dans la hiérarchie du système de fichiers initrd. Ceci est censé être utilisé pour passer des images d'extension système supplémentaires spécifiques à l'UKI à l'initrd. Voir systemd-sysext(8) pour les détails sur les images d'extension système. L'archive cpio générée contenant ces images d'extension système est mesurée dans le PCR 13 du TPM (si un TPM est présent).
•De même, les fichiers /loader/extensions/*.sysext.raw sont empaquetés dans une archive cpio et placés dans le répertoire /.extra/global_sysext/ dans la hiérarchie du système de fichiers initrd. Ceci est censé être utilisé pour passer des images d'extension système globales supplémentaires à l'initrd. Voir systemd-sysext(8) pour les détails sur les images d'extension système. L'archive cpio générée contenant ces images d'extension système est mesurée dans le PCR 13 du TPM (si un TPM est présent).
•De même, les fichiers foo.efi.extra.d/*.confext.raw sont empaquetés dans une archive cpio et placés dans le répertoire /.extra/confext/ dans la hiérarchie du système de fichiers initrd. Ceci est censé être utilisé pour passer des images d'extension de configuration supplémentaires spécifiques à l'UKI à l'initrd. Voir systemd-confext(8) pour les détails sur les images d'extension de configuration. L'archive cpio générée contenant ces images d'extension de configuration est mesurée dans le PCR 12 du TPM (si un TPM est présent).
•De même, les fichiers /loader/extensions/*.confext.raw sont empaquetés dans une archive cpio et placés dans le répertoire /.extra/global_confext/ dans la hiérarchie du système de fichiers initrd. Ceci est censé être utilisé pour passer des images d'extension de configuration globales supplémentaires à l'initrd. Voir systemd-confext(8) pour les détails sur les images d'extension de configuration. L'archive cpio générée contenant ces images d'extension de configuration est mesurée dans le PCR 12 du TPM (si un TPM est présent).
•De même, les fichiers foo.efi.extra.d/*.addon.efi sont chargés et vérifiés en tant que binaires PE, et des sections spécifiques en sont chargées. Les extensions permettent de passer des paramètres de ligne de commande supplémentaires du noyau ("section .cmdline"), ou des blobs DeviceTree ("section .dtb"), des initrds supplémentaires ("section .initrd"), et des mises à jour de microcode ("section .ucode"). Les extensions permettent de passer ces ressources indépendamment de la version du noyau démarré, permettant par exemple aux fournisseurs de plateformes d'expédier une configuration spécifique à la plateforme.

En cas d'activation du démarrage sécurisé, ces fichiers seront validés à l'aide des clés dans la DB UEFI, la DB de Shim ou le MOK de Shim, et ne seront chargés que si la vérification réussit. De plus, si l'extension et l'UKI contiennent tous deux une section ".uname", l'extension sera rejetée si elles ne correspondent pas exactement. Il est recommandé d'ajouter toujours une section ".sbat" à toutes les extensions signées, afin qu'elles puissent être révoquées avec une mise à jour de la politique SBAT, sans nécessiter de blocage via DBX/MOKX. L'outil ukify(1) ajoutera une politique SBAT par défaut si aucune n'est passée lors de la construction des extensions. Pour plus d'informations sur SBAT, voir la documentation de Shim[2].

Les fichiers d'extension sont triés, chargés et mesurés dans le PCR 12 du TPM (si un TPM est présent) et ajoutés à la ligne de commande du noyau. Les options de ligne de commande de l'UKI sont listées en premier, suivies des options des extensions dans /loader/addons/*.addon.efi, et enfin des extensions spécifiques à l'UKI. Les blobs de l'arbre de périphériques sont chargés et mesurés en suivant le même algorithme. Les extensions de microcode sont passées au noyau dans l'ordre inverse (extensions spécifiques à l'UKI, extensions globales, section intégrée à l'UKI). C'est parce que le pilote de mise à jour du microcode s'arrête au premier nom de fichier correspondant. Les extensions sont toujours chargées dans le même ordre en fonction du nom de fichier, de sorte qu'étant donné le même ensemble d'extensions, le même ensemble de mesures peut être attendu dans le PCR12. Cependant, notez que le nom de fichier n'est pas protégé par la signature PE, et en tant que tel, un attaquant ayant un accès en écriture à l'ESP pourrait potentiellement renommer ces fichiers pour changer l'ordre dans lequel ils sont chargés, d'une manière qui pourrait altérer la fonctionnalité du noyau, car certaines options pourraient dépendre de l'ordre. Si vous signez de telles extensions, vous devriez faire attention aux valeurs du PCR12 et utiliser un service d'attestation afin que l'utilisation inappropriée de vos extensions signées puisse être détectée et traitée à l'aide de l'un des mécanismes de révocation mentionnés ci-dessus.

•Les fichiers /loader/credentials/*.cred sont empaquetés dans une archive cpio et placés dans le répertoire /.extra/global_credentials/ de la hiérarchie du système de fichiers initrd. Ceci est censé être utilisé pour passer des identifiants supplémentaires à l'initrd, indépendamment de la version du noyau démarré. L'archive cpio générée est mesurée dans le PCR 12 du TPM (si un TPM est présent).
•De plus, les fichiers /loader/addons/*.addon.efi sont chargés et vérifiés en tant que binaires PE, et les sections ".cmdline", ".dtb", ".initrd" et ".ucode" en sont analysées. Ceci est censé être utilisé pour passer des paramètres de ligne de commande supplémentaires, des blobs DeviceTree, des initrds et des mises à jour de microcode au noyau, indépendamment de la version du noyau démarré.

Ces mécanismes peuvent être utilisés pour paramétrer et étendre des images initrd immuables et fiables (c'est-à-dire signées) d'une manière raisonnablement sûre : toutes les données qu'elles contiennent sont mesurées dans les PCR du TPM. Lors de l'accès, elles devraient être validées davantage : dans le cas des identifiants, en les chiffrant/authentifiant via le TPM, comme exposé par systemd-creds encrypt -T (voir systemd-creds(1) pour les détails) ; dans le cas des images d'extension système, en utilisant des images Verity signées.

UKIs MULTI-PROFIL

Dans de nombreux contextes, il est utile de permettre l'invocation d'un UKI unique dans plusieurs modes (ou "profils") différents sans compromettre l'intégrité cryptographique, les mesures, etc. du processus de démarrage. Par exemple, un UKI unique pourrait fournir trois profils distincts : un démarrage régulier, un qui invoque une opération de "réinitialisation d'usine", et un qui démarre en mode cible de stockage (comme dans systemd-storagetm.service(8)). Chaque profil utiliserait alors les mêmes sections ".linux" et ".initrd", mais aurait une section ".cmdline" distincte. Par exemple, les deux derniers profils étenderaient la ligne de commande du noyau régulier avec "systemd.unit=factory-reset.target" ou "rd.systemd.unit=storagetm.target".

Un UKI unique peut prendre en charge plusieurs profils au moyen de la section PE spéciale ".profile". Cette section agit comme un séparateur entre les sections PE des profils individuels. Les sections PE ".profile" peuvent donc apparaître plusieurs fois dans un UKI unique, et les autres sections PE listées ci-dessus peuvent également apparaître plusieurs fois, si les ".profile" sont utilisés, mais une seule fois avant la première section ".profile", une fois entre chaque paire subséquente, et une fois après la dernière apparition de ".profile". Les sections listées avant la première section ".profile" sont considérées comme le profil "de base" de l'UKI. Chaque section ".profile" introduit ensuite un nouveau profil, numéroté à partir de zéro. Les sections PE suivant chaque section ".profile" sont spécifiques à ce profil. Lors du démarrage dans un profil spécifique, les profils de la section de base sont utilisés en combinaison avec les sections du profil spécifique : si la même section est définie dans les deux, la section par profil remplace la version du profil de base, sinon les sections du profil de base sont utilisées.

Un UKI ne contenant pas de ".profile" est considéré comme équivalent à un UKI contenant une seule section ".profile", n'ayant qu'un seul profil "@0".

Voici un exemple simple pour les sections d'un UKI multi-profil, inspiré de la configuration suggérée ci-dessus :

Tableau 1. Exemple d'UKI Multi-Profil

Section Profil
".linux" Profil de base
".osrel"
".cmdline"
".initrd"
".profile" Profil @0
".profile" Profil @1
".cmdline"
".profile" Profil @2
".cmdline"

La liste des sections ci-dessus définirait trois profils. Les quatre premières sections constituent le profil de base. Une
section ".profile" introduit ensuite le profil @0. Elle ne remplace aucune section (ni n'en ajoute) de la section de base, elle est donc immédiatement suivie d'une autre section ".profile" qui introduit ensuite la section @1. Ce profil remplace la ligne de commande du noyau. Enfin, les deux dernières sections définissent la section @2, remplaçant à nouveau la ligne de commande. (Notez que dans cet exemple, la première ".cmdline" aurait également pu être déplacée derrière la première ".profile" avec un effet équivalent. Pour garder les choses bien extensibles, il est probablement judicieux de conserver la ligne de commande générique dans la section de base plutôt que dans le profil 0, au cas où les profils ajoutés ultérieurement voudraient la réutiliser.)

Le profil à démarrer peut être contrôlé via la ligne de commande de l'UKI lui-même : si le premier argument commence par "@", suivi d'un nombre entier positif en décimal, cela sélectionne le profil dans lequel démarrer. Si le premier argument n'est pas spécifié de cette manière, l'UKI démarrera automatiquement dans le profil 0.

Une section ".profile" peut contenir des méta-informations sur le profil. Elle suit un format similaire à celui de ".osrel" (c'est-à-dire une liste de chaînes séparées par des sauts de ligne, semblable à un bloc d'affectation de variables d'environnement). Actuellement, deux champs sont définis : "ID=" est censé contenir une courte chaîne d'identification qui identifie le profil (c'est-à-dire

.g. "ID=factory-reset"). "TITLE=" doit contenir une chaîne de caractères lisible par l'homme qui peut apparaître dans l'entrée du menu de démarrage pour ce profil (par exemple, "TITLE='Réinitialisation d'usine de cet appareil'").

NOTES SUR LES PCR TPM

Notez que lorsqu'un noyau unifié utilisant systemd-stub est invoqué, le firmware le mesurera dans son intégralité pour le PCR 4 du TPM, couvrant toutes les ressources intégrées, telles que le code du stub lui-même, le noyau principal, l'initrd embarqué et la ligne de commande du noyau (voir ci-dessus pour une liste complète), y compris tous les profils UKI.

Notez également que lorsque systemd-stub mesure une section PE, il mesurera la quantité d'octets que la section occupe en mémoire (VirtualSize) et non la quantité d'octets que la section occupe sur le disque (SizeOfRawData). Cela signifie que si la taille en mémoire est supérieure à la taille sur le disque, systemd-stub finira par mesurer des zéros supplémentaires. Pour éviter que cela ne se produise, il est recommandé de s'assurer que la taille en mémoire de chaque section mesurée par systemd-stub est toujours inférieure ou égale à la taille sur le disque. ukify s'assure automatiquement que c'est le cas lors de la construction des UKI ou des add-ons.

Notez également que le noyau Linux mesurera tous les initrds qu'il reçoit dans le PCR 9 du TPM. Cela signifie que chaque type d'initrd (du profil UKI sélectionné) sera potentiellement mesuré deux ou trois fois : les initrds intégrés dans l'image du noyau seront mesurés aux PCR 4, 9 et 11 ; l'initrd synthétisé à partir des identifiants (et celui synthétisé à partir des extensions de configuration) sera mesuré aux PCR 9 et 12 ; l'initrd synthétisé à partir des extensions système sera mesuré aux PCR 4 et 9. VARIABLES EFI

Les variables EFI suivantes sont définies, définies et lues par
systemd-stub, sous l'UUID du vendeur "4a67b082-0a4c-41cf-b6c7-440b29bb8c4f", pour la communication entre le stub de démarrage et le système d'exploitation :

LoaderDevicePartUUID

Contient l'UUID de la partition depuis laquelle le chargeur de démarrage a été lancé lors du démarrage actuel (généralement une partition système EFI). Si elle est déjà définie par le chargeur de démarrage, elle restera inchangée par systemd-stub. Si elle n'est pas encore définie, elle sera définie sur l'UUID de la partition depuis laquelle le noyau unifié est lancé, afin de prendre en charge les systèmes qui démarrent directement sur une image de noyau unifiée, en contournant tout chargeur de démarrage. systemd-gpt-auto-generator(8) utilise ces informations pour trouver automatiquement le disque à partir duquel il a démarré, afin de découvrir automatiquement diverses autres partitions sur le même disque.

Ajouté dans la version 224.

LoaderFirmwareInfo, LoaderFirmwareType

Brèves informations sur le firmware. Utilisez bootctl(1) pour afficher ces données.

Ajouté dans la version 250.

LoaderTpm2ActivePcrBanks

Représentation sous forme de chaîne hexadécimale d'un masque de bits avec des valeurs définies par la spécification du protocole EFI TCG pour TPM 2.0 sous forme d'EFI_TCG2_BOOT_HASH_ALG_*. Si aucun support TPM2 ou aucune banque active n'a été détecté, sera défini sur 0. Défini par le chargeur de démarrage. Utilisez systemd-analyze(1) pour afficher ces données.

Ajouté dans la version 258.

LoaderImageIdentifier

Le chemin d'accès au système de fichiers de l'exécutable EFI du chargeur de démarrage pour le démarrage actuel, relatif au répertoire racine de la partition (c'est-à-dire relatif à la partition indiquée par LoaderDevicePartUUID, voir ci-dessus). S'il n'est pas encore défini, il sera défini sur le chemin d'accès au système de fichiers de l'exécutable EFI du noyau unifié démarré, afin de prendre en charge les systèmes qui démarrent directement sur une image de noyau unifiée, en contournant tout chargeur de démarrage. Utilisez bootctl(1) pour afficher ces données.

Ajouté dans la version 237.

StubDevicePartUUID, StubImageIdentifier

Similaire à LoaderDevicePartUUID et LoaderImageIdentifier, mais indique l'emplacement du binaire EFI de l'image du noyau unifié plutôt que l'emplacement du binaire du chargeur de démarrage, indépendamment du fait qu'il ait été démarré via un chargeur de démarrage ou non.

Ajouté dans la version 257.

StubDeviceURL

Si l'image du noyau a été invoquée via un démarrage réseau, cette variable contient l'URL d'origine. Ceci peut être utilisé pour acquérir automatiquement des ressources supplémentaires de la même source.

Ajouté dans la version 258.

StubInfo

Brèves informations sur le stub. Utilisez bootctl(1) pour afficher ces données.

Ajouté dans la version 250.

StubPcrKernelImage

L'indice du registre PCR dans lequel l'image du noyau, l'image initrd, l'écran de démarrage, la base de données de l'arbre de périphériques et la ligne de commande intégrée sont mesurés, formaté sous forme de chaîne décimale ASCII (par exemple, "11"). Cette variable est définie si une mesure a été effectuée avec succès, et reste non définie sinon.

Ajouté dans la version 252.

StubPcrKernelParameters

L'indice du registre PCR dans lequel la ligne de commande du noyau et les identifiants sont mesurés, formaté sous forme de chaîne décimale ASCII (par exemple, "12"). Cette variable est définie si une mesure a été effectuée avec succès, et reste non définie sinon.

Ajouté dans la version 252.

StubPcrInitRDSysExts

L'indice du registre PCR des extensions système pour l'initrd, qui sont récupérées à partir du système de fichiers sur lequel l'image du noyau est située. Formaté sous forme de chaîne décimale ASCII (par exemple, "13"). Cette variable est définie si une mesure a été effectuée avec succès, et reste non définie sinon.

Ajouté dans la version 252.

StubPcrInitRDConfExts

L'indice du registre PCR des extensions de configuration pour l'initrd, qui sont récupérées à partir du système de fichiers sur lequel l'image du noyau est située. Formaté sous forme de chaîne décimale ASCII (par exemple, "12"). Cette variable est définie si une mesure a été effectuée avec succès, et reste non définie sinon.

Ajouté dans la version 255.

StubProfile

L'indice numérique du profil sélectionné, sans le "@", formaté sous forme de chaîne décimale. Défini sur les UKI à profil unique et multi-profils. (Dans le premier cas, cette variable sera définie sur "0" sans condition.)

Ajouté dans la version 257.

Notez que certaines des variables ci-dessus peuvent également être définies par le chargeur de démarrage. Le stub les définira uniquement si elles ne sont pas déjà définies. Certaines de ces variables sont définies par l'Interface du chargeur de démarrage[5].

RESSOURCES INITRD

Les ressources suivantes sont passées sous forme d'archives cpio initrd au noyau démarré, et constituent ainsi la hiérarchie du système de fichiers initiale dans l'environnement d'exécution de l'initrd :

/

L'initrd principal de la section PE ".initrd" de l'image du noyau unifiée.

Ajouté dans la version 252.

/.extra/credentials/*.cred

Les fichiers d'identifiants (suffixe ".cred") placés à côté de l'image du noyau unifiée (comme décrit ci-dessus) sont copiés dans le répertoire /.extra/credentials/ de l'environnement d'exécution de l'initrd.

Ajouté dans la version 252.

/.extra/global_credentials/*.cred

De même, les fichiers d'identifiants du répertoire /loader/credentials/ dans le système de fichiers où se trouve l'image du noyau unifiée sont copiés dans le répertoire /.extra/global_credentials/ de l'environnement d'exécution de l'initrd.

Ajouté dans la version 252.

/.extra/sysext/*.sysext.raw

Les fichiers d'image d'extension système (suffixe ".sysext.raw") placés à côté de l'image du noyau unifiée (comme décrit ci-dessus) sont copiés dans le répertoire /.extra/sysext/ de l'environnement d'exécution de l'initrd.

Ajouté dans la version 252.

/.extra/global_sysext/*.sysext.raw

De même, les fichiers d'image d'extension système (suffixe ".sysext.raw") placés dans le répertoire /loader/extensions/ dans le système de fichiers où se trouve l'image du noyau unifiée sont copiés dans le répertoire /.extra/global_sysext/ de l'environnement d'exécution de l'initrd.

Ajouté dans la version 258.

/.extra/confext/*.confext.raw

Les fichiers d'image d'extension de configuration (suffixe ".confext.raw") placés à côté de l'image du noyau unifiée (comme décrit ci-dessus) sont copiés dans le répertoire /.extra/confext/ de l'environnement d'exécution de l'initrd.

Ajouté dans la version 255.

/.extra/global_confext/*.confext.raw

De même, les fichiers d'image d'extension de configuration (suffixe ".confext.raw") placés dans le répertoire /loader/extensions/ dans le système de fichiers où se trouve l'image du noyau unifiée sont copiés dans le répertoire /.extra/global_confext/ de l'environnement d'exécution de l'initrd.

Ajouté dans la version 258.

/.extra/tpm2-pcr-signature.json

L'objet JSON de signature des PCR TPM2 incluéd dans la section PE ".pcrsig" de l'image noyau unifiée est copiée dans le fichier /.extra/tpm2-pcr-signature.json dans l'environnement d'exécution de l'initrd.

Ajouté dans la version 252.

/.extra/tpm2-pcr-public-key.pem

La clé publique PEM incluse dans la section PE ".pcrpkey" de l'image noyau unifiée est copiée dans le fichier /.extra/tpm2-pcr-public-key.pem dans l'environnement d'exécution de l'initrd.

Ajouté dans la version 252.

/.extra/profile, /.extra/os-release

Le contenu des sections ".profile" et ".osrel" du profil sélectionné, le cas échéant.

Ajouté dans la version 257.

Notez que tous ces fichiers sont situés dans le système de fichiers "tmpfs" que le noyau configure pour la hiérarchie de fichiers de l'initrd et sont donc perdus lorsque le système passe de l'environnement d'exécution de l'initrd au système de fichiers hôte. Si ces ressources doivent être conservées lors de cette transition, elles doivent d'abord être copiées dans un emplacement qui survit à la transition, par exemple via une ligne tmpfiles.d(5) appropriée. Par défaut, cela est fait pour les fichiers de signature et de clé publique du PCR TPM2.

CHAÎNES SMBIOS TYPE 11

systemd-stub peut être configuré à l'aide des chaînes SMBIOS Type 11. Les chaînes applicables consistent en un nom, suivi de "=", suivi de la valeur. À moins que systemd-stub ne détecte qu'il s'exécute dans un environnement de calcul confidentiel, systemd-stub recherche dans la table une chaîne portant un nom spécifique et, si elle est trouvée, utilise sa valeur. Les chaînes suivantes sont lues :

io.systemd.stub.kernel-cmdline-extra

Si elle est définie, la valeur de cette chaîne est ajoutée à la liste des arguments de la ligne de commande du noyau qui sont mesurés dans PCR12 et passés au noyau.

Ajouté dans la version 254.
