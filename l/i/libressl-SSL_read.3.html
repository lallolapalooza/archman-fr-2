SSL_READ(3) Manuel des fonctions de bibliothèque SSL_READ(3)

NOM

SSL_read_ex, SSL_read, SSL_peek_ex, SSL_peek — lire des octets d'une connexion TLS

SYNTAXIS

bibliothèque « libssl » libcrypto
#include <openssl/ssl.h>

int
SSL_read_ex(SSL *ssl, void *buf, size_t num, size_t *readbytes);

int
SSL_read(SSL *ssl, void *buf, int num);

int
SSL_peek_ex(SSL *ssl, void *buf, size_t num, size_t *readbytes);

int
SSL_peek(SSL *ssl, void *buf, int num);

DESCRIPTION

SSL_read_ex() et SSL_read() tentent de lire num octets depuis le ssl spécifié dans le tampon buf. En cas de succès, SSL_read_ex() stocke le nombre d'octets réellement lus dans *readbytes.

SSL_peek_ex() et SSL_peek() sont identiques à SSL_read_ex() et SSL_read(), respectivement, sauf qu'aucun octet n'est retiré du BIO sous-jacent pendant la lecture, de sorte qu'un appel ultérieur à SSL_read_ex() ou SSL_read() retournera au moins les mêmes octets une fois de plus.

Ci-après, SSL_read_ex(), SSL_read(), SSL_peek_ex(), et SSL_peek() sont appelées « fonctions de lecture ».

Si nécessaire, une fonction de lecture négociera une session TLS, si elle n'a pas déjà été explicitement effectuée par SSL_connect(3) ou SSL_accept(3). Si le pair demande une renégociation, elle sera effectuée de manière transparente pendant l'opération de la fonction de lecture. Le comportement des fonctions de lecture dépend du BIO sous-jacent.

Pour que la négociation transparente réussisse, le ssl doit avoir été initialisé en mode client ou serveur. Ceci est fait en appelant SSL_set_connect_state(3) ou SSL_set_accept_state(3) avant le premier appel à une fonction de lecture.

Les fonctions de lecture fonctionnent sur la base des enregistrements TLS. Les données sont reçues dans des enregistrements (avec une taille maximale d'enregistrement de 16 Ko). Ce n'est qu'une fois qu'un enregistrement a été complètement reçu qu'il peut être traité (déchiffré et vérifié pour son intégrité). Par conséquent, les données qui n'ont pas été récupérées lors du dernier appel de lecture peuvent encore être mises en tampon à l'intérieur de la couche TLS et seront récupérées lors du prochain appel de lecture. Si num est supérieur au nombre d'octets mis en tampon, les fonctions de lecture retourneront avec les octets mis en tampon. S'il n'y a plus d'octets dans le tampon, les fonctions de lecture déclencheront le traitement du prochain enregistrement. Ce n'est que lorsque l'enregistrement a été reçu et traité complètement que les fonctions de lecture retourneront en signalant le succès. Au plus, le contenu de l'enregistrement sera retourné. Comme la taille d'un enregistrement TLS peut dépasser la taille maximale du paquet de la couche de transport sous-jacente (par exemple, TCP), il peut être nécessaire de lire plusieurs paquets de la couche de transport avant que l'enregistrement ne soit complet et que l'appel de lecture ne réussisse.

Si le BIO sous-jacent est bloquant, une fonction de lecture ne retournera que lorsque l'opération de lecture sera terminée ou qu'une erreur se produira, sauf lorsqu'une renégociation a lieu, auquel cas un SSL_ERROR_WANT_READ peut survenir. Ce comportement peut être contrôlé avec le drapeau SSL_MODE_AUTO_RETRY de l'appel SSL_CTX_set_mode(3).

Si le BIO sous-jacent est non bloquant, une fonction de lecture retournera également lorsque le BIO sous-jacent n'a pas pu satisfaire les besoins de la fonction pour continuer l'opération. Dans ce cas, un appel à SSL_get_error(3) avec la valeur de retour de la fonction de lecture donnera SSL_ERROR_WANT_READ ou SSL_ERROR_WANT_WRITE. Comme à tout moment une renégociation est possible, une fonction de lecture peut également provoquer des opérations d'écriture. Le processus appelant doit alors répéter l'appel après avoir pris les mesures appropriées pour satisfaire les besoins de la fonction de lecture. L'action dépend du BIO sous-jacent. Lors de l'utilisation d'un socket non bloquant, rien ne doit être fait, mais select(2) peut être utilisé pour vérifier la condition requise. Lors de l'utilisation d'un BIO tamponné, comme une paire de BIO, des données doivent être écrites dans ou récupérées hors du BIO avant de pouvoir continuer.

SSL_pending(3) peut être utilisé pour savoir s'il y a des octets mis en tampon disponibles pour une récupération immédiate. Dans ce cas, une fonction de lecture peut être appelée sans bloquer ni recevoir réellement de nouvelles données du socket sous-jacent.

Lorsqu'une opération de fonction de lecture doit être répétée en raison de SSL_ERROR_WANT_READ ou SSL_ERROR_WANT_WRITE, elle doit être répétée avec les mêmes arguments.

VALEUR DE RETOUR

SSL_read_ex() et SSL_peek_ex() retournent 1 en cas de succès ou 0 en cas d'échec. Le succès signifie qu'un ou plusieurs octets de données d'application ont été lus depuis la connexion SSL. L'échec signifie qu'aucun octet n'a pu être lu depuis la connexion SSL. Les échecs peuvent être répétables (par exemple, nous attendons que plus d'octets soient livrés par le réseau) ou non répétables (par exemple, une erreur réseau fatale). En cas d'échec, appelez SSL_get_error(3) pour déterminer la raison, qui indique si l'appel est répétable ou non.

Pour SSL_read() et SSL_peek(), les valeurs de retour suivantes peuvent se produire :

>0
L'opération de lecture a réussi. La valeur de retour est le nombre d'octets réellement lus depuis la connexion TLS.
0
L'opération de lecture n'a pas réussi. La raison peut être une fermeture propre due à une alerte « close notify » envoyée par le pair (auquel cas le drapeau SSL_RECEIVED_SHUTDOWN dans l'état de fermeture ssl est défini (voir SSL_shutdown(3) et SSL_set_shutdown(3)). Il est également possible que le pair ait simplement fermé le transport sous-jacent et que la fermeture soit incomplète. Appelez SSL_get_error(3) avec la valeur de retour pour savoir si une erreur s'est produite ou si la connexion a été fermée proprement (SSL_ERROR_ZERO_RETURN).
<0
L'opération de lecture n'a pas réussi, soit parce qu'une erreur s'est produite, soit parce que le processus appelant doit prendre une mesure. Appelez SSL_get_error(3) avec la valeur de retour pour connaître la raison.

VOIR AUSSI

SSL_connect(3), SSL_peek(3), SSL_read_ex(3), SSL_CTX_set_mode(3), SSL_shutdown(3)

libressl-SSL_read.3.en

NAME

SSL_read, SSL_read_ex, SSL_peek, SSL_peek_ex ― read or peek at data from an SSL/TLS connection

SYNOPSIS

#include <openssl/ssl.h>
int SSL_read_ex(SSL *ssl, void *buf, size_t num, size_t *readbytes);
int SSL_read(SSL *ssl, void *buf, int num);
int SSL_peek_ex(SSL *ssl, void *buf, size_t num, size_t *readbytes);
int SSL_peek(SSL *ssl, void *buf, int num);

DESCRIPTION

The SSL_read_ex() function attempts to read up to num bytes from the SSL/TLS connection described by ssl into the buffer buf. The actual number of bytes read is stored in the location pointed to by readbytes. The function may return before reading num bytes, even if the connection is not yet closed.

The SSL_read() function is a legacy version of SSL_read_ex(). It attempts to read up to num bytes from the SSL/TLS connection described by ssl into the buffer buf. The return value is the number of bytes read, or a value less than or equal to 0 if an error occurred.

The SSL_peek_ex() function is similar to SSL_read_ex(), but it does not consume the data from the input buffer. The next call to SSL_read() or SSL_peek() will return the same data again. It attempts to peek at up to num bytes from the SSL/TLS connection described by ssl into the buffer buf. The actual number of bytes peeked at is stored in the location pointed to by readbytes. The function may return before peeking at num bytes, even if the connection is not yet closed.

The SSL_peek() function is a legacy version of SSL_peek_ex(). It is similar to SSL_read(), but does not consume the data. It attempts to peek at up to num bytes from the SSL/TLS connection described by ssl into the buffer buf. The return value is the number of bytes peeked at, or a value less than or equal to 0 if an error occurred.

After a call to any of these functions, the application must check the return value. If it is positive, the expected number of bytes was read or peeked at. If it is 0 or negative, an error occurred. The error can be determined by checking the return value of SSL_get_error(3).

A return value of 0 from SSL_read() or SSL_peek() indicates that the TLS/SSL connection was closed by the peer.

A return value of -1 from SSL_read_ex() or SSL_peek_ex() indicates an error. The actual error code can be retrieved using SSL_get_error(3).

A return value of 0 from SSL_read_ex() or SSL_peek_ex() indicates that the TLS/SSL connection was closed by the peer.

If SSL_get_error() returns SSL_ERROR_WANT_READ or SSL_ERROR_WANT_WRITE, the operation did not make progress and the application should try again after waiting for the appropriate file descriptor to become ready.

If SSL_get_error() returns SSL_ERROR_ZERO_RETURN, the TLS/SSL connection was closed by the peer.

The SSL_read() and SSL_peek() functions are retained for compatibility with older versions of OpenSSL. New applications should use SSL_read_ex() and SSL_peek_ex() respectively.

RETURN VALUES

SSL_read_ex() and SSL_peek_ex() return 1 on success, and 0 on failure or closure of the connection.

SSL_read() and SSL_peek() return the number of bytes read or peeked at on success, 0 if the connection was closed by the peer, or a negative value if an error occurred.

Use SSL_get_error(3) to determine the error cause.

SEE ALSO

BIO_new(3), ssl(3), SSL_accept(3), SSL_connect(3), SSL_CTX_new(3), SSL_CTX_set_mode(3), SSL_get_error(3), SSL_pending(3), SSL_set_connect_state(3), SSL_set_shutdown(3), SSL_shutdown(3), SSL_write(3)

HISTORY

SSL_read() appeared in SSLeay 0.4 or earlier. SSL_peek() first appeared in SSLeay 0.6.6. Both functions have been available since OpenBSD 2.4.

SSL_read_ex() and SSL_peek_ex() first appeared in OpenSSL 1.1.1 and have been available since OpenBSD 7.1.
