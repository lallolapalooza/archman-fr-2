NOM

libgetdns -- une implémentation d'une API DNS moderne et asynchrone par et pour les développeurs d'applications

BIBLIOTHÈQUE

Bibliothèque de résolution DNS (libgetdns, -lgetdns)

SYNOPSIS

libgetdns

Cette page man décrit la bibliothèque getdns, les concepts généraux derrière l'API et certains des éléments communs de l'interface publique de la bibliothèque. Chacun des points d'entrée publics et des types de données plus complexes sont décrits dans des pages man distinctes.

DESCRIPTION

getdns est une API DNS asynchrone moderne conçue pour être utile aux développeurs d'applications et aux distributeurs de systèmes d'exploitation en tant que moyen de rendre tous les types d'informations DNS facilement accessibles dans de nombreux types de programmes. Les principales fonctionnalités de cette nouvelle API sont :


Prise en charge complète de la programmation événementielle
Prend en charge DNSSEC de plusieurs manières
Miroir de la résolution dans getaddrinfo()
Prend facilement en charge tous les types d'enregistrements (RRtypes), même ceux non encore définis

Chacun des points d'entrée est proposé avec des signatures asynchrones et synchrones. Les fonctions asynchrones s'appuient sur la gestion des événements et les rappels via libevent. Les fonctions sont thread-safe.

Une structure de contexte maintient les données de requête et de réponse DNS et est utilisée pour maintenir l'état pendant les appels aux points d'entrée publics.

La page du projet pour cette implémentation se trouve à

http://getdnsapi.net

La spécification est maintenue à

http://getdnsapi.net/spec

Le dépôt git pour cette implémentation se trouve à

http://github.com/getdnsapi/getdns

STRUCTURES DE DONNÉES

L'API utilise quelques structures de données pour passer des données dans et retourner des données depuis les points d'entrée publics.

liste
une liste ordonnée, les membres de la liste peuvent être n'importe lequel des quatre types de données.
dictionnaire
une paire nom-valeur. Le nom est une chaîne littérale et la valeur peut être n'importe lequel des quatre types de données. L'ordre des paires nom-valeur dans un dictionnaire n'est pas important.
entier
un entier compatible avec uint32_t.
données binaires
une structure utilisée pour contenir des données binaires définies comme { size_t size; uint8_t *binary_stuff; }.

UTILISATION ASYNCHRONE

La spécification getdns met l'accent sur la nature asynchrone de l'API et permet aux implémentations de définir leur propre approche. Cette page documente les décisions de cette implémentation et les facilités fournies au développeur.

Cette implémentation fournit un support asynchrone via les mécanismes suivants :

Interrogation de descripteurs de fichiers
Intégrations de boucle d'événements :
libevent
libuv
libev
Intégrations de boucle d'événements personnalisées

Toutes les fonctions et tous les types mentionnés dans cette page sont déclarés dans getdns_extra.h

Boucle d'événements intégrée

La bibliothèque possède une boucle d'événements intégrée qui peut être utilisée si aucune des extensions pour les boucles d'événements externes n'est utilisée. La bibliothèque exécutera les requêtes et distribuera les rappels avec un appel à getdns_context_run(). Si une extension de boucle d'événements est utilisée, cela exécutera la boucle d'événements de l'extension.

void getdns_context_run(getdns_context *context)

Exécute la boucle d'événements du contexte jusqu'à ce qu'il n'y ait plus rien à faire.

uint32_t getdns_context_get_num_pending_requests(getdns_context* context, struct timeval* next_timeout)

Obtient le nombre de requêtes asynchrones en attente pour un contexte donné ainsi que le temps restant jusqu'au prochain délai d'attente. La structure next_timeout peut être NULL. Si elle est fournie et que le nombre de requêtes en attente est supérieur à 0, alors le délai d'attente représente le temps relatif jusqu'au prochain délai d'attente.

getdns_return_t getdns_context_process_async(getdns_context* context)

Informe le contexte de traiter ses requêtes en attente. Les utilisateurs doivent appeler cela lorsqu'un délai d'attente s'est produit ou que le descripteur de fichier signale qu'il est prêt. Les rappels utilisateur sont déclenchés pendant cet appel.

Intégrations de boucles d'événements incluses

Un certain nombre d'applications obtiennent un comportement asynchrone en tirant parti des bibliothèques d'abstraction de boucles d'événements. Si le système de construction détecte une bibliothèque de boucle d'événements prise en charge, l'extension de la boucle d'événements est construite en plus de la bibliothèque getdns. Les extensions sont construites en tant que bibliothèque partagée supplémentaire. Les bibliothèques de boucle d'événements suivantes sont prises en charge :

libevent1 et libevent2

L'extension libevent permet à un contexte de se connecter à une event_base. La boucle d'événements est ensuite exécutée comme toute autre application utilisant libevent via event_base_dispatch ou event_base_loop, et les rappels getdns sont attendus.

Notez que si libevent1 et libevent2 résident sur le système, l'extension utilise libevent2.

Bibliothèque d'extension : libgetdns_ext_event.[shared_lib_ext]
En-tête d'extension : getdns/getdns_ext_libevent.h

libuv

L'extension libuv permet à un contexte de se connecter à une uv_loop_s. La boucle d'événements peut alors être exécutée comme toute autre application utilisant libuv via uv_run et les rappels getdns sont attendus.

Bibliothèque d'extension : libgetdns_ext_uv.[shared_lib_ext]
En-tête d'extension : getdns_ext_libuv.h

libev

L'extension libev permet à un contexte de se connecter à une ev_loop. La boucle d'événements peut alors être exécutée comme toute autre application utilisant libev via ev_run et les rappels getdns sont attendus.

Bibliothèque d'extension : libgetdns_ext_ev.[shared_lib_ext]
En-tête d'extension : getdns_ext_libev.h

Fonctions de l'extension de boucle d'événements getdns_context

Les fonctions suivantes sont utilisées par le point d'entrée de l'extension pour se connecter à un contexte particulier.

L'application définit une extension de boucle d'événements sur un contexte. Les extension_data sont des données optionnelles qui sont passées aux méthodes d'extension. Si une boucle d'événements est déjà définie sur un contexte, elle est nettoyée. Toutes les requêtes en attente sont également annulées.

getdns_return_t getdns_extension_set_eventloop(struct getdns_context* context, getdns_eventloop_extension* extension, void* extension_data);

L'application obtient les données d'extension associées à un contexte.

void* getdns_context_get_extension_data(struct getdns_context* context);

Lorsqu'il n'y a plus de travail à effectuer, l'application détache une boucle d'événements d'un contexte.

getdns_return_t getdns_extension_detach_eventloop(struct getdns_context* context);

UTILISATION SYNCHRONE

Il existe quatre fonctions synchrones parallèles aux quatre fonctions asynchrones getdns, à l'exception du fait qu'il n'y a pas de paramètre de rappel. Lorsqu'une application appelle l'une de ces fonctions synchrones, l'API rassemble toutes les informations nécessaires puis retourne le résultat. La valeur retournée est exactement la même que la réponse retournée dans le rappel si vous aviez utilisé la version asynchrone de la fonction.

Lorsque vous avez terminé avec les données de la réponse, appelez getdns_free_sync_request_memory afin que l'API puisse libérer la mémoire de son pool interne.

Pour utiliser une extension, ajoutez-la au dictionnaire d'extensions avant de faire l'appel au point d'entrée public et définissez la valeur en fonction du comportement attendu. Défini sur GETDNS_EXTENSION_TRUE pour que les résultats des enregistrements A et AAAA pour le nom interrogé soient inclus dans l'objet de réponse.

DNSSEC

Si une application souhaite que l'API effectue la validation DNSSEC pour une requête, elle doit définir une ou plusieurs extensions liées à DNSSEC. Notez que par défaut, aucune de ces extensions n'est définie et l'API n'effectuera pas de validation DNSSEC. Notez que l'obtention de résultats DNSSEC peut prendre plus de temps dans certains cas.

Pour renvoyer le statut DNSSEC pour chaque enregistrement DNS dans la liste replies_tree, utilisez l'extension dnssec_return_status. La valeur de l'extension (un entier) est définie sur GETDNS_EXTENSION_TRUE pour que le statut renvoyé porte le nom dnssec_status (un entier) ajouté aux autres noms du dictionnaire de l'enregistrement ("header", "question", etc.). Les valeurs pour ce nom sont GETDNS_DNSSEC_SECURE, GETDNS_DNSSEC_BOGUS, GETDNS_DNSSEC_INDETERMINATE et GETDNS_DNSSEC_INSECURE. Ainsi, une réponse pourrait ressembler à ceci :

{     # Ceci est la première réponse
      "dnssec_status": GETDNS_DNSSEC_INDETERMINATE,
      "header": { "id": 23456, "qr": 1, "opcode": 0, ... },
      . . .

Si, au lieu de renvoyer le statut, vous souhaitez uniquement voir les résultats sécurisés, utilisez l'extension dnssec_return_only_secure. La valeur de l'extension (un entier) est définie sur GETDNS_EXTENSION_TRUE pour que seuls les enregistrements que l'API peut valider comme sécurisés avec DNSSEC soient renvoyés dans les listes replies_tree et replies_full. Aucun nom supplémentaire n'est ajouté au dictionnaire de l'enregistrement ; le changement est que certains enregistrements pourraient ne pas apparaître dans les résultats. Lorsque cette option de contexte est définie, si l'API reçoit des réponses DNS mais qu'aucune n'est déterminée comme étant sécurisée, le code d'erreur au niveau supérieur de l'objet de réponse est GETDNS_RESPSTATUS_NO_SECURE_ANSWERS.

ENREGISTREMENTS DE RESSOURCES OPT

Pour les recherches qui nécessitent un enregistrement de ressource OPT dans la section Données supplémentaires, utilisez l'extension add_opt_parameters. La valeur de l'extension (un dictionnaire) contient les paramètres ; ceux-ci sont décrits plus en détail dans la RFC 2671. Ce sont :

maximum_udp_payload_size (un entier) entre 512 et 65535 ; si non spécifié, il prend par défaut les valeurs du contexte DNS

extended_rcode (un entier) entre 0 et 255 ; si non spécifié, il prend par défaut les valeurs du contexte DNS

version (un entier) entre 0 et 255 ; si non spécifié, il prend par défaut 0

do_bit (un entier) entre 0 et 1 ; si non spécifié, il prend par défaut les valeurs du contexte DNS

options (une liste) contient des dictionnaires pour chaque option à spécifier. Chaque élément de liste contient deux noms : option_code (un entier) et option_data (des données binaires). L'API analyse l'ensemble des options en un RDATA correctement formaté pour l'enregistrement de ressource.

Il est très important de noter que l'enregistrement de ressource OPT spécifié dans l'extension add_opt_parameters pourrait ne pas être le même que celui que l'API envoie dans la requête. Par exemple, si l'application inclut également l'une des extensions DNSSEC, l'API s'assurera que l'enregistrement de ressource OPT configure correctement l'enregistrement de ressource, en apportant les modifications nécessaires aux paramètres de l'extension add_opt_parameters.

L'utilisation de cette extension peut entrer en conflit avec les valeurs du contexte DNS. Par exemple, la valeur par défaut pour un système d'exploitation pourrait être une taille de charge utile maximale de 65535, mais l'extension pourrait spécifier 1550. Dans un tel cas, l'API respectera les valeurs indiquées dans l'extension, mais honorera les valeurs du contexte DNS si aucune valeur n'est donnée dans l'extension.

DONNÉES DE RÉPONSE

La fonction de rappel contient un pointeur vers un objet de réponse. Un objet de réponse est toujours un dictionnaire. L'objet de réponse contient toujours au moins trois noms : replies_full (une liste) et replies_tree (une liste), et status (un entier). replies_full est une liste de réponses DNS (chacune étant des données binaires) telles qu'elles apparaissent sur le réseau. replies_tree est une liste de réponses DNS (chacune étant un dictionnaire) avec les différentes parties de la réponse analysées. status est un code d'état pour la requête.

Étant donné que l'API peut être étendue à l'avenir, un objet de réponse peut également contenir des noms autres que replies_full, replies_tree et status. De même, tous les dictionnaires décrits ici peuvent être étendus dans les versions ultérieures de l'API. Ainsi, une application utilisant l'API ne doit pas supposer qu'elle connaît tous les noms possibles dans un dictionnaire.

La liste suivante présente les codes d'état pour les objets de réponse. Notez que, si le statut indique qu'il n'y a pas de réponses pour la requête, les listes dans replies_full et replies_tree auront une longueur nulle.

GETDNS_RESPSTATUS_GOOD Au moins une réponse a été renvoyée

GETDNS_RESPSTATUS_NO_NAME Les requêtes pour le nom ont abouti à des réponses négatives

GETDNS_RESPSTATUS_ALL_TIMEOUT Toutes les requêtes pour le nom ont expiré

GETDNS_RESPSTATUS_NO_SECURE_ANSWERS Le paramètre de contexte pour obtenir uniquement des réponses sécurisées a été spécifié, et au moins une réponse DNS a été reçue, mais aucune réponse DNS n'a été déterminée comme étant sécurisée via DNSSEC.

Le niveau supérieur de replies_tree peut éventuellement avoir les noms suivants : canonical_name (données binaires), intermediate_aliases (liste), answer_ipv4_address (données binaires), answer_ipv6_address (données binaires) et answer_type (un entier).

La valeur de canonical_name est le nom que l'API a utilisé pour sa recherche. Elle est au format de présentation FQDN. Les valeurs de la liste intermediate_aliases sont des noms de domaine provenant de tout CNAME ou DNAME non synthétisé trouvé lors de la résolution de la requête originale. La liste peut avoir zéro entrée s'il n'y avait pas de CNAME dans le chemin. Ceux-ci peuvent être utiles, par exemple, pour les comparaisons de noms lors du suivi des règles de la RFC 612

5. La valeur de answer_ipv4_address et answer_ipv6_address sont les adresses du serveur à partir duquel la réponse a été reçue. La valeur de answer_type est le type de service de nom qui a généré la réponse. Les valeurs sont :


GETDNS_NAMETYPE_DNS
DNS normal (RFC 1035)
GETDNS_NAMETYPE_WINS
Le service de noms WINS (une référence est nécessaire)

Si l'appel était getdns_address ou getdns_address_sync, le niveau supérieur de replies_tree a un nom supplémentaire, just_address_answers (une liste). La valeur de just_address_answers est une liste qui contient tous les enregistrements A et AAAA des sections de réponse de toutes les réponses, dans l'ordre où ils apparaissent dans les réponses. Chaque élément de la liste est un dictionnaire avec au moins deux noms : address_type (dont la valeur est un bindata ; il est actuellement soit "IPv4", soit "IPv6") et address_data (dont la valeur est un bindata). Notez que l'extension dnssec_return_only_secure affecte ce qui apparaîtra dans la liste just_address_answers. Si le DNS renvoie d'autres types d'adresses, ces types apparaîtront également dans cette liste.

L'API peut faciliter la découverte de services via les enregistrements SRV. Si l'appel était getdns_service ou getdns_service_sync, le niveau supérieur de replies_tree a un nom supplémentaire, srv_addresses (une liste). La liste est ordonnée par priorité et poids selon l'algorithme de pondération de la RFC 2782, la valeur de priorité la plus basse en premier. Chaque élément de la liste est un dictionnaire qui a au moins deux noms : port et domain_name. Si l'API a pu déterminer l'adresse du nom de domaine cible (par exemple, à partir de son cache ou de la section Additional des réponses), le dictionnaire d'un élément contiendra également address_type (dont la valeur est un bindata ; il est actuellement soit "IPv4", soit "IPv6") et address_data (dont la valeur est un bindata). Notez que l'extension dnssec_return_only_secure affecte ce qui apparaîtra dans la liste srv_addresses.

STRUCTURE DE REPLIES_TREE DNS

Les noms dans chaque entrée de la liste replies_tree pour les réponses DNS comprennent header (un dictionnaire), question (un dictionnaire), answer (une liste), authority (une liste) et additional (une liste), correspondant aux sections du format du message DNS. Les listes answer, authority et additional contiennent chacune zéro ou plusieurs dictionnaires, chaque dictionnaire de chaque liste représentant un enregistrement de ressource.

Les noms du dictionnaire header sont tous les champs de la section 4.1.1. de la RFC 1035. Ce sont : id, qr, opcode, aa, tc, rd, ra, z, rcode, qdcount, ancount, nscount et arcount. Tous sont des entiers.

Les noms du dictionnaire question sont les trois champs de la section 4.1.2. de la RFC 1035 : qname (un bindata), qtype (un entier) et qclass (un entier).

Les enregistrements de ressources sont un peu différents des en-têtes et des sections de questions dans la mesure où la partie RDATA a souvent sa propre structure. Les autres noms dans les dictionnaires d'enregistrements de ressources sont name (un bindata), type (un entier), class (un entier), ttl (un entier) et rdata (un dictionnaire) ; il n'y a pas d'équivalent de nom pour le champ RDLENGTH.

Le dictionnaire rdata a des noms différents pour chaque type de réponse. Il existe une liste complète des types définis dans l'API. Pour les noms qui se terminent par "-obsolete" ou "-unknown", le bindata est l'intégralité du champ RDATA. Par exemple, le rdata d'un enregistrement A a un nom ipv4_address (un bindata) ; le rdata d'un enregistrement SRV a les noms priority (un entier), weight (un entier), port (un entier) et target (un bindata).

Chaque dictionnaire rdata a également un champ rdata_raw (un bindata). Ceci est utile pour les types non définis dans cette version de l'API. Il pourrait également être utile si une version ultérieure de l'API autorisait des analyseurs supplémentaires. Ainsi, interroger des types non reconnus par l'API renverra toujours un résultat : un rdata avec seulement un rdata_raw.

Il est prévu que des extensions ultérieures de l'API donnent des noms différents à certains types DNS. Il est également possible que des extensions ultérieures modifient les noms de certains des types DNS listés ci-dessus.

FONCTIONS DE RAPPEL

Un appel aux fonctions asynchrones getdns retourne généralement avant que toute opération d'E/S réseau ou de fichier ne se produise. Après que l'API a marshallé toutes les informations nécessaires, elle appelle la fonction de rappel qui a été passée par l'application. La fonction de rappel peut être appelée à tout moment, même avant que la fonction appelante n'ait retourné. L'API garantit que la fonction de rappel sera appelée exactement une fois, sauf si la fonction appelante a retourné une erreur, auquel cas la fonction de rappel n'est jamais appelée.

La fonction appelante getdns appelle la fonction de rappel avec les paramètres définis comme suit :

typedef void (*getdns_callback_t)(

getdns_context_t context,
uint16_t callback_type,
getdns_dict *response,
void *userarg,
getdns_transaction_t transaction_id)

context Voir getdns_context (3)

callback_type Indique la raison du rappel.

GETDNS_CALLBACK_COMPLETE La réponse contient les données demandées

GETDNS_CALLBACK_CANCEL Le programme appelant a annulé le rappel ; response est NULL

GETDNS_CALLBACK_TIMEOUT L'action demandée a expiré ; response est NULL

GETDNS_CALLBACK_ERROR L'action demandée a rencontré une erreur ; response est NULL

response Un objet de réponse contenant les données de réponse. Ceci est décrit dans la section intitulée "DONNÉES DE RÉPONSE" ailleurs dans cette page de manuel. L'objet de réponse fait partie de l'espace mémoire de l'API et sera libéré par l'API une fois le rappel retourné.

userarg Identique au userarg passé à la fonction appelante.

transaction_id L'identifiant de transaction attribué par la fonction appelante, utilisé pour associer une réponse DNS à une requête DNS spécifique.

Pour annuler un rappel en attente, utilisez la fonction suivante.


getdns_return_t
getdns_cancel_callback (getdns_context_t context, getdns_transaction_t transaction_id)

Ceci provoque l'appel de la fonction de rappel par l'API avec un callback_type de GETDNS_CALLBACK_CANCEL si la fonction de rappel pour cet transaction_id n'a pas déjà été appelée. Le code de rappel pour l'annulation doit nettoyer toute mémoire liée à l'appel identifié, par exemple, pour désallouer la mémoire du userarg. getdns_cancel_callback() peut retourner immédiatement, même avant que la fonction de rappel n'ait terminé son travail et ne retourne. Appeler getdns_cancel_callback() avec un transaction_id d'une fonction de rappel déjà appelée ou d'un transaction_id inconnu retourne GETDNS_RETURN_UNKNOWN_TRANSACTION ; sinon, getdns_cancel_callback() retourne GETDNS_RETURN_GOOD.
