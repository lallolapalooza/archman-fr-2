I. Introduction

Ce fichier décrit comment utiliser et modifier la bibliothèque de référence PNG (connue sous le nom de libpng) pour votre propre usage. En plus de ce fichier, example.c est un bon point de départ pour utiliser la bibliothèque, car il est très commenté et devrait inclure tout ce dont la plupart des gens auront besoin. Nous supposons que libpng est déjà installé ; consultez le fichier INSTALL pour les instructions sur la façon de configurer et d'installer libpng.

Pour des exemples d'utilisation de libpng, consultez les fichiers "example.c", "pngtest.c", et les fichiers du répertoire "contrib", qui sont tous inclus dans la distribution libpng.

Libpng a été écrit en complément de la spécification PNG, comme moyen de réduire le temps et l'effort nécessaires pour supporter le format de fichier PNG dans les programmes d'application.

La spécification PNG (Troisième Édition), juin 2025, est disponible en tant que recommandation W3C à l'adresse : https://www.w3.org/TR/2025/REC-png-3-20250624/.

La spécification PNG (Deuxième Édition), novembre 2003, est disponible en tant que recommandation W3C et en tant que norme ISO (ISO/IEC 15948:2004 (E)) à l'adresse : https://www.w3.org/TR/2003/REC-PNG-20031110/. Les documents W3C et ISO ont un contenu technique identique.

La spécification PNG-1.2 est disponible à l'adresse : https://www.libpng.org/pub/png/spec/1.2/. Elle est techniquement équivalente à la spécification PNG (Deuxième Édition) mais contient du matériel supplémentaire.

La spécification PNG-1.0 est disponible en tant que RFC 2083 à l'adresse : https://www.libpng.org/pub/png/spec/1.0/ et en tant que recommandation W3C à l'adresse : https://www.w3.org/TR/REC-png-961001.

Certains chunks supplémentaires sont décrits dans les documents sur les chunks publics à usage spécial à l'adresse : http://www.libpng.org/pub/png/spec/register/

D'autres informations sur PNG, et la dernière version de libpng, peuvent être trouvées sur la page d'accueil de PNG, à l'adresse : http://www.libpng.org/pub/png/.

La plupart des utilisateurs n'auront pas à modifier la bibliothèque de manière significative ; les utilisateurs avancés pourraient vouloir la modifier davantage. Tous les efforts ont été faits pour la rendre aussi complète que possible, tout en gardant le code facile à comprendre. Actuellement, cette bibliothèque ne supporte que le C. Le support pour d'autres langages est à l'étude.

Libpng a été conçue pour gérer plusieurs sessions simultanément, pour être facilement modifiable, pour être portable sur la grande majorité des machines disponibles (ANSI, K&R, 16, 32 et 64 bits), et pour être facile à utiliser. L'objectif ultime de libpng est de promouvoir l'acceptation du format de fichier PNG de toutes les manières possibles. Bien qu'il reste encore du travail à faire (voir le fichier TODO), libpng devrait couvrir la majorité des besoins de ses utilisateurs.

Libpng utilise zlib pour sa compression et sa décompression des fichiers PNG. Des informations supplémentaires sur zlib, et la dernière version de zlib, peuvent être trouvées sur la page d'accueil de zlib, à l'adresse : https://zlib.net/. L'utilitaire de compression zlib est un utilitaire à usage général qui est utile pour plus que les fichiers PNG, et peut être utilisé sans libpng. Voir la documentation fournie avec zlib pour plus de détails. Vous pouvez généralement trouver les fichiers sources de l'utilitaire zlib là où vous trouvez les fichiers sources de libpng.

Libpng est thread-safe, à condition que les threads utilisent des instances différentes des structures. Chaque thread doit avoir ses propres instances de png_struct et png_info, et donc sa propre image. Libpng ne se protège pas contre deux threads utilisant la même instance d'une structure.

II. Structures

Il existe deux structures principales importantes pour libpng : png_struct et png_info. Les deux sont des structures internes qui ne sont plus exposées dans l'interface libpng (depuis libpng 1.5.0).

La structure png_info est conçue pour fournir des informations sur le fichier PNG. À une époque, les champs de png_info étaient destinés à être directement accessibles à l'utilisateur. Cependant, cela a entraîné des problèmes avec les applications utilisant des bibliothèques chargées dynamiquement, et par conséquent, un ensemble de fonctions d'interface pour png_info (les fonctions png_get_*() et png_set_*()) a été développé, et l'accès direct aux champs de png_info a été déprécié.

La structure png_struct est l'objet utilisé par la bibliothèque pour décoder une seule image. Depuis la version 1.5.0, cette structure n'est pas non plus exposée.

Presque toutes les API de libpng nécessitent un pointeur vers un png_struct comme premier argument. Beaucoup (en particulier les API png_set et png_get) nécessitent également un pointeur vers png_info comme deuxième argument. Certaines macros visibles par l'application définies dans png.h conçues pour l'accès de base aux données (lecture et écriture d'entiers au format PNG) ne prennent pas de pointeur png_info, mais il est presque toujours sûr de supposer qu'un (png_struct*) doit être passé pour appeler une fonction API.

Vous pouvez avoir plus d'une structure png_info associée à une image, comme illustré dans pngtest.c, une pour les informations valides avant les chunks IDAT et une autre (appelée "end_info" ci-dessous) pour les éléments après eux.

Le fichier d'en-tête png.h est une référence inestimable pour la programmation avec libpng. Et tant que j'y suis, assurez-vous d'inclure le fichier d'en-tête libpng :

#include <png.h>

et aussi (depuis libpng-1.5.0) le fichier d'en-tête zlib, si vous en avez besoin :

#include <zlib.h>

Types

Le fichier d'en-tête png.h définit un certain nombre de types intégraux utilisés par les API. La plupart d'entre eux sont assez évidents ; par exemple, les types correspondant à des entiers de tailles particulières et les types pour passer les valeurs de couleur.

Une exception concerne la gestion des nombres non entiers. Pour la commodité de l'application, la plupart des API qui acceptent de tels nombres ont des arguments C (double) ; cependant, en interne, PNG et libpng utilisent des entiers signés de 32 bits et codent la valeur en multipliant par 100 000. Depuis libpng 1.5.0, une macro de commodité PNG_FP_1 est définie dans png.h avec un type (png_fixed_point) qui est simplement (png_int_32).

Toutes les API qui acceptent des arguments (double) ont également une API correspondante qui accepte les arguments d'entiers à point fixe correspondants. L'API à point fixe porte le même nom que celle à virgule flottante, avec "_fixed" ajouté. La plage réelle de valeurs autorisées dans les API est fréquemment inférieure à la plage complète de (png_fixed_point) (-21474 à +21474). Lorsque les API requièrent un argument non négatif, le type est enregistré comme png_uint_32 ci-dessus. Consultez le fichier d'en-tête et le texte ci-dessous pour plus d'informations.

Une attention particulière doit être accordée à la gestion des chunks sCAL car le chunk lui-même utilise des valeurs non entières codées sous forme de chaînes contenant des nombres à virgule flottante décimaux. Voir les commentaires dans le fichier d'en-tête.

Configuration

Les déclarations de fonctions principales dans le fichier d'en-tête sont souvent protégées par des directives de préprocesseur C de la forme :


#ifdef PNG_feature_SUPPORTED
declare-function
#endif
...
#ifdef PNG_feature_SUPPORTED
use-function
#endif

La bibliothèque peut être construite sans prise en charge de ces API, bien qu'une construction standard ait toutes les API implémentées. Les programmes d'application doivent vérifier les macros de fonctionnalité avant d'utiliser une API pour une portabilité maximale. Depuis libpng 1.5.0, les macros de fonctionnalité définies lors de la construction de libpng sont enregistrées dans le fichier d'en-tête "pnglibconf.h" et ce fichier est toujours inclus par png.h.

Si vous n'avez pas besoin de modifier la configuration de la bibliothèque par rapport à la configuration par défaut, passez à la section suivante ("Lecture").

Notez que certains makefiles dans le répertoire 'scripts' et (en 1.5.0) tous les fichiers de projet de construction dans le répertoire 'projects' copient simplement scripts/pnglibconf.h.prebuilt vers pnglibconf.h. Cela signifie que ces systèmes de construction ne permettent pas une configuration automatique facile de la bibliothèque - ils ne supportent que la configuration par défaut.

La manière la plus simple d'apporter des modifications mineures à la configuration de libpng lorsque la configuration automatique est prise en charge est d'ajouter des définitions à la ligne de commande en utilisant (typiquement) CPPFLAGS. Par exemple :

CPPFLAGS=-DPNG_NO_FLOATING_ARITHMETIC

modifiera l'implémentation mathématique interne de libpng pour la correction gamma et d'autres calculs arithmétiques pour utiliser le point fixe, évitant ainsi le besoin d'un support flottant rapide. Le résultat peut être vu dans le pnglibconf.h généré - assurez-vous qu'il contient le paramètre macro de fonctionnalité modifié.

Si vous avez besoin d'apporter des modifications de configuration plus étendues - plus d'un ou deux paramètres de macro de fonctionnalité - vous pouvez soit ajouter -DPNG_USER_CONFIG à la ligne de commande de construction et placer une liste de paramètres de macro de fonctionnalité dans pngusr.h, soit définir DFA_XTRA (une variable makefile) sur un fichier contenant les mêmes informations sous forme de paramètres 'option'.

II. Configuration

Libpng is configurable at compile time, and also at run time. Compile time configuration is done by setting preprocessor options. Run time configuration is done by calling library functions which are described below.

A. Compile time

There are many options that can be set at compile time by defining preprocessor macros. These macros are listed in `scripts/pnglibconf.dfa`. You can define them on the command line, e.g.:


make CFLAGS='-DPNG_DEBUG=1 -DPNG_ZBUF_SIZE=16384'

This example enables debugging output and increases the zlib compression buffer size. The macros are described in the file `scripts/pnglibconf.dfa`. The meanings of the macros and their values are fully described in the C comments in that file. Be sure to read the file carefully. Pay particular attention to the `option` information in `scripts/pnglibconf.dfa` that describes those features and their requirements. This is easy to get wrong.

B. Configuration using DFA_XTRA

Rebuilding from pnglibconf.dfa is easy if a functioning 'awk', or a later variant such as 'nawk' or 'gawk', is available. The configure build will automatically find an appropriate awk and build pnglibconf.h. The scripts/pnglibconf.mak file contains a set of make rules for doing the same thing if configure is not used, and many of the makefiles in the scripts directory use this approach.

When rebuilding simply write a new file containing changed options and set DFA_XTRA to the name of this file. This causes the build to append the new file to the end of scripts/pnglibconf.dfa. The pngusr.dfa file should contain lines of the following forms:

everything = off

This turns all optional features off. Include it at the start of pngusr.dfa to make it easier to build a minimal configuration. You will need to turn at least some features on afterward to enable either reading or writing code, or both.

option feature on option feature off

Enable or disable a single feature. This will automatically enable other features required by a feature that is turned on or disable other features that require a feature which is turned off. Conflicting settings will cause an error message to be emitted by awk.

setting feature default value

Changes the default value of setting 'feature' to 'value'. There are a small number of settings listed at the top of pnglibconf.h, they are documented in the source code. Most of these values have performance implications for the library but most of them have no visible effect on the API. Some can also be overridden from the API.

This method of building a customized pnglibconf.h is illustrated in contrib/pngminim/*. See the "$(PNGCONF):" target in the makefile and pngusr.dfa in these directories.

C. Configuration using PNG_USER_CONFIG

If -DPNG_USER_CONFIG is added to the CPPFLAGS when pnglibconf.h is built, the file pngusr.h will automatically be included before the options in scripts/pnglibconf.dfa are processed. Your pngusr.h file should contain only macro definitions turning features on or off or setting settings.

Apart from the global setting "everything = off" all the options listed above can be set using macros in pngusr.h:

#define PNG_feature_SUPPORTED

is equivalent to:

option feature on

#define PNG_NO_feature

is equivalent to:

option feature off

#define PNG_feature value

is equivalent to:

setting feature default value

Notice that in both cases, pngusr.dfa and pngusr.h, the contents of the pngusr file you supply override the contents of scripts/pnglibconf.dfa

If confusing or incomprehensible behavior results it is possible to examine the intermediate file pnglibconf.dfn to find the full set of dependency information for each setting and option. Simply locate the feature in the file and read the C comments that precede it.

This method is also illustrated in the contrib/pngminim/* makefiles and pngusr.h.

III. Reading

We'll now walk you through the possible functions to call when reading in a PNG file sequentially, briefly explaining the syntax and purpose of each one. See example.c and png.h for more detail. While progressive reading is covered in the next section, you will still need some of the functions discussed in this section to read a PNG file.

Setup

You will want to do the I/O initialization(*) before you get into libpng, so if it doesn't work, you don't have much to undo. Of course, you will also want to insure that you are, in fact, dealing with a PNG file. Libpng provides a simple check to see if a file is a PNG file. To use it, pass in the first 1 to 8 bytes of the file to the function png_sig_cmp(), and it will return 0 (false) if the bytes match the corresponding bytes of the PNG signature, or nonzero (true) otherwise. Of course, the more bytes you pass in, the greater the accuracy of the prediction.

If you are intending to keep the file pointer open for use in libpng, you must ensure you don't read more than 8 bytes from the beginning of the file, and you also have to make a call to png_set_sig_bytes() with the number of bytes you read from the beginning. Libpng will then only check the bytes (if any) that your program didn't read.

(*): If you are not using the standard I/O functions, you will need to replace them with custom functions. See the discussion under Customizing libpng.


FILE *fp = fopen(file_name, "rb");
if (!fp)
{
return ERROR;
}


if (fread(header, 1, number, fp) != number)
{
return ERROR;
}


is_png = (png_sig_cmp(header, 0, number) == 0);
if (!is_png)
{
return NOT_PNG;
}

Next, png_struct and png_info need to be allocated and initialized. In order to ensure that the size of these structures is correct even with a dynamically linked libpng, there are functions to initialize and allocate the structures. We also pass the library version, optional pointers to error handling functions, and a pointer to a data struct for use by the error functions, if necessary (the pointer and functions can be NULL if the default error handlers are to be used). See the section on Changes to Libpng below regarding the old initialization functions. The structure allocation functions quietly return NULL if they fail to create the structure, so your application should check for that.


png_structp png_ptr = png_create_read_struct
(PNG_LIBPNG_VER_STRING, (png_voidp)user_error_ptr,
user_error_fn, user_warning_fn);


if (!png_ptr)
return ERROR;


png_infop info_ptr = png_create_info_struct(png_ptr);


if (!info_ptr)
{
png_destroy_read_struct(&png_ptr, NULL, NULL);
return ERROR;
}

If you want to use your own memory allocation routines, use a libpng that was built with PNG_USER_MEM_SUPPORTED defined, and use png_create_read_struct_2() instead of png_create_read_struct():


png_structp png_ptr = png_create_read_struct_2
(PNG_LIBPNG_VER_STRING, (png_voidp)user_error_ptr,
user_error_fn, user_warning_fn, (png_voidp)
user_mem_ptr, user_malloc_fn, user_free_fn);

The error handling routines passed to png_create_read_struct() and the memory alloc/free routines passed to png_create_struct_2() are only necessary if you are not using the libpng supplied error handling and memory alloc/free functions.

When libpng encounters an error, it expects to longjmp back to your routine. Therefore, you will need to call setjmp and pass your png_jmpbuf(png_ptr). If you read the file from different routines, you will need to update the longjmp buffer every time you enter a new routine that will call a png_*() function.

See your documentation of setjmp/longjmp for your compiler for more information on setjmp/longjmp. See the discussion on libpng error handling in the Customizing Libpng section below for more information on the libpng error handling. If an error occurs, and libpng longjmp's back to your setjmp, you will want to call png_destroy_read_struct() to free any memory.


if (setjmp(png_jmpbuf(png_ptr)))
{
png_destroy_read_struct(&png_ptr, &info_ptr, &end_info);
fclose(fp);
return ERROR;
}

Pass NULL instead of &end_info if you didn't create an end_info structure.

If you would rather avoid the complexity of setjmp/longjmp issues, you can compile libpng with PNG_NO_SETJMP, in which case errors will result in a call to PNG_ABORT() which defaults to abort().

You can #define PNG_ABORT() to a function that does something more useful than abort(), as long as your function does not return.

Now you need to set up the input code. The default for libpng is to use the C function fread(). If you use this, you will need to pass a valid FILE * in the function png_init_io(). Be sure that the file is opened in binary mode. If you wish to handle reading data in another way, you need not call the png_init_io() function, but you must then implement the libpng I/O methods discussed in the Customizing Libpng section below.


png_init_io(png_ptr, fp);

If you had previously opened the file and read any of the signature from the beginning in order to see if this was a PNG file, you need to let libpng know that there are some bytes missing from the start of the file.


png_set_sig_bytes(png_ptr, number);

You can change the zlib compression buffer size to be used while reading compressed data with


png_set_compression_buffer_size(png_ptr, buffer_size);

where the default size is 8192 bytes. Note that the buffer size is changed immediately and the buffer is reallocated immediately, instead of setting a flag to be acted upon later.

If you want CRC errors to be handled in a different manner than the default, use


png_set_crc_action(png_ptr, crit_action, ancil_action);

The values for png_set_crc_action() say how libpng is to handle CRC errors in ancillary and critical chunks, and whether to use the data contained therein. Starting with libpng-1.6.26, this also governs how an ADLER32 error is handled while reading the IDAT chunk. Note that it is impossible to "discard" data in a critical chunk.

Choices for (int) crit_action are
PNG_CRC_DEFAULT 0 error/quit
PNG_CRC_ERROR_QUIT 1 error/quit
PNG_CRC_WARN_USE 3 warn/use data
PNG_CRC_QUIET_USE 4 quiet/use data
PNG_CRC_NO_CHANGE 5 use the current value

Choices for (int) ancil_action are
PNG_CRC_DEFAULT 0 error/quit
PNG_CRC_ERROR_QUIT 1 error/quit
PNG_CRC_WARN_DISCARD 2 warn/discard data
PNG_CRC_WARN_USE 3 warn/use data
PNG_CRC_QUIET_USE 4 quiet/use data
PNG_CRC_NO_CHANGE 5 use the current value

When the setting for crit_action is PNG_CRC_QUIET_USE, the CRC and ADLER32 checksums are not only ignored, but they are not evaluated.

Setting up callback code

This is a discussion of how to set up the callback code that libpng uses to read data. If you want to use the default C I/O functions, then you will need to call `png_init_io()` and pass it a valid file pointer. If you want to use your own I/O functions, then you will not call `png_init_io()`, but will instead implement a read callback function and pass it to libpng using `png_set_read_fn()`. The read callback function has the following signature:


void YourReadCallback(png_structp png_ptr, png_bytep data,
png_size_t length);

Your callback function should read 'length' bytes from your data source into the buffer 'data'. If an error occurs, or if you run out of data, your callback should call `png_error(png_ptr, "your message")`.

In addition, you must also supply a pointer to your data source in the call to `png_set_read_fn()`. This pointer will be passed to your read callback function each time it is called. This is useful if you are reading from something other than a standard C FILE * file pointer, such as a memory buffer or a network stream.


png_set_read_fn(png_ptr, user_data, YourReadCallback);

The 'user_data' pointer is passed as the first argument to your read callback function. If you are using standard C I/O, you can pass `fp` (your FILE * pointer) as the user_data. Libpng will then pass this pointer to your read callback function.

Note that if you use `png_set_read_fn()`, libpng will no longer call `png_init_io()`. You must choose one or the other.

You also need to call `png_set_error_fn()` to tell libpng what functions to call when an error or warning occurs. You should pass pointers to your error handling functions, and a pointer to your data structure. The error handling functions have the following signatures:


void YourErrorFunction(png_structp png_ptr, png_const_charp error_message);


void YourWarningFunction(png_structp png_ptr, png_const_charp warning_message);


png_set_error_fn(png_ptr, user_error_ptr, YourErrorFunction,
YourWarningFunction);

The user_error_ptr is passed as the first argument to your error and warning functions. It can be NULL if you don't need it.

If you want libpng to use the default error handling, you can pass NULL for the error and warning function pointers. However, you should still call `png_set_error_fn()` to pass in your user_error_ptr, even if you are using the default error handlers.

If you are using the default error handlers, and an error occurs, libpng will longjmp back to the setjmp location you specified. If you are using your own error handlers, then libpng will call your error handler, and it is up to your error handler to decide what to do. It can call `png_longjmp(png_ptr, 1)` to jump back to the setjmp location, or it can call `abort()`, or do something else.

If libpng is compiled with PNG_NO_SETJMP, then errors will cause a call to PNG_ABORT(), which by default calls abort().

If you wish to override the default memory allocation routines used by libpng, you can use `png_set_mem_fn()`:


png_set_mem_fn(png_ptr, user_mem_ptr, YourMallocFunction,
YourFreeFunction);

YourMallocFunction should have the signature:


png_voidp YourMallocFunction(png_structp png_ptr, png_size_t size);

YourFreeFunction should have the signature:


void YourFreeFunction(png_structp png_ptr, png_voidp ptr);

The user_mem_ptr is passed to your malloc and free functions. It can be NULL if you don't need it.

If you are not using the default memory allocation routines, then you must call `png_set_mem_fn()` before calling any other libpng functions that allocate memory.

If you want to change the default zlib compression buffer size, you can use `png_set_compression_buffer_size()`:


png_set_compression_buffer_size(png_ptr, size);

This function changes the buffer size immediately. The default size is 8192 bytes.

You can change the action libpng takes on CRC errors using `png_set_crc_action()`:


png_set_crc_action(png_ptr, crit_action, ancil_action);

See the description of `png_set_crc_action()` in the setup section above for more details on the possible values for crit_action and ancil_action.

Finally, you need to read the PNG file info header using `png_read_info()`:


png_read_info(png_ptr, info_ptr);

This function reads the PNG file signature and all of the header chunks, including the IHDR, PLTE, and any ancillary chunks before the IDAT chunk. It also determines the size of the image and checks for color type and bit depth.

The info_ptr structure is filled with information about the PNG file, including the image width, height, bit depth, color type, and interlace method.

If you want to read the PNG file progressively, you will need to call `png_start_read_image()` after `png_read_info()` and before you start reading the actual pixel data.


png_start_read_image(png_ptr);

This function prepares libpng for reading the image data. It does not actually read any data.

Reading the file

After calling `png_read_info()` and `png_start_read_image()`, you can begin reading the image data. You will need to allocate memory for the image data. The size of the memory needed is determined by the image width, height, and bit depth, which are available in the info_ptr structure.


png_bytep *row_pointers = (png_bytep*) malloc(sizeof(png_bytep) *
info_ptr->height);
for (y=0; y<info_ptr->height; y++)
{
row_pointers[y] = (png_bytep) malloc(png_get_rowbytes(png_ptr, info_ptr));
}

Then, you can read the image data row by row using `png_read_row()`:


for (y=0; y<info_ptr->height; y++)
{
png_read_row(png_ptr, row_pointers[y], NULL);
}

The third argument to `png_read_row()` is for progressive display, which is not covered in this section.

Once you have read all the rows, you need to call `png_read_end()`:


png_read_end(png_ptr, end_info);

This function reads any remaining chunks until the IEND chunk. If you have allocated an end_info structure, it will be filled with information about the remaining ancillary chunks.

Finally, you should free the memory allocated for the row pointers, and then destroy the libpng structures:


for (y=0; y<info_ptr->height; y++)
{
free(row_pointers[y]);
}


free(row_pointers);


png_destroy_read_struct(&png_ptr, &info_ptr, &end_info);

This will free all the memory allocated by libpng.

Progressive reading

Progressive reading is similar to sequential reading, but instead of reading the image row by row, you read it scanline by scanline. This allows you to display the image as it is being read, which can be useful for slow network connections.

To read a PNG file progressively, you need to call `png_set_read_fn()` with your own read callback function. You also need to call `png_start_read_image()` after `png_read_info()`.

Then, instead of calling `png_read_row()`, you call `png_read_row()` with a NULL second argument:


png_read_row(png_ptr, NULL, row_pointers[y]);

This will read a scanline of data into the buffer pointed to by the third argument. You can then process the scanline as needed.

You will need to call `png_read_end()` after you have read all the scanlines.

Finally, you should destroy the libpng structures as described above.

Integer limits

Libpng uses unsigned integers for pixel component values. The PNG specification states that pixel components are between 0 and (2^bpp)-1, where bpp is the number of bits per pixel component. This implies that for 8-bit PNGs, values range from 0 to 255. For 16-bit PNGs, values range from 0 to 65535.

Libpng has internal checks for these limits. For example, if you have an 8-bit PNG, and libpng encounters a pixel component value greater than 255, it will report an error. Similarly, for 16-bit PNGs, it will report an error if a value greater than 65535 is encountered.

These checks are performed regardless of whether the PNG file is being read or written. They are intended to help prevent the use of malformed PNG files.

Other reading functions

There are several other functions that can be used when reading PNG files:

  • `png_get_image_width(png_ptr, info_ptr)`: Returns the width of the image.

  • `png_get_image_height(png_ptr, info_ptr)`: Returns the height of the image.

  • `png_get_bit_depth(png_ptr, info_ptr)`: Returns the bit depth of the image.

  • `png_get_color_type(png_ptr, info_ptr)`: Returns the color type of the image.

  • `png_get_interlace_type(png_ptr, info_ptr)`: Returns the interlace type of the image.

  • `png_get_channels(png_ptr, info_ptr)`: Returns the number of channels in the image (e.g., 1 for grayscale, 3 for RGB, 4 for RGBA).

  • `png_get_rowbytes(png_ptr, info_ptr)`: Returns the number of bytes in a row of the image. This takes into account the bit depth and number of channels.

  • `png_set_palette_to_rgb(png_ptr)`: Converts a paletted image to RGB. This is often necessary if you want to process the image data as RGB.

  • `png_set_strip_alpha(png_ptr)`: Strips the alpha channel from an image. This is useful if you don't need the alpha channel and want to reduce the amount of memory used.

  • `png_set_background(png_ptr, background_color, gamma)`: Applies a background color to transparent images. This is useful if you want to display a transparent PNG on a solid background.

  • `png_set_gamma(png_ptr, display_gamma, screen_gamma)`: Applies gamma correction to the image. This is useful if you want to ensure that the image is displayed correctly on different screens.

  • `png_read_chunk(png_ptr, chunk_name)`: Reads a specific ancillary chunk from the PNG file. This can be useful if you want to access custom chunks or other non-critical information in the PNG file.

  • `png_get_current_row_number(png_ptr)`: Returns the number of the current row being read. This is useful for tracking progress during progressive reading.

Gestion des morceaux inconnus

Maintenant, vous pouvez définir la manière dont la bibliothèque traite les morceaux inconnus dans le flux PNG d'entrée. Les morceaux connus et inconnus seront lus. Le comportement normal est que les morceaux connus sont analysés dans des informations dans divers membres de 'info_ptr', tandis que les morceaux inconnus sont ignorés. Ce comportement peut être inefficace si votre application n'utilisera jamais certains types de morceaux connus. Pour changer cela, vous pouvez appeler :


png_set_keep_unknown_chunks(png_ptr, keep,
chunk_list, num_chunks);


keep - 0 : gestion par défaut des morceaux inconnus
1 : ignorer ; ne pas conserver
2 : conserver uniquement si sûr à copier
3 : conserver même si non sûr à copier


Vous pouvez utiliser ces définitions :
PNG_HANDLE_CHUNK_AS_DEFAULT 0
PNG_HANDLE_CHUNK_NEVER 1
PNG_HANDLE_CHUNK_IF_SAFE 2
PNG_HANDLE_CHUNK_ALWAYS 3


chunk_list - liste des morceaux affectés (une chaîne d'octets,
cinq octets par morceau, NULL ou ' ' si
num_chunks est positif ; ignoré si
numchunks <= 0).


num_chunks - nombre de morceaux affectés ; si 0, tous
les morceaux inconnus sont affectés. S'il est positif,
seuls les morceaux de la liste sont affectés,
et s'il est négatif, tous les morceaux inconnus et
tous les morceaux connus sauf IHDR,
PLTE, tRNS, IDAT et IEND sont
affectés.

Les morceaux inconnus déclarés de cette manière seront sauvegardés sous forme de données brutes dans une liste de structures png_unknown_chunk. Si un morceau normalement connu de libpng est nommé dans la liste, il sera traité comme inconnu, conformément à la directive "keep". Si un morceau est nommé dans des instances successives de png_set_keep_unknown_chunks(), la dernière instance aura la priorité. Les morceaux IHDR et IEND ne doivent pas être nommés dans chunk_list ; s'ils le sont, libpng les traitera normalement de toute façon. Si vous savez que votre application n'utilisera jamais certains morceaux particuliers, utilisez PNG_HANDLE_CHUNK_NEVER (ou 1) comme démontré ci-dessous.

115, 80, 76, 84, (png_byte) ' ', /* sPLT */

};
#endif


...

*/

Limites utilisateur

La spécification PNG autorise la largeur et la hauteur d'une image à être aussi grandes que 2^(31-1 (0x7fffffff), soit environ 2,147 milliards de lignes et de colonnes. Par mesure de sécurité, libpng impose une limite par défaut de 1 million de lignes et de colonnes. Les images plus grandes seront rejetées immédiatement avec un appel à png_error(). Si vous souhaitez modifier ces limites, vous pouvez utiliser


png_set_user_limits(png_ptr, width_max, height_max);

pour définir vos propres limites (libpng peut quand même rejeter certaines images très larges en raison de potentielles conditions de débordement de tampon).

Vous devriez placer cette instruction après avoir créé la structure PNG et avant d'appeler png_read_info(), png_read_png(), ou png_process_data().

Lors de la rédaction d'un flux de données PNG, placez cette instruction avant d'appeler png_write_info() ou png_write_png().

Si vous avez besoin de récupérer les limites appliquées, utilisez


width_max = png_get_user_width_max(png_ptr);
height_max = png_get_user_height_max(png_ptr);

La spécification PNG ne fixe aucune limite au nombre de morceaux auxiliaires autorisés dans un flux de données PNG. Par défaut, libpng impose une limite totale de 1000 morceaux sPLT, tEXt, iTXt, zTXt et inconnus à stocker. Si vous avez configuré à la fois info_ptr et end_info_ptr, la limite s'applique séparément à chacun. Vous pouvez modifier la limite sur le nombre total de tels morceaux qui seront stockés, avec


png_set_chunk_cache_max(png_ptr, user_chunk_cache_max);

où 0x7fffffffL signifie illimité. Vous pouvez récupérer cette limite avec


chunk_cache_max = png_get_chunk_cache_max(png_ptr);

Libpng impose une limite de 8 Mégaoctets (8 000 000 octets) à la quantité de mémoire que tout morceau autre que IDAT peut occuper, à l'origine ou après décompression (avant libpng-1.6.32, la limite ne s'appliquait qu'aux morceaux compressés après décompression). Vous pouvez modifier cette limite avec


png_set_chunk_malloc_max(png_ptr, user_chunk_malloc_max);

et vous pouvez récupérer la limite avec


chunk_malloc_max = png_get_chunk_malloc_max(png_ptr);

Tout morceau qui dépasserait l'une de ces limites sera ignoré.

Informations sur votre système

Si vous avez l'intention d'afficher le PNG ou de l'incorporer dans d'autres données d'image, vous devez fournir à libpng des informations sur votre écran ou votre surface de dessin afin que libpng puisse convertir les valeurs de l'image pour qu'elles correspondent à l'affichage.

À partir de libpng-1.5.4, ces informations peuvent être définies avant la lecture de l'en-tête du fichier PNG. Dans les versions antérieures, png_set_gamma() existait mais se comportait incorrectement s'il était appelé avant la lecture de l'en-tête du fichier PNG et png_set_alpha_mode() n'existait pas.

Si vous avez besoin de prendre en charge les versions antérieures à libpng-1.5.4, testez le numéro de version comme illustré ci-dessous en utilisant "PNG_LIBPNG_VER >= 10504" et suivez les procédures décrites dans la page manuelle appropriée.

Vous donnez à libpng le codage attendu par votre système, exprimé sous forme de valeur 'gamma'. Vous pouvez également spécifier un codage par défaut pour le fichier PNG au cas où les informations requises seraient manquantes dans le fichier. Par défaut, libpng suppose que les données PNG correspondent à votre système, pour conserver ce défaut, appelez :


png_set_gamma(png_ptr, screen_gamma, output_gamma);

ou vous pouvez utiliser l'équivalent en virgule fixe :


png_set_gamma_fixed(png_ptr, PNG_FP_1*screen_gamma,
PNG_FP_1*output_gamma);

Si vous ne connaissez pas le gamma de votre système, il est probablement de 2.2 - une bonne approximation de la norme CEI pour les systèmes d'affichage (sRGB). Si les images sont trop contrastées ou délavées, vous vous êtes trompé de valeur - consultez la documentation de votre système !

De nombreux systèmes permettent de modifier le gamma du système via une table de correspondance dans le pilote d'affichage, quelques systèmes, y compris les anciens Mac, modifient la réponse par défaut. Depuis la version 1.5.4, trois valeurs spéciales sont disponibles.

gérer les situations courantes :


PNG_DEFAULT_sRGB : Indique que le système est conforme à la norme
IEC 61966-2-1. Cela correspond à la quasi-totalité des
systèmes.
PNG_GAMMA_MAC_18 : Indique que le système est un ancien
système Apple Macintosh (antérieur à Mac OS 10.6) avec
les paramètres par défaut.
PNG_GAMMA_LINEAR : La valeur fixe de 1.0, indiquant que le
système attend des données sans encodage gamma.

Vous utiliseriez la valeur linéaire (non encodée) si vous avez besoin de traiter davantage les valeurs de pixels, car cela évite d'avoir à décoder et ré-encoder chaque valeur de composant lorsque des opérations arithmétiques sont effectuées. De nombreux logiciels graphiques utilisent des valeurs linéaires pour cette raison, souvent avec des valeurs de composants de plus haute précision pour préserver la précision globale.

La valeur `output_gamma` exprime comment décoder les valeurs de sortie, et non comment elles sont encodées. Les valeurs utilisées correspondent aux nombres normaux utilisés pour décrire le gamma global d'un système d'affichage d'ordinateur ; par exemple, 2.2 pour un système conforme sRGB. Les valeurs sont mises à l'échelle par 100000 dans la version `_fixed` de l'API (donc 220000 pour sRGB).

L'inverse de la valeur est toujours utilisé pour fournir une valeur par défaut pour l'encodage du fichier PNG s'il n'a pas de chunk gAMA et si `png_set_gamma()` n'a pas été appelé pour remplacer les informations de gamma PNG.

Lorsque le mode `ALPHA_OPTIMIZED` est sélectionné, le gamma de sortie est utilisé pour encoder les pixels opaques ; cependant, les pixels avec des valeurs alpha inférieures ne sont pas encodés, quelle que soit la valeur du gamma de sortie.

Lorsque le traitement standard Porter Duff est demandé avec le mode 1, l'encodage de sortie est défini sur linéaire et la valeur `output_gamma` n'est pertinente que comme valeur par défaut pour les données d'entrée qui n'ont pas d'informations gamma. L'encodage de sortie linéaire sera remplacé si `png_set_gamma()` est appelé – les résultats peuvent être très inattendus !

Les nombres suivants sont dérivés de la norme sRGB et de la recherche qui la sous-tend. sRGB est défini comme étant approximé par une valeur de chunk gAMA PNG de 0.45455 (1/2.2) pour PNG. La valeur inclut implicitement toute correction de visualisation nécessaire pour tenir compte des différences dans l'environnement couleur de la scène d'origine et l'environnement d'affichage prévu ; la valeur exprime comment *décoder* l'image pour l'affichage, et non comment les données d'origine ont été *encodées*.

sRGB fournit un point de référence pour la norme PNG en définissant un environnement de visualisation. sRGB lui-même, et les normes TV antérieures, utilisent en fait une transformation plus complexe (une partie linéaire puis une loi de puissance gamma 2.4) que PNG ne peut exprimer. (PNG est limité aux lois de puissance simples.) En indiquant qu'une image destinée à être affichée directement sur un système conforme sRGB doit être stockée avec une valeur de chunk gAMA de 45455 (11.3.3.2 et 11.3.3.5 de la spécification ISO PNG), la spécification PNG permet de dériver des valeurs pour d'autres systèmes et environnements d'affichage.

La valeur Mac est déduite de sRGB sur la base de l'hypothèse que la correction de visualisation supplémentaire réelle utilisée dans les anciens systèmes d'affichage Mac était implémentée comme une table de correspondance de puissance 1.45.

Tout système où une table de correspondance programmable est utilisée ou où le comportement des caractéristiques du périphérique d'affichage final peut être modifié nécessite un code spécifique au système pour obtenir la caractéristique actuelle. Cependant, cela peut être difficile et la plupart des corrections gamma PNG ne nécessitent qu'une valeur approximative.

Par défaut, si `png_set_alpha_mode()` n'est pas appelé, libpng suppose que toutes les valeurs sont des valeurs linéaires non encodées et que le périphérique de sortie a également une caractéristique linéaire. Ceci est rarement correct - il est invariablement préférable d'appeler `png_set_alpha_mode()` avec `PNG_DEFAULT_sRGB` plutôt que de se fier à la valeur par défaut si vous ne savez pas quelle est la bonne réponse !

La valeur spéciale `PNG_GAMMA_MAC_18` indique un ancien système Mac (antérieur à Mac OS 10.6) qui utilisait une table de correction pour implémenter un gamma quelque peu plus bas sur un système sRGB par ailleurs.

Ces deux valeurs sont réservées (pas des valeurs gamma simples) afin de permettre une correction plus précise en interne à l'avenir.

NOTE : les valeurs peuvent être passées aux API à virgule fixe ou flottante, mais l'API à virgule flottante acceptera également des valeurs à virgule flottante.

La deuxième chose à propos de laquelle vous pourriez avoir besoin d'informer libpng est la manière dont votre système gère les informations de canal alpha. Certains fichiers PNG, mais pas tous, contiennent un canal alpha. Pour afficher correctement ces fichiers, vous devez composer les données sur un fond approprié, comme décrit dans la spécification PNG.

Libpng ne prend en charge que la composition sur une couleur unique (en utilisant `png_set_background` ; voir ci-dessous). Sinon, vous devez effectuer la composition vous-même et, dans ce cas, vous devrez peut-être appeler `png_set_alpha_mode` :


#if PNG_LIBPNG_VER >= 10504
png_set_alpha_mode(png_ptr, mode, screen_gamma);
#else
png_set_gamma(png_ptr, screen_gamma, 1.0/screen_gamma);
#endif

La valeur `screen_gamma` est la même que l'argument de `png_set_gamma` ; cependant, son effet sur la sortie dépend du mode. `png_set_alpha_mode()` définit le gamma de fichier par défaut sur `1/screen_gamma`, vous n'avez donc normalement pas besoin d'appeler `png_set_gamma`. Si vous avez besoin de valeurs par défaut différentes, appelez `png_set_gamma()` avant `png_set_alpha_mode()` – si vous l'appelez après, cela remplacera les paramètres faits par `png_set_alpha_mode()`.

Le mode est le suivant :


PNG_ALPHA_PNG : Les données sont encodées conformément à la spécification PNG. Les composantes rouge, verte et bleue, ou grise, sont des valeurs couleur encodées en gamma et ne sont pas prémultipliées par la valeur alpha. La valeur alpha est une mesure linéaire de la contribution du pixel au pixel de sortie final correspondant.

Vous devriez normalement utiliser ce format si vous avez l'intention d'effectuer une correction de couleur sur les valeurs de couleur ; la plupart, peut-être tous, les logiciels de correction de couleur n'ont pas de gestion du canal alpha et, de toute façon, les mathématiques pour gérer les valeurs de composant prémultipliées sont inutilement complexes.

Avant de procéder à des opérations arithmétiques sur les valeurs de composants, vous devez supprimer l'encodage gamma et multiplier par le canal alpha. Voir la spécification PNG pour plus de détails. Il est important de noter que lorsqu'une image avec un canal alpha est mise à l'échelle, des valeurs de composant linéaires et prémultipliées doivent être utilisées !

Les modes restants supposent que vous n'avez pas besoin d'effectuer d'autres corrections de couleur ou que, si vous en faites, votre logiciel de correction de couleur connaît tout sur l'alpha (ce qui est peu probable !). Ils 'associent' l'alpha aux informations de couleur en stockant des valeurs de canaux de couleur qui ont été mises à l'échelle par l'alpha. L'avantage est que les canaux de couleur peuvent être rééchantillonnés (l'image peut être mise à l'échelle) sous cette forme. L'inconvénient est que la pratique normale consiste à stocker des valeurs linéaires, et non encodées (en gamma), et cela nécessite des canaux 16 bits pour les images fixes plutôt que les canaux 8 bits qui sont à peine suffisants si l'encodage gamma est utilisé. De plus, tous les pixels non transparents, y compris ceux complètement opaques, doivent être encodés en gamma pour produire l'image finale. Ce sont les modes 'STANDARD', 'ASSOCIÉ' ou 'PRÉMULTIPLIÉ' décrits ci-dessous (les deux derniers étant les deux noms courants pour les canaux de couleur alpha associés). Notez que les fichiers PNG contiennent toujours des canaux de couleur non associés ; `png_set_alpha_mode()` avec l'un des modes amène le décodeur à convertir les pixels en une forme associée avant de les retourner à votre application.

Comme il n'est pas nécessaire d'effectuer des opérations arithmétiques sur les valeurs de couleur opaques tant qu'elles ne sont pas rééchantillonnées et qu'elles se trouvent dans l'espace couleur final, il est possible d'optimiser la gestion de l'alpha en stockant les pixels opaques dans le format PNG (ajusté pour l'espace couleur de sortie) tout en stockant les pixels partiellement opaques dans le format linéaire standard. La précision requise pour la composition alpha standard est relativement faible, car les pixels sont isolés, donc généralement la perte de précision lors du stockage de valeurs linéaires 8 bits est acceptable. (Ce n'est pas vrai si le canal alpha est utilisé pour simuler la transparence sur de grandes zones - utilisez 16 bits ou le mode PNG dans ce cas !) C'est le mode 'OPTIMISÉ'. Pour ce mode, un pixel est traité comme opaque uniquement si la valeur alpha est égale à la valeur maximale.


PNG_ALPHA_STANDARD : Les données produites par libpng sont encodées de la manière standard supposée par la plupart des logiciels graphiques correctement écrits. L'encodage gamma sera supprimé par libpng et les valeurs de composant linéaires seront prémultipliées par le canal alpha.

Avec ce format, l'image finale doit être ré-encodée pour correspondre au gamma d'affichage avant d'être affichée. Si votre système ne le fait pas, mais semble tout de même effectuer des opérations arithmétiques sur les pixels sans les décoder, il est défectueux – examinez les modes ci-dessous.

Avec `PNG_ALPHA_STANDARD`, libpng produit toujours des valeurs de composant linéaires, quel que soit le `screen_gamma` que vous fournissez. La valeur `screen_gamma` est cependant utilisée comme valeur par défaut pour le gamma de fichier si le fichier PNG n'a pas d'informations gamma.

Si vous appelez `png_set_gamma()` après `png_set_alpha_mode()`, vous remplacerez l'encodage linéaire. Au lieu de cela, les valeurs de pixels prémultipliées seront encodées en gamma, mais le canal alpha restera linéaire. Cela peut correspondre aux exigences de certains logiciels défectueux, mais c'est peu probable.

Bien que les données linéaires 8 bits soient souvent utilisées, elles n'ont pas une précision suffisante pour toute image avec une plage dynamique raisonnable. Pour éviter les problèmes, et si votre logiciel le prend en charge, utilisez `png_set_expand_16()` pour forcer tous les composants à 16 bits.


PNG_ALPHA_OPTIMIZED : Ce mode est identique à `PNG_ALPHA_STANDARD`, sauf que les pixels complètement opaques sont encodés en gamma conformément à la valeur `screen_gamma`. Les pixels avec un alpha inférieur à 1.0 auront toujours des composants linéaires.

Utilisez ce format si vous avez le contrôle sur votre logiciel de composition et que vous n'effectuez donc pas d'autres opérations arithmétiques (telles que la mise à l'échelle) sur les données que vous obtenez de libpng. Votre logiciel de composition peut simplement copier les pixels opaques vers la sortie, mais dispose toujours de valeurs linéaires pour les pixels non opaques.

Dans la composition normale, où le canal alpha encode une couverture de pixel partielle (par opposition à la translucidité de large zone), les imprécisions de la représentation 8 bits des pixels non opaques sont sans importance.

Vous pouvez également essayer ce format si votre logiciel est défectueux ; cela pourrait avoir un meilleur rendu.


PNG_ALPHA_BROKEN : C'est `PNG_ALPHA_STANDARD` ; cependant, toutes les valeurs de composant, y compris le canal alpha, sont encodées en gamma. C'est défectueux car, en pratique, aucune implémentation qui utilise ce choix ne défait correctement l'encodage avant de gérer la composition alpha. Utilisez ce choix uniquement si d'autres erreurs graves dans le logiciel ou le matériel que vous utilisez le rendent impératif. Dans la plupart des cas de logiciels ou de matériel défectueux, le bogue dans l'affichage final se manifeste par un halo subtil autour des parties composées de l'image. Vous ne le percevrez peut-être même pas comme un halo ; la partie composée de l'image peut simplement apparaître séparée de l'arrière-plan, comme si elle avait été découpée dans du papier et collée ensuite.

Si vous n'avez pas à traiter avec des bogues dans les logiciels ou le matériel, ou si vous pouvez les corriger, il existe trois façons recommandées d'utiliser `png_set_alph

C'est une approche inspirée de Jim Blinn, quelque peu plus réaliste. Autres cas

Si ni l'encodage PNG ni l'encodage linéaire standard ne vous conviennent en raison du logiciel ou du matériel que vous utilisez, alors vous avez un gros problème. Cette option réduira également les halos, mais il y aura de légers halos sombres autour des parties opaques de l'image où le fond est clair. Allocating and reading the row pointers

The png_set_rows() function is used to tell libpng where the row data is stored. This is only used if the application has allocated the data and wants libpng to use it.

The structure of the call is:


png_set_rows(png_ptr, info_ptr, row_pointers);


png_ptr - pointer to a png_struct structure
info_ptr - pointer to a png_info structure
row_pointers - pointer to an array of pointers to
png_byte (row_pointers[i] is a pointer to the
first byte of row i)

Note that png_set_rows() takes a pointer to the array of row pointers. This is because libpng may need to reallocate the array of row pointers if it is doing interlaced reading and the number of rows has changed. For this reason the array of row pointers must be allocated with png_malloc, and the pointer to the array must be passed into the call.

The array of row pointers must be allocated with png_malloc().


png_bytepp row_pointers;


/* Guard against integer overflow */
if (height > PNG_SIZE_MAX / sizeof(png_bytep))
png_error(png_ptr, "Row pointers would be too large");


row_pointers = (png_bytepp)png_malloc(png_ptr,
height * sizeof(png_bytep));

libpng must also know the size of the image, and the width of each row in bytes. This information is read from the IHDR chunk, and can be retrieved using png_get_IHDR() (see below). The size of the image, in bytes, is width * height * channels. The size of a row is png_get_rowbytes(). libpng uses this information to determine how much memory to allocate for each row.

You can choose to allocate each row separately, or you can allocate a single large buffer and have the row pointers point into it. The second method is generally more efficient, but requires careful handling of the buffer size.

The maximum size of an image is limited by PNG_SIZE_MAX. However, this is usually much larger than can be handled by the system's memory manager. Therefore, it's good practice to check the image size before attempting to allocate it.


/* Guard against integer overflow */
if (height > PNG_SIZE_MAX / pixel_size)
png_error(png_ptr,
"Image is too wide to process in memory");


row_pointers = png_malloc(png_ptr,
height*(sizeof (png_bytep)));


for (int i = 0; i < height, i++)
row_pointers[i] = NULL; /* security precaution */


for (int i = 0; i < height, i++)
row_pointers[i] = png_malloc(png_ptr,
width*pixel_size);


png_set_rows(png_ptr, info_ptr, &row_pointers);

Alternatively you could allocate your image in one big block and define row_pointers[i] to point into the proper places in your block, but first be sure that your platform is able to allocate such a large buffer:


/* Guard against integer overflow */
if (height > PNG_SIZE_MAX/(width*pixel_size))
png_error(png_ptr, "image_data buffer would be too large");


png_bytep buffer = png_malloc(png_ptr,
height*width*pixel_size);


for (int i = 0; i < height, i++)
row_pointers[i] = buffer + i*width*pixel_size;


png_set_rows(png_ptr, info_ptr, &row_pointers);

If you use png_set_rows(), the application is responsible for freeing row_pointers (and row_pointers[i], if they were separately allocated).

If you don't allocate row_pointers ahead of time, png_read_png() will do it, and it'll be free'ed by libpng when you call png_destroy_*().

L'interface de lecture de bas niveau

Si vous optez pour la voie de bas niveau, vous êtes maintenant prêt à lire toutes les informations du fichier jusqu'aux données d'image réelles. Vous le faites avec un appel à png_read_info().


png_read_info(png_ptr, info_ptr);

Cela traitera tous les blocs jusqu'aux données d'image, mais sans les inclure.

Cela copie également certaines données du fichier PNG dans la structure de décodage pour une utilisation dans des transformations ultérieures. Les informations importantes copiées sont :

1) Le gamma du fichier PNG provenant du bloc gAMA. Cela écrase la valeur par défaut fournie par un appel antérieur à png_set_gamma ou png_set_alpha_mode().

2) Avant libpng-1.5.4, la couleur de fond d'un bloc bKGd. Cela endommage les informations fournies par un appel antérieur à png_set_background(), entraînant un comportement inattendu. Libpng-1.5.4 ne fait plus cela.

3) Le nombre de bits significatifs dans la valeur de chaque composante. Libpng utilise cela pour optimiser la gestion du gamma en réduisant la taille des tables de correspondance internes.

4) Les informations de couleur transparente d'un bloc tRNS. Cela peut être modifié par un appel ultérieur à png_set_tRNS().

Un mot rapide sur text_ptr et num_text. PNG stocke les commentaires par paires mot-clé/texte, une paire par bloc, sans limite sur le nombre de blocs de texte, et avec une limite de taille de 2^31 octets. Bien qu'il existe des mots-clés suggérés, il n'est pas obligatoire de restreindre leur utilisation à ces chaînes. Il est fortement suggéré que les mots-clés et les textes soient compréhensibles par les humains (c'est le but), donc n'utilisez pas d'abréviations. Les symboles non imprimables ne sont pas autorisés. Voir la spécification PNG pour plus de détails. Il n'est pas non plus obligatoire d'avoir du texte après le mot-clé.

Les mots-clés doivent être limités à 79 caractères Latin-1 sans espaces de début ou de fin, mais des espaces non consécutifs sont autorisés à l'intérieur du mot-clé. Il est possible d'avoir le même mot-clé un nombre quelconque de fois. text_ptr est un tableau de structures png_text, chacune contenant un pointeur vers une chaîne de langue, un pointeur vers un mot-clé et un pointeur vers une chaîne de texte. La chaîne de texte, le code de langue et le mot-clé traduit peuvent être des chaînes vides ou des pointeurs NULL. Les paires mot-clé/texte sont placées dans le tableau dans l'ordre où elles sont reçues. Cependant, tout ou partie des blocs de texte peuvent se trouver après l'image. Ainsi, pour vous assurer d'avoir lu tous les blocs de texte, ne manipulez pas ces derniers avant d'avoir lu les informations après l'image. Cela sera mentionné à nouveau ci-dessous dans la discussion concernant png_read_end().

Transformations d'entrée

Après avoir lu les informations d'en-tête, vous pouvez configurer la bibliothèque pour gérer des transformations spéciales des données d'image. Les différentes manières de transformer les données seront décrites dans l'ordre où elles doivent se produire. Ceci est important, car certaines de ces transformations modifient le type de couleur et/ou la profondeur de bits des données, et d'autres ne fonctionnent que sur des types de couleur et des profondeurs de bits spécifiques.

Les transformations que vous demandez sont ignorées si elles n'ont aucun sens pour un format de données d'entrée particulier. Cependant, certaines transformations peuvent avoir un effet suite à une transformation précédente. Si vous spécifiez un ensemble contradictoire de transformations, par exemple, ajouter et supprimer le canal alpha, vous ne pouvez pas prédire le résultat final.

La couleur utilisée pour les valeurs de transparence doit être fournie dans le même format/profondeur que les données d'image actuelles. Elle est stockée dans le même format/profondeur que les données d'image dans un bloc tRNS, c'est donc ce que libpng attend pour ces données.

La couleur utilisée pour la valeur de fond dépend de l'argument need_expand décrit ci-dessous.

="Pp">Les données seront décodées dans les tampons de ligne fournis, compressées en octets, sauf si la bibliothèque a été configurée pour les transformer dans un autre format. Par exemple, les données RVB palettisées ou en niveaux de gris avec 4 bits/pixel seront retournées avec 2 pixels/octet, le pixel de gauche dans les bits de poids fort de l'octet, sauf si png_set_packing() est appelée. Les données RVB 8 bits seront stockées au format RVB RVB RVB, sauf si png_set_filler() ou png_set_add_alpha() est appelée pour insérer des octets de remplissage, soit avant, soit après chaque triplet RVB.

Les données RVB 16 bits seront retournées R G B R G B, avec l'octet le plus significatif de la valeur de couleur en premier, sauf si png_set_scale_16() est appelée pour la transformer en triplets RVB RVB réguliers, ou si png_set_filler() ou png_set_add_alpha() est appelée pour insérer deux octets de remplissage, soit avant, soit après chaque triplet RRGGBB. De même, les données en niveaux de gris 8 bits ou 16 bits peuvent être modifiées avec png_set_filler(), png_set_add_alpha(), png_set_strip_16() ou png_set_scale_16().

Le code suivant transforme les images en niveaux de gris de moins de 8 bits en 8 bits, convertit les images palettisées en RVB et ajoute un canal alpha complet s'il y a des informations de transparence dans un bloc tRNS. Depuis la version 1.2.9 de libpng, png_set_expand_gray_1_2_4_to_8() a été ajoutée. Elle étend la profondeur d'échantillonnage sans modifier tRNS en alpha.

Depuis la version 1.5.2 de libpng, png_set_expand_16() a été ajoutée. Elle se comporte comme png_set_expand() ; cependant, les canaux résultants ont 16 bits au lieu de 8. Utilisez-la lorsque les canaux de couleur ou de niveau de gris de sortie sont linéarisés pour éviter une perte d'exactitude assez sévère.

Dans les fichiers PNG, le canal alpha d'une image représente le niveau d'opacité. Si vous avez besoin que le canal alpha d'une image représente le niveau de transparence au lieu de l'opacité, vous pouvez inverser le canal alpha (ou les données du bloc tRNS) après sa lecture, de sorte que 0 soit entièrement opaque et 255 (dans les images 8 bits ou palettisées) ou 65535 (dans les images 16 bits) soit entièrement transparent, avec


png_set_invert_alpha(png_ptr);

Les fichiers PNG compressent les pixels de profondeurs de bits 1, 2 et 4 en octets aussi petits que possible, ce qui entraîne, par exemple, 8 pixels par octet pour les fichiers 1 bit. Ce code s'étend à 1 pixel par octet sans modifier les valeurs des pixels :


if (bit_depth < 8)
png_set_packing(png_ptr);

Les fichiers PNG ont des profondeurs de bits possibles de 1, 2, 4, 8 et 16. Tous les pixels stockés dans une image PNG ont été "mis à l'échelle" ou "décalés" vers la profondeur de bits possible supérieure (par exemple, de 5 bits/échantillon dans la plage [0,31] à 8 bits/échantillon dans la plage [0, 255]). Cependant, il est également possible de reconvertir les données de pixels PNG à la profondeur de bits d'origine de l'image. Cet appel réduit les pixels à la profondeur de bits d'origine :


png_color_8p sig_bit;


if (png_get_sBIT(png_ptr, info_ptr, &sig_bit))
png_set_shift(png_ptr, sig_bit);

Les fichiers PNG stockent les pixels 3 couleurs dans l'ordre rouge, vert, bleu. Ce code change le stockage des pixels en bleu, vert, rouge :


if (color_type == PNG_COLOR_TYPE_RGB ||
color_type == PNG_COLOR_TYPE_RGB_ALPHA)
png_set_bgr(png_ptr);

Les fichiers PNG stockent les pixels RVB compressés en 3 ou 6 octets. Ce code les étend en 4 ou 8 octets pour les systèmes de fenêtrage qui en ont besoin dans ce format :


if (color_type == PNG_COLOR_TYPE_RGB)
png_set_filler(png_ptr, filler, PNG_FILLER_BEFORE);

où "filler" est le nombre de 8 bits ou 16 bits à utiliser pour le remplissage, et l'emplacement est soit PNG_FILLER_BEFORE, soit PNG_FILLER_AFTER, selon que vous souhaitez le remplissage avant ou après le RVB. Lors du remplissage d'un pixel 8 bits, les 8 bits les moins significatifs du nombre sont utilisés, si un nombre 16 bits est fourni. Cette transformation n'affecte pas les images qui ont déjà des canaux alpha complets. Pour ajouter un canal alpha opaque, utilisez filler=0xffff et PNG_FILLER_AFTER, ce qui générera des pixels RGBA.

Notez que png_set_filler() ne modifie pas le type de couleur. Si vous souhaitez le faire, vous pouvez ajouter un véritable canal alpha avec


if (color_type == PNG_COLOR_TYPE_RGB ||
color_type == PNG_COLOR_TYPE_GRAY)
png_set_add_alpha(png_ptr, filler, PNG_FILLER_AFTER);

où "filler" contient la valeur alpha à attribuer à chaque pixel. La fonction png_set_add_alpha() a été ajoutée dans libpng-1.2.7.

Les valeurs par défaut proviennent du bloc `cHRM` du fichier PNG s'il est présent ; sinon, les valeurs par défaut correspondent à la recommandation ITU-R 709, et également à l'espace colorimétrique sRGB, comme recommandé dans le FAQ sur les couleurs de Charles Poynton, Copyright (c) 2006-11-28 Charles Poynton, dans la section 9 :

http://www.poynton.com/notes/colour_and_gamma/ColorFAQ.html#RTFToC9


Y = 0.2126 * R + 0.7152 * G + 0.0722 * B

Les versions précédentes de ce document, de 1998 à 2002, recommandaient une formule légèrement différente :


Y = 0.212671 * R + 0.715160 * G + 0.072169 * B

Libpng utilise une approximation entière :


Y = (6968 * R + 23434 * G + 2366 * B)/32768

Le calcul est effectué dans un espace colorimétrique linéaire, si la gamma de l'image peut être déterminée.

La fonction `png_set_background()` a déjà été décrite ; elle indique à libpng de composer les images avec alpha ou une transparence simple par rapport à la couleur de fond fournie. Pour la compatibilité avec les versions de libpng antérieures à libpng-1.5.4, il est recommandé d'appeler la fonction après la lecture de l'en-tête du fichier, même si vous ne souhaitez pas utiliser la couleur d'un bloc `bKGD` s'il en existe un.

Si le fichier PNG contient un bloc `bKGD` (`PNG_INFO_bKGD` valide), vous pouvez utiliser cette couleur, ou en fournir une autre plus adaptée à l'affichage actuel (par exemple, la couleur de fond d'une page Web). Vous devez indiquer à libpng comment la couleur est représentée, à la fois le format des valeurs des composantes de la couleur (le nombre de bits) et l'encodage gamma de la couleur. La fonction prend deux arguments, `background_gamma_mode` et `need_expand`, pour transmettre ces informations ; cependant, seules deux combinaisons sont susceptibles d'être utiles :

PNG_BACKGROUND_GAMMA_FILE, 1/*doit être développé*/, 1);

PNG_BACKGROUND_GAMMA_SCREEN, 0/*ne pas développer*/, 1);

Parce que vous connaissez maintenant le format du PNG, il est possible d'éviter la nécessité de choisir une sortie 8 bits ou 16 bits et de conserver les images de palette (les couleurs de la palette seront modifiées de manière appropriée et le bloc `tRNS` sera supprimé). Cependant, si vous faites cela, veillez à ne pas demander de transformations sans vérifier d'abord qu'elles s'appliquent !

Dans le premier appel, la couleur de fond a la profondeur de bits et le type de couleur d'origine du fichier PNG. Ainsi, pour les images de palette, la couleur est fournie sous forme d'index de palette et pour les images en niveaux de gris avec peu de bits, la couleur est une valeur réduite en bits dans `image_background->gray`.

Si vous n'avez pas appelé `png_set_gamma()` avant de lire l'en-tête du fichier, par exemple si votre code doit rester compatible avec les anciennes versions de libpng avant libpng-1.5.4, c'est ici qu'il faut l'appeler.

Ne l'appelez pas si vous avez appelé `png_set_alpha_mode()` ; cela endommagerait les paramètres mis en place par `png_set_alpha_mode()`. (Si `png_set_alpha_mode()` est supporté, vous pouvez certainement faire `png_set_gamma()` avant de lire l'en-tête PNG.)

Cette API définit inconditionnellement les valeurs de gamma de l'écran et du fichier, elle remplacera donc la valeur du fichier PNG sauf si elle est appelée avant le début de la lecture du fichier PNG. Pour cette raison, vous devez toujours l'appeler avec la valeur du fichier PNG lorsque vous l'appelez à cette position :


if (png_get_gAMA(png_ptr, info_ptr, &file_gamma))


png_set_gamma(png_ptr, screen_gamma, file_gamma);


else


png_set_gamma(png_ptr, screen_gamma, 0.45455);

Si vous avez besoin de réduire un fichier RVB à un fichier en palette, ou si un fichier en palette a plus d'entrées qu'il n'en tient sur votre écran, `png_set_quantize()` s'en chargera. Notez qu'il s'agit d'une simple quantification par correspondance qui trouve simplement la couleur la plus proche disponible. Cela devrait fonctionner assez bien avec des palettes optimisées, mais assez mal avec des cubes de couleurs linéaires. Les fichiers PNG décrivent le monochrome avec le noir comme zéro et le blanc comme un. Le code suivant inversera cela (le noir sera un et le blanc sera zéro) :


if (bit_depth == 1 && color_type == PNG_COLOR_TYPE_GRAY)


png_set_invert_mono(png_ptr);

Cette fonction peut également être utilisée pour inverser les images en niveaux de gris et en niveaux de gris avec alpha :


if (color_type == PNG_COLOR_TYPE_GRAY ||


color_type == PNG_COLOR_TYPE_GRAY_ALPHA)


png_set_invert_mono(png_ptr);

Les fichiers PNG stockent les pixels 16 bits en ordre des octets réseau (big-endian, c'est-à-dire les bits les plus significatifs d'abord). Ce code change le stockage dans l'autre sens (little-endian, c'est-à-dire les bits les moins significatifs d'abord, la manière dont les PC les stockent) :


if (bit_depth == 16)


png_set_swap(png_ptr);

Si vous utilisez des images avec pixels compactés (1, 2 ou 4 bits/pixel), et que vous devez changer l'ordre dans lequel les pixels sont compactés en octets, vous pouvez utiliser :


if (bit_depth < 8)


png_set_packswap(png_ptr);

Enfin, vous pouvez écrire votre propre fonction de transformation si aucune de celles existantes ne répond à vos besoins. Cela se fait en définissant une fonction de rappel avec :


png_set_read_user_transform_fn(png_ptr,


read_transform_fn);

Vous devez fournir la fonction :


void read_transform_fn(png_structp png_ptr, png_row_infop


row_info, png_bytep data)

Consultez `pngtest.c` pour un exemple fonctionnel. Votre fonction sera appelée après que toutes les autres transformations aient été traitées. Faites attention aux images entrelacées si vous gérez l'entrelacement vous-même - la largeur de la ligne est la largeur dans `row_info`, pas la largeur globale de l'image.

Si elles sont prises en charge, libpng fournit deux routines d'information que vous pouvez utiliser pour savoir où vous en êtes dans le traitement de l'image :


png_get_current_pass_number(png_structp png_ptr);


png_get_current_row_number(png_structp png_ptr);

N'essayez pas de les utiliser en dehors d'une fonction de rappel de transformation - premièrement, elles ne sont prises en charge que si les transformations utilisateur sont prises en charge, deuxièmement, elles peuvent retourner des résultats inattendus sauf si la ligne est effectivement en cours de traitement au moment où elles sont appelées.

Avec les images entrelacées, la valeur retournée est la ligne dans l'image d'entrée du sous-image. Utilisez `PNG_ROW_FROM_PASS_ROW(row, pass)` et `PNG_COL_FROM_PASS_COL(col, pass)` pour trouver le pixel de sortie (x,y) étant donné un pixel de sous-image entrelacée (row,col,pass).

La discussion sur la gestion de l'entrelacement ci-dessus contient plus d'informations sur la façon d'utiliser ces valeurs.

Vous pouvez également configurer un pointeur vers une structure utilisateur pour être utilisée par votre fonction de rappel, et vous pouvez informer libpng que votre fonction de transformation modifiera le nombre de canaux ou la profondeur de bits avec la fonction :


png_set_user_transform_info(png_ptr, user_ptr,


user_depth, user_channels);

L'application de l'utilisateur, et non libpng, est responsable de l'allocation et de la libération de toute mémoire requise pour la structure utilisateur.

Vous pouvez récupérer le pointeur via la fonction `png_get_user_transform_ptr()`. Par exemple :


voidp read_user_transform_ptr =


png_get_user_transform_ptr(png_ptr);

La dernière chose à gérer est l'entrelacement ; ceci est traité en détail ci-dessous, mais vous devez appeler la fonction ici si vous souhaitez que libpng gère le développement de l'image entrelacée.


number_of_passes = png_set_interlace_handling(png_ptr);

Après avoir défini les transformations, libpng peut mettre à jour votre structure `png_info` pour refléter les transformations que vous avez demandées avec cet appel.


png_read_update_info(png_ptr, info_ptr);

Ceci est très utile pour mettre à jour le champ `rowbytes` de la structure `info` afin que vous puissiez l'utiliser pour allouer la mémoire de votre image. Cette fonction mettra également à jour votre palette avec le `screen_gamma` et le fond corrects si ceux-ci ont été fournis avec les appels ci-dessus. Vous ne pouvez appeler `png_read_update_info()` qu'une seule fois avec un `info_ptr` donné.

Après avoir appelé `png_read_update_info()`, vous pouvez allouer toute la mémoire dont vous avez besoin pour contenir l'image. Les données de ligne sont simplement des données brutes pour toutes les formes d'images. Comme l'allocation réelle varie selon les applications, aucun exemple ne sera donné. Si vous allouez un seul gros bloc, vous devrez construire un tableau de pointeurs vers chaque ligne, car il sera nécessaire pour certaines des fonctions ci-dessous.

Assurez-vous que votre plateforme peut allouer le tampon dont vous aurez besoin. libpng vérifie en interne les largeurs excessives, mais vous devrez effectuer votre propre vérification pour `number_of_rows*width*pixel_size` si vous utilisez un tampon de plusieurs lignes :


/* Gard contre le débordement d'entiers */


if (number_of_rows > PNG_SIZE_MAX/(width*pixel_size))


png_error(png_ptr, "le tampon image_data serait trop grand");

Rappelez-vous : Avant d'appeler `png_read_update_info()`, les fonctions `png_get_*()` retournent les valeurs correspondant à l'image PNG d'origine. Après avoir appelé `png_read_update_info()`, les valeurs se réfèrent à l'image que libpng produira. Par conséquent, vous devez appeler toutes les fonctions `png_set_*()` avant d'appeler `png_read_update_info()`. C'est particulièrement important pour `png_set_interlace_handling()` - si vous allez appeler `png_read_update_info()`, vous devez appeler `png_set_interlace_handling()` avant, sauf si vous voulez recevoir une sortie entrelacée.

Lecture des données image

Après avoir alloué de la mémoire, vous pouvez lire les données image. La manière la plus simple est d'appeler une seule fonction. Si vous allouez suffisamment de mémoire pour contenir l'image entière, vous pouvez simplement appeler png_read_image() et libpng lira toutes les données image et les placera dans la zone mémoire fournie. Vous devrez fournir un tableau de pointeurs vers chaque ligne.

Cette fonction gère automatiquement l'entrelacement, vous n'avez donc pas besoin d'appeler png_set_interlace_handling() (sauf si vous appelez png_read_update_info()) ou d'appeler cette fonction plusieurs fois, ou toute autre chose nécessaire avec png_read_rows().


png_read_image(png_ptr, row_pointers);

où row_pointers est :


png_bytep row_pointers[height];

Vous pouvez pointer vers void ou char ou tout ce que vous utilisez pour les pixels.

Si vous ne souhaitez pas lire l'image entière en une seule fois, vous pouvez utiliser png_read_rows() à la place. S'il n'y a pas d'entrelacement (vérifiez interlace_type == PNG_INTERLACE_NONE), c'est simple :


png_read_rows(png_ptr, row_pointers, NULL,
number_of_rows);

où row_pointers est le même que dans l'appel à png_read_image().

Si vous ne lisez qu'une seule ligne à la fois, vous pouvez le faire avec un seul pointeur de ligne au lieu d'un tableau de pointeurs de lignes :


png_bytep row_pointer = row;
png_read_row(png_ptr, row_pointer, NULL);

Si le fichier est entrelacé (interlace_type != 0 dans le chunk IHDR), les choses deviennent un peu plus compliquées. Le seul type d'entrelacement actuel (version 1.2 de la spécification PNG) pour PNG est (interlace_type == PNG_INTERLACE_ADAM7) ; un schéma d'entrelacement 2D quelque peu compliqué, connu sous le nom d'Adam7, qui divise une image en sept images plus petites de tailles variables, basées sur une grille 8x8. Ce nombre est défini (depuis libpng 1.5) comme PNG_INTERLACE_ADAM7_PASSES dans png.h

libpng peut remplir ces images ou vous les donner "telles quelles". Il est presque toujours préférable de laisser libpng gérer l'entrelacement. Si vous souhaitez que les images soient remplies, il y a deux façons de le faire. Celle mentionnée dans la spécification PNG consiste à étendre chaque pixel pour couvrir les pixels qui n'ont pas encore été lus (méthode "rectangle"). Cela donne une image pixellisée pour la première passe, qui s'adoucit progressivement au fur et à mesure que plus de pixels sont lus. L'autre méthode est la méthode "étincelle" ("sparkle"), où les pixels sont dessinés uniquement à leurs emplacements finaux, le reste de l'image conservant les couleurs avec lesquelles il a été initialisé avant le début de la lecture. La première méthode est généralement plus belle, mais tend à être plus lente, car il y a plus de pixels à placer dans les lignes.

Si, comme il est probable, vous souhaitez que libpng étende les images, appelez ceci avant d'appeler png_start_read_image() ou png_read_update_info() :


if (interlace_type == PNG_INTERLACE_ADAM7)
number_of_passes
= png_set_interlace_handling(png_ptr);

Cela renverra le nombre de passes nécessaires. Actuellement, c'est sept, mais cela pourrait changer si un autre type d'entrelacement est ajouté. Cette fonction peut être appelée même si le fichier n'est pas entrelacé, auquel cas elle renverra une passe. Vous devrez alors lire l'image entière 'number_of_passes' fois. Chaque fois, les pixels de la passe actuelle seront distribués à l'endroit correct dans l'image de sortie, vous devez donc fournir les mêmes lignes à png_read_rows() pour chaque passe.

Si vous n'allez pas afficher l'image après chaque passe, mais que vous allez attendre que toute l'image soit lue, utilisez l'effet étincelle. Cet effet est plus rapide et le résultat final des deux méthodes est exactement le même. Si vous prévoyez d'afficher l'image après chaque passe, l'effet "rectangle" est généralement considéré comme plus beau.

Si vous ne souhaitez que l'effet "étincelle", appelez simplement png_read_row() ou png_read_rows() comme d'habitude, avec le troisième paramètre NULL. Assurez-vous de parcourir l'image 'number_of_passes' fois, et de ne pas modifier les données dans les lignes entre les appels. Vous pouvez modifier les emplacements des données, mais pas les données elles-mêmes. Chaque passe n'écrit que les pixels appropriés pour cette passe, et suppose que les données des passes précédentes sont toujours valides.


png_read_rows(png_ptr, row_pointers, NULL,
number_of_rows);
ou
png_read_row(png_ptr, row_pointers, NULL);

Si vous ne souhaitez que le premier effet (les rectangles), faites la même chose qu'auparavant, sauf que vous passez le tampon de ligne dans le troisième paramètre et laissez le deuxième paramètre à NULL.


png_read_rows(png_ptr, NULL, row_pointers,
number_of_rows);
ou
png_read_row(png_ptr, NULL, row_pointers);

Si vous ne souhaitez pas que libpng gère les détails de l'entrelacement, appelez simplement png_read_rows() PNG_INTERLACE_ADAM7_PASSES fois pour lire toutes les images. Chacune des images est une image valide en soi ; cependant, vous devrez presque certainement distribuer les pixels de chaque sous-image à l'endroit correct. C'est là que tout devient très délicat.

Si vous souhaitez récupérer les images séparées, vous devez passer le nombre correct de lignes à chaque appel successif de png_read_rows(). Le calcul devient assez compliqué pour les petites images, où certaines sous-images peuvent même ne pas exister car leur largeur ou leur hauteur devient zéro. libpng fournit deux macros pour vous aider dans les versions 1.5 et ultérieures :


png_uint_32 width = PNG_PASS_COLS(image_width, pass_number);
png_uint_32 height = PNG_PASS_ROWS(image_height, pass_number);

Ces macros vous indiquent respectivement la largeur et la hauteur de la sous-image correspondant à la passe numérotée. 'pass' est dans la plage 0 à 6 - cela peut être déroutant car la spécification fait référence aux mêmes passes comme 1 à 7 ! Faites attention, vous devez vérifier la largeur et la hauteur avant d'appeler png_read_rows() et ne pas l'appeler pour cette passe si l'une ou l'autre est nulle.

Vous pouvez, bien sûr, lire chaque sous-image ligne par ligne. Si vous souhaitez produire un code optimal pour transformer une image entrelacée pixel par pixel, c'est la meilleure approche ; lisez chaque ligne de chaque passe, transformez-la et écrivez-la dans une nouvelle image entrelacée.

Si vous souhaitez désentrelacer l'image vous-même, libpng fournit d'autres macros pour vous aider, qui vous indiquent où placer les pixels dans l'image de sortie. Comme le schéma d'entrelacement est rectangulaire - les pixels de la sous-image sont toujours disposés sur une grille rectangulaire - tout ce que vous devez savoir pour chaque passe est la colonne et la ligne de départ dans l'image de sortie du premier pixel, plus l'espacement entre chaque pixel. À partir de libpng 1.5, quatre macros permettent de récupérer ces informations :


png_uint_32 x = PNG_PASS_START_COL(pass);
png_uint_32 y = PNG_PASS_START_ROW(pass);
png_uint_32 xStep = 1U << PNG_PASS_COL_SHIFT(pass);
png_uint_32 yStep = 1U << PNG_PASS_ROW_SHIFT(pass);

Celles-ci vous permettent d'écrire la boucle évidente :


png_uint_32 input_y = 0;
png_uint_32 output_y = PNG_PASS_START_ROW(pass);


while (output_y < output_image_height)
{
png_uint_32 input_x = 0;
png_uint_32 output_x = PNG_PASS_START_COL(pass);


while (output_x < output_image_width)
{
image[output_y][output_x] =
subimage[pass][input_y][input_x++];


output_x += xStep;
}


++input_y;
output_y += yStep;
}

Notez que les pas entre les lignes et colonnes de sortie successives sont renvoyés sous forme de décalages. Ceci est possible car les pixels des sous-images sont toujours espacés d'une puissance de 2 - 1, 2, 4 ou 8 pixels - dans l'image d'origine. En pratique, vous devrez peut-être calculer directement la coordonnée de sortie étant donné une coordonnée d'entrée. libpng fournit deux macros supplémentaires à cet effet :


png_uint_32 output_x = PNG_COL_FROM_PASS_COL(input_x, pass);
png_uint_32 output_y = PNG_ROW_FROM_PASS_ROW(input_y, pass);

Enfin, une paire de macros sont fournies pour vous indiquer si une ligne ou une colonne d'image particulière apparaît dans une passe donnée :


int col_in_pass = PNG_COL_IN_INTERLACE_PASS(output_x, pass);
int row_in_pass = PNG_ROW_IN_INTERLACE_PASS(output_y, pass);

Gardez à l'esprit que vous devrez probablement également vérifier la largeur et la hauteur de la passe en plus de ce qui précède pour vous assurer que la passe existe même !

Avec un peu de chance, vous êtes maintenant convaincu que vous ne voulez pas gérer vous-même l'entrelacement. En réalité, la seule bonne raison de le faire est si vous traitez des fichiers PNG pixel par pixel et que vous ne souhaitez pas charger tout le fichier en mémoire lorsqu'il est entrelacé.

libpng inclut un programme de test, pngvalid, qui illustre la lecture et l'écriture d'images entrelacées. Si vous n'arrivez pas à faire fonctionner l'entrelacement dans votre code et que vous ne voulez pas le laisser à libpng (l'approche recommandée), regardez comment pngvalid.c procède.

Finir une lecture séquentielle

Après avoir terminé la lecture de l'image via l'interface de bas niveau, vous pouvez finir de lire le fichier.

Si vous souhaitez utiliser une action CRC différente pour gérer les erreurs CRC dans les chunks après les données image, vous pouvez appeler png_set_crc_action() à nouveau à ce stade.

Si vous vous intéressez aux commentaires ou au temps, qui peuvent être stockés avant ou après les données image, vous devriez passer la structure png_info séparée si vous souhaitez conserver les commentaires d'avant et d'après l'image séparément.


png_infop end_info = png_create_info_struct(png_ptr);


if (!end_info)
{
png_destroy_read_struct(&png_ptr, &info_ptr, NULL);
return ERROR;
}


png_read_end(png_ptr, end_info);

Si cela ne vous intéresse pas, vous devriez quand même appeler png_read_end() mais vous pouvez passer NULL, évitant ainsi de créer une structure end_info. Si vous le faites, libpng ne traitera aucun chunk après IDAT, à part les ignorer et peut-être (selon que vous ayez appelé png_set_crc_action()) vérifier leurs CRC tout en recherchant le chunk IEND.


png_read_end(png_ptr, NULL);

Si vous n'appelez pas png_read_end(), alors votre pointeur de fichier restera pointant vers le premier chunk après le dernier IDAT, ce qui n'est probablement pas ce que vous souhaitez si vous vous attendez à lire quelque chose au-delà de la fin du flux de données PNG.

Lorsque vous avez terminé, vous pouvez libérer toute la mémoire allouée par libpng comme suit :


png_destroy_read_struct(&png_ptr, &info_ptr, &end_info);

ou, si vous n'avez pas créé de structure end_info,


png_destroy_read_struct(&png_ptr, &info_ptr, NULL);

III. Callbacks

The libpng library provides callbacks for a variety of reasons. Some are for handling errors, some for handling I/O, and some for handling various parts of the PNG file format. This section covers the callbacks that are described in the API, but not those in the "Customizing Libpng" section.

Reading callbacks

There are three callbacks associated with reading. The first is a row_callback, which is called after each row has been read. This can be used to control a progress meter or the like. The function has the signature: 

void row_callback(png_structp png_ptr, png_uint_32 row, int pass)

(You can give it another name that you like instead of "row_callback")

To inform libpng about your function, use 

png_set_read_status_fn(png_ptr, row_callback);

When this function is called the row has already been completely processed and it has also been read. The 'row' and 'pass' refer to the row that was just handled. For the non-interlaced case the row that was just handled is simply 'row' and 'pass' will always be 0. For the interlaced case the row numbers skip rows depending on the pass number. Because interlacing may skip a pass you cannot be sure that the preceding pass is just 'pass-1', if you really need to know what the last pass is record (row,pass) from the callback and use the last recorded value each time.

You may also wish to transform the image data on the fly. You can do this by setting up a row transform function. This function is called after the row has been read, but before any filters have been applied. The function has the signature: 

void row_transform_callback(png_structp png_ptr, png_bytep row,
    png_uint_32 row_num, int pass)

(You can give it another name that you like instead of "row_transform_callback")

To inform libpng about your function, use 

png_set_read_user_transform_fn(png_ptr, row_transform_callback);

Note that this callback can only be used if you are reading the whole image at once (i.e. not using png_start_row). The row_num indicates the row number being processed, starting at 0. The pass is the interlacing pass number, starting at 0. The row is a pointer to the row data. The function can modify the row data in place.

Finally, there is an end_callback. This function is called after the entire image has been read, including any chunks after the image (up to and including the IEND). The function has the signature: 

void end_callback(png_structp png_ptr, png_infop info)

(You can give it another name that you like instead of "end_callback")

To inform libpng about your function, use 

png_set_end_info_fn(png_ptr, end_callback);

This function is called after the whole image has been read, including any chunks after the image (up to and including the IEND). You will usually have the same info chunk as you had in the header, although some data may have been added to the comments and time fields.

Most people won't do much here, perhaps setting a flag that marks the image as finished.

You can also call png_process_data_pause in this callback - see above.

Much of this is very similar to reading. However, everything of importance is repeated here, so you won't have to constantly look back up in the reading section to understand writing.

Setup

You will want to do the I/O initialization before you get into libpng, so if it doesn't work, you don't have anything to undo. If you are not using the standard I/O functions, you will need to replace them with custom writing functions. See the discussion under Customizing libpng.

png_structp png_ptr = png_create_write_struct

If you would rather avoid the complexity of setjmp/longjmp issues, you can compile libpng with PNG_NO_SETJMP, in which case errors will result in a call to PNG_ABORT() which defaults to abort().

You can #define PNG_ABORT() to a function that does something more useful than abort(), as long as your function does not return.

Checking for invalid palette index on write was added at libpng 1.5.10. If a pixel contains an invalid (out-of-range) index libpng issues a benign error. This is enabled by default because this condition is an error according to the PNG specification, Clause 11.3.2, but the error can be ignored in each png_ptr with 

png_set_check_for_invalid_index(png_ptr, 0);

If the error is ignored, or if png_benign_error() treats it as a warning, any invalid pixels are written as-is by the encoder, resulting in an invalid PNG datastream as output. In this case the application is responsible for ensuring that the pixel indexes are in range when it writes a PLTE chunk with fewer entries than the bit depth would allow.

Now you need to set up the output code. The default for libpng is to use the C function fwrite(). If you use this, you will need to pass a valid FILE * in the function png_init_io(). Be sure that the file is opened in binary mode. Again, if you wish to handle writing data in another way, see the discussion on libpng I/O handling in the Customizing Libpng section below. 

png_init_io(png_ptr, fp);

If you are embedding your PNG into a datastream such as MNG, and don't want libpng to write the 8-byte signature, or if you have already written the signature in your application, use 

png_set_sig_bytes(png_ptr, 8);

to inform libpng that it should not write a signature.

At this point, you can set up a callback function that will be called after each row has been written, which you can use to control a progress meter or the like. It's demonstrated in pngtest.c. You must supply a function

png_set_write_status_fn(png_ptr, write_row_callback);

When this function is called the row has already been completely processed and it has also been written out. The 'row' and 'pass' refer to the next row to be handled. For the non-interlaced case the row that was just handled is simply one less than the passed in row number, and pass will always be 0. For the interlaced case the same applies unless the row value is 0, in which case the row just handled was the last one from one of the preceding passes. Because interlacing may skip a pass you cannot be sure that the preceding pass is just 'pass-1', if you really need to know what the last pass is record (row,pass) from the callback and use the last recorded value each time.

As with the user transform you can find the output row using the PNG_ROW_FROM_PASS_ROW macro.

You now have the option of modifying how the compression library will run. The following functions are mainly for testing, but may be useful in some cases, like if you need to write PNG files extremely fast and are willing to give up some compression, or if you want to get the maximum possible compression at the expense of slower writing. If you have no special needs in this area, let the library do what it wants by not calling this function at all, as it has been tuned to deliver a good speed/compression ratio. The second parameter to png_set_filter() is the filter method, for which the only valid values are 0 (as of the July 1999 PNG specification, version 1.2) or 64 (if you are writing a PNG datastream that is to be embedded in a MNG datastream). The third parameter is a flag that indicates which filter type(s) are to be tested for each scanline. See the PNG specification for details on the specific filter types. 

/* turn on or off filtering, and/or choose

   PNG_FILTER_VALUE_NAME or the bitwise OR of one
   or more PNG_FILTER_NAME masks.

png_set_filter(png_ptr, 0,

   PNG_FILTER_SUB | PNG_FILTER_VALUE_SUB |
   PNG_FILTER_UP | PNG_FILTER_VALUE_UP |
   PNG_FILTER_AVG | PNG_FILTER_VALUE_AVG |
   PNG_FILTER_PAETH | PNG_FILTER_VALUE_PAETH|
   PNG_ALL_FILTERS | PNG_FAST_FILTERS);

If you are writing a PNG datastream that is to be embedded in a MNG datastream, the second parameter can be either 0 or 64.

Un mot rapide sur text et num_text. text est un tableau de structures png_text. num_text est le nombre de structures valides dans le tableau. Chaque structure png_text contient un code de langue, un mot-clé, une valeur de texte et un type de compression.

Les types de compression ont les mêmes numéros valides que les types de compression des données d'image. Actuellement, le seul numéro valide est zéro. Cependant, vous pouvez stocker le texte de manière compressée ou non compressée, contrairement aux images, qui doivent toujours être compressées. Donc, si vous ne souhaitez pas que le texte soit compressé, définissez le type de compression sur PNG_TEXT_COMPRESSION_NONE. Étant donné que les blocs tEXt et zTXt n'ont pas de champ de langue, si vous spécifiez PNG_TEXT_COMPRESSION_NONE ou PNG_TEXT_COMPRESSION_zTXt, tout code de langue ou mot-clé traduit ne sera pas écrit.

Tant que le texte ne dépasse pas quelques centaines d'octets, il n'est pas utile de le compresser. Une fois que le texte a été écrit dans le fichier, le type de compression est défini sur PNG_TEXT_COMPRESSION_NONE_WR ou PNG_TEXT_COMPRESSION_zTXt_WR, afin qu'il ne soit pas réécrit à la fin (au cas où vous appelleriez png_write_end() avec la même structure).

Les mots-clés donnés dans la spécification PNG sont :


Title Titre court (une ligne) ou légende pour l'image


Author Nom du créateur de l'image


Description Description de l'image (éventuellement longue)


Copyright Avis de droit d'auteur


Creation Time Heure de création de l'image originale
(généralement au format RFC 1123, voir ci-dessous)


Software Logiciel utilisé pour créer l'image


Disclaimer Clause de non-responsabilité légale


Warning Avertissement concernant la nature du contenu


Source Périphérique utilisé pour créer l'image


Comment Commentaire divers ; conversion
depuis un autre format d'image

Les paires mot-clé-texte fonctionnent comme suit. Les mots-clés doivent être de courtes descriptions simples de ce que concerne le commentaire. Certains mots-clés typiques se trouvent dans la spécification PNG, ainsi que des recommandations sur les mots-clés. Vous pouvez répéter des mots-clés dans un fichier. Vous pouvez même écrire du texte avant l'image et après. Par exemple, vous pourriez vouloir mettre une description de l'image avant celle-ci, mais laisser le disclaimer pour après, afin que les spectateurs utilisant des connexions modem ne doivent pas attendre le disclaimer avant de commencer à voir l'image. Enfin, les mots-clés doivent être des mots complets, pas des abréviations. Les mots-clés et les textes sont dans le jeu de caractères ISO 8859-1 (Latin-1) (un sur-ensemble de l'ASCII standard) et ne peuvent pas contenir de caractères NUL, et ne devraient pas contenir de caractères de contrôle ou d'autres caractères non imprimables. Pour rendre les commentaires largement lisibles, privilégiez l'ASCII de base et évitez les extensions de jeux de caractères spécifiques aux machines comme le jeu de caractères IBM-PC. Le mot-clé doit être présent, mais vous pouvez omettre la chaîne de texte sur les paires non compressées. Les paires compressées doivent avoir une chaîne de texte, car seule la chaîne de texte est compressée de toute façon, donc la compression serait dénuée de sens.

PNG prend en charge l'heure de modification via la structure png_time. Deux routines de conversion sont fournies, png_convert_from_time_t() pour time_t et png_convert_from_struct_tm() pour struct tm. La routine time_t utilise gmtime(). Vous n'êtes pas obligé d'utiliser l'une ou l'autre de ces routines, mais si vous souhaitez remplir directement la structure png_time, vous devriez fournir l'heure en temps universel (GMT) si possible plutôt que votre heure locale. Notez que le numéro de l'année est l'année complète (par exemple, 1998, plutôt que 98 - PNG est conforme à l'an 2000 !), et que les mois commencent à 1.

Si vous souhaitez stocker l'heure de création de l'image originale, vous devriez utiliser un bloc tEXt ordinaire avec le mot-clé "Creation Time". Ceci est nécessaire car l'"heure de création" d'une image PNG est quelque peu vague, dépendant si vous entendez le fichier PNG, l'heure à laquelle l'image a été créée dans un format non-PNG, une photo fixe à partir de laquelle l'image a été numérisée, ou éventuellement le sujet lui-même. Afin de faciliter les dates lisibles par machine, il est recommandé que le bloc tEXt "Creation Time" utilise le format de date RFC 1123 (par exemple, "22 May 1997 18:07:10 GMT"), bien que ce ne soit pas une exigence. Contrairement au bloc tIME, le bloc tEXt "Creation Time" n'est pas censé être automatiquement modifié par le logiciel. Pour faciliter l'utilisation des dates RFC 1123, une fonction png_convert_to_rfc1123_buffer(buffer, png_timep) est fournie pour convertir du temps PNG en une chaîne de format RFC 1123. L'appelant doit fournir un tampon inscriptible d'au moins 29 octets.

Écriture des blocs inconnus

Vous pouvez utiliser la fonction png_set_unknown_chunks pour mettre en file d'attente des blocs privés à écrire. Vous lui fournissez un nom de bloc, une localisation, des données brutes et une taille. Vous devez également utiliser png_set_keep_unknown_chunks() pour vous assurer que libpng les gérera. C'est tout. Les blocs seront écrits par la fonction suivante png_write_info_before_PLTE, png_write_info, ou png_write_end, en fonction de la localisation spécifiée. Tous les blocs précédemment lus dans la liste des blocs inconnus de la structure d'informations seront également écrits dans un ordre qui satisfait aux règles d'ordonnancement de la spécification PNG.

Voici un exemple d'écriture de deux blocs privés, prVt et miNE :


#ifdef PNG_WRITE_UNKNOWN_CHUNKS_SUPPORTED
/* Définir les données du bloc inconnu */
png_unknown_chunk unk_chunk[2];
strcpy((char *) unk_chunk[0].name, "prVt";
unk_chunk[0].data = (unsigned char *) "PRIVATE DATA";
unk_chunk[0].size = strlen(unk_chunk[0].data)+1;
unk_chunk[0].location = PNG_HAVE_IHDR;
strcpy((char *) unk_chunk[1].name, "miNE";
unk_chunk[1].data = (unsigned char *) "MY CHUNK DATA";
unk_chunk[1].size = strlen(unk_chunk[0].data)+1;
unk_chunk[1].location = PNG_AFTER_IDAT;
png_set_unknown_chunks(write_ptr, write_info_ptr,
unk_chunk, 2);
/* Nécessaire car miNE n'est pas sûr à copier */
png_set_keep_unknown_chunks(png, PNG_HANDLE_CHUNK_ALWAYS,
(png_bytep) "miNE", 1);
#endif

L'interface d'écriture de haut niveau

À ce stade, il y a deux façons de procéder ; via l'interface d'écriture de haut niveau, ou via une séquence d'opérations d'écriture de bas niveau. Vous pouvez utiliser l'interface de haut niveau si vos données d'image sont présentes dans la structure d'informations. Toutes les transformations de sortie définies sont autorisées, activées par les masques suivants.

pour être LSB d'abord
PNG_TRANSFORM_INVERT_MONO Inverser les images monochromes
PNG_TRANSFORM_SHIFT Normaliser les pixels à la profondeur
sBIT

en BGRA

en AG
PNG_TRANSFORM_INVERT_ALPHA Changer l'alpha de l'opacité
en transparence

PNG_TRANSFORM_STRIP_FILLER_AFTER Supprimer les octets de remplissage de queue

Si vous avez des données d'image valides dans la structure d'informations (vous pouvez utiliser png_set_rows() pour insérer des données d'image dans la structure d'informations), faites simplement ceci :


png_write_png(png_ptr, info_ptr, png_transforms, NULL)

où png_transforms est un entier contenant le OU bit à bit d'un ensemble de drapeaux de transformation. Cet appel est équivalent à png_write_info(), suivi de l'ensemble des transformations indiquées par le masque de transformation, puis png_write_image(), et enfin png_write_end().

(Le dernier paramètre de cet appel n'est pas encore utilisé. Un jour, il pourrait pointer vers des paramètres de transformation requis par une future transformation de sortie.)

Vous devez utiliser png_transforms et ne pas appeler de fonctions png_set_transform() lorsque vous utilisez png_write_png().

L'interface d'écriture de bas niveau

Si vous optez pour la voie de bas niveau, vous êtes maintenant prêt à écrire toutes les informations du fichier jusqu'aux données d'image réelles. Vous le faites avec un appel à png_write_info().


png_write_info(png_ptr, info_ptr);

Notez qu'il y a une transformation que vous pourriez avoir besoin de faire avant png_write_info(). Dans les fichiers PNG, le canal alpha d'une image représente le niveau d'opacité. Si vos données sont fournies comme un niveau de transparence, vous pouvez inverser le canal alpha avant de l'écrire, de sorte que 0 soit entièrement transparent et 255 (dans les images 8 bits ou palettisées) ou 65535 (dans les images 16 bits) soit entièrement opaque, avec


png_set_invert_alpha(png_ptr);

Ceci doit apparaître avant png_write_info() au lieu de plus tard avec les autres transformations car, dans le cas des images palettisées, les données du bloc tRNS doivent être inversées avant que le bloc tRNS ne soit écrit. Si votre image n'est pas une image palettisée, les données tRNS (qui dans de tels cas représentent une seule couleur à rendre comme transparente) n'auront pas besoin d'être modifiées, et vous pouvez effectuer cette transformation en toute sécurité après votre appel à png_write_info().

Si vous avez besoin d'écrire un bloc privé qui doit apparaître avant le bloc PLTE lorsque PLTE est présent, vous pouvez écrire les informations PNG en deux étapes et insérer du code pour écrire votre propre bloc entre elles :


png_write_info_before_PLTE(png_ptr, info_ptr);
png_set_unknown_chunks(png_ptr, info_ptr, ...);
png_write_info(png_ptr, info_ptr);

Une fois que vous avez écrit les informations du fichier, vous pouvez configurer la bibliothèque pour gérer les transformations spéciales des données d'image. Les différentes manières de transformer les données seront décrites dans l'ordre où elles doivent se produire. Ceci est important, car certaines d'entre elles modifient le type de couleur et/ou la profondeur de bits des données, et d'autres ne fonctionnent que sur certains types de couleur et profondeurs de bits. Même si chaque transformation vérifie si elle a des données sur lesquelles elle peut agir, vous devez vous assurer de n'activer une transformation que si elle sera valide pour les données. Par exemple, ne échangez pas le rouge et le bleu sur des niveaux de gris

le data.

Les fichiers PNG stockent les pixels RGB regroupés en 3 ou 6 octets. Ce code indique à la bibliothèque de réduire les données d'entrée ayant 4 ou 8 octets par pixel à 3 ou 6 octets (ou de réduire les données de niveaux de gris/remplissage de 2 ou 4 octets à 1 ou 2 octets par pixel).


png_set_filler(png_ptr, 0, PNG_FILLER_BEFORE);

où le 0 n'est pas utilisé, et l'emplacement est soit PNG_FILLER_BEFORE, soit PNG_FILLER_AFTER, selon que l'octet de remplissage dans le pixel est stocké XRGB ou RGBX.

Les fichiers PNG regroupent les pixels de profondeurs de bits 1, 2 et 4 en octets aussi petits que possible, ce qui donne, par exemple, 8 pixels par octet pour les fichiers de 1 bit. Si les données sont fournies à raison de 1 pixel par octet, utilisez ce code, qui regroupra correctement les pixels dans un seul octet :


png_set_packing(png_ptr);

Les fichiers PNG réduisent les profondeurs de bits possibles à 1, 2, 4, 8 et 16. Si vos données ont une profondeur de bits différente, vous pouvez écrire un chunk sBIT dans le fichier afin que les décodeurs puissent récupérer les données d'origine si désiré.


/* Définir la vraie profondeur de bits des données de l'image */
if (color_type & PNG_COLOR_MASK_COLOR)
{
sig_bit.red = true_bit_depth;
sig_bit.green = true_bit_depth;
sig_bit.blue = true_bit_depth;
}


else
{
sig_bit.gray = true_bit_depth;
}


if (color_type & PNG_COLOR_MASK_ALPHA)
{
sig_bit.alpha = true_bit_depth;
}


png_set_sBIT(png_ptr, info_ptr, &sig_bit);

Si les données sont stockées dans le tampon de ligne dans une profondeur de bits autre qu'une prise en charge par PNG (par exemple, des données de 3 bits dans la plage 0-7 pour un PNG de 4 bits), cela mettra à l'échelle les valeurs pour qu'elles apparaissent avec la profondeur de bits correcte, comme requis par PNG.


png_set_shift(png_ptr, &sig_bit);

Les fichiers PNG stockent les pixels de 16 bits en ordre de réseau (big-endian, c'est-à-dire les bits les plus significatifs en premier). Ce code serait utilisé s'ils sont fournis dans l'autre sens (little-endian, c'est-à-dire les bits les moins significatifs en premier, la façon dont les PC les stockent) :


if (bit_depth > 8)
png_set_swap(png_ptr);

Si vous utilisez des images à pixels compressés (1, 2 ou 4 bits/pixel) et que vous avez besoin de changer l'ordre dans lequel les pixels sont regroupés en octets, vous pouvez utiliser :


if (bit_depth < 8)
png_set_packswap(png_ptr);

Les fichiers PNG stockent les pixels en 3 couleurs dans l'ordre rouge, vert, bleu. Ce code serait utilisé s'ils sont fournis en bleu, vert, rouge :


png_set_bgr(png_ptr);

Les fichiers PNG décrivent le monochrome comme étant noir zéro et blanc un. Ce code serait utilisé si les pixels sont fournis avec cet ordre inversé (noir un et blanc zéro) :


png_set_invert_mono(png_ptr);

Enfin, vous pouvez écrire votre propre fonction de transformation si aucune des fonctions existantes ne répond à vos besoins. Ceci est fait en définissant une fonction de rappel avec


png_set_write_user_transform_fn(png_ptr,
write_transform_fn);

Vous devez fournir la fonction


void write_transform_fn(png_structp png_ptr, png_row_infop
row_info, png_bytep data)

Voir pngtest.c pour un exemple fonctionnel. Votre fonction sera appelée avant que toutes les autres transformations ne soient traitées. Si elle est prise en charge, libpng fournit également une routine d'information qui peut être appelée depuis votre fonction de rappel :


png_get_current_row_number(png_ptr);
png_get_current_pass_number(png_ptr);

Cela renvoie la ligne actuelle transmise à la transformation. Avec les images entrelacées, la valeur renvoyée est la ligne dans la sous-image d'entrée. Utilisez PNG_ROW_FROM_PASS_ROW(row, pass) et PNG_COL_FROM_PASS_COL(col, pass) pour trouver le pixel de sortie (x,y) étant donné un pixel de sous-image entrelacée (row,col,pass).

La discussion sur la gestion de l'entrelacement ci-dessus contient plus d'informations sur la façon d'utiliser ces valeurs.

Vous pouvez également configurer un pointeur vers une structure utilisateur pour l'utilisation par votre fonction de rappel.


png_set_user_transform_info(png_ptr, user_ptr, 0, 0);

Les paramètres user_channels et user_depth de cette fonction sont ignorés lors de l'écriture ; vous pouvez les définir à zéro comme indiqué.

Vous pouvez récupérer le pointeur via la fonction png_get_user_transform_ptr(). Par exemple :


voidp write_user_transform_ptr =
png_get_user_transform_ptr(png_ptr);

Il est possible de faire en sorte que libpng vide les sorties en attente, soit manuellement, soit automatiquement après qu'un certain nombre de lignes ont été écrites. Pour vider le flux de sortie une seule fois, appelez :


png_write_flush(png_ptr);

Et pour que libpng vide le flux de sortie périodiquement après qu'un certain nombre de lignes de balayage ont été écrites, appelez :


png_set_flush(png_ptr, nrows);

Notez que la distance entre les lignes est depuis la dernière fois que png_write_flush() a été appelée, ou la première ligne de l'image si elle n'a jamais été appelée. Ainsi, si vous écrivez 50 lignes, puis png_set_flush 25, cela videra la sortie sur la ligne de balayage suivante, et toutes les 25 lignes par la suite, à moins que png_write_flush() ne soit appelée avant que 25 lignes supplémentaires aient été écrites. Si nrows est trop petit (moins d'environ 10 lignes pour une image RVB de 640 pixels de large), la compression de l'image peut diminuer sensiblement (bien que cela puisse être acceptable pour les applications en temps réel). Un vidage peu fréquent ne dégradera les performances de compression que de quelques pour cent par rapport aux images qui n'utilisent pas le vidage.

Écriture des données de l'image

C'est tout pour les transformations. Vous pouvez maintenant écrire les données de l'image. La manière la plus simple de le faire est en un seul appel de fonction. Si vous avez l'image entière en mémoire, vous pouvez simplement appeler png_write_image() et libpng écrira l'image. Vous devrez fournir un tableau de pointeurs vers chaque ligne. Cette fonction gère automatiquement l'entrelacement, vous n'avez donc pas besoin d'appeler png_set_interlace_handling() ou d'appeler cette fonction plusieurs fois, ou toute autre chose nécessaire avec png_write_rows().


png_write_image(png_ptr, row_pointers);

où row_pointers est :


png_byte *row_pointers[height];

Vous pouvez pointer vers void ou char ou tout ce que vous utilisez pour les pixels.

Si vous ne souhaitez pas écrire l'image entière en une seule fois, vous pouvez utiliser png_write_rows() à la place. Si le fichier n'est pas entrelacé, c'est simple :


png_write_rows(png_ptr, row_pointers,
number_of_rows);

row_pointers est le même que dans l'appel png_write_image().

Si vous n'écrivez qu'une ligne à la fois, vous pouvez le faire avec un seul row_pointer au lieu d'un tableau de row_pointers :


png_bytep row_pointer = row;


png_write_row(png_ptr, row_pointer);

Lorsque le fichier est entrelacé, les choses peuvent devenir beaucoup plus compliquées. Le seul schéma d'entrelacement actuellement (à la date de la spécification PNG version 1.2, datée de juillet 1999) défini pour les fichiers PNG est le schéma d'entrelacement "Adam7", qui divise une image en sept images plus petites de tailles variables. libpng construira ces images pour vous, ou vous pouvez le faire vous-même. Si vous souhaitez les construire vous-même, consultez la spécification PNG pour connaître les détails des pixels à écrire et quand.

Si vous ne voulez pas que libpng gère les détails de l'entrelacement, utilisez simplement png_set_interlace_handling() et appelez png_write_rows() le nombre de fois correct pour écrire toutes les sous-images (png_set_interlace_handling() renvoie le nombre de sous-images.)

Si vous voulez que libpng construise les sous-images, appelez ceci avant de commencer à écrire des lignes :


number_of_passes = png_set_interlace_handling(png_ptr);

Cela renverra le nombre de passes nécessaires. Actuellement, il est de sept, mais peut changer si un autre type d'entrelacement est ajouté.

Ensuite, écrivez l'image complète number_of_passes fois.


png_write_rows(png_ptr, row_pointers, number_of_rows);

Réfléchissez bien avant d'écrire une image entrelacée. Typiquement, le code qui lit de telles images charge toutes les données de l'image en mémoire, décompressées, avant de procéder à un quelconque traitement. Seul le code qui peut afficher une image à la volée peut tirer parti de l'entrelacement et même dans ce cas, l'image doit avoir exactement la bonne taille pour le périphérique de sortie, car la mise à l'échelle d'une image nécessite des pixels adjacents qui ne sont pas disponibles tant que toutes les passes n'ont pas été lues.

Si vous écrivez une image entrelacée, vous n'aurez presque jamais besoin de gérer l'entrelacement vous-même. Appelez png_set_interlace_handling() et utilisez l'approche décrite ci-dessus.

La seule fois où il est concevable que vous ayez vraiment besoin d'écrire une image entrelacée passe par passe est lorsque vous avez lu une image passe par passe et y avez apporté une transformation pixel par pixel, comme décrit dans le code de lecture ci-dessus. Dans ce cas, utilisez les macros PNG_PASS_ROWS et PNG_PASS_COLS pour déterminer la taille de chaque sous-image à tour de rôle et écrivez simplement les lignes que vous avez obtenues du code de lecture.

Fin d'une écriture séquentielle

V. API simplifiée

L'API simplifiée, disponible depuis libpng-1.6.0, masque les détails de libpng et du format de fichier PNG lui-même. Elle permet de lire des fichiers PNG dans un nombre très limité de formats de bitmap en mémoire ou de les écrire à partir des mêmes formats. Si ces formats ne répondent pas à vos besoins, vous pouvez et devriez utiliser les API plus sophistiquées ci-dessus - celles-ci prennent en charge une grande variété de formats en mémoire et une grande variété de transformations de ces formats, ainsi qu'une grande variété d'API pour manipuler des informations auxiliaires.

Pour lire un fichier PNG en utilisant l'API simplifiée :


1) Déclarez une structure 'png_image' (voir ci-dessous) sur la pile, définissez le
champ version à PNG_IMAGE_VERSION et le pointeur 'opaque' à NULL
(ceci est REQUIS, votre programme peut planter si vous ne le faites pas.)


2) Appelez la fonction png_image_begin_read... appropriée.


3) Définissez le membre 'format' de png_image au format d'échantillon requis.


4) Allouez un tampon pour l'image et, si nécessaire, la palette de couleurs.


5) Appelez png_image_finish_read pour lire l'image et, si nécessaire, la
palette de couleurs dans vos tampons.

Il n'y a aucune restriction sur le format de l'entrée PNG elle-même ; tous les types de couleurs, profondeurs de bits et méthodes d'entrelacement valides sont acceptables, et l'image d'entrée est transformée si nécessaire au format en mémoire demandé pendant l'étape png_image_finish_read(). La seule mise en garde est que si vous demandez une image avec palette à partir d'un PNG en couleur ou qui utilise de manière complexe un canal alpha, la transformation est extrêmement coûteuse en données et le résultat peut être terrible.

Pour écrire un fichier PNG en utilisant l'API simplifiée :


1) Déclarez une structure 'png_image' sur la pile et initialisez-la
à zéro avec memset().


2) Initialisez les membres de la structure qui décrivent l'image, en définissant le
membre 'format' au format des échantillons de l'image.


3) Appelez la fonction png_image_write... appropriée avec un
pointeur vers l'image et, si nécessaire, la palette de couleurs pour écrire
les données PNG.

png_image est une structure qui décrit le format en mémoire d'une image lorsqu'elle est lue ou définit le format en mémoire d'une image que vous devez écrire. La structure "png_image" contient les membres suivants :


png_controlp opaque Initialisé à NULL, à libérer avec png_image_free
png_uint_32 version Défini à PNG_IMAGE_VERSION
png_uint_32 width Largeur de l'image en pixels (colonnes)
png_uint_32 height Hauteur de l'image en pixels (lignes)
png_uint_32 format Format de l'image tel que défini ci-dessous
png_uint_32 flags Un masque de bits contenant des indicateurs d'information
png_uint_32 colormap_entries; Nombre d'entrées dans la palette de couleurs
png_uint_32 warning_or_error;
char message[64];

En cas d'erreur ou d'avertissement, le champ "warning_or_error" sera défini à une valeur non nulle et le champ 'message' contiendra une chaîne terminée par un ' ' avec le message d'erreur ou d'avertissement de libpng. Si des avertissements et une erreur ont été rencontrés, seule l'erreur est enregistrée. S'il y a plusieurs avertissements, seul le premier est enregistré.

Les 30 bits supérieurs de la valeur "warning_or_error" sont réservés ; les deux bits de poids faible contiennent un code de deux bits tel qu'une valeur supérieure à 1 indique un échec dans l'API appelée :


0 - aucun avertissement ni erreur
1 - avertissement
2 - erreur
3 - erreur précédée d'un avertissement

Les pixels (échantillons) de l'image ont un à quatre canaux dont les composantes ont des valeurs originales dans la plage de 0 à 1.0 :


1 : Un seul canal de gris ou de luminance (G).
2 : Un canal de gris/luminance et un canal alpha (GA).
3 : Trois canaux de couleur rouge, vert, bleu (RVB).
4 : Trois canaux de couleur et un canal alpha (RVBA).

Les canaux sont encodés de l'une des deux manières suivantes :


a) Comme un petit entier, valeur 0..255, contenu dans un seul octet. Pour le canal alpha, la valeur originale est simplement valeur/255. Pour les canaux de couleur ou de luminance, la valeur est encodée selon la spécification sRGB et correspond au format 8 bits attendu par les périphériques d'affichage typiques.

Les canaux de couleur/gris ne sont pas mis à l'échelle (pré-multipliés) par le canal alpha et conviennent à être transmis à un logiciel de gestion des couleurs.


b) Comme une valeur dans la plage 0..65535, contenue dans un entier de 2 octets, dans l'ordre des octets natif de la plateforme sur laquelle l'application s'exécute. Tous les canaux peuvent être convertis en la valeur originale en divisant par 65535 ; tous les canaux sont linéaires. Les canaux de couleur utilisent l'encodage RVB (points d'extrémité RVB) de la spécification sRGB. Cet encodage est identifié par le drapeau PNG_FORMAT_FLAG_LINEAR ci-dessous.

Lorsque l'API simplifiée doit convertir entre les couleurs sRGB et les couleurs linéaires, la courbe de transfert sRGB réelle définie dans la spécification sRGB (voir l'article sur https://en.wikipedia.org/wiki/SRGB) est utilisée, et non l'approximation gamma=1/2.2 utilisée ailleurs dans libpng.

Lorsqu'un canal alpha est présent, il est censé indiquer la couverture de pixels des canaux de couleur ou de luminance et est renvoyé sous forme de canal alpha associé : les canaux de couleur/gris sont mis à l'échelle (pré-multipliés) par la valeur alpha.

Les échantillons sont soit contenus directement dans les données de l'image, entre 1 et 8 octets par pixel selon l'encodage, soit stockés dans une palette de couleurs indexée par des octets dans les données de l'image. Dans le cas d'une palette de couleurs, les entrées de la palette sont des échantillons individuels, encodés comme ci-dessus, et les données de l'image ont un octet par pixel pour sélectionner l'échantillon pertinent dans la palette de couleurs.

Les #defines à utiliser dans png_image::format. Chaque #define identifie une disposition particulière des données de canal et, le cas échéant, des valeurs alpha. Il existe des définitions séparées pour chacun des deux encodages de composants.

Un format est construit à l'aide de valeurs de drapeaux à un seul bit. Toutes les combinaisons sont valides. Les formats peuvent être construits à partir des valeurs de drapeaux ou vous pouvez utiliser l'une des valeurs prédéfinies ci-dessous. PNG_IMAGE_FLAG_*

Les indicateurs contenant des informations supplémentaires sur l'image sont stockés dans le champ 'flags' de png_image.


PNG_IMAGE_FLAG_COLORSPACE_NOT_sRGB == 0x01
Ceci indique que les valeurs RVB du bitmap en mémoire ne
correspondent pas aux points d'extrémité rouge, vert et bleu définis par sRGB.


PNG_IMAGE_FLAG_FAST == 0x02
À l'écriture, privilégier la vitesse à la compression ; le fichier PNG résultant sera
plus grand mais sera produit de manière significativement plus rapide, en particulier pour les grandes
images. N'utilisez pas cette option pour les images qui seront distribuées, utilisez-la
uniquement lors de la production de fichiers intermédiaires qui seront lus et réécrits
de manière répétée. Pour une image typique de 24 bits, l'option doublera la vitesse de lecture
au prix d'une augmentation de 25% de la taille de l'image, cependant pour de nombreuses
images plus compressibles, le fichier PNG peut être 10 fois plus grand avec seulement un
léger gain de vitesse.

les images produites par l'API simplifiée ont toujours des informations gamma ; la définition
de cet indicateur n'affecte que l'interprétation des images 16 bits provenant d'une
source externe. Il est recommandé que l'application expose cet indicateur
à l'utilisateur ; l'utilisateur peut normalement facilement reconnaître la différence entre
l'encodage linéaire et sRGB. Cet indicateur n'a aucun effet à l'écriture - les données
passées aux API d'écriture doivent avoir le bon encodage (tel que défini
ci-dessus.)


Si l'indicateur n'est pas défini (par défaut), les données entrantes de 16 bits par composant sont
supposées être linéaires.

VI. Modification/Personnalisation de libpng

Il y a deux problèmes ici. Le premier consiste à modifier la manière dont libpng effectue des opérations standard comme l'allocation de mémoire, l'entrée/sortie et la gestion des erreurs. Le second concerne des aspects plus complexes tels que l'ajout de nouvelles clés, de nouvelles transformations et la modification générale du fonctionnement de libpng. Ces deux aspects sont des problèmes de compilation ; c'est-à-dire qu'ils sont généralement déterminés au moment de la rédaction du code, et il est rarement nécessaire de fournir à l'utilisateur un moyen de les modifier.

Allocation de mémoire, entrée/sortie et gestion des erreurs

Toute l'allocation de mémoire, l'entrée/sortie et la gestion des erreurs dans libpng passent par des rappels (callbacks) configurables par l'utilisateur. Les routines par défaut se trouvent respectivement dans pngmem.c, pngrio.c, pngwio.c et pngerror.c. Pour modifier ces fonctions, appelez la fonction appropriée png_set_*_fn().

L'allocation de mémoire est effectuée par les fonctions png_malloc(), png_calloc() et png_free(). Les fonctions png_malloc() et png_free() appellent actuellement les fonctions C standard et png_calloc() appelle png_malloc() puis efface la mémoire nouvellement allouée à zéro ; notez que png_calloc(png_ptr, size) n'est pas la même chose que la fonction calloc(nombre, taille) fournie par stdlib.h. Il existe un support limité pour certains systèmes avec des architectures de mémoire segmentée et les types de pointeurs déclarés par png.h correspondent à cela ; vous devrez utiliser les pointeurs appropriés dans votre application. Si vous préférez utiliser une méthode différente pour allouer et libérer des données, vous pouvez utiliser png_create_read_struct_2() ou png_create_write_struct_2() pour enregistrer vos propres fonctions comme décrit ci-dessus. Ces fonctions fournissent également un pointeur void qui peut être récupéré via


mem_ptr = png_get_mem_ptr(png_ptr);

Vos fonctions de mémoire de remplacement doivent avoir les prototypes suivants :


png_voidp malloc_fn(png_structp png_ptr,
png_alloc_size_t size);


void free_fn(png_structp png_ptr, png_voidp ptr);

Votre malloc_fn() doit retourner NULL en cas d'échec. La fonction png_malloc() appellera normalement png_error() si elle reçoit un NULL de l'allocateur mémoire système ou de votre remplacement malloc_fn().

Votre free_fn() ne sera jamais appelée avec un pointeur NULL, car png_free() de libpng vérifie la valeur NULL avant d'appeler free_fn().

L'entrée/sortie dans libpng est effectuée via png_read() et png_write(), qui appellent actuellement fread() et fwrite(). Le FILE * est stocké dans png_struct et est initialisé via png_init_io(). Si vous souhaitez modifier la méthode d'E/S, la bibliothèque fournit des rappels que vous pouvez définir via la fonction png_set_read_fn() et png_set_write_fn() au moment de l'exécution, au lieu d'appeler la fonction png_init_io(). Ces fonctions fournissent également un pointeur void qui peut être récupéré via la fonction png_get_io_ptr(). Par exemple :


png_set_read_fn(png_structp read_ptr,
voidp read_io_ptr, png_rw_ptr read_data_fn)


png_set_write_fn(png_structp write_ptr,
voidp write_io_ptr, png_rw_ptr write_data_fn,
png_flush_ptr output_flush_fn);


voidp read_io_ptr = png_get_io_ptr(read_ptr);
voidp write_io_ptr = png_get_io_ptr(write_ptr);

Les fonctions d'E/S de remplacement doivent avoir les prototypes suivants :


void user_read_data(png_structp png_ptr,
png_bytep data, size_t length);


void user_write_data(png_structp png_ptr,
png_bytep data, size_t length);


void user_flush_data(png_structp png_ptr);

La fonction user_read_data() est responsable de la détection et de la gestion des erreurs de fin de données.

Fournir NULL pour les fonctions de lecture, d'écriture ou de vidage les remet à utiliser les fonctions de flux C par défaut, qui attendent que io_ptr pointe vers une structure *FILE standard. Il est probablement erroné d'utiliser NULL pour l'une des fonctions write_data_fn et output_flush_fn mais pas les deux, à moins que vous n'ayez compilé libpng avec PNG_NO_WRITE_FLUSH défini. Il est erroné de lire à partir d'un flux d'écriture, et vice versa.

La gestion des erreurs dans libpng est effectuée via png_error() et png_warning(). Les erreurs gérées via png_error() sont fatales, ce qui signifie que png_error() ne doit jamais retourner à son appelant. Actuellement, cela est géré via setjmp() et longjmp() (sauf si vous avez compilé libpng avec PNG_NO_SETJMP, auquel cas c'est géré via PNG_ABORT()), mais vous pourriez modifier cela pour faire des choses comme exit() si vous le souhaitez, tant que votre fonction ne retourne pas.

En cas d'erreurs non fatales, png_warning() est appelée pour afficher un message d'avertissement, puis le contrôle retourne au code appelant. Par défaut, png_error() et png_warning() affichent un message sur stderr via fprintf() à moins que la bibliothèque ne soit compilée avec PNG_NO_CONSOLE_IO défini (parce que vous ne voulez pas des messages) ou PNG_NO_STDIO défini (parce que fprintf() n'est pas disponible). Si vous souhaitez modifier le comportement des fonctions d'erreur, vous devrez configurer vos propres rappels de message. Ces fonctions sont normalement fournies au moment de la création de png_struct. Il est également possible de rediriger les erreurs et les avertissements vers vos propres fonctions de remplacement après que png_create_*_struct() ait été appelé en appelant :


png_set_error_fn(png_structp png_ptr,
png_voidp error_ptr, png_error_ptr error_fn,
png_error_ptr warning_fn);

Si NULL est fourni pour error_fn ou warning_fn, alors la fonction par défaut de libpng sera utilisée, appelant fprintf() et/ou longjmp() si un problème est rencontré. Les fonctions d'erreur de remplacement doivent avoir les paramètres suivants :


void user_error_fn(png_structp png_ptr,
png_const_charp error_msg);


void user_warning_fn(png_structp png_ptr,
png_const_charp warning_msg);

Ensuite, dans votre user_error_fn ou user_warning_fn, vous pouvez récupérer error_ptr si vous en avez besoin, en appelant


png_voidp error_ptr = png_get_error_ptr(png_ptr);

La motivation derrière l'utilisation de setjmp() et longjmp() est les méthodes de gestion des exceptions throw et catch de C++. Cela rend le code beaucoup plus facile à écrire, car il n'est pas nécessaire de vérifier chaque code de retour de chaque appel de fonction. Cependant, il y a des incertitudes quant à l'état des variables locales après un longjmp, donc l'utilisateur peut vouloir être prudent quant à toute action après le retour de setjmp non nul, à part retourner lui-même. Consultez la documentation de votre compilateur pour plus de détails. Pour une approche alternative, vous pourriez vouloir utiliser la fonction "cexcept" (voir https://cexcept.sourceforge.io/), qui est illustrée dans pngvalid.c et dans contrib/visupng.

À partir de libpng-1.4.0, l'API png_set_benign_errors() est devenue disponible. Vous pouvez l'utiliser pour traiter certaines erreurs (normalement traitées comme des erreurs) comme des avertissements.


png_set_benign_errors (png_ptr, int allowed);


allowed : 0 : traite png_benign_error() comme une erreur.
1 : traite png_benign_error() comme un avertissement.

À partir de libpng-1.6.0, la condition par défaut est de traiter les erreurs bénignes comme des avertissements lors de la lecture et comme des erreurs lors de l'écriture.

Clés personnalisées

Si vous avez besoin de lire ou d'écrire des clés personnalisées, vous pourriez avoir besoin d'approfondir le code de libpng. La bibliothèque dispose désormais de mécanismes pour stocker et écrire des clés de type inconnu ; vous pouvez même déclarer des rappels pour des clés personnalisées. Cependant, cela pourrait ne pas être suffisant si le code de la bibliothèque lui-même a besoin de connaître les interactions entre votre clé et les clés 'intrinsèques' existantes.

Si vous avez besoin d'écrire une nouvelle clé intrinsèque, lisez d'abord la spécification PNG. Acquérir une première compréhension de son fonctionnement. Portez une attention particulière aux sections qui décrivent les noms des clés, et regardez comment les autres clés ont été conçues, afin de faire les choses de manière similaire. Deuxièmement, consultez les sections de libpng qui lisent et écrivent des clés. Essayez de trouver une clé similaire à la vôtre et utilisez-la comme modèle. Plus de détails peuvent être trouvés dans les commentaires à l'intérieur du code. Il est préférable de gérer les clés privées ou inconnues de manière générique, via des fonctions de rappel, plutôt qu'en modifiant les fonctions de libpng. Ceci est illustré dans pngtest.c, qui utilise une fonction de rappel pour gérer une clé privée "vpAg" et la nouvelle clé "sTER", qui sont toutes deux inconnues de libpng.

Si vous souhaitez écrire votre propre transformation pour les données, parcourez la partie du code qui effectue les transformations, et examinez certaines des transformations les plus simples pour avoir une idée de leur fonctionnement. Essayez de trouver une transformation similaire à celle que vous souhaitez ajouter et copiez-la. Plus de détails peuvent être trouvés dans les commentaires à l'intérieur du code lui-même.

Configuration pour les plateformes graphiques/de fenêtrage :

Vous devrez écrire de nouvelles fonctions d'erreur et d'avertissement qui utilisent l'interface graphique, comme décrit précédemment, et les définir comme fonctions d'erreur et d'avertissement au moment où png_create_*_struct() est appelé, afin de les avoir disponibles pendant l'initialisation de la structure. Elles peuvent être modifiées ultérieurement via png_set_error_fn(). Sur certains compilateurs, vous pourriez également avoir à modifier les allocateurs mémoire (png_malloc, etc.).

Configuration de zlib :

Il existe des fonctions spéciales pour configurer la compression. La plus utile change probablement le niveau de compression, qui utilise actuellement des valeurs de compression d'entrée dans la plage 0 - 9. La bibliothèque utilise normalement le niveau de compression par défaut (Z_DEFAULT_COMPRESSION = 6). Des tests ont montré que pour une grande majorité d'images, les valeurs de compression dans la plage 3-6 compressent presque aussi bien que les niveaux supérieurs, et ce, beaucoup plus rapidement. Pour les applications en ligne, il peut être souhaitable d'avoir une vitesse maximale (Z_BEST_SPEED = 1). Avec les versions de zlib après v0.99, vous pouvez également spécifier aucune compression (Z_NO_COMPRESSION = 0), mais cela créerait des fichiers plus grands que simplement s

toring le bitmap brut. Vous pouvez spécifier le niveau de compression en appelant :


#include zlib.h
png_set_compression_level(png_ptr, level);

Une autre fonction utile permet de réduire la quantité de mémoire utilisée par la bibliothèque. Le niveau de mémoire est par défaut à 8, mais il peut être abaissé si vous manquez de mémoire (en utilisant DOS, par exemple, où vous n'avez que 640K). Notez que le niveau de mémoire a un effet sur la compression ; entre autres choses, des niveaux plus bas entraîneront l'émission de sections de données incompressibles dans des blocs stockés plus petits, avec une surcharge relative proportionnellement plus grande allant jusqu'à 15% dans le pire des cas.


#include zlib.h
png_set_compression_mem_level(png_ptr, level);

Les autres fonctions servent à configurer zlib. Leur utilisation n'est pas recommandée pour un usage normal et peut entraîner la création d'un fichier PNG invalide. Voir zlib.h pour plus d'informations sur ce qu'elles signifient.


#include zlib.h
png_set_compression_strategy(png_ptr,
strategy);


png_set_compression_window_bits(png_ptr,
window_bits);


png_set_compression_method(png_ptr, method);

Ceci contrôle la taille des blocs IDAT (par défaut 8192) :


png_set_compression_buffer_size(png_ptr, size);

À partir de la version 1.5.4 de libpng, des API supplémentaires sont disponibles pour définir ces paramètres séparément pour les blocs compressés non-IDAT tels que zTXt, iTXt et iCCP :


#include zlib.h
#if PNG_LIBPNG_VER >= 10504
png_set_text_compression_level(png_ptr, level);


png_set_text_compression_mem_level(png_ptr, level);


png_set_text_compression_strategy(png_ptr,
strategy);


png_set_text_compression_window_bits(png_ptr,
window_bits);


png_set_text_compression_method(png_ptr, method);
#endif

Contrôle du filtrage des lignes

Si vous souhaitez contrôler si libpng utilise le filtrage ou non, quels filtres sont utilisés et comment il choisit les filtres de ligne, vous pouvez appeler l'une de ces fonctions. La sélection et la configuration des filtres de ligne peuvent avoir un impact significatif sur la taille et la vitesse d'encodage, et un impact légèrement moindre sur la vitesse de décodage d'une image. Le filtrage est activé par défaut pour les images RVB et en niveaux de gris (avec et sans alpha), mais pas pour les images avec palette ni pour les images dont la profondeur de bits est inférieure à 8 bits/pixel.

Le paramètre 'method' définit la méthode de filtrage principale, qui est actuellement seulement '0' dans la spécification PNG 1.2. Le paramètre 'filters' définit quels filtres, le cas échéant, doivent être utilisés pour chaque ligne de balayage. Les valeurs possibles sont PNG_ALL_FILTERS, PNG_NO_FILTERS ou PNG_FAST_FILTERS pour activer ou désactiver le filtrage, ou pour activer uniquement l'ensemble de filtres à décodage rapide, respectivement.

Les types de filtres individuels sont PNG_FILTER_NONE, PNG_FILTER_SUB, PNG_FILTER_UP, PNG_FILTER_AVG, PNG_FILTER_PAETH, qui peuvent être combinés par un OU bit à bit ('|') pour spécifier un ou plusieurs filtres à utiliser. Ces filtres sont décrits plus en détail dans la spécification PNG. Si vous avez l'intention de changer le type de filtre pendant l'écriture de l'image, vous devriez commencer avec les drapeaux configurés pour tous les filtres que vous avez l'intention d'utiliser afin que libpng puisse initialiser ses structures internes de manière appropriée pour tous les types de filtres. (Notez que cela signifie que la première ligne doit toujours être filtrée de manière adaptative, car libpng n'alloue pas les tampons de filtre tant que png_write_row() n'est pas appelé pour la première fois.)


filters = PNG_NO_FILTERS;
filters = PNG_ALL_FILTERS;
filters = PNG_FAST_FILTERS;


ou


filters = PNG_FILTER_NONE | PNG_FILTER_SUB |
PNG_FILTER_UP | PNG_FILTER_AVG |
PNG_FILTER_PAETH;


png_set_filter(png_ptr, PNG_FILTER_TYPE_BASE,
filters);


Le deuxième paramètre peut aussi être
PNG_INTRAPIXEL_DIFFERENCING si vous écrivez
un PNG à intégrer dans un flux de données MNG.
Ce paramètre doit être identique à la valeur de
filter_method utilisée dans png_set_IHDR().

Demande d'affichage de débogage

La définition de macro PNG_DEBUG peut être utilisée pour demander un affichage de débogage. Définissez-la à une valeur entière comprise entre 0 et 3. Des nombres plus élevés entraînent une quantité croissante d'informations de débogage. Les informations sont imprimées sur le fichier "stderr", à moins qu'un autre nom de fichier ne soit spécifié dans la définition de macro PNG_DEBUG_FILE.

Lorsque PNG_DEBUG > 0, les fonctions (macros) suivantes deviennent disponibles :


png_debug(level, message)
png_debug1(level, message, p1)
png_debug2(level, message, p1, p2)

dans lesquels "level" est comparé à PNG_DEBUG pour décider s'il faut imprimer le message, "message" est la chaîne formatée à imprimer, et p1 et p2 sont des paramètres à intégrer dans la chaîne selon des directives de formatage de type printf. Par exemple,


png_debug1(2, "foo=%d", foo);

est développé en


if (PNG_DEBUG > 2)
fprintf(PNG_DEBUG_FILE, "foo=%d\n", foo);

Lorsque PNG_DEBUG est défini mais vaut zéro, les macros ne sont pas définies, mais vous pouvez toujours utiliser PNG_DEBUG pour contrôler votre propre débogage :


#ifdef PNG_DEBUG
fprintf(stderr, ...);
#endif

Lorsque PNG_DEBUG = 1, les macros sont définies, mais seules les instructions png_debug ayant un niveau = 0 seront imprimées. Il n'y a aucune de ces instructions dans cette version de libpng, mais si vous en insérez, elles seront imprimées.

VII. Prise en charge de MNG

La spécification MNG (disponible à http://www.libpng.org/pub/mng) permet certaines extensions de PNG pour les images PNG intégrées dans des flux de données MNG. Libpng peut prendre en charge certaines de ces extensions. Pour les activer, utilisez la fonction png_permit_mng_features() :


feature_set = png_permit_mng_features(png_ptr, mask)


mask est un png_uint_32 contenant le OU bit à bit des
fonctionnalités que vous souhaitez activer. Celles-ci incluent
PNG_FLAG_MNG_EMPTY_PLTE
PNG_FLAG_MNG_FILTER_64
PNG_ALL_MNG_FEATURES


feature_set est un png_uint_32 qui est le ET bit à bit de
votre masque avec l'ensemble des fonctionnalités MNG prises en charge
par la version de libpng que vous utilisez.

Il est erroné d'utiliser cette fonction lors de la lecture ou de l'écriture d'un fichier PNG autonome avec la signature PNG de 8 octets. Le flux de données PNG doit être encapsulé dans un flux de données MNG. Au minimum, il doit contenir la signature MNG de 8 octets et les blocs MHDR et MEND. Libpng ne fournit pas de prise en charge pour ces blocs ou tout autre bloc MNG ; votre application doit fournir sa propre prise en charge. Vous pourriez envisager d'utiliser libmng (disponible à https://www.libmng.com/) à la place.

VIII. Modifications de Libpng depuis la version 0.88

Il convient de noter que les versions de libpng ultérieures à 0.96 ne sont pas distribuées par l'auteur original de libpng, Guy Schalnat, ni par Andreas Dilger, qui avait pris la relève de Guy en 1996 et 1997, et distribué les versions 0.89 à 0.96, mais plutôt par un autre membre du groupe PNG original, Glenn Randers-Pehrson. Guy et Andreas sont toujours vivants et en bonne santé, mais ils sont passés à d'autres choses.

Les anciennes fonctions libpng png_read_init(), png_write_init(), png_info_init(), png_read_destroy(), et png_write_destroy() ont été déplacées vers PNG_INTERNAL dans la version 0.95 pour décourager leur utilisation. Ces fonctions seront supprimées de la version 1.4.0 de libpng.

La méthode préférée pour créer et initialiser les structures libpng est via png_create_read_struct(), png_create_write_struct(), et png_create_info_struct() car elles isolent la taille des structures de l'application, permettent la vérification des erreurs de version, et permettent également l'utilisation de routines de gestion d'erreurs personnalisées pendant l'initialisation, ce que les anciennes fonctions ne font pas. Les fonctions png_read_destroy() et png_write_destroy() ne libèrent pas réellement la mémoire que libpng a allouée pour ces structures, mais réinitialisent simplement les structures de données, elles peuvent donc être utilisées à la place de png_destroy_read_struct() et png_destroy_write_struct() si vous estimez qu'il y a trop de surcharge système à allouer et libérer le png_struct pour chaque image lue.

La configuration des rappels d'erreur via png_set_message_fn() avant png_read_init() comme suggéré dans libpng-0.88 n'est plus prise en charge car cela provoquait des échecs des applications qui n'utilisent pas de fonctions d'erreur personnalisées si le png_ptr n'était pas initialisé à zéro. Il est toujours possible de configurer les rappels d'erreur APRÈS png_read_init(), ou de les modifier avec png_set_error_fn(), qui est essentiellement la même fonction, mais avec un nouveau nom pour forcer des erreurs de compilation avec les applications qui essaient d'utiliser l'ancienne méthode.

La prise en charge des blocs sCAL, iCCP, iTXt et sPLT a été ajoutée dans libpng-1.0.6 ; cependant, la prise en charge de iTXt n'était pas activée par défaut.

À partir de la version 1.0.7, vous pouvez connaître la version de la bibliothèque que vous utilisez à l'exécution :


png_uint_32 libpng_vn = png_access_version_number();

Le nombre libpng_vn est construit à partir de la version majeure, de la version mineure avec zéro initial (leader zero) et du numéro de publication avec zéro initial (leader zero) (par exemple, libpng_vn pour la version 1.0.7 est 10007).

Notez que cette fonction ne prend pas de png_ptr, vous pouvez donc l'appeler avant d'en avoir créé un.

Vous pouvez également vérifier quelle version de png.h vous avez utilisée lors de la compilation de votre application :


png_uint_32 application_vn = PNG_LIBPNG_VER;

Nous avons supprimé les fonctions stub obsolètes png_get_mmx_flagmask(), png_set_mmx_thresholds(), png_get_asm_flags(), png_get_mmx_bitdepth_threshold(), png_get_mmx_rowbytes_threshold(), png_set_asm_flags() et png_mmx_supported()

Nous avons supprimé les fonctions obsolètes png_check_sig(), png_memcpy_check() et png_memset_check(). Utilisez plutôt respectivement png_sig_cmp() == 0, memcpy() et memset().

La fonction png_set_gray_1_2_4_to_8() a été supprimée. Elle est dépréciée depuis libpng-1.0.18 et 1.2.9, où elle a été remplacée par png_set_expand_gray_1_2_4_to_8() car la première fonction étendait également tout bloc tRNS à un canal alpha.

Les macros pour png_get_uint_16, png_get_uint_32 et png_get_int_32 ont été ajoutées et sont utilisées par défaut à la place des fonctions correspondantes. Malheureusement, de libpng-1.4.0 à 1.4.4, la macro png_get_uint_16 (mais pas la fonction) renvoyait incorrectement une valeur de type png_uint_32.

Nous avons modifié le prototype de png_malloc() de
png_malloc(png_structp png_ptr, png_uint_32 size) à
png_malloc(png_structp png_ptr, png_alloc_size_t size)

Cela s'applique également au prototype de la fonction de remplacement par l'utilisateur malloc_fn().

La fonction png_calloc() a été ajoutée et est utilisée à la place de « png_malloc(); memset(); » sauf dans le cas de png_read_png() où le tableau est composé de pointeurs ; dans ce cas, une boucle « for » est utilisée après png_malloc() pour définir les pointeurs à NULL, afin d'assurer un comportement robuste au cas où l'application manquerait de mémoire en cours de traitement.

Nous avons modifié les prototypes de png_get_compression_buffer_size() et png_set_compression_buffer_size() pour qu'ils fonctionnent avec size_t au lieu de png_uint_32.

La prise en charge des messages d'erreur numérotés a été supprimée par défaut, car nous n'avons jamais réussi à numéroter réellement les messages d'erreur. La fonction png_set_strip_error_numbers() a été supprimée de la bibliothèque par défaut.

Les fonctions png_zalloc() et png_zfree() ne sont plus exportées. La fonction png_zalloc() ne zéroise plus la mémoire qu'elle alloue. Les applications qui appelaient png_zalloc(png_ptr, nombre, taille) peuvent appeler png_calloc(png_ptr, nombre*taille) à la place, et peuvent appeler png_free() à la place de png_zfree().

La prise en charge du tramage a été désactivée par défaut dans libpng-1.4.0, car elle n'a pas été bien testée et ne fait pas réellement de « tramage ». Le code n'a cependant pas été supprimé et pouvait être activé en compilant libpng avec PNG_READ_DITHER_SUPPORTED défini. Dans libpng-1.4.2, cette prise en charge a été réactivée, mais la fonction a été renommée png_set_quantize() pour refléter plus précisément ce qu'elle fait réellement. Dans le même temps, les macros PNG_DITHER_[RED,GREEN_BLUE]_BITS ont également été renommées en PNG_QUANTIZE_[RED,GREEN,BLUE]_BITS, et PNG_READ_DITHER_SUPPORTED a été renommée en PNG_READ_QUANTIZE_SUPPORTED.

Nous avons supprimé le '.' final des messages d'avertissement et d'erreur.

VI. Changements apportés à Libpng entre les versions 1.4.x et 1.5.x

De libpng-1.4.0 à 1.4.4, la macro png_get_uint_16 (mais pas la fonction) renvoyait incorrectement une valeur de type png_uint_32. La macro incorrecte a été supprimée de libpng-1.4.5.

La vérification des index de palette invalides lors de l'écriture a été ajoutée dans libpng 1.5.10. Si un pixel contient un index invalide (hors limites), libpng émet une erreur bénigne. Ceci est activé par défaut car cette condition est une erreur selon la spécification PNG, Clause 11.3.2, mais l'erreur peut être ignorée dans chaque png_ptr avec


png_set_check_for_invalid_index(png_ptr, allowed);


allowed - l'un des éléments suivants
0: désactive l'erreur bénigne (accepte les
données invalides sans avertissement).
1: active l'erreur bénigne (traite les
données invalides comme une erreur ou un
avertissement).

Si l'erreur est ignorée, ou si png_benign_error() la traite comme un avertissement, les pixels invalides sont décodés comme du noir opaque par le décodeur et écrits tels quels par l'encodeur.

La récupération de l'index de palette maximum trouvé a été ajoutée dans libpng-1.5.15. Cette instruction doit apparaître après png_read_png() ou png_read_image() lors de la lecture, et après png_write_png() ou png_write_image() lors de l'écriture.


int max_palette = png_get_palette_max(png_ptr, info_ptr);

Ceci renverra l'index de palette maximum trouvé dans l'image, ou « -1 » si la palette n'a pas été vérifiée, ou « 0 » si aucune palette n'a été trouvée. Notez que cela ne tient pas compte de l'index de palette utilisé par les blocs auxiliaires tels que le bloc bKGD ; vous devez les vérifier séparément pour déterminer l'index de palette maximum réellement utilisé.

Il n'y a pas de changements d'API substantiels entre les parties non dépréciées de l'API 1.4.5 et l'API 1.5.0 ; cependant, la possibilité d'accéder directement aux membres des structures de contrôle principales de libpng, png_struct et png_info, dépréciée dans les versions antérieures de libpng, a été complètement supprimée de libpng 1.5, et de nouveaux fichiers d'en-tête privés « pngstruct.h », « pnginfo.h » et « pngdebug.h » ont été créés.

Nous n'incluons plus zlib.h dans png.h. L'instruction d'inclusion a été déplacée vers pngstruct.h, où elle n'est pas accessible par les applications. Les applications qui ont besoin d'accéder aux informations de zlib.h devront ajouter la directive '#include "zlib.h"'. Il n'a pas d'importance si celle-ci est placée avant ou après la directive '#include png.h'.

Les macros png_sprintf(), png_strcpy() et png_strncpy() ne sont plus utilisées et ont été supprimées.

Nous avons déplacé png_strle

n(), png_memcpy(), png_memset(), et png_memcmp() dans un fichier d'en-tête privé (pngpriv.h) qui n'est pas accessible aux applications.

Dans png_get_iCCP, le type de "profile" a été changé de png_charpp à png_bytepp, et dans png_set_iCCP, de png_charp à png_const_bytep.

Il y a des changements de forme dans png.h, incluant de nouvelles macros et des macros modifiées pour déclarer des parties de l'API. Certaines fonctions de l'API avec des arguments qui sont des pointeurs vers des données non modifiées à l'intérieur de la fonction ont été corrigées pour déclarer ces arguments avec const.

Une grande partie de l'utilisation interne des macros C pour contrôler la construction de la bibliothèque a également changé et une partie de cela est visible dans les fichiers d'en-tête exportés, en particulier l'utilisation de macros pour contrôler les données et les éléments de l'API visibles lors de la compilation de l'application peut nécessiter une révision significative du code de l'application. (Il est extrêmement rare qu'une application fasse cela.)

Tout programme qui a compilé contre libpng 1.4 et n'a pas utilisé de fonctionnalités obsolètes ou accédé à des structures internes de la bibliothèque devrait compiler et fonctionner contre libpng 1.5, à l'exception du changement dans le prototype des fonctions de l'API png_get_iCCP() et png_set_iCCP() mentionné ci-dessus.

libpng 1.5.0 ajoute les macros PNG_ PASS pour aider à la lecture et à l'écriture d'images entrelacées. Les macros retournent le nombre de lignes et de colonnes dans chaque passe et des informations qui peuvent être utilisées pour désentrelacer et (si absolument nécessaire) entrelacer une image.

libpng 1.5.0 ajoute une API png_longjmp(png_ptr, value). Cette API appelle le png_longjmp_ptr fourni par l'application sur le tampon de longjmp interne, mais initialisé par l'application. Elle est fournie comme une commodité pour éviter le besoin d'utiliser la macro png_jmpbuf, qui avait l'effet secondaire inutile de réinitialiser la valeur interne de png_longjmp_ptr.

libpng 1.5.0 inclut une API complète en virgule fixe. Par défaut, elle est présente avec l'API correspondante en virgule flottante. En général, l'API en virgule fixe est plus rapide et plus petite que celle en virgule flottante car le format de fichier PNG utilisait la virgule fixe, pas la virgule flottante. Cela s'applique même si la bibliothèque utilise la virgule flottante dans les calculs internes. Une nouvelle macro, PNG_FLOATING_ARITHMETIC_SUPPORTED, révèle si la bibliothèque utilise l'arithmétique en virgule flottante (par défaut) ou en virgule fixe en interne pour les calculs critiques en termes de performances tels que la correction gamma. Dans certains cas, les calculs gamma peuvent produire des résultats légèrement différents. Cela a modifié les résultats dans png_rgb_to_gray et dans la composition alpha (png_set_background par exemple). Cela s'applique même si l'image d'origine était déjà linéaire (gamma == 1.0) et, par conséquent, il n'est pas nécessaire de linéariser l'image. C'est parce que libpng n'a pas été modifiée pour optimiser correctement ce cas, pas encore.

Le support en virgule fixe pour le chunk sCAL est assorti d'une remarque importante ; la spécification sCAL utilise un encodage décimal des valeurs en virgule flottante et la précision des valeurs en virgule fixe PNG est insuffisante pour représenter ces valeurs. Par conséquent, une API de "chaîne" (png_get_sCAL_s et png_set_sCAL_s) est le seul moyen fiable de lire des chunks sCAL arbitraires en l'absence de l'API en virgule flottante ou des calculs internes en virgule flottante. À partir de libpng-1.5.0, ces deux fonctions sont présentes lorsque PNG_sCAL_SUPPORTED est défini. Avant libpng-1.5.0, leur présence dépendait également de la définition de PNG_FIXED_POINT_SUPPORTED et de la non-définition de PNG_FLOATING_POINT_SUPPORTED.

Les applications n'ont plus besoin d'inclure le fichier d'en-tête de distribution optionnel pngusr.h ou de définir les macros correspondantes lors de la compilation de l'application pour voir la bonne variante de l'API libpng. À partir de 1.5.0, le code de l'application peut vérifier la macro _SUPPORTED correspondante :

#ifdef PNG_INCH_CONVERSIONS_SUPPORTED
/* code qui utilise les API de conversion en pouces. */ #endif

Cette macro ne sera définie que si les fonctions de conversion en pouces ont été compilées dans libpng. L'ensemble complet des macros, et si le support a été compilé ou non, sont disponibles dans le fichier d'en-tête pnglibconf.h. Ce fichier d'en-tête est spécifique à la compilation de libpng. Notez qu'avant 1.5.0, les macros _SUPPORTED auraient toujours la définition par défaut à moins d'être réinitialisées par pngusr.h ou par des réglages explicites sur la ligne de commande du compilateur. Ces réglages peuvent produire des avertissements ou des erreurs de compilation dans 1.5.0 en raison de la redéfinition des macros.

Les applications peuvent maintenant choisir si elles veulent utiliser ces macros ou appeler la fonction correspondante en définissant PNG_USE_READ_MACROS ou PNG_NO_USE_READ_MACROS avant d'inclure png.h. Notez que ce n'est supporté qu'à partir de 1.5.0 ; définir PNG_NO_USE_READ_MACROS avant 1.5.0 entraînera un échec de liaison.

Avant libpng-1.5.4, le compresseur zlib utilisait le même ensemble de paramètres lors de la compression des données IDAT et des données textuelles telles que zTXt et iCCP. Dans libpng-1.5.4, nous avons réinitialisé le flux zlib pour chaque type de données. Nous avons ajouté cinq fonctions png_set_text_*() pour définir les paramètres à utiliser avec les données textuelles.

Avant libpng-1.5.4, l'option PNG_READ_16_TO_8_ACCURATE_SCALE_SUPPORTED était désactivée par défaut, et une mise à l'échelle légèrement inexacte se produisait. Cette option ne peut plus être désactivée, et le choix de la mise à l'échelle 16 vers 8 précise ou inexacte se fait en utilisant la nouvelle API png_set_scale_16_to_8() pour une mise à l'échelle précise ou l'ancienne API png_set_strip_16_to_8() pour un simple découpage. Dans libpng-1.5.4, la macro PNG_READ_16_TO_8_ACCURATE_SCALE_SUPPORTED est devenue PNG_READ_SCALE_16_TO_8_SUPPORTED, et la macro PNG_READ_16_TO_8 est devenue PNG_READ_STRIP_16_TO_8_SUPPORTED, pour activer séparément les deux fonctions png_set_*_16_to_8().

Avant libpng-1.5.4, la fonction png_set_user_limits() ne pouvait être utilisée que pour réduire les limites de largeur et de hauteur par rapport à la valeur de PNG_USER_WIDTH_MAX et PNG_USER_HEIGHT_MAX, bien que ce document dise qu'elle pouvait être utilisée pour les remplacer. Désormais, cette fonction réduira ou augmentera les limites.

À partir de libpng-1.5.22, des limites utilisateur par défaut ont été établies. Celles-ci peuvent être remplacées par des appels d'application à png_set_user_limits(), png_set_user_chunk_cache_max(), et/ou png_set_user_malloc_max(). Les limites sont maintenant
maximum possible par défaut
png_user_width_max 0x7fffffff 1 000 000
png_user_height_max 0x7fffffff 1 000 000
png_user_chunk_cache_max 0 (illimité) 1000
png_user_chunk_malloc_max 0 (illimité) 8 000 000

La fonction png_set_option() (et le membre "options" de la structure png) a été ajoutée à libpng-1.5.15, avec l'option PNG_ARM_NEON.

La bibliothèque prend maintenant en charge une implémentation complète en virgule fixe et peut donc être utilisée sur des systèmes qui n'ont pas de support en virgule flottante ou un support très limité ou lent. Auparavant, la correction gamma, partie essentielle du support complet PNG, nécessitait une virgule flottante raisonnablement rapide.

Dans ce cadre, le mécanisme exact utilisé pour contrôler les attributs des fonctions de l'API a changé, comme décrit dans le fichier INSTALL.

Un nouveau programme de test, pngvalid, est fourni en plus de pngtest. pngvalid valide la précision arithmétique des calculs de correction gamma et comprend un certain nombre de validations du format de fichier. Un sous-ensemble de la gamme complète de tests est exécuté lorsque "make check" est effectué (dans la construction 'configure'.) pngvalid permet également d'évaluer l'utilisation totale de la mémoire allouée et effectue une validation supplémentaire des dépassements de mémoire.

De nombreux changements ont été apportés aux macros de fonctionnalités individuelles. Les changements suivants sont ceux qui seront les plus probablement remarqués par les constructeurs de bibliothèques qui configurent libpng :

1) Toutes les macros de fonctionnalités ont maintenant des noms cohérents :

#define PNG_NO_feature désactive la fonctionnalité #define PNG_feature_SUPPORTED active la fonctionnalité

pnglibconf.h contient une ligne pour chaque macro de fonctionnalité qui est soit :

#define PNG_feature_SUPPORTED

si la fonctionnalité est supportée ou :

/*#undef PNG_feature_SUPPORTED*/

si elle ne l'est pas. Le code de la bibliothèque vérifie systématiquement la macro 'SUPPORTED'. Il ne vérifie pas, et les applications libpng ne devraient pas vérifier, la macro 'NO' qui ne sera normalement pas définie même si la fonctionnalité n'est pas supportée. Les macros 'NO' ne sont utilisées qu'en interne pour définir ou non les macros 'SUPPORTED' correspondantes.

La compatibilité avec les anciens noms est assurée comme suit :

PNG_INCH_CONVERSIONS active PNG_INCH_CONVERSIONS_SUPPORTED

Et les définitions suivantes désactivent la fonctionnalité correspondante :

PNG_SETJMP_NOT_SUPPORTED désactive SETJMP PNG_READ_TRANSFORMS_NOT_SUPPORTED désactive READ_TRANSFORMS PNG_NO_READ_COMPOSITED_NODIV désactive READ_COMPOSITE_NODIV PNG_WRITE_TRANSFORMS_NOT_SUPPORTED désactive WRITE_TRANSFORMS PNG_READ_ANCILLARY_CHUNKS_NOT_SUPPORTED désactive READ_ANCILLARY_CHUNKS PNG_WRITE_ANCILLARY_CHUNKS_NOT_SUPPORTED désactive WRITE_ANCILLARY_CHUNKS

Les constructeurs de bibliothèques devraient supprimer l'utilisation des noms incohérents ci-dessus.

2) Le formatage des messages d'avertissement et d'erreur était auparavant conditionnel à la fonctionnalité STDIO. La bibliothèque a été modifiée pour utiliser la fonctionnalité CONSOLE_IO à la place. Cela signifie que si CONSOLE_IO est désactivé, la bibliothèque n'utilise plus les fonctions printf(3), même si les implémentations de lecture/écriture par défaut utilisent les fonctions stdio.h de style (FILE).

3) Trois macros de fonctionnalités contrôlent maintenant les décisions en virgule fixe/flottante :

PNG_FLOATING_POINT_SUPPORTED active les API en virgule flottante

PNG_FIXED_POINT_SUPPORTED active les API en virgule fixe ; cependant, en pratique, celles-ci sont normalement requises en interne de toute façon (car le format de fichier PNG est en virgule fixe), donc dans la plupart des cas, PNG_NO_FIXED_POINT empêche simplement la fonction d'être exportée.

PNG_FLOATING_ARITHMETIC_SUPPORTED choisit entre l'implémentation interne en virgule flottante ou celle en virgule fixe. Typiquement, l'implémentation en virgule fixe est plus grande et plus lente que l'implémentation en virgule flottante sur un système qui supporte la virgule flottante ; cependant, elle peut être plus rapide sur un système qui manque de matériel en virgule flottante et utilise donc une émulation logicielle.

4) Ajout de PNG_{READ,WRITE}_INT_FUNCTIONS_SUPPORTED. Cela permet de désactiver indépendamment les fonctions de lecture et d'écriture d'entiers de PNG_USE_READ_MACROS, ce qui permet de construire libpng avec les fonctions même si la valeur par défaut est d'utiliser les macros - cela permet aux applications de choisir au moment de la compilation de l'application d'utiliser ou non les macros (auparavant impossible car les fonctions n'étaient pas dans la construction par défaut.)

La condition par défaut pour benign_errors est maintenant de traiter les erreurs bénignes comme des avertissements lors de la lecture et comme des erreurs lors de l'écriture.

La bibliothèque émet maintenant un avertissement si le traitement en arrière-plan et la conversion RVB en niveaux de gris sont utilisés lors de la correction gamma. Comme avec les versions précédentes de la bibliothèque, les résultats sont numériquement très incorrects dans ce cas.

Il y a quelques changements arithmétiques mineurs dans certaines transformations comme png_set_background(), qui pourraient être détectés par certains tests de régression.

La gestion des chunks inconnus a été améliorée en interne, sans changement d'API. Cela ajoute un contrôle d'option plus correct de la gestion des inconnus, corrige un bug préexistant où le paramètre 'keep' par chunk était ignoré, et permet de sauter les chunks IDAT dans le lecteur séquentiel.

png_set_option(png_ptr, PNG_MAXIMUM_INFLATE_WINDOW,

png_user_chunk_malloc_max 8 000 000 illimité

À partir de libpng-1.6.18, une macro PNG_RELEASE_BUILD a été ajoutée, qui permet aux constructeurs de bibliothèques de contrôler la compilation pour un système installé (une compilation de version). Elle peut être définie pour tester les compilations de débogage ou bêta afin de s'assurer qu'elles compileront lorsque le type de compilation sera commuté sur RC ou STABLE. Essentiellement, cela remplace la définition PNG_LIBPNG_BUILD_BASE_TYPE qui n'est pas directement contrôlable par l'utilisateur.

À partir de libpng-1.6.19, tenter de définir un chunk PLTE trop long est une erreur. Auparavant, cette exigence de la spécification PNG n'était pas appliquée, et la palette était toujours limitée à 256 entrées. Un chunk PLTE trop long trouvé dans un PNG d'entrée est silencieusement tronqué.

À partir de libpng-1.6.31, le chunk eXIf est pris en charge. Libpng ne tente pas de décoder le profil Exif ; il retourne simplement un tableau d'octets contenant le profil à l'application appelante qui doit effectuer son propre décodage.

XIII. Détection de libpng

La fonction png_get_io_ptr() est présente depuis libpng-0.88, n'a jamais changé et n'est pas affectée par les macros de compilation conditionnelle. C'est le meilleur choix à utiliser dans les scripts de configuration pour détecter la présence de toute version de libpng depuis 0.88. Dans un "configure.in" autoconf, vous pourriez utiliser


AC_CHECK_LIB(png, png_get_io_ptr, ...)

libpng – un programmeur d'interface de bibliothèque pour la lecture et l'écriture de fichiers Portable Network Graphics (PNG)

SYNOPIS

libpng est une bibliothèque C qui fournit une API pour lire et écrire des fichiers PNG. Il n'y a pas de programme en ligne de commande à appeler directement.

DESCRIPTION

La bibliothèque libpng fournit une interface de programmation d'applications (API) qui permet aux programmes d'écrire et de lire des fichiers au format Portable Network Graphics (PNG). Le format PNG est une spécification ouverte et libre de droits développée par le PNG Development Group. Le format PNG est un format d'image bitmap raster destiné à être utilisé sur le World Wide Web. Il prend en charge la correction gamma, la transparence et les images entrelacées.

La bibliothèque libpng est écrite en langage C ANSI standard. Il est utilisé par de nombreux programmes et bibliothèques graphiques.

Cette page de manuel fait référence à la bibliothèque libpng et à son API. Pour plus d'informations, voir les fichiers d'en-tête et la documentation fournie avec la bibliothèque.

LIBPNG.TXT

Les règles de formatage du code C suivantes sont utilisées dans ce code.

Les commentaires de début de fichier, les commentaires d'en-tête et les commentaires de section de commentaire sont démarrés avec des commentaires C /*, et le texte de commentaire est sur une ligne distincte, avec la première ligne de commentaire précédée d'un astérisque *. La fin de la section de commentaire est marquée par le commentaire C */.

Les commentaires peuvent être placés après la fin de l'instruction à laquelle ils se rapportent :


instruction; /* commentaire */

Nous n'utilisons pas les commentaires de style C++ ("//"). Nous les avons cependant utilisés par le passé dans certains codes d'assemblage MMX maintenant abandonnés.

Les fonctions et leurs accolades ne sont pas indentées, et les fonctions exportées sont marquées avec PNGAPI :


/* Ceci est une fonction publique visible par les
* programmeurs d'applications. Elle fait ceci et cela.
*/
void PNGAPI
png_fonction_exportee(png_ptr, png_info, foo)
{
corps;
}

Le type de retour et les décorations sont placés sur une ligne séparée avant le nom de la fonction, comme illustré ci-dessus.

Les prototypes de toutes les fonctions exportées apparaissent dans png.h, au-dessus du commentaire qui dit


/* Mainteneur : Mettez ici les nouveaux prototypes publics ... */

Nous marquons toutes les fonctions non exportées avec "/* PRIVÉ */" :


void /* PRIVÉ */
png_fonction_non_exportee(png_ptr, png_info, foo)
{
corps;
}

Les prototypes des fonctions non exportées (sauf ceux de pngtest) apparaissent dans pngpriv.h au-dessus du commentaire qui dit


/* Mainteneur : Mettez ici les nouveaux prototypes privés ^ */

Pour éviter de polluer l'espace de noms global, les noms de toutes les fonctions et variables exportées commencent par "png_", et toutes les macros du préprocesseur C publiquement visibles commencent par "PNG". Nous demandons aux applications qui utilisent libpng de ne pas commencer leurs propres symboles par l'une ou l'autre de ces chaînes.

Nous mettons un espace après l'opérateur "sizeof" et nous omettons les parenthèses facultatives autour de son argument lorsque l'argument est une expression, pas un nom de type, et nous encadrons toujours l'opérateur sizeof, avec son argument, entre parenthèses :


(sizeof (png_uint_32))
(sizeof tableau)

Avant libpng-1.6.0, nous utilisions une macro "png_sizeof()", formatée comme une fonction.

Les mots-clés de contrôle if, for, while et switch sont toujours suivis d'un espace pour les distinguer des appels de fonction, qui n'ont pas d'espace final.

Nous mettons un espace après chaque virgule et après chaque point-virgule dans les instructions "for", et nous mettons des espaces avant et après chaque opérateur binaire C et après "for" ou "while", et avant "?". Nous ne mettons pas d'espace entre un transtypage et l'expression transtypée, ni entre un nom de fonction et la parenthèse ouvrante qui le suit :


for (i = 2; i > 0; --i)
y[i] = a(x) + (int)b;

Nous préférons #ifdef et #ifndef à #if defined() et #if !defined() lorsqu'il n'y a qu'une seule macro testée. Nous utilisons toujours des parenthèses avec "defined".

Nous exprimons les constantes entières utilisées comme masques de bits en format hexadécimal, avec un nombre pair de chiffres hexadécimaux en minuscules, et pour les rendre non signées (par exemple, 0x00U, 0xffU, 0x0100U) et longues si elles sont supérieures à 0x7fff (par exemple, 0xffffUL).

Nous préférons utiliser des underscores plutôt que camelCase dans les noms, à l'exception de quelques noms de types dont nous héritons de zlib.h.

Nous préférons "if (quelquechose != 0)" et "if (quelquechose == 0)" à "if (quelquechose)" et si "(!quelquechose)", respectivement, et pour les pointeurs, nous préférons "if (pointeur_quelconque != NULL)" ou "if (pointeur_quelconque == NULL)".

Nous n'utilisons pas le caractère TAB pour l'indentation dans les sources C.

Les lignes ne dépassent pas 80 caractères.

D'autres règles peuvent être déduites en inspectant le code source de libpng.

#include <png.h>

La bibliothèque libpng fournit des fonctions pour lire et écrire des fichiers Portable Network Graphics (PNG) en C. Elle est largement utilisée dans diverses applications pour gérer les images au format PNG.

Configuration de libpng

La configuration de libpng peut être effectuée à l'aide des options standard de GNU configure.

Fonctionnalités prises en charge par libpng

libpng prend en charge un large éventail de fonctionnalités du format PNG, y compris différentes profondeurs de couleur, modes de couleur, canaux alpha, et trames spécifiques.

Trames prises en charge

libpng peut lire et écrire les trames PNG standard, y compris :

  • IHDR : En-tête d'image
  • PLTE : Palette de couleurs
  • IDAT : Données d'image
  • IEND : Fin d'image
  • tRNS : Transparence
  • cHRM : Informations chromatiques
  • gAMA : Correction gamma
  • iCCP : Profil de couleur ICC
  • sRGB : Spécification sRGB
  • iTXt : Texte international
  • tEXt : Texte
  • zTXt : Texte compressé
  • bKGD : Couleur d'arrière-plan
  • hIST : Historique de palette
  • pHYs : Pixels par unité de dimension
  • sBIT : Bits de couleur réels
  • tIME : Dernière modification de temps
  • acTL : En-têtes d'animation (supporté à partir de certaines versions)
  • fcTL : Contrôle de cadre d'animation (supporté à partir de certaines versions)
  • fdAT : Données de cadre d'animation (supporté à partir de certaines versions)
