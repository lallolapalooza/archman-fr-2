DESCRIPTION

Ces fonctions manipulent un objet X509_VERIFY_PARAM associé à une opération de vérification de certificat.

X509_VERIFY_PARAM_get0_name() renvoie le nom de l'objet param donné, décrivant généralement son objectif, par exemple « default », « pkcs7 », « smime_sign », « ssl_client » ou « ssl_server ». Pour les objets définis par l'utilisateur, le pointeur renvoyé peut être NULL même si l'objet est par ailleurs valide.

X509_VERIFY_PARAM_set1_name() définit le nom de param sur une copie de name, ou sur NULL si name est NULL.

X509_VERIFY_PARAM_set_flags() définit les drapeaux dans param en effectuant une opération OR avec flags. Voir la section VERIFICATION FLAGS pour une description complète des valeurs que le paramètre flags peut prendre.

Si l'argument flags inclut l'un des drapeaux contenus dans X509_V_FLAG_POLICY_MASK, c'est-à-dire X509_V_FLAG_POLICY_CHECK, X509_V_FLAG_EXPLICIT_POLICY, X509_V_FLAG_INHIBIT_ANY, et X509_V_FLAG_INHIBIT_MAP, alors X509_V_FLAG_POLICY_CHECK est défini en plus des drapeaux contenus dans l'argument flags.

X509_VERIFY_PARAM_get_flags() renvoie les drapeaux dans param.

X509_VERIFY_PARAM_clear_flags() efface les flags spécifiés dans param.

Appeler cette fonction peut entraîner des états internes inhabituels de l'objet param, par exemple avoir une heure de vérification configurée mais avoir X509_V_FLAG_USE_CHECK_TIME désactivé, ou avoir X509_V_FLAG_EXPLICIT_POLICY activé mais X509_V_FLAG_POLICY_CHECK désactivé, ce qui peut avoir des effets surprenants.

X509_VERIFY_PARAM_set_purpose() définit l'identifiant d'purpose de vérification dans param. Cela détermine l'objectif acceptable de la chaîne de certificats, par exemple X509_PURPOSE_SSL_CLIENT ou X509_PURPOSE_SSL_SERVER. Les objectifs standards sont listés dans X509_check_purpose(3), et des objectifs supplémentaires peuvent être définis avec X509_PURPOSE_add(3).

">X509_VERIFY_PARAM_set_trust() définit le paramètre de confiance dans param à trust.

X509_VERIFY_PARAM_set_time() définit l'indicateur X509_V_FLAG_USE_CHECK_TIME dans param en plus des indicateurs déjà définis et définit l'heure de vérification à t. Si cette fonction n'est pas appelée, l'heure actuelle est utilisée à la place, ou l'Epoch UNIX (1er janvier 1970) si X509_V_FLAG_USE_CHECK_TIME est défini manuellement en utilisant X509_VERIFY_PARAM_set_flags().

X509_VERIFY_PARAM_add0_policy() active la vérification des politiques (elle est désactivée par défaut) et ajoute policy à l'ensemble des politiques acceptables.

X509_VERIFY_PARAM_set1_policies() active la vérification des politiques (elle est désactivée par défaut) et définit l'ensemble des politiques acceptables à policies. Tout ensemble de politiques existant est effacé. Le paramètre policies peut être NULL pour effacer un ensemble de politiques existant.

X509_VERIFY_PARAM_set_depth() définit la profondeur de vérification maximale à depth. C'est le nombre maximum de certificats d'AC non approuvés qui peuvent apparaître dans une chaîne.

X509_VERIFY_PARAM_set_auth_level() définit le niveau de sécurité tel que défini dans SSL_CTX_set_security_level(3) pour la validation de la chaîne de certificats. Pour qu'une chaîne de certificats soit valide, les clés publiques de tous les certificats doivent atteindre le niveau de sécurité spécifié. Le niveau de sécurité de l'algorithme de signature n'est pas appliqué pour le certificat d'ancre de confiance de la chaîne, qui est soit approuvé directement, soit validé par des moyens autres que sa signature.

Du point de vue de la bibliothèque X.509, le niveau de sécurité par défaut est 0. Cependant, la bibliothèque SSL utilise un niveau de sécurité par défaut différent de 1 et appelle X509_VERIFY_PARAM_set_auth_level() avec son propre niveau avant de valider une chaîne de certificats.

X509_VERIFY_PARAM_set1_host() définit le nom d'hôte DNS attendu à name, effaçant tout nom d'hôte ou noms précédemment spécifiés. Si name est NULL ou vide, la liste des noms d'hôtes est effacée, et les vérifications de nom ne sont pas effectuées sur le certificat du pair. namelen doit être défini à la longueur de name. Pour des raisons de compatibilité historique, si name est terminé par NUL, namelen peut être spécifié comme zéro. Lorsqu'un nom d'hôte est spécifié, la vérification du certificat invoque automatiquement X509_check_host(3) avec les indicateurs égaux à l'argument flags donné à X509_VERIFY_PARAM_set_hostflags() (zéro par défaut). X509_VERIFY_PARAM_set1_host() échouera si name contient des octets 0 intégrés.

X509_VERIFY_PARAM_add1_host() ajoute name comme identifiant de référence supplémentaire qui peut correspondre au certificat du pair. Tous les noms précédents définis via X509_VERIFY_PARAM_set1_host() et X509_VERIFY_PARAM_add1_host() sont conservés. Aucune modification n'est apportée si name est NULL ou vide. namelen doit être défini à la longueur de name. Pour des raisons de compatibilité historique, si name est terminé par NUL, namelen peut être spécifié comme zéro. X509_VERIFY_PARAM_add1_host() échouera si name contient des octets 0 intégrés. Lorsque plusieurs noms sont configurés, le pair est considéré comme vérifié lorsqu'un nom correspond.

X509_VERIFY_PARAM_get0_peername() renvoie le nom d'hôte DNS ou le CommonName du sujet du certificat du pair qui correspondait à l'un des identifiants de référence. Lorsque la correspondance de caractères génériques n'est pas désactivée, ou lorsqu'un identifiant de référence spécifie un domaine parent (commence par ".") plutôt qu'un nom d'hôte, le nom du pair peut être un nom générique ou un sous-domaine de l'identifiant de référence respectivement.

X509_VERIFY_PARAM_set1_email() définit l'adresse e-mail RFC 822 attendue à email. emaillen doit être défini à la longueur de email. Pour des raisons de compatibilité historique, si email est terminé par NUL, emaillen peut être spécifié comme zéro. X509_VERIFY_PARAM_set1_email() échouera si email est NULL, une chaîne vide, ou contient des octets 0 intégrés. Lorsqu'une adresse e-mail est spécifiée, la vérification du certificat invoque automatiquement X509_check_email(3).

X509_VERIFY_PARAM_set1_ip() définit l'adresse IP attendue à ip. L'argument ip est au format binaire, en ordre d'octets réseau, et iplen doit être défini à 4 pour IPv4 et 16 pour IPv6. X509_VERIFY_PARAM_set1_ip() échouera si ip est NULL ou si iplen n'est ni 4 ni 16. Lorsqu'une adresse IP est spécifiée, la vérification du certificat invoque automatiquement X509_check_ip(3).

X509_VERIFY_PARAM_set1_ip_asc() définit l'adresse IP attendue à ipasc. L'argument ipasc est une chaîne ASCII terminée par NUL : quad décimal pointé pour IPv4 et hexadécimal séparé par des deux-points pour IPv6. La notation condensée "::" est prise en charge pour les adresses IPv6. X509_VERIFY_PARAM_set1_ip_asc() échouera si ipasc n'est pas analysable.

VALEURS DE RETOUR

X509_VERIFY_PARAM_set1_name(), X509_VERIFY_PARAM_set_flags(), X509_VERIFY_PARAM_clear_flags(), X509_VERIFY_PARAM_set_purpose(), X509_VERIFY_PARAM_set_trust(), X509_VERIFY_PARAM_add0_policy(), et X509_VERIFY_PARAM_set1_policies() retournent 1 en cas de succès ou 0 en cas d'échec.

X509_VERIFY_PARAM_set1_host(), X509_VERIFY_PARAM_add1_host(), X509_VERIFY_PARAM_set1_email(), X509_VERIFY_PARAM_set1_ip(), et X509_VERIFY_PARAM_set1_ip_asc() retournent 1 en cas de succès ou 0 en cas d'échec. Un échec de ces routines empoisonnera l'objet X509_VERIFY_PARAM de sorte que les appels futurs à X509_verify_cert(3) utilisant l'objet empoisonné échoueront.

X509_VERIFY_PARAM_get_flags() renvoie les indicateurs de vérification actuels.

X509_VERIFY_PARAM_get_time() renvoie toujours l'heure de vérification configurée. Elle le fait même si l'heure renvoyée ne sera pas utilisée car l'indicateur X509_V_FLAG_USE_CHECK_TIME est désactivé.

X509_VERIFY_PARAM_get_depth() renvoie la profondeur de vérification actuelle.

X509_VERIFY_PARAM_get0_name() et X509_VERIFY_PARAM_get0_peername() renvoient des pointeurs vers des chaînes qui ne sont valides que pendant la durée de vie de l'objet param donné et qui ne doivent pas être libérés par le programme d'application.

INDICATEURS DE VÉRIFICATION

Les indicateurs de vérification consistent en zéro ou plus des indicateurs suivants combinés par OR.

X509_V_FLAG_CRL_CHECK active la vérification CRL pour le certificat feuille de la chaîne de certificats. Une erreur se produit si une CRL appropriée ne peut être trouvée.

X509_V_FLAG_CRL_CHECK_ALL active la vérification CRL pour toute la chaîne de certificats.

X509_V_FLAG_IGNORE_CRITICAL désactive la vérification des extensions critiques. Par défaut, toute extension critique non gérée dans les certificats ou (si vérifiées) les CRL entraîne une erreur fatale. Si cet indicateur est défini, les extensions critiques non gérées sont ignorées. AVERTISSEMENT : la définition de cette option pour autre chose que le débogage peut présenter un risque de sécurité. Un contrôle plus fin sur les extensions prises en charge peut être effectué dans le rappel de vérification.

L'indicateur X509_V_FLAG_X509_STRICT désactive les solutions de contournement pour certains certificats défectueux et rend la vérification strictement conforme aux règles X509.

X509_V_FLAG_ALLOW_PROXY_CERTS indicateur obsolète qui activait auparavant la vérification des certificats proxy. Dans LibreSSL, cet indicateur n'a aucun effet.

X509_V_FLAG_POLICY_CHECK active la vérification des politiques de certificat ; par défaut, aucune vérification de politique n'est effectuée. Des informations supplémentaires sont envoyées au rappel de vérification concernant la vérification des politiques.

X509_V_FLAG_EXPLICIT_POLICY, X509_V_FLAG_INHIBIT_ANY, et X509_V_FLAG_INHIBIT_MAP définissent respectivement les indicateurs « exiger une politique explicite », « inhiber toute politique » et « inhiber le mappage des politiques », tels que définis dans la RFC 3280. Ces trois indicateurs sont ignorés à moins que X509_V_FLAG_POLICY_CHECK ne soit également défini.

DESCRIPTION

The verification process is controlled by a X509_VERIFY_PARAM object. This object contains flags, host name matching parameters, purpose, trust settings, policy settings, depth, time, and authentication level. See X509_VERIFY_PARAM_new(3) for details on how to create and destroy such an object.

The functions listed here are used to set and get the various parameters associated with certificate verification.

The X509_VERIFY_PARAM_set1_host() function sets the expected hostname for verification. This is used to check the name constraints in the peer's certificate and also used for name matching of the peer's certificate subject name. The namelen argument specifies the length of the hostname. If namelen is zero, then strlen is used. The function copies the hostname. X509_VERIFY_PARAM_add1_host() adds to the list of expected hostnames. This is useful for checking wildcard hostnames.

The X509_VERIFY_PARAM_set1_email(), X509_VERIFY_PARAM_set1_ip(), and X509_VERIFY_PARAM_set1_ip_asc() functions set the expected email address, IP address, and IP address in ASCII string format, respectively. These are used for name matching of the peer's certificate subject name.

The X509_VERIFY_PARAM_set_auth_level() function sets the maximum acceptable number of intermediate CA certificates in a certificate chain. The default value is 0, which means only self-signed certificates are trusted. A value of 1 means that certificates signed by a self-signed root CA are trusted, and so on.

X509_VERIFY_PARAM_get_flags() returns the flags set.

VERIFICATION FLAGS

The following flags can be set using X509_VERIFY_PARAM_set_flags() and cleared using X509_VERIFY_PARAM_clear_flags().

X509_V_FLAG_CRL_CHECK
If this flag is set, then certificates are checked against the configured CRLs. If no CRLs are found for a certificate, then the verification fails.
X509_V_FLAG_CRL_CHECK_LEAF
If this flag is set, then the leaf certificate is checked against the configured CRLs. If no CRL is found for the leaf certificate, then the verification proceeds without checking the leaf certificate against a CRL.
X509_V_FLAG_IGNORE_CRITICAL
If this flag is set, then critical extensions that are not understood are ignored. By default, unknown critical extensions cause verification to fail.
X509_V_FLAG_X509_STRICT
If this flag is set, then certificate policies are checked. If the certificate contains policy information, then the verification must succeed. By default, policy checking is disabled.
X509_V_FLAG_NOTIFY_POLICY
If X509_V_FLAG_NOTIFY_POLICY is set and policy checking is successful, a special status code is sent to the verification callback.
X509_V_FLAG_EXTENDED_CRL_SUPPORT
By default some additional features such as indirect CRLs and CRLs signed by different keys are disabled. If X509_V_FLAG_EXTENDED_CRL_SUPPORT is set, they are enabled.
X509_V_FLAG_USE_DELTAS
If X509_V_FLAG_USE_DELTAS is set, delta CRLs (if present) are used to determine certificate status. If not set, deltas are ignored.
X509_V_FLAG_CHECK_SS_SIGNATURE
Enables checking of the root CA self signed certificate signature. By default this check is disabled because it doesn't add any additional security but in some cases applications might want to check the signature anyway. A side effect of not checking the root CA signature is that disabled or unsupported message digests on the root CA are not treated as fatal errors.
X509_V_FLAG_CB_ISSUER_CHECK
The deprecated X509_V_FLAG_CB_ISSUER_CHECK flag used to enable debugging of certificate issuer checks. It is provided for binary backwards compatibility and has no effect.
X509_V_FLAG_TRUSTED_FIRST
When X509_V_FLAG_TRUSTED_FIRST is set, construction of the certificate chain in X509_verify_cert(3) will search the trust store for issuer certificates before searching the provided untrusted certificates. Local issuer certificates are often more likely to satisfy local security requirements and lead to a locally trusted root. This is especially important when some certificates in the trust store have explicit trust settings; see the trust settings options of the x509 command in openssl(1).
X509_V_FLAG_NO_ALT_CHAINS
The X509_V_FLAG_NO_ALT_CHAINS flag suppresses checking for alternative chains. By default, unless X509_V_FLAG_TRUSTED_FIRST is set, when building a certificate chain, if the first certificate chain found is not trusted, then OpenSSL will attempt to replace untrusted certificates supplied by the peer with certificates from the trust store to see if an alternative chain can be found that is trusted.
X509_V_FLAG_PARTIAL_CHAIN
The X509_V_FLAG_PARTIAL_CHAIN flag causes intermediate certificates in the trust store to be treated as trust-anchors, in the same way as the self-signed root CA certificates. This makes it possible to trust certificates issued by an intermediate CA without having to trust its ancestor root CA.
X509_V_FLAG_USE_CHECK_TIME
If X509_V_FLAG_USE_CHECK_TIME is set, the validity period of certificates and CRLs is checked. In this case, X509_V_FLAG_NO_CHECK_TIME is ignored. If the validation time was set with X509_VERIFY_PARAM_set_time(), that time is used. If X509_VERIFY_PARAM_set_time() was not called, the UNIX Epoch (January 1, 1970) is used.
X509_V_FLAG_USE_CHECK_TIME
If neither X509_V_FLAG_USE_CHECK_TIME nor X509_V_FLAG_NO_CHECK_TIME is set, the validity period of certificates and CRLs is checked using the current time. This is the default behaviour. In this case, if a validation time was set with X509_VERIFY_PARAM_set_time() but X509_V_FLAG_USE_CHECK_TIME was later cleared with X509_VERIFY_PARAM_clear_flags(), the configured validation time is ignored and the current time is used anyway.
X509_V_FLAG_NO_CHECK_TIME
If X509_V_FLAG_USE_CHECK_TIME is not set but X509_V_FLAG_NO_CHECK_TIME is set, the validity period of certificates and CRLs is not checked at all, and like in the previous case, any configured validation time is ignored.

EXAMPLES

Enable CRL checking when performing certificate verification during SSL connections associated with an SSL_CTX structure ctx:

X509_VERIFY_PARAM *param;

param = X509_VERIFY_PARAM_new();
X509_VERIFY_PARAM_set_flags(param, X509_V_FLAG_CRL_CHECK);
SSL_CTX_set1_param(ctx, param);
X509_VERIFY_PARAM_free(param);

BUGS

Delta CRL checking is currently primitive. Only a single delta can be used and (partly due to limitations of X509_STORE) constructed CRLs are not maintained.

If CRLs checking is enabled, CRLs are expected to be available in the corresponding X509_STORE structure. No attempt is made to download CRLs from the CRL distribution points extension.
