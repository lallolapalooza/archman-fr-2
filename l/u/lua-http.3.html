Introduction

lua-http est une bibliothèque HTTP et WebSocket performante et capable pour Lua 5.1, 5.2, 5.3 et LuaJIT. Certaines des fonctionnalités de la bibliothèque incluent :

•
Prise en charge des versions HTTP 1, 1.1 et 2 telles que spécifiées par les RFC 7230 (https://tools.ietf.org/html/rfc7230) et RFC 7540 (https://tools.ietf.org/html/rfc7540)
•
Fournit des API client et serveur
•
API entièrement asynchrone qui ne bloque pas le thread courant lors de l'exécution d'opérations qui bloquent normalement
•
Prise en charge des WebSockets telle que spécifiée par la RFC 6455 (https://tools.ietf.org/html/rfc6455), y compris ping/pong, transfert de données binaires et chiffrement TLS
•
Sécurité de la couche transport (TLS) - lua-http prend en charge HTTPS et WSS via luaossl (https://github.com/wahern/luaossl).
•
Intégration facile dans d'autres boucles d'événements ou scripts

Pourquoi lua-http ?

La bibliothèque lua-http a été écrite pour combler une lacune dans l'écosystème Lua en fournissant une bibliothèque HTTP et WebSocket avec les caractéristiques suivantes :

•
Asynchrone et performante
•
Peut être utilisée sans forcer le développeur à suivre un modèle spécifique. Inversement, la bibliothèque peut être adaptée à de nombreux modèles courants.
•
Peut être utilisée à un niveau très élevé sans avoir besoin de comprendre le transport des données HTTP (autre que les adresses de connexion).
•
Fournit une API de bas niveau riche, si désiré, pour créer des outils puissants basés sur HTTP au niveau du protocole.

En conséquence de ces objectifs de conception, la bibliothèque est simple et discrète et peut accueillir des dizaines de milliers de connexions sur du matériel courant.

lua-http est une bibliothèque HTTP et WebSocket flexible qui permet aux développeurs de se concentrer sur les fonctionnalités métier lors de la création d'applications connectées à Internet. Si vous cherchez un moyen de rationaliser le développement d'une application connectée à Internet, d'activer la mise en réseau HTTP dans votre jeu, de créer un nouveau système de l'Internet des Objets (IoT), ou d'écrire un serveur web personnalisé et performant pour un cas d'utilisation spécifique, lua-http dispose des outils dont vous avez besoin.

Portabilité

lua-http est du code Lua pur avec des dépendances sur les bibliothèques externes suivantes :

•
cqueues (http://25thandclement.com/~william/projects/cqueues.html) - Bibliothèque API Posix pour Lua
•
luaossl (http://25thandclement.com/~william/projects/luaossl.html) - Bindings Lua pour TLS/SSL
•
lua-zlib (https://github.com/brimworks/lua-zlib) - Bindings Lua optionnels pour zlib

lua-http peut fonctionner sur n'importe quel système d'exploitation pris en charge par cqueues et openssl, ce qui, au moment de la rédaction, inclut GNU/Linux, FreeBSD, NetBSD, OpenBSD, OSX et Solaris.

Cas d'utilisation courants

Les exemples suivants sont deux démonstrations simples de la manière dont la bibliothèque lua-http peut être utilisée :

Récupération d'un document

L'interface de plus haut niveau pour les clients est http.request. En construisant un objet request à partir d'une URI à l'aide de new_from_uri et en l'évaluant immédiatement, vous pouvez facilement récupérer une ressource HTTP.

local http_request = require "http.request"
local headers, stream = assert(http_request.new_from_uri("http://example.com"):go())
local body = assert(stream:get_body_as_string())
if headers:get ":status" ~= "200" then
    error(body)
end
print(body)

Communications WebSocket

Pour demander des informations à un serveur WebSocket, utilisez le module websocket pour créer un nouveau client WebSocket.

local websocket = require "http.websocket"
local ws = websocket.new_from_uri("wss://echo.websocket.org")
assert(ws:connect())
assert(ws:send("koo-eee!"))
local data = assert(ws:receive())
assert(data == "koo-eee!")
assert(ws:close())

Opération asynchrone

lua-http a été conçu pour fonctionner de manière asynchrone afin qu'il puisse être utilisé dans votre application, serveur ou jeu sans bloquer votre boucle principale. Les opérations asynchrones sont réalisées en utilisant cqueues, une bibliothèque Lua/C qui intègre le yield Lua et les API de niveau noyau pour réduire l'utilisation du CPU. Toutes les opérations de lua-http, y compris la résolution DNS, la négociation TLS et les opérations de lecture/écriture, ne bloqueront pas le thread d'application principal lorsqu'elles sont exécutées à partir d'une file d'attente cqueues ou d'un "conteneur" activé par cqueues. Bien qu'il soit parfois nécessaire de bloquer une routine (yield) et d'attendre des données externes, tous les appels d'API bloquants prennent un délai d'attente optionnel pour garantir le bon comportement des applications réseau et éviter les routines non réactives ou "mortes".

Les opérations asynchrones sont l'une des fonctionnalités les plus puissantes de lua-http et ne nécessitent aucun effort de la part du développeur. Par exemple, un serveur HTTP peut être instancié dans n'importe quelle boucle principale Lua et fonctionner aux côtés du code de l'application sans affecter négativement le processus d'application principal. Si d'autres composants compatibles cqueues sont intégrés dans une boucle cqueues, l'application est entièrement pilotée par événements via des API de sondage au niveau du noyau.

cqueues peut être utilisé conjointement avec lua-http pour intégrer d'autres fonctionnalités dans votre application Lua et créer des applications web puissantes, performantes et activées. Certains des exemples de ce guide utiliseront cqueues pour des démonstrations simples. Pour plus de ressources sur cqueues, veuillez consulter :

•
Le site web de cqueues (http://25thandclement.com/~william/projects/cqueues.html) pour plus d'informations sur la bibliothèque cqueues.
•
Les exemples de cqueues peuvent être trouvés avec le code source de cqueues disponible via git ou des archives (http://www.25thandclement.com/~william/projects/cqueues.html#download) ou accédés en ligne ici (https://github.com/wahern/cqueues/tree/master/examples).
•
Pour plus d'informations sur l'intégration de cqueues avec d'autres bibliothèques de boucle d'événements, veuillez consulter l'intégration avec d'autres boucles principales (https://github.com/wahern/cqueues/wiki/Integrations-with-other-main-loops).
•
Pour d'autres bibliothèques qui utilisent cqueues, telles que les API asynchrones pour Redis et PostgreSQL, veuillez consulter l'entrée wiki de cqueues ici (https://github.com/wahern/cqueues/wiki/Libraries-that-use-cqueues).

Conventions

Voici une liste de conventions d'API et de référence générale :

HTTP

•
Les requêtes HTTP 1 et les champs de ligne de statut sont transmis à l'intérieur des objets headers sous les clés ":authority", ":method", ":path", ":scheme" et ":status", comme défini dans HTTP 2. En tant que tels, ils sont tous conservés sous forme de chaîne (important à retenir pour le champ :status).
•
Les champs d'en-tête doivent toujours être utilisés avec des clés en minuscules.

Erreurs

•
Des paramètres de fonction invalides lèveront une erreur Lua (s'ils sont validés).
•
Les connexions qui se ferment sans qu'une réponse ne soit reçue renverront une erreur lorsque l'opération est demandée. Il est important de gérer les erreurs d'opération correctement pour s'assurer que les routines ne tombent pas en panne.
•
Si une requête de niveau supérieur échoue, elle renvoie une chaîne d'erreur contenant plus d'informations sur la défaillance.

Certaines opérations HTTP 2 renvoient/lèvent des objets d'erreur HTTP 2 spéciaux.

Timeouts

Toutes les opérations susceptibles de bloquer le thread courant acceptent un argument timeout. Cet argument est toujours le nombre de secondes à accorder avant de renvoyer nil, msg_erreur, ETIMEDOUT où msg_erreur est un message d'erreur localisé tel que "la connexion a expiré".

Terminologie

Une grande partie de la terminologie de lua-http est empruntée à HTTP 2.

Connexion - Une abstraction sur une socket TCP/IP sous-jacente. lua-http possède actuellement deux types de connexions : une pour HTTP 1, une pour HTTP 2.

Flux - Une requête/réponse sur un objet connexion. lua-http possède deux types de flux : un pour les flux HTTP 1 et un pour les flux HTTP 2. Les interfaces communes sont décrites dans flux.

Interfaces

lua-http a des modules distincts pour les protocoles HTTP 1 et HTTP 2, mais les différentes versions partagent de nombreux concepts communs. lua-http fournit une interface commune pour les opérations qui ont du sens pour les deux versions de protocole (ainsi que pour les développements futurs).

Les sections suivantes décrivent les interfaces exposées par la bibliothèque lua-http.

connection

Une connexion encapsule une socket et fournit des opérations spécifiques au protocole. Une connexion peut avoir des flux qui encapsulent les requêtes/réponses se produisant sur une connexion. Alternativement, vous pouvez ignorer complètement les flux et utiliser les opérations de bas niveau spécifiques au protocole pour lire et écrire sur la socket.

Tous les types de connexion exposent les champs suivants :

connection.type

Le mode d'utilisation de l'objet connexion. Les valeurs valides sont :

•
"client" : Agit en tant que client ; ce type de connexion est utilisé par les entités qui souhaitent effectuer des requêtes
•
"server" : Agit en tant que serveur ; ce type de connexion est utilisé par les entités qui souhaitent répondre aux requêtes

connection.version

Le numéro de version HTTP de la connexion sous forme de nombre.

connection:pollfd()

connection:events()

connection:timeout()

connection:connect(timeout)

Achève la connexion au serveur distant en utilisant l'adresse spécifiée, la version HTTP et toutes les options spécifiées dans le constructeur connection.new. La fonction connect attendra jusqu'à ce que la tentative de connexion se termine (succès ou échec) ou jusqu'à ce que le timeout soit dépassé. La connexion peut inclure des recherches DNS, la négociation TLS et l'échange de paramètres HTTP2. Renvoie true en cas de succès. En cas d'erreur, renvoie nil, un message d'erreur et un numéro d'erreur.

connection:checktls()

Vérifie la socket pour une connexion Transport Layer Security valide. Renvoie l'objet ssl luaossl si la connexion est sécurisée. Renvoie nil et un message d'erreur s'il n'y a pas de session TLS active. Veuillez consulter le site Web de luaossl (http://25thandclement.com/~william/projects/luaossl.html) pour plus d'informations sur l'objet ssl.

connection:localname()

Renvoie les informations de connexion pour la socket locale. Renvoie la famille d'adresses, l'adresse IP et le port pour une socket externe. Pour les sockets de domaine Unix, la fonction renvoie AF_UNIX et le chemin. Si l'objet connexion n'est pas connecté, renvoie AF_UNSPEC (0). En cas d'erreur, renvoie nil, un message d'erreur et un numéro d'erreur.

connection:peername()

Renvoie les informations de connexion pour le pair de la socket (c'est-à-dire le prochain saut). Renvoie la famille d'adresses, l'adresse IP et le port pour une socket externe. Pour les sockets Unix, la fonction renvoie AF_UNIX et le chemin. Si l'objet connexion n'est pas connecté, renvoie AF_UNSPEC (0). En cas d'erreur, renvoie nil, un message d'erreur et un numéro d'erreur.

Note : Si le client utilise un proxy, les valeurs renvoyées par :peername() pointent vers le proxy, pas vers le serveur distant.

connection:flush(timeout)

Vide les données sortantes mises en mémoire tampon sur la socket vers le système d'exploitation. Renvoie true en cas de succès. En cas d'erreur, renvoie nil, un message d'erreur et un numéro d'erreur.

connection:shutdown()

Effectue une fermeture ordonnée de la connexion en fermant tous les flux et en appelant :shutdown() sur la socket. La connexion ne peut pas être rouverte.

connection:close()

Ferme une connexion et libère les ressources du système d'exploitation. Notez que :close() effectue un connection:shutdown() avant de libérer les ressources.

connection:new_stream()

Crée et renvoie un nouveau flux sur la connexion.

connection:get_next_incoming_stream(timeout)

Renvoie le prochain flux initié par le pair sur la connexion. Cette fonction peut être utilisée pour attendre et « écouter » les flux HTTP entrants.

connection:onidle(new_handler)

Fournit une fonction de rappel à appeler lorsque la connexion devient inactive, c'est-à-dire lorsqu'il n'y a pas de requête en cours et pas de flux en attente dans le pipeline. Lorsqu'elle est appelée, elle recevra la connexion comme premier argument. Renvoie le gestionnaire précédent.

stream

Un flux HTTP est une abstraction d'une requête/réponse dans une connexion HTTP. À l'intérieur d'un flux, il peut y avoir un certain nombre de blocs d'« en-têtes » ainsi que des données connues sous le nom de « corps ».

Tous les types de flux exposent les champs et fonctions suivants :

stream.connection

L'objet connexion sous-jacent.

stream:checktls()

Wrapper de commodité équivalent à stream.connection:checktls()

stream:localname()

Wrapper de commodité équivalent à stream.connection:localname()

stream:peername()

Wrapper de commodité équivalent à stream.connection:peername()

stream:get_headers(timeout)

Récupère le prochain objet d'en-têtes complet (c'est-à-dire un bloc d'en-têtes ou de remorques) du flux.

stream:write_headers(headers, end_stream, timeout)

Écrit l'objet headers donné dans le flux. La fonction prend un indicateur indiquant s'il s'agit du dernier bloc dans le flux. Si la valeur est true, le flux sera fermé. Si un timeout est spécifié, le flux attendra que l'envoi soit terminé jusqu'à ce que le timeout soit dépassé.

stream:write_continue(timeout)

Envoie un bloc d'en-tête 100-continue.

stream:get_next_chunk(timeout)

Renvoie le prochain bloc du corps http depuis la socket, potentiellement en attendant jusqu'à timeout secondes. En cas d'erreur, renvoie nil, un message d'erreur et un numéro d'erreur.

stream:each_chunk()

Lit l'intégralité du corps du flux et le renvoie sous forme de chaîne de caractères. En cas d'erreur, renvoie nil, un message d'erreur et un numéro d'erreur.

stream:get_body_chars(n, timeout)

Lit n caractères (octets) du corps du flux et les renvoie sous forme de chaîne de caractères. Si le flux se termine avant que n caractères ne soient lus, renvoie le résultat partiel. En cas d'erreur, renvoie nil, un message d'erreur et un numéro d'erreur.

Places str back on the incoming data buffer, allowing it to be returned again on a subsequent command (“un-gets” the data). Returns true on success. On error, returns nil, an error message and an error number.

new_store()

Crée un nouveau magasin de cookies.

Les cookies sont uniques pour un tuple de domaine, chemin et nom ; bien que plusieurs cookies du même nom puissent exister dans une requête en raison de chemins ou de domaines qui se chevauchent.

Un objet lua-psl (https://github.com/daurnimator/lua-psl) à utiliser pour vérifier la liste des suffixes publics (Public Suffix List). Définissez ce champ sur false pour ignorer la vérification de la liste des suffixes.

Par défaut, utilise la dernière version (https://rockdaboot.github.io/libpsl/libpsl-Public-Suffix-List-functions.html#psl-latest) de la PSL sur le système. Si lua-psl n'est pas installé, il sera nil.

store.time()

Une fonction utilisée par le store pour obtenir l'heure actuelle pour les expirations et autres.

Par défaut, utilise une fonction basée sur os.time (https://www.lua.org/manual/5.3/manual.html#pdf-os.time).

La longueur maximale (en octets) des cookies dans le magasin ; cette valeur est également utilisée comme longueur maximale de cookie par défaut pour :lookup(). Diminuer cette valeur empêchera seulement l'ajout de nouveaux cookies, cela ne supprimera pas les anciens.

Par défaut, l'infini (pas de taille maximale).

Le nombre maximal de cookies autorisés dans le store. Diminuer cette valeur empêchera seulement l'ajout de nouveaux cookies, cela ne supprimera pas les anciens.

Par défaut, l'infini (tout nombre de cookies est autorisé).

Le nombre maximal de cookies autorisés dans le store par domaine. Diminuer cette valeur empêchera seulement l'ajout de nouveaux cookies, cela ne supprimera pas les anciens.

http.headers

Une liste ordonnée de champs d'en-tête. Chaque champ a un nom, une valeur et un indicateur never_index qui indique si le champ d'en-tête contient des données potentiellement sensibles.

Chaque objet d'en-têtes est indexé par nom de champ pour récupérer efficacement les valeurs par clé. Gardez à l'esprit qu'il peut y avoir plusieurs valeurs pour un nom de champ donné. (par exemple, un serveur HTTP peut envoyer deux en-têtes Set-Cookie).

Comme noté dans la section Conventions, les champs de ligne de requête et de statut HTTP 1 sont passés dans des objets d'en-têtes sous les clés ":authority", ":method", ":path", ":scheme" et ":status" tels que définis dans HTTP 2. En tant que tels, ils sont tous conservés sous forme de chaînes de caractères (il est important de s'en souvenir pour le champ ":status").

Exemple

myheaders:append("set-cookie", "foo=bar")
myheaders:append("connection", "close")
myheaders:append("set-cookie", "baz=qux")
for name, value, never_index in myheaders:each() do
    print(name, value, never_index)
end
--[[ prints:
":status", "200", false
"set-cookie", "foo=bar", true
"connection", "close", false
"set-cookie", "baz=qux", true
]]

http.server

Les objets http.server sont utilisés pour encapsuler l'accept() et la distribution des clients http. Chaque nouvelle requête client invoquera le rappel onstream dans une nouvelle coroutine gérée par cqueues. En plus de construire et de retourner une réponse HTTP, un gestionnaire onstream peut décider de prendre possession de la connexion à d'autres fins, par exemple, une mise à niveau d'une connexion HTTP 1.1 vers une connexion WebSocket.

Pour des exemples d'utilisation de la bibliothèque serveur, veuillez consulter le répertoire des exemples (https://github.com/daurnimator/lua-http/tree/master/examples) dans l'arborescence des sources.

new(options)

Crée une nouvelle instance d'un serveur HTTP écoutant sur le socket donné.

•
.socket (cqueues.socket) : le socket sur lequel accept() sera appelé
•
.onerror (function) : Fonction qui sera appelée lorsqu'une erreur se produit (le gestionnaire par défaut lève une erreur). Voir server:onerror()
•
.onstream (function) : Fonction de rappel pour gérer une nouvelle requête client. La fonction reçoit le serveur et le nouveau flux comme paramètres. Si le rappel lève une erreur, elle sera signalée depuis :step() ou :loop()
•
.tls (boolean) : Spécifie si le système doit utiliser la sécurité de la couche de transport. Les valeurs sont :
•
nil : Autorise les connexions TLS et non-TLS
•
true : Autorise uniquement les connexions TLS
•
false : Autorise uniquement les connexions non-TLS
•
.ctx (objet context) : Un objet openssl.ssl.context à utiliser pour les connexions tls. Si nil est passé, un contexte auto-signé sera généré.
•
.connection_setup_timeout (nombre) : Délai d'attente (en secondes) pour que le client envoie les premiers octets et/ou complète la négociation TLS. Par défaut, 10 secondes.
•
.intra_stream_timeout (nombre) : Délai d'attente (en secondes) pour un nouveau flux sur une connexion inactive avant d'abandonner et de fermer la connexion.
•
.version (nombre) : La version http à autoriser pour la connexion (par défaut : toute).
•
.cq (cqueue) : Un contrôleur cqueues à utiliser comme boucle principale. Par défaut, un nouveau contrôleur pour le serveur.
•
.max_concurrent (nombre) : Nombre maximum de connexions autorisées simultanément. Par défaut, l'infini.

listen(options)

Crée un nouveau socket et retourne un serveur HTTP qui effectuera un accept() à partir de celui-ci. Les paramètres sont les mêmes que new(options), sauf qu'au lieu de .socket, vous fournissez les éléments suivants :

•
.host (string) : Adresse IP locale en notation décimale ou IPV6. Cette valeur est requise si .path n'est pas spécifié.
•
.port (number) : Port IP pour le socket local. Spécifiez 0 pour une sélection automatique du port. Les ports 1-1024 nécessitent que l'application ait les privilèges root pour s'exécuter. La valeur maximale est 65535. Si .tls == nil alors cette valeur est requise. Sinon, les valeurs par défaut sont :
•
80 si .tls == false
•
443 si .tls == true
•
.path (string) : Chemin vers un socket UNIX. Cette valeur est requise si .host n'est pas spécifié.
•
.family (string) : Famille de protocole. Par défaut, "AF_INET".
•
.v6only (boolean) : Spécifiez true pour limiter toutes les connexions à ipv6 uniquement (pas d'ipv4-mappé-ipv6). Par défaut, false.
•
.mode (string) : fchmod ou chmod le socket après avoir créé le socket de domaine UNIX.
•
.mask (boolean) : Définit et restaure umask lors de la liaison d'un socket de domaine UNIX.
•
.unlink (boolean) : true signifie supprimer le chemin du socket avant la liaison.
•
.reuseaddr (boolean) : Active le drapeau SO_REUSEADDR.
•
.reuseport (boolean) : Active le drapeau SO_REUSEPORT.

http.zlib

Une couche d'abstraction au-dessus des diverses bibliothèques lua zlib.

engine

Actuellement soit "lua-zlib" (https://github.com/brimworks/lua-zlib) soit "lzlib" (https://github.com/LuaDist/lzlib)

inflate()

Retourne une closure qui décompresse (uncompresse) un flux zlib.

La closure prend une chaîne de données compressées et un indicateur de fin de flux (boolean) en paramètres et retourne la sortie décompressée sous forme de chaîne. La fonction lèvera une erreur si l'entrée n'est pas un flux zlib valide.

deflate()

Retourne une closure qui compresse un flux zlib.

La closure prend une chaîne de données non compressées et un indicateur de fin de flux (boolean) en paramètres et retourne la sortie compressée sous forme de chaîne.

Exemple

local zlib = require "http.zlib"
local original = "la voiture de course a couru autour de la piste de la voiture de course"
local deflater = zlib.deflate()
local compressed = deflater(original, true)
print(#original, #compressed) -- compressed devrait être plus petit
local inflater = zlib.inflate()
local uncompressed = inflater(compressed, true)
assert(original == uncompressed)

http.compat.prosody

Fournit une utilisation similaire au module net.http de prosody (https://prosody.im/doc/developers/net/http)

request(url, ex, callback)

Quelques différences clés par rapport à net.http.request de prosody :

•
doit être appelé depuis une cqueue en cours d'exécution
•
Le callback peut être appelé depuis un thread différent de la cqueue
•
L'objet retourné sera un objet http.request
•
Cet objet est passé au callback en cas d'erreur et comme quatrième argument en cas de succès
•
L'agent utilisateur par défaut proviendra de lua-http (plutôt que "Prosody XMPP Server")
•
Les fonctionnalités de lua-http (telles que HTTP2) seront utilisées lorsque possible

Exemple

local prosody_http = require "http.compat.prosody"
local cqueues = require "cqueues"
local cq = cqueues.new()
cq:wrap(function()
    prosody_http.request("http://httpbin.org/ip", {}, function(b, c, r)
        print(c) --> 200
        print(b) --> {"origin": "123.123.123.123"}
    end)
end)
assert(cq:loop())

http.compat.socket

Fournit la compatibilité avec le module http.request de luasocket (http://w3.impa.br/~diego/software/luasocket/http.html).

Différences :

•
Sera automatiquement non bloquant lorsqu'il est exécuté à l'intérieur d'une coroutine gérée par cqueues
•
Les fonctionnalités de lua-http (telles que HTTP2) seront utilisées lorsque possible

Exemple

Utilisation de l'interface `simple' dans le cadre d'un script normal :

local socket_http = require "http.compat.socket"
local body, code = assert(socket_http.request("http://lua.org"))
print(code, #body) --> 200, 2514
