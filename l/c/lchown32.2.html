chown(2) Manuel des appels système chown(2)

NOM

chown, fchown, lchown, fchownat - changer le propriétaire d'un fichier

BIBLIOTHÉQUE

Bibliothèque C standard (libc, -lc)

SYNTAXE

#include <unistd.h>
int chown(const char *path, uid_t owner, gid_t group);
int fchown(int fd, uid_t owner, gid_t group);
int lchown(const char *path, uid_t owner, gid_t group);
#include <fcntl.h>           /* Définition des constantes AT_* */
#include <unistd.h>
int fchownat(int dirfd, const char *path,
             uid_t owner, gid_t group, int flags);
Exigences de macros de test de fonctionnalité pour glibc (voir feature_test_macros(7)):

fchown(), lchown():

    /* Depuis glibc 2.12 : */ _POSIX_C_SOURCE >= 200809L
        || _XOPEN_SOURCE >= 500
        || /* glibc <= 2.19 : */ _BSD_SOURCE

fchownat():

    Depuis glibc 2.10 :
        _POSIX_C_SOURCE >= 200809L
    Avant glibc 2.10 :
        _ATFILE_SOURCE

DESCRIPTION

Ces appels système modifient le propriétaire et le groupe d'un fichier. Les appels système chown(), fchown() et lchown() ne diffèrent que par la manière dont le fichier est spécifié :

•
chown() modifie le propriétaire du fichier spécifié par path, qui est déréférencé s'il s'agit d'un lien symbolique.
•
fchown() modifie le propriétaire du fichier auquel le descripteur de fichier ouvert fd fait référence.
•
lchown() est similaire à chown(), mais ne déréférence pas les liens symboliques.

Seul un processus privilégié (Linux : celui ayant la capacité CAP_CHOWN) peut changer le propriétaire d'un fichier. Le propriétaire d'un fichier peut changer le groupe du fichier pour n'importe quel groupe dont ce propriétaire fait partie. Un processus privilégié (Linux : avec CAP_CHOWN) peut changer le groupe arbitrairement.

Si owner ou group est spécifié comme -1, alors cet ID n'est pas modifié.

Lorsque le propriétaire ou le groupe d'un fichier exécutable est modifié par un utilisateur non privilégié, les bits de mode S_ISUID et S_ISGID sont effacés. POSIX ne spécifie pas si cela doit également se produire lorsque root effectue le chown() ; le comportement de Linux dépend de la version du noyau, et depuis Linux 2.2.13, root est traité comme les autres utilisateurs. Dans le cas d'un fichier non exécutable par groupe (c'est-à-dire pour lequel le bit S_IXGRP n'est pas défini), le bit S_ISGID indique un verrouillage obligatoire et n'est pas effacé par un chown().

Lorsque le propriétaire ou le groupe d'un fichier exécutable est modifié (par n'importe quel utilisateur), tous les jeux de capacités pour le fichier sont effacés.

fchownat()

L'appel système fchownat() fonctionne exactement de la même manière que chown(), à l'exception des différences décrites ici.

Si path est relatif, il est interprété par rapport au répertoire auquel dirfd fait référence (plutôt que par rapport au répertoire de travail actuel du processus appelant, comme le fait chown() pour un nom de chemin relatif).

Si path est relatif et dirfd est la valeur spéciale AT_FDCWD, alors path est interprété par rapport au répertoire de travail actuel du processus appelant (comme chown()).

Si path est absolu, alors dirfd est ignoré.

L'argument flags est un masque de bits créé en combinant 0 ou plus des valeurs suivantes ;

AT_EMPTY_PATH (depuis Linux 2.6.39)
Si path est une chaîne vide, opérer sur le fichier auquel dirfd fait référence (qui peut avoir été obtenu en utilisant l'option O_PATH de open(2)). Dans ce cas, dirfd peut faire référence à n'importe quel type de fichier, pas seulement un répertoire. Si dirfd est AT_FDCWD, l'appel opère sur le répertoire de travail actuel. Ce drapeau est spécifique à Linux ; définissez _GNU_SOURCE pour obtenir sa définition.
AT_SYMLINK_NOFOLLOW
Si path est un lien symbolique, ne pas le déréférencer : opérer à la place sur le lien lui-même, comme lchown(). (Par défaut, fchownat() déréférence les liens symboliques, comme chown().)

Voir openat(2) pour une explication de la nécessité de fchownat().

VALEUR DE RETOUR

En cas de succès, zéro est retourné. En cas d'erreur, -1 est retourné et errno est défini pour indiquer l'erreur.

ERREURS

En fonction du système de fichiers, des erreurs autres que celles listées ci-dessous peuvent être retournées.

Les erreurs plus générales pour chown() sont listées ci-dessous.

EACCES
La permission de recherche est refusée sur une composante du préfixe du chemin. (Voir aussi path_resolution(7).)
EBADF
(fchown()) fd n'est pas un descripteur de fichier ouvert valide.
EBADF
(fchownat()) path est relatif mais dirfd n'est ni AT_FDCWD ni un descripteur de fichier valide.
EFAULT
path pointe en dehors de votre espace d'adressage accessible.
EINVAL
(fchownat()) Drapeau invalide spécifié dans flags.
EIO
(fchown()) Une erreur d'E/S de bas niveau s'est produite lors de la modification de l'inode.
ELOOP
Trop de liens symboliques ont été rencontrés lors de la résolution de path.
ENAMETOOLONG
path est trop long.
ENOENT
Le fichier n'existe pas.
ENOMEM
Mémoire noyau insuffisante disponible.
ENOTDIR
Une composante du préfixe du chemin n'est pas un répertoire.
ENOTDIR
(fchownat()) path est relatif et dirfd est un descripteur de fichier faisant référence à un fichier autre qu'un répertoire.
EPERM
Le processus appelant n'avait pas les permissions requises (voir ci-dessus) pour changer le propriétaire et/ou le groupe.
EPERM
Le fichier est marqué comme immuable ou append-only. (Voir FS_IOC_SETFLAGS(2const).)
EROFS
Le fichier nommé réside sur un système de fichiers en lecture seule.

VERSIONS

La version 4.4BSD ne peut être utilisée que par le superutilisateur (c'est-à-dire que les utilisateurs ordinaires ne peuvent pas céder de fichiers).

NORMES

chown, fchown, lchown(2) — Manuel Linux

NOM

chown, fchown, lchown — changer le propriétaire et le groupe d'un fichier

BIBLIOTHÈQUE

Bibliothèque C standard (libc, depuis glibc)

SYNTAXE

#include <sys/types.h>
#include <unistd.h>

int chown(const char *pathname, uid_t owner, gid_t group);
int fchown(int fd, uid_t owner, gid_t group);
int lchown(const char *pathname, uid_t owner, gid_t group);

DESCRIPTION

Ces fonctions de bibliothèque modifient le propriétaire (ID utilisateur) et/ou le groupe (ID de groupe) du fichier désigné par pathname (pour chown et lchown) ou par le descripteur de fichier fd (pour fchown).

Seul le superutilisateur (root) peut modifier le propriétaire d'un fichier. Seul le superutilisateur ou un processus ayant le privilège CAP_CHOWN peut modifier le propriétaire d'un fichier. Seul le superutilisateur ou un processus ayant le privilège CAP_CHOWN ou le propriétaire du fichier peut modifier le groupe d'un fichier.

Si owner est -1, l'ID utilisateur du fichier n'est pas modifié. Si group est -1, l'ID de groupe du fichier n'est pas modifié.

La différence entre chown et lchown est la même que celle entre link et symlink : si pathname est un lien symbolique, chown opère sur le fichier auquel le lien pointe, tandis que lchown opère sur le lien lui-même. fchown opère sur le fichier pointé par le descripteur de fichier fd.

Selon le système de fichiers, les valeurs de owner et group peuvent être limitées à 16 bits. Pour plus de détails, voir la page de manuel chown32(2).

Lorsqu'un nouveau fichier est créé (par exemple, par open(2) ou mkdir(2)), son propriétaire est défini comme étant le même que l'ID utilisateur du système de fichiers du processus créateur. Le groupe du fichier dépend de divers facteurs, notamment le type de système de fichiers, les options utilisées pour monter le système de fichiers, et si le bit de mode set-group-ID est activé sur le répertoire parent. Si le système de fichiers supporte les options de montage mount(8) -o grpid (ou, de manière synonyme, -o bsdgroups) et -o nogrpid (ou, de manière synonyme, -o sysvgroups), alors les règles sont les suivantes :

•
Si le système de fichiers est monté avec -o grpid, alors le groupe d'un nouveau fichier est défini comme étant le même que celui du répertoire parent.
•
Si le système de fichiers est monté avec -o nogrpid et que le bit set-group-ID est désactivé sur le répertoire parent, alors le groupe d'un nouveau fichier est défini comme étant le même que l'ID de groupe (GID) du processus.
•
Si le système de fichiers est monté avec -o nogrpid et que le bit set-group-ID est activé sur le répertoire parent, alors le groupe d'un nouveau fichier est défini comme étant le même que celui du répertoire parent.

Depuis Linux 4.12, les options de montage -o grpid et -o nogrpid sont supportées par ext2, ext3, ext4 et XFS. Les systèmes de fichiers qui ne supportent pas ces options de montage suivent les règles de -o nogrpid.

glibc notes

Sur les noyaux plus anciens où fchownat() n'est pas disponible, la fonction wrapper glibc se rabat sur l'utilisation de chown() et lchown(). Lorsque path est relatif, glibc construit un nom de chemin basé sur le lien symbolique dans /proc/self/fd qui correspond à l'argument dirfd.

NFS

Les sémantiques de chown() sont délibérément violées sur les systèmes de fichiers NFS pour lesquels le mappage UID est activé. De plus, les sémantiques de tous les appels système qui accèdent au contenu des fichiers sont violées, car chown() peut entraîner une révocation immédiate d'accès sur des fichiers déjà ouverts. La mise en cache côté client peut entraîner un délai entre le moment où la propriété a été changée pour autoriser l'accès à un utilisateur et le moment où le fichier peut effectivement être accédé par l'utilisateur sur d'autres clients.

Détails historiques

Les appels système Linux d'origine chown(), fchown() et lchown() ne supportaient que les ID utilisateur et groupe de 16 bits. Par la suite, Linux 2.4 a ajouté chown32(), fchown32() et lchown32(), supportant les ID 32 bits. Les fonctions wrappers glibc chown(), fchown() et lchown() gèrent transparencement les variations entre les versions du noyau.

Avant Linux 2.1.81 (sauf 2.1.46), chown() ne suivait pas les liens symboliques. Depuis Linux 2.1.81, chown() suit les liens symboliques, et il existe un nouvel appel système lchown() qui ne suit pas les liens symboliques. Depuis Linux 2.1.86, ce nouvel appel (qui a les mêmes sémantiques que l'ancien chown()) a le même numéro de syscall, et chown() a reçu le numéro nouvellement introduit.

EXEMPLES

Le programme suivant modifie la propriété du fichier nommé dans son deuxième argument de ligne de commande à la valeur spécifiée dans son premier argument de ligne de commande. Le nouveau propriétaire peut être spécifié soit comme un ID utilisateur numérique, soit comme un nom d'utilisateur (qui est converti en ID utilisateur en utilisant getpwnam(3) pour effectuer une recherche dans le fichier de mot de passe du système).

Source du programme

#include <pwd.h>
#include <stdio.h>
#include <stdlib.h>
#include <sys/types.h>
#include <unistd.h>
int
main(int argc, char *argv[])
{
    char           *endptr;
    uid_t          uid;
    struct passwd  *pwd;
    if (argc != 3 || argv[1][0] == '\0') {
        fprintf(stderr, "%s <propriétaire> <fichier>\n", argv[0]);
        exit(EXIT_FAILURE);
    }
    uid = strtol(argv[1], &endptr, 10);  /* Permet une chaîne numérique */
    if (*endptr != '\0') {         /* N'était pas une chaîne purement numérique */
        pwd = getpwnam(argv[1]);   /* Essaie d'obtenir l'UID pour le nom d'utilisateur */
        if (pwd == NULL) {
            perror("getpwnam");
            exit(EXIT_FAILURE);
        }
        uid = pwd->pw_uid;
    }
    if (chown(argv[2], uid, -1) == -1) {
        perror("chown");
        exit(EXIT_FAILURE);
    }
    exit(EXIT_SUCCESS);
}
