chown(2) Manuel des appels système chown(2)

NOM

chown, fchown, lchown, fchownat - changer la propriété d'un fichier

BIBLIOTHÈQUE

Bibliothèque C standard (libc, -lc)

SYNTAXE

#include <unistd.h>
int chown(const char *path, uid_t owner, gid_t group);
int fchown(int fd, uid_t owner, gid_t group);
int lchown(const char *path, uid_t owner, gid_t group);
#include <fcntl.h>           /* Définition des constantes AT_* */
#include <unistd.h>
int fchownat(int dirfd, const char *path,
             uid_t owner, gid_t group, int flags);

DESCRIPTION

Ces appels système changent le propriétaire et le groupe d'un fichier. Les appels système chown(), fchown() et lchown() ne diffèrent que par la manière dont le fichier est spécifié :

•
chown() change la propriété du fichier spécifié par path, qui est déréférencé s'il s'agit d'un lien symbolique.
•
fchown() change la propriété du fichier référencé par le descripteur de fichier ouvert fd.
•
lchown() est similaire à chown(), mais ne déréférence pas les liens symboliques.

Seul un processus privilégié (Linux : possédant la capacité CAP_CHOWN) peut changer le propriétaire d'un fichier. Le propriétaire d'un fichier peut changer le groupe du fichier pour tout groupe dont ce propriétaire est membre. Un processus privilégié (Linux : possédant CAP_CHOWN) peut changer le groupe arbitrairement.

Si owner ou group est spécifié comme -1, alors cet ID n'est pas modifié.

Lorsque le propriétaire ou le groupe d'un fichier exécutable est modifié par un utilisateur non privilégié, les bits de mode S_ISUID et S_ISGID sont effacés. POSIX ne spécifie pas si cela doit également se produire lorsque root effectue le chown() ; le comportement de Linux dépend de la version du noyau, et depuis Linux 2.2.13, root est traité comme les autres utilisateurs. Dans le cas d'un fichier non exécutable par le groupe (c'est-à-dire pour lequel le bit S_IXGRP n'est pas défini), le bit S_ISGID indique un verrouillage obligatoire et n'est pas effacé par un chown().

Lorsque le propriétaire ou le groupe d'un fichier exécutable est modifié (par n'importe quel utilisateur), tous les jeux de capacités pour le fichier sont effacés.

fchownat()

L'appel système fchownat() fonctionne exactement de la même manière que chown(), à l'exception des différences décrites ici.

Si path est relatif, il est interprété par rapport au répertoire référencé par le descripteur de fichier dirfd (plutôt que par rapport au répertoire de travail courant du processus appelant, comme le fait chown() pour un nom de chemin relatif).

Si path est relatif et dirfd est la valeur spéciale AT_FDCWD, alors path est interprété par rapport au répertoire de travail courant du processus appelant (comme chown()).

Si path est absolu, alors dirfd est ignoré.

L'argument flags est un masque de bits créé en combinant par OU 0 ou plusieurs des valeurs suivantes ;

AT_EMPTY_PATH (depuis Linux 2.6.39)
Si path est une chaîne vide, opère sur le fichier référencé par dirfd (qui peut avoir été obtenu en utilisant l'indicateur open(2) O_PATH). Dans ce cas, dirfd peut référencer tout type de fichier, pas seulement un répertoire. Si dirfd est AT_FDCWD, l'appel opère sur le répertoire de travail courant. Cet indicateur est spécifique à Linux ; définissez _GNU_SOURCE pour obtenir sa définition.
AT_SYMLINK_NOFOLLOW
Si path est un lien symbolique, ne le déréférencez pas : opérez à la place sur le lien lui-même, comme lchown(). (Par défaut, fchownat() déréférence les liens symboliques, comme chown().)

Voir openat(2) pour une explication de la nécessité de fchownat().

VALEUR DE RETOUR

En cas de succès, zéro est retourné. En cas d'erreur, -1 est retourné, et errno est défini pour indiquer l'erreur.

ERREURS

Selon le système de fichiers, des erreurs autres que celles listées ci-dessous peuvent être retournées.

Les erreurs plus générales pour chown() sont listées ci-dessous.

EACCES
L'autorisation de recherche est refusée sur un composant du préfixe du chemin. (Voir aussi path_resolution(7).)
EBADF
(fchown()) fd n'est pas un descripteur de fichier ouvert valide.
EBADF
(fchownat()) path est relatif mais dirfd n'est ni AT_FDCWD ni un descripteur de fichier valide.
EFAULT
path pointe en dehors de votre espace d'adressage accessible.
EINVAL
(fchownat()) Indicateur invalide spécifié dans flags.
EIO
(fchown()) Une erreur d'E/S de bas niveau s'est produite lors de la modification de l'inode.
ELOOP
Trop de liens symboliques ont été rencontrés lors de la résolution de path.
ENAMETOOLONG
path est trop long.
ENOENT
Le fichier n'existe pas.
ENOMEM
La mémoire noyau disponible était insuffisante.
ENOTDIR
Un composant du préfixe du chemin n'est pas un répertoire.
ENOTDIR
(fchownat()) path est relatif et dirfd est un descripteur de fichier faisant référence à un fichier autre qu'un répertoire.
EPERM
Le processus appelant n'avait pas les permissions requises (voir ci-dessus) pour changer le propriétaire et/ou le groupe.
EPERM
Le fichier est marqué comme immuable ou en mode ajout uniquement. (Voir FS_IOC_SETFLAGS(2const).)
EROFS
Le fichier nommé réside sur un système de fichiers en lecture seule.

VERSIONS

La version 4.4BSD ne peut être utilisée que par le superutilisateur (c'est-à-dire que les utilisateurs ordinaires ne peuvent pas céder des fichiers).

Le groupe du fichier dépend d'une série de facteurs, y compris le type de système de fichiers, les options utilisées pour monter le système de fichiers, et si le bit de mode set-group-ID est activé ou non sur le répertoire parent. Si le système de fichiers prend en charge les options de montage -o grpid (ou, synonymement -o bsdgroups) et -o nogrpid (ou, synonymement -o sysvgroups) de mount(8), alors les règles sont les suivantes :

•
Si le système de fichiers est monté avec -o grpid, alors le groupe d'un nouveau fichier est rendu identique à celui du répertoire parent.
•
Si le système de fichiers est monté avec -o nogrpid et que le bit set-group-ID est désactivé sur le répertoire parent, alors le groupe d'un nouveau fichier est rendu identique à l'ID de groupe (GID) du système de fichiers du processus.
•
Si le système de fichiers est monté avec -o nogrpid et que le bit set-group-ID est activé sur le répertoire parent, alors le groupe d'un nouveau fichier est rendu identique à celui du répertoire parent.

Au moment de Linux 4.12, les options de montage -o grpid et -o nogrpid sont prises en charge par ext2, ext3, ext4 et XFS. Les systèmes de fichiers qui ne prennent pas en charge ces options de montage suivent les règles de -o nogrpid.

notes glibc

Sur les anciens noyaux où fchownat() n'est pas disponible, la fonction enveloppe de glibc utilise en retour chown() et lchown(). Lorsque path est relatif, glibc construit un nom de chemin basé sur le lien symbolique dans /proc/self/fd qui correspond à l'argument dirfd.

NFS

Les sémantiques de chown() sont délibérément violées sur les systèmes de fichiers NFS qui ont le mappage UID activé. De plus, les sémantiques de tous les appels système qui accèdent au contenu du fichier sont violées, car chown() peut provoquer une révocation immédiate de l'accès sur des fichiers déjà ouverts. La mise en cache côté client peut entraîner un délai entre le moment où la propriété a été modifiée pour permettre l'accès à un utilisateur et le moment où le fichier peut réellement être accédé par l'utilisateur sur d'autres clients.

Détails historiques

Les appels système Linux d'origine chown(), fchown() et lchown() ne prenaient en charge que les identifiants utilisateur et groupe de 16 bits. Par la suite, Linux 2.4 a ajouté chown32(), fchown32() et lchown32(), prenant en charge les identifiants de 32 bits. Les fonctions enveloppes de glibc chown(), fchown() et lchown() gèrent de manière transparente les variations entre les versions du noyau.

Avant Linux 2.1.81 (sauf 2.1.46), chown() ne suivait pas les liens symboliques. Depuis Linux 2.1.81, chown() suit les liens symboliques, et il existe un nouvel appel système lchown() qui ne suit pas les liens symboliques. Depuis Linux 2.1.86, ce nouvel appel (qui a les mêmes sémantiques que l'ancien chown()) a le même numéro d'appel système, et chown() a reçu le numéro nouvellement introduit.

EXEMPLES

Le programme suivant modifie la propriété du fichier nommé dans son deuxième argument de ligne de commande à la valeur spécifiée dans son premier argument de ligne de commande. Le nouvel propriétaire peut être spécifié soit comme un identifiant utilisateur numérique, soit comme un nom d'utilisateur (qui est converti en identifiant utilisateur en utilisant getpwnam(3) pour effectuer une recherche dans le fichier de mots de passe système).

Source du programme

#include <pwd.h>
#include <stdio.h>
#include <stdlib.h>
#include <sys/types.h>
#include <unistd.h>
int
main(int argc, char *argv[])
{
    char           *endptr;
    uid_t          uid;
    struct passwd  *pwd;
    if (argc != 3 || argv[1][0] == '\0') {
        fprintf(stderr, "%s <propriétaire> <fichier>\n", argv[0]);
        exit(EXIT_FAILURE);
    }
    uid = strtol(argv[1], &endptr, 10);  /* Permet une chaîne numérique */
    if (*endptr != '\0') {         /* N'était pas une chaîne purement numérique */
        pwd = getpwnam(argv[1]);   /* Essaye d'obtenir l'UID pour le nom d'utilisateur */
        if (pwd == NULL) {
            perror("getpwnam");
            exit(EXIT_FAILURE);
        }
        uid = pwd->pw_uid;
    }
    if (chown(argv[2], uid, -1) == -1) {
        perror("chown");
        exit(EXIT_FAILURE);
    }
    exit(EXIT_SUCCESS);
}
