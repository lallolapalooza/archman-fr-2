LATEXMK(1) Manuel des commandes générales LATEXMK(1)

NOM

latexmk - générer un document LaTeX

SYNOPSIS

latexmk [options] [fichier ...]

DESCRIPTION

Latexmk automatise entièrement le processus de compilation d'un document LaTeX. Essentiellement, c'est comme une version spécialisée de l'utilitaire général make, mais qui détermine les dépendances automatiquement et possède d'autres fonctionnalités très utiles. Dans son mode de fonctionnement de base, latexmk reçoit le nom du fichier source principal d'un document, et il exécute la séquence appropriée de commandes pour générer une version .dvi, .ps, .pdf et/ou imprimée du document.

Par défaut, latexmk exécutera les commandes nécessaires pour générer un fichier .dvi, ce qui reproduit le comportement des versions antérieures lorsque seul latex était disponible.

Latexmk peut également être configuré pour s'exécuter en continu avec un aperçu approprié. Dans ce cas, le programme latex (ou l'un de ses dérivés), etc., est réexécuté chaque fois que l'un des fichiers sources est modifié, et l'aperçu met automatiquement à jour la vue à l'écran du document compilé.

Latexmk détermine quels sont les fichiers sources en examinant le fichier journal. (Optionnellement, il examine également la liste des fichiers d'entrée et de sortie générée par l'option -recorder des versions modernes de latex (et pdflatex, xelatex, lualatex). Voir la documentation de l'option -recorder de latexmk ci-dessous.) Lorsque latexmk est exécuté, il examine les propriétés des fichiers sources, et si certains ont été modifiés depuis la dernière génération du document, latexmk exécutera les divers programmes de traitement LaTeX nécessaires. En particulier, il répétera l'exécution de latex (ou d'un programme apparenté) suffisamment souvent pour résoudre toutes les références croisées ; selon les packages macro utilisés. Avec certains packages macro et classes de document, quatre, voire plus, exécutions peuvent être nécessaires. Si nécessaire, latexmk exécutera également bibtex, biber, et/ou makeindex. De plus, latexmk peut être configuré pour générer d'autres fichiers nécessaires. Par exemple, à partir d'un fichier de figure mis à jour, il peut automatiquement générer un fichier dans un format approprié comme encapsulated postscript ou autre pour être lu par LaTeX.

Latexmk propose deux options d'aperçu différentes. Avec l'option simple -pv, un aperçu dvi, postscript ou pdf est automatiquement lancé après la génération de la version dvi, postscript ou pdf du document. Le type de fichier à afficher est sélectionné en fonction des paramètres de configuration et des options de ligne de commande.

La deuxième option d'aperçu est la puissante option -pvc (mnémonique : « preview continuously » - aperçu en continu). Dans ce cas, latexmk s'exécute en continu, surveillant régulièrement tous les fichiers sources pour détecter tout changement. Chaque fois qu'un changement est détecté, latexmk exécute tous les programmes nécessaires pour générer une nouvelle version du document. Un bon aperçu mettra alors automatiquement à jour son affichage. Ainsi, l'utilisateur peut simplement modifier un fichier et, lorsque les modifications sont écrites sur le disque, latexmk automatise complètement le cycle de mise à jour du fichier .dvi (et/ou .ps et .pdf), et de rafraîchissement de l'affichage de l'aperçu. Ce n'est pas tout à fait WYSIWYG, mais s'en rapproche utilement.

Pour d'autres aperçus, l'utilisateur peut devoir demander manuellement à l'aperçu de mettre à jour son affichage, ce qui peut être (par exemple, avec certaines versions de xdvi et gsview) aussi simple que de forcer un redessin de son affichage.

Latexmk a la capacité d'imprimer une bannière en gris en diagonale sur chaque page lors de la création du fichier postscript. Il peut également, si nécessaire, appeler un programme externe pour effectuer d'autres post-traitements sur les fichiers dvi et postscript générés. (Voir les options -dF et -pF, et la documentation des variables de configuration $dvi_filter et $ps_filter.) Ces capacités datent d'anciennes versions de latexmk, mais sont actuellement non fonctionnelles. Plus de flexibilité peut être obtenue dans les versions actuelles, car les chaînes de commandes pour exécuter *latex peuvent maintenant être configurées pour exécuter plusieurs commandes. Cela étend également la possibilité de post-traiter les fichiers générés.

Latexmk est hautement configurable, à la fois depuis la ligne de commande et dans les fichiers de configuration, de sorte qu'il peut s'adapter à une grande variété de besoins des utilisateurs et de configurations système. Les valeurs par défaut sont définies en fonction du système d'exploitation, de sorte que latexmk fonctionne souvent sans configuration spéciale sur MS-Windows, cygwin, Linux, OS-X et d'autres systèmes UNIX. Voir la section « Configuration/Initialisation (rc) Files », puis les sections ultérieures « How to Set Variables in Initialization Files », « Format of Command Specifications », « List of Configuration Variables Usable in Initialization Files », « Custom Dependencies », et « Advanced Configuration »

Une complication très ennuyeuse gérée de manière très fiable par latexmk est que LaTeX est un système à passes multiples. À chaque exécution, LaTeX lit les informations générées lors d'une exécution précédente, pour des choses comme les références croisées et l'indexation. Dans les cas les plus simples, une seconde exécution de LaTeX suffit, et souvent le fichier journal contient un message indiquant la nécessité d'une passe supplémentaire. Cependant, il existe une grande variété de packages macro additionnels pour LaTeX, avec des comportements variés. Le résultat est de casser les déterminations simples du nombre d'exécutions nécessaires et des programmes à utiliser. Latexmk a une solution très générale et efficace à ces problèmes. La solution consiste à conserver entre les exécutions les informations sur les fichiers sources, et un symptôme est que latexmk génère un fichier supplémentaire (avec l'extension .fdb_latexmk, par défaut) qui contient les informations sur les fichiers sources.

OPTIONS ET ARGUMENTS DE LATEXMK SUR LA LIGNE DE COMMANDE

En général, la ligne de commande pour invoquer latexmk a la forme

latexmk [options] [fichier]

Toutes les options peuvent être introduites par un ou deux caractères « - », par exemple « latexmk -help » ou « latexmk --help ».

Note 1 : Dans la documentation, « *latex » signifie n'importe lequel des moteurs pris en charge, c'est-à-dire actuellement latex, lualatex, pdflatex, xelatex. La mention d'un moteur spécifique fait normalement référence à ce moteur spécifique. Les versions antérieures de cette documentation n'étaient pas aussi cohérentes. Le moteur utilisé pour compiler un document dépend de la configuration et des arguments de la ligne de commande.

Note 2 : En plus des options de la liste ci-dessous, latexmk reconnaît presque toutes les options reconnues par les programmes *latex dans leurs implémentations TeXLive et MiKTeX actuelles. Certaines des options de ces programmes déclenchent une action ou un comportement spécial de la part de latexmk, auquel cas elles ont des explications spécifiques dans ce document ; dans ce cas, elles peuvent ou non être transmises à *latex.

Exécutez latexmk avec -showextraoptions pour obtenir une liste des options que latexmk accepte et qui sont simplement transmises à *latex. Voir également l'explication de l'option -showextraoptions pour plus d'informations.

Définitions des options et arguments

fichier
Un ou plusieurs fichiers peuvent être spécifiés. Si aucun fichier n'est spécifié, latexmk s'exécutera par défaut sur tous les fichiers du répertoire de travail courant ayant l'extension « .tex ». Ce comportement peut être modifié : voir la description concernant la variable @default_files dans la section « List of configuration variables usable in initialization files ».

Si un fichier est spécifié sans extension, l'extension « .tex » est automatiquement ajoutée, tout comme le fait LaTeX. Ainsi, si vous spécifiez :

latexmk foo

alors latexmk opérera sur le fichier « foo.tex ».

Il existe certaines restrictions sur les caractères pouvant figurer dans un nom de fichier ; certains caractères sont soit interdits, soit problématiques pour les programmes latex, etc. Ces caractères sont : « $ », « % », « \ », « ~ », le caractère guillemet double, et les caractères de contrôle nul, tabulation, saut de page, retour chariot, saut de ligne, et suppression. De plus, « & » est interdit lorsqu'il est le premier caractère d'un nom de fichier.

-auxdir=FOO ou -aux-directory=FOO
Définit le répertoire des fichiers de sortie auxiliaires de *latex (.aux, .log etc). Ce sont tous les fichiers générés, à l'exception des fichiers de sortie finaux (.dvi, .ps, .pdf, .synctex.gz, .synctex). Voir l'option -outdir/-output-directory pour les répertoires des fichiers de sortie principaux, et l'option -out2dir pour les fichiers de sortie finaux.

Si le répertoire spécifié pour l'option -aux/-aux-directory est vide, alors le défaut est utilisé, ce qui signifie qu'il est le même que le répertoire de sortie.

Si vous utilisez également l'option -cd, et que le répertoire de sortie auxiliaire spécifié est un chemin relatif, alors le chemin est interprété par rapport au répertoire du document.

Voir la section DIRECTORIES AUXILIAIRES ET DE SORTIE pour plus de détails.

-bibtex
Lorsque le fichier source utilise des fichiers bbl pour la bibliographie, exécute bibtex ou biber selon les besoins pour régénérer les fichiers bbl.

Cette propriété peut également être configurée en définissant la variable $bibtex_use à 2 dans un fichier de configuration.

-bibtex-
Ne jamais exécuter bibtex ou biber. De plus, toujours traiter les fichiers .bbl comme précieux, c'est-à-dire ne pas les supprimer lors d'une opération de nettoyage.

Une utilisation courante de cette option est lorsqu'un document provient d'une source externe, avec ses fichiers bbl correspondants, et que l'utilisateur ne dispose pas des fichiers bib correspondants. Dans cette situation, l'utilisation de l'option -bibtex- empêchera latexmk d'essayer d'exécuter bibtex ou biber, ce qui entraînerait l'écrasement des fichiers bbl.

Cette propriété peut également être configurée en définissant la variable $bibtex_use à 0 dans un fichier de configuration.

-bibtex-cond
Lorsque le fichier source utilise un fichier bbl pour la bibliographie et que bibtex est utilisé pour générer la bibliographie, exécute bibtex selon les besoins pour régénérer les fichiers bbl uniquement si les fichiers bib pertinents existent. Ainsi, lorsque les fichiers bib ne sont pas disponibles, bibtex n'est pas exécuté, évitant ainsi l'écrasement du fichier bbl. De plus, toujours traiter les fichiers .bbl comme précieux, c'est-à-dire ne pas les supprimer lors d'une opération de nettoyage.

C'est le réglage par défaut. Il peut également être configuré en définissant la variable $bibtex_use à 1 dans un fichier de configuration.

La raison d'utiliser ce réglage est d'abord de permettre le passage automatique entre l'utilisation et la non-utilisation de bibtex en fonction de l'existence ou non d'un fichier bib. De plus, lors de la soumission d'articles à une revue scientifique, il est courant de soumettre uniquement les fichiers .tex et .bbl (plus les fichiers graphiques), mais pas de fichier .bib. Il est donc souvent utile de traiter les fichiers .bbl comme de véritables fichiers sources, qui doivent être préservés lors d'une opération de nettoyage.

Cette propriété peut également être configurée en définissant la variable $bibtex_use à 1 dans un fichier de configuration.

Note que lorsque biber est utilisé, et qu'un fichier bib n'existe pas, cette option n'empêche pas biber d'être exécuté, le fichier bbl étant alors incorrect. Voir la documentation sur $bibtex_use pour plus de détails. Cependant, un fichier bbl est traité comme précieux lors d'une opération de nettoyage.

-bibtex-cond1
Identique à -bibtex-cond sauf que les fichiers .bbl ne sont traités comme précieux que si un ou plusieurs fichiers bib n'existent pas.

Ainsi, si tous les fichiers bib existent, bibtex est exécuté pour générer les fichiers .bbl si nécessaire, et il est alors approprié de supprimer les fichiers bbl lors d'un nettoyage puisqu'ils peuvent être régénérés.

Cette propriété peut également être configurée en définissant la variable $bibtex_use à 1.5 dans un fichier de configuration.

Note que lorsque biber est utilisé, et qu'un fichier bib n'existe pas, cette option n'empêche pas biber d'être exécuté, le fichier bbl étant alors incorrect. Voir la documentation sur $bibtex_use pour plus de détails. Cependant, un fichier bbl est traité comme précieux lors d'une opération de nettoyage.

-bibtexfudge ou -bibfudge
Active le "fudge" de changement de répertoire pour bibtex. Voir la documentation de $bibtex_fudge pour plus de détails.
-bibtexfudge- ou -bibfudge-
Désactive le "fudge" de changement de répertoire pour bibtex. Voir la documentation de $bibtex_fudge pour plus de détails.
-bm <message>
Un message de bannière à imprimer en diagonale sur chaque page lors de la conversion du fichier dvi en postscript. Le message doit être un seul argument sur la ligne de commande, alors faites attention à la mise entre guillemets des espaces et autres.

Notez que si l'option -bm est spécifiée, l'option -ps est supposée.

-bi <intensité>
Quelle doit être la noirceur du message de bannière. Un nombre décimal entre 0 et 1. 0 est noir et 1 est blanc. La valeur par défaut est 0.95, ce qui convient sauf si votre cartouche de toner est presque vide.
-bs <échelle>
Un nombre décimal qui spécifie la taille à laquelle le message de bannière sera imprimé. Des expérimentations sont nécessaires pour obtenir la bonne échelle pour votre message, en règle générale l'échelle devrait être environ égale à 1100 divisé par le nombre de caractères dans le message. La valeur par défaut est 220.0, ce qui convient parfaitement pour des messages de 5 caractères.
-commands
Liste les commandes utilisées par latexmk pour traiter les fichiers, puis quitte.
-c
Nettoie (supprime) tous les fichiers régénérables générés par latex et bibtex ou biber sauf les dvi, postscript et pdf. Ces fichiers sont une combinaison de fichiers journaux, de fichiers aux, du fichier de base de données de latexmk contenant les informations sur les fichiers sources, et de ceux dont les extensions sont spécifiées dans la variable de configuration @generated_exts. De plus, les fichiers spécifiés par les variables de configuration $clean_ext et @generated_exts sont supprimés.

Ce nettoyage remplace un make régulier. Voir l'option -gg si vous voulez faire un nettoyage suivi d'un make.

Traitement des fichiers .bbl: Si $bibtex_use est défini à 0 ou 1, les fichiers bbl sont toujours traités comme non régénérables. Si $bibtex_use est défini à 1.5, les fichiers bbl sont considérés comme non régénérables conditionnellement: Si le fichier bib existe, alors les fichiers bbl sont régénérables et sont supprimés lors d'un nettoyage. Mais si $bibtex_use est 1.5 et qu'un fichier bib n'existe pas, alors les fichiers bbl sont traités comme non régénérables et ne sont donc pas supprimés.

En revanche, si $bibtex_use est défini à 2, les fichiers bbl sont toujours traités comme régénérables et sont supprimés lors d'un nettoyage.

Traitement des fichiers générés par des dépendances personnalisées: Si $cleanup_includes_cusdep_generated est différent de zéro, les fichiers régénérables sont considérés comme incluant ceux générés par des dépendances personnalisées et sont également supprimés. Sinon, ces fichiers ne sont pas supprimés.

-C
Nettoie (supprime) tous les fichiers régénérables générés par latex et bibtex ou biber. C'est la même chose que l'option -c avec l'ajout des fichiers dvi, postscript et pdf, et ceux spécifiés dans la variable de configuration $clean_full_ext.

Ce nettoyage remplace un make régulier. Voir l'option -gg si vous voulez faire un nettoyage suivi d'un make.

Voir l'option -c pour la spécification de si les fichiers .bbl sont traités comme non régénérables ou régénérables.

Si $cleanup_includes_cusdep_generated est différent de zéro, les fichiers régénérables sont considérés comme incluant ceux générés par des dépendances personnalisées et sont également supprimés. Sinon, ces fichiers ne sont pas supprimés.

-CA
(Obsolète). Maintenant équivalent à l'option -C. Voir cette option pour les détails.
-cd
Change vers le répertoire contenant le fichier source principal avant de le traiter. Alors tous les fichiers générés (.aux, .log, .dvi, .pdf, etc) seront relatifs au fichier source.

Cette option est particulièrement utile lorsque latexmk est invoqué à partir d'une interface graphique configurée pour invoquer latexmk avec un chemin d'accès complet au fichier source.

Cette option fonctionne en définissant la variable de configuration $do_cd à un ; vous pouvez définir cette variable si vous souhaitez configurer latexmk pour avoir l'effet de l'option -cd sans la spécifier sur la ligne de commande. Voir la documentation de cette variable.

-cd-
Ne PAS changer vers le répertoire contenant le fichier source principal avant de le traiter. Alors tous les fichiers générés (.aux, .log, .dvi, .pdf, etc) seront relatifs au répertoire courant plutôt qu'au fichier source.

C'est le comportement par défaut et cela correspond au comportement des programmes *latex. Cependant, ce n'est pas un comportement souhaitable lorsque latexmk est invoqué par une interface graphique configurée pour invoquer latexmk avec un chemin d'accès complet au fichier source. Voir l'option -cd.

Cette option fonctionne en définissant la variable de configuration $do_cd à zéro. Voir la documentation de cette variable pour plus d'informations.

-CF
Supprime le fichier contenant la base de données des informations des fichiers sources, avant de réaliser les autres actions demandées.
-d
Définit le mode brouillon. Ceci imprime le message de bannière "DRAFT" en diagonale sur votre page lors de la conversion du fichier dvi en postscript. La taille et l'intensité peuvent être modifiées avec les options -bs et -bi
options. L'option -bm remplacera cette option car il s'agit en fait d'une manière abrégée de spécifier :

latexmk -bm DRAFT

Notez que si l'option -d est spécifiée, l'option -ps est supposée.
-deps
Afficher une liste des fichiers dépendants après le traitement. Ceci se présente sous la forme d'une liste de dépendances telle qu'utilisée par le programme make, et convient donc pour une utilisation dans un Makefile. Elle donne une vue d'ensemble des fichiers sans lister les fichiers intermédiaires, autant que latexmk puisse les déterminer.

Par défaut, la liste des fichiers dépendants est envoyée à la sortie standard (c'est-à-dire, normalement à l'écran sauf si vous avez redirigé la sortie de latexmk). Mais vous pouvez définir le nom du fichier où la liste est envoyée avec l'option -deps-out=.

Voir la section « UTILISER latexmk AVEC make » pour un exemple d'utilisation d'une liste de dépendances avec make.

Les utilisateurs familiers avec GNU automake et gcc trouveront que l'option -deps est très similaire dans son but et ses résultats à l'option -M de gcc. (En fait, latexmk a aussi des options -M, -MF et -MP qui se comportent comme celles de gcc.)
-dependents
Équivalent à -deps.
-deps-
Ne pas afficher de liste de fichiers dépendants après le traitement. (C'est le comportement par défaut.)
-dependents-
Équivalent à -deps-.
-deps-escape=<chaîne>
Définit le type d'échappement utilisé pour les espaces dans la liste de dépendances. Les valeurs possibles sont « none », « unix », « nmake », correspondant respectivement à aucun échappement, à l'échappement avec un « \ » approprié pour le make Unix standard, et à l'échappement avec « ^ », approprié pour le nmake de Microsoft.
-deps-out=NOMDEFICHIER
Définit le nom du fichier dans lequel la liste des fichiers dépendants est écrite. Si l'argument NOMDEFICHIER est omis ou défini à « - », la sortie est envoyée à la sortie standard.

L'utilisation de cette option active également la sortie de la liste des fichiers dépendants après le traitement.
-dF
Filtrage de fichier Dvi. L'argument de cette option est un filtre qui générera un fichier dvi filtré avec l'extension « .dviF ». Tout traitement supplémentaire (par exemple, conversion en postscript, prévisualisation, impression) sera alors effectué sur ce fichier dvi filtré.

Exemple d'utilisation : Pour utiliser dviselect afin de sélectionner uniquement les pages paires du fichier dvi :

latexmk -dF "dviselect even" foo.tex
-diagnostics
Afficher des diagnostics détaillés pendant une exécution. Cela peut aider à déboguer des problèmes ou à comprendre le comportement de latexmk dans des situations difficiles.
-dir-report
Pour chaque fichier .tex traité, liste les paramètres des répertoires auxiliaires et de sortie, après qu'ils aient été normalisés à partir des paramètres spécifiés lors de l'initialisation. Voir la description de la variable $aux_out_dir_report pour plus de détails.
-dir-report-
Ne pas signaler les paramètres des répertoires auxiliaires et de sortie. (Par défaut)
-dir-report-only
Après que toute l'initialisation soit terminée, donner les paramètres pour les répertoires auxiliaires et de sortie, puis s'arrêter. Cette option est principalement utilisée pour le débogage de problèmes de configuration.
-dvi
Générer la version dvi du document en utilisant latex. (Et désactiver toute requête incompatible.)
-dvilua
Générer la version dvi du document en utilisant lualatex au lieu de latex. (Et désactiver toute requête incompatible.)
-dvi-
Désactiver la génération de la version dvi du document. (Cela peut être remplacé si un autre fichier est créé (par exemple, un fichier .ps) qui est généré à partir du fichier dvi, ou si aucun fichier généré du tout n'est demandé.)
-dvilualatex="COMMANDE"
Ceci définit la chaîne spécifiant la commande pour exécuter dvi lualatex. Il se comporte comme l'option -pdflatex, mais définit la variable $dvilualatex.

Note : Cette option, lorsqu'elle est fournie avec l'argument COMMANDE, ne fait que définir la commande pour invoquer dvilualatex ; elle n'active pas l'utilisation de dvilualatex. Cela est fait par d'autres options ou dans un fichier d'initialisation.
-e <code>
Exécuter le code d'initialisation spécifié avant le traitement. Le code est du code Perl de la même forme que celui utilisé dans les fichiers d'initialisation de latexmk. Pour plus de détails, voir les informations sur l'option -r, et la section sur « Fichiers de configuration/initialisation (RC) ». Le code est généralement une séquence d'instructions d'affectation séparées par des points-virgules.

Le code est exécuté lorsque l'option -e est rencontrée lors de l'analyse de la ligne de commande par latexmk. Voir l'option -r pour un moyen d'exécuter le code d'initialisation à partir d'un fichier. Une erreur entraîne l'arrêt de latexmk. Plusieurs instances des options -r et -e peuvent être utilisées, et elles sont exécutées dans l'ordre où elles apparaissent sur la ligne de commande.

Il faut faire attention à bien gérer les guillemets des caractères spéciaux dans le code sur la ligne de commande. Par exemple, si vous voulez définir la commande latex pour qu'elle utilise son option -shell-escape, alors sous UNIX/Linux vous pourriez utiliser la ligne :

latexmk -e '$latex=q/latex %O -shell-escape %S/' file.tex

Notez que les guillemets simples bloquent les shells de commandes UNIX/Linux normaux de considérer les caractères à l'intérieur des guillemets comme spéciaux. (Dans cet exemple, la construction q/.../ est une idiome Perl équivalente à l'utilisation de guillemets simples. Cela évite les complications d'avoir un caractère de guillemet à l'intérieur d'une chaîne déjà mise entre guillemets d'une manière indépendante du shell et du système d'exploitation.)

La ligne de commande ci-dessus NE fonctionnera PAS sous MS-Windows avec cmd.exe ou command.com ou 4nt.exe. Pour MS-Windows avec ces shells de commande, vous pourriez utiliser :

latexmk -e "$latex=q/latex %O -shell-escape %S/" file.tex

ou

latexmk -e "$latex='latex %O -shell-escape %S'" file.tex

Les deux derniers exemples NE fonctionneront PAS avec les shells de commandes UNIX/Linux.

(Note : les exemples ci-dessus sont destinés à montrer comment utiliser -e pour spécifier le code d'initialisation à exécuter. Mais l'effet particulier peut également être obtenu en utilisant l'option -latex avec moins de problèmes de gestion des guillemets.)
-emulate-aux-dir
Émuler l'utilisation d'un répertoire auxiliaire au lieu de laisser les programmes *latex s'en charger. (MiKTeX prend en charge -aux-directory, mais TeXLive ne le fait pas.)

-jobname=NAME
This option is available to allow you to specify the jobname that is used internally by latexmk, and also by the underlying LaTeX compiler (e.g. by latex, pdflatex, xelatex, lualatex) when generating output files. The default jobname is the basename of the main input file, which is the file specified on the command line to latexmk. The TeX file. The primary purpose is when multiple files are specified on the command line to latexmk, and you wish to use a jobname with a different file-dependent value for each file. For example, suppose you had .tex files test1.tex and test2.tex, and you wished to compare the results of compilation by *latex and those with xelatex. Then under a unix-type operating system you could use the command line


latexmk -pdf -jobname=%A-pdflatex *.tex
latexmk -pdfxe -jobname=%A-xelatex *.tex

Then the .aux, .log, and .pdf files from the use of pdflatex would have basenames test1-pdflatex and test2-pdflatex, while from xelatex, the basenames would be test1-xelatex and test2-xelatex.

Under MS-Windows with cmd.exe, you would need to double the percent sign, so that the percent character is passed to latexmk rather than being used to substitute an environment variable:


latexmk -pdf -jobname=%%A-pdflatex *.tex
latexmk -pdfxe -jobname=%%A-xelatex *.tex

Définir le type de fichier à imprimer. Cette option garantit également que le fichier requis est créé, et active l'impression.

Le cas (par défaut) -print=auto détermine le type de fichier d'impression automatiquement à partir de l'ensemble des fichiers qui sont générés. Le premier de la liste postscript, pdf, dvi parmi les fichiers à générer est celui utilisé pour l'impression.

-ps
Générer une version postscript du document. (Et désactiver toute demande incompatible.)
-ps-
Désactiver la génération de la version postscript du document. Ceci peut être utilisé pour remplacer un réglage dans un fichier de configuration. (Il peut être remplacé par une autre option nécessitant un fichier postscript, par exemple une demande d'impression.)
-pF
Filtrage de fichier postscript. L'argument de cette option est un filtre qui générera un fichier postscript filtré avec l'extension « .psF ». Tout traitement supplémentaire (par exemple, aperçu, impression) sera alors effectué sur ce fichier postscript filtré.

Exemple d'utilisation : utiliser psnup pour imprimer deux pages sur une seule page :

latexmk -ps -pF 'psnup -2' foo.tex

ou

latexmk -ps -pF "psnup -2" foo.tex

L'utilisation de guillemets simples ou doubles autour de « psnup -2 » dépendra de votre interpréteur de commandes, tel qu'utilisé par la version particulière de perl et le système d'exploitation de votre ordinateur.

-pv
Exécuter un prévisualiseur de fichier. Si l'option -view est utilisée, elle sélectionnera le type de fichier à prévisualiser (.pdf, .ps ou .dvi). Sinon, le visualiseur visualisera le type de fichier de sortie « le plus élevé » généré, avec l'ordre .pdf, .ps, .dvi (de haut en bas). Cette option est incompatible avec les options -p et -pvc, donc elle les désactive.
-pv-
Désactiver -pv.
-pvc
Exécuter un prévisualiseur de fichier et mettre continuellement à jour les fichiers .dvi, .ps et/ou .pdf chaque fois que des modifications sont apportées aux fichiers source (voir la Description ci-dessus). Le type de fichier généré et visualisé est régi par les autres options, et est le même que pour l'option -pv. L'option de prévisualisation continue -pvc ne peut fonctionner qu'avec un seul fichier. Donc, dans ce cas, vous ne spécifierez normalement qu'un seul nom de fichier sur la ligne de commande.
Il est également incompatible avec les options -p et -pv, il désactive donc ces options.

L'option -pvc désactive également le mode forcé (-f), comme il est normalement préférable pour le mode de prévisualisation continue. Si vous voulez vraiment le mode forcé, utilisez les options dans l'ordre -pvc -f.

Avec un bon aperçu, l'affichage sera automatiquement mis à jour. (Sous *certaines mais pas toutes* les versions d'UNIX/Linux, « gv -watch » le fait pour les fichiers postscript ; cela peut être défini par une variable de configuration. Cela fonctionnerait également pour les fichiers pdf, sauf pour un bug apparent dans gv qui provoque une erreur lors de la lecture du fichier pdf nouvellement mis à jour.) De nombreux autres aperçus nécessiteront une mise à jour manuelle.

Note importante : le programme acroread sous MS-Windows verrouille le fichier pdf et empêche l'écriture de nouvelles versions, il est donc déconseillé d'utiliser acroread pour afficher les fichiers pdf en mode prévisualisation continue. Il est préférable d'utiliser un autre visualiseur : SumatraPDF et gsview sont de bonnes possibilités.

Il existe d'autres méthodes pour organiser une mise à jour, notamment utiles pour de nombreuses versions de xdvi et xpdf. Celles-ci sont mieux définies dans la configuration de latexmk ; voir ci-dessous.

Notez que si latexmk plante ou est arrêté par l'utilisateur, l'aperçu « forké » continuera de fonctionner. Des invocations successives avec l'option -pvc ne créeront pas de nouveaux aperçus, mais latexmk utilisera normalement l'aperçu existant. (Cela se produira au moins lorsque latexmk s'exécute sous un système d'exploitation où il sait comment déterminer si un aperçu existant est en cours d'exécution.)

-pvc-
Désactiver -pvc.
-pvctimeout
En mode pvc, le délai d'inactivité expire après une période d'inactivité, qui est de 30 minutes par défaut. L'inactivité signifie une période pendant laquelle latexmk n'a détecté aucun changement de fichier et n'a donc effectué aucune action telle que la compilation du document.
-pvctimeout-
Ne pas expirer en mode pvc après une période d'inactivité.
-pvctimeoutmins=<temps>
Définir la période d'inactivité en minutes pour le délai d'attente pvc.
-quiet
Identique à -silent
-r <rcfile>
Lire le fichier d'initialisation spécifié (« fichier RC ») avant le traitement.

Faites attention à l'ordre : (1) Les fichiers d'initialisation standard -- voir la section ci-dessous sur les « Fichiers de configuration/initialisation (RC) » -- sont lus en premier. (2) Ensuite, les options de la ligne de commande sont traitées dans l'ordre où elles sont données. Par conséquent, si un fichier d'initialisation est spécifié par l'option -r, il est lu pendant cette deuxième étape. Ainsi, un fichier d'initialisation spécifié avec l'option -r peut remplacer à la fois les fichiers d'initialisation standard et les options spécifiées précédemment. Mais tout cela peut être remplacé par des options ultérieures.

Le contenu du fichier RC est simplement un morceau de code dans le langage de programmation Perl (typiquement une séquence d'instructions d'affectation) ; il est exécuté lorsque l'option -r est rencontrée lors de l'analyse de la ligne de commande de latexmk. Voir l'option -e pour un moyen de donner du code d'initialisation directement sur la ligne de commande de latexmk. Une erreur entraîne l'arrêt de latexmk. Plusieurs occurrences des options -r et -e peuvent être utilisées, et elles sont exécutées dans l'ordre où elles apparaissent sur la ligne de commande.

-rc-report
Après initialisation, afficher une liste des fichiers RC lus. (Par défaut)
-rc-report-
Après initialisation, ne pas afficher de liste des fichiers RC lus.
-recorder
Fournir l'option -recorder à *latex. Dans (la plupart des) versions modernes de ces programmes, cela se traduit par un fichier d'extension .fls contenant une liste des fichiers que ces programmes ont lus et écrits. Latexmk utilisera alors ce fichier pour améliorer sa détection des fichiers source et des fichiers générés après une exécution de *latex. C'est le paramètre par défaut de latexmk, sauf s'il est remplacé dans un fichier d'initialisation.

Pour plus d'informations, voir la documentation de la variable de configuration $recorder.

-recorder-
Ne pas fournir l'option -recorder à *latex.
-rules
Afficher une liste des règles et dépendances de latemk après traitement.
-rules-
Ne pas afficher de liste des règles et dépendances de latexmk après traitement. (Ceci est le défaut.)
-showextraoptions
Afficher la liste des options supplémentaires de *latex que latexmk reconnaît, mais qu'il transmet simplement aux programmes *latex lors de leur exécution. Ces options sont (actuellement) une combinaison de celles autorisées par les implémentations TeXLive et MiKTeX. (Si une option particulière est donnée à latexmk mais n'est pas gérée par l'implémentation particulière de *latex utilisée, ce programme affichera probablement un avertissement ou une erreur.) Ces options sont très nombreuses, mais ne sont pas listées dans cette documentation car elles n'affectent pas les actions de latexmk.

Il y a quelques options (par exemple, -includedirectory=dir, -initialize, -ini) qui ne sont pas reconnues, soit parce qu'elles ne correspondent pas aux opérations prévues par latexmk, soit parce qu'elles nécessitent un traitement spécial par latexmk qui n'est pas implémenté (du moins, pas encore).

Il existe certaines options pour *latex (par exemple, -recorder) qui déclenchent des actions ou un comportement spécial de latexmk lui-même. Selon l'action, elles peuvent également être transmises sous une certaine forme au programme *latex appelé, et/ou affecter d'autres programmes. Ces options ont des entrées dans cette documentation. Parmi ces options figurent : -jobname=STRING, -aux-directory=dir, -output-directory=DIR, -quiet, et -recorder.

Il existe également des options acceptées par *latex, mais qui déclenchent plutôt des actions purement par latexmk : -help, -version.

-silent
Exécuter les commandes silencieusement, c'est-à-dire avec des options qui réduisent la quantité de diagnostics générés. Par exemple, avec les paramètres par défaut, la commande « latex -interaction=batchmode » est utilisée pour latex, et de même pour ses semblables.

Voir aussi les options -logfilewarninglist et -logfilewarninglist-.

Réduit également le nombre de messages d'information que latexmk lui-même génère.

Pour modifier les options utilisées pour exécuter les commandes silencieusement, vous devez configurer latexmk avec des valeurs modifiées de ses variables de configuration, les plus pertinentes étant $bibtex_silent_switch, $biber_silent_switch, $dvipdf_silent_switch, $dvips_silent_switch, $dvilualatex_silent_switch, $latex_silent_switch, $lualatex_silent_switch $makeindex_silent_switch, $pdflatex_silent_switch, et $xelatex_silent_switch

-stdtexcmds
Définit les commandes pour latex, etc, de sorte qu'elles soient les commandes standard. Ceci est utile pour remplacer des configurations spéciales.

Le résultat est que $latex = 'latex %O %S', et de même pour $pdflatex, $lualatex, et $xelatex. (L'option -no-pdf nécessaire pour $xelatex est fournie automatiquement, étant donné que %O apparaît dans la définition.)

-time
Afficher le temps utilisé. (Sur MS Windows, ce qui est affiché est le temps d'horloge ; sur d'autres systèmes, le temps CPU.) Voir également la variable de configuration $show_time.
-time-
Ne pas afficher le temps utilisé. Voir également la variable de configuration $show_time.
-use-make
Lorsque, après une exécution de *latex, il y a des avertissements sur des fichiers manquants (par exemple, comme demandé par les commandes LaTeX \input, \include et \includegraphics), latexmk essaie de les créer par une dépendance personnalisée. Si aucune dépendance personnalisée pertinente avec un fichier source approprié n'est trouvée, et si l'option -use-make est définie, alors en dernier recours latexmk essaiera d'utiliser le programme make pour essayer de créer les fichiers manquants.

Notez que le nom de fichier peut être spécifié sans extension, par exemple par \includegraphics{drawing} dans un fichier LaTeX. Dans ce cas, latexmk essaiera de créer drawing.ext avec ext défini à tour de rôle pour les extensions possibles qui sont pertinentes pour latex (ou selon le cas pour pdflatex, lualatex, xelatex).

Voir également la documentation de la variable de configuration $use_make_for_missing_files.

-use-make-
Ne pas utiliser le programme make pour essayer de créer des fichiers manquants. (Par défaut.)
-usepretex
Définit les lignes de commande pour latex, etc, de sorte qu'elles utilisent le code défini par la variable $pre_tex_code ou celui défini par l'option -pretex=CODE pour exécuter le code TeX spécifié avant que le fichier source ne soit lu. Cette option remplace toute définition précédente des lignes de commande.

Le résultat est que $latex = 'latex %O %P', et de même pour $pdflatex, $lualatex, et $xelatex. (L'option -no-pdf nécessaire pour $xelatex est fournie automatiquement, étant donné que %O apparaît dans la définition.)

-usepretex=CODE
Équivalent à -pretex=CODE -usepretex. Exemple


latexmk -usepretex='\AtBeginDocument{Message\par}' foo.tex

-v ou -version
Affiche le numéro de version de latexmk.
-verbose
Opposé de -silent. C'est le réglage par défaut.
-view=default, -view=dvi, -view=hnt, -view=ps, -view=pdf, -view=none
Définit le type de fichier utilisé lors de la demande de prévisualisation (par exemple, par les options -pv ou -pvc). Par défaut, le système visualise le fichier du type "le plus élevé" demandé (dans l'ordre croissant : .dvi, .hnt, .ps, .pdf).

Notez la possibilité de -view=none, où aucun visualiseur n'est ouvert du tout. Un exemple d'utilisation est en conjonction avec l'option -pvc, lorsque vous souhaitez que latexmk effectue une compilation automatiquement chaque fois que les fichiers sources changent, mais que vous ne souhaitez pas qu'un prévisualiseur s'ouvre.

-Werror
Cela amène latexmk à retourner un code de statut non nul si l'un des fichiers traités génère un avertissement concernant des problèmes de citations ou de références (c'est-à-dire des citations ou références non définies ou des références multiples définies). Ceci intervient après que latexmk ait terminé toutes les exécutions nécessaires pour tenter de résoudre les références et les citations. Ainsi, -Werror amène latexmk à traiter ces avertissements comme des erreurs, mais uniquement lorsqu'ils se produisent lors de la dernière exécution de *latex et seulement après que le traitement soit terminé. Peut également être défini par la variable de configuration $warnings_as_errors.
-xdv
Génère la version xdv du document en utilisant xelatex. (Et désactive toute demande incompatible.)
-xelatex
Utilise xelatex. C'est-à-dire, utilise xelatex pour traiter le(s) fichier(s) source. Ceci entraînera la génération d'un pdf (mais indirectement via un fichier xdv). (Et désactive toute demande incompatible.)

Cette option est équivalente à l'utilisation de l'option suivante :


-pdfxe

[Note : Notez que la méthode d'implémentation de cette option, mais pas son effet principal prévu, diffère de certaines versions antérieures de latexmk. Latexmk utilise d'abord xelatex pour créer un fichier .xdv, et effectue toutes les exécutions supplémentaires nécessaires (y compris celles de bibtex, etc.). Ce n'est qu'après cela qu'il crée le fichier pdf à partir du fichier .xdv, en utilisant xdvipdfmx. Voir la documentation de -pdfxe pour savoir pourquoi cela est fait.]

-xelatex="COMMAND"
Définit la chaîne spécifiant la commande pour exécuter xelatex. Elle définit la variable $xelatex.

Avertissement : Il est important de s'assurer que -no-pdf est utilisé lorsque xelatex est appelé, car latexmk s'attend à ce que xelatex produise un fichier .xdv, et non un fichier .pdf. Si vous fournissez %O dans la spécification de la commande, cela sera fait automatiquement. Voir la documentation de l'option -pdfxe pour savoir pourquoi latexmk crée un fichier .xdv plutôt qu'un fichier .pdf lorsque xelatex est utilisé.

Un exemple d'utilisation de l'option -xelatex :


latexmk -pdfxe -xelatex="xelatex --shell-escape %O %S" foo.tex

Note : Cette option, lorsqu'elle est fournie avec l'argument COMMAND, ne fait que définir la commande pour l'invocation de xelatex ; elle n'active pas l'utilisation de lualatex. Cela est fait par d'autres options ou dans un fichier d'initialisation.

Compatibilité entre les options

L'option de prévisualisation continue -pvc ne peut fonctionner qu'avec un seul fichier. Ainsi, dans ce cas, vous ne spécifierez normalement qu'un seul nom de fichier sur la ligne de commande.

Les options -p, -pv et -pvc sont mutuellement exclusives. Ainsi, chacune de ces options désactive les autres.

EXEMPLES

% latexmk thesis		# exécute latex suffisamment de fois pour résoudre
				les références croisées
% latexmk -pvc -ps thesis	# exécute latex suffisamment de fois pour résoudre
					les références croisées, crée un fichier postscript,
					lance un visualiseur. Ensuite, surveille les changements dans le fichier source
					thesis.tex et tous les fichiers qu'il utilise. Après tout changement, réexécute latex
					le nombre approprié de fois et recrée le fichier postscript. Si latex
					rencontre une erreur, latexmk continuera de s'exécuter,
					surveillant les changements de fichiers sources.
% latexmk -c		# supprime les fichiers .aux, .log, .bbl, .blg, .dvi,
					.pdf, .ps & .bbl

GESTION DES ERREURS, PROBLÈMES, ETC.

Quelques possibilités :

a. Si vous obtenez une erreur étrange, examinez attentivement la sortie affichée à l'écran et dans les fichiers journaux. Bien que la sortie de latex soit notoirement verbeuse (et que latexmk y ajoute), cette verbosité a une raison : permettre à l'utilisateur de diagnostiquer les problèmes. Latexmk répète certains messages à la fin d'une exécution qui, selon lui, pourraient autrement être facilement manqués au milieu d'autres sorties.

b. En général, rappelez-vous que latexmk effectue son travail en exécutant d'autres programmes. Votre première priorité en cas d'erreurs devrait être d'examiner ce qui s'est mal passé avec les programmes individuels. Ensuite, vous devrez corriger les causes des erreurs dans les exécutions de ces programmes. (Souvent, celles-ci proviennent d'erreurs dans le document source, mais elles peuvent aussi concerner des paquets LaTeX manquants, etc.)

c. Si latexmk n'exécute pas les programmes comme vous le souhaitez, vous devrez consulter cette documentation pour connaître la liste des options de ligne de commande, puis les sections sur les fichiers de configuration/initialisation. Une grande partie du comportement de latexmk est configurable pour faire face à des situations particulières. (Mais il y a beaucoup de lecture !)

Le reste de ces notes contient des idées pour gérer des situations plus difficiles.

d. Des astuces supplémentaires peuvent impliquer le remplacement des commandes standard exécutées par latexmk par d'autres commandes ou scripts.

e. Pour des exemples possibles de code à utiliser dans un fichier RC, consultez le répertoire example_rcfiles dans la distribution de latexmk (par exemple, à http://mirror.ctan.org/support/latexmk/example_rcfiles). Même si ces exemples ne font pas ce que vous voulez, ils peuvent vous inspirer.

f. Il existe une astuce utile lorsque vous utilisez lualatex au lieu de pdflatex (et dans certaines situations similaires). Le problème est que latexmk ne détecte pas une dépendance sur un fichier, disons bar.baz, qui est lu par le code lua de votre document au lieu de la partie LaTeX. (Ainsi, si vous modifiez bar.baz et réexécutez latexmk, latexmk pensera qu'aucun fichier n'a changé et ne réexécutera pas lualatex, alors que si vous aviez '\input{bar.baz}' dans la partie LaTeX du document, latexmk remarquerait le changement.) Une solution consiste simplement à placer le code suivant quelque part dans la partie LaTeX du document :


\typeout{(bar.baz)}

Ceci insère une ligne dans le fichier journal que latexmk traitera comme impliquant que le fichier bar.baz a été lu. (Actuellement, je ne connais pas de moyen de faire cela automatiquement.) Bien sûr, si le fichier a un nom différent, remplacez bar.baz par le nom de votre fichier.

g. Voir également la section "Configuration avancée : Quelques ressources supplémentaires".

h. Consultez tex.stackexchange, c'est-à-dire à http://tex.stackexchange.com/questions/tagged/latexmk Quelqu'un a peut-être déjà résolu votre problème.

i. Posez une question sur tex.stackexchange.com.

j. Ou demandez-moi (l'auteur de latexmk). Mon e-mail se trouve à la fin de cette documentation.

RÉPERTOIRES AUXILIAIRES ET DE SORTIE

L'exécution de *latex et des programmes associés génère un certain nombre de fichiers. Il est souvent pratique de faire en sorte que les fichiers générés se trouvent dans un répertoire différent de celui des fichiers sources d'un document. Pour nos besoins ici, nous identifions deux classes de fichiers générés.

Une classe comprend ce que l'on peut appeler les fichiers de sortie finaux, par exemple, le fichier .pdf généré en exécutant pdflatex, ou le fichier .dvi à partir de latex. Dans cette classe se trouvent également le fichier ps généré en appliquant dvips à un fichier .dvi. Il existe également des fichiers .synctec ou .synctex.gz qui peuvent être utilisés par les programmes affichant des fichiers .pdf et similaires pour relier les positions dans ces fichiers aux positions dans les fichiers sources.

La deuxième classe de fichiers est composée de tous les autres fichiers générés : Ceux-ci incluent notamment les fichiers .aux utilisés pour implémenter la référence croisée, et qui sont générés lors d'une exécution et lus lors d'une exécution ultérieure. De nombreux paquets génèrent encore d'autres fichiers intermédiaires, ainsi que des programmes comme bibtex, makeindex, etc. Il y a également des fichiers .log provenant de *latex et des fichiers correspondants d'autres programmes.

Utilisons le terme "répertoire de sortie" pour le répertoire qui reçoit les fichiers de sortie finaux, et "répertoire auxiliaire" pour le répertoire des autres fichiers générés. Si aucune option spéciale n'est fournie aux programmes *latex, ces répertoires sont par défaut le répertoire courant, et alors les fichiers générés ne sont pas séparés. Si les deux répertoires sont identiques, comme dans la situation la plus simple, alors tous les fichiers générés sont écrits dans le même répertoire, et on parle souvent simplement du répertoire de sortie, sans mentionner de répertoire auxiliaire distinct.

Les programmes *latex offrent un support pour cela : par l'option unique -output-directory pour les implémentations TeXLive, et par les options -aux-directory et -output-directory pour les implémentations MiKTeX. Un support spécial comme celui-ci est nécessaire pour deux raisons : Premièrement, il existe de nombreux paquets qui écrivent des fichiers et il faut s'assurer qu'ils sont automatiquement écrits dans le répertoire approprié sans aucune réécriture du code des paquets. Deuxièmement, les fichiers sont souvent relus lors d'exécutions ultérieures de *latex, et il est nécessaire que le programme sache où trouver ces fichiers.

Une complication est que l'implémentation TeXLive ne permet pas de répertoires auxiliaires et de sortie séparés. Latexmk gère cela en étant capable d'émuler un répertoire auxiliaire séparé : Dans cette méthode, il invoque *latex avec seulement l'option -output-directory, le répertoire n'étant pas défini sur le répertoire de sortie souhaité, mais sur le répertoire auxiliaire. Après avoir exécuté *latex, il déplace le

fichiers de sortie finaux. L'émulation peut être activée en définissant la variable de configuration $emulate_aux à un dans un fichier de configuration ou en utilisant l'option -emulate-aux-dir de latexmk. La méthode d'émulation fonctionne aussi bien si MiKTeX est utilisé.

Latexmk active également l'émulation si elle est jugée nécessaire, comme suit. Supposons que l'émulation soit initialement désactivée, mais que les répertoires aux et de sortie soient différents. Latexmk invoque alors *latex avec une option -aux-directory et, après l'exécution, constate qu'elle n'a pas été respectée, notamment parce que le fichier .log se trouve dans le répertoire de sortie plutôt que dans le répertoire aux. Latexmk active alors l'émulation et réessaie. On pourrait imaginer qu'il déplace tous les fichiers générés appropriés du répertoire de sortie vers le répertoire aux ; mais il existe une telle variété de possibilités pour ces fichiers qu'il est difficile de les identifier tous de manière fiable, sauf dans des cas simples.

Notez que le problème d'émulation ne se pose que lorsque l'utilisateur a fait en sorte que les répertoires aux et de sortie soient différents. Lorsqu'ils sont égaux, par exemple parce que l'utilisateur n'a défini que la variable $out_dir, latexmk invoque *latex avec uniquement une option -output-directory, ce qui fonctionne comme prévu avec TeXLive et MiKTeX.

De plus, latexmk organise les invocations de tous les programmes auxiliaires tels que bibtex et makeindex de manière à ce qu'ils lisent et écrivent les fichiers pertinents depuis et vers le répertoire aux. Des programmes tels que dvips, dvipdf, ps2pdf et xdvipdfmx sont invoqués de manière à ce qu'ils lisent depuis les emplacements appropriés et écrivent leur sortie dans le répertoire de sortie.

Fichiers considérés comme fichiers de sortie finaux, c'est-à-dire ceux qui appartiennent au répertoire de sortie plutôt qu'au répertoire aux : Ceux-ci ont les extensions .dvi, .ps., .pdf, .synctex et .synctex.gz. Un cas spécial, en raison de problèmes de compatibilité, concerne les fichiers .fls : voir ci-dessous.

Notez que xelatex, lorsqu'il est invoqué avec son option -no-pdf, comme le fait latexmk, génère un fichier .xdv, qui semble avoir le même statut qu'un fichier .dvi généré par latex. Néanmoins, latexmk traite .xdv comme un fichier intermédiaire qui se trouve dans le répertoire aux. Ceci est pour correspondre au traitement par MiKTeX de l'option -aux-directory. Comme justification supplémentaire, on peut dire que dans les conditions modernes, un fichier .xdv est (presque) toujours un fichier intermédiaire. Historiquement, la situation avec les fichiers .dvi de latex était différente, et des visualiseurs dvi existent actuellement.

Variables et options pour les répertoires : Les variables pour définir les répertoires aux et de sortie sont $aux_dir et $out_dir, avec les options de ligne de commande correspondantes -auxdir (ou -aux-directory) et -outdir (ou -output-directory). Lorsqu'une valeur pour ceux-ci est vide (ce qui est la valeur par défaut), cela implique l'utilisation d'une valeur par défaut : Pour le répertoire aux, la valeur par défaut est de le définir égal au répertoire de sortie. Pour le répertoire de sortie, la valeur par défaut est le répertoire courant.

Pour l'activation et la désactivation du mode d'émulation, il existe la variable de configuration $emulate_aux et les options -emulate-aux-dir, -emulate-aux-dir-, -noemulate-aux-dir.

Interaction avec l'option -cd : Lorsque l'option -cd est utilisée (ou le réglage équivalent de la variable $do_cd), latexmk change le répertoire de travail vers le répertoire du document avant d'invoquer *latex. Si les répertoires aux et/ou de sortie sont donnés par des chemins relatifs, par exemple par -outdir=output pour un répertoire nommé "output", alors les répertoires sont relatifs au répertoire du document, plutôt qu'au répertoire de travail qui était en vigueur lorsque latexmk a été invoqué. Ceci correspond au comportement de *latex lorsqu'il est invoqué avec le ou les arguments de répertoire fournis après le changement de répertoire de travail vers le répertoire du document.

Création automatique des répertoires aux et de sortie : Contrairement à *latex, si latexmk constate que le(s) répertoire(s) demandé(s) n'existe(nt) pas, il le(s) crée, évitant ainsi les erreurs lors de l'invocation de *latex.

Si le document utilise la macro \include pour lire un fichier .tex d'un sous-répertoire, *latex tentera d'écrire un fichier aux supplémentaire dans le sous-répertoire correspondant du répertoire aux. Si le sous-répertoire n'existe pas, *latex se plaindra de ne pas pouvoir écrire le fichier aux. Après l'exécution de *latex, latexmk détecte cette situation, crée le répertoire nécessaire et relance *latex avec la situation d'erreur corrigée.

Choix des répertoires aux et de sortie : Souvent, les répertoires aux et de sortie sont donnés comme sous-répertoires du répertoire du document, par exemple par -outdir=output. Mais il est possible de fournir, par exemple, un chemin absolu ou un chemin relatif à un répertoire parent, par exemple, "/tmp/foo" ou "../output". Sachez qu'en général cela peut causer des problèmes, notamment avec makeindex ou bibtex. En effet, les versions modernes de ces programmes refuseront par défaut de fonctionner lorsqu'ils constateront qu'on leur demande d'écrire dans un fichier situé dans un répertoire qui ne semble pas être le répertoire de travail courant ou l'un de ses sous-répertoires. Ceci fait partie des mesures de sécurité de l'ensemble du système TeX qui visent à empêcher les documents TeX malveillants ou erronés de manipuler incorrectement les fichiers d'un utilisateur.

Par défaut, latexmk évite ce problème : Avant d'exécuter bibtex et makeindex, latexmk change le répertoire de travail vers le répertoire aux, avec des réglages appropriés des chemins de recherche. L'utilisation ou non de cette astuce est régie par les variables $bibtex_fudge et $makeindex_fudge. Malheureusement, l'astuce rend parfois bibtex et makeindex incapables de trouver des fichiers.

Si nécessaire, l'astuce peut être désactivée. Mais cela est incompatible avec un répertoire aux comme "/tmp/foo" ou "../output". Si vous devez absolument traiter cette situation, et uniquement si vous devez le faire, alors vous devez désactiver les mesures de sécurité (et assumer les risques éventuels). Une façon de le faire est de définir temporairement une variable d'environnement du système d'exploitation openout_any à "a" (comme dans "all"), pour remplacer le réglage par défaut "paranoid".

Certains noms de répertoires aux et de sortie non autorisés sur Microsoft Windows : Il est naturel de vouloir utiliser le nom "aux" pour le répertoire aux, par exemple en utilisant l'option -auxdir=aux. Mais sur les systèmes d'exploitation Microsoft, "aux" est l'un des noms qui ne sont pas autorisés pour un fichier ou un répertoire. Je trouve utile de standardiser sur un nom comme "auxdir" (par exemple, en utilisant -auxdir=auxdir); cela fonctionne indépendamment du système d'exploitation.

Emplacement du fichier .fls : Une grande partie des informations de dépendance que latexmk utilise provient du fichier .fls généré lorsque *latex est invoqué avec l'option -recorder, ce que latexmk fait par défaut. Il peut sembler rationnel que cela soit écrit dans le répertoire aux. Mais en fait, les versions de MiKTeX antérieures à Oct. 2020 l'écrivaient dans le répertoire de sortie. Les versions ultérieures l'écrivent dans le répertoire aux. Pour y remédier, latexmk fait deux choses : Premièrement, si latexmk constate que le fichier .fls n'a été généré que dans le répertoire "incorrect" (ou inattendu), alors latexmk le copie dans le répertoire attendu, après quoi le fonctionnement de latexmk se poursuit correctement indépendamment du comportement de *latex. Deuxièmement, il permet de configurer son idée du répertoire "correct" (ou attendu) par la variable $fls_uses_aux_dir. Celle-ci est par défaut à zéro, pour correspondre au comportement actuel de MiKTeX.

AUTORISER LA MODIFICATION DU TYPE DE FICHIER DE SORTIE

Lorsqu'un des moteurs latex est exécuté, la situation habituelle est que latex produit un fichier .dvi, tandis que pdflatex et lualatex produisent un fichier .pdf. Pour xelatex, la valeur par défaut est de produire un fichier .pdf, mais pour optimiser le temps de traitement, latexmk exécute xelatex avec son option -no-pdf afin qu'il produise un fichier .xdv. Le traitement ultérieur par latexmk utilise cela comme point de départ.

Cependant, le fichier de sortie réel peut différer de l'attente normale ; et alors latexmk peut ajuster son traitement pour s'adapter à cette situation. La différence dans le type de fichier de sortie peut se produire pour deux raisons : L'une est que pour latex, pdflatex et lualatex, le document lui-même peut remplacer les valeurs par défaut. L'autre est qu'il peut y avoir une configuration, ou une mauvaise configuration, telle que le programme que latexmk invoque pour compiler le document n'est pas celui attendu, ou qu'il reçoit des options incompatibles avec ce que latexmk attend initialement.

Sous latex et pdflatex, le contrôle du format de sortie par le document se fait en réglant la macro \pdfoutput. Sous lualatex, la macro \outputmode est utilisée à la place.

Un exemple d'utilisation importante du contrôle du format de sortie par le document est un document qui utilise le package psfrag pour insérer des éléments graphiques dans le fichier de sortie. Le package psfrag réalise ses effets en insérant du code postscript dans la sortie de la compilation du document. Cela implique la compilation vers un fichier .dvi, suivie de la conversion en fichier postscript (soit directement, comme par dvips, soit implicitement, comme étape intermédiaire par dvipdf). Il est alors utile de forcer la sortie au format .dvi en insérant \pdfoutput=0 dans le préambule du document.

Un autre exemple est celui d'un document qui utilise des fichiers graphiques de type .pdf, .jpg et png. Avec le réglage par défaut pour le package graphicx, ceux-ci peuvent être traités lors de la compilation vers .pdf mais pas lors de la compilation vers .dvi. Dans ce cas, il est utile d'insérer \pdfoutput=1 dans le préambule du document pour forcer la compilation au format de sortie .pdf.

Dans tous ces cas, il est nécessaire que latexmk ajuste son traitement pour gérer une divergence entre le format de sortie réel (parmi .pdf, .dvi, .xdv) et celui initialement attendu, si possible. Latexmk le fait à condition que les conditions suivantes soient remplies.

La première est que la variable de configuration $allow_switch de latexmk soit définie à une valeur non nulle, comme c'est le cas par défaut. Si cette variable est à zéro, une divergence de types de fichiers dans les résultats de compilation entraîne une erreur.

La deuxième condition pour que latexmk puisse gérer un changement de type de sortie est qu'aucune demande explicite de fichiers .dvi ou .ps ne soit faite. Les demandes explicites sont faites par les options -dvi et -ps, -print=dvi, -print=ps, -view=dvi et -view=ps, et par les réglages correspondants des variables de configuration $dvi_mode, $postscript_mode, $print_type et $view. Les restrictions de type d'impression et de type de visualisation ne s'appliquent que lorsque l'impression et la visualisation sont explicitement demandées, respectivement. À cette fin, l'utilisation des options -pdfdvi et -pdfps (et le réglage correspondant de la variable $pdf_mode) ne compte pas comme une demande explicite

pour les fichiers .dvi et .ps ; ils sont simplement considérés comme une demande de création d'un fichier .pdf accompagnée d'une proposition initiale pour la voie de traitement pour y parvenir.

Notez que lors de l'adaptation d'un changement de type de fichier de sortie, il y a un changement substantiel dans le réseau de règles que latexmk utilise dans ses actions. La deuxième condition appliquée pour accommoder un changement est d'éviter les situations où le changement dans le réseau de règles est trop radical pour être facilement géré automatiquement.

latexmk - Implémentation Perl de emacs' latex.mk

latexmk [options] [fichier(s)]

DESCRIPTION

Le script latexmk est un script de construction et de gestion de dépendances qui automatise la construction de documents LaTeX et, dans une certaine mesure, de documents TeX. Il est similaire à make, mais a été conçu spécifiquement pour les besoins de LaTeX. Il est particulièrement utile pour gérer des documents complexes qui nécessitent plusieurs passes de compilation, la génération de bibliographies, d'index, etc.

L'objectif principal de latexmk est de s'assurer que le document LaTeX est correctement compilé, en exécutant les commandes nécessaires (comme latex, bibtex, makeindex, etc.) dans le bon ordre et le bon nombre de fois. Il suit les dépendances entre les fichiers (par exemple, les fichiers .aux, .toc, .bib) et recompile uniquement les parties nécessaires du document.

latexmk peut être configuré via des fichiers d'initialisation (fichiers rc), ce qui permet de personnaliser le comportement, les commandes utilisées, les options, etc.

FICHIERS D'INITIALISATION (FICHIERS RC)

latexmk peut être configuré en utilisant des fichiers d'initialisation (fichiers rc). Ces fichiers contiennent des instructions Perl qui définissent le comportement de latexmk. Les fichiers sont lus dans l'ordre suivant :

  1. system-wide rc file : Ce fichier est défini lors de l'installation de latexmk. Son emplacement varie selon le système d'exploitation.
  2. user-specific rc file : Ce fichier est généralement nommé .latexmkrc et se trouve dans le répertoire personnel de l'utilisateur.
  3. project-specific rc file : Ce fichier est généralement nommé .latexmk et se trouve dans le répertoire du projet, au même niveau que les fichiers source du document.

Les configurations définies dans les fichiers lus ultérieurement écrasent celles définies dans les fichiers lus précédemment.

CONFIGURATION DE COMMANDES

La configuration des commandes utilisées par latexmk se fait en définissant des variables spéciales dans les fichiers rc. Ces variables contiennent des chaînes de caractères qui représentent la commande à exécuter, avec des placeholders spéciaux qui seront remplacés par latexmk au moment de l'exécution.

Les placeholders couramment utilisés sont :

%O
Options pour la commande.
%S
Nom du fichier source.
%B
Nom de base du fichier source (sans extension).
%D
Nom du répertoire de sortie.
%T
Nom du fichier de travail (généralement le même que %S).

Voici quelques exemples de configuration de commandes :

Utilisation de placehoders : Si vous spécifiez des placeholders dans la définition d'une commande, latexmk les utilisera. Par exemple :


$latex = 'latex %O %S';

Si vous ne fournissez aucun placeholder dans la spécification d'une commande, latexmk utilisera les valeurs par défaut que son auteur estime appropriées. Cela permet la compatibilité avec les anciens fichiers de configuration de latexmk qui n'utilisaient pas de placeholders.

"Détacher" une commande : Normalement, lorsque latexmk exécute une commande, il attend que celle-ci se termine. C'est approprié pour les commandes comme latex, bien sûr. Mais pour les visualiseurs, la commande doit normalement s'exécuter de manière détachée, afin que latexmk lance le visualiseur, puis passe à sa prochaine tâche (ou se termine s'il n'y a rien d'autre à faire). Pour obtenir cet effet de détachement d'une commande, vous devez préfixer le nom de la commande par "start ", comme dans :


$dvi_previewer = 'start xdvi %O %S';

Cela sera traduit de manière appropriée pour votre système d'exploitation.

Notes : (1) Dans certaines circonstances, latexmk exécutera toujours une commande de manière détachée. C'est le cas pour un visualiseur en mode continu, car sinon, la visualisation continue n'aurait pas de sens. (2) Cela exclut la possibilité d'exécuter une commande nommée start. (3) Si le mot start apparaît plus d'une fois au début de la chaîne de commande, cela équivaut à n'en avoir qu'un seul. (4) Sous Cygwin, certaines complications surviennent, car Cygwin est un mélange complexe d'UNIX et de MS-Windows. Voir le code source pour la manière dont ce problème a été géré.

Noms de commandes contenant des espaces : Sous MS-Windows, il est courant que le nom d'une commande contienne des espaces, car les logiciels sont souvent installés dans un sous-répertoire de "C:\Program Files". De tels noms de commandes doivent être entourés de guillemets doubles, comme dans :

Utilisation des associations de fichiers MS-Windows : Une astuce utile sous les versions modernes de MS-Windows (par exemple, WinXP) consiste à utiliser simplement la commande 'start' :


$dvi_previewer = 'start %S';

Sous MS-Windows, cela exécutera le programme que le système a associé aux fichiers dvi. (Il en va de même pour un visualiseur de postscript et un visualiseur pdf.) Mais notez que cette astuce n'est pas toujours adaptée pour le visualiseur pdf, si votre système utilise acroread comme visualiseur pdf par défaut. Comme expliqué ailleurs, acroread sous MS-Windows ne fonctionne pas bien avec latex et latexmk, car acroread verrouille le fichier pdf.

Ne pas utiliser une commande particulière : Si une commande ne doit pas être exécutée, le nom de commande NONE est utilisé, comme dans :


$lpr = 'NONE lpr';

Ceci est généralement utilisé lorsqu'une commande appropriée n'existe pas sur votre système. La chaîne après "NONE" est effectivement un commentaire.

Options pour les commandes : La définition du nom d'une commande peut être utilisée non seulement pour changer le nom de la commande appelée, mais aussi pour ajouter des options à la commande. Supposons que vous souhaitiez que latexmk utilise latex avec les options source specials activées. Vous pourriez alors utiliser la ligne suivante dans un fichier d'initialisation :


$latex = 'latex --src-specials %O %S';

Exécuter une sous-routine au lieu d'une commande externe : Utilisez une spécification commençant par "internal", comme dans :


$latex = 'internal mylatex %O %S';
sub mylatex {
my @args = @_;
# Prétraitement possible ici
return system 'latex', @args;
}

Pour certaines des possibilités plus exotiques qui deviennent alors disponibles, voir la section "Configuration avancée : Quelques ressources supplémentaires et astuces avancées". Voir aussi quelques exemples dans le répertoire example_rcfiles de la distribution latexmk.

Astuces avancées : Normalement, on spécifie une seule commande pour les commandes invoquées par latexmk. Naturellement, s'il y a un traitement supplémentaire compliqué dont vous avez besoin dans votre situation spéciale, vous pouvez écrire un script (ou un fichier batch) pour effectuer le traitement, puis configurer latexmk pour utiliser votre script à la place du programme standard.

Vous pouvez également utiliser une sous-routine Perl au lieu d'un script - voir ci-dessus. C'est généralement la solution la plus flexible et la plus portable.

Il est également possible de configurer latexmk pour exécuter plusieurs commandes. Par exemple, si lors de l'exécution de pdflatex pour générer un fichier pdf à partir d'un fichier tex, vous devez exécuter un autre programme après pdflatex pour effectuer un traitement supplémentaire, vous pourriez faire quelque chose comme ceci :


$pdflatex = 'pdflatex --shell-escape %O %S; pst2pdf_for_latexmk %B';

Cette définition suppose que vous utilisez un système de type UNIX (ce qui inclut Linux et OS-X), de sorte que les deux commandes à exécuter sont séparées par le point-virgule au milieu de la chaîne.

Si vous utilisez MS-Windows, vous remplaceriez la ligne ci-dessus par :


$pdflatex = 'cmd /c pdflatex --shell-escape %O %S'
. '&& pst2pdf_for_latexmk %B';

Ici, le séparateur de commande UNIX ; est remplacé par &&. De plus, il y a un problème : certaines versions de Perl sur MS-Windows ne respectent pas le séparateur de commande ; ce problème est résolu en invoquant explicitement le processeur de ligne de commande MS-Windows cmd.exe.

LISTE DES VARIABLES DE CONFIGURATION UTILISABLES DANS LES FICHIERS D'INITIALISATION

Dans cette section sont spécifiées les variables dont les valeurs peuvent être ajustées pour configurer latexmk. (Voir la section précédente "Configuration/Initialisation (rc) Files" pour les fichiers où les configurations sont effectuées.)

Les valeurs par défaut sont indiquées entre crochets. Notez que pour les variables booléennes, concernant si latexmk se comporte ou non d'une certaine manière, une valeur non nulle, normalement 1, indique vrai, c'est-à-dire que le comportement se produit, tandis qu'une valeur nulle indique faux, c'est-à-dire que le comportement ne se produit pas.

$allow_subdir_creation [1]

Spécifie l'action à entreprendre lorsqu'un ou plusieurs messages dans le fichier .log indiquent un échec d'une tentative de compilation *latex pour écrire un fichier dans un sous-répertoire du répertoire de sortie parce que le sous-répertoire n'existait pas.

Si la valeur de $allow_subdir_creation est 0, aucune action n'est entreprise. Si elle est de 1, alors le sous-répertoire approprié est créé et une nouvelle exécution de *latex est déclenchée, mais seulement si le fichier en cours d'écriture est un fichier .aux. (Cela se produit, par exemple, si le document inclut un fichier d'un sous-répertoire du répertoire du document, via la commande \include. Si la valeur de $allow_subdir_creation est 2, alors la création du sous-répertoire est effectuée indépendamment du type de fichier concerné.

$allow_switch [1]

Contrôle ce qui se passe lorsque l'extension de sortie de latex, pdflatex, lualatex ou xelatex diffère de ce qui est attendu. (Les extensions possibles sont .dvi, .pdf, .xdv.) Cela peut se produire avec l'utilisation de la macro \pdfoutput dans un document compilé sous latex ou pdflatex, ou avec l'utilisation de la macro \outputmode sous lualatex. Cela peut également se produire avec certains types de configuration incorrecte.

Dans un tel cas, latexmk peut ajuster de manière appropriée son réseau de règles. L'ajustement est effectué si $allow_switch est activé, et si aucune demande de fichier dvi ou ps n'a été faite.

Voir la section AUTORISER LE CHANGEMENT D'EXTENSION DE SORTIE.

$always_view_file_via_temporary [0]
Indique si les fichiers .ps et .pdf doivent d'abord être créés dans un répertoire temporaire, puis déplacés vers leur emplacement final. (Cela s'applique aux opérations dvips, dvipdf et ps2pdf, ainsi qu'aux opérateurs de filtrage sur les fichiers .dvi et .ps. Cela ne s'applique pas à pdflatex, malheureusement, car pdflatex ne fournit aucun moyen de spécifier un nom choisi pour le fichier de sortie.)

Cette utilisation d'un fichier temporaire résout le problème que la création de ces fichiers peut prendre un temps considérable. Si un visualiseur (notamment gv) constate que le fichier a changé, il peut lire le nouveau fichier avant que le programme écrivant le fichier n'ait terminé son travail, ce qui peut causer des ravages.

Voir la variable $pvc_view_file_via_temporary pour un paramètre qui ne s'applique que si le mode preview-continuous (-pvc option) est utilisé. Voir $tmpdir pour la définition du répertoire où le fichier temporaire est créé.

$analyze_input_log_always [1]

Après une exécution de latex (etc), analyser toujours le .log pour les fichiers d'entrée dans les constructions <...> et (...). Sinon, l'analyse n'est effectuée que si le fichier fls n'existe pas ou est obsolète.

Dans des circonstances normales, les données du fichier fls sont fiables et le test du fichier journal génère de nombreux faux positifs ; généralement, il est préférable de régler $analyze_input_log_always à zéro. Mais le test du fichier journal est nécessaire au moins dans la situation suivante : lorsqu'un utilisateur a besoin de convaincre latexmk qu'un certain fichier est un fichier source, et que latexmk ne le trouve pas autrement. L'utilisateur peut alors écrire du code qui provoque l'écriture d'une ligne avec (...) dans le fichier journal. Un cas important concerne lualatex, qui ne génère pas toujours des lignes dans le fichier .fls pour les fichiers lua d'entrée.

(La situation avec lualatex est TRÈS dépendante de la version, par exemple, il y a eu un grand changement entre TeXLive 2016 et TeXLive 2017.)

Pour maintenir la compatibilité ascendante avec les anciennes versions de latexmk, la valeur par défaut est de définir $analyze_input_log_always à 1.

$auto_rc_use [1]
Indique s'il faut lire automatiquement les fichiers d'initialisation (rc) standard, qui sont le fichier RC système, le fichier RC de l'utilisateur et le fichier RC du répertoire courant. L'option de ligne de commande -norc peut être utilisée pour désactiver ce réglage. Chaque fichier RC peut également désactiver ce réglage, c'est-à-dire qu'il peut définir $auto_rc_use à zéro pour empêcher la lecture automatique des fichiers RC ultérieurs.

Cette variable n'affecte pas la lecture des fichiers RC spécifiés en ligne de commande par l'option -r.

$aux_dir [""]
Le répertoire des fichiers auxiliaires, c'est-à-dire le répertoire dans lequel les fichiers auxiliaires (aux, log, etc.) doivent être écrits par une exécution de *latex.

Si cette variable n'est pas définie, mais que $out_dir est définie, alors latexmk prend le répertoire auxiliaire égal au répertoire de sortie, qui est le répertoire dans lequel les fichiers de sortie finaux doivent être écrits.

Si aucune des deux variables n'est définie, alors le répertoire courant lors de l'invocation de *latex est utilisé à la fois pour les répertoires auxiliaires et de sortie.

Si les répertoires auxiliaires et de sortie sont distincts, alors le répertoire auxiliaire contient tous les fichiers générés à l'exception des "fichiers de sortie finaux", qui sont définis comme étant les fichiers .dvi, .ps, .pdf, .synctex et .synctex.gz.

Voir la section RÉPERTOIRES AUXILIAIRES ET DE SORTIE pour plus de détails.

$aux_out_dir_report [0]
Si cette variable est définie à 1, alors avant le traitement de chaque fichier .tex primaire, liste les paramètres des répertoires auxiliaires et de sortie, après qu'ils aient été normalisés à partir des paramètres spécifiés lors de l'initialisation.

Ce rapport rappelle où chercher les fichiers générés.

Le rapport est effectué par fichier .tex primaire, en raison des changements de répertoire possibles pour chaque fichier (lorsque l'option -cd est utilisée). Dans les cas les plus simples, les noms de répertoire sont les mêmes que ceux spécifiés à l'origine. Mais en général, un certain nettoyage/normalisation est effectué; cela améliore les performances et nettoie la sortie vers l'écran.

Si cette variable est définie à 2, alors arrêtez-vous après avoir signalé les paramètres des répertoires auxiliaires et de sortie, plutôt que de continuer le traitement des fichiers tex. Ce réglage est principalement utilisé pour le débogage des problèmes de configuration. Voir l'option -dir-report-only.

$bad_warning_is_error [0]
Indique s'il faut traiter les avertissements incorrects signalés par *latex dans le fichier journal comme des erreurs. Les spécifications des messages d'avertissement se trouvent dans @bad_warnings.
@bad_warnings
Tableau d'expressions régulières spécifiant les messages dans le fichier journal qui sont officiellement traités comme des avertissements plutôt que des erreurs par *latex, mais que l'utilisateur peut traiter comme des erreurs : Voir $bad_warning_is_error.

Actuellement, l'ensemble par défaut de ces avertissements concerne les messages sur \end se produisant à l'intérieur de constructions.

$banner [0]
Si non nul, le message de bannière est imprimé sur chaque page lors de la conversion du fichier dvi en postscript. Sans modifier la variable $banner_message, cela équivaut à spécifier l'option -d.

Notez que si $banner est non nul, le mode $postscript_mode est supposé et le fichier postscript est toujours généré, même s'il est plus récent que le fichier dvi.

$banner_intensity [0.95]
Équivalent à l'option -bi, il s'agit d'un nombre décimal compris entre 0 et 1 qui spécifie la densité d'impression du message de bannière. 0 est noir, 1 est blanc. La valeur par défaut est juste ce qu'il faut si votre cartouche de toner n'est pas trop basse.
$banner_message ["DRAFT"]
Le message de bannière à imprimer sur chaque page lors de la conversion du fichier dvi en postscript. Ceci est équivalent à l'option -bm.
$banner_scale [220.0]
Un nombre décimal qui spécifie la taille à laquelle le message de bannière sera imprimé. Des expérimentations sont nécessaires pour obtenir la bonne échelle pour votre message, à titre indicatif, l'échelle devrait être approximativement égale à 1100 divisé par le nombre de caractères dans le message. La valeur par défaut est juste ce qu'il faut pour les messages de 5 caractères. Ceci est équivalent à l'option -bs.
@BIBINPUTS
Ceci est une variable tableau, maintenant largement obsolète, qui spécifie les répertoires où latexmk doit rechercher les fichiers .bib. Par défaut, elle est définie à partir de la variable d'environnement BIBINPUTS du système d'exploitation. Si cette variable d'environnement n'est pas définie, une liste à un seul élément composée du répertoire courant est définie. Le format des noms de répertoire dépend de votre système d'exploitation, bien sûr. Exemples de définition de cette variable :


@BIBINPUTS = ( ".", "C:\\bibfiles" );
@BIBINPUTS = ( ".", "\\server\bibfiles" );
@BIBINPUTS = ( ".", "C:/bibfiles" );
@BIBINPUTS = ( ".", "//server/bibfiles" );
@BIBINPUTS = ( ".", "/usr/local/texmf/bibtex/bib" );

Notez que sous Windows, soit une barre oblique "/" soit une barre oblique inversée "\" peut être utilisée pour séparer les composants du chemin d'accès, donc les deux premiers et les deux derniers exemples sont équivalents. Chaque barre oblique inversée doit être doublée pour éviter les problèmes avec les règles de Perl pour l'écriture des chaînes. En général, il est plus simple d'utiliser toujours des barres obliques plutôt que des barres obliques inversées.

Note importante : Cette variable est maintenant largement obsolète dans la version actuelle de latexmk, car elle utilise une meilleure méthode de recherche de fichiers via la commande kpsewhich. Cependant, si votre système est inhabituel et ne dispose pas de la commande kpsewhich, vous devrez peut-être définir la variable @BIBINPUTS.

Le programme de traitement biber.
$biber_silent_switch ["--onlylog"]

Le programme de traitement BibTeX.
$bibtex_fudge [1]
Lors de l'utilisation de bibtex, indique s'il faut changer de répertoire pour aller vers $aux_dir avant d'exécuter bibtex.

Le besoin se pose comme suit :

a. Avec bibtex avant environ 2019, si le nom de fichier qui lui est donné contient un composant de chemin, il y avait un bug qui empêchait bibtex de trouver des fichiers aux supplémentaires, tels que ceux produits par la commande \include dans TeX.

b. Avec toutes les versions moyennement récentes de bibtex, bibtex peut refuser d'écrire ses fichiers bbl et blg, pour des raisons de sécurité, dans certains cas du composant de chemin du nom de fichier qui lui est donné.

Cependant, il existe également des cas rares où la méthode de changement de répertoire empêche bibtex de trouver certains fichiers bib ou bst. Dans ce cas, $bibtex_fudge doit être défini à 0.

$bibtex_silent_switch ["-terse"]
Commutateur(s) pour le programme de traitement BibTeX lorsque le mode silencieux est activé.
$bibtex_use [1]
Dans quelles conditions exécuter bibtex ou biber. Lorsque latexmk découvre d'après le fichier journal qu'une ou plusieurs bibliographies générées par bibtex/biber sont utilisées, il peut exécuter bibtex ou biber chaque fois que cela semble nécessaire pour régénérer le(s) fichier(s) bbl à partir de leur(s) fichier(s) de base de données bib source. Mais parfois, les fichiers bib ne sont pas disponibles (par exemple, pour un document obtenu à partir d'une archive externe), mais les fichiers bbl sont fournis. Dans ce cas, l'utilisation de bibtex ou biber entraînerait l'écrasement incorrect des précieux fichiers bbl. La variable $bibtex_use contrôle si cela se produit, et contrôle également si les fichiers .bbl sont supprimés lors d'une opération de nettoyage.

Les valeurs possibles de $bibtex_use sont :
0 : jamais utiliser bibtex ou biber ; jamais supprimer les fichiers .bbl lors d'un nettoyage.
1 : utiliser bibtex ou biber uniquement si les fichiers bib existent ; jamais
supprimer les fichiers .bbl lors d'un nettoyage.
1.5 : utiliser bibtex ou biber uniquement si les fichiers bib existent ;
supprimer conditionnellement les fichiers .bbl lors d'un nettoyage (c'est-à-dire, les supprimer uniquement lorsque
tous les fichiers bib existent).
2 : exécuter bibtex ou biber chaque fois qu'il semble nécessaire de mettre à jour le(s) fichier(s) bbl, sans tester l'existence des fichiers bib ; toujours supprimer les fichiers .bbl lors d'un nettoyage.

Note : Lorsque biber est utilisé, une utilisation conditionnelle de biber peut être problématique. Du point de vue de latexmk, le problème est que, compte tenu du fonctionnement de biber, une connaissance complète de ses fichiers source ne peut être obtenue qu'après avoir exécuté biber. En revanche, pour bibtex, des informations complètes sur les fichiers bib utilisés sont obtenues à partir des fichiers .aux après une exécution de *latex. Mais pour biber, les informations correspondantes sont quelque peu incomplètes ; il s'agit des informations obtenues dans le fichier .bcf qui est généré par le package biblatex lors d'une exécution de *latex.

$cleanup_includes_cusdep_generated [0]
Si non nul, spécifie que le nettoyage supprime également les fichiers générés par des dépendances personnalisées. (Lors d'un nettoyage, par exemple, en utilisant l'option -C, les dépendances personnalisées sont celles listées dans le fichier .fdb_latexmk d'une exécution précédente.)
$cleanup_includes_generated [0]
Si non nul, spécifie que le nettoyage supprime également les fichiers détectés dans le fichier fls (ou à défaut, dans le fichier journal) comme étant générés. Il inclura également les fichiers créés à partir de ces fichiers générés de première génération.

Cette opération est quelque peu dangereuse et peut avoir des conséquences imprévues, car les fichiers à supprimer sont déterminés à partir d'un fichier créé par *latex, qui peut contenir des informations erronées. Par conséquent, cette variable est désactivée par défaut, et les fichiers à supprimer sont alors limités à ceux explicitement spécifiés par les motifs configurés dans les variables clean_ext, clean_full_ext et @generated_exts. Les cas standard (par exemple, les fichiers .log) apparaissent dans la valeur initiale de latexmk pour le tableau @generated_exts.

$cleanup_mode [0]
Si non nul, spécifie le mode de nettoyage : 1 pour un nettoyage complet, 2 pour un nettoyage à l'exception des fichiers .dvi, .ps et .pdf, 3 pour un nettoyage à l'exception des fichiers dep et aux. (Il y a également un nettoyage supplémentaire spécifié par les variables $clean_ext, $clean_full_ext et @generated_exts.)

Cette variable est équivalente à la spécification de l'une des options -c ou -C. Mais elle sh

pas nécessaire de définir cette variable à partir d'un fichier RC.

$clean_ext [""]
Extensions supplémentaires des fichiers que latexmk doit supprimer lorsque l'une des options de nettoyage (-c ou -C) est sélectionnée. La valeur de cette variable est une chaîne contenant les extensions séparées par des espaces.

Il est également possible de spécifier un modèle plus général de fichier à supprimer, en utilisant le substitut %R, comme dans les commandes, et il est aussi possible d'utiliser des caractères génériques. Ainsi, en définissant


$clean_ext = "out %R-blx.bib %R-figures*.log pythontex-files-%R/*";

dans un fichier d'initialisation, cela impliquera que lorsqu'une opération de nettoyage est spécifiée, non seulement l'ensemble standard de fichiers est supprimé, mais aussi les fichiers de la forme FOO.out, FOO-blx.bib, FOO-figures*.log, et pythontex-files-FOO/*, où FOO représente le nom de base du fichier traité (comme FOO.tex).

La plupart des fichiers à supprimer sont relatifs au répertoire spécifié par $aux_dir. Notez que si $out_dir est défini mais pas $aux_dir, alors lors de son initialisation, latexmk définit $aux_dir égal à $out_dir. Une situation normale est donc que $aux_dir soit égal à $out_dir, ce qui est le seul cas directement pris en charge par TeXLive, contrairement à MiKTeX. Notez que même avec TeXLive, latexmk prend désormais en charge des valeurs différentes pour les répertoires -- voir l'explication de la variable $emulate_aux.

Si $out_dir et $aux_dir sont différents, latexmk supprime réellement tous les fichiers des noms spécifiés dans $aux_dir et $out_dir ; ceci est parce que dans certaines conditions d'erreur, les fichiers peuvent être placés dans $out_dir au lieu de $aux_dir. Cela gère également le cas de la suppression de tout fichier fls, puisque ce fichier se trouve dans $out_dir.

Les noms de fichiers spécifiés pour une opération de nettoyage peuvent faire référence non seulement à des fichiers ordinaires mais aussi à des répertoires. Les répertoires ne sont supprimés que s'ils sont vides. Un exemple d'application concerne pythontex, qui crée des fichiers dans un répertoire particulier. Vous pouvez organiser la suppression des deux, fichiers et répertoire, en définissant


$clean_ext = "pythontex-files-%R/* pythontex-files-%R";

Voir aussi la variable (tableau) @generated_exts. Par le passé, cette variable avait certains usages au-delà de ceux de $clean_ext. Mais maintenant, ils accomplissent les mêmes choses. En fait, après initialisation, y compris le traitement des options de ligne de commande, latexmk ajoute simplement la liste des extensions de $clean_ext au tableau @generated_exts.

$clean_full_ext [""]
Extensions supplémentaires des fichiers que latexmk doit supprimer lorsque l'option -C est sélectionnée, c'est-à-dire les extensions des fichiers à supprimer lors du nettoyage des fichiers .dvi, etc.

Des modèles plus généraux sont autorisés, comme pour $clean_ext.

Les fichiers spécifiés par $clean_full_ext à supprimer sont relatifs au répertoire spécifié par $out_dir.

$compiling_cmd [""], $failure_cmd [""], $warning_cmd [""], $success_cmd [""]

Ces variables spécifient des commandes qui sont exécutées à certains points des compilations. L'une des motivations de leur existence est de permettre des indications visuelles très utiles et pratiques de l'état de la compilation, même lorsque la fenêtre recevant la sortie écran de la compilation est cachée. Ceci est particulièrement utile en mode preview-continuous.

Les commandes sont exécutées aux points suivants : $compiling_cmd au début de la compilation, $success_cmd à la fin d'une compilation entièrement réussie, $failure_cmd à la fin d'une compilation infructueuse, $warning_cmd à la fin d'une compilation par ailleurs réussie qui donne des avertissements sur des citations ou des références non définies ou sur des références définies plusieurs fois. Si l'une des variables ci-dessus n'est pas définie ou est vide (situation par défaut), la commande correspondante n'est pas exécutée.

Cependant, lorsque $warning_cmd n'est pas définie, dans le cas d'une compilation avec des avertissements concernant les références ou les citations, mais sans autre erreur, l'une ou l'autre de $success_cmd ou $failure_cmd est utilisée (si elle est définie) en fonction du réglage de $warnings_as_errors.

Un exemple de réglage simple de ces variables est le suivant


$compiling_cmd = "xdotool search --name \"%D\" set_window --name \"%D compiling\"";
$success_cmd = "xdotool search --name \"%D\" set_window --name \"%D OK\"";
$warning_cmd = "xdotool search --name \"%D\" ".
"set_window --name \"%D CITE/REF ISSUE\"";
$failure_cmd = "xdotool search --name \"%D\" set_window --name \"%D FAILURE\"";

Ces commandes supposent que le programme xdotool est installé, que le visualiseur utilise un système de fenêtrage X pour l'affichage, et que le titre de la fenêtre contient le nom du fichier affiché, comme c'est normalement le cas. Lorsque les commandes sont exécutées, la chaîne de substitution %D est remplacée par le nom du fichier de destination, qui est le fichier visualisé. Les commandes ci-dessus aboutissent à l'ajout d'une chaîne appropriée au nom de fichier dans le titre de la fenêtre : " compiling", " OK", ou " FAILURE".

D'autres substituts utilisables sont %S, %T et %R, %S et %T étant normalement identiques. Ceux-ci peuvent être utiles pour une commande modifiant le titre de la fenêtre d'édition. L'indication visuelle dans un titre de fenêtre peut être utile, car l'utilisateur n'a pas à détourner constamment son attention vers la fenêtre de compilation (éventuellement cachée) pour connaître l'état de la compilation.

Les situations plus compliquées peuvent être mieux gérées en définissant une sous-routine Perl pour invoquer les commandes nécessaires, et en utilisant le mot-clé "internal" dans les définitions pour que la sous-routine soit invoquée. (Voir la section "Format des Spécifications de Commande" pour savoir comment faire cela.)

Naturellement, les réglages ci-dessus qui invoquent le programme xdotool ne sont applicables que lorsque le système de fenêtrage X est utilisé pour la ou les fenêtres concernées. Pour d'autres cas, vous devrez trouver les solutions logicielles disponibles.

@cus_dep_list [()]
Liste de dépendances personnalisée -- voir la section sur les "Dépendances Personnalisées".
@default_excluded_files [()]
Lorsque latexmk est invoqué sans fichiers spécifiés sur la ligne de commande, il traite par défaut tous les fichiers du répertoire courant avec l'extension .tex. (En général, il traitera les fichiers spécifiés dans la variable @default_files.)

Mais parfois, vous voulez exclure certains fichiers de cette liste par défaut. Dans ce cas, vous pouvez spécifier les fichiers exclus dans le tableau @default_excluded_files. Par exemple, si vous voulez traiter tous les fichiers .tex à l'exception de common.tex, qui n'est pas un fichier LaTeX autonome mais un fichier inclus par certains ou tous les autres, vous pouvez faire


@default_files = ("*.tex");


@default_excluded_files = ("common.tex");

Si vous avez un nombre important ou grand de fichiers à traiter, cette méthode vous évite de les lister en détail dans @default_files et de devoir mettre à jour la liste chaque fois que vous modifiez l'ensemble des fichiers à traiter.

Notes : 1. Cette variable n'a aucun effet sauf lorsque aucun fichier n'est spécifié sur la ligne de commande de latexmk. 2. Les caractères génériques sont autorisés dans @default_excluded_files.

@default_files [("*.tex")]
Liste par défaut des fichiers à traiter.

Si aucun nom de fichier n'est spécifié sur la ligne de commande, latexmk traite tous les fichiers tex spécifiés dans la variable @default_files, qui par défaut est définie sur tous les fichiers tex ("*.tex") du répertoire courant. C'est une commodité : il suffit de lancer latexmk et il traitera un ensemble approprié de fichiers. Mais parfois, vous ne voulez que certains de ces fichiers soient traités. Dans ce cas, vous pouvez lister les fichiers à traiter en définissant @default_files dans un fichier d'initialisation (par exemple, le fichier "latexmkrc" dans le répertoire courant). Alors, si aucun fichier n'est spécifié sur la ligne de commande, les fichiers que vous spécifiez en définissant @default_files seront traités.

Trois exemples :


@default_files = ("paper_current");


@default_files = ("paper1", "paper2.tex");


@default_files = ("*.tex", "*.dtx");

Notez que plusieurs fichiers peuvent être donnés, et que l'extension par défaut est ".tex". Les caractères génériques sont autorisés. Les parenthèses sont utilisées car @default_files est une variable tableau, c'est-à-dire qu'une séquence de spécifications de noms de fichiers est possible.

Si vous souhaitez que latexmk traite tous les fichiers .tex à quelques exceptions près, consultez la variable tableau @default_excluded_files.

@file_not_found
Il s'agit d'un tableau d'expressions régulières Perl qui sont des motifs pour trouver des messages dans le fichier .log d'une exécution de *latex indiquant qu'un fichier a été recherché et non trouvé. Pour voir l'ensemble par défaut actuel, vous devriez regarder la définition de @file_not_found dans le fichier latexmk.pl.

Dans l'expression régulière, la chaîne pour le nom du fichier manquant doit être encadrée par des parenthèses. Cela implique qu'après que latexmk ait obtenu une correspondance réussie avec le motif, la variable $1 est définie avec le nom du fichier, qui est ensuite récupéré par latexmk.

Si vous rencontrez un package qui donne un message de fichier manquant d'une forme différente de celle qui correspond à l'un des motifs intégrés, vous pouvez ajouter un autre motif au tableau. Un exemple serait :


push @file_not_found, '^No file\\s+(.+)\\s*$';

L'expression régulière elle-même est :


^Missing file\s+(.+)\s*$

Mais la spécification de chaîne correspondante dans l'instruction push doit avoir les antislashs doublés.

Cette expression régulière correspond à une ligne qui commence par "No file", puis a un ou plusieurs caractères d'espacement, puis n'importe quel nombre de caractères formant le nom du fichier, puis des espaces possibles, et enfin la fin de la ligne. (Voir la documentation sur les expressions régulières Perl pour les détails.)

$filetime_causality_threshold [5]
L'utilisation de cette variable est la suivante : À plusieurs endroits, latexmk doit déterminer si un fichier particulier a été produit lors d'une exécution juste terminée d'une règle/programme ou s'il s'agit d'un reste d'une exécution précédente. (Un exemple est la production d'un fichier .bcf par le package biblatex lors d'une exécution de *latex pour fournir des informations bibliographiques au programme biber. Si un fichier .bcf n'est pas produit lors d'une exécution actuelle de *latex, mais qu'il s'agit d'un reste d'une exécution précédente, alors latexmk doit conclure que le document .tex a changé de sorte que biber ne doit plus être utilisé.)

Le critère de latexmk pour qu'un fichier ait été produit lors d'une exécution est que l'heure de modification du fichier est plus récente que l'heure système au début de l'exécution. Fondamentalement, si l'heure de modification est antérieure à cela, alors c'est un reste d'une exécution précédente. Cependant, une utilisation naïve du critère peut, entre autres, se heurter à la granularité de la manière dont les heures de fichiers sont stockées dans certains systèmes de fichiers, ce qui signifie qu'il est possible que l'heure signalée par le système de fichiers pour un fichier soit une seconde ou plus antérieure à l'heure de modification réelle, la différence exacte étant assez aléatoire.

La variable $fi

letime_causality_threshold permet une certaine tolérance dans l'utilisation de l'heure de modification des fichiers par latexmk. Elle peut être assez généreuse ; elle doit simplement être inférieure à l'échelle de temps sur laquelle un utilisateur humain apporte des modifications aux fichiers sources d'un document (ou aux fichiers de configuration, etc).

$fls_uses_out_dir [0]
Cette variable détermine si le fichier .fls doit se trouver dans le répertoire de sortie au lieu du répertoire naturel, qui est le répertoire aux. Si la variable est non nulle, le fichier .fls doit se trouver dans le répertoire de sortie. Voir la section RÉPERTOIRES AUXILIAIRES ET DE SORTIE pour plus de détails sur ces répertoires. La raison de l'existence de la variable $fls_uses_out_dir y est expliquée.

Dans tous les cas, si latexmk constate qu'un fichier .fls a été généré dans le répertoire opposé à celui spécifié par $fls_uses_out_dir, il copie le fichier dans l'autre répertoire (répertoire aux ou répertoire de sortie, selon le cas). Le fichier est copié plutôt que simplement déplacé, afin d'éviter des conflits potentiels avec d'autres logiciels qui supposent que le fichier .fls est généré dans le répertoire où il a été écrit par *latex. Ainsi, l'effet d'un réglage incorrect de $fls_uses_out_dir n'est que de provoquer la génération d'une copie superflue du fichier .fls.

@generated_exts [( 'aux', 'bcf', 'fls', 'idx', 'ind', 'lof', 'lot', 'out', 'toc', 'blg', 'ilg', 'log', 'xdv' )]

Cette variable contient une liste d'extensions de fichiers qui sont générés pendant le traitement et qui doivent être supprimés lors d'une opération de nettoyage principale, telle qu'invoquée par l'option de ligne de commande -c. (L'utilisation de -C ou -gg effectue ce nettoyage et plus encore.)

Les valeurs par défaut sont les extensions des fichiers standard générés par *latex, bibtex, et similaires. (Notez que le nettoyage supprime également le fichier fdb_latexmk, mais cela est codé séparément dans latexmk, actuellement.)

Après l'initialisation de latexmk et le traitement de sa ligne de commande, les éléments de clean_ext sont ajoutés à @generated_exts. Ces deux variables ont donc la même signification (contrairement aux anciennes versions de latexmk).

Les éléments de @generated_exts sont normalement des extensions de fichiers dont le nom de base est le même que celui du fichier tex principal. Mais il est également possible de spécifier des motifs incluant ce nom de base --- voir l'explication de la variable $clean_ext.

En plus de spécifier les fichiers à supprimer lors d'un nettoyage, latexmk utilise la même spécification pour aider à l'examen des modifications dans les fichiers sources : dans certaines situations, il doit identifier ces modifications dans les fichiers (depuis une exécution précédente) qui sont censées être dues à l'édition d'un fichier par l'utilisateur. Ceci contraste avec les cas de fichiers générés par un programme exécuté par latexmk et qui diffèrent des résultats de l'exécution précédente. Cette utilisation de @generated_exts est normalement sans importance, compte tenu de la précision habituelle des autres méthodes de latexmk pour déterminer ces fichiers générés.

Un moyen pratique d'ajouter une extension supplémentaire à la liste, sans perdre celles déjà définies, est d'utiliser une commande push dans la ligne d'un fichier RC. Par exemple,


push @generated_exts, "end";

ajoute l'extension "end" à la liste des extensions générées prédéfinies. (Cette extension est utilisée par le package RevTeX, par exemple.)

%hash_calc_ignore_pattern
!!!Cette variable est réservée aux experts !!!

La règle générale que latexmk utilise pour déterminer quand une exécution supplémentaire d'un programme est nécessaire est que l'un des fichiers sources a changé. Mais considérez, par exemple, un package latex qui génère un fichier postscript encapsulé (un fichier "eps") qui doit être lu lors de l'exécution suivante. Le fichier contient une ligne de commentaire indiquant sa date et son heure de création. Lors de l'exécution suivante, l'heure change, latex constate que le fichier eps a changé, et relance donc latex. Cela provoque une boucle infinie, qui n'est terminée que parce que latexmk a une limite sur le nombre d'exécutions pour se prémunir contre les situations pathologiques.

Mais la ligne changeante n'a aucun effet réel, puisqu'il s'agit d'un commentaire. Vous pouvez indiquer à latex d'ignorer la ligne incriminée comme suit :


$hash_calc_ignore_pattern{'eps'} = '^%%CreationDate: ';

Ceci crée une règle pour les fichiers avec l'extension .eps concernant les lignes à ignorer. Le côté gauche est un idiome Perl pour définir un élément dans une table de hachage. Notez que l'extension de fichier est spécifiée sans point. La valeur, sur le côté droit, est une chaîne contenant une expression régulière. (Voir la documentation de Perl pour savoir comment elles sont spécifiées en général.) Cette expression régulière particulière spécifie que les lignes commençant par "%%CreationDate: " doivent être ignorées pour déterminer si un fichier de l'extension .eps donnée a changé.

Il n'y a qu'une seule expression régulière disponible pour chaque extension. Si vous avez besoin de plus d'un motif pour spécifier les lignes à ignorer, vous devez combiner les motifs en une seule expression régulière. La méthode la plus simple est de séparer les différents motifs simples par un caractère barre verticale (indiquant une "alternation" dans le jargon des expressions régulières). Par exemple,


$hash_calc_ignore_pattern{'eps'} = '^%%CreationDate: |^%%Title: ';

provoque l'ignorance des lignes commençant par "^%%CreationDate: " ou "^%%Title: ".

Il peut arriver qu'un motif à ignorer soit spécifié dans, par exemple, un fichier d'initialisation système ou utilisateur, et que vous souhaitiez le supprimer dans un fichier lu ultérieurement. Pour ce faire, vous utilisez la fonction delete de Perl, par exemple,


delete $hash_calc_ignore_pattern{'eps'};

$jobname [""]

Ceci spécifie le nom de travail, c'est-à-dire le nom de base utilisé pour les fichiers générés (.aux, .log, .dvi, .ps, .pdf, etc.). Si cette variable est une chaîne nulle, le nom de base est le nom de base du fichier tex principal. (Actuellement, la chaîne dans $jobname ne doit pas contenir d'espaces.)

Le marqueur '%A' est autorisé. Il sera substitué par le nom de base du fichier TeX. $jobname = "%A-$^O";

dans un fichier d'initialisation. (Ici, $^O est une variable fournie par perl qui contient le nom de perl pour le système d'exploitation.)

Supposons que vous ayez les fichiers .tex test1.tex et test2.tex. Ensuite, lorsque vous exécutez


latexmk -pdf *.tex

les deux fichiers seront compilés. Les fichiers .aux, .log et .pdf auront les noms de base test1-MSWin32 et test2-MSWin32 sur un système MS-Windows, test1-darwin et test2-darwin sur un système OS-X, et une variété de cas similaires sur les systèmes linux.

Le programme appelé pour localiser un fichier source lorsque le nom seul n'est pas suffisant. Cette variable de configuration n'a d'effet que lorsque latexmk s'exécute sous MS-Windows. Avec la valeur par défaut de 1 pour cette variable, lorsqu'une commande est exécutée sous MS-Windows, latexmk remplace "\" par le caractère séparateur entre les composants d'un nom de répertoire. $warnings_as_errors [0]
Normalement, latexmk reproduit le comportement de latex en considérant les références et citations non définies et les références multiples comme des conditions qui génèrent un avertissement mais pas une erreur. La variable $warnings_as_errors contrôle si ce comportement est modifié.

Lorsque la variable est non nulle, latexmk à la fin de son exécution retournera un code de statut non nul au système d'exploitation si l'un des fichiers traités génère un avertissement concernant des problèmes de citations ou de références (c'est-à-dire des citations ou références non définies ou des références définies plusieurs fois). Ceci intervient après que latexmk ait terminé toutes les exécutions nécessaires pour tenter de résoudre les références et citations. Ainsi, si $warnings_as_errors est non nul, latexmk traite ces avertissements comme des erreurs, mais seulement lorsqu'ils surviennent lors de la dernière exécution de *latex et seulement après le traitement

ing est terminé. Une valeur non nulle $warnings_as_errors peut être définie par l'option de ligne de commande -Werror.

Le comportement par défaut est normalement satisfaisant dans le cycle habituel édition-compilation-édition. Mais, par exemple, latexmk peut aussi être utilisé dans le cadre d'un processus de construction pour un projet plus important, par exemple, pour créer de la documentation lors de la construction d'une application logicielle. Il est alors souvent judicieux de considérer les avertissements de citation et de référence comme des erreurs qui nécessitent l'interruption du processus de construction global. Bien sûr, puisque plusieurs exécutions de *latex sont généralement nécessaires pour résoudre les références et les citations, ce qui compte, ce ne sont pas les avertissements lors de la première exécution, mais les avertissements lors de la dernière exécution ; latexmk en tient compte de manière appropriée.

De plus, lorsque le mode aperçu-continu est utilisé, une valeur non nulle pour $warnings_as_errors modifie l'utilisation des commandes $failure_cmd, $warning_cmd et $success_cmd après une compilation. S'il y a des avertissements de citation ou de référence, mais aucune autre erreur, le comportement est le suivant. Si $warning_cmd est défini, il est utilisé. S'il n'est pas défini, alors si $warnings_as_errors est non nul et $failure_cmd est défini, alors $failure_cmd. Sinon $success_cmd est utilisé, s'il est défini. (L'explication précédente est assez compliquée, car latexmk doit gérer le cas où une ou plusieurs des commandes ne sont pas définies.)

DÉPENDANCES PERSONNALISÉES

Dans n'importe quel fichier RC, un ensemble de dépendances personnalisées peut être configuré pour convertir un fichier avec une extension en un fichier avec une autre. Un exemple d'utilisation serait de permettre à latexmk de convertir un fichier .fig en .eps pour être inclus dans le fichier .tex.

Définir une dépendance personnalisée :

L'ancienne méthode de configuration de latexmk pour utiliser une dépendance personnalisée consistait à manipuler directement le tableau @cus_dep_list qui contient les informations définissant les dépendances personnalisées. (Voir la section "Ancienne méthode de définition des dépendances personnalisées" pour les détails.) Cette méthode fonctionne toujours, mais n'est plus préférée.

Une meilleure méthode consiste à utiliser les sous-routines qui permettent des manipulations pratiques de la liste des dépendances personnalisées. Ce sont :


add_cus_dep( extension_source, extension_cible, doit_exister, sous_routine )
remove_cus_dep( extension_source, extension_cible )
show_cus_dep()

Les arguments sont les suivants :

extension source :
L'extension du fichier à partir duquel nous convertissons (par exemple, "fig"). Elle est spécifiée sans point.
extension cible :
L'extension du fichier vers lequel nous convertissons (par exemple, "eps"). Elle est spécifiée sans point.
doit_exister :
Si non nul, le fichier à partir duquel nous convertissons **doit** exister. S'il n'existe pas, latexmk affichera un message d'erreur et quittera, sauf si l'option -f est spécifiée. Si doit_exister est nul et que le fichier à partir duquel nous convertissons n'existe pas, alors aucune action n'est entreprise. Généralement, la valeur appropriée de doit_exister est zéro.
sous_routine :
Le nom de la sous-routine que latexmk doit appeler pour effectuer la conversion de fichier. Le premier argument de la sous-routine est le nom de base du fichier à convertir sans aucune extension. Les sous-routines sont déclarées dans la syntaxe de Perl. La fonction doit retourner 0 si elle a réussi et un nombre non nul si elle a échoué.

Naturellement, add_cus_dep ajoute une dépendance personnalisée avec les extensions source et cible spécifiées. Si une dépendance personnalisée a déjà été définie (par exemple, dans un fichier rc lu précédemment), elle est remplacée par la nouvelle.

La sous-routine remove_cus_dep supprime la dépendance personnalisée spécifiée. La sous-routine show_cus_dep provoque l'envoi d'une liste des dépendances personnalisées actuellement définies vers la sortie écran.

Comment les dépendances personnalisées sont utilisées :

Une instance d'une règle de dépendance personnalisée est créée chaque fois que latexmk détecte qu'une exécution de *latex nécessite la lecture d'un fichier, tel qu'un fichier graphique, dont l'extension est l'extension cible d'une dépendance personnalisée. Alors, latexmk vérifie si un fichier existe avec le même nom, mais avec l'extension source correspondante, comme spécifié dans la dépendance personnalisée. Si c'est le cas, une instance correspondante de la dépendance personnalisée est créée, après quoi la règle est invoquée chaque fois que le fichier de destination (celui avec l'extension cible) est obsolète par rapport au fichier source correspondant.

Pour créer le nouveau fichier de destination, la sous-routine Perl spécifiée dans la règle est invoquée, avec comme argument le nom de base des fichiers en question. Les cas simples impliquent simplement une sous-routine appelant un programme externe ; cela peut être fait en suivant les modèles ci-dessous, même par ceux qui ne connaissent pas le langage de programmation Perl. Bien sûr, les experts pourraient faire quelque chose de beaucoup plus élaboré.

Un élément de la spécification de chaque règle de dépendance personnalisée, étiqueté "doit_exister" ci-dessus, spécifie comment la règle doit être appliquée lorsque le fichier source n'existe pas.

Lorsque latex signale qu'un fichier d'entrée (par exemple, un fichier graphique) n'existe pas, latexmk essaie de trouver un fichier source et une dépendance personnalisée qui peuvent être utilisés pour le créer. S'il réussit, il crée une instance de la dépendance personnalisée et l'invoque pour créer le fichier manquant, après quoi le passage suivant de latex etc. pourra lire le fichier nouvellement créé.

Note pour un usage avancé : La variable d'environnement du système d'exploitation TEXINPUTS peut être utilisée pour spécifier un chemin de recherche pour trouver les fichiers par latex etc. De manière correspondante, lorsqu'un fichier manquant est signalé, latexmk recherche dans les répertoires spécifiés dans TEXINPUTS ainsi que dans le répertoire courant, pour trouver un fichier source à partir duquel une instance d'une dépendance personnalisée peut être utilisée pour créer le fichier manquant.

Fonction pour implémenter une dépendance personnalisée, méthode traditionnelle :

La fonction qui implémente une dépendance personnalisée obtient les informations sur les fichiers à traiter de deux manières. La première est via son unique argument ; l'argument contient le nom de base des fichiers source et destination. La seconde manière est décrite plus loin.

Un exemple simple et typique de code dans un fichier rc d'initialisation utilisant la première méthode est :


add_cus_dep( 'fig', 'eps', 0, 'fig2eps' );
sub fig2eps {
system( "fig2dev -Leps \"$_[0].fig\" \"$_[0].eps\"" );
}

La première ligne ajoute une dépendance personnalisée qui convertit un fichier avec l'extension "fig", tel que créé par le programme xfig, en un fichier postscript encapsulé, avec l'extension "eps". Les lignes restantes définissent une sous-routine qui effectue la conversion. Si une règle de conversion de fichiers "fig" en "eps" existe déjà (par exemple, à partir d'un fichier d'initialisation précédemment lu), latexmk supprimera cette règle avant d'en créer une nouvelle.

Supposons que latexmk utilise cette règle pour convertir un fichier "figure.fig" en "figure.eps". Il invoquera alors la sous-routine fig2eps définie dans le code ci-dessus avec un seul argument "figure", qui est le nom de base de chacun des fichiers (éventuellement avec un composant de chemin). Cet argument est référencé par Perl comme $_[0]. Dans l'exemple ci-dessus, la sous-routine utilise la commande Perl system pour invoquer le programme fig2dev. Les guillemets autour de la chaîne sont une *idiome* de Perl qui s

ignify que chaque chaîne de la forme d'un nom de variable, $_[0] dans ce cas, doit être substituée par sa valeur.

Si la valeur de retour de la sous-routine est non nulle, alors latexmk supposera qu'une erreur s'est produite lors de l'exécution de la sous-routine. Dans l'exemple ci-dessus, aucune valeur de retour explicite n'est donnée, et au lieu de cela, la valeur de retour est celle renvoyée par la dernière (et seule) instruction, c'est-à-dire l'appel de system, qui renvoie la valeur 0 en cas de succès.

Si vous utilisez pdflatex, lualatex ou xelatex au lieu de latex, vous préférerez probablement convertir vos fichiers graphiques au format pdf, auquel cas vous remplaceriez le code ci-dessus dans un fichier d'initialisation par


add_cus_dep( 'fig', 'pdf, 0, 'fig2pdf' );
sub fig2pdf {
system( "fig2dev -Lpdf \"$_[0].fig\" \"$_[0].pdf\"" );
}

Note 1 : Dans les lignes de commande données dans les commandes système des exemples ci-dessus, des guillemets doubles ont été insérés autour des noms de fichiers (implémentés par '\"' dans le langage Perl). Ils protègent l'exécution du programme contre les caractères spéciaux dans les noms de fichiers. Très souvent, ces guillemets ne sont pas nécessaires, c'est-à-dire qu'ils peuvent être omis. Mais il est normalement plus sûr de les conserver. Même si les règles de mise entre guillemets varient entre les systèmes d'exploitation, les shells de commande et les logiciels individuels, les guillemets dans les exemples ci-dessus ne causent pas de problèmes dans les cas que j'ai testés.

Note 2 : Un cas où les guillemets sont importants est lorsque les fichiers se trouvent dans un sous-répertoire et que votre système d'exploitation est Microsoft Windows. Dans ce cas, le caractère séparateur pour les composants de répertoire peut être soit une barre oblique '/' soit la barre oblique inverse '\' plus courante chez Microsoft. Les barres obliques avant sont générées par latexmk, pour maintenir sa cohérence avec des logiciels comme MiKTeX qui mélangent les deux séparateurs de répertoire ; mais leur utilisation correcte nécessite normalement des noms de fichiers entre guillemets. (Voir un fichier journal d'une exécution de MiKTeX (au moins dans la v. 2.9) pour un exemple d'utilisation des deux séparateurs de répertoire.)

Note 3 : Les sous-routines implémentant des dépendances personnalisées dans les exemples donnés ne contiennent qu'une seule ligne appelant un programme externe. C'est la situation habituelle. Mais comme les sous-routines sont en langage Perl, vous pouvez implémenter des traitements beaucoup plus complexes si vous en avez besoin.

Suppression des dépendances personnalisées, et quand vous pourriez avoir besoin de le faire :

Si vous avez défini des dépendances personnalisées générales dans le fichier d'initialisation système ou utilisateur, vous pourriez trouver que pour un projet particulier, elles sont indésirables. Vous pourriez donc vouloir supprimer celles qui ne sont pas nécessaires. Une situation où cela serait souhaitable est lorsqu'il existe plusieurs dépendances personnalisées avec la même extension de départ ou la même extension d'arrivée. Dans ce cas, latexmk pourrait en choisir une différente de celle que vous souhaitez pour un projet spécifique. Par exemple, pour supprimer toute règle de conversion de "fig" en "eps", vous utiliseriez :


remove_cus_dep( 'fig', 'eps' );

Si vous avez des ensembles complexes de dépendances personnalisées, vous pourriez vouloir obtenir une liste des dépendances personnalisées. Cela se fait en utilisant la ligne


show_cus_dep();

dans un fichier d'initialisation.

Fonction implémentant une dépendance personnalisée, méthodes alternatives :

Jusqu'à présent, les exemples de fonctions pour implémenter des dépendances personnalisées utilisaient l'argument de la fonction pour spécifier le nom de base du fichier converti. Cette méthode est disponible depuis de très anciennes versions de latexmk, et de nombreux exemples peuvent être trouvés, par exemple sur le web.

Cependant, dans les versions ultérieures de latexmk, la structure interne de l'implémentation de ses "règles" pour les étapes de traitement, y compris les dépendances personnalisées, est devenue beaucoup plus puissante. La fonction implémentant une dépendance personnalisée est exécutée dans un contexte spécial où un certain nombre de variables et de sous-routines supplémentaires sont définies. Celles qui sont documentées publiquement et destinées à être stables à long terme sont listées ci-dessous, sous la rubrique "Variables et sous-routines pour le traitement d'une règle".

Des exemples de leur utilisation sont donnés dans les exemples suivants, concernant plusieurs fichiers d'index et glossaires.

La seule conversion de fichier d'index intégrée à latexmk est d'un fichier ".idx" écrit lors d'une exécution de *latex à un fichier ".ind" à lire lors d'une exécution ultérieure. Mais avec le paquet index.sty, par exemple, vous pouvez créer des index supplémentaires avec des extensions que vous configurez. Latexmk ne sait pas comment déduire les extensions à partir des informations dont il dispose. Mais vous pouvez facilement écrire une dépendance personnalisée. Par exemple, si votre fichier latex utilise la commande "\newindex{special}{ndx}{nnd}{Special index}", vous devrez faire en sorte que latexmk convertisse les fichiers avec l'extension .ndx en .nnd. La méthode la plus élémentaire consiste à définir une dépendance personnalisée comme suit :


add_cus_dep( 'ndx', 'nnd', 0, 'ndx2nnd' );
sub ndx2nnd {
return system( "makeindex -o \"$_[0].nnd\" \"$_[0].ndx\"" );
}
push @generated_exts, 'ndx', 'nnd';

Remarquez la ligne ajoutée par rapport aux exemples précédents. La ligne supplémentaire ajoute les extensions "ndx" et "nnd" à la liste des extensions pour les fichiers générés ; alors les fichiers d'index supplémentaires seront supprimés par les opérations de nettoyage.

Mais si vous avez encore plus d'index avec des extensions encore différentes, par exemple "adx" et "and", alors vous aurez besoin d'une fonction séparée pour chaque paire d'extensions. C'est assez ennuyeux. Vous pouvez utiliser la fonction Run_subst pour simplifier les définitions afin d'utiliser une seule fonction :


add_cus_dep( 'ndx', 'nnd', 0, 'dx2nd' );
add_cus_dep( 'adx', 'and', 0, 'dx2nd' );
sub dx2nd {
return Run_subst( "makeindex -o %D %S" );
}
push @generated_exts, 'ndx', 'nnd', 'adx', 'and';

Vous pourriez également utiliser à la place :


add_cus_dep( 'ndx', 'nnd', 0, 'dx2nd' );
add_cus_dep( 'adx', 'and', 0, 'dx2nd' );
sub dx2nd {
return Run_subst( $makeindex );
}
push @generated_exts, 'ndx', 'nnd', 'adx', 'and';

Ce dernier exemple utilise la spécification de commande dans $makeindex, et donc toute personnalisation que vous avez faite pour l'index standard s'applique également à vos index supplémentaires.

Des techniques similaires peuvent être appliquées pour les glossaires.

Ceux d'entre vous qui ont de l'expérience avec Makefiles, pourraient s'inquiéter que le fichier .ndx est écrit pendant une exécution de *latex et est toujours postérieur au fichier .nnd lu précédemment. Ainsi, le fichier .nnd semble être perpétuellement obsolète. Cette situation, de dépendances circulaires, est endémique au latex, et est l'une des questions que latexmk est programmé pour surmonter. Il examine le contenu des fichiers (par utilisation d'une somme de contrôle), et ne refait une compilation que lorsque le contenu des fichiers a effectivement changé.

Bien sûr, si vous choisissez d'écrire des données aléatoires dans le fichier .nnd (ou dans le fichier .aux, etc.) qui changent à chaque nouvelle exécution, vous aurez un problème. Pour les vrais experts : consultez %hash_calc_ignore_pattern si vous devez traiter de tels problèmes.

Ancienne méthode de définition des dépendances personnalisées :

Dans les versions beaucoup plus anciennes de latexmk, la seule méthode pour définir des dépendances personnalisées était de manipuler directement la table des dépendances personnalisées. Celle-ci est contenue dans le tableau @cus_dep_list. C'est un tableau de chaînes de caractères, et chaque chaîne du tableau contient quatre éléments, séparés par un espace : l'extension de départ, l'extension d'arrivée, l'élément "must" (obligatoire) et le nom de la sous-routine pour la dépendance personnalisée. Tous ceux-ci ont été définis ci-dessus.

Un exemple de l'ancienne méthode de définition des dépendances personnalisées est le suivant. C'est le code d'un fichier RC pour assurer la conversion automatique des fichiers .fig en fichiers .eps :


push @cus_dep_list, "fig eps 0 fig2eps";
sub fig2eps {
return system( "fig2dev -Lps \"$_[0].fig\" \"$_[0].eps\"" );
}

Cette méthode fonctionne toujours, et est presque équivalente au code donné précédemment qui utilisait la sous-routine add_cus_dep. Cependant, l'ancienne méthode ne supprime aucune dépendance personnalisée précédente pour la même conversion. La nouvelle méthode est donc préférable.

Variables et sous-routines pour le traitement d'une règle

Une étape du traitement est appelée une règle. Une possibilité pour implémenter le traitement d'une règle est par une sous-routine Perl. C'est toujours le cas pour les dépendances personnalisées. De plus, pour toute autre règle, vous pouvez utiliser une sous-routine en préfixant la spécification de commande par le mot "internal" -- voir la section FORMAT DES SPÉCIFICATIONS DE COMMANDE.

Lorsque vous utilisez une sous-routine pour traiter une règle, toutes les possibilités de programmation Perl sont bien sûr disponibles. De plus, certaines des variables et sous-routines internes de latexmk sont disponibles. Celles qui sont listées ci-dessous sont destinées à être disponibles pour les utilisateurs (avancés), et leurs spécifications auront généralement une stabilité lors des mises à jour. Généralement, les varia

doivent être considérés comme en lecture seule : Modifier leurs valeurs peut avoir des conséquences néfastes, car cela risque de perturber la cohérence de ce que latexmk est en train de faire.

$rule
Cette variable contient le nom de la règle, tel qu'il est connu de latexmk. Notez que le contenu exact de cette variable pour une règle donnée peut dépendre de la version de latexmk.
$$Pbase
Ceci donne le nom de base de la règle. Généralement, il détermine les noms des fichiers générés. Par exemple, pour une exécution de *latex, le nom du fichier .log est le répertoire auxiliaire concaténé avec le nom de base, puis `.log'.

Pour une règle *latex, le nom de base est sans composant de répertoire. Pour d'autres règles, il inclut le composant de répertoire (s'il y en a un utilisé).

Cette différence (agaçante) est associée aux différentes manières dont les commandes invoquées par latexmk fonctionnent lorsque la ligne de commande inclut un nom de fichier source qui comprend un composant de répertoire. Pour les commandes *latex, le répertoire du fichier source est sans importance pour le composant de répertoire des fichiers générés, qui est plutôt déterminé par les valeurs des options -aux-directory et/ou -output-directory.

En revanche, de nombreux autres programmes (par exemple, biber, bibtex) placent leurs fichiers générés dans le même répertoire que le fichier source, simplement avec une extension modifiée.

Notez les doubles signes dollar : En termes Perl, la variable $Pbase est une référence vers une variable qui contient le nom de base. Le second signe dollar déréférence la référence pour donner la valeur réelle. (Une référence est utilisée un peu comme un pointeur, et le 'P' (pour 'pointeur') au début du nom de la variable est une convention utilisée dans latexmk pour indiquer que la variable est une variable de référence.)

$$Pdest
Ceci donne le nom du fichier de sortie principal, le cas échéant. Notez les doubles signes dollar.
$$Psource
Ceci donne le nom du fichier source principal. Notez les doubles signes dollar.
add_hook( <nom_pile>, <sous_routine> )
Voir la section 'Hooks' pour plus de détails.

Ceci ajoute la sous-routine spécifiée dans le deuxième argument à la pile de hooks de latexmk spécifiée par le nom de la pile. Elle renvoie 1 en cas de succès, et zéro sinon (par exemple, si la pile de hooks spécifiée n'existe pas).

La sous-routine peut être spécifiée par une référence à la sous-routine, comme dans


add_hook( 'after_xlatex_analysis', mmz_analyze )

Étant donné que la sous-routine mmz_analyze a été définie dans le fichier rc.

La sous-routine peut être spécifiée par une chaîne dont la valeur est le nom de la sous-routine, par exemple,


add_hook( 'after_xlatex_analysis', 'mmz_analyze' )

Dans des cas simples, la sous-routine peut être une sous-routine anonyme définie dans l'appel à add_hooks,


add_hook( 'after_main_pdf', sub{ print "TEST\n"; return 0; } );

Notez qu'en cas de succès, la sous-routine doit retourner 0 (comme un appel à la sous-routine system de Perl), donc normalement cela devrait être codé explicitement. Si une sous-routine de hook retourne une valeur non nulle, latexmk traite cela comme une condition d'erreur.

ensure_path( var, valeurs ...)

Le premier paramètre est le nom d'une des variables d'environnement du système pour les chemins de recherche. Les paramètres restants sont les valeurs qui devraient être dans la variable. Pour chacune des valeurs paramétrées, si elle n'est pas déjà dans la variable, elle est ajoutée au début de la variable ; dans ce cas, la variable d'environnement est créée si elle n'existe pas déjà. Pour séparer les valeurs, le caractère approprié au système d'exploitation est utilisé -- voir la variable de configuration $search_path_separator.

Exemple :


ensure_path( 'TEXINPUTS', './custom_cls_sty_files//' );

(Dans cet exemple, le '//' final est documenté par les systèmes TeX comme signifiant que *latex recherche les fichiers dans le répertoire spécifié et dans tous les sous-répertoires.)

Techniquement, ensure_path fonctionne en définissant la variable Perl $ENV{var}, où var est le nom de la variable cible. La valeur modifiée est ensuite transmise comme variable d'environnement aux programmes invoqués.

pushd( chemin ), popd()
Ces sous-routines sont utilisées lorsqu'il est nécessaire de changer temporairement le répertoire de travail, comme dans


pushd( 'un_certain_repertoire' );
... Traitement effectué avec 'un_certain_repertoire' comme répertoire de travail
popd()

Elles remplissent exactement la même fonction que les commandes du même nom dans les shells de commandes de systèmes d'exploitation comme bash sur Unix et cmd.exe sur Windows.

rdb_add_generated( fichier, ... )
Cette sous-routine doit être utilisée dans le contexte d'une règle, c'est-à-dire à partir d'une sous-routine qui effectue le traitement d'une règle. Tel est le cas de la sous-routine implémentant une dépendance personnalisée, ou de la sous-routine invoquée en utilisant le mot-clé "internal" dans la spécification de commande comme dans la variable $latex.

Ses arguments sont une séquence de noms de fichiers qui sont générés lors de l'exécution de la règle. Les noms peuvent provenir d'une analyse des résultats de l'exécution, par exemple dans un fichier journal, ou de la connaissance des propriétés de la règle spécifique. Appeler rdb_add_generated avec ces noms de fichiers garantit que ces fichiers sont marqués comme générés par la règle dans les structures de données internes de latexmk. Fondamentalement, aucune action n'est effectuée si les fichiers ont déjà été marqués comme générés.

Un objectif principal de l'utilisation de cette sous-routine est la situation où un fichier généré est également le fichier source d'une autre règle, de sorte que latexmk puisse correctement lier les informations de dépendance dans son réseau de règles.

Note : Contrairement à certaines autres sous-routines de cette section, il n'y a pas d'argument de règle pour rdb_add_generated. Au lieu de cela, la sous-routine doit être invoquée lors du traitement d'une règle lorsque latexmk a configuré un contexte approprié (c'est-à-dire des variables appropriées). En revanche, les sous-routines avec un argument de règle peuvent également être utilisées en dehors d'un contexte de règle.

rdb_ensure_file( $règle, fichier )
Cette sous-routine garantit que le fichier donné fait partie des fichiers sources pour la règle spécifiée. Elle est généralement utilisée lorsque, lors du traitement d'une règle, on sait qu'un fichier supplémentaire particulier fait partie des dépendances que latexmk doit connaître, mais que ses méthodes par défaut ne trouvent pas la dépendance. Presque toujours, le premier argument est le nom de la règle en cours de traitement, il est donc approprié de le spécifier par $règle.

Pour des exemples d'utilisation, voir certains des fichiers dans le répertoire example_rcfiles de la distribution de latexmk. Actuellement, les cas qui utilisent cette sous-routine sont bib2gls-latexmkrc, exceltex_latexmkrc et texinfo-latexmkrc. Ceux-ci illustrent des cas typiques où le traitement normal de latexmk ne parvient pas à détecter certains fichiers sources supplémentaires.

Notez que rdb_ensure_file n'a qu'un seul argument de nom de fichier, contrairement aux autres sous-routines de cette section. Si vous souhaitez appliquer son action à plusieurs fichiers, vous aurez besoin d'un appel à rdb_ensure_file pour chaque fichier.

rdb_ensure_files_here( fichier, ... )
Comme la sous-routine rdb_ensure_files, sauf que (a) elle suppose que le contexte est celui d'une règle et que les fichiers doivent être ajoutés à la liste source pour cette règle ; (b) plusieurs fichiers sont autorisés.
rdb_remove_files( $règle, fichier, ... )
Cette sous-routine supprime un ou plusieurs fichiers de la liste des dépendances pour la règle donnée.
rdb_remove_generated( fichier, ... )
Cette sous-routine doit être utilisée dans le contexte d'une règle, c'est-à-dire à partir d'une sous-routine qui effectue le traitement d'une règle. Elle effectue l'action opposée à rdb_add_generated. Son effet est de garantir que les noms de fichiers donnés ne sont pas listés dans les structures de données internes de latexmk comme étant générés par la règle.
rdb_list_source( $règle )
Cette sous-routine renvoie la liste des fichiers sources (c'est-à-dire la liste des dépendances) pour la règle donnée.
rdb_set_source( $règle, fichier, ... )
rdb_set_source( $règle, @fichiers )
Cette sous-routine définit la liste des dépendances pour la règle donnée comme étant les fichiers spécifiés. Les fichiers déjà présents dans la liste conservent leurs informations. Les fichiers qui n'étaient pas dans la liste sont ajoutés. Les fichiers de la liste de dépendances précédente qui ne figurent pas dans la nouvelle liste de fichiers spécifiée sont supprimés de la liste des dépendances.
Run_subst( spec_commande )
Cette sous-routine exécute la commande spécifiée par spec_commande. La spécification est une chaîne au format indiqué dans la section "Format des spécifications de commande". Une action importante de Run_subst est d'effectuer des substitutions de placeholders, par exemple %S et %D pour les fichiers source et destination ; ceux-ci sont substitués avant l'exécution de la commande. De plus, la commande après substitution est imprimée à l'écran sauf si latexmk est en mode silencieux.
test_gen_file_time ( <fichier> )
Cette sous-routine est utilisée dans le contexte d'une règle. Elle renvoie vrai ou faux selon que le fichier du nom donné existe et a été généré lors de la dernière exécution de la règle. Si la sous-routine renvoie faux, mais que le fichier existe, alors le fichier est un reste d'une exécution précédente.

Le test pour qu'un fichier soit généré lors de l'exécution actuelle consiste à vérifier si l'heure de modification du fichier est au moins aussi récente que l'heure à laquelle

t le fonctionnement de base a été démarré. Une marge est prévue pour la granularité des valeurs des temps de modification sur les systèmes de fichiers. Voir la description de la variable $filetime_causality_threshold pour plus de détails.

En outre, latexmk prend en compte la possibilité que les fichiers soient hébergés sur un ordinateur différent de celui qui exécute latexmk et que les horloges système des deux ordinateurs ne soient pas synchronisées. Configuration coordonnée des commandes pour *latex

Pour définir $dvilualatex, $hilatex, $latex, $pdflatex, $lualatex et $xelatex sur un modèle commun, vous pouvez utiliser l'une des sous-routines suivantes : std_tex_cmds, alt_tex_cmds et set_tex_cmds.

Pour obtenir les commandes standard, utilisez


&std_tex_cmds;

Cela résulte en $latex = 'latex %O %S', et de même pour $dvilualatex, $hilatex, $pdflatex, $lualatex et $xelatex. Notez l'esperluette dans l'invocation ; cela indique à Perl qu'une sous-routine est appelée. (L'utilisation de cette sous-routine vous permet de remplacer les redéfinitions précédentes des variables $latex, etc., qui auraient pu survenir dans un fichier rc lu précédemment.)

Pour pouvoir utiliser la chaîne fournie par l'option -pretex (le cas échéant), vous pouvez utiliser


&alt_tex_cmds;

Cela résulte en $latex = 'latex %O %P', etc. Encore une fois, notez l'esperluette dans l'invocation ; cela indique à Perl qu'une sous-routine est appelée.

Une manière plus générale de spécifier les variables est d'utiliser


set_tex_cmds( 'CMD_SPEC' );

Ici, CMD_SPEC est la ligne de commande sans le nom du programme. Cela résulte en $latex = 'latex CMD_SPEC', et de même pour $pdflatex, etc. (Une esperluette précédant le nom de la sous-routine n'est pas nécessaire ici, car les parenthèses indiquent à Perl qu'une sous-routine est invoquée.)

Un exemple qui fournit l'option --interaction=batchmode aux commandes *latex serait


set_tex_cmds( '--interaction=batchmode %O %S' );

Cela résulte en $latex = 'latex --interaction=batchmode %O %S ', etc. Notez que lorsque '%O' apparaît après l'option ajoutée, comme ici, les options fournies sur la ligne de commande à latexmk peuvent remplacer celle fournie.

Une ligne de commande plus générale peut être configurée en utilisant le placeholder '%C' dans CMD_SPEC. Le '%C' est substitué par le nom de base de la commande, c'est-à-dire celle de 'latex', 'pdflatex', etc. qui convient. (Plusieurs occurrences de '%C' sont autorisées.) Par exemple, pour utiliser les versions de développement/pré-version de latex, etc., qui portent les noms 'latex-dev', 'pdflatex-dev', etc., vous pourriez utiliser


set_tex_cmds( '%C-dev %O %S' );

Cela résulte en $latex = 'latex-dev %O %S', etc. (Les programmes de pré-version latex-dev, etc., sont fournis dans les distributions actuelles de TeXLive et MiKTeX.)

Hooks

Latexmk fournit un moyen de faire appeler des sous-routines définies par l'utilisateur à certains points du traitement. Celles-ci peuvent être utilisées pour configurer un comportement et des actions appropriés au-delà du comportement normal de latexmk. Pour un bon exemple de la manière dont elles peuvent être utilisées pour adapter le comportement de latexmk à des packages particuliers, consultez le fichier memoize_latexmkrc dans le sous-répertoire example_rcfiles de la distribution latexmk. (Dans une installation standard de TeXLive, ce sous-répertoire se trouve dans texmf-dist/doc/support/latexmk/)

Le mécanisme de hook est complémentaire à la méthode de redéfinition des chaînes de commande comme $pdflatex, etc. Les deux méthodes ont des domaines d'utilité qui se chevauchent.

Configuration avancée : Utilisation de latexmk avec make

Cette section s'adresse uniquement aux utilisateurs avancés qui utilisent le programme make pour des projets complexes, comme pour le développement logiciel, avec les dépendances spécifiées par un Makefile.

La tâche de base de latexmk est d'exécuter les programmes appropriés pour créer une version visualisable d'un document LaTeX. Cependant, le programme make habituel n'est pas adapté à cet usage pour au moins deux raisons. Premièrement, l'utilisation de LaTeX implique des dépendances circulaires (par exemple, via les fichiers .aux), et celles-ci ne peuvent pas être gérées par le programme make standard. Deuxièmement, dans un document volumineux, l'ensemble des fichiers source peut changer assez fréquemment, en particulier avec les fichiers graphiques inclus ; dans cette situation, maintenir manuellement un Makefile à jour est inapproprié et sujet aux erreurs, surtout lorsque les dépendances peuvent être déterminées automatiquement. Latexmk résout ces deux problèmes de manière robuste.

Ainsi, pour de nombreux documents LaTeX standard, latexmk peut être utilisé seul, sans le programme make. Dans un projet complexe, il suffit de le configurer de manière appropriée. Une configuration standard consisterait à définir des dépendances personnalisées pour créer des fichiers graphiques à partir de leurs fichiers source (par exemple, tels que créés par le programme xfig). Les dépendances personnalisées sont l'équivalent dans latexmk des règles de pattern dans les Makefiles.

Néanmoins, il existe des projets pour lesquels un Makefile est approprié, et il est utile de savoir comment utiliser latexmk à partir d'un Makefile. Un exemple typique serait de générer la documentation d'un projet logiciel. Potentiellement, l'interaction avec le reste des règles du Makefile pourrait être assez complexe, par exemple si certains des fichiers source d'un document LaTeX sont générés par le logiciel du projet.

Dans cette section, je donne quelques exemples de la manière dont latexmk peut être utilement invoqué à partir d'un Makefile. Les exemples utilisent des fonctionnalités spécifiques des versions actuelles de GNU make, qui est la valeur par défaut sur les systèmes linux et OS-X. Ils peuvent nécessiter des modifications pour d'autres versions de make.

La méthode la plus simple consiste à déléguer toutes les tâches pertinentes à latexmk, comme cela convient pour un document LaTeX simple. Pour cela, un Makefile approprié ressemble à


.PHONY : FORCE_MAKE
all : try.pdf
%.pdf : %.tex FORCE_MAKE
latexmk -pdf -dvi- -ps- $<

(Note : la dernière ligne doit être introduite par une tabulation pour que le Makefile fonctionne correctement !) Naturellement, si la création de try.pdf à partir de son fichier LaTeX associé try.tex était la seule tâche à effectuer, une utilisation directe de latexmk sans Makefile serait normalement préférable. ADVANCED CONFIGURATION: SOME EXTRA RESOURCES AND ADVANCED TRICKS

This section covers some advanced configuration tricks. These are mostly for people who want to exploit the full power of make to handle their document production, and want latexmk to delegate to make as much as possible.

The simplest use of latexmk is to have it manage the running of pdflatex (or other LaTeX compilers), and possibly bibtex and other auxiliary programs. This is done by latexmk itself, and make is not involved at all. The user simply invokes make, and this runs latexmk. Latexmk knows how to run itself as many times as is needed, and it can detect whether any action is needed. The primary way it does this is by checking the timestamps of the output file (e.g. .pdf) and its source files (e.g. .tex). If any source file is newer than the output file, then the source file is rerun.

However, this is not enough if there are other files involved, e.g. graphics files that are generated by some other program. In this case, the user has to ensure that these files are also remade when needed. This can be done by putting rules into the Makefile. The following is an example of a simple Makefile:


all : try.pdf
try.pdf : try.tex
make -f Makefile.latex FORCE_MAKE
.PHONY : FORCE_MAKE
FORCE_MAKE

(Again, the lines containing the commands for the rules should be started with tabs.) This example shows how make can be used to manage the generation of a .pdf file. The primary rule is to make `all', which has a prerequisite `try.pdf'. The rule for `try.pdf' has a prerequisite `try.tex'. When make is invoked, it sees that `try.pdf' is out-of-date with respect to `try.tex', and it runs the command to make it. The command is `make -f Makefile.latex FORCE_MAKE'. This invokes make again, using the file Makefile.latex. This second invocation of make is to ensure that latexmk is invoked. The invocation is forced by the phony prerequisite `FORCE_MAKE'.

The file Makefile.latex might contain something like this:


TARGET=try.pdf
LATEXMK=latexmk -pdf -dvi- -ps-
all : $(TARGET)
$(TARGET) : FORCE_MAKE
$(LATEXMK) $<
.PHONY : FORCE_MAKE
FORCE_MAKE

This is a pattern rule for making a .pdf file from a .tex file, and it is defined to use latexmk in the obvious way. There is a conventional default target named "all", with a prerequisite of try.pdf. So when make is invoked, by default it makes try.pdf. The only complication is that there may be many source files beyond try.tex, but these aren't specified in the Makefile, so changes in them will not by themselves cause latexmk to be invoked. Instead, the pattern rule is equipped with a "phony" prerequisite FORCE_MAKE; this has the effect of causing the rule to be always out-of-date, so that latexmk is always run. It is latexmk that decides whether any action is needed, e.g., a rerun of pdflatex. Effectively the Makefile delegates all decisions to latexmk, while make has no knowledge of the list of source files except for primary LaTeX file for the document. If there are, for example, graphics files to be made, these must be made by custom dependencies configured in latexmk.

But something better is needed in more complicated situations, for example, when the making of graphics files needs to be specified by rules in the Makefile. To do this, one can use a Makefile like the following:


TARGETS = document1.pdf document2.pdf
DEPS_DIR = .deps
LATEXMK = latexmk -recorder -use-make -deps \
-e 'warn qq(In Makefile, turn off custom dependencies\n);' \
-e '@cus_dep_list = ();' \
-e 'show_cus_dep();'
all : $(TARGETS)
$(foreach file,$(TARGETS),$(eval -include $(DEPS_DIR)/$(file)P))
$(DEPS_DIR) :
mkdir $@
%.pdf : %.tex
if [ ! -e $(DEPS_DIR) ]; then mkdir $(DEPS_DIR); fi
$(LATEXMK) -pdf -dvi- -ps- -deps-out=$(DEPS_DIR)/$@P $<
%.pdf : %.fig
fig2dev -Lpdf $< $@

(Again, the lines containing the commands for the rules should be started with tabs.) This example was inspired by how GNU automake handles automatic dependency tracking of C source files.

After each run of latexmk, dependency information is put in a file in the .deps subdirectory. The Makefile causes these dependency files to be read by make, which now has the full dependency information for each target .pdf file. To make things less trivial it is specificed that two files document1.pdf and document2.pdf are the targets. The dependency files are .deps/document1.pdfP and .deps/document2.pdfP.

There is now no need for the phony prerequisite for the rule to make .pdf files from .tex files. But I have added a rule to make .pdf files from .fig files produced by the xfig program; these are commonly used for graphics insertions in LaTeX documents. Latexmk is arranged to output a dependency file after each run. It is given the -recorder option, which improves its detection of files generated during a run of pdflatex; such files should not be in the dependency list. The -e options are used to turn off all custom dependencies, and to document this. Instead the -use-make is used to delegate the making of missing files to make itself.

Suppose in the LaTeX file there is a command \includegraphics{graph}, and an xfig file "graph.fig" exists. On a first run, pdflatex reports a missing file, named "graph". Latexmk succeeds in making "graph.pdf" by calling "make graph.pdf", and after completion of its work, it lists "fig.pdf" among the dependents of the file latexmk is making. Then let "fig.fig" be updated, and then let make be run. Make first remakes "fig.pdf", and only then reruns latexmk.

Thus we now have a method by which all the subsidiary processing is delegated to make.

Escaping of characters in dependency lists: There are certain special characters that need to be escaped when names of files and directories containing them appear in a dependency list used by a make program. Generally, such special characters are best avoided.

By default, latexmk does no escaping of this kind, and the user will have to arrange to deal with the issue separately, if the relevant special characters are used. Note that the rules for escaping depend on which make program is used, and on its version.

One special case is of spaces, since those are particularly prevalent, notably in standard choices of name for a user's home directory. So latexmk does provide an option to escape spaces. See the option -deps_escape=... and the variable $deps_escape for details.

NON_ASCII CHARACTERS IN FILENAMES, RC FILES, ETC

Modern operating systems and file systems allow non-ASCII characters in the names of files and directories that encompass the full Unicode range. Mostly, latexmk deals with these correctly. However, there are some situations in which there are problems, notably on Microsoft Windows. Prior to version 4.77, latexmk had problems with non-ASCII filenames on Windows, even though there were no corresponding problems on macOS and Linux. These problems are corrected in the present version.

BUGS (SELECTED)

Sometimes a viewer (gv) tries to read an updated .ps or .pdf file after its creation is started but before the file is complete. Work around: manually refresh (or reopen) display. Or use one of the other previewers and update methods.

(The following isn't really a bug, but concerns features of previewers.) Preview continuous mode only works perfectly with certain previewers: Xdvi on UNIX/Linux works for dvi files. Gv on UNIX/Linux works for both postscript and pdf. Ghostview on UNIX/Linux needs a manual update (reopen); it views postscript and pdf. Gsview under MS-Windows works for both postscript and pdf, but only reads the updated file when its screen is refreshed. Acroread under UNIX/Linux views pdf, but the file needs to be closed and reopened to view an updated version. Under MS-Windows, acroread locks its input file and so the pdf file cannot be updated. (Remedy: configure latexmk to use sumatrapdf instead.)
