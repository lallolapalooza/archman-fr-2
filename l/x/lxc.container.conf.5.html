NOM

lxc.container.conf - Fichier de configuration de conteneur LXC

DESCRIPTION

LXC est le moteur d'exécution de conteneurs Linux bien connu et largement testé. Il est en développement actif depuis 2008 et a fait ses preuves dans des environnements de production critiques dans le monde entier. Certains de ses contributeurs principaux sont les mêmes personnes qui ont aidé à implémenter diverses fonctionnalités de conteneurisation bien connues au sein du noyau Linux.

LXC se concentre principalement sur les conteneurs système. C'est-à-dire des conteneurs qui offrent un environnement aussi proche que possible de celui que vous obtiendriez d'une VM, mais sans la surcharge liée à l'exécution d'un noyau séparé et à la simulation de tout le matériel.

Ceci est réalisé grâce à une combinaison de fonctionnalités de sécurité du noyau telles que les espaces de noms (namespaces), le contrôle d'accès mandataire (MAC) et les cgroups (control groups).

LXC prend en charge les conteneurs non privilégiés. Les conteneurs non privilégiés sont des conteneurs exécutés sans aucun privilège. Cela nécessite la prise en charge des espaces de noms utilisateur dans le noyau sur lequel le conteneur est exécuté. LXC a été le premier moteur d'exécution à prendre en charge les conteneurs non privilégiés après l'intégration des espaces de noms utilisateur dans le noyau principal.

Essentiellement, les espaces de noms utilisateur isolent des ensembles donnés d'UID et de GID. Ceci est réalisé en établissant une correspondance entre une plage d'UID et de GID sur l'hôte et une plage différente (non privilégiée) d'UID et de GID dans le conteneur. Le noyau traduira cette correspondance de telle sorte qu'à l'intérieur du conteneur, tous les UID et GID apparaissent comme vous vous attendriez de l'hôte, tandis que sur l'hôte, ces UID et GID sont en fait non privilégiés. Par exemple, un processus s'exécutant en tant qu'UID et GID 0 à l'intérieur du conteneur peut apparaître comme UID et GID 100000 sur l'hôte. L'implémentation et les détails de fonctionnement peuvent être obtenus à partir de la page de manuel correspondante sur les espaces de noms utilisateur. Les correspondances UID et GID peuvent être définies avec la clé lxc.idmap.

Les clés de configuration des conteneurs Linux utilisent des points simples. Cela signifie que des clés de configuration complexes telles que lxc.net.0 exposent diverses sous-clés telles que lxc.net.0.type, lxc.net.0.link, lxc.net.0.ipv6.address, et d'autres pour une configuration encore plus précise.

CONFIGURATION

Afin de simplifier l'administration de plusieurs conteneurs apparentés, il est possible qu'un fichier de configuration de conteneur charge un autre fichier. Par exemple, la configuration réseau peut être définie dans un fichier commun qui est inclus par plusieurs conteneurs. Ensuite, si les conteneurs sont déplacés vers un autre hôte, un seul fichier peut nécessiter une mise à jour.

lxc.include
Spécifie le fichier à inclure. Le fichier inclus doit être dans le même format de fichier de configuration lxc valide.

ARCHITECTURE

Permet de définir l'architecture du conteneur. Par exemple, définir une architecture 32 bits pour un conteneur exécutant des binaires 32 bits sur un hôte 64 bits. Cela corrige les scripts du conteneur qui dépendent de l'architecture pour effectuer certaines tâches comme le téléchargement des paquets.

lxc.arch
Spécifie l'architecture pour le conteneur.

Certaines options valides sont x86, i686, x86_64, amd64

NOM D'HÔTE

La section utsname définit le nom d'hôte à définir pour le conteneur. Cela signifie que le conteneur peut définir son propre nom d'hôte sans modifier celui du système. Cela rend le nom d'hôte privé pour le conteneur.

lxc.uts.name
spécifie le nom d'hôte pour le conteneur

SIGNAL D'ARRÊT

Permet de spécifier le nom ou le numéro du signal envoyé au processus d'init du conteneur pour arrêter proprement le conteneur. Différents systèmes d'init pourraient utiliser différents signaux pour effectuer une séquence d'arrêt propre. Cette option permet de spécifier le signal à la manière de kill(1), par exemple SIGPWR, SIGRTMIN+14, SIGRTMAX-10 ou un numéro simple. Le signal par défaut est SIGPWR.

lxc.signal.halt
spécifie le signal utilisé pour arrêter le conteneur

SIGNAL DE REDÉMARRAGE

Permet de spécifier le nom ou le numéro du signal pour redémarrer le conteneur. Cette option permet de spécifier le signal à la manière de kill(1), par exemple SIGTERM, SIGRTMIN+14, SIGRTMAX-10 ou un numéro simple. Le signal par défaut est SIGINT.

lxc.signal.reboot
spécifie le signal utilisé pour redémarrer le conteneur

SIGNAL D'ARRÊT FORCE

Permet de spécifier le nom ou le numéro du signal pour arrêter de manière forcée le conteneur. Cette option permet de spécifier le signal à la manière de kill(1), par exemple SIGKILL, SIGRTMIN+14, SIGRTMAX-10 ou un numéro simple. Le signal par défaut est SIGKILL.

lxc.signal.stop
spécifie le signal utilisé pour arrêter le conteneur

COMMANDE INIT

Définit la commande à utiliser comme système d'init pour les conteneurs.

lxc.execute.cmd
Chemin absolu depuis le rootfs du conteneur vers le binaire à exécuter par défaut. Ceci est principalement utile pour lxc-execute.
lxc.init.cmd
Chemin absolu depuis le rootfs du conteneur vers le binaire à utiliser comme init. Ceci est principalement utile pour lxc-start. La valeur par défaut est /sbin/init.

RÉPERTOIRE DE TRAVAIL INIT

Définit le chemin absolu à l'intérieur du conteneur comme répertoire de travail pour les conteneurs. LXC basculera vers ce répertoire avant d'exécuter init.

lxc.init.cwd
Chemin absolu à l'intérieur du conteneur à utiliser comme répertoire de travail.

ID INIT

Définit l'UID/GID à utiliser pour le système d'init, et les commandes subséquentes. Notez que l'utilisation d'un UID non root lors du démarrage d'un conteneur système ne fonctionnera probablement pas en raison de privilèges manquants. La définition de l'UID/GID est principalement utile lors de l'exécution de conteneurs d'applications. Par défaut : UID(0), GID(0)

lxc.init.uid
UID à utiliser pour init.
lxc.init.gid
GID à utiliser pour init.

PLANIFICATION COEUR

La planification sur cœur (Core scheduling) définit si la charge utile du conteneur est marquée comme étant planifiable sur le même cœur. Faire cela amènera le planificateur du noyau à s'assurer que les tâches qui ne font pas partie du même groupe ne s'exécutent jamais simultanément sur un cœur. Ceci peut servir de mesure de sécurité supplémentaire pour empêcher la charge utile du conteneur d'utiliser des attaques inter-threads.

lxc.sched.core
Les seules valeurs autorisées sont 0 et 1. Réglez ceci à 1 pour créer un domaine de planification sur cœur pour le conteneur ou 0 pour ne pas en créer un. Si non défini explicitement, aucun domaine de planification sur cœur ne sera créé pour le conteneur.

PROC FILESYSTEM

Permet de spécifier des fichiers dans le système de fichiers virtuel du conteneur.

Spécifie le nom du fichier proc à définir. Les noms de fichiers disponibles sont ceux listés sous /proc/PID/. Exemple :

EPHEMERE

Permet de spécifier si un conteneur doit être détruit à l'arrêt.

lxc.ephemeral
Les seules valeurs autorisées sont 0 et 1. Mettez cette valeur à 1 pour détruire un conteneur à l'arrêt.

RESEAU

La section réseau définit comment le réseau est virtualisé dans le conteneur. La virtualisation réseau agit au niveau de la couche deux. Afin d'utiliser la virtualisation réseau, des paramètres doivent être spécifiés pour définir les interfaces réseau du conteneur. Plusieurs interfaces virtuelles peuvent être assignées et utilisées dans un conteneur même si le système n'a qu'une seule interface réseau physique.

lxc.net
peut être utilisé sans valeur pour effacer toutes les options réseau précédentes.
lxc.net.[i].type
spécifie le type de virtualisation réseau à utiliser pour le conteneur. Doit être spécifié avant toute autre option sur le périphérique réseau. Plusieurs réseaux peuvent être spécifiés en utilisant un index supplémentaire i après toutes les clés lxc.net.*. Par exemple, lxc.net.0.type = veth et lxc.net.1.type = veth spécifient deux réseaux différents du même type. Toutes les clés partageant le même index i seront traitées comme appartenant au même réseau. Par exemple, lxc.net.0.link = br0 appartiendra à lxc.net.0.type. Actuellement, les différents types de virtualisation peuvent être :

empty : créera uniquement l'interface de bouclage.

veth : un périphérique de paire d'éthernet virtuel est créé, un côté étant assigné au conteneur et l'autre côté à l'hôte. lxc.net.[i].veth.mode spécifie le mode que le parent veth utilisera sur l'hôte. Les modes acceptés sont bridge et router. Le mode par défaut est bridge s'il n'est pas spécifié. En mode bridge, le côté hôte est attaché à un pont spécifié par l'option lxc.net.[i].link. Si le lien de pont n'est pas spécifié, alors le périphérique de paire veth sera créé mais non attaché à un pont. Sinon, le pont doit être créé sur le système avant de démarrer le conteneur. lxc ne gérera aucune configuration extérieure au conteneur. En mode router, des routes statiques sont créées sur l'hôte pour les adresses IP du conteneur pointant vers l'interface veth côté hôte. De plus, des entrées Proxy ARP et Proxy NDP sont ajoutées sur l'interface veth côté hôte pour les adresses IP de passerelle définies dans le conteneur afin de permettre au conteneur d'atteindre l'hôte. Par défaut, lxc choisit un nom pour le périphérique réseau extérieur au conteneur, mais si vous souhaitez gérer ce nom vous-même, vous pouvez dire à lxc de définir un nom spécifique avec l'option lxc.net.[i].veth.pair (sauf pour les conteneurs non privilégiés où cette option est ignorée pour des raisons de sécurité). Des routes statiques peuvent être ajoutées sur l'hôte pointant vers le conteneur en utilisant les options lxc.net.[i].veth.ipv4.route et lxc.net.[i].veth.ipv6.route. Plusieurs lignes spécifient plusieurs routes. La route est au format x.y.z.t/m, par exemple 192.168.1.0/24. En mode bridge, l'appartenance VLAN sans étiquette peut être définie avec l'option lxc.net.[i].veth.vlan.id. Elle accepte une valeur spéciale 'none' indiquant que le port du conteneur doit être retiré du VLAN par défaut sans étiquette du pont. L'option lxc.net.[i].veth.vlan.tagged.id peut être spécifiée plusieurs fois pour définir l'appartenance du port de pont du conteneur à un ou plusieurs VLANs étiquetés.

vlan : une interface vlan est liée à l'interface spécifiée par lxc.net.[i].link et assignée au conteneur. L'identifiant vlan est spécifié avec l'option lxc.net.[i].vlan.id.

macvlan : une interface macvlan est liée à l'interface spécifiée par lxc.net.[i].link et assignée au conteneur. lxc.net.[i].macvlan.mode spécifie le mode que macvlan utilisera pour communiquer entre différents macvlan sur le même périphérique supérieur. Les modes acceptés sont private, vepa, bridge et passthru. En mode private, le périphérique ne communique jamais avec un autre périphérique sur le même upper_dev (par défaut). En mode vepa (Virtual Ethernet Port Aggregator), il est supposé que le pont adjacent renvoie toutes les trames où la source et la destination sont locales au port macvlan, c'est-à-dire que le pont est configuré comme un relais réfléchissant. Les trames de diffusion provenant de l'upper_dev sont inondées vers toutes les interfaces macvlan en mode VEPA, les trames locales ne sont pas délivrées localement. En mode bridge, il fournit le comportement d'un simple pont entre différentes interfaces macvlan sur le même port. Les trames d'une interface à une autre sont délivrées directement et ne sont pas envoyées à l'extérieur. Les trames de diffusion sont inondées vers tous les autres ports de pont et vers l'interface externe, mais lorsqu'elles reviennent d'un relais réfléchissant, elles ne sont pas délivrées à nouveau. Comme nous connaissons toutes les adresses MAC, le mode bridge macvlan ne nécessite pas d'apprentissage ni de STP comme le module bridge. En mode passthru, toutes les trames reçues par l'interface physique sont transférées à l'interface macvlan. Une seule interface macvlan en mode passthru est possible pour une interface physique.

ipvlan : une interface ipvlan est liée à l'interface spécifiée par lxc.net.[i].link et assignée au conteneur. lxc.net.[i].ipvlan.mode spécifie le mode que ipvlan utilisera pour communiquer entre différents ipvlan sur le même périphérique supérieur. Les modes acceptés sont l3, l3s et l2. Par défaut, le mode est l3. En mode l3, le traitement TX jusqu'à la couche L3 se produit dans l'instance de pile attachée au périphérique dépendant et les paquets sont acheminés vers l'instance de pile du périphérique parent pour le traitement L2, et le routage à partir de cette instance sera utilisé avant que les paquets ne soient mis en file d'attente sur le périphérique sortant. En mode l3, les périphériques dépendants ne recevront ni ne pourront envoyer de trafic multicast/broadcast. En mode l3s, le traitement TX est très similaire au mode L3, sauf que iptables (conn-tracking) fonctionne dans ce mode et donc il est L3-symétrique (L3s). Cela aura des performances légèrement inférieures, mais cela ne devrait pas poser de problème puisque vous choisissez ce mode plutôt que le mode L3 simple pour faire fonctionner le conn-tracking. En mode l2, le traitement TX se produit dans l'instance de pile attachée au périphérique dépendant et les paquets sont acheminés et mis en file d'attente vers le périphérique parent pour l'envoi aux périphériques. En mode l2, les périphériques dépendants recevront/enverront du trafic multicast et broadcast (si applicable). lxc.net.[i].ipvlan.isolation spécifie le mode d'isolation. Les valeurs d'isolation acceptées sont bridge, private et vepa. Par défaut, le mode est bridge. En mode d'isolation bridge, les périphériques dépendants peuvent communiquer entre eux en plus de communiquer via le périphérique parent. En mode d'isolation private, le port est défini en mode privé, c'est-à-dire que le port n'autorisera pas la communication croisée entre les périphériques dépendants. En mode d'isolation vepa, le port est défini en mode VEPA, c'est-à-dire que le port déchargera la fonctionnalité de commutation vers l'entité externe comme décrit dans 802.1Qbg.

phys : une interface déjà existante spécifiée par lxc.net.[i].link est assignée au conteneur.

lxc.net.[i].flags
Spécifie une action à effectuer pour le réseau.

up : active l'interface.

lxc.net.[i].link
Spécifie l'interface à utiliser pour le trafic réseau réel.
lxc.net.[i].l2proxy
Contrôle si des entrées de proxy de voisins IP de couche 2 seront ajoutées à l'interface lxc.net.[i].link pour les adresses IP du conteneur. Peut être défini à 0 ou 1. Par défaut à 0. Utilisé avec des adresses IPv4, les valeurs sysctl suivantes doivent être définies : net.ipv4.conf.[link].forwarding=1. Utilisé avec des adresses IPv6, les valeurs sysctl suivantes doivent être définies : net.ipv6.conf.[link].proxy_ndp=1 net.ipv6.conf.[link].forwarding=1
lxc.net.[i].mtu
Spécifie l'unité de transfert maximale pour cette interface.
lxc.net.[i].name
Le nom de l'interface est alloué dynamiquement, mais si un autre nom est nécessaire car les fichiers de configuration utilisés par le conteneur utilisent un nom générique, par exemple eth0, cette option renommera l'interface dans le conteneur.
lxc.net.[i].hwaddr
L'adresse MAC de l'interface est allouée dynamiquement par défaut à l'interface virtuelle, mais dans certains cas, ceci est nécessaire pour résoudre un conflit d'adresse MAC ou pour toujours avoir la même adresse IPv6 de lien local. Tout "x" dans l'adresse sera remplacé par une valeur aléatoire, ce qui permet de définir des modèles d'adresses MAC.
lxc.net.[i].ipv4.address
Spécifie l'adresse IPv4 à assigner à l'interface virtualisée. Plusieurs lignes spécifient plusieurs adresses IPv4. L'adresse est au format x.y.z.t/m, par exemple 192.168.1.123/24. Vous pouvez éventuellement spécifier l'adresse de diffusion après l'adresse IP, par exemple 192.168.1.123/24 255.255.255.255. Sinon, elle est calculée automatiquement à partir de l'adresse IP.
lxc.net.[i].ipv4.gateway
Spécifie l'adresse IPv4 à utiliser comme passerelle à l'intérieur du conteneur. L'adresse est au format x.y.z.t, par exemple 192.168.1.123. Peut également avoir la valeur spéciale auto, ce qui signifie de prendre l'adresse principale de l'interface de pont (telle que spécifiée par l'option lxc.net.[i].link) et de l'utiliser comme passerelle. auto n'est disponible que lors de l'utilisation des types de réseau veth, macvlan et ipvlan. Peut également avoir la valeur spéciale dev, ce qui signifie de définir la passerelle par défaut comme une route de périphérique. Ceci est principalement destiné à être utilisé avec n de couche 3

OPTIONS DE CONFIGURATION DE RÉSEAU

Ces options permettent de configurer le comportement du réseau pour un conteneur.

lxc.net.[i].type
Spécifie le type de périphérique réseau à créer. Les valeurs valides sont :
•
veth : Crée une paire de périphériques réseau virtuels (veth). Un côté est connecté au conteneur et l'autre côté est connecté à un pont sur l'hôte.
•
macvlan : Crée un périphérique réseau virtuel qui utilise l'adresse MAC du périphérique hôte. Permet à plusieurs conteneurs de partager le même périphérique physique tout en ayant leurs propres adresses MAC.
•
ipvlan : Similaire à macvlan, mais utilise l'adressage IP plutôt que MAC pour la séparation. Utile pour les environnements virtualisés où les commutateurs physiques ne sont pas contrôlés.
•
empty : Crée un périphérique réseau vide, sans aucune connexion. Utile pour les scénarios où le réseau est géré entièrement par l'utilisateur à l'intérieur du conteneur.
•
none : Ne crée aucun périphérique réseau. L'utilisateur est responsable de toute la configuration réseau.
•
phys : Lie un périphérique réseau physique existant au conteneur. Soyez prudent lors de l'utilisation de ce type, car il contourne une partie de la gestion réseau de l'hôte.

Pour les types macvlan et ipvlan, le périphérique parent est spécifié par lxc.net.[i].link. Pour le type veth, le périphérique côté hôte est nommé par lxc.net.[i].host_name et le côté conteneur est nommé par lxc.net.[i].name (ou par défaut eth[i]).

lxc.net.[i].link
Spécifie le périphérique sur l'hôte auquel le périphérique réseau virtuel du conteneur sera connecté. Ceci est principalement utilisé pour les types macvlan et ipvlan. Par exemple, pour lier un conteneur au pont br0 sur l'hôte, vous définiriez ceci sur br0.
lxc.net.[i].name
Spécifie le nom de l'interface réseau dans le conteneur. Par défaut, il s'agit de eth[i], où [i] est l'index de l'interface réseau.
lxc.net.[i].host_name
Spécifie le nom du périphérique côté hôte pour une interface veth. Par défaut, il s'agit de veth[i].
lxc.net.[i].macvlan.mode
Spécifie le mode de fonctionnement pour un périphérique macvlan. Les modes valides sont bridge, private, vepa et passthru.
lxc.net.[i].ipvlan.mode
Spécifie le mode de fonctionnement pour un périphérique ipvlan. Les modes valides sont l2 et l3.
lxc.net.[i].hwaddr
Spécifie l'adresse MAC à attribuer à l'interface virtualisée. Doit être au format XX:XX:XX:XX:XX:XX.
lxc.net.[i].ipv4.address
Spécifie l'adresse IPv4 à attribuer à l'interface virtualisée. Plusieurs lignes spécifient plusieurs adresses IPv4. L'adresse est au format A.B.C.D/M, par exemple 192.168.1.100/24.
lxc.net.[i].ipv4.gateway
Spécifie l'adresse IPv4 à utiliser comme passerelle à l'intérieur du conteneur. L'adresse est au format A.B.C.D, par exemple 192.168.1.1. Peut également avoir la valeur spéciale auto, ce qui signifie qu'il utilisera l'adresse IP principale du périphérique de pont (spécifiée par l'option lxc.net.[i].link) comme passerelle. auto n'est disponible que lors de l'utilisation des types de réseau veth, macvlan et ipvlan. Peut également avoir la valeur spéciale dev, ce qui signifie que la passerelle par défaut sera définie comme une route de périphérique. Ceci est principalement destiné à être utilisé avec les modes réseau de couche 3, tels que IPVLAN.
lxc.net.[i].ipv6.address
Spécifie l'adresse IPv6 à attribuer à l'interface virtualisée. Plusieurs lignes spécifient plusieurs adresses IPv6. L'adresse est au format x::y/m, par exemple 2003:db8:1:0:214:1234:fe0b:3596/64.
lxc.net.[i].ipv6.gateway
Spécifie l'adresse IPv6 à utiliser comme passerelle à l'intérieur du conteneur. L'adresse est au format x::y, par exemple 2003:db8:1:0::1. Peut également avoir la valeur spéciale auto, ce qui signifie qu'il utilisera l'adresse principale du périphérique de pont (spécifiée par l'option lxc.net.[i].link) et l'utilisera comme passerelle. auto n'est disponible que lors de l'utilisation des types de réseau veth, macvlan et ipvlan. Peut également avoir la valeur spéciale dev, ce qui signifie que la passerelle par défaut sera définie comme une route de périphérique. Ceci est principalement destiné à être utilisé avec les modes réseau de couche 3, tels que IPVLAN.
lxc.net.[i].script.up
Ajoute une option de configuration pour spécifier un script à exécuter après la création et la configuration du réseau du côté hôte.

En plus des informations disponibles pour tous les hooks, les informations suivantes sont fournies au script :

•
LXC_HOOK_TYPE : le type de hook. Il s'agit de 'up' ou 'down'.
•
LXC_HOOK_SECTION : le type de section 'net'.
•
LXC_NET_TYPE : le type de réseau. Il s'agit de l'un des types de réseau valides répertoriés ici (par exemple, 'vlan', 'macvlan', 'ipvlan', 'veth').
•
LXC_NET_PARENT : le périphérique parent sur l'hôte. Ceci n'est défini que pour les types de réseau 'mavclan', 'veth', 'phys'.
•
LXC_NET_PEER : le nom du périphérique homologue sur l'hôte. Ceci n'est défini que pour les types de réseau 'veth'. Notez que ces informations ne sont disponibles que lorsque lxc.hook.version est défini sur 1.

Que ces informations soient fournies sous forme de variables d'environnement ou d'arguments au script dépend de la valeur de lxc.hook.version. Si elle est définie sur 1, les informations sont fournies sous forme de variables d'environnement. Si elle est définie sur 0, les informations sont fournies comme arguments au script.

La sortie standard du script est enregistrée au niveau de débogage. La sortie d'erreur standard n'est pas enregistrée, mais peut être capturée par le hook en redirigeant sa sortie d'erreur standard vers la sortie standard.

lxc.net.[i].script.down
Ajoute une option de configuration pour spécifier un script à exécuter avant la destruction du réseau du côté hôte.

En plus des informations disponibles pour tous les hooks, les informations suivantes sont fournies au script :

•
LXC_HOOK_TYPE : le type de hook. Il s'agit de 'up' ou 'down'.
•
LXC_HOOK_SECTION : le type de section 'net'.
•
LXC_NET_TYPE : le type de réseau. Il s'agit de l'un des types de réseau valides répertoriés ici (par exemple, 'vlan', 'macvlan', 'ipvlan', 'veth').
•
LXC_NET_PARENT : le périphérique parent sur l'hôte. Ceci n'est défini que pour les types de réseau 'mavclan', 'veth', 'phys'.
•
LXC_NET_PEER : le nom du périphérique homologue sur l'hôte. Ceci n'est défini que pour les types de réseau 'veth'. Notez que ces informations ne sont disponibles que lorsque lxc.hook.version est défini sur 1.

Que ces informations soient fournies sous forme de variables d'environnement ou d'arguments au script dépend de la valeur de lxc.hook.version. Si elle est définie sur 1, les informations sont fournies sous forme de variables d'environnement. Si elle est définie sur 0, les informations sont fournies comme arguments au script.

La sortie standard du script est enregistrée au niveau de débogage. La sortie d'erreur standard n'est pas enregistrée, mais peut être capturée par le hook en redirigeant sa sortie d'erreur standard vers la sortie standard.

CONSOLE SYSTÈME DU CONTENEUR

Si le conteneur est configuré avec un système de fichiers racine et que le fichier inittab est configuré pour utiliser la console, vous voudrez peut-être spécifier où va la sortie de cette console.

lxc.console.buffer.size
Définir cette option demande à liblxc d'allouer un tampon circulaire en mémoire. La sortie de la console du conteneur sera écrite dans le tampon circulaire. Notez que le tampon circulaire doit être au moins aussi grand qu'une taille de page standard. Lorsqu'une valeur inférieure à une taille de page unique est fournie, liblxc allouera un tampon circulaire d'une taille de page unique. Une taille de page est généralement de 4 Ko. Le mot-clé 'auto' amènera liblxc à allouer un tampon circulaire de 128 Ko. Lors de la spécification manuelle d'une taille pour le tampon circulaire, la valeur doit être une puissance de 2 une fois convertie en octets. Les préfixes de taille valides sont 'KB', 'MB', 'GB'. (Notez que toutes les conversions sont basées sur des multiples de 1024. Cela signifie que 'KB' == 'KiB', 'MB' == 'MiB', 'GB' == 'GiB'. De plus, la casse du suffixe est ignorée, c'est-à-dire que 'kB', 'KB' et 'Kb' sont traités de la même manière.)
lxc.console.size
Définir cette option demande à liblxc de limiter la taille du fichier journal de la console spécifié dans lxc.console.logfile. Notez que la taille du fichier journal doit être au moins aussi grande qu'une taille de page standard. Lorsqu'une valeur inférieure à une taille de page unique est fournie, liblxc définira la taille du fichier journal à une taille de page unique. Une taille de page est généralement de 4 Ko. Le mot-clé 'auto' amènera liblxc à imposer une limite de 128 Ko au fichier journal. Lors de la spécification manuelle d'une taille pour le fichier journal, la valeur doit être une puissance de 2 une fois convertie en octets. Les préfixes de taille valides sont 'KB', 'MB', 'GB'. (Notez que toutes les conversions sont basées sur des multiples de 1024. Cela signifie que 'KB' == 'KiB', 'MB' == 'MiB', 'GB' == 'GiB'. De plus, la casse du suffixe est ignorée, c'est-à-dire que 'kB', 'KB' et 'Kb' sont traités de la même manière.) Si les utilisateurs souhaitent refléter le tampon circulaire de la console sur disque, ils doivent définir lxc.console.size égal à lxc.console.buffer.size.
lxc.console.logfile
Spécifie un chemin vers un fichier où la sortie de la console sera écrite. Notez que contrairement au fichier journal du tampon circulaire sur disque, ce fichier continuera de croître, remplissant potentiellement les disques de l'utilisateur s'il n'est pas archivé et supprimé. Ce problème peut également être évité en utilisant les options de tampon circulaire en mémoire lxc.console.buffer.size et lxc.console.buffer.logfile.
lxc.console.rotate
Indique s'il faut archiver le fichier journal de la console spécifié dans lxc.console.logfile. Les utilisateurs peuvent envoyer une requête d'API pour archiver le fichier journal. Notez que l'ancien fichier journal portera le même nom que l'original avec le suffixe ".1" ajouté. Les utilisateurs qui souhaitent éviter que le fichier journal de la console ne remplisse le disque doivent archiver le fichier journal et le supprimer s'il n'est pas nécessaire. Ce problème peut également être évité en utilisant les options de tampon circulaire en mémoire lxc.console.buffer.size et lxc.console.buffer.logfile.
lxc.console.path
Spécifie un chemin vers un périphérique auquel la console sera attachée. Le mot-clé 'none' désactivera simplement la console. Notez que lorsque 'none' est spécifié et qu'un nœud de périphérique est créé pour la console dans le conteneur sous /dev/console ou que le /dev/console de l'hôte est monté en association dans le conteneur sous /dev/console, le conteneur aura un accès direct au /dev/console de l'hôte. Ceci est dangereux lorsque le conteneur a un accès en écriture au périphérique et doit donc être utilisé avec prudence.

CONSOLE VIA LES TTY

Cette option est utile si le conteneur est configuré avec un système de fichiers racine et que le fichier inittab est configuré pour lancer un getty sur les ttys. L'option spécifie le nombre de ttys disponibles pour le conteneur. Spécifie le nombre de tty à rendre disponibles au conteneur.

EMPLACEMENT DES PÉRIPHÉRIQUES CONSOLE

Les consoles LXC sont fournies via des pseudo-terminaux Unix98 créés sur l'hôte et montés en association sur les périphériques attendus dans le conteneur. Par défaut, ils sont montés en association sur /dev/console et /dev/ttyN. Cela peut empêcher les mises à niveau de paquets dans l'invité. Par conséquent, vous pouvez spécifier un emplacement de répertoire (sous /dev) sous lequel LXC créera les fichiers et les montera en association. Ceux-ci seront ensuite liés symboliquement à /dev/console et /dev/ttyN. Une mise à niveau de paquet pourra alors réussir car elle sera capable de supprimer et de remplacer les liens symboliques.

lxc.tty.dir
Spécifie un répertoire sous /dev sous lequel créer les périphériques de console du conteneur. Notez que LXC déplacera tous les montages en association ou les nœuds de périphérique pour /dev/console dans ce répertoire.

RÉPERTOIRE /DEV

Par défaut, lxc crée quelques liens symboliques (fd, stdin, stdout, stderr) dans le répertoire /dev du conteneur, mais ne crée pas automatiquement d'entrées de nœuds de périphérique. Cela permet au /dev du conteneur d'être configuré selon les besoins dans le système de fichiers racine du conteneur. Si lxc.autodev est défini sur 1, alors après avoir monté le système de fichiers racine du conteneur, LXC montera un nouveau tmpfs sous /dev (limité à 500 Ko par défaut, sauf définition

d dans lxc.autodev.tmpfs.size) et remplir un ensemble minimal de périphériques initiaux. Ceci est généralement requis lors du démarrage d'un conteneur contenant un système d'initialisation basé sur "systemd", mais peut être facultatif à d'autres moments. Des périphériques supplémentaires dans le répertoire /dev du conteneur peuvent être créés en utilisant le hook lxc.hook.autodev.
lxc.autodev
Définissez ceci à 0 pour empêcher LXC de monter et de peupler un /dev minimal lors du démarrage du conteneur.
lxc.autodev.tmpfs.size
Définissez ceci pour spécifier la taille du tmpfs /dev. La valeur par défaut est 500000 (500 Ko). Si le paramètre est utilisé mais sans valeur, la valeur par défaut est utilisée.

POINTS DE MONTAGE

La section des points de montage spécifie les différents endroits à monter. Ces points de montage seront privés au conteneur et ne seront pas visibles par les processus exécutés en dehors du conteneur. C'est utile pour monter /etc, /var ou /home par exemple.

NOTE - LXC s'assurera généralement que les cibles de montage et les sources de bind-mount relatives sont correctement confinées sous la racine du conteneur, afin d'éviter les attaques impliquant le montage de répertoires et de fichiers de l'hôte. (Les liens symboliques dans les sources de montage absolues sont ignorés) Cependant, si la configuration du conteneur monte d'abord un répertoire qui est sous le contrôle de l'utilisateur du conteneur, comme /home/joe, dans le conteneur à un certain chemin, puis monte sous ce chemin, alors une attaque TOCTTOU serait possible où l'utilisateur du conteneur modifierait un lien symbolique dans son répertoire personnel au bon moment.

lxc.mount.fstab
spécifie l'emplacement d'un fichier au format fstab, contenant les informations de montage. L'emplacement de la cible de montage peut, et dans la plupart des cas devrait, être un chemin relatif, qui deviendra relatif à la racine du conteneur montée. Par exemple, 
             proc proc proc nodev,noexec,nosuid 0 0

Monter un système de fichiers proc sous le /proc du conteneur, quel que soit l'origine du système de fichiers racine. Ceci est résistant aux systèmes de fichiers basés sur des périphériques blocs ainsi qu'au clonage de conteneurs.

Notez que lors du montage d'un système de fichiers à partir d'un fichier image ou d'un périphérique bloc, le troisième champ (fs_vfstype) ne peut pas être auto comme avec mount(8) mais doit être explicitement spécifié.

lxc.mount.entry
spécifie un point de montage correspondant à une ligne au format fstab. De plus, lxc prend en charge la propagation des montages, tels que rshared ou rprivate, et ajoute trois options de montage supplémentaires. optional ne pas échouer si le montage ne fonctionne pas. create=dir ou create=file pour créer un répertoire (ou un fichier) lorsque le point sera monté. relative le chemin source est considéré comme relatif à la racine du conteneur montée. Par exemple, 
             dev/null proc/kcore none bind,relative 0 0

Développera dev/null en ${LXC_ROOTFS_MOUNT}/dev/null, et le montera sur proc/kcore à l'intérieur du conteneur.

lxc.mount.auto
spécifie quels systèmes de fichiers noyau standard doivent être automatiquement montés. Ceci peut simplifier considérablement la configuration. Les systèmes de fichiers sont :
•
proc:mixed (ou proc) : monte /proc en lecture-écriture, mais remonte /proc/sys et /proc/sysrq-trigger en lecture seule pour des raisons de sécurité / d'isolation du conteneur.
•
proc:rw : monte /proc en lecture-écriture
•
sys:mixed (ou sys) : monte /sys en lecture seule mais avec /sys/devices/virtual/net en écriture.
•
sys:ro : monte /sys en lecture seule pour des raisons de sécurité / d'isolation du conteneur.
•
sys:rw : monte /sys en lecture-écriture
•
cgroup:mixed : Monte un tmpfs sur /sys/fs/cgroup, crée des répertoires pour toutes les hiérarchies auxquelles le conteneur est ajouté, crée des sous-répertoires dans ces hiérarchies avec le nom du cgroup, et bind-monte le propre cgroup du conteneur dans ce répertoire. Le conteneur pourra écrire dans son propre répertoire de cgroup, mais pas dans les répertoires parents, car ceux-ci seront remontés en lecture seule.
•
cgroup:mixed:force : L'option force obligera LXC à effectuer les montages cgroup pour le conteneur en toutes circonstances. Sinon, c'est similaire à cgroup:mixed. Ceci est principalement utile lorsque les espaces de noms cgroup sont activés, où LXC laissera normalement le montage des cgroups à l'exécutable init du conteneur car c'est parfaitement sûr.
•
cgroup:ro : similaire à cgroup:mixed, mais tout sera monté en lecture seule.
•
cgroup:ro:force : L'option force obligera LXC à effectuer les montages cgroup pour le conteneur en toutes circonstances. Sinon, c'est similaire à cgroup:ro. Ceci est principalement utile lorsque les espaces de noms cgroup sont activés, où LXC laissera normalement le montage des cgroups à l'exécutable init du conteneur car c'est parfaitement sûr.
•
cgroup:rw : similaire à cgroup:mixed, mais tout sera monté en lecture-écriture. Notez que les chemins menant au propre cgroup du conteneur seront inscriptibles, mais ne seront pas un système de fichiers cgroup mais simplement une partie du tmpfs de /sys/fs/cgroup
•
cgroup:rw:force : L'option force obligera LXC à effectuer les montages cgroup pour le conteneur en toutes circonstances. Sinon, c'est similaire à cgroup:rw. Ceci est principalement utile lorsque les espaces de noms cgroup sont activés, où LXC laissera normalement le montage des cgroups à l'exécutable init du conteneur car c'est parfaitement sûr.
•
cgroup (sans spécificateur) : par défaut cgroup:rw si le conteneur conserve la capacité CAP_SYS_ADMIN, sinon cgroup:mixed.
•
cgroup-full:mixed : monte un tmpfs sur /sys/fs/cgroup, crée des répertoires pour toutes les hiérarchies auxquelles le conteneur est ajouté, bind-monte les hiérarchies de l'hôte vers le conteneur et rend tout en lecture seule sauf le propre cgroup du conteneur. Notez que par rapport à cgroup, où tous les chemins menant au propre cgroup du conteneur sont juste des répertoires simples dans le tmpfs sous-jacent, ici /sys/fs/cgroup/$hierarchy contiendra la hiérarchie complète des cgroups de l'hôte, bien qu'en lecture seule en dehors du propre cgroup du conteneur. Cela peut divulguer beaucoup d'informations dans le conteneur.
•
cgroup-full:mixed:force : L'option force obligera LXC à effectuer les montages cgroup pour le conteneur en toutes circonstances. Sinon, c'est similaire à cgroup-full:mixed. Ceci est principalement utile lorsque les espaces de noms cgroup sont activés, où LXC laissera normalement le montage des cgroups à l'exécutable init du conteneur car c'est parfaitement sûr.
•
cgroup-full:ro : similaire à cgroup-full:mixed, mais tout sera monté en lecture seule.
•
cgroup-full:ro:force : L'option force obligera LXC à effectuer les montages cgroup pour le conteneur en toutes circonstances. Sinon, c'est similaire à cgroup-full:ro. Ceci est principalement utile lorsque les espaces de noms cgroup sont activés, où LXC laissera normalement le montage des cgroups à l'exécutable init du conteneur car c'est parfaitement sûr.
•
cgroup-full:rw : similaire à cgroup-full:mixed, mais tout sera monté en lecture-écriture. Notez que dans ce cas, le conteneur peut s'échapper de son propre cgroup. (Notez également que si le conteneur a le support CAP_SYS_ADMIN et peut monter le système de fichiers cgroup lui-même, il peut le faire de toute façon.)
•
cgroup-full:rw:force : L'option force obligera LXC à effectuer les montages cgroup pour le conteneur en toutes circonstances. Sinon, c'est similaire à cgroup-full:rw. Ceci est principalement utile lorsque les espaces de noms cgroup sont activés, où LXC laissera normalement le montage des cgroups à l'exécutable init du conteneur car c'est parfaitement sûr.
•
cgroup-full (sans spécificateur) : par défaut cgroup-full:rw si le conteneur conserve la capacité CAP_SYS_ADMIN, sinon cgroup-full:mixed.

Si les espaces de noms cgroup sont activés, alors toute demande de montage automatique cgroup sera ignorée, car le conteneur peut monter les systèmes de fichiers lui-même, et le montage automatique peut perturber l'init du conteneur.

Notez que si le montage automatique du système de fichiers cgroup est activé, le tmpfs sous /sys/fs/cgroup sera toujours monté en lecture-écriture (mais pour les cas :mixed et :ro, les hiérarchies individuelles, /sys/fs/cgroup/$hierarchy, seront en lecture seule). Ceci est destiné à contourner une bizarrerie de la commande mountall(8) d'Ubuntu qui provoquera l'attente d'une saisie utilisateur au démarrage du conteneur si /sys/fs/cgroup est monté en lecture seule et que le conteneur ne peut pas le remonter en lecture-écriture en raison d'un manque de CAP_SYS_ADMIN.

Exemples :

              lxc.mount.auto = proc sys cgroup
              lxc.mount.auto = proc:rw sys:rw cgroup-full:rw

SYSTEME DE FICHIERS RACINE

Le système de fichiers racine du conteneur peut être différent de celui du système hôte.

lxc.rootfs.path
spécifie le système de fichiers racine pour le conteneur. Il peut s'agir d'un fichier image, d'un répertoire ou d'un périphérique bloc. S'il n'est pas spécifié, le conteneur partage son système de fichiers racine avec l'hôte.

Pour les conteneurs basés sur des répertoires ou des périphériques blocs simples, un nom de chemin peut être utilisé. Si le rootfs est basé sur un périphérique nbd, alors nbd:fichier:1 spécifie que fichier doit être attaché à un périphérique nbd, et la partition 1 doit être montée comme rootfs. nbd:fichier spécifie que le périphérique nbd lui-même doit être monté. overlayfs:/inférieur:/supérieur spécifie que le rootfs doit être une superposition avec /supérieur monté en lecture-écriture par-dessus un montage en lecture seule de /inférieur. These configuration keys are for specifying the root filesystem for the container.

lxc.rootfs.path
Specify the path to the container's root filesystem. This can be a directory on the host or a path to a specific image type, such as a directory containing a tarball or a path to a btrfs subvolume. For example, lxc.rootfs.path = /path/to/my/container/rootfs.
lxc.rootfs.mount
where to recursively bind lxc.rootfs.path before pivoting. This is to ensure success of the pivot_root(8) syscall. Any directory suffices, the default should generally work.

Specify extra mount options to use when mounting the rootfs. The format of the mount options corresponds to the format used in fstab. In addition, LXC supports the custom idmap= mount option. CONTROL GROUPS ("CGROUPS")

The control group section contains the configuration for the different subsystem. lxc does not check the correctness of the subsystem name. This has the disadvantage of not detecting configuration errors until the container is started, but has the advantage of permitting any future subsystem.

The kernel implementation of cgroups has changed significantly over the years. With Linux 4.5 support for a new cgroup filesystem was added usually referred to as "cgroup2" or "unified hierarchy". Since then the old cgroup filesystem is usually referred to as "cgroup1" or the "legacy hierarchies". Please see the cgroups manual page for a detailed explanation of the differences between the two versions.

LXC distinguishes settings for the legacy and the unified hierarchy by using different configuration key prefixes. To alter settings for controllers in a legacy hierarchy the key prefix lxc.cgroup. must be used and in order to alter the settings for a controller in the unified hierarchy the lxc.cgroup2. key must be used. Note that LXC will ignore lxc.cgroup. settings on systems that only use the unified hierarchy. Conversely, it will ignore lxc.cgroup2. options on systems that only use legacy hierarchies.

At its core a cgroup hierarchy is a way to hierarchically organize processes. Usually a cgroup hierarchy will have one or more "controllers" enabled. A "controller" in a cgroup hierarchy is usually responsible for distributing a specific type of system resource along the hierarchy. Controllers include the "pids" controller, the "cpu" controller, the "memory" controller and others. Some controllers however do not fall into the category of distributing a system resource, instead they are often referred to as "utility" controllers. One utility controller is the device controller. Instead of distributing a system resource it allows one to manage device access.

In the legacy hierarchy the device controller was implemented like most other controllers as a set of files that could be written to. These files where named "devices.allow" and "devices.deny". The legacy device controller allowed the implementation of both "allowlists" and "denylists".

An allowlist is a device program that by default blocks access to all devices. In order to access specific devices "allow rules" for particular devices or device classes must be specified. In contrast, a denylist is a device program that by default allows access to all devices. In order to restrict access to specific devices "deny rules" for particular devices or device classes must be specified.

In the unified cgroup hierarchy the implementation of the device controller has completely changed. Instead of files to read from and write to a eBPF program of BPF_PROG_TYPE_CGROUP_DEVICE can be attached to a cgroup. Even though the kernel implementation has changed completely LXC tries to allow for the same semantics to be followed in the legacy device cgroup and the unified eBPF-based device controller. The following paragraphs explain the semantics for the unified eBPF-based device controller.

As mentioned the format for specifying device rules for the unified eBPF-based device controller is the same as for the legacy cgroup device controller; only the configuration key prefix has changed. Specifically, device rules for the legacy cgroup device controller are specified via lxc.cgroup.devices.allow and lxc.cgroup.devices.deny whereas for the cgroup2 eBPF-based device controller lxc.cgroup2.devices.allow and lxc.cgroup2.devices.deny must be used.

•
A denylist device rule 
	        lxc.cgroup2.devices.deny = a

will cause LXC to instruct the kernel to block access to all devices by default. To grant access to devices allow device rules must be added via the lxc.cgroup2.devices.allow key. This is referred to as a "allowlist" device program.

•
An allowlist device rule 
	        lxc.cgroup2.devices.allow = a

will cause LXC to instruct the kernel to allow access to all devices by default. To deny access to devices deny device rules must be added via lxc.cgroup2.devices.deny key. This is referred to as a "denylist" device program.

•
Specifying any of the aforementioned two rules will cause all previous rules to be cleared, i.e. the device list will be reset.
•
When an allowlist program is requested, i.e. access to all devices is blocked by default, specific deny rules for individual devices or device classes are ignored.
•
When a denylist program is requested, i.e. access to all devices is allowed by default, specific allow rules for individual devices or device classes are ignored.

For example the set of rules:

          lxc.cgroup2.devices.deny = a
          lxc.cgroup2.devices.allow = c *:* m
          lxc.cgroup2.devices.allow = b *:* m
          lxc.cgroup2.devices.allow = c 1:3 rwm

implements an allowlist device program, i.e. the kernel will block access to all devices not specifically allowed in this list. This particular program states that all character and block devices may be created but only /dev/null might be read or written.

If we instead switch to the following set of rules:

          lxc.cgroup2.devices.allow = a
          lxc.cgroup2.devices.deny = c *:* m
          lxc.cgroup2.devices.deny = b *:* m
          lxc.cgroup2.devices.deny = c 1:3 rwm

then LXC would instruct the kernel to implement a denylist, i.e. the kernel will allow access to all devices not specifically denied in this list. This particular program states that no character devices or block devices might be created and that /dev/null is not allow allowed to be read, written, or created.

Now consider the same program but followed by a "global rule" which determines the type of device program (allowlist or denylist) as explained above:

          lxc.cgroup2.devices.allow = a
          lxc.cgroup2.devices.deny = c *:* m
          lxc.cgroup2.devices.deny = b *:* m
          lxc.cgroup2.devices.deny = c 1:3 rwm
          lxc.cgroup2.devices.allow = a

The last line will cause LXC to reset the device list without changing the type of device program.

If we specify:

          lxc.cgroup2.devices.allow = a
          lxc.cgroup2.devices.deny = c *:* m
          lxc.cgroup2.devices.deny = b *:* m
          lxc.cgroup2.devices.deny = c 1:3 rwm
          lxc.cgroup2.devices.deny = a

instead then the last line will cause LXC to reset the device list and switch from an allowlist program to a denylist program.

lxc.cgroup.[controller name].[controller file]
Specify the control group value to be set on a legacy cgroup hierarchy. The controller name is the literal name of the control group. The permitted names and the syntax of their values is not dictated by LXC, instead it depends on the features of the Linux kernel running at the time the container is started, eg. lxc.cgroup.cpuset.cpus
lxc.cgroup2.[controller name].[controller file]
Specify the control group value to be set on the unified cgroup hierarchy. The controller name is the literal name of the control group. The permitted names and the syntax of their values is not dictated by LXC, instead it depends on the features of the Linux kernel running at the time the container is started, eg. lxc.cgroup2.memory.high
lxc.cgroup.dir
specify a directory or path in which the container's cgroup will be created. For example, setting lxc.cgroup.dir = my-cgroup/first for a container named "c1" will create the container's cgroup as a sub-cgroup of "my-cgroup". For example, if the user's current cgroup "my-user" is located in the root cgroup of the cpuset controller in a cgroup v1 hierarchy this would create the cgroup "/sys/fs/cgroup/cpuset/my-user/my-cgroup/first/c1" for the container. Any missing cgroups will be created by LXC. This presupposes that the user has write access to its current cgroup.
lxc.cgroup.dir.container
This is similar to lxc.cgroup.dir, but must be used together with lxc.cgroup.dir.monitor and affects only the container's cgroup path. This option is mutually exclusive with lxc.cgroup.dir. Note that the final path the container attaches to may be extended further by the lxc.cgroup.dir.container.inner option.
lxc.cgroup.dir.monitor
This is the monitor process counterpart to lxc.cgroup.dir.container.
lxc.cgroup.dir.monitor.pivot
On container termination the PID o
si le processus moniteur est attaché à ce cgroup. Ce chemin ne doit pas être un sous-chemin d'un autre répertoire de cgroup configuré pour garantir la suppression appropriée des autres chemins de cgroup lors de la résiliation du conteneur.
lxc.cgroup.dir.container.inner
Spécifiez un sous-répertoire supplémentaire où l'espace de noms cgroup sera créé. Avec cette option, les limites cgroup seront appliquées au chemin externe spécifié dans lxc.cgroup.dir.container, qui n'est pas accessible depuis l'intérieur du conteneur, ce qui permet de mieux appliquer les limites pour les conteneurs privilégiés d'une manière qu'ils ne peuvent pas outrepasser. Ceci ne fonctionne qu'en conjonction avec les options lxc.cgroup.dir.container et lxc.cgroup.dir.monitor et n'a sinon aucun effet.
lxc.cgroup.relative
Définissez ceci sur 1 pour indiquer à LXC de ne jamais échapper au cgroup racine. Cela permet aux utilisateurs de se conformer facilement aux restrictions appliquées par cgroup2 et systemd. Plus précisément, cela rend possible l'exécution de conteneurs LXC en tant que services systemd.

CAPACITÉS

Les capacités peuvent être supprimées dans le conteneur si celui-ci est exécuté en tant que root.

lxc.cap.drop
Spécifiez la capacité à supprimer dans le conteneur. Une seule ligne définissant plusieurs capacités avec une séparation par espace est autorisée. Le format est la casse inférieure de la définition de la capacité sans le préfixe "CAP_", par exemple CAP_SYS_MODULE doit être spécifié comme sys_module. Voir capabilities(7). Si utilisé sans valeur, lxc effacera toutes les capacités de suppression spécifiées jusqu'à ce point.
lxc.cap.keep
Spécifiez la capacité à conserver dans le conteneur. Toutes les autres capacités seront supprimées. Lorsqu'une valeur spéciale "none" est rencontrée, lxc effacera toutes les capacités de conservation spécifiées jusqu'à ce point. Une valeur "none" seule peut être utilisée pour supprimer toutes les capacités.

ESPACES NOMINAUX

Un espace de noms peut être cloné (lxc.namespace.clone), conservé (lxc.namespace.keep) ou partagé (lxc.namespace.share.[identifiant d'espace de noms]).

lxc.namespace.clone
Spécifiez les espaces de noms avec lesquels le conteneur doit être créé. Les espaces de noms à créer sont spécifiés sous forme de liste séparée par des espaces. Chaque espace de noms doit correspondre à l'un des identifiants d'espace de noms standard tels que vus dans le répertoire /proc/PID/ns. Lorsque lxc.namespace.clone n'est pas explicitement défini, tous les espaces de noms pris en charge par le noyau et la configuration actuelle seront utilisés.

Pour créer un nouvel espace de noms de montage, réseau et ipc, définissez lxc.namespace.clone=mount net ipc.

lxc.namespace.keep
Spécifiez les espaces de noms que le conteneur doit hériter du processus qui l'a créé. Les espaces de noms à conserver sont spécifiés sous forme de liste séparée par des espaces. Chaque espace de noms doit correspondre à l'un des identifiants d'espace de noms standard tels que vus dans le répertoire /proc/PID/ns. lxc.namespace.keep est une option de liste noire, c'est-à-dire qu'elle est utile pour garantir que les conteneurs conservent un ensemble spécifique d'espaces de noms.

Pour conserver les espaces de noms réseau, utilisateur et ipc, définissez lxc.namespace.keep=user net ipc.

Notez que le partage des espaces de noms pid ne fonctionnera probablement pas avec la plupart des systèmes init.

Notez que si le conteneur demande un nouvel espace de noms utilisateur et que le conteneur souhaite hériter de l'espace de noms réseau, il doit également hériter de l'espace de noms utilisateur.

lxc.namespace.share.[identifiant d'espace de noms]
Spécifiez un espace de noms à hériter d'un autre conteneur ou processus. Le suffixe [identifiant d'espace de noms] doit être remplacé par l'un des espaces de noms qui apparaissent dans le répertoire /proc/PID/ns.

Pour hériter de l'espace de noms d'un autre processus, définissez lxc.namespace.share.[identifiant d'espace de noms] sur le PID du processus, par exemple lxc.namespace.share.net=42.

Pour hériter de l'espace de noms d'un autre conteneur, définissez lxc.namespace.share.[identifiant d'espace de noms] sur le nom du conteneur, par exemple lxc.namespace.share.pid=c3.

Pour hériter de l'espace de noms d'un autre conteneur situé dans un chemin différent du chemin liblxc standard, définissez lxc.namespace.share.[identifiant d'espace de noms] sur le chemin complet du conteneur, par exemple lxc.namespace.share.user=/opt/c3.

Afin d'hériter des espaces de noms, l'appelant doit avoir un privilège suffisant sur le processus ou le conteneur.

Notez que le partage des espaces de noms pid entre conteneurs système ne fonctionnera probablement pas avec la plupart des systèmes init.

Notez que si deux processus sont dans des espaces de noms utilisateur différents et qu'un processus souhaite hériter de l'espace de noms réseau de l'autre, il doit généralement hériter également de l'espace de noms utilisateur.

Notez que sans configuration supplémentaire prudente d'un LSM, le partage des espaces de noms utilisateur+pid avec une tâche peut permettre à cette tâche d'escalader les privilèges de la tâche appelant liblxc.

lxc.time.offset.boot
Spécifiez un décalage positif ou négatif pour l'horloge de démarrage. Le format accepte les heures (h), les minutes (m), les secondes (s), les millisecondes (ms), les microsecondes (us) et les nanosecondes (ns).
lxc.time.offset.monotonic
Spécifiez un décalage positif ou négatif pour l'horloge monotone. Le format accepte les heures (h), les minutes (m), les secondes (s), les millisecondes (ms), les microsecondes (us) et les nanosecondes (ns).

LIMITES DE RESSOURCES

Les limites de ressources douces et dures pour le conteneur peuvent être modifiées. Les conteneurs non privilégiés ne peuvent que les abaisser. Les ressources qui ne sont pas explicitement spécifiées seront héritées.

lxc.prlimit.[nom de la limite]
Spécifiez la limite de ressources à définir. Une limite est spécifiée par deux valeurs séparées par des deux-points, qui sont soit numériques, soit le mot 'unlimited'. Une seule valeur peut être utilisée comme raccourci pour définir la limite douce et la limite dure à la même valeur. Les noms autorisés sont les noms de ressources "RLIMIT_" en minuscules sans le préfixe "RLIMIT_", par exemple RLIMIT_NOFILE doit être spécifié comme "nofile". Voir setrlimit(2). Si utilisé sans valeur, lxc effacera la limite de ressources spécifiée jusqu'à ce point. Une ressource sans limitation explicitement configurée sera héritée du processus qui démarre le conteneur.

SYSCTL

Configurez les paramètres du noyau pour le conteneur.

lxc.sysctl.[nom des paramètres du noyau]
Spécifiez les paramètres du noyau à définir. Les paramètres disponibles sont ceux listés sous /proc/sys/. Notez que tous les sysctls ne sont pas dans des espaces de noms. Modifier des sysctls non-namespacés modifiera le paramètre global du système. sysctl(8). Si utilisé sans valeur, lxc effacera les paramètres spécifiés jusqu'à ce point.

PROFIL APPARMOR

Si lxc a été compilé et installé avec le support apparmor, et que le système hôte a apparmor activé, alors le profil apparmor sous lequel le conteneur doit être exécuté peut être spécifié dans la configuration du conteneur. Le défaut est lxc-container-default-cgns si le noyau hôte est conscient des espaces de noms cgroup, ou lxc-container-default sinon.

lxc.apparmor.profile
Spécifiez le profil apparmor sous lequel le conteneur doit être exécuté. Pour spécifier que le conteneur doit être non restreint (unconfined), utilisez 
lxc.apparmor.profile = unconfined

Si le profil apparmor doit rester inchangé (c'est-à-dire si vous imbriquez des conteneurs et que vous êtes déjà restreint), utilisez

lxc.apparmor.profile = unchanged

Si vous demandez à LXC de générer le profil apparmor, utilisez

lxc.apparmor.profile = generated
lxc.apparmor.allow_incomplete
Les profils Apparmor sont basés sur les noms de chemin. Par conséquent, de nombreuses restrictions de fichiers nécessitent des restrictions de montage pour être efficaces contre un attaquant déterminé. Cependant, ces restrictions de montage ne sont pas encore implémentées dans le noyau en amont. Sans les restrictions de montage, les profils apparmor protègent toujours contre les dommages accidentels.

Si ce drapeau est 0 (par défaut), le conteneur ne sera pas démarré si le noyau manque des fonctionnalités de montage apparmor, de sorte qu'une régression après une mise à niveau du noyau sera détectée. Pour démarrer le conteneur sous une protection apparmor partielle, définissez ce drapeau sur 1.

lxc.apparmor.allow_nesting
Si vous définissez ceci sur 1, cela entraîne les changements suivants. Lorsque des profils apparmor générés sont utilisés, ils contiendront les changements nécessaires pour permettre la création d'un conteneur imbriqué. En plus des points de montage habituels, /dev/.lxc/proc et /dev/.lxc/sys contiendront des points de montage procfs et sysfs sans les superpositions lxcfs, qui, si des profils apparmor générés sont utilisés, ne seront pas lisibles/inscriptibles directement.
lxc.apparmor.raw
Une liste de lignes de profil AppArmor brutes à ajouter au profil. Valide uniquement lors de l'utilisation de profils générés.

CONTEXTE SELINUX

Si lxc a été compilé et installé avec le support SELinux, et que le système hôte a SELinux activé, alors le contexte SELinux sous lequel le conteneur doit être exécuté

peut être spécifié dans la configuration du conteneur. La valeur par défaut est unconfined_t, ce qui signifie que lxc n'essaiera pas de changer de contexte. Voir /usr/share/lxc/selinux/lxc.te pour un exemple de politique et plus d'informations.

lxc.selinux.context
Spécifie le contexte SELinux sous lequel le conteneur doit être exécuté ou unconfined_t. Par exemple : 
lxc.selinux.context = system_u:system_r:lxc_t:s0:c22
lxc.selinux.context.keyring
Spécifie le contexte SELinux sous lequel la keyring du conteneur doit être créée. Par défaut, il s'agit du même contexte que lxc.selinux.context, ou du contexte sous lequel lxc est exécuté si lxc.selinux.context n'a pas été défini. 
lxc.selinux.context.keyring = system_u:system_r:lxc_t:s0:c22

KEYRING DU NOYAU

Le mécanisme de keyring du noyau Linux est principalement un moyen pour divers composants du noyau de conserver ou de mettre en cache des données de sécurité, des clés d'authentification, des clés de chiffrement et d'autres données dans le noyau. Par défaut, lxc créera une nouvelle keyring de session pour l'application démarrée.

lxc.keyring.session
Désactive la création d'une nouvelle keyring de session par lxc. L'application démarrée héritera alors de la keyring de session actuelle. Par défaut, ou lors de la transmission de la valeur 1, une nouvelle keyring sera créée. 
lxc.keyring.session = 0

CONFIGURATION SECCOMP

Un conteneur peut être démarré avec un ensemble réduit d'appels système disponibles en chargeant un profil seccomp au démarrage. Le fichier de configuration seccomp doit commencer par un numéro de version sur la première ligne, un type de politique sur la deuxième ligne, suivi de la configuration.

Les versions 1 et 2 sont actuellement prises en charge. Dans la version 1, la politique est une simple liste d'autorisation (allowlist). La deuxième ligne doit donc indiquer "allowlist", le reste du fichier contenant un numéro d'appel système (numérique) par ligne. Chaque appel système est autorisé, tandis que tous les numéros non listés sont interdits (denylist) pour une utilisation dans le conteneur.

Dans la version 2, la politique peut être une liste d'interdiction (denylist) ou une liste d'autorisation (allowlist), prend en charge des actions par défaut par règle et par politique, et prend en charge la résolution des appels système par architecture à partir de noms textuels.

Un exemple de politique de liste d'interdiction, dans laquelle tous les appels système sont autorisés à l'exception de mknod, qui ne fera simplement rien et retournera 0 (succès), ressemble à ceci :

      2
      denylist
      mknod errno 0
      ioctl notify

Spécifier "errno" comme action amènera LXC à enregistrer un filtre seccomp qui provoquera le retour d'un errno spécifique à l'appelant. La valeur de l'errno peut être spécifiée après le mot d'action "errno".

Spécifier "notify" comme action amènera LXC à enregistrer un écouteur seccomp et à récupérer un descripteur de fichier d'écoute auprès du noyau. Lorsqu'un appel système est effectué et enregistré comme "notify", le noyau générera un événement poll et enverra un message via le descripteur de fichier. L'appelant peut lire ce message, inspecter les appels système, y compris leurs arguments. Sur la base de ces informations, l'appelant est censé renvoyer un message informant le noyau de l'action à entreprendre. Jusqu'à ce que ce message soit envoyé, le noyau bloquera le processus appelant. Le format des messages à lire et à envoyer est documenté dans seccomp lui-même.

lxc.seccomp.profile
Spécifie un fichier contenant la configuration seccomp à charger avant le démarrage du conteneur.
lxc.seccomp.allow_nesting
Si ce drapeau est défini sur 1, les filtres seccomp seront empilés, même si un profil seccomp est déjà chargé. Cela permet aux conteneurs imbriqués de charger leur propre profil seccomp. Le réglage par défaut est 0.
lxc.seccomp.notify.proxy
Spécifie un socket unix auquel LXC se connectera et transférera les événements seccomp. Le chemin doit être sous la forme unix:/chemin/vers/socket ou unix:@socket. Le premier spécifie un socket de domaine unix lié à un chemin, tandis que le second spécifie un socket de domaine unix abstrait.
lxc.seccomp.notify.cookie
Une chaîne supplémentaire envoyée avec les requêtes de notification seccomp proxifiées.

PR_SET_NO_NEW_PRIVS

Avec PR_SET_NO_NEW_PRIVS actif, execve() promet de ne pas accorder de privilèges pour faire quoi que ce soit qui n'aurait pas pu être fait sans l'appel execve() (par exemple, rendre les bits de mode set-user-ID et set-group-ID, ainsi que les capacités de fichier non fonctionnels). Une fois défini, ce bit ne peut pas être désactivé. La définition de ce bit est héritée par les enfants créés par fork() et clone(), et préservée à travers execve(). Notez que PR_SET_NO_NEW_PRIVS est appliqué après que le conteneur ait changé vers son profil AppArmor ou son contexte SELinux prévu.

lxc.no_new_privs
Spécifie si le drapeau PR_SET_NO_NEW_PRIVS doit être défini pour le conteneur. Définir sur 1 pour activer.

MAPPAGES UID

Un conteneur peut être démarré dans un espace de noms utilisateur privé avec des mappages d'identifiants utilisateur et groupe. Par exemple, vous pouvez mapper l'identifiant utilisateur 0 dans le conteneur à l'identifiant utilisateur 200000 sur l'hôte. L'utilisateur root dans le conteneur sera privilégié dans le conteneur, mais non privilégié sur l'hôte. Normalement, un conteneur système voudra une plage d'identifiants, vous mapperez donc, par exemple, les identifiants utilisateur et groupe 0 à 20 000 dans le conteneur aux identifiants 200 000 à 220 000.

lxc.idmap
Quatre valeurs doivent être fournies. D'abord un caractère, soit 'u', soit 'g', pour spécifier si les identifiants utilisateur ou groupe sont mappés. Ensuite, le premier identifiant utilisateur tel qu'il est vu dans l'espace de noms utilisateur du conteneur. Ensuite, l'identifiant utilisateur tel qu'il est vu sur l'hôte. Enfin, une plage indiquant le nombre d'identifiants consécutifs à mapper.

ACCROCHAGES CONTENEUR

Les accrochages de conteneur sont des programmes ou des scripts qui peuvent être exécutés à divers moments de la durée de vie d'un conteneur.

Lorsqu'un accrochage de conteneur est exécuté, des informations supplémentaires sont transmises. L'argument lxc.hook.version peut être utilisé pour déterminer si les arguments suivants sont passés en tant qu'arguments de ligne de commande ou via des variables d'environnement. Les arguments sont :

•
Nom du conteneur.
•
Section (toujours 'lxc').
•
Type d'accrochage (c'est-à-dire 'clone' ou 'pre-mount').
•
Arguments supplémentaires. Dans le cas de l'accrochage clone, tous les arguments supplémentaires passés apparaîtront comme d'autres arguments de l'accrochage. Dans le cas de l'accrochage stop, les chemins des descripteurs de fichiers pour chacun des espaces de noms du conteneur ainsi que leurs types sont passés.

Les variables d'environnement suivantes sont définies :

•
LXC_CGNS_AWARE : indicateur si le conteneur est conscient de l'espace de noms cgroup.
•
LXC_CONFIG_FILE : chemin vers le fichier de configuration du conteneur.
•
LXC_HOOK_TYPE : type d'accrochage (par exemple, 'clone', 'mount', 'pre-mount'). Notez que l'existence de cette variable d'environnement est conditionnelle à la valeur de lxc.hook.version. Si elle est définie sur 1, LXC_HOOK_TYPE sera défini.
•
LXC_HOOK_SECTION : type de section (par exemple, 'lxc', 'net'). Notez que l'existence de cette variable d'environnement est conditionnelle à la valeur de lxc.hook.version. Si elle est définie sur 1, LXC_HOOK_SECTION sera défini.
•
LXC_HOOK_VERSION : version des accrochages. Cette valeur est identique à la valeur de l'élément de configuration lxc.hook.version du conteneur. Si elle est définie sur 0, des accrochages à l'ancienne sont utilisés. Si elle est définie sur 1, des accrochages à la nouvelle méthode sont utilisés.
•
LXC_LOG_LEVEL : niveau de journalisation du conteneur.
•
LXC_NAME : nom du conteneur.
•
LXC_[IDENTIFIANT_ESPACE_DE_NOMS]_NS : chemin sous /proc/PID/fd/ vers un descripteur de fichier faisant référence à l'espace de noms du conteneur. Pour chaque type d'espace de noms préservé, il y aura une variable d'environnement distincte. Ces variables d'environnement ne seront définies que si lxc.hook.version est défini sur 1.
•
LXC_ROOTFS_MOUNT : chemin vers le système de fichiers racine monté.
•
LXC_ROOTFS_PATH : il s'agit de l'entrée lxc.rootfs.path pour le conteneur. Notez que ce n'est probablement pas là que se trouve le système de fichiers racine monté ; utilisez LXC_ROOTFS_MOUNT pour cela.
•
LXC_SRC_NAME : dans le cas de l'accrochage clone, il s'agit du nom du conteneur d'origine.

La sortie standard des accrochages est enregistrée au niveau de débogage. La sortie d'erreur standard n'est pas enregistrée, mais peut être capturée par l'accrochage en redirigeant sa sortie d'erreur standard vers la sortie standard.

lxc.hook.version
Pour passer les arguments dans le nouveau style via des variables d'environnement, définir sur 1, sinon sur 0 pour les passer en tant qu'arguments. Ce réglage affecte tous les arguments des accrochages qui étaient traditionnellement passés en tant qu'arguments au script. Spécifiquement, il affecte les arguments du nom du conteneur, de la section (par exemple, 'lxc', 'net') et du type d'accrochage (par exemple, 'clone', 'mount', 'pre-mount'). Si des accrochages de nouveau style sont utilisés, les arguments seront disponibles sous forme de variables d'environnement. Le nom du conteneur sera défini dans LXC_NAME. (Ceci est défini indépendamment de la valeur utilisée pour cet élément de configuration.) La section sera définie dans LXC_HOOK_SECTION et le type d'accrochage sera défini dans LXC_HOOK_TYPE. Cela affecte également la manière dont les chemins des descripteurs de fichiers faisant référence aux espaces de noms du conteneur sont passés. S'il est défini sur 1, alors pour chaque espace de noms, une variable d'environnement distincte LXC_[IDENTIFIANT_ESPACE_DE_NOMS]_NS sera définie. S'il est défini sur 0, les chemins seront passés en tant qu'arguments à l'accrochage stop.
lxc.hook.pre-start
Un accrochage à exécuter dans l'espace de noms de l'hôte avant que les tty, consoles ou montages du conteneur ne soient activés.
lxc.hook.pre-mount
Un accrochage à exécuter dans l'espace de noms de l'hôte avant le montage de la racine du système de fichiers du conteneur.

HOOKS DU CONTENEUR

Les hooks sont des scripts appelés à divers stades de la vie du conteneur. Chaque hook est spécifié par une clé de configuration qui définit le type de hook. La valeur de la clé est le chemin absolu du script à exécuter.

Chaque hook est appelé avec plusieurs arguments passés dans le cadre de l'environnement de la commande. Ces arguments sont définis plus bas dans la section VARIABLES D'ENVIRONNEMENT DES HOOKS DE CONTENEUR.

lxc.hook.pre-mount
Un hook à exécuter dans l'espace de noms fs du conteneur mais avant que le rootfs n'ait été configuré. Cela permet la manipulation du rootfs, par exemple, pour monter un système de fichiers chiffré. Les montages effectués dans ce hook ne seront pas reflétés sur l'hôte (à part la propagation des montages), ils seront donc automatiquement nettoyés lorsque le conteneur s'arrête.
lxc.hook.mount
Un hook à exécuter dans l'espace de noms du conteneur après le montage, mais avant le pivot_root.
lxc.hook.autodev
Un hook à exécuter dans l'espace de noms du conteneur après le montage et après l'exécution des hooks de montage, mais avant le pivot_root, si lxc.autodev == 1. Le but de ce hook est d'aider à peupler le répertoire /dev du conteneur lorsque l'option autodev est utilisée pour les conteneurs basés sur systemd. Le répertoire /dev du conteneur est relatif à la variable d'environnement ${LXC_ROOTFS_MOUNT} disponible lorsque le hook est exécuté.
lxc.hook.start-host
Un hook à exécuter dans l'espace de noms de l'hôte après la configuration du conteneur, et juste avant de démarrer l'init du conteneur.
lxc.hook.start
Un hook à exécuter dans l'espace de noms du conteneur juste avant d'exécuter l'init du conteneur. Cela nécessite que le programme soit disponible dans le conteneur.
lxc.hook.stop
Un hook à exécuter dans l'espace de noms de l'hôte avec des références aux espaces de noms du conteneur après l'arrêt du conteneur. Pour chaque espace de noms, un argument supplémentaire est passé au hook contenant le type de l'espace de noms et un nom de fichier qui peut être utilisé pour obtenir un descripteur de fichier vers l'espace de noms correspondant, séparés par deux-points. Le type est le nom tel qu'il apparaîtrait dans le répertoire /proc/PID/ns. Par exemple, pour l'espace de noms de montage, l'argument ressemble généralement à mnt:/proc/PID/fd/12.
lxc.hook.post-stop
Un hook à exécuter dans l'espace de noms de l'hôte après l'arrêt du conteneur.
lxc.hook.clone
Un hook à exécuter lorsque le conteneur est cloné en un nouveau. Voir lxc-clone(1) pour plus d'informations.
lxc.hook.destroy
Un hook à exécuter lorsque le conteneur est détruit.

VARIABLES D'ENVIRONNEMENT DES HOOKS DE CONTENEUR

Un certain nombre de variables d'environnement sont mises à disposition des hooks de démarrage pour fournir des informations de configuration et aider au fonctionnement des hooks. Toutes les variables ne sont pas valides dans tous les contextes. En particulier, tous les chemins sont relatifs au système hôte et, à ce titre, ne sont pas valides pendant le hook lxc.hook.start.

LXC_NAME
Le nom LXC du conteneur. Utile pour enregistrer des messages dans des environnements de journalisation communs. [-n]
LXC_CONFIG_FILE
Chemin relatif à l'hôte vers le fichier de configuration du conteneur. Cela permet au conteneur de référencer le fichier de configuration d'origine, de niveau supérieur, pour le conteneur afin de localiser toute information de configuration supplémentaire non rendue disponible autrement. [-f]
LXC_CONSOLE
Le chemin vers la sortie console du conteneur s'il n'est pas NULL. [-c] [lxc.console.path]
LXC_CONSOLE_LOGPATH
Le chemin vers la sortie du journal de la console du conteneur s'il n'est pas NULL. [-L]
LXC_ROOTFS_MOUNT
L'emplacement de montage auquel le conteneur est initialement lié. Ce sera le chemin relatif à l'hôte vers le rootfs du conteneur pour l'instance de conteneur en cours de démarrage et c'est là que les modifications doivent être apportées pour cette instance. [lxc.rootfs.mount]
LXC_ROOTFS_PATH
Le chemin relatif à l'hôte vers la racine du conteneur qui a été montée à l'emplacement rootfs.mount. [lxc.rootfs.path]
LXC_SRC_NAME
Uniquement pour le hook de clonage. Est défini sur le nom du conteneur d'origine.
LXC_TARGET
Uniquement pour le hook d'arrêt. Est défini sur "stop" pour un arrêt de conteneur ou "reboot" pour un redémarrage de conteneur.
LXC_CGNS_AWARE
Si non défini, alors cette version de lxc n'est pas consciente des espaces de noms cgroup. S'il est défini, il sera défini sur 1, et lxc est conscient des espaces de noms cgroup. Notez que cela ne garantit pas que les espaces de noms cgroup sont activés dans le noyau. Ceci est utilisé par le hook de montage lxcfs.

JOURNALISATION

La journalisation peut être configurée par conteneur. Par défaut, en fonction de la manière dont le paquet lxc a été compilé, le démarrage du conteneur est journalisé uniquement au niveau ERREUR, et journalisé dans un fichier portant le nom du conteneur (avec '.log' ajouté) soit sous le chemin du conteneur, soit sous /var/log/lxc.

Le niveau de journalisation par défaut et le fichier de journalisation peuvent être spécifiés dans le fichier de configuration du conteneur, remplaçant ainsi le comportement par défaut. Notez que les entrées du fichier de configuration peuvent à leur tour être remplacées par les options de la ligne de commande de lxc-start.

lxc.log.level
Le niveau auquel journaliser. Le niveau de journalisation est un entier dans la plage 0..8 inclusivement, où un nombre plus bas signifie un débogage plus verbeux. En particulier, 0 = trace, 1 = debug, 2 = info, 3 = notice, 4 = warn, 5 = error, 6 = critical, 7 = alert, et 8 = fatal. Si non spécifié, le niveau est par défaut à 5 (error), de sorte que seuls les erreurs et au-dessus soient journalisés.

Notez que lorsqu'un script (tel qu'un script de hook ou un script d'interface réseau montante ou descendante) est appelé, la sortie standard du script est journalisée au niveau 1, debug.

lxc.log.file
Le fichier dans lequel les informations de journalisation doivent être écrites.
lxc.log.syslog
Envoyer les informations de journalisation à syslog. Il respecte le niveau de journalisation défini dans lxc.log.level. L'argument doit être la facilité syslog à utiliser, les facilités valides sont : daemon, local0, local1, local2, local3, local4, local5, local5, local6, local7.

DÉMARRAGE AUTOMATIQUE

Les options de démarrage automatique permettent de marquer quels conteneurs doivent être démarrés automatiquement et dans quel ordre. Ces options peuvent être utilisées directement par les outils LXC ou par des outils externes fournis par les distributions.

lxc.start.auto
Si le conteneur doit être démarré automatiquement. Les valeurs valides sont 0 (désactivé) et 1 (activé).
lxc.start.delay
Combien de temps attendre (en secondes) après le démarrage du conteneur avant de démarrer le suivant.
lxc.start.order
Un entier utilisé pour trier les conteneurs lors du démarrage automatique d'une série de conteneurs à la fois. Une valeur plus faible signifie un démarrage plus précoce.
lxc.monitor.unshare
Si différent de zéro, l'espace de noms de montage sera dissocié de l'hôte avant l'initialisation du conteneur (avant l'exécution de tout hook de pré-démarrage). Cela nécessite la capacité CAP_SYS_ADMIN au démarrage. La valeur par défaut est 0.
lxc.monitor.signal.pdeath
Définit le signal à envoyer à l'init du conteneur lorsque le moniteur lxc se termine. Par défaut, il est défini sur SIGKILL, ce qui entraînera la mise à mort de tous les processus du conteneur lorsque le processus moniteur lxc meurt. Pour s'assurer que les conteneurs restent actifs même si le moniteur lxc meurt, définissez ceci sur 0.
lxc.group
Une clé à valeurs multiples (peut être utilisée plusieurs fois) pour placer le conteneur dans un groupe de conteneurs. Ces groupes peuvent ensuite être utilisés (entre autres) pour démarrer une série de conteneurs liés.

DÉMARRAGE AUTOMATIQUE ET DÉMARRAGE SYSTÈME

Chaque conteneur peut faire partie d'un nombre quelconque de groupes ou d'aucun groupe. Deux groupes sont spéciaux. L'un est le groupe NULL, c'est-à-dire que le conteneur n'appartient à aucun groupe. L'autre groupe est le groupe "onboot".

Lorsque le système démarre avec le service LXC activé, il tentera d'abord de démarrer tous les conteneurs avec lxc.start.auto == 1 qui sont membres du groupe "onboot". Le démarrage se fera dans l'ordre de lxc.start.order. Si un lxc.start.delay a été spécifié, ce délai sera respecté avant de tenter de démarrer le conteneur suivant pour laisser au conteneur actuel le temps de commencer son initialisation et de réduire la surcharge du système hôte. Après avoir démarré les membres du groupe "onboot", le système LXC procédera au démarrage des conteneurs avec lxc.start.auto == 1 qui ne sont membres d'aucun groupe (le groupe NULL) et continuera comme avec le groupe onboot.

ENVIRONNEMENT DU CONTENEUR

Si vous souhaitez passer des variables d'environnement dans le conteneur (c'est-à-dire des variables d'environnement qui seront disponibles pour init et tous ses descendants), vous pouvez utiliser les paramètres lxc.environment pour ce faire. Veillez à ne pas passer d'informations sensibles ; tout processus dans le conteneur dont l'environnement n'a pas été purgé aura ces variables à sa disposition, et les variables d'environnement sont toujours disponibles via /proc/PID/environ.

Ce paramètre de configuration peut être spécifié plusieurs fois ; une fois pour chaque variable d'environnement que vous souhaitez configurer.

NAME

lxc.container.conf - lxc container configuration file format

DESCRIPTION

This document describes the format of the configuration files used by LXC containers.

These files are generally located in /var/lib/lxc/<container_name>/config, but can be specified on the command line with the -f option for commands like lxc-start.

Configuration directives are processed in the order they appear in the file. Later directives override earlier ones.

Comments start with a # character and extend to the end of the line.

Directives are of the form key = value. Whitespace around the = sign is ignored. Whitespace within the key or value is significant.

Some directives can be specified multiple times. For example, multiple network devices or multiple capabilities to drop.

lxc.uts.name
Specify the hostname for the container. If not specified, the hostname will be the same as the name of the container. For example:
        lxc.uts.name = mycontainerhostname
lxc.console.path
Specify the path to the virtual console device. For example:
        lxc.console.path = pts/2
lxc.console.dev
Specify the device node for the virtual console. For example:
        lxc.console.dev = /dev/pts/2
lxc.console.fifo.path
Specify the path to the FIFO device for the console. For example:
        lxc.console.fifo.path = /var/run/lxc/mycontainer/console.fifo
lxc.console.fifo.owner
Specify the owner of the FIFO device. For example:
        lxc.console.fifo.owner = <user>:<group>
lxc.console.logfile
Specify the path to the console log file. For example:
        lxc.console.logfile = /var/log/lxc/mycontainer.log
lxc.rootfs.path
Specify the path to the root filesystem of the container. This can be a path on the host system, or a special value like `dir:/path/to/rootfs` for a directory, `tar:/path/to/rootfs.tar.gz` for a tarball, or `pivot:/path/to/rootfs` for a rootfs that uses pivot_root. For example:
        lxc.rootfs.path = dir:/var/lib/lxc/mycontainer/rootfs
        lxc.rootfs.path = lxc:/var/lib/lxc/mycontainer/rootfs
lxc.rootfs.options
Specify mount options for the root filesystem. For example, to use `idmap=ms_phys` which maps the container's root user to the host's root user:
        lxc.rootfs.options = idmap=ms_phys
lxc.cap.keep
Specify capabilities to keep within the container. These are added to the capabilities dropped by default. For example:
        lxc.cap.keep = sys_admin net_admin
lxc.cap.drop
Specify capabilities to drop from the container. For example:
        lxc.cap.drop = sys_module mknod setuid net_raw
lxc.cgroup.path
Specify the path to the control group for the container. If not specified, it defaults to `lxc/`. For example:
        lxc.cgroup.path = machine.slice/lxc-.service
lxc.cgroup.<subsystem>.<parameter>
Set a specific control group parameter. For example, to restrict the container to CPUs 0 and 1:
        lxc.cgroup.cpuset.cpus = 0,1

See cgroups(7) for available subsystems and parameters.

lxc.idmap
Specify a user or group ID mapping. The format is `type offset host_id uid_map_count`. For example, to map UIDs 0-9999 in the container to UIDs 100000-109999 on the host:
        lxc.idmap = u 0 100000 10000
        lxc.idmap = g 0 100000 10000
lxc.hook.autodev
If set to 1, LXC will automatically create the /dev directory inside the container based on the host's /dev directory. This is deprecated and will be removed in a future release.
lxc.hook.pre-mount
Path to an executable script to run before the root filesystem is mounted.
lxc.hook.mount
Path to an executable script to run after the root filesystem is mounted, but before other mounts.
lxc.hook.start
Path to an executable script to run after the container's namespaces are created and it's ready to run processes.
lxc.hook.stop
Path to an executable script to run before the container's processes are stopped.
lxc.hook.umount
Path to an executable script to run after the container's processes have been stopped and before the root filesystem is unmounted.
lxc.hook.post-stop
Path to an executable script to run after the container has been fully stopped and unmounted.
lxc.mount.entry
Define a mount point inside the container. The format is similar to fstab(5). For example:
        lxc.mount.entry = /dev/pts devpts devpts rw,noexec,nosuid 0 0
        lxc.mount.entry = proc proc proc defaults 0 0
        lxc.mount.entry = sysfs sysfs sysfs defaults 0 0
        lxc.mount.entry = /path/to/host/data /path/in/container none bind,rw 0 0
lxc.mount.fstab
Specify an alternative fstab file to use for mounting the container's filesystems.
lxc.environment
Specify an environment variable to pass into the container. Example: 
              lxc.environment = APP_ENV=production
              lxc.environment = SYSLOG_SERVER=192.0.2.42

It is possible to inherit host environment variables by setting the name of the variable without a "=" sign. For example:

              lxc.environment = PATH
