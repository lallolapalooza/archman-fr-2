NOM

lxc - conteneurs Linux

APERÇU

La technologie des conteneurs est activement intégrée au noyau Linux standard. Elle offre la gestion des ressources via les cgroups et l'isolation des ressources via les namespaces.

lxc vise à utiliser ces nouvelles fonctionnalités pour fournir un objet conteneur utilisateur (userspace) offrant une isolation complète des ressources et un contrôle des ressources pour une application ou un système complet.

lxc est suffisamment léger pour gérer facilement un conteneur avec des commandes simples, et suffisamment complet pour être utilisé à d'autres fins.

EXIGENCES

Le noyau version >= 3.10, fourni avec les distributions, fonctionnera avec lxc. Celui-ci aura moins de fonctionnalités, mais suffisamment pour être intéressant.

lxc repose sur un ensemble de fonctionnalités fournies par le noyau. Le script d'aide lxc-checkconfig vous donnera des informations sur la configuration de votre noyau, les fonctionnalités requises et manquantes.

SPÉCIFICATION FONCTIONNELLE

Un conteneur est un objet isolant certaines ressources de l'hôte, pour l'application ou le système qui y tourne.

L'application / le système sera lancé à l'intérieur d'un conteneur spécifié par une configuration soit créée initialement, soit passée en paramètre des commandes.

Comment exécuter une application dans un conteneur

Avant d'exécuter une application, vous devez savoir quelles ressources vous souhaitez isoler. La configuration par défaut isole les PID, l'IPC sysv et les points de montage. Si vous souhaitez exécuter un simple shell dans un conteneur, une configuration de base est nécessaire, surtout si vous souhaitez partager le rootfs. Si vous souhaitez exécuter une application telle que sshd, vous devez fournir une nouvelle pile réseau et un nouveau nom d'hôte. Si vous souhaitez éviter les conflits avec certains fichiers, par exemple /var/run/httpd.pid, vous devez remonter /var/run avec un répertoire vide. Si vous souhaitez éviter les conflits dans tous les cas, vous pouvez spécifier un rootfs pour le conteneur. Le rootfs peut être une arborescence de répertoires, précédemment montée avec le rootfs initial, vous permettant ainsi d'utiliser toujours votre distribution mais avec vos propres /etc et /home.

Voici un exemple d'arborescence de répertoires pour sshd :

[root@lxc sshd]$ tree -d rootfs

rootfs	
|-- bin	
|-- dev	
|   |-- pts
|   `-- shm
|       `-- network
|-- etc	
|   `-- ssh
|-- lib	
|-- proc
|-- root
|-- sbin
|-- sys	
|-- usr	
`-- var	
    |-- empty
    |   `-- sshd
    |-- lib
    |   `-- empty
    |       `-- sshd
    `-- run
        `-- sshd

et le fichier des points de montage associé :

	[root@lxc sshd]$ cat fstab
	/lib /home/root/sshd/rootfs/lib none ro,bind 0 0
	/bin /home/root/sshd/rootfs/bin none ro,bind 0 0
	/usr /home/root/sshd/rootfs/usr none ro,bind 0 0
	/sbin /home/root/sshd/rootfs/sbin none ro,bind 0 0

Comment exécuter un système dans un conteneur

Exécuter un système à l'intérieur d'un conteneur est paradoxalement plus simple que d'exécuter une application. Pourquoi ? Parce que vous n'avez pas à vous soucier des ressources à isoler, tout doit être isolé, les autres ressources sont spécifiées comme étant isolées mais sans configuration car le conteneur les mettra en place. Par exemple, l'adresse ipv4 sera configurée par les scripts d'initialisation du conteneur système. Voici un exemple de fichier des points de montage :

	[root@lxc debian]$ cat fstab
	/dev	/home/root/debian/rootfs/dev none bind 0 0
	/dev/pts /home/root/debian/rootfs/dev/pts  none bind 0 0

CYCLE DE VIE DU CONTENEUR

Lorsque le conteneur est créé, il contient les informations de configuration. Lorsqu'un processus est lancé, le conteneur démarre et s'exécute. Lorsque le dernier processus en cours d'exécution dans le conteneur se termine, le conteneur est arrêté.

En cas d'échec lors de l'initialisation du conteneur, celui-ci passe par l'état d'abandon.

CONFIGURATION

Le conteneur est configuré via un fichier de configuration, dont le format est décrit dans lxc.conf(5)

CRÉATION / DESTRUCTION DES CONTENEURS

Un objet conteneur persistant peut être créé via la commande lxc-create. Elle prend en paramètre un nom de conteneur et un fichier de configuration et un modèle optionnels. Le nom est utilisé par les différentes commandes pour faire référence à ce conteneur. La commande lxc-destroy détruit l'objet conteneur.

lxc-create -n foo
lxc-destroy -n foo

CONTENEUR VOLATILE

Il n'est pas obligatoire de créer un objet conteneur avant de le lancer. Le conteneur peut être lancé directement avec un fichier de configuration en paramètre.

LANCEMENT / ARRÊT DU CONTENEUR

Une fois le conteneur créé, il est prêt à exécuter une application / un système. C'est le but des commandes lxc-execute et lxc-start. Si le conteneur n'a pas été créé avant le lancement de l'application, le conteneur utilisera le fichier de configuration passé en paramètre de la commande, et s'il n'y a pas de tel paramètre, il utilisera une isolation par défaut. Si l'application se termine, le conteneur sera arrêté, mais si nécessaire, la commande lxc-stop peut être utilisée pour arrêter le conteneur.

Exécuter une application dans un conteneur n'est pas exactement la même chose qu'exécuter un système. Pour cette raison, il existe deux commandes différentes pour exécuter une application dans un conteneur :

lxc-execute -n foo [-f config] /bin/bash
lxc-start -n foo [-f config] [/bin/bash]

La commande lxc-execute exécutera la commande spécifiée dans un conteneur via un processus intermédiaire, lxc-init. Ce lxc-init, après avoir lancé la commande spécifiée, attendra sa fin et tous les autres processus réparentés. (pour supporter les démons dans le conteneur). En d'autres termes, dans le conteneur, lxc-init a le PID 1 et le premier processus de l'application a le PID 2.

La commande lxc-start exécutera directement la commande spécifiée dans le conteneur. Le PID du premier processus est 1. Si aucune commande n'est spécifiée, lxc-start exécutera la commande définie dans lxc.init.cmd ou, si elle n'est pas définie, /sbin/init.

Pour résumer, lxc-execute est destiné à l'exécution d'une application et lxc-start est plus adapté à l'exécution d'un système.

Si l'application ne répond plus, est inaccessible ou ne parvient pas à se terminer par elle-même, une commande lxc-stop sauvage tuera sans pitié tous les processus du conteneur.

lxc-stop -n foo -k

SE CONNECTER À UN TTY DISPONIBLE

Si le conteneur est configuré avec des tty, il est possible d'y accéder via ceux-ci. Il appartient au conteneur de fournir un ensemble de tty disponibles à utiliser par la commande suivante. Lorsque le tty est perdu, il est possible de s'y reconnecter sans avoir à se reconnecter.

lxc-console -n foo -t 3

GELER / DÉGELER LE CONTENEUR

Parfois, il est utile d'arrêter tous les processus appartenant à un conteneur, par exemple pour la planification des tâches. Les commandes :

lxc-freeze -n foo

mettront tous les processus dans un état ininterrompu et

lxc-unfreeze -n foo

les reprendront.

lxc - manuel

NOM

lxc � gestionnaire de conteneurs Linux

VUE D'ENSEMBLE

lxc est un ensemble d'outils pour créer et gérer des conteneurs Linux. Il utilise le support natif du noyau Linux pour la virtualisation au niveau du système d'exploitation.

Les conteneurs sont des environnements légers et isolés qui partagent le noyau du système hôte mais ont leur propre espace utilisateur. Cela permet d'exécuter plusieurs applications ou systèmes d'exploitation isolés sur un seul hôte, avec une surcharge minimale.

EXIGENCES

Les conteneurs LXC nécessitent un noyau Linux compatible avec les cgroups (groupes de contrôle) et les namespaces (espaces de noms).

La fonctionnalité de suspension/reprise des conteneurs (freezer cgroup v1 controller) doit être activée dans le noyau.

SPÉCIFICATIONS FONCTIONNELLES

OBTENIR DES INFORMATIONS SUR UN CONTENEUR

Lorsqu'il y a beaucoup de conteneurs, il est difficile de suivre ce qui a été créé ou détruit, ce qui est en cours d'exécution ou quels sont les PID s'exécutant dans un conteneur spécifique. Pour cette raison, les commandes suivantes peuvent être utiles :

lxc-ls -f
lxc-info -n foo

lxc-ls liste les conteneurs.

lxc-info donne des informations pour un conteneur spécifique.

Voici un exemple de la façon dont la combinaison de ces commandes permet de lister tous les conteneurs et de récupérer leur état.

for i in $(lxc-ls -1); do
  lxc-info -n $i
done

SURVEILLER UN CONTENEUR

Il est parfois utile de suivre les états d'un conteneur, par exemple pour le surveiller ou simplement pour attendre un état spécifique dans un script.

La commande lxc-monitor surveillera un ou plusieurs conteneurs. Le paramètre de cette commande accepte une expression régulière par exemple :

lxc-monitor -n "foo|bar"

surveillera les états des conteneurs nommés 'foo' et 'bar', et :

lxc-monitor -n ".*"

surveillera tous les conteneurs.

Pour un conteneur 'foo' qui démarre, effectue un travail et se termine, la sortie sera de la forme :

'foo' changed state to [STARTING]
'foo' changed state to [RUNNING]
'foo' changed state to [STOPPING]
'foo' changed state to [STOPPED]

La commande lxc-wait attendra un changement d'état spécifique et se terminera. Ceci est utile pour les scripts afin de synchroniser le lancement d'un conteneur ou sa fin. Le paramètre est une combinaison OR de différents états. L'exemple suivant montre comment attendre un conteneur s'il a démarré avec succès en tant que démon.

# lance lxc-wait en arrière-plan
lxc-wait -n foo -s STOPPED &
LXC_WAIT_PID=$!
# cette commande passe en arrière-plan
lxc-execute -n foo mydaemon &
# bloque jusqu'à ce que lxc-wait se termine
# et lxc-wait se termine lorsque le conteneur
# est STOPPED
wait $LXC_WAIT_PID
echo "'foo' est terminé"

PARAMÈTRES CGROUP POUR LES CONTENEURS

Le conteneur est lié aux groupes de contrôle. Lorsqu'un conteneur est démarré, un groupe de contrôle est créé et associé à celui-ci. Les propriétés du groupe de contrôle peuvent être lues et modifiées lorsque le conteneur est en cours d'exécution en utilisant la commande lxc-cgroup.

La commande lxc-cgroup est utilisée pour définir ou récupérer un sous-système de groupe de contrôle associé à un conteneur. Le nom du sous-système est géré par l'utilisateur, la commande ne fera aucune vérification de syntaxe sur le nom du sous-système ; si le nom du sous-système n'existe pas, la commande échouera.

lxc-cgroup -n foo cpuset.cpus

affichera le contenu de ce sous-système.

lxc-cgroup -n foo cpu.shares 512

définira le sous-système à la valeur spécifiée.
