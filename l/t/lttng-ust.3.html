DESCRIPTION

Le projet Linux Trace Toolkit: next generation http://lttng.org/ est une collection de logiciels libres utilisée pour le traçage corrélé du noyau Linux, des applications et des bibliothèques de l'espace utilisateur.

LTTng-UST est la composante de traçage de l'espace utilisateur du projet LTTng. Il s'agit d'un portage en espace utilisateur des capacités de traçage à faible surcharge du traçeur du noyau Linux LTTng. La bibliothèque liblttng-ust est utilisée pour tracer les applications et bibliothèques de l'espace utilisateur.


Note

Cette page de manuel concerne la bibliothèque liblttng-ust. Le projet LTTng-UST fournit également des paquets Java et Python pour tracer les applications écrites dans ces langages. La manière d'instrumenter et de tracer les applications Java et Python est documentée dans la documentation LTTng en ligne http://lttng.org/docs/.

Il existe trois façons d'utiliser liblttng-ust :

•En utilisant l'API lttng_ust_tracef(3), qui est similaire à printf(3).
•En utilisant l'API lttng_ust_tracelog(3), qui est lttng_ust_tracef(3) avec un paramètre de niveau de journalisation.
•En définissant vos propres points de trace. Voir la section Création d'un fournisseur de points de trace ci-dessous.

Compatibilité avec les anciennes APIs

Depuis LTTng-UST 2.13, la définition LTTNG_UST_COMPAT_API_VERSION contrôle quelles APIs LTTng-UST sont disponibles (compilées) :

Non défini

N (0 ou entier positif)

L'API version N, ainsi que toutes les APIs existantes suivantes, sont disponibles. Les APIs précédentes ne sont pas disponibles (non compilées).

Un fournisseur de points de trace est un objet compilé contenant les sondes d'événements correspondant à vos définitions de points de trace personnalisés. Un fournisseur de points de trace contient le code pour obtenir la taille d'un événement et pour le sérialiser, entre autres choses.

Pour créer un fournisseur de points de trace, commencez avec le modèle d'en-tête de fournisseur de points de trace suivant :

#undef LTTNG_UST_TRACEPOINT_PROVIDER
#define LTTNG_UST_TRACEPOINT_PROVIDER my_provider
#undef LTTNG_UST_TRACEPOINT_INCLUDE
#define LTTNG_UST_TRACEPOINT_INCLUDE "./tp.h"
#if !defined(_TP_H) || \
    defined(LTTNG_UST_TRACEPOINT_HEADER_MULTI_READ)
#define _TP_H
#include <lttng/tracepoint.h>
/*
 * LTTNG_UST_TRACEPOINT_EVENT(), LTTNG_UST_TRACEPOINT_EVENT_CLASS(),
 * LTTNG_UST_TRACEPOINT_EVENT_INSTANCE(),
 * LTTNG_UST_TRACEPOINT_LOGLEVEL(), et `LTTNG_UST_TRACEPOINT_ENUM()`
 * sont utilisés ici.
 */
#endif /* _TP_H */
#include <lttng/tracepoint-event.h>

Dans ce modèle, le fournisseur de points de trace est nommé my_provider (définition LTTNG_UST_TRACEPOINT_PROVIDER). Le fichier doit porter le nom de la définition LTTNG_UST_TRACEPOINT_INCLUDE (tp.h dans ce cas). Entre #include <lttng/tracepoint.h> et #endif se trouvent les appels des macros LTTNG_UST_TRACEPOINT_EVENT(), LTTNG_UST_TRACEPOINT_EVENT_CLASS(), LTTNG_UST_TRACEPOINT_EVENT_INSTANCE(), LTTNG_UST_TRACEPOINT_LOGLEVEL() et LTTNG_UST_TRACEPOINT_ENUM().


Note

Vous pouvez éviter d'écrire le prologue et l'épilogue répétitifs dans le fichier modèle ci-dessus en utilisant l'outil lttng-gen-tp(1) fourni avec LTTng-UST.

Le fichier d'en-tête du fournisseur de points de trace doit être inclus dans un fichier source qui ressemble à ceci :

#define LTTNG_UST_TRACEPOINT_CREATE_PROBES
#include "tp.h"

Ensemble, ces deux fichiers (appelons-les tp.h et tp.c) forment les sources du fournisseur de points de trace, prêts à être compilés.

Vous pouvez créer plusieurs fournisseurs de points de trace à utiliser dans une seule application, mais chacun doit avoir son propre fichier d'en-tête.

La section d'utilisation de LTTNG_UST_TRACEPOINT_EVENT() ci-dessous montre comment utiliser la macro LTTNG_UST_TRACEPOINT_EVENT() pour définir les points de trace réels dans le fichier d'en-tête du fournisseur de points de trace.

Voir la section EXEMPLE ci-dessous pour un exemple complet.

Utilisation de LTTNG_UST_TRACEPOINT_EVENT()

La macro LTTNG_UST_TRACEPOINT_EVENT() est utilisée dans un fichier d'en-tête de fournisseur modèle (voir la section Création d'un fournisseur de points de trace ci-dessus) pour définir les points de trace LTTng-UST.

Le modèle d'utilisation de LTTNG_UST_TRACEPOINT_EVENT() est le suivant :

LTTNG_UST_TRACEPOINT_EVENT(
    /* Nom du fournisseur de points de trace */
    my_provider,
    /* Nom du point de trace/événement */
    my_tracepoint,
    /* Liste des arguments du point de trace (entrée) */
    LTTNG_UST_TP_ARGS(
        ...
    ),
    /* Liste des champs de l'événement éventuel (sortie) */
    LTTNG_UST_TP_FIELDS(
        ...
    )
)

La macro LTTNG_UST_TP_ARGS() contient les arguments d'entrée du point de trace. Ces arguments peuvent être utilisés dans les expressions d'arguments des champs de sortie définis dans LTTNG_UST_TP_FIELDS().

Le format des paramètres de LTTNG_UST_TP_ARGS() est : type C, puis nom de l'argument ; répéter autant que nécessaire, jusqu'à dix fois. Par exemple :

LTTNG_UST_TP_ARGS(
    int, my_int,
    const char *, my_string,
    FILE *, my_file,
    double, my_float,
    struct my_data *, my_data
)

La macro LTTNG_UST_TP_FIELDS() contient les champs de sortie du point de trace, c'est-à-dire les données réelles qui peuvent être enregistrées dans la charge utile d'un événement émis par ce point de trace.

La macro LTTNG_UST_TP_FIELDS() contient une liste de macros lttng_ust_field_*() NON séparées par des virgules. Les macros disponibles sont documentées dans la section Macros de type de champ lttng_ust_field_*() disponibles ci-dessous.

Utilisation de LTTNG_UST_TRACEPOINT_ENUM()

Un champ d'énumération est une liste de mappages entre des entiers, ou une plage d'entiers, et des chaînes de caractères (parfois appelés *labels* ou *énumérateurs*). Les champs d'énumération peuvent être utilisés pour avoir une trace plus compacte lorsque les valeurs possibles pour un champ sont limitées.

Un champ d'énumération est défini avec la macro LTTNG_UST_TRACEPOINT_ENUM() :

LTTNG_UST_TRACEPOINT_ENUM(
    /* Nom du fournisseur de tracepoint */
    mon_fournisseur,
    /* Nom de l'énumération (unique dans tout le fournisseur de tracepoint) */
    mon_enum,
    /* Mappages de l'énumération */
    LTTNG_UST_TP_ENUM_VALUES(
        ...
    )
)

LTTNG_UST_TP_ENUM_VALUES() contient une liste de mappages d'énumération, NON séparés par des virgules. Deux macros peuvent être utilisées dans LTTNG_UST_TP_ENUM_VALUES() : lttng_ust_field_enum_value() et lttng_ust_field_enum_range().

lttng_ust_field_enum_value() est un mappage de valeur unique :

lttng_ust_field_enum_value(label, valeur)

Cette macro mappe la chaîne de caractères label donnée à la valeur valeur.

lttng_ust_field_enum_range() est un mappage de plage :

lttng_ust_field_enum_range(label, début, fin)

Cette macro mappe la chaîne de caractères label donnée à la plage d'entiers de début à fin, inclusivement. Les mappages de plage peuvent se chevaucher, mais le comportement est défini par l'implémentation : chaque lecteur de trace gère les plages qui se chevauchent comme il le souhaite.

Voir la section *EXEMPLE* ci-dessous pour un exemple complet.

Utilisation de LTTNG_UST_TRACEPOINT_EVENT_CLASS()

Une classe de tracepoint est une classe de tracepoints partageant les mêmes types et noms de champs. Une instance de tracepoint est une instance d'une telle classe de tracepoint déclarée, avec son propre nom d'événement.

LTTng-UST crée une fonction de sérialisation d'événements par classe de tracepoint. L'utilisation de LTTNG_UST_TRACEPOINT_EVENT() crée une classe de tracepoint par définition de tracepoint, tandis que l'utilisation de LTTNG_UST_TRACEPOINT_EVENT_CLASS() et LTTNG_UST_TRACEPOINT_EVENT_INSTANCE() crée une classe de tracepoint, et une ou plusieurs instances de tracepoint de cette classe. En d'autres termes, de nombreux tracepoints peuvent réutiliser le même code de sérialisation. Réutiliser le même code, lorsque cela est possible, peut réduire la pollution du cache, améliorant ainsi les performances.

La macro LTTNG_UST_TRACEPOINT_EVENT_CLASS() accepte les mêmes paramètres que la macro LTTNG_UST_TRACEPOINT_EVENT(), sauf qu'au lieu d'un nom d'événement, son deuxième paramètre est le *nom de la classe de tracepoint* :

#define LTTNG_UST_TRACEPOINT_PROVIDER mon_fournisseur
/* ... */
LTTNG_UST_TRACEPOINT_EVENT_CLASS(
    /* Nom du fournisseur de la classe de tracepoint */
    mon_fournisseur,
    /* Nom de la classe de tracepoint */
    ma_classe_tracepoint,
    /* Liste des arguments du tracepoint (entrée) */
    LTTNG_UST_TP_ARGS(
        ...
    ),
    /* Liste des champs de l'événement éventuel (sortie) */
    LTTNG_UST_TP_FIELDS(
        ...
    )
)

Une fois la classe de tracepoint définie, vous pouvez créer autant d'instances de tracepoint que nécessaire :

#define LTTNG_UST_TRACEPOINT_PROVIDER natalite
/* ... */
LTTNG_UST_TRACEPOINT_EVENT_INSTANCE(
    /* Nom du fournisseur de la classe de tracepoint */
    mon_fournisseur,
    /* Nom de la classe de tracepoint */
    ma_classe_tracepoint,
    /* Nom du fournisseur local (d'instance) */
    natalite,
    /* Nom du tracepoint/événement */
    mon_tracepoint,
    /* Liste des arguments du tracepoint (entrée) */
    LTTNG_UST_TP_ARGS(
        ...
    )
)

Comme vous pouvez le voir, LTTNG_UST_TRACEPOINT_EVENT_INSTANCE() ne contient pas la macro LTTNG_UST_TP_FIELDS(), car ils sont définis au niveau de LTTNG_UST_TRACEPOINT_EVENT_CLASS().

Notez que la macro LTTNG_UST_TRACEPOINT_EVENT_INSTANCE() nécessite deux noms de fournisseur :

•Le nom du fournisseur de la classe de tracepoint (mon_fournisseur dans l'exemple ci-dessus).

C'est le même que le premier argument de l'expansion LTTNG_UST_TRACEPOINT_EVENT_CLASS() auquel se référer.

•Le nom du fournisseur local, ou d'instance (natalite dans l'exemple ci-dessus).

C'est le nom du fournisseur qui devient la partie préfixe du nom des événements que crée un tel tracepoint.

Les deux noms de fournisseur peuvent être différents si la classe de tracepoint et les macros d'instance de tracepoint se trouvent dans deux unités de traduction différentes.

Voir la section *EXEMPLE* ci-dessous pour un exemple complet.

Utilisation de LTTNG_UST_TRACEPOINT_LOGLEVEL()

Facultativement, un niveau de journal peut être attribué à un tracepoint défini. L'attribution de différents niveaux de gravité aux tracepoints peut être utile : lors du contrôle des sessions de traçage, vous pouvez choisir de n'activer que les événements tombant dans une plage de niveaux de journal spécifiques en utilisant les options --loglevel et --loglevel-only de la commande lttng-enable-event(1).

Les niveaux de journal sont attribués aux tracepoints qui sont déjà définis à l'aide de la macro LTTNG_UST_TRACEPOINT_LOGLEVEL(). Cette dernière doit être utilisée après avoir utilisé LTTNG_UST_TRACEPOINT_EVENT() ou LTTNG_UST_TRACEPOINT_EVENT_INSTANCE() pour un tracepoint donné. La macro LTTNG_UST_TRACEPOINT_LOGLEVEL() est utilisée comme suit :

LTTNG_UST_TRACEPOINT_LOGLEVEL(
    /* Nom du fournisseur de tracepoint */
    mon_fournisseur,
    /* Nom du tracepoint/événement */
    mon_tracepoint,
    /* Niveau de journal */
    LTTNG_UST_TRACEPOINT_LOGLEVEL_INFO
)

Les définitions de niveaux de journal disponibles sont :

LTTNG_UST_TRACEPOINT_LOGLEVEL_EMERG

Le système est inutilisable.

LTTNG_UST_TRACEPOINT_LOGLEVEL_ALERT

Une action doit être entreprise immédiatement.

LTTNG_UST_TRACEPOINT_LOGLEVEL_CRIT

Conditions critiques.

LTTNG_UST_TRACEPOINT_LOGLEVEL_ERR

Conditions d'erreur.

LTTNG_UST_TRACEPOINT_LOGLEVEL_WARNING

Conditions d'avertissement.

LTTNG_UST_TRACEPOINT_LOGLEVEL_NOTICE

Condition normale mais significative.

LTTNG_UST_TRACEPOINT_LOGLEVEL_INFO

Message informatif.

LTTNG_UST_TRACEPOINT_LOGLEVEL_DEBUG_SYSTEM

Informations de débogage avec une portée au niveau du système (ensemble de programmes).

LTTNG_UST_TRACEPOINT_LOGLEVEL_DEBUG_PROGRAM

Informations de débogage avec une portée au niveau du programme (ensemble de processus).

LTTNG_UST_TRACEPOINT_LOGLEVEL_DEBUG_PROCESS

Informations de débogage avec une portée au niveau du processus (ensemble de modules).

LTTNG_UST_TRACEPOINT_LOGLEVEL_DEBUG_MODULE

Informations de débogage avec une portée au niveau du module (exécutable/bibliothèque) (ensemble d'unités).

Instrumenter votre application

Une fois le fournisseur de tracepoint créé (voir la section *Créer un fournisseur de tracepoint* ci-dessus), vous pouvez instrumenter votre application avec les tracepoints définis grâce à la macro lttng_ust_tracepoint() :

#define lttng_ust_tracepoint(nom_prov, nom_t, ...)

Avec :

nom_prov

Nom du fournisseur de tracepoint.

nom_t

Nom du tracepoint/événement.

...

Arguments du tracepoint, le cas échéant.

Assurez-vous d'inclure le fichier d'en-tête du fournisseur de tracepoint partout où vous utilisez lttng_ust_tracepoint() pour ce fournisseur.


Note

Bien que LTTng-UST prenne en charge les duplications de sites d'appel lttng_ust_tracepoint() ayant les mêmes noms de fournisseur et de tracepoint, il est recommandé d'utiliser une paire fournisseur/tracepoint une seule fois dans le code source de l'application pour aider à mapper les événements à leurs sites d'appel lors de l'analyse de la trace.

Parfois, les arguments du tracepoint sont coûteux à calculer (prendre la pile d'appels, par exemple). Pour éviter le calcul lorsque le tracepoint est désactivé, vous pouvez utiliser les macros lttng_ust_tracepoint_enabled() et lttng_ust_do_tracepoint() :

#define lttng_ust_tracepoint_enabled(nom_prov, nom_t)
#define lttng_ust_do_tracepoint(nom_prov, nom_t, ...)

lttng_ust_tracepoint_enabled() renvoie une valeur non nulle si le tracepoint nommé nom_t du fournisseur nommé nom_prov est activé à l'exécution.

lttng_ust_do_tracepoint() est comme lttng_ust_tracepoint(), sauf qu'il ne vérifie pas si le tracepoint est activé. L'utilisation de lttng_ust_tracepoint() avec lttng_ust_tracepoint_enabled() est dangereuse car lttng_ust_tracepoint() contient également la vérification lttng_ust_tracepoint_enabled(), donc une condition de concurrence est possible dans cette situation :

if (lttng_ust_tracepoint_enabled(mon_fournisseur, mon_tracepoint)) {
    truc = preparer_truc();
}
lttng_ust_tracepoint(mon_fournisseur, mon_tracepoint, truc);

Si le tracepoint est activé après la condition, alors truc n'est pas préparé : l'événement émis contiendra soit des données incorrectes, soit l'application entière pourrait planter (erreur de segmentation, par exemple).


Note

Ni lttng_ust_tracepoint_enabled() ni lttng_ust_do_tracepoint() n'ont d'appel STAP_PROBEV(), donc si vous en avez besoin, vous devez l'émettre vous-même.

Liaison statique du fournisseur de points de trace

Avec la méthode de liaison statique, les fournisseurs de points de trace compilés sont copiés dans l'application cible.

Définissez la définition LTTNG_UST_TRACEPOINT_DEFINE sous la définition LTTNG_UST_TRACEPOINT_CREATE_PROBES dans la source du fournisseur de points de trace:

#define LTTNG_UST_TRACEPOINT_CREATE_PROBES
#define LTTNG_UST_TRACEPOINT_DEFINE
#include "tp.h"

Créez le fichier objet du fournisseur de points de trace:

$ cc -c -I. tp.c

Note

Bien qu'une application instrumentée avec des points de trace LTTng-UST puisse être compilée avec un compilateur C++, les sondes de points de trace devraient être compilées avec un compilateur C.

À ce stade, vous *pouvez* archiver ce fichier objet de fournisseur de points de trace, éventuellement avec d'autres fichiers objets de votre application ou avec d'autres fichiers objets de fournisseurs de points de trace, sous forme de bibliothèque statique:

$ ar rc tp.a tp.o

L'utilisation d'une bibliothèque statique présente l'avantage de centraliser les objets des fournisseurs de points de trace afin qu'ils puissent être partagés entre plusieurs applications. De cette façon, lorsque le fournisseur de points de trace est modifié, les modifications du code source n'ont pas à être appliquées à l'arborescence du code source de chaque application. Les applications doivent être relinkées après chaque modification, mais pas autrement recompilées (sauf si l'API du fournisseur de points de trace change).

Ensuite, liez votre application avec ce fichier objet (ou avec la bibliothèque statique qui le contient) et avec liblttng-ust et libdl (libc sur un système BSD):

$ cc -o app tp.o app.o -llttng-ust -ldl

Chargement dynamique du fournisseur de points de trace

La deuxième approche pour empaqueter le fournisseur de points de trace consiste à utiliser le chargeur dynamique: la bibliothèque et ses fonctions membres sont explicitement recherchées, chargées au moment de l'exécution.

Dans ce scénario, le fournisseur de points de trace est compilé en tant qu'objet partagé.

Le processus de création de l'objet partagé du fournisseur de points de trace est à peu près le même que la *méthode de liaison statique*, sauf que:

•Étant donné que le fournisseur de points de trace ne fait pas partie de l'application, LTTNG_UST_TRACEPOINT_DEFINE doit être défini, pour chaque fournisseur de points de trace, dans un fichier source unique de l'*application*.
•LTTNG_UST_TRACEPOINT_PROBE_DYNAMIC_LINKAGE doit être défini à côté de LTTNG_UST_TRACEPOINT_DEFINE.

Concernant LTTNG_UST_TRACEPOINT_DEFINE et LTTNG_UST_TRACEPOINT_PROBE_DYNAMIC_LINKAGE, la pratique recommandée est d'utiliser un fichier source C séparé dans votre application pour les définir, puis d'inclure les fichiers d'en-tête du fournisseur de points de trace par la suite. Par exemple, comme tp-define.c:

#define LTTNG_UST_TRACEPOINT_DEFINE
#define LTTNG_UST_TRACEPOINT_PROBE_DYNAMIC_LINKAGE
#include "tp.h"

Le fichier objet du fournisseur de points de trace utilisé pour créer la bibliothèque partagée est construit comme pour la méthode de liaison statique, mais avec l'option -fpic:

$ cc -c -fpic -I. tp.c

Il est ensuite lié en tant que bibliothèque partagée comme suit:

$ cc -shared -Wl,--no-as-needed -o tp.so tp.o -llttng-ust

Cet objet partagé de fournisseur de points de trace n'est pas lié à l'application utilisateur: il doit être chargé manuellement. C'est pourquoi l'application est construite sans mention de ce fournisseur de points de trace, mais nécessite toujours libdl:

$ cc -o app app.o tp-define.o -ldl

Il existe deux façons de charger dynamiquement l'objet partagé du fournisseur de points de trace:

•Le charger manuellement depuis l'application en utilisant dlopen(3)
•Faire en sorte que le chargeur dynamique le charge avec la variable d'environnement LD_PRELOAD (voir ld.so(8))

Si l'application ne charge pas dynamiquement l'objet partagé du fournisseur de points de trace en utilisant l'une des méthodes ci-dessus, le traçage est désactivé pour cette application, et les événements ne sont pas listés dans la sortie de lttng-list(1).

Notez qu'il n'est pas sûr d'utiliser dlclose(3) sur un objet partagé de fournisseur de points de trace qui est activement utilisé pour le traçage, en raison d'un manque de comptage de références de LTTng-UST vers l'objet partagé.

Par exemple, lier statiquement un fournisseur de points de trace à un objet partagé qui doit être chargé dynamiquement par une application (un plugin, par exemple) n'est pas sûr: l'objet partagé, qui contient le fournisseur de points de trace, pourrait être dynamiquement fermé (dlclose(3)) à tout moment par l'application.

Pour instrumenter un objet partagé, soit:

•Liez statiquement le fournisseur de points de trace à l'application, soit
•Construisez le fournisseur de points de trace en tant qu'objet partagé (en suivant la procédure décrite dans cette section), et préchargez-le lorsque le traçage est nécessaire en utilisant la variable d'environnement LD_PRELOAD.

Utilisation de LTTng-UST avec des démons

Des précautions supplémentaires sont nécessaires lors de l'utilisation de liblttng-ust avec des applications démons qui appellent fork(2), clone(2), ou le rfork(2) de BSD sans un appel système de famille exec(3) qui suit. La bibliothèque liblttng-ust-fork.so doit être préchargée avant de démarrer l'application avec la variable d'environnement LD_PRELOAD (voir ld.so(8)).

Pour utiliser liblttng-ust avec une application démon qui ferme des descripteurs de fichiers qui n'ont pas été ouverts par elle, préchargez la bibliothèque liblttng-ust-fd.so avant de démarrer l'application. Les cas d'utilisation typiques incluent les démons qui ferment tous les descripteurs de fichiers après fork(2), et les applications boguées qui effectuent des «doubles fermetures».

DESCRIPTION

This man page describes how to instrument your C/C++ application code with LTTng-UST (Linux Trace Toolkit next Generation - Userspace Tracing) tracepoints.

LTTng-UST allows you to emit events from your application code. These events can then be captured by the LTTng tracer and saved into a trace file, which can be analyzed later with tools like babeltrace(1).

LTTng-UST tracepoints are defined using a specific C preprocessor macro API. A tracepoint is identified by a provider name and an event name.

The main goal is to provide a way to define and emit events from an application without having to modify the LTTng tracer itself. This means that you can add tracing to your application without needing to recompile LTTng.

The LTTng-UST API is composed of a set of macros that allow you to declare tracepoint providers, declare event structures, and emit events.

Tracepoint provider definition

A tracepoint provider is a logical grouping of tracepoints. It is defined in a header file using the following macros:

#undef LTTNG_UST_TRACEPOINT_PROVIDER
#define LTTNG_UST_TRACEPOINT_PROVIDER provider_name
#undef LTTNG_USTTRACEPOINT_INCLUDE
#define LTTNG_USTTRACEPOINT_INCLUDE "path/to/your/header.h"

provider_name is the name of your tracepoint provider. This name is used to identify the source of the tracepoints.

path/to/your/header.h is the path to the header file that defines your tracepoints. This is necessary for the tracepoint definition macros to work correctly.

The tracepoints themselves are defined using the LTTNG_UST_TRACEPOINT_EVENT macro:

LTTNG_UST_TRACEPOINT_EVENT(
    provider_name,
    event_name,
    LTTNG_UST_TP_ARGS(
        type1, arg1,
        type2, arg2,
        ...
    ),
    LTTNG_UST_TP_FIELDS(
        lttng_ust_field_type(field_name, value)
        ...
    )
)

event_name is the name of the tracepoint event.

LTTNG_UST_TP_ARGS(...) defines the arguments that will be passed to the tracepoint function. Each argument is defined by its type and name.

LTTNG_UST_TP_FIELDS(...) defines the fields that will be recorded in the trace event. Each field is defined by its type, name, and the value to be recorded. The value can be a variable, a literal, or an expression.

The available field types are:

lttng_ust_field_integer()
lttng_ust_field_integer_hex()
lttng_ust_field_integer_binary()
lttng_ust_field_integer_octal()
lttng_ust_field_float()
lttng_ust_field_string()
lttng_ust_field_array()
lttng_ust_field_array_text()
lttng_ust_field_sequence()
lttng_ust_field_sequence_text()
lttng_ust_field_enum()

For more details on the field types and their usage, please refer to the LTTng-UST documentation.

You can also define log levels for your tracepoints:

LTTNG_UST_TRACEPOINT_LOGLEVEL(provider_name, event_name, level)

Where level can be one of:

LTTNG_UST_TRACEPOINT_LOGLEVEL_EMERGENCY
LTTNG_UST_TRACEPOINT_LOGLEVEL_ALERT
LTTNG_UST_TRACEPOINT_LOGLEVEL_CRITICAL
LTTNG_UST_TRACEPOINT_LOGLEVEL_ERROR
LTTNG_UST_TRACEPOINT_LOGLEVEL_WARNING
LTTNG_UST_TRACEPOINT_LOGLEVEL_NOTICE
LTTNG_UST_TRACEPOINT_LOGLEVEL_INFO
LTTNG_UST_TRACEPOINT_LOGLEVEL_DEBUG_SYSTEM
LTTNG_UST_TRACEPOINT_LOGLEVEL_DEBUG_PROGRAM
LTTNG_UST_TRACEPOINT_LOGLEVEL_DEBUG_PROCESS
LTTNG_UST_TRACEPOINT_LOGLEVEL_DEBUG_MODULE
LTTNG_UST_TRACEPOINT_LOGLEVEL_DEBUG_UNIT
LTTNG_UST_TRACEPOINT_LOGLEVEL_DEBUG

Event classes and instances can be used to group events and reuse definitions:

LTTNG_UST_TRACEPOINT_EVENT_CLASS(
    provider_name,
    class_name,
    LTTNG_UST_TP_ARGS(...),
    LTTNG_UST_TP_FIELDS(...)
)
LTTNG_UST_TRACEPOINT_EVENT_INSTANCE(
    provider_name,
    class_name,
    provider_name,
    instance_name,
    LTTNG_UST_TP_ARGS(...)
)

Enums can also be defined:

LTTNG_UST_TRACEPOINT_ENUM(
    provider_name,
    enum_name,
    LTTNG_UST_TP_ENUM_VALUES(
        lttng_ust_field_enum_value("name1", value1)
        lttng_ust_field_enum_value("name2", value2)
        ...
        lttng_ust_field_enum_range("name_range", start, end)
    )
)

Tracepoint provider implementation

To implement the tracepoints defined in the header file, you need to create a source file (e.g., tp.c) that includes the header file and uses the following macros:

#define LTTNG_UST_TRACEPOINT_CREATE_PROBES
#define LTTNG_UST_TRACEPOINT_DEFINE
#include "your_header.h"

LTTNG_UST_TRACEPOINT_CREATE_PROBES is used to create the probe functions for the tracepoints.

LTTNG_UST_TRACEPOINT_DEFINE is used to define the tracepoint event structure.

These macros should be placed in a C file that will be compiled and linked into your application.

Emitting tracepoints from an application

Once the tracepoints are defined and implemented, you can emit them from your application code using the following macro:

lttng_ust_tracepoint(provider_name, event_name, arg1, arg2, ...);

The arguments passed to this macro must match the arguments defined in the tracepoint definition (LTTNG_UST_TP_ARGS).

If you want to emit tracepoints that have been defined as event instances, you can use the same macro:

lttng_ust_tracepoint(provider_name, instance_name, arg1, arg2, ...);

The arguments passed must match the arguments defined for the event class of the instance.

You can also use the tracepoint macros directly if you prefer:

tracepoint_provider_name:event_name(arg1, arg2, ...);

This is equivalent to the lttng_ust_tracepoint() macro.

Linking with liblttng-ust

To use LTTng-UST in your application, you need to link against the liblttng-ust library. This is typically done during the linking stage:

$ cc -o my_app my_app.c -llttng-ust

If you are using tracepoint providers that rely on shared libraries (e.g., dynamic linking), you might also need to link with -ldl.

$ cc -o my_app my_app.c -llttng-ust -ldl

You will also need to include the LTTng-UST header files. This is usually handled automatically by your build system if LTTng-UST is installed correctly. If not, you might need to specify the include path:

$ cc -I/path/to/lttng/include -o my_app my_app.c -L/path/to/lttng/lib -llttng-ust

Static linking: It is also possible to statically link your application with liblttng-ust. This involves using the static library version of liblttng-ust (e.g., liblttng-ust.a) and potentially defining LTTNG_UST_STATIC before including LTTng-UST headers.

$ cc -c my_app.c -DLTTNG_UST_STATIC -I/path/to/lttng/include
$ cc -o my_app my_app.o /path/to/lttng/lib/liblttng-ust.a

Note that static linking of LTTng-UST requires careful management of symbol visibility and potential issues with runtime loading of plugins.

    100, -35, 1, 23, 14, -6, 28, 1001, -3000,

int main(int argc, char* argv[])
{
    FILE *stream;
    struct app_struct app_struct;
    lttng_ust_tracepoint(my_provider, simple_event, argc, argv[0]);
    stream = fopen("/tmp/app.txt", "w");

        fprintf(stderr,
                "Error: Cannot open /tmp/app.txt for writing\n");
        return EXIT_FAILURE;
    }
    if (fprintf(stream, "0123456789") != 10) {
        fclose(stream);
        fprintf(stderr, "Error: Cannot write to /tmp/app.txt\n");
        return EXIT_FAILURE;
    }
    lttng_ust_tracepoint(my_provider, big_event, 35,
                         "hello tracepoint", stream, -3.14,
                         array_of_ints);
    fclose(stream);
    app_struct.b = argc;
    app_struct.c = "[the string]";
    lttng_ust_tracepoint(my_provider, event_instance1, 23,
                         &app_struct);
    app_struct.b = argc * 5;
    app_struct.c = "[other string]";
    lttng_ust_tracepoint(my_provider, event_instance2, 17,
                         &app_struct);
    app_struct.b = 23;
    app_struct.c = "nothing";
    lttng_ust_tracepoint(my_provider, event_instance3, -52,
                         &app_struct);
    return EXIT_SUCCESS;
}

ENVIRONMENT VARIABLES

LTTNG_HOME

Alternative user’s home directory. This variable is useful when the user running the instrumented application has a non-writable home directory. This path is where Unix sockets for communication with the per-user session daemon are located.

LTTNG_UST_ABORT_ON_CRITICAL

If set, abort the instrumented application on a critical error message.

LTTNG_UST_ALLOW_BLOCKING

If set, allow the application to retry event tracing when there’s no space left for the event record in the sub-buffer, therefore effectively blocking the application until space is made available or the configured timeout is reached.

To allow an application to block during tracing, you also need to specify a blocking timeout when you create a channel with the --blocking-timeout option of the lttng-enable-channel(1) command.

This option can be useful in workloads generating very large trace data throughput, where blocking the application is an acceptable trade-off to prevent discarding event records.


Warning
Setting this environment variable may significantly affect application timings.

LTTNG_UST_APP_PATH

Path of the directory where to expect the LTTng session daemon to place the following files to receive instrumented application connection requests:
•The application registration Unix socket.
•The "wait" shared memory files to wake up instrumented applications that are waiting for a session daemon to start.
•The agent port file.

This file contains the TCP port the agents must connect to in order to enable LTTng tracing.

This directory must exist when you start the application for LTTng tracing to be enabled.

When LTTNG_UST_APP_PATH is set, liblttng-ust:

•Only considers this path to connect to a session daemon.
•Won’t connect to root and/or user session daemons as usual.

See the corresponding LTTNG_UST_CTL_PATH environment variable of lttng-sessiond(8).

LTTNG_UST_CLOCK_PLUGIN

Path to the shared object which acts as the clock override plugin. An example of such a plugin can be found in the LTTng-UST documentation under examples/clock-override https://github.com/lttng/lttng-ust/tree/stable-2.14/doc/examples/clock-override.

DESCRIPTION

The LTTng-UST (Lightweight Tracing Next Generation - User Space Tracer) library provides a flexible and high-performance tracing framework for user-space applications.

This library exposes a C API to allow instrumenting applications with tracepoints, creating tracing sessions, managing channels, and adding contextual information to trace data.

The main components of LTTng-UST are:

  • Tracepoints: User-defined events that can be emitted from an application.
  • Channels: Buffers that store trace data.
  • Sessions: A collection of channels that form a complete tracing context.
  • Contexts: Additional information (e.g., process ID, thread ID, CPU ID) that can be associated with trace events.

The LTTng-UST library also supports dynamic loading of tracing runtime libraries (e.g., for runtime instrumentation) and provides hooks for dynamic probes.

EXAMPLE

This is a simple example of using LTTng-UST to trace a custom event:

tracepoint.h:

#undef LTTNG_UST_TRACEPOINT_EVENT
#define LTTNG_UST_TRACEPOINT_EVENT(my_event)

#undef LTTNG_UST_TRACEPOINT_BINDINGS
#define LTTNG_UST_TRACEPOINT_BINDINGS(my_event) \
    LTTNG_UST_TRACEPOINT_BIND_FIELD(int, my_data)

#include <lttng/tracepoint.h>

main.c:

#include <stdio.h>
#include "tracepoint.h"

int main(int argc, char **argv)
{
    /* Initialize LTTng-UST */
    lttng_ust_tracef("Initializing LTTng-UST...");

    /* Create a session named "my_session" */
    if (lttng_ust_session_create("my_session", NULL) == NULL) {
        perror("Failed to create LTTng session");
        return 1;
    }

    /* Enable the "my_event" tracepoint */
    lttng_ust_probe_enable(my_event, NULL);

    /* Start the session */
    lttng_ust_session_start(NULL);

    /* Emit the tracepoint */
    my_event(42);

    /* Stop the session */
    lttng_ust_session_stop(NULL);

    /* Destroy the session */
    lttng_ust_session_destroy(NULL);

    lttng_ust_tracef("LTTng-UST tracing complete.");

    return 0;
}

ENVIRONMENT VARIABLES

LTTNG_UST_DEBUG

If set, enable the debug and error output of liblttng-ust.

LTTNG_UST_GETCPU_PLUGIN

Path to the shared object which acts as the getcpu() override plugin. An example of such a plugin can be found in the LTTng-UST documentation under examples/getcpu-override https://github.com/lttng/lttng-ust/tree/stable-2.14/doc/examples/getcpu-override.

LTTNG_UST_MAP_POPULATE_POLICY

If set, override the policy used to populate shared memory pages within the application.

The possible values are:

none (default)

Do not pre-populate any page: take minor faults on first access while tracing.

cpu_possible

Pre-populate pages for all possible CPUs in the system, as shown in /sys/devices/system/cpu/possible.

LTTNG_UST_REGISTER_TIMEOUT

Waiting time for the registration done session daemon command before proceeding to execute the main program (milliseconds).

The value 0 means do not wait. The value -1 means wait forever. Setting this environment variable to 0 is recommended for applications with time constraints on the process startup time.

Default: 3000.

LTTNG_UST_WITHOUT_BADDR_STATEDUMP

If set, prevents liblttng-ust from performing a base address state dump (see the LTTng-UST state dump section above).

LTTNG_UST_WITHOUT_PROCNAME_STATEDUMP

If set, prevents liblttng-ust from performing a procname state dump (see the LTTng-UST state dump section above).
