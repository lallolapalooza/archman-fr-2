DESCRIPTION

Le Linux Trace Toolkit: next generation http://lttng.org/ est un ensemble de logiciels open source utilisé pour le traçage corrélé du noyau Linux, des applications utilisateur et des bibliothèques utilisateur.

LTTng-UST est le composant de traçage utilisateur du projet LTTNG. C'est un portage en espace utilisateur des capacités de traçage à faible surcharge du traceur noyau LTTng. La bibliothèque liblttng-ust est utilisée pour tracer les applications et bibliothèques utilisateur.


Note

Cette page de manuel concerne la bibliothèque liblttng-ust. Le projet LTTng-UST fournit également des paquets Java et Python pour tracer les applications écrites dans ces langages. La manière d'instrumenter et de tracer les applications Java et Python est documentée dans la documentation en ligne de LTTng http://lttng.org/docs/.

Il y a trois façons d'utiliser liblttng-ust :

•Utiliser l'API lttng_ust_tracef(3), qui est similaire à printf(3).
•Utiliser l'API lttng_ust_tracelog(3), qui est lttng_ust_tracef(3) avec un paramètre de niveau de journalisation.
•Définir vos propres points de trace. Voir la section Création d'un fournisseur de point de trace ci-dessous.

Compatibilité avec les API précédentes

Depuis LTTng-UST 2.13, la définition LTTNG_UST_COMPAT_API_VERSION contrôle quelles API LTTng-UST sont disponibles (compilées) :

Non définie

Toutes les API sont disponibles.

N (0 ou entier positif)

L'API version N, et toutes les API existantes suivantes, sont disponibles. Les API précédentes ne sont pas disponibles (non compilées).

Le tableau suivant montre la correspondance entre les versions de LTTng-UST (jusqu'à LTTng-UST 2.14.0) et les versions d'API disponibles :

Version LTTng-UST Versions d'API disponibles
2.0 à 2.12 0
2.13 0 et 1

Cette page de manuel ne documente que la version 1 de l'API.

Si vous souhaitez avoir accès à la version 0 de l'API (par exemple, les macros tracepoint(), ctf_integer() et TRACEPOINT_EVENT()), alors ne définissez pas LTTNG_UST_COMPAT_API_VERSION, ou définissez-la à 0 avant d'inclure un quelconque en-tête LTTng-UST.

NAME

lttng-ust - LTTng tracepoint usage

DESCRIPTION

This document describes how to use the LTTng-UST (User Space Tracer) tracepoint API. It is a simplified C API that allows applications to emit trace events. LTTng-UST tracepoints can be statically or dynamically linked to your application. Using tracepoints has zero runtime cost when disabled.

A tracepoint provider is a compiled object containing the event probes corresponding to your custom tracepoint definitions. A tracepoint provider contains the code to get the size of an event and to serialize it, amongst other things.

To create a tracepoint provider, start with the following tracepoint provider header template:

#undef LTTNG_UST_TRACEPOINT_PROVIDER
#define LTTNG_UST_TRACEPOINT_PROVIDER my_provider
#undef LTTNG_UST_TRACEPOINT_INCLUDE
#define LTTNG_UST_TRACEPOINT_INCLUDE "./tp.h"
#if !defined(_TP_H) || \
    defined(LTTNG_UST_TRACEPOINT_HEADER_MULTI_READ)
#define _TP_H
#include <lttng/tracepoint.h>
/*
 * LTTNG_UST_TRACEPOINT_EVENT(), LTTNG_UST_TRACEPOINT_EVENT_CLASS(),
 * LTTNG_UST_TRACEPOINT_EVENT_INSTANCE(),
 * LTTNG_UST_TRACEPOINT_LOGLEVEL(), and `LTTNG_UST_TRACEPOINT_ENUM()`
 * are used here.
 */
#endif /* _TP_H */
#include <lttng/tracepoint-event.h>

In this template, the tracepoint provider is named my_provider (LTTNG_UST_TRACEPOINT_PROVIDER definition). The file needs to bear the name of the LTTNG_UST_TRACEPOINT_INCLUDE definition (tp.h in this case). Between #include <lttng/tracepoint.h> and #endif go the invocations of the LTTNG_UST_TRACEPOINT_EVENT(), LTTNG_UST_TRACEPOINT_EVENT_CLASS(), LTTNG_UST_TRACEPOINT_EVENT_INSTANCE(), LTTNG_UST_TRACEPOINT_LOGLEVEL(), and LTTNG_UST_TRACEPOINT_ENUM() macros.


Note

You can avoid writing the prologue and epilogue boilerplate in the template file above by using the lttng-gen-tp(1) tool shipped with LTTng-UST.

The tracepoint provider header file needs to be included in a source file which looks like this:

#define LTTNG_UST_TRACEPOINT_CREATE_PROBES
#include "tp.h"

Together, those two files (let’s call them tp.h and tp.c) form the tracepoint provider sources, ready to be compiled.

You can create multiple tracepoint providers to be used in a single application, but each one must have its own header file.

The LTTNG_UST_TRACEPOINT_EVENT() usage section below shows how to use the LTTNG_UST_TRACEPOINT_EVENT() macro to define the actual tracepoints in the tracepoint provider header file.

See the EXAMPLE section below for a complete example.

LTTNG_UST_TRACEPOINT_EVENT() usage

The LTTNG_UST_TRACEPOINT_EVENT() macro is used in a template provider header file (see the Creating a tracepoint provider section above) to define LTTng-UST tracepoints.

The LTTNG_UST_TRACEPOINT_EVENT() usage template is as follows:

LTTNG_UST_TRACEPOINT_EVENT(
    /* Tracepoint provider name */
    my_provider,
    /* Tracepoint/event name */
    my_tracepoint,
    /* List of tracepoint arguments (input) */
    LTTNG_UST_TP_ARGS(
        ...
    ),
    /* List of fields of eventual event (output) */
    LTTNG_UST_TP_FIELDS(
        ...
    )
)

The LTTNG_UST_TP_ARGS() macro contains the input arguments of the tracepoint. Those arguments can be used in the argument expressions of the output fields defined in LTTNG_UST_TP_FIELDS().

The format of the LTTNG_UST_TP_ARGS() parameters is: C type, then argument name; repeat as needed, up to ten times. For example:

LTTNG_UST_TP_ARGS(
    int, my_int,
    const char *, my_string,
    FILE *, my_file,
    double, my_float,
    struct my_data *, my_data
)

The LTTNG_UST_TP_FIELDS() macro contains the output fields of the tracepoint, that is, the actual data that can be recorded in the payload of an event emitted by this tracepoint.

The LTTNG_UST_TP_FIELDS() macro contains a list of lttng_ust_field_*() macros NOT separated by commas. The available macros are documented in the Available lttng_ust_field_*() field type macros section below.

Available field macros

This section documents the available lttng_ust_field_*() macros that can be inserted in the LTTNG_UST_TP_FIELDS() macro of the LTTNG_UST_TRACEPOINT_EVENT() macro.

lttng_ust_field_integer_nowrite(int_type, field_name, expr)

Integer in network byte order, displayed in base 16:

lttng_ust_field_array_nowrite(int_type, field_name, expr, count)

                                     len_type, len_expr)

                                             expr, len_type,

lttng_ust_field_sequence_text(char, field_name, expr, len_type,
                              len_expr)
lttng_ust_field_sequence_text_nowrite(char, field_name, expr,
                                      len_type, len_expr)

Enumeration. The enumeration field must be defined before using this macro with the LTTNG_UST_TRACEPOINT_ENUM() macro. See the LTTNG_UST_TRACEPOINT_ENUM() usage section for more information.

lttng_ust_field_enum(prov_name, enum_name, int_type, field_name,
                     expr)
lttng_ust_field_enum_nowrite(prov_name, enum_name, int_type,
                             field_name, expr)

The parameters are:

count

Number of elements in array/sequence. This must be known at compile time.

enum_name

Name of an enumeration field previously defined with the LTTNG_UST_TRACEPOINT_ENUM() macro. See the LTTNG_UST_TRACEPOINT_ENUM() usage section for more information.

expr

C expression resulting in the field value. This expression can use one or more arguments passed to the tracepoint. The arguments of a given tracepoint are defined in the LTTNG_UST_TP_ARGS() macro (see the Creating a tracepoint provider section above).

field_name

Event field name (C identifier syntax, NOT a literal string).

float_type

Float C type (float or double). The size of this type determines the size of the floating point number field.

int_type

Integer C type. The size of this type determines the size of the integer/enumeration field.

len_expr

C expression resulting in the sequence length. This expression can use one or more arguments passed to the tracepoint.

len_type

Unsigned integer C type of sequence length.

prov_name

Tracepoint provider name. This must be the same as the tracepoint provider name used in a previous field definition.

Utilisation de LTTNG_UST_TRACEPOINT_ENUM()

Un champ d'énumération est une liste de correspondances entre des entiers, ou une plage d'entiers, et des chaînes de caractères (parfois appelées étiquettes ou énumérateurs). Les champs d'énumération peuvent être utilisés pour avoir une trace plus compacte lorsque les valeurs possibles pour un champ sont limitées.

Un champ d'énumération est défini avec la macro LTTNG_UST_TRACEPOINT_ENUM() :

LTTNG_UST_TRACEPOINT_ENUM(
    /* Nom du fournisseur de tracepoint */
    my_provider,
    /* Nom de l'énumération (unique dans tout le fournisseur de tracepoint) */
    my_enum,
    /* Mappages d'énumération */
    LTTNG_UST_TP_ENUM_VALUES(
        ...
    )
)

LTTNG_UST_TP_ENUM_VALUES() contient une liste de mappages d'énumération, NON séparés par des virgules. Deux macros peuvent être utilisées dans LTTNG_UST_TP_ENUM_VALUES() : lttng_ust_field_enum_value() et lttng_ust_field_enum_range().

lttng_ust_field_enum_value() est un mappage de valeur unique :

lttng_ust_field_enum_value(étiquette, valeur)

Cette macro associe la chaîne étiquette donnée à la valeur valeur.

lttng_ust_field_enum_range() est un mappage de plage :

lttng_ust_field_enum_range(étiquette, début, fin)

Cette macro associe la chaîne étiquette donnée à la plage d'entiers de début à fin, inclusivement. Les mappages de plage peuvent se chevaucher, mais le comportement est défini par l'implémentation : chaque lecteur de trace gère les plages qui se chevauchent comme il le souhaite.

Voir la section EXEMPLE ci-dessous pour un exemple complet.

Utilisation de LTTNG_UST_TRACEPOINT_EVENT_CLASS()

Une classe de tracepoint est une classe de tracepoints partageant les mêmes types et noms de champs. Une instance de tracepoint est une instance d'une telle classe de tracepoint déclarée, avec son propre nom d'événement.

LTTng-UST crée une fonction de sérialisation d'événements par classe de tracepoint. L'utilisation de LTTNG_UST_TRACEPOINT_EVENT() crée une classe de tracepoint par définition de tracepoint, tandis que l'utilisation de LTTNG_UST_TRACEPOINT_EVENT_CLASS() et LTTNG_UST_TRACEPOINT_EVENT_INSTANCE() crée une classe de tracepoint, et une ou plusieurs instances de tracepoint de cette classe. Autrement dit, de nombreux tracepoints peuvent réutiliser le même code de sérialisation. Réutiliser le même code, lorsque c'est possible, peut réduire la pollution du cache, et donc améliorer les performances.

La macro LTTNG_UST_TRACEPOINT_EVENT_CLASS() accepte les mêmes paramètres que la macro LTTNG_UST_TRACEPOINT_EVENT(), à la différence qu'au lieu d'un nom d'événement, son deuxième paramètre est le nom de la classe de tracepoint :

#define LTTNG_UST_TRACEPOINT_PROVIDER my_provider
/* ... */
LTTNG_UST_TRACEPOINT_EVENT_CLASS(
    /* Nom du fournisseur de la classe de tracepoint */
    my_provider,
    /* Nom de la classe de tracepoint */
    my_tracepoint_class,
    /* Liste des arguments du tracepoint (entrée) */
    LTTNG_UST_TP_ARGS(
        ...
    ),
    /* Liste des champs de l'événement éventuel (sortie) */
    LTTNG_UST_TP_FIELDS(
        ...
    )
)

Une fois la classe de tracepoint définie, vous pouvez créer autant d'instances de tracepoint que nécessaire :

#define LTTNG_UST_TRACEPOINT_PROVIDER natality
/* ... */
LTTNG_UST_TRACEPOINT_EVENT_INSTANCE(
    /* Nom du fournisseur de la classe de tracepoint */
    my_provider,
    /* Nom de la classe de tracepoint */
    my_tracepoint_class,
    /* Nom du fournisseur local (instance) */
    natality,
    /* Nom du tracepoint/événement */
    my_tracepoint,
    /* Liste des arguments du tracepoint (entrée) */
    LTTNG_UST_TP_ARGS(
        ...
    )
)

Comme vous pouvez le voir, LTTNG_UST_TRACEPOINT_EVENT_INSTANCE() ne contient pas la macro LTTNG_UST_TP_FIELDS(), car ils sont définis au niveau de la macro LTTNG_UST_TRACEPOINT_EVENT_CLASS().

Notez que la macro LTTNG_UST_TRACEPOINT_EVENT_INSTANCE() nécessite deux noms de fournisseur :

•Le nom du fournisseur de la classe de tracepoint (my_provider dans l'exemple ci-dessus).

C'est le même que le premier argument de l'expansion LTTNG_UST_TRACEPOINT_EVENT_CLASS() pour y faire référence.

•Le nom du fournisseur local, ou d'instance (natality dans l'exemple ci-dessus).

C'est le nom du fournisseur qui devient la partie préfixe du nom des événements créés par un tel tracepoint.

Les deux noms de fournisseur peuvent être différents si la classe de tracepoint et les macros d'instance de tracepoint se trouvent dans deux unités de traduction distinctes.

Voir la section EXEMPLE ci-dessous pour un exemple complet.

Utilisation de LTTNG_UST_TRACEPOINT_LOGLEVEL()

Optionnellement, un niveau de journal peut être attribué à un tracepoint défini. Attribuer différents niveaux de gravité aux tracepoints peut être utile : lors du contrôle des sessions de traçage, vous pouvez choisir de n'activer que les événements relevant d'une plage de niveaux de journal spécifique en utilisant les options --loglevel et --loglevel-only de la commande lttng-enable-event(1).

Les niveaux de journal sont attribués aux tracepoints déjà définis à l'aide de la macro LTTNG_UST_TRACEPOINT_LOGLEVEL(). Cette dernière doit être utilisée après avoir utilisé LTTNG_UST_TRACEPOINT_EVENT() ou LTTNG_UST_TRACEPOINT_EVENT_INSTANCE() pour un tracepoint donné. La macro LTTNG_UST_TRACEPOINT_LOGLEVEL() est utilisée comme suit :

LTTNG_UST_TRACEPOINT_LOGLEVEL(
    /* Nom du fournisseur de tracepoint */
    my_provider,
    /* Nom du tracepoint/événement */
    my_tracepoint,
    /* Niveau de journal */
    LTTNG_UST_TRACEPOINT_LOGLEVEL_INFO
)

Les définitions de niveaux de journal disponibles sont :

LTTNG_UST_TRACEPOINT_LOGLEVEL_EMERG

Le système est inutilisable.

LTTNG_UST_TRACEPOINT_LOGLEVEL_ALERT

Une action doit être entreprise immédiatement.

LTTNG_UST_TRACEPOINT_LOGLEVEL_CRIT

Conditions critiques.

LTTNG_UST_TRACEPOINT_LOGLEVEL_ERR

Conditions d'erreur.

LTTNG_UST_TRACEPOINT_LOGLEVEL_WARNING

Conditions d'avertissement.

LTTNG_UST_TRACEPOINT_LOGLEVEL_NOTICE

Condition normale, mais significative.

LTTNG_UST_TRACEPOINT_LOGLEVEL_INFO

Message informatif.

LTTNG_UST_TRACEPOINT_LOGLEVEL_DEBUG_SYSTEM

Informations de débogage avec une portée au niveau du système (ensemble de programmes).

LTTNG_UST_TRACEPOINT_LOGLEVEL_DEBUG_PROGRAM

Informations de débogage avec une portée au niveau du programme (ensemble de processus).

LTTNG_UST_TRACEPOINT_LOGLEVEL_DEBUG_PROCESS

Informations de débogage avec une portée au niveau du processus (ensemble de modules).

LTTNG_UST_TRACEPOINT_LOGLEVEL_DEBUG_MODULE

Informations de débogage avec une portée au niveau du module (exécutable/bibliothèque) (ensemble d'unités).

LTTNG_UST_TRACEPOINT_LOGLEVEL_DEBUG_UNIT

Informations de débogage avec une portée au niveau de l'unité de compilation (ensemble de fonctions).

LTTNG_UST_TRACEPOINT_LOGLEVEL_DEBUG_FUNCTION

Informations de débogage avec une portée au niveau de la fonction.

LTTNG_UST_TRACEPOINT_LOGLEVEL_DEBUG_LINE

Informations de débogage avec une portée au niveau de la ligne (niveau de journal par défaut).

LTTNG_UST_TRACEPOINT_LOGLEVEL_DEBUG

Instrumenter votre application

Une fois le fournisseur de tracepoint créé (voir la section Création d'un fournisseur de tracepoint ci-dessus), vous pouvez instrumenter votre application avec les tracepoints définis grâce à la macro lttng_ust_tracepoint() :

#define lttng_ust_tracepoint(nom_prov, nom_t, ...)

Avec :

nom_prov

Nom du fournisseur de tracepoint.

nom_t

Nom du tracepoint/événement.

...

Arguments du tracepoint, le cas échéant.

Assurez-vous d'inclure le fichier d'en-tête du fournisseur de tracepoint partout où vous utilisez lttng_ust_tracepoint() pour ce fournisseur.


Note

Bien que LTTng-UST prenne en charge les duplications d'appels lttng_ust_tracepoint() ayant les mêmes noms de fournisseur et de tracepoint, il est recommandé d'utiliser une paire nom de fournisseur/nom de tracepoint une seule fois dans le code source de l'application pour aider à mapper les événements à leurs sites d'appel lors de l'analyse de la trace.

Parfois, les arguments du tracepoint sont coûteux à calculer (par exemple, prendre la pile d'appels). Pour éviter le calcul lorsque le tracepoint est désactivé, vous pouvez utiliser les macros lttng_ust_tracepoint_enabled() et lttng_ust_do_tracepoint() :

#define lttng_ust_tracepoint_enabled(nom_prov, nom_t)
#define lttng_ust_do_tracepoint(nom_prov, nom_t, ...)

lttng_ust_tracepoint_enabled() renvoie une valeur non nulle si le tracepoint nommé nom_t du fournisseur nommé nom_prov est activé à l'exécution.

lttng_ust_do_tracepoint() est similaire à lttng_ust_tracepoint(), à la différence qu'il ne vérifie pas si le tracepoint est activé. Utiliser lttng_ust_tracepoint() avec lttng_ust_tracepoint_enabled() est dangereux car lttng_ust_tracepoint() contient également la vérification lttng_ust_tracepoint_enabled(), donc une condition de concurrence est possible dans cette situation :

if (lttng_ust_tracepoint_enabled(my_provider, my_tracepoint)) {
    stuff = prepare_stuff();
}
lttng_ust_tracepoint(my_provider, my_tracepoint, stuff);

Si le tracepoint est activé après la condition, alors stuff n'est pas préparé : l'événement émis contiendra soit des données incorrectes, soit l'application entière pourrait planter (par exemple, une erreur de segmentation).


Note

Ni lttng_ust_tracepoint_enabled() ni lttng_ust_do_tracepoint() n'ont d'appel STAP_PROBEV(), donc si vous en avez besoin, vous devriez l'émettre vous-même.

_C/C++_constructeurs_et_destructeurs'>Traçage des constructeurs et destructeurs C/C++

Si l'une des conditions suivantes est vraie :

•Vous compilez votre application C++ avec GCC ≤ 4.8.
•Vous compilez votre application C/C++ avec un compilateur C++ et définissez LTTNG_UST_ALLOCATE_COMPOUND_LITERAL_ON_HEAP.

Alors LTTng ne tracera pas :

•Les constructeurs et destructeurs C de l'application elle-même ou des archives liées statiquement.
•Certains constructeurs et destructeurs C++ de l'application elle-même ou des archives liées statiquement.

Dans ce cas, les constructeurs et destructeurs C++ exacts qui ne seront pas tracés dépendent de l'ordre d'initialisation au sein de chaque unité de traduction et à travers le programme entier lorsque toutes les unités de traduction sont liées ensemble.

Liaison statique du fournisseur de points de trace

Avec la méthode de liaison statique, les fournisseurs de points de trace compilés sont copiés dans l'application cible.

Définissez la définition LTTNG_UST_TRACEPOINT_DEFINE en dessous de la définition LTTNG_UST_TRACEPOINT_CREATE_PROBES dans la source du fournisseur de points de trace :

#define LTTNG_UST_TRACEPOINT_CREATE_PROBES
#define LTTNG_UST_TRACEPOINT_DEFINE
#include "tp.h"

Créez le fichier objet du fournisseur de points de trace :

$ cc -c -I. tp.c

Note

Bien qu'une application instrumentée avec des points de trace LTTng-UST puisse être compilée avec un compilateur C++, les sondes de points de trace doivent être compilées avec un compilateur C.

À ce stade, vous *pouvez* archiver ce fichier objet du fournisseur de points de trace, éventuellement avec d'autres fichiers objets de votre application ou avec d'autres fichiers objets de fournisseurs de points de trace, en tant que bibliothèque statique :

$ ar rc tp.a tp.o

L'utilisation d'une bibliothèque statique présente l'avantage de centraliser les objets des fournisseurs de points de trace afin qu'ils puissent être partagés entre plusieurs applications. De cette façon, lorsque le fournisseur de points de trace est modifié, les changements de code source n'ont pas à être patchés dans l'arborescence du code source de chaque application. Les applications doivent être relinkées après chaque changement, mais n'ont pas besoin d'être recompilées autrement (sauf si l'API du fournisseur de points de trace change).

Ensuite, liez votre application avec ce fichier objet (ou avec la bibliothèque statique qui le contient) et avec liblttng-ust et libdl (libc sur un système BSD) :

$ cc -o app tp.o app.o -llttng-ust -ldl

Chargement dynamique du fournisseur de points de trace

La deuxième approche pour empaqueter le fournisseur de points de trace est d'utiliser le chargeur dynamique : la bibliothèque et ses fonctions membres sont explicitement recherchées, chargées au moment de l'exécution.

Dans ce scénario, le fournisseur de points de trace est compilé en objet partagé.

Le processus de création de l'objet partagé du fournisseur de points de trace est à peu près le même que la *méthode de liaison statique*, sauf que :

•Étant donné que le fournisseur de points de trace ne fait pas partie de l'application, LTTNG_UST_TRACEPOINT_DEFINE doit être défini, pour chaque fournisseur de points de trace, dans exactement un fichier source de *l'application*.
•LTTNG_UST_TRACEPOINT_PROBE_DYNAMIC_LINKAGE doit être défini à côté de LTTNG_UST_TRACEPOINT_DEFINE.

Concernant LTTNG_UST_TRACEPOINT_DEFINE et LTTNG_UST_TRACEPOINT_PROBE_DYNAMIC_LINKAGE, la pratique recommandée est d'utiliser un fichier source C séparé dans votre application pour les définir, puis d'inclure les fichiers d'en-tête du fournisseur de points de trace par la suite. Par exemple, comme tp-define.c :

#define LTTNG_UST_TRACEPOINT_DEFINE
#define LTTNG_UST_TRACEPOINT_PROBE_DYNAMIC_LINKAGE
#include "tp.h"

Le fichier objet du fournisseur de points de trace utilisé pour créer la bibliothèque partagée est construit comme avec la méthode de liaison statique, mais avec l'option -fpic :

$ cc -c -fpic -I. tp.c

Il est ensuite lié en tant que bibliothèque partagée comme ceci :

$ cc -shared -Wl,--no-as-needed -o tp.so tp.o -llttng-ust

Cet objet partagé de fournisseur de points de trace n'est pas lié à l'application utilisateur : il doit être chargé manuellement. C'est pourquoi l'application est construite sans mention de ce fournisseur de points de trace, mais nécessite toujours libdl :

$ cc -o app app.o tp-define.o -ldl

Il existe deux façons de charger dynamiquement l'objet partagé du fournisseur de points de trace :

•Le charger manuellement depuis l'application en utilisant dlopen(3).
•Faire charger l'objet partagé par le chargeur dynamique avec la variable d'environnement LD_PRELOAD (voir ld.so(8)).

Si l'application ne charge pas dynamiquement l'objet partagé du fournisseur de points de trace en utilisant l'une des méthodes ci-dessus, le traçage est désactivé pour cette application, et les événements ne sont pas listés dans la sortie de lttng-list(1).

Notez qu'il n'est pas sûr d'utiliser dlclose(3) sur un objet partagé de fournisseur de points de trace qui est activement utilisé pour le traçage, en raison d'un manque de comptage de références de LTTng-UST vers l'objet partagé.

Par exemple, lier statiquement un fournisseur de points de trace à un objet partagé qui doit être chargé dynamiquement par une application (un plugin, par exemple) n'est pas sûr : l'objet partagé, qui contient le fournisseur de points de trace, pourrait être fermé dynamiquement (dlclose(3)) à tout moment par l'application.

Pour instrumenter un objet partagé, soit :

•Liez statiquement le fournisseur de points de trace à l'application, soit
•Construisez le fournisseur de points de trace comme objet partagé (en suivant la procédure décrite dans cette section), et chargezle au préalable lorsque le traçage est nécessaire en utilisant la variable d'environnement LD_PRELOAD.

Utilisation de LTTng-UST avec les démons

Des précautions supplémentaires sont nécessaires lors de l'utilisation de liblttng-ust avec des applications démons qui appellent fork(2), clone(2), ou le rfork(2) de BSD sans appel système de la famille exec(3) qui suit. La bibliothèque liblttng-ust-fork.so doit être chargée au préalable avant de lancer l'application avec la variable d'environnement LD_PRELOAD (voir ld.so(8)).

Pour utiliser liblttng-ust avec une application démon qui ferme les descripteurs de fichiers qui n'ont pas été ouverts par elle, chargez au préalable la bibliothèque liblttng-ust-fd.so avant de démarrer l'application. Les cas d'utilisation typiques incluent les démons qui ferment tous les descripteurs de fichiers après fork(2), et les applications buggées qui font des « doubles fermetures ».

Détecter si LTTng-UST est chargé

Pour détecter si liblttng-ust est chargé depuis une application :

1.Définir le symbole faible lttng_ust_loaded globalement : 
int lttng_ust_loaded __attribute__((weak));

Ce symbole faible est défini par le constructeur de liblttng-ust.

2.Tester lttng_ust_loaded si nécessaire : 
/* ... */
if (lttng_ust_loaded) {
    /* LTTng-UST est chargé */
} else {
    /* LTTng-UST N'est PAS chargé */
}
/* ... */

static int array_of_ints[] = {
    100, -35, 1, 23, 14, -6, 28, 1001, -3000,
};
int main(int argc, char* argv[])
{
    FILE *stream;
    struct app_struct app_struct;
    lttng_ust_tracepoint(my_provider, simple_event, argc, argv[0]);
    stream = fopen("/tmp/app.txt", "w");
    if (!stream) {
        fprintf(stderr,
                "Error: Cannot open /tmp/app.txt for writing\n");
        return EXIT_FAILURE;
    }
    if (fprintf(stream, "0123456789") != 10) {
        fclose(stream);
        fprintf(stderr, "Error: Cannot write to /tmp/app.txt\n");
        return EXIT_FAILURE;
    }
    lttng_ust_tracepoint(my_provider, big_event, 35,
                         "hello tracepoint", stream, -3.14,
                         array_of_ints);
    fclose(stream);
    app_struct.b = argc;
    app_struct.c = "[the string]";
    lttng_ust_tracepoint(my_provider, event_instance1, 23,
                         &app_struct);
    app_struct.b = argc * 5;
    app_struct.c = "[other string]";
    lttng_ust_tracepoint(my_provider, event_instance2, 17,
                         &app_struct);
    app_struct.b = 23;
    app_struct.c = "nothing";
    lttng_ust_tracepoint(my_provider, event_instance3, -52,
                         &app_struct);
    return EXIT_SUCCESS;
}

VARIABLES ENVIRONNEMENTALES

LTTNG_HOME

Répertoire personnel alternatif de l'utilisateur. Cette variable est utile lorsque l'utilisateur exécutant l'application instrumentée a un répertoire personnel non accessible en écriture. Ce chemin est l'endroit où se trouvent les sockets Unix pour la communication avec le démon de session par utilisateur.

LTTNG_UST_ABORT_ON_CRITICAL

Si défini, abandonne l'application instrumentée en cas de message d'erreur critique.

LTTNG_UST_ALLOW_BLOCKING

Si défini, permet à l'application de réessayer le traçage d'événements lorsqu'il n'y a plus d'espace pour l'enregistrement d'événement dans le sous-buffer, bloquant ainsi effectivement l'application jusqu'à ce que de l'espace soit disponible ou que le délai d'attente configuré soit atteint.

Pour permettre à une application de se bloquer pendant le traçage, vous devez également spécifier un délai d'attente de blocage lorsque vous créez un canal avec l'option --blocking-timeout de la commande lttng-enable-channel(1).

Cette option peut être utile dans les charges de travail générant un débit de données de trace très élevé, où le blocage de l'application est un compromis acceptable pour éviter de perdre des enregistrements d'événements.


Avertissement
Définir cette variable d'environnement peut affecter considérablement les timings de l'application.

LTTNG_UST_APP_PATH

Chemin du répertoire où le démon de session LTTng est censé placer les fichiers suivants pour recevoir les requêtes de connexion des applications instrumentées :
•Le socket Unix d'enregistrement de l'application.
•Les fichiers de mémoire partagée "wait" pour réveiller les applications instrumentées qui attendent le démarrage d'un démon de session.
•Le fichier du port de l'agent.

Ce fichier contient le port TCP auquel les agents doivent se connecter pour activer le traçage LTTng.

Ce répertoire doit exister lorsque vous démarrez l'application pour que le traçage LTTng soit activé.

Lorsque LTTNG_UST_APP_PATH est défini, liblttng-ust :

•Ne considère que ce chemin pour se connecter à un démon de session.
•Ne se connectera pas aux démons de session root et/ou utilisateur comme d'habitude.

Voir la variable d'environnement correspondante LTTNG_UST_CTL_PATH de lttng-sessiond(8).

LTTNG_UST_CLOCK_PLUGIN

Chemin de l'objet partagé agissant comme plugin de remplacement d'horloge. Un exemple d'un tel plugin se trouve dans la documentation LTTng-UST sous examples/clock-override https://github.com/lttng/lttng-ust/tree/stable-2.14/doc/examples/clock-override.v>

LTTNG_UST_DEBUG

Si défini, active la sortie de débogage et d'erreur de liblttng-ust.

LTTNG_UST_GETCPU_PLUGIN

Chemin vers l'objet partagé qui agit comme plugin de remplacement de getcpu(). Un exemple de tel plugin se trouve dans la documentation LTTng-UST sous examples/getcpu-override https://github.com/lttng/lttng-ust/tree/stable-2.14/doc/examples/getcpu-override.

LTTNG_UST_MAP_POPULATE_POLICY

Si défini, remplace la politique utilisée pour remplir les pages de mémoire partagée au sein de l'application.

Les valeurs possibles sont :

none (par défaut)

Ne pré-remplit aucune page : prend des fautes mineures à la première accès lors du traçage.

cpu_possible

Pré-remplit les pages pour tous les CPU possibles du système, comme indiqué dans /sys/devices/system/cpu/possible.

LTTNG_UST_REGISTER_TIMEOUT

Temps d'attente pour la commande de démon de session registration done avant de passer à l'exécution du programme principal (millisecondes).

La valeur 0 signifie ne pas attendre. La valeur -1 signifie attendre indéfiniment. Définir cette variable d'environnement à 0 est recommandé pour les applications ayant des contraintes de temps sur le temps de démarrage du processus.

Par défaut : 3000.

LTTNG_UST_WITHOUT_BADDR_STATEDUMP

Si défini, empêche liblttng-ust d'effectuer un vidage d'état de l'adresse de base (voir la section LTTng-UST state dump ci-dessus).

LTTNG_UST_WITHOUT_PROCNAME_STATEDUMP

Si défini, empêche liblttng-ust d'effectuer un vidage d'état du nom de processus (voir la section LTTng-UST state dump ci-dessus).
