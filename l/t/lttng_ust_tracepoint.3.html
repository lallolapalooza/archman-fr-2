DESCRIPTION

Le projet Linux Trace Toolkit: next generation http://lttng.org/ est un ensemble de logiciels libres utilisés pour le traçage corrélé du noyau Linux, des applications et des bibliothèques en espace utilisateur.

LTTng-UST est le composant de traçage en espace utilisateur du projet LTTng. Il s'agit d'un portage en espace utilisateur des capacités de traçage à faible surcharge du traceur du noyau Linux LTTng. La bibliothèque liblttng-ust est utilisée pour tracer les applications et bibliothèques en espace utilisateur.


Note

Cette page de manuel concerne la bibliothèque liblttng-ust. Le projet LTTng-UST fournit également des paquets Java et Python pour tracer des applications écrites dans ces langages. La manière d'instrumenter et de tracer les applications Java et Python est documentée dans la documentation LTTng en ligne http://lttng.org/docs/.

Il existe trois façons d'utiliser liblttng-ust :

•Utilisation de l'API lttng_ust_tracef(3), qui est similaire à printf(3).
•Utilisation de l'API lttng_ust_tracelog(3), qui est lttng_ust_tracef(3) avec un paramètre de niveau de journalisation.
•Définition de vos propres points de trace. Voir la section Création d'un fournisseur de points de trace ci-dessous.

Compatibilité avec les anciennes APIs

Depuis LTTng-UST 2.13, la définition LTTNG_UST_COMPAT_API_VERSION contrôle quelles APIs LTTng-UST sont disponibles (compilées) :

Non définie

Toutes les APIs sont disponibles.

N (0 ou entier positif)

L'API version N, et toutes les APIs existantes suivantes, sont disponibles. Les APIs précédentes ne sont pas disponibles (non compilées).

Le tableau suivant montre la correspondance entre les versions de LTTng-UST (jusqu'à LTTng-UST 2.14.0) et les versions d'API disponibles :

Version de LTTng-UST Versions d'API disponibles
2.0 à 2.12 0
2.13 0 et 1

Cette page de manuel ne documente que la version 1 de l'API.

Si vous souhaitez avoir accès à la version 0 de l'API (par exemple, les macros tracepoint(), ctf_integer(), et TRACEPOINT_EVENT()), alors ne définissez pas LTTNG_UST_COMPAT_API_VERSION, ou définissez-la à 0 avant d'inclure tout en-tête LTTng-UST.

Création d'un fournisseur de points de trace

La création d'un fournisseur de points de trace est la première étape de l'utilisation de liblttng-ust. Les étapes suivantes sont :

•Instrumentation de votre application avec des appels lttng_ust_tracepoint()
•Compilation de votre application avec le support LTTng-UST

Ce site n'est en aucun cas associé à Arch Linux ni affilié à ce projet. Le contenu est uniquement une traduction des pages de manuel d'Arch publiées sur man.archlinux.org.

, soit statiquement, soit dynamiquement.

Un fournisseur de points de trace est un objet compilé contenant les sondes d'événements correspondant à vos définitions de points de trace personnalisés. Un fournisseur de points de trace contient le code pour obtenir la taille d'un événement et pour le sérialiser, entre autres choses.

Pour créer un fournisseur de points de trace, commencez avec le modèle en-tête de fournisseur de points de trace suivant :

#undef LTTNG_UST_TRACEPOINT_PROVIDER
#define LTTNG_UST_TRACEPOINT_PROVIDER mon_fournisseur
#undef LTTNG_UST_TRACEPOINT_INCLUDE
#define LTTNG_UST_TRACEPOINT_INCLUDE "./tp.h"
#if !defined(_TP_H) || \
    defined(LTTNG_UST_TRACEPOINT_HEADER_MULTI_READ)
#define _TP_H
#include <lttng/tracepoint.h>
/*
 * LTTNG_UST_TRACEPOINT_EVENT(), LTTNG_UST_TRACEPOINT_EVENT_CLASS(),
 * LTTNG_UST_TRACEPOINT_EVENT_INSTANCE(),
 * LTTNG_UST_TRACEPOINT_LOGLEVEL(), et `LTTNG_UST_TRACEPOINT_ENUM()`
 * sont utilisés ici.
 */
#endif /* _TP_H */
#include <lttng/tracepoint-event.h>

Dans ce modèle, le fournisseur de points de trace est nommé mon_fournisseur (définition LTTNG_UST_TRACEPOINT_PROVIDER). Le fichier doit porter le nom de la définition LTTNG_UST_TRACEPOINT_INCLUDE (tp.h dans ce cas). Entre #include <lttng/tracepoint.h> et #endif se trouvent les appels des macros LTTNG_UST_TRACEPOINT_EVENT(), LTTNG_UST_TRACEPOINT_EVENT_CLASS(), LTTNG_UST_TRACEPOINT_EVENT_INSTANCE(), LTTNG_UST_TRACEPOINT_LOGLEVEL(), et LTTNG_UST_TRACEPOINT_ENUM().


Note

Vous pouvez éviter d'écrire le prologue et l'épilogue du modèle ci-dessus en utilisant l'outil lttng-gen-tp(1) fourni avec LTTng-UST.

Le fichier d'en-tête du fournisseur de points de trace doit être inclus dans un fichier source qui ressemble à ceci :

#define LTTNG_UST_TRACEPOINT_CREATE_PROBES
#include "tp.h"

Ensemble, ces deux fichiers (appelons-les tp.h et tp.c) forment les sources du fournisseur de points de trace, prêts à être compilés.

Vous pouvez créer plusieurs fournisseurs de points de trace à utiliser dans une seule application, mais chacun doit avoir son propre fichier d'en-tête.

La section d'utilisation de LTTNG_UST_TRACEPOINT_EVENT() ci-dessous montre comment utiliser la macro LTTNG_UST_TRACEPOINT_EVENT() pour définir les points de trace réels dans le fichier d'en-tête du fournisseur de points de trace.

Voir la section EXEMPLE ci-dessous pour un exemple complet.

Utilisation de LTTNG_UST_TRACEPOINT_EVENT()

La macro LTTNG_UST_TRACEPOINT_EVENT() est utilisée dans un fichier d'en-tête de fournisseur modèle (voir la section Création d'un fournisseur de points de trace ci-dessus) pour définir les points de trace LTTng-UST.

Le modèle d'utilisation de LTTNG_UST_TRACEPOINT_EVENT() est le suivant :

LTTNG_UST_TRACEPOINT_EVENT(
    /* Nom du fournisseur de points de trace */
    mon_fournisseur,
    /* Nom du point de trace/événement */
    mon_point_de_trace,
    /* Liste des arguments du point de trace (entrée) */
    LTTNG_UST_TP_ARGS(
        ...
    ),
    /* Liste des champs de l'événement résultant (sortie) */
    LTTNG_UST_TP_FIELDS(
        ...
    )
)

La macro LTTNG_UST_TP_ARGS() contient les arguments d'entrée du point de trace. Ces arguments peuvent être utilisés dans les expressions d'arguments des champs de sortie définis dans LTTNG_UST_TP_FIELDS().

Le format des paramètres de LTTNG_UST_TP_ARGS() est : type C, puis nom de l'argument ; répéter autant que nécessaire, jusqu'à dix fois. Par exemple :

LTTNG_UST_TP_ARGS(
    int, mon_entier,
    const char *, ma_chaine,
    FILE *, mon_fichier,
    double, mon_flottant,
    struct ma_donnee *, ma_donnee
)

La macro LTTNG_UST_TP_FIELDS() contient les champs de sortie du point de trace, c'est-à-dire les données réelles qui peuvent être enregistrées dans la charge utile d'un événement émis par ce point de trace.

La macro LTTNG_UST_TP_FIELDS() contient une liste de macros lttng_ust_field_*() NON séparées par des virgules. Les macros disponibles sont documentées dans la section des macros de type de champ Available lttng_ust_field_*() ci-dessous.

Les paramètres sont :

compteur

Nombre d'éléments dans le tableau/la séquence. Ceci doit être connu au moment de la compilation.

nom_enum

Nom d'un champ d'énumération préalablement défini avec la macro LTTNG_UST_TRACEPOINT_ENUM(). Voir la section d'utilisation de LTTNG_UST_TRACEPOINT_ENUM() pour plus d'informations.

expression

Expression C résultant de la valeur du champ. Cette expression peut utiliser un ou plusieurs arguments passés au point de trace. Les arguments d'un point de trace donné sont définis dans la macro LTTNG_UST_TP_ARGS() (voir la section Création d'un fournisseur de points de trace ci-dessus).

nom_champ

Nom du champ de l'événement (syntaxe d'identifiant C, PAS une chaîne littérale).

type_flottant

Type C flottant (float ou double). La taille de ce type détermine la taille du champ flottant.

type_entier

Type C entier. La taille de ce type détermine la taille du champ entier/énumération.

expression_longueur

Expression C résultant de la longueur de la séquence. Cette expression peut utiliser un ou plusieurs arguments passés au point de trace.

type_longueur

Type C entier non signé de la longueur de la séquence.

nom_prov

Nom du fournisseur de points de trace. Il doit s'agir du même nom que celui utilisé dans une définition de champ précédente.

mais sont sinon identiques. Leur objectif principal est de rendre une partie du contexte de l'événement disponible aux filtres d'événements sans avoir à valider les données dans des sous-tampons. Voir lttng-enable-event(1) pour en savoir plus sur le filtrage dynamique des événements.

Utilisation de LTTNG_UST_TRACEPOINT_ENUM()

Un champ d'énumération est une liste de correspondances entre un entier, ou une plage d'entiers, et des chaînes de caractères (parfois appelées labels ou énumérateurs). Les champs d'énumération peuvent être utilisés pour avoir une trace plus compacte lorsque les valeurs possibles d'un champ sont limitées.

Un champ d'énumération est défini avec la macro LTTNG_UST_TRACEPOINT_ENUM() :

LTTNG_UST_TRACEPOINT_ENUM(
    /* Nom du fournisseur de tracepoint */
    my_provider,
    /* Nom de l'énumération (unique dans tout le fournisseur de tracepoint) */
    my_enum,
    /* Mappages d'énumération */
    LTTNG_UST_TP_ENUM_VALUES(
        ...
    )
)

LTTNG_UST_TP_ENUM_VALUES() contient une liste de mappages d'énumération, NON séparés par des virgules. Deux macros peuvent être utilisées dans LTTNG_UST_TP_ENUM_VALUES() : lttng_ust_field_enum_value() et lttng_ust_field_enum_range().

lttng_ust_field_enum_value() est un mappage de valeur unique :

lttng_ust_field_enum_value(label, valeur)

Cette macro mappe la chaîne de caractères label donnée à la valeur valeur.

lttng_ust_field_enum_range() est un mappage de plage :

lttng_ust_field_enum_range(label, début, fin)

Cette macro mappe la chaîne de caractères label donnée à la plage d'entiers de début à fin, inclusivement. Les mappages de plage peuvent se chevaucher, mais le comportement est défini par l'implémentation : chaque lecteur de trace gère les plages qui se chevauchent comme il le souhaite.

Voir la section EXEMPLE ci-dessous pour un exemple complet.

Utilisation de LTTNG_UST_TRACEPOINT_EVENT_CLASS()

Une classe de tracepoint est une classe de tracepoints partageant les mêmes types et noms de champs. Une instance de tracepoint est une instance d'une telle classe de tracepoint déclarée, avec son propre nom d'événement.

LTTng-UST crée une fonction de sérialisation d'événements par classe de tracepoint. Utiliser LTTNG_UST_TRACEPOINT_EVENT() crée une classe de tracepoint par définition de tracepoint, tandis qu'utiliser LTTNG_UST_TRACEPOINT_EVENT_CLASS() et LTTNG_UST_TRACEPOINT_EVENT_INSTANCE() crée une classe de tracepoint, et une ou plusieurs instances de tracepoint de cette classe. En d'autres termes, de nombreux tracepoints peuvent réutiliser le même code de sérialisation. Réutiliser le même code, lorsque c'est possible, peut réduire la pollution du cache, et ainsi améliorer les performances.

La macro LTTNG_UST_TRACEPOINT_EVENT_CLASS() accepte les mêmes paramètres que la macro LTTNG_UST_TRACEPOINT_EVENT(), à la différence qu'au lieu d'un nom d'événement, son deuxième paramètre est le nom de la classe de tracepoint :

#define LTTNG_UST_TRACEPOINT_PROVIDER my_provider
/* ... */
LTTNG_UST_TRACEPOINT_EVENT_CLASS(
    /* Nom du fournisseur de la classe de tracepoint */
    my_provider,
    /* Nom de la classe de tracepoint */
    my_tracepoint_class,
    /* Liste des arguments du tracepoint (entrée) */
    LTTNG_UST_TP_ARGS(
        ...
    ),
    /* Liste des champs de l'événement éventuel (sortie) */
    LTTNG_UST_TP_FIELDS(
        ...
    )
)

Une fois la classe de tracepoint définie, vous pouvez créer autant d'instances de tracepoint que nécessaire :

#define LTTNG_UST_TRACEPOINT_PROVIDER natality
/* ... */
LTTNG_UST_TRACEPOINT_EVENT_INSTANCE(
    /* Nom du fournisseur de la classe de tracepoint */
    my_provider,
    /* Nom de la classe de tracepoint */
    my_tracepoint_class,
    /* Nom du fournisseur local (d'instance) de tracepoint */
    natality,
    /* Nom du tracepoint/événement */
    my_tracepoint,
    /* Liste des arguments du tracepoint (entrée) */
    LTTNG_UST_TP_ARGS(
        ...
    )
)

Comme vous pouvez le voir, LTTNG_UST_TRACEPOINT_EVENT_INSTANCE() ne contient pas la macro LTTNG_UST_TP_FIELDS(), car ils sont définis au niveau de LTTNG_UST_TRACEPOINT_EVENT_CLASS().

Notez que la macro LTTNG_UST_TRACEPOINT_EVENT_INSTANCE() nécessite deux noms de fournisseur :

• Le nom du fournisseur de la classe de tracepoint (my_provider dans l'exemple ci-dessus).

C'est le même que le premier argument de l'expansion de LTTNG_UST_TRACEPOINT_EVENT_CLASS() auquel il est fait référence.

• Le nom du fournisseur local, ou d'instance (natality dans l'exemple ci-dessus).

C'est le nom du fournisseur qui devient la partie préfixe du nom des événements créés par un tel tracepoint.

Les deux noms de fournisseur peuvent être différents si la classe de tracepoint et les macros d'instance de tracepoint sont dans deux unités de traduction différentes.

Voir la section EXEMPLE ci-dessous pour un exemple complet.

Utilisation de LTTNG_UST_TRACEPOINT_LOGLEVEL()

Optionnellement, un niveau de journal peut être attribué à un tracepoint défini. L'attribution de différents niveaux de gravité aux tracepoints peut être utile : lors du contrôle des sessions de traçage, vous pouvez choisir de n'activer que les événements tombant dans une plage de niveaux de journal spécifique en utilisant les options --loglevel et --loglevel-only de la commande lttng-enable-event(1).

Les niveaux de journal sont attribués aux tracepoints déjà définis à l'aide de la macro LTTNG_UST_TRACEPOINT_LOGLEVEL(). Cette dernière doit être utilisée après avoir utilisé LTTNG_UST_TRACEPOINT_EVENT() ou LTTNG_UST_TRACEPOINT_EVENT_INSTANCE() pour un tracepoint donné. La macro LTTNG_UST_TRACEPOINT_LOGLEVEL() est utilisée comme suit :

LTTNG_UST_TRACEPOINT_LOGLEVEL(
    /* Nom du fournisseur de tracepoint */
    my_provider,
    /* Nom du tracepoint/événement */
    my_tracepoint,
    /* Niveau de journal */
    LTTNG_UST_TRACEPOINT_LOGLEVEL_INFO
)

Les définitions de niveaux de journal disponibles sont :

LTTNG_UST_TRACEPOINT_LOGLEVEL_EMERG

Le système est inutilisable.

LTTNG_UST_TRACEPOINT_LOGLEVEL_ALERT

Une action doit être entreprise immédiatement.

LTTNG_UST_TRACEPOINT_LOGLEVEL_CRIT

Conditions critiques.

LTTNG_UST_TRACEPOINT_LOGLEVEL_ERR

Conditions d'erreur.

LTTNG_UST_TRACEPOINT_LOGLEVEL_WARNING

Conditions d'avertissement.

LTTNG_UST_TRACEPOINT_LOGLEVEL_NOTICE

Condition normale mais significative.

LTTNG_UST_TRACEPOINT_LOGLEVEL_INFO

Message informatif.

LTTNG_UST_TRACEPOINT_LOGLEVEL_DEBUG_SYSTEM

Informations de débogage avec une portée système (ensemble de programmes).

LTTNG_UST_TRACEPOINT_LOGLEVEL_DEBUG_PROGRAM

Instrumenter votre application

Une fois le fournisseur de tracepoint créé (voir la section Création d'un fournisseur de tracepoint ci-dessus), vous pouvez instrumenter votre application avec les tracepoints définis grâce à la macro lttng_ust_tracepoint() :

#define lttng_ust_tracepoint(nom_prov, nom_t, ...)

Avec :

nom_prov

Nom du fournisseur de tracepoint.

nom_t

Nom du tracepoint/événement.

...

Arguments du tracepoint, le cas échéant.

Assurez-vous d'inclure le fichier d'en-tête du fournisseur de tracepoint partout où vous utilisez lttng_ust_tracepoint() pour ce fournisseur.


Note

Bien que LTTng-UST prenne en charge les duplications de site d'appel lttng_ust_tracepoint() ayant les mêmes noms de fournisseur et de tracepoint, il est recommandé d'utiliser une paire nom de fournisseur/tracepoint une seule fois dans le code source de l'application pour aider à mapper les événements à leurs sites d'appel lors de l'analyse de la trace.

Parfois, les arguments du tracepoint sont coûteux à calculer (prendre la pile d'appels, par exemple). Pour éviter le calcul lorsque le tracepoint est désactivé, vous pouvez utiliser les macros lttng_ust_tracepoint_enabled() et lttng_ust_do_tracepoint() :

#define lttng_ust_tracepoint_enabled(nom_prov, nom_t)
#define lttng_ust_do_tracepoint(nom_prov, nom_t, ...)

lttng_ust_tracepoint_enabled() renvoie une valeur non nulle si le tracepoint nommé nom_t du fournisseur nommé nom_prov est activé à l'exécution.

lttng_ust_do_tracepoint() est comme lttng_ust_tracepoint(), sauf qu'il ne vérifie pas si le tracepoint est activé. Utiliser lttng_ust_tracepoint() avec lttng_ust_tracepoint_enabled() est dangereux car lttng_ust_tracepoint() contient également la vérification lttng_ust_tracepoint_enabled(), donc une condition de concurrence est possible dans cette situation :

if (lttng_ust_tracepoint_enabled(my_provider, my_tracepoint)) {
    stuff = prepare_stuff();
}
lttng_ust_tracepoint(my_provider, my_tracepoint, stuff);

Si le tracepoint est activé après la condition, alors stuff n'est pas préparé : l'événement émis contiendra soit des données incorrectes, soit l'application entière pourrait planter (segmentation fault, par exemple).


Note

Ni lttng_ust_tracepoint_enabled() ni lttng_ust_do_tracepoint() n'ont d'appel STAP_PROBEV(), donc si vous en avez besoin, vous devez émettre cet appel vous-même.

Traçage C/

Traçage des constructeurs et destructeurs C/C++

Si l'une des conditions suivantes est vraie :

• Vous compilez votre application C++ avec GCC ≤ 4.8.
• Vous compilez votre application C/C++ avec un compilateur C++ et définissez LTTNG_UST_ALLOCATE_COMPOUND_LITERAL_ON_HEAP.

Alors LTTng ne tracera pas :

• Les constructeurs et destructeurs C dans l'application elle-même ou dans des archives liées statiquement.
• Certains constructeurs et destructeurs C++ dans l'application elle-même ou dans des archives liées statiquement.

Dans ce cas, le comportement exact des constructeurs et destructeurs C++ qui ne seront pas tracés dépend de l'ordre d'initialisation au sein de chaque unité de traduction et à travers le programme entier lorsque toutes les unités de traduction sont liées ensemble.

Liaison statique du fournisseur de points de trace

Avec la méthode de liaison statique, les fournisseurs de points de trace compilés sont copiés dans l'application cible.

Définissez la macro LTTNG_UST_TRACEPOINT_DEFINE sous la définition LTTNG_UST_TRACEPOINT_CREATE_PROBES dans le code source du fournisseur de points de trace :

#define LTTNG_UST_TRACEPOINT_CREATE_PROBES
#define LTTNG_UST_TRACEPOINT_DEFINE
#include "tp.h"

Créez le fichier objet du fournisseur de points de trace :

$ cc -c -I. tp.c

Note

Bien qu'une application instrumentée avec des points de trace LTTng-UST puisse être compilée avec un compilateur C++, les sondes de points de trace devraient être compilées avec un compilateur C.

À ce stade, vous *pouvez* archiver ce fichier objet de fournisseur de points de trace, éventuellement avec d'autres fichiers objets de votre application ou avec d'autres fichiers objets de fournisseurs de points de trace, en tant que bibliothèque statique :

$ ar rc tp.a tp.o

L'utilisation d'une bibliothèque statique présente l'avantage de centraliser les objets des fournisseurs de points de trace afin qu'ils puissent être partagés entre plusieurs applications. De cette façon, lorsque le fournisseur de points de trace est modifié, les changements de code source n'ont pas besoin d'être appliqués dans l'arbre source de chaque application. Les applications doivent être relinkées après chaque changement, mais n'ont pas besoin d'être autrement recompilées (sauf si l'API du fournisseur de points de trace change).

Ensuite, liez votre application avec ce fichier objet (ou avec la bibliothèque statique qui le contient) et avec liblttng-ust et libdl (libc sur un système BSD) :

$ cc -o app tp.o app.o -llttng-ust -ldl

Chargement dynamique du fournisseur de points de trace

La deuxième approche pour empaqueter le fournisseur de points de trace consiste à utiliser le chargeur dynamique : la bibliothèque et ses fonctions membres sont recherchées explicitement, chargées à l'exécution.

Dans ce scénario, le fournisseur de points de trace est compilé en tant qu'objet partagé.

Le processus de création de l'objet partagé du fournisseur de points de trace est pratiquement le même que celui de la *méthode de liaison statique*, sauf que :

• Comme le fournisseur de points de trace ne fait pas partie de l'application, LTTNG_UST_TRACEPOINT_DEFINE doit être défini, pour chaque fournisseur de points de trace, dans exactement un fichier source de l' *application*.
• LTTNG_UST_TRACEPOINT_PROBE_DYNAMIC_LINKAGE doit être défini à côté de LTTNG_UST_TRACEPOINT_DEFINE.

Concernant LTTNG_UST_TRACEPOINT_DEFINE et LTTNG_UST_TRACEPOINT_PROBE_DYNAMIC_LINKAGE, la pratique recommandée est d'utiliser un fichier source C séparé dans votre application pour les définir, puis d'inclure les fichiers d'en-tête du fournisseur de points de trace par la suite. Par exemple, sous la forme de tp-define.c :

#define LTTNG_UST_TRACEPOINT_DEFINE
#define LTTNG_UST_TRACEPOINT_PROBE_DYNAMIC_LINKAGE
#include "tp.h"

Le fichier objet du fournisseur de points de trace utilisé pour créer la bibliothèque partagée est construit comme il l'est en utilisant la méthode de liaison statique, mais avec l'option -fpic :

$ cc -c -fpic -I. tp.c

Il est ensuite lié en tant que bibliothèque partagée comme suit :

$ cc -shared -Wl,--no-as-needed -o tp.so tp.o -llttng-ust

Cet objet partagé de fournisseur de points de trace n'est pas lié à l'application utilisateur : il doit être chargé manuellement. C'est pourquoi l'application est construite sans mention de ce fournisseur de points de trace, mais nécessite toujours libdl :

$ cc -o app app.o tp-define.o -ldl

Il existe deux façons de charger dynamiquement l'objet partagé du fournisseur de points de trace :

• Le charger manuellement depuis l'application en utilisant dlopen(3).
• Faire en sorte que le chargeur dynamique le charge avec la variable d'environnement LD_PRELOAD (voir ld.so(8)).

Si l'application ne charge pas dynamiquement l'objet partagé du fournisseur de points de trace en utilisant l'une des méthodes ci-dessus, le traçage est désactivé pour cette application, et les événements ne sont pas listés dans la sortie de lttng-list(1).

Notez qu'il n'est pas sûr d'utiliser dlclose(3) sur un objet partagé de fournisseur de points de trace qui est activement utilisé pour le traçage, en raison d'un manque de comptage de références de LTTng-UST à l'objet partagé.

Par exemple, lier statiquement un fournisseur de points de trace à un objet partagé qui doit être chargé dynamiquement par une application (un plugin, par exemple) n'est pas sûr : l'objet partagé, qui contient le fournisseur de points de trace, pourrait être fermé dynamiquement (dlclose(3)) à tout moment par l'application.

Pour instrumenter un objet partagé, soit :

• Lier statiquement le fournisseur de points de trace à l'application, ou
• Compiler le fournisseur de points de trace en tant qu'objet partagé (en suivant la procédure décrite dans cette section), et le précharger lorsque le traçage est nécessaire en utilisant la variable d'environnement LD_PRELOAD.

Utilisation de LTTng-UST avec des démons

Des précautions supplémentaires sont nécessaires lors de l'utilisation de liblttng-ust avec des applications démons qui appellent fork(2), clone(2), ou le rfork(2) de BSD sans un appel système de la famille exec(3) qui suit. La bibliothèque liblttng-ust-fork.so doit être préchargée avant de démarrer l'application avec la variable d'environnement LD_PRELOAD (voir ld.so(8)).

Pour utiliser liblttng-ust avec une application démon qui ferme des descripteurs de fichiers qui n'ont pas été ouverts par elle, préchargez la bibliothèque liblttng-ust-fd.so avant de démarrer l'application. Les cas d'utilisation typiques incluent les démons fermant tous les descripteurs de fichiers après fork(2), et les applications buggées effectuant des "doubles fermetures".

VARIABLES D'ENVIRONNEMENT

LTTNG_HOME

Répertoire personnel alternatif de l'utilisateur. Cette variable est utile lorsque l'utilisateur exécutant l'application instrumentée a un répertoire personnel non inscriptible. Ce chemin est l'emplacement des sockets Unix pour la communication avec le démon de session par utilisateur.

LTTNG_UST_ABORT_ON_CRITICAL

Si défini, quitte l'application instrumentée en cas de message d'erreur critique.

LTTNG_UST_ALLOW_BLOCKING

Si défini, autorise l'application à retenter le traçage des événements lorsqu'il n'y a plus d'espace pour l'enregistrement de l'événement dans le sous-buffer, bloquant ainsi effectivement l'application jusqu'à ce que de l'espace soit disponible ou que le délai d'attente configuré soit atteint.

Pour autoriser une application à bloquer pendant le traçage, vous devez également spécifier un délai d'attente de blocage lorsque vous créez un canal avec l'option --blocking-timeout de la commande lttng-enable-channel(1).

Cette option peut être utile pour les charges de travail générant un très haut débit de données de trace, où le blocage de l'application est un compromis acceptable pour éviter de perdre des enregistrements d'événements.


Avertissement
La définition de cette variable d'environnement peut affecter considérablement les temps d'exécution de l'application.

LTTNG_UST_APP_PATH

Chemin du répertoire où le démon de session LTTng est censé placer les fichiers suivants pour recevoir les demandes de connexion des applications instrumentées :
•Le socket Unix d'enregistrement de l'application.
•Les fichiers de mémoire partagée « wait » pour réveiller les applications instrumentées qui attendent le démarrage d'un démon de session.
•Le fichier de port de l'agent.

Ce fichier contient le port TCP auquel les agents doivent se connecter pour activer le traçage LTTng.

Ce répertoire doit exister lorsque vous démarrez l'application pour que le traçage LTTng soit activé.

Lorsque LTTNG_UST_APP_PATH est défini, liblttng-ust :

•Ne considère que ce chemin pour se connecter à un démon de session.
•Ne se connectera pas aux démons de session root et/ou utilisateur comme d'habitude.

Voir la variable d'environnement correspondante LTTNG_UST_CTL_PATH de lttng-sessiond(8).

LTTNG_UST_CLOCK_PLUGIN

Chemin vers l'objet partagé qui sert de plugin de substitution d'horloge. Un exemple d'un tel plugin se trouve dans la documentation LTTng-UST sous examples/clock-override https://github.com/lttng/lttng-ust/tree/stable-2.14/doc/examples/clock-override.

LTTNG_UST_DEBUG

Si défini, active la sortie de débogage et d'erreur de liblttng-ust.

LTTNG_UST_GETCPU_PLUGIN

Chemin vers l'objet partagé qui agit comme plugin de remplacement de getcpu(). Un exemple d'un tel plugin peut être trouvé dans la documentation LTTng-UST sous examples/getcpu-override https://github.com/lttng/lttng-ust/tree/stable-2.14/doc/examples/getcpu-override.

LTTNG_UST_MAP_POPULATE_POLICY

Si défini, remplace la politique utilisée pour remplir les pages de mémoire partagée dans l'application.

Les valeurs possibles sont :

none (par défaut)

Ne pré-remplit aucune page : prend des défauts mineurs lors du premier accès pendant le traçage.

cpu_possible

Pré-remplit les pages pour tous les CPU possibles du système, comme indiqué dans /sys/devices/system/cpu/possible.

LTTNG_UST_REGISTER_TIMEOUT

Temps d'attente pour la commande de démon de session registration done avant de continuer à exécuter le programme principal (millisecondes).

La valeur 0 signifie ne pas attendre. La valeur -1 signifie attendre indéfiniment. Il est recommandé de régler cette variable d'environnement sur 0 pour les applications dont le temps de démarrage du processus est limité.

Par défaut : 3000.

LTTNG_UST_WITHOUT_BADDR_STATEDUMP

Si défini, empêche liblttng-ust d'effectuer un vidage d'état d'adresse de base (voir la section Vidage d'état LTTng-UST ci-dessus).

LTTNG_UST_WITHOUT_PROCNAME_STATEDUMP

Si défini, empêche liblttng-ust d'effectuer un vidage d'état de nom de processus (voir la section Vidage d'état LTTng-UST ci-dessus).
