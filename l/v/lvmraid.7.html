NOM

lvmraid — LVM RAID

DESCRIPTION

lvm(8) RAID est une méthode pour créer un Volume Logique (LV) qui utilise plusieurs périphériques physiques pour améliorer les performances ou tolérer les pannes de périphériques. Dans LVM, les périphériques physiques sont des Périphériques Physiques (PV) au sein d'un seul Groupe de Volumes (VG).

La manière dont les blocs de données du LV sont placés sur les PV est déterminée par le niveau RAID. Les niveaux RAID sont couramment désignés par 'raid' suivi d'un nombre, par exemple raid1, raid5 ou raid6. La sélection d'un niveau RAID implique des compromis entre : les exigences en matière de périphériques physiques, la tolérance aux pannes et les performances. Une description des niveaux RAID peut être trouvée à : Technical_Position.pdf

LVM RAID utilise à la fois le Device Mapper (DM) et les pilotes Multiple Device (MD) du noyau Linux. DM est utilisé pour créer et gérer les périphériques LVM visibles, et MD est utilisé pour placer les données sur les périphériques physiques.

LVM crée des LV cachés (périphériques dm) superposés entre le LV visible et les périphériques physiques. Les LV dans les couches intermédiaires sont appelés sous-LV. Pour LVM raid, une paire de sous-LV pour stocker les données et les métadonnées (superbloc RAID et bitmap d'intention d'écriture) est créée par image/branche RAID (voir les exemples de commande lvs(8) ci-dessous).

UTILISATION

Pour créer un LV RAID, utilisez lvcreate et spécifiez un type de LV. Le type de LV correspond à un niveau RAID. Les niveaux RAID de base qui peuvent être utilisés sont : raid0, raid1, raid4, raid5, raid6, raid10.

lvcreate --type NiveauRaid [OPTIONS] --name Nom --size Taille VG [PVs]

Pour afficher le type de LV d'un LV existant, exécutez :

# lvs -o name,segtype LV

(Le type de LV est également appelé « type de segment » ou « segtype ».)

Les LV peuvent être créés avec les types suivants :

raid0

Aussi appelé entrelacement (striping), raid0 répartit les données du LV sur plusieurs périphériques par unités de taille de bande. Ceci est utilisé pour augmenter les performances. Les données du LV seront perdues si l'un des périphériques tombe en panne.

lvcreate --type raid0 [--stripes Nombre --stripesize Taille] VG [PVs]

--stripes Nombre
spécifie le Nombre de périphériques sur lesquels répartir le LV.
--stripesize Taille
spécifie la Taille de chaque bande en kilooctets. C'est la quantité de données qui est écrite sur un périphérique avant de passer au suivant.
PVs
spécifie les périphériques à utiliser. S'il n'est pas spécifié, lvm choisira Nombre périphériques, un pour chaque bande en fonction du nombre de PV disponibles ou fournis.

raid1

Aussi appelé mise en miroir (mirroring), raid1 utilise plusieurs périphériques pour dupliquer les données du LV. Les données du LV restent disponibles si tous les périphériques sauf un tombent en panne. Le nombre minimum de périphériques (c'est-à-dire de paires de sous-LV) requis est de 2.

lvcreate --type raid1 [--mirrors Nombre] VG [PVs]

--mirrors Nombre
spécifie le Nombre d'images miroir en plus de l'image LV d'origine, par exemple --mirrors 1 signifie qu'il y a deux images des données, l'originale et une image miroir.
PVs
spécifie les périphériques à utiliser. S'il n'est pas spécifié, lvm choisira Nombre périphériques, un pour chaque image.

raid4

raid4 est une forme d'entrelacement qui utilise un périphérique supplémentaire, le premier, dédié au stockage des blocs de parité. Les données du LV restent disponibles si un périphérique tombe en panne. La parité est utilisée pour recalculer les données perdues d'un seul périphérique. Le nombre minimum de périphériques requis est de 3.

lvcreate --type raid4 [--stripes Nombre --stripesize Taille] VG [PVs]

--stripes Nombre
spécifie le Nombre de périphériques à utiliser pour les données du LV. Ceci n'inclut pas le périphérique supplémentaire que lvm ajoute pour stocker les blocs de parité. Un LV raid4 avec Nombre bandes nécessite Nombre+1 périphériques. Nombre doit être égal ou supérieur à 2.
--stripesize Taille
spécifie la Taille de chaque bande en kilooctets. C'est la quantité de données qui est écrite sur un périphérique avant de passer au suivant.
PVs
spécifie les périphériques à utiliser. S'il n'est pas spécifié, lvm choisira Nombre+1 périphériques distincts.

raid4 est appelé parité non rotative car les blocs de parité sont toujours stockés sur le même périphérique.

raid5

raid5 est une forme d'entrelacement qui utilise un périphérique supplémentaire pour stocker les blocs de parité. Les données du LV et les blocs de parité sont stockés sur chaque périphérique, généralement dans un schéma rotatif pour des raisons de performance. Les données du LV restent disponibles si un périphérique tombe en panne. La parité est utilisée pour recalculer les données perdues d'un seul périphérique. Le nombre minimum de périphériques requis est de 3 (sauf lors de la conversion d'un raid1 à 2 branches pour le remodeler en plus de bandes ; voir remodeler).

lvcreate --type raid5 [--stripes Nombre --stripesize Taille] VG [PVs]

--stripes Nombre
spécifie le Nombre de périphériques à utiliser pour les données du LV. Ceci n'inclut pas le périphérique supplémentaire que lvm ajoute pour stocker les blocs de parité. Un LV raid5 avec Nombre bandes nécessite Nombre+1 périphériques. Nombre doit être égal ou supérieur à 2.
--stripesize Taille
spécifie la Taille de chaque bande en kilooctets. C'est la quantité de données qui est écrite sur un périphérique avant de passer au suivant.
PVs
spécifie les périphériques à utiliser. S'il n'est pas spécifié, lvm choisira Nombre+1 périphériques distincts.

raid5 est appelé parité rotative car les blocs de parité sont placés sur différents périphériques selon une séquence circulaire. Il existe des variantes de raid5 avec différents algorithmes pour placer les blocs de parité. La variante par défaut est raid5_ls (raid5 left symmetric, qui est une parité rotative 0 avec redémarrage des données).
Voir VARIANTES RAID5 ci-dessous.

raid6

raid6 est une forme d'entrelacement comme raid5, mais utilise deux périphériques supplémentaires pour les blocs de parité. Les données du LV et les blocs de parité sont stockés sur chaque périphérique, généralement dans un schéma rotatif pour des raisons de performance. Les données du LV restent disponibles si jusqu'à deux périphériques tombent en panne. La parité est utilisée pour recalculer les données perdues d'un ou deux périphériques. Le nombre minimum de périphériques requis est de 5.

lvcreate --type raid6 [--stripes Nombre --stripesize Taille] VG [PVs]

--stripes Nombre
spécifie le Nombre de périphériques à utiliser pour les données du LV. Ceci n'inclut pas les deux périphériques supplémentaires que lvm ajoute pour stocker les blocs de parité. Un LV raid6 avec Nombre bandes nécessite Nombre+2 périphériques. Nombre doit être égal ou supérieur à 3.
--stripesize Taille
spécifie la Taille de chaque bande en kilooctets. C'est la quantité de données qui est écrite sur un périphérique avant de passer au suivant.
PVs
spécifie les périphériques à utiliser. S'il n'est pas spécifié, lvm choisira Nombre+2 périphériques distincts.

Comme raid5, il existe des variantes de raid6 avec différents algorithmes pour placer les blocs de parité. La variante par défaut est raid6_zr (raid6 zero restart, alias left symmetric, qui est une parité rotative 0 avec redémarrage des données.

rt).
Voir RAID6 VARIANTS ci-dessous.

raid10

raid10 est une combinaison de raid1 et raid0, qui entrelace les données sur des périphériques mis en miroir. Les données LV restent disponibles si un ou plusieurs périphériques restent dans chaque ensemble de miroir. Le nombre minimum de périphériques requis est de 4.

lvcreate --type raid10 [--mirrors NombreMiroirs] [--stripes NombreBandes --stripesize Taille] VG [PVs]

--mirrors NombreMiroirs
spécifie le nombre d'images miroir dans chaque bande. par exemple, --mirrors 1 signifie qu'il y a deux images des données, l'original et une image miroir.
--stripes NombreBandes
spécifie le nombre total de périphériques à utiliser dans toutes les images raid1 (pas le nombre de périphériques raid1 sur lesquels répartir le LV, même si c'est le résultat effectif). Le nombre de périphériques dans chaque miroir raid1 sera NombreBandes/(NombreMiroirs+1), par exemple, miroirs 1 et bandes 4 entrelaceront les données sur deux miroirs raid1, où chaque miroir contient deux périphériques.
--stripesize Taille
spécifie la Taille de chaque bande en kilo-octets. C'est la quantité de données qui est écrite sur un périphérique avant de passer au suivant.
PVs
spécifie les périphériques à utiliser. S'il n'est pas spécifié, lvm choisira les périphériques nécessaires. Les périphériques sont utilisés pour créer des miroirs dans l'ordre indiqué, par exemple, pour des miroirs 1, bandes 2, lister PV1 PV2 PV3 PV4 résulte en miroirs PV1/PV2 et PV3/PV4.

RAID10 ne fait pas de mise en miroir par-dessus des bandes, ce qui serait RAID01, qui est moins tolérant aux pannes de périphériques.

Surveillance

Lorsqu'un LV RAID est activé, le processus dmeventd(8) est lancé pour surveiller la santé du LV. Divers événements détectés dans le noyau peuvent entraîner l'envoi d'une notification du device-mapper au processus de surveillance, y compris les pannes de périphériques et l'achèvement de la synchronisation (par exemple, pour l'initialisation ou le nettoyage).

Le fichier de configuration LVM contient des options qui affectent la manière dont le processus de surveillance répondra aux événements de défaillance (par exemple, raid_fault_policy). Il est possible d'activer et de désactiver la surveillance avec lvchange, mais il n'est pas recommandé de désactiver cela à moins d'avoir une connaissance approfondie des conséquences.

Synchronisation

La synchronisation est le processus qui rend tous les périphériques d'un LV RAID cohérents entre eux.

Dans un LV RAID1, toutes les images miroir doivent contenir les mêmes données. Lorsqu'une nouvelle image miroir est ajoutée, ou qu'une image miroir manque de données, les images doivent être synchronisées. Des blocs de données sont copiés d'une image existante vers une image nouvelle ou obsolète pour les faire correspondre.

Dans un LV RAID 4/5/6, les blocs de parité et les blocs de données doivent correspondre en fonction du calcul de parité. Lorsque les périphériques d'un LV RAID changent, les données et les blocs de parité peuvent devenir incohérents et nécessiter une synchronisation. Les blocs corrects sont lus, la parité est calculée et les blocs recalculés sont écrits.

L'implémentation RAID garde une trace des parties d'un LV RAID qui sont synchronisées. Lorsque un LV RAID est créé et activé pour la première fois, la première synchronisation est appelée initialisation. Un pointeur stocké dans les métadonnées RAID suit le processus d'initialisation, ce qui permet de le redémarrer après une désactivation du RaidLV ou un crash. Toute écriture sur le RaidLV salit la région correspondante du bitmap d'intention d'écriture, ce qui permet une récupération rapide des régions après un crash. Sans cela, le LV entier devrait être synchronisé chaque fois qu'il serait activé.

La synchronisation automatique se produit lors de l'activation d'un LV RAID, mais elle est généralement partielle car les bitmaps réduisent les zones qui sont vérifiées. Une synchronisation complète devient nécessaire lorsque les périphériques du LV RAID sont remplacés.

L'état de synchronisation d'un LV RAID est rapporté par la commande suivante, où "Cpy%Sync" = "100%" signifie que la synchronisation est terminée :

# lvs -a -o name,sync_percent

Nettoyage

Le nettoyage est un scan complet du LV RAID demandé par un utilisateur. Le nettoyage peut trouver des problèmes qui sont manqués par la synchronisation partielle.

Le nettoyage suppose que les métadonnées RAID et les bitmaps peuvent être inexacts, il vérifie donc toutes les métadonnées RAID, les données LV et les blocs de parité. Le nettoyage peut trouver des incohérences causées par des erreurs matérielles ou une dégradation. Ces types de problèmes peuvent être indétectables par la synchronisation automatique qui exclut les zones en dehors du bitmap d'intention d'écriture RAID.

La commande pour nettoyer un LV RAID peut fonctionner dans deux modes différents :

lvchange --syncaction check|repair LV

check
Le mode de vérification est en lecture seule et ne détecte que les zones incohérentes dans le LV RAID, il ne les corrige pas.
repair
Le mode de réparation vérifie et écrit des blocs corrigés pour synchroniser les zones incohérentes.

Le nettoyage peut consommer beaucoup de bande passante et ralentir les E/S des applications sur le LV RAID. Pour contrôler le taux d'E/S utilisé pour le nettoyage, utilisez :

--maxrecoveryrate Taille[k|UNIT]
Définit le taux de récupération maximum pour un LV RAID. La Taille est spécifiée comme une quantité par seconde pour chaque périphérique du tableau. Si aucun suffixe n'est donné, alors KiB/sec/périphérique est utilisé. Définir le taux de récupération à 0 signifie qu'il sera illimité.
--minrecoveryrate Taille[k|UNIT]
Définit le taux de récupération minimum pour un LV RAID. La Taille est spécifiée comme une quantité par seconde pour chaque périphérique du tableau. Si aucun suffixe n'est donné, alors KiB/sec/périphérique est utilisé. Définir le taux de récupération à 0 signifie qu'il sera illimité.

Pour afficher le nettoyage en cours sur un LV, y compris le mode syncaction et le pourcentage d'achèvement, exécutez :

# lvs -a -o name,raid_sync_action,sync_percent

Une fois le nettoyage terminé, pour afficher le nombre de blocs incohérents trouvés, exécutez :

# lvs -o name,raid_mismatch_count

De plus, si des incohérences ont été trouvées, le champ d'attributs de lvs(8) affichera la lettre "m" (mismatch) dans la 9ème position, par exemple :

# lvs -o name,vgname,segtype,attr vg/lv
  LV VG   Type  Attr
  lv vg   raid1 Rwi-a-r-m-

Limitations du nettoyage

Le mode check ne peut signaler que le nombre de blocs incohérents, il ne peut pas indiquer quels blocs sont incohérents. Il est donc impossible de savoir quel périphérique a des erreurs, ou si les erreurs affectent les données du système de fichiers, les métadonnées ou rien du tout.

Le mode repair peut rendre les données du LV RAID cohérentes, mais il ne sait pas quelles données sont correctes. Le résultat peut être des données cohérentes mais incorrectes. Lorsque deux blocs de données différents doivent être rendus cohérents, il choisit le bloc du périphérique qui serait utilisé lors de l'initialisation RAID. Cependant, si le PV contenant des données corrompues est connu, lvchange --rebuild peut être utilisé à la place du nettoyage pour reconstruire les données sur le périphérique défectueux.

Les développements futurs pourraient inclure :

Permettre à un utilisateur de choisir la version correcte des données lors de la réparation.

Utiliser une majorité de périphériques pour déterminer la version correcte des données à utiliser dans un RAID1 ou RAID6 à 3 voies.

Utiliser un périphérique de somme de contrôle pour identifier quand et où une erreur se produit, permettant ainsi de la réécrire.

Sous-LV

Un LV est souvent une combinaison d'autres LV cachés appelés Sous-LV. Les Sous-LV utilisent soit des périphériques physiques, soit sont construits à partir d'autres Sous-LV eux-mêmes. Les Sous-LV contiennent des blocs de données LV, des blocs de parité RAID et des métadonnées RAID. Les Sous-LV sont généralement cachés, donc l'option lvs -a est nécessaire pour les afficher :

# lvs -a -o name,segtype,devices

Les noms des Sous-LV commencent par le nom du LV visible et ont un suffixe automatique indiquant son rôle :

 •
Les Sous-LV contenant des blocs de données ou de parité LV ont le suffixe _rimage_#.
Ces Sous-LV sont parfois appelés DataLV.
 •
Les Sous-LV contenant des métadonnées RAID ont le suffixe _rmeta_#. Les métadonnées RAID incluent les informations de superblock, le type RAID, le bitmap et les informations de santé des périphériques.
Ces Sous-LV sont parfois appelés MetaLV.

Les Sous-LV sont un détail d'implémentation interne de LVM. La manière dont ils sont utilisés, construits et nommés peut changer.

Les exemples suivants montrent l'agencement des Sous-LV pour chacun des types de LV RAID de base, en utilisant le nombre minimum de périphériques autorisé pour chacun.

Exemples

Chaque Sous-LV rimage contient une partie des données LV. Aucune parité n'est utilisée. Aucune métadonnée RAID n'est utilisée.

# lvs -a -o name,segtype,devices

DEFAILLANCE DE PERIPHERIQUE

Les périphériques physiques d'un LV RAID peuvent tomber en panne ou être perdus pour plusieurs raisons. Un périphérique peut être déconnecté, définitivement défaillant ou temporairement déconnecté. Le but des LVs RAID (niveaux 1 et supérieurs) est de continuer à fonctionner en mode dégradé, sans perte de données du LV, même après la défaillance d'un périphérique. Le nombre de périphériques qui peuvent tomber en panne sans perte de données du LV dépend du niveau RAID :

 •
Les LVs RAID0 (en bande) ne peuvent tolérer la perte d'aucun périphérique. Les données du LV seront perdues si un quelconque périphérique tombe en panne.
 •
Les LVs RAID1 peuvent tolérer la perte de tous les périphériques sauf un sans perte de données du LV.
 •
Les LVs RAID4 et RAID5 peuvent tolérer la perte d'un périphérique sans perte de données du LV.
 •
Les LVs RAID6 peuvent tolérer la perte de deux périphériques sans perte de données du LV.
 •
RAID10 est variable et dépend des périphériques perdus. Il répartit sur plusieurs groupes miroirs avec une disposition raid1, donc il peut tolérer la perte de tous les périphériques sauf un dans chacun de ces groupes sans perte de données du LV.

Si un LV RAID a des périphériques manquants, ou s'il présente d'autres problèmes liés aux périphériques, lvs(8) le signale dans les champs health_status (et attr) :

# lvs -o name,lv_health_status
partiel

Activation d'un LV avec des périphériques manquants

Un LV RAID auquel il manque des périphériques peut être activé ou non, en fonction du « mode d'activation » utilisé dans lvchange :

lvchange -ay --activationmode complete|degraded|partial LV

complete
Le LV n'est activé que si tous les périphériques sont présents.
degraded
Le LV est activé avec des périphériques manquants si le niveau RAID peut tolérer le nombre de périphériques manquants sans perte de données du LV.
partial
Le LV est toujours activé, même si des parties des données du LV sont manquantes en raison du(des) périphérique(s) manquant(s). Ceci ne devrait être utilisé que pour effectuer des opérations de récupération ou de réparation extrêmes.

Mode d'activation par défaut lorsqu'il n'est pas spécifié par la commande :
lvm.conf(5) activation/activation_mode

La valeur par défaut est affichée par :

# lvmconfig --type default activation/activation_mode

Remplacement des périphériques

Les périphériques d'un LV RAID peuvent être remplacés par d'autres périphériques du VG. Lors du remplacement de périphériques qui ne sont plus visibles sur le système, utilisez lvconvert --repair. Lors du remplacement de périphériques encore visibles, utilisez lvconvert --replace. La commande de remplacement peut être répétée pour remplacer plusieurs PV. Les périphériques de remplacement peuvent être listés optionnellement avec l'une ou l'autre option.

lvconvert --repair LV [NouveauxPVs]

lvconvert --replace AncienPV LV [NouveauPV]

lvconvert --replace AncienPV1 --replace AncienPV2 ... LV [NouveauxPVs]

Les nouveaux périphériques nécessitent une synchronisation avec les périphériques existants.
Voir Synchronisation.

Si l'intégrité est utilisée, elle devra être désactivée avant que les commandes de réparation/remplacement puissent être utilisées (lvconvert --raidintegrity n). L'intégrité pourra être réactivée par la suite (lvconvert --raidintegrity y).

Actualisation d'un LV

L'actualisation d'un LV RAID efface toute défaillance transitoire de périphérique (périphérique déconnecté temporairement) et ramène le LV à son mode entièrement redondant. La restauration d'un périphérique nécessitera généralement au moins une synchronisation partielle (Voir Synchronisation). Si l'on ne parvient pas à effacer une défaillance transitoire, le LV RAID fonctionnera en mode dégradé jusqu'à sa réactivation. Utilisez la commande lvchange pour actualiser un LV :

lvchange --refresh LV

# lvs -o name,vgname,segtype,attr,size vg
  LV   VG Type  Attr       LSize
  lv   vg raid1 Rwi-a-r-r- 100.00g
# lvchange --refresh vg/lv
# lvs -o name,vgname,segtype,attr,size vg
  LV   VG Type  Attr       LSize
  lv   vg raid1 Rwi-a-r--- 100.00g

Réparation automatique

Si un périphérique d'un LV RAID tombe en panne, le device-mapper du noyau notifie le processus de surveillance dmeventd(8) (Voir Surveillance). dmeventd peut être configuré pour réagir automatiquement en utilisant :
lvm.conf(5) activation/raid_fault_policy

Les paramètres possibles sont :

warn
Un avertissement est ajouté au journal système indiquant qu'un périphérique est défaillant dans le LV RAID. Il appartient à l'utilisateur de réparer le LV, par exemple en remplaçant les périphériques défaillants.
allocate
dmeventd tente automatiquement de réparer le LV en utilisant des périphériques de secours dans le VG. Notez que même une défaillance transitoire est traitée comme une défaillance permanente dans ce paramètre. Un nouveau périphérique est alloué et une synchronisation complète est initiée.

La commande spécifique exécutée par dmeventd(8) pour avertir ou réparer est :
lvconvert --repair --use-policies LV

Données corrompues

Les données sur un périphérique peuvent être corrompues en raison d'erreurs matérielles sans que le périphérique ne soit jamais déconnecté ou qu'il y ait un défaut dans le logiciel. Ceci devrait être rare et peut être détecté (Voir Nettoyage (Scrubbing)).

Reconstruire des PV spécifiques

Si des PV spécifiques dans un LV RAID sont connus pour contenir des données corrompues, le

data on those PVs can be reconstructed with:

lvchange --rebuild PV LV

The rebuild option can be repeated with different PVs to replace the data on multiple PVs.

Réactivation des grappes après perte temporaire de périphérique

Lorsqu'une grappe RAID perd un nombre critique de périphériques, ce qui l'empêche de fonctionner de manière fiable, la grappe s'arrête et nécessite une réparation.

Lancez le processus de réparation avec cette commande :

lvconvert --repair LV

Si les périphériques précédemment indisponibles redeviennent accessibles, ce processus de réparation mettra à jour leurs métadonnées et la grappe RAID pourra être réactivée.

INTÉGRITÉ DES DONNÉES

La cible d'intégrité du device mapper peut être utilisée en combinaison avec les niveaux RAID 1,4,5,6,10 pour détecter et corriger la corruption des données dans les images RAID. Une couche dm-integrity est placée au-dessus de chaque image RAID, et un sous-LV supplémentaire est créé pour contenir les métadonnées d'intégrité (sommes de contrôle des données) pour chaque image RAID. Lorsque des données sont lues à partir d'une image, les sommes de contrôle d'intégrité sont utilisées pour détecter la corruption. Si elle est détectée, dm-raid lit les données d'une autre image (bonne) pour les renvoyer à l'appelant. dm-raid écrira également automatiquement les données correctes dans l'image contenant les données incorrectes pour corriger la corruption.

Lors de la création d'un LV RAID avec intégrité, ou de l'ajout d'intégrité, de l'espace est requis pour les métadonnées d'intégrité. Tous les 500 Mo de données LV nécessitent 4 Mo supplémentaires à allouer pour les métadonnées d'intégrité, pour chaque image RAID.

Créez un LV RAID avec intégrité :

lvcreate --type raidN --raidintegrity y

Ajoutez de l'intégrité à un LV RAID existant :

lvconvert --raidintegrity y LV

Supprimez l'intégrité d'un LV RAID :

lvconvert --raidintegrity n LV

Options d'intégrité

--raidintegritymode journal|bitmap
Utilisez un journal (par défaut) ou une bitmap pour maintenir la cohérence des sommes de contrôle d'intégrité en cas de crash. Les zones de bitmap sont recalculées après un crash, donc la corruption dans ces zones ne serait pas détectée. Un journal n'a pas ce problème. Le mode journal double les écritures sur le stockage, mais peut améliorer les performances pour les écritures dispersées regroupées en une seule écriture de journal. Le mode bitmap peut en théorie atteindre le débit d'écriture complet du périphérique, mais ne bénéficierait pas de l'optimisation potentielle des écritures dispersées.
--raidintegrityblocksize 512|1024|2048|4096
La taille de bloc à utiliser pour dm-integrity sur les images RAID. La taille de bloc d'intégrité doit généralement correspondre à la taille de bloc logique du périphérique, ou aux tailles de secteur/bloc du système de fichiers. Elle peut être inférieure à la taille de secteur/bloc du système de fichiers, mais pas inférieure à la taille de bloc logique du périphérique. Valeurs possibles : 512, 1024, 2048, 4096.
--integritysettings key=val
Les options ajustables du noyau dm-integrity peuvent être spécifiées ici. Les paramètres peuvent être inclus avec lvcreate ou lvconvert lors de l'activation initiale de l'intégrité, ou modifiés avec lvchange sur un LV inactif existant. Consultez la documentation du noyau pour les descriptions des options ajustables. Répétez l'option pour définir plusieurs valeurs. Utilisez lvs -a -o integritysettings VG/LV_rimage_N pour afficher les valeurs configurées. Utilisez lvchange --integritysettings "" pour effacer toutes les valeurs configurées (dm-integrity utilisera ses valeurs par défaut.)

Initialisation de l'intégrité

Lorsque l'intégrité est ajoutée à un LV, le noyau doit initialiser les métadonnées d'intégrité (sommes de contrôle crc32) pour tous les blocs du LV. La vérification de la corruption des données effectuée par dm-integrity ne s'appliquera qu'aux zones du LV qui sont déjà initialisées. La progression de l'initialisation de l'intégrité est signalée par le champ de rapport LV « syncpercent » (et sous la colonne Cpy%Sync de lvs(8)).

Limitations de l'intégrité

Pour contourner certaines limitations, il est possible de supprimer l'intégrité du LV, d'apporter la modification, puis de rajouter l'intégrité. (Les métadonnées d'intégrité devraient être initialisées lors de leur réajout.)

LVM doit pouvoir allouer le sous-LV de métadonnées d'intégrité sur un seul PV déjà utilisé par l'image RAID associée. Cela peut potentiellement poser un problème lors de l'extension de LV si le PV d'origine contenant l'image et les métadonnées d'intégrité est plein. Pour contourner cette limitation, supprimez l'intégrité, étendez le LV, puis ajoutez à nouveau l'intégrité.

Des images RAID supplémentaires peuvent être ajoutées aux LV raid1, mais pas aux autres niveaux RAID.

Un LV raid1 avec intégrité ne peut pas être converti en linéaire (supprimez l'intégrité pour le faire.)

Les LV RAID avec intégrité ne peuvent pas encore être utilisés comme sous-LV avec d'autres types de LV.

Les opérations suivantes ne sont pas encore autorisées sur les LV RAID avec intégrité : lvreduce, pvmove, lvconvert --splitmirrors, lvchange --rebuild.

RÉGLAGE FIN RAID1

Un LV RAID1 peut être configuré de manière à ce que certains périphériques soient évités pour la lecture, tout en continuant à écrire sur tous les périphériques.

lvchange --[raid]writemostly PV[:y|n|t] LV

Le périphérique spécifié sera marqué comme « write mostly » (priorité à l'écriture), ce qui signifie que la lecture de ce périphérique sera évitée, et d'autres périphériques seront préférés pour la lecture (sauf si aucun autre périphérique n'est disponible). Cela minimise les E/S vers le périphérique spécifié.

Si le nom du PV n'a pas de suffixe, l'attribut write mostly est défini. Si le nom du PV a le suffixe :n, l'attribut write mostly est effacé, et le suffixe :t bascule l'état actuel.

L'option write mostly peut être répétée sur la ligne de commande pour modifier plusieurs périphériques à la fois.

Pour afficher le paramètre write mostly actuel, le champ attr de lvs(8) affichera la lettre « w » en 9ème position lorsque write mostly est défini :

lvs -a -o name,attr

Lorsqu'un périphérique est marqué comme write mostly, le nombre maximal d'écritures en attente vers ce périphérique peut être configuré. Une fois le maximum atteint, les écritures ultérieures deviennent synchrones. En mode synchrone, une écriture sur le LV ne sera pas terminée tant que les écritures sur toutes les images miroir ne seront pas terminées.

lvchange --[raid]writebehind Nombre LV

Pour afficher le paramètre write behind actuel, exécutez :

lvs -o name,raid_write_behind

Lorsque write behind n'est pas configuré, ou est défini sur 0, toutes les écritures LV sont synchrones.

PRISE EN CHARGE RAID

La prise en charge RAID consiste à convertir un LV RAID d'un niveau RAID à un autre, par exemple de raid5 à raid6. La modification du niveau RAID est généralement effectuée pour augmenter ou diminuer la résilience aux échecs de périphériques ou pour restriper les LV. Ceci est fait à l'aide de lvconvert en spécifiant le nouveau niveau RAID comme type de LV :

lvconvert --type RaidLevel LV [PVs]

Les conversions de prise en charge RAID les plus courantes et recommandées sont :

linéaire à raid1
Linéaire est une seule image des données LV, et sa conversion en raid1 ajoute une image miroir qui est une copie directe de l'image linéaire d'origine.
stripé/raid0 à raid4/5/6
L'ajout de périphériques de parité à un volume stripé aboutit à raid4/5/6.

Les conversions non naturelles qui ne sont pas recommandées incluent la conversion entre types stripés et non stripés. En effet, les systèmes de fichiers optimisent souvent les modèles d'E/S en fonction des valeurs de striping des périphériques. Si ces valeurs changent, cela peut réduire les performances.

La conversion vers un niveau RAID supérieur nécessite d'allouer de nouveaux sous-LV pour contenir les métadonnées RAID, et de nouveaux sous-LV pour contenir les blocs de parité des données LV. La conversion vers un niveau RAID inférieur supprime les sous-LV qui ne sont plus nécessaires.

La conversion nécessite souvent une synchronisation complète du LV RAID (voir Synchronisation). La conversion vers RAID1 nécessite la copie de tous les blocs de données LV vers N nouvelles images sur de nouveaux périphériques. La conversion vers un niveau RAID de parité nécessite la lecture de tous les blocs de données LV, le calcul de la parité et l'écriture des nouveaux blocs de parité. La synchronisation peut prendre beaucoup de temps en fonction du débit des périphériques utilisés et de la taille du RaidLV. Elle peut dégrader les performances. Les contrôles de débit s'appliquent également à la conversion ; voir --minrecoveryrate et --maxrecoveryrate.

Attention : bien qu'il soit possible de créer des LV stripés avec jusqu'à 128 bandes, un maximum de 64 bandes peuvent être converties en raid0, 63 en raid4/5 et 62 en raid6 en raison des sous-LV de parité ajoutés. Un LV stripé avec un maximum de 32 bandes peut être converti en raid10.

Les conversions de prise en charge suivantes sont actuellement possibles :

entre stripé et raid0.

entre linéaire et raid1.
 •
entre miroir et raid1.
 •

entre stripé/raid0 et raid5.

entre stripé/raid0 et raid6.

Conversions indirectes

La conversion d'un niveau RAID à un autre peut nécessiter plusieurs étapes, en passant d'abord par des niveaux RAID intermédiaires.

linéaire à raid6

Pour convertir un LV de linéaire à raid6 :

1. convertir en raid1 avec deux images

2. convertir en raid5 (interne raid5_ls) avec deux images

3. convertir en raid5 avec trois bandes ou plus

(reshape)
4. convertir en raid6 (interne raid6_ls_6)
5. convertir en raid6 (interne raid6_zr, reshape)

Les commandes pour effectuer les étapes ci-dessus sont :
1. lvconvert --type raid1 --mirrors 1 LV
2. lvconvert --type raid5 LV
3. lvconvert --stripes 3 LV
4. lvconvert --type raid6 LV
5. lvconvert --type raid6 LV

La conversion finale de raid6_ls_6 vers raid6_zr est effectuée pour éviter la réduction potentielle des performances d'écriture/récupération dans raid6_ls_6 en raison du périphérique de parité dédié. raid6_zr fait pivoter les blocs de données et de parité pour éviter cela.

linéaire vers stripé

Pour convertir un LV de linéaire vers stripé :
1. convertir en raid1 avec deux images
2. convertir en raid5_n
3. convertir en raid5_n avec cinq bandes de 128k (reshape)
4. convertir raid5_n en stripé

Les commandes pour effectuer les étapes ci-dessus sont :
1. lvconvert --type raid1 --mirrors 1 LV
2. lvconvert --type raid5_n LV
3. lvconvert --stripes 5 --stripesize 128k LV
4. lvconvert --type striped LV

Le type raid5_n à l'étape 2 est utilisé car il dispose de SubLVs de parité dédiés à la fin, et peut être converti directement en stripé. La taille de bande est augmentée à l'étape 3 pour ajouter de l'espace supplémentaire pour le processus de conversion. Cette étape augmente la taille du LV d'un facteur cinq. Après conversion, cet espace supplémentaire peut être réduit (ou utilisé pour agrandir le système de fichiers en utilisant le LV).

L'inversion de ces étapes convertira un LV stripé en linéaire.

raid6 vers stripé

Pour convertir un LV de raid6_nr en stripé :
1. convertir en raid6_n_6
2. convertir en stripé

Les commandes pour effectuer les étapes ci-dessus sont :
1. lvconvert --type raid6_n_6 LV
2. lvconvert --type striped LV

RESHAPING RAID

Le reshaping RAID consiste à modifier les attributs d'un LV RAID tout en conservant le même niveau RAID. Cela inclut la modification de la disposition RAID, de la taille de bande ou du nombre de bandes.

Lors de la modification de la disposition RAID ou de la taille de bande, aucun nouveau SubLV (MetaLV ou DataLV) n'a besoin d'être alloué, mais les DataLV sont étendus d'une petite quantité (généralement 1 extent). L'espace supplémentaire permet de mettre à jour en toute sécurité les blocs d'une bande, et de ne pas les corrompre en cas de crash. Si un crash survient, le reshaping peut simplement être redémarré.

(Si les blocs d'une bande étaient mis à jour sur place, un crash pourrait les laisser partiellement mis à jour et corrompus. Au lieu de cela, une bande existante est mise en veille, lue, modifiée dans sa disposition, et la nouvelle bande est écrite dans un espace libre. Une fois cela fait, la nouvelle bande est déverrouillée et utilisée.)

NAME

lvconvert — Convert LVM logical volumes between various on-disk layouts

DESCRIPTION

This command can convert between different on-disk layouts for logical volumes. This includes converting linear mode volumes to RAID1, RAID5, RAID6, RAID10, RAID1E, RAID0, or striped volumes. It can also convert RAID volumes back to linear or mirror modes. It can also convert between different RAID types (e.g. RAID5 to RAID6).

The conversion process can take a significant amount of time and may impact system performance during the operation.

USAGE

lvconvert [options] LogicalVolumePath
lvconvert [options] LogicalVolumePath?LogicalVolumePath [...]

The command can be used to convert various volume types. The options depend on the source and target volume types.

Below are some common examples of conversion:

# lvconvert --type raid1 vg/lv
  Logical volume vg/lv successfully converted.

This converts a linear logical volume `vg/lv` to a RAID1 mirrored logical volume. If the source volume is already active, LVM will attempt to perform an online conversion, which may be slower and more resource-intensive. If the source volume is inactive, LVM will perform an offline conversion.

# lvconvert --type mirror --mirrortype sync vg/lv
  Logical volume vg/lv successfully converted.

This converts a linear logical volume `vg/lv` to a mirrored logical volume using synchronous mirroring. This is identical to the previous example, as synchronous mirroring is the default for RAID1.

# lvconvert --type raid5 --stripes 3 --poolmetadatasize 128m vg/lv
  Round down to nearest allocation unit.
  Logical volume vg/lv successfully converted.

This converts a linear logical volume `vg/lv` to RAID5 with 3 data stripes (meaning 4 total devices, 3 data + 1 parity). A pool metadata size is specified to manage the metadata for the RAID conversion. The size is rounded down to the nearest allocation unit.

# lvconvert --type raid5_ls --stripes 5 vg/lv
  This will convert the volume to RAID5 left symmetric with 5 data stripes.
  It requires 6 devices (5 data + 1 parity).
  If you have fewer devices, the conversion may fail or require resizing.
  Logical volume vg/lv successfully converted.

This example converts a volume to RAID5 left symmetric with 5 data stripes. The command implicitly checks the number of available devices. It will inform the user if the required number of devices is not available.

Mind the facts that stripes are removed thus the capacity of the RaidLV will shrink and that changing the RaidLV layout will influence its performance.

"lvconvert --stripes 1 vg/lv" for converting to 1 stripe will inform upfront about the reduced size to allow for resizing the content or growing the RaidLV before actually converting to 1 stripe. The --force option is needed to allow stripe removing conversions to prevent data loss.

Of course any interim step can be the intended last one (e.g. striped → raid1).

HISTORY

The 2.6.38-rc1 version of the Linux kernel introduced a device-mapper target to interface with the software RAID (MD) personalities. This provided device-mapper with RAID 4/5/6 capabilities and a larger development community. Later, support for RAID1, RAID10, and RAID1E (RAID10 variants) were added. Support for these new kernel RAID targets was added to LVM version 2.02.87. The capabilities of the LVM raid1 type have surpassed the old mirror type. raid1 is now recommended instead of mirror. raid1 became the default for mirroring in LVM version 2.02.100.
