LVM(8) Manuel du gestionnaire système LVM(8)

NOM

lvm — Outils LVM

SYNTAXE

lvm [commande|fichier]

DESCRIPTION

Le Gestionnaire de Volumes Logiques (LVM) fournit des outils pour créer des périphériques de blocs virtuels à partir de périphériques physiques. Les périphériques virtuels peuvent être plus faciles à gérer que les périphériques physiques et peuvent offrir des fonctionnalités dépassant celles fournies par les périphériques physiques eux-mêmes. Un Groupe de Volumes (VG) est une collection d'un ou plusieurs périphériques physiques, chacun appelé Volume Physique (PV). Un Volume Logique (LV) est un périphérique de bloc virtuel qui peut être utilisé par le système ou les applications. Chaque bloc de données dans un LV est stocké sur un ou plusieurs PV dans le VG, selon des algorithmes implémentés par Device Mapper (DM) dans le noyau.

La commande lvm, et les autres commandes listées ci-dessous, sont les outils en ligne de commande pour LVM. Une page de manuel distincte décrit chaque commande en détail.

Si lvm est appelé sans arguments, il présente une invite readline (en supposant qu'il ait été compilé avec le support readline). Les commandes LVM peuvent être entrées interactivement à cette invite avec les fonctionnalités readline, y compris l'historique et la complétion des noms de commande et des options. Référez-vous à readline(3) pour plus de détails.

Si lvm est appelé avec argv[0] défini sur le nom d'une commande LVM spécifique (par exemple, en utilisant un lien physique ou symbolique), il agit comme cette commande.

Lors de l'invocation, lvm exige que seuls les descripteurs de fichiers standard stdin, stdout et stderr soient disponibles. Si d'autres sont trouvés, ils sont fermés et des messages sont émis pour avertir de la fuite. Cet avertissement peut être supprimé en définissant la variable d'environnement LVM_SUPPRESS_FD_WARNINGS.

Lorsque les commandes prennent des noms de VG ou LV comme arguments, le nom de chemin complet est facultatif. Un LV appelé "lvol0" dans un VG appelé "vg0" peut être spécifié comme "vg0/lvol0". Lorsqu'une liste de VG est requise mais laissée vide, une liste de tous les VG sera substituée. Lorsqu'une liste de LV est requise mais qu'un VG est donné, une liste de tous les LV de ce VG sera substituée. Ainsi, lvdisplay vg0 affichera tous les LV de "vg0".

Un fichier contenant un script simple avec une commande par ligne peut également être donné en ligne de commande. Le script peut également être exécuté directement si la première ligne est #! suivie du chemin absolu de lvm.

Les tirets supplémentaires dans les noms d'options sont ignorés. Par exemple, --readonly et --read-only sont tous deux acceptés.

NOMS VALIDES

Les caractères valides pour les noms de VG et LV sont : a–z A–Z 0–9 + _ . -

Les noms de VG ne peuvent pas commencer par un trait d'union. Le nom d'un nouveau LV ne peut pas non plus commencer par un trait d'union. Cependant, si le paramètre de configuration metadata/record_lvs_history est activé, alors un nom de LV avec un trait d'union comme préfixe indique que, bien que le LV ait été supprimé, il est toujours suivi car il fait partie de l'historique d'au moins un LV qui est toujours présent. Cela aide à enregistrer l'ascendance des snapshots minces même après la suppression de certains liens dans la chaîne. Une référence au LV historique 'lvol1' dans le VG 'vg00' serait 'vg00/-lvol1' ou juste '-lvol1' si le VG est déjà défini. (La forme de ce dernier doit être précédée de '--' pour terminer le traitement des options de ligne de commande avant d'atteindre cet argument.)

Il existe également divers noms réservés qui sont utilisés interne par LVM et qui ne peuvent pas être utilisés comme noms de LV ou de VG. Un VG ne peut pas être appelé quoi que ce soit qui existe dans /dev/ au moment de sa création, ni ne peut être appelé '.' ou '..'. Un LV ne peut pas être appelé '.', '..', 'snapshot' ou 'pvmove'. Le nom du LV ne peut pas non plus contenir l'une des chaînes suivantes : '_cdata', '_cmeta', '_corig', '_iorig', '_mimage', '_mlog', '_pmspare', '_rimage', '_rmeta', '_tdata', '_tmeta', '_vdata', '_vorigin' ou '_wcorig'. Un répertoire portant le nom de chaque groupe de volumes est créé sous /dev lorsque l'un de ses volumes logiques est activé. Chaque volume logique actif est accessible à partir de ce répertoire sous forme de lien symbolique menant à un nœud de périphérique. Les liens ou nœuds dans /dev/mapper sont destinés uniquement à un usage interne et le format précis et l'échappement peuvent changer entre les versions et les distributions. Les autres logiciels et scripts doivent utiliser le format /dev/NomDuVolumeGroupe/NomDuVolumeLogique pour réduire le risque d'avoir besoin de modifications lors de la mise à jour du logiciel. Si vous avez besoin de traiter les noms de nœuds dans /dev/mapper, vous pouvez utiliser dmsetup splitname pour séparer le VG d'origine, le LV et les noms de couches internes.

NOMS UNIQUES

Les noms de VG doivent être uniques. vgcreate produira une erreur si le nom de VG spécifié correspond à un nom de VG existant. Cependant, il existe des cas où différents VG du même nom peuvent apparaître à LVM, par exemple, après le déplacement de disques ou la modification de filtres.

Lorsque des VG du même nom existent, les commandes opérant sur tous les VG incluront tous les VG du même nom. Si le nom de VG ambigu est spécifié sur la ligne de commande, la commande produira une erreur. L'erreur indique que plusieurs VG existent avec le nom spécifié. Pour traiter spécifiquement l'un des VG, l'option --select doit être utilisée avec l'UUID du VG souhaité : --select vg_uuid=<uuid>

Une exception est si tous les VG portant le nom partagé, à l'exception d'un seul, sont étrangers (voir lvmsystemid(7)). Dans ce cas, le VG qui n'est pas étranger est supposé être le VG prévu et est traité.

Les noms de LV sont uniques au sein d'un VG. Le nom d'un LV historique ne peut pas être réutilisé tant que le LV historique lui-même n'a pas été supprimé ou renommé.

TAGS

Les tags sont des chaînes définies par l'utilisateur qui peuvent être attachées aux PV, VG et LV. Les tags peuvent être affichés avec les commandes pvs/vgs/lvs -o tags. Certaines commandes accepteront un nom de tag à la place d'un nom de PV, VG ou LV. Dans ces cas, la commande opérera sur chaque PV/VG/LV avec le tag donné. Les tags doivent être précédés de @ pour éviter toute ambiguïté.
Les caractères autorisés dans les tags sont : A–Z a–z 0–9 _ + . - / = ! : # &

ALLOCATION

Lorsqu'une opération nécessite d'allouer des extentions physiques pour un ou plusieurs volumes logiques, les outils procèdent comme suit :

Tout d'abord, ils génèrent l'ensemble complet des extentions physiques non allouées dans le groupe de volumes. Si des plages d'extentions physiques sont fournies à la fin de la ligne de commande, seules les extentions physiques non allouées dans ces plages sur les volumes physiques spécifiés sont prises en compte.

Ensuite, ils essaient chaque politique d'allocation tour à tour, en commençant par la politique la plus stricte (contiguous) et en terminant par la politique d'allocation spécifiée à l'aide de --alloc ou définie comme valeur par défaut pour le volume logique ou le groupe de volumes concerné. Pour chaque politique, en travaillant à partir de l' extensão logique de numéro le plus bas de l'espace vide du volume logique qui doit être rempli, ils allouent autant d'espace que possible selon les restrictions imposées par la politique. Si plus d'espace est nécessaire, ils passent à la politique suivante.

Les restrictions sont les suivantes :

Contiguous exige que l'emplacement physique de toute extension logique qui n'est pas la première extension logique d'un volume logique soit adjacente à l'emplacement physique de l'extension logique qui la précède immédiatement.

Cling exige que le volume physique utilisé pour toute extension logique à ajouter à un volume logique existant soit déjà utilisé par au moins une extension logique antérieure dans ce volume logique. Si le paramètre de configuration allocation/cling_tag_list est défini, alors deux volumes physiques sont considérés comme correspondants si l'un des tags listés est présent sur les deux volumes physiques. Cela permet aux groupes de volumes physiques ayant des propriétés similaires (telles que leur emplacement physique) d'être tagués et traités comme équivalents à des fins d'allocation.

Lorsqu'un volume logique est strippé ou mis en miroir, les restrictions ci-dessus sont appliquées indépendamment à chaque stripe ou image miroir (branche) qui nécessite de l'espace.

Normal ne choisira pas une extension physique qui partage le même volume physique qu'une extension logique déjà allouée à un volume logique parallèle (c'est-à-dire une branche ou une image miroir différente) au même décalage dans ce volume logique parallèle.

Lors de l'allocation d'un journal de miroir en même temps que des volumes logiques pour contenir les données du miroir, Normal essaiera d'abord de sélectionner des volumes physiques différents pour le journal et les données. Si cela n'est pas possible et que le paramètre de configuration allocation/mirror_logs_require_separate_pvs est défini sur 0, il permettra alors au journal de partager des volumes physiques avec une partie des données.

Lors de l'allocation de métadonnées de pool mince, des considérations similaires à celles d'un journal de miroir dans le dernier paragraphe s'appliquent en fonction de la valeur du paramètre de configuration allocation/thin_pool_metadata_require_separate_pvs.

Si vous vous fiez à un comportement de mise en page au-delà de ce qui est documenté ici, sachez qu'il pourrait changer dans les futures versions du code.

Par exemple, si vous fournissez sur la ligne de commande deux volumes physiques vides qui ont un nombre identique d'extensions libres disponibles pour l'allocation, le code actuel considère l'utilisation de chacun d'eux dans l'ordre où ils sont listés, mais il n'y a aucune garantie que les futures versions maintiendront cette propriété. S'il est important d'obtenir une mise en page spécifique pour un volume logique particulier, vous devez le construire par une séquence d'étapes lvcreate(8) et lvconvert(8) de telle sorte que les restrictions décrites ci-dessus appliquées à chaque étape ne laissent aucun choix aux outils concernant la mise en page.

Pour visualiser le fonctionnement actuel du processus d'allocation dans un cas spécifique, lisez la sortie de journalisation de débogage, par exemple en ajoutant -vvvv à une commande.

TYPES DE VOLUMES LOGIQUES

Certains types de volumes logiques sont simples à créer et peuvent être réalisés avec une seule commande lvcreate(8). Les types de volumes logiques linéaires et strippés en sont un exemple. D'autres types de volumes logiques peuvent nécessiter plus d'une commande pour être créés. Les types cache (lvmcache(7)) et de provisionnement fin (lvmthin(7)) en sont des exemples.

DIAGNOSTICS

Tous les outils retournent un code de statut zéro en cas de succès ou un code non nul en cas d'échec. Les codes non nuls distinguent uniquement entre les grandes catégories de commandes non reconnues, les problèmes de traitement des arguments de ligne de commande et tout autre échec. LVM restant en cours de développement actif, le code utilisé dans un cas spécifique change occasionnellement entre les versions. Le texte des messages peut également changer.

Répertoire contenant lvm.conf(5) et d'autres fichiers système LVM. Par défaut, "/etc/lvm".
LVM_SUPPRESS_FD_WARNINGS
Supprimer les avertissements concernant les descripteurs de fichiers inattendus passés à LVM.
LVM_SUPPRESS_SYSLOG
Supprimer la prise de contact avec syslog.
LVM_VG_NAME
Le nom du groupe de volumes supposé pour toute référence à un volume logique qui ne spécifie pas de chemin. Non défini par défaut.
LVM_LVMPOLLD_PIDFILE
Chemin vers le fichier qui stocke l'identifiant du processus lvmpolld.
LVM_LVMPOLLD_SOCKET
Chemin vers le socket utilisé pour communiquer avec lvmpolld.
LVM_LOG_FILE_EPOCH
Une chaîne de caractères d'un maximum de 32 lettres ajoutée au nom du fichier journal et suivie de l'identifiant du processus et d'un horodatage de démarrage au format "_%s_%d_%llu". Lorsqu'elle est définie, chaque processus enregistre dans un fichier séparé.
LVM_LOG_FILE_MAX_LINES
Si plus de lignes que ce nombre sont envoyées au fichier journal, la commande est interrompue. Les tests automatisés utilisent cela pour terminer les commandes en boucle.
LVM_EXPECTED_EXIT_STATUS
Le statut attendu lors de la sortie du processus. Utilisez ">N" pour faire correspondre tout statut supérieur à N. Si le statut de sortie réel correspond et qu'un fichier journal a été produit, il est supprimé. LVM_LOG_FILE_EPOCH et LVM_EXPECTED_EXIT_STATUS permettent ensemble aux scripts de test automatisés de supprimer les données de journal non intéressantes.
LVM_SUPPRESS_LOCKING_FAILURE_MESSAGES
Utilisé pour supprimer les messages d'avertissement lorsque le verrouillage configuré n'est pas disponible.
DM_ABORT_ON_INTERNAL_ERRORS
Interrompre le traitement si le code détecte une erreur interne non fatale.
DM_DISABLE_UDEV
Éviter l'interaction avec udev. LVM gérera les nœuds pertinents dans /dev directement.
DM_DEBUG_WITH_LINE_NUMBERS
Ajoute le nom du fichier source et le numéro de ligne du code au début des débogages de libdm.
