NOM

lvmcache — Cache LVM

DESCRIPTION

lvm(8) inclut deux types de mise en cache qui peuvent être utilisés pour améliorer les performances d'un Volume Logique (LV). Lors de la mise en cache, des sous-ensembles variables des données d'un LV sont temporairement stockés sur un périphérique plus petit et plus rapide (par exemple, un SSD) pour améliorer les performances du LV.

Pour ce faire avec lvm, un nouveau LV spécial est d'abord créé à partir du périphérique plus rapide. Ce LV contiendra le cache. Ensuite, le nouveau LV rapide est attaché au LV principal au moyen d'une commande lvconvert. lvconvert insère l'une des cibles de mise en cache du device mapper dans le chemin d'E/S du LV principal. La cible du device mapper combine le LV principal et le LV rapide en un périphérique hybride qui ressemble au LV principal, mais offre de meilleures performances. Pendant que le LV principal est utilisé, des parties de ses données seront stockées temporairement et de manière transparente sur le LV rapide spécial.

Les deux types de mise en cache sont :

•
Une cache des points chauds en lecture et écriture, utilisant le module noyau dm-cache. Cette cache suit les modèles d'accès et ajuste délibérément son contenu de sorte que les parties couramment utilisées du LV principal soient susceptibles d'être trouvées sur le stockage rapide. LVM fait référence à cela en utilisant le type de LV cache.
•
Une cache en écriture, utilisant le module noyau dm-writecache. Cette cache peut être utilisée avec des périphériques SSD ou PMEM pour accélérer toutes les écritures sur le LV principal. Les données lues depuis le LV principal ne sont pas stockées dans la cache, seulement les nouvelles données écrites. LVM fait référence à cela en utilisant le type de LV writecache.

UTILISATION

1. Identifier le LV principal qui nécessite une mise en cache

Le LV principal peut déjà exister et se trouve sur des périphériques plus grands et plus lents. Un LV principal serait créé avec une commande comme :

# lvcreate -n main -L Taille vg /dev/slow_hhd

2. Identifier le LV rapide à utiliser comme cache

Un LV rapide est créé en utilisant un ou plusieurs périphériques rapides, comme un SSD. Ce LV spécial sera utilisé pour stocker la cache :

# lvcreate -n fast -L Taille vg /dev/fast_ssd
# lvs -a
  LV   Attr       Type   Devices
  fast -wi------- linear /dev/fast_ssd
  main -wi------- linear /dev/slow_hhd

3. Commencer la mise en cache du LV principal

Pour commencer la mise en cache du LV principal, convertissez le LV principal au type de mise en cache souhaité et spécifiez le LV rapide à utiliser comme cache :

en utilisant dm-cache (avec cachepool) :

# lvconvert --type cache --cachepool fast vg/main

en utilisant dm-cache (avec cachevol) :

# lvconvert --type cache --cachevol fast vg/main

en utilisant dm-writecache (avec cachevol) :

# lvconvert --type writecache --cachevol fast vg/main

Pour plus d'alternatives, voir :
raccourci commande dm-cache
dm-cache avec des LVs de données et de métadonnées séparés

4. Afficher les LVs

Une fois que le LV rapide a été attaché au LV principal, lvm rapporte le type du LV principal comme cache ou writecache selon le type utilisé. Pendant l'attachement, le LV rapide est caché et renommé avec un suffixe _cvol ou _cpool. Il est affiché par lvs -a. Le LV _corig ou _wcorig représente le LV original sans le cache.

en utilisant dm-cache (avec cachepool) :

# lvs -ao+devices
  LV                 Pool         Type       Devices
  main               [fast_cpool] cache      main_corig(0)
  [fast_cpool]                    cache-pool fast_pool_cdata(0)
  [fast_cpool_cdata]              linear     /dev/fast_ssd
  [fast_cpool_cmeta]              linear     /dev/fast_ssd
  [main_corig]                    linear     /dev/slow_hhd

en utilisant dm-cache (avec cachevol) :

# lvs -ao+devices
  LV           Pool        Type   Devices
  main         [fast_cvol] cache  main_corig(0)
  [fast_cvol]              linear /dev/fast_ssd
  [main_corig]             linear /dev/slow_hhd

en utilisant dm-writecache (avec cachevol) :

# lvs -ao+devices
  LV            Pool        Type       Devices
  main          [fast_cvol] writecache main_wcorig(0)
  [fast_cvol]               linear     /dev/fast_ssd
  [main_wcorig]             linear     /dev/slow_hhd

5. Utiliser le LV principal

Utilisez le LV jusqu'à ce que le cache ne soit plus souhaité, ou qu'il doive être modifié.

6. Arrêter la mise en cache

Pour arrêter la mise en cache du LV principal et supprimer également le pool de cache inutile, utilisez --uncache :

# lvconvert --uncache vg/main
# lvs -a
  LV   VG Attr       Type   Devices
  main vg -wi------- linear /dev/slow_hhd

Pour arrêter la mise en cache du LV principal, séparez le LV rapide du LV principal. Cela ramène le type du LV principal à ce qu'il était avant l'attachement du cache.

# lvconvert --splitcache vg/main
# lvs -a
  LV   VG Attr       Type   Devices
  fast vg -wi------- linear /dev/fast_ssd
  main vg -wi------- linear /dev/slow_hhd

7. Créer un nouveau LV avec mise en cache

Un nouveau LV peut être créé avec la mise en cache attachée au moment de la création en utilisant la commande suivante :

# lvcreate --type cache|writecache -n Nom -L Taille
	--cachedevice /dev/fast_ssd vg /dev/slow_hhd

Le LV principal est créé avec le Nom et la Taille spécifiés à partir du slow_hhd. Un LV rapide caché est créé sur le fast_ssd et est ensuite attaché au nouveau LV principal. Si le fast_ssd est inutilisé, le disque entier sera utilisé comme cache, sauf si l'option --cachesize est utilisée pour spécifier une taille pour le LV rapide. L'option --cachedevice peut être répétée pour utiliser plusieurs disques pour le LV rapide.

OPTIONS

option arguments

--cachepool CachePoolLV|LV
Passez cette option à un pool de cache LV ou à un LV standard. Lors de l'utilisation d'un pool de cache, lvm place les données de cache et les métadonnées de cache sur différents LVs. Les deux LVs ensemble sont appelés un pool de cache. Cela offre de meilleures performances pour dm-cache et permet une sélection spécifique de l'emplacement et du type de segment pour les volumes de données et de métadonnées. Un pool de cache est représenté par un type spécial de LV qui ne peut pas être utilisé directement. Si un LV standard est passé avec cette option, lvm le convertira d'abord en pool de cache en le combinant avec un autre LV à utiliser pour les métadonnées. Cette option peut être utilisée avec dm-cache.
--cachevol LV
Passez cette option à un LV rapide qui devrait être utilisé pour stocker le cache. Avec un cachevol, les données de cache et les métadonnées sont stockées dans différentes parties du même LV rapide. Cette option peut être utilisée avec dm-writecache ou dm-cache.
--cachedevice PV
Cette option peut être utilisée à la place de --cachevol, auquel cas un cachevol LV sera créé en utilisant le périphérique spécifié. Cette option peut être répétée pour créer un cachevol utilisant plusieurs périphériques, ou un nom d'étiquette peut être spécifié, auquel cas le cachevol sera créé en utilisant l'un des périphériques avec l'étiquette donnée. Si un périphérique de cache nommé est inutilisé, le périphérique entier sera utilisé pour créer le cachevol. Pour créer un cachevol d'une taille spécifique à partir des périphériques de cache, incluez l'option --cachesize.

dm-cache taille bloc

Un pool de cache aura une taille de bloc logique de 4096 octets s'il est créé sur un périphérique avec une taille de bloc logique de 4096 octets.

Si un LV principal a une taille de bloc logique de 512 (avec un système de fichiers xfs existant utilisant cette taille), il ne peut pas utiliser un pool de cache avec une taille de bloc logique de 4096. Si le pool de cache est attaché, le LV principal échouera probablement au montage.

Pour éviter ce problème, utilisez une option mkfs pour spécifier une taille de bloc de 4096 pour le système de fichiers,

o joindre le pool de cache avant d'exécuter mkfs.

dm-writecache taille de bloc

La taille de bloc de dm-writecache peut être de 4096 octets (par défaut) ou de 512 octets. Le réglage par défaut de 4096 offre de meilleures performances et doit être utilisé sauf lorsque 512 est nécessaire pour des raisons de compatibilité. La taille de bloc de dm-writecache est spécifiée avec --cachesettings block_size=4096|512 lors du démarrage du cache.

Lorsqu'un système de fichiers comme xfs existe déjà sur le LV principal avant la mise en cache, et que le système de fichiers utilise une taille de bloc de 512, la taille de bloc de writecache doit être réglée sur 512. (Le système de fichiers échouera probablement au montage si une taille de bloc de writecache de 4096 est utilisée dans ce cas.)

Vérifiez la taille de secteur xfs pendant que le système de fichiers est monté :

# xfs_info /dev/vg/main
Regardez sectsz=512 ou sectsz=4096

La taille de bloc de writecache doit être choisie pour correspondre à la valeur xfs sectsz.

Il est également possible de spécifier une taille de secteur de 4096 à mkfs.xfs lors de la création du système de fichiers. Dans ce cas, la taille de bloc de writecache de 4096 peut être utilisée.

La taille de bloc de writecache est affichée par la commande :

# lvs -o writecacheblocksize VG/LV

dm-writecache utilisation de la mémoire

La quantité de mémoire système principale utilisée par dm-writecache peut être un facteur lors de la sélection de la taille du cachevol de writecache et de la taille de bloc de writecache.

•
taille de bloc de writecache 4096 : chaque 100 Gio de cachevol de writecache utilise un peu plus de 2 Gio de mémoire système.
•
taille de bloc de writecache 512 : chaque 100 Gio de cachevol de writecache utilise un peu plus de 16 Gio de mémoire système.

dm-writecache réglages

Pour spécifier les réglages ajustables de dm-writecache sur la ligne de commande, utilisez :
--cachesettings 'option=N' ou
--cachesettings 'option1=N option2=N ...'

Par exemple, --cachesettings 'high_watermark=90 writeback_jobs=4'.

Pour inclure les réglages lors du démarrage du cache, exécutez :

# lvconvert --type writecache --cachevol fast \
	--cachesettings 'option=N' vg/main

Pour modifier les réglages d'un writecache existant, exécutez :

# lvchange --cachesettings 'option=N' vg/main

Pour effacer tous les réglages appliqués, exécutez :

# lvchange --cachesettings '' vg/main

Pour afficher les réglages appliqués à un LV de writecache, exécutez :

# lvs -o cachesettings vg/main

Les réglages ajustables sont :

high_watermark = <pourcentage>
Démarrer la réécriture lorsque l'utilisation du cache d'écriture atteint ce pourcentage (0-100).
low_watermark = <pourcentage>
Arrêter la réécriture lorsque l'utilisation du cache d'écriture atteint ce pourcentage (0-100).
writeback_jobs = <nombre>
Limiter le nombre de blocs en cours de traitement lors de la réécriture. Définir cette valeur réduit le débit de réécriture, mais peut améliorer la latence des requêtes de lecture.
autocommit_blocks = <nombre>
Lorsque l'application écrit cette quantité de blocs sans émettre la requête FLUSH, les blocs sont automatiquement validés.
autocommit_time = <millisecondes>
Les données sont automatiquement validées si ce temps s'écoule et qu'aucune requête FLUSH n'est reçue.
fua = 0|1
Utiliser le drapeau FUA lors de l'écriture de données de la mémoire persistante vers le périphérique sous-jacent. Applicable uniquement à la mémoire persistante.
nofua = 0|1
Ne pas utiliser le drapeau FUA lors de la réécriture des données et envoyer la requête FLUSH par la suite. Certains périphériques sous-jacents offrent de meilleures performances avec fua, d'autres avec nofua. Des tests sont nécessaires pour déterminer lequel. Applicable uniquement à la mémoire persistante.
cleaner = 0|1
Définir cleaner=1 active le mode nettoyeur de writecache dans lequel les données sont progressivement vidées du cache. Si cela est fait avant de détacher le writecache, la commande splitcache aura peu ou pas de vidange à effectuer. Si cela n'est pas fait au préalable, la commande splitcache active le mode nettoyeur et attend que la vidange soit terminée avant de détacher le writecache. L'ajout de cleaner=0 à la commande splitcache ignorera le mode nettoyeur, et toute vidange nécessaire sera effectuée lors de la suspension du périphérique.
max_age = <millisecondes>
Spécifie l'âge maximum d'un bloc en millisecondes. Si un bloc est stocké dans le cache trop longtemps, il sera écrit sur le périphérique sous-jacent et nettoyé.
metadata_only = 0|1
Seules les métadonnées sont promues dans le cache. Cette option améliore les performances pour les charges de travail REQ_META plus lourdes.
pause_writeback = <millisecondes>
Suspendre la réécriture s'il y a eu des opérations d'écriture redirigées vers le volume d'origine dans les dernières millisecondes.

dm-writecache utilisation des profils de métadonnées

En plus de spécifier les réglages de writecache sur la ligne de commande, ils peuvent également être définis dans lvm.conf(5), ou dans un fichier de profil, en utilisant la structure de configuration allocation/cache_settings/writecache illustrée ci-dessous.

Il est possible de préparer un certain nombre de fichiers de profil différents dans le répertoire /etc/lvm/profile et de spécifier le nom du fichier de profil lors du démarrage de writecache.

Exemple

# cat <<EOF > /etc/lvm/profile/cache_writecache.profile
allocation {
cache_settings {
writecache {
high_watermark=60
writeback_jobs=1024
}
}
}
EOF
# lvcreate -an -L10G --name fast vg /dev/fast_ssd
# lvcreate --type writecache -L10G --name main  --cachevol fast \
   --metadataprofile cache_writecache vg /dev/slow_hdd

dm-cache avec LVs de données et de métadonnées séparés

La manière préférée d'utiliser dm-cache est de placer les métadonnées de cache et les données de cache sur des LVs séparés. Pour ce faire, un "pool de cache" est créé, qui est un LV spécial faisant référence à deux LVs fils, un pour les données et un pour les métadonnées.

Pour créer un pool de cache d'une taille de données donnée et laisser lvm2 calculer la taille de métadonnées appropriée :

# lvcreate --type cache-pool -L DataSize -n fast vg /dev/fast_ssd1

Pour créer un pool de cache à partir d'un LV séparé et laisser lvm2 calculer la taille de métadonnées de cache appropriée :

# lvcreate -n fast -L DataSize vg /dev/fast_ssd1
# lvconvert --type cache-pool vg/fast /dev/fast_ssd1

Pour créer un pool de cache à partir de deux LVs séparés :

# lvcreate -n fast -L DataSize vg /dev/fast_ssd1
# lvcreate -n fastmeta -L MetadataSize vg /dev/fast_ssd2
# lvconvert --type cache-pool --poolmetadata fastmeta vg/fast

Utilisez ensuite le LV de pool de cache pour démarrer la mise en cache du LV principal :

# lvconvert --type cache --cachepool fast vg/main

Une variation de la même procédure crée automatiquement un pool de cache lors du démarrage de la mise en cache. Pour ce faire, utilisez un LV standard comme --cachepool (qui contiendra les données du cache) et un autre LV standard comme --poolmetadata (qui contiendra les métadonnées du cache). LVM créera un LV de pool de cache à partir des deux LVs spécifiés et utilisera ce pool de cache pour démarrer la mise en cache du LV principal.

# lvcreate -n fast -L DataSize vg /dev/fast_ssd1
# lvcreate -n fastmeta -L MetadataSize vg /dev/fast_ssd2
# lvconvert --type cache --cachepool fast \
        --poolmetadata fastmeta vg/main

dm-cache modes de cache

Le mode de cache dm-cache par défaut est "writethrough". Writethrough garantit que toute donnée écrite sera stockée à la fois dans le cache et sur le LV d'origine. La perte d'un périphérique associé au cache dans ce cas n'entraînerait pas la perte de données.

Un second mode de cache est "writeback". Writeback retarde l'écriture des blocs de données du cache vers le LV d'origine. Ce mode augmentera les performances, mais la perte d'un périphérique de cache peut entraîner une perte de données.

Avec l'option --cachemode, le mode de cache peut être défini lors du démarrage de la mise en cache, ou modifié sur un LV déjà mis en cache. Le mode de cache actuel peut être affiché avec l'option de rapport cache_mode :

# lvs -o+cache_mode VG/LV

lvm.conf(5) allocation/cache_mode – définit le mode de cache par défaut.

# lvconvert --type cache --cachemode writethrough \
        --cachepool fast vg/main
# lvconvert --type cache --cachemode writethrough \
        --cachevol fast vg/main

dm-cache taille de bloc

La taille des blocs de données gérés par dm-cache peut être spécifiée avec l'option --chunksize lors du démarrage de la mise en cache. L'unité par défaut est KiB. La valeur doit être un multiple de 32 KiB, comprise entre 32 KiB et 1 Gio. Les blocs de cache plus grands que 512 KiB ne devraient être utilisés que lorsque nécessaire.

L'utilisation d'une taille de bloc trop grande peut entraîner une utilisation inutile du cache, où de petites lectures et écritures provoquent le stockage de grandes sections d'un LV dans le cache. Cela peut également nécessiter d'augmenter le seuil de migration qui est par défaut à 2048 secteurs (1 Mio). Lvm2 garantit que le seuil de migration est d'au moins 8 blocs. Cela peut dans certains cas entraîner une charge de bande passante très élevée lors du transfert de données entre le LV de cache et son LV d'origine de cache. Cependant, choisir une taille de bloc trop petite peut entraîner plus de surcharge lors de la gestion des nombreux blocs qui sont mappés dans le cache. La surcharge peut inclure un temps CPU excessif pour rechercher des blocs, ainsi qu'une mémoire excessive pour suivre les blocs.

Commande pour afficher la taille de bloc :

# lvs -o+chunksize VG/LV

lvm.conf(5) allocation/cache_pool_chunk_size

c

NOM

lvmcache — Étendre les volumes logiques avec une mise en cache.

DESCRIPTION

lvmcache est une commande qui étend la fonctionnalité de lvm(8) pour permettre la création et la gestion de volumes logiques (LVs) en mode cache, qui utilisent un périphérique de stockage rapide (typiquement un SSD) pour accélérer l'accès aux données d'un périphérique de stockage plus lent.

Cette commande crée un nouveau LV de type cache et l'attache à un LV principal existant (origine) pour la mise en cache.

dm-cache taille de bloc

La taille de bloc par défaut est contrôlée par la configuration suivante dans lvm.conf(5) :

allocation/cache_pool_chunk_size

La valeur par défaut est affichée par :

# lvmconfig --type default allocation/cache_pool_chunk_size

Vérification du seuil de migration (en secteurs) d'un LV en cache en cours d'exécution :

# lvs -o+kernel_cache_settings VG/LV

dm-cache paramètres de cache

Pour définir les paramètres de cache dm-cache, utilisez :

--cachesettings 'option1=N option2=N ...'

Pour annuler/supprimer un paramètre de cache et restaurer sa valeur par défaut du noyau, utilisez le mot-clé spécial 'default' comme paramètre d'option :

--cachesettings 'option1=default option2=default ...'

dm-cache paramètre de cache du seuil de migration

La migration des données entre le LV d'origine et le LV de cache utilise de la bande passante. L'utilisateur peut définir une limitation pour éviter qu'une quantité excessive de migration ne se produise à un moment donné. Actuellement, dm-cache ne tient pas compte du trafic d'E/S normal vers les périphériques.

L'utilisateur peut définir le seuil de migration via les paramètres de la politique de cache sous la forme "migration_threshold=<#secteurs>" pour définir le nombre maximum de secteurs migrés. La valeur par défaut est de 2048 secteurs (1 Mio) ou 8 blocs de cache, la valeur la plus grande des deux étant choisie.

Commande pour définir le seuil de migration à 2 Mio (4096 secteurs) :

# lvcreate --cachesettings 'migration_threshold=4096' VG/LV

Commande pour afficher le seuil de migration :

# lvs -o+kernel_cache_settings,cache_settings VG/LV
# lvs -o+chunksize VG/LV

Commande pour restaurer/rétablir la valeur par défaut :

# lvchange --cachesettings 'migration_threshold=default' VG/LV

dm-cache politique de cache

Le sous-système dm-cache a des paramètres supplémentaires par LV : la politique de cache à utiliser, et éventuellement des paramètres ajustables pour la politique de cache. Trois politiques sont actuellement disponibles : "smq" est la politique par défaut, "mq" est une ancienne implémentation, et "cleaner" est utilisé pour forcer le cache à écrire (vider) toutes les écritures mises en cache vers le LV d'origine.

L'ancienne politique "mq" possède un certain nombre de paramètres ajustables. Les valeurs par défaut sont choisies pour être adaptées à la majorité des systèmes, mais dans des circonstances spéciales, la modification des paramètres peut améliorer les performances. Les noyaux plus récents associent cependant cette politique à la politique "smq". Les paramètres de cache utilisés pour configurer la politique "mq" [random_threshold, sequential_threshold, discard_promote_adjustment, read_promote_adjustment, write_promote_adjustment] sont donc silencieusement ignorés et les performances correspondent à "smq".

Avec les options --cachepolicy et --cachesettings, la politique de cache et ses paramètres peuvent être définis lors du démarrage de la mise en cache, ou modifiés sur un LV en cache existant (les deux options peuvent être utilisées ensemble). La politique de cache actuelle et ses paramètres peuvent être affichés avec les options de rapport cache_policy et cache_settings :

# lvs -o+cache_policy,cache_settings VG/LV

Modification de la politique de cache et des paramètres d'un LV existant.

# lvchange --cachepolicy mq --cachesettings \
	'migration_threshold=2048 random_threshold=4' vg/main

lvm.conf(5) allocation/cache_policy – définit la politique de cache par défaut.

lvm.conf(5) allocation/cache_settings – définit les paramètres de cache par défaut.

dm-cache utilisation des profils de métadonnées

Les pools de cache permettent de définir une variété d'options. Beaucoup de ces paramètres peuvent être spécifiés dans lvm.conf ou dans les paramètres de profil. Vous pouvez préparer un certain nombre de profils différents dans le répertoire /etc/lvm/profile et simplement spécifier le nom du fichier de profil de métadonnées lors de la mise en cache d'un LV ou de la création d'un pool de cache. Vérifiez la sortie de :

# lvmconfig --type default --withcomments

pour une description détaillée de tous les paramètres de cache individuels.

Exemple

# cat <<EOF > /etc/lvm/profile/cache_big_chunk.profile
allocation {
cache_pool_metadata_require_separate_pvs=0
cache_pool_chunk_size=512
cache_metadata_format=2
cache_mode="writethrough"
cache_policy="smq"
cache_settings {
smq {
migration_threshold=8192
}
}
}
EOF
# lvcreate --cache -L10G --metadataprofile cache_big_chunk vg/main \
        /dev/fast_ssd
# lvcreate --cache -L10G vg/main --config \
        'allocation/cache_pool_chunk_size=512' /dev/fast_ssd

dm-cache LV de métadonnées de secours

Voir lvmthin(7) pour une description du LV "pool metadata spare". Le même concept est utilisé pour les pools de cache.

dm-cache formats de métadonnées

Il existe deux formats de disque pour les métadonnées dm-cache. Le format de métadonnées peut être spécifié avec --cachemetadataformat lors du démarrage de la mise en cache, et ne peut pas être modifié. Le format 2 a de meilleures performances ; il est plus compact et stocke les bits sales dans une b-tree séparée, ce qui améliore la vitesse d'arrêt du cache. Avec auto, lvm sélectionne la meilleure option fournie par le module noyau dm-cache actuel.

RAID1 périphérique de cache

RAID1 peut être utilisé pour créer le LV rapide contenant le cache afin qu'il puisse tolérer une défaillance de périphérique. (Lors de l'utilisation de dm-cache avec des LV de données et de métadonnées séparés, chacun des sous-LVs peut utiliser RAID1.)

# lvcreate -n main -L Size vg /dev/slow
# lvcreate --type raid1 -m 1 -n fast -L Size vg /dev/ssd1 /dev/ssd2
# lvconvert --type cache --cachevol fast vg/main

dm-cache raccourci de commande

Une seule commande peut être utilisée pour mettre en cache un LV principal avec création automatique d'un pool de cache :

# lvcreate --cache --size CacheDataSize VG/LV [FastPVs]

ou la variante plus longue

# lvcreate --type cache --size CacheDataSize \
        --name NameCachePool VG/LV [FastPVs]

Dans cette commande, le LV spécifié existe déjà et est le LV principal à mettre en cache. La commande crée un nouveau pool de cache de la taille et du nom spécifiés, ou le nom est automatiquement sélectionné dans une séquence lvolX_cpool, en utilisant les PV rapides optionnellement spécifiés (typiquement un SSD). Ensuite, elle attache le nouveau pool de cache au LV principal existant pour commencer la mise en cache.

(Note : assurez-vous que le LV principal spécifié est un LV standard. Si un LV de pool de cache est spécifié par erreur, la commande fait quelque chose de différent.)

(Note : l'option type est interprétée différemment par cette commande que par les commandes lvcreate normales dans lesquelles --type spécifie le type du LV nouvellement créé. Dans ce cas, un LV de type cache-pool est créé, et le LV principal existant est converti en type cache.)
