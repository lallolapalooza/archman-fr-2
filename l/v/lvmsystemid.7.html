NOM

lvmsystemid — ID système LVM

DESCRIPTION

Le système ID de lvm(8) limite l'accès à un groupe de volumes (VG) à un seul hôte. Ceci est utile lorsqu'un VG est placé sur des périphériques de stockage partagés, ou lorsque des périphériques locaux sont visibles à la fois par le système d'exploitation hôte et invité. Dans de tels cas, un VG peut être visible par plusieurs hôtes simultanément, et un mécanisme est nécessaire pour l'empêcher d'être utilisé par plus d'un hôte à la fois.

L'ID système d'un VG identifie un hôte comme propriétaire du VG. L'hôte avec un ID système correspondant peut utiliser le VG et ses LV, tandis que LVM sur d'autres hôtes l'ignorera. Cela protège le VG contre une utilisation accidentelle par d'autres hôtes.

L'ID système est une chaîne qui identifie de manière unique un hôte. Il peut être configuré comme une valeur personnalisée, ou il peut être attribué automatiquement par LVM à l'aide d'un identifiant unique déjà disponible sur l'hôte, par exemple, machine-id ou uname.

Lorsqu'un nouveau VG est créé, l'ID système de l'hôte local est enregistré dans les métadonnées du VG. L'hôte créateur possède alors le nouveau VG, et LVM sur d'autres hôtes l'ignorera. Lorsqu'un VG exporté existant est importé (vgimport), l'ID système de l'hôte local est enregistré dans les métadonnées du VG, et l'hôte importateur possède le VG.

Un VG sans ID système peut être utilisé par LVM sur n'importe quel hôte où les périphériques du VG sont visibles. Lorsque les ID système ne sont pas utilisés, les filtres de périphériques doivent être configurés sur tous les hôtes pour exclure les périphériques du VG de tous les hôtes sauf un.

Un VG étranger est un VG vu par un hôte avec un ID système non correspondant, c'est-à-dire que l'ID système dans les métadonnées du VG ne correspond pas à l'ID système configuré sur l'hôte. Si l'hôte n'a pas d'ID système et que le VG en a un, le VG est étranger et LVM l'ignorera. Si le VG n'a pas d'ID système, l'accès est illimité et LVM peut y accéder depuis n'importe quel hôte, que l'hôte ait un ID système ou non.

Les modifications apportées à l'ID système d'un hôte et à l'ID système d'un VG peuvent être effectuées dans des circonstances limitées (voir vgexport et vgimport). Des modifications inappropriées peuvent entraîner la perte d'accès d'un hôte à son VG, ou la corruption accidentelle d'un VG par accès depuis un hôte non prévu. Même des modifications limitées de l'ID système du VG peuvent ne pas être parfaitement reflétées entre les hôtes. Une vue plus cohérente du stockage partagé nécessite un système de verrouillage inter-hôtes pour coordonner l'accès.

Les caractères valides pour un ID système sont les mêmes que les caractères valides pour un nom de VG. Si un ID système contient des caractères invalides, ces caractères sont omis et les caractères restants sont utilisés. Si un ID système est plus long que la longueur maximale du nom, les caractères jusqu'à la longueur maximale sont utilisés. La longueur maximale d'un ID système est de 128 caractères.

Affiche l'ID système d'un VG pour vérifier s'il est défini :

vgs -o systemid VG

Affiche l'ID système de l'hôte local pour vérifier s'il est configuré :

lvm systemid

Limitations et avertissements

Pour bénéficier pleinement de l'ID système, tous les hôtes doivent avoir un ID système configuré, et tous les VG doivent avoir un ID système défini. Sans aucune méthode pour restreindre l'accès, par exemple l'ID système ou les filtres de périphériques, un VG visible par plusieurs hôtes peut être accidentellement endommagé ou détruit.

•
Un VG sans ID système peut être utilisé sans restriction par n'importe quel hôte où il est visible, même depuis des hôtes qui ont un ID système.
•
De nombreux VG n'auront pas d'ID système défini car LVM ne l'a pas activé par défaut, et même lorsqu'il est activé, de nombreux VG ont été créés avant que la fonctionnalité ne soit ajoutée à LVM ou activée. Un ID système peut être attribué à ces VG en utilisant vgchange --systemid (voir ci-dessous).
•
Deux hôtes ne doivent pas se voir attribuer le même ID système. Le faire irait à l'encontre de l'objectif de distinguer les différents hôtes avec cette valeur.
•
Les PV orphelins (ou périphériques inutilisés) sur stockage partagé ne sont pas protégés par la fonctionnalité d'ID système. Les commandes qui utilisent ces PV, comme vgcreate ou vgextend, ne sont pas empêchées d'effectuer des opérations conflictuelles et de corrompre les PV. Voir la section orphans pour plus d'informations.
•
L'ID système ne protège pas les périphériques d'un VG contre les programmes autres que LVM.
•
Un hôte utilisant une ancienne version de LVM (sans la fonctionnalité d'ID système) ne reconnaîtra pas un ID système défini dans les VG. L'ancien LVM peut lire un VG avec un ID système, mais est empêché d'écrire dans le VG (ou ses LV). La fonctionnalité d'ID système modifie le mode d'écriture d'un VG, le faisant apparaître en lecture seule pour les versions antérieures de LVM.

Cela signifie également que si un hôte rétrograde vers l'ancienne version de LVM, il perdra l'accès à tous les VG qu'il avait créés avec un ID système. Pour éviter cela, l'ID système doit être supprimé des VG locaux avant de rétrograder LVM vers une version sans la fonctionnalité d'ID système.

Types d'accès VG

Un VG local est destiné à être utilisé par un seul hôte.

Un VG partagé ou clusterisé est destiné à être utilisé par plusieurs hôtes.

Ceux-ci peuvent être distingués comme suit :

Illimité :
Un VG local qui n'a pas d'ID système. Ce type de VG n'est pas protégé et est accessible à n'importe quel hôte.
Possédé :
Un VG local auquel un ID système est attribué, tel que vu par l'hôte avec un ID système correspondant (le propriétaire). Ce type de VG est accessible à l'hôte.
Étranger :
Un VG local auquel un ID système est attribué, tel que vu par n'importe quel hôte avec un ID système non correspondant (ou aucun ID système). Il est possédé par un autre hôte. Ce type de VG n'est pas accessible à l'hôte.
Exporté :
Un VG local qui a été exporté avec vgexport et n'a pas d'ID système. Ce type de VG ne peut être accédé que par vgimport qui le transformera en possédé.
Partagé :
Un VG partagé ou « lockd » a le type de verrouillage défini et n'a pas d'ID système. Un VG partagé est destiné à être utilisé sur un stockage partagé à partir de plusieurs hôtes, et n'est accessible qu'aux hôtes utilisant lvmlockd. Applicable uniquement si LVM est compilé avec le support de lvmlockd.
Clusterisé :
Un VG clusterisé ou « clvm » a le drapeau clusterisé défini et n'a pas d'ID système. Un VG clusterisé est destiné à être utilisé sur un stockage partagé à partir de plusieurs hôtes, et n'est accessible qu'aux hôtes utilisant clvmd. Applicable uniquement si LVM est compilé avec le support de clvm.

Configuration de l'ID système de l'hôte

L'ID système de l'hôte lui-même peut être défini de plusieurs manières. La configuration globale de lvm.conf system_id_source définit la méthode que LVM utilisera pour trouver l'ID système local :

none
LVM n'utilisera pas d'ID système. LVM est autorisé à accéder aux VG sans ID système, et créera de nouveaux VG sans ID système. Une system_id_source non définie est équivalente à none.

lvm.conf

global {
    system_id_source = "none"
}
appmachineid
Une dérivation spécifique à LVM de /etc/machine-id est utilisée comme ID système. Voir machine-id(5) pour vérifier si machine-id est disponible sur l'hôte.

lvm.conf

global {
    system_id_source = "appmachineid"
}
machineid
Le contenu de /etc/machine-id est utilisé comme ID système s'il est disponible. (appmachineid est recommandé pour éviter d'exposer le machine-id confidentiel.)

lvm.conf

global {
    system_id_source = "machineid"
}
uname
La chaîne utsname.nodename de uname(2) est utilisée comme ID système. Un uname commençant par "localhost" est ignoré et équivaut à none.

lvm.conf

global {
    system_id_source = "uname"
}
lvmlocal
L'ID système est défini dans lvmlocal.conf local/system_id.

NAME

lvmsystemid — LVM volume group system ID

DESCRIPTION

A system ID is a string that identifies a specific host. LVM uses system IDs to restrict access to Volume Groups (VGs). By default, a VG is only accessible by hosts that have a matching system ID. This prevents accidental or malicious use of VGs by unintended hosts.

A VG's system ID is stored in its metadata. When a VG is created, the system ID of the host running the command is assigned to the VG. This system ID can be overridden at creation time or changed later.

A VG can have no system ID, in which case it is accessible by all hosts. This is the default for VGs created before the system ID feature was introduced, and it is also used for shared or clustered VGs.

System ID Source

The system ID of a host is determined by the configuration parameter global/system_id_source in lvm.conf. The following sources are supported:

none
No system ID is assigned to the host. The host can access VGs with no system ID, but cannot access VGs with a system ID set.
local
The system ID is taken from the local/system_id setting in lvmlocal.conf.

lvmlocal.conf

local {
    system_id = "example_name"
}
file
The system ID is defined in a file specified by lvm.conf global/system_id_file.

lvm.conf

global {
    system_id_source = "file"
    system_id_file = "/path/to/file"
}

Changing system_id_source will likely cause the system ID of the host to change, which will prevent the host from using VGs that it previously used (see extra_system_ids below to handle this.)

If a system_id_source other than none fails to produce a system ID value, it is the equivalent of having none. The host will be allowed to access VGs with no system ID, but will not be allowed to access VGs with a system ID set.

Overriding system ID

In some cases, it may be necessary for a host to access VGs with different system IDs, e.g. if a host's system ID changes, and it wants to use VGs that it created with its old system ID. To allow a host to access VGs with other system IDs, those other system IDs can be listed in lvmlocal.conf local/extra_system_ids.

lvmlocal.conf

local {
    extra_system_ids = [ "my_other_name" ]
}

A safer option may be configuring the extra values as needed on the command line as:
--config 'local/extra_system_ids=["id"]'

vgcreate

In vgcreate, the host running the command assigns its own system ID to the new VG. To override this and set another system ID:

vgcreate --systemid SystemID VG PVs

Overriding the host's system ID makes it possible for a host to create a VG that it may not be able to use. Another host with a system ID matching the one specified may not recognize the new VG without manually rescanning devices.

If the --systemid argument is an empty string (""), the VG is created with no system ID, making it accessible to other hosts (see warnings above.)

report/display

The system ID of a VG is displayed with the "systemid" reporting option.

Report/display commands ignore foreign VGs by default. To report foreign VGs, the --foreign option can be used. This causes the VGs to be read from disk.

vgs --foreign -o +systemid

When a host with no system ID sees foreign VGs, it warns about them as they are skipped. The host should be assigned a system ID, after which standard reporting commands will silently ignore foreign VGs.

vgexport/vgimport

vgexport clears the VG system ID when exporting the VG.

vgimport sets the VG system ID to the system ID of the host doing the import.

vgchange

A host can change the system ID of its own VGs, but the command requires confirmation because the host may lose access to the VG being changed:

vgchange --systemid SystemID VG

The system ID can be removed from a VG by specifying an empty string ("") as the new system ID. This makes the VG accessible to other hosts (see warnings above.)

A host cannot directly change the system ID of a foreign VG.

To move a VG from one host to another, vgexport and vgimport should be used.

To forcibly gain ownership of a foreign VG, a host can temporarily add the foreign system ID to its extra_system_ids list, and change the system ID of the foreign VG to its own. See Overriding system ID above.

shared VGs

A shared VG has no system ID set, allowing multiple hosts to use it via lvmlockd. Changing a VG to shared will clear the existing system ID. Applicable only if LVM is compiled with lvmlockd support.

clustered VGs

A clustered/clvm VG has no system ID set, allowing multiple hosts to use it via clvmd. Changing a VG to clustered will clear the existing system ID. Changing a VG to not clustered will set the system ID to the host running the vgchange command.

creation_host

In vgcreate, the VG metadata field creation_host is set by default to the host's uname. The creation_host cannot be changed, and is not used to control access. When system_id_source is "uname", the system_id and creation_host fields will be the same.

orphans

Orphan PVs are unused devices; they are not currently used in any VG. Because of this, they are not protected by a system ID, and any host can use them. Coordination of changes to orphan PVs is beyond the scope of system ID. The same is true of any block device that is not a PV.
