NOM

v4l2-compliance - Une application pour tester les pilotes video4linux

SYNOPIS

v4l2-compliance [-h] [-d <périph>] [nombreuses autres options]

DESCRIPTION

L'outil v4l2-compliance est utilisé pour tester les périphériques video4linux, qu'ils soient vidéo, vbi, radio ou swradio, en entrée et en sortie. Il tente de tester presque tous les aspects d'un périphérique V4L2 et couvre presque tous les ioctls V4L2. Il offre un très bon support pour la capture et la sortie vidéo, la capture et la sortie VBI, et le réglage et la transmission radio (logiciel).

Le support des périphériques mémoire-à-mémoire est limité pour le moment.

Si vous avez des questions sur v4l2-compliance, envoyez-les à la liste de diffusion linux-media@vger.kernel.org.

Lorsque vous testez un pilote, compilez toujours l'utilitaire à partir du code source le plus récent du dépôt git (http://git.linuxtv.org/cgit.cgi/v4l-utils.git/). La version fournie par les distributions Linux est presque certainement trop ancienne.

De plus, si un test échoue, il affichera le code source et la ligne où l'échec s'est produit, vous aurez donc souvent besoin d'un accès au code source pour comprendre de quoi il s'agit.

Notez que v4l2-compliance teste non seulement la conformité à l'API V4L2, mais aussi si le pilote utilise tous les bons frameworks. Ces frameworks fournissent souvent automatiquement des ioctls qui sont strictement parlant optionnels, mais qui sont gratuits si vous utilisez ces frameworks. En exigeant leur présence, l'utilitaire v4l2-compliance forcera leur utilisation.

Si vous souhaitez soumettre un nouveau pilote V4L2, ce pilote doit réussir les tests v4l2-compliance sans échec. La meilleure méthode pour utiliser cet outil afin de tester votre pilote est de d'abord tester sans aucune option de streaming et de corriger tous les échecs, du premier au dernier. Parfois, des échecs précédents peuvent générer des échecs ultérieurs, alors commencez à les corriger dans l'ordre et testez à nouveau après chaque correction.

Ensuite, testez votre pilote avec l'option -s pour effectuer les tests de streaming de base. Cela nécessite qu'il existe une entrée ou une sortie valide.

Chaque fois que vous exécutez v4l2-compliance, il enregistrera l'état actuel du pilote et le restaurera une fois tous les tests terminés (y compris lorsque vous appuyez sur Ctrl-C). Tous les tests de streaming sont effectués en utilisant la configuration enregistrée. Cela permet de préparer les tests de streaming en configurant le périphérique avant d'appeler v4l2-compliance.

Enfin, vous devriez tester votre pilote en utilisant les options -f et -c pour vérifier que tous les formats de pixels vidéo sont correctement pris en charge. Vous devez effectuer les trois tests de streaming pour toutes les entrées et sorties. Vous pouvez utiliser l'option -a pour automatiser cela si cela est possible pour votre matériel.

Si votre pilote réussit tous les tests, vous pouvez être assuré que votre pilote est en très bon état !

OPTIONS

-d, --device <périph>
Utilise le périphérique <périph> comme périphérique vidéo. Si <périph> est un nombre, alors /dev/video<périph> est utilisé. Sinon, si -z a été spécifié précédemment, alors <périph> est le nom de l'entité ou l'ID de l'interface (s'il est préfixé par 0x) trouvé dans la topologie du périphérique média avec la chaîne d'informations du bus spécifiée par l'option -z.
-V, --vbi-device <périph>
Utilise le périphérique <périph> comme périphérique VBI. Si <périph> est un nombre, alors /dev/vbi<périph> est utilisé. Sinon, si -z a été spécifié précédemment, alors <périph> est le nom de l'entité ou l'ID de l'interface (s'il est préfixé par 0x) trouvé dans la topologie du périphérique média avec la chaîne d'informations du bus spécifiée par l'option -z.
-r, --radio-device <périph>
Utilise le périphérique <périph> comme périphérique radio. Si <périph> est un nombre, alors /dev/radio<périph> est utilisé. Sinon, si -z a été spécifié précédemment, alors <périph> est le nom de l'entité ou l'ID de l'interface (s'il est préfixé par 0x) trouvé dans la topologie du périphérique média avec la chaîne d'informations du bus spécifiée par l'option -z.
-S, --sdr-device <périph>
Utilise le périphérique <périph> comme périphérique SDR. Si <périph> est un nombre, alors /dev/swradio<périph> est utilisé. Sinon, si -z a été spécifié précédemment, alors <périph> est le nom de l'entité ou l'ID de l'interface (s'il est préfixé par 0x) trouvé dans la topologie du périphérique média avec la chaîne d'informations du bus spécifiée par l'option -z.
-t, --touch-device <périph>
Utilise le périphérique <périph> comme périphérique tactile. Si <périph> est un nombre, alors /dev/v4l-touch<périph> est utilisé. Sinon, si -z a été spécifié précédemment, alors <périph> est le nom de l'entité ou l'ID de l'interface (s'il est préfixé par 0x) trouvé dans la topologie du périphérique média avec la chaîne d'informations du bus spécifiée par l'option -z.
-u, --subdev-device <périph>
Utilise le périphérique <périph> comme périphérique v4l-subdevX. Si <périph> est un nombre, alors /dev/v4l-subdev<périph> est utilisé. Sinon, si -z a été spécifié précédemment, alors <périph> est le nom de l'entité -e, --exp-buf-device <périph> Utilise le périphérique <périph> comme périphérique vidéo utilisé pour exporter des buffers DMABUF afin d'effectuer des tests de streaming DMABUF. Si <périph> est un nombre, alors /dev/video<périph> est utilisé. Sinon, si -z a été spécifié précédemment, alors <périph> est le nom de l'entité ou l'ID de l'interface (s'il est préfixé par 0x) trouvé dans la topologie du périphérique média avec la chaîne d'informations du bus spécifiée par l'option -z. Si cette option n'est pas spécifiée, les tests de streaming DMABUF seront ignorés.
-z, --media-bus-info <infos-bus>
Trouve le périphérique média avec la chaîne d'informations du bus donnée. Si défini, les options ci-dessus peuvent utiliser le nom de l'entité ou l'ID de l'interface pour faire référence aux nœuds de périphérique. Exemple : v4l2-compliance -z platform:vivid-000 -d vivid-000-vid-cap
-m, --media-device <périph>
Utilise le périphérique <périph> comme périphérique de contrôle média. En plus de ce périphérique, il teste également toutes les interfaces qu'il trouve. Si <périph> commence par un chiffre, alors /dev/media<périph> est utilisé. Si <périph> n'existe pas, alors on tente de trouver un périphérique média avec une chaîne d'informations du bus égale à <périph>. Exemple : v4l2-compliance -m platform:vivid-000
-M, --media-device-only <périph>
Utilise le périphérique <périph> comme périphérique de contrôle média. Teste uniquement ce périphérique, ne parcourt pas toutes les interfaces. Si <périph> commence par un chiffre, alors /dev/media<périph> est utilisé. Si <périph> n'existe pas, alors on tente de trouver un périphérique média avec une chaîne d'informations du bus égale à <périph>. Exemple : v4l2-compliance -M platform:vivid-000
--stream-from [<formatpixel>=]<fichier>, --stream-from-hdr [<formatpixel>=]<fichier>
Utilise le contenu du fichier pour remplir les buffers de sortie. Si le fourcc du format de pixel est donné, alors utilise le fichier pour les buffers de sortie en utilisant uniquement ce format de pixel. La variante --stream-from-hdr utilise le format écrit par v4l2-ctl --stream-to-hdr où les tailles de charge utile pour chaque buffer sont stockées dans un en-tête. Utile pour les formats compressés.
-s, --streaming <compte>
Active les tests de streaming. Définissez <compte> sur le nombre d'images à streamer (par défaut 60). Cela nécessite qu'avant que v4l2-compliance ne soit appelé, le périphérique ait été configuré avec une entrée (ou sortie) et une fréquence valides (lorsque le périphérique a un syntoniseur). Pour les tests DMABUF, --expbuf-device doit également être défini.

La configuration du pilote au moment où v4l2-compliance a été appelé sera utilisée pour les tests de streaming.

-f, --stream-all-formats [<compte>]
Teste si tous les formats disponibles peuvent être streamés. Ceci à
tentatives de diffusion en mode MMAP ou lecture/écriture (si V4L2_MEMORY_MMAP n'est pas disponible) pendant une seconde pour tous les formats, à toutes les tailles, à tous les intervalles et avec toutes les valeurs de champ. De plus, si le pilote prend en charge la mise à l'échelle, le rognage ou la composition, il le testera également dans diverses combinaisons. Si le pilote prend en charge de nombreuses combinaisons, ce test peut prendre beaucoup de temps. Si <count> est donné, alors diffusez pour ce nombre d'images au lieu d'une seconde.

La configuration du pilote au moment où v4l2-compliance a été appelé sera utilisée pour les tests de diffusion.

-c, --stream-all-color color=red|green|blue,skip=<skip>,perc=<perc>
Pour tous les formats non compressés pris en charge, diffusez <skip + 1> images. Pour la dernière image, parcourez tous les pixels et calculez lequel des composantes de couleur R, G et B d'un pixel a la valeur la plus élevée et comptez-le comme un pixel rouge, vert ou bleu. Le test réussit si au moins perc pour cent de l'image a la couleur color donnée. Cela nécessite qu'un signal vidéo valide et majoritairement rouge, vert ou bleu soit présent sur les entrées. Si skip n'est pas spécifié, capturez simplement la première image. Une valeur skip non nulle est utile s'il faut quelques images pour que l'appareil s'étalonne. Si perc n'est pas spécifié, alors cela vaut par défaut 90%.

La plupart des générateurs de signaux sont capables de générer une vidéo purement rouge, bleue ou verte. Pour les caméras, vous pouvez imprimer une image complètement rouge, verte ou bleue et la tenir devant la caméra.

Le but de ce test est de déterminer si tous les formats de pixels interpréteront correctement les couleurs rouge, verte et bleue et qu'aucun composant de couleur n'est échangé.

La configuration du pilote au moment où v4l2-compliance a été appelé sera utilisée pour les tests de diffusion.

-a, --stream-all-io
Effectuez les tests de diffusion -s, -c et -f pour toutes les entrées ou sorties au lieu de seulement l'entrée ou la sortie actuelle. Cela nécessite qu'un signal vidéo valide soit présent sur toutes les entrées ou que toutes les sorties soient connectées.
-E, --exit-on-fail
Quittez cette application lors de la première erreur au lieu de continuer avec un état potentiellement incohérent.
-C, --color <when>
Mettez en surbrillance les chaînes OK/warn/fail/FAIL avec des couleurs. OK est marqué en vert, warn est marqué en gras, et fail/FAIL sont marqués en rouge vif si activé. <when> peut être always, never, ou auto (par défaut).
-n, --no-warnings
Désactivez les messages d'avertissement. Ils sont toujours comptés dans le résumé, mais vous ne les verrez pas.
-P, --no-progress
Désactivez les messages de progression. Utile lors de la redirection de la sortie vers un fichier.
-T, --trace
Suivez tous les ioctls appelés.
-v, --verbose
Activez le rapport détaillé.
--version
Afficher les informations de version.
-w, --wrapper
Utilisez la bibliothèque wrapper libv4l2 pour tous les accès aux périphériques V4L2. Notez que cela entraînera l'échec de certains tests car la bibliothèque libv4l2 n'est pas entièrement conforme à V4L2. Par défaut, v4l2-compliance contournera libv4l2 et accédera directement aux périphériques V4L2.
-W, --exit-on-warn
Quittez cette application lors du premier avertissement au lieu de continuer.
-h, --help
Affiche le message d'aide.

STATUT DE SORTIE

En cas de succès, renvoie 0. Sinon, il renvoie le code d'erreur.

BOGUES

Ceci est en cours de développement, et de temps en temps, il s'avère que certains tests effectués par v4l2-compliance sont trop stricts ou tout simplement erronés. Si vous pensez que c'est le cas, signalez ces bugs à la liste de diffusion linux-media@vger.kernel.org.
