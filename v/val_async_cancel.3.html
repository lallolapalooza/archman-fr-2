libval_async(3) Manuel du programmeur libval_async(3)

NOM

val_async_submit() - soumet une requête pour le traitement asynchrone des requêtes DNS.

val_async_select_info() - définit les descripteurs de fichiers appropriés pour les requêtes asynchrones en attente.

val_async_check_wait() - gère les délais d'attente ou traite les réponses DNS aux requêtes en attente.

val_async_cancel() - annule une requête asynchrone.

val_async_cancel_all() - annule toutes les requêtes asynchrones pour un contexte donné.

SYNTAXE

#include <validator/validator.h>

typedef int (*val_async_event_cb)(val_async_status *async_status,
int event, val_context_t *context,
void *cb_data, val_cb_params_t *cbp);

int val_async_submit(val_context_t *context,
const char * name, int class,
int type, unsigned int flags,
val_async_event_cb callback, void *cb_data,
val_async_status **async_status);

int val_async_select_info(val_context_t *context,
fd_set *fds,
int *num_fds,
struct timeval *timeout);

int val_async_check_wait(val_context_t *context,
fd_set *pending_desc, int *nfds,
struct timeval *tv, unsigned int flags);

int val_async_cancel(val_context_t *context,
val_async_status *as,
unsigned int flags);

int val_async_cancel_all(val_context_t *context,
unsigned int flags);

DESCRIPTION

L'API asynchrone du validateur DNSSEC permet à une application de soumettre plusieurs requêtes qui peuvent être traitées en parallèle. Dans la plupart des cas, cela permettra à la validation de s'achever beaucoup plus rapidement qu'une série de requêtes synchrones.

Le paramètre ctx dans les différentes fonctions ci-dessous spécifie le contexte de validation, qui peut être défini à NULL pour les valeurs par défaut (voir libval(3) et dnsval.conf pour plus de détails sur les contextes de validation et la politique de validation).

La fonction val_async_submit() soumet une requête pour le traitement asynchrone des requêtes DNS pour les données associées au nom de domaine name, à la classe class et au type type donnés. L'objet async_status identifie de manière unique une requête particulière et fournit un handle pour les opérations futures sur cette requête asynchrone, y compris son annulation avant l'achèvement de la recherche.

Le paramètre flags affecte quand et à quelle fréquence le rappel est appelé. Les drapeaux suivants sont définis.

VAL_AS_IGNORE_CACHE
N'utilise aucun cache interne pour les réponses à cette requête.
VAL_AS_NO_NEW_QUERIES
N'envoie aucune nouvelle requête. Les réponses seront retournées depuis le cache interne.
VAL_AS_NO_ANSWERS
L'appelant ne se soucie pas des résultats des réponses. Ceci peut être utilisé pour amorcer le cache.
VAL_AS_NO_CALLBACKS
N'appelle aucun rappel.
VAL_AS_NO_CANCEL_CALLBACKS
Appelle les rappels avec les résultats, mais n'appelle aucun rappel lorsque la requête est annulée.
VAL_AS_INTERIM_CALLBACKS
Appelle la fonction de rappel avec des résultats intermédiaires. Si ce drapeau n'est pas spécifié, la fonction de rappel ne sera appelée que lorsque tous les résultats de validation seront prêts.

Lorsque les résultats de l'appel asynchrone deviennent disponibles, la fonction callback (si elle n'est pas NULL) sera appelée avec la valeur cb_data, initialement fournie à l'appel val_async_submit(), comme l'un de ses arguments. Les résultats de la recherche sont retournés dans cb_data, qui est un pointeur vers la structure val_cb_params_t présentée ci-dessous.

typedef struct val_cb_params_s {
    val_status_t             val_status;
    char                    *name;
    int                      class_h;
    int                      type_h;
    int                      retval;
    struct val_result_chain *results;
    struct val_answer_chain *answers;
} val_cb_params_t;

La structure val_cb_params_t contient les paramètres de la requête originale dans name, class_h et type_h respectivement, la valeur de retour pour l'opération de recherche dans retval, des pointeurs vers les chaînes results et answers (voir libval(3) pour plus de détails), et le statut final de validation de l'opération de recherche dans val_status. L'application doit libérer la mémoire associée à results et answers en utilisant respectivement val_free_result_chain() et val_free_answer_chain() (voir libval(3) pour plus de détails).

À l'achèvement de l'opération de recherche asynchrone, un code d'événement est retourné dans event. Les types d'événements suivants sont définis :

VAL_AS_EVENT_COMPLETED
La requête a été complétée.
VAL_AS_EVENT_INTERIM
La requête est toujours en cours de traitement, mais des résultats intermédiaires sont disponibles.
VAL_AS_EVENT_CANCELED
La requête a été annulée. Les membres val_status, results et answers de la structure de paramètres de rappel sont indéfinis.

La fonction val_async_select_info() examine toutes les requêtes asynchrones en attente pour le contexte donné et définit les descripteurs de fichiers appropriés, la valeur de délai d'attente et la valeur maximale du descripteur de fichier en préparation d'un appel à select(3).

Le descripteur de fichier pour chaque socket attendant une réponse est défini dans le paramètre fds et max_fd est défini sur le numéro de descripteur de fichier le plus élevé de toute requête asynchrone en attente, sauf si cette valeur est inférieure à la valeur actuelle de max_fd, auquel cas elle est laissée inchangée. Le champ timeout est défini sur la valeur de délai d'attente la plus basse de toute requête asynchrone en attente dont le délai est inférieur à la valeur actuelle de ce champ par l'application.

Après que l'application appelle select(3), elle doit également appeler val_async_check_wait() avec le fd_set et le nombre de descripteurs de fichiers prêts, ndfs, retournés par select(). La fonction val_async_check_wait() gère les délais d'attente ou traite les réponses DNS aux requêtes en attente. Elle appelle également les rappels pour les requêtes terminées.

val_async_check_wait() fournit deux modes de fonctionnement. Le premier est destiné à être utilisé avec une application qui possède sa propre boucle select(). L'application définit ses propres descripteurs de fichiers, appelle val_async_select_info() pour définir les descripteurs de fichiers pour les requêtes en attente et appelle select(). Les paramètres fds et nfds de select sont passés à val_async_check_wait et la valeur de délai d'attente est ignorée. Si des réponses pour un descripteur de fichier sont traitées, le descripteur de fichier approprié dans fds est effacé et nfds est décrémenté.

Dans le second mode de fonctionnement, l'application peut définir fds et nfds sur NULL pour spécifier une valeur pour timeout. Ici, val_async_select_info() et select() sont appelés en interne et toutes les réponses reçues avant l'expiration de la valeur de délai d'attente sont traitées.

La fonction val_async_cancel() peut être utilisée pour annuler la requête asynchrone identifiée par son handle as, tandis que val_async_cancel_all() peut être utilisée pour annuler toutes les requêtes asynchrones associées à un contexte donné. Le drapeau suivant peut être défini pour la requête d'annulation.

VAL_AS_CANCEL_NO_CALLBACKS
Ne pas appeler les rappels terminés ou annulés.

VALEURS DE RETOUR

La fonction val_async_submit() retourne VAL_NO_ERROR en cas de succès et l'une des valeurs suivantes en cas d'échec : VAL_RESOURCE_UNAVAILABLE, VAL_BAD_ARGUMENT ou VAL_INTERNAL_ERROR.

>val_async_select_info() renvoie VAL_NO_ERROR en cas de succès et VAL_BAD_ARGUMENT si un argument illégal a été passé à la fonction.

val_async_check_wait() renvoie 0 lorsqu'aucune requête en attente n'est trouvée et un entier positif lorsque des requêtes sont toujours en attente. Une valeur inférieure à zéro en cas d'erreur.

val_async_cancel() et val_async_cancel_all() renvoient VAL_NO_ERROR en cas de succès.
