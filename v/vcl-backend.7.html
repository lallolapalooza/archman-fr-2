NOM

VCL-backends - Configuration des backends

DÉFINITION DES BACKENDS

Une déclaration de backend crée et initialise un objet backend nommé. Une déclaration commence par le mot-clé backend suivi du nom du backend. La déclaration réelle est entre accolades, sous forme de paires clé/valeur :

backend nom {
    .attribut1 = valeur;
    .attribut2 = valeur;
    [...]
}

S'il existe un backend nommé default, il sera utilisé à moins qu'un autre backend ne soit explicitement défini. Si aucun backend n'est nommé default, le premier backend du programme VCL devient le backend par défaut.

Si vous utilisez uniquement des backends dynamiques créés par des VMODs, un backend vide, toujours défaillant (503), peut être spécifié :

backend default none;

Un backend doit être spécifié avec un attribut .host ou un attribut .path, mais pas les deux. Tous les autres attributs ont des valeurs par défaut.

ATTRIBUT .HOST

Pour spécifier un backend réseau, .host accepte soit une adresse IPv4/IPv6 numérique, soit un nom de domaine qui se résout en au plus une adresse IPv4 et une adresse IPv6 :

.host = "127.0.0.1";
.host = "[::1]:8080";
.host = "exemple.com:8081";
.host = "exemple.com:http";

ATTRIBUT .PORT

Le port TCP ou le nom de service peut être spécifié dans .host comme ci-dessus, ou séparément en utilisant l'attribut .port :

.port = "8081";
.port = "http";

ATTRIBUT .PATH

Le chemin absolu vers un socket de domaine Unix(4) d'un backend local :

.path = "/var/run/http.sock";

ou, là où disponible, @ suivi du nom d'un socket abstrait d'un backend local :

.path = "@monbackend";

Un avertissement sera émis si le socket uds n'existe pas lors du chargement du VCL. Cela permet de démarrer le pair écoutant le UDS, ou de définir les permissions du fichier socket ultérieurement.

Si le socket uds n'existe pas ou si les permissions le refusent, les tentatives de connexion échoueront.

ATTRIBUT .HOST_HEADER

Un en-tête hôte à ajouter aux sondes et aux requêtes backend régulières si elles n'en ont pas :

.host_header = "exemple.com";

ATTRIBUTS DE DÉLAI

Ces attributs contrôlent la patience de varnishd lors des récupérations de backend :

.connect_timeout = 1.4s;
.first_byte_timeout = 20s;
.between_bytes_timeout = 10s;

Les valeurs par défaut proviennent des paramètres portant les mêmes noms, voir varnishd(1).

ATTRIBUT .MAX_CONNECTIONS

Limite le nombre de connexions simultanées que varnish peut ouvrir vers le backend :

.max_connections = 1000;

ATTRIBUT .WAIT_LIMIT

Nombre maximum de transactions qui peuvent être mises en file d'attente en attendant qu'une connexion backend devienne disponible :

.wait_limit = 1000;

Notez que cette fonctionnalité doit être utilisée avec prudence, car elle peut entraîner une accumulation de threads et augmenter les temps de réponse.

Par défaut, utilise le paramètre backend_wait_limit de varnishd(1).

ATTRIBUT .WAIT_TIMEOUT

Lorsqu'une transaction est mise en file d'attente en attendant qu'une connexion backend devienne disponible (voir .wait_limit), c'est le temps pendant lequel la transaction attendra avant d'abandonner :

.wait_timeout = 1s;

Il est fortement conseillé de ne jamais définir cette valeur au-dessus de quelques secondes.

Par défaut, utilise le paramètre backend_wait_timeout de varnishd(1).

ATTRIBUT .PROXY_HEADER

Envoyer un en-tête PROXY protocol au backend avec les valeurs de client.ip et server.ip :

.proxy_header = 2;

Les valeurs légales sont un et deux, selon la version du protocole PROXY que vous souhaitez.

Note : ce réglage entraînera l'utilisation des connexions backend pour une seule requête à la fois (sous réserve d'améliorations futures). Par conséquent, prenez des précautions supplémentaires pour éviter les connexions backend défaillantes avec EADDRNOTAVAIL en raison de l'indisponibilité de ports locaux. Options possibles :

  • Utiliser des connexions backend supplémentaires vers des adresses IP ou des ports TCP supplémentaires
  • Augmenter le nombre de ports disponibles (sysctl Linux net.ipv4.ip_local_port_range)
  • Réutiliser rapidement les ports de connexion backend (sysctl Linux net.ipv4.tcp_tw_reuse)

ATTRIBUT .PREAMBLE

Envoyer un BLOB sur toutes les nouvelles connexions ouvertes vers le backend :

.preamble = :SGVsbG8gV29ybGRcbgo=:;

ATTRIBUT .VIA

Nom d'un autre backend proxy via lequel établir la connexion au backend destination en utilisant le protocole PROXY2, par exemple :

backend proxy {
  .path = "/chemin/vers/endpoint_proxy2";
}
backend destination {
  .host = "1.2.3.4";
  .via = proxy;
}

Le backend proxy peut également utiliser une définition .host/.port au lieu de .path.

L'utilisation de l'attribut .path pour le backend destination n'est pas prise en charge.

L'attribut .via n'est pas lié à .proxy_header. Si les deux sont utilisés, un deuxième en-tête est envoyé conformément à la spécification .proxy_header.

Sauf indication contraire pour la destination, les attributs connect_timeout, first_byte_timeout et between_bytes_timeout sont copiés du proxy vers la destination.

À partir de cette version, le backend proxy utilisé avec .via ne peut pas être un directeur, il ne peut pas utiliser lui-même .via (erreur : Impossible d'empiler des backends .via) et le protocole est fixé à PROXY2.

Détail d'implémentation :

Si .via = <proxy> est utilisé, un préambule PROXY2 est créé avec les informations d'adresse du backend destination comme dst_addr/dst_port et, éventuellement, d'autres attributs TLV. La connexion est ensuite établie à l'endpoint du backend proxy (path ou host/port). Ceci est techniquement équivalent à spécifier un backend destination_via_proxy avec un attribut .preamble contenant le préambule PROXY2 approprié pour le backend destination.

ATTRIBUT .AUTHORITY

L'autorité HTTP à utiliser lors de la connexion à ce backend. Si non défini, .host_header ou .host sont utilisés.

.authority = "" désactive l'envoi d'une autorité.

.authority ne peut pas être une adresse IP.

ATTRIBUTE .AUTHORITY

Ce n'est pas un attribut de back-end, mais un type d'attribut de connexion au back-end. La connexion à un back-end peut se voir attribuer des données d'autorité. Les données d'autorité sont utilisées pour construire la valeur du champ de requête Authority du côté client, et par le protocole PROXY protocol version 2.

Pour les connexions utilisant le protocole PROXY protocol version 2, les données d'autorité sont envoyées dans le préambule sous forme d'un TLV de type PP2_TYPE_AUTHORITY.

Toutes les spécifications de back-end, y compris ceux qui ne sont pas des back-ends d'hébergement, mais qui sont simplement utilisés pour les informations de routage par le proxy, peuvent avoir cet attribut défini. Par exemple :

backend default {
    .host = "192.168.0.1";
    .port = "8080";
    .authority = "example.com";
}

Cela définit le back-end pour qu'il utilise « example.com » comme valeur pour son champ de requête Authority. Le champ Authority est utilisé pour le schéma d'URI (par exemple, « http ») et le nom d'hôte ou l'adresse IP et le port du serveur cible.

La valeur de cet attribut ne peut pas être modifiée après que la connexion a été établie. Si cet attribut est défini sur un back-end qui n'est pas utilisé dans une connexion qui demande une valeur d'autorité, il sera simplement ignoré.

Au moment de cette publication, l'attribut n'est utilisé que par les connexions .via en tant que TLV PP2_TYPE_AUTHORITY dans le préambule PROXY2.
