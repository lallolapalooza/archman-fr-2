NOM

vnstatd — service de mise à jour de base de données pour vnStat

SYNTAXE

vnstatd [-Ddnpstv?] [--alwaysadd [mode]] [--config fichier] [--daemon] [--debug] [-g groupe] [--group groupe] [--help] [--initdb] [--noadd] [--nodaemon] [--noremove] [--pidfile fichier] [--startempty] [--sync] [--timestamp] [--u utilisateur] [--user utilisateur] [--version]

DESCRIPTION

L'objectif de vnstatd est de fournir un moyen flexible et robuste de collecter des données pour la base de données utilisée par vnstat(1). La disponibilité de chaque interface est automatiquement suivie, ce qui élimine le besoin de scripts supplémentaires à implémenter et à appeler lorsqu'une interface est activée ou désactivée.

vnstatd est la commande pour démarrer le service. Le service peut soit se détacher pour s'exécuter en arrière-plan, soit rester attaché au terminal. Il prend en charge la journalisation directement sur le terminal, dans un fichier sélectionnable par l'utilisateur ou via syslog.

Une fois démarré, le service lira vnstat.conf(5) si disponible, puis vérifiera si une base de données est présente dans le répertoire de base de données spécifié dans le fichier de configuration. Par défaut, si aucune base de données n'est trouvée, une base de données sera créée au démarrage avec des entrées pour toutes les interfaces disponibles, à l'exclusion des interfaces pseudo lo, lo0 et sit0. Ce comportement de création automatique d'entrée de base de données peut être désactivé en utilisant l'option --noadd. Alternativement, l'option --alwaysadd peut être utilisée pour demander au service de créer de nouvelles entrées de base de données chaque fois que des interfaces non encore dans les bases de données deviennent visibles. Par défaut, sauf si l'option --startempty est utilisée, le service ne restera pas en cours d'exécution si aucune interface n'est découverte lors du démarrage et si la base de données ne contient aucune interface.

Le service procédera au suivi de la disponibilité des interfaces surveillées, au traitement des statistiques de trafic de l'interface et à l'écriture de nouvelles valeurs dans la base de données à un intervalle configuré. Par conséquent, le service passe la majeure partie du temps à dormir entre les mises à jour. Les nouvelles interfaces ajoutées à la base de données seront automatiquement prises en compte pour la surveillance sans que le service n'ait besoin d'être notifié.

Lorsque l'option de configuration UseUTC n'est pas activée, les données sont stockées dans la base de données en utilisant l'heure locale basée sur l'environnement d'exécution du service lorsque l'option de configuration n'est pas activée. Tout changement dans l'horloge système ou la configuration du fuseau horaire du système entraînera l'insertion des données selon la nouvelle heure locale sans aucune recalculation pour les données déjà stockées. Le service et la base de données ne sont essentiellement pas conscients du fuseau horaire utilisé ou de l'heure d'été et ne peuvent pas être configurés pour décaler les horodatages dans une direction ou une autre. Si un changement d'horloge système ou de fuseau horaire système ou la fin de l'observation de l'heure d'été entraîne la répétition d'une période de temps déjà vue, les valeurs existantes de la base de données seront incrémentées avec les nouvelles données.

OPTIONS

--alwaysadd [mode]
Active la création automatique de nouvelles entrées de base de données pour les interfaces qui ne sont pas actuellement dans la base de données, même si le fichier de base de données existe déjà lorsque le service démarre. De nouvelles entrées de base de données seront également créées pour les nouvelles interfaces détectées pendant que le service fonctionne. Les interfaces pseudo lo, lo0 et sit0 sont toujours exclues de l'ajout. L'utilisation de l'option sans mode défini ou avec mode défini sur 1 active la fonctionnalité. La définition de mode sur 0 désactive la fonctionnalité. Cette option en ligne de commande remplace l'option de configuration AlwaysAddNewInterfaces lorsqu'elle est utilisée.
--config fichier
Utilise fichier comme fichier de configuration au lieu d'utiliser la recherche automatique de fichiers de configuration.
-d, --daemon
Détache le processus en arrière-plan et l'exécute en tant que service.
-D, --debug
Fournit une sortie supplémentaire à des fins de débogage. Le processus restera attaché au terminal pour la sortie.
-g, --group groupe
Définit le groupe de processus du service sur groupe au démarrage. groupe peut être le nom du groupe ou un identifiant numérique de groupe. Cette option ne peut être utilisée que lorsque le processus est démarré en tant que root.
--initdb
Crée une nouvelle base de données, importe les données des bases de données héritées trouvées si l'option --noadd n'est pas utilisée et quitte sans créer d'entrées de base de données pour les interfaces disponibles si aucune donnée héritée n'a été importée. Si la base de données existe déjà, seul l'accès est vérifié. Le service ne restera pas en cours d'exécution lorsque cette option est utilisée. Cette option ne peut pas être utilisée en combinaison avec -d, --daemon, -n, --nodaemon ou --startempty.
--noadd
Lorsqu'elle est utilisée en combinaison avec -d, --daemon ou -n, --nodaemon, désactive la création automatique de nouvelles entrées de base de données pour toutes les interfaces actuellement disponibles lorsque le service démarre sans base de données existante ou avec une base de données contenant zéro interface. Le service créera toujours une base de données vide si elle n'existe pas déjà. Les interfaces pseudo lo, lo0 et sit0 sont toujours exclues de l'ajout, quelle que soit cette option.
Lorsqu'elle est utilisée en combinaison avec --initdb, crée uniquement une base de données vide si elle n'existe pas déjà, sans importer de données des bases de données héritées possibles, puis quitte.
-n, --nodaemon
Reste en premier plan attaché au terminal actuel et démarre le processus de mise à jour.
--noremove
Désactive la suppression automatique des interfaces de la base de données qui ne sont pas actuellement visibles et qui n'ont pas vu de trafic.
-p, --pidfile fichier
Écrit l'identifiant du processus dans fichier et l'utilise pour le verrouillage afin qu'une autre instance du service ne puisse pas être démarrée si le même fichier est spécifié. Cette option n'a aucun effet si elle est utilisée en combinaison avec -n, --nodaemon.
--startempty
Démarre même lorsqu'aucune interface n'a été découverte et que la base de données est vide. Le service restera en cours d'exécution et attendra que des interfaces soient ajoutées à la base de données ou trouvées si l'option --alwaysadd a également été utilisée. Cette option ne peut pas être utilisée en combinaison avec --initdb.
-s, --sync
Synchronise les compteurs internes de la base de données avec les compteurs d'interface pour toutes les interfaces disponibles avant de commencer la surveillance du trafic. Utilisez cette option si le trafic entre l'arrêt précédent et le démarrage actuel du service doit être ignoré. Cette option n'est pas requise en utilisation normale car le service synchronisera automatiquement les compteurs internes après un redémarrage du système, si suffisamment de temps s'est écoulé depuis que le service fonctionnait précédemment ou si les compteurs internes sont clairement désynchronisés.
-t, --timestamp
Ajoute un horodatage au début de chaque impression du service lorsque le processus s'exécute en premier plan, attaché à un terminal, après avoir été démarré avec l'option -n, --nodaemon.
-u, --user utilisateur
Définit l'utilisateur du processus du service sur utilisateur au démarrage. utilisateur peut être soit le nom de connexion de l'utilisateur, soit un identifiant numérique d'utilisateur. Cette option ne peut être utilisée que lorsque le processus est démarré en tant que root.
-v, --version
Affiche la version actuelle de l'exécutable du service.
-?, --help
Affiche un résumé des options de commande.

CONFIGURATION

Le comportement du service est principalement configuré à l'aide des mots-clés de configuration UpdateInterval, PollInterval et SaveInterval dans le fichier de configuration.

vnstatd(8) - ArchWiki

NAME

vnstatd

network traffic monitor daemon

SYNOPSIS

vnstatd [-d] [-p] [-s] [-l] [-c file] [-C file] [-p file] [-L file] [-P file] [-f file] [-F file]

DESCRIPTION

The vnstatd daemon is used for collecting network traffic statistics. It runs in the background and periodically updates the traffic data based on the system's network interfaces. The collected data can then be viewed using the vnstat(1) command.

The daemon uses configuration parameters to control how often it updates the interface data, checks for interface changes, and saves the data to disk. It also handles signals for graceful shutdown and configuration reloading.

OPTIONS

-d
Debug mode. Prints all actions to standard output.
-p
Poll mode. The daemon will exit after checking for new configuration settings and applying them.
-s
Save data. The daemon will write cached data to disk and exit.
-l
List available interfaces and exit.
-c file
Use specified file as pid file.
-C file
Use specified file as configuration file.
-p file
Use specified file as database directory.
-L file
Use specified file as log file.
-P file
Use specified file as pid file.
-f file
Use specified file as lock file.
-F file
Use specified file as database cache file.

CONFIGURATION

The daemon's behavior is controlled by the configuration file, typically located at /etc/vnstat.conf. The following options are relevant:

UpdateInterval defines in seconds how often the interface data is fetched and updated. This is similar to the run interval for alternative cron based updating. However, the difference is that the data doesn't directly get written to disk during updates.

PollInterval defines in seconds how often the list of available interfaces is checked for possible changes. The minimum value is 2 seconds and the maximum 60 seconds. PollInterval also defines the resolution for other intervals.

SaveInterval defines in minutes how often cached interface data is written to disk. A write can only occur during the updating of interface data. Therefore, the value should be a multiple of UpdateInterval with a maximum value of 60 minutes.

The default values of UpdateInterval 30, SaveInterval 5 and PollInterval 5 are usually suitable for most systems and provide a similar behaviour as cron based updating does but with a better resolution for interface changes and fast interfaces.

For embedded and/or low power systems more tuned configurations are possible. In such cases if the interfaces are mostly static the PollInterval can be increased to around 10-30 seconds and UpdateInterval set to 60 seconds. Higher values up to 300 seconds are possible if the interface speed is 10 Mbit or less. SaveInterval can be increased for example to 15, 30 or even 60 minutes depending on how often the data needs to be viewed.

SIGNALS

The daemon is listening to signals SIGHUP, SIGINT and SIGTERM. Sending the SIGHUP signal to the daemon will cause cached data to be written to disk, a rescan of the database directory and a reload of settings from the configuration file. However, the pid file location will not be changed even if it's configuration setting has been modified.

SIGTERM and SIGINT signals will cause the daemon to write all cached data to disk and then exit.

FILES

/var/lib/vnstat/
Default database directory.
/etc/vnstat.conf
Config file that will be used unless $HOME/.vnstatrc exists. See the configuration chapter and vnstat.conf(5) for more information.
/var/log/vnstat/vnstat.log
Log file that will be used if logging to file is enable and no other file is specified in the config file.
/var/run/vnstat/vnstat.pid
File used for storing the process id when running as a background process and if no other file is specified in the configuration file or using the command line parameter.

RESTRICTIONS

Updates need to be executed at least as often as it is possible for the interface to generate enough traffic to overflow the kernel interface traffic counter. Otherwise, it is possible that some traffic won't be seen. With 32-bit interface traffic counters, the maximum time between two updates depends on how fast the interface can transfer 4 GiB. Note that there is no guarantee that a 64-bit kernel has 64-bit interface traffic counters for all interfaces. Calculated theoretical times are:

10 Mbit: 54 minutes
100 Mbit: 5 minutes
1000 Mbit: 30 seconds
Virtual and aliased interfaces cannot be monitored because the kernel doesn't provide traffic information for that type of interfaces. Such interfaces are usually named eth0:0, eth0:1, eth0:2 etc. where eth0 is the actual interface being aliased.
