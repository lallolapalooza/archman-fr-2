VARNISHD(1) Manuel des commandes générales VARNISHD(1)

NOM

varnishd - démon d'accélération HTTP

SYNTAXE

varnishd
[-a [nom=][adresse_ecoute[,PROTO|,option=valeur,...]] [-b [hote[:port]|chemin]] [-C] [-d] [-F] [-f config] [-h type[,options]] [-I fichier_cli] [-i identite] [-j jail[,options_jail]] [-l vsl] [-M adresse:port] [-n rep_travail] [-P fichier] [-p param=valeur] [-r param[,param...]] [-S fichier_secret] [-s [nom=]type[,options]] [-T adresse[:port]] [-t TTL] [-V] [-W waiter]

varnishd [-x parametre|vsl|cli|builtin|optstring]

varnishd [-?]

DESCRIPTION

Le démon varnishd accepte les requêtes HTTP des clients, les transmet à un serveur backend et met en cache les documents retournés pour mieux satisfaire les futures requêtes pour le même document.

OPTIONS

Options de base

-a <[nom=][adresse_ecoute[,PROTO|,option=valeur,...]]>
Syntaxe générique pour accepter les requêtes clients sur une adresse d'écoute. Voir ci-dessous pour les détails.

Le nom est référencé dans les journaux et disponible pour VCL en tant que local.socket. Si le nom n'est pas spécifié, a avec une séquence numérique ("a0", "a1", etc.) est utilisé.

Tous les arguments après l'adresse d'écoute séparés par une virgule sont considérés comme une paire option=valeur de l'accepteur s'ils contiennent un =, ou comme une sélection de PROTO(cole) sinon.

Les options valides dépendent du type d'accepteur, voir ci-dessous.

PROTO peut être "HTTP" (par défaut) ou "PROXY". Les versions 1 et 2 du protocole proxy peuvent être utilisées.

Plusieurs arguments -a sont autorisés.

Si aucun argument -a n'est donné, le défaut -a :80 écoutera sur toutes les interfaces IPv4 et IPv6.

-a <[nom=][adresse_ip[:port][,PROTO]]>
L'adresse_ip peut être un nom d'hôte ("localhost"), un quad-dotté IPv4 ("127.0.0.1") ou une adresse IPv6 entre crochets ("[::1]").

Le port peut être un numéro de port (80), un nom de service (http), ou une plage de ports (80-81). Les plages de ports sont inclusives et ne peuvent pas se chevaucher. Si le port n'est pas spécifié, le port 80 (http) est utilisé.

Au moins l'un des champs adresse_ip ou port est requis.

-a <[nom=][chemin][,PROTO][,utilisateur=nom][,groupe=nom][,mode=octal]>
(VCL4.1 et supérieur)

Accepte les connexions sur un socket de domaine Unix. Le chemin doit être absolu ("/chemin/vers/listen.sock") ou "@" suivi du nom d'un socket abstrait ("@monvarnishd").

Les sous-arguments utilisateur, groupe et mode peuvent être utilisés pour spécifier les permissions du fichier socket -- utilisez des noms pour utilisateur et groupe, et une valeur octale à 3 chiffres pour le mode. Ces sous-arguments ne s'appliquent pas aux sockets abstraits.

-b <[hote[:port]|chemin]>
Utilise l'hôte spécifié comme serveur backend. Si le port n'est pas spécifié, la valeur par défaut est 8080.

Si la valeur de -b commence par /, elle est interprétée comme le chemin absolu d'un socket de domaine Unix auquel Varnish se connecte. Dans ce cas, la valeur de -b doit satisfaire les conditions requises pour le champ .path d'une déclaration de backend, voir vcl(7). Les backends avec des adresses de socket Unix ne peuvent être utilisés qu'avec les versions VCL >= 4.1.

-b ne peut être utilisé qu'une seule fois, et pas conjointement avec -f.

-f config
Utilise le fichier de configuration VCL spécifié au lieu du défaut intégré. Voir vcl(7) pour les détails de la syntaxe VCL.

Si une seule option -f est utilisée, alors l'instance VCL chargée depuis le fichier est nommée "boot" et devient immédiatement active. Si plusieurs options -f sont utilisées, les instances VCL sont nommées "boot0", "boot1", et ainsi de suite, dans l'ordre correspondant aux arguments -f, et la dernière est nommée "boot", qui devient active.

Soit -b, soit une ou plusieurs options -f doivent être spécifiées, mais pas les deux, et ils ne peuvent pas être omis tous les deux, sauf si -d est utilisé pour démarrer varnishd en mode débogage. Si la chaîne vide est spécifiée comme seule option -f, alors varnishd démarre sans démarrer le processus worker, et le processus de gestion acceptera les commandes CLI. Vous pouvez également combiner une option -f vide avec un script d'initialisation (option -I) et le processus enfant sera démarré s'il y a une VCL active à la fin de l'initialisation.

Lorsqu'il est utilisé avec un nom de fichier relatif, config est recherché dans le vcl_path. Il est possible de définir ce chemin avant d'utiliser les options -f avec une option -p. Pendant le démarrage, varnishd ne se plaint pas des chemins VCL non sécurisés : contrairement au varnish-cli(7) qui pourrait être accédé plus tard à distance, le démarrage de varnishd nécessite des privilèges locaux.

-n rep_travail
Répertoire d'exécution pour la mémoire partagée, les VCL compilées, etc.

Dans les applications critiques en termes de performance, ce répertoire devrait être sur un système de fichiers monté en RAM.

Lors de l'exécution de plusieurs instances varnishd, des répertoires séparés doivent être utilisés.

La valeur par défaut est tirée de la variable d'environnement VARNISH_DEFAULT_N.

Les chemins relatifs seront ajoutés à /var/lib/varnish.

Si ni VARNISH_DEFAULT_N ni -n ne sont présents, la valeur est /var/lib/varnish/varnishd.

Note : Ces valeurs par défaut peuvent être spécifiques à la distribution.

Options de documentation

Pour ces options, varnishd imprime des informations sur la sortie standard et quitte. Lorsqu'une option -x est utilisée, elle doit être la seule option (elle produit la documentation en reStructuredText, aka RST).

-?

Imprime le message d'utilisation.
-x parametre
Imprime la documentation des paramètres d'exécution (options -p), voir Liste des Paramètres.
-x vsl
Imprime la documentation des balises utilisées dans le journal de mémoire partagée de Varnish, voir vsl(7).
-x cli
Imprime la documentation de l'interface de ligne de commande, voir varnish-cli(7).
-x builtin
Imprime le contenu du programme VCL par défaut builtin.vcl.
-x optstring
Imprime la chaîne d'options pour getopt(3) pour aider à l'écriture de scripts wrappers.

Options d'exploitation

-F
Ne pas dédoubler, exécuter au premier plan. Une seule option parmi -F ou -d peut être spécifiée, et -F ne peut pas être utilisée conjointement avec -C.
-T <adresse[:port]>
Offre une interface de gestion sur l'adresse et le port spécifiés. Voir varnish-cli(7) pour la documentation des commandes de gestion. Pour désactiver l'interface de gestion, utilisez none.
-M <adresse:port>
Se connecte à ce port et offre l'interface de ligne de commande. Considérez-le comme un shell inversé. En cas d'exécution avec -M et sans backend défini, le processus enfant (le cache) ne démarrera pas initialement.
-P fichier
>Écrire le PID du processus dans le fichier spécifié.
-i identity
Spécifiez l'identité du serveur Varnish. Ceci est accessible via server.identity depuis VCL.

L'identité du serveur est utilisée pour le champ received-by des en-têtes Via générés par Varnish. Pour cette raison, elle doit être un jeton valide tel que défini par la grammaire HTTP.

Si elle n'est pas spécifiée, le résultat de gethostname(3) est utilisé, auquel cas la syntaxe est supposée correcte.

-I clifile
Exécutez les commandes de gestion dans le fichier donné comme clifile avant le démarrage du processus worker, voir Fichier de commandes CLI.

Options de réglage

-t TTL
Spécifie le temps de vie (TTL) par défaut pour les objets mis en cache. Ceci est un raccourci pour spécifier le paramètre d'exécution default_ttl.
-p <param=valeur>
Définit le paramètre spécifié par param à la valeur spécifiée, voir Liste des paramètres pour les détails. Cette option peut être utilisée plusieurs fois pour spécifier plusieurs paramètres.
-s <[nom=]type[,options]>
Utilise le backend de stockage spécifié. Voir la section Backend de stockage.

Cette option peut être utilisée plusieurs fois pour spécifier plusieurs fichiers de stockage. Le nom est référencé dans les journaux, VCL, statistiques, etc. Si le nom n'est pas spécifié, "s0", "s1", etc. sont utilisés.

-l <vsl>
Spécifie la taille de l'espace pour les enregistrements VSL, raccourci pour -p vsl_space=<vsl>. Des suffixes d'échelle comme 'K' et 'M' peuvent être utilisés jusqu'à (G)igaoctets. Voir vsl_space pour plus d'informations.

Options de sécurité

-r <param[,param...]>
Rend les paramètres listés en lecture seule. Cela donne à l'administrateur système un moyen de limiter ce que le CLI Varnish peut faire. Envisagez de rendre les paramètres tels que cc_command, vcc_allow_inline_c et vmod_path en lecture seule car ils peuvent potentiellement être utilisés pour élever les privilèges depuis le CLI.
-S fichier-secret
Chemin vers un fichier contenant un secret utilisé pour autoriser l'accès au port de gestion. Pour désactiver l'authentification, utilisez none.

Si cet argument n'est pas fourni, un secret tiré du PRNG du système sera écrit dans un fichier nommé _.secret dans le répertoire de travail (voir opt_n) avec la propriété et les permissions de l'utilisateur qui a démarré varnish.

Ainsi, les utilisateurs souhaitant déléguer le contrôle sur varnish voudront probablement créer un fichier secret personnalisé avec les permissions appropriées (c'est-à-dire lisible par un groupe unix pour déléguer le contrôle).

-j <jail[,options_jail]>
Spécifie le mécanisme de jail à utiliser. Voir la section Jail.

Options avancées, de développement et de débogage

-d
Active le mode débogage : le processus parent s'exécute au premier plan avec une connexion CLI sur stdin/stdout, et le processus enfant doit être démarré explicitement avec une commande CLI. La terminaison du processus parent terminera également l'enfant.

Une seule des options -d ou -F peut être spécifiée, et -d ne peut pas être utilisée avec -C.

-C
Imprime le code VCL compilé en langage C et quitte. Spécifiez le fichier VCL à compiler avec l'option -f. Soit -f soit -b doit être utilisé avec -C, et -C ne peut pas être utilisé avec -F ou -d.
-V
Affiche le numéro de version et quitte. Ce doit être la seule option.
-h <type[,options]>
Spécifie l'algorithme de hachage. Voir la section Algorithme de hachage pour une liste des algorithmes supportés.
-W waiter
Spécifie le type de waiter à utiliser.

Algorithme de hachage

Les algorithmes de hachage suivants sont disponibles :

-h critbit
Structure d'arbre auto-redimensionnable. L'algorithme de hachage par défaut dans Varnish Cache 2.1 et versions ultérieures. Par rapport à un arbre B plus traditionnel, l'arbre critbit est presque entièrement sans verrou. Ne changez pas cela sauf si vous êtes certain de ce que vous faites.
-h simple_list
Une simple liste doublement chaînée. Non recommandé pour une utilisation en production.
-h <classic[,buckets]>
Une table de hachage standard. La clé de hachage est le CRC32 de l'URL de l'objet modulo la taille de la table de hachage. Chaque entrée de table pointe vers une liste d'éléments qui partagent la même clé de hachage. Le paramètre buckets spécifie le nombre d'entrées dans la table de hachage. La valeur par défaut est 16383.

Backend de stockage

Plusieurs backends de stockage (où les objets mis en cache et en cours sont conservés) peuvent être définis, et VCL peut piloter quel stockage est utilisé en définissant la variable beresp.storage (voir man vcl-var pour plus d'informations).

Le format de l'argument pour définir les backends de stockage est :

-s <[nom]=type[,options]>
Si nom est omis, Varnish nommera les stockages sN, en commençant par s0 et en incrémentant N pour chaque nouveau stockage.

Pour type et options, voir les détails ci-dessous.

Les stockages peuvent être utilisés en vcl comme storage.nom, donc, par exemple, si myStorage a été défini par -s myStorage=malloc,5G, il pourrait être utilisé en VCL comme suit :

set beresp.storage = storage.myStorage;

Un nom spécial est Transient, qui est le stockage par défaut pour les objets non cacheables résultant d'un passage, d'un hit-for-miss ou d'un hit-for-pass.

Si aucune option -s n'est donnée, la valeur par défaut est :

-s default,100m

Si aucun stockage Transient n'est défini, la valeur par défaut est un stockage default non lié, comme s'il était défini comme suit :

-s Transient=default

Les types et options de stockage suivants sont disponibles :

-s <default[,taille]>
Le type de stockage par défaut se résout en umem là où il est disponible et en malloc sinon.
-s <malloc[,taille]>
malloc est un backend basé sur la mémoire.
-s <umem[,taille]>
umem est un backend de stockage plus efficace que malloc sur les plateformes où il est disponible.

Voir la section sur umem dans le chapitre Backends de stockage de The Varnish Users Guide pour plus de détails.

-s <file,chemin[,taille[,granularité[,conseil]]]>
Le backend de fichier stocke les données dans un fichier sur disque. Le fichier sera accédé en utilisant mmap. Notez que ce stockage ne fournit aucune persistance du cache.

Le chemin est obligatoire. Si le chemin pointe vers un répertoire, un fichier temporaire sera créé dans ce répertoire et immédiatement détaché. Si le chemin pointe vers un fichier inexistant, le fichier sera créé.

Si la taille est omise et que le chemin pointe vers un fichier existant d'une taille supérieure à zéro, la taille de ce fichier sera utilisée. Sinon, une erreur sera signalée.

Granularité définit la taille du bloc d'allocation. Par défaut, c'est la taille de page du système ou la taille de bloc du système de fichiers, le plus grand des deux.

Conseil indique au noyau comment varnishd s'attend à utiliser cette région mappée afin que le noyau puisse choisir les techniques appropriées de prélecture et de mise en cache. Les valeurs possibles sont normal, random et sequential, correspondant respectivement aux arguments de conseil de l'appel madvise() MADV_NORMAL, MADV_RANDOM et MADV_SEQUENTIAL. Par défaut, c'est random.

-s <persistent,chemin,taille>
Stockage persistant. Varnish stockera les objets dans un fichier de manière à assurer la survie de la plupart des objets en cas d'arrêt planifié ou non planifié de Varnish. Le backend de stockage persistant présente plusieurs problèmes et sera probablement supprimé d'une future version de Varnish.

Jail

Les jails de Varnish sont une généralisation de diverses méthodes spécifiques à la plateforme pour réduire les privilèges des processus Varnish. Elles peuvent avoir des options spécifiques. Les jails disponibles sont :

-j <solaris[,worker=`privspec`]>
Réduit les privilèges(5) pour varnishd et les sous-processus à l'ensemble minimal requis. Uniquement disponible sur les plateformes qui ont l'appel setppriv(2).

L'argument optionnel worker peut être utilisé pour passer une spécification de privilèges (voir ppriv(1)) par laquelle étendre l'ensemble effectif du processus worker de varnish. Bien que des privilèges étendus puissent être requis par des vmods personnalisés, *ne pas* utiliser l'option worker est toujours plus sûr.

Exemple pour accorder des privilèges de base au processus worker :

-j solaris,worker=basic
-j <linux[,transparent_hugepage=`thp_setting`][,`unixjailoption`...]>
Par défaut sur les plateformes Linux, il étend la jail UNIX avec des mécanismes spécifiques à Linux :
  • Il émet un avertissement lorsque workdir n'est pas sur un tmpfs.
  • Il essaie de garder le processus dumpable après avoir abandonné les privilèges.
  • Il ajoute le contrôle sur le réglage des pages volumineuses transparentes (THP).

thp_setting peut prendre les valeurs suivantes :

  • ignore : Ne rien faire
  • enable : Activer THP (voir Note ci-dessous)
  • disable : Désactiver THP
  • try-disable (par défaut) : Essayer de désactiver, ignorer l'échec (mais émettre un avertissement)

Note : Techniquement, enable est "désactiver la désactivation", donc il n'active pas nécessairement THP. Les noms des paramètres ont été choisis pour éviter une double négation déroutante.

-j <unix[,user=`user`][,ccgroup=`group`][,workuser=`user`]>
Par défaut sur toutes les autres plateformes lorsque varnishd est démarré avec un UID effectif de 0 ("en tant que root").

Avec le mécanisme de jail unix activé, varnish passera à un utilisateur alternatif pour les sous-processus et modifiera l'UID effectif du processus maître chaque fois que possible.

L'argument optionnel user spécifie quel utilisateur alternatif utiliser. Il est par défaut varnish.

L'argument optionnel ccgroup spécifie un groupe à ajouter aux sous-processus varnish nécessitant l'accès à un compilateur C. Il n'y a pas de valeur par défaut.

L'argument optionnel workuser spécifie un utilisateur alternatif à utiliser pour le processus de travail. Il est par défaut vcache.

Les utilisateurs donnés pour les arguments user et workuser doivent avoir le même groupe principal ("login").

Pour configurer un système pour les utilisateurs par défaut avec un nom de groupe varnish, des commandes shell similaires à celles-ci peuvent être utilisées :

groupadd varnish
useradd -g varnish -d /nonexistent -s /bin/false \
  -c "Varnish-Cache Daemon User" varnish
useradd -g varnish -d /nonexistent -s /bin/false \
  -c "Varnish-Cache Worker User" vcache
-j none
choix de jail en dernier recours : Avec le mécanisme de jail none, varnish exécutera tous les processus avec les privilèges avec lesquels il a été démarré.

Interface de gestion

Si l'option -T a été spécifiée, varnishd proposera une interface de gestion en ligne de commande sur l'adresse et le port spécifiés. La méthode recommandée pour se connecter à l'interface de gestion en ligne de commande est via varnishadm(1).

Les commandes disponibles sont documentées dans varnish-cli(7).

Fichier de commandes CLI

L'option -I permet d'exécuter des commandes de gestion arbitraires lors du lancement de varnishd, avant que le processus de travail ne soit démarré. En particulier, c'est ainsi que l'on peut charger des configurations, leur appliquer des étiquettes, et rendre un instance VCL active utilisant ces étiquettes au démarrage :

vcl.load panic /etc/varnish_panic.vcl
vcl.load siteA0 /etc/varnish_siteA.vcl
vcl.load siteB0 /etc/varnish_siteB.vcl
vcl.load siteC0 /etc/varnish_siteC.vcl
vcl.label siteA siteA0
vcl.label siteB siteB0
vcl.label siteC siteC0
vcl.load main /etc/varnish_main.vcl
vcl.use main

Chaque ligne du fichier, y compris la dernière, doit être terminée par un saut de ligne ou un retour chariot, sinon elle sera considérée comme tronquée, ce qui constitue une erreur fatale.

Si une commande dans le fichier est préfixée par '-', l'échec n'interrompra pas le démarrage.

Notez qu'il est nécessaire d'inclure une commande explicite vcl.use pour sélectionner la VCL qui sera la VCL active lorsque vous utilisez le Fichier de Commandes CLI pour charger les configurations au démarrage.

PARAMETRES DE FONCTIONNEMENT

Les paramètres de fonctionnement peuvent être définis soit au démarrage avec l'option de ligne de commande -p pour varnishd(1), soit via l'interface CLI en utilisant les commandes param.set ou param.reset. Ils peuvent être verrouillés au démarrage avec l'option de ligne de commande -r.

Unités des paramètres de fonctionnement

Il existe différents types de paramètres qui peuvent accepter une liste de valeurs spécifiques, ou prendre optionnellement un suffixe d'unité.

bool

Un paramètre booléen accepte les valeurs on et off.

Il reconnaîtra également les valeurs suivantes :

  • yes et no
  • true et false
  • enable et disable

octets

Un paramètre en octets nécessite l'un des suffixes d'unité suivants :

  • b (octets)
  • k (kibioctets, 1024 octets)
  • m (mebioctets, 1024 kibioctets)
  • g (gibioctets, 1024 mebioctets)
  • t (tebioctets, 1024 gibioctets)
  • p (pebioctets, 1024 tebioctets)

Les unités multiplicatrices peuvent être suivies d'un b supplémentaire. Par exemple, 32k est équivalent à 32kb. Les unités d'octets ne sont pas sensibles à la casse.

secondes

Un paramètre de durée peut accepter les suffixes d'unités suivants :

  • ms (millisecondes)
  • s (secondes)
  • m (minutes)
  • h (heures)
  • d (jours)
  • w (semaines)
  • y (années)

Si le paramètre est un délai d'attente ou une échéance, une valeur de "never" (si autorisée) désactive l'effet du paramètre.

Indicateurs des paramètres de fonctionnement

Les paramètres de fonctionnement sont marqués par des indicateurs abrégés pour éviter de répéter le même texte encore et encore dans le tableau ci-dessous. La signification des indicateurs est :

  • experimental

    Nous n'avons aucune information solide sur les valeurs bonnes/mauvaises/optimales pour ce paramètre. Les retours d'expérience et les observations sont les bienvenus.

  • delayed

    Ce paramètre peut être modifié à la volée, mais ne prendra pas effet immédiatement.

  • restart

    Le processus de travail doit être arrêté et redémarré avant que ce paramètre ne prenne effet.

  • reload

    Les programmes VCL doivent être rechargés pour que ce paramètre prenne effet.

  • wizard

    Ne touchez pas à moins de savoir vraiment ce que vous faites.

  • only_root

    Ne fonctionne que si varnishd est exécuté en tant que root.

Exceptions de valeur par défaut sur les systèmes 32 bits

Attention, sur les systèmes 32 bits, certaines valeurs par défaut ou maximales sont réduites par rapport aux valeurs listées ci-dessous, afin de conserver de l'espace VM :

  • workspace_client: 24k
  • workspace_backend: 20k
  • http_resp_size: 8k
  • http_req_size: 12k
  • gzip_buffer: 4k
  • vsl_buffer: 4k
  • vsl_space: 1G (maximum)
  • thread_pool_stack: 64k

Liste des paramètres

Ce texte est produit à partir du même texte que vous trouverez dans l'interface CLI si vous utilisez la commande param.show :

accept_filter

NB : Ce paramètre dépend d'une fonctionnalité qui n'est pas disponible sur toutes les plateformes.

  • Unités : bool
  • Défaut : on (si votre plateforme prend en charge les filtres d'acceptation)

Active les filtres d'acceptation du noyau. Cela peut nécessiter qu'un module noyau soit chargé pour avoir un effet lorsqu'il est activé.

L'activation de accept_filter peut empêcher certaines requêtes d'atteindre Varnish en premier lieu. Les requêtes malformées peuvent passer inaperçues et n'augmenteront pas le compteur client_req_400. Les requêtes GET ou HEAD avec un corps peuvent être complètement bloquées.

acceptor_sleep_decay

  • Défaut : 0.9
  • Minimum : 0
  • Maximum : 1
  • Indicateurs : experimental

Si nous manquons de ressources, telles que des descripteurs de fichiers ou des threads de travail, l'accepteur dormira entre les acceptations. Ce paramètre réduit (multiplicativement) la durée du sommeil pour chaque acceptation réussie. (c'est-à-dire : 0.9 = réduction de 10 %)

acceptor_sleep_incr

  • Unités : secondes
  • Défaut : 0.000
  • Minimum : 0.000
  • Maximum : 1.000
  • Indicateurs : experimental

Si nous manquons de ressources, telles que des descripteurs de fichiers ou des threads de travail, l'accepteur dormira entre les acceptations. Ce paramètre contrôle combien de temps plus nous dormons, chaque fois que nous ne parvenons pas à accepter une nouvelle connexion.

acceptor_sleep_max

  • Unités : secondes
  • Par défaut : 0.050
  • Minimum : 0.000
  • Maximum : 10.000
  • Indicateurs : expérimental

Si nous manquons de ressources, telles que des descripteurs de fichiers ou des threads de travail, l'accepteur dormira entre les acceptations. Ce paramètre limite la durée pendant laquelle il peut dormir entre les tentatives d'acceptation de nouvelles connexions.

auto_restart

  • Unités : bool
  • Par défaut : on

Redémarre automatiquement le processus enfant/travailleur s'il meurt.

backend_idle_timeout

  • Unités : secondes
  • Par défaut : 60.000
  • Minimum : 1.000

Délai avant que nous ne fermions les connexions backend inutilisées.

backend_local_error_holddown

  • Unités : secondes
  • Par défaut : 10.000

  • Unités : bans
  • Par défaut : 0
  • Minimum : 0
  • Indicateurs : expérimental

Expurge le contenu de la "longue traîne" du cache pour maintenir le nombre d'interdictions en dessous de cette valeur. 0 désactive.

Lorsque ce paramètre est défini sur une valeur non nulle, le "ban lurker" continue de traiter la liste des interdictions comme d'habitude, de haut en bas, mais lorsqu'il atteint la énième interdiction (définie par ban_cutoff), il traite tous les objets comme s'ils correspondaient à une interdiction et les expurge du cache. Comme les objets activement utilisés sont testés par rapport à la liste des interdictions au moment de la requête et sont donc susceptibles d'être associés à des interdictions près du haut de la liste, avec ban_cutoff, les objets les moins récemment accédés (la "longue traîne") sont supprimés.

Ce paramètre est une mesure de sécurité pour éviter les temps de réponse médiocres dus aux interdictions testées au moment de la recherche. Définir une coupure échange le temps de réponse contre l'efficacité du cache. La valeur recommandée est proportionnelle au taux de bans_lurker_tests_tested / n_objects pendant que le ban lurker travaille, ce qui correspond au nombre d'interdictions que le système peut supporter. La latence supplémentaire due au test des interdictions de requête est de l'ordre de ban_cutoff / rate(bans_lurker_tests_tested). Par exemple, pour un taux de bans_lurker_tests_tested de 2M/s et une latence tolérable de 100 ms, une bonne valeur pour ban_cutoff peut être de 200K.

  • Unités : threads

  • Maximum : 95% de thread_pool_min
  • Indicateurs : delayed

Le nombre de threads de travail réservés pour les tâches vitales dans chaque pool.

Les tâches peuvent nécessiter la complétion d'autres tâches (par exemple, les requêtes client peuvent nécessiter des requêtes backend, les sessions http2 nécessitent des flux, qui nécessitent des requêtes). Cette réserve est là pour s'assurer que les tâches de priorité inférieure n'empêchent pas l'exécution des tâches de priorité supérieure, même sous forte charge.

La valeur effective est d'au moins 5 (le nombre de classes de priorité internes), quelle que soit ce paramètre.

thread_pool_stack

  • Unités : octets
  • Défaut : 80k
  • Minimum : sysconf(_SC_THREAD_STACK_MIN)
  • Indicateurs : delayed

Taille de la pile des threads de travail. Ceci sera probablement arrondi à un multiple de 4k (ou quelle que soit la taille de page) par le noyau.

La taille de pile requise est principalement déterminée par la profondeur de l'arbre d'appels. Les facteurs déterminants les plus courants dans le code de base de Varnish sont la compression/décompression GZIP, le traitement ESI et les correspondances d'expressions régulières. Les VMOD peuvent également nécessiter une quantité importante de pile supplémentaire. La profondeur imbriquée des sous-programmes VCL est un autre facteur, bien que généralement pas prédominant.

La taille de la pile est par thread, de sorte que la mémoire totale maximale requise pour les piles de threads de travail est de l'ordre de taille = thread_pools x thread_pool_max x thread_pool_stack.

Ainsi, en particulier pour les configurations avec de nombreux threads, maintenir la taille de la pile à un minimum aide à réduire la quantité de mémoire requise par Varnish.

D'autre part, thread_pool_stack doit être suffisamment grand dans toutes les circonstances, sinon varnish plantera en raison d'un débordement de pile. Habituellement, un débordement de pile se manifeste par une erreur de segmentation (également appelée segfault / SIGSEGV) avec l'adresse fautive proche du pointeur de pile (sp).

À moins que l'utilisation de la pile ne puisse être réduite, thread_pool_stack doit être augmenté lorsqu'un débordement de pile se produit. Il est recommandé de l'augmenter par incréments de 150% à 200% jusqu'à ce que les débordements de pile cessent.

thread_pools

  • Unités : pools
  • Défaut : 2
  • Minimum : 1
  • Maximum : 32
  • Indicateurs : delayed, experimental

Nombre de pools de threads de travail.

Augmenter le nombre de pools de travail diminue la contention des verrous. Trop de pools gaspillent du CPU et de la RAM, et plus d'un pool par CPU est très probablement préjudiciable aux performances.

Peut être augmenté à la volée, mais les diminutions nécessitent un redémarrage pour prendre effet, à moins que l'indicateur de débogage expérimental drop_pools ne soit défini.

CODES DE SORTIE

Varnish et les outils inclus sortiront, dans la plupart des cas, avec l'un des codes suivants

  • 0 OK
  • 1 Une erreur qui peut dépendre du système et/ou être transitoire
  • 2 Erreur de configuration / de paramètre grave - retenter avec la même configuration / les mêmes paramètres est très probablement inutile

Le processus maître varnishd peut également OR son code de sortie

  • avec 0x20 lorsque le processus enfant varnishd est mort,
  • avec 0x40 lorsque le processus enfant varnishd a été terminé par un signal et
  • avec 0x80 lorsqu'un cœur a été vidé.
