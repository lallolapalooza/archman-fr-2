NOM

VTC - Syntaxe des tests Varnish (Varnish Test Case)

APERÇU

Ce document décrit la syntaxe utilisée par les fichiers de tests Varnish (.vtc). Un fichier vtc décrit un scénario avec différentes entités scriptées parlant HTTP, et généralement une ou plusieurs instances de Varnish à tester.

ANALYSE SYNTAXIQUE

Un fichier vtc sera lu mot par mot, avec très peu de tokenisation, ce qui signifie qu'une erreur de syntaxe ne sera détectée que lorsque le test atteindra réellement l'action pertinente dans le test.

Une erreur d'analyse syntaxique déclenchera le plus souvent une assertion. Si cela se produit, veuillez vous référer au fichier source et au numéro de ligne correspondants. Cependant, ce guide devrait vous aider à éviter les erreurs les plus courantes.

Mots et chaînes

L'analyseur sépare les mots en détectant les caractères d'espacement et une chaîne est un mot, ou une série de mots sur la même ligne entourés de guillemets doubles ("..."), ou, pour les chaînes multi-lignes, entourés d'accolades ({...}).

Commentaires

Les espaces blancs en début de ligne sont ignorés. Les lignes vides (ou celles ne contenant que des espaces blancs) sont également ignorées, tout comme les lignes commençant par "#" qui sont des commentaires.

Lignes et commandes

Les fichiers de test prennent au maximum une commande par ligne, le premier mot de la ligne étant la commande et les suivants ses arguments. Pour continuer sur une nouvelle ligne sans casser la chaîne d'arguments, vous pouvez échapper le caractère de nouvelle ligne (\n) avec une barre oblique inverse (\).

MACROS

Lorsqu'une chaîne est traitée, une expansion de macro est effectuée. Les macros sont sous la forme ${<nom>[,<args>...]}, elles ont un nom suivi d'une liste optionnelle d'arguments séparés par des virgules ou des espaces. Les espaces en début et fin de chaîne sont ignorés.

Les macros ${foo,bar,baz} et ${ foo bar baz } sont équivalentes. Si un argument contient un espace ou une virgule, les arguments peuvent être mis entre guillemets. Par exemple, la macro ${foo,"bar,baz"} transmet un argument bar,baz à la macro nommée foo.

Sauf indication contraire, toutes les macros sont des macros simples qui ne prennent pas d'arguments.

Macros intégrées

${bad_backend}
Une adresse de socket qui n'acceptera jamais de connexions de manière fiable.
${bad_ip}
Une adresse IPv4 peu probable.
${date}
La date et l'heure actuelles formatées pour HTTP.
${listen_addr}
L'adresse d'écoute par défaut utilisée par divers composants, par défaut un port aléatoire sur localhost.
${localhost}
La première adresse IP qui se résout en "localhost".
${pwd}
Le répertoire de travail à partir duquel varnishtest a été exécuté.
${string,<action>[,<args>...]}
La macro string est le point d'entrée pour la génération de texte, elle prend une action spécialisée avec chacun ses propres arguments.
${string,repeat,<uint>,<str>}
Répète uint fois la chaîne str.
${testdir}
Le répertoire contenant le script VTC de l'exécution du cas de test en cours.
${tmpdir}
Le répertoire de travail dédié à l'exécution du cas de test en cours, qui est également le répertoire de travail actuel. Utile lorsqu'un chemin absolu vers le répertoire de travail est nécessaire.

SYNTAXE

barrière

NOTE : Cette commande est disponible partout où des commandes peuvent être données.

Les barrières permettent de synchroniser différents threads pour s'assurer que les événements se produisent dans le bon ordre. Il est même possible de les utiliser en VCL.

Tout d'abord, il est nécessaire de déclarer la barrière :

barrier bNOM TYPE NOMBRE [-cyclic]

Avec les arguments étant :

bNOM
c'est le nom de la barrière, utilisé pour l'identifier lorsque vous créerez des points de synchronisation. Il doit commencer par 'b'.
TYPE
il peut être "cond" (mutex) ou "sock" (socket) et définit le comportement interne. Si vous n'avez pas besoin de synchronisation VCL, utilisez cond.
NOMBRE
nombre de points de synchronisation nécessaires pour passer la barrière.
-cyclic
si présent, la barrière se réinitialise et est prête pour un nouveau cycle une fois franchie.

Ensuite, pour ajouter un point de synchronisation :

barrier bNOM sync

Cela bloquera le thread parent jusqu'à ce que le nombre de points de synchronisation pour bNOM atteigne le NOMBRE donné dans la déclaration de la barrière.

Si vous souhaitez synchroniser la VCL, vous devez déclarer une barrière "sock". Cela émettra une définition de macro nommée "bNOM_sock" que vous pouvez utiliser en VCL (après avoir importé le vmod vtc) :

vtc.barrier_sync("${bNOM_sock}");

Cette fonction retourne 0 si tout s'est bien passé et est l'équivalent de barrier bNOM sync au niveau supérieur du VTC.

client/serveur

Les threads clients et serveurs sont de fausses entités HTTP utilisées pour tester votre Varnish et votre VCL. Ils acceptent un nombre quelconque d'arguments, et ceux qui ne sont pas reconnus, en supposant qu'ils ne commencent pas par '-', sont traités comme des spécifications, décrivant les actions à entreprendre :

client cNOM [...]
serveur sNOM [...]

Les clients et serveurs sont identifiés par une chaîne qui est le premier argument, les noms des clients commencent par 'c' et ceux des serveurs par 's'.

Comme les commandes client et serveur partagent une bonne partie des arguments et des actions de spécification, elles sont regroupées dans cette section unique, les éléments spécifiques seront explicitement marqués comme tels.

Macros et comportement automatique

Pour simplifier les choses dans le cas général, les clients se connectent par défaut à un serveur Varnish appelé v1. Pour se connecter à un autre serveur Varnish, utilisez '-connect ${vNAME_sock}'.

Le commutateur -vcl+backend de la commande varnish ajoutera tous les serveurs déclarés en tant que backends. Faites attention cependant, les serveurs écouteront par défaut sur l'IP 127.0.0.1 et choisiront un port aléatoire, et publieront 3 macros : sNAME_addr, sNAME_port et sNAME_sock, mais seulement une fois qu'ils seront démarrés. Pour que 'varnish -vcl+backend' crée le vcl avec les bonnes valeurs, le serveur doit être démarré en premier.

Fait comme chunked sauf que la chaîne sera générée pour vous, avec une longueur de NOMBRE caractères.

Ferme la connexion. Notez que si l'on opère en mode HTTP/2, aucune trame supplémentaire (GOAWAY) n'est envoyée, il s'agit simplement d'une fermeture TCP.

Teste si "CHAÎNE1 OP CHAÎNE2" est vrai, et sinon, échoue le test. OP peut être ==, <, <=, >, >= lorsque CHAÎNE1 et CHAÎNE2 représentent des nombres, auquel cas il s'agit d'un opérateur de comparaison. Si CHAÎNE1 et CHAÎNE2 sont destinées à être des chaînes, OP est un opérateur de correspondance, soit == (correspondance exacte), soit ~ (correspondance d'expression régulière).

logexpect

Lit le VSL et recherche des enregistrements correspondant à un spécifié

ification. Il traitera les enregistrements en essayant de faire correspondre le premier modèle, et une fois terminé, continuera le traitement, en essayant de faire correspondre le modèle suivant. Si un modèle n'est pas trouvé, le test échouera.

Les threads logexpect sont déclarés comme suit :

logexpect lNAME -v <id> [-g <grouping>] [-d 0|1] [-q query] \
        [arguments vsl] {
                expect <skip> <vxid> <tag> <regex>
                expect <skip> <vxid> <tag> <regex>
                fail add <vxid> <tag> <regex>
                fail clear
                abort
                ...
        } [-start|-wait|-run]

Et une fois déclarés, vous pouvez les démarrer ou attendre qu'ils se terminent :

logexpect lNAME <-start|-wait>

Avec :

lNAME
Nom du thread logexpect, il doit commencer par 'l'.
-v id
Spécifie l'instance varnish à utiliser (le plus souvent, id=v1).
-g <session|request|vxid|raw
Décide comment les enregistrements sont groupés, voir -g dans man varnishlog pour plus d'informations.
-d <0|1>
Commence le traitement des enregistrements de log depuis le début du log au lieu de la fin.
-q query
Filtre les enregistrements en utilisant une expression de requête, voir man vsl-query pour plus d'informations. Les options -q multiples ne sont pas supportées.
-m
Émet également des enregistrements de log pour les misses (uniquement pour le débogage)
-err
Inverse la signification du succès. Généralement appelé une fois pour s'attendre à ce que logexpect échoue.
-start
Démarre le thread logexpect en arrière-plan.
-wait
Attend que le thread logexpect se termine.
-run
Équivalent à "-start -wait".

Arguments VSL (similaires aux options varnishlog) :

-C
Utilise les regex insensible à la casse.
-i <taglist>
Inclut les tags.
-I <[taglist:]regex>
Inclut par regex.
-T <secondes>
Délai d'attente de fin de transaction.

Spécification d'attente :

skip: [uint|*|?]
Nombre maximum d'enregistrements à sauter.
vxid: [uint|*|=]
vxid à faire correspondre.
tag: [nom_tag|*|=]
Tag à faire correspondre.
regex:
Expression régulière à faire correspondre (optionnel).

Pour skip, vxid et tag, '*' correspond à n'importe quoi, '=' attend la valeur de l'enregistrement précédemment correspondant. Le marqueur '?' est équivalent à zéro, attendant une correspondance sur l'enregistrement suivant. La différence est que '?' peut être utilisé lorsque l'ordre des logs consécutifs individuels n'est pas déterministe. En d'autres termes, les lignes d'un bloc d'alternatives marquées par '?' peuvent être correspondantes dans n'importe quel ordre, mais toutes doivent correspondre finalement.

Spécification d'échec :

add: Ajoute à la liste d'échecs.

Les arguments sont équivalents à expect, sauf pour skip qui est manquant.

clear: Efface la liste d'échecs.

Un nombre quelconque de spécifications d'échec peut être actif pendant l'exécution d'un logexpect. Toutes les spécifications d'échec actives sont comparées à chaque ligne de log et, si l'une d'elles correspond, le logexpect échoue immédiatement.

Pour qu'un logexpect se termine avec succès, il ne doit y avoir aucune spécification dans la liste d'échecs, donc les logexpects doivent toujours se terminer par

expect <skip> <vxid> <tag> <condition-de-terminaison> fail clear

Spécification d'interruption :

abort(3) varnishtest, destiné à aider au débogage de la bibliothèque client VSL elle-même.

process

Exécute un processus avec stdin+stdout sur un pseudo-terminal et stderr sur un pipe.

La sortie du pseudo-terminal est copiée telle quelle dans ${pNAME_out}, et les drapeaux -log/-dump/-hexdump la placeront également dans le vtc-log.

Le pseudo-terminal n'est pas en mode ECHO, mais si les programmes exécutés le règlent en mode ECHO ("stty sane"), toute entrée envoyée au processus apparaîtra également dans ce flux en raison de l'ECHO.

La sortie du pipe stderr est copiée telle quelle dans ${pNAME_err}, et est toujours incluse dans le vtc_log.

process pNAME SPEC [-allow-core] [-expect-exit N] [-expect-signal N]
[-dump] [-hexdump] [-log] [-run] [-close] [-kill SIGNAL] [-start] [-stop] [-wait] [-write CHAINE] [-writeln CHAINE] [-writehex CHAINEHEX] [-need-bytes [+]NOMBRE] [-screen-dump] [-winsz LIGNES COLONNES] [-ansi-response] [-expect-cursor LIGNE COLONNE] [-expect-text LIGNE COLONNE TEXTE] [-match-text LIGNE COLONNE REGEXP]
pNAME
Nom du processus. Il doit commencer par 'p'.
SPEC
La ou les commandes à exécuter dans ce processus.
-hexdump
Enregistre la sortie avec vtc_hexdump(). Doit précéder -start/-run.
-dump
Enregistre la sortie avec vtc_dump(). Doit précéder -start/-run.
-log
Enregistre la sortie avec VLU/vtc_log(). Doit précéder -start/-run.
-start
Démarre le processus.
-expect-exit N
Attend le code de sortie N.
-expect-signal N
Attend le signal N dans le code de sortie.
-allow-core
Une vidage de noyau dans le code de sortie est acceptable.
-wait
Attend que le processus se termine.
-run
Raccourci pour -start -wait.

Dans la plupart des cas, si vous voulez juste démarrer un processus et attendre sa fin, vous pouvez utiliser la commande shell à la place. Les commandes suivantes sont équivalentes :

shell "do --something"
process p1 "do --something" -run

Cependant, vous pouvez utiliser la variante process pour collecter commodément l'entrée et la sortie standard sans avoir à vous occuper vous-même des redirections shell. La commande shell peut également attendre une expression de n'importe quelle sortie, envisagez de l'utiliser si vous n'avez besoin de faire correspondre qu'une seule.

-key KEYSYM
Envoie une touche émulée. KEYSYM peut être l'un des éléments suivants (NPAGE, PPAGE, HOME, END)
-kill SIGNAL
Envoie un signal au processus. L'argument peut être soit la chaîne "TERM", "INT", ou "KILL" pour les signaux SIGTERM, SIGINT ou SIGKILL, respectivement, soit un tiret (-) suivi du numéro de signal.

Si vous avez besoin d'utiliser d'autres noms de signaux, vous pouvez utiliser la commande kill(1) directement :

shell "kill -USR1 ${pNAME_pid}"

Notez que l'utilisation de SIGHUP est déconseillée dans les cas de test.

Raccourci pour -kill TERM.
-close
Alias pour "-kill HUP".
-winsz LIGNES COLONNES

-write CHAINE
Écrit une chaîne dans l'entrée standard du processus.
-writeln CHAINE

-writehex CHAINEHEX

-need-bytes [+]NOMBRE

-ansi-response

-expect-cursor LIGNE COLONNE

stream

(note : cette section est au niveau supérieur pour une navigation plus facile, mais elle fait partie de la spécification client/serveur)

Les flux correspondent approximativement à une requête dans HTTP/2, une requête est envoyée sur le flux N, la réponse aussi, puis le flux est discardé. La principale exception est le premier flux, 0, qui sert de coordinateur.

La syntaxe des flux suit celle du client/serveur :

stream ID [SPEC] [ACTION]

ID est le numéro de flux HTTP/2, tandis que SPEC décrit ce qui sera fait dans ce flux. Si ID a la valeur next, le numéro de flux réel est calculé en fonction du dernier.

Notez que, lors de l'analyse d'une action de flux, si l'entité n'opère pas en mode HTTP/2, ces spécifications sont exécutées avant :

txpri/rxpri # client/serveur
stream 0 {
    txsettings
    rxsettings
    txsettings -ack
    rxsettings
    expect settings.ack == true
} -run

Et le mode HTTP/2 est ensuite activé avant l'analyse de la spécification.

Actions

-start
Exécute la spécification dans un thread, redonnant le contrôle immédiatement.
-wait
Attend que le thread démarré termine l'exécution de la spécification.
-run
équivalent à appeler -start puis -wait.

Specification

La spécification d'un flux suit exactement les mêmes règles que celle d'un client ou d'un serveur.

txreq, txresp, txcont, txpush

Ces quatre commandes concernent l'envoi d'en-têtes. txreq et txresp enverront des trames HEADER ; txcont enverra des trames CONTINUATION ; txpush des trames PUSH. La seule différence entre txreq et txresp réside dans les en-têtes par défaut définis par chacune d'elles.

-noadd
N'ajoute pas les en-têtes par défaut. Utile pour éviter les doublons lors de l'envoi d'en-têtes par défaut à l'aide de -hdr, -idxHdr et -litIdxHdr.
-status INT (txresp)
Définit le pseudo-en-tête :status.
-url STRING (txreq, txpush)
Définit le pseudo-en-tête :path.
-method STRING (txreq, txpush)
Définit le pseudo-en-tête :method.
-req STRING (txreq, txpush)
Alias pour -method.
-scheme STRING (txreq, txpush)
Définit le pseudo-en-tête :scheme.
-hdr STRING1 STRING2
Insère un en-tête, STRING1 étant le nom et STRING2 la valeur.
-idxHdr INT
Insère un en-tête indexé, en utilisant INT comme index.
-litIdxHdr inc|not|never INT huf|plain STRING
Insère un en-tête littéral indexé. Le premier argument spécifie si l'en-tête doit être ajouté à la table, ne doit pas l'être, ou ne doit pas être compressé s'il est retransmis.

INT est l'index du nom de l'en-tête à utiliser.

Le troisième argument informe sur le codage Huffman : oui (huf) ou non (plain).

Le dernier terme est la valeur littérale de l'en-tête.

-litHdr inc|not|never huf|plain STRING1 huf|plain STRING2
Insère un en-tête littéral, avec le même premier argument que -litIdxHdr.

Les deuxième et troisième termes indiquent le nom de l'en-tête et s'il doit être codé en Huffman, tandis que les deux derniers font de même concernant la valeur.

-body STRING (txreq, txresp)
Spécifie un corps, plaçant effectivement STRING dans une trame DATA après l'envoi de la trame HEADER.
-bodyfrom FILE (txreq, txresp)
Identique à -body mais le contenu est lu à partir de FILE.
-bodylen INT (txreq, txresp)
Fait la même chose que -body mais génère une chaîne de INT longueur pour vous.
-gzipbody STRING (txreq, txresp)
Gzippe STRING et l'envoie comme corps.
-gziplen NUMBER (txreq, txresp)
Combine -bodylen et -gzipbody : génère une chaîne de longueur NUMBER, la zippe et l'envoie comme corps.
-nostrend (txreq, txresp)
Ne définit pas automatiquement le drapeau END_STREAM, ce qui fait que le pair attend un corps après les en-têtes.
-nohdrend
Ne définit pas automatiquement le drapeau END_HEADERS, ce qui fait que le pair attend plus de trames HEADER.
-dep INT (txreq, txresp)
Indique au pair que ce contenu dépend du flux avec l'ID INT.
-ex (txreq, txresp)
Rend la dépendance exclusive (-dep est toujours nécessaire).
-weight (txreq, txresp)
Définit le poids de la dépendance.
-promised INT (txpush)
L'ID du flux promis.
-pad STRING / -padlen INT (txreq, txresp, txpush)
Ajoute la chaîne comme padding à la trame, soit celle que vous avez fournie avec -pad, soit une générée pour vous, de longueur INT dans le cas de -padlen.

txdata

Par défaut, les trames de données sont vides. Le destinataire saura que tout le corps a été livré grâce au drapeau END_STREAM défini dans la dernière trame DATA, et txdata le définit automatiquement.

-data STRING
Données à intégrer dans la trame.
-datalen INT
Génère une chaîne de INT octets de long à envoyer dans la trame.
-pad STRING / -padlen INT
Ajoute la chaîne comme padding à la trame, soit celle que vous avez fournie avec -pad, soit une générée pour vous, de longueur INT dans le cas de -padlen.
-nostrend
Ne définit pas le drapeau END_STREAM, permettant d'envoyer plus de données sur ce flux.

rxreq, rxresp

Ce sont deux fonctions pratiques pour recevoir les en-têtes et le corps d'une requête ou d'une réponse entrante. La seule différence est que rxreq ne peut être utilisée que par un serveur, et rxresp par un client.

-all

-some INT
Récupère INT - 1 trames CONTINUATION après la trame HEADER.

Cela fonctionne comme rxhdrs, attendant une trame PUSH puis zéro ou plusieurs trames CONTINUATION.

Continue d'attendre des trames CONTINUATION jusqu'à ce que le drapeau END_HEADERS soit vu.

Récupère INT - 1 trames CONTINUATION après la trame PUSH.

tunnel

L'objectif d'un tunnel est d'aider à contrôler le transfert de données entre deux parties, par exemple pour déclencher des timeouts de socket au milieu des trames de protocole, sans avoir besoin de modifier la façon dont les deux parties sont implémentées.

Un tunnel accepte une connexion puis se connecte au nom de la source à la destination souhaitée. Une fois les deux connexions établies, le tunnel transférera les octets inchangés entre la source et la destination. Le transfert peut être interrompu, généralement à l'aide de méthodes de synchronisation comme les barrières. Une fois le transfert mis en pause, il est possible de laisser une quantité spécifique d'octets circuler dans un sens ou dans l'autre.

Arguments

-start
Démarre le tunnel en arrière-plan, traitant la dernière spécification donnée.
-start+pause
Démarre le tunnel, mais déjà en pause.
-wait
Bloque jusqu'à ce que le thread se termine.
-listen STRING
Indique le socket d'écoute pour le serveur. STRING est de la forme "IP PORT", ou "HOST PORT".

Écoute par défaut sur un port aléatoire local.

-connect STRING
Indique le serveur auquel se connecter. STRING est également de la forme "IP PORT", ou "HOST PORT".

Se connecte par défaut à une instance varnish nommée v1.

Spécification

La spécification contient une liste de commandes de tunnel qui peuvent être combinées avec des barrières et des délais. Par exemple :

tunnel t1 {
    barrier b1 sync
    pause
    delay 1
    send 42
    barrier b2 sync
    resume
} -start

Si une extrémité du tunnel est fermée avant la fin de la spécification, le cas de test échouera. Une spécification qui se termine dans un état de pause reprendra implicitement le tunnel.

pause
Attend que les octets en transit soient transférés et met le tunnel en pause.

Le tunnel doit être en cours d'exécution.

recv NUMBER
Attend que NUMBER octets soient transférés de la destination vers la source.

Le tunnel doit être en pause, il reste en pause ensuite.

resume
Reprend le transfert des octets dans les deux directions.

Le tunnel doit être en pause.

send NUMBER
Attend que NUMBER octets soient transférés de la source vers la destination.

Le tunnel doit être en pause, il reste en pause ensuite.

Définit et interagit avec des instances varnish.

Pour définir un serveur Varnish, vous utiliserez cette syntaxe :

varnish vNAME [-arg STRING] [-vcl STRING] [-vcl+backend STRING]
        [-errvcl STRING STRING] [-jail STRING] [-proto PROXY]

La première invocation de varnish vNAME démarrera le processus maître varnishd en arrière-plan, attendant le switch -start pour réellement démarrer le processus enfant.

Types utilisés dans la description ci-dessous :

PATTERN
est un motif de style 'glob' (c'est-à-dire : fnmatch(3)) tel qu'utilisé dans l'expansion de noms de fichiers du shell.

Arguments :

vNAME
Identifie le serveur Varnish avec une chaîne, elle doit commencer par 'v'.
-arg STRING
Passe un argument à varnishd, par exemple "-h simple_list".

Si les macros ${varnishd_args_prepend} ou ${varnishd_args_append} sont définies, elles sont développées et insérées avant / ajoutées à la ligne de commande de varnishd telle que construite par varnishtest, avant que la ligne de commande elle-même ne soit développée. Cela permet des ajustements à la ligne de commande de varnishd sans modifier les cas de test. Ces macros peuvent être définies à l'aide de l'option -D pour varnishtest.

-vcl STRING
Spécifie le VCL à charger sur cette instance Varnish. Vous voudrez probablement utiliser des chaînes multilignes pour cela ({...}).
-vcl+backend STRING
Fait exactement la même chose que -vcl, mais ajoute le bloc de définition des backends connus (c'est-à-dire déjà définis).
-errvcl STRING1 STRING2
Charge STRING2 comme VCL, en s'attendant à ce que cela échoue, et que Varnish envoie une chaîne d'erreur correspondant à STRING1.
-jail STRING
Consultez man varnishd (-j) pour plus d'informations.
-proto PROXY
Demande à Varnish d'utiliser le protocole proxy. Notez que PROXY est ici la chaîne réelle.

Vous pouvez décider de démarrer l'instance Varnish et/ou d'attendre plusieurs événements :

varnish vNAME [-start] [-wait] [-wait-running] [-wait-stopped]
-start
Démarre le processus enfant.

Une fois démarré avec succès, les macros suivantes sont disponibles pour l'adresse d'écoute par défaut : ${vNAME_addr}, ${vNAME_port} et ${vNAME_sock}. Des macros supplémentaires sont disponibles, y compris l'écoute de l'adresse

vtc(7) — Varnish Test Controller

NAME

vtc — Varnish Test Controller

OVERVIEW

The Varnish test suite uses a test script language which can be used to control Varnish instances and verify their behaviour. This manual page describes the commands available in that language.

The test script language has a small set of commands that can be used to control Varnish instances and verify their behaviour.

varnish

Start and manage Varnish instances. The syntax is:

varnish vNAME [-svl|VARNISH_PROG] [-flags STRING] [-vcl STRING]
              [-connect-timeout NUMBER] [-subdir STRING]
              [-start-timeout NUMBER] [-wait] [-stop]
              [-syntax LEVEL] [-wait-running] [-wait-stopped]
              [-cleanup] [-expectexit NUMBER]
vNAME
Identify the varnish instance. The name must start with a ‘v’. A varnish instance is a full varnishd process.
-svl|VARNISH_PROG
Specify the varnishd executable to use. Defaults to varnishd. This option can be used multiple times to specify different executables, and the test will try to use them in the order specified.
-flags STRING
Set the varnishd command line flags. The string is appended to the command line for the varnishd executable.
-vcl STRING
Set the VCL configuration for this instance. The STRING is the name of the VCL file to use. The file is expected to be in the ./vcl directory.
-connect-timeout NUMBER
Set the timeout for connecting to the varnish instance. Default is 5 seconds.
-subdir STRING
Set the subdirectory for the varnish instance. This is used to specify where the varnish instance should be created. By default, this is ${v1_dir}.
-start-timeout NUMBER
Wait for the varnish instance to start for at most NUMBER seconds. Default is 5 seconds.

This command also defines a variable ${vNAME_addr} which contains the address, and ${vNAME_port} which contains the port varnish is listening on. Also ${vNAME_dir} which contains the directory the instance is running in.

The following options control the lifecycle of the varnish instance:

-wait
Wait for the varnish instance to terminate.
-stop
Stop the child process.
-syntax
Set the VCL syntax level for this command (default: 4.1)
-wait
Wait for that instance to terminate.
-wait-running
Wait for the Varnish child process to be started.
-wait-stopped
Wait for the Varnish child process to stop.
-cleanup
Once Varnish is stopped, clean everything after it. This is only used in very few tests and you should never need it.
-expectexit NUMBER
Expect varnishd to exit(3) with this value

Once Varnish is started, you can talk to it (as you would through varnishadm) with these additional switches:

varnish vNAME [-cli STRING] [-cliok STRING] [-clierr STRING]
              [-clijson STRING]
-cli STRING|-cliok STRING|-clierr STATUS STRING|-cliexpect REGEXP STRING
All four of these will send STRING to the CLI, the only difference is what they expect the result to be. -cli doesn't expect anything, -cliok expects 200, -clierr expects STATUS, and -cliexpect expects the REGEXP to match the returned response.
-clijson STRING
Send STRING to the CLI, expect success (CLIS_OK/200) and check that the response is parsable JSON.

It is also possible to interact with its shared memory (as you would through tools like varnishstat) with additional switches:

-expect !PATTERN|PATTERN OP NUMBER|PATTERN OP PATTERN
Look into the VSM and make sure the first VSC counter identified by PATTERN has a correct value. OP can be ==, >, >=, <, <=. For example:
varnish v1 -expect SM?.s1.g_space > 1000000
varnish v1 -expect cache_hit >= cache_hit_grace

In the ! form the test fails if a counter matches PATTERN.

The MAIN. namespace can be omitted from PATTERN.

The test takes up to 5 seconds before timing out.

-vsc PATTERN
Dump VSC counters matching PATTERN.
-vsl_catchup
Wait until the logging thread has idled to make sure that all the generated log is flushed

varnishtest

Alternate name for 'vtest', see above.

vsm

Interact with the shared memory of a varnish instance.

To define a VSM consumer, use this syntax:

vsm mNAME [-n STRING]

Arguments:

mNAME
Identify the VSM consumer, it must starts with 'm'.
-n STRING
Choose the working directory of the varnish instance. By default a VSM consumer connects to ${v1_name}.
-attach
Attach to a new varnish instance. Implicitly detach from the current varnish instance if applicable.
-detach
Detach from the current varnish instance.
-expect-status STRING
Check that the status of VSM matches the list of status flags from STRING. The expected status is represented as a comma-separated list of flags. The list of flags in STRING is not sensitive to the order of flags.

The available flags are:

  • mgt-running
  • mgt-changed
  • mgt-restarted
  • wrk-running
  • wrk-changed
  • wrk-restarted

Expecting a status automatically attaches to the varnish instance if that was not already the case.

vtest

This should be the first command in your vtc as it will identify the test case with a short yet descriptive sentence. It takes exactly one argument, a string, eg:

vtest "Check that vtest is actually a valid command"

It will also print that string in the log.
