virtualenv est un outil pour créer des environnements Python isolés.

VIRTUALENV VS VENV

Depuis Python 3.3, une partie de cet outil a été intégrée à la bibliothèque standard sous le module venv https://docs.python.org/3/library/venv.html. Le module venv n'offre pas toutes les fonctionnalités de cette bibliothèque, pour n'en nommer que quelques-unes des plus importantes :

  • il est plus lent (car il n'a pas la méthode de "seed" app-data),
  • il n'est pas aussi extensible,
  • il ne peut pas créer d'environnements virtuels pour des versions Python installées arbitrairement (et les découvrir automatiquement),
  • il n'est pas possible de le mettre à jour via pip https://pip.pypa.io/en/stable/installing/,
  • il n'a pas d'API programmatique aussi riche (pour décrire des environnements virtuels sans les créer).

CONCEPT ET BUT DE VIRTUALENV

Le problème fondamental auquel on s'attaque est celui des dépendances et des versions, et indirectement des permissions. Imaginez que vous ayez une application qui nécessite la version 1 de LibFoo, mais qu'une autre application requière la version 2. Comment utiliser ces deux bibliothèques ? Si vous installez tout dans votre Python global (par exemple, python3.8), il est facile de se retrouver dans une situation où deux paquets ont des exigences conflictuelles.

Ou plus généralement, que faire si vous voulez installer une application et la laisser tranquille ? Si une application fonctionne, tout changement dans ses bibliothèques ou dans les versions de ces bibliothèques peut la casser. De plus, que faire si vous ne pouvez pas installer de paquets dans le répertoire global site-packages, car vous n'avez pas les permissions pour modifier l'environnement Python global ?

Dans tous ces cas, virtualenv peut vous aider. Il crée un environnement qui a ses propres répertoires d'installation, qui ne partage pas les bibliothèques avec d'autres environnements virtualenv (et qui, optionnellement, n'accède pas non plus aux bibliothèques installées globalement).

Installation

via pipx

virtualenv https://pypi.org/project/virtualenv est un outil CLI qui nécessite un interpréteur Python pour fonctionner. Si vous avez déjà un interpréteur Python 3.7+, il est préférable d'utiliser pipx https://pypi.org/project/pipx pour installer virtualenv dans un environnement isolé. Cela a l'avantage de vous permettre plus tard de mettre à jour virtualenv sans affecter d'autres parties du système.

pipx install virtualenv
virtualenv --help

via pip

Alternativement, vous pouvez l'installer dans l'interpréteur Python global lui-même (peut-être en tant que paquet utilisateur via le drapeau --user). Soyez prudent si vous utilisez une installation Python gérée par votre système d'exploitation ou un autre gestionnaire de paquets. pip peut ne pas se coordonner avec ces outils et peut laisser votre système dans un état incohérent. Notez que si vous choisissez cette voie, vous devez vous assurer que pip est suffisamment récent, conformément aux sous-sections ci-dessous :

python -m pip install --user virtualenv
python -m virtualenv --help

wheel

L'installation de virtualenv via une roue (wheel, par défaut avec pip) nécessite un installateur capable de comprendre la balise python-requires (voir PEP-503 https://www.python.org/dev/peps/pep-0503/), avec pip, il s'agit de la version 9.0.0 (sortie en novembre 2016). De plus, si vous ne l'installez pas via PyPi, vous devez utiliser un miroir qui transmet correctement la balise python-requires (notamment les miroirs OpenStack ne le font pas, ou les anciennes versions de devpi https://github.com/devpi/devpi - ajoutée avec la version 4.7.0).

Introduction

Virtualenv a une commande de base :

virtualenv venv

Note :

Lors de la création d'un environnement virtuel, il est recommandé d'utiliser une version spécifique de Python, par exemple, en appelant virtualenv avec python3.10 -m virtualenv venv. Si vous utilisez une commande générique comme python3 -m virtualenv venv, l'environnement créé sera lié à /usr/bin/python3. Cela peut poser problème car lorsqu'une nouvelle version de Python est installée sur le système, le lien symbolique /usr/bin/python3 sera probablement mis à jour pour pointer vers la nouvelle version. Cela amènera l'environnement virtuel à utiliser involontairement la nouvelle version de Python, ce qui n'est souvent pas le comportement souhaité. L'utilisation d'une version spécifique garantit que l'environnement virtuel est lié à cette version exacte, offrant ainsi stabilité et prévisibilité.

Cela créera un environnement virtuel Python de la même version que virtualenv, installé dans le sous-répertoire venv. L'outil en ligne de commande possède de nombreux indicateurs qui modifient son comportement, pour une liste complète, consultez les indicateurs CLI <#cli-flags>.

L'outil fonctionne en deux phases :

  • Phase 1 découvre un interpréteur Python pour créer un environnement virtuel à partir duquel (par défaut, il s'agit du même Python que celui que virtualenv utilise, cependant, nous pouvons modifier cela via l'option p <#p>).
  • Phase 2 crée un environnement virtuel à la destination spécifiée (dest <#dest>), cela peut être décomposé en quatre sous-étapes supplémentaires :
  • créer un Python qui correspond à l'interpréteur Python cible de la phase 1,
  • installer (amorcer) les paquets de semence (un ou plusieurs de pip https://pypi.org/project/pip, setuptools https://pypi.org/project/setuptools, wheel https://pypi.org/project/wheel) dans l'environnement virtuel créé,
  • installer les scripts d'activation dans le répertoire binaire de l'environnement virtuel (ceux-ci permettront aux utilisateurs finaux d' *activer* l'environnement virtuel depuis différents shells).
  • créer des fichiers qui marquent l'environnement virtuel comme devant être ignoré par les systèmes de contrôle de version (actuellement, nous prenons en charge Git uniquement, car Mercurial, Bazaar ou SVN ne prennent pas en charge les fichiers ignore dans les sous-répertoires). Cette étape peut être ignorée avec l'option no-vcs-ignore <#no-vcs-ignore>.

Le Python de votre nouveau virtualenv est effectivement isolé du Python qui a été utilisé pour le créer.

Découverte Python

La première chose dont nous avons besoin pour pouvoir créer un environnement virtuel est un interpréteur Python. Cela décrira à l'outil quel type d'environnement virtuel vous souhaitez créer, considérez-le comme : version, architecture, implémentation.

virtualenv étant une application Python, dispose toujours d'au moins un interpréteur disponible, celui que virtualenv utilise lui-même, et à ce titre, c'est l'élément découvert par défaut. Cela signifie que si vous installez virtualenv sous Python 3.8, virtualenv créera par défaut des environnements virtuels qui sont également de version 3.8.

Les environnements virtuels Python créés ne sont généralement pas autonomes. Un empaquetage Python complet est généralement composé de milliers de fichiers, il n'est donc pas efficace d'installer l'intégralité de Python à nouveau dans un nouveau dossier. Au lieu de cela, les environnements virtuels ne sont que des shells, qui contiennent peu en eux-mêmes, et empruntent la plupart de leurs ressources au Python système (c'est ce que vous avez installé, lorsque vous avez installé Python lui-même). Cela signifie que si vous mettez à niveau votre Python système, vos environnements virtuels *pourraient* se casser, alors soyez prudent. L'avantage, en se référant au Python système, est que la création d'environnements virtuels peut être rapide.

Ici, nous décrirons le mécanisme intégré (notez que cela peut être étendu par des plugins). L'indicateur CLI p <#p> ou python <#python> vous permet de spécifier un spécificateur Python pour le type d'environnement virtuel que vous souhaitez, le format est soit :

  • un chemin relatif/absolu vers un interpréteur Python,
  • un spécificateur identifiant l'implémentation Python, vers
ion, architecture dans le format suivant : 
{nom de l'implémentation python}{version}{architecture}

Nous avons les restrictions suivantes :

  • l'implémentation python est composée uniquement de caractères alphabétiques (python signifie n'importe quelle implémentation, et s'il est manquant, la valeur par défaut est python),
  • la version est un numéro de version séparé par des points, éventuellement suivi de t pour le threading libre,
  • l'architecture est soit -64 soit -32 (manquant signifie n'importe laquelle).

Par exemple :

  • python3.8.1 signifie n'importe quelle implémentation python ayant la version 3.8.1,
  • 3 signifie n'importe quelle implémentation python ayant la version majeure 3,
  • 3.13t signifie n'importe quelle implémentation python ayant la version 3.13 avec threading libre,
  • cpython3 signifie une implémentation CPython ayant la version 3,
  • pypy2 signifie un interpréteur python avec l'implémentation PyPy et la version majeure 2.

Étant donné le spécificateur virtualenv appliquera la stratégie suivante pour découvrir/trouver l'exécutable système :

  • Si nous sommes sous Windows, nous consulterons le registre Windows et vérifierons s'il existe des implémentations Python enregistrées qui correspondent aux spécifications. Ceci est conforme aux attentes définies dans la PEP 514 https://www.python.org/dev/peps/pep-0514/
  • Si des installations Python gérées par uv https://docs.astral.sh/uv/concepts/python-versions/ sont disponibles, nous utiliserons la première qui correspond à la spécification.
  • Nous tenterons de découvrir un exécutable python correspondant dans les dossiers énumérés dans la variable d'environnement PATH. Dans ce cas, nous essaierons de trouver un exécutable dont le nom est à peu près similaire à la spécification (pour une logique exacte, veuillez consulter le code d'implémentation).

Attention :

Comme détaillé ci-dessus, les environnements virtuels empruntent généralement des éléments au Python système, ils ne contiennent pas réellement toutes les données du Python système. La version de l'exécutable python est codée en dur dans l'exécutable python lui-même. Par conséquent, si vous mettez à niveau votre Python système, votre environnement virtuel continuera d'afficher la version antérieure à la mise à niveau, même si maintenant, outre l'exécutable, tout le contenu supplémentaire (bibliothèque standard, bibliothèques binaires, etc.) est de la nouvelle version.

À moins de quelques incompatibilités majeures (ce qui est rare), l'environnement virtuel continuera de fonctionner, mais à part le contenu intégré dans l'exécutable python, il se comportera comme la version mise à niveau. Si un tel Python d'environnement virtuel est spécifié comme interpréteur cible, nous créerons des environnements virtuels qui correspondent à la nouvelle version de Python système, et non à la version signalée par l'environnement virtuel.

Créateurs

Ce sont eux qui mettent en place l'environnement virtuel, généralement en référence au Python système. Virtualenv dispose actuellement de deux types d'environnements virtuels :

  • venv - ceci délègue le processus de création au module venv, comme décrit dans la PEP 405 https://www.python.org/dev/peps/pep-0405. Ceci n'est disponible que pour les interpréteurs Python de version 3.5 ou ultérieure, et présente également l'inconvénient que virtualenv doit créer un processus pour appeler ce module (sauf si virtualenv est installé dans le Python système), ce qui peut être une opération coûteuse (surtout sous Windows).
  • builtin - ceci signifie que virtualenv est capable de réaliser l'opération de création lui-même (en sachant exactement quels fichiers créer et quels fichiers système doivent être référencés). Le créateur nommé builtin est un alias du premier créateur de ce type (nous fournissons des créateurs pour divers environnements cibles, qui diffèrent tous dans les opérations de création réelles, comme CPython 2 sous Windows, PyPy2 sous Windows, CPython3 sous Posix, PyPy3 sous Posix, etc. ; pour une liste complète, voir creator <#creator>).

Seeders

Ceux-ci installeront pour vous des paquets de base (un ou plusieurs parmi : pip https://pypi.org/project/pip, setuptools https://pypi.org/project/setuptools, wheel https://pypi.org/project/wheel) qui vous permettront d'installer des paquets python supplémentaires dans l'environnement virtuel créé (en appelant pip). L'installation de setuptools https://pypi.org/project/setuptools est désactivée par défaut sur les environnements Python 3.12+. wheel https://pypi.org/project/wheel est uniquement installé sur Python 3.8, par défaut. Il existe deux principaux mécanismes de seeding disponibles :

  • pip - cette méthode utilise le pip intégré à virtualenv pour installer les paquets de base (notez qu'un nouveau processus enfant doit être créé pour cela, ce qui peut être coûteux, surtout sous Windows).
  • app-data - cette méthode utilise le répertoire de données d'application de l'utilisateur pour créer des images d'installation. Ces images ne doivent être créées qu'une seule fois, et les environnements virtuels ultérieurs peuvent simplement lier/copier ces images dans leur chemin de bibliothèque python pur (le dossier site-packages). Cela permet à toutes les créations d'environnement virtuel, sauf la première, d'être extrêmement rapides (un mécanisme pip prend généralement 98 % du temps de création de virtualenv, donc en créant cette image d'installation que nous pouvons simplement lier dans le répertoire d'installation des environnements virtuels, nous pouvons obtenir des gains de vitesse en passant de 1 minute et 10 secondes à seulement 8 secondes dans le cas d'une copie, ou 0.8 seconde si des liens symboliques sont disponibles - c'est sous Windows, sous Linux/macOS avec des liens symboliques, cela peut descendre à 100 ms à partir de 3+ secondes). Pour outrepasser l'emplacement du système de fichiers du cache de base, on peut utiliser la variable d'environnement VIRTUALENV_OVERRIDE_APP_DATA.

Wheels

Pour installer un paquet de base via la méthode pip ou app-data, virtualenv doit acquérir un wheel du paquet cible. Ces wheels peuvent être acquis à partir de plusieurs emplacements comme suit :

  • virtualenv distribue nativement un ensemble de wheels embarqués pour les trois paquets de base (pip https://pypi.org/project/pip, setuptools https://pypi.org/project/setuptools, wheel https://pypi.org/project/wheel). Ceux-ci sont empaquetés avec les fichiers sources de virtualenv et ne changent qu'à la mise à niveau de virtualenv. Différentes versions de Python nécessitent différentes versions de ceux-ci, et comme virtualenv prend en charge une large gamme de versions de Python, le nombre de wheels embarqués nativement est supérieur à 3. Chaque fois que de nouvelles versions de ces paquets embarqués sont publiées en amont, le projet virtualenv les met à jour et publie une nouvelle version. Par conséquent, la mise à niveau de virtualenv périodiquement mettra également à jour la version des paquets de base.
  • Cependant, les utilisateurs finaux pourraient ne pas être en mesure de mettre à niveau virtualenv aussi rapidement que nous publions de nouvelles versions. Par conséquent, un utilisateur pourrait demander à mettre à niveau la liste des wheels embarqués en invoquant virtualenv avec le drapeau upgrade-embed-wheels <#upgrade-embed-wheels>. Si l'opération est déclenchée manuellement de cette manière, les exécutions ultérieures de virtualenv utiliseront toujours les wheels embarqués mis à niveau.

    L'opération peut également être déclenchée automatiquement, en tant que processus d'arrière-plan lors de l'invocation de virtualenv, si aucune mise à niveau de ce type n'a été effectuée au cours des 14 derniers jours. Il ne commencera à utiliser les wheels mis à niveau automatiquement que s'ils sont sortis depuis plus de 28 jours, et que la mise à niveau automatique s'est terminée il y a au moins une heure :

  • la période de 28 jours devrait garantir que les utilisateurs finaux ne récupèrent pas automatiquement des versions ayant des bugs connus,
  • la période d'une heure après la fin de la mise à niveau automatique est mise en œuvre pour que les services d'intégration continue ne commencent pas à utiliser de nouvelles versions embarquées en cours de route.

Le comportement automatique peut être désactivé via le drapeau/option de configuration no-periodic-update <#no-periodic-update>. Pour acquérir la date de publication d'un paquet, virtualenv effectuera les opérations suivantes :

  • recherche https://pypi.org/pypi/<distribution>/json (source de vérité primaire),
  • enregistre la date à laquelle la version a été découverte pour la première fois, et attend que 28 jours se soient écoulés.
•
Les utilisateurs peuvent spécifier un ensemble de chemins locaux contenant des wheels supplémentaires en utilisant le drapeau d'argument de commande extra-search-dir <#extra-search-dir>.

Lors de la recherche d'un wheel à utiliser, virtualenv effectue la recherche dans l'ordre suivant :

  • wheels embarqués,
  • wheels embarqués mis à niveau,
  • répertoire de recherche supplémentaire.

Les wheels groupés sont les trois ci-dessus réunis. Si aucun des emplacements ne contient la version de wheel demandée ou si l'option download <#download> est définie, il utilisera pip pour télécharger la dernière version disponible sur le serveur d'index.

Intégration des wheels pour les distributions

Les distributions personnalisées souhaitent souvent utiliser leur propre ensemble de versions de wheels à distribuer au lieu de celui que virtualenv publie sur PyPi. La raison est de tenter de maintenir les versions système de ces paquets synchronisées avec celles utilisées par virtualenv. Dans de tels cas, elles devraient patcher le module virtualenv.seed.wheels.embed https://github.com/pypa/virtualenv/tree/main/src/virtualenv/seed/wheels/embed, en veillant à fournir la fonction get_embed_wheel (qui renvoie le wheel à utiliser étant donné une distribution/version python). Les variables BUNDLE_FOLDER, BUNDLE_SUPPORT et MAX sont nécessaires s'ils souhaitent utiliser virtualen

v's suite de tests pour valider.

De plus, ils pourraient vouloir désactiver la mise à jour périodique en patchant `virtualenv.seed.embed.base_embed.PERIODIC_UPDATE_ON_BY_DEFAULT` https://github.com/pypa/virtualenv/tree/main/src/virtualenv/seed/embed/base_embed.py à False, et laisser le mécanisme de mise à jour du système gérer cela. Notez dans ce cas que l'utilisateur peut toujours demander une mise à niveau des roues intégrées en invoquant virtualenv via upgrade-embed-wheels <#upgrade-embed-wheels>, mais cela ne se produira plus automatiquement et n'altérera pas les roues fournies par le système d'exploitation.

Activateurs

Ce sont des scripts d'activation qui manipulent les paramètres de votre shell afin de garantir que les commandes provenant de l'environnement virtuel Python aient la priorité sur vos chemins système. Par exemple, si l'invocation de pip depuis votre shell retournait le pip du Python système avant l'activation, une fois l'activation effectuée, cela devrait se référer au pip de l'environnement virtuel. Notez cependant que tout ce que nous faisons est de changer la priorité ; ainsi, si le dossier bin/Scripts de votre environnement virtuel ne contient pas un certain exécutable, celui-ci sera toujours résolu de la même manière qu'il l'aurait été avant l'activation.

Pour une liste des shells pour lesquels nous fournissons des activateurs, voir activators <#activators>. Leur emplacement est juste à côté des exécutables Python : généralement le dossier Scripts sous Windows, bin sous POSIX. Ils sont nommés activate, plus une extension spécifique à chaque activateur, sans extension pour Bash. Vous pouvez les invoquer, généralement en les sourçant. La commande source peut varier selon le shell - par exemple, sous Bash, c'est source (ou .) :

source venv/bin/activate

Le script d'activation ajoute le dossier binaire de l'environnement virtuel au début de la variable d'environnement PATH. C'est vraiment une commodité pour le faire, car vous pourriez le faire vous-même.

Notez que vous n'avez pas besoin d'activer un environnement virtuel pour l'utiliser. Vous pouvez plutôt utiliser les chemins complets vers ses exécutables, au lieu de vous fier à votre shell pour les résoudre vers votre environnement virtuel.

Les scripts d'activation modifient également votre invite de commande pour indiquer quel environnement est actuellement actif, en ajoutant le nom de l'environnement (ou le nom spécifié par --prompt lors de la création initiale de l'environnement) entre crochets, comme (venv). Vous pouvez désactiver ce comportement en définissant la variable d'environnement VIRTUAL_ENV_DISABLE_PROMPT à n'importe quelle valeur. Vous pouvez également obtenir le nom de l'environnement via la variable d'environnement VIRTUAL_ENV_PROMPT si vous souhaitez personnaliser votre invite, par exemple.

Les scripts fournissent également une commande deactivate qui vous permettra d'annuler l'opération :

deactivate

Note :

Si vous utilisez Powershell, le script activate est soumis aux politiques d'exécution http://technet.microsoft.com/en-us/library/dd347641.aspx sur le système. Par défaut, Windows 7 et versions ultérieures, la politique d'exécution du système est définie sur Restricted, ce qui signifie qu'aucun script comme le script activate n'est autorisé à être exécuté.

Cependant, cela ne nous empêche pas de changer cela légèrement pour permettre son exécution. Vous pouvez assouplir la politique d'exécution du système pour permettre l'exécution de scripts locaux sans vérifier la signature du code en utilisant ce qui suit :

Set-ExecutionPolicy RemoteSigned

Étant donné que le script activate.ps1 est généré localement pour chaque virtualenv, il n'est pas considéré comme un script distant et peut donc être exécuté.

Une explication plus détaillée de ceci peut être trouvée dans l'article de blog d'Allison Kaptur de 2013 : There's no magic: virtualenv edition https://www.recurse.com/blog/14-there-is-no-magic-virtualenv-edition explique comment virtualenv utilise bash et Python et PATH et PYTHONHOME pour isoler les chemins des environnements virtuels.

Discovery options

Comprendre la découverte d'interprète : --python contre --try-first-with

Vous pouvez contrôler quel interprète Python virtualenv sélectionne à l'aide des options --python et --try-first-with. Pour éviter toute confusion, il est préférable de les considérer comme la « règle » et l'« indice ».

``--python <spéc>`` : La règle

Cette option définit les exigences obligatoires pour l'interpréteur. Le <spéc> peut être :

  • Une chaîne de version (par exemple, python3.8, pypy3). virtualenv recherchera tout interpréteur qui correspond à cette version.
  • Un chemin absolu (par exemple, /usr/bin/python3.8). Il s'agit d'une exigence stricte. Seul l'interpréteur à ce chemin exact sera utilisé. S'il n'existe pas ou s'il ne s'agit pas d'un interpréteur valide, la création échouera.

``--try-first-with <chemin>`` : L'indice

Cette option fournit un chemin vers un exécutable Python à vérifier avant que virtualenv n'effectue sa recherche standard. Cela peut accélérer la découverte ou aider à sélectionner un interpréteur spécifique lorsque plusieurs versions existent sur votre système.

Comment ils fonctionnent ensemble

virtualenv n'utilisera un interpréteur de --try-first-with que s'il satisfait la règle de l'option --python. La règle --python l'emporte toujours.

Exemples :

1.
L'indice ne correspond pas à la règle :
virtualenv --python python3.8 --try-first-with /usr/bin/python3.10 my-env

2.
L'indice ne correspond pas à une règle de chemin stricte :
virtualenv --python /usr/bin/python3.8 --try-first-with /usr/bin/python3.10 my-env
•
Résultat : virtualenv inspecte /usr/bin/python3.10. Il constate que cela ne correspond pas à la règle stricte /usr/bin/python3.8 et le rejette. Il procède ensuite à sa recherche normale pour trouver un interpréteur correspondant à la règle /usr/bin/python3.8 ailleurs.

•
Résultat : virtualenv inspecte /usr/bin/python3.8. Cela correspond à la règle 3.8 et est utilisé pour créer l'environnement.

Cette approche garantit que le comportement est prévisible et que --python reste la source de vérité définitive pour l'intention de l'utilisateur.

Défauts

Fichier de configuration

À moins que VIRTUALENV_CONFIG_FILE ne soit défini, virtualenv recherche un fichier de configuration standard virtualenv.ini. L'emplacement exact dépend du système d'exploitation que vous utilisez, tel que déterminé par la définition de configuration d'application de platformdirs https://pypi.org/project/platformdirs. Il peut être remplacé en définissant la variable d'environnement VIRTUALENV_CONFIG_FILE. L'emplacement du fichier de configuration est imprimé à la fin de la sortie lorsque --help est passé.

Les clés des paramètres sont dérivées de l'option de ligne de commande (supprimer les caractères - à gauche, et remplacer - par _). Lorsque plusieurs drapeaux sont disponibles, le premier trouvé l'emporte (l'ordre est celui indiqué sous --help).

Par exemple, --python serait spécifié comme suit :

[virtualenv]
python = /opt/python-3.8/bin/python

Les options qui acceptent plusieurs valeurs, comme extra-search-dir, peuvent être spécifiées comme suit :

[virtualenv]
extra_search_dir =
    /chemin/vers/dists
    /chemin/vers/autres/dists

Variables d'environnement

Les valeurs par défaut peuvent également être spécifiées via des variables d'environnement. Les clés des paramètres sont dérivées de l'option de ligne de commande (supprimer les caractères - à gauche, et remplacer - par _, puis capitaliser le nom). Lorsque plusieurs drapeaux sont disponibles, le premier trouvé l'emporte (l'ordre est celui indiqué sous --help).

Par exemple, pour utiliser un binaire Python personnalisé, au lieu de celui avec lequel virtualenv est exécuté, vous pouvez définir la variable d'environnement VIRTUALENV_PYTHON comme suit :

env VIRTUALENV_PYTHON=/opt/python-3.8/bin/python virtualenv

Lorsque l'option accepte plusieurs valeurs, par exemple pour python ou extra-search-dir, les valeurs peuvent être séparées soit par des sauts de ligne littéraux, soit par des virgules. Les sauts de ligne et les virgules ne peuvent pas être mélangés et s'ils sont tous deux présents, seul le saut de ligne est utilisé pour séparer les valeurs. Exemples de valeurs multiples :

env VIRTUALENV_PYTHON=/opt/python-3.8/bin/python,python3.8 virtualenv
env VIRTUALENV_EXTRA_SEARCH_DIR=/chemin/vers/dists\n/chemin/vers/autres/dists virtualenv

L'invocation équivalente basée sur les indicateurs CLI pour les exemples ci-dessus serait :

virtualenv --python=/opt/python-3.8/bin/python --python=python3.8
virtualenv --extra-search-dir=/chemin/vers/dists --extra-search-dir=/chemin/vers/autres/dists

Étendre la fonctionnalité

virtualenv permet d'étendre la fonctionnalité intégrée via un système de plugins. Pour ajouter un plugin, vous devez :

  • écrire un fichier python contenant le code du plugin qui suit notre interface attendue,
  • l'empaqueter sous forme de bibliothèque python,
  • l'installer aux côtés de l'environnement virtuel.

Découverte de Python

Le mécanisme de découverte de Python est un composant qui doit répondre à la question suivante : sur la base d'un type d'entrée utilisateur, donnez-moi un interpréteur Python sur la machine qui correspond. L'interpréteur intégré essaie de découvrir un interpréteur Python installé (basé sur la découverte PEP-515 et PATH) sur la machine de l'utilisateur où l'entrée utilisateur est une spécification Python. Un mécanisme de découverte alternatif serait, par exemple, d'utiliser le populaire projet pyenv https://github.com/pyenv/pyenv pour découvrir, et si inexistant, installer l'interpréteur Python demandé. Les mécanismes de découverte Python doivent être enregistrés sous la clé virtualenv.discovery, et le plugin doit implémenter virtualenv.discovery.discover.Discover :

Exécution des tests

Les tests de virtualenv sont écrits en utilisant le framework de test pytest https://pypi.org/project/pytest. tox https://pypi.org/project/tox est utilisé pour automatiser la configuration et l'exécution des tests de virtualenv.

Pour exécuter les tests localement, exécutez :

tox -e py

Cela exécutera la suite de tests pour la même version de Python que celle sous laquelle tox est installé. Alternativement, vous pouvez spécifier une version spécifique de Python en utilisant le format pyNN, tel que : py38, pypy3, etc.

tox a été configuré pour transmettre tout argument supplémentaire qu'il reçoit à pytest. Cela permet d'utiliser la riche interface de ligne de commande de pytest https://docs.pytest.org/en/latest/usage.html#specifying-tests-selecting-tests. Par exemple, vous pouvez sélectionner des tests en utilisant les différentes méthodes que pytest fournit :

# En utilisant des marqueurs
tox -e py -- -m "not slow"
# En utilisant des mots-clés
tox -e py -- -k "test_extra"

Certains tests nécessitent des dépendances supplémentaires pour être exécutés, comme les différents activateurs de shell (bash, fish, powershell, etc.). Ces tests seront automatiquement ignorés si ceux-ci ne sont pas présents. Notez cependant que dans le CI, tous les tests sont exécutés ; ainsi, même si tous les tests réussissent localement pour vous, ils peuvent quand même échouer dans le CI.

Exécution des linters

virtualenv utilise pre-commit https://pypi.org/project/pre-commit pour gérer le linting de la base de code. pre-commit effectue diverses vérifications sur tous les fichiers de virtualenv et utilise des outils qui aident à suivre un style de code cohérent au sein de la base de code. Pour utiliser les linters localement, exécutez :

tox -e fix

Note :

Évitez d'utiliser des commentaires # noqa pour supprimer les avertissements du linter - chaque fois que possible, les avertissements doivent être corrigés. Les commentaires # noqa sont réservés aux cas rares où le style recommandé cause de graves problèmes de lisibilité.

Construction de la documentation

La documentation de virtualenv est construite à l'aide de Sphinx https://pypi.org/project/Sphinx. La documentation est écrite en reStructuredText. Pour la construire localement, exécutez :

tox -e docs

La documentation construite se trouvera dans le dossier .tox/docs_out et pourra être consultée en ouvrant index.html dans ce dossier.

Version

Le calendrier de publication de virtualenv est lié à pip et setuptools. Nous regroupons la dernière version de ces bibliothèques, donc chaque fois qu'il y a une nouvelle version de l'une d'entre elles, il y aura une nouvelle version de virtualenv peu de temps après (nous attendons généralement quelques jours pour éviter de ramener des versions cassées).

Contributions

Soumission des pull requests

Soumettez les pull requests contre la branche main, en fournissant une bonne description de ce que vous faites et pourquoi. Vous devez avoir l'autorisation légale de distribuer tout code que vous contribuez à virtualenv et il doit être disponible sous la licence MIT. Fournissez des tests qui couvrent vos changements et exécutez les tests localement d'abord. virtualenv prend en charge <#compatibility-requirements> plusieurs versions de Python et systèmes d'exploitation. Toute pull request doit prendre en compte et fonctionner sur toutes ces plateformes.

Les Pull Requests doivent être petites pour faciliter la revue. Gardez-les autonomes et limitées en portée. Des études ont montré https://www.kessler.de/

Revue de code par les pairs

Comme indiqué dans https://github.com/smartbear/quality-code-review-wiki/blob/master/BestPracticesForPeerCodeReview.pdf, la qualité de la revue diminue à mesure que la taille des patchs augmente. Cela peut parfois entraîner de nombreuses petites PR pour intégrer une seule grande fonctionnalité. En particulier, les requêtes de tirage (pull requests) ne doivent pas être traitées comme des « branches de fonctionnalités », avec un développement continu ayant lieu au sein de la PR. Au lieu de cela, la fonctionnalité doit être décomposée en parties plus petites et indépendantes qui peuvent être revues et fusionnées individuellement.

De plus, évitez d'inclure des modifications « cosmétiques » dans le code qui ne sont pas liées à votre modification, car celles-ci rendent la revue de la PR plus difficile. Les exemples incluent le réarrangement du texte dans les commentaires ou la documentation, ou l'ajout ou la suppression de lignes vides ou d'espaces blancs dans les lignes. De telles modifications peuvent être apportées séparément, sous la forme d'une PR de « nettoyage de formatage », si nécessaire.

Tests automatisés

Toutes les requêtes de tirage et les fusions vers la branche 'main' sont testées à l'aide d'Azure Pipelines https://azure.microsoft.com/en-gb/services/devops/pipelines/ (configuré par le fichier azure-pipelines.yml à la racine du dépôt). Vous pouvez trouver le statut et les résultats des exécutions CI pour votre PR sur l'interface utilisateur Web de GitHub pour la requête de tirage. Vous pouvez également trouver des liens vers les pages des services CI pour les builds spécifiques sous forme de liens « Détails », au cas où l'exécution CI échouerait et que vous souhaiteriez visualiser la sortie.

Pour déclencher une nouvelle exécution CI pour une requête de tirage, vous pouvez fermer et rouvrir la requête de tirage ou soumettre une autre modification à la requête de tirage. Si nécessaire, les mainteneurs du projet peuvent déclencher manuellement un redémarrage d'un travail/build.

Entrées NEWS

Le fichier changelog.rst est géré à l'aide de towncrier https://pypi.org/project/towncrier et toutes les modifications non triviales doivent être accompagnées d'une entrée de nouvelles. Pour ajouter une entrée au fichier de nouvelles, vous devez d'abord avoir créé un ticket décrivant la modification que vous souhaitez apporter. Une requête de tirage elle-même *peut* servir à cet effet, mais il est préférable d'avoir un ticket dédié (par exemple, au cas où la PR serait rejetée pour des raisons de qualité du code).

Une fois que vous avez un ticket ou une PR, vous prenez le numéro et vous créez un fichier dans le répertoire docs/changelog nommé d'après ce numéro de ticket avec une extension :

  • feature.rst,
  • bugfix.rst,
  • doc.rst,
  • removal.rst,
  • misc.rst.

Ainsi, si votre numéro de ticket ou de PR est 1234 et que cette modification corrige un bug, vous créeriez un fichier docs/changelog/1234.bugfix.rst. Les PR peuvent couvrir plusieurs catégories en créant plusieurs fichiers (par exemple, si vous avez ajouté une fonctionnalité et déprécié/supprimé l'ancienne fonctionnalité en même temps, vous créeriez docs/changelog/1234.bugfix.rst et docs/changelog/1234.remove.rst). De même, si une PR touche plusieurs tickets/PRs, vous pouvez créer un fichier pour chacun d'eux avec le même contenu et towncrier https://pypi.org/project/towncrier les dédupliquera.

Contenu d'une entrée NEWS

Le contenu de ce fichier est du texte formaté en reStructuredText qui sera utilisé comme contenu de l'entrée du fichier de nouvelles. Vous n'avez pas besoin de référencer les numéros de ticket ou de PR ici car towncrier ajoutera automatiquement une référence à tous les tickets concernés lors du rendu du fichier de nouvelles.

Afin de maintenir un style cohérent dans le fichier changelog.rst, il est préférable de rester concis dans l'entrée de nouvelles, d'utiliser la casse de phrase, de ne pas dépasser 120 caractères et d'utiliser un ton impératif — une entrée doit compléter la phrase Ce changement .... Dans de rares cas, où une seule ligne ne suffit pas, utilisez une ligne de résumé sur un ton impératif suivie d'une ligne vide séparant celle-ci d'une description de la fonctionnalité/du changement en un ou plusieurs paragraphes, chacun limité à 120 caractères. N'oubliez pas qu'une entrée de nouvelles est destinée aux utilisateurs finaux et ne doit contenir que des détails pertinents pour un utilisateur final.

Choix du type d'une entrée NEWS

Une modification triviale est tout ce qui ne justifie pas une entrée dans le fichier de nouvelles. Quelques exemples sont : les refactorisations de code qui ne changent rien du point de vue du public, les corrections de fautes de frappe, les modifications d'espaces blancs, etc. Pour marquer une PR comme triviale, un contributeur doit simplement ajouter un fichier vide nommé aléatoirement dans le répertoire news/ avec l'extension .trivial.

Devenir un mainteneur

Si vous souhaitez devenir un mainteneur officiel, commencez par aider. Comme première étape, nous vous invitons à trier les tickets sur le tracker de tickets de virtualenv. Les mainteneurs de virtualenv accordent des capacités de triage aux contributeurs lorsqu'ils sont présents depuis un certain temps et ont contribué positivement au projet. Ceci est facultatif et fortement recommandé pour devenir un mainteneur de virtualenv. Plus tard, lorsque vous pensez être prêt, contactez l'un des mainteneurs et ils initieront un vote parmi les mainteneurs existants.

Remarque :

  • Accès GitHub Push

  • Capacités d'administration CI

      NAME

      virtualenv - créer des environnements Python virtuels.

      VIRTUALENV VS VENV

      Bien que les noms soient très similaires, virtualenv et venv ont des objectifs et des caractéristiques différents. Le module venv est intégré à Python depuis la version 3.3, tandis que virtualenv est un package tiers qui doit être installé séparément. Les principales différences sont les suivantes :

      • venv est généralement plus simple à utiliser et est intégré à Python, ce qui signifie qu'il n'y a pas de dépendances supplémentaires.
      • virtualenv est plus flexible et prend en charge un plus grand nombre de versions de Python, y compris les anciennes versions qui ne sont pas prises en charge par venv.
      • virtualenv offre plus d'options de configuration, telles que la possibilité d'inclure ou d'exclure certains packages, et la création d'environnements plus légers.

      En général, si vous utilisez Python 3.3 ou une version ultérieure et que vous n'avez pas besoin de fonctionnalités avancées, venv est un bon choix. Si vous avez besoin de plus de flexibilité, de prise en charge de versions plus anciennes de Python, ou de fonctionnalités avancées, virtualenv est une meilleure option.

      CONCEPT ET OBJECTIF DE VIRTUALENV

      Le concept principal derrière virtualenv est la création d'environnements isolés pour Python. Ceci est particulièrement utile lorsque vous travaillez sur plusieurs projets qui peuvent avoir des dépendances différentes ou nécessiter différentes versions de bibliothèques Python. Sans environnements virtuels, toutes les bibliothèques sont installées globalement dans le site-packages de votre installation Python. Cela peut entraîner des conflits de dépendances entre les projets.

      Un environnement virtuel est essentiellement un répertoire qui contient une installation Python autonome. Cet environnement a son propre ensemble de bibliothèques installées, distinctes de l'installation Python globale du système. Lorsque vous activez un environnement virtuel, votre shell est configuré pour utiliser les exécutables Python et les bibliothèques de cet environnement spécifique.

      L'objectif de virtualenv est de permettre aux développeurs de :

      • Installer différentes versions de bibliothèques pour différents projets sans conflit.
      • Maintenir des dépendances de projet propres et reproductibles.
      • Tester des projets avec différentes versions de bibliothèques ou de Python.
      • Éviter d'encombrer l'installation Python globale avec de nombreuses dépendances de projet.
