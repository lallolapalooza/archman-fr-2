NOM

VSL - Varnish Shared Memory Logging

APERÇU

Ce document décrit le format et le contenu de toutes les étiquettes de journalisation en mémoire partagée de Varnish. Ces étiquettes sont utilisées par les outils de journalisation tels que varnishlog(1), varnishtop(1), etc. fournis avec Varnish.

Étiquettes VSL

BackendClose - Connexion backend fermée
Enregistré lorsqu'une connexion backend est fermée.

Le format est :

%d %s %s [ %s ]
|  |  |    |
|  |  |    +- Raison optionnelle, voir SessClose pour l'explication
|  |  +------ "close" ou "recycle"
|  +--------- Nom d'affichage du backend
+------------ Descripteur de fichier de connexion
BackendOpen - Connexion backend ouverte
Enregistré lorsqu'une nouvelle connexion backend est ouverte.

Le format est :

%d %s %s %s %s %s %s
|  |  |  |  |  |  |
|  |  |  |  |  |  +- "connect" ou "reuse"
|  |  |  |  |  +---- Port local
|  |  |  |  +------- Adresse locale
|  |  |  +---------- Port distant
|  |  +------------- Adresse distante
|  +---------------- Nom d'affichage du backend
+------------------- Descripteur de fichier de connexion
Backend_health - Contrôle de santé du backend
Le résultat d'une sonde de santé du backend.

Le format est :

%s %s %s %s %u %u %u %f %f %s
|  |  |  |  |  |  |  |  |  |
|  |  |  |  |  |  |  |  |  +- Informations sur la réponse HTTP de la sonde / l'erreur
|  |  |  |  |  |  |  |  +---- Temps de réponse moyen
|  |  |  |  |  |  |  +------- Temps de réponse
|  |  |  |  |  |  +---------- Taille de la fenêtre de la sonde
|  |  |  |  |  +------------- Niveau de seuil de la sonde
|  |  |  |  +---------------- Nombre de sondes réussies dans la fenêtre
|  |  |  +------------------- Bits de la fenêtre de la sonde
|  |  +---------------------- "healthy" ou "sick"
|  +------------------------- "Back", "Still" ou "Went"
+---------------------------- Nom du backend

Les bits de la fenêtre de la sonde sont :

'-': Impossible de se connecter
'4': IPv4 correct
'6': IPv6 correct
'U': UNIX correct
'x': Erreur Xmit
'X': Xmit correct
'r': Erreur Recv
'R': Recv correct
'H': Happy

Lorsque le backend vient d'être créé, les bits de fenêtre pour les emplacements de contrôle de santé qui n'ont pas encore été exécutés apparaissent comme des échecs de connexion ('-').

Debug - Messages de débogage
Les messages de débogage peuvent normalement être ignorés, mais sont parfois utiles lors du dépannage. La plupart des messages de débogage doivent être explicitement activés avec des paramètres.

ExpBan - Objet évincé en raison d'une interdiction

ExpKill - Événement d'expiration d'objet
Enregistre les événements liés à l'expiration des objets. Les événements sont :
EXP_Rearm
Enregistré lorsque le temps d'expiration d'un objet change.
EXP_Inbox
Enregistré lorsque le thread d'expiration retire un objet de la boîte de réception pour traitement.
EXP_Kill
Enregistré lorsque le thread d'expiration tue un objet depuis la boîte de réception.
EXP_When
Enregistré lorsque le thread d'expiration déplace un objet sur le tas binéaire (binheap).
EXP_Inspect
Enregistré lorsque le thread d'expiration inspecte le prochain objet prévu pour expiration.
EXP_Expired
Enregistré lorsque le thread d'expiration expire un objet.
EXP_Removed
Enregistré lorsque le thread d'expiration supprime un objet avant son expiration.
VBF_Superseded
Enregistré lorsqu'un objet en remplace un autre.
LRU_Cand
Enregistré lorsqu'un objet est évalué pour une expiration forcée LRU.
LRU
Enregistré lorsqu'un objet est expiré de force en raison de LRU.
LRU_Fail
Enregistré lorsqu'aucun objet candidat approprié n'est trouvé pour une expiration forcée LRU.

Le format est :

EXP_Rearm p=%p E=%f e=%f f=0x%x
EXP_Inbox p=%p e=%f f=0x%x
EXP_Kill p=%p e=%f f=0x%x
EXP_When p=%p e=%f f=0x%x
EXP_Inspect p=%p e=%f f=0x%x
EXP_Expired x=%u t=%f h=%u
EXP_Removed x=%u t=%f h=%u
VBF_Superseded x=%u n=%u
LRU_Cand p=%p f=0x%x r=%d
LRU x=%u
LRU_Fail
Légende :
p=%p         Pointeur Objcore
t=%f         TTL restant (s)
e=%f         Heure d'expiration (époque Unix)
E=%f         Ancienne heure d'expiration (époque Unix)
f=0x%x       Drapeaux Objcore
r=%d         Compteur de références Objcore
x=%u         VXID de l'objet
n=%u         Nouveau VXID de l'objet
h=%u         Hits Objcore

Gzip - G(dé)compression effectuée sur l'objet
Un enregistrement Gzip est émis pour chaque instance de travail gzip ou gunzip effectuée. Dans le pire des cas, une transaction ESI stockée dans des objets compressés mais livrée décompressée, rencontrera plusieurs de ces enregistrements.

Le format est :

%c %c %c %d %d %d %d %d
|  |  |  |  |  |  |  |
|  |  |  |  |  |  |  +- Longueur en bits des données compressées
|  |  |  |  |  |  +---- Position en bits du dernier bit
|  |  |  |  |  +------- Position en bits du premier bloc de décompression
|  |  |  |  +---------- Octets en sortie
|  |  |  +------------- Octets en entrée
|  |  +---------------- 'E' : ESI, '-' : Objet simple
|  +------------------- 'F' : Fetch, 'D' : Deliver
+---------------------- 'G' : Gzip, 'U' : Gunzip, 'u' : Test de Gunzip

Exemples :

U F E 182 159 80 80 1392
G F E 159 173 80 1304 1314

SessClose - Connexion client fermée
SessClose est le dernier enregistrement pour toute connexion client.

Le format est :

%s %f
|  |
|  +- Durée pendant laquelle la session a été ouverte
+---- Raison de la fermeture de la connexion
Explication des raisons (première colonne) :
  • REM_CLOSE : Client fermé
  • REQ_CLOSE : Le client a demandé la fermeture
  • REQ_HTTP10 : Proto < HTTP/1.1
  • RX_BAD : Requête/réponse reçue incorrecte
  • RX_BODY : Échec de réception du corps
  • RX_JUNK : Données indésirables reçues
  • RX_OVERFLOW : Dépassement de tampon reçu
  • RX_TIMEOUT : Délai d'attente de réception dépassé
  • RX_CLOSE_IDLE : timeout_idle atteint
  • TX_PIPE : Transaction mise en pipeline
  • TX_ERROR : Transaction d'erreur
  • TX_EOF : Transmission EOF
  • RESP_CLOSE : Fermeture demandée par le backend/VCL
  • OVERLOAD : Manque d'une ressource
  • PIPE_OVERFLOW : Dépassement du pipeline de session
  • RANGE_SHORT : Données insuffisantes pour la plage
  • REQ_HTTP20 : HTTP2 non accepté
  • VCL_FAILURE : Échec VCL
  • RAPID_RESET : Réinitialisation rapide HTTP2

TTL - TTL défini sur l'objet
Un enregistrement TTL est émis chaque fois que les valeurs ttl, grace ou keep d'un objet sont définies, ainsi que pour indiquer si l'objet est cacheable ou non.

Le format est :

%s %d %d %d %d [ %d %d %u %u ] %s
|  |  |  |  |    |  |  |  |    |
|  |  |  |  |    |  |  |  |    +- "cacheable" ou "uncacheable"
|  |  |  |  |    |  |  |  +------ Max-Age de l'en-tête Cache-Control
|  |  |  |  |    |  |  +--------- En-tête Expires
|  |  |  |  |    |  +------------ En-tête Date
|  |  |  |  |    +--------------- Age (incluant la valeur de l'en-tête Age:)
|  |  |  |  +-------------------- Temps de référence pour le TTL
|  |  |  +----------------------- Keep
|  |  +-------------------------- Grace
|  +----------------------------- TTL
+-------------------------------- "RFC", "VCL" ou "HFP"

Les quatre champs optionnels ne sont présents que dans les en-têtes "RFC".

Exemples :

RFC 60 10 -1 1312966109 1312966109 1312966109 0 60 cacheable
VCL 120 10 0 1312966111 uncacheable
HFP 2 0 0 1312966113 uncacheable
Timestamp - Informations de chronométrage
Contient des informations de chronométrage pour les threads de travail Varnish.

Les horodatages sont émis par Varnish lors de certains événements et indiquent l'heure absolue de l'événement, le temps écoulé depuis le début de l'unité de travail et le temps écoulé depuis le dernier horodatage enregistré. Voir la section TIMESTAMPS ci-dessous pour des informations sur les horodatages individuels.

Le format est :

%s: %f %f %f
|   |  |  |
|   |  |  +- Temps écoulé depuis le dernier horodatage
|   |  +---- Temps écoulé depuis le début de l'unité de travail
|   +------- Heure absolue de l'événement
+----------- Étiquette de l'événement

|   +---------------- Nom de l'ACL pour MATCH ou NO_MATCH

vsl - Varnish Shared Library, log format

APERÇU

Le format des journaux Varnish est une suite de lignes de texte, chaque ligne représentant un enregistrement de journal. Les enregistrements de journal sont triés par ordre chronologique. Chaque enregistrement de journal est précédé d'une estampille temporelle qui indique le moment où l'événement s'est produit.

Le format général d'un enregistrement de journal est le suivant :

%d %d %s
|  |  |
|  |  +- Nom du filtre
|  +---- Nombre d'appels effectués
+------- Octets totaux produits

L'estampille temporelle est basée sur le temps de référence de Varnish, qui est le nombre de secondes depuis le 1er janvier 1970 UTC. La date et l'heure complètes sont insérées dans le journal sous forme d'estampille temporelle. La date et l'heure actuelles sont affichées sous la forme :

1033272935.123

Le décalage est le nombre de secondes depuis le début de l'époque Unix, et le fractionnement est le nombre de millisecondes depuis la dernière seconde.

Les enregistrements de journal sont générés par le sous-système de journalisation partagé de Varnish. Chaque enregistrement de journal est précédé d'une estampille temporelle, qui indique le moment où l'événement s'est produit. Le format général d'un enregistrement de journal est le suivant :

%s %d %d
|  |  |
|  |  +- Octets totaux produits
|  +---- Nombre d'appels effectués
+------- Nom du filtre

NB : cet enregistrement de journal est masqué par défaut.

ESTAMPILLAGES TEMPORELS

Les estampillages temporels sont insérés dans le journal lors de l'achèvement de certains événements pendant la gestion des tâches du thread de travail. Les estampillages temporels comportent une étiquette indiquant quel événement a été achevé. Les champs rapportés indiquent le temps absolu de l'événement, le temps passé depuis le début de la tâche et le temps passé depuis que le dernier estampillage temporel a été enregistré.

Les estampillages temporels enregistrés automatiquement par Varnish sont insérés après l'achèvement des événements qui devraient entraîner des délais (par exemple, E/S réseau ou temps d'attente sur une liste d'attente). Des estampillages temporels peuvent également être insérés depuis VCL en utilisant la fonction std.timestamp(). Si vous effectuez des tâches longues dans la configuration VCL, il est bon d'enregistrer un estampillage temporel après l'achèvement de cette tâche. Cela évite que les informations de synchronisation des estampillages temporels ultérieurs n'incluent le temps passé sur l'événement VCL.

MESSAGES NOTICE

Les messages de type « notice » contiennent des informations sur le traitement d'une requête. Il peut s'agir de circonstances exceptionnelles rencontrées qui entraînent une déviation par rapport au traitement normal. Les messages sont préfixés par vsl: pour les messages générés par le cœur de Varnish, et les auteurs de VMOD sont encouragés à utiliser vmod_<nom>: pour leurs propres messages de type « notice ». Cela correspond au nom de la page de manuel où des descriptions détaillées des messages de type « notice » sont attendues.

Les messages du cœur sont décrits ci-dessous.

Récupération conditionnelle attente d'objet en streaming

Le backend a répondu 304 Not Modified à une récupération conditionnelle en utilisant un objet qui n'a pas encore été entièrement récupéré comme objet modèle obsolète. Cela ne peut se produire que lorsque le TTL de l'objet est inférieur au temps nécessaire pour le récupérer. La récupération est suspendue jusqu'à ce que l'objet obsolète soit entièrement récupéré, après quoi le nouvel objet est créé normalement. Pendant l'attente, tout temps de grâce sur l'objet obsolète sera en vigueur.

Nombre élevé de variantes

Les objets sont principalement recherchés dans un index à l'aide de la clé de hachage calculée à partir de la fonction VCL hash_data(). Lorsque des variantes sont impliquées, c'est-à-dire lorsqu'une réponse de backend a été stockée avec un en-tête Vary, une recherche secondaire est effectuée mais elle n'est pas indexée. À mesure que le nombre de variantes pour une clé donnée augmente, cela peut ralentir les recherches dans le cache, et comme cela se produit sous un verrou, cela peut considérablement augmenter la contention de verrouillage, encore plus pour les objets fréquemment demandés. Les variantes doivent donc être utilisées avec parcimonie sur les réponses cacheables, mais comme elles peuvent provenir de VCL ou de serveurs d'origine, cet avis devrait aider à identifier les ressources problématiques.
