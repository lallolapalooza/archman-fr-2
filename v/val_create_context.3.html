DESCRIPTION

La fonction val_resolve_and_check() interroge un ensemble de serveurs de noms pour le tuple <domain_name, type, class> et vérifie et valide la réponse. La vérification implique la vérification des RRSIGs, et la validation est la vérification d'une chaîne d'authentification à partir d'une ancre de confiance configurée.

Le paramètre flags peut être utilisé pour contrôler les résultats de la validation. Les valeurs suivantes, qui peuvent être combinées par OU, sont actuellement définies pour ce champ :

VAL_QUERY_DONT_VALIDATE
Ce drapeau amène le validateur à désactiver la validation pour cette requête.
VAL_QUERY_IGNORE_SKEW
Ce drapeau amène le validateur à désactiver la vérification des dates d'inception et d'expiration des signatures sur les RRSIGs.
VAL_QUERY_AC_DETAIL
Ce drapeau amène le validateur à copier les détails de la chaîne d'authentification dans le membre val_rc_answer de la structure val_result_chain retournée.
VAL_QUERY_ASYNC
Ce drapeau active la résolution asynchrone des requêtes pour cette recherche.
VAL_QUERY_NO_DLV
Ce drapeau amène le validateur à désactiver le traitement DLV pour cette requête. Ceci n'est disponible que si la bibliothèque libval(3) a été compilée avec le support DLV.
VAL_QUERY_NO_EDNS0_FALLBACK
Lors de l'interrogation de divers serveurs de noms, libsres(3) tentera également plusieurs tailles EDNS0, se terminant par une requête sans EDNS0 (c'est-à-dire sans bit CD défini). Ce drapeau amène libval à désactiver le repli EDNS0 pour la requête.
VAL_QUERY_ITERATE
Ce drapeau force libval à effectuer une recherche itérative en interrogeant divers serveurs de noms dans la hiérarchie de délégation, au lieu de demander ces informations à tout serveur de noms cache pouvant être configuré dans dnsval.conf.
VAL_QUERY_SKIP_RESOLVER
Ce drapeau force libval à ne consulter que son cache lors de la tentative de résolution d'un nom.
VAL_QUERY_SKIP_CACHE
Il y a deux niveaux de mise en cache dans libval : au niveau de l'assertion et au niveau de la réponse. Ce drapeau force libval à ignorer les données des deux caches lors de la tentative de résolution d'un nom.
VAL_QUERY_SKIP_ANS_CACHE
Il y a deux niveaux de mise en cache dans libval : au niveau de l'assertion et au niveau de la réponse. Ce drapeau force libval à ignorer les données du cache de réponses lors de la tentative de résolution d'un nom. Si une assertion existe déjà pour le nom, la classe et le type donnés, cette assertion est réutilisée jusqu'à son expiration. Une fois expirée, le nom est recherché via une requête même si un enregistrement plus récent (obtenu par une autre assertion dans le même contexte ou un contexte différent) est disponible dans son cache de réponses.

Le premier paramètre de val_resolve_and_check() est le contexte du validateur. Les applications peuvent créer un nouveau contexte de validateur en utilisant la fonction val_create_context(). Cette fonction analyse les fichiers de configuration du résolveur et du validateur et crée le handle newcontext pour ces informations analysées. Les informations stockées dans le contexte du validateur incluent la politique de validation et la politique du résolveur.

Les politiques de validation et de résolution sont lues par défaut à partir des fichiers /etc/dnsval.conf et /etc/resolv.conf. /etc/root.hints fournit les informations d'amorçage pour le validateur lorsqu'il fonctionne comme un résolveur complet (voir dnsval.conf(3)). Ces valeurs par défaut peuvent être différentes si une autre valeur a été spécifiée lors de la configuration de la bibliothèque. Si le fichier de configuration du résolveur par défaut n'est pas trouvé à l'emplacement spécifié, libval tentera également de se rabattre sur /etc/resolv.conf en dernier recours.

Les applications peuvent également créer un contexte de validateur avec une politique personnalisée en utilisant la fonction val_create_context_ex().

L'argument opt dans val_create_context_ex() pointe vers la structure suivante :

typedef struct val_context_opt {
    unsigned int vc_qflags;
    unsigned int vc_polflags;
    char *vc_valpol;
    char *vc_nslist;
    char *vc_val_conf;
    char *vc_res_conf;
    char *vc_root_conf;
    val_global_opt_t *gopt, 
} val_context_opt_t;

vc_qflags spécifie les drapeaux de requête par défaut pour les requêtes associées au contexte. Ce champ est identique à l'argument flags dans la fonction val_resolve_and_check().

Les champs vc_val_conf, vc_res_conf et vc_root_conf peuvent être utilisés pour spécifier des fichiers de configuration alternatifs à la place des fichiers par défaut utilisés pour les informations de configuration du validateur, du résolveur et des indices racine.

Le champ vc_valpol peut être utilisé pour fournir un "extrait" de configuration de validateur personnalisé au validateur. Le validateur analyse ces informations et les applique à la configuration du validateur par défaut, soit comme une extension, soit comme une substitution, comme spécifié par le champ vc_polflags. Le champ vc_nslist, similairement, peut être utilisé pour fournir une liste personnalisée de serveurs de noms récursifs auxquels envoyer les requêtes, en plus (ou à la place) de la liste de serveurs de noms spécifiée dans le fichier resolv.conf. La liste des serveurs de noms dans vc_res_conf doit être spécifiée comme une liste d'adresses IP ou IPv6 séparées par des espaces blancs.

Une correspondance personnalisée entre une zone et un serveur de noms peut être créée à l'aide de la fonction val_context_store_ns_for_zone().

vc_polflags peut être configuré avec les valeurs suivantes :

CTX_DYN_POL_VAL_OVR
Lorsque ce drapeau est défini, seule la configuration du validateur spécifiée dans le champ vc_valpol est utilisée pour la configuration du validateur. Les options spécifiées dans le fichier dnsval.conf sont ignorées.
CTX_DYN_POL_RES_OVR
Lorsque ce drapeau est défini, seule la configuration du résolveur spécifiée dans le champ vc_res_conf est utilisée pour la configuration du résolveur. Les options spécifiées dans le fichier resolv.conf sont ignorées.

La fonction val_context_setqflags() permet de modifier les drapeaux de requête d'un contexte de validateur existant. Les options action et flags déterminent si les drapeaux doivent être ajoutés, retirés ou remplacés.

Les fonctions p_val_status(), p_ac_status() et p_val_error() renvoient des chaînes de caractères lisibles par l'homme représentant le statut de validation, le statut de la chaîne d'authentification et le code d'erreur, respectivement.

Les fonctions val_istrusted(), val_isvalidated() et val_does_not_exist() sont des fonctions utilitaires qui vérifient des propriétés spécifiques du statut de validation.

La fonction val_log_add_optarg() permet de contrôler la verbosité et la destination de la sortie des messages de journal émis par la bibliothèque.

Lorsque vous avez terminé avec un contexte de validateur, vous devez le libérer en utilisant la fonction val_free_context(). De même, la chaîne de résultats renvoyée par val_resolve_and_check() doit être libérée en utilisant val_free_result_chain().

VALEUR DE RETOUR

Toutes les fonctions de création et de configuration retournent 0 en cas de succès et une valeur d'erreur négative en cas d'échec.

Les fonctions de vérification retournent généralement une valeur entière non nulle en cas de succès et 0 en cas d'échec.

Les fonctions p_val_status(), p_ac_status() et p_val_error() retournent un pointeur vers une chaîne de caractères qui ne doit pas être libérée.

Le champ gopt pointe vers la structure suivante :

typedef struct val_global_opt {
    int local_is_trusted;
    long edns0_size;
    int env_policy;
    int app_policy;
    char *log_target;
    int closest_ta_only;
    int rec_fallback;
    long max_refresh;
    int proto;
} val_global_opt_t;

Définir la valeur 1 pour local_is_trusted est équivalent à spécifier l'option trust-oob-answers dans le fichier dnsval.conf à yes. De même, définir les membres closest_ta_only et rec_fallback à 1 est équivalent à définir les options closest-ta-only et rec-fallback à yes dans le fichier dnsval.conf. Une valeur de 0 est équivalente au réglage no pour ces options.

Définir le membre edns0_size à une valeur particulière a le même effet que définir l'option edns0-size dans le fichier dnsval.conf.

Définir le membre max_refresh à une valeur particulière a le même effet que définir l'option max-refresh dans le fichier dnsval.conf.

Définir le membre proto à une valeur particulière a le même effet que définir l'option proto dans le fichier dnsval.conf.

env_policy et app_policy peuvent être définis sur l'un des valeurs VAL_POL_GOPT_DISABLE, VAL_POL_GOPT_ENABLE, ou VAL_POL_GOPT_OVERRIDE. Ces valeurs correspondent directement aux options disable, enable et override pour les réglages env-policy et app-policy dans le fichier dnsval.conf.

Les valeurs de -1 pour les champs ci-dessus sont traitées comme des conditions "ignorer" en ce sens que le validateur n'inclura pas les options globales fournies dynamiquement avec une valeur de -1 lors de la création de son contexte. Cela permet à une application de remplacer un sous-ensemble d'options globales tout en utilisant par défaut les options globales fournies dans le fichier dnsval.conf.

Le champ log_target permet à l'application de fournir des cibles de journalisation *en plus* de celles configurées dans le fichier de configuration.

Voir dnsval.conf(3) pour plus de détails sur la spécification de la politique du validateur.

Les drapeaux de requête par défaut peuvent être définis et désactivés pour un contexte donné à l'aide de val_context_setqflags(). Cela permet à une application de modifier le traitement du validateur DNSSEC, tout en ayant la plupart de la configuration par défaut plus granulaire spécifiée dans son fichier de configuration. Le paramètre action peut être défini sur l'une des options suivantes.

VAL_CTX_FLAG_SET
Cette option amène le validateur à définir le drapeau donné comme l'un des drapeaux de requête par défaut.
VAL_CTX_FLAG_RESET
Cette option amène le validateur à réinitialiser le drapeau donné s'il avait été défini comme l'un des drapeaux de requête par défaut pour le contexte.

Les réponses retournées par val_resolve_and_check() sont disponibles dans la liste chaînée *results. Chaque réponse correspond à un RRset distinct ; plusieurs RR au sein du RRset font partie de la même réponse. Plusieurs réponses sont possibles lorsque type est ns_t_any ou ns_t_rrsig.

Les éléments individuels de *results pointent vers des listes chaînées val_authentication_chain. Les éléments de la chaîne d'authentification dans val_authentication_chain contiennent les RRsets réels renvoyés par le serveur de noms en réponse à la requête.

Les valeurs de résultat de validation retournées dans val_result_chain peuvent être converties en format ASCII à l'aide de p_val_status(). Les valeurs de statut de la chaîne d'authentification retournées dans chaque élément de la liste chaînée val_authentication_chain peuvent être converties en format ASCII à l'aide des fonctions p_ac_status().

Bien que certaines applications, comme les utilitaires de dépannage DNSSEC et les outils d'inspection de paquets, puissent examiner les éléments individuels de la chaîne d'authentification pour identifier les raisons réelles de l'erreur de validation, la plupart des applications ne s'intéresseront qu'à un seul code d'erreur pour déterminer l'authenticité des données.

val_isvalidated() identifie si une valeur de statut de résultat de validation donnée correspond à une réponse qui a été cryptographiquement vérifiée et validée à l'aide d'une ancre de confiance configurée localement.

val_istrusted() identifie si une valeur de statut de validateur donnée est fiable. Une réponse peut être localement fiable sans être validée.

val_does_not_exist() identifie si une valeur de statut de validateur donnée correspond à l'un des types de non-existence.

La bibliothèque libval alloue en interne de la mémoire pour *results et cela doit être libéré par l'application appelante à l'aide de l'interface free_result_chain().

Pointeur vers le RRset suivant dans l'ensemble des réponses retournées pour une requête.

val_rc_status
Statut de validation pour un RRset donné. Il peut s'agir de l'un des éléments suivants :
VAL_SUCCESS
Réponse reçue et validée avec succès.
VAL_NONEXISTENT_NAME
Aucun nom n'était présent et une preuve valide de non-existence confirmant le nom manquant (plage NSEC ou NSEC3) a été retournée. Les composants de la preuve ont également été validés individuellement.
VAL_NONEXISTENT_TYPE
Aucun type n'existe pour le nom et une preuve valide de non-existence confirmant le nom manquant a été retournée. Les composants de la preuve ont également été validés individuellement.
VAL_NONEXISTENT_NAME_NOCHAIN
Aucun nom n'était présent et une preuve valide de non-existence confirmant le nom manquant a été retournée. Les composants de la preuve ont également été identifiés comme fiables, mais ils n'ont pas été validés individuellement.
VAL_NONEXISTENT_TYPE_NOCHAIN
Aucun type n'existe pour le nom et une preuve valide de non-existence confirmant le nom manquant (plage NSEC ou NSEC3) a été retournée. Les composants de la preuve ont également été identifiés comme fiables, mais ils n'ont pas été validés individuellement.
VAL_PINSECURE
L'enregistrement ou un ancêtre de l'enregistrement dans la chaîne d'authentification vers l'ancre de confiance était connu pour être prouvablement non sécurisé.
VAL_PINSECURE_UNTRUSTED
L'enregistrement ou un ancêtre de l'enregistrement dans la chaîne d'authentification vers l'ancre de confiance était connu pour être prouvablement non sécurisé. Mais la condition prouvablement non sécurisée a été configurée comme non fiable.
VAL_BARE_RRSIG
Aucune validation DNSSEC possible, la requête portait sur un RRSIG.
VAL_IGNORE_VALIDATION
La politique locale a été configurée pour ignorer la validation de la zone d'où proviennent ces données.
VAL_UNTRUSTED_ZONE
La politique locale a été configurée pour rejeter toutes les données reçues de la zone donnée.
VAL_OOB_ANSWER
La réponse a été obtenue via une méthode hors bande, telle qu'un fichier de configuration local.
VAL_BOGUS
La réponse n'a pas pu être validée en raison d'échecs de vérification de signature ou de l'impossibilité de vérifier les preuves dans la chaîne d'authentification.
VAL_DNS_ERROR
Une erreur s'est produite pendant le traitement DNS.
VAL_INDETERMINATE
La réponse n'a pas pu être validée en raison de métadonnées DNSSEC manquantes

DESCRIPTION

The libval validation library provides a programmatic interface for DNSSEC validation. It is intended to be used by DNS resolvers and other DNSSEC-aware applications.

The library provides functions for retrieving DNSSEC validation results, manipulating DNSSEC data, and interfacing with trust anchors.

The following data structures are defined by libval:

struct val_context
struct val_context
{
    int val_ctx_flags;
    void *val_ctx_priv;
    int (*val_ctx_log) (const char *fmt, ...);
    val_astatus_t (*val_ctx_validate_response) (void *ctx,
        const char *qname, uint16_t qtype, int qclass,
        unsigned flags,
        struct val_authentication_chain **result);
    struct val_context *val_ctx_next;
};
val_ctx_flags
Flags that control the behavior of the validation context. See val_context_flags(3) for a list of possible flags.
val_ctx_priv
A pointer to private data that may be used by the validation context.
val_ctx_log
A pointer to a logging function. If set to NULL, the default logging mechanism will be used.
val_ctx_validate_response
A pointer to a function that performs DNSSEC validation of a response. This is the primary function used to obtain validation results.
val_ctx_next
A pointer to the next validation context in a linked list. This allows for multiple validation contexts to be chained together.
val_astatus_t
This enumerated type defines the possible status values returned by the validation functions. These values indicate the result of the DNSSEC validation process.
VAL_UNKNOWN
The validation status is unknown or could not be determined.
VAL_INSECURE
The DNSSEC data is not available or not present for the queried domain, and the domain is not configured to be DNSSEC-signed.
VAL_BOGUS
The DNSSEC data is invalid or could not be verified. This indicates a potential security issue.
VAL_VERIFIED
The DNSSEC data was successfully verified, and the response is considered secure.
VAL_SUSPENDED
Validation was suspended, possibly due to a temporary issue or policy setting.
VAL_NOTRUST
All available components in the authentication chain verified properly, but there was no trust anchor available.

Status values in val_status_t returned by the validator can be displayed in ASCII format using p_val_status().

VAL_AC_RRSIG_MISSING

VAL_AC_DNSKEY_MISSING
The DNSKEY for an RRSIG covering a resource record could not be retrieved.
VAL_AC_DS_MISSING
The DS record covering a DNSKEY record was not available.
VAL_AC_DATA_MISSING

VAL_AC_DNS_ERROR

VAL_AC_NOT_VERIFIED

VAL_AC_VERIFIED

val_ac_trust

    exist in the apex keyset.

For each val_rr_rec member of type DNSKEY (or DS, where relevant) within the authentication chain val_ac_rrset, the validation status is stored in the variable rr_status and can return one of the following values:

VAL_AC_TRUST_POINT
    The given DNSKEY or a DS record was configured 
    as a DNSSEC trust anchor.
VAL_AC_SIGNING_KEY
    This DNSKEY was used to create an RRSIG for
    the resource record set.
VAL_AC_VERIFIED_LINK
    This DNSKEY provided the link in the authentication
    chain from the trust anchor to the signed record.
VAL_AC_UNKNOWN_ALGORITHM_LINK
    This DNSKEY provided the link in the authentication
    chain from the trust anchor to the signed record,
    but the DNSKEY algorithm was unknown.
VAL_AC_UNKNOWN_DNSKEY_PROTOCOL
    The DNSKEY protocol number was unrecognized.
VAL_AC_ALGORITHM_NOT_SUPPORTED
    The DNSKEY or DS algorithm was not supported.

VAL_AC_DS_NOMATCH
    An RRSIG was created with a key that did not
    exist in the parent DS record set.
VAL_AC_INVALID_KEY
    The key used to verify the RRSIG was not a valid DNSKEY.
VAL_AC_INVALID_DS
    The DS used to validate the DNSKEY could not be parsed.
rr_next
Points to the next resource record in the RRset.

JOURNALISATION

libval fournit la fonction val_log_add_optarg() pour contrôler la verbosité et l'emplacement de la sortie des messages de journalisation.

La fonction val_log_add_optarg() prend deux arguments : le premier argument args est une chaîne de caractères qui spécifie l'emplacement et la verbosité. Le second argument, use_stderr, s'il est défini sur une valeur supérieure à 0, permet à libval d'envoyer des messages de journalisation vers stderr.

La chaîne de caractères qui spécifie l'emplacement de la cible de journalisation et la verbosité a un format spécifique :

<debug-level>:<dest-type>[:<dest-options>]

où
<debug-level> est de 1 à 7, pour des niveaux croissants de verbosité
<dest-type> est l'un des suivants : file, net, syslog, stderr, stdout
<dest-options> dépend de <dest-type>
file:<file-name> (ouvert en mode ajout)
net[:<host-name>:<host-port>] (127.0.0.1:1053)
syslog[:facility] (0-23 (par défaut 1 USER))

Les niveaux de journalisation peuvent être globalement traduits en différents types de messages de journalisation comme suit (les messages retournés pour chaque niveau dans cette liste englobent les messages retournés pour le niveau supérieur) :

3 : Error   : erreur rencontrée
4 : Warning : récupération après une erreur
5 : Notice  : donne les résultats finaux de validation pour une requête
              et des détails sur les fichiers de politique et les étiquettes utilisées
6 : Info
: donne des détails sur les chaînes d'authentification 7 : Debug : donne des informations sur le niveau de débogage
