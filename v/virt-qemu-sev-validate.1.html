Nom

virt-qemu-sev-validate - valider une mesure de lancement de domaine AMD SEV

SYNTAXE

virt-qemu-sev-validate [OPTIONS]

DESCRIPTION

Ce programme valide la mesure rapportée pour un domaine lancé avec AMD SEV. Si le programme se termine avec un code d'état zéro, le propriétaire de la machine virtuelle peut être assuré que son système d'exploitation invité s'exécute sous la protection offerte par la plateforme SEV / SEV-ES.

Notez que le niveau de protection varie en fonction de la génération de la plateforme AMD SEV et que la description des différences sort du cadre de ce document.

Pour que les résultats de ce programme soient considérés dignes de confiance, il est requis de l'exécuter sur une machine qui est déjà digne de confiance par le propriétaire de la machine virtuelle. Il peut s'agir d'une machine sur laquelle le propriétaire de la machine virtuelle a un contrôle physique direct, ou d'une autre machine virtuelle protégée par AMD SEV dont la mesure de lancement a déjà été validée. L'exécution de ce programme sur l'hôte de virtualisation ne produira pas une réponse digne de confiance.

S'il est demandé de se connecter à libvirt, il refusera d'utiliser une connexion libvirt locale à la machine, car celle-ci ne peut pas être digne de confiance. Cependant, à des fins de test ou de démonstration, il peut être forcé de s'exécuter dans ce scénario en utilisant l'indicateur --insecure. Le résultat ne sera bien entendu toujours pas digne de confiance.

OPTIONS

Options communes

-h, --help

Affiche l'aide d'utilisation de la ligne de commande puis quitte.

-d, --debug

Affiche les informations de débogage pendant l'exécution.

-q, --quiet

N'affiche pas d'informations sur le résultat de l'attestation.

Options d'état invité

Ces options fournissent des informations sur l'état de la machine virtuelle dont le démarrage doit être attesté.

--measurement BASE64-STRING

La mesure de lancement rapportée par l'hyperviseur du domaine à valider. La mesure doit être de 48 octets de données binaires encodées en chaîne base64.

--api-major VERSION

La version majeure de l'API SEV de l'hyperviseur sur lequel le domaine s'exécute.

--api-minor VERSION

La version mineure de l'API SEV de l'hyperviseur sur lequel le domaine s'exécute.

--build-id ID

L'identifiant de build SEV de l'hyperviseur sur lequel le domaine s'exécute.

--policy POLiCY

Le masque de bits de politique associé aux données de lancement de session du domaine à valider.

Options de configuration invité

Ces options fournissent les éléments nécessaires pour calculer la mesure de lancement du domaine attendue. Celle-ci sera ensuite comparée à la mesure de lancement rapportée.

-f PATH, --firmware=PATH

Chemin vers le binaire du chargeur de firmware. Il s'agit de la compilation EDK2 qui sait comment initialiser AMD SEV. Pour que la validation soit digne de confiance, il est important que la compilation du firmware utilisée n'ait aucun support pour le chargement de variables non volatiles depuis la NVRAM, même si la NVRAM est exposée à la machine virtuelle.

-k PATH, --kernel=PATH

Chemin vers le binaire du noyau en cas de démarrage direct du noyau.

-r PATH, --initrd=PATH

Chemin vers le binaire initrd en cas de démarrage direct du noyau. Par défaut, contenu de longueur nulle si omis.

-e STRING, --cmdline=STRING

Chaîne contenant les paramètres de ligne de commande du noyau utilisés lors du démarrage du domaine. Par défaut, chaîne vide si omis.

-n COUNT, --num-cpus=COUNT

Le nombre de processeurs virtuels pour le domaine. Ceci est requis lorsque la politique du domaine est définie pour nécessiter SEV-ES.

-0 PATH, --vmsa-cpu0=PATH

Chemin vers l'état initial du VMSA pour le processeur de démarrage. Ceci est requis lorsque la politique du domaine est définie pour nécessiter SEV-ES. Le contenu du fichier doit être exactement de 4096 octets.

-1 PATH, --vmsa-cpu1=PATH

Chemin vers l'état initial du VMSA pour le processeur non-démarrage. Ceci est requis lorsque la politique du domaine est définie pour nécessiter SEV-ES et que le domaine possède plus d'un processeur. Le contenu du fichier doit être exactement de 4096 octets.

--tik PATH

Fichier TIK pour le domaine. Ce fichier doit être exactement de 16 octets et contient la clé d'intégrité de transport unique associée aux données de lancement de session du domaine. Ceci est mutuellement exclusif avec l'argument --tk.

--tek PATH

Fichier TEK pour le domaine. Ce fichier doit être exactement de 16 octets et contient la clé de chiffrement de transport unique associée aux données de lancement de session du domaine. Ceci est mutuellement exclusif avec l'argument --tk.

--tk PATH

Fichier TEK/TIK combiné pour le domaine. Ce fichier doit être exactement de 32 octets, les 16 premiers octets contenant le TEK et les 16 derniers octets contenant le TIK. Ceci est mutuellement exclusif avec les arguments --tik et --tek.

Options Libvirt

Ces options sont utilisées lors de la connexion à libvirt pour obtenir automatiquement l'état et les informations de configuration du domaine à attester.

-c, --connect URI

URI de connexion libvirt. Pour que la validation soit digne de confiance, il doit s'agir d'une URI résolvant vers un hôte de virtualisation distant. Cette exigence peut être contournée en utilisant l'argument --insecure.

-o, --domain ID|NAME|UUID

ID du domaine, ou nom du domaine ou UUID du domaine. Utilisé pour identifier quel domaine libvirt doit avoir sa mesure de lancement prise. Le domaine doit être en cours d'exécution, et serait normalement démarré en pause, pour permettre la validation avant que les processeurs de la machine virtuelle ne commencent leur exécution.

-i, --insecure

Continuer même si le scénario d'utilisation est connu pour être non sécurisé. Cela permet au programme de se connecter à un hyperviseur libvirt local et de s'appuyer sur le contenu des fichiers de l'hôte de virtualisation. Cela permet également à la validation de continuer même si les processeurs de la machine virtuelle ne sont pas dans l'état de pause initial. Le résultat de la validation ne doit pas être digne de confiance.

-g, --ignore-config

Ne pas tenter de vérifier la configuration du domaine. Le comportement par défaut est d'afficher des erreurs si des éléments de configuration sont identifiés dans le XML du domaine qui invalideraient la mesure de lancement. Cela peut aider le propriétaire du domaine à comprendre les erreurs de configuration qui ont été commises. Si l'argument --ignore-config est donné, cette vérification de la configuration sera ignorée. Le résultat est que la validation échouera probablement.

Options d'injection de secret

Ces options fournissent un moyen d'injecter un secret si la validation de la mesure de lancement réussit.

--inject-secret ALIAS-OR-GUID:PATH

Chemin vers un fichier contenant un secret à injecter dans le système d'exploitation invité. L'utilisation typique serait de fournir un mot de passe pour déverrouiller le chiffrement complet du disque de la partition racine. ALIAS peut être l'un des secrets bien connus :

•
luks-key - octets à utiliser comme clé pour déverrouiller un slot de clé LUKS. GUID de 736869e5-84f0-4973-92ec-06879ce3da0b.

Alternativement, GUID fait référence à un UUID arbitraire choisi par l'appelant. Le contenu de PATH est défini par les exigences de l'UUID associé, et sera utilisé tel quel sans modification. En particulier, soyez conscient :

  • Évitez les caractères de nouvelle ligne finaux indésirables dans PATH, sauf si cela est requis par l'UUID.
  • Tout octet NUL final doit être explicitement inclus dans PATH s'il est requis par l'UUID.

Cet argument peut être répété plusieurs fois, à condition qu'un GUID différent soit fourni pour chaque instance.

--secret-header PATH

Chemin vers un fichier dans lequel l'en-tête secret injecté sera écrit au format base64 et plus tard injecté

Ce site n'est en aucun cas associé à Arch Linux ni affilié à ce projet. Le contenu est uniquement une traduction des pages de manuel d'Arch publiées sur man.archlinux.org.

OPTIONS

Command line options

--connect URL
Libvirt connection URL. If not specified, the default connection will be used.
--firmware PATH
Path to the firmware binary file used to boot the guest. This is required unless the guest is configured to use the firmware defined in libvirt XML configuration. The path can be absolute or relative. If the path is relative, it will be interpreted relative to the current working directory.
--kernel PATH
Path to the kernel image file used to boot the guest. This is required if the guest is configured for direct kernel boot. The path can be absolute or relative. If the path is relative, it will be interpreted relative to the current working directory.
--initrd PATH
Path to the initrd image file used to boot the guest. This is required if the guest is configured for direct kernel boot and an initrd image is provided. The path can be absolute or relative. If the path is relative, it will be interpreted relative to the current working directory.
--cmdline STRING
Kernel command line string. This is required if the guest is configured for direct kernel boot. Whitespace must be preserved exactly, including any leading or trailing spaces.
--num-cpus NUMBER
Number of virtual CPUs to be used by the guest. This is only relevant for SEV-ES guests. If not specified, the default value is 1.
--vmsa-cpu0 PATH
Path to the VMSA file for CPU0. This is required for SEV-ES guests if the VMSA is not automatically constructed by QEMU. The path can be absolute or relative. If the path is relative, it will be interpreted relative to the current working directory.
--vmsa-cpu1 PATH
Path to the VMSA file for CPU1. This is required for SEV-ES guests if the VMSA is not automatically constructed by QEMU. The path can be absolute or relative. If the path is relative, it will be interpreted relative to the current working directory.
--cpu-family NUMBER
CPU family number. This is used to automatically construct the VMSA for SEV-ES guests if --vmsa-cpu0 and --vmsa-cpu1 are not specified. The default value is 0x6 (6).
--cpu-model NUMBER
CPU model number. This is used to automatically construct the VMSA for SEV-ES guests if --vmsa-cpu0 and --vmsa-cpu1 are not specified. The default value is 0x82 (130).
--cpu-stepping NUMBER
CPU stepping number. This is used to automatically construct the VMSA for SEV-ES guests if --vmsa-cpu0 and --vmsa-cpu1 are not specified. The default value is 0.
--tk PATH
Path to the TIK/TEK keypair file. This file contains the TIK and TEK keys in binary format. This is required for all SEV guests.
--measurement BASE64_STRING
The expected measurement hash of the guest in base64 format. This is required if the measurement is not fetched from libvirt.
--api-major NUMBER
The major version of the SEV API. This is required if the measurement is not fetched from libvirt.
--api-minor NUMBER
The minor version of the SEV API. This is required if the measurement is not fetched from libvirt.
--build-id NUMBER
The build ID of the SEV firmware. This is required if the measurement is not fetched from libvirt.
--policy NUMBER
The security policy of the guest. This is required if the measurement is not fetched from libvirt.
--domain NAME
The name of the guest domain to validate. This is required if the measurement is fetched from libvirt.
--insecure
Perform validation on the local hypervisor without any security considerations. This is only intended for testing and debugging purposes.
--inject-secret UUID:PATH
Inject a secret into the guest on successful measurement validation. The secret is identified by its UUID and stored in the file specified by PATH. The UUID must be in the format xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx. The secret will be injected into the guest via the virtual TPM device. The secret will be written in base64 format into the specified files.
--secret-header PATH
Path to a file in which the injected secret header will be written in base64 format and later injected into the domain. This is required if there is no connection to libvirt, otherwise the secret will be directly injected.
--secret-payload PATH
Path to a file in which the injected secret payload will be written in base64 format and later injected into the domain. This is required if there is no connection to libvirt, otherwise the secret will be directly injected.

EXAMPLES

Fully offline execution

This scenario allows a measurement to be securely validated in a completely offline state without any connection to the hypervisor host. All required data items must be provided as command line parameters. This usage model is considered secure, because all input data is provided by the user.

Validate the measurement of a SEV guest booting from disk:

# virt-qemu-sev-validate \
    --firmware OVMF.sev.fd \
    --tk this-guest-tk.bin \
    --measurement Zs2pf19ubFSafpZ2WKkwquXvACx9Wt/BV+eJwQ/taO8jhyIj/F8swFrybR1fZ2ID \
    --api-major 0 \
    --api-minor 24 \
    --build-id 13 \
    --policy 3

Validate the measurement of a SEV guest with direct kernel boot:

# virt-qemu-sev-validate \
    --firmware OVMF.sev.fd \
    --kernel vmlinuz-5.11.12 \
    --initrd initramfs-5.11.12 \
    --cmdline "root=/dev/vda1" \
    --tk this-guest-tk.bin \
    --measurement Zs2pf19ubFSafpZ2WKkwquXvACx9Wt/BV+eJwQ/taO8jhyIj/F8swFrybR1fZ2ID \
    --api-major 0 \
    --api-minor 24 \
    --build-id 13 \
    --policy 3

Validate the measurement of a SEV-ES SMP guest booting from disk:

# virt-qemu-sev-validate \
    --firmware OVMF.sev.fd \
    --num-cpus 2 \
    --vmsa-cpu0 vmsa0.bin \
    --vmsa-cpu1 vmsa1.bin \
    --tk this-guest-tk.bin \
    --measurement Zs2pf19ubFSafpZ2WKkwquXvACx9Wt/BV+eJwQ/taO8jhyIj/F8swFrybR1fZ2ID \
    --api-major 0 \
    --api-minor 24 \
    --build-id 13 \
    --policy 7

Validate the measurement of a SEV-ES SMP guest booting from disk, with automatically constructed VMSA:

# virt-qemu-sev-validate \
    --firmware OVMF.sev.fd \
    --num-cpus 2 \
    --cpu-family 23 \
    --cpu-model 49 \
    --cpu-stepping 0 \
    --tk this-guest-tk.bin \
    --measurement Zs2pf19ubFSafpZ2WKkwquXvACx9Wt/BV+eJwQ/taO8jhyIj/F8swFrybR1fZ2ID \
    --api-major 0 \
    --api-minor 24 \
    --build-id 13 \
    --policy 7

Validate the measurement of a SEV guest booting from disk and inject a disk password on success:

# virt-qemu-sev-validate \
    --firmware OVMF.sev.fd \
    --tk this-guest-tk.bin \
    --measurement Zs2pf19ubFSafpZ2WKkwquXvACx9Wt/BV+eJwQ/taO8jhyIj/F8swFrybR1fZ2ID \
    --api-major 0 \
    --api-minor 24 \
    --build-id 13 \
    --policy 3 \
    --inject-secret 736869e5-84f0-4973-92ec-06879ce3da0b:passwd.txt \
    --secret-header secret-header.b64 \
    --secret-payload secret-payload.b64

The secret-header.b64 and secret-payload.b64 files can now be sent to the virtualization host for injection.

Fetch from remote libvirt

This scenario allows fetching certain data from a remote hypervisor via a connection to libvirt. It will aid in debugging by analysing the guest configuration and reporting anything that could invalidate the measurement of the guest. This usage model is considered secure, because the limited information obtained from the untrusted hypervisor cannot be used to change the result.

Validate the measurement of a SEV guest booting from disk:

# virt-qemu-sev-validate \
    --connect qemu+ssh://root@some.remote.host/system \
    --firmware OVMF.sev.fd \
    --tk this-guest-tk.bin \
    --domain fedora34x86_64

Fetch from local libvirt

This scenario allows fetching all data from the local hypervisor via a connection to libvirt. It is only to be used for the purpose of testing, debugging, or demonstrations, because running on the local hypervisor is not a secure scenario. To enable this usage, the --insecure flag must be specified. Given a pointer to the libvirt guest to validate, all information needed to perform a validation, except the TIK/TEK pair can be acquired automatically.

Validate the measurement of a SEV guest booting from disk:

# virt-qemu-sev-validate \
    --insecure \
    --tk this-guest-tk.bin \
    --domain fedora34x86_64

COMMON MISTAKES CHECKLIST

The complexity of configuring a guest and validating its boot measurement means it is very likely to see the failure:

ERROR: Measurement does not match, VM is not trustworthy

This error message assumes the worst, but in most cases will failure will be a result of either mis-configuring the guest, or passing the wrong information when trying to validate it. The following information is a guide for what items to check in order to stand the best chance of diagnosing the problem

  • Check the VM configuration for the DH certificate and session blob in the libvirt guest XML.

    The content for these fields should be in base64 format, which is what sevctl session generates. Other tools may generate the files in binary format, so ensure it has been correctly converted to base64.

  • Check the VM configuration policy value matches the session blob

    The <policy> value in libvirt guest XML has to match the value passed to the sevctl session command. If this is mismatched then the guest will not even start, and QEMU will show an error such as:

sev_launch_start: LAUNCH_START ret=1 fw_error=11 'Bad measurement'
  • Check the correct TIK/TEK keypair are passed

    The TIK/TEK keypair are uniquely tied to each DH cert and session blob. Make sure that the TIK/TEK keypair passed to this program the ones matched to the DH cert and session blob configured for the libvirt guest XML. This is one of the most common mistakes. Further ensure that the TIK and TEK files are not swapped.

  • Check the firmware binary matches the one used to boot

    The firmware binary content is part of the data covered by the launch measurement. Ensure that the firmware binary passed to this program matches the one used to launch the guest. The hypervisor host will periodically get software updates which introduce a new firmware binary version.

  • Check the kernel, initrd and cmdline match the one used to boot

    If the guest is configured to use direct kernel boot, check that the kernel, initrd and cmdline passed to this program match the ones used to boot the guest. In the kernel cmdline whitespace must be preserved exactly, including any leading or trailing spaces.

  • Check whether the kernel hash measurement is enabled

    The kernelHashes property in the libvirt guest XML controls whether hashes of the kernel, initrd and cmdline content are covered by the boot measurement. If enabled, then the matching content must be passed to this program. UIf disabled, then the content must NOT be passed.

  • Check that the correct measurement hash is passed

    The measurement hash includes a nonce, so it will be different on every boot attempt. Thus w

hen validating the measuremnt it is important ensure the most recent measurement is used.

  • Check the correct VMSA blobs / CPU SKU values for the host are used

    Les blobs VMSA fournissent l'état initial des registres pour le CPU de démarrage et tout CPU supplémentaire. L'un des registres code le SKU du CPU (famille, modèle, révision) du CPU physique de l'hôte. Assurez-vous que le blob VMSA utilisé pour la validation correspond au SKU de l'hôte sur lequel le guest est démarré. Passer les valeurs du SKU du CPU directement à l'outil peut réduire la probabilité d'utiliser les mauvaises.

  • Check the CPU count is correct

    Lors du passage des blobs VMSA pour les guests SEV-ES, le nombre de CPU présents influencera le résultat de la mesure. Assurez-vous que le nombre correct de vCPU est utilisé, correspondant à la tentative de démarrage du guest.

    • La meilleure pratique est d'exécuter cet outil en mode entièrement hors ligne et de passer toutes les informations sous forme de paramètres explicites de ligne de commande. Cependant, lors du débogage des échecs, il peut être utile de lui dire de se connecter à libvirt et de récupérer les informations. S'il se connecte à une instance libvirt distante, il récupérera toutes les informations qui peuvent être fiables, à savoir les données de base de l'état de lancement de la VM. Il vérifiera également la configuration XML pour identifier certaines erreurs courantes. Si le drapeau --insecure est passé, il peut extraire certaines informations de configuration et les utiliser pour le processus d'attestation.

    Si l'erreur ne peut toujours pas être identifiée, cet outil peut être exécuté sur l'hôte de virtualisation. Dans ce scénario, les trois seuls paramètres de ligne de commande requis sont pour le TIK, le TEK et le nom du domaine libvirt. Il devrait être capable de déterminer automatiquement toutes les autres informations requises. S'il signale toujours un échec, cela indique très fortement que la paire TIK/TEK ne correspond pas au certificat DH configuré et au blob de session.

    Le drapeau --debug affichera les hachages et/ou les dumps hexadécimaux pour diverses informations utilisées dans le processus d'attestation. Comparer la sortie de --debug lors de l'exécution sur l'hôte hyperviseur avec celle obtenue lors de l'exécution en mode hors ligne peut donner des indications supplémentaires sur le paramètre qui est incohérent.

    Comme mentionné précédemment dans ce document, gardez à l'esprit qu'en général, toute réponse d'attestation obtenue en exécutant sur l'hôte hyperviseur ne doit pas être considérée comme fiable. Donc, si une erreur de configuration est identifiée, il est fortement recommandé de relancer l'attestation en mode hors ligne sur une machine de confiance.

    STATUT DE SORTIE

    Lors de l'attestation réussie de la mesure de lancement, un statut de sortie de 0 sera défini.

    En cas d'échec de l'attestation de la mesure de lancement, l'un des codes suivants sera défini :

    • 1 - La mesure du guest n'a pas pu être validée

      En supposant que les entrées de ce programme soient correctes, le lancement de la machine virtuelle a été compromis et ne doit plus être considéré comme fiable.

    • 2 - Le scénario d'utilisation ne peut pas être pris en charge

      La manière dont ce programme a été invoqué l'empêche de pouvoir valider la mesure de lancement.

    • 3 - Le scénario d'utilisation n'est pas sécurisé

      La manière dont ce programme a été invoqué signifie que le résultat de toute validation de mesure de lancement ne sera pas sécurisé.

      Le programme peut être réinvoqué avec l'argument --insecure pour forcer une validation, cependant, les résultats de celle-ci ne doivent pas être considérés comme fiables. Ceci ne devrait être utilisé qu'à des fins de test, de débogage ou de démonstration, jamais dans un déploiement en production.

    • 4 - Le domaine a une configuration incorrecte pour être mesuré

      La manière dont le guest a été configuré empêche ce programme de pouvoir valider la mesure de lancement. Notez qu'en général, la configuration du guest rapportée par l'hyperviseur n'est pas fiable, il est donc possible que cette erreur soit un faux positif conçu pour causer un déni de service.

      Ce programme peut être réinvoqué avec l'argument --ignore-config pour ignorer les vérifications de cohérence sur le XML du domaine. Cela résultera probablement en un échec avec un code de sortie de 1, indiquant que la mesure est invalide.

    • 5 - Le domaine est dans un état incorrect pour être mesuré

      Le domaine doit être en cours d'exécution pour valider une mesure de lancement.

    • 6 - une erreur inattendue s'est produite dans le code

      Une faille logique dans ce programme signifie qu'il est incapable d'achever la validation de la mesure. C'est un bogue qui devrait être signalé aux mainteneurs.
