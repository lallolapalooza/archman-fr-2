V2CC.LIBS(5) Formats de fichiers V2CC.LIBS(5)

NOM

v2cc.libs - Fichier de mappage de bibliothèques VHDL pour le compilateur/simulateur FreeHDL.

DESCRIPTION

FreeHDL est une suite de compilateur/simulateur pour le langage de description matérielle VHDL. Les normes VHDL'93 ainsi que VHDL'87 sont prises en charge.

FreeHDL traduit les fichiers sources VHDL originaux en C++. Ensuite, le code source C++ peut être compilé et lié au noyau pour construire le programme de simulation. Le lancement de l'exécutable généré simulera le modèle VHDL correspondant. Le processus de construction réel pour générer le simulateur à partir du code source VHDL est un processus complexe qui est géré par le script gvhdl.

FreeHDL n'a pas de notion opaque de bibliothèques de conception. Les fichiers VHDL ne sont pas pré-analysés et enregistrés dans une base de données de bibliothèques comme dans d'autres systèmes de compilateurs/simulateurs VHDL. Au lieu de cela, chaque fois qu'une référence à une unité de conception doit être faite, FreeHDL analyse le code VHDL de cette unité de conception à partir de zéro. Par conséquent, il doit être capable de trouver le fichier source d'une unité de conception étant donné le nom VHDL de cette unité.

Ainsi, pour FreeHDL, une bibliothèque de conception est un mappage des identificateurs VHDL vers des noms de fichiers. Il existe également un mappage pour obtenir les noms de bibliothèques à partir des fichiers de mappage.

Un tel mappage est spécifié via un « fichier de mappage ». Il contient une liste de règles de modèles qui transforment chacune une certaine classe d'identificateurs en noms de fichiers.

La syntaxe d'un fichier de mappage est :


Lexical :


litchar : 'a'..'z' | 'A'..'Z' | '0'..'9' | '_' | '/' | '-' | '.' escchar


escchar : '\' char


whitespace : ' ' | '\n' | '\v' | '\t' | comment


comment : '#' any_character* '\n'


opchar : ':' | ',' | '(' | ')'


specchar : chaque caractère imprimable sauf litchar, whitespace et opchar


symchar : litchar | specchar


symbol : symchar+


Grammaire :


mapping : version patternrule*


version : « v2cc_mapfile » « 0 »


patternrule : symbol [ ':' symbol ]

Les commentaires sont ignorés.

Un fichier de mappage spécifie une séquence de règles de modèle. Lors de la transformation d'un identificateur, chaque règle est essayée successivement et la première qui correspond est choisie.

Une règle ressemble à


pattern : filename

Lorsque la partie « : filename » est omise, elle prend par défaut « patternEXT » où « EXT » est déterminé par l'utilisateur du fichier de mappage.

Le « pattern » peut contenir le caractère spécial « < » qui introduit un `caractère générique'. Le « < » doit être suivi d'un « > », avec des caractères arbitraires entre les deux. Ces caractères forment le nom du caractère générique. Un caractère générique correspond à toute séquence de caractères. Il peut y avoir n'importe quel nombre de caractères génériques dans le modèle, mais chacun doit avoir un nom unique.

Le « filename » peut également contenir le caractère « < », suivi d'un nom, suivi de « > ». Là, il introduit une `substitution de caractère générique'. Il sera remplacé par les caractères qui ont correspondu au caractère générique portant le même nom dans « pattern ». Lorsqu'il n'y a pas de caractère générique dans « pattern » avec le nom correct, il sera remplacé par rien. Lors de cette substitution, les caractères « # » et « / » sont remplacés par « ## », et « #- » respectivement. Aucune autre traduction de caractère n'est effectuée, donc si vous avez des caractères inhabituels dans vos identificateurs VHDL, vous aurez des caractères inhabituels dans vos noms de fichiers.

Avant d'effectuer la comparaison avec les modèles, l'identificateur VHDL est mis sous une forme canonique : lorsqu'il ne s'agit pas d'un identificateur abstrait, tous ses caractères sont convertis en minuscules.

Lorsque le nom de fichier résultant est relatif (ne commence pas par « / »), il est préfixé par le répertoire du fichier de mappage.

Un fichier de mappage inexistant est équivalent à la règle unique


<>

Un fichier de mappage vide est juste cela : un mappage vide.

Le mappage n'a pas besoin d'être réversible. Il est acceptable que plusieurs identificateurs correspondent à un seul nom de fichier.

Aucun caractère spécial autre que « < » et « > » n'est valide dans « pattern » ou « filename ». Ils sont réservés pour des extensions futures.

Les fichiers de mappage pour passer des noms d'unités de conception aux noms de fichiers sont trouvés en recherchant dans les répertoires spécifiés par le `chemin de bibliothèque v2cc'. Vous pouvez utiliser la variable d'environnement V2CC_LIBRARY_PATH et les options de ligne de commande pour définir le chemin. Lorsque la variable d'environnement n'est pas définie, elle prend par défaut une valeur qui rend disponibles les bibliothèques standard distribuées et installées avec v2cc lui-même. Lorsqu'elle est définie, elle écrase complètement cette valeur par défaut.

La variable V2CC_LIBRARY_PATH est composée de noms de fichiers séparés par « : ». Le nom de fichier « * » est remplacé par la valeur par défaut mentionnée ci-dessus.

En plus de la variable d'environnement, vous pouvez utiliser l'option de ligne de commande « -L libdir » avec v2cc. Les répertoires spécifiés avec « -L » sont ajoutés avant ceux spécifiés par V2CC_LIBRARY_PATH. Dans le chemin final des bibliothèques, ils apparaissent dans le même ordre que sur la ligne de commande.

La recherche d'une unité de conception nommée UNIT dans une bibliothèque nommée LIB se fait comme suit :


pour chaque composant du chemin de bibliothèque, L
si L est un fichier régulier
définir LMAP à L
sinon si L est un répertoire
définir LMAP à L/v2cc.libs
sinon
continuer avec le composant suivant
traduire LIB en FLIB en utilisant LMAP avec EXT=""
si FLIB.vhdl existe
terminer avec FLIB.vhdl comme résultat
si FLIB.v2cc existe
définir UMAP à FLIB.v2cc
sinon si FLIB est un répertoire
définir UMAP à FLIB/v2cc.units
sinon
continuer avec le composant suivant
traduire UNIT en FUNIT en utilisant UMAP avec EXT=".vhdl"
terminer avec FUNIT comme résultat
terminer sans succès

Ce mécanisme est utilisé pour toutes les unités de conception référencées depuis du code VHDL (ou par d'autres moyens). Il y a cependant une complication avec les architectures et les corps de paquetages, car ils ne sont pas identifiés de manière unique par un seul identificateur. Pour eux, un identificateur artificiel est construit. Les architectures reçoivent des noms de la forme


<entity>(<architecture>)

tandis que les corps de paquetages deviennent


<package>(body)

Par exemple, « architecture struct of model » est transformé en « model(struct) » et « package body misc » est transformé en « misc(body) ».

Lorsqu'un fichier de conception contient plusieurs unités de conception, elles sont toutes analysées, vérifiées pour leur exactitude et mémorisées, mais seule l'unité nécessaire sera utilisée pour la génération de code. C'est-à-dire que lorsqu'un fichier de conception contient à la fois un en-tête de paquetage et un corps de paquetage et que l'en-tête de paquetage est référencé depuis une autre unité de conception, aucun code ne sera généré pour le corps de paquetage. Lorsque l'une des unités ignorées sera référencée plus tard lors de la même invocation de v2cc, le fichier de conception ne sera pas relu car toutes les unités de conception sont conservées en mémoire.

EXEMPLES

La situation la plus simple est lorsque vous n'avez aucun fichier de mappage. Une bibliothèque de conception est alors un répertoire sur votre chemin de bibliothèques. Le nom de ce répertoire est celui de la bibliothèque en VHDL. Chaque fichier dans ce répertoire avec une extension « .vhdl » est utilisé pour une unité de conception portant le même nom que le fichier sans l'extension.

Supposons que vous ayez cette structure de répertoires


somedir/
std/
standard.vhdl
textio.vhdl
ieee/
numeric_bit.vhdl
std_logic_1164.vhdl

Lorsque vous placez « somedir » dans votre chemin de bibliothèques, vous avez accès aux unités de conception


STD.STANDARD
STD.TEXTIO
IEEE.NUMERIC_BIT
IEEE.STD_LOGIC_1164

Dans cette situation, vous avez un fichier par unité de conception. Lorsque vous avez un fichier par bibliothèque de conception, cela ressemblerait à ceci


somedir/
fmf.vhdl

Toutes les références aux unités de conception de la bibliothèque de conception FMF seraient acheminées vers « fmf.vhdl ».

v2cc.libs(5) — FreeHDL

NAME

v2cc.libs — mapping control file for v2cc

DESCRIPTION

The v2cc compiler is used to compile VHDL designs for the FreeHDL project. It can be instructed to map VHDL libraries to specific directories on the file system. This mapping is done via a mapping control file, which is specified using the command-line option “-m”.

The mapping control file consists of a list of library mappings. Each line in the file specifies one or more VHDL libraries and their corresponding directory. The general syntax is:

  v2cc_mapfile <version> [ <library_name> : <directory_path> ... ]

Where:

  • “v2cc_mapfile” is the magic string that identifies the file.

  • “<version>” is the version number of the mapfile format. Currently, the only supported version is “0”.

  • “<library_name>” is the name of the VHDL library. This is case-sensitive.

  • “<directory_path>” is the path to the directory where the VHDL files for the specified library are located. This path can be relative or absolute.

Multiple library mappings can be specified on a single line, separated by spaces. Each mapping consists of the library name, followed by a colon “:”, followed by the directory path.

EXAMPLES

Suppose you have two VHDL libraries, “lib1” and “lib2”. The models for “lib1” are stored in “/foo/lib1_dir”, and the models for “lib2” are stored in “/foo/lib2_dir”. The library root directory is “/foo”.

The file/directory structure is as follows:

/foo <- library root directory /foo/v2cc.libs <- mapping control file /foo/lib1_dir <- library dir for VHDL library lib1 /foo/lib1_dir/comp1.vhdl <- file that contains VHDL model comp1 /foo/lib2_dir <- library dir for VHDL library lib2 /foo/lib2_dir/comp2.vhdl <- file that contains VHDL model comp2

Then, file “/foo/v2cc.libs” should contain:

v2cc_mapfile 0 lib1 : lib1_dir lib2 : lib2_dir

In order to compile a design named comp1 (stored in file comp1.vhdl) into VHDL library lib1 goto subdir “/foo/lib1_dir” and execute:


gvhdl -c -L .. -l lib1 comp1.vhdl

Note that option “-l lib1” forces the compiler to associate the model stored in “comp1.vhdl” with VHDL library lib1. Note further, that the compiler switch “-L ..” specifies the path to the directory where “v2cc.libs” is stored. You may also specify an absolute path:


gvhdl -c -L /foo -l lib1 comp1.vhdl

Note that comp1 should reside in a file named “comp1.vhdl”.

If lib2 contains a design comp2 that makes use of comp1 from lib1 then goto “/foo/lib2_dir” and run the following command to create an executable for model comp2:


gvhdl -L .. -l lib2 comp2.vhdl ../lib1_dir/comp1.o

NOM

v2cc.libs — fichier de contrôle de mappage pour v2cc

DESCRIPTION

Le compilateur v2cc est utilisé pour compiler des designs VHDL pour le projet FreeHDL. Il peut être instruit pour mapper des bibliothèques VHDL à des répertoires spécifiques sur le système de fichiers. Ce mappage est effectué via un fichier de contrôle de mappage, spécifié à l'aide de l'option de ligne de commande “-m”.

Le fichier de contrôle de mappage se compose d'une liste de mappages de bibliothèques. Chaque ligne du fichier spécifie une ou plusieurs bibliothèques VHDL et leur répertoire correspondant. La syntaxe générale est :

  v2cc_mapfile <version> [ <nom_bibliotheque> : <chemin_repertoire> ... ]

Où :

  • “v2cc_mapfile” est la chaîne magique qui identifie le fichier.

  • “<version>” est le numéro de version du format de fichier de mappage. Actuellement, la seule version prise en charge est “0”.

  • “<nom_bibliotheque>” est le nom de la bibliothèque VHDL. Ceci est sensible à la casse.

  • “<chemin_repertoire>” est le chemin d'accès au répertoire où se trouvent les fichiers VHDL pour la bibliothèque spécifiée. Ce chemin peut être relatif ou absolu.

Plusieurs mappages de bibliothèques peuvent être spécifiés sur une seule ligne, séparés par des espaces. Chaque mappage se compose du nom de la bibliothèque, suivi d'un deux-points “:”, suivi du chemin du répertoire.

EXEMPLES

Supposons que vous ayez deux bibliothèques VHDL, “lib1” et “lib2”. Les modèles pour “lib1” sont stockés dans “/foo/lib1_dir”, et les modèles pour “lib2” sont stockés dans “/foo/lib2_dir”. Le répertoire racine de la bibliothèque est “/foo”.

La structure des fichiers/répertoires est la suivante :

/foo <- répertoire racine de la bibliothèque /foo/v2cc.libs <- fichier de contrôle de mappage /foo/lib1_dir <- répertoire de la bibliothèque pour la bibliothèque VHDL lib1 /foo/lib1_dir/comp1.vhdl <- fichier contenant le modèle VHDL comp1 /foo/lib2_dir <- répertoire de la bibliothèque pour la bibliothèque VHDL lib2 /foo/lib2_dir/comp2.vhdl <- fichier contenant le modèle VHDL comp2

Alors, le fichier “/foo/v2cc.libs” devrait contenir :

v2cc_mapfile 0 lib1 : lib1_dir lib2 : lib2_dir

Afin de compiler un design nommé comp1 (stocké dans le fichier comp1.vhdl) dans la bibliothèque VHDL lib1, allez dans le sous-répertoire “/foo/lib1_dir” et exécutez :


gvhdl -c -L .. -l lib1 comp1.vhdl

Notez que l'option “-l lib1” force le compilateur à associer le modèle stocké dans “comp1.vhdl” à la bibliothèque VHDL lib1. Notez également que le commutateur du compilateur “-L ..” spécifie le chemin vers le répertoire où se trouve “v2cc.libs”. Vous pouvez également spécifier un chemin absolu :


gvhdl -c -L /foo -l lib1 comp1.vhdl

Notez que comp1 doit résider dans un fichier nommé “comp1.vhdl”.

Si lib2 contient un design comp2 qui utilise comp1 de lib1, allez dans “/foo/lib2_dir” et exécutez la commande suivante pour créer un exécutable pour le modèle comp2 :


gvhdl -L .. -l lib2 comp2.vhdl ../lib1_dir/comp1.o
