VDE_CRYPTCAB(1) Manuel des commandes générales VDE_CRYPTCAB(1)

NOM

vde_cryptcab - Gestionnaire de câble chiffré pour Virtual Distributed Ethernet

SYNTAXE

vde_cryptcab [ -p numéro_port ] [ -s chemin_socket ] [ -c [utilisateur_distant@]hôte[:numéro_port_distant] ] [ -P clé_prépartagée.key ]| [ -x ] [ -v [v][v][v] ] [ -k ] [ -d ]

DESCRIPTION

Un vde_cryptcab est un gestionnaire de câble distribué pour les commutateurs VDE. Il permet à deux commutateurs VDE sur deux machines de communiquer en utilisant un canal chiffré ChaCha.

Lorsqu'il est utilisé en mode client (c'est-à-dire avec l'option -c), il génère une clé ChaCha aléatoire et utilise scp (1) pour transférer la clé vers le serveur distant.

Côté client, la variable d'environnement SCP_EXTRA_OPTIONS peut être définie afin d'ajouter des options à la ligne de commande scp (ce qui est utile par exemple lorsque dropbear ou un autre client ssh non standard est utilisé pour transférer la clé ChaCha).

Après une phase de négociation à 4 voies pour vérifier les informations d'identification du client, le serveur et le client échangeront des datagrammes VDE en les encapsulant dans des cryptogrammes qui sont envoyés via udp à chaque hôte distant.

Côté serveur, on peut exécuter :


vde_cryptcab -s /tmp/vde2.ctl -p 2100
Pour démarrer un serveur cryptcab multi-pairs, acceptant les datagrammes udp sur le port 2100, qui connecte chaque client distant authentifié à un port différent du commutateur. En fait, une nouvelle instance de vde_plug (1) est lancée et connectée au commutateur via un socket unix local.

La commande


vde_cryptcab -s /tmp/vde2.ctl -c foo@remote.machine.org:2100
connectera un client au serveur distant, fonctionnant sur le port udp 2100. À ce stade, côté serveur, une vérification des informations d'identification de l'utilisateur "foo" est requise, cela pourrait typiquement être : l'authentification basée sur l'hôte, un défi de mot de passe ou une authentification par clé publique. Voir ssh (1) pour plus de détails à ce sujet.

Si les deux vde_switches fonctionnent comme des démons et sont connectés à des interfaces tap, un tunnel chiffré de niveau 2 est établi.

OPTIONS

-p numéro_port
Il est possible de décider quel port udp local utiliser. Lorsque cette option n'est pas spécifiée, cryptcab utilisera le numéro de port udp par défaut, 7667.
-c [utilisateur_distant@]hôte[:numéro_port_distant]
exécute vde_cryptcab en mode client, essayant de se connecter à hôte. Les deux paramètres utilisateur_distant et numéro_port_distant ne sont pas requis. S'ils ne sont pas spécifiés, l'utilisateur exécutant vde_cryptcab est utilisé pour l'authentification sur le serveur, et le port udp par défaut 7667 est utilisé.
-s chemin_socket
spécifie le socket UNIX qui sera utilisé par les programmes locaux pour rejoindre le VDE. La valeur par défaut est "/tmp/vde.ctl".
-P chemin_clé_prépartagée.key
si spécifié, vde_cryptcab fonctionnera en mode clé pré-partagée, au lieu de générer une clé aléatoire à transmettre avec ssh. L'option donnée est le chemin du fichier de clé symétrique pré-partagée à utiliser pour le chiffrement des données. La même clé doit être utilisée côté client et côté serveur.
-x
Désactive le chiffrement par clé symétrique.
-k
Envoie des paquets "keepalive" périodiques pour éviter les timeouts du serveur. Utile lorsque vous voulez maintenir un lien à faible trafic disponible.
-d
Exécuter en tant que démon.
-v
Verbeux. (Utilisez -vv -vvv ou -vvvv pour plus de verbosité)

PROBLEMES CONNUS

L'encapsulation des paquets IP dans une couche session+udp résulte en des datagrammes réels plus grands que le mtu de l'interface tap. Comme vde_cryptcab est confus par la fragmentation des paquets, le mtu de l'interface tap doit être réglé à une valeur inférieure au mtu de l'interface réelle. Utilisez ip(8) ou ifconfig(8) pour configurer le mtu de votre interface tap.

Désactiver explicitement le chiffrement entraîne des problèmes de sécurité évidents. Il est conseillé d'éviter le mode non chiffré (-x) dans les réseaux non contrôlés.
