NOM

varnish-cli - Interface en ligne de commande de Varnish

DESCRIPTION

Varnish possède une interface en ligne de commande (CLI) qui peut contrôler et modifier la plupart des paramètres opérationnels et la configuration de Varnish, sans interrompre le service en cours d'exécution.

La CLI peut être utilisée pour les tâches suivantes :

configuration
Vous pouvez téléverser, modifier et supprimer des fichiers VCL depuis la CLI.
paramètres
Vous pouvez inspecter et modifier les différents paramètres disponibles dans Varnish via la CLI. Les paramètres individuels sont documentés dans la page de manuel varnishd(1).
interdictions
Les interdictions sont des filtres appliqués pour empêcher Varnish de servir du contenu obsolète. Lorsque vous émettez une interdiction, Varnish ne servira aucun objet interdit mis en cache, mais le récupérera plutôt auprès de ses serveurs backend.
gestion des processus
Vous pouvez arrêter et démarrer le processus de cache (enfant) via la CLI. Vous pouvez également récupérer la dernière trace de pile si le processus enfant s'est bloqué.

Si vous invoquez varnishd(1) avec -T, -M ou -d, la CLI sera disponible. En mode de débogage (-d), la CLI sera au premier plan ; avec -T, vous pouvez vous y connecter avec varnishadm ou telnet ; et avec -M, varnishd se connectera en retour à un service d'écoute poussant la CLI vers ce service. Veuillez consulter varnishd(1) pour plus de détails.

Syntaxe

La CLI de Varnish est similaire à une autre interface en ligne de commande, le Bourne Shell. Les commandes sont généralement terminées par un saut de ligne et peuvent prendre des arguments. La commande et ses arguments sont tokenisés avant l'analyse, et par conséquent, les arguments contenant des espaces doivent être entourés de guillemets doubles.

Cela signifie que l'analyse de la commande

help banner

est équivalente à

"help" banner

car les guillemets doubles indiquent uniquement les limites du jeton help.

Dans les guillemets doubles, vous pouvez échapper des caractères avec \ (antislash). Les caractères \n, \r et \t sont traduits en sauts de ligne, retours chariot et tabulations. Les guillemets doubles et les antislashs eux-mêmes peuvent être échappés avec \" et \\ respectivement.

Pour entrer des caractères en octal, utilisez la syntaxe \nnn. Les hexadécimaux peuvent être entrés avec la syntaxe \xnn.

Les commandes ne doivent pas se terminer par un saut de ligne lorsqu'un here document de style shell (here-document ou heredoc) est utilisé. Le format d'un here document est :

<< word
     here document
word

word peut être toute chaîne continue choisie pour s'assurer qu'elle n'apparaît pas naturellement dans le here document suivant. Traditionnellement, EOF ou END est utilisé.

Pièges des guillemets

L'intégration avec la CLI de Varnish peut parfois surprendre lorsque les guillemets sont impliqués. Par exemple, dans le Bourne Shell, le délimiteur utilisé avec les here documents peut être séparé ou non par des espaces du jeton << :

cat <<EOF
hello
world
EOF
hello
world

Avec la CLI de Varnish, les jetons << et EOF doivent être séparés par au moins un espace :

vcl.inline boot <<EOF
106 258
Message from VCC-compiler:
VCL version declaration missing
Update your VCL to Version 4 syntax, and add
        vcl 4.0;
on the first line of the VCL files.
('<vcl.inline>' Line 1 Pos 1)
<<EOF
##---
Running VCC-compiler failed, exited with 2
VCL compilation failed

Sans l'espace manquant, le here document peut être ajouté et le VCL réel peut être chargé :

vcl.inline test << EOF
vcl 4.0;
backend be {
        .host = "localhost";
}
EOF
200 14
VCL compiled.

Une grande différence avec un here document de shell est la gestion du jeton <<. Tout comme les noms de commande peuvent être cités, le jeton here document conserve sa signification, même cité :

vcl.inline test "<<" EOF
vcl 4.0;
backend be {
        .host = "localhost";
}
EOF
200 14
VCL compiled.

Lors de l'utilisation d'un frontal pour la CLI de Varnish comme varnishadm, il faut tenir compte de la double expansion qui se produit. D'abord dans le shell qui lance la commande varnishadm, puis dans la CLI de Varnish elle-même. Lorsqu'un paramètre de commande nécessite des espaces, vous devez vous assurer que la CLI de Varnish voit les guillemets doubles :

varnishadm param.set cc_command '"my alternate cc command"'
Change will take effect when VCL script is reloaded

Sinon, si vous ne citez pas les guillemets, vous pourriez obtenir un message d'erreur apparemment sans rapport :

varnishadm param.set cc_command "my alternate cc command"
Unknown request.
Type 'help' for more info.
Too many parameters
Command failed with error code 105

Si vous citez avec un here document, vous devez l'envelopper dans un argument multi-lignes du shell :

varnishadm vcl.inline test '<< EOF
vcl 4.0;
backend be {
        .host = "localhost";
}
EOF'
VCL compiled.

Une autre différence avec un here document de shell est qu'un seul here document peut être utilisé sur une seule ligne de commande. Par exemple, il est possible de faire ceci dans un script shell :

#!/bin/sh
cat << EOF1 ; cat << EOF2
hello
EOF1
world
EOF2

La sortie attendue est :

hello
world

Avec la CLI de Varnish, seul le dernier argument peut utiliser la forme here document, ce qui restreint considérablement le nombre de commandes qui peuvent les utiliser efficacement. Essayer d'utiliser plusieurs here documents ne prend en compte que le dernier.

Par exemple :

command argument << EOF1 << EOF2
heredoc1
EOF1
heredoc2
EOF2

Ceci résulte conceptuellement en la ligne de commande suivante :

  • "command"
  • "argument"
  • "<<"
  • "EOF1"
  • "heredoc1\nEOF1\nheredoc2\n"

Les autres pièges incluent l'expansion des variables du shell qui invoque varnishadm, mais cela n'est pas directement lié à la CLI de Varnish. Si vous gérez correctement les guillemets, vous devriez vous en sortir même avec des commandes complexes.

JSON

Un certain nombre de commandes avec des réponses informatives prennent en charge un paramètre -j pour la sortie JSON, comme spécifié ci-dessous. La structure de premier niveau de la réponse JSON est un tableau contenant ces trois premiers éléments :

  • Un numéro de version du format JSON (entier)
  • Un tableau de chaînes de caractères qui composent la commande CLI reçue
  • L'heure à laquelle la réponse a été générée, sous forme d'heure d'époque Unix en secondes avec précision milliseconde (nombre à virgule flottante)

Les éléments restants du tableau constituent les données spécifiques à la commande CLI, et leur structure et leur contenu dépendent de la commande.

Par exemple, la réponse à status -j contient simplement une chaîne dans le tableau de premier niveau indiquant l'état du processus enfant ("running", "stopped", etc.) :

[ 2, ["status", "-j"], 1538031732.632, "running"
]

Les réponses JSON à d'autres commandes peuvent avoir des listes d'éléments plus longues, qui peuvent avoir des types de données simples ou former des objets structurés.

La sortie JSON n'est renvoyée que si l'exécution de la commande a réussi. La sortie d'une réponse d'erreur est toujours la même qu'elle aurait été pour la commande sans le paramètre -j.

Commandes

Ce site n'est en aucun cas associé à Arch Linux ni affilié à ce projet. Le contenu est uniquement une traduction des pages de manuel d'Arch publiées sur man.archlinux.org.

Commandes

auth <réponse>

Authentifier.

backend.list [-j] [-p] [<backend_pattern>]

Lister les backends.

-p affiche également l'état de la sonde.

-j spécifie une sortie JSON.

Sauf si -j est spécifié pour une sortie JSON, le format de sortie est constitué de cinq colonnes de largeur dynamique, séparées par des espaces blancs avec les champs :

  • Nom du backend
  • Admin : Comment l'état de santé est déterminé :
  • sain : Défini comme sain via backend.set_health.
  • malade : Défini comme malade via backend.set_health.
  • sonde : L'état de santé est déterminé par une sonde ou un autre mécanisme dynamique.
  • supprimé : Le backend a été supprimé, mais pas encore nettoyé.

L'admin a la priorité sur l'état de santé.

  • Sonde X/Y : X sur Y contrôles ont réussi

    X et Y sont spécifiques au backend et peuvent représenter des contrôles de sonde, d'autres backends ou toute autre métrique.

    S'il n'y a pas de sonde ou si le directeur ne fournit pas de détails sur les résultats des contrôles de sonde, 0/0 est affiché.

  • Santé : État de santé de la sonde
  • sain
  • malade

En l'absence de sonde, sain est affiché.

•
Dernier changement : Horodatage du dernier changement d'état de santé.

L'état de santé rapporté ici est générique. La santé d'un backend peut également dépendre du contexte dans lequel il est utilisé (par exemple, le hash de l'objet), de sorte que l'état de santé réel tel que visible depuis VCL (par exemple, en utilisant std.healthy()) peut différer.

Pour -j, les membres de l'objet doivent être explicites, correspondant aux champs décrits ci-dessus. probe_message a le format [X, Y, « état »] tel que décrit ci-dessus pour Sonde. Les détails de la sonde JSON (arguments -j -p) sont spécifiques au directeur.

backend.set_health <backend_pattern> [auto|sain|malade]

Définir l'état de santé du ou des backends correspondant à <backend_pattern>.
  • Avec auto, l'état de santé est déterminé par une sonde ou un autre mécanisme dynamique, le cas échéant.
  • sain définit le backend comme utilisable.
  • malade définit le backend comme inutilisable.

ban <champ> <opérateur> <arg> [&& <champ> <opérateur> <arg> ...]

Marquer comme obsolètes tous les objets pour lesquels toutes les conditions correspondent.

Voir std.ban() pour plus de détails.

ban.list [-j]

Lister les bans actifs.

Sauf si -j est spécifié pour une sortie JSON, le format de sortie est :

  • Heure d'émission du ban.
  • Objets faisant référence à ce ban.
  • C si le ban est terminé = plus de tests contre lui.
  • si le débogage lurker est activé :
  • R pour les tests req.*
  • O pour les tests obj.*
  • Pointeur vers l'objet ban
•
Spécification du ban

Les durées des spécifications de ban sont normalisées, par exemple "7d" est changé en "1w".

banner

Afficher la bannière de bienvenue.

help [-j|<commande>]

Afficher l'aide sur la commande/le protocole.

-j spécifie une sortie JSON.

panic.clear [-z]

Effacer le dernier panic, le cas échéant, -z effacera le(s) compteur(s) varnishstat associé(s).

panic.show [-j]

Retourner le dernier panic, le cas échéant.

-j spécifie une sortie JSON -- le message de panic est retourné comme une chaîne JSON non structurée.

param.reset [-j] <param>

Réinitialiser le paramètre à sa valeur par défaut.

La sortie JSON est identique à param.show -j <param> et contient la valeur mise à jour telle qu'elle serait représentée par une exécution ultérieure de param.show.

param.set [-j] <param> <valeur>

Définir la valeur d'un paramètre.

La sortie JSON est identique à param.show -j <param> et contient la valeur mise à jour telle qu'elle serait représentée par une exécution ultérieure de param.show.

Ceci peut être utile pour vérifier ultérieurement qu'une valeur de paramètre n'a pas changé et pour utiliser la valeur de la sortie JSON afin de réinitialiser le paramètre à la valeur souhaitée.

param.show [-l|-j] [<param>|changé]

Afficher les paramètres et leurs valeurs.

La forme longue avec -l affiche des informations supplémentaires, y compris la documentation et les valeurs minimales, maximales et par défaut, si elles sont définies pour le paramètre. La sortie JSON est spécifiée avec -j, dans laquelle les informations de la forme longue sont incluses ; un seul des arguments -l ou -j est autorisé. Si un paramètre est spécifié avec <param>, affichez uniquement ce paramètre. Si changé est spécifié, affichez uniquement les paramètres dont les valeurs diffèrent de leurs valeurs par défaut.

pid [-j]

Afficher le PID du processus maître, et de l'ouvrier s'il est en cours d'exécution.

-j spécifie une sortie JSON.

ping [-j] [<horodatage>]

Maintenir la connexion active.

La réponse est formatée en JSON si -j est spécifié.

quit

Fermer la connexion.

start

Démarrer le processus de cache Varnish.

status [-j]

Vérifier l'état du processus de cache Varnish.

-j spécifie une sortie JSON.

stop

Arrêter le processus de cache Varnish.

storage.list [-j]

Lister les périphériques de stockage.

-j spécifie une sortie JSON.

vcl.deps [-j]

Lister toutes les configurations chargées et leurs dépendances.

Sauf si -j est spécifié pour une sortie JSON, le format de sortie est constitué de jusqu'à deux colonnes de largeur dynamique séparées par des espaces blancs avec les champs :

  • VCL : un programme VCL
  • Dépendance : un autre programme VCL dont il dépend

Seules les dépendances directes sont listées, et les VCL avec plusieurs dépendances sont listées plusieurs fois.

vcl.discard <name_pattern>...

Décharger les configurations nommées (si possible).

Décharge les configurations et les étiquettes nommées correspondant à au moins un modèle de nom. Toutes les configurations et étiquettes correspondantes sont déchargées dans le bon ordre par rapport aux dépendances potentielles. Si une configuration ou une étiquette n'a pas pu être déchargée car une de ses dépendances resterait, rien n'est déchargé. Chaque modèle de nom individuel doit correspondre à au moins une configuration ou étiquette nommée.

vcl.inline <configname> <quoted_VCLstring> [auto|cold|warm]

Comp
ile et charge les données VCL sous le nom fourni.

La saisie VCL multi-lignes peut être effectuée à l'aide du here-document ref_syntax.

vcl.label <label> <configname>

Applique une étiquette à une configuration.

Une étiquette VCL est comme un lien symbolique UNIX, un nom sans substance, qui pointe vers un autre VCL.

Les étiquettes sont obligatoires lorsque VCL référence un autre VCL.

vcl.list [-j]

Liste toutes les configurations chargées.

Sauf si -j est spécifié pour une sortie JSON, le format de sortie est de cinq ou sept colonnes de largeur dynamique, séparées par des espaces blancs avec les champs :

  • statut : active, disponible ou mise au rebut
  • état : étiquette, froid, tiède ou auto
  • température : init, froid, tiède, occupée ou refroidissement
  • occupée : nombre de références à ce vcl (entier)
  • nom : le nom donné à ce vcl ou à cette étiquette
  • [ <- | -> ] et informations sur l'étiquette les deux derniers champs)
  • -> <vcl> : l'étiquette « pointe vers » le <vcl> nommé
  • <- (<n> étiquette(s)) : le vcl a <n> étiquette(s)

vcl.load <nom_config> <nom_fichier> [auto|froid|tiède]

Compile et charge le fichier VCL sous le nom fourni.

vcl.show [-v] [<nom_config>]

Affiche le code source de la configuration spécifiée.

vcl.state <nom_config> auto|froid|tiède

Force l'état de la configuration nommée.

vcl.symtab

Décharge les tables de symboles VCL.

vcl.use <nom_config|étiquette>

Passe à la configuration nommée immédiatement.

Modèle de Backend

Un modèle de backend peut être un nom de backend ou une combinaison d'un nom VCL et d'un nom de backend au format « VCL.backend ». Si le nom VCL est omis, le VCL actif est supposé. La correspondance partielle sur les noms de backend et VCL est prise en charge à l'aide de caractères génériques de style shell, par exemple l'astérisque (*).

Exemples :

backend.list def*
backend.list b*.def*
backend.set_health default sick
backend.set_health def* healthy
backend.set_health * auto

Expressions de Bannissement

Une expression de bannissement se compose d'une ou plusieurs conditions. Une condition se compose d'un champ, d'un opérateur et d'un argument. Les conditions peuvent être combinées avec « && ».

Un champ peut être l'une des variables de VCL, par exemple req.url, req.http.host ou obj.http.set-cookie.

Les opérateurs sont « == » pour la comparaison directe, « ~ » pour une correspondance d'expression régulière, et « > » ou « < » pour les comparaisons de taille. Préfixer un opérateur avec « ! » nie l'expression.

L'argument peut être une chaîne entre guillemets, une expression régulière ou un entier. Les entiers peuvent avoir « KB », « MB », « GB » ou « TB » ajoutés pour les champs liés à la taille.

Température VCL

Un programme VCL passe par plusieurs états liés aux différentes commandes : il peut être chargé, utilisé, puis mis au rebut. Vous pouvez charger plusieurs programmes VCL et passer d'un à l'autre à tout moment. Il n'y a qu'un seul VCL actif, mais le VCL actif précédent sera maintenu actif jusqu'à la fin de toutes ses transactions.

Avec le temps, si vous rafraîchissez souvent votre VCL et conservez les versions précédentes, la consommation de ressources augmentera, vous ne pourrez pas y échapper. Cependant, la plupart du temps, vous souhaitez payer le prix uniquement pour le VCL actif et conserver les anciens VCL au cas où vous auriez besoin de revenir à une version précédente.

La température VCL vous permet de minimiser l'empreinte des VCL inactifs. Une fois qu'un VCL devient froid, Varnish libérera toutes les ressources qui peuvent être réacquises plus tard. Vous pouvez définir manuellement la température d'un VCL ou laisser varnish le gérer automatiquement.

EXEMPLES

Chargez un VCL multi-lignes à l'aide d'un *here document* de style shell :

vcl.inline example << EOF
vcl 4.0;
backend www {
    .host = "127.0.0.1";
    .port = "8080";
}
EOF

Bannissez toutes les requêtes où req.url correspond exactement à la chaîne /news :

ban req.url == "/news"

Bannissez tous les documents où l'hôte de service est « example.com » ou « www.example.com », et où l'en-tête Set-Cookie reçu du backend contient « USERID=1663 » :

ban req.http.host ~ "^(?i)(www\\.)?example\\.com$" && obj.http.set-cookie ~ "USERID=1663"
