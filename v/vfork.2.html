vfork(2) Manuel des appels système vfork(2)

NOM

vfork - créer un processus enfant et bloquer le parent

BIBLIOTHÈQUE

Bibliothèque C standard (libc, -lc)

SYNTAXE

#include <unistd.h>
pid_t vfork(void);
Exigences des macros de test de fonctionnalités pour glibc (voir feature_test_macros(7)) :

vfork() :

    Depuis glibc 2.12 :
        (_XOPEN_SOURCE >= 500) && ! (_POSIX_C_SOURCE >= 200809L)
            || /* Depuis glibc 2.19 : */ _DEFAULT_SOURCE
            || /* glibc <= 2.19 : */ _BSD_SOURCE
    Avant glibc 2.12 :
        _BSD_SOURCE || _XOPEN_SOURCE >= 500

DESCRIPTION

Description standard

(De POSIX.1) La fonction vfork() a le même effet que fork(2), sauf que le comportement est indéfini si le processus créé par vfork() modifie des données autres qu'une variable de type pid_t utilisée pour stocker la valeur de retour de vfork(), ou si elle retourne de la fonction dans laquelle vfork() a été appelée, ou si elle appelle une autre fonction avant d'appeler avec succès _exit(2) ou l'une des familles de fonctions exec(3).

Description Linux

vfork(), tout comme fork(2), crée un processus enfant du processus appelant. Pour les détails, la valeur de retour et les erreurs, voir fork(2).

vfork() est un cas particulier de clone(2). Il est utilisé pour créer de nouveaux processus sans copier les tables de pages du processus parent. Il peut être utile dans les applications sensibles aux performances où un enfant est créé qui émet ensuite immédiatement un execve(2).

vfork() diffère de fork(2) en ce que le thread appelant est suspendu jusqu'à ce que l'enfant se termine (normalement, en appelant _exit(2), ou anormalement, après la livraison d'un signal fatal), ou qu'il effectue un appel à execve(2). Jusqu'à ce point, l'enfant partage toute la mémoire avec son parent, y compris la pile. L'enfant ne doit pas retourner de la fonction actuelle ni appeler exit(3) (ce qui aurait pour effet d'appeler les gestionnaires de sortie établis par le processus parent et de vider les tampons stdio(3) du parent), mais peut appeler _exit(2).

Comme avec fork(2), le processus enfant créé par vfork() hérite de copies de divers attributs de processus de l'appelant (par exemple, les descripteurs de fichiers, les dispositions des signaux et le répertoire de travail actuel) ; l'appel vfork() ne diffère que dans le traitement de l'espace d'adressage virtuel, comme décrit ci-dessus.

Les signaux envoyés au parent arrivent après que l'enfant libère la mémoire du parent (c'est-à-dire après que l'enfant se termine ou appelle execve(2)).

Description historique

Sous Linux, fork(2) est implémenté à l'aide de pages en copie sur écriture, donc le seul coût encouru par fork(2) est le temps et la mémoire nécessaires pour dupliquer les tables de pages du parent, et pour créer une structure de tâche unique pour l'enfant. Cependant, dans les temps anciens, un fork(2) aurait nécessité une copie complète de l'espace de données de l'appelant, souvent inutilement, puisque généralement juste après un exec(3) est effectué. Ainsi, pour une plus grande efficacité, BSD a introduit l'appel système vfork(), qui ne copiait pas complètement l'espace d'adressage du processus parent, mais empruntait la mémoire et le fil d'exécution du parent jusqu'à un appel à execve(2) ou une sortie. Le processus parent était suspendu pendant que l'enfant utilisait ses ressources. L'utilisation de vfork() était délicate : par exemple, ne pas modifier les données du processus parent dépendait de la connaissance des variables qui étaient conservées dans un registre.

VERSIONS

Les exigences imposées à vfork() par les normes sont moins strictes que celles imposées à fork(2), de sorte qu'une implémentation où les deux sont synonymes est conforme. En particulier, le programmeur ne peut pas compter sur le fait que le parent reste bloqué jusqu'à ce que l'enfant se termine ou appelle execve(2), et ne peut pas compter sur un comportement spécifique concernant la mémoire partagée.

Certains considèrent que la sémantique de vfork() est une imperfection architecturale, et le manuel 4.2BSD indiquait : « Cet appel système sera éliminé lorsque les mécanismes de partage système appropriés seront implémentés. Les utilisateurs ne doivent pas dépendre des sémantiques de partage de mémoire de vfork car il sera, dans ce cas, rendu synonyme de fork. » Cependant, bien que les systèmes modernes de gestion de la mémoire aient réduit la différence de performance entre fork(2) et vfork(), il existe diverses raisons pour lesquelles Linux et d'autres systèmes ont conservé vfork() :

•
Certaines applications critiques pour les performances nécessitent l'avantage de performance réduit conféré par vfork().
•
vfork() peut être implémenté sur des systèmes qui n'ont pas d'unité de gestion de la mémoire (MMU), mais fork(2) ne peut pas être implémenté sur de tels systèmes. (POSIX.1-2008 a supprimé vfork() de la norme ; la justification POSIX pour la fonction posix_spawn(3) note que cette fonction, qui fournit des fonctionnalités équivalentes à fork(2)+exec(3), est conçue pour être implémentable sur des systèmes qui n'ont pas de MMU.)
•
Sur les systèmes où la mémoire est limitée, vfork() évite de devoir engager temporairement de la mémoire (voir la description de /proc/sys/vm/overcommit_memory dans proc(5)) afin d'exécuter un nouveau programme. (Cela peut être particulièrement avantageux lorsqu'un processus parent volumineux souhaite exécuter un petit programme auxiliaire dans un processus enfant.) Par conséquent, utiliser fork(2) dans ce scénario nécessite soit d'engager une quantité de mémoire égale à la taille du processus parent (si un sur-engagement strict est en vigueur) soit de sur-engager la mémoire avec le risque qu'un processus soit terminé par le tueur de mémoire insuffisante (OOM).

Notes Linux

Les gestionnaires de fork établis à l'aide de pthread_atfork(3) ne sont pas appelés lorsqu'un programme multithread utilisant la bibliothèque de threads NPTL appelle vfork(). Les gestionnaires de fork sont appelés dans ce cas dans un programme utilisant la bibliothèque de threads LinuxThreads. (Voir pthreads(7) pour une description des bibliothèques de threads Linux.)

Un appel à vfork() est équivalent à l'appel de clone(2) avec flags spécifié comme :


 CLONE_VM | CLONE_VFORK | SIGCHLD

NORMES

Aucune.

HISTORIQUE

4.3BSD ; POSIX.1-2001 (mais marqué OBSOLÈTE). POSIX.1-2008 supprime la spécification de vfork().

L'appel système vfork() est apparu dans 3.0BSD. Dans 4.4BSD, il a été rendu synonyme de fork(2) mais NetBSD l'a réintroduit ; voir http://www.netbsd.org/Documentation/kernel/vfork.html. Dans Linux, il a été équivalent à fork(2) jusqu'à Linux 2.2.0-pre6 environ. Depuis Linux 2.2.0-pre9 (sur i386, un peu plus tard sur d'autres architectures), c'est un appel système indépendant. La prise en charge a été ajoutée dans glibc 2.0.112.

MISE EN GARDE

Le processus enfant doit prendre garde à ne pas modifier la mémoire de manière involontaire, car de telles modifications seront vues par le processus parent une fois que l'enfant se terminera ou exécutera un autre programme. À cet égard, les gestionnaires de signaux peuvent être particulièrement problématiques : si un gestionnaire de signaux invoqué dans l'enfant de vfork() modifie la mémoire, ces modifications peuvent entraîner un état de processus incohérent du point de vue du processus parent (par exemple, les modifications de mémoire seraient visibles dans le parent, mais les modifications de l'état des descripteurs de fichiers ouverts ne le seraient pas).

Lorsque vfork() est appelé dans un processus multithreadé, seul le thread appelant est suspendu jusqu'à ce que l'enfant se termine ou exécute un nouveau programme. Cela signifie que l'enfant partage un espace d'adressage avec d'autres codes en cours d'exécution. Cela peut être dangereux si un autre thread du processus parent modifie les identifiants (en utilisant setuid(2) ou similaire), car il y a maintenant deux processus avec différents niveaux de privilèges s'exécutant dans le même espace d'adressage. À titre d'exemple des dangers, supposons qu'un programme multithreadé s'exécutant en tant que root crée un enfant en utilisant vfork(). Après le vfork(), un thread du processus parent abaisse le processus à un utilisateur sans privilèges afin d'exécuter du code non fiable (par exemple, peut-être via un plugin ouvert avec dlopen(3)). Dans ce cas, des attaques sont possibles où le processus parent utilise mmap(2) pour mapper du code qui sera exécuté par le processus enfant privilégié.

BOGUES

Les détails de la gestion des signaux sont obscurs et diffèrent selon les systèmes. La page de manuel BSD indique : « Pour éviter une situation de blocage potentiel, les processus qui sont des enfants au milieu d'un vfork() ne reçoivent jamais les signaux SIGTTOU ou SIGTTIN ; plutôt, les sorties ou les ioctl sont autorisées et les tentatives d'entrée entraînent une indication de fin de fichier. »
