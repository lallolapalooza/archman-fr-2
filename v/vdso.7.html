vDSO(7) Manuel d'informations diverses vDSO(7)

NOM

vdso — présentation de l'objet partagé dynamique virtuel (vDSO)

SYNTAXE

#include <sys/auxv.h>
void *vdso = (uintptr_t) getauxval(AT_SYSINFO_EHDR);

DESCRIPTION

L'« objet partagé dynamique virtuel » (vDSO) est une petite bibliothèque partagée que le noyau mappe automatiquement dans l'espace d'adressage de toutes les applications en espace utilisateur. Les applications n'ont généralement pas besoin de se préoccuper de ces détails car le vDSO est le plus souvent appelé par la bibliothèque C. De cette manière, vous pouvez coder normalement en utilisant des fonctions standard et la bibliothèque C se chargera d'utiliser toute fonctionnalité disponible via le vDSO.

Pourquoi le vDSO existe-t-il ? Il existe certains appels système que le noyau fournit et que le code en espace utilisateur utilise fréquemment, au point que ces appels peuvent dominer les performances globales. Ceci est dû à la fois à la fréquence de l'appel et aux frais généraux de changement de contexte résultant de la sortie de l'espace utilisateur et de l'entrée dans le noyau.

Le reste de cette documentation s'adresse aux curieux et/ou aux rédacteurs de bibliothèques C plutôt qu'aux développeurs généraux. Si vous essayez d'appeler le vDSO dans votre propre application plutôt que d'utiliser la bibliothèque C, vous faites très probablement une erreur.

Contexte d'exemple

Effectuer des appels système peut être lent. Sur les systèmes x86 32 bits, vous pouvez déclencher une interruption logicielle (int $0x80) pour indiquer au noyau que vous souhaitez effectuer un appel système. Cependant, cette instruction est coûteuse : elle passe par les chemins complets de gestion des interruptions du microcode du processeur ainsi que du noyau. Les processeurs plus récents disposent d'instructions plus rapides (mais incompatibles avec les versions précédentes) pour initier des appels système. Plutôt que d'obliger la bibliothèque C à déterminer si cette fonctionnalité est disponible à l'exécution, la bibliothèque C peut utiliser les fonctions fournies par le noyau dans le vDSO.

Notez que la terminologie peut prêter à confusion. Sur les systèmes x86, la fonction vDSO utilisée pour déterminer la méthode préférée pour effectuer un appel système est nommée « __kernel_vsyscall », mais sur x86-64, le terme « vsyscall » fait également référence à une méthode obsolète pour demander au noyau quelle heure il est ou sur quel processeur se trouve l'appelant.

Un appel système fréquemment utilisé est gettimeofday(2). Cet appel système est appelé directement par les applications en espace utilisateur ainsi qu'indirectement par la bibliothèque C. Pensez aux horodatages ou aux boucles de temporisation ou à la sonderie — toutes ces opérations ont souvent besoin de savoir quelle heure il est maintenant. Ces informations ne sont pas non plus secrètes — n'importe quelle application dans n'importe quel mode de privilège (root ou tout utilisateur non privilégié) obtiendra la même réponse. Ainsi, le noyau s'arrange pour que les informations requises pour répondre à cette question soient placées dans une mémoire accessible au processus. Désormais, un appel à gettimeofday(2) passe d'un appel système à un appel de fonction normal et à quelques accès mémoire.

Trouver le vDSO

L'adresse de base du vDSO (s'il en existe un) est transmise par le noyau à chaque programme dans le vecteur auxiliaire initial (voir getauxval(3)), via la balise AT_SYSINFO_EHDR.

Vous ne devez pas supposer que le vDSO est mappé à un endroit particulier dans la carte mémoire de l'utilisateur. L'adresse de base sera généralement aléatoire à l'exécution, à chaque création d'une nouvelle image de processus (au moment de execve(2)). Ceci est fait pour des raisons de sécurité, afin d'empêcher les attaques de type « return-to-libc ».

Pour certaines architectures, il existe également une balise AT_SYSINFO. Celle-ci est utilisée uniquement pour localiser le point d'entrée du vsyscall et est souvent omise ou définie à 0 (signifiant qu'elle n'est pas disponible). Cette balise est un vestige du travail initial du vDSO (voir « Historique » ci-dessous) et son utilisation doit être évitée.

Format de fichier

Comme le vDSO est une image ELF entièrement formée, vous pouvez y effectuer des recherches de symboles. Cela permet d'ajouter de nouveaux symboles avec des versions plus récentes du noyau et permet à la bibliothèque C de détecter les fonctionnalités disponibles à l'exécution lors de l'exécution sous différentes versions du noyau. Souvent, la bibliothèque C effectue la détection lors du premier appel, puis met en cache le résultat pour les appels ultérieurs.

Tous les symboles sont également versionnés (en utilisant le format de version GNU). Cela permet au noyau de mettre à jour la signature de la fonction sans casser la compatibilité descendante. Cela signifie changer les arguments que la fonction accepte ainsi que la valeur de retour. Ainsi, lors de la recherche d'un symbole dans le vDSO, vous devez toujours inclure la version pour correspondre à l'ABI attendu.

Typiquement, le vDSO suit la convention de nommage consistant à préfacer tous les symboles avec « __vdso_ » ou « __kernel_ » afin de les distinguer des autres symboles standard. Par exemple, la fonction « gettimeofday » est nommée « __vdso_gettimeofday ».

Vous utilisez les conventions d'appel C standard lorsque vous appelez l'une de ces fonctions. Pas besoin de s'inquiéter d'un comportement étrange des registres ou de la pile.

NOTES

Source

Lorsque vous compilez le noyau, il compilera et liera automatiquement le code vDSO pour vous. Vous le trouverez fréquemment dans le répertoire spécifique à l'architecture :


find arch/$ARCH/ -name '*vdso*.so*' -o -name '*gate*.so*'

Noms du vDSO

Le nom du vDSO varie selon les architectures. Il apparaît souvent dans des choses comme la sortie de ldd(1) de glibc. Le nom exact ne devrait avoir aucune importance pour aucun code, ne le codez donc pas en dur.

strace(1), seccomp(2), et le vDSO

Lors du traçage des appels système avec strace(1), les symboles (appels système) qui sont exportés par le vDSO n'apparaîtront *pas* dans la sortie du traçage. Ces appels système ne seront pas non plus visibles par les filtres seccomp(2).

NOTES SPÉCIFIQUES À L'ARCHITECTURE

Les sous-sections ci-dessous fournissent des notes spécifiques à l'architecture sur le vDSO.

Notez que le vDSO utilisé est basé sur l'ABI de votre code en espace utilisateur et non sur l'ABI du noyau. Ainsi, par exemple, lorsque vous exécutez un binaire ELF 32 bits i386, vous obtiendrez le même vDSO, que vous l'exécutiez sous un noyau 32 bits i386 ou sous un noyau 64 bits x86-64. Par conséquent, le nom de l'ABI de l'espace utilisateur doit être utilisé pour déterminer quelle section ci-dessous est pertinente.

fonctions parisc (hppa)

Le port parisc dispose d'une page de code avec des fonctions utilitaires appelée page de passerelle. Plutôt que d'utiliser l'approche normale du vecteur auxiliaire ELF, il transmet l'adresse de la page au processus via le registre SR2. Les permissions sur la page sont telles que la simple exécution de ces adresses exécute automatiquement avec les privilèges du noyau et non en espace utilisateur. Ceci est fait pour correspondre à la façon dont HP-UX fonctionne.

Comme il ne s'agit que d'une page de code brute, il n'y a pas d'informations ELF pour la recherche de symboles ou le versionnement. Appelez simplement l'offset approprié via l'instruction de branchement, par exemple :


ble <offset>(%sr2, %r0)
décalage fonction
00b0 lws_entry (opérations CAS)
00e0 set_thread_pointer (utilisé par glibc)
0100 linux_gateway_entry (appel système)

vdso(7) — Linux manual pages

NAME

vdso - virtual dynamic shared object

SYNOPSIS

The vDSO is an in-memory shared library that the kernel automatically maps into the address space of every user-space process. It provides a faster way to execute certain system calls.

DESCRIPTION

The vDSO is a mechanism by which the kernel can expose a subset of its functionality to user space without requiring a context switch. This is achieved by mapping a small shared library (the vDSO) into the address space of each process. When a user-space application calls one of the functions exported by the vDSO, it executes the code directly in user space, avoiding the overhead of a system call.

The vDSO is not visible as a regular file on the filesystem. It is instead represented in a process's memory map (e.g., as shown by proc(5)) as a region with read and execute permissions, typically labeled "[vdso]".

The functions provided by the vDSO vary depending on the kernel version and the architecture. The primary goal is to provide fast access to time-related system calls, such as clock_gettime(2), gettimeofday(2), and time(2). These are typically implemented as vDSO functions when possible.

User-space applications should not call the vDSO functions directly. Instead, they should use the standard C library wrappers (e.g., clock_gettime(2) in glibc). The C library will automatically detect the presence of the vDSO and use it when appropriate. If the vDSO is not available or if the specific function is not exported by the vDSO, the C library will fall back to making a regular system call.

The vDSO functions are usually exported with specific version strings, such as LINUX_2.6. This helps ensure compatibility across different kernel versions.

NOTES

The vDSO is a performance optimization. The correctness of the system calls is guaranteed by the kernel itself. If the vDSO is unavailable or fails for any reason, the C library will automatically use the traditional system call mechanism.

The set of functions provided by the vDSO can change between kernel versions. Applications should rely on the C library to handle these changes transparently.

The memory region occupied by the vDSO is read-only for user space after it has been set up by the kernel.

History

The vDSO was originally just a single function—the vsyscall. In older kernels, you might see that name in a process's memory map rather than "vdso". Over time, people realized that this mechanism was a great way to pass more functionality to user space, so it was reconceived as a vDSO in the current format.
