VI(1P) Manuel du programmeur POSIX VI(1P)

PROLOG

Cette page de manuel fait partie du Manuel du programmeur POSIX. L'implémentation Linux de cette interface peut différer (consultez la page de manuel Linux correspondante pour les détails du comportement sous Linux), ou l'interface peut ne pas être implémentée sous Linux.

NOM

vi — éditeur visuel orienté écran

SYNTAXE

vi [-rR] [-c commande] [-t mot-clé] [-w taille] [fichier...]

DESCRIPTION

Cet utilitaire doit être fourni sur les systèmes qui prennent en charge l'option Utilitaires de portabilité utilisateur et qui définissent le symbole POSIX2_CHAR_TERM. Sur d'autres systèmes, il est facultatif.

L'utilitaire vi (visuel) est un éditeur de texte orienté écran. Seuls les modes ouvert et visuel de l'éditeur sont décrits dans POSIX.1‐2008 ; consultez l'éditeur de ligne ex pour des capacités d'édition supplémentaires utilisées dans vi. L'utilisateur peut passer de vi à ex et exécuter des commandes ex depuis vi.

Cette page de référence utilise le terme tampon d'édition pour décrire le texte de travail actuel. Aucune implémentation spécifique n'est impliquée par ce terme. Toutes les modifications d'édition sont effectuées sur le tampon d'édition, et aucune modification de celui-ci n'affectera un fichier tant qu'une commande de l'éditeur n'écrira pas le fichier.

Lors de l'utilisation de vi, l'écran du terminal agit comme une fenêtre sur le tampon d'édition. Les modifications apportées au tampon d'édition se refléteront dans l'affichage de l'écran ; la position du curseur sur l'écran indiquera la position dans le tampon d'édition.

Certains terminaux n'ont pas toutes les capacités nécessaires pour prendre en charge la définition complète de vi. Lorsque ces commandes ne peuvent pas être prises en charge sur de tels terminaux, cette condition ne produira pas de message d'erreur tel que « not an editor command » (pas une commande d'éditeur) ni ne signalera d'erreur de syntaxe. L'implémentation peut soit accepter les commandes et produire des résultats à l'écran qui résultent d'une tentative infructueuse de répondre aux exigences de ce volume de POSIX.1‐2017, soit signaler une erreur décrivant la déficience liée au terminal.

ENTRÉE STANDARD

Si l'entrée standard n'est pas un terminal, les résultats ne sont pas définis. L'entrée standard se compose d'une série de commandes et de texte d'entrée, comme décrit dans la section DESCRIPTION ÉTENDUE.

Si une lecture de l'entrée standard renvoie une erreur, ou si l'éditeur détecte une condition de fin de fichier depuis l'entrée standard, cela équivaut à un événement asynchrone SIGHUP.

SORTIE STANDARD

Si la sortie standard n'est pas un terminal, des résultats indéfinis se produisent.

La sortie standard peut être utilisée pour écrire des invites à l'utilisateur, pour des messages d'information et pour écrire des lignes du fichier.

Si la sortie standard n'est pas un terminal, des résultats indéfinis se produisent.

L'erreur standard ne doit être utilisée que pour les messages diagnostiques.

DESCRIPTION ÉTENDUE

Si le terminal n'a pas les capacités nécessaires pour prendre en charge une partie non spécifiée de la définition de vi, les implémentations commenceront initialement en mode ex ou en mode ouvert. Sinon, après l'initialisation, vi sera en mode commande ; le mode de saisie de texte peut être activé par l'une des plusieurs commandes utilisées pour insérer ou modifier du texte. En mode de saisie de texte, <ESC> peut être utilisé pour revenir au mode commande ; d'autres utilisations de <ESC> sont décrites plus loin dans cette section ; voir Terminer une commande ou un mode de saisie.

Descriptions des commandes dans vi

Les symboles suivants sont utilisés dans cette page de référence pour représenter les arguments des commandes.

tampon
Voir la description de tampon dans la section DESCRIPTION ÉTENDUE de l'utilitaire ex ; voir Descriptions des commandes dans ex.

En mode ouvert et visuel, lorsqu'un synopsis de commande montre à la fois [tampon] et [compteur] précédant le nom de la commande, ils peuvent être spécifiés dans n'importe quel ordre.

compteur
Un entier positif utilisé comme argument facultatif pour la plupart des commandes, soit pour donner un nombre de répétitions, soit comme taille. Cet argument est facultatif et sera par défaut à 1 sauf indication contraire.

Les lignes de synopsis pour les commandes vi <control>‐G, <control>‐L, <control>‐R, <control>‐], %, &, ^, D, m, M, Q, u, U et ZZ n'ont pas compteur comme argument facultatif. Quoi qu'il en soit, spécifier un compteur à ces commandes ne sera pas une erreur, et tout compteur spécifié sera ignoré.

mouvement
Un argument final facultatif utilisé par les commandes !, <, >, c, d et y, qui est utilisé pour indiquer la région de texte qui sera affectée par la commande. Le mouvement peut être soit l'un des caractères de commande répété, soit l'une de plusieurs autres commandes vi (listées dans le tableau suivant). Dans le reste de la description de l'utilitaire vi, le terme ``ligne de tampon'' fait référence à une ligne dans le tampon d'édition et le terme ``ligne d'affichage'' fait référence à la ou les lignes sur l'écran d'affichage utilisées pour afficher une ligne de tampon. Le terme ``ligne actuelle'' fait référence à une ``ligne de tampon'' spécifique.

S'il y a des lignes d'affichage à l'écran pour lesquelles il n'y a pas de lignes de tampon correspondantes parce qu'elles correspondent à des lignes qui seraient après la fin du fichier, elles seront affichées comme un seul caractère <tilde> ('~'), plus la fin <nouvelle-ligne>.

La dernière ligne de l'écran sera utilisée pour signaler les erreurs ou afficher des messages d'information. Elle sera également utilisée pour afficher l'entrée des ``commandes orientées ligne'' (/, ?, : et !). Lorsqu'une commande orientée ligne est exécutée, l'éditeur entrera en mode de saisie de texte sur la dernière ligne de l'écran, en utilisant les caractères de commande respectifs comme caractères d'invite. (Dans le cas de la commande !, le mouvement associé sera saisi par l'utilisateur avant que l'éditeur n'entre en mode de saisie de texte.) La ligne saisie par l'utilisateur sera terminée par une <nouvelle-ligne>, un <retour-chariot> échappé par un <control>‐V, ou un <ESC> non échappé. Il n'est pas spécifié si plus de caractères que ne le nécessitent une largeur d'affichage moins un numéro de colonne d'écrans peuvent être saisis.

Si une commande est exécutée qui écrase une partie de l'écran autre que la dernière ligne de l'écran (par exemple, les commandes ex suspend ou !), autre que la commande ex shell, l'utilisateur sera invité à saisir un caractère avant que l'écran ne soit rafraîchi et que la session d'édition ne continue.

<tab> Les caractères <tab> occuperont le nombre de colonnes à l'écran défini par l'option d'édition tabstop (voir ex), sauf s'il y a moins de ce nombre de colonnes avant la marge d'affichage qui provoqueront le retour à la ligne de la ligne affichée ; dans ce cas, ils n'occuperont que le nombre de colonnes jusqu'à cette limite.

Le curseur sera placé sur la ligne actuelle et par rapport à la colonne actuelle, comme spécifié par chaque commande décrite dans les sections suivantes.

En mode ouvert, si la ligne actuelle n'est pas déjà affichée, elle sera alors affichée.

En mode visuel, si la ligne actuelle n'est pas affichée, les lignes qui sont affichées seront étendues, défilées ou redessinées pour afficher une partie non spécifiée de la ligne actuelle. Si l'écran est redessiné, pas plus que le nombre de lignes d'affichage spécifié par la valeur de l'option d'édition window ne sera affiché (sauf si la ligne actuelle ne peut pas être complètement affichée dans le nombre de lignes d'affichage spécifié par l'option d'édition window) et la ligne actuelle sera positionnée aussi près que possible du centre des lignes affichées (dans les contraintes imposées par la distance de la ligne par rapport au début ou à la fin du tampon d'édition). Si la ligne actuelle est avant la première ligne affichée et que l'écran est défilé, une partie non spécifiée de la ligne actuelle sera placée sur la première ligne de l'affichage. Si la ligne actuelle est après la dernière ligne affichée et que l'écran est défilé, une partie non spécifiée de la ligne actuelle sera placée sur la dernière ligne de l'affichage.

En mode visuel, si une ligne du tampon d'édition (autre que la ligne actuelle) ne rentre pas entièrement dans les lignes du bas de l'affichage qui sont disponibles pour sa présentation, l'éditeur peut choisir de ne pas afficher une partie de cette ligne. Les lignes de l'affichage qui ne contiennent pas de texte du tampon d'édition pour cette raison consisteront chacune en un seul caractère '@'.

En mode visuel, l'éditeur peut choisir, pour des raisons non spécifiées, de ne pas mettre à jour les lignes de l'affichage pour qu'elles correspondent au texte sous-jacent du tampon d'édition. Les lignes de l'affichage qui ne correspondent pas correctement au texte du tampon d'édition pour cette raison consisteront en un seul caractère '@' (plus la fin <nouvelle-ligne>), et la commande <control>‐R provoquera la mise à jour de l'écran par l'éditeur pour représenter correctement le tampon d'édition.

Les commandes en mode ouvert et visuel qui définissent la colonne actuelle la définissent sur une position de colonne dans l'affichage, et non une position de caractère dans le

ligne. Dans ce cas, cependant, la position de la colonne dans l'affichage sera calculée pour un affichage de largeur infinie ; par exemple, la colonne liée à un caractère qui fait partie d'une ligne qui a été repliée sur des lignes d'écran supplémentaires sera décalée par rapport à la colonne de la ligne d'affichage où commence la ligne du tampon, et non à partir du début d'une ligne d'affichage particulière.

La colonne du curseur d'affichage dans l'écran est basée sur la valeur de la colonne actuelle, comme suit, chaque règle étant appliquée successivement :

1.
Si la colonne actuelle est après la dernière colonne de ligne d'affichage utilisée par la ligne affichée, la colonne du curseur d'affichage sera définie sur la dernière colonne de ligne d'affichage occupée par le dernier caractère non <newline> de la ligne actuelle ; sinon, la colonne du curseur d'affichage sera définie sur la colonne actuelle.
2.
Si le caractère dont une partie est affichée dans la colonne de ligne d'affichage spécifiée par la colonne du curseur d'affichage nécessite plus d'une colonne d'affichage :
a.
Si en mode de saisie de texte, la colonne du curseur d'affichage sera ajustée à la première colonne de ligne d'affichage dans laquelle une partie de ce caractère est affichée.
b.
Sinon, la colonne du curseur d'affichage sera ajustée à la dernière colonne de ligne d'affichage dans laquelle une partie de ce caractère est affichée.

La colonne actuelle ne sera pas modifiée par ces ajustements de la colonne du curseur d'affichage.

Si une erreur se produit lors de l'analyse ou de l'exécution d'une commande vi :

*
Le terminal sera alerté. L'exécution de la commande vi s'arrêtera, et le curseur (par exemple, la ligne et la colonne actuelles) ne sera pas davantage modifié.
*
Sauf spécification contraire dans les sections de commande suivantes, il n'est pas spécifié si un message d'information sera affiché.
*
Toute commande vi partiellement saisie sera rejetée.
*
Si la commande vi est le résultat d'une expansion map, tous les caractères de cette expansion map seront rejetés, sauf spécification contraire par la commande map (voir ex).
*
Si la commande vi est le résultat de l'exécution d'un tampon, aucune commande supplémentaire causée par l'exécution du tampon ne sera exécutée.

Synopsis :
[count] <control>-D

Si la ligne actuelle est la dernière ligne du tampon d'édition, cela constituera une erreur.

Si aucun count n'est spécifié, count prendra par défaut la valeur count associée à la commande précédente <control>‐D ou <control>‐U. S'il n'y a pas eu de commande <control>‐D ou <control>‐U précédente, count prendra par défaut la valeur de l'option d'édition scroll.

Commandes en Mode d'Entrée en vi

En mode d'entrée de texte, la ligne courante consistera en zéro ou plus des catégories suivantes, plus le <newline> de terminaison :

1.
Caractères précédant le point d'entrée de l'entrée de texte

Les caractères de cette catégorie ne seront pas modifiés pendant le mode d'entrée de texte.

2.
Caractères autoindent

Les caractères autoindent seront automatiquement insérés dans chaque ligne créée en mode d'entrée de texte, soit suite à l'entrée d'un <newline> ou <carriage-return> en mode d'entrée de texte, soit en conséquence de la commande elle-même ; par exemple, O ou o (voir la commande ex autoindent), comme s'ils étaient entrés par l'utilisateur.

Il sera possible d'effacer les caractères autoindent avec la commande <control>‐D ; il n'est pas spécifié s'ils peuvent être effacés par les caractères <control>‐H, <control>‐U et <control>‐W. L'effacement d'un caractère autoindent transforme le glyphe en colonnes d'effacement et supprime le caractère du buffer d'édition, mais ne change pas sa représentation à l'écran.

3.
Caractères d'entrée de texte

Les caractères d'entrée de texte sont les caractères entrés par l'utilisateur. L'effacement de tout caractère d'entrée de texte transforme le glyphe en colonnes d'effacement et supprime le caractère du buffer d'édition, mais ne change pas sa représentation à l'écran.

Chaque caractère d'entrée de texte entré par l'utilisateur (qui n'a pas de signification spéciale) sera traité comme suit :

a.
Le caractère d'entrée de texte sera ajouté au dernier caractère du buffer d'édition à partir de la première, deuxième ou troisième catégorie.
b.
S'il n'y a pas de colonnes d'effacement à l'écran, la commande d'entrée de texte était la commande R, et des caractères de la cinquième catégorie de la ligne originale suivent le curseur, le caractère suivant sera supprimé du buffer d'édition. Si l'option d'édition slowopen n'est pas définie, le glyphe correspondant à l'écran deviendra des colonnes d'effacement.
c.
S'il y a des colonnes d'effacement à l'écran, autant de colonnes qu'elles occupent, ou autant que nécessaire, seront écrasées pour afficher le caractère d'entrée de texte. (Si seule une partie d'un glyphe multi-colonnes est écrasée, le reste restera à l'écran, et continuera d'être traité comme des colonnes d'effacement ; il n'est pas spécifié si le reste du glyphe est modifié d'une quelconque manière.)
d.
Si des colonnes d'affichage supplémentaires sont nécessaires pour afficher le caractère d'entrée de texte :
i.
Si l'option d'édition slowopen est définie, les caractères d'entrée de texte seront affichés dans les colonnes d'affichage suivantes, en écrasant tous les caractères affichés dans ces colonnes.
ii.
Sinon, tous les caractères actuellement affichés à partir de la colonne où le caractère d'entrée de texte doit être affiché, seront décalés du nombre de colonnes d'affichage nécessaire pour afficher le reste du caractère d'entrée de texte.
4.
Colonnes d'effacement

Les colonnes d'effacement ne font pas logiquement partie du buffer d'édition, n'apparaissent qu'à l'écran, et peuvent être écrasées à l'écran par des caractères d'entrée de texte ultérieurs. Lorsque le mode d'entrée de texte se termine, toutes les colonnes d'effacement n'apparaîtront plus à l'écran.

Les colonnes d'effacement sont initialement la région de texte spécifiée par la commande c (voir Changer) ; cependant, l'effacement des caractères autoindent ou d'entrée de texte provoque le traitement des glyphes des caractères effacés comme des colonnes d'effacement.

5.
Caractères suivant la région de texte pour la commande c, ou le point d'entrée de l'entrée de texte pour toutes les autres commandes

Les caractères de cette catégorie ne seront pas modifiés pendant le mode d'entrée de texte, sauf comme spécifié dans la catégorie 3.b. pour la commande d'entrée de texte R, ou comme caractères <espace> supprimés lorsqu'un <newline> ou <carriage-return> est entré.

Il n'est pas spécifié si c'est une erreur de tenter d'effacer avant le début d'une ligne créée par l'entrée d'un <newline> ou <carriage-return> pendant le mode d'entrée de texte. Si ce n'est pas une err

ou, l'éditeur se comportera comme si le caractère d'effacement avait été entré immédiatement après le dernier caractère d'entrée de texte entré sur la ligne précédente, et tous les caractères non-<newline> sur la ligne courante seront traités comme des colonnes d'effacement.

Lorsque le mode d'entrée de texte est entré, ou après qu'un caractère de mode d'entrée de texte a été entré (sauf spécification contraire pour les caractères spéciaux ci-dessous), le curseur sera positionné comme suit :

1.
Sur la première colonne qui affiche une partie de la première colonne d'effacement, si elle existe
2.
Sinon, si l'option d'édition slowopen est définie, sur la première colonne de ligne d'affichage après le dernier caractère des première, deuxième ou troisième catégories, si elle existe
3.
Sinon, la première colonne qui affiche une partie du premier caractère de la cinquième catégorie, si elle existe
4.
Sinon, la colonne de ligne d'affichage après le dernier caractère des première, deuxième ou troisième catégories, si elle existe
5.
Sinon, sur la position de colonne 1

Les caractères qui sont mis à jour à l'écran pendant le mode d'entrée de texte sont non spécifiés, autre que le fait que le dernier caractère d'entrée de texte sera toujours mis à jour, et, si l'option d'édition slowopen n'est pas définie, le caractère de curseur courant sera toujours mis à jour.

RATIONNEL

Voir le RATIONNEL de ex pour plus d'informations sur vi. De larges portions de la spécification de l'utilitaire vi renvoient à ex pour éviter une divergence involontaire. Bien que ex et vi aient historiquement été implémentés comme un seul utilitaire, ce n'est pas requis par POSIX.1‐2008.

Il est reconnu que certaines parties de vi seraient difficiles, voire impossibles, à implémenter de manière satisfaisante sur un terminal en mode bloc, ou un terminal sans aucune forme d'adressage de curseur, par conséquent, il n'est pas obligatoire que de telles fonctionnalités fonctionnent sur tous les terminaux. L'intention est cependant qu'une implémentation de vi fournisse l'ensemble complet des capacités sur tous les terminaux capables de les supporter.

Historiquement, vi se terminait immédiatement si l'entrée standard n'était pas un terminal. POSIX.1‐2008 autorise, mais n'exige pas, ce comportement. Une condition de fin de fichier n'est pas équivalente à un caractère de fin de fichier. Un caractère de fin de fichier courant, <control>‐D, est historiquement une commande de vi.

Le texte de la section STDOUT reflète l'utilisation du verbe display dans cette section ; certaines implémentations de vi utilisent la sortie standard pour écrire sur le terminal, mais POSIX.1‐2008 n'exige pas que ce soit le cas.

Historiquement, les implémentations revenaient en mode ouvert si le terminal était incapable de supporter le mode visuel complet. POSIX.1‐2008 exige ce comportement. Historiquement, le mode ouvert de vi se comportait à peu près de la même manière que le mode visuel, à la différence qu'une seule ligne du tampon d'édition (une « ligne de tampon ») était maintenue à jour à la fois. Cette ligne était normalement affichée sur l'avant-dernière ligne d'un terminal avec adressage de curseur (et la dernière ligne effectuait ses fonctions visuelles normales pour les commandes orientées ligne et les messages). De plus, quelques commandes se comportaient différemment en mode ouvert qu'en mode visuel. POSIX.1‐2008 exige la conformité à la pratique historique.

Historiquement, les implémentations de ex et vi s'attendaient à ce que le texte progresse dans l'ordre européen/latin habituel, de gauche à droite, de haut en bas. POSIX.1‐2008 n'exige pas que ce soit le cas. La spécification a été délibérément écrite avec des mots tels que « avant », « après », « premier » et « dernier » afin de permettre aux implémentations de supporter l'ordre naturel du texte de la langue.

Historiquement, les lignes au-delà de la fin du tampon d'édition étaient marquées avec des caractères <tilde> ('~') uniques ; c'est-à-dire, si l'affichage basé sur un, basé sur un, était de 20 lignes de long, et que la dernière ligne du fichier était sur la ligne un, alors les lignes 2 à 20 ne contenaient qu'un seul caractère '~'.

Historiquement, l'éditeur vi tentait d'afficher uniquement des lignes complètes en bas de l'écran (il affichait des lignes partielles en haut de l'écran). Si une ligne était trop longue pour tenir entièrement en bas de l'écran, les lignes d'écran où la ligne aurait été affichée étaient affichées comme des caractères '@' uniques, au lieu d'afficher une partie de la ligne. POSIX.1‐2008 autorise, mais n'exige pas, ce comportement. Il est recommandé aux implémentations de tenter toujours d'afficher une ligne complète en bas de l'écran lors du défilement ou du positionnement de l'écran par lignes de tampon.

Historiquement, les lignes marquées avec '@' étaient également utilisées pour minimiser les sorties vers les terminaux « dumb » sur des lignes lentes ; c'est-à-dire que les changements locaux au curseur étaient mis à jour, mais les changements apportés aux lignes de l'écran qui n'étaient pas proches du curseur étaient simplement marqués d'un signe '@' au lieu d'être mis à jour pour correspondre au texte actuel. POSIX.1‐2008 autorise, mais n'exige pas cette fonctionnalité car elle est de moins en moins utilisée à mesure que les terminaux deviennent plus intelligents et que les connexions sont plus rapides.

Descriptions de commandes dans vi

Les commandes de mouvement font partie des aspects les plus complexes de vi à décrire. À quelques exceptions près, l'effet d'une commande de mouvement sur une région de texte et le type de tampon d'une commande vi sont décrits au cas par cas. Les descriptions des régions de texte dans POSIX.1‐2008 ne visent pas à impliquer une direction ; c'est-à-dire qu'une région inclusive de la ligne n à la ligne n+5 est identique à une région de la ligne n+5 à la ligne n. Ceci présente plus qu'un intérêt académique : les mouvements vers des marques peuvent être effectués dans les deux sens, et si l'option wrapscan est activée, il en va de même pour les mouvements vers des points de recherche. Historiquement, les lignes sont toujours stockées dans les tampons dans l'ordre du texte ; c'est-à-dire, du début du tampon d'édition à la fin. POSIX.1‐2008 exige la conformité à la pratique historique.

Historiquement, les comptes de commandes étaient appliqués à tout mouvement associé, et étaient multiplicatifs à tout compte de mouvement fourni. Par exemple, 2cw est identique à c2w, et 2c3w est identique à c6w. POSIX.1‐2008 exige ce comportement. Historiquement, les commandes vi qui utilisaient les gros mots, mots, paragraphes et phrases comme objets traitaient les groupes de lignes vides, ou les lignes ne contenant que des caractères <espace>, de manière incohérente. Certaines commandes les traitaient comme une seule entité, tandis que d'autres traitaient chaque ligne séparément. Par exemple, les commandes w, W et B traitaient les groupes de lignes vides comme des mots individuels ; c'est-à-dire que la commande déplaçait le curseur vers chaque nouvelle ligne vide. Les commandes e et E traitaient les groupes de lignes vides comme un seul mot ; c'est-à-dire que la première utilisation passait après le groupe de lignes. La commande b faisait simplement biper l'utilisateur, ou si elle était exécutée depuis le début de la ligne comme commande de mouvement, échouait de manière inattendue. Si les lignes contenaient uniquement des caractères <espace> (ou se terminaient par ceux-ci), les commandes w et W faisaient simplement biper l'utilisateur, les commandes E et e traitaient le groupe comme un seul mot, et les commandes B et b traitaient les lignes comme des mots individuels. Pour la cohérence et la simplicité de spécification, POSIX.1‐2008 exige que toutes les commandes vi traitent les groupes de lignes vides ou blanches comme une seule entité, et que le mouvement à travers les lignes se terminant par des caractères <espace> soit cohérent avec les autres mouvements.

Historiquement, la documentation de vi indiquait que n'importe quel nombre de guillemets doubles était ignoré après les signes de ponctuation aux limites de phrase ; cependant, les implémentations n'ignoraient que les apostrophes. POSIX.1‐2008 exige que les deux soient ignorés.

Historiquement, les premiers et derniers caractères du tampon d'édition étaient des limites de mots. Cette pratique historique est requise par POSIX.1‐2008.

Historiquement, vi tentait de mettre à jour le nombre minimum de colonnes possible à l'écran, ce qui pouvait conduire à l'affichage d'informations trompeuses. POSIX.1‐2008 ne fait aucune exigence autre que le caractère en cours de saisie soit affiché correctement, laissant toutes les autres décisions dans ce domaine à la discrétion de l'implémentation.

Historiquement, les lignes étaient arbitrairement pliées entre des colonnes de n'importe quels caractères nécessitant plusieurs positions de colonne à l'écran, à l'exception des tabulations, qui s'arrêtaient à la marge droite. POSIX.1‐2008 autorise le premier cas et exige le second. Les implémentations qui ne plient pas arbitrairement les lignes entre des colonnes de caractères occupant plusieurs positions de colonne ne devraient pas permettre au curseur de se reposer sur une colonne qui ne contient aucune partie d'un caractère.

Le vi historique avait un problème dans le sens où tous les mouvements étaient basés sur les lignes du tampon, et non sur les lignes d'affichage ou d'écran. C'est souvent la bonne chose à faire ; par exemple, les mouvements d'une seule ligne, tels que j ou k, devraient fonctionner sur les lignes du tampon. Des commandes comme dj, ou j., où . est une commande de modification, n'ont de sens que pour les lignes du tampon. Ce n'est cependant pas la bonne chose à faire pour les mouvements d'écran ou les commandes de défilement comme <control>‐D, <control>‐F et H. Si la fenêtre est assez petite, utiliser les lignes du tampon dans ces cas peut entraîner des mouvements complètement aléatoires ; par exemple, 1<control>‐D peut entraîner un écran complètement modifié, sans aucun chevauchement. Ce n'est clairement pas ce que l'utilisateur voulait. Le problème est encore pire dans le cas des commandes H, L et M — comme elles positionnent le curseur sur le premier caractère non <espace> de la ligne, elles peuvent toutes faire référence au même emplacement dans de grandes lignes, et entraîneront aucun mouvement du tout.

De plus, si la ligne est plus grande que l'écran, l'utilisation des lignes du tampon peut rendre impossible l'affichage de parties de la ligne — il n'existe aucune commande qui n'affiche pas le début de la ligne dans le vi historique, et si le début et la fin de la ligne ne peuvent pas être simultanément à l'écran, l'utilisateur en pâtit. Enfin, les commandes de défilement de page et de demi-page se déplaçaient historiquement vers le premier caractère non <espace> de la nouvelle ligne. Si la ligne est approximativement de la même taille que l'écran, c'est insuffisant car le curseur avant et après une commande <control>‐D fera référence au même emplacement à l'écran.

Il existe des implémentations de ex et vi qui n'ont pas ces problèmes car les commandes pertinentes (<control>‐B, <control>‐D, <control>‐F, <control>‐U, <control>‐Y, <control>‐E, H, L et M) opèrent sur les lignes d'affichage (écran), et non sur les lignes (d'édition) du tampon.

POSIX.1‐2008 n'autorise pas ce comportement par défaut car les développeurs de la norme pensaient que les utilisateurs trouveraient cela trop déroutant. Cependant, la pratique historique a été assouplie. Par exemple, ex et vi tentaient historiquement, bien que parfois sans succès, de ne jamais mettre une partie d'une ligne sur les dernières lignes d'un écran ; par exemple, si une ligne ne rentrait pas en entier, aucune partie de la ligne n'était affichée, et les lignes d'écran correspondant à la ligne contenaient des caractères '@' uniques. Ce comportement est autorisé, mais pas requis par POSIX.1‐2008, de sorte qu'il est possible pour les implémentations de prendre en charge les longues lignes sur de petits écrans de manière plus raisonnable sans modifier les commandes pour qu'elles soient orientées vers l'affichage (au lieu d'être orientées vers le tampon). POSIX.1‐2008 autorise également les implémentations à refuser d'éditer tout tampon d'édition contenant une ligne qui ne rentre pas entièrement à l'écran.

La zone d'affichage (par exemple, la valeur de l'option d'édition window) a historiquement été "agrandie", ou étendue, pour afficher du nouveau texte lors de mouvements locaux effectués dans des affichages où le nombre de lignes affichées est inférieur au maximum possible. L'expansion a historiquement été le premier choix, lorsque la ligne cible était à moins de la valeur maximale d'expansion possible. Le défilement a historiquement été le choix suivant, effectué lorsque la ligne cible était à moins d'un demi-affichage, et sinon, l'écran était redessiné. Il y avait cependant des exceptions, car les commandes ex provoquaient généralement toujours le redessin de l'écran. POSIX.1‐2008 ne spécifie pas de comportement standard car il peut y avoir des problèmes externes, tels que la vitesse de connexion, le nombre de caractères nécessaires pour redessiner par opposition à faire défiler, ou les capacités du terminal que les implémentations devront accommoder.

La ligne actuelle dans POSIX.1‐2008 correspond un à un à une ligne du tampon dans le fichier. La colonne actuelle ne correspond pas. Il existe deux valeurs de colonne différentes décrites par POSIX.1‐2008. La première est la valeur de la colonne actuelle telle que définie par bon nombre des commandes vi. Cette valeur est mémorisée pendant toute la durée de vie de l'éditeur. La seconde valeur de colonne est la position réelle à l'écran où repose le curseur. Les deux ne sont pas toujours identiques. Par exemple, lorsque le curseur est en arrière d'un caractère multi-colonnes, la position réelle du curseur à l'écran a historiquement été la dernière colonne du caractère en mode commande, et la première colonne du caractère en mode saisie.

Les commandes qui définissent la ligne actuelle, mais qui ne définissent pas la valeur du curseur actuel (par exemple, j et k) tentent de se rapprocher au maximum de la position de colonne mémorisée, de sorte que le curseur tend à se restreindre à une colonne verticale lorsque l'utilisateur se déplace dans le tampon d'édition. POSIX.1‐2008 exige la conformité à la pratique historique, exigeant que l'emplacement d'affichage du curseur sur la ligne d'affichage soit ajusté à partir de la valeur de colonne actuelle si nécessaire pour prendre en charge ce comportement historique.

Historiquement, seule une seule ligne (et pour certains terminaux, une seule ligne moins 1 colonne) de caractères pouvait être entrée par l'utilisateur pour les commandes orientées ligne ; c'est-à-dire :, !, /, ou ?. POSIX.1‐2008 autorise, mais n'exige pas, cette limitation.

Historiquement, les "erreurs douces" dans vi provoquaient l'alerte du terminal, mais aucun message d'erreur n'était affiché. En règle générale, aucun message d'erreur n'était affiché pour les erreurs d'exécution de commande dans vi, lorsque l'erreur résultait de la tentative par l'utilisateur d'une action invalide ou impossible, ou lorsqu'un objet recherché n'était pas trouvé. Les erreurs douces comprenaient h en marge gauche, <control>‐B ou [[ au début du fichier, 2G à la fin du fichier, etc. De plus, des erreurs telles que %, ]], }, ), N, n, f, F, t et T ne trouvant pas l'objet recherché étaient également douces. Moins systématiquement, / et ? affichaient un message d'erreur si le motif n'était pas trouvé, /, ?, N et n affichaient un message d'erreur si aucune expression régulière précédente n'avait été spécifiée, et ; n'affichait pas de message d'erreur si aucune commande f, F, t ou T précédente n'avait eu lieu. En outre, le comportement dans ce domaine pourrait raisonnablement être basé sur une évaluation à l'exécution de la vitesse d'une connexion réseau. Enfin, certaines implémentations ont fourni des messages d'erreur pour les erreurs douces afin d'aider les utilisateurs novices, en fonction de la valeur d'une option d'édition verbose. POSIX.1‐2008 ne liste pas d'erreurs spécifiques pour lesquelles un message d'erreur doit être affiché. Les implémentations devraient se conformer à la pratique historique en l'absence de toute raison impérieuse de s'en écarter.

Page précédente

Les commandes <control>‐B et <control>‐F considéraient historiquement comme une erreur de tenter de passer avant le début ou après la fin du fichier, alors que les commandes <control>‐D et <control>‐U se déplaçaient simplement au début ou à la fin du fichier. Pour la cohérence, POSIX.1‐2008 exige le comportement de ce dernier pour les quatre commandes. Les quatre commandes continuent toujours

considérez-le comme une erreur si la ligne actuelle se trouve au début (<control>‐B, <control>‐U) ou à la fin (<control>‐F, <control>‐D) du fichier. Historiquement, les commandes <control>‐B et <control>‐F sautaient deux lignes afin d'inclure les lignes qui se chevauchent lorsqu'une seule commande était entrée. Cela a moins de sens en présence d'un nombre, car il n'y aura, par définition, aucune ligne qui se chevauche. Le calcul réel utilisé par les implémentations historiques de l'éditeur vi pour <control>‐B était :

((ligne de début actuelle) - nombre x (option d'édition de fenêtre)) +2

et pour <control>‐F était :

((ligne de début actuelle) + nombre x (option d'édition de fenêtre)) -2

Ce calcul ne fonctionne pas bien lors de l'interposition de commandes avec et sans nombres ; par exemple, 3<control>‐F n'est pas équivalent à entrer la commande <control>‐F trois fois, et n'est pas réversible en entrant la commande <control>‐B trois fois. Pour la cohérence avec d'autres commandes vi qui prennent des nombres, POSIX.1‐2008 exige un calcul différent.

Défilement avant

Les implémentations 4BSD et System V de vi différaient sur la valeur initiale utilisée par la commande scroll. 4BSD utilisait :

((option d'édition de fenêtre) +1) /2

tandis que System V utilisait la valeur de l'option d'édition scroll. La version System V est spécifiée par POSIX.1‐2008 car les développeurs de la norme pensaient qu'elle était plus intuitive et permettait à l'utilisateur une méthode de réglage de la valeur de défilement initialement sans régler également le nombre de lignes affichées.

Défilement avant par ligne

Historiquement, les commandes <control>‐E et <control>‐Y considéraient comme une erreur si les dernières et premières lignes, respectivement, étaient déjà à l'écran. POSIX.1‐2008 exige la conformité à la pratique historique. Historiquement, les commandes <control>‐E et <control>‐Y n'avaient aucun effet en mode ouvert. Pour la simplicité et la cohérence de la spécification, POSIX.1‐2008 exige qu'elles se comportent comme d'habitude, bien qu'avec un écran à une seule ligne.

Effacer et réafficher

La commande historique <control>‐L rafraîchissait l'écran exactement comme il était censé être actuellement affiché, remplaçant tout caractère '@' pour les lignes qui avaient été supprimées mais non mises à jour à l'écran par des caractères '@' rafraîchis. L'intention de la commande <control>‐L est de rafraîchir lorsque l'écran a été accidentellement écrasé ; par exemple, par une commande write d'un autre utilisateur, ou du bruit de modem.

Redessiner l'écran

La commande historique <control>‐R redessinait seulement quand c'était nécessaire pour mettre à jour les lignes qui avaient été supprimées mais non mises à jour à l'écran et qui étaient marquées par des caractères '@'. Il n'est pas exigé que l'écran soit rafraîchi d'une quelconque manière si aucune ligne de cette forme n'est actuellement affichée. POSIX.1‐2008 permet aux implémentations d'étendre cette commande pour rafraîchir les lignes à l'écran marquées par des caractères '@' parce qu'elles sont trop longues pour être affichées dans le cadre actuel ; cependant, la ligne et la colonne actuelles n'ont pas besoin d'être modifiées.

Rechercher une chaîne de marqueur

Historiquement, le premier caractère non-<espace> à ou après le curseur était le premier caractère, et tous les caractères subséquents qui étaient des caractères de mot, jusqu'à la fin de la ligne, étaient inclus. Par exemple, avec le curseur sur l'espace de début ou sur le caractère '#' dans le texte "#bar@", la marque était "#bar". Sur le caractère 'b' c'était "bar", et sur le 'a' c'était "ar". POSIX.1‐2008 exige ce comportement.

Remplacer le texte par les résultats d'une commande shell

Historiquement, les commandes <, >, et ! considéraient la plupart des mouvements de curseur autres que les mouvements orientés ligne comme une erreur ; par exemple, la commande >/foo<CR> réussissait, tandis que la commande >l échouait, même si la région de texte décrite par les deux commandes pouvait être identique. Pour la cohérence, les trois commandes ne considèrent que des lignes entières et non des lignes partielles, et la région est définie comme toute ligne contenant un caractère spécifié par le mouvement.

Se déplacer vers le caractère correspondant

D'autres caractères correspondants ont été laissés à la définition de l'implémentation afin de permettre des extensions telles que la correspondance de '<' et '>' pour la recherche HTML, ou #ifdef, #else, et #endif pour la recherche C.

Répéter la substitution

POSIX.1‐2008 exige que tous les indicateurs c et g spécifiés à la précédente commande de substitution soient ignorés ; cependant, l'indicateur r peut toujours s'appliquer, s'il est pris en charge par l'implémentation.

Retour au précédent (Contexte ou Section)

Les commandes [[, ]], (, ), {, et } sont toutes affectées par les ``limites de section'', mais dans certaines implémentations historiques, toutes les commandes ne reconnaissaient pas les mêmes limites de section. C'est un bug, pas une fonctionnalité, et un algorithme unique de limite de section n'a pas été décrit pour chaque commande. Un cas spécial qui est conservé est que la commande de phrase se déplace à la fin de la dernière ligne du tampon d'édition tandis que les autres commandes vont au début, afin de conserver les sémantiques traditionnelles de coupe de caractères de la commande de phrase. Historiquement, les limites de section de vi au début et à la fin du tampon d'édition étaient le premier caractère non-<espace> sur la première et la dernière ligne du tampon d'édition s'il en existait un ; sinon, le dernier caractère des première et dernière lignes du tampon d'édition s'il en existait un. Pour accroître la cohérence avec d'autres emplacements de section, cela a été simplifié par POSIX.1‐2008 au premier caractère des première et dernière lignes du tampon d'édition, ou aux première et dernière lignes du tampon d'édition si elles sont vides.

Les limites de phrases étaient problématiques dans le vi historique. Elles n'étaient pas seulement les limites telles que définies pour les commandes de section et de paragraphe, mais elles étaient également le premier caractère non-<espace> qui survenait après ces limites. Historiquement, les commandes de section de vi étaient documentées comme prenant une taille de fenêtre optionnelle comme nombre précédant la commande. Cela n'a pas été implémenté dans les versions historiques, donc POSIX.1‐2008 exige que le nombre répète la commande, pour la cohérence avec d'autres commandes vi.

Répéter

Historiquement, les commandes mappées autres que les commandes de saisie de texte ne pouvaient pas être répétées à l'aide de la commande point. POSIX.1‐2008 exige la conformité à la pratique historique.

Les restrictions sur l'interprétation des caractères spéciaux (par exemple, <control>‐H) dans la répétition des commandes en mode saisie de texte sont destinées à correspondre à la pratique historique. Par exemple, étant donné la séquence d'entrée :

iab<control>-H<control>-H<control>-Hdef<escape>

l'utilisateur devrait être informé d'une erreur lorsque la séquence est entrée pour la première fois, mais pas lors d'une répétition de commande. Le caractère <control>‐T est spécifiquement exempté de cette restriction. Les implémentations historiques de vi ignoraient les caractères <control>‐T qui étaient entrés dans la commande originale lors de la répétition de commande. POSIX.1‐2008 interdit ce comportement.

Rechercher une expression régulière

Historiquement, les commandes n'affectaient pas la ligne recherchée ou depuis si la commande de mouvement était une recherche (/, ?, N, n) et la position finale était le début/la fin de la ligne. Il y avait quelques cas spéciaux et vi n'était pas cohérent. POSIX.1‐2008 ne permet pas ce comportement, pour la cohérence. Les implémentations historiques permettaient mais ne pouvaient pas gérer les recherches comme des commandes de mouvement qui faisaient un retour (c'est-à-dire, en raison de l'option d'édition wrapscan) à l'emplacement d'origine. POSIX.1‐2008 exige que ce comportement soit traité comme une erreur.

Historiquement, la syntaxe "/RE/0" était utilisée pour forcer la commande à couper du texte en mode ligne. POSIX.1‐2008 exige la conformité à la pratique historique.

Historiquement, en mode ouvert, un z spécifié à une commande de recherche redessinait la ligne actuelle au lieu d'afficher l'écran actuel avec la ligne actuelle mise en évidence. Pour la cohérence et la simplicité de la spécification, POSIX.1‐2008 ne permet pas ce comportement.

Historiquement, les commandes z finales étaient permises et ignorées si elles étaient entrées dans le cadre d'une recherche utilisée comme commande de mouvement. Pour la cohérence et la simplicité de la spécification, POSIX.1‐2008 ne permet pas ce comportement.

Exécuter une commande ex

Historiquement, les implémentations de vi restreignaient les commandes qui pouvaient être entrées sur la ligne de commande deux-points (par exemple, append et change), et certaines autres commandes étaient connues pour provoquer des erreurs catastrophiques. Pour la cohérence, POSIX.1‐2008 ne permet pas ces restrictions. Lors de l'exécution d'une commande ex en entrant :, il n'est pas possible d'entrer un <newline> dans le cadre de la commande car il est considéré comme la fin de la commande. Une approche différente consiste à entrer en mode commande ex en utilisant la commande vi Q (et plus tard à reprendre le mode visuel avec la commande ex vi). En mode commande ex, la limitation à une seule ligne n'existe pas. Donc, par exemple, ce qui suit est valide :

Q
s/break here/break\
here/
vi

POSIX.1‐2008 exige que, si la commande ex écrase une partie de l'écran qui serait effacée par un rafraîchissement, vi pause pour attendre un caractère de l'utilisateur. Historiquement, ce caractère pouvait être n'importe quel caractère ; par exemple, un caractère entré par l'utilisateur avant l'apparition du message, ou même un caractère mappé. C'est probablement un bug, mais les implémentations qui ont essayé d'être plus rigoureuses en exigeant que l'utilisateur entre un caractère spécifique, ou que l'utilisateur entre un caractère après l'affichage du message, ont été forcées par l'indignation des utilisateurs à revenir au comportement historique. POSIX.1‐2008 exige la conformité à la pratique historique.

Décalage Gauche (Droite)

Se référer à la section Rationale pour les commandes ! et /. Historiquement, les commandes < et > déplaçaient parfois le curseur vers le premier caractère non-<espace> (par exemple si la commande était répétée ou avec _ comme commande de mouvement), et parfois le laissaient inchangé. POSIX.1‐2008 ne permet pas cette incohérence, exigeant plutôt que le curseur se déplace toujours vers le premier caractère non-<espace>. Historiquement, les commandes < et > ne supportaient pas les arguments de tampon, bien que certaines implémentations permettent la spécification d'un tampon optionnel. Ce comportement n'est ni requis ni interdit par POSIX.1‐2008.

Exécuter

Historiquement, les tampons pouvaient exécuter d'autres tampons, et des boucles, infinies ou non, étaient possibles. POSIX.1‐2008 exige la conformité à la pratique historique. La syntaxe *tampon de ex n'est pas requise dans vi, car ce n'est pas une pratique historique et a été utilisée dans certaines implémentations de vi pour supporter des langages de script supplémentaires.

Inverser la casse

Historiquement, la commande ~ ignorait tout compteur associé, et n'agissait que sur les caractères de la ligne courante. Pour la cohérence avec les autres commandes vi, POSIX.1‐2008 exige qu'un compteur associé agisse sur les compteur caractères suivants, et que la commande se déplace vers les lignes suivantes si justifié par le compteur, afin de permettre la modification de grands blocs de texte de manière raisonnablement efficace. Il existe des implémentations de vi qui exigent optionnellement une commande de mouvement associée pour la commande ~. Les implémentations supportant cette fonctionnalité sont encouragées à la baser sur l'option d'édition tildedop et à gérer les régions de texte et le positionnement du curseur de manière identique à la commande yank.

Ajouter

Historiquement, les compteurs spécifiés aux commandes A, a, I, et i répétaient l'entrée de la première ligne compteur fois, et ne répétaient pas les lignes suivantes du texte d'entrée. POSIX.1‐2008 exige que tout le texte entré soit répété compteur fois.

Reculer vers le mot précédent

Historiquement, vi devenait confus si les commandes de mot étaient utilisées comme commandes de mouvement dans des fichiers vides. POSIX.1‐2008 exige que ce soit une erreur. Les implémentations historiques de vi avaient un grand nombre de bugs dans les commandes de mouvement de mot, et elles variaient grandement en comportement en présence de lignes vides, de "mots" composés d'un seul caractère, et de lignes ne contenant que des caractères <espace>. Pour la cohérence et la simplicité de la spécification, POSIX.1‐2008 ne permet pas ce comportement.

Changer jusqu'à la fin de la ligne

Certaines implémentations historiques de la commande C ne se comportaient pas comme décrit par POSIX.1‐2008 lorsque la touche $ était remappée, car elles étaient implémentées en plaçant la touche $ dans la file d'attente d'entrée et en la retraitant. POSIX.1‐2008 ne permet pas ce comportement. Historiquement, les commandes C, S, et s ne copiaient pas le texte remplacé dans les tampons numériques. Pour la cohérence et la simplicité de la spécification, POSIX.1‐2008 exige qu'elles se comportent comme leurs commandes c respectives à tous égards.

Supprimer

Historiquement, les lignes en mode ouvert qui étaient supprimées étaient déroulées vers le haut, et un glyphe @ était écrit par-dessus le début de la ligne. Dans le cas de terminaux incapables des mouvements de curseur nécessaires, l'éditeur effaçait la ligne supprimée de l'écran. POSIX.1‐2008 exige la conformité à la pratique historique ; c'est-à-dire que si le terminal ne peut pas afficher le caractère '@', la ligne ne peut pas rester à l'écran.

Supprimer jusqu'à la fin de la ligne

Certaines implémentations historiques de la commande D ne se comportaient pas comme décrit par POSIX.1‐2008 lorsque la touche $ était remappée, car elles étaient implémentées en plaçant la touche $ dans la file d'attente d'entrée et en la retraitant. POSIX.1‐2008 ne permet pas ce comportement.

Joindre

Une bizarrerie historique de vi est que les commandes J, 1J, et 2J sont toutes équivalentes. POSIX.1‐2008 exige la conformité à la pratique historique. La commande J de vi est spécifiée en termes de la commande ex join avec une valeur de compteur de commande ex. La correction d'adresse pour un compteur qui est au-delà de la fin du tampon d'édition est nécessaire pour la compatibilité historique tant pour ex que pour vi.

Marquer la position

La pratique historique est que seules les lettres minuscules, plus la backquote et la quote simple, pouvaient être utilisées pour marquer une position de curseur. POSIX.1‐2008 exige la conformité à la pratique historique, mais encourage les implémentations à supporter également d'autres caractères comme marques.

Répéter la Recherche d'Expression Régulière (Avant et Arrière)

Historiquement, les commandes N et n ne pouvaient pas être utilisées comme composantes de mouvement pour la commande c. À l'exception de la commande cN, qui fonctionnait si la recherche traversait une limite de ligne, la région de texte était rejetée, et l'utilisateur n'était pas en mode d'entrée de texte. Pour la cohérence et la simplicité de la spécification, POSIX.1‐2008 ne permet pas ce comportement.

Insérer une Ligne Vide (En Dessous et Au Dessus)

Historiquement, les compteurs des commandes O et o étaient utilisés comme nombre de lignes physiques à ouvrir, si le terminal était basique et que l'option slowopen n'était pas définie. Ceci visait à minimiser le trafic sur les connexions lentes et le réaffichage pour les terminaux basiques. POSIX.1‐2008 ne permet pas ce comportement, exigeant qu'un compteur pour la commande open se comporte comme pour les autres commandes d'entrée de texte. Ce changement par rapport à la pratique historique a été fait pour la cohérence, et parce qu'un superset de la fonctionnalité est fourni par l'option d'édition slowopen.

Coller depuis le Tampon (Après et Avant)

Historiquement, les compteurs des commandes p et P étaient ignorés si le tampon était un tampon de mode ligne, mais étaient (principalement) implémentés comme décrit dans POSIX.1‐2008 si le tampon était un tampon de mode caractère. Parce qu'il existe des implémentations qui n'ont pas cette limitation, et parce que coller des lignes plusieurs fois est généralement utile, POSIX.1‐2008 exige que le compteur soit supporté pour toutes les commandes p et P.

Les implémentations historiques de vi étaient largement connues pour avoir des problèmes majeurs avec les commandes p et P, particulièrement lorsque des régions de texte inhabituelles étaient copiées dans le tampon d'édition. Les développeurs du standard considéraient ceux-ci comme des bugs, et ils ne sont pas autorisés pour la cohérence et la simplicité de la spécification.

Historiquement, une commande P ou p (ou une commande ex put exécutée depuis le mode ouvert ou visuel) exécutée dans un fichier vide, laissait une ligne vide comme première ligne du fichier. Pour la cohérence et la simplicité de la spécification, POSIX.1‐2008 ne permet pas ce comportement.

Remplacer le caractère

Historiquement, la commande r ne gérait pas correctement les caractères effacer et effacer mot comme arguments, ni ne gérait un compteur associé supérieur à 1 avec un argument de <retour chariot>, pour lequel elle remplaçait compteur caractères par un seul <nouvelle ligne>. POSIX.1‐2008 ne permet pas ces incohérences.

Historiquement, la commande r permettait l'échappement <contrôle>‐V des caractères saisis, tels que <ESC> et le <retour chariot>; cependant, elle nécessitait deux <contrôle>‐V en préfixe au lieu d'un. POSIX.1‐2008 exige que cela soit modifié pour la cohérence avec les autres commandes d'entrée de texte de vi.

Historiquement, il est une erreur d'entrer la commande r s'il y a moins de compteur caractères au niveau ou après le curseur dans la ligne. Bien qu'une extension raisonnable et non ambiguë serait de permettre la commande r sur des lignes vides, elle nécessiterait qu'un compteur trop grand soit ajusté pour correspondre au nombre de caractères au niveau ou après le curseur par cohérence, ce qui est suffisamment différent de la pratique historique pour être évité. POSIX.1‐2008 exige la conformité à la pratique historique.

Remplacer les caractères

Historiquement, s'il y avait des caractères autoindent dans la ligne sur laquelle la commande R était exécutée, et que autoindent était défini, le premier <nouvelle ligne> était correctement indenté et aucun caractère n'était remplacé par le <nouvelle ligne>. Chaque <nouvelle ligne> supplémentaire remplaçait n caractères, où n était le nombre de caractères nécessaires pour indenter le reste de la ligne au niveau d'indentation correct. Ce comportement est un bug et n'est pas permis par POSIX.1‐2008.

Annuler

La pratique historique pour le positionnement du curseur après l'annulation des commandes était mitigée. Dans la plupart des cas, lors de l'annulation de commandes qui affectaient une seule ligne, le curseur était déplacé au début du texte ajouté ou modifié, ou immédiatement après le texte supprimé. Cependant, si l'utilisateur s'était déplacé de la ligne en cours de modification, la colonne était soit définie sur le premier caractère non-<espace>, soit ramenée à l'origine de la commande, soit restait inchangée. Lors de l'annulation de commandes qui affectaient plusieurs lignes ou des lignes entières, le curseur était déplacé vers le premier caractère de la première ligne restaurée. À titre d'exemple de l'incohérence, une recherche, suivie d'une commande d'entrée de texte o, suivie d'une undo ramènerait le curseur à l'emplacement où la commande o a été entrée, mais une commande cw suivie d'une commande o suivie d'une undo ramènerait le curseur au premier caractère non-<espace> de la ligne. POSIX.1‐2008 exige le comportement le plus utile de ces comportements, et rejette le moins utile, dans l'intérêt de la cohérence et de la simplicité de la spécification.

Yank

Historiquement, la commande yank ne se déplaçait pas à la fin du mouvement si le mouvement était dans la direction avant. Elle se déplaçait à la fin du mouvement si le mouvement était dans la direction arrière, à l'exception de la commande _, ou des commandes G et ' lorsque la fin du mouvement était sur la ligne actuelle. Cela était encore compliqué par le fait que pour un certain nombre de commandes de mouvement, la commande yank déplaçait le curseur mais ne mettait pas à jour l'écran; par exemple, une commande ultérieure déplaçait le curseur à la fin du mouvement, même si le curseur à l'écran n'avait pas reflété le déplacement du curseur pour la commande yank. POSIX.1‐2008 exige que toutes les commandes yank associées aux mouvements arrière déplacent le curseur à la fin du mouvement pour assurer la cohérence, et spécifiquement, pour rendre les commandes ' comme mouvements cohérents avec les modèles de recherche comme mouvements.

Yank Ligne Actuelle

Certaines implémentations historiques de la commande Y ne se comportaient pas comme décrit par POSIX.1‐2008 lorsque la touche '_' était remappée car elles étaient implémentées en poussant la touche '_' dans la file d'attente d'entrée et en la retraîtant. POSIX.1‐2008 ne permet pas ce comportement.

Redessiner Fenêtre

Historiquement, la commande z redessinait toujours l'écran. Ceci est permis mais pas requis par POSIX.1‐2008, en raison de l'utilisation fréquente de la commande z dans des macros telles que map n nz. pour le positionnement de l'écran, plutôt que son utilisation pour changer la taille de l'écran. Les développeurs du standard pensaient que l'expansion ou le défilement de l'écran offraient une meilleure interface pour les utilisateurs. La capacité de redessiner l'écran est préservée si la nouvelle taille de fenêtre optionnelle est spécifiée, et dans les commandes <control>‐L et <control>‐R.

La sémantique de z^ est au mieux confuse. La pratique historique est que l'écran avant l'écran qui se terminait par la ligne spécifiée est affiché. POSIX.1‐2008 exige la conformité à la pratique historique.

Historiquement, la commande z n'affichait pas de ligne partielle en haut ou en bas de l'écran. Si la ligne partielle était normalement affichée en bas de l'écran, la commande fonctionnait, mais la ligne partielle était remplacée par des caractères '@'. Si la ligne partielle était normalement affichée en haut de l'écran, la commande échouait. Pour assurer la cohérence et la simplicité de la spécification, POSIX.1‐2008 ne permet pas ce comportement.

Historiquement, la commande z avec une spécification de ligne de 1 ignorait la commande. Pour assurer la cohérence et la simplicité de la spécification, POSIX.1‐2008 ne permet pas ce comportement.

Historiquement, la commande z ne positionnait pas la colonne du curseur sur le premier caractère non- si le premier écran devait être affiché et était déjà affiché. Pour assurer la cohérence et la simplicité de la spécification, POSIX.1‐2008 ne permet pas ce comportement.

Commandes du Mode d'Entrée dans vi

Les implémentations historiques de vi ne permettaient pas à l'utilisateur d'effacer plus d'une seule ligne d'entrée, ou d'utiliser les caractères d'effacement normaux tels que effacement de ligne, effacement de mot et effacement pour effacer les caractères autoindent. Comme il existe des implémentations de vi qui n'ont pas ces limitations, les deux comportements sont permis, mais seule la pratique historique est requise. Dans le cas de ces extensions, vi est requis de s'arrêter aux limites autoindent et à la ligne précédente.

Les implémentations historiques de vi mettaient à jour seulement la partie de l'écran où le caractère du curseur actuel était affiché. Par exemple, considérez les frappes d'entrée vi:

iabcd<escape>0C<tab>

Historiquement, la tabulation écrasait les caractères "abcd" lorsqu'elle était affichée. D'autres implémentations remplacent seulement le caractère 'a' par la tabulation, puis poussent le reste des caractères devant le curseur. Les deux implémentations ont des problèmes. L'implémentation historique est probablement plus agréable visuellement pour l'exemple ci-dessus; cependant, pour les frappes:

iabcd<ESC>0R<tab><ESC>

l'implémentation historique a pour résultat que la chaîne "bcd" disparaît puis réapparaît comme par magie lorsque le caractère <ESC> est entré. POSIX.1‐2008 exige le premier comportement lors de l'écrasement des colonnes d'effacement - c'est-à-dire, l'écrasement de caractères qui ne font plus logiquement partie du tampon d'édition - et le second comportement sinon.

Les implémentations historiques de vi jetaient les caractères <control>‐D et <control>‐T lorsqu'ils étaient entrés à des endroits où leur fonctionnalité de commande n'était pas appropriée. POSIX.1‐2008 exige que la fonctionnalité <control>‐T soit toujours disponible, et que <control>‐D soit traité comme n'importe quelle autre touche lorsqu'il n'opère pas sur des caractères autoindent.

NUL

Certaines implémentations historiques de vi limitaient le nombre de caractères entrés en utilisant le caractère d'entrée NUL à 256 octets. POSIX.1‐2008 permet cette limitation; cependant, les implémentations sont encouragées à supprimer cette limite.

<control>‐D

Voir également le Rationale pour la commande du mode d'entrée <newline>. Les hypothèses cachées dans la commande <control>‐D (et dans la spécification autoindent de vi en général) sont que les caractères <espace> occupent une seule colonne à l'écran et que les caractères <tab> sont composés d'un nombre entier de caractères <espace>.

<newline>

Les implémentations sont autorisées à réécrire les caractères autoindent dans la ligne lorsque <newline>, <carriage-return>, <control>‐D, et <control>‐T sont entrés, ou lorsque les commandes shift sont utilisées, car les implémentations historiques l'ont fait et ont trouvé nécessaire de le faire. Par exemple, un <control>‐D lorsque le curseur est précédé d'une seule tabulation, avec tabstop réglé sur 8, et shiftwidth réglé sur 3, entraînera le remplacement de la tabulation par plusieurs caractères <espace>.

<control>‐T

Voir également le Rationale pour la commande du mode d'entrée <newline>. Historiquement, <control>‐T fonctionnait seulement si aucun caractère non-espace n'avait encore été entré dans la ligne d'entrée actuelle. De plus, les caractères insérés par <control>‐T étaient traités comme des caractères autoindent, et ne pouvaient pas être effacés en utilisant les caractères d'effacement normaux de l'utilisateur. Comme il existe des implémentations qui n'ont pas ces limitations, et comme le déplacement vers une limite de colonne est généralement utile, POSIX.1‐2008 exige que les deux limitations soient supprimées.

<control>‐V

Historiquement, vi utilisait ^V, indépendamment de la valeur du caractère literal-next du terminal. POSIX.1‐2008 exige la conformité à la pratique historique.

Les utilisations décrites pour <control>‐V peuvent également être réalisées avec <control>‐Q, ce qui est utile sur les terminaux qui utilisent <control>‐V pour la fonction de flèche vers le bas. Cependant, la plupart des implémentations historiques utilisent <control>‐Q pour le caractère START de termios, donc l'éditeur ne recevra généralement pas <control>‐Q à moins que le mode stty ixon ne soit désactivé. (De plus, certaines implémentations historiques de vi activaient explicitement le mode ixon, il était donc difficile pour l'utilisateur de le désactiver.) N'importe lequel des caractères de commande décrits dans POSIX.1‐2008 peut être rendu inefficace par leur sélection comme caractères de contrôle termios, en utilisant l'utilitaire stty ou d'autres méthodes décrites dans le volume Interfaces Système de POSIX.1‐2017.

<ESC>

Historiquement, SIGINT alertait le terminal lorsqu'il était utilisé pour terminer le mode d'entrée. Ce comportement est permis, mais pas requis, par POSIX.1‐2008.
