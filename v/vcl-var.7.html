NOM

VCL-VARIABLES - L'album complet

DESCRIPTION

Ceci est une liste de toutes les variables du langage VCL.

Les noms des variables prennent la forme scope.variable[.index], par exemple :

req.url
beresp.http.date
client.ip

Les opérations possibles sur chaque variable sont décrites ci-dessous, souvent avec le raccourci "backend" qui couvre les sous-programmes vcl_backend_* {} et "client" qui couvre le reste, à l'exception de vcl_init {} et vcl_fini {}.

local, serveur, distant et client

Ces variables décrivent la connexion réseau entre le client et varnishd.

Sans protocole PROXY :

     client    serveur
     distant    local
       v          v
CLIENT ------------ VARNISHD

Avec protocole PROXY :

     client    serveur   distant     local
       v          v       v          v
CLIENT ------------ PROXY ------------ VARNISHD

client.identity

Type : STRING

Lisible depuis : client, backend

Écrivable depuis : client

Identification du client, utilisée pour l'équilibrage de charge dans le directeur client. Par défaut : client.ip

Cette variable peut être écrasée avec des informations plus précises, par exemple extraites d'un en-tête Cookie:.

client.ip

Type : IP

Lisible depuis : client, backend

L'adresse IP du client, soit la même que remote.ip, soit ce que le protocole PROXY nous a dit.

server.hostname

Type : STRING

Lisible depuis : tous

Le nom d'hôte du serveur, tel que retourné par la fonction système gethostname(3).

server.identity

Type : STRING

Lisible depuis : tous

L'identité du serveur, telle que définie par le paramètre -i.

Si un paramètre -i n'est pas passé à varnishd, la valeur de retour de la fonction système gethostname(3) sera utilisée.

server.ip

Type : IP

Lisible depuis : client, backend

L'adresse IP du socket sur lequel la connexion client a été reçue, soit la même que local.ip, soit ce que le protocole PROXY nous a dit.

remote.ip

Type : IP

Lisible depuis : client, backend

L'adresse IP de l'autre extrémité de la connexion TCP. Il peut s'agir de l'adresse IP du client ou de l'adresse IP sortante d'un serveur proxy.

Si la connexion est un socket de domaine UNIX, la valeur sera 0.0.0.0:0

local.endpoint VCL >= 4.1

Type : STRING

Lisible depuis : client, backend

L'adresse du socket '-a' sur lequel la session a été acceptée.

Si l'argument était -a foo=:81, ce serait ":81"

local.ip

Type : IP

Lisible depuis : client, backend

L'adresse IP (et le numéro de port) de l'extrémité locale de la connexion TCP, par exemple 192.168.1.1:81

Si la connexion est un socket de domaine UNIX, la valeur sera 0.0.0.0:0

local.socket VCL >= 4.1

Type : STRING

Lisible depuis : client, backend

Le nom du socket '-a' sur lequel la session a été acceptée.

Si l'argument était -a foo=:81, ce serait "foo".

Notez que tous les '-a' reçoivent un nom par défaut sous la forme a%d si aucun nom n'est fourni.

req et req_top

Ces variables décrivent la requête actuelle, et lorsque des requêtes ESI:include sont traitées, req_top pointe vers la requête reçue du client.

req

Type : HTTP

Lisible depuis : client

La structure entière des données HTTP de la requête. Principalement utile pour la passer aux VMODs.

req.backend_hint

Type : BACKEND

Lisible depuis : client

Écrivable depuis : client

Définit bereq.backend à cette valeur si nous tentons de récupérer. Lorsqu'elle est définie sur un directeur, la lecture de cette variable retourne un backend réel si le directeur a été résolu immédiatement, ou le directeur sinon. Lorsqu'elle est utilisée dans un contexte de chaîne de caractères, elle retourne le nom du directeur ou du backend, respectivement.

req.can_gzip

Type : BOOL

Lisible depuis : client

Vrai si le client a fourni gzip ou x-gzip dans l'en-tête Accept-Encoding.

req.esi VCL <= 4.0

Type : BOOL

Lisible depuis : client

Écrivable depuis : client

Défini à false pour désactiver le traitement ESI quel que soit la valeur dans beresp.do_esi. Par défaut : true. Cette variable est remplacée par resp.do_esi dans VCL 4.1.

req.esi_level

Type : INT

Lisible depuis : client

Un compteur indiquant le nombre de niveaux de requêtes ESI dans lesquels nous nous trouvons actuellement.

req.filters

Type : STRING

Lisible depuis : vcl_recv

Écrivable depuis : vcl_recv

Liste des filtres Varnish Fetch Processor (VFP) à travers lesquels le corps de la requête (req.body) sera tiré. L'ordre de gauche à droite signifie le traitement du client vers le cache, c'est-à-dire que le filtre le plus à gauche est exécuté en premier sur le corps tel que reçu du client après le décodage de tous les encodages de transfert.

Les filtres VFP modifient le corps avant qu'il ne soit potentiellement mis en cache (par exemple, en utilisant std.cache_req.body()) et/ou traité côté backend, où il peut être à nouveau traité par les filtres bereq.

Tenter de définir req.filters après le traitement du corps de la requête (encore une fois, par exemple avec std.cache_req.body()) déclenche une erreur VCL.

req.grace

Type : DURATION

Lisible depuis : client

Écrivable depuis : client

Non définissable depuis : client

Limite supérieure de la grâce de l'objet.

Lors de la recherche, le minimum de req.grace et la valeur de grâce stockée de l'objet seront utilisés comme grâce de l'objet.

Lors de la lecture de la valeur non définie, elle est retournée comme -1.

req.hash

Type : BLOB

Lisible depuis : vcl_hit, vcl_miss, vcl_pass, vcl_purge, vcl_deliver, vcl_synth, vcl_pipe

La clé de hachage de cette requête. Principalement utile pour la passer aux VMODs, mais peut également être utile pour le débogage de l'état hit/miss.

req.hash_always_miss

Type : BOOL

Lisible depuis : client

Écrivable depuis : client

Par défaut : false.

Force un cache miss pour cette requête, même si des objets correspondants parfaitement bons sont dans le cache.

Ceci est utile pour forcer la mise à jour du cache sans invalider les entrées existantes en cas d'échec de la récupération.

req.hash_ignore_busy

Type : BOOL

Lisible depuis : client

Écrivable depuis : client

Par défaut : false.

Ignore tout objet occupé pendant la recherche dans le cache.

Vous ne voudriez faire cela que lorsque vous avez deux serveurs recherchant du contenu mutuellement pour éviter les blocages.

req.hash_ignore_vary

Type : BOOL

Lisible depuis : client

Écrivable depuis : client

Par défaut : false.

req.http.*

Type: HEADER

Lisible depuis : client

Écrivable depuis : client

Non supprimable depuis : client

Les en-têtes de la requête, des choses comme req.http.date.

Les RFC autorisent plusieurs en-têtes portant le même nom, et à la fois set et unset supprimeront tous les en-têtes portant le nom donné.

Le nom d'en-tête * est un symbole VCL et en tant que tel ne peut pas, par exemple, commencer par un chiffre. Pour travailler avec des en-têtes valides qui ne peuvent pas être représentés comme des symboles VCL, il est possible de citer le nom, comme req.http."grammatically.valid". Aucun des en-têtes HTTP présents dans les registres IANA n'a besoin d'être cité, donc la syntaxe citée est découragée mais disponible pour l'interopérabilité.

Certains en-têtes qui ne peuvent pas être manipulés pour une récupération ou une livraison HTTP correcte sont en lecture seule.

bereq

Ceci est la requête que nous envoyons au backend, elle est construite à partir des champs req.* du client en filtrant les champs "per-hop" qui ne doivent pas être transmis (Connection:, Range: et similaires).

Un peu plus de champs sont autorisés pour les fetches pass que pour les fetches miss, par exemple ``Range.

beresp.filters

Type: STRING

Lisible depuis : vcl_backend_response

Écrivable depuis : vcl_backend_response

Liste des filtres Varnish Fetch Processor (VFP) à travers lesquels le corps de beresp sera traité. L'ordre de gauche à droite signifie le traitement du backend vers le cache, c'est-à-dire que le filtre le plus à gauche est exécuté en premier sur le corps tel que reçu du backend après décodage des éventuels encodages de transfert.

Les filtres VFP modifient le corps avant de le mettre dans le cache et/ou de le remettre au client, où il peut être à nouveau traité par resp.filters.

Les filtres VFP suivants existent dans varnish-cache :

  • gzip : compresse un corps en utilisant gzip
  • testgunzip : Teste si un corps est un gzip valide et le refuse sinon
  • gunzip : Décompresse le contenu gzip
  • esi : Traite le contenu texte brut ESI
  • esi_gzip : Sauvegarde les fragments gzippés pour un traitement ESI efficace

    Ce filtre permet d'assembler les ESI à partir de fragments individuellement gzippés, économisant ainsi de la puissance de traitement pour la recompression côté client au détriment d'une certaine efficacité de compression.

Des filtres VFP supplémentaires sont disponibles via les VMODs.

Par défaut, beresp.filters est construit comme suit :

  • gunzip est ajouté pour le contenu gzippé si beresp.do_gunzip ou beresp.do_esi sont vrais.
  • esi_gzip est ajouté si beresp.do_esi est vrai avec beresp.do_gzip ou si le contenu est déjà compressé.
  • esi est ajouté si beresp.do_esi est vrai
  • gzip est ajouté pour le contenu non compressé si beresp.do_gzip est vrai
  • testgunzip est ajouté pour le contenu compressé si beresp.do_gunzip est faux.

Après que beresp.filters a été défini, l'utilisation de l'un des commutateurs beresp.do_* mentionnés précédemment est une erreur VCL.

beresp.keep

Type: DURATION

Lisible depuis : vcl_backend_response, vcl_backend_error, vcl_backend_refresh

NOM

vcl.7 - Varnish Configuration Language

DESCRIPTION

This document is a reference manual for the Varnish Configuration Language (VCL). It details VCL syntax, semantics, and available objects and methods.

VCL is a domain-specific language for writing cache policies in Varnish Cache. It allows developers to define how Varnish should handle requests, interact with backends, and manage cached objects.

VCL syntax

VCL code is organized into subroutines (like C functions) that are called at specific points in Varnish's request processing lifecycle. Common subroutines include:

  • vcl_init: Called once when VCL is loaded. Used for initialization.
  • vcl_recv: Called upon receiving a client request. Used to decide whether to serve from cache, fetch from backend, or deny the request.
  • vcl_pipe: Called when a request is piped directly to the backend.
  • vcl_backend_fetch: Called to fetch an object from a backend.
  • vcl_backend_response: Called after receiving a response from a backend. Used to decide if the response should be cached.
  • vcl_backend_error: Called when a backend fetch fails.
  • vcl_deliver: Called before delivering a response to the client.
  • vcl_synth: Called to generate synthetic responses.
  • vcl_hit: Called when a cache hit occurs.
  • vcl_miss: Called when a cache miss occurs.
  • vcl_synth: Called when generating a synthetic response.
  • vcl_error: Called when an error occurs.

VCL uses a C-like syntax with support for variables, control structures (if, else, return), and expressions.

Champs d'en-tête protégés

Les en-têtes content-length et transfer-encoding sont en lecture seule. Ils doivent être préservés pour garantir la cohérence du framage HTTP/1 et maintenir une synchronisation correcte des requêtes et des réponses avec les clients et les backends.

Les VMODs peuvent toujours mettre à jour ces en-têtes lorsqu'il y a une raison de changer le framage, comme une transformation du corps d'une requête ou d'une réponse.

Statut de réponse HTTP

Un code d'état HTTP a 3 chiffres XYZ où X doit être compris entre 1 et 5 inclus. Comme il n'est pas rare de voir des clients ou des serveurs HTTP s'appuyer sur des codes d'état non standard ou même invalides, Varnish peut fonctionner avec n'importe quel statut entre 100 et 999.

Dans le code VCL, il est même possible d'utiliser des codes d'état sous la forme VWXYZ tant que la valeur globale est inférieure à 65536, mais seule la partie XYZ sera envoyée au client, moment où le X doit également devenir non nul.

La forme VWXYZ des codes d'état peut communiquer des informations supplémentaires dans resp.status et beresp.status pour return(synth(...)) et return(error(...)), afin d'indiquer quel contenu synthétique produire :

sub vcl_recv {
    if ([...]) {
        return synth(12404);
    }
}
sub vcl_synth {
    if (resp.status == 12404) {
        [...]       // ce 404 spécifique
    } else if (resp.status % 1000 == 404) {
        [...]       // tous les autres 404
    }
}

La variable obj.status héritera de la forme VWXYZ, mais dans une expression de bannière seule la partie XYZ sera disponible. La forme VWXYZ est strictement limitée à l'exécution VCL.

L'affectation d'un code standardisé HTTP à resp.status ou beresp.status définira également resp.reason ou beresp.reason au message de statut correspondant.

Gestion du 304

Pour une réponse 304, le code principal de Varnish modifie beresp avant d'appeler vcl_backend_response :

  • Si le statut gzip a changé, Content-Encoding est désactivé et tout Etag est affaibli.
  • Tous les en-têtes non présents dans la réponse 304 sont copiés de l'objet de cache existant. Content-Length est copié s'il est présent dans l'objet de cache existant et écarté sinon.
  • Le statut est défini à 200.

beresp.was_304 indique que ce traitement conditionnel de réponse a eu lieu.

Note : Les requêtes conditionnelles du backend sont indépendantes des requêtes conditionnelles du client, donc les clients peuvent recevoir des réponses 304, qu'une requête backend ait été conditionnelle ou non.

beresp.ttl / beresp.grace / beresp.keep

Avant d'appeler vcl_backend_response, le code principal définit beresp.ttl en fonction du statut de la réponse et des en-têtes de réponse Age, Cache-Control ou Expires et Date comme suit :

  • Si présent et valide, la valeur de l'en-tête Age est déduite de tous les calculs de ttl.
  • Pour les codes d'état 200, 203, 204, 300, 301, 304, 404, 410 et 414 :
  • Si Cache-Control contient un champ s-maxage ou max-age (dans cet ordre de préférence), le ttl est défini à la valeur respective non négative ou à 0 si négative.
  • Sinon, si aucun en-tête Expires n'existe, le ttl par défaut est utilisé.
  • Sinon, si Expires contient un horodatage antérieur à Date, le ttl est défini à 0.
  • Sinon, si aucun en-tête Date n'est présent ou si l'horodatage de l'en-tête Date diffère de l'horloge locale de plus du paramètre clock_skew, le ttl est défini à
  • 0 si Expires indique un horodatage passé ou
  • la différence entre l'horloge locale et l'en-tête Expires sinon.
•
Sinon, le ttl est défini à la différence entre Expires et Date.
  • Pour les codes d'état 302 et 307, le calcul est identique sauf que le ttl par défaut n'est pas utilisé et -1 est retourné si ni Cache-Control ni Expires n'existe.
  • Pour tous les autres codes d'état, ttl -1 est retourné.

beresp.grace prend par défaut la valeur du paramètre default_grace.

Pour un ttl non négatif, si Cache-Control contient une valeur de champ stale-while-revalidate, beresp.grace est défini à cette valeur si non négative ou à 0 sinon.

beresp.keep prend par défaut la valeur du paramètre default_keep.
