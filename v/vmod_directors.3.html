DESCRIPTION

vmod_directors permet l'équilibrage de charge des backends dans Varnish.

Le module implémente des techniques d'équilibrage de charge, et sert également d'exemple sur la façon dont on pourrait étendre les capacités d'équilibrage de charge de Varnish.

Pour activer l'équilibrage de charge, vous devez importer ce vmod (directors).

Ensuite, vous définissez vos backends. Une fois les backends déclarés, vous pouvez les ajouter à un directeur. Cela se fait dans le code VCL exécuté. Si vous souhaitez émuler le comportement précédent de Varnish 3.0, vous pouvez simplement initialiser les directeurs dans vcl_init{}, comme ceci :

sub vcl_init {
    new vdir = directors.round_robin();
    vdir.add_backend(backend1);
    vdir.add_backend(backend2);
}

Comme vous pouvez le voir, rien ne vous empêche de manipuler les directeurs ailleurs dans VCL. Ainsi, vous pourriez avoir du code VCL qui ajouterait plus de backends à un directeur lorsqu'une URL spécifique est appelée.

Notez que les directeurs peuvent utiliser d'autres directeurs comme backends.

new xround_robin = directors.round_robin()

Ce directeur choisira les backends en mode round robin.

Exemple :

new vdir = directors.round_robin();

new xfallback = directors.fallback(BOOL sticky=0)

Crée un directeur de repli.

Un directeur de repli essaiera chacun des backends ajoutés en tournée, et retournera le premier qui est sain.

Si sticky est défini sur true, le directeur continuera d'utiliser le backend sain, même si un backend de priorité supérieure devient disponible. Une fois que la liste entière des backends est épuisée, il recommencera depuis le début.

Exemple :

new vdir = directors.fallback();

Crée un directeur de backend aléatoire.

Le directeur distribue la charge sur les backends en utilisant une distribution de probabilité aléatoire pondérée.

Le générateur aléatoire "testable" dans varnishd est utilisé, ce qui permet d'exécuter des tests déterministes (Voir : d00004.vtc).

Exemple :

new vdir = directors.random();

VOID xrandom.add_backend(BACKEND, REAL)

Ajoute un backend au directeur avec un poids donné.

Chaque backend recevra approximativement 100 * (poids / (somme(tous_les_poids_ajoutés))) pour cent du trafic envoyé à ce directeur.

Exemple :

# 2/3 vers backend1, 1/3 vers backend2.
vdir.add_backend(backend1, 10.0);
vdir.add_backend(backend2, 5.0);

Crée un directeur de partitionnement (shard director).

Introduction

Le directeur de partitionnement sélectionne les backends par une clé, qui peut être fournie directement ou dérivée de chaînes. Pour la même clé, le directeur de partitionnement retournera toujours le même backend, à moins que la configuration du backend ou son état de santé ne change. Inversement, pour des clés différentes, le directeur de partitionnement choisira probablement des backends différents. Dans la configuration par défaut, les backends non sains ne sont pas sélectionnés.

Le directeur de partitionnement ressemble au directeur de hachage, mais son avantage principal est que, lorsque la configuration des backends ou leurs états de santé changent, l'association des clés aux backends reste aussi stable que possible.

De plus, les fonctionnalités de montée en charge progressive (rampup) et de pré-chauffage (warmup) peuvent aider à améliorer davantage les temps de réponse perçus par l'utilisateur.

Partitionnement (Sharding)

Cette technique de base permet de nombreuses applications comme l'optimisation de l'efficacité du cache des serveurs backend, le clustering Varnish ou la persistance des sessions vers les serveurs sans conserver d'état, et, en particulier, sans nécessiter de synchroniser l'état entre les nœuds d'un cluster de serveurs Varnish :

  • De nombreuses applications utilisent des caches pour des objets de données, donc, dans un cluster de serveurs d'applications, demander des objets similaires au même serveur peut aider à optimiser l'efficacité de tels caches.

    Par exemple, le partitionnement par URL ou par un composant id de l'URL a montré une amélioration drastique de l'efficacité de nombreux systèmes de gestion de contenu.

  • Comme cas spécial de l'exemple précédent, dans les clusters de serveurs Varnish sans logique de distribution de requêtes supplémentaire, chaque cache devra stocker tous les objets "chauds", donc la taille effective du cache est approximativement la plus petite taille de cache de n'importe quel serveur du cluster.

    Le partitionnement permet de séparer les objets au sein du cluster de telle sorte que chaque objet ne soit mis en cache que sur un des serveurs (ou sur un primaire et un secondaire, sur un primaire pour une longue durée et d'autres pour une courte durée, etc...). Efficacement, cela mènera à une taille de cache de l'ordre de la somme de tous les caches individuels, avec le potentiel d'augmenter drastiquement l'efficacité (mise à l'échelle par le nombre de serveurs).

  • Une autre application est l'implémentation de la persistance des requêtes backend, de telle sorte que toutes les requêtes partageant un certain critère (tel qu'une adresse IP ou un identifiant de session) soient transférées vers le même serveur backend.

Lorsqu'il est utilisé avec des clusters de serveurs Varnish, le directeur de partitionnement, s'il est configuré de manière identique par ailleurs, prendra la même décision sur tous les serveurs. En d'autres termes, les requêtes partageant un critère commun utilisé comme clé de partitionnement seront équilibrées sur le(s) même(s) serveur(s) backend, quel que soit le serveur Varnish qui traite la requête.

Les inconvénients sont :

  • la distribution des requêtes dépend du nombre de requêtes par clé et de l'uniformité de la distribution des valeurs de clés. En bref, bien que cette technique puisse conduire à une efficacité globale bien meilleure, elle peut aussi conduire à un moins bon équilibrage de charge dans des cas spécifiques.
  • Lorsqu'un serveur backend devient indisponible, toute technique de persistance doit re-sélectionner un nouveau serveur backend, mais cette technique reviendra également au serveur préféré une fois qu'il sera de nouveau sain. Ainsi, lorsqu'elle est utilisée pour la persistance, elle est généralement moins stable par rapport aux techniques avec état (qui continueraient à utiliser un serveur sélectionné aussi longtemps que possible (ou dicté par un TTL)).

Méthode

Lorsque xshard.reconfigure() est appelé explicitement (ou implicitement à la fin de toute tâche contenant des reconfigurations comme xshard.add_backend()), une structure de données circulaire de hachage cohérent est construite à partir des 32 derniers bits des valeurs de hachage SHA256 de <ident><n> (ident par défaut étant le nom du backend) pour chaque backend et pour un nombre séquentiel n de 1 à l'argument replicas de xshard.reconfigure(). Le hachage crée l'ordre apparemment aléatoire pour le placement des backends sur le cercle de hachage cohérent. Lorsque xshard.add_backend() a été appelé avec un argument weight, replicas est mis à l'échelle par ce poids pour ajouter proportionnellement plus de copies de ce backend sur le cercle.

Lorsque xshard.backend() est appelé, une clé d'équilibrage de charge est générée, sauf si elle est fournie. La plus petite valeur de hachage sur le cercle qui est supérieure à la clé est recherchée (en cherchant dans le sens des aiguilles d'une montre et en revenant au début si nécessaire). Le backend pour cette valeur de hachage est le backend préféré pour la clé donnée.

Si un backend sain est demandé, la recherche se poursuit linéairement sur le cercle tant que les backends trouvés sont non sains ou que tous les backends ont été vérifiés. L'ordre de ces "backends alternatifs" sur le cercle est susceptible de différer pour différentes clés. Des backends alternatifs peuvent également être sélectionnés explicitement.

Signalement d'erreurs

Les méthodes échouées doivent signaler les erreurs à VSL avec la balise Error, donc lors de la configuration du directeur de partitionnement, il est conseillé de vérifier :

varnishlog -I Error:^vmod_directors.shard

Des informations supplémentaires peuvent être fournies sous forme de Notices, qui peuvent être vérifiées à l'aide de

varnishlog -I Notice:^vmod_directors.shard

VOID xshard.set_warmup(REAL probability=0.0)

Définit la probabilité de pré-chauffage par défaut. Voir le paramètre warmup de xshard.backend(). Si probability est 0.0 (par défaut), le pré-chauffage est désactivé.

VOID xshard.set_rampup(DURATION duration=0)

Définit la durée de montée en charge progressive par défaut. Voir le paramètre rampup de xshard.backend(). Si duration est 0 (par défaut), la montée en charge progressive est désactivée.

VOID xshard.associate(BLOB param=0)

Associe un objet directors.shard_param() par défaut ou efface une association.

La valeur de l'argument param doit être un appel à la méthode xshard_param.use(). Aucun argument n'efface l'association.

L'association peut être modifiée par requête backend en utilisant l'argument param de xshard.backend().

BOOL xshard.add_backend(BACKEND backend, [STRING ident], [DURATION rampup], [REAL weight])

BOOL xshard.add_backend(
      BACKEND backend,
      [STRING ident],
      [DURATION rampup],
      [REAL weight]
)

Ajoute un backend backend au directeur.

ident : Spécifie optionnellement une chaîne d'identification pour ce backend, qui sera hachée par xshard.reconfigure() pour construire le cercle de hachage cohérent. La chaîne d'identification est par défaut le nom du backend.

ident permet d'ajouter plusieurs instances du même backend.

rampup : Spécifie optionnellement une durée de montée en charge progressive spécifique pour ce backend. Sinon, la durée de montée en charge progressive par directeur est utilisée (voir xshard.set_rampup()).

weight : Spécifie optionnellement un poids pour mettre à l'échelle le paramètre replicas de xshard.reconfigure(). Le weight est limité à au moins 1. Les valeurs supérieures à 10 n'ont probablement pas beaucoup de sens. L'effet du weight est également plafonné de telle sorte que le nombre total de répliques ne dépasse pas UINT32_MAX.

Recherche un backend sur l'anneau de hachage cohérent.

Cette documentation utilise la notion d'ordre des backends pour une clé de shard particulière. Cet ordre est déterministe mais apparemment aléatoire tel que déterminé par l'algorithme de hachage cohérent et est susceptible de différer pour différentes clés, en fonction du nombre de backends et du nombre de répliques. En particulier, l'ordre des backends mentionné ici n'est *pas* l'ordre donné lors de l'ajout des backends.

•
par comment déterminer la clé de sharding
•
HASH :
  • lorsqu'appelé dans un contexte de backend et dans vcl_pipe {} : Utiliser la valeur de hachage varnish définie par vcl_hash{}
  • lorsqu'appelé dans un contexte client autre que vcl_pipe {} : hacher req.url
  • URL : hacher req.url / bereq.url
  • KEY : utiliser l'argument clé
  • BLOB : utiliser l'argument clé_blob
  • clé clé de recherche avec par=KEY

    la méthode xshard.key() peut être utile pour générer une clé de sharding à partir de chaînes personnalisées.

  • clé_blob clé de recherche avec par=BLOB

    Actuellement, cela utilise les 4 premiers octets du blob fourni en ordre d'octets réseau (big endian), remplis de zéros à gauche pour les blobs de moins de 4 octets.

  • alt sélection de backend alternative

    Sélectionner le alt-ième backend alternatif pour la clé donnée.

    Ceci est particulièrement utile pour les tentatives / redémarrages en raison d'erreurs de backend : en définissant alt=req.restarts ou alt=bereq.retries avec healthy=ALL, un autre serveur est sélectionné.

    Les fonctionnalités rampup et warmup ne sont actives que pour alt==0

  • rampup démarrage lent pour les serveurs qui viennent d'être en bonne santé

    Si alt==0 et que le backend choisi est dans sa période de rampup, avec une probabilité proportionnelle à la fraction de temps depuis que le backup est devenu sain jusqu'à la période de rampup, retourner le backend alternatif suivant, sauf si celui-ci est également dans sa période de rampup.

    L'intervalle de rampup par défaut peut être défini par directeur de shard en utilisant la méthode xshard.set_rampup() ou spécifiquement par backend avec la méthode xshard.add_backend().

  • warmup sélection probabiliste de serveur alternatif

    valeurs possibles : -1, 0..1

    -1 : utiliser la probabilité de warmup de la définition du directeur

    Utilisé uniquement pour alt==0 : Définit le ratio de requêtes (0,0 à 1,0) qui va vers le backend alternatif suivant pour le chauffer lorsque le backend préféré est sain. Non actif si le backend préféré ou alternatif est en rampup.

    warmup=0.5 est un moyen pratique de répartir la charge pour chaque clé sur deux backends dans des conditions de fonctionnement normales.

  • healthy
  • CHOSEN : Retourner un backend sain si possible.

    Pour alt==0, retourner le premier backend sain ou aucun.

    Pour alt > 0, ignorer l'état de santé des backends sautés pour la sélection de backend alternatif, puis retourner le backend sain suivant. Si celui-ci n'existe pas, retourner le dernier backend sain parmi ceux qui ont été sautés ou aucun.

  • IGNORE : Ignorer complètement l'état de santé du backend

    Retourner simplement le premier ou le alt-ième backend alternatif, en ignorant l'état de santé, rampup et warmup.

  • ALL : Vérifier également l'état de santé pour la sélection de backend alternatif

    Pour alt > 0, retourner le alt-ième backend alternatif de tous les backends sains, le dernier backend sain trouvé ou aucun.

resolve

défaut : LAZY dans vcl_init{}, NOW sinon

  • NOW : rechercher un backend et le retourner.

    Ne peut pas être utilisé dans vcl_init{}.

  • LAZY : retourner une instance de ce directeur pour une résolution ultérieure du backend.

    Le mode LAZY est requis pour référencer des instances de directeurs de shard, par exemple comme backends pour d'autres directeurs (couches de directeurs).

    Dans vcl_init{} et côté client, le mode LAZY ne peut pas être utilisé avec d'autres arguments.

    Côté backend et dans vcl_pipe {}, les paramètres des arguments ou un ensemble de paramètres associé affectent l'instance du directeur de shard pour la requête backend, indépendamment de l'endroit où elle est référencée.

•
param

Utiliser ou associer un ensemble de paramètres. La valeur de l'argument param doit être un appel à la méthode xshard_param.use().

défaut : tel que défini par xshard.associate() ou non défini.

  • pour resolve=NOW, prendre les paramètres par défaut de l'ensemble de paramètres directors.shard_param()
  • pour resolve=LAZY, associer l'ensemble de paramètres directors.shard_param() pour cette requête backend

    Notes d'implémentation pour l'utilisation d'ensembles de paramètres avec resolve=LAZY :

  • Un argument param reste associé et toute modification de l'ensemble de paramètres associé affecte la décision de sharding une fois que le directeur se résout en un backend réel.
  • Si d'autres arguments de paramètre sont également donnés, ils ont la priorité et sont conservés même si l'ensemble de paramètres donné par l'argument param est modifié ultérieurement dans la même requête backend.
  • Chaque appel à xshard.backend() remplace l'appel précédent.

VOID xshard.debug(INT)

intentionnellement non documenté

new xshard_param = directors.shard_param()

Crée un ensemble de paramètres de shard.

Un ensemble de paramètres permet la réutilisation des arguments de xshard.backend() sur de nombreuses instances de directeurs de shard et simplifie les cas d'utilisation avancés (par exemple, un directeur de shard avec des paramètres personnalisés superposés à d'autres directeurs).

Les ensembles de paramètres ont deux portées :

  • portée par VCL définie dans vcl_init{}
  • portée par requête backend

La portée par VCL définit les valeurs par défaut pour la portée par backend. Toute modification d'un ensemble de paramètres dans un contexte de backend et dans vcl_pipe {} n'affecte que la requête backend respective.

Les ensembles de paramètres ne peuvent pas être utilisés dans un contexte client, à l'exception de vcl_pipe {}.

L'exemple suivant est un cas d'utilisation typique : un ensemble de paramètres est associé à plusieurs directeurs. Le choix du directeur se fait côté client et les paramètres sont modifiés côté backend pour implémenter des tentatives sur des backends alternatifs :

sub vcl_init {
  new shard_param = directors.shard_param();
  new dir_A = directors.shard();
  dir_A.add_backend(...);
  dir_A.reconfigure();
  dir_A.associate(shard_param.use()); # <-- !
  new dir_B = directors.shard();
  dir_B.add_backend(...);
  dir_B.reconfigure();
  dir_B.associate(shard_param.use()); # <-- !
}
sub vcl_recv {
  if (...) {
    set req.backend_hint = dir_A.backend(resolve=LAZY);
  } else {
    set req.backend_hint = dir_B.backend(resolve=LAZY);
  }
}
sub vcl_backend_fetch {
  # modifie le comportement de dir_A et dir_B
  shard_param.set(alt=bereq.retries, par=URL);
}

Réinitialise l'ensemble de paramètres aux valeurs par défaut, comme documenté pour xshard.backend().

  • dans vcl_init{}, réinitialise la valeur par défaut de l'ensemble de paramètres pour cette VCL
  • dans le contexte backend et dans vcl_pipe {}, réinitialise l'ensemble de paramètres pour cette requête backend aux valeurs par défaut de la VCL

Restreint à : vcl_pipe, backend, housekeeping.

NAME

vmod_directors - VCL directors module

SYNOPSIS

director   [arguments...]

directors.

Methods:

    xshard_param.set(...)
    xshard_param.get_by()
    xshard_param.get_key()
    xshard_param.get_alt()
    xshard_param.get_warmup()
    xshard_param.get_rampup()
    xshard_param.get_healthy()
    xshard_param.use()
    BACKEND.lookup(STRING)

DESCRIPTION

This module provides a set of VCL directors that can be used to distribute requests among a pool of backends. The directors are:

  • shard: Selects a backend based on a hash of a given key.
  • round_robin: Selects backends in a round-robin fashion.
  • random: Selects backends randomly.
  • client: Selects backends based on a hash of the client IP address.
  • fail: A director that always returns a failure.
  • fixed: Selects a single, fixed backend.
  • fallback: Selects a backend, and if it fails, selects another backend.
  • set: A composite director that combines multiple directors.
