VARNISHNCSA(1) Manuel des commandes générales VARNISHNCSA(1)

NOM

varnishncsa - Affiche les journaux Varnish au format combiné des journaux Apache / NCSA

SYNTAXE

varnishncsa [-a] [-b] [-c] [-C] [-d] [-D] [-E] [-F <format>] [-f <fichier_format>] [-g <requête|vxid>] [-h] [-j] [-k <num>] [-L <limite>] [-n <répertoire_travail>] [-P <fichier>] [-Q <fichier>] [-q <requête>] [-r <nom_fichier>] [-R <limite[/durée]>] [-t <secondes|off>] [-V] [-w <nom_fichier>]

DESCRIPTION

L'utilitaire varnishncsa lit les journaux de mémoire partagée de varnishd(1) et les présente au format combiné des journaux Apache / NCSA.

Chaque ligne de journal générée est basée sur une seule transaction de type Requête collectée à partir du journal de mémoire partagée. La transaction Requête est ensuite analysée pour en extraire les parties pertinentes afin de produire une ligne de journal. Pour filtrer les lignes de journal générées, utilisez le langage de requête pour sélectionner les transactions applicables. Les transactions non-requêtes sont ignorées.

Les options suivantes sont disponibles :

-a
Lors de l'écriture de la sortie dans un fichier, ajoutez à la fin du fichier plutôt que de l'écraser. Cette option n'a aucun effet sans l'option -w.
-b
Journalise les requêtes vers le backend. Si -c n'est pas spécifié, seules les requêtes vers le backend déclencheront des lignes de journal.
-c
Journalise les requêtes du client. C'est le comportement par défaut. Si -b est spécifié, alors -c est nécessaire pour journaliser également les requêtes du client.
-C
Effectue toutes les correspondances d'expressions régulières et de chaînes sans tenir compte de la casse.
-d
Traite les enregistrements de journal au début du journal et quitte.
-D
Se détache du terminal (daemonize).
-E
Affiche les requêtes ESI, implique le mode client.
-F <format>
Définit la chaîne de format du journal de sortie.
-f <fichier_format>
Lit le format de sortie à partir d'un fichier. Lira une seule ligne du fichier spécifié et utilisera cette ligne comme format.
-g <requête|vxid>
Le regroupement des enregistrements de journal. Par défaut, le regroupement se fait par vxid.
-h
Affiche l'aide du programme et quitte.
-j
Rend les remplacements de spécificateurs de format compatibles JSON. Lors de l'échappement des caractères, utilise des séquences d'échappement de type \uXXXX (style JSON) au lieu de séquences \xXX (style C). Les chaînes vides seront remplacées par "" au lieu de "-", et les entiers vides seront remplacés par null. Utilisez -F ou -f en combinaison avec -j pour écrire des journaux JSON.
-k <num>
Traite ce nombre de transactions de journal correspondantes avant de quitter.
-L <limite>
Définit la limite supérieure des transactions incomplètes conservées avant que la transaction la plus ancienne ne soit forcée à se terminer. Un enregistrement d'avertissement est synthétisé lorsque cela se produit. Ce réglage maintient une limite supérieure à l'utilisation de la mémoire des requêtes en cours d'exécution. La valeur par défaut est 1000 transactions.
-n <répertoire_travail>
Spécifie le répertoire de travail de l'instance varnish à laquelle se connecter. Voir la documentation de l'option -n de varnishd(1) pour des informations supplémentaires et les valeurs par défaut.
-P <fichier>
Écrit le PID du processus dans le fichier spécifié.
-Q <fichier>
Spécifie le fichier contenant la requête VSL à utiliser. Lorsque plusieurs options -Q ou -q sont spécifiées, toutes les requêtes sont considérées comme si l'opérateur 'ou' avait été utilisé pour les combiner.
-q <requête>
Spécifie la requête VSL à utiliser. Lorsque plusieurs options -q ou -Q sont spécifiées, toutes les requêtes sont considérées comme si l'opérateur 'ou' avait été utilisé pour les combiner.
-r <nom_fichier>
Lit le journal au format binaire à partir de ce fichier. Le fichier peut être créé avec varnishlog -w nom_fichier. Si le nom de fichier est -, les journaux sont lus depuis l'entrée standard et il ne peut pas fonctionner en tant que daemon.
-R <limite[/durée]>
Restreint la sortie à la limite spécifiée. Les transactions dépassant la limite seront supprimées. La limite est spécifiée comme le nombre maximum de transactions (par rapport à la méthode de regroupement choisie) et une période de temps optionnelle. Si aucune durée n'est spécifiée, une valeur par défaut de s est utilisée. Le champ durée peut être formaté comme en VCL (par exemple, -R 10/2m) ou comme une simple période de temps sans le préfixe (par exemple, -R 5/m). En mode de regroupement -g raw, ce réglage ne peut pas être utilisé avec -i, -I, -x ou -X, et nous recommandons d'utiliser -q à la place.
-t <secondes|off>
Délai avant de renvoyer une erreur lors de la connexion initiale VSM. S'il est défini, la connexion VSM est retentée toutes les 0,5 secondes pendant ce nombre de secondes. S'il est mis à zéro, la connexion est tentée une seule fois et échouera immédiatement si elle n'est pas réussie. S'il est défini sur "off", la connexion n'échouera pas, permettant à l'utilitaire de démarrer et d'attendre indéfiniment que l'instance Varnish apparaisse. La valeur par défaut est 5 secondes.
-V
Affiche les informations sur la version et quitte.
-w <nom_fichier>
Redirige la sortie vers un fichier. Le fichier sera écrasé sauf si l'option -a a été spécifiée. Si l'application reçoit un SIGHUP en mode daemon, le fichier sera rouvert, permettant à l'ancien fichier d'être archivé. Cette option est requise lors de l'exécution en mode daemon. Si le nom de fichier est -, varnishncsa écrit sur la sortie standard et ne peut pas fonctionner en tant que daemon.
--optstring
Affiche la chaîne d'options (optstring) de getopt(3) pour aider à écrire des scripts d'encapsulation.

MODES

Le mode par défaut de varnishncsa est le "mode client". Dans ce mode, le journal sera similaire à ce qu'un serveur web produirait en l'absence de varnish. Le mode client peut être sélectionné explicitement en utilisant -c.

Si le commutateur -b est spécifié, varnishncsa fonctionnera en mode "backend". Dans ce mode, les requêtes générées par varnish vers les backends seront journalisées. Sauf si -c est également spécifié, les requêtes client reçues par varnish seront ignorées.

Lors de l'exécution de varnishncsa en mode backend et client, il est fortement conseillé d'inclure le spécificateur de format %{Varnish:side}x pour distinguer les requêtes backend et client.

Les requêtes client qui résultent en un pipe (c'est-à-dire return(pipe) en vcl) ne généreront pas de journal en mode backend. Ceci parce que varnish ne génère pas de requêtes, mais transmet aveuglément des octets dans les deux sens. Cependant, une instance varnishncsa fonctionnant en mode normal peut voir ce cas en utilisant le formateur %{Varnish:handling}x, qui sera 'pipe'.

En mode backend, certains champs de la chaîne de format obtiennent des significations différentes. Notamment, les formateurs de comptage d'octets (%b, %I, %O) considèrent varnish comme le client.

Il est possible de faire tourner deux instances varnishncsa, une en mode backend, et une en mode client, en les dirigeant vers des fichiers différents.

FORMAT

Spécifie le format de journal à utiliser. Si aucun format n'est spécifié, le format de journal par défaut est utilisé :

%h %l %u %t "%r" %s %b "%{Referer}i" "%{User-agent}i"

Les séquences d'échappement \n et \t sont prises en charge.

Les formateurs pris en charge sont :

%b
En mode client, taille de la réponse en octets, en excluant les en-têtes HTTP. En mode backend, le nombre d'octets reçus du backend, en excluant les en-têtes HTTP. En format CLF, c'est-à-dire un '-' plutôt qu'un 0 lorsqu'aucun octet n'est envoyé.
%D
En mode client, temps passé
n pour servir la requête, en microsecondes. En mode backend, temps écoulé entre l'envoi de la requête et la réception complète du corps. Ceci est équivalent à %{us}T.
%H
Le protocole de la requête. Par défaut HTTP/1.0 s'il n'est pas connu.
%h
Hôte distant. Par défaut '-' s'il n'est pas connu. En mode backend, il s'agit de l'adresse IP du serveur backend.
%I
En mode client, octets totaux reçus du client. En mode backend, octets totaux envoyés au backend.
%{X[:first|last]}i
Le contenu de l'en-tête de requête X avant tout traitement VCL côté client, et avant vcl_backend_response pour le côté backend. Si l'en-tête apparaît plusieurs fois dans une seule transaction, la dernière occurrence est utilisée en mode backend et la première en mode client.

Si une option :first ou :last est utilisée, le traitement VCL sera pris en compte et la règle de correspondance sera la première correspondance ou la dernière correspondance respectivement. Lors de l'utilisation de :last, les en-têtes non définis seront toujours capturés.

%l
Nom d'utilisateur distant du log. Toujours '-'.
%m
Méthode de la requête. Par défaut '-' s'il n'est pas connu.
%{X[:first|last]}o
Le contenu de l'en-tête de réponse X, tel qu'il a été livré en mode client, et avant le traitement VCL pour le mode backend. Si l'en-tête apparaît plusieurs fois dans une seule transaction, la dernière occurrence est utilisée en mode client et la première en mode backend.

Si une option :first ou :last est utilisée, le traitement VCL sera pris en compte et la règle de correspondance sera la première correspondance ou la dernière correspondance respectivement. Lors de l'utilisation de :last, les en-têtes non définis seront toujours capturés.

%O
En mode client, octets totaux envoyés au client. En mode backend, octets totaux reçus du backend.
%q
La chaîne de requête. Par défaut une chaîne vide si elle n'est pas présente.
%r
La première ligne de la requête. Synthétisée à partir d'autres champs, elle peut donc ne pas être la requête exacte. Voir la section NOTES.
%s
Statut envoyé au client. En mode backend, statut reçu du backend.
%t
En mode client, heure à laquelle la requête a été reçue, au format date/heure HTTP. En mode backend, heure à laquelle la requête a été envoyée.
%{X}t
En mode client, heure à laquelle la requête a été reçue, au format spécifié par X. En mode backend, heure à laquelle la requête a été envoyée. Le format de spécification de l'heure est le même que pour strftime(3) avec ces extensions :
  • %{sec} : nombre de secondes depuis l'Époque
  • %{msec} : nombre de millisecondes depuis l'Époque
  • %{usec} : nombre de millisecondes depuis l'Époque
  • %{msec_frac} : fraction de milliseconde
  • %{usec_frac} : fraction de microseconde

Les extensions ne peuvent pas être combinées entre elles ou avec strftime(3) dans la même spécification. Utilisez plusieurs spécifications %{X}t à la place.

%T
En mode client, temps nécessaire pour servir la requête, en secondes. En mode backend, temps écoulé entre l'envoi de la requête et la réception complète du corps. Ceci est équivalent à %{s}T.
%{X}T
En mode client, temps nécessaire pour servir la requête, au format spécifié par X. En mode backend, temps écoulé entre l'envoi de la requête et la réception complète du corps. Le format de spécification de l'heure peut être l'un des suivants : s (identique à %T), ms ou us (identique à %D).
%U
L'URL de la requête sans la chaîne de requête. Par défaut '-' s'il n'est pas connu.
%u
Utilisateur distant de l'authentification.
%{X}x
Variables étendues. Les variables supportées sont :
Varnish:default_format
Le format de log utilisé lorsque les options -f ou -F ne sont pas spécifiées. Utile pour ajouter/préfacer avec d'autres formateurs.
Varnish:time_firstbyte
Temps écoulé entre le début du traitement de la requête et l'envoi du premier octet au client, en secondes. Pour le mode backend : Temps écoulé entre l'envoi de la requête au backend et la réception complète de l'en-tête.
Varnish:hitmiss
En mode client, une des chaînes 'hit' ou 'miss', selon que la requête a été un succès de cache ou un échec. Pipe, pass et synth sont considérés comme des échecs. En mode backend, ce champ est vide.
Varnish:handling
En mode client, une des chaînes 'hit', 'hitmiss', 'hitpass', 'miss', 'pass', 'pipe' ou 'synth' indiquant comment la requête a été traitée. En mode backend, ce champ est vide.
Varnish:side
Côté backend ou client. Un des deux valeurs, 'b' ou 'c', selon où la requête a été effectuée. En mode purement backend ou client, ce champ sera constant.
Varnish:vxid
Le VXID de la transaction Varnish.
VCL_Log:key
La valeur définie par std.log("key:value") dans VCL.
VSL:tag:record-prefix[field]
La valeur de l'entrée VSL pour la combinaison tag-record prefix-field donnée. Tag est obligatoire, les autres composants sont optionnels.

Le préfixe d'enregistrement limitera les correspondances aux enregistrements qui ont ce préfixe comme première partie du contenu de l'enregistrement suivi d'un deux-points.

Le champ, s'il est présent, traitera l'enregistrement de log comme une liste de champs séparés par des espaces blancs, et seule la nième partie de l'enregistrement sera mise en correspondance. Les champs commencent à compter à partir de 1 et vont jusqu'à 255.

Par défaut '-' lorsque le tag n'est pas vu, le préfixe d'enregistrement ne correspond pas ou le champ est hors limites. Si un tag apparaît plusieurs fois dans une seule transaction, la première occurrence est utilisée.

SIGNALS

  • SIGHUP

    Faire pivoter le fichier journal (voir l'option -w) en mode démon, abandonner la boucle et mourir gracieusement lors de l'exécution au premier plan.

  • SIGUSR1

    Vider toutes les transactions en attente.

NOTES

Le formateur %r est équivalent à %m http://%{Host}i%U%q %H. Cela diffère du comportement du %r du serveur HTTP Apache, équivalent à %m %U%q %H.

Notez que les champs de requête sont collectés sur la base de la première correspondance en mode client et de la dernière correspondance en mode backend. De même, les champs de réponse sont collectés sur la base de la première correspondance en mode backend et de la dernière correspondance en mode client.

Autrement dit, les en-têtes de requête sont enregistrés tels qu'ils ont été reçus du client et tels qu'ils ont été envoyés au backend, tandis que les en-têtes de réponse sont enregistrés tels qu'ils ont été envoyés au client et tels qu'ils ont été reçus du backend.

De plus, ces règles s'appliquent également aux éléments qui apparaissent plusieurs fois dans une transaction. Par exemple, si un en-tête apparaît plusieurs fois dans une requête client, la première occurrence est enregistrée en mode client, tandis qu'en mode backend, la dernière occurrence est enregistrée.

Avant la version 7.7, les formats %{X}i et %{X}o incluaient les champs d'en-tête remplis par VCL. Considérer %{VCL_Log:key}x à la place pour capturer des données des transactions VCL.

EXEMPLE

Enregistre le deuxième champ de l'enregistrement Begin, correspondant au VXID de la transaction parente :

varnishncsa -F "%{VSL:Begin[2]}x"

Enregistre l'intégralité de l'enregistrement Timestamp associé à la durée de traitement :

varnishncsa -F "%{VSL:Timestamp:Process}x"

Enregistre en JSON, en utilisant le drapeau -j pour s'assurer que la sortie est un JSON valide pour toutes les entrées :

varnishncsa -j -F '{"size": %b, "time": "%t", "ua": "%{User-Agent}i"}'

Enregistre les première et dernière valeurs d'un en-tête de requête modifié plusieurs fois dans VCL :

varnishncsa -F "%{x-custom-header:first}i %{x-custom-header:last}i"

NOM

varnishncsa - Convertisseur de format de journal pour Varnish HTTP Cache

SYNTAXE

varnishncsa [-aabbreviate] [-bbytes] [-Fformat] [-flogfile] [-iin-format] [-nnull] [-qquery] [-uuniquifier] [-wwidth] [-?]

DESCRIPTION

varnishncsa est un programme utilitaire qui prend les journaux de Varnish (qui sont par défaut au format ELFL) et les convertit en format NCSA/Apache Common Log Format. Ce format est plus lisible par l'homme et plus facile à analyser pour d'autres outils de journalisation.

Le programme lit depuis l'entrée standard par défaut, ou à partir d'un fichier spécifié avec l'option -f. La sortie est envoyée vers la sortie standard par défaut.

MODES

Il existe deux modes de fonctionnement :

  • Mode en ligne : varnishncsa lit des lignes depuis l'entrée standard et écrit la sortie formatée vers la sortie standard. Ce mode est utile pour le traitement en temps réel des journaux de Varnish, par exemple en utilisant des pipes.
  • Mode fichier : varnishncsa lit un fichier journal spécifié avec l'option -f et écrit la sortie formatée vers la sortie standard. Ce mode est utile pour le traitement de fichiers journaux existants.

FORMAT

Le format de sortie est configurable à l'aide de l'option -F. Les codes de format sont les suivants :

  • %h : Nom d'hôte de l'adresse IP distante.
  • %l : Identité du client (généralement un tiret).
  • %u : Nom d'utilisateur si une authentification a été effectuée (généralement un tiret).
  • %t : Heure à laquelle la requête a été reçue.
  • %r : Première ligne de la requête du client (méthode, URL, protocole).
  • %>s : Code d'état renvoyé par le serveur.
  • %b : Taille de l'objet renvoyé au client en octets.
  • %D : Temps total de traitement de la requête en microsecondes.
  • %{X-Header}i : Valeur d'un en-tête de requête entrant (remplacez X-Header par le nom de l'en-tête).
  • %{X-Header}o : Valeur d'un en-tête de réponse sortant (remplacez X-Header par le nom de l'en-tête).
  • %t_date_format : L'heure formatée selon la chaîne date_format.

Le format par défaut est %h %l %u %t \"%r\" %>s %b.

SIGNAUX

varnishncsa réagit aux signaux suivants :

  • SIGHUP : Rouvre le fichier journal. Si le programme est configuré pour écrire dans un fichier, il va maintenant écrire dans un nouveau fichier en ajoutant un horodatage.
  • SIGUSR1 : Affiche les statistiques actuelles sur la sortie d'erreur standard.
  • SIGUSR2 : Vide le tampon des statistiques.

NOTES

Le programme varnishncsa est généralement utilisé en combinaison avec le programme varnishlog pour traiter les journaux de Varnish. Il est souvent exécuté comme un service système.

EXEMPLE

Pour convertir les journaux de Varnish en format NCSA et les envoyer vers stdout :

varnishlog | varnishncsa

Pour lire les journaux depuis un fichier et les formater en utilisant le format combiné d'Apache (CLF) et de Varnish :

varnishncsa -f /var/log/varnish/varnish.log -F "%h %l %u [%t] \"%r\" %>s %b \"%{Referer}i\" \"%{User-agent}i\""
