VARLINKCTL(1) varlinkctl VARLINKCTL(1)

NOM

varlinkctl - Introspecter et invoquer des services Varlink

SYNTAXE

varlinkctl [OPTIONS...] info ADRESSE

varlinkctl [OPTIONS...] list-interfaces ADRESSE

varlinkctl [OPTIONS...] list-methods ADRESSE [INTERFACE...]

varlinkctl [OPTIONS...] introspect ADRESSE [INTERFACE...]

varlinkctl [OPTIONS...] call ADRESSE METHODE [ARGUMENTS]

varlinkctl [OPTIONS...] --exec call call ADRESSE METHODE ARGUMENTS -- LIGNE_DE_COMMANDE

varlinkctl [OPTIONS...] validate-idl [FICHIER]

DESCRIPTION

varlinkctl peut être utilisé pour introspecter et invoquer des services Varlink[1].

Les services sont référencés par l'un des éléments suivants :

•Une référence de service Varlink commençant par la chaîne "unix:", suivie d'un chemin de socket AF_UNIX absolu, ou par "@" et une chaîne arbitraire (cette dernière pour référencer des sockets dans l'espace de noms abstrait). Dans ce cas, une connexion de socket de flux est établie vers le socket spécifié.
•Une référence de service Varlink commençant par la chaîne "exec:", suivie d'un chemin absolu d'un binaire à exécuter. Dans ce cas, le processus spécifié est bifurqué localement, avec un socket de flux connecté passé en argument.
•Une référence de service Varlink commençant par la chaîne "ssh-unix:", suivie d'une spécification d'hôte SSH, suivie de ":", suivie d'un chemin de socket AF_UNIX absolu. (Cela nécessite OpenSSH 9.4 ou plus récent côté serveur, et les sockets de l'espace de noms abstrait ne sont pas pris en charge.)
•Une référence de service Varlink commençant par la chaîne "ssh-exec:", suivie d'une spécification d'hôte SSH, suivie de ":", suivie d'une ligne de commande. Dans ce cas, la commande est invoquée et le protocole Varlink est parlé sur les entrées et sorties standard de la commande invoquée.

Pour plus de commodité, ces deux syntaxes d'adresse de service plus simples (redondantes) sont également prises en charge :

•Un chemin du système de fichiers vers un socket AF_UNIX, soit absolu (c'est-à-dire commençant par "/"), soit relatif (auquel cas il doit commencer par "./").
•Un chemin du système de fichiers vers un exécutable, soit absolu, soit relatif (comme ci-dessus, doit commencer respectivement par "/" ou "./").

COMMANDES

Les commandes suivantes sont comprises :

info ADRESSE

Affiche des informations brèves sur le service spécifié, y compris le nom du fournisseur et la liste des interfaces implémentées. Attend une adresse de service dans l'un des formats décrits ci-dessus.

Ajouté dans la version 255.

list-interfaces ADRESSE

Affiche une liste des interfaces implémentées par le service spécifié. Attend une adresse de service dans l'un des formats décrits ci-dessus.

Ajouté dans la version 255.

list-methods ADRESSE [INTERFACE...]

Affiche une liste des méthodes implémentées par le service spécifié. Attend une adresse de service dans l'un des formats décrits ci-dessus ainsi qu'un ou plusieurs noms d'interface. Si aucun nom d'interface n'est spécifié, liste toutes les méthodes de toutes les interfaces implémentées par le service, sinon seulement les méthodes des interfaces spécifiées.

Ajouté dans la version 257.

introspect ADRESSE [INTERFACE...]

Affiche les définitions d'interface des interfaces spécifiées fournies par le service spécifié. Attend une adresse de service dans l'un des formats décrits ci-dessus et éventuellement un ou plusieurs noms d'interface Varlink. Si aucun nom d'interface n'est spécifié, affiche toutes les interfaces fournies par le service.

Ajouté dans la version 255.

call ADRESSE METHODE [ARGUMENTS]

Appelle la méthode spécifiée du service spécifié. Attend une adresse de service dans le format décrit ci-dessus, un nom de méthode Varlink entièrement qualifié et un objet d'arguments JSON. Si l'objet d'arguments n'est pas spécifié, il est lu depuis STDIN à la place. Pour passer une liste vide de paramètres, spécifiez l'objet vide "{}".

Les paramètres de réponse sont écrits sous forme d'objets JSON sur STDOUT.

Ajouté dans la version 255.

validate-idl [FICHIER]

Lit un fichier de définition d'interface Varlink, le parse et le valide, puis l'affiche avec coloration syntaxique. Cela vérifie la syntaxe et la cohérence interne de l'interface. Attend un nom de fichier pour lire la définition de l'interface. Si omis, lit la définition de l'interface depuis STDIN.

Ajouté dans la version 255.

help

Affiche l'aide sur la syntaxe des commandes.

Ajouté dans la version 255.

OPTIONS

Les options suivantes sont comprises :

--more

Lors de l'utilisation avec call : attend plusieurs réponses de méthode. Si ce drapeau est défini, l'appel de méthode est envoyé avec le drapeau more défini, ce qui indique au service de générer plusieurs réponses, si nécessaire. La commande reste en cours d'exécution jusqu'à ce que le service envoie un message de réponse indiquant qu'il s'agit de la dernière de la série (ou si le délai d'attente configuré est atteint, voir ci-dessous). Ce drapeau ne doit être défini que pour les appels de méthode qui prennent en charge ce mécanisme.

Si ce mode est activé, la sortie est automatiquement basculée en mode JSON-SEQ, de sorte que les objets de réponse individuels puissent être facilement discernés.

Ce commutateur n'a aucun effet sur le délai d'attente de l'appel de méthode appliqué par défaut. Que --more soit spécifié ou non, le délai d'attente par défaut sera de 45 s. Utilisez --timeout= (voir ci-dessous) pour modifier ou désactiver le délai d'attente. Lors de l'appel d'un appel de méthode qui renvoie continuellement des mises à jour, il est typiquement souhaitable de désactiver le délai d'attente avec --timeout=infinity. D'autre part, lors de l'appel d'une méthode --more dans le but d'énumérer des objets (qui se terminera probablement rapidement), il est généralement avantageux de laisser la logique de délai d'attente activée, pour des raisons de robustesse.

Ajouté dans la version 255.

-E

Raccourci pour --more --timeout=infinity. Ce commutateur est utile pour les appels de méthode qui implémentent la souscription à un flux continu de mises à jour.

Ajouté dans la version 257.

--collect

Ceci est similaire à --more, mais collecte toutes les réponses dans un tableau JSON, et l'affiche, plutôt qu'en mode JSON-SEQ.

Ajouté dans la version 256.

--oneway

Lors de l'utilisation avec call : n'attend pas de réponse de méthode. Si ce drapeau est défini, l'appel de méthode est envoyé avec le drapeau oneway défini (la commande se termine immédiatement après), ce qui indique au service de ne pas générer de réponse.

Ajouté dans la version 255.

--json=MODE

Sélectionne le formatage de la sortie JSON, soit "pretty" pour une sortie joliment indentée et colorisée, soit "short" pour une sortie concise avec un minimum d'espace blanc et pas de sauts de ligne. Par défaut, c'est "short".

Ajouté dans la version 255.

-j

Équivalent à --json=pretty lorsqu'il est invoqué interactivement depuis un terminal. Sinon, il est équivalent à --json=short, en particulier lorsque la sortie est redirigée vers un autre programme.

Ajouté dans la version 255.

--quiet, -q

Supprime la sortie des réponses aux appels de méthode.

Ajouté dans la version 257.

--graceful=

Prend un nom d'erreur Varlink qualifié, c'est-à-dire un nom d'interface, suffixé par un nom d'erreur, séparé par un point, par exemple "org.varlink.service.InvalidParameter". Garantit que, si un appel de méthode échoue avec l'erreur spécifiée, cela sera traité comme un succès, c'est-à-dire que l'invocation de varlinkctl se terminera avec un code de sortie nul. Cette option peut être utilisée plusieurs fois afin de traiter plusieurs erreurs différentes comme des succès.

Ajouté dans la version 257.

--timeout=

Attend un délai d'attente en secondes comme paramètre. Par défaut, un délai d'attente de 45 s est appliqué. Pour désactiver le délai d'attente, spécifiez "infinity" ou une chaîne vide.

Ajouté dans la version 257.

--exec

Une fois que l'appel de méthode émis via call s'est terminé avec succès, chargez en chaîne la ligne de commande spécifiée, avec les paramètres de sortie de l'appel de méthode sérialisés en JSON passés à l'entrée standard (et la sortie standard et l'erreur standard héritées du processus appelant). De plus, tous les descripteurs de fichiers renvoyés sur le socket de communication sous-jacent sont transmis au processus invité via le protocole habituel $LISTEN_FDS. Cette fonctionnalité peut être utilisée pour consommer des réponses accompagnées de descripteurs de fichiers de manière raisonnable.

Maintenant, si --exec est spécifié, le troisième paramètre de call n'est pas facultatif (c'est-à-dire les paramètres de l'appel de méthode).

Ajouté dans la version 258.

--push-fd=

Prend un numéro de descripteur de fichier numérique comme paramètre. Peut être utilisé pour passer un descripteur de fichier avec l'appel de méthode, si le transport sous-jacent le prend en charge. Peut être utilisé plusieurs fois pour passer plusieurs descripteurs de fichiers, en conservant l'ordre dans lequel ils sont spécifiés. Les descripteurs de fichiers spécifiés doivent être transmis à l'invocation de varlinkctl. Facultativement, à la place d'un numéro de descripteur de fichier numérique, un chemin de système de fichiers absolu ou relatif (ce dernier doit être préfixé par "./") peut être spécifié, qui est ouvert en lecture seule.

Ajouté dans la version 258.

--no-pager

Ne pas rediriger la sortie vers un paginateur.

-h, --help

Imprime un court texte d'aide et quitte.

--version

Imprime une courte chaîne de version et quitte.

EXEMPLES

Exemple 1. Investigation d'un service

Les trois commandes suivantes inspectent le service "io.systemd.Resolve" implémenté par systemd-resolved.service(8), listent les informations générales du service et les interfaces implémentées, puis affichent la définition de l'interface de son interface principale :

$ varlinkctl info /run/systemd/resolve/io.systemd.Resolve
    Vendor: The systemd Project
   Product: systemd (systemd-resolved)
   Version: 254 (254-1522-g4790521^)
       URL: https://systemd.io/
Interfaces: io.systemd
            io.systemd.Resolve
            org.varlink.service
$ varlinkctl list-interfaces /run/systemd/resolve/io.systemd.Resolve
io.systemd
io.systemd.Resolve
org.varlink.service
$ varlinkctl introspect /run/systemd/resolve/io.systemd.Resolve io.systemd.Resolve
interface io.systemd.Resolve
type ResolvedAddress(
        ifindex: ?int,
        ...

(La définition de l'interface a été tronquée dans l'exemple ci-dessus, par souci de concision.)

Exemple 2. Invocation d'une méthode

La commande suivante résout un nom d'hôte via l'appel de méthode ResolveHostname de systemd-resolved.service(8).

$ varlinkctl call /run/systemd/resolve/io.systemd.Resolve io.systemd.Resolve.ResolveHostname '{"name":"systemd.io","family":2}' -j
{
        "addresses" : [
                {
                        "ifindex" : 2,
                        "family" : 2,
                        "address" : [
                                185,
                                199,
                                111,
                                153
                        ]
                }
        ],
        "name" : "systemd.io",
        "flags" : 1048577
}

Exemple 3. Investigation d'un exécutable de service

La commande suivante inspecte l'exécutable /usr/lib/systemd/systemd-pcrextend et les API IPC qu'il fournit. Elle invoque ensuite une méthode sur celui-ci :

# varlinkctl info /usr/lib/systemd/systemd-pcrextend
    Vendor: The systemd Project
   Product: systemd (systemd-pcrextend)
   Version: 254 (254-1536-g97734fb)
       URL: https://systemd.io/
Interfaces: io.systemd
            io.systemd.PCRExtend
            org.varlink.service
# varlinkctl introspect /usr/lib/systemd/systemd-pcrextend io.systemd.PCRExtend
interface io.systemd.PCRExtend
method Extend(
        pcr: int,
        text: ?string,
        data: ?string
) -> ()
# varlinkctl call /usr/lib/systemd/systemd-pcrextend io.systemd.PCRExtend.Extend '{"pcr":15,"text":"foobar"}'
{}

Exemple 4. Invocation d'une méthode à distance via SSH

La commande suivante obtient un rapport sur l'identité d'un hôte distant "somehost" à partir de systemd-hostnamed.service(8) en se connectant via SSH au socket AF_UNIX sur lequel le service écoute :

# varlinkctl call ssh-unix:somehost:/run/systemd/io.systemd.Hostname io.systemd.Hostname.Describe '{}'

Pour invoquer directement un binaire de service Varlink sur l'hôte distant, plutôt que de communiquer avec un service via AF_UNIX, on peut faire comme ceci :

# varlinkctl call ssh-exec:somehost:systemd-creds org.varlink.service.GetInfo '{}'
