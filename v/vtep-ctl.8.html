NOM

vtep-ctl - utilitaire pour interroger et configurer une base de données VTEP

SYNTAXE

vtep-ctl [options] -- [options] commande [arguments] [-- [options] commande [arguments]]...

DESCRIPTION

Le programme vtep-ctl configure une base de données VTEP. Voir vtep(5) pour une documentation complète du schéma de la base de données.

vtep-ctl se connecte à un processus ovsdb-server qui maintient une base de données de configuration VTEP. En utilisant cette connexion, il interroge et éventuellement applique des modifications à la base de données, en fonction des commandes fournies.

vtep-ctl peut exécuter n'importe quel nombre de commandes en une seule fois, implémenté comme une seule transaction atomique contre la base de données.

La ligne de commande vtep-ctl commence par des options globales (voir OPTIONS ci-dessous pour plus de détails). Les options globales sont suivies d'une ou plusieurs commandes. Chaque commande doit commencer par -- seul comme argument de ligne de commande, pour la séparer des commandes suivantes. (Le -- avant la première commande est facultatif.) La commande elle-même commence par des options spécifiques à la commande, le cas échéant, suivies du nom de la commande et de ses arguments. Voir EXEMPLES ci-dessous pour des exemples de syntaxe.

OPTIONS

Les options suivantes affectent le comportement de vtep-ctl dans son ensemble. Certaines commandes individuelles acceptent également leurs propres options, qui sont données juste avant le nom de la commande. Si la première commande sur la ligne de commande a des options, alors ces options doivent être séparées des options globales par --.

--db=serveur
Définit serveur comme serveur de base de données auquel vtep-ctl se connecte pour interroger ou modifier la configuration. serveur peut être une méthode de connexion active ou passive OVSDB, telle que décrite dans ovsdb(7). La valeur par défaut est unix:/run/openvswitch/db.sock.
--no-syslog
Par défaut, vtep-ctl enregistre ses arguments et les détails de toute modification qu'il effectue dans le journal système. Cette option désactive cette journalisation.
Cette option est équivalente à --verbose=vtep_ctl:syslog:warn.
--oneline
Modifie le format de sortie de sorte que la sortie de chaque commande soit imprimée sur une seule ligne. Les caractères de nouvelle ligne qui sépareraient autrement les lignes sont imprimés sous forme de \n, et toutes les occurrences de \ qui apparaîtraient autrement dans la sortie sont doublées. Imprime une ligne vide pour chaque commande qui n'a pas de sortie. Cette option n'affecte pas le formatage de la sortie des commandes list ou find ; voir Options de formatage de tableau ci-dessous.
--dry-run
Empêche vtep-ctl de modifier réellement la base de données.
-t secs

--timeout=secs
Par défaut, ou avec une valeur de secs de 0, vtep-ctl attend indéfiniment une réponse de la base de données. Cette option limite le temps d'exécution à environ secs secondes. Si le délai expire, vtep-ctl se terminera avec un signal SIGALRM. (Un délai d'attente se produirait normalement uniquement si la base de données ne peut pas être contactée, ou si le système est surchargé.)

Options de formatage de tableau

Ces options contrôlent le format de la sortie des commandes list et find.

-f format

--format=format
Définit le type de formatage du tableau. Les types de format suivants sont disponibles :
table
Tableaux textuels 2D avec colonnes alignées.
list (par défaut)
Une liste avec une colonne par ligne et des lignes séparées par une ligne blanche.
html
Tableaux HTML.
csv
Valeurs séparées par des virgules telles que définies dans la RFC 4180.
json
Format JSON tel que défini dans la RFC 4627. La sortie est une séquence d'objets JSON, chacun correspondant à un tableau. Chaque objet JSON a les membres suivants avec les valeurs indiquées :
caption
La légende du tableau. Ce membre est omis si le tableau n'a pas de légende.
headings
Un tableau avec un élément par colonne de tableau. Chaque élément du tableau est une chaîne de caractères donnant l'en-tête de la colonne correspondante.
data
Un tableau avec un élément par ligne de tableau. Chaque élément est également un tableau avec un élément par colonne de tableau. Les éléments de ce tableau de second niveau sont les cellules qui constituent le tableau. Les cellules qui représentent des données ou des types de données OVSDB sont exprimées dans le format décrit dans la spécification OVSDB ; les autres cellules sont simplement exprimées sous forme de chaînes de caractères.
-d format

--data=format
Définit le formatage des cellules dans les tableaux de sortie, sauf si le format de tableau est défini sur json, auquel cas le formatage json est toujours utilisé lors du formatage des cellules. Les types de format suivants sont disponibles :
string (par défaut)
Le format simple décrit dans la section Valeurs de la base de données de ovs-vsctl(8).
bare
Le format simple avec la ponctuation retirée : [] et {} sont omis autour des ensembles, des cartes et des colonnes vides, les éléments au sein des ensembles et des cartes sont séparés par des espaces, et les chaînes ne sont jamais mises entre guillemets. Ce format peut être plus facile à analyser pour les scripts.
json
Le format JSON RFC 4627 tel que décrit ci-dessus.
--no-headings
Cette option supprime la ligne d'en-tête qui apparaît autrement dans la première ligne de la sortie du tableau.
--pretty
Par défaut, le JSON en sortie est imprimé de manière aussi compacte que possible. Cette option fait en sorte que le JSON en sortie soit imprimé d'une manière plus lisible. Les membres des objets et les éléments des tableaux sont imprimés un par ligne, avec indentation.
Cette option n'affecte pas le JSON dans les tableaux, qui est toujours imprimé de manière compacte.
--bare
Équivalent à --format=list --data=bare --no-headings.
--max-column-width=n
Pour la sortie de tableau uniquement, limite la largeur de toute colonne dans la sortie à n colonnes. Les données de cellule plus longues sont tronquées pour s'adapter, si nécessaire. Les colonnes sont toujours assez larges pour afficher les noms de colonnes, si la ligne d'en-tête est imprimée.

OPTIONS

-c certificate.pem

--certificate=certificate.pem
Specifies a PEM file containing a private key and the associated certificate, which vtep-ctl will use to authenticate itself to SSL/TLS peers. The certificate must be signed by the certificate authority (CA) that the peer in SSL/TLS connections will use to verify it.
-C cacert.pem

--ca-cert=cacert.pem
Specifies a PEM file containing the CA certificate that vtep-ctl should use to verify certificates presented to it by SSL/TLS peers. (This may be the same certificate that SSL/TLS peers use to verify the certificate specified on -c or --certificate, or it may be a different one, depending on the PKI design in use.)
-C none

--ca-cert=none
Disables verification of certificates presented by SSL/TLS peers. This introduces a security risk, because it means that certificates cannot be verified to be those of known trusted hosts.
--bootstrap-ca-cert=cacert.pem
When cacert.pem exists, this option has the same effect as -C or --ca-cert. If it does not exist, then vtep-ctl will attempt to obtain the CA certificate from the SSL/TLS peer on its first SSL/TLS connection and save it to the named PEM file. If it is successful, it will immediately drop the connection and reconnect, and from then on all SSL/TLS connections must be authenticated by a certificate signed by the CA certificate thus obtained.
This option exposes the SSL/TLS connection to a man-in-the-middle attack obtaining the initial CA certificate, but it may be useful for bootstrapping.
This option is only useful if the SSL/TLS peer sends its CA certificate as part of the SSL/TLS certificate chain. SSL/TLS protocols do not require the server to send the CA certificate.
This option is mutually exclusive with -C and --ca-cert.
--peer-ca-cert=peer-cacert.pem
Specifies a PEM file that contains one or more additional certificates to send to SSL/TLS peers. peer-cacert.pem should be the CA certificate used to sign vtep-ctl's own certificate, that is, the certificate specified on -c or --certificate. If vtep-ctl's certificate is self-signed, then --certificate and --peer-ca-cert should specify the same file.
This option is not useful in normal operation, because the SSL/TLS peer must already have the CA certificate for the peer to have any confidence in vtep-ctl's identity. However, this offers a way for a new installation to bootstrap the CA certificate on its first SSL/TLS connection.
-v[spec]

--verbose=[spec]
Sets logging levels. Without any spec, sets the log level for every module and destination to dbg. Otherwise, spec is a list of words separated by spaces or commas or colons, up to one from each category below:
  • A valid module name, as displayed by the vlog/list command on ovs-appctl(8), limits the log level change to the specified module.
  • syslog, console, or file, to limit the log level change to only to the system log, to the console, or to a file, respectively. (If --detach is specified, vtep-ctl closes its standard file descriptors, so logging to the console will have no effect.)
On Windows platform, syslog is accepted as a word and is only useful along with the --syslog-target option (the word has no effect otherwise).
•
off, emer, err, warn, info, or dbg, to control the log level. Messages of the given severity or higher will be logged, and messages of lower severity will be filtered out. off filters out all messages. See ovs-appctl(8) for a definition of each log level.
Case is not significant within spec.
Regardless of the log levels set for file, logging to a file will not take place unless --log-file is also specified (see below).
For compatibility with older versions of OVS, any is accepted as a word but has no effect.
-v

--verbose
Sets the maximum logging verbosity level, equivalent to --verbose=dbg.
-vPATTERN:destination:pattern

--verbose=PATTERN:destination:pattern
Sets the log pattern for destination to pattern. Refer to ovs-appctl(8) for a description of the valid syntax for pattern.
-vFACILITY:facility

--verbose=FACILITY:facility
Sets the RFC5424 facility of the log message. facility can be one of kern, user, mail, daemon, auth, syslog, lpr, news, uucp, clock, ftp, ntp, audit, alert, clock2, local0, local1, local2, local3, local4, local5, local6 or local7. If this option is not specified, daemon is used as the default for the local system syslog and local0 is used while sending a message to the target provided via the --syslog-target option.
--log-file[=file]
Enables logging to a file. If file is specified, then it is used as the exact name for the log file. The default log file name used if file is omitted is /var/log/openvswitch/vtep-ctl.log.
--syslog-target=host:port
Send syslog messages to UDP port on host, in addition to the system syslog. The host must be a numerical IP address, not a hostname.
--syslog-method=method
Specify method how syslog messages should be sent to syslog daemon. Following forms are supported:
  • libc, use libc syslog() function. Downside of using this options is that libc adds fixed prefix to every message before it is actually sent to the syslog daemon over /dev/log UNIX domain socket.
  • unix:file, use UNIX domain socket directly. It is possible to specify arbitrary message format with this option. However, rsyslogd 8.9 and older versions use hard coded parser function anyway that limits UNIX domain socket use. If you want to use arbitrary message format with older rsyslogd versions, then use UDP socket to localhost IP address instead.
  • udp:ip:port, use UDP socket. With this method it is possible to use arbitrary message format also with older rsyslogd. When sending syslog messages over UDP socket extra precaution needs to be taken into account, for example, syslog daemon needs to be configured to listen on the specified UDP port, accidental iptables rules could be interfering with local syslog traffic and there are some security considerations that apply to UDP sockets, but do not apply to UNIX domain sockets.
  • null, discards all messages logged to syslog.
The default is taken from the OVS_SYSLOG_METHOD environment variable; if it is unset, the default is libc.
-h

--help
Prints a brief help message to the console.
-V

--version
Prints version information to the console.

COMMANDS

The commands implemented by vtep-ctl are described in the sections below.

Commandes de commutateur physique

These commands examine and manipulate physical switches.

[--may-exist] add-ps pswitch
Creates a new physical switch named pswitch. Initially the switch will have no ports.
Without --may-exist, attempting to create a switch that exists is an error. With --may-exist, this command does nothing if pswitch already exists.
[--if-exists] del-ps pswitch
Deletes pswitch and all of its ports.
Without --if-exists, attempting to delete a switch that does not exist is an error. With --if-exists, attempting to delete a switch that does not exist has no effect.
list-ps
Lists all existing physical switches on standard output, one per line.
ps-exists pswitch
Tests whether pswitch exists. If so, vtep-ctl exits successfully with exit code 0. If not, vtep-ctl exits unsuccessfully with exit code 2.

Commandes de ports

These commands examine and manipulate VTEP physical ports.

list-ports pswitch
Lists all of the ports within pswitch on standard output, one per line.
[--may-exist] add-port pswitch port
Creates on pswitch a new port named port from the network device of the same name.
Without --may-exist, attempting to crea
une porte qui existe déjà est une erreur. Avec --may-exist, cette commande ne fait rien si port existe déjà sur pswitch.
[--if-exists] del-port [pswitch] port
Supprime port. Si pswitch est omis, port est supprimé du commutateur qui le contient ; si pswitch est spécifié, il doit s'agir du commutateur qui contient port.
Sans --if-exists, tenter de supprimer une porte qui n'existe pas est une erreur. Avec --if-exists, tenter de supprimer une porte qui n'existe pas n'a aucun effet.

Commandes de commutateurs logiques

Ces commandes examinent et manipulent les commutateurs logiques.

[--may-exist] add-ls lswitch
Crée un nouveau commutateur logique nommé lswitch. Initialement, le commutateur n'aura aucune liaison de localisateur.
Sans --may-exist, tenter de créer un commutateur qui existe est une erreur. Avec --may-exist, cette commande ne fait rien si lswitch existe déjà.
[--if-exists] del-ls lswitch
Supprime lswitch.
Sans --if-exists, tenter de supprimer un commutateur qui n'existe pas est une erreur. Avec --if-exists, tenter de supprimer un commutateur qui n'existe pas n'a aucun effet.
list-ls
Liste tous les commutateurs logiques existants sur la sortie standard, un par ligne.
ls-exists lswitch
Teste si lswitch existe. Si c'est le cas, vtep-ctl se termine avec succès et un code de sortie 0. Sinon, vtep-ctl se termine avec un échec et un code de sortie 2.
bind-ls pswitch port vlan lswitch
Lie le commutateur logique lswitch à la combinaison port/vlan sur le commutateur physique pswitch.
unbind-ls pswitch port vlan
Supprime la liaison de commutateur logique de la combinaison port/vlan sur le commutateur physique pswitch.
list-bindings pswitch port
Liste les liaisons de commutateurs logiques pour le port sur le commutateur physique pswitch.
set-replication-mode lswitch mode_replication
Définit le mode de réplication du commutateur logique lswitch sur mode_replication ; les seules valeurs valides pour le mode de réplication sont "service_node" et "source_node". Pour gérer le trafic de diffusion L2, de multidiffusion et de monodiffusion inconnue, les paquets peuvent être envoyés à tous les membres d'un commutateur logique référencé par un commutateur physique. Il existe différents modes pour répliquer les paquets. Le mode de réplication par défaut consiste à envoyer le trafic à un nœud de service, qui peut être un hyperviseur, un serveur ou une appliance, et à laisser le nœud de service gérer la réplication vers d'autres nœuds de transport (hyperviseurs ou autres commutateurs physiques VTEP). Ce mode est appelé réplication par nœud de service. Un mode de réplication alternatif, appelé réplication par nœud source, implique que le nœud source envoie aux autres nœuds de transport. Les hyperviseurs sont toujours responsables de leur propre réplication pour les machines virtuelles connectées localement dans les deux modes. Le mode nœud de service est le mode par défaut, si le mode de réplication n'est pas explicitement défini. Le mode de réplication par nœud de service est considéré comme une exigence de base car il ne nécessite que l'envoi du paquet à un seul nœud de transport.
get-replication-mode lswitch
Obtient le mode de réplication du commutateur logique lswitch. Les seules valeurs valides pour le mode de réplication sont "service_node" et "source_node". Une réponse vide pour le mode de réplication implique par défaut "service_node".

Commandes de routeur logique

Ces commandes examinent et manipulent les routeurs logiques.

[--may-exist] add-lr lrouter
Crée un nouveau routeur logique nommé lrouter.
Sans --may-exist, tenter de créer un routeur qui existe est une erreur. Avec --may-exist, cette commande ne fait rien si lrouter existe déjà.
[--if-exists] del-lr lrouter
Supprime lrouter.
Sans --if-exists, tenter de supprimer un routeur qui n'existe pas est une erreur. Avec --if-exists, tenter de supprimer un routeur qui n'existe pas n'a aucun effet.
list-lr
Liste tous les routeurs logiques existants sur la sortie standard, un par ligne.
lr-exists lrouter
Teste si lrouter existe. Si c'est le cas, vtep-ctl se termine avec succès et un code de sortie 0. Sinon, vtep-ctl se termine avec un échec et un code de sortie 2.

Commandes de liaison MAC locale

Ces commandes examinent et manipulent les liaisons MAC locales pour le commutateur logique. Les cartes locales sont écrites par le VTEP pour faire référence aux MAC qu'il a apprises sur ses ports physiques.

add-ucast-local lswitch mac [encap] ip
Lie l'adresse Ethernet de monodiffusion mac à l'emplacement physique ip en utilisant l'encapsulation encap sur lswitch. Si encap n'est pas spécifié, la valeur par défaut est "vxlan_over_ipv4". Les liaisons locales sont utilisées par le VTEP pour faire référence aux MAC apprises sur ses ports physiques.
del-ucast-local lswitch mac
Supprime la liaison d'adresse Ethernet de monodiffusion locale mac de lswitch. Les liaisons locales sont utilisées par le VTEP pour faire référence aux MAC apprises sur ses ports physiques.
add-mcast-local lswitch mac [encap] ip
Ajoute l'emplacement physique ip en utilisant l'encapsulation encap à la table de liaison MAC locale pour l'adresse Ethernet de multidiffusion mac sur lswitch. Si encap n'est pas spécifié, la valeur par défaut est "vxlan_over_ipv4". Les liaisons locales sont utilisées par le VTEP pour faire référence aux MAC apprises sur ses ports physiques.
del-mcast-local lswitch mac [encap] ip
Supprime l'emplacement physique ip en utilisant l'encapsulation encap de la table de liaison MAC locale pour l'adresse Ethernet de multidiffusion mac sur lswitch. Si encap n'est pas spécifié, la valeur par défaut est "vxlan_over_ipv4". Les liaisons locales sont utilisées par le VTEP pour faire référence aux MAC apprises sur ses ports physiques.
clear-local-macs lswitch
Efface les liaisons MAC locales pour lswitch.
list-local-macs lswitch
Liste les liaisons MAC locales pour lswitch, une par ligne.

Si encap n'est pas spécifié, la valeur par défaut est "vxlan_over_ipv4". Les liaisons distantes sont utilisées par la plateforme de virtualisation du réseau pour faire référence aux MAC qu'elle a apprises.

Supprime l'emplacement physique ip en utilisant l'encapsulation encap de la table de liaison MAC distante pour l'adresse Ethernet de multidiffusion mac sur lswitch. Si encap n'est pas spécifié, la valeur par défaut est "vxlan_over_ipv4". Les liaisons distantes sont utilisées par la plateforme de virtualisation du réseau pour faire référence aux MAC qu'elle a apprises.

Efface les liaisons MAC distantes pour lswitch.

Connectivité Manager

Ces commandes manipulent la colonne managers dans la table Global et les lignes de la table Managers. Lorsque ovsdb-server est configuré pour utiliser la colonne managers pour les connexions OVSDB (comme décrit dans les scripts de démarrage fournis avec Open vSwitch), cela permet à l'administrateur d'utiliser vtep-ctl pour configurer les connexions de base de données.

get-manager
Affiche le ou les gestionnaires configurés.
del-manager
Supprime le ou les gestionnaires configurés.
set-manager cible...
Définit la ou les cibles de gestionnaire configurées. Chaque cible peut être une méthode de connexion OVSDB active ou passive, par exemple pssl:6640, comme décrit dans ovsdb(7).

Commandes de base de données

Ces commandes interrogent et modifient le contenu des tables ovsdb. Elles constituent une légère abstraction de l'interface ovsdb et, à ce titre, fonctionnent à un niveau inférieur aux autres commandes vtep-ctl.

Identification des tables, enregistrements et colonnes

Chacune de ces commandes possède un paramètre table pour identifier une table dans la base de données. Beaucoup d'entre elles acceptent également un paramètre record qui identifie un enregistrement particulier dans une table. Le paramètre record peut être l'UUID d'un enregistrement, et de nombreuses tables offrent des moyens supplémentaires d'identifier les enregistrements. Certaines commandes acceptent également des paramètres column qui identifient un champ particulier dans les enregistrements d'une table.

Les tables suivantes sont actuellement définies :

Global
Configuration de haut niveau pour un VTEP matériel. Cette table contient exactement un enregistrement, identifié en spécifiant . comme nom d'enregistrement.
Manager
Configuration d'une connexion OVSDB. Les enregistrements peuvent être identifiés par leur cible (par exemple, tcp:1.2.3.4).
Physical_Switch
Un commutateur physique qui implémente un VTEP. Les enregistrements peuvent être identifiés par le nom du commutateur physique.
Physical_Port
Un port au sein d'un commutateur physique.
Logical_Binding_Stats
Rapporte les statistiques pour le commutateur logique auquel une VLAN sur un port physique est associée.
Logical_Switch
Un commutateur Ethernet logique. Les enregistrements peuvent être identifiés par le nom du commutateur logique.
Ucast_Macs_Local
Mappage des adresses MAC unicast découvertes localement aux tunnels.
Ucast_Macs_Remote
Mappage des adresses MAC unicast programmées à distance aux tunnels.
Mcast_Macs_Local
Mappage des adresses MAC multicast découvertes localement aux tunnels.
Mcast_Macs_Remote
Mappage des adresses MAC multicast programmées à distance aux tunnels.
Physical_Locator_Set
Un ensemble d'un ou plusieurs localisateurs physiques.
Physical_Locator
Identifie un point d'extrémité auquel le trafic du commutateur logique peut être encapsulé et acheminé. Les enregistrements peuvent être identifiés par le nom du localisateur physique.

Les noms d'enregistrement doivent être spécifiés en entier et avec la casse correcte, à l'exception des UUID qui peuvent être abrégés à leurs 4 premiers chiffres hexadécimaux (ou plus), tant que cela est unique dans la table. Les noms des tables et des colonnes ne sont pas sensibles à la casse, et les caractères - et _ sont traités de manière interchangeable. Des abréviations uniques des noms de tables et de colonnes sont acceptables, par exemple, man ou m suffisent pour identifier la table Manager.

Valeurs de base de données

Chaque colonne de la base de données accepte un type de données fixe. Les types de base actuellement définis, et leurs représentations, sont :

entier
Un entier décimal dans la plage de -2**63 à 2**63-1, inclus.
réel
Un nombre à virgule flottante.
Booléen
Vrai ou faux, écrit true ou false, respectivement.
chaîne
Une chaîne Unicode arbitraire, à l'exception des octets nuls qui ne sont pas autorisés. Les guillemets sont facultatifs pour la plupart des chaînes qui commencent par une lettre anglaise ou un trait de soulignement et ne contiennent que des lettres, des traits de soulignement, des tirets et des points. Cependant, true et false ainsi que les chaînes qui ressemblent à la syntaxe des UUID (voir ci-dessous) doivent être entourées de guillemets doubles pour les distinguer des autres types de base. Lorsque des guillemets doubles sont utilisés, la syntaxe est celle des chaînes en JSON, par exemple, les barres obliques inverses peuvent être utilisées pour échapper les caractères spéciaux. La chaîne vide doit être représentée par une paire de guillemets doubles ("").
UUID
Soit un identifiant unique universel dans le style de la RFC 4122, par exemple, f81d4fae-7dec-11d0-a765-00a0c91e6bf6, soit un nom @nom défini par une commande get ou create dans la même invocation vtep-ctl.

Les valeurs multiples dans une seule colonne peuvent être séparées par des espaces ou une seule virgule. Lorsque plusieurs valeurs sont présentes, les doublons ne sont pas autorisés et l'ordre n'a pas d'importance. Inversement, certaines colonnes de la base de données peuvent avoir un ensemble vide de valeurs, représenté par [], et des crochets peuvent éventuellement entourer d'autres ensembles non vides ou des valeurs uniques. Pour une colonne acceptant un ensemble d'entiers, les commandes de la base de données acceptent une plage. Une plage est représentée par deux entiers séparés par un tiret (-). Une plage est inclusive. Une plage a une taille maximale de 4096 éléments. Si plus d'éléments sont nécessaires, ils peuvent être spécifiés dans des plages séparées.

Quelques colonnes de la base de données sont des ``cartes'' de paires clé-valeur, où la clé et la valeur sont chacune un type de base fixe. Celles-ci sont spécifiées sous la forme clé=valeur, où clé et valeur suivent la syntaxe du type de clé et du type de valeur de la colonne, respectivement. Lorsque plusieurs paires sont présentes (séparées par des espaces ou une virgule), les clés dupliquées ne sont pas autorisées, et là encore l'ordre n'a pas d'importance. Les valeurs dupliquées sont autorisées. Une carte vide est représentée par {}. Des accolades peuvent éventuellement entourer des cartes non vides également (mais utilisez des guillemets pour éviter que le shell n'étende other-config={0=x,1=y} en other-config=0=x other-config=1=y, ce qui pourrait ne pas avoir l'effet désiré).

Syntaxe des commandes de base de données
[--if-exists] [--columns=colonne[,colonne]...] list table [enregistrement]...
Liste les données de chaque enregistrement spécifié. Si aucun enregistrement n'est spécifié, liste tous les enregistrements de la table.
Si --columns est spécifié, seules les colonnes demandées sont listées, dans l'ordre spécifié. Sinon, toutes les colonnes sont listées, par ordre alphabétique selon le nom de la colonne.
Sans --if-exists, c'est une erreur si un enregistrement spécifié n'existe pas. Avec --if-exists, la commande ignore tout enregistrement qui n'existe pas, sans produire de sortie.
[--columns=colonne[,colonne]...] find table [colonne[:clé]=valeur]...
Liste les données de chaque enregistrement dans table dont la colonne est égale à valeur ou, si clé est spécifiée, dont la colonne contient une clé avec la valeur spécifiée. Les opérateurs suivants peuvent être utilisés là où = est écrit dans le résumé de la syntaxe :
= != < > <= >=
Sélectionne les enregistrements dans lesquels colonne[:clé] est égal, différent, inférieur, supérieur, inférieur ou égal, ou supérieur ou égal à valeur, respectivement.
Considère colonne[:clé] et valeur comme des ensembles d'éléments. Des ensembles identiques sont considérés comme égaux. Sinon, si les ensembles ont un nombre différent d'éléments, alors l'ensemble avec plus d'éléments est considéré comme plus grand. Sinon, considérez un élément de chaque ensemble par paire, dans l'ordre croissant dans chaque ensemble. La première paire qui diffère détermine le résultat. (Pour une colonne qui contient des paires clé-valeur, d'abord toutes les clés sont comparées, et les valeurs ne sont considérées que si les deux ensembles contiennent des clés identiques.)
{=} {!=}
Teste l'égalité ou l'inégalité de l'ensemble, respectivement.
{<=}
Sélectionne les enregistrements dans lesquels colonne[:clé] est un sous-ensemble de valeur. Par exemple, flood-vlans{<=}1,2 sélectionne les enregistrements dans lesquels la colonne flood-vlans est l'ensemble vide ou contient 1 ou 2 ou les deux.
{<}
Sélectionne les enregistrements dans lesquels colonne[:clé] est un sous-ensemble propre de valeur. Par exemple, flood-vlans{<}1,2 sélectionne les enregistrements dans lesquels la colonne flood-vlans est l'ensemble vide ou contient 1 ou 2 mais pas les deux.
{>=} {>}
Identique à {<=} et {<}, respectivement, sauf que la relation est inversée. Par exemple, flood-vlans{>=}1,2 sélectionne les enregistrements dans lesquels la colonne flood-vlans contient à la fois 1 et 2.

Les opérateurs suivants ne sont disponibles qu'à partir d'Open vSwitch 2.16 :

{in}
Sélectionne les enregistrements dans lesquels chaque élément de colonne[:clé] est également dans valeur. (C'est la même chose que {<=}.)
{not-in}
Sélectionne les enregistrements dans lesquels chaque élément de colonne[:clé] n'est pas dans valeur.
Pour les opérateurs arithmétiques (= != < > <= >=), lorsque clé est spécifiée mais qu'un enregistrement particulier n'a pas la colonne contenant la clé, l'enregistrement est toujours omis des résultats. Ainsi, la condition other-config:mtu!=1500 correspond aux enregistrements qui ont une clé mtu dont la valeur n'est pas 1500, mais pas ceux qui n'ont pas de clé mtu.
Pour les opérateurs d'ensemble, lorsque clé est spécifiée mais qu'un enregistrement particulier n'a pas la colonne contenant la clé, la comparaison est effectuée avec un ensemble vide. Ainsi, la condition other-config:mtu{!=}1500 correspond aux enregistrements qui ont une clé mtu dont la valeur n'est pas 1500 et à ceux qui n'ont pas de clé mtu.
N'oubliez pas d'échapper < ou > pour éviter leur interprétation par le shell.
Si --columns est spécifié, seules les colonnes demandées sont listées, dans l'ordre spécifié. Sinon, toutes les colonnes sont listées, par ordre alphabétique selon le nom de la colonne.
Les UUID affichés pour les lignes créées dans la même invocation vtep-ctl seront incorrects.
[--if-exists] [--id=@nom] get table enregistrement [colonne[:clé]]...
Affiche la valeur de chaque colonne spécifiée dans l' enregistrement donné dans la table. Pour les colonnes de type map, une clé
y peut facultativement être spécifié, auquel cas la valeur associée à clé dans la colonne est imprimée, au lieu de la carte entière.
Sans --if-exists, il s'agit d'une erreur si enregistrement n'existe pas ou si clé est spécifiée, si clé n'existe pas dans enregistrement. Avec --if-exists, un enregistrement manquant ne produit aucune sortie et une clé manquante imprime une ligne vide.
Si @nom est spécifié, alors l'UUID pour enregistrement peut être référencé par ce nom plus tard dans la même invocation vtep-ctl dans des contextes où un UUID est attendu.
Les arguments --id et colonne sont facultatifs, mais généralement au moins l'un ou l'autre devrait être spécifié. Si les deux sont omis, alors get n'a aucun effet sauf pour vérifier que enregistrement existe dans table.
--id et --if-exists ne peuvent pas être utilisés ensemble.
[--if-exists] set table enregistrement colonne[:clé]=valeur...
Définit la valeur de chaque colonne spécifiée dans le enregistrement donné dans table à valeur. Pour les colonnes de type carte, une clé peut facultativement être spécifiée, auquel cas la valeur associée à clé dans cette colonne est modifiée (ou ajoutée, si aucune n'existe), au lieu de la carte entière.
Sans --if-exists, il s'agit d'une erreur si enregistrement n'existe pas. Avec --if-exists, cette commande ne fait rien si enregistrement n'existe pas.
[--if-exists] add table enregistrement colonne [clé=]valeur...
Ajoute la valeur spécifiée ou la paire clé-valeur à colonne dans enregistrement dans table. Si colonne est une carte, alors clé est requise, sinon elle est interdite. Si clé existe déjà dans une colonne de type carte, alors la valeur actuelle n'est pas remplacée (utilisez la commande set pour remplacer une valeur existante).
Sans --if-exists, il s'agit d'une erreur si enregistrement n'existe pas. Avec --if-exists, cette commande ne fait rien si enregistrement n'existe pas.
[--if-exists] remove table enregistrement colonne valeur...

[--if-exists] remove table enregistrement colonne clé...

[--if-exists] remove table enregistrement colonne clé=valeur...
Supprime les valeurs spécifiées ou les paires clé-valeur de colonne dans enregistrement dans table. La première forme s'applique aux colonnes qui ne sont pas des cartes : chaque valeur spécifiée est supprimée de la colonne. La deuxième et la troisième forme s'appliquent aux colonnes de type carte : si seule une clé est spécifiée, alors toute paire clé-valeur avec la clé donnée est supprimée, quelle que soit sa valeur ; si une valeur est donnée, alors une paire est supprimée uniquement si la clé et la valeur correspondent.
Il ne s'agit pas d'une erreur si la colonne ne contient pas la clé ou la valeur ou la paire spécifiée.
Sans --if-exists, il s'agit d'une erreur si enregistrement n'existe pas. Avec --if-exists, cette commande ne fait rien si enregistrement n'existe pas.
[--if-exists] clear table enregistrement colonne...
Définit chaque colonne dans enregistrement dans table à l'ensemble vide ou à la carte vide, selon le cas. Cette commande s'applique uniquement aux colonnes qui sont autorisées à être vides.
Sans --if-exists, il s'agit d'une erreur si enregistrement n'existe pas. Avec --if-exists, cette commande ne fait rien si enregistrement n'existe pas.
[--id=(@nom | uuid] create table colonne[:clé]=valeur...
Crée un nouvel enregistrement dans table et définit les valeurs initiales de chaque colonne. Les colonnes non explicitement définies recevront leurs valeurs par défaut. Affiche l'UUID de la nouvelle ligne.
Si @nom est spécifié, alors l'UUID de la nouvelle ligne peut être référencé par ce nom ailleurs dans la même invocation vtep-ctl dans des contextes où un UUID est attendu. De telles références peuvent précéder ou suivre la commande create.
Si un uuid valide est spécifié, alors il est utilisé comme UUID de la nouvelle ligne.
Attention (ovs-vsctl comme exemple)
Les enregistrements dans la base de données Open vSwitch sont significatifs uniquement lorsqu'ils peuvent être atteints directement ou indirectement depuis la table Open_vSwitch. À l'exception des enregistrements dans les tables QoS ou Queue, les enregistrements qui ne sont pas atteignables depuis la table Open_vSwitch sont automatiquement supprimés de la base de données. Cette suppression se produit immédiatement, sans attendre de commandes ovs-vsctl supplémentaires ou d'autres activités de base de données. Ainsi, une commande create doit généralement être accompagnée de commandes supplémentaires au sein de la même invocation ovs-vsctl pour ajouter une chaîne de références au nouvel enregistrement créé depuis l'enregistrement de haut niveau Open_vSwitch. La section EXEMPLES donne quelques exemples qui montrent comment faire cela.
[--if-exists] destroy table enregistrement...
Supprime chaque enregistrement spécifié de table. Sauf si --if-exists est spécifié, chaque enregistrement doit exister.
--all destroy table
Supprime tous les enregistrements de la table.
Attention (ovs-vsctl comme exemple)
La commande destroy est uniquement utile pour les enregistrements dans les tables QoS ou Queue. Les enregistrements dans d'autres tables sont automatiquement supprimés de la base de données lorsqu'ils deviennent inatteignables depuis la table Open_vSwitch. Cela signifie que la suppression de la dernière référence à un enregistrement est suffisante pour supprimer l'enregistrement lui-même. Pour les enregistrements dans ces tables, destroy est silencieusement ignoré. Voir la section EXEMPLES ci-dessous pour plus d'informations.
wait-until table enregistrement [colonne[:clé]=valeur]...
Attend jusqu'à ce que table contienne un enregistrement nommé enregistrement dont la colonne est égale à valeur ou, si clé est spécifiée, dont la colonne contient une clé avec la valeur spécifiée. Cette commande prend en charge les mêmes opérateurs et sémantiques décrits pour la commande find ci-dessus.
Si aucun argument colonne[:clé]=valeur n'est donné, cette commande attend seulement jusqu'à ce que enregistrement existe. Si plusieurs arguments de ce type sont donnés, la commande attend jusqu'à ce qu'ils soient tous satisfaits.
Attention (ovs-vsctl comme exemple)
Généralement, wait-until doit être placé au début d'un ensemble de commandes ovs-vsctl. Par exemple, wait-until bridge br0 -- get bridge br0 datapath_id attend qu'un pont nommé br0 soit créé, puis affiche sa colonne datapath_id, tandis que get bridge br0 datapath_id -- wait-until bridge br0 échouera s'il n'existe aucun pont nommé br0 lorsque ovs-vsctl se connecte initialement à la base de données.
Envisagez de spécifier --timeout=0 avec --wait-until, pour empêcher vtep-ctl de se terminer après avoir attendu au maximum 5 secondes.
comment [arg]...
Cette commande n'a aucun effet sur le comportement, mais tout enregistrement de journal de base de données créé par la commande inclura la commande et ses arguments.
