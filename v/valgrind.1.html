NOM

valgrind - une suite d'outils pour le débogage et le profilage de programmes

SYNTAXE

valgrind [options-valgrind] [votre-programme] [options-de-votre-programme]

DESCRIPTION

Valgrind est un programme flexible pour le débogage et le profilage d'exécutables Linux. Il est composé d'un noyau, qui fournit un CPU synthétique en logiciel, et d'une série d'outils de débogage et de profilage. L'architecture est modulaire, de sorte que de nouveaux outils peuvent être créés facilement et sans perturber la structure existante.

Certaines des options décrites ci-dessous fonctionnent avec tous les outils Valgrind, et d'autres ne fonctionnent qu'avec quelques-uns ou un seul. La section OPTIONS DE MEMCHECK et celles qui suivent décrivent les options spécifiques aux outils.

Cette page de manuel ne couvre que l'utilisation et les options de base. Pour des informations plus complètes, veuillez consulter la documentation HTML sur votre système : $INSTALL/share/doc/valgrind/html/index.html, ou en ligne : http://www.valgrind.org/docs/manual/index.html.

OPTIONS DE SÉLECTION D'OUTIL

L'option la plus importante.

--tool=<nom-outil> [défaut : memcheck]

Exécute l'outil Valgrind appelé nom-outil, par exemple memcheck, cachegrind, callgrind, helgrind, drd, massif, dhat, lackey, none, exp-bbv, etc.

OPTIONS DE BASE

Ces options fonctionnent avec tous les outils.

-h --help

Affiche l'aide pour toutes les options, à la fois pour le noyau et pour l'outil sélectionné. Si l'option est répétée, elle est équivalente à donner --help-debug.

--help-debug

Identique à --help, mais liste également les options de débogage qui ne sont généralement utiles qu'aux développeurs de Valgrind.

--version

Affiche le numéro de version du noyau Valgrind. Les outils peuvent avoir leurs propres numéros de version. Un système est en place pour garantir que les outils ne s'exécutent que lorsque la version du noyau est compatible. Ceci a été fait pour minimiser les risques de problèmes étranges dus à des incompatibilités de version entre l'outil et le noyau.

-q, --quiet

Exécute silencieusement, et n'affiche que les messages d'erreur. Utile si vous exécutez des tests de régression ou si vous avez une sorte de système de test automatisé.

-v, --verbose

Soyez plus verbeux. Donne des informations supplémentaires sur divers aspects de votre programme, tels que : les objets partagés chargés, les suppressions utilisées, la progression des moteurs d'instrumentation et d'exécution, et les avertissements sur les comportements inhabituels. Répéter l'option augmente le niveau de verbosité.

--trace-children=<oui|non> [défaut : non]

Lorsque cette option est activée, Valgrind suivra les sous-processus initiés via l'appel système exec. Ceci est nécessaire pour les programmes multi-processus.

Notez que Valgrind suit l'enfant d'un appel fork (il serait difficile de ne pas le faire, puisque fork crée une copie identique d'un processus), donc cette option est sans doute mal nommée. Cependant, la plupart des enfants d'appels fork appellent immédiatement exec de toute façon.

--trace-children-skip=patt1,patt2,...

Cette option n'a d'effet que lorsque --trace-children=oui est spécifié. Elle permet de sauter certains enfants. L'option prend une liste de motifs séparés par des virgules pour les noms des exécutables enfants que Valgrind ne doit pas suivre. Les motifs peuvent inclure les métacaractères ? et *, qui ont la signification habituelle.

Cela peut être utile pour élaguer des branches non intéressantes d'un arbre de processus en cours d'exécution sur Valgrind. Mais vous devez être prudent lors de son utilisation. Lorsque Valgrind évite de suivre un exécutable, il ne se contente pas d'éviter de suivre cet exécutable, il évite également de suivre tous les processus enfants de cet exécutable. En d'autres termes, le drapeau n'entraîne pas simplement l'arrêt du suivi aux exécutables spécifiés -- il évite le suivi de sous-arbres de processus entiers enracinés à l'un des exécutables spécifiés.

--trace-children-skip-by-arg=patt1,patt2,...

C'est la même chose que --trace-children-skip, avec une seule différence : la décision de suivre ou non un processus enfant est prise en examinant les arguments du processus enfant, plutôt que le nom de son exécutable.

--child-silent-after-fork=<oui|non> [défaut : non]

Lorsque cette option est activée, Valgrind n'affichera aucune sortie de débogage ou de journalisation pour le processus enfant résultant d'un appel fork. Cela peut rendre la sortie moins confuse (bien que plus trompeuse) lors du traitement de processus qui créent des enfants. C'est particulièrement utile en conjonction avec --trace-children=. L'utilisation de cette option est également fortement recommandée si vous demandez une sortie XML (--xml=yes), car sinon le XML de l'enfant et du parent pourrait se mélanger, ce qui le rend généralement inutile.

--vgdb=<non|oui|complet> [défaut : oui]

Valgrind fournira une fonctionnalité de type "gdbserver" lorsque --vgdb=oui ou --vgdb=complet est spécifié. Cela permet à un débogueur GNU GDB externe de contrôler et de déboguer votre programme lorsqu'il s'exécute sur Valgrind. --vgdb=complet entraîne des surcoûts de performance importants, mais fournit des points d'arrêt et des points de surveillance plus précis. Voir Débogage de votre programme à l'aide du gdbserver de Valgrind et GDB pour une description détaillée.

Si le gdbserver embarqué est activé mais qu'aucun gdb n'est actuellement utilisé, l'utilitaire en ligne de commande vgdb peut envoyer des "commandes moniteur" à Valgrind depuis un shell. Le noyau Valgrind fournit un ensemble de commandes moniteur Valgrind. Un outil peut éventuellement fournir des commandes moniteur spécifiques à l'outil, qui sont documentées dans le chapitre spécifique à l'outil.

--vgdb-error=<nombre> [défaut : 999999999]

Utilisez cette option lorsque le gdbserver Valgrind est activé avec --vgdb=oui ou --vgdb=complet. Les outils qui signalent des erreurs attendront que "nombre" erreurs soient signalées avant de figer le programme et d'attendre que vous vous connectiez avec GDB. Il s'ensuit qu'une valeur de zéro provoquera le démarrage du gdbserver avant l'exécution de votre programme. Ceci est généralement utilisé pour insérer des points d'arrêt GDB avant l'exécution, et fonctionne également avec les outils qui ne signalent pas d'erreurs, tels que Massif.

--vgdb-stop-at=<ensemble> [défaut : aucun]

Utilisez cette option lorsque le gdbserver Valgrind est activé avec --vgdb=oui ou --vgdb=complet. Le gdbserver Valgrind sera invoqué pour chaque erreur après que --vgdb-error ait été signalée. Vous pouvez en outre demander que le gdbserver Valgrind soit invoqué pour d'autres événements, spécifiés de l'une des manières suivantes :
•une liste séparée par des virgules d'un ou plusieurs de ces éléments : startup exit abexit valgrindabexit.

Les valeurs startup exit valgrindabexit indiquent respectivement d'invoquer gdbserver avant l'exécution de votre programme, après la dernière instruction de votre programme, lors de la sortie anormale de Valgrind (par exemple, erreur interne, manque de mémoire, ...).

L'option abexit est similaire à exit mais demande d'invoquer gdbserver uniquement lorsque votre application se termine anormalement (c'est-à-dire avec un code de sortie différent de 0).

Remarque : startup et --vgdb-error=0 demanderont tous deux l'invocation du gdbserver Valgrind avant l'exécution de votre programme. --vgdb-error=0 demandera en outre que votre programme s'arrête sur toutes les erreurs ultérieures.

•all pour spécifier l'ensemble complet. C'est équivalent à --vgdb-stop-at=startup,exit,abexit,valgrindabexit.
•none pour l'ensemble vide.

--track-fds=<oui|non|tous> [défaut : non]

Lorsque cette option est activée, Valgrind affichera une liste des descripteurs de fichiers ouverts à la sortie ou sur demande, via la commande moniteur gdbserver v.info open_fds. Avec chaque descripteur de fichier, il affiche une trace de la pile de l'endroit où le fichier a été ouvert et tous les détails relatifs au descripteur de fichier tels que le nom du fichier ou les détails du socket. Utilisez tous pour inclure le rapport sur stdin, stdout et stderr.

--modify-fds=<non|haut> [défaut : non]

Lorsque cette option est activée, lorsqu'un nouveau descripteur de fichier est ouvert par le programme, le descripteur de fichier disponible le plus élevé est retourné au lieu du plus bas.

--time-stamp=<oui|non> [défaut : non]

Lorsque cette option est activée, chaque message est précédé d'une indication du temps écoulé depuis le démarrage, exprimé en jours, heures, minutes, secondes et millisecondes.
onds.

--log-fd=<nombre> [par défaut : 2, stderr]

Spécifie que Valgrind doit envoyer tous ses messages au descripteur de fichier spécifié. La valeur par défaut, 2, est le canal d'erreur standard (stderr). Notez que cela peut interférer avec l'utilisation de stderr par le client lui-même, car la sortie de Valgrind sera entremêlée avec toute sortie que le client envoie à stderr.

--log-file=<nom_de_fichier>

Spécifie que Valgrind doit envoyer tous ses messages au fichier spécifié. Si le nom de fichier est vide, cela provoque un arrêt. Il existe trois spécificateurs de format spéciaux qui peuvent être utilisés dans le nom de fichier.

%p est remplacé par l'ID du processus actuel. Ceci est très utile pour les programmes qui invoquent plusieurs processus. ATTENTION : Si vous utilisez --trace-children=yes et que votre programme invoque plusieurs processus OU que votre programme effectue un fork sans appeler exec par la suite, et que vous n'utilisez pas ce spécificateur (ou le spécificateur %q ci-dessous), la sortie Valgrind de tous ces processus ira dans un seul fichier, potentiellement brouillé, et potentiellement incomplet. Note : Si le programme effectue un fork et appelle exec par la suite, la sortie Valgrind de l'enfant pendant la période entre le fork et l'exec sera perdue. Heureusement, cet intervalle est vraiment très court pour la plupart des programmes ; et les programmes modernes utilisent de toute façon posix_spawn.

%n est remplacé par un numéro de séquence de fichier unique pour ce processus. Ceci est utile pour les processus qui produisent plusieurs fichiers à partir du même modèle de nom de fichier.

%q{FOO} est remplacé par le contenu de la variable d'environnement FOO. Si la partie {FOO} est malformée, cela provoque un arrêt. Ce spécificateur est rarement nécessaire, mais très utile dans certaines circonstances (par exemple, lors de l'exécution de programmes MPI). L'idée est que vous spécifiez une variable qui sera définie différemment pour chaque processus du travail, par exemple BPROC_RANK ou tout autre élément applicable dans votre configuration MPI. Si la variable d'environnement nommée n'est pas définie, cela provoque un arrêt. Notez que dans certains shells, les caractères { et } peuvent devoir être échappés avec une barre oblique inverse.

%% est remplacé par %.

Si un % est suivi d'un autre caractère, cela provoque un arrêt.

Si le nom de fichier spécifie un nom de fichier relatif, il est placé dans le répertoire de travail initial du programme : c'est le répertoire courant lorsque le programme a commencé son exécution après le fork ou après l'exec. S'il spécifie un nom de fichier absolu (c'est-à-dire commence par '/'), il y est placé. là.

--log-socket=<adresse-ip:numéro-de-port>

Spécifie que Valgrind doit envoyer tous ses messages au port spécifié à l'adresse IP spécifiée. Le port peut être omis, auquel cas le port 1500 est utilisé. Si une connexion ne peut pas être établie au socket spécifié, Valgrind se rabat sur l'écriture de la sortie sur l'erreur standard (stderr). Cette option est destinée à être utilisée conjointement avec le programme valgrind-listener. Pour plus de détails, consultez le commentaire dans le manuel.

--enable-debuginfod=<non|oui> [par défaut : oui]

Lorsqu'il est activé, Valgrind tentera de télécharger les informations de débogage manquantes à partir des serveurs debuginfod si des URL de serveurs séparées par des espaces sont présentes dans la variable d'environnement $DEBUGINFOD_URLS. Cette option n'est prise en charge que sous Linux.

OPTIONS LIÉES AUX ERREURS

Ces options sont utilisées par tous les outils qui peuvent signaler des erreurs, par exemple, Memcheck, mais pas Cachegrind.

--xml=<oui|non> [par défaut : non]

Lorsqu'il est activé, les parties importantes de la sortie (par exemple, les messages d'erreur de l'outil) seront au format XML plutôt qu'en texte brut. De plus, la sortie XML sera envoyée à un canal de sortie différent de la sortie texte brut. Par conséquent, vous devez également utiliser l'une des options --xml-fd, --xml-file ou --xml-socket pour spécifier où le XML doit être envoyé.

Les messages moins importants seront toujours imprimés en texte brut, mais comme la sortie XML et la sortie texte brut sont envoyées à des canaux de sortie différents (la destination de la sortie texte brut est toujours contrôlée par --log-fd, --log-file et --log-socket), cela ne devrait pas causer de problèmes.

Cette option vise à faciliter la vie des outils qui utilisent la sortie de Valgrind comme entrée, tels que les interfaces graphiques. Actuellement, cette option fonctionne avec Memcheck, Helgrind et DRD. Le format de sortie est spécifié dans le fichier docs/internals/xml-output-protocol4.txt dans l'arborescence des sources pour Valgrind 3.5.0 ou ultérieur.

Les options recommandées pour une interface graphique sont : --xml=yes pour activer la sortie XML, --xml-file pour envoyer la sortie XML à un fichier (probablement sélectionné par l'interface graphique), --log-file pour envoyer la sortie texte brut à un deuxième fichier sélectionné par l'interface graphique, --child-silent-after-fork=yes, et -q pour limiter la sortie texte brut aux messages d'erreur critiques créés par Valgrind lui-même. Par exemple, l'échec de lecture d'un fichier de suppressions spécifié est considéré comme un message d'erreur critique. Ainsi, pour une exécution réussie, le fichier de sortie texte sera vide. Mais s'il n'est pas vide, il contiendra des informations importantes dont l'utilisateur de l'interface graphique devrait être informé.

--xml-fd=<nombre> [par défaut : -1, désactivé]

Spécifie que Valgrind doit envoyer sa sortie XML au descripteur de fichier spécifié. Il doit être utilisé conjointement avec --xml=yes.

--xml-file=<nom_de_fichier>

Spécifie que Valgrind doit envoyer sa sortie XML au fichier spécifié. Il doit être utilisé conjointement avec --xml=yes. Tous les séquences %p ou %q apparaissant dans le nom du fichier sont développées exactement de la même manière qu'elles le sont pour --log-file. Voir la description de --log-file pour plus de détails.

--xml-socket=<adresse-ip:numéro-de-port>

Spécifie que Valgrind doit envoyer sa sortie XML au port spécifié à l'adresse IP spécifiée. Il doit être utilisé conjointement avec --xml=yes. La forme de l'argument est la même que celle utilisée par --log-socket. Voir la description de --log-socket pour plus de détails.

--xml-user-comment=<chaîne>

Intègre une chaîne de commentaire utilisateur supplémentaire au début de la sortie XML. Ne fonctionne que lorsque --xml=yes est spécifié ; ignoré sinon.

--demangle=<oui|non> [par défaut : oui]

Active/désactive le démasquage automatique (décodage) des noms C++, D, Rust, Java, Ada. Activé par défaut. Lorsqu'il est activé, Valgrind tentera de traduire les noms encodés dans les langages listés pour revenir à quelque chose d'approchant l'original. Notez que l'outil callgrind désactive toujours le démasquage Ada afin de différencier les fonctions et procédures surchargées dans le graphe d'appels. Le démasqueur gère les symboles masqués par g++ versions 2.X, 3.X et 4.X.

Un fait important concernant le démasquage est que les noms de fonctions mentionnés dans les fichiers de suppressions doivent être sous leur forme masquée. Valgrind ne démasque pas les noms de fonctions lors de la recherche des suppressions applicables, car faire autrement rendrait le contenu des fichiers de suppressions dépendant de l'état de la machinerie de démasquage de Valgrind, et ralentirait également la correspondance des suppressions.

--num-callers=<nombre> [par défaut : 12]

Spécifie le nombre maximum d'entrées affichées dans les traces de pile qui identifient les emplacements des programmes. Notez que les erreurs sont groupées en utilisant uniquement les quatre emplacements de fonction supérieurs (l'endroit dans la fonction actuelle et ceux de ses trois appelants immédiats). Donc, cela n'affecte pas le nombre total d'erreurs signalées.

La valeur maximale est de 500. Notez que des paramètres plus élevés rendront Valgrind un peu plus lent et consommeront un peu plus de mémoire, mais peuvent être utiles lorsque vous travaillez avec des programmes ayant des chaînes d'appels profondément imbriquées.

--unw-stack-scan-thresh=<nombre> [par défaut : 0] , --unw-stack-scan-frames=<nombre> [par défaut : 5]

La prise en charge de l'analyse de la pile n'est disponible que sur les cibles ARM.

Ces indicateurs activent et contrôlent le déroulement de la pile par analyse de la pile. Lorsque les mécanismes normaux de déroulement de la pile - utilisation des enregistrements Dwarf CFI et suivi des pointeurs de frame - échouent, l'analyse de la pile peut permettre de récupérer une trace de pile.

Notez que l'analyse de la pile est un mécanisme imprécis et heuristique qui peut donner des résultats très trompeurs, ou aucun du tout. Elle ne doit être utilisée qu'en cas d'urgence, lorsque le déroulement normal échoue, et qu'il est néanmoins important d'avoir des traces de pile.

L'analyse de la pile est une technique simple : le dérouleur lit des mots de la pile et essaie de deviner lesquels pourraient être des adresses de retour, en vérifiant s'ils pointent juste après des instructions d'appel ARM ou Thumb. S'ils le font, le mot est ajouté à la trace.

Le principal danger survient lorsqu'un appel de fonction se termine, laissant son adresse de retour exposée, et qu'un nouveau fonction est appelée, mais que la nouvelle fonction ne remplace pas l'ancienne adresse. Le résultat est que la trace peut contenir des entrées pour des fonctions qui se sont déjà terminées, et être ainsi très confuse.

Une deuxième limitation de cette implémentation est qu'elle n'analysera que la page (4 Ko, normalement) contenant le pointeur de pile de départ. Si les frames de pile sont volumineux, cela peut entraîner seulement quelques frames (voire aucune) dans la trace. De plus, si vous n'avez pas de chance et que vous avez un pointeur de pile initial près de la fin de sa page parente, l'analyse pourrait manquer toutes les frames intéressantes.

Par défaut, l'analyse de la pile est désactivée. Le cas d'utilisation normal est de demander son activation lorsqu'une trace de pile serait autrement très courte. Ainsi, pour l'activer, utilisez --unw-stack-scan-thresh=nombre. Cela demande à Valgrind d'essayer d'utiliser l'analyse de la pile pour "étendre" les traces de pile qui contiennent moins de nombre de frames.

Si une analyse de pile a lieu, elle ne générera au maximum que le nombre de frames spécifié par --unw-stack-scan-frames. Typiquement, l'analyse de pile génère tellement d'entrées incorrectes que cette valeur est définie sur une petite valeur (5) par défaut. Dans aucun cas une trace de pile plus grande que la valeur spécifiée par --num-callers ne sera créée.

--error-limit=<oui|non> [par défaut : oui]

Lorsqu'il est activé, Valgrind arrête de signaler les erreurs après 10 000 000 au total, ou 1 000 différentes, ont été rencontrées. Ceci afin d'éviter que le mécanisme de suivi des erreurs ne devienne une surcharge de performance considérable dans les programmes comportant de nombreuses erreurs.

--error-exitcode=<nombre> [par défaut : 0]

Spécifie un code de sortie alternatif à retourner si Valgrind a signalé des erreurs lors de l'exécution. Lorsqu'il est défini sur la valeur par défaut (zéro), la valeur de retour de Valgrind sera toujours la valeur de retour du processus simulé. Lorsqu'il est défini sur une valeur non nulle, cette valeur est retournée à la place, si Valgrind détecte des erreurs. Ceci est utile pour utiliser Valgrind dans le cadre d'une suite de tests automatisés, car il permet de détecter facilement les cas de test pour lesquels Valgrind a signalé des erreurs, simplement en inspectant les codes de retour. Lorsque s
et vers une valeur non nulle et que Valgrind ne détecte aucune erreur, la valeur de retour de Valgrind sera la valeur de retour du programme simulé.

--exit-on-first-error=<yes|no> [par défaut : no]

Si cette option est activée, Valgrind s'arrête à la première erreur. Une valeur de sortie non nulle doit être définie à l'aide de l'option --error-exitcode. Utile si vous exécutez des tests de régression ou si vous avez d'autres mécanismes de test automatisés.

--error-markers=<begin>,<end> [par défaut : none]

Lorsque les erreurs sont affichées en texte brut (c'est-à-dire sans XML), --error-markers demande d'afficher une ligne contenant la chaîne begin (end) avant (après) chaque erreur.

Ces lignes de marqueur facilitent la recherche d'erreurs et/ou l'extraction d'erreurs dans un fichier de sortie qui contient des erreurs valgrind mélangées à la sortie du programme.

Notez que les marqueurs vides sont acceptés. Il est donc possible d'utiliser uniquement un marqueur de début (ou de fin).

--show-error-list=no|yes|all [par défaut : no]

Si cette option est 'yes', pour les outils qui signalent des erreurs, valgrind affichera la liste des erreurs détectées et la liste des suppressions utilisées à la sortie. La valeur 'all' indique d'afficher également la liste des erreurs supprimées.

Notez qu'à la verbosité 2 et plus, valgrind affiche automatiquement la liste des erreurs détectées et la liste des suppressions utilisées à la sortie, sauf si --show-error-list=no est sélectionné.

-s

Spécifier -s est équivalent à --show-error-list=yes.

--sigill-diagnostics=<yes|no> [par défaut : yes]

Active/désactive l'affichage des diagnostics d'instruction illégale. Activé par défaut, mais désactivé par défaut lorsque --quiet est utilisé. Le comportement par défaut peut toujours être explicitement remplacé en donnant cette option.

Lorsque cette option est activée, un message d'avertissement sera affiché, ainsi que des diagnostics, chaque fois qu'une instruction que Valgrind ne peut pas décoder ou traduire est rencontrée, avant que le programme ne reçoive un signal SIGILL. Souvent, une instruction illégale indique un bug dans le programme ou un support manquant pour l'instruction particulière dans Valgrind. Mais certains programmes essaient délibérément d'exécuter une instruction qui pourrait manquer et piègent le signal SIGILL pour détecter les fonctionnalités du processeur. L'utilisation de ce drapeau permet d'éviter la sortie de diagnostic que vous obtiendriez autrement dans de tels cas.

--keep-debuginfo=<yes|no> [par défaut : no]

Lorsque cette option est activée, conservez ("archivez") les symboles et toutes les autres informations de débogage pour le code déchargé. Cela permet aux traces de pile sauvegardées d'inclure des informations de fichier/ligne pour le code qui a été dlclose'd (ou similaire). Faites attention à cela, car cela peut entraîner une utilisation illimitée de la mémoire pour les programmes qui chargent et déchargent de manière répétée des objets partagés.

Certains outils et certaines fonctionnalités ont un support limité pour les informations de débogage archivées. Memcheck le prend entièrement en charge. Généralement, les outils qui signalent des erreurs peuvent utiliser les informations de débogage archivées pour afficher les traces de pile des erreurs. Les limitations connues sont : la trace d'accès passée des conditions de concurrence de Helgrind n'utilise pas les informations de débogage archivées. Massif (et plus généralement le format de sortie Massif xtree) n'utilise pas les informations de débogage archivées. Seul Memcheck a été (dans une certaine mesure) testé avec --keep-debuginfo=yes, donc d'autres outils peuvent avoir des limitations inconnues.

--show-below-main=<yes|no> [par défaut : no]

Par défaut, les traces de pile pour les erreurs n'affichent pas les fonctions qui apparaissent sous main car il s'agit le plus souvent de choses de la bibliothèque C sans intérêt et/ou incompréhensibles. Alternativement, si main n'est pas présent dans la trace de pile, les traces de pile n'afficheront aucune fonction sous les fonctions de type main comme __libc_start_main de glibc. De plus, si des fonctions de type main sont présentes dans la trace, elles sont normalisées en (below main), afin de rendre la sortie plus déterministe.

Si cette option est activée, toutes les entrées de la trace de pile seront affichées et les fonctions de type main ne seront pas normalisées.

--fullpath-after=<string> [par défaut : n'affiche pas les chemins sources]

Par défaut, Valgrind n'affiche que les noms de fichiers dans les traces de pile, mais pas les chemins complets vers les fichiers sources. Lors de l'utilisation de Valgrind dans de grands projets où les sources résident dans plusieurs répertoires différents, cela peut être gênant. --fullpath-after offre une solution flexible à ce problème. Lorsque cette option est présente, le chemin de chaque fichier source est affiché, avec la mise en garde importante suivante : si string est trouvé dans le chemin, alors le chemin jusqu'à et y compris string est omis, sinon le chemin est affiché sans modification. Notez que string n'est pas obligé d'être un préfixe du chemin.

Par exemple, considérons un fichier nommé /home/janedoe/blah/src/foo/bar/xyzzy.c. Spécifier --fullpath-after=/home/janedoe/blah/src/ amènera Valgrind à afficher le nom comme foo/bar/xyzzy.c.

Parce que la chaîne n'est pas obligée d'être un préfixe, --fullpath-after=src/ produira le même résultat. Ceci est utile lorsque le chemin contient des caractères générés par machine arbitraires. Par exemple, le chemin /my/build/dir/C32A1B47/blah/src/foo/xyzzy peut être réduit à foo/xyzzy en utilisant --fullpath-after=/blah/src/.

Si vous souhaitez simplement voir le chemin complet, spécifiez une chaîne vide : --fullpath-after=. Ce n'est pas un cas spécial, simplement une conséquence logique des règles ci-dessus.

Enfin, vous pouvez utiliser --fullpath-after plusieurs fois. Toute apparition de celui-ci amène Valgrind à passer à l'affichage des chemins complets et à l'application de la règle de filtrage ci-dessus. Chaque chemin produit est comparé à toutes les chaînes spécifiées par --fullpath-after, dans l'ordre spécifié. La première chaîne correspondante entraîne la troncature du chemin comme décrit ci-dessus. Si aucune ne correspond, le chemin complet est affiché. Cela facilite la suppression des préfixes lorsque les sources proviennent d'un certain nombre de répertoires non liés.

--extra-debuginfo-path=<path> [par défaut : indéfini et non utilisé]

Par défaut, Valgrind recherche dans plusieurs chemins bien connus les objets de débogage, tels que /usr/lib/debug/.

Cependant, il peut y avoir des scénarios où vous souhaiteriez placer les objets de débogage à un emplacement arbitraire, tel qu'un stockage externe lors de l'exécution de Valgrind sur un appareil mobile avec un espace de stockage local limité. Un autre exemple pourrait être une situation où vous n'avez pas l'autorisation d'installer des packages d'objets de débogage sur le système où vous exécutez Valgrind.

Dans ces scénarios, vous pouvez fournir un chemin absolu comme emplacement supplémentaire et final où Valgrind doit rechercher les objets de débogage en spécifiant --extra-debuginfo-path=/chemin/vers/objets/de/debogage. Le chemin donné sera ajouté au début du nom de chemin absolu de l'objet recherché. Par exemple, si Valgrind recherche les informations de débogage pour /w/x/y/zz.so et que --extra-debuginfo-path=/a/b/c est spécifié, il recherchera un objet de débogage à /a/b/c/w/x/y/zz.so.

Ce drapeau ne doit être spécifié qu'une seule fois. S'il est spécifié plusieurs fois, seule la dernière instance est prise en compte.

--debuginfo-server=ipaddr:port [par défaut : indéfini et non utilisé]

Il s'agit d'une nouvelle fonctionnalité expérimentale introduite dans la version 3.9.0.

Dans certains scénarios, il peut être pratique de lire les informations de débogage à partir d'objets stockés sur une machine différente. Avec ce drapeau, Valgrind interrogera un serveur d'informations de débogage exécuté sur ipaddr et écoutant sur le port port, s'il ne trouve pas l'objet d'informations de débogage dans le système de fichiers local.

Le serveur d'informations de débogage doit accepter les connexions TCP sur le port port. Le serveur d'informations de débogage est contenu dans le fichier source auxprogs/valgrind-di-server.c. Il ne servira que depuis le répertoire dans lequel il est démarré. Le port est par défaut à 1500 dans le client et le serveur si non spécifié.

Si Valgrind recherche les informations de débogage pour /w/x/y/zz.so en utilisant le serveur d'informations de débogage, il supprimera les composants du chemin et ne demandera que zz.so sur le serveur. Celui-ci recherchera alors uniquement dans son répertoire de travail actuel un objet d'informations de débogage correspondant.

Les données d'informations de débogage sont transmises en petits fragments (8 Ko) tels que demandés par Valgrind. Chaque bloc est compressé à l'aide de LZO pour réduire le temps de transmission. L'implémentation a été optimisée pour de meilleures performances sur une liaison réseau 802.11g (WiFi) à un seul étage.

Notez que les vérifications de correspondance entre les objets principaux et de débogage, utilisant le schéma CRC de debuglink GNU, sont effectuées même lors de l'utilisation du serveur d'informations de débogage. Pour désactiver ces vérifications, vous devez également spécifier --allow-mismatched-debuginfo=yes.

Par défaut, le système de build Valgrind compilera valgrind-di-server pour la plateforme cible, ce qui n'est presque certainement pas ce que vous voulez. Jusqu'à présent, nous n'avons pas réussi à trouver comment faire compiler par automake/autoconf pour la plateforme de build. Si vous souhaitez l'utiliser, vous devrez le recompiler manuellement en utilisant la commande indiquée en haut de auxprogs/valgrind-di-server.c.

Valgrind peut également télécharger des informations de débogage via debuginfod. Voir la section DEBUGINFOD pour plus d'informations.

--allow-mismatched-debuginfo=no|yes [no]

Lors de la lecture d'informations de débogage à partir d'objets de débogage séparés, Valgrind vérifiera par défaut que les objets principaux et de débogage correspondent, en utilisant le mécanisme GNU debuglink. Cela garantit qu'il ne lit pas les informations de débogage à partir d'objets de débogage obsolètes, et garantit également que Valgrind ne peut pas planter en raison de décalages.

Cette vérification peut être remplacée en utilisant --allow-mismatched-debuginfo=yes. Cela peut être utile lorsque les objets de débogage et principaux n'ont pas été séparés de la manière appropriée. Soyez prudent lors de l'utilisation de ceci, cependant : cela désactive toutes les vérifications de cohérence, et Valgrind a été observé planter lorsque les objets principaux et de débogage ne correspondent pas.

--suppressions=<filename> [par défaut : $PREFIX/lib/valgrind/default.supp]

Spécifie un fichier supplémentaire à partir duquel lire les descriptions d'erreurs à supprimer. Vous pouvez utiliser jusqu'à 100 fichiers de suppression supplémentaires.

--gen-suppressions=<yes|no|all> [par défaut : no]

Lorsqu'il est défini sur yes, Valgrind fera une pause après chaque erreur affichée et affichera la ligne : 
---- Afficher la suppression ? --- [Retour/N/n/Y/y/C/c] ----

Appuyer sur Entrée, ou N Entrée ou n Entrée, amène Valgrind à continuer l'exécution sans afficher de suppression pour cette erreur.

Appuyer sur Y Entrée ou y Entrée amène Valgrind à écrire une suppression pour cette erreur. Vous pouvez ensuite la copier-coller dans un fichier de suppression si vous ne souhaitez plus entendre parler de cette erreur à l'avenir.

Lorsqu'il est défini sur all, Valgrind affichera une suppression pour chaque erreur signalée, sans interroger l'utilisateur.

Cette option est particulièrement utile avec les programmes C++, car elle affiche les suppressions avec les noms déformés (mangled names), comme requis.

Notez que les suppressions affichées sont aussi spécifiques que possible. Vous pourriez vouloir regrouper des suppressions similaires, en ajoutant des caractères génériques aux fonctions na

mes, et en utilisant des caractères génériques au niveau de l'image. Les facilités de caractères génériques sont puissantes mais flexibles, et avec un peu d'édition soignée, vous pourrez peut-être supprimer toute une famille d'erreurs apparentées avec seulement quelques suppressions.

Parfois, deux erreurs différentes sont supprimées par la même suppression, dans ce cas Valgrind affichera la suppression plus d'une fois, mais vous n'avez besoin que d'une copie dans votre fichier de suppressions (mais en avoir plus d'une ne causera pas de problèmes). De plus, le nom de la suppression est donné sous la forme <insérer un nom de suppression ici>; le nom n'a pas vraiment d'importance, il n'est utilisé qu'avec l'option -v qui affiche tous les enregistrements de suppression utilisés.

--input-fd=<nombre> [défaut : 0, stdin]

Lorsque vous utilisez --gen-suppressions=yes, Valgrind s'arrêtera pour lire les entrées du clavier de votre part à chaque occurrence d'erreur. Par défaut, il lit depuis l'entrée standard (stdin), ce qui pose problème pour les programmes qui ferment stdin. Cette option vous permet de spécifier un descripteur de fichier alternatif à partir duquel lire l'entrée.

--dsymutil=no|yes [yes]

Cette option n'est pertinente que lorsque vous exécutez Valgrind sur macOS.

macOS utilise un schéma de liaison de débogage différé (debuginfo). Lorsque les fichiers objets contenant des informations de débogage sont liés dans une .dylib ou un exécutable, les informations de débogage ne sont pas copiées dans le fichier final. Au lieu de cela, les informations de débogage doivent être liées manuellement en exécutant dsymutil, un utilitaire fourni par le système, sur l'exécutable ou la .dylib. Les informations de débogage combinées résultantes sont placées dans un répertoire à côté de l'exécutable ou de la .dylib, mais avec l'extension .dSYM.

Avec --dsymutil=no, Valgrind détectera les cas où le répertoire .dSYM est soit manquant, soit présent mais ne semble pas correspondre à l'exécutable ou à la .dylib associée, très probablement parce qu'il est obsolète. Dans ces cas, Valgrind affichera un message d'avertissement mais ne prendra aucune autre mesure.

Avec --dsymutil=yes, Valgrind exécutera automatiquement dsymutil, si nécessaire, pour mettre à jour les informations de débogage. Dans la pratique, si vous utilisez toujours --dsymutil=yes, il n'y aura jamais besoin d'exécuter dsymutil manuellement ou dans le cadre du système de build de vos applications, car Valgrind l'exécutera au besoin.

Valgrind n'essaiera pas d'exécuter dsymutil sur des exécutables ou bibliothèques dans /usr/, /bin/, /sbin/, /opt/, /sw/, /System/, /Library/ ou /Applications/ car dsymutil échouera toujours dans de telles situations. Il échoue à la fois parce que les informations de débogage pour ces composants système préinstallés ne sont disponibles nulle part, et aussi parce que cela nécessiterait des privilèges d'écriture dans ces répertoires.

Soyez prudent lorsque vous utilisez --dsymutil=yes, car cela entraînera la suppression et la recréation silencieuses des répertoires .dSYM préexistants. Notez également que dsymutil est assez lent, parfois excessivement.

--max-stackframe=<nombre> [défaut : 2000000]

La taille maximale d'une image de pile. Si le pointeur de pile se déplace de plus que ce montant, Valgrind supposera que le programme bascule vers une autre pile.

Vous devrez peut-être utiliser cette option si votre programme a de grands tableaux alloués sur la pile. Valgrind garde une trace du pointeur de pile de votre programme. S'il change de plus que le seuil, Valgrind suppose que votre programme bascule vers une autre pile, et Memcheck se comporte différemment de ce qu'il ferait pour un changement de pointeur de pile inférieur au seuil. Habituellement, cette heuristique fonctionne bien. Cependant, si votre programme alloue de grandes structures sur la pile, cette heuristique sera trompée, et Memcheck signalera par la suite un grand nombre d'accès à la pile invalides. Cette option vous permet de modifier le seuil à une valeur différente.

Vous ne devriez envisager d'utiliser cette option que si la sortie de débogage de Valgrind vous y dirige. Dans ce cas, elle vous indiquera le nouveau seuil que vous devriez spécifier.

En général, allouer de grandes structures sur la pile est une mauvaise idée, car vous pouvez facilement manquer d'espace de pile, en particulier sur les systèmes avec une mémoire limitée ou qui s'attendent à prendre en charge un grand nombre de threads ayant chacun une petite pile, et aussi parce que la vérification des erreurs effectuée par Memcheck est plus efficace pour les données allouées sur le tas que pour les données allouées sur la pile. Si vous devez utiliser cette option, vous pourriez envisager de réécrire votre code pour allouer sur le tas plutôt que sur la pile.

--main-stacksize=<nombre> [défaut : utilise la valeur 'ulimit' actuelle]

Spécifie la taille de la pile du thread principal.

Pour simplifier sa gestion de la mémoire, Valgrind réserve tout l'espace requis pour la pile du thread principal au démarrage. Cela signifie qu'il a besoin de connaître la taille de pile requise au démarrage.

Par défaut, Valgrind utilise la valeur actuelle de « ulimit » pour la taille de la pile, ou 16 Mo, le plus bas des deux. Dans de nombreux cas, cela donne une taille de pile comprise entre 8 et 16 Mo, ce qui ne dépasse presque jamais pour la plupart des applications.

Si vous avez besoin d'une taille de pile totale plus grande, utilisez --main-stacksize pour la spécifier. Ne la réglez qu'aussi haut que nécessaire, car réserver beaucoup plus d'espace que nécessaire (c'est-à-dire des centaines de mégaoctets de plus que nécessaire) contraint les allocateurs de mémoire de Valgrind et peut réduire la quantité totale de mémoire que Valgrind peut utiliser. Ceci n'est vraiment significatif que sur les machines 32 bits.

Sur Linux, vous pouvez demander une pile d'une taille allant jusqu'à 2 Go. Valgrind s'arrêtera avec un message de diagnostic si la pile ne peut pas être allouée.

--main-stacksize n'affecte que la taille de la pile du thread initial du programme. Il n'a aucune incidence sur la taille des piles de threads, car Valgrind ne les alloue pas.

Vous pourriez avoir besoin d'utiliser à la fois --main-stacksize et --max-stackframe ensemble. Il est important de comprendre que --main-stacksize définit la taille totale maximale de la pile, tandis que --max-stackframe spécifie la taille la plus grande de toute image de pile individuelle. Vous devrez déterminer vous-même la valeur de --main-stacksize (généralement, si votre application se termine de manière anormale). Mais Valgrind vous indiquera la taille --max-stackframe nécessaire, si nécessaire.

Comme expliqué plus en détail dans la description de --max-stackframe, une exigence de pile volumineuse est un signe de problèmes de portabilité potentiels. Il est fortement conseillé de placer toutes les données volumineuses dans de la mémoire allouée sur le tas.

--max-threads=<nombre> [défaut : 500]

Par défaut, Valgrind peut gérer jusqu'à 500 threads. Parfois, ce nombre est trop faible. Utilisez cette option pour fournir une limite différente. Par exemple : --max-threads=3000.

--realloc-zero-bytes-frees=yes|no [défaut : yes pour glibc no sinon]

Le comportement de realloc() avec une taille de zéro est défini par l'implémentation dans C17 et indéfini dans C23. Valgrind essaie de fonctionner de la même manière que le système sous-jacent et la bibliothèque d'exécution C sur lesquels il a été configuré et construit. Cependant, si vous utilisez une bibliothèque d'exécution C différente, ce défaut peut être incorrect. Si la valeur est yes, alors realloc désallouera la mémoire et retournera NULL. Si la valeur est no, alors realloc ne désallouera pas la mémoire et la taille sera traitée comme s'il s'agissait d'un octet.

À titre d'exemple, si vous utilisez Valgrind installé via un paquet sur une distribution Linux utilisant GNU libc, mais que vous liez votre exécutable de test avec musl libc ou la bibliothèque JEMalloc, envisagez d'utiliser --realloc-zero-bytes-frees=no.

Address Sanitizer a une option similaire et encore plus verbeuse allocator_frees_and_returns_null_on_realloc_zero.

OPTIONS LIÉES À MALLOC()

Pour les outils qui utilisent leur propre version de malloc (par exemple, Memcheck, Massif, Helgrind, DRD), les options suivantes s'appliquent.

--alignment=<nombre> [défaut : 8 ou 16, selon la plateforme]

Par défaut, le malloc, realloc, etc. de Valgrind renvoient un bloc dont l'adresse de départ est alignée sur 8 octets ou sur 16 octets (la valeur dépend de la plateforme et correspond au défaut de la plateforme). Cette option vous permet de spécifier un alignement différent. La valeur fournie doit être supérieure ou égale au défaut, inférieure ou égale à 4096, et doit être une puissance de deux.

--redzone-size=<nombre> [défaut : dépend de l'outil]

Le malloc, realloc, etc. de Valgrind ajoutent des blocs de rembourrage avant et après chaque bloc de tas alloué par le programme en cours d'exécution. Ces blocs de rembourrage sont appelés zones rouges. La valeur par défaut de la taille de la zone rouge dépend de l'outil. Par exemple, Memcheck ajoute et protège un minimum de 16 octets avant et après chaque bloc alloué par le client. Cela lui permet de détecter les sous-dépassements ou surdépassements de bloc jusqu'à 16 octets.

Augmenter la taille de la zone rouge permet de détecter des surdépassements de distances plus grandes, mais augmente la quantité de mémoire utilisée par Valgrind. Diminuer la taille de la zone rouge réduira la mémoire nécessaire à Valgrind mais réduira également les chances de détecter les sur/sous-dépassements, ce qui n'est donc pas recommandé.

--xtree-memory=none|allocs|full [none]

Les outils qui remplacent le malloc, realloc, etc. de Valgrind peuvent éventuellement produire un arbre d'exécution détaillant quel morceau de code est responsable de l'utilisation de la mémoire du tas. Voir Arbres d'exécution pour une explication détaillée des arbres d'exécution.

Lorsqu'il est défini sur none, aucun arbre d'exécution mémoire n'est produit.

Lorsqu'il est défini sur allocs, l'arbre d'exécution mémoire donne le nombre actuel d'octets alloués et le nombre actuel de blocs alloués.

Lorsqu'il est défini sur full, l'arbre d'exécution mémoire donne 6 mesures différentes : le nombre actuel d'octets et de blocs alloués (mêmes valeurs que pour allocs), le nombre total d'octets et de blocs alloués, le nombre total d'octets et de blocs libérés.

Notez que la surcharge en CPU et en mémoire pour produire un xtree dépend de l'outil. La surcharge en CPU est faible pour la valeur allocs, car les informations nécessaires pour produire ce rapport sont maintenues dans tous les cas par l'outil. Pour massif et helgrind, spécifier full implique de capturer une trace de pile pour chaque opération de libération, alors qu'habituellement ces outils ne capturent qu'une trace de pile d'allocation. Pour Memcheck, la surcharge CPU pour la valeur full est faible, car cela ne peut être utilisé qu'en combinaison avec --keep-stacktraces=alloc-and-free ou --keep-stacktraces=alloc-then-free, qui enregistre déjà une trace de pile pour chaque opération de libération. La surcharge mémoire varie entre 5 et 10 mots par trace de pile unique dans l'xtree, plus la mémoire nécessaire pour enregistrer la trace de pile pour les opérations de libération, si nécessaire spécifiquement pour l'xtree.

--xtree-memory-file=<nom de fichier> [défaut : xtmemory.kcg.%p]

Spécifie que Valgrind doit produire le rapport d'arbre mémoire xtree dans le fichier spécifié. Toute séquence %p ou %q apparaissant dans le nom de fichier est développée exactement de la même manière qu'elle l'est pour --log-file. Voir la description de --log-file pour plus de détails.

Si le nom de fichier contient l'extension .ms, alors le format de fichier produit sera un format de fichier de sortie massif. Si le nom de fichier contient l'extension .kcg ou si aucune extension n'est fournie ou reconnue, alors le format de fichier produit sera un format de sortie callgrind.

Voir Arbres d'exécution pour une explication détaillée sur les formats d'arbres d'exécution.

OPTIONS PEU COMMUNES

Ces options s'appliquent à tous les outils, car elles affectent certains fonctionnements obscurs du noyau Valgrind. La plupart des gens n'auront pas besoin de les utiliser.

--smc-check=<none|stack|all|all-non-file> [défaut : all-non-file pour x86/amd64/s390x, stack pour les autres architectures]

Cette option contrôle la détection par Valgrind du code auto-modifiant. Si aucun contrôle n'est effectué, lorsqu'un programme exécute du code, puis le remplace par du nouveau code, et exécute le nouveau code, Valgrind continuera à exécuter les traductions qu'il a faites pour l'ancien code. Cela conduira probablement à un comportement incorrect et/ou à des plantages.

Pour les architectures "modernes" -- tout ce qui n'est pas x86, amd64 ou s390x -- la valeur par défaut est stack. C'est parce qu'un programme correct doit prendre des mesures explicites pour rétablir la cohérence du cache D-I après la modification du code. Valgrind observe et respecte de telles actions, avec pour résultat que le code auto-modifiant est géré de manière transparente sans coût supplémentaire.

Pour x86, amd64 et s390x, le programme n'est pas tenu de notifier le matériel de la synchronisation requise de la cohérence D-I. Par conséquent, la valeur par défaut est all-non-file, qui couvre le cas normal de génération de code dans une zone mappée mmap'd anonyme (non sauvegardée sur fichier).

La signification des quatre paramètres disponibles est la suivante. Aucune détection (none), détection de code auto-modifiant sur la pile (utilisée par GCC pour implémenter les fonctions imbriquées) (stack), détection de code auto-modifiant partout (all), et détection de code auto-modifiant partout sauf dans les mappages sauvegardés sur fichier (all-non-file).

L'exécution avec all ralentira Valgrind de manière notable. L'exécution avec none accélérera rarement les choses, car très peu de code est généré dynamiquement dans la plupart des programmes. La requête client VALGRIND_DISCARD_TRANSLATIONS est une alternative à --smc-check=all et --smc-check=all-non-file qui demande plus d'efforts au programmeur mais permet à Valgrind d'exécuter votre programme plus rapidement, en lui indiquant précisément quand les traductions doivent être refaites.

--smc-check=all-non-file offre une version moins coûteuse mais plus limitée de --smc-check=all. Elle ajoute des vérifications à toutes les traductions qui ne proviennent pas de mappages mémoire sauvegardés sur fichier. Les applications typiques qui génèrent du code, par exemple les JIT dans les navigateurs Web, génèrent du code dans des zones mmap'd anonymes, tandis que le code "fixe" du navigateur réside toujours dans des mappages sauvegardés sur fichier. --smc-check=all-non-file tire parti de cette observation, limitant la surcharge de vérification au code susceptible d'être généré par JIT.

--run-libc-freeres=<yes|no> [défaut : yes]

Cette option n'est pertinente que lors de l'exécution de Valgrind sous Linux avec GNU libc.

La bibliothèque C GNU (libc.so), utilisée par tous les programmes, peut allouer de la mémoire pour ses propres usages. Habituellement, elle ne prend pas la peine de libérer cette mémoire lorsque le programme se termine—cela n'aurait aucun intérêt, car le noyau Linux récupère toutes les ressources du processus lorsqu'un processus se termine de toute façon, donc cela ne ferait que ralentir les choses.

Les auteurs de glibc ont réalisé que ce comportement entraîne des vérificateurs de fuites, tels que Valgrind, à signaler à tort des fuites dans glibc, lorsqu'une vérification de fuite est effectuée à la sortie. Afin d'éviter cela, ils ont fourni une routine appelée __libc_freeres spécifiquement pour que glibc libère toute la mémoire qu'elle a allouée. Memcheck essaie donc d'exécuter __libc_freeres à la sortie.

Malheureusement, dans certaines versions très anciennes de glibc, __libc_freeres est suffisamment buggé pour provoquer des fautes de segmentation. Cela a été particulièrement visible sur Red Hat 7.1. Cette option est donc fournie pour interdire l'exécution de __libc_freeres. Si votre programme semble fonctionner correctement sous Valgrind, mais se termine par une faute de segmentation, vous pourriez constater que --run-libc-freeres=no résout ce problème, bien qu'au prix de signaler éventuellement à tort des fuites d'espace dans libc.so.

--run-cxx-freeres=<yes|no> [défaut : yes]

Cette option n'est pertinente que lors de l'exécution de programmes C++ Valgrind sous Linux, FreeBSD ou Solaris utilisant libstdc++.

La bibliothèque C++ Standard GNU (libstdc++.so), utilisée par tous les programmes C++ compilés avec g++, peut allouer de la mémoire pour ses propres usages. Habituellement, elle ne se soucie pas de libérer cette mémoire lorsque le programme se termine—cela n'aurait aucun sens, car le noyau récupère toutes les ressources du processus lorsqu'un processus se termine de toute façon, donc cela ne ferait que ralentir les choses.

Les auteurs de gcc ont réalisé que ce comportement entraîne les vérificateurs de fuites, tels que Valgrind, à signaler à tort des fuites dans libstdc++, lorsqu'une vérification de fuite est effectuée à la sortie. Afin d'éviter cela, ils ont fourni une routine appelée __gnu_cxx::__freeres spécifiquement pour que libstdc++ libère toute la mémoire qu'elle a allouée. Memcheck essaie donc d'exécuter __gnu_cxx::__freeres à la sortie.

Pour des raisons de flexibilité et en raison de problèmes imprévus avec __gnu_cxx::__freeres, l'option --run-cxx-freeres=no existe, bien qu'au prix de signaler éventuellement à tort des fuites d'espace dans libstdc++.so.

--sim-hints=hint1,hint2,...

Passe des indices divers à Valgrind qui modifient légèrement le comportement simulé de manière non standard ou dangereuse, potentiellement pour aider à la simulation de fonctionnalités étranges. Par défaut, aucun indice n'est activé. À utiliser avec prudence ! Les indices actuellement connus sont :
•lax-ioctls : Soyez très laxiste dans la gestion des ioctl ; la seule hypothèse est que la taille est correcte. Ne nécessite pas que le tampon complet soit initialisé lors de l'écriture. Sans cela, utiliser certains pilotes de périphériques avec un grand nombre de commandes ioctl étranges devient très fastidieux.
•fuse-compatible : Activez un traitement spécial pour certains appels système qui peuvent se bloquer dans un système de fichiers FUSE. Cela peut être nécessaire lors de l'exécution de Valgrind sur un programme multi-thread qui utilise un thread pour
manage un système de fichiers FUSE et un autre thread pour y accéder.
•enable-outer: Active une magie spéciale nécessaire lorsque le programme exécuté est lui-même Valgrind.
•no-inner-prefix: Désactive l'affichage d'un préfixe > devant chaque ligne de sortie stdout ou stderr dans un Valgrind interne exécuté par un Valgrind externe. Ceci est utile lors de l'exécution des tests de régression Valgrind dans une configuration externe/interne. Notez que le préfixe > sera toujours affiché devant les lignes de journalisation de débogage internes.
•no-nptl-pthread-stackcache: Cet indice n'est pertinent que lors de l'exécution de Valgrind sous Linux ; il est ignoré sous FreeBSD, Solaris et macOS.

La bibliothèque pthread GNU glibc (libpthread.so), utilisée par les programmes pthread, maintient un cache de piles pthread. Lorsqu'un pthread se termine, la mémoire utilisée pour la pile pthread et certaines structures de données liées au stockage local des threads ne sont pas toujours directement libérées. Cette mémoire est conservée dans un cache (jusqu'à une certaine taille) et réutilisée si un nouveau thread est démarré.

Ce cache entraîne des erreurs de condition de concurrence (race condition) faussement positives signalées par l'outil helgrind sur cette mémoire mise en cache, car helgrind ne comprend pas les primitives de synchronisation internes du cache de glibc. Ainsi, lors de l'utilisation d'helgrind, la désactivation du cache permet d'éviter les fausses détections de conditions de concurrence, en particulier lors de l'utilisation de variables de stockage local de threads (par exemple, les variables utilisant le qualificateur __thread).

Lors de l'utilisation de l'outil memcheck, la désactivation du cache garantit que la mémoire utilisée par glibc pour gérer les variables __thread est directement libérée lorsqu'un thread se termine.

Remarque : Valgrind désactive le cache en utilisant des connaissances internes de l'implémentation du cache de piles de glibc et en examinant les informations de débogage de la bibliothèque pthread. Cette technique est donc quelque peu fragile et peut ne pas fonctionner pour toutes les versions de glibc. Cela a été testé avec succès avec diverses versions de glibc (par exemple, 2.11, 2.16, 2.18) sur diverses plateformes.

•lax-doors: (Solaris uniquement) Soyez très laxiste concernant la gestion des appels système de portes sur des descripteurs de fichiers de portes non reconnus. Ne nécessite pas que le tampon complet soit initialisé lors de l'écriture. Sans cela, les programmes utilisant la fonctionnalité libdoor(3LIB) avec des sémantiques entièrement propriétaires peuvent signaler un grand nombre de faux positifs.
•fallback-llsc: (MIPS et ARM64 uniquement) : Active une implémentation alternative des instructions Load-Linked (LL) et Store-Conditional (SC). L'implémentation standard donne un comportement plus correct, mais peut entraîner une boucle infinie sur certaines implémentations de processeurs qui ne tolèrent pas les références mémoire supplémentaires entre LL et SC. Jusqu'à présent, cela n'est connu que sur les cœurs Cavium 3. Vous ne devriez pas avoir besoin d'utiliser cet indicateur, car les cœurs pertinents sont détectés au démarrage et l'implémentation alternative est activée automatiquement si nécessaire. Il n'y a pas d'anti-indicateur équivalent : vous ne pouvez pas forcer la désactivation de l'implémentation alternative si elle est automatiquement activée. Le problème sous-jacent réside dans le fait que l'implémentation "standard" de LL et SC est réalisée en copiant les instructions LL et SC dans le code instrumenté. Cependant, les outils peuvent insérer des références mémoire d'instrumentation supplémentaires entre les instructions LL et SC. Ces références mémoire ne sont pas présentes dans le code original non instrumenté, et leur présence dans le code instrumenté peut entraîner l'échec persistant des instructions SC, conduisant à une boucle infinie dans les blocs LL-SC. L'implémentation alternative donne un comportement correct des instructions LL et SC entre les threads d'un processus, y compris le scénario ABA. Elle donne également un comportement correct entre un thread Valgrind et un thread non-Valgrind exécuté dans un processus différent, qui communiquent via une mémoire partagée, mais uniquement jusqu'au comportement CAS correct - dans ce cas, le scénario ABA peut ne pas être correctement géré.

--scheduling-quantum=<nombre> [défaut : 100000]

L'option --scheduling-quantum contrôle le nombre maximum de blocs de base exécutés par un thread avant de libérer le verrou utilisé par Valgrind pour sérialiser l'exécution des threads. Des valeurs plus petites donnent un entrelacement plus fin mais augmentent la surcharge de planification. Un entrelacement plus fin peut être utile pour reproduire les conditions de concurrence avec helgrind ou DRD. Pour plus de détails sur le schéma de sérialisation des threads de Valgrind et son impact sur les performances et la planification des threads, voir Scheduling and Multi-Thread Performance.

--fair-sched=<no|yes|try> [défaut : no]

L'option --fair-sched contrôle le mécanisme de verrouillage utilisé par Valgrind pour sérialiser l'exécution des threads. Le mécanisme de verrouillage contrôle la manière dont les threads sont planifiés, et différents réglages offrent différents compromis entre l'équité et les performances. Pour plus de détails sur le schéma de sérialisation des threads de Valgrind et son impact sur les performances et la planification des threads, voir Scheduling and Multi-Thread Performance.
•La valeur --fair-sched=yes active un planificateur équitable. En bref, si plusieurs threads sont prêts à s'exécuter, les threads seront planifiés en mode tour de rôle. Ce mécanisme n'est pas disponible sur toutes les plateformes ou toutes les versions de Linux. S'il n'est pas disponible, l'utilisation de --fair-sched=yes entraînera l'arrêt de Valgrind avec une erreur.

Vous trouverez peut-être que ce réglage améliore la réactivité globale si vous exécutez un programme interactif multithreadé, par exemple un navigateur Web, sur Valgrind.

•La valeur --fair-sched=try active la planification équitable si elle est disponible sur la plateforme. Sinon, elle se rabattra automatiquement sur --fair-sched=no.
•La valeur --fair-sched=no active un planificateur qui ne garantit pas l'équité entre les threads prêts à s'exécuter, mais qui offre généralement les meilleures performances.

--kernel-variant=variant1,variant2,...

Gère les appels système et les ioctls provenant de variantes mineures du noyau par défaut pour cette plateforme. Ceci est utile pour exécuter sur des noyaux modifiés ou avec des modules noyau qui prennent en charge des ioctls non standard, par exemple. À utiliser avec prudence. Si vous ne comprenez pas ce que fait cette option, vous n'en avez presque certainement pas besoin. Les variantes actuellement connues sont :
•bproc : prend en charge l'appel système sys_broc sur x86. Ceci est pour l'exécution sur BProc, qui est une variante mineure de Linux standard parfois utilisée pour la construction de clusters.
•android-no-hw-tls : certaines versions de l'émulateur Android pour ARM ne fournissent pas de registre matériel TLS (thread-local state), et Valgrind plante au démarrage. Utilisez cette variante pour sélectionner le support logiciel pour le TLS.
•android-gpu-sgx5xx : utilisez ceci pour prendre en charge la gestion des ioctls propriétaires pour la série de GPU PowerVR SGX 5XX sur les appareils Android. Ne pas sélectionner ceci ne cause pas de problèmes de stabilité, mais peut amener Memcheck à signaler des erreurs fausses après que le programme ait effectué des ioctls spécifiques au GPU.
•android-gpu-adreno3xx : de même, utilisez ceci pour prendre en charge la gestion des ioctls propriétaires pour la série de GPU Qualcomm Adreno 3XX sur les appareils Android.

--merge-recursive-frames=<nombre> [défaut : 0]

Certains algorithmes récursifs, par exemple les implémentations d'arbres binaires équilibrés, créent de nombreuses traces de pile différentes, contenant chacune des cycles d'appels. Un cycle est défini comme deux valeurs de compteur de programme identiques séparées par zéro ou plusieurs autres valeurs de compteur de programme. Valgrind peut alors utiliser beaucoup de mémoire pour stocker toutes ces traces de pile. C'est une mauvaise utilisation de la mémoire étant donné que ces traces de pile contiennent des appels récursifs non intéressants répétés au lieu d'informations plus intéressantes telles que la fonction qui a initié l'appel récursif.

L'option --merge-recursive-frames=<nombre> indique à Valgrind de détecter et de fusionner les cycles d'appels récursifs d'une taille allant jusqu'à <nombre> frames. Lorsqu'un tel cycle est détecté, Valgrind enregistre le cycle dans la trace de pile sous forme d'un compteur de programme unique.

La valeur 0 (la valeur par défaut) n'entraîne aucune fusion d'appels récursifs. Une valeur de 1 entraînera l'effondrement des traces de pile d'algorithmes récursifs simples (par exemple, une implémentation factorielle). Une valeur de 2 sera généralement nécessaire pour effondrer les traces de pile produites par des algorithmes récursifs tels que les arbres binaires, le tri rapide, etc. Des valeurs plus élevées pourraient être nécessaires pour des algorithmes récursifs plus complexes.

Remarque : les appels récursifs sont détectés par analyse des valeurs du compteur de programme. Ils ne sont pas détectés par l'examen des noms de fonctions.

--num-transtab-sectors=<nombre> [défaut : 6 pour les plateformes Android, 16 pour toutes les autres]

Valgrind traduit et instrumente le code machine de votre programme en petits fragments (blocs de base). Les traductions sont stockées dans un cache de traduction divisé en un certain nombre de sections (secteurs). Si le cache est plein, le secteur contenant les traductions les plus anciennes est vidé et réutilisé. Si ces anciennes traductions sont à nouveau nécessaires, Valgrind doit retraduire et réinstrumenter le code machine correspondant, ce qui est coûteux. Si l'ensemble de travail des "instructions exécutées" d'un programme est volumineux, augmenter le nombre de secteurs peut améliorer les performances en réduisant le nombre de retraductions nécessaires. Les secteurs sont alloués à la demande. Une fois alloué, un secteur ne peut jamais être libéré et occupe un espace considérable, en fonction de l'outil et de la valeur de --avg-transtab-entry-size (environ 40 Mo par secteur pour Memcheck). Utilisez l'option --stats=yes pour obtenir des informations précises sur la mémoire utilisée par un secteur et sur l'allocation et le recyclage des secteurs.

--avg-transtab-entry-size=<nombre> [défaut : 0, ce qui signifie utiliser la valeur par défaut fournie par l'outil]

Taille moyenne d'un bloc de base traduit. Cette taille moyenne est utilisée pour dimensionner la taille d'un secteur. Chaque outil fournit une valeur par défaut à utiliser. Si cette valeur par défaut est trop petite, les secteurs de traduction se rempliront trop rapidement. Si cette valeur par défaut est trop grande, une partie importante de la mémoire du secteur de traduction sera inutilisée. Notez que la taille moyenne de la traduction d'un bloc de base dépend de l'outil et peut dépendre des options de l'outil. Par exemple, l'option memcheck --track-origins=yes augmente la taille des traductions de blocs de base. Utilisez --avg-transtab-entry-size pour ajuster la taille des secteurs, soit pour économiser de la mémoire, soit pour éviter trop de retraductions.

--aspace-minaddr=<adresse> [défaut : dépend de la plateforme]

Pour éviter les conflits potentiels avec certaines bibliothèques système, Valgrind n'utilise pas l'espace d'adressage inférieur à la valeur --aspace-minaddr, le gardant réservé au cas où une bibliothèque demanderait spécifiquement de la mémoire dans cette région. Ainsi, une valeur "pessimiste" est devinée par Valgrind en fonction de la plateforme. Sous Linux, par défaut, Valgrind évite d'utiliser les 64 premiers Mo, même s'il n'y a généralement pas de conflit dans toute cette zone. Vous pouvez utiliser l'option --aspace-minaddr pour permettre à votre application gourmande en mémoire de bénéficier d'une plus grande partie de cette mémoire inférieure. Sur le
other hand, if you encounter a conflict, increasing aspace-minaddr value might solve it. Conflicts will typically manifest themselves with mmap failures in the low range of the address space. The provided address must be page aligned and must be equal or bigger to 0x1000 (4KB). To find the default value on your platform, do something such as valgrind -d -d date 2&1 | grep -i minaddr. Values lower than 0x10000 (64KB) are known to create problems on some distributions.

--valgrind-stacksize=<nombre> [par défaut : 1 Mo]

Pour chaque thread, Valgrind a besoin de sa propre pile « privée ». La taille par défaut de ces piles est largement dimensionnée et devrait donc suffire dans la plupart des cas. Si la taille est trop petite, Valgrind provoquera un segfault. Avant de planter, Valgrind peut émettre un avertissement lorsque la limite est approchée.

Utilisez l'option --valgrind-stacksize si un tel avertissement (improbable) est produit, ou si Valgrind plante en raison d'une violation de segmentation. De telles violations de segmentation ont été observées lors de la démanglation d'énormes symboles C++.

Si votre application utilise de nombreux threads et nécessite beaucoup de mémoire, vous pouvez économiser de la mémoire en réduisant la taille de ces piles Valgrind en utilisant l'option --valgrind-stacksize.

--show-emwarns=<oui|non> [par défaut : non]

Lorsqu'elle est activée, Valgrind émettra des avertissements concernant son émulation CPU dans certains cas. Ceux-ci ne sont généralement pas intéressants.

--require-text-symbol=:sonamepatt:fnnamepatt

Lorsqu'un objet partagé dont le soname correspond à sonamepatt est chargé dans le processus, examinez tous les symboles de texte qu'il exporte. Si aucun d'entre eux ne correspond à fnnamepatt, affichez un message d'erreur et abandonnez l'exécution. Cela permet de s'assurer que l'exécution ne continue pas à moins qu'un objet partagé donné ne contienne un nom de fonction particulier.

sonamepatt et fnnamepatt peuvent tous deux être écrits en utilisant les caractères génériques habituels ? et *. Par exemple : ":*libc.so*:foo?bar". Vous pouvez utiliser des caractères autres qu'un deux-points pour séparer les deux motifs. Il est seulement important que le premier caractère et le caractère séparateur soient les mêmes. Par exemple, l'exemple ci-dessus pourrait également être écrit "Q*libc.so*Qfoo?bar". Plusieurs indicateurs --require-text-symbol sont autorisés, auquel cas les objets partagés qui sont chargés dans le processus seront vérifiés par rapport à tous ceux-ci.

Le but est de prendre en charge l'utilisation fiable des bibliothèques annotées. Par exemple, supposons que nous ayons une version de libgomp.so de GCC qui a été annotée pour prendre en charge Helgrind. Il est très facile et déroutant de charger la mauvaise version, non annotée, de libgomp.so dans l'application. L'idée est donc la suivante : ajouter un symbole de texte dans la bibliothèque annotée, par exemple annotated_for_helgrind_3_6, puis fournir l'indicateur --require-text-symbol=:*libgomp*so*:annotated_for_helgrind_3_6 afin que lorsque libgomp.so est chargé, Valgrind scanne sa table de symboles et si le symbole n'est pas présent, l'exécution est abandonnée, plutôt que de continuer silencieusement avec la bibliothèque non annotée. Notez que vous devriez mettre l'indicateur entier entre guillemets pour empêcher les shells d'étendre les caractères génériques * et ?.

--soname-synonyms=syn1=pattern1,syn2=pattern2,...

Lorsqu'une bibliothèque partagée est chargée, Valgrind recherche des fonctions dans la bibliothèque qui doivent être remplacées ou encapsulées. Par exemple, Memcheck remplace certaines fonctions de chaîne et de mémoire (strchr, strlen, strcpy, memchr, memcpy, memmove, etc.) par ses propres versions. De tels remplacements sont normalement effectués uniquement dans les bibliothèques partagées dont le soname correspond à un motif de soname prédéfini (par exemple, libc.so* sous Linux). Par défaut, aucun remplacement n'est effectué pour un binaire lié statiquement ou pour des bibliothèques alternatives, à l'exception des fonctions d'allocation (malloc, free, calloc, memalign, realloc, operator new, operator delete, etc.). Ces fonctions d'allocation sont interceptées par défaut dans toute bibliothèque partagée ou dans l'exécutable s'ils sont exportés en tant que symboles globaux. Cela signifie que si une bibliothèque d'allocation de remplacement comme tcmalloc est trouvée, ses fonctions sont également interceptées par défaut. Dans certains cas, les remplacements permettent à --soname-synonyms de spécifier un motif de synonyme supplémentaire, offrant une flexibilité dans le remplacement. Ou pour empêcher l'interception de tous les symboles d'allocation publics.

Actuellement, cette flexibilité n'est autorisée que pour les fonctions liées à malloc, en utilisant le synonyme somalloc. Ce synonyme est utilisable pour tous les outils effectuant le remplacement standard des fonctions liées à malloc (par exemple, memcheck, helgrind, drd, massif, dhat).

•Bibliothèque malloc alternative : pour remplacer les fonctions liées à malloc dans une bibliothèque alternative spécifique avec le soname mymalloclib.so (et pas dans d'autres), donnez l'option --soname-synonyms=somalloc=mymalloclib.so. Un motif peut être utilisé pour correspondre à plusieurs sonames de bibliothèques. Par exemple, --soname-synonyms=somalloc=*tcmalloc* correspondra au soname de toutes les variantes de la bibliothèque tcmalloc (variantes tcmalloc natives, debug, profilées, ...).

Remarque : le soname d'une bibliothèque partagée elf peut être récupéré à l'aide de l'utilitaire readelf.

•Les remplacements dans une bibliothèque liée statiquement se font en utilisant le motif NONE. Par exemple, si vous liez avec libtcmalloc.a, et que vous souhaitez uniquement intercepter les fonctions liées à malloc dans l'exécutable (et les bibliothèques standard) eux-mêmes, mais pas dans d'autres bibliothèques partagées, vous pouvez donner l'option --soname-synonyms=somalloc=NONE. Notez qu'un motif NONE correspondra à l'exécutable principal et à toute bibliothèque partagée n'ayant pas de soname.
•Pour intercepter uniquement les symboles d'allocation dans les bibliothèques système par défaut, mais pas dans d'autres bibliothèques partagées ou l'exécutable définissant des fonctions publiques liées à malloc ou operator new, utilisez un nom de bibliothèque inexistant comme --soname-synonyms=somalloc=nouserintercepts (où nouserintercepts peut être un nom de bibliothèque inexistant).
•La bibliothèque partagée du linker dynamique (runtime) est exclue de la recherche de symboles globaux publics, tels que ceux des fonctions liées à malloc (identifiés par le synonyme somalloc).

--progress-interval=<nombre> [par défaut : 0, ce qui signifie : 'désactivé']

Il s'agit d'une amélioration de la sortie de débogage de Valgrind. Elle ne devrait pas intéresser les utilisateurs finaux.

Lorsque nombre est défini sur une valeur non nulle, Valgrind affichera un résumé de progression d'une ligne toutes les nombre secondes. Les valeurs valides pour nombre sont comprises entre 0 et 3600 inclus. Voici un exemple de sortie lorsque nombre est défini sur 10 :

PROGRESS: U 110s, W 113s, 97.3% CPU, EvC 414.79M, TIn 616.7k, TOut 0.5k, #thr 67
PROGRESS: U 120s, W 124s, 96.8% CPU, EvC 505.27M, TIn 636.6k, TOut 3.0k, #thr 64
PROGRESS: U 130s, W 134s, 97.0% CPU, EvC 574.90M, TIn 657.5k, TOut 3.0k, #thr 63

Chaque ligne indique :

•U : temps utilisateur total
•W : temps d'horloge total
•CPU : utilisation moyenne globale du CPU
•EvC : nombre de vérifications d'événements. Une vérification d'événement est une branche arrière dans le programme simulé, c'est donc une mesure de la progression avant du programme.
•TIn : nombre de blocs de code instrumentés par le JIT
•TOut : nombre de blocs de code instrumentés qui ont été supprimés
•#thr : nombre de threads dans le programme

À partir de la progression de ceux-ci, il est possible d'observer :

•lorsque le programme est limité par le calcul (TIn augmente lentement, EvC augmente rapidement)
•lorsque le programme est dans une boucle de rotation (TIn/TOut fixe, EvC augmente rapidement)
•lorsque le programme est limité par le JIT (TIn augmente rapidement)
•lorsque le programme supprime rapidement du code (TOut augmente rapidement)
•lorsque le programme est sur le point d'atteindre un état attendu (EvC atteint une valeur attendue)
•lorsque le programme est inactif (U augmente plus lentement que W)

OPTIONS DE DÉBOGAGE VALGRIND

Il existe également quelques options pour déboguer Valgrind lui-même. Vous ne devriez pas avoir besoin de les utiliser dans le cours normal des choses. Si vous souhaitez voir la liste, utilisez l'option --help-debug.

OPTIONS MEMCHECK

--leak-check=<non|résumé|oui|complet> [par défaut : résumé]

Lorsqu'il est activé, recherche les fuites de mémoire à la fin du programme client. S'il est défini sur résumé, il indique combien de fuites se sont produites. S'il est défini sur complet ou oui, chaque fuite individuelle sera montrée en détail et/ou comptée comme une erreur, comme spécifié par les options --show-leak-kinds et --errors-for-leak-kinds.

Si --xml=yes est utilisé, memcheck utilisera automatiquement la valeur --leak-check=full. Vous pouvez utiliser --show-leak-kinds=none pour réduire la taille de la sortie xml si vous n'êtes pas intéressé par les résultats des fuites.

--leak-resolution=<faible|moyenne|élevée> [par défaut : élevée]

Lors de la vérification des fuites, détermine à quel point Memcheck est disposé à considérer différentes traces d'appels comme étant les mêmes aux fins de fusionner plusieurs fuites en un seul rapport de fuite. Lorsqu'il est défini sur faible, seules les deux premières entrées doivent correspondre. Lorsqu'il est moyen, quatre entrées doivent correspondre. Lorsqu'il est élevé, toutes les entrées doivent correspondre.

Pour le débogage intensif des fuites, vous voudrez probablement utiliser --leak-resolution=high conjointement avec --num-callers=40 ou un nombre aussi élevé.

Notez que le réglage de --leak-resolution n'affecte pas la capacité de Memcheck à trouver des fuites. Il modifie seulement la façon dont les résultats sont présentés.

--show-leak-kinds=<ensemble> [par défaut : défini,possible]

Spécifie les types de fuites à afficher dans une recherche de fuites complète, de l'une des manières suivantes :
•une liste séparée par des virgules d'un ou plusieurs des éléments suivants : défini indirect possible accessible.
•tous pour spécifier l'ensemble complet (tous les types de fuites). C'est équivalent à --show-leak-kinds=definite,indirect,possible,reachable.
•aucun pour l'ensemble vide.

--errors-for-leak-kinds=<ensemble> [par défaut : défini,possible]

Spécifie les types de fuites à compter comme erreurs dans une recherche de fuites complète. L' <ensemble> est spécifié de manière similaire à --show-leak-kinds

--leak-check-heuristics=<ensemble> [par défaut : tous]

Spécifie l'ensemble des heuristiques de vérification des fuites
pour être utilisé lors des recherches de fuites. Les heuristiques contrôlent quels pointeurs intérieurs vers un bloc le font considérer comme accessible. L'ensemble d'heuristiques est spécifié de l'une des manières suivantes :
•Une liste séparée par des virgules d'un ou plusieurs de stdstring length64 newarray multipleinheritance.
•all pour activer l'ensemble complet d'heuristiques. C'est équivalent à --leak-check-heuristics=stdstring,length64,newarray,multipleinheritance.
•none pour l'ensemble vide.

Notez que ces heuristiques dépendent de la disposition des objets produits par le compilateur C++. Elles ont été testées avec certaines versions de gcc (par exemple, 4.4 et 4.7). Elles pourraient ne pas fonctionner correctement avec d'autres compilateurs C++.

--show-reachable=<yes|no> , --show-possibly-lost=<yes|no>

Ces options offrent un moyen alternatif de spécifier les types de fuites à afficher :
•--show-reachable=no --show-possibly-lost=yes est équivalent à --show-leak-kinds=definite,possible.
•--show-reachable=no --show-possibly-lost=no est équivalent à --show-leak-kinds=definite.
•--show-reachable=yes est équivalent à --show-leak-kinds=all.

Notez que --show-possibly-lost=no n'a aucun effet si --show-reachable=yes est spécifié.

--xtree-leak=<no|yes> [no]

Si défini sur yes, les résultats de la recherche de fuites effectuée à la sortie seront générés dans un fichier d'arbre d'exécution au 'Format Callgrind'. Notez que cela définit automatiquement les options --leak-check=full et --show-leak-kinds=all, pour permettre aux outils de visualisation d'arbres xtree tels que kcachegrind de sélectionner les types de fuites à visualiser. Le fichier produit contiendra les événements suivants :
•RB : octets accessibles
•PB : octets potentiellement perdus
•IB : octets indirectement perdus
•DB : octets définitivement perdus (directs plus indirects)
•DIB : octets indirectement définitivement perdus (sous-ensemble de DB)
•RBk : blocs accessibles
•PBk : blocs potentiellement perdus
•IBk : blocs indirectement perdus
•DBk : blocs définitivement perdus

L'augmentation ou la diminution de tous les événements ci-dessus sera également générée dans le fichier pour fournir le delta (augmentation ou diminution) entre 2 recherches de fuites successives. Par exemple, iRB est l'augmentation de l'événement RB, dPBk est la diminution de l'événement PBk. Les valeurs pour les événements d'augmentation et de diminution seront nulles pour la première recherche de fuites effectuée.

Voir Arbres d'exécution pour une explication détaillée des arbres d'exécution.

--xtree-leak-file=<nom_fichier> [défaut : xtleak.kcg.%p]

Spécifie que Valgrind doit générer le rapport de fuites xtree dans le fichier spécifié. Toutes les séquences %p, %q ou %n apparaissant dans le nom du fichier sont développées exactement de la même manière que pour --log-file. Voir la description de --log-file pour plus de détails.

Voir Arbres d'exécution pour une explication détaillée des formats d'arbres d'exécution.

--undef-value-errors=<yes|no> [défaut : yes]

Contrôle si Memcheck signale les erreurs d'utilisation de valeurs indéfinies. Réglez ceci sur no si vous ne souhaitez pas voir les erreurs de valeurs indéfinies. Cela a également pour effet d'accélérer légèrement Memcheck. AddrCheck (supprimé dans Valgrind 3.1.0) fonctionnait comme Memcheck avec --undef-value-errors=no.

--track-origins=<yes|no> [défaut : no]

Contrôle si Memcheck suit l'origine des valeurs non initialisées. Par défaut, il ne le fait pas, ce qui signifie que bien qu'il puisse vous indiquer qu'une valeur non initialisée est utilisée de manière dangereuse, il ne peut pas vous dire d'où provient la valeur non initialisée. Cela rend souvent difficile de trouver le problème à la source.

Lorsqu'il est défini sur yes, Memcheck suit les origines de toutes les valeurs non initialisées. Ensuite, lorsqu'une erreur de valeur non initialisée est signalée, Memcheck essaie de montrer l'origine de la valeur. Une origine peut être l'un des quatre endroits suivants : un bloc de tas, une allocation sur la pile, une requête client, ou diverses autres sources (par exemple, un appel à brk).

Pour les valeurs non initialisées provenant d'un bloc de tas, Memcheck montre où le bloc a été alloué. Pour les valeurs non initialisées provenant d'une allocation sur la pile, Memcheck peut vous dire quelle fonction a alloué la valeur, mais rien de plus - typiquement, il vous montre l'emplacement source de l'accolade ouvrante de la fonction. Vous devriez donc vérifier soigneusement que toutes les variables locales de la fonction sont initialisées correctement.

Coût de performance : le suivi des origines est coûteux. Il divise la vitesse de Memcheck par deux et augmente l'utilisation de la mémoire d'au moins 100 Mo, et potentiellement plus. Néanmoins, cela peut considérablement réduire l'effort requis pour identifier la cause profonde des erreurs de valeurs non initialisées, et constitue donc souvent un gain en productivité pour le programmeur, malgré une exécution plus lente.

Précision : Memcheck suit les origines de manière assez précise. Pour éviter des surcoûts de temps et d'espace très importants, certaines approximations sont faites. Il est possible, bien qu'improbable, que Memcheck signale une origine incorrecte, ou ne parvienne pas à identifier une origine.

Notez que la combinaison --track-origins=yes et --undef-value-errors=no est absurde. Memcheck vérifie et rejette cette combinaison au démarrage.

--partial-loads-ok=<yes|no> [défaut : yes]

Contrôle comment Memcheck gère les chargements de 32, 64, 128 et 256 bits naturellement alignés à partir d'adresses pour lesquelles certains octets sont adressables et d'autres non. Lorsque yes, de tels chargements ne produisent pas d'erreur d'adresse. Au lieu de cela, les octets chargés provenant d'adresses illégales sont marqués comme non initialisés, et ceux correspondant à des adresses légales sont traités normalement.

Lorsque no, les chargements à partir d'adresses partiellement invalides sont traités de la même manière que les chargements à partir d'adresses complètement invalides : une erreur d'adresse illégale est émise, et les octets résultants sont marqués comme initialisés.

Notez que le code qui se comporte de cette manière viole les normes ISO C/C++ et doit être considéré comme défectueux. Si possible, un tel code devrait être corrigé.

--expensive-definedness-checks=<no|auto|yes> [défaut : auto]

Contrôle si Memcheck doit employer une instrumentation plus précise mais aussi plus coûteuse (en temps) lors de la vérification de l'état de définition de certaines valeurs. En particulier, cela affecte l'instrumentation des additions, soustractions et comparaisons d'égalité d'entiers.

Sélectionner --expensive-definedness-checks=yes amène Memcheck à utiliser l'analyse la plus précise possible. Cela minimise les faux taux d'erreur mais peut entraîner une dégradation des performances allant jusqu'à 30%.

Sélectionner --expensive-definedness-checks=no amène Memcheck à utiliser l'instrumentation la moins coûteuse possible. Cela maximise les performances mais donnera normalement un taux de faux erreurs inutilisable trop élevé.

Le réglage par défaut, --expensive-definedness-checks=auto, est fortement recommandé. Il amène Memcheck à utiliser le minimum d'instrumentation coûteuse nécessaire pour obtenir le même taux de faux erreurs que --expensive-definedness-checks=yes. Il active également un passage d'analyse au moment de l'instrumentation qui vise à réduire davantage les coûts d'une instrumentation précise. Dans l'ensemble, la perte de performance est généralement d'environ 5% par rapport à --expensive-definedness-checks=no, bien que cela dépende fortement de la charge de travail. Notez que les réglages d'instrumentation exacts dans ce mode dépendent de l'architecture.

--keep-stacktraces=<alloc|free|alloc-and-free|alloc-then-free|none [défaut : alloc-and-free]

Contrôle quelles traces de pile (stack traces) sont conservées pour les blocs alloués par malloc et/ou libérés.

Avec alloc-then-free, une trace de pile est enregistrée au moment de l'allocation et est associée au bloc. Lorsque le bloc est libéré, une deuxième trace de pile est enregistrée et remplace la trace de pile d'allocation. Par conséquent, les erreurs de type "utilisation après libération" relatives à ce bloc ne peuvent montrer qu'une trace de pile de l'endroit où le bloc a été libéré.

Avec alloc-and-free, les traces de pile d'allocation et de désallocation du bloc sont stockées. Ainsi, une erreur "utilisation après libération" montrera les deux, ce qui peut faciliter le diagnostic de l'erreur. Comparé à alloc-then-free, ce réglage augmente légèrement l'utilisation de la mémoire de Valgrind car le bloc contient deux références au lieu d'une.

Avec alloc, seule la trace de pile d'allocation est enregistrée (et signalée). Avec free, seule la trace de pile de désallocation est enregistrée (et signalée). Ces valeurs diminuent quelque peu l'utilisation de mémoire et de CPU de Valgrind. Elles peuvent être utiles en fonction des types d'erreurs que vous recherchez et du niveau de détail dont vous avez besoin pour les analyser. Par exemple, si vous ne vous intéressez qu'aux erreurs de fuites de mémoire, il suffit d'enregistrer les traces de pile d'allocation.

Avec none, aucune trace de pile n'est enregistrée pour les opérations malloc et free. Si votre programme alloue un grand nombre de blocs et/ou alloue/libère à partir de nombreuses traces de pile différentes, cela peut réduire considérablement la charge CPU et/ou la mémoire requise. Bien sûr, peu de détails seront signalés pour les erreurs liées aux blocs de tas.

Notez qu'une fois qu'une trace de pile est enregistrée, Valgrind la conserve en mémoire même si elle n'est référencée par aucun bloc. Certains programmes (par exemple, les algorithmes récursifs) peuvent générer un nombre énorme de traces de pile. Si Valgrind utilise trop de mémoire dans de telles circonstances, vous pouvez réduire la mémoire requise avec les options --keep-stacktraces et/ou en utilisant une valeur plus petite pour l'option --num-callers.

Si vous souhaitez utiliser le profilage mémoire --xtree-memory=full (voir Arbres d'exécution), vous ne pouvez pas spécifier --keep-stacktraces=free ou --keep-stacktraces=none.

--freelist-vol=<nombre> [défaut : 20000000]

Lorsque le programme client libère de la mémoire en utilisant free (en C) ou delete (C++), cette mémoire n'est pas immédiatement rendue disponible pour une réallocation. Au lieu de cela, elle est marquée comme inaccessible et placée dans une file d'attente de blocs libérés. Le but est de retarder autant que possible le moment où la mémoire libérée revient en circulation. Cela augmente la probabilité que Memcheck soit capable de détecter des accès invalides à des blocs pendant une période de temps significative après leur libération.

Cette option spécifie la taille totale maximale, en octets, des blocs dans la file d'attente. La valeur par défaut est de vingt millions d'octets. Augmenter cette valeur augmente la quantité totale de mémoire utilisée par Memcheck mais peut détecter des utilisations invalides de blocs libérés qui, autrement, passeraient inaperçues.

/p>

--freelist-big-blocks=<nombre> [défaut : 1000000]

Lors de la création de blocs à partir de la file d'attente des blocs libérés disponibles pour la réallocation, Memcheck recirculera en priorité les blocs d'une taille supérieure ou égale à --freelist-big-blocks. Cela garantit que la libération de gros blocs (en particulier ceux plus grands que --freelist-vol) n'entraîne pas immédiatement une recirculation de tous (ou d'une grande partie) des petits blocs de la liste libre. En d'autres termes, cette option augmente la probabilité de détecter des pointeurs dangling pour les blocs « petits », même lorsque de gros blocs sont libérés.

Définir une valeur de 0 signifie que tous les blocs sont recirculés dans un ordre FIFO.

--workaround-gcc296-bugs=<oui|non> [défaut : non]

Lorsque cette option est activée, on suppose que les lectures et écritures à une petite distance en dessous du pointeur de pile sont dues à des bugs dans GCC 2.96, et elles ne sont pas signalées. La « petite distance » est de 256 octets par défaut. Notez que GCC 2.96 est le compilateur par défaut sur certaines anciennes distributions Linux (RedHat 7.X) et vous pourriez avoir besoin d'utiliser cette option. Ne l'utilisez pas si vous n'êtes pas obligé de le faire, car elle peut conduire à ignorer des erreurs réelles. Une meilleure alternative est d'utiliser une version plus récente de GCC dans laquelle ce bug est corrigé.

Vous pourriez également avoir besoin d'utiliser cette option lorsque vous travaillez avec GCC 3.X ou 4.X sous Linux PowerPC 32 bits. En effet, GCC génère du code qui accède occasionnellement en dessous du pointeur de pile, en particulier pour les conversions de nombres flottants vers/depuis des entiers. Ceci est une violation de la spécification ELF PowerPC 32 bits, qui ne prévoit aucune disposition pour que les emplacements en dessous du pointeur de pile soient accessibles.

Cette option est obsolète à partir de la version 3.12 et pourrait être supprimée dans les futures versions. Vous devriez plutôt utiliser --ignore-range-below-sp pour spécifier la plage exacte d'offsets en dessous du pointeur de pile qui doit être ignorée. Un équivalent approprié est --ignore-range-below-sp=1024-1.

--ignore-range-below-sp=<nombre>-<nombre>

Ceci est un remplacement plus général pour l'option obsolète --workaround-gcc296-bugs. Lorsqu'elle est spécifiée, elle fait en sorte que Memcheck n'indique pas les erreurs pour les accès aux offsets spécifiés en dessous du pointeur de pile. Les deux offsets doivent être des nombres décimaux positifs et -- un peu contre-intuitivement -- le premier doit être plus grand, afin d'impliquer une plage d'adresses non circulaire à ignorer. Par exemple, pour ignorer les accès de 4 octets à 8192 octets en dessous du pointeur de pile, utilisez --ignore-range-below-sp=8192-8189. Une seule plage peut être spécifiée.

--show-mismatched-frees=<oui|non> [défaut : oui]

Lorsque cette option est activée, Memcheck vérifie que les blocs du tas sont désalloués en utilisant une fonction qui correspond à la fonction d'allocation. C'est-à-dire qu'il s'attend à ce que free soit utilisé pour désallouer les blocs alloués par malloc, delete pour les blocs alloués par new, et delete[] pour les blocs alloués par new[]. Si une discordance est détectée, une erreur est signalée. Ceci est généralement important car dans certains environnements, libérer avec une fonction non correspondante peut provoquer des plantages.

Il existe cependant un scénario où de telles discordances ne peuvent être évitées. C'est lorsque l'utilisateur fournit des implémentations de new/new[] qui appellent malloc et de delete/delete[] qui appellent free, et que ces fonctions sont asymétriquement intégrées. Par exemple, imaginez que delete[] est intégré mais new[] ne l'est pas. Le résultat est que Memcheck « voit » tous les appels delete[] comme des appels directs à free, même lorsque le code source du programme ne contient aucune discordance.

Cela provoque de nombreux rapports d'erreurs déroutants et non pertinents. --show-mismatched-frees=no désactive ces vérifications. Il n'est cependant généralement pas conseillé de les désactiver, car vous pourriez manquer des erreurs réelles en conséquence.

--show-realloc-size-zero=<oui|non> [défaut : oui]

Lorsque cette option est activée, Memcheck vérifie les utilisations de realloc avec une taille de zéro. Cette utilisation de realloc n'est pas sûre car elle n'est pas portable. Sur certains systèmes, elle se comportera comme free. Sur d'autres systèmes, elle ne fera rien ou se comportera comme un appel à free suivi d'un appel à malloc avec une taille de zéro.

--ignore-ranges=0xPP-0xQQ[,0xRR-0xSS]

Toutes les plages listées dans cette option (et plusieurs plages peuvent être spécifiées, séparées par des virgules) seront ignorées par la vérification d'adressabilité de Memcheck.

--malloc-fill=<nombre hexadécimal>

Remplit les blocs alloués par malloc, new, etc., mais pas par calloc, avec l'octet spécifié. Ceci peut être utile pour dépister des problèmes de corruption de mémoire obscurs. La zone allouée est toujours considérée comme indéfinie par Memcheck -- cette option n'affecte que son contenu. Notez que --malloc-fill n'affecte pas un bloc de mémoire lorsqu'il est utilisé comme argument pour les requêtes client VALGRIND_MEMPOOL_ALLOC ou VALGRIND_MALLOCLIKE_BLOCK.

--free-fill=<nombre hexadécimal>

Remplit les blocs libérés par free, delete, etc., avec la valeur d'octet spécifiée. Ceci peut être utile pour dépister des problèmes de corruption de mémoire obscurs. La zone libérée est toujours considérée par Memcheck comme invalide pour l'accès -- cette option n'affecte que son contenu. Notez que --free-fill n'affecte pas un bloc de mémoire lorsqu'il est utilisé comme argument pour les requêtes client VALGRIND_MEMPOOL_FREE ou VALGRIND_FREELIKE_BLOCK.

OPTIONS CALLGRIND

--callgrind-out-file=<fichier>

Écrit les données de profil dans fichier plutôt que dans le fichier de sortie par défaut, callgrind.out.<pid>. Les spécificateurs de format %p et %q peuvent être utilisés pour intégrer l'ID du processus et/ou le contenu d'une variable d'environnement dans le nom, comme c'est le cas pour l'option de base --log-file. Lorsque plusieurs dumps sont effectués, le nom du fichier est modifié davantage ; voir ci-dessous.

--dump-line=<non|oui> [défaut : oui]

Ceci spécifie que le comptage des événements doit être effectué au niveau de la ligne source. Cela permet une annotation de la source pour les sources qui sont compilées avec des informations de débogage (-g).

--dump-instr=<non|oui> [défaut : non]

Ceci spécifie que le comptage des événements doit être effectué au niveau de l'instruction. Cela permet une annotation du code assembleur. Actuellement, les résultats ne peuvent être affichés que par KCachegrind.

--compress-strings=<non|oui> [défaut : oui]

Cette option influence le format de sortie des données de profil. Elle spécifie si les chaînes (noms de fichiers et de fonctions) doivent être identifiées par des numéros. HELGRIND OPTIONS

--free-is-write=no|yes [default: no]

When enabled (not the default), Helgrind treats freeing of heap memory as if the memory was written immediately before the free. This exposes races where memory is referenced by one thread, and freed by another, but there is no observable synchronisation event to ensure that the reference happens before the free.

This functionality is new in Valgrind 3.7.0, and is regarded as experimental. It is not enabled by default because its interaction with custom memory allocators is not well understood at present. User feedback is welcomed.

--track-lockorders=no|yes [default: yes]

When enabled (the default), Helgrind performs lock order consistency checking. For some buggy programs, the large number of lock order errors reported can become annoying, particularly if you're only interested in race errors. You may therefore find it helpful to disable lock order checking.

--history-level=none|approx|full [default: full]

--history-level=full (the default) causes Helgrind collects enough information about "old" accesses that it can produce two stack traces in a race report -- both the stack trace for the current access, and the trace for the older, conflicting access. To limit memory usage, "old" accesses stack traces are limited to a maximum of --history-backtrace-size entries (default 8) or to --num-callers value if this value is smaller.

Collecting such information is expensive in both speed and memory, particularly for programs that do many inter-thread synchronisation events (locks, unlocks, etc). Without such information, it is more difficult to track down the root causes of races. Nonetheless, you may not need it in situations where you just want to check for the presence or absence of races, for example, when doing regression testing of a previously race-free program.

--history-level=none is the opposite extreme. It causes Helgrind not to collect any information about previous accesses. This can be dramatically faster than --history-level=full.

--history-level=approx provides a compromise between these two extremes. It causes Helgrind to show a full trace for the later access, and approximate information regarding the earlier access. This approximate information consists of two stacks, and the earlier access is guaranteed to have occurred somewhere between program points denoted by the two stacks. This is not as useful as showing the exact stack for the previous access (as --history-level=full does), but it is better than nothing, and it is almost as fast as --history-level=none.

--history-backtrace-size=<number> [default: 8]

When --history-level=full is selected, --history-backtrace-size=number indicates how many entries to record in "old" accesses stack traces.

--delta-stacktrace=no|yes [default: yes on linux amd64/x86]

This flag only has any effect at --history-level=full.

--delta-stacktrace configures the way Helgrind captures the stacktraces for the option --history-level=full. Such a stacktrace is typically needed each time a new piece of memory is read or written in a basic block of instructions.

--delta-stacktrace=no causes Helgrind to compute a full history stacktrace from the unwind info each time a stacktrace is needed.

--delta-stacktrace=yes indicates to Helgrind to derive a new stacktrace from the previous stacktrace, as long as there was no call instruction, no return instruction, or any other instruction changing the call stack since the previous stacktrace was captured. If no such instruction was executed, the new stacktrace can be derived from the previous stacktrace by just changing the top frame to the current program counter. This option can speed up Helgrind by 25% when using --history-level=full.

The following aspects have to be considered when using --delta-stacktrace=yes :

•In some cases (for example in a function prologue), the valgrind unwinder might not properly unwind the stack, due to some limitations and/or due to wrong unwind info. When using --delta-stacktrace=yes, the wrong stack trace captured in the function prologue will be kept till the next call or return.
•On the other hand, --delta-stacktrace=yes sometimes helps to obtain a correct stacktrace, for example when the unwind info allows a correct stacktrace to be done in the beginning of the sequence, but not later on in the instruction sequence.
•Determining which instructions are changing the callstack is partially based on platform dependent heuristics, which have to be tuned/validated specifically for the platform. Also, unwinding in a function prologue must be good enough to allow using --delta-stacktrace=yes. Currently, the option --delta-stacktrace=yes has been reasonably validated only on linux x86 32 bits and linux amd64 64 bits. For more details about how to validate --delta-stacktrace=yes, see debug option --hg-sanity-flags and the function check_cached_rcec_ok in libhb_core.c.

--conflict-cache-size=N [default: 1000000]

This flag only has any effect at --history-level=full.

Information about "old" conflicting accesses is stored in a cache of limited size, with LRU-style management. This is necessary because it isn't practical to store a stack trace for every single memory access made by the program. Historical information on not recently accessed locations is periodically discarded, to free up space in the cache.

This option controls the size of the cache, in terms of the number of different memory addresses for which conflicting access information is stored. If you find that Helgrind is showing race errors with only one stack instead of the expected two stacks, try increasing this value.

The minimum value is 10,000 and the maximum is 30,000,000 (thirty times the default value). Increasing the value by 1 increases Helgrind's memory requirement by very roughly 100 bytes, so the maximum value will easily eat up three extra gigabytes or so of memory.

--check-stack-refs=no|yes [default: yes]

By default Helgrind checks all data memory accesses made by your program. This flag enables you to skip checking for accesses to thread stacks (local variables). This can improve performance, but comes at the cost of missing races on stack-allocated data.

--ignore-thread-creation=<yes|no> [default: no]

Controls whether all activities during thread creation should be ignored. By default enabled only on Solaris. Solaris provides higher throughput, parallelism and scalability than other operating systems, at the cost of more fine-grained locking activity. This means for example that when a thread is created under glibc, just one big lock is used for all thread setup. Solaris libc uses several fine-grained locks and the creator thread resumes its activities as soon as possible, leaving for example stack and TLS setup sequence to the created thread. This situation confuses Helgrind as it assumes there is some false ordering in place between creator and created thread; and therefore many types of race conditions in the application would not be reported. To prevent such false ordering, this command line option is set to yes by default on Solaris. All activity (loads, stores, client requests) is therefore ignored during:
•pthread_create() call in the creator thread
•thread creation phase (stack and TLS setup for the new thread)
) dans le thread créé

Aussi, la nouvelle mémoire allouée pendant la création du thread n'est pas suivie, c'est-à-dire que le rapport de courses y est supprimé. DRD fait la même chose implicitement. Ceci est nécessaire car la libc de Solaris met en cache de nombreux objets et les réutilise pour différents threads, ce qui confond Helgrind.

2.The number of conditional branches encountered and the number and proportion of those taken.
3.The number of superblocks entered and completed by the program. Note that due to optimisations done by the JIT, this is not at all an accurate value.
4.The number of guest (x86, amd64, ppc, etc.) instructions and IR statements executed. IR is Valgrind's RISC-like intermediate representation via which all instrumentation is done.
5.Ratios between some of these counts.
6.The exit code of the client program.

--detailed-counts=<no|yes> [default: no]

When enabled, Lackey prints a table containing counts of loads, stores and ALU operations, differentiated by their IR types. The IR types are identified by their IR name ("I1", "I8", ... "I128", "F32", "F64", and "V128").

--trace-mem=<no|yes> [default: no]

When enabled, Lackey prints the size and address of almost every memory access made by the program. See the comments at the top of the file lackey/lk_main.c for details about the output format, how it works, and inaccuracies in the address trace. Note that this option produces immense amounts of output.

--trace-superblocks=<no|yes> [default: no]

When enabled, Lackey prints out the address of every superblock (a single entry, multiple exit, linear chunk of code) executed by the program. This is primarily of interest to Valgrind developers. See the comments at the top of the file lackey/lk_main.c for details about the output format. Note that this option produces large amounts of output.

--fnname=<name> [default: main]

Changes the function for which calls are counted when --basic-counts=yes is specified.

DEBUGINFOD

Valgrind supports the downloading of debuginfo files via debuginfod, an HTTP server for distributing ELF/DWARF debugging information. When a debuginfo file cannot be found locally, Valgrind is able to query debuginfod servers for the file using the file's build-id.

In order to use this feature debuginfod-find must be installed and the $DEBUGINFOD_URLS environment variable must contain space-separated URLs of debuginfod servers. Valgrind does not support debuginfod-find verbose output that is normally enabled with $DEBUGINFOD_PROGRESS and $DEBUGINFOD_VERBOSE. These environment variables will be ignored. This feature is supported on Linux only.

For more information regarding debuginfod, see Elfutils Debuginfod[1] .
