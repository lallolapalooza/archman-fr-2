NOM

vtep - Schéma de base de données hardware_vtep

Ce schéma spécifie les relations qu'un VTEP peut utiliser pour intégrer des ports physiques dans des commutateurs logiques maintenus par un contrôleur de virtualisation réseau tel que NSX.

Glossaire :

VTEP
VXLAN Tunnel End Point, une entité qui origine et/ou termine des tunnels VXLAN.
HSC
Hardware Switch Controller.
NVC
Network Virtualization Controller, ex: NSX.
VRF
Instance Virtual Routing and Forwarding.

Colonne Commune

Certaines tables contiennent une colonne nommée other_config. Cette colonne a la même forme et le même but partout où elle apparaît, nous la décrivons donc ici pour économiser de l'espace plus tard.

other_config: map de paires chaîne-chaîne
Paires clé-valeur pour configurer des fonctionnalités rarement utilisées ou propriétaires.
Certaines tables n'ont pas de colonne other_config car aucune paire clé-valeur n'a encore été définie pour elles.

Détails :

switches: ensemble de Physical_Switchs
Le ou les commutateurs physiques gérés par le VTEP.
Lorsqu'un commutateur physique intègre le support de ce schéma VTEP, ce qui est attendu dans le cas le plus fréquent, cette colonne doit pointer vers un enregistrement Physical_Switch qui représente le commutateur lui-même. Dans une autre implémentation possible, un serveur ou une VM présente une interface frontale de schéma VTEP à un ou plusieurs commutateurs physiques, communiquant probablement avec ces commutateurs physiques via un protocole propriétaire. Dans ce cas, cette colonne pointerait vers un Physical_Switch pour chaque commutateur physique, et l'ensemble pourrait changer au fil du temps à mesure que le serveur frontal représente un ensemble différent de commutateurs.

Les méthodes de connexion suivantes sont actuellement prises en charge :

Le port SSL/TLS spécifié (par défaut : 6640) sur l'hôte donné, qui peut être un nom DNS (si compilé avec la bibliothèque unbound) ou une adresse IP.
La configuration de la clé et du certificat SSL/TLS se fait en dehors de la base de données.

Le port TCP spécifié (par défaut : 6640) sur l'hôte donné, qui peut être un nom DNS (si compilé avec la bibliothèque unbound) ou une adresse IP.

Écoute les connexions SSL/TLS sur le port TCP spécifié (par défaut : 6640). Si un hôte, qui peut être un nom DNS (si compilé avec la bibliothèque unbound) ou une adresse IP, est spécifié, alors les connexions sont restreintes à l'adresse IP locale résolue ou spécifiée.
ptcp :[port][:hôte]
Écoute les connexions sur le port TCP spécifié (par défaut : 6640). Si un hôte, qui peut être un nom DNS (si compilé avec la bibliothèque unbound) ou une adresse IP, est spécifié, alors les connexions sont restreintes à l'adresse IP locale résolue ou spécifiée.
Détection et gestion des échecs clients :
max_backoff : entier facultatif, au moins 1 000
Nombre maximum de millisecondes à attendre entre les tentatives de connexion. La valeur par défaut dépend de l'implémentation.
inactivity_probe : entier facultatif
Nombre maximum de millisecondes de temps d'inactivité sur la connexion au client avant d'envoyer un message de sonde d'inactivité. Si la base de données Open vSwitch ne communique pas avec le client pendant le nombre de secondes spécifié, elle enverra une sonde. Si aucune réponse n'est reçue pendant la même durée supplémentaire, le serveur de base de données suppose que la connexion est rompue et tente de se reconnecter. La valeur par défaut dépend de l'implémentation. Une valeur de 0 désactive les sondes d'inactivité.

is_connected : booléen
true si actuellement connecté à ce gestionnaire, false sinon.
status : last_error : chaîne facultative
Une description lisible par l'homme de la dernière erreur sur la connexion au gestionnaire ; c'est-à-dire strerror(errno). Cette clé existera uniquement si une erreur s'est produite.
status : state : chaîne facultative, l'une des valeurs : ACTIVE, BACKOFF, CONNECTING, IDLE ou VOID
L'état de la connexion au gestionnaire :
VOID
La connexion est désactivée.
BACKOFF
Tentative de reconnexion à intervalles croissants.
CONNECTING
Tentative de connexion.
ACTIVE
Connecté, l'hôte distant répond.
IDLE
La connexion est inactive. En attente d'une réponse de maintien de l'activité.
Ces valeurs peuvent changer à l'avenir. Elles sont fournies uniquement pour la compréhension humaine.
status : sec_since_connect : chaîne facultative, contenant un entier, au moins 0
Le temps écoulé depuis que ce gestionnaire s'est connecté avec succès à la base de données (en secondes). La valeur est vide si le gestionnaire ne s'est jamais connecté avec succès.
status : sec_since_disconnect : chaîne facultative, contenant un entier, au moins 0
Le temps écoulé depuis que ce gestionnaire s'est déconnecté de la base de données (en secondes). La valeur est vide si le gestionnaire ne s'est jamais déconnecté.
status : locks_held : chaîne facultative
Liste séparée par des espaces des noms des verrous OVSDB que la connexion détient. Omis si la connexion ne détient aucun verrou.
status : locks_waiting : chaîne facultative
Liste séparée par des espaces des noms des verrous OVSDB que la connexion attend actuellement d'acquérir. Omis si la connexion n'attend aucun verrou.
status : locks_lost : chaîne facultative
Liste séparée par des espaces des noms des verrous OVSDB que la connexion a vu être volés par un autre client OVSDB. Omis si aucun verrou n'a été volé à cette connexion.
status : n_connections : chaîne facultative, contenant un entier, au moins 2
Lorsque target spécifie une méthode de connexion qui écoute les connexions entrantes (par exemple, ptcp : ou pssl :) et que plusieurs connexions sont effectivement actives, la valeur est le nombre de connexions actives. Sinon, cette paire clé-valeur est omise.
Lorsque plusieurs connexions sont actives, les colonnes de statut et les paires clé-valeur (autres que celle-ci) rapportent le statut d'une connexion choisie arbitrairement.
Paramètres de connexion :

Configuration supplémentaire pour une connexion entre le gestionnaire et le serveur de base de données.

other_config : dscp : chaîne facultative, contenant un entier
Le Differentiated Service Code Point (DSCP) est spécifié à l'aide de 6 bits dans le champ Type de Service (TOS) de l'en-tête IP. DSCP fournit un mécanisme pour classifier le trafic réseau et fournir une Qualité de Service (QoS) sur les réseaux IP. La valeur DSCP spécifiée ici est utilisée lors de l'établissement de la connexion entre le gestionnaire et le serveur de base de données. Si aucune valeur n'est spécifiée, une valeur par défaut de 48 est choisie. Les valeurs DSCP valides doivent être comprises entre 0 et 63.

Il est recommandé qu'un NVC soit proactif et teste la prise en charge de la réplication du nœud source en utilisant un commutateur logique de test sur des nœuds de commutateur physique vtep, puis en essayant de changer le mode de réplication en "nœud source" sur ce commutateur logique, en vérifiant les erreurs. Le mode de réplication du nœud de service est considéré comme une exigence de base car il ne nécessite que l'envoi d'un paquet à un seul nœud de transport, il n'est donc pas attendu qu'un commutateur signale que le mode de nœud de service ne peut pas être pris en charge.

Détection de transfert bidirectionnel (BFD) :

BFD, défini dans la RFC 5880, permet la détection des pannes de connectivité point à point par une transmission occasionnelle de messages de contrôle BFD. Les VTEP sont censés implémenter BFD.

BFD fonctionne en transmettant régulièrement des messages de contrôle BFD à un rythme négocié indépendamment dans chaque direction. Chaque point d'extrémité spécifie le rythme a

BFD TABLE

Bidirectional Forwarding Detection (BFD) is a fast failure detection protocol used to detect failures in the bidirectional path between two forwarding engines, including the failure of a given user-plane connection.

A hardware VTEP uses BFD to determine the reachability of the devices at the end of the tunnels with which it exchanges data. This allows the VTEP to select a functioning service node among a group of service nodes that provide high availability. It also allows the NVC (Network Virtualization Controller) to report the health status of tunnels.

In many cases, the BFD peer of a hardware VTEP is an Open vSwitch instance. The Open vSwitch implementation of BFD aims to comply with the requirements set forth in RFC 5880. Open vSwitch does not implement the optional Authentication or "Echo Mode" features.

BFD operates by periodically sending control messages between endpoints. Each endpoint advertises the interval at which it expects to receive control messages and the rate at which it is willing to transmit them. An endpoint that fails to receive BFD control messages for a period three times the expected reception rate will signal a connectivity fault. In the case of a unidirectional connectivity issue, the system not receiving BFD control messages will signal the problem to its peer in the messages it transmits.

BFD Local Configuration:

The HSC (Host Software Controller) writes the key-value pairs in the bfd_config_local column to specify the local configurations to be used for BFD sessions on this tunnel.

bfd_config_local : bfd_dst_mac: optional string
Set to an Ethernet address in the form xx:xx:xx:xx:xx:xx to set the MAC address expected as the destination for received BFD packets. The default is 00:23:20:00:00:01.
bfd_config_local : bfd_dst_ip: optional string
Set to an IPv4 address to specify the IP address expected as the destination for received BFD packets. The default is 169.254.1.0.
BFD Remote Configuration:

The bfd_config_remote column is the remote counterpart of the bfd_config_local column. The NVC writes the key-value pairs in this column.

bfd_config_remote : bfd_dst_mac: optional string
Set to an Ethernet address in the form xx:xx:xx:xx:xx:xx to set the destination MAC address to be used for transmitted BFD packets. The default is 00:23:20:00:00:01.
bfd_config_remote : bfd_dst_ip: optional string
Set to an IPv4 address to specify the IP address used as the destination for transmitted BFD packets. The default is 169.254.1.1.
BFD Parameters:

The NVC sets up key-value pairs in the bfd_params column to enable and configure BFD.

bfd_params : enable: optional string, either true or false
Set to true to enable BFD on this Tunnel. If not specified, BFD will not be enabled by default.
bfd_params : min_rx: optional string, containing an integer, at least 1
The shortest interval, in milliseconds, at which this BFD session offers to receive BFD control messages. The remote endpoint may choose to send messages at a slower rate. Defaults to 1000.
bfd_params : min_tx: optional string, containing an integer, at least 1
The shortest interval, in milliseconds, at which this BFD session is willing to transmit BFD control messages. Messages will actually be transmitted at a slower rate if the remote endpoint is not willing to receive as quickly as specified. Defaults to 100.
bfd_params : decay_min_rx: optional string, containing an integer
An alternate receive interval, in milliseconds, that must be greater than or equal to bfd_params:min_rx. The implementation should switch from bfd_params:min_rx to bfd_params:decay_min_rx when there is no obvious incoming data traffic on the tunnel, to reduce the CPU and bandwidth cost of monitoring an idle tunnel. This feature may be disabled by setting a value of 0. This feature is reset whenever bfd_params:decay_min_rx or bfd_params:min_rx changes.
bfd_params : forwarding_if_rx: optional string, either true or false
When set to true, traffic received on the Tunnel is used to indicate the capability of packet I/O. BFD control packets are still transmitted and received. At least one BFD control packet must be received every 100 * bfd_params:min_rx amount of time. Otherwise, even if traffic is received, the bfd_params:forwarding will be false.
bfd_params : cpath_down: optional string, either true or false
Set to true to notify the remote endpoint that traffic should not be forwarded to this system for reasons other than a connectivity failure on the interface being monitored. The typical underlying reason is "concatenated path down," meaning that connectivity beyond the local system is down. Defaults to false.
bfd_params : check_tnl_key: optional string, either true or false
Set to true to make BFD accept only control messages with a tunnel key of zero. By default, BFD accepts control messages with any tunnel key.
BFD Status:

The VTEP sets key-value pairs in the bfd_status column to report the status of BFD on this tunnel. When BFD is not enabled with bfd_params:enable, the HSC clears all key-value pairs from bfd_status.

bfd_status : enabled: optional string, either true or false
Set to true if the BFD session has been successfully enabled. Set to false if the VTEP cannot support BFD or has insufficient resources to enable BFD on this tunnel. The NVC will disable BFD monitoring on the other side of the tunnel once this value is set to false.
bfd_status : state: optional string, one of admin_down, down, init, or up
Reports the state of the BFD session. The BFD session is fully healthy and negotiated if it is UP.
bfd_status : forwarding: optional string, either true or false
Reports whether the BFD session believes this Tunnel may be used to forward traffic. Typically, this means the local session is signaling UP, and the remote system is not signaling a problem such as concatenated path down.
bfd_status : diagnostic: optional string
A diagnostic code specifying the local system's reason for the last change in session state. The error messages are defined in section 4.1 of [RFC 5880].
bfd_status : remote_state: optional string, one of admin_down, down, init, or up
Reports the state of the remote endpoint's BFD session.
bfd_status : remote_diagnostic: optional string
A diagnostic code specifying the remote system's reason for the last change in session state. The error messages are defined in section 4.1 of [RFC 5880].
bfd_status : info: optional string
A short message providing further information about the BFD status (possibly including reasons why BFD could not be enabled).

Details:

vlan_bindings: map of integer-Logical_Switch pairs, key in range 0 to 4,095
Identifies how VLANs on the physical port are bound to logical switches. If, for example, the map contains a (VLAN, logical switch) pair, a packet that arrives on the port in the VLAN is considered to belong to the paired logical switch. A value of
zero dans le champ VLAN signifie que le trafic non marqué sur le port physique est mappé au commutateur logique.
acl_bindings: map de paires entier-ACL, clé dans la plage 0 à 4 095
Attachez des listes de contrôle d'accès (ACL) au port physique. La colonne se compose d'une carte des balises VLAN aux ACL. Si la valeur de la balise VLAN dans la carte est 0, cela signifie que l'ACL est associée à l'ensemble du port physique. Les valeurs non nulles signifient que l'ACL doit être appliquée uniquement aux paquets portant cette valeur de balise VLAN. Les commutateurs ne supporteront pas nécessairement la correspondance sur la balise VLAN pour toutes les ACL, et les liaisons ACL non prises en charge entraîneront la génération d'erreurs. La liaison d'une ACL à un VLAN spécifique et la liaison d'une ACL à l'ensemble du port physique ne doivent pas être combinées sur un seul port physique. C'est-à-dire qu'un mélange de clés nulles et non nulles dans la carte n'est pas recommandé.
vlan_stats: map de paires entier-Logical_Binding_Stats, clé dans la plage 0 à 4 095
Statistiques pour les VLAN liés aux commutateurs logiques sur le port physique. Une implémentation qui prend entièrement en charge ces statistiques remplirait cette colonne avec une correspondance pour chaque VLAN lié dans vlan_bindings. Une implémentation qui ne prend pas en charge ces statistiques ou ne les prend en charge que partiellement ne remplirait pas cette colonne ou la remplirait partiellement, respectivement. Une valeur de zéro dans le champ VLAN fait référence au trafic non marqué sur le port physique.

name: string
Nom symbolique du port. Le nom doit être unique au sein d'un Physical_Switch donné, mais la base de données n'est pas capable de le garantir.
description: string
Une description détaillée du port.
Notification d'erreur :

Une entrée dans cette colonne indique au NVC que le port physique a rencontré une faute. Le commutateur doit effacer cette colonne lorsque l'erreur a été corrigée.

port_fault_status : invalid_vlan_map: none
Indique qu'une association VLAN-commutateur logique demandée par le contrôleur n'a pas pu être instanciée par le commutateur en raison d'un conflit avec la configuration locale.

Clé de tunnel par commutateur logique :

Les protocoles de tunnel ont tendance à avoir un champ qui permet de partitionner le tunnel en sous-tunnels : VXLAN a un VNI, GRE et STT ont une clé, CAPWAP a un WSI, etc. Nous appelons cela génériquement des « clés de tunnel ». Étant donné qu'il faut utiliser une clé de tunnel, il existe au moins deux façons raisonnables d'attribuer leurs valeurs :

•
Par paire Logical_Switch+Physical_Locator. C'est-à-dire que chaque commutateur logique peut se voir attribuer une clé de tunnel différente sur chaque Physical_Locator. Ce modèle est particulièrement flexible.
Dans ce modèle, Physical_Locator transporte la clé de tunnel. Par conséquent, un enregistrement Physical_Locator existera pour chaque commutateur logique transporté à une destination IP donnée.
•
Par Logical_Switch. C'est-à-dire que chaque tunnel associé à un commutateur logique particulier transporte la même clé de tunnel, quel que soit le Physical_Locator auquel le tunnel est adressé. Ce modèle peut faciliter l'implémentation du commutateur car il impose moins d'exigences au plan de données matériel.
Dans ce modèle, Logical_Switch transporte la clé de tunnel. Par conséquent, un enregistrement Physical_Locator existera pour chaque destination IP.
tunnel_key: entier optionnel
Cette colonne est utilisée uniquement dans le modèle de clé de tunnel par Logical_Switch (voir ci-dessus), car c'est seulement dans ce modèle qu'il y a une clé de tunnel associée à un commutateur logique.
Pour le chiffrement vxlan_over_ipv4, lorsque le modèle de clé de tunnel par Logical_Switch est utilisé, cette colonne est le VNI VXLAN qui identifie un commutateur logique. Il doit être dans la plage de 0 à 16 777 215.
Mode de réplication :

Pour gérer le trafic L2 broadcast, multicast et unknown unicast, les paquets peuvent être envoyés à tous les membres d'un commutateur logique référencé par un commutateur physique. Il existe différents modes pour répliquer les paquets. Le mode de réplication par défaut consiste à envoyer le trafic à un nœud de service, qui peut être un hyperviseur, un serveur ou un appareil, et laisser le nœud de service gérer la réplication vers d'autres nœuds de transport (hyperviseurs ou autres commutateurs physiques VTEP). Ce mode est appelé réplication par nœud de service. Un mode de réplication alternatif, appelé réplication par nœud source, implique que le nœud source envoie aux autres nœuds de transport. Les hyperviseurs sont toujours responsables de faire leur propre réplication pour les VM attachées localement dans les deux modes. Le mode de réplication par nœud de service est le mode par défaut et est considéré comme une exigence de base car il nécessite seulement l'envoi du paquet à un seul nœud de transport.

replication_mode: chaîne optionnelle, soit service_node soit source_node
Cette colonne optionnelle définit le mode de réplication par Logical_Switch. Il y a 2 valeurs valides, service_node et source_node. Si la colonne n'est pas définie, le mode de réplication est par défaut service_node.
