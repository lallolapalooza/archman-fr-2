NOM

virt-install - provisionner de nouvelles machines virtuelles

SYNTAXE

virt-install [OPTION]...

DESCRIPTION

virt-install est un outil en ligne de commande pour créer de nouveaux invités KVM, Xen ou conteneurs Linux en utilisant la bibliothèque de gestion d'hyperviseur libvirt. Voir la section EXEMPLES à la fin de ce document pour commencer rapidement.

L'outil virt-install prend en charge les installations graphiques utilisant (par exemple) VNC ou SPICE, ainsi que les installations en mode texte via une console série. L'invité peut être configuré pour utiliser un ou plusieurs disques virtuels, interfaces réseau, périphériques audio, périphériques USB ou PCI physiques, entre autres.

Le support d'installation peut être un média local ISO ou CDROM, ou un arbre d'installation de distribution hébergé à distance sur HTTP, FTP, ou dans un répertoire local. Dans le cas d'un arbre d'installation, virt-install récupérera les fichiers minimaux nécessaires pour lancer le processus d'installation, permettant à l'invité de récupérer le reste de la distribution du système d'exploitation au besoin. Le démarrage PXE et l'importation d'une image disque existante (sautant ainsi la phase d'installation) sont également pris en charge.

Avec des arguments de ligne de commande appropriés, virt-install est capable de fonctionner de manière complètement autonome, l'invité se 'kickstartant' lui-même. Cela permet une automatisation facile des installations d'invités. Cela peut être fait manuellement, ou plus simplement avec l'option --unattended.

De nombreuses options ont des sous-options, spécifiées comme opt1=foo,opt2=bar, etc. Essayez --option=? pour voir une liste complète des sous-options associées à cet argument, exemple : virt-install --disk=?

La plupart des options ne sont pas obligatoires. Si une valeur --osinfo appropriée est spécifiée ou détectée, tous les paramètres par défaut seront remplis et rapportés dans la sortie du terminal. Sinon, les options minimales requises sont --memory, le stockage invité (--disk ou --filesystem), et un choix de méthode d'installation.

CONNEXION À LIBVIRT

--connect

Syntaxe : --connect URI

Se connecter à un hyperviseur non par défaut. Si ceci n'est pas spécifié, libvirt essaiera de choisir le défaut le plus approprié.

Quelques options valides ici sont :

qemu:///system
Pour créer des invités KVM et QEMU à exécuter par l'instance libvirtd système. C'est le mode par défaut que virt-manager utilise, et ce que la plupart des utilisateurs KVM veulent.
qemu:///session
Pour créer des invités KVM et QEMU pour libvirtd s'exécutant en tant qu'utilisateur normal.
xen:///
Pour se connecter à Xen.
lxc:///
Pour créer des conteneurs Linux

OPTIONS GÉNÉRALES

Paramètres de configuration généraux qui s'appliquent à tous les types d'installation d'invités.

-n, --name

Syntaxe : -n, --name NOM

Nom de la nouvelle instance de machine virtuelle invitée. Cela doit être unique parmi tous les invités connus de l'hyperviseur sur la connexion, y compris ceux qui ne sont pas actuellement actifs. Pour redéfinir un invité existant, utilisez l'outil virsh(1) pour l'arrêter ('virsh shutdown') et le supprimer ('virsh undefine') avant d'exécuter virt-install.

--memory

Syntaxe : --memory OPTIONS

Mémoire à allouer pour l'invité, en Mio. Ceci déprécie l'option -r/--ram. Des sous-options sont disponibles, comme 'memory', 'currentMemory', 'maxMemory' et 'maxMemory.slots', qui correspondent toutes aux valeurs XML portant le même nom.

Les valeurs de rétrocompatibilité 'memory' correspondent à l'élément <currentMemory>, et 'maxmemory' à l'élément <memory>.

Pour configurer des modules de mémoire qui peuvent être débranchés à chaud, voir la description de --memdev.

Utilisez --memory=? pour voir la liste de toutes les sous-options disponibles. Détails complets sur https://libvirt.org/formatdomain.html#memory-allocation

--memorybacking

Syntaxe : --memorybacking OPTIONS

Cette option influencera la manière dont les pages de mémoire virtuelle sont sauvegardées par les pages hôtes.

Utilisez --memorybacking=? pour voir la liste de toutes les sous-options disponibles. Détails complets sur https://libvirt.org/formatdomain.html#memory-backing

--arch

Syntaxe : --arch ARCH

Demander une architecture CPU non native pour la machine virtuelle invitée. Si omis, l'architecture CPU de l'hôte sera utilisée dans l'invité.

--machine

Syntaxe : --machine MACHINE

Le type de machine à émuler. Cela ne nécessitera généralement pas d'être spécifié pour Xen ou KVM, mais est utile pour choisir les types de machine d'architectures plus exotiques.

--metadata

Syntaxe : --metadata OPT=VAL,[...]

Spécifier des valeurs de métadonnées pour l'invité. Les options possibles incluent nom, uuid, titre et description. Cette option déprécie -u/--uuid et --description.

Utilisez --metadata=? pour voir la liste de toutes les sous-options disponibles. Détails complets sur https://libvirt.org/formatdomain.html#general-metadata

--events

Syntaxe : --events OPT=VAL,[...]

Spécifier des valeurs d'événements pour l'invité. Les options possibles incluent on_poweroff, on_reboot, et on_crash.

Utilisez --events=? pour voir la liste de toutes les sous-options disponibles. Détails complets sur https://libvirt.org/formatdomain.html#events-configuration

--resource

Syntaxe : --resource OPT=VAL,[...]

Spécifier le partitionnement des ressources pour l'invité.

Utilisez --resource=? pour voir la liste de toutes les sous-options disponibles. Détails complets sur https://libvirt.org/formatdomain.html#resource-partitioning

--sysinfo

Syntaxe : --sysinfo OPT=VAL,[...]

Configurer les valeurs sysinfo/SMBIOS exposées au système d'exploitation de la VM. Exemples :

--sysinfo host
Type spécial qui expose les informations SMBIOS de l'hôte dans la VM.
--sysinfo emulate
Type spécial où l'hyperviseur générera des informations SMBIOS dans la VM.
--sysinfo bios.vendor=custom ou --sysinfo smbios,bios.vendor=custom
Le type par défaut est smbios et permet aux utilisateurs de spécifier les informations SMBIOS manuellement.

Utilisez --sysinfo=? pour voir la liste de toutes les sous-options disponibles.

Détails complets sur
https://libvirt.org/formatdomain.html#operating-system-booting et
https://libvirt.org/formatdomain.html#smbios-system-information pour l'élément XML smbios.

--xml

Syntaxe : --xml ARGS

Effectuer des modifications directes sur le XML généré en utilisant la syntaxe XPath. Prenons un exemple comme

virt-install --xml ./@foo=bar --xml ./newelement/subelement=1

Cela modifiera le XML généré pour contenir :

<domain foo='bar' ...>
  ...
  <newelement>
    <subelement>1</subelement>
  </newelement>
</domain>

L'option --xml a 4 sous-options :

--xml xpath.set=XP
Permet de définir ou de modifier une valeur dans le XML. Le premier argument est la cible XPath, le second est la valeur.
--xml xpath.append=XPATH
Permet d'ajouter un nouveau nœud XML à la cible XPath spécifiée. S'il y a plusieurs éléments correspondant à XPATH, le nouveau sera ajouté à la fin du dernier.
--xml xpath.insert=XPATH
Permet d'insérer un nouveau nœud XML avant la cible XPath spécifiée. S'il y a plusieurs éléments correspondant à XPATH, le nouveau sera inséré avant le premier.
--xml xpath.delete=XPATH
Permet de supprimer un nœud XML à la cible XPath spécifiée.

Utilisez --xml=? pour voir une liste de toutes les sous-options disponibles. Détails complets sur https://libvirt.org/formatdomain.html#elements-for-xml-editing

OPTIONS_D_INSTALLATION

Options pour déterminer la méthode d'installation et les supports.

--cdrom

Syntaxe : --cdrom PATH

Permet d'installer à partir d'un CDROM ou d'un DVD.

--location

Syntaxe : --location URI[,opt=VAL,...]

URL ou chemin vers un arbre d'installation. Cela peut être un répertoire local, un chemin ISO, un partage NFS, un partage SMB, HTTP, HTTPS, FTP, FTPS ou une image de disque de système d'exploitation. Lorsque cette option est utilisée, virt-install essaiera de déterminer automatiquement le système d'exploitation, et le type d'installation (par exemple, 'gtk' pour des installations graphiques, 'text' pour des installations en mode texte, etc.). Les sous-options disponibles sont :

kernel=PATH
Chemin du noyau à charger à partir du chemin d'installation.
initrd=PATH
Chemin de l'initrd à charger à partir du chemin d'installation.
append=STRING
Chaîne de caractères à ajouter à la ligne de commande du noyau.
driver.interface=mac|none
Options pour le pilote de l'interface réseau. Peut être 'mac' ou 'none'.
driver.copy_image=true|false
Indique s'il faut copier l'image du disque de l'invité. Par défaut, les images sont utilisées directement, sauf si elles sont sur un support de type CDROM.
kernel.cmdline=STRING
Ligne de commande du noyau. Peut être utilisée pour passer des options supplémentaires au noyau, par exemple pour le démarrage sans assistance.
install.variant=STRING
Spécifie une variante d'installation, par exemple 'virtio' pour une installation optimisée pour virtio.
os.variant=STRING
Spécifie une variante du système d'exploitation.
skip_verification=true|false
Indique s'il faut sauter la vérification des signatures de clés.
compat=STRING
Spécifie la version de compatibilité de libvirt à utiliser pour générer le XML.
nocatch=true|false
Si défini à 'true', l'installeur ne tentera pas de rattraper l'état actuel des ressources (par exemple, pour les appareils partagés).
auto_disk_layout=true|false
Si défini à 'true', l'installeur tentera de déduire automatiquement la disposition du disque.
graphics.type=vnc|spice|none
Type de graphiques à utiliser. Par défaut, il essaie d'utiliser SPICE, puis VNC. Si défini à 'none', aucun graphique ne sera utilisé (installation série uniquement).
graphics.autoport=true|false
Si défini à 'true', un port VNC ou SPICE sera automatiquement choisi.
graphics.port=PORT
Spécifie le port VNC ou SPICE à utiliser.
graphics.listen=IP
Spécifie l'adresse IP sur laquelle les graphiques doivent être écoutés.
graphics.keymap=KEYMAP
Spécifie la disposition du clavier pour les graphiques.
graphics.password=PASSWORD
Spécifie un mot de passe pour les connexions VNC.
graphics.websocket=WS_URI
Spécifie une URI de websocket pour les connexions SPICE.
graphics. Sebagai=true|false
Permet l'utilisation de l'accélération graphique 3D.
virtio_fs.cache=auto|always|never
Type de cache pour le système de fichiers virtio-fs.
virtio_fs.mount_tag=TAG
Balise de montage pour le système de fichiers virtio-fs.
debug.exec=PATH
Chemin vers un exécutable de débogage à utiliser lors de l'installation.

Utilisez --location=? pour voir la liste de toutes les sous-options disponibles.

EXEMPLES

Installer une Fedora 20 64 bits à partir d'une image ISO en utilisant une interface réseau virtio et un disque de 10Gio dans le répertoire par défaut :

virt-install \
 --name myfedora \
 --ram 2048 \
 --cdrom /path/to/fedora-20-x86_64-netinst.iso \
 --os-variant fedora20 \
 --network=model=virtio \
 --disk size=10 \
 --graphics spice

Installer une machine virtuelle Debian Squeeze sans assistance, à partir d'un miroir HTTP, avec un script de préconfiguration :

virt-install \
 --name mydebian \
 --ram 1024 \
 --location 'http://ftp.debian.org/debian/dists/squeeze/main/installer-amd64/' \
 --os-variant debian7 \
 --unattended \
 --extra-args="auto=true url=http://example.com/preseed.cfg"

Importer un disque existant et créer une machine virtuelle à partir de celui-ci :

virt-install \
 --name myimported \
 --ram 1024 \
 --import \
 --disk path=/path/to/existing/disk.img,format=raw

Configurer un invité avec deux cartes réseau, l'une connectée à un réseau 'public' et l'autre à un réseau 'private' :

virt-install \
 --name multi-nic \
 --ram 2048 \
 --network network=public \
 --network network=private,source_dev=br1,model=virtio \
 --disk size=20

Configurer un invité avec un noyau spécifié et une image initrd, et passer des arguments au noyau :

virt-install \
 --name custom-kernel \
 --ram 1024 \
 --kernel /boot/vmlinuz-custom \
 --initrd /boot/initrd-custom.img \
 --append "root=/dev/sda1 console=ttyS0" \
 --disk size=10

Configurer un invité avec l'accélération graphique 3D et une résolution spécifique :

virt-install \
 --name graphic-accel \
 --ram 2048 \
 --disk size=20 \
 --graphics spice,1678468000 - 1678468000

--vcpus

Syntaxe : --vcpus OPTIONS

Nombre de processeurs virtuels à configurer pour l'invité. Si 'maxvcpus' est spécifié, l'invité pourra ajouter à chaud jusqu'à MAX processeurs virtuels pendant que l'invité est en cours d'exécution, mais démarrera avec VCPUS.

La topologie du processeur peut en outre être spécifiée avec des sockets, des dies, des cœurs et des threads. Si les valeurs sont omises, le reste sera rempli automatiquement en privilégiant les cœurs avant les sockets avant les threads. Les cœurs sont privilégiés car cela correspond aux caractéristiques du silicium réel moderne et constitue donc un meilleur ajustement pour ce que le système d'exploitation invité s'attendra à traiter.

'cpuset' définit les processeurs physiques que l'invité peut utiliser. CPUSET est une liste de nombres séparés par des virgules, qui peuvent également être spécifiés sous forme de plages ou de processeurs à exclure. Exemple :

0,2,3,5     : Utilise les processeurs 0,2,3 et 5
1-5,^3,8    : Utilise les processeurs 1,2,4,5 et 8

Si la valeur 'auto' est passée, virt-install tente de déterminer automatiquement un épinglage CPU optimal en utilisant les données NUMA, si disponibles.

--cpu

Syntaxe : --cpu MODEL[,+feature][,-feature][,match=MATCH][,vendor=VENDOR],...

Configure le modèle de CPU et les fonctionnalités du CPU exposées à l'invité. La seule valeur requise est MODEL, qui est un modèle de CPU valide tel que connu de libvirt.

Les valeurs de politique de fonctionnalité de Libvirt forcent, exigent, rendent optionnel, désactivent ou interdisent, ou avec la syntaxe courte '+feature' et '-feature', qui équivaut à 'force=feature' et 'disable=feature' respectivement.

Si un modèle de CPU exact est spécifié, virt-install copiera automatiquement les fonctionnalités du CPU disponibles sur l'hôte pour atténuer les vulnérabilités de sécurité récentes liées aux exécutions spéculatives du CPU et aux données du tampon de magasin microarchitectural. Cela aura cependant un certain impact sur les performances et interrompra la migration vers des hôtes sans correctifs de sécurité. Afin de contrôler ce comportement, il existe un paramètre secure. Les valeurs possibles sont on et off, avec on par défaut. Il est fortement recommandé de laisser cette option activée et de s'assurer que tous les hôtes de virtualisation disposent de microcode, de noyau et de logiciels de virtualisation entièrement à jour.

Quelques exemples :

--cpu core2duo,+x2apic,disable=vmx
Exposer le modèle CPU core2duo, forcer l'activation de x2apic, mais ne pas exposer vmx
--cpu host-model
Exposer la configuration du CPU de l'hôte à l'invité. Ceci permet à l'invité de profiter de nombreuses fonctionnalités du CPU de l'hôte (meilleures performances), mais peut causer des problèmes lors de la migration de l'invité vers un hôte sans CPU identique.
--cpu numa.cell0.memory=1234,numa.cell0.cpus=0-3,numa.cell1.memory=5678,numa.cell1.cpus=4-7
Exemple de spécification de deux cellules NUMA. Ceci générera du XML comme :
<cpu>
  <numa>
    <cell cpus="0-3" memory="1234"/>
    <cell cpus="4-7" memory="5678"/>
  </numa>
</cpu>
--cpu host-passthrough,cache.mode=passthrough
Exemple de passage des informations de cache du CPU hôte.
--cpu maximum
Exposer le CPU le plus riche en fonctionnalités possible. Utile lors de l'exécution d'un invité d'architecture étrangère, par exemple un invité riscv64 sur un hôte x86_64. Non recommandé lors de l'utilisation de KVM pour exécuter un invité de même architecture.

OPTIONS D'INSTALLATION

-c, --cdrom

Syntaxe : --cdrom PATH

Fichier ISO ou périphérique CDROM à utiliser pour le support d'installation de la VM. Après l'installation, le périphérique CDROM virtuel restera attaché à la VM, mais avec l'ISO ou le chemin d'accès hôte éjecté.

-l, --location

Syntaxe : -l, --location OPTIONS

Source d'installation de l'arbre de distribution. virt-install peut reconnaître certains arbres de distribution et récupérer une paire noyau/initrd bootable pour lancer l'installation.

--location permet des choses comme --extra-args pour les arguments du noyau, et l'utilisation de --initrd-inject. Si vous souhaitez utiliser ces options avec un support CDROM, vous pouvez également passer l'ISO à --location, ce qui fonctionne pour certains, mais pas tous, les supports CDROM.

Le LOCATION peut prendre l'une des formes suivantes :

https://host/path
Un emplacement de serveur HTTP contenant une image de distribution installable.
<ftp://host/path>
Un emplacement de serveur FTP contenant une image de distribution installable.
ISO
Extraire les fichiers directement du chemin ISO
RÉPERTOIRE
Chemin vers un répertoire local contenant une image de distribution installable. Notez que le répertoire ne sera pas accessible par l'invité après le premier démarrage, donc l'installateur de l'OS aura besoin d'un autre moyen pour accéder au reste du support d'installation.

Quelques exemples d'URL spécifiques à des distributions :

Basé sur Fedora/Red Hat

https://download.fedoraproject.org/pub/fedora/linux/releases/29/Server/x86_64/os
Debian

https://debian.osuosl.org/debian/dists/stable/main/installer-amd64/
Ubuntu

https://us.archive.ubuntu.com/ubuntu/dists/wily/main/installer-amd64/
Suse

https://download.opensuse.org/pub/opensuse/distribution/leap/42.3/repo/oss/

De plus, --location peut prendre les sous-options 'kernel' et 'initrd'. Ces chemins relatifs à l'URL/ISO de localisation spécifié permettent de sélectionner des fichiers spécifiques pour le noyau/initrd dans l'arbre d'installation. Cela peut être utile si virt-install/libosinfo ne sait pas où trouver le noyau dans le --location spécifié.

Par exemple, si vous avez un ISO que libosinfo ne connaît pas, appelé my-unknown.iso, avec un noyau dans 'kernel/fookernel' et un initrd dans 'kernel/fooinitrd', vous pouvez faire fonctionner cela avec :

--location my-unknown.iso,kernel=kernel/fookernel,initrd=kernel/fooinitrd

--pxe

Installer depuis PXE. Ceci indique simplement à la VM de démarrer sur le réseau pour le premier démarrage.

--import

Ignorer le processus d'installation de l'OS et construire une invitée autour d'une image disque existante. Le périphérique utilisé pour le démarrage est le premier périphérique spécifié via --disk ou --filesystem.

-x, --extra-args

Syntaxe : -x, --extra-args KERNELARGS

Arguments de ligne de commande supplémentaires du noyau à passer à l'installateur lors de l'installation d'une invitée à partir de --location. Une utilisation courante est la spécification d'un fichier kickstart anaconda pour les installations automatisées, telle que --extra-args "ks=https://myserver/my.ks"

--initrd-inject

Syntaxe : --initrd-inject PATH

Ajoute PATH à la racine de l'initrd récupéré avec --location. Ceci peut être utilisé pour exécuter une installation automatisée sans nécessiter de fichier kickstart hébergé sur le réseau : --initrd-inject=/path/to/my.ks --extra-args "ks=file:/my.ks"

--install

C'est un point d'entrée plus large pour divers types d'opérations d'installation. La commande a plusieurs sous-arguments, similaires à --disk et ses semblables. Cette option est strictement pour les opérations d'installation de VM, configurant essentiellement le premier démarrage.

L'utilisation la plus simple pour installer par exemple fedora29 est :

--install fedora29

Et virt-install récupérera une URL --location de libosinfo, et en tirera les valeurs par défaut.

Sous-options disponibles :

os=
Il s'agit de l'option d'installation de l'OS décrite ci-dessus. La manière explicite de spécifier cela serait --install os=fedora29 . os= est l'option par défaut si aucune n'est spécifiée
kernel=, initrd=
Spécifier une paire noyau et initrd à utiliser comme support d'installation. Ils sont copiés dans un emplacement temporaire avant de démarrer la VM, ils peuvent donc être combinés avec --initrd-inject et votre support source ne sera pas modifié. Le support sera téléchargé vers une connexion distante si nécessaire.

Exemple d'utilisation de chemins de système de fichiers locaux : --install kernel=/path/to/kernel,initrd=/path/to/initrd

Exemple d'utilisation de chemins réseau. Le noyau/initrd seront d'abord téléchargés localement, puis passés à la VM comme des chemins de système de fichiers locaux : --install kernel=https://127.0.0.1/tree/kernel,initrd=https://127.0.0.1/tree/initrd

Notez que ceci est uniquement pour le démarrage lors de l'installation. Si vous souhaitez définir le noyau utilisé pour le démarrage permanent de la VM, utilisez l'option --boot.

kernel_args=, kernel_args_overwrite=yes|no
Spécifier les arguments du noyau au moment de l'installation (XML <cmdline> libvirt). Ceux-ci peuvent être combinés avec par ex. les options noyau/initrd, ou le support --location. Par défaut, kernel_args est comme --extra-args, et _ajoutera_ aux arguments que virt-install essaiera de définir par défaut pour la plupart des installations --location. Si vous souhaitez remplacer les valeurs par défaut de virt-install, spécifiez en plus kernel_args_overwrite=yes
bootdev=
Spécifiez le périphérique de démarrage pour l'installation (hd, cdrom, floppy, network) à partir duquel démarrer pour la phase d'installation. Ceci correspond à la balise libvirt <os><boot dev=X> XML.

Si vous souhaitez installer à partir d'un cdrom ou du réseau, il est probablement plus simple et plus compatible avec les versions antérieures d'utiliser simplement --cdrom ou --pxe , mais cette option offre un contrôle précis sur le processus d'installation si nécessaire.

no_install=yes|no
Indiquez à virt-install qu'aucune installation n'a lieu en réalité, et que vous voulez simplement créer la VM. --import est juste un alias pour cela, tout comme spécifier --boot sans autres options d'installation. L'option obsolète --live est identique à '--cdrom $ISO --install no_install=yes'

--reinstall DOMAIN

Réinstallez une VM existante. DOMAIN peut être un nom de VM, un UUID ou un numéro d'ID. virt-install récupérera le XML du domaine de libvirt, appliquera les changements de configuration d'installation spécifiés, démarrera la VM pour le processus d'installation, puis reviendra à peu près au même XML de départ.

Seules les options liées à l'installation sont traitées, toutes les autres options de configuration de VM telles que --name, --disk, etc. sont complètement ignorées.

Si --reinstall est utilisé avec --cdrom, un CDROM existant attaché à la VM sera utilisé s'il y en a un disponible, sinon un périphérique CDROM permanent sera ajouté.

--unattended

Syntaxe : --unattended [OPTIONS]

Effectuez une installation sans surveillance à l'aide de la prise en charge des scripts d'installation de libosinfo. Il s'agit essentiellement d'une base de données de scripts d'installation automatique pour diverses distributions : scripts kickstart Red Hat, scripts d'installation Debian, installations unattended de Windows, et potentiellement d'autres. L'invocation la plus simple consiste à la combiner avec --install comme suit :

--install fedora29 --unattended

--cdrom /chemin/vers/mon/windows.iso --unattended

profile=

Un fichier utilisé pour définir le mot de passe admin/root du système d'exploitation de la VM. user-login=
Le nom de connexion de l'utilisateur à utiliser dans la VM. virt-install utilisera votre nom d'utilisateur hôte actuel par défaut si cette option n'est pas spécifiée. Notez que lorsque vous exécutez virt-install en tant que "root", cette option doit être spécifiée.
user-password-file=
Un fichier utilisé pour définir le mot de passe utilisateur de la VM. product-key=

--boot

Syntaxe : --boot BOOTOPTS

Spécifiez éventuellement la configuration de démarrage de la VM après l'installation. Cette option permet de spécifier un ordre de périphériques de démarrage, de démarrer en permanence à partir d'un noyau/initrd avec des arguments de noyau optionnels, et d'activer un menu de démarrage BIOS (nécessite libvirt 0.8.3 ou version ultérieure)

--boot peut être spécifié en plus d'autres options d'installation (telles que --location, --cdrom, etc.) ou peut être spécifié seul. Dans ce dernier cas, le comportement est similaire à l'option d'installation --import : il n'y a pas de phase 'installation', l'invité est simplement créé et lancé comme spécifié.

Quelques exemples :

--boot cdrom,fd,hd,network
Définir la priorité des périphériques de démarrage comme premier cdrom, premier floppy, premier disque dur, démarrage PXE réseau. Remarque : les invités s390x ne prennent en charge qu'un seul périphérique de démarrage, donc tout ce qui n'est pas le premier type de périphérique sera ignoré.
--boot kernel=KERNEL,initrd=INITRD,kernel_args="console=/dev/ttyS0"
Faire démarrer l'invité en permanence à partir d'une paire noyau/initrd locale, avec les options spécifiées pour le noyau.
--boot kernel=KERNEL,initrd=INITRD,dtb=DTB
Faire démarrer l'invité en permanence à partir d'une paire noyau/initrd locale avec un fichier binaire de l'arbre de périphériques externe. Le DTB peut être requis pour certaines configurations non x86 comme ARM ou PPC
--boot loader=BIOSPATH
Utiliser BIOSPATH comme BIOS de la machine virtuelle.
--boot bootmenu.enable=on,bios.useserial=on
Activer le menu de démarrage du BIOS, et activer l'envoi de la sortie texte du BIOS via la console série.
--boot init=INITPATH
Chemin vers un binaire que l'invité conteneur utilisera comme init. Si un --filesystem root a été spécifié, virt-install utilisera /sbin/init par défaut, sinon il utilisera /bin/sh par défaut.
--boot uefi, --boot uefi=on
Configurer la VM pour démarrer avec UEFI. Pour que virt-install connaisse les bons paramètres UEFI, libvirt doit annoncer les binaires UEFI connus via le XML domcapabilities, donc cela ne fonctionnera probablement que si vous utilisez des paquets de distribution correctement configurés. C'est la configuration UEFI recommandée.
--boot uefi=off
Ne pas utiliser UEFI si la VM y passerait normalement par défaut.
--boot uefi,firmware.feature0.name=secure-boot,firmware.feature0.enabled=yes,firmware.feature1.name=enrolled-keys,firmware.feature1.enabled=yes
Configurer la VM pour démarrer avec UEFI avec le support Secure Boot activé. Seuls les systèmes d'exploitation signés pourront démarrer avec cette configuration.
--boot uefi,firmware.feature0.name=secure-boot,firmware.feature0.enabled=no
Configurer la VM pour démarrer avec UEFI avec le support Secure Boot désactivé. Cette configuration permet d'exécuter des systèmes d'exploitation signés et non signés.

Des informations supplémentaires sur les fonctionnalités du firmware secure-boot et enrolled-keys et comment elles peuvent être utilisées pour influencer la sélection du firmware sont disponibles à l'adresse :
https://libvirt.org/kbase/secureboot.html

--boot loader=/.../OVMF_CODE.fd,loader.readonly=yes,loader.type=pflash,nvram.template=/.../OVMF_VARS.fd,loader_secure=no
Spécifier que la machine virtuelle utilise le binaire OVMF personnalisé comme firmware de démarrage, mappé comme une puce flash virtuelle. De plus, demander à
libvirt instancie le varstore UEFI spécifique à la VM à partir du modèle de varstore personnalisé "/.../OVMF_VARS.fd". Cette configuration n'est pas recommandée et ne devrait être utilisée que si --boot uefi ne connaît pas vos binaires UEFI.

Utilisez --boot=? pour voir la liste de toutes les sous-options disponibles. Détails complets sur
https://libvirt.org/formatdomain.html#operating-system-booting

--idmap

Syntaxe : --idmap OPTIONS

Si la configuration de l'invité déclare un mappage UID ou GID, l'espace de noms 'user' sera activé pour les appliquer. Un mappage UID/GID correctement configuré est un prérequis pour sécuriser les conteneurs, en l'absence de confinement sVirt.

--idmap peut être spécifié pour activer l'espace de noms utilisateur pour les conteneurs LXC. Exemple :

--idmap uid.start=0,uid.target=1000,uid.count=10,gid.start=0,gid.target=1000,gid.count=10

OPTIONS DE L'OS INVITÉ

--osinfo, --os-variant

Syntaxe : --osinfo [NOM_OS|OPT1=VAL1,...]

Optimise la configuration de l'invité pour un système d'exploitation spécifique. Dans la plupart des cas, un système d'exploitation doit être spécifié ou détecté à partir du média d'installation afin que des fonctionnalités critiques pour les performances comme virtio puissent être activées.

L'utilisation la plus simple est --osinfo NOM_OS ou --os-variant NOM_OS, par exemple --osinfo fedora32. Les sous-options prises en charge sont :

name=, short-id=
Le nom/id court de l'OS de libosinfo. Exemples : fedora32, win10
id=
L'ID libosinfo complet de style URL. Par exemple, name=win10 est identique à id=http://microsoft.com/win/10
detect=on|off
Indique si virt-install doit tenter de détecter l'OS à partir du média d'installation spécifié. La détection n'est actuellement tentée que pour les installations par URL et CDROM, et n'est pas fiable à 100 %.
require=on|off
Si on, virt-install générera une erreur si aucune valeur d'OS n'est définie ou détectée.

Quelques exemples intéressants :

--osinfo detect=on,require=on
Cela indique à virt-install de tenter la détection à partir du média d'installation, mais d'échouer explicitement si cela ne réussit pas. Cela garantira que vos invocations de virt-install ne se rabattront pas sur une configuration peu performante.
--osinfo detect=on,name=NOM_OS
Tente de détecter l'OS à partir du média d'installation, mais si cela échoue, utilise NOM_OS comme solution de repli.

Si une valeur manuelle --osinfo est spécifiée, la valeur par défaut est que tous les autres paramètres sont désactivés ou non définis.

Par défaut, virt-install tentera toujours --osinfo detect=on pour les médias d'installation appropriés. Si aucun OS n'est détecté, nous échouerons dans la plupart des cas courants. Cette erreur fatale a été ajoutée en 2022. Vous pouvez contourner ce problème en utilisant l'exemple de solution de repli ci-dessus, ou en désactivant l'option require. Si vous souhaitez simplement revenir rapidement au comportement précédent non fatal, définissez la variable d'environnement VIRTINSTALL_OSINFO_DISABLE_REQUIRE=1.

Utilisez la commande virt-install --osinfo list pour obtenir la liste des variantes d'OS acceptées. Voir osinfo-query os pour encore plus de sorties.

Note : --osinfo et --os-variant sont des alias l'un pour l'autre. --osinfo est le nommage de style nouveau préféré.

OPTIONS DE STOCKAGE

--disk

Syntaxe : --disk OPTIONS

Spécifie le média à utiliser comme stockage pour l'invité, avec diverses options. Le format général d'une chaîne de disque est

--disk opt1=val1,opt2=val2,...

L'invocation la plus simple pour créer une nouvelle image disque de 10G et le périphérique disque associé :

--disk size=10

virt-install générera un nom de chemin et le placera dans l'emplacement d'image par défaut pour l'hyperviseur. Pour spécifier un média, la commande peut être soit :

--disk /chemin/vers/stockage[,opt1=val1]...

ou spécifier explicitement l'un des arguments suivants :

path
Un chemin vers un média de stockage à utiliser, existant ou non. Le média existant peut être un fichier ou un périphérique bloc.

La spécification d'un chemin inexistant implique une tentative de création du nouveau stockage et nécessitera la spécification d'une valeur 'size'. Même pour les hôtes distants, virt-install essaiera d'utiliser les API de stockage libvirt pour créer automatiquement le chemin spécifié.

Si l'hyperviseur le prend en charge, path peut également être une URL réseau, comme
https://example.com/some-disk.img . Pour les chemins réseau, l'hyperviseur accédera directement au stockage, rien ne sera téléchargé localement.

pool
Un nom de pool de stockage libvirt existant sur lequel créer un nouveau stockage. Nécessite la spécification d'une valeur 'size'.
vol
Un volume de stockage libvirt existant à utiliser. Ceci est spécifié sous la forme 'nompool/nomvol'.

Options qui s'appliquent à la création de stockage :

size
taille (en GiB) à utiliser lors de la création d'un nouveau stockage
sparse
indique s'il faut ignorer l'allocation complète du stockage nouvellement créé. La valeur est 'yes' ou 'no'. Par défaut, c'est 'yes' (ne pas allouer complètement) sauf si cela n'est pas pris en charge par le type de stockage sous-jacent.

Le temps initial nécessaire pour allouer complètement le disque virtuel de l'invité (sparse=no) sera généralement compensé par des temps d'installation plus rapides à l'intérieur de l'invité. Par conséquent, l'utilisation de cette option est recommandée pour garantir des performances élevées et constantes et pour éviter les erreurs d'E/S dans l'invité si le système de fichiers hôte se remplit.

format
Format de l'image disque. Pour les volumes de fichiers, cela peut être 'raw', 'qcow2', 'vmdk', etc. Voir les types de format dans https://libvirt.org/storage.html pour les valeurs possibles. Ceci est souvent mappé à la valeur driver_type également.

Si non spécifié lors de la création d'images de fichiers, la valeur par défaut sera 'qcow2'.

Si vous créez un stockage, ce sera le format de la nouvelle image. Si vous utilisez une image existante, cela remplacera la détection automatique du format par libvirt.

backing_store
Chemin vers un disque à utiliser comme magasin de sauvegarde pour l'image nouvellement créée.
backing_format
Format de l'image disque de backing_store

Quelques exemples d'sous-options de configuration de périphérique :

device
Type de périphérique disque. Les exemples de valeurs sont 'cdrom', 'disk', 'lun' ou 'floppy'. Par défaut, c'est 'disk'.
boot.order
L'installation de l'invité avec plusieurs disques nécessitera ce paramètre pour démarrer correctement après son installation. Un paramètre boot.order prendra les valeurs 1,2,3,... Les périphériques avec une valeur inférieure ont une priorité plus élevée. Cette option s'applique également aux autres types de périphériques démarrables.
target.bus** ou *bus
Type de bus disque. Les exemples de valeurs sont 'ide', 'sata', 'scsi', 'usb', 'virtio' ou 'xen'. La valeur par défaut dépend de l'hyperviseur, car tous les hyperviseurs ne prennent pas en charge tous les types de bus.
readonly
Définit le lecteur comme lecture seule (prend 'on' ou 'off')
shareable
Définit le lecteur comme partageable (prend 'on' ou 'off')
cache
Le mode de cache à utiliser. Le cache de page hôte fournit la mémoire cache. La valeur du cache peut être 'none', 'writethrough', 'directsync', 'unsafe' ou 'writeback'. 'writethrough' fournit un cache de lecture. 'writeback' fournit un cache de lecture et d'écriture. 'directsync' contourne le cache de page hôte. 'unsafe' peut mettre en cache tout le contenu et ignorer les demandes de vidage de l'invité.
driver.discard
Indique si les requêtes discard (également connues sous le nom de « trim » ou « unmap ») sont ignorées ou transmises au système de fichiers. La valeur peut être « unmap » (permettre la transmission de la requête discard) ou « ignore » (ignorer la requête discard). Depuis 1.0.6 (uniquement QEMU et KVM)
driver.name
Nom du pilote que l'hyperviseur doit utiliser lors de l'accès au stockage spécifié. Généralement, il n'est pas nécessaire de le définir par l'utilisateur.
driver.type
Format/type de pilote que l'hyperviseur doit utiliser lors de l'accès au stockage spécifié. Généralement, il n'est pas nécessaire de le définir par l'utilisateur.
driver.io
Backend E/S disque. Peut être « threads », « native » ou « io_uring ».
driver.error_policy
Comment l'invité doit réagir si une erreur d'écriture est rencontrée. Peut être l'une des options suivantes : « stop », « ignore », ou « enospace »
serial
Numéro de série du périphérique de disque émulé. Il est utilisé dans les invités Linux pour définir les liens symboliques /dev/disk/by-id. Un numéro de série exemple pourrait être : WD-WMAP9A966149
source.startupPolicy
Définit ce qu'il faut faire avec le disque si le fichier source n'est pas accessible.
snapshot
Définit le comportement par défaut du disque pendant les instantanés de disque.

Voir la section exemples pour quelques utilisations. Cette option remplace -f/--file, -s/--file-size, --nonsparse, et --nodisks.

Utilisez --disk=? pour voir la liste de toutes les sous-options disponibles. Détails complets sur
https://libvirt.org/formatdomain.html#hard-drives-floppy-disks-cdroms

--filesystem

Spécifie un répertoire sur l'hôte à exporter vers l'invité. L'appel le plus simple est :

--filesystem /source/on/host,/target/point/in/guest

Ce qui fonctionnera pour les QEMU récents et les systèmes d'exploitation invités Linux ou les conteneurs LXC. Pour QEMU, le point cible n'est qu'un indice de montage dans sysfs, il ne sera donc pas monté automatiquement.

Quelques exemples de sous-options :

type
Le type ou le répertoire source. Les valeurs valides sont 'mount' (par défaut) ou 'template' pour les modèles OpenVZ.
accessmode ou mode
Le mode d'accès au répertoire source depuis le système d'exploitation invité. Utilisé uniquement avec QEMU et type=mount. Les modes valides sont 'mapped' (par défaut), 'passthrough', ou 'squash'. Voir la documentation XML du domaine libvirt pour plus d'informations.
source
Le répertoire sur l'hôte à partager.
target
L'emplacement de montage à utiliser dans l'invité.

Utilisez --filesystem=? pour voir la liste de toutes les sous-options disponibles. Détails complets sur https://libvirt.org/formatdomain.html#filesystems

OPTIONS RÉSEAU

-w, --network

Syntaxe : -w, --network OPTIONS

Connecte l'invité au réseau de l'hôte. Exemples pour spécifier le type de réseau :

bridge=BRIDGE
Se connecte à un périphérique de pont sur l'hôte nommé BRIDGE. Utilisez cette option si l'hôte a une configuration réseau statique et que l'invité nécessite une connectivité sortante et entrante complète vers/depuis le LAN. Utilisez également cette option si la migration à chaud sera utilisée avec cet invité.
network=NAME
Se connecte à un réseau virtuel sur l'hôte nommé NAME. Les réseaux virtuels peuvent être listés, créés, supprimés à l'aide de l'outil en ligne de commande virsh. Dans une installation non modifiée de libvirt, il y a généralement un réseau virtuel nommé default. Utilisez un réseau virtuel si l'hôte a une configuration réseau dynamique (par exemple, NetworkManager), ou utilise le Wi-Fi. L'invité sera NATé vers le LAN par la connexion active.
type=direct,source=IFACE[,source.mode=MODE]
Connexion directe à l'interface de l'hôte IFACE en utilisant macvtap.
user
Se connecte au LAN en utilisant SLIRP. Utilisez ceci uniquement si vous exécutez un invité QEMU en tant qu'utilisateur non privilégié. Ceci fournit une forme très limitée de NAT.
none
Indique à virt-install de ne pas ajouter d'interface réseau par défaut.

Si --network est omis, une seule carte réseau sera créée dans l'invité. S'il existe un périphérique de pont sur l'hôte avec une interface physique attachée, celle-ci sera utilisée pour la connectivité. Sinon, le réseau virtuel nommé default sera utilisé. Cette option peut être spécifiée plusieurs fois pour configurer plus d'une carte réseau.

Quelques exemples de sous-options :

model.type ou model
Modèle de périphérique réseau tel qu'il est vu par l'invité. La valeur peut être n'importe quel modèle de carte réseau pris en charge par l'hyperviseur, par exemple : 'e1000', 'rtl8139', 'virtio', ...
mac.address ou mac
Adresse MAC fixe pour l'invité ; si ce paramètre est omis, ou si la valeur RANDOM est spécifiée, une adresse appropriée sera générée aléatoirement. Pour les machines virtuelles Xen, il est requis que les 3 premières paires de l'adresse MAC soient la séquence '00:16:3e', tandis que pour les machines virtuelles QEMU ou KVM, elle doit être '52:54:00'.
filterref.filter
Contrôle le pare-feu et le filtrage réseau dans libvirt. La valeur peut être n'importe quel filtre réseau défini par les sous-commandes 'nwfilter' de virsh. Les filtres disponibles peuvent être listés en exécutant 'virsh nwfilter-list', par exemple : 'clean-traffic', 'no-mac-spoofing', ...
options virtualport.*
Configure le profil du port virtuel de l'appareil. Ceci est utilisé pour la configuration 802.Qbg, 802.Qbh, midonet et openvswitch.

Utilisez --network=? pour voir la liste de toutes les sous-options disponibles. Détails complets sur https://libvirt.org/formatdomain.html#network-interfaces

Cette option remplace -m/--mac, -b/--bridge et --nonetworks

hostdev=HOSTDEV
Utilise le périphérique nodedev référencé comme source pour type=hostdev comme décrit ici : https://libvirt.org/formatdomain.html#pci-passthrough

Pour le format HOSTDEV, voir la documentation --hostdev

portForward=[ADDRESS:]HOSTPORT[:GUESTPORT][/PROTO]
Option simplifiée pour spécifier la redirection de port avec les réseaux --network passt. Correspond approximativement à la syntaxe podman run -p. HOSTPORT peut être représenté comme une plage comme 7000-8000, mais GUESTPORT ne peut être qu'un port unique. Si GUESTPORT n'est pas fourni, les ports hôte et invité sont supposés correspondre.

Exemples :

--network passt,portForward=8080:80 \
--network passt,portForward0=7000-8000/udp,portForward1=127.0.0.1:2222:22 \

OPTIONS GRAPHIQUES

Si aucune option graphique n'est spécifiée, virt-install essayera de sélectionner les graphiques appropriés si la variable d'environnement DISPLAY est définie, sinon '--graphics none' est utilisé.

--graphics

Syntaxe : --graphics TYPE,opt1=arg1,opt2=arg2,...

Spécifie la configuration de l'affichage graphique. Ceci ne configure aucun matériel virtuel, seulement la manière dont l'affichage graphique de l'invité peut être accédé. Généralement, l'utilisateur n'a pas besoin de spécifier cette option, virt-install essaiera de choisir une valeur par défaut utile et lancera une connexion appropriée.

Le format général d'une chaîne graphique est

--graphics TYPE,opt1=arg1,opt2=arg2,...

Par exemple :

--graphics vnc,password=foobar

Certaines valeurs de TYPE prises en charge :

vnc
Configure une console virtuelle dans l'invité et l'exporte en tant que serveur VNC sur l'hôte. Sauf si le paramètre port est également fourni, le serveur VNC s'exécutera sur le premier port libre à partir de 5900. L'affichage VNC réel alloué peut être obtenu en utilisant la commande vncdisplay de virsh (ou virt-viewer(1) peut être utilisé, qui gère ce détail pour l'utilisateur).
spice
Exporte la console de l'invité en utilisant le protocole Spice. Spice permet des fonctionnalités avancées telles que le streaming audio et d'appareils USB, ainsi qu'une meilleure performance graphique.

L'utilisation du type graphique spice fonctionnera comme si les arguments suivants étaient donnés :

--video qxl --channel spicevmc
none
Aucune console graphique ne sera allouée pour l'invité. Les invités devront probablement avoir une console texte configurée sur le premier port série dans l'invité (cela peut être fait via l'option --extra-args). La commande 'virsh console NOM' peut être utilisée pour se connecter au périphérique série.

Certaines sous-options prises en charge :

port
Demande un numéro de port permanent et statiquement assigné pour la console de l'invité. Ceci est utilisé par 'vnc' et 'spice'.
tlsPort
Spécifie le port TLS de spice.
websocket
Demande un port WebSocket VNC pour la console de l'invité.

Si -1 est spécifié, le port WebSocket est alloué automatiquement.

Ceci est utilisé par 'vnc' et 'spice'.

listen
Adresse sur laquelle écouter pour les connexions VNC/Spice. Par défaut, c'est généralement 127.0.0.1 (localhost uniquement), mais certains hyperviseurs permettent de changer cela globalement (par exemple, la valeur par défaut du pilote qemu peut être modifiée dans /etc/libvirt/qemu.conf). Utilisez 0.0.0.0 pour autoriser l'accès depuis d'autres machines.

Utilisez 'none' pour spécifier que le serveur d'affichage ne doit pas écouter sur aucun port. Le serveur d'affichage ne peut être accédé que localement via le socket Unix de libvirt (virt-viewer avec --attach par exemple).

Ce paramètre est utilisé par 'vnc' et 'spice'.

Utilisez 'socket' pour que la VM écoute sur un chemin de socket unix généré par libvirt sur le système de fichiers hôte.

Ceci est utilisé par 'vnc' et 'spice'.

password
Demande un mot de passe de console, requis au moment de la connexion. Attention, ces informations peuvent se retrouver dans les fichiers journaux de virt-install, n'utilisez donc pas un mot de passe important. Ceci est utilisé par 'vnc' et 'spice'.
gl.enable
Indique s'il faut utiliser le rendu accéléré OpenGL. La valeur est 'yes' ou 'no'. Ceci est utilisé par 'spice'.
gl.rendernode
Chemin du nœud de rendu DRM à utiliser. Ceci est utilisé lorsque 'gl' est activé.

Utilisez --graphics=? pour voir une liste de toutes les sous-options disponibles. Détails complets sur https://libvirt.org/formatdomain.html#graphical-framebuffers

Ceci supprime les options suivantes : --vnc, --vncport, --vnclisten, -k/--keymap, --sdl, --nographics

--autoconsole

Syntaxe : --autoconsole OPTIONS

Configure la console interactive que virt-install lancera pour la VM. Cette option n'est pas requise ; le comportement par défaut est adaptatif et dépend de la configuration de la VM. Mais vous pouvez utiliser cette option pour remplacer le choix par défaut.

--autoconsole graphical
Utilise le virt-viewer(1) graphique comme console interactive.
--autoconsole text
Utilise le mode texte virsh console comme console interactive.
--autoconsole none
Ceci est identique à --noautoconsole.
--noautoconsole
N'essaie pas automatiquement de se connecter à la console de l'invité. Identique à --autoconsole none.

Notez que virt-install se termine rapidement lorsque cette option est spécifiée. Si votre commande demandait une installation en plusieurs étapes, comme --cdrom ou --location, après la fin de la phase d'installation, la VM sera arrêtée, qu'un redémarrage ait été demandé ou non pour la VM. Si vous souhaitez que la VM redémarre, virt-install doit rester en cours d'exécution. Vous pouvez utiliser '--wait' pour maintenir virt-install actif, même si --noautoconsole est spécifié.

OPTIONS DE VIRTUALISATION

Options pour remplacer les choix par défaut de type de virtualisation.

-v, --hvm

Demande l'utilisation de la virtualisation complète, si la virtualisation para et la virtualisation complète sont toutes deux disponibles sur l'hôte. Ce paramètre peut ne pas être disponible si vous vous connectez à un hyperviseur Xen sur une machine sans prise en charge de la virtualisation matérielle. Ce paramètre est implicite si vous vous connectez à un hyperviseur basé sur QEMU.

-p, --paravirt

Cet invité doit être un invité paravirtualisé. Si l'hôte prend en charge la virtualisation para et la virtualisation complète, et que ni ce paramètre ni --hvm ne sont spécifiés, ceci sera supposé.

--container

Cet invité doit être un invité de type conteneur. Cette option n'est requise que si l'hyperviseur prend en charge d'autres types d'invités (ainsi, par exemple, cette option est le comportement par défaut pour LXC et OpenVZ, mais est fournie pour la complétude).

--virt-type

L'hyperviseur sur lequel installer. Les choix possibles sont kvm, qemu ou xen. Les options disponibles sont listées via 'virsh capabilities' dans les balises <domain>.

Ceci supprime l'option --accelerate, qui est maintenant le comportement par défaut. Pour installer un invité QEMU simple, utilisez '--virt-type qemu'.

--hostdev, --host-device

Syntaxe : --hostdev, --host-device OPTIONS

Attache un périphérique hôte physique à l'invité. Quelques exemples de valeurs pour HOSTDEV :

--watchdog

Syntaxe : --watchdog MODÈLE[,action=ACTION]

Attache un périphérique matériel de surveillance virtuel à l'invité. Ceci nécessite un démon et un pilote de périphérique dans l'invité. La surveillance déclenche un signal lorsque la machine virtuelle semble bloquée. ACTION spécifie ce que libvirt fera lorsque la surveillance se déclenchera. Les valeurs sont :

reset
Réinitialise de force l'invité (par défaut).
poweroff
Arrête de force l'invité.
pause
Met en pause l'invité.
none
Ne fait rien.
shutdown
Arrête proprement l'invité (non recommandé, car un invité bloqué ne répondra probablement pas à un arrêt propre).

MODÈLE est le modèle de périphérique émulé : soit i6300esb (par défaut), soit ib700. Quelques exemples :

--watchdog default
Utilise les paramètres recommandés.
--watchdog i6300esb,action=poweroff
Utilise le i6300esb avec l'action 'poweroff'.

--serial

Syntaxe : --serial OPTIONS

Spécifie un périphérique série à attacher à l'invité, avec diverses options. Le format général d'une chaîne série est

--serial type,opt1=val1,opt2=val2,...

Les périphériques --serial et --parallel partagent toutes les mêmes options, sauf indication contraire. Certains types de caractère

ter redirection de périphériques sont :

--serial pty
Pseudo TTY. Le pty alloué sera listé dans la description XML des invités en cours d'exécution.
--serial dev,path=CHEMIN_HOTE
Périphérique hôte. Pour les périphériques série, cela pourrait être /dev/ttyS0. Pour les périphériques parallèle, cela pourrait être /dev/parport0.
--serial file,path=NOM_FICHIER
Écrit la sortie dans NOM_FICHIER.
--serial tcp,host=HOTE:PORT,source.mode=MODE,protocol.type=PROTOCOLE
Console réseau TCP. MODE est soit 'bind' (attend les connexions sur HOTE:PORT) soit 'connect' (envoie la sortie à HOTE:PORT), le défaut est 'bind'. HOTE vaut par défaut '127.0.0.1', mais PORT est requis. PROTOCOLE peut être soit 'raw' soit 'telnet' (défaut 'raw'). Si 'telnet', le port agit comme un serveur ou client telnet. Quelques exemples :

Attend les connexions sur n'importe quelle adresse, port 4567 :

--serial tcp,host=0.0.0.0:4567

Se connecte à localhost, port 1234 :

--serial tcp,host=:1234,source.mode=connect

Attend une connexion telnet sur localhost, port 2222. L'utilisateur pourrait alors se connecter interactivement à cette console via 'telnet localhost 2222' :

--serial tcp,host=:2222,source.mode=bind,source.protocol=telnet

--serial udp,host=HOTE_CONNEXION:PORT,bind_host=HOTE_LIAISON:PORT_LIAISON
Console réseau UDP. HOTE:PORT est la destination à laquelle envoyer la sortie (HOTE par défaut est '127.0.0.1', PORT est requis). HOTE_LIAISON:PORT_LIAISON est l'adresse locale optionnelle à laquelle se lier (HOTE_LIAISON par défaut est 127.0.0.1, mais n'est définie que si PORT_LIAISON est spécifié). Quelques exemples :

Envoie la sortie au port syslog par défaut (peut nécessiter une modification de /etc/rsyslog.conf en conséquence) :

--serial udp,host=:514

Envoie la sortie à l'hôte distant 192.168.10.20, port 4444 (cette sortie peut être lue sur l'hôte distant en utilisant 'nc -u -l 4444') :

--serial udp,host=192.168.10.20:4444

--serial unix,path=CHEMIN_UNIX,mode=MODE
Socket Unix, voir unix(7). MODE a un comportement et des valeurs par défaut similaires à --serial tcp,mode=MODE

Utilisez --serial=? pour voir la liste de toutes les sous-options disponibles. Détails complets sur
https://libvirt.org/formatdomain.html#consoles-serial-parallel-channel-devices

--channel

Spécifie un périphérique de canal de communication pour connecter l'invité et la machine hôte. Cette option utilise les mêmes options que --serial et --parallel pour spécifier l'extrémité hôte/source du canal. Des options 'target' supplémentaires sont utilisées pour spécifier comment l'invité voit le canal.

Certains types de redirection de périphérique caractère sont :

--channel SOURCE,target.type=guestfwd,target.address=HOTE:PORT
Canal de communication utilisant la pile réseau usermode de QEMU. L'invité peut se connecter au canal en utilisant la combinaison HOTE:PORT spécifiée.
--channel SOURCE,target.type=virtio[,target.name=NOM]
Canal de communication utilisant le port série virtio (nécessite 2.6.34 ou plus récent sur l'hôte et l'invité). Chaque instance d'une ligne --channel virtio est exposée dans l'invité comme /dev/vport0p1, /dev/vport0p2, etc. NOM est une métadonnée optionnelle, et peut être n'importe quelle chaîne, telle que org.linux-kvm.virtioport1. S'il est spécifié, il sera exposé dans l'invité à /sys/class/virtio-ports/vport0p1/NOM
--channel spicevmc,target.type=virtio[,target.name=NOM]
Canal de communication pour l'agent SPICE de QEMU, utilisant le port série virtio (nécessite 2.6.34 ou plus récent sur l'hôte et l'invité). NOM est une métadonnée optionnelle, et peut être n'importe quelle chaîne, telle que le défaut com.redhat.spice.0 qui spécifie comment l'invité verra le canal.
--channel qemu-vdagent,target.type=virtio[,target.name=NOM]
Canal de communication pour l'agent vd de QEMU, utilisant le port série virtio (nécessite 2.6.34 ou plus récent sur l'hôte et l'invité). Ceci permet la fonctionnalité copier/coller avec les invités VNC. Notez que l'intégration du presse-papiers de l'invité est implémentée via spice-vdagent, qui doit être exécuté même lorsque l'invité n'utilise pas de graphiques spice. NOM est une métadonnée optionnelle qui spécifie comment l'invité verra le canal, et devrait être laissée par défaut com.redhat.spice.0 à moins que vous ne sachiez ce que vous faites.

Utilisez --channel=? pour voir la liste de toutes les sous-options disponibles. Détails complets sur https://libvirt.org/formatdomain.html#channel

OPTIONS DIVERSES

-h, --help

Afficher le message d'aide et quitter

--version

Afficher le numéro de version du programme et quitter

--autostart

Définir le drapeau d'autodémarrage pour un domaine. Cela permet au domaine de démarrer au démarrage de l'hôte.

--transient

Utiliser --import ou --boot et --transient si vous souhaitez une VM libvirt transitoire. Ces VM n'existent que jusqu'à l'arrêt du domaine ou le redémarrage du serveur hôte. Libvirt oublie la configuration XML de la VM après l'un de ces événements. Notez que les disques de la VM ne seront pas supprimés. Voir :
https://wiki.libvirt.org/page/VM_lifecycle#Transient_guest_domains_vs_Persistent_guest_domains

--destroy-on-exit

Lorsque la fenêtre de console de la VM est fermée, détruire (forcer l'arrêt) la VM. Si vous combinez cela avec --transient, cela fait que la commande virt-install fonctionne de manière similaire à qemu, où la VM est arrêtée lorsque la fenêtre de console est fermée par l'utilisateur.

--print-xml

Syntax: --print-xml [STEP]

Imprimer le XML généré de l'invité, au lieu de le définir. Par défaut, cela CRÉERA le stockage (peut être désactivé avec --dry-run). Cette option implique --quiet.

Si l'installation de la VM comporte plusieurs phases, par défaut, cela imprimera tout le XML généré. Si vous souhaitez imprimer une phase particulière, utilisez --print-xml 2 (pour le XML de la deuxième phase).

--noreboot

Empêcher le domaine de redémarrer automatiquement après la fin de l'installation.

--wait

Syntax: --wait WAIT

Configurer la façon dont virt-install attendra la fin de l'installation. Sans cette option, virt-install attendra la fermeture de la console (ce qui n'indique pas nécessairement que l'invité s'est arrêté), ou dans le cas de --noautoconsole, lancera simplement l'installation et quittera.

'--wait' seul ou toute valeur négative fera attendre virt-install indéfiniment. Tout nombre positif représente le nombre de minutes pendant lesquelles virt-install attendra. Si la limite de temps est dépassée, virt-install quittera simplement, laissant la machine virtuelle dans son état actuel.

--dry-run

Poursuivre le processus de création de l'invité, mais NE PAS créer de périphériques de stockage, modifier la configuration des périphériques hôtes, ou enseigner réellement libvirt à propos de l'invité. virt-install peut toujours récupérer les médias d'installation, car cela est nécessaire pour détecter correctement le système d'exploitation à installer.

--check

Activer ou désactiver certaines vérifications de validation. Quelques exemples incluent l'avertissement concernant l'utilisation d'un disque déjà attribué à une autre VM (--check path_in_use=on|off), ou l'avertissement sur un potentiel manque d'espace lors de l'allocation de disque (--check disk_size=on|off). La plupart des vérifications sont effectuées par défaut.

-q, --quiet

N'imprimer que les messages d'erreur fatals.

-d, --debug

Afficher les informations de débogage dans le terminal lors de l'exécution du processus d'installation. Les informations de débogage sont également stockées dans ~/.cache/virt-manager/virt-install.log même si ce paramètre est omis.

EXEMPLES

L'invocation la plus simple pour installer interactivement une VM Fedora 29 KVM avec les paramètres par défaut recommandés. virt-viewer(1) sera lancé pour interagir graphiquement avec l'installation de la VM

# sudo virt-install --install fedora29

Similaire, mais utiliser le support d'installation sans surveillance de libosinfo, qui effectuera l'installation de fedora29 automatiquement sans intervention de l'utilisateur :

# sudo virt-install --install fedora29 --unattended

Installer une VM Windows 10, en utilisant 40 Go de stockage à l'emplacement par défaut et 4096 Mo de RAM, et s'assurer que nous nous connectons à l'instance libvirtd du système :

# virt-install \
   --connect qemu:///system \
   --name my-win10-vm \
   --memory 4096 \
   --disk size=40 \
   --osinfo win10 \
   --cdrom /path/to/my/win10.iso

Installer une VM CentOS 7 KVM à partir d'une URL, avec les paramètres par défaut des périphériques recommandés et le stockage requis par défaut, mais demander spécifiquement des graphiques VNC au lieu de SPICE par défaut, et demander 8 processeurs virtuels et 8192 Mo de mémoire :

# virt-install \
    --connect qemu:///system \
    --memory 8192 \
    --vcpus 8 \
    --graphics vnc \
    --osinfo centos7.0 \
    --location http://mirror.centos.org/centos-7/7/os/x86_64/

Créer une VM autour d'une image disque debian9 existante :

# virt-install \
    --import \
    --memory 512 \
    --disk /home/user/VMs/my-debian9.img \
    --osinfo debian9

Démarrer une VM ARM QEMU série, qui nécessite de spécifier un noyau manuel.

# virt-install \
    --name armtest \
    --memory 1024 \
    --arch armv7l --machine vexpress-a9 \
    --disk /home/user/VMs/myarmdisk.img \
    --boot kernel=/tmp/my-arm-kernel,initrd=/tmp/my-arm-initrd,dtb=/tmp/my-arm-dtb,kernel_args="console=ttyAMA0 rw root=/dev/mmcblk0p3" \
    --graphics none

Remarque : L'indicateur IOMMU doit être activé avec driver.iommu pour les périphériques virtio. L'utilisation de --memtune est actuellement requise en raison des limitations de SEV, reportez-vous à la documentation libvirt pour une explication détaillée.

# virt-install \
    --name foo \
    --memory 4096 \
    --boot uefi \
    --machine q35 \
    --memtune hard_limit=4563402 \
    --disk size=15,target.bus=scsi \
    --import \
    --controller type=scsi,model=virtio-scsi,driver.iommu=on \
    --controller type=virtio-serial,driver.iommu=on \
    --network network=default,model=virtio,driver.iommu=on \
    --rng /dev/random,driver.iommu=on \
    --memballoon driver.iommu=on \
    --launchSecurity sev
