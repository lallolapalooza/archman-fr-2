NOM

varnishtest - Programme de test pour Varnish

SYNTAXE

varnishtest [-hikLlqv] [-b taille] [-D nom=val] [-j jobs] [-n iter] [-t durée] fichier [fichier ...]

DESCRIPTION

Le programme varnishtest est un programme piloté par script utilisé pour tester Varnish Cache.

Le programme varnishtest, lorsqu'il est lancé et qu'on lui fournit un ou plusieurs fichiers de script, peut créer un certain nombre de threads représentant des backends, certains threads représentant des clients, et un processus varnishd. Ceci est ensuite utilisé pour simuler une transaction afin de provoquer un comportement spécifique.

Les options suivantes sont disponibles :

-b taille
Définir la taille du tampon interne (défaut : 1M)

-D nom=val Définir une macro à utiliser dans les scripts

-h
Afficher l'aide
-i
Définir PATH et vmod_path pour trouver les binaires varnish dans l'arborescence de build
-j jobs
Exécuter ce nombre de tests en parallèle
-k
Continuer en cas d'échec du test
-L
Toujours laisser les temporaires vtc.*
-l
Laisser les temporaires vtc.* si le test échoue
-n itérations
Exécuter les tests ce nombre de fois

-p nom=val Passer des paramètres à toutes les lignes de commande varnishd

-q
Mode silencieux : signaler uniquement les échecs
-t durée
Expirer les tests après cette durée (défaut : 60s)
-v
Mode verbeux : toujours signaler le journal du test

fichier Fichier à utiliser comme script

Si TMPDIR est défini dans l'environnement, varnishtest crée des répertoires temporaires vtc.* pour chaque test dans $TMPDIR, sinon dans /tmp.

SCRIPTS

La syntaxe vtc est documentée en détail dans vtc(7). Si vous souhaitez plus d'exemples que celui ci-dessous, vous pouvez consulter le dépôt du code source de Varnish, sous bin/varnishtest/tests/, où tous les tests de régression pour Varnish sont conservés.

Un exemple :

varnishtest "#1029"
server s1 {
        rxreq
        expect req.url == "/bar"
        txresp -gzipbody {[bar]}
        rxreq
        expect req.url == "/foo"
        txresp -body {<h1>FOO<esi:include src="/bar"/>BARF</h1>}
} -start
varnish v1 -vcl+backend {
        sub vcl_backend_response {
                set beresp.do_esi = true;
                if (bereq.url == "/foo") {
                        set beresp.ttl = 0s;
                } else {
                        set beresp.ttl = 10m;
                }
        }
} -start
client c1 {
        txreq -url "/bar" -hdr "Accept-Encoding: gzip"
        rxresp
        gunzip
        expect resp.bodylen == 5
        txreq -url "/foo" -hdr "Accept-Encoding: gzip"
        rxresp
        expect resp.bodylen == 21
} -run

Lorsqu'il est exécuté, le script ci-dessus simulera un serveur (s1) qui attend deux requêtes différentes. Il démarrera un serveur Varnish (v1) et ajoutera la définition du backend au VCL spécifié (-vcl+backend). Enfin, il démarrera le client c1, qui est un client unique envoyant deux requêtes.

TESTER UNE ARBORESCENCE DE BUILD

Que vous construisiez un VMOD ou que vous utilisiez un VMOD que vous venez de construire, vous pouvez indiquer à varnishtest de passer un vmod_path à varnishd instances démarrées à l'aide de la commande varnish -start dans votre cas de test :

varnishtest -p vmod_path=... /chemin/vers/*.vtc

De cette façon, vous pouvez utiliser les mêmes cas de test sur des VMOD installés et construits :

server s1 {...} -start
varnish v1 -vcl+backend {
    import wossname;
    ...
} -start
...

Vous n'êtes pas limité à vmod_path et pouvez passer n'importe quel paramètre, vous permettant d'exécuter une matrice de build sans changer la suite de tests. Vous pouvez obtenir le même résultat avec des macros, mais elles doivent alors être définies à chaque exécution.

Vous pouvez voir les lignes de commande varnishd réelles dans les sorties de test, elles ressemblent à ceci :

exec varnishd [paramètres varnish -p] [paramètres de test] [paramètres de vtc -arg]

Les paramètres que vous définissez avec varnishtest -p peuvent être remplacés par les paramètres nécessaires à varnishtest pour fonctionner correctement, et ils peuvent à leur tour être remplacés par les paramètres définis dans les scripts de test.

Il existe également un mode spécial dans lequel varnishtest construit lui-même un PATH et un vmod_path afin de trouver les binaires de Varnish (programmes et VMODs) dans l'arborescence de build qui entoure le binaire varnishtest. Ceci est destiné aux tests de Varnish en cours de développement et ignorera votre vmod_path si vous en définissez un.

Si vous devez tester votre VMOD contre une arborescence de build de Varnish, vous devez d'abord l'installer, par exemple dans un répertoire temporaire. Avec les informations fournies par pkg-config(1) de l'installation, vous pouvez construire un PATH approprié pour accéder aux programmes Varnish, et un vmod_path pour accéder à la fois à votre VMOD et aux VMODs intégrés :

export PKG_CONFIG_PATH=/chemin/vers/installation/lib/pkgconfig
BINDIR="$(pkg-config --variable=bindir varnishapi)"
SBINDIR="$(pkg-config --variable=sbindir varnishapi)"
PATH="SBINDIR:BINDIR:$PATH"
VMODDIR="$(pkg-config --variable=vmoddir varnishapi)"
VMOD_PATH="/chemin/vers/votre/repertoire/build/vmod:$VMODDIR"
varnishtest -p vmod_path="$VMOD_PATH" ...
