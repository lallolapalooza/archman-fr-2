vwait(n) Commandes intégrées Tcl vwait(n)

NOM

vwait - Traite les événements jusqu'à ce qu'une variable soit écrite

SYNOPSIS

vwait nomVar

DESCRIPTION

Cette commande entre dans la boucle d'événements Tcl pour traiter les événements, bloquant l'application si aucun événement n'est prêt. Elle continue le traitement des événements jusqu'à ce qu'un gestionnaire d'événements quelconque définisse la valeur de la variable globale nomVar. Une fois que nomVar a été définie, la commande vwait ne retournera que lorsque le gestionnaire d'événements qui a modifié nomVar aura terminé son exécution. L'argument nomVar est toujours interprété comme un nom de variable dans l'espace de noms global, mais peut faire référence aux variables de n'importe quel espace de noms si le nom complètement qualifié est donné.

Dans certains cas, la commande vwait peut ne pas retourner immédiatement après que nomVar a été définie. Cela se produit si le gestionnaire d'événements qui définit nomVar ne se termine pas immédiatement. Par exemple, si un gestionnaire d'événements définit nomVar puis appelle lui-même vwait pour attendre une autre variable, il peut ne pas retourner avant longtemps. Pendant ce temps, le vwait de haut niveau est bloqué en attendant que le gestionnaire d'événements se termine, il ne peut donc pas retourner non plus. (Voir les ATTENTES NIDIFIÉES PAR L'EXEMPLE ci-dessous.)

Pour être clair, plusieurs appels à vwait s'empileront et ne se produiront pas en parallèle. L'appel le plus externe à vwait ne retournera que lorsque tous les appels internes auront retourné. Il est recommandé que le code ne devrait jamais empiler les appels à vwait (en évitant de les mettre dans des rappels d'événements), mais lorsque cela n'est pas possible, il faut prendre soin d'ajouter des variables d'interverrouillage au code pour prévenir tous les appels réentrants à vwait qui ne sont pas *strictement* nécessaires. Sachez que les modes de fonctionnement synchrones de certains packages Tcl (par exemple, http) utilisent vwait en interne ; si vous utilisez la boucle d'événements, il est préférable d'utiliser les modes de fonctionnement asynchrones basés sur les rappels de ces packages lorsque cela est disponible.

EXEMPLES

Exécute la boucle d'événements en continu jusqu'à ce qu'un événement appelle exit. (Vous pouvez utiliser n'importe quelle variable non mentionnée ailleurs, mais le nom forever rappelle l'intention en un coup d'œil.)

vwait forever

Attend cinq secondes pour une connexion à un socket serveur, sinon ferme le socket et continue l'exécution du script :

# Initialise l'état
after 5000 set state timeout
set server [socket -server accept 12345]
proc accept {args} {
    global state connectionInfo
    set state accepted
    set connectionInfo $args
}
# Attend que quelque chose se passe
vwait state
# Nettoie les événements qui auraient pu se produire
close $server
after cancel set state timeout
# Fait quelque chose en fonction de la façon dont vwait s'est terminé...
switch $state {
    timeout {
        puts "pas de connexion sur le port 12345"
    }
    accepted {
       puts "connexion : $connectionInfo"
       puts [lindex $connectionInfo 0] "Bonjour !"
    }
}

Une commande qui attendra un délai, en attendant qu'une variable d'un espace de noms soit définie. Inclut un interverrouillage pour empêcher les attentes imbriquées.

namespace eval example {
    variable v done
    proc wait {delay} {
        variable v
        if {$v ne "waiting"} {
            set v waiting
            after $delay [namespace code {set v done}]
            vwait [namespace which -variable v]
        }
        return $v
    }
}

Lorsqu'il s'exécute à l'intérieur d'une coroutine, une alternative à l'utilisation de vwait est de céder à une boucle d'événements externe et d'être repris lorsque la variable est définie, ou à un moment inactif après cela.

coroutine tache apply {{} {
    # simule [after 1000]
    after 1000 [info coroutine]
    yield
    # planifie la définition d'une variable globale, comme d'habitude
    after 2000 {set var 1}
    # simule [vwait var]
    proc updatedVar {tache args} {
        after idle $tache
        trace remove variable ::var write "updatedVar $tache"
    }
    trace add variable ::var write "updatedVar [info coroutine]"
    yield
}}

ATTENTES NIDIFIÉES PAR L'EXEMPLE

Cet exemple démontre ce qui peut arriver lorsque la commande vwait est imbriquée. Le script ne se terminera jamais car l'attente de la variable a ne se termine jamais ; cette commande vwait attend toujours qu'un script planifié avec after se termine, lequel se trouve justement exécuter un vwait interne (pour b) même si l'événement que le vwait externe attendait (la définition de a) s'est produit.

after 500 {
    puts "attente de b"
    vwait b
    puts "b a été défini"
}
after 1000 {
    puts "définition de a"
    set a 10
}
puts "attente de a"
vwait a
puts "a a été défini"
puts "définition de b"
set b 42

Si vous exécutez le code ci-dessus, vous obtenez cette sortie :

attente de a
attente de b
définition de a

Le script n'imprimera jamais « a a été défini » avant d'avoir imprimé « b a été défini » à cause de l'imbrication des commandes vwait, et pourtant b ne sera pas défini avant que le vwait externe ne retourne, donc le script s'est bloqué (deadlock). Les seules façons d'éviter cela sont soit de structurer le programme global en style de passage de continuation, soit d'utiliser coroutine pour rendre les continuations implicites. La première de ces options serait écrite comme suit :

after 500 {
    puts "attente de b"
    trace add variable b write {apply {args {
        global a b
        trace remove variable ::b write \
                [lrange [info level 0] 0 1]
        puts "b a été défini"
        set ::done ok
    }}}
}
after 1000 {
    puts "définition de a"
    set a 10
}
puts "attente de a"
trace add variable a write {apply {args {
    global a b
    trace remove variable a write [lrange [info level 0] 0 1]
    puts "a a été défini"
    puts "définition de b"
    set b 42
}}}
vwait done

La deuxième option, avec coroutine et quelques procédures auxiliaires, se fait comme suit :

# Une commande d'attente de variable basée sur les coroutines
proc waitvar globalVar {
    trace add variable ::$globalVar write \
            [list apply {{v c args} {
        trace remove variable $v write \
                [lrange [info level 0] 0 3]
        after 0 $c
    }} ::$globalVar [info coroutine]]
    yield
}
# Une commande d'attente de temps basée sur les coroutines
proc waittime ms {
    after $ms [info coroutine]
    yield
}
coroutine task-1 eval {
    puts "attente de a"
    waitvar a
    puts "a a été défini"
    puts "définition de b"
    set b 42
}
coroutine task-2 eval {
    waittime 500
    puts "attente de b"
    waitvar b
    puts "b a été défini"
    set done ok
}
coroutine task-3 eval {
    waittime 1000
    puts "définition de a"
    set a 10
}
vwait done
