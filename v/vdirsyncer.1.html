NOM

vdirsyncer - Documentation de vdirsyncer

  • Documentation
  • Code source

Vdirsyncer est un outil en ligne de commande pour synchroniser des calendriers et des carnets d'adresses entre divers serveurs et le système de fichiers local. L'utilisation la plus courante est de synchroniser un serveur avec un dossier local et d'utiliser un ensemble d'autres programmes pour modifier les événements et contacts locaux. Vdirsyncer peut ensuite resynchroniser ces modifications vers le serveur.

Cependant, vdirsyncer ne se limite pas à la synchronisation entre clients et serveurs. Il peut également être utilisé pour synchroniser directement des calendriers et/ou des carnets d'adresses entre deux serveurs.

QUAND AI-JE BESOIN DE VDIRSYNCER ?

Pourquoi pas Dropbox + todo.txt ?

Que fait un logiciel de synchronisation de fichiers si les deux fichiers ont été modifiés depuis la dernière synchronisation ? La réponse est d'ignorer la question, de synchroniser aussi souvent que possible, et d'espérer le meilleur. Car en cas de conflit de synchronisation, la plupart des services de synchronisation n'osent pas fusionner les fichiers et créent plutôt deux copies sur chaque ordinateur. La fusion des deux listes de tâches est laissée à l'utilisateur.

Une meilleure idée aurait été d'utiliser git pour synchroniser le fichier todo.txt, qui est au moins capable de résoudre quelques conflits de base.

Pourquoi pas la synchronisation de fichiers (Dropbox, git, ...) + vdir ?

Comme les vdirs ne sont qu'un ensemble de fichiers, il est évident d'essayer la synchronisation de fichiers pour synchroniser vos données entre plusieurs ordinateurs, tels que :

  • Syncthing
  • Dropbox ou l'un des gajillions de services similaires
  • unison
  • Juste git avec un sshd.

Les inconvénients de ces solutions dépendent largement du programme de synchronisation de fichiers exact choisi :

  • Comme avec todo.txt, Dropbox et ses semblables sont évidemment agnostiques/inconscients du contenu des fichiers. Si un fichier a été modifié des deux côtés, Dropbox copie simplement les deux versions des deux côtés.

    C'est une bonne idée si l'utilisateur interagit directement avec le système de fichiers et est capable de résoudre les conflits lui-même. Ici, cela pourrait entraîner un comportement erroné avec, par exemple, khal, car il y a maintenant deux événements avec le même UID.

    Ce point ne s'applique pas à git : il possède d'excellentes capacités de fusion, meilleures que celles que vdirsyncer a actuellement.

  • Une telle configuration ne fonctionne pas du tout avec les smartphones. Vdirsyncer, en revanche, se synchronise avec les serveurs CardDAV/CalDAV, qui sont accessibles avec, par exemple, DAVx⁵ ou d'autres applications intégrées aux smartphones.

Installation manuelle

Si votre distribution ne fournit pas de paquet pour vdirsyncer, vous pouvez toujours utiliser le gestionnaire de paquets de Python, "pip". Tout d'abord, vous devrez vérifier que les éléments suivants sont installés :

  • Python 3.8 à 3.13 et pip.
  • libxml et libxslt
  • zlib
  • Linux ou macOS. Windows n'est pas pris en charge, voir le problème #535.

Sur les systèmes Linux, l'utilisation du gestionnaire de paquets de la distribution est le meilleur moyen de le faire, par exemple, en utilisant Ubuntu :

sudo apt-get install libxml2 libxslt1.1 zlib1g python3

Ensuite, vous avez plusieurs options. Le texte suivant s'applique d'ailleurs à la plupart des logiciels Python.

pipx: La méthode propre et facile

pipx installera vdirsyncer dans ~/.local/pipx/venvs/vdirsyncer

En supposant que pipx est installé, vdirsyncer peut être installé avec :

pipx install vdirsyncer

Il peut ensuite être mis à jour vers la dernière version avec :

pipx upgrade vdirsyncer

Et peut être désinstallé avec :

pipx uninstall vdirsyncer

Cette dernière commande supprimera vdirsyncer et toutes les dépendances installées dans l'emplacement ci-dessus.

La méthode sale et facile

Si pipx n'est pas disponible sur votre distribution, le moyen le plus simple d'installer vdirsyncer à ce stade serait d'exécuter :

•

Cette méthode a cependant un défaut majeur : Pip ne suit pas les fichiers qu'il installe. Les fichiers de Vdirsyncer seraient situés quelque part dans ~/.local/lib/python*, mais vous ne pouvez pas savoir quels paquets ont été installés

Installation

There are two ways to install vdirsyncer:

The easy, but dirty, way

This is the way you'd install any other Python package. The command is:

pip install vdirsyncer

The problem with this method is that it installs packages globally on your system, which has several drawbacks:

  • It requires root privileges.
  • It pollutes your system's Python environment. If some other package requires a version of a dependency that vdirsyncer doesn't want, you'll have problems.
  • It will install data files into system directories. You won't be able to tell which files were installed as dependencies of vdirsyncer and which ones were not, should you decide to uninstall it. In other words, using pip that way would pollute your home directory.

The clean, hard way

virtualenv ~/vdirsyncer_env
~/vdirsyncer_env/bin/pip install vdirsyncer
alias vdirsyncer="~/vdirsyncer_env/bin/vdirsyncer"

You'll have to put the last line into your .bashrc or .bash_profile.

This method has two advantages:

  • It separately installs all Python packages into ~/vdirsyncer_env/, without relying on the system packages. This works around OS- or distro-specific issues.
  • You can delete ~/vdirsyncer_env/ to uninstall vdirsyncer entirely.

Configuration

NOTE:

  • The config.example from the repository contains a very terse version of this.
  • In this example we set up contacts synchronization, but calendar sync works almost the same. Just swap type = "carddav" for type = "caldav" and fileext = ".vcf" for fileext = ".ics".
  • Take a look at the Known Problems page if anything doesn't work like planned.

By default, vdirsyncer looks for its configuration file in the following locations:

  • The file pointed to by the VDIRSYNCER_CONFIG environment variable.
  • ~/.vdirsyncer/config.
  • $XDG_CONFIG_HOME/vdirsyncer/config, which is normally ~/.config/vdirsyncer/config. See the XDG-Basedir specification.

The config file should start with a general section, where the only required parameter is status_path. The following is a minimal example:

[general]
status_path = "~/.vdirsyncer/status/"

After the general section, an arbitrary amount of pair and storage sections might come.

In vdirsyncer, synchronization is always done between two storages. Such storages are defined in storage sections, and which pairs of storages should actually be synchronized is defined in pair section. This format is copied from OfflineIMAP, where storages are called repositories and pairs are called accounts.

The following example synchronizes ownCloud's addressbooks to ~/.contacts/:

[pair my_contacts]
a = "my_contacts_local"
b = "my_contacts_remote"
collections = ["from a", "from b"]
[storage my_contacts_local]
type = "filesystem"
path = "~/.contacts/"
fileext = ".vcf"
[storage my_contacts_remote]
type = "carddav"
# We can simplify this URL here as well. In theory it shouldn't matter.
url = "https://owncloud.example.com/remote.php/carddav/"
username = "bob"
password = "asdf"

NOTE:

Configuration for other servers can be found at Servers.

After running vdirsyncer discover and vdirsyncer sync, ~/.contacts/ will contain subfolders for each addressbook, which in turn will contain a bunch of .vcf files which all contain a contact in VCARD format each. You can modify their contents, add new ones and delete some [1], and your changes will be synchronized to the CalDAV server after you run vdirsyncer sync again. For further reference, it uses the storages filesystem and carddav.

However, if new collections are created on the server, it will not automatically start synchronizing those [2]. You need to run vdirsyncer discover again to re-fetch this list instead.

[1]
You'll want to use a helper program for this.
[2]
Because collections are added rarely, and checking for this case before every synchronization isn't worth the overhead.

More Configuration

Conflict resolution

What if the same item is changed on both sides? What should vdirsyncer do? Three options are currently provided:

1.
vdirsyncer displays an error message (the default);
2.
vdirsyncer chooses one alternative version over the other;
3.
vdirsyncer starts a command of your choice that is supposed to merge the two alternative versions.

Options 2 and 3 require adding a "conflict_resolution" parameter to the pair section. Option 2 requires giving either "a wins" or "b wins" as value to the parameter:

[pair my_contacts]
...
conflict_resolution = "b wins"

Earlier we wrote that b = "my_contacts_remote", so when vdirsyncer encounters the situation where an item changed on both sides, it will simply overwrite the local item with the one from the server.

Option 3 requires specifying as value of "conflict_resolution" an array starting with "command" and containing paths and arguments to a command. For example:

[pair my_contacts]
...
conflict_resolution = ["command", "vimdiff"]

In this example, vimdiff <a> <b> will be called with <a> and <b> being two temporary files containing the conflicting files. The files need to be exactly the same when the command returns. More arguments can be passed to the command by adding more elements to the array.

See Pair Section for the reference documentation.

Metadata synchronization

Besides items, vdirsyncer can also synchronize metadata like the addressbook's or calendar's "human-friendly" name (internally called "displayname") or the color associated with a calendar. For the purpose of explaining this feature, let's switch to a different base example. This time we'll synchronize calendars:

[pair my_calendars]
a = "my_calendars_local"
b = "my_calendars_remote"
collections = ["from a", "from b"]
metadata = ["color"]
[storage my_calendars_local]
type = "filesystem"
path = "~/.calendars/"
fileext = ".ics"
[storage my_calendars_remote]
type = "caldav"
url = "https://owncloud.example.com/remote.php/caldav/"
username = "bob"
password = "asdf"

Run vdirsyncer discover for discovery. Then you can use vdirsyncer metasync to synchronize the color property between your local calendars in ~/.calendars/ and your ownCloud. Locally the color is just represented as a file called color within the calendar folder.

More information about collections

"Collection" is a collective term for addressbooks and calendars. A Cardav or Caldav server can contains several "collections" which correspond to several addressbooks or calendar.

Each collection from a storage has a "collection name", a unique identifier for each collection. In the case of filesystem-storage, this is the name of the directory that represents the collection, in the case of the DAV-storages this is the last segment of the URL. We use this identifier in the collections parameter in the pair-section.

This identifier doesn't change even if you rename your calendar in whatever UI you have, because that only changes the so-called "displayname" property [3]. On some servers (iCloud, Google) this identifier is randomly generated and has no correlation with the displayname you chose.

[3]
Which you can also synchronize with metasync using metadata = ["displayname"].

There are three collection names that have a special meaning:

  • "from a", "from b": A placeholder for all collections that can be found on side A/B when running vdirsyncer discover.
  • null: The parameters give to the storage are exact and require no discovery.

The last one requires a bit more explanation. Assume this config which synchronizes two directories of addressbooks:

[pair foobar]
a = "foo"
b = "bar"
collections = ["from a", "from b"]
[storage foo]
type = "filesystem"
fileext = ".vcf"
path = "./contacts_foo/"
[storage bar]
type = "filesystem"
fileext = ".vcf"
path = "./contacts_bar/"

As we saw previously this will synchronize all collections in ./contacts_foo/ with each same-named collection in ./contacts_bar/. If there

'est une collection qui existe d'un côté mais pas de l'autre, vdirsyncer demandera si le dossier doit être créé de l'autre côté.

Si nous définissons collections = null, ./contacts_foo/ et ./contacts_bar/ ne sont plus traités comme des dossiers avec des collections, mais comme des collections elles-mêmes. Cela signifie que ./contacts_foo/ et ./contacts_bar/ contiendront des fichiers .vcf, et non des sous-dossiers contenant des fichiers .vcf.

Ceci est utile dans les situations où la liste de toutes les collections échoue car votre serveur DAV ne le prend pas en charge, par exemple. Dans ce cas, vous pouvez définir l' url de votre stockage carddav ou caldav vers une URL qui pointe directement vers votre collection CalDAV/CardDAV.

Notez que tous les stockages ne prennent pas en charge la collection null, par exemple google_contacts et google_calendar ne le font pas.

Configuration avancée des collections (synchronisation serveur-à-serveur)

Les exemples ci-dessus sont suffisants si vous souhaitez synchroniser un serveur distant avec un disque précédemment vide. Cependant, des astuces supplémentaires sont nécessaires lorsque vous avez deux serveurs avec des collections déjà existantes que vous souhaitez synchroniser.

Le problème principal dans cette situation est que vdirsyncer associe les collections par leur nom par défaut (voir la définition dans la section précédente, essentiellement un nom de dossier ou un UUID distant). Lorsque vous avez deux serveurs, ces noms de collections peuvent ne pas correspondre joliment. Supposons que vous avez créé deux calendriers "Test", un sur un serveur NextCloud et un sur iCloud, en utilisant leurs interfaces Web respectives. Les URL ressemblent à ceci:

NextCloud: https://example.com/remote.php/dav/calendars/user/test/
iCloud:    https://p-XX.caldav.icloud.com/YYY/calendars/3b4c9995-5c67-4021-9fa0-be4633623e1c

Ce sont deux collections de calendrier DAV. Leurs noms de collection seront respectivement test et 3b4c9995-5c67-4021-9fa0-be4633623e1c, vous n'avez donc pas un seul nom pour les adresser toutes les deux. Vous devrez manuellement "associer" (aucun jeu de mots) ces collections comme ceci:

[pair doublecloud]
a = "my_nextcloud"
b = "my_icloud"
collections = [["mytest", "test", "3b4c9995-5c67-4021-9fa0-be4633623e1c"]]

mytest donne à cette combinaison de calendriers un nom agréable que vous pouvez utiliser pour en parler, vous utiliseriez donc vdirsyncer sync doublecloud/mytest pour dire : "Synchronisez uniquement ces deux stockages, rien d'autre qui pourrait être configuré".

NOTE :

Pourquoi ne pas utiliser les displaynames ?

Vous vous demandez peut-être pourquoi vdirsyncer n'a pas pu simplement le découvrir par lui-même. Après tout, vous avez nommé les deux collections "Test" (ce qui s'appelle "le displayname"), alors pourquoi ne pas associer les collections par cette valeur ?

Il y a quelques problèmes avec cette idée :

  • Deux calendriers peuvent avoir exactement le même displayname.
  • Un calendrier peut ne pas avoir de displayname (non vide).
  • Le displayname peut changer. Soit vous renommez le calendrier, soit le calendrier se renomme car vous changez un paramètre de langue.

En fin de compte, cette propriété n'a jamais été conçue pour être analysée par des machines.

STOCKAGE DES MOTS DE PASSE

Modifié en version 0.7.0 : La configuration des mots de passe a été complètement remaniée.

Vdirsyncer peut récupérer les mots de passe à partir de plusieurs sources autres que le fichier de configuration.

Commande

Disons que vous avez la configuration suivante :

[storage foo]
type = "caldav"
url = ...
username = "foo"
password = "bar"

Mais cela vous dérange que le mot de passe soit stocké en clair dans le fichier de configuration. Vous pouvez faire ceci :

[storage foo]
type = "caldav"
url = ...
username = "foo"
password.fetch = ["command", "~/get-password.sh", "more", "args"]

Vous pouvez également récupérer le nom d'utilisateur :

[storage foo]
type = "caldav"
url = ...
username.fetch = ["command", "~/get-username.sh"]
password.fetch = ["command", "~/get-password.sh"]

Ou vraiment n'importe quel type de paramètre dans une section de stockage.

Vous pouvez également passer la commande sous forme de chaîne à exécuter dans un shell :

password.fetch = ["command", "pass", "caldav"]

Accéder au porte-clés système

Comme indiqué ci-dessus, vous pouvez utiliser la stratégie command pour récupérer vos identifiants à partir de sources arbitraires. Un cas d'utilisation très courant est de récupérer votre mot de passe à partir du porte-clés système.

pip install keyring

Utilisation de base :

password.fetch = ["command", "keyring", "get", "example.com", "foouser"]

Invite de mot de passe

Vous pouvez également simplement demander le mot de passe :

[storage foo]
type = "caldav"
username = "myusername"
password.fetch = ["prompt", "Mot de passe pour CalDAV"]

Variable d'environnement

Pour lire le mot de passe à partir d'une variable d'environnement :

[storage foo]
type = "caldav"
username = "myusername"
password.fetch = ["command", "printenv", "DAV_PW"]

Ceci est particulièrement utile si vous utilisez le même mot de passe plusieurs fois (par exemple, pour un stockage CardDAV et un stockage CalDAV). Sur bash, vous pouvez lire et exporter le mot de passe sans l'afficher :

Étape 1 : Créer le calendrier cible

Vous devez d'abord créer le calendrier avec lequel vous souhaitez synchroniser le calendrier WebCAL. La plupart des serveurs proposent une interface web pour cela. Vous devrez ensuite noter l'URL CalDAV de votre calendrier. Notez que cette URL doit pointer directement vers le calendrier que vous venez de créer, ce qui signifie que vous aurez une URL de ce type pour chaque calendrier que vous possédez.

Étape 2 : Créer la configuration

Collez ceci dans votre configuration vdirsyncer :

[pair holidays]
a = "holidays_public"
b = "holidays_private"
collections = null
[storage holidays_public]
type = "http"
# L'URL de votre fichier iCalendar.
url = "..."
[storage holidays_private]
type = "caldav"
# L'URL directe de votre calendrier.
url = "..."
# Les identifiants de votre serveur CalDAV
username = "..."
password = "..."

Ensuite, exécutez vdirsyncer discover holidays et vdirsyncer sync holidays, et votre calendrier précédemment créé devrait être rempli d'événements.

Étape 3 : Le paramètre partial_sync

Ajouté dans la version 0.14.

Vous pourriez vous retrouver dans une situation où vous souhaitez masquer ou modifier certains événements de votre calendrier holidays. Si vous essayez de le faire à ce stade, vous remarquerez que vdirsyncer annulera toute modification que vous avez apportée après quelques exécutions de sync. C'est parce que vdirsyncer veut tout maintenir synchronisé, et il ne peut pas synchroniser les modifications apportées au calendrier public des jours fériés car il n'a pas les droits pour le faire.

À ces fins, vous pouvez définir le paramètre partial_sync sur ignore :

[pair holidays]
a = "holidays_public"
b = "holidays_private"
collections = null
partial_sync = ignore

Voir la documentation de configuration pour plus d'informations.

Section Générale

[general]
status_path = ...
•
status_path : Un répertoire où vdirsyncer stockera des données supplémentaires pour la prochaine synchronisation.

Les données sont nécessaires pour déterminer si un nouvel élément signifie qu'il a été ajouté d'un côté ou supprimé de l'autre. Les chemins relatifs seront interprétés comme étant relatifs au répertoire du fichier de configuration.

Section de Paire

[pair pair_name]
a = ...
b = ...
#collections = null
#conflict_resolution = null
  • Les noms de paire peuvent être constitués de caractères alphanumériques et du caractère de soulignement.
  • a et b font référence aux stockages à synchroniser par leurs noms.
  • collections : Une liste de collections à synchroniser lors de l'exécution de vdirsyncer sync. Voir aussi Plus d'informations sur les collections.

    Les valeurs spéciales "from a" et "from b" indiquent à vdirsyncer d'essayer la découverte automatique sur un stockage spécifique. Cela signifie toutes les collections du côté A / côté B.

    Si la collection que vous souhaitez synchroniser n'a pas le même nom de chaque côté, vous pouvez également utiliser une valeur de la forme ["nom_config", "nom_a", "nom_b"]. Cela synchronisera la collection nom_a du côté A avec la collection nom_b du côté B. Le nom_config sera utilisé pour la représentation dans les arguments de la ligne de commande et la journalisation.

    Exemples :

  • collections = ["from b", "foo", "bar"] fait en sorte que vdirsyncer synchronise toutes les collections du côté B, ainsi que les collections nommées "foo" et "bar".
  • collections = ["from b", "from a"] fait en sorte que vdirsyncer synchronise toutes les collections existantes de chaque côté.
  • collections = [["bar", "bar_a", "bar_b"], "foo"] fait en sorte que vdirsyncer synchronise bar_a du côté A avec bar_b du côté B, et synchronise également foo des deux côtés l'un avec l'autre.
•
conflict_resolution : Facultatif, définit comment gérer les conflits. Un conflit survient lorsqu'un élément (événement, tâche) a été modifié des deux côtés depuis la dernière synchronisation. Voir aussi Résolution des conflits.

Les valeurs valides sont :

  • null, où une erreur est affichée et aucune modification n'est effectuée.
  • "a wins" et "b wins", où l'élément entier est pris d'un côté.
  • ["command", "vimdiff"] : vimdiff <a> <b> sera appelé où <a> et <b> sont des fichiers temporaires contenant respectivement l'élément de chaque côté. Les fichiers doivent être exactement les mêmes lorsque la commande renvoie.
  • vimdiff peut être remplacé par n'importe quelle autre commande. Par exemple, en POSIX, ["command", "cp"] équivaut à "a wins".
  • Les éléments de liste supplémentaires seront transmis en tant qu'arguments. Par exemple, ["command", "vimdiff", "--noplugin"] exécute vimdiff --noplugin.

Vdirsyncer ne tente jamais de "fusionner automatiquement" les deux éléments.

•
partial_sync : Supposer que A est en lecture seule, B ne l'est pas. Si vous modifiez des éléments sur B, vdirsyncer ne peut pas synchroniser les modifications sur A. Que doit-il se passer à la place ?
  • error : Une erreur est affichée.
  • ignore : La modification est ignorée. Cependant : Les événements supprimés dans B réapparaissent toujours s'ils sont mis à jour dans A.
  • revert (par défaut) : La modification est annulée lors de la prochaine synchronisation.

Voir aussi Synchronisation avec des stockages en lecture seule.

•
metadata : Clés de métadonnées qui doivent être synchronisées lors de l'exécution de vdirsyncer metasync. Exemple :
metadata = ["color", "displayname", "description", "order"]

Ceci synchronise les propriétés suivantes :

  • color : http://apple.com/ns/ical/:calendar-color
  • displayname : DAV:displayname
  • description : CalDAV:calendar-description et CardDAV:addressbook-description

[storage storage_name]

  • Les noms de stockage peuvent être constitués de caractères alphanumériques et du caractère de soulignement.
  • type définit le type de stockage. Voir Stockages Supportés.

Trop de fournisseurs WebCAL génèrent des UID de tous les composants VEVENT à la volée, c'est-à-dire que tous les UID changent chaque fois que le calendrier est téléchargé. Cela amène de nombreux programmes de synchronisation à croire que tous les événements ont été supprimés et de nouveaux créés, et par conséquent provoque de nombreux téléchargements et suppressions inutiles de l'autre côté. Vdirsyncer ignore complètement les UID provenant de http et les remplacera par un hachage du contenu normalisé de l'élément.

Paramètres
  • url -- URL du fichier .ics.
  • username -- Nom d'utilisateur pour l'authentification.
  • password -- Mot de passe pour l'authentification.
  • verify -- Facultatif. Chemin local vers un certificat SSL auto-signé. Voir Validation SSL et des certificats pour plus d'informations.
  • verify_fingerprint -- Facultatif. Empreinte SHA256 du certificat serveur attendu. Voir Validation SSL et des certificats pour plus d'informations.
  • auth -- Facultatif. Soit basic, digest ou guess. La valeur par défaut est l'authentification Basic préventive, envoyant les identifiants même si le serveur ne les a pas demandés. Cela évite un aller-retour supplémentaire par requête. Envisagez de définir guess si cela cause des problèmes avec votre serveur.
  • auth_cert -- Facultatif. Soit un chemin vers un certificat avec un certificat client et la clé, soit une liste de chemins vers les fichiers correspondants.
  • useragent -- Par défaut vdirsyncer.
  • filter_hook -- Facultatif. Une commande de filtrage à appeler pour chaque élément récupéré, passée sous forme brute à stdin et retournée via stdout. Si rien n'est retourné par la commande de filtrage, l'élément est ignoré. Cela peut être utilisé pour modifier les champs si nécessaire lors du traitement de fournisseurs générant des événements mal formés.

Vdirsyncer avec Claws Mail

Tout d'abord, Claws-Mail ne prend en charge que les fonctions en lecture seule pour les vCards. Il peut uniquement lire les contacts, mais il n'y a pas d'éditeur.

Préparation

Nous devons installer vdirsyncer, pour cela regardez ici. Ensuite, nous devons créer quelques dossiers :

mkdir ~/.vdirsyncer
mkdir ~/.contacts

Configuration

Nous créons maintenant la configuration pour vdirsyncer. Ouvrez ~/.vdirsyncer/config avec un éditeur de texte. La configuration devrait ressembler à ceci :

[general]
status_path = "~/.vdirsyncer/status/"
[storage local]
type = "singlefile"
path = "~/.contacts/%s.vcf"
[storage online]
type = "carddav"
url = "CARDDAV_LINK"
username = "USERNAME"
password = "PASSWORD"
read_only = true
[pair contacts]
a = "local"
b = "online"
collections = ["from a", "from b"]
conflict_resolution = "b wins"
  • Dans la section générale, nous définissons le chemin du dossier de statut, pour les collections découvertes et généralement les éléments qui doivent persister entre les synchronisations.
  • Dans la section locale, nous définissons que tous les contacts doivent être synchronisés dans un seul fichier et le chemin pour les contacts.
  • Dans la section en ligne, vous devez modifier l'url, le nom d'utilisateur et le mot de passe pour votre configuration. Nous définissons également le stockage en lecture seule afin qu'aucun changement ne soit synchronisé en retour. Claws-Mail ne devrait de toute façon pas être capable d'effectuer des modifications, mais c'est une mesure de sécurité supplémentaire au cas où les fichiers seraient corrompus ou si vdirsyncer se comportait de manière erratique. Vous pouvez omettre cette partie si vous souhaitez pouvoir modifier ces fichiers localement.
  • Dans la dernière section, nous configurons que les contacts en ligne l'emportent en cas de conflit. Configurez cette partie comme vous le souhaitez. Une valeur correcte dépend de quel côté est le plus susceptible d'être à jour.

Synchronisation

Nous découvrons et synchronisons maintenant nos contacts :

vdirsyncer discover contacts
vdirsyncer sync contacts

Ouvrez Claws-Mail. Allez dans Outils => Carnet d'adresses.

Cliquez sur Carnet d'adresses => Nouvelle vCard. Choisissez un nom pour le carnet.

Recherchez ensuite la vCard dans le dossier ~/.contacts/. Cliquez sur OK, et vous verrez vos contacts.

Crontab

Enfin, nous créons un crontab, afin que vdirsyncer synchronise automatiquement nos contacts toutes les 30 minutes :

crontab -e

À la fin de ce fichier, entrez cette ligne :

*/30 * * * * /usr/local/bin/vdirsyncer sync > /dev/null

Et vous avez terminé !

Exécution en tant que systemd.timer

vdirsyncer inclut des fichiers d'unité pour s'exécuter à intervalles réguliers (par défaut toutes les 15 ± 5 minutes).

NOTE :

Ceux-ci ne sont pas installés lors de l'installation via pip, seulement via les paquets de distribution. Si vous avez installé via pip, ou si votre distribution ne fournit pas de fichiers d'unité systemd, vous devrez télécharger vdirsyncer.service et vdirsyncer.timer dans soit /etc/systemd/user/, soit ~/.local/share/systemd/user.

Activation

Pour activer le timer, exécutez simplement systemctl --user enable vdirsyncer.timer. Pour voir les logs des exécutions précédentes, utilisez journalctl --user -u vdirsyncer.

Configuration

Il est tout à fait possible que l'intervalle par défaut "toutes les quinze minutes" ne vous convienne pas. Aucune valeur par défaut ne conviendra à tout le monde, mais ceci est configurable en exécutant simplement :

systemctl --user edit vdirsyncer.timer

Cela ouvrira un éditeur vide, où vous pourrez remplacer le timer en incluant :

OnBootSec=5m  # C'est combien de temps après le démarrage la première exécution a lieu.
OnUnitActiveSec=15m  # C'est la fréquence des exécutions suivantes.

La raison de cette séparation est la suivante : nous prévoyons de générer des rapports de couverture séparés pour chacune de ces suites de tests. Idéalement, unit générerait une couverture acceptable de l'ensemble du code à lui seul, et la combinaison de system et storage également.

LE FORMAT DE STOCKAGE VDIR

Ce document décrit une norme pour stocker des calendriers et des carnets d'adresses sur un système de fichiers, dans le but principal d'être facile à implémenter.

Vdirsyncer se synchronise vers des vdirs via le système de fichiers. Chaque vdir (essentiellement juste un répertoire avec quelques fichiers à l'intérieur) représente un calendrier ou un carnet d'adresses.

Structure de base

Le répertoire principal (racine) contient un nombre arbitraire de sous-répertoires (collections), qui ne contiennent que des fichiers (éléments). Les synonymes de "collection" peuvent être "carnet d'adresses" ou "calendrier".

Un élément est :

  • Un fichier vCard, auquel cas l'extension du fichier doit être .vcf, ou
  • Un fichier iCalendar, auquel cas l'extension du fichier doit être .ics.

Un élément doit contenir une propriété UID telle que décrite par les normes vCard et iCalendar. S'il contient plus d'une propriété UID, les valeurs de celles-ci ne doivent pas différer.

Le fichier doit contenir exactement un événement, une tâche ou un contact. Dans la plupart des cas, cela implique également seulement

un VEVENT/VTODO/VCARD composant par fichier, mais par exemple les exceptions de récurrence nécessiteraient plusieurs composants VEVENT par événement.

Le nom de fichier doit avoir des propriétés similaires à l'UID du contenu du fichier. Cependant, il n'est pas obligatoire que ces deux-là soient identiques. Les programmes peuvent choisir de stocker des métadonnées supplémentaires dans ce nom de fichier, mais en même temps, ils *ne doivent pas* supposer que les métadonnées qu'ils ont inclus seront préservées par d'autres programmes.

Métadonnées

N'importe lequel des fichiers de métadonnées ci-dessous peut être absent. Aucun des fichiers listés ci-dessous n'a d'extension de fichier.

  • Un fichier appelé color à l'intérieur du vdir indique la couleur du vdir, une propriété qui n'est pertinente que dans la conception de l'interface utilisateur.

    Son contenu est une valeur hexadécimale RGB encodée en ASCII de la forme #RRGGBB. Par exemple, un contenu de fichier de #FF0000 indique que le vdir a une couleur rouge (visible par l'utilisateur). Aucune forme courte ou valeur informelle telle que red (comme connu de CSS, par exemple) n'est autorisée. Le préfixe # doit être présent.

  • Les fichiers appelés displayname et description contiennent une étiquette/description encodée en UTF-8, qui peut être utilisée pour représenter le vdir dans les interfaces utilisateur.
  • Un fichier appelé order à l'intérieur du vdir inclut l'ordre relatif du calendrier, une propriété qui n'est pertinente que dans la conception de l'interface utilisateur.

Écriture dans les vdirs

Écrire dans un fichier temporaire sur le même périphérique physique, puis le déplacer à l'emplacement approprié est généralement une solution très efficace. À cette fin, des fichiers avec l'extension .tmp peuvent être créés à l'intérieur des collections.

Lors de la modification d'un élément, le nom de fichier d'origine *doit* être utilisé.

Lecture depuis les vdirs

  • Tout fichier se terminant par .tmp ou sans extension de fichier *ne doit pas* être traité comme un élément.
  • La partie ident du nom de fichier *ne doit pas* être analysée pour améliorer la vitesse de recherche des éléments.

Considérations

Performance

Actuellement, les vdirs souffrent d'un problème de performance assez majeur, que les implémentations actuelles tentent d'atténuer en construisant des index des collections pour une recherche et une recherche plus rapides.

La raison pour laquelle les noms de fichiers des éléments ne contiennent aucune information supplémentaire est simple : les solutions présentées ont induit une duplication de données, où un doublon pourrait devenir obsolète en raison de mauvaises implémentations. Tel qu'il se présente actuellement, un format d'index pourrait cependant être formalisé séparément.

vdirsyncer n'a pas vraiment à se soucier de la recherche efficace d'éléments, car son algorithme de synchronisation doit de toute façon récupérer la liste complète des éléments. La détection des modifications est facilement implémentée en vérifiant l'heure de modification des fichiers.

Versions des dépendances

Comme pour la plupart des packages Python, setup.py indique les dépendances de vdirsyncer. Il contient également les versions minimales de chaque dépendance. Les versions plus anciennes seront rejetées par la suite de tests.

Tests

Tout ce qui concerne les tests passe par le Makefile à la racine du dépôt ou du package PyPI. Essayer, par exemple, d'exécuter pytest directement nécessitera la définition de nombreuses variables d'environnement (pour la configuration) et vous ne voudrez probablement pas vous en occuper.

Vous pouvez installer toutes les dépendances de développement avec :

make install-dev

Vous ne le voudrez probablement pas car cela utilisera pip pour télécharger les dépendances. Alternativement, les dépendances de test sont listées comme dépendances optionnelles test dans pyproject.toml, encore une fois avec des exigences de version minimales.

Vous devez également avoir vdirsyncer entièrement installé à ce point. Se contenter de faire un cd dans l'archive tarball ne sera pas suffisant.

L'exécution des tests se fait avec :

pytest

Hypothesis générera aléatoirement des entrées de test. Si vous vous souciez des tests déterministes, définissez la variable DETERMINISTIC_TESTS sur "true" :

make DETERMINISTIC_TESTS=true test

Il existe de nombreuses variables supplémentaires qui vous permettent de tester vdirsyncer contre un serveur particulier. Ces variables ne sont pas "stables" et peuvent changer radicalement entre les versions mineures. Ne les utilisez pas, il est peu probable que vous trouviez des bugs que le CI de vdirsyncer n'a pas trouvés.

Documentation

En utilisant Sphinx, vous pouvez générer la documentation que vous lisez actuellement dans une variété de formats, tels que HTML, PDF, ou même en tant que page de manuel. Cela dit, je ne m'occupe que du formatage des documents HTML.

Vous pouvez trouver une liste des dépendances dans docs-requirements.txt. Encore une fois, vous pouvez les installer en utilisant pip avec :

pip install -r docs-requirements.txt

Ensuite, déplacez-vous dans le répertoire docs/ et créez le format que vous souhaitez en utilisant le Makefile qui s'y trouve (exécutez make pour les formats que vous pouvez construire).

  • Les invocations de password_command avec un code de sortie non nul sont désormais fatales (et arrêteront la synchronisation) au lieu de produire simplement un avertissement.
  • Vdirsyncer est désormais capable de synchroniser les métadonnées des collections. Définissez metadata = ["displayname"] et exécutez vdirsyncer metasync.
  • Emballeurs : N'utilisez pas les tarballs GitHub, mais ceux de PyPI.
  • Emballeurs : build.sh a disparu, et Makefile est inclus dans les tarballs. Voir le contenu de Makefile pour savoir comment exécuter les tests après l'empaquetage.
  • verify_fingerprint ne désactive plus automatiquement verify.

Version 0.5.2

publié le 15 juin 2015

  • Vdirsyncer vérifie et corrige désormais les permissions des fichiers de statut.
  • Vdirsyncer est désormais plus robuste face aux changements d'UID à l'intérieur des éléments.
  • Vdirsyncer gère désormais correctement les href et les UID Unicode. Les logiciels qui produisent des UID non ASCII sont défectueux, mais ils existent apparemment.

Version 0.5.1

publié le 29 mai 2015

  • N.b. : L'upload PyPI de 0.5.0 est complètement défectueux.
  • Augmente la version de requests-toolbelt requis à 0.4.0.
  • La ligne de commande devrait être beaucoup plus rapide lorsqu'aucun travail n'est effectué, par exemple pour l'affichage de l'aide.
  • Correction de la compatibilité avec iCloud à nouveau.
  • Utilise un seul worker si le mode débogage est activé.
  • verify=false est maintenant interdit dans vdirsyncer, utilisez plutôt verify_fingerprint.
  • Correction d'un bug où le stockage DAV de vdirsyncer n'utilisait pas l'agent utilisateur configuré pour la découverte de collections.

Version 0.4.4

publié le 12 mars 2015

  • Prise en charge des certificats client via le nouveau paramètre auth_cert, voir problème #182 et demande de tirage #183.
  • Le package icalendar n'est plus requis.
  • Plusieurs corrections de bugs liés à la création de collections.

Version 0.4.3

publié le 20 février 2015

  • Plus d'améliorations de performance pour le stockage singlefile.
  • Ajout du paramètre post_hook au stockage filesystem.
  • La création de collections fonctionne désormais également avec les serveurs basés sur SabreDAV, tels que Baikal ou ownCloud.
  • Suppression de quelques solutions de contournement pour Radicale. La mise à jour vers la dernière version de Radicale résoudra les problèmes.
  • Correction des problèmes avec la découverte iCloud.
  • Vdirsyncer inclut désormais une simple commande repair qui vise à corriger certains éléments cassés.

Version 0.4.2

publié le 30 janvier 2015

  • Vdirsyncer respecte désormais les redirections lors du téléchargement et de la mise à jour des éléments. Cela pourrait résoudre les problèmes avec Zimbra.
  • Les valeurs relatives de status_path sont désormais interprétées comme relatives au répertoire du fichier de configuration.
  • Correction de la compatibilité avec les serveurs SabreDAV personnalisés. Voir problème #166.
  • Capture des exceptions de threading inoffensives qui surviennent lors de l'arrêt de vdirsyncer. Voir problème #167.
  • Vdirsyncer dépend désormais de atomicwrites.
  • Améliorations massives des performances pour le stockage singlefile.
  • Les éléments avec des UID extrêmement longs devraient désormais être sauvegardés correctement dans le stockage filesystem. Voir problème #173.

Version 0.4.1

publié le 05 janvier 2015

  • Tous les arguments create de tous les stockages ont disparu. Vdirsyncer demande désormais s'il doit essayer de créer des collections.
  • Les anciennes valeurs de configuration True, False, on, off et None sont désormais invalides.
  • Les conflits d'UID sont désormais correctement gérés au lieu d'ignorer un élément. Les serveurs Card- et CalDAV sont censés s'en occuper cependant.
  • Support officiel de Baikal ajouté.

Version 0.4.0

publié le 31 décembre 2014

  • Le paramètre passwordeval a été renommé en password_command.
  • L'ancienne manière d'écrire certaines valeurs de configuration, comme les listes, a disparu.
  • La découverte de collections a été réécrite. Les anciens fichiers de configuration devraient être compatibles, mais vdirsyncer met désormais en cache les résultats de la découverte de collections. Vous devez exécuter vdirsyncer discover si des collections ont été ajoutées ou supprimées d'un côté.
  • Les noms de paires et de stockages sont désormais restreints à certains caractères. Vdirsyncer affichera un message d'erreur clair si votre fichier de configuration est invalide à cet égard.
  • Vdirsyncer prend désormais en charge la spécification XDG-Basedir. Si la variable d'environnement VDIRSYNCER_CONFIG n'est pas définie et que le fichier ~/.vdirsyncer/config n'existe pas, il recherchera le fichier de configuration à l'adresse $XDG_CONFIG_HOME/vdirsyncer/config.
  • Quelques améliorations de la découverte CardDAV et CalDAV, basées sur des problèmes rencontrés avec FastMail. La prise en charge des URI .well-known a été ajoutée.

Version 0.3.1
