val_add_valpolicy(3)

Paquet: dnssec-tools

Licences: BSD

dnsval.conf(3) Manuel du programmeur dnsval.conf(3)

NOM

dnsval.conf, resolv.conf, root.hints - Politiques de configuration pour la bibliothèque de validation DNSSEC libval(3)

val_add_valpolicy - Ajouter dynamiquement une nouvelle politique au contexte du validateur

val_remove_valpolicy - Supprimer une politique ajoutée dynamiquement du contexte du validateur

SYNTAXE

int val_add_valpolicy(val_context_t *context, 
                void *policy_definition,
                val_policy_entry_t **pol);
int val_remove_valpolicy(val_context_t *context,
                val_policy_entry_t *pol);
typedef struct {
    char *keyword;
    char *zone;
    char *value;
    long ttl;
} libval_policy_definition_t;

DESCRIPTION

Les applications peuvent utiliser une politique locale pour influencer le résultat de la validation. Des exemples d'éléments de politique locale incluent les ancres de confiance pour différentes zones et les algorithmes non fiables pour les clés cryptographiques et les hachages. La politique locale peut varier en fonction des applications et des scénarios d'exploitation.

La fonction val_add_valpolicy() peut être utilisée pour ajouter dynamiquement une nouvelle politique pour un contexte donné (les politiques ne sont pas ajoutées de manière persistante à la configuration du système). Le champ policy_definition contient une définition spécifique à l'implémentation de la politique du validateur à ajouter. Pour la bibliothèque libval, ceci est représenté par la structure libval_policy_definition_t, qui contient quatre champs : les arguments keyword, zone et value sont identiques à keyword, zone et additional-data définis ci-dessous pour dnsval.conf. ttl spécifie la durée en secondes pendant laquelle la politique est maintenue en vigueur. Une valeur tt de -1 ajoute la politique au contexte indéfiniment. Un identifiant de la nouvelle politique ajoutée est retourné dans *pol. Cette structure est opaque pour les applications ; les applications ne doivent pas modifier le contenu de la mémoire retournée dans *pol.

Les applications peuvent également révoquer les effets d'une politique nouvellement ajoutée, pol, avant l'expiration de son intervalle de temps mort en utilisant la politique val_remove_valpolicy().

La bibliothèque de validation lit les informations de configuration à partir de trois fichiers distincts : resolv.conf, root.hints et dnsval.conf.

resolv.conf
Les options nameserver et search sont prises en charge dans le fichier resolv.conf.

L'option nameserver est utilisée pour spécifier l'adresse IP du serveur de noms auquel les requêtes doivent être envoyées par défaut. Par exemple,

nameserver 10.0.0.1

Un certain nombre de champs supplémentaires peuvent être spécifiés pour qualifier le serveur de noms. Par exemple, dans la ligne suivante :

nameserver [10.0.0.1][example.tsigkey:hmac-md5.sig-alg.reg.int:300:0jnu3SdsMvzzlmTDPYRceA==]:8053

example.tsigkey fait référence au nom de la clé TSIG ; hmac-md5.sig-alg.reg.int fait référence à l'algorithme TSIG, 300 est le facteur de fudge TSIG, et la clé est spécifiée comme une valeur encodée en base64. La valeur 8053 fait référence au numéro de port.

Les valeurs de l'algorithme TSIG et du facteur de fudge dans l'exemple ci-dessus sont les valeurs par défaut. Elles peuvent être omises comme suit :

nameserver [10.0.0.1][example.tsigkey:::0jnu3SdsMvzzlmTDPYRceA==]:8053

La partie TSIG peut également être complètement omise, auquel cas la représentation est la suivante :

nameserver [10.0.0.1]:8053

L'option search est utilisée pour spécifier le chemin de recherche pour les requêtes émises. Par exemple,

search test.dnssec-tools.org dnssec-tools.org

L'option forward est utilisée pour rediriger les requêtes pour les noms qui correspondent à un nom de zone donné vers le serveur de noms fourni. Par exemple,

forward 76.216.12.217 test.dnssec-tools.org

Si le fichier resolv.conf ne contient aucun serveur de noms, le validateur tente de répondre récursivement à la requête en utilisant les informations présentes dans root.hints.

root.hints
Le fichier root.hints contient les informations d'amorçage pour le résolveur lors de sa tentative de réponse récursive aux requêtes. Le contenu de ce fichier peut être généré par la commande suivante : 
dig @e.root-servers.net . ns > root.hints
dnsval.conf
Le fichier dnsval.conf contient la politique du validateur. Il se compose d'une séquence des "fragments de politique" suivants : 
<label> <keyword> <additional-data>;

Les politiques sont identifiées par de simples chaînes de caractères appelées étiquettes (labels), qui doivent être uniques dans le système de configuration. Par exemple, "browser" pourrait être utilisée comme étiquette définissant la politique du validateur pour tous les navigateurs web d'un système. Une valeur d'étiquette de ":" identifie la politique par défaut, la politique utilisée lorsqu'un contexte NULL est spécifié comme paramètre ctx pour les interfaces listées dans libval(3), val_getaddrinfo(3), et val_gethostbyname(3). La politique par défaut doit être unique dans le système de configuration.

keyword spécifie le composant de politique dans le fragment de politique. Le format de additional-data dépend du mot-clé spécifié.

Si plusieurs fragments de politique sont définis pour la même combinaison d'étiquette et de mot-clé, la première définition dans le fichier est utilisée.

Les mots-clés suivants sont définis pour dnsval.conf :

trust-anchor
Pour l'attribut "trust-anchor", additional-data est une séquence de paires ordonnées, chacune composée du nom de zone et de la partie RDATA de l'ancre de confiance avec un préfixe optionnel. Les ancres de confiance peuvent être des enregistrements DNSKEY ou DS, le préfixe dans RDATA est utilisé pour indiquer le type d'enregistrement. DNSKEY est supposé si aucun préfixe n'est spécifié.

Un exemple est donné ci-dessous.

browser trust-anchor
    .   DS  19036  8  2  \
        49AAC11D7B6F6446702E54A1607371607A1A41855200FD2CE\
        1CDDE32F24E8FB5
    example.com   257 3 5 AQO8XS4y9r77X 9SHBmrx MoJf1Pf9\
        AT9Mr/L5BBGtO9/e9f/zl4FFgM2l B6M2 XEm6mp6 mit4tzp\
        B/sAEQw1McYz6bJdKkTiqtuWTCfDmgQhI6 /Ha0 Ef GPNSqn\
        Y 99FmbSeWNIRaa4fgSCVFhvbrYq1nXkNVy QPeEVHk oDNCA\
        lr qOA3lw==
;
zone-security-expectation
Pour l'attribut "zone-security-expectation", additional-data est une séquence de tuples <nom de domaine,valeur> représentant l'attente de sécurité pour les noms dans ce domaine, où la valeur peut être l'une des suivantes :
ignore
Ignorer la validation DNSSEC pour les noms sous ce domaine.
validate
Effectuer la validation DNSSEC des réponses reçues pour les noms sous ce domaine.
untrusted
Rejeter toutes les réponses reçues pour les noms sous ce domaine.

Cette construction de politique de validateur DNSSEC zone-security-expectation permet de définir diverses îles de confiance pour les zones prenant en charge DNSSEC et d'ignorer ou de valider les données de zones sélectionnées. L'attente de sécurité par défaut pour un domaine est "validate". Dans l'exemple suivant, pour les contextes de validateur DNSSEC créés avec une étiquette de politique de validateur DNSSEC "browser", la validation DNSSEC n'est effectuée que pour les noms sous le domaine example.com ; les noms sous le domaine somebogus.org sont toujours considérés comme non fiables et la validation DNSSEC pour tous les autres noms de domaine est ignorée.

browser zone-security-expectation   
    example.com  validate      
    somebogusname.org untrusted
    . ignore
;
provably-insecure-status
Pour l'attribut "provably-insecure-status", additional-data est une séquence de tuples <nom de domaine,valeur> représentant la validité de la condition prouvablement non sécurisée, où la valeur est l'une des suivantes :
trusted
Traiter la condition prouvablement non sécurisée comme valide.
untrusted
Traiter la condition de sécurité douteuse comme invalide.

La valeur par défaut pour le statut de sécurité douteuse d'un domaine est "trusted". Dans l'exemple suivant, pour les contextes de validation DNSSEC créés avec le libellé par défaut, la condition de sécurité douteuse est traitée comme valide pour tous les domaines sauf le domaine net, où cette condition est traitée comme invalide.

: provably-insecure-status
    . trusted
    net untrusted
;
clock-skew
Pour l'attribut "clock-skew", les données supplémentaires sont une séquence du nom de domaine et du nombre de secondes de décalage d'horloge acceptable pour les signatures sur les noms de ce domaine. Une valeur de décalage d'horloge de -1 a pour effet de désactiver les vérifications des heures d'inception et d'expiration sur les signatures de ce domaine. Le décalage d'horloge par défaut est de 0. Dans l'exemple suivant, pour les contextes de validation DNSSEC créés avec le libellé "mta", les vérifications d'inception et d'expiration de signature sont désactivées pour tous les noms sous le domaine example.com.
nsec3-max-iter [seulement si LIBVAL_NSEC3 est activé]
Spécifie le nombre maximum d'itérations autorisées lors du calcul du hachage NSEC3 pour une zone. Une valeur de -1 ne place aucune limite maximale sur le nombre d'itérations. C'est aussi le paramètre par défaut pour une zone.
dlv-trust-points [seulement si LIBVAL_DLV est activé]
Spécifie l'arbre DLV pour la zone cible. Dans l'exemple suivant, libval utilisera le registre DLV défini à dlv.isc.org. pour toutes les requêtes sous la racine qui ne nous donnent pas de réponse fiable en utilisant le mécanisme DNSSEC normal, et ont une attente de sécurité de zone de validate. 
dlv dlv-trust-points
    .   dlv.isc.org.
;

Pour que DLV soit utilisé dans l'exemple ci-dessus, une politique de point d'ancrage de confiance doit également être définie pour le registre dlv, avec la politique d'attente de sécurité de zone pour le registre définie à validate.

dlv trust-anchor
    dlv.isc.org DS  19297  5  2  \
                A11D16F6733983E159EDF8053B2FB57B479D81A309A5\
                0EAA79A81AF48A47C617
;

En dehors des options de configuration spécifiques aux zones, il est également possible de configurer des options globales pour la validation dans dnsval.conf. Les options globales peuvent être spécifiées en utilisant la construction ci-dessous.

global-options 
    keyowrd1 value1
    keyword2 value2
    ...
;

Il ne peut y avoir qu'une seule construction global-options définie pour dnsval.conf. Si plusieurs constructions sont définies, seule la première est utilisée.

Les mots-clés suivants sont définis pour global-options dans dnsval.conf

trust-local-answers
Cette option est obsolète. Utilisez trust-oob-answers à la place.
trust-oob-answers
Si la valeur associée à cette option est yes, alors pour toutes les réponses renvoyées à l'aide d'un mécanisme hors bande (par exemple, un stockage de fichiers tel que /etc/hosts), la valeur renvoyée par la fonction val_istrusted() (voir libval(3)) est supérieure à un.
edns0-size
Lors de l'interrogation de divers serveurs de noms, libsres tentera plusieurs tailles EDNS0, se terminant par une requête EDNS0 désactivé (c'est-à-dire aucun bit CD défini). Les tailles EDNS0 suivantes sont essayées par défaut : 4096, 1492, 512. Le bouton de politique "edns0-size" peut être utilisé pour modifier la plus grande taille EDNS0 tentée.
env-policy
Cette option permet à l'administrateur de dnsval.conf de contrôler si libval utilise les valeurs spécifiées par l'utilisateur dans les variables d'environnement lors de la détermination des politiques libval et des cibles de journalisation. Voir la section ci-dessous sur la substitution des politiques dnsval.conf pour plus de détails sur cette option.
app-policy
Cette option permet à l'administrateur du fichier dnsval.conf de contrôler si libval recherchera automatiquement une politique de validation avec un libellé égal au nom de l'application dans dnsval.conf. Voir la section ci-dessous sur la substitution des politiques dnsval.conf pour plus de détails sur cette option.
closest-ta-only
Le comportement de validation par défaut consiste à rechercher toute chaîne d'authentification qui valide avec succès. Ainsi, s'il existe des ancres de confiance pour example.com et test.example.com, le validateur renverra un succès si la chaîne d'authentification peut être ancrée à l'ancre de confiance example.com, même si l'ancre de confiance pour test.example.com ne correspond pas. Dans les cas où cela n'est pas souhaitable, l'option closest-ta-only peut être utilisée.

Si cette option est définie à yes, l'algorithme de validation se termine au TA le plus proche.

rec-fallback
Cette option est utilisée pour contrôler si libval tentera de recourir à une recherche récursive du nom si la réponse du serveur de noms de mise en cache a renvoyé une erreur. Par défaut, cette option est définie à yes; elle peut être désactivée en la définissant à no.
max-refresh
Cette option est utilisée en conjonction avec le drapeau de requête VAL_QUERY_SKIP_CACHE. Lorsque les requêtes ont ce drapeau activé, elles ignoreront normalement les entrées mises en cache. Cependant, max-refresh peut limiter la fréquence d'envoi des requêtes sur le fil. Lorsque cette option est définie à une valeur positive, une nouvelle requête n'est envoyée que si la valeur mise en cache a été stockée il y a plus de (la valeur spécifiée par) max-refresh secondes. Si max-refresh est 0, le cache est toujours ignoré. Si la valeur est -1, le cache est jamais ignoré. La valeur par défaut pour max-refresh est de 60 secondes. Cela signifie que deux requêtes envoyées avec le drapeau VAL_QUERY_SKIP_CACHE défini à moins d'une minute d'intervalle ne résulteront que par une seule requête vue sur le fil.
proto
Cette option est utilisée pour contrôler le protocole réseau que libval utilise pour envoyer des requêtes à divers serveurs de noms. Si la valeur est définie sur ipv6, libval n'utilise que IPv6 ; si elle est définie sur ipv4, libval n'utilise que IPv4. La valeur par défaut est any, ce qui amène libval à envoyer sur n'importe lequel des protocoles disponibles pour le serveur de noms donné.
timeout
Cette option remplace la valeur par défaut du délai d'attente du résolveur par la valeur fournie.
retry
Cette option remplace la valeur par défaut du nombre de tentatives du résolveur par la valeur fournie.
log
Cette option contrôle le niveau de journalisation et la cible de journalisation pour libval. La valeur attendue pour cette option est la même que celle spécifiée pour val_add_log_optarg (voir libval(3)).

Un exemple de construction global-options est donné ci-dessous:

global-options
    trust-oob-answers yes
    edns0-size 4096
    env-policy enable
    app-policy enable
    log 5:stderr
;

SUBSTITUTION DES POLITIQUES resolv.conf

libval examine d'abord les options du résolveur présentes dans le fichier resolv.conf spécifié au moment de la configuration. Si ce fichier est absent, libval recherche les options du résolveur dans le fichier /etc/resolv.conf.

Cela permet aux utilisateurs de substituer facilement les politiques du résolveur. Le resolv.conf spécifique au système peut rester inchangé, tandis que toute politique supplémentaire qui pourrait être nécessaire pour libval peut être utilisée dans le fichier resolv.conf fourni par la configuration.

SUBSTITUTION DES POLITIQUES dnsval.conf

libval offre trois moyens d'adapter les politiques dnsval.conf à un environnement donné.

Fichiers d'inclusion multiples
libval autorise l'inclusion de fichiers dnsval.conf supplémentaires dans un fichier dnsval.conf donné. L'option est spécifiée comme suit: 
include /chemin/vers/fichier/de/substitution/dnsval.conf

Les fichiers sont lus en largeur. Les politiques sont évaluées de manière à ce que la dernière politique définie ait plus de poids que les précédentes. Par conséquent, un administrateur peut fournir un dnsval.conf avec des politiques par défaut incluant un autre fichier du répertoire personnel de l'utilisateur. Le fichier inclus peut être utilisé pour substituer les politiques spécifiées dans le fichier dnsval.conf de base.

Politiques par nom d'application
Si l'option globale app-policy n'est pas désactivée, libval recherche automatiquement une politique dans dnsval.conf avec une valeur de libellé construite à partir du nom de l'application. Par exemple, dnsval.conf peut être défini avec des politiques de validation pour le libellé foo. L'application foo, lorsqu'elle est exécutée, utilisera la politique définie sous le libellé foo pendant son opération de validation.
Politiques via l'environnement
Si l'option globale env-policy n'est pas désactivée, libval examine les variables d'environnement VAL_CONTEXT_LABEL et VAL_LOG_TARGET afin de déterminer le libellé de la politique du validateur et la cible de journalisation.
Priorité des libellés de validateur
Il existe effectivement quatre types de libellés de politique qui peuvent être appliqués par libval : les politiques par nom d'application, les politiques via VAL_CONTEXT_LABEL, et les libellés spécifiés par l'application (NULL ou non-NULL). La priorité de l'application de ces libellés est définie par les règles suivantes:

1. Si env-policy est "override", utiliser le libellé spécifié dans la variable d'environnement VAL_CONTEXT_LABEL (si elle est définie).

2. Si env-policy est "enable" et que la politique spécifiée par l'application est NULL, utiliser le libellé spécifié dans la variable d'environnement VAL_CONTEXT_LABEL (si elle est définie).

3. Si app-policy est "override", utiliser le libellé généré à partir du nom de l'application. Si ce libellé de politique n'existe pas dans le système de configuration, utiliser la politique par défaut.

4. Si app-policy est "enable" et que la politique spécifiée par l'application est NULL, utiliser le libellé généré à partir du nom de l'application.

5.

Si la politique spécifiée par l'application n'est pas NULL, utilisez ce label.

6. Utiliser la politique par défaut

Les cas d'utilisation suivants peuvent donc être définis

Système verrouillé avec une politique unique
Un administrateur qui souhaite (et est capable de) verrouiller un système à une politique de validation particulière doit définir les options globales env-policy et app-policy sur désactiver. Cela nécessite également que les administrateurs soient capables de verrouiller le système à des applications spécifiques et que ces applications ne soient pas écrites de manière à leur permettre de spécifier des labels de politique non-NULL lors de la création du contexte. (voir val_create_context dans libval(3)).
Système verrouillé avec des politiques spécifiques aux applications
Un administrateur qui souhaite (et est capable de) verrouiller un système sur un fichier dnsval.conf particulier, mais souhaite utiliser différentes politiques pour différentes applications doit définir app-policy sur override et env-policy sur disable. L'administrateur doit également définir des politiques pour divers noms d'applications dans dnval.conf ; pour les applications qui n'ont pas de politique avec un label correspondant à leur nom, la politique par défaut est utilisée.

L'administrateur peut définir app-policy sur enable si les politiques non-NULL spécifiées par l'application lors de la création du contexte du validateur sont jugées acceptables.

Contrôlé par l'utilisateur
Un administrateur peut définir env-policy sur override pour donner à l'utilisateur un contrôle total sur le label de politique utilisé lors de la validation. La politique de validation est lue via la variable d'environnement VAL_CONTEXT_LABEL.

Si VAL_CONTEXT_LABEL est spécifié globalement pour le système, l'administrateur peut plutôt choisir l'option globale env-policy sur enable. Dans ce cas, le label donné dans VAL_CONTEXT_LABEL est utilisé uniquement lorsque la politique spécifiée par l'application est non-NULL.

Le label dans VAL_CONTEXT_LABEL est utilisé uniquement s'il est défini. Si cette valeur est NULL, libval lira d'autres labels de politique comme indiqué par les règles de précédence ci-dessus.
