NOM

virt-builder - Construire rapidement des images de machines virtuelles

SYNTAXE

virt-builder os-version
   [-o|--output DISKIMAGE] [--size TAILLE] [--format raw|qcow2]
   [--arch ARCHITECTURE] [--attach ISOFILE]
   [--append-line FICHIER:LIGNE] [--chmod PERMISSIONS:FICHIER]
   [--chown UID:GID:PATH] [--commands-from-file NOMFICHIER]
   [--copy SOURCE:DEST] [--copy-in CHEMINLOCAL:REPERTOIREDEST]
   [--delete PATH] [--edit FICHIER:EXPRESSION] [--firstboot SCRIPT]
   [--firstboot-command 'CMD+ARGUMENTS'] [--firstboot-install PKG,PKG..]
   [--hostname NOMHOTE] [--inject-blnsvr METHODE]
   [--inject-qemu-ga METHODE] [--inject-virtio-win METHODE]
   [--install PKG,PKG..] [--link CIBLE:LIEN[:LIEN..]] [--mkdir DIR]
   [--move SOURCE:DEST] [--password UTILISATEUR:SELECTEUR]
   [--root-password SELECTEUR] [--run SCRIPT]
   [--run-command 'CMD+ARGUMENTS'] [--scrub FICHIER] [--sm-attach SELECTEUR]
   [--sm-register] [--sm-remove] [--sm-unregister]
   [--ssh-inject UTILISATEUR[:SELECTEUR]] [--tar-in TARFILE:REPERTOIREDEST]
   [--timezone TIMEZONE] [--touch FICHIER] [--truncate FICHIER]
   [--truncate-recursive PATH] [--uninstall PKG,PKG..] [--update]
   [--upload FICHIER:DEST] [--write FICHIER:CONTENU] [--no-logfile]
   [--password-crypto md5|sha256|sha512] [--no-selinux-relabel]
   [--selinux-relabel] [--sm-credentials SELECTEUR]
virt-builder -l|--list [--long] [--list-format short|long|json] [os-version]
virt-builder --notes os-version
virt-builder --print-cache
virt-builder --cache-all-templates
virt-builder --delete-cache
virt-builder --get-kernel DISKIMAGE
   [--format raw|qcow2] [--output REPERTOIREDESORTIE]

DESCRIPTION

Virt-builder est un outil permettant de construire rapidement de nouvelles machines virtuelles. Vous pouvez construire une variété de VM pour un usage local ou cloud, généralement en quelques minutes ou moins. Virt-builder offre également de nombreuses façons de personnaliser ces VM. Tout est exécuté depuis la ligne de commande et ne nécessite aucun privilège root, ce qui rend l'automatisation et le scripting simples.

Notez que virt-builder n'installe pas les invités à partir de zéro. Il prend des modèles d'OS préparés proprement, signés numériquement et les personnalise. Cette approche est utilisée car elle est beaucoup plus rapide, mais si vous avez besoin de faire des installations fraîches, vous pourriez vouloir regarder virt-install(1) et oz-install(1).

La façon la plus simple de commencer est de regarder les exemples dans la section suivante.

EXEMPLES

Lister les machines virtuelles disponibles

virt-builder --list

listra les systèmes d'exploitation disponibles à l'installation. Une sélection de systèmes d'exploitation librement redistribuables est disponible en standard. Vous pouvez également ajouter les vôtres (voir ci-dessous).

Après avoir choisi un invité dans la liste, vous pourriez vouloir voir s'il y a des notes d'installation :

virt-builder --notes fedora-41

Construire une machine virtuelle

virt-builder fedora-41

construira une image Fedora 41 pour la même architecture que virt-builder (donc l'exécuter depuis une installation i686 essaiera de construire une image i686, si disponible). Elle aura toute la configuration par défaut (taille minimale, pas de comptes utilisateurs, mot de passe root aléatoire, juste le strict minimum de logiciels installés, etc.).

Vous n'avez pas besoin d'exécuter cette commande en tant que root.

La première fois que cela s'exécute, il faut télécharger le modèle sur le réseau, mais celui-ci est mis en cache (voir "MISE EN CACHE").

Le nom du fichier de sortie est dérivé du nom du modèle, donc ci-dessus ce sera fedora-41.img. Vous pouvez changer le nom du fichier de sortie en utilisant l'option -o :

virt-builder fedora-41 -o mydisk.img

Vous pouvez également utiliser l'option -o pour écrire sur des périphériques ou des volumes logiques existants.

virt-builder fedora-41 --format qcow2

Comme ci-dessus, mais écrit la sortie au format qcow2 dans fedora-41.qcow2.

virt-builder fedora-41 --size 20G

Comme ci-dessus, mais la taille de sortie sera de 20 Go. Le système d'exploitation invité est redimensionné lors de sa copie vers la sortie (automatiquement, en utilisant virt-resize(1)).

virt-builder fedora-41 --arch i686

Comme ci-dessus, mais en utilisant un modèle i686, si disponible.

Définir le mot de passe root

virt-builder fedora-41 --root-password file:/tmp/rootpw

Crée une image Fedora 41. Le mot de passe root est pris du fichier /tmp/rootpw.

Notez que si vous ne définissez pas --root-password, alors l'invité reçoit un mot de passe root aléatoire qui est affiché sur stdout.

Vous pouvez également créer des comptes utilisateurs. Voir "UTILISATEURS ET MOTS DE PASSE" ci-dessous.

Définir le nom d'hôte

virt-builder fedora-41 --hostname virt.example.com

Définit le nom d'hôte à "virt.example.com".

Installer des logiciels

Pour installer des paquets à partir du dépôt logiciel ordinaire (invité) (par ex. dnf ou apt) :

virt-builder fedora-41 --install "inkscape,@Xfce Desktop"

(Sous Fedora, "@" est utilisé pour installer des groupes de paquets. Sous Debian, vous installeriez un méta-paquet à la place.)

Pour mettre à jour les paquets installés vers la dernière version :

virt-builder debian-7 --update

Personnaliser l'installation

Il existe de nombreuses options qui vous permettent de personnaliser l'installation. Celles-ci incluent : --run/--run-command, qui exécutent un script shell ou une commande pendant la génération de l'image disque et vous permettent d'ajouter ou de modifier des fichiers qui entrent dans l'image disque. --firstboot/--firstboot-command, qui vous permettent d'ajouter des scripts/commandes qui sont exécutés la première fois que l'invité démarre. --edit pour éditer des fichiers. --upload pour télécharger des fichiers.

Par exemple :

cat <<'EOF' > /tmp/dnf-update.sh
dnf -y --best update
EOF

virt-builder fedora-41 --firstboot /tmp/dnf-update.sh

ou simplement :

virt-builder fedora-41 --firstboot-command 'dnf -y --best update'

ce qui fait que la commande dnf(8) "update" s'exécute une fois lors du premier démarrage de l'invité.

Ou :

virt-builder fedora-41 \
  --edit '/etc/dnf/dnf.conf:
            s/gpgcheck=1/gpgcheck=0/'

qui édite /etc/dnf/dnf.conf à l'intérieur de l'image disque (pendant la création de l'image disque, bien avant le démarrage).

Vous pouvez combiner ces options, et avoir plusieurs options de tous types.

Voir aussi "ARCHITECTURE".

--attach ISOFILE
Pendant la phase de personnalisation, le disque donné est attaché à l'appliance libguestfs. Ceci est utilisé pour fournir des dépôts de logiciels supplémentaires ou d'autres données pour la personnalisation.

mkdir /tmp/montage

--cache DIR

--cache DIR définit le répertoire à utiliser/vérifier pour les fichiers de modèles mis en cache. S'il n'est pas défini, il utilise par défaut $XDG_CACHE_HOME/virt-builder/ ou $HOME/.cache/virt-builder/.

--cache-all-templates
Télécharge tous les modèles dans le cache, puis quitte. Voir "MISE EN CACHE".

Notez que cela ne met pas tout en cache. D'autres modèles pourraient être téléchargés. De plus, cela ne met pas en cache les paquets (les options --install, --update).

--check-signature
--no-check-signature
Vérifie/ne vérifie pas la signature numérique du modèle de système d'exploitation. La valeur par défaut est de vérifier la signature et de quitter si elle n'est pas correcte. L'utilisation de --no-check-signature contourne cette vérification.

Voir aussi --fingerprint.

--colors
--colours
Utilise des séquences de couleurs ANSI pour coloriser les messages. C'est la valeur par défaut lorsque la sortie est un tty. Si la sortie du programme est redirigée vers un fichier, les séquences de couleurs ANSI sont désactivées sauf si vous utilisez cette option.
--curl CURL
Spécifie un binaire curl(1) alternatif. Vous pouvez également l'utiliser pour ajouter des paramètres curl, par exemple pour désactiver les vérifications de certificat https : 
virt-builder --curl "curl --insecure" [...]
--delete-cache
Supprime le cache des modèles. Voir "MISE EN CACHE".
--no-delete-on-failure
Ne supprime pas le fichier de sortie en cas d'échec de la construction. Vous pouvez l'utiliser pour déboguer les échecs d'exécution de scripts. Voir "DÉBOGAGE DES CONSTRUCTIONS" pour les méthodes de débogage des images.

Par défaut, le fichier de sortie est supprimé si virt-builder échoue (ou si un script qu'il exécute échoue, par exemple).

--fingerprint 'AAAA BBBB ...'
Vérifie que l'index et les modèles sont signés par la clé avec l'empreinte digitale donnée. (L'empreinte digitale est une longue chaîne, généralement écrite sous forme de 10 groupes de 4 chiffres hexadécimaux).

Vous pouvez donner cette option plusieurs fois. Si vous avez plusieurs URL sources, vous pouvez avoir soit aucune empreinte digitale, soit une empreinte digitale, soit plusieurs empreintes digitales. Si vous en avez plusieurs, chacune doit correspondre 1 à 1 à une URL source.

--format qcow2
--format brut
Pour les constructions ordinaires, cela sélectionne le format de sortie. La valeur par défaut est brut.

Avec --get-kernel, cela spécifie le format d'entrée.

Pour créer un fichier qcow2 de style ancien (pour la compatibilité avec RHEL 6 ou un qemu très ancien < 1.1), après avoir exécuté virt-builder, utilisez cette commande :

qemu-img amend -f qcow2 -o compat=0.10 output.qcow2
--get-kernel IMAGE
Cette option extrait le noyau et l'initramfs d'une image disque précédemment construite appelée "IMAGE" (en fait, elle fonctionne pour n'importe quelle image de disque de VM, pas seulement celles construites avec virt-builder).

Notez que cette méthode est obsolète : il existe un outil séparé pour cela, virt-get-kernel(1), qui offre plus d'options pour l'extraction de fichiers.

Le noyau et l'initramfs sont écrits dans le répertoire courant, sauf si vous spécifiez également le répertoire --output "outputdir".

Le format de l'image disque est détecté automatiquement, sauf si vous le spécifiez en utilisant l'option --format.

Dans le cas où l'invité contient plusieurs noyaux, celui avec le numéro de version le plus élevé est choisi. Pour extraire des noyaux arbitraires de l'image disque, voir guestfish(1). Pour extraire l'intégralité du répertoire /boot d'un invité, voir virt-copy-out(1).

--gpg GPG
Spécifie un binaire gpg(1) (GNU Privacy Guard) alternatif. Par défaut, virt-builder recherche soit "gpg2", soit "gpg" dans le $PATH.

Vous pouvez également l'utiliser pour ajouter des paramètres gpg, par exemple pour spécifier un répertoire personnel alternatif :

virt-builder --gpg "gpg --homedir /tmp" [...]
-l [version-os]
--list [version-os]
--list --list-format format [version-os]
--list --long [version-os]
Liste tous les modèles disponibles si aucun invité n'est spécifié, ou seulement pour celui spécifié.

Il est possible de choisir avec --list-format le format de sortie pour la liste des modèles :

short
Le format par défaut, imprime uniquement l'identifiant du modèle et, à côté, sa description courte.
long
Imprime une liste textuelle avec les détails des sources disponibles, suivis des détails des modèles disponibles.

Imprime un objet JSON avec les détails des sources disponibles et les détails des modèles disponibles.

La clé "version" dans l'objet principal représente la "version de compatibilité", et elle est incrémentée chaque fois que la sortie JSON résultante devient incompatible avec les versions précédentes (par exemple, la structure a changé, ou des clés non optionnelles ne sont plus présentes).

--long est un raccourci pour le format "long".

Cette option est utilisée pour rendre la sortie plus conviviale pour les machines lorsqu'elle est analysée par d'autres programmes. Voir "SORTIE LISIBLE PAR MACHINE" ci-dessous.

La valeur par défaut peut être trouvée avec cette commande :

guestfish get-memsize
--network
--no-network
Active ou désactive l'accès réseau depuis l'invité pendant l'installation.

L'activation est la valeur par défaut. Utilisez --no-network pour désactiver l'accès.

Le réseau n'autorise que les connexions sortantes et présente d'autres limitations mineures. Voir "RÉSEAU" dans virt-rescue(1).

Si vous utilisez --no-network, d'autres options telles que --install ne fonctionneront pas.

Cela n'affecte pas la capacité de l'invité à accéder au réseau une fois qu'il a démarré, car cela est contrôlé par votre hyperviseur ou votre environnement cloud et n'a rien à voir avec virt-builder.

En général, vous ne devriez pas utiliser --no-network. Mais voici quelques raisons pour lesquelles vous pourriez vouloir le faire :

1.
Parce que le backend libguestfs que vous utilisez ne prend pas en charge le réseau. (Voir : "BACKEND" dans guestfs(3)).
2.
Tout logiciel dont vous avez besoin est installé à partir d'un ISO joint, vous n'avez donc pas besoin du réseau.
3.
Vous ne voulez pas que du code invité non fiable tente d'accéder à votre réseau hôte lors de l'exécution de virt-builder. C'est particulièrement un problème lorsque vous ne faites pas confiance à la source des modèles de système d'exploitation. (Voir "SÉCURITÉ" ci-dessous).
4.
Vous n'avez pas de réseau hôte (par exemple, dans des environnements sécurisés/restreints).
--no-sync
Ne synchronise pas le fichier de sortie à la sortie.

Virt-builder "fsync" le fichier de sortie ou l'image disque à la sortie.

La raison est que le mode de mise en cache par défaut de qemu/KVM est "none" ou "directsync", qui tous deux contournent le cache de pages de l'hôte. Par conséquent, ils ne fonctionneraient pas correctement si vous démarriez immédiatement l'invité après avoir exécuté virt-builder - ils ne verraient pas le fichier de sortie complet. (Notez que vous ne devriez pas utiliser ces modes de mise en cache - ils sont fondamentalement défectueux pour cela et d'autres raisons).

Si vous n'utilisez pas ces modes de mise en cache défectueux, vous pouvez utiliser --no-sync pour éviter cette synchronisation inutile et gagner considérablement en performance.

Sélectionnez la taille du disque de sortie, où la taille peut être spécifiée en utilisant des noms courants tels que "32G" (32 gigaoctets), etc.

Options de personnalisation

--append-line FICHIER:LIGNE
Ajouter une seule ligne de texte à "FICHIER". Si le fichier ne se termine pas déjà par un saut de ligne, un saut de ligne est ajouté avant la ligne ajoutée. Un saut de ligne est également ajouté à la fin de la chaîne "LIGNE" automatiquement.

Par exemple (en supposant des guillemets shell ordinaires) cette commande :

--append-line '/etc/hosts:10.0.0.1 foo'

ajoutera soit "10.0.0.1 foo⏎", soit "⏎10.0.0.1 foo⏎" au fichier, ce dernier uniquement si le fichier existant ne se termine pas déjà par un saut de ligne.

"⏎" représente un caractère de saut de ligne, qui est deviné en examinant le contenu existant du fichier, donc cette commande fait ce qu'il faut pour les fichiers utilisant des fins de ligne Unix ou Windows. Cela fonctionne également pour les fichiers vides ou inexistants.

Pour insérer plusieurs lignes, utilisez la même option plusieurs fois :

--append-line '/etc/hosts:10.0.0.1 foo'
--append-line '/etc/hosts:10.0.0.2 bar'

Pour insérer une ligne vide avant la ligne ajoutée, faites :

--append-line '/etc/hosts:'
--append-line '/etc/hosts:10.0.0.1 foo'
--chmod PERMISSIONS:FICHIER
Changer les permissions de "FICHIER" en "PERMISSIONS".

Note : "PERMISSIONS" par défaut sera décimal, à moins que vous ne le préfixiez avec 0 pour obtenir de l'octal, c'est-à-dire utilisez 0700 et non 700.

--chown UID:GID:CHEMIN
Changer l'utilisateur propriétaire et l'ID de groupe d'un fichier ou d'un répertoire dans l'invité. Note :
  • Seuls les UID et GID numériques fonctionneront, et ceux-ci peuvent ne pas être les mêmes à l'intérieur de l'invité que sur l'hôte.
  • Cela ne fonctionnera pas avec les invités Windows.

Par exemple :

virt-customize --chown '0:0:/var/log/audit.log'

Voir aussi : --upload.

--commands-from-file NOMDEFichier
Lire les commandes de personnalisation à partir d'un fichier, une par ligne (avec ses arguments).

Chaque ligne contient une seule commande de personnalisation et ses arguments, par exemple :

delete /some/file
install some-package
password some-user:password:its-new-password

Les lignes vides sont ignorées, et les lignes commençant par "#" sont des commentaires et sont également ignorées. De plus, les arguments peuvent être répartis sur plusieurs lignes, en ajoutant un "\" (caractère de continuation) à la fin d'une ligne, par exemple

edit /some/file:\
  s/^OPT=.*/OPT=ok/

Les commandes sont traitées dans le même ordre qu'elles apparaissent dans le fichier, comme si elles étaient spécifiées comme --delete /some/file sur la ligne de commande.

--copy SOURCE:DEST
Copier des fichiers ou des répertoires récursivement à l'intérieur de l'invité.

Les jokers ne peuvent pas être utilisés.

--copy-in CHEMINLOCAL:RÉPERTOIREDISTANT
Copier des fichiers ou des répertoires locaux récursivement dans l'image disque, en les plaçant dans le répertoire "RÉPERTOIREDISTANT" (qui doit exister).

Les jokers ne peuvent pas être utilisés.

--delete CHEMIN
Supprimer un fichier de l'invité. Ou supprimer un répertoire (et tout son contenu, récursivement).

Vous pouvez utiliser des caractères glob shell dans le chemin spécifié. Faites attention à échapper les caractères glob du shell hôte, si nécessaire. Par exemple :

virt-customize --delete '/var/log/*.log'.

Voir aussi : --upload, --scrub.

--edit FICHIER:EXPRESSION
Modifier "FICHIER" en utilisant l'expression Perl "EXPRESSION".

Faites attention à bien citer l'expression pour éviter qu'elle ne soit modifiée par le shell.

Notez que cette option n'est disponible que lorsque Perl 5 est installé.

Voir "ÉDITION NON INTERACTIVE" dans virt-edit(1).

--firstboot SCRIPT
Installer "SCRIPT" à l'intérieur de l'invité, de sorte que lorsque l'invité démarre pour la première fois, le script s'exécute (en tant que root, tard dans le processus de démarrage).

Le script est automatiquement rendu exécutable (chmod +x) après son installation dans l'invité.

La version alternative --firstboot-command est la même, mais elle encapsule commodément la commande dans un script d'une seule ligne pour vous.

Vous pouvez avoir plusieurs options --firstboot. Elles s'exécutent dans le même ordre qu'elles apparaissent sur la ligne de commande.

Veuillez consulter "SCRIPTS DE PREMIER DÉMARRAGE" pour plus d'informations et d'avertissements sur les scripts de premier démarrage.

Voir aussi --run.

--firstboot-command 'CMD+ARGS'
Exécuter la commande (et ses arguments) à l'intérieur de l'invité lors du premier démarrage de l'invité (en tant que root, tard dans le processus de démarrage).

Vous pouvez avoir plusieurs options --firstboot. Elles s'exécutent dans le même ordre qu'elles apparaissent sur la ligne de commande.

Veuillez consulter "SCRIPTS DE PREMIER DÉMARRAGE" pour plus d'informations et d'avertissements sur les scripts de premier démarrage.

Voir aussi --run.

--firstboot-install PKG,PKG..
Installer les paquets nommés (une liste séparée par des virgules). Ceux-ci sont installés lors du premier démarrage de l'invité en utilisant le gestionnaire de paquets de l'invité (par exemple, apt, yum, etc.) et la connexion réseau de l'invité.

RÉFÉRENCE

INSTALLATION DE PAQUETS

Il existe plusieurs approches pour installer des paquets ou des applications dans l'invité, qui présentent des compromis différents.

Installation de paquets au moment de la construction

Si le système d'exploitation invité que vous installez est similaire au système d'exploitation hôte (par exemple, les deux sont Linux), et si libguestfs prend en charge les connexions réseau, alors vous pouvez utiliser --install pour installer des paquets comme ceci :

virt-builder fedora-41 --install inkscape

Ceci utilise le gestionnaire de paquets de l'invité et la connexion réseau de l'hôte.

Mise à jour de paquets au moment de la construction

Pour mettre à jour les paquets installés dans le template au moment de la construction :

virt-builder fedora-41 --update

La plupart des templates livrés avec virt-builder sont livrés avec une sélection très minimale de paquets (connue sous le nom de "JEOS" ou "Just Enough Operating System"), qui sont à jour au moment de la création du template, mais pourraient être obsolètes au moment où vous installez un système d'exploitation à partir du template. Cette option met à jour ces paquets du template.

Installation de paquets au premier démarrage

Une autre option est d'installer les paquets au premier démarrage de l'invité :

virt-builder fedora-41 --firstboot-install inkscape

Ceci utilise le gestionnaire de paquets de l'invité et la connexion réseau de l'invité.

Les inconvénients sont que l'invité prendra beaucoup plus de temps à démarrer pour la première fois, et qu'il n'y a pas grand-chose que vous puissiez faire si l'installation des paquets échoue (par exemple, si un problème réseau empêche l'invité d'atteindre les dépôts de paquets).

Installation de paquets au moment de la construction à partir d'un dépôt secondaire

Si le logiciel que vous souhaitez installer n'est pas disponible dans le dépôt de paquets principal de l'invité, vous pouvez ajouter un dépôt secondaire. Habituellement, cela se présente sous la forme d'un fichier ISO (image de CD) contenant des paquets supplémentaires.

Vous pouvez créer l'image disque en utilisant soit genisoimage(1) soit virt-make-fs(1). Pour genisoimage, utilisez une commande comme celle-ci :

genisoimage -o extra-packages.iso -R -J -V EXTRA cdcontents/

Créez un script qui monte l'ISO et configure le dépôt. Pour dnf, créez /tmp/install.sh contenant :

mkdir /tmp/mount
mount LABEL=EXTRA /tmp/mount

cat <<'EOF' > /etc/yum.repos.d/extra.repo
[extra]
name=extra
baseurl=file:///tmp/mount
enabled=1
EOF

dnf -y install famousdatabase

Pour apt, créez /tmp/install.sh contenant :

mkdir /tmp/mount
mount LABEL=EXTRA /tmp/mount

apt-cdrom -d=/tmp/mount add
apt-get -y install famousdatabase

Utilisez l'option --attach pour attacher l'image CD / disque et l'option --run pour exécuter le script :

virt-builder fedora-41 \
  --attach extra-packages.iso \
  --run /tmp/install.sh

UTILISATEURS ET MOTS DE PASSE

L'option --root-password est utilisée pour changer le mot de passe root (sinon un mot de passe aléatoire est utilisé). Cette option prend un mot de passe "SELECTOR" dans l'un des formats suivants :

--root-password file:FILENAME
Lire le mot de passe root depuis "FILENAME". Toute la première ligne de ce fichier est le mot de passe de remplacement. Toutes les autres lignes sont ignorées. Vous devriez créer le fichier avec le mode 0600 pour vous assurer que personne d'autre ne peut le lire.
--root-password password:PASSWORD
Définir le mot de passe root à la chaîne littérale "PASSWORD".

Note : ce n'est pas sécurisé car tout utilisateur sur la même machine peut voir le mot de passe en clair en utilisant ps(1).

--root-password random
Choisir un mot de passe aléatoire, qui est imprimé sur la sortie standard. Le mot de passe a environ 120 bits d'aléatoire.

C'est la valeur par défaut.

--root-password disabled
Le mot de passe du compte root est désactivé. C'est comme mettre "*" dans le champ du mot de passe.
--root-password locked:file:FILENAME
--root-password locked:password:PASSWORD
--root-password locked:random
Le compte root est verrouillé, mais un mot de passe est placé sur le compte. S'il est déverrouillé pour la première fois (en utilisant "passwd -u") alors les connexions utiliseront le mot de passe donné.
--root-password locked
--root-password locked:disabled
Le compte root est verrouillé et le mot de passe est désactivé.

Création de comptes utilisateurs

Pour créer des comptes utilisateurs, utilisez la commande useradd(8) avec --firstboot-command comme suit :

virt-builder --firstboot-command \
   'useradd -m -p "" rjones ; chage -d 0 rjones'

La commande ci-dessus créera un compte "rjones" sans mot de passe, et forcera l'utilisateur à définir un mot de passe lors de sa première connexion. Il existe d'autres moyens de gérer les mots de passe, voir useradd(8) pour plus de détails.

DISPOSITION DU CLAVIER

Étant donné qu'il existe de nombreuses façons de définir la disposition du clavier dans les distributions Linux, virt-builder n'essaie pas encore d'avoir une option de ligne de commande simple. Cette section décrit comment définir le clavier pour certaines distributions Linux courantes.

Disposition du clavier avec systemd

Pour les distributions qui utilisent systemd "localectl", utilisez une commande comme celle-ci :

virt-builder fedora-41 \
  --firstboot-command 'localectl set-keymap uk'

Voir localectl(1) et https://www.happyassassin.net/2013/11/23/keyboard-layouts-in-fedora-20-and-previously/ pour plus de détails.

Disposition du clavier via /etc/sysconfig/keyboard

Pour RHEL ≤ 6, Fedora ≤ 18 et similaires, téléversez ou modifiez le fichier de configuration du clavier en utilisant les options --upload, --write ou --edit. Par exemple :

virt-builder centos-6 \
  --edit '/etc/sysconfig/keyboard: s/^KEYTABLE=.*/KEYTABLE="uk"/'

Le format de ce fichier peut être trouvé documenté dans de nombreux endroits en ligne.

Disposition du clavier avec les distributions dérivées de Debian

Pour les distributions dérivées de Debian utilisant /etc/default/keyboard, téléversez ou modifiez le fichier clavier en utilisant les options --upload, --write ou --edit. Par exemple :

virt-builder debian-8 \
  --edit '/etc/default/keyboard: s/^XKBLAYOUT=.*/XKBLAYOUT="gb"/'

Voir https://wiki.debian.org/Keyboard.

LANGUE

La plupart des distributions Linux prennent en charge plusieurs paramètres régionaux afin que vous puissiez avoir les messages de l'invité affichés dans une autre langue, comme le russe.

Cependant, il n'y a pas de paramètre unique qui contrôle cela, car des paquets supplémentaires peuvent devoir être installés pour prendre en charge les polices de console et X, ainsi que les méthodes de saisie du clavier. Les paquets requis, et leur configuration, sont très spécifiques à la distribution, et il est hors de portée de virt-builder de le faire.

Cette section contient des exemples pour certaines distributions Linux courantes.

CLÉS SSH

L'option --ssh-inject est utilisée pour injecter des clés ssh pour les utilisateurs dans l'invité, afin qu'ils puissent se connecter sans fournir de mot de passe.

La partie "SELECTOR" de la valeur de l'option est facultative ; dans ce cas, --ssh-inject "USER" signifie que nous recherchons dans le répertoire ~/.ssh de l'utilisateur actuel pour trouver le fichier d'ID public par défaut. Cette clé est téléchargée. "ID public par défaut" est le fichier default_ID_file décrit dans ssh-copy-id(1).

Si spécifié, le "SELECTOR" peut être dans l'un des formats suivants :

--ssh-inject USER:file:FILENAME
Lire la clé ssh à partir de FILENAME. FILENAME est généralement un fichier .pub.
--ssh-inject USER:string:KEY_STRING
Utiliser la chaîne spécifiée "KEY_STRING". "KEY_STRING" est généralement une chaîne publique comme ssh-rsa AAAA.... user@localhost.

Dans tous les cas, le répertoire ~USER/.ssh et le fichier ~USER/.ssh/authorized_keys seront créés s'ils n'existent pas déjà.

SCRIPTS DE PREMIÈRE INITIALISATION

Les options --firstboot et --firstboot-command vous permettent d'exécuter des commandes lors de la première initialisation de l'invité. Pour ce faire, un script d'initialisation pour le système d'initialisation de l'invité est installé, qui se charge d'exécuter tous les scripts et commandes ajoutés.

Les systèmes d'exploitation pris en charge sont :

Linux
Les systèmes d'initialisation pris en charge sont : systemd, System-V init (également connu sous le nom de sysvinit) et Upstart (utilisant les scripts System-V).

Notez que généralement les scripts d'initialisation s'exécutent en tant que root, mais avec un environnement plus limité que ce qui pourrait être disponible à partir d'un shell normal : par exemple, $HOME peut être non défini ou vide.

La sortie des scripts de première initialisation est disponible dans l'invité sous ~root/virt-sysprep-firstboot.log.

Windows

Il est requis, et la configuration des scripts de première initialisation échouera s'il n'est pas présent.

rhsrvany.exe ou pvvxsvc.exe est copié depuis l'emplacement pointé par la variable d'environnement "VIRT_TOOLS_DATA_DIR" ; si elle n'est pas définie, une valeur par défaut intégrée sera utilisée (quelque chose comme /usr/share/virt-tools).

La sortie des scripts de première initialisation est disponible dans l'invité sous C:\Program Files\Guestfs\Firstboot\log.txt.

GESTIONNAIRE D'ABONNEMENT

Il est possible d'automatiser l'enregistrement et l'attachement du système en utilisant "subscription-manager". Ceci est typique sur les invités Red Hat Enterprise Linux. Il existe quelques options qui facilitent ce processus, évitent d'exécuter des commandes manuellement et d'exposer des mots de passe sur la ligne de commande.

--sm-register démarre le processus d'enregistrement et nécessite que --sm-credentials soit spécifié ; le format du "SELECTOR" de --sm-credentials est l'un des formats suivants :

--sm-credentials USER:file:FILENAME
Lire le mot de passe pour l'utilisateur spécifié "USER" à partir de FILENAME.
--sm-credentials USER:password:PASSWORD
Utiliser la chaîne littérale "PASSWORD" pour l'utilisateur spécifié "USER".

--sm-attach attache le système aux abonnements ; le format de son "SELECTOR" est l'un des suivants :

--sm-attach auto
"subscription-manager" s'attache aux abonnements les mieux adaptés au système.
--sm-attach file:FILENAME
Lire l'ID de pool à partir de FILENAME.
--sm-attach pool:POOL
Utiliser la chaîne littérale "POOL" comme ID de pool.

--sm-remove supprime tous les abonnements de l'invité, tandis que --sm-unregister désenregistre complètement le système.

PROCESSUS D'INSTALLATION

Lorsque vous invoquez virt-builder, l'installation se déroule comme suit :

  • L'image modèle est téléchargée.

    Si l'image modèle est présente dans le cache, la version mise en cache est utilisée à la place. (Voir "MISE EN CACHE").

  • La signature du modèle est vérifiée.
  • Le modèle est décompressé dans un fichier temporaire.
  • L'image modèle est redimensionnée dans la destination, en utilisant virt-resize(1).
  • Des disques supplémentaires sont attachés (--attach).
  • Une nouvelle graine aléatoire est générée pour l'invité.
  • La personnalisation de l'invité est effectuée, dans l'ordre spécifié sur la ligne de commande.
  • Le réétiquetage SELinux est effectué, sauf s'il est désactivé avec --no-selinux-relabel.

IMPORTATION DE L'IMAGE DISQUE

Importation dans libvirt

Importez l'image disque dans libvirt en utilisant l'option --import de virt-install(1).

virt-install --import \
  --name guest --ram 2048 \
  --disk path=disk.img,format=raw --os-variant fedora27

Notes :

1.
Vous devez spécifier le format correct. Le format est "raw" sauf si vous avez utilisé l'option --format de virt-builder.
2.
--os-variant est fortement recommandé, car il présentera les périphériques optimaux pour que l'invité fonctionne le plus efficacement possible. Pour obtenir une liste de toutes les variantes, faites : 
osinfo-query os

L'outil ci-dessus est fourni par le paquet libosinfo.

3.
Vous pouvez exécuter virt-install en tant que root ou non-root. Chacun fonctionne légèrement différemment car libvirt gère un ensemble différent de machines virtuelles pour chaque utilisateur. En particulier, virt-manager affiche normalement les VM appartenant à root, tandis que Boxes affiche les VM appartenant à l'utilisateur, et d'autres outils fonctionnent probablement différemment également.

Importation dans OpenStack

Importez l'image dans Glance (le magasin d'images OpenStack) en faisant :

glance image-create --name fedora-41-image --file fedora-41.img \
  --disk-format raw --container-format bare \
  --is-public True

Le paramètre --file est l'image disque générée par virt-builder. Il doit correspondre à l'option --output de virt-builder. Le paramètre --disk-format doit correspondre à l'option --format de virt-builder (ou "raw" si vous n'avez pas utilisé cette option). Le paramètre --container-format doit toujours être "bare" car virt-builder ne met pas les images dans des conteneurs.

Vous pouvez utiliser la commande "glance image-show fedora-41-image" pour afficher les propriétés de l'image.

Pour démarrer une instance de votre image sur un nœud de calcul Nova, faites :

nova boot fedora-41-server --image fedora-41-image \
  --flavor m1.medium

Utilisez "nova flavor-list" pour lister les saveurs de machines possibles. Utilisez "nova list" pour lister les instances en cours d'exécution.

Démarrage direct à l'aide de qemu ou KVM

La ligne de commande qemu n'est pas très stable ou facile à utiliser, par conséquent libvirt devrait être utilisé si possible. Cependant, une ligne de commande similaire à la suivante pourrait être utilisée pour démarrer la machine virtuelle :

qemu-system-x86_64 \
  -machine accel=kvm:tcg \
  -cpu host \
  -m 2048 \
  -drive file=disk.img,format=raw,if=virtio

Comme avec libvirt, il est très important que le format correct soit choisi. Ce sera "raw" sauf si l'option --format a été utilisée.

virt-builder

virt-builder manual

The virt-builder utility creates new virtual machine disk images from templates.

A template is a disk image plus a set of customizations that are applied to it. For example, a template might be a standard Linux installation plus packages like openssh-server installed, and configuration files like /etc/ssh/sshd_config set up.

You can build a disk image using a template by running:

virt-builder [TEMPLATE] [OPTION]...

To see a list of available templates, run:

virt-builder --list

To see the options and arguments, run:

virt-builder --help

You can download and use templates from online repositories, or create your own.

For example, to create a Fedora 41 image in disk.img: (This requires the libguestfs-tools package to be installed).

virt-builder fedora-41 -o disk.img

See the "SOURCES OF TEMPLATES" section below for information on how to add your own template sources.

If you need to install any packages that virt-builder relies on, such as libguestfs, see the installation guide for your Linux distro. For further information see: https://docs.puppet.com/puppet/latest/install_pre.html

DEBUGGING BUILDS

If virt-builder itself fails, then enable debugging (-v) and report a bug (see "BUGS" below).

If virt-builder fails because some script or package it is installing fails, try using --no-delete-on-failure to preserve the output file, and continue reading this section.

If virt-builder is successful but the image doesn’t work, here are some things to try:

Use virt-rescue
Run virt-rescue(1) on the disk image: 
virt-rescue -a disk.img

This gives you a rescue shell. You can mount the filesystems from the disk image on /sysroot and examine them using ordinary Linux commands. You can also chroot into the guest to reinstall the bootloader. The virt-rescue man page has a lot more information and examples.

Use guestfish
Run guestfish(1) on the disk image: 
guestfish -a disk.img -i

Use guestfish commands like "ll /directory" and "cat /file" to examine directories and files.

Use guestmount
Mount the disk image safely on the host using FUSE and guestmount(1): 
mkdir /tmp/mp
guestmount -a disk.img -i /tmp/mp
cd /tmp/mp

To unmount the disk image do:

fusermount -u /tmp/mp
Add a serial console
If the guest hangs during boot, it can be helpful to add a serial console to the guest, and direct kernel messages to the serial console. Adding the serial console will involve looking at the documentation for your hypervisor. To direct kernel messages to the serial console, add the following on the kernel command line: 
console=tty0 console=ttyS0,115200

SOURCES OF TEMPLATES

virt-builder reads the available sources from configuration files, with the .conf extension and located in the following paths:

  • $XDG_CONFIG_HOME/virt-builder/repos.d/ ($XDG_CONFIG_HOME is $HOME/.config if not set).
  • $VIRT_BUILDER_DIRS/virt-builder/repos.d/ (where $VIRT_BUILDER_DIRS means any of the directories in that environment variable, or just /etc if not set).

Each .conf file in those paths has a simple text format like the following:

[libguestfs.org]
uri=http://libguestfs.org/download/builder/index.asc
gpgkey=file:///etc/xdg/virt-builder/repos.d/libguestfs.gpg

The part in square brackets is the repository identifier, which is used as unique identifier.

The following fields can appear:

"uri=URI"
The URI of the index file which this repository refers to.

This field is required.

"gpgkey=URI"
This optional field represents the URI (although only file:// URIs are accepted) of the key used to sign the index file. If not present, the index file referred by uri=.. is not signed.
"proxy=MODE"
This optional field specifies the proxy mode, to be used when downloading the index file of this repository. The possible values are:
no, off
No proxy is being used at all, even overriding the system configuration.
system
The proxy used is the system one.
anything else
Specifies the actual proxy configuration to be used, overriding the system configuration.

If not present, the assumed value is to respect the proxy settings of the system (i.e. as if system would be specified).

"format=FORMAT"
This optional field specifies the format of the repository. The possible values are:
native
The native format of the "virt-builder" repository. See also "Creating and signing the index file" below.
simplestreams
The URI represents the root of a Simple Streams v1.0 tree of metadata.

For more information about Simple Streams, see also https://launchpad.net/simplestreams.

If not present, the assumed value is "native".

For serious virt-builder use, you may want to create your own repository of templates.

Libguestfs.org repository

Out of the box, virt-builder downloads the file http://libguestfs.org/download/builder/index.asc which is an index of available templates plus some information about each one, wrapped up in a digital signature. The command "virt-builder --list" lists out the information in this index file.

The templates hosted on libguestfs.org were created using shell scripts, kickstart files and preseed files which can be found in the libguestfs source tree, in "builder/templates".

Setting up the repository

You can set up your own site containing an index file and some templates, and then point virt-builder at the site by creating a .conf file pointing to it.

Note that if your index is signed, you will need to properly fill gpgkey=.. in your .conf file, making sure to deploy also the GPG key file.

virt-builder --source https://example.com/builder/index.asc \
   --fingerprint 'AAAA BBBB ...' \
   --list

You can host this on any web or FTP server, or a local or network filesystem.

Setting up a GPG key

If you don’t have a GnuPG key, you will need to set one up. (Strictly speaking this is optional, but if your index and template files are not signed then virt-builder users will have to use the --no-check-signature flag every time they use virt-builder.)

To create a key, see the GPG manual http://www.gnupg.org/gph/en/manual.html.

Export your GPG public key:

gpg --export -a "you@example.com" > pubkey

Create the templates

There are many ways to create the templates. For example you could clone existing guests (see virt-sysprep(1)), or you could install a guest by hand (virt-install(1)). To see how the templates were created for virt-builder, look at the scripts in "builder/templates"

Virt-builder supports any image format (e.g. raw, qcow2, etc) as template, both as-is, and compressed as XZ. This way, existing images (e.g. cleaned using virt-sysprep(1)) can be used as templates.

For best results when compressing the templates, use the following xz options (see nbdkit-xz-plugin(1) for further explanation):

xz --best --block-size=16777216 disk

Creating and signing the index file

The index file has a simple text format (shown here without the digital signature):

[fedora-41]
name=Fedora® 41
osinfo=fedora41
arch=x86_64
file=fedora-41.xz
checksum[sha512]=...
format=raw
size=6442450944
compressed_size=148947524
expand=/dev/sda3

[fedora-42]
name=Fedora® 42
osinfo=fedora42
arch=x86_64
file=fedora-42.xz
checksum[sha512]=...
revision=3
format=raw
size=4294967296
compressed_size=172190964
expand=/dev/sda3

The part in square brackets is the "os-version", which is the same string that is used on the virt-builder command line to build that OS.

The index file creation and signature can be eased with the virt-builder-repository(1) tool.

After preparing the "index" file in the correct format, clearsign it using the following command:

gpg --clearsign --armor index

This will create the final file called index.asc which can be uploaded to the server (and is the uri=.. URL). As noted above, signing the index file is optional, but recommended.

The following fields can appear:

"name=NAME"
The user-friendly name of this template. This is displayed in the --list output but is otherwise not significant.
"osinfo=ID"
This optional field maps the operating system to the associated libosinfo ID. Virt-builder does not use it (yet).
"arch=ARCH"
The architecture of the operating system installed within the template. This field is required.
"file=PATH"
The path (relative to the index) of the xz-compressed template.

Note that absolute paths or URIs are not permitted here. This is because virt-builder has a "same origin" policy for templates so they cannot come from other servers.

"sig=PATH"
This option is deprecated. Use the checksum field instead.

The path (relative to the index) of the GPG detached signature of the xz file.

Note that absolute paths or URIs are not permitted here. This is because virt-builder has a "same origin" policy for templates so they cannot come from other servers.

The file can be created as follows:

gpg --detach-sign --armor -o disk.xz.sig disk.xz
"checksum[sha512]=7b882fe9b82eb0fef..."
The SHA-512 checksum of the file specified in file=.. is checked after it is download
ed. Pour calculer la signature, exécutez : 
sha512sum disk.xz

Notez que si vous utilisez cette option, vous n'avez pas besoin de signer le fichier, c'est-à-dire n'utilisez pas "sig". Cette option remplace "sig".

"checksum=7b882fe9b82eb0fef..."
"checksum" est un alias pour "checksum[sha512]".

Si vous avez besoin d'interopérer avec virt-builder = 1.24.0, vous devez utiliser "checksum" car cette version produirait une erreur d'analyse avec des crochets et des chiffres dans la clé d'un champ. Ceci est corrigé dans virt-builder ≥ 1.24.1.

"revision=N"
La révision est un entier utilisé pour contrôler le cache des modèles. Augmenter le numéro de révision oblige les clients à télécharger à nouveau le modèle même s'ils en ont une copie dans le cache.

Le numéro de révision est facultatif. S'il est omis, la valeur par défaut est 1.

"format=raw"
"format=qcow2"
Spécifiez le format de l'image disque ; s'il est compressé, c'est le format avant la compression. S'il n'est pas spécifié, le format est auto-détecté, mais il est généralement préférable d'être explicite sur le format désiré.

Notez qu'il s'agit du format source, différent de l'option --format (format de sortie demandé). Virt-builder effectue une conversion à la volée du format source vers le format de sortie demandé.

"size=NNN"
La taille virtuelle de l'image en octets. C'est la taille de l'image une fois décompressée. Si vous utilisez un format non brut comme qcow2, cela signifie la taille du disque virtuel, pas la taille du fichier qcow2.

Ce champ est requis.

Virt-builder l'utilise également comme taille minimale que les utilisateurs peuvent demander via l'option --size, ou comme taille par défaut s'il n'y a pas d'option --size.

"compressed_size=NNN"
La taille réelle de l'image disque en octets, c'est-à-dire ce qui a été spécifié dans file=... Ceci est uniquement utilisé à titre informatif (lors de l'utilisation des formats "long" et "json" de --list).
"expand=/dev/sdaX"
Lors de l'extension de l'image à sa taille finale, demandez à virt-resize(1) d'étendre la partition nommée dans l'image invitée pour occuper tout l'espace disponible. Cela fonctionne comme l'option --expand de virt-resize.

Vous devriez généralement mettre ici le nom de périphérique du système de fichiers racine de l'invité.

Il est conseillé d'utiliser cette option, mais ce n'est pas obligatoire. Si le champ est omis, virt-resize créera une partition supplémentaire à la fin du disque pour couvrir l'espace libre, ce qui est beaucoup moins convivial.

"lvexpand=/dev/VolGroup/LogVol"
Lors de l'extension de l'image à sa taille finale, demandez à virt-resize(1) d'étendre le volume logique nommé dans l'image invitée pour occuper tout l'espace disponible. Cela fonctionne comme l'option --lv-expand de virt-resize.

Si l'invité utilise LVM2, vous devriez généralement mettre ici le LV du système de fichiers racine de l'invité. Si l'invité n'utilise pas LVM2 ou si son système de fichiers racine n'est pas sur un LV, n'utilisez pas cette option.

"notes=NOTES"
Toutes les notes accompagnant cette image, en particulier les notes décrivant les paquets présents dans l'image, la manière dont l'image a été préparée et les informations de licence.

Ces informations sont affichées dans les modes --notes et --list --long.

Vous pouvez utiliser des notes multilignes ici en indentant chaque nouvelle ligne avec au moins un caractère d'espacement (même sur les lignes vides) :

notes=Cette image a été préparée en utilisant
 le script kickstart suivant :
                               <-- une espace au début de la ligne
 part /boot --fstype ext3
 ...
"hidden=true"
L'utilisation du drapeau caché empêche le modèle d'être listé par l'option --list (mais il reste installable). Ceci est utilisé pour les images de test.
"aliases=ALIAS1 ALIAS2 ..."
Ce champ facultatif spécifie une liste d'alias, séparés par des espaces, pour l'image. Par exemple, un alias pourrait être utilisé pour pointer toujours vers la dernière version d'une image spécifique, laissant les anciennes versions disponibles dans l'index au lieu de mettre à jour la même image (voir le champ "revision").

Exécution de virt-builder sur plusieurs sources

Il est possible d'utiliser plusieurs sources avec virt-builder. La méthode recommandée est de déployer des fichiers .conf pointant vers les fichiers d'index. Une autre méthode consiste à spécifier les sources en utilisant plusieurs options --source et/ou --fingerprint :

virt-builder \
  --source http://example.com/s1/index.asc \
  --source http://example.com/s2/index.asc

Vous pouvez fournir N ou 1 empreintes digitales. Dans le cas où vous fournissez N empreintes digitales, N = nombre de sources et il y a une correspondance 1 pour 1 entre chaque source et chaque empreinte digitale :

virt-builder \
  --source http://example.com/s1/index.asc --fingerprint '0123 ...' \
  --source http://example.com/s2/index.asc --fingerprint '9876 ...'

Dans le cas où vous fournissez 1 empreinte digitale, la même empreinte digitale est utilisée pour toutes les sources.

Vous "devez" fournir au moins 1 empreinte digitale.

Licence des modèles

Vous devez être conscient de la licence des images que vous distribuez. Pour les invités open source, fournissez un lien vers le code source dans le champ "notes" et respectez les autres exigences (par exemple, concernant les marques déposées).

Spécification formelle du fichier d'index

Le format du fichier d'index a une spécification formelle définie par le scanner flex et le parseur bison utilisés pour analyser le fichier. Ceci peut être trouvé dans les fichiers suivants de l'arborescence source de libguestfs :

builder/index-scan.l
builder/index-parse.y

Un outil appelé virt-index-validate(1) est disponible pour valider le fichier d'index afin de s'assurer qu'il est correct.

Notez que le parseur et l'outil peuvent fonctionner sur le fichier d'index signé ou non signé (c'est-à-dire index ou index.asc).

L'index est toujours encodé en UTF-8.

CACHAGE

Mise en cache des modèles

Étant donné que les modèles sont généralement très volumineux, les modèles téléchargés sont mis en cache dans le répertoire personnel de l'utilisateur.

L'emplacement du cache est $XDG_CACHE_HOME/virt-builder/ ou $HOME/.cache/virt-builder.

Vous pouvez afficher des informations sur le répertoire de cache, y compris quels invités sont actuellement mis en cache, en exécutant :

virt-builder --print-cache

Le cache peut être supprimé si vous souhaitez économiser de l'espace en exécutant :

virt-builder --delete-cache

Vous pouvez télécharger tous les modèles (actuels) dans le cache local en exécutant :

virt-builder --cache-all-templates

Pour désactiver le cache des modèles, utilisez --no-cache.

Seuls les modèles sont mis en cache. L'index et les signatures numériques détachées ne sont pas mis en cache.

Mise en cache des paquets

Virt-builder utilise curl(1) pour télécharger des fichiers et utilise également les paramètres actuels de "http_proxy" (etc) lors de l'installation de paquets (--install, --update).

Vous pourriez donc vouloir définir ces variables d'environnement afin de maximiser la quantité de mise en cache locale qui se produit. Voir "VARIABLES D'ENVIRONNEMENT" et curl(1).

Miroirs locaux

Pour augmenter la vitesse et la fiabilité de l'installation des paquets, vous pouvez configurer un miroir local de la distribution cible, et pointer le gestionnaire de paquets invité vers celui-ci.

Utilisation d'un miroir local avec Fedora

Pour installer un invité Fedora à l'aide d'un miroir local :

virt-builder fedora-41 \
  --edit '/etc/yum.repos.d/fedora.repo:
      s{.*baseurl=.*}{baseurl=http://example.com/mirror/};
      s{.*metalink=.*}{};
  ' \
  --edit '/etc/yum.repos.d/fedora-updates.repo:
      s{.*baseurl=.*}{baseurl=http://example.com/mirror-updates/};
      s{.*metalink=.*}{};
  ' \
  --run-command 'dnf -y update' \
  --install 'pkg1,pkg2,...'

Utilisation d'un miroir local avec Debian

En supposant que vous utilisez "apt-proxy" pour mettre en miroir le dépôt, vous devriez créer un nouveau fichier sources.list pour pointer vers votre proxy (voir https://help.ubuntu.com/community/AptProxy) et ensuite faire :

virt-builder debian-8 \
  --upload sources.list:/etc/apt/sources.list \
  --run-command 'apt-get -y update' \
  --install 'pkg1,pkg2,...'

SIGNATURES NUMÉRIQUES

Virt-builder utilise GNU Privacy Guard (GnuPG ou gpg) pour vérifier que l'index et les modèles n'ont pas été falsifiés.

La source pointe vers un fichier d'index, qui est facultativement signé.

Virt-builder télécharge l'index et vérifie que la signature est valide et que l'empreinte digitale du signataire correspond à l'empreinte digitale spécifiée (c'est-à-dire celle spécifiée dans gpgkey=.. dans le fichier .conf, ou avec --fingerprint, dans cet ordre).

Pour vérifier par rapport à la clé publique/empreinte digitale intégrée, cela nécessite d'importer la clé publique dans le trousseau gpg local de l'utilisateur (c'est ainsi que gpg fonctionne).

Lorsqu'un modèle est téléchargé, sa signature est vérifiée de la même manière.

Bien que les signatures soient facultatives, si vous ne les avez pas, les utilisateurs de virt-builder devront utiliser --no-check-signature sur la ligne de commande. Cela empêche un attaquant de remplacer le fichier d'index signé par un fichier d'index non signé et que virt-builder fonctionne silencieusement sans vérifier la signature. Dans tous les cas, il est fortement recommandé de toujours créer des index et des modèles signés.

Virt-builder peut construire un invité pour n'importe quelle architecture, quelle que soit l'architecture hôte. Par exemple, un invité x86-64 sur un hôte ARM.

Cependant, certaines options peuvent ne pas fonctionner, en particulier les options qui nécessitent l'exécution de commandes dans l'invité pendant le processus de construction : --install, --update, --run, --run-command. Vous devrez peut-être les remplacer par leurs équivalents de premier démarrage.

SÉCURITÉ

Virt-builder n'a pas besoin de s'exécuter en tant que root (en fait, ne devrait pas s'exécuter en tant que root), et n'utilise pas setuid, "sudo" ou tout autre mécanisme similaire.

--install, --update, --run et --run-command sont implémentés à l'aide d'une appliance (une petite machine virtuelle) afin que ces commandes ne s'exécutent pas sur l'hôte. Si vous utilisez le backend libvirt de libguestfs et que SELinux est activé, la machine virtuelle est en outre encapsulée dans un conteneur SELinux (sVirt).

Cependant, ces options auront accès au réseau de l'hôte et, comme le modèle peut contenir du code non fiable, le code pourrait tenter d'accéder à des ressources réseau de l'hôte auxquelles il ne devrait pas avoir accès. Vous pouvez utiliser --no-network pour éviter cela.

Les commandes de premier démarrage s'exécutent dans le contexte de l'invité lorsqu'il démarre, et la sécurité de votre hyperviseur / cloud devrait donc être prise en considération.

Virt-builder injecte une graine aléatoire dans chaque invité qu'il construit. Cela permet de s'assurer que les numéros de séquence TCP, les UUID, les clés d'hôte SSH, etc., sont véritablement aléatoires au démarrage de l'invité.

Vous devez vérifier les signatures numériques et ne pas ignorer les erreurs de signature.

CLONES

Si vous souhaitez créer de nombreux nouveaux invités du même type, il est tentant d'exécuter virt-builder une fois, puis de copier le fichier de sortie. Vous ne devez **pas** faire cela. Vous devez exécuter virt-builder une fois pour chaque nouvel invité dont vous avez besoin.

La raison est que chaque clone a besoin d'avoir (au moins) une graine aléatoire distincte, et potentiellement d'autres caractéristiques uniques (telles que les UUID de système de fichiers) dans les futures versions de virt-builder.

Une autre chose que vous ne devez **pas** faire est de démarrer l'invité, puis de cloner l'image disque démarrée. La raison est que certains invités créent des identifiants de machine, des clés d'hôte SSH, etc., uniques au premier démarrage, et vous ne voudriez pas que les clones aient des identités dupliquées.

Voir également : virt-sysprep(1).

PERFORMANCE

L'aspect le plus important pour obtenir de bonnes performances est la mise en cache. Les modèles sont téléchargés dans le cache la première fois qu'ils sont utilisés, ou si vous utilisez l'option --cache-all-templates. Voir "MISE EN CACHE" ci-dessus pour plus d'informations.

Les paquets requis pour les options --install et --update sont téléchargés à l'aide de la connexion réseau de l'hôte. La définition des variables d'environnement "http_proxy", "https_proxy" et "ftp_proxy" pour pointer vers un cache web local peut garantir qu'ils n'ont besoin d'être téléchargés qu'une seule fois. Vous pouvez également essayer d'utiliser un dépôt de paquets local, bien que cela puisse être complexe à configurer et varie selon la distribution Linux que vous essayez d'installer.

Utilisation de --no-sync

Utilisez --no-sync. Cependant, lisez les mises en garde dans la section "OPTIONS" ci-dessus, car cela peut provoquer une corruption du disque si mal utilisé.

Saut de virt-resize

Virt-builder peut sauter l'étape virt-resize dans certaines conditions. Cela rend virt-builder beaucoup plus rapide. Les conditions sont :

  • la sortie doit être un fichier régulier (pas un périphérique bloc), **et**
  • l'utilisateur n'a **pas** utilisé l'option --size, **et**
  • le format de sortie est le même que le format du modèle (généralement brut).

pxzcat

Virt-builder utilise une implémentation interne de pxzcat (xzcat parallèle) si liblzma a été trouvé au moment de la compilation. Si liblzma n'a pas été trouvé au moment de la compilation, xzcat régulier (monothread) est utilisé.

SELINUX

Les invités qui utilisent SELinux (tels que Fedora et Red Hat Enterprise Linux) nécessitent que chaque fichier ait un libellé SELinux correct.

Virt-builder ne sait pas comment attribuer un libellé aux nouveaux fichiers, il existe donc deux stratégies possibles qu'il peut utiliser pour assurer un libellé correct :

Re-étiquetage automatique
Cela exécute setfiles(8) juste avant de finaliser l'invité, ce qui définit correctement les libellés SELinux dans l'image disque.

C'est la méthode recommandée.

Utilisation de --no-selinux-relabel --touch /.autorelabel
Les modèles d'invités peuvent déjà contenir un fichier appelé /.autorelabel ou vous pouvez le créer.

Pour les invités qui utilisent SELinux, cela fait exécuter restorecon(8) au premier démarrage. Les invités redémarreront une fois la première fois que vous les utiliserez, ce qui est normal et sans danger.

SORTIE LISIBLE PAR MACHINE

L'option --machine-readable peut être utilisée pour rendre la sortie plus conviviale pour les machines, ce qui est utile lors de l'appel de virt-builder à partir d'autres programmes, d'interfaces graphiques, etc.

Utilisez l'option seule pour interroger les capacités du binaire virt-builder. La sortie typique ressemble à ceci :

$ virt-builder --machine-readable
virt-builder
arch
config-file
customize
json-list
pxzcat

Une liste de fonctionnalités est imprimée, une par ligne, et le programme se termine avec le statut 0.

Il est possible de spécifier une chaîne de format pour contrôler la sortie ; voir "SORTIE AVANCÉE LISIBLE PAR MACHINE" dans guestfs(3).
