FORK(3P) Manuel du programmeur POSIX FORK(3P)

PROLOGUE

Cette page manuelle fait partie du Manuel du programmeur POSIX. L'implémentation Linux de cette interface peut différer (consultez la page manuelle Linux correspondante pour les détails du comportement de Linux), ou l'interface peut ne pas être implémentée sur Linux.

NOM

fork — créer un nouveau processus

SYNOPSIS

#include <unistd.h>
pid_t fork(void);

DESCRIPTION

La fonction fork() crée un nouveau processus. Le nouveau processus (processus fils) est une copie exacte du processus appelant (processus parent), sauf comme détaillé ci-dessous :

*
Le processus fils possède un identifiant de processus unique.
*
L'identifiant du processus fils ne correspond non plus à aucun identifiant de groupe de processus actif.
*
Le processus fils possède un identifiant de processus parent différent, qui est l'identifiant du processus appelant.
*
Le processus fils possède sa propre copie des descripteurs de fichiers du parent. Chaque descripteur de fichier du fils fait référence à la même description de fichier ouverte que le descripteur de fichier correspondant du parent.
*
Le processus fils possède sa propre copie des flux de répertoires ouverts du parent. Chaque flux de répertoire ouvert dans le processus fils peut partager le positionnement du flux de répertoire avec le flux de répertoire correspondant du parent.
*
Le processus fils possède sa propre copie des descripteurs de catalogue de messages du parent.
*
Les valeurs tms_utime, tms_stime, tms_cutimeet tms_cstime du processus fils sont mises à 0.
*
Le temps restant avant un signal de réveil est remis à zéro, et le réveil, s'il existe, est annulé ; voir alarm().
*
Toutes les valeurs semadj sont effacées.
*
Les verrous de fichiers définis par le processus parent ne sont pas hérités par le processus fils.
*
L'ensemble des signaux en attente pour le processus fils est initialisé à l'ensemble vide.
*
Les minuteurs d'intervalle sont réinitialisés dans le processus fils.
*
Tout sémaphore ouvert dans le processus parent est également ouvert dans le processus fils.
*
Le processus fils n'hérite d'aucun verrou de mémoire d'espace d'adressage établi par le processus parent via des appels à mlockall() ou mlock().
*
Les correspondances mémoire créées dans le parent sont conservées dans le processus fils. Les correspondances MAP_PRIVATE héritées du parent sont également des correspondances MAP_PRIVATE dans le fils, et toute modification des données dans ces correspondances effectuée par le parent avant l'appel à fork() est visible par le fils. Toute modification des données dans les correspondances MAP_PRIVATE effectuée par le parent après le retour de fork() n'est visible que par le parent. Les modifications des données dans les correspondances MAP_PRIVATE effectuées par le fils ne sont visibles que par le fils.
*
Pour les politiques d'ordonnancement SCHED_FIFO et SCHED_RR, le processus fils hérite de la politique et des paramètres de priorité du processus parent lors d'un appel à la fonction fork(). Pour les autres politiques d'ordonnancement, la politique et les paramètres de priorité lors de fork() sont définis par l'implémentation.
*
Les minuteurs par processus créés par le parent ne sont pas hérités par le processus fils.
*
Le processus fils possède sa propre copie des descripteurs de file d'attente de messages du parent. Chaque descripteur de message du fils fait référence à la même description de file d'attente de messages ouverte que le descripteur de message correspondant du parent.
*
Aucune opération d'entrée ou de sortie asynchrone n'est héritée par le processus fils. Toute utilisation de blocs de contrôle asynchrones créés par le parent produit un comportement indéfini.
*
Un processus est créé avec un seul thread. Si un processus multi-thread appelle fork(), le nouveau processus contient une réplique du thread appelant et de tout son espace d'adressage, éventuellement y compris les états des mutex et d'autres ressources. Par conséquent, pour éviter des erreurs, le processus fils ne peut exécuter que des opérations sûres vis-à-vis des signaux asynchrones jusqu'à ce qu'une des fonctions exec soit appelée.

Lorsque l'application appelle fork() depuis un gestionnaire de signal et que l'un des gestionnaires fork enregistrés par pthread_atfork() appelle une fonction qui n'est pas sûre vis-à-vis des signaux asynchrones, le comportement est indéfini.

*
Si l'option Trace et l'option Trace Inherit sont toutes deux prises en charge :

Si le processus appelant était tracé dans un flux de trace dont la politique d'héritage était définie sur POSIX_TRACE_INHERITED, le processus fils sera tracé dans ce flux de trace, et le processus fils héritera de la correspondance du parent entre les noms d'événements de trace et les identifiants de type d'événement de trace. Si le flux de trace dans lequel le processus appelant était tracé avait sa politique d'héritage définie sur POSIX_TRACE_CLOSE_FOR_CHILD, le processus fils ne sera pas tracé dans ce flux de trace. La politique d'héritage est définie par un appel à la fonction posix_trace_attr_setinherited().

*
Si l'option Trace est prise en charge, mais que l'option Trace Inherit ne l'est pas :

Le processus fils ne sera tracé dans aucun des flux de trace de son processus parent.

*
Si l'option Trace est prise en charge, le processus fils d'un processus contrôleur de trace ne contrôlera pas les flux de trace contrôlés par son processus parent.
*
La valeur initiale de l'horloge de temps processeur du processus fils est mise à zéro.
*
La valeur initiale de l'horloge de temps processeur du thread unique du processus fils est mise à zéro.

Toutes les autres caractéristiques de processus définies par POSIX.1‐2008 sont les mêmes dans les processus parent et fils. L'héritage des caractéristiques de processus non définies par POSIX.1‐2008 n'est pas spécifié par POSIX.1‐2008.

Après fork(), les processus parent et fils sont tous deux capables d'exécuter indépendamment avant que l'un des deux ne se termine.

VALEUR RENVOYÉE

Lors de l'achèvement avec succès, fork() renvoie 0 au processus fils et renvoie l'identifiant du processus fils au processus parent. Les deux processus continuent de s'exécuter à partir de la fonction fork(). Sinon, -1 est renvoyé au processus parent, aucun processus fils n'est créé, et errno est défini pour indiquer l'erreur.

ERREURS

La fonction fork() échoue si :

EAGAIN
Le système manquait des ressources nécessaires pour créer un autre processus, ou la limite imposée par le système sur le nombre total de processus en cours d'exécution à l'échelle du système ou par un utilisateur unique {CHILD_MAX} serait dépassée.

La fonction fork() peut échouer si :

ENOMEM
L'espace de stockage disponible est insuffisant.

EXEMPLES

Aucun.

UTILISATION PAR LES APPLICATIONS

Aucune.

JUSTIFICATION

De nombreuses implémentations historiques présentent des fenêtres de synchronisation où un signal envoyé à un groupe de processus (par exemple, un SIGINT interactif) juste avant ou pendant l'exécution de fork() est délivré au parent après le fork() mais pas au fils parce que le code de fork() efface l'ensemble des signaux en attente du fils. Ce volume de POSIX.1‐2017 ne requiert pas, ni ne permet même, ce comportement. Cependant, il est pragmatique de s'attendre à ce que des problèmes de cette nature continuent d'exister dans des implémentations qui semblent conformes à ce volume de POSIX.1‐2017 et qui passent les suites de vérification disponibles. Ce comportement n'est qu'une conséquence de l'échec de l'implémentation à rendre totalement invisible l'intervalle entre la génération et la délivrance du signal. Du point de vue de l'applicationn's perspective, a fork () call should appear atomic. A signal that is generated prior to the fork () should be delivered prior to the fork (). A signal sent to the process group after the fork () should be delivered to both parent and child. The implementation may actually initialize internal data structures corresponding to the child's set of pending signals to include signals sent to the process group during the fork (). Since the fork () call can be considered as atomic from the application's perspective, the set would be initialized as empty and such signals would have arrived after the for

k

(); see also <signal.h> . One approach that has been suggested to address the problem of signal inheritance across

fork

() is to add an [EINTR] error, which would be returned when a signal is detected during the call. While this is preferable to losing signals, it was not considered an optimal solution. Although it is not recommended for this purpose, such an error would be an allowable extension for an implementation. The [ENOMEM] error value is reserved for those implementations that detect and distinguish such a condition. This condition occurs when an implementation detects that there is not enough memory to create the process. This is intended to be returned when [EAGAIN

]

is inappropriate because there can never be enough memory (either primary or secondary storage) to perform the operation. Since for

k

() duplicates an existing process, this must be a condition where there is sufficient memory for one such process, but not for two. Many historical implementations actually return [ENOMEM

]

due to temporary lack of memory, a case that is not generally distinct from [EAGAIN

]

from the perspective of a conforming application. Part of the reason for including the optional error [ENOMEM] is because the SVID specifies it and it should be reserved for the error condition specified there. The condition is not applicable on many implementations. IEEE Std 1003.1‐1988 neglected to require concurrent execution of the parent and

child of

fork (). A system that single-threads processes was clearly not intended and is considered an unacceptable ``toy implementation'' of this volume of POSIX.1‐2017. The only objection anticipated to the phrase ``executing independently'' is testability, but this assertion should be testable. Such tests require that both the parent and child can block on a detectable action of the other, such as a write to a pipe or a signal. An interactive exchange of such actions should be possible for the system to conform to the intent of this volume of POSIX.1‐2017. The [EAGAIN

]

error exists to warn applications that such a condition might occur. Whether it occurs or not is not in any practical sense under the control of the application because the condition is usually a consequence of the user's use of the system, not of the application's code. Thus, no application can or should rely upon its occurrence under any circumstances, nor should the exact semantics of what concept of ``user'' is used be of concern to the application developer. Validation writers should be cognizant of this limitation. There are two reasons why POSIX programmers call fork (). One reason is to create a new thread of control within the same program (which was originally only possible in POSIX by creating a new process); the other is to create a new process running a different program. In the latter case, the call to fork () is soon followed by a call to one of the exe

c

functions. The general problem with making fork () work in a multi-threaded world is what to do with all of the threads. There are two alternatives. One is to copy all of the threads into the new process. This causes the programmer or implementation to deal with threads that are suspended on system calls or that might be about to execute system calls that should not be executed in the new process. The other alternative is to copy only the thread that calls fork (). This creates the difficulty that the state of process-local resources is usually held in process memory. If a thread that is not calling fork () holds a resource, that resource is never released in the child process because the thread whose job it is to release the resource does not exist in the child process. When a programmer is writing a multi-threaded program, the first described

use of

fork (), creating new threads in the same program, is provided by the pthread_create () function. The

fork

() function is thus used only to run new programs, and the effects of calling functions that require certain resources between the call to fork () and the call to an exec function are undefined. The addition of the forkall () function to the standard was considered and rejected. The forkall () function lets all the threads in the parent be duplicated in the child. This essentially duplicates the state of the parent in the child. This allows threads in the child to continue processing and allows locks and the state to be preserved without explicit pthread_atfork () code. The calling process has to ensure that the threads processing state that is shared between the parent and child (that is, file descriptors or

MAP_SHARED memory) behaves
properly after

forkal

l

(). For example, if a thread is reading a file descriptor

in the
parent when

forkal

l

() is called, then two threads (one in the parent and one in the child) are reading the file descriptor after the forkall (). If this is not desired behavior, the parent process has to synchronize with such threads before calling forkall (). While the fork () function is async-signal-safe, there is no way for an implementation to determine whether the fork handlers established by pthread_atfork () are async-signal-safe. The fork handlers may attempt to execute portions of the implementation that are not async-signal-safe, such as those that are protected by mutexes, leading to a deadlock condition. It is therefore undefined for the fork handlers to execute functions that are not async-signal-safe when fork () is called from a signal handler. When forkal

l

wait
