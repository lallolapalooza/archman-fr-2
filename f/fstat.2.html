stat(2) Manuel des appels système stat(2)

NOM

stat, fstat, lstat, fstatat - obtenir le statut d'un fichier

BIBLIOTHÈQUE

Bibliothèque C standard (libc, -lc)

SYNTAXE

#include <sys/stat.h>
int stat(const char *restrict path,
         struct stat *restrict statbuf);
int fstat(int fd, struct stat *statbuf);
int lstat(const char *restrict path,
         struct stat *restrict statbuf);
#include <fcntl.h>           /* Définition des constantes AT_* */
#include <sys/stat.h>
int fstatat(int dirfd, const char *restrict path,
         struct stat *restrict statbuf, int flags);

DESCRIPTION

Ces fonctions retournent des informations sur un fichier, dans le tampon pointé par statbuf. Aucune permission n'est requise sur le fichier lui-même, mais — dans le cas de stat(), fstatat(), et lstat() — une permission d'exécution (de recherche) est requise sur tous les répertoires du chemin path qui mènent au fichier.

stat() et fstatat() récupèrent des informations sur le fichier pointé par path ; les différences pour fstatat() sont décrites ci-dessous.

lstat() est identique à stat(), sauf que si path est un lien symbolique, elle retourne des informations sur le lien lui-même, et non sur le fichier auquel le lien fait référence.

fstat() est identique à stat(), sauf que le fichier pour lequel des informations doivent être récupérées est spécifié par le descripteur de fichier fd.

La structure stat

Tous ces appels système retournent une structure stat (voir stat(3)).

Note : pour des raisons de performance et de simplicité, différents champs de la structure stat peuvent contenir des informations d'état provenant de différents moments pendant l'exécution de l'appel système. Par exemple, si st_mode ou st_uid est modifié par un autre processus en appelant chmod(2) ou chown(2), stat() pourrait retourner l'ancien st_mode avec le nouveau st_uid, ou l'ancien st_uid avec le nouveau st_mode.

fstatat()

L'appel système fstatat() est une interface plus générale pour accéder aux informations de fichier, qui peut fournir exactement le comportement de chacun de stat(), lstat(), et fstat().

Si path est relatif, il est interprété par rapport au répertoire référencé par le descripteur de fichier dirfd (plutôt que par rapport au répertoire de travail courant du processus appelant, comme le font stat() et lstat() pour un nom de chemin relatif).

Si path est relatif et dirfd est la valeur spéciale AT_FDCWD, alors path est interprété par rapport au répertoire de travail courant du processus appelant (comme stat() et lstat()).

Si path est absolu, alors dirfd est ignoré.

flags peut être 0, ou inclure un ou plusieurs des drapeaux suivants ORés :

AT_EMPTY_PATH (depuis Linux 2.6.39)
Si path est une chaîne vide (ou NULL, depuis Linux 6.11) opérer sur le fichier référencé par dirfd (qui peut avoir été obtenu en utilisant le drapeau open(2) O_PATH). Dans ce cas, dirfd peut référencer n'importe quel type de fichier, pas seulement un répertoire, et le comportement de fstatat() est similaire à celui de fstat(). Si dirfd est AT_FDCWD, l'appel opère sur le répertoire de travail courant. Ce drapeau est spécifique à Linux ; définissez _GNU_SOURCE pour obtenir sa définition.
AT_NO_AUTOMOUNT (depuis Linux 2.6.38)
Ne pas automonter le composant final ("basename") de path. Depuis Linux 3.1 ce drapeau est ignoré. Depuis Linux 4.11 ce drapeau est implicite.
AT_SYMLINK_NOFOLLOW
Si path est un lien symbolique, ne pas le déréférencer : retourner à la place des informations sur le lien lui-même, comme lstat(). (Par défaut, fstatat() déréférence les liens symboliques, comme stat().)

Voir openat(2) pour une explication de la nécessité de fstatat().

VALEUR DE RETOUR

En cas de succès, zéro est retourné. En cas d'erreur, -1 est retourné, et errno est défini pour indiquer l'erreur.

ERREURS

EACCES
La permission de recherche est refusée pour l'un des répertoires du préfixe du chemin path. (Voir aussi path_resolution(7).)
EBADF
fd n'est pas un descripteur de fichier ouvert valide.
EBADF
(fstatat()) path est relatif mais dirfd n'est ni AT_FDCWD ni un descripteur de fichier valide.
EFAULT
Mauvaise adresse.
EINVAL
(fstatat()) Drapeau invalide spécifié dans flags.
ELOOP
Trop de liens symboliques rencontrés lors de la traversée du chemin.
ENAMETOOLONG
path est trop long.
ENOENT
Un composant de path n'existe pas ou est un lien symbolique invalide.
ENOENT
path est une chaîne vide et AT_EMPTY_PATH n'a pas été spécifié dans flags.
ENOMEM
Mémoire insuffisante (c'est-à-dire mémoire du noyau).
ENOTDIR
Un composant du préfixe du chemin path n'est pas un répertoire.
ENOTDIR
(fstatat()) path est relatif et dirfd est un descripteur de fichier faisant référence à un fichier autre qu'un répertoire.
EOVERFLOW
path ou fd fait référence à un fichier dont la taille, le numéro d'inode, ou le nombre de blocs ne peuvent pas être représentés dans les types off_t, ino_t, ou blkcnt_t respectivement. Cette erreur peut survenir lorsque, par exemple, une application compilée sur une plateforme 32 bits sans -D_FILE_OFFSET_BITS=64 appelle stat() sur un fichier dont la taille dépasse (1<<31)-1 octets.

NORMES

POSIX.1-2024.

HISTORIQUE

stat()
fstat()
lstat()
SVr4, 4.3BSD, POSIX.1-2001.
fstatat()
POSIX.1-2008. Linux 2.6.16, glibc 2.4.

Selon POSIX.1-2001, lstat() sur un lien symbolique doit retourner des informations valides uniquement dans le champ st_size et le type de fichier

du st_mode champ de la structure stat . POSIX.1-2008 resserre la spécification, exigeant que lstat() renvoie des informations valides dans tous les champs sauf les bits de mode dans st_mode.

L'utilisation des champs st_blocks et st_blksize peut être moins portable. (Ils ont été introduits dans BSD. L'interprétation diffère entre les systèmes, et possiblement sur un même système lorsque des montages NFS sont impliqués.)

C différences bibliothèque/noyau

Au fil du temps, les augmentations de la taille de la structure stat ont conduit à trois versions successives de stat() : sys_stat() (emplacement __NR_oldstat), sys_newstat() (emplacement __NR_stat), et sys_stat64() (emplacement __NR_stat64) sur les plateformes 32 bits telles que i386. Les deux premières versions étaient déjà présentes dans Linux 1.0 (bien qu'avec des noms différents) ; la dernière a été ajoutée dans Linux 2.4. Des remarques similaires s'appliquent à fstat() et lstat().

Les versions internes au noyau de la structure stat traitées par les différentes versions sont, respectivement :

__old_kernel_stat
La structure originale, avec des champs plutôt étroits, et sans rembourrage.
stat
Champ st_ino plus grand et rembourrage ajouté à diverses parties de la structure pour permettre une expansion future.
stat64
Champ st_ino encore plus grand, champs st_uid et st_gid plus grands pour accommoder l'expansion des UIDs et GIDs à 32 bits dans Linux-2.4, et divers autres champs agrandis et rembourrage supplémentaire dans la structure. (Divers octets de rembourrage ont finalement été consommés dans Linux 2.6, avec l'avènement d'identifiants de périphérique 32 bits et de composantes en nanosecondes pour les champs d'horodatage.)

La fonction enveloppe stat() de glibc masque ces détails aux applications, invoquant la version la plus récente de l'appel système fournie par le noyau, et repackant les informations renvoyées si nécessaire pour les vieilles binaires.

Sur les systèmes 64 bits modernes, la vie est plus simple : il existe un appel système stat() unique et le noyau traite une stat structure qui contient des champs d'une taille suffisante.

L'appel système sous-jacent employé par la fonction enveloppe fstatat() de glibc est en réalité appelé fstatat64() ou, sur certaines architectures, newfstatat().

EXEMPLES

Le programme suivant appelle lstat() et affiche des champs sélectionnés dans la structure stat renvoyée.

#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <sys/stat.h>
#include <sys/sysmacros.h>
#include <time.h>
int
main(int argc, char *argv[])
{
    struct stat sb;
    if (argc != 2) {
        fprintf(stderr, "Usage: %s <path>\n", argv[0]);
        exit(EXIT_FAILURE);
    }
    if (lstat(argv[1], &sb) == -1) {
        perror("lstat");
        exit(EXIT_FAILURE);
    }
    printf("ID of containing device:  [%x,%x]\n",
           major(sb.st_dev),
           minor(sb.st_dev));
    printf("File type:                ");
    switch (sb.st_mode & S_IFMT) {
    case S_IFBLK:  printf("block device\n");            break;
    case S_IFCHR:  printf("character device\n");        break;
    case S_IFDIR:  printf("directory\n");               break;
    case S_IFIFO:  printf("FIFO/pipe\n");               break;
    case S_IFLNK:  printf("symlink\n");                 break;
    case S_IFREG:  printf("regular file\n");            break;
    case S_IFSOCK: printf("socket\n");                  break;
    default:       printf("unknown?\n");                break;
    }
    printf("I-node number:            %ju\n", (uintmax_t) sb.st_ino);
    printf("Mode:                     %jo (octal)\n",
           (uintmax_t) sb.st_mode);
    printf("Link count:               %ju\n", (uintmax_t) sb.st_nlink);
    printf("Ownership:                UID=%ju   GID=%ju\n",
           (uintmax_t) sb.st_uid, (uintmax_t) sb.st_gid);
    printf("Preferred I/O block size: %jd bytes\n",
           (intmax_t) sb.st_blksize);
    printf("File size:                %jd bytes\n",
           (intmax_t) sb.st_size);
    printf("Blocks allocated:         %jd\n",
           (intmax_t) sb.st_blocks);
    printf("Last status change:       %s", ctime(&sb.st_ctime));
    printf("Last file access:         %s", ctime(&sb.st_atime));
    printf("Last file modification:   %s", ctime(&sb.st_mtime));
    exit(EXIT_SUCCESS);
}
