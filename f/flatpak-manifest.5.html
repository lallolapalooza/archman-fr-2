NOM

flatpak-manifest - Informations pour la construction d'une application

DESCRIPTION

Flatpak utilise des fichiers manifeste, ou recettes, au format json ou yaml pour décrire comment une application et ses dépendances intégrées peuvent être construites à partir des sources. Le manifeste est utilisé par flatpak-builder.

FORMAT DU FICHIER

Le niveau supérieur du fichier manifeste décrit les attributs globaux de l'application, comment elle peut être construite, et la liste des modules qui doivent être construits.

Propriétés de premier niveau

Voici les propriétés acceptées :

id ou app-id (chaîne)

Une chaîne définissant l'identifiant de l'application.

Notez que « app-id » est obsolète et n'est conservé que pour la rétrocompatibilité.

branch (chaîne)

La branche à utiliser lors de l'exportation de l'application. Si cette propriété n'est pas définie, la valeur par défaut provient de l'option default-branch.

Cette clé remplace à la fois la clé default-branch et l'option --default-branch de la ligne de commande. Sauf si vous avez besoin d'un nom de branche très spécifique (comme pour un runtime ou une extension), il est recommandé d'utiliser la clé default-branch à la place, car celle-ci peut être remplacée par l'option --default-branch.

default-branch (chaîne)

La branche par défaut à utiliser lors de l'exportation de l'application. La valeur par défaut est master.

Cette clé peut être remplacée par l'option --default-branch de la ligne de commande.

collection-id (chaîne)

L'identifiant de collection du dépôt, par défaut non défini. Définir un identifiant de collection globalement unique permet aux applications du dépôt d'être partagées via des systèmes pair-à-pair sans nécessiter de configuration supplémentaire. Lors de la construction dans un dépôt existant, l'identifiant de collection doit correspondre à l'identifiant de collection configuré existant pour ce dépôt.

extension-tag (chaîne)

Lors de la construction d'une extension, le tag du point d'extension à utiliser. Depuis flatpak 0.11.4, un runtime peut définir plusieurs emplacements pour le même point d'extension dans l'intention que différentes branches pour l'extension soient montées à chaque emplacement. Lors de la construction d'une extension, il est nécessaire de savoir sur quel point d'extension installer l'extension. Cette option résout toute ambiguïté quant au point d'extension à choisir. Si elle n'est pas spécifiée, le choix par défaut est d'installer soit dans l'unique emplacement du point d'extension, soit dans l'emplacement du point d'extension sans tag. S'il y a plusieurs emplacements pour le même point d'extension définis avec différents tags, une erreur se produira.

token-type (entier)

Le type de jeton nécessaire pour installer ce commit. Définir cette valeur à une valeur supérieure à 0 implique qu'une authentification sera nécessaire pour installer le flatpak.

runtime (chaîne)

Le nom du runtime utilisé par l'application.

runtime-version (chaîne)

La version du runtime utilisée par l'application, par défaut master.

sdk (chaîne)

Le nom du runtime de développement avec lequel l'application est construite.

var (chaîne)

Initialise le /var (autrement vide) inscriptible dans la construction avec une copie de ce runtime.

metadata (chaîne)

Utilise ce fichier comme fichier de métadonnées de base lors de la finalisation.

command (chaîne)

Le nom de fichier ou le chemin vers le binaire principal de l'application. Notez que cela doit être un exécutable unique, et non une ligne de commande ou un chemin absolu. Si vous souhaitez passer des arguments, installez un script shell wrapper et utilisez-le comme commande.

Notez également que la commande est utilisée lorsque l'application est exécutée via flatpak run, et n'affecte pas ce qui est exécuté lorsque l'application est exécutée d'autres manières, par exemple via le fichier desktop ou l'activation D-Bus.

build-runtime (booléen)

Construit un nouveau runtime au lieu d'une application.

build-extension (booléen)

Construit une extension.

separate-locales (booléen)

Sépare les fichiers de locale et les traductions dans un runtime d'extension. La valeur par défaut est true.

id-platform (chaîne)

Lors de la construction d'un sdk runtime, crée également une plateforme basée sur celui-ci avec cet identifiant.

metadata-platform (chaîne)

Le fichier de métadonnées à utiliser pour la plateforme que nous créons.

writable-sdk (booléen)

Si vrai, utilise une copie inscriptible du sdk pour /usr. La valeur par défaut est true si build-runtime est spécifié.

appstream-compose (booléen)

Exécute appstreamcli compose pendant la phase de nettoyage. La valeur par défaut est true.

sdk-extensions (tableau de chaînes)

Installe ces extensions sdk supplémentaires dans /usr.

platform-extensions (tableau de chaînes)

Installe ces extensions sdk supplémentaires lors de la création de la plateforme.

base (chaîne)

Commence avec les fichiers de l'application spécifiée. Cela peut être utilisé pour créer des applications qui étendent une autre application.

base-version (chaîne)

Utilise cette version spécifique de l'application spécifiée dans base. Si non spécifiée, utilise la valeur spécifiée dans branch

base-extensions (tableau de chaînes)

Installe ces extensions supplémentaires de l'application de base lors de l'initialisation du répertoire de l'application.

inherit-extensions (tableau de chaînes)

Hérite de ces points d'extension supplémentaires de l'application de base ou du sdk lors de la finalisation de la construction.

inherit-sdk-extensions (tableau de chaînes)

Hérite de ces points d'extension supplémentaires de l'application de base ou du sdk lors de la finalisation de la construction, mais ne les hérite pas dans la plateforme.

tags (tableau de chaînes)

Ajoute ces tags au fichier de métadonnées.

build-options (objet)

Objet spécifiant l'environnement de construction. Voir ci-dessous pour les détails.

modules (tableau d'objets ou de chaînes)

Un tableau d'objets spécifiant les modules à construire dans l'ordre. Les éléments de chaîne dans le tableau sont interprétés comme le nom d'un fichier json ou yaml séparé contenant un module. Voir ci-dessous pour les détails.

add-extensions (objets)

C'est un dictionnaire d'objets d'extension. La clé est le nom de l'extension. Voir ci-dessous pour les détails.

add-build-extensions (objets)

C'est un dictionnaire d'objets d'extension similaire à add-extensions. La principale différence est que les extensions sont ajoutées tôt et sont disponibles pour une utilisation pendant la construction.

cleanup (tableau de chaînes)

Un tableau de motifs de fichiers qui doivent être supprimés à la fin. Les motifs commençant par / sont considérés comme des chemins complets (sans le préfixe /app), sinon ils ne correspondent qu'au nom de base.

cleanup-commands (tableau de chaînes)

Un tableau de lignes de commande qui sont exécutées pendant la phase de nettoyage.

cleanup-platform (tableau de chaînes)

Fichiers supplémentaires à nettoyer dans la plateforme.

cleanup-platform-commands (tableau de chaînes)

Un tableau de lignes de commande qui sont exécutées pendant la phase de nettoyage de la plateforme.

prepare-platform-commands (tableau de chaînes)

Un tableau de lignes de commande qui sont exécutées après l'importation de la plateforme de base, mais avant l'application des nouveaux fichiers du sdk. C'est un bon endroit pour, par exemple, supprimer des éléments de la base qui pourraient entrer en conflit avec les fichiers ajoutés dans le sdk.

finish-args (tableau de chaînes)

Un tableau d'arguments passés à la commande flatpak build-finish .

rename-desktop-file (chaîne)

Tout fichier desktop avec ce nom sera renommé en un nom basé sur id pendant la phase de nettoyage. Le fichier appdata launchable sera mis à jour si nécessaire.

rename-appdata-file (chaîne)

Tout fichier appdata (metainfo) avec ce nom sera renommé en un nom basé sur id pendant la phase de nettoyage. L'id dans le fichier sera mis à jour si nécessaire ainsi que les provides subséquents. (depuis 1.4.1)

rename-mime-file (chaîne)

Toute fichier mimetypes avec ce nom sera renommé en un nom basé sur l'ID lors de la phase de nettoyage. (depuis 1.4.0)

rename-icon (string)

Toute icône avec ce nom sera renommée en un nom basé sur l'ID lors de la phase de nettoyage. Notez qu'il s'agit du nom de l'icône, pas du nom de fichier complet, elle ne doit donc pas inclure d'extension de nom de fichier.

rename-mime-icons (tableau de chaînes)

Toutes les icônes mime avec l'un de ces noms seront renommées en un nom préfixé par l'ID lors de la phase de nettoyage. Notez qu'il s'agit des noms d'icônes, pas des noms de fichiers complets, elles ne doivent donc pas inclure d'extension de nom de fichier. (depuis 1.4.0)

appdata-license (string)

Remplacez le champ project_license des données d'application (metainfo) par cette chaîne. Ceci est utile car la licence en amont concerne généralement l'application elle-même, tandis que l'application groupée peut contenir d'autres licences.

copy-icon (booléen)

Si rename-icon est défini, conservez une copie de l'ancien fichier icône.

desktop-file-name-prefix (string)

Cette chaîne sera préfixée à la clé Name dans le fichier desktop principal de l'application.

desktop-file-name-suffix (string)

Cette chaîne sera suffixée à la clé Name dans le fichier desktop principal de l'application.

Options de construction

Les options de construction spécifient l'environnement de construction d'un module, et peuvent être spécifiées globalement ainsi que par module. Les options peuvent également être spécifiées par architecture à l'aide de la propriété arch.

Voici les propriétés acceptées :

cflags (string)

Ceci est défini dans la variable d'environnement CFLAGS pendant la construction. Les spécifications multiples de ceci (dans par ex. la zone par architecture) sont concaténées, séparées par des espaces.

cflags-override (booléen)

Si ceci est vrai, effacez les cflags des options de construction précédentes avant de les ajouter à partir de ces options.

cppflags (string)

Ceci est défini dans la variable d'environnement CPPFLAGS pendant la construction. Les spécifications multiples de ceci (dans par ex. la zone par architecture) sont concaténées, séparées par des espaces.

cppflags-override (booléen)

Si ceci est vrai, effacez les cppflags des options de construction précédentes avant de les ajouter à partir de ces options.

cxxflags (string)

Ceci est défini dans la variable d'environnement CXXFLAGS pendant la construction. Les spécifications multiples de ceci (dans par ex. la zone par architecture) sont concaténées, séparées par des espaces.

cxxflags-override (booléen)

Si ceci est vrai, effacez les cxxflags des options de construction précédentes avant de les ajouter à partir de ces options.

ldflags (string)

Ceci est défini dans la variable d'environnement LDFLAGS pendant la construction. Les spécifications multiples de ceci (dans par ex. la zone par architecture) sont concaténées, séparées par des espaces.

ldflags-override (booléen)

Si ceci est vrai, effacez les ldflags des options de construction précédentes avant de les ajouter à partir de ces options.

prefix (string)

Le préfixe de construction pour les modules (par défaut /app pour les applications et /usr pour les runtimes).

libdir (string)

Le libdir de construction pour les modules (par défaut /app/lib pour les applications et /usr/lib pour les runtimes).

append-path (string)

Ceci sera ajouté à PATH dans l'environnement de construction (avec un deux-points initial si nécessaire).

prepend-path (string)

Ceci sera préfixé à PATH dans l'environnement de construction (avec un deux-points final si nécessaire).

append-ld-library-path (string)

Ceci sera ajouté à LD_LIBRARY_PATH dans l'environnement de construction (avec un deux-points initial si nécessaire).

prepend-ld-library-path (string)

Ceci sera préfixé à LD_LIBRARY_PATH dans l'environnement de construction (avec un deux-points final si nécessaire).

append-pkg-config-path (string)

Ceci sera ajouté à PKG_CONFIG_PATH dans l'environnement de construction (avec un deux-points initial si nécessaire).

prepend-pkg-config-path (string)

Ceci sera préfixé à PKG_CONFIG_PATH dans l'environnement de construction (avec un deux-points final si nécessaire).

env (objet)

Il s'agit d'un dictionnaire définissant les variables d'environnement à définir pendant la construction. Les éléments ici remplacent les propriétés qui définissent l'environnement, comme cflags et ldflags. Les clés avec une valeur nulle suppriment la variable correspondante.

secret-env (tableau de chaînes)

Il s'agit d'un tableau définissant quelles variables d'environnement de l'hôte sont transférées à l'environnement de build-commands ou post-install.

build-args (tableau de chaînes)

Il s'agit d'un tableau contenant des options supplémentaires à passer à flatpak build.

test-args (tableau de chaînes)

Similaire à build-args mais affecte les tests, pas la construction normale.

config-opts (tableau de chaînes)

Il s'agit d'un tableau contenant des options supplémentaires passées au système de construction pendant la configuration.

secret-opts (tableau de chaînes)

Il s'agit d'un tableau d'options qui seront passées à configure. Ceci est destiné à être utilisé pour passer des secrets via des variables d'environnement de l'hôte. Les variables d'environnement dans les options seront développées. '-DSECRET_ID=$CI_SECRET'

make-args (tableau de chaînes)

Un tableau d'arguments supplémentaires qui seront passés à make

make-install-args (tableau de chaînes)

Un tableau d'arguments supplémentaires qui seront passés à make install

strip (booléen)

Si ceci est vrai (la valeur par défaut est false), tous les fichiers ELF seront purgés après l'installation.

no-debuginfo (booléen)

Par défaut (si strip n'est pas vrai), flatpak-builder extrait toutes les informations de débogage des fichiers ELF dans des fichiers séparés et les place dans une extension. Si vous souhaitez désactiver cela, définissez no-debuginfo à vrai.

no-debuginfo-compression (booléen)

Par défaut, lors de l'extraction des informations de débogage, les sections de débogage sont compressées. Si vous souhaitez désactiver cela, définissez no-debuginfo-compression à vrai.

arch (objet)

Il s'agit d'un dictionnaire définissant un objet d'options de construction séparé pour chaque architecture, pour remplacer les options de construction principales.

Extension

Définit des points d'extension dans l'application ou le runtime qui peuvent être implémentés par des extensions, fournissant des fichiers supplémentaires disponibles pendant l'exécution.

Voici les propriétés acceptées :

directory (string)

Le répertoire où l'extension est montée. Si le point d'extension est pour une application, ce chemin est relatif à /app, sinon il est relatif à /usr.

bundle (booléen)

Si ceci est vrai, les données créées dans le répertoire d'extension sont omises du résultat, et plutôt empaquetées dans une extension séparée.

remove-after-build (booléen)

Si ceci est vrai, l'extension est supprimée à la fin. Ceci n'est intéressant que pour les extensions dans la propriété add-build-extensions.

De plus, les propriétés standard d'extension flatpak sont prises en charge et placées directement dans le fichier de métadonnées : autodelete, no-autodownload, subdirectories, add-ld-path, download-if, enable-if, autoprune-unless, merge-dirs, subdirectory-suffix, locale-subset, version, versions. Voir la documentation des métadonnées flatpak pour plus d'informations à ce sujet.

Module

Chaque module spécifie une source qui doit être construite et installée séparément. Il contient les options de construction et une liste de sources à télécharger et à extraire avant la construction.

Les modules peuvent être imbriqués, afin d'activer ou de désactiver des modules liés avec une seule clé. Les portées des modules sont toujours isolées, de sorte que les modules imbriqués n'héritent pas des attributs des modules parents.

Voici les propriétés acceptées :

name (string)

Le nom du module, utilisé par exemple dans les journaux de construction. Le nom est également utilisé pour construire les noms de fichiers et les arguments de ligne de commande, par conséquent, utiliser des espaces ou '/' dans cette chaîne est une mauvaise idée.

disabled (booléen)

Si vrai, saute ce module

sources (tableau d'objets ou de chaînes)

Un tableau d'objets définissant les sources qui seront téléchargées et extraites dans l'ordre. Les membres de chaîne dans le tableau sont interprétés comme le nom d'un fichier json ou yaml séparé contenant les sources. Voir ci-dessous pour les détails.

Un tableau d'options qui seront passées à configure, destiné à être utilisé pour passer des secrets via des variables d'environnement de l'hôte. Mettez l'option avec des variables d'environnement et elle sera résolue au préalable. '-DSECRET_ID=$CI_SECRET'

ENVIRONNEMENT DE

BUILD

Lors de la construction de l'application, chaque commande est exécutée dans un bac à sable séparé avec accès uniquement aux éléments nécessaires. Cette section décrit les détails du bac à sable. Toutes les options ici peuvent être remplacées globalement ou par module avec l'option build-args (bien qu'un tel manifeste ne fonctionnera pas si vous démarrez flatpak-builder avec --sandb

ox).

Système de

fichiers

Chaque module est construit dans son propre répertoire de build, stocké dans un sous-répertoire appelé build/$modulename-$count dans le répertoire d'état (qui est généralement .flatpak-builder/). De plus, il y a un lien symbolique build/$modulename vers la dernière version. Afin de générer des builds reproductibles, ce répertoire est également monté comme /run/build/$modulename dans le bac à sable (ou /run/build-runtime/$modulename lors de la construction des runtimes) et aussi comme /run/active-build depuis 1.4.7. C'est utilisé comme répertoire de travail courant pour toutes les opérations de

build.

Le répertoire de destination pour l'installation est accessible en écriture à l'endroit où il sera vu à l'exécution. Dans le cas d'une application régulière, ce sera /app. S'il s'agit de la construction d'un runtime, ce sera plutôt /usr, et lors de la construction d'une extension, ce sera dans le répertoire extensionpoint quelque part sous /app (pour une extension d'app) ou /usr (pour des extensions de runtime)

.

De plus, il y aura (selon les besoins, selon ce qui est construit) des mont

ages en lecture seule du sdk à /usr, des extensions sdk sous celui-ci, et l
'application à /app. Aucun autre accès au système de fichiers n'est disponible.

Permission

s

Les builds ont les permissions --allow=devel et --allow=multiarch que les exécutions fla

tpak régulières n'ont pas par défaut. Cela limite le filtrage des appels système normal
ement effectué afin que les outils de développement comme les débogueurs fonctionnent.
Sinon, le bac à sable de build est très limité, par exemple il n'y a pas d'accès réseau.
