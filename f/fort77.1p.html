FORT77(1P) Manuel du programmeur POSIX FORT77(1P)

PROLOGUE

Cette page de manuel fait partie du Manuel du programmeur POSIX. L'implémentation Linux de cette interface peut différer (consultez la page de manuel Linux correspondante pour les détails du comportement sous Linux), ou l'interface peut ne pas être implémentée sous Linux.

NOM

fort77 — Compilateur FORTRAN (FORTRAN)

SYNTAXE

fort77 [-c] [-g] [-L répertoire]... [-O niveau_opt] [-o fichier_sortie] [-s]
    [-w] opérande...

DESCRIPTION

L'utilitaire fort77 est l'interface du système de compilation FORTRAN ; il doit accepter le langage FORTRAN-77 complet défini par la norme ANSI X3.9‐1978. Le système se compose conceptuellement d'un compilateur et d'un éditeur de liens. Les fichiers référencés par les opérandes sont compilés et liés pour produire un fichier exécutable. Il est indéterminé si la liaison se produit entièrement dans le cadre de l'opération de fort77 ; certaines implémentations peuvent produire des objets qui ne sont entièrement résolus que lors de l'exécution du fichier.

Si l'option -c est présente, pour tous les opérandes de type chemin d'accès de la forme fichier.f, les fichiers :

$(basename chemin_accès.f).o

doivent être créés ou écrasés à la suite d'une compilation réussie. Si l'option -c n'est pas spécifiée, il est indéterminé si de tels fichiers .o sont créés ou supprimés pour les opérandes fichier.f.

S'il n'y a pas d'options qui empêchent l'édition de liens (telles que -c) et si tous les opérandes compilent et se lient sans erreur, le fichier exécutable résultant doit être écrit dans le fichier nommé par l'option -o (si présente) ou dans le fichier a.out. Le fichier exécutable doit être créé comme spécifié dans le volume « System Interfaces » de POSIX.1‐2017, à l'exception du fait que les permissions du fichier doivent être définies sur : S_IRWXO | S_IRWXG | S_IRWXU

et que les bits spécifiés par le umask du processus doivent être effacés.

OPTIONS

L'utilitaire fort77 doit être conforme aux directives de syntaxe des utilitaires du volume « Base Definitions » de POSIX.1‐2017, Section 12.2, à l'exception du fait que :

*
Les opérandes -l bibliothèque ont le format d'options, mais leur position dans une liste d'opérandes affecte l'ordre de recherche des bibliothèques.
*
L'ordre de spécification des multiples options -L est significatif.
*
Les applications conformes doivent spécifier chaque option séparément ; c'est-à-dire que le regroupement des lettres d'option (par exemple, -cg) n'est pas nécessairement reconnu par toutes les implémentations.

Les options suivantes doivent être prises en charge :

-c
Supprime la phase d'édition de liens de la compilation et ne supprime aucun fichier objet produit.
-g
Produit des informations symboliques dans les fichiers objets ou exécutables ; la nature de ces informations est indéterminée et peut être modifiée par des interactions définies par l'implémentation avec d'autres options.
-s
Produit des fichiers objets ou exécutables, ou les deux, à partir desquels les informations symboliques et autres non requises pour une exécution correcte utilisant la famille de fonctions exec définie dans le volume « System Interfaces » de POSIX.1‐2017 ont été supprimées (strippées). Si les options -g et -s sont toutes deux présentes, l'action effectuée est indéterminée.
-o fichier_sortie
Utilise le chemin d'accès fichier_sortie, au lieu du a.out par défaut, pour le fichier exécutable produit. Si l'option -o est présente avec -c, le résultat est indéterminé.
-L répertoire
Modifie l'algorithme de recherche des bibliothèques nommées dans les opérandes -l pour rechercher dans le répertoire nommé par le chemin d'accès répertoire avant de rechercher aux endroits habituels. Les répertoires nommés dans les options -L doivent être recherchés dans l'ordre spécifié. Au moins dix instances de cette option doivent être prises en charge dans une seule invocation de commande fort77. Si un répertoire spécifié par une option -L contient un fichier nommé libf.a, les résultats sont indéterminés.
-O niveau_opt
Spécifie le niveau d'optimisation du code. Si l'argument d'option niveau_opt est le chiffre '0', toutes les optimisations spéciales du code doivent être désactivées. S'il s'agit du chiffre '1', la nature de l'optimisation est indéterminée. Si l'option -O est omise, la nature de l'optimisation par défaut du système est indéterminée. Il est indéterminé si le code généré en présence de l'option -O 0 est identique à celui généré lorsque -O est omis. D'autres valeurs de niveau_opt peuvent être prises en charge.
-w
Supprime les avertissements.

Plusieurs instances des options -L peuvent être spécifiées.

OPÉRANDES

Un opérande est soit sous la forme d'un chemin d'accès, soit sous la forme -l bibliothèque. Au moins un opérande de type chemin d'accès doit être spécifié. Les opérandes suivants doivent être pris en charge :

fichier.f
Le chemin d'accès d'un fichier source FORTRAN à compiler et éventuellement à passer à l'éditeur de liens. L'opérande nom de fichier doit être de cette forme si l'option -c est utilisée.
fichier.a
Une bibliothèque de fichiers objets généralement produite par ar, et passée directement à l'éditeur de liens. Les implémentations peuvent reconnaître des suffixes indéterminés autres que .a comme désignant des bibliothèques de fichiers objets.
fichier.o
Un fichier objet produit par fort77 -c et passé directement à l'éditeur de liens. Les implémentations peuvent reconnaître des suffixes indéterminés autres que .o comme désignant des fichiers objets.

Le traitement des autres fichiers est indéterminé.

-l bibliothèque
(La lettre ell.) Recherche la bibliothèque nommée :
libbibliothèque.a

Une bibliothèque est recherchée lorsque son nom est rencontré, donc le placement d'un opérande -l est significatif. Plusieurs bibliothèques standard peuvent être spécifiées de cette manière, comme décrit dans la section DESCRIPTION ÉTENDUE. Les implémentations peuvent reconnaître des suffixes indéterminés autres que .a comme désignant des bibliothèques.

ENTRÉE STANDARD

Non utilisée.

FICHIERS D'ENTRÉE

Le fichier d'entrée doit être l'un des suivants : un fichier texte contenant du code source FORTRAN ; un fichier objet dans le format produit par fort77 -c ; ou une bibliothèque de fichiers objets, dans le format produit en archivant zéro ou plusieurs fichiers objets, à l'aide de ar. Les implémentations peuvent fournir des utilitaires supplémentaires qui produisent des fichiers dans ces formats. Les fichiers d'entrée supplémentaires sont indéterminés.

Une tabulation (<tab>) rencontrée dans les six premiers caractères d'une ligne de code source provoquera l'interprétation du caractère suivant par le compilateur comme s'il s'agissait du septième caractère de la ligne (c'est-à-dire dans la colonne 7).

ERREURS

Lorsque fort77 rencontre une erreur de compilation, il doit écrire un diagnostic sur l'erreur standard et continuer à compiler les autres opérandes de code source. JUSTIFICATIO

N

Le nom de cette utilitaire a été choisi comme fort77 pour faire écho au renommage du compilateur C. Le nom f77 n'a pas été choisi pour éviter des problèmes avec les implémentations historiques. Le standard ANSI X3.9‐1978 a été sélectionné comme référence normative parce que la version ISO/IEC de FORTRAN-77 a été supplantée par le standard ISO/IEC 1539:

1991.

Les mécanismes d'inclusion de fichier et de définition de symbole #define utilisés par l'utilitaire c99 n'ont pas été inclus dans ce volume de POSIX.1‐2017—même s'ils sont couramment implémentés—car il n'y a pas d'exigence que le compilateur FORTRAN utilise le préprocesseur

C.

L'option -onetrip n'a pas été incluse dans ce volume de POSIX.1‐2017, même si de nombreux compilateurs historiques la prennent en charge, parce qu'elle est dérivée de FORTRAN-66 ; c'est un anachronisme qui ne devrait pas être

perpétué.

Certaines implémentations produisent des listages de compilation. Cet aspect de FORTRAN a été laissé non spécifié parce qu'il y avait de la controverse concernant les différentes méthodes proposées pour l'implémenter : une option -V se chevauchait avec la pratique historique des fournisseurs et une convention de nommage consistant à créer des fichiers avec des suffixes .l entrait en conflit avec la pratique historique de nommage des fichiers lex

.

Il n'y a pas d'option -I dans cette version de ce volume de POSIX.1‐2017 pour spécifier un répertoire pour l'inclusion de fichiers. Une directive INCLUDE a fait partie des discussions sur Fortran-90, mais une interface prenant en charge ce standard n'est pas dans la portée

actuelle.

Il est noté que de nombreux compilateurs FORTRAN produisent un module objet même lorsque des erreurs de compilation se produisent ; lors d'une compilation ultérieure, le compilateur peut corriger le module objet plutôt que de recompiler tout le code. Par conséquent, il appartient à l'implémenteur de décider si un fichier objet est créé ou

non.

Une référence à MIL-STD-1753 a été retirée d'une proposition précoce en réponse à une demande des développeurs du standard POSIX de liaison FORTRAN. Ce n'était pas l'intention des développeurs du standard d'exiger une certification du compilateur FORTRAN, et IEEE Std 1003.9‐1992 ne spécifie pas le standard militaire ni aucune exigence particulière de prétraitement. De plus, l'utilisation de ce document aurait été inappropriée pour un standard

international.

La spécification de l'optimisation a été sujette à des changements à travers les propositions précoces. À un moment, -O et -N étaient booléens : optimiser et ne pas optimiser (avec une valeur par défaut non spécifiée). Certaines pratiques historiques ont conduit à ce que cela soit changé en

Il n'est pas toujours clair si « une bonne génération de code » est la même chose que l'optimisation. Les optimisations simples d'actions locales n'affectent généralement pas la sémantique d'un programme. L'option -O 0 a été incluse pour prendre en compte la nature très particulière des calculs scientifiques dans un environnement hautement optimisé ; les compilateurs font des erreurs. Un certain degré d'optimisation est attendu, même s'il n'est pas documenté ici, et la capacité de l'éteindre complètement pourrait être importante lors du portage d'une application. Une implémentation peut traiter -O 0 comme « faire moins que d'habitude » si elle le souhaite, mais cela n'a de sens que si l'une des opérations qu'elle effectue peut affecter la sémantique d'un programme. Il dépend fortement de l'implémentation de savoir si faire moins que d'habitude est logique. Ce n'est pas l'intention de l'option -O 0 de demander une génération de code inefficace, mais plutôt de s'assurer que toute optimisation sémantiquement visible est

supprimée.

La spécification de l'accès à la bibliothèque standard est cohérente avec la spécification du compilateur C. Les implémentations ne sont pas tenues d'avoir /usr/lib/libf.a, comme le font de nombreuses implémentations historiques, mais si ce n'est pas le cas, elles doivent reconnaître f comme un

jeton.

Les limites de taille des symboles externes figurent dans le texte normatif ; les applications conformes doivent connaître ces limites. Cependant, la longueur maximale de symbole minimale doit être considérée comme une contrainte sur une application conforme, et non sur une implémentation, et par conséquent l'action prise pour un symbole dépassant la limite n'est pas spécifiée. La taille minimale de la table des symboles externes a été ajoutée pour des raisons

similaires.

La section CONSÉQUENCES DES ERREURS spécifie clairement le comportement du compilateur lorsque des erreurs de compilation ou d'édition de liens se produisent. Le comportement de plusieurs implémentations historiques a été examiné, et le choix a été fait de se taire sur le statut du fichier exécutable, ou a.out, face aux erreurs du compilateur ou de l'éditeur de liens. Si un éditeur de liens écrit le fichier exécutable, puis le lie sur disque avec des lseek() et des write(), le fichier exécutable partiellement lié peut être laissé sur disque et ses bits d'exécution désactivés si l'édition de liens échoue. Cependant, si l'éditeur de liens lie l'image en mémoire avant d'écrire le fichier sur disque, il n'a pas besoin de toucher au fichier exécutable (s'il existe déjà) parce que l'édition de liens échoue. Puisque les deux approches sont une pratique historique, une application conforme doit se fier au code de sortie de fort77, plutôt qu'à l'existence ou au mode du fichier

exécutable.

Les options -g et -s ne sont pas spécifiées comme mutuellement exclusives. Historiquement, ces deux options étaient mutuellement exclusives, mais comme les deux sont si vaguement spécifiées, il a semblé approprié de laisser leur interaction non

spécifiée.

L'exigence selon laquelle les applications conformes spécifient les options du compilateur séparément vise à réserver l'espace de noms des options multi-caractères pour les options de compilateur spécifiques au fournisseur, dont on sait qu'elles existent dans de nombreuses implémentations historiques. Les implémentations ne sont pas tenues de reconnaître, par exemple, -gc comme si c'était -g -c ; elles ne sont pas non plus interdites de le faire. La SYNOPSIS montre toutes les options séparément pour mettre en évidence cette exigence sur les

applications.

L'affichage des noms de fichiers sur l'erreur standard est considéré comme un message de diagnostic car il serait sinon difficile d'associer un message d'erreur au fichier fautif. Ils sont décrits avec « peut » pour permettre aux implémentations d'utiliser d'autres méthodes d'identification des fichiers et pour aligner la description sur celle de c9

9
.
