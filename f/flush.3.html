Description

détaillée

Une interface i/o

abstraite.

Avertisseme

nt
Ceci est du matériel avancé et pointu. Vous n'en avez pas besoin sauf si vous savez vraiment ce que vous faites. La plupart des applications n'auront pas besoin de
cela.

Historiquement, PhysicsFS fournissait un accès au système de fichiers physique et aux archives au sein de ce système de fichiers. Cependant, parfois vous avez besoin de plus de puissance que cela. Peut-être avez-vous besoin de fournir une archive qui est entièrement contenue en RAM, ou vous avez besoin de faire le pont avec une autre API de i/o de fichier vers PhysicsFS, ou vous avez besoin de traduire les bits (peut-être avez-vous un fichier .zip standard qui est chiffré, et vous avez besoin de déchiffrer à la volée pour l'archivier zip insoupçonné)

.

Un PHYSFS_Io est l'interface que les Archivers utilisent pour obtenir les données d'archive. Historiquement, cela correspondait au i/o de fichier vers le système de fichiers physique, mais à partir de PhysicsFS 2.1, les applications peuvent fournir leurs propres implémentations de i/o à

l'exécution.

Cette interface n'est pas nécessairement un bon ajustement universel pour le i/o. Il y a quelques exigences à noter

:
  • Elles ne font que du i/o bloquant (au moins, pour l'instant)
    • .
  • Elles doivent pouvoir se dupliquer. Si vous avez un descripteur de fichier de fopen(), vous devez pouvoir créer un clone unique de celui-ci (afin que nous ayons deux descripteurs vers le même fichier qui peuvent tous deux chercher/lire/etc sans se marcher les uns sur les autres)
    • .
  • Elles doivent connaître la taille de leur ensemble de données
    • complet.
  • Elles doivent pouvoir
    • chercher et revenir en
arrière à la demande.

...en bref, vous n'allez probablement pas écrire une implémentation

HTTP.

Sécurité des threads : Les implémentations de PHYSFS_Io ne sont pas garanties être sûres en elles-mêmes pour les threads. Sous le capot, là où PhysicsFS les utilise, la bibliothèque fournit ses propres verrous. Si vous prévoyez de les utiliser directement depuis des threads séparés, vous devriez soit utiliser des mutex pour les protéger, soit ne pas utiliser le même PHYSFS_Io depuis deux threads en même

temps.

void(* PHYSFS_Io::destroy) (struct PHYSFS_Io

*io)

Nettoyer et désallouer l'instance i/o. Libérer les ressources associées, y compris (opaque) si

applicable.

Cette fonction doit toujours réussir : en tant que telle, elle retourne void. Le système peut appeler votre méthode flush() avant celle-ci. Vous pouvez signaler une échec là-bas si nécessaire. Cette méthode peut toujours être appelée si flush() échoue, auquel cas vous devrez abandonner les données non vidées et les autres conditions d'échec et

nettoyer.

Une fois que cette méthode est appelée pour une instance donnée, le système supposera qu'il n'est pas sûr de toucher à cette instance à nouveau et rejettera toute référence à

celle-ci.

*io)

Dupliquer cette instance i/o. Cela doit résulter en une copie complète de ce PHYSFS_Io, qui peut vivre complètement indépendamment. La copie doit être capable d'effectuer toutes ses opérations sans altérer l' original, y compris la destruction séparée de chaque objet (donc, par exemple : ils ne peuvent pas partager un descripteur de fichier ; chacun a besoin du sien)
