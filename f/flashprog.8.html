Programmeur internal

Activation des cartes mères

Certaines cartes mères nécessitent l'exécution d'un code spécifique à la carte mère pour activer la prise en charge de l'effacement et de l'écriture de la mémoire flash (et la prise en charge de la sonde sur les anciens systèmes avec mémoire flash parallèle). La marque et le modèle de la carte mère (si un code spécifique est requis) sont généralement détectés automatiquement à l'aide de l'un des mécanismes suivants : Si votre système exécute coreboot, le type de carte mère est déterminé à partir de la table coreboot. Sinon, la carte mère est détectée en examinant les périphériques PCI embarqués et éventuellement les informations DMI. Si PCI et DMI ne contiennent pas d'informations pour identifier de manière unique la carte mère (ce qui est exceptionnel), ou si vous souhaitez remplacer le modèle de carte mère détecté, vous pouvez spécifier la carte mère en utilisant la syntaxe

flashprog -p internal:mainboard=<vendor>:<board>.

Voir la section 'Known boards' ou 'Known laptops' dans la sortie de 'flashprog -L' pour une liste des cartes qui nécessitent la spécification du nom de la carte, si aucune table coreboot n'est trouvée.

Certaines de ces fonctions d'activation de mémoire flash spécifiques à la carte mère (appelées activations de carte mère) dans flashprog n'ont pas encore été testées. Si votre carte mère est détectée comme nécessitant une fonction d'activation de carte mère non testée, un message d'avertissement est affiché et la fonction d'activation de carte mère n'est pas exécutée, car une fonction d'activation de carte mère incorrecte pourrait entraîner un comportement erratique du système, les fonctions d'activation de carte mère touchant les internes de bas niveau d'une carte mère. Ne pas exécuter une fonction d'activation de carte mère (si elle est nécessaire) pourrait entraîner un échec de détection ou d'effacement. Si votre carte ne protège qu'une partie de la mémoire flash (souvent l'extrémité supérieure, appelée bloc de démarrage), flashprog pourrait rencontrer une erreur seulement après avoir effacé la partie non protégée, donc exécuter sans la fonction d'activation de carte mère pourrait être dangereux pour l'effacement et l'écriture (qui inclut l'effacement).

La procédure suggérée pour une carte mère avec un code spécifique non testé est d'essayer d'abord de sonder la ROM (il suffit d'appeler flashprog et de vérifier qu'il détecte votre type de puce flash) sans exécuter le code d'activation de carte mère (c'est-à-dire sans aucun paramètre). S'il trouve votre puce, tant mieux. Sinon, réessayez de sonder votre puce avec le code d'activation de carte mère en cours d'exécution, en utilisant

flashprog -p internal:boardenable=force

Si votre puce n'est toujours pas détectée, le code d'activation de carte mère semble défectueux ou la puce flash non prise en charge. Sinon, faites une sauvegarde du contenu actuel de votre ROM (en utilisant -r) et stockez-la sur un support externe à votre ordinateur, comme une clé USB ou un partage réseau. Si vous avez déjà dû exécuter le code d'activation de carte mère pour la sonde, utilisez-le également pour la lecture. Si la lecture réussit et que le contenu du fichier lu semble légitime, vous pouvez essayer d'écrire la nouvelle image. Vous devriez activer le code d'activation de carte mère dans tous les cas maintenant, car il est connu que l'écriture/effacement sans l'activation de carte mère échouera. Dans tous les cas (succès ou échec), veuillez faire un rapport à la liste de diffusion flashprog, voir ci-dessous.

Coreboot

Sur les systèmes exécutant coreboot, flashprog vérifie si l'image souhaitée correspond à votre carte mère. Cela nécessite une identifiant de carte spécial dans l'image. Si flashprog détecte que l'image que vous souhaitez écrire et la carte actuelle ne correspondent pas, il refusera d'écrire l'image à moins que vous ne spécifiiez

flashprog -p internal:coreboot=yes

Ceci désactive le contrôle de correspondance de la carte mère.

p class="Pp"> flashprog -p internal:boardmismatch=force

Super I/O ITE IT87

Si votre carte mère est fabriquée par GIGABYTE et prend en charge DualBIOS, il est très probable qu'elle utilise un Super I/O de la série ITE IT87 pour basculer entre les deux puces flash. Une seule d'entre elles peut être accessible à la fois et vous pouvez sélectionner manuellement celle à utiliser avec la

flashprog -p internal:dualbiosindex=chip

syntaxe où chip est l'index de la puce à utiliser (0 = principale, 1 = de secours). Vous pouvez vérifier laquelle est actuellement sélectionnée en omettant le chip paramètre.

Si votre carte mère utilise un Super I/O de la série ITE IT87 pour la traduction du bus flash LPC<->SPI, flashprog devrait détecter automatiquement cette configuration. Si vous souhaitez définir manuellement le port de base E/S du contrôleur SPI de la série IT87 au lieu d'utiliser la valeur fournie par le BIOS, utilisez la

flashprog -p internal:it87spiport=portnum

syntaxe où portnum est le numéro de port E/S (doit être un multiple de 8). Dans le cas peu probable où flashprog ne détecte pas un pont IT87 LPC<->SPI actif, veuillez envoyer un rapport de bogue afin que nous puissions diagnostiquer le problème.

Chipsets AMD

À partir du chipset SB700, il existe un microcontrôleur intégré (IMC) basé sur le 8051 embarqué dans chaque southbridge AMD. Son firmware réside dans la même puce flash que celui de l'hôte, ce qui rend l'écriture dans la flash risquée si l'IMC est actif. flashprog essaie de désactiver temporairement l'IMC, mais même dans ce cas, modifier le contenu de la flash peut avoir des effets indésirables : lorsque l'IMC reprend (au plus tard après un redémarrage), il continuera à exécuter le code à partir de la flash. Si le code a été supprimé ou modifié de manière inopportune, il est imprévisible ce que l'IMC fera. Par conséquent, si flashprog détecte un IMC actif, il désactivera la prise en charge de l'écriture à moins que l'utilisateur ne le force avec la

flashprog -p internal:amd_imc_force=yes

syntaxe. L'utilisateur est responsable de fournir une image appropriée ou d'omettre la région IMC à l'aide d'un fichier de disposition. Cette limitation pourrait être supprimée à l'avenir lorsque nous aurons mieux compris les détails et reçu suffisamment de retours des utilisateurs. Veuillez signaler le résultat si vous avez dû utiliser cette option pour écrire sur une puce.

Un paramètre spispeed optionnel spécifie la fréquence du bus SPI lorsque cela s'applique (c'est-à-dire SB600 ou ultérieur avec une puce flash SPI directement attachée au chipset). La syntaxe est

flashprog -p internal:spispeed=frequency

où frequency peut être '16.5 MHz', '22 MHz', '33 MHz', '66 MHz', '100 MHZ', ou '800 kHz'. La prise en charge des fréquences individuelles dépend de la génération du chipset :

* SB6xx, SB7xx, SP5xxx : de 16.5 MHz jusqu'à et y compris 33 MHz

* SB8xx, SB9xx, Hudson : de 16.5 MHz jusqu'à et y compris 66 MHz

* Yangtze (avec le moteur SPI 100 trouvé dans Kabini et Tamesh) : toutes

La valeur par défaut est d'utiliser 16.5 MHz et de désactiver les lectures rapides (Fast Reads).

Chipsets Intel

Si vous avez un chipset Intel avec un southbridge ICH8 ou ultérieur avec une flash SPI attachée, et si un descripteur valide a été écrit dessus (par exemple par le fabricant), le chipset fournit un moyen alternatif d'accéder à la ou aux puces flash nommé Hardware Sequencing. Il est beaucoup plus simple que la méthode d'accès normale (appelée Software Sequencing), mais ne permet pas au logiciel de choisir les commandes SPI à envoyer. Vous pouvez utiliser la

flashprog -p internal:ich_spi_mode=value

syntaxe où value peut être auto, swseq ou hwseq. Par défaut (ou lorsque l'on définit ich_spi_mode=auto) le module essaie d'utiliser swseq et n'active hwseq que si nécessaire (par exemple si des opcodes importants sont inaccessibles en raison du verrouillage ; ou si plus d'une puce flash est attachée). Les autres options (swseq, hwseq) sélectionnent le mode respectif (si possible).

Les southbridges ICH8 et ultérieurs peuvent également avoir des plages d'adresses verrouillées de différents types si un descripteur valide a été écrit dessus. L'espace d'adressage de la flash est alors partitionné en plusieurs soi-disant "Flash Regions" contenant respectivement le firmware de l'hôte, le firmware ME, etc. Le descripteur flash peut également spécifier jusqu'à 5 soi-disant "Protected Regions", qui sont des plages d'adresses librement choisies indépendantes des "Flash Regions" susmentionnées. Toutes peuvent être protégées en écriture et/ou en lecture individuellement.

Si vous avez un chipset Intel avec un southbridge ICH2 ou ultérieur et si vous souhaitez définir des valeurs IDSEL spécifiques pour une puce flash non par défaut ou un contrôleur embarqué (EC), vous pouvez utiliser la

flashprog -p internal:fwh_idsel=value

syntaxe où value est la valeur brute hexadécimale sur 48 bits à écrire dans les registres IDSEL du southbridge Intel. Les 32 bits supérieurs utilisent un chiffre hexadécimal chacun par plage de 512 kB entre 0xffc00000 et 0xffffffff, et les 16 bits inférieurs utilisent un chiffre hexadécimal chacun par plage de 1024 kB entre 0xff400000 et 0xff7fffff. Le chiffre hexadécimal le plus à droite correspond à la plage d'adresses la plus basse. Toutes les plages d'adresses ont une plage correspondante à 4 MB en dessous avec des paramètres IDSEL identiques. La valeur par défaut pour ICH7 est donnée dans l'exemple ci-dessous.

Exemple : flashprog -p internal:fwh_idsel=0x001122334567

Ordinateurs portables

Utiliser flashprog sur d'anciens ordinateurs portables qui ne démarrent pas depuis le bus SPI est dangereux et peut facilement rendre votre matériel inutilisable (voir aussi la section BUGS ). Le contrôleur embarqué (EC) dans certaines machines peut mal interagir avec le flashage. Plus d'informations sont dans le wiki ⟨https://flashprog.org/Laptops⟩. Des problèmes surviennent lorsque la puce flash est partagée entre le BIOS et le firmware EC, et que ce dernier ne s'attend pas à ce que flashprog accède à la puce. Pendant que flashprog essaie de changer le contenu de cette mémoire, l'EC pourrait avoir besoin de récupérer de nouvelles instructions ou données et pourrait cesser de fonctionner correctement. La détection et la lecture de la puce peuvent aussi irriter votre EC et causer une défaillance du ventilateur, une défaillance du rétroéclairage, une coupure soudaine de l'alimentation et d'autres effets désagréables. flashprog essaiera de détecter s'il s'exécute sur un tel ordinateur portable et limitera la détection aux bus SPI. Si vous voulez quand même détecter le bus LPC à vos propres risques, utilisez

flashprog -p internal:laptop=force_I_want_a_brick

Nous ne vous aiderons pas si vous forcez le flashage sur un ordinateur portable car c'est vraiment une idée stupide.

Le programmeur dummy n'opère que sur un tampon en mémoire. Il fournit un moyen sûr et rapide de tester divers aspects de flashprog et est principalement utilisé lors du développement et du débogage. Programmeur serprog

Ce module prend en charge tous les programmeurs utilisant le protocole serprog. Cela inclut certains appareils basés sur Arduino ainsi que divers programmeurs de Urja Rannikko, Juhana Helovuo, Stefan Tauner, Chi Zhang et de nombreux autres.

Un paramètre obligatoire spécifie soit un périphérique série (et son débit), soit une combinaison IP/port pour communiquer avec le programmeur. La combinaison périphérique/débit doit commencer par dev= et séparer le débit optionnel par un deux-points. Par exemple :

flashprog -p serprog:dev=/dev/ttyS0:115200

Si aucun débit n'est donné, les valeurs par défaut du système d'exploitation/matériel seront utilisées. Pour les connexions IP, vous devez utiliser la syntaxe

flashprog -p serprog:ip=adresse_ip:port

En cas de prise en charge par le périphérique, vous pouvez définir la fréquence d'horloge SPI avec le paramètre optionnel spispeed. La fréquence est interprétée en Hertz, sauf si un suffixe M ou k est donné, indiquant respectivement les mégaHertz ou les kiloHertz. Exemple pour définir la fréquence à 2 MHz :

flashprog -p serprog:dev=/dev/ttyACM0,spispeed=2M

En cas de prise en charge par le périphérique, vous pouvez définir quelle puce de sélection SPI (Chip Select) utiliser avec le paramètre optionnel cs. Exemple indiquant au programmeur d'utiliser la puce de sélection numéro 0 :

flashprog -p serprog:dev=/dev/ttyACM0:cs=0

Plus d'informations sur serprog sont disponibles dans serprog-protocol.txt dans la distribution source.

flashprog -p buspirate_spi:dev=/dev/périphérique,spispeed=fréquence

Le canal de données d'affichage (DDC) est un bus I2C présent sur les connecteurs VGA et DVI, qui permet d'échanger des informations entre un ordinateur et les écrans connectés. Ses utilisations les plus courantes consistent à obtenir les capacités d'affichage via EDID (à l'adresse I2C 0x50) et à envoyer des commandes à l'écran en utilisant le protocole DDC/CI (à l'adresse 0x37). Sur les écrans pilotés par les SoC MSTAR, il est également possible d'accéder à la mémoire flash du firmware du SoC (connectée au SoC via un autre bus SPI) en utilisant un port de programmation en système (ISP), généralement à l'adresse 0x49. Ce module flashprog permet cette dernière fonction via le pilote I2C de Linux.

IMPORTANT : Avant d'utiliser ce programmeur, l'écran DOIT être en mode veille et uniquement connecté à l'ordinateur qui exécutera flashprog en utilisant un câble VGA, à une sortie VGA inactive. Il ne doit absolument PAS être utilisé comme écran pendant la procédure !

Vous devez spécifier le contrôleur DDC/I2C et l'adresse I2C à utiliser avec la syntaxe

flashprog -p mstarddc_spi:dev=/dev/i2c-X:YY

où /dev/i2c-X est le nœud de périphérique Linux pour votre contrôleur I2C connecté au canal DDC de l'écran, et YY est l'adresse (hexadécimale) du port ISP MSTAR (l'adresse 0x49 est généralement utilisée). Exemple utilisant le contrôleur I2C /dev/i2c-1 et l'adresse 0x49 :

flashprog -p mstarddc_spi:dev=/dev/i2c-1:49

Il est également possible d'inhiber la commande de réinitialisation qui est normalement envoyée à l'écran une fois l'opération flashprog terminée, en utilisant le paramètre optionnel noreset. Une valeur de 1 empêche flashprog d'envoyer la commande de réinitialisation. Exemple ne réinitialisant pas l'écran à la fin de l'opération :

flashprog -p mstarddc_spi:dev=/dev/i2c-1:49,noreset=1

Veuillez noter que l'envoi de la commande de réinitialisation est également inhibé si une erreur s'est produite pendant l'opération. Pour envoyer la commande de réinitialisation ultérieurement, vous pouvez simplement exécuter flashprog une fois de plus, en mode de sondage de puce (sans spécifier d'opération), sans le paramètre noreset, une fois que l'opération de lecture/écriture de puce que vous aviez l'intention d'effectuer s'est terminée avec succès.

Veuillez également noter que le pilote mstarddc_spi ne fonctionne que sur Linux.

Programmeur ch341a_spi

Le programmeur WCH CH341A ne prend actuellement en charge aucun paramètre. La fréquence SPI est fixe à 2 MHz et CS0 est utilisé conformément au dispositif.

Programmeur ch347_spi

Le pilote est actuellement codé en dur pour utiliser CS0. Un paramètre optionnel spispeed spécifie la fréquence du bus SPI. La syntaxe est

flashprog -p ch347_spi:spispeed=fréquence

où fréquence est donnée en kHz et peut être dans la plage 468 .. 60000. La fréquence sera arrondie à la valeur inférieure supportée (60 MHz divisé par une puissance de 2). La valeur par défaut est une fréquence de 7,5 MHz. Le mode SPI peut également être défini à l'aide du paramètre spimode :

flashprog -p ch347_spi:spimode=mode

où mode est dans la plage 0 à 3. Le mode par défaut est le mode 0.

Programmeur ni845x_spi

Un paramètre optionnel voltage pourrait être utilisé pour spécifier la tension d'E/S. Ce paramètre est disponible pour l'appareil NI USB-8452. L'unité par défaut est Volt si aucune unité n'est spécifiée. Vous pouvez utiliser mV, milliVolt, V ou Volt comme spécificateur d'unité. La syntaxe est

flashprog -p ni845x_spi:voltage=valeur

où valeur peut être 1.2V, 1.5V, 1.8V, 2.5V, 3.3V ou l'équivalent en mV.

Dans le cas où aucune des tensions d'E/S prises en charge par le programmeur n'est dans la plage de tension supportée par la puce flash détectée, flashprog interrompra l'opération (pour éviter d'endommager la puce flash). Vous pouvez outrepasser ce comportement en passant "yes" au paramètre ignore_io_voltage_limits (par exemple, si vous utilisez un circuit traducteur de tension externe). La syntaxe est

flashprog -p ni845x_spi:ignore_io_voltage_limits=yes

Vous pouvez utiliser le paramètre serial pour spécifier explicitement quel appareil NI USB-845x connecté doit être utilisé. Vous devez utiliser le numéro de série hexadécimal à 7 chiffres de votre appareil. Exemple d'utilisation pour sélectionner l'appareil avec le numéro de série 1230A12 :

flashprog -p ni845x_spi:serial=1230A12

Un paramètre optionnel spispeed spécifie la fréquence du bus SPI. La syntaxe est

flashprog -p ni845x_spi:spispeed=fréquence

où fréquence doit être un nombre correspondant à la fréquence souhaitée en kHz. La fréquence maximale est de 12 MHz (12000 kHz) pour l'USB-8451 et de 50 MHz (50000 kHz) pour l'USB-8452. La valeur par défaut est une fréquence de 1 MHz (1000 kHz).

Un paramètre optionnel cs spécifie quelle ligne de sélection de puce cible doit être utilisée. La syntaxe est

flashprog -p ni845x_spi:csnumber=valeur

où valeur doit être comprise entre 0 et 7. Par défaut, CS0 est utilisé.

Programmeur digilent_spi

Un paramètre optionnel spispeed spécifie la fréquence du bus SPI. La syntaxe est

flashprog -p digilent_spi:spispeed=fréquence

où fréquence peut être 62.5k, 125k, 250k, 500k, 1M, 2M ou 4M (en Hz). La valeur par défaut est une fréquence de 4 MHz.

Programmeur dirtyjtag_spi

Un paramètre optionnel spispeed spécifie la fréquence du bus SPI. La syntaxe est

flashprog -p dirtyjtag_spi:spispeed=fréquence

où fréquence peut être toute valeur en hertz, kilohertz ou mégahertz prise en charge par le programmeur. La valeur par défaut est une fréquence de 100 kHz.

PROGRAMMER-SPECIFIC INFORMATION

jlink_spi programmer

This module supports SPI flash programming through the SEGGER J-Link programmer/debugger's SPI bridge interface.

The programmer can be selected with the

flashprog -p jlink_spi:cs=pin

syntax where pin can be either TRST or RESET. The default pin for chip select is RESET. Note that, when using RESET, it is normal that the indicator LED blinks orange or red.
Additionally, the VTref pin of the programmer must be attached to the logic level of the flash chip. The programmer measures the voltage on this pin and generates the reference voltage for its input comparators and adapts its output voltages to it.

Pinout for devices with 20-pin JTAG connector:


+-------+
| 1 2 | 1: VTref 2:
| 3 4 | 3: TRST 4: GND
| 5 6 | 5: TDI 6: GND
+-+ 7 8 | 7: 8: GND
| 9 10 | 9: TCK 10: GND
| 11 12 | 11: 12: GND
+-+ 13 14 | 13: TDO 14:
| 15 16 | 15: RESET 16:
| 17 18 | 17: 18:
| 19 20 | 19: PWR_5V 20:
+-------+

If there is more than one compatible device connected, you can select which one should be used by specifying its serial number with the

flashprog -p jlink_spi:serial=number

syntax where number is the serial number of the device (which can be found for example in the output of lsusb -v).

The SPI speed can be selected by using the

flashprog -p jlink_spi:spispeed=frequency

syntax where frequency is the SPI clock frequency in kHz. The maximum speed depends on the device in use.

The power=on option can be used to activate the 5 V power supply (PWR_5V) of the J-Link during a flash operation.

stlinkv3_spi programmer

This module supports SPI flash programming through the STMicroelectronics STLINK V3 programmer/debugger's SPI bridge interface

flashprog -p stlinkv3_spi

If there is more than one compatible device connected, you can select which one should be used by specifying its serial number with the

flashprog -p stlinkv3_spi:serial=number

syntax where number is the serial number of the device (which can be found for example in the output of lsusb -v).

The SPI speed can be selected by using the

flashprog -p stlinkv3_spi:spispeed=frequency

syntax where frequency is the SPI clock frequency in kHz. If the passed frequency is not supported by the adapter the nearest lower supported frequency will be used.

EXEMPLES

Pour sauvegarder et mettre à jour votre BIOS, exécutez

flashprog -p internal -r backup.rom -o backuplog.txt
flashprog -p internal -w newbios.rom -o writelog.txt

Assurez-vous de copier backup.rom sur un support externe avant d'essayer d'écrire. Cela facilite la récupération hors ligne.
Si l'écriture échoue et que flashprog se plaint que la puce est dans un état inconnu, vous pouvez essayer de restaurer la sauvegarde en exécutant

flashprog -p internal -w backup.rom -o restorelog.txt

Si vous rencontrez des problèmes, veuillez nous contacter et fournir backuplog.txt, writelog.txt et restorelog.txt. Voir la section BUGS pour les informations de contact.

EXIGENCES

flashprog nécessite différentes permissions d'accès pour différents programmeurs.

internal nécessite un accès mémoire brut, un accès à l'espace de configuration PCI, un accès aux ports d'E/S bruts (x86) et un accès MSR (x86).

atavia nécessite un accès à l'espace de configuration PCI.

nic3com, nicrealtek et nicnatsemi nécessitent un accès en lecture à l'espace de configuration PCI et un accès aux ports d'E/S bruts.

atahpt nécessite un accès à l'espace de configuration PCI et un accès aux ports d'E/S bruts.

gfxnvidia, drkaiser et it8212 nécessitent un accès à l'espace de configuration PCI et un accès mémoire brut.

rayer_spi nécessite un accès aux ports d'E/S bruts.

satasii, nicintel, nicintel_eeprom et nicintel_spi nécessitent un accès en lecture à l'espace de configuration PCI et un accès mémoire brut.

satamv et atapromise nécessitent un accès en lecture à l'espace de configuration PCI, un accès aux ports d'E/S bruts et un accès mémoire brut.

serprog nécessite un accès TCP au réseau ou un accès en espace utilisateur à un port série.

buspirate_spi nécessite un accès en espace utilisateur à un port série.

ft2232_spi, usbblaster_spi et pickit2_spi nécessitent un accès au périphérique USB respectif via l'API libusb version 0.1.

ch341a_spi et dediprog nécessitent un accès au périphérique USB respectif via l'API libusb version 1.0.

dummy ne nécessite aucune permission d'accès.

internal, nic3com, nicrealtek, nicnatsemi, gfxnvidia, drkaiser, satasii, satamv, atahpt, atavia et atapromise doivent être exécutés en tant que superutilisateur/root, et nécessitent une permission d'accès brut supplémentaire.

serprog, buspirate_spi, dediprog, usbblaster_spi, ft2232_spi, pickit2_spi, ch341a_spi, digilent_spi et dirtyjtag_spi peuvent être exécutés en tant qu'utilisateur normal sur la plupart des systèmes d'exploitation si les permissions appropriées du périphérique sont définies.

ogp nécessite un accès en lecture à l'espace de configuration PCI et un accès mémoire brut.

Sur OpenBSD, vous pouvez obtenir l'autorisation d'accès brut en définissant securelevel=-1 dans /etc/rc.securelevel et en redémarrant, ou en redémarrant en mode mono-utilisateur.

Utiliser flashprog sur de vieux ordinateurs portables est dangereux et peut facilement rendre votre matériel inutilisable. flashprog tentera de détecter s'il fonctionne sur un ordinateur portable susceptible et restreindra l'interrogation des puces flash pour des raisons de sécurité. Veuillez lire la discussion détaillée de ce sujet et les options flashprog associées dans le paragraphe Ordinateurs portables de la sous-section PROGRAMMEUR interne de la section INFORMATIONS SPÉCIFIQUES AU PROGRAMMEUR et les informations sur notre wiki ⟨https://flashprog.org/Laptops⟩.

Mémoire programmable une seule fois (OTP) et identifiants uniques

Certaines puces flash contiennent une mémoire OTP souvent désignée comme des "registres de sécurité". Elles ont généralement une capacité allant de quelques octets à quelques centaines d'octets et peuvent être utilisées pour donner des identifiants uniques aux appareils, etc. flashprog n'est pas capable de lire ou d'écrire dans ces mémoires et peut donc ne pas être en mesure de dupliquer complètement une puce. Pour les types de puces connus pour contenir des mémoires OTP, un avertissement est affiché lorsqu'ils sont détectés.

Similaires aux mémoires OTP sont les identifiants uniques, programmés en usine, infalsifiables. Ils ne sont pas modifiables par l'utilisateur du tout.

NAME

flashprog - utilitaire en ligne de commande pour lire, écrire et effacer les mémoires flash.

SYNTAXE

flashprog [-p programmer] [-d device] [-c chipname] [-s speed] [-w filename] [-r filename] [-e] [-f] [-v] [-h]

DESCRIPTION

L'utilitaire flashprog est conçu pour lire, écrire et effacer les mémoires flash utilisées couramment dans les systèmes embarqués et les périphériques informatiques. Il prend en charge une large gamme de programmateurs et de puces mémoire.

OPTIONS

-p programmer
Spécifie le programmateur matériel à utiliser. Les valeurs courantes incluent "serial", "parport", "usbblaster", etc.
-d device
Spécifie le périphérique de bas niveau à utiliser pour la communication avec le programmateur (par exemple, "/dev/ttyUSB0" pour un programmateur série USB).
-c chipname
Spécifie le nom de la puce mémoire flash à utiliser. Si non spécifié, flashprog tentera de détecter automatiquement la puce.
-s speed
Définit la vitesse de communication du programmateur.
-w filename
Écrit le contenu du fichier spécifié dans la mémoire flash.
-r filename
Lit le contenu de la mémoire flash et le sauvegarde dans le fichier spécifié.
-e
Efface la mémoire flash entière.
-f
Force l'opération même si des avertissements sont rencontrés.
-v
Mode verbeux. Affiche des informations détaillées sur le processus.
-h
Affiche le message d'aide et quitte.

INFORMATIONS SPÉCIFIQUES AU PROGRAMMATEUR

Certains programmateurs peuvent nécessiter des options supplémentaires ou des configurations spécifiques. Reportez-vous à la documentation de flashprog pour plus de détails sur les programmateurs pris en charge.

EXEMPLES

Pour écrire un fichier "firmware.bin" sur une puce avec un programmateur série sur /dev/ttyS0 :

flashprog -p serial -d /dev/ttyS0 -w firmware.bin

Pour lire le contenu de la flash et le sauvegarder dans "backup.bin" en utilisant un programmateur USB-Blaster :

flashprog -p usbblaster -r backup.bin

Pour effacer une mémoire flash avec détection automatique de puce :

flashprog -e

STATUT DE SORTIE

flashprog retourne 0 en cas de succès, et une valeur non nulle en cas d'erreur.
