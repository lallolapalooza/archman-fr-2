FLATPAK-BUILDER(1) flatpak builder FLATPAK-BUILDER(1)

NOM

flatpak-builder - Aide à la construction des dépendances des applications

SYNOPSIS

flatpak-builder [OPTION...] RÉPERTOIRE MANIFESTE

flatpak-builder --run [OPTION...] RÉPERTOIRE MANIFESTE COMMANDE

flatpak-builder --show-deps [OPTION...] MANIFESTE

flatpak-builder --show-manifest [OPTION...] MANIFESTE

DESCRIPTION

flatpak-builder est un enveloppeur autour de la commande flatpak build qui automatise la construction des applications et de leurs dépendances. C'est une option que vous pouvez utiliser pour construire des applications.

Le but de flatpak-builder est de transférer autant de connaissances sur la façon de construire les modules que possible vers les projets amont individuels. Il le fait en supposant que les modules adhèrent à l'API de Build spécifiée sur https://github.com/cgwalters/build-api. Cela signifie essentiellement qu'il suit le schéma ./configure && make && make install avec un script autogen optionnel. Si l'amont n'adhère pas à l'API, vous pouvez le faire en ajoutant des correctifs et des fichiers supplémentaires.

Une invocation de flatpak-builder se déroule en ces étapes, chacune étant spécifiée en détail au format json dans le MANIFESTE :

•Télécharger toutes les sources
•Initialiser le répertoire de l'application avec flatpak build-init
•Construire et installer chaque module avec flatpak build
•Nettoyer l'arborescence de construction finale en supprimant les fichiers indésirables et, par exemple, en dépouillant les binaires
•Finaliser le répertoire de l'application avec flatpak build-finish

Après cela, vous obtiendrez une construction de l'application dans le RÉPERTOIRE, que vous pouvez exporter vers un dépôt avec la commande flatpak build-export Si vous utilisez l'option --repo , flatpak-builder effectuera l'exportation pour vous à la fin du processus de construction. Lorsque flatpak-builder effectue l'exportation, il stocke également le manifeste utilisé pour la construction dans /app/manifest.json. Le manifeste est « résolu », c'est-à-dire que les noms de branches git sont remplacés par les identifiants de commit réels utilisés dans la construction.

À chacune des étapes ci-dessus, flatpak met en cache le résultat, et si vous construisez le même fichier à nouveau, il commencera à la première étape où quelque chose change. Par exemple, la première source sous contrôle de version à laquelle de nouveaux commits ont été ajoutés, ou le premier module où des changements dans le fichier MANIFESTE ont causé un changement de l'environnement de construction. Cela rend flatpak-builder très efficace pour les constructions incrémentales.

Lors de la construction d'un flatpak destiné à être publié sur Internet, --collection-id=COLLECTION-ID devrait être spécifié comme une valeur DNS inverse globalement unique pour identifier la collection de flatpaks à laquelle cela sera ajouté. Définir un identifiant de collection globalement unique permet aux applications du dépôt d'être partagées via des systèmes de pair à pair sans nécessiter de configuration supplémentaire.

MANIFESTE

Le fichier manifeste est un fichier json ou yaml dont le format est décrit en détail dans sa propre page de manuel.

OPTIONS

Les options suivantes sont reconnues :

-h, --help

Afficher les options d'aide et quitter.

-v, --verbose

Afficher les informations de débogage pendant le traitement de la commande.

--version

Afficher les informations de version et quitter.

--arch=ARCH

Spécifier l'architecture de la machine pour laquelle construire. Si aucune architecture n'est spécifiée, l'architecture de l'hôte sera automatiquement détectée. Seules les architectures compatibles avec l'hôte peuvent être spécifiées.

--default-branch=BRANCHE

Définir la branche par défaut sur BRANCHE. C'est utilisé si le manifeste ne spécifie pas de branche. La valeur par défaut est master.

--disable-cache

Ne pas regarder le cache existant pour une construction précédente, reconstruire les modules à la place.

--disable-rofiles-fuse

Désactiver l'utilisation de rofiles-fuse pour optimiser l'utilisation du cache via des extractions par liens physiques.

--disable-download

Ne télécharger aucune source. Cela ne fonctionne que si une certaine version de toutes les sources est déjà téléchargée. C'est utile si vous voulez garantir qu'aucune entrée/sortie réseau n'est effectuée. Cependant, la construction échouera si une source n'est pas disponible localement.

--disable-updates

Télécharger les sources manquantes, mais ne pas mettre à jour les miroirs locaux des dépôts de contrôle de version. C'est utile pour reconstruire des choses mais sans mettre à jour les dépôts git, bzr ou svn depuis le dépôt distant.

--disable-tests

Ne pas exécuter aucun des tests.

--run

Exécuter une commande dans un bac à sable basé sur le répertoire de construction. Cela démarre flatpak build, avec des arguments supplémentaires pour donner le même environnement que la construction, et les mêmes permissions que l'application finale aura (sauf les permissions du système de fichiers). La commande à exécuter doit être le dernier argument passé à flatpak-builder, après le répertoire et le manifeste.

Seules les options --arch=ARCH, --ccache et --verbose peuvent être combinées avec cette option.

--build-shell=MODULENAME

Extraire et préparer les sources pour le module nommé, et puis démarrer un shell dans un bac à sable identique à celui que flatpak-builder utiliserait pour construire le module. C'est utile pour déboguer un module.

--show-deps

Lister tous les fichiers (locaux) dont le manifeste dépend.

Seule l'option --verbose peut être combinée avec cette option.

--show-manifest

Charger le manifeste, y compris tous les fichiers inclus, et l'afficher au format json canonique. C'est utile pour les outils qui veulent gérer les fichiers manifeste afin d'éviter de devoir supporter à la fois yaml et json, ainsi que certaines manipulations json non standard qui sont supportées (par exemple les commentaires et les chaînes multilignes).

Seule l'option --verbose peut être combinée avec cette option.

--download-only

Quitter avec succès après avoir téléchargé les sources requises.

--bundle-sources

Créer un environnement d'exécution supplémentaire avec le code source pour ce module. Il sera nommé app-id.Sources, par exemple org.gnome.Maps.Sources.

--build-only

Ne pas effectuer les étapes de nettoyage et de finalisation, ce qui est utile si vous voulez construire plus de choses dans l'application.

--finish-only

Effectuer uniquement les étapes de nettoyage, de finalisation et d'exportation, en reprenant là où une commande --build-only s'est arrêtée.

--export-only

Effectuer uniquement les étapes d'exportation, en reprenant le résultat de la construction d'une construction précédente. Cela peut être utilisé pour diviser la construction et l'exportation/la signature en deux appels en omettant --repo dans le premier appel.

--require-changes

Ne rien faire, en laissant un RÉPERTOIRE inexistant si rien n'a changé depuis la dernière construction mise en cache. Si cela n'est pas spécifié, la dernière version du cache sera placée dans le RÉPERTOIRE.

--state-dir=CHEMIN

Utiliser ce répertoire pour stocker l'état (téléchargements, répertoires de construction, cache de construction, etc.) plutôt que .flatpak-builder. Cela peut être un chemin absolu ou relatif, mais doit être sur le même système de fichiers que le RÉPERTOIRE cible spécifié.

--keep-build-dirs

Ne pas supprimer les sources et la construction après avoir construit et installé chaque module. Cela crée également un lien symbolique vers le répertoire de construction avec un nom stable ("build-nomdumodule").

--delete-build-dirs

Toujours supprimer les sources et la construction après avoir construit chaque module, même si la construction a échoué. Par défaut, les répertoires de construction échoués sont conservés mais les réussis sont supprimés. C'est utile dans, par exemple, les systèmes de construction automatiques.

--ccache

Activer l'utilisation de ccache dans la construction (nécessite ccache dans le sdk). Le dossier ccache par défaut peut être remplacé en définissant la variable d'environnement CCACHE_DIR.

--stop-at=MODULENAME

S'arrêter au module spécifié, en l'ignorant ainsi que tous les modules suivants dans les phases « téléchargement » et « construction ». C'est utile pour le débogage et le développement. Par exemple, vous pouvez construire toutes les dépendances, mais vous arrêter à l'application principaleion afin que vous puissiez ensuite effectuer une compilation à partir d'une copie de travail préexistante. Implique --build-only.

--repo=DIR

Après la fin de la compilation, exécute flatpak build-export pour exporter le résultat vers le dépôt DIR. Si DIR existe, il doit s'agir d'un dépôt OSTree ; sinon, un nouveau dépôt sera créé.

-s, --subject=SUBJECT

Sujet d'une ligne pour le message de commit. Utilisé lors de l'export des résultats de la compilation.

-b, --body=BODY

Description complète pour le message de commit. Utilisé lors de l'export des résultats de la compilation.

--collection-id=COLLECTION-ID

Définit l'identifiant de collection du dépôt. La définition d'un identifiant de collection globalement unique permet le partage des applications du dépôt via des systèmes pair à pair sans nécessiter de configuration supplémentaire. Lors de la compilation dans un dépôt existant, l'identifiant de collection doit correspondre à l'identifiant de collection configuré pour ce dépôt.

--token-type=VAL

Définit le type de jeton requis pour installer ce commit. Définir cette valeur à une valeur supérieure à 0 implique qu'une authentification sera nécessaire pour installer le flatpak. Une token-type propriété définie dans le manifeste prend la priorité sur cette option. Utilisé lors de l'export des résultats de la compilation.

--gpg-sign=KEYID

Signe le commit avec cette clé GPG. Utilisé lors de l'export des résultats de la compilation. Cette option peut être utilisée plusieurs fois.

--gpg-homedir=PATH

Répertoire personnel GPG à utiliser lors de la recherche des trousseaux de clés. Utilisé lors de l'export des résultats de la compilation.

--jobs=JOBS

Limite le nombre de tâches parallèles pendant la compilation. La valeur par défaut est le nombre de CPU de la machine.

--force-clean

Efface le contenu précédent de DIRECTORY s'il n'est pas vide. Depuis la version 1.4.6, la suppression sera refusée si DIRECTORY est le répertoire de travail courant, le répertoire d'état, ou l'un de leurs répertoires parents.

--sandbox

Désactive la possibilité de spécifier des build-args qui sont transmis à flatpak build. Cela signifie que le processus de compilation ne peut pas s'échapper de son bac à sable, et est utile lors de la compilation de logiciels moins fiables.

--allow-missing-runtimes

Ne pas échouer immédiatement si les environnements d'exécution sdk ou platform ne sont pas installés sur ce système. La tentative de compilation de n'importe quel module du manifeste échouera toujours si le sdk est manquant, mais peut être utile pour les applications qui installent des fichiers sans une compilation en bac à sable.

--rebuild-on-sdk-change

Enregistre la version exacte du sdk dans le cache et recompile tout si elle change. C'est utile si vous compilez contre un environnement d'exécution à API instable, comme une compilation nightly.

--skip-if-unchanged

Si le fichier json est inchangé depuis la dernière compilation de ce nom de fichier, alors ne rien faire et retourner le code de sortie 42.

--mirror-screenshots-url=URL

Réplique tous les médias dans appstream et réécrit les URL des médias dans le fichier xml appstream vers l'URL spécifiée. Les fichiers résultants seront stockés dans le sous-répertoire "screenshots" du répertoire de l'application pour les versions antérieures à 1.3.4 et dans le sous-répertoire "files/share/app-info/media" pour les versions plus récentes. Depuis la version 1.4.5, cela créera également une référence de capture d'écran dans le dépôt OSTree exporté pour chaque architecture contenant les médias répliqués.

--extra-sources=SOURCE-DIR

Lors du téléchargement des sources (archives, fichiers, git, bzr, svn), chercher dans ce répertoire des copies préexistantes et les utiliser au lieu de télécharger. Le répertoire doit correspondre à la structure du répertoire d'état :
•Les fichiers et archives doivent être à l'intérieur du dossier : downloads/<sha256>/
•Les sources de type git, bzr et svn doivent être à l'intérieur du dossier : <type>/<converted-uri>/

Le converted-uri est construit à partir du chemin ou de l'URL (dans le cas de git) et de l'URL (dans le cas de bzr et svn). :// est converti en un seul soulignement et chaque autre / est remplacé par un soulignement. Par exemple, https://github.com/user/repo.git devient https_github.com_user_repo.git. Dans le cas des sources svn, si une révision est présente, le nom du dossier est svn/<converted-uri>__r<revision>/. Dans le cas des sources git, il doit s'agir d'un clone répliqué.

--extra-sources-url=URL

Lors du téléchargement des sources (archives, fichiers, git, bzr, svn), consulter cette URL pour les téléchargements répliqués avant de télécharger depuis l'URL originale.

--from-git=GIT

Chercher le manifeste dans le dépôt git indiqué. Si cette option est donnée, MANIFEST est interprété comme un chemin relatif à l'intérieur du dépôt.

--from-git-branch=BRANCH

La branche à utiliser avec --from-git.

--no-shallow-clone

Ne pas utiliser de clones superficiels lors de la réplication des dépôts git.

--override-source-date-epoch

Définit cet horodatage comme SOURCE_DATE_EPOCH pour effectuer la compilation, au lieu de l'heure de dernière modification du manifeste. C'est disponible depuis la version 1.3.1.

--compose-url-policy=POLICY

Définit la politique d'URL de composition AppStream. Les valeurs acceptées sont partial et full. full nécessite AppStream version >= 0.16.3. La valeur par défaut est partial si non spécifiée. Cette politique ne prend effet que lorsqu'elle est utilisée en conjonction avec --mirror-screenshots-url=URL; sinon le catalogue Appstream conservera les URL des médias sources.

--add-tag=TAG

Ajoute cette balise à la liste des balises du manifeste avant la compilation.

--remove-tag=TAG

Supprime cette balise de la liste des balises du manifeste avant la compilation. La suppression a lieu avant le traitement de l'option --add-tag, donc si les deux sont spécifiées, --app-tag l'emporte.

--install-deps-from=REMOTE

Installe/met à jour les dépendances requises pour la compilation depuis le dépôt distant spécifié.

--install-deps-only

S'arrête après le téléchargement des dépendances.

--install

Lorsque la compilation est terminée, installe le résultat localement.

--user

Installe les dépendances dans une installation par utilisateur.

--system

Installe les dépendances dans l'installation système par défaut.

--installation=NAME

Installe les dépendances dans une installation système spécifiée par NAME parmi celles définies dans /etc/flatpak/installations.d/. Utiliser --installation=default est équivalent à utiliser --system.

MISE EN CACHE

flatpak-builder met en cache les sources et les résultats partiels de compilation dans le répertoire d'état (par défaut le sous-répertoire .flatpak-builder du répertoire courant). Si vous utilisez --keep-build-dirs, les répertoires de compilation de chaque module sont également stockés ici.

Il est sûr de supprimer le répertoire d'état. Cela forcera une compilation complète la prochaine fois que vous compilerez.

$ flatpak-builder my-app-dir manifest.json
