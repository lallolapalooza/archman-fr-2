FMTUTIL(1) Commandes utilisateur FMTUTIL(1)

NOM

fmtutil - gérer les formats TeX et les bases Metafont, par utilisateur
fmtutil-sys - gérer les formats TeX et les bases Metafont, pour tout le système
mktexfmt - créer un format TeX ou une base Metafont

SYNTAXE

fmtutil [-user|-sys] [OPTION] ... [COMMANDE]
fmtutil-sys [OPTION] ... [COMMANDE]
fmtutil-user [OPTION] ... [COMMANDE]
mktexfmt FORMAT.fmt|BASE.base|NOMFORMAT

DESCRIPTION

fmtutil version r68962 (2023-11-25 00:01:43 +0100)

Reconstruit et gère les formats TeX (fmts) et les bases Metafont (bases), collectivement appelés « formats » ici. (MetaPost n'utilise plus les anciens « mems ».)

Si l'on n'opère pas en mode mktexfmt, une seule commande doit être donnée, les extensions de nom de fichier ne doivent généralement pas être spécifiées, aucun argument non optionnel n'est autorisé, et plusieurs formats peuvent être générés.

Si le nom de la commande se termine par mktexfmt, un seul format peut être créé. Les seules options prises en charge sont --help et --version, et la ligne de commande doit être soit un nom de format, avec extension, soit un nom simple qui est passé comme argument à --byfmt (voir ci-dessous). Le nom complet du fichier généré (le cas échéant) est écrit sur la sortie standard, et rien d'autre. Les répertoires système sont utilisés s'ils sont inscriptibles, sinon les répertoires utilisateur.

Par défaut, le code de retour est zéro si tous les formats demandés sont construits avec succès, sinon non nul.

OPTIONS

--sys
utilise TEXMFSYS{VAR,CONFIG}
--user
utilise TEXMF{VAR,CONFIG}
--cnffile FICHIER
lit FICHIER au lieu de fmtutil.cnf (peut être spécifié plusieurs fois, auquel cas tous les fichiers sont utilisés)
--dry-run, -n
ne construit pas réellement les formats
--fmtdir REP
écrit les formats sous REP au lieu de TEXMF[SYS]VAR
--no-engine-subdir
n'utilise pas de sous-répertoire spécifique au moteur dans le répertoire des formats
--no-error-if-no-format
termine avec succès si aucun format n'est sélectionné
--no-error-if-no-engine=MOTEUR1,MOTEUR2,...
termine avec succès même si un MOTEUR requis
est manquant, s'il est inclus dans la liste.
--no-strict
termine avec succès même si un format échoue à la construction
--nohash
ne met pas à jour les fichiers ls-R
--recorder
passe l'option -recorder et sauvegarde les fichiers .fls
--refresh
recrée uniquement les fichiers de format existants
--status-file FICHIER
ajoute les informations de statut sur les formats construits à FICHIER
--quiet
soit silencieux
--catcfg
(ne fait rien, existe pour la compatibilité)
--dolinks
(ne fait rien, existe pour la compatibilité)
--force
(ne fait rien, existe pour la compatibilité)
--test
(ne fait rien, existe pour la compatibilité)

Commandes (exactement une doit être spécifiée) :

--all
recrée tous les fichiers de format
--missing
crée tous les fichiers de format manquants
--byengine MOTEUR
(re)crée les formats construits avec MOTEUR
--byfmt FORMAT
(re)crée le format FORMAT
--byhyphen FICHIERTIRET
(re)crée les formats qui dépendent de FICHIERTIRET
--enablefmt
FORMAT[/MOTEUR] active FORMAT, tel que construit avec MOTEUR
--disablefmt FORMAT[/MOTEUR]
désactive FORMAT, tel que construit avec MOTEUR Si plusieurs formats ont le même nom et
des moteurs différents, le spécificateur /MOTEUR est requis.
--listcfg
liste les configurations (activées et désactivées), filtrées aux formats disponibles
--showhyphen FORMAT
affiche le nom du fichier de césure pour FORMAT
--version
affiche les informations de version et quitte
--help
affiche ce message et quitte

ENVIRONNEMENT

Explication des arbres et fichiers normalement utilisés :

Si --cnffile est spécifié sur la ligne de commande (éventuellement plusieurs fois), ses valeurs sont utilisées. Sinon, fmtutil lit tous les fichiers fmtutil.cnf trouvés en exécutant "kpsewhich -all fmtutil.cnf", dans l'ordre retourné par kpsewhich. Les fichiers spécifiés via --cnffile sont d'abord essayés d'être chargés directement, et s'ils ne sont pas trouvés et que les noms de fichiers ne contiennent pas de parties de répertoire, ils sont recherchés via kpsewhich.
Dans tous les cas, si plusieurs fichiers fmtutil.cnf sont trouvés, toutes les définitions de format trouvées dans tous les fichiers fmtutil.cnf sont fusionnées.
Ainsi, si des fichiers fmtutil.cnf sont présents dans tous les arbres, et que la disposition par défaut est utilisée telle qu'expédiée avec TeX Live, les fichiers suivants sont lus, dans l'ordre donné.
Pour fmtutil-sys :
TEXMFSYSCONFIG $TEXLIVE/YYYY/texmf-config/web2c/fmtutil.cnf
TEXMFSYSVAR    $TEXLIVE/YYYY/texmf-var/web2c/fmtutil.cnf
TEXMFLOCAL     $TEXLIVE/texmf-local/web2c/fmtutil.cnf
TEXMFDIST      $TEXLIVE/YYYY/texmf-dist/web2c/fmtutil.cnf
Pour fmtutil-user :
TEXMFCONFIG    $HOME/.texliveYYYY/texmf-config/web2c/fmtutil.cnf
TEXMFVAR       $HOME/.texliveYYYY/texmf-var/web2c/fmtutil.cnf
TEXMFHOME      $HOME/texmf/web2c/fmtutil.cnf
TEXMFSYSCONFIG $TEXLIVE/YYYY/texmf-config/web2c/fmtutil.cnf
TEXMFSYSVAR    $TEXLIVE/YYYY/texmf-var/web2c/fmtutil.cnf
TEXMFLOCAL     $TEXLIVE/texmf-local/web2c/fmtutil.cnf
TEXMFDIST      $TEXLIVE/YYYY/texmf-dist/web2c/fmtutil.cnf
(où YYYY est la version de la distribution TeX Live).
Selon les actions, fmtutil peut mettre à jour l'un des fichiers cnf existants ou créer un nouveau fmtutil.cnf, comme décrit ci-dessous.

Où les fichiers de format sont écrits :

Par défaut, les fichiers de format sont (re)écrits dans $TEXMFSYSVAR/ENGINE par fmtutil-sys, et $TEXMFVAR/ENGINE par fmtutil-user, où /ENGINE est un sous-répertoire nommé d'après le moteur utilisé, tel que "pdftex".
Pour mktexfmt, TEXMFSYSVAR est utilisé s'il est inscriptible, sinon TEXMFVAR.
Si l'option --fmtdir=REP est spécifiée, REP est utilisé à la place de TEXMF[SYS]VAR, mais le sous-répertoire /ENGINE est toujours utilisé par défaut.
Dans tous les cas, si l'option --no-engine-subdir est spécifiée, le sous-répertoire /ENGINE est omis.

Où les modifications de configuration sont sauvegardées :

Si des fichiers de configuration sont donnés sur la ligne de commande, alors le premier fichier donné sera utilisé pour sauvegarder les changements de --enable ou --disable.

Résolution des définitions multiples d'un format

:
Si un format est défini dans plus d'un fichier de
configuration, alors la définition proven
ant du fmtutil.cnf listé en premier est utilisée.

Désactivation des formats

:
Les fichiers fmtutil.cnf de priorité plus élevée (listés en premier) peuvent désactiver des formats dans les fichiers fmtutil.cnf de priorité inférieure (listés en dernier) en écrivant une ligne comme celle-ci dans le fichier fmtutil.cnf de priorité supérieure
:
#! <fmtname> <enginename> <hyphen>
<args>
Le #! doit être au début de la ligne, suivi d'au moins un espace ou une tabulation, et il doit y avoir un espace entre chaque mot de la
liste.
Par exemple, vous pouvez désactiver le format luajitlatex en créant le fichier $TEXMFCONFIG/web2c/fmtutil.cnf avec la
ligne
#! luajitlatex luajittex language.dat,language.dat.lua lualatex.
ini
(Comme il arrive, les formats liés à luajittex sont précisément la raison pour laquelle l'option --no-error-if-no-engine existe, puisque luajittex ne peut pas être
compilé sur toutes les plateforme
s. Donc cela n'est pas nécessaire.)

fmtutil-user (fmtutil -user) vs. fmtutil-sys (fmtutil -sys)

:
Lorsque fmtutil-sys est exécuté ou que l'option de ligne de commande -sys est utilisée, TEXMFSYSCONFIG et TEXMFSYSVAR sont utilisés au lieu de TEXMFCONFIG et TEXMFVAR, respectivement. C'est la principale différence entre fmtutil-sys et
fmtutil-user.
Voir https://tug.org/texlive/scripts-sys-user.html pour plus de
détails.

Bins de développement pris en charge

:
Si un nom de moteur se termine par "-dev", les formats sont créés dans le répertoire respectif avec le -dev supprimé. Cela permet d'exécuter facilement
des binaires de dév
eloppement en parallèle avec les binaires publiés.
