DESCRIPTIO

N

fork() crée un nouveau processus en dupliquant le processus appelant. Le nouveau processus est appelé le processus fils. Le processus appelant est appelé le processus p

arent.

Le processus fils et le processus parent s'exécutent dans des espaces mémoire séparés. Au moment de l'appel à fork(), les deux espaces mémoire ont le même contenu. Les écritures en mémoire, les mappages de fichiers (mmap(2)) et les dé-mappages (munmap(2)) effectués par l'un des processus n'affectent pas

l'autre.

Le processus fils est une copie exacte du processus parent, à l'exception des points suivants

:
•
Le fils possède son propre identifiant de processus unique, et ce PID ne correspond à l'identifiant d'aucun groupe de processus existant (setpgid(2)) ni d'aucune
session.
•
L'identifiant du processus parent du fils est le même que l'identifiant du processus du
parent.
•
Le fils n'hérite pas des verrous mémoire de son parent (mlock(2), mlockall(
2)).
•
Les utilisations de ressources du processus (getrusage(2)) et les compteurs de temps processeur (times(2)) sont remis à zéro dans le
fils.
•
L'ensemble des signaux en attente du fils est initialement vide (sigpending
(2)).
•
Le fils n'hérite pas des ajustements de sémaphores de son parent (semop(2
)).
•
Le fils n'hérite pas des verrous d'enregistrement associés au processus de son parent (fcntl(2)). (En revanche, il hérite des fcntl(2) verrous de description de fichier ouvert et des flock(2) verrous de son parent.
)
•
Le fils n'hérite pas des minuteurs de son parent (setitimer(2), alarm(2), timer_creat
e(2)).
•
Le fils n'hérite pas des opérations d'E/S asynchrones en attente de son parent (aio_read(3), aio_write(3)), ni il n'hérite de aucun contexte d'E/S asynchrone de son parent (voir io_set
up(2
)).

Les attributs de processus de la liste ci-dessus sont tous spécifiés dans POSIX.1. Le parent et le fils diffèrent également pour les attributs de processus spécifiques à Linux suivants

:
•
Le fils n'hérite pas des notifications de changement de répertoire (dnotify) de son parent (voir la description de F_NOTIFY dans fcntl(2
)).
•
Le paramètre prctl(2) PR_SET_PDEATHSIG est réinitialisé afin que le fils ne reçoive pas de signal lorsque son parent se
termine.
•
La valeur par défaut du relâchement de minuteur (timer slack) est définie sur la valeur actuelle du relâchement de minuteur du parent. Voir la description de PR_SET_TIMERSLACK dans prctl(
2).
•
Les mappages mémoire qui ont été marqués avec le madvise(2) MADV_DONTFORK ne sont pas hérités à travers un fork(
).
•
La mémoire dans les plages d'adresses qui ont été marquées avec le madvise(2) MADV_WIPEONFORK est mise à zéro dans le fils après un fork(). (Le paramètre MADV_WIPEONFORK reste en place pour ces plages d'adresses dans le fils.
)
•
Le signal de terminaison du fils est toujours SIGCHLD (voir clone(2
)).
•
Les bits de permission d'accès aux ports définis par ioperm(2) ne sont pas hérités par le fils ; le fils doit activer les bits dont il a besoin en utilisant ioper
m(2
).

Notez les points suivants supplémentaires

:
•
Le processus fils est créé avec un seul thread—celui qui a appelé fork(). L'espace d'adresses virtuelles entier du parent est répliqué dans le fils, y compris les états des mutexes, des variables de condition et des autres objets pthreads ; l'utilisation de pthread_atfork(3) peut être utile pour gérer les problèmes que cela peut
causer.
•
Après un fork() dans un programme multi-thread, le fils peut en toute sécurité appeler uniquement des fonctions sûres pour les signaux asynchrones (voir signal-safety(7)) jusqu'à ce qu'il appelle execve(
2).
•
Le fils hérite de copies de l'ensemble des descripteurs de fichiers ouverts du parent. Chaque descripteur de fichier dans le fils fait référence à la même description de fichier ouvert (voir open(2)) que le descripteur de fichier correspondant dans le parent. Cela signifie que les deux descripteurs de fichier partagent les drapeaux de statut de fichier ouvert, le décalage de fichier et les attributs d'E/S pilotés par signal (voir la description de F_SETOWN et F_SETSIG dans fcntl(2
)).
•
Le fils hérite de copies de l'ensemble des descripteurs de files de messages ouvertes du parent (voir mq_overview(7)). Chaque descripteur de fichier dans le fils fait référence à la même description de file de messages ouverte que le descripteur de fichier correspondant dans le parent. Cela signifie que les deux descripteurs de fichier partagent les mêmes drapeaux (mq_flag
s).
•
Le fils hérite de copies de l'ensemble des flux de répertoires ouverts du parent (voir opendir(3)). POSIX.1 dit que les flux de répertoires correspondants dans le parent et le fils peuvent partager le positionnement du fl
ux de répertoir
e ; sur Linux/glibc,
ils ne le font pas.

S

Différences entre la bibliothèque C et le

noyau

Depuis glibc 2.3.3, plutôt que d'invoquer l'appel système fork() du noyau, le conteneur fork() de glibc fourni dans le cadre de l'implémentation des fils d'exécution NPTL invoque clone(2) avec des drapeaux qui produisent le même effet que l'appel système traditionnel. (Un appel à fork() est équivalent à un appel à clone(2) spécifiant les drapeaux comme étant simplement SIGCHLD.) Le conteneur de glibc invoque tous les gestionnaires de fork qui ont été établis à l'aide de pthread_a

tfork

EXEMPLE

S

Voir pipe(2) et wait(2) pour plus

d'exemples. 
#include <signal.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <sys/types.h>
#include <unistd.h>
int
main(void)
{
    pid_t pid;
    if (signal(SIGCHLD, SIG_IGN) == SIG_ERR) {
        perror("signal");
        exit(EXIT_FAILURE);
    }
    pid = fork();
    switch (pid) {
    case -1:
        perror("fork");
        exit(EXIT_FAILURE);
    case 0:
        puts("Child exiting.");
        fflush(stdout);
        _exit(EXIT_SUCCESS);
    default:
        printf("Child is PID %jd\n", (intmax_t) pid);
        puts("Parent exiting.");
        exit(EXIT_SUCCESS);
    }
}
