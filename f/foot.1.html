foot(1) Manuel des commandes générales foot(1)

NOM

foot - Émulateur de terminal Wayland

SYNTAXE

foot [OPTIONS]
foot [OPTIONS] <commande> [OPTIONS DE COMMANDE]

Tous les arguments finaux (non-options) sont traités comme une commande et ses arguments, à exécuter (au lieu du shell par défaut).

DESCRIPTION

foot est un émulateur de terminal Wayland. Le lancer sans arguments ouvrira une nouvelle fenêtre de terminal avec votre shell par défaut.

Vous pouvez remplacer le shell par défaut en ajoutant une commande personnalisée à la ligne de commande de foot.

foot htop

OPTIONS

-c,--config=CHEMIN

Chemin vers le fichier de configuration, voir foot.ini(5) pour les détails.

-C,--check-config

Vérifie la configuration puis quitte avec 0 si elle est correcte, sinon quitte avec 230 (voir STATUT DE SORTIE).

-o,--override=[SECTION.]CLE=VALEUR

Remplace une option définie dans le fichier de configuration. Si SECTION n'est pas fournie, elle vaut par défaut main.

-f,--font=POLICE

Liste de polices séparées par des virgules à utiliser, au format fontconfig (voir FORMAT DE POLICE).

La première police est la police principale. Les polices restantes sont des polices de secours qui seront utilisées chaque fois qu'un glyphe ne sera pas trouvé dans la police principale.

Les polices de secours sont recherchées dans l'ordre où elles apparaissent. Si un glyphe ne peut être trouvé dans aucune des polices de secours, la liste de secours dynamique de fontconfig (pour la police principale) est recherchée.

Par défaut : monospace.

-w,--window-size-pixels=LARGEURxHAUTEUR

Définit la largeur et la hauteur initiales de la fenêtre, en pixels. Par défaut : 700x500.

-W,--window-size-chars=LARGEURxHAUTEUR

Définit la largeur et la hauteur initiales de la fenêtre, en caractères. Par défaut : non défini.

-t,--term=TERM

Valeur à définir pour la variable d'environnement TERM (voir TERMINFO et ENVIRONNEMENT). Par défaut : foot.

-T,--title=TITRE

Titre initial de la fenêtre. Par défaut : foot.

-a,--app-id=ID

Valeur à définir pour la propriété app-id de la fenêtre Wayland. Par défaut : foot (mode normal), ou footclient (mode serveur).

-m,--maximized

Démarrer en mode maximisé. Si --maximized et --fullscreen sont spécifiés, le dernier prend la prédominance.

-F,--fullscreen

Démarrer en mode plein écran. Si --maximized et --fullscreen sont spécifiés, le dernier prend la prédominance.

-L,--login-shell

Démarre un shell de connexion, en ajoutant un '-' devant argv[0].

--pty

Affiche un pty existant au lieu d'en créer un. Ceci est utile pour interagir avec les consoles de machines virtuelles.

Cette option n'est actuellement pas supportée en combinaison avec -s,--server.

-D,--working-directory=REP

Répertoire de travail initial pour l'application cliente. Par défaut : CWD de foot.

-s,--server[=CHEMIN|FD]

Exécute en tant que serveur. Dans ce mode, une seule instance de foot héberge plusieurs terminaux (fenêtres). Utilisez footclient(1) pour lancer de nouveaux terminaux.

Cela permet d'économiser de la mémoire car, par exemple, les polices et les caches de glyphes peuvent être partagés entre les terminaux.

Cela permet également d'économiser du temps de démarrage car la configuration a déjà été chargée et analysée, et surtout, les polices ont déjà été chargées (et leurs caches de glyphes ont probablement déjà été remplis).

Chaque terminal aura ses propres threads de rendu, mais toute la communication Wayland, ainsi que les entrées/sorties vers le shell, est multiplexée dans le thread principal. Par conséquent, ce mode peut entraîner une performance légèrement moins bonne lorsque plusieurs terminaux sont sous une charge importante.

Soyez également conscient que si un terminal plante, il entraînera les autres avec lui.

Le chemin par défaut est $XDG_RUNTIME_DIR/foot-$WAYLAND_DISPLAY.sock.

Si $XDG_RUNTIME_DIR n'est pas défini, le chemin par défaut est /tmp/foot.sock.

Si $XDG_RUNTIME_DIR est défini, mais pas $WAYLAND_DISPLAY, le chemin par défaut est $XDG_RUNTIME_DIR/foot.sock.

Notez que si vous modifiez le chemin par défaut, vous devrez également utiliser l'option --server-socket dans footclient(1) et la pointer vers votre chemin de socket personnalisé.

Si l'argument est un nombre, foot l'interprétera comme le descripteur de fichier d'un socket fourni par un démon de supervision (tel que systemd ou s6), et l'utilisera comme son propre socket.

Deux unités systemd (foot-server.{service,socket}) sont fournies pour utiliser cette fonctionnalité avec systemd. Pour utiliser l'activation par socket, activez uniquement l'unité de socket.

Notez que le démarrage de foot --server en tant que service systemd utilisera l'environnement de l'instance utilisateur systemd ; par conséquent, vous devrez y importer $WAYLAND_DISPLAY en utilisant systemctl --user import-environment WAYLAND_DISPLAY.

-H,--hold

Reste ouvert après la sortie du processus enfant.

-p,--print-pid=FICHIER|FD

Imprime le PID dans ce fichier, ou FD, lors du démarrage réussi. Le fichier (ou FD) est fermé immédiatement après l'écriture du PID. Lorsqu'un FICHIER est spécifié, le fichier est désolidarisé à la sortie.

Cette option ne peut être utilisée qu'en combinaison avec -s,--server.

-d,--log-level={info,warning,error,none}

Niveau de journalisation, utilisé à la fois pour la sortie du journal sur stderr et pour syslog. Par défaut : warning.

-l,--log-colorize=[{never,always,auto}]

Active ou désactive la colorisation de la sortie du journal sur stderr. Par défaut : auto.

-S,--log-no-syslog

Désactive la journalisation syslog. La journalisation se fait uniquement sur stderr. Cette option ne peut être utilisée qu'en combinaison avec -s,--server.

-v,--version

Affiche le numéro de version et quitte.

-e

Ignoré ; pour la compatibilité avec xterm -e.

Cette option a été ajoutée en réponse à plusieurs lanceurs de programmes qui passaient -e à des terminaux arbitraires, en supposant qu'ils implémentent tous les mêmes sémantiques pour celui-ci que xterm(1). L'ignorer permet d'invoquer foot par exemple avec foot -e man foot avec les mêmes résultats qu'avec xterm, au lieu de produire une erreur "option invalide".

FORMAT DE LA POLICE

La police est spécifiée selon la syntaxe de FontConfig. C'est-à-dire, une liste de noms de polices et d'options de police séparés par des deux-points.

Exemples:

  • Dina:weight=bold:slant=italic
  • Courier New:size=12

URL

Foot prend en charge la détection des URL. Mais, contrairement à de nombreux autres émulateurs de terminal, où les URL sont surlignées lorsqu'elles sont survolées et ouvertes en cliquant dessus, foot utilise une approche pilotée par le clavier.

Presser ctrl+shift+o entre en « mode d'ouverture d'URL », où toutes les URL actuellement visibles sont soulignées, et est associé à une « étiquette de saut ». L'étiquette de saut indique la séquence de touches (par exemple « AF ») à utiliser pour activer l'URL.

La liaison de touches peut, bien sûr, être personnalisée, comme toutes les autres liaisons de touches dans foot. Voir show-urls-launch et show-urls-copy dans foot.ini(5).

show-urls-launch ouvre l'URL par défaut avec xdg-open. Cela peut être modifié avec l'option url-launch .

show-urls-copy est une alternative à show-urls-launch, qui change ce que fait l'activation d'une URL ;au lieu de l'ouvrir, elle la copie dans le presse-papiers. Elle n'est pas liée par défaut.

Les couleurs des étiquettes de saut, la couleur du soulignement des URL et les lettres utilisées dans les séquences de touches des étiquettes de saut peuvent être configurées.

CARACTÈRES ALT/META

Par défaut, foot préfixe les caractères meta avec ESC. Cela correspond à l'option metaSendsEscape de XTerm définie à true.

Cela peut être désactivé programmatiquement avec E[?1036l (et réactivé avec E[?1036h).

Lorsque c'est désactivé, foot définit à la place le 8:ème bit du caractère meta puis l'encode en UTF-8. Cela correspond à l'option eightBitMeta de XTerm définie à true.

Cela peut aussi être désactivé programmatiquement avec rmm (Reset Meta Mode, E[?1034l), et réactivé avec smm (Set Meta Mode, E[?1034h).

RETOUR ARRIÈRE

Foot transmet DEL (^?) lors du retour arrière. Cela correspond à l'option backarrowKey de XTerm définie à false, et à DECBKM réinitialisé.

Pour transmettre BS (^H) à la place, pressez ctrl+backspace.

Notez que foot n'implémente pas DECBKM, et que le comportement décrit ci-dessus ne peut pas être modifié.

Enfin, presser alt préfixera l.octet transmis avec ESC.

PAVÉ NUMÉRIQUE

Par défaut, Num Lock prévaut sur le mode de pavé numérique de la configuration à l'exécution ; lorsqu'il est actif, le pavé numérique est toujours considéré comme étant en mode numérique . Cela correspond à l'option numLock de XTerm définie à true.

Dans ce mode, les touches du pavé numérique envoient toujours soit des chiffres (Num Lock actif) soit des touches de déplacement du curseur (haut, bas, gauche, droite, page up, page down, etc.).

Cela peut être désactivé programmatiquement avec E[?1035l (et réactivé avec E[?1035h).

Lorsque c'est désactivé, le pavé numérique envoie des séquences d'échappement personnalisées au lieu de chiffres, lorsqu'il est en mode application .

CONFIGURATION

foot recherchera un fichier de configuration aux emplacements suivants, dans cet ordre :

  • XDG_CONFIG_HOME/foot/foot.ini (par défaut $HOME/.config/foot/foot.ini si non défini)
  • XDG_CONFIG_DIRS/foot/foot.ini (par défaut /etc/xdg/foot/foot.ini si non défini)

Un exemple de fichier de configuration contenant toutes les options avec leurs valeurs par défaut la valeur commentée sera généralement installée dans /etc/xdg/foot/foot.ini.

Pour plus d'informations, voir foot.ini(5).

INTÉGRATION AVEC LE SHELL

Répertoire de travail courant

Les nouvelles instances de terminal foot (liées à ctrl+shift+n par défaut) s'ouvriront dans le répertoire de travail courant, si le shell du terminal « parent » signale les changements de répertoire. Cela se fait avec la séquence d'échappement OSC-7. La plupart des shells peuvent être scriptés pour faire cela, s'ils ne le supportent pas nativement. Voir le wiki (

https://codeberg.org/dnkl/foot/wiki#user-content-spawning-new-terminal-instances-in-the-current-working-directory) pour plus de détails.Sauter entre les invites

Foot peut déplacer le viewport courant pour se concentrer sur les invites de commandes déjà exécutées (lié à

ctrl +shift+z/xpar défaut). Pour que cela fonctionne, le shell doit émettre une séquence OSC-133;A (

\E]133;A\E\\) avant chaque invite.Dans zsh, une façon de faire cela est d'ajouter un hook

precmd : precmd() {

print -Pn "\e]133;A\e\\"
}
Voir le wiki (

https://codeberg.org/dnkl/foot/wiki#user-content-jumping-between-prompts) pour plus de détails et des exemples pour d'autres shells.Rediriger la sortie de la dernière commande

La liaison de touche

pipe-command-output peut rediriger la sortie de la dernière commande vers une application de votre choix (similaire aux autres liaisons de touches pipe-* ) : [key-bindings]

pipe-command-output=[sh -c "f=$(mktemp); cat - > $f; footclient emacsclient -nw $f; rm $f"] Control+Shift+g
En appuyant sur

ctrl +shift+g, la sortie de la dernière commande est écrite dans un fichier temporaire, puis un emacsclient est démarré dans une nouvelle instance de footclient. Le fichier temporaire est supprimé après la fermeture de l'instance footclient.Pour que cela fonctionne, le shell doit émettre une séquence OSC-133;C (

\E]133;C\E\\) avant que la sortie de la commande ne commence, et une OSC-133;D (\E]133;D\E\\) lorsque la sortie de la commande se termine.Dans fish, une façon de faire cela est d'ajouter des hooks

preexec et postexec : function foot_cmd_start --on-event fish_preexec

echo -en "\e]133;C\e\\"
end
function foot_cmd_end --on-event fish_postexec

echo -en "\e]133;D\e\\"

end
Voir le wiki (

https://codeberg.org/dnkl/foot/wiki#user-content-piping-last-commands-output) pour plus de détails et des exemples pour d'autres shellsTERMINFO

Les applications clientes utilisent l'identifiant terminfo spécifié par la variable d'environnement

TERM (définie par foot) pour déterminer les capacités du terminal. Foot a deux définitions terminfo :

foot et foot-direct , avecfoot étant la valeur par défaut. La différence entre les deux réside dans le nombre de couleurs qu'elles décrivent ;

foot décrit 256 couleurs et foot-direct 16,7 millions de couleurs (truecolor 24 bits). Notez que l'utilisation de l'entrée terminfo

foot ne limite pas le nombre de couleurs utilisables à 256 ; les applications peuvent toujours utiliser des couleurs RGB 24 bits. En fait, la plupart des applications fonctionnent mieux avec foot (y compris les couleurs 24 bits). L'utilisation des entrées terminfo *-direct a été connue pour faire planter certaines applications ncurses. Il existe cependant des applications qui ont besoin d'une entrée terminfo

*-direct pour le support 24 bits. Emacs est un tel exemple. Bien qu'il soit fortement recommandé d'utiliser

foot ou foot-direct , il est possible d'utiliser par exemple xterm-256color . Cela peut être utile lors de l'accès à distance à un système où les entrées terminfo de foot ne peuvent pas facilement être installées. Notez que les entrées terminfo peuvent être installées dans le répertoire personnel de l'utilisateur. C'est-à-dire que si vous n'avez pas d'accès root, ou s'il n'existe pas de paquet de distribution pour les entrées terminfo de foot, vous pouvez installer manuellement les entrées terminfo de foot en copiant

foot et foot-direct vers ~/.terminfo/f/ .XTGETTCAP

XTGETTCAP

est une séquence d'échappement initialement introduite par XTerm, et également implémentée (et étendue, dans une certaine mesure) par Kitty. Elle permet d'interroger le terminal pour obtenir la définition terminfo classique, basée sur des fichiers. Par exemple, si toutes les applications utilisaient cette fonctionnalité, vous n'auriez plus à installer les entrées terminfo de foot sur les hôtes distants auxquels vous vous connectez en SSH.

L'implémentation de XTerm (en tant qu'XTerm-370) ne supporte que l'interrogation des capacités de touches (clavier) et trois capacités personnalisées :

TN - nom du terminal

  • Co - nombre de couleurs (alias de la capacité colors)
  • RGB - nombre de bits par canal de couleur (sémantique différente de la capacité RGB dans les définitions terminfo basées sur des fichiers !).
  • Kitty a étendu cela et supporte également l'interrogation de toutes les capacités entières et de chaînes.

Foot supporte cela et l'étend encore plus loin, pour inclure également les capacités booléennes. Cela signifie que l'intégralité du terminfo de foot peut être interrogée via

XTGETTCAP .Notez que Kitty et foot traitent les réponses aux interrogations multi-capacités légèrement différemment, par rapport à XTerm.

XTerm enverra une seule réponse DCS, avec des paires capacité/valeur séparées par des « ; ». Il y a quelques problèmes avec cela :

Le drapeau succès/échec au début de la réponse est toujours 1 (succès), sauf si la toute première capacité interrogée est invalide.

  • XTerm ne répondra pas du tout à une capacité invalide, sauf si c'est la première dans l'interrogation XTGETTCAP.
  • XTerm terminera la réponse à la première capacité invalide.
  • En d'autres termes, si vous envoyez une grande interrogation multi-capacités, vous ne recevrez des réponses que jusqu'à, mais sans inclure, la première capacité invalide. Toutes les capacités suivantes seront ignorées.

Kitty et foot, quant à eux, envoient une réponse DCS pour chaque capacité dans l'interrogation multiple. Cela nous permet d'envoyer un drapeau succès/échec approprié pour chaque capacité interrogée. Les réponses pour toutes les capacités interrogées sont toujours envoyées. Aucune interrogation n'est jamais ignorée.

CODE DE SORTIE

Foot se terminera avec le code 230 en cas d'échec de foot lui-même.

Dans tous les autres cas, le code de sortie est celui de l'application cliente (c'est-à-dire le shell).

Signaux

Les signaux suivants ont une signification particulière dans foot :

  • SIGUSR1 : basculer vers le thème de couleurs 1 (c'est-à-dire utiliser la section [colors] ).
  • SIGUSR2 : basculer vers le thème de couleurse 2 (c'est-à-dire utiliser la [colors2] section).

Remarque : vous pouvez envoyer SIGUSR1/SIGUSR2 à un foot --server processus aussi, auquel cas toutes les instances clientes changeront de thème. De plus, toutes les futures instances clientes utiliseront également le thème sélectionné.

Vous pouvez également envoyer SIGUSR1/SIGUSR2 à une instance de footclient, voir footclient(1) pour plus de détails.

BUGS

Veuillez signaler les bugs à https://codeberg.org/dnkl/foot/issues

Avant d'ouvrir un nouveau ticket, veuillez rechercher dans les rapports de bugs existants, qu'ils soient ouverts ou fermés. Il est possible que quelqu'un d'autre ait déjà signalé le même problème.
