DESCRIPTIO

N

Le fichier /etc/freeipmi//freeipmi_interpret_sel.conf définit la manière dont les entrées du journal des événements système (SEL) IPMI doivent être interprétées. Les événements système IPMI spécifient un certain nombre d'états/seuils lorsqu'ils sont lus. Sur la base de ces états/seuils, les bibliothèques et outils tels que libipmimonitoring(3) et ipmi-sel(8) peuvent signaler si un événement est « bon » ou « mauvais » via un rapport d'un état NOMINAL, AVERTISSEMENT ou CRITIQUE. Un état différent peut être rapporté pour un événement selon qu'il est affirmé ou

désaffirmé.

Chacun des états listés ci-dessous est (on l'espère) suffisamment descriptif pour décrire les conditions d'état qui peuvent être définies/réinitialisées pour chaque capteur ou type d'événement. Pour des informations plus détaillées sur chacun des états individuels listés ci-dessous, veuillez consulter les « Sensor and Event Code Tables » de la spécification IPMI. Ipmi-sensors(8) peut être utilisé pour déterminer les types de capteurs et les états/seuils qui existent sur un système en produisant une sortie très verbeuse et en voyant quels types d'événements d'affirmation ou de désaffirmation sont

possibles.

Chacun des événements ci-dessous peut prendre 1 ou 2 des états suivants en

entrée.

Nominal - Signale une lecture nominale si l'événement se

déclenche

Warning - Signale une lecture d'avertissement si l'événement se

déclenche

Critical - Signale une lecture critique si l'événement se

déclenche

Si un seul état est listé, cet état sera interprété lorsque l'événement est affirmé ou désaffirmé. Si deux états sont listés, le premier état sera interprété lorsque l'événement est affirmé, et le second sera interprété lorsque l'événement est

désaffirmé.

Tous les types de capteurs et les types d'événements IPMI ne sont pas actuellement pris en charge. Si vous souhaitez que d'autres le soient, veuillez envoyer un courriel à la liste de diffusion

FreeIPMI.

Les valeurs par défaut sélectionnées pour le déclenchement des événements individuels sont basées sur les meilleures suppositions et les cartes mères analysées. Si vous pensez qu'elles devraient être modifiées, veuillez envoyer un courriel à la liste de diffusion FreeIPMI pour discuter de ce que devraient être les valeurs par

défaut.

La plupart des interprétations par défaut peuvent être déterminées assez facilement et peuvent répondre aux besoins de la plupart des utilisateurs. Par exemple, une lecture de « Performa

nce_Met » est normalement meilleure que « Performance_Lags ». Cependant, certains capteurs peuvent être ambigus et dépendent entièrement du fabricant. Par exemple, « State_Asserted » vs
. « State_Deasserted » sont entièrement à l'interprétation du fournisseur. Il est conseillé aux utilisateurs d'ajuster les interprétations ci-dessous selon les besoins de leurs machines.

Les options de configuration suivantes peuvent être utilisées pour configurer les événements du journal des événements système OEM. Les règles d'interprétation pour une combinaison spécifique de Manufacturer-ID, Product-ID, et Record-Type sont parcourues et l'état de capteur le plus grave résultant est retourné (c'est-à-dire Warning < Nominal, Critical < Warning). Si aucune correspondance n'est trouvée, aucun état n'est retourné pour l'événement OEM. Pour chacune des options de configuration ci-dessous, <Manufacturer-ID> est l'identifiant numérique IANA du fabricant en question. Le <Product-ID> est un ou plusieurs identifiants numériques représentant le produit du fabricant. Le <Product-ID> peut être listé comme un nombre numérique unique (par exemple 1234), une plage d'identifiants séparés par un tiret (par exemple 12-20), ou une liste de Product-ID spécifiques séparés par un plus (par exemple 12+19+22). À la fois le Manufacturer-ID et le Product-ID peuvent être trouvés en utilisant bmc-info(8). Plusieurs <Manufacturer-ID> et <Product-ID> peuvent être ent
rés séparés par
des virgules.
IPMI_OEM_Sensor_System_Event_Record <Manufacturer-ID>:<Product-ID>,... Event-Reading-Type-Code Sensor-Type Event-Direction EventData1 EventData2 EventData3 Sta
te
IPMI_OEM_System_Event_Record peut être utilisé pour configurer une interprétation d'état pour une combinaison spécifique de Manufacturer-ID, Product-ID, Event-Reading-Type-Code, et Sensor-Type, et une combinaison spécifique de Event-Direction, EventData1, EventData2, et EventData3. Le champ Event-Direction doit spécifier Assertion, Deassertion, ou ANY. Chacun des champs EventData doit spécifier un octet hexadécimal à faire correspondre ou le mot-clé ANY pour faire correspondre n'importe quoi. Le Event-Reading-Type-Code et le Sensor-Type n'ont pas besoin d'être des types OEM. Ils peuvent être des types non-OEM et utilisés pour fournir des règles d'interprétation pour des capteurs qui peuvent se comporter en dehors du standard de la spécification
IPMI.
IPMI_OEM_Timestamped_Record <Manufacturer-ID>:<Product-ID>,... Record-Type OEMDATA1 OEMDATA2 OEMDATA3 OEMDATA4 OEMDATA5 OEMDATA6 State>
IPMI_OEM_Timestamped_Record peut être utilisé pour configurer une interprétation pour une combinaison spécifique de Manufacturer-ID, Product-ID, Record-Type et données OEM. Le Record-Type doit être un type d'enregistrement valide pour les enregistrements horodatés OEM (actuellement 0xC0-0xDF). Chacun des champs OEMDATA doit spécifier un octet hexadécimal à faire correspondre ou le mot-clé ANY pour faire correspondre n'importe quoi.
IPMI_OEM_Non_Timestamped_Record <Manufacturer-ID>:<Product-ID>,... Record-Type OEMDATA1 OEMDATA2 OEMDATA3 OEMDATA4 OEMDATA5 OEMDATA6 OEMDATA7 OEMDATA8 OEMDATA9 OEMDATA10 OEMDATA11 OEMDATA12 OEMDATA13 State
IPMI_OEM_Non_Timestamped_Record peut être utilisé pour configurer une interprétation pour une combinaison spécifique de Manufacturer-ID, Product-ID, Record-Type et données OEM. Le Record-Type doit être un type d'enregistrement valide pour les enregistrements non horodatés OEM (actuellement 0xEO-0xFF). Chacun des champs OEMDATA doit spécifier un octet hexadécimal à faire correspondre ou le mot-clé ANY pour faire correspondre n'importe quoi.
