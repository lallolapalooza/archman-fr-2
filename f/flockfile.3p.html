FLOCKFILE(3P) Manuel du programmeur POSIX FLOCKFILE(3P)

PROLOGUE

Cette page man fait partie du Manuel du programmeur POSIX. L'implémentation Linux de cette interface peut différer (consultez la page man Linux correspondante pour les détails du comportement de Linux), ou l'interface peut ne pas être implémentée sur Linux.

NOM

flockfile, ftrylockfile, funlockfile — fonctions de verrouillage stdio

SYNOPSIS

#include <stdio.h>
void flockfile(FILE *file);
int ftrylockfile(FILE *file);
void funlockfile(FILE *file);

DESCRIPTION

Ces fonctions doivent permettre le verrouillage explicite au niveau de l'application des objets stdio (FILE *). Ces fonctions peuvent être utilisées par un thread pour délimiter une séquence d'instructions d'E/S exécutées comme une unité.

La flockfile() fonction doit acquérir pour un thread la propriété d'un objet (FILE *).

La ftrylockfile() fonction doit acquérir pour un thread la propriété d'un objet (FILE *) si l'objet est disponible ; ftrylockfile() est une version non bloquante de flockfile().

La funlockfile() fonction doit renoncer à la propriété accordée au thread. Le comportement est indéfini si un thread autre que le propriétaire actuel appelle la funlockfile() fonction.

Les fonctions doivent se comporter comme s'il y avait un compteur de verrouillage associé à chaque objet (FILE *). Ce compteur est implicitement initialisé à zéro lorsque l'objet (FILE *) est créé. L'objet (FILE *) est déverrouillé lorsque le compteur est zéro. Lorsque le compteur est positif, un seul thread possède l'objet (FILE *). Lorsque la flockfile() fonction est appelée, si le compteur est zéro ou si le compteur est positif et que l'appelant possède l'objet (FILE *), le compteur doit être incrémenté. Sinon, le thread appelant doit être suspendu, attendant que le compteur revienne à zéro. Chaque appel à funlockfile() doit décrémenter le compteur. Cela permet aux appels appariés à flockfile() (ou aux appels réussis à ftrylockfile()) et funlockfile() d'être imbriqués.

Toutes les fonctions qui référencent des objets (FILE *), à l'exception de celles dont les noms se terminent par _unlocked, doivent se comporter comme si elles utilisaient flockfile() et funlockfile() en interne pour obtenir la propriété de ces objets (FILE *).

VALEUR DE RETOUR

Aucune pour flockfile() et funlockfile().

La ftrylockfile() fonction doit retourner zéro en cas de succès et non-zéro pour indiquer que le verrou ne peut pas être acquis.

ERREURS

Aucune erreur n'est définie.

UTILISATION PAR LES APPLICATIONS

Les applications utilisant ces fonctions peuvent être sujettes à l'inversion de priorité, comme discuté dans le volume des définitions de base de POSIX.1‐2017, Section 3.291, Inversion de priorité.

Un appel à exit() peut bloquer jusqu'à ce que les flux verrouillés soient déverrouillés, car un thread possédant un objet (FILE*) bloque tous les appels de fonction qui référencent cet objet (FILE*) (à l'exception de ceux dont les noms se terminent par _unlocked) provenant d'autres threads, y compris les appels à exit().

JUSTIFICATION

Les fonctions flockfile() et funlockfile() fournissent un verrou d'exclusion mutuelle orthogonal pour chaque FILE. La ftrylockfile() fonction fournit une tentative non bloquante d'acquérir un verrou de fichier, analogue à pthread_mutex_trylock().

Ces verrous se comportent comme s'ils étaient les mêmes que ceux utilisés en interne par stdio pour la sécurité des threads. Cela fournit à la fois la sécurité des threads de ces fonctions sans nécessiter un deuxième niveau de verrouillage interne et permet aux fonctions dans stdio d'être implémentées en termes d'autres stdio fonctions.

Les développeurs et les implémenteurs d'applications doivent être conscients qu'il y a des problèmes potentiels d'interblocage sur les objets FILE . Par exemple, la sémantique de vidage à la ligne des flux stdio (demandée via {_IOLBF}) exige que certaines opérations d'entrée provoquent parfois le vidage du contenu tamponné des flux de sortie tamponnés à la ligne définis par l'implémentation. Si deux threads tiennent chacun le verrou sur le FILEde l'autre, un interblocage s'ensuit. Ce type d'interblocage peut être évité en acquérant les verrous FILE dans un ordre cohérent. En particulier, l'interblocage des flux de sortie tamponnés à la ligne peut généralement être évité en acquérant les verrous sur les flux d'entrée avant les verrous sur les flux de sortie si un thread devait acquérir les deux.

En résumé, les threads partageant les flux stdio avec d'autres threads peuvent utiliser flockfile() et funlockfile() pour faire en sorte que les séquences d'E/S effectuées par un seul thread soient conservées groupées. Le seul cas où l'utilisation de flockfile() et funlockfile() est requise est pour fournir une portée protégeant l'utilisation des *_unlocked fonctions/macros. Cela déplace le compromis coût/performance au point optimal.
