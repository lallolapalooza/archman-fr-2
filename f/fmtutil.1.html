DESCRIPTIO

N

fmtutil version r65989 (2023-02-20 22:52:59

+0100)

Reconstruire et gérer les fmts TeX et les bases Metafont, appelés collectivement « formats » ici. (MetaPost n'utilise plus l'équivalent passé « mems ».

)

Si le mode mktexfmt n'est pas utilisé, exactement une commande doit être donnée, les suffixes de nom de fichier ne doivent généralement pas être spécifiés, aucun argument non-option n'est autorisé, et plusieurs formats peuvent être

générés.

Si le nom de la commande se termine par mktexfmt, un seul format peut être créé. Les seules options prises en charge sont --help et --version, et la ligne de commande doit être soit un nom de format, avec extension, soit un nom simple qui est passé comme argument à --byfmt (voir ci-dessous). Le nom complet du fichier généré (s'il y en a un) est écrit sur stdout, et rien d'autre. Les répertoires système sont utilisés s'ils sont inscriptibles, sinon les répertoires de

l'utilisateur.

Par défaut, le statut de retour est zér

o si tous les formats demandés sont
construits avec succès, sinon non nul.

T

Explication des arbres et fichiers normalement utilisés

:
Si --cnffile est spécifié sur la ligne de commande (éventuellement plusieurs fois), sa ou ses valeurs sont utilisées. Sinon, fmtutil lit tous les fichiers fmtutil.cnf trouvés en exécutant "kpsewhich -all fmtutil.cnf", dans l'ordre renvoyé par kpsewhich. Les fichiers spécifiés via --cnffile sont d'abord essayés d'être chargés directement, et s'ils ne sont pas trouvés et que les noms de fichiers ne contiennent pas de parties de répertoire, ils sont recherchés via
kpsewhich.
Dans tous les cas, si plusieurs fichiers fmtutil.cnf sont trouvés, toutes les définitions de format trouvées dans tous les fichiers fmtutil.cnf sont
fusionnées.
Ainsi, si des fichiers fmtutil.cnf sont présents dans tous les arbres, et que la disposition par défaut telle que livrée avec TeX Live est utilisée, les fichiers suivants sont lus, dans l'ordre
donné. 
Pour fmtutil-sys :
TEXMFSYSCONFIG $TEXLIVE/YYYY/texmf-config/web2c/fmtutil.cnf
TEXMFSYSVAR    $TEXLIVE/YYYY/texmf-var/web2c/fmtutil.cnf
TEXMFLOCAL     $TEXLIVE/texmf-local/web2c/fmtutil.cnf
TEXMFDIST      $TEXLIVE/YYYY/
texmf-dist/web
2c/fmtutil.cnf 
Pour fmtutil-user :
TEXMFCONFIG    $HOME/.texliveYYYY/texmf-config/web2c/fmtutil.cnf
TEXMFVAR       $HOME/.texliveYYYY/texmf-var/web2c/fmtutil.cnf
TEXMFHOME      $HOME/texmf/web2c/fmtutil.cnf
TEXMFSYSCONFIG $TEXLIVE/YYYY/texmf-config/web2c/fmtutil.cnf
TEXMFSYSVAR    $TEXLIVE/YYYY/texmf-var/web2c/fmtutil.cnf
TEXMFLOCAL     $TEXLIVE/texmf-local/web2c/fmtutil.cnf
TEXMFDIST      $TEXLIVE/YYYY/
texmf-dist/web
2c/fmtutil.cnf 
(où YYYY est la version de la publication TeX
Live)
.
Selon les actions, fmtutil peut mettre à jour
l'un des fichiers cnf existants ou créer un
nouveau fmtutil.cnf, comme décrit ci-dessous.

Où les fichiers de format sont écrits

:
Par défaut, les fichiers de format sont (ré)écrits dans $TEXMFSYSVAR/ENGINE par fmtutil-sys, et $TEXMFVAR/ENGINE par fmtutil-user, où /ENGINE est un sous-répertoire nommé d'après le moteur utilisé, comme
"pdftex".
Pour mktexfmt, TEXMFSYSVAR est utilisé s'il est inscriptible, sinon
TEXMFVAR.
Si l'option --fmtdir=RÉP est spécifiée, RÉP est utilisé à la place de TEXMF[SYS]VAR, mais le sous-répertoire /ENGINE est toujours utilisé par
défaut.
Dans tous les cas, si l'option --no-engine-subdir est spécifiée, le sous-répertoire
/ENGINE e
st omis.

Où les changements de configuration sont sauvegardés

:
Si des fichiers de configuration sont donnés sur la ligne de commande, alors le premier donné sera utilisé pour sauvegarder tout changement provenant de --enable ou --disabl
e.
Si les fichiers de configuration sont pris de la sortie de kpsewhich, alors l'algorithme est plus compliqué
:
1) Si $TEXMFCONFIG/web2c/fmtutil.cnf ou $TEXMFHOME/web2c/fmtutil.cnf apparaît dans la liste des fichiers utilisés, puis celle listée en premier par kpsewhich --all (équivalente, celle renvoyée par "kpsewhich fmtutil.cnf"), est
utilisée.
2) Si aucune des deux précédentes n'est présente et que des modifications sont effectuées, un nouveau fichier de configuration est créé dans $TEXMFCONFIG/web2c/fm
tutil.cnf.
En général, l'idée est que si un fichier de configuration donné n'est pas inscriptible, un fichier de niveau supérieur peu
t être utilisé. De cette façon, les réglages de la distribution peuvent être remplacés à l'échelle du système via TEXMFLO
CAL, et les réglages système peuvent être remplacés à nouveau dans le TEXMFHOME ou TEXMFCONF d'un utilisateur particulier.

Résolution des définitions multiples d'un format

:
Si un format est défini dans plus d'un fichier
de configuration, la définition provenan
t du fmtutil.cnf listé en premier est utilisée.

Désactivation des formats

:
Les fichiers fmtutil.cnf de priorité plus élevée (listés plus tôt) peuvent désactiver des formats dans les fichiers fmtutil.cnf de priorité inférieure (listés plus tard) en écrivant une ligne comme celle-ci dans le fichier fmtutil.cnf de priorité supérieure
:
#! <fmtname> <enginename> <hyphen>
<args>
Le #! doit se trouver au début de la ligne, suivi d'au moins un espace ou d'une tabulation, et il doit y avoir des espaces entre chaque mot de la
liste.
Par exemple, vous pouvez désactiver le format luajitlatex en créant le fichier $TEXMFCONFIG/web2c/fmtutil.cnf contenant la
ligne
#! luajitlatex luajittex language.dat,language.dat.lua lualatex.
ini
(Comme il arrive, les formats liés à luajittex sont précisément la raison pour laquelle l'option --no-error-if-no-engine existe, car luajittex ne peut pas être
compilé sur toutes les plateform
es. Ce n'est donc pas nécessaire.)

fmtutil-user (fmtutil -user) vs. fmtutil-sys (fmtutil -sys)

:
Lorsque fmtutil-sys est exécuté ou que l'option de ligne de commande -sys est utilisée, TEXMFSYSCONFIG et TEXMFSYSVAR sont utilisés à la place de TEXMFCONFIG et TEXMFVAR, respectivement. C'est la principale différence entre fmtutil-sys et
fmtutil-user.
Voir https://tug.org/texlive/scripts-sys-user.html pour plus de
détails.
D'autres emplacements peuvent être utilisés si vous les indiqu
ez sur la ligne de commande, ou si ces arborescences n'
existent pas, ou si vous n'utilisez pas le TeX Live d'origine.

Prise en charge des binaires de développement

:
Si un nom de moteur se termine par "-dev", les formats sont créés dans le répertoire respectif avec le -dev supprimé. Cela permet d'exécuter facilement
les binaires de
développement en parallè
le des binaires publiés.
