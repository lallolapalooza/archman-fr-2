DESCRIPTIO

N

La fonction fsync() doit demander que toutes les données du descripteur de fichier ouvert nommé par fildes soient transférées vers le périphérique de stockage associé au fichier décrit par fildes. La nature du transfert est définie par l'implémentation. La fonction fsync() ne doit pas retourner avant que le système ait terminé cette action ou avant qu'une erreur ne soit

détectée.

Si _POSIX_SYNCHRONIZED_IO est défini, la fonction fsync() doit forcer toutes les opérations d'E/S actuellement en file d'attente associées au fichier indiqué par le descripteur de fichier fildes à l'état de complétion des E/S synchronisées. Toutes les opérations d'E/S doivent être

complétées comme défini pour la complétion de
l'intégrité des fichiers en E/S synchronisées.

APPLICATIONS

La fonction fsync() devrait être utilisée par les programmes qui exigent que les modifications d'un fichier soient terminées avant de continuer ; par exemple, un programme qui contien

t une simple fonctionnalité de transaction pourrait l'utiliser pour s'assurer que toutes l

JUSTIFICATIO

N

La fonction fsync() est destinée à forcer une écriture physique des données du cache tampon, et à assurer qu'après un crash système ou une autre défaillance, toutes les données jusqu'au moment de l'appel fsync() soient enregistrées sur le disque. Puisque les concepts de « cache tampon », « crash système », « écriture physique » et « stockage non volatile » ne sont pas définis ici, la formulation doit être plus

abstraite.

Si _POSIX_SYNCHRONIZED_IO n'est pas défini, la formulation repose fortement sur le document de conformité pour indiquer à l'utilisateur ce qui peut être attendu du système. Il est explicitement prévu qu'une implémentation nulle soit autorisée. Cela pourrait être valide dans le cas où le système ne peut assurer un stockage non volatile dans aucune circonstance, ou lorsque le système est hautement tolérant aux pannes et que la fonctionnalité n'est pas requise. Dans le cas intermédiaire entre ces extrêmes, fsync() pourrait ou non causer réellement l'écriture des données à un endroit sûr contre une panne de courant. Le document de conformité devrait identifier au moins qu'une configuration existe (et comment obtenir cette configuration) où cela peut être assuré pour au moins certains fichiers que l'utilisateur peut sélectionner pour stocker des données critiques. Il n'est pas prévu qu'une liste exhaustive soit requise, mais plutôt qu'un nombre suffisant d'informations soit fourni afin que, si des données critiques doivent être sauvegardées, l'utilisateur puisse déterminer comment le système doit être configuré pour permettre l'écriture des données sur un stockage non

volatile.

Il est raisonnable d'affirmer que les aspects clés de fsync() sont déraisonnables à tester dans une suite de tests. Cela ne rend pas la fonction moins précieuse, seulement plus difficile à tester. Un test de conformité formel devrait probablement forcer un crash système (arrêt d'alimentation) pendant le test pour cette condition, mais cela doit être fait de telle sorte que les tests automatisés ne nécessitent pas cela, sauf lorsqu'un enregistrement formel des résultats est effectué. Il ne serait pas non plus déraisonnable d'omettre le test de fsync(), en le traitant comme un problème de qualité d'implémentatio
