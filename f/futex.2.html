DESCRIPTIO

N

L'appel système futex() fournit une méthode pour attendre qu'une certaine condition devienne vraie. Il est généralement utilisé comme construction bloquante dans le contexte de la synchronisation en mémoire partagée. Lors de l'utilisation des futexes, la majorité des opérations de synchronisation sont effectuées en espace utilisateur. Un programme en espace utilisateur n'emploie l'appel système futex() que lorsqu'il est probable que le programme devra se bloquer pendant un certain temps jusqu'à ce que la condition devienne vraie. D'autres opérations futex() peuvent être utilisées pour réveiller tout processus ou thread en attente d'une condition

particulière.

Un futex est une valeur de 32 bits — appelée ci-dessous mot futex — dont l'adresse est fournie à l'appel système futex(). (Les futexes font 32 bits sur toutes les plateformes, y compris les systèmes 64 bits.) Toutes les opérations de futex sont régies par cette valeur. Afin de partager un futex entre processus, le futex est placé dans une région de mémoire partagée, créée à l'aide de (par exemple) mmap(2) ou shmat(2). (Ainsi, le mot futex peut avoir des adresses virtuelles différentes dans différents processus, mais ces adresses désignent toutes le même emplacement en mémoire physique.) Dans un programme multithread, il suffit de placer le mot futex dans une variable globale partagée par tous les

threads.

Lors de l'exécution d'une opération de futex demandant de bloquer un thread, le noyau ne bloquera que si le mot futex a la valeur que le thread appelant a fournie (en tant qu'un des arguments de l'appel futex()) comme valeur attendue du mot futex. Le chargement de la valeur du mot futex, la comparaison de cette valeur avec la valeur attendue et le blocage effectif se produiront de manière atomique et seront totalement ordonnés par rapport aux opérations concurrentes effectuées par d'autres threads sur le même mot futex. Ainsi, le mot futex est utilisé pour connecter la synchronisation en espace utilisateur avec l'implémentation du blocage par le noyau. De manière analogue à une opération atomique de comparaison et échange qui modifie potentiellement la mémoire partagée, le blocage via un futex est une opération atomique de comparaison et

blocage.

Une utilisation des futexes est l'implémentation de verrous. L'état du verrou (c'est-à-dire acquis ou non acquis) peut être représenté comme un drapeau accessible de manière atomique en mémoire partagée. Dans le cas non contended, un thread peut accéder ou modifier l'état du verrou avec des instructions atomiques, par exemple en le changeant atomiquement de non acquis à acquis à l'aide d'une instruction atomique de comparaison et échange. (De telles instructions sont effectuées entièrement en mode utilisateur, et le noyau ne conserve aucune information sur l'état du verrou.) D'autre part, un thread peut être incapable d'acquérir un verrou car il est déjà acquis par un autre thread. Il peut alors passer le drapeau du verrou comme mot futex et la valeur représentant l'état acquis comme valeur attendue à une opération d'attente futex(). Cette opération futex() bloquera si et seulement si le verrou est toujours acquis (c'est-à-dire si la valeur dans le mot futex correspond toujours à l'« état acquis »). Lors du relâchement du verrou, un thread doit d'abord réinitialiser l'état du verrou à non acquis, puis exécuter une opération de futex qui réveille les threads bloqués sur le drapeau du verrou utilisé comme mot futex (cela peut être davantage optimisé pour éviter des réveils inutiles). Voir futex(7) pour plus de détails sur l'utilisation des

futexes.

En plus de la fonctionnalité de base d'attente et de réveil des futexes, il existe d'autres opérations de futex visant à prendre en charge des cas d'utilisation plus

complexes.

Notez qu'aucune initialisation ou destruction explicite n'est nécessaire pour utiliser les futexes ; le noyau ne conserve un futex (c'est-à-dire l'artefact d'implémentation interne au noyau) que pendant que des opérations telles que FUTEX_WAIT(2const) sont effectuées sur un mot futex

particulier.

Argument

s

L'argument uaddr pointe vers le mot futex. Sur toutes les plateformes, les futexes sont des entiers de quatre octets qui doivent être alignés sur une frontière de quatre octets. L'opération à effectuer sur le futex est spécifiée dans l'argument op

.

Futexes à héritage de

priorité

Linux prend en charge les futexes à héritage de priorité (PI) afin de gérer les problèmes d'inversion de priorité qui peuvent être rencontrés avec les verrous de futex normaux. L'inversion de priorité est le problème qui survient lorsqu'une tâche de haute priorité est bloquée en attendant d'acquérir un verrou détenu par une tâche de basse priorité, tandis que des tâches de priorité intermédiaire préemptent continuellement la tâche de basse priorité du CPU. Par conséquent, la tâche de basse priorité ne progresse pas vers le relâchement du verrou, et la tâche de haute priorité reste

bloquée.

L'héritage de priorité est un mécanisme pour traiter le problème d'inversion de priorité. Avec ce mécanisme, lorsqu'une tâche de haute priorité devient bloquée par un verrou détenu par une tâche de basse priorité, la priorité de la tâche de basse priorité est temporairement élevée à celle de la tâche de haute priorité, afin qu'elle ne soit pas préemptée par des tâches de niveau intermédiaire et puisse ainsi progresser vers le relâchement du verrou. Pour être efficace, l'héritage de priorité doit être transitif, ce qui signifie que si une tâche de haute priorité se bloque sur un verrou détenu par une tâche de priorité inférieure qui est elle-même bloquée par un verrou détenu par une autre tâche de priorité intermédiaire (et ainsi de suite, pour des chaînes de longueur arbitraire), alors ces deux tâches (ou plus généralement, toutes les tânes

Les verrous sont levés pour être identiques au verrou de tâche à haute priorité.

Du point de vue de l'espace utilisateur, ce qui rend un futex conscient de la PI est un accord de politique (décrit ci-dessous) entre l'espace utilisateur et le noyau concernant la valeur du mot futex, combiné à l'utilisation des opérations PI-futex décrites ci-dessous. (Contrairement aux autres opérations futex décrites ci-dessus, les opérations PI-futex sont conçues pour l'implémentation de mécanismes IPC très spécifiques.)

Les opérations PI-futex décrites ci-dessous diffèrent des autres opérations futex en ce qu'elles imposent une politique sur l'utilisation de la valeur du mot futex :

•
Si le verrou n'est pas acquis, la valeur du mot futex doit être 0.
•
Si le verrou est acquis, la valeur du mot futex doit être l'ID du thread (TID ; voir gettid(2)) du thread propriétaire.
•
Si le verrou est détenu et qu'il y a des threads en concurrence pour le verrou, alors le bit FUTEX_WAITERS doit être défini dans la valeur du mot futex ; en d'autres termes, cette valeur est :

FUTEX_WAITERS | TID

(Notez qu'il est invalide pour un mot PI-futex de n'avoir aucun propriétaire et que FUTEX_WAITERS soit défini.)

Avec cette politique en place, une application en espace utilisateur peut acquérir un verrou non acquis ou libérer un verrou à l'aide d'instructions atomiques exécutées en mode utilisateur (par exemple, une opération de comparaison et échange telle que cmpxchg sur l'architecture x86). Acquérir un verrou consiste simplement à utiliser la comparaison et échange pour définir atomiquement la valeur du mot futex à l'ID du thread appelant si sa valeur précédente était 0. Libérer un verrou nécessite d'utiliser la comparaison et échange pour définir la valeur du mot futex à 0 si la valeur précédente était l'ID du thread attendu.

Si un futex est déjà acquis (c'est-à-dire qu'il a une valeur non nulle), les attentes doivent utiliser les opérations FUTEX_LOCK_PI(2const) ou FUTEX_LOCK_PI2(2const) pour acquérir le verrou. Si d'autres threads attendent le verrou, alors le bit FUTEX_WAITERS est défini dans la valeur du futex ; dans ce cas, le propriétaire du verrou doit utiliser l'opération FUTEX_UNLOCK_PI(2const) pour libérer le verrou.

Dans les cas où les appelants sont forcés d'entrer dans le noyau (c'est-à-dire qu'ils doivent effectuer un appel futex()), ils traitent alors directement avec un prétendu RT-mutex, un mécanisme de verrouillage du noyau qui implémente les sémantiques d'héritage de priorité requises. Une fois le RT-mutex acquis, la valeur du futex est mise à jour en conséquence avant que le thread appelant ne retourne à l'espace utilisateur.

Il est important de noter que le noyau mettra à jour la valeur du mot futex avant de retourner à l'espace utilisateur. (Cela évite la possibilité que la valeur du mot futex se retrouve dans un état invalide, comme avoir un propriétaire mais une valeur de 0, ou avoir des attentes sans que le bit FUTEX_WAITERS soit défini.)

Si un futex a un RT-mutex associé dans le noyau (c'est-à-dire qu'il y a des attentes bloquées) et que le propriétaire du futex/RT-mutex meurt inopinément, alors le noyau nettoie le RT-mutex et le transmet au prochain attendant. Cela nécessite à son tour que la valeur de l'espace utilisateur soit mise à jour en conséquence. Pour indiquer que cela est requis, le noyau définit le bit FUTEX_OWNER_DIED dans le mot futex avec l'ID du thread du nouveau propriétaire. L'espace utilisateur peut détecter cette situation par la présence du bit FUTEX_OWNER_DIED et est alors responsable du nettoyage de l'état obsolète laissé par le propriétaire décédé.

Les PI futex sont opérées en spécifiant l'une des valeurs listées ci-dessous dans op. Notez que les opérations PI futex doivent être utilisées comme opérations appariées et sont soumises à certaines exigences supplémentaires :

•
FUTEX_LOCK_PI(2const), FUTEX_LOCK_PI2(2const) et FUTEX_TRYLOCK_PI(2const) s'apparient avec FUTEX_UNLOCK_PI(2const). FUTEX_UNLOCK_PI(2const) doit être appelé uniquement sur un futex détenu par le thread appelant, tel que défini par la politique de valeur, sinon l'erreur EPERM en résulte.
•
FUTEX_WAIT_REQUEUE_PI(2const) s'apparient avec FUTEX_CMP_REQUEUE_PI(2const). Cela doit être effectué d'un futex non-PI vers un futex PI distinct (ou l'erreur EINVAL en résulte). De plus, le nombre d'attentes à réveiller doit être de 1 (ou l'erreur EINVAL en résulte).

Les opérations PI futex sont les suivantes :

FUTEX_LOCK_PI(2const)
FUTEX_LOCK_PI2(2const)
FUTEX_TRYLOCK_PI(2const)
FUTEX_UNLOCK_PI(2const)
FUTEX_CMP_REQUEUE_PI(2const)
FUTEX_WAIT_REQUEUE_PI(2const)

Les FUTEX_WAIT_REQUEUE_PI(2const) et FUTEX_CMP_REQUEUE_PI(2const) ont été ajoutés pour prendre en charge un cas d'utilisation assez spécifique : le support des variables de condition POSIX conscientes de l'héritage de priorité. L'idée est que ces opérations doivent toujours être appariées, afin de garantir que l'espace utilisateur et le noyau restent synchronisés. Ainsi, dans l'opération FUTEX_WAIT_REQUEUE_PI(2const), l'application en espace utilisateur pré-spécifie la cible de la réorganisation qui a lieu dans l'opération FUTEX_CMP_REQUEUE_PI(2const).

VALEUR DE RETOUR

En cas d'erreur, -1 est retourné et errno est défini pour indiquer l'erreur.

La valeur de retour en cas de succès dépend de l'opération.

ERREURS

EACCES
Pas d'accès en lecture à la mémoire d'un mot futex.
EFAULT
uaddr ne pointe pas vers une adresse d'espace utilisateur valide.
EINVAL
uaddr ne pointe pas vers un objet valide, c'est-à-dire que l'adresse n'est pas alignée sur quatre octets.
EINVAL
Argument invalide.
ENOSYS
Opération invalide spécifiée dans op.
ENOSYS
L'option FUTEX_CLOCK_REALTIME a été spécifiée dans op, mais l'opération associée n'était ni FUTEX_WAIT_BITSET(2const), ni FUTEX_WAIT_REQUEUE_PI(2const), ni FUTEX_LOCK_PI2(2const).

EXEMPLES

Le programme ci-dessous démontre l'utilisation des futex dans un programme où un processus parent et un processus enfant utilisent une paire de futex situés dans un mapping anonyme partagé pour synchroniser l'accès à une ressource partagée : le terminal. Les deux processus écrivent chacun nloops (un argument de ligne de commande qui vaut 5 par défaut s'il est omis) messages sur le terminal et utilisent un protocole de synchronisation qui garantit qu'ils alternent dans l'écriture des messages. Lors de l'exécution de ce programme, nous voyons une sortie telle que celle-ci :


$ ./futex_demo;
Parent (18534) 0
Child  (18535) 0
Parent (18534) 1
Child  (18535) 1
Parent (18534) 2
Child  (18535) 2
Parent (18534) 3
Child  (18535) 3
Parent (18534) 4
Child  (18535) 4

Source du programme

/* futex_demo.c
   Usage: futex_demo [nloops]
                    (Défaut : 5)
   Démontre l'utilisation des futex dans un programme où le parent et l'enfant
   utilisent une paire de futex situés dans un mapping anonyme partagé pour
   synchroniser l'accès à une ressource partagée : le terminal. Les deux
   processus écrivent chacun 'num-loops' messages sur le terminal et utilisent
   un protocole de synchronisation qui garantit qu'ils alternent dans
   l'écriture des messages.
*/
#define _GNU_SOURCE
#include <err.h>
#include <errno.h>
#include <linux/futex.h>
#include <stdatomic.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <sys/mman.h>
#include <sys/syscall.h>
#include <sys/time.h>
#include <sys/wait.h>
#include <unistd.h&h>
static uint32_t *futex1, *futex2, *iaddr;
static int
futex(uint32_t *uaddr, int op, uint32_t val,
      const struct timespec *timeout, uint32_t *uaddr2, uint32_t val3)
{
    return syscall(SYS_futex, uaddr, op, val,
                   timeout, uaddr2, val3);
}
/* Acquiert le futex pointé par 'futexp' : attend que sa valeur devienne 1,
   puis définit la valeur à 0.  */
static void
fwait(uint32_t *futexp)
{
    long            s;
    const uint32_t  one = 1;
    /* atomic_compare_exchange_strong(ptr, oldval, newval)
       exécute atomiquement l'équivalent de :
           if (*ptr == *oldval)
               *ptr = newval;
       Il renvoie true si le test a été vrai et que *ptr a été mis à jour.  */
    while (1) {
        /* Le futex est-il disponible ? */
        if (atomic_compare_exchange_strong(futexp, &one, 0))
            break;      /* Oui */
        /* Le futex n'est pas disponible ; attendre.  */
        s = futex(futexp, FUTEX_WAIT, 0, NULL, NULL, 0);
        if (s == -1 && errno != EAGAIN)
            err(EXIT_FAILURE, "futex-FUTEX_WAIT");
    }
}
/* Libère le futex pointé par 'futexp' : si le futex a actuellement
   la valeur 0, définit sa valeur à 1, puis réveille les attentes du futex,
   de sorte que si le pair est bloqué dans fwait(), il puisse continuer.  */
static void
fpost(uint32_t *futexp)
{
    long            s;
    const uint32_t  zero = 0;
    /* atomic_compare_exchange_strong() a été décrit
       dans les commentaires ci-dessus.  */
    if (atomic_compare_exchange_strong(futexp, &zero, 1)) {
        s = futex(futexp, FUTEX_WAKE, 1, NULL, NULL, 0);
        if (s  == -1)
            err(EXIT_FAILURE, "futex-FUTEX_WAKE");
    }
}
int
main(int argc, char *argv[])
{
    pid_t         childPid;
    unsigned int  nloops;
    setbuf(stdout, NULL);
    nloops = (argc > 1) ? atoi(argv[1]) : 5;
    /* Créer un mapping anonyme partagé qui contiendra les futex.
       Comme les futex sont partagés entre processus, */
        nous utilisons ensuite les opérations futex « partagées » (c'est-à-dire celles qui ne se terminent pas par « _PRIVATE »). */
    iaddr = mmap(NULL, sizeof(*iaddr) * 2, PROT_READ | PROT_WRITE,
                 MAP_ANONYMOUS | MAP_SHARED, -1, 0);
    if (iaddr == MAP_FAILED)
        err(EXIT_FAILURE, "mmap");
    futex1 = &iaddr[0];
    futex2 = &iaddr[1];
    *futex1 = 0;        /* État : indisponible */
    *futex2 = 1;        /* État : disponible */
    /* Crée un processus enfant qui hérite du mappage anonyme partagé. */
    childPid = fork();
    if (childPid == -1)
        err(EXIT_FAILURE, "fork");
    if (childPid == 0) {        /* Enfant */
        for (unsigned int j = 0; j < nloops; j++) {
            fwait(futex1);
            printf("Enfant  (%jd) %u\n", (intmax_t) getpid(), j);
            fpost(futex2);
        }
        exit(EXIT_SUCCESS);
    }
    /* Le parent continue ici. */
    for (unsigned int j = 0; j < nloops; j++) {
        fwait(futex2);
        printf("Parent (%jd) %u\n", (intmax_t) getpid(), j);
        fpost(futex1);
    }
    wait(NULL);
    exit(EXIT_SUCCESS);
}
