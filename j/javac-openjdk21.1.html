NOM

javac - lit les déclarations Java et les compile en fichiers de classe

SYNTAXE

javac [options] [fichiers-source ou noms-de-classe]

options
Options en ligne de commande.
fichiers-source ou noms-de-classe
Fichiers source à compiler (par exemple, Shape.java) ou noms de classes précédemment compilées à traiter pour les annotations (par exemple, geometry.MyShape).

DESCRIPTION

La commande javac lit les fichiers source qui contiennent des déclarations de modules, de paquets et de types écrites dans le langage de programmation Java, et les compile en fichiers de classe qui s'exécutent sur la Machine Virtuelle Java.

La commande javac peut également traiter les annotations dans les fichiers source et les classes Java.

Les fichiers source doivent avoir l'extension de nom de fichier .java. Les fichiers de classe ont l'extension de nom de fichier .class. Les fichiers source et de classe ont normalement des noms de fichier qui identifient leur contenu. Par exemple, une classe appelée Shape serait déclarée dans un fichier source appelé Shape.java, et compilée en un fichier de classe appelé Shape.class.

Il existe deux façons de spécifier les fichiers source à javac:

•
Pour un petit nombre de fichiers source, vous pouvez lister leurs noms de fichier sur la ligne de commande.
•
Pour un grand nombre de fichiers source, vous pouvez utiliser l'option @nom-de-fichier sur la ligne de commande pour spécifier un fichier d'arguments qui liste leurs noms de fichier. Voir Options Standard pour une description de l'option et Fichiers d'arguments en ligne de commande pour une description des fichiers d'arguments de javac.

L'ordre des fichiers source spécifiés sur la ligne de commande ou dans un fichier d'arguments n'est pas important. javac compilera les fichiers ensemble, en groupe, et résoudra automatiquement toute dépendance entre les déclarations dans les divers fichiers source.

javac s'attend à ce que les fichiers source soient arrangés dans une ou plusieurs hiérarchies de répertoires sur le système de fichiers, décrites dans Disposition du Code Source.

Pour compiler un fichier source, javac doit trouver la déclaration de chaque classe ou interface qui est utilisée, étendue ou implémentée par le code dans le fichier source. Cela permet à javac de vérifier que le code a le droit d'accéder à ces classes et interfaces. Plutôt que de spécifier explicitement les fichiers source de ces classes et interfaces, vous pouvez utiliser des options en ligne de commande pour indiquer à javac où rechercher leurs fichiers source. Si vous avez compilé précédemment ces fichiers source, vous pouvez utiliser des options pour indiquer à javac où rechercher les fichiers de classe correspondants. Les options, qui ont toutes un nom se terminant par "path", sont décrites dans Options Standard, et plus en détail dans Configuration d'une Compilation et Recherche des Déclarations de Modules, de Paquets et de Types.

Par défaut, javac compile chaque fichier source en un fichier de classe dans le même répertoire que le fichier source. Cependant, il est recommandé de spécifier un répertoire de destination séparé avec l'option -d.

Les options en ligne de commande et les variables d'environnement contrôlent également la manière dont javac effectue diverses tâches:

•
Compiler du code pour s'exécuter sur des versions antérieures du JDK.
•
Compiler du code pour s'exécuter sous un débogueur.
•
Vérifier les problèmes stylistiques dans le code source Java.
•
Vérifier les problèmes dans les commentaires javadoc (/** ... */).
•
Traiter les annotations dans les fichiers source et les fichiers de classe.
•
Mettre à jour et patcher les modules dans l'environnement de compilation.

javac prend en charge la Compilation pour les Versions Antérieures de la Plateforme et peut également être invoqué depuis du code Java en utilisant l'une des API

OPTIONS

javac fournit des options standard et des options supplémentaires qui sont soit non standard, soit destinées à un usage avancé.

Certaines options prennent un ou plusieurs arguments. Si un argument contient des espaces ou d'autres caractères d'espacement, la valeur doit être mise entre guillemets selon les conventions de l'environnement utilisé pour invoquer javac. Si l'option commence par un tiret simple (-), l'argument doit soit suivre directement le nom de l'option, soit être séparé par un deux-points (:) ou un espace blanc, selon l'option. Si l'option commence par un double tiret (--), l'argument peut être séparé soit par un espace blanc, soit par un signe égal (=) sans espace supplémentaire. Par exemple,


-Anom="J. Duke"
-proc:only
-d monRepertoire
--module-version 3
--module-version=3

Dans les listes d'options suivantes, un argument path représente un chemin de recherche, composé d'une liste d'emplacements du système de fichiers séparés par le caractère séparateur de chemin de la plateforme (point-virgule ; sur Windows, ou deux-points : sur les autres systèmes). Selon l'option, les emplacements du système de fichiers peuvent être des répertoires, des fichiers JAR ou des fichiers JMOD.

ENVIRONMENT VARIABLES

CLASSPATH

If the --class-path option or any of its alternate forms are not specified, the class path will default to the value of the CLASSPATH environment variable if it is set. However, it is recommended that this environment variable should not be set, and that the --class-path option should be used to provide an explicit value for the class path when one is required.

JDK_JAVAC_OPTIONS

The content of the JDK_JAVAC_OPTIONS environment variable, separated by white-spaces ( ) or white-space characters (\n, \t, \r, or \f) is prepended to the command line arguments passed to javac as a list of arguments.

The encoding requirement for the environment variable is the same as the javac command line on the system. JDK_JAVAC_OPTIONS environment variable content is treated in the same manner as that specified in the command line.

Single quotes (') or double quotes (") can be used to enclose arguments that contain whitespace characters. All content between the open quote and the first matching close quote are preserved by simply removing the pair of quotes. In case a matching quote is not found, the launcher will abort with an error message. @files are supported as they are specified in the command line. However, as in @files, use of a wildcard is not supported.

Examples of quoting arguments containing white spaces:

export JDK_JAVAC_OPTIONS='@"C:\white spaces\argfile"'

export JDK_JAVAC_OPTIONS='"@C:\white spaces\argfile"'

export JDK_JAVAC_OPTIONS='@C:\"white spaces"\argfile'

COMMAND-LINE ARGUMENT FILES

An argument file can include command-line options and source file names in any combination. The arguments within a file can be separated by spaces or new line characters. If a file name contains embedded spaces, then put the whole file name in double quotation marks.

File names within an argument file are relative to the current directory, not to the location of the argument file. Wildcards (*) are not allowed in these lists (such as for specifying *.java). Use of the at sign (@) to recursively interpret files is not supported. The -J options are not supported because they're passed to the launcher, which does not support argument files.

When executing the javac command, pass in the path and name of each argument file with the at sign (@) leading character. When the javac command encounters an argument beginning with the at sign (@), it expands the contents of that file into the argument list.

ARRANGEMENT OF SOURCE CODE

In the Java language, classes and interfaces can be organized into packages, and packages can be organized into modules. javac expects that the physical arrangement of source files in directories of the file system will mirror the organization of classes into packages, and packages into modules.

It is a widely adopted convention that module names and package names begin with a lower-case letter, and that class names begin with an upper-case letter.

Arrangement of Source Code for a Package

When classes and interfaces are organized into a package, the package is represented as a directory, and any subpackages are represented as subdirectories.

For example:

•
The package p is represented as a directory called p.
•
The package p.q -- that is, the subpackage q of package p -- is represented as the subdirectory q of directory p. The directory tree representing package p.q is therefore p\q on Windows, and p/q on other systems.
•
The package p.q.r is represented as the directory tree p\q\r (on Windows) or p/q/r (on other systems).

Within a directory or subdirectory, .java files represent classes and interfaces in the corresponding package or subpackage.

For example:

•
The class X declared in package p is represented by the file X.java in the p directory.
•
The class Y declared in package p.q is represented by the file Y.java in the q subdirectory of directory p.
•
The class Z declared in package p.q.r is represented by the file Z.java in the r subdirectory of p\q (on Windows) or p/q (on other systems).

In some situations, it is convenient to split the code into separate directories, each structured as described above, and the aggregate list of directories specified to javac.

Arrangement of Source Code for a Module

In the Java language, a module is a set of packages designed for reuse. In addition to .java files for classes and interfaces, each module has a source file called module-info.java which:

1.
declares the module's name;
2.
lists the packages exported by the module (to allow reuse by other modules);
3.
lists other modules required by the module (to reuse their exported packages).

When packages are organized into a module, the module is represented by one or more directories representing the packages in the module, one of which contains the module-info.java file. It may be convenient, but it is not required, to use a single directory, named after the module, to contain the module-info.java file alongside the directory tree which represents the packages in the module (i.e., the package hierarchy described above). The exact arrangement of source code for a module is typically dictated by the conventions adopted by a development environment (IDE) or build system.

For example:

•
The module a.b.c may be represented by the directory a.b.c, on all systems.
•
The module's declaration is represented by the file module-info.java in the a.b.c directory.
•
If the module contains package p.q.r, then the a.b.c directory contains the directory tree p\q\r (on Windows) or p/q/r (on other systems).

The development environment may prescribe some directory hierarchy between the directory named for the module and the

Fichiers source à lire par javac.

Par exemple :

•
Le module a.b.c peut être représenté par le répertoire a.b.c
•
La déclaration du module et les packages du module peuvent se trouver dans un sous-répertoire de a.b.c, tel que src\main\java (sous Windows) ou src/main/java (sur d'autres systèmes).

CONFIGURER UNE COMPILATION

Cette section décrit comment configurer javac pour effectuer une compilation de base.

Voir Configurer le système de modules pour des détails supplémentaires à utiliser lors de la compilation pour une version de la plateforme qui prend en charge les modules.

Fichiers source

•
Spécifiez les fichiers source à compiler sur la ligne de commande.

S'il n'y a pas d'erreurs de compilation, les fichiers de classe correspondants seront placés dans le répertoire de sortie.

Certains systèmes peuvent limiter la taille de ce que vous pouvez mettre sur une ligne de commande ; pour contourner ces limites, vous pouvez utiliser des fichiers d'arguments.

Lors de la compilation de code pour des modules, vous pouvez également spécifier les fichiers source indirectement, en utilisant l'option --module ou -m.

Répertoire de sortie

•
Utilisez l'option -d pour spécifier un répertoire de sortie dans lequel placer les fichiers de classe compilés.

Ceci sera normalement organisé selon une hiérarchie de packages, sauf si vous compilez du code source à partir de plusieurs modules, auquel cas il sera organisé comme une hiérarchie de modules.

Une fois la compilation terminée, si vous compilez un ou plusieurs modules, vous pouvez placer le répertoire de sortie sur le chemin du module pour le lanceur Java ; sinon, vous pouvez placer le répertoire de sortie sur le chemin de classe pour le lanceur Java.

Code précompilé

Le code à compiler peut faire référence à des bibliothèques autres que celles fournies par la plateforme. Si c'est le cas, vous devez placer ces bibliothèques sur le chemin de classe ou le chemin du module. Si le code de la bibliothèque n'est pas dans un module, placez-le sur le chemin de classe ; s'il est dans un module, placez-le sur le chemin du module.

•
Utilisez l'option --class-path pour spécifier les bibliothèques à placer sur le chemin de classe. Les emplacements sur le chemin de classe doivent être organisés selon une hiérarchie de packages. Vous pouvez également utiliser des formes alternatives de l'option : -classpath ou -cp.
•
Utilisez l'option --module-path pour spécifier les bibliothèques à placer sur le chemin du module. Les emplacements sur le chemin du module doivent être soit des modules, soit des répertoires de modules. Vous pouvez également utiliser une forme alternative de l'option : -p.

Voir Configurer le système de modules pour savoir comment modifier la configuration par défaut des modules de bibliothèque.

Note : les options pour le chemin de classe et le chemin du module ne sont pas mutuellement exclusives, bien qu'il ne soit pas courant de spécifier le chemin de classe lors de la compilation de code pour un ou plusieurs modules.

Fichiers source supplémentaires

Le code à compiler peut faire référence à des types dans des fichiers source supplémentaires qui ne sont pas spécifiés sur la ligne de commande. Si c'est le cas, vous devez placer ces fichiers source sur le chemin source ou le chemin du module. Vous ne pouvez spécifier qu'une seule de ces options : si vous ne compilez pas de code pour un module, ou si vous ne compilez que du code pour un seul module, utilisez le chemin source ; si vous compilez du code pour plusieurs modules, utilisez le chemin source du module.

•
Utilisez l'option --source-path pour spécifier les emplacements des fichiers source supplémentaires qui peuvent être lus par javac. Les emplacements sur le chemin source doivent être organisés selon une hiérarchie de packages. Vous pouvez également utiliser une forme alternative de l'option : -sourcepath.
•
Utilisez l'option --module-source-path une ou plusieurs fois pour spécifier l'emplacement des fichiers source supplémentaires dans différents modules qui peuvent être lus par javac, ou lors de la compilation de fichiers source dans plusieurs modules. Vous pouvez soit spécifier les emplacements pour chaque module individuellement, soit organiser les fichiers source de manière à pouvoir spécifier les emplacements tous ensemble. Pour plus de détails, voir L'option Module Source Path.

Si vous souhaitez pouvoir faire référence à des types dans des fichiers source supplémentaires mais que vous ne voulez pas qu'ils soient compilés, utilisez l'option -implicit.

Note : si vous compilez du code pour plusieurs modules, vous devez toujours spécifier un chemin source de module, et tous les fichiers source spécifiés sur la ligne de commande doivent se trouver dans l'un des répertoires du chemin source de module, ou dans un sous-répertoire de celui-ci.

CONFIGURER LE SYSTÈME DE MODULES

Si vous souhaitez inclure des modules supplémentaires dans votre compilation, utilisez l'option --add-modules. Cela peut être nécessaire lorsque vous compilez du code qui n'est pas dans un module, ou qui est dans un module automatique, et que le code fait référence à une API dans les modules supplémentaires.

Si vous souhaitez restreindre l'ensemble des modules dans votre compilation, utilisez l'option --limit-modules. Cela peut être utile si vous souhaitez vous assurer que le code que vous compilez est capable de s'exécuter sur un système avec un ensemble limité de modules installés.

Si vous souhaitez briser l'encapsulation et spécifier que des packages supplémentaires doivent être considérés comme exportés par un module, utilisez l'option --add-exports. Cela peut être utile lors des tests en boîte blanche ; il est fortement déconseillé de s'appuyer sur l'accès à des API internes dans le code de production.

Si vous souhaitez spécifier que des packages supplémentaires doivent être considérés comme requis par un module, utilisez l'option --add-reads. Cela peut être utile lors des tests en boîte blanche ; il est fortement déconseillé de s'appuyer sur l'accès à des API internes dans le code de production.

Vous pouvez patcher du contenu supplémentaire dans n'importe quel module en utilisant l'option --patch-module. Voir [Patching a Module] pour plus de détails.

RECHERCHER DES DÉCLARATIONS DE MODULE, DE PACKAGE ET DE TYPE

Pour compiler un fichier source, le compilateur a souvent besoin d'informations sur un module ou un type, mais la déclaration ne se trouve pas dans les fichiers source spécifiés sur la ligne de commande.

javac a besoin d'informations de type pour chaquey classe ou interface utilisée, étendue ou implémentée dans le fichier source. Cela inclut les classes et interfaces non explicitement mentionnées dans le fichier source, mais qui fournissent des informations par héritage.

Par exemple, lorsque vous créez une sous-classe de java.awt.Window, vous utilisez également les classes ancêtres de Window : java.awt.Container, java.awt.Component et java.lang.Object.

Lors de la compilation du code d'un module, le compilateur doit également avoir disponible la déclaration de ce module.

Une recherche réussie peut produire un fichier de classe, un fichier source, ou les deux. Si les deux sont trouvés, vous pouvez utiliser l'option -Xprefer pour indiquer au compilateur lequel utiliser.

Si une recherche trouve et utilise un fichier source, javac compile par défaut ce fichier source. Ce comportement peut être modifié avec -implicit.

Le compilateur peut ne pas découvrir le besoin de certaines informations de type avant la fin du traitement des annotations. Lorsque les informations de type sont trouvées dans un fichier source et qu'aucune option -implicit n'est spécifiée, le compilateur affiche un avertissement indiquant que le fichier est compilé sans être soumis au traitement des annotations. Pour désactiver l'avertissement, spécifiez le fichier sur la ligne de commande (afin qu'il soit soumis au traitement des annotations) ou utilisez l'option -implicit pour spécifier si des fichiers de classe doivent être générés pour de tels fichiers source.

La manière dont javac localise les déclarations de ces types dépend de si la référence existe dans le code d'un module ou non.

Recherche dans les chemins orientés par paquets

Lors de la recherche d'un fichier source ou de classe sur un chemin composé d'emplacements orientés par paquets, javac vérifiera chaque emplacement sur le chemin tour à tour pour la présence possible du fichier. La première occurrence d'un fichier particulier masque toute occurrence ultérieure de fichiers portant le même nom. Cette occultation n'affecte aucune recherche pour les fichiers portant un nom différent. Cela peut être pratique lors de la recherche de fichiers source, qui peuvent être regroupés dans différents emplacements, tels que le code partagé, le code spécifique à la plateforme et le code généré. Cela peut également être utile lors de l'injection de versions alternatives d'un fichier de classe dans un paquet, pour le débogage ou d'autres raisons d'instrumentation. Mais cela peut aussi être dangereux, par exemple lors de la mise de versions incompatibles différentes d'une bibliothèque sur le chemin de classe.

Recherche dans les chemins orientés par modules

Avant d'analyser les chemins de modules pour les déclarations de paquets ou de types, javac analysera de manière paresseuse les chemins et emplacements suivants pour déterminer les modules qui seront utilisés dans la compilation.

•
Le chemin source des modules (voir l'option --module-source-path)
•
Le chemin pour les modules pouvant être mis à niveau (voir l'option --upgrade-module-path)
•
Les modules système (voir l'option --system)
•
Le chemin des modules utilisateur (voir l'option --module-path)

Pour tout module, la première occurrence du module lors de l'analyse masque complètement toute apparition ultérieure d'un module portant le même nom. Lors de la localisation des modules, javac est capable de déterminer les paquets exportés par le module et d'associer à chaque module un chemin orienté par paquets pour le contenu du module. Pour tout module précédemment compilé, ce chemin sera généralement une seule entrée pour un répertoire ou un fichier qui fournit une hiérarchie interne de type répertoire, telle qu'un fichier JAR. Ainsi, lors de la recherche d'un type qui se trouve dans un paquet connu pour être exporté par un module, javac peut localiser la déclaration directement et efficacement.

Recherche de la déclaration d'un module

Si le module a été précédemment compilé, la déclaration du module se trouve dans un fichier nommé module-info.class à la racine de la hiérarchie des paquets pour le contenu du module.

Si le module est l'un de ceux en cours de compilation, la déclaration du module sera soit le fichier nommé module-info.class à la racine de la hiérarchie des paquets pour le module dans le répertoire de sortie des classes, soit le fichier nommé module-info.java dans l'un des emplacements du chemin source ou du chemin source des modules pour le module.

Recherche de la déclaration d'un type lorsque la référence n'est pas dans un module

Lors de la recherche d'un type référencé dans du code qui ne se trouve pas dans un module, javac recherchera aux endroits suivants :

•
Les classes de la plateforme (ou les types dans les paquets exportés des modules de la plateforme) (Ceci concerne uniquement les fichiers de classe compilés.)
•

Lors de la recherche d'un type référencé dans le code d'un module, javac examinera la déclaration du module englobant pour déterminer si le type se trouve dans un paquet exporté par un autre module lisible par le module englobant. Si tel est le cas, javac ira simplement et directement à la définition de ce module pour trouver la définition du type requis. À moins que le module ne soit un autre des modules en cours de compilation, javac recherchera uniquement les fichiers de classe compilés. En d'autres termes, javac ne recherchera pas les fichiers source dans les modules de plateforme ou les modules sur le chemin des modules.

Si le type référencé ne se trouve pas dans un autre module lisible, javac examinera le module en cours de compilation pour tenter de trouver la déclaration du type. javac recherchera la déclaration du type comme suit :

•
Les fichiers source spécifiés sur la ligne de commande, sur le chemin source ou sur le chemin source des modules.
•
Les fichiers précédemment compilés dans le répertoire de sortie.

HIÉRARCHIES DE RÉPERTOIRES

javac suppose généralement que les fichiers source et les fichiers de classe compilés seront organisés dans une hiérarchie de répertoires du système de fichiers ou dans un type de fichier qui prend en charge une hiérarchie de répertoires interne, telle qu'un fichier JAR. Trois types de hiérarchies sont pris en charge : une *hiérarchie de paquets*, une *hiérarchie de modules* et une *hiérarchie source de modules*.

Bien que javac soit assez flexible quant à l'organisation du code source, au-delà de l'attente que le code source soit organisé en une ou plusieurs hiérarchies de paquets, et puisse généralement s'adapter aux organisations prescrites par les environnements de développement et les outils de construction, les outils Java en général, et javac et le lanceur Java en particulier, sont plus stricts quant à l'organisation des fichiers de classe compilés, et ceux-ci seront organisés en hiérarchies de paquets ou en hiérarchies de modules, selon le cas.

L'emplacement de ces hiérarchies est spécifié à javac via des options de ligne de commande, dont les noms se terminent généralement par « path », comme --source-path ou --class-path. De plus, en règle générale, les options de chemin dont le nom inclut le mot module, comme --module-path, sont utilisées pour spécifier les hiérarchies de modules, bien que certaines options de chemin liées aux modules permettent de spécifier une hiérarchie de paquets par module. Toutes les autres options de chemin sont utilisées pour spécifier les hiérarchies de paquets.

Hiérarchie de paquets

Dans une hiérarchie de paquets, les répertoires et sous-répertoires sont utilisés pour représenter les composantes du nom du paquet, le fichier source ou le fichier de classe compilé d'un type étant stocké sous forme de fichier avec une extension .java ou .class dans le répertoire le plus imbriqué.

Par exemple, dans une hiérarchie de paquets, le fichier source d'une classe com.example.MyClass sera stocké dans le fichier com/example/MyClass.java

Hiérarchie de modules

Dans une hiérarchie de modules, le premier niveau de répertoires est nommé d'après les modules de la hiérarchie ; à l'intérieur de chacun de ces répertoires, le contenu du module est organisé en hiérarchies de paquets.

Par exemple, dans une hiérarchie de modules, le fichier de classe compilé d'un type appelé com.example.MyClass dans un module appelé my.library sera stocké dans my.library/com/example/MyClass.class.

Les différents répertoires de sortie utilisés par javac (le répertoire de sortie des classes, le répertoire de sortie source et le répertoire de sortie des en-têtes natifs) seront tous organisés en hiérarchie de modules lorsque plusieurs modules sont compilés.

Hiérarchie source de modules

Bien que la source de chaque module individuel doive toujours être organisée en hiérarchie de paquets, il peut être pratique de regrouper ces hiérarchies dans une hiérarchie source de modules. Ceci est similaire à une hiérarchie de modules, à l'exception qu'il peut y avoir des répertoires intermédiaires entre le répertoire du module et le répertoire qui est la racine de la hiérarchie de paquets pour le code source du module.

TRAITEMENT DES

ANNOTATIONS

La commande javac fournit une prise en charge directe du traitement des

annotations.

L'API pour les processeurs d'annotations est définie dans les paquets javax.annotation.processing et javax.lang.model et leurs

sous-paquets.

Fonctionnement du traitement des

annotations

À moins que le traitement des annotations ne soit désactivé avec l'option -proc:none , le compilateur recherche les processeurs d'annotations disponibles. Le chemin de recherche peut être spécifié avec l'option -processorpath . Si aucun chemin n'est spécifié, le chemin de classe de l'utilisateur est utilisé. Les processeurs sont localisés au moyen de fichiers de configuration de fournisseur de service nommés META-INF/services/javax.annotation.processing.Processor sur le chemin de recherche. Ces fichiers doivent contenir les noms des processeurs d'annotations à utiliser, un par ligne. Alternativement, les processeurs peuvent être spécifiés explicitement, à l'aide de l'option -processor

.

Après avoir analysé les fichiers source et les classes sur la ligne de commande pour déterminer quelles annotations sont présentes, le compilateur interroge les processeurs pour déterminer quelles annotations ils traitent. Lorsqu'une correspondance est trouvée, le processeur est appelé. Un processeur peut revendiquer les annotations qu'il traite, au quel cas aucune tentative supplémentaire n'est faite pour trouver des processeurs pour ces annotations. Une fois toutes les annotations revendiquées, le compilateur ne recherche pas de processeurs supplémentaires

.

Si des processeurs génèrent de nouveaux fichiers source, un autre tour de traitement des annotations a lieu : les nouveaux fichiers source générés sont analysés, et les annotations sont traitées comme précédemment. Les processeurs appelés lors des tours précédents sont également appelés lors de tous les tours suivants. Cela continue jusqu'à ce que plus aucun nouveau fichier source ne soit

généré.

Après un tour où aucun nouveau fichier source n'est généré, les processeurs d'annotations sont appelés une dernière fois, pour leur donner la chance de terminer tout travail restant. Enfin, à moins que l'option -proc:only ne soit utilisée, le compilateur compile le fichier source original et tous les fichiers source

générés.

Si vous utilisez un processeur d'annotations qui génère des fichiers source supplémentaires à inclure dans la compilation, vous pouvez spécifier un module par défaut à utiliser pour les fichiers nouvellement générés, pour le cas où une déclaration de module n'est pas également générée. Dans ce cas, utilisez l'option --default-module-for-created-files

.

Environnement de compilation et environnement

d'exécution.

Les déclarations dans les fichiers source et les fichiers de classe compilés précédemment sont analysées par javac dans un environnement de compilation qui est distinct de l' environnement d'exécution utilisé pour exécuter javac lui-même. Bien qu'il y ait une similitude délibérée entre de nombreuses options javac et des options portant le même nom pour le lanceur Java, comme --class-path, --module-path, etc., il est important de comprendre qu'en général les options javac n'affectent que l'environnement dans lequel les fichiers source sont compilés, et n'affectent pas le fonctionnement de javac

lui-même.

La distinction entre l'environnement de compilation et l'environnement d'exécution est significative lorsqu'il s'agit d'utiliser des processeurs d'annotations. Bien que les processeurs d'annotations traitent des éléments (déclarations) qui existent dans l'environnement de compilation, le processeur d'annotation lui-même est exécuté dans l'environnement d'exécution. Avertit sur les opérations non vérifiées sur les types bruts. L'instruction suivante génère un avertissement rawtypes :

void countElements(List l) { ... }

L'exemple suivant ne génère pas d'avertissement rawtypes :

void countElements(List<?> l) { ... }

List est un type brut. Cependant, List<?> est un type paramétré avec un joker illimité. Comme List est une interface paramétrée, spécifiez toujours son argument de type. Dans cet exemple, l'argument formel List est spécifié avec un joker illimité (?) comme paramètre de type formel, ce qui signifie que la méthode countElements peut accepter n'importe quelle instanciation de l'interface List.

serial
Avertit sur l'absence de définition de serialVersionUID dans les classes sérialisables. Par exemple :

public class PersistentTime implements Serializable
{
  private Date time;
   public PersistentTime() {
     time = Calendar.getInstance().getTime();
   }
   public Date getTime() {
     return time;
   }
}

Le compilateur génère l'avertissement suivant :


warning: [serial] serializable class PersistentTime has no definition of
serialVersionUID

Si une classe sérialisable ne déclare pas explicitement un champ nommé serialVersionUID, l'environnement d'exécution de la sérialisation calcule une valeur serialVersionUID par défaut pour cette classe en fonction de divers aspects de la classe, comme décrit dans la spécification de sérialisation d'objets Java. Cependant, il est fortement recommandé que toutes les classes sérialisables déclarent explicitement des valeurs serialVersionUID car le processus par défaut de calcul des valeurs serialVersionUID est très sensible aux détails de la classe qui peuvent varier en fonction des implémentations du compilateur. Par conséquent, cela pourrait entraîner des exceptions InvalidClassExceptions inattendues lors de la désérialisation. Pour garantir une valeur serialVersionUID cohérente entre différentes implémentations de compilateur Java, une classe sérialisable doit déclarer une valeur serialVersionUID explicite.

Un avertissement 'this escape' est généré lorsqu'un constructeur effectue une action qui pourrait entraîner l'appel d'une méthode de sous-classe avant le retour du constructeur. Dans ce cas, la méthode de la sous-classe opérerait sur une instance incomplètement initialisée. Dans l'exemple ci-dessus, une sous-classe de MyClass qui surcharge hashCode() pour y inclure ses propres champs produirait probablement un résultat incorrect lorsqu'elle est appelée comme indiqué.

Les avertissements ne sont générés que si une sous-classe pourrait exister en dehors du module actuel (ou du package, s'il n'y a pas de module) en cours de compilation. Ainsi, par exemple, les constructeurs dans des classes finales et non publiques ne génèrent pas d'avertissements.

try
Avertit sur les problèmes liés à l'utilisation des blocs try, y compris les instructions try-with-resources. Par exemple, un avertissement est généré pour l'instruction suivante car la ressource ac déclarée dans le bloc try n'est pas utilisée :

try ( AutoCloseable ac = getResource() ) {    // do nothing}
unchecked
Donne plus de détails sur les avertissements de conversion non vérifiée qui sont imposés par la spécification du langage Java, par exemple :

List l = new ArrayList<Number>();
List<String> ls = l;       // unchecked warning

Lors de l'effacement de type, les types ArrayList<Number> et List<String> deviennent respectivement ArrayList et List.

La commande ls a le type paramétré List<String>. Lorsque la List référencée par l est assignée à ls, le compilateur génère un avertissement non vérifié. Au moment de la compilation, le compilateur et la JVM ne peuvent pas déterminer si l fait référence à un type List<String>. Dans ce cas, l ne fait pas référence à un type List<String>. Par conséquent, une pollution du tas se produit.

Une situation de pollution du tas se produit lorsque l'objet List l, dont le type statique est List<Number>, est assigné à un autre objet List, ls, qui a un type statique différent, List<String>. Cependant, le compilateur autorise toujours cette affectation. Il doit autoriser cette affectation pour préserver la compatibilité descendante avec les versions de Java SE qui ne prennent pas en charge les génériques. En raison de l'effacement de type, List<Number> et List<String> deviennent toutes deux List. Par conséquent, le compilateur autorise l'affectation de l'objet l, qui a un type brut de List, à l'objet ls.

varargs
Avertit sur l'utilisation non sécurisée des méthodes à arguments variables (varargs), en particulier celles qui contiennent des arguments non réifiables, par exemple :

public class ArrayBuilder {
  public static <T> void addToList (List<T> listArg, T... elements) {
    for (T x : elements) {
      listArg.add(x);
    }
  }
}

Un type non réifiable est un type dont les informations de type ne sont pas entièrement disponibles au moment de l'exécution.

Le compilateur génère l'avertissement suivant pour la définition de la méthode ArrayBuilder.addToList :


warning: [varargs] Possible heap pollution from parameterized vararg type T

Lorsque le compilateur rencontre une méthode varargs, il traduit le paramètre formel varargs en un tableau. Cependant, le langage de programmation Java ne permet pas la création de tableaux de types paramétrés. Dans la méthode ArrayBuilder.addToList, le compilateur traduit le paramètre formel varargs T... elements en paramètre formel T[] elements, un tableau. Cependant, en raison de l'effacement de type, le compilateur convertit le paramètre formel varargs en Object[] elements. Par conséquent, il existe une possibilité de pollution du tas.
