DESCRIPTIO

N

La commande java démarre une application Java. Elle le fait en démarrant l'Environnement d'exécution Java (JRE), en chargeant la classe spécifiée, et en appelant la méthode main() de cette classe. La méthode doit être déclarée public et static, elle ne doit retourner aucune valeur, et elle doit accepter un tableau de String comme paramètre. La déclaration de la méthode a la forme suivante

: 
public static void
main(Stri
ng[] args)

La commande java peut être utilisée pour lancer une application JavaFX en chargeant une classe qui possède soit une méthode main(), soit qui étend javafx.application.Application. Dans ce dernier cas, le lanceur construit une instance de la classe Application, appelle sa méthode init(), puis appelle la méthode start(javafx.stage.Stage)

.

Par défaut, le premier argument qui n'est pas une option de la commande java est le nom qualifié complet de la classe à appeler. Si l'option -jar est spécifiée, son argument est le nom du fichier JAR contenant les fichiers de classes et de ressources de l'application. La classe de démarrage doit être indiquée par l'en-tête de manifeste Main-Class dans son code

source.

Le JRE recherche la classe de démarrage (et les autres classes utilisées par l'application) dans trois ensembles d'emplacements : le chemin de classes d'amorçage, les extensions installées, et le chemin de classes de

l'utilisateur.

Les arguments après le nom du fichier de classe ou le nom du fichier JAR sont passés à la méthode

Les options standard sont garanties d'être prises en charge par toutes les implémentations de la Machine Virtuelle Java (JVM). Elles sont utilisées pour des actions courantes, telles que la vérification de la version du JRE, la définition du chemin de classes, l'activation de la sortie verbeuse,

Les options non standard sont des options à usage général qui sont spécifiques à la Machine Virtuelle Java HotSpot ; elles ne sont donc pas garanties d'être prises en charge par toutes les implémentations de la JVM et sont susceptibles de changer. Ces options commencent par -X

.

Les options avancées ne sont pas recommandées pour un usage courant. Ce sont des options de développement utilisées pour régler des domaines spécifiques du fonctionnement de la Machine Virtuelle Java HotSpot qui ont souvent des exigences système spécifiques et peuvent nécessiter un accès privilégié aux paramètres de configuration du système. Elles ne sont pas non plus garanties d'être prises en charge par toutes les implémentations de la JVM et sont susceptibles de changer. Les options avancées commencent par -XX

.

Pour suivre les options qui ont été dépréciées ou supprimées dans la dernière version, il existe une section nommée Options dépréciées et supprimées à la fin du

document.

Les options booléennes servent soit à activer une fonctionnalité désactivée par défaut, soit à désactiver une fonctionnalité activée par défaut. De telles options ne nécessitent pas de paramètre. Les options booléennes -XX sont activées à l'aide du signe plus (-XX:+OptionName) et désactivées à l'aide du signe moins (-XX:-OptionNa

me).

Pour les options qui nécessitent un argument, l'argument peut être séparé du nom de l'option par un espace, un deux-points (:) ou un signe égal (=), ou l'argument peut suivre directement l'option (la syntaxe exacte diffère pour chaque option). Si vous êtes censé spécifier la taille en octets, vous pouvez ne pas utiliser de suffixe, ou utiliser le suffixe k ou K pour les kilooctets (KB), m ou M pour les mégaoctets (MB), g ou G pour les gigaoctets (GB). Par exemple, pour définir la taille à 8 Go, vous pouvez spécifier soit 8g, 8192m, 8388608k, ou 8589934592 comme argument. Si vous êtes censé spécifier un pourcentage, utilisez un nombre de 0 à 1 (par exemple, spécifiez 0.25 pour 25 %)

-version:<release>

Spécifie la version de publication à utiliser pour exécuter l'application. Si la version de la commande java appelée ne répond pas à cette spécification et qu'une implémentation appropriée est trouvée sur le système, alors l'implémentation appropriée sera utilisée.

L'argument release spécifie soit la chaîne de version exacte, soit une liste de chaînes de version et de plages séparées par des espaces. Une chaîne de version est la désignation par le développeur du numéro de version sous la forme suivante : 1.x.0_u (où x est le numéro de version principal et u est le numéro de version de mise à jour). Une plage de versions est constituée d'une chaîne de version suivie d'un signe plus (+) pour désigner cette version ou les versions ultérieures, ou d'une partie d'une chaîne de version suivie d'un astérisque (*) pour désigner toute chaîne de version avec un préfixe correspondant. Les chaînes de version et les plages peuvent être combinées en utilisant un espace pour une combinaison logique OU, ou un ampersand (&) pour une combinaison logique ET de deux chaînes de version/plages. Par exemple, si l'exécution de la classe ou du fichier JAR nécessite JRE 6u13 (1.6.0_13), ou toute JRE 6 à partir de 6u10 (1.6.0_10), spécifiez ce qui suit :

-version:"1.6.0_13 1.6* & 1.6.0_10+"
Les guillemets ne sont nécessaires que s'il y a des espaces dans le paramètre release.

Pour les fichiers JAR, la préférence est de spécifier les exigences de version dans le manifeste du fichier JAR plutôt que sur la ligne de commande.

Options Non Standard

Ces options sont des options générales qui sont spécifiques à la machine virtuelle Java HotSpot.

-X

Affiche l'aide pour toutes les options -X disponibles.

-Xbatch

Désactive la compilation en arrière-plan. Par défaut, la JVM compile la méthode comme une tâche d'arrière-plan, exécutant la méthode en mode interpréteur jusqu'à ce que la compilation en arrière-plan soit terminée. Le commutateur -Xbatch désactive la compilation en arrière-plan, de sorte que la compilation de toutes les méthodes se déroule comme une tâche de premier plan jusqu'à son achèvement.

Cette option est équivalente à -XX:-BackgroundCompilation.

-Xbootclasspath:<chemin>

Spécifie une liste de répertoires, de fichiers JAR et d'archives ZIP séparés par des deux-points (:) à rechercher pour les fichiers de classe de démarrage. Ceux-ci sont utilisés à la place des fichiers de classe de démarrage inclus dans le JDK.

Ne déployez pas d'applications qui utilisent cette option pour remplacer une classe dans rt.jar, car cela viole la licence du code binaire JRE.

-Xbootclasspath/a:<chemin>

Spécifie une liste de répertoires, de fichiers JAR et d'archives ZIP séparés par des deux-points (:) à ajouter à la fin du chemin de classes de démarrage par défaut.

Ne déployez pas d'applications qui utilisent cette option pour remplacer une classe dans rt.jar, car cela viole la licence du code binaire JRE.

-Xbootclasspath/p:<chemin>

Spécifie une liste de répertoires, de fichiers JAR et d'archives ZIP séparés par des deux-points (:) à préfixer au chemin de classes de démarrage par défaut.

Ne déployez pas d'applications qui utilisent cette option pour remplacer une classe dans rt.jar, car cela viole la licence du code binaire JRE.

-Xcheck:jni

Effectue des vérifications supplémentaires pour les fonctions de l'interface Java Native Interface (JNI). Plus précisément, il valide les paramètres passés à la fonction JNI et les données de l'environnement d'exécution avant de traiter la requête JNI. Toute donnée invalide rencontrée indique un problème dans le code natif, et la JVM se terminera avec une erreur irrécupérable dans de tels cas. Attendez-vous à une dégradation des performances lorsque cette option est utilisée.

Force la compilation des méthodes lors de la première invocation. Par défaut, la JVM Client (-client) effectue 1 000 invocations de méthodes interprétées et la JVM Server (-server) effectue 10 000 invocations de méthodes interprétées pour recueillir des informations pour une compilation efficace. Spécifier le
-Xcomp désactive les invocations de méthodes interprétées pour augmenter les performances de compilation au détriment de l'efficacité.

Vous pouvez également modifier le nombre d'invocations de méthodes interprétées avant la compilation à l'aide de l'option -XX:CompileThreshold.

-Xmntaille

Définit la taille initiale et maximale (en octets) du tas pour la jeune génération (nursery). Ajoutez la lettre k ou K pour indiquer des kilo-octets, m ou M pour indiquer des méga-octets, g ou G pour indiquer des giga-octets.

La région de la jeune génération du tas est utilisée pour les nouveaux objets. Le GC est effectué dans cette région plus souvent que dans d'autres régions. Si la taille de la jeune génération est trop petite, de nombreuses collectes de garbage mineures seront effectuées. Si la taille est trop grande, seules des collectes de garbage complètes seront effectuées, ce qui peut prendre beaucoup de temps à terminer. Oracle recommande de garder la taille de la jeune génération entre la moitié et un quart de la taille totale du tas.

Les exemples suivants montrent comment définir la taille initiale et maximale de la jeune génération à 256 Mo en utilisant diverses unités :

-Xmn256m
-Xmn262144k
-Xmn268435456
Au lieu de l'option -Xmn pour définir la taille initiale et maximale du tas pour la jeune génération, vous pouvez utiliser -XX:NewSize pour définir la taille initiale et -XX:MaxNewSize pour définir la taille maximale.

-Xmstaille

Définit la taille initiale (en octets) du tas. Cette valeur doit être un multiple de 1024 et supérieure à 1 Mo. Ajoutez la lettre k ou K pour indiquer des kilo-octets, m ou M pour indiquer des méga-octets, g ou G pour indiquer des giga-octets.

Les exemples suivants montrent comment définir la taille de la mémoire allouée à 6 Mo en utilisant diverses unités :

-Xms6291456
-Xms6144k
-Xms6m
Si vous ne définissez pas cette option, la taille initiale sera la somme des tailles allouées à la vieille génération et à la jeune génération. La taille initiale du tas pour la jeune génération peut être définie à l'aide de l'option -Xmn ou de l'option -XX:NewSize.

-Xmxtaille

Spécifie la taille maximale (en octets) du pool d'allocation de mémoire. Cette valeur doit être un multiple de 1024 et supérieure à 2 Mo. Ajoutez la lettre k ou K pour indiquer des kilo-octets, m ou M pour indiquer des méga-octets, g ou G pour indiquer des giga-octets. La valeur par défaut est choisie à l'exécution en fonction de la configuration du système. Pour les déploiements serveur, -Xms et -Xmx sont souvent définis à la même valeur. Voir la section "Ergonomie" dans le *Guide de réglage du garbage collection de la machine virtuelle Java HotSpot SE* à http://docs.oracle.com/javase/8/docs/technotes/guides/vm/gctuning/index.html.

Les exemples suivants montrent comment définir la taille maximale autorisée de la mémoire allouée à 80 Mo en utilisant diverses unités :

-Xmx83886080
-Xmx81920k
-Xmx80m
L'option -Xmx est équivalente à -XX:MaxHeapSize.

-Xnoclassgc

Désactive le garbage collection (GC) des classes. Cela peut économiser du temps de GC, ce qui réduit les interruptions pendant l'exécution de l'application.

Lorsque vous spécifiez -Xnoclassgc au démarrage, les objets de classe dans l'application resteront inchangés pendant le GC et seront toujours considérés comme vivants. Cela peut entraîner une occupation de mémoire permanente plus importante qui, si elle n'est pas utilisée avec soin, provoquera une exception de manque de mémoire.

-Xprof

Profile le programme en cours d'exécution et envoie les données de profilage à la sortie standard. Cette option est fournie comme un utilitaire utile dans le développement de programmes et n'est pas destinée à être utilisée dans les systèmes de production.

-Xrs

Réduit l'utilisation des signaux du système d'exploitation par la JVM.

Les hooks de fermeture permettent une fermeture ordonnée d'une application Java en exécutant du code de nettoyage utilisateur (comme la fermeture de connexions de base de données) lors de la fermeture, même si la JVM se termine de manière abrupte.

La JVM intercepte les signaux pour implémenter les hooks de fermeture pour les terminaisons inattendues. La JVM utilise SIGHUP, SIGINT et SIGTERM pour initier l'exécution des hooks de fermeture.

La JVM utilise un mécanisme similaire pour implémenter la fonctionnalité de vidage des piles de threads à des fins de débogage. La JVM utilise SIGQUIT pour effectuer des vidages de threads.

Les applications intégrant la JVM doivent fréquemment intercepter des signaux tels que SIGINT ou SIGTERM, ce qui peut interférer avec les gestionnaires de signaux de la JVM. L'option -Xrs est disponible pour résoudre ce problème. Lorsque -Xrs est utilisée, les masques de signaux pour SIGINT, SIGTERM, SIGHUP et SIGQUIT ne sont pas modifiés par la JVM, et les gestionnaires de signaux pour ces signaux ne sont pas installés.

L'utilisation de -Xrs a deux conséquences :

•Les vidages de threads SIGQUIT ne sont pas disponibles.
•Le code utilisateur est responsable de déclencher l'exécution des hooks de fermeture, par exemple, en appelant System.exit() lorsque la JVM doit être terminée.

Options de runtime avancées

Ces options contrôlent le comportement d'exécution de la VM Java HotSpot.

-XX:+CheckEndorsedAndExtDirs

Active l'option pour empêcher la commande java d'exécuter une application Java si elle utilise le mécanisme de remplacement des normes approuvées ou le mécanisme d'extension. Cette option vérifie si une application utilise l'un de ces mécanismes en examinant les éléments suivants :
•Le
java.ext.dirs ou la propriété système java.endorsed.dirs est définie.
•Le répertoire lib/endorsed existe et n'est pas vide.
•Le répertoire lib/ext contient des fichiers JAR autres que ceux du JDK.
•Le répertoire d'extensions spécifique à la plateforme au niveau du système contient des fichiers JAR.

-XX:+DisableAttachMechanism

Active l'option qui désactive le mécanisme permettant aux outils de se connecter à la JVM. Par défaut, cette option est désactivée, ce qui signifie que le mécanisme d'attachement est activé et que vous pouvez utiliser des outils tels que jcmd, jstack, jmap et jinfo.

-XX:ErrorFile=nom_de_fichier

Spécifie le chemin et le nom du fichier dans lequel les données d'erreur sont écrites en cas d'erreur irrécupérable. Par défaut, ce fichier est créé dans le répertoire de travail actuel et nommé hs_err_pidpid.log où pid est l'identifiant du processus qui a causé l'erreur. L'exemple suivant montre comment définir le fichier journal par défaut (notez que l'identifiant du processus est spécifié comme %p) : 
-XX:ErrorFile=./hs_err_pid%p.log
L'exemple suivant montre comment définir le fichier journal d'erreurs sur /var/log/java/java_error.log : 
-XX:ErrorFile=/var/log/java/java_error.log
Si le fichier ne peut pas être créé dans le répertoire spécifié (en raison d'un espace insuffisant, d'un problème d'autorisation ou d'un autre problème), le fichier est créé dans le répertoire temporaire du système d'exploitation. Le répertoire temporaire est /tmp.

-XX:+FailOverToOldVerifier

Active le basculement automatique vers l'ancien vérificateur lorsque le nouveau vérificateur de type échoue. Par défaut, cette option est désactivée et elle est ignorée (c'est-à-dire traitée comme désactivée) pour les classes avec une version de bytecode récente. Vous pouvez l'activer pour les classes avec des versions plus anciennes de bytecode.

-XX:LargePageSizeInBytes=taille

Sur Solaris, définit la taille maximale (en octets) des grandes pages utilisées pour le tas Java. L'argument taille doit être une puissance de 2 (2, 4, 8, 16, ...). Ajoutez la lettre k ou K pour indiquer des kilo-octets, m ou M pour indiquer des méga-octets, g ou G pour indiquer des giga-octets. Par défaut, la taille est définie sur 0, ce qui signifie que la JVM choisit automatiquement la taille des grandes pages.

L'exemple suivant illustre comment définir la taille des grandes pages sur 4 méga-octets (Mo) :

-XX:LargePageSizeInBytes=4m

-XX:MaxDirectMemorySize=taille

Définit la taille totale maximale (en octets) des allocations de tampons directs de New I/O (le package java.nio). Ajoutez la lettre k ou K pour indiquer des kilo-octets, m ou M pour indiquer des méga-octets, g ou G pour indiquer des giga-octets. Par défaut, la taille est définie sur 0, ce qui signifie que la JVM choisit automatiquement la taille des allocations de tampons directs NIO.

Les exemples suivants illustrent comment définir la taille NIO sur 1024 Ko dans différentes unités :

-XX:MaxDirectMemorySize=1m
-XX:MaxDirectMemorySize=1024k
-XX:MaxDirectMemorySize=1048576

-XX:NativeMemoryTracking=mode

Spécifie le mode de suivi de l'utilisation de la mémoire native de la JVM. Les arguments de mode possibles pour cette option incluent les suivants :

off

Ne pas suivre l'utilisation de la mémoire native de la JVM. C'est le comportement par défaut si vous ne spécifiez pas l'option -XX:NativeMemoryTracking.

summary

Suivre uniquement l'utilisation de la mémoire par les sous-systèmes JVM, tels que le tas Java, la classe, le code et le thread.

detail

En plus de suivre l'utilisation de la mémoire par les sous-systèmes JVM, suivre l'utilisation de la mémoire par chaque CallSite, chaque région de mémoire virtuelle et ses régions engagées.

-XX:ObjectAlignmentInBytes=alignement

Définit l'alignement mémoire des objets Java (en octets). Par défaut, la valeur est définie sur 8 octets. La valeur spécifiée doit être une puissance de deux et doit être comprise entre 8 et 256 (inclus). Cette option permet d'utiliser des pointeurs compressés avec de grandes tailles de tas Java.

La limite de taille du tas en octets est calculée comme suit :

4 Go * ObjectAlignmentInBytes

Remarque : À mesure que la valeur d'alignement augmente, l'espace inutilisé entre les objets augmente également. Par conséquent, vous pourriez ne pas bénéficier de l'utilisation de pointeurs compressés avec de grandes tailles de tas Java.

-XX:OnError=chaîne

Définit une commande personnalisée ou une série de commandes séparées par des points-virgules à exécuter en cas d'erreur irrécupérable. Si la chaîne contient des espaces, elle doit être placée entre guillemets.

L'exemple suivant montre comment l'option -XX:OnError peut être utilisée pour exécuter la commande gcore afin de créer l'image core, et le débogueur est démarré pour se connecter au processus en cas d'erreur irrécupérable (le %p désigne le processus actuel) :

-XX:OnError="gcore %p;dbx - %p"

-XX:OnOutOfMemoryError=chaîne

Définit une commande personnalisée ou une série de commandes séparées par des points-virgules à exécuter lorsqu'une exception OutOfMemoryError est levée pour la première fois. Si la chaîne contient des espaces, elle doit être placée entre guillemets. Pour un exemple de chaîne de commande, voir la description de l'option -XX:OnError.

-XX:+PerfDataSaveToFile

Si activé, enregistre les données binaires de jstat(1) lorsque l'application Java se termine. Ces données binaires sont enregistrées dans un fichier nommé hsperfdata_<pid>, où <pid> est l'identifiant du processus de l'application Java que vous avez exécutée. Utilisez jstat pour afficher les données de performance contenues dans ce fichier comme suit : 
jstat -class file:///<chemin>/hsperfdata_<pid>
jstat -gc file:///<chemin>/hsperfdata_<pid>

-XX:+PrintCommandLineFlags

Active l'impression des indicateurs JVM sélectionnés ergonomiquement qui sont apparus sur la ligne de commande. Il peut être utile de connaître les valeurs ergonomiques définies par la JVM, telles que la taille de l'espace du tas et le collecteur de déchets sélectionné. Par défaut, cette option est désactivée et les indicateurs ne sont pas imprimés.

-XX:+PrintNMTStatistics

Active l'impression des données de suivi de la mémoire native collectées à la sortie de la JVM lorsque le suivi de la mémoire native est activé (voir -XX:NativeMemoryTracking). Par défaut, cette option est désactivée et les données de suivi de la mémoire native ne sont pas imprimées.

-XX:+RelaxAccessControlCheck

Diminue le nombre de vérifications de contrôle d'accès dans le vérificateur. Par défaut, cette option est désactivée et elle est ignorée (c'est-à-dire traitée comme désactivée) pour les classes avec une version de bytecode récente. Vous pouvez l'activer pour les classes avec des versions plus anciennes de bytecode.

-XX:+ShowMessageBoxOnError

Active l'affichage d'une boîte de dialogue lorsque la JVM rencontre une erreur irrécupérable. Cela empêche la JVM de se terminer et maintient le processus actif afin que vous puissiez y attacher un débogueur pour enquêter sur la cause de l'erreur. Par défaut, cette option est désactivée.

-XX:ThreadStackSize=taille

Définit la taille de la pile de threads (en octets). Ajoutez la lettre k ou K pour indiquer des kilo-octets, m ou M pour indiquer des méga-octets, g ou G pour indiquer des giga-octets. La valeur par défaut dépend de la plateforme :
•Linux/ARM (32 bits) : 320 Ko
•Linux/i386 (32 bits) : 320 Ko
•Linux/x64 (64 bits) : 1024 Ko
•OS X (64 bits) : 1024 Ko
•Oracle Solaris/i386 (32 bits) : 320 Ko
•Oracle Solaris/x64 (64 bits) : 1024 Ko

Les exemples suivants montrent comment définir la taille de la pile de threads sur 1024 Ko dans différentes unités :

-XX:ThreadStackSize=1m
-XX:ThreadStackSize=1024k
-XX:ThreadStackSize=1048576
Cette option est équivalente à -Xss.

-XX:+TraceClassLoading

Active le traçage des classes lors de leur chargement. Par défaut, cette option est désactivée et les classes ne sont pas tracées.

-XX:+TraceClassLoadingPreorder

Active le traçage de toutes les classes chargées dans l'ordre dans lequel elles sont référencées. Par défaut, cette option est désactivée et les classes ne sont pas tracées.

-XX:+TraceClassResolution

Active le traçage des résolutions du pool de constantes. Par défaut, cette option est désactivée et les résolutions du pool de constantes ne sont pas tracées.

-XX:+TraceClassUnloading

Active le traçage des classes lors de leur déchargement. Par défaut, cette option est désactivée et les classes ne sont pas tracées.

-XX:+TraceLoaderConstraints

Active le traçage de l'enregistrement des contraintes de chargeur. Par défaut, cette option est désactivée et l'enregistrement des contraintes de chargeur n'est pas tracé.

-XX:+UseAltSigs

Active l'utilisation de signaux alternatifs au lieu de SIGUSR1 et SIGUSR2 pour les signaux internes de la JVM. Par défaut, cette option est désactivée et les signaux alternatifs ne sont pas utilisés. Cette option est équivalente à -Xusealtsigs.

-XX:-UseBiasedLocking

Désactive l'utilisation du verrouillage biaisé. Certaines applications avec une quantité significative de synchronisation non contestée peuvent obtenir des gains de vitesse significatifs avec cet indicateur activé, tandis que les applications avec certains modèles de verrouillage peuvent connaître des ralentissements. Pour plus d'informations sur la technique de verrouillage biaisé, voir l'exemple dans le document Java Tuning White Paper à l'adresse http://www.oracle.com/technetwork/java/tuning-139912.html#section4.2.5

Par défaut, cette option est activée.

-XX:-UseCompressedOops

Désactive l'utilisation des pointeurs compressés. Par défaut, cette option est activée et les pointeurs compressés sont utilisés lorsque les tailles de tas Java sont inférieures à 32 Go. Lorsque cette option est activée, les références d'objets sont représentées par des décalages de 32 bits au lieu de pointeurs de 64 bits, ce qui augmente généralement les performances lors de l'exécution de l'application avec des tailles de tas Java inférieures à 32 Go. Cette option ne fonctionne que pour les JVM 64 bits.

Il est également possible d'utiliser des pointeurs compressés lorsque les tailles de tas Java sont supérieures à 32 Go. Voir l'option -XX:ObjectAlignmentInBytes.

-XX:+UseHugeTLBFS

Cette option pour Linux est l'équivalent de la spécification de -XX:+UseLargePages. Cette option est désactivée par défaut. Cette option pré-alloue toutes les grandes pages à l'avance, lorsque la mémoire est réservée ; par conséquent, la JVM ne peut pas agrandir ou réduire dynamiquement les zones mémoire des grandes pages ; voir -XX:UseTransparen
tHugePages si vous souhaitez ce comportement.

Pour plus d'informations, voir "Grandes pages".

-XX:+UseLargePages

Active l'utilisation de la mémoire à grandes pages. Par défaut, cette option est désactivée et la mémoire à grandes pages n'est pas utilisée.

Pour plus d'informations, voir "Grandes pages".

-XX:+UseMembar

Active l'émission de membars lors des transitions d'état des threads. Cette option est désactivée par défaut sur toutes les plateformes sauf les serveurs ARM, où elle est activée. (Il est recommandé de ne pas désactiver cette option sur les serveurs ARM.)

-XX:+UsePerfData

Active la fonctionnalité perfdata. Cette option est activée par défaut pour permettre la surveillance et les tests de performance de la JVM. Sa désactivation supprime la création des répertoires hsperfdata_userid. Pour désactiver la fonctionnalité perfdata, spécifiez -XX:-UsePerfData.

-XX:+UseTransparentHugePages

Sous Linux, active l'utilisation de grandes pages qui peuvent croître ou rétrécir dynamiquement. Cette option est désactivée par défaut. Vous pourriez rencontrer des problèmes de performance avec les pages transparentes volumineuses, car le système d'exploitation déplace d'autres pages pour créer des pages volumineuses ; cette option est disponible pour des expérimentations.

Pour plus d'informations, voir "Grandes pages".

-XX:+AllowUserSignalHandlers

Permet l'installation de gestionnaires de signaux par l'application. Par défaut, cette option est désactivée et l'application n'est pas autorisée à installer de gestionnaires de signaux.

Options avancées du compilateur JIT

Ces options contrôlent la compilation dynamique juste-à-temps (JIT) effectuée par la VM Java HotSpot.

-XX:+AggressiveOpts

Active l'utilisation de fonctionnalités d'optimisation de performance agressives, qui devraient devenir par défaut dans les prochaines versions. Par défaut, cette option est désactivée et les fonctionnalités de performance expérimentales ne sont pas utilisées.

-XX:AllocateInstancePrefetchLines=lignes

Définit le nombre de lignes à précharger avant le pointeur d'allocation d'instance. Par défaut, le nombre de lignes à précharger est défini sur 1 : 
-XX:AllocateInstancePrefetchLines=1
Seule la VM serveur Java HotSpot prend en charge cette option.

-XX:AllocatePrefetchDistance=taille

Définit la taille (en octets) de la distance de préchargement pour l'allocation d'objets. La mémoire qui sera écrite avec la valeur de nouveaux objets est préchargée jusqu'à cette distance en commençant par l'adresse du dernier objet alloué. Chaque thread Java a son propre point d'allocation.

Les valeurs négatives indiquent que la distance de préchargement est choisie en fonction de la plateforme. Les valeurs positives sont les octets à précharger. Ajoutez la lettre k ou K pour indiquer des kilooctets, m ou M pour indiquer des mégaoctets, g ou G pour indiquer des gigaoctets. La valeur par défaut est définie sur -1.

L'exemple suivant montre comment définir la distance de préchargement à 1024 octets :

-XX:AllocatePrefetchDistance=1024
Seule la VM serveur Java HotSpot prend en charge cette option.

-XX:AllocatePrefetchInstr=instruction

Définit l'instruction de préchargement pour précharger avant le pointeur d'allocation. Seule la VM serveur Java HotSpot prend en charge cette option. Les valeurs possibles sont de 0 à 3. Les instructions réelles derrière les valeurs dépendent de la plateforme. Par défaut, l'instruction de préchargement est définie sur 0 : 
-XX:AllocatePrefetchInstr=0
Seule la VM serveur Java HotSpot prend en charge cette option.

-XX:AllocatePrefetchLines=lignes

Définit le nombre de lignes de cache à charger après la dernière allocation d'objet en utilisant les instructions de préchargement générées dans le code compilé. La valeur par défaut est 1 si le dernier objet alloué était une instance, et 3 s'il s'agissait d'un tableau.

L'exemple suivant montre comment définir le nombre de lignes de cache chargées à 5 :

-XX:AllocatePrefetchLines=5
Seule la VM serveur Java HotSpot prend en charge cette option.

-XX:AllocatePrefetchStepSize=taille

Définit la taille du pas (en octets) pour les instructions de préchargement séquentielles. Ajoutez la lettre k ou K pour indiquer des kilooctets, m ou M pour indiquer des mégaoctets, g ou G pour indiquer des gigaoctets. Par défaut, la taille du pas est définie sur 16 octets : 
-XX:AllocatePrefetchStepSize=16
Seule la VM serveur Java HotSpot prend en charge cette option.

-XX:AllocatePrefetchStyle=style

Définit le style de code généré pour les instructions de préchargement. L'argument style est un entier de 0 à 3 :

0

Ne génère pas d'instructions de préchargement.

1

Exécute des instructions de préchargement après chaque allocation. C'est le paramètre par défaut.

2

Utilise le pointeur de filigrane du bloc d'allocation local au thread (TLAB) pour déterminer quand les instructions de préchargement sont exécutées.

3

Utilise l'instruction BIS sur SPARC pour le préchargement d'allocation.

Seule la VM serveur Java HotSpot prend en charge cette option.

-XX:+BackgroundCompilation

Active la compilation en arrière-plan. Cette option est activée par défaut. Pour désactiver la compilation en arrière-plan, spécifiez -XX:-BackgroundCompilation (ce qui équivaut à spécifier -Xbatch).

-XX:CICompilerCount=threads

Définit le nombre de threads de compilateur à utiliser pour la compilation. Par défaut, le nombre de threads est défini sur 2 pour la JVM serveur, sur 1 pour la JVM client, et il s'adapte au nombre de cœurs si la compilation hiérarchisée est utilisée. L'exemple suivant montre comment définir le nombre de threads à 2 : 
-XX:CICompilerCount=2

-XX:CodeCacheMinimumFreeSpace=taille

Définit l'espace libre minimum (en octets) requis pour la compilation. Ajoutez la lettre k ou K pour indiquer des kilooctets, m ou M pour indiquer des mégaoctets, g ou G pour indiquer des gigaoctets. Lorsqu'il reste moins que l'espace libre minimum, la compilation s'arrête. Par défaut, cette option est définie sur 500 Ko. L'exemple suivant montre comment définir l'espace libre minimum sur 1024 Mo : 
-XX:CodeCacheMinimumFreeSpace=1024m

-XX:CompileCommand=commande,méthode[,option]

Spécifie une commande à exécuter sur une méthode. Par exemple, pour exclure la méthode indexOf() de la classe String de la compilation, utilisez ce qui suit : 
-XX:CompileCommand=exclude,java/lang/String.indexOf
Notez que le nom de classe complet est spécifié, y compris tous les packages et sous-packages séparés par une barre oblique (/). Pour faciliter les opérations de copier-coller, il est également possible d'utiliser le format de nom de méthode produit par les options -XX:+PrintCompilation et -XX:+LogCompilation : 
-XX:CompileCommand=exclude,java.lang.String::indexOf
Si la méthode est spécifiée sans la signature, la commande sera appliquée à toutes les méthodes portant le nom spécifié. Cependant, vous pouvez également spécifier la signature de la méthode au format du fichier de classe. Dans ce cas, vous devez entourer les arguments de guillemets, car sinon le shell traite le point-virgule comme la fin de la commande. Par exemple, si vous souhaitez exclure uniquement la méthode indexOf(String) de la classe String de la compilation, utilisez ce qui suit : 
-XX:CompileCommand="exclude,java/lang/String.indexOf,(Ljava/lang/String;)I"
Vous pouvez également utiliser l'astérisque (*) comme caractère générique pour les noms de classe et de méthode. Par exemple, pour exclure toutes les méthodes indexOf() dans toutes les classes de la compilation, utilisez ce qui suit : 
-XX:CompileCommand=exclude,*.indexOf
Les virgules et les points sont des alias pour des espaces, ce qui facilite le passage des commandes de compilation via un shell. Vous pouvez passer des arguments à -XX:CompileCommand en utilisant des espaces comme séparateurs en entourant l'argument de guillemets : 
-XX:CompileCommand="exclude java/lang/String indexOf"
Notez qu'après l'analyse des commandes passées sur la ligne de commande à l'aide des options -XX:CompileCommand, le compilateur JIT lit ensuite les commandes du fichier .hotspot_compiler. Vous pouvez ajouter des commandes à ce fichier ou spécifier un fichier différent à l'aide de l'option -XX:CompileCommandFile.

Pour ajouter plusieurs commandes, spécifiez l'option -XX:CompileCommand plusieurs fois, ou séparez chaque argument par le séparateur de nouvelle ligne (\n). Les commandes suivantes sont disponibles :

break

Définit un point d'arrêt lors du débogage de la JVM pour s'arrêter au début de la compilation de la méthode spécifiée.

compileonly

Exclut toutes les méthodes de la compilation à l'exception de la méthode spécifiée. Alternativement, vous pouvez utiliser l'option -XX:CompileOnly, qui permet de spécifier plusieurs méthodes.

dontinline

Empêche l'inlining de la méthode spécifiée.

exclude

Exclut la méthode spécifiée de la compilation.

help

Affiche un message d'aide pour l'option -XX:CompileCommand.

inline

Tente d'inliner la méthode spécifiée.

log

Exclut la journalisation de la compilation (avec l'option -XX:+LogCompilation) pour toutes les méthodes sauf la méthode spécifiée. Par défaut, la journalisation est effectuée pour toutes les méthodes compilées.

option

Cette commande peut être utilisée pour passer une option de compilation JIT à la méthode spécifiée à la place du dernier argument (option). L'option de compilation est définie à la fin, après le nom de la méthode. Par exemple, pour activer l'option BlockLayoutByFrequency pour la méthode append() de la classe StringBuffer, utilisez ce qui suit : 
-XX:CompileCommand=option,java/lang/StringBuffer.append,BlockLayoutByFrequency
Vous pouvez spécifier plusieurs options de compilation, séparées par des virgules ou des espaces.

print

Affiche le code assembleur généré après la compilation de la méthode spécifiée.

quiet

N'affiche pas les commandes de compilation. Par défaut, les commandes que vous spécifiez avec l'option -XX:CompileCommand sont affichées ; par exemple, si vous excluez de la compilation la méthode indexOf() de la classe String, alors ce qui suit sera affiché sur la sortie standard :

Permet l'impression des horodatages à chaque GC. Par défaut, cette option est désactivée.

-XX:+PrintStringDeduplicationStatistics

Affiche des statistiques de déduplication détaillées. Par défaut, cette option est désactivée. Voir l'option -XX:+UseStringDeduplication.

-XX:+PrintTenuringDistribution

Permet l'impression des informations d'âge de promotion. Voici un exemple de sortie : 
Taille souhaitée des survivants 48286924 octets, nouveau seuil 10 (max 10)
- âge 1 : 28992024 octets, 28992024 total
- âge 2 : 1366864 octets, 30358888 total
- âge 3 : 1425912 octets, 31784800 total
...
Les objets d'âge 1 sont les survivants les plus jeunes (ils ont été créés après le dernier vidage, ont survécu au dernier vidage et ont été déplacés de l'espace Eden vers l'espace survivant). Les objets d'âge 2 ont survécu à deux vidages (lors du deuxième vidage, ils ont été copiés d'un espace survivant à l'autre). Et ainsi de suite.

Dans l'exemple précédent, 28 992 024 octets ont survécu à un vidage et ont été copiés d'Eden vers l'espace survivant, 1 366 864 octets sont occupés par des objets d'âge 2, etc. La troisième valeur de chaque ligne est la taille cumulative des objets d'âge n ou moins.

Par défaut, cette option est désactivée.

-XX:+ScavengeBeforeFullGC

Active le GC de la jeune génération avant chaque GC complet. Cette option est activée par défaut. Oracle recommande de *ne pas* la désactiver, car le vidage de la jeune génération avant un GC complet peut réduire le nombre d'objets joignables de l'ancien espace de génération vers le jeune espace de génération. Pour désactiver le GC de la jeune génération avant chaque GC complet, spécifiez -XX:-ScavengeBeforeFullGC.

-XX:SoftRefLRUPolicyMSPerMB=temps

Définit la durée (en millisecondes) pendant laquelle un objet faiblement accessible est conservé actif dans le tas après la dernière référence. La valeur par défaut est une seconde de durée de vie par mégaoctet libre dans le tas. L'option -XX:SoftRefLRUPolicyMSPerMB accepte des valeurs entières représentant des millisecondes par mégaoctet de taille de tas actuelle (pour Java HotSpot Client VM) ou de taille de tas maximale possible (pour Java HotSpot Server VM). Cette différence signifie que la VM Client a tendance à vider les références douces plutôt qu'à augmenter la taille du tas, tandis que la VM Server a tendance à augmenter la taille du tas plutôt qu'à vider les références douces. Dans ce dernier cas, la valeur de l'option -Xmx a un effet significatif sur la rapidité avec laquelle les références douces sont collectées par le garbage collector.

L'exemple suivant montre comment définir la valeur à 2,5 secondes :

-XX:SoftRefLRUPolicyMSPerMB=2500

-XX:StringDeduplicationAgeThreshold=seuil

Les objets String atteignant l'âge spécifié sont considérés comme des candidats à la déduplication. L'âge d'un objet est une mesure du nombre de fois où il a survécu à la collecte de garbage. Ceci est parfois appelé promotion ; voir l'option -XX:+PrintTenuringDistribution. Notez que les objets String qui sont promus dans une région de tas ancienne avant que cet âge ne soit atteint sont toujours considérés comme des candidats à la déduplication. La valeur par défaut pour cette option est 3. Voir l'option -XX:+UseStringDeduplication.

-XX:SurvivorRatio=ratio

Définit le rapport entre la taille de l'espace Eden et la taille de l'espace survivant. Par défaut, cette option est définie sur 8. L'exemple suivant montre comment définir le rapport d'espace Eden/survivant à 4 : 
-XX:SurvivorRatio=4

-XX:TargetSurvivorRatio=pourcentage

Définit le pourcentage souhaité de l'espace survivant (0 à 100) utilisé après la collecte de garbage de la jeune génération. Par défaut, cette option est définie sur 50 %.

L'exemple suivant montre comment définir le rapport d'espace survivant cible à 30 % :

-XX:TargetSurvivorRatio=30

-XX:TLABSize=taille

Définit la taille initiale (en octets) d'un tampon d'allocation local au thread (TLAB). Ajoutez la lettre k ou K pour indiquer des kilo-octets, m ou M pour indiquer des méga-octets, g ou G pour indiquer des giga-octets. Si cette option est définie sur 0, la JVM choisit la taille initiale automatiquement.

L'exemple suivant montre comment définir la taille initiale du TLAB à 512 Ko :

-XX:TLABSize=512k

-XX:+UseAdaptiveSizePolicy

Permet l'utilisation du dimensionnement adaptatif des générations. Cette option est activée par défaut. Pour désactiver le dimensionnement adaptatif des générations, spécifiez -XX:-UseAdaptiveSizePolicy et définissez explicitement la taille du pool d'allocation de mémoire (voir l'option -XX:SurvivorRatio).

-XX:+UseCMSInitiatingOccupancyOnly

Permet d'utiliser la valeur d'occupation comme seul critère pour initier le collecteur CMS. Par défaut, cette option est désactivée et d'autres critères peuvent être utilisés.

-XX:+UseConcMarkSweepGC

Permet l'utilisation du collecteur de garbage Concurrent Mark Sweep (CMS) pour l'ancienne génération. Oracle recommande d'utiliser le collecteur CMS lorsque les exigences de latence de l'application ne peuvent pas être satisfaites par le collecteur de garbage à débit (-XX:+UseParallelGC). Le collecteur G1 (-XX:+UseG1GC) est une autre alternative.

Par défaut, cette option est désactivée et le collecteur est choisi automatiquement en fonction de la configuration de la machine et du type de la JVM. Lorsque cette option est activée, l'option -XX:+UseParNewGC est automatiquement définie et vous ne devez pas la désactiver, car la combinaison d'options suivante a été dépréciée dans JDK 8 : -XX:+UseConcMarkSweepGC -XX:-UseParNewGC.

-XX:+UseG1GC

Permet l'utilisation du collecteur de garbage Garbage-First (G1). C'est un collecteur de garbage de style serveur, ciblant les machines multiprocesseurs avec une grande quantité de RAM. Il répond aux objectifs de temps de pause du GC avec une forte probabilité, tout en maintenant un bon débit. Le collecteur G1 est recommandé pour les applications nécessitant de grands tas (tailles d'environ 6 Go ou plus) avec des exigences de latence GC limitées (temps de pause stable et prévisible inférieur à 0,5 seconde).

Par défaut, cette option est désactivée et le collecteur est choisi automatiquement en fonction de la configuration de la machine et du type de la JVM.

-XX:+UseGCOverheadLimit

Permet l'utilisation d'une politique qui limite la proportion de temps passé par la JVM sur le GC avant qu'une exception OutOfMemoryError ne soit levée. Cette option est activée par défaut et le GC parallèle lèvera une OutOfMemoryError si plus de 98 % du temps total est passé sur la collecte de garbage et moins de 2 % du tas est récupéré. Lorsque le tas est petit, cette fonctionnalité peut être utilisée pour empêcher les applications de s'exécuter pendant de longues périodes avec peu ou pas de progrès. Pour désactiver cette option, spécifiez -XX:-UseGCOverheadLimit.

-XX:+UseNUMA

Permet l'optimisation des performances d'une application sur une machine avec une architecture mémoire non uniforme (NUMA) en augmentant l'utilisation par l'application de la mémoire à latence plus faible. Par défaut, cette option est désactivée et aucune optimisation pour NUMA n'est effectuée. L'option n'est disponible que lorsque le collecteur de garbage parallèle est utilisé (-XX:+UseParallelGC).

-XX:+UseParallelGC

Permet l'utilisation du collecteur de garbage parallèle (également connu sous le nom de collecteur à débit) pour améliorer les performances de votre application en tirant parti de plusieurs processeurs.

Par défaut, cette option est désactivée et le collecteur est choisi automatiquement en fonction de la configuration de la machine et du type de la JVM. Si elle est activée, l'option -XX:+UseParallelOldGC est automatiquement activée, sauf si vous la désactivez explicitement.

-XX:+UseParallelOldGC

Permet l'utilisation du collecteur de garbage parallèle pour les GC complets. Par défaut, cette option est désactivée. Son activation active automatiquement l'option -XX:+UseParallelGC.

-XX:+UseParNewGC

Permet l'utilisation de threads parallèles pour la collecte dans la jeune génération. Par défaut, cette option est désactivée. Elle est automatiquement activée lorsque vous définissez l'option -XX:+UseConcMarkSweepGC. L'utilisation de l'option -XX:+UseParNewGC sans l'option -XX:+UseConcMarkSweepGC a été dépréciée dans JDK 8.

-XX:+UseSerialGC

Permet l'utilisation du collecteur de garbage série. C'est généralement le meilleur choix pour les applications petites et simples qui ne nécessitent aucune fonctionnalité spéciale de la part de la collecte de garbage. Par défaut, cette option est désactivée et le collecteur est choisi automatiquement en fonction de la configuration de la machine et du type de la JVM.

-XX:+UseSHM

Sous Linux, permet à la JVM d'utiliser la mémoire partagée pour configurer de grandes pages.

Pour plus d'informations, voir « Grandes pages ».

-XX:+UseStringDeduplication

Permet la déduplication des chaînes. Par défaut, cette option est désactivée. Pour utiliser cette option, vous devez activer le collecteur de garbage Garbage-First (G1). Voir l'option -XX:+UseG1GC.

La déduplication des chaînes réduit l'empreinte mémoire des objets String sur le tas Java en profitant du fait que de nombreux objets String sont identiques. Au lieu que chaque objet String pointe vers son propre tableau de caractères, les objets String identiques peuvent pointer et partager le même tableau de caractères.

-XX:+UseTLAB

Permet l'utilisation de blocs d'allocation locaux aux threads (TLAB) dans l'espace de la jeune génération. Cette option est activée par défaut. Pour désactiver l'utilisation des TLAB, spécifiez -XX:-UseTLAB.

NOM

java - interface Java.

SYNTAXE

DESCRIPTION

Le programme java lance une application Java. Il interprète ou compile (just-in-time) les fichiers de classe Java compilés, qui sont généralement fournis sous forme de fichiers.class ou de fichiers .jar.

Il existe deux façons de lancer une application Java avec la commande java:

1. Nom de la classe : spécifiez le nom de la classe principale qui contient la méthode main. Par exemple :

java MyApp

2. Fichier jar : spécifiez l'option -jar suivie du nom du fichier jar. Par exemple :

java -jar MyApp.jar

La spécification du nom de la classe principale dans la ligne de commande est facultative si le fichier manifest du fichier jar contient une ligne Main-Class.

Les options Java commencent toutes par -, suivies d'une lettre ou de deux, puis de ce qui suit. Les options Java sensibles à la casse sont : -X. Les options non standard sont préfixées par -. Les options standard sont préfixées par -.

GRANDES PAGES

Aussi connues sous le nom de pages énormes, les grandes pages sont des pages mémoire beaucoup plus grandes que la taille de page mémoire standard (qui varie en fonction du processeur et du système d'exploitation). Les grandes pages optimisent les tampons de traduction (Translation-Lookaside Buffers) du processeur.

Un tampon de traduction (TLB) est un cache de traduction de page qui contient les traductions d'adresse virtuelle-physique les plus récemment utilisées. Le TLB est une ressource système rare. Une absence de TLB peut être coûteuse car le processeur doit alors lire dans la table de pages hiérarchique, ce qui peut nécessiter plusieurs accès mémoire. En utilisant une taille de page mémoire plus grande, une seule entrée TLB peut représenter une plage mémoire plus grande. La pression sur le TLB sera moindre et les applications gourmandes en mémoire peuvent avoir de meilleures performances.

Cependant, la mémoire de grandes pages peut affecter négativement les performances du système. Par exemple, lorsqu'une grande quantité de mémoire est épinglée par une application, cela peut créer une pénurie de mémoire régulière et entraîner un pagination excessive chez d'autres applications, ralentissant ainsi l'ensemble du système. De plus, un système en cours d'exécution depuis longtemps pourrait produire une fragmentation excessive, qui pourrait rendre impossible la réservation de suffisamment de mémoire de grandes pages. Lorsque cela se produit, soit le système d'exploitation, soit la JVM revient à l'utilisation de pages régulières.

Support des grandes pages

Solaris et Linux prennent en charge les grandes pages.

Solaris

Solaris 9 et versions ultérieures incluent le support de tailles multiples de pages (MPSS) ; aucune configuration supplémentaire n'est nécessaire. Voir http://www.oracle.com/technetwork/server-storage/solaris10/overview/solaris9-features-scalability-135663.html.

Linux

Le noyau 2.6 prend en charge les grandes pages. Certains fournisseurs ont rétrofitté le code pour leurs versions basées sur le noyau 2.4. Pour vérifier si votre système peut prendre en charge la mémoire de grandes pages, essayez ce qui suit :

# cat /proc/meminfo | grep Huge
HugePages_Total: 0
HugePages_Free: 0
Hugepagesize: 2048 kB

Si la sortie affiche les trois variables "Huge", votre système peut prendre en charge la mémoire de grandes pages mais elle doit être configurée. Si la commande n'affiche rien, votre système ne prend pas en charge les grandes pages. Pour configurer le système afin d'utiliser la mémoire de grandes pages, connectez-vous en tant que root, puis suivez ces étapes :

1.Si vous utilisez l'option -XX:+UseSHM (au lieu de -XX:+UseHugeTLBFS), augmentez la valeur SHMMAX. Elle doit être supérieure à la taille du tas Java. Sur un système avec 4 Go de RAM physique (ou moins), ce qui suit rendra toute la mémoire partageable : 
# echo 4294967295 > /proc/sys/kernel/shmmax
2.Si vous utilisez l'option -XX:+UseSHM ou -XX:+UseHugeTLBFS, spécifiez le nombre de grandes pages. Dans l'exemple suivant, 3 Go d'un système de 4 Go sont réservés pour les grandes pages (en supposant une taille de grande page de 2048 Ko, alors 3 Go = 3 * 1024 Mo = 3072 Mo = 3072 * 1024 Ko = 3145728 Ko et 3145728 Ko / 2048 Ko = 1536) : 
# echo 1536 > /proc/sys/vm/nr_hugepages

Note
4 • Notez que les valeurs contenues dans /proc seront réinitialisées après le redémarrage de votre système, vous voudrez donc peut-être les définir dans un script d'initialisation (par exemple, rc.local ou sysctl.conf). 4 • Si vous configurez (ou redimensionnez) les paramètres du noyau du système d'exploitation /proc/sys/kernel/shmmax ou /proc/sys/vm/nr_hugepages, les processus Java peuvent allouer de grandes pages pour des zones en plus du tas Java. Ces étapes peuvent allouer de grandes pages pour les zones suivantes : 4 • Tas Java 4 • Cache de code 4 • La structure de données de bitmap de marquage pour le GC parallèle Par conséquent, si vous configurez le paramètre nr_hugepages à la taille du tas Java, la JVM peut échouer lors de l'allocation des zones de cache de code car ces zones sont de grande taille.
