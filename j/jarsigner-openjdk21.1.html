DESCRIPTIO

N

L'outil jarsigner a deux objectifs

:
•
Signer les fichiers Java Archive (JAR)
.
•
Vérifier les signatur
es et l'intégrité des
fichiers JAR signés.

La fonctionnalité JAR permet d'empaqueter des fichiers de classes, des images, des sons et d'autres données numériques dans un seul fichier pour une distribution plus rapide et plus facile. Un outil nommé jar permet aux développeurs de produire des fichiers JAR. (Techniquement, tout fichier ZIP peut aussi être considéré comme un fichier JAR, bien que, lorsqu'il est créé par la commande jar ou traité par la commande jarsigner, les fichiers JAR contiennent également un fichier META-INF/MANIFEST.MF.

)

Une signature numérique est une chaîne de bits calculée à partir de certaines données (les données étant signées) et de la clé privée d'une entité (une personne, une entreprise, etc.). De même qu'une signature manuscrite, une signature numérique possède de nombreuses caractéristiques utiles

:
•
Son authenticité peut être vérifiée par un calcul utilisant la clé publique correspondant à la clé privée utilisée pour générer la
signature.
•
Elle ne peut pas être falsifiée, à condition que la clé privée reste
secrète.
•
Elle est une fonction des données signées et ne peut donc pas être revendiquée comme la signature d'autres données
également.
•
Les données signées ne peuvent pas être modifiées.
Si les données sont modifiées, alors la sign
ature ne peut pas être vérifiée comme authentique.

Pour générer la signature d'une entité pour un fichier, l'entité doit d'abord avoir une paire de clés publique/privée associée à elle et un ou plusieurs certificats qui authentifient sa clé publique. Un certificat est une déclaration numériquement signée par une entité indiquant que la clé publique d'une autre entité a une valeur

particulière.

La commande jarsigner utilise les informations de clés et de certificats d'un magasin de clés pour générer des signatures numériques pour les fichiers JAR. Un magasin de clés est une base de données de clés privées et de leurs chaînes de certificats X.509 associées qui authentifient les clés publiques correspondantes. La commande keytool est utilisée pour créer et administrer les magasins de

clés.

La commande jarsigner utilise la clé privée d'une entité pour générer une signature. Le fichier JAR signé contient, entre autres, une copie du certificat du magasin de clés pour la clé publique correspondant à la clé privée utilisée pour signer le fichier. La commande jarsigner peut vérifier la signature numérique du fichier JAR signé en utilisant le certificat qu'il contient (dans son fichier de bloc de signature)

.

La commande jarsigner peut générer des signatures incluant un horodatage permettant à un système ou à un déployeur de vérifier si le fichier JAR a été signé alors que le certificat de signature était encore

valide.

De plus, des API permettent aux applications d'obtenir les informations

d'horodatage.

Pour l'instant, la commande jarsigner ne peut signer que des fichiers JAR créés par la commande jar ou des fichiers zip. Les fichiers JAR sont identiques aux fichiers zip, sauf qu'ils contiennent également un fichier META-INF/MANIFEST.MF. Un fichier META-INF/MANIFEST.MF est créé lorsque la commande jarsigner signe un fichier

zip.

Le comportement par défaut de la commande jarsigner est de signer un fichier JAR ou zip. Utilisez l'option -verify pour vérifier un fichier JAR

signé.

La commande jarsigner tente également de valider le certificat du signataire après la signature ou la vérification. Lors de la validation, elle vérifie l'état de révocation de chaque certificat dans la chaîne de certificats du signataire lorsque l'option -revCheck est spécifiée. S'il y a une erreur de validation ou tout autre problème, la commande génère des messages d'avertissement. Si vous spécifiez l'option -strict, la commande traite les avertissements graves comme des erreurs. Voir Erreurs et av

ertisse
ments.

ALIAS DU MAGASIN DE

CLÉS

Toutes les entités du magasin de clés sont accessibles avec des alias

uniques.

Lorsque vous utilisez la commande jarsigner pour signer un fichier JAR, vous devez spécifier l'alias de l'entrée du magasin de clés contenant la clé privée nécessaire pour générer la signature. Si aucun fichier de sortie n'est spécifié, il remplace le fichier JAR original par le fichier JAR

signé.

Les magasins de clés sont protégés par un mot de passe, le mot de passe du magasin doit donc être spécifié. Il vous est demandé si vous ne le spécifiez pas sur l

a ligne de commande. De même, les clés privées sont protégées dans un magasin de clés par un mot de passe, le mot de passe de la clé privée doit donc être spé
cifié, et le mot de passe vous est demandé lorsque vous ne le spécifiez pas sur la ligne de commande et qu'il n'est pas identique au mot de passe du magasin.

EMPLACEMENT DU MAGASIN DE

CLÉS

La commande jarsigner a une option -keystore pour spécifier l'URL du magasin de clés à utiliser. Le magasin de clés est par défaut stocké dans un fichier nommé .keystore dans le répertoire personnel de l'utilisateur, tel que déterminé par la propriété système user.

home.

Linux et macOS : user.home correspond par défaut au répertoire personnel de

l'utilisateur.

Le flux d'entrée de l'option -keystore est transmis à la méthode KeyStore.load. Si NONE est spécifié comme

URL, un flux nul est transmis à la méthode KeyStore.load. NONE doit être spécifié lorsque la classe KeyS
tore n'est pas basée sur des fichiers, par exemple lorsqu'elle réside sur un périphérique à jeton matériel.

IMPLÉMENTATION DU MAGASIN DE

CLÉS

La classe KeyStore fournie dans le paquet java.security fournit un certain nombre d'interfaces bien définies pour accéder et modifier les informations dans un magasin de clés. Vous pouvez avoir plusieurs implémentations concrètes différentes, où chaque implémentation est pour un type particulier de magasin de

clés.

Actuellement, il existe deux outils en ligne de commande qui utilisent des implémentations de magasin de clés (keytool et jarsigner)

.

L'implémentation par défaut du magasin de clés est PKCS12. Il s'agit d'un magasin de clés multiplateforme basé sur la norme de syntaxe d'échange d'informations personnelles RSA PKCS12. Cette norme est principalement destinée au stockage ou au transport des clés privées, des certificats et des secrets divers d'un utilisateur. Il existe une autre implémentation intégrée, fournie par Oracle. Elle implémente le magasin de clés sous forme de fichier avec un type de magasin de clés propriétaire (format) nommé JKS. Elle protège chaque clé privée avec son mot de passe individuel et protège également l'intégrité de l'ensemble du magasin de clés avec un (éventuellement différent) mot de

passe.

Les implémentations de magasin de clés sont basées sur les fournisseurs, ce qui signifie que les interfaces d'application fournies par la classe KeyStore sont implémentées en termes d'interface de fournisseur de service (SPI). Il existe une classe abstraite correspondante KeystoreSpi, également dans le paquet java.security, qui définit les méthodes de l'interface de fournisseur de service que les fournisseurs doivent implémenter. Le terme fournisseur fait référence à un paquet ou à un ensemble de paquets fournissant une implémentation concrète d'un sous-ensemble de services pouvant être accessibles par l'API de sécurité Java. Pour fournir une implémentation de magasin de clés, les clients doivent implémenter un fournisseur et fournir une implémentation de sous-classe KeystoreSpi, comme décrit dans Comment implémenter un fournisseur dans l'architecture de cryptographie Java [https://www.oracle.com/pls/topic/lookup?ctx=en/java/javase&id=security_guide_implement_provider_jca]

.

Les applications peuvent choisir différents types d'implémentations de magasins de clés (keystores) provenant de différents fournisseurs, à l'aide de la méthode factory getInstance de la classe KeyStore. Un type de keystore définit le format de stockage et de données des informations du keystore ainsi que les algorithmes utilisés pour protéger les clés privées dans le keystore et l'intégrité du keystore lui-même. Les implémentations de keystores de types différents ne sont pas

compatibles.

Les commandes jarsigner peuvent lire des keystores basés sur des fichiers depuis n'importe quel emplacement pouvant être spécifié à l'aide d'une URL. De plus, ces commandes peuvent lire des keystores non basés sur des fichiers, tels que ceux fournis par MSCAPI sur Windows et PKCS11 sur toutes les

plateformes.

Pour les commandes jarsigner et keytool, vous pouvez spécifier un type de keystore sur la ligne de commande avec l'option

-storetype.

Si vous ne spécifiez pas explicitement un type de keystore, les outils choisissent une implémentation de keystore basée sur la valeur de la propriété keystore.type spécifiée dans le fichier de propriétés de sécurité. Le fichier de propriétés de sécurité s'appelle java.security et il se trouve dans le répertoire des propriétés de sécurité du JDK, java.home/conf/security

.

Chaque outil récupère la valeur keystore.type puis examine tous les fournisseurs installés jusqu'à ce qu'il en trouve un qui implémente des keystores de ce type. Il utilise alors l'implémentation de keystore de ce

fournisseur.

La classe KeyStore définit une méthode statique nommée getDefaultType qui permet aux applications de récupérer la valeur de la propriété keystore.type. La ligne de code suivante crée une instance du type de keystore par défaut tel que spécifié dans la propriété keystore.type

:

KeyStore keyStore = KeyStore.getInstance(KeyStore.getDefaultType()

)
;

Le type de keystore par défaut est pkcs12, qui est un keystore multiplateformes basé sur la norme RSA PKCS12 Personal Information Exchange Syntax. Ceci est spécifié par la ligne suivante dans le fichier de propriétés de sécurité

:

keystor

e.type
=pkcs12

La casse n'a pas d'importance dans les désignations de type de keystore. Par exemple, JKS est identique à

jks.

Pour que les outils utilisent une implémentation de keystore autre que celle par défaut, vous pouvez modifier cette ligne pour spécifier un type de keystore différent. Par exemple, si vous souhaitez utiliser l'implémentation de keystore jks d'Oracle, modifiez la ligne comme suit

:

keys

VÉRIFICATION DU FICHIER

JAR

Une vérification réussie du fichier JAR se produit lorsque les signatures sont valides et qu'aucun des fichiers qui se trouvaient dans le fichier JAR au moment de la génération des signatures n'a changé depuis. La vérification du fichier JAR implique les étapes suivantes

:
1
.
Vérifier la
signature du
fichier .SF.

La vérification s'assure que la signature stockée dans chaque fichier de bloc de signature a été générée à l'aide de la clé privée correspondan

t à la clé publique dont le certificat (ou la chaîne de certificats) apparaît également dans le fichier de bloc de signature. Elle s'assure ég
alement que la signature est une signature valide du fichier de signature (.SF) correspondant, et donc que le fichier .SF n'a pas été falsifié.
2
.
Vérifier le digest listé dans chaque
entrée du fichier .SF avec chaque sect
ion correspondante dans le manifeste.

Le fichier .SF inclut par défaut un en-tête qui contient un hachage de l'ensemble du fichier manifeste. Lorsque l'en-tête est présent, la vérification peut vérifier si le hachage dans l'en-tête correspond ou non au hachage du fichier manifeste. S'il y a correspondance, la vérification passe à l'étape

suivante.

S'il n'y a pas de correspondance, une vérification moins optimisée est nécessaire pour s'assurer que le hachage dans chaque section d'informations de fichier source du fichier .SF est égal au hachage de sa section correspondante dans le fichier manifeste. Voir Fichier de

signature.

Une raison pour laquelle le hachage du fichier manifeste stocké dans l'en-tête du fichier .SF pourrait ne pas être égal au hachage du manifeste actuelile est que cela pourrait contenir des sections pour des fichiers nouvellement ajoutés après la signature du fichier. Par exemple, supposons qu'un ou plusieurs fichiers ont été ajoutés au fichier JAR signé (en utilisant l'outil jar) qui contient déjà une signature et un fichier .SF. Si le fichier JAR est à nouveau signé par un signataire différent, le fichier manifeste est modifié (des sections sont ajoutées pour les nouveaux fichiers par l'outil jarsigner) et un nouveau fichier .SF est créé, mais le fichier .SF original n'est pas modifié. Une vérification est toujours considérée comme réussie si aucun des fichiers qui se trouvaient dans le fichier JAR lors de la génération de la signature originale n'a été modifié depuis lors. Cela est dû au fait que les sommes de contrôle dans les sections non-en-tête du fichier .SF correspondent aux sommes de contrôle des sections correspondantes dans le fichier manifeste.

3.
Lisez chaque fichier du fichier JAR qui a une entrée dans le fichier .SF. Pendant la lecture, calculez le résumé (digest) du fichier et comparez le résultat avec le résumé de ce fichier dans la section du manifeste. Les résumés doivent être identiques, sinon la vérification échoue.

Si des échecs de vérification graves se produisent pendant le processus de vérification, le processus est arrêté et une exception de sécurité est levée. La commande jarsigner intercepte et affiche l'exception.

4.
Vérifiez l'utilisation d'algorithmes désactivés. Voir Algorithmes pris en charge.

Note :

Vous devriez lire tous les avertissements supplémentaires (ou erreurs si vous avez spécifié l'option -strict), ainsi que le contenu du certificat (en spécifiant les options -verbose et -certs) pour déterminer si la signature peut être fiable.

SIGNATURES MULTIPLES POUR UN FICHIER JAR

Un fichier JAR peut être signé par plusieurs personnes en exécutant la commande jarsigner sur le fichier plusieurs fois et en spécifiant l'alias d'une personne différente à chaque fois, comme suit :


jarsigner myBundle.jar susan
jarsigner myBundle.jar kevin

Lorsqu'un fichier JAR est signé plusieurs fois, il y a plusieurs fichiers .SF et blocs de signature dans le fichier JAR résultant, une paire pour chaque signature. Dans l'exemple précédent, le fichier JAR de sortie inclut des fichiers avec les noms suivants :


SUSAN.SF
SUSAN.RSA
KEVIN.SF
KEVIN.RSA

OPTIONS POUR JARSIGNER

Les sections suivantes décrivent les options de jarsigner. Soyez conscient des normes suivantes :

•
Tous les noms d'options sont précédés d'un signe moins (-).
•
Les options peuvent être fournies dans n'importe quel ordre.
•
Les éléments en italique ou soulignés (valeurs des options) représentent les valeurs réelles qui doivent être fournies.
•
Les options -storepass, -keypass, -sigfile, -sigalg, -digestalg, -signedjar et celles liées à TSA ne sont pertinentes que lors de la signature d'un fichier JAR ; elles ne sont pas pertinentes lors de la vérification d'un fichier JAR signé. L'option -keystore est pertinente pour la signature et la vérification d'un fichier JAR. De plus, les alias sont spécifiés lors de la signature et de la vérification d'un fichier JAR.
-keystore url
Spécifie l'URL qui indique l'emplacement du magasin de clés (keystore). Par défaut, il s'agit du fichier .keystore dans le répertoire personnel de l'utilisateur, tel que déterminé par la propriété système user.home.

Un magasin de clés est requis lors de la signature. Vous devez spécifier explicitement un magasin de clés si le magasin de clés par défaut n'existe pas ou si vous souhaitez en utiliser un autre que celui par défaut.

Un magasin de clés n'est pas requis lors de la vérification, mais s'il en est spécifié un ou si le magasin par défaut existe et que l'option -verbose a également été spécifiée, des informations supplémentaires seront affichées concernant la présence ou non des certificats utilisés pour vérifier le fichier JAR dans ce magasin de clés.

L'argument -keystore peut être un nom de fichier et un chemin plutôt qu'une URL, auquel cas il est traité de la même manière qu'une URL file:, par exemple, les éléments suivants sont équivalents :

•
-keystore cheminEtNomFichier
•
-keystore file:cheminEtNomFichier

Si le fournisseur Sun PKCS #11 a été configuré dans le fichier de propriétés de sécurité java.security (situé dans le répertoire $JAVA_HOME/conf/security du JDK), alors les outils keytool et jarsigner peuvent fonctionner sur le jeton PKCS #11 en spécifiant ces options :

-keystore NONE -storetype PKCS11

Par exemple, la commande suivante liste le contenu du jeton PKCS#11 configuré :

keytool -keystore NONE -storetype PKCS11 -list

-storepass [:env | :file] argument
Spécifie le mot de passe requis pour accéder au magasin de clés. Ceci n'est nécessaire que lors de la signature (pas de la vérification) d'un fichier JAR. Dans ce cas, si une option -storepass n'est pas fournie en ligne de commande, l'utilisateur est invité à entrer le mot de passe.

Si le modificateur env ou file n'est pas spécifié, alors le mot de passe a la valeur de l'argument. Sinon, le mot de passe est récupéré comme suit :

•
env : Récupérer le mot de passe de la variable d'environnement nommée argument.
•
file : Récupérer le mot de passe du fichier nommé argument.

Note :

Le mot de passe ne doit pas être spécifié en ligne de commande ou dans un script, sauf à des fins de test, ou si vous êtes sur un système sécurisé.

-storetype storetype

Lors du processus de signature ou de vérification, la commande jarsigner peut émettre diverses erreurs ou

avertissements.

En cas d'échec, la commande jarsigner se termine avec le code 1. En l'absence d'échec, mais s'il y a un ou plusieurs avertissements graves, la commande jarsigner se termine avec le code 0 lorsque l'option -strict n'est pas spécifiée, ou se termine avec la valeur OU des codes d'avertissement lorsque -strict est spécifié. S'il n'y a que des avertissements informatifs ou aucun avertissement du tout, la commande se termine toujours avec le code

0.

spécifiée.

NAME

        
jarsigner - Sign and verify jar files

    

    

        
SYNOPSIS

        
jarsigner [options] jar-file alias

        
jarsigner [options] -verify jar-file ...

        
jarsigner [options] -jarsigner signed-jar-file unsigned-jar-file

        
jarsigner [options] -verify -jarsigner signed-jar-file unsigned-jar-file

    

    

        
DESCRIPTION

        
The jarsigner command is a tool for signing, verifying, and displaying the
    contents of a signed JAR file. It is part of the Java Development Kit (JDK).

        
A JAR (Java Archive) file is a package file format that aggregates many files
    into one. It is built upon the ZIP file format and is used to bundle Java
    class files for distribution. Signed JAR files are used to digitally sign
    applets and applications, providing authenticity and integrity.

    

    

        
KEYSTORE ALIASES

        
An alias is a unique identifier for a private key and its associated public-key
    certificate chain in a keystore. When signing a JAR file, you specify the alias
    of the private key you want to use for signing.

    

    

        
KEYSTORE LOCATION

        
The keystore is a repository of keys and certificates. By default, jarsigner
    looks for the keystore in a file named .keystore in the user's home
    directory. You can specify a different keystore location using the -keystore
    option.

    

    

        
KEYSTORE IMPLEMENTATION

        
The jarsigner command supports various keystore implementations, including
    the default Java KeyStore (JKS), PKCS12, and others. The implementation is typically
    determined by the keystore file format or can be specified using the -storetype
    option.

    

    

        
SUPPORTED ALGORITHMS

        
jarsigner supports a range of cryptographic algorithms for signing and
    verification, including:

        
    
            
  • Signature Algorithms: SHA-256withRSA, SHA-1withRSA, etc.
    • 
            
  • Digest Algorithms: SHA-256, SHA-1, MD5, etc.
    • 
        

        
The specific algorithms used depend on the keys and certificates involved.

    

    

        
THE SIGNED JAR FILE

        
A signed JAR file contains additional files in the META-INF directory
    that are not present in an unsigned JAR file. These files include:

        
    
            
  • Manifest file (META-INF/MANIFEST.MF): Contains a list
        of all the files in the JAR and their corresponding digests.
    • 
            
  • Signature files (META-INF/*.SF): Contain the digital
        signature of the manifest file.
    • 
            
  • Signature block files (META-INF/*.DSA, META-INF/*.RSA,
        META-INF/*.EC): Contain the actual digital signature data and
        certificates.
    • 
        

    

    

        
SIGNATURE FILE

        
The signature file (.SF) contains the base64 encoded SHA-1 digest of
    the manifest file. It is signed by the private key specified by the alias.

    

    

        
SIGNATURE BLOCK FILE

        
The signature block file (.DSA, .RSA, or .EC)
    contains the actual digital signature and the signer's certificate chain. The
    extension depends on the signature algorithm used.

    

    

        
SIGNATURE TIME STAMP

        
A signature timestamp is an electronic timestamp that indicates when a digital
    signature was applied to a JAR file. It is typically provided by a trusted third-party
    Time-Stamping Authority (TSA).

        
The timestamp helps to verify the validity of the signature even after the
    signer's certificate has expired. The timestamping process involves the TSA
    digitally signing a digest of the JAR file's signature at a specific time.

    

    

        
JAR FILE VERIFICATION

        
The -verify option checks the integrity and authenticity of a signed JAR
    file. It performs the following checks:

        
    
            
  • Verifies that the digests of the files in the manifest match the actual
        digests of the files in the JAR.
    • 
            
  • Verifies that the signature of the manifest file in the .SF file
        matches the computed signature.
    • 
            
  • Verifies the digital signature of the JAR file using the signer's public
        key contained in the certificates.
    • 
            
  • Checks the validity of the signer's certificate chain, including expiration
        dates and trust anchors.
    • 
            
  • Validates the timestamp, if present, to ensure the signature was applied
        while the certificate was valid.
    • 
        

    

    

        
MULTIPLE SIGNATURES FOR A JAR FILE

        
A JAR file can be signed multiple times by different signers. Each signature
    is stored in a separate signature block file (e.g., META-INF/SIGChain1.DSA,
    META-INF/SIGChain2.RSA).

        
When verifying a JAR file with multiple signatures, jarsigner checks each
    signature independently.

    

    

        
OPTIONS FOR JARSIGNER

        

            
-verify

            
Verifies the signature of a JAR file.

            
-jarsigner signed-jar-file unsigned-jar-file

            
Copies a signed JAR file to an unsigned JAR file, or vice versa. This
        option is used to remove or add signatures.

            
-keystore <url>

            
Specifies the location of the keystore.

            
-storetype <type>

            
Specifies the keystore type (e.g., JKS, PKCS12).

            
-storepass <password>

            
Specifies the password for the keystore.

            
-keypass <password>

            
Specifies the password for the private key.

            
-signedjar <output-jar-file>

            
Specifies the output JAR file name when signing.

            
-tsacert <cert-alias>

            
Specifies the alias of the certificate to use for timestamping.

            
-rfc

            
Outputs information in RFC2822 format.

        

    

    

        
ERRORS AND WARNINGS

        
jarsigner reports various errors and warnings during the signing and
    verification process. These messages provide information about the status of the
    operation and potential issues.

    

    

        
FAILURE

        
A failure indicates that the JAR file verification has failed. This could be due
    to tampering, an invalid signature, an expired certificate without a valid
    timestamp, or other cryptographic errors.

    

    

        
SEVERE WARNINGS

        
Severe warnings indicate potential problems that might compromise the security
    or integrity of the signed JAR file. Examples include:

        
    
            
  • The signer's certificate has expired.
    • 
            
  • The timestamping authority's certificate is invalid or has expired.
    • 
            
  • The JAR file has been modified since it was signed.
    • 
        

    

    

        
INFORMATIONAL WARNINGS

        
Informational warnings provide additional details about the signature and
    certificates, but do not necessarily indicate a security risk. Examples include:

        
    
            
  • The signer's certificate is self-signed.
    • 
            
  • The certificate is untrusted.
    • 
        

    

    

        
EXAMPLE OF SIGNING A JAR FILE

        
To sign a JAR file named my_app.jar with the alias mykey,
    using a keystore password mypassword and key password mypassword:

        
jarsigner -keystore mykeystore.jks -storepass mypassword -keypass mypassword my_app.jar mykey
        

    

    

        
EXAMPLE OF VERIFYING A SIGNED JAR FILE

        
To verify a signed JAR file named my_app.jar:

        
jarsigner -verify my_app.jar
