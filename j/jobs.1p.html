JOBS(1P) Manuel du programmeur POSIX JOBS(1P)

PROLOG

Cette page de manuel fait partie du Manuel du programmeur POSIX. L'implémentation Linux de cette interface peut différer (consultez la page de manuel Linux correspondante pour les détails du comportement sous Linux), ou l'interface peut ne pas être implémentée sous Linux.

NOM

jobs — afficher l'état des tâches dans la session courante

SYNTAXE

jobs [-l|-p] [id_tache...]

DESCRIPTION

L'utilitaire jobs affichera l'état des tâches qui ont été démarrées dans l'environnement shell courant ; voir Section 2.12, Environnement d'exécution du shell.

Lorsque jobs signale le statut de terminaison d'une tâche, le shell supprimera son identifiant de processus de la liste de ceux « connus dans l'environnement d'exécution du shell courant » ; voir Section 2.9.3.1, Exemples.

OPTIONS

L'utilitaire jobs sera conforme aux Définitions de Base du volume de POSIX.1‐2017, Section 12.2, Lignes directrices de syntaxe des utilitaires.

Les options suivantes seront supportées :

-l
(La lettre ell.) Fournir plus d'informations sur chaque tâche listée. Ces informations comprendront le numéro de la tâche, la tâche courante, l'identifiant du groupe de processus, l'état et la commande qui a formé la tâche.
-p
Afficher uniquement les identifiants de processus des chefs de groupe de processus des tâches sélectionnées.

Par défaut, l'utilitaire jobs affichera l'état de toutes les tâches arrêtées, des tâches en cours d'exécution en arrière-plan et de toutes les tâches dont l'état a changé et n'a pas encore été signalé par le shell.

OPÉRANDES

L'opérande suivant sera supporté :

id_tache
Spécifie les tâches pour lesquelles l'état doit être affiché. Si aucun id_tache n'est fourni, les informations d'état de toutes les tâches seront affichées. Le format de id_tache est décrit dans le volume Définitions de Base de POSIX.1‐2017, Section 3.204, ID de tâche de contrôle de tâche.

SORTIE STANDARD

Si l'option -p est spécifiée, la sortie consistera en une ligne pour chaque identifiant de processus :

"%d\n", <identifiant de processus>

Sinon, si l'option -l n'est pas spécifiée, la sortie sera une série de lignes de la forme :

"[%d] %c %s %s\n", <numéro de tâche>, <courante>, <état>, <commande>

où les champs seront les suivants :

<courante>
Le caractère '+' identifie la tâche qui serait utilisée par défaut pour les utilitaires fg ou bg ; cette tâche peut également être spécifiée en utilisant l'id_tache %+ ou "%%". Le caractère '-' identifie la tâche qui deviendrait la tâche par défaut si la tâche par défaut courante se terminait ; cette tâche peut également être spécifiée en utilisant l'id_tache %-. Pour les autres tâches, ce champ est un <espace>. Au plus une tâche peut être identifiée avec '+' et au plus une tâche peut être identifiée avec '-'. S'il y a une tâche suspendue, alors la tâche courante sera une tâche suspendue. S'il y a au moins deux tâches suspendues, alors la tâche précédente sera également une tâche suspendue.
<numéro de tâche>
Un nombre qui peut être utilisé pour identifier le groupe de processus avec les utilitaires wait, fg, bg et kill. En utilisant ces utilitaires, la tâche peut être identifiée en préfixant le numéro de tâche avec '%'.
<état>
L'une des chaînes suivantes (dans la locale POSIX) :
Running
Indique que la tâche n'a pas été suspendue par un signal et n'est pas terminée.
Done
Indique que la tâche s'est terminée et a retourné un code de sortie zéro.
Done(code)
Indique que la tâche s'est terminée normalement et qu'elle s'est terminée avec le code de sortie non nul spécifié, code, exprimé en nombre décimal.
Stopped
Indique que la tâche a été suspendue par le signal SIGTSTP.
Stopped (SIGTSTP)

Indique que la tâche a été suspendue par le signal SIGTSTP.
Stopped (SIGSTOP)

Indique que la tâche a été suspendue par le signal SIGSTOP.
Stopped (SIGTTIN)

Indique que la tâche a été suspendue par le signal SIGTTIN.
Stopped (SIGTTOU)

Indique que la tâche a été suspendue par le signal SIGTTOU.

L'implémentation peut substituer la chaîne Suspended à la place de Stopped. Si la tâche a été terminée par un signal, le format de <état> n'est pas spécifié, mais il sera visiblement distinct de tous les autres formats de <état> montrés ici et indiquera le nom ou la description du signal causant la terminaison.

<commande>
La commande associée qui a été donnée au shell.

Si l'option -l est spécifiée, un champ contenant l'identifiant du groupe de processus sera inséré avant le champ <état>. De plus, d'autres processus d'un groupe de processus peuvent être affichés sur des lignes séparées, en utilisant uniquement les champs identifiant de processus et <commande>.

La sortie d'erreur ne sera utilisée que pour les messages diagnostiques.

UTILISATION DANS LES

APPLICATIONS

L'option -p est le seul moyen portable de connaître le groupe de processus d'un travail, car les différentes implémentations utilisent des stratégies différentes pour définir le groupe de processus d'un travail. Une utilisation telle que $(jobs -p) fournit un moyen de faire référence au groupe de processus du travail d'une manière indépendante de l'implémentation

.

L'utilitaire jobs ne fonctionne pas comme prévu lorsqu'il s'exécute dans son propre environnement d'exécution, car cet environnement ne contient aucun travail applicable à manipuler. Voir la section UTILISATION DANS LES APPLICATIONS pour bg. Pour cette raison, jobs est généralement implémenté en tant q

e régulière du shell.

JUSTIFICATIO

N

À la fois "%%" et "%+" sont utilisés pour faire référence au travail courant. Les deux formes sont également valides — le "%%" faisant écho à "$$" et "%+" faisant écho à la sortie de jobs. Les deux formes reflètent la pratique historique du KornShell et du C shell avec le contrôle des

travaux.

Les fonctionnalités de contrôle des travaux fournies par bg, fg et jobs sont basées sur le KornShell. Les développeurs de la norme ont examiné les caractéristiques des versions C shell de ces utilitaires et ont constaté qu'il existe des différences. Malgré l'utilisation répandue du C shell, les versions KornShell ont été choisies pour ce volume de POSIX.1‐2017 afin de maintenir un certain degré d'uniformité avec le reste des fonctionnalités KornShell sélectionnées (telles que les très populaires fonctionnalités d'édition de ligne de commande)

.

L'utilitaire jobs ne dépend pas de l'option de contrôle des travaux, contrairement aux utilitaires apparemment liés bg et fg, car jobs est utile pour examiner les travaux d'arrière-plan, quel que soit l'état du contrôle des travaux. Lorsque l'utilisateur a invoqué la commande set +m et que le contrôle des travaux a été désactivé, jobs peut toujours être utilisé pour examiner les travaux d'arrière-plan associés à cette session courante. De même, kill peut alors être utilisé pour tuer les travaux d'arrière-plan avec kill %<numéro de travail d'arr
