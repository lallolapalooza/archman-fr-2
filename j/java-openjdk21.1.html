JAVA(1) Commandes JDK JAVA(1)

NOM

java - lance une application Java

SYNOPSIS

Pour lancer un fichier de classe :

java [options] mainclass [args ...]

Pour lancer la classe principale dans un fichier JAR :

java [options] -jar jarfile [args ...]

Pour lancer la classe principale dans un module :

java [options] -m module[/mainclass] [args ...]

ou

java [options] --module module[/mainclass] [args ...]

Pour lancer un programme à fichier source unique :

java [options] source-file [args ...]

options
Facultatif : Spécifie les options de ligne de commande séparées par des espaces. Voir Aperçu des options Java pour une description des options disponibles.
mainclass
Spécifie le nom de la classe à lancer. Les entrées de ligne de commande suivant classname sont les arguments pour la méthode main.
-jar jarfile
Exécute un programme encapsulé dans un fichier JAR. L'argument jarfile est le nom d'un fichier JAR avec un manifeste qui contient une ligne de la forme Main-Class:classname qui définit la classe avec la méthode public static void main(String[] args) qui sert de point de départ à votre application. Lorsque vous utilisez -jar, le fichier JAR spécifié est la source de toutes les classes utilisateur, et les autres paramètres du chemin de classe sont ignorés. Si vous utilisez des fichiers JAR, voir jar.
-m ou --module module[/mainclass]
Exécute la classe principale dans un module spécifié par mainclass si celui-ci est fourni, ou, s'il n'est pas fourni, la valeur dans le module. En d'autres termes, mainclass peut être utilisé lorsqu'il n'est pas spécifié par le module, ou pour remplacer la valeur lorsqu'il est spécifié.

Voir Options standard pour Java.

source-file
Utilisé uniquement pour lancer un programme à fichier source unique. Spécifie le fichier source qui contient la classe principale lors de l'utilisation du mode source-file. Voir Utilisation du mode source-file pour lancer des programmes à code source à fichier unique
args ...
Facultatif : Les arguments suivant mainclass, source-file, -jar jarfile, et -m ou --module module/mainclass sont transmis en tant qu'arguments à la classe principale.

DESCRIPTION

La commande java démarre une application Java. Elle le fait en démarrant la machine virtuelle Java (JVM), en chargeant la classe spécifiée, et en appelant la méthode main() de cette classe. La méthode doit être déclarée public et static, elle ne doit retourner aucune valeur, et elle doit accepter un tableau de String comme paramètre. La déclaration de la méthode a la forme suivante :

public static void main(String[] args)

En mode source-file, la commande java peut lancer une classe déclarée dans un fichier source. Voir Utilisation du mode source-file pour lancer des programmes à code source à fichier unique pour une description de l'utilisation du mode source-file .

Remarque : Vous pouvez utiliser la variable d'environnement du lanceur JDK_JAVA_OPTIONS pour préfixer son contenu à la ligne de commande réelle du lanceur java. Voir Utilisation de la variable d'environnement du lanceur JDK_JAVA_OPTIONS.

Par défaut, le premier argument qui n'est pas une option de la commande java est le nom qualifié complet de la classe à appeler. Si -jar est spécifié, alors son argument est le nom du fichier JAR contenant les fichiers de classe et de ressources pour l'application. La classe de démarrage doit être indiquée par l'en-tête de manifeste Main-Class dans son fichier manifeste.

Les arguments après le nom du fichier de classe ou le nom du fichier JAR sont transmis à la méthode main().

javaw

Windows : La commande javaw est identique à java, sauf qu'avec javaw il n'y a pas de fenêtre de console associée. Utilisez javaw lorsque vous ne voulez pas qu'une fenêtre d'invite de commande apparaisse. Le lanceur javaw affichera cependant une boîte de dialogue avec des informations d'erreur si le lancement échoue.

UTILISATION DU MODE SOURCE-FILE POUR LANCER DES PROGRAMMES À CODE SOURCE À FICHIER UNIQUE

Pour lancer une classe déclarée dans un fichier source, exécutez le lanceur java en mode source-file. L'entrée en mode source-file est déterminée par deux éléments sur la ligne de commande java :

•
Le premier élément sur la ligne de commande qui n'est pas une option ou une partie d'une option. En d'autres termes, l'élément sur la ligne de commande qui serait sinon le nom de la classe principale.
•
L'option --source version , si présente.

Si la classe identifie un fichier existant qui a une extension .java , ou si l'option --source est spécifiée, alors le mode source-file est sélectionné. Le fichier source est alors compilé et exécuté. L'option --source peut être utilisée pour spécifier la source version ou N du code source. Cela détermine l'API qui peut être utilisée. Lorsque vous définissez --source N, vous ne pouvez utiliser que l'API publique qui a été définie dans le JDK N.

Remarque : Les valeurs valides de N changent pour chaque version, avec de nouvelles valeurs ajoutées et d'anciennes valeurs supprimées. Vous obtiendrez un message d'erreur si vous utilisez une valeur de N qui n'est plus supportée. Les valeurs supportées de N sont la version Java SE actuelle (21) et un nombre limité de versions précédentes, détaillées dans l'aide en ligne de commande pour javac, sous les options --source et --release.

Si le fichier n'a pas l'extension .java, l'option --source doit être utilisée pour indiquer à la commande java d'utiliser le mode source-file. L'option --source est utilisée pour les cas où le fichier source est un « script » à exécuter et le nom du fichier source ne suit pas les conventions de nommage normales pour les fichiers source Java.

En mode source-file, l'effet est comme si le fichier source était compilé en mémoire, et la première classe trouvée dans le fichier source était exécutée. Tous les arguments placés après le nom du fichier source dans la ligne de commande originale sont transmis à la classe compilée lorsqu'elle est exécutée.

Par exemple, si un fichier était nommé HelloWorld.java et contenait une classe nommée hello.World, alors la commande en mode source-file pour lancer la classe serait :

java HelloWorld.java

L'exemple illustre que la classe peut être dans un paquet nommé, et n'a pas besoin d'être dans le paquet non nommé. Cette utilisation du mode source-file est informellement équivalente à l'utilisation des deux commandes suivantes où hello.World est le nom de la classe dans le paquet :


javac -d <memory> HelloWorld.java
java -cp <memory> hello.World

En mode source-file, toutes les options supplémentaires de ligne de commande sont traitées comme suit :

•
Le lanceur analyse les options spécifiées avant le fichier source pour toute option pertinente afin de compiler le fichier source.

Cela inclut : --class-path, --module-path, --add-exports, --add-modules, --limit-modules, --patch-module, --upgrade-module-path, et toute forme variante de ces options. Cela inclut également la nouvelle option --enable-preview, décrite dans le JEP 12.

•
Aucune disposition n'est prévue pour transmettre des options supplémentaires au compilateur, telles que -processor ou -Werror.
•
Les fichiers d'arguments de ligne de commande (@-files) peuvent être utilisés de la manière standard. De longues listes d'arguments pour la VM ou le programme appelé peuvent être placées dans des fichiers spécifiés sur la ligne de commande en préfixant le nom de fichier avec un caractère @.

En mode source-file, la compilation se déroule comme suit :

•
Toutes les options de ligne de commande pertinentes pour l'environnement de compilation sont prises en compte.
•
Aucun autre fichier source n'est trouvé et compilé, comme si le chemin source était défini à une valeur vide.
•
Le traitement des annotations est désactivé, comme si -proc:none était en vigueur.
•
Si une version est spécifiée, via l'option --source, la valeur est utilisée comme l'argument pour une option --release implicite pour la compilation. Cela définit à la fois la version source acceptée par le compilateur et l'API système qui peut être utilisée par le code dans le fichier source.
•
Le fichier source est compilé dans le contexte d'un module non nommé.
•
Le fichier source doit contenir une ou plusieurs classes de premier niveau, dont la première est considérée comme la classe à exécuter.
•
Le compilateur n'applique pas la restriction facultative définie à la fin du JLS 7.6, selon laquelle un type dans un nommé package doit exister dans un fichier dont le nom est composé du nom du type suivi de l'extension .java.
•
Si le fichier source contient des erreurs, des messages d'erreur appropriés sont écrits sur le flux d'erreur standard, et le lanceur se termine avec un code de sortie non nul.

En mode fichier source, l'exécution se déroule comme suit :

•
La classe à exécuter est la première classe de premier niveau trouvée dans le fichier source. Elle doit contenir une déclaration de la méthode standard public static void main(String[]).
•
Les classes compilées sont chargées par un chargeur de classes personnalisé, qui délègue au chargeur de classes de l'application. Cela implique que les classes présentes sur le chemin de classes de l'application ne peuvent référencer aucune des classes déclarées dans le fichier source.
•
Les classes compilées sont exécutées dans le contexte d'un module non nommé, comme si --add-modules=ALL-DEFAULT était en vigueur. Cela s'ajoute à toute autre option --add-module qui aurait pu être spécifiée sur la ligne de commande.
•
Tous les arguments apparaissant après le nom du fichier sur la ligne de commande sont passés à la méthode main standard de manière évidente.
•
C'est une erreur s'il existe une classe sur le chemin de classes de l'application dont le nom est le même que celui de la classe à exécuter.

Voir JEP 330 : Lancement de programmes à fichier source unique [https://openjdk.org/jeps/330] pour plus de détails.

UTILISATION DE LA VARIABLE D'ENVIRONNEMENT DU LANCEUR JDK_JAVA_OPTIONS

JDK_JAVA_OPTIONS préfixe son contenu aux options analysées depuis la ligne de commande. Le contenu de la variable d'environnement JDK_JAVA_OPTIONS est une liste d'arguments séparés par des caractères d'espacement blanc (tel que déterminé par isspace()). Ceux-ci sont ajoutés en tête des arguments de la ligne de commande passés au lanceur java. La exigence d'encodage pour la variable d'environnement est la même que pour la ligne de commande java sur le système. Le contenu de la variable d'environnement JDK_JAVA_OPTIONS est traité de la même manière que ce qui est spécifié dans la ligne de commande.

Les guillemets simples (') ou doubles (") peuvent être utilisés pour entourer des arguments contenant des caractères d'espacement blanc. Tout le contenu entre le guillemet d'ouverture et le premier guillemet de fermeture correspondant est conservé en supprimant simplement la paire de guillemets. Si aucun guillemet correspondant n'est trouvé, le lanceur s'interrompt avec un message d'erreur. Les fichiers @ sont pris en charge comme ils sont spécifiés dans la ligne de commande. Cependant, comme dans les fichiers @, l'utilisation d'un caractère générique n'est pas prise en charge. Afin de limiter une éventuelle utilisation abusive du comportement de JDK_JAVA_OPTIONS, les options qui spécifient la classe principale (telles que -jar) ou qui font que le lanceur java se termine sans exécuter la classe principale (telles que -h) ne sont pas autorisées dans la variable d'environnement. Si l'une de ces options apparaît dans la variable d'environnement, le lanceur s'interrompt avec un message d'erreur. Lorsque JDK_JAVA_OPTIONS est défini, le lanceur imprime un message sur stderr comme rappel.

Exemple :


$ export JDK_JAVA_OPTIONS='-g @file1 -Dprop=value @file2 -Dws.prop="white spaces"'
$ java -Xint @file3

est équivalent à la ligne de commande :


java -g @file1 -Dprop=value @file2 -Dws.prop="white spaces" -Xint @file3

APERÇU DES OPTIONS JAVA

La commande java prend en charge un large éventail d'options dans les catégories suivantes :

•
Options standard pour Java: Options garanties d'être prises en charge par toutes les implémentations de la Machine Virtuelle Java (JVM). Elles sont utilisées pour des actions courantes, telles que la vérification de la version de la JRE, la définition du chemin de classes, l'activation de la sortie verbeuse, etc.
•
Options supplémentaires pour Java: Options à usage général qui sont spécifiques à la Machine Virtuelle Java HotSpot. Leur prise en charge par toutes les implémentations de JVM n'est pas garantie et elles sont sujettes à changement. Ces options commencent par -X.

Les options avancées ne sont pas recommandées pour un usage courant. Ce sont des options de développement utilisées pour régler des domaines spécifiques du fonctionnement de la Machine Virtuelle Java HotSpot qui ont souvent des exigences système spécifiques et peuvent nécessiter un accès privilégié aux paramètres de configuration du système. Plusieurs exemples de réglage des performances sont fournis dans Exemples de réglage des performances. Ces options ne sont pas garanties d'être prises en charge par toutes les implémentations de JVM et sont sujettes à changement. Les options avancées commencent par -XX.

•
Options d'exécution avancées pour Java: Contrôlent le comportement d'exécution de la Machine Virtuelle Java HotSpot.
•
Options de compilateur JIT avancées pour java: Contrôlent la compilation dynamique just-in-time (JIT) effectuée par la Machine Virtuelle Java HotSpot.
•
Options de maintenance avancées pour Java: Permettent la collecte d'informations système et l'exécution de débogage approfondi.
•
Options de collecte de déchets avancées pour Java: Contrôlent la manière dont la collecte de déchets (GC) est effectuée par la Machine Virtuelle Java HotSpot

Les options booléennes sont utilisées pour activer une fonctionnalité désactivée par défaut ou désactiver une fonctionnalité activée par défaut. De telles options ne nécessitent pas de paramètre. Les options booléennes -XX sont activées à l'aide du signe plus (-XX:+OptionName) et désactivées à l'aide du signe moins (-XX:-OptionName).

Pour les options qui nécessitent un argument, l'argument peut être séparé du nom de l'option par un espace, un deux-points (:), ou un signe égal (=), ou l'argument peut suivre directement l'option (la syntaxe exacte diffère pour chaque option). Si vous devez spécifier la taille en octets, vous pouvez utiliser aucun suffixe, ou utiliser le suffixe k ou K pour kilooctets (KB), m ou M pour mégaoctets (MB), ou g ou G pour gigaoctets (GB). Par exemple, pour définir la taille à 8 Go, vous pouvez spécifier soit 8g, 8192m, 8388608k, ou 8589934592 comme argument. Si vous devez spécifier un pourcentage, utilisez un nombre de 0 à 1. Par exemple, spécifiez 0.25 pour 25 %.

Les sections suivantes décrivent les options qui sont obsolètes, dépassées et supprimées :

•
Options Java obsolètes (dépréciées): Acceptées et prises en compte --- un avertissement est émis lors de leur utilisation.
•
Options Java dépassées (obsolètes): Acceptées mais ignorées --- un avertissement est émis lors de leur utilisation.
•
Options Java supprimées: Supprimées --- leur utilisation entraîne une erreur.

OPTIONS STANDARD POUR JAVA

Ce sont les options les plus couramment utilisées, prises en charge par toutes les implémentations de la JVM.

Remarque : Pour spécifier un argument pour une option longue, vous pouvez utiliser soit --name=value soit --name value.

-agentlib:libname[=options]
Charge la bibliothèque d'agent native spécifiée. Après le nom de la bibliothèque, une liste d'options séparées par des virgules et spécifiques à la bibliothèque peut être utilisée. Si l'option -agentlib:foo est spécifiée, la JVM tente de charger la bibliothèque nommée foo en utilisant les conventions de nommage et les emplacements spécifiques à la plateforme :
•
Linux et autres plateformes de type POSIX : La JVM tente de charger la bibliothèque nommée libfoo.so dans l'emplacement spécifié par la variable système LD_LIBRARY_PATH.
•
macOS : La JVM tente de charger la bibliothèque nommée libfoo.dylib dans l'emplacement spécifié par la variable système DYLD_LIBRARY_PATH.
•
Windows : La JVM tente de charger la bibliothèque nommée foo.dll dans l'emplacement spécifié par la variable système PATH.

L'exemple suivant montre comment charger la bibliothèque du protocole de débogage Java (JDWP) et écouter la connexion de socket sur le port 8000, en suspendant la JVM avant le chargement de la classe principale :

-agentlib:jdwp=transport=dt_socket,server=y,address=8000

-agentpath:pathname[=options]
Charge la bibliothèque d'agent native spécifiée par le chemin absolu. Cette option est équivalente à -agentlib mais utilise le chemin complet et le nom de fichier de la bibliothèque.
--class-path classpath, -classpath classpathou -cp classpath
Spécifie une liste de répertoires, de fichiers JAR et d'archives ZIP dans lesquels rechercher des fichiers de classes.

Sur Windows, les points-virgules (;) séparent les entités de cette liste ; sur les autres plateformes, c'est un deux-points (:).

La spécification de classpath remplace tout paramètre de la variable d'environnement CLASSPATH. Si l'option de chemin de classes n'est pas utilisée et que classpath n'est pas défini, alors le chemin de classes de l'utilisateur se compose du répertoire courant (.).

Par commodité, un élément de chemin de classes contenant un nom de base d'astérisque (*) est considéré comme équivalent à la spécification d'une liste de tous les fichiers du répertoire avec l'extension .jar ou .JAR. Un programme Java ne peut pas faire la différence entre les deux invocations. Par exemple, si le répertoire mydir contient a.jar et b.JAR, alors l'élément de chemin de classes mydir/* est développé en A.jar:b.JAR, sauf que l'ordre des fichiers JAR n'est pas spécifié. Tous les fichiers .jar du répertoire spécifié, même les fichiers cachés, sont inclus dans la liste. Une entrée de chemin de classes consistant en un astérisque (*) se développe en une liste de tous les fichiers jar du répertoire courant. La variable d'environnement CLASSPATH, si elle est définie, est développée de la même manière. Toute expansion de caractère générique de chemin de classes qui se produit avant le démarrage de la Machine Virtuelle Java. Les programmes Java ne voient jamais de caractères génériques qui ne sont pas développés, sauf en interrogeant l'environnement, comme en appelant System.getenv("CLASSPATH").

Définit la taille initiale et maximale (en octets) du tas pour la jeune génération (nursery) dans les collecteurs générationnels. Ajoutez la lettre k ou K pour indiquer les kilooctets, m ou M pour indiquer les mégaoctets, ou g ou G pour indiquer les gigaoctets. -Xrs
Réduit l'utilisation des signaux du système d'exploitation par la JVM. Les hooks de fermeture (shutdown hooks) permettent la fermeture ordonnée d'une application Java en exécutant du code de nettoyage défini par l'utilisateur (comme la fermeture des connexions à la base de données) lors de la fermeture, même si la JVM se termine de manière abrupte.
•
Non-Windows :
•
La JVM intercepte les signaux pour implémenter les hooks de fermeture en cas de terminaison inattendue. La JVM utilise SIGHUP, SIGINT et SIGTERM pour initier l'exécution des hooks de fermeture.
•
Les applications intégrant la JVM doivent souvent intercepter des signaux comme SIGINT ou SIGTERM, ce qui peut interférer avec les gestionnaires de signaux de la JVM. L'option -Xrs est disponible pour résoudre ce problème. Lorsque -Xrs est utilisée, les masques de signaux pour SIGINT, SIGTERM, SIGHUP et SIGQUIT ne sont pas modifiés par la JVM, et les gestionnaires de signaux pour ces signaux ne sont pas installés.
•
Windows :
•
La JVM surveille les événements de contrôle de la console pour implémenter les hooks de fermeture en cas de terminaison inattendue. Plus précisément, la JVM enregistre un gestionnaire de contrôle de console qui démarre le traitement des hooks de fermeture et renvoie TRUE pour CTRL_C_EVENT, CTRL_CLOSE_EVENT, CTRL_LOGOFF_EVENT et CTRL_SHUTDOWN_EVENT.
•
La JVM utilise un mécanisme similaire pour implémenter la fonctionnalité de vidage des piles de threads à des fins de débogage. La JVM utilise CTRL_BREAK_EVENT pour effectuer des vidages de threads.
•
Si la JVM est exécutée en tant que service (par exemple, en tant que moteur de servlet pour un serveur web), elle peut recevoir CTRL_LOGOFF_EVENT mais ne doit pas initier la fermeture car le système d'exploitation ne termine pas réellement le processus. Pour éviter une éventuelle interférence de ce type, l'option -Xrs peut être utilisée. Lorsque l'option -Xrs est utilisée, la JVM n'installe pas de gestionnaire de contrôle de console, ce qui implique qu'elle ne surveille ni ne traite CTRL_C_EVENT, CTRL_CLOSE_EVENT, CTRL_LOGOFF_EVENT ou CTRL_SHUTDOWN_EVENT.

Il y a deux conséquences à la spécification de -Xrs :

•
Non-Windows : Les vidages de threads SIGQUIT ne sont pas disponibles.
•
Windows : Les vidages de threads Ctrl + Break ne sont pas disponibles.

Le code utilisateur est responsable de déclencher l'exécution des hooks de fermeture, par exemple, en appelant System.exit() lorsque la JVM doit être terminée.

OPTIONS D'EXÉCUTION AVANCÉES POUR JAVA

Ces options java contrôlent le comportement d'exécution de la machine virtuelle Java HotSpot.

-XX:ActiveProcessorCount=x
Remplace le nombre de CPU que la machine virtuelle utilisera pour calculer la taille des pools de threads qu'elle utilisera pour diverses opérations telles que la collecte des déchets et ForkJoinPool.

La machine virtuelle détermine normalement le nombre de processeurs disponibles à partir du système d'exploitation. Cet indicateur peut être utile pour partitionner les ressources CPU lors de l'exécution de plusieurs processus Java dans des conteneurs docker. Cet indicateur est honoré même si UseContainerSupport n'est pas activé. Voir -XX:-UseContainerSupport pour une description de l'activation et de la désactivation du support des conteneurs.

-XX:AllocateHeapAt=path
Prend un chemin d'accès au système de fichiers et utilise le mappage mémoire pour allouer le tas d'objets sur le périphérique mémoire. L'utilisation de cette option permet à la machine virtuelle HotSpot d'allouer le tas d'objets Java sur un périphérique mémoire alternatif, tel qu'un NV-DIMM, spécifié par l'utilisateur.

Les périphériques mémoire alternatifs qui ont les mêmes sémantiques que la DRAM, y compris les sémantiques des opérations atomiques, peuvent être utilisés à la place de la DRAM pour le tas d'objets sans modifier le code d'application existant. Toutes les autres structures mémoire (telles que le tas de code, le métaspace et les piles de threads) continuent de résider en DRAM.

Certains systèmes d'exploitation exposent de la mémoire non DRAM à travers le fichier système. Les fichiers mappés en mémoire dans ces systèmes de fichiers contournent le cache de pages et fournissent un mappage direct de la mémoire virtuelle vers la mémoire physique sur le périphérique. Les indicateurs existants liés au tas (tels que -Xmx et -Xms) et les indicateurs liés à la collecte des déchets continuent de fonctionner comme avant.

-XX:-CompactStrings
Désactive la fonctionnalité Compact Strings. Par défaut, cette option est activée. Lorsque cette option est activée, les chaînes Java contenant uniquement des caractères d'un seul octet sont représentées et stockées en interne sous forme de chaînes d'un octet par caractère en utilisant l'encodage ISO-8859-1 / Latin-1. Cela réduit de 50 % l'espace requis pour les chaînes contenant uniquement des caractères d'un seul octet. Pour les chaînes Java contenant au moins un caractère multioctet : celles-ci sont représentées et stockées sur 2 octets par caractère en utilisant l'encodage UTF-16. Désactiver la fonctionnalité Compact Strings force l'utilisation de l'encodage UTF-16 comme représentation interne pour toutes les chaînes Java.

Les cas où il peut être bénéfique de désactiver Compact Strings incluent les suivants :

•
Lorsqu'il est connu qu'une application allouera de manière prédominante des chaînes de caractères multioctets
•
Dans l'événement inattendu où une régression de performance est observée lors de la migration de Java SE 8 à Java SE 9 et qu'une analyse montre que Compact Strings introduit la régression

Dans ces deux scénarios, désactiver Compact Strings a du sens.

La seule fois où vous pourriez avoir besoin de la désactiver est sur macOS, où son utilisation impose un maximum de 10240, ce qui est inférieur au maximum réel du système.
-XX:NativeMemoryTracking=mode
Spécifie le mode de suivi de l'utilisation de la mémoire native de la JVM. Les arguments mode possibles pour cette option incluent les suivants :
off
Indique de ne pas suivre l'utilisation de la mémoire native de la JVM. C'est le comportement par défaut si vous ne spécifiez pas l'option -XX:NativeMemoryTracking.
summary
Suit l'utilisation de la mémoire uniquement par les sous-systèmes de la JVM, tels que le tas Java, la classe, le code et le thread.
detail
En plus de suivre l'utilisation de la mémoire par les sous-systèmes de la JVM, suit l'utilisation de la mémoire par chaque CallSite, chaque région de mémoire virtuelle et ses régions engagées.
-XX:TrimNativeHeapInterval=millis

Cette option n'est prise en charge que sous Linux avec la bibliothèque C GNU (glibc).

-XX:+NeverActAsServerClassMachine

La quantité maximale de mémoire que la JVM peut utiliser (contrôlée par le drapeau -XX:MaxRAM=n) est définie par défaut à 1 Go. La chaîne « emulated-client » est ajoutée à la chaîne de version de la JVM.

Par défaut, le drapeau est défini sur true uniquement sous Windows en mode 32 bits et sur false dans tous les autres cas.

-XX:ObjectAlignmentInBytes=alignement
Définit l'alignement de la mémoire des objets Java (en octets). Par défaut, la valeur est réglée sur 8 octets. La valeur spécifiée doit être une puissance de 2 et doit être comprise dans l'intervalle de 8 à 256 (inclus). Cette option permet d'utiliser des pointeurs compressés avec de grandes tailles de tas Java.

La limite de taille du tas en octets est calculée comme suit :

4 Go * ObjectAlignmentInBytes

Remarque : à mesure que la valeur d'alignement augmente, l'espace inutilisé entre les objets augmente également. Par conséquent, vous ne bénéficierez peut-être pas de l'utilisation des pointeurs compressés avec de grandes tailles de tas Java.

-XX:+PrintCommandLineFlags

-XX:+PreserveFramePointer

-XX:+PrintNMTStatistics

delay=temps
Spécifie le délai entre l'heure de lancement de l'application Java et le début de l'enregistrement. Prend à la fois le nom et l'identifiant d'un enregistrement.

Spécifie l'âge maximal des données sur disque à conserver pour l'enregistrement. Ce paramètre n'est valide que lorsque le paramètre disk est défini à true. -XX:-UseCompressedOops
Désactive l'utilisation des pointeurs compressés. Par défaut, cette option est activée et les pointeurs compressés sont utilisés. Cela limitera automatiquement la taille maximale du tas Java déterminée de manière ergonomique à la quantité maximale de mémoire pouvant être couverte par les pointeurs compressés. Par défaut, cette plage est de 32 Go.

Avec les oops compressés activés, les références d'objets sont représentées comme des décalages de 32 bits au lieu de pointeurs de 64 bits, ce qui augmente généralement les performances lors de l'exécution de l'application avec des tailles de tas Java inférieures à la plage de pointeurs des oops compressés. Cette option ne fonctionne que pour les JVM 64 bits.

Il est possible d'utiliser des pointeurs compressés avec des tailles de tas Java supérieures à 32 Go. Voir l'option -XX:ObjectAlignmentInBytes.

La journalisation unifiée est disponible pour aider à diagnostiquer les problèmes liés à cette prise en charge.

OPTIONS AVANCÉES DU COMPILATEUR JIT POUR JAVA

Ces options java contrôlent la compilation dynamique just-in-time (JIT) effectuée par la Java HotSpot VM.

-XX:AllocateInstancePrefetchLines=lignes
Définit le nombre de lignes à précharger en avant du pointeur d'allocation d'instance. Par défaut, le nombre de lignes à précharger est défini à 1 :

-XX:AllocateInstancePrefetchLines=1

-XX:AllocatePrefetchDistance=taille
Définit la taille (en octets) de la distance de préchargement pour l'allocation d'objets. La mémoire sur le point d'être écrite avec la valeur des nouveaux objets est préchargée jusqu'à cette distance à partir de l'adresse du dernier objet alloué. Chaque thread Java a son propre point d'allocation.

Les valeurs négatives indiquent que la distance de préchargement est choisie en fonction de la plateforme. Les valeurs positives sont le nombre d'octets à précharger. Ajoutez la lettre k ou K pour indiquer les kilo-octets, m ou M pour indiquer les mégaoctets, ou g ou G pour indiquer les gigaoctets. La valeur par défaut est définie à -1.

L'exemple suivant montre comment définir la distance de préchargement à 1024 octets :

-XX:AllocatePrefetchDistance=1024

-XX:AllocatePrefetchInstr=instruction
Définit l'instruction de préchargement pour précharger en avant du pointeur d'allocation. Les valeurs possibles vont de 0 à 3. Les instructions réelles derrière les valeurs dépendent de la plateforme. Par défaut, l'instruction de préchargement est définie à 0 :

-XX:AllocatePrefetchInstr=0

-XX:AllocatePrefetchLines=lignes
Définit le nombre de lignes de cache à charger après la dernière allocation d'objet en utilisant les instructions de préchargement générées dans le code compilé. La valeur par défaut est 1 si le dernier objet alloué était une instance, et 3 si c'était un tableau.

L'exemple suivant example montre comment définir le nombre de lignes de cache chargées à 5 :

-XX:AllocatePrefetchLines=5

-XX:AllocatePrefetchStepSize=taille
Définit la taille du pas (en octets) pour les instructions de préchargement séquentielles. Ajoutez la lettre k ou K pour indiquer les kilooctets, m ou M pour indiquer les mégaoctets, g ou G pour indiquer les gigaoctets. Par défaut, la taille du pas est de 16 octets :

-XX:AllocatePrefetchStepSize=16

-XX:AllocatePrefetchStyle=style
Définit le style de code généré pour les instructions de préchargement. L'argument style est un entier allant de 0 à 3 :
0
Ne génère pas d'instructions de préchargement.
1
Exécute les instructions de préchargement après chaque allocation. C'est le paramètre par défaut.
2
Utilise le pointeur de filigrane du bloc d'allocation local au thread (TLAB) pour déterminer quand les instructions de préchargement sont exécutées.
3
Génère une instruction de préchargement par ligne de cache.
-XX:+BackgroundCompilation
Active la compilation en arrière-plan. Cette option est activée par défaut. Pour désactiver la compilation en arrière-plan, spécifiez -XX:-BackgroundCompilation (ce qui équivaut à spécifier -Xbatch).
-XX:CICompilerCount=threads
Définit le nombre de threads de compilateur à utiliser pour la compilation. Par défaut, le nombre de threads de compilateur est sélectionné automatiquement en fonction du nombre de processeurs et de la mémoire disponibles pour le code compilé. L'exemple suivant montre comment définir le nombre de threads à 2 :

-XX:CICompilerCount=2

-XX:+UseDynamicNumberOfCompilerThreads
Crée dynamiquement des threads de compilateur jusqu'à la limite spécifiée par -XX:CICompilerCount. Cette option est activée par défaut.
-XX:CompileCommand=commande,méthode[,option]
Spécifie une commande à effectuer sur une méthode. Par exemple, pour exclure la méthode indexOf() de la classe String de la compilation, utilisez ce qui suit :

-XX:CompileCommand=exclude,java/lang/String.indexOf

Notez que le nom de classe complet est spécifié, y compris tous les paquets et sous-paquets séparés par une barre oblique (/). Pour faciliter les opérations de copier-coller, il est également possible d'utiliser le format de nom de méthode produit par les options -XX:+PrintCompilation et -XX:+LogCompilation :

-XX:CompileCommand=exclude,java.lang.String::indexOf

Si la méthode est spécifiée sans la signature, la commande est appliquée à toutes les méthodes portant le même nom. Cependant, vous pouvez également spécifier la signature de la méthode au format de fichier de classe. Dans ce cas, vous devez entourer les arguments de guillemets, car sinon l'interpréteur de commandes traite le point-virgule comme la fin de la commande. Par exemple, si vous souhaitez exclure uniquement la méthode indexOf(String) de la classe String de la compilation, utilisez ce qui suit :

-XX:CompileCommand="exclude,java/lang/String.indexOf,(Ljava/lang/String;)I"

Vous pouvez également utiliser l'astérisque (*) comme joker pour les noms de classes et de méthodes. Par exemple, pour exclure toutes les méthodes indexOf() dans toutes les classes de la compilation, utilisez ce qui suit :

-XX:CompileCommand=exclude,*.indexOf

Les virgules et les points sont des alias pour des espaces, ce qui facilite le passage des commandes de compilation via un interpréteur de commandes. Vous pouvez passer des arguments à -XX:CompileCommand en utilisant des espaces comme séparateurs en entourant l'argument de guillemets :

-XX:CompileCommand="exclude java/lang/String indexOf"

Notez qu'après avoir analysé les commandes passées sur la ligne de commande à l'aide des options -XX:CompileCommand, le compilateur JIT lit ensuite les commandes du fichier .hotspot_compiler. Vous pouvez ajouter des commandes à ce fichier ou spécifier un fichier différent à l'aide de l'option -XX:CompileCommandFile.

Pour ajouter plusieurs commandes, spécifiez l'option -XX:CompileCommand plusieurs fois, ou séparez chaque argument par le séparateur de nouvelle ligne (\n). Les commandes suivantes sont disponibles :

break
Définit un point d'arrêt lors du débogage de la JVM pour s'arrêter au début de la compilation de la méthode spécifiée.
compileonly
Exclut toutes les méthodes de la compilation à l'exception de la méthode spécifiée. Vous pouvez également utiliser l'option -XX:CompileOnly, qui vous permet de spécifier plusieurs méthodes.
dontinline
Empêche l'inlining de la méthode spécifiée.
exclude
Exclut la méthode spécifiée de la compilation.
help
Affiche un message d'aide pour l'option -XX:CompileCommand.
inline
Tente d'inliner la méthode spécifiée.
log
Exclut la journalisation de la compilation (avec l'option -XX:+LogCompilation) pour toutes les méthodes à l'exception de la méthode spécifiée. Par défaut, la journalisation est effectuée pour toutes les méthodes compilées.
option
Passe une option de compilation JIT à la méthode spécifiée à la place du dernier argument (option). L'option de compilation est définie à la fin, après le nom de la méthode. Par exemple, pour activer l'option BlockLayoutByFrequency pour la méthode append() de la classe StringBuffer, utilisez ce qui suit :

-XX:CompileCommand=option,java/lang/StringBuffer.append,BlockLayoutByFrequency

Vous pouvez spécifier plusieurs options de compilation, séparées par des virgules ou des espaces.

print
Affiche le code assembleur généré après la compilation de la méthode spécifiée.
quiet
Indique de ne pas afficher les commandes de compilation. Par défaut, les commandes que vous spécifiez avec l'option -XX:CompileCommand sont affichées ; par exemple, si vous excluez de la compilation la méthode indexOf() de la classe String, alors ce qui suit est affiché sur la sortie standard :

Génère du code de verrouillage Restricted Transactional Memory (RTM) pour tous les verrous gonflés, avec le mécanisme de verrouillage normal comme gestionnaire de secours. Cette option est désactivée par défaut. Les options relatives à RTM ne sont disponibles que sur les processeurs x86 qui prennent en charge les extensions de synchronisation transactionnelle (TSX).

RTM fait partie de TSX d'Intel, qui est un jeu d'instructions x86 étendu et facilite la création d'applications multithreadées. RTM introduit les nouvelles instructions XBEGIN, XABORT, XEND et XTEST. Les instructions XBEGIN et XEND encapsulent un ensemble d'instructions à exécuter comme une transaction. Si aucun conflit n'est trouvé lors de l'exécution de la transaction, les modifications de mémoire et de registre sont validées ensemble à l'instruction XEND. L'instruction XABORT peut être utilisée pour abandonner explicitement une transaction et l'instruction XTEST vérifie si un ensemble d'instructions est en cours d'exécution dans une transaction.

Un verrou sur une transaction est gonflé lorsqu'un autre thread tente d'accéder à la même transaction, bloquant ainsi le thread qui n'a pas initialement demandé l'accès à la transaction. RTM exige qu'un ensemble d'opérations de secours soit spécifié au cas où une transaction serait abandonnée ou échouerait. Un verrou RTM est un verrou qui a été délégué au système TSX.

RTM améliore les performances pour les verrous très contestés avec peu de conflits dans une région critique (qui est du code auquel plus d'un thread ne peut accéder simultanément). RTM améliore également les performances du verrouillage "coarse-grain", qui ne fonctionne généralement pas bien dans les applications multithreadées. (Le verrouillage "coarse-grain" est la stratégie consistant à conserver les verrous pendant de longues périodes pour minimiser les frais de prise et de libération des verrous, tandis que le verrouillage "fine-grain" est la stratégie consistant à essayer d'obtenir un parallélisme maximal en verrouillant uniquement lorsque c'est nécessaire et en déverrouillant dès que possible.) De plus, pour les verrous légèrement contestés utilisés par différents threads, RTM peut réduire le partage de ligne de cache "faux", également connu sous le nom de "cache line ping-pong". Cela se produit lorsque plusieurs threads de processeurs différents accèdent à des ressources différentes, mais que les ressources partagent la même ligne de cache. En conséquence, les processeurs invalident à plusieurs reprises les lignes de cache des autres processeurs, ce qui les oblige à lire à partir de la mémoire principale au lieu de leur cache.

Ces données binaires sont enregistrées dans un fichier nommé hsperfdata_pid, où pid est l'identificateur du processus de l'application Java que vous avez exécutée. Utilisez la commande jstat pour afficher les données de performance contenues dans ce fichier comme suit :

jstat -class file:///chemin/hsperfdata_pid

jstat -gc file:///chemin/hsperfdata_pid

-XX:+UsePerfData
Active la fonctionnalité perfdata. Cette option est activée par défaut pour permettre la surveillance et les tests de performance de la JVM. Sa désactivation supprime la création des répertoires hsperfdata_userid. Pour désactiver la fonctionnalité perfdata, spécifiez -XX:-UsePerfData.

OPTIONS AVANCÉES DE GC POUR JAVA

Ces options java contrôlent la façon dont la collecte des garbage (GC) est effectuée par la JVM Java HotSpot.

-XX:+AggressiveHeap
Active l'optimisation du tas Java. Cela définit divers paramètres pour être optimaux pour les tâches de longue durée avec une allocation de mémoire intensive, en fonction de la configuration de l'ordinateur (RAM et CPU). Par défaut, l'option est désactivée et les tailles de tas sont configurées de manière moins agressive.
-XX:+AlwaysPreTouch
Demande à la JVM de toucher chaque page du tas Java après l'avoir demandée au système d'exploitation et avant de remettre la mémoire à l'application. Par défaut, cette option est désactivée et toutes les pages sont validées au fur et à mesure que l'application utilise l'espace du tas.
-XX:ConcGCThreads=threads
Définit le nombre de threads utilisés pour le GC concurrent. Définit threads à environ 1/4 du nombre de threads de garbage collection parallèles. La valeur par défaut dépend du nombre de CPU disponibles pour la JVM.

Par exemple, pour définir le nombre de threads de GC concurrent à 2, spécifiez l'option suivante :

-XX:ConcGCThreads=2

-XX:+DisableExplicitGC
Active l'option qui désactive le traitement des appels à la méthode System.gc(). Cette option est désactivée par défaut, ce qui signifie que les appels à System.gc() sont traités. Si le traitement des appels à System.gc() est désactivé, la JVM effectue toujours le GC si nécessaire.
-XX:+ExplicitGCInvokesConcurrent
Active l'invocation du GC concurrent en utilisant la requête System.gc(). Cette option est désactivée par défaut et ne peut être activée qu'avec l'option -XX:+UseG1GC.
-XX:G1AdaptiveIHOPNumInitialSamples=nombre
Lorsque -XX:UseAdaptiveIHOP est activé, cette option définit le nombre de cycles de marquage terminés utilisés pour collecter des échantillons jusqu'à ce que G1 détermine de manière adaptative la valeur optimale de -XX:InitiatingHeapOccupancyPercent. Auparavant, G1 utilise directement la valeur de -XX:InitiatingHeapOccupancyPercent à cette fin. La valeur par défaut est 3.
-XX:G1HeapRegionSize=taille
Définit la taille des régions dans lesquelles le tas Java est subdivisé lors de l'utilisation du collecteur garbage-first (G1). La valeur est une puissance de 2 et peut varier de 1 Mo à 32 Mo. La taille de région par défaut est déterminée ergonomiquement en fonction de la taille du tas, avec un objectif d'environ 2048 régions.

L'exemple suivant définit la taille des subdivisions à 16 Mo :

-XX:G1HeapRegionSize=16m

-XX:G1HeapWastePercent=pourcentage
Définit le pourcentage du tas que vous êtes prêt à gaspiller. La JVM Java HotSpot n'initie pas le cycle de garbage collection mixte lorsque le pourcentage récupérable est inférieur au pourcentage de gaspillage du tas. La valeur par défaut est de 5 pour cent.
-XX:G1MaxNewSizePercent=pourcentage
Définit le pourcentage de la taille du tas à utiliser comme maximum pour la taille de la génération jeune. La valeur par défaut est de 60 % de votre tas Java.

Il s'agit d'un indicateur expérimental. Ce paramètre remplace le paramètre -XX:DefaultMaxNewGenPercent.

-XX:G1MixedGCCountTarget=nombre
Définit le nombre cible de garbage collections mixtes après un cycle de marquage pour collecter les régions anciennes avec au plus G1MixedGCLIveThresholdPercent de données vivantes. La valeur par défaut est de 8 garbage collections mixtes. L'objectif pour les collections mixtes est de se situer dans ce nombre cible.
-XX:G1MixedGCLiveThresholdPercent=pourcentage
Définit le seuil d'occupation d'une région ancienne pour qu'elle soit incluse dans un cycle de garbage collection mixte. L'occupation par défaut est de 85 pour cent.

Il s'agit d'un indicateur expérimental. Ce paramètre remplace le paramètre -XX:G1OldCSetRegionLiveThresholdPercent.

-XX:G1NewSizePercent=pourcentage
Définit le pourcentage du tas à utiliser comme minimum pour la taille de la génération jeune. La valeur par défaut est de 5 % de votre tas Java.

Il s'agit d'un indicateur expérimental. Ce paramètre remplace le paramètre -XX:DefaultMinNewGenPercent.

-XX:G1OldCSetRegionThresholdPercent=pourcentage
Définit une limite supérieure au nombre de régions anciennes à collecter pendant un cycle de garbage collection mixte. La valeur par défaut est de 10 % du tas Java.
-XX:G1ReservePercent=pourcentage
Définit le pourcentage du tas (0 à 50) qui est réservé comme faux plafond pour réduire la possibilité d'échec de promotion pour le collecteur G1. Lorsque vous augmentez ou diminuez le pourcentage, assurez-vous d'ajuster le tas Java total du même montant. Par défaut, cette option est définie sur 10 %.

L'exemple suivant définit le tas réservé à 20 % :

-XX:G1ReservePercent=20

-XX:+G1UseAdaptiveIHOP
Contrôle le calcul adaptatif de l'occupation de la génération ancienne pour démarrer un travail en arrière-plan préparant une collection de génération ancienne. S'il est activé, G1 utilise -XX:InitiatingHeapOccupancyPercent pour les premières fois, comme spécifié par la valeur de -XX:G1AdaptiveIHOPNumInitialSamples, et calcule ensuite automatiquement une nouvelle valeur optimale pour l'occupation initiale de manière adaptative. Sinon, le processus de collection de la génération ancienne démarre toujours à l'occupation de la génération ancienne déterminée par -XX:InitiatingHeapOccupancyPercent.

La valeur par défaut est activée.

-XX:InitialHeapSize=taille
Définit la taille initiale (en octets) du pool d'allocation de mémoire. Cette valeur doit être 0, ou un multiple de 1024 et supérieure à 1 Mo. Ajoutez la lettre k ou K pour indiquer les kilo-octets, m ou M pour indiquer les méga-octets, ou g ou G pour indiquer les giga-octets. La valeur par défaut est sélectionnée au moment de l'exécution en fonction de la configuration du système.

Les exemples suivants montrent comment définir la taille de la mémoire allouée à 6 Mo en utilisant différentes unités :


-XX:InitialHeapSize=6291456
-XX:InitialHeapSize=6144k
-XX:InitialHeapSize=6m

Si vous définissez cette option sur 0, la taille initiale est définie comme la somme des tailles allouées pour la génération ancienne et la génération jeune. La taille du tas pour la génération jeune peut être définie à l'aide de l'option -XX:NewSize. Notez que l'option -Xms définit à la fois la taille minimale et la taille initiale du tas. Si -Xms apparaît après -XX:InitialHeapSize sur la ligne de commande, la taille initiale du tas est définie à la valeur spécifiée avec -Xms.

-XX:InitialRAMPercentage=pourcentage
Définit la quantité initiale de mémoire que la JVM utilisera pour le tas Java avant d'appliquer les heuristiques ergonomiques, en pourcentage de la quantité maximale déterminée comme décrit dans l'option -XX:MaxRAM. La valeur par défaut est de 1,5625 pour cent.

L'exemple suivant montre comment définir le pourcentage de la quantité initiale de mémoire utilisée pour le tas Java :

-XX:InitialRAMPercentage=5

-XX:InitialSurvivorRatio=ratio
Définit le ratio initial de l'espace survivant utilisé par le collecteur de garbage de débit (qui est activé par -XX:+UseParall
(option elGC). Le dimensionnement adaptatif est activé par défaut avec le ramasse-miettes de débit en utilisant l'option -XX:+UseParallelGC, et l'espace survivor est redimensionné en fonction du comportement de l'application, en commençant par la valeur initiale. Si le dimensionnement adaptatif est désactivé (en utilisant l'option -XX:-UseAdaptiveSizePolicy), alors l'option -XX:SurvivorRatio doit être utilisée pour définir la taille de l'espace survivor pour toute l'exécution de l'application.

La formule suivante peut être utilisée pour calculer la taille initiale de l'espace survivor (S) en fonction de la taille de la jeune génération (Y) et du rapport initial de l'espace survivor (R) :

S=Y/(R+2)

Le 2 dans l'équation représente deux espaces survivors. Plus la valeur spécifiée pour le rapport initial de l'espace survivor est élevée, plus la taille initiale de l'espace survivor est petite.

Par défaut, le rapport initial de l'espace survivor est défini sur 8. Si la valeur par défaut pour la taille de l'espace de la jeune génération est utilisée (2 Mo), alors la taille initiale de l'espace survivor est de 0,2 Mo.

L'exemple suivant montre comment définir le rapport initial de l'espace survivor sur 4 :

-XX:InitialSurvivorRatio=4

-XX:InitiatingHeapOccupancyPercent=pourcentage
Définit le pourcentage d'occupation de la vieille génération (0 à 100) à partir duquel démarrer les premiers cycles de marquage concurrents pour le ramasse-miettes G1.

Par défaut, la valeur d'initiation est définie sur 45 %. Une valeur de 0 implique des cycles de GC concurrents nonstop à partir du début jusqu'à ce que G1 ajuste cette valeur.

Voir également les options -XX:G1UseAdaptiveIHOP et -XX:G1AdaptiveIHOPNumInitialSamples.

L'exemple suivant montre comment définir l'occupation d'heap d'initiation à 75 % :

-XX:InitiatingHeapOccupancyPercent=75

-XX:MaxGCPauseMillis=temps
Définit une cible pour le temps de pause GC maximal (en millisecondes). C'est un objectif souple, et la JVM fera de son mieux pour l'atteindre. La valeur spécifiée ne s'adapte pas à la taille de votre heap. Par défaut, pour G1, la cible de temps de pause maximal est de 200 millisecondes. Les autres collecteurs générationnels n'utilisent pas de cible de temps de pause par défaut.

L'exemple suivant montre comment définir le temps de pause cible maximal à 500 ms :

-XX:MaxGCPauseMillis=500

-XX:MaxHeapSize=taille
Définit la taille maximale (en octets) du pool d'allocation mémoire. Cette valeur doit être un multiple de 1024 et supérieure à 2 Mo. Ajoutez la lettre k ou K pour indiquer les kilo-octets, m ou M pour indiquer les méga-octets, ou g ou G pour indiquer les giga-octets. La valeur par défaut est sélectionnée au moment de l'exécution en fonction de la configuration du système. Pour les déploiements serveur, les options -XX:InitialHeapSize et -XX:MaxHeapSize sont souvent définies sur la même valeur.

Les exemples suivants montrent comment définir la taille maximale autorisée de mémoire allouée à 80 Mo en utilisant différentes unités :


-XX:MaxHeapSize=83886080
-XX:MaxHeapSize=81920k
-XX:MaxHeapSize=80m

L'option -XX:MaxHeapSize est équivalente à -Xmx.

-XX:MaxHeapFreeRatio=pourcentage
Définit le pourcentage maximal autorisé d'espace libre dans la heap (0 à 100) après un événement GC. Si l'espace libre de la heap dépasse cette valeur, la heap est réduite. Par défaut, cette valeur est définie à 70 %.

Minimisez la taille de la heap Java en abaissant les valeurs des paramètres MaxHeapFreeRatio (valeur par défaut 70 %) et MinHeapFreeRatio (valeur par défaut 40 %) avec les options de ligne de commande -XX:MaxHeapFreeRatio et -XX:MinHeapFreeRatio. Abaisser MaxHeapFreeRatio jusqu'à 10 % et MinHeapFreeRatio jusqu'à 5 % a réussi à réduire la taille de la heap sans trop de régression de performance ; cependant, les résultats peuvent varier considérablement en fonction de votre application. Essayez différentes valeurs pour ces paramètres jusqu'à ce qu'elles soient aussi basses que possible tout en conservant des performances acceptables.

-XX:MaxHeapFreeRatio=10 -XX:MinHeapFreeRatio=5

Les clients qui essaient de maintenir la heap petite devraient également ajouter l'option -XX:-ShrinkHeapInSteps. Définit la quantité maximale de mémoire native pouvant être allouée pour les métadonnées de classe. Par défaut, la taille n'est pas limitée. -XX:MaxMetaspaceSize=256m

-XX:+UseNUMA
Active l'optimisation des performances d'une application sur une machine avec une architecture mémoire non uniforme (NUMA) en augmentant l'utilisation par l'application de la mémoire à latence plus faible. Par défaut, cette option est désactivée et aucune optimisation pour NUMA n'est effectuée. L'option n'est disponible que lorsque le ramasse-miettes parallèle est utilisé (-XX:+UseParallelGC).
-XX:+UseParallelGC
Active l'utilisation du ramasse-miettes parallèle scavenge (également connu sous le nom de collecteur de débit) pour améliorer les performances de votre application en exploitant plusieurs processeurs.

Par défaut, cette option est désactivée et le collecteur par défaut est utilisé.

-XX:+UseSerialGC
Active l'utilisation du ramasse-miettes séquentiel. C'est généralement le meilleur choix pour les petites applications simples qui ne nécessitent aucune fonctionnalité particulière de la collecte des déchets. Par défaut, cette option est désactivée et le collecteur par défaut est utilisé.
-XX:+UseSHM
Linux uniquement : Permet à la JVM d'utiliser la mémoire partagée pour configurer les grandes pages.

Voir Grandes pages pour la configuration des grandes pages.

-XX:+UseStringDeduplication
Active la déduplication des chaînes. Par défaut, cette option est désactivée. Pour utiliser cette option, vous devez activer le ramasse-miettes garbage-first (G1).

La déduplication des chaînes réduit l'empreinte mémoire des objets String sur le heap Java en tirant parti du fait que de nombreux objets String sont identiques. Au lieu que chaque objet String pointe vers son propre tableau de caractères, les objets String identiques peuvent pointer vers et partager le même tableau de caractères.

-XX:+UseTLAB
Active l'utilisation des blocs d'allocation locaux au thread (TLAB) dans l'espace de la génération jeune. Cette option est activée par défaut. Pour désactiver l'utilisation des TLAB, spécifiez l'option -XX:-UseTLAB.
-XX:+UseZGC
Active l'utilisation du ramasse-miettes Z (ZGC). C'est un ramasse-miettes à faible latence, fournissant des temps de pause maxima de quelques millisecondes, au prix d'un certain coût en débit. Les temps de pause sont indépendants de la taille du heap utilisée. Prend en charge des tailles de heap de 8 Mo à 16 To.
-XX:ZAllocationSpikeTolerance=facteur
Définit la tolérance aux pics d'allocation pour ZGC. Par défaut, cette option est définie à 2,0. Ce facteur décrit le niveau des pics d'allocation à attendre. Par exemple, l'utilisation d'un facteur de 3,0 signifie que le taux d'allocation actuel peut tripler à tout moment.
-XX:ZCollectionInterval=secondes
Définit l'intervalle maximal (en secondes) entre deux cycles de GC lors de l'utilisation de ZGC. Par défaut, cette option est définie à 0 (désactivé).
-XX:ZFragmentationLimit=pourcentage
Définit la fragmentation maximale acceptable du heap (en pourcentage) pour ZGC. Par défaut, cette option est définie à 25. L'utilisation d'une valeur plus basse entraînera une compaction plus agressive du heap, pour récupérer plus de mémoire au prix d'une utilisation accrue du temps CPU.
-XX:+ZProactive
Active les cycles de GC proactifs lors de l'utilisation de ZGC. Par défaut, cette option est activée. ZGC démarrera un cycle de GC proactif si cela est prévu d'avoir un impact minimal sur l'application en cours d'exécution. C'est utile si l'application est principalement inactive ou alloue très peu d'objets, mais que vous souhaitez toujours maintenir la taille du heap basse et permettre le traitement des références même lorsqu'il y a beaucoup d'espace libre sur le heap.
-XX:+ZUncommit
Active le désengagement (uncommit) de la mémoire de heap inutilisée lors de l'utilisation de ZGC. Par défaut, cette option est activée. Le désengagement de la mémoire de heap inutilisée réduira l'empreinte mémoire de la JVM et rendra cette mémoire disponible pour d'autres processus.
-XX:ZUncommitDelay=secondes
Définit la duréetemps (en secondes) pendant lequel la mémoire du tas doit être inutilisée avant d'être désengagée. Par défaut, cette option est définie à 300 (5 minutes). L'engagement et le désengagement de la mémoire sont des opérations relativement coûteuses. L'utilisation d'une valeur inférieure entraînera le désengagement de la mémoire du tas plus tôt, au risque de devoir la réengager bientôt.

FICHIERS DARGUMENTS DE COMMANDE JAVA

Vous pouvez raccourcir ou simplifier la commande java en utilisant des fichiers d'arguments @ pour spécifier un ou plusieurs fichiers texte contenant des arguments, tels que des options et des noms de classe, qui sont passés à la commande java. Cela vous permet de créer des commandes java de n'importe quelle longueur sur n'importe quel système d'exploitation.

Dans la ligne de commande, utilisez le préfixe arobase (@) pour identifier un fichier d'arguments contenant des options et des noms de classe Java. Lorsque la commande java rencontre un fichier commençant par l'arobase (@), elle développe le contenu de ce fichier en une liste d'arguments, comme s'ils étaient spécifiés sur la ligne de commande.

Le lanceur java développe le contenu du fichier d'arguments jusqu'à ce qu'il rencontre l'option --disable-@files. Vous pouvez utiliser l'option --disable-@files n'importe où dans la ligne de commande, y compris dans un fichier d'arguments, pour arrêter le développement des fichiers d'arguments @.

Les éléments suivants décrivent la syntaxe des fichiers d'arguments Java :

•
Le fichier d'arguments doit contenir uniquement des caractères ASCII ou des caractères dans le codage système par défaut qui soit compatible avec ASCII, tel que UTF-8.
•
La taille du fichier d'arguments ne doit pas dépasser MAXINT (2 147 483 647) octets.
•
Le lanceur ne développe pas les caractères génériques présents dans un fichier d'arguments.
•
Utilisez des espaces ou des caractères de nouvelle ligne pour séparer les arguments inclus dans le fichier.
•
Les espaces incluent un caractère d'espace blanc, \t, \n, \r et \f.

•

•

•

Lors de l'utilisation de file=nom_fichier, la spécification de %p et/ou %t dans le nom du fichier est développée en PID de la JVM et en horodatage de démarrage, respectivement. Vous pouvez également configurer les fichiers texte pour gérer la rotation des fichiers en fonction de la taille du fichier et du nombre de fichiers à faire pivoter. La taille cible des fichiers n'est pas garantie d'être exacte, c'est juste une valeur approximative. Les fichiers sont mis en rotation par défaut avec jusqu'à 5 fichiers mis en rotation d'une taille cible de 20 Mo, sauf configuration contraire. Par défaut, les messages de journalisation sont affichés de manière synchrone - chaque message de journal est écrit dans la sortie désignée lorsque l'appel de journalisation est effectué. Mais vous pouvez utiliser le mode de journalisation asynchrone en spécifiant :

-Xlog:async
Écrit toute la journalisation de manière asynchrone.

En mode de journalisation asynchrone, les sites de journalisation mettent en file d'attente tous les messages de journalisation dans un tampon intermédiaire et un thread autonome est responsable de les vider vers les sorties correspondantes. Le tampon intermédiaire est limité et en cas d'épuisement du tampon, le message mis en file d'attente est rejeté. Les opérations d'écriture d'entrées de journal sont garanties non bloquantes.

L'option -XX:AsyncLogBufferSize=N spécifie le budget mémoire en octets pour le tampon intermédiaire. La valeur par défaut devrait être suffisamment grande pour la plupart des cas. Les utilisateurs peuvent fournir une valeur personnalisée pour échanger la surcharge de mémoire contre la précision des journaux s'ils le souhaitent.

Décorations

Les messages de journalisation sont décorés d'informations sur le message. Vous pouvez configurer chaque sortie pour utiliser un ensemble personnalisé de décorateurs. L'ordre de la sortie est toujours le même que celui indiqué dans le tableau. Vous pouvez configurer les décorations à utiliser à l'exécution. Les décorations sont ajoutées avant le message de journal. Par exemple :


[6.567s][info][gc,old] Old collection complete

Omettre les décorateurs utilise par défaut l'uptime, le niveau et les balises. Le décorateur 'none' est spécial et sert à désactiver toutes les décorations.

VALIDATION DES ARGUMENTS DES FLAGS DE LA MACHINE VIRTUELLE JAVA

Vous utilisez les valeurs fournies à tous les arguments de ligne de commande des flags de la Machine Virtuelle Java (JVM) pour la validation et, si la valeur d'entrée est invalide ou hors limites, un message d'erreur approprié est affiché.

Qu'ils soient définis de manière ergonomique, dans une ligne de commande, par un outil d'entrée ou via les API (par exemple, les classes contenues dans le package java.lang.management), les valeurs fournies à tous les arguments de ligne de commande des Machine Virtuelle Java (JVM) sont validées. L'ergonomie est décrite dans le Guide de réglage du garbage collection de la machine virtuelle HotSpot de la plateforme Java, édition Standard.

Les plages et les contraintes sont validées soit lorsque toutes les valeurs des flags sont définies lors de l'initialisation de la JVM, soit lorsqu'une valeur de flag est modifiée pendant l'exécution (par exemple, à l'aide de l'outil jcmd). La JVM se termine si une valeur viole la vérification de plage ou de contrainte et un message d'erreur approprié est imprimé sur le flux d'erreurs.

Par exemple, si un flag viole une vérification de plage ou de contrainte, la JVM se termine avec une erreur :


java -XX:AllocatePrefetchStyle=5 -version
intx AllocatePrefetchStyle=5 est en dehors de la plage autorisée [ 0 ... 3 ]
Option VM incorrectement spécifiée 'AllocatePrefetchStyle=5'
Erreur : Impossible de créer la machine virtuelle Java.
Erreur : Une exception fatale s'est produite. Le programme va se terminer.

Le flag -XX:+PrintFlagsRanges imprime la plage de tous les flags. Ce flag permet le test automatique des flags par les valeurs fournies par les plages. Pour les flags dont les plages sont spécifiées, le type, le nom et la plage réelle sont imprimés dans la sortie.

Par exemple,


intx   ThreadStackSize [ 0 ... 9007199254740987 ] {pd product}

Pour les flags dont la plage n'est pas spécifiée, les valeurs ne sont pas affichées dans la sortie. Par exemple :


size_t NewSize         [   ...                  ] {product}

Cela aide à identifier les flags qui doivent être implémentés. Le framework de test automatique peut ignorer les flags qui n'ont pas de valeurs et qui ne sont pas implémentés.

GRANDES PAGES

Vous utilisez les grandes pages, également appelées pages énormes, comme pages mémoire qui sont significativement plus grandes que la taille de page mémoire standard (qui varie en fonction du processeur et du système d'exploitation). Les grandes pages optimisent les tampons de traduction (TLB) du processeur.

Un tampon de traduction de page (TLB) est un cache de traduction de page qui contient les traductions d'adresses virtuelles en physiques les plus récemment utilisées. Un TLB est une ressource système rare. Une erreur de TLB peut être coûteuse car le processeur doit alors lire à partir de la table des pages hiérarchique, ce qui peut nécessiter plusieurs accès mémoire. En utilisant une taille de page mémoire plus grande, une seule entrée TLB peut représenter une plage mémoire plus grande. Cela exerce moins de pression sur un TLB, et les applications gourmandes en mémoire peuvent avoir de meilleures performances.

Cependant, l'utilisation de grandes pages peut affecter négativement les performances du système. Par exemple, lorsqu'une grande quantité de mémoire est épinglée par une application, cela peut créer une pénurie de mémoire régulière et entraîner un pagination excessive des autres applications et ralentir l'ensemble du système. De plus, un système qui fonctionne depuis longtemps peut produire une fragmentation excessive, ce qui peut rendre impossible la réservation de suffisamment de mémoire de grandes pages. Lorsque cela se produit, soit le système d'exploitation, soit la JVM revient à l'utilisation de pages régulières.

Linux et Windows prennent en charge les grandes pages.

Prise en charge des grandes pages pour Linux

Linux prend en charge les grandes pages depuis la version 2.6. Pour vérifier si votre environnement prend en charge les grandes pages, essayez ce qui suit :


# cat /proc/meminfo | grep Huge
HugePages_Total: 0
HugePages_Free: 0
...
Hugepagesize: 2048 kB

Si la sortie contient des éléments précédés de "Huge", votre système prend en charge les grandes pages. Les valeurs peuvent varier en fonction de l'environnement. Le champ Hugepagesize indique la taille de grande page par défaut dans votre environnement, et les autres champs montrent les détails des grandes pages de cette taille. Les noyaux plus récents prennent en charge plusieurs tailles de grandes pages. Pour lister les tailles de page prises en charge, exécutez ceci :


# ls /sys/kernel/mm/hugepages/
hugepages-1048576kB  hugepages-2048kB

L'environnement ci-dessus prend en charge les grandes pages de 2 Mo et 1 Go, mais elles doivent être configurées pour que la JVM puisse les utiliser. Lors de l'utilisation de grandes pages et de la désactivation des pages énormes transparentes (option -XX:+UseTransparentHugePages), le nombre de grandes pages doit être pré-alloué. Par exemple, pour allouer 8 Go de mémoire pour être prise en charge par de grandes pages de 2 Mo, connectez-vous en tant que root et exécutez :

# echo 4096 > /sys/kernel/mm/hugepages/hugepages-2048kB/nr_hugepages

Il est toujours recommandé

terminé pour vérifier la valeur de nr_hugepages après la demande afin de s'assurer que le noyau a pu allouer le nombre demandé de pages géantes.

Lorsque vous utilisez l'option -XX:+UseSHM pour activer les pages géantes, vous devez également vous assurer que le paramètre SHMMAX est configuré pour permettre l'allocation de segments de mémoire partagée suffisamment grands. Pour permettre un segment partagé maximum de 8 Go, connectez-vous en tant que root et exécutez :

# echo 8589934592 > /proc/sys/kernel/shmmax

Dans certains environnements, cela n'est pas nécessaire car la valeur par défaut est suffisamment grande, mais il est important de s'assurer que la valeur est suffisamment grande pour contenir la quantité de mémoire destinée à être prise en charge par les pages géantes.

Remarque : Les valeurs contenues dans /proc et /sys sont réinitialisées après le redémarrage de votre système ; vous pouvez donc vouloir les définir dans un script d'initialisation (par exemple, rc.local ou sysctl.conf).

Si vous configurez les paramètres du noyau du système d'exploitation pour activer l'utilisation des pages géantes, les processus Java peuvent allouer des pages géantes pour le tas Java ainsi que pour d'autres zones internes, par exemple :

•
Cache de code
•
Bitmaps de marquage

Par conséquent, si vous configurez le paramètre nr_hugepages à la taille du tas Java, la JVM peut tout de même échouer à allouer le tas à l'aide de pages géantes, car d'autres zones telles que le cache de code peuvent avoir déjà utilisé certaines des pages géantes configurées.

Prise en charge des grandes pages pour Windows

Pour utiliser la prise en charge des grandes pages sur Windows, l'administrateur doit d'abord attribuer des privilèges supplémentaires à l'utilisateur qui exécute l'application :

1.
Sélectionnez Panneau de configuration, Outils d'administration, puis Stratégie de sécurité locale.
2.
Sélectionnez Stratégies locales puis Attribution des droits utilisateur.
3.
Double-cliquez sur Verrouiller les pages en mémoire, puis ajoutez des utilisateurs et/ou des groupes.
4.
Redémarrez votre système.

Notez que ces étapes sont requises même si c'est l'administrateur qui exécute l'application, car les administrateurs n'ont pas par défaut le privilègue de verrouiller les pages en mémoire.

PARTAGE DES DONNÉES DE CLASSE D'APPLICATION

Le partage des données de classe d'application (AppCDS) stocke les classes utilisées par vos applications dans un fichier d'archive. Comme ces classes sont stockées dans un format qui peut être chargé très rapidement (par rapport aux classes stockées dans un fichier JAR), AppCDS peut améliorer le temps de démarrage de vos applications. De plus, AppCDS peut réduire l'empreinte mémoire d'exécution en partageant des parties de ces classes entre plusieurs processus.

Les classes dans l'archive CDS sont stockées dans un format optimisé qui est environ 2 à 5 fois plus volumineux que les classes stockées dans les fichiers JAR ou l'image d'exécution du JDK. Il est donc judicieux de n'archiver que les classes réellement utilisées par votre application. Ce sont généralement seulement une petite portion de toutes les classes disponibles. Par exemple, votre application peut n'utiliser que quelques API fournies par une grande bibliothèque.

Utilisation des archives CDS

Par défaut, dans la plupart des distributions JDK, sauf si -Xshare:off est spécifié, la JVM démarre avec une archive CDS par défaut, qui se trouve généralement dans JAVA_HOME/lib/server/classes.jsa (ou JAVA_HOME\bin\server\classes.jsa sous Windows). Cette archive contient environ 1300 classes de bibliothèque de base utilisées par la plupart des applications.

Pour utiliser CDS pour l'ensemble exact des classes utilisées par votre application, vous pouvez utiliser l'option -XX:SharedArchiveFile, qui a la forme générale :

-XX:SharedArchiveFile=<static_archive>:<dynamic_archive>

•
Le <static_archive> remplace l'archive CDS par défaut.
•
Le <dynamic_archive> fournit des classes supplémentaires qui peuvent être chargées par-dessus celles du <static_archive>.
•
Sous Windows, le délimiteur de chemin : ci-dessus doit être remplacé par ;

(Les noms « static » et « dynamic » sont utilisés pour des raisons historiques. La seule signification est que l'archive « static » est chargée en premier et que l'archive « dynamic » est chargée en second).

La JVM peut utiliser jusqu'à deux archives. Pour utiliser uniquement un seul <static_archive>, vous pouvez omettre la portion <dynamic_archive> :

-XX:SharedArchiveFile=<static_archive>

Par commodité, le <dynamic_archive> enregistre l'emplacement du <static_archive>. Vous pouvez donc omettre le <static_archive> en indiquant simplement :

-XX:SharedArchiveFile=<dynamic_archive>

Création manuelle des archives CDS

Les archives CDS peuvent être créées manuellement à l'aide de plusieurs méthodes :

•
-Xshare:dump
•
-XX:ArchiveClassesAtExit
•
jcmd VM.cds

Une opération commune à toutes ces méthodes est une « exécution d'essai », où vous exécutez l'application une fois pour déterminer les classes qui doivent être stockées dans l'archive.

Création d'un fichier d'archive CDS statique avec -Xshare:dump

Les étapes suivantes créent un fichier d'archive CDS statique qui contient toutes les classes utilisées par l'application test.Hello.

1.
Créez une liste de toutes les classes utilisées par l'application test.Hello. La commande suivante crée un fichier nommé hello.classlist qui contient une liste de toutes les classes utilisées par cette application :

java -Xshare:off -XX:DumpLoadedClassList=hello.classlist -cp hello.jar test.Hello

Le chemin de classe spécifié par le paramètre -cp ne doit contenir que des fichiers JAR.

2.
Créez une archive statique, nommée hello.jsa, qui contient toutes les classes de hello.classlist :

java -Xshare:dump -XX:SharedArchiveFile=hello.jsa -XX:SharedClassListFile=hello.classlist -cp hello.jar

3.
Exécutez l'application test.Hello avec l'archive hello.jsa :

java -XX:SharedArchiveFile=hello.jsa -cp hello.jar test.Hello

4.
Facultatif Vérifiez que l'application test.Hello utilise la classe contenue dans l'archive partagée hello.jsa :

java -XX:SharedArchiveFile=hello.jsa -cp hello.jar -Xlog:class+load test.Hello

La sortie de cette commande doit contenir le texte suivant :

[info][class,load] test.Hello source: shared objects file

Création d'un fichier d'archive CDS dynamique avec -XX:ArchiveClassesAtExit

Les avantages des archives CDS dynamiques sont les suivants :

•
Elles utilisent généralement moins d'espace disque, car elles n'ont pas besoin de stocker les classes qui sont déjà dans l'archive statique.
•
Elles sont créées avec une étape de moins que l'archive statique équivalente.

Les étapes suivantes créent un fichier d'archive CDS dynamique qui contient les classes utilisées par l'application test.Hello, à l'exclusion de celles qui sont déjà dans l'archive CDS par défaut.

1.
Créez une archive CDS dynamique, nommée hello.jsa, qui contient toutes les classes de hello.jar chargées par l'application test.Hello :

java -XX:ArchiveClassesAtExit=hello.jsa -cp hello.jar Hello

2.
Exécutez l'application test.Hello avec l'archive partagée hello.jsa :

java -XX:SharedArchiveFile=hello.jsa -cp hello.jar test.Hello

3.
Facultatif Répétez l'étape 4 de la section précédente pour vérifier que l'application test.Hello utilise la classe contenue dans l'archive partagée hello.jsa.

Il est également possible de créer une archive CDS dynamique avec une archive CDS statique non par défaut. Par exemple :

java -XX:SharedArchiveFile=base.jsa -XX:ArchiveClassesAtExit=hello.jsa -cp hello.jar Hello

Pour exécuter l'application en utilisant cette archive CDS dynamique :

java -XX:SharedArchiveFile=base.jsa:hello.jsa -cp hello.jar Hello

(Sous Windows, le délimiteur de chemin : ci-dessus doit être remplacé par ;)

Comme mentionné ci-dessus, le nom de l'archive statique peut être ignoré :

java -XX:SharedArchiveFile=hello.jsa -cp hello.jar Hello

Création de fichiers d'archive CDS avec jcmd

Les deux sections précédentes vous obligent à modifier le script de démarrage de l'application afin de créer une archive CDS. Cela peut parfois être difficile, par exemple si le chemin de classe de l'application est défini par des routines complexes.

La commande jcmd VM.cds fournit une méthode moins intrusive pour créer une archive CDS en se connectant à un processus JVM en cours d'exécution. Vous pouvez créer soit une archive statique :

jcmd <pid> VM.cds static_dump my_static_archive.jsa

soit une archive dynamique :

jcmd <pid> VM.cds dynamic_dump my_dynamic_archive.jsa

Pour utiliser le fichier d'archive résultant lors d'une exécution ultérieure de l'application sans modifier le script de démarrage de l'application, vous pouvez utiliser la technique suivante :

env JAVA_TOOL_OPTIONS=-XX:SharedArchiveFile=my_static_archive.jsa bash app_start.sh

Remarque : pour utiliser jcmd <pid> VM.cds dynamic_dump, le processus JVM identifié par <pid> doit être démarré avec -XX:+RecordDynamicDumpInfo, qui peut également être transmis à l'applicatiau script de démarrage avec la même technique :

env JAVA_TOOL_OPTIONS=-XX:+RecordDynamicDumpInfo bash app_start.sh

Création d'un fichier d'archive CDS dynamique avec -XX:+AutoCreateSharedArchive

-XX:+AutoCreateSharedArchive est une méthode plus pratique pour créer/utiliser des archives CDS. Contrairement aux méthodes de création manuelle d'archives CDS décrites dans la section précédente, avec -XX:+AutoCreateSharedArchive, il n'est plus nécessaire d'effectuer une exécution d'essai séparée. À la place, vous pouvez toujours exécuter l'application avec la même ligne de commande et profiter automatiquement des avantages de CDS.

java -XX:+AutoCreateSharedArchive -XX:SharedArchiveFile=hello.jsa -cp hello.jar Hello

Si le fichier d'archive spécifié existe et a été créé par la même version du JDK, il sera chargé en tant qu'archive dynamique ; sinon, il est ignoré au démarrage de la VM.

À la sortie de la VM, si le fichier d'archive spécifié n'existe pas, il sera créé. S'il existe mais a été créé avec une version différente (mais postérieure à JDK 19) du JDK, il sera remplacé. Dans les deux cas, l'archive sera prête à être chargée la prochaine fois que la JVM sera lancée avec la même ligne de commande.

Si le fichier d'archive spécifié existe mais a été créé par une version du JDK antérieure à JDK 19, il sera ignoré : ni chargé au démarrage, ni remplacé à la sortie.

Les développeurs doivent noter que le contenu du fichier d'archive CDS est spécifique à chaque compilation du JDK. Par conséquent, si vous passez à une compilation différente du JDK, -XX:+AutoCreateSharedArchive recréera automatiquement l'archive pour correspondre au JDK. Si vous prévoyez d'utiliser cette fonctionnalité avec une archive existante, vous devez vous assurer que l'archive est créée par au moins la version 19 du JDK.

Restrictions sur le chemin de classe et le chemin de module

•
Ni le chemin de classe (-classpath et -Xbootclasspath/a) ni le chemin de module (--module-path) ne peuvent contenir de répertoires non vides.
•
Seuls les fichiers JAR modulaires sont pris en charge dans --module-path. Les modules éclatés (exploded) ne sont pas pris en charge.
•
Le chemin de classe utilisé au moment de la création de l'archive doit être identique à (ou un préfixe de) celui utilisé à l'exécution. (Il n'y a pas une telle exigence pour le chemin de module.)
•
L'archive CDS ne peut pas être chargée si des fichiers JAR du chemin de classe ou du chemin de module sont modifiés après la génération de l'archive.
•
Si l'une des options de VM --upgrade-module-path, --patch-module ou --limit-modules est spécifiée, CDS est désactivé. Cela signifie que la JVM s'exécutera sans charger d'archives CDS. De plus, si vous essayez de créer une archive CDS avec l'une de ces 3 options spécifiées, la JVM signalera une erreur.

EXEMPLES DE RÉGLAGE DES PERFORMANCES

Vous pouvez utiliser les options avancées d'exécution Java pour optimiser les performances de vos applications.

Réglage pour un débit plus élevé

Utilisez les commandes et options avancées suivantes pour obtenir un débit plus élevé pour votre application :

java -server -XX:+UseParallelGC -XX:+UseLargePages -Xmn10g -Xms26g -Xmx26g

Réglage pour un temps de réponse plus faible

Utilisez les commandes et options avancées suivantes pour obtenir des temps de réponse plus faibles pour votre application :

java -XX:+UseG1GC -XX:MaxGCPauseMillis=100

Maintenir le tas Java petit et réduire l'empreinte dynamique des applications embarquées

Utilisez les options d'exécution avancées suivantes pour maintenir le tas Java petit et réduire l'empreinte dynamique des applications embarquées :

-XX:MaxHeapFreeRatio=10 -XX:MinHeapFreeRatio=5

Remarque : Les valeurs par défaut de ces deux options sont respectivement 70 % et 40 %. Étant donné que des compromis de performance peuvent survenir lors de l'utilisation de ces petits réglages, vous devriez optimiser pour une petite empreinte en réduisant ces réglages autant que possible sans introduire une dégradation de performance inacceptable.
