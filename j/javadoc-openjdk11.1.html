FICHIERS DE COMMENTAIRES DE PAQUET

Pour créer un fichier de commentaires de paquet, vous pouvez placer vos commentaires dans l'un des fichiers suivants :

•
Le fichier package-info.java peut contenir la déclaration de paquet, les annotations de paquet, les commentaires de paquet et les balises Javadoc. Ce fichier est préféré.
•
Le fichier package.html contient uniquement les commentaires de paquet et les balises Javadoc. Pas d'annotations de paquet.

Un paquet peut avoir un seul fichier package.html ou un seul fichier package-info.java, mais pas les deux. Placez l'un ou l'autre fichier dans le répertoire du paquet dans l'arborescence source avec vos fichiers source.

Le fichier package-info.java

Le fichier package-info.java peut contenir un commentaire de paquet de la structure suivante. Le commentaire est placé avant la déclaration de paquet.

Note : Les séparateurs de commentaires /** et */ doivent être présents, mais les astérisques de début sur les lignes intermédiaires peuvent être omis.

 * @since 1.0
 * @see java.awt

package java.lang.applet;

Le fichier package.html est un fichier HTML typique et n'inclut pas de déclaration de paquet. Le contenu du fichier de commentaires de paquet est écrit en HTML, à une exception près. Le commentaire de documentation ne doit pas inclure les séparateurs de commentaires /** et */ ni les astérisques de début. Lors de la rédaction du commentaire, faites de la première phrase un résumé sur le paquet, et ne mettez pas de titre ni d'autre texte entre la balise <body> et la première phrase. Vous pouvez inclure des balises de paquet. Toutes les balises de bloc doivent apparaître après la description principale. Si vous ajoutez une balise @see dans un fichier de commentaires de paquet, elle doit avoir un nom entièrement qualifié.

Traitement du fichier de commentaires

Lorsque la commande javadoc s'exécute, elle recherche le fichier de commentaires de paquet. Si le fichier de commentaires de paquet est trouvé, la commande javadoc effectue les actions suivantes :

•
Copie le commentaire pour traitement. Pour package.html, la commande javadoc copie tout le contenu entre les balises HTML <body> et </body>. Vous pouvez inclure une section <head> pour mettre une balise <title>, une déclaration de copyright du fichier source ou d'autres informations, mais rien de tout cela n'apparaît dans la documentation générée.
•
Traite les balises de paquet. Voir Balises de paquet.
•
Insère le texte traité en bas de la page de résumé du paquet générée. Voir Aperçu de la spécification de l'API Java Platform, Standard Edition à l'adresse http://docs.oracle.com/javase/8/docs/api/overview-summary.html
•
Copie la première phrase du commentaire de paquet en haut de la page de résumé du paquet. La commande javadoc ajoute également le nom du paquet et cette première phrase à la liste des paquets sur la page d'aperçu. Voir Aperçu de la spécification de l'API Java Platform, Standard Edition à l'adresse http://docs.oracle.com/javase/8/docs/api/overview-summary.html

La fin de la phrase est déterminée par les mêmes règles que celles utilisées pour la fin de la première phrase des descriptions principales de classes et de membres.

FICHIERS DE COMMENTAIRES D'APERÇU

Chaque application ou ensemble de paquets que vous documentez peut avoir son propre commentaire de documentation d'aperçu qui est conservé dans son propre fichier source, que la commande javadoc fusionne dans la page d'aperçu générée. Vous incluez généralement dans ce commentaire toute documentation qui s'applique à l'ensemble de l'application ou de l'ensemble des paquets.

Vous pouvez nommer le fichier comme vous le souhaitez, par exemple overview.html, et le placer n'importe où. Un emplacement typique est en haut de l'arborescence source.

Par exemple, si les fichiers source du paquet java.applet sont contenus dans le répertoire /home/user/src/java/applet, vous pouvez alors créer un fichier de commentaires d'aperçu à l'adresse /home/user/src/overview.html.

Vous pouvez avoir plusieurs fichiers de commentaires d'aperçu pour le même ensemble de fichiers source au cas où vous voudriez exécuter la commande javadoc plusieurs fois sur différents ensembles de paquets. Par exemple, vous pourriez exécuter la commande javadoc une fois avec -private pour la documentation interne et une autre fois sans cette option pour la documentation publique. Dans ce cas, vous pourriez décrire la documentation comme publique ou interne dans la première phrase de chaque fichier de commentaires d'aperçu.

Le contenu du fichier de commentaires d'aperçu est un grand commentaire de documentation écrit en HTML. Faites de la première phrase un résumé sur l'application ou l'ensemble des paquets. Ne placez pas de titre ni d'autre texte entre la balise <body> et la première phrase. Toutes les balises, à l'exception des balises en ligne comme une balise {@link}, doivent apparaître après la description principale. Si vous ajoutez une balise @see, elle doit avoir un nom entièrement qualifié.

Lorsque vous exécutez la commande javadoc, spécifiez le nom du fichier de commentaires d'aperçu avec l'option -overview. Le fichier est ensuite traité de manière similaire à celle d'un fichier de commentaires de paquet. La commande javadoc effectue les actions suivantes :

•
Copie tout le contenu entre les balises <body> et </body> pour le traitement.
•
Traite les balises d'aperçu présentes. Voir Balises d'aperçu.
•
Insère le texte traité en bas de la page d'aperçu générée. Voir Aperçu de la spécification Java Platform Standard Edition à l'adresse http://docs.oracle.com/javase/8/docs/api/overview-summary.html
•
Copie la première phrase du commentaire d'aperçu en haut de la page de résumé de l'aperçu.

FICHIERS NON&#x00A0;TRAITÉS

Vos fichiers source peuvent inclure tous les fichiers que vous souhaitez que la commande javadoc copie dans le répertoire de destination. Ces fichiers incluent généralement des fichiers graphiques, des exemples de fichiers source et de classe Java, ainsi que des fichiers HTML autonomes avec une grande quantité de contenu qui submergerait le commentaire de documentation d'un fichier source Java typique.

Pour inclure des fichiers non traités, placez-les dans un répertoire appelé doc-files. Le répertoire doc-files peut être un sous-répertoire de n'importe quel répertoire de paquet contenant des fichiers source. Vous pouvez avoir un sous-répertoire doc-files pour chaque paquet.

Par exemple, si vous souhaitez inclure l'image d'un bouton dans la documentation de la classe java.awt.Button, placez le fichier image dans le répertoire /home/user/src/java/awt/doc-files/. Ne placez pas le répertoire doc-files à /home/user/src/java/doc-files/, car java n'est pas un paquet. Il ne contient aucun fichier source.

Tous les liens vers les fichiers non traités doivent être inclus dans le code, car la commande javadoc n'examine pas les fichiers. La commande javadoc copie le répertoire et tout son contenu dans la destination. L'exemple suivant montre à quoi pourrait ressembler le lien dans le commentaire de documentation de Button.java :

/**
 * Ce bouton ressemble à ceci : 
 * <img src="doc-files/Button.gif">
 */

FICHIERS&#x00A0;DE&#x00A0;TEST&#x00A0;ET&#x00A0;DE&#x00A0;MODÈLE

Vous pouvez stocker des fichiers de test et des fichiers modèles dans l'arborescence source, dans le même répertoire que les fichiers source ou dans un sous-répertoire de celui-ci. Pour empêcher le traitement des fichiers de test et des fichiers modèles, exécutez la commande javadoc et passez explicitement les noms de fichiers source individuels.

Les fichiers de test sont des fichiers source valides et compilables. Les fichiers modèles ne sont pas des fichiers source valides et compatibles, mais ils ont souvent le suffixe .java.

Fichiers de test

Si vous souhaitez que vos fichiers de test appartiennent à un paquet sans nom ou à un paquet autre que celui dans lequel se trouvent les fichiers source, placez les fichiers de test dans un sous-répertoire sous les fichiers source et donnez au répertoire un nom invalide. Si vous placez les fichiers de test dans le même répertoire que les sources et appelez la commande javadoc avec un argument de ligne de commande qui indique son nom de paquet, les fichiers de test provoqueront des avertissements ou des erreurs. Si les fichiers se trouvent dans un sous-répertoire avec un nom invalide, le répertoire des fichiers de test sera ignoré et aucune erreur ou avertissement ne sera émis. Par exemple, pour ajouter des fichiers de test pour des fichiers source dans com.package1, placez-les dans un sous-répertoire avec un nom de paquet invalide. Le nom de répertoire suivant est invalide car il contient un trait d'union :

com/package1/test-files/

Si vos fichiers de test contiennent des commentaires de documentation, vous pouvez configurer une exécution distincte de la commande javadoc pour générer la documentation des fichiers de test en passant leurs noms de fichiers source de test avec des caractères génériques, tels que com/package1/test-files/*.java.

GÉNÉRÉES

La commande javadoc génère une déclaration au début de la description de chaque classe, interface, champ, constructeur et méthode pour cet élément d'API. Par exemple, la déclaration pour la classe Boolean est

: 
public final class
Boolean 
extends
Object 
implements
Serializable

La déclaration pour la méthode Boolean.valueOf est

: 
public static Boolean valueOf(String
s)

La commande javadoc peut inclure les modificateurs public, protected, private, abstract, final, static, transient et volatile, mais pas synchronized ou native. Les modificateurs synchronized et native sont considérés comme des détails d'implémentation et ne font pas partie de la spécification de

l'API.

Plutôt que de s'appuyer sur le mot-clé synchronized, les API devraient documenter leur sémantique de concurrence dans la description principale du commentaire. Par exemple, une description pourrait être : Une énumération unique ne peut pas être utilisée simultanément par plusieurs threads. Le document ne devrait pas décrire comment obtenir ces sémantiques. Comme autre exemple, bien que l'option Hashtable devrait être thread-safe, il n'y a aucune raison de spécifier que cela est obtenu en synchroni

sant toutes ses méthodes exportées. Il est préférable de
se réserver le droit de synchroniser en interne au
niveau des buckets pour une concurrence plus élevée.

DOCUMENTATION

Cette section décrit les commentaires du code source et l'héritage des

commentaires.

COMMENTAIRES DU CODE

SOURCE

Vous pouvez inclure des commentaires de documentation dans le code source, avant les déclarations de n'importe quelle classe, interface, méthode, constructeur ou champ. Vous pouvez également créer des commentaires de documentation pour chaque package et un autre pour l'aperçu, bien que leur syntaxe soit légèrement différente. Un commentaire de documentation se compose des caractères entre /** et */ qui le terminent. Des astérisques de début sont autorisés sur chaque ligne et sont décrits plus en détail dans la section suivante. Le texte d'un commentaire peut se poursuivre sur plusieurs

lignes. 
/*
* 
 * Ceci est le format typique d'un simple commentaire de
documentation 
 * qui s'étend sur deux
lignes. 
 *
/

Pour économiser de l'espace, vous pouvez mettre un commentaire sur une seule ligne

: 
/** Ce commentaire ne prend qu'une seule ligne.
*/

Emplacement des

commentaires

Les commentaires de documentation ne sont reconnus que lorsqu'ils sont placés immédiatement avant les déclarations de classe, interface, constructeur, méthode ou champ. Les commentaires de documentation placés dans le corps d'une méthode sont ignorés. La commande javadoc ne reconnaît qu'un seul commentaire de documentation par instruction de déclaration. Voir Où les balises peuvent être

utilisées.

Une erreur courante est de mettre une instruction import entre le commentaire de classe et la déclaration de la classe. Ne mettez pas d'instruction import à cet endroit car la commande javadoc ignore le commentaire de

classe. 
/*
* 
 * Ceci est le commentaire de la classe
Whatever. 
 *
/ 
import com.example;   // ERREUR - Important de ne pas mettre d'instruction import
ici 
public class Whatever{
}

Parties des

commentaires

Un commentaire de documentation a une description principale suivie d'une section de balises. La description principale commence après le délimiteur de début /** et se poursuit jusqu'à la section de balises. La section de balises commence par la première balise de bloc, qui est définie par le premier caractère @ qui commence une ligne (en ignorant les astérisques de début, les espaces blancs et le séparateur de début /**). Il est possible d'avoir un commentaire avec seulement une section de balises et pas de description principale. La description principale ne peut pas se poursuivre après le début de la section de balises. L'argument d'une balise peut s'étendre sur plusieurs lignes. Il peut y avoir n'importe quel nombre de balises, et certains types de balises peuvent être répétés tandis que d'autres ne peuvent pas. Par exemple, cette balise @see commence la section de balises

: 
/*
* 
 * Cette phrase contient la description principale pour ce commentaire de
documentation. 
 * @see java.lang.
Object 
 *
/

Balises de bloc et balises en

ligne

Une balise est un mot-clé spécial dans un commentaire de documentation que la commande javadoc traite. Il y a deux types de balises : les balises de bloc, qui apparaissent comme une balise @tag (également connues sous le nom de balises autonomes), et les balises en ligne, qui apparaissent entre accolades, comme une balise {@tag}. Pour être interprétée, une balise de bloc doit apparaître au début d'une ligne, en ignorant les astérisques de début, les espaces blancs et le séparateur (/**). Cela signifie que vous pouvez utiliser le caractère @ ailleurs dans le texte et il ne sera pas interprété comme le début d'une balise. Si vous voulez commencer une ligne par le caractère @ sans qu'il soit interprété, utilisez l'entité HTML &. Chaque balise de bloc a un texte associé, qui inclut tout texte suivant la balise jusqu'à, mais sans inclure, soit la balise suivante, soit la fin du commentaire de documentation. Ce texte associé peut s'étendre sur plusieurs lignes. Une balise en ligne est autorisée et interprétée partout où le texte est autorisé. L'exemple suivant contient la balise de bloc @deprecated et la balise en ligne {@link}. Voir Balises

Javadoc. 
/*
* 
 * @deprecated  Depuis JDK 1.1, remplacée par {@link #setBounds(int,int,int,int)
} 
 *
/

Écrire les commentaires en

HTML

Le texte doit être écrit en HTML avec des entités HTML et des balises HTML. Vous pouvez utiliser n'importe quelle version de HTML prise en charge par votre navigateur. Le doclet standard génère du code conforme à HTML 3.2 ailleurs (en dehors des commentaires de documentation) avec l'inclusion de feuilles de style en cascade et de cadres. HTML 4.0 est préféré pour les fichiers générés en raison des ensembles de

cadres.

Par exemple, les entités pour le symbole inférieur à (<) et le symbole supérieur à (>) devraient être écrites comme & et &. De même, l'esperluette (&) devrait être écrite comme &. La balise HTML de gras <b> est montrée dans l'exemple

suivant.

* 
 * Ceci est un commentaire <b>doc</b>

Object

Astérisques de

début

Lorsque la commande javadoc analyse un commentaire de documentation, les astérisques de début (*) de chaque ligne sont supprimés, et les espaces et tabulations précédant les astérisques initiaux (*) sont également supprimés. Si vous omettez l'astérisque de début sur une ligne, l'espace blanc de début n'est alors plus supprimé afin que vous puissiez coller des exemples de code directement dans un commentaire de documentation à l'intérieur d'une balise <PRE> avec son indentation préservée. Les espaces sont interprétés par les navigateurs de manière plus uniforme que les tabulations. L'indentation est relative à la marge de gauche (plutôt qu'au séparateur /** ou à la balise <PRE>)

.

Première

phrase

La première phrase de chaque commentaire de documentation devrait être une phrase résumé qui contient une description concise mais complète de l'entité déclarée. Cette phrase se termine au premier point suivi d'un espace, d'une tabulation ou d'un terminateur de ligne, ou à la première balise de bloc. La commande javadoc copie cette première phrase dans le résumé du membre en haut de la page

HTML.

Déclarations de champs

multiples

La plateforme Java vous permet de déclarer plusieurs champs dans une seule instruction, mais cette instruction ne peut avoir qu'un seul commentaire de documentation qui est copié pour tous les champs. Si vous voulez des commentaires de documentation individuels pour chaque champ, déclarez chaque champ dans une instruction séparée. Par exemple, le commentaire de documentation suivant n'a pas de sens écrit comme une seule déclaration et serait mieux géré comme deux déclarations

d'en-tête

HÉRITAGE DES COMMENTAIRES DE

MÉTHODES

La commande javadoc permet l'héritage des commentaires de méthodes dans les classes et les interfaces pour compléter le texte manquant ou pour hériter explicitement des commentaires de méthodes. Les constructeurs, les champs et les classes imbriquées n'héritent pas des commentaires de

documentation.

Remarque : Le fichier source d'une méthode héritée doit se trouver sur le chemin spécifié par l'option -sourcepath pour que le commentaire de documentation soit disponible pour être copié. Ni la classe ni son package n'ont besoin d'être passés en ligne de commande. Cela contraste avec la version 1.3.n et les versions antérieures, où la classe devait être une classe

documentée.

Compléter le texte

manquant

Lorsqu'une description principale, ou une balise @return, @param ou @throws est manquante dans un commentaire de méthode, la commande javadoc copie la description principale ou le commentaire de balise correspondant de la méthode qu'elle surcharge ou implémente (le cas échéant). Voir Héritage des commentaires de

méthodes.

Lorsqu'une balise @param pour un paramètre particulier est manquante, le commentaire pour ce paramètre est copié de la méthode plus haut dans la hiérarchie d'héritage. Lorsqu'une balise @throws pour une exception particulière est manquante, la balise @throws n'est copiée que lorsque cette exception est

déclarée.

Ce comportement contraste avec la version 1.3 et les versions antérieures, où la présence de n'importe quelle description principale ou balise empêchait l'héritage de tous les

commentaires.

Voir Balises et options

Javadoc.

explicite

Insérez la balise en ligne {@inheritDoc} dans une description principale de méthode ou dans un commentaire de balise @return, @param ou @throws. La description principale ou le commentaire de

balise hérité correspond

HÉRITAGE DE CLASSES ET D'INTERFACES

CLASSE ET INTERFACE D'HÉRITAGE

L'héritage des commentaires se produit dans tous les cas possibles d'héritage de classes et d'interfaces :

•
Lorsqu'une méthode dans une classe remplace une méthode dans une superclasse.
•
Lorsqu'une méthode dans une interface remplace une méthode dans une superinterface.
•
Lorsqu'une méthode dans une classe implémente une méthode dans une interface.

Dans les deux premiers cas, la commande javadoc génère le sous-titre Remplace dans la documentation de la méthode qui remplace. Un lien vers la méthode remplacée est inclus, que le commentaire soit hérité ou non.

Dans le troisième cas, lorsqu'une méthode dans une classe spécifiée implémente une méthode dans une interface, la commande javadoc génère le sous-titre Spécifié par dans la documentation de la méthode qui remplace. Un lien vers la méthode implémentée est inclus, que le commentaire soit hérité ou non.

ALGORITHME DE COMMENTAIRES DE MÉTHODES

Si une méthode n'a pas de commentaire de documentation, ou a une balise {@inheritDoc}, alors la commande javadoc utilise l'algorithme suivant pour rechercher un commentaire applicable. L'algorithme est conçu pour trouver le commentaire de documentation applicable le plus spécifique et pour donner la préférence aux interfaces sur les superclasses :

1.
Rechercher dans chaque interface directement implémentée (ou étendue) dans l'ordre où elles apparaissent après le mot implements (ou extends) dans la déclaration de la méthode. Utiliser le premier commentaire de documentation trouvé pour cette méthode.
2.
Si l'étape 1 n'a pas permis de trouver de commentaire de documentation, alors appliquer récursivement tout cet algorithme à chaque interface directement implémentée (ou étendue) dans le même ordre où elles ont été examinées à l'étape 1.
3.
Lorsque l'étape 2 n'a pas permis de trouver de commentaire de documentation et qu'il s'agit d'une classe autre que la classe Object, mais pas une interface :
1.
Si la superclasse a un commentaire de documentation pour cette méthode, alors l'utiliser.
2.
Si l'étape 3a n'a pas permis de trouver de commentaire de documentation, alors appliquer récursivement tout cet algorithme à la superclasse.

BALISES JAVADOC

La commande javadoc analyse les balises spéciales lorsqu'elles sont intégrées dans un commentaire de documentation Java. Les balises javadoc vous permettent de générer automatiquement une API complète et bien formatée à partir de votre code source. Les balises commencent par une arobase (@) et ne sont pas sensibles à la casse. Elles doivent être tapées avec les lettres majuscules et minuscules telles qu'elles sont indiquées. Une balise doit commencer au début d'une ligne (après les espaces en retrait et un astérisque facultatif), sinon elle est traitée comme du texte. Par convention, les balises ayant le même nom sont regroupées. Par exemple, regroupez toutes les balises @see ensemble. Pour plus d'informations, voir Où les balises peuvent être utilisées.

Les balises sont des types suivants :

•
Balises de bloc : Placez les balises de bloc uniquement dans la section de balises qui suit la description. Les balises de bloc ont la forme : @balise.
•
Balises en ligne : Placez les balises en ligne n'importe où dans la description principale ou dans les commentaires des balises de bloc. Les balises en ligne sont entourées d'accolades : {@balise}.

Pour les balises personnalisées, voir -tag tagname:Xaoptcmf:"taghead". Voir également Où les balises peuvent être utilisées.

DESCRIPTIONS DE BALISES

@author texte-nom
Introduit dans JDK 1.0

Ajoute une entrée Auteur avec le texte du nom spécifié aux documents générés lorsque l'option -author est utilisée. Un commentaire de documentation peut contenir plusieurs balises @author. Vous pouvez spécifier un nom par balise @author ou plusieurs noms par balise. Dans le premier cas, la commande javadoc insère une virgule (,) et un espace entre les noms. Dans le second cas, l'intégralité du texte est copiée dans le document généré sans être analysée. Par conséquent, vous pouvez utiliser plusieurs noms par ligne si vous souhaitez un séparateur de nom localisé autre qu'une virgule. Voir @author dans Comment écrire des commentaires de documentation pour l'outil Javadoc à http://www.oracle.com/technetwork/java/javase/documentation/index-137868.html#@author

{@code texte}
Introduit dans JDK 1.5

Équivalent à <code>{@literal}</code>.

Affiche le texte en police de code sans interpréter le texte comme du balisage HTML ou des balises Javadoc imbriquées. Cela vous permet d'utiliser des crochets normaux (< et >) au lieu des entités HTML (&lt; et &gt;) dans les commentaires de documentation, comme dans les types de paramètres (<Object>), les inégalités (3 < 4), ou les flèches (<-). Par exemple, le texte du commentaire de documentation {@code A<B>C} affiché sur la page HTML générée inchangé est A<B>C. Cela signifie que <B> n'est pas interprété comme gras et est en police de code. Si vous souhaitez la même fonctionnalité sans la police de code, utilisez la balise {@literal}.

@deprecated texte-obsolète
Introduit dans JDK 1.0

Ajoute un commentaire indiquant que cette API ne doit plus être utilisée (même si elle peut continuer à fonctionner). La commande javadoc place texte-obsolète avant la description principale, en le mettant en italique et en le faisant précéder d'un avertissement en gras : Obsolète. Cette balise est valide dans tous les commentaires de documentation : aperçu, package, classe, interface, constructeur, méthode et champ.

La première phrase du texte obsolète doit indiquer à l'utilisateur quand l'API a été rendue obsolète et quoi utiliser en remplacement. La commande javadoc copie la première phrase dans la section de résumé et l'index. Les phrases suivantes peuvent également expliquer pourquoi elle a été rendue obsolète. Vous devez inclure une balise {@link} (pour Javadoc 1.2 ou ultérieur) qui pointe vers l'API de remplacement.

Utilisez la balise d'annotation @deprecated pour rendre un élément de programme obsolète. Voir Comment et quand rendre les API obsolètes à http://docs.oracle.com/javase/8/docs/technotes/guides/javadoc/deprecation/deprecation.html

Voir également @deprecated dans Comment écrire des commentaires de documentation pour l'outil Javadoc à http://www.oracle.com/technetwork/java/javase/documentation/index-137868.html#@deprecated

{@docRoot}
Introduit dans JDK 1.3

Représente le chemin relatif vers le répertoire racine du document généré (de destination) à partir de n'importe quelle page générée. Cette balise est utile lorsque vous souhaitez inclure un fichier, tel qu'une page de copyright ou le logo de l'entreprise, auquel vous souhaitez faire référence à partir de toutes les pages générées. Lier la page de copyright en bas de chaque page est courant.

Cette balise {@docRoot} peut être utilisée à la fois sur la ligne de commande et dans un commentaire de documentation. Cette balise est valide dans tous les commentaires de documentation : aperçu, package, classe, interface, constructeur, méthode et champ, et inclut la partie texte de toute balise (telle que les balises @return, @param et @deprecated).

•
Sur la ligne de commande, où l'en-tête, le pied de page ou le bas sont définis : javadoc -bottom '<a href="{@docRoot}/copyright.html">Copyright</a>'.

Lorsque vous utilisez la balise {@docRoot} de cette manière dans un fichier make, certains programmes makefile nécessitent une manière spéciale d'échapper les caractères d'accolade {}. Par exemple, la version 5.2 de Inprise MAKE s'exécutant sur Windows nécessite des doubles accolades : {{@docRoot}}. Elle nécessite également des guillemets doubles (plutôt que simples) pour entourer les arguments des options telles que l'option -bottom (les guillemets autour de l'argument href étant omis).

•
Dans un commentaire de documentation : 
/**
 * Voir le <a href="{@docRoot}/copyright.html">Copyright</a>.
 */

Cette balise est nécessaire car les documents générés sont dans des répertoires hiérarchiques, aussi profonds que le nombre de sous-packages. L'expression : <a href="{@docRoot}/copyright.html"> se résout en <a href="../../copyright.html"> pour java/lang/Object.java et en <a href="../../../copyright.html"> pour java/lang/ref/Reference.java.

@exception nom-classe description
Introduit dans JDK 1.0

Identique à la balise @throws. Voir @throws nom-classe description.

{@inheritDoc}
Introduit dans JDK 1.4

Hérite (copie) la documentation de la classe héritable ou de l'interface implémentable la plus proche dans le commentaire de documentation actuel à l'emplacement de cette balise. Cela vous permet d'écrire des commentaires plus généraux plus haut dans l'arbre d'héritage et d'écrire autour du texte copié.

Cette balise est valide uniquement dans les endroits suivants d'un commentaire de documentation :

•
Dans le bloc de description principale d'une méthode. Dans ce cas, la description principale est copiée d'une classe ou d'une interface en remontant la hiérarchie.
•
Dans les arguments texte des balises @return, @param et @throws d'une méthode. Dans ce cas, le texte de la balise est copié de la balise correspondante en remontant la hiérarchie.

Voir Héritage des commentaires de méthodes pour une description de la manière dont les commentaires sont trouvés dans la hiérarchie d'héritage. Notez que si cette balise est manquante, alors le commentaire est ou n'est pas automatiquement hérité selon les règles décrites dans cette section.

{@link package.classe#membre libellé}
Introduit dans JDK 1.2

Insère un lien en ligne avec un libellé de texte visible qui pointe vers la documentation du package, de la classe ou du nom de membre spécifié d'une classe référencée. Cette balise est valide dans tous les commentaires de documentation : aperçu, package, classe, interface, constructeur, méthode et champ, y compris la partie texte de toute balise, telle que les balises @return, @param et @deprecated. Voir @link dans Comment écrire des commentaires de documentation pour l'outil Javadoc à http://www.oracle.com/tech

{@link package.class#member label}
Ce tag est similaire au tag @see. Les deux tags nécessitent les mêmes références et acceptent la même syntaxe pour package.class#member et label. La principale différence est que le tag {@link} génère un lien inline plutôt que de placer le lien dans la section "See Also". Le tag {@link} commence et se termine par des accolades pour le séparer du reste du texte inline. Si vous avez besoin d'utiliser l'accolade droite (}) à l'intérieur du label, utilisez la notation d'entité HTML &#125;.

Il n'y a aucune limite au nombre de tags {@link} autorisés dans une phrase. Vous pouvez utiliser ce tag dans la partie description principale de tout commentaire de documentation ou dans la partie texte de tout tag, tel que les tags @deprecated, @return ou @param.

Par exemple, voici un commentaire qui fait référence à la méthode getComponentAt(int, int):

Utilisez la méthode {@link #getComponentAt(int, int) getComponentAt}.

À partir de ce code, le doclet standard génère le HTML suivant (en supposant qu'il fait référence à une autre classe du même package):

La ligne précédente apparaît sur la page Web comme suit:

Utilisez la méthode getComponentAt.

Introduit dans JDK 1.4

Se comporte de la même manière que le tag {@link}, sauf que le label du lien est affiché en texte brut plutôt qu'en police de code. Utile lorsque le label est du texte brut. Par exemple, Référez-vous à {@linkplain add() la méthode surchargée}. s'affiche comme suit : Référez-vous à la méthode surchargée.

{@literal text}
Introduit dans JDK 1.5

Affiche du texte sans interpréter ce texte comme du balisage HTML ou des tags Javadoc imbriqués. Cela vous permet d'utiliser des crochets (< et >) au lieu des entités HTML (&lt; et &gt;) dans les commentaires de documentation, comme dans les types de paramètres (<Object>), les inégalités (3 < 4) ou les flèches (<-). Par exemple, le texte du commentaire de documentation {@literal A<B>C} s'affiche inchangé dans la page HTML générée dans votre navigateur, comme A<B>C. Le <B> n'est pas interprété comme du gras (et n'est pas en police de code). Si vous souhaitez la même fonctionnalité avec du texte en police de code, utilisez le tag {@code}.

@see référence
Introduit dans JDK 1.0

Ajoute un en-tête Voir également avec un lien ou une entrée texte qui pointe vers une référence. Un commentaire de documentation peut contenir un nombre quelconque de tags @see, qui sont tous regroupés sous le même en-tête. Le tag @see a trois variations. La forme est la plus courante. Ce tag est valide dans n'importe quel commentaire de documentation: aperçu, package, classe, interface, constructeur, méthode ou champ. Pour insérer un lien inline dans une phrase vers un package, une classe ou un membre, voir {@link}.

Forme 1. La forme du tag @see string ajoute une entrée texte pour string. Aucun lien n'est généré. La chaîne est un livre ou une autre référence à des informations non disponibles par URL. La commande javadoc distingue cela des cas précédents en recherchant un guillemet double (") comme premier caractère. Par exemple, @see "The Java Programming Language" qui génère le texte suivant:

Voir également:

"The Java Programming Language"

Forme 2. La forme @see <a href="URL#value">label</a> ajoute un lien tel que défini par URL#value. Le paramètre URL#value est une URL relative ou absolue. La commande javadoc distingue cela des autres cas en recherchant un signe inférieur à (<) comme premier caractère. Par exemple, @see <a href="spec.html#section">Java Spec</a> génère le lien suivant:

Voir également:

Java Spec

Forme 3. La forme @see package.class#member label ajoute un lien avec un label texte visible qui pointe vers la documentation de l'élément nommé spécifié dans le langage Java référencé. Le label est facultatif. Si le label est omis, alors le nom apparaît à la place comme texte visible, correctement raccourci. Utilisez l'option -noqualifier pour supprimer globalement le nom du package de ce texte visible. Utilisez le label lorsque vous souhaitez que le texte visible soit différent du texte visible autogénéré. Voir Comment un nom apparaît.

En Java SE 1.2 seulement, le nom mais pas le label apparaît automatiquement dans les tags HTML <code>. À partir de Java SE 1.2.2, le tag <code> est toujours inclus autour du texte visible, que le label soit utilisé ou non.

•
package.class#member est tout nom d'élément de programme valide qui est référencé, tel qu'un nom de package, de classe, d'interface, de constructeur, de méthode ou de champ, à la différence que le caractère précédant le nom du membre doit être un signe numérique (#). La classe représente toute classe ou interface de premier niveau ou imbriquée. Le membre représente tout constructeur, méthode ou champ (pas une classe ou interface imbriquée). Si ce nom se trouve dans les classes documentées, alors la commande javadoc crée un lien vers celui-ci. Pour créer des liens vers des classes référencées externes, utilisez l'option -link. Utilisez l'une des deux autres formes de tag @see pour faire référence à la documentation d'un nom qui n'appartient pas à une classe référencée. Voir Spécifier un nom.

Remarque: Les classes référencées externes sont des classes qui ne sont pas passées à la commande javadoc en ligne de commande. Les liens dans la documentation générée vers les classes référencées externes sont appelés références externes ou liens externes. Par exemple, si vous exécutez la commande javadoc uniquement sur le package java.awt, alors toute classe dans java.lang, telle que Object, est une classe référencée externe. Utilisez les options -link et -linkoffline pour créer des liens vers des classes référencées externes. Les commentaires sources des classes référencées externes ne sont pas disponibles pour l'exécution de la commande javadoc.

•
label est un texte facultatif qui est visible en tant que label du lien. Le label peut contenir des espaces. Si label est omis, alors package.class.member apparaît, correctement raccourci par rapport à la classe et au package actuels. Voir Comment un nom apparaît.
•
Un espace est le délimiteur entre package.class#member et label. Un espace à l'intérieur des parenthèses n'indique pas le début d'un label, donc des espaces peuvent être utilisés entre les paramètres d'une méthode.

Dans l'exemple suivant, un tag @see (dans la classe Character) fait référence à la méthode equals dans la classe String. Le tag inclut les deux arguments: le nom String#equals(Object) et le label equals.

/**
 * @see String#equals(Object) equals
 */

Le doclet standard produit un HTML similaire à:

<dl>
<dt><b>Voir également:</b></dt>
<dd><a href="../../java/lang/String#equals(java.lang.Object)"><code>equals</code></a>
</dl>

Le code précédent ressemble à ce qui suit dans un navigateur, où le label est le texte du lien visible:

Voir également:

equals

Spécifier un nom

L'avantage de fournir des noms plus courts et partiellement qualifiés est qu'ils sont plus courts à taper et qu'il y a moins d'encombrement dans le code source. Notes sur la liste précédente :

•
Le premier ensemble de formes sans classe ni package amène la commande javadoc à rechercher uniquement dans la hiérarchie de la classe actuelle. Elle trouve un membre de la classe ou de l'interface actuelle, une de ses superclasses ou interfaces, ou une de ses classes ou interfaces encapsulantes (éléments de recherche 1 à 3). Elle ne recherche pas dans le reste du package actuel ni dans d'autres packages (éléments de recherche 4 à 5). Voir Ordre de recherche pour la balise @see.
•
Si une méthode ou un constructeur est entré sous forme de nom sans parenthèses, tel que getValue, et s'il n'y a pas de champ du même nom, alors la commande javadoc crée quand même un lien vers la méthode. Si cette méthode est surchargée, alors la commande javadoc lie vers la première méthode que sa recherche rencontre, ce qui n'est pas spécifié.
•
Les classes internes doivent être spécifiées comme externe.interne, et non simplement interne, pour toutes les formes.
•
Comme indiqué, le signe dièse (#), plutôt qu'un point (.), sépare un membre de sa classe. Cela permet à la commande javadoc de résoudre les ambiguïtés, car le point sépare également les classes, les classes internes, les packages et les sous-packages. Cependant, la commande javadoc analyse correctement un point lorsqu'il n'y a pas d'ambiguïté, mais affiche un avertissement pour vous alerter.

Ordre de recherche pour la balise @see

La commande javadoc traite une balise @see qui apparaît dans un fichier source, un fichier de package ou un fichier d'aperçu. Dans les deux derniers fichiers, vous devez qualifier complètement le nom que vous fournissez avec la balise @see. Dans un fichier source, vous pouvez spécifier un nom qualifié complètement ou partiellement. qualifié.

Voici l'ordre de recherche pour la balise @see.

1.
La classe ou l'interface actuelle.
2.
Toutes les classes et interfaces encapsulantes, en recherchant d'abord la plus proche.
3.
Toutes les superclasses et interfaces, en recherchant d'abord la plus proche.
4.
Le package actuel.
5.
Tous les packages, classes et interfaces importés, en recherchant dans l'ordre de l'instruction import.

La commande javadoc continue de rechercher récursivement dans les éléments 1 à 3 pour chaque classe qu'elle rencontre jusqu'à ce qu'elle trouve une correspondance. C'est-à-dire qu'après avoir recherché dans la classe actuelle et sa classe encapsulante E, elle recherche dans les superclasses de E avant les classes encapsulantes de E. Dans les éléments 4 et 5, la commande javadoc ne recherche pas les classes ou interfaces au sein d'un package dans un ordre spécifié (cet ordre dépend du compilateur particulier). Dans l'élément 5, la commande javadoc recherche dans java.lang car celui-ci est importé par tous les programmes.

Lorsque la commande javadoc rencontre une balise @see dans un fichier source qui n'est pas complètement qualifié, elle recherche le nom spécifié dans le même ordre que le compilateur Java, sauf que la commande javadoc ne détecte pas certaines ambiguïtés d'espace de noms car elle suppose que le code source est exempt de ces erreurs. Cet ordre de recherche est formellement défini dans la spécification du langage Java. La commande javadoc recherche ce nom dans toutes les classes et tous les packages liés et importés. En particulier, elle recherche dans cet ordre :

1.
La classe ou l'interface actuelle.
2.
Toutes les classes et interfaces encapsulantes, en recherchant d'abord la plus proche.
3.
Toutes les superclasses et interfaces, en recherchant d'abord la plus proche.
4.
Le package actuel.
5.
Tous les packages, classes et interfaces importés, en recherchant dans l'ordre des instructions import.

La commande javadoc ne recherche pas nécessairement dans les sous-classes, ni dans d'autres packages même lorsque leur documentation est générée lors de la même exécution. Par exemple, si la balise @see se trouve dans la classe java.awt.event.KeyEvent et fait référence à un nom dans le package java.awt, alors la commande javadoc ne recherche pas dans ce package à moins que cette classe ne l'importe.

Comment un nom apparaît

Si label est omis, alors package.classe.membre apparaît. En général, il est correctement raccourci par rapport à la classe et au package actuels. Raccourci signifie que la commande javadoc affiche uniquement le nom minimum nécessaire. Par exemple, si la méthode String.toUpperCase() contient des références à un membre de la même classe et à un membre d'une classe différente, alors le nom de la classe n'est affiché que dans ce dernier cas, comme le montre la liste suivante. Utilisez l'option -noqualifier pour supprimer globalement les noms de package.

Type de référence : la balise @see fait référence à un membre de la même classe, même package
Exemple dans : @see String#toLowerCase()
Apparaît comme : toLowerCase() - omet les noms de package et de classe

Type de référence : la balise @see fait référence à un membre d'une classe différente, même package
Exemple dans : @see Character#toLowerCase(char)
Apparaît comme : Character.toLowerCase(char) - omet le nom de package, inclut le nom de classe

Type de référence : la balise @see fait référence à un membre d'une classe différente, package différent
Exemple dans : @see java.io.File#exists()
Apparaît comme : java.io.File.exists() - inclut les noms de package et de classe

@serial description-du-champ | include | exclude
Introduit dans JDK 1.2

Utilisé dans le commentaire de documentation pour un champ sérialisable par défaut. Voir Documenting Serializable Fields and Data for a Class à http://docs.oracle.com/javase/8/docs/platform/serialization/spec/serial-arch.html#5251

Voir également les critères d'Oracle pour inclure les classes dans la spécification de la forme sérialisée à http://www.oracle.com/technetwork/java/javase/documentation/serialized-criteria-137781.html

Une description-du-champ facultative doit expliquer la signification du champ et énumérer les valeurs acceptables. Le cas échéant, la description peut s'étendre sur plusieurs lignes. Le doclet standard ajoute ces informations à la page de forme sérialisée. Voir Pages de référence croisée.

Si un champ sérialisable a été ajouté à une classe après que celle-ci est devenue sérialisable, alors une déclaration doit être ajoutée à sa description principale pour identifier la version à laquelle il a été ajouté.

Les arguments include et exclude identifient si une classe ou un package doit être inclus ou exclu de la page de forme sérialisée. Ils fonctionnent comme suit :

•
Une classe publique ou protégée qui implémente Serializable est incluse sauf si cette classe (ou son package) est marquée avec la balise @serial exclude.
•
Une classe privée ou de portée de package qui implémente Serializable est exclue sauf si cette classe (ou son package) est marquée avec la balise @serial include.

Par exemple, le package javax.swing est marqué avec la balise @serialexclude dans package.html ou package-info.java. La classe publique java.security.BasicPermission est marquée avec la balise @serial exclude. La classe de portée de package java.util.PropertyPermissionCollection est marquée avec la balise @serial include.

La balise @serial au niveau de la classe remplace la balise @serial au niveau du package.

Introduit dans JDK 1.2

Utilise la valeur description-des-données pour documenter les types et l'ordre des données dans la forme sérialisée. Ces données comprennent les données facultatives écrites par la méthode writeObject et toutes les données (y compris les classes de base) écrites par la méthode Externalizable.writeExternal.

La balise @serialData peut être utilisée dans la documentation

sur commentaire pour les méthodes writeObject, readObject, writeExternal, readExternal, writeReplace et readResolve.

@since texte-depuis
Introduit dans le JDK 1.1

Ajoute un en-tête Depuis avec la valeur spécifiée texte-depuis à la documentation générée. Le texte n'a pas de structure interne spéciale. Cette balise est valide dans tout commentaire de documentation : aperçu, package, classe, interface, constructeur, méthode ou champ. Cette balise signifie que ce changement ou cette fonctionnalité existe depuis la version du logiciel spécifiée par la valeur texte-depuis, par exemple : @since 1.5.

Pour le code source de la plateforme Java, la balise @since indique la version de la spécification de l'API de la plateforme Java, ce qui n'est pas nécessairement le moment où le code source a été ajouté à l'implémentation de référence. Plusieurs balises @since sont autorisées et sont traitées comme plusieurs balises @author. Vous pouvez utiliser plusieurs balises lorsque l'élément de programme est utilisé par plus d'une API.

@throws nom-classedescription
Introduit dans le JDK 1.2

Se comporte de la même manière que la balise @exception. Voir @throws dans Comment écrire des commentaires Javadoc pour l'outil Javadoc à l'adresse http://www.oracle.com/technetwork/java/javase/documentation/index-137868.html#@exception

La balise @throws ajoute une sous-section Lève à la documentation générée, avec le nom-classe et la description. Le nom-classe est le nom de l'exception qui peut être levée par la méthode. Cette balise est valide uniquement dans le commentaire de documentation d'une méthode ou d'un constructeur. Si cette classe n'est pas entièrement spécifiée, la commande javadoc utilise l'ordre de recherche pour trouver cette classe. Plusieurs balises @throws peuvent être utilisées dans un commentaire de documentation spécifié pour des exceptions identiques ou différentes. Voir Ordre de recherche pour la balise @see.

Pour s'assurer que toutes les exceptions vérifiées sont documentées, lorsqu'une balise @throws est absente pour une exception dans la clause throws, la commande javadoc ajoute cette exception à la sortie HTML (sans description) comme si elle était documentée avec la balise @throws.

La documentation @throws est copiée d'une méthode surchargée à une sous-classe uniquement lorsque l'exception est explicitement déclarée dans la méthode surchargée. Il en va de même pour la copie d'une méthode d'interface à une méthode d'implémentation. Vous pouvez utiliser la balise {@inheritDoc} pour forcer la balise @throws à hériter de la documentation.

{@value package.classe#champ}
Introduit dans le JDK 1.4

Affiche les valeurs constantes. Lorsque la balise {@value} est utilisée sans argument dans le commentaire de documentation d'un champ statique, elle affiche la valeur de cette constante :

/**
 * La valeur de cette constante est {@value}.
 */
public static final String SCRIPT_START = "<script>"

Lorsqu'elle est utilisée avec l'argument package.classe#champ dans tout commentaire de documentation, la balise {@value} affiche la valeur de la constante spécifiée :

/**
 * Évalue le script commençant par {@value #SCRIPT_START}.
 */
public String evalScript(String script) {}

L'argument package.classe#champ prend une forme similaire à celle de l'argument de la balise @see, à l'exception que le membre doit être un champ statique.

Les valeurs de ces constantes sont également affichées dans les valeurs de champs constants à l'adresse http://docs.oracle.com/javase/8/docs/api/constant-values.html

@version texte-version
Introduit dans le JDK 1.0

Ajoute une sous-section Version avec la valeur spécifiée texte-version aux documents générés lorsque l'option -version est utilisée. Cette balise est destinée à contenir le numéro de version actuel du logiciel dont ce code fait partie, par opposition à la balise @since, qui contient le numéro de version où ce code a été introduit. La valeur texte-version n'a pas de structure interne spéciale. Voir @version dans Comment écrire des commentaires Javadoc pour l'outil Javadoc à http://www.oracle.com/technetwork/java/javase/documentation/index-137868.html#@version

Un commentaire de documentation peut contenir plusieurs balises @version. Lorsque cela est pertinent, vous pouvez spécifier un numéro de version par balise @version ou plusieurs numéros de version par balise. Dans le premier cas, la commande javadoc insère une virgule (,) et un espace entre les noms. Dans le second cas, le texte entier est copié dans le document généré sans être analysé. Par conséquent, vous pouvez utiliser plusieurs noms par ligne lorsque vous souhaitez un séparateur de nom localisé autre qu'une virgule.

OÙ LES BALISES PEUVENT ÊTRE UTILISÉES

Les sections suivantes décrivent où les balises peuvent être utilisées. Notez que les balises suivantes peuvent être utilisées dans tous les commentaires de documentation : @see, @since, @deprecated, {@link}, {@linkplain} et {@docroot}.

BALISES&#x00A0;D'APERÇU

Les balises d'aperçu sont des balises qui peuvent apparaître dans le commentaire de documentation de la page d'aperçu (qui réside dans le fichier source généralement nommé overview.html). Semblables à tout autre commentaire de documentation, ces balises doivent apparaître après la description principale.

Remarque : La balise {@link} présente un bug dans les documents d'aperçu de Java SE 1.2. Le texte apparaît correctement mais sans lien. La balise {@docRoot} ne fonctionne actuellement pas dans les documents d'aperçu.

Les balises d'aperçu sont les suivantes :

@see référence || @since texte-depuis || @serialField nom-champ type-champ description-champ || @author texte-nom || @version texte-version || {@link package.classe#membre étiquette} || {@linkplain package.classe#membre étiquette} || {@docRoot} ||

BALISES&#x00A0;DE&#x00A0;PACKAGE

Les balises de package sont des balises qui peuvent apparaître dans le commentaire de documentation d'un package, qui réside dans le fichier source nommé package.html ou package-info.java. La balise @serial ne peut y être utilisée qu'avec l'argument include ou exclude.

Les balises de package sont les suivantes :

@see référence || @since texte-depuis || @serial description-champ | include | exclude || @author texte-nom || @version texte-version || {@linkplain package.classe#membre étiquette} || {@linkplain package.classe#membre étiquette} || {@docRoot} ||

BALISES&#x00A0;DE&#x00A0;CLASSE&#x00A0;ET&#x00A0;D'INTERFACE

Voici les balises qui peuvent apparaître dans le commentaire de documentation d'une classe ou d'une interface. La balise @serial ne peut être utilisée qu'au sein de la documentation d'une classe ou d'une interface avec un argument include ou exclude.

@see référence || @since texte-depuis || @deprecated texte-déprécié || @serial description-champ | include | exclude || @author texte-nom || @version texte-version || {@link package.classe#membre étiquette} || {@linkplain package.classe#membre étiquette} || {@docRoot} ||

/**
 * Une classe représentant une fenêtre à l'écran.
 * Par exemple :
 * <pre>
 *    Window win = new Window(parent);
 *    win.show();
 * </pre>
 *
 * @author  Sami Shaio
 * @version 1.13, 06/08/06
 * @see     java.awt.BaseWindow
 * @see     java.awt.Button
 */
class Window extends BaseWindow {
   ...
}

DESCRIPTION

The javadoc tool analyzes the documentation comments in a set of specified source files and generates the HTML documentation pages for them. Documentation comments are comments that begin with the following sequence of characters:

•  /\**

where the first character after the exclamation point is a asterisk. This comment is followed by the rest of the comment text. The javadoc tool reads the Java classes in the specified source files, and then generates HTML files that describe the classes, interfaces, fields, methods, and constructors.

The javadoc tool also generates documentation for any packages specified in the source files, and can create an overview page that summarizes all the packages. For example, if you run javadoc on the source code for the java.lang package, it generates HTML documentation for all the classes and interfaces in that package, such as String, Integer, and Runnable. It also generates an overview page (summary for the package).

The javadoc command parses the HTML tags within the documentation comments and generates tags for the documentation. For example, if the documentation comment contains the @see tag, then the javadoc tool generates a link to the class or method specified by the tag. The javadoc tool generates standard HTML files that can be viewed with a web browser.

The javadoc tool can also be extended by writing custom doclets. A doclet is a program that specifies the output format of the generated documentation. For example, you can write a doclet that generates documentation in XML format, or that generates documentation in a different language. See Doclet Overview at http://docs.oracle.com/javase/8/docs/technotes/guides/javadoc/doclet/overview.html

Reports warnings for bad references, lack of accessibility and missing Javadoc comments, and reports errors for invalid Javadoc syntax and missing HTML tags.

This option enables the javadoc command to check for all documentation comments included in the generated output. As always, you can select which items to include in the generated output with the standard options -public, -protected, -package and -private.

When the -Xdoclint is enabled, it reports issues with messages similar to the javac command. The javadoc command prints a message, a copy of the source line, and a caret pointing at the exact position where the error was detected. Messages may be either warnings or errors, depending on their severity and the likelihood to cause an error if the generated documentation were run through a validator. For example, bad references or missing Javadoc comments do not cause the javadoc command to generate invalid HTML, so these issues are reported as warnings. Syntax errors or missing HTML end tags cause the javadoc command to generate invalid output, so these issues are reported as errors.

By default, the -Xdoclint option is enabled. Disable it with the option -Xdoclint:none.

•

•

•

•

The variable group has one of the following values:

•
accessibility : Checks for the issues to be detected by an accessibility checker (for example, no caption or summary attributes specified in a <table> tag).
•

•

•

Pour raccourcir ou simplifier la commande javadoc, vous pouvez spécifier un ou plusieurs fichiers contenant des arguments pour la commande javadoc (sauf les options -J). Cela vous permet de créer des commandes javadoc de toute longueur sur n'importe quel système d'exploitation.

Un fichier d'arguments peut inclure des options javac et des noms de fichiers source dans n'importe quelle combinaison. Les arguments dans un fichier peuvent être séparés par des espaces ou des sauts de ligne. Si un nom de fichier contient des espaces, placez le nom de fichier complet entre guillemets doubles.

Les noms de fichiers dans un fichier d'arguments sont relatifs au répertoire courant, pas à l'emplacement du fichier d'arguments. Les caractères génériques (*) ne sont pas autorisés dans ces listes (par exemple, pour spécifier *.java). L'utilisation du signe arobase (@) pour interpréter récursivement les fichiers n'est pas prise en charge. Les options -J ne sont pas prises en charge car elles sont transmises au lanceur, qui ne prend pas en charge les fichiers d'arguments.

Lorsque vous exécutez la commande javadoc, transmettez le chemin et le nom de chaque fichier d'arguments avec le caractère @ en préfixe. Lorsque la commande javadoc rencontre un argument commençant par le signe arobase (@), elle développe le contenu de ce fichier dans la liste des arguments.

NAME


javadoc - generate HTML API documentation from doc comments in Java source files






SYNOPSIS


javadoc [options] [packagenames] [sourcefiles]






DESCRIPTION


The javadoc command parses the declarations and
    documentation comments in a set of Java™
    source files and produces a set of HTML pages that describe a projected API.


This is a configuration file that specifies options for the
    javadoc command.


The settings specified in this file are used when the javadoc
    command is invoked.




PACKAGES


        java.lang java.lang.reflect        /* Définit les packages à documenter */


        java.util java.io java.net         \


        java.applet






OPTIONS


WINDOWTITLE = 'Java™ SE 7 API Specification'


DOCTITLE = 'Java™ Platform Standard Edition 7 API Specification'


HEADER = '<b>Java™ SE 7</font>'


BOTTOM = '<font size="-1">


      <a href="http://bugreport.sun.com/bugreport/">Soumettre un bug ou une fonctionnalité</a><br/>


      Copyright &copy; 1993, 2011, Oracle et/ou ses affiliés. Tous droits réservés.<br/>


      Oracle est une marque déposée d'Oracle Corporation et/ou ses affiliés.


      Les autres noms peuvent être des marques de commerce de leurs propriétaires respectifs.</font>'


GROUPCORE = '"Packages de base" "java.*:com.sun.java.*:org.omg.*"'

NOTES



  
•

  
Si vous omettez l'option -windowtitle, la commande
      javadoc copie le titre du document dans le titre de la fenêtre. Le
      texte de l'option -windowtitle est similaire à celui de l'option
      -doctitle, mais sans les balises HTML pour empêcher que ces balises
      n'apparaissent sous forme de texte brut dans le titre de la fenêtre.

  
•

  
Si vous omettez l'option -footer, la commande
      javadoc copie le texte de l'en-tête dans le pied de page.

  
•

  
D'autres options importantes que vous pourriez vouloir utiliser, mais qui
      n'étaient pas nécessaires dans l'exemple précédent, sont les options
      -classpath et -link.










GENERAL TROUBLESHOOTING



  
•

  
La commande javadoc ne lit que les fichiers contenant des noms de
      classes valides. Si la commande javadoc ne lit pas correctement le
      contenu d'un fichier, vérifiez que les noms de classes sont valides. Voir
      Process Source Files.

  
•

  
Voir la FAQ Javadoc pour des informations sur les bugs courants et des
      conseils de dépannage à
      http://www.oracle.com/technetwork/java/javase/documentation/index-137483.html








ERRORS AND WARNINGS


Les messages d'erreur et d'avertissement contiennent le nom du fichier
    et le numéro de ligne de la ligne de déclaration plutôt que de la ligne
    particulière dans le commentaire de documentation.


Par exemple, ce message erreur : impossible de lire : Class1.java
    signifie que la commande javadoc essaie de charger
    Class1.java dans le répertoire courant. Le nom de la classe est
    affiché avec son chemin (absolu ou relatif).






ENVIRONMENT



  
CLASSPATH

  
CLASSPATH est la variable d'environnement qui fournit le chemin que
      la commande javadoc utilise pour trouver les fichiers de classe
      utilisateur. Cette variable d'environnement est remplacée par l'option
      -classpath. Séparez les répertoires par un point-virgule pour Windows
      ou par un deux-points pour Oracle Solaris.
    
Exemple Windows :
        .;C:\classes;C:\home\java\classes

    
Exemple Oracle Solaris :
        .:/home/classes:/usr/local/java/classes.
