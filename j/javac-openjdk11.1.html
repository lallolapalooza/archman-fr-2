NOM

javac - Lit les définitions de classes et d'interfaces Java et les compile en bytecode et en fichiers de classe.

SYNTAXE

javac [ options ] [ fichiers-source ] [ classes] [ @fichiers-arguments ]

Les arguments peuvent être dans n'importe quel ordre :

options
Options de ligne de commande. Voir Options.
fichiers-source
Un ou plusieurs fichiers source à compiler (comme MaClasse.java).
classes
Une ou plusieurs classes à traiter pour les annotations (comme MonPaquet.MaClasse).
@fichiers-arguments
Un ou plusieurs fichiers listant les options et les fichiers source. Les options -J ne sont pas autorisées dans ces fichiers. Voir Fichiers d'arguments de ligne de commande.

DESCRIPTION

La commande javac lit les définitions de classes et d'interfaces, écrites dans le langage de programmation Java, et les compile en fichiers de classe bytecode. La commande javac peut également traiter les annotations dans les fichiers source et les classes Java.

Il existe deux façons de passer les noms de fichiers de code source à javac.

•
Pour un petit nombre de fichiers source, listez les noms de fichiers sur la ligne de commande.
•
Pour un grand nombre de fichiers source, listez les noms de fichiers dans un fichier séparé par des espaces ou des sauts de ligne. Utilisez le nom du fichier de liste précédé d'un signe arobase (@) avec la commande javac.

Les noms de fichiers de code source doivent avoir les suffixes .java, les noms de fichiers de classe doivent avoir les suffixes .class, et les fichiers source et classe doivent avoir des noms racine qui identifient la classe. Par exemple, une classe appelée MaClasse serait écrite dans un fichier source appelé MaClasse.java et compilée en un fichier de classe bytecode appelé MaClasse.class.

Les définitions de classes internes produisent des fichiers de classe supplémentaires. Ces fichiers de classe ont des noms qui combinent les noms des classes internes et externes, comme MaClasse$MaClasseInterne.class.

Organisez les fichiers source dans une arborescence de répertoires qui reflète leur arborescence de paquets. Par exemple, si tous vos fichiers source se trouvent dans /workspace, placez le code source de com.mesoft.monpaquet.MaClasse dans /workspace/com/mesoft/monpaquet/MaClasse.java.

Par défaut, le compilateur place chaque fichier de classe dans le même répertoire que son fichier source. Vous pouvez spécifier un répertoire de destination séparé avec l'option -d.

OPTIONS

Le compilateur dispose d'un ensemble d'options standard prises en charge sur l'environnement de développement actuel. Un ensemble supplémentaire d'options non standard sont spécifiques aux implémentations de machine virtuelle et de compilateur actuelles et sont susceptibles d'être modifiées à l'avenir. Les options non standard commencent par l'option -X.

-Aclé[=valeur]

Spécifie les options à passer aux processeurs d'annotations. Ces options ne sont pas interprétées directement par javac, mais sont mises à la disposition des processeurs individuels. La valeur de clé doit être un ou plusieurs identifiants séparés par un point (.).
-cp chemin ou -classpath chemin

Spécifie où trouver les fichiers de classe utilisateur, et (facultativement) les processeurs d'annotations et les fichiers source. Ce chemin de classe remplace le chemin de classe utilisateur dans la variable d'environnement CLASSPATH. Si ni CLASSPATH, ni -cp ni -classpath ne sont spécifiés, alors le chemin de classe utilisateur est le répertoire courant. Voir Définition du chemin de classe.

Si l'option -sourcepath n'est pas spécifiée, alors le chemin de classe utilisateur est également recherché pour les fichiers source.

Si l'option -processorpath n'est pas spécifiée, alors le chemin de classe est également recherché pour les processeurs d'annotations.

-Djava.ext.dirs=répertoires

Remplace l'emplacement des extensions installées.
-Djava.endorsed.dirs=répertoires

Remplace l'emplacement du chemin des standards approuvés.
-d répertoire

Définit le répertoire de destination pour les fichiers de classe. Le répertoire doit déjà exister car javac ne le crée pas. Si une classe fait partie d'un paquet, alors javac place le fichier de classe dans un sous-répertoire qui reflète le nom du paquet et crée des répertoires si nécessaire.

Si vous spécifiez -d/home/mesclasses et que la classe s'appelle com.monpaquet.MaClasse, alors le fichier de classe est /home/mesclasses/com/monpaquet/MaClasse.class.

Si l'option -d n'est pas spécifiée, alors javac place chaque fichier de classe dans le même répertoire que le fichier source à partir duquel il a été généré.

Note : Le répertoire spécifié par l'option -d n'est pas automatiquement ajouté à votre chemin de classe utilisateur.

-deprecation

Affiche une description de chaque utilisation ou substitution d'un membre ou d'une classe obsolète. Sans l'option -deprecation, javac affiche un résumé des fichiers source qui utilisent ou remplacent des membres ou des classes obsolètes. OPTIONS

-Joption

Passes the specified option directly to the Java Virtual Machine (JVM) launcher, where option is one of the options described on the reference page for the Java launcher. For example, -J-Xms48m sets the startup memory to 48 MB. See java(1).

Note: The CLASSPATH, -classpath, -bootclasspath, and -extdirs options do not specify the classes used to run javac. Trying to customize the compiler implementation with these options and variables is risky and often does not accomplish what you want. If you must customize the complier implementation, then use the -J option to pass options through to the underlying Java launcher.

-nowarn

Disables warning messages. This option operates the same as the -Xlint:none option.
-parameters

Stores formal parameter names of constructors and methods in the generated class file so that the method java.lang.reflect.Executable.getParameters from the Reflection API can retrieve them.
-proc: [none, only]

Controls whether annotation processing and compilation are done. -proc:none means that compilation takes place without annotation processing. -proc:only means that only annotation processing is done, without any subsequent compilation.

Names of the annotation processors to run. This bypasses the default discovery process.

Specifies where to find annotation processors. If this option is not used, then the class path is searched for processors.
-s dir

Specifies the directory where to place the generated source files. The directory must already exist because javac does not create it. If a class is part of a package, then the compiler puts the source file in a subdirectory that reflects the package name and creates directories as needed.

CROSS-COMPILATION OPTIONS

By default, classes are compiled against the bootstrap and extension classes of the platform that javac shipped with. But javac also supports cross-compiling, where classes are compiled against a bootstrap and extension classes of a different Java platform implementation. It is important to use the -bootclasspath and -extdirs options when cross-compiling.

-target version

Generates class files that target a specified release of the virtual machine. Class files will run on the specified target and on later releases, but not on earlier releases of the JVM. Valid targets are 1.1, 1.2, 1.3, 1.4, 1.5 (also 5), 1.6 (also 6), 1.7 (also 7), and 1.8 (also 8).

The default for the -target option depends on the value of the -source option:

•
If the -source option is not specified, then the value of the -target option is 1.8
•
If the -source option is 1.2, then the value of the -target option is 1.4
•
If the -source option is 1.3, then the value of the -target option is 1.4
•
If the -source option is 1.5, then the value of the -target option is 1.8
•
If the -source option is 1.6, then the value of the -target is option 1.8
•
If the -source option is 1.7, then the value of the -target is option 1.8
•
For all other values of the -source option, the value of the -target option is the value of the -source option.
-bootclasspath bootclasspath

Cross-compiles against the specified set of boot classes. As with the user class path, boot class path entries are separated by colons (:) and can be directories, JAR archives, or ZIP archives.

COMPACT PROFILE OPTION

Beginning with JDK 8, the javac compiler supports compact profiles. With compact profiles, applications that do not require the entire Java platform can be deployed and run with a smaller footprint. The compact profiles feature could be used to shorten the download time for applications from app stores. This feature makes for more compact deployment of Java applications that bundle the JRE. This feature is also useful in small devices.

The supported profile values are compact1, compact2, and compact3. These are additive layers. Each higher-numbered compact profile contains all of the APIs in profiles with smaller number names.

-profile

When using compact profiles, this option specifies the profile name when compiling. For example: 
javac -profile compact1 Hello.java

javac does not compile source code that uses any Java SE APIs that is not in the specified profile. Here is an example of the error message that results from attempting to compile such source code:

cd jdk1.8.0/bin
./javac -profile compact1 Paint.java
Paint.java:5: error: Applet is not available in profile 'compact1'
import java.applet.Applet;

In this example, you can correct the error by modifying the source to not use the Applet class. You could also correct the error by compiling without the -profile option. Then the compilation would be run against the full set of Java SE APIs. (None of the compact profiles include the Applet class.)

An alternative way to compile with compact profiles is to use the -bootclasspath option to specify a path to an rt.jar file that specifies a profile's image. Using the -profile option instead does not require a profile image to be present on the system at compile time. This is useful when cross-compiling.

OPTIONS XLINT

path
Avertit des éléments de chemin invalides et des répertoires inexistants dans le chemin d'accès sur la ligne de commande (par rapport au classpath, au sourcepath et à d'autres chemins). Ces avertissements ne peuvent pas être supprimés avec l'annotation @SuppressWarnings, par exemple : 
javac -Xlint:path -classpath /nonexistentpath Example.java
processing
Avertit des problèmes liés au traitement des annotations. Le compilateur génère cet avertissement lorsque vous avez une classe qui possède une annotation et que vous utilisez un processeur d'annotations qui ne peut pas gérer ce type d'exception. Par exemple, le code suivant est un simple processeur d'annotations :

Fichier source AnnocProc.java :

import java.util.*;
import javax.annotation.processing.*;
import javax.lang.model.*;
import javax.lang.model.element.*;
@SupportedAnnotationTypes("NotAnno")
public class AnnoProc extends AbstractProcessor {
  public boolean process(Set elems, RoundEnvironment renv){
     return true;
  }
  public SourceVersion getSupportedSourceVersion() {
     return SourceVersion.latest();
   }
}

Fichier source AnnosWithoutProcessors.java :

@interface Anno { }
@Anno
class AnnosWithoutProcessors { }

Les commandes suivantes compilent le processeur d'annotations AnnoProc, puis exécutent ce processeur d'annotations sur le fichier source AnnosWithoutProcessors.java :

javac AnnoProc.java
javac -cp . -Xlint:processing -processor AnnoProc -proc:only AnnosWithoutProcessors.java

Lorsque le compilateur exécute le processeur d'annotations sur le fichier source AnnosWithoutProcessors.java, il génère l'avertissement suivant :

warning: [processing] No processor claimed any of these annotations: Anno

Pour résoudre ce problème, vous pouvez renommer l'annotation définie et utilisée dans la classe AnnosWithoutProcessors de Anno à NotAnno.

rawtypes
Avertit des opérations non vérifiées sur des types bruts. L'instruction suivante génère un avertissement rawtypes : 
void countElements(List l) { ... }

L'exemple suivant ne génère pas d'avertissement rawtypes :

void countElements(List l) { ... }

List est un type brut. Cependant, List est un type paramétré avec un wildcard illimité. Comme List est une interface paramétrée, spécifiez toujours son argument de type. Dans cet exemple, l'argument formel List est spécifié avec un wildcard illimité (?) comme paramètre de type formel, ce qui signifie que la méthode countElements peut accepter n'importe quelle instanciation de l'interface List.

Serial
Avertit de l'absence de définitions de serialVersionUID dans les classes sérialisables, par exemple : 
public class PersistentTime implements Serializable
{
  private Date time;
   public PersistentTime() {
     time = Calendar.getInstance().getTime();
   }
   public Date getTime() {
     return time;
   }
}

Le compilateur génère l'avertissement suivant :

warning: [serial] serializable class PersistentTime has no definition of
serialVersionUID

Si une classe sérialisable ne déclare pas explicitement un champ nommé serialVersionUID, l'environnement d'exécution de la sérialisation calcule une valeur par défaut de serialVersionUID pour cette classe en fonction de divers aspects de la classe, comme décrit dans la spécification de sérialisation d'objets Java. Cependant, il est fortement recommandé que toutes les classes sérialisables déclarent explicitement des valeurs de serialVersionUID car le processus par défaut de calcul des valeurs de serialVersionUID est très sensible aux détails de la classe qui peuvent varier en fonction des implémentations du compilateur, et par conséquent, pourraient causer des InvalidClassExceptions inattendues lors de la désérialisation. Pour garantir une valeur cohérente de serialVersionUID entre différentes implémentations de compilateur Java, une classe sérialisable doit déclarer une valeur explicite de serialVersionUID.

warning: [static] static method should be qualified by type name,

Pour résoudre ce problème, vous pouvez appeler la méthode static m1 comme suit :

XLintStatic.m1();

Alternativement, vous pouvez supprimer le mot-clé static de la déclaration de la méthode m1.

try
Avertit des problèmes liés à l'utilisation des blocs try, y compris les instructions try-with-resources. Par exemple, un avertissement est généré pour l'instruction suivante car la ressource ac déclarée dans le bloc try n'est pas utilisée : 
try ( AutoCloseable ac = getResource() ) { // do nothing}
unchecked
Fournit plus de détails pour les avertissements de conversion non vérifiée qui sont mandatés par la spécification du langage Java, par exemple : 
List l = new ArrayList();
List ls = l; // unchecked warning

Lors de l'effacement de type, les types ArrayList<Number> et List<String> deviennent respectivement ArrayList et List.

La commande ls a le type paramétré List<String>. Lorsque le List référencé par l est assigné à ls, le compilateur génère un avertissement non vérifié. Au moment de la compilation, le compilateur et la JVM ne peuvent pas déterminer si l fait référence à un type List<String>. Dans ce cas, l ne fait pas référence à un type List<String>. Par conséquent, une pollution de tas se produit.

Une situation de pollution de tas se produit lorsque l'objet List l, dont le type statique est List<Number>, est assigné à un autre objet List, ls, qui a un type statique différent, List<String>. Cependant, le compilateur autorise toujours cette affectation. Il doit autoriser cette affectation pour préserver la compatibilité ascendante avec les versions de Java SE qui ne prennent pas en charge les génériques. En raison de l'effacement de type, List<Number> et List<String> deviennent tous deux List. Par conséquent, le compilateur autorise l'affectation de l'objet l, qui a un type brut List, à l'objet ls.

varargs
Avertit des utilisations non sécurisées des méthodes à arguments variables (varargs), en particulier celles qui contiennent des arguments non réifiables, par exemple : 
public class ArrayBuilder {
  public static <T> void addToList (List<T> listArg, T... elements) {
    for (T x : elements) {
      listArg.add(x);
    }
  }
}

Note : Un type non réifiable est un type dont les informations de type ne sont pas entièrement disponibles au moment de l'exécution.

Le compilateur génère l'avertissement suivant pour la définition de la méthode ArrayBuilder.addToList :

warning: [varargs] Possible heap pollution from parameterized vararg type T

Lorsque le compilateur rencontre une méthode varargs, il traduit le paramètre formel varargs en un tableau. Cependant, le langage de programmation Java ne permet pas la création de tableaux de types paramétrés. Dans la méthode ArrayBuilder.addToList, le compilateur traduit le paramètre formel varargs T... elements en paramètre formel T[] elements, un tableau. Cependant, en raison de l'effacement de type, le compilateur convertit le paramètre formel varargs en Object[] elements. Par conséquent, il y a une possibilité de pollution de tas.

TRAITEMENT DES

ANNOTATIONS

La commande javac fournit une prise en charge directe du traitement des annotations, supprimant la nécessité de la commande distincte de traitement des annotations, apt

L'API pour les processeurs d'annotations est définie dans les paquets javax.annotation.processing et javax.lang.model et leurs

sous-paquets.

FONCTIONNEMENT DU TRAITEMENT DES

ANNOTATIONS

Sauf si le traitement des annotations est désactivé avec l'option -proc:none, le compilateur recherche tout processeur d'annotations disponible. Le chemin de recherche peut être spécifié avec l'option -processorpath. Si aucun chemin n'est spécifié, le chemin de classe de l'utilisateur est utilisé. Les processeurs sont localisés au moyen de fichiers de configuration de fournisseur de service nommés META-INF/services/javax.annotation.processing.Processor sur le chemin de recherche. Ces fichiers doivent contenir les noms de tout processeur d'annotations à utiliser, un par ligne. Alternativement, les processeurs peuvent être spécifiés explicitement, en utilisant l'option -processor

.

Après avoir analysé les fichiers source et les classes sur la ligne de commande pour déterminer quelles annotations sont présentes, le compilateur interroge les processeurs pour déterminer quelles annotations ils traitent. Lorsqu'une correspondance est trouvée, le processeur est appelé. Un processeur peut revendiquer les annotations qu'il traite, auquel cas aucune tentative supplémentaire n'est faite pour trouver des processeurs pour ces annotations. Une fois toutes les annotations revendiquées, le compilateur ne recherche pas de processeurs supplémentaires

.

Si des processeurs génèrent de nouveaux fichiers source, un autre tour de traitement des annotations se produit : Tout nouveau fichier source généré est analysé, et les annotations sont traitées comme avant. Tout processeur appelé lors des tours précédents est également appelé lors de tous les tours suivants. Cela continue jusqu'à ce qu'aucun nouveau fichier source ne soit

généré.

Après un tour où aucun nouveau fichier source n'est généré, les processeurs d'annotations sont appelés une dernière fois, pour leur donner une chance de terminer tout travail restant. Enfin, sauf si l'option -proc:only est utilisée, le compilateur compile les fic

hiers source originaux et tou
s les fichiers source générés.

RECHERCHE DE

TYPES

Pour compiler un fichier source, le compilateur a souvent besoin d'informations sur un type, mais la définition du type n'est pas dans les fichiers source spécifiés sur la ligne de commande. Le compilateur a besoin d'informations de type pour chaque classe ou interface utilisée, étendue ou implémentée dans le fichier source. Cela inclut les classes et interfaces non explicitement mentionnées dans le fichier source, mais qui fournissent des informations par

héritage.

Par exemple, lorsque vous créez une sous-classe java.applet.Applet, vous utilisez également les classes ancêtres de Applet : java.awt.Panel, java.awt.Container, java.awt.Component, et java.lang.O

bject.

Lorsque le compilateur a besoin d'informations de type, il recherche un fichier source ou un fichier classe qui définit le type. Le compilateur recherche les fichiers classe d'abord dans les classes de démarrage et d'extension, puis dans le chemin de classe de l'utilisateur (qui par défaut est le répertoire courant). Le chemin de classe de l'utilisateur est défini en définissant la variable d'environnement CLASSPATH ou en utilisant l'option -classpath

.

Si vous définissez l'option -sourcepath, le compilateur recherche les fichiers source sur le chemin indiqué. Sinon, le compilateur recherche dans le chemin de classe de l'utilisateur à la fois les fichiers classe et les fichiers

source.

Vous pouvez spécifier des classes de démarrage ou d'extension différentes avec les -bootclasspath et -extdirs options. Voir Options de compilation

croisée.

Une recherche de type réussie peut produire un fichier classe, un fichier source, ou les deux. Si les deux sont trouvés, vous pouvez utiliser l'option -Xprefer pour indiquer au compilateur lequel utiliser. Si newer est spécifié, le compilateur utilise le plus récent des deux fichiers. Si source est spécifié, le compilateur utilise le fichier source. La valeur par défaut est newer

.

Si une recherche de type trouve un fichier source pour un type requis, que ce soit par lui-même, ou à la suite du paramètre de l'option -Xprefer, le compilateur lit le fichier source pour obtenir les informations dont il a besoin. Par défaut, le compilateur compile également le fichier source. Vous pouvez utiliser l'option -implicit pour spécifier le comportement. Si none est spécifié, aucun fichier classe n'est généré pour le fichier source. Si class est spécifié, des fichiers classe sont générés pour le fichier

source.

Le compilateur pourrait ne pas découvrir le besoin de certaines informations de type avant la fin du traitement des annotations. Lorsque les informations de type sont trouvées dans un fichier source et qu'aucune option -implicit n'est spécifiée, le compilateur émet un avertissement indiquant que le fichier est compilé sans être soumis au traitement des annotations. Pour désactiver l'avertissement, spécifiez soit le fichier sur la ligne de commande (afin qu'il soit soumis au traitement des annotations) ou utilisez l'option -implicit pour spécifier si des fichiers classe doiv

ent être générés ou non pou
r de tels fichiers source.

                        NAME
                    

                    
javac - Java programming language compiler

                

                

                    

                        SYNOPSIS
                    

                    

                        javac
                         [options] [sourcepath] [compilation-units]
                    

                

                

                    

                        DESCRIPTION
                    

                    
The javac command reads
                        Java class source files and compiles them into Java
                        class files. This package includes the Java compiler
                        for the OpenJDK 11 release.

                    
The compiler operates in a number of
                        stages:

                    
    
                        
  • Lexical analysis
    • 
                        
  • Syntactic analysis
    • 
                        
  • Semantic analysis
    • 
                        
  • Abstract syntax tree construction
    • 
                        
  • Type checking
    • 
                        
  • Bytecode generation
    • 
                    

                    
The compiler can also perform annotation processing.
                        This allows custom code to run during compilation, for
                        example, to generate source files based on annotations in
                        other source files.

                

                

                    

                        OPTIONS
                    

                    
The javac command supports
                        a number of options that control the compilation process.
                        Some of the most common options are:

                    

                        
-classpath classpath

                        
Specifies the location of user-defined classes and
                            application extension JAR files to search for class
                            files. If this option is not set, the compiler
                            searches the user class path for classes.

                        
-source path

                        
Specifies the release of the Java programming
                            language from which you want the source code to be
                            read. For example, -source 1.7
                            or -source 7.

                        
-target release

                        
Specifies the release of virtual machine to which
                            you want the Java class files to be compiled. For
                            example, -target 1.7 or
                            -target 7.

                        
-bootclasspath path

                        
Overrides the default bootstrap class path. This
                            allows you to specify a particular version of the
                            Java platform to compile against.

                        
-extdirs dirs

                        
Overrides the default location of installed
                            extensions.

                        
-nowarn

                        
Suppresses all compiler warnings.

                        
-verbose

                        
Enables verbose output. This will cause the compiler
                            to print out messages about what it is doing,
                            including the files it is compiling and the
                            options it is using.

                    

                

                

                    

                        ENABLE OR  DISABLE WARNINGS WITH THE -XLINT OPTION
                    

                    
The javac compiler offers
                        a powerful mechanism for controlling compiler warnings.
                        You can enable or disable specific categories of warnings
                        using the -Xlint option. This
                        option takes a comma-separated list of warning names. For
                        example, -Xlint:deprecation
                        enables deprecation warnings, while
                        -Xlint:-path disables path
                        warnings.

                    
You can also use -Xlint:all
                        to enable all warnings, or -Xlint:none
                        to disable all warnings (equivalent to
                        -nowarn).

                

                

                    

                        COMMAND-LINE ARGUMENT FILES
                    

                    
If the list of source files or options becomes
                        too long for a single command line, you can use
                        argument files. An argument file is a text file that
                        contains compiler options and source file names, one per
                        line. You can specify an argument file by prefixing its
                        name with the @ symbol.

                    
javac @myoptions.txt @sourcefiles.txt


                

                

                    

                        ANNOTATION PROCESSING
                    

                    
Annotation processing is a feature that allows
                        you to extend the Java compiler. Annotation processors can
                        read annotations from your source code and generate new
                        source files, classes, or resources. This can be used for
                        tasks such as code generation, compile-time checking, and
                        documentation generation.

                    
To enable annotation processing, you can use the
                        following options:

                    

                        
-processor classnames

                        
Specifies the names of the annotation processors to
                            run.

                        
-processorpath path

                        
Specifies the path to search for annotation
                            processors.

                        
-s dir

                        
Specifies the directory in which to generate
                            processor-generated source files.

                        
-p dir

                        
Specifies the directory in which to place
                            processor-generated class files.

                    

                

                

                    

                        SEARCHING FOR TYPES
                    

                    
The Java compiler searches for types in several
                        locations, in the following order:

                    
    
                        
  1. The compiler's internal API
    2. 
                        
  2. Bootstrap class path
    3. 
                        
  3. Extension directories
    4. 
                        
  4. User class path
    5. 
                    

                    
The CLASSPATH environment
                        variable or the -classpath option
                        can be used to specify the user class path.

                

                

                    

                        PROGRAMMATIC INTERFACE
                    

                    
The Java compiler can also be invoked programmatically
                        from within a Java application. This is done using the
                        JavaCompiler interface, which is
                        part of the Java Management Extensions (JMX) API.
