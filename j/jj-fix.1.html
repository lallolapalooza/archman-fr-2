jj-fix(1) Manuel des commandes générales jj-fix(1)

NOM

jj-fix - Met à jour les fichiers avec des corrections de formatage ou d'autres modifications

SYNTAXE

jj fix [-s|--source] [--include-unchanged-files] [-R|--repository] [--ignore-working-copy] [--ignore-immutable] [--at-operation] [--debug] [--color] [--quiet] [--no-pager] [--config] [--config-file] [-h|--help] [FILESSETS]

DESCRIPTION

Met à jour les fichiers avec des corrections de formatage ou d'autres modifications

L'utilisation principale de cette commande est d'appliquer les résultats des outils de formatage de code automatique aux révisions qui peuvent ne pas être correctement formatées. Elle peut également être utilisée pour modifier des fichiers avec d'autres outils comme `sed` ou `sort`.

### Comment ça marche

Les fichiers modifiés dans les révisions données seront mis à jour avec les corrections déterminées en passant leur contenu de fichier à travers les outils externes que l'utilisateur a configurés pour ces fichiers. Les descendants seront également mis à jour en passant leurs versions des mêmes fichiers à travers les mêmes outils, ce qui garantira que les corrections ne seront pas perdues. Cela ne résultera jamais en de nouveaux conflits. Les fichiers avec des conflits existants seront mis à jour de tous les côtés du conflit, ce qui peut potentiellement augmenter ou diminuer le nombre de marqueurs de conflit.

### Configuration

Voir `jj help -k config` chapitre `Formatage du code et autres transformations de contenu de fichier` pour comprendre comment configurer vos outils.

### Exemple d'exécution

Considérons la configuration suivante. Nous avons deux formateurs de code (`clang-format` et `black`), qui s'appliquent à trois extensions de fichier différentes (`.cc`, `.h`, et `.py`):

```toml [fix.tools.clang-format] command = ["/usr/bin/clang-format", "--assume-filename=$path"] patterns = ["glob:'**/*.cc'",
"glob:'**/*.h'"]

[fix.tools.black] command = ["/usr/bin/black", "-", "--stdin-filename=$path"] patterns = ["glob:'**/*.py'"] ```

Maintenant, voyons ce qui arriverait à l'historique suivant, lors de l'exécution de `jj fix`.

```text C (mutable) | Modifie fichier: foo.py | B @ (copie de travail - mutable) | Modifie fichier: README.md | A (mutable) | Modifie les fichiers: src/bar.cc et src/bar.h | X (immuable) ```

Par défaut, `jj fix` modifiera les révisions qui correspondent au revset `reachable(@, mutable())` (voir `jj help -k revsets`) qui correspond aux révisions `A`, `B` et `C` ici.

Les opérations suivantes se produiront alors :

- Pour la révision `A`, le contenu de cette révision pour les fichiers `src/bar.cc` et
`src/bar.h` sera passé à `clang-format` et le résultat sera utilisé pour
recréer la révision `A`, que nous appellerons `A'`. Tous les autres
fichiers sont inchangés. - Pour la révision `B`, la même chose se produit pour les fichiers
`src/bar.cc` et `src/bar.h`. Leur contenu provenant de la révision `B`
passera par `clang-format`. Le fichier `README.md`, comme tout autre fichier,
n'est pas modifié car aucun motif ne lui correspond. Nous obtenons la
révision `B'`. - Pour la révision `C`, `src/bar.cc` et `src/bar.h` passent par `clang-format`
et le fichier `foo.py` est corrigé à l'aide de `black`. Tout autre fichier est inchangé. Nous obtenons la révision `C'`.

```text C (mutable) /-> C' | src/bar.cc -> clang-format -| | | src/bar.h --> clang-format -| | | foo.py -----> black --------| | | * --------------------------/ | | | B @ (copie de travail - mutable) /-> B' @ | src/bar.cc -> clang-format -| | | src/bar.h --> clang-format -| | | * --------------------------| | | | A (mutable) /-> A' | src/bar.cc -> clang-format -| | | src/bar.h --> clang-format -| | | * --------------------------/ | | | X (immuable) X ```

Les révisions sont maintenant toutes correctement formatées selon la configuration.

OPTIONS

-s, --source <REVSETS>
Corrige les fichiers dans les révisions spécifiées et leurs descendants. Si aucune révision n'est spécifiée, cela utilise par défaut le réglage `revsets.fix`, ou `reachable(@, mutable())` s'il n'est pas défini.
--include-unchanged-files
Corrige les fichiers inchangés en plus de ceux qui ont été modifiés. Si aucun chemin n'est spécifié, tous les fichiers du dépôt seront corrigés.
-h, --help
Affiche l'aide (voir un résumé avec '-h')
[FILESSETS]
Corrige uniquement ces chemins.

OPTIONS GLOBALES

-R, --repository <RÉPOSITORIE>
Chemin vers le dépôt à manipuler.

Par défaut, Jujutsu recherche le répertoire .jj/ le plus proche parmi les ancêtres du répertoire de travail actuel.

--ignore-working-copy
Ne pas enregistrer la copie de travail et ne pas la mettre à jour.

Par défaut, Jujutsu enregistre la copie de travail au début de chaque commande. La copie de travail est également mise à jour à la fin de la commande, si la commande a modifié le commit de la copie de travail (`@`). Si vous souhaitez éviter d'enregistrer la copie de travail et voir plutôt un commit de copie de travail potentiellement obsolète, vous pouvez utiliser `--ignore-working-copy`. Cela peut être utile par exemple dans une invite de commande, surtout si un autre processus effectue des commits de la copie de travail.

Le chargement du dépôt à une opération spécifique avec `--at-operation` implique `--ignore-working-copy`.

--ignore-immutable
Permettre la réécriture des commits immuables.

Par défaut, Jujutsu empêche la réécriture des commits dans l'ensemble configuré de commits immuables. Cette option désactive cette vérification et vous permet de réécrire n'importe quel commit sauf le commit racine.

Cette option n'affecte que la vérification. Elle n'affecte pas le revset `immutable_heads()` ni le mot-clé de modèle `immutable`.

--at-operation <AT_OPERATION>
Opération à laquelle charger le dépôt.

Opération à laquelle charger le dépôt. Par défaut, Jujutsu charge le dépôt à l'opération la plus récente, ou à la fusion des opérations divergentes s'il y en a.

Vous pouvez utiliser `--at-op=<ID d'opération>` pour voir à quoi ressemblait le dépôt lors d'une opération précédente. Par exemple, `jj --at-op=<ID d'opération> st` vous montrera ce que `jj st` aurait affiché lorsque l'opération donnée venait de se terminer. `--at-op=@` est pratiquement identique par défaut, sauf que les opérations divergentes ne seront jamais fusionnées.

Utilisez `jj op log` pour trouver l'ID d'opération souhaité. Toute préfixe non ambigu de l'ID d'opération est suffisant.

Lors du chargement du dépôt à une opération précédente, la copie de travail sera ignorée, comme si `--ignore-working-copy` avait été spécifié.

Il est possible d'exécuter des commandes mutantes lors du chargement du dépôt à une opération précédente. Cela équivaut à avoir exécuté des commandes concurrentes commençant à l'opération précédente. Il y a rarement une raison de le faire, mais c'est possible.

--debug
Activer la journalisation de débogage.
--color <QUAND>
Quand coloriser la sortie.

[valeurs possibles : always, never, debug, auto]

--quiet
Réduire au silence la sortie non principale de la commande.

Par exemple, `jj file list` listera toujours les fichiers, mais il ne vous dira pas si la copie de travail a été enregistrée ou si les descendants ont été rebasés.

Les avertissements et les erreurs seront toujours affichés.

--no-pager
Désactiver le pagineur.
--config <NOM=VALEUR>
Options de configuration supplémentaires (peuvent être répétées).

Le nom doit être spécifié sous forme de clés pointées TOML. La valeur doit être spécifiée comme une expression TOML. Si la valeur chaîne n'est pas entourée de constructions TOML (telles que la notation de tableau), les guillemets peuvent être omis.

--config-file <CHEMIN>
Fichiers de configuration supplémentaires (peuvent être répétés)

NAME

jj-fix - Fix commit

SYNOPSIS

jj fix [OPTIONS] [--message|-m MESSAGE] [--edit|-e]

DESCRIPTION

This command allows you to modify the most recent commit. If you don't provide any option other than --message or --edit, jj will attempt to create a commit with an empty message. This is useful if you forgot to set a commit message. If you want to set a commit message, you can use --message. If you want to edit the commit message, you can use --edit.

By default, jj fix will modify the most recent commit. If you want to modify a different commit, you can specify it.

This command is useful for making small changes to the last commit without having to create a new one. For example, if you forgot to add a file to the last commit, you can stage it and then run jj fix to add it to the last commit.

OPTIONS

--message, -m <message>
Set the commit message.
--edit, -e
Edit the commit message.

GLOBAL OPTIONS

--help, -h
Print help (see also jj help).
--config-var <VAR=VALUE>
Set a runtime configuration variable.
--log-format <log-format>

Configure the logging format. Possible values:

  • default (the default)
  • json
--log-level <log-level>

Configure the logging level. Possible values:

  • off
  • error
  • warn (the default)
  • info
  • debug
  • trace
--no-ignore-config
Disable the loading of the configuration file.
--quiet, -q
Silence anything that might be outputted.
--version, -V
Print version info.

SEE ALSO

jj(1), jj-commit(1), jj-rebase(1)

The commit message can be edited (or set from scratch) in an editor. If the editor is quit without saving, the commit is aborted.
