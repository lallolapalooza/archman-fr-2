DESCRIPTIO

N

L'outil javadoc analyse les déclarations et les commentaires de documentation dans un ensemble de fichiers source Java et les traite à l'aide d'un moteur arrière modulaire appelé doclet

.

Le doclet standard est celui qui est utilisé par défaut et peut produire les pages HTML correspondantes décrivant les classes publiques et protégées, les classes imbriquées et déclarées implicitement (mais pas les classes internes anonymes), les interfaces, les constructeurs, les méthodes et les champs. Le doclet standard interprète le contenu des commentaires de documentation conformément à la Spécification des commentaires de documentation JavaDoc pour le Doclet standard. Les balises personnalisées dans les commentaires de documentation sont prises en charge au moyen de taglets

.

Vous pouvez utiliser l'outil javadoc et le doclet standard pour générer la documentation d'API ou la documentation d'implémentation pour un ensemble de fichiers

source.

Vous pouvez exécuter l'outil javadoc sur des paquets entiers, des fichiers source individuels, ou les deux. Lors de la documentation de paquets entiers, vous pouvez utiliser l'option -subpackages soit pour parcourir récursivement un répertoire et ses sous-répertoires, soit pour passer une liste explicite de noms de paquets. Lorsque vous documentez des fichiers source individuels, passez une liste de noms de fichiers source

Java.

Commentaires de

documentation

L'outil javadoc utilise le commentaire de documentation, s'il existe, qui précède immédiatement le début de la déclaration, qu'il s'agisse d'une annotation, d'un modificateur ou du nom déclaré. S'il y a plusieurs commentaires de documentation avant la déclaration, seul le dernier (le plus proche de la déclaration) sera utilisé. S'il y a des commentaires de documentation après le début de la déclaration, ils seront ignorés. Pour détecter les commentaires de documentation superflus ou mal placés, compilez votre code source avec l'option javac -Xlint, ou plus précisément, -Xlint:dangling-doc-comments. Dans un fichier source, vous pouvez supprimer les avertissements générés par ces options en utilisant @SuppressWarnings("dangling-doc-comments")

sur une déclaration
englobante appropriée.

Conformit

é

Le doclet standard ne valide pas le contenu des commentaires de documentation pour la conformité et ne tente pas de corriger les erreurs éventuelles dans les commentaires de documentation. Il est conseillé à toute personne exécutant javadoc de prendre conscience des problèmes qui peuvent survenir lors de la génération d'une sortie non conforme ou d'une sortie contenant du contenu exécutable, tel que du JavaScript. Le doclet standard fournit la fonctionnalité DocLint pour aider les développeurs à détecter les problèmes courants dans les commentaires de documentation ; mais il est également recommandé de vérifier la sortie générée avec tout outil de vérification de conformité ou autre

approprié.

Pour plus de détails sur les exigences de conformité pour les documents HTML5, voir Exigences de conformité pour les auteurs [https://html.spec.whatwg.org/multipage/introduction.html#conformance-requirements-for-authors] dans la spécification HTML5. Pour plus de détails sur les problèmes de sécurité liés aux pages web, voir la page Open Web Application Security Project (OWASP)[https://w

ww.o

org].

-breakiterat

Calcule la première phrase de la description dans un commentaire de documentation à l'aide d'une instance de java.text.BreakIterator pour détecter les fins de phrase. Les règles utilisées dépendent de la locale actuelle : par exemple, pour l'anglais, une fin de phrase survient après un point, un point d'interrogation ou un point d'exclamation suivi d'un espace lorsqu
e le mot suivant commence par une majuscule. (Cela est destiné à gérer la plupart d

L'option est activée par défaut si la langue de la locale actuelle n'est pas l'anglais. Si la langue de la locale actuelle est l'anglais, et que l'option -breakiterator n'est pas spécifiée, un simple algorithme par défaut est utilisé, qui cherche simplement un point suivi d'une

Dans un commentaire /**...*/ traditionnel, la recherche de la fin de la première phrase est interrompue par une balise de bloc HTML, telle que <p>, <pre>, ou la balise d'un

Dans un commentaire /// Markdown, la recherche de la fin de la première phrase ignore tout caractère encadré dans des segments de code et des liens, et est interrompue par la fin du bloc initial, comme indiqué par une ligne vide ou le début du bloc suivant, tel qu'une liste, une rupture thématique ou un bloc

La première phrase de la description dans un commentaire de documentation est utilisée dans les tableaux récapitulatifs, les pages d'index et d'autres situations où un résumé court est requis. Pour un contrôle plus explicite dans n'importe quel commentaire de documentation individuel, encadrez le contenu de la première phrase dans une balise {@summary ...}, ou, le cas échéant, dans une balise {@return ...

DocLint permet de vérifier les problèmes possibles dans les commentaires de documentation. Les problèmes peuvent être signalés comme des avertissements ou des erreurs, selon leur gravité. Par exemple, un commentaire manquant peut être un mauvais style qui mérite un avertissement, mais un lien vers une déclaration Java inconnue est plus grave et mérite une erreur. Les problèmes sont organisés en groupes, et des options peuvent être utilisées pour activer ou désactiver les messages dans un ou plusieurs groupes. Dans le code source, les messages dans un ou plusieurs groupes peuvent être supprimés en utilisant les annotations @SuppressWarnings

.

Lorsqu'il est invoqué depuis javadoc, par défaut DocLint vérifie tous les commentaires utilisés dans la documentation générée. Il s'appuie donc sur d'autres options de ligne de commande pour déterminer quelles déclarations, et quels commentaires de documentation correspondants seront inclus. Remarque : cela peut signifier que même les commentaires sur certains membres privés de classes sérialisables seront également vérifiés, si les membres doivent être documentés dans la page Formes sérialisées

générée.

En revanche, lorsque DocLint est invoqué depuis javac, DocLint s'appuie uniquement sur les différentes options -Xdoclint... pour déterminer quels commentaires de documentation

vérifier.

DocLint n'essaie pas de corriger les entrées invalides, il les signale

simplement.

Remarque : DocLint ne garantit pas l'exhaustivité de ces vérifications. En particulier, ce n'est pas un vérificateur de conformité HTML complet. Le but est simplement de signaler les erreurs courantes de manière

pratique.

Les noms dans LISTE peuvent être spécifiés de manière équivalente dans des arguments séparés de l'annotation. Par exemple, les suivants sont équivalents

Le problème sera ignoré si une telle annotation est trouvée contenant la chaîne simple doclint ou la forme plus longue doclint:LISTE où LISTE contient le nom du groupe pour le

Comparaison avec les outils de validation en

aval

DocLint est une utilitaire intégré dans javac et javadoc qui vérifie le contenu des commentaires de documentation, tels que trouvés dans les fichiers source. En revanche, les outils de validation en aval peuvent être utilisés pour valider la sortie générée à partir de ces commentaires de documentation par javadoc et le doclet

standard.

Bien qu'il y ait un certain chevauchement dans les fonctionnalités, les deux mécanismes are différents et chacun a ses propres forces et faiblesses.

•
Les outils de validation en aval peuvent vérifier le résultat final de toute documentation générée, tel qu'il sera vu par l'utilisateur final. Cela inclut le contenu de toutes les sources, y compris les commentaires de documentation, le doclet standard lui-même, les taglets fournis par l'utilisateur et le contenu fourni via les options de ligne de commande. Étant donné que de tels outils analysent des pages HTML complètes, ils peuvent effectuer des vérifications plus complètes que DocLint. Cependant, lorsqu'un problème est trouvé dans les pages générées, il peut être plus difficile de déterminer exactement où dans le pipeline de construction le problème doit être corrigé.
•
DocLint vérifie le contenu des commentaires de documentation, dans les fichiers source. Cela permet d'identifier très facilement la position exacte de tout problème qui pourrait être trouvé. DocLint peut également détecter certaines erreurs sémantiques dans les commentaires de documentation que les outils en aval ne peuvent pas détecter, telles que les commentaires manquants, l'utilisation d'une balise @return dans une méthode retournant void, ou une balise @param décrivant un paramètre inexistant. Mais par sa nature, DocLint ne peut pas signaler les problèmes tels que les liens manquants, les erreurs dans les taglets personnalisés fournis par l'utilisateur, ou les problèmes dans le doclet standard lui-même. Il ne peut pas non plus détecter de manière fiable les erreurs dans les commentaires de documentation aux frontières entre le contenu d'un commentaire de documentation et le contenu généré par un taglet personnalisé.
