DESCRIPTIO

N

L'outil jarsigner a deux objectifs

:
•
Signer des fichiers Java Archive (JAR)
.
•
Vérifier les signatur

La fonctionnalité JAR permet d'empaqueter des fichiers de classes, des images, des sons et d'autres données numériques dans un seul fichier pour une distribution plus rapide et plus facile. Un outil nommé jar permet aux développeurs de produire des fichiers JAR. (Techniquement, tout fichier zip peut aussi être considéré comme un fichier JAR, bien que lorsqu'ils sont créés par la commande jar ou traités par la commande jarsigner, les fichiers JAR contiennent également un fichier META-INF/MANIFEST.MF.) META-INF/MANI

FEST.MF

Une signature numérique est une chaîne de bits calculée à partir de certaines données (les données étant signées) et de la clé privée d'une entité (une personne, une entreprise, etc.). De même qu'une signature manuscrite, une signature numérique possède de nombreuses caractéristiques utiles

:
•
Son authenticité peut être vérifiée par un calcul utilisant la clé publique correspondant à la clé privée utilisée pour générer la
signature.
•
Elle ne peut pas être contrefaite, à condition que la clé privée reste
secrète.
•
Elle est une fonction des données signées et ne peut donc pas être revendiquée comme la signature d'autres données
également.
•
Les données signées ne peuvent pas être modifiée
s. Si les données sont modifiées, la signat
ure ne peut pas être vérifiée comme authentique.

Pour générer la signature d'une entité pour un fichier, l'entité doit d'abord avoir une paire de clés publique/privée qui lui est associée et un ou plusieurs certificats qui authentifient sa clé publique. Un certificat est une déclaration signée numériquement par une entité qui indique que la clé publique d'une autre entité a une valeur

particulière.

La commande jarsigner utilise les informations de clé et de certificat d'un magasin de clés pour générer des signatures numériques pour les fichiers JAR. Un magasin de clés est une base de données de clés privées et de leurs chaînes de certificats X.509 associées qui authentifient les clés publiques correspondantes. La commande keytool est utilisée pour créer et administrer les magasins de

clés.

La commande jarsigner utilise la clé privée d'une entité pour générer une signature. Le fichier JAR signé contient, entre autres, une copie du certificat du magasin de clés pour la clé publique correspondant à la clé privée utilisée pour signer le fichier. La commande jarsigner peut vérifier la signature numérique du fichier JAR signé en utilisant le certificat qu'il contient (dans son fichier de bloc de signature)

.

La commande jarsigner peut générer des signatures qui incluent un horodatage permettant à un administrateur système ou de déploiement (y compris Java Plug-in) de vérifier si le fichier JAR a été signé alors que le certificat de signature était encore valide. De plus, des API permettent aux applications d'obtenir les informations

d'horodatage.

Pour l'instant, la commande jarsigner ne peut signer que les fichiers JAR créés par la commande jar ou les fichiers zip. Les fichiers JAR sont identiques aux fichiers zip, sauf qu'ils contiennent également un fichier META-INF/MANIFEST.MF. Un fichier META-INF/MANIFEST.MF est créé lorsque la commande jarsigner signe un fichier

zip.

Le comportement par défaut de la commande jarsigner est de signer un fichier JAR ou zip. Utilisez l'option -verify pour vérifier un fichier JAR

signé.

La commande jarsigner tente également de valider le certificat du signataire après la signature ou la vérification. S'il y a une erreur de validation ou tout autre problème, la commande génère des messages d'avertissement. Si vous spécifiez l'option -strict, la commande traite les avertissements graves comme des erreurs. Voir Erreurs et

avertissements.

IMPLÉMENTATION DU MAGASIN DE

CLÉS

La classe KeyStore fournie dans le paquet java.security fournit un certain nombre d'interfaces bien définies pour accéder et modifier les informations d'un magasin de clés. Vous pouvez avoir plusieurs implémentations concrètes différentes, où chaque implémentation est pour un type particulier de magasin de

clés.

Actuellement, il existe deux outils en ligne de commande qui utilisent des implémentations de magasin de clés (keytool et jarsigner), et un outil basé sur une interface graphique nommé Policy Tool. Comme la classe KeyStore est publiquement disponible, les utilisateurs du JDK peuvent écrire des applications de sécurité supplémentaires qui

l'utilisent.

Il existe une implémentation par défaut intégrée fournie par Oracle qui implémente le magasin de clés sous forme de fichier, qui utilise un type de magasin de clés (format) propriétaire nommé JKS. L'implémentation intégrée protège chaque clé privée avec son mot de passe individuel et protège l'intégrité de l'ensemble du magasin de clés avec un mot de passe (possiblement différent)

.

Les implémentations de magasin de clés sont basées sur les fournisseurs, ce qui signifie que les interfaces d'application fournies par la classe KeyStore sont implémentées en termes d'Interface de Fournisseur de Service (SPI). Il existe une classe abstraite correspondante KeystoreSpi, également dans le paquet java.security, qui définit les méthodes de l'Interface de Fournisseur de Service que les fournisseurs doivent implémenter. Le terme fournisseur fait référence à un paquet ou à un ensemble de paquets qui fournissent une implémentation concrète d'un sous-ensemble de services qui peuvent être accessibles via l'API de sécurité Java. Pour fournir une implémentation de magasin de clés, les clients doivent implémenter un fournisseur et fournir une KeystoreSpisous-classe KeyStoreSpi d'implémentation, comme décrit dans How to Implement a Provider in the Java Cryptography Architecture (Comment implémenter un fournisseur dans l'architecture de cryptographie Java) à l'adresse http://docs.oracle.com/javase/8/docs/technotes/guides/security/crypto/HowToImplAProvider.

html

Les applications peuvent choisir différents types d'implémentations de coffres de clés provenant de différents fournisseurs, avec la getInstance méthode fabrique de la classe KeyStore. Un type de coffre de clés définit le stockage et le format des données des informations du coffre de clés ainsi que les algorithmes utilisés pour protéger les clés privées dans le coffre de clés et l'intégrité du coffre de clés lui-même. Les implémentations de coffres de clés de types différents ne sont pas

compatibles.

Les jarsigner et policytool peuvent lire des coffres de clés basés sur des fichiers depuis n'importe quel emplacement pouvant être spécifié à l'aide d'une URL. De plus, ces commandes peuvent lire des coffres de clés non basés sur des fichiers, tels que ceux fournis par MSCAPI sur Windows et PKCS11 sur toutes les

plateformes.

Pour les commandes jarsigner et keytool, vous pouvez spécifier un type de coffre de clés en ligne de commande avec l'option -storetype . Pour Policy Tool, vous pouvez spécifier un type de coffre de clés avec la commande Edit dans le menu KeyStore

.

Si vous ne spécifiez pas explicitement un type de coffre de clés, les outils choisissent une implémentation de coffre de clés basée sur la valeur de la propriété keystore.type spécifiée dans le fichier de propriétés de sécurité. Le fichier de propriétés de sécurité est appelé java.security et se trouve dans le répertoire des propriétés de sécurité du JDK, java.home/lib/security, où java.home est le répertoire de l'environnement d'exécution. Le répertoire jre dans le JDK ou le répertoire de niveau supérieur de Java Runtime Environment (JRE)

.

Chaque outil obtient la valeur keystore.type et examine ensuite tous les fournisseurs installés jusqu'à ce qu'il en trouve un qui implémente des coffres de clés de ce type. Il utilise ensuite l'implémentation de coffre de clés de ce

fournisseur.

La classe KeyStore définit une méthode statique nommée getDefaultType qui permet aux applications et aux applets de récupérer la valeur de la propriété keystore.type. La ligne de code suivante crée une instance du type de coffre de clés par défaut tel que spécifié dans la propriété keystore.type

: 
KeyStore keyStore = KeyStore.getInstance(KeyStore.getDefaultType())
;

Le type de coffre de clés par défaut est jks (le type propriétaire de l'implémentation de coffre de clés fournie par Oracle). Cela est spécifié par la ligne suivante dans le fichier de propriétés de sécurité

: 
keystore.
type=jks

La casse n'a pas d'importance dans les désignations de type de coffre de clés. Par exemple, JKS est la même chose que jks

.

Pour que les outils utilisent une implémentation de coffre de clés autre que celle par défaut, changez cette ligne pour spécifier un type de coffre de clés différent. Par exemple, si vous avez un paquet de fournisseur qui fournit une implémentation de coffre de clés pour un type de coffre de clés appelé pkcs12, changez la ligne en ce qui suit

: 
keystore.
type=pkcs12

Remarque : Si vous utilisez le paquet de fournisseur PKCS 11, consultez « KeyTool » et « JarSigner » dans Java PKCS #11 Reference Guide (Guide de référence PKCS #11 de Java) à l'adresse http://docs.oracle.com/ja

vase/8/docs/technotes/guid
es/security/p11guide.html

VÉRIFICATION DU FICHIER

JAR

Une vérification de fichier JAR réussie se produit lorsque les signatures sont valides et qu'aucun des fichiers qui se trouvaient dans le fichier JAR au moment de la génération des signatures n'a changé depuis lors. La vérification du fichier JAR implique les étapes suivantes

:
1
.
Vérifier la signature du fichier .SF.

La vérification garantit que la signature stockée dans chaque fichier de bloc de signature (.DSA) a été générée à l'aide de la clé privée correspondant à la clé publique dont le certificat (ou la chaîne de certificats) apparaît également dans le fichier .DSA. Elle garantit également que la signature est une signature valide du fichier de signature correspondant (.SF) et que le fichier .SF n'a pas

été a
ltéré.
2
.
Vérifier le hachage listé dans chaque entrée du fichier .SF avec chaque section correspondante dans le manifeste.

Le fichier .SF inclut par défaut un en-tête qui contient un hachage de l'ensemble du fichier manifeste. Lorsque l'en-tête est présent, la vérification peut vérifier si le hachage dans l'en-tête correspond au hachage du fichier manifeste. S'il y a correspondance, la vérification passe à l'étape

suivante.

S'il n'y a pas de correspondance, une vérification moins optimisée est nécessaire pour garantir que le hachage dans chaque section d'informations de fichier source du fichier .SF est égal au hachage de sa section correspondante dans le fichier manifeste. Consultez Fichier de

signature.

Une raison pour laquelle le hachage du fichier manifeste stocké dans l'en-tête du fichier .SF pourrait ne pas être égal au hachage du fichier manifeste actuel est que un ou plusieurs fichiers ont été ajoutés au fichier JAR (avec l'outil jar) après la génération de la signature et du fichier .SF. Lorsque l'outil jar est utilisé pour ajouter des fichiers, le fichier manifeste est modifié en y ajoutant des sections pour les nouveaux fichiers, mais le fichier .SF n'est pas modifié. Une vérification est toujours considérée comme réussie lorsque aucun des fichiers qui se trouvaient dans le fichier JAR au moment de la génération de la signature n'a été modifié depuis lors. Cela se produit lorsque les hachages des sections autres que l'en-tête du fichier .SF sont égaux aux hachages des sections c

orrespondantes dans
le fichier manifeste.

-verbose

Lorsque l'option -verbose apparaît sur la ligne de commande, elle indique le mode verbeux, ce qui amène jarsigner à afficher des informations supplémentaires sur la progression de la signature ou de la vérification du JAR.
-internalsf

Par le passé, le fichier .DSA (bloc de signature) généré lors de la signature d'un fichier JAR incluait une copie complète encodée du fichier .SF (fichier de signature) également généré. Ce comportement a été modifié. Pour réduire la taille globale du fichier JAR de sortie, le fichier .DSA ne contient plus par défaut une copie du fichier .SF. Si -internalsf apparaît sur la ligne de commande, alors l'ancien comportement est utilisé. Cette option est utile pour les tests. En pratique, n'utilisez pas l'option -internalsf car elle entraîne une surcharge plus importante.
-sectionsonly

Si l'option -sectionsonly apparaît sur la ligne de commande, alors le fichier .SF (fichier de signature) généré lors de la signature d'un fichier JAR n'inclut pas d'en-tête contenant un hachage de l'ensemble du fichier manifeste. Il ne contient que les informations et les hachages relatifs à chaque fichier source individuel inclus dans le fichier JAR. Voir Fichier de signature.

Par défaut, cet en-tête est ajouté, comme optimisation. Lorsque l'en-tête est présent, chaque fois que le fichier JAR est vérifié, la vérification peut d'abord vérifier si le hachage dans l'en-tête correspond au hachage de l'ensemble du fichier manifeste. En cas de correspondance, la vérification passe à l'étape suivante. En l'absence de correspondance, il est nécessaire d'effectuer une vérification moins optimisée, à savoir que le hachage dans chaque section d'informations de fichier source du fichier .SF est égal au hachage de sa section correspondante dans le fichier manifeste. Voir Vérification du fichier JAR.

L'option -sectionsonly est principalement utilisée pour les tests. Elle ne doit pas être utilisée autrement que pour les tests, car son utilisation entraîne une surcharge plus importante.

-protected

Les valeurs peuvent être true ou false. Spécifiez true lorsqu'un mot de passe doit être spécifié via un chemin d'authentification protégé tel qu'un lecteur de code PIN dédié.
-providerClass nom-classe-fournisseur

Utilisé pour spécifier le nom du fichier de classe maître du fournisseur de services cryptographiques lorsque le fournisseur de services n'est pas répertorié dans le fichier de propriétés de sécurité java.security.

Utilisé avec l'option -providerArg CheminFichierConfig, les outils keytool et jarsigner installent le fournisseur dynamiquement et utilisent CheminFichierConfig pour le chemin d'accès au fichier de configuration du jeton. L'exemple suivant montre une commande pour lister un keystore PKCS #11 lorsque le fournisseur Oracle PKCS #11 n'était pas configuré dans le fichier de propriétés de sécurité.

jarsigner -keystore AUCUN -storetype PKCS11 \
          -providerClass sun.security.pkcs11.SunPKCS11 \
          -providerArg /mondossier1/mondossier2/jeton.config \
          -list
-providerName nomFournisseur

Si plusieurs fournisseurs ont été configurés dans le fichier de propriétés de sécurité java.security, vous pouvez utiliser l'option -providerName pour cibler une instance de fournisseur spécifique. L'argument de cette option est le nom du fournisseur.

Pour le fournisseur Oracle PKCS #11, nomFournisseur est de la forme SunPKCS11-NomJeton, où NomJeton est le suffixe de nom avec lequel l'instance du fournisseur a été configurée, comme détaillé dans le tableau des attributs de configuration. Par exemple, la commande suivante liste le contenu de l'instance du fournisseur de keystore PKCS #11 avec le suffixe de nom SmartCard :

jarsigner -keystore AUCUN -storetype PKCS11 \
        -providerName SunPKCS11-SmartCard \
        -list
-Joptionjava

Transmet la chaîne optionjava spécifiée directement à l'interpréteur Java. La commande jarsigner est un wrapper autour de l'interpréteur. Cette option ne doit pas contenir d'espaces. Elle est utile pour ajuster l'environnement d'exécution ou l'utilisation de la mémoire. Pour une liste des options d'interpréteur possibles, tapez java -h ou java -X sur la ligne de commande.
-tsa url

Si -tsa http://example.tsa.url apparaît sur la ligne de commande lors de la signature d'un fichier JAR, alors un horodatage est généré pour la signature. L'URL, http://example.tsa.url, identifie l'emplacement de l'Autorité d'Horodatage (TSA) et remplace toute URL trouvée avec l'option -tsacert. L'option -tsa ne nécessite pas que le certificat de clé publique de la TSA soit présent dans le keystore.

Pour générer l'horodatage, jarsigner communique avec la TSA en utilisant le protocole d'horodatage (TSP) défini dans la RFC 3161. En cas de succès, le jeton d'horodatage renvoyé par la TSA est stocké avec la signature dans le fichier de bloc de signature.

-tsacert alias

Lorsque -tsacert alias apparaît sur la ligne de commande lors de la signature d'un fichier JAR, un horodatage est généré pour la signature. L'alias identifie le certificat de clé publique de la TSA dans le keystore qui est en vigueur. Le certificat de l'entrée est examiné pour une extension d'accès aux informations du sujet qui contient une URL identifiant l'emplacement de la TSA.

Le certificat de clé publique de la TSA doit être présent dans le keystore lors de l'utilisation de l'option -tsacert.

-tsapolicyid identifiantpolitique

Spécifie l'identifiant d'objet (OID) qui identifie l'identifiant de politique à envoyer au serveur TSA. Si cette option n'est pas spécifiée, aucun identifiant de politique n'est envoyé et le serveur TSA choisira un identifiant de politique par défaut.

Les identifiants d'objet sont définis par la norme X.696 de l'UIT-T (Union Internationale des Télécommunications - Secteur de la Normalisation des Télécommunications). Ces identifiants sont généralement des ensembles de chiffres non négatifs séparés par des points, tels que 1.2.3.4, par exemple.

-altsigner classe

Cette option spécifie un mécanisme de signature alternatif. Le nom de classe entièrement qualifié identifie un fichier de classe qui étend la classe abstraite com.sun.jarsigner.ContentSigner. Le chemin d'accès à ce fichier de classe est défini par l'option -altsignerpath. Si l'option -altsigner est utilisée, alors la commande jarsigner utilise le mécanisme de signature fourni par la classe spécifiée. Sinon, la commande jarsigner utilise son mécanisme de signature par défaut.

Par exemple, pour utiliser le mécanisme de signature fourni par une classe nommée com.sun.sun.jarsigner.AuthSigner, utilisez l'option jarsigner -altsigner com.sun.jarsigner.AuthSigner.

-altsignerpath listecodepath

Spécifie le chemin d'accès au fichier de classe et à tout fichier JAR dont il dépend. Le nom du fichier de classe est spécifié avec l'option -altsigner. Si le fichier de classe se trouve dans un fichier JAR, alors cette option spécifie le chemin d'accès à ce fichier JAR.

Un chemin absolu ou un chemin relatif au répertoire courant peut être spécifié. Si listecodepath contient plusieurs chemins ou fichiers JAR, ils doivent être séparés par un deux-points (:) sur Oracle Solaris et un point-virgule (;) sous Windows. Cette option n'est pas nécessaire lorsque la classe est déjà dans le chemin de recherche.

L'exemple suivant montre comment spécifier le chemin d'accès à un fichier JAR contenant le fichier de classe. Le nom du fichier JAR est inclus.

-altsignerpath /home/utilisateur/lib/authsigner.jar

L'exemple suivant montre comment spécifier le chemin d'accès au fichier JAR contenant le fichier de classe. Le nom du fichier JAR est omis.

-altsignerpath /home/utilisateur/classes/com/sun/tools/jarsigner/
-strict

Pendant le processus de signature ou de vérification, la commande peut émettre des messages d'avertissement. Si vous spécifiez cette option, le code de sortie de l'outil reflète les messages d'avertissement sévères que cette commande a trouvés. Voir Erreurs et avertissements.
-verbose sous-options

Pour le processus de vérification, l'option -verbose prend des sous-options pour déterminer la quantité d'informations affichées. Si l'option -certs est également spécifiée, alors le mode par défaut (ou la sous-option all) affiche chaque entrée lorsqu'elle est traitée, et après cela, les informations de certificat pour chaque signataire du fichier JAR. Si les sous-options -certs et -verbose:grouped sont spécifiées, alors les entrées avec les mêmes informations de signataire sont regroupées et affichées avec leurs informations de certificat. Si -certs et les sous-options -verbose:summary sont spécifiées, alors les entrées avec les mêmes informations de signataire sont regroupées et affichées avec leurs informations de certificat. Les détails de chaque entrée sont résumés et affichés comme une entrée (et plus). Voir Exemples.

ERREURS ET AVERTISSEMENTS

Lors du processus de signature ou de vérification, la commande jarsigner peut émettre diverses erreurs ou avertissements.

En cas d'échec, la commande jarsigner se termine avec le code 1. S'il n'y a pas d'échec, mais qu'il y a un ou plusieurs avertissements sévères, la commande jarsigner se termine avec le code 0 lorsque l'option -strict n'est *pas* spécifiée, ou se termine avec la valeur OR des codes d'avertissement lorsque -strict est spécifié. S'il n'y a pas d'o

nly informational warnings or no warning at all, the command always exits with code

0.

For example, if a certificate used to sign an entry is expired and has a KeyUsage extension that does not allow it to sign a file, the jarsigner command exits with code 12 (=4+8) when the -strict option is

specified.

Note: Exit codes are reused because only the values from 0 to 255 are legal on Unix-based operating

systems.
