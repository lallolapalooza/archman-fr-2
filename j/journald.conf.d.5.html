DESCRIPTIO

N

Ces fichiers configurent divers paramètres du service journal systemd, systemd-journald.service(8). Voir systemd.syntax(7) pour une description générale de la

syntaxe.

L'instance systemd-journald gérant l'espace de noms par défaut est configurée par /etc/systemd/journald.conf et les drop-ins associés. Les instances gérant d'autres espaces de noms lisent /etc/systemd/journald@NAMESPACE.conf et les drop-ins associés avec l'identifiant de l'espace de noms remplacé. Cela permet à chaque espace de noms d'avoir une configuration distincte. Voir systemd-journald.service(8) pour plus de d

étails sur les espace
s de noms du journal.

RÉPERTOIRES DE CONFIGURATION ET

PRÉCÉDENCE

La configuration par défaut est définie lors de la compilation ; une configuration n'est donc nécessaire que lorsqu'il faut s'écarter de ces valeurs par défaut. Le fichier de configuration principal est chargé depuis l'un des répertoires listés par ordre de priorité ; seul le premier fichier trouvé est utilisé : /etc/systemd/, /run/systemd/, /usr/local/lib/systemd/ [1], /usr/lib/systemd/. La version du fichier fournie par le fournisseur contient des entrées commentées montrant les valeurs par défaut, à titre de guide pour l'administrateur. Des surcharges locales peuvent également être créées en créant des drop-ins, comme décrit ci-dessous. Le fichier de configuration principal peut également être modifié à cette fin (ou une copie dans /etc/ s'il est fourni sous /usr/), mais l'utilisation de drop-ins pour la configuration locale est recommandée plutôt que la modification du fichier de configuration

principal.

En plus du fichier de configuration principal, des extraits de configuration drop-in sont lus depuis /usr/lib/systemd/*.conf.d/, /usr/local/lib/systemd/*.conf.d/ et /etc/systemd/*.conf.d/. Ces drop-ins ont une priorité plus élevée et remplacent le fichier de configuration principal. Les fichiers dans les sous-répertoires de configuration *.conf.d/ sont triés par leur nom de fichier dans l'ordre lexicographique, indépendamment du sous-répertoire dans lequel ils se trouvent. Lorsque plusieurs fichiers spécifient la même option, pour les options qui n'acceptent qu'une seule valeur, l'entrée du fichier trié en dernier prend la priorité, et pour les options qui acceptent une liste de valeurs, les entrées sont collectées au fur et à mesure qu'elles apparaissent dans les fichiers

triés.

Lorsque les paquets doivent personnaliser la configuration, ils peuvent installer des drop-ins sous /usr/. Les fichiers dans /etc/ sont réservés à l'administrateur local, qui peut utiliser cette logique pour remplacer les fichiers de configuration installés par les paquets du fournisseur. Des drop-ins doivent être utilisés pour remplacer les drop-ins des paquets, car le fichier de configuration principal a une priorité plus faible. Il est recommandé de préfixer tous les noms de fichiers dans ces sous-répertoires avec un numéro à deux chiffres et un tiret, afin de simplifier le tri. Cela définit également un concept de priorité des drop-ins pour permettre aux fournisseurs de systèmes d'exploitation de fournir des drop-ins dans une plage spécifique inférieure à celle utilisée par les utilisateurs. Cela devrait réduire le risque que les drop-ins des paquets remplacent accidentellement des drop-ins définis par les utilisateurs. Il est recommandé d'utiliser la plage 10-40 pour les drop-ins dans /usr/ et la plage 60-90 pour les drop-ins dans /etc/ et /run/, afin de s'assurer que les drop-ins locaux et transitoires ont la priorité sur les drop-ins fournis par le fournisseur du système

d'exploitation.

Pour désactiver un fichier de configuration fourni par le fournisseur, la méthode recomman

dée consiste à placer un lien symbolique vers /dev/null dans le répertoire de configurati
on dans /etc/, avec le même nom de fichier que le fichier de configuration du fournisseur.

Storage

=
Contrôle où stocker les données du journal. Une des valeurs "volatile", "persistent", "auto" et "none". Si "volatile", les données du journal seront stockées uniquement en mémoire, c'est-à-dire sous la hiérarchie /run/log/journal (qui est créée si nécessaire). Si "persistent", les données seront stockées de préférence sur disque, c'est-à-dire sous la hiérarchie /var/log/journal (qui est créée si nécessaire), avec un repli sur /run/log/journal (qui est créée si nécessaire), lors du démarrage précoce et si le disque n'est pas inscriptible. "auto" se comporte comme "persistent" si le répertoire /var/log/journal existe, et "volatile" sinon (l'existence du répertoire contrôle le mode de stockage). "none" désactive tout stockage ; toutes les données de journal reçues seront abandonnées (mais la transmission vers d'autres cibles, comme la console, le tampon de journalisation du noyau ou un socket syslog, fonctionnera toujours). Par défaut, "auto" dans l'espace de noms du journal par défaut, et "persistent" dans tous les autres.

Notez que journald utilisera initialement le stockage volatile, jusqu'à ce qu'un appel à journalctl --flush (ou l'envoi de SIGUSR1 à journald) le fasse passer à la journalisation persistante (dans les conditions mentionnées ci-dessus). Cela se fait automatiquement au démarrage via "systemd-journal-flush.

service".

Notez que lorsque cette option est changée en "volatile", les données persistantes existantes ne sont pas supprimées. Dans l'autre sens, journalctl(1) avec l'option --flush peut être utilisé pour déplacer les données volatiles vers le stockage

persistant.

Lorsque l'espace de noms du journal (voir LogNamespace= dans systemd.exec(5)) est utilisé, le réglage de Storage= sur "volatile" ou "auto" n'aura pas d'effet sur la création du répertoire des journaux par espace de noms dans /var/log/journal/, car le fichier de service systemd-journald@.service contient par défaut LogsDirectory=. Pour désactiver cela, ajoutez un fichier drop-in d'unité qui définit LogsDirectory= à une chaîne

vide.

Notez que les fichiers de journal par utilisateur ne sont pas pris en charge à moins que le stockage persistant soit activé, ce qui rend journalctl --user

indisponible.

Le stockage à utiliser peut également être spécifié via la référence "journal.storage". Les valeurs configurées via les fichiers de configuration ont la priorité sur les valeurs configurées via la

référence.

ForwardToSyslog=, ForwardToKMsg=, ForwardToConsole=, ForwardToWall=, ForwardToSocket= Contrôle si les messages de journal reçus par le démon de journal doivent être transférés à un démon syslog traditionnel, au tampon de journal du noyau (kmsg), à la console système, envoyés comme messages wall à tous les utilisateurs connectés ou envoyés via un socket. Ces options prennent des arguments booléens sauf "ForwardToSocket=" qui prend une adresse à la place. Audit

=
Prend une valeur booléenne ou la valeur spéciale "keep". Si activé systemd-journald activera l'audit du noyau au démarrage. S'il est désactivé, il le désactivera. LineMax

=
La longueur de ligne maximale à autoriser lors de la conversion des journaux de flux en journaux d'enregistrements. Lorsque la sortie standard / erreur d'une unité systemd est connectée au journal via un socket de flux, les données lues sont divisées en enregistrements de journal individuels aux caractères de nouvelle ligne ("\n", ASCII 10) et NUL . Si aucun délimiteur de ce type n'est lu pour le nombre d'octets spécifié, une limite d'enregistrement de journal stricte est insérée artificiellement, divisant les lignes trop longues en plusieurs enregistrements de journal. Le choix de valeurs trop grandes augmente l'utilisation mémoire possible du démon Journal pour chaque client de flux, car dans le pire des cas, le démon journal doit tamponner le nombre d'octets spécifié en mémoire avant de pouvoir vider un nouvel enregistrement de journal sur le disque. Notez également qu'autoriser des longueurs de ligne maximales trop grandes affecte la compatibilité avec les protocoles de journalisation traditionnels, car les enregistrements de journal pourraient ne plus tenir dans un seul datagramme AF_UNIX ou AF_INET. Prend une taille en octets. Si la valeur est suffixée avec K, M, G ou T, la taille spécifiée est interprétée respectivement comme des Kilooctets, Mégaoctets, Gigaoctets ou Téraoctets (avec la base 1024). La valeur par défaut est 48K, ce qui est relativement grand mais encore assez petit pour que les enregistrements de journal aient probablement leur place dans les datagrammes réseau avec de la place supplémentaire pour les métadonnées. Notez que les valeurs inférieures à 79 ne sont pas acceptées et seront portées à 79.

TRANSMISSION AUX DÉMONS SYSLOG

TRADITIONNELS

Les événements du journal peuvent être transférés à un autre démon de journalisation de deux manières différentes. Avec la première méthode, les messages sont immédiatement transmis à un socket (/run/systemd/journal/syslog), où le démon syslog traditionnel peut les lire. Cette méthode est contrôlée par l'option ForwardToSyslog=. Avec une deuxième méthode, un démon syslog se comporte comme un client de journal normal et lit les messages à partir des fichiers du journal, de manière similaire à journalctl(1). Avec cela, les messages n'ont pas à être lus immédiatement, ce qui permet à un démon de journalisation qui n'est démarré que tard dans la séquence de démarrage d'accéder à tous les messages depuis le démarrage du système. De plus, les métadonnées structurées complètes lui sont disponibles. Cette méthode n'est bien sûr disponible que si les messages sont stockés dans un fichier de journal. Elle ne fonctionnera donc pas si Storage=none est défini. Il convient de noter que généralement la deuxième méthode est utilisée par les démons syslog, donc le paramètre Storage=, et non le paramètre ForwardToSyslog=,
