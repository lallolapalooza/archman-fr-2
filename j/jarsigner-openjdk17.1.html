DESCRIPTIO

N

L'outil jarsigner a deux objectifs

:
•
Signer des fichiers d'archive Java (JAR)
.
•
Vérifier les signatur
es et l'intégrité des
fichiers JAR signés.

La fonctionnalité JAR permet d'empaqueter des fichiers de classes, des images, des sons et d'autres données numériques dans un seul fichier pour une distribution plus rapide et plus facile. Un outil nommé jar permet aux développeurs de produire des fichiers JAR. (Techniquement, tout fichier ZIP peut aussi être considéré comme un fichier JAR, bien que lorsqu'il est créé par la commande jar ou traité par la commande jarsigner, les fichiers JAR contiennent également un fichier META-INF/MANIFEST.MF.

)

Une signature numérique est une chaîne de bits calculée à partir de certaines données (les données étant signées) et de la clé privée d'une entité (une personne, une entreprise, etc.). De même qu'une signature manuscrite, une signature numérique possède de nombreuses caractéristiques utiles

:
•
Son authenticité peut être vérifiée par un calcul utilisant la clé publique correspondant à la clé privée utilisée pour générer la
signature.
•
Elle ne peut pas être contrefaite, à condition que la clé privée reste
secrète.
•
Elle est une fonction des données signées et ne peut donc pas être revendiquée comme la signature d'autres données
également.
•
Les données signées ne peuvent pas être modifiée
s. Si les données sont modifiées, la signat
ure ne peut pas être vérifiée comme authentique.

Pour générer la signature d'une entité pour un fichier, l'entité doit d'abord avoir une paire de clés publique/privée qui lui est associée et un ou plusieurs certificats qui authentifient sa clé publique. Un certificat est une déclaration signée numériquement par une entité qui indique que la clé publique d'une autre entité a une valeur

particulière.

La commande jarsigner utilise les informations de clé et de certificat d'un magasin de clés pour générer des signatures numériques pour les fichiers JAR. Un magasin de clés est une base de données de clés privées et de leurs chaînes de certificats X.509 associées qui authentifient les clés publiques correspondantes. La commande keytool est utilisée pour créer et administrer les magasins de

clés.

La commande jarsigner utilise la clé privée d'une entité pour générer une signature. Le fichier JAR signé contient, entre autres, une copie du certificat du magasin de clés pour la clé publique correspondant à la clé privée utilisée pour signer le fichier. La commande jarsigner peut vérifier la signature numérique du fichier JAR signé en utilisant le certificat qu'il contient (dans son fichier de bloc de signature)

.

La commande jarsigner peut générer des signatures qui incluent un horodatage permettant à un administrateur système ou au déployeur de vérifier si le fichier JAR a été signé alors que le certificat de signature était encore

valide.

De plus, des API permettent aux applications d'obtenir les informations

d'horodatage.

Pour le moment, la commande jarsigner ne peut signer que les fichiers JAR créés par la commande jar ou les fichiers zip. Les fichiers JAR sont identiques aux fichiers zip, sauf qu'ils contiennent aussi un fichier META-INF/MANIFEST.MF. Un fichier META-INF/MANIFEST.MF est créé lorsque la commande jarsigner signe un fichier

zip.

Le comportement par défaut de la commande jarsigner est de signer un fichier JAR ou zip. Utilisez l'option -verify pour vérifier un fichier JAR

signé.

La commande jarsigner tente également de valider le certificat du signataire après la signature ou la vérification. Lors de la validation, elle vérifie le statut de révocation de chaque certificat de la chaîne de certificats du signataire lorsque l'option -revCheck est spécifiée. S'il y a une erreur de validation ou tout autre problème, la commande génère des messages d'avertissement. Si vous spécifiez l'option -strict, la commande traite alors les avertissements graves comme des erreurs. Voir Erreurs et av

ertisse
ments.

IMPLÉMENTATION DU MAGASIN DE

CLÉS

La classe KeyStore fournie dans le paquet java.security fournit un certain nombre d'interfaces bien définies pour accéder et modifier les informations d'un magasin de clés. Vous pouvez avoir plusieurs implémentations concrètes différentes, où chaque implémentations est pour un type particulier de magasin de

clés.

Actuellement, il existe deux outils en ligne de commande qui utilisent des implémentations de magasin de clés (keytool> et jarsigner) .

L'implémentation de magasin de clés par défaut est PKCS12. Il s'agit d'un magasin de clés multiplateforme basé sur la norme PKCS12 d'échange d'informations personnelles d'RSA. Cette norme est principalement destinée au stockage ou au transport des clés privées, des certificats et des secrets divers d'un utilisateur. Il existe une autre implémentation intégrée, fournie par Oracle. Elle implémente le magasin de clés sous la forme d'un fichier avec un type (format) de magasin de clés propriétaire nommé JKS. Elle protège chaque clé privée avec son mot de passe individuel, et protège également l'intégrité de l'ensemble du magasin de clés avec un mot de

passe

(éventuellement différent). Les implémentations de magasin de clés sont basées sur des fournisseurs, ce qui signifie que les interfaces d'application fournies par la classe KeyStore sont implémentées en termes d' SPI (Service Provider Interface). Il existe une classe abstraite correspondante KeystoreSpi, également dans le package java.security, qui définit les méthodes du SPI que les fournisseurs doivent implémenter. Le terme fournisseur fait référence à un package ou à un ensemble de packages qui fournissent une implémentation concrète d'un sous-ensemble de services qui peuvent être accessibles par l' API de sécurité Java. Pour fournir une implémentation de magasin de clés, les clients doivent implémenter un fournisseur et fournir une implémentation de sous-classe de KeystoreSpi, comme décrit dans Comment implémenter unfournisseur dans l'architecture de cryptographie Java [ https://www.oracle.com/pls/topic/lookup?ctx=en/java/javase/11/tools&i

d

=JSSEC-GUID-2BCFDD85-D533-4E6C-8CE9-29990DEB0190]. Les applications peuvent choisir différents types d'implémentations de magasin de clés provenant de différents fournisseurs, avec la méthode factory getInstance dans la classe KeyStore. Un type de magasin de clés définit le format de stockage et de données des informations du magasin de clés et les algorithmes utilisés pour protéger les clés privées dans le magasin de clés et l'intégrité du magasin

de

clés lui-même. Les implémentations de magasins de clés de types différents ne sont pas compatibles. Les commandes jarsigner peuvent lire des magasins de clés basés sur des fichiers depuis tout emplacement pouvant être spécifié à l'aide d'une URL. De plus, ces

commandes

Le fichier de signature, par défaut, inclut un en-tête avec un hachage de l'ensemble du fichier manifeste. L'en-tête contient également un hachage de l'en-tête du manifeste. La présence de l'en-tête permet l'optimisation de la vérification. Voir VÉRIFICATION DU FICHIER JAR.

VÉRIFICATION DU FICHIER JAR

Une vérification de fichier JAR réussie se produit lorsque les signatures sont valides et qu'aucun des fichiers qui se trouvaient dans le fichier JAR au moment où les signatures ont été générées n'a été modifié depuis. La vérification du fichier JAR implique les étapes suivantes :

1.
Vérifier la signature du fichier .SF.

La vérification garantit que la signature stockée dans chaque fichier de bloc de signature a été générée à l'aide de la clé privée correspondant à la clé publique dont le certificat (ou la chaîne de certificats) apparaît également dans le fichier de bloc de signature. Elle garantit également que la signature est une signature valide du fichier de signature correspondant (.SF), et donc que le fichier .SF n'a pas été falsifié.

2.
Vérifier le condensat indiqué dans chaque entrée du fichier .SF avec chaque section correspondante du manifeste.

Le fichier .SF inclut par défaut un en-tête contenant un hachage de l'intégralité du fichier manifeste. Lorsque l'en-tête est présent, la vérification peut vérifier si le hachage dans l'en-tête correspond ou non au hachage du fichier manifeste. S'il y a correspondance, la vérification passe à l'étape suivante.

En l'absence de correspondance, une vérification moins optimisée est nécessaire pour garantir que le hachage dans chaque section d'informations de fichier source du fichier .SF est égal au hachage de sa section correspondante dans le manifeste. Voir Fichier de signature.

Une raison pour laquelle le hachage du fichier manifeste stocké dans l'en-tête du fichier .SF pourrait ne pas correspondre au hachage du fichier manifeste actuel est qu'il pourrait contenir des sections pour des fichiers nouvellement ajoutés après que le fichier a été signé. Par exemple, supposons qu'un ou plusieurs fichiers ont été ajoutés au fichier JAR signé (à l'aide de l'outil jar) qui contient déjà une signature et un fichier .SF. Si le fichier JAR est à nouveau signé par un signataire différent, le fichier manifeste est modifié (des sections y sont ajoutées pour les nouveaux fichiers par l'outil jarsigner) et un nouveau fichier .SF est créé, mais le fichier .SF d'origine reste inchangé. Une vérification est toujours considérée comme réussie si aucun des fichiers qui se trouvaient dans le fichier JAR au moment où la signature d'origine a été générée n'a été modifié depuis. En effet, les hachages dans les sections sans en-tête du fichier .SF sont égaux aux hachages des sections correspondantes dans le fichier manifeste.

3.
Lire chaque fichier du JAR qui a une entrée dans le fichier .SF. Pendant la lecture, calculer le condensat du fichier et comparer le résultat avec le condensat de ce fichier dans la section du manifeste. Les condensats doivent être identiques, sinon la vérification échoue.

Si des échecs de vérification graves surviennent pendant le processus de vérification, le processus est arrêté et une exception de sécurité est levée. La commande jarsigner intercepte et affiche l'exception.

4.
Vérifier l'utilisation d'algorithmes désactivés. Voir Algorithmes pris en charge.

Remarque :

Vous devriez lire tous les avertissements supplémentaires (ou les erreurs si vous avez spécifié l'option -strict), ainsi que le contenu du certificat (en spécifiant les options -verbose et -certs) pour déterminer si la signature peut être fiable.

SIGNATURES MULTIPLES POUR UN FICHIER JAR

Un fichier JAR peut être signé par plusieurs personnes en exécutant la commande jarsigner sur le fichier plusieurs fois et en spécifiant l'alias d'une personne différente à chaque fois, comme suit :


jarsigner monBundle.jar susan
jarsigner monBundle.jar kevin

Lorsqu'un fichier JAR est signé plusieurs fois, il y a plusieurs fichiers .SF et de blocs de signature dans le fichier JAR résultant, une paire pour chaque signature. Dans l'exemple précédent, le fichier JAR de sortie inclut des fichiers avec les noms suivants :


SUSAN.SF
SUSAN.RSA
KEVIN.SF
KEVIN.RSA

OPTIONS POUR JARSIGNER

Les sections suivantes décrivent les options de jarsigner. Soyez conscient des normes suivantes :

•
Tous les noms d'options sont précédés d'un trait d'union (-).
•
Les options peuvent être fournies dans n'importe quel ordre.
•
Les éléments en italique ou soulignés (valeurs d'options) représentent les valeurs réelles qui doivent être fournies.
•
Les options -storepass, -keypass, -sigfile, -sigalg, -digestalg, -signedjar et les options liées à TSA ne sont pertinentes que lors de la signature d'un fichier JAR ; elles ne sont pas pertinentes lors de la vérification d'un fichier JAR signé. L'option -keystore est pertinente pour la signature et la vérification d'un fichier JAR. De plus, les alias sont spécifiés lors de la signature et de la vérification d'un fichier JAR.
-keystore url
Spécifie l'URL qui indique l'emplacement du magasin de clés. Par défaut, il s'agit du fichier .keystore dans le répertoire personnel de l'utilisateur, tel que déterminé par la propriété système user.home.

Un magasin de clés est requis lors de la signature. Vous devez spécifier explicitement un magasin de clés si le magasin de clés par défaut n'existe pas ou si vous souhaitez en utiliser un autre que le défaut.

Un magasin de clés n'est pas requis lors de la vérification, mais s'il est spécifié ou si le défaut existe et que l'option -verbose a également été spécifiée, des informations supplémentaires sont générées concernant la présence ou non de l'un des certificats utilisés pour vérifier le fichier JAR dans ce magasin de clés.

L'argument -keystore peut être un nom de fichier et une spécification de chemin plutôt qu'une URL, auquel cas il est traité de la même manière qu'une URL de fichier, par exemple, les éléments suivants sont équivalents :

•
-keystore cheminEtNomFichier
•
-keystore file:cheminEtNomFichier

Si le fournisseur Sun PKCS #11 a été configuré dans le fichier de propriétés de sécurité java.security (situé dans le répertoire $JAVA_HOME/conf/security du JDK), alors les outils keytool et jarsigner peuvent fonctionner sur le jeton PKCS #11 en spécifiant ces options :

-keystore NONE -storetype PKCS11

Par exemple, la commande suivante liste le contenu du jeton PKCS#11 configuré :

keytool -keystore NONE -storetype PKCS11 -list

-storepass [:env | :file] argument
Spécifie le mot de passe requis pour accéder au magasin de clés. Ceci n'est nécessaire que lors de la signature (pas de la vérification) d'un fichier JAR. Dans ce cas, si une option -storepass n'est pas fournie sur la ligne de commande, l'utilisateur est invité à entrer le mot de passe.

Si le modificateur env ou file n'est pas spécifié, alors le mot de passe a la valeur argument. Sinon, le mot de passe est récupéré comme suit :

•
env : Récupérer le mot de passe à partir de la variable d'environnement nommée argument.
•
file : Récupérer le mot de passe à partir du fichier nommé argument.

-storetype type de magasin
Spécifie le type de magasin de clés à instancier. Le type de magasin de clés par défaut est celui qui est spécifié comme valeur de la propriété keystore.type dans le fichier de propriétés de sécurité, tel que retourné par la méthode statique getDefaultType dans java.security.KeyStore.

Le PIN d'un jeton PKCS #11 peut également être spécifié avec l'option -storepass. Si aucun n'est spécifié, alors les commandes keytool et jarsigner demandent le PIN du jeton. Si le jeton a un chemin d'authentification protégé (tel qu'un pavé numérique dédié ou un lecteur biométrique), alors l'option -protected doit être spécifiée et aucune option de mot de passe ne peut être spécifiée.

-keypass [:env | :file] argument -certchain fichier
Spécifie le mot de passe utilisé pour protéger la clé privée de l'entrée du magasin de clés adressée par l'alias spécifié sur la ligne de commande. Le mot de passe est requis lors de l'utilisation de jarsigner pour signer un fichier JAR. Si aucun mot de passe n'est fourni sur la ligne de commande, et que le mot de passe requis est différent du mot de passe du magasin, alors l'utilisateur est invité à le fournir.

Si le modificateur env ou file n'est pas spécifié, alors le mot de passe a la valeur argument. Sinon, le mot de passe est récupéré comme suit :

•
env : Récupère le mot de passe de la variable d'environnement nommée argument.
•
file : Récupère le mot de passe du fichier nommé argument.

Remarque :

Le mot de passe ne doit pas être spécifié sur la ligne de commande ou dans un script, sauf à des fins de test, ou si vous êtes sur un système sécurisé.

-certchain fichier
Spécifie la chaîne de certificats à utiliser lorsque la chaîne de certificats associée à la clé privée de l'entrée du magasin de clés adressée par l'alias spécifié sur la ligne de commande n'est pas complète. Cela peut se produire lorsque le magasin de clés est situé sur un jeton matériel qui n'a pas suffisamment de capacité pour contenir une chaîne de certificats complète. Le fichier peut être une séquence de certificats X.509 concaténés, ou un bloc de données unique au format PKCS#7, soit au format d'encodage binaire, soit au format d'encodage imprimable (également appelé encodage Base64) tel que défini par la norme Internet RFC 1421 Certificate Encoding Standard [http://tools.ietf.org/html/rfc1421].
-sigfile fichier
Spécifie le nom de base du fichier à utiliser pour les fichiers .SF et de bloc de signature générés. Par exemple, si le fichier est DUKESIGN, alors les fichiers .SF et de bloc de signature générés sont nommés DUKESIGN.SF et DUKESIGN.RSA, et placés dans le répertoire META-INF du fichier JAR signé.

Les caractères dans le fichier doivent provenir de l'ensemble a-zA-Z0-9_-. Seuls les lettres, les chiffres, les caractères de soulignement et les tirets sont autorisés. Tous les caractères minuscules sont convertis en majuscules pour les noms de fichiers .SF et de bloc de signature.

Si aucune option -sigfile n'apparaît sur la ligne de commande, alors le nom de base du fichier pour les fichiers .SF et de bloc de signature est constitué des 8 premiers caractères du nom d'alias spécifié sur la ligne de commande, tous convertis en majuscules. Si le nom d'alias a moins de 8 caractères, alors le nom d'alias complet est utilisé. Si le nom d'alias contient des caractères qui ne sont pas valides dans un nom de fichier de signature, alors chaque caractère est converti en un caractère de soulignement (_) pour former le nom du fichier.

-signedjar fichier
Spécifie le nom du fichier JAR signé.
-digestalg algorithme
Spécifie le nom de l'algorithme de résumé de message à utiliser lors du résumé des entrées d'un fichier JAR.

Pour une liste des noms d'algorithmes de résumé de message standard, voir Java Security Standard Algorithm Names.

Si cette option n'est pas spécifiée, alors SHA256 est utilisé. Il doit y avoir soit un fournisseur installé statiquement fournissant une implémentation de l'algorithme spécifié, soit l'utilisateur doit en spécifier un avec les options -addprovider ou -providerClass ; sinon, la commande échouera.

-sigalg algorithme
Spécifie le nom de l'algorithme de signature à utiliser pour signer le fichier JAR.

Cet algorithme doit être compatible avec la clé privée utilisée pour signer le fichier JAR. Si cette option n'est pas spécifiée, alors un algorithme par défaut correspondant à la clé privée est utilisé, comme décrit dans la section Supported Algorithms. Il doit y avoir soit un fournisseur installé statiquement fournissant une implémentation de l'algorithme spécifié, soit vous devez en spécifier un avec l'option -addprovider ou -providerClass ; sinon, la commande n'aboutit pas.

Pour une liste des noms d'algorithmes de résumé de message standard, voir Java Security Standard Algorithm Names.

-verify
Vérifie un fichier JAR signé.
-verbose[:sous-options]
Lorsque l'option -verbose apparaît sur la ligne de commande, elle indique que jarsigner utilise le mode verbeux lors de la signature ou de la vérification, les sous-options déterminant la quantité d'informations affichée. Cela provoque, ce qui fait que jarsigner affiche des informations supplémentaires sur la progression de la signature ou de la vérification du JAR. Les sous-options peuvent être all, grouped, ou summary.

Si l'option -certs est également spécifiée, alors le mode par défaut (ou la sous-option all) affiche chaque entrée au fur et à mesure de son traitement, puis les informations de certificat de chaque signataire du fichier JAR.

Si les sous-options -certs et -verbose:grouped sont spécifiées, alors les entrées ayant les mêmes informations de signataire sont regroupées et affichées ensemble avec leurs informations de certificat.

Si les sous-options -certs et -verbose:summary sont spécifiées, alors les entrées ayant les mêmes informations de signataire sont regroupées et affichées ensemble avec leurs informations de certificat.

Les détails de chaque entrée sont résumés et affichés comme une entrée (et plus). Voir Exemple de vérification d'un fichier JAR signé et Exemple de vérification avec informations de certificat.

-certs
Si l'option -certs apparaît sur la ligne de commande avec les options -verify et -verbose, alors la sortie inclut les informations de certificat pour chaque signataire du fichier JAR. Ces informations incluent le nom du type de certificat (stocké dans le fichier de bloc de signature) qui certifie la clé publique du signataire, et si le certificat est un certificat X.509 (une instance de java.security.cert.X509Certificate), alors le nom distinctif du signataire.

Le magasin de clés est également examiné. Si aucune valeur de magasin de clés n'est spécifiée sur la ligne de commande, alors le fichier de magasin de clés par défaut (le cas échéant) est vérifié. Si le certificat de clé publique d'un signataire correspond à une entrée dans le magasin de clés, alors le nom d'alias de l'entrée du magasin de clés pour ce signataire est affiché entre parenthèses.

-revCheck
Cette option active la vérification de révocation des certificats lors de la signature ou de la vérification d'un fichier JAR. La commande jarsigner tente d'établir des connexions réseau pour récupérer les réponses OCSP et les listes CRL si l'option -revCheck est spécifiée sur la ligne de commande. Notez que les vérifications de révocation ne sont pas activées à moins que cette option ne soit spécifiée.
-tsa url
Si -tsa http://example.tsa.url apparaît sur la ligne de commande lors de la signature d'un fichier JAR, alors un horodatage est généré pour la signature. L'URL, http://example.tsa.url, identifie l'emplacement de l'Autorité d'Horodatage (TSA) et remplace toute URL trouvée avec l'option -tsacert. L'option -tsa ne nécessite pas que le certificat de clé publique de la TSA soit présent dans le magasin de clés.

Pour générer l'horodatage, jarsigner communique avec la TSA en utilisant le protocole Time-Stam

p Protocole (TSP) défini dans la RFC 3161. En cas de succès, le jeton d'horodatage retourné par la TSA est stocké avec la signature dans le fichier du bloc de signature.

-tsacert alias
Lorsque -tsacert alias apparaît sur la ligne de commande lors de la signature d'un fichier JAR, un horodatage est généré pour la signature. L'alias identifie le certificat de clé publique de la TSA dans le keystore qui est actif. Le certificat de l'entrée est examiné pour une extension d'accès aux informations du sujet (Subject Information Access) qui contient une URL identifiant l'emplacement de la TSA.

Le certificat de clé publique de la TSA doit être présent dans le keystore lors de l'utilisation de l'option -tsacert.

-tsapolicyid policyid
Spécifie l'identificateur d'objet (OID) qui identifie l'ID de politique à envoyer au serveur TSA. Si cette option n'est pas spécifiée, aucun ID de politique n'est envoyé et le serveur TSA choisira un ID de politique par défaut.

Les identificateurs d'objet sont définis par X.696, qui est une norme de l'UIT-T (Union Internationale des Télécommunications - Secteur de la Normalisation des Télécommunications). Ces identificateurs sont généralement des ensembles de chiffres non négatifs séparés par des points, tels que 1.2.3.4, par exemple.

-tsadigestalg algorithm
Spécifie l'algorithme de résumé de message utilisé pour générer l'empreinte du message à envoyer au serveur TSA. Si cette option n'est pas spécifiée, SHA-256 sera utilisé.

Voir Supported Algorithms.

Pour une liste des noms d'algorithmes de résumé de message standard, voir Java Security Standard Algorithm Names.

-internalsf
Dans le passé, le fichier de bloc de signature généré lors de la signature d'un fichier JAR incluait une copie encodée complète du fichier .SF (fichier de signature) également généré. Ce comportement a été modifié. Pour réduire la taille globale du fichier JAR de sortie, le fichier de bloc de signature ne contient plus par défaut une copie du fichier .SF. Si -internalsf apparaît sur la ligne de commande, alors l'ancien comportement est utilisé. Cette option est utile pour les tests. En pratique, n'utilisez pas l'option -internalsf car elle entraîne une surcharge plus importante.
-sectionsonly
Si l'option -sectionsonly apparaît sur la ligne de commande, alors le fichier .SF (fichier de signature) généré lors de la signature d'un fichier JAR n'inclut pas d'en-tête contenant un hachage de l'ensemble du fichier manifeste. Il contient uniquement les informations et les hachages relatifs à chaque fichier source individuel inclus dans le fichier JAR. Voir Signature File.

Par défaut, cet en-tête est ajouté, par optimisation. Lorsque l'en-tête est présent, chaque fois que le fichier JAR est vérifié, la vérification peut d'abord vérifier si le hachage dans l'en-tête correspond au hachage de l'ensemble du fichier manifeste. En cas de correspondance, la vérification passe à l'étape suivante. En l'absence de correspondance, il est nécessaire d'effectuer une vérification moins optimisée pour s'assurer que le hachage dans chaque section d'informations de fichier source du fichier .SF est égal au hachage de sa section correspondante dans le fichier manifeste. Voir JAR File Verification.

L'option -sectionsonly est principalement utilisée pour les tests. Elle ne doit pas être utilisée en dehors des tests, car son utilisation entraîne une surcharge plus importante.

-protected
Les valeurs peuvent être true ou false. Spécifiez true lorsqu'un mot de passe doit être spécifié via un chemin d'authentification protégé tel qu'un lecteur de carte à puce dédié.
-providerName providerName
Si plusieurs fournisseurs ont été configurés dans le fichier de propriétés de sécurité java.security, vous pouvez utiliser l'option -providerName pour cibler une instance de fournisseur spécifique. L'argument de cette option est le nom du fournisseur.

Pour le fournisseur Oracle PKCS #11, providerName est de la forme SunPKCS11-NomDuToken, où NomDuToken est le suffixe de nom avec lequel l'instance du fournisseur a été configurée, comme détaillé dans le tableau des attributs de configuration. Par exemple, la commande suivante liste le contenu de l'instance du fournisseur de keystore PKCS #11 avec le suffixe de nom SmartCard :

jarsigner -keystore NONE -storetype PKCS11 -providerName SunPKCS11-SmartCard -list

-addprovider name [-providerArg arg]
Ajoute un fournisseur de sécurité par nom (tel que SunPKCS11) et un argument de configuration facultatif. La valeur du fournisseur de sécurité est le nom d'un fournisseur de sécurité défini dans un module.

Utilisé avec l'option -providerArg ConfigFilePath, les outils keytool et jarsigner installent le fournisseur dynamiquement et utilisent ConfigFilePath pour le chemin d'accès au fichier de configuration du jeton. L'exemple suivant montre une commande pour lister un keystore PKCS #11 lorsque le fournisseur Oracle PKCS #11 n'a pas été configuré dans le fichier de propriétés de sécurité.

jarsigner -keystore NONE -storetype PKCS11 -addprovider SunPKCS11 -providerArg /mydir1/mydir2/token.config

-providerClass provider-class-name [-providerArg arg]
Utilisé pour spécifier le nom du fichier maître de classe du fournisseur de services cryptographiques lorsque le fournisseur de services n'est pas répertorié dans le fichier de propriétés de sécurité java.security. Ajoute un fournisseur de sécurité par nom de classe entièrement qualifié et un argument de configuration facultatif.

Note :

La méthode préférée pour charger PKCS11 est d'utiliser des modules. Voir -addprovider.

-Jjavaoption
Passe la chaîne javaoption spécifiée directement à l'interpréteur Java. La commande jarsigner est un wrapper autour de l'interpréteur. Cette option ne doit pas contenir d'espaces. Elle est utile pour ajuster l'environnement d'exécution ou l'utilisation de la mémoire. Pour une liste des options d'interpréteur possibles, tapez java -h ou java -X à la ligne de commande.
-strict
Pendant le processus de signature ou de vérification, la commande peut émettre des messages d'avertissement. Si vous spécifiez cette option, le code de sortie de l'outil reflète les avertissements sévères que cette commande a trouvés. Voir Errors and Warnings.
-conf url
Spécifie un fichier d'options préconfiguré. Lisez la documentation de keytool pour plus de détails. Les clés de propriété prises en charge sont "jarsigner.all" pour toutes les actions, "jarsigner.sign" pour la signature et "jarsigner.verify" pour la vérification. Les arguments de jarsigner, y compris le nom du fichier JAR et les noms d'alias, ne peuvent pas être définis dans ce fichier.

Pendant le processus de signature ou de vérification, la commande jarsigner peut émettre diverses erreurs ou

avertissements.

En cas d'échec, la commande jarsigner se termine avec le code 1. 0.

spécifiée.

jarsigner

        
jarsigner - signer et vérifier les fichiers JAR

    






    
NAME

    
jarsigner - signer et vérifier les fichiers JAR






    
SYNOPSIS

    
jarsigner [options] jar-file alias

        jarsigner [options] -verify jar-file [alias...]






    
DESCRIPTION

    
L'utilitaire jarsigner permet de signer numériquement des fichiers JAR avec
      une clé privée et un certificat, puis de vérifier les signatures des fichiers JAR signés.
      Il peut également afficher les informations de l'élément d'un fichier JAR,
      telles que les certificats et les listes de fichiers signés.

    
Dans la première forme de la commande, la signature est ajoutée au fichier JAR spécifié par
      jar-file, en utilisant la clé privée et le certificat associés à l'alias alias
      dans un keystore. Par défaut, le keystore est le fichier nommé ".keystore"
      dans le répertoire personnel de l'utilisateur.

    
Dans la deuxième forme, les signatures du fichier JAR spécifié par jar-file sont vérifiées.
      Si un ou plusieurs alias sont spécifiés, seuls les fichiers correspondant à ces alias
      seront vérifiés. Si aucun alias n'est spécifié, tous les fichiers signés dans le JAR seront vérifiés.






    
KEYSTORE ALIASES

    
Un alias est un nom qui pointe vers une paire clé privée/certificat dans un keystore.
      Le keystore peut contenir plusieurs paires clé privée/certificat, chacune identifiée par un alias unique.






    
KEYSTORE LOCATION

    
L'emplacement du keystore est déterminé comme suit :

    
    
        
  • L'option -keystore spécifie l'emplacement du fichier keystore.
    • 
        
  • Si l'option -keystore n'est pas utilisée, le keystore par défaut est le fichier ".keystore"
          dans le répertoire personnel de l'utilisateur.
    • 
    






    
KEYSTORE IMPLEMENTATION

    
Par défaut, jarsigner utilise l'implémentation de keystore par défaut du fournisseur
      Java, qui est généralement le format "JKS". D'autres implémentations peuvent être spécifiées
      en utilisant l'option -storetype.






    
SUPPORTED ALGORITHMS

    
jarsigner prend en charge les algorithmes de signature suivants :

    
    
        
  • SHA-1 avec RSA
    • 
        
  • SHA-256 avec RSA
    • 
        
  • SHA-512 avec RSA
    • 
    

    
Les algorithmes de hachage pris en charge sont SHA-1 et SHA-256.






    
THE SIGNED JAR FILE

    
Lorsqu'un fichier JAR est signé, deux nouveaux fichiers sont ajoutés au répertoire META-INF :
      un fichier de signature et un fichier de bloc de signature.






    
SIGNATURE FILE

    
Le fichier de signature porte le nom de l'alias utilisé pour la signature, suivi de l'extension ".SF".
      Il contient un manifeste signé. Par exemple, si l'alias est "monalias", le fichier de signature
      sera "monalias.SF".






    
SIGNATURE BLOCK FILE

    
Le fichier de bloc de signature contient les informations de signature réelles, telles que le certificat
      du signataire et la signature numérique du fichier de manifeste. Il porte le nom de l'alias utilisé
      pour la signature, suivi d'une extension telle que ".DSA", ".RSA" ou ".EC", en fonction de l'algorithme de clé utilisé.
      Par exemple, si l'alias est "monalias" et que l'algorithme de clé est RSA, le fichier de bloc de signature
      sera "monalias.RSA".






    
SIGNATURE TIME STAMP

    
Il est possible de faire sceller la signature par une autorité de timestamping tierce.
      Cela permet de vérifier que le fichier JAR était signé avant l'expiration du certificat du signataire,
      même si le certificat a expiré depuis.






    
JAR FILE VERIFICATION

    
Lorsqu'un fichier JAR est vérifié, jarsigner examine les fichiers de signature et de bloc de signature
      pour s'assurer que le contenu du JAR n'a pas été modifié depuis sa signature.
      Il vérifie également la validité du certificat du signataire et de l'éventuelle chaîne de confiance.






    
MULTIPLE SIGNATURES FOR A JAR FILE

    
Un fichier JAR peut être signé plusieurs fois, avec différents alias.
      Dans ce cas, le répertoire META-INF contiendra plusieurs fichiers de signature et de bloc de signature.






    
OPTIONS FOR JARSIGNER

    
Les options suivantes sont disponibles pour jarsigner :

    
    
        
  • -keystore keystore : Spécifie le chemin d'accès au fichier keystore.
    • 
        
  • -storetype type : Spécifie le type de keystore (par exemple, JKS, PKCS12).
    • 
        
  • -storepass password : Spécifie le mot de passe du keystore.
    • 
        
  • -keypass password : Spécifie le mot de passe de la clé privée.
    • 
        
  • -certchain : Inclut la chaîne complète des certificats du signataire.
    • 
        
  • -tsa url : Spécifie l'URL du serveur de timestamping.
    • 
        
  • -tsacert certificat : Spécifie le certificat du serveur de timestamping.
    • 
        
  • -signedjar nom-fichier : Spécifie le nom du fichier JAR signé de sortie.
    • 
        
  • -verify : Vérifie les signatures du fichier JAR.
    • 
        
  • -verbose : Affiche des informations détaillées pendant la signature ou la vérification.
    • 
        
  • -internalsf : Inclut le fichier de signature dans le fichier JAR signé.
    • 
        
  • -sectionsonly : Ne signe que les sections spécifiées dans le manifeste.
    • 
        
  • -digestalg algorithme : Spécifie l'algorithme de hachage à utiliser pour le manifeste.
    • 
        
  • -sigalg algorithme : Spécifie l'algorithme de signature à utiliser.
    • 
    






    
DEPRECATED OPTIONS

    
Les options suivantes sont obsolètes et ne doivent plus être utilisées :

    
    
        
  • -})}{ : (obsolète) Spécifie le mot de passe du keystore. Utilisez -storepass à la place.
    • 
    






    
ERRORS AND WARNINGS

    
jarsigner peut générer différents types d'erreurs et d'avertissements, notamment :






    
FAILURE

    
Ces messages indiquent un échec de la signature ou de la vérification du fichier JAR.

    
    
        
  • jarsigner : le keystore n'existe pas : Le fichier keystore spécifié n'a pas été trouvé.
    • 
        
  • jarsigner : mot de passe de keystore incorrect : Le mot de passe fourni pour le keystore est incorrect.
    • 
        
  • jarsigner : alias introuvable : L'alias spécifié n'existe pas dans le keystore.
    • 
        
  • jarsigner : la signature est invalide : La signature du fichier JAR est invalide. Le fichier a peut-être été modifié depuis sa signature.
    • 
        
  • jarsigner : le certificat du signataire a expiré : Le certificat du signataire a expiré.
    • 
    






    
SEVERE WARNINGS

    
Ces avertissements indiquent des problèmes potentiels qui pourraient affecter la sécurité.

    
    
        
  • Le fichier JAR sera plus tard valide jusqu'à l'expiration du timestamp : Le certificat du signataire a expiré, mais le timestamp est valide. Le JAR est considéré comme valide jusqu'à l'expiration du timestamp.
    • 
    






    
INFORMATIONAL WARNINGS

    
Ces avertissements fournissent des informations utiles mais n'affectent pas nécessairement la validité du JAR.

    
    
        
  • La signature a été vérifiée : La signature du fichier JAR a été vérifiée avec succès.
    • 
        
  • L'entrée est répertoriée dans le manifeste : L'entrée du fichier JAR est répertoriée dans le manifeste.
    • 
        
  • Au moins un certificat a été trouvé dans le keystore : Au moins un certificat a été trouvé dans le keystore.
    • 
    






    
EXAMPLE OF SIGNING A JAR FILE

    
Pour signer un fichier JAR nommé myapp.jar avec l'alias monalias et le mot de passe du keystore mypass :

    
jarsigner -keystore mykeystore -storepass mypass myapp.jar monalias






    
EXAMPLE OF VERIFYING A SIGNED JAR FILE

    
Pour vérifier toutes les signatures du fichier JAR myapp.jar avec le mot de passe du keystore mypass :

    
jarsigner -verify -keystore mykeystore -storepass mypass myapp.jar






    
EXAMPLE OF VERIFICATION WITH CERTIFICATE INFORMATION

    
Pour vérifier le fichier JAR myapp.jar et afficher des informations détaillées sur les certificats, utilisez l'option -verbose :

    
jarsigner -verify -verbose -keystore mykeystore -storepass mypass myapp.jar
