DESCRIPTIO

N

Le débogueur Java (JDB) est un débogueur simple en ligne de commande pour les classes Java. La commande jdb et ses options appellent le JDB. La commande jdb démontre l'architecture de débogage de la plateforme Jav

a et permet l'inspection et le déboga
ge d'une JVM locale ou distante.

DÉMARRAGE D'UNE SESSION

JDB

Il existe de nombreuses façons de démarrer une session JDB. La méthode la plus fréquemment utilisée est de faire en sorte que le JDB lance une nouvelle JVM avec la classe principale de l'application à déboguer. Faites-le en remplaçant la commande jdb par la commande java dans la ligne de commande. Par exemple, si la classe principale de votre application est MyClass, utilisez alors la commande suivante pour la déboguer sous le JDB

:

jdb

MyC
lass

Lorsqu'elle est démarrée de cette manière, la commande jdb appelle une seconde JVM avec les paramètres spécifiés, charge la classe spécifiée et arrête la JVM avant d'exécuter la première instruction de cette

classe.

Une autre façon d'utiliser la commande jdb est de l'attacher à une JVM déjà en cours d'exécution. La syntaxe pour démarrer une JVM à laquelle la commande jdb s'attache lorsque la JVM est en cours d'exécution est la suivante. Cela charge les bibliothèques de débogage dans le processus et spécifie le type de connexion à

établir.

java -agentlib:jdwp

=transport=dt_socket,ser
ver=y,suspend=n MyClass

Vous pouvez ensuite attacher la commande jdb à la JVM avec la commande suivante

jdb -

8000 est l'adresse de la JVM en cours

d'exécution.

L'argument MyClass n'est pas spécifié dans la ligne de commande jdb dans ce cas parce que la commande jdb se connecte à une JVM existante au lieu de lancer une nouvelle

JVM.

Il existe de nombreuses autres façons de connecter le débogueur à une JVM, et toutes sont prises en charge par la commande jdb. L'architecture de débogage de la plateforme Java pos

sède une documentation supplémentair

EXCEPTION

S

Lorsqu'une exception se produit pour laquelle il n'y a pas de instruction catch nulle part dans la pile d'appels du thread qui la lance, la JVM imprime généralement une trace d'exception et se termine. Lors de l'exécution sous le JDB, cependant, le contrôle revient au JDB au moment du throw fautif. Vous pouvez alors utiliser la commande jdb pour diagnostiquer la cause de

l'exception.

Utilisez la commande catch pour faire en sorte que l'application déboguée s'arrête à d'autres exceptions lancées, par exemple : catch java.io.FileNotFoundException ou catch mypackage.BigTroubleException. Toute exception qui est une instance de la classe spécifiée ou d'une sous-classe arrête l'application au point où l'exception est

lancée.

La commande ignore annule l'effet d'une commande catch précédente. La commande ignore ne fait pas ignorer des exceptions spécifiqu

es par la JVM déboguée, mais s
eulement ignorer le débogueur.

UTILISATION DES THREADS VIRTUELS

Souvent, les threads virtuels sont créés en si grand nombre et si fréquemment qu'ils peuvent submerger un débogueur. Pour cette raison, par défaut, JDB ne suit pas les threads virtuels lorsqu'ils sont créés. Il ne suivra que les threads virtuels sur lesquels un événement est arrivé, tel qu'un événement de point d'arrêt. L'option -trackallthreads peut être utilisée pour que JDB suive tous les threads virtuels lorsqu'ils sont créés.

Lorsque JDB se connecte pour la première fois, il demande une liste de tous les threads connus à l'agent de débogage. Par défaut, l'agent de débogage ne renvoie aucun thread virtuel dans cette liste, encore une fois parce que la liste pourrait être si volumineuse qu'elle submerge le débogueur. L'agent de débogage dispose d'une option includevirtualthreads qui peut être activée pour modifier ce comportement afin que tous les threads virtuels connus soient inclus dans la liste. L'option JDB -trackallthreads amènera JDB à activer automatiquement l'option includevirtualthreads de l'agent de débogage lorsque JDB lance une application à déboguer. Cependant, gardez à l'esprit que l'agent de débogage peut ne pas connaître tous les threads virtuels qui ont été créés avant que JDB ne se connecte à l'application déboguée.
