fallthrough
Vérifie les blocs switch pour les cas de "fall-through" et affiche un message d'avertissement pour ceux qui sont trouvés. Les cas de "fall-through" sont des cas dans un bloc switch, autres que le dernier cas du bloc, dont le code ne contient pas d'instruction break, permettant à l'exécution du code de passer du cas actuel au cas suivant. Par exemple, le code suivant l'étiquette case 1 dans ce bloc switch ne se termine pas par une instruction break : 
switch (x) {
case 1:
  System.out.println("1");
  // Pas d'instruction break ici.
case 2:
  System.out.println("2");
}

Si l'option -Xlint:fallthrough a été utilisée lors de la compilation de ce code, le compilateur émet un avertissement concernant un possible "fall-through" dans le cas, avec le numéro de ligne du cas en question.

finally
Avertit des clauses finally qui ne peuvent pas se terminer normalement, par exemple : 
public static int m() {
  try {
     throw new NullPointerException();
  }  catch (NullPointerException(); {
     System.err.println("Caught NullPointerException.");
     return 1;
   } finally {
     return 0;
   }
  }

Le compilateur génère un avertissement pour le bloc finally dans cet exemple. Lorsque la méthode int est appelée, elle renvoie une valeur de 0. Un bloc finally s'exécute lorsque le bloc try se termine. Dans cet exemple, lorsque le contrôle est transféré au bloc catch, la méthode int se termine. Cependant, le bloc finally doit s'exécuter, il est donc exécuté, même si le contrôle a été transféré hors de la méthode.

COMMANDE

Pour raccourcir ou simplifier la commande javac, vous pouvez spécifier un ou plusieurs fichiers contenant des arguments pour la commande javac (sauf les options -J). Cela vous permet de créer des commandes javac de n'importe quelle longueur sur n'importe quel système

d'exploitation.

Un fichier d'arguments peut inclure des options javac et des noms de fichiers source dans n'importe quelle combinaison. Les arguments dans un fichier peuvent être séparés par des espaces ou des caractères de nouvelle ligne. Si un nom de fichier contient des espaces, mettez le nom de fichier entier entre guillemets

doubles.

Les noms de fichiers dans un fichier d'arguments sont relatifs au répertoire courant, et non à l'emplacement du fichier d'arguments. Les caractères génériques (*) ne sont pas autorisés dans ces listes (par exemple pour spécifier *.java). L'utilisation du signe at (@) pour interpréter récursivement les fichiers n'est pas prise en charge. Les options -J ne sont pas prises en charge car elles sont transmises au lanceur, qui ne prend pas en charge les fichiers

d'arguments.

Lors de l'exécution de la commande javac, transmettez le chemin et le nom de chaque fichier d'arguments avec le signe at (@) en caractère initial. Lorsque la commande javac rencontre un argument commençant par le signe atn (@), il développe le contenu de ce fichier dans la liste

d'arguments.

TRAITEMENT DES

ANNOTATIONS

La commande javac fournit une prise en charge directe du traitement des annotations, remplaçant la nécessité de la commande distincte de traitement des annotations, apt

.

L'API pour les processeurs d'annotations est définie dans les paquets javax.annotation.processing et javax.lang.model et leurs

sous-paquets.

FONCTIONNEMENT DU TRAITEMENT DES

ANNOTATIONS

À moins que le traitement des annotations ne soit désactivé avec l'option -proc:none, le compilateur recherche tout processeur d'annotations disponible. Le chemin de recherche peut être spécifié avec l'option -processorpath. Si aucun chemin n'est spécifié, le chemin de classe de l'utilisateur est utilisé. Les processeurs sont localisés au moyen de fichiers de configuration de fournisseur de service nommés META-INF/services/javax.annotation.processing.Processor sur le chemin de recherche. Ces fichiers doivent contenir les noms de tout processeur d'annotations à utiliser, un par ligne. Alternativement, les processeurs peuvent être spécifiés explicitement, en utilisant l'option -processor

.

Après avoir analysé les fichiers source et les classes sur la ligne de commande pour déterminer quelles annotations sont présentes, le compilateur interroge les processeurs pour déterminer quelles annotations ils traitent. Lorsqu'une correspondance est trouvée, le processeur est appelé. Un processeur peut revendiquer les annotations qu'il traite, auquel cas aucune tentative supplémentaire n'est faite pour trouver des processeurs pour ces annotations. Une fois que toutes les annotations sont revendiquées, le compilateur ne recherche pas de processeurs supplémentaires

.

Si des processeurs génèrent de nouveaux fichiers source, un autre tour de traitement des annotations a lieu : Tout nouveau fichier source généré est analysé, et les annotations sont traitées comme avant. Tout processeur appelé lors des tours précédents est également appelé lors de tous les tours suivants. Cela continue jusqu'à ce que plus aucun nouveau fichier source ne soit

généré.

Après un tour où aucun nouveau fichier source n'est généré, les processeurs d'annotations sont appelés une dernière fois, pour leur donner l'occasion de terminer tout travail restant. Enfin, à moins que l'option -proc:only ne soit utilisée, le compilateur compile les f

ichiers source originaux et tou
s les fichiers source générés.

RECHERCHE DE

TYPES

Pour compiler un fichier source, le compilateur a souvent besoin d'informations sur un type, mais la définition du type n'est pas dans les fichiers source spécifiés sur la ligne de commande. Le compilateur a besoin d'informations sur le type pour chaque classe ou interface utilisée, étendue ou implémentée dans le fichier source. Cela inclut les classes et interfaces non explicitement mentionnées dans le fichier source, mais qui fournissent des informations par

héritage.

Par exemple, lorsque vous créez une sous-classe de java.applet.Applet, vous utilisez également les classes ancêtres de Applet : java.awt.Panel, java.awt.Container, java.awt.Component, et java.lang.O

bject.

Lorsque le compilateur a besoin d'informations sur le type, il recherche un fichier source ou un fichier classe qui définit le type. Le compilateur recherche d'abord les fichiers classe dans les classes d'amorçage et d'extension, puis dans le chemin de classe de l'utilisateur (qui par défaut est le répertoire courant). Le chemin de classe de l'utilisateur est défini en définissant la variable d'environnement CLASSPATH ou en utilisant l'option -classpath

.

Si vous définissez l'option -sourcepath, le compilateur recherche les fichiers source dans le chemin indiqué. Sinon, le compilateur recherche dans le chemin de classe de l'utilisateur à la fois les fichiers classe et les fichiers

source.

Vous pouvez spécifier des classes d'amorçage ou d'extension différentes avec les -bootclasspath et -extdirs. Voir Options de compilation

croisée.

Une recherche de type réussie peut produire un fichier classe, un fichier source, ou les deux. Si les deux sont trouvés, vous pouvez utiliser l'option -Xprefer pour indiquer au compilateur lequel utiliser. Si newer est spécifié, le compilateur utilise le plus récent des deux fichiers. Si source est spécifié, le compilateur utilise le fichier source. La valeur par défaut est newer

.

Si une recherche de type trouve un fichier source pour un type requis, soit par lui-même, soit en raison du paramètre de l'option -Xprefer, le compilateur lit le fichier source pour obtenir les informations dont il a besoin. Par défaut, le compilateur compile également le fichier source. Vous pouvez utiliser l'option -implicit pour spécifier le comportement. Si none est spécifié, aucun fichier classe n'est généré pour le fichier source. Si class est spécifié, des fichiers classe sont générés pour le fichier

source.

Le compilateur pourrait ne pas découvrir le besoin de certaines informations sur le type avant la fin du traitement des annotations. Lorsque les informations sur le type sont trouvées dans un fichier source et qu'aucune option -implicit n'est spécifiée, le compilateur émet un avertissement indiquant que le fichier est compilé sans être soumis au traitement des annotations. Pour désactiver l'avertissement, spécifiez soit le fichier sur la ligne de commande (de sorte qu'il sera soumis au traitement des annotations), soit utilisez l'option -implicit pour spécifier si des fichiers classe d

de tels fichiers source.
