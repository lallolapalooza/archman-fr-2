RÉPERTOIRES DE CONFIGURATION ET PRÉCÉDENCELa configuration par défaut est définie lors de la compilation ; une configuration n'est donc nécessaire que lorsqu'il faut s'écarter de ces valeurs par défaut. Le fichier de configuration principal est chargé depuis l'un des répertoires listés par ordre de priorité ; seul le premier fichier trouvé est utilisé : /etc/systemd/, /run/systemd/, /usr/local/lib/systemd/ [1], /usr/lib/systemd/. La version du fichier fournie par le fournisseur contient des entrées commentées montrant les valeurs par défaut, à titre de guide pour l'administrateur. Des surcharges locales peuvent également être créées en créant des drop-ins, comme décrit ci-dessous. Le fichier de configuration principal peut également être modifié à cette fin (ou une copie dans /etc/ s'il est fourni sous /usr/), cependant il est recommandé d'utiliser des drop-ins pour la configuration
locale plutôt que de modifier
le fichier de configuration principal.

En plus du fichier de configuration principal, des extraits de configuration drop-in sont lus depuis /usr/lib/systemd/*.conf.d/, /usr/local/lib/systemd/*.conf.d/ et /etc/systemd/*.conf.d/. Ces drop-ins ont une priorité plus élevée et remplacent le fichier de configuration principal. Les fichiers dans les sous-répertoires de configuration *.conf.d/ sont triés par leur nom de fichier dans l'ordre lexicographique, quel que soit le sous-répertoire dans lequel ils se trouvent. Lorsque plusieurs fichiers spécifient la même option, pour les options qui n'acceptent qu'une seule valeur, l'entrée du fichier trié en dernier prend la priorité, et pour les options qui acceptent une liste de valeurs, les entrées sont collectées

au fur et à mesure qu'elles apparaissent dans les fichiers triés.

Lorsque les paquets doivent personnaliser la configuration, ils peuvent installer des drop-ins sous /usr/. Les fichiers dans /etc/ sont réservés à l'administrateur local, qui peut utiliser cette logique pour remplacer les fichiers de configuration installés par les paquets du fournisseur. Des drop-ins doivent être utilisés pour remplacer les drop-ins des paquets, car le fichier de configuration principal a une priorité plus faible. Il est recommandé de préfixer tous les noms de fichiers dans ces sous-répertoires avec un numéro à deux chiffres et un tiret, afin de simplifier le tri. Cela définit également un concept de priorité des drop-ins pour permettre aux fournisseurs de systèmes d'exploitation de fournir des drop-ins dans une plage spécifique inférieure à celle utilisée par les utilisateurs. Cela devrait réduire le risque que les drop-ins des paquets remplacent accidentellement les drop-ins définis par les utilisateurs. Il est recommandé d'utiliser la plage 10-40 pour les drop-ins dans /usr/ et la plage 60-90 pour les drop-ins dans /etc/ et /run/, afin de s'assurer que les drop-ins locaux et transitoires ont la priorité sur les drop-ins fournis par le fournisseur du système d'exploitation. Pour désactiver un fichier de configuration fourni par le fournisseur, la méthode recommandée consiste à placer un lien symbolique vers /dev/null dans le répertoire de configuration dans /etc/, avec le même nom de fichier que le fichier de configuration du fournisseur. Toutes les options sont configurées dans la section [Journal] : Storage=Contrôle où stocker les données du journal. L'une des valeurs "volatile", "persistent", "auto" et "none". Si "volatile", les données du journal seront stockées uniquement en mémoire, c'est-à-dire sous la hiérarchie /run/log/journal (qui est créée si nécessaire). Si "persistent", les données seront stockées de préférence sur disque, c'est-à-dire sous la hiérarchie /var/log/journal (qui est créée si nécessaire), avec un repli sur /run/log/journal (qui est créée si nécessaire), lors du démarrage précoce et si le disque n'est pas inscriptible. SplitMode

=
Contrôle si les fichiers de journal doivent être divisés par utilisateur, soit "uid" soit "none". Les fichiers de journal divisés sont principalement utiles pour le contrôle d'accès : sur UNIX/Linux, le contrôle d'accès est géré par fichier, et le démon du journal accordera aux utilisateurs un accès en lecture à leurs fichiers de journal. Si "uid", tous les utilisateurs réguliers (avec un UID en dehors de la plage des utilisateurs système, des utilisateurs de service dynamiques et de l'utilisateur nobody) auront chacun leurs propres fichiers de journal, et les utilisateurs système journaliseront dans le journal système. Voir Utilisateurs, groupes, UID et GID sur les systèmes systemd[3] pour plus de détails sur les plages d'UID. Si la valeur est "none", les fichiers de journal ne sont pas répartis par utilisateur et tous les messages sont à la place stockés dans le journal système unique. Dans ce mode, les utilisateurs non privilégiés n'ont généralement pas accès à leurs propres données de journal. Notez que la répartition des fichiers de journal par utilisateur n'est disponible que pour les journaux stockés de manière persistante. Si les journaux sont stockés sur un stockage volatile (voir Storage= ci-dessus), un seul fichier de journal est utilisé. La valeur par défaut est "uid".

RateLimitIntervalSec=, RateLimitBurst=

Configure la limitation de débit appliquée à tous les messages générés sur le système. Si, dans l'intervalle de temps défini par RateLimitIntervalSec=, plus de messages que spécifié dans RateLimitBurst= sont journalisés par un service, tous les messages supplémentaires de l'intervalle sont abandonnés jusqu'à la fin de l'intervalle. Un message indiquant le nombre de messages abandonnés est généré. Cette limitation de débit est appliquée par service, de sorte que deux services qui journalisent n'interfèrent pas avec les limites de l'autre. La valeur par défaut est de 10000 messages en 30s. La spécification de temps pour RateLimitIntervalSec= peut être spécifiée dans les unités suivantes : "s", "min", "h", "ms", "us". Pour désactiver toute limitation de débit, définissez l'une des valeurs à 0.

Notez que la limite de débit effective est multipliée par un facteur dérivé de l'espace disque libre disponible pour le journal. Actuellement, ce facteur est calculé à l'aide du logarithme en base 2.

SystemMaxUse=, SystemKeepFree=, SystemMaxFileSize=, SystemMaxFiles=, RuntimeMaxUse=, RuntimeKeepFree=, RuntimeMaxFileSize=, RuntimeMaxFiles=

Fait respecter des limites de taille sur les fichiers de journal stockés. Les options préfixées par "System" s'appliquent aux fichiers de journal lorsqu'ils sont stockés sur un système de fichiers persistant, plus précisément /var/log/journal. Les options préfixées par "Runtime" s'appliquent aux fichiers de journal lorsqu'ils sont stockés sur un système de fichiers volatile en mémoire, plus précisément /run/log/journal. Les premières ne sont utilisées que lorsque /var/ est monté, accessible en écriture, et que le répertoire /var/log/journal existe. Sinon, seules les secondes s'appliquent. Notez que cela signifie que pendant le démarrage précoce et si l'administrateur a désactivé la journalisation persistante, seules les options "Runtime" s'appliquent, tandis que les options "System" s'appliquent si la journalisation persistante est activée et que le système est complètement démarré. journalctl et systemd-journald ignorent tous les fichiers dont les noms ne se terminent pas par ".journal" ou ".journal~", de sorte que seuls de tels fichiers, situés dans les répertoires appropriés, sont pris en compte lors du calcul de l'utilisation actuelle du disque.

SystemMaxUse= et RuntimeMaxUse= contrôlent la quantité d'espace disque que le journal peut utiliser au maximum. SystemKeepFree= et RuntimeKeepFree= contrôlent la quantité d'espace disque que systemd-journald doit laisser libre pour d'autres utilisations. systemd-journald respectera les deux limites et utilisera la plus petite des deux valeurs.

La première paire a pour valeur par défaut 10% et la seconde 15% de la taille du système de fichiers respectif, mais chacune des valeurs par défaut calculées est plafonnée à 4G. Si le système de fichiers est presque plein et que soit SystemKeepFree= soit RuntimeKeepFree= est violé lorsque systemd-journald est démarré, la limite sera augmentée au pourcentage effectivement libre. Cela signifie que s'il y avait suffisamment d'espace libre avant et que des fichiers de journal ont été créés, et que quelque chose d'autre fait ensuite que le système de fichiers se remplit, journald cessera d'utiliser plus d'espace, mais il ne supprimera pas non plus les fichiers existants pour réduire à nouveau l'empreinte. Notez également que seuls les fichiers archivés sont supprimés pour réduire l'espace occupé par les fichiers de journal. Cela signifie qu'en fait, il peut encore y avoir plus d'espace utilisé que la limite SystemMaxUse= ou RuntimeMaxUse= après qu'une opération de nettoyage soit terminée.

SystemMaxFileSize= et RuntimeMaxFileSize= contrôlent la taille maximale à laquelle les fichiers de journal individuels peuvent croître. Cela influence la granularité avec laquelle l'espace disque est rendu disponible par la rotation, c'est-à-dire la suppression des données historiques. La valeur par défaut est un huitième des valeurs configurées avec SystemMaxUse= et RuntimeMaxUse= plafonnée à 128M, de sorte que généralement sept fichiers de journal tournés sont conservés comme historique. Si le mode compactage du journal est activé (activé par défaut), la taille maximale du fichier est plafonnée à 4G.

Spécifiez les valeurs en octets ou utilisez K, M, G, T, P, E comme unités pour les tailles spécifiées (équivalent à 1024, 1024², ... octets). Notez que les limites de taille sont appliquées de manière synchrone lorsque les fichiers de journal sont étendus, et aucune étape de rotation explicite déclenchée par le temps n'est nécessaire.

SystemMaxFiles= et RuntimeMaxFiles= contrôlent le nombre maximal de fichiers de journal individuels à conserver. Notez que seuls les fichiers archivés sont supprimés pour réduire le nombre de fichiers jusqu'à ce que cette limite soit atteinte ; les fichiers actifs resteront. Cela signifie qu'en fait, il peut encore y avoir plus de fichiers de journal au total que cette limite après qu'une opération de nettoyage soit terminée. Ce paramètre a pour valeur par défaut 100.

MaxFileSec=

Le temps maximal de stockage des entrées dans un fichier de journal unique avant de passer au suivant. Normalement, la rotation basée sur le temps ne devrait pas être nécessaire car la rotation basée sur la taille avec des options telles que SystemMaxFileSize= devrait être suffisante pour garantir que les fichiers de journal ne grandissent pas sans limites. Cependant, pour garantir que pas trop de données soient perdues d'un coup lorsque les anciens fichiers de journal sont supprimés, il peut être judicieux de changer cette valeur de la valeur par défaut d'un mois. Définissez à 0 pour désactiver cette fonctionnalité. Ce paramètre accepte des valeurs de temps qui peuvent être suffixées par les unités "year", "month", "week", "day", "h" ou "m" pour remplacer l'unité de temps par défaut qui est la seconde.

Ajouté dans la version 195.

MaxRetentionSec=

Le temps maximal de stockage des entrées de journal. Cela contrôle si les fichiers de journal contenant des entrées plus anciennes que l'intervalle de temps spécifié sont supprimés. Normalement, la suppression basée sur le temps des anciens fichiers de journal ne devrait pas être nécessaire car la suppression basée sur la taille avec des options telles que SystemMaxUse= devrait être suffisante pour garantir que les fichiers de journal ne grandissent pas sans limites. Cependant, pour faire respecter des politiques de rétention des données, il peut être judicieux de changer cette valeur de la valeur par défaut 0 (ce qui désactive cette fonctionnalité). Ce paramètre accepte également des valeurs de temps qui peuvent être suffixées par les unités "year", "month", "week", "day", "h" ou "m" pour remplacer l'unité de temps par défaut qui est la seconde.

Ajouté dans la version 195.

SyncIntervalSec=

Le délai d'attente avant la synchronisation des fichiers de journal sur le disque. Après la synchronisation, les fichiers de journal sont placés dans l'état OFFLINE. Notez que la synchronisation est faite de manière inconditionnelle immédiatement après qu'un message de journal de priorité CRIT, ALERT ou EMERG a été journalisé. Ce paramètre ne s'applique donc qu'aux messages des niveaux ERR, WARNING, NOTICE, INFO, DEBUG. Le délai d'attente par défaut est de 5 minutes.

Ajouté dans la version 199.

ForwardToSyslog=, ForwardToKMsg=, ForwardToConsole=, ForwardToWall=, ForwardToSocket=

Contrôle si les messages de journal reçus par le démon de journal doivent être transférés à un démon syslog traditionnel, au tampon de journalisation du noyau (kmsg), à la console système, envoyés comme messages wall à tous les utilisateurs connectés ou envoyés via un socket. Ces options prennent des arguments booléens sauf "ForwardToSocket=" qui prend une adresse à la place. Si le transfert vers syslog est activé mais que rien ne lit les messages depuis le socket, le transfert vers syslog n'a aucun effet. Par défaut, seul le transfert vers wall est activé. Ces paramètres peuvent être remplacés au moment du démarrage avec les options de ligne de commande du noyau "systemd.journald.forward_to_syslog", "systemd.journald.forward_to_kmsg", "systemd.journald.forward_to_console", et "systemd.journald.forward_to_wall". Si le nom de l'option est spécifié sans "=" et l'argument suivant, true est supposé. Sinon, l'argument est analysé comme un booléen.

L'adresse de transfert du socket peut être spécifiée avec la information d'identification "journal.forward_to_socket". Les types de socket suivants sont pris en charge :

AF_INET (par ex. "192.168.0.11:4444"), AF_INET6 (par ex. "[2001:db8::ff00:42:8329]:4444"), AF_UNIX (par ex. "/run/host/journal/socket"), AF_VSOCK (par ex. "vsock:2:1234")

Lors du transfert vers la console, la TTY vers laquelle journaliser peut être changée avec TTYPath=, décrit ci-dessous.

Lors du transfert vers le tampon de journalisation du noyau (kmsg), assurez-vous de sélectionner une taille de tampon de journalisation suffisamment grande, par exemple en ajoutant "log_buf_len=8M" à la ligne de commande du noyau. systemd désactivera automatiquement la limitation de débit du noyau appliquée aux processus de l'espace utilisateur (équivalent à définir "printk.devkmsg=on").

Lors du transfert via un socket, le Format d'exportation du journal[4] est utilisé lors de l'envoi sur le réseau. Notamment, cela inclut le champ de métadonnées __REALTIME_TIMESTAMP de sorte que systemd-journal-remote (voir systemd-journal-remote.service(8)) peut être utilisé pour recevoir les entrées de journal transférées.

Note : Le transfert est effectué de manière synchrone au sein de journald et peut affecter significativement ses performances. C'est particulièrement pertinent lors de l'utilisation de ForwardToConsole=yes dans des environnements cloud, où la console est souvent un port série virtuel lent. Comme journald est implémenté comme un démon conventionnel à processus unique, le transfert vers une console complètement bloquée bloquera journald. Cela peut avoir un effet en cascade résultant en ce que tous les services journalisant de manière synchrone vers le journal bloqué deviennent également bloqués. À moins de déboguer/développer activement quelque chose, il est généralement préférable de configurer un service de type journalctl --follow redirigé vers la console, à la place de ForwardToConsole=yes, pour une utilisation en production.

Note : L'utilisation de ForwardToSocket= sur des liens IPv4/IPv6 peut être très lent en raison de la nature synchrone des sockets. Veillez à vous assurer que votre lien est un lien local à faible latence si possible. Typiquement, le réseau IP n'est pas disponible partout où journald s'exécute, par ex. dans ll'initrd au démarrage. Envisagez d'utiliser AF_VSOCK/AF_UNIX pour cela si possible.

MaxLevelStore=, MaxLevelSyslog=, MaxLevelKMsg=, MaxLevelConsole=, MaxLevelWall=, MaxLevelSocket=

Contrôle le niveau de journalisation maximal des messages qui sont stockés dans le journal, transmis à syslog, kmsg, la console, le mur ou un socket (si cela est activé, voir ci-dessus). Comme argument, accepte l'une des valeurs « emerg », « alert », « crit », « err », « warning », « notice », « info », « debug », ou des valeurs entières dans la plage de 0 à 7 (correspondant aux mêmes niveaux). Les messages dont le niveau est égal ou inférieur au niveau spécifié sont stockés/transmis, les messages supérieurs sont ignorés. La valeur par défaut est « debug » pour MaxLevelStore=, MaxLevelSyslog= et MaxLevelSocket=, afin de s'assurer que tous les messages sont stockés dans le journal et transmis à syslog et au socket s'il existe. La valeur par défaut est « notice » pour MaxLevelKMsg=, « info » pour MaxLevelConsole=, et « emerg » pour MaxLevelWall=. Ces paramètres peuvent être remplacés au démarrage avec les options de ligne de commande du noyau « systemd.journald.max_level_store= », « systemd.journald.max_level_syslog= », « systemd.journald.max_level_kmsg= », « systemd.journald.max_level_console= », « systemd.journald.max_level_wall= », « systemd.journald.max_level_socket= ».

ReadKMsg=

Prend une valeur booléenne. Si activé systemd-journal traite les messages /dev/kmsg générés par le noyau. Dans l'espace de noms de journal par défaut, cette option est activée par défaut ; elle est désactivée dans tous les autres.

Ajouté dans la version 235.

Audit=

Prend une valeur booléenne ou la valeur spéciale « keep ». Si activé systemd-journald activera l'audit du noyau au démarrage. S'il est désactivé, il le désactivera. Avec « keep », il ne l'activera ni ne le désactivera, laissant l'état précédent inchangé. Cela signifie que si un autre outil active l'audit, même si systemd-journald l'a laissé désactivé, il collectera quand même les messages générés. La valeur par défaut est « yes » dans l'espace de noms de journal par défaut, et « keep » sinon.

Notez que cette option ne contrôle pas si systemd-journald collecte les enregistrements d'audit générés, elle contrôle seulement s'il indique au noyau de les générer. Si vous devez empêcher systemd-journald de collecter les messages générés, l'unité socket « systemd-journald-audit.socket » peut être désactivée et, dans ce cas, ce paramètre est sans effet.

TTYPath=

Change le TTY de console à utiliser si ForwardToConsole=yes est utilisé. La valeur par défaut est /dev/console.

LineMax=

La longueur de ligne maximale autorisée lors de la conversion des journaux de flux en journaux d'enregistrements. Lorsque la sortie standard/erreur d'une unité systemd est connectée au journal via un socket de flux, les données lues sont divisées en enregistrements de journal individuels aux caractères de nouvelle ligne (« \n », ASCII 10) et NUL . Si aucun délimiteur de ce type n'est lu pour le nombre d'octets spécifié, une limite d'enregistrement de journal stricte est insérée artificiellement, divisant les lignes trop longues en plusieurs enregistrements de journal. Le choix de valeurs trop grandes augmente l'utilisation mémoire possible du démon du Journal pour chaque client de flux, car dans le pire des cas, le démon du journal doit mettre en mémoire tampon le nombre d'octets spécifié avant de pouvoir écrire un nouvel enregistrement de journal sur le disque. Notez également qu'autoriser des longueurs de ligne maximales trop grandes affecte la compatibilité avec les protocoles de journalisation traditionnels, car les enregistrements de journal pourraient ne plus tenir dans un seul AF_UNIX ou AF_INET datagramme. Prend une taille en octets. Si la valeur est suffixée avec K, M, G ou T, la taille spécifiée est interprétée respectivement comme Kilooctets, Mégaoctets, Gigaoctets ou Téraoctets (avec la base 1024). La valeur par défaut est 48K, ce qui est relativement grand mais encore suffisamment petit pour que les enregistrements de journal puissent probablement tenir dans des datagrammes réseau avec de la place supplémentaire pour les métadonnées. Notez que les valeurs inférieures à 79 ne sont pas acceptées et seront portées à 79.

Ajouté dans la version 235.

TRANSMISSION AUX DÉMONS SYSLOG TRADITIONNELS

Les événements du journal peuvent être transférés vers un autre démon de journalisation de deux manières différentes. Avec la première méthode, les messages sont immédiatement transmis à un socket (/run/systemd/journal/syslog), où le démon syslog traditionnel peut les lire. Cette méthode est contrôlée par l'option ForwardToSyslog= . Avec la deuxième méthode, un démon syslog se comporte comme un client de journal normal et lit les messages à partir des fichiers du journal, de manière similaire à journalctl(1). Ainsi, les messages n'ont pas besoin d'être lus immédiatement, ce qui permet à un démon de journalisation qui n'est démarré que tard dans la séquence de démarrage d'accéder à tous les messages depuis le démarrage du système. De plus, des métadonnées structurées complètes lui sont disponibles. Cette méthode est bien entendu disponible uniquement si les messages sont stockés dans un fichier de journal du tout. Elle ne fonctionnera donc pas si Storage=none est défini. Il convient de noter que généralement, c'est la deuxième méthode qui est utilisée par les démons syslog, c'est donc l'option Storage= , et non l'option ForwardToSyslog= , qui est pertinente pour eux.
