Déchiffre le texte chiffré avec le CEK en utilisant le streaming. Description détaillée JSON Web Encryption (RFC 7516) Un objet JSON Web Encryption (JWE) contient (généralement) deux niveaux de chiffrement. Tout d'abord, le texte en clair est chiffré avec une clé symétrique aléatoire. Dans José, nous appelons cette clé la clé de chiffrement du contenu (Content Encryption Key ou CEK). Ensuite, le CEK est emballé (chiffré) avec une ou plusieurs clés. Ces clés sont des clés JSON Web standard (JWK) et peuvent être symétriques ou asymétriques.
Il y a donc (généralement) un CEK et un ou plusieurs JWK. Cependant, il existe quelques exceptions à cette règle. Deux exemples sont les algorithmes : « dir » et « ECDH-ES ». Dans le premier cas, le JWK est une clé symétrique et est utilisé directement comme CEK. Dans le second cas, un échange de clés ECDH est effectué et le résultat est utilisé directement comme CEK. Mais en général, cette règle s'applique.

Cela signifie que vous pouvez chiffrer les données avec un CEK puis chiffrer le CEK pour plusieurs destinataires. Avec ce schéma, plusieurs destinataires peuvent chacun déchiffrer les données avec leur propre clé sans avoir à envoyer un texte chiffré séparé à chaque

destinataire.

Pour une flexibilité maximale, José structure son API pour tirer parti de ce schéma. Par exemple, lors du chiffrement pour deux destinataires, le code pourrait ressembler à ceci (gestion des erreurs

omise) :

json_t *enc(void *plaintext, size_t len, json_t *jwk0, json_t *jwk1) { json_auto_t *jwe = json_object(); json_auto_t *cek = json_object(); // Emballe pour le premier destinataire (CEK généré implicitement) jose_jwe_enc_jwk(NULL, jwe, NULL, jwk0, cek); // Emballe pour le deuxième destinataire jose_jwe_enc_jwk(NULL, jwe, NULL, jwk1, cek); // Chiffre le texte en clair avec le CEK généré jose_jwe_enc_cek(NULL, jwe, cek, plaintext, len); return json_incref(jwe);

}

Cependant, parce que José vise à être facile à utiliser, nous fournissons également des raccourcis. Par exemple, vous pourriez utiliser un JWKSet qui contient plusieurs JWK

:

json_t *enc(void *plaintext, size_t len, json_t *jwkset) { json_auto_t *jwe = json_object(); // Effectue l'emballage et le chiffrement pour tous les destinataires jose_jwe_enc(NULL, jwe, NULL, jwkset, plaintext, len); return json_incref(jwe);

}

Voici deux conseils à retenir. Premièrement, laissez José générer votre CEK implicitement. Deuxièmement, effectuez toujours l'emballage avant le chiffrement. Ces deux conseils sont importants car certains algorithmes d'emballage peuvent imposer des contraintes sur la génération du

CEK. 
Pour déchiffrer un JWE, nous faisons simplement l'inverse. D'abord,
    nous utilisons un JWK pour déballer le CEK. Ensuite, nous utilisons le CEK
    pour déchiffrer le texte chiffré. Voici à quoi cela pourrait ressembler en
    code (encore une fois, gestion des erreurs omise)
:

void *dec(json_t *jwe, json_t *jwk, size_t *len) { json_auto_t *cek = NULL; // Déballe le CEK avec notre JWK cek = jose_jwe_dec_jwk(NULL, jwe, NULL, jwk); // Déchiffre le texte chiffré avec le CEK return jose_jwe_dec_cek(NULL, jwe, cek, len);

} 
Ou, encore une fois, sous une forme simplifiée
:

void *dec(json_t *jwe, json_t *jwk, size_t *len) { return jose_jwe_dec(NULL, jwe, NULL, jwk, len);

}

Si vous devez transférer un JWE à un nouveau destinataire, vous pouvez le faire sans effectuer de re-chiffrement. Déballez simplement le CEK puis réemballez le CEK avec un nouveau JWK. Par exemple

: 
void fwd(json_t *jwe, json_t *oldjwk, json_t *newjwk) {
    json_auto_t *cek = NULL;
    // Déballe le CEK avec l'ancien JWK
    cek = jose_jwe_dec_jwk(NULL, jwe, NULL, oldjwk);
    // Emballe le CEK pour le nouveau JWK
    jose_jwe_enc_jwk(NULL, jwe, NULL, newjwk, cek);
}

Dans tous les exemples ci-dessus, des paramètres tels que les algorithmes de chiffrement à utiliser ont été inférés à partir de nos clés. Lorsqu'une telle inférence ne peut pas être faite, des valeurs par défaut raisonnables et sécurisées ont été choisies automatiquement. Si vous souhaitez plus de contrôle sur le processus, définissez simplement les paramètres dans les objets appropriés (voir la documentation des fonctions pour plus de détails). Par exemple, pour activer la compression du texte en clair, vous pouvez spécifier

la propriété zip 
dans l'en-tête protégé du JWE
:

json_t *enc(void *plaintext, size_t len, json_t *jwkset) { json_auto_t *jwe = json_pack("{s:{s:s}}", "protected", "zip", "DEF"); // Effectue l'emballage compressé et le chiffrement pour tous les destinataires jose_jwe_enc(NULL, jwe, NULL, jwkset, plaintext, len); return json_incref(jwe);

}

    « enc » et « zip », ainsi que tous les paramètres d'en-tête spécifiques à
    l'algorithme utilisés par les algorithmes spécifiques que nous implémentons.
    D'autres paramètres d'en-tête peuvent être spécifiés, mais n'affectent pas
    le comportement de l'implémentation JWE de

bool jose_jwe_enc_jwk (jose_cfg_t * cfg, json_t * jwe, json_t * rcp, const json_t * jwk, json_t * cek)

Enveloppe un CEK avec un JWK. Le but de cette fonction est d'envelopper (chiffrer) ou, dans certains cas, de produire le CEK (cek) à partir du(des) JWK(s) fourni(s) (jwk). Cette fonction peut être utilisée dans deux modes : JWK unique et JWK multiples.

En mode JWK unique, le paramètre jwk contient un objet JWK et le paramètre rcp doit contenir soit un objet destinataire JWE, soit NULL, au quel cas un objet destinataire JWE vide par défaut est créé en interne.

Le mode JWK multiples fonctionne exactement de la même manière que le mode JWK unique, sauf qu'il effectue plusieurs enveloppements dans un seul appel. Ce mode est activé en passant soit un tableau d'objets JWK, soit un JWKSet en paramètre jwk . Dans ce mode, le paramètre rcp contient l'une des valeurs suivantes :

1.
Un objet destinataire JWE qui sera utilisé pour tous les enveloppements. Dans ce cas, une copie sera faite pour chaque enveloppement et rcp ne sera modifié d'aucune manière.
2.
Un tableau d'objets destinataires JWE. Chaque objet sera utilisé avec son JWK correspondant de jwk. Si les tableaux dans sig et jwk sont de tailles différentes, une erreur se produira.
3.
NULL. Cela a le même effet que de passer NULL pour chaque JWK séparé.

Dans les deux modes, si le JWE résultant (jwe) ne contenait qu'un seul destinataire, le JWE sera représenté en Syntaxe de Sérialisation JSON JWE Flattened. Sinon, il sera représenté en Syntaxe de Sérialisation JSON JWE General.

Si le paramètre 'alg' n'est pas spécifié dans l'en-tête JOSE, il sera déduit du JWK et l'algorithme choisi sera ajouté à l'En-tête Non Protégé par Destinataire du JWE. De même, tout paramètre spécifique à l'algorithme manquant et requis sera soit déduit, soit des valeurs par défaut raisonnables et sécurisées seront choisies et les résultats seront ajoutés à l'En-tête Non Protégé par Destinataire du JWE.

Si le CEK fourni (cek) ne contient pas de matériel de clé, il sera généré implicitement lors du premier appel à jose_jwe_enc_jwk(). Cette fonctionnalité importante permet l'utilisation des algorithmes 'dir' et 'ECDH-ES'. Dans le cas de l'algorithme 'dir', le JWK est le CEK et donc le matériel de clé est copié de jwk vers cek. Une situation similaire se produit avec l'algorithme 'ECDH-ES' où le résultat d'un échange de clés est utilisé comme CEK ; ainsi, le CEK est produit pendant le processus d'enveloppement. Cette fonctionnalité implique que si plusieurs enveloppements sont créés, seul un d'entre eux peut avoir l'algorithme 'ECDH-ES' et il doit être le premier enveloppement. Tenter d'utiliser 'ECDH-ES' avec un CEK existant entraînera une erreur.

Il est également possible de passer une chaîne JSON de mot de passe comme entrée de clé à la famille d'algorithmes PBES2 partout où un JWK peut être utilisé. De même, si le paramètre JOSE 'alg' n'est pas spécifié et qu'une chaîne JSON est utilisée à la place d'un JWK, la famille d'algorithmes PBES2 sera déduite.

Paramètres :

cfg Le contexte de configuration (optionnel).
jwe L'objet JWE.
rcp L'objet(s) destinataire JWE ou NULL.
jwk Le(s) JWK(s) ou le JWKSet utilisé pour l'enveloppement.
cek Le CEK à envelopper (si vide, généré).

Renvoie :

true en cas de succès. Sinon, false.

jose_io_t* jose_jwe_enc_cek_io (jose_cfg_t * cfg, json_t * jwe, const json_t * cek, jose_io_t * next)

Chiffre le texte en clair avec le CEK en utilisant le streaming. Le texte en clair est fourni à travers l'objet IO retourné. Le texte en clair sera chiffré et écrit dans l'objet IO suivant . Cet objet IO travaille sur des données binaires, donc vous devrez peut-être utiliser un décodeur Base64 sûr pour les URL en entrée et un encodeur Base64 sûr pour les URL en sortie, selon votre situation.

Le texte en clair compressé peut être activé implicitement en spécifiant le paramètre 'zip' dans l'En-tête Protégé du JWE.

Si l'En-tête Protégé du JWE est un objet JSON plutôt qu'une chaîne encodée, cette fonction encodera l'En-tête Protégé du JWE dans son encodage Base64 sûr pour les URL tel que défini dans la RFC 7516. Cependant, cette fonction ne modifiera jamais un En-tête Protégé du JWE qui est déjà encodé.

Si le paramètre 'enc' n'est pas spécifié dans l'En-tête Protégé du JWE ou l'En-tête Non Protégé Partagé du JWE, il sera déduit du CEK et stocké soit dans l'En-tête Protégé du JWE, soit dans l'En-tête Non Protégé Partagé du JWE (en préférant l'En-tête Protégé du JWE s'il peut être modifié).

Veuillez noter que la propriété 'tag' ne sera ajoutée au JWE que lorsque jose_io_t::done() renverra.

Paramètres :

cfg Le contexte de configuration (optionnel).
jwe L'objet JWE.
cek L'objet CEK.
next L'objet IO suivant dans la chaîne.

Le nouvel objet IO ou NULL en cas d'erreur.

json_t* jose_jwe_dec_jwk (jose_cfg_t * cfg, const json_t * jwe, const json_t * rcp, const json_t * jwk)

Désenveloppe un CEK avec un JWK. Le but de cette fonction est de désenvelopper (déchiffrer) ou, dans certains cas, de produire le CEK (cek) à partir du(des) JWK(s) fourni(s) (jwk). Cette fonction peut être utilisée dans deux modes : JWK unique et JWK multiples.

En mode JWK unique, le paramètre jwk contient un objet JWK et le paramètre rcp doit contenir soit un objet destinataire JWE que vous souhaitez désenvelopper, soit NULL, auquel cas tous les destinataires JWE seront essayés.

Le mode JWK multiples fonctionne exactement de la même manière que le mode JWK unique, sauf qu'il tente de désenvelopper avec plusieurs JWK dans un seul appel. Ce mode est activé en passant soit un tableau d'objets JWK, soit un JWKSet en paramètre jwk . Dans ce mode, le paramètre rcp contient l'une des valeurs suivantes :

1.
Un objet destinataire JWE qui sera utilisé pour tous les tentatives de désenveloppement.
2.
Un tableau d'objets destinataires JWE. Chaque objet sera utilisé avec son JWK correspondant de jwk. Si les tableaux dans sig et jwk sont de tailles différentes, une erreur se produira.
3.
NULL. Cela a le même effet que de passer NULL pour chaque JWK séparé.

Dans les deux modes, un CEK est renvoyé pour le premier JWK qui désenveloppe avec succès un CEK. Deux exceptions à cette règle sont si les algorithmes 'dir' ou 'ECDH-ES' sont utilisés. Dans ce cas, un CEK peut être renvoyé qui échouera lors du déchiffrement puisqu'il n'y a aucun moyen de valider complètement le JWK avec ces algorithmes. Ainsi, nous suggérons de placer les clés pour ces algorithmes en dernier lors du désenveloppement avec plusieurs JWK.

Si le paramètre 'alg' n'est pas spécifié dans l'en-tête JOSE, il sera déduit du JWK. Cela inclut l'utilisation d'une chaîne JSON à la place d'un JWK pour la famille d'algorithmes PBES2.

Paramètres :

cfg Le contexte de configuration (optionnel).
jwe L'objet JWE.
rcp L'objet(s) destinataire JWE ou NULL.
jwk Le(s) JWK ou JWKSet utilisé(s) pour l'enveloppement.

Renvoie :

En cas de succès, un objet CEK nouvellement alloué. Sinon, NULL.

jose_io_t* jose_jwe_dec_cek_io (jose_cfg_t * cfg, const json_t * jwe, const json_t * cek, jose_io_t * next)

Déchiffre le texte chiffré avec le CEK en utilisant le streaming. Le texte chiffré est fourni à travers l'objet IO retourné. Le texte chiffré sera déchiffré et écrit dans l'objet IO suivant. Cet objet IO fonctionne sur des données binaires, vous devrez donc peut-être utiliser un décodeur Base64 sûr pour les URL en entrée et un encodeur Base64 sûr pour les URL en sortie, selon votre situation.

Veuillez noter que la validation de l'intégrité de la protection du texte chiffré est différée jusqu'à ce que jose_io_t::done() renvoie. Cela signifie qu'il est extrêmement important de vérifier cette valeur de retour et qu'il est également important de faire attention au texte clair émis jusqu'à ce que cette vérification soit effectuée.

Le texte clair compressé sera décompressé en interne si la propriété 'zip' est définie de manière appropriée.

Si le paramètre 'enc' n'est pas spécifié dans l'en-tête protégé du JWE ou dans l'en-tête non protégé partagé du JWE, il sera déduit du CEK.

Veuillez noter que la propriété 'tag' du JWE ne sera accédée que lorsque jose_io_t::done() est appelée. Vous pouvez donc la définir à tout moment sur l'objet JWE avant d'appeler jose_io_t::done().

Paramètres :

cfg Le contexte de configuration (optionnel).
jwe L'objet JWE.
cek L'objet CEK.
next L'objet IO suivant dans la chaîne.

Renvoie :

Le nouvel objet IO ou NULL en cas d'erreur.
