NOM

javadoc - générer des pages HTML de documentation d'API à partir de fichiers source Java

SYNTAXE

javadoc [options] [noms-de-paquets] [fichiers-source] [@fichiers]

options
Spécifie les options de ligne de commande, séparées par des espaces. Voir Options standard de javadoc, Options supplémentaires de javadoc, Options standard pour le Doclet Standard et Options supplémentaires pour le Doclet Standard.
noms-de-paquets
Spécifie les noms des paquets que vous souhaitez documenter, séparés par des espaces, par exemple java.lang java.lang.reflect java.awt. Si vous souhaitez également documenter les sous-paquets, utilisez l'option -subpackages pour spécifier les paquets.

Par défaut, javadoc recherche les paquets spécifiés dans le répertoire courant et ses sous-répertoires. Utilisez l'option -sourcepath pour spécifier la liste des répertoires où chercher les paquets.

fichiers-source
Spécifie les noms des fichiers source Java que vous souhaitez documenter, séparés par des espaces, par exemple Class.java Object.java Button.java. Par défaut, javadoc recherche les classes spécifiées dans le répertoire courant. Cependant, vous pouvez spécifier le chemin complet du fichier de classe et utiliser des caractères génériques, par exemple /home/src/java/awt/Graphics*.java. Vous pouvez également spécifier le chemin relatif au répertoire courant.
@fichiers
Spécifie les noms de fichiers qui contiennent une liste d'options de l'outil javadoc, de noms de paquets et de noms de fichiers source dans n'importe quel ordre.

DESCRIPTION

L'outil javadoc analyse les déclarations et les commentaires de documentation dans un ensemble de fichiers source Java et produit des pages HTML correspondantes qui décrivent (par défaut) les classes publiques et protégées, les classes imbriquées et anonymes (mais pas les classes internes anonymes), les interfaces, les constructeurs, les méthodes et les champs. Vous pouvez utiliser l'outil javadoc pour générer la documentation de l'API ou la documentation de l'implémentation d'un ensemble de fichiers source.

Vous pouvez exécuter l'outil javadoc sur des paquets entiers, des fichiers source individuels, ou les deux. Lors de la documentation de paquets entiers, vous pouvez utiliser l'option -subpackages soit pour parcourir récursivement un répertoire et ses sous-répertoires, soit pour passer une liste explicite de noms de paquets. Lorsque vous documentez des fichiers source individuels, passez une liste de noms de fichiers source Java.

Conformité

Le Doclet Standard ne valide pas le contenu des commentaires de documentation pour la conformité, ni n'essaie de corriger les erreurs dans les commentaires de documentation. Il est conseillé à quiconque utilise javadoc d'être conscient des problèmes qui peuvent survenir lors de la génération de sorties non conformes ou de sorties contenant du contenu exécutable, tel que JavaScript. Le Doclet Standard fournit la fonctionnalité DocLint pour aider les développeurs à détecter les problèmes courants dans les commentaires de documentation ; mais il est également recommandé de vérifier la sortie générée avec tous les outils de conformité et autres outils de vérification appropriés.

Pour plus de détails sur les exigences de conformité des documents HTML5, voir Exigences de conformité [https://www.w3.org/TR/html5/infrastructure.html#conformance-requirements] dans la spécification HTML5. Pour plus de détails sur les problèmes de sécurité liés aux pages Web, voir la page Open Web Application Security Project (OWASP) [https://www.owasp.org].

OPTIONS

javadoc prend en charge les options de ligne de commande pour l'outil javadoc principal et le doclet actuellement sélectionné. Le Doclet Standard est utilisé si aucun autre doclet n'est spécifié.

Les options de style GNU (c'est-à-dire celles commençant par --) peuvent utiliser un signe égal (=) au lieu d'espaces pour séparer le nom d'une option de sa valeur.

Les options suivantes sont les options javadoc principales qui ne sont pas équivalentes à une option javac correspondante :

-breakiterator
Calcule la première phrase avec BreakIterator. La première phrase est copiée dans le résumé du paquet, de la classe ou du membre et dans l'index alphabétique. La classe BreakIterator est utilisée pour déterminer la fin d'une phrase pour toutes les langues sauf l'anglais.
•
Algorithme par défaut de fin de phrase en anglais --- S'arrête à un point suivi d'un espace ou d'une balise de bloc HTML, telle que <P>.
•
Algorithme de fin de phrase de Breakiterator --- S'arrête à un point, un point d'interrogation ou un point d'exclamation suivi d'un espace lorsque le mot suivant commence par une majuscule. Ceci est destiné à gérer la plupart des abréviations (par exemple, "Le numéro de série. est valide", mais ne gérera pas "M. Smith"). L'option -breakiterator ne s'arrête pas aux balises HTML ni aux phrases commençant par des chiffres ou des symboles. L'algorithme s'arrête au dernier point dans ../nom_fichier, même lorsqu'il est intégré dans une balise HTML.
-doclet classe
Génère la sortie en utilisant un doclet alternatif. Utilisez le nom qualifié complet. Ce doclet définit le contenu et formate la sortie. Si l'option -doclet n'est pas utilisée, l'outil javadoc utilise le doclet standard pour générer le format HTML par défaut. Cette classe doit contenir la méthode start(Root). Le chemin vers cette classe de départ est défini par l'option -docletpath.
-docletpath chemin
Spécifie où trouver les fichiers de classe du doclet (spécifiés avec l'option -doclet) et tous les fichiers JAR dont il dépend. Si le fichier de classe de départ est dans un fichier JAR, alors cette option spécifie le chemin vers ce fichier JAR. Vous pouvez spécifier un chemin absolu ou un chemin relatif au répertoire courant. Si la liste des chemins de classe contient plusieurs chemins ou fichiers JAR, ils doivent être séparés par un deux-points (:) sous Linux et un point-virgule (;) sous Windows. Cette option n'est pas nécessaire lorsque la classe de départ du doclet est déjà dans le chemin de recherche.
-exclude liste-paquets
Exclut inconditionnellement les paquets spécifiés et leurs sous-paquets de la liste formée par -subpackages. Il exclut ces paquets même lorsqu'ils seraient autrement inclus par une option -subpackages antérieure ou ultérieure.

L'exemple suivant inclurait java.io, java.util, et java.math (entre autres), mais exclurait les paquets racines à java.net et java.lang. Notez que ces exemples excluent java.lang.ref, qui est un sous-paquet de java.lang.

•
Linux et macOS :

javadoc -sourcepath /home/user/src -subpackages java -exclude java.net:java.lang
•
Windows :

javadoc -sourcepath \user\src -subpackages java -exclude java.net:java.lang
--expand-requires valeur
Indique à l'outil javadoc d'étendre l'ensemble des modules à documenter. Par défaut, seuls les modules donnés explicitement sur la ligne de commande sont documentés. Prend en charge les valeurs suivantes :
•
transitive : inclut en plus toutes les dépendances transitives requises de ces modules.
•
all : inclut toutes les dépendances.
--help, -help, -h ou -?
Affiche un synoptique des options standard.
--help-extra ou -X
Affiche un synoptique de l'ensemble des options supplémentaires.
-Jflag
Passe flag directement à l'environnement d'exécution Java (JRE) qui exécute l'outil javadoc. Par exemple, si vous devez garantir que le système alloue 32 Mo de mémoire pour traiter la documentation générée, vous appelleriez l'option -Xmx comme suit : javadoc -J-Xmx32m -J-Xms32m com.mypackage. Soyez conscient que -Xms est facultatif car il ne définit que la taille de la mémoire initiale, ce qui est utile lorsque vous connaissez la quantité minimale de mémoire requise.

Il n'y a pas d'espace entre le J et le drapeau.

Utilisez l'option -version pour signaler la version du JRE utilisée pour exécuter l'outil javadoc.


javadoc -J-version
java version "17" 2021-09-14 LTS
Java(TM) SE Runtime Environment (build 17+35-LTS-2724)
Java HotSpot(TM) 64-Bit Server VM (build 17+35-LTS-2724, mixed mode, sharing)
-locale name
Spécifie la locale que l'outil javadoc utilise lors de la génération de la documentation. L'argument est le nom de la locale, tel que décrit dans la documentation de java.util.Locale, par exemple en_US (anglais, États-Unis) ou en_US_WIN (variante Windows).

La spécification d'une locale amène l'outil javadoc à choisir les fichiers de ressources de cette locale pour les messages tels que les chaînes de la barre de navigation, les titres des listes et des tableaux, le contenu des fichiers d'aide, les commentaires du fichier stylesheet.css, etc. Elle spécifie également l'ordre de tri pour les listes triées par ordre alphabétique, et le séparateur de phrase pour déterminer la fin de la première phrase. L'option -locale ne détermine pas la locale du texte des commentaires de documentation spécifié dans les fichiers source des classes documentées.

-package
Affiche uniquement les classes et membres de package, protégés et publics.
-private
Affiche toutes les classes et tous les membres.
-protected
Affiche uniquement les classes et membres protégés et publics. C'est la valeur par défaut.
-public
Affiche uniquement les classes et membres publics.
-quiet
Désactive les messages afin que seuls les avertissements et les erreurs apparaissent pour les rendre plus faciles à visualiser. Il supprime également la chaîne de version.
--show-members value
Spécifie quels membres (champs ou méthodes) sont documentés, où value peut être l'un des éléments suivants :
•
public --- affiche uniquement les membres publics
•
protected --- affiche les membres publics et protégés ; c'est la valeur par défaut
•
package --- affiche les membres publics, protégés et de package
•
private --- affiche tous les membres
--show-module-contents value
Spécifie la granularité de la documentation des déclarations de modules, où value peut être api ou all.
--show-packages value
Spécifie quels packages de modules sont documentés, où value peut être exported ou all packages.
--show-types value
Spécifie quels types (classes, interfaces, etc.) sont documentés, où value peut être l'un des éléments suivants :
•
public --- affiche uniquement les types publics
•
protected --- affiche les types publics et protégés ; c'est la valeur par défaut
•
package --- affiche les types publics, protégés et de package
•
private --- affiche tous les types
-subpackages subpkglist
Génère de la documentation à partir des fichiers source dans les packages spécifiés et récursivement dans leurs sous-packages. Cette option est utile lors de l'ajout de nouveaux sous-packages au code source car ils sont automatiquement inclus. Chaque argument de package est un sous-package de haut niveau (tel que java) ou un package complètement qualifié (tel que javax.swing) qui n'a pas besoin de contenir de fichiers source. Les arguments sont séparés par des deux-points sur tous les systèmes d'exploitation. Les caractères génériques ne sont pas autorisés. Utilisez -sourcepath pour spécifier où trouver les packages. Cette option ne traite pas les fichiers source qui se trouvent dans l'arborescence source mais qui n'appartiennent pas aux packages.

Par exemple, les commandes suivantes génèrent la documentation pour les packages nommés java et javax.swing et tous leurs sous-packages.

•
Linux et macOS :

javadoc -d docs -sourcepath /home/user/src -subpackages java:javax.swing
•
Windows :

javadoc -d docs -sourcepath \user\src -subpackages java:javax.swing
-verbose
Fournit des messages plus détaillés pendant l'exécution de l'outil javadoc. Sans l'option -verbose, des messages apparaissent pour le chargement des fichiers source, la génération de la documentation (un message par fichier source) et le tri. L'option -verbose provoque l'impression de messages supplémentaires spécifiant le nombre de millisecondes nécessaires pour analyser chaque fichier source Java.
--version
Affiche les informations de version.
-Werror
Signale une erreur si des avertissements surviennent.

Options standard pour le Doclet standard

Les options suivantes sont fournies par le doclet standard.

--add-script file
Ajoute file comme fichier JavaScript supplémentaire à la documentation générée. Cette option peut être utilisée une ou plusieurs fois pour spécifier des fichiers de script supplémentaires.

Exemple de ligne de commande :

javadoc --add-script first_script.js --add-script second_script.js pkg_foo

--add-stylesheet file
Ajoute file comme fichier de feuille de style supplémentaire à la documentation générée. Cette option peut être utilisée une ou plusieurs fois pour spécifier des feuilles de style supplémentaires incluses dans la documentation.

Exemple de ligne de commande :


javadoc --add-stylesheet new_stylesheet_1.css --add-stylesheet new_stylesheet_2.css pkg_foo
--allow-script-in-comments
Autorise JavaScript dans les options et les commentaires.
-author
Inclut le texte @author dans les documents générés.
-bottom html-code
Spécifie le texte à placer en bas de chaque fichier de sortie. Le texte est placé en bas de la page, sous la barre de navigation inférieure. Le texte peut contenir des balises HTML et des espaces blancs, mais lorsqu'il le fait, le texte doit être entouré de guillemets. Utilisez des caractères d'échappement pour les guillemets internes dans le texte.
-charset name
Spécifie le jeu de caractères HTML de ce document. Le nom doit être un nom MIME préféré tel que spécifié dans le Registre IANA, Jeux de caractères [http://www.iana.org/assignments/character-sets].

Par exemple :


javadoc -charset "iso-8859-1" mypackage

Cette commande insère la ligne suivante dans l'en-tête de chaque page générée :


<meta http-equiv="Content-Type" content="text/html; charset=ISO-8859-1">

La balise meta est décrite dans la norme HTML (4197265 et 4137321), Représentation de document HTML [http://www.w3.org/TR/REC-html40/charset.html#h-5.2.2].

-d directory
Spécifie le répertoire de destination où l'outil javadoc enregistre les fichiers HTML générés. Si vous omettez l'option -d, les fichiers sont enregistrés dans le répertoire courant. La valeur du répertoire peut être absolue ou relative au répertoire de travail courant. Le répertoire de destination est automatiquement créé lorsque l'outil javadoc s'exécute.
•
Linux et macOS : Par exemple, la commande suivante génère la documentation pour le package com.mypackage et enregistre les résultats dans le répertoire /user/doc/ :

javadoc -d /user/doc/ com.mypackage
•
Windows : Par exemple, la commande suivante génère la documentation pour le package com.mypackage et enregistre les résultats dans le répertoire \user\doc\ :

javadoc -d \user\doc\ com.mypackage

  • -docfilessubdirs

    Copie récursivement les sous-répertoires de doc-file. Active la copie profonde des répertoires doc-files. Les sous-répertoires et tout leur contenu sont copiés récursivement vers la destination. Par exemple, le répertoire doc-files/example/images et tout son contenu sont copiés. L'option -excludedocfilessubdir peut être utilisée pour exclure des sous-répertoires spécifiques.

  • -doctitle code-html

    Spécifie le titre à placer près du haut du fichier de résumé d'aperçu. Le texte spécifié dans la balise title est placé comme un titre centré de niveau un, directement sous la barre de navigation supérieure. La balise title peut contenir des balises HTML et des espaces blancs, mais lorsqu'elle le fait, vous devez entourer le titre de guillemets. Les guillemets supplémentaires à l'intérieur de la balise title doivent être échappés. Par exemple, javadoc -doctitle "<b>Ma Bibliothèque</b><br>v1.0" com.mypackage.

  • -excludedocfilessubdir nom1,nom2...

    Exclut tous les sous-répertoires avec les noms donnés lors de la copie récursive des sous-répertoires doc-file. Voir -docfilessubdirs. Pour des raisons historiques, : peut être utilisé n'importe où dans l'argument comme séparateur au lieu de ,.

  • -footer code-html

    Spécifie le texte du pied de page à placer en bas de chaque fichier de sortie. La valeur code-html est placée à droite de la barre de navigation inférieure. La valeur code-html peut contenir des balises HTML et des espaces blancs, mais lorsqu'elle le fait, la valeur code-html doit être entourée de guillemets. Utilisez des caractères d'échappement pour tous les guillemets internes dans un pied de page.

  • -group nom p1,p2...

    Regroupe les paquets spécifiés sur la page d'aperçu. Pour des raisons historiques, : peut être utilisé comme séparateur n'importe où dans l'argument au lieu de ,.

  • -header code-html

    Spécifie le texte d'en-tête à placer en haut de chaque fichier de sortie. L'en-tête est placé à droite de la barre de navigation supérieure. L'en-tête peut contenir des balises HTML et des espaces blancs, mais lorsqu'il le fait, l'en-tête doit être entouré de guillemets. Utilisez des caractères d'échappement pour les guillemets internes dans un en-tête. Par exemple, javadoc -header "<b>Ma Bibliothèque</b><br>v1.0" com.mypackage.

  • -helpfile nomfichier

    Inclut le fichier qui renvoie au lien AIDE dans les barres de navigation supérieure et inférieure. Sans cette option, l'outil javadoc crée un fichier d'aide help-doc.html qui est codé en dur dans l'outil javadoc. Cette option vous permet de remplacer la valeur par défaut. Le nomfichier peut être n'importe quel nom et n'est pas restreint à help-doc.html. L'outil javadoc ajuste les liens dans la barre de navigation en conséquence. Par exemple :

  • -html5

    Cette option est une opération nulle et est conservée uniquement pour la compatibilité ascendante.

  • --javafx ou -javafx

    Active la fonctionnalité JavaFX. Cette option est activée par défaut si les classes de la bibliothèque JavaFX sont détectées sur le chemin du module.

  • -keywords

    Ajoute des balises HTML de mots-clés <meta> au fichier généré pour chaque classe. Ces balises peuvent aider les moteurs de recherche qui recherchent des balises <meta> à trouver les pages. La plupart des moteurs de recherche qui parcourent l'ensemble d'Internet ne consultent pas les balises <meta>, car les pages peuvent les utiliser à mauvais escient. Les moteurs de recherche proposés par les entreprises qui limitent leurs recherches à leur propre site Web peuvent bénéficier de la consultation des balises <meta>. Les balises <meta> incluent le nom qualifié complet de la classe et les noms non qualifiés des champs et des méthodes. Les constructeurs ne sont pas inclus car ils sont identiques au nom de la classe. Par exemple, la classe String commence par ces mots-clés :

    <dt></dt> <dd> 
    <b></b>
<meta name="keywords" content="java.lang.String class">
<meta name="keywords" content="CASE_INSENSITIVE_ORDER">
<meta name="keywords" content="length()">
<meta name="keywords" content="charAt()">
<b></b>
    </dd>
  • -link url

    Crée des liens vers la documentation générée par javadoc des classes référencées extérieurement. L'argument url est l'URL absolue ou relative du répertoire qui contient la documentation externe générée par javadoc. Vous pouvez spécifier plusieurs options -link dans une exécution donnée de l'outil javadoc pour lier vers plusieurs documents.

    Soit un fichier package-list, soit un fichier element-list doit se trouver dans ce répertoire url (sinon, utilisez l'option -linkoffline).

    Remarque : Les fichiers package-list et element-list sont générés par l'outil javadoc lors de la génération de la documentation de l'API et ne doivent pas être modifiés par l'utilisateur.

    Lorsque vous utilisez l'outil javadoc pour documenter des paquets, il utilise le fichier package-list pour déterminer les paquets déclarés dans une API. Lorsque vous générez des documents d'API pour des modules, l'outil javadoc utilise le fichier element-list pour déterminer les modules et les paquets déclarés dans une API.

    L'outil javadoc lit les noms du fichier de liste approprié, puis se connecte aux paquets ou aux modules à cette URL.

    Lorsque l'outil javadoc s'exécute, la valeur url est copiée dans les liens <A HREF> qui sont créés. Par conséquent, url doit être l'URL du répertoire et non d'un fichier.

    Vous pouvez utiliser un lien absolu pour url afin de permettre à vos documents de se connecter à un document sur n'importe quel site Web, ou vous pouvez utiliser un lien relatif pour ne vous connecter qu'à un emplacement relatif. Si vous utilisez un lien relatif, alors la valeur que vous passez doit être le chemin relatif depuis le répertoire de destination (spécifié avec l'option -d) vers le répertoire contenant les paquets auxquels vous vous connectez. Lorsque vous spécifiez un lien absolu, vous utilisez généralement un lien HTTP. Cependant, si vous souhaitez vous connecter à un système de fichiers qui n'a pas de serveur Web, vous pouvez utiliser un lien de type fichier. Utilisez un lien de type fichier uniquement lorsque tout le monde qui souhaite accéder à la documentation générée partage le même système de fichiers. Dans tous les cas, et sur tous les systèmes d'exploitation, utilisez une barre oblique comme séparateur, que l'URL soit absolue ou relative, et https:, http:, ou file: comme spécifié dans l'URL Memo : Uniform Resource Locators [http://www.ietf.org/rfc/rfc1738.txt].

    <dt></dt> <dd> 
    <b></b>
-link https://<hôte>/<répertoire>/<répertoire>/.../<nom>
-link http://<hôte>/<répertoire>/<répertoire>/.../<nom>
-link file://<hôte>/<répertoire>/<répertoire>/.../<nom>
-link <répertoire>/<répertoire>/.../<nom>
<b></b>
    </dd>
  • --link-modularity-mismatch (warn|info)

    Spécifie si la documentation externe avec une modularité incorrecte (par exemple, une documentation non modulaire pour une bibliothèque modulaire, ou le cas inverse) doit être signalée comme un avertissement (warn) ou simplement comme un message (info). Le comportement par défaut est de signaler un avertissement.

  • -linkoffline url1 url2

    Cette option est une variation de l'option -link. Elles créent toutes deux des liens vers la documentation générée par javadoc pour les classes référencées extérieurement. Vous pouvez spécifier plusieurs options -linkoffline dans une exécution donnée de l'outil javadoc.

    Utilisez l'option -linkoffline lorsque :

DOCLINT

DocLint offre la possibilité de vérifier les problèmes potentiels dans les commentaires de documentation. Les problèmes peuvent être signalés comme des avertissements ou des erreurs, en fonction de leur gravité. Par exemple, un commentaire manquant peut être un mauvais style qui mérite un avertissement, mais un lien vers une déclaration Java inconnue est plus grave et mérite une erreur. Les problèmes sont organisés en groupes, et des options peuvent être utilisées pour activer ou désactiver les messages dans un ou plusieurs groupes. Dans le code source, les messages dans un ou plusieurs groupes peuvent être supprimés en utilisant des annotations @SuppressWarnings.

Lorsqu'il est invoqué depuis javadoc, DocLint vérifie par défaut tous les commentaires utilisés dans la documentation générée. Il s'appuie ainsi sur d'autres options de ligne de commande pour déterminer quelles déclarations, et quels commentaires correspondants, seront inclus. Note : cela peut signifier que même les commentaires sur certains membres privés de classes sérialisables seront vérifiés, si les membres doivent être documentés dans les formes sérialisées générées.

En revanche, lorsqu'il est invoqué depuis javac, DocLint s'appuie uniquement sur les différentes options -Xdoclint... pour déterminer quels commentaires de documentation vérifier.

DocLint n'essaie pas de corriger les entrées invalides, il les signale simplement.

DESCRIPTION

DocLint est un vérificateur de commentaires de documentation qui est intégré aux compilateurs javac et javadoc. Il vérifie que les commentaires de documentation sont correctement formatés et ne contiennent pas d'erreurs courantes.

DocLint n'est pas un vérificateur complet de conformité HTML. Son objectif est de signaler simplement les erreurs courantes d'une manière pratique.

Groupes

Les vérifications effectuées par DocLint sont organisées en groupes. Les avertissements et les erreurs de chaque groupe peuvent être activés ou désactivés à l'aide d'options en ligne de commande, ou supprimés à l'aide d'annotations @SuppressWarnings.

Les groupes sont les suivants:

•
accessibilite --- Vérifie les problèmes liés à l'accessibilité. Par exemple, l'absence d'un attribut alt dans un élément <img>, ou l'absence d'attributs de légende ou de résumé dans un élément <table>.

Les problèmes sont signalés comme des erreurs si un outil de validation en aval est susceptible de signaler une erreur dans les fichiers générés par javadoc.

Pour référence, consultez les Web Content Accessibility Guidelines [https://www.w3.org/WAI/standards-guidelines/wcag/].

•
html --- Détecte les problèmes HTML courants de haut niveau. Par exemple, placer des éléments de bloc à l'intérieur d'éléments en ligne, ou ne pas fermer les éléments qui nécessitent une balise de fin.

Les problèmes sont signalés comme des erreurs si un outil de validation en aval est susceptible de signaler une erreur dans les fichiers générés par javadoc.

Pour référence, consultez le HTML Living Standard [https://html.spec.whatwg.org/multipage/].

•
manquant --- Vérifie l'absence de commentaires de documentation ou de balises. Par exemple, un commentaire manquant sur une déclaration de classe, ou une balise @param ou @return manquante dans le commentaire pour une déclaration de méthode.

Les problèmes liés aux éléments manquants sont généralement signalés comme des avertissements car ils sont peu susceptibles d'être signalés comme des erreurs par les outils de validation en aval qui peuvent être utilisés pour vérifier la sortie générée par javadoc.

•
reference --- Vérifie les problèmes liés aux références aux éléments de l'API Java à partir des balises de commentaires de documentation. Par exemple, la référence dans @see ou {@link ...} ne peut pas être trouvée, ou un mauvais nom est donné pour @param ou @throws.

Les problèmes sont généralement signalés comme des erreurs car, bien que le problème puisse ne pas causer de problèmes dans les fichiers générés, l'auteur a probablement commis une erreur qui entraînera une documentation incorrecte ou inattendue.

•
syntaxe --- Vérifie les problèmes syntaxiques de bas niveau dans les commentaires de documentation. Par exemple, les crochets non échappés (< et >) et les ampersands (&) et les balises de commentaires de documentation invalides.

Les problèmes sont généralement signalés comme des erreurs car les problèmes peuvent entraîner une documentation incorrecte ou inattendue.

Suppression des messages

DocLint recherche et reconnaît deux chaînes de caractères qui peuvent être présentes dans les arguments d'une annotation @SuppressWarnings.

•
doclint
•
doclint:LIST

où LIST est une liste séparée par des virgules d'un ou plusieurs des éléments suivants : accessibilite, html, manquant, syntaxe, reference.

Les noms dans LIST sont les mêmes noms de groupe que ceux pris en charge par l'option -Xdoclint en ligne de commande pour javac et javadoc. (C'est la même convention que celle suivie par l'option javac -Xlint et les noms correspondants pris en charge par @SuppressWarnings.)

Les noms dans LIST peuvent être spécifiés de manière équivalente dans des arguments distincts de l'annotation. Par exemple, les éléments suivants sont équivalents:

•
@SuppressWarnings("doclint:accessibilite,manquant")
•
@SuppressWarnings("doclint:accessibilite", "doclint:manquant")

Lorsque DocLint détecte un problème dans un commentaire de documentation, il recherche la présence de @SuppressWarnings sur la déclaration associée et sur toutes les déclarations qui l'englobent lexicalement. Le problème sera ignoré si une telle annotation est trouvée contenant la chaîne simple doclint ou la forme plus longue doclint:LIST où LIST contient le nom du groupe pour le problème.

Note : comme pour les autres utilisations de @SuppressWarnings, l'utilisation de l'annotation sur une déclaration de module ou de paquet n'affecte que cette déclaration ; elle n'affecte pas le contenu du module ou du paquet dans d'autres fichiers source.

Tous les messages relatifs à un problème sont supprimés par la présence d'une annotation @SuppressWarnings appropriée : cela inclut les erreurs ainsi que les avertissements.

Note : il est seulement possible de supprimer des messages. Si une annotation @SuppressWarnings("doclint") est fournie sur une déclaration de niveau supérieur, tous les messages DocLint pour cette déclaration et les déclarations englobées seront supprimés ; il n'est pas possible de réactiver sélectivement les messages pour les problèmes dans les déclarations englobées.

Comparaison avec les outils de validation en aval

DocLint est un utilitaire intégré à javac et javadoc qui vérifie le contenu des commentaires de documentation, tels qu'ils se trouvent dans les fichiers source. En revanche, les outils de validation en aval peuvent être utilisés pour valider la sortie générée à partir de ces commentaires de documentation par javadoc et le Standard Doclet.

Bien qu'il y ait un chevauchement fonctionnel, les deux mécanismes sont différents et chacun a ses propres forces et faiblesses.

•
Les outils de validation en aval peuvent vérifier le résultat final de toute documentation générée, telle qu'elle sera vue par l'utilisateur final. Cela inclut le contenu de toutes les sources, y compris les commentaires de documentation, le Standard Doclet lui-même, les taglets fournis par l'utilisateur et le contenu fourni via les options en ligne de commande. Étant donné que ces outils analysent des pages HTML complètes, ils peuvent effectuer des vérifications plus complètes que DocLint. Cependant, lorsqu'un problème est trouvé dans les pages générées, il peut être plus difficile de déterminer exactement où dans le pipeline de construction le problème doit être corrigé.
•
DocLint vérifie le contenu des commentaires de documentation, dans les fichiers source. Cela permet d'identifier très facilement la position exacte de tout problème qui pourrait être trouvé. DocLint peut également détecter certaines erreurs sémantiques dans les commentaires de documentation que les outils en aval ne peuvent pas détecter, telles que les commentaires manquants, l'utilisation d'une balise @return dans une méthode retournant void, ou une balise @param décrivant un paramètre inexistant. Mais par nature, DocLint ne peut pas signaler les problèmes tels que les liens manquants, ou les erreurs dans les taglets personnalisés fournis par l'utilisateur, ou les problèmes dans le Standard Doclet lui-même. Il ne peut pas non plus détecter de manière fiable les erreurs dans les commentaires de documentation aux limites entre le contenu d'un commentaire de documentation et le contenu généré par un taglet personnalisé.
