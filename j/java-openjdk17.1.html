UTILISATION DE LA VARIABLE D'ENVIRONNEMENT DE LANCEUR JDK_JAVA_OPTION

S

JDK_JAVA_OPTIONS préfixe son contenu aux options analysées depuis la ligne de commande. Le contenu de la variable d'environnement JDK_JAVA_OPTIONS est une liste d'arguments séparés par des caractères d'espacement (tel que déterminé par isspace()). Ceux-ci sont préfixés aux arguments de la ligne de commande passés au lanceur java. L'exigence d'encodage pour la variable d'environnement est la même que pour la ligne de commande java sur le système. Le contenu de la variable d'environnement JDK_JAVA_OPTIONS est traité de la même manière que ce qui est spécifié dans la ligne de

commande.

Les guillemets simples (') ou doubles (") peuvent être utilisés pour encadrer des arguments contenant des caractères d'espacement. Tout le contenu entre la quote d'ouverture et la première quote de fermeture correspondante est conservé en supprimant simplement la paire de quotes. Si aucune quote correspondante n'est trouvée, le lanceur s'arrêtera avec un message d'erreur. Les fichiers @ sont pris en charge comme ils sont spécifiés dans la ligne de commande. Cependant, comme dans les fichiers @, l'utilisation d'un joker n'est pas prise en charge. Afin d'atténuer une éventuelle mauvaise utilisation du comportement de JDK_JAVA_OPTIONS, les options qui spécifient la classe principale (telles que -jar) ou qui font que le lanceur java se termine sans exécuter la classe principale (telles que -h) sont interdites dans la variable d'environnement. Si l'une de ces options apparaît dans la variable d'environnement, le lanceur s'arrêtera avec un message d'erreur. Lorsque JDK_JAVA_OPTIONS est défini, le lanceur imprime un message sur stderr comme

rappel.

Exemple

: 

$ export JDK_JAVA_OPTIONS='-g @file1 -Dprop=value @file2 -Dws.prop="white spaces"'
$ java -Xint @file3

est équivalent à la ligne de commande

: 

java -g @file1 -Dprop=value @file2 -Dws.prop="white spaces" -Xint @file3

Plusieurs exemples de réglage des performances sont fournis dans Exemples de réglage des performances . Pour les options qui nécessitent un argument, l'argument peut être séparé du nom de l'option par un espace, deux-points (:) ou un signe égal (=), ou l'argument peut suivre directement l'option (la syntaxe exacte diffère pour chaque option). -Xmn taille
Définit la taille initiale et maximale (en octets) du tas (heap) pour la jeune génération (nursery) dans les collecteurs génératifs. Ajoutez la lettre k ou K pour indiquer les kilooctets, m ou M pour indiquer les mégaoctets, ou g ou G pour indiquer les gigaoctets. La région de jeune génération du tas est utilisée pour les nouveaux objets. Le garbage collector (GC) est exécuté dans cette région plus souvent que dans d'autres régions. Si la taille de la jeune génération est trop petite, de nombreux cycles de garbage collection mineurs sont effectués. Si la taille est trop grande, seuls les cycles de garbage collection complets sont exécutés, ce qui peut prendre beaucoup de temps. Il est recommandé de ne pas définir la taille de la jeune génération pour le collecteur G1, et de maintenir la taille de la jeune génération supérieure à 25 % et inférieure à 50 % de la taille totale du tas pour les autres collecteurs. Les exemples suivants montrent comment définir la taille initiale et maximale de la jeune génération à 256 Mo en utilisant différentes unités :

-Xmn256m
-Xmn262144k
-Xmn268435456

Au lieu de l'option -Xmn pour définir la taille initiale et maximale du tas pour la jeune génération, vous pouvez utiliser -XX:NewSize pour définir la taille initiale et -XX:MaxNewSize pour définir la taille maximale.

-Xms taille

Ajoutez la lettre k ou K pour indiquer les kilooctets, m ou M pour indiquer les mégaoctets, g ou G pour indiquer les gigaoctets. Les exemples suivants montrent comment définir la taille de la mémoire allouée à 6 Mo en utilisant différentes unités :

Si vous ne définissez pas cette option, la taille initiale est définie comme la somme des tailles allouées pour la vieille génération et la jeune génération. La taille initiale du tas pour la jeune génération peut être définie à l'aide de l'option -Xmn ou de l'option -XX:NewSize.

-Xmx taille

-Xnoclassgc
Désactive le garbage collection (GC) des classes. Cela peut économiser du temps de GC, ce qui réduit les interruptions pendant l'exécution de l'application. Lorsque vous spécifiez -Xnoclassgc au démarrage, les objets de classe de l'application sont laissés intacts pendant le GC et seront toujours considérés comme actifs. Cela peut entraîner une occupation permanente de plus de mémoire, ce qui, si ce n'est pas utilisé avec précaution, peut provoquer une exception de manque de mémoire (out-of-memory exception).
-Xrs
Réduit l'utilisation des signaux du système d'exploitation par la JVM. Les hooks de fermeture (shutdown hooks) permettent la fermeture ordonnée d'une application Java en exécutant le code de nettoyage utilisateur (comme la fermeture des connexions à la base de données) lors de la fermeture, même si la JVM se termine brutalement.
•
Linux et macOS :
•
La JVM intercepte les signaux pour implémenter les hooks de fermeture en cas de terminaison inattendue. La JVM utilise SIGHUP, SIGINT et SIGTERM pour initier l'exécution des hooks de fermeture.
•
Les applications embarquant la JVM doivent fréquemment intercepter des signaux tels que SIGINT ou SIGTERM, ce qui peut interférer avec les gestionnaires de signaux de la JVM. L'option -Xrs est disponible pour résoudre ce problème. Lorsque -Xrs est utilisée, les masques de signaux pour SIGINT, SIGTERM, SIGHUP et SIGQUIT ne sont pas modifiés par la JVM, et les gestionnaires de signaux pour ces signaux ne sont pas installés.
•
Windows :
•
La JVM surveille les événements de contrôle de la console pour implémenter les hooks de fermeture en cas de terminaison inattendue. Plus précisément, la JVM enregistre un gestionnaire de contrôle de la console qui lance le traitement des hooks de fermeture et renvoie TRUE pour CTRL_C_EVENT, CTRL_CLOSE_EVENT, CTRL_LOGOFF_EVENT et CTRL_SHUTDOWN_EVENT.
•
La JVM utilise un mécanisme similaire pour implémenter la fonctionnalité de vidage des piles de threads à des fins de débogage. La JVM utilise CTRL_BREAK_EVENT pour effectuer des vidages de threads.
•
Si la JVM est exécutée en tant que service (par exemple, comme un moteur de servlet pour un serveur web), elle peut recevoir CTRL_LOGOFF_EVENT mais ne doit pas initier de fermeture car le système d'exploitation ne termine pas réellement le processus. Pour éviter d'éventuelles interférences de ce type, l'option -Xrs peut être utilisée. Lorsque l'option -Xrs est utilisée, la JVM n'installe pas de gestionnaire de contrôle de la console, ce qui signifie qu'elle ne surveille ni ne traite CTRL_C_EVENT, CTRL_CLOSE_EVENT, CTRL_LOGOFF_EVENT ou CTRL_SHUTDOWN_EVENT.

Il y a deux conséquences à spécifier -Xrs :

•
Linux et macOS : Les vidages de threads SIGQUIT ne sont pas disponibles.
•
Windows : Les vidages de threads Ctrl + Break ne sont pas disponibles.

Le code utilisateur est responsable de provoquer l'exécution des hooks de fermeture, par exemple, en appelant System.exit() lorsque la JVM doit être terminée.

-XX:AllocateInstancePrefetchLines=lign
es
Définit le nombre de lignes àrefetch avant le pointeur d'allocation d'instance. Par défaut, le nombre de lignes à pré-charger est défini sur 1:

-XX:AllocateInstancePrefetchLines=1

-XX:AllocatePrefetchDistance=taille
Définit la taille (en octets) de la distance de pré-charge pour l'allocation d'objets. La mémoire qui sera bientôt écrite avec la valeur des nouveaux objets est pré-chargée jusqu'à cette distance à partir de l'adresse du dernier objet alloué. Chaque thread Java possède son propre pointeur d'allocation.

Les valeurs négatives indiquent que la distance de pré-charge est choisie en fonction de la plateforme. Les valeurs positives correspondent aux octets à pré-charger. Ajoutez la lettre k ou K pour indiquer les kilo-octets, m ou M pour indiquer les méga-octets, ou g ou G pour indiquer les giga-octets. La valeur par défaut est -1.

L'exemple suivant montre comment définir la distance de pré-charge à 1024 octets:

-XX:AllocatePrefetchDistance=1024

-XX:AllocatePrefetchInstr=instruction
Définit l'instruction de pré-charge pour pré-charger avant le pointeur d'allocation. Les valeurs possibles vont de 0 à 3. Les instructions réelles derrière les valeurs dépendent de la plateforme. Par défaut, l'instruction de pré-charge est définie sur 0:

-XX:AllocatePrefetchInstr=0

-XX:AllocatePrefetchLines=lignes
Définit le nombre de lignes de cache à charger après la dernière allocation d'objet en utilisant les instructions de pré-charge générées dans le code compilé. La valeur par défaut est 1 si le dernier objet alloué était une instance, et 3 s'il s'agissait d'un tableau.

L'exemple suivant montre comment définir le nombre de lignes de cache chargées à 5:

-XX:AllocatePrefetchLines=5

-XX:AllocatePrefetchStepSize=taille
Définit la taille de pas (en octets) pour les instructions de pré-charge séquentielles. Ajoutez la lettre k ou K pour indiquer les kilo-octets, m ou M pour indiquer les méga-octets, g ou G pour indiquer les giga-octets. Par défaut, la taille de pas est de 16 octets:

-XX:AllocatePrefetchStepSize=16

-XX:AllocatePrefetchStyle=style
Définit le style de code généré pour les instructions de pré-charge. L'argument style est un entier de 0 à 3:
0
Ne génère pas d'instructions de pré-charge.
1
Exécute les instructions de pré-charge après chaque allocation. C'est le paramètre par défaut.
2
Utilise le pointeur de filigrane du bloc d'allocation local au thread (TLAB) pour déterminer quand les instructions de pré-charge sont exécutées.
3
Génère une instruction de pré-charge par ligne de cache.

-XX:CompileCommand=commande,méthode[,option]
Spécifie une commande à effectuer sur une méthode. Par exemple, pour exclure la méthode indexOf() de la classe String de la compilation, utilisez ce qui suit:

-XX:CompileCommand=exclude,java/lang/String.indexOf

Notez que le nom de classe complet est spécifié, y compris tous les packages et sous-packages séparés par une barre oblique (/). Pour des opérations de copier-coller plus faciles, il est également possible d'utiliser le format de nom de méthode produit par les options -XX:+PrintCompilation et -XX:+LogCompilation:

-XX:CompileCommand=exclude,java.lang.String::indexOf

Si la méthode est spécifiée sans sa signature, la commande est appliquée à toutes les méthodes portant ce nom. Cependant, vous pouvez également spécifier la signature de la méthode au format du fichier de classe. Dans ce cas, vous devez encadrer les arguments entre guillemets, car sinon le shell interprète le point-virgule comme la fin de la commande. Par exemple, si vous souhaitez exclure uniquement la méthode indexOf(String) de la classe String de la compilation, utilisez ce qui suit:

-XX:CompileCommand="exclude,java/lang/String.indexOf,(Ljava/lang/String;)I"

Vous pouvez également utiliser l'astérisque (*) comme caractère générique pour les noms de classe et de méthode. Par exemple, pour exclure toutes les méthodes indexOf() dans toutes les classes de la compilation, utilisez ce qui suit:

-XX:CompileCommand=exclude,*.indexOf

Les virgules et les points sont des alias pour les espaces, ce qui facilite le passage des commandes du compilateur via un shell. Vous pouvez passer des arguments à -XX:CompileCommand en utilisant des espaces comme séparateurs en encadrant l'argument entre guillemets:

-XX:CompileCommand="exclude java/lang/String indexOf"

Notez qu'après avoir analysé les commandes passées sur la ligne de commande à l'aide des options -XX:CompileCommand, le compilateur JIT lit ensuite les commandes du fichier .hotspot_compiler. Vous pouvez ajouter des commandes à ce fichier ou spécifier un fichier différent à l'aide de l'option -XX:CompileCommandFile.

break
Définit un point d'arrêt lors du débogage de la JVM pour s'arrêter au début de la compilation de la méthode spécifiée.
compileonly
Exclut toutes les méthodes de la compilation sauf la méthode spécifiée. Alternativement, vous pouvez utiliser l'option -XX:CompileOnly, qui vous permet de spécifier plusieurs méthodes.
dontinline
Empêche l'inlining de la méthode spécifiée.
exclude
Exclut la méthode spécifiée de la compilation.
help
Affiche un message d'aide pour l'option -XX:CompileCommand.
inline
Tente d'inliner la méthode spécifiée.
log
Exclut la journalisation de la compilation (avec l'option -XX:+LogCompilation) pour toutes les méthodes sauf la méthode spécifiée. Par défaut, la journalisation est effectuée pour toutes les méthodes compilées.
option
Passe une option de compilation JIT à la méthode spécifiée à la place du dernier argument (option). L'option de compilation est définie à la fin, après le nom de la méthode. Par exemple, pour activer l'option BlockLayoutByFrequency pour la méthode append() de la classe StringBuffer, utilisez ce qui suit:

Définit le fichier à partir duquel les commandes du compilateur JIT sont lues. Par défaut, le fichier .hotspot_compiler est utilisé pour stocker les commandes effectuées par le compilateur JIT.

GRANDES

PAGES

Vous utilisez les grandes pages, également connues sous le nom de pages géantes, comme des pages mémoire qui sont significativement plus grandes que la taille standard de page mémoire (qui varie selon le processeur et le système d'exploitation). Les grandes pages optimisent les tampons de traduction d'adresses (TLB) du

processeur.

Un tampon de traduction d'adresses (TLB) est un cache de traduction de pages qui contient les traductions d'adresses virtuelles vers physiques les plus récemment utilisées. Un TLB est une ressource système rare. Une absence de TLB peut être coûteuse car le processeur doit alors lire depuis la table de pages hiérarchique, ce qui peut nécessiter plusieurs accès mémoire. En utilisant une taille de page mémoire plus grande, une seule entrée de TLB peut représenter une plage mémoire plus grande. Cela résulte en moins de pression sur un TLB, et les applications gourmandes en mémoire peuvent avoir de meilleures

performances.

Cependant, l'utilisation de grandes pages peut affecter négativement lesperformance. Par exemple, lorsqu'une grande quantité de mémoire est épinglée par une application, cela peut créer une pénurie de mémoire régulière et provoquer un paging excessif dans d'autres applications et ralentir l'ensemble du système. De plus, un système qui tourne depuis longtemps peut produire une fragmentation excessive, ce qui pourrait rendre impossible la réservation d'une quantité suffisante de mémoire en grandes pages. Lorsque cela se produit, soit l'OS, soit la JVM revient à l'utilisation de pages

régulières.

Linux et Windows prennent en charge les grandes

pages.

DESCRIPTION

The java utility starts a Java Virtual Machine (JVM), loads the specified class, and calls its main method. The main method must be declared as public, must return void, and must accept a single argument of type String array.

The java utility can also launch applications packaged as a single executable JAR file using the -jar option.

The java utility can also launch a script, specified by the --source option, which is compiled and run dynamically.

The classpath can be specified using the -cp or -classpath option. If these options are not specified, the classpath defaults to the current directory. The classpath can also be specified using the CLASSPATH environment variable. If neither is specified, the classpath defaults to the current directory.

The module path can be specified using the --module-path or -p option. If this option is not specified, the module path defaults to the current directory.

The java utility accepts a number of options, some of which are described in the following sections.

USING SOURCE-FILE MODE TO LAUNCH SINGLE-FILE SOURCE-CODE PROGRAMS

You can run a single-file source code program without explicitly compiling it first. For example, consider the following file named Hello.java:

public class Hello {
    public static void main(String[] args) {
        System.out.println("Hello, world!");
    }
}

You can compile and run this file with the following command:

java Hello.java

The output of this command should be:

Hello, world!

This feature is available starting from Java 11.

USING THE JDK_JAVA_OPTIONS LAUNCHER ENVIRONMENT VARIABLE

The java launcher supports a JDK_JAVA_OPTIONS environment variable. This variable can be used to set Java VM options in a convenient way. For example, to enable debug options by default, you can set the following environment variable:

export JDK_JAVA_OPTIONS=“-agentlib:jdwp=transport=dt_socket,server=y,suspend=n”

In this case, the Java application will be started with the debug options enabled by default. The options specified on the command line will override the options specified in the environment variable.

This feature is available starting from Java 11.

ADVANCED OPTIONS FOR JAVA

The following options are advanced options. Use them with caution.

Creating a Static CDS Archive File with -XX:SharedArchiveFile

This section describes how to create a static CDS (Class Data Sharing) archive file. CDS allows the JVM to share common class data between multiple Java processes, potentially improving startup time and reducing memory footprint.

The following steps demonstrate how to create a static CDS archive file named hello.jsa.

1.
Create a static CDS archive file that contains the classes in hello.jar:

java -XX:ArchiveClassesAtExit=hello.jsa -cp hello.jar test.Hello

2.
Run the application test.Hello with the shared archive hello.jsa:

java -XX:SharedArchiveFile=hello.jsa -cp hello.jar -Xlog:class+load test.Hello

The output of this command should contain the following text:

[info][class,load] test.Hello source: shared objects file

Creating a Dynamic CDS Archive File with -XX:SharedArchiveFile

Advantages of dynamic CDS archives are:

•
They usually use less disk space, since they don't need to store the classes that are already in the static archive.
•
They are created with one fewer step than the comparable static archive.

The following steps create a dynamic CDS archive file that contains the classes that are used by the test.Hello application, excluding those that are already in the default CDS archive.

1.
Create a dynamic CDS archive, named hello.jsa, that contains all the classes in hello.jar loaded by the application test.Hello:

java -XX:ArchiveClassesAtExit=hello.jsa -cp hello.jar Hello

2.
Run the application test.Hello with the shared archive hello.jsa:

java -XX:SharedArchiveFile=hello.jsa -cp hello.jar test.Hello

3.
Optional Repeat step 4 of the previous section to verify that the test.Hello application is using the class contained in the hello.jsa shared archive.

It's also possible to create a dynamic CDS archive with a non-default static CDS archive. E.g.,

java -XX:SharedArchiveFile=base.jsa -XX:ArchiveClassesAtExit=hello.jsa -cp hello.jar Hello

To run the application using this dynamic CDS archive:

java -XX:SharedArchiveFile=base.jsa:hello.jsa -cp hello.jar Hello

(On Windows, the above path delimiter : should be replaced with ;)

As mention above, the name of the static archive can be skipped:

java -XX:SharedArchiveFile=hello.jsa -cp hello.jar Hello

Creating CDS Archive Files with jcmd

The previous two sections require you to modify the application's start-up script in order to create a CDS archive. Sometimes this could be difficult, for example, if the application's class path is set up by complex routines.

The jcmd VM.cds command provides a less intrusive way for creating a CDS archive by connecting to a running JVM process. You can create either a static:

jcmd <pid> VM.cds static_dump my_static_archive.jsa

or a dynamic archive:

jcmd <pid> VM.cds dynamic_dump my_dynamic_archive.jsa

To use the resulting archive file in a subsequent run of the application without modifying the application's start-up script, you can use the following technique:

env JAVA_TOOL_OPTIONS=-XX:SharedArchiveFile=my_static_archive.jsa bash app_start.sh

Note: to use jcmd <pid> VM.cds dynamic_dump, the JVM process identified by <pid> must be started with -XX:+RecordDynamicDumpInfo, which can also be passed to the application start-up script with the same technique:

env JAVA_TOOL_OPTIONS=-XX:+RecordDynamicDumpInfo bash app_start.sh

Restrictions on Class Path and Module Path

•
Neither the class path (-classpath and -Xbootclasspath/a) nor the module path (--module-path) can contain non-empty directories.
•
Only modular JAR files are supported in --module-path. Exploded modules are not supported.
•
The class path used at archive creation time must be the same as (or a prefix of) the class path used at run time. (There's no such requirement for the module path.)
•
The CDS archive cannot be loaded if any JAR files in the class path or module path are modified after the archive is generated.
•
If any of the VM options --upgrade-module-path, --patch-module or --limit-modules are specified, CDS is disabled. This means that the JVM will execute without loading any CDS archives. In addition, if you try to create a CDS archive with any of these 3 options specified, the JVM will report an error.

java -server -XX:+UseParallelGC -XX:+UseLargePages -Xmn10g  -Xms26g -Xmx26g

Tuning for Lower Response Time

Use the following commands and advanced options to achieve lower response times for your application:

java -XX:+UseG1GC -XX:MaxGCPauseMillis=100

Keeping the Java Heap Small and Reducing the Dynamic Footprint of

Embedded Applications

Use the following advanced runtime options to keep the Java heap small and reduce the dynamic footprint of embedded applications:

-XX:MaxHeapFreeRatio=10 -XX:MinHeapFreeRatio=5

Note: The defaults for these two options are 70% and 40% respectively. Because performance sacrifices can occur when using these small settings, you should optimize for a small footprint by reducing these settings as much as possible without introducing unacceptable performance degradation.
