JAIL.CONF(5) Configuration Fail2Ban JAIL.CONF(5)

NOM

jail.conf - configuration du serveur fail2ban

SYNOPIS

fail2ban.conf fail2ban.d/*.conf fail2ban.local fail2ban.d/*.local

jail.conf jail.d/*.conf jail.local jail.d/*.local

action.d/*.conf action.d/*.local action.d/*.py

filter.d/*.conf filter.d/*.local

DESCRIPTION

Fail2ban a quatre types de fichiers de configuration :

fail2ban.conf
Configuration globale de Fail2Ban (telle que la journalisation)
filter.d/*.conf
Filtres spécifiant comment détecter les échecs d'authentification
action.d/*.conf
Actions définissant les commandes pour bannir et débannir une adresse IP
jail.conf
Jails définissant des combinaisons de Filtres avec des Actions.

FORMAT DES FICHIERS DE CONFIGURATION

Les fichiers *.conf sont distribués par Fail2Ban. Il est recommandé de ne pas modifier les fichiers *.conf afin de faciliter les mises à niveau. Si nécessaire, les personnalisations doivent être fournies dans les fichiers *.local. Par exemple, si vous souhaitez activer la jail [ssh-iptables-ipset] spécifiée dans jail.conf, créez jail.local contenant

jail.local
[ssh-iptables-ipset]

enabled = true

Dans les fichiers .local, spécifiez uniquement les paramètres que vous souhaitez modifier et le reste de la configuration proviendra alors du fichier .conf correspondant qui est analysé en premier.

jail.d/ et fail2ban.d/

En plus de .local, pour le fichier jail.conf ou fail2ban.conf, il peut y avoir un répertoire .d/ correspondant contenant des fichiers .conf supplémentaires. L'ordre, par exemple pour la configuration de jail, serait :

jail.conf
jail.d/*.conf (par ordre alphabétique)
jail.local
jail.d/*.local (par ordre alphabétique).

c'est-à-dire que tous les fichiers .local sont analysés après les fichiers .conf dans le fichier de configuration original et les fichiers du répertoire .d. Les paramètres dans le fichier analysé plus tard prennent le dessus sur les entrées identiques dans les fichiers analysés précédemment. Les fichiers sont classés par ordre alphabétique, par exemple :

fail2ban.d/01_custom_log.conf - pour utiliser un chemin de journal différent

jail.d/01_enable.conf - pour activer une jail spécifique
jail.d/02_custom_port.conf - pour modifier le(s) port(s) d'une jail.

Les fichiers de configuration ont des sections, celles spécifiées avec [nom de section], et des paires nom = valeur. Pour les éléments nommés qui peuvent accepter plusieurs valeurs, spécifiez les valeurs séparées par des espaces, ou sur des lignes séparées avec une indentation par un espace au début de la ligne avant la deuxième valeur.

Les fichiers de configuration peuvent inclure d'autres fichiers de configuration (définissant des variables communes), ce qui est souvent utilisé dans les Filtres et les Actions. Ces inclusions sont définies dans une section appelée [INCLUDES] :

avant
indique que le fichier spécifié doit être analysé avant le fichier actuel.
après
indique que le fichier spécifié doit être analysé après le fichier actuel.

En utilisant les mécanismes d'« interpolation de chaînes » de Python, d'autres définitions sont autorisées et peuvent ensuite être utilisées dans d'autres définitions sous la forme %(nom)s.

Fail2ban a une syntaxe plus avancée (similaire à l'interpolation étendue de Python). Cette interpolation étendue utilise %(section/paramètre)s pour désigner une valeur d'une section étrangère.
En plus de l'interpolation inter-sections, la valeur du paramètre dans la section [DEFAULT] peut être récupérée avec %(default/paramètre)s.
Fail2ban prend également en charge une autre fonctionnalité nommée %(connu/paramètre)s (signifie la dernière option connue avec le nom paramètre). Cette interpolation permet d'étendre une regexp de filtre ou de jail d'origine dans le fichier .local (par opposition à la simple définition de failregex/ignoreregex qui la remplace), par exemple :

baduseragents = IE|wget|%(my-settings/baduseragents)s
failregex = %(known/failregex)s
            useragent=%(baduseragents)s

En plus de l'interpolation %(known/parameter)s, qui ne fonctionne pas pour les paramètres d'initialisation de filtre/action, une balise d'interpolation <known/parameter> peut être utilisée (signifie la dernière définition d'initialisation connue des filtres ou actions nommés parameter). Cette interpolation permet d'étendre les paramètres d'un filtre ou d'une action d'origine directement dans la jail dans le fichier jail.conf/jail.local sans créer de fichier filter.d/*.local séparé, par exemple :

# filter.d/test.conf : 
[Init]
test.method = GET
baduseragents = IE|wget
[Definition]
failregex = ^%(__prefix_line)\s+"<test.method>"\s+test\s+regexp\s+-\s+useragent=(?:<baduseragents>)
# jail.local :
[test]
# utilise le filtre "test", remplace la méthode par "POST" et étend les agents bannis connus avec "badagent" :
filter = test[test.method=POST, baduseragents="badagent|<known/baduseragents>"]

Commentaires : utilisez '#' pour les lignes de commentaire et '; ' (l'espace est important) pour les commentaires en ligne.

FICHIER(S) DE CONFIGURATION DE FAIL2BAN (fail2ban.conf)

Les éléments qui peuvent être définis dans la section [Definition] sont :

loglevel
niveau de verbosité de la sortie du journal : CRITICAL, ERROR, WARNING, NOTICE, INFO, DEBUG, TRACEDEBUG, HEAVYDEBUG ou valeur numérique correspondante (50-5). Par défaut : INFO (égal à 20)
logtarget
cible du journal : nom de fichier, SYSLOG, STDERR ou STDOUT. Par défaut : STDOUT si non défini dans fail2ban.conf/fail2ban.local
Note. Si fail2ban s'exécute en tant que service systemd, pour écrire dans le journal systemd, logtarget peut être défini sur STDOUT
Une seule cible de journal peut être spécifiée. Si vous modifiez logtarget par rapport à la valeur par défaut et que vous utilisez logrotate, ajustez ou désactivez également la rotation dans le fichier de configuration correspondant (par exemple, /etc/logrotate.d/fail2ban sur les systèmes Debian).
socket
nom de fichier du socket. Par défaut : /var/run/fail2ban/fail2ban.sock
Ceci est utilisé pour la communication avec le démon serveur fail2ban. Ne supprimez pas ce fichier lorsque Fail2ban est en cours d'exécution. Il ne sera alors plus possible de communiquer avec le serveur.
pidfile
nom de fichier PID. Par défaut : /var/run/fail2ban/fail2ban.pid
Ceci est utilisé pour stocker l'identifiant du processus du serveur fail2ban.
allowipv6
option pour autoriser l'interface IPv6 - auto, yes (on, true, 1) ou no (off, false, 0). Par défaut : auto
Cette valeur peut être utilisée pour déclarer à fail2ban si l'IPv6 est autorisé ou non.
dbfile
nom de fichier de la base de données. Par défaut : /var/lib/fail2ban/fail2ban.sqlite3
Ceci définit où sont stockées les données persistantes pour fail2ban. Ces données persistantes permettent de rétablir les bannissements et de continuer à lire les fichiers journaux depuis la dernière position lue lorsque fail2ban est redémarré. Une valeur de None désactive cette fonctionnalité.
dbmaxmatches
Nombre maximum de correspondances stockées dans la base de données par ticket. Par défaut : 10
Cette option définit le nombre maximum de lignes de journaux correspondantes qui peuvent être stockées par ticket dans la base de données. Cela affecte également les valeurs résolubles via les balises <ipmatches> et <ipjailmatches> dans les actions.
dbpurgeage
Âge de purge de la base de données en secondes. Par défaut : 86400 (24 heures)
Ceci définit l'âge auquel les bannissements doivent être purgés de la base de données.

Les paramètres de configuration de la section [Thread] sont :

Ce site n'est en aucun cas associé à Arch Linux ni affilié à ce projet. Le contenu est uniquement une traduction des pages de manuel d'Arch publiées sur man.archlinux.org.

stacksize
Taille de la pile de chaque thread dans fail2ban. Par défaut : 0 (plateforme ou valeur par défaut configurée)
Ceci spécifie la taille de la pile (en Kio) à utiliser pour les threads créés ultérieurement, et doit être 0 ou un entier positif d'au moins 32.

FICHIER(S) DE CONFIGURATION DE JAIL (jail.conf)

Les options suivantes s'appliquent à n'importe quelle jail. Elles apparaissent dans une section spécifiant le nom de la jail ou dans la section [DEFAULT] qui définit les valeurs par défaut à utiliser si elles ne sont pas spécifiées dans la section individuelle.

filter
nom du filtre -- nom du fichier du filtre dans /etc/fail2ban/filter.d/ sans l'extension .conf/.local.
Un seul filtre peut être spécifié.
logpath
nom(s) de fichier(s) des journaux à surveiller, séparés par des retours à la ligne.
Les caractères génériques -- chemins contenant * et ? ou [0-9] -- peuvent être utilisés, cependant seuls les fichiers qui existent au démarrage et qui correspondent à ce modèle de caractères génériques seront considérés.

L'option facultative 'tail', séparée par un espace, peut être ajoutée à la fin du chemin pour que le fichier journal soit lu par la fin, sinon l'option par défaut 'head' lit le fichier depuis le début.

Assurez-vous que syslog ou le programme qui génère le fichier journal n'est pas configuré pour compresser les messages de journal répétés à "*dernier message répété 5 fois*", sinon il ne pourra pas les détecter. Ceci s'appelle RepeatedMsgReduction dans rsyslog et devrait être Off.

logencoding
encodage des fichiers journaux utilisé pour le décodage. La valeur par défaut "auto" utilise la locale actuelle du système.
logtimezone
forcer le fuseau horaire pour les lignes de journal qui n'en ont pas.

Si cette option n'est pas spécifiée, les lignes de journal pour lesquelles aucun fuseau horaire explicite n'a été trouvé sont interprétées par fail2ban dans son propre fuseau horaire système, ce qui peut s'avérer inapproprié. Bien que la meilleure pratique soit de configurer les applications surveillées pour inclure des décalages explicites, cette option est destinée à gérer les cas où cela n'est pas possible.

Les fuseaux horaires pris en charge dans cette option sont ceux avec un décalage fixe : Z, UTC[+-]hhmm (vous pouvez également utiliser GMT comme alias pour UTC).

Cette option n'a aucun effet sur les lignes de journal pour lesquelles un fuseau horaire explicite a été trouvé. Exemples :

        logtimezone = UTC
        logtimezone = UTC+0200
        logtimezone = GMT-0100
banaction
action de bannissement (par défaut iptables-multiport) généralement spécifiée dans la section [DEFAULT] pour toutes les jails.
Ce paramètre sera utilisé par la substitution standard de action et peut être redéfini centralement dans la section [DEFAULT] à l'intérieur de jail.local (pour l'appliquer à toutes les jails à la fois) ou séparément dans chaque jail, où cette substitution sera utilisée.
banaction_allports
identique à banaction mais pour certaines jails "allports" comme "pam-generic" ou "recidive" (par défaut iptables-allports).
action
action(s) de /etc/fail2ban/action.d/ sans l'extension .conf/.local.
Des arguments peuvent être passés aux actions pour remplacer les valeurs par défaut de la section [Init] du fichier d'action. Les arguments sont spécifiés par :

[name=value,name2=value,name3="values,values"]

Les valeurs peuvent également être mises entre guillemets (requis lorsque la valeur inclut une ","). Plus d'une action peuvent être spécifiées (sur des lignes séparées).
ignoreself
valeur booléenne (par défaut true) indiquant que le bannissement des propres adresses IP doit être évité
ignoreip
liste d'IP à ne pas bannir. Elles peuvent inclure une réponse DNS ou un masque CIDR. L'option affecte en plus de ignoreself (si true) et n'a pas besoin de contenir la réponse DNS propre ou les IPs de l'hôte en cours d'exécution.
ignorecommand
commande exécutée pour déterminer si l'IP candidate actuelle au bannissement (ou l'ID d'échec pour les IDs bruts) ne devrait pas être bannie. Cette option fonctionne parallèlement aux options ignoreself et ignoreip. Elle est exécutée en premier, uniquement si ni ignoreself ni ignoreip ne correspondent aux critères.
L'IP ne sera pas bannie si la commande retourne un succès (code de sortie 0). Comme pour les FICHIERS D'ACTION, les balises comme <ip> peuvent être incluses dans la valeur de ignorecommand et seront substituées avant l'exécution.
ignorecache
fournit des paramètres de cache (par défaut désactivé) pour la vérification des échecs d'ignorance (mise en cache du résultat de ignoreip, ignoreself et ignorecommand), syntaxe : 
        ignorecache = key="<F-USER>@<ip-host>", max-count=100, max-time=5m
        ignorecommand = if [ "<F-USER>" = "technical" ] && [ "<ip-host>" = "my-host.example.com" ]; then exit 0; fi;
                        exit 1
Ceci mettra en cache le résultat de ignorecommand (ne l'appellera pas de manière répétée) pendant 5 minutes (temps de cache) pour un maximum de 100 entrées (taille du cache), en utilisant les valeurs substituées comme "utilisateur@hôte" comme clés de cache. Définir l'option ignorecache sur une valeur vide désactive le cache.
bantime
durée effective du bannissement (en secondes ou format d'abréviation de temps).
findtime
intervalle de temps (en secondes ou format d'abréviation de temps) avant l'heure actuelle pendant lequel les échecs compteront pour un bannissement.
maxretry
nombre d'échecs qui doivent se produire dans les dernières findtime secondes pour bannir l'IP.
backend
backend à utiliser pour détecter les modifications dans le logpath.
Par défaut, c'est "auto" qui essaiera "pyinotify", "systemd" avant "polling". L'un de ceux-ci peut être spécifié. "pyinotify" n'est valide que sur les systèmes Linux avec les bibliothèques Python "pyinotify".
usedns
utilise le DNS pour résoudre les noms d'hôtes qui apparaissent dans les journaux. Par défaut, c'est "warn" qui résoudra les noms d'hôtes en IPs, mais il enregistrera également un avertissement. Si vous utilisez le DNS ici, vous pourriez bannir les mauvaises IPs en raison de la nature asymétrique du DNS inversé (que l'application a utilisé pour écrire le nom de domaine dans le journal) par rapport au DNS direct que fail2ban utilise pour le résoudre en une IP (mais pas nécessairement la même). Idéalement, vous devriez configurer vos applications pour enregistrer une vraie IP. Ceci peut être réglé sur "yes" pour éviter les avertissements dans le journal ou "no" pour désactiver complètement la résolution DNS (ignorant ainsi les entrées où le nom d'hôte, et non une IP, est enregistré)..
prefregex
regex (expression régulière Python) pour analyser une partie commune contenue dans chaque message (voir prefregex dans la section FILTER FILES pour les détails).
failregex
regex (expression régulière Python) à ajouter aux failregexes du filtre (voir failregex dans la section FILTER FILES pour les détails). Si cela est utile à d'autres utilisateurs de votre application, veuillez partager votre expression régulière avec les développeurs de fail2ban en signalant un problème (voir SIGNALEMENT DE BUGS ci-dessous).
ignoreregex
regex qui, si la ligne de journal correspond, empêcherait Fail2Ban de considérer cette ligne. Cette ligne sera ignorée même si elle correspond à une failregex de la jail ou à l'un de ses filtres.
maxmatches
nombre maximum de lignes de journal correspondantes que la jail conservera en mémoire par ticket. Par défaut, c'est la même valeur que maxretry de la jail (ou la valeur par défaut). Cette option affecte également les valeurs résolubles via la balise <matches> dans les actions.

Backends

Les options disponibles sont listées ci-dessous.

pyinotify
nécessite que pyinotify (un moniteur de modification de fichier) soit installé. Si pyinotify n'est pas installé, Fail2ban utilisera auto.
polling
utilise un algorithme de sondage qui ne nécessite pas de bibliothèques externes.
systemd
utilise la bibliothèque Python systemd pour accéder au journal systemd. La spécification de logpath n'est pas valide pour ce backend et utilise à la place journalmatch de la configuration du filtre associée aux jails. Plusieurs indicateurs spécifiques à systemd peuvent être passés au backend, y compris journalpath et journalfiles, pour définir explicitement le chemin d'un répertoire ou d'un ensemble de fichiers. journalflags, qui par défaut est 4 et exclut les fichiers de session utilisateur, peut être défini pour les inclure avec journalflags=1, voir la documentation python-systemd pour d'autres paramètres et détails supplémentaires. Exemples :
backend = systemd[journalpath=/run/log/journal/machine-1]
backend = systemd[journalfiles="/path/to/system.journal, /path/to/user.journal"]
backend = systemd[journalflags=1]

Actions

Chaque jail peut être configurée avec un seul filtre, mais peut avoir plusieurs actions. Par défaut, le nom d'une action est le nom du fichier d'action, et dans le cas des actions Python, l'extension de fichier ".py" est supprimée. Lorsque plusieurs actions identiques doivent être utilisées, l'option actname peut être assignée à l'action pour éviter les duplications, par exemple :
