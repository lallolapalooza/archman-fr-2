-d directory
Définit le répertoire de destination (ou répertoire de sortie des classes) pour les fichiers de classe. Si une classe fait partie d'un package, javac place le fichier de classe dans un sous-répertoire qui reflète le nom du module (si approprié) et le nom du package. Le répertoire, ainsi que tous les sous-répertoires nécessaires, seront créés s'ils n'existent pas déjà.

Si l'option -d n'est pas spécifiée, javac place chaque fichier de classe dans le même répertoire que le fichier source à partir duquel il a été généré.

Sauf lors de la compilation de code pour plusieurs modules, le contenu du répertoire de sortie des classes sera organisé selon une hiérarchie de packages. Lors de la compilation de code pour plusieurs modules, le contenu du répertoire de sortie sera organisé selon une hiérarchie de modules, avec le contenu de chaque module dans un sous-répertoire séparé, chacun organisé comme une hiérarchie de packages.

Note : Lors de la compilation de code pour un ou plusieurs modules, le répertoire de sortie des classes sera automatiquement vérifié lors de la recherche des classes précédemment compilées. Lorsque vous ne compilez pas pour des modules, pour des raisons de compatibilité descendante, le répertoire n'est *pas* automatiquement vérifié pour les classes précédemment compilées, il est donc recommandé de spécifier le répertoire de sortie des classes comme l'un des emplacements du classpath de l'utilisateur, en utilisant l'option --class-path ou l'une de ses formes alternatives.

-Xdoclint
Active les vérifications recommandées pour les problèmes dans les commentaires de documentation.
-Xdoclint:(all|none|[-]group)[/access]
Active ou désactive des groupes de vérifications spécifiques dans les commentaires de documentation.

group peut avoir l'une des valeurs suivantes : accessibility, html, missing, reference, syntax.

La variable access spécifie le niveau de visibilité minimum des classes et des membres que l'option -Xdoclint vérifie. Elle peut avoir l'une des valeurs suivantes (par ordre de visibilité la plus élevée à la plus faible) : public, protected, package, private.

Le niveau access par défaut est private.

Lorsqu'ils sont préfixés par doclint:, les noms de group et all peuvent être utilisés avec @SuppressWarnings pour supprimer les avertissements concernant les commentaires de documentation dans les parties du code en cours de compilation.

Pour plus d'informations sur ces groupes de vérifications, consultez la section DocLint de la documentation de la commande javadoc. L'option -Xdoclint est désactivée par défaut dans la commande javac.

Par exemple, l'option suivante vérifie les classes et les membres (avec tous les groupes de vérifications) ayant le niveau d'accès protected et supérieur (ce qui inclut protected et public) :

-Xdoclint:all/protected

L'option suivante active tous les groupes de vérifications pour tous les niveaux d'accès, sauf qu'elle ne vérifiera pas les erreurs HTML pour les classes et les membres ayant le niveau d'accès package et supérieur (ce qui inclut package, protected et public) :

-Xdoclint:all,-html/package

-Xdoclint/package:[-]packages(,[-]package)*
Active ou désactive les vérifications dans des packages spécifiques. Chaque package est soit le nom qualifié d'un package, soit un préfixe de nom de package suivi de .*, qui s'étend à tous les sous-packages du package donné. Chaque package peut être préfixé par un tiret (-) pour désactiver les vérifications pour un package ou des packages spécifiés.

Pour plus d'informations, consultez la section DocLint de la documentation de la commande javadoc.

L'exigence de codage pour la variable d'environnement est la même que pour la ligne de commande javac sur le système. Le contenu de la variable d'environnement JDK_JAVAC_OPTIONS est traité de la même manière que celui spécifié sur la ligne de commande.

Cependant, comme pour les fichiers @fichiers, l'utilisation d'un caractère générique n'est pas prise en charge.

Exemples de mise entre guillemets d'arguments contenant des espaces :

export JDK_JAVAC_OPTIONS='@"C:\espaces blancs\fichier_args"'

export JDK_JAVAC_OPTIONS='"@C:\espaces blancs\fichier_args"'

export JDK_JAVAC_OPTIONS='@C:\"espaces blancs\"\fichier_args'

FICHIERS ARGUMENTS DE LIGNE DE COMMANDE

Un fichier d'arguments peut inclure des options de ligne de commande et des noms de fichiers source dans n'importe quelle combinaison. Les arguments dans un fichier peuvent être séparés par des espaces ou des caractères de nouvelle ligne. Si un nom de fichier contient des espaces intégrés, mettez le nom de fichier entier entre guillemets doubles.

Les noms de fichiers dans un fichier d'arguments sont relatifs au répertoire courant, et non à l'emplacement du fichier d'arguments. Les caractères génériques (*) ne sont pas autorisés dans ces listes (par exemple, pour spécifier *.java). L'utilisation du signe arobase (@) pour interpréter récursivement les fichiers n'est pas prise en charge. Les options -J ne sont pas prises en charge car elles sont transmises au lanceur, qui ne prend pas en charge les fichiers d'arguments.

Lors de l'exécution de la commande javac, transmettez le chemin et le nom de chaque fichier d'arguments avec le caractère arobase (@) en préfixe. Lorsque la commande javac rencontre un argument commençant par le signe arobase (@), elle développe le contenu de ce fichier dans la liste des arguments.

ORGANISATION DU CODE SOURCE

Dans le langage Java, les classes et les interfaces peuvent être organisées en paquets, et les paquets peuvent être organisés en modules. javac s'attend à ce que l'organisation physique des fichiers source dans les répertoires du système de fichiers reflète l'organisation des classes en paquets et des paquets en modules.

Il est de convention largement adoptée que les noms de modules et de paquets commencent par une lettre minuscule, et que les noms de classes commencent par une lettre majuscule.

Organisation du code source pour un paquet

Lorsque les classes et les interfaces sont organisées en paquet, le paquet est représenté par un répertoire, et les sous-paquets éventuels sont représentés par des sous-répertoires.

Par exemple :

•
Le paquet p est représenté par un répertoire nommé p.
•
Le paquet p.q -- c'est-à-dire le sous-paquet q du paquet p -- est représenté par le sous-répertoire q du répertoire p. L'arborescence de répertoires représentant le paquet p.q est donc p\q sous Windows, et p/q sur les autres systèmes.
•
Le paquet p.q.r est représenté par l'arborescence de répertoires p\q\r (sous Windows) ou p/q/r (sur les autres systèmes).

Dans un direc

tory ou sous-répertoire, les fichiers .java représentent des classes et des interfaces dans le package ou sous-package correspondant.

Par exemple :

•
La classe X déclarée dans le package p est représentée par le fichier X.java dans le répertoire p.
•
La classe Y déclarée dans le package p.q est représentée par le fichier Y.java dans le sous-répertoire q du répertoire p.
•
La classe Z déclarée dans le package p.q.r est représentée par le fichier Z.java dans le sous-répertoire r de p\q (sous Windows) ou p/q (sur d'autres systèmes).

Dans certaines situations, il est commode de diviser le code en répertoires séparés, chacun structuré comme décrit ci-dessus, et la liste agrégée des répertoires spécifiés à javac.

Disposition du code source pour un module

Dans le langage Java, un module est un ensemble de packages conçus pour la réutilisation. En plus des fichiers .java pour les classes et interfaces, chaque module possède un fichier source appelé module-info.java qui :

1.
déclare le nom du module ;
2.
liste les packages exportés par le module (pour permettre la réutilisation par d'autres modules) ;
3.
liste les autres modules requis par le module (pour réutiliser leurs packages exportés).

Lorsque les packages sont organisés en un module, le module est représenté par un ou plusieurs répertoires représentant les packages du module, dont l'un contient le fichier module-info.java. Il peut être commode, mais ce n'est pas obligatoire, d'utiliser un seul répertoire, nommé d'après le module, pour contenir le fichier module-info.java aux côtés de l'arborescence de répertoires représentant les packages du module (c'est-à-dire la hiérarchie de packages décrite ci-dessus). La disposition exacte du code source pour un module est généralement dictée par les conventions adoptées par un environnement de développement (IDE) ou un système de build.

Par exemple :

•
Le module a.b.c peut être représenté par le répertoire a.b.c, sur tous les systèmes.
•
La déclaration du module est représentée par le fichier module-info.java dans le répertoire a.b.c.
•
Si le module contient le package p.q.r, alors le répertoire a.b.c contient l'arborescence p\q\r (sous Windows) ou p/q/r (sur d'autres systèmes).

L'environnement de développement peut prescrire une hiérarchie de répertoires entre le répertoire nommé pour le module et les fichiers source à lire par javac.

Par exemple :

•
Le module a.b.c peut être représenté par le répertoire a.b.c
•
La déclaration du module et les packages du module peuvent se trouver dans un sous-répertoire de a.b.c, tel que src\main\java (sous Windows) ou src/main/java (sur d'autres systèmes).

Configuration d'une compilation

Cette section décrit comment configurer javac pour effectuer une compilation de base.

Voir Configuration du système de modules pour des détails supplémentaires à utiliser lors de la compilation pour une version de la plateforme qui prend en charge les modules.

Fichiers source

•
Spécifiez les fichiers source à compiler sur la ligne de commande.

S'il n'y a pas d'erreurs de compilation, les fichiers de classe correspondants seront placés dans le répertoire de sortie.

Certains systèmes peuvent limiter la quantité d'informations que vous pouvez placer sur une ligne de commande ; pour contourner ces limites, vous pouvez utiliser des fichiers d'arguments.

Lors de la compilation de code pour des modules, vous pouvez également spécifier des fichiers source indirectement, en utilisant l'option --module ou -m.

Répertoire de sortie

•
Utilisez l'option -d pour spécifier un répertoire de sortie dans lequel placer les fichiers de classe compilés.

Celui-ci sera normalement organisé selon une hiérarchie de packages, à moins que vous ne compiliez du code source provenant de plusieurs modules, auquel cas il sera organisé selon une hiérarchie de modules.

Une fois la compilation terminée, si vous compilez un ou plusieurs modules, vous pouvez placer le répertoire de sortie sur le chemin des modules du lanceur Java ; sinon, vous pouvez placer le répertoire de sortie sur le chemin des classes du lanceur Java.

Code précompilé

Le code à compiler peut faire référence à des bibliothèques autres que celles fournies par la plateforme. Si c'est le cas, vous devez placer ces bibliothèques sur le chemin des classes ou le chemin des modules. Si le code de la bibliothèque n'est pas dans un module, placez-le sur le chemin des classes ; s'il est dans un module, placez-le sur le chemin des modules.

•
Utilisez l'option --class-path pour spécifier les bibliothèques à placer sur le chemin des classes. Les emplacements sur le chemin des classes doivent être organisés selon une hiérarchie de packages. Vous pouvez également utiliser des formes alternatives de l'option : -classpath ou -cp.
•
Utilisez l'option --module-path pour spécifier les bibliothèques à placer sur le chemin des modules. Les emplacements sur le chemin des modules doivent être soit des modules, soit des répertoires de modules. Vous pouvez également utiliser une forme alternative de l'option : -p.

Voir Configuration du système de modules pour savoir comment modifier la configuration par défaut des modules de bibliothèque.

Remarque : les options pour le chemin des classes et le chemin des modules ne sont pas mutuellement exclusives, bien qu'il ne soit pas courant de spécifier le chemin des classes lors de la compilation de code pour un ou plusieurs modules.

Fichiers source supplémentaires

Le code à compiler peut faire référence à des types dans des fichiers source supplémentaires qui ne sont pas spécifiés sur la ligne de commande. Si c'est le cas, vous devez placer ces fichiers source sur le chemin des sources ou le chemin des modules. Vous ne pouvez spécifier qu'une seule de ces options : si vous ne compilez pas de code pour un module, ou si vous compilez du code pour un seul module, utilisez le chemin des sources ; si vous compilez du code pour plusieurs modules, utilisez le chemin source des modules.

•
Utilisez l'option --source-path pour spécifier les emplacements des fichiers source supplémentaires qui peuvent être lus par javac. Les emplacements sur le chemin des sources doivent être organisés selon une hiérarchie de packages. Vous pouvez également utiliser une forme alternative de l'option : -sourcepath.
•
Utilisez l'option --module-source-path une ou plusieurs fois pour spécifier l'emplacement des fichiers source supplémentaires dans différents modules qui peuvent être lus par javac, ou lors de la compilation de fichiers source dans plusieurs modules. Vous pouvez soit spécifier les emplacements pour chaque module individuellement, soit organiser les fichiers source de manière à pouvoir spécifier tous les emplacements ensemble. Pour plus de détails, voir L'option de chemin source des modules.

Si vous souhaitez pouvoir faire référence à des types dans des fichiers source supplémentaires mais ne souhaitez pas qu'ils soient compilés, utilisez l'option -implicit.

Remarque : si vous compilez du code pour plusieurs modules, vous devez toujours spécifier un chemin source des modules, et tous les fichiers source spécifiés sur la ligne de commande doivent se trouver dans l'un des répertoires du chemin source des modules, ou dans un sous-répertoire de ceux-ci.

CONFIGURING THE MODULE SYSTEM

If you want to include additional modules in your compilation, use the --add-modules option. This may be necessary when you are compiling code that is not in a module, or which is in an automatic module, and the code refers to API in the additional modules.

If you want to restrict the set of modules in your compilation, use the --limit-modules option. This may be useful if you want to ensure that the code you are compiling is capable of running on a system with a limited set of modules installed.

If you want to break encapsulation and specify that additional packages should be considered as exported from a module, use the --add-exports option. This may be useful when performing white-box testing; relying on access to internal API in production code is strongly discouraged.

If you want to specify that additional packages should be considered as required by a module, use the --add-reads option. This may be useful when performing white-box testing; relying on access to internal API in production code is strongly discouraged.

You can patch additional content into any module using the --patch-module option. See [Patching a Module] for more details.

SEARCHING FOR MODULE, PACKAGE AND TYPE DECLARATIONS

To compile a source file, the compiler often needs information about a module or type, but the declaration is not in the source files specified on the command line.

javac needs type information for every class or interface used, extended, or implemented in the source file. This includes classes and interfaces not explicitly mentioned in the source file, but that provide information through inheritance.

For example, when you create a subclass of java.awt.Window, you are also using the ancestor classes of Window: java.awt.Container, java.awt.Component, and java.lang.Object.

When compiling code for a module, the compiler also needs to have available the declaration of that module.

A successful search may produce a class file, a source file, or both. If both are found, then you can use the -Xprefer option to instruct the compiler which to use.

If a search finds and uses a source file, then by default javac compiles that source file. This behavior can be altered with -implicit.

The compiler might not discover the need for some type information until after annotation processing completes. When the type information is found in a source file and no -implicit option is specified, the compiler gives a warning that the file is being compiled without being subject to annotation processing. To disable the warning, either specify the file on the command line (so that it will be subject to annotation processing) or use the -implicit option to specify whether or not class files should be generated for such source files.

The way that javac locates the declarations of those types depends on whether the reference exists within code for a module or not.

Searching Package Oriented Paths

When searching for a source or class file on a path composed of package oriented locations, javac will check each location on the path in turn for the possible presence of the file. The first occurrence of a particular file shadows (hides) any subsequent occurrences of like-named files. This shadowing does not affect any search for any files with a different name. This can be convenient when searching for source files, which may be grouped in different locations, such as shared code, platform-specific code and generated code. It can also be useful when injecting alternate versions of a class file into a package, to debugging or other instrumentation reasons. But, it can also be dangerous, such as when putting incompatible different versions of a library on the class path.

Searching Module Oriented Paths

Prior to scanning any module paths for any package or type declarations, javac will lazily scan the following paths and locations to determine the modules that will be used in the compilation.

•
The module source path (see the --module-source-path option)
•
The path for upgradeable modules (see the --upgrade-module-path option)
•
The system modules (see the --system option)
•
The user module path ( see the --module-path option)

For any module, the first occurrence of the module during the scan completely shadows (hides) any subsequent appearance of a like-named module. While locating the modules, javac is able to determine the packages exported by the module and to associate with each module a package oriented path for the contents of the module. For any previously compiled module, this path will typically be a single entry for either a directory or a file that provides an internal directory-like hierarchy, such as a JAR file. Thus, when searching for a type that is in a package that is known to be exported by a module, javac can locate the declaration directly and efficiently.

Searching for the Declaration of a Module

If the module has been previously compiled, the module declaration is located in a file named module-info.class in the root of the package hierarchy for the content of the module.

If the module is one of those currently being compiled, the module declaration will be either the file named module-info.class in the root of the package hierarchy for the module in the class output directory, or the file named module-info.java in one of the locations on the source path or one the module source path for the module.

Searching for the Declaration of a Type When the Reference is not in a Module

When searching for a type that is referenced in code that is not in a module, javac will look in the following places:

•
The platform classes (or the types in exported packages of the platform modules) (This is for compiled class files only.)
•
Types in exported packages of any modules on the module path, if applicable. (This is for compiled class files only.)
•
Types in packages on the class path and/or source path:
•
If both are specified, javac looks for compiled class files on the class path and for source files on the source path.
•
If the class path is specified, but not source path, javac looks for both compiled class files and source files on the class path.
•
If the class path is not specified, it defaults to the current directory.

When looking for a type on the class path and/or source path, if both a compiled class file and a source file are found, the most recently modified file will be used by default. If the source file is newer, it will be compiled and will may override any previously compiled version of the file. You can use the -Xprefer option to override the default behavior.

Searching for the Declaration of a Type When the Reference is in a Module

When searching for a type that is referenced in code in a module, javac will examine the declaration of the enclosing module to determine if the type is in a package that is exported from another module that is readable by the enclosing module. If so,

javac ira simplement et directement à la définition de ce module pour trouver la définition du type requis. À moins que le module ne soit un autre des modules en cours de compilation, javac ne recherchera que des fichiers de classes compilées. En d'autres termes, javac ne recherchera pas de fichiers source dans les modules de la plateforme ou les modules présents sur le chemin des modules.

Si le type référencé ne se trouve pas dans un autre module lisible, javac examinera le module en cours de compilation pour essayer de trouver la déclaration du type. javac recherchera la déclaration du type comme suit :

•
Fichiers sources spécifiés sur la ligne de commande, sur le chemin source ou sur le chemin source des modules.
•
Fichiers précédemment compilés dans le répertoire de sortie.

HIERARCHIES DE_REPERTOIRES

javac suppose généralement que les fichiers sources et les fichiers de classes compilées seront organisés dans une hiérarchie de répertoires du système de fichiers ou dans un type de fichier qui prend en charge une hiérarchie de répertoires interne, tel qu'un fichier JAR. Trois types de hiérarchies sont pris en charge : une hiérarchie de paquets, une hiérarchie de modules et une hiérarchie de sources de modules.

Bien que javac soit assez souple quant à l'organisation du code source, au-delà de l'attente que le code source soit organisé en une ou plusieurs hiérarchies de paquets, et puisse généralement s'adapter aux organisations prescrites par les environnements de développement et les outils de build, les outils Java en général, et javac et le lanceur Java en particulier, sont plus stricts concernant l'organisation des fichiers de classes compilées, et ceux-ci seront organisés en hiérarchies de paquets ou en hiérarchies de modules, selon le cas.

L'emplacement de ces hiérarchies est spécifié à javac via des options de ligne de commande, dont les noms se terminent généralement par « path », comme --source-path ou --class-path. De plus, par règle générale, les options de chemin dont le nom inclut le mot module, comme --module-path, sont utilisées pour spécifier les hiérarchies de modules, bien que certaines options de chemin liées aux modules permettent de spécifier une hiérarchie de paquets par module. Toutes les autres options de chemin sont utilisées pour spécifier les hiérarchies de paquets.

HIERARCHIE DE_PAQUETS

Dans une hiérarchie de paquets, les répertoires et sous-répertoires sont utilisés pour représenter les parties composantes du nom du paquet, le fichier source ou le fichier de classe compilé pour un type étant stocké sous forme de fichier avec une extension .java ou .class dans le répertoire le plus imbriqué.

Par exemple, dans une hiérarchie de paquets, le fichier source d'une classe com.example.MyClass sera stocké dans le fichier com/example/MyClass.java

HIERARCHIE DE_MODULES

Dans une hiérarchie de modules, le premier niveau de répertoires est nommé pour les modules de la hiérarchie ; à l'intérieur de chacun de ces répertoires, le contenu du module est organisé en hiérarchies de paquets.

Par exemple, dans une hiérarchie de modules, le fichier de classe compilé d'un type appelé com.example.MyClass dans un module appelé my.library sera stocké dans my.library/com/example/MyClass.class.

Les différents répertoires de sortie utilisés par javac (le répertoire de sortie des classes, le répertoire de sortie des sources, et le répertoire de sortie des en-têtes natifs) seront tous organisés en une hiérarchie de modules lorsque plusieurs modules sont compilés.

HIERARCHIE SOURCE_DES_MODULES

Bien que les sources de chaque module individuel doivent toujours être organisées en une hiérarchie de paquets, il peut être pratique de regrouper ces hiérarchies dans une hiérarchie de sources de modules. Ceci est similaire à une hiérarchie de modules, sauf qu'il peut y avoir des répertoires intermédiaires entre le répertoire du module et le répertoire qui est la racine de la hiérarchie de paquets pour le code source du module.

Par exemple, dans une hiérarchie de sources de modules, le fichier source d'un type appelé com.example.MyClass dans un module appelé my.library peut être stocké dans un fichier tel que my.library/src/main/java/com/example/MyClass.java.

L_OPTION_MODULE_SOURCE_PATH

L'option --module-source-path a deux formes : une forme spécifique au module, dans laquelle un chemin de paquet est donné pour chaque module contenant du code à compiler, et une forme modèle de module, dans laquelle le chemin source de chaque module est spécifié par un modèle. La forme spécifique au module est généralement plus simple à utiliser lorsqu'un petit nombre de modules sont impliqués ; la forme modèle de module peut être plus pratique lorsque le nombre de modules est important et que les modules sont organisés de manière régulière qui peut être décrite par un modèle.

Plusieurs instances de l'option --module-source-path peuvent être fournies, chacune utilisant soit la forme modèle de module, soit la forme spécifique au module, sous réserve des limitations suivantes :

•
la forme modèle de module ne peut être utilisée qu'une seule fois
•
la forme spécifique au module ne peut être utilisée qu'une seule fois pour un module donné

Si la forme spécifique au module est utilisée pour un module quelconque, le chemin de recherche associé remplace tout chemin qui aurait pu être déduit de la forme modèle de module.

Forme spécifique au module

La forme spécifique au module permet de donner un chemin de recherche explicite pour tout module spécifique. Cette forme est :

•
--module-source-path nom-module=chemin-fichier (séparateur-chemin chemin-fichier)*

Le caractère séparateur de chemin est ; sous Windows, et : sinon.

Note : ceci est similaire à la forme utilisée pour l'option --patch-module.

Forme modèle de module

La forme modèle de module permet une spécification concise du chemin source des modules pour un nombre quelconque de modules organisés de manière régulière.

•
--module-source-path modèle

Le modèle est défini par les règles suivantes, qui sont appliquées dans l'ordre :

•
L'argument est considéré comme une série de segments séparés par le caractère séparateur de chemin (; sous Windows, et : sinon).
•
Chaque segment contenant des accolades de la forme
chaîne1{alt1 ( ,alt2 )* } chaîne2

est considéré comme étant remplacé par une série de segments formés par « l'expansion » des accolades :

chaîne1 alt1 chaîne2
chaîne1 alt2 chaîne2
et ainsi de suite...

Les accolades peuvent être imbriquées.

Cette règle est appliquée pour toutes les utilisations d'accolades.

•
Chaque segment doit contenir au plus un astérisque (*). Si un segment ne contient pas d'astérisque, il est considéré comme s'il était suivi d'un séparateur de fichier et d'un astérisque.

Pour tout module M, le chemin source de ce module est formé à partir de la série de segments obtenus en substituant le nom du module M à l'astérisque dans chaque segment.

Note : dans ce contexte, l'astérisque est juste utilisé comme marqueur spécial, pour indiquer la position dans le chemin du nom du module. Il ne doit pas être confondu avec l'utilisation de * comme caractère générique de nom de fichier, tel qu'on le trouve sur la plupart des systèmes d'exploitation.

PATCH_DES_MODULES

javac permet de patcher n'importe quel contenu, qu'il soit sous forme source ou compilée, dans n'importe quel module à l'aide de l'option --patch-module. Vous pourriez vouloir faire cela pour compiler des implémentations alternatives d'une classe à patcher au moment de l'exécution dans une JVM, ou pour injecter des classes supplémentaires dans le module, comme lors des tests.

La forme de l'option est :

•
--patch-module nom-module=chemin-fichier (séparateur-chemin chemin-fichier )*

Le caractère séparateur de chemin est ; sous Windows, et : sinon. Les chemins fournis pour le module doivent spécifier la racine d'une hiérarchie de paquets pour le contenu du module.

L'option peut être fournie au plus une fois pour un module donné. Tout contenu sur le chemin masquera tout contenu de même nom plus loin dans le chemin et dans le module patché.

Lors du patch de code source dans plusieurs modules, --module-source-path doit également être utilisé, de sorte que le répertoire de sortie soit organisé en une hiérarchie de modules, et capable de contenir les fichiers de classes compilées pour les modules en cours de compilation.

TRAITEMENT_DES_ANNOTATIONS

La commande javac offre un support direct pour le traitement des annotations.

L'API pour les processeurs d'annotations est définie dans les paquets javax.annotation.processing et javax.lang.model et leurs sous-paquets.

Comment_fonctionne_le_traitement_des_annotations

Le traitement des annotations est demandé en utilisant une option pour configurer le traitement des annotations, telle que -processor, --processor-path, --processor-module-path ou en activant explicitement le traitement avec les options -proc:full ou -proc:only. Le traitement des annotations est désactivé en utilisant l'option -proc:none.

Si le traitement des annotations est demandé, le compilateur recherche les processeurs d'annotations disponibles.

Le chemin de recherche peut être spécifié avec l'option -processorpath. Si aucun chemin n'est spécifié, alors le chemin de classes utilisateur est utilisé. Les processeurs sont localisés au moyen de fichiers de configuration de fournisseurs de services nommés META-INF/services/javax.annotation.processing.Processor sur le chemin de recherche. Ces fichiers doivent contenir les noms des processeurs d'annotations à utiliser, listés un par ligne. Alternativement, les processeurs peuvent être spécifiés explicitement, en utilisant l'option -processor.

Après avoir analysé les fichiers source et les classes sur la ligne de commande pour déterminer quelles annotations sont présentes, le compilateur interroge les processeurs pour déterminer quelles annotations ils traitent. Lorsqu'une correspondance est trouvée, le processeur est appelé. Un processeur peut revendiquer les annotations qu'il traite, auquel cas aucune autre tentative n'est faite pour trouver des processeurs pour ces annotations. Une fois toutes les annotations revendiquées, le compilateur ne recherche plus de processeurs supplémentaires.

Si des processeurs génèrent de nouveaux fichiers source, une autre ronde de traitement des annotations se produit : les nouveaux fichiers source générés sont analysés, et les annotations sont traitées comme auparavant. Tous les processeurs appelés lors des rondes précédentes sont également appelés lors de toutes les rondes ultérieures. Cela continue jusqu'à ce qu'aucun nouveau fichier source ne soit généré.

Après une ronde au cours de laquelle aucun nouveau fichier source n'est généré, les processeurs d'annotations sont appelés une dernière fois, pour leur donner une chance de terminer tout travail restant. Enfin, à moins que l'option -proc:only ne soit utilisée, le compilateur compile les fichiers source originaux et tous les fichiers source générés.

Si vous utilisez un processeur d'annotations qui génère des fichiers source supplémentaires à inclure dans la compilation, vous pouvez spécifier un module par défaut à utiliser pour les nouveaux fichiers générés, à utiliser lorsqu'une déclaration de module n'est pas également générée. Dans ce cas, utilisez l'option --default-module-for-created-files.

Environnement de compilation et environnement d'exécution.

Les déclarations dans les fichiers source et les fichiers de classes précédemment compilés sont analysées par javac dans un environnement de compilation distinct de l'environnement d'exécution utilisé pour exécuter javac lui-même. Bien qu'il y ait une similitude délibérée entre de nombreuses options javac et les options homonymes pour le lanceur Java, telles que --class-path, --module-path, etc., il est important de comprendre qu'en général, les options javac affectent uniquement l'environnement dans lequel les fichiers source sont compilés, et n'affectent pas le fonctionnement de javac lui-même.

La distinction entre l'environnement de compilation et l'environnement d'exécution est significative lorsqu'il s'agit d'utiliser des processeurs d'annotations. Bien que les processeurs d'annotations traitent les éléments (déclarations) qui existent dans l'environnement de compilation, le processeur d'annotations lui-même est exécuté dans l'environnement d'exécution. Si un processeur d'annotations a des dépendances sur des bibliothèques qui ne sont pas dans des modules, les bibliothèques peuvent être placées, avec le processeur d'annotations lui-même, sur le chemin du processeur. (Voir l'option --processor-path.) Si le processeur d'annotations et ses dépendances sont dans des modules, vous devriez utiliser le chemin des modules du processeur à la place. (Voir l'option --processor-module-path.) Lorsque ceux-ci sont insuffisants, il peut être nécessaire de fournir une configuration supplémentaire de l'environnement d'exécution. Cela peut être fait de deux manières :

1.
Si javac est invoqué depuis la ligne de commande, les options peuvent être passées à l'environnement d'exécution sous-jacent en préfixant l'option par -J.
2.
Vous pouvez démarrer une instance d'une machine virtuelle Java directement et utiliser des options de ligne de commande et une API pour configurer un environnement dans lequel javac peut être invoqué via l'une de ses API.

COMPILATION POUR LES VERSIONS ANTÉRIEURES DE LA PLATEFORME

javac peut compiler du code destiné à être utilisé sur d'autres versions de la plateforme, en utilisant soit l'option --release, soit les options --source/-source et --target/-target, avec des options supplémentaires pour spécifier les classes de la plateforme.

En fonction de la version de la plateforme souhaitée, certaines restrictions s'appliquent à certaines des options utilisables.

•
Lors de la compilation pour JDK 8 et les versions antérieures, vous ne pouvez pas utiliser d'option destinée à être utilisée avec le système de modules. Cela inclut toutes les options suivantes :
•
--module-source-path, --upgrade-module-path, --system, --module-path, --add-modules, --add-exports, --add-opens, --add-reads, --limit-modules, --patch-module

Si vous utilisez les options --source/-source ou --target/-target, vous devez également définir les classes de plateforme appropriées en utilisant la famille d'options de chemin de classes de démarrage.

•
Lors de la compilation pour JDK 9 et les versions ultérieures, vous ne pouvez pas utiliser d'option destinée à configurer le chemin des classes de démarrage. Cela inclut toutes les options suivantes :
•
-Xbootclasspath/p:, -Xbootclasspath, -Xbootclasspath/a:, -endorseddirs, -Djava.endorsed.dirs, -extdirs, -Djava.ext.dirs, -profile

Si vous utilisez les options --source/-source ou --target/-target, vous devez également définir les classes de plateforme appropriées en utilisant l'option --system pour indiquer l'emplacement d'une version installée appropriée de JDK.

Lors de l'utilisation de l'option --release, seule l'API documentée prise en charge pour cette version peut être utilisée ; vous ne pouvez utiliser aucune option pour briser l'encapsulation afin d'accéder à des classes internes.

API

Le compilateur javac peut être invoqué en utilisant une API de trois manières différentes :

La Java Compiler API
Celle-ci offre le moyen le plus flexible d'invoquer le compilateur, y compris la possibilité de compiler des fichiers source fournis dans des tampons en mémoire ou d'autres systèmes de fichiers non standard.
La ToolProvider API
Un ToolProvider pour javac peut être obtenu en appelant ToolProvider.findFirst("javac"). Ceci renvoie un objet avec des fonctionnalités équivalentes à l'outil en ligne de commande.

Note : Cette API ne doit pas être confondue avec l'API du même nom dans le package javax.tools.

La Legacy API de javac
Cette API est conservée uniquement pour des raisons de compatibilité ascendante. Tout nouveau code doit utiliser soit la Java Compiler API, soit la ToolProvider API.

Note : Toutes les autres classes et méthodes trouvées dans un package dont les noms commencent par com.sun.tools.javac (sous-packages de com.sun.tools.javac) sont strictement internes et sujettes à modification à tout moment.
