La fonctionnalité JAR permet d'empaqueter des fichiers de classes, des images, des sons et d'autres données numériques dans un fichier unique pour une distribution plus rapide et plus facile. Un outil nommé jar permet aux développeurs de produire des fichiers JAR. (Techniquement, tout fichier zip peut aussi être considéré comme un fichier JAR, bien que lorsque ceux-ci sont créés par la commande jar ou traités par la commande jarsigner, les fichiers JAR contiennent également un fichier META-INF/MANIFEST.MF.) Une signature numérique est une chaîne de bits calculée à partir de certaines données (les données étant signées) et de la clé privée d'une entité (une personne, une entreprise, etc.). De même qu'une signature manuscrite, une signature numérique possède de nombreuses caractéristiques utiles

:
•
Son authenticité peut être vérifiée par un calcul utilisant la clé publique correspondant à la clé privée utilisée pour générer la
signature.
•
Elle ne peut pas être contrefaite, à condition que la clé privée reste
secrète.
•
Elle est une fonction des données signées et ne peut donc pas être revendiquée comme étant la signature d'autres données
également.
•
Les données signées ne peuvent pas être modifiée
s. Si les données sont modifiées, la signat
ure ne peut pas être vérifiée comme authentique.

Pour générer la signature d'une entité pour un fichier, l'entité doit d'abord avoir une paire de clés publique/privée qui lui est associée et un ou plusieurs certificats qui authentifient sa clé publique. Un certificat est une déclaration signée numériquement par une entité qui indique que la clé publique d'une autre entité a une valeur

particulière.

La commande jarsigner utilise les informations de clé et de certificat d'un magasin de clés pour générer des signatures numériques pour les fichiers JAR. Un magasin de clés est une base de données de clés privées et de leurs chaînes de certificats X.509 associées qui authentifient les clés publiques correspondantes. La commande keytool est utilisée pour créer et administrer les magasins de

clés.

La commande jarsigner utilise la clé privée d'une entité pour générer une signature. Le fichier JAR signé contient, entre autres, une copie du certificat du magasin de clés pour la clé publique correspondant à la clé privée utilisée pour signer le fichier. La commande jarsigner peut vérifier la signature numérique du fichier JAR signé en utilisant le certificat qu'il contient (dans son fichier de bloc de signature)

.

La commande jarsigner peut générer des signatures qui incluent un horodatage permettant à un administrateur système ou de déploiement (y compris Java Plug-in) de vérifier si le fichier JAR a été signé alors que le certificat de signature était encore valide. De plus, des API permettent aux applications d'obtenir les informations

d'horodatage.

Pour l'instant, la commande jarsigner ne peut signer que les fichiers JAR créés par la commande jar ou les fichiers zip. Les fichiers JAR sont identiques aux fichiers zip, sauf qu'ils contiennent également un fichier META-INF/MANIFEST.MF. Un fichier META-INF/MANIFEST.MF est créé lorsque la commande jarsigner signe un fichier

zip.

Le comportement par défaut de la commande jarsigner est de signer un fichier JAR ou zip. Utilisez l'option -verify pour vérifier un fichier JAR

signé.

La commande jarsigner tente également de valider le certificat du signataire après la signature ou la vérification. S'il y a une erreur de validation ou tout autre problème, la commande génère des messages d'avertissement. Si vous spécifiez l'option -strict, la commande traite les avertissements graves comme des erreurs. Voir Erreurs et

avertissements.

CLÉS

La commande jarsigner a une option -keystore pour spécifier l'URL du magasin de clés à utiliser. Le magasin de clés est par défaut stocké dans un fichier nommé .keystore dans le répertoire personnel de l'utilisateur, tel que déterminé par la propriété système user.ho

Sur les systèmes Oracle Solaris, user.home correspond par défaut au répertoire personnel de

Le flux d'entrée de l'option -keystore est transmis à la méthode KeyStore.load. Si NONE est spécifié comme URL, un flux nul est transmis à la méthode KeyStore.load. NONE doit être spécifié lorsque la classe KeyStore n'est pas basée sur des fichiers, par exempl

e lorsqu'elle réside sur un
dispositif de jeton matériel.

IMPLÉMENTATION DU MAGASIN DE

CLÉS

La classe KeyStore fournie dans le paquet java.security fournit un certain nombre d'interfaces bien définies pour accéder et modifier les informations d'un magasin de clés. Vous pouvez avoir plusieurs implémentations concrètes différentes, où chaque implémentations est pour un type particulier de magasin de

clés.

Actuellement, il existe deux outils en ligne de commande qui utilisent des implémentations de magasin de clés (keytool et jarsigner), et un outil basé sur une interface graphique nommé Policy Tool. Comme la classe KeyStore est publiquement disponible, les utilisateurs du JDK peuvent écrire des applications de sécurité supplémentaires qui

l'utilisent.

Il existe une implémentation par défaut intégrée fournie par Oracle qui implémente le magasin de clés sous forme de fichier, qui utilise un type (format) de magasin de clés propriétaire nommé JKS. L'implémentation intégrée protège chaque clé privée avec son mot de passe individuel et protège l'intégrité de l'ensemble du magasin de clés avec un mot de passe (possiblement différent)

.

Les implémentations de magasin de clés sont basées sur des fournisseurs, ce qui signifie que les interfaces d'application fournies par la classe KeyStore sont implémentées en termes d'Interface de Fournisseur de Service (SPI). Il existe une classe abstraite correspondante KeystoreSpi, également dans le paquet java.security, qui définit les méthodes de l'Interface de Fournisseur de Service que les fournisseurs doivent implémenter. Le terme fournisseur fait référence à un paquet ou à un ensemble de paquets qui fournissent une implémentation concrète d'un sous-ensemble de services qui peuvent être accessibles via l'API de Sécurité Java. Pour fournir une implémentation de magasin de clés, les clients doivent implémenter un fournisseur et fournir une implémentation de sous-classe de KeystoreSpi, comme décrit dans Comment implémenter un fournisseur

GESTION DU MAGASIN DE CLÉS

L'architecture de chiffrement Java définit des types de magasins de clés, des fournisseurs et des formats de données spécifiques. La gestion des magasins de clés s'effectue au moyen de l'API KeyStore, qui est décrite plus en détail dans l'architecture de chiffrement Java à http://docs.oracle.com/javase/8/docs/technotes/guides/security/crypto/HowToImplAProvider.html

Les applications peuvent choisir différents types d'implémentations de magasins de clés auprès de différents fournisseurs, en utilisant la méthode usine getInstance de la classe KeyStore. Un type de magasin de clés définit le format de stockage et de données des informations du magasin de clés, ainsi que les algorithmes utilisés pour protéger les clés privées dans le magasin de clés et l'intégrité du magasin de clés lui-même. Les implémentations de magasins de clés de types différents ne sont pas compatibles.

La commande jarsigner peut lire des magasins de clés basés sur des fichiers depuis n'importe quel emplacement spécifiable à l'aide d'une URL. En outre, la commande peut lire des magasins de clés non basés sur des fichiers, tels que ceux fournis par MSCAPI sous Windows et PKCS11 sur toutes les plateformes.

Pour les commandes jarsigner et keytool, vous pouvez spécifier un type de magasin de clés en ligne de commande avec l'option -storetype. Pour Policy Tool, vous pouvez spécifier un type de magasin de clés avec la commande Edit dans le menu KeyStore.

Si vous ne spécifiez pas explicitement de type de magasin de clés, les outils choisissent une implémentation de magasin de clés en fonction de la valeur de la propriété keystore.type spécifiée dans le fichier de propriétés de sécurité. Le fichier de propriétés de sécurité s'appelle java.security et réside dans le répertoire des propriétés de sécurité du JDK, java.home/lib/security, où java.home est le répertoire de l'environnement d'exécution. Le répertoire jre dans le JDK ou le répertoire de niveau supérieur de l'environnement d'exécution Java (JRE).

Chaque outil récupère la valeur keystore.type, puis examine tous les fournisseurs installés jusqu'à ce qu'il en trouve un qui implémente des magasins de clés de ce type. Il utilise ensuite l'implémentation du magasin de clés de ce fournisseur.

La classe KeyStore définit une méthode statique nommée getDefaultType qui permet aux applications et aux applets de récupérer la valeur de la propriété keystore.type. La ligne de code suivante crée une instance du type de magasin de clés par défaut, tel que spécifié dans la propriété keystore.type :

KeyStore keyStore = KeyStore.getInstance(KeyStore.getDefaultType());

Le type de magasin de clés par défaut est jks (le type propriétaire de l'implémentation du magasin de clés fournie par Oracle). Ceci est spécifié par la ligne suivante dans le fichier de propriétés de sécurité :

keystore.type=jks

La casse n'a pas d'importance dans les désignations de type de magasin de clés. Par exemple, JKS est identique à jks.

Pour que les outils utilisent une implémentation de magasin de clés autre que celle par défaut, modifiez cette ligne pour spécifier un autre type de magasin de clés. Par exemple, si vous avez un package fournisseur qui fournit une implémentation de magasin de clés pour un type de magasin de clés appelé pkcs12, modifiez alors la ligne comme suit :

keystore.type=pkcs12

Note : Si vous utilisez le package fournisseur PKCS 11, consultez « KeyTool » et « JarSigner » dans le Guide de référence Java PKCS #11 à http://docs.oracle.com/javase/8/docs/technotes/guides/security/p11guide.html

ALGORITHMES SUPPORTÉS

Par défaut, la commande jarsigner signe un fichier JAR à l'aide de l'un des algorithmes suivants :

•
Algorithme de signature numérique (DSA) avec l'algorithme de hachage SHA1
•
Algorithme RSA avec l'algorithme de hachage SHA256
•
Algorithme de cryptographie à courbe elliptique (EC) avec l'algorithme de signature numérique ECDSA sur SHA256.

Si les clés publique et privée du signataire sont des clés DSA, jarsigner signe le fichier JAR avec l'algorithme SHA1withDSA. Si les clés du signataire sont des clés RSA, jarsigner tente de signer le fichier JAR avec l'algorithme SHA256withRSA. Si les clés du signataire sont des clés EC, jarsigner signe le fichier JAR avec l'algorithme SHA256withECDSA.

Ces algorithmes de signature par défaut peuvent être remplacés à l'aide de l'option -sigalg.

LE FICHIER JAR SIGNÉ

Lorsque la commande jarsigner est utilisée pour signer un fichier JAR, le fichier JAR signé de sortie est exactement le même que le fichier JAR d'entrée, à l'exception de deux fichiers supplémentaires placés dans le répertoire META-INF :

•
Un fichier de signature avec une extension .SF
•
Un fichier de bloc de signature avec une extension .DSA, .RSA ou .EC

Les noms de fichiers de base de ces deux fichiers proviennent de la valeur de l'option -sigFile. Par exemple, lorsque l'option est -sigFile MKSIGN, les fichiers sont nommés MKSIGN.SF et MKSIGN.DSA

Si aucune option -sigfile n'apparaît sur la ligne de commande, le nom de fichier de base des fichiers .SF et .DSA est les 8 premiers caractères du nom d'alias spécifié sur la ligne de commande, tous convertis en majuscules. Si le nom d'alias comporte moins de 8 caractères, le nom d'alias complet est utilisé. Si le nom d'alias contient des caractères non autorisés dans un nom de fichier de signature, chaque caractère est converti en un trait de soulignement (_) lors de la formation du nom de fichier. Les caractères valides incluent les lettres, les chiffres, les traits de soulignement et les tirets.

Fichier de signature

Un fichier de signature (fichier .SF) ressemble au fichier manifeste toujours inclus dans un fichier JAR lorsque la commande jarsigner est utilisée pour signer le fichier. Pour chaque fichier source inclus dans le fichier JAR, le fichier .SF comporte trois lignes, comme dans le fichier manifeste, qui répertorient les éléments suivants :

•
Nom du fichier
•
Nom de l'algorithme de hachage (SHA)
•
Valeur de hachage SHA

Dans le fichier manifeste, la valeur de hachage SHA pour chaque fichier source est le hachage (empreinte) des données binaires du fichier source. Dans le fichier .SF, la valeur de hachage pour un fichier source spécifié est le hachage des trois lignes du fichier manifeste pour ce fichier source.

Le fichier de signature, par défaut, inclut un en-tête avec un hachage de l'ensemble du fichier manifeste. L'en-tête contient également un hachage de l'en-tête du manifeste. La présence de l'en-tête permet l'optimisation de la vérification. Voir Vérification du fichier JAR.

Fichier de bloc de signature

Le fichier .SF est signé et la signature est placée dans le fichier de bloc de signature. Ce fichier contient également, encodé à l'intérieur, le certificat ou la chaîne de certificats du magasin de clés qui authentifie la clé publique correspondant à la clé privée utilisée pour la signature. Le fichier a l'extension .DSA, .RSA ou .EC, selon l'algorithme de hachage utilisé.

HORODATAGE DE SIGNATURE

La commande jarsigner peut générer et stocker un horodatage de signature lors de la signature d'un fichier JAR. De plus, jarsigner prend en charge les mécanismes de signature alternatifs. Ce comportement est facultatif et contrôlé par l'utilisateur au moment de la signature via ces options. Voir Options.

VÉRIFICATION DU FICHIER JAR

Une vérification réussie du fichier JAR se produit lorsque les signatures sont valides et qu'aucun des fichiers qui se trouvaient dans le fichier JAR lors de la génération des signatures n'a été modifié depuis. La vérification du fichier JAR implique les étapes suivantes :

1.
Vérifier la signature du fichier .SF.

La vérification garantit que la signature stockée dans chaque fichier de bloc de signature (.DSA) a été générée à l'aide de la clé privée correspondant à la clé publique dont le certificat (ou la chaîne de certificats) apparaît également dans le fichier .DSA. Elle garantit également que la signature est une signature valide du fichier de signature correspondant (.SF), et donc que le fichier .SF n'a pas été altéré.

2.
Vérifier le hachage répertorié dans chaque entrée du fichier .SF avec chaque section correspondante dans le manifeste.

Le fichier .SF inclut par défaut un en-tête contenant un hachage de l'ensemble du fichier manifeste. Lorsque l'en-tête est présent, la vérification peut déterminer si le hachage dans l'en-tête correspond ou non au hachage du fichier manifeste. S'il y a une correspondance, la vérification passe à l'étape suivante.

En l'absence de correspondance, une vérification moins optimisée est nécessaire pour garantir que le hachage dans chaque section d'informations de fichier source du fichier .SF est égal au hachage de sa section correspondante dans le fichier manifeste. Voir Fichier de signature.

L'une des raisons pour lesquelles le hachage du fichier manifeste stocké dans l'en-tête du fichier .SF pourrait ne pas correspondre au hachage du fichier manifeste actuel est que des fichiers ont été ajoutés au fichier JAR (avec l'outil jar) après la génération de la signature et du fichier .SF. Lorsque l'outil jar est utilisé pour ajouter des fichiers, le fichier manifeste est modifié en y ajoutant des sections pour les nouveaux fichiers, mais le fichier .SF n'est pas modifié. Une vérification est toujours considérée comme réussie lorsque aucun des fichiers qui se trouvaient dans le fichier JAR lors de la génération de la signature n'a été modifié depuis. Cela se produit lorsque les hachages des sections non-en-tête du fichier .SF correspondent aux hachages des sections correspondantes dans le fichier manifeste.

3.

Lire chaque fichier du JAR qui a une entrée dans le fichier .SF. Pendant la lecture, calculer le hachage du fichier et comparer le résultat avec le hachage de ce fichier dans la section du manifeste. Les hachages doivent être identiques, sinon la vérification échoue.

Si des échecs de vérification graves surviennent pendant le processus de vérification, le processus est arrêté et une exception de sécurité est levée. La commande jarsigner intercepte et affiche l'exception.

Note : Vous devez lire tous les avertissements supplémentaires (ou erreurs si vous avez spécifié l'option -strict), ainsi que le contenu du certificat (en spécifiant th

si la signatu

ERREURS ET

AVERTISSEMENTS

Lors du processus de signature ou de vérification, la commande jarsigner peut émettre diverses erreurs ou

avertissements.

En cas d'échec, la commande jarsigner se termine avec le code 1. S'il n'y a pas d'échec, mais qu'il y a un ou plusieurs avertissements graves, la commande jarsigner se termine avec le code 0 lorsque l'option -strict n'est pas spécifiée, ou se termine avec la valeur OU (OR) des codes d'avertissement lorsque l'option -strict est spécifiée. S'il n'y a que des avertissements informatifs ou aucun avertissement du tout, la commande se termine toujours avec le code

0.

Fopar exemple, si un certificat utilisé pour signer une entrée est expiré et a une extension KeyUsage qui ne lui permet pas de signer un fichier, la commande jarsigner se termine avec le code 12 (=4+8) lorsque l'option -strict est spécifiée.

Note : Les codes de sortie sont réutilisés car seules les valeurs de 0 à 255 sont autorisées sur les systèmes d'exploitation basés sur Unix.

Les sections suivantes décrivent les noms, codes et descriptions des erreurs et avertissements que la commande jarsigner peut émettre.

ERREURS

Les raisons pour lesquelles la commande jarsigner échoue incluent (sans s'y limiter) une erreur d'analyse de ligne de commande, l'incapacité de trouver une paire de clés pour signer le fichier JAR, ou l'échec de la vérification d'un fichier JAR signé.

échec
Code 1. La signature ou la vérification échoue.

EXEMPLES

SIGNER UN FICHIER JAR

Utilisez la commande suivante pour signer bundle.jar avec la clé privée d'un utilisateur dont l'alias de keystore est jane dans un keystore nommé mystore dans le répertoire working et nommer le fichier JAR signé sbundle.jar:

jarsigner -keystore /working/mystore
    -storepass <mot de passe du keystore>
    -keypass <mot de passe de la clé privée>
    -signedjar sbundle.jar bundle.jar jane

Aucun -sigfile n'est spécifié dans la commande précédente, donc les fichiers .SF et .DSA générés à placer dans le fichier JAR signé ont des noms par défaut basés sur le nom de l'alias. Ils sont nommés JANE.SF et JANE.DSA.

Si vous souhaitez être invité à entrer le mot de passe du magasin et le mot de passe de la clé privée, vous pouvez raccourcir la commande précédente comme suit :

jarsigner -keystore /working/mystore
    -signedjar sbundle.jar bundle.jar jane

Si le keystore est le keystore par défaut (.keystore dans votre répertoire personnel), vous n'avez pas besoin de spécifier de keystore, comme suit :

jarsigner -signedjar sbundle.jar bundle.jar jane

Si vous souhaitez que le fichier JAR signé écrase le fichier JAR d'entrée (bundle.jar), vous n'avez pas besoin de spécifier une option -signedjar, comme suit :

jarsigner bundle.jar jane

VÉRIFIER UN FICHIER JAR SIGNÉ

Pour vérifier un fichier JAR signé afin de s'assurer que la signature est valide et que le fichier JAR n'a pas été falsifié, utilisez une commande telle que la suivante :

jarsigner -verify sbundle.jar

Lorsque la vérification est réussie, jar verified est affiché. Sinon, un message d'erreur est affiché. Vous pouvez obtenir plus d'informations en utilisant l'option -verbose. Un exemple d'utilisation de jarsigner avec l'option -verbose suit :

jarsigner -verify -verbose sbundle.jar
