NOM

javadoc - Génère des pages HTML de documentation d'API à partir de fichiers source Java.

SYNOPSIS

javadoc {paquets|fichiers-source} [options] [@argfiles]
paquets
Noms des paquets que vous souhaitez documenter, séparés par des espaces, par exemple java.lang java.lang.reflect java.awt. Si vous souhaitez également documenter les sous-paquets, utilisez l'option -subpackages pour spécifier les paquets.

Par défaut, javadoc recherche les paquets spécifiés dans le répertoire courant et ses sous-répertoires. Utilisez l'option -sourcepath pour spécifier la liste des répertoires dans lesquels rechercher les paquets.

fichiers-source
Noms des fichiers source Java que vous souhaitez documenter, séparés par des espaces, par exemple Class.java Object.java Button.java. Par défaut, javadoc recherche les classes spécifiées dans le répertoire courant. Cependant, vous pouvez spécifier le chemin complet du fichier de classe et utiliser des caractères génériques, par exemple /home/src/java/awt/Graphics*.java. Vous pouvez également spécifier le chemin relatif au répertoire courant.
options
Options de ligne de commande, séparées par des espaces. Voir Options.
@argfiles
Noms des fichiers contenant une liste d'options de commande javadoc , de noms de paquets et de noms de fichiers source dans n'importe quel ordre.

DESCRIPTION

La commande javadoc analyse les déclarations et les commentaires de documentation dans un ensemble de fichiers source Java et produit un ensemble correspondant de pages HTML qui décrivent (par défaut) les classes publiques et protégées, les classes imbriquées (mais pas les classes internes anonymes), les interfaces, les constructeurs, les méthodes et les champs. Vous pouvez utiliser la commande javadoc pour générer la documentation d'API ou la documentation d'implémentation pour un ensemble de fichiers source.

Vous pouvez exécuter la commande javadoc sur des paquets entiers, des fichiers source individuels, ou les deux. Lors de la documentation de paquets entiers, vous pouvez soit utiliser l'option -subpackages pour parcourir récursivement un répertoire et ses sous-répertoires, soit passer une liste explicite de noms de paquets. Lorsque vous documentez des fichiers source individuels, passez une liste de noms de fichiers source Java. Voir Exemples simples.

TRAITEMENT DES FICHIERS SOURCE

La commande javadoc traite les fichiers se terminant par source et les autres fichiers décrits dans Fichiers source. Si vous exécutez la commande javadoc en passant des noms de fichiers source individuels, vous pouvez déterminer exactement quels fichiers source sont traités. Cependant, ce n'est pas la façon dont la plupart des développeurs souhaitent travailler, car il est plus simple de passer des noms de paquets. La commande javadoc peut être exécutée de trois manières sans spécifier explicitement les noms de fichiers source. Vous pouvez passer des noms de paquets, utiliser l'option -subpackages ou utiliser des caractères génériques avec les noms de fichiers source. Dans ces cas, la commande javadoc traite un fichier source uniquement lorsque le fichier remplit toutes les conditions suivantes :

•
Le préfixe du nom de fichier (avec .java supprimé) est un nom de classe valide.
•
Le chemin relatif à la racine de l'arborescence source est un nom de paquet valide après conversion des séparateurs en points.
•
L'instruction package contient le nom de paquet valide.

Traitement des liens

Lors d'une exécution, la commande javadoc ajoute des liens de référence croisée vers les noms de paquets, de classes et de membres qui sont documentés dans le cadre de cette exécution. Les liens apparaissent aux endroits suivants. Voir Balises Javadoc pour une description des balises @.

•
Déclarations (types de retour, types d'arguments et types de champs).
•
Sections Voir aussi générées à partir des balises @see .
•
Texte en ligne généré à partir des balises {@link} .
•
Noms d'exceptions générés à partir des balises @throws .
•
Liens Spécifié par vers les membres d'interface et liens Redéfini par vers les membres de classe. Voir Héritage des commentaires de méthode. vers les membres de classe. Voir Héritage des commentaires de méthode.
•
Tableaux récapitulatifs listant les paquets, les classes et les membres.
•
Arbres d'héritage des paquets et des classes.
•
L'index.

Vous pouvez ajouter des liens vers le texte existant pour les classes qui ne sont pas incluses dans la ligne de commande (mais générées séparément) au moyen des options -link et -linkoffline .

Détails du traitement

La commande javadoc produit un document complet à chaque exécution. Elle n'effectue pas de constructions incrémentielles qui modifient ou incorporent directement les résultats des exécutions précédentes. Cependant, la commande javadoc peut faire référence aux résultats d'autres exécutions.

L'implémentation de la commande javadoc nécessite et repose sur le compilateur Java. La commande javadoc appelle une partie de la commande javac pour compiler les déclarations et ignorer les implémentations des membres. La commande javadoc construit une représentation interne riche des classes qui inclut la hiérarchie des classes et les relations d'utilisation pour générer le HTML. La commande javadoc récupère également la documentation fournie par l'utilisateur à partir des commentaires de documentation dans le code source. Voir Commentaires de documentation.

La commande javadoc s'exécute sur des fichiers source qui sont de purs fichiers stub sans corps de méthode. Cela signifie que vous pouvez écrire des commentaires de documentation et exécuter la commande javadoc aux premiers stades de la conception avant l'implémentation de l'API.

S'appuyer sur le compilateur garantit que la sortie HTML correspond exactement à l'implémentation réelle, qui peut reposer sur du code source implicite plutôt qu'explicite. Par exemple, la commande javadoc documente les constructeurs par défaut qui sont présents dans les fichiers de classe compilés mais pas dans le code source.

Dans de nombreux cas, la commande javadoc vous permet de générer de la documentation pour des fichiers source contenant du code incomplet ou erroné. Vous pouvez générer la documentation avant que tout le débogage et le dépannage ne soient terminés. La commande javadoc effectue une vérification élémentaire des commentaires de documentation.

Lorsque la commande javadoc construit sa structure interne pour la documentation, elle charge toutes les classes référencées. En raison de cela, la commande javadoc doit être capable de trouver toutes les classes référencées, qu'il s'agisse de classes bootstrap, d'extensions ou de classes utilisateur. Voir Comment les classes sont trouvées sur http://docs.oracle.com/javase/8/docs/technotes/tools/findingclasses.html

En général, les classes que vous créez doivent soit être chargées comme extension, soit se trouver dans le chemin de classe de la commande javadoc .

DOCLETS JAVADOC

Vous pouvez personnaliser le contenu et le format de la sortie de la commande javadoc au moyen de doclets. La commande javadoc possède un doclet intégré par défaut, appelé doclet standard, qui génère une documentation d'API au format HTML. Vous pouvez modifier ou créer une sous-classe du doclet standard, ou écrire votre propre doclet pour générer du HTML, du XML, du MIF, du RTF ou tout autre format de sortie souhaité.

Lorsqu'un doclet personnalisé n'est pas spécifié avec l'option -doclet , la commande javadoc utilise le doclet standard par défaut. La commande javadoc possède plusieurs options disponibles quel que soit le doclet utilisé. Le doclet standard ajoute un ensemble supplémentaire d'options de ligne de commande. Voir Options.

FICHIERS SOURCE

La commande javadoc génère une sortie provenant des types de fichiers source suivants : fichiers source du langage Java pour les classes (.java), fichiers de commentaires de paquet, fichiers de commentaires de vue d'ensemble et divers fichiers non traités. Cette section décrit également les fichiers de test et les fichiers de modèle qui peuvent également se trouver dans l'arborescence source, mais que vous souhaitez ne pas documenter.

FICHIERS SOURCE DE CLASSE

Chaque classe ou interface et ses membres peuvent avoir leurs propres commentaires de documentation contenus dans un fichier source. Voir Commentaires de documentation.

FICHIERS DE COMMENTAIRES DE PAQUET

Chaque paquet peut avoir son propre commentaire de documentation, contenu dans son propre fichier source, que la commande javadoc fusionne dans la page de résumé du paquet générée. Vous incluez généralement

Dans ce commentaire, tout la documentation qui s'applique à l'ensemble du package.

Pour créer un fichier de commentaire de package, vous pouvez placer vos commentaires dans l'un des fichiers suivants :

•
Le fichier package-info.java peut contenir la déclaration de package, les annotations de package, les commentaires de package et les tags Javadoc. Ce fichier est préféré.
•
Le fichier package.html ne contient que les commentaires de package et les tags Javadoc. Aucune annotation de package.

Un package peut avoir un seul fichier package.html ou un seul fichier package-info.java, mais pas les deux. Placez l'un ou l'autre fichier dans le répertoire du package de l'arborescence source avec vos fichiers source.

Le fichier package-info.java

Le fichier package-info.java peut contenir un commentaire de package de la structure suivante. Le commentaire est placé avant la déclaration du package.

Note : Les séparateurs de commentaire /** et */ doivent être présents, mais les astérisques de début sur les lignes intermédiaires peuvent être omis.

/**
 * Fournit les classes nécessaires pour créer un 
 * applet et les classes qu'un applet utilise 
 * pour communiquer avec son contexte d'applet.
 * <p>
 * Le framework des applets implique deux entités :
 * l'applet et le contexte d'applet.
 * Un applet est une fenêtre intégrable (voir la
 * classe {@link java.awt.Panel}) avec quelques méthodes supplémentaires
 * que le contexte d'applet peut utiliser pour
 * initialiser, démarrer et arrêter l'applet.
 *
 * @since 1.0
 * @see java.awt
 */
package java.lang.applet;

Le fichier package.html

Le fichier package.html peut contenir un commentaire de package de la structure suivante. Le commentaire est placé dans l'élément <body>.

Fichier : java/applet/package.html

<HTML>
<BODY>
Fournit les classes nécessaires pour créer un applet et les
classes qu'un applet utilise pour communiquer avec son contexte d'applet.
<p>
Le framework des applets implique deux entités : l'applet
et le contexte d'applet. Un applet est une fenêtre intégrable
(voir la classe {@link java.awt.Panel}) avec quelques
méthodes supplémentaires que le contexte d'applet peut utiliser pour
initialiser, démarrer et arrêter l'applet.
@since 1.0
@see java.awt
</BODY>
</HTML>

Le fichier package.html est un fichier HTML typique et n'inclut pas de déclaration de package. Le contenu du fichier de commentaire de package est écrit en HTML, à une exception près. Le commentaire de documentation ne doit pas inclure les séparateurs de commentaire /** et */ ni les astérisques de début. Lors de la rédaction du commentaire, faites de la première phrase un résumé sur le package, et ne placez aucun titre ou autre texte entre la balise <body> et la première phrase. Vous pouvez inclure des tags de package. Tous les tags de bloc doivent apparaître après la description principale. Si vous ajoutez un tag @see dans un fichier de commentaire de package, il doit avoir un nom entièrement qualifié.

Traitement du fichier de commentaire

Lorsque la commande javadoc s'exécute, elle recherche le fichier de commentaire de package. Si le fichier de commentaire de package est trouvé, la commande javadoc effectue les opérations suivantes :

•
Copie le commentaire pour traitement. Pour package.html, la commande javadoc copie tout le contenu entre les balises HTML <body> et </body>. Vous pouvez inclure une section <head> pour y placer une balise <title>, une déclaration de copyright du fichier source ou d'autres informations, mais aucune de ces informations n'apparaît dans la documentation générée.
•
Traite les tags de package. Voir Tags de Package.
•
Insère le texte traité en bas de la page récapitulative du package générée. Voir Aperçu de la spécification de l'API de la Plateforme Java, Édition Standard à http://docs.oracle.com/javase/8/docs/api/overview-summary.html
•
Copie la première phrase du commentaire de package en haut de la page récapitulative du package. La commande javadoc ajoute également le nom du package et cette première phrase à la liste des packages sur la page d'aperçu. Voir Aperçu de la spécification de l'API de la Plateforme Java, Édition Standard à http://docs.oracle.com/javase/8/docs/api/overview-summary.html

La fin de la phrase est déterminée par les mêmes règles que pour la fin de la première phrase des descriptions principales de classes et de membres.

FICHIERS DE COMMENTAIRE D'APERÇU

Chaque application ou ensemble de packages que vous documentez peut avoir son propre commentaire de documentation d'aperçu, conservé dans son propre fichier source, que la commande javadoc fusionne dans la page d'aperçu générée. Vous incluez généralement dans ce commentaire toute documentation qui s'applique à l'ensemble de l'application ou de l'ensemble de packages.

Vous pouvez nommer le fichier comme vous le souhaitez, par exemple overview.html, et le placer n'importe où. Un emplacement typique est en haut de l'arborescence source.

Par exemple, si les fichiers source du package java.applet sont contenus dans le répertoire /home/user/src/java/applet, vous pourriez créer un fichier de commentaire d'aperçu à /home/user/src/overview.html.

Vous pouvez avoir plusieurs fichiers de commentaire d'aperçu pour le même ensemble de fichiers source au cas où vous voudriez exécuter la commande javadoc plusieurs fois sur différents ensembles de packages. Par exemple, vous pourriez exécuter la commande javadoc une fois avec -private pour la documentation interne et une autre fois sans cette option pour la documentation publique. Dans ce cas, vous pourriez décrire la documentation comme publique ou interne dans la première phrase de chaque fichier de commentaire d'aperçu.

Le contenu du fichier de commentaire d'aperçu est un grand commentaire de documentation écrit en HTML. Faites de la première phrase un résumé sur l'application ou l'ensemble de packages. Ne placez aucun titre ni aucun autre texte entre la balise <body> et la première phrase. Tous les tags, à l'exception des tags inline comme un tag {@link}, doivent apparaître après la description principale. Si vous ajoutez un tag @see, il doit avoir un nom entièrement qualifié.

Lorsque vous exécutez la commande javadoc, spécifiez le nom du fichier de commentaire d'aperçu avec l'option -overview. Le fichier est alors traité de manière similaire à celle d'un fichier de commentaire de package. La commande javadoc effectue les opérations suivantes :

•
Copie tout le contenu entre les balises <body> et </body> pour le traitement.
•
Traite les tags d'aperçu présents. Voir Tags d'Aperçu.
•
Insère le texte traité en bas de la page d'aperçu générée. Voir Aperçu de la spécification de l'API de la Plateforme Java Standard Edition à http://docs.oracle.com/javase/8/docs/api/overview-summary.html
•
Copie la première phrase du commentaire d'aperçu en haut de la page récapitulative de l'aperçu.

FICHIERS NON TRAITÉS

Vos fichiers source peuvent inclure tous les fichiers que vous souhaitez que la commande javadoc copie dans le répertoire de destination. Ces fichiers incluent généralement des fichiers graphiques, des exemples de fichiers source et de classe Java, et des fichiers HTML autonomes avec beaucoup de contenu qui submergerait le commentaire de documentation d'un fichier source Java typique.

Pour inclure des fichiers non traités, placez-les dans un répertoire appelé doc-files. Le répertoire doc-files peut être un sous-répertoire de n'importe quel répertoire de package contenant des fichiers source. Vous pouvez avoir un sous-répertoire doc-files pour chaque package.

Par exemple, si vous souhaitez inclure l'image d'un bouton dans la documentation de la classe java.awt.Button, placez le fichier image dans le répertoire /home/user/src/java/awt/doc-files/. Ne placez pas le répertoire doc-files à /home/user/src/java/doc-files, car java n'est pas un package. Il ne contient aucun fichier source.

Tous les liens vers les fichiers non traités doivent être inclus dans le code car la commande javadoc ne consulte pas les fichiers. La commande javadoc copie le répertoire et tout son contenu dans la destination. L'exemple suivant montre à quoi pourrait ressembler le lien dans le commentaire de documentation de Button.java :

/**
 * Ce bouton ressemble à ceci :
 * <img src="doc-files/Button.gif">
 */

FICHIERS DE TEST ET DE MODÈLE

Vous pouvez stocker les fichiers de test et de modèle dans l'arborescence source, dans le même répertoire ou dans un sous-répertoire du répertoire où résident les fichiers source. Pour empêcher le traitement des fichiers de test et de modèle, exécutez la commande javadoc et transmettez explicitement les noms de fichiers source individuels.

Les fichiers de test sont des fichiers source valides et compilables. Les fichiers de modèle ne sont pas des fichiers source valides et compatibles, mais ils ont souvent l'extension .java.

Fichiers de test

Si vous souhaitez que vos fichiers de test appartiennent à un package sans nom ou à un package autre que celui des fichiers source, placez les fichiers de test dans un sous-répertoire sous les fichiers source et donnez au répertoire un nom invalide. Si vous placez les fichiers de test dans le même répertoire que les sources et appelez la commande javadoc avec un argument de ligne de commande indiquant son nom de package, les fichiers de test provoqueront des avertissements ou des erreurs. Si les fichiers se trouvent dans un sous-répertoire avec un nom invalide, le répertoire des fichiers de test est ignoré et aucune erreur ou avertissement n'est émis. Par exemple, pour ajouter des fichiers de test pour les fichiers source dans com.package1, placez-les dans un sous-répertoire avec un nom de package invalide. Le nom de répertoire suivant est invalide car il contient un trait d'union :

com/package1/test-files/

Si vos fichiers de test contiennent des commentaires de documentation, vous pouvez configurer une exécution distincte de la commande javadoc pour produire la documentation des fichiers de test en transmettant leurs noms de fichiers source de test avec des jokers, tels que com/package1/test-files/*.java.

Fichiers de modèle

Si vous souhaitez qu'un fichier de modèle se trouve dans le répertoire source, mais qu'il ne génère pas d'erreurs lors de l'exécution de la commande javadoc, donnez-lui un

invalid file name such as Buffer-Template.java to prevent it from being processed. The javadoc command only processes source files with names, when stripped of the .java suffix, that are valid class names.

FICHIERS GÉNÉRÉS

Par défaut, la commande javadoc utilise un doclet standard qui génère une documentation formatée en HTML. Le doclet standard génère un contenu de base, des pages de références croisées et des pages de support décrites ici. Chaque page HTML correspond à un fichier distinct. La commande javadoc génère deux types de fichiers. Le premier type est nommé d'après les classes et les interfaces. Le second type contient des traits d'union (tel que package-summary.html) pour éviter les conflits avec le premier type de fichier.

PAGES DE&#x00A0;CONTENU DE BASE

•
Une page de classe ou d'interface (classname.html) pour chaque classe ou interface documentée.
•
Une page de package (package-summary.html) pour chaque package documenté. La commande javadoc inclut tout texte HTML fourni dans un fichier nommé package.html ou package-info.java dans le répertoire du package de l'arborescence source.
•
Une page d'aperçu (overview-summary.html) pour l'ensemble des packages. La page d'aperçu est la première page du document généré. La commande javadoc inclut tout texte HTML fourni dans un fichier spécifié par l'option -overview. La page d'aperçu n'est créée que lorsque vous passez deux noms de package ou plus à la commande javadoc. Voir HTML Frames and Options.

PAGES DE&#x00A0;RÉFÉRENCES&#x00A0;CROISÉES

•
Une page de hiérarchie des classes pour l'ensemble des packages (overview-tree.html). Pour afficher la page de hiérarchie, cliquez sur Overview dans la barre de navigation, puis sur Tree.
•
Une page de hiérarchie des classes pour chaque package (package-tree.html). Pour afficher la page de hiérarchie, accédez à une page de classe, d'interface ou de package particulière, puis cliquez sur Tree pour afficher la hiérarchie de ce package.
•
Une page d'utilisation pour chaque package (package-use.html) et une page d'utilisation distincte pour chaque classe et interface (class-use/classname.html). La page d'utilisation décrit quels packages, classes, méthodes, constructeurs et champs utilisent une partie du package, de la classe ou de l'interface spécifié. Par exemple, étant donné une classe ou une interface A, sa page d'utilisation inclut les sous-classes de A, les champs déclarés comme A, les méthodes qui retournent A, et les méthodes et constructeurs avec des paramètres de type A. Pour afficher la page d'utilisation, accédez au package, à la classe ou à l'interface, puis cliquez sur le lien Use dans la barre de navigation.
•
Une page d'API obsolètes (deprecated-list.html) qui liste toutes les API obsolètes et leurs remplacements suggérés. Évitez les API obsolètes car elles peuvent être supprimées dans les futures implémentations.
•
Une page de valeurs de champs constants (constant-values.html) pour les valeurs des champs statiques.
•
Une page de forme sérialisée (serialized-form.html) qui fournit des informations sur les classes sérialisables et externalisables avec des descriptions de champs et de méthodes. Les informations sur cette page sont intéressantes pour les réimplémenteurs, et non pour les développeurs qui souhaitent utiliser l'API. Pour accéder à la page de forme sérialisée, accédez à une classe sérialisée et cliquez sur Serialized Form dans la section See Also du commentaire de classe. Le doclet standard génère une page de forme sérialisée qui liste toute classe (publique ou non publique) qui implémente Serializable avec ses méthodes readObject et writeObject, les champs qui sont sérialisés, et les commentaires de documentation des balises @serial, @serialField et @serialData. Les classes sérialisables publiques peuvent être exclues en les marquant (ou leur package) avec @serial exclude, et les classes sérialisables private peuvent être incluses en les marquant (ou leur package) avec un @serial include. Depuis la version 1.4, vous pouvez générer la forme sérialisée complète pour les classes publiques et privées en exécutant la commande javadoc sans spécifier l'option -private. Voir Options.
•
Une page d'index (index-*.html) de tous les noms de classes, interfaces, constructeurs, champs et méthodes, par ordre alphabétique. La page d'index est internationalisée pour Unicode et peut être générée sous forme d'un seul fichier ou d'un fichier séparé pour chaque caractère de départ (tel que A–Z pour l'anglais).

PAGES DE&#x00A0;SUPPORT

•
Une page d'aide (help-doc.html) qui décrit la barre de navigation et les pages précédentes. Utilisez -helpfile pour remplacer le fichier d'aide par défaut par votre propre fichier d'aide personnalisé.
•
Un fichier index.html qui crée les cadres HTML pour l'affichage. Chargez ce fichier pour afficher la première page avec les cadres. Le fichier index.html ne contient aucun contenu textuel.
•
Plusieurs fichiers de cadres (*-frame.html) qui contiennent des listes de packages, de classes et d'interfaces. Les fichiers de cadres affichent les cadres HTML.
•
Un fichier de liste de packages (package-list) qui est utilisé par les options -link et -linkoffline. Le fichier de liste de packages est un fichier texte qui n'est pas accessible via les liens.
•
Un fichier de feuille de style (stylesheet.css) qui contrôle une quantité limitée de couleurs, de familles de polices, de tailles de polices, de styles de polices et d'informations de positionnement sur les pages générées.
•
Un répertoire doc-files qui contient des images, des exemples, du code source ou d'autres fichiers que vous souhaitez copier dans le répertoire de destination. Ces fichiers ne sont pas traités par la commande javadoc. Ce répertoire n'est pas traité à moins qu'il n'existe dans l'arborescence source.

Voir Options.

CADRES HTML

La commande javadoc génère le nombre minimum de cadres (deux ou trois) nécessaire en fonction des valeurs passées à la commande. Elle omet la liste des packages lorsque vous passez un nom de package unique ou des fichiers source appartenant à un seul package comme argument à la commande javadoc. Au lieu de cela, la commande javadoc crée un cadre dans la colonne de gauche qui affiche la liste des classes. Lorsque vous passez deux noms de package ou plus, la commande javadoc crée un troisième cadre qui liste tous les packages et une page d'aperçu (overview-summary.html). Pour contourner les cadres, cliquez sur le lien No Frames ou accédez à l'ensemble de pages à partir de la page overview-summary.html.

STRUCTURE&#x00A0;DES&#x00A0;FICHIERS&#x00A0;GÉNÉRÉS

Les fichiers de classes et d'interfaces générés sont organisés selon la même hiérarchie de répertoires que les fichiers source Java et les fichiers de classes. Cette structure est un répertoire par sous-package.

Par exemple, la documentation générée pour la classe java.applet.Applet serait située à java/applet/Applet.html.

La structure de fichiers pour le package java.applet suit, en supposant que le répertoire de destination est nommé apidocs. Tous les fichiers contenant le mot frame apparaissent dans les cadres supérieur gauche ou inférieur gauche, comme indiqué. Tous les autres fichiers HTML apparaissent dans le cadre droit.

Les répertoires sont en gras. Les astérisques (*) indiquent les fichiers et répertoires qui sont omis lorsque les arguments de la commande javadoc sont des noms de fichiers source plutôt que des noms de package. Lorsque les arguments sont des noms de fichiers source, une liste de packages vide est créée. DÉCLARATIONS D'API GÉNÉRÉES

La commande javadoc génère une déclaration au début de la description de chaque classe, interface, champ, constructeur et méthode pour cet élément d'API. Par exemple, la déclaration pour la classe Boolean est :

public final class Boolean
extends Object
implements Serializable

La déclaration pour la méthode Boolean.valueOf est :

public static Boolean valueOf(String s)

La commande javadoc peut inclure les modificateurs public, protected, private, abstract, final, static, transient, et volatile, mais pas synchronized ou native. Les modificateurs synchronized et native sont considérés comme des détails d'implémentation et ne font pas partie de la spécification de l'API.

Plutôt que de s'appuyer sur le mot-clé synchronized, les API devraient documenter leur sémantique de concurrence dans la description principale du commentaire. Par exemple, une description pourrait être : Une énumération unique ne peut pas être utilisée simultanément par plusieurs threads. Le document ne doit pas décrire comment obtenir ces sémantiques. Comme autre exemple, bien que l'option Hashtable devrait être thread-safe, il n'y a aucune raison de spécifier que cela est obtenu en synchronisant toutes ses méthodes exportées. Il est préférable de se réserver le droit de synchroniser en interne au niveau des buckets pour une concurrence plus élevée.

COMMENTAIRES DE DOCUMENTATION

Cette section décrit les commentaires de code source et l'héritage des commentaires.

COMMENTAIRES DE CODE SOURCE

Vous pouvez inclure des commentaires de documentation dans le code source, avant les déclarations de n'importe quelle classe, interface, méthode, constructeur ou champ. Vous pouvez également créer des commentaires de documentation pour chaque paquet et un autre pour l'aperçu, bien que leur syntaxe soit légèrement différente. Un commentaire de documentation se compose des caractères entre /** et */ qui le terminent. Des astérisques de début sont autorisés sur chaque ligne et sont décrits plus en détail dans la section suivante. Le texte d'un commentaire peut se poursuivre sur plusieurs lignes.

/**
 * Ceci est le format typique d'un commentaire de documentation simple
 * qui s'étend sur deux lignes.
 */

Pour économiser de l'espace, vous pouvez mettre un commentaire sur une seule ligne :

/** Ce commentaire ne prend qu'une seule ligne. */

Emplacement des commentaires

Les commentaires de documentation ne sont reconnus que lorsqu'ils sont placés immédiatement avant les déclarations de classe, interface, constructeur, méthode ou champ. Les commentaires de documentation placés dans le corps d'une méthode sont ignorés. La commande javadoc ne reconnaît qu'un seul commentaire de documentation par instruction de déclaration. Voir Où les balises peuvent être utilisées.

Une erreur courante consiste à placer une instruction import entre le commentaire de classe et la déclaration de classe. Ne placez pas une instruction import à cet emplacement car la commande javadoc ignore le commentaire de classe.

/**
 * Ceci est le commentaire de classe pour la classe Whatever.
 */
import com.example;   // ERREUR - Important de ne pas mettre l'instruction import ici
public class Whatever{ }

Parties des commentaires

Un commentaire de documentation a une description principale suivie d'une section de balises. La description principale commence après le délimiteur de début /** et se poursuit jusqu'à la section de balises. La section de balises commence par la première balise de bloc, qui est définie par le premier caractère @ qui commence une ligne (en ignorant les astérisques de début, les espaces blancs et le séparateur de début /**). Il est possible d'avoir un commentaire avec seulement une section de balises et pas de description principale. La description principale ne peut pas se poursuivre après le début de la section de balises. L'argument d'une balise peut s'étendre sur plusieurs lignes. Il peut y avoir n'importe quel nombre de balises, et certains types de balises peuvent être répétés tandis que d'autres ne peuvent pas. Par exemple, cette balise @see commence la section de balises :

/**
 * Cette phrase contient la description principale pour ce commentaire de documentation.
 * @see java.lang.Object
 */

Balises de bloc et en ligne

Une balise est un mot-clé spécial dans un commentaire de documentation que la commande javadoc traite. Il y a deux types de balises : les balises de bloc, qui apparaissent comme une balise @tag (également connues sous le nom de balises autonomes), et les balises en ligne, qui apparaissent entre accolades, comme une balise {@tag} . Pour être interprétée, une balise de bloc doit apparaître au début d'une ligne, en ignorant les astérisques de début, les espaces blancs et le séparateur (/**). Cela signifie que vous pouvez utiliser le caractère @ ailleurs dans le texte et il ne sera pas interprété comme le début d'une balise. Si vous voulez commencer une ligne par le caractère @ sans qu'il soit interprété, utilisez l'entité HTML &. Chaque balise de bloc a un texte associé, qui inclut tout texte suivant la balise jusqu'à, mais sans inclure, soit la balise suivante, soit la fin du commentaire de documentation. Ce texte associé peut s'étendre sur plusieurs lignes. Une balise en ligne est autorisée et interprétée partout où le texte est autorisé. L'exemple suivant contient la balise de bloc @deprecated et la balise en ligne {@link} . Voir Balises Javadoc.

/**
 * @deprecated  Depuis JDK 1.1, remplacé par {@link #setBounds(int,int,int,int)}
 */

Écrire des commentaires en HTML

Le texte doit être écrit en HTML avec des entités HTML et des balises HTML. Vous pouvez utiliser la version de HTML prise en charge par votre navigateur. Le doclet standard génère du code conforme à HTML 3.2 ailleurs (en dehors des commentaires de documentation) avec l'inclusion de feuilles de style en cascade et de cadres. HTML 4.0 est préféré pour les fichiers générés en raison des ensembles de cadres.

Par exemple, les entités pour le symbole inférieur à (<) et le symbole supérieur à (>) devraient être écrites comme & et &. De même, l'esperluette (&) devrait être écrite comme &. La balise HTML de gras <b> est montrée dans l'exemple suivant.

/**
 * Ceci est un commentaire <b>doc</b>.
 * @see java.lang.Object
 */

Astérisques de début

Lorsque la commande javadoc analyse un commentaire de documentation, les astérisques de début (*) de chaque ligne sont supprimés, et les espaces et tabulations précédant les astérisques initiaux (*) sont également supprimés. Si vous omettez l'astérisque de début sur une ligne, l'espace blanc de début n'est alors plus supprimé afin que vous puissiez coller des exemples de code directement dans un commentaire de documentation à l'intérieur d'une balise <PRE> avec son indentation préservée. Les espaces sont interprétés par les navigateurs plus uniformément que les tabulations. L'indentation est relative à la marge gauche (plutôt qu'au séparateur /** ou à la balise <PRE> ).

Première phrase

La première phrase de chaque commentaire de documentation devrait être une phrase résumé contenant une description concise mais complète de l'entité déclarée. Cette phrase se termine au premier point suivi d'un espace, d'une tabulation ou d'un terminateur de ligne, ou à la première balise de bloc. La commande javadoc copie cette première phrase vers le résumé du membre en haut de la page HTML.

Déclarations de champs multiples

La plateforme Java vous permet de déclarer plusieurs champs dans une seule instruction, mais cette instruction ne peut avoir qu'un seul commentaire de documentation qui est copié pour tous les champs. Si vous voulez des commentaires de documentation individuels pour chaque champ, déclarez chaque champ dans une instruction séparée. Par exemple, le commentaire de documentation suivant n'a pas de sens écrit comme une seule déclaration et serait mieux géré comme deux déclarations :

/** 
 * Les distances horizontale et verticale du point (x,y)
 */
public int x, y;      // Évitez ceci

La commande javadoc génère la documentation suivante à partir du code précédent :

public int x

Les distances horizontale et verticale du point (x, y).

public int y

Les distances horizontale et verticale du point (x, y).

Utilisation des balises d'en-tête

Lors de l'écriture de commentaires de documentation pour les membres, il est préférable de ne pas utiliser les balises d'en-tête HTML telles que <H1> et <H2>, car la commande javadoc crée un document structuré complet, et ces balises structurelles pourraient interférer avec le formatage du document généré. Cependant, vous pouvez utiliser ces en-têtes dans les commentaires de classe et de paquet pour fournir votre propre structure.

HÉRITAGE DES COMMENTAIRES DE MÉTHODE

La commande javadoc permet l'héritage des commentaires de méthode dans les classes et les interfaces pour compléter le texte manquant ou hériter explicitement des commentaires de méthode. Les constructeurs, les champs et les classes imbriquées n'héritent pas des commentaires de documentation.

Remarque : Le fichier source d'une méthode héritée doit se trouver sur le chemin spécifié par l'option -sourcepath pour que le commentaire de documentation soit disponible pour la copie. Ni la classe ni son paquet n'ont besoin d'être passés sur la ligne de commande. Cela contraste avec la version 1.3,n et les versions antérieures, où la classe devait être une classe documentée.

Compléter le texte manquant

Lorsqu'une description principale, ou une balise @return, @paramou @throws est manquante dans un commentaire de méthode, la commande javadoc copie la description principale ou le commentaire de balise correspondant de la méthode qu'elle remplace ou implémente (le cas échéant). Voir Héritage des commentaires de méthode.

Lorsqu'une balise @param pour un paramètre particulier est manquante, le commentaire pour ce paramètre est copié de la méthode plus haut dans la hiérarchie d'héritage. Lorsqu'une balise @throws pour une exception particulière est manquante, la balise @throws n'est copiée que lorsque cette exception est déclarée.

Ce comportement contraste avec la version 1.3 et antérieures, où la présence de n'importe quelle description principale ou balise empêchait l'héritage de tous les commentaires.

Introduit dans JDK 1.0

Ajoute une rubrique Regarder aussi avec un lien ou une entrée textuelle qui pointe vers une référence. Un commentaire de documentation peut contenir un nombre quelconque de tags @see, qui sont tous regroupés sous la même rubrique. Le tag @see a trois variations. La forme est la plus courante. Ce tag est valide dans tout commentaire de documentation : vue d'ensemble, package, classe, interface, constructeur, méthode ou champ. Forme 1. La forme de tag @see chaîne ajoute une entrée textuelle pour chaîne. Aucun lien n'est généré. La chaîne est un livre ou une autre référence à des informations non disponibles par URL. La commande javadoc distingue cela des cas précédents en recherchant un guillemet double (") comme premier caractère. Par exemple, @see "The Java Programming Language" qui génère le texte suivant:

La commande javadoc distingue cela des autres cas en recherchant un symbole inférieur à (<) comme premier caractère. Forme 3. La forme @see package.classe#membre libellé ajoute un lien avec un libellé textuel visible qui pointe vers la documentation du nom spécifié dans le langage Java qui est référencé. Le libellé est optionnel. Si le libellé est omis, alors le nom apparaît à la place en tant que texte visible, correctement raccourci. Utilisez l'option -noqualifier pour supprimer globalement le nom du package de ce texte visible. Utilisez le libellé lorsque vous souhaitez que le texte visible soit différent du texte visible autogénéré. Voir Comment un nom apparaît.

Dans Java SE 1.2 uniquement, le nom mais pas le libellé apparaît automatiquement dans les tags HTML <code>. À partir de Java SE 1.2.2, le tag <code> est toujours inclus autour du texte visible, qu'un libellé soit utilisé ou non.

•
package.class#member est tout nom d'élément de programme valide qui est référencé, tel qu'un nom de package, de classe, d'interface, de constructeur, de méthode ou de champ, sauf que le caractère précédant le nom du membre doit être un signe de livre (#). La classe représente toute classe ou interface de niveau supérieur ou imbriquée. Le membre représente tout constructeur, méthode ou champ (pas une classe ou interface imbriquée). Si ce nom est dans les classes documentées, alors la commande javadoc crée un lien vers celui-ci. Pour créer des liens vers des classes référencées externes, utilisez l'option -link. Utilisez l'une des deux autres formes de tag @see pour faire référence à la documentation d'un nom qui n'appartient pas à une classe référencée. Voir Spécifier un nom.

Note: Les classes référencées externes sont les classes qui ne sont pas passées à la commande javadoc sur la ligne de commande. Les liens dans la documentation générée vers des classes référencées externes sont appelés références externes ou liens externes. Par exemple, si vous exécutez la commande javadoc uniquement sur le package java.awt, alors toute classe dans java.lang, telle que Object, est une classe référencée externe. Utilisez les options -link et -linkoffline pour créer des liens vers des classes référencées externes. Les commentaires source des classes référencées externes ne sont pas disponibles pour l'exécution de la commande javadoc.

•

@since texte-depuis
Introduit dans JDK 1.1

Ajoute un titre Since avec la valeur texte-depuis spécifiée à la documentation générée. Le texte n'a pas de structure interne spéciale. Pour le code source de la plateforme Java, le tag @since indique la version de la spécification de l'API de la plateforme Java, qui n'est pas nécessairement le moment où le code source a été ajouté à l'implémentation de référence. FICHIERS D'ARGUMENTS DE LIGNE DE COMMANDE

Pour raccourcir ou simplifier la commande javadoc, vous pouvez spécifier un ou plusieurs fichiers contenant des arguments pour la commande javadoc (à l'exception des options -J). Cela vous permet de créer des commandes javadoc de n'importe quelle longueur sur n'importe quel système d'exploitation.

Un fichier d'arguments peut inclure des options javac et des noms de fichiers source dans n'importe quelle combinaison. Les arguments à l'intérieur d'un fichier peuvent être séparés par des espaces ou par des sauts de ligne. Si un nom de fichier contient des espaces, placez le nom de fichier entier entre guillemets doubles.

Les noms de fichiers dans un fichier d'arguments sont relatifs au répertoire courant, pas à l'emplacement du fichier d'arguments. Les caractères génériques (*) ne sont pas autorisés dans ces listes (par exemple, pour spécifier *.java). L'utilisation du signe arobase (@) pour interpréter récursivement les fichiers n'est pas prise en charge. Les options -J ne sont pas prises en charge car elles sont transmises au lanceur, qui ne prend pas en charge les fichiers d'arguments.

Lorsque vous exécutez la commande javadoc, transmettez le chemin et le nom de chaque fichier d'arguments avec le caractère arobase (@) comme préfixe. Lorsque la commande javadoc rencontre un argument commençant par le signe arobase, elle développe le contenu de ce fichier dans la liste des arguments.

Documenter un ou plusieurs paquets

Pour documenter un paquet, les fichiers source de ce paquet doivent être situés dans un répertoire portant le même nom que le paquet.

Si un nom de paquet contient plusieurs identificateurs (séparés par des points, comme `java.awt.color`), chaque identificateur suivant doit correspondre à un sous-répertoire plus profond (comme `java/awt/color`).

Vous pouvez répartir les fichiers source d'un même paquet entre deux arbres de répertoires situés à des endroits différents, tant que `-sourcepath` les pointe tous les deux. Par exemple, `src1/java/awt/color` et `src2/java/awt/color`.

Vous pouvez exécuter la commande `javadoc` soit en changeant de répertoire (avec la commande `cd`), soit en utilisant l'option `-sourcepath`. Les exemples suivants illustrent les deux alternatives.

Exemple 1 Exécution récursive à partir d'un ou plusieurs paquets

Cet exemple utilise `-sourcepath` afin que la commande `javadoc` puisse être exécutée depuis n'importe quel répertoire, et `-subpackages` (une nouvelle option de la version 1.4) pour la récursion. Il traverse les sous-paquets du répertoire `java` en excluant les paquets basés sur `java.net` et `java.lang`. Notez que cela exclut `java.lang.ref`, un sous-paquet de `java.lang`. Pour traverser également d'autres arbres de paquets, ajoutez leurs noms à l'argument `-subpackages`, comme `java:javax:org.xml.sax`.

javadoc -d /home/html -sourcepath /home/src -subpackages java -exclude

Exemple 2 Changement vers la racine et exécution de paquets explicites

Accédez au répertoire parent du paquet qualifié complet. Ensuite, exécutez la commande `javadoc` avec les noms d'un ou plusieurs paquets que vous souhaitez documenter :

cd /home/src/
javadoc -d /home/html java.awt java.awt.event

Pour traverser également d'autres arbres de paquets, ajoutez leurs noms à l'argument `-subpackages`, comme `java:javax:org.xml.sax`.

Exemple 3 Exécution depuis n'importe quel répertoire sur des paquets explicites dans un arbre

Dans ce cas, le répertoire courant n'a pas d'importance. Exécutez la commande `javadoc` et utilisez l'option `-sourcepath` avec le répertoire parent du paquet de niveau supérieur. Fournissez les noms d'un ou plusieurs paquets que vous souhaitez documenter :

javadoc -d /home/html -sourcepath /home/src java.awt java.awt.event

Exemple 4 Exécution depuis n'importe quel répertoire sur des paquets explicites dans plusieurs arbres

Exécutez la commande `javadoc` et utilisez l'option `-sourcepath` avec une liste séparée par des deux-points des chemins d'accès à la racine de chaque arbre. Comme deux paquets ou plus sont générés, le document comporte trois cadres HTML : un pour la liste des paquets, un autre pour la liste des classes et le troisième pour les pages de classes principales.

L'API d'accès Javadoc permet à l'utilisateur d'appeler l'outil Javadoc directement depuis une application Java sans exécuter un nouveau processus.

import javax.tools.DocumentationTool;
import javax.tools.ToolProvider;
public class JavaAccessSample{
    public static void main(String[] args){
        DocumentationTool javadoc = ToolProvider.getSystemDocumentationTool();
        int rc = javadoc.run( null, null, null,
                 "-d", "/home/html",
                 "-sourcepath", "home/src",
                 "-subpackages", "java",
                 "-exclude", "java.net:java.lang",
                 "com.example");
     }
 }

Les trois premiers arguments de la méthode `run` spécifient les flux d'entrée, de sortie standard et d'erreur standard. `Null` est la valeur par défaut pour `System.in`, `System.out` et `System.err`, respectivement.

NAME

javadoc - Java documentation generator

SYNOPSIS

javadoc [options] [packages] [sourcefiles]

DESCRIPTION

The javadoc command analyzes a set of Java™ source files and generates documentation in HTML format. The documentation is created from doc comments in the source files. Doc comments are block comments that start with •/‪‪ and end with ‪‪/.

The javadoc tool extracts the documentation comments and the public and protected classes, interfaces, constructors, methods, and fields from the specified source files, and then writes the documentation to HTML files.

The javadoc tool can generate documentation for packages, classes, interfaces, constructors, methods, and fields. The documentation can also include additional HTML files, such as a top-level overview for the entire set of packages.

DOCUMENTATION COMMENTS

Doc comments are Java block comments that start with •/‪‪ and end with ‪‪/.

/**
 * This is a doc comment.
 */

The first sentence of a doc comment is used as the summary comment for the declaration. This sentence ends at the first period that is followed by a space or a tab. You can also use HTML tags within doc comments.

Doc comments can include tags, which are preceded by an ‪@‪. Tags provide additional information about the documentation comment. For example, the ‪@param‪ tag is used to describe a parameter, and the ‪@return‪ tag is used to describe the return value of a method.

OPTIONS

The javadoc command supports a wide variety of options. Some of the most common options are:

-classpath classpath
Specifies the path that javadoc uses to find user class files. This option overrides the CLASSPATH environment variable. Separate directories with a semicolon (;) for Windows or a colon (:) for Oracle Solaris.
-doclet class
Specifies the doclet class to use for generating documentation. A doclet is a program that reads the documentation tags and uses the emitted HTML files as a source of information to create a text, XML, or other format documentation.
-docletpath classpath
Specifies the path to the doclet, overriding the default doclet path. This is used only if the -doclet option is also specified.
-help
Displays a short help message.
-link url
Creates a link to the Javadoc documentation generated from other packages. This option can be used multiple times to create links to multiple packages.
-linkoffline linkname url
Creates a link to Javadoc documentation generated from other packages, where the documentation is not available online. The linkname argument specifies the name of the package to link to, and the url argument specifies the path to the Javadoc documentation.
-locale locale
Specifies the locale to use when generating documentation. The locale determines the language and formatting of the documentation. For example, -locale en_US uses U.S. English.
-overview file
Specifies the overview HTML file to use for the top-level documentation. This file is used to create the overview page for the entire set of packages.
-package
Specifies that only public and protected classes and members should be documented. This is the default behavior.
-private
Specifies that all classes and members, including private ones, should be documented.
-protected
Specifies that only protected classes and members should be documented. This is the default behavior.
-public
Specifies that only public classes and members should be documented.
-since
Includes the ‪@since‪ tags in the generated documentation.
-source version
Specifies the version of the source code. This option is used to enable features of a later Java version while still compiling with an earlier Java version.
-sourcetab width
Specifies the number of spaces to use for source code tabs. The default is 8.
-use
Includes a "Use" page for each package and class, which describes how each documented class or interface is used.
-verbose
Enables verbose output. This option prints additional information about the documentation generation process.
-windowtitle text
Specifies the title to be displayed in the browser window's title bar. This option overrides the document title specified by the -doctitle option.

COMMAND-LINE ARGUMENT FILES

You can specify command-line options and file names in a file. This is useful for long command lines. Each option or file name must be on a separate line. Lines starting with ‪#‪ are ignored.

For example, create a file named myjavadoc.options with the following content:

-windowtitle 'My Java API Documentation'
-overview overview.html
-public
-use
-link http://docs.oracle.com/javase/8/docs/api/

Then, run javadoc as follows:

javadoc @myjavadoc.options com.mypackage

RUNNING THE JAVADOC COMMAND

The following example shows how to run the javadoc command to generate documentation for a set of packages:

javadoc -windowtitle 'Java™ SE 7 API Specification' \
        -doctitle 'Java™ SE 7 API Specification' \
        -header 'Java™ SE 7' \
        -bottom '<font size="-1">
                <a href="http://bugreport.sun.com/bugreport/">Submit a bug or feature</a><br/>
                Copyright &copy; 1993, 2011, Oracle and/or its affiliates. All rights reserved.<br/>
                Oracle is a registered trademark of Oracle Corporation and/or its affiliates.
                Other names may be trademarks of their respective owners.</font>' \
        -top    '<font size="-1">
                <a href="http://bugreport.sun.com/bugreport/">Submit a bug or feature</a><br/>
                Copyright &copy; 1993, 2011, Oracle and/or its affiliates. All rights reserved.<br/>
                Oracle is a registered trademark of Oracle Corporation and/or its affiliates.
                Other names may be trademarks of their respective owners.</font>' \
        -group 'Core Packages' 'java.*:com.sun.java.*:org.omg.*' \
        -group 'Extension Packages' 'javax.*' \
        -sourcepath /java/jdk/1.7.0/src/share/classes \
        -use \
        -splitIndex \
        -public \
        -nodeprecated \
        -author \
        -version \
        -linkoffline http://download.oracle.com/javase/7/docs/api/ \
        -linksource \
        -quiet \
        -Xmx180m \
        java.lang java.lang.reflect java.util java.io java.net java.applet

This command generates documentation for the specified packages and includes the following:

  • A window title of 'Java™ SE 7 API Specification'.
  • A document title of 'Java™ SE 7 API Specification'.
  • A header of 'Java™ SE 7'.
  • A bottom text with copyright and trademark information.
  • The "Use" page enabled.
  • The index split into alphabetical sections.
  • Only public classes and members documented.
  • Deprecated classes and members excluded.
  • Author and version information included.
  • Links to the Java SE 7 API documentation.
  • Source code links enabled.
  • Quiet mode enabled.
  • Memory set to 180MB.
  • Packages to document: java.lang java.lang.reflect java.util java.io java.net java.applet

NOTES

•
If you omit the -windowtitle option, then the javadoc command copies the document title to the window title. The -windowtitle option text is similar to the the -doctitle option, but without HTML tags to prevent those tags from appearing as raw text in the window title.
•
If you omit the -footer option, then the javadoc command copies the header text to the footer.
•
Other important options you might want to use, but were not needed in the previous example, are the -classpath and -link options.

GENERAL TROUBLESHOOTING

•
The javadoc command reads only files that contain valid class names. If the javadoc command is not correctly reading the contents of a file, then verify that the class names are valid. See Process Source Files.
•
See the Javadoc FAQ for information about common bugs and for troubleshooting tips at http://www.oracle.com/technetwork/java/javase/documentation/index-137483.html

ERRORS AND WARNINGS

Error and warning messages contain the file name and line number to the declaration line rather than to the particular line in the documentation comment.

For example, this message error: cannot read: Class1.java means that the javadoc command is trying to load Class1.java in the current directory. The class name is shown with its path (absolute or relative).

ENVIRONMENT

CLASSPATH
CLASSPATH is the environment variable that provides the path that the javadoc command uses to find user class files. This environment variable is overridden by the -classpath option. Separate directories with a semicolon for Windows or a colon for Oracle Solaris.

Windows example: .;C:\classes;C:\home\java\classes

Oracle Solaris example: .:/home/classes:/usr/local/java/classes.
