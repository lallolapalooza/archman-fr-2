UTILISATION DE LA VARIABLE D'ENVIRONNEMENT DU LANCEUR JDK_JAVA_OPTION

S

JDK_JAVA_OPTIONS préfixe son contenu aux options analysées depuis la ligne de commande. Le contenu de la variable d'environnement JDK_JAVA_OPTIONS est une liste d'arguments séparés par des caractères d'espacement (tels que déterminés par isspace()). Ceux-ci sont préfixés aux arguments de ligne de commande passés au lanceur java. L'exigence d'encodage pour la variable d'environnement est la même que pour la ligne de commande java sur le système. Le contenu de la variable d'environnement JDK_JAVA_OPTIONS est traité de la même manière que ce qui est spécifié sur la ligne de

commande.

Les guillemets simples (') ou doubles (") peuvent être utilisés pour entourer des arguments contenant des caractères d'espacement. Tout le contenu entre la quote d'ouverture et la première quote de fermeture correspondante est conservé en supprimant simplement la paire de guillemets. Si aucune quote correspondante n'est trouvée, le lanceur s'arrêtera avec un message d'erreur. Les fichiers @ sont pris en charge comme ils sont spécifiés sur la ligne de commande. Tout caractère générique littéral * dans le contenu de la variable d'environnement JDK_JAVA_OPTIONS n'est pas développé et est transmis tel quel à la VM démarrée. Afin d'atténuer les utilisations abusives potentielles du comportement de JDK_JAVA_OPTIONS, les options qui spécifient la classe principale (telles que -jar) ou qui font que le lanceur java se termine sans exécuter la classe principale (telles que -h) sont interdites dans la variable d'environnement. Si l'une de ces options apparaît dans la variable d'environnement, le lanceur s'arrêtera avec un message d'erreur. Lorsque JDK_JAVA_OPTIONS est défini, le lanceur imprime un message sur stderr comme

Ce sont les options les plus couramment utilisées prises en charge par toutes les implémentations de la JVM.

Remarque : Pour spécifier un argument pour une option longue, vous pouvez utiliser soit --nom=valeur soit --nom valeur.

-agentlib:nom_lib[=options]
Charge la bibliothèque d'agents natifs spécifiée. Après le nom de la bibliothèque, une liste d'options spécifiques à la bibliothèque, séparées par des virgules, peut être utilisée. Si l'option -agentlib:foo est spécifiée, la JVM tente de charger la bibliothèque nommée foo en utilisant les conventions de nommage et les emplacements spécifiques à la plateforme :\n
•
Plateformes Linux et autres plateformes similaires à POSIX : La JVM tente de charger la bibliothèque nommée libfoo.so dans l'emplacement spécifié par la variable système LD_LIBRARY_PATH.
•
macOS : La JVM tente de charger la bibliothèque nommée libfoo.dylib dans l'emplacement spécifié par la variable système DYLD_LIBRARY_PATH.
•
Windows : La JVM tente de charger la bibliothèque nommée foo.dll dans l'emplacement spécifié par la variable système PATH.

L'exemple suivant montre comment charger la bibliothèque du protocole JDWP (Java Debug Wire Protocol) et écouter la connexion socket sur le port 8000, en suspendant la JVM avant le chargement de la classe principale :

-agentlib:jdwp=transport=dt_socket,server=y,address=8000

-agentpath:chemin_complet[=options]
Charge la bibliothèque d'agents natifs spécifiée par le chemin d'accès absolu. Cette option est équivalente à -agentlib mais utilise le chemin d'accès complet et le nom de fichier de la bibliothèque.
--class-path chemin_classe, -classpath chemin_classe, ou -cp chemin_classe
Spécifie une liste de répertoires, de fichiers JAR et d'archives ZIP à rechercher pour les fichiers de classe.

Sous Windows, les points-virgules (;) séparent les entités de cette liste ; sur d'autres plateformes, c'est un deux-points (:).

La spécification de chemin_classe remplace tout paramètre de la variable d'environnement CLASSPATH. Si l'option de chemin de classe n'est pas utilisée et que chemin_classe n'est pas défini, le chemin de classe de l'utilisateur se compose du répertoire courant (.).

Par souci de commodité, un élément de chemin de classe contenant un nom de base d'astérisque (*) est considéré comme équivalent à la spécification d'une liste de tous les fichiers du répertoire avec l'extension .jar ou .JAR. Un programme Java ne peut pas faire la différence entre les deux invocations. Par exemple, si le répertoire mydir contient a.jar et b.JAR, l'élément de chemin de classe mydir/* est développé en A.jar:b.JAR, sauf que l'ordre des fichiers JAR n'est pas spécifié. Tous les fichiers .jar du répertoire spécifié, même ceux qui sont masqués, sont inclus dans la liste. Un élément de chemin de classe constitué d'un astérisque (*) est développé en une liste de tous les fichiers jar du répertoire courant. La variable d'environnement CLASSPATH, lorsqu'elle est définie, est développée de manière similaire. Toute expansion de joker de chemin de classe qui se produit avant le démarrage de la VM Java. Les programmes Java ne voient jamais de jokers non développés, sauf en interrogeant l'environnement, par exemple en appelant System.getenv("CLASSPATH").

--enable-native-access module[,module...]
L'accès natif implique l'accès à du code ou des données en dehors de l'environnement d'exécution Java. Ceci est généralement dangereux et, si fait de manière incorrecte, peut planter la JVM ou entraîner une corruption de mémoire. L'accès natif peut se produire à la suite de l'appel d'une méthode qui est soit restreinte [https://openjdk.org/jeps/454#Safety], soit native. ---illegal-native-access=paramètre
Cette option spécifie un mode de gestion de l'accès natif illégal :

Remarque : Cette option sera supprimée dans une future version.

•
allow : Ce mode autorise l'accès natif illégal dans tous les modules, sans aucun avertissement.
•
warn : Ce mode est identique à allow, sauf qu'un message d'avertissement est émis pour le premier accès natif illégal trouvé dans un module. Ce mode est le défaut pour le JDK actuel, mais il changera dans une future version.
•
deny : Ce mode désactive l'accès natif illégal. Autrement dit, tout accès natif illégal provoque une IllegalCallerException. Ce mode deviendra le défaut dans une future version.

Pour vérifier que votre application est prête pour une future version du JDK, exécutez-la avec --illegal-native-access=deny ainsi que toutes les options --enable-native-access nécessaires.

--finalization=valeur

Chaque module est soit un JAR modulaire, soit un répertoire de modules décompressé.

Sous Windows, les points-virgules (;) séparent les éléments de chemin de cette liste ; sur d'autres plateformes, c'est un deux-points (:).

•

-XX:-CompactStrings
Désactive la fonctionnalité Compact Strings. Par défaut, cette option est activée. Lorsque cette option est activée, les chaînes Java contenant uniquement des caractères sur un octet sont représentées et stockées en interne sous forme de chaînes sur un octet par caractère utilisant le codage ISO-8859-1 / Latin-1. Cela réduit de 50 % l'espace requis pour les chaînes contenant uniquement des caractères sur un octet. Pour les chaînes Java contenant au moins un caractère multibyte : elles sont représentées et stockées sous forme de 2 octets par caractère en utilisant le codage UTF-16. La désactivation de la fonctionnalité Compact Strings force l'utilisation du codage UTF-16 comme représentation interne de toutes les chaînes Java.

Les cas où il peut être avantageux de désactiver Compact Strings incluent les suivants :

•
Lorsqu'il est connu qu'une application allouera majoritairement des chaînes de caractères multibytes.

La région de génération jeune du tas est utilisée pour les nouveaux objets. Le GC est effectué dans cette région plus souvent que dans d'autres régions. -XX:RTMAbortRatio=pourcentage_d_échec
Spécifie le pourcentage (%) de toutes les transactions RTM exécutées pour le rapport d'échec RTM. Si le nombre de transactions échouées dépasse ce rapport, le code compilé est désoptimisé. Ce rapport est utilisé lorsque l'option -XX:+UseRTMDeopt est activée. La valeur par défaut de cette option est 50. Cela signifie que le code compilé est désoptimisé si 50 % de toutes les transactions échouent.
-XX:RTMRetryCount=nombre_de_réessais
Spécifie le nombre de fois où le code de verrouillage RTM est réessayé, lorsqu'il échoue ou est occupé, avant de revenir au mécanisme de verrouillage normal. La valeur par défaut de cette option est 5. L'option -XX:+UseRTMLocking doit être activée.
-XX:+UseRTMDeopt
Optimise automatiquement le verrouillage RTM en fonction du rapport d'échec. Ce rapport est spécifié par l'option -XX:RTMAbortRatio. Si le nombre de transactions échouées dépasse le rapport d'échec, la méthode contenant le verrou est désoptimisée et recompilée avec tous les verrous comme des verrous normaux. Cette option est désactivée par défaut. L'option -XX:+UseRTMLocking doit être activée.
-XX:+UseRTMLocking
Génère du code de verrouillage RTM (Restricted Transactional Memory) pour tous les verrous gonflés, avec le mécanisme de verrouillage normal comme gestionnaire de secours. Cette option est désactivée par défaut. Les options liées à RTM ne sont disponibles que sur les processeurs x86 qui prennent en charge les extensions de synchronisation transactionnelle (TSX).

RTM fait partie de TSX d'Intel, qui est un jeu d'instructions x86 et facilite la création d'applications multithreadées. RTM introduit les nouvelles instructions XBEGIN, XABORT, XEND et XTEST. Les instructions XBEGIN et XEND encadrent un ensemble d'instructions à exécuter comme une transaction. Si aucun conflit n'est trouvé lors de l'exécution de la transaction, les modifications de mémoire et de registre sont validées ensemble au niveau de l'instruction XEND. L'instruction XABORT peut être utilisée pour abandonner explicitement une transaction et l'instruction XTEST vérifie si un ensemble d'instructions est en cours d'exécution dans une transaction.

Un verrou sur une transaction est gonflé lorsqu'un autre thread tente d'accéder à la même transaction, bloquant ainsi le thread qui n'avait pas initialement demandé l'accès à la transaction. RTM nécessite qu'un ensemble d'opérations de secours soit spécifié au cas où une transaction échouerait ou serait abandonnée. Un verrou RTM est un verrou qui a été délégué au système TSX.

RTM améliore les performances pour les verrous très contestés avec peu de conflits dans une région critique (qui est un code auquel plusieurs threads ne peuvent pas accéder simultanément). RTM améliore également les performances du verrouillage grossier, qui ne fonctionne généralement pas bien dans les applications multithreadées. (Le verrouillage grossier est la stratégie consistant à conserver les verrous pendant de longues périodes pour minimiser le surcoût de prise et de libération des verrous, tandis que le verrouillage fin est la stratégie visant à obtenir un parallélisme maximal en verrouillant uniquement lorsque nécessaire et en déverrouillant dès que possible.) De plus, pour les verrous légèrement contestés utilisés par différents threads, RTM peut réduire le partage de ligne de cache parasite, également appelé "cache line ping-pong". Cela se produit lorsque plusieurs threads de différents processeurs accèdent à différentes ressources, mais que ces ressources partagent la même ligne de cache. En conséquence, les processeurs invalident à plusieurs reprises les lignes de cache des autres processeurs, ce qui les oblige à lire depuis la mémoire principale plutôt que depuis leur cache.

Xlog

This option controls Java Virtual Machine (JVM) logging. The format of the option is -Xlog[:[tag][=level][,tag...][=level]...][X], where X is an optional parameter that controls the output format. The default value for tag is all, the default value for level is info, and the default value for X is default. The default output destination is stdout.

The following are some examples of using the -Xlog option:

-Xlog:all=info
Logs all messages using the info level to stdout. The default configuration for all other messages at level warning is in effect.
-Xlog:help
Prints a help message about the -Xlog option and exits.
-Xlog:help=detailed
Prints a detailed help message about the -Xlog option and exits.
-Xlog:stdout
Logs all messages using the default info level to stdout. The default configuration for all other messages at level warning is in effect.
-Xlog:stdout,tag
Logs all messages using the default info level to stdout. The default configuration for all other messages at level warning is in effect.
-Xlog:all=info:stdout:uptime,levels,tags
Logs all messages using the info level to stdout with decorations for uptime, levels, and tags. This is equivalent to using:

-Xlog:all=info:stdout:uptime,levels,tags

-Xlog:gc
Logs messages tagged with the gc tag using info level to stdout. The default configuration for all other messages at level warning is in effect.
-Xlog:gc,safepoint
Logs messages tagged either with the gc or safepoint tags, both using the info level, to stdout, with default decorations. Messages tagged with both gc and safepoint won't be logged.
-Xlog:gc+ref=debug
Logs messages tagged with both gc and ref tags, using the debug level to stdout, with default decorations. Messages tagged only with one of the two tags won't be logged.
-Xlog:gc=debug:file=gc.txt:none
Logs messages tagged with the gc tag using the debug level to a file called gc.txt with no decorations. The default configuration for all other messages at level warning is still in effect.
-Xlog:gc=trace:file=gctrace.txt:uptimemillis,pid:filecount=5,filesize=1024
Logs messages tagged with the gc tag using the trace level to a rotating file set with 5 files with size 1 MB with the base name gctrace.txt and uses decorations uptimemillis and pid.

The default configuration for all other messages at level warning is still in effect.

-Xlog:gc::uptime,tid
Logs messages tagged with the gc tag using the default 'info' level to default the output stdout and uses decorations uptime and tid. The default configuration for all other messages at level warning is still in effect.
-Xlog:gc*=info,safepoint*=off
Logs messages tagged with at least gc using the info level, but turns off logging of messages tagged with safepoint. Messages tagged with both gc and safepoint won't be logged.
-Xlog:disable -Xlog:safepoint=trace:safepointtrace.txt
Turns off all logging, including warnings and errors, and then enables messages tagged with safepointusing tracelevel to the file safepointtrace.txt. The default configuration doesn't apply, because the command line started with -Xlog:disable.

VALIDATION DES ARGUMENTS DE FLAGS DE LA MACHINE VIRTUELLE JAVA

Vous utilisez les valeurs fournies à tous les indicateurs de ligne de commande de la Machine Virtuelle Java (JVM) pour la validation et, si la valeur d'entrée est invalide ou hors limites, un message d'erreur approprié est affiché.

Qu'ils soient définis de manière ergonomique, en ligne de commande, par un outil d'entrée ou via les API (par exemple, les classes contenues dans le package java.lang.management), les valeurs fournies à tous les indicateurs de ligne de commande de la Machine Virtuelle Java (JVM) sont validées. L'ergonomie est décrite dans le Java Platform, Standard Edition HotSpot Virtual Machine Garbage Collection Tuning Guide.

Les plages et les contraintes sont validées soit lorsque toutes les valeurs des indicateurs sont définies lors de l'initialisation de la JVM, soit lorsque la valeur d'un indicateur est modifiée pendant l'exécution (par exemple, en utilisant l'outil jcmd). La JVM est terminée si une valeur enfreint la vérification de plage ou de contrainte et un message d'erreur approprié est imprimé sur le flux d'erreurs.

Par exemple, si un indicateur enfreint une vérification de plage ou de contrainte, la JVM se termine avec une erreur :

java -XX:AllocatePrefetchStyle=5 -version
intx AllocatePrefetchStyle=5 is outside the allowed range [ 0 ... 3 ]
Improperly specified VM option 'AllocatePrefetchStyle=5'
Error: Could not create the Java Virtual Machine.
Error: A fatal exception has occurred. Program will exit.

L'indicateur -XX:+PrintFlagsRanges imprime la plage de tous les indicateurs. Cet indicateur permet le test automatique des indicateurs par les valeurs fournies par les plages. Pour les indicateurs dont les plages sont spécifiées, le type, le nom et la plage réelle sont imprimés dans la sortie.

Par exemple,

intx   ThreadStackSize [ 0 ... 9007199254740987 ] {pd product}

Pour les indicateurs dont la plage n'est pas spécifiée, les valeurs ne sont pas affichées dans la sortie. Par exemple :

size_t NewSize         [   ...                  ] {product}

Cela aide à identifier les indicateurs qui doivent être implémentés. Le framework de test automatique peut ignorer ces indicateurs qui n'ont pas de valeurs et ne sont pas implémentés.

GRANDES PAGES

Vous utilisez de grandes pages, également connues sous le nom de pages immenses (huge pages), comme pages mémoire qui sont significativement plus grandes que la taille de page mémoire standard (qui varie en fonction du processeur et du système d'exploitation). Les grandes pages optimisent les Buffers de traduction à translation anticipée du processeur.

Un Buffer de traduction à translation anticipée (TLB) est un cache de traduction de page qui contient les traductions d'adresses virtuelles à physiques les plus récemment utilisées. Un TLB est une ressource système rare. Une défaillance de TLB peut être coûteuse car le processeur doit alors lire à partir de la table de pages hiérarchique, ce qui peut nécessiter plusieurs accès mémoire. En utilisant une taille de page mémoire plus grande, une seule entrée TLB peut représenter une plage mémoire plus grande. Cela entraîne moins de pression sur un TLB, et les applications gourmandes en mémoire peuvent avoir de meilleures performances.

Cependant, l'utilisation de grandes pages peut affecter négativement les performances du système. Par exemple, lorsqu'une grande quantité de mémoire est épinglée par une application, cela peut créer une pénurie de mémoire régulière et provoquer un pagination excessive dans d'autres applications, ralentissant ainsi l'ensemble du système. De plus, un système en cours d'exécution depuis longtemps pourrait produire une fragmentation excessive, ce qui pourrait rendre impossible la réservation de suffisamment de mémoire de grandes pages. Lorsque cela se produit, soit le système d'exploitation, soit la JVM revient à l'utilisation de pages régulières.

Linux et Windows prennent en charge les grandes pages.

Lorsque -XX:AOTMode est utilisé sur la ligne de commande, AOTClassLinking est automatiquement activé. Pour le désactiver, vous devez passer explicitement l'option -XX:-AOTClassLinking.

Lorsque -XX:AOTMode n'est pas utilisé sur la ligne de commande, AOTClassLinking est désactivé par défaut pour assurer une compatibilité totale avec les options CDS traditionnelles telles que `-Xshare:dump.

La première occurrence de la séquence spéciale %p dans *configfile* etcachefile est remplacée par l'ID du processus JVM lancé sur la ligne de commande, et de même, la première occurrence de %t est remplacée par l'horodatage de démarrage de la JVM. (Après remplacement, il ne doit plus y avoir d'occurrences de %p ou %t, afin d'éviter des problèmes avec les sous-processus.) Par exemple :

java -XX:AOTConfiguration=foo%p.aotconfig -XX:AOTCacheOutput=foo%p.aot -cp foo.jar Foo

créera deux fichiers : foopid123.aotconfig et foopid123.aot, où 123 est l'ID du processus JVM qui a exécuté l'application Foo.

EXEMPLES DE REGLAGE DES PERFORMANCES

Vous pouvez utiliser les options d'exécution avancées de Java pour optimiser les performances de vos applications.

Reglage pour un Debit Plus Eleve

Utilisez les commandes et options avancées suivantes pour obtenir des performances de débit plus élevées pour votre application :

java -server -XX:+UseParallelGC -XX:+UseLargePages -Xmn10g -Xms26g -Xmx26g

Reglage pour un Temps de Reponse Plus Bas

Utilisez les commandes et options avancées suivantes pour obtenir des temps de réponse plus bas pour votre application :

java -XX:+UseG1GC -XX:MaxGCPauseMillis=100

Maintenir un Tas Java Petit et Reduire lEmpreinte Dynamique des Applications Integrees

Utilisez les options d'exécution avancées suivantes pour maintenir un tas Java petit et réduire l'empreinte dynamique des applications intégrées :

-XX:MaxHeapFreeRatio=10 -XX:MinHeapFreeRatio=5

Remarque : Les valeurs par défaut pour ces deux options sont respectivement 70% et 40%. Étant donné que des sacrifices de performance peuvent survenir lors de l'utilisation de ces petits paramètres, vous devriez optimiser pour une petite empreinte en réduisant ces paramètres autant que possible sans introduire une dégradation inacceptable des performances.
