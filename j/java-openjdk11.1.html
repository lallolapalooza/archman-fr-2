-Xrs

Réduit l'utilisation des signaux du système d'exploitation par la JVM.

Les hooks d'arrêt permettent un arrêt ordonné d'une application Java en exécutant du code de nettoyage utilisateur (tel que la fermeture de connexions de base de données) à l'arrêt, même si la JVM se termine brutalement.

La JVM intercepte les signaux pour implémenter les hooks d'arrêt en cas de terminaison inattendue. La JVM utilise SIGHUP, SIGINT et SIGTERM pour initier l'exécution des hooks d'arrêt.

La JVM utilise un mécanisme similaire pour implémenter la fonctionnalité de vidage des piles de threads à des fins de débogage. La JVM utilise SIGQUIT pour effectuer des vidages de threads.

Les applications intégrant la JVM doivent souvent intercepter des signaux tels que SIGINT ou SIGTERM, ce qui peut interférer avec les gestionnaires de signaux de la JVM. L'option -Xrs est disponible pour résoudre ce problème. Lorsque -Xrs est utilisé, les masques de signaux pour SIGINT, SIGTERM, SIGHUP et SIGQUIT ne sont pas modifiés par la JVM, et les gestionnaires de signaux pour ces signaux ne sont pas installés.

Il y a deux conséquences à la spécification de -Xrs :

•Les vidages de threads SIGQUIT ne sont pas disponibles.
•Le code utilisateur est responsable de l'exécution des hooks d'arrêt, par exemple, en appelant System.exit() lorsque la JVM doit être terminée.

Ces options contrôlent le comportement d'exécution de la VM Java HotSpot.

-XX:+DisableAttachMechanism

Active l'option qui désactive le mécanisme permettant aux outils de se connecter à la JVM. Par défaut, cette option est désactivée, ce qui signifie que le mécanisme d'attachement est activé et que vous pouvez utiliser des outils tels que jcmd, jstack, jmap et jinfo.

-XX:ErrorFile=filename

Spécifie le chemin et le nom du fichier dans lequel les données d'erreur sont écrites en cas d'erreur irrécupérable. Par défaut, ce fichier est créé dans le répertoire de travail actuel et nommé hs_err_pidpid.log, où pid est l'identifiant du processus qui a causé l'erreur. L'exemple suivant
ple montre comment définir le fichier journal par défaut (notez que l'identifiant du processus est spécifié comme %p): 
-XX:ErrorFile=./hs_err_pid%p.log
L'exemple suivant montre comment définir le journal d'erreur sur /var/log/java/java_error.log: 
-XX:ErrorFile=/var/log/java/java_error.log
Si le fichier ne peut pas être créé dans le répertoire spécifié (en raison d'un espace insuffisant, d'un problème de permissions ou d'un autre problème), le fichier est créé dans le répertoire temporaire du système d'exploitation. Le répertoire temporaire est /tmp.

Vous pouvez l'activer pour les classes ayant des versions plus anciennes du bytecode.

Par défaut, la taille est définie sur 0, ce qui signifie que la JVM choisit automatiquement la taille des grandes pages.

L'exemple suivant illustre comment définir la taille des grandes pages sur 4 mégaoctets (MB) :

-XX:LargePageSizeInBytes=4m

-XX:MaxDirectMemorySize=size

-XX:NativeMemoryTracking=mode

Spécifie le mode de suivi de l'utilisation de la mémoire native de la JVM. Les arguments mode possibles pour cette option sont les suivants :

off

Ne pas suivre l'utilisation de la mémoire native de la JVM. C'est le comportement par défaut si vous ne spécifiez pas l'option -XX:NativeMemoryTracking .

summary

Suivre uniquement l'utilisation de la mémoire par les sous-systèmes de la JVM, tels que le tas Java, les classes, le code et les threads.

detail

En plus du suivi de l'utilisation de la mémoire par les sous-systèmes de la JVM, suivre l'utilisation de la mémoire par chaque CallSite, chaque région de mémoire virtuelle et ses régions engagées.

-XX:ObjectAlignmentInBytes=alignment

Définit l'alignement mémoire des objets Java (en octets). Par défaut, la valeur est définie sur 8 octets. La valeur spécifiée doit être une puissance de deux et doit se trouver dans la plage de 8 à 256 (inclus). Cette option permet d'utiliser des pointeurs compressés avec de grandes tailles de tas Java.

La limite de la taille du tas en octets est calculée comme suit :

4GB * ObjectAlignmentInBytes

Remarque : À mesure que la valeur d'alignement augmente, l'espace inutilisé entre les objets augmente également. Par conséquent, vous ne réaliserez peut-être aucun avantage de l'utilisation de pointeurs compressés avec de grandes tailles de tas Java.

-XX:OnError=string

L'exemple suivant montre comment l'option -XX:OnError peut être utilisée pour exécuter la commande gcore afin de créer l'image du cœur, et le débogueur est démarré pour s'attacher au processus en cas d'erreur irrécupérable (le %p désigne le processus courant) :

-XX:OnOutOfMemoryError=string

Définit une commande personnalisée ou une série de commandes séparées par des points-virgules à exécuter lorsqu'une exception OutOfMemoryError est levée pour la première fois. Si la chaîne contient des espaces, elle doit être entourée de guillemets. Pour un exemple de chaîne de commandes, voir la description de l'option -XX:OnError .

Options avancées du compilateur JIT

Ces options contrôlent la compilation dynamique juste-à-temps (JIT) effectuée par la machine virtuelle Java HotSpot.

-XX:+AggressiveOpts

Active l'utilisation de fonctionnalités d'optimisation de performance agressives, qui devraient devenir les options par défaut dans les prochaines versions. Par défaut, cette option est désactivée et les fonctionnalités de performance expérimentales ne sont pas utilisées.

-XX:AllocateInstancePrefetchLines=lignes

Définit le nombre de lignes à précharger avant le pointeur d'allocation d'instance. Par défaut, le nombre de lignes à précharger est défini à 1 : 
-XX:AllocateInstancePrefetchLines=1
Seule la machine virtuelle serveur Java HotSpot prend en charge cette option.

-XX:AllocatePrefetchDistance=taille

Définit la taille (en octets) de la distance de préchargement pour l'allocation d'objets. La mémoire qui va être écrite avec la valeur de nouveaux objets est préchargée jusqu'à cette distance à partir de l'adresse du dernier objet alloué. Chaque thread Java a son propre bloc d'allocation.

Les valeurs négatives indiquent que la distance de préchargement est choisie en fonction de la plateforme. Les valeurs positives représentent les octets à précharger. Ajoutez la lettre k ou K pour indiquer les kilooctets, m ou M pour indiquer les mégaoctets, g ou G pour indiquer les gigaoctets. La valeur par défaut est définie à -1.

L'exemple suivant montre comment définir la distance de préchargement à 1024 octets :

-XX:AllocatePrefetchDistance=1024
Seule la machine virtuelle serveur Java HotSpot prend en charge cette option.

-XX:AllocatePrefetchInstr=instruction

Définit l'instruction de préchargement pour précharger avant le pointeur d'allocation. Seule la machine virtuelle serveur Java HotSpot prend en charge cette option. Les valeurs possibles sont de 0 à 3. Les instructions réelles derrière les valeurs dépendent de la plateforme. Par défaut, l'instruction de préchargement est définie à 0 : 
-XX:AllocatePrefetchInstr=0
Seule la machine virtuelle serveur Java HotSpot prend en charge cette option.

-XX:AllocatePrefetchLines=lignes

Définit le nombre de lignes de cache à charger après la dernière allocation d'objet en utilisant les instructions de préchargement générées dans le code compilé. La valeur par défaut est 1 si le dernier objet alloué était une instance, et 3 s'il s'agissait d'un tableau.

L'exemple suivant montre comment définir le nombre de lignes de cache chargées à 5 :

-XX:AllocatePrefetchLines=5
Seule la machine virtuelle serveur Java HotSpot prend en charge cette option.

-XX:AllocatePrefetchStepSize=taille

Définit la taille du pas (en octets) pour les instructions de préchargement séquentielles. Ajoutez la lettre k ou K pour indiquer les kilooctets, m ou M pour indiquer les mégaoctets, g ou G pour indiquer les gigaoctets. Par défaut, la taille du pas est définie à 16 octets : 
-XX:AllocatePrefetchStepSize=16
Seule la machine virtuelle serveur Java HotSpot prend en charge cette option.

-XX:AllocatePrefetchStyle=style

Définit le style du code généré pour les instructions de préchargement. L'argument style est un entier de 0 à 3 :

0

Ne génère pas d'instructions de préchargement.

1

Exécute les instructions de préchargement après chaque allocation. C'est le paramètre par défaut.

2

Utilise le pointeur de filigrane du bloc d'allocation local au thread (TLAB) pour déterminer quand les instructions de préchargement sont exécutées.

3

Utilise l'instruction BIS sur SPARC pour le préchargement d'allocation.

Seule la machine virtuelle serveur Java HotSpot prend en charge cette option.

-XX:+BackgroundCompilation

Active la compilation en arrière-plan. Cette option est activée par défaut. Pour désactiver la compilation en arrière-plan, spécifiez -XX:-BackgroundCompilation (ce qui est équivalent à spécifier -Xbatch).

-XX:CICompilerCount=threads

Définit le nombre de threads de compilateur à utiliser pour la compilation. Par défaut, le nombre de threads est défini à 2 pour la JVM serveur, à 1 pour la JVM client, et il s'adapte au nombre de cœurs si la compilation par niveaux est utilisée. L'exemple suivant montre comment définir le nombre de threads à 2 : 
-XX:CICompilerCount=2

-XX:CodeCacheMinimumFreeSpace=taille

Définit l'espace libre minimum (en octets) requis pour la compilation. Ajoutez la lettre k ou K pour indiquer les kilooctets, m ou M pour indiquer les mégaoctets, g ou G pour indiquer les gigaoctets. Lorsque moins que l'espace libre minimum reste, la compilation s'arrête. Par défaut, cette option est définie à 500 Ko. L'exemple suivant montre comment définir l'espace libre minimum à 1024 Mo : 
-XX:CodeCacheMinimumFreeSpace=1024m

-XX:CompileCommand=commande,méthode[,option]

Spécifie une commande à effectuer sur une méthode. Par exemple, pour exclure la méthode indexOf() de la classe String de la compilation, utilisez ce qui suit : 
-XX:CompileCommand=exclude,java/lang/String.indexOf
Notez que le nom complet de la classe est spécifié, y compris tous les packages et sous-packages séparés par une barre oblique (/). Pour faciliter les opérations de copier-coller, il est également possible d'utiliser le format de nom de méthode produit par les options -XX:+PrintCompilation et -XX:+LogCompilation : 
-XX:CompileCommand=exclude,java.lang.String::indexOf
Si la méthode est spécifiée sans la signature, la commande sera appliquée à toutes les méthodes portant le nom spécifié. Cependant, vous pouvez également spécifier la signature de la méthode au format du fichier de classe. Dans ce cas, vous devriez encadrer les arguments entre guillemets, car sinon le shell traite le point-virgule comme la fin de la commande. Par exemple, si vous souhaitez exclure uniquement la méthode indexOf(String) de la classe String de la compilation, utilisez ce qui suit : 
-XX:CompileCommand="exclude,java/lang/String.indexOf,(Ljava/lang/String;)I"
Vous pouvez également utiliser l'astérisque (*) comme caractère générique pour les noms de classe et de méthode. Par exemple, pour exclure toutes les méthodes indexOf() dans toutes les classes de la compilation, utilisez ce qui suit : 
-XX:CompileCommand=exclude,*.indexOf
Les virgules et les points sont des alias pour les espaces, ce qui facilite la transmission des commandes du compilateur via un shell. Vous pouvez passer des arguments à -XX:CompileCommand en utilisant des espaces comme séparateurs en encadrant l'argument entre guillemets : 
-XX:CompileCommand="exclude java/lang/String indexOf"
Notez qu'après l'analyse des commandes passées sur la ligne de commande à l'aide des options -XX:CompileCommand, le compilateur JIT lit ensuite les commandes du fichier .hotspot_compiler. Vous pouvez ajouter des commandes à ce fichier ou spécifier un fichier différent à l'aide de l'option -XX:CompileCommandFile.

Pour ajouter plusieurs commandes, soit spécifiez l'option -XX:CompileCommand plusieurs fois, soit séparez chaque argument par le sépareur de nouvelle ligne (\n). Les commandes suivantes sont disponibles :

break

Définit un point d'arrêt lors du débogage de la JVM pour s'arrêter au début de la compilation de la méthode spécifiée.

compileonly

Exclut toutes les méthodes de la compilation à l'exception de la méthode spécifiée. Alternativement, vous pouvez utiliser l'option -XX:CompileOnly, qui permet de spécifier plusieurs méthodes.

dontinline

Empêche l'inlining de la méthode spécifiée.

exclude

Exclut la méthode spécifiée de la compilation.

help

Affiche un message d'aide pour l'option -XX:CompileCommand.

inline

Tente d'inliner la méthode spécifiée.

log

Exclut la journalisation de la compilation (avec l'option -XX:+LogCompilation) pour toutes les méthodes sauf la méthode spécifiée. Par défaut, la journalisation est effectuée pour toutes les méthodes compilées.

option

Cette commande peut être utilisée pour passer une option de compilation JIT à la méthode spécifiée à la place du dernier argument (option). L'option de compilation est définie à la fin, après le nom de la méthode. Par exemple, pour activer l'option BlockLayoutByFrequency pour la méthode append() de la classe StringBuffer, utilisez ce qui suit : 
-XX:CompileCommand=option,java/lang/StringBuffer.append,BlockLayoutByFrequency
Vous pouvez spécifier plusieurs options de compilation, séparées par des virgules ou des espaces.

print

Affiche le code assembleur généré après la compilation de la méthode spécifiée.

quiet

N'affiche pas les commandes de compilation. Par défaut, les commandes que vous spécifiez avec l'option -XX:CompileCommand sont affichées ; par exemple, si vous excluez de la compilation la méthode indexOf() de la classe String, alors ce qui suit sera affiché sur la sortie standard : 
CompilerOracle: exclude java/lang/String.indexOf
Vous pouvez supprimer cela en spécifiant l'option -XX:CompileCommand=quiet avant les autres options -XX:CompileCommand.

-XX:CompileCommandFile=nomfichier

Définit le fichier à partir duquel les commandes du compilateur JIT sont lues. Par défaut, le fichier .hotspot_compiler est utilisé pour stocker les commandes effectuées par le compilateur JIT.

Chaque ligne du fichier de commandes représente une commande, un nom de classe et un nom de méthode pour lesquels la commande est utilisée. Par exemple, cette ligne affiche le code assembleur pour la méthode toString() de la classe String :

print java/lang/String toString
Pour plus d'informations sur la spécification des commandes que le compilateur JIT doit effectuer sur les méthodes, voir l'option -XX:CompileCommand.

-XX:CompileOnly=méthodes

Définit la liste des méthodes (séparées par des virgules) auxquelles la compilation doit être limitée. Seules les méthodes spécifiées seront compilées. Spécifiez chaque méthode avec le nom complet de la classe (y compris les packages et sous-packages). Par exemple, pour compiler uniquement la méthode length()
méthode de la classe String et la méthode size() de la classe List, utilisez les éléments suivants : 
-XX:CompileOnly=java/lang/String.length,java/util/List.size
Notez que le nom complet de la classe est spécifié, y compris tous les packages et sous-packages séparés par une barre oblique (/). Pour faciliter les opérations de copier-coller, il est également possible d'utiliser le format de nom de méthode produit par les options -XX:+PrintCompilation et -XX:+LogCompilation : 
-XX:CompileOnly=java.lang.String::length,java.util.List::size
Bien que les jokers ne soient pas pris en charge, vous pouvez spécifier uniquement le nom de classe ou de package pour compiler toutes les méthodes de cette classe ou de ce package, ainsi que spécifier uniquement la méthode pour compiler des méthodes de ce nom dans n'importe quelle classe : 
-XX:CompileOnly=java/lang/String
-XX:CompileOnly=java/lang
-XX:CompileOnly=.length

-XX:CompileThreshold=invocations

-XX:+UseRTMLocking

Génère du code de verrouillage RTM (Restricted Transactional Memory) pour tous les verrous gonflés, avec le mécanisme de verrouillage normal comme gestionnaire de secours. Cette option est désactivée par défaut. Les options liées à RTM ne sont disponibles que pour la JVM Java HotSpot Server sur les processeurs x86 qui prennent en charge les extensions de synchronisation transactionnelle (TSX).

RTM fait partie du TSX d'Intel, qui est une extension d'instruction x86 et facilite la création d'applications multithreadées. RTM introduit les nouvelles instructions XBEGIN, XABORT, XEND et XTEST. Les instructions XBEGIN et XEND encapsulent un ensemble d'instructions à exécuter comme une transaction. Si aucun conflit n'est détecté lors de l'exécution de la transaction, les modifications de mémoire et de registre sont validées conjointement au niveau de l'instruction XEND. L'instruction XABORT peut être utilisée pour abandonner explicitement une transaction et l'instruction XEND pour vérifier si un ensemble d'instructions est exécuté dans une transaction.

Un verrou sur une transaction est gonflé lorsqu'un autre thread tente d'accéder aula même transaction, bloquant ainsi le thread qui n'avait pas initialement demandé l'accès à la transaction. RTM exige qu'un ensemble d'opérations de repli soit spécifié en cas d'abandon ou d'échec d'une transaction. Un verrou RTM est un verrou qui a été délégué au système TSX.

RTM améliore les performances des verrous fortement contestés avec peu de conflits dans une région critique (qui est un code auquel on ne peut pas accéder par plus d'un thread simultanément). RTM améliore également les performances du verrouillage à gros grain, qui n'est généralement pas performant dans les applications multithreadées. (Le verrouillage à gros grain est la stratégie consistant à conserver les verrous pendant de longues périodes pour minimiser le surcoût de prise et de libération des verrous, tandis que le verrouillage à grain fin est la stratégie consistant à essayer d'obtenir un parallélisme maximal en ne verrouillant que lorsque c'est nécessaire et en déverrouillant dès que possible.) De plus, pour les verrous légèrement contestés utilisés par différents threads, RTM peut réduire le partage de lignes de cache fictif, également appelé « cache line ping-pong ». Cela se produit lorsque plusieurs threads de différents processeurs accèdent à différentes ressources, mais que ces ressources partagent la même ligne de cache. En conséquence, les processeurs invalident de manière répétée les lignes de cache des autres processeurs, ce qui les oblige à lire depuis la mémoire principale au lieu de leur cache.

-XX:InitialSurvivorRatio=ratio

Définit le rapport initial de l'espace survivor utilisé par le garbage collector de débit (qui est activé par les options -XX:+UseParallelGC et/ou -XX:+UseParallelOldGC). Le dimensionnement adaptatif est activé par défaut avec le garbage collector de débit en utilisant les options -XX:+UseParallelGC et -XX:+UseParallelOldGC, et l'espace survivor est redimensionné en fonction du comportement de l'application, en commençant par la valeur initiale. La formule suivante peut être utilisée pour calculer la taille initiale de l'espace survivor (S) en fonction de la taille de la génération jeune (Y) et du rapport initial de l'espace survivor (R) :

S=Y/(R+2)
Le 2 dans l'équation représente deux espaces survivors. Plus la valeur spécifiée comme rapport initial de l'espace survivor est grande, plus la taille initiale de l'espace survivor est petite.

Par défaut, le rapport initial de l'espace survivor est défini sur 8. Si la valeur par défaut pour la taille de l'espace de la génération jeune (2 Mo) est utilisée, la taille initiale de l'espace survivor sera de 0,2 Mo.

GRANDES PAGES

Aussi connues sous le nom de pages géantes, les grandes pages sont des pages mémoire qui sont significativement plus grandes que la taille de page mémoire standard (qui varie en fonction du processeur et du système d'exploitation). Les grandes pages optimisent les tampons de traduction d'adresses (TLB) du processeur.

Un tampon de traduction d'adresses (TLB) est un cache de traduction de pages qui conserve les traductions d'adresses virtuelles vers physiques les plus récemment utilisées. Le TLB est une ressource système limitée. Une absence dans le TLB peut être coûteuse car le processeur doit alors lire dans la table de pages hiérarchique, ce qui peut nécessiter plusieurs accès mémoire. En utilisant une taille de page mémoire plus grande, une seule entrée de TLB peut représenter une plage mémoire plus grande. La pression sur le TLB sera moindre, et les applications gourmandes en mémoire peuvent avoir de meilleures performances.

Cependant, la mémoire des grandes pages peut affecter négativement les performances du système. Par exemple, lorsqu'une grande quantité de mémoire est épinglée par une application, cela peut créer une pénurie de mémoire régulière et provoquer un paging excessif dans d'autres applications et ralentir l'ensemble du système. De plus, un système qui est allumé depuis longtemps peut produire une fragmentation excessive, ce qui pourrait rendre impossible la réservation d'une quantité suffisante de mémoire en grandes pages. Lorsque cela se produit, soit le système d'exploitation, soit la JVM revient à l'utilisation de pages régulières.

Prise en charge des grandes pages

Solaris et Linux prennent en charge les grandes pages.

Solaris

Solaris 9 et versions ultérieures incluent la prise en charge de tailles de pages multiples (MPSS) ; aucune configuration supplémentaire n'est nécessaire. Voir http://www.oracle.com/technetwork/server-storage/solaris10/overview/solaris9-features-scalability-135663.html.

Linux

Le noyau 2.6 prend en charge les grandes pages. Certains fournisseurs ont rétroporté le code vers leurs versions basées sur le 2.4. Pour vérifier si votre système peut prendre en charge la mémoire en grandes pages, essayez ce qui suit :

# cat /proc/meminfo | grep Huge
HugePages_Total: 0
HugePages_Free: 0
Hugepagesize: 2048 kB

Si la sortie montre les trois variables "Huge", alors votre système peut prendre en charge la mémoire en grandes pages mais elle doit être configurée. Si la commande n'imprime rien, alors votre système ne prend pas en charge les grandes pages. Pour configurer le système afin d'utiliser la mémoire en grandes pages, connectez-vous en tant que root, et suivez ensuite ces étapes :

1.Si vous utilisez l'option -XX:+UseSHM (au lieu de -XX:+UseHugeTLBFS), augmentez la SHMMAX valeur. Elle doit être plus grande que la taille du tas Java. Sur un système avec 4 Go de RAM physique (ou moins), ce qui suit rendra toute la mémoire partageable : 
# echo 4294967295 > /proc/sys/kernel/shmmax
2.Si vous utilisez l'option -XX:+UseSHM ou -XX:+UseHugeTLBFS, spécifiez le nombre de grandes pages. Dans l' exemple suivant, 3 Go d'un système de 4 Go sont réservés pour les grandes pages (en supposant une taille de page de 2048kB, alors 3 Go = 3 * 1024 Mo = 3072 Mo = 3072 * 1024 ko = 3145728 ko et 3145728 ko / 2048 ko = 1536) : 
# echo 1536 > /proc/sys/vm/nr_hugepages

Remarque
4 • Notez que les valeurs contenues dans /proc seront réinitialisées après le redémarrage de votre système, vous pouvez donc vouloir les définir dans un script d'initialisation (par exemple, rc.local ou sysctl.conf). 4 • Si vous configurez (ou redimensionnez) les paramètres du noyau du système d'exploitation /proc/sys/kernel/shmmax ou /proc/sys/vm/nr_hugepages, les processus Java peuvent allouer des grandes pages pour des zones en plus du tas Java. Ces étapes peuvent allouer des grandes pages pour les zones suivantes : 4 • Tas Java 4 • Cache de code 4 • La structure de données de bitmap de marquage pour le GC parallèle Par conséquent, si vous configurez le nr_hugepages paramètre à la taille du tas Java, alors la JVM peut échouer à allouer les zones du cache de code en grandes pages car ces zones sont assez grandes en taille.
