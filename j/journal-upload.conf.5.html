RÉPERTOIRES DE CONFIGURATION ET

PRÉCÉDENCE

La configuration par défaut est définie lors de la compilation, la configuration n'est donc nécessaire que lorsqu'il faut s'écarter de ces valeurs par défaut. Le fichier de configuration principal est chargé depuis l'un des répertoires listés par ordre de priorité, seul le premier fichier trouvé est utilisé : /etc/systemd/, /run/systemd/, /usr/local/lib/systemd/ [1], /usr/lib/systemd/. La version du fichier fournie par le fournisseur contient des entrées commentées montrant les valeurs par défaut, à titre de guide pour l'administrateur. Des surcharges locales peuvent également être créées en créant des drop-ins, comme décrit ci-dessous. Le fichier de configuration principal peut également être modifié à cette fin (ou une copie dans /etc/ s'il est fourni sous /usr/), cependant l'utilisation de drop-ins pour la configuration locale est recommandée par rapport aux modifications du fichier de configuration

principal.

En plus du fichier de configuration principal, des extraits de configuration drop-in sont lus depuis /usr/lib/systemd/*.conf.d/, /usr/local/lib/systemd/*.conf.d/, et /etc/systemd/*.conf.d/. Ces drop-ins ont une priorité plus élevée et remplacent le fichier de configuration principal. Les fichiers dans les sous-répertoires de configuration *.conf.d/ sont triés par leur nom de fichier dans l'ordre lexicographique, quel que soit le sous-répertoire dans lequel ils se trouvent. Lorsque plusieurs fichiers spécifient la même option, pour les options qui n'acceptent qu'une seule valeur, l'entrée du fichier trié en dernier prend la priorité, et pour les options qui acceptent une liste de valeurs, les entrées sont collectées au fur et à mesure qu'elles apparaissent dans les fichiers

triés.

Lorsque les paquets doivent personnaliser la configuration, ils peuvent installer des drop-ins sous /usr/. Les fichiers dans /etc/ sont réservés à l'administrateur local, qui peut utiliser cette logique pour remplacer les fichiers de configuration installés par les paquets du fournisseur. Des drop-ins doivent être utilisés pour remplacer les drop-ins des paquets, car le fichier de configuration principal a une priorité plus faible. Il est recommandé de préfixer tous les noms de fichiers dans ces sous-répertoires avec un numéro à deux chiffres et un tiret, afin de simplifier le tri. Cela définit également un concept de priorité des drop-ins pour permettre aux fournisseurs de systèmes d'exploitation de fournir des drop-ins dans une plage spécifique inférieure à celle utilisée par les utilisateurs. Cela devrait réduire le risque que les drop-ins des paquets remplacent accidentellement les drop-ins définis par les utilisateurs. Il est recommandé d'utiliser la plage 10-40 pour les drop-ins dans /usr/ et la plage 60-90 pour les drop-ins dans /etc/ et /run/, afin de s'assurer que les drop-ins locaux et transitoires ont la priorité sur les drop-ins fournis par le fournisseur du système

d'exploitation.

Pour désactiver un fichier de configuration fourni par le fournisseur, la méthode recomm

andée est de placer un lien symbolique vers /dev/null dans le répertoire de configuration
dans /etc/, avec le même nom de fichier que le fichier de configuration du fournisseur.

OPTION

S

Toutes les options sont configurées dans la section [Upload]

URL

=
L'URL vers laquelle envoyer les entrées du journal. Voir la description de l'option --url= dans systemd-journal-upload(8) pour la description des valeurs possibles. Il n'y a pas de valeur par défaut, donc soit cette option soit l'option de ligne de commande doit toujours être présente pour effectuer un envoi.

NetworkTimeoutSec

=
Lorsque la connectivité réseau au serveur est perdue, cette option configure le temps d'attente pour que la connectivité soit rétablie. Si le serveur n'est pas joignable via le réseau pendant le temps configuré, systemd-journal-upload se termine. Prend une valeur en secondes (ou dans d'autres unités de temps si suffixée par "ms", "min", "h", etc). Pour plus de détails, voir systemd.time(7).

ns la ver
sion 249.

Compression

=
Configure l'algorithme de compression à appliquer aux données des journaux avant l'envoi. Prend une liste d'algorithmes de compression séparés par des espaces, ou "no". Les algorithmes pris en charge sont "zstd", "xz", ou "lz4". Optionnellement, chaque algorithme peut être suivi d'un deux-points (":") et de son niveau de compression, par exemple "zstd:4". Le niveau de compression doit être un entier positif. Lorsque "no" est spécifié, aucun algorithme de compression ne sera appliqué aux données à envoyer. Cette option peut être spécifiée plusieurs fois. Si une chaîne vide est assignée, alors toutes les assignations précédentes sont effacées. Par défaut non défini, et tous les algorithmes de compression pris en charge avec leurs niveaux de compression par défaut sont listés.

Exemple

: 
Compress
ion=zstd
:4 lz4:2

Même lorsque la compression est activée, les requêtes initiales sont envoyées sans compression. Elle devient effective soit si "ForceCompression=" est activé, soit si la réponse du serveur contient des en-têtes "Accept-Encoding" avec une liste d'algorithmes de compression contenant l'un des algorithmes spécifiés dans cette

option.

sion 258.

ForceCompression

=
Prend une valeur booléenne, force l'utilisation de la compression sans négociation d'encodage de contenu. Par défaut "false".

Ajouté da

ns la ver
sion 258.

Header

=
Spécifie un en-tête HTTP supplémentaire à ajouter à chaque requête vers une URL. Prend une paire nom de l'en-tête et valeur séparés par un deux-points (":"), par exemple "Nom:Valeur". Le nom de l'en-tête peut contenir des valeurs alphanumériques, ainsi que les symboles "_" et "-". Cette option peut être spécifiée plus d'une fois, auquel cas tous les en-têtes listés seront définis. Si le même nom d'en-tête est listé plus d'une fois, toutes ses valeurs uniques seront concaténées avec une virgule. Définir Header= à une chaîne vide efface toutes les assignations précédentes.

Exemple

: 
Header=HeaderName: HeaderValue
Header=HeaderName: NewValue
Header=HeaderName: HeaderValue

ajoute l'en-tête "HeaderName" avec "HeaderValue, NewValue" à chaque requête

HTTP.
