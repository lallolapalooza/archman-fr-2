NOM

javac - lire des déclarations Java et les compiler en fichiers classe

SYNTAXE

javac [options] [fichiers-source-ou-noms-de-classes]

options
Options de ligne de commande.
fichiers-source-ou-noms-de-classes
Fichiers source à compiler (par exemple, Forme.java) ou les noms de classes précédemment compilées à traiter pour les annotations (par exemple, geometrie.MaForme).

DESCRIPTION

La commande javac lit des fichiers source contenant des déclarations de modules, de paquets et de types écrites dans le langage de programmation Java, et les compile en fichiers classe qui s'exécutent sur la Java Virtual Machine.

La commande javac peut également traiter les annotations dans les fichiers source et les classes Java.

Les fichiers source doivent avoir l'extension de nom de fichier .java. Les fichiers classe ont l'extension de nom de fichier .class. Les fichiers source et classe ont normalement des noms de fichiers qui identifient leur contenu. Par exemple, une classe appelée Forme serait déclarée dans un fichier source appelé Forme.java et compilée en un fichier classe appelé Forme.class.

Il existe deux façons de spécifier des fichiers source à javac :

•
Pour un petit nombre de fichiers source, vous pouvez lister leurs noms de fichiers sur la ligne de commande.
•
Pour un grand nombre de fichiers source, vous pouvez utiliser l'option @nomfichier sur la ligne de commande pour spécifier un fichier d'arguments qui liste leurs noms de fichiers. Voir Options Standard pour une description de l'option et Fichiers d'Arguments de Ligne de Commande pour une description des fichiers d'arguments de javac.

L'ordre des fichiers source spécifiés sur la ligne de commande ou dans un fichier d'arguments n'est pas important. javac compilera les fichiers ensemble, en groupe, et résoudra automatiquement toutes les dépendances entre les déclarations des différents fichiers source.

javac s'attend à ce que les fichiers source soient organisés dans une ou plusieurs hiérarchies de répertoires sur le système de fichiers, décrites dans Organisation du Code Source.

Pour compiler un fichier source, javac doit trouver la déclaration de chaque classe ou interface qui est utilisée, étendue ou implémentée par le code du fichier source. Cela permet à javac de vérifier que le code a le droit d'accéder à ces classes et interfaces. Plutôt que de spécifier explicitement les fichiers source de ces classes et interfaces, vous pouvez utiliser des options de ligne de commande pour indiquer à javac où rechercher leurs fichiers source. Si vous avez déjà compilé ces fichiers source, vous pouvez utiliser des options pour indiquer à javac où rechercher les fichiers classe correspondants. Les options, dont les noms se terminent par « path », sont décrites dans Options Standard, et plus en détail dans Configuration d'une Compilation et Recherche de Déclarations de Modules, Paquets et Types.

Par défaut, javac compile chaque fichier source en un fichier classe dans le même répertoire que le fichier source. Cependant, il est recommandé de spécifier un répertoire de destination séparé avec l'option -d.

Les options de ligne de commande et les variables d'environnement contrôlent également la manière dont javac effectue diverses tâches :

•
Compilation de code destiné à s'exécuter sur des versions antérieures du JDK.
•
Compilation de code destiné à s'exécuter sous un débogueur.
•
Vérification des problèmes de style dans le code source Java.
•
Vérification des problèmes dans les commentaires javadoc (/** ... */).
•
Traitement des annotations dans les fichiers source et les fichiers classe.
•
Mise à jour et application de correctifs aux modules dans l'environnement de compilation.

javac prend en charge la Compilation pour les Versions Antérieures de la Plateforme et peut également être invoqué depuis du code Java en utilisant l'une des nombreuses APIs.

OPTIONS

javac fournit des options standard et des options supplémentaires qui sont soit non standard, soit destinées à un usage avancé.

Certaines options prennent un ou plusieurs arguments. Si un argument contient des espaces ou d'autres caractères d'espacement, la valeur doit être entre guillemets conformément aux conventions de l'environnement utilisé pour invoquer javac. Si l'option commence par un tiret simple (-), l'argument doit soit suivre directement le nom de l'option, soit être séparé par deux-points (:) ou un espace, selon l'option. Si l'option commence par deux tirets (--), l'argument peut être séparé soit par un espace, soit par un signe égal (=) sans espace supplémentaire. Par exemple,


-Anom="J. Duke"
-proc:only
-d monRepertoire
--module-version 3
--module-version=3

Dans les listes d'options suivantes, un argument de chemin représente un chemin de recherche, composé d'une liste d'emplacements du système de fichiers séparés par le caractère séparateur de chemin de la plateforme (point-virgule ; sous Windows, ou deux-points : sur d'autres systèmes). Selon l'option, les emplacements du système de fichiers peuvent être des répertoires, des fichiers JAR ou des fichiers JMOD.

Options Standard

@nomfichier
Lit les options et les noms de fichiers à partir d'un fichier. Pour raccourcir ou simplifier la commande javac, vous pouvez spécifier un ou plusieurs fichiers contenant des arguments pour la commande javac (sauf les options -J). Cela vous permet de créer des commandes javac de n'importe quelle longueur sur n'importe quel système d'exploitation. Voir Fichiers d'Arguments de Ligne de Commande.
-Acle[=valeur]
Spécifie les options à passer aux processeurs d'annotations. Ces options ne sont pas interprétées directement par javac, mais sont mises à disposition pour être utilisées par des processeurs individuels. La valeur de la cle doit être un ou plusieurs identifiants séparés par un point (.).
--add-modules module,module
Spécifie les modules racine à résoudre en plus des modules initiaux, ou tous les modules du chemin des modules si module est ALL-MODULE-PATH.
--boot-class-path chemin ou -bootclasspath chemin
Remplace l'emplacement des fichiers classe de démarrage.

Note : Ceci ne peut être utilisé que lors de la compilation pour des versions antérieures au JDK 9. Le cas échéant, voir les descriptions dans --release, -source, ou -target pour plus de détails. Pour le JDK 9 ou plus récent, voir --system.

--class-path chemin, -classpath chemin, ou -cp chemin
Spécifie où trouver les fichiers classe utilisateur et les processeurs d'annotations. Ce chemin de classes remplace le chemin de classes utilisateur dans l
variable d'environnement CLASSPATH.
•
Si --class-path, -classpath ou -cp ne sont pas spécifiés, alors le chemin de classe utilisateur est la valeur de la variable d'environnement CLASSPATH, si elle est définie, sinon le répertoire courant.
•
Si vous ne compilez pas de code pour les modules, si l'option --source-path ou -sourcepath` n'est pas spécifiée, alors le chemin de classe utilisateur est également recherché pour les fichiers source.
•
Si l'option -processorpath n'est pas spécifiée, alors le chemin de classe est également recherché pour les processeurs d'annotations.
-d répertoire
Définit le répertoire de destination (ou répertoire de sortie des classes) pour les fichiers de classe. Si une classe fait partie d'un package, alors javac place le fichier de classe dans un sous-répertoire qui reflète le nom du module (si approprié) et le nom du package. Le répertoire, et tous les sous-répertoires nécessaires, seront créés s'ils n'existent pas déjà.

Si l'option -d n'est pas spécifiée, alors javac place chaque fichier de classe dans le même répertoire que le fichier source à partir duquel il a été généré.

Sauf lors de la compilation de code pour plusieurs modules, le contenu du répertoire de sortie des classes sera organisé dans une hiérarchie de packages. Lors de la compilation de code pour plusieurs modules, le contenu du répertoire de sortie sera organisé dans une hiérarchie de modules, avec le contenu de chaque module dans un sous-répertoire séparé, chacun organisé comme une hiérarchie de packages.

Note : Lors de la compilation de code pour un ou plusieurs modules, le répertoire de sortie des classes sera automatiquement vérifié lors de la recherche de classes précédemment compilées. Lorsque vous ne compilez pas pour des modules, pour des raisons de compatibilité ascendante, le répertoire n'est pas automatiquement vérifié pour les classes précédemment compilées, et il est donc recommandé de spécifier le répertoire de sortie des classes comme l'un des emplacements du chemin de classe utilisateur, en utilisant l'option --class-path ou l'une de ses formes alternatives.

-deprecation
Affiche une description de chaque utilisation ou surcharge d'un membre ou d'une classe obsolète. Sans l'option -deprecation, javac affiche un résumé des fichiers source qui utilisent ou surchargent des membres ou des classes obsolètes. L'option -deprecation est un raccourci pour -Xlint:deprecation.
--enable-preview
Active les fonctionnalités linguistiques en avant-première. Utilisé conjointement avec -source ou --release.
-encoding encodage
Spécifie l'encodage des caractères utilisé par les fichiers source, tel que EUC-JP et UTF-8. Si l'option -encoding n'est pas spécifiée, alors le convertisseur par défaut de la plateforme est utilisé.

Si vous compilez pour une version de la plateforme qui prend en charge le mécanisme d'extension, alors cette option spécifie les répertoires qui contiennent les classes d'extension. Voir [Compilation pour d'autres versions de la plateforme].

Le répertoire, et tous les sous-répertoires nécessaires, seront créés s'ils n'existent pas déjà.

VARIABLES D'ENVIRONNEMENT

CLASSPATH

Si l'option --class-path ou l'une de ses formes alternatives n'est pas spécifiée, le classpath sera par défaut la valeur de la variable d'environnement CLASSPATH si elle est définie. Cependant, il est recommandé de ne pas définir cette variable d'environnement et d'utiliser l'option --class-path pour fournir une valeur explicite pour le classpath lorsqu'elle est nécessaire.

JDK_JAVAC_OPTIONS

Le contenu de la variable d'environnement JDK_JAVAC_OPTIONS, séparé par des espaces blancs ( ) ou des caractères d'espacement ( \n, \t, \r, ou \f) est ajouté au début des arguments de la ligne de commande passés à javac sous forme de liste d'arguments.

L'exigence de codage pour la variable d'environnement est la même que celle de la ligne de commande javac sur le système. Le contenu de la variable d'environnement JDK_JAVAC_OPTIONS est traité de la même manière que celui spécifié sur la ligne de commande.

Des guillemets simples (') ou des guillemets doubles (") peuvent être utilisés pour entourer les arguments contenant des caractères d'espacement. Tout le contenu entre le guillemet ouvrant et le premier guillemet fermant correspondant est conservé en supprimant simplement la paire de guillemets. Si un guillemet correspondant n'est pas trouvé, le lanceur s'arrêtera avec un message d'erreur. Les fichiers @fichiers sont pris en charge tels qu'ils sont spécifiés sur la ligne de commande. Cependant, comme pour les fichiers @fichiers, l'utilisation d'un caractère générique n'est pas prise en charge.

Exemples de mise entre guillemets d'arguments contenant des espaces blancs :

export JDK_JAVAC_OPTIONS='@"C:\espaces blancs\fichier_args"'

export JDK_JAVAC_OPTIONS='"@C:\espaces blancs\fichier_args"'

Un fichier d'arguments peut inclure des options de ligne de commande et des noms de fichiers source dans n'importe quelle combinaison. CONFIGURATION DU SYSTÈME DE MODULES

Si vous souhaitez inclure des modules supplémentaires dans votre compilation, utilisez l'option --add-modules. Cela peut être nécessaire lorsque vous compilez du code qui ne fait pas partie d'un module, ou qui fait partie d'un module automatique, et que le code fait référence à des API dans les modules supplémentaires.

Si vous souhaitez restreindre l'ensemble des modules de votre compilation, utilisez l'option --limit-modules. Cela peut être utile si vous souhaitez vous assurer que le code que vous compilez est capable de s'exécuter sur un système avec un ensemble limité de modules installés.

Si vous souhaitez casser l'encapsulation et spécifier que des packages supplémentaires doivent être considérés comme exportés par un module, utilisez l'option --add-exports. Cela peut être utile lors de tests en boîte blanche ; il est fortement déconseillé de s'appuyer sur l'accès aux API internes dans le code de production.

Si vous souhaitez spécifier que des packages supplémentaires doivent être considérés comme requis par un module, utilisez l'option --add-reads. Cela peut être utile lors de tests en boîte blanche ; il est fortement déconseillé de s'appuyer sur l'accès aux API internes dans le code de production.

Vous pouvez patcher du contenu supplémentaire dans n'importe quel module en utilisant l'option --patch-module. Voir [Patching d'un Module] pour plus de détails.

RECHERCHE DE DÉCLARATIONS DE MODULES, DE PACKAGES ET DE TYPES

Pour compiler un fichier source, le compilateur a souvent besoin d'informations sur un module ou un type, mais la déclaration ne se trouve pas dans les fichiers source spécifiés sur la ligne de commande.

javac a besoin d'informations de type pour chaque classe ou interface utilisée, étendue ou implémentée dans le fichier source. Cela inclut les classes et interfaces non explicitement mentionnées dans le fichier source, mais qui fournissent des informations par l'héritage.

Par exemple, lorsque vous créez une sous-classe de java.awt.Window, vous utilisez également les classes ancêtres de Window : java.awt.Container, java.awt.Component et java.lang.Object.

Lors de la compilation de code pour un module, le compilateur doit également avoir accès à la déclaration de ce module.

Une recherche réussie peut produire un fichier de classe, un fichier source, ou les deux. Si les deux sont trouvés, vous pouvez utiliser l'option -Xprefer pour indiquer au compilateur lequel utiliser.

Si une recherche trouve et utilise un fichier source, alors par défaut javac compile ce fichier source. Ce comportement peut être modifié avec -implicit.

Le compilateur peut ne pas découvrir le besoin de certaines informations de type avant la fin du traitement des annotations. Lorsque les informations de type sont trouvées dans un fichier source et qu'aucune option -implicit n'est spécifiée, le compilateur émet un avertissement indiquant que le fichier est compilé sans être soumis au traitement des annotations. Pour désactiver l'avertissement, spécifiez le fichier sur la ligne de commande (afin qu'il soit soumis au traitement des annotations) ou utilisez l'option -implicit pour spécifier si des fichiers de classe doivent être générés ou non pour de tels fichiers source.

La manière dont javac localise les déclarations de ces types dépend si la référence existe dans du code pour un module ou non.

Recherche dans les chemins orientés paquets

Lors de la recherche d'un fichier source ou de classe sur un chemin composé d'emplacements orientés paquets, javac vérifiera chaque emplacement du chemin tour à tour pour la présence possible du fichier. La première occurrence d'un fichier particulier masque toute occurrence ultérieure de fichiers portant le même nom. Ce masquage n'affecte aucune recherche pour d'autres fichiers portant un nom différent. Cela peut être pratique lors de la recherche de fichiers source, qui peuvent être regroupés dans différents emplacements, tels que du code partagé, du code spécifique à la plateforme et du code généré. Cela peut également être utile lors de l'injection de versions alternatives d'un fichier de classe dans un package, à des fins de débogage ou d'instrumentation. Mais cela peut aussi être dangereux, par exemple lorsque l'on place des versions incompatibles d'une bibliothèque sur le chemin de classe.

Recherche dans les chemins orientés modules

Avant d'analyser tous les chemins de modules pour les déclarations de packages ou de types, javac analysera paresseusement les chemins et emplacements suivants pour déterminer les modules qui seront utilisés dans la compilation.

•
Le chemin source des modules (voir l'option --module-source-path)
•
Le chemin des modules améliorable (voir l'option --upgrade-module-path)
•
Les modules système (voir l'option --system)
•
Le chemin des modules utilisateur (voir l'option --module-path)

Pour tout module, la première occurrence du module lors de l'analyse masque complètement toute apparition ultérieure d'un module portant le même nom. Lors de la localisation des modules, javac est capable de déterminer les packages exportés par le module et d'associer à chaque module un chemin orienté paquet pour le contenu du module. Pour tout module précédemment compilé, ce chemin sera typiquement une seule entrée pour un répertoire ou un fichier fournissant une hiérarchie interne de type répertoire, tel qu'un fichier JAR. Ainsi, lors de la recherche d'un type se trouvant dans un package connu pour être exporté par un module, javac peut localiser la déclaration directement et efficacement.

Recherche de la déclaration d'un module

Si le module a été préalablement compilé, la déclaration du module se trouve dans un fichier nommé module-info.class à la racine de la hiérarchie de packages du contenu du module.

Si le module fait partie de ceux en cours de compilation, la déclaration du module sera soit le fichier nommé module-info.class à la racine de la hiérarchie de packages du module dans le répertoire de sortie des classes, soit le fichier nommé module-info.java dans l'un des emplacements du chemin source ou du chemin source des modules pour le module.

HIÉRARCHIES DE RÉPERTOIRES

javac suppose généralement que les fichiers source et les fichiers de classe compilés seront organisés dans une hiérarchie de répertoires du système de fichiers ou dans un type de fichier qui prend en charge une hiérarchie de répertoires interne, tel qu'un fichier JAR. Trois types de hiérarchie sont pris en charge : une hiérarchie de packages, une hiérarchie de modules et une hiérarchie source de modules.

Bien que javac soit assez souple quant à l'organisation du code source, au-delà de l'attente que le code source soit organisé dans une ou plusieurs hiérarchies de packages, et puisse généralement s'adapter aux organisations prescrites par les environnements de développement et les outils de build, les outils Java en général, et javac et le lanceur Java en particulier, sont plus stricts quant à l'organisation des fichiers de classe compilés, qui seront organisés dans des hiérarchies de packages ou des hiérarchies de modules, selon le cas.

L'emplacement de ces hiérarchies est spécifié à javac via des options en ligne de commande, dont les noms se terminent généralement par "path", comme --source-path ou --class-path. De plus, en règle générale, les options de chemin dont le nom inclut le mot module, comme --module-path, sont utilisées pour spécifier les hiérarchies de modules, bien que certaines options de chemin liées aux modules permettent de spécifier une hiérarchie de packages au niveau de chaque module. Toutes les autres options de chemin sont utilisées pour spécifier des hiérarchies de packages.

Hiérarchie de packages

Dans une hiérarchie de packages, les répertoires et sous-répertoires sont utilisés pour représenter les parties constitutives du nom du package, le fichier source ou le fichier de classe compilé pour un type étant stocké sous forme de fichier avec l'extension .java ou .class dans le répertoire le plus imbriqué.

Par exemple, dans une hiérarchie de packages, le fichier source d'une classe com.example.MyClass sera stocké dans le fichier com/example/MyClass.java

Hiérarchie de modules

Dans une hiérarchie de modules, le premier niveau de répertoires est nommé d'après les modules de la hiérarchie ; à l'intérieur de chacun de ces répertoires, le contenu du module est organisé en hiérarchies de packages.

Par exemple, dans une hiérarchie de modules, le fichier de classe compilé d'un type appelé com.example.MyClass dans un module appelé my.library sera stocké dans my.library/com/example/MyClass.class.

Les différents répertoires de sortie utilisés par javac (le répertoire de sortie des classes, le répertoire de sortie des sources et le répertoire de sortie des en-têtes natifs) seront tous organisés en une hiérarchie de modules lorsque plusieurs modules sont compilés.

Hiérarchie source de modules

Bien que la source de chaque module individuel doive toujours être organisée en une hiérarchie de packages, il peut être pratique de regrouper ces hiérarchies dans une hiérarchie source de modules. Ceci est similaire à une hiérarchie de modules, sauf qu'il peut y avoir des répertoires intermédiaires entre le répertoire du module et le répertoire racine de la hiérarchie de packages pour le code source du module.

Par exemple, dans une hiérarchie source de modules, le fichier source d'un type appelé com.example.MyClass dans un module appelé my.library peut être stocké dans un fichier tel que my.library/src/main/java/com/example/MyClass.java.

L_OPTION MODULE SOURCE PATH

L'option --module-source-path a deux formes : une forme spécifique au module, dans laquelle un chemin de package est donné pour chaque module contenant du code à compiler, et une forme motif de module, dans laquelle le chemin source pour chaque module est spécifié par un motif. La forme spécifique au module est généralement plus simple à utiliser lorsqu'un petit nombre de modules sont impliqués ; la forme motif de module peut être plus pratique lorsque le nombre de modules est important et que les modules sont organisés de manière régulière pouvant être décrite par un motif.

Plusieurs instances de l'option --module-source-path peuvent être fournies, chacune utilisant soit la forme motif de module, soit la forme spécifique au module, sous réserve des limitations suivantes :

•
la forme motif de module ne peut être utilisée qu'une seule fois
•
la forme spécifique au module ne peut être utilisée qu'une seule fois pour un module donné

Si la forme spécifique au module est utilisée pour un module, le chemin de recherche associé remplace tout chemin qui aurait autrement pu être déduit de la forme motif de module.

Forme spécifique au module

La forme spécifique au module permet de donner un chemin de recherche explicite pour tout module spécifique. Cette forme est :

•
--module-source-path nom-module=chemin-fichier (séparateur-chemin chemin-fichier)*

Le caractère séparateur de chemin est ; sous Windows, et : sinon.

Note : ceci est similaire à la forme utilisée pour l'option --patch-module.

Forme motif de module

La forme motif de module permet une spécification concise du chemin source des modules pour un nombre quelconque de modules organisés de manière régulière.

•
--module-source-path motif

Le motif est défini par les règles suivantes, qui sont appliquées dans l'ordre :

•
L'argument est considéré comme une série de segments séparés par le caractère séparateur de chemin (; sous Windows et : sinon).
•
Chaque segment contenant des accolades de la forme

chaîne1{alt1 ( ,alt2 )* } chaîne2

est considéré comme remplacé par une série de segments formés en "développant" les accolades :


chaîne1 alt1 chaîne2
chaîne1 alt2 chaîne2
et ainsi de suite...

Les accolades peuvent être imbriquées.

Cette règle s'applique à toutes les utilisations d'accolades.

•
Chaque segment doit contenir au plus un astérisque (*). Si un segment ne contient pas d'astérisque, il est considéré comme si le caractère séparateur de fichier et un astérisque étaient ajoutés.

Pour tout module M, le chemin source de ce module est formé à partir de la série de segments obtenus en substituant le nom du module M à l'astérisque dans chaque segment.

Note : dans ce contexte, l'astérisque est uniquement utilisé comme marqueur spécial, pour indiquer la position dans le chemin du nom du module. Il ne doit pas être confondu avec l'utilisation de * comme caractère joker de nom de fichier, tel qu'on le trouve sur la plupart des systèmes d'exploitation.

PATCHING MODULES

javac autorise le patching de tout contenu, qu'il soit sous forme source ou compilée, dans n'importe quel module à l'aide de l'option --patch-module. Vous pourriez vouloir le faire pour compiler des implémentations alternatives d'une classe à patcher au moment de l'exécution dans une JVM, ou pour injecter des classes supplémentaires dans le module, par exemple lors de tests.

La forme de l'option est :

•
--patch-module nom-module=chemin-fichier (séparateur-chemin chemin-fichier )*

Le caractère séparateur de chemin est ; sous Windows, et : sinon. Les chemins donnés pour le module doivent spécifier la racine d'une hiérarchie de packages pour le contenu du module.

L'option ne peut être donnée qu'une seule fois pour un module donné. Tout contenu sur le chemin masquera tout contenu portant le même nom plus loin dans le chemin et dans le module patché.

Lors du patching de code source dans plusieurs modules, --module-source-path doit également être utilisé, afin que le répertoire de sortie soit organisé selon une hiérarchie de modules et capable de contenir les fichiers de classe compilés pour les modules en cours de compilation.

TRAITEMENT DES ANNOTATIONS

La commande javac offre un support direct pour le traitement des annotations.

L'API pour les processeurs d'annotations est définie dans les packages javax.annotation.processing et javax.lang.model et leurs sous-packages.

Comment fonctionne le traitement des annotations

Sauf si le traitement des annotations est désactivé avec l'option -proc:none, le compilateur recherche tous les processeurs d'annotations disponibles. Le chemin de recherche peut être spécifié avec l'option -processorpath. Si aucun chemin n'est spécifié, le classpath utilisateur est utilisé. Les processeurs sont localisés au moyen de fichiers de configuration de fournisseurs de services nommés META-INF/services/javax.annotation.processing. Les processeurs sur le chemin de recherche. De tels fichiers doivent contenir les noms de tous les processeurs d'annotations à utiliser, listés un par ligne. Alternativement, les processeurs peuvent être spécifiés explicitement, en utilisant l'option -processor.

Après avoir analysé les fichiers source et les classes sur la ligne de commande pour déterminer quelles annotations sont présentes, le compilateur interroge les processeurs pour déterminer quelles annotations ils traitent. Lorsqu'une correspondance est trouvée, le processeur est appelé. Un processeur peut revendiquer les annotations qu'il traite, auquel cas aucune tentative supplémentaire n'est faite pour trouver d'autres processeurs pour ces annotations. Une fois toutes les annotations revendiquées, le compilateur ne recherche plus d'autres processeurs.

Si des processeurs génèrent de nouveaux fichiers source, une autre série de traitements d'annotations se produit : tous les fichiers source nouvellement générés sont analysés et les annotations sont traitées comme auparavant. Tous les processeurs appelés lors des tours précédents sont également appelés lors de tous les tours suivants. Cela continue jusqu'à ce qu'aucun nouveau fichier source ne soit généré.

Après un tour où aucun nouveau fichier source n'est généré, les processeurs d'annotations sont appelés une dernière fois, pour leur donner une chance de terminer le travail restant. Enfin, à moins que l'option -proc:only ne soit utilisée, le compilateur compile les fichiers source originaux et tous les fichiers source générés.

Si vous utilisez un processeur d'annotations qui génère des fichiers source supplémentaires à inclure dans la compilation, vous pouvez spécifier un module par défaut à utiliser pour les nouveaux fichiers générés, à utiliser lorsqu'une déclaration de module n'est pas également générée. Dans ce cas, utilisez l'option --default-module-for-created-files.

Environnement de compilation et environnement d'exécution.

Les déclarations dans les fichiers source et les fichiers de classe précédemment compilés sont analysées par javac dans un *environnement de compilation* distinct de l'*environnement d'exécution* utilisé pour exécuter javac lui-même. Bien qu'il y ait une similitude délibérée entre de nombreuses options javac et les options du même nom pour le lanceur Java, telles que --class-path, --module-path et ainsi de suite, il est important de comprendre qu'en général les options javac affectent uniquement l'environnement dans lequel les fichiers source sont compilés, et n'affectent pas le fonctionnement de javac lui-même.

La distinction entre l'environnement de compilation et l'environnement d'exécution est importante lorsqu'il s'agit d'utiliser des processeurs d'annotations. Bien que les processeurs d'annotations traitent les éléments (déclarations) qui existent dans l'environnement de compilation, le processeur d'annotations lui-même est exécuté dans l'environnement d'exécution. Si un processeur d'annotations a des dépendances sur des bibliothèques qui ne sont pas dans des modules, ces bibliothèques peuvent être placées, avec le processeur d'annotations lui-même, sur le chemin du processeur. (Voir l'option --processor-path.) Si le processeur d'annotations et ses dépendances sont dans des modules, vous devriez utiliser le chemin des modules du processeur à la place. (Voir l'option --processor-module-path.) Lorsque ceux-ci sont insuffisants, il peut être nécessaire de fournir une configuration supplémentaire de l'environnement d'exécution. Cela peut être fait de deux manières :

1.
Si javac est invoqué depuis la ligne de commande, des options peuvent être passées à l'environnement d'exécution sous-jacent en précédant l'option par -J.
2.
Vous pouvez démarrer une instance d'une machine virtuelle Java directement et utiliser les options de ligne de commande et l'API pour configurer un environnement dans lequel javac peut être invoqué via l'une de ses APIs.

COMPILATION POUR DES VERSIONS ANTÉRIEURES DE LA PLATEFORME

javac peut compiler du code destiné à être utilisé sur d'autres versions de la plateforme, en utilisant soit l'option --release, soit les options --source/-source et --target/-target, conjointement avec des options supplémentaires pour spécifier les classes de la plateforme.

Selon la version de la plateforme souhaitée, il existe certaines restrictions sur certaines des options pouvant être utilisées.

•
Lors de la compilation pour les versions JDK 8 et antérieures, vous ne pouvez pas utiliser d'option destinée à être utilisée avec le système de modules. Cela inclut toutes les options suivantes :
•
--module-source-path, --upgrade-module-path, --system, --module-path, --add-modules, --add-exports, --add-opens, --add-reads, --limit-modules, --patch-module

Si vous utilisez les options --source/-source ou --target/-target, vous devriez également définir les classes de plateforme appropriées en utilisant la famille d'options du classpath de démarrage.

•
Lors de la compilation pour les versions JDK 9 et ultérieures, vous ne pouvez pas utiliser d'option destinée à configurer le classpath de démarrage. Cela inclut toutes les options suivantes :
•
-Xbootclasspath/p:, -Xbootclasspath, -Xbootclasspath/a:, -endorseddirs, -Djava.endorsed.dirs, -extdirs, -Djava.ext.dirs, -profile

Si vous utilisez les options --source/-source ou --target/-target, vous devriez également définir les classes de plateforme appropriées en utilisant l'option --system pour indiquer l'emplacement d'une version installée appropriée de JDK.

Lors de l'utilisation de l'option --release, seule l'API documentée supportée pour cette version peut être utilisée ; vous ne pouvez utiliser aucune option pour casser l'encapsulation afin d'accéder à des classes internes.

APIS

Le compilateur javac peut être invoqué à l'aide d'une API de trois manières différentes :

L'API Java Compiler API
Elle offre le moyen le plus flexible d'invoquer le compilateur, y compris la possibilité de compiler des fichiers source fournis dans des buffers en mémoire ou d'autres systèmes de fichiers non standard.
L'API ToolProvider API
Un ToolProvider pour javac peut être obtenu en appelant ToolProvider.findFirst("javac"). Cela renvoie un objet avec les fonctionnalités équivalentes de l'outil en ligne de commande.

Remarque : Cette API ne doit pas être confondue avec l'API du même nom dans le package javax.tools.

L'API Legacy API de javac
Cette API est conservée uniquement pour des raisons de compatibilité descendante. Tout nouveau code doit utiliser soit l'API Java Compiler API, soit l'API ToolProvider API.

Remarque : Toutes les autres classes et méthodes trouvées dans un package dont les noms commencent par com.sun.tools.javac (sous-packages de com.sun.tools.javac) sont strictement internes et sujettes à modification à tout moment.

Lorsque le compilateur rencontre une méthode varargs, il traduit le paramètre formel varargs en un tableau. Cependant, le langage de programmation Java ne permet pas la création de tableaux de types paramétrés. Dans la méthode ArrayBuilder.addToList, le compilateur traduit le paramètre formel varargs T... éléments en paramètre formel T[] éléments, un tableau. Cependant, en raison de l'effacement de type, le compilateur convertit le paramètre formel varargs en Object[] éléments. Par conséquent, il existe une possibilité de pollution de tas.
