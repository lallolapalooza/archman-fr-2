Actuellement, il existe deux outils en ligne de commande qui utilisent des implémentations de magasin de clés (keytool et jarsigner )

L'implémentation de magasin de clés par défaut est PKCS12. Il s'agit d'un keystore multiplateforme basé sur la norme RSA PKCS12 Personal Information Exchange Syntax Standard. Cette norme est principalement destinée au stockage ou au transport des clés privées d'un utilisateur, de ses certificats et de divers secrets. Il existe une autre implémentation intégrée, fournie par Oracle. Elle implémente le keystore sous forme de fichier avec un type de keystore (format) propriétaire nommé JKS. Elle protège chaque clé privée avec son mot de passe individuel, et protège également l'intégrité de l'ensemble du keystore avec un mot de passe (éventuellement différent).

Les implémentations de keystore sont basées sur des fournisseurs, ce qui signifie que les interfaces d'application fournies par la classe KeyStore sont implémentées en termes d'une interface de fournisseur de services (SPI). Il existe une classe abstraite correspondante KeystoreSpi, également dans le package java.security, qui définit les méthodes de l'interface du fournisseur de services que les fournisseurs doivent implémenter. Le terme fournisseur fait référence à un package ou à un ensemble de packages qui fournissent une implémentation concrète d'un sous-ensemble de services accessibles par l'API de sécurité Java. Pour fournir une implémentation de keystore, les clients doivent implémenter un fournisseur et fournir une implémentation de sous-classe KeystoreSpi, comme décrit dans Comment implémenter un fournisseur dans l'architecture de cryptographie Java [https://www.oracle.com/pls/topic/lookup?ctx=en/java/javase&id=security_guide_implement_provider_jca].

Les applications peuvent choisir différents types d'implémentations de keystore provenant de différents fournisseurs, avec la méthode usine getInstance de la classe KeyStore. Un type de keystore définit le format de stockage et de données des informations du keystore, ainsi que les algorithmes utilisés pour protéger les clés privées dans le keystore et l'intégrité du keystore lui-même. Les implémentations de keystore de différents types ne sont pas compatibles.

Les commandes jarsigner peuvent lire des keystores basés sur des fichiers depuis n'importe quel emplacement spécifiable à l'aide d'une URL. De plus, ces commandes peuvent lire des keystores non basés sur des fichiers, tels que ceux fournis par MSCAPI sous Windows et PKCS11 sur toutes les plateformes.

Pour les commandes jarsigner et keytool, vous pouvez spécifier un type de keystore en ligne de commande avec l'option -storetype.

Si vous ne spécifiez pas explicitement de type de keystore, les outils choisissent une implémentation de keystore en fonction de la valeur de la propriété keystore.type spécifiée dans le fichier de propriétés de sécurité. Le fichier de propriétés de sécurité s'appelle java.security et se trouve dans le répertoire des propriétés de sécurité du JDK, java.home/conf/security.

Chaque outil récupère la valeur de keystore.type, puis examine tous les fournisseurs installés jusqu'à ce qu'il en trouve un qui implémente des keystores de ce type. Il utilise ensuite l'implémentation de keystore de ce fournisseur.

La classe KeyStore définit une méthode statique nommée getDefaultType qui permet aux applications de récupérer la valeur de la propriété keystore.type. La ligne de code suivante crée une instance du type de keystore par défaut tel que spécifié dans la propriété keystore.type :

KeyStore keyStore = KeyStore.getInstance(KeyStore.getDefaultType());

Le type de keystore par défaut est pkcs12, un keystore multiplateforme basé sur la norme RSA PKCS12 Personal Information Exchange Syntax Standard. Ceci est spécifié par la ligne suivante dans le fichier de propriétés de sécurité :

keystore.type=pkcs12

La casse n'a pas d'importance dans les désignations de type de keystore. Par exemple, JKS est identique à jks.

Pour que les outils utilisent une implémentation de keystore autre que celle par défaut, vous pouvez modifier cette ligne pour spécifier un autre type de keystore. Par exemple, si vous souhaitez utiliser l'implémentation de keystore jks d'Oracle, modifiez la ligne comme suit :

keystore.type=jks

Les propriétés de sécurité jdk.jar.disabledAlgorithms et jdk.security.legacyAlgorithms sont définies dans le fichier java.security (situé dans le répertoire $JAVA_HOME/conf/security du JDK).

Si l'interopérabilité avec les anciennes versions du JDK est importante, assurez-vous que les valeurs par défaut sont prises en charge par ces versions, ou utilisez alternativement l'option -sigalg pour remplacer les valeurs par défaut à vos risques et périls.

LE FICHIER JAR SIGNE

Lorsque la commande jarsigner est utilisée pour signer un fichier JAR, le fichier JAR signé résultant est exactement le même que le fichier JAR d'entrée, à l'exception de deux fichiers supplémentaires placés dans le répertoire META-INF :

•
Un fichier de signature avec une extension .SF
•
Un fichier bloc de signature avec une extension .DSA, .RSA ou .EC

Les noms de base de ces deux fichiers proviennent de la valeur de l'option -sigfile. Par exemple, lorsque l'option est -sigfile MKSIGN, les fichiers sont nommés MKSIGN.SF et MKSIGN.RSA. Dans ce document, nous supposons que le signataire utilise toujours une clé RSA.

Si aucune option -sigfile n'apparaît sur la ligne de commande, le nom de fichier de base pour les fichiers .SF et de bloc de signature est les 8 premiers caractères du nom d'alias spécifié sur la ligne de commande, tous convertis en majuscules. Si le nom d'alias a moins de 8 caractères, le nom d'alias complet est utilisé. Si le nom d'alias contient des caractères non autorisés dans un nom de fichier de signature, chaque caractère de ce type est converti en un trait de soulignement (_) lors de la formation du nom de fichier. Les caractères valides incluent les lettres, les chiffres, les traits de soulignement et les traits d'union.

FICHIER DE SIGNATURE

Un fichier de signature (fichier .SF) ressemble au fichier manifeste qui est toujours inclus dans un fichier JAR lorsque la commande jarsigner est utilisée pour signer le fichier. Pour chaque fichier source inclus dans le fichier JAR, le fichier .SF a deux lignes, comme dans le fichier manifeste, qui répertorient ce qui suit :

•
Nom du fichier
•
Nom de l'algorithme de digest (SHA)
•
Valeur du digest SHA

Remarque :

Le nom de l'algorithme de digest (SHA) et la valeur du digest SHA se trouvent sur la même ligne.

Dans le fichier manifeste, la valeur du digest SHA pour chaque fichier source est le digest (hachage) des données binaires du fichier source. Dans le fichier .SF, la valeur du digest pour un fichier source spécifié est le hachage des deux lignes du fichier manifeste relatives à ce fichier source.

Le fichier de signature, par défaut, inclut un en-tête avec un hachage de l'ensemble du fichier manifeste. L'en-tête contient également un hachage de l'en-tête du manifeste. La présence de l'en-tête permet l'optimisation de la vérification. Voir Vérification de fichier JAR.

FICHIER BLOC DE SIGNATURE

BLOC DE SIGNATURE

Le fichier .SF est signé et la signature est placée dans le fichier de bloc de signature. Ce fichier contient également, encodé en son sein, le certificat ou la chaîne de certificats du magasin de clés qui authentifie la clé publique correspondant à la clé privée utilisée pour la signature. Le fichier a l'extension .DSA, .RSAou .EC, selon l'algorithme de clé utilisé. Voir le tableau dans Algorithmes pris en charge.

VÉRIFICATION DU FICHIER JAR

Une vérification réussie d'un fichier JAR se produit lorsque les signatures sont valides et qu'aucun des fichiers qui se trouvaient dans le fichier JAR au moment de la génération des signatures n'a changé depuis. La vérification du fichier JAR implique les étapes suivantes :

1.
Vérifier la signature du fichier .SF .

La vérification garantit que la signature stockée dans chaque fichier de bloc de signature a été générée à l'aide de la clé privée correspondant à la clé publique dont le certificat (ou la chaîne de certificats) apparaît également dans le fichier de bloc de signature. Elle garantit également que la signature est une signature valide du fichier de signature (.SF) correspondant, et donc que le fichier .SF n'a pas été altéré.

2.
Vérifier l'empreire répertoriée dans chaque entrée du fichier .SF avec chaque section correspondante du manifeste.

Le fichier .SF inclut par défaut un en-tête qui contient un hachage de l'intégralité du fichier manifeste. Lorsque l'en-tête est présent, la vérification peut vérifier si le hachage de l'en-tête correspond ou non au hachage du fichier manifeste. S'il y a correspondance, la vérification passe à l'étape suivante.

S'il n'y a pas de correspondance, une vérification moins optimisée est nécessaire pour garantir que le hachage dans chaque section d'informations de fichier source du fichier .SF est égal au hachage de sa section correspondante dans le fichier manifeste. Voir Fichier de signature.

Une raison pour laquelle le hachage du fichier manifeste stocké dans l'en-tête du fichier .SF peut ne pas être égal au hachage du manifeste actuel est qu'il peut contenir des sections pour des fichiers ajoutés après la signature du fichier. Par exemple, supposons qu'un ou plusieurs fichiers ont été ajoutés au fichier JAR signé (à l'aide de l'outil jar ) qui contient déjà une signature et un fichier .SF . Si le fichier JAR est signé à nouveau par un signataire différent, le fichier manifeste est modifié (des sections y sont ajoutées pour les nouveaux fichiers par l'outil jarsigner ) et un nouveau fichier .SF est créé, mais le fichier .SF d'origine est inchangé. Une vérification est toujours considérée comme réussie si aucun des fichiers qui se trouvaient dans le fichier JAR au moment de la génération de la signature d'origine n'a été modifié depuis. Cela est dû au fait que les hachages des sections autres que l'en-tête du fichier .SF sont égaux aux hachages des sections correspondantes dans le fichier manifeste.

3.
Lire chaque fichier du fichier JAR qui a une entrée dans le fichier .SF . Pendant la lecture, calculer l'empreire du fichier et comparer le résultat avec l'empreire de ce fichier dans la section du manifeste. Les empreires doivent être identiques, sinon la vérification échoue.

Si des échecs graves de vérification surviennent pendant le processus de vérification, le processus est interrompu et une exception de sécurité est levée. La commande jarsigner intercepte et affiche l'exception.

4.
Vérifier l'utilisation d'algorithmes désactivés. Voir Algorithmes pris en charge.

Remarque :

Vous devez lire tous les avertissements supplémentaires (ou les erreurs si vous avez spécifié l'option -strict ), ainsi que le contenu du certificat (en spécifiant les options -verbose et -certs ) pour déterminer si la signature peut être considérée comme fiable.

SIGNATURES MULTIPLES POUR UN FICHIER JAR

Un fichier JAR peut être signé par plusieurs personnes en exécutant la commande jarsigner sur le fichier plusieurs fois et en spécifiant l'alias d'une personne différente à chaque fois, comme suit :

jarsigner myBundle.jar susan
jarsigner myBundle.jar kevin

Lorsqu'un fichier JAR est signé plusieurs fois, il y a plusieurs fichiers .SF et de blocs de signature dans le fichier JAR résultant, une paire pour chaque signature. Dans l'exemple précédent, le fichier JAR de sortie inclut des fichiers avec les noms suivants :

SUSAN.SF
SUSAN.RSA
KEVIN.SF
KEVIN.RSA

OPTIONS POUR JARSIGNER

Les sections suivantes décrivent les options pour jarsigner. Tenez compte des normes suivantes :

•
Tous les noms d'options sont précédés d'un signe tiret (-).
•
Les options peuvent être fournies dans n'importe quel ordre.
•
Les éléments en italique ou soulignés (valeurs d'options) représentent les valeurs réelles qui doivent être fournies.
•
Les options -storepass, -keypass, -sigfile, -sigalg, -digestalg, -signedjaret les options liées à la TSA ne sont pertinentes que lors de la signature d'un fichier JAR ; elles ne sont pas pertinentes lors de la vérification d'un fichier JAR signé. L'option -keystore est pertinente pour la signature et la vérification d'un fichier JAR. De plus, les alias sont spécifiés lors de la signature et de la vérification d'un fichier JAR.
-keystore url
Spécifie l'URL qui indique l'emplacement du magasin de clés. Par défaut, il s'agit du fichier .keystore dans le répertoire personnel de l'utilisateur, tel que déterminé par la propriété système user.home .

Un magasin de clés est requis lors de la signature. Vous devez spécifier explicitement un magasin de clés lorsque le magasin de clés par défaut n'existe pas ou si vous souhaitez en utiliser un autre que celui par défaut.

Un magasin de clés n'est pas requis lors de la vérification, mais si un magasin est spécifié ou si celui par défaut existe et que l'option -verbose a également été spécifiée, des informations supplémentaires sont affichées concernant le fait que les certificats utilisés pour vérifier le fichier JAR sont ou non contenus dans ce magasin de clés.

L'argument -keystore peut être une spécification de nom de fichier et de chemin plutôt qu'une URL, auquel cas il est traité de la même manière qu'une URL file:, par exemple, les éléments suivants sont équivalents :

•
-keystore filePathAndName
•
-keystore file:filePathAndName

Si le fournisseur Sun PKCS #11 a été configuré dans le fichier de propriétés de sécurité java.security (situé dans le répertoire $JAVA_HOME/conf/security du JDK), les outils keytool et jarsigner peuvent opérer sur le jeton PKCS #11 en spécifiant ces options :

-keystore NONE -storetype PKCS11

Par exemple, la commande suivante liste le contenu du jeton PKCS#11 configuré :

keytool -keystore NONE -storetype PKCS11 -list

-storepass [:env | :file] argument
Spécifie le mot de passe requis pour accéder au magasin de clés. Cela n'est nécessaire que lors de la signature (et non de la vérification) d'un fichier JAR. Dans ce cas, si une option -storepass n'est pas fournie à la ligne de commande, l'utilisateur est invité à saisir le mot de passe.

Si le modificateur env ou file n'est pas spécifié, le mot de passe a la valeur argument. Sinon, le mot de passe est récupéré comme suit :

•
env: Récupérer le mot de passe à partir de la variable d'environnement nommée argument.
•
file: Récupérer le mot de passe à partir du fichier nommé argument.

Remarque :

Le mot de passe ne doit pas être spécifié sur la ligne de commande ou dans un script, sauf s'il est utilisé à des fins de test ou si vous êtes sur un système sécurisé.

-storetype storetype
Spécifie le type de magasin de clés à instancier. Le type de magasin de clés par défaut est celui spécifié comme valeur de la propriété keystore.type dans le fichier de propriétés de sécurité, qui est retourné par la méthode statique getDefaultType dans java.security.KeyStore.

Le PIN d'un jeton PKCS #11 peut également être spécifié avec l'option -storepass . Si aucun n'est spécifié, les commandes keytool et jarsigner demandent le PIN du jeton. OPTIONS

The following options are available for the jarsigner command:

jarsigner [options] jar-file alias [verify]
Signs the specified file, or verifies a signed JAR file.

The jar-file is the archive to be signed or verified. The alias is the name of the private key identity used for signing.

The optional verify argument is used to specify an alias for the trusted certificate that was used to sign the JAR file. When this argument is present, jarsigner verifies the signature using the specified certificate.

The following options can be used:

jarsigner [options] -verify [-certs] alias jar-file
Verifies the signature of the specified file. The -certs option prints the signer certificate chain.
jarsigner [options] -showcerts jar-file [alias ...]
Shows the certificates associated with the specified alias(es).
jarsigner [options] -printcert jar-file [alias ...]
Prints the certificate associated with the specified alias(es).
jarsigner [options] -resolve jar-file
Resolves all signatures in the specified file.

The options are described below.

-keystore url
Specifies the location of the keystore. If this option is not specified, the default keystore location is used. The default keystore is the keystore file named .keystore in the user's home directory.
-storetype type
Specifies the type of the keystore. If this option is not specified, the default keystore type is used. The default keystore type is determined by the security.provider.x properties in the java.security file.
-storepass password
Specifies the password to access the keystore. If this option is not specified, you will be prompted for the password.
-keypass password
Specifies the password to access the private key. If this option is not specified, you will be prompted for the password.
-signedby alias,...
Signs the JAR file using the private key specified by the given alias(es). If this option is not specified, then all private keys in the keystore will be used to sign the JAR file.
-internalsf
When a JAR file is signed, the signature block file generated includes an encoded copy of the .SF file (signature file) that was also generated. This behavior has been changed. To reduce the overall size of the output JAR file, the signature block file by default does not contain a copy of the .SF file. If -internalsf appears on the command line, then the old behavior is utilized. This option is useful for testing. In practice, do not use the -internalsf option because it incurs higher overhead.
-sectionsonly
When the -sectionsonly option appears on the command line, the .SF file (signature file) generated when a JAR file is signed does not include a header that contains a hash of the whole manifest file. It contains only the information and hashes related to each individual source file included in the JAR file. See Signature File.

By default, this header is added, as an optimization. When the header is present, whenever the JAR file is verified, the verification can first check to see whether the hash in the header matches the hash of the whole manifest file. When there is a match, verification proceeds to the next step. When there is no match, it is necessary to do a less optimized verification that the hash in each source file information section in the .SF file equals the hash of its corresponding section in the manifest file. See JAR File Verification.

The -sectionsonly option is primarily used for testing. It should not be used other than for testing because using it incurs higher overhead.

-protected
Values can be either true or false. Specify true when a password must be specified through a protected authentication path such as a dedicated PIN reader.
-providerName providerName
If more than one provider was configured in the java.security security properties file, then you can use the -providerName option to target a specific provider instance. The argument to this option is the name of the provider.

For the Oracle PKCS #11 provider, providerName is of the form SunPKCS11-TokenName, where TokenName is the name suffix that the provider instance has been configured with, as detailed in the configuration attributes table. For example, the following command lists the contents of the PKCS #11 keystore provider instance with name suffix SmartCard:

jarsigner -keystore NONE -storetype PKCS11 -providerName SunPKCS11-SmartCard -list

-addprovider name [-providerArg arg]
Adds a security provider by name (such as SunPKCS11) and an optional configure argument. The value of the security provider is the name of a security provider that is defined in a module.

Used with the -providerArg ConfigFilePath option, the keytool and jarsigner tools install the provider dynamically and use ConfigFilePath for the path to the token configuration file. The following example shows a command to list a PKCS #11 keystore when the Oracle PKCS #11 provider was not configured in the security properties file.

jarsigner -keystore NONE -storetype PKCS11 -addprovider SunPKCS11 -providerArg /mydir1/mydir2/token.config

-providerClass provider-class-name [-providerArg arg]
Used to specify the name of the cryptographic service provider's master class file when the service provider is not listed in the java.security security properties file. Adds a security provider by fully-qualified class name and an optional configure argument.

Note:

The preferred way to load PKCS11 is by using modules. See -addprovider.

-providerPath classpath
Used to specify the classpath for providers specified by the -providerClass option. Multiple paths should be separated by the system-dependent path-separator character.
-Jjavaoption
Passes through the specified javaoption string directly to the Java interpreter. The jarsigner command is a wrapper around the interpreter. This option should not contain any spaces. It is useful for adjusting the execution environment or memory usage. For a list of possible interpreter options, type java -h or java -X at the command line.
-strict
During the signing or verifying process, the command may issue warning messages. If you specify this option, the exit code of the tool reflects the severe warning messages that this command found. See ERRORS AND WARNINGS.
-conf url
Specifies a pre-configured options file. Read the keytool documentation for details. The property keys supported are "jarsigner.all" for all actions, "jarsigner.sign" for signing, and "jarsigner.verify" for verification. jarsigner arguments including the JAR file name and alias name(s) cannot be set in this file.
-version
Prints the program version.

ERREURS ET AVERTISSEMENTS

During the signing or verifying process, the jarsigner command may issue various errors or warnings.

If there is a failure, the jarsigner command exits with code 1. If there is no failure, but there are one or more severe warnings, the jarsigner command exits with code 0 when the -strict option is not specified, or exits with the OR-value of the warning codes when the -strict is specified. If there is only informational warnings or no warning at all, the command always exits with code 0.

For example, if a certificate used to sign an entry is expired and has a KeyUsage extension that doesn't allow it to sign a file, the jarsigner command exits with code 12 (=4+8) when the -strict option is specified.

Note: Exit codes are reused because only the values from 0 to 255 are legal on Linux and macOS.

The following sections describe the names, codes, and descriptions of the errors and warnings that the jarsigner command can issue.

ÉCHEC

Reasons why the jarsigner command fails include (but are not limited to) a command line parsing error, the inability to find a keypair to sign the JAR file, or the verification of a signed JAR fails.

EXEMPLE DE SIGNATURE D'UN FICHIER JAR

Utilisez la commande suivante pour signer bundle.jar avec la clé privée d'un utilisateur dont l'alias dans le magasin de clés est jane dans un magasin de clés nommé mystore dans le répertoire working et nommez le fichier JAR signé sbundle.jar:

jarsigner -keystore /working/mystore -storepass keystore_password -keypass private_key_password -signedjar sbundle.jar bundle.jar jane

Il n'y a pas d'option -sigfile spécifiée dans la commande précédente, donc les fichiers .SF et les fichiers de bloc de signature placés dans le fichier JAR signé auront des noms par défaut basés sur le nom de l'alias. Ils sont nommés JANE.SF et JANE.RSA.

Si vous souhaitez être invité à saisir le mot de passe du magasin de clés et le mot de passe de la clé privée, vous pouvez raccourcir la commande précédente comme suit :

jarsigner -keystore /working/mystore -signedjar sbundle.jar bundle.jar jane

Si le magasin de clés est le magasin de clés par défaut(.keystore dans votre répertoire personnel), vous n'avez pas besoin de spécifier un magasin de clés, comme suit :

jarsigner -signedjar sbundle.jar bundle.jar jane

Si vous souhaitez que le fichier JAR signé écrase le fichier JAR d'entrée (bundle.jar), vous n'avez pas besoin de spécifier l'option -signedjar , comme suit :

jarsigner bundle.jar jane
