UNLINK(3P) Manuel du programmeur POSIX UNLINK(3P)

PROLOGUE

Cette page de manuel fait partie du Manuel du programmeur POSIX. L'implémentation Linux de cette interface peut différer (consultez la page de manuel Linux correspondante pour connaître les détails du comportement sous Linux), ou l'interface peut ne pas être implémentée sous Linux.

NOM

unlink, unlinkat — supprimer une entrée de répertoire

SYNTAXE

#include <unistd.h>
int unlink(const char *path);
#include <fcntl.h>
int unlinkat(int fd, const char *path, int flag);

DESCRIPTION

La fonction unlink() supprime un lien vers un fichier. Si path désigne un lien symbolique, unlink() supprime le lien symbolique nommé par path et n'affecte aucun fichier ou répertoire nommé par le contenu du lien symbolique. Sinon, unlink() supprime le lien nommé par le chemin pointé par path et décrémente le compteur de liens du fichier référencé par le lien.

Lorsque le compteur de liens du fichier atteint 0 et qu'aucun processus n'a le fichier ouvert, l'espace occupé par le fichier est libéré et le fichier n'est plus accessible. Si un ou plusieurs processus ont le fichier ouvert lorsque le dernier lien est supprimé, le lien est supprimé avant que unlink() ne retourne, mais la suppression du contenu du fichier est reportée jusqu'à ce que toutes les références au fichier soient fermées.

L'argument path ne doit pas désigner un répertoire, sauf si le processus dispose des privilèges appropriés et que l'implémentation permet d'utiliser unlink() sur les répertoires.

En cas de succès, unlink() marque pour mise à jour les horodatages de la dernière modification des données et du dernier changement de statut du fichier du répertoire parent. De plus, si le compteur de liens du fichier n'est pas 0, l'horodatage du dernier changement de statut du fichier est marqué pour mise à jour.

La fonction unlinkat() est équivalente aux fonctions unlink() ou rmdir() sauf dans le cas où path spécifie un chemin relatif. Dans ce cas, l'entrée de répertoire à supprimer est déterminée par rapport au répertoire associé au descripteur de fichier fd au lieu du répertoire de travail courant. Si le mode d'accès de la description de fichier ouverte associée au descripteur de fichier n'est pas O_SEARCH, la fonction vérifie si les recherches de répertoires sont autorisées en utilisant les permissions courantes du répertoire sous-jacent au descripteur de fichier. Si le mode d'accès est O_SEARCH, la fonction n'effectue pas la vérification.

Les valeurs pour flag sont construites par une OU binaire inclusive des indicateurs de la liste suivante, définis dans <fcntl.h>:

AT_REMOVEDIR

Supprime l'entrée de répertoire spécifiée par fd et path en tant que répertoire, pas en tant que fichier normal.

Si unlinkat() reçoit la valeur spéciale AT_FDCWD dans le paramètre fd, le répertoire de travail courant est utilisé et le comportement est identique à un appel à unlink() ou rmdir() respectivement, selon que le bit AT_REMOVEDIR est défini ou non dans flag.

VALEUR DE RETOUR

En cas de succès, ces fonctions retournent 0. Sinon, ces fonctions retournent -1 et définissent errno pour indiquer l'erreur. Si -1 est retourné, le fichier nommé n'est pas modifié.

ERREURS

Ces fonctions échouent et ne suppriment pas le fichier si :

EACCES
La permission de recherche est refusée pour un composant du préfixe du chemin, ou la permission d'écriture est refusée sur le répertoire contenant l'entrée de répertoire à supprimer.
EBUSY
Le fichier nommé par l'argument path ne peut pas être supprimé car il est utilisé par le système ou un autre processus et l'implémentation considère cela comme une erreur.
ELOOP
Une boucle existe dans les liens symboliques rencontrés lors de la résolution de l'argument path.
ENAMETOOLONG

La longueur d'un composant d'un nom de fichier est supérieure à {NAME_MAX}.
ENOENT
Un composant de path ne désigne pas un fichier existant ou path est une chaîne vide.
ENOTDIR
Un composant du préfixe du chemin désigne un fichier existant qui n'est ni un répertoire ni un lien symbolique vers un répertoire, ou l'argument path contient au moins un caractère non <slash> et se termine par un ou plusieurs <slash> finaux et le dernier composant du chemin désigne un fichier existant qui n'est ni un répertoire ni un lien symbolique vers un répertoire.
EPERM
Le fichier nommé par path est un répertoire, et soit le processus appelant n'a pas les privilèges appropriés, soit l'implémentation interdit d'utiliser unlink() sur les répertoires.
EPERM ou EACCES

L'indicateur S_ISVTX est défini sur le répertoire contenant le fichier auquel fait référence l'argument path et le processus ne satisfait pas les critères spécifiés dans le volume des Définitions de base de POSIX.1‐2017, Section 4.3, Protection des répertoires.
EROFS
L'entrée de répertoire à supprimer fait partie d'un système de fichiers en lecture seule.

La fonction unlinkat() échoue si :

EACCES
Le mode d'accès de la description de fichier ouverte associée à fd n'est pas O_SEARCH et les permissions du répertoire sous-jacent à fd n'autorisent pas les recherches de répertoires.
EBADF
L'argument path ne spécifie pas un chemin absolu et l'argument fd n'est ni AT_FDCWD ni un descripteur de fichier valide ouvert en lecture ou en recherche.
ENOTDIR
L'argument path n'est pas un chemin absolu et fd est un descripteur de fichier associé à un fichier non répertoire.
EEXIST ou ENOTEMPTY

Le paramètre flag a le bit AT_REMOVEDIR défini et l'argument path désigne un répertoire qui n'est pas un répertoire vide, ou il y a des liens physiques vers le répertoire autres que le point ou une entrée unique dans le point-point.
ENOTDIR
Le paramètre flag a le bit AT_REMOVEDIR défini et path ne désigne pas un répertoire.

Ces fonctions peuvent échouer et ne pas supprimer le fichier si :

EBUSY
Le fichier nommé par path est un STREAM nommé.
ELOOP
Plus de {SYMLOOP_MAX} liens symboliques ont été rencontrés lors de la résolution de l'argument path.
ENAMETOOLONG

La longueur d'un nom de fichier dépasse {PATH_MAX}, ou la résolution de nom de fichier d'un lien symbolique a produit un résultat intermédiaire dont la longueur dépasse {PATH_MAX}.
ETXTBSY
L'entrée à supprimer est la dernière entrée de répertoire d'un fichier de procédure pure (texte partagé) en cours d'exécution.

La fonction unlinkat() peut échouer si :

EINVAL
La valeur de l'argument flag n'est pas valide.

unlink(3p) — L’appel système pour supprimer un lien

PROLOG

This page is a manual page for the Linux operating system. It describes the unlink() system call, part of the POSIX standard, and its behavior on Linux.

The POSIX standard defines the unlink() function for removing links to files, and also for removing directories. The standard specifies that removing a directory with unlink() is restricted to the superuser.

This manual page is a translation of the original IEEE/The Open Group Standard, POSIX.1-2017, section 2.4.1, File Removal.

NAME

unlink, unlinkat - supprimer un lien vers un fichier

SYNOPSIS

#include <unistd.h>

int unlink(const char *pathname);
int unlinkat(int dirfd, const char *pathname, int flags);

DESCRIPTION

The unlink() function shall remove a link to a file. If that link was the last link to a file and all other references to the file have been removed, the file shall be destroyed. If destoyed, the space occupied by the file shall be freed for reuse by the system.

The pathname argument shall point to a character string argument that specifies the path name of the link to be removed.

If the pathname argument is a relative path, it is interpreted relative to the current working directory.

If pathname refers to a directory, the behavior depends on the implementation. POSIX.1-2017 specifies that removing a directory with unlink() is restricted to the superuser. Many implementations forbid it to all users. A conforming application should use rmdir() to remove directories.

If the file referred to by pathname is a symbolic link, unlink() shall remove the symbolic link itself and not the file or directory it points to.

If the file referred to by pathname is not a directory, and other references to the file exist, the link is removed, but the file is not destroyed until the last reference to the file is removed.

If the file referred to by pathname is not a directory, and the link referred to by pathname is the only reference to the file, the link is removed, and the file is destroyed.

The unlinkat() function shall be equivalent to the unlink() function except that if pathname specifies a relative path, then the location referred to by pathname is resolved relative to the directory referred to by the file descriptor dirfd instead of the current working directory. If pathname is an absolute path, the dirfd argument is ignored.

The flags argument is valid only if pathname is relative and dirfd refers to a directory. It is used to specify options that affect the operation of unlinkat(). The only flag defined by POSIX.1-2017 is AT_REMOVEDIR. If this flag is specified and pathname refers to a directory, then unlinkat() shall remove the directory entry referred to by pathname. If pathname does not refer to a directory, or if AT_REMOVEDIR is not specified, then unlinkat() shall remove the link named by pathname. If AT_REMOVEDIR is specified and pathname refers to a directory, then the behavior is equivalent to calling rmdir() on that directory, except that the path is interpreted relative to dirfd.

The standard developers reviewed TR 24715‐2006 and noted that LSB-conforming implementations may return [EISDIR] instead of [EPERM] when unlinking a directory. A change to permit this behavior by changing the requirement for [EPERM] to [EPERM] or [EISDIR] was considered, but decided against since it would break existing strictly conforming and conforming applications. Applications written for portability to both POSIX.1‐2008 and the LSB should be prepared to handle either error code.

The purpose of the unlinkat() function is to remove directory entries in directories other than the current working directory without exposure to race conditions. Any part of the path of a file could be changed in parallel to a call to unlink(), resulting in unspecified behavior. By opening a file descriptor for the target directory and using the unlinkat() function it can be guaranteed that the removed directory entry is located relative to the desired directory.

RETURN VALUE

Upon successful completion, 0 shall be returned. Otherwise, -1 shall be returned and errno shall be set to indicate the error.

ERRORS

[EACCES]
Search permission is denied for a component of the path prefix. [EACCES] is also returned if the requested access to the file is not permitted, or if the file is a directory and the calling process does not have write and search permission on the directory containing the directory entry.
[EDQUOT]
The file system is out of disk space.
[EFAULT]
pathname points to an inaccessible buffer.
[EINTR]
A signal was caught during the execution of this function.
[EISDIR]
pathname refers to a directory and the calling process does not have write and search permission on the directory containing the directory entry, or the implementation forbids unlinking directories. (See RATIONALE.)
[ELOOP]
A loop exists in symbolic links encountered in resolving pathname.
[EMLINK]
The file system cannot support more links than it currently has ([EMLINK] is not returned for directories).
[ENAMETOOLONG]
The length of a component of pathname is longer than {NAME_MAX}.
[ENOENT]
The link named pathname does not exist, or pathname points to an empty string.
[ENOTDIR]
A component of the prefix of pathname is not a directory, or pathname refers to a file descriptor that refers to a directory, but the AT_REMOVEDIR flag was specified and pathname was not a directory.
[ENXIO]
The named file does not exist and O_CREAT was not specified.
[EPERM]
The effective user ID of the process is not the superuser, and the containing directory is not writable by the user.
[EROFS]
The link named pathname resides on a read-only file system.
[ETXTBSY]
The file is a regular file that is being executed from within by one or more processes. This error is implementation-dependent.
[EXDEV]
The link named pathname is a hard link to a file on a different file system.

EXAMPLES

The following example fragment uses unlink() to remove a file named /modules/pass1.

#include <unistd.h>
char *path = "/modules/pass1";
int   status;
...
status = unlink(path);

Checking for an Error

The following example fragment creates a temporary password lock file named LOCKFILE, which is defined as /etc/ptmp, and gets a file descriptor for it. If the file cannot be opened for writing, unlink() is used to remove the link between the file descriptor and LOCKFILE.

#include <sys/types.h>
#include <stdio.h>
#include <fcntl.h>
#include <errno.h>
#include <unistd.h>
#include <sys/stat.h>
#define LOCKFILE "/etc/ptmp"
int pfd;  /* Integer for file descriptor returned by open call. */
FILE *fpfd;  /* File pointer for use in putpwent(). */
...
/* Open password Lock file. If it exists, this is an error. */
if ((pfd = open(LOCKFILE, O_WRONLY| O_CREAT | O_EXCL, S_IRUSR
    | S_IWUSR | S_IRGRP | S_IROTH)) == -1)  {
    fprintf(stderr, "Cannot open /etc/ptmp. Try again later.\n");
    exit(1);
}
/* Lock file created; proceed with fdopen of lock file so that
   putpwent() can be used.
 */
if ((fpfd = fdopen(pfd, "w")) == NULL) {
    close(pfd);
    unlink(LOCKFILE);
    exit(1);
}

Replacing Files

The following example fragment uses unlink() to discard links to files, so that they can be replaced with new versions of the files. The first call removes the link to LOCKFILE if an error occurs. Successive calls remove the links to SAVEFILE and PASSWDFILE so that new links can be created, then removes the link to LOCKFILE when it is no longer needed.

#include <sys/types.h>
#include <stdio.h>
#include <fcntl.h>
#include <errno.h>
#include <unistd.h>
#include <sys/stat.h>
#define LOCKFILE "/etc/ptmp"
#define PASSWDFILE "/etc/passwd"
#define SAVEFILE "/etc/opasswd"
...
/* If no change was made, assume error and leave passwd unchanged. */
if (!valid_change) {
    fprintf(stderr, "Could not change password for user %s\n", user);
    unlink(LOCKFILE);
    exit(1);
}
/* Change permissions on new password file. */
chmod(LOCKFILE, S_IRUSR | S_IRGRP | S_IROTH);
/* Remove saved password file. */
unlink(SAVEFILE);
/* Save current password file. */
link(PASSWDFILE, SAVEFILE);
/* Remove current password file. */
unlink(PASSWDFILE);
/* Save new password file as current password file. */
link(LOCKFILE,PASSWDFILE);
/* Remove lock file. */
unlink(LOCKFILE);
exit(0);

APPLICATION USAGE

Applications should use rmdir() to remove a directory.

RATIONALE

Unlinking a directory is restricted to the superuser in many historical implementations for reasons given in link() (see also rename()).

The meaning of [EBUSY] in historical implementations is ``mount point busy''. Since this volume of POSIX.1‐2017 does not cover the system administration concepts of mounting and unmounting, the description of the error was changed to ``resource busy''. (This meaning is used by some device drivers when a second process tries to open an exclusive use device.) The wording is also intended to allow implementations to refuse to remove a directory if it is the root or current working directory of any process.

The standard developers reviewed TR 24715‐2006 and noted that LSB-conforming implementations may return [EISDIR] instead of [EPERM] when unlinking a directory. A change to permit this behavior by changing the requirement for [EPERM] to [EPERM] or [EISDIR] was considered, but decided against since it would break existing strictly conforming and conforming applications. Applications written for portability to both POSIX.1‐2008 and the LSB should be prepared to handle either error code.

The purpose of the unlinkat() function is to remove directory entries in directories other than the current working directory without exposure to race conditions. Any part of the path of a file could be changed in parallel to a call to unlink(), resulting in unspecified behavior. By opening a file descriptor for the target directory and using the unlinkat() function it can be guaranteed that the removed directory entry is located relative to the desired directory.
