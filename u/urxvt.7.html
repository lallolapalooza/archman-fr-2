RXVT-UNICODE/URXVT QUESTIONS FRÉQUEMMENT POSÉES

Meta, Fonctionnalités & Problèmes de ligne de commande

Ma question n'est pas répondue ici, puis-je demander à un humain ?

Avant de m'envoyer un e-mail, vous pouvez aller sur IRC : "irc.libera.chat", le canal "#rxvt-unicode" contient quelques passionnés de rxvt-unicode qui pourraient être intéressés par l'apprentissage de problèmes nouveaux et excitants (mais pas de FAQ :)).

J'utilise Gentoo, et j'ai un problème...

Il y a deux gros problèmes avec Gentoo Linux : premièrement, la plupart sinon tous les systèmes Gentoo sont complètement cassés (fichiers d'en-tête manquants ou mal appariés, compilateur cassé, etc. ne sont que la pointe de l'iceberg) ; deuxièmement, il devrait être appelé Gentoo GNU/Linux.

Pour ces raisons, il est impossible de supporter rxvt-unicode sur Gentoo. Les problèmes apparaissant sur les systèmes Gentoo seront généralement simplement ignorés sauf s'ils peuvent être reproduits sur des systèmes non-Gentoo.

Prend-il en charge les onglets, puis-je avoir un rxvt-unicode avec des onglets ?

À partir de la version 7.3, il existe une extension Perl qui implémente un simple terminal à onglets. Elle est installée par défaut, donc n'importe laquelle de ces commandes devrait vous donner des onglets :

urxvt -pe tabbed
URxvt.perl-ext-common: default,tabbed

Cela fonctionnera également très bien avec la fonctionnalité d'onglets de nombreux gestionnaires de fenêtres ou programmes d'onglets similaires, et ses fonctionnalités d'intégration lui permettent d'être intégré dans d'autres programmes, comme en témoigne doc/rxvt-tabbed ou le prochain module Perl "Gtk2::URxvt", qui propose un terminal urxvt à onglets (murxvt) comme application d'intégration exemple.

Comment savoir quelle version de rxvt-unicode j'utilise ?

Le numéro de version est affiché avec l'aide (-h). De plus, la séquence d'échappement "ESC [ 8 n" définit le titre de la fenêtre au numéro de version. Lorsque vous utilisez le client urxvtc, la version affichée est celle du démon.

Rxvt-unicode utilise beaucoup de mémoire, comment puis-je la réduire ?

Rxvt-unicode essaie de respecter la règle de ne pas vous facturer quelque chose que vous n'utilisez pas. Une chose que vous devriez essayer est de désactiver tous les paramètres dont vous n'avez pas besoin, par exemple, le support Xft est un gouffre à ressources par conception, lorsqu'il est utilisé. Le compiler en dehors garantit qu'aucune police Xft ne sera chargée accidentellement lorsque rxvt-unicode essaie de trouver une police pour vos caractères.

De plus, beaucoup de gens (moi y compris) aiment les grandes fenêtres et les tampons de défilement encore plus grands : Sans "--enable-unicode3", rxvt-unicode utilisera 6 octets par cellule d'écran. Pour une fenêtre de 160x??, cela représente presque un kilooctet par ligne. Un tampon de défilement de 10000 lignes utilisera alors (s'il est plein) 10 mégaoctets de mémoire. Avec "--enable-unicode3", cela empire, car rxvt-unicode utilise alors 8 octets par cellule d'écran.

Comment puis-je démarrer urxvtd d'une manière sans courses (race-free) ?

Essayez "urxvtd -f -o", ce qui indique à urxvtd d'ouvrir l'affichage, de créer le socket d'écoute puis de se forker.

Comment puis-je démarrer urxvtd automatiquement lorsque j'exécute urxvtc ?

Si vous souhaitez démarrer urxvtd automatiquement chaque fois que vous exécutez urxvtc et que le démon n'est pas encore en cours d'exécution, utilisez ce script :

#!/bin/sh
urxvtc "$@"
if [ $? -eq 2 ]; then
   urxvtd -q -o -f
   urxvtc "$@"
fi

Cela tente de créer un nouveau terminal, et s'il échoue avec le statut de sortie 2, signifiant qu'il n'a pas pu se connecter au démon, il démarrera le démon et réexécutera la commande. Les invocations ultérieures du script réutiliseront le démon existant.

Une autre option consiste à utiliser l'activation basée sur les sockets de systemd (voir systemd.socket(5)). Voici un exemple de fichier d'unité de service et de fichier d'unité de socket pour le chemin de socket par défaut :

urxvtd.service
[Unit]
Description=Démon de terminal urxvt
Requires=urxvtd.socket
[Service]
ExecStart=/usr/bin/urxvtd -o
urxvtd.socket
[Unit]
Description=Socket du démon de terminal urxvt
[Socket]
ListenStream=%h/.urxvt/urxvtd-%H
[Install]
WantedBy=sockets.target

Comment puis-je distinguer si j'exécute rxvt-unicode ou un xterm normal ? J'en ai besoin pour décider de la définition des couleurs, etc.

Le rxvt et le rxvt-unicode d'origine exportent toujours la variable "COLORTERM", vous pouvez donc vérifier et voir si elle est définie. Notez que plusieurs programmes, JED, slrn, Midnight Commander vérifient automatiquement cette variable pour décider d'utiliser ou non la couleur.

Comment puis-je définir l'adresse IP complète et correcte pour la variable DISPLAY ?

Si vous avez compilé rxvt-unicode avec DISPLAY_IS_IP et activé le mode non sécurisé, il est possible d'utiliser les extraits de script shell suivants pour définir correctement l'affichage. Si votre version de rxvt-unicode n'a pas été compilée avec ESCZ_ANSWER (comme supposé dans ces extraits), alors la variable COLORTERM peut être utilisée pour distinguer rxvt-unicode d'un xterm normal.

Avec l'aimable autorisation de Chuck Blake <cblake@BBN.COM> avec les extraits de script shell suivants :

# Famille de shells Bourne/Korn/POSIX :
[ ${TERM:-foo} = foo ] && TERM=xterm # suppose un xterm si nous ne savons pas
if [ ${TERM:-foo} = xterm ]; then
   stty -icanon -echo min 0 time 15 # voir si rxvt amélioré ou non
   printf "\eZ"
   read term_id
   stty icanon echo
   if [ ""${term_id} = '^[[?1;2C' -a ${DISPLAY:-foo} = foo ]; then
      printf '\e[7n'        # interroger le rxvt dans lequel nous sommes pour la chaîne DISPLAY
      read DISPLAY          # la définir dans notre shell local
   fi
fi

Comment puis-je compiler les pages man moi-même ?

Vous devez avoir une version récente de perl installée en tant que /usr/bin/perl, une qui est livrée avec pod2man, pod2text et pod2xhtml (de Pod::Xhtml). Ensuite, allez dans le sous-répertoire doc et entrez "make alldoc".

Performance &

The C++ compiler allocates (but of course doesn't use unless you are out of memory). Also, using an xft font instead of a core font immediately adds a few megabytes of RSS. Xft indeed is responsible for a lot of RSS even when not used.

Of course, due to every character using two or four bytes instead of one, a large scrollback buffer will ultimately make rxvt-unicode use more memory.

Compared to e.g. Eterm (5112k), aterm (3132k) and xterm (4680k), this still fares rather well. And compared to some monsters like gnome-terminal (21152k + extra 4204k in separate processes) or konsole (22200k + extra 43180k in daemons that stay around after exit, plus half a minute of startup time, including the hundreds of warnings it spits out), it fares extremely well *g*.

Why C++, isn't that unportable/bloated/uncool?

Is this a question? :) It comes up very often. The simple answer is: I had to write it, and C++ allowed me to write and maintain it in a fraction of the time and effort (which is a scarce resource for me). Put even shorter: It simply wouldn't exist without C++.

My personal stance on this is that C++ is less portable than C, but in the case of rxvt-unicode this hardly matters, as its portability limits are defined by things like X11, pseudo terminals, locale support and unix domain sockets, which are all less portable than C++ itself.

Regarding the bloat, see the above question: It's easy to write programs in C that use gobs of memory, and certainly possible to write programs in C++ that don't. C++ also often comes with large libraries, but this is not necessarily the case with GCC. Here is what rxvt links against on my system with a minimal config:

Rendu, Police & Apparence

Je n'arrive pas à faire fonctionner la transparence, qu'est-ce que je fais de mal ?

Tout d'abord, la transparence n'est pas officiellement supportée dans rxvt-unicode, donc vous êtes largement seul. Ne dérangez pas l'auteur à ce sujet (mais vous pouvez déranger tout le monde). De plus, si vous n'arrivez pas à la faire fonctionner, considérez cela comme un rite de passage : ... et vous avez échoué.

Voici quatre façons d'obtenir la transparence. **Lisez** la page de manuel et les descriptions des options pour les programmes mentionnés et rxvt-unicode. Vraiment, faites-le !

1. Utiliser la pseudo-transparence :

Esetroot wallpaper.jpg
urxvt -tr -tint red -sh 40

Cela fonctionne. Si vous pensez que ce n'est pas le cas, vous manquez de support pour la transparence et la teinte, ou vous êtes incapable de lire. Cette méthode nécessite que le programme de réglage de l'arrière-plan définisse la propriété _XROOTPMAP_ID ou ESETROOT_PMAP_ID. Les programmes compatibles sont Esetroot, hsetroot et feh.

2. Utiliser un pixmap simple et émuler la pseudo-transparence. Cela vous permet d'utiliser d'autres effets que la teinte et l'ombrage : Ombre/teinte/quoi que ce soit de votre image avec gimp ou tout autre outil :

convert wallpaper.jpg -blur 20x20 -modulate 30 background.jpg
urxvt -pixmap "background.jpg;:root"

Cela fonctionne. Si vous pensez que ce n'est pas le cas, vous manquez de support GDK-PixBuf, ou vous êtes incapable de lire.

3. Utiliser un visuel ARGB :

urxvt -depth 32 -fg grey90 -bg rgba:0000/0000/4444/cccc

Cela nécessite le support XFT, et le support de votre serveur X. Si cela ne fonctionne pas pour vous, trouvez un gestionnaire de composition ou un gestionnaire de fenêtres compatible, tous deux doivent supporter les visuels ARGB pour les fenêtres clientes.

4. Utiliser xcompmgr et le laisser faire le travail :

xprop -frame -f _NET_WM_WINDOW_OPACITY 32c \
      -set _NET_WM_WINDOW_OPACITY 0xc0000000

Cliquez ensuite sur une fenêtre que vous souhaitez rendre transparente. Remplacez 0xc0000000 par d'autres valeurs pour modifier le degré d'opacité. Si cela ne fonctionne pas et que votre serveur plante, vous devrez en assumer les conséquences.

Pourquoi rxvt-unicode laisse-t-il parfois des décalcomanies de pixels ?

La plupart des polices n'ont pas été conçues pour être utilisées dans un terminal, ce qui signifie que la taille des caractères varie beaucoup. Une police qui convient par ailleurs à un usage terminal peut contenir certains caractères trop larges. Rxvt-unicode évitera ces caractères. Pour les caractères qui sont juste "un peu" trop larges, un mode de rendu spécial "prudent" est utilisé qui redessine les caractères adjacents.

Tout cela nécessite que les polices ne mentent pas sur les tailles de caractères, cependant : les polices Xft dessinent souvent des glyphes plus grands que leur boîte englobante annoncée, et rxvt-unicode n'a aucun moyen de le détecter (la bonne méthode est de demander la boîte englobante du caractère, qui est malheureusement erronée dans ces cas).

Il n'est pas clair (du moins pour moi) s'il s'agit d'un bug dans Xft, freetype, ou la police respective. Si vous rencontrez ce problème, vous pourriez essayer d'utiliser l'option "-lsp" pour donner plus de hauteur à la police. Si cela ne fonctionne pas, vous pourriez être obligé d'utiliser une police différente.

Tout cela n'est pas un problème lors de l'utilisation des polices core X11, car leurs données de boîte englobante sont correctes.

Comment puis-je empêcher rxvt-unicode d'utiliser autant la vidéo inversée ?

Tout d'abord, assurez-vous d'exécuter avec les bons paramètres de terminal ("TERM=rxvt-unicode"), ce qui éliminera la plupart de ces effets. Ensuite, assurez-vous d'avoir spécifié les couleurs pour l'italique et le gras, sinon rxvt-unicode pourrait utiliser la vidéo inversée pour simuler l'effet :

URxvt.colorBD:  white
URxvt.colorIT:  green

Certains programmes supposent des couleurs totalement étranges (rouge au lieu de bleu), comment puis-je corriger cela ?

Pour une raison inexplicable, certains programmes rares supposent une palette de couleurs très étrange lorsqu'ils sont confrontés à un terminal avec plus que les 8 couleurs standard (rxvt-unicode en supporte 88). La bonne solution est, bien sûr, de corriger ces programmes pour qu'ils ne supposent pas de couleurs non-ISO sans très bonnes raisons.

En attendant, vous pouvez soit modifier la définition de votre terminal "rxvt-unicode" pour qu'elle ne réclame que 8 couleurs, soit utiliser "TERM=rxvt", ce qui corrigera les couleurs mais vous empêchera d'utiliser d'autres fonctionnalités de rxvt-unicode.

Puis-je changer les polices à la volée ?

Oui, en utilisant une séquence d'échappement. Essayez quelque chose comme ceci, qui a le même effet que l'utilisation de l'option "-fn", et prend effet immédiatement :

printf '\33]50;%s\007' "9x15bold,xft:Kochi Gothic"

Ceci est utile si, par exemple, vous travaillez principalement en japonais (et préférez une police japonaise), mais que vous devez passer temporairement au chinois, où les polices japonaises ne feraient que vous gêner.

Vous pouvez considérer cela comme une sorte de commutation manuelle ISO-2022.

Pourquoi les caractères italiques semblent-ils coupés ?

Beaucoup de polices ont des difficultés avec les caractères italiques et le hinting. Par exemple, la police sinon très bien hintée "xft:Bitstream Vera Sans Mono" échoue complètement dans sa variante italique. Une solution de contournement pourrait être d'activer le autohinting de freetype, c'est-à-dire, comme ceci :

URxvt.italicFont:        xft:Bitstream Vera Sans Mono:italic:autohint=true
URxvt.boldItalicFont:    xft:Bitstream Vera Sans Mono:bold:italic:autohint=true

Puis-je accélérer le rendu Xft d'une manière ou d'une autre ?

Oui, le moyen le plus évident de l'accélérer est d'éviter Xft complètement, car il est simplement lent. Si vous voulez toujours des polices Xft, vous pouvez essayer de désactiver l'anti-crénelage (en ajoutant ":antialias=false"), ce qui économise beaucoup de mémoire et accélère considérablement le rendu.

Rxvt-unicode ne semble pas anti-aliaser ses polices, qu'est-ce qui ne va pas ?

Rxvt-unicode utilisera ce que vous spécifiez comme police. S'il doit recourir à sa liste de recherche de polices par défaut, il privilégiera les polices core X11, car elles sont petites et rapides, puis utilisera les polices Xft. Il a l'anti-crénelage désactivé pour la plupart d'entre elles, car l'auteur pense qu'elles sont plus belles ainsi.

Si vous voulez l'anti-crénelage, vous devez spécifier les polices manuellement.

Qu'en est-il de ce truc de gras/clignotement ?

Si aucune couleur de gras n'est définie via "colorBD:", le gras inversera le texte en utilisant la couleur de premier plan standard.

Pour la couleur d'arrière-plan standard, le clignotement fera effectivement clignoter le texte lorsqu'il est compilé avec "--enable-text-blink". Sans "--enable-text-blink", l'attribut de clignotement sera ignoré.

Sur les couleurs ANSI, les attributs gras/clignotement sont utilisés pour définir les couleurs de premier plan/arrière-plan haute intensité.

color0-7 sont les couleurs basse intensité.

color8-15 sont les couleurs haute intensité correspondantes.

Pourquoi certains caractères sont-ils si différents des autres ?

Voir l'entrée suivante.

Comment rxvt-unicode choisit-il les polices ?

La plupart des polices ne contiennent pas toute la gamme Unicode, ce qui est normal. Il y a de fortes chances que la police que vous (ou l'administrateur/responsable du package de votre système

tem/os) spécifiés ne couvrent pas tous les caractères que vous souhaitez afficher.

rxvt-unicode fait de son mieux pour trouver une police de remplacement. Souvent, le résultat est satisfaisant, mais parfois la police choisie est laide/moche/incorrecte. Certaines polices ont des caractères totalement étranges qui ne ressemblent pas du tout au glyphe correct, et rxvt-unicode manque de l'intelligence artificielle nécessaire pour détecter qu'un glyphe spécifique est incorrect : il doit croire que la police qui prétend contenir ces caractères les affiche bien.

Dans ce cas, sélectionnez une police de votre goût et ajoutez-la à la liste des polices, par exemple :

urxvt -fn basefont,font2,font3...

Lorsque rxvt-unicode voit un caractère, il examine d'abord la police de base. Si la police de base ne contient pas le caractère, il passe à la police suivante, et ainsi de suite. La spécification de vos propres polices accélérera également cette recherche et utilisera moins de ressources dans rxvt-unicode et le serveur X.

La seule limitation est qu'aucune des polices ne peut être plus grande que la police de base, car la police de base définit la taille de la cellule de caractère du terminal, qui doit être la même en raison du fonctionnement des terminaux.

Pourquoi certains caractères chinois ont-ils un aspect si différent des autres ?

C'est parce qu'il y a une différence entre l'écriture et la langue -- rxvt-unicode ne sait pas quelle est la langue du texte affiché, car il ne connaît que les codes de caractères Unicode. Si rxvt-unicode rencontre d'abord un caractère japonais/chinois, il pourrait choisir une police japonaise pour l'affichage. Les caractères japonais suivants utiliseront cette police. Or, de nombreux caractères chinois ne sont pas représentés dans les polices japonaises, donc lorsqu'un premier caractère non japonais apparaît, rxvt-unicode recherchera une police chinoise -- malheureusement, à ce stade, il utilisera toujours la police japonaise pour les caractères chinois qui sont également présents dans la police japonaise.

La solution de contournement est simple : ajoutez simplement une police chinoise à la fin de votre liste de polices (voir la question précédente). L'idée est de considérer la liste des polices comme une liste de préférences : si vous attendez plus de japonais, listez une police japonaise en premier. Si vous attendez plus de chinois, mettez une police chinoise en premier.

À l'avenir, il pourrait être possible de changer les préférences de langue à la volée (la structure de données interne n'a aucun problème à utiliser différentes polices pour le même caractère en même temps, mais aucune interface pour cela n'a encore été conçue).

En attendant, vous pourriez vous en sortir en changeant les polices à la volée (voir "Puis-je changer les polices à la volée ?" plus loin dans ce document).

Comment faire pour que mplayer affiche correctement la vidéo ?

Nous y travaillons, en attendant, comme solution de contournement, utilisez quelque chose comme :

urxvt -b 600 -geometry 20x1 -e sh -c 'mplayer -wid $WINDOWID file...'

Pourquoi le curseur clignote-t-il maintenant dans emacs/vi/... ?

Ceci est probablement causé par l'utilisation par votre éditeur/programme de la capacité terminfo "cvvis". Emacs l'utilise par défaut, ainsi que certaines versions de vi et potentiellement d'autres programmes.

Dans emacs, vous pouvez désactiver cela en ajoutant ceci à votre fichier ".emacs" :

(setq visible-cursor nil)

Pour les autres programmes, s'ils n'ont pas d'option, vous devrez supprimer la capacité "cvvis" de la description terminfo.

Lorsque urxvt a d'abord ajouté l'option de curseur clignotant, il n'a pas ajouté de capacité "cvvis", qui n'avait aucun but auparavant. La version 9.21 a introduit "cvvis" (et la capacité de contrôler le clignotement indépendamment de la forme du curseur) pour la compatibilité avec d'autres terminaux, qui utilisent traditionnellement un curseur clignotant pour "cvvis". Cela reflète également l'intention de programmes comme emacs, qui s'attendent à ce que "cvvis" active un curseur clignotant.

La nouvelle sélection sélectionne des morceaux trop grands, comment sélectionner des mots individuels ?

Si vous souhaitez sélectionner par exemple des mots alphanumériques, vous pouvez utiliser le réglage suivant :

URxvt.selection.pattern-0: ([[:word:]]+)

Si vous cliquez plus de deux fois, la sélection sera étendue de plus en plus.

Pour obtenir une sélection très similaire à l'ancien code, essayez ce motif :

URxvt.selection.pattern-0: ([^"&'()*,;<=>?@[\\\\]^`{|})]+)

Veuillez également noter que la combinaison *clic gauche* + *Shift-clic gauche* sélectionne également des mots comme l'ancien code.

Je n'aime pas la nouvelle sélection/les menus contextuels/les raccourcis/perl, comment puis-je les modifier/désactiver ?

Vous pouvez désactiver complètement l'extension perl en définissant la ressource perl-ext-common sur une chaîne vide, ce qui évite également à rxvt-unicode d'initialiser perl, économisant ainsi de la mémoire.

Si vous souhaitez uniquement désactiver des fonctionnalités spécifiques, vous devez d'abord identifier quelle extension perl en est responsable. Pour cela, lisez la section EXTENSIONS PRÉEMBALLÉES dans le manuel urxvtperl(3). Par exemple, pour désactiver les extensions selection-popup et option-popup, spécifiez la ressource perl-ext-common suivante :

URxvt.perl-ext-common: default,-selection-popup,-option-popup

Cela conservera les extensions par défaut, mais désactivera les deux extensions de menu contextuel. Certaines extensions peuvent également être configurées, par exemple, le mode de recherche de défilement est déclenché par M-s. Vous pouvez le déplacer vers une autre combinaison en ajoutant une ressource keysym qui associe la combinaison souhaitée à l'action "start" de "searchable-scrollback" et une autre qui associe M-s à l'action "builtin:" :

URxvt.keysym.CM-s: searchable-scrollback:start
URxvt.keysym.M-s: builtin:

Pendant les sessions rlogin/ssh/telnet/etc., cliquer près du curseur produit des séquences d'échappement étranges, comment corriger cela ?

Ceci est causé par l'extension perl "readline". Dans des circonstances normales, elle déplacera votre curseur lorsque vous cliquez sur la ligne qui la contient. Elle essaie de ne pas faire cela au mauvais moment, mais lors de l'exécution d'un programme qui ne parse pas les mouvements du curseur ou dans certains cas lors de sessions rlogin, elle échoue à le détecter correctement.

Vous pouvez désactiver définitivement cette fonctionnalité en désactivant l'extension "readline" :

Ma touche Compose (Multi_key) ne fonctionne plus.

Les causes les plus courantes sont soit que votre locale n'est pas correctement configurée, soit que vous avez spécifié un preeditType qui n'est pas pris en charge par votre méthode d'entrée. Par exemple, si vous avez spécifié OverTheSpot et que votre méthode d'entrée (par exemple, la méthode d'entrée par défaut gérant les touches Compose) ne le prend pas en charge (parce qu'elle n'est pas visuelle, par exemple), alors rxvt-unicode continuera sans méthode d'entrée.

Dans ce cas, ne spécifiez pas de preeditType ou spécifiez plusieurs styles de pré-édition, tels que OverTheSpot,Root,None.

Si cela ne fonctionne toujours pas, alors peut-être que votre méthode d'entrée ne prend pas en charge les séquences Compose -- pour revenir à celle intégrée, assurez-vous de ne pas spécifier de méthode d'entrée via "-im" ou "XMODIFIERS".

Je ne peux pas taper "Ctrl-Shift-2" pour obtenir un NUL ASCII à cause de la norme ISO 14755

Essayez "Ctrl-2" seul (il est souvent mappé à NUL ASCII même sur les claviers internationaux) ou utilisez simplement le support de la norme ISO 14755 à votre avantage, en tapant <Ctrl-Shift-0> pour obtenir un NUL ASCII. Cela fonctionne aussi pour d'autres codes, comme "Ctrl-Shift-1-d" pour taper le caractère d'échappement telnet par défaut, etc.

La copie/coupe par la souris ne fonctionne plus soudainement.

Assurez-vous que le reporting de la souris est effectivement désactivé car tuer certains éditeurs prématurément peut le laisser actif. J'ai entendu dire que tcsh peut utiliser le reporting de la souris à moins qu'il ne soit spécifié autrement. Une vérification rapide consiste à voir si la copie/coupe fonctionne lorsque les touches Alt ou Shift sont enfoncées.

Qu'en est-il du comportement étrange des touches Backspace/Suppr ?

En supposant que la touche Backspace physique corresponde au keysym Backspace (peu probable pour Linux... voir la question suivante), il y a deux valeurs standard qui peuvent être utilisées pour Backspace : "^H" et "^?".

Historiquement, l'une ou l'autre valeur est correcte, mais rxvt-unicode adopte la politique Debian d'utiliser "^?" en cas de doute, car c'est le seul choix correct :).

Il est possible de basculer entre "^H" et "^?" avec le mode privé DECBKM :

# utiliser Backspace = ^H
$ stty erase ^H
$ printf "\e[?67h"
# utiliser Backspace = ^?
$ stty erase ^?
$ printf "\e[?67l"

Cela aide à résoudre certaines des divergences de comportement de Backspace, mais si vous utilisez Backspace = "^H", assurez-vous que la valeur termcap/terminfo reflète correctement cela.

La touche Suppr est une autre victime du problème mal défini de Backspace. Pour éviter toute confusion entre les touches Backspace et Suppr, la touche Suppr s'est vu attribuer une séquence d'échappement pour correspondre au vt100 pour Exécuter ("ESC [ 3 ~") et elle est dans le termcap/terminfo fourni.

Quelques autres problèmes de Backspace :

certains éditeurs utilisent termcap/terminfo, certains éditeurs (vim m'a-t-on dit) attendent Backspace = ^H, GNU Emacs (et les éditeurs de type Emacs) utilisent ^H pour l'aide.

Peut-être qu'un jour tout cela sera résolu de manière cohérente.

Pourquoi rxvt-unicode ne lit-il pas mes ressources ?

Eh bien, pourquoi, en effet ? Il le fait, d'une manière très similaire aux autres applications X. Plus important encore, cela signifie que si vous ou votre système d'exploitation chargez des ressources dans l'affichage X (la bonne façon de le faire), rxvt-unicode ignorera tous les fichiers de ressources de votre répertoire personnel. Il ne lira $HOME/.Xdefaults que lorsqu'aucune ressource n'est attachée à l'affichage.

Si vous avez ou utilisez un fichier $HOME/.Xresources, il y a de fortes chances que des ressources soient chargées dans votre serveur X. Dans ce cas, vous devez vous reconnecter après chaque modification (ou exécuter xrdb -merge $HOME/.Xresources).

Considérez également la forme que doivent utiliser les ressources :

URxvt.resource: value

Si vous souhaitez utiliser une autre forme (il existe de nombreuses façons différentes de spécifier les ressources), assurez-vous de comprendre si et pourquoi elle fonctionne. En cas de doute, utilisez la forme ci-dessus.

Lorsque je me connecte à un autre système, il m'informe de l'absence de données terminfo ?

La description du terminal utilisée par rxvt-unicode n'est pas aussi répandue que celle de xterm, ou même de rxvt (pour lequel le même problème survient souvent).

La solution correcte à ce problème est d'installer le terminfo, cela peut être fait en installant simplement rxvt-unicode sur le système distant également (si vous avez un bon gestionnaire de paquets), ou vous pouvez installer la base de données terminfo manuellement comme ceci (avec ncurses infocmp. fonctionne en tant qu'utilisateur et root) :

REMOTE=remotesystem.domain
infocmp rxvt-unicode | ssh $REMOTE "mkdir -p .terminfo && cat >/tmp/ti && tic /tmp/ti"

Sur certains systèmes, vous devrez peut-être définir $TERMINFO sur le chemin complet de $HOME/.terminfo pour que cela fonctionne.

Si vous ne pouvez pas ou ne voulez pas le faire, alors vous pouvez simplement définir "TERM=rxvt" ou même "TERM=xterm", et vivre avec le petit nombre de problèmes qui en découlent, notamment un mappage de touches incorrect, moins de couleurs et des couleurs différentes, et quelques erreurs d'affichage dans les applications plein écran. C'est une bonne solution de contournement rapide et sale pour les cas rares, cependant.

Si vous souhaitez toujours le faire (et que les conséquences ne vous dérangent pas), vous pouvez soit recompiler rxvt-unicode avec la valeur TERM souhaitée, soit utiliser une ressource pour la définir :

URxvt.termName: rxvt

Si vous n'avez pas l'intention d'utiliser rxvt (assez courant...), vous pourriez également remplacer le fichier terminfo de rxvt par celui de rxvt-unicode et utiliser "TERM=rxvt".

Configuration Issues

Can't find configuration file?

Rxvt-unicode looks for configuration files in the following order:

  1. "$XDG_CONFIG_HOME/rxvt-unicode/Xresources"
  2. "$HOME/.Xresources"
  3. "$HOME/.Xdefaults"

If none of these files exist, rxvt-unicode will run with its default compile-time settings.

My configuration file is not read?

Are you sure you loaded it? Rxvt-unicode, like other X clients, reads X resources from files like ".Xresources" or ".Xdefaults". You need to load these files into the X server resources database using the xrdb command. For example:

xrdb -merge $HOME/.Xresources

You should run this command once after creating or modifying your resource file. It's common practice to put this command in your ".xinitrc" or ".xprofile" file.

How can I set the default font?

Use the "font" resource:

URxvt.font: xft:Bitstream Vera Sans Mono:size=10

See the man page ("man rxvt-unicode") for details on fonts and the "xft" font configuration.

How can I set the cursor color?

Use the "cursorColor" resource:

URxvt.cursorColor: #8080ff

How can I make the scrollbar appear on the left?

Use the "scrollbar.left" resource:

URxvt.scrollbar.left: true

Why does my shell have strange characters at the end of the line?

Try editing the "use" line in the terminfo entry for rxvt-unicode. Find the file usually in "/usr/share/terminfo/r/rxvt-unicode" (or similar) and replace the line starting with "use=" with the following defi

nition for "enacs=". Just replace it by "enacs=\E[0@" and try again.

"bash"'s readline does not work correctly under urxvt.

See next entry.

I need a termcap file entry.

One reason you might want this is that some distributions or operating systems still compile some programs using the long-obsoleted termcap library (Fedora's bash is one example) and rely on a termcap entry for "rxvt-unicode".

You could use rxvt's termcap entry with reasonable results in many cases. You can also create a termcap entry by using terminfo's infocmp program like this:

infocmp -C rxvt-unicode

Or you could use the termcap entry in doc/etc/rxvt-unicode.termcap, generated by the command above.

Why does "ls" no longer have coloured output?

The "ls" in the GNU coreutils unfortunately doesn't use terminfo to decide whether a terminal has colour, but uses its own configuration file. Needless to say, "rxvt-unicode" is not in its default file (among with most other terminals supporting colour). Either add:

TERM rxvt-unicode

to "/etc/DIR_COLORS" or simply add:

alias ls='ls --color=auto'

to your ".profile" or ".bashrc".

Unicode does not seem to work?

If you encounter strange problems like typing an accented character but getting two unrelated other characters or similar, or if program output is subtly garbled, then you should check your locale settings.

Rxvt-unicode must be started with the same "LC_CTYPE" setting as the programs running in it. Often rxvt-unicode is started in the "C" locale, while the login script running within the rxvt-unicode window changes the locale to something else, e.g. "en_GB.UTF-8". Needless to say, this is not going to work, and is the most common cause for problems.

The best thing is to fix your startup environment, as you will likely run into other problems. If nothing works you can try this in your .profile.

printf '\33]701;%s\007' "$LC_CTYPE"   # $LANG or $LC_ALL are worth a try, too

If this doesn't work, then maybe you use a "LC_CTYPE" specification not supported on your systems. Some systems have a "locale" command which displays this (also, "perl -e0" can be used to check locale settings, as it will complain loudly if it cannot set the locale). If it displays something like:

locale: Cannot set LC_CTYPE to default locale: ...

Then the locale you specified is not supported on your system.

If nothing works and you are sure that everything is set correctly then you will need to remember a little known fact: Some programs just don't support locales :(

How does rxvt-unicode determine the encoding to use?

See next entry.

Is there an option to switch encodings?

Unlike some other terminals, rxvt-unicode has no encoding switch, and no specific "utf-8" mode, such as xterm. In fact, it doesn't even know about UTF-8 or any other encodings with respect to terminal I/O.

The reasons is that there exists a perfectly fine mechanism for selecting the encoding, doing I/O and (most important) communicating this to all applications so everybody agrees on character properties such as width and code number. This mechanism is the locale. Applications not using that info will have problems (for example, "xterm" gets the width of characters wrong as it uses its own, locale-independent table under all locales).

Rxvt-unicode uses the "LC_CTYPE" locale category to select encoding. All programs doing the same (that is, most) will automatically agree in the interpretation of characters.

Unfortunately, there is no system-independent way to select locales, nor is there a standard on how locale specifiers will look like.

On most systems, the content of the "LC_CTYPE" environment variable contains an arbitrary string which corresponds to an already-installed locale. Common names for locales are "en_US.UTF-8", "de_DE.ISO-8859-15", "ja_JP.EUC-JP", i.e. "language_country.encoding", but other forms (i.e. "de" or "german") are also common.

Rxvt-unicode ignores all other locale categories, and except for the encoding, ignores country or language-specific settings, i.e. "de_DE.UTF-8" and "ja_JP.UTF-8" are the normally same to rxvt-unicode.

If you want to use a specific encoding you have to make sure you start rxvt-unicode with the correct "LC_CTYPE" category.

Can I switch locales at runtime?

Yes, using an escape sequence. Try something like this, which sets rxvt-unicode's idea of "LC_CTYPE".

printf '\33]701;%s\007' ja_JP.SJIS

See also the previous answer.

Sometimes this capability is rather handy when you want to work in one locale (e.g. "de_DE.UTF-8") but some programs don't support it (e.g. UTF-8). For example, I use this script to start "xjdic", which first switches to a locale supported by xjdic and back later:

printf '\33]701;%s\007' ja_JP.SJIS
xjdic -js
printf '\33]701;%s\007' de_DE.UTF-8

You can also use xterm's "luit" program, which usually works fine, except for some locales where character width differs between program- and rxvt-unicode-locales.

I have problems getting my input method working.

Try a search engine, as this is slightly different for every input method server.

Here is a checklist:

- Make sure your locale and the imLocale are supported on your OS.
Try "locale -a" or check the documentation for your OS.
- Make sure your locale or imLocale matches a locale supported by your XIM.
For example, kinput2 does not support UTF-8 locales, you should use "ja_JP.EUC-JP" or equivalent.
- Make sure your XIM server is actually running.
- Make sure the "XMODIFIERS" environment variable is set correctly when starting rxvt-unicode.
When you want to use e.g. kinput2, it must be set to "@im=kinput2". For scim, use "@im=SCIM". You can see what input method servers are running with this command: 
xprop -root XIM_SERVERS

My input method wants <some encoding> but I want UTF-8, what can I do?

You can specify separate locales for the input method and the rest of the terminal, using the resource "imlocale":

URxvt.imlocale: ja_JP.EUC-JP

Now you can start your terminal with "LC_CTYPE=ja_JP.UTF-8" and still use your input method. Please note, however, that, depending on your Xlib version, you may not be able to input characters outside "EUC-JP" in a normal way then, as your input method limits you.

Rxvt-unicode crashes when the X Input Method changes or exits.

Unfortunately, this is unavoidable, as the XIM protocol is racy by design. Applications can avoid some crashes at the expense of memory leaks, and Input Methods can avoid some crashes by careful ordering at exit time. kinput2 (and derived input methods) generally succeeds, while SCIM (or similar input methods) fails. In the end, however, crashes cannot be completely avoided even if both sides cooperate.

So the only workaround is not to kill your Input Method Servers.

Operating Systems / Package Maintaining

I am maintaining rxvt-unicode for distribution/OS XXX, any recommendation?

You should build one binary with the default options. configure now enables most useful options, and the trend goes to making them runtime-switchable, too, so there is usually no drawback to enabling them, except higher disk and possibly memory usage. The perl interpreter should be enabled, as important functionality (menus, selection, likely more in the future) depends on it.

You should not overwrite the "perl-ext-common" and "perl-ext" resources system-wide (except maybe with "defaults"). This will result in useful behaviour. If your distribution aim

s à faible mémoire, ajoutez une ressource vide "perl-ext-common" dans le fichier app-defaults. Cela gardera l'interpréteur perl désactivé jusqu'à ce que l'utilisateur l'active.

Si vous pouvez/voulez construire plus de binaires, je recommande de construire une version minimale avec "--disable-everything" (très utile) et une version maximale avec "--enable-everything" (moins utile, elle sera très volumineuse en raison de nombreux encodages intégrés qui augmentent les temps de téléchargement et sont rarement utilisés).

Je dois la rendre setuid/setgid pour prendre en charge utmp/ptys sur mon OS, est-ce sûr ?

Ça devrait l'être, à partir de la version 7.1. Il est maintenant recommandé d'installer correctement urxvt avec les privilèges nécessaires pour votre OS.

Lorsque rxvt-unicode détecte qu'il s'exécute en mode setuid ou setgid, il se divise en un processus auxiliaire pour les opérations privilégiées (gestion des pty sur certains systèmes, gestion de utmp/wtmp/lastlog sur d'autres) et abandonne immédiatement les privilèges. C'est beaucoup plus sûr que la plupart des autres terminaux qui conservent les privilèges pendant l'exécution (mais c'est plus pertinent pour urxvt, car il contient des éléments comme des interpréteurs perl, qui pourraient être "utiles" aux attaquants).

Cette division est effectuée tout au début de main(), ce qui est très précoce et réduit les bugs possibles au code d'initialisation exécuté avant main(), ou à des choses comme le chargeur dynamique de votre système, ce qui devrait entraîner un risque très faible.

Je suis sous FreeBSD et rxvt-unicode ne semble pas fonctionner du tout.

Rxvt-unicode nécessite que le symbole "__STDC_ISO_10646__" soit défini dans votre environnement de compilation, ou une implémentation qui le met en œuvre, qu'elle définisse ce symbole ou non. "__STDC_ISO_10646__" exige que wchar_t soit représenté comme unicode.

Comme vous l'avez peut-être deviné, FreeBSD ne définit pas ce symbole et ne le prend pas en charge. Au lieu de cela, il utilise sa propre représentation interne de wchar_t. C'est, bien sûr, tout à fait conforme aux normes.

Cependant, cela signifie que rxvt-unicode ne fonctionne que dans les locales "POSIX", "ISO-8859-1" et "UTF-8" sous FreeBSD (qui utilisent toutes Unicode comme wchar_t).

"__STDC_ISO_10646__" est la seule manière raisonnable de prendre en charge les applications multilingues dans un OS, car l'utilisation d'une représentation de wchar_t dépendante de la locale (et non standardisée) rend impossible la conversion entre wchar_t (tel qu'utilisé par X11 et vos applications) et tout autre encodage sans implémenter des wrappers spécifiques à l'OS pour chaque locale. Il n'existe simplement pas d'API pour convertir wchar_t en autre chose que l'encodage de la locale actuelle.

Certaines applications (comme le formidable mlterm) contournent ce problème en transportant leurs propres fonctions de remplacement pour la gestion des jeux de caractères, et en implémentant des hacks dépendants de l'OS ou en effectuant plusieurs conversions (ce qui est lent et peu fiable si l'OS implémente les encodages légèrement différemment de l'émulateur de terminal).

L'auteur de rxvt-unicode insiste sur le fait que la bonne façon de résoudre ce problème est de le faire dans les bibliothèques système une fois pour toutes, au lieu de forcer chaque application à transporter des remplacements complets pour elles :)

Comment puis-je utiliser rxvt-unicode sous cygwin ?

rxvt-unicode devrait compiler et s'exécuter directement sous cygwin, en utilisant les bibliothèques X11 fournies par cygwin. L'émulation de libW11 n'est plus prise en charge (et n'a plus de sens, car elle ne prenait en charge qu'une seule police). Je recommande de démarrer le serveur X en mode "-multiwindow" ou "-rootless" à la place, ce qui donnera un look&feel similaire à l'ancienne émulation libW11.

Au moment de la rédaction, cygwin ne semblait pas prendre en charge les encodages multi-octets (vous pouvez essayer "LC_CTYPE=C-UTF-8"), vous serez donc probablement limité aux encodages 8 bits.

Les largeurs de caractères ne sont pas correctes.

urxvt utilise la fonction wcwidth du système pour connaître les informations sur la largeur des caractères, donc sur les systèmes avec des données de locale incorrectes, vous obtiendrez probablement de mauvais résultats. Deux exemples notoires sont Solaris 9, où des caractères de largeur unique comme U+2514 sont signalés comme double largeur, et Darwin 8, où les caractères combinés sont signalés comme ayant une largeur de 1.

La solution est de mettre à niveau votre système ou d'en choisir un meilleur. Une solution de contournement potentiellement fonctionnelle consiste à utiliser une implémentation de wcwidth comme

http://www.cl.cam.ac.uk/~mgk25/ucs/wcwidth.c

Rapport Souris

Lorsque le rapport de souris est activé et qu'aucun des modes de souris étendus (1005, 1006, 1015) n'est actif, urxvt envoie la séquence suivante lors d'un événement de souris :

"ESC [ M <b> <x> <y>"

Les 2 bits de poids faible de "<b>" indiquent le bouton :

Bouton = "(<b> - ESPACE) & 3"
0 Bouton1 pressé
1 Bouton2 pressé
2 Bouton3 pressé
3 bouton relâché (rapport souris X11)

Les bits de poids fort de "<b>" indiquent les modificateurs lors de la pression du bouton et sont ajoutés ensemble (rapport souris X11 uniquement) :

État = "(<b> - ESPACE) & ~3"
4 Shift
8 Meta
16 Control
32 Motion Notify
32 Double Clic (extension rxvt), désactivé par défaut
64 Bouton1 est en fait Bouton4, Bouton2 est en fait Bouton5, etc.

"x" et "y" encodent les coordonnées (1|1 est le coin supérieur gauche, comme pour le positionnement du curseur) :

Col = "<x> - ESPACE"
Row = "<y> - ESPACE"

Les paramètres incluent un décalage de 32 pour garantir qu'ils soient des caractères imprimables.

Exemple : Clic sur le bouton 1 avec la touche Maj enfoncée, en haut de la ligne, colonne 80.

ESC [ M $ p !

La coordonnée la plus grande qui peut être représentée dans ce codage est 223. La plage peut être étendue en utilisant l'un des modes de souris étendus, qui doit être activé *avant* d'activer le rapport de souris, pour des raisons assez évidentes.

Mode 1005

Si le mode 1005 est actif, urxvt envoie la séquence

"ESC [ M <b> <x> <y>"

avec les coordonnées fournies sous forme de caractères dans le codage de la locale au lieu d'octets sur 1 caractère. Ce mode ne fonctionne pas correctement dans les locales non-UTF-8 et doit donc être évité.

Mode 1006

Si le mode 1006 est actif, urxvt envoie les séquences suivantes :

"ESC [ < <b>;<x>;<y> M"
appui et mouvement du bouton
"ESC [ < <b>;<x>;<y> m"
relâchement du bouton

où les paramètres sont fournis sous forme de nombres décimaux au lieu d'octets et n'incluent pas de décalage de 32.

Les 2 bits de poids faible de "b" encodent le numéro du bouton également lors du relâchement du bouton (au lieu de la valeur 3). Le caractère final de la séquence (M ou m) spécifie le type d'événement (appui/mouvement ou relâchement).

Exemple : Clic sur le bouton 1 avec la touche Maj enfoncée, en haut de la ligne, colonne 80.

ESC [ < 4 ; 80 ; 1 M

Mode 1015

Si le mode 1015 est actif, urxvt envoie la séquence

"ESC [ <b>;<x>;<y> M"

où les paramètres sont fournis sous forme de nombres décimaux au lieu d'octets et seul "b" inclut un décalage de 32.

Exemple : Clic sur le bouton 1 avec la touche Maj enfoncée, en haut de la ligne, colonne 80.

ESC [ 36 ; 80 ; 1 M

Ajoute la prise en charge du clignotement du texte.
--enable-pointer-blank (défaut : activé)
Ajoute la prise en charge pour que le pointeur disparaisse lors de la frappe ou lorsqu'il est inactif.
--enable-perl (défaut : activé)
Active un interpréteur perl intégré. Voir le manuel urxvtperl(3) pour plus d'informations sur cette fonctionnalité, ou les fichiers dans src/perl/ pour les extensions qui sont installées par défaut. L'interpréteur perl utilisé peut être spécifié via la variable d'environnement "PERL" lors de l'exécution de configure. Même compilé, perl ne sera *pas* initialisé lorsque toutes les extensions auront été désactivées "-pe "" --perl-ext-common """, il devrait donc être sûr de l'activer d'un point de vue ressources.
--enable-assert (défaut : désactivé)
Active les assertions dans le code, normalement désactivées. Cette option n'est utile que lors du développement de rxvt-unicode.
--enable-256-color (défaut : désactivé)
Force l'utilisation du mode dit 256 couleurs, pour contourner les applications boguées qui ne prennent pas en charge termcap/terminfo, ou simplement pour améliorer la prise en charge des applications qui codent en dur la table des 256 couleurs de xterm.

Cette option casse la compatibilité termcap/terminfo avec "TERM=rxvt-unicode", et par conséquent définit "TERM" à "rxvt-unicode-256color" par défau

lt (doc/etc/ contient des définitions termcap/terminfo pour les deux).

Cela entraîne également une consommation de mémoire plus élevée et peut ralentir considérablement urxvt lorsque plus de six polices sont utilisées par une instance de terminal.

--with-name=NAME (défaut : urxvt)
Définit le nom de base des binaires installés, résultant en "urxvt", "urxvtd" etc.). Spécifiez "--with-name=rxvt" pour remplacer par "rxvt".
--with-term=NAME (défaut : rxvt-unicode)
Définit la valeur par défaut de "TERM" qu'urxvt définit. La valeur par défaut est soit "rxvt-unicode", soit "rxvt-unicode-256color", selon le cas.
--with-terminfo=PATH
S'il est défini, urxvt définira la variable d'environnement "TERMINFO" sur le PATH donné, ce qui peut être utile en dernier recours si l'installation des entrées terminfo au niveau du système n'est pas possible.
--with-x
Utiliser le système de fenêtrage X (presque par défaut, hein ?).
