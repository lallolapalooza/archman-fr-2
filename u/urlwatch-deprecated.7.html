NOM

urlwatch-deprecated - Documentation de la dépréciation de fonctionnalités dans urlwatch

Au fur et à mesure que les fonctionnalités sont dépréciées et supprimées, elles sont documentées ici avec les étapes pour mettre à jour votre configuration pour les remplacements.

NETWORKIDLE0 ET NETWORKIDLE2 POUR WAIT_UNTIL DANS LES TRAVAUX DE NAVIGATION (DEPUIS 2.28)

Depuis la version 2.28, l'exécution des travaux de navigation utilise Playwright à la place de pyppetteer.

Les valeurs précédemment prises en charge pour wait_until, à savoir networkidle0 et networkidle2, ne sont plus supportées. Playwright prend en charge les valeurs load, domcontentloaded, networkidle (déconseillé) ou commit à la place.

Les réglages existants de networkidle0 et networkidle2 seront mappés à networkidle, et un avertissement sera émis. Pour faire taire l'avertissement et continuer à utiliser networkidle, spécifiez explicitement wait_until: networkidle.

FILTRES SANS SOUS-FILTRES (DEPUIS 2.22)

Dans les anciennes versions d'urlwatch, il était possible d'écrire des filtres personnalisés qui ne prenaient pas un subfilter comme argument.

Si vous avez écrit votre propre code de filtre comme ceci :

class CustomFilter(filters.FilterBase):
    """Mon ancien filtre personnalisé"""
    __kind__ = 'foo'
    def filter(self, data):
        ...

Vous devez mettre à jour votre filtre pour qu'il prenne un argument de sous-filtre optionnel (si la configuration du filtre ne définit pas de sous-filtre, la valeur de subfilter sera None) :

class CustomFilter(filters.FilterBase):
    """Mon nouveau filtre personnalisé"""
    __kind__ = 'foo'
    def filter(self, data, subfilter):
        ...

DÉFINITIONS DE FILTRES BASÉES SUR DES CHAÎNES (DEPUIS 2.19)

Avec urlwatch 2.19, les listes de filtres basées sur des chaînes sont dépréciées, car elles ne sont pas aussi flexibles que les listes de filtres basées sur des dictionnaires et présentaient certains problèmes (par exemple, : et , sont traités de manière spéciale et ne peuvent pas être utilisés facilement dans les sous-filtres). Si vous avez une définition de filtre comme celle-ci :

filter: css:body,html2text:re,strip

Vous pouvez obtenir les mêmes résultats avec une définition de filtre comme celle-ci :

filter:
  - css:
      selector: body
  - html2text:
      method: re
  - strip

Comme selector est le sous-filtre par défaut pour css, et method est le sous-filtre par défaut pour html2text, cela peut également s'écrire comme suit :

filter:
  - css: body
  - html2text: re
  - strip

Si vous n'avez qu'un seul filtre tel que :

filter: html2text

Vous pouvez modifier ce filtre pour qu'il soit basé sur un dictionnaire en utilisant :

filter:
  - html2text

RÉGLAGE KEYRING DANS LA CONFIGURATION DU RAPPORTEUR SMTP (DEPUIS 2.18)

Depuis la version 2.18, la configuration du rapporteur SMTP utilise auth pour décider si l'authentification SMTP doit être effectuée ou non. Auparavant, ce réglage s'appelait keyring. Si vous avez une ancienne configuration comme celle-ci :

report:
  email:
    smtp:
      host: localhost
      keyring: false
      port: 25
      starttls: true
    subject: '{count} changes: {jobs}'

Vous pouvez modifier le réglage pour qu'il devienne ceci (remplacez keyring par auth) :

report:
  email:
    smtp:
      host: localhost
      auth: false
      port: 25
      starttls: true
    subject: '{count} changes: {jobs}'
