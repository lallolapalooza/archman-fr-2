NOM

ukify - Combiner des composants en une Image de Noyau Unifiée signée pour les systèmes UEFI

SYNTAXE

ukify [OPTIONS...] build

ukify [OPTIONS...] genkey

ukify [OPTIONS...] inspect FICHIER...

DESCRIPTION

ukify est un outil dont le but principal est de combiner des composants (généralement un noyau, un initrd et un programme de démarrage UEFI) pour créer une Image de Noyau Unifiée (UKI)[1] — un binaire PE qui peut être exécuté par le firmware pour démarrer le noyau Linux embarqué. Voir systemd-stub(7) pour plus de détails sur le stub.

COMMANDES

Les commandes suivantes sont comprises :

build

Cette commande crée une Image de Noyau Unifiée. Les deux options principales qui doivent être spécifiées pour le verbe build sont Linux=/--linux=, et Initrd=/--initrd=. Initrd= accepte plusieurs chemins séparés par des espaces et --initrd= peut être spécifié plusieurs fois.

Des sections supplémentaires seront insérées dans l'UKI, soit automatiquement, soit uniquement si une option spécifique est fournie. Voir les discussions sur Microcode=/--microcode=, Cmdline=/--cmdline=, OSRelease=/--os-release=, DeviceTree=/--devicetree=, DeviceTreeAuto=/--devicetree-auto=, HWIDs=/--hwids=, Splash=/--splash=, PCRPKey=/--pcrpkey=, Uname=/--uname=, SBAT=/--sbat=, et --section= ci-dessous.

ukify peut également être utilisé pour assembler un binaire PE qui n'est pas exécutable mais contient des données auxiliaires, par exemple des entrées de ligne de commande de noyau supplémentaires.

Si des clés de signature PCR sont fournies via les options PCRPrivateKey=/--pcr-private-key= et PCRPublicKey=/--pcr-public-key= ou PCRCertificate=/--pcr-certificate=, les valeurs PCR qui seront vues après le démarrage avec le noyau, l'initrd et les autres sections donnés, seront calculées, signées et intégrées dans l'UKI. systemd-measure(1) est utilisé pour effectuer ce calcul et la signature.

Le calcul des valeurs PCR est effectué pour des chemins de phase de démarrage spécifiques. Ceux-ci peuvent être spécifiés avec l'option Phases=/--phases=. Si non spécifié, la valeur par défaut fournie par systemd-measure est utilisée. Il est également possible de spécifier les arguments PCRPrivateKey=/--pcr-private-key=, PCRPublicKey=/--pcr-public-key= ou PCRCertificate=/--pcr-certificate=, et Phases=/--phases= plus d'une fois. Les signatures seront alors effectuées avec chacune des clés spécifiées. Sur la ligne de commande, lorsque --phases= et --pcr-private-key= sont utilisés, ils doivent être spécifiés le même nombre de fois, et alors l'ensemble n-ième de chemins de phase de démarrage sera signé par la n-ième clé. Ceci peut être utilisé pour construire différentes politiques de confiance pour différentes phases du démarrage. Dans le fichier de configuration, PCRPrivateKey=, PCRPublicKey=, et Phases= sont regroupés en sections distinctes, décrivant différentes phases de démarrage. Si SigningEngine=/--signing-engine= ou SigningProvider=/--signing-provider= est spécifié, alors les arguments de clé privée seront passés tels quels à openssl(1) sous forme d'URIs, et les arguments de clé publique seront chargés comme certificats X.509, de manière à ce que la signature puisse être effectuée avec un moteur ou un fournisseur OpenSSL respectivement.

Si une clé de signature SecureBoot est fournie via l'option SecureBootPrivateKey=/--secureboot-private-key=, le binaire PE résultant sera signé dans son ensemble, permettant ainsi à l'UKI résultant d'être approuvé par SecureBoot. Voir également la discussion sur l'enregistrement automatique dans systemd-boot(7).

Si le stub et/ou le noyau contiennent des sections ".sbat" elles seront fusionnées dans l'UKI afin que les mises à jour de révocation affectant l'un ou l'autre soient prises en compte lorsque l'UKI sera chargé par Shim. Pour plus d'informations sur SBAT, voir la documentation Shim[2].

genkey

Cette commande crée les clés pour la signature PCR et la clé ainsi que le certificat utilisés pour la signature SecureBoot. Les mêmes options de configuration qui déterminent quelles clés et dans quels chemins seront nécessaires pour la signature lors de l'utilisation de build, déterminent ici quelles clés seront créées. Voir la discussion sur PCRPrivateKey=/--pcr-private-key=, PCRPublicKey=/--pcr-public-key=, et SecureBootPrivateKey=/--secureboot-private-key= ci-dessous.

Les fichiers de sortie ne doivent pas exister.

inspect

Affiche des informations sur les sections dans un ou plusieurs binaires donnés. Si --all est spécifié, toutes les sections sont affichées. Sinon, si l'option --section= est spécifiée au moins une fois, seules ces sections sont affichées. Sinon, les sections connues qui sont typiquement incluses dans une UKI sont affichées. Pour chaque section, son nom, sa taille et son digest sha256 sont imprimés. Pour les sections texte, le contenu est imprimé.

Voir également la description de -j/--json= et --section=.

D'autres outils potentiellement utiles pour inspecter les UKI : llvm-objdump(1) -p et pe-inspect.

PARAMÈTRES DE CONFIGURATION

Les paramètres peuvent apparaître dans les fichiers de configuration (syntaxe avec Paramètre=valeur) et sur la ligne de commande (syntaxe avec --paramètre=valeur). Pour certains paramètres de ligne de commande, un raccourci à une seule lettre est également autorisé. Dans les fichiers de configuration, le paramètre doit se trouver dans la section appropriée, de sorte que les descriptions soient regroupées par section ci-dessous. Lorsque le même paramètre apparaît dans le fichier de configuration et sur la ligne de commande, généralement le paramètre de la ligne de commande a une priorité plus élevée et écrase complètement le paramètre du fichier de configuration. Si un paramètre se comporte différemment, cela est décrit ci-dessous.

Si aucun fichier de configuration n'est fourni via l'option --config=CHEMIN, ukify tentera de rechercher un fichier de configuration par défaut dans les chemins suivants dans cet ordre : /etc/systemd/ukify.conf, /run/systemd/ukify.conf, /usr/local/lib/systemd/ukify.conf, et /usr/lib/systemd/ukify.conf, puis chargera le premier trouvé. ukify continuera normalement si aucun fichier de configuration n'est spécifié et qu'aucun fichier par défaut n'est trouvé.

Les arguments positionnels LINUX et INITRD, ou les paramètres équivalents Linux= et Initrd=, sont optionnels. Si plus d'un initrd est spécifié, ils seront tous combinés en une seule section PE. Ceci est utile pour, par exemple, préfixer le microcode avant l'initrd réel.

Les options et paramètres suivants sont compris :

Options en ligne de commande uniquement

--config=CHEMIN

Charge la configuration à partir du fichier de configuration donné. En général, les paramètres spécifiés dans le fichier de configuration ont une priorité inférieure à celle des paramètres spécifiés via les options. Dans les cas où l'option de ligne de commande ne remplace pas complètement le paramètre du fichier de configuration, cela est explicitement mentionné dans les descriptions des options individuelles.

Ajouté dans la version 254.

--measure, --no-measure

Active ou désactive un appel à systemd-measure(1) pour afficher les valeurs PCR pré-calculées. Par défaut, c'est faux.

Ajouté dans la version 253.

--policy-digest, --no-policy-digest

Active ou désactive un appel à systemd-measure(1) pour afficher les digests de politiques TPM2 pré-calculés. Utile pour la signature hors ligne des politiques PCR. Par défaut, c'est faux.

Ajouté dans la version 258.

--section=NOM:TEXTE|@CHEMIN, --section=NOM:texte|binaire[@CHEMIN]

Pour tous les verbes sauf inspect, la première syntaxe est utilisée. Spécifie une section arbitraire supplémentaire nommée "NOM". L'argument peut être une chaîne littérale, ou "@" suivi d'un nom de chemin. Cette option peut être spécifiée plus d'une fois.

Ce site n'est en aucun cas associé à Arch Linux ni affilié à ce projet. Le contenu est uniquement une traduction des pages de manuel d'Arch publiées sur man.archlinux.org.

ce. Toute section spécifiée de cette manière sera insérée (dans l'ordre) avant la section ".linux", qui est toujours la dernière.

Pour le verbe inspect, la deuxième syntaxe est utilisée. La section NAME sera inspectée (si trouvée). Si le deuxième argument est "text", le contenu sera imprimé. Si le troisième argument est fourni, le contenu sera sauvegardé dans le fichier nommé PATH.

Notez que le nom est utilisé tel quel, et si le nom de la section doit commencer par un point, il doit être inclus dans NAME.

Ajouté dans la version 253.

--join-profile=PATH

Prend un chemin vers un fichier PE existant contenant un profil supplémentaire à ajouter à l'image noyau unifiée. Le profil peut être généré au préalable avec ukify. Le profil n'a pas besoin d'être signé ou de contenir des mesures PCR. Toutes les sections PE de l'image noyau unifiée du fichier PE spécifié sont copiées dans l'image noyau unifiée générée. Ceci est utile pour générer des images noyau unifiées multi-profils. Notez que cela ne copie que les sections PE définies par la spécification de l'image noyau unifiée et ignore toute autre, par exemple ".text" ou similaire.

Ajouté dans la version 257.

--sign-profile=ID

Prend un identifiant de profil pour lequel des mesures PCR signées doivent être générées par ukify. Cette option peut être utilisée conjointement avec --join-profile= lors de la construction de l'image noyau unifiée finale. Si elle n'est pas spécifiée, des mesures PCR signées seront ajoutées pour tous les profils.

Ajouté dans la version 258.

--join-pcrsig=PATH, --pcrsig=TEXT|@PATH

--join-pcrsig= prend un chemin vers un fichier PE existant contenant une image noyau unifiée précédemment construite. --pcrsig= prend un chemin vers un blob JSON pcrsig existant, ou un blob littéral en ligne. Ils doivent être utilisés ensemble, et sans spécifier d'autres paramètres de section d'image noyau unifiée. ukify attachera le blob JSON pcrsig à l'image noyau unifiée. Ceci est utile en combinaison avec --policy-digest pour créer une image noyau unifiée, puis signer les digests de politique TPM2 hors ligne.

Ajouté dans la version 258.

--tools=DIRS

Spécifiez un ou plusieurs répertoires contenant des outils d'aide. ukify recherchera les outils d'aide dans ces répertoires en premier, et s'ils ne sont pas trouvés, essaiera de les charger depuis $PATH de la manière habituelle.

Ajouté dans la version 253.

--output=FILENAME

Le nom du fichier de sortie. S'il n'est pas spécifié, le nom de l'argument LINUX, avec le suffixe ".unsigned.efi" ou ".signed.efi" sera utilisé, en fonction de si la signature pour SecureBoot a été effectuée.

Ajouté dans la version 253.

--summary

Imprime un résumé de la configuration chargée et quitte. Ceci est utile pour vérifier comment les options du fichier de configuration et de la ligne de commande sont combinées.

Ajouté dans la version 254.

--all

Imprime toutes les sections (avec le verbe inspect).

Ajouté dans la version 255.

--json

Génère une sortie JSON (avec le verbe inspect).

Ajouté dans la version 255.

-h, --help

Imprime un bref message d'aide et quitte.

--version

Imprime une courte chaîne de version et quitte.

Section [UKI]

Linux=LINUX, --linux=LINUX

Un chemin vers le binaire du noyau.

Ajouté dans la version 254.

OSRelease=TEXT|@PATH, --os-release=TEXT|@PATH

La description os-release (la section ".osrel"). L'argument peut être une chaîne littérale, ou "@" suivi d'un nom de chemin. S'il n'est pas spécifié, le fichier os-release(5) sera récupéré du système hôte.

Ajouté dans la version 253.

Cmdline=TEXT|@PATH, --cmdline=TEXT|@PATH

La ligne de commande du noyau (la section ".cmdline"). L'argument peut être une chaîne littérale, ou "@" suivi d'un nom de chemin. S'il n'est pas spécifié, aucune ligne de commande ne sera intégrée.

Ajouté dans la version 253.

Initrd=INITRD..., --initrd=LINUX

Zéro ou plusieurs chemins d'initrd. Dans le fichier de configuration, les éléments sont séparés par des espaces. Les initrds sont combinés dans l'ordre de spécification, avec les initrds spécifiés dans le fichier de configuration en premier.

Ajouté dans la version 254.

Microcode=UCODE, --microcode=UCODE

Chemin vers l'initrd contenant les mises à jour du microcode. S'il n'est pas spécifié, la section ne sera pas présente.

Ajouté dans la version 256.

Splash=PATH, --splash=PATH

Une image à afficher pendant le démarrage (la section ".splash"). L'argument est un chemin vers un fichier BMP. S'il n'est pas spécifié, la section ne sera pas présente.

Ajouté dans la version 253.

DeviceTree=PATH, --devicetree=PATH

La description de l'arbre de périphériques (la section ".dtb"). L'argument est un chemin vers un fichier d'arbre de périphériques binaire compilé. S'il n'est pas spécifié, la section ne sera pas présente.

Ajouté dans la version 253.

DeviceTreeAuto=PATH..., --devicetree-auto=PATH

Zéro ou plusieurs fichiers d'arbre de périphériques sélectionnables automatiquement. Dans le fichier de configuration, les éléments sont séparés par des espaces. Chaque arbre de périphériques sera dans une section ".dtbauto" distincte.

Ajouté dans la version 257.

HWIDs=PATH, --hwids=PATH

La table des identifiants matériels des périphériques (la section ".hwids"). L'argument est un chemin vers un répertoire contenant des fichiers de description JSON des périphériques HWID. Chaque fichier doit contenir un seul objet JSON avec les clés "name", "compatible" et "hwids". Les clés "name" et "compatible" doivent avoir des valeurs de type chaîne et la clé "hwids" doit avoir une liste de chaînes comme valeur, où les chaînes doivent être des UUID valides représentant des CHID/HWID. Exemple : 
{
    "type": "devicetree",
    "name": "Exemple Ordinateur Portable 16 Génération 7",
    "compatible": "example,laptop-16-g7",
    "hwids": [
        "5dc05bf4-01f6-4089-b464-a08c47ea9295",
        "3e3f8f3c-2003-46f2-811c-85554f7d5952"
    ]
}

Ici, "Exemple Ordinateur Portable 16 Génération 7" est le "name" de l'appareil (tel que défini par le fabricant), "example,laptop-16-g7" est le "compatible" (tel que défini par le noyau) et "hwids" est un tableau de CHID/HWID (extrait, par exemple, de la sortie de fwupdtool hwids). S'il n'est pas spécifié, la section ne sera pas présente. Il est recommandé de spécifier ce paramètre si des arbres de périphériques sélectionnables automatiquement doivent être utilisés.

Ajouté dans la version 257.

Uname=VERSION, --uname=VERSION

Spécifie la version du noyau (comme dans uname -r, la section ".uname"). S'il n'est pas spécifié, une tentative sera faite pour extraire la chaîne de version de l'image du noyau. Il est recommandé de le passer explicitement si connu, car l'extraction est basée sur des heuristiques et n'est pas très fiable. S'il n'est pas spécifié et que l'extraction échoue, la section ne sera pas présente.

Ajouté dans la version 253.

SBAT=TEXT|@PATH, --sbat=TEXT|@PATH

Métadonnées SBAT associées à l'image noyau unifiée ou à un module complémentaire. Les politiques SBAT sont utiles pour révoquer des groupes entiers d'images noyau unifiées ou de modules complémentaires avec une seule mise à jour de politique statique qui ne prend pas de place dans DBX/MOKX. S'il n'est pas spécifié manuellement, une entrée de métadonnées par défaut composée de 
uki,1,UKI,uki,1,https://uapi-group.org/specifications/specs/unified_kernel_image/

pour les images noyau unifiées et

uki-addon,1,UKI Addon,addon,1,https://www.freedesktop.org/software/systemd/man/latest/systemd-stub.html

pour les modules complémentaires sera utilisée, afin de garantir qu'il est toujours possible de les révoquer. Pour plus d'informations sur SBAT, voir la documentation Shim[2].

Ajouté dans la version 254.

PCRPKey=PATH, --pcrpkey=PATH

Un chemin vers une clé publique à intégrer dans la section ".pcrpkey". S'il n'est pas spécifié, et qu'il y a exactement un argument PCRPublicKey=/--pcr-public-key= ou PCRCertificate=/--pcr-certificate=, cette clé sera utilisée. Sinon, la section ne sera pas présente.

Ajouté dans la version 253.

Profile=PATH, --profile=PATH

Un chemin vers un profil d'image noyau unifiée à placer dans une section ".profile". Cette option est utile pour créer des images noyau unifiées multi-profils, et est généralement utilisée en combinaison avec --join-profile=, pour étendre l'image noyau unifiée spécifiée avec un profil supplémentaire.

Ajouté dans la version 257.

PCRBanks=PATH, --pcr-banks=PATH

Une liste de banques PCR séparées par des virgules ou des espaces pour signer une politique. S'il n'est pas présent, toutes les banques connues seront utilisées ("sha1", "sha256", "sha384", "sha512"), ce qui échouera si elles ne sont pas prises en charge par le système.

Ajouté dans la version 253.

SecureBootSigningTool=SIGNER, --signtool=SIGNER

Indique s'il faut utiliser "sbsign", "pesign" ou "systemd-sbsign". Selon ce choix, des paramètres différents sont requis pour signer une image. Par défaut, "sbsign".

Ajouté dans la version 254.

SecureBootPrivateKey=SB_KEY, --secureboot-private-key=SB_KEY

Un chemin vers une clé privée à utiliser pour la signature du binaire résultant. Si l'option SigningEngine=/--signing-engine= ou SigningProvider=/--signing-provider= est utilisée, cela peut également être une désignation spécifique à un moteur ou à un fournisseur. Cette option est requise par SecureBootSigningTool=sbsign/--signtool=sbsign et SecureBootSigningTool=systemd-sbsign/--signtool=systemd-sbsign.

Ajouté dans la version 253.

SecureBootCertificate=SB_CERT, --secureboot-certificat e=SB_CERT

Un chemin vers un certificat à utiliser pour la signature du binaire résultant. Si l'option SigningEngine=/--signing-engine= ou SigningProvider=/--signing-provider= est utilisée, cela peut également être une désignation spécifique au moteur ou au fournisseur de signature. Cette option est requise par SecureBootSigningTool=sbsign/--signtool=sbsign et SecureBootSigningTool=systemd-sbsign/--signtool=systemd-sbsign.

Ajouté dans la version 253.

SecureBootCertificateDir=SB_PATH, --secureboot-certificate-dir=SB_PATH

Un chemin vers un répertoire de base de données de certificats nss à utiliser pour la signature du binaire résultant. Prend effet lorsque SecureBootSigningTool=pesign/--signtool=pesign est utilisé. Par défaut, /etc/pki/pesign.

Ajouté dans la version 254.

SecureBootCertificateName=SB_CERTNAME, --secureboot-certificate-name=SB_CERTNAME

Le nom de l'entrée de la base de données de certificats nss à utiliser pour la signature du binaire résultant. Cette option est requise par SecureBootSigningTool=pesign/--signtool=pesign.

Ajouté dans la version 254.

SecureBootCertificateValidity=DAYS, --secureboot-certificate-validity=DAYS

Période de validité (en jours) pour un certificat créé par genkey. Par défaut, 3650, soit 10 ans.

Ajouté dans la version 254.

SigningEngine=ENGINE, --signing-engine=ENGINE

Un moteur OpenSSL à utiliser pour signer le binaire résultant et les mesures PCR, voir openssl-engine(1).

Ajouté dans la version 253.

SigningProvider=PROVIDER, --signing-provider=PROVIDER

Un fournisseur OpenSSL à utiliser pour signer le binaire résultant et les mesures PCR, voir provider(7). Cette option ne peut être utilisée qu'avec systemd-sbsign comme outil de signature.

Ajouté dans la version 257.

CertificateProvider=PROVIDER, --certificate-provider=PROVIDER

Un fournisseur OpenSSL à utiliser pour charger le certificat utilisé pour signer le binaire résultant et les mesures PCR, voir provider(7). Cette option ne peut être utilisée qu'avec systemd-sbsign comme outil de signature.

Ajouté dans la version 257.

SignKernel=BOOL, --sign-kernel, --no-sign-kernel

Annuler la détection si le binaire Linux lui-même doit être signé avant d'être intégré à l'image combinée. Si non spécifié, il sera signé si une clé de signature Secure Boot est fournie via l'option SecureBootPrivateKey=/--secureboot-private-key= et que le binaire n'a pas déjà été signé. Si SignKernel=/--sign-kernel est vrai, et que le binaire a déjà été signé, la signature sera ajoutée de toute façon.

Ajouté dans la version 253.

Section [PCRSignature:NAME]

Dans le fichier de configuration, ces options sont regroupées par section. Sur la ligne de commande, elles doivent être spécifiées dans le même ordre. Les sections spécifiées dans les deux sources sont combinées.

PCRPrivateKey=PATH, --pcr-private-key=PATH

Une clé privée à utiliser pour signer les politiques PCR. Sur la ligne de commande, cette option peut être spécifiée plusieurs fois, auquel cas plusieurs signatures seront effectuées.

Ajouté dans la version 253.

PCRPublicKey=PATH, --pcr-public-key=PATH

Une clé publique à utiliser pour signer les politiques PCR.

Sur la ligne de commande, cette option peut être spécifiée plus d'une fois, de manière similaire à l'option --pcr-private-key=. Si elle n'est pas présente, les clés publiques seront extraites des clés privées. Sur la ligne de commande, si elle est présente, cette option doit être spécifiée autant de fois que l'option --pcr-private-key=. Ne peut pas être spécifiée si --pcr-certificate= est utilisée.

Ajouté dans la version 253.

PCRCertificate=PATH, --pcr-certificate=PATH

Un certificat X.509 à utiliser pour signer les politiques PCR.

Sur la ligne de commande, cette option peut être spécifiée plus d'une fois, de manière similaire à l'option --pcr-private-key=. Si elle n'est pas présente, les clés publiques seront extraites des clés privées. Sur la ligne de commande, si elle est présente, cette option doit être spécifiée autant de fois que l'option --pcr-private-key=. Ne peut pas être spécifiée si --pcr-public-key= est utilisée.

Ajouté dans la version 258.

Phases=LIST, --phases=LIST

Une liste de chemins de phases, séparés par des virgules ou des espaces, et séparés par des deux-points, pour signer une politique. Chaque ensemble de chemins de phases de démarrage sera signé avec la clé privée correspondante. Si non présent, le défaut de systemd-measure(1) sera utilisé.

Sur la ligne de commande, lorsque cet argument est présent, il doit apparaître le même nombre de fois que l'option --pcr-private-key=.

Ajouté dans la version 253.

EXEMPLES

Exemple 1. Invocation minimale

$ ukify build \
      --linux=/lib/modules/6.0.9-300.fc37.x86_64/vmlinuz \
      --initrd=/some/path/initramfs-6.0.9-300.fc37.x86_64.img \
      --cmdline='quiet rw'

Ceci crée un UKI non signé ./vmlinuz.unsigned.efi.

Exemple 2. Toutes options et fonctionnalités

$ ukify build \
      --linux=/lib/modules/6.0.9-300.fc37.x86_64/vmlinuz \
      --initrd=early_cpio \
      --initrd=/some/path/initramfs-6.0.9-300.fc37.x86_64.img \
      --sbat='sbat,1,SBAT Version,sbat,1,https://github.com/rhboot/shim/blob/main/SBAT.md
      uki.author.myimage,1,UKI for System,uki.author.myimage,1,https://uapi-group.org/specifications/specs/unified_kernel_image/' \
      --pcr-private-key=tpm2-pcr-initrd-private-key.pem \
      --pcr-public-key=tpm2-pcr-initrd-public-key.pem \
      --phases='enter-initrd' \
      --pcr-private-key=tpm2-pcr-private-key-system.pem \
      --pcr-public-key=tpm2-pcr-public-key-system.pem \
      --phases='enter-initrd:leave-initrd enter-initrd:leave-initrd:sysinit \
                enter-initrd:leave-initrd:sysinit:ready' \
      --pcr-banks=sha384,sha512 \
      --secureboot-private-key=secureboot-private-key.pem \
      --secureboot-certificate=secureboot-certificate.pem \
      --sign-kernel \
      --cmdline='quiet rw rhgb'

Ceci crée un UKI signé ./vmlinuz.signed.efi. La section initrd contient deux parties concaténées, early_cpio et initramfs-6.0.9-300.fc37.x86_64.img. La politique intégrée dans la section ".pcrsig" sera signée pour l'initrd (la phase enter-initrd) avec la clé tpm2-pcr-initrd-private-key.pem, et pour le système principal (phases leave-initrd, sysinit, ready) avec la clé tpm2-pcr-private-key-system.pem. Le binaire Linux et l'image combinée résultante seront signés avec la clé SecureBoot secureboot-private-key.pem.

Exemple 3. Toutes options et fonctionnalités, via un fichier de configuration

C'est identique à l'exemple précédent, mais cette fois la configuration est stockée dans un fichier :

$ cat ukify.conf
[UKI]
Initrd=early_cpio
Cmdline=quiet rw rhgb
SecureBootPrivateKey=secureboot-private-key.pem
SecureBootCertificate=secureboot-certificate.pem
SignKernel=yes
PCRBanks=sha384,sha512
[PCRSignature:initrd]
PCRPrivateKey=tpm2-pcr-initrd-private-key.pem
PCRPublicKey=tpm2-pcr-initrd-public-key.pem
Phases=enter-initrd
[PCRSignature:system]
PCRPrivateKey=tpm2-pcr-private-key-system.pem
PCRPublicKey=tpm2-pcr-public-key-system.pem
Phases=enter-initrd:leave-initrd
       enter-initrd:leave-initrd:sysinit
       enter-initrd:leave-initrd:sysinit:ready
$ ukify -c ukify.conf build \
        --linux=/lib/modules/6.0.9-300.fc37.x86_64/vmlinuz \
        --initrd=/some/path/initramfs-6.0.9-300.fc37.x86_64.img

Un "initrd" (early_cpio) est spécifié dans le fichier de configuration, et l'autre initrd (initramfs-6.0.9-300.fc37.x86_64.img) est spécifié sur la ligne de commande. Cela peut être utile, par exemple, lorsque le premier initrd contient le microcode du CPU et n'a pas besoin d'être mis à jour lorsque la version du noyau change, contrairement à l'initrd réel.

Exemple 4. Extension de ligne de commande du noyau PE

ukify build \
      --secureboot-private-key=secureboot-private-key.pem \
      --secureboot-certificate=secureboot-certificate.pem \
      --cmdline='debug' \
      --sbat='sbat,1,SBAT Version,sbat,1,https://github.com/rhboot/shim/blob/main/SBAT.md
      uki-addon.author,1,UKI Addon for System,uki-addon.author,1,https://www.freedesktop.org/software/systemd/man/systemd-stub.html'
      --output=debug.addon.efi

Ceci crée un binaire PE signé qui contient le paramètre de ligne de commande supplémentaire du noyau "debug" avec des métadonnées SBAT faisant référence au propriétaire de l'extension.

Exemple 5. Décider de la politique de signature, et créer un certificat et des clés

D'abord, créons un fichier de configuration qui spécifie quelles signatures doivent être effectuées :

# cat >/etc/kernel/uki.conf <<EOF
[UKI]
SecureBootPrivateKey=/etc/kernel/secureboot-private-key.pem
SecureBootCertificate=/etc/kernel/secureboot-certificate.pem
[PCRSignature:initrd]
Phases=enter-initrd
PCRPrivateKey=/etc/systemd/tpm2-pcr-initrd-private-key.pem
PCRPublicKey=/etc/systemd/tpm2-pcr-initrd-public-key.pem
[PCRSignature:system]
Phases=enter-initrd:leave-initrd enter-initrd:leave-initrd:sysinit
       enter-initrd:leave-initrd:sysinit:ready
PCRPrivateKey=/etc/systemd/tpm2-pcr-private-key-system.pem
PCRPublicKey=/etc/systemd/tpm2-pcr-public-key-system.pem
EOF

Ensuite, nous pouvons générer le certificat et les clés :

# ukify genkey --config=/etc/kernel/uki.conf
Writing SecureBoot private key to /etc/kernel/secureboot-private-key.pem
Writing SecureBoot certificate to /etc/kernel/secureboot-certificate.pem
Writing private key for PCR signing to /etc/systemd/tpm2-pcr-initrd-private-key.pem
Writing public key for PCR signing to /etc/systemd/tpm2-pcr-initrd-public-key.pem
Writing private key for PCR signing to /etc/systemd/tpm2-pcr-private-key-system.pem
Writing public key for PCR signing to /etc/systemd/tpm2-pcr-public-key-system.pem

(Les deux opérations doivent être effectuées en tant que root pour permettre l'accès en écriture à /etc/kernel/.)

Les invocations ultérieures utilisant le fichier de configuration (ukify build

--config=/etc/kernel/uki.conf) utiliseront ces fichiers de certificat et de clé. Notez que le plugin kernel-install(8) 60-ukify.install utilise /etc/kernel/uki.conf par défaut, donc après la création de ce fichier, les installations de noyaux qui créent une UKI sur la machine locale à l'aide de kernel-install effectueront la signature en utilisant cette configuration.

Exemple 6. UKI multi-profils

Tout d'abord, créez quelques profils :

$ ukify build \
      --profile='TITLE=Base' \
      --output=profile0.efi

Ajoutez un deuxième profil (@1) :

$ ukify build \
      --profile='TITLE=Démarrer en mode cible de stockage
ID=storagetm' \
      --cmdline='quiet rw rd.systemd.unit=storage-target-mode.target' \
      --output=profile1.efi

Ajoutez un troisième profil (@2) :

$ ukify build \
      --profile='TITLE=Réinitialisation d'usine
ID=factory-reset' \
      --cmdline='quiet rw systemd.unit=factory-reset.target' \
      --output=profile2.efi

Ensuite, créez une UKI et incluez tous les profils générés :

$ ukify build \
      --linux=/lib/modules/6.0.9-300.fc37.x86_64/vmlinuz \
      --initrd=/some/path/initramfs-6.0.9-300.fc37.x86_64.img \
      --cmdline='quiet rw' \
      --join-profile=profile0.efi \
      --join-profile=profile1.efi \
      --join-profile=profile2.efi \
      --output=base.efi

L'UKI résultante base-with-profile-0-1-2.efi contiendra maintenant trois profils.

Exemple 7. Signature hors ligne de la section pcrsig

Tout d'abord, créez une UKI et enregistrez le blob JSON des PCR :

$ ukify build \
      --linux=/lib/modules/6.0.9-300.fc37.x86_64/vmlinuz \
      --initrd=/some/path/initramfs-6.0.9-300.fc37.x86_64.img \
      --cmdline='quiet rw' \
      --pcr-public-key=tpm2-pcr-initrd-public-key.pem \
      --policy-digest \
      --json=short \
      --output=base.efi >base.pcrs

Ensuite, signez les digestions PCR hors ligne et insérez-les dans le blob JSON :

#!/usr/bin/python3
import base64, json, subprocess
priv_key = '/home/zbyszek/src/systemd/tpm2-pcr-private.pem'
base_file = 'base.pcrs'
base = json.load(open(base_file))
for bank,policies in base.items():
    for policy in policies:
        pol = base64.b16decode(policy['pol'].upper())
        call = subprocess.run(['openssl', 'dgst', f'-{bank}', '-sign', priv_key],
                              input=pol,
                              check=True,
                              capture_output=True)
        sig = base64.b64encode(call.stdout).decode()
        policy['sig'] = sig
print(json.dumps(base))

Enfin, attachez le blob JSON mis à jour à l'UKI :

$ ukify build \
      --join-pcrsig=base.efi \
      --pcrsig=@base.pcrs \
      --json=short \
      --output=base-signed.efi

L'UKI résultante base-signed.efi contiendra maintenant les digestions PCR signées.
