UPSMON(8) Manuel NUT UPSMON(8)

NOM

upsmon - Moniteur et contrôleur d'arrêt d'onduleur

SYNTAXE

upsmon -h

upsmon -c commande [-P pid]

upsmon [-D] [-F | -B] [-K] [-p] [-u utilisateur]

DESCRIPTION

upsmon est le processus client responsable de la partie la plus importante de la surveillance d'onduleur : l'arrêt du système en cas de coupure de courant. Il peut faire appel à d'autres programmes auxiliaires à des fins de notification lors des événements d'alimentation.

upsmon peut surveiller plusieurs systèmes en utilisant un seul processus. Chaque onduleur défini dans le fichier de configuration upsmon.conf(5) se voit attribuer une valeur de puissance et un type (primary ou secondary).

OPTIONS

-c commande

Envoie la commande commande au processus upsmon existant. Les commandes valides sont :

fsd

Arrête tous les onduleurs en mode primaire (à utiliser avec prudence)

stop

Arrête la surveillance et quitte

reload

relit le fichier de configuration upsmon.conf(5). Voir la section « nuances de rechargement » ci-dessous si cela ne fonctionne pas.

-P pid

Envoie le signal de commande ci-dessus en utilisant le numéro PID spécifié, plutôt que de consulter le fichier PID. Cela peut aider à définir des unités de service qui démarrent upsmon principal en premier plan, afin qu'il n'ait pas à dépendre d'un fichier PID.

-D

Augmente le niveau de débogage. upsmon s'exécutera en premier plan par défaut et affichera des informations sur stdout concernant le processus de surveillance. Utilisez cette option plusieurs fois pour plus de détails.

-F

upsmon s'exécutera en premier plan, indépendamment des paramètres de débogage.

-B

upsmon s'exécutera en arrière-plan, indépendamment des paramètres de débogage.

-K

Teste le drapeau d'arrêt. S'il existe et contient la chaîne magique de upsmon, alors upsmon se terminera avec EXIT_SUCCESS. Toute autre condition entraînera la sortie de upsmon avec EXIT_FAILURE.

Vous pouvez tester une sortie réussie de upsmon -K dans vos scripts d'arrêt pour savoir quand appeler upsdrvctl(8) pour arrêter l'onduleur.

-p

Exécute avec les privilèges tout le temps. Normalement, upsmon se divisera en deux processus. La majorité du code s'exécute en tant qu'utilisateur non privilégié, et seule une petite partie s'exécute en tant que root pour appeler éventuellement SHUTDOWNCMD si nécessaire. Ce commutateur désactivera ce mode et exécutera l'ancien système « tout root tout le temps ».

Ce n'est pas le mode recommandé, et vous ne devriez pas l'utiliser sauf si vous avez une très bonne raison.

-u utilisateur

Définit l'utilisateur pour le processus de surveillance non privilégié. Cela n'a aucun effet lors de l'utilisation de -p.

L' utilisateur par défaut est défini lors de la configuration de compilation avec configure --with-user=.... Typiquement, c'est nobody (sauf configuration contraire), ce qui est loin d'être idéal, donc la plupart des distributions packagées auront probablement un utilisateur nut spécifique pour cette tâche. Si vos scripts de notification doivent s'exécuter en tant qu'utilisateur spécifique, définissez-le ici.

Vous pouvez également définir cela dans le fichier upsmon.conf(5) avec la directive RUN_AS_USER.

OPTIONS COMMUNES

-h

Affiche le message d'aide de la ligne de commande.

-V

Affiche la bannière de la version NUT. Plus de détails peuvent être disponibles si vous exportez également NUT_DEBUG_LEVEL=1 ou un niveau de verbosité supérieur.

-W secondes

Définit le délai d'attente pour les connexions réseau initiales (par défaut, elles sont indéfiniment non bloquantes, ou jusqu'à ce que le système interrompe la tentative). Remplace la variable d'environnement optionnelle NUT_DEFAULT_CONNECT_TIMEOUT.

DÉFINITIONS ONDULEUR

Dans le fichier upsmon.conf(5), vous devez spécifier au moins un onduleur qui sera surveillé. Utilisez la directive MONITOR comme ceci :

MONITOR 'système' 'valeur_puissance' 'nom_utilisateur' 'mot_de_passe' 'type'

Le système fait référence à un serveur upsd(8), sous la forme nom_onduleur[@nom_hôte[:port]]. Le nom_hôte par défaut est "localhost", et le port par défaut est 3493. Voici quelques exemples :

•"su700@ma_machine" signifie un onduleur appelé "su700" sur une machine nommée "ma_machine". C'est la forme normale.
•"fenton@grosse_machine:5678" est un onduleur appelé "fenton" sur une machine nommée "grosse_machine" qui exécute upsd(8) sur le port "5678".

La valeur_puissance fait référence au nombre d'alimentations de ce système client qui sont alimentées par cet onduleur. Ceci est typiquement réglé sur 1, mais consultez la section sur les valeurs de puissance ci-dessous.

Le nom_utilisateur est une section de votre fichier upsd.users(5). Quel que soit le mot de passe que vous définissez dans cette section doit correspondre au mot_de_passe défini dans ce fichier pour l'instance correspondante du serveur de données.

Le type défini dans cette section de la configuration du serveur de données doit également correspondre au type ici — primary ou secondary (considérez-le comme un « rôle upsmon »). En général, un processus client « primaire » est celui qui s'exécute sur le système où l'onduleur est réellement branché sur un port série ou USB, et un « secondaire » tire son énergie de l'onduleur mais ne peut pas y communiquer directement. Voir la section sur les types d'onduleurs pour plus d'informations.

ÉVÉNEMENTS DE NOTIFICATION

upsmon détecte plusieurs événements lorsqu'il surveille chaque onduleur. Ils sont appelés « événements de notification », car ils peuvent être utilisés pour informer les utilisateurs et les administrateurs du changement d'état. Voir les sections supplémentaires liées à la notification ci-dessous pour des informations sur la personnalisation de la distribution de ces messages.

ONLINE

L'onduleur est de retour en ligne.

ONBATT

L'onduleur fonctionne sur batterie.

LOWBATT

La batterie de l'onduleur est faible (tel que déterminé par le pilote).

FSD

L'onduleur a été commandé en mode « arrêt forcé ».

COMMOK

La communication avec l'onduleur a été établie.

COMMBAD

La communication avec l'onduleur vient d'être perdue.

SHUTDOWN

Le système local est en train d'être arrêté.

REPLBATT

La batterie de l'onduleur doit être remplacée.

NOCOMM

L'onduleur ne peut pas être contacté pour la surveillance.

NOPARENT

Le processus parent de upsmon est mort - arrêt impossible.

CAL

Calibration de l'onduleur en cours.

NOTCAL

Calibration de l'onduleur terminée.

OFF

Onduleur administrativement OFF ou en veille.

NOTOFF

Onduleur plus administrativement OFF ou en veille.

BYPASS

Onduleur sur le bypass (alimenté, non protecteur).

NOTBYPASS

Onduleur plus sur le bypass.

ECO

Onduleur en mode ECO ou similaire (tel que défini et nommé par le vendeur) ; d'autres noms incluent le mode Haute Efficacité et le Système d'Économie d'Énergie.

Par exemple, la documentation Eaton définit le mode Haute Efficacité comme une sorte de bypass surveillé par matériel avec basculement en moins de 10 ms en mode Online en cas de problèmes (ce qui était appelé Line-Interactive dans le passé), qui peut être choisi au lieu de fonctionner toujours en mode double conversion (plus sûr, mais plus gaspilleur et avec un impact sur la durée de vie de la batterie). Les anciens appareils n'implémentaient que l'un ou l'autre.

NOTECO

Onduleur plus en mode ECO (voir ci-dessus).

ALARM

L'onduleur a une ou plusieurs alarmes actives (regardez ups.alarm pour les détails).

NOTALARM

L'onduleur n'est plus en état d'alarme (aucune alarme active).

OVER

L'onduleur est surchargé.

NOTOVER

L'onduleur n'est plus surchargé.

TRIM

L'onduleur régule la tension d'entrée.

NOTTRIM

L'onduleur ne régule plus la tension d'entrée.

BOOST

L'onduleur augmente la tension d'entrée.

NOTBOOST

L'onduleur n'augmente plus la tension d'entrée.

OTHER

L'onduleur a au moins un jeton de statut non classifié.

NOTOTHER

L'onduleur n'a plus de jetons de statut non classifiés.

SUSPEND_STARTING

Le système d'exploitation entre en mode veille/suspension/hibernation.

SUSPEND_FINISHED

Le système d'exploitation vient de terminer le mode veille/suspension/hibernation, désactivant les lectures obsolètes de l'onduleur pour éviter un arrêt inopportun.

COMMANDE DE NOTIFICATION

Dans upsmon.conf(5), vous pouvez configurer un programme appelé NOTIFYCMD qui gérera les événements qui se produisent.

La syntaxe est : NOTIFYCMD "chemin vers le programme"

Exemple :

•NOTIFYCMD ""/usr/local/bin/notifyme""

N'oubliez pas d'encadrer le chemin avec des guillemets doubles s'il contient des espaces. Il ne devrait probablement pas dépendre de la réception d'arguments en ligne de commande.

Le programme que vous exécutez en tant que NOTIFYCMD peut utiliser les variables d'environnement NOTIFYTYPE et UPSNAME pour savoir ce qui s'est passé et sur quel onduleur. Il reçoit également le message de notification (voir ci-dessous) comme premier (et unique) argument, vous pouvez donc également délivrer un message pré-formaté.

Notez que le NOTIFYCMD ne sera appelé pour un événement donné que lorsque vous définissez le drapeau EXEC en utilisant les drapeaux de notification, comme détaillé ci-dessous.

DRAPEAUX DE NOTIFICATION

Par défaut, tous les événements de notification (voir ci-dessus) génèrent un message global (wall) à tous les utilisateurs, et sont également enregistrés via syslog. Sauf pour Windows où upsmon écrit uniquement dans syslog par défaut. Vous pouvez modifier cela avec la directive NOTIFYFLAG dans le fichier de configuration :

La syntaxe est : NOTIFYFLAG notifynotifype drapeaux

Exemples :

•NOTIFYFLAG ONLINE SYSLOG
•NOTIFYFLAG ONBATT SYSLOG+WALL
•NOTIFYFLAG LOWBATT SYSLOG+WALL+EXEC

Les drapeaux qui peuvent être définis pour un événement de notification donné sont :

SYSLOG

Écrire ce message dans syslog.

WALL

Envoyer ce message à tous les utilisateurs du système via wall(1).

EXEC

Exécuter le NOTIFYCMD.

IGNORE

Ne rien faire. Si vous utilisez ceci, n'utilisez aucun des autres drapeaux.

Vous pouvez mélanger ces drapeaux ; par exemple, SYSLOG+WALL+EXEC fait les trois pour un événement donné.

MESSAGES DE NOTIFICATION

upsmon est livré avec des messages par défaut pour chacun des événements de NOTIFICATION. Ceux-ci peuvent être modifiés avec la directive NOTIFYMSG.

La syntaxe est : NOTIFYMSG type ""message""

Exemples :

•NOTIFYMSG ONLINE "Onduleur %s récupère le courant secteur"
•NOTIFYMSG ONBATT "Quelqu'un a débranché %s"

La première occurrence de %s est remplacée par l'identifiant de l'onduleur qui a généré l'événement. Ces messages sont utilisés lors de l'envoi de murs aux utilisateurs directement depuis upsmon, et sont également transmis au NOTIFYCMD.


Note

Certaines notifications, telles que NOTIFY_ALARM et NOTIFY_OTHER, peuvent accepter une deuxième occurrence de %s qui serait remplacée par le texte de l'alarme ou le jeton non reconnu, respectivement.

VALEURS DE PUISSANCE

La "valeur globale de puissance actuelle" est la somme de tous les onduleurs qui sont actuellement capables d'alimenter le système hébergeant upsmon. Tout onduleur qui est soit en ligne, soit simplement sur batterie contribue à ce nombre. Si un onduleur est critique (sur batterie et batterie faible) ou a été mis en mode "arrêt forcé", il ne contribue plus.

La syntaxe est : MONITOR nom_onduleur valeur_puissance nom_utilisateur mot_de_passe type

Une "valeur de puissance" sur une ligne MONITOR dans le fichier de configuration est le nombre d'alimentations que l'onduleur fait fonctionner sur le système actuel.

•Normalement, vous n'avez qu'une seule alimentation, donc elle sera réglée sur 1.

Exemple :

•MONITOR mononduleur@monhost 1 nomutilisateur mondemotdepasse primaire
•Sur un grand serveur avec des alimentations redondantes, la valeur de puissance d'un onduleur peut être supérieure à 1. Vous pouvez également en avoir plus d'un défini.

Exemples pour un serveur avec quatre modules d'alimentation et deux onduleurs (chacun alimentant deux alimentations de ce serveur) :

•MONITOR onduleur-alpha@monhost 2 nomutilisateur mondemotdepasse primaire
•MONITOR onduleur-beta@monhost 2 nomutilisateur mondemotdepasse primaire
•Vous pouvez également définir la valeur de puissance d'un onduleur à 0 s'il n'alimente pas ce système. Ceci est généralement utilisé lorsque vous souhaitez utiliser les fonctionnalités de notification d'upsmon pour un onduleur même s'il n'alimente pas réellement le système qui héberge cette instance du client upsmon.

Ne réglez pas ceci sur "primaire" à moins que vous ne vouliez vraiment éteindre cet onduleur lorsque cette instance de upsmon doit s'arrêter pour ses propres raisons.

Exemple :

•MONITOR lointain@autreboite 0 nomutilisateur mondemotdepasse secondaire

La "valeur minimale de puissance" est le nombre d'alimentations qui doivent recevoir de l'énergie pour que l'ordinateur de ce client upsmon continue de fonctionner.

La syntaxe est : MINSUPPLIES valeur

•Les PC typiques n'en ont qu'un, donc la plupart des utilisateurs laisseront cette valeur par défaut.

Exemple :

•MINSUPPLIES 1
•Si vous avez un serveur ou un système similaire avec une alimentation redondante, cette valeur sera généralement réglée plus haut. Un système qui nécessite que trois alimentations sur quatre soient en fonctionnement à tout moment le réglera simplement sur 3.

Exemple :

•MINSUPPLIES 3

Lorsque la valeur globale globale de puissance externe protégée par onduleur tombe en dessous de la valeur de puissance minimale requise, upsmon démarre la séquence d'arrêt. Cette conception vous permet de perdre certaines de vos alimentations dans un environnement d'alimentation redondante sans arrêter tout le système, tout en fonctionnant correctement pour les systèmes plus petits.

TYPES D'ONduleur

upsmon et upsd(8) ne s'exécutent pas toujours sur le même système. Lorsqu'ils le font, tous les onduleurs directement connectés à l'hôte upsmon doivent être surveillés en mode "primaire". Cela permet à upsmon de prendre en charge cet équipement, et il attendra que les systèmes "secondaires" se déconnectent avant d'arrêter le système local. Cela permet aux systèmes distants (surveillés via le réseau) de s'arrêter proprement avant que upsdrvctl shutdown ne s'exécute localement et ne les éteigne tous.

Lorsque upsmon s'exécute en tant que secondaire, il dépend du système distant pour connaître l'état de l'onduleur. Lorsque cet onduleur devient critique (sur batterie et batterie faible), il déclenche immédiatement la commande d'arrêt locale. Cela doit se produire rapidement. Une fois que tous les secondaires se sont déconnectés du serveur distant upsd(8), son upsmon en mode primaire lancera son propre processus d'arrêt. Vos systèmes secondaires doivent tous s'arrêter proprement avant que le primaire n'éteigne la source d'alimentation partagée, sinon des dommages au système de fichiers pourraient survenir.

upsmon gère les secondaires qui se bloquent, se figent ou ne parviennent pas à se déconnecter gracieusement de upsd(8) en temps voulu avec le minuteur HOSTSYNC. Pendant une situation d'arrêt, le upsmon primaire abandonnera après cet intervalle et s'arrêtera quand même. Cela évite que le primaire ne reste là indéfiniment (ce qui mettrait en danger cet hôte) si un secondaire venait à se dégrader. Cela est réglé par défaut sur 15 secondes.

Si votre système primaire s'arrête trop rapidement, réglez l'intervalle FINALDELAY sur une valeur supérieure à la valeur par défaut de 15 secondes. Ne la réglez pas trop haut, sinon la batterie de votre onduleur pourrait s'épuiser avant que le processus upsmon primaire n'arrête ce système.

ARRÊTS PLANIFIÉS

Pour les rares situations où le processus d'arrêt ne peut pas être achevé entre le moment où la batterie faible est signalée et le moment où l'onduleur coupe effectivement la charge, utilisez le programme utilitaire upssched(8). Vous pouvez l'utiliser avec upsmon pour planifier un arrêt basé sur l'événement "sur batterie". upssched peut alors revenir à upsmon pour initier l'arrêt une fois qu'il est sur batterie trop longtemps.

Cela peut être compliqué et désordonné, alors tenez-vous-en à la gestion par défaut de l'onduleur critique si vous le pouvez.

ALIMENTATIONS REDONDANTES

Si vous avez plus d'une alimentation pour une alimentation redondante, vous pouvez également avoir plus d'un onduleur alimentant votre ordinateur. upsmon peut gérer cela. Assurez-vous de régler correctement les valeurs de puissance de l'onduleur et la valeur MINSUPPLIES suffisamment élevée pour qu'il continue de fonctionner jusqu'à ce qu'il ait réellement besoin de s'arrêter.

Par exemple, le HP NetServer LH4 a par défaut 3 alimentations installées, avec un emplacement vide. Il a deux cordons d'alimentation, un de chaque côté du boîtier. Cela signifie qu'un cordon d'alimentation alimente deux baies d'alimentation, et que vous ne pouvez avoir que deux onduleurs alimentant.

Connectez l'onduleur "alpha" au cordon alimentant deux alimentations, et l'onduleur "beta" au cordon alimentant la troisième et l'emplacement vide. Définissez alpha comme une valeur de puissance de 2, et beta comme une valeur de puissance de 1. Réglez MINSUPPLIES sur 2.

Lorsque alpha passe sur batterie, votre valeur de puissance globale actuelle restera à 3, car elle alimente toujours. Cependant, une fois qu'il

goes critique (sur batterie et batterie faible), il cessera de contribuer à la valeur globale de puissance actuelle. Cela signifie que la valeur sera de 1 (beta seul), ce qui est inférieur à 2. C'est insuffisant pour faire fonctionner le système, et upsmon déclenchera la séquence d'arrêt.

Cependant, si beta devient critique, sa contribution soustraite fera passer la valeur globale actuelle de 3 à 2. C'est juste assez pour satisfaire le minimum, donc le système continuera de fonctionner comme auparavant. Si beta revient plus tard, il sera rajouté et la valeur actuelle reviendra à 3. Cela vous permet d'échanger des onduleurs, de changer une configuration d'alimentation, ou quoi que ce soit d'autre, tant que vous maintenez la valeur de puissance minimale à tout moment.

OPÉRATIONS MIXTES

En plus de pouvoir surveiller plusieurs onduleurs, upsmon peut également les surveiller selon différents rôles. Si vous avez un système avec plusieurs alimentations électriques desservies par des batteries d'onduleurs séparées, il est possible d'être un primaire sur un onduleur et un secondaire sur l'autre. Cela se produit généralement lorsque vous manquez de ports série ou USB et que vous devez effectuer la surveillance via un autre système proche.

C'est aussi compliqué, surtout lorsqu'il s'agit d'éteindre un onduleur qui est devenu critique mais qui n'alimente pas le système local. Vous pouvez le faire avec un peu de magie de script dans votre script de commande de notification, mais c'est au-delà de la portée de ce manuel.

ARRÊTS FORCÉS

Lorsque upsmon est forcé d'arrêter le système local, il définit le drapeau "FSD" (arrêt forcé) sur tous les onduleurs qu'il surveille en mode primaire. Ceci est utilisé pour synchroniser les systèmes secondaires dans le cas où un primaire qui est par ailleurs correct doit être arrêté en raison d'un événement urgent sur le système de gestion de l'onduleur.

Vous pouvez déclencher manuellement ce mode sur le système avec upsmon en mode primaire en démarrant une autre copie du programme avec l'argument de ligne de commande -c fsd. Ceci est utile lorsque vous souhaitez initier un arrêt avant le stade critique par un moyen externe, tel que upssched(8).


Attention

Veuillez noter que par conception, étant donné que nous exigeons une coupure de courant de la charge et que nous ne voulons pas que certains systèmes soient éteints pendant que d'autres restent en marche si l'alimentation secteur revient au mauvais moment comme d'habitude, le drapeau "FSD" ne peut pas être supprimé du serveur de données à moins que son démon ne soit redémarré. Si nous franchissons la première étape en mode critique, alors nous avons normalement l'intention d'aller jusqu'au bout - arrêter tous les serveurs en douceur, et éteindre l'onduleur.

Gardez à l'esprit que certains appareils UPS et leurs pilotes correspondants peuvent également verrouiller ou autrement refaire surface l'état "FSD" même si l'alimentation secteur est disponible, mais que la charge de batterie restante est inférieure à un seuil configuré comme "sûr" dans l'appareil (généralement si vous allumez manuellement l'onduleur après une longue panne de courant). Ceci est par conception des fournisseurs d'onduleurs respectifs, car dans une telle situation, ils ne peuvent garantir que si une nouvelle panne de courant survient, leur onduleur arrêtera à nouveau safement vos systèmes. Il est donc jugé préférable et plus sûr de rester éteint jusqu'à ce que les batteries soient suffisamment chargées.

Lorsqu'il est temps d'arrêter, upsmon crée POWERDOWNFLAG pour communiquer au système d'exploitation que l'onduleur doit être commandé d'éteindre tard dans la séquence d'arrêt. Ce fichier est supprimé s'il est présent lorsque upsmon démarre, de sorte que le prochain arrêt normal ne provoque pas l'extinction de l'onduleur. (Le fichier ne peut généralement pas être supprimé pendant l'arrêt car le système de fichiers peut être en lecture seule. Si le fichier se trouve dans un système de fichiers monté en RAM, il ne sera pas présent et la vérification pour le supprimer ne s'exécutera pas.)

SIMULATION DE PANNE DE COURANT

Pour tester un arrêt synchronisé sans débrancher votre ou vos onduleurs, il suffit de définir le drapeau d'arrêt forcé (FSD) sur eux. Vous pouvez le faire en appelant à nouveau upsmon pour définir le drapeau, c'est-à-dire :

:; upsmon -c fsd

Après cela, le primaire et le secondaire effectueront leur séquence d'arrêt habituelle comme si la batterie était devenue critique, pendant que vous pourrez mesurer le temps qu'il leur faut. C'est beaucoup plus facile pour votre équipement UPS, et cela évite de ramper sous un bureau pour trouver la prise.

Notez que vous pouvez également utiliser un réglage SHUTDOWNCMD factice pour simplement signaler que les systèmes s'arrêteraient à ce moment-là, sans interrompre réellement leur travail.


Attention

Après de telles expériences "factices", vous devrez peut-être redémarrer le serveur de données NUT upsd pour effacer son drapeau "FSD" pour les appareils et les clients concernés, et vous assurer qu'aucun fichier nommé par l'option POWERDOWNFLAG (par exemple, /etc/killpower) ne reste sur les systèmes primaires upsmon en cours de test.

ONDEURS EN PANNE

Dans le cas où upsmon ne peut pas atteindre upsd(8), il déclare que l'onduleur est "mort" après un certain intervalle contrôlé par DEADTIME dans upsmon.conf(5). Si cela se produit alors que cet onduleur était dernièrement connu pour être sur batterie, il est supposé être devenu critique et ne contribue plus à la valeur de puissance globale.

upsmon vous alertera d'un onduleur qu'il ne peut pas contacter pour la surveillance avec un notificateur "NOCOMM" par défaut toutes les 300 secondes. Ceci peut être modifié avec le paramètre NOCOMMWARNTIME.

De plus, upsmon signale normalement les échecs d'interrogation pour chaque appareil qui se produisent dans chaque boucle POLLFREQ (par exemple, "Données obsolètes" ou "Pilote non connecté") au journal système tel que configuré. Si vos appareils sont censés être indisponibles pendant une période prolongée, vous pouvez utiliser POLLFAIL_LOG_THROTTLE_MAX pour réduire la charge sur le trafic syslog et le stockage, en postant ces messages une seule fois toutes les quelques cycles de boucle, et lorsque la condition d'erreur a changé ou a été résolue. Une valeur négative signifie un comportement standard (journalisation à chaque boucle, effectivement identique à max=1), et une valeur zéro signifie ne jamais répéter le message (journalisation uniquement au début et à la fin/changement de l'état d'échec).

Notez que ce limiteur ne s'applique qu'à un seul état d'erreur le plus récent par appareil surveillé.

ALARMES ONDULEUR

Les fabricants d'onduleurs et les pilotes d'onduleurs peuvent implémenter des alarmes spécifiques à l'appareil pour informer l'utilisateur des conditions potentiellement graves de l'onduleur. Le statut "ALARM" sera défini sur de tels onduleurs comme dénominateur commun pour les différentes implémentations à travers les divers pilotes d'onduleurs et généralement chaque fois qu'une variable "ups.alarm" est signalée par le pilote d'onduleur spécifique.

Les alarmes peuvent être traitées par l'utilisateur en utilisant les notificateurs "ALARM" et "NOTALARM", qui sont rapportés par upsmon lorsque le statut "ALARM" se produit ou disparaît.

Comme les alarmes déclenchées par l'onduleur sont généralement de nature grave, upsmon surveille un onduleur dans un tel état de plus près, augmentant la fréquence d'interrogation si nécessaire.

Lorsqu'une perte de connexion se produit dans un tel état d'alarme, upsmon considérera par défaut l'onduleur volatil comme critique/mort et cela peut entraîner des arrêts intempestifs si l'alarme réelle était d'une nature banale (par exemple, causée par un mode HE/ECO). Ceci peut être modifié en utilisant le réglage ALARMCRITICAL dans upsmon.conf.

NUANCES DE RECHARGEMENT

upsmon renonce généralement aux pouvoirs root pour le processus qui effectue la majeure partie du travail, y compris la gestion des signaux comme SIGHUP pour recharger le fichier de configuration. Cela signifie que votre fichier upsmon.conf(5) doit être lisible par le compte non-root vers lequel upsmon bascule.

Si vous souhaitez que les rechargements fonctionnent, upsmon doit s'exécuter en tant qu'utilisateur ayant les permissions de lire le fichier de configuration. Nous recommandons de créer un nouvel utilisateur juste pour ce faire, car rendre le fichier lisible par "personne" (l'utilisateur par défaut) serait une mauvaise idée ; les paquets expédient généralement avec un utilisateur nut ou ups pour exécuter les services de démon NUT.

Voir la section RUN_AS_USER dans upsmon.conf(5) pour en savoir plus sur ce sujet.

De plus, vous ne pouvez pas modifier les définitions SHUTDOWNCMD ou POWERDOWNFLAG avec un rechargement en raison du modèle de processus divisé. Si vous modifiez ces valeurs, vous **devez** arrêter upsmon et le redémarrer. upsmon vous avertira dans syslog si vous apportez des modifications à l'une de ces valeurs lors d'un rechargement.

VARIABLES ENVIRONNEMENT

NUT_DEBUG_LEVEL définit la verbosité de débogage par défaut si aucun argument -D n'a été fourni sur la ligne de commande, mais ne demande pas que le démon s'exécute en mode premier plan.

NUT_CONFPATH est le nom de chemin du répertoire qui contient upsmon.conf et d'autres fichiers de configuration. Si cette variable n'est pas définie, upsmon utilise un défaut intégré, qui est souvent /usr/local/ups/etc.

NUT_QUIET_INIT_UPSNOTIFY=true peut être utilisé pour empêcher les démons qui peuvent notifier les frameworks de gestion de services (comme systemd) du passage de leurs jalons de cycle de vie d'émettre de telles notifications (y compris celles concernant l'absence de support du système pour de telles fonctionnalités modernes, une fois par exécution).

NUT_QUIET_INIT_BANNER=true peut être utilisé pour supprimer la bannière du nom et de la version de l'outil NUT. NON recommandé pour les services en raison d'un impact négatif sur le dépannage, mais peut être utile dans les profils de shell ou les scripts qui traitent les sorties des outils NUT.
