DESCRIPTION

Les fonctions constituent un système assez extensible d'analyse de divers fichiers de configuration au moment de l'exécution d'une application. Le flux des fichiers de configuration est divisé dans les phases suivantes :

1.
Enregistrement des gestionnaires.
2.
Lecture des fichiers de configuration pour les besoins d'analyse préalable aux MIB.
3.
Lecture et analyse des fichiers MIB textuels.
4.
Lecture des fichiers de configuration pour les directives de configuration.
5.
Optionnellement, relecture des fichiers de configuration à une date ultérieure.

L'idée est que l'application appelante puisse enregistrer des gestionnaires pour certains jetons spécifiés dans certains fichiers de configuration nommés. La fonction read_configs() peut ensuite être appelée pour rechercher tous les fichiers de configuration pertinents, faire correspondre le premier mot de chaque ligne à la liste des jetons enregistrés et passer le reste de la ligne au gestionnaire enregistré approprié.

ENREGISTREMENT D'UN GESTIONNAIRE

register_config_handler()
Enregistre une routine de gestionnaire de configuration, qui doit être appelée pour traiter les directives de configuration commençant par le jeton spécifié. Par exemple :
register_config_handler("snmp", "exampleToken", example_handler, NULL, "ARG1 [ARG2]");
enregistrerait la fonction example_handler() de telle sorte qu'elle soit appelée chaque fois que le premier mot d'une ligne dans le(s) fichier(s) de configuration snmp.conf correspond à "exampleToken".
Appeler les gestionnaires appropriés pour traiter les directives du fichier de configuration est la responsabilité de read_configs() (voir ci-dessous).
register_const_config_handler()
Similaire à la fonction register_config_handler(), mais la routine d'analyse est explicitement contrainte de ne pas modifier la chaîne analysée.
register_prenetsnmp_mib_handler()
Similaire à la fonction register_config_handler(), mais la routine de gestionnaire enregistrée sera appelée avant que les MIB textuels ne soient lus. Ceci est généralement utilisé pour les jetons qui affecteront la configuration de l'analyseur MIB, et ne sera normalement utilisé qu'à l'intérieur de la bibliothèque SNMP elle-même.
register_mib_handlers()
Routine d'initialisation pour enregistrer les gestionnaires de configuration internes de la bibliothèque SNMP.
unregister_config_handler()
Supprime le gestionnaire de configuration enregistré pour le filePrefix et le token spécifiés.
unregister_all_config_handlers()
Supprime tous les gestionnaires de configuration enregistrés.

Gestionnaires de jetons

Les fonctions de gestionnaire doivent avoir la signature suivante :

void handler(const char *token, char *line);
ou
void handler(const char *token, const char *line); br (si enregistré à l'aide de register_const_config_handler)

La fonction sera appelée avec deux arguments, le premier étant le jeton qui a déclenché l'appel à cette fonction (c'est-à-dire le jeton utilisé lors de l'enregistrement du gestionnaire), et le second étant le reste de la ligne du fichier de configuration (c'est-à-dire tout ce qui suit l'espace blanc après le jeton correspondant).

Gestionnaires de libération

Si la fonction de gestionnaire de jetons alloue dynamiquement des ressources lors du traitement d'une entrée de configuration, celles-ci devront peut-être être libérées avant de relire les fichiers de configuration. Si le quatrième paramètre ( releaser ) passé à register_config_handler n'est pas NULL, il spécifie une fonction à appeler avant de relire les fichiers de configuration. Cette fonction doit libérer toutes les ressources allouées par la fonction de gestionnaire de jetons et réinitialiser sa notion de la configuration à ses valeurs par défaut. La fonction de gestionnaire de jetons peut alors être appelée à nouveau en toute sécurité. Aucun argument n'est passé au gestionnaire de libération de ressources.
Notez que cette fonction n'est pas appelée lorsque le gestionnaire est désenregistré individuellement (mais est appelée dans le cadre de unregister_all_config_handlers() ).

Gestionnaires d'applications

register_app_config_handler()
register_app_prenetsnmp_mib_handler()
unregister_app_config_handler()

Ces fonctions sont similaires à leurs homologues de gestionnaire de configuration, mais elles s'appliquent aux fichiers de configuration spécifiques à l'application (c'est-à-dire qui ne sont pas préfixés par un nom de fichier de configuration spécifique à MIB). L'argument filePrefix est donc omis pour ces fonctions.

Les gestionnaires d'applications ne sont pas appelés par read_configs(), mais ils sont appelés par le système d'options de la ligne de commande getopt_parse_args() et par la fonction read_command_line_configs().

LECTURE DES FICHIERS DE CONFIGURATION

read_premib_configs()
Lit les fichiers de configuration avant que les MIB ne soient analysés. Les gestionnaires enregistrés avec register_prenetsnmp_mib_handler() et register_app_prenetsnmp_mib_handler() seront appelés.
read_configs()
Lit tous les fichiers de configuration pertinents et appelle les gestionnaires enregistrés appropriés. Les gestionnaires enregistrés avec register_config_handler() et register_app_config_handler() seront appelés.

Ces fonctions recherchent les fichiers de configuration dans les emplacements par défaut standard ainsi que dans ceux spécifiés par la variable d'environnement NETSNMP_CONFIG_DIR et le chemin de configuration du système.

AIDE ET ERREURS

read_config_print_usage()
Imprime les lignes d'aide enregistrées pour tous les gestionnaires de configuration enregistrés. L'argument lead est une chaîne à imprimer au début de chaque ligne d'aide.
config_pwarn()
Imprime un message d'avertissement sur stderr, précédé de "Avertissement :".
config_perror()
Imprime un message d'erreur sur stderr, précédé de "Erreur :".

EXEMPLE

Pour enregistrer un gestionnaire pour une directive mySetting=value dans myapp.conf:

void
my_setting_handler(const char *token, char *line)
{
    char mySetting[100];
    char myValue[100];

    if (sscanf(line, "%99s %99s", mySetting, myValue) == 2) {
        /* Do something with mySetting and myValue */
    }
}

void
my_setting_releaser(void)
{
    /* Free any allocated resources */
}

void init_my_app(void) {
    /* Register a handler for mySetting in myapp.conf */
    register_config_handler("myapp", "mySetting", my_setting_handler,
                             my_setting_releaser, "mySetting VALUE");
}

L'appel de read_configs() analysera le fichier myapp.conf. Si une ligne comme mySetting myValue est trouvée, la fonction my_setting_handler sera appelée avec mySetting comme jeton et myValue comme ligne.

LECTURE DES FICHIERS DE CONFIGURATION

read_premib_configs()
read_configs()
Ces routines traitent les fichiers de configuration trouvés dans le chemin de recherche de configuration (voir ci-dessous). Pour chaque entrée, le gestionnaire enregistré pour ce jeton de configuration est appelé.

read_premib_configs() est exécuté avant la lecture des fichiers MIB et traite les jetons de configuration enregistrés à l'aide de register_prenetsnmp_mib_handler() (ou register_app_prenetsnmp_mib_handler()). Toutes les autres entrées sont ignorées.

read_configs() est exécuté après la lecture des fichiers MIB et traite les jetons de configuration enregistrés à l'aide de register_config_handler() (ou register_app_config_handler()). S'il rencontre un jeton de configuration pour lequel aucun gestionnaire n'a été enregistré (avant ou après les MIB), il affichera un message d'avertissement et continuera le traitement avec la ligne suivante du fichier de configuration.

Chemin de recherche de configuration

Les fichiers de configuration à lire sont trouvés en recherchant dans une liste de répertoires de configuration des fichiers nommés de manière appropriée. Dans chaque répertoire, la bibliothèque recherchera les fichiers nommés snmp.conf, snmp.local.conf, app.conf, app.local.conf,
(où app est le préfixe de fichier spécifique à l'application utilisé pour enregistrer les gestionnaires de configuration). Il n'est pas nécessaire que ces fichiers soient présents ou non dans chaque répertoire. Les fichiers manquants seront silencieusement ignorés.
L'idée derrière les deux suffixes différents est que le premier fichier peut être partagé (via rdist ou un montage NFS) sur un grand nombre de machines et le second fichier peut être utilisé pour configurer les paramètres locaux pour une machine particulière.

La liste par défaut des répertoires à rechercher est /etc/snmp, suivi de /usr/share/snmp, suivi de /usr/lib/snmp, suivi de $HOME/.snmp. Cette liste peut être modifiée en définissant la variable d'environnement SNMPCONFPATH sur une liste de répertoires (séparés par des deux-points) à rechercher.

init_snmp()

Le mode de fonctionnement normal consisterait à enregistrer les gestionnaires de configuration spécifiques à l'application, puis à appeler init_snmp(). Cela appellerait les routines listées ci-dessus pour enregistrer les gestionnaires de configuration internes de la bibliothèque, traiter tous les jetons de configuration enregistrés avec register_prenetsnmp_mib_handler(), lire les fichiers MIB textuels à l'aide de init_mib(), et enfin analyser les jetons de fichier de configuration enregistrés avec register_config_handler().

Si la fonction init_snmp() est utilisée, aucune de ces fonctions ne doit être appelée explicitement par l'application.

CHAÎNES D'AIDE ET ERREURS

Le paramètre usageLine passé à register_config_handler() et aux appels similaires, est utilisé pour afficher des informations d'aide lorsque la fonction read_config_print_usage() est appelée. Cette fonction est utilisée par toutes les applications lorsque le drapeau -H est passé sur la ligne de commande. Elle affiche un résumé de toutes les lignes de fichier de configuration et des fichiers associés que le système de configuration comprend. Le paramètre usageLine doit être une liste d'arguments attendus après le jeton, et non une description longue (qui devrait plutôt aller dans une page de manuel). Le préfixe lead sera ajouté à chaque ligne que la fonction imprime sur stderr, où elle affiche sa sortie.

La fonction init_snmp() doit être appelée avant la fonction read_config_print_usage(), afin que la bibliothèque puisse enregistrer ses directives de fichier de configuration également pour que la fonction read_config_print_usage() les affiche.

Fonctions de gestion des erreurs

Les deux fonctions config_pwarn() et config_perror() prennent toutes deux une chaîne d'erreur comme argument et l'impriment sur stderr avec le fichier et le numéro de ligne qui ont causé l'erreur. Un appel à la deuxième fonction forcera également read_configs() à retourner éventuellement avec un code d'erreur indiquant à sa fonction appelante qu'elle doit abandonner l'opération de l'application.

VARIABLES D'ENVIRONNEMENT

SNMPCONFPATH
Une liste séparée par des deux-points des répertoires à rechercher pour les fichiers de configuration. Par défaut :
/etc/snmp:/usr/share/snmp:/usr/lib/snmp:$HOME/.snmp
