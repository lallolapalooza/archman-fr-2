DESCRIPTION

Unbound is an implementation of a DNS resolver, that does caching and DNSSEC validation. This is the library API, for using the -lunbound library. The server daemon is described in unbound(8). The library works independent from a running unbound server, and can be used to convert hostnames to ip addresses, and back, and obtain other information from the DNS. The library performs public-key validation of results with DNSSEC.

The library uses a variable of type struct ub_ctx to keep context between calls. The user must maintain it, creating it with ub_ctx_create and deleting it with ub_ctx_delete. It can be created and deleted at any time. Creating it anew removes any previous configuration (such as trusted keys) and clears any cached results.

The functions are thread-safe, and a context can be used in a threaded (as well as in a non-threaded) environment. Also resolution (and validation) can be performed blocking and non-blocking (also called asynchronous). The async method returns from the call immediately, so that processing can go on, while the results become available later.

The functions are discussed in turn below.

FUNCTIONS

ub_ctx_create
Create a new context, initialised with defaults. The information from /etc/resolv.conf and /etc/hosts is not utilised by default. Use ub_ctx_resolvconf and ub_ctx_hosts to read them. Before you call this, use the openssl functions CRYPTO_set_id_callback and CRYPTO_set_locking_callback to set up asynchronous operation if you use lib openssl (the application calls these functions once for initialisation). Openssl 1.0.0 or later uses the CRYPTO_THREADID_set_callback function.
ub_ctx_delete
Delete validation context and free associated resources. Outstanding async queries are killed and callbacks are not called for them.
ub_ctx_set_option
A power-user interface that lets you specify one of the options from the config file format, see unbound.conf(5). Not all options are relevant. For some specific options, such as adding trust anchors, special routines exist. Pass the option name with the trailing ':'.
ub_ctx_get_option
A power-user interface that gets an option value. Some options cannot be gotten, and others return a newline separated list. Pass the option name without trailing ':'. The returned value must be free(2)d by the caller.
ub_ctx_config
A power-user interface that lets you specify an unbound config file, see unbound.conf(5), which is read for configuration. Not all options are relevant. For some specific options, such as adding trust anchors, special routines exist. This function is thread-safe only if a single instance of ub_ctx* exists in the application. If several instances exist the application has to ensure that ub_ctx_config is not called in parallel by the different instances.
ub_ctx_set_fwd
Set machine to forward DNS queries to, the caching resolver to use. IP4 or IP6 address. Forwards all DNS requests to that machine, which is expected to run a recursive resolver. If the proxy is not DNSSEC capable, validation may fail. Can be called several times, in that case the addresses are used as backup servers. At this time it is only possible to set configuration before the first resolve is done.
ub_ctx_set_stub
Set a stub zone, authoritative dns servers to use for a particular zone. IP4 or IP6 address. If the address is NULL the stub entry is removed. Set isprime true if you configure root hints with it. Otherwise similar to the stub zone item from unbound's config file. Can be called several times, for different zones, or to add multiple addresses for a particular zone. At this time it is only possible to set configuration before the first resolve is done.
ub_ctx_set_tls
Enable DNS over TLS (DoT) for machines set with ub_ctx_set_fwd. At this time it is only possible to set configuration before the first resolve is done.
ub_ctx_resolvconf
By default the root servers are queried and full resolver mode is used, but you can use this call to read the list of nameservers to use from the filename given. Usually "/etc/resolv.conf". Uses those nameservers as caching proxies. If they do not support DNSSEC, validation may fail. Only nameservers are picked up, the searchdomain, ndots and other settings from resolv.conf(5) are ignored. If fname NULL is passed, "/etc/resolv.conf" is used (if on Windows, the system-wide configured nameserver is picked instead). At this time it is only possible to set configuration before the first resolve is done.
ub_ctx_hosts
Read list of hosts from the filename given. Usually "/etc/hosts". When queried for, these addresses are not marked DNSSEC secure. If fname NULL is passed, "/etc/hosts" is used (if on Windows, etc/hosts from WINDIR is picked instead). At this time it is only possible to set configuration before the first resolve is done.

DESCRIPTION

Unbound est une implémentation d'un résolveur DNS, qui effectue la mise en cache et la validation DNSSEC. Ceci est l'API de bibliothèque, pour utiliser la bibliothèque -lunbound. Le démon serveur est décrit dans unbound(8). La bibliothèque fonctionne indépendamment d'un serveur unbound en cours d'exécution et peut être utilisée pour convertir des noms d'hôte en adresses IP, et vice-versa, et obtenir d'autres informations du DNS. La bibliothèque effectue la validation par clé publique des résultats avec DNSSEC.

La bibliothèque utilise une variable de type struct ub_ctx pour conserver le contexte entre les appels. L'utilisateur doit la gérer, en la créant avec ub_ctx_create et en la supprimant avec ub_ctx_delete. Elle peut être créée et supprimée à tout moment. La recréer supprime toute configuration précédente (telles que les clés de confiance) et efface tous les résultats mis en cache.

Les fonctions sont thread-safe, et un contexte peut être utilisé dans un environnement threadé (ainsi que dans un environnement non threadé). La résolution (et la validation) peut également être effectuée de manière bloquante et non bloquante (également appelée asynchrone). La méthode asynchrone retourne immédiatement de l'appel, de sorte que le traitement puisse continuer, tandis que les résultats deviennent disponibles plus tard.

Les fonctions sont discutées tour à tour ci-dessous.

FONCTIONS

ub_ctx_create
Crée un nouveau contexte, initialisé avec des valeurs par défaut. Les informations de /etc/resolv.conf et /etc/hosts ne sont pas utilisées par défaut. Utilisez ub_ctx_resolvconf et ub_ctx_hosts pour les lire. Avant d'appeler cette fonction, utilisez les fonctions openssl CRYPTO_set_id_callback et CRYPTO_set_locking_callback pour configurer le fonctionnement asynchrone si vous utilisez la bibliothèque openssl (l'application appelle ces fonctions une fois pour l'initialisation). Openssl 1.0.0 ou version ultérieure utilise la fonction CRYPTO_THREADID_set_callback.
ub_ctx_delete
Supprime le contexte de validation et libère les ressources associées. Les requêtes asynchrones en cours sont annulées et les rappels ne sont pas appelés pour elles.
ub_ctx_set_option
Une interface pour utilisateurs avancés qui vous permet de spécifier l'une des options du format de fichier de configuration, voir unbound.conf(5). Toutes les options ne sont pas pertinentes. Pour certaines options spécifiques, telles que l'ajout d'ancres de confiance, des routines spéciales existent. Transmettez le nom de l'option avec le ':' final.
ub_ctx_get_option
Une interface pour utilisateurs avancés qui récupère une valeur d'option. Certaines options ne peuvent pas être récupérées, et d'autres retournent une liste séparée par des sauts de ligne. Transmettez le nom de l'option sans le ':' final. La valeur retournée doit être libérée (free(2)) par l'appelant.
ub_ctx_config
Une interface pour utilisateurs avancés qui vous permet de spécifier un fichier de configuration unbound, voir unbound.conf(5), qui est lu pour la configuration. Toutes les options ne sont pas pertinentes. Pour certaines options spécifiques, telles que l'ajout d'ancres de confiance, des routines spéciales existent. Cette fonction n'est thread-safe que si une seule instance de ub_ctx* existe dans l'application. Si plusieurs instances existent, l'application doit s'assurer que ub_ctx_config n'est pas appelée en parallèle par les différentes instances.
ub_ctx_set_fwd
Définit la machine vers laquelle les requêtes DNS seront transférées, le résolveur de cache à utiliser. Adresse IP4 ou IP6. Transfère toutes les requêtes DNS vers cette machine, qui est censée exécuter un résolveur récursif. Si le proxy n'est pas compatible DNSSEC, la validation peut échouer. Peut être appelé plusieurs fois, dans ce cas les adresses sont utilisées comme serveurs de secours. À l'heure actuelle, il n'est possible de définir la configuration qu'avant que la première résolution ne soit effectuée.
ub_ctx_set_stub
Définit une zone stub, des serveurs DNS faisant autorité à utiliser pour une zone particulière. Adresse IP4 ou IP6. Si l'adresse est NULL, l'entrée stub est supprimée. Définissez isprime à vrai si vous configurez des indications racine avec. Sinon, c'est similaire à l'élément de zone stub du fichier de configuration d'unbound. Peut être appelé plusieurs fois, pour différentes zones, ou pour ajouter plusieurs adresses pour une zone particulière. À l'heure actuelle, il n'est possible de définir la configuration qu'avant que la première résolution ne soit effectuée.
ub_ctx_set_tls
Active le DNS sur TLS (DoT) pour les machines définies avec ub_ctx_set_fwd. À l'heure actuelle, il n'est possible de définir la configuration qu'avant que la première résolution ne soit effectuée.
ub_ctx_resolvconf
Par défaut, les serveurs racines sont interrogés et le mode résolveur complet est utilisé, mais vous pouvez utiliser cet appel pour lire la liste des serveurs de noms à utiliser depuis le fichier donné. Habituellement "/etc/resolv.conf". Utilise ces serveurs de noms comme proxys de cache. S'ils ne prennent pas en charge DNSSEC, la validation peut échouer. Seuls les serveurs de noms sont récupérés, le domaine de recherche, ndots et d'autres paramètres de resolv.conf(5) sont ignorés. Si fname est NULL, "/etc/resolv.conf" est utilisé (sous Windows, le serveur de noms configuré globalement est choisi à la place). À l'heure actuelle, il n'est possible de définir la configuration qu'avant que la première résolution ne soit effectuée.
ub_ctx_hosts
Lit la liste des hôtes à partir du nom de fichier donné. Habituellement "/etc/hosts". Lors de l'interrogation, ces adresses ne sont pas marquées comme sécurisées par DNSSEC. Si fname est NULL, "/etc/hosts" est utilisé (sous Windows, etc/hosts de WINDIR est choisi à la place). À l'heure actuelle, il n'est possible de définir la configuration qu'avant la première résolution.

ub_ctx_add_ta
Ajoute une ancre de confiance au contexte donné. À ce stade, il est seulement possible d'ajouter des clés de confiance avant que la première résolution ne soit effectuée. Le format est une chaîne de caractères, similaire au format de fichier de zone, [nom de domaine] [type] [contenu rdata]. Les enregistrements DS et DNSKEY sont acceptés.
ub_ctx_add_ta_autr
Ajoute un fichier avec une ancre de confiance suivie automatiquement au contexte donné. Passez le nom d'un fichier avec l'ancre de confiance gérée. Vous pouvez créer ce fichier avec unbound-anchor(8) pour l'ancre racine. Vous pouvez également le créer avec un fichier initial contenant une seule ligne avec un enregistrement DNSKEY ou DS. Si le fichier est accessible en écriture, il est mis à jour lorsque l'ancre de confiance change. À ce stade, il est seulement possible d'ajouter des clés de confiance avant que la première résolution ne soit effectuée.
ub_ctx_add_ta_file
Ajoute des ancres de confiance au contexte donné. Passez le nom d'un fichier contenant des enregistrements DS et DNSKEY au format de fichier de zone. À ce stade, il est seulement possible d'ajouter des clés de confiance avant que la première résolution ne soit effectuée.
ub_ctx_trustedkeys
Ajoute des ancres de confiance au contexte donné. Passez le nom d'un fichier de configuration de style bind contenant trusted-keys{}. À ce stade, il est seulement possible d'ajouter des clés de confiance avant que la première résolution ne soit effectuée.
ub_ctx_debugout
Définit la sortie des journaux de débogage et d'erreur vers le flux donné. Passez NULL pour désactiver la sortie. Par défaut, c'est stderr. Les noms de fichiers ou l'utilisation de syslog peuvent être activés à l'aide des options de configuration, cette routine est pour utiliser votre propre flux.
ub_ctx_debuglevel
Définit la verbosité du débogage pour le contexte. La sortie est dirigée vers stderr. Un niveau de débogage plus élevé donne plus de sortie.
ub_ctx_async
Définit un comportement de contexte pour une action asynchrone. Si défini à true, active le multithreading et un appel à ub_resolve_async crée un thread pour gérer le travail en arrière-plan. Si défini à false, un processus est bifurqué pour gérer le travail en arrière-plan. Les changements apportés à ce paramètre après que des appels à ub_resolve_async aient été effectués n'ont aucun effet (supprimez et recréez le contexte pour changer).
ub_poll
Interroge un contexte pour voir s'il a de nouveaux résultats. Ne pas interroger dans une boucle, mais plutôt extraire le fd ci-dessous pour interroger sa disponibilité, puis vérifier, ou attendre en utilisant la routine d'attente. Retourne 0 s'il n'y a rien à lire, ou une valeur non nulle si un résultat est disponible. Si non nulle, appelez ub_process pour effectuer les rappels.
ub_wait
Attend qu'un contexte termine avec des résultats. Appelle ub_process après l'attente pour vous. Après l'attente, il n'y a plus de requêtes asynchrones en cours.
ub_fd
Obtient le descripteur de fichier. Attendez qu'il devienne lisible, à ce moment-là les réponses sont retournées par le résolveur de validation asynchrone. Ensuite, appelez ub_process pour continuer le traitement.
ub_process
Appelez cette routine pour continuer le traitement des résultats du résolveur de validation (lorsque le fd devient lisible). Effectuera les rappels nécessaires.
ub_resolve
Effectue la résolution et la validation du nom cible. Le nom est un nom de domaine dans une chaîne de caractères texte terminée par zéro. Les types rrtype et rrclass sont les codes de type et de classe DNS. La structure de résultat est nouvellement allouée avec les données résultantes.
ub_resolve_async
Effectue la résolution et la validation asynchrones du nom cible. Les arguments signifient la même chose que pour ub_resolve, sauf qu'aucune donnée n'est retournée immédiatement, au lieu de cela, un rappel est appelé plus tard. Le rappel reçoit une copie du pointeur mydata, que vous pouvez utiliser pour passer des informations au rappel. Le type de rappel est un pointeur de fonction vers une fonction déclarée comme suit :
void my_callback_function(void* my_arg, int err,
                struct ub_result* result);

L' async_id est retourné afin que vous puissiez (à votre discrétion) décider de le suivre et d'annuler la requête si nécessaire. Si vous passez un pointeur NULL, l' async_id n'est pas retourné.

ub_cancel
Annule une requête asynchrone en cours. Cela peut retourner une erreur si la requête n'existe pas, ou si la requête est déjà en cours de livraison, dans ce cas, vous pourriez encore recevoir un rappel pour la requête.
ub_resolve_free
Libère le contenu de la structure ub_result après utilisation.
ub_strerror
Convertit la valeur d'erreur d'une des fonctions de la bibliothèque unbound en une chaîne de caractères lisible par l'homme.
ub_ctx_print_local_zones
Affiche les informations d'autorité locale dans la sortie de débogage.
ub_ctx_zone_add
Ajoute une nouvelle zone aux informations d'autorité locale, comme l'instruction unbound.conf(5) local-zone.
ub_ctx_zone_remove
Supprime une zone des informations d'autorité locale.
ub_ctx_data_add
Ajoute des données d'enregistrement de ressources aux informations d'autorité locale, comme l'instruction unbound.conf(5) local-data.
ub_ctx_data_remove
Supprime les données d'autorité locale du nom donné.

STRUCTURE DE DONNÉES DE RÉSULTAT

Le résultat de la résolution et de la validation DNS est retourné sous forme de struct ub_result. La structure de résultat contient les entrées suivantes :

struct ub_result {
     char* qname;         /* chaîne de caractères, question originale */
     int qtype;           /* code de type demandé */
     int qclass;          /* code de classe demandé */
     char** data;         /* tableau d'éléments rdata, terminé par NULL */
     int* len;            /* tableau avec les longueurs des éléments rdata */
     char* canonname;     /* nom canonique du résultat */
     int rcode;           /* code d'erreur supplémentaire en cas d'absence de données */
     void* answer_packet; /* paquet de réponse complet au format réseau */
     int answer_len;      /* longueur du paquet en octets */
     int havedata;        /* vrai s'il y a des données */
     int nxdomain;        /* vrai s'il n'y a pas de données car le nom n'existe pas */
     int secure;          /* vrai si le résultat est sécurisé */
     int bogus;           /* vrai si un échec de sécurité s'est produit */
     char* why_bogus;     /* chaîne avec l'erreur si bogus */
     int was_ratelimited; /* vrai si la requête a été limitée par débit (SERVFAIL) par unbound */
     int ttl;             /* nombre de secondes pendant lesquelles le résultat est valide */
};

Si secure et bogus sont tous deux faux, la sécurité n'a pas été activée pour le domaine de la requête. Sinon, ils ne sont pas tous deux vrais, l'un d'eux est vrai.

VALEURS DE RETOUR

De nombreuses routines retournent un code d'erreur. La valeur 0 (zéro) indique qu'aucune erreur ne s'est produite. D'autres valeurs peuvent être passées à ub_strerror pour obtenir une chaîne d'erreur lisible. ub_strerror retourne une chaîne terminée par zéro. ub_ctx_create retourne NULL en cas d'erreur (un échec malloc). ub_poll retourne true si des informations peuvent être disponibles, false sinon. ub_fd retourne un descripteur de fichier ou -1 en cas d'erreur. ub_ctx_config et ub_ctx_resolvconf tentent de laisser errno informatif en cas de retour de fonction avec échec de lecture de fichier.
