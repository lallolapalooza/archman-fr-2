NAME

usbguard-rules.conf - Fichier de règles USBGuard.

DESCRIPTION

Le fichier usbguard-rules.conf est chargé par le démon USBGuard après l'analyse du fichier de configuration principal, usbguard-daemon.conf(5). Le démon s'attend à ce que le fichier contienne des règles écrites dans un langage qui est décrit dans la section Langage des règles ci-dessous.

LANGAGE DES RÈGLES

Le démon USBGuard décide quel périphérique USB autoriser en fonction d'une politique définie par un ensemble de règles. Lorsqu'un périphérique USB est inséré dans le système, le démon parcourt les règles existantes séquentiellement. Si une règle correspondante est trouvée, elle autorise (allow), bloque (block) ou rejette (reject) le périphérique, en fonction de la cible de la règle. Si aucune règle correspondante n'est trouvée, la décision est basée sur une cible par défaut implicite. Celle-ci consiste à bloquer le périphérique jusqu'à ce qu'une décision soit prise par l'utilisateur. La grammaire du langage des règles, exprimée dans une syntaxe de type BNF, est la suivante :

    rule ::= target attributes.
    target ::= "allow" | "block" | "reject".
    attributes ::= attributes | attribute.
    attributes ::= .

Les attributs de règle spécifient quels périphériques faire correspondre ou quelles conditions doivent être remplies pour que la règle soit applicable. Voir la section Spécification des périphériques pour la liste des attributs disponibles et les Conditions pour la liste des conditions de règle prises en charge.

Cibles

La cible d'une règle spécifie si le périphérique sera autorisé ou non. Trois types de cibles sont reconnus :

•allow - Autorise le périphérique. Le périphérique et ses interfaces pourront communiquer avec le système.
•block - Bloque le périphérique. Le périphérique restera dans un état bloqué jusqu'à ce qu'il soit autorisé.
•reject - Bloque et retire le périphérique du système. Le périphérique devra être réinséré pour redevenir visible par le système.

Spécification des périphériques

À l'exception de la cible, tous les autres champs d'une règle sont optionnels. Une règle où seule la cible est spécifiée correspondra à n'importe quel périphérique. Cela permet à l'administrateur de politique d'écrire une cible par défaut explicite. Si aucune règle de la politique n'est applicable au périphérique, une cible implicite configurée dans usbguard-daemon.conf(5) sera utilisée. Cependant, si l'on souhaite restreindre l'applicabilité d'une règle à un ensemble de périphériques ou à un seul, il est possible de le faire avec des attributs de périphérique et des conditions de règle.

Attributs de périphérique

Les attributs de périphérique sont des valeurs spécifiques lues à partir du périphérique USB après son insertion dans le système. Les attributs disponibles sont définis ci-dessous. Certains attributs sont dérivés et d'autres sont basés sur des attributs lus directement depuis le périphérique. Tous les attributs supportent deux formes :

•à valeur unique avec la syntaxe : 
    nom valeur
•à valeurs multiples avec la syntaxe : 
    nom [opérateur] { valeur1 valeur2 ... }

où l' opérateur optionnel est l'un des suivants :

all-of

L'ensemble des attributs du périphérique doit contenir toutes les valeurs spécifiées pour que la règle corresponde.

one-of

L'ensemble des attributs du périphérique doit contenir au moins une des valeurs spécifiées pour que la règle corresponde.

none-of

L'ensemble des attributs du périphérique ne doit contenir aucune des valeurs spécifiées pour que la règle corresponde.

equals

L'ensemble des attributs du périphérique doit contenir exactement le même ensemble de valeurs pour que la règle corresponde.

equals-ordered

L'ensemble des attributs du périphérique doit contenir exactement le même ensemble de valeurs dans le même ordre pour que la règle corresponde.

match-all

L'ensemble des attributs du périphérique doit être un sous-ensemble des valeurs spécifiées pour que la règle corresponde.

Si l'opérateur n'est pas spécifié, il est défini sur equals.

Liste des attributs :

id usb-device-id

Correspond à un identifiant de périphérique USB.

id [opérateur] { usb-device-id ... }

Correspond à un ensemble d'identifiants de périphériques USB.

hash "valeur"

Correspond à un hachage calculé à partir des valeurs d'attributs du périphérique et des données du descripteur USB. Le hachage est calculé pour chaque périphérique par USBGuard.

hash [opérateur] { "valeur" ... }

Correspond à un ensemble de hachages de périphériques.

parent-hash "valeur"

Correspond à un hachage du périphérique parent.

parent-hash [opérateur] { "valeur" ... }

Correspond à un ensemble de hachages de périphériques parents.

name "nom-périphérique"

Correspond à l'attribut de nom de périphérique USB.

name [opérateur] { "nom-périphérique" ... }

Correspond à un ensemble de noms de périphériques USB.

serial "numéro-de-série"

Correspond à l'attribut iSerial du périphérique USB.

serial [opérateur] { "numéro-de-série" ... }

Correspond à un ensemble d'attributs iSerial de périphériques USB.

via-port "id-port"

Correspond au port USB par lequel le périphérique est connecté. Notez que certains systèmes ont une numérotation de port instable. Le port peut changer après le redémarrage du système ou lors du rechargement de certains modules du noyau. Utilisez l'attribut parent-hash si vous voulez vous assurer qu'un périphérique est connecté via un périphérique parent spécifique.

via-port [opérateur] { "id-port" ... }

Correspond à un ensemble de ports USB.

with-interface type-interface

Correspond à un type d'interface que le périphérique USB fournit.

with-interface [opérateur] { type-interface ... }

Correspond à un ensemble de types d'interface par rapport à l'ensemble des interfaces que le périphérique USB fournit.

with-connect-type "type-connexion"

Correspond à l'attribut de périphérique port/connect_type USB.

with-connect-type [opérateur] { "type-connexion" ... }

Correspond à un ensemble d'attributs de périphérique port/connect_type USB.

label "étiquette"

Associe une chaîne de caractères arbitraire à une règle. L'étiquette est utile pour stocker des informations contextuelles sur une règle ou pour filtrer les règles par étiquette. Cet attribut n'est pas utilisé lors de la vérification de l'applicabilité d'une règle à un périphérique.

L' usb-device-id est une paire délimitée par des deux-points sous la forme vendor_id:product_id. Tous les périphériques USB ont cet identifiant attribué par le fabricant et il devrait identifier de manière unique un type de produit USB. Le vendor_id et le product_id sont des nombres de 16 bits représentés en base hexadécimale. Il est possible d'utiliser un caractère astérisque pour faire correspondre n'importe quel identifiant de périphérique *:* ou n'importe quel identifiant de produit d'un fournisseur spécifique, par exemple 1234:*.

La valeur de l' id-port est une identification de port USB spécifique à la plateforme. Sur Linux, elle est sous la forme "usbN" dans le cas d'un contrôleur USB (plus précisément un "root hub") ou "bus-port[.port[.port ...]]" (par exemple 1-2, 1-2.1, ...) dans le cas d'un périphérique USB.

Le type-interface représente une interface USB et doit être formaté en trois nombres de 8 bits en base hexadécimale délimités par un deux-points, c'est-à-dire cc:ss:pp. Les nombres représentent la classe (cc), la sous-classe (ss) et le protocole (pp) de l'interface tels qu'assignés par l'USB-IF. Voir la liste des classes, sous-classes et protocoles assignés pour plus de détails. Au lieu du numéro de sous-classe et de protocole, vous pouvez écrire un caractère astérisque (*) pour correspondre à toutes les sous-classes ou tous les protocoles. La correspondance d'une classe spécifique et d'un protocole spécifique n'est pas autorisée, c'est-à-dire que si vous utilisez un astérisque comme numéro de sous-classe, vous devez également utiliser un astérisque pour le protocole.

NAME

usbguard-rules.conf — USBGuard rule syntax

DESCRIPTION

This manual page describes the syntax of the rules.conf file used by USBGuard.

A rule consists of an action and a target. The rule target is optional. If no rule target is specified, the rule applies to any device.

The action can be either allow, deny, or reject.

allow
Allows the device to be connected.
deny
Prevents the device from being connected. The device will be disconnected if it is already connected.
reject
Prevents the device from being connected. The device will be disconnected if it is already connected.

Rules are evaluated in the order they appear in the file. The first rule that matches the device will be applied. If no rule matches the device, the default policy (defined by the Policy option in usbguard-daemon.conf(5)) is applied.

A rule target consists of one or more conditions and an optional set operator. If no set operator is specified, the default is all-of.

A rule condition is a function call, which returns true or false. If the condition evaluates to true, the rule action is applied. Otherwise, the rule evaluation continues with the next rule. A rule conditions has the following syntax:

     if [!]condition
     if [operator] { [!]conditionA [!]conditionB ... }

Optionally, an exclamation mark (!) can be used to negate the result of a condition.

Interpretation of the set operator:

all-of

Evaluate to true if all of the specified conditions evaluated to true.

one-of

Evaluate to true if one of the specified conditions evaluated to true.

none-of

Evaluate to true if none of the specified conditions evaluated to true.

equals

Same as all-of.

equals-ordered

Same as all-of.

List of conditions:

localtime(time_range)

Evaluates to true if the local time is in the specified time range. time_range can be written either as HH:MM[:SS] or HH:MM[:SS]-HH:MM[:SS].

allowed-matches(query)

Evaluates to true if an allowed device matches the specified query. The query uses the rule syntax. Conditions in the query are not evaluated.

rule-applied

Evaluates to true if the rule currently being evaluated ever matched a device.

rule-applied(past_duration)

Evaluates to true if the rule currently being evaluated matched a device in the past duration of time specified by the parameter. past_duration can be written as HH:MM:SS, HH:MM, or SS.

rule-evaluated

Evaluates to true if the rule currently being evaluated was ever evaluated before.

rule-evaluated(past_duration)

Evaluates to true if the rule currently being evaluated was evaluated in the pas duration of time specified by the parameter. past_duration can be written as HH:MM:SS, HH:MM, or SS.

random

Evaluates to true/false with a probability of p(true)=0.5.

random(p_true)

Evaluates to true with the specified probability p(true)=p_true.

true

Evaluates always to true.

false

Evaluates always to false.

Partial rule

Partial rule is a rule without a rule target. Partial rules may by used by some commands of usbguard CLI tool.

Comments

In order to easily understand the meaning of each rule, comments can be used. Everything after the "#" character is ignored by the rule parser.

INITIAL POLICY

Using the usbguard CLI tool and its generate-policy subcommand, you can generate an initial policy for your system instead of writing one from scratch. The tool generates an allow policy for all devices connected to the system at the time of execution. It has several options to tweak the resulting policy, see usbguard(1) for further details.

The policy will be printed out on the standard output. It’s a good idea to review the generated rules before using them on a system. The typical workflow for generating an initial policy could look like this:

    $ sudo usbguard generate-policy > rules.conf
    $ vi rules.conf
    (review/modify the rule set)
    $ sudo install -m 0600 -o root -g root rules.conf /etc/usbguard/rules.conf
    $ sudo systemctl restart usbguard

EXAMPLE POLICIES

The following examples show what to put into the rules.conf file in order to implement the given policy.

1.Allow USB mass storage devices (USB flash disks) and block everything else

This policy will block any device that isn’t just a mass storage device. Devices with a hidden keyboard interface in a USB flash disk will be blocked. Only devices with a single mass storage interface will be allowed to interact with the operating system. The policy consists of a single rule:

    allow with-interface equals { 08:*:* }

The blocking is implicit in this case because we didn’t write a block rule. Implicit blocking is useful to desktop users. A desktop applet listening to USBGuard events can ask the user for a decision if an implicit target was applied.

2.Allow a specific Yubikey device to be connected via a specific port (and reject everything else on that port) 
    allow 1050:0011 name "Yubico Yubikey II" serial "0001234567" via-port "1-2" hash "044b5e168d40ee0245478416caf3d998"
    reject via-port "1-2"

We could use just the hash to match the device. However, using the name and serial attributes provide an useful hint for later inspection of the policy. On the other hand, the hash is the most specific value we can use to identify a device. It’s the best attribute to use if you want a rule to match just one device.

3.Reject devices with suspicious combination of interfaces

A USB flash disk which implements a keyboard or a network interface is very suspicious. The following set of rules forms a policy that allows USB flash disks and explicitly rejects devices with an additional and suspicious (as defined before) interface.

    allow with-interface equals { 08:*:* }
    reject with-interface all-of { 08:*:* 03:00:* }
    reject with-interface all-of { 08:*:* 03:01:* }
    reject with-interface all-of { 08:*:* e0:*:* }
    reject with-interface all-of { 08:*:* 02:*:* }

The policy rejects all USB flash disk devices with an interface from the HID/Keyboard, Communications and Wireless classes. Note that default allow is the wrong approach and you shouldn’t just reject a set of devices and allow the rest. The policy above assumes that blocking is the default. Rejecting a set of devices considered as "bad" is a good approach how to limit the exposure of the OS to such devices as much as possible.

4.Allow a keyboard-only USB device only if there isn’t already a USB device with a keyboard interface allowed 
    allow with-interface one-of { 03:00:01 03:01:01 } if !allowed-matches(with-interface one-of { 03:00:01 03:01:01 })
5.Play "Russian roulette" with USB devices 
    allow if random(0.1666)
    reject
