NOM

umoci repack - Reconditionne un bundle OCI en une étiquette d'image

SYNTAXE

umoci repack --image=image[:étiquette] [--no-history] [--history.comment=commentaire] [--history.created_by=créé_par] [--history.author=auteur] [--history-created=date] [--refresh-bundle] bundle

DESCRIPTION

Étant donné un bundle OCI modifié extrait avec umoci-unpack(1) (au chemin spécifié bundle), umoci-repack(1) calcule la différence du système de fichiers pour le rootfs du bundle OCI. La différence est utilisée pour générer une couche de différence, qui est ensuite ajoutée au manifeste de l'image d'origine (qui a été utilisé comme argument pour umoci-unpack(1)) et étiquetée comme une nouvelle étiquette d'image. Entre un appel à umoci-unpack(1) et umoci-repack(1), les utilisateurs NE DOIVENT PAS modifier l'image OCI d'une quelconque manière (en particulier, vous NE DEVEZ PAS utiliser umoci-gc(1)).

Tous les paramètres --uid-map et --gid-map sont implicites à partir des valeurs sauvegardées spécifiées dans umoci-unpack(1), ils ne sont donc pas disponibles pour umoci-repack(1).

Si --no-history n'a pas été spécifié, une entrée d'historique est ajoutée à l'image OCI étiquetée pour ce changement (avec les différents indicateurs --history. contrôlant les valeurs utilisées). Pour visualiser l'historique, voir umoci-stat(1).

Notez que l'étiquette d'image d'origine (utilisée avec umoci-unpack(1)) ne sera PAS modifiée, sauf si la cible de umoci-repack(1) est l'étiquette d'image d'origine.

OPTIONS

Les options globales sont définies dans umoci(1).

--image=image[:étiquette]
L'étiquette de destination pour l'image OCI reconditionnée. image doit être un chemin
vers une image OCI valide (et la même image utilisée dans umoci-unpack(1) pour créer
le bundle) et étiquette doit être un nom d'étiquette valide. Si une autre étiquette porte déjà le
même nom que étiquette, elle sera écrasée. Si étiquette n'est pas fournie, elle
par défaut à "latest".

--no-history
Aucune entrée d'historique n'est ajoutée pour cette opération. Ce n'est pas
recommandé pour l'utilisation avec umoci-repack(1), car cela a pour conséquence que l'historique
n'inclut pas toutes les couches de l'image -- et causera ainsi de la confusion avec les outils
qui consultent l'historique de l'image.

--history.comment=commentaire
Commentaire pour l'entrée d'historique correspondant à cette modification de l'image.
Si non spécifié, umoci(1) générera une valeur dépendante de l'implémentation.

--history.created_by=créé_par
Entrée CreatedBy pour l'entrée d'historique correspondant à cette modification de
l'image. Si non spécifié, umoci(1) générera une valeur dépendante
de l'implémentation.

--history.author=auteur
Valeur de l'auteur pour l'entrée d'historique correspondant à cette modification de
l'image. Si non spécifiée, cette valeur sera la valeur de l'auteur de l'image après
toutes les modifications apportées par cet appel de umoci-config(1).

--history-created=date
Date de création pour l'entrée d'historique correspondant à ces modifications
de l'image. Il doit s'agir d'un horodatage au format ISO8601 (voir date(1)). Si
non spécifié, l'heure actuelle est utilisée.

--refresh-bundle
Indique s'il faut mettre à jour les métadonnées du bundle OCI (c'est-à-dire mtree et les
métadonnées umoci) après avoir reconditionné l'image. Si défini, le nouvel état
du bundle doit être équivalent au dépaquetage de la nouvelle étiquette d'image.

EXEMPLE

L'exemple suivant télécharge une image à partir d'un registre docker(1) en utilisant skopeo(1), la décompresse avec umoci-unpack(1), la modifie puis la reconditionne.

% skopeo copy docker://opensuse/amd64:42.2 oci:image:latest
# umoci unpack --image image bundle
# touch bundle/rootfs/a_new_file
# umoci repack --image image:new-42.2 bundle
