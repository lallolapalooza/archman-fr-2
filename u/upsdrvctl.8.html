NOM

upsdrvctl - Contrôleur de pilotes Network UPS Tools

SYNOPIS

upsdrvctl -h

upsdrvctl [OPTIONS] {start | stop | shutdown | status} [ups]

upsdrvctl [OPTIONS] {list | -l} [ups]

upsdrvctl [OPTIONS] -c COMMAND [ups]

DESCRIPTION

upsdrvctl fournit une interface uniforme pour contrôler vos pilotes d'onduleurs. Vous devriez utiliser la commande upsdrvctl au lieu d'appels directs aux pilotes dans la mesure du possible.

Lorsqu'il est utilisé correctement, upsdrvctl vous permet de maintenir des scripts de démarrage identiques sur plusieurs systèmes avec différentes configurations d'onduleurs.


Attention

Pour les systèmes d'exploitation dotés de cadres de gestion de services, tels que Solaris/illumos SMF ou Linux systemd, upsdrvsvcctl(8) peut être un meilleur choix.

En fait, les instances de service préparées par nut-driver-enumerator(8) en fonction du contenu de votre fichier ups.conf(5) et gérées automatiquement par le cadre respectif peuvent entrer en conflit avec l'exécution manuelle des pilotes. Dans ce cas, upsdrvctl émettra un avertissement dans les compilations NUT avec cette capacité (peut être supprimé en exportant la variable d'environnement NUT_QUIET_INIT_NDE_WARNING avec n'importe quelle valeur).

Il peut vous être demandé d'arrêter les unités de service (si utilisées) et d'exécuter les programmes pilotes directement plutôt que via upsdrvctl pour le dépannage, par exemple pour faciliter la collecte de journaux de débogage ou tester des constructions personnalisées de pilotes sans conflit avec une instance groupée en cours d'exécution normale.

OPTIONS

-h

Affiche le texte d'aide.

-r répertoire

Si un pilote est démarré, cette valeur l'amènera à chroot(2) dans répertoire. Cela peut être utile lors de la sécurisation des systèmes.

Cela peut être défini dans le fichier ups.conf(5) avec la directive chroot dans la section globale.

-t

Active le mode test. Cela active également le mode de débogage. Le mode test fait en sorte que upsdrvctl affiche les actions qu'il exécuterait sans les réaliser réellement. Utilisez-le pour tester votre configuration sans rien faire à vos pilotes d'onduleurs.

Cela peut être utile lors de la définition de la directive sdorder dans votre section ups.conf(5) pour l'appareil.

-u nomutilisateur

Si un pilote est démarré, cette valeur l'amènera à setuid(2) à l'identifiant utilisateur associé à nomutilisateur.

Si le pilote est démarré en tant que root sans spécifier cette valeur, il utilisera le nom d'utilisateur qui a été compilé dans le binaire. Par défaut, il s'agit de nobody (si non configuré autrement), ce qui est loin d'être idéal.

Cela peut être défini dans ups.conf(5) avec la directive user dans la section globale.

-D

Augmente le niveau de débogage. Utilisez-le plusieurs fois pour des détails supplémentaires.

Notez que cela n'empêche pas l'outil upsdrvctl de se terminer une fois son travail terminé (cependant, une option explicite -F le fait).

Notez également que cette option seule modifie la verbosité du débogage de l'outil, mais pas celle des pilotes qu'il lance. Voir l'option supplémentaire -d pour cela.

-d

Transmet le niveau de débogage sélectionné de upsdrvctl aux pilotes lancés.

Notez que par défaut pour les démons NUT, le débogage activé signifie s'exécuter en mode premier plan ; vous pouvez spécifier -B en plus pour éviter cela.

-F

Le pilote s'exécutera en premier plan (ne se détachera pas du processus upsdrvctl), quelles que soient les options de débogage. Il maintiendrait également l'outil lui-même au premier plan avec les démons pilotes fonctionnant comme ses enfants (dans le cas du démarrage d'un seul pilote, il ne se détacherait même pas).

Il n'attendra pas non plus que les pilotes terminent leur initialisation, donc upsdrvctl avertira de telles situations.

Spécifiez deux fois (-FF ou -F -F) pour enregistrer le fichier PID du pilote même dans ce mode (non enregistré par défaut lors du maintien au premier plan).

-B

Les pilotes s'exécuteront en arrière-plan, quelles que soient les options de débogage, telles que définies par les options -D et transmises par les options -d.

-l

Alias pour la commande list.

COMMANDES

upsdrvctl prend en charge trois commandes actives : start, stop et shutdown. Il prend également en charge la transmission de requêtes aux pilotes en cours d'exécution en utilisant la syntaxe -c COMMAND, similaire à celle de certains autres démons. Quelques commandes d'aide sont également disponibles : list et status.

Elles peuvent toutes prendre un argument optionnel qui est un nom d'onduleur provenant de ups.conf(5). Sans cet argument, elles opèrent sur chaque onduleur actuellement configuré.


Note

upsdrvctl ne peut pas gérer les appareils non répertoriés dans ups.conf (tels que les pilotes de test démarrés avec l'option -s TMP).

start

Démarre le ou les pilotes d'onduleur. En cas d'échec du démarrage dans le délai maxstartdelay, des tentatives supplémentaires peuvent être exécutées en utilisant les valeurs maxretry et retrydelay. Inversement, l'option globale nowait peut être utilisée, notamment pour accélérer le démarrage parallèle de nombreux pilotes.

Consultez ups.conf(5) pour ces options. Les valeurs par défaut intégrées sont : maxstartdelay=75 (sec), maxretry=1 (signifiant une tentative de démarrage), retrydelay=5 (sec).

stop

Arrête le ou les pilotes d'onduleur. Cela n'envoie pas de commandes à l'onduleur.

shutdown

Commande le ou les pilotes d'onduleur à exécuter leur séquence d'arrêt. Cela suppose que le pilote n'est plus en cours d'exécution et lance une nouvelle instance via drivername -k. Il est destiné à être utilisé comme dernière étape de l'arrêt du système, après que les systèmes de fichiers ne soient plus montés en rw. Les pilotes sont arrêtés selon leur valeur sdorder — voir ups.conf(5).

Attention

Cela coupera probablement l'alimentation de vos ordinateurs, alors ne jouez pas avec cette option. Utilisez-la uniquement lorsque vos systèmes sont préparés à perdre l'alimentation.


Note

Reportez-vous à ups.conf(5) pour utiliser le paramètre nowait. Il peut être remplacé par la variable d'environnement NUT_IGNORE_NOWAIT (par exemple, utilisée pour contourner certains problèmes avec systemd autrement).

list

Sans argument supplémentaire, rapporte tous les noms de configuration d'appareils actuellement connus à la sortie standard, un par ligne. Avec un argument, essaie également de rapporter ce nom, mais se termine avec un code d'erreur si ce nom n'est pas connu.

Note

L'outil se terminera avec une erreur si le fichier ups.conf n'est pas trouvé, n'est pas lisible, ou ne définit aucune section d'appareil (dont les noms sont rapportés ici et gérés dans d'autres commandes).


Note

Le nom de l'outil et la bannière de version NUT sont également imprimés sur la sortie standard avant tout autre traitement. Cela peut être supprimé par la variable d'environnement NUT_QUIET_INIT_BANNER (exportée par l'appelant et vide ou "true") :

:; NUT_QUIET_INIT_BANNER=true upsdrvctl list
dummy
UPS1
UPS2

status

Similaire à list, mais rapporte plus d'informations : le nom du pilote, le PID s'il est en cours d'exécution, et le résultat d'une sonde de signal pour vérifier qu'il répond. La suppression de la bannière NUT_QUIET_INIT_BANNER peut être utile pour l'analyse par script. S'il y a quelque chose à imprimer (au moins un appareil est connu), la première ligne du rapport de statut sera l'en-tête avec les noms des colonnes : 
:; NUT_QUIET_INIT_BANNER=true upsdrvctl status
UPSNAME              UPSDRV  RUNNING PF_PID  S_RESPONSIVE    S_PID   S_STATUS
dummy             dummy-ups  N/A     -3      NOT_RESPONSIVE  N/A
eco650           usbhid-ups  RUNNING 3559207 RESPONSIVE      3559207 "OL"
UPS2              dummy-ups  RUNNING 31455   RESPONSIVE      31455   "OL BOOST"

Les valeurs sont séparées par des TAB, mais UPSNAME et UPSDRV peuvent être remplis d'espaces à droite et à gauche respectivement. Toutes les valeurs de chaîne complexes seraient entre guillemets doubles.

CHAMPS SIGNALÉS

Champs signalés (PF_* = selon le fichier PID, s'il y en a ; S_* = via le protocole socket) :

UPSNAME

nom de configuration de la section driver

UPSDRV

nom du programme driver selon ups.conf

RUNNING

RUNNING si PF_PID ou S_PID est valide, STOPPED si au moins une valeur PID a été analysée mais aucune n'a été trouvée en cours d'exécution avec un nom de programme correct ; N/A si aucun fichier PID/réponse socket ou échec de l'analyse. En premier lieu, le fichier PID est consulté, mais il peut être absent soit en raison des paramètres en ligne de commande des daemons, soit en raison de la plateforme (WIN32). Si aucune valeur PID n'a été trouvée et confirmée de cette manière, nous revenons à la vérification du PID signalé via le protocole (si disponible et différent).

PF_PID

PID du driver selon le fichier PID (s'il y en a), ou certaines valeurs négatives en cas d'erreur (telles que définies dans common.c) y compris un fichier PID absent, un contenu invalide, ou une plateforme non prise en charge pour ce mécanisme (par ex. WIN32)

S_RESPONSIVE

RESPONSIVE si PING/PONG lors de la configuration de la session de protocole socket a réussi ; NOT_RESPONSIVE sinon

S_PID

PID du driver selon la requête active GETPID, ou N/A si la requête a échoué

S_STATUS

Valeur entre guillemets de la variable ups.status

Ce mode ne découvre pas les drivers qui ne sont pas dans ups.conf (par ex. lancés manuellement pour des expériences avec de nombreuses options CLI -x).

-c commande

Envoyer la commande au processus d'arrière-plan sous forme de signal. Les commandes valides sont :

dump

demander aux drivers de déverser l'état actuellement connu sur leur sortie standard (si elle est attachée quelque part)

reload

relire les fichiers de configuration, en ignorant les paramètres modifiés qui ne peuvent pas être appliqués « à la volée »

reload-or-error

relire les fichiers de configuration, en ignorant mais en comptant les valeurs modifiées qui nécessitent un redémarrage du driver (ne peuvent pas être modifiées à la volée), et renvoyer un code succès/échec basé sur ce compte, afin que l'appelant puisse décider du sort de l'instance de driver actuellement en cours d'exécution

reload-or-exit

relire les fichiers de configuration, en quittant l'ancien processus driver s'il rencontre des paramètres modifiés qui ne peuvent pas être appliqués « à la volée » (afin qu'un appelant comme systemd puisse lancer une autre copie du driver)

exit

demander à l'instance de driver actuellement en cours d'exécution de simplement quitter (afin qu'un appelant externe comme la nouvelle instance de driver, ou les frameworks systemd ou SMF en démarrent une autre copie)

Si upsdrvctl a été lancé pour rester en mémoire et gérer les processus drivers NUT, il peut recevoir les signaux pris en charge et les transmettre à ces drivers.

VARIABLES D'ENVIRONNEMENT

NUT_DEBUG_LEVEL définit la verbosité de débogage par défaut si aucun argument -D n'a été fourni en ligne de commande, mais ne demande pas au démon de s'exécuter en mode premier plan.

NUT_CONFPATH est le nom du chemin du répertoire qui contient ups.conf et d'autres fichiers de configuration. Si cette variable n'est pas définie, upsdrvctl (et les drivers) utilisent une valeur par défaut intégrée, qui est souvent /usr/local/ups/etc.

NUT_ALTPIDPATH est le nom du chemin du répertoire dans lequel upsd et les drivers stockent les fichiers .pid. Si cette variable n'est pas définie, upsd et les drivers utilisent soit NUT_STATEPATH s'il est défini, soit ALTPIDPATH s'il est défini, soit autrement la valeur par défaut intégrée STATEPATH.

DIAGNOSTICS

upsdrvctl retournera un code de sortie non nul s'il rencontre une erreur lors de l'exécution de l'opération souhaitée. Cela se produira également si un driver met plus de temps que la période maxstartdelay pour passer en arrière-plan.
