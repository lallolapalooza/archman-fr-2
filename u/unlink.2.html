unlink(2) Manuel des appels système unlink(2)

NOM

unlink, unlinkat - supprimer un nom et éventuellement le fichier auquel il fait référence

BIBLIOTHÈQUE

Bibliothèque C standard (libc, -lc)

SYNTAXE

#include <unistd.h>
int unlink(const char *path);
#include <fcntl.h>           /* Définition des constantes AT_* */
#include <unistd.h>
int unlinkat(int dirfd, const char *path, int flags);
Exigences de macro de test de fonctionnalités pour glibc (voir feature_test_macros(7)):

unlinkat():

    Depuis glibc 2.10 :
        _POSIX_C_SOURCE >= 200809L
    Avant glibc 2.10 :
        _ATFILE_SOURCE

DESCRIPTION

unlink() supprime un nom du système de fichiers. Si ce nom était le dernier lien vers un fichier et qu'aucun processus n'a le fichier ouvert, le fichier est supprimé et l'espace qu'il utilisait est rendu disponible pour réutilisation.

Si le nom était le dernier lien vers un fichier mais que des processus ont encore le fichier ouvert, le fichier restera en existence jusqu'à ce que le dernier descripteur de fichier qui y fait référence soit fermé.

Si le nom faisait référence à un lien symbolique, le lien est supprimé.

Si le nom faisait référence à une socket, un FIFO ou un périphérique, le nom est supprimé mais les processus qui ont l'objet ouvert peuvent continuer à l'utiliser.

unlinkat()

L'appel système unlinkat() fonctionne exactement de la même manière que unlink() ou rmdir(2) (selon que flags inclut ou non le drapeau AT_REMOVEDIR) sauf pour les différences décrites ici.

Si path est relatif, il est interprété par rapport au répertoire référencé par le descripteur de fichier dirfd (plutôt que par rapport au répertoire de travail actuel du processus appelant, comme le font unlink() et rmdir(2) pour un chemin relatif).

Si path est relatif et que dirfd a la valeur spéciale AT_FDCWD, alors path est interprété par rapport au répertoire de travail actuel du processus appelant (comme unlink() et rmdir(2)).

Si path est absolu, alors dirfd est ignoré.

flags est un masque de bits qui peut être spécifié comme 0, ou en combinant des valeurs de drapeaux qui contrôlent le fonctionnement de unlinkat(). Actuellement, un seul drapeau est défini :

AT_REMOVEDIR
Par défaut, unlinkat() effectue l'équivalent de unlink() sur path. Si le drapeau AT_REMOVEDIR est spécifié, il effectue l'équivalent de rmdir(2) sur path.

Voir openat(2) pour une explication de la nécessité de unlinkat().

VALEUR DE RETOUR

En cas de succès, zéro est retourné. En cas d'erreur, -1 est retourné, et errno est défini pour indiquer l'erreur.

ERREURS

EACCES
L'accès en écriture au répertoire contenant path n'est pas autorisé pour l'UID effectif du processus, ou l'un des répertoires dans path n'autorisait pas les permissions de recherche. (Voir aussi path_resolution(7).)
EBUSY
path ne peut pas être désolidarisé car il est utilisé par le système ou par un autre processus ; par exemple, c'est un point de montage ou le logiciel client NFS l'a créé pour représenter un inode actif mais sans nom ("NFS silly renamed").
EFAULT
path pointe en dehors de votre espace d'adressage accessible.
EIO
Une erreur d'E/S s'est produite.
EISDIR
path fait référence à un répertoire. (C'est la valeur non-POSIX retournée depuis Linux 2.1.132.)
ELOOP
Trop de liens symboliques ont été rencontrés lors de la traduction de path.
ENAMETOOLONG
path était trop long.
ENOENT
Un composant dans path n'existe pas ou est un lien symbolique pendant, ou path est vide.
ENOMEM
La mémoire noyau disponible était insuffisante.
ENOTDIR
Un composant utilisé comme répertoire dans path n'est pas, en fait, un répertoire.
EPERM
Le système n'autorise pas la suppression de répertoires, ou la suppression de répertoires nécessite des privilèges que le processus appelant ne possède pas. (C'est le retour d'erreur prescrit par POSIX ; comme indiqué ci-dessus, Linux retourne EISDIR pour ce cas.)
EPERM (Linux seulement)
Le système de fichiers n'autorise pas la suppression de fichiers.
EPERM ou EACCES
Le répertoire contenant path a le bit collant (S_ISVTX) activé et l'UID effectif du processus n'est ni l'UID du fichier à supprimer ni celui du répertoire qui le contient, et le processus n'est pas privilégié (Linux : ne possède pas la capacité CAP_FOWNER).
EPERM
Le fichier à désolidariser est marqué comme immuable ou en mode ajout seulement. (Voir FS_IOC_SETFLAGS(2const).)
EROFS
path fait référence à un fichier sur un système de fichiers en lecture seule.

Les mêmes erreurs qui surviennent pour unlink() et rmdir(2) peuvent également survenir pour unlinkat(). Les erreurs supplémentaires suivantes peuvent survenir pour unlinkat():

EBADF
path est relatif mais dirfd n'est ni AT_FDCWD ni un descripteur de fichier valide.
EINVAL
Une valeur de drapeau invalide a été spécifiée dans flags.
EISDIR
path fait référence à un répertoire, et AT_REMOVEDIR n'a pas été spécifié dans flags.
ENOTDIR
path est relatif et dirfd est un descripteur de fichier faisant référence à un fichier autre qu'un répertoire.

NORMES

POSIX.1-2024.

HISTORIQUE

unlink()
SVr4, 4.3BSD, POSIX.1-2001.
unlinkat()
POSIX.1-2008. Linux 2.6.16, glibc 2.4.

glibc

Sur les anciens noyaux où unlinkat() n'est pas disponible, la fonction enveloppante glibc se rabat sur l'utilisation de unlink() ou rmdir(2). Lorsque path est relatif, glibc construit un nom de chemin basé sur le lien symbolique dans /proc/self/fd qui correspond à l'argument dirfd.

BOGUES

Des problèmes dans le protocole sous-jacent de NFS peuvent provoquer la disparition inattendue de fichiers qui sont toujours en cours d'utilisation.
