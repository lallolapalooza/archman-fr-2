UNIX(7) Manuel d'information divers UNIX(7)

NOM

unix - sockets pour la communication interprocessus locale

SYNTAXE

#include <sys/socket.h>
#include <sys/un.h>
socket_unix = socket(AF_UNIX, type, 0);
erreur = socketpair(AF_UNIX, type, 0, int *sv);

DESCRIPTION

La famille de sockets AF_UNIX (également connue sous le nom de AF_LOCAL) est utilisée pour communiquer efficacement entre processus sur la même machine. Traditionnellement, les sockets de domaine UNIX peuvent être sans nom, ou liés à un chemin de système de fichiers (marqué comme étant de type socket). Linux prend également en charge un espace de noms abstrait qui est indépendant du système de fichiers.

Les types de sockets valides dans le domaine UNIX sont : SOCK_STREAM, pour un socket orienté flux ; SOCK_DGRAM, pour un socket orienté datagramme qui préserve les limites des messages (comme sur la plupart des implémentations UNIX, les sockets datagrammes UNIX sont toujours fiables et ne réordonnent pas les datagrammes) ; et (depuis Linux 2.6.4) SOCK_SEQPACKET, pour un socket à paquet séquencé qui est orienté connexion, préserve les limites des messages et livre les messages dans l'ordre où ils ont été envoyés.

Les sockets de domaine UNIX prennent en charge le passage de descripteurs de fichiers ou d'identifiants de processus à d'autres processus à l'aide de données auxiliaires.

Format d'adresse

Une adresse de socket UNIX est représentée dans la structure suivante :


struct sockaddr_un {
    sa_family_t sun_family;               /* AF_UNIX */
    char        sun_path[108];            /* Chemin */
};

Le champ sun_family contient toujours AF_UNIX. Sur Linux, sun_path a une taille de 108 octets ; voir également ERREURS, ci-dessous.

Divers appels système (par exemple, bind(2), connect(2) et sendto(2)) prennent un argument sockaddr_un en entrée. D'autres appels système (par exemple, getsockname(2), getpeername(2), recvfrom(2) et accept(2)) retournent un argument de ce type.

Trois types d'adresses sont distingués dans la structure sockaddr_un :

chemin
un socket UNIX peut être lié à un chemin de système de fichiers terminé par un caractère nul à l'aide de bind(2). Lorsque l'adresse d'un socket de chemin est renvoyée (par l'un des appels système mentionnés ci-dessus), sa longueur est

offsetof(struct sockaddr_un, sun_path) + strlen(sun_path) + 1

et sun_path contient le chemin terminé par un caractère nul. (Sur Linux, l'expression offsetof() ci-dessus équivaut à la même valeur que sizeof(sa_family_t), mais certaines autres implémentations incluent d'autres champs avant sun_path, de sorte que l'expression offsetof() décrit plus portablement la taille de la structure d'adresse.)
Pour plus de détails sur les sockets de chemin, voir ci-dessous.
sans nom
un socket de flux qui n'a pas été lié à un chemin à l'aide de bind(2) n'a pas de nom. De même, les deux sockets créés par socketpair(2) sont sans nom. Lorsque l'adresse d'un socket sans nom est renvoyée, sa longueur est sizeof(sa_family_t), et sun_path ne doit pas être inspecté.
abstrait
une adresse de socket abstraite se distingue (d'un socket de chemin) par le fait que sun_path[0] est un octet nul ('\0'). L'adresse du socket dans cet espace de noms est donnée par les octets supplémentaires dans sun_path qui sont couverts par la longueur spécifiée de la structure d'adresse. (Les octets nuls dans le nom n'ont pas de signification spéciale.) Le nom n'a aucun lien avec les chemins du système de fichiers. Lorsque l'adresse d'un socket abstrait est renvoyée, l' addrlen renvoyé est supérieur à sizeof(sa_family_t) (c'est-à-dire supérieur à 2), et le nom du socket est contenu dans les premiers (addrlen - sizeof(sa_family_t)) octets de sun_path.

Sockets de chemin

Lors de la liaison d'un socket à un chemin, quelques règles doivent être observées pour une portabilité maximale et une facilité de codage :

•
Le chemin dans sun_path doit être terminé par un caractère nul.
•
La longueur du chemin, y compris le caractère nul de terminaison, ne doit pas excéder la taille de sun_path.
•
L'argument addrlen qui décrit la structure sockaddr_un englobante doit avoir une valeur d'au moins :

offsetof(struct sockaddr_un, sun_path)+strlen(addr.sun_path)+1

ou, plus simplement, addrlen peut être spécifié comme sizeof(struct sockaddr_un).

Il existe des variations dans la manière dont les implémentations gèrent les adresses de sockets UNIX qui ne suivent pas les règles ci-dessus. Par exemple, certaines (mais pas toutes) implémentations ajoutent un terminateur nul s'il n'y en a pas dans le sun_path fourni.

Lors du codage d'applications portables, gardez à l'esprit que certaines implémentations ont un sun_path aussi court que 92 octets.

Divers appels système (accept(2), recvfrom(2), getsockname(2), getpeername(2)) renvoient des structures d'adresse de socket. Lorsqu'ils sont appliqués aux sockets UNIX, l'argument addrlen de type valeur-résultat fourni à l'appel doit être initialisé comme ci-dessus. Au retour, l'argument est défini pour indiquer la taille *réelle* de la structure d'adresse. L'appelant devrait vérifier la valeur renvoyée dans cet argument : si la valeur de sortie dépasse la valeur d'entrée, alors il n'y a aucune garantie qu'un terminateur nul soit présent dans sun_path. (Voir ERREURS.)

Propriété et permissions des sockets de chemin

Dans l'implémentation Linux, les sockets de chemin respectent les permissions du répertoire dans lequel ils se trouvent. La création d'un nouveau socket échoue si le processus n'a pas les permissions d'écriture et de recherche (exécution) sur le répertoire où le socket est créé.

Sur Linux, la connexion à un objet socket de flux nécessite une permission d'écriture sur ce socket ; l'envoi d'un datagramme à un socket datagramme nécessite également une permission d'écriture sur ce socket. POSIX ne fait aucune déclaration sur l'effet des permissions sur un fichier socket, et sur certains systèmes (par exemple, les anciennes versions BSD), les permissions du socket sont ignorées. Les programmes portables ne devraient pas s'appuyer sur cette fonctionnalité pour la sécurité.

Lors de la création d'un nouveau socket, le propriétaire et le groupe du fichier socket sont définis conformément aux règles habituelles. Le fichier socket a toutes les permissions activées, autres que celles qui sont désactivées par le umask(2) du processus.

Le propriétaire, le groupe et les permissions d'un socket de chemin peuvent être modifiés (à l'aide de chown(2) et chmod(2)).

Sockets abstraits

Les permissions des sockets n'ont aucun sens pour les sockets abstraits : le umask(2) du processus n'a aucun effet lors de la liaison d'un socket abstrait, et la modification de la propriété et des permissions de l'objet (via fchown(2) et fchmod(2)) n'a aucun effet sur l'accessibilité du socket.

Les sockets abstraits disparaissent automatiquement lorsque toutes les références ouvertes au socket sont fermées.

L'espace de noms des sockets abstraits est une extension non portable de Linux.

Options de socket

Les options suivantes sont spécifiques à AF_UNIX. Elles peuvent être définies avec setsockopt(2) et lues avec getsockopt(2) en spécifiant SOL_SOCKET comme famille de sockets.

SO_PASSCRED
L'activation de cette option de socket entraîne la réception des identifiants du processus d'envoi dans un message auxiliaire SCM_CREDENTIALS lors de chaque message reçu ultérieurement. Les identifiants retournés sont ceux spécifiés par l'expéditeur à l'aide de SCM_CREDENTIALS, ou une valeur par défaut incluant l'identifiant de processus (PID), l'identifiant utilisateur réel (real user ID) et l'identifiant de groupe réel (real group ID) de l'expéditeur, si celui-ci n'a pas spécifié de données auxiliaires SCM_CREDENTIALS.
Lorsque cette option est définie et que le socket n'est pas encore connecté, un nom unique dans l'espace de noms abstrait sera généré automatiquement.
La valeur transmise comme argument à setsockopt(2) et retournée comme résultat de getsockopt(2) est un indicateur booléen entier.
SO_PASSSEC
Permet de recevoir le label de sécurité SELinux du socket distant dans un message auxiliaire de type SCM_SECURITY (voir ci-dessous).
La valeur transmise comme argument à setsockopt(2) et retournée comme résultat de getsockopt(2) est un indicateur booléen entier.
L'option SO_PASSSEC est prise en charge pour les sockets datagrammes du domaine UNIX depuis Linux 2.6.18 ; la prise en charge des sockets de flux du domaine UNIX a été ajoutée dans Linux 4.2.
SO_PEEK_OFF
Voir socket(7).
SO_PEERCRED
Cette option de socket en lecture seule retourne les identifiants du processus distant connecté à ce socket. Les identifiants retournés sont ceux qui étaient en vigueur au moment de l'appel à connect(2), listen(2), ou socketpair(2).
L'argument de getsockopt(2) est un pointeur vers une structure ucred ; définissez la macro de test de fonctionnalité _GNU_SOURCE pour obtenir la définition de cette structure à partir de <sys/socket.h>.
L'utilisation de cette option n'est possible que pour les sockets de flux AF_UNIX connectés et pour les paires de sockets de flux et datagrammes AF_UNIX créées à l'aide de socketpair(2).
SO_PEERSEC
Cette option de socket en lecture seule retourne le contexte de sécurité du socket distant connecté à ce socket. Par défaut, ce sera le même que le contexte de sécurité du processus qui a créé le socket distant, sauf s'il est remplacé par la politique ou par un processus disposant des permissions requises.
L'argument de getsockopt(2) est un pointeur vers un tampon de la longueur spécifiée en octets dans lequel la chaîne de contexte de sécurité sera copiée. Si la longueur du tampon est inférieure à la longueur de la chaîne de contexte de sécurité, alors getsockopt(2) retourne -1, définit errno à ERANGE, et retourne la longueur requise via optlen. L'appelant doit allouer au moins NAME_MAX octets pour le tampon initialement, bien que cela ne soit pas garanti d'être suffisant. Il peut être nécessaire de redimensionner le tampon à la longueur retournée et de réessayer.
La chaîne de contexte de sécurité peut inclure un caractère nul de terminaison dans la longueur retournée, mais ce n'est pas garanti : un contexte de sécurité "foo" pourrait être représenté soit par {'f','o','o'} d'une longueur de 3, soit par {'f','o','o','\0'} d'une longueur de 4, qui sont considérés comme interchangeables. La chaîne est imprimable, ne contient pas de caractères nuls non terminants, et est dans un encodage non spécifié (en particulier, elle n'est pas garantie d'être en ASCII ou en UTF-8).
L'utilisation de cette option pour les sockets de la famille d'adresses AF_UNIX est prise en charge depuis Linux 2.6.2 pour les sockets de flux connectés, et depuis Linux 4.18 également pour les paires de sockets de flux et datagrammes créées à l'aide de socketpair(2).

Fonctionnalité d'autolias

Si un appel à bind(2) spécifie addrlen comme sizeof(sa_family_t), ou si l'option de socket SO_PASSCRED a été spécifiée pour un socket qui n'a pas été explicitement lié à une adresse, alors le socket est automatiquement lié à une adresse abstraite. L'adresse consiste en un octet nul suivi de 5 octets dans le jeu de caractères [0-9a-f]. Ainsi, il y a une limite de 2^20 adresses d'autolias. (Depuis Linux 2.1.15, lors de l'ajout de la fonctionnalité d'autolias, 8 octets étaient utilisés, et la limite était donc de 2^32 adresses d'autolias. Le changement à 5 octets est intervenu dans Linux 2.3.15.)

API des sockets

Les paragraphes suivants décrivent les détails spécifiques au domaine et les fonctionnalités non prises en charge de l'API des sockets pour les sockets de domaine UNIX sous Linux.

Les sockets de domaine UNIX ne prennent pas en charge la transmission de données hors bande (le drapeau MSG_OOB pour send(2) et recv(2)).

Le drapeau MSG_MORE de send(2) n'est pas pris en charge par les sockets de domaine UNIX.

Avant Linux 3.4, l'utilisation de MSG_TRUNC dans l'argument flags de recv(2) n'était pas prise en charge par les sockets de domaine UNIX.

L'option de socket SO_SNDBUF a un effet pour les sockets de domaine UNIX, mais l'option SO_RCVBUF n'en a pas. Pour les sockets datagrammes, la valeur de SO_SNDBUF impose une limite supérieure à la taille des datagrammes sortants. Cette limite est calculée comme le double de la valeur de l'option (voir socket(7)) moins 32 octets utilisés pour la surcharge.

Messages auxiliaires

Les données auxiliaires sont envoyées et reçues à l'aide de sendmsg(2) et recvmsg(2). Pour des raisons historiques, les types de messages auxiliaires listés ci-dessous sont spécifiés avec un type SOL_SOCKET même s'ils sont spécifiques à AF_UNIX. Pour les envoyer, définissez le champ cmsg_level de la structure cmsghdr à SOL_SOCKET et le champ cmsg_type au type. Pour plus d'informations, voir cmsg(3).

SCM_RIGHTS
Envoyer ou recevoir un ensemble de descripteurs de fichiers ouverts à partir d'un autre processus. La partie données contient un tableau d'entiers des descripteurs de fichiers.
Couramment, cette opération est désignée par "passer un descripteur de fichier" à un autre processus. Cependant, plus précisément, ce qui est passé est une référence à une description de fichier ouverte (voir open(2)), et dans le processus récepteur, il est probable qu'un numéro de descripteur de fichier différent sera utilisé. Sémantiquement, cette opération est équivalente à dupliquer (dup(2)) un descripteur de fichier dans la table des descripteurs de fichier d'un autre processus.
Si le tampon utilisé pour recevoir les données auxiliaires contenant des descripteurs de fichiers est trop petit (ou absent), alors les données auxiliaires sont tronquées (ou rejetées) et les descripteurs de fichiers excédentaires sont automatiquement fermés dans le processus récepteur.
Si le nombre de descripteurs de fichiers reçus dans les données auxiliaires devait entraîner le dépassement de la limite de ressources RLIMIT_NOFILE du processus (voir getrlimit(2)), les descripteurs de fichiers excédentaires sont automatiquement fermés dans le processus récepteur.
La constante du noyau SCM_MAX_FD définit une limite sur le nombre de descripteurs de fichiers dans le tableau. Tenter d'envoyer un tableau plus grand que cette limite entraîne l'échec de sendmsg(2) avec l'erreur EINVAL. SCM_MAX_FD a la valeur 253 (ou 255 avant Linux 2.6.38).
SCM_CREDENTIALS
Envoyer ou recevoir des identifiants UNIX. Cela peut être utilisé pour l'authentification. Les identifiants sont passés sous forme de message auxiliaire struct ucred. Cette structure est définie dans <sys/socket.h> comme suit :

struct ucred {
    pid_t pid;    /* Process ID du processus d'envoi */
    uid_t uid;    /* User ID du processus d'envoi */
    gid_t gid;    /* Group ID du processus d'envoi */
};

Depuis glibc 2.8, la macro de test de fonctionnalité _GNU_SOURCE doit être définie (avant d'inclure tous les fichiers d'en-tête) afin d'obtenir la définition de cette structure.
Les identifiants que l'expéditeur spécifie sont vérifiés par le noyau. Un processus privilégié est autorisé à spécifier des valeurs qui ne correspondent pas aux siennes. L'expéditeur doit spécifier son propre identifiant de processus (sauf s'il a la capacité CAP_SYS_ADMIN, auquel cas le PID de tout processus existant peut être spécifié), son identifiant utilisateur réel, son identifiant utilisateur effectif, ou son identifiant utilisateur enregistré (saved set-user-ID) (sauf s'il a CAP_SETUID), et son identifiant de groupe réel, son identifiant de groupe effectif, ou son identifiant de groupe enregistré (saved set-group-ID) (sauf s'il a CAP_SETGID).
Pour recevoir un message struct ucred, l'option SO_PASSCRED doit être activée sur le socket.
SCM_SECURITY
Recevoir le contexte de sécurité SELinux (le label de sécurité) du socket distant. Les données auxiliaires reçues sont une chaîne terminée par un caractère nul contenant le contexte de sécurité. Le récepteur doit allouer au moins NAME_MAX octets dans la partie données du message auxiliaire pour ces données.
Pour recevoir le contexte de sécurité, l'option SO_PASSSEC doit être activée sur le socket (voir ci-dessus).

Lors de l'envoi de données auxiliaires avec sendmsg(2), un seul élément de chacun des types ci-dessus peut être inclus dans le message envoyé.

Au moins un octet de données réelles doit être envoyé lors de l'envoi de données auxiliaires. Sous Linux, ceci est requis pour envoyer avec succès des données auxiliaires sur un socket de flux de domaine UNIX. Lors de l'envoi de données auxiliaires sur un socket datagramme de domaine UNIX, il n'est pas nécessaire sous Linux d'envoyer d'accompagnement

SO_PEERCRED

La famille d'adresses unix(7) et le type de socket socket(2)SOCK_STREAM ou SOCK_DGRAM prennent en charge l'option de socket SO_PEERCRED. Lorsque cette option est activée, la structure struct ucred contenant l'ID de processus (PID), l'ID utilisateur (UID) et l'ID de groupe (GID) du processus distant est renvoyée avec les données. Cette structure est généralement obtenue à l'aide de getsockopt(2).

int socket;
struct ucred ucred;
socklen_t len = sizeof(struct ucred);

getsockopt(socket, SOL_SOCKET, SO_PEERCRED, &ucred, &len);

Pour que cette option fonctionne, le fichier spécial du système de fichiers UNIX doit être créé avec les permissions appropriées. Par exemple, si vous créez un socket UNIX dans /tmp, qui est généralement accessible en écriture à tout le monde, les processus non privilégiés pourront lire les informations d'identification du pair.

Lorsque SO_PEERCRED est activé, chaque paquet reçu via recvmsg(2) inclut des données supplémentaires qui décrivent le processus émetteur. Si l'espace alloué pour les données supplémentaires est insuffisant, les données supplémentaires sont tronquées et le flag MSG_CTRUNC est défini dans le champ msg.msg_flags.

Lorsque vous utilisez sendmsg(2) pour envoyer des données via un socket, vous pouvez joindre des données supplémentaires comme les informations d'identification du processus émetteur en utilisant l'option SCM_CREDENTIALS. Cela nécessite que le socket soit de type SOCK_STREAM ou SOCK_DGRAM. Les données supplémentaires sont transmises dans la structure cmsghdr.

Pour que l'envoi de données supplémentaires soit fiable, le socket doit inclure au moins un octet de données réelles lors de l'envoi de données supplémentaires via un socket datagramme. Les applications portables doivent également inclure au moins un octet de données réelles lors de l'envoi de données supplémentaires via un socket datagramme.

Lors de la réception à partir d'un socket de flux, les données supplémentaires forment une sorte de barrière pour les données reçues. Par exemple, supposons que l'expéditeur transmet comme suit :

(1)
sendmsg(2) de quatre octets, sans données supplémentaires.
(2)
sendmsg(2) d'un octet, avec des données supplémentaires.
(3)
sendmsg(2) de quatre octets, sans données supplémentaires.

Supposons que le récepteur effectue maintenant des appels recvmsg(2), chacun avec une taille de tampon de 20 octets. Le premier appel recevra cinq octets de données, ainsi que les données supplémentaires envoyées par le deuxième appel sendmsg(2). L'appel suivant recevra les quatre octets de données restants.

Si l'espace alloué pour la réception de données supplémentaires entrantes est trop petit, les données supplémentaires sont tronquées au nombre d'en-têtes qui tiennent dans le tampon fourni (ou, dans le cas d'une liste de descripteurs de fichiers SCM_RIGHTS, la liste des descripteurs de fichiers peut être tronquée). Si aucun tampon n'est fourni pour les données supplémentaires entrantes (c'est-à-dire que le champ msg_control de la structure msghdr fournie à recvmsg(2) est NULL), alors les données supplémentaires entrantes sont ignorées. Dans ces deux cas, le flag MSG_CTRUNC sera défini dans la valeur msg.msg_flags retournée par recvmsg(2).

Ioctls

Les appels ioctl(2) suivants renvoient des informations dans value. La syntaxe correcte est :

int value;
error = ioctl(unix_socket, ioctl_type, &value);

ioctl_type peut être :

SIOCINQ
Pour les sockets SOCK_STREAM, cet appel renvoie le nombre d'octets non lus dans le tampon de réception. Le socket ne doit pas être en état d'écoute, sinon une erreur (EINVAL) est renvoyée. SIOCINQ est défini dans <linux/sockios.h>. Alternativement, vous pouvez utiliser le synonyme FIONREAD, défini dans <sys/ioctl.h>. Pour les sockets SOCK_DGRAM, la valeur renvoyée est la même que pour les sockets datagrammes du domaine Internet ; voir udp(7).

ERREURS

EADDRINUSE
L'adresse locale spécifiée est déjà utilisée ou l'objet socket du système de fichiers existe déjà.
EBADF
Cette erreur peut survenir pour sendmsg(2) lors de l'envoi d'un descripteur de fichier en tant que données supplémentaires sur un socket de domaine UNIX (voir la description de SCM_RIGHTS, ci-dessus), et indique que le numéro de descripteur de fichier qui est envoyé n'est pas valide (par exemple, ce n'est pas un descripteur de fichier ouvert).
ECONNREFUSED
L'adresse distante spécifiée par connect(2) n'était pas un socket d'écoute. Cette erreur peut également survenir si le chemin cible n'est pas un socket.
ECONNRESET
Le socket distant a été fermé de manière inattendue.
EFAULT
L'adresse mémoire utilisateur n'était pas valide.
EINVAL
Argument invalide passé. Une cause courante est que la valeur AF_UNIX n'a pas été spécifiée dans le champ sun_type des adresses fournies, ou que le socket était dans un état invalide pour l'opération appliquée.
EISCONN
connect(2) appelé sur un socket déjà connecté ou une adresse cible a été spécifiée sur un socket connecté.
ENFILE
La limite système globale du nombre total de fichiers ouverts a été atteinte.
ENOENT
Le chemin dans l'adresse distante spécifié à connect(2) n'existait pas.
ENOMEM
Manque de mémoire.
ENOTCONN
Opération sur socket nécessitant une adresse cible, mais le socket n'est pas connecté.
EOPNOTSUPP
Opération de flux appelée sur un socket non orienté flux ou tentative d'utilisation de l'option de données hors bande.
EPERM
L'expéditeur a passé des informations d'identification invalides dans la structure struct ucred.
EPIPE
Le socket distant a été fermé sur un socket de flux. Si activé, un signal SIGPIPE est également envoyé. Cela peut être évité en passant le flag MSG_NOSIGNAL à send(2) ou sendmsg(2).
EPROTONOSUPPORT
Le protocole passé n'est pas AF_UNIX.
EPROTOTYPE
Le socket distant ne correspond pas au type de socket local (SOCK_DGRAM versus SOCK_STREAM).
ESOCKTNOSUPPORT
Type de socket inconnu.
ESRCH
Lors de l'envoi d'un message supplémentaire contenant des informations d'identification (SCM_CREDENTIALS), l'appelant a spécifié un PID qui ne correspond à aucun processus existant.
ETOOMANYREFS
Cette erreur peut survenir pour sendmsg(2) lors de l'envoi d'un descripteur de fichier en tant que données supplémentaires sur un socket de domaine UNIX (voir la description de SCM_RIGHTS, ci-dessus). Elle survient si le nombre de descripteurs de fichiers "en cours" dépasse la limite de ressources RLIMIT_NOFILE et que l'appelant n'a pas la capacité CAP_SYS_RESOURCE. Un descripteur de fichier en cours est un descripteur qui a été envoyé en utilisant sendmsg(2) mais qui n'a pas encore été accepté dans le processus destinataire en utilisant recvmsg(2).
Cette erreur est diagnostiquée depuis la version principale de Linux 4.5 (et dans certaines versions antérieures du noyau où la correction a été rétroportée). Dans les versions antérieures du noyau, il était possible de placer un nombre illimité de descripteurs de fichiers en cours en envoyant chaque descripteur de fichier avec sendmsg(2) puis en fermant le descripteur de fichier de sorte qu'il ne soit pas comptabilisé par rapport à la limite de ressources RLIMIT_NOFILE.

D'autres erreurs peuvent être générées par la couche socket générique ou par le système de fichiers lors de la génération d'un objet socket de système de fichiers. Voir les pages man appropriées pour plus d'informations.

VERSIONS

SCM_CREDENTIALS et le namespace abstrait ont été introduits avec Linux 2.2 et ne doivent pas être utilisés dans les programmes portables. (Certains systèmes dérivés de BSD prennent également en charge le passage des informations d'identification, mais les détails d'implémentation diffèrent.)

NOTES

La liaison à un socket avec un nom de fichier crée un socket dans le système de fichiers qui doit être supprimé par l'appelant lorsqu'il n'est plus nécessaire (en utilisant unlink(2)). Les sémantiques habituelles de fermeture par la suite de UNIX s'appliquent ; le socket peut être désenregistré à tout moment et sera finalement supprimé du système de fichiers lorsque la dernière référence à celui-ci sera fermée.

Pour passer des descripteurs de fichiers ou des informations d'identification sur un socket SOCK_STREAM, vous devez envoyer ou recevoir au moins un octet de données non supplémentaires dans le même appel sendmsg(2) ou recvmsg(2).

Les sockets de flux UNIX ne prennent pas en charge la notion de données hors bande.

BOGUES

Lors de la liaison d'un socket à une adresse, Linux est l'une des implémentations qui ajoutent un terminateur nul si aucun n'est fourni dans sun_path. Dans la plupart des cas, cela n'est pas problématique : lorsque l'adresse du socket est récupérée, elle sera plus longue d'un octet que celle fournie lors de la liaison du socket. Cependant, il existe un cas où un comportement déroutant peut en résulter : si 108 octets non nuls sont fournis lors de la liaison d'un socket, l'ajout du terminateur nul fait dépasser la longueur du chemin sizeof(sun_path). Par conséquent, lors de la récupération de l'adresse du socket (par exemple, via accept(2)), si l'argument addrlen d'entrée pour l'appel de récupération est spécifié comme sizeof(struct sockaddr_un), alors la structure d'adresse retournée n'aura **pas** de terminateur nul dans sun_path.

De plus, certaines implémentations n'exigent pas de terminateur nul lors de la liaison d'un socket (l'argument addrlen est utilisé pour déterminer la longueur de sun_path) et lorsque l'adresse du socket est récupérée sur ces implémentations, il n'y a pas de terminateur nul dans sun_path.

Les applications qui récupèrent les adresses de socket peuvent (de manière portable) coder pour gérer la possibilité qu'il n'y ait pas de terminateur nul dans sun_path en respectant le fait que le nombre d'octets valides dans le chemin est :


strnlen(addr.sun_path, addrlen - offsetof(sockaddr_un, sun_path))

Alternativement, une application peut récupérer l'adresse du socket en allouant un tampon de taille sizeof(struct sockaddr_un)+1 qui est mis à zéro avant la récupération. L'appel de récupération peut spécifier addrlen comme sizeof(struct sockaddr_un), et l'octet zéro supplémentaire garantit qu'il y aura un terminateur nul pour la chaîne renvoyée dans sun_path :


void *addrp;
addrlen = sizeof(struct sockaddr_un);
addrp = malloc(addrlen + 1);
if (addrp == NULL)
    /* Gérer l'erreur */ ;
memset(addrp, 0, addrlen + 1);
if (getsockname(sfd, (struct sockaddr *) addrp, &addrlen)) == -1)
    /* Gérer l'erreur */ ;
printf("sun_path = %s\n", ((struct sockaddr_un *) addrp)->sun_path);

Ce genre de désordre peut être évité s'il est garanti que les applications qui *créent* p

athname sockets suivent les règles décrites ci-dessus sous Sockets de noms de chemin.

EXEMPLES

Le code suivant démontre l'utilisation de sockets de paquets séquencés pour la communication interprocessus locale. Il se compose de deux programmes. Le programme serveur attend une connexion du programme client. Le client envoie chacun de ses arguments de ligne de commande dans des messages distincts. Le serveur traite les messages entrants comme des entiers et les additionne. Le client envoie la chaîne de commande "END". Le serveur renvoie un message contenant la somme des entiers du client. Le client affiche la somme et se termine. Le serveur attend que le client suivant se connecte. Pour arrêter le serveur, le client est appelé avec l'argument de ligne de commande "DOWN".

La sortie suivante a été enregistrée lors de l'exécution du serveur en arrière-plan et de l'exécution répétée du client. L'exécution du programme serveur se termine lorsqu'il reçoit la commande "DOWN".

Exemple de sortie


$ ./server &
[1] 25887
$ ./client 3 4;
Result = 7
$ ./client 11 -5;
Result = 6
$ ./client DOWN;
Result = 0
[1]+  Done                    ./server
$

Source du programme

/*
 * Fichier connection.h
 */
#ifndef CONNECTION_H
#define CONNECTION_H
#define SOCKET_NAME "/tmp/9Lq7BNBnBycd6nxy.socket"
#define BUFFER_SIZE 12
#endif  // garde d'inclusion
/*
 * Fichier server.c
 */
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/socket.h>
#include <sys/types.h>
#include <sys/un.h>
#include <unistd.h>
#include "connection.h"
int
main(void)
{
    int                 down_flag = 0;
    int                 ret;
    int                 connection_socket;
    int                 data_socket;
    int                 result;
    ssize_t             r, w;
    struct sockaddr_un  name;
    char                buffer[BUFFER_SIZE];
    /* Créer un socket local.  */
    connection_socket = socket(AF_UNIX, SOCK_SEQPACKET, 0);
    if (connection_socket == -1) {
        perror("socket");
        exit(EXIT_FAILURE);
    }
    /*
     * Pour la portabilité, effacer toute la structure, car certaines
     * implémentations ont des champs supplémentaires (non standard) dans
     * la structure.
     */
    memset(&name, 0, sizeof(name));
    /* Lier le socket au nom du socket.  */
    name.sun_family = AF_UNIX;
    strncpy(name.sun_path, SOCKET_NAME, sizeof(name.sun_path) - 1);
    ret = bind(connection_socket, (const struct sockaddr *) &name,
               sizeof(name));
    if (ret == -1) {
        perror("bind");
        exit(EXIT_FAILURE);
    }
    /*
     * Préparer l'acceptation des connexions. La taille de la file d'attente est définie
     * à 20. Ainsi, pendant qu'une requête est traitée, d'autres requêtes
     * peuvent attendre.
     */
    ret = listen(connection_socket, 20);
    if (ret == -1) {
        perror("listen");
        exit(EXIT_FAILURE);
    }
    /* C'est la boucle principale pour gérer les connexions.  */
    for (;;) {
        /* Attendre la connexion entrante.  */
        data_socket = accept(connection_socket, NULL, NULL);
        if (data_socket == -1) {
            perror("accept");
            exit(EXIT_FAILURE);
        }
        result = 0;
        for (;;) {
            /* Attendre le prochain paquet de données.  */
            r = read(data_socket, buffer, sizeof(buffer));
            if (r == -1) {
                perror("read");
                exit(EXIT_FAILURE);
            }
            /* Assurer que le buffer est terminé par 0.  */
            buffer[sizeof(buffer) - 1] = 0;
            /* Gérer les commandes.  */
            if (!strncmp(buffer, "DOWN", sizeof(buffer))) {
                down_flag = 1;
                continue;
            }
            if (!strncmp(buffer, "END", sizeof(buffer))) {
                break;
            }
            if (down_flag) {
                continue;
            }
            /* Ajouter le sommande reçu.  */
            result += atoi(buffer);
        }
        /* Envoyer le résultat.  */
        sprintf(buffer, "%d", result);
        w = write(data_socket, buffer, sizeof(buffer));
        if (w == -1) {
            perror("write");
            exit(EXIT_FAILURE);
        }
        /* Fermer le socket.  */
        close(data_socket);
        /* Quitter sur la commande DOWN.  */
        if (down_flag) {
            break;
        }
    }
    close(connection_socket);
    /* Supprimer le socket.  */
    unlink(SOCKET_NAME);
    exit(EXIT_SUCCESS);
}
/*
 * Fichier client.c
 */
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/socket.h>
#include <sys/types.h>
#include <sys/un.h>
#include <unistd.h>
#include "connection.h"
int
main(int argc, char *argv[])
{
    int                 ret;
    int                 data_socket;
    ssize_t             r, w;
    struct sockaddr_un  addr;
    char                buffer[BUFFER_SIZE];
    /* Créer un socket local.  */
    data_socket = socket(AF_UNIX, SOCK_SEQPACKET, 0);
    if (data_socket == -1) {
        perror("socket");
        exit(EXIT_FAILURE);
    }
    /*
     * Pour la portabilité, effacer toute la structure, car certaines
     * implémentations ont des champs supplémentaires (non standard) dans
     * la structure.
     */
    memset(&addr, 0, sizeof(addr));
    /* Connecter le socket à l'adresse du socket.  */
    addr.sun_family = AF_UNIX;
    strncpy(addr.sun_path, SOCKET_NAME, sizeof(addr.sun_path) - 1);
    ret = connect(data_socket, (const struct sockaddr *) &addr,
                   sizeof(addr));
    if (ret == -1) {
        fprintf(stderr, "Le serveur est en panne.\n");
        exit(EXIT_FAILURE);
    }
    /* Envoyer les arguments.  */
    for (int i = 1; i < argc; ++i) {
        w = write(data_socket, argv[i], strlen(argv[i]) + 1);
        if (w == -1) {
            perror("write");
            break;
        }
    }
    /* Demander le résultat.  */
    strcpy(buffer, "END");
    w = write(data_socket, buffer, strlen(buffer) + 1);
    if (w == -1) {
        perror("write");
        exit(EXIT_FAILURE);
    }
    /* Recevoir le résultat.  */
    r = read(data_socket, buffer, sizeof(buffer));
    if (r == -1) {
        perror("read");
        exit(EXIT_FAILURE);
    }
    /* Assurer que le buffer est terminé par 0.  */
    buffer[sizeof(buffer) - 1] = 0;
    printf("Résultat = %s\n", buffer);
    /* Fermer le socket.  */
    close(data_socket);
    exit(EXIT_SUCCESS);
}
