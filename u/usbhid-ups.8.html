NOM

usbhid-ups - Pilote pour matériel onduleur USB/HID

SYNTAXE

usbhid-ups -h

usbhid-ups -a NOM_ONDULEUR [OPTIONS]


Note

Cette page de manuel documente uniquement les fonctionnalités spécifiques au matériel du pilote usbhid-ups. Pour des informations sur le pilote principal, consultez nutupsdrv(8).

MATÉRIEL SUPPORTÉ

usbhid-ups apporte la surveillance des onduleurs USB/HID à NUT sur toutes les plateformes supportant l'USB via libusb. Il devrait détecter tout onduleur utilisant la classe de périphériques d'alimentation HID, mais la quantité de données variera en fonction du fabricant et du modèle.

Actuellement, usbhid-ups prend en charge :

•les modèles Eaton USB plus récents,
•tous les modèles MGE USB,
•tous les modèles Dell USB,
•tous les modèles AMETEK Powervar UPM,
•certains modèles APC,
•certains modèles Belkin,
•certains modèles Cyber Power Systems,
•certains modèles Powercom,
•certains modèles PowerWalker,
•certains modèles TrippLite.

Pour une liste plus complète, référez-vous à la liste de compatibilité matérielle NUT, disponible dans la distribution source de NUT sous le nom data/driver.list, ou sur le site web de NUT.

Vous pouvez utiliser l'option de pilote 'explore' pour recueillir des informations sur les onduleurs HID qui ne sont pas encore pris en charge, afin d'aider à ajouter une telle prise en charge ; voir ci-dessous pour plus de détails.

Ce pilote est connu pour fonctionner sur :

•la plupart des systèmes Linux,
•FreeBSD (stade bêta) et peut-être d'autres *BSD,
•Darwin / Mac OS X,
•Solaris 10 et les distributions basées sur illumos.

ARGUMENTS SUPPLÉMENTAIRES

Ce pilote prend également en charge les paramètres optionnels suivants :

port = chaîne

Option requise pour tous les pilotes NUT. Une valeur doit être définie, typiquement auto pour les pilotes qui gèrent les connexions USB.

Note
Il peut s'agir d'un chemin de périphérique dans le système de fichiers comme /dev/usb/hiddev0, mais l'utilisation actuelle de l'API libusb empêche la connaissance et la correspondance par de tels identifiants. Ils peuvent également être intrinsèquement peu fiables (dépendants des rebranchements et de l'ordre d'énumération). À l'heure actuelle, la valeur réelle est ignorée, mais syntaxiquement, une configuration de port doit toujours être présente.

Il est possible de contrôler plusieurs unités onduleur simultanément en exécutant plusieurs instances de ce pilote, à condition qu'elles puissent être distinguées de manière unique en définissant une combinaison des options vendor, product, vendorid, productid, serial, bus et/ou device détaillées ci-dessous. Pour les périphériques ou systèmes d'exploitation qui ne fournissent pas suffisamment d'informations, l'option allow_duplicates peut être utile (limitée et risquée !)

vendorid = regex, productid = regex, vendor = regex, product = regex, serial = regex

Sélectionne un onduleur spécifique, s'il y en a plus d'un connecté via USB. Chaque option spécifie une expression régulière étendue (voir regex(7) pour plus d'informations sur les expressions régulières), qui doit correspondre aux valeurs complètes de la chaîne fournisseur/produit/série respective de l'onduleur (sans les espaces blancs environnants), ou au code hexadécimal complet à 4 chiffres pour vendorid et productid.

Essayez lsusb(8) ou exécutez ce pilote NUT avec l'argument de ligne de commande -DD pour trouver les chaînes à faire correspondre.

Exemples :

•-x vendor="Foo.Corporation.*"
•-x vendorid="051d*" (APC)
•-x product=".*(Smart|Back)-?UPS.*"

bus = regex

OPTIONNEL, NON RECOMMANDÉ.

Sélectionne un onduleur sur un bus USB spécifique ou un groupe de bus. L'argument est une expression régulière qui doit correspondre au nom du bus sur lequel l'onduleur est connecté (par exemple, bus="002" ou bus="00[2-3]") tel qu'il apparaît sous Linux dans /sys/bus/usb/devices ou lsusb(8) ; y compris les zéros de tête.


Note
Les numéros de bus ne sont pas garantis par le système d'exploitation comme étant stables lors des redémarrages, des rechargements de pilotes de noyau ou des rebranchements de périphériques (par exemple, en changeant la population visible des concentrateurs USB).

device = regex

OPTIONNEL, NON RECOMMANDÉ.

Sélectionne un onduleur sur un périphérique USB spécifique ou un groupe de périphériques. L'argument est une expression régulière qui doit correspondre au nom du périphérique sur lequel l'onduleur est connecté (par exemple, device="001" ou device="00[1-2]") tel qu'il apparaît sous Linux dans /sys/bus/usb/devices ou lsusb(8) ; y compris les zéros de tête.


Note
Les numéros de périphérique ne sont pas garantis par le système d'exploitation comme étant stables lors des redémarrages ou des rebranchements de périphériques.

busport = regex

OPTIONNEL, NON RECOMMANDÉ.

Si supporté par le matériel, le système d'exploitation et libusb dans le déploiement particulier, cette option devrait permettre de spécifier les numéros de port physique sur un concentrateur USB, plutôt que les valeurs d'énumération logique des périphériques, et en retour — cela devrait être moins volatile lors des redémarrages ou des rebranchements. La valeur peut être vue dans la sortie de topologie USB de lsusb -tv sur les systèmes disposant de cet outil, par exemple.


Note
Cette option n'est pas pratiquement supportée par certaines constructions NUT (elle devrait alors être ignorée avec un avertissement), et pas par tous les systèmes sur lesquels NUT peut s'exécuter.

allow_duplicates

OPTIONNEL, NON RECOMMANDÉ.

Si vous avez plusieurs appareils onduleurs qui ne peuvent pas être identifiés de manière unique par les options ci-dessus (par exemple, seul le VID:PID peut y être découvert), ce drapeau permet à chaque instance de pilote où il est défini de prendre la première correspondance si elle est disponible, ou de continuer à en essayer une autre.

Normalement, l'initialisation du pilote s'arrêterait à ce stade en déclarant "Ressource occupée" ou une erreur similaire, en supposant que le périphérique autrement correctement identifié est unique — et qu'un autre processus le gère déjà.


Avertissement
Cette fonctionnalité est intrinsèquement non déterministe ! L'association du nom de l'instance du pilote avec le périphérique réel peut varier entre les exécutions !

Si vous voulez seulement savoir qu'au moins un de vos onduleurs sans nom est en ligne, cette option peut aider.

Si vous devez vraiment savoir lequel, cela ne fonctionnera pas !

usb_set_altinterface = bAlternateSetting

Force un appel redondant à usb_set_altinterface(), en particulier si nécessaire pour les périphériques servant plusieurs rôles USB où l'onduleur n'est pas représenté par l'interface numéro 0 (par défaut).

usb_config_index, usb_hid_rep_index, usb_hid_desc_index, usb_hid_ep_in, usb_hid_ep_out

Force l'utilisation d'indices d'interface, de points de terminaison, de descripteurs, etc. spécifiques, plutôt que de prendre la valeur par défaut 0 (rarement d'autres valeurs dans certains pilotes pour certains périphériques connus pour utiliser des numéros non nuls). Spécifié comme un nombre hexadécimal.

En règle générale, pour la découverte de usb_hid_desc_index, vous pouvez voir de plus grandes valeurs wDescriptorLength (environ 600 octets ou plus) dans les rapports de lsusb ou d'outils similaires.

LIBUSB_DEBUG = ENTIER

Le dépannage au moment de l'exécution des pilotes NUT capables d'USB peut impliquer non seulement d'augmenter la verbosité de débogage commune de NUT (par exemple, en utilisant le réglage DEBUG_MIN dans ups.conf(5) ou des commandes de protocole pour modifier la valeur de debug du pilote), mais peut également bénéficier du débogage spécifique à LibUSB.

Pour ce dernier, vous pouvez définir l'option de pilote LIBUSB_DEBUG ; alternativement, vous pouvez classiquement exporter la variable d'environnement LIBUSB_DEBUG avant de démarrer un programme de pilote NUT (peut être défini et "exporté" dans le script d'initialisation du pilote ou la méthode de service, peut-être via nut.conf(5)), à une valeur numérique telle que 4 ("Tous les messages sont émis").

Pour plus de détails, y compris les valeurs actuellement supportées pour votre version de la bibliothèque, voir par exemple :

•https://libusb.sourceforge.io/api-1.0/
•https://libusb.sourceforge.io/api-1.0/group__libusb__lib.html

sous-pilote=regex

Sélectionne manuellement le sous-pilote HID USB pour le périphérique, lorsque la correspondance automatique par les attributs du périphérique ne suffit pas (par exemple, pour de nouveaux périphériques pour lesquels aucune paire vendorid/productid n'a été intégrée à un pilote - mais un support HID USB courant est anticipé, ou pour des périphériques aux capacités différentes avec les mêmes puces d'interface, notamment "phoenixtec/liebert" et "mge").

Exécutez le programme du pilote avec l'option --help pour voir la liste exacte des valeurs de sous-pilote qu'il reconnaîtrait actuellement.


Note
Cette option vérifie d'abord les correspondances exactes des chaînes d'identification du sous-pilote, telles que "TrippLite HID 0.85" (qui sont sujettes à la détérioration par bit), et s'il n'y a pas de correspondance exacte, elle réessaie avec une expression régulière étendue insensible à la casse.

Note
Lorsque vous utilisez cette option, il est obligatoire de spécifier également les paramètres de correspondance vendorid et productid.

bas batt=num

Définit le pourcentage auquel l'onduleur considérera la charge de la batterie comme étant critique, pouvant entraîner une situation de coupure forcée (FSD).

Cette valeur est généralement dictée par le périphérique onduleur, bien qu'il existe une valeur par défaut de repli de 30 (en pourcentage). Modifier cette valeur peut être utile lorsque l'onduleur la définit à un pourcentage inférieur à celui prévu.

delai-arret=num

Définit le délai avant que l'onduleur ne s'éteigne après l'envoi de la commande d'arrêt d'alimentation (via le commutateur -k).

La valeur par défaut est de 20 (en secondes), ou 60 pour les périphériques CPS. Habituellement, cela doit être inférieur à delai-marche, mais le pilote ne vous avertira pas au démarrage si ce n'est pas le cas.

Notez que de nombreux modèles Cyber Power Systems (CPS) ont tendance à diviser ce délai par 60 et à arrondir à l'inférieur, donc la valeur minimale advisée est de 60 pour éviter une extinction immédiate après que NUT ait envoyé la commande d'arrêt à l'onduleur. Plus de détails ci-dessous.

delai-marche=num

Définit le délai pour que l'onduleur se rallume au cas où l'alimentation reviendrait après l'envoi de la commande d'arrêt, mais avant l'arrêt effectif. Cela garantit que les machines connectées à l'onduleur sont, dans tous les cas, redémarrées après une coupure de courant.

La valeur par défaut est de 30 (en secondes), ou 120 pour les périphériques CPS. Habituellement, cela doit être supérieur à delai-arret, mais le pilote ne vous avertira pas au démarrage si ce n'est pas le cas. Certains onduleurs redémarreront quoi qu'il arrive, même si l'alimentation est (toujours) coupée au moment où ce délai expire. Dans ce cas, vous pourriez vérifier si le réglage delai-marche = -1 dans ups.conf aide.

Notez que de nombreux modèles CPS ont tendance à diviser ce délai par 60 et à arrondir à l'inférieur, donc la valeur minimale conseillée est de 120 pour permettre un court délai entre l'arrêt de l'onduleur et le retour de l'alimentation. Selon les déclarations de support (pour au moins certains modèles CPS), "nos systèmes d'onduleurs ne sont pas en mesure de configurer le délai de mise sous tension".

freq-sonde=num

Définit la fréquence de sondage pour les mises à jour complètes, en secondes. Comparé aux mises à jour rapides effectuées toutes les "intervalles-sonde" (cette dernière option est décrite dans ups.conf(5)), l'intervalle "freq-sonde" est pour le sondage des variables moins critiques. La valeur par défaut est de 30 (en secondes), ou 12 secondes pour les périphériques CPS.

Note
Ce réglage est différent de POLLFREQ pris en charge par upsmon(8) (pour plus de détails, voir son upsmon.conf(5)).

sonde-seulement

Si ce drapeau est activé, le pilote n'utilisera pas les transferts Interrupt In pendant les cycles plus courts de "intervalles-sonde" (non recommandé, mais nécessaire si ces rapports sont défectueux sur votre onduleur).

tolerance-interrupt-pipe-sans-evenements=num

Définit la tolérance pour le nombre de fois consécutives où nous pourrions avoir "Got 0 HID objects" en utilisant le mode d'interruption USB ? Cela peut normalement être dû à un périphérique n'ayant rien d'urgent à signaler, donc la valeur par défaut est -1 et cette situation n'est traitée d'aucune manière spéciale. Cependant, avec certains périphériques, cela a été observé en conjonction avec un contrôleur gelé, où seule une reconnexion du pilote a rétabli l'échange de données (par exemple, APC BXnnnnMI) - dans de tels cas, vous pourriez vouloir utiliser une valeur non négative raisonnable ici.

batterie-decharge-en-ligne

Si ce drapeau est activé, le pilote traitera le statut OL+DISCHRG comme hors ligne/sur batterie.

Pour la plupart des périphériques, cette combinaison signifie un étalonnage ou une maintenance similaire ; cependant, certains modèles d'onduleurs (par exemple, CyberPower UT series) émettent OL+DISCHRG lorsque l'alimentation du secteur est perdue - et nécessitent cette option pour gérer les coupures.

decharge-en-ligne

OBSOLÈTE, ancien nom pour batterie-decharge-en-ligne décrit ci-dessus.

calibrage-decharge-en-ligne

Si ce drapeau est activé, le pilote traitera le statut OL+DISCHRG comme en mode étalonnage. Certains modèles d'onduleurs (par exemple, APC ont été vus le faire) rapportent OL+DISCHRG lorsqu'ils sont en mode d'étalonnage. Cela se produit généralement après quelques secondes indiquant également un état OFF, pendant que le matériel passe en mode batterie.

Note
Si cela prend trop de temps sur votre périphérique qu'une coupure soit émise, vous pourriez vouloir examiner l'option upsmon OFFDURATION pour filtrer les valeurs temporaires de "OFF administratif" comme n'étant pas une perte d'alimentation pour la charge alimentée.

seuil-journal-decharge-en-ligne=num

Définit la fréquence minimale (en secondes) à laquelle des avertissements seraient émis pour une combinaison de statuts de périphérique OL+DISCHRG non gérée autrement. Les valeurs négatives désactivent les messages répétés séquentiellement (lorsque cet état apparaît et persiste).

Si le périphérique ne rapporte pas battery.charge, la valeur par défaut est de 30 secondes (assez fréquent, au cas où la combinaison de statuts rapportée par l'onduleur refléterait une mauvaise condition d'alimentation et donc que la situation serait urgente).

S'il rapporte battery.charge, par défaut les notifications répétées ne seraient enregistrées que si cette charge est différente de celle lors de l'émission du message précédent (par exemple, lorsque la batterie est réellement en décharge).

Si cette option est définie et que battery.charge est correctement rapporté, l'une ou l'autre de ces règles permet à la notification d'être enregistrée.

seuil-hovercharge-journal-decharge-en-ligne=num

Voir les détails dans seuil-journal-decharge-en-ligne et la description du limitation des messages de journalisation basée sur battery.charge ci-dessus. Cette option ajoute un concept de "maintien" par l'onduleur d'une charge de batterie à un niveau jugé sûr pour sa chimie, et ne force pas sa charge complète tout le temps. Tant que la valeur actuelle de battery.charge reste égale ou supérieure à ce pourcentage seuil (par défaut 100), la journalisation du message OL+DISCHRG n'est pas déclenchée par des variations de la charge.

delai-journal-lbrb=num

Définit le délai pour définir les statuts (et les messages de journalisation) concernant l'entrée du périphérique dans l'état LB ou LB+RB.

Certains modèles ou versions de firmware d'onduleurs APC BXnnnnMI (signalés en 2023-2024), ou modèles d'onduleurs APC BVKnnnnM2, ou APC BKnnnnM2-CH (modèle réservé au marché chinois), rapportent fréquemment des états de "batterie faible", "remplacer la batterie" et "tout va bien" qui changent rapidement en quelques secondes, parfois (mais pas toujours) précédés par OL+DISCHRG (probablement un étalonnage).

Ce réglage permet au pilote d'ignorer les états de courte durée et de ne faire attention que s'ils persistent plus longtemps que ce réglage (et que l'état d'alimentation du périphérique est OL).

delai-journal-lbrb-sans-calibrage

Définit l'application de delai-journal-lbrb même si le périphérique n'est pas en cours de calibrage.

desactiver-correction-rapport-desc

Définit pour désactiver les corrections pour l'encodage USB défectueux, etc., que nous appliquons par défaut sur certains modèles (fournisseurs/produits) qui ont été signalés comme ne respectant pas strictement le protocole. Ce drapeau permet de désactiver la fonctionnalité dans des configurations de périphériques particulières.

Il est toujours possible que les fournisseurs publient finalement des firmwares corrigés, ou réutilisent des identifiants par lesquels nous identifions des périphériques suspects défectueux pour des produits sans rapport, donc le traitement de ces corrections serait une perte de temps là-bas.

Il est également toujours possible que les corrections NUT causent des problèmes sur certains périphériques, que ce soit en raison de bogues NUT ou parce que l'implémentation du protocole du fournisseur est défectueuse à plus d'un endroit.

ordre-octets-secours-powercom-sdcmd

Le code original du sous-pilote PowerCOM HID (jusqu'à la version 0.7) envoyait les commandes d'arrêt et de maintien d'arrêt de l'onduleur dans un ordre d'octets incorrect, par rapport à ce qui est nécessaire pour les périphériques réels rencontrés sur le terrain en 2024. L'ordre des octets est corrigé pour satisfaire les nouveaux périphériques par défaut depuis la version 0.71. Au cas où il existerait différents firmwares avec des comportements opposés, nous fournissons ce sélecteur pour utiliser l'ancien comportement dans un déploiement particulier. Peut-être que c'était juste un bug et que personne n'a besoin de ce secours...

explorer

Avec cette option, le pilote se connectera à n'importe quel périphérique, y compris ceux qui ne sont pas encore pris en charge. Cela doit toujours être combiné avec l'option "vendorid". Dans ce mode, le pilote ne fera rien d'utile, à part imprimer des informations de débogage (généralement utilisé avec -DD).

maxrapport

Avec cette option, le pilote active un ajustement pour contourner les firmwares défectueux renvoyant une longueur de rapport HID invalide. Certaines unités APC Back-UPS sont connues pour avoir ce bug.

interruptonly

Si ce drapeau est activé, le pilote ne sondra pas l'onduleur. Cela implique également l'utilisation des objets marqués INPUT. Certaines unités Powercom nécessitent cette option.

taille-interruption=num

Limite le nombre d'octets à lire depuis le tuyau d'interruption. Pour certaines unités Powercom, cette option devrait être égale à 8.

attendre-avant-reconnexion=num

Le pilote tente automatiquement de se reconnecter à l'onduleur en cas d'erreur inattendue. Ce paramètre (en secondes) lui permet d'attendre avant de tenter la reconnexion. La valeur par défaut est 0.

Note
par exemple, il a été constaté que le firmware de l'onduleur Eaton MGE Ellipse Max 1500 FR cesse de répondre toutes les quelques heures, ce qui amène le pilote usbhid-ups à détecter une erreur de mémoire insuffisante libusb ; dans ce cas, lorsque le pilote usbhid-ups tente de se reconnecter trop tôt, l'activité amenait parfois le firmware de l'onduleur à planter et à couper la charge immédiatement ! La définition de ce paramètre à 30 secondes a résolu ce problème (tandis que 20 secondes n'étaient pas suffisantes).

INSTALLATION

Ce pilote peut ne pas être intégré par défaut. Vous pouvez le compiler en installant les prérequis et en utilisant configure --with-usb=oui. Notez que cela installera également d'autres pilotes USB.

Vous devez également installer manuellement les fichiers hotplug hérités (libhidups et libhid.usermap, généralement dans /etc/hotplug/usb/), ou le fichier udev (nut-usbups.rules, généralement dans /etc/udev/rules.d/) pour résoudre le problème des paramètres d'autorisation. Pour plus d'informations, référez-vous aux fichiers scripts/hotplug/README.adoc ou scripts/udev/README.adoc dans les sources de NUT.

IMPLÉMENTATION

Sélectionner un UPS spécifique

Comme mentionné ci-dessus, le pilote ignore la valeur "port" dans ups.conf.

Contrairement aux versions précédentes de ce pilote, il est désormais possible de contrôler plusieurs unités UPS simultanément avec des instances de ce pilote exécutées en parallèle, à condition qu'elles puissent être distinguées en définissant une combinaison des options de correspondance d'appareils.

Par exemple :

[mge]
        driver = usbhid-ups
        port = auto
        vendorid = 0463
[tripplite]
        driver = usbhid-ups
        port = auto
        vendorid = 09ae

Pour surveiller des appareils utilisant la même identification de vendeur et de produit (par exemple, deux appareils du même modèle), vous devrez trouver un critère de correspondance unique fiable :

•Le numéro de série est la meilleure option, s'il est rempli.
•Le bus/périphérique/port du bus au niveau de la liaison peut être peu fiable (en raison du ré-énumération à la volée par le système d'exploitation).
•Si rien d'autre n'aide, allow_duplicates peut être une option dans certains cas.

Interrogation USB et transferts interruptibles

Le pilote usbhid-ups a deux intervalles d'interrogation. L'option de configuration "pollinterval" contrôle ce qui peut être considéré comme la "boucle interne", où le pilote interroge et attend brièvement les rapports "interrupt". L'option "pollfreq" est pour des mises à jour moins fréquentes d'un plus grand ensemble de valeurs, et à ce titre, nous recommandons de définir cet intervalle à plusieurs fois la valeur de "pollinterval".

De nombreux UPS répondent à un transfert USB Interrupt In avec des rapports HID correspondant aux valeurs qui ont changé. Cela évite au pilote d'avoir à interroger chaque valeur individuellement avec des transferts de contrôle USB. Comme les indicateurs d'état OB et LB sont importants pour un arrêt propre, le pilote interroge également explicitement les chemins HID correspondant à ces bits d'état pendant la période de temps "pollinterval" interne. L'option "pollonly" peut être utilisée pour sauter les transferts Interrupt In s'ils ne fonctionnent pas.

PROBLÈMES CONNUS ET BOGUES

L'UPS rapporte 65535 sec (ou 18:12:15) de batterie.runtime capability

D'après plusieurs rapports, il semble que certains appareils ne puissent pas signaler plus qu'une valeur entière non signée de 16 bits dans le champ standard pour le temps d'exécution restant (des champs étendus du vendeur peuvent exister mais être inconnus des tables de mappage dans votre version actuelle du pilote NUT), ou retournent -1 pour une erreur qui est ensuite traitée comme une valeur entière non signée de 16 bits de 65535.

Selon certaines discussions sur les problèmes, le passage d'un test de batterie (étalonnage) peut aider l'UPS à réestimer le temps plus correctement.

Ce problème peut également être lié à un UPS de grande capacité très peu chargé. Dans certains cas, la documentation du vendeur indique explicitement que le calcul de l'autonomie n'est pas fiable avec des charges inférieures à par exemple 10 %.

Timeout répétitif et obsolescence

Certains modèles ont tendance à ne pas répondre avec la fréquence d'interrogation par défaut. Le résultat est que votre journal système contiendra de nombreux messages comme :

usb 2-1: control timeout on ep0in
usb 2-1: usbfs: USBDEVFS_CONTROL failed cmd usbhid-ups rqt 128 rq 6 len 256
ret -110

Dans ce cas, modifiez simplement le paramètre général "pollinterval" à une valeur plus élevée (par exemple, 10 secondes). Cela devrait résoudre le problème.

Notez que si vous augmentez "pollinterval" au-delà de 10 ou 15 secondes, vous pourriez également vouloir augmenter "pollfreq" du même facteur.

Avec certains appareils et systèmes d'exploitation, notamment les ID de vendeur USB MGE/Eaton (0x0463) sur certaines versions du noyau Linux, vous pourriez rencontrer une mauvaise interaction avec le mécanisme "USB HID quirk", qui empêche Linux de voir l'appareil comme un hid-generic d'abord, pour le remettre plus tard à un pilote NUT. Pour plus de détails, voir le document FAQ de NUT. Ce "quirk" particulier peut être réglé avec un paramètre de démarrage du noyau (via GRUB etc.) :

usbhid.quirks=0x0463:0xffff:0x08

Inversement, certains contrôleurs matériels peuvent "s'endormir" s'ils ne sont pas contactés pendant trop longtemps ; les appareils CPS sont couramment associés à un tel comportement. Dans ce cas, envisagez d'activer le drapeau pollonly et/ou de garder pollfreq et/ou pollinterval petits.

Got EPERM: Operation not permitted au démarrage du pilote

Vous avez oublié d'installer les fichiers hotplug, comme expliqué dans la section INSTALLATION ci-dessus. N'oubliez pas de redémarrer hotplug pour qu'il applique ces modifications.

Arrêts automatiques non surveillés

Le matériel qui a été utilisé pour le développement de ce pilote est très probablement différent de ce que vous avez, et tous les fabricants ne suivent pas les spécifications de la classe de périphériques d'alimentation USB HID à la lettre. Vous ne voulez pas découvrir que le vôtre a des problèmes à ce niveau lorsqu'une panne de courant frappe votre salle de serveurs et que vous n'êtes pas là pour redémarrer manuellement vos serveurs.

Si vous comptez sur l'UPS pour arrêter vos systèmes en cas de panne de courant et pour les redémarrer lorsque le courant revient, vous devez tester cela. Vous pouvez le faire en exécutant upsmon -c fsd. Avec le secteur présent, cela devrait arrêter vos systèmes puis cycler l'alimentation pour les redémarrer. Si vous faites de même sans le secteur, cela devrait faire de même, mais dans ce cas, les sorties resteront éteintes jusqu'à ce que le secteur soit rétabli.

L'UPS coupe l'alimentation trop tôt

Notez que de nombreux modèles Cyber Power Systems (CPS) ont tendance à diviser offdelay par 60 et à arrondir à l'inférieur, de sorte que la valeur minimale conseillée est de 60 (secondes) pour éviter de couper l'alimentation immédiatement après que NUT ait envoyé la commande d'arrêt à l'UPS.

Pour de nombreux UPS Cyberpower, offdelay doit être défini sur 0 pour un comportement normal (la charge est restaurée lorsque le courant alternatif revient). Définir offdelay supérieur à 0 redémarrera la charge UPS indépendamment du retour du courant, et définir offdelay inférieur à 0 désactivera la fonction de mise sous tension automatique de l'UPS, maintenant la charge éteinte même lorsque le courant revient.

L'UPS ne définit pas battery.charge.low mais dit OK

Notez que de nombreux modèles Cyber Power Systems (CPS) ont tendance à n'autoriser que certaines valeurs pour battery.charge.low et tout ce qui sort de l'ensemble des valeurs autorisées est arrondi ou ignoré.

Une boucle shell comme celle-ci peut vous aider à cartographier les valeurs autorisées :

for i in `seq 90 -1 0`; do echo "set to $i"; \
    upsrw -s battery.charge.low=$i -u * -p * cps-big; \
    sleep 1; upsc cps-big battery.charge.low; echo ""; \
done

Par exemple, pour le modèle CPS PR1000LCDRTXL2U, les seules valeurs autorisées sont [60,55,50,45,40,35,30,25,20] et dans certains cas, votre UPS peut effectivement ne pas prendre en charge une valeur de 10 pour le réglage battery.charge.low.

usbhid-ups(8)

usbhid-ups - Périphérique d'alimentation sans interruption (UPS) compatible USB HID

NOM

usbhid-ups - Périphérique d'alimentation sans interruption (UPS) compatible USB HID

SYNTAXIS

usbhid-ups [-DD] [-i input] [-o output] [-p pollfreq] [-s startup] [-x extra arguments]

DESCRIPTION

Le pilote usbhid-ups gère les périphériques d'alimentation sans interruption (UPS) compatibles USB HID. Ces UPS se connectent généralement à un port USB et n'utilisent pas de protocole de communication série propriétaire. Ce pilote est conçu pour fonctionner avec le cadre NUT (Network UPS Tools).

MATÉRIEL

La prise en charge du matériel est généralement déterminée par le noyau Linux et les pilotes USB HID. usbhid-ups suppose que le noyau a déjà détecté et configuré l'UPS comme un périphérique HID standard. Les UPS courants prenant en charge ce pilote incluent certains modèles de CyberPower, APC, et d'autres fabricants.

ARGUMENTS SUPPLÉMENTAIRES

Les arguments supplémentaires sont transmises directement à l'infrastructure NUT. Cela peut inclure des options pour spécifier les capteurs à surveiller, les valeurs de seuil, et le comportement en cas de perte de communication.

INSTALLATION

Pour utiliser usbhid-ups, vous devez installer le paquet NUT (Network UPS Tools) sur votre système. Le pilote usbhid-ups est généralement inclus dans les distributions binaires de NUT ou peut être compilé à partir des sources.

Une fois NUT installé, vous devrez configurer le fichier ups.conf pour reconnaître votre UPS. Vous devrez spécifier le type de pilote comme usbhid-ups et fournir les identifiants USB appropriés si nécessaire.

Exemple de configuration dans ups.conf :

[mon_ups]
    driver = usbhid-ups
    port = auto
    # usbhid-ups ne nécessite pas d'argument de port spécifique comme les ports série.
    # Cependant, vous pouvez spécifier un ID de périphérique si plusieurs UPS sont connectés :
    # device = VID:PID
    desc = "Mon UPS USB HID"

IMPLÉMENTATION

usbhid-ups interroge périodiquement l'UPS via l'interface USB HID pour obtenir des informations sur son état, telles que la charge de la batterie, l'état de l'alimentation secteur, et les événements (par exemple, coupure de courant, batterie faible). Ces informations sont ensuite transmises au démon upsd de NUT pour traitement et mise à disposition des clients.

PROBLÈMES CONNUS ET BUGS

Certains UPS USB HID peuvent ne pas signaler toutes les informations attendues, ou peuvent avoir des formats de rapport légèrement différents. Cela peut entraîner une prise en charge incomplète ou des erreurs dans l'affichage des données NUT.

Il est recommandé de consulter la documentation de NUT et les listes de diffusion pour connaître les problèmes spécifiques à votre modèle d'UPS.

HISTORIQUE

Le pilote usbhid-ups a été développé pour prendre en charge une nouvelle génération d'UPS utilisant le standard USB HID, offrant une alternative aux pilotes série propriétaires.

AUTEURS

Le projet Network UPS Tools (NUT) est maintenu par une communauté de développeurs. Pour une liste complète des contributeurs, veuillez consulter la documentation du projet NUT.
