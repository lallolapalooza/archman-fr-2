uri(7) Informations diverses sur le manuel uri(7)

NOM

uri, url, urn - identifiant de ressource uniforme (URI), incluant une URL ou une URN

SYNTAXE

URI = [ URI_absolue | URI_relative ] [ "#" fragment ]
URI_absolue = schéma ":" ( partie_hiérarchique | partie_opaque )
URI_relative = ( chemin_réseau | chemin_absolu | chemin_relatif ) [ "?" requête ]
schéma = "http" | "ftp" | "gopher" | "mailto" | "news" | "telnet" | "file" | "ftp" | "man" | "info" | "whatis" | "ldap" | "wais" | ...
partie_hiérarchique = ( chemin_réseau | chemin_absolu ) [ "?" requête ]
chemin_réseau = "//" autorité [ chemin_absolu ]
chemin_absolu = "/" segments_chemin
chemin_relatif = segment_relatif [ chemin_absolu ]

DESCRIPTION

Un Identifiant de Ressource Uniforme (URI) est une courte chaîne de caractères identifiant une ressource abstraite ou physique (par exemple, une page web). Une Localisation de Ressource Uniforme (URL) est une URI qui identifie une ressource par son mécanisme d'accès principal (par exemple, sa « localisation » réseau), plutôt que par son nom ou un autre attribut de cette ressource. Un Nom de Ressource Uniforme (URN) est une URI qui doit rester globalement unique et persistante même lorsque la ressource cesse d'exister ou devient indisponible.

Les URI sont le moyen standard de nommer les destinations de liens hypertexte pour des outils tels que les navigateurs Web. La chaîne « http://www.kernel.org » est une URL (et donc aussi une URI). Beaucoup de gens utilisent le terme URL de manière imprécise comme synonyme d'URI (bien que techniquement les URL soient un sous-ensemble des URI).

Les URI peuvent être absolues ou relatives. Un identifiant absolu fait référence à une ressource indépendamment du contexte, tandis qu'un identifiant relatif fait référence à une ressource en décrivant la différence par rapport au contexte actuel. Dans une référence de chemin relatif, les segments de chemin complets « . » et « .. » ont des significations spéciales : « le niveau hiérarchique actuel » et « le niveau au-dessus de ce niveau hiérarchique », respectivement, tout comme ils le font dans les systèmes de type UNIX. Un segment de chemin contenant un caractère deux-points ne peut pas être utilisé comme premier segment d'un chemin d'URI relatif (par exemple, « this:that »), car il serait confondu avec un nom de schéma ; précédez de tels segments avec ./ (par exemple, « ./this:that »). Notez que les descendants de MS-DOS (par exemple, Microsoft Windows) remplacent les deux-points des noms de périphérique par la barre verticale (« | ») dans les URI, donc « C: » devient « C| ».

Un identifiant de fragment, s'il est inclus, fait référence à une partie nommée particulière (fragment) d'une ressource ; le texte après un « # » identifie le fragment. Une URI commençant par « # » fait référence à ce fragment dans la ressource actuelle.

UTILISATION

Il existe de nombreux schémas d'URI différents, chacun avec des règles et des significations supplémentaires spécifiques, mais ils sont intentionnellement conçus pour être aussi similaires que possible. Par exemple, de nombreux schémas d'URL autorisent l'autorité à avoir le format suivant, appelé ici un serveur_ip (les crochets indiquent ce qui est facultatif) :

serveur_ip = [utilisateur [ : mot_de_passe ] @ ] hôte [ : port]

Ce format vous permet d'insérer éventuellement un nom d'utilisateur, un utilisateur plus un mot de passe, et/ou un numéro de port. L'hôte est le nom de l'ordinateur hôte, soit son nom tel que déterminé par DNS, soit une adresse IP (nombres séparés par des points). Ainsi, l'URI http://fred:fredpassword@example.com:8080/ se connecte à un serveur Web sur l'hôte example.com en tant que fred (en utilisant fredpassword) via le port 8080. Évitez d'inclure un mot de passe dans une URI si possible en raison des nombreux risques de sécurité liés à l'écriture d'un mot de passe. Si l'URL fournit un nom d'utilisateur mais pas de mot de passe, et que le serveur distant demande un mot de passe, le programme interprétant l'URL devrait en demander un à l'utilisateur.

Voici quelques-uns des schémas les plus courants utilisés sur les systèmes de type UNIX et compris par de nombreux outils. Notez que de nombreux outils utilisant des URI ont également des schémas internes ou spécialisés ; consultez la documentation de ces outils pour plus d'informations sur ces schémas.

http - Serveur Web (HTTP)

http://serveur_ip/chemin
http://serveur_ip/chemin?requête

Il s'agit d'une URL accédant à un serveur Web (HTTP). Le port par défaut est 80. Si le chemin fait référence à un répertoire, le serveur Web choisira quoi renvoyer ; généralement, s'il existe un fichier nommé « index.html » ou « index.htm », son contenu est renvoyé ; sinon, une liste des fichiers du répertoire courant (avec les liens appropriés) est générée et renvoyée. Un exemple est http://lwn.net.

Une requête peut être donnée dans le format archaïque « isindex », consistant en un mot ou une phrase et n'incluant pas de signe égal (=). Une requête peut également être dans le format plus long « GET », qui contient une ou plusieurs entrées de requête de la forme clé=valeur séparées par le caractère ampersand (&). Notez que la clé peut être répétée plus d'une fois, bien qu'il appartienne au serveur Web et à ses programmes d'application de déterminer s'il y a un sens à cela. Il existe une interaction malheureuse avec HTML/XML/SGML et le format de requête GET ; lorsque de telles URI avec plusieurs clés sont intégrées dans des documents SGML/XML (y compris HTML), l'ampersand (&) doit être réécrit en &amp;. Notez que toutes les requêtes n'utilisent pas ce format ; les formulaires plus volumineux peuvent être trop longs pour être stockés comme URI, ils utilisent donc un mécanisme d'interaction différent (appelé POST) qui n'inclut pas les données dans l'URI. Voir la spécification Common Gateway Interface à http://www.w3.org/CGI pour plus d'informations.

ftp - Protocole de transfert de fichiers (FTP)

ftp://serveur_ip/chemin

Il s'agit d'une URL accédant à un fichier via le protocole de transfert de fichiers (FTP). Le port par défaut (pour le contrôle) est 21. Si aucun nom d'utilisateur n'est inclus, le nom d'utilisateur « anonymous » est fourni, et dans ce cas, de nombreux clients fournissent comme mot de passe l'adresse e-mail Internet du demandeur. Un exemple est <ftp://ftp.is.co.za/rfc/rfc1808.txt>.

gopher - Serveur Gopher

gopher://serveur_ip/type_gopher sélecteur
gopher://serveur_ip/type_gopher sélecteur%09recherche
gopher://serveur_ip/type_gopher sélecteur%09recherche%09chaîne_gopher+

Le port Gopher par défaut est 70. type_gopher est un champ d'un seul caractère pour indiquer le type Gopher de la ressource à laquelle l'URL fait référence. Le chemin entier peut également être vide, auquel cas le délimiteur « / » est également facultatif, et le type_gopher est « 1 » par défaut.

sélecteur est la chaîne de sélection Gopher. Dans le protocole Gopher, les chaînes de sélection Gopher sont une séquence d'octets qui peuvent contenir n'importe quels octets à l'exception de 09 hexadécimal (tabulation caractère US-ASCII), 0A hexadécimal (caractère US-ASCII LF), et 0D (caractère US-ASCII CR).

mailto - Adresse e-mail

mailto:adresse-e-mail

Il s'agit d'une adresse e-mail, généralement sous la forme nom@nom_hote. Voir mailaddr(7) pour plus d'informations sur le format correct d'une adresse e-mail. Notez que tout caractère % doit être réécrit en %25. Un exemple est <mailto:dwheeler@dwheeler.com>.

news - Groupe de discussion ou message de news

news:nom_groupe_de_discussion
news:id_message

Un groupe_de_discussion

Ce site n'est en aucun cas associé à Arch Linux ni affilié à ce projet. Le contenu est uniquement une traduction des pages de manuel d'Arch publiées sur man.archlinux.org.

URL SCHEMES

This document lists and describes the URL schemes that are commonly supported by browsers and other software.

news - Usenet news groups

news:newsgroup
news:message-id

The newsgroup name is a period-delimited hierarchical name, such as "comp.infosystems.www.misc". If newsgroup is "*" (as in news:*), it is used to refer to "all available news groups". An example is news:comp.lang.ada.

A message-id corresponds to the Message-ID of IETF RFC 1036, without the enclosing "<" and ">"; it takes the form unique@full_domain_name. A message identifier may be distinguished from a news group name by the presence of the "@" character.

telnet - Telnet login

telnet://ip_server/

The Telnet URL scheme is used to designate interactive text services that may be accessed by the Telnet protocol. The final "/" character may be omitted. The default port is 23. An example is <telnet://melvyl.ucop.edu/>.

file - Normal file

file://ip_server/path_segments
file:path_segments

This represents a file or directory accessible locally. As a special case, ip_server can be the string "localhost" or the empty string; this is interpreted as "the machine from which the URL is being interpreted". If the path is to a directory, the viewer should display the directory's contents with links to each containee; not all viewers currently do this. KDE supports generated files through the URL <file:/cgi-bin>. If the given file isn't found, browser writers may want to try to expand the filename via filename globbing (see glob(7) and glob(3)).

The second format (e.g., <file:/etc/passwd>) is a correct format for referring to a local file. However, older standards did not permit this format, and some programs don't recognize this as a URI. A more portable syntax is to use an empty string as the server name, for example, <file:///etc/passwd>; this form does the same thing and is easily recognized by pattern matchers and older programs as a URI. Note that if you really mean to say "start from the current location", don't specify the scheme at all; use a relative address like <../test.txt>, which has the side-effect of being scheme-independent. An example of this scheme is <file:///etc/passwd>.

man - Man page documentation

man:command-name
man:command-name(section)

This refers to local online manual (man) reference pages. The command name can optionally be followed by a parenthesis and section number; see man(7) for more information on the meaning of the section numbers. This URI scheme is unique to UNIX-like systems (such as Linux) and is not currently registered by the IETF. An example is <man:ls(1)>.

info - Info page documentation

info:virtual-filename
info:virtual-filename#nodename
info:(virtual-filename)
info:(virtual-filename)nodename

This scheme refers to online info reference pages (generated from texinfo files), a documentation format used by programs such as the GNU tools. This URI scheme is unique to UNIX-like systems (such as Linux) and is not currently registered by the IETF. As of this writing, GNOME and KDE differ in their URI syntax and do not accept the other's syntax. The first two formats are the GNOME format; in nodenames, all spaces are written as underscores. The second two formats are the KDE format; spaces in nodenames must be written as spaces, even though this is forbidden by the URI standards. It's hoped that in the future most tools will understand all of these formats and will always accept underscores for spaces in nodenames. In both GNOME and KDE, if the form without the nodename is used, the nodename is assumed to be "Top". Examples of the GNOME format are <info:gcc> and <info:gcc#G++_and_GCC>. Examples of the KDE format are <info:(gcc)> and <info:(gcc)G++ and GCC>.

whatis - Documentation search

whatis:string

This scheme searches the database of short (one-line) descriptions of commands and returns a list of descriptions containing that string. Only complete word matches are returned. See whatis(1). This URI scheme is unique to UNIX-like systems (such as Linux) and is not currently registered by the IETF.

ghelp - GNOME help documentation

ghelp:name-of-application

This loads GNOME help for the given application. Note that not much documentation currently exists in this format.

ldap - Lightweight Directory Access Protocol

ldap://hostport
ldap://hostport/
ldap://hostport/dn
ldap://hostport/dn?attributes
ldap://hostport/dn?attributes?scope
ldap://hostport/dn?attributes?scope?filter
ldap://hostport/dn?attributes?scope?filter?extensions

This scheme supports queries to the Lightweight Directory Access Protocol (LDAP), a protocol for querying a set of servers for hierarchically organized information (such as people and computing resources). See RFC 2255 for more information on the LDAP URL scheme. The components of this URL are:

hostport
the LDAP server to query, written as a hostname optionally followed by a colon and the port number. The default LDAP port is TCP port 389. If empty, the client determines which the LDAP server to use.
dn
the LDAP Distinguished Name, which identifies the base object of the LDAP search (see RFC 2253 section 3).
attributes
a comma-separated list of attributes to be returned; see RFC 2251 section 4.1.5. If omitted, all attributes should be returned.
scope
specifies the scope of the search, which can be one of "base" (for a base object search), "one" (for a one-level search), or "sub" (for a subtree search). If scope is omitted, "base" is assumed.
filter
specifies the search filter (subset of entries to return). If omitted, all entries should be returned. See RFC 2254 section 4.
extensions
a comma-separated list of type=value pairs, where the =value portion may be omitted for options not requiring it. An extension prefixed with a '!' is critical (must be supported to be valid), otherwise it is noncritical (optional).

LDAP queries are easiest to explain by example. Here's a query that asks ldap.itd.umich.edu for information about the University of Michigan in the U.S.:

ldap://ldap.itd.umich.edu/o=University%20of%20Michigan,c=US

To just get its postal address attribute, request:

ldap://ldap.itd.umich.edu/o=University%20of%20Michigan,c=US?postalAddress

To ask a host.com at port 6666 for information about the person with common name (cn) "Babs Jensen" at University of Michigan, request:

ldap://host.com:6666/o=University%20of%20Michigan,c=US??sub?(cn=Babs%20Jensen)

wais - Wide Area Information Servers

wais://hostport/database
wais://hostport/database?search
wais://hostport/database/wtype/wpath

This scheme designates a WAIS database, search, or document (see IETF RFC 1625 for more information on WAIS). Hostport is the hostname, optionally followed by a colon and port number (the default port number is 210).

The first form designates a WAIS database for searching. The second form designates a particular search of the WAIS database database. The third form designates a particular document within a WAIS database to be retrieved. wtype is the WAIS designation of the type of the object, and wpath is the WAIS document-id.

other schemes

There are many other URI schemes. Most tools that accept URIs support a set of internal URIs (e.g., Mozilla has the about: scheme for internal information, and the GNOME help browser has the toc: scheme for various starting locations). There are many schemes that have been defined but are not as widely used at the current time (e.g., prospero). The nntp: scheme is deprecated in favor of the news: scheme. URNs are to be supported by the urn: scheme, with a hierarchical name space (e.g., urn:ietf:... would identify IETF documents); at this time, URNs are not widely implemented. Not all tools support all schemes.

Character encoding

URIs use a limited number of characters so that they can be typed in and used in a variety of situations.

The following characters are reserved, that is, they may appear in a URI but their use is limited to their reserved purpose (conflicting data must be escaped before forming the URI):


; / ? : @ & = + $ ,

Unreserved characters may be included in a URI. Unreserved characters include uppercase and lowercase Latin letters, decimal digits, and the following limited set of punctuation marks and symbols:


- _ . ! ~ * ' ( )

All other characters must be escaped. An escaped octet is encoded as a character triplet, consisting of the percent character "%" followed by the two hexadecimal digits representing the octet code (you can use uppercase or lowercase letters for the hexadecimal digits). For example, a blank space must be escaped as "%20", a tab character as "%09", and the "&" as "%26". Because the percent "%" character always has the reserved purpose of being the escape indicator, it must be escaped as "%25". It is common practice to escape space characters as the plus symbol (+) in query text; this practice isn't uniformly defined in the relevant RFCs (which recommend %20 instead) but any tool accepting URIs with query text should be prepared for them. URI(7)
Français

NOM

URI - conventions et formats pour les identificateurs de ressources uniformes

SYNTAXE

URI
URL

DESCRIPTION

Un identificateur de ressources uniforme (URI) est une chaîne de caractères qui identifie une ressource de manière unique. Une URL (Localisateur de Ressources Uniforme) est un sous-ensemble d'URI qui spécifie à la fois un identificateur et un mécanisme d'accès à cette ressource, typiquement via un réseau.

Les caractères dans un URI sont divisés en caractères réservés et non réservés. Les caractères réservés ont une signification spéciale dans le contexte de l'URI, tandis que les caractères non réservés n'en ont pas. Les caractères non réservés peuvent être échappés sans changer la sémantique de l'URI, mais cela ne devrait pas être fait à moins que l'URI ne soit utilisé dans un contexte qui n'autorise pas le caractère non échappé. Par exemple, « %7e » est parfois utilisé à la place de « ~ » dans le chemin d'une URL HTTP, mais les deux sont équivalents pour une URL HTTP.

Pour les URI qui doivent gérer des caractères en dehors de l'ensemble des caractères US ASCII, la spécification HTML 4.01 (section B.2) et la RFC 3986 de l'IETF (dernier paragraphe de la section 2.5) recommandent l'approche suivante :

(1)
traduire les séquences de caractères en UTF-8 (RFC 3629 de l'IETF) — voir utf-8(7) — et ensuite
(2)
utiliser le mécanisme d'échappement des URI, c'est-à-dire, utiliser l'encodage %HH pour les octets non sécurisés.

Écrire un URI

Lorsqu'ils sont écrits, les URI doivent être placés entre guillemets doubles (par exemple, « http://www.kernel.org »), encadrés par des chevrons (par exemple, http://lwn.net), ou placés sur une ligne séparée. Un avertissement pour ceux qui utilisent des guillemets doubles : ne déplacez jamais la ponctuation superflue (telle que le point final d'une phrase ou la virgule dans une liste) à l'intérieur d'un URI, car cela changerait la valeur de l'URI. Utilisez plutôt des chevrons, ou passez à un système de citation qui n'inclut jamais de caractères superflus à l'intérieur des guillemets. Ce dernier système, appelé système de citation « nouveau » ou « logique » par les « Hart's Rules » et l'« Oxford Dictionary for Writers and Editors », est une pratique préférée en Grande-Bretagne et dans diverses langues européennes. Les anciens documents suggéraient d'insérer le préfixe « URL : » juste avant l'URI, mais cette forme n'a jamais pris.

La syntaxe des URI a été conçue pour être sans ambiguïté. Cependant, à mesure que les URI sont devenus courants, les médias traditionnels (télévision, radio, journaux, panneaux publicitaires, etc.) ont de plus en plus utilisé des références d'URI abrégées consistant uniquement en la partie autorité et chemin de la ressource identifiée (par exemple, <www.w3.org/Addressing>). Ces références sont principalement destinées à l'interprétation humaine plutôt qu'à la machine, avec l'hypothèse que des heuristiques basées sur le contexte sont suffisantes pour compléter l'URI (par exemple, les noms d'hôte commençant par « www » sont susceptibles d'avoir un préfixe URI de « http:// » et les noms d'hôte commençant par « ftp » un préfixe de « ftp:// »). De nombreuses implémentations clientes résolvent de manière heuristique ces références. Ces heuristiques peuvent changer avec le temps, en particulier lorsque de nouveaux schémas sont introduits. Étant donné qu'un URI abrégé a la même syntaxe qu'un chemin d'URL relatif, les références d'URI abrégées ne peuvent pas être utilisées là où les URI relatifs sont autorisés, et ne peuvent être utilisées qu'en l'absence d'une base définie (comme dans les boîtes de dialogue). N'utilisez pas d'URI abrégés comme liens hypertextes à l'intérieur d'un document ; utilisez le format standard tel que décrit ici.

NOTES

Tout outil acceptant des URI (par exemple, un navigateur Web) sur un système Linux devrait pouvoir gérer (directement ou indirectement) tous les schémas décrits ici, y compris les schémas man: et info:. Les gérer en invoquant un autre programme est acceptable et même encouragé.

Techniquement, le fragment ne fait pas partie de l'URI.

Pour savoir comment intégrer des URI (y compris des URL) dans un format de données, consultez la documentation de ce format. HTML utilise le format <A HREF="uri"> texte </A>. Les fichiers Texinfo utilisent le format @uref{uri}. Man et mdoc ont récemment ajouté la macro UR, ou incluent simplement l'URI dans le texte (les visualiseurs devraient pouvoir détecter :// comme faisant partie d'un URI).

Les environnements de bureau GNOME et KDE varient actuellement dans les URI qu'ils acceptent, en particulier dans leurs navigateurs d'aide respectifs. Pour lister les pages de manuel, GNOME utilise <toc:man> tandis que KDE utilise <man:(index)>, et pour lister les pages d'information, GNOME utilise <toc:info> tandis que KDE utilise <info:(dir)> (l'auteur de cette page de manuel préfère l'approche KDE ici, bien qu'un format plus régulier serait encore meilleur). En général, KDE utilise <file:/cgi-bin/> comme préfixe à un ensemble de fichiers générés. KDE préfère la documentation en HTML, accessible via <file:/cgi-bin/helpindex>. GNOME préfère le schéma ghelp pour stocker et trouver la documentation. Aucun des navigateurs ne gère les références file: vers des répertoires au moment de la rédaction, ce qui rend difficile la référence à un répertoire entier avec un URI consultable. Comme mentionné ci-dessus, ces environnements diffèrent dans la manière dont ils gèrent le schéma info:, probablement la variation la plus importante. On s'attend à ce que GNOME et KDE convergent vers des formats d'URI communs, et une future version de cette page de manuel décrira le résultat convergé. Les efforts pour aider à cette convergence sont encouragés.

Sécurité

Un URI ne pose pas en soi de menace pour la sécurité. Il n'y a aucune garantie générale qu'une URL, qui à un moment donné localisait une ressource donnée, continuera à le faire. Il n'y a pas non plus de garantie qu'une URL ne localisera pas une ressource différente à un moment ultérieur ; une telle garantie ne peut être obtenue qu'auprès de la ou des personnes contrôlant cet espace de noms et la ressource en question.

Il est parfois possible de construire une URL de telle sorte qu'une tentative d'exécution d'une opération apparemment inoffensive, telle que la récupération d'une entité associée à la ressource, entraînera en fait une opération à distance potentiellement dommageable. L'URL non sécurisée est généralement construite en spécifiant un numéro de port autre que celui réservé au protocole réseau en question. Le client contacte à l'insu un site qui exécute en fait un protocole différent. Le contenu de l'URL contient des instructions qui, lorsqu'elles sont interprétées selon ce autre protocole, provoquent une opération inattendue. Un exemple a été l'utilisation d'une URL gopher pour provoquer l'envoi d'un message non intentionnel ou d'usurpation via un serveur SMTP.

La prudence doit être de mise lors de l'utilisation de toute URL spécifiant un numéro de port autre que celui par défaut pour le protocole ; en particulier, lorsque c'est un numéro dans l'espace réservé.

Il faut prendre garde lorsqu'un URI contient des délimiteurs échappés pour un protocole donné (par exemple, les caractères CR et LF pour les protocoles telnet) à ce que ceux-ci ne soient pas déséchappés avant la transmission. Cela pourrait violer le protocole, mais éviterait que ces caractères ne soient utilisés pour simuler une opération ou un paramètre supplémentaire dans ce protocole, ce qui pourrait entraîner une opération à distance inattendue et potentiellement dangereuse.

Il est clairement déconseillé d'utiliser un URI contenant un mot de passe destiné à être secret. En particulier, l'utilisation d'un mot de passe dans le composant « userinfo » d'un URI est fortement déconseillée, sauf dans les rares cas où le paramètre « mot de passe » est destiné à être public.

BOGUES

La documentation peut être placée dans divers endroits, il n'existe donc actuellement pas de schéma URI approprié pour la documentation générale en ligne dans des formats arbitraires. Les références de la forme <file:///usr/doc/ZZZ> ne fonctionnent pas, car différentes distributions et les exigences d'installation locales peuvent placer les fichiers dans des répertoires différents (il peut être dans /usr/doc, ou /usr/local/doc, ou /usr/share, ou ailleurs). De plus, le répertoire ZZZ change généralement lorsqu'une version change (bien que le globbing de noms de fichiers puisse partiellement surmonter cela). Enfin, l'utilisation du schéma file: ne prend pas facilement en charge les personnes qui chargent dynamiquement la documentation à partir d'Internet (au lieu de charger les fichiers sur un système de fichiers local). Un futur schéma URI pourrait être ajouté (par exemple, « userdoc: ») pour permettre aux programmes d'inclure des références croisées vers une documentation plus détaillée sans avoir à connaître l'emplacement exact de cette documentation. Alternativement, une future version de la spécification du système de fichiers peut spécifier les emplacements des fichiers suffisamment pour que le schéma file: puisse localiser la documentation.

De nombreux programmes et formats de fichiers n'incluent pas de moyen d'incorporer ou d'implémenter des liens à l'aide d'URI.

De nombreux programmes ne peuvent pas gérer tous ces différents formats d'URI ; il devrait y avoir un mécanisme standard pour charger un URI arbitraire qui détecte automatiquement l'environnement de l'utilisateur (par exemple, texte ou graphique, environnement de bureau, préférences utilisateur locales et outils en cours d'exécution) et invoque le bon outil pour n'importe quel URI.
