uri(7) Manuel d'informations diverses uri(7)

NOM

uri, url, urn - Identifiant uniforme de ressource (URI), incluant un URL ou URN

SYNTAXE

URI = [ absoluteURI | relativeURI ] [ "#" fragment ]
absoluteURI = scheme ":" ( hierarchical_part | opaque_part )
relativeURI = ( net_path | absolute_path | relative_path ) [ "?" query ]
scheme = "http" | "ftp" | "gopher" | "mailto" | "news" | "telnet" | "file" | "ftp" | "man" | "info" | "whatis" | "ldap" | "wais" | ...
hierarchical_part = ( net_path | absolute_path ) [ "?" query ]
net_path = "//" authority [ absolute_path ]
absolute_path = "/" path_segments
relative_path = relative_segment [ absolute_path ]

DESCRIPTION

Un Identifiant Uniforme de Ressource (URI) est une courte chaîne de caractères identifiant une ressource abstraite ou physique (par exemple, une page web). Un Localisateur Uniforme de Ressource (URL) est un URI qui identifie une ressource par son mécanisme d'accès principal (par exemple, son "emplacement" réseau), plutôt que par son nom ou un autre attribut de cette ressource. Un Nom Uniforme de Ressource (URN) est un URI qui doit rester globalement unique et persistant même lorsque la ressource cesse d'exister ou devient indisponible.

Les URI sont la méthode standard pour nommer les destinations de liens hypertextes pour des outils tels que les navigateurs web. La chaîne "http://www.kernel.org" est un URL (et donc aussi un URI). Beaucoup de gens utilisent le terme URL de manière informelle comme synonyme d'URI (bien que techniquement les URL soient un sous-ensemble des URI).

Les URI peuvent être absolus ou relatifs. Un identifiant absolu fait référence à une ressource indépendamment du contexte, tandis qu'un identifiant relatif fait référence à une ressource en décrivant la différence par rapport au contexte actuel. Dans une référence de chemin relatif, les segments de chemin complets "." et ".." ont des significations spéciales : "le niveau hiérarchique actuel" et "le niveau au-dessus de ce niveau hiérarchique", respectivement, tout comme ils le font dans les systèmes de type UNIX. Un segment de chemin contenant un caractère deux-points ne peut pas être utilisé comme premier segment d'un chemin d'URI relatif (par exemple, "this:that"), car il serait confondu avec un nom de schéma ; précédez de tels segments avec ./ (par exemple, "./this:that"). Notez que les descendants de MS-DOS (par exemple, Microsoft Windows) remplacent les deux-points des noms de périphérique par la barre verticale ("|") dans les URI, de sorte que "C:" devient "C|".

Un identifiant de fragment, s'il est inclus, fait référence à une partie (fragment) nommée particulière d'une ressource ; le texte après un '#' identifie le fragment. Un URI commençant par '#' fait référence à ce fragment dans la ressource actuelle.

UTILISATION

Il existe de nombreux schémas d'URI différents, chacun avec des règles et des significations supplémentaires spécifiques, mais ils sont intentionnellement conçus pour être aussi similaires que possible. Par exemple, de nombreux schémas d'URL autorisent l'autorité à avoir le format suivant, appelé ici un ip_server (les crochets indiquent ce qui est facultatif) :

ip_server = [user [ : password ] @ ] host [ : port]

Ce format vous permet d'insérer facultativement un nom d'utilisateur, un utilisateur plus un mot de passe et/ou un numéro de port. L' host est le nom de l'ordinateur hôte, soit son nom tel que déterminé par le DNS, soit une adresse IP (nombres séparés par des points). Ainsi, l'URI http://fred:fredpassword@example.com:8080/ se connecte à un serveur web sur l'hôte example.com en tant que fred (en utilisant fredpassword) en utilisant le port 8080. Évitez d'inclure un mot de passe dans un URI si possible en raison des nombreux risques de sécurité liés à l'écriture d'un mot de passe. Si l'URL fournit un nom d'utilisateur mais pas de mot de passe, et que le serveur distant demande un mot de passe, le programme interprétant l'URL doit en demander un à l'utilisateur.

Voici quelques-uns des schémas les plus courants utilisés sur les systèmes de type UNIX et compris par de nombreux outils. Notez que de nombreux outils utilisant des URI ont également des schémas internes ou spécialisés ; consultez la documentation de ces outils pour plus d'informations sur ces schémas.

http - Serveur Web (HTTP)

http://ip_server/path
http://ip_server/path?query

Ceci est un URL accédant à un serveur web (HTTP). Le port par défaut est 80. Si le chemin fait référence à un répertoire, le serveur web choisit quoi renvoyer ; généralement, s'il existe un fichier nommé "index.html" ou "index.htm", son contenu est renvoyé ; sinon, une liste des fichiers du répertoire actuel (avec les liens appropriés) est générée et renvoyée. Un exemple est http://lwn.net.

Une requête peut être donnée dans le format archaïque "isindex", composée d'un mot ou d'une phrase et ne contenant pas de signe égal (=). Une requête peut également être dans le format plus long "GET", qui contient une ou plusieurs entrées de requête de la forme clé=valeur séparées par le caractère esperluette (&). Notez que clé peut être répétée plusieurs fois, bien qu'il appartienne au serveur web et à ses programmes d'application de déterminer s'il y a un sens à cela. Il y a une interaction malheureuse avec HTML/XML/SGML et le format de requête GET ; lorsque de tels URI avec plus d'une clé sont intégrés dans des documents SGML/XML (y compris HTML), l'esperluette (&) doit être réécrite comme &amp;. Notez que toutes les requêtes n'utilisent pas ce format ; des formulaires plus grands peuvent être trop longs pour être stockés en tant qu'URI, ils utilisent donc un mécanisme d'interaction différent (appelé POST) qui n'inclut pas les données dans l'URI. Voir la spécification Common Gateway Interface à http://www.w3.org/CGI pour plus d'informations.

ftp - Protocole de transfert de fichiers (FTP)

ftp://ip_server/path

Ceci est un URL accédant à un fichier via le protocole de transfert de fichiers (FTP). Le port par défaut (pour le contrôle) est 21. Si aucun nom d'utilisateur n'est inclus, le nom d'utilisateur "anonymous" est fourni, et dans ce cas, de nombreux clients fournissent comme mot de passe l'adresse e-mail Internet du demandeur. Un exemple est <ftp://ftp.is.co.za/rfc/rfc1808.txt>.

gopher - Serveur Gopher

gopher://ip_server/gophertype selector
gopher://ip_server/gophertype selector%09search
gopher://ip_server/gophertype selector%09search%09gopher+_string

Le port gopher par défaut est 70. gophertype est un champ d'un seul caractère pour désigner le type Gopher de la ressource à laquelle l'URL fait référence. Le chemin entier peut également être vide, auquel cas le type de gopher par défaut est "1".

selector est la chaîne de sélection Gopher. Dans le protocole Gopher, les chaînes de sélection Gopher sont une séquence d'octets qui peuvent contenir n'importe quels octets sauf 09 hexadécimal (US-ASCII HT ou tabulation), 0A hexadécimal (caractère US-ASCII LF) et 0D (caractère US-ASCII CR).

mailto - Adresse e-mail

mailto:email-address

Ceci est une adresse e-mail, généralement de la forme nom@nomd. Voir mailaddr(7) pour plus d'informations sur le format correct d'une adresse e-mail. Notez que tout caractère % doit être réécrit en %25. Un exemple est <mailto:dwheeler@dwheeler.com>.

news - Groupe de discussion ou message d'actualités

news:nom-groupe-discussion
news:id-message

Un groupe de discussion

group-name est un nom hiérarchique délimité par des points, tel que « comp.infosystems.www.misc ». Si <newsgroup-name> est « * » (comme dans <news:*>), il est utilisé pour faire référence à « tous les groupes de discussion disponibles ». Un exemple est <news:comp.lang.ada>.

Un message-id correspond au Message-ID de IETF RFC 1036, sans les guillemets « < » et « > » ; il prend la forme unique@nom_de_domaine_complet. Un identifiant de message peut être distingué d'un nom de groupe de discussion par la présence du caractère « @ ».

telnet - Connexion Telnet

telnet://ip_serveur/

Le schéma d'URL Telnet est utilisé pour désigner des services textuels interactifs qui peuvent être accédés par le protocole Telnet. Le caractère « / » final peut être omis. Le port par défaut est 23. Un exemple est <telnet://melvyl.ucop.edu/>.

file - Fichier normal

file://ip_serveur/segments_chemin
file:segments_chemin

Ceci représente un fichier ou un répertoire accessible localement. À titre de cas particulier, ip_serveur peut être la chaîne « localhost » ou la chaîne vide ; ceci est interprété comme « la machine à partir de laquelle l'URL est interprétée ». Si le chemin mène à un répertoire, le visualiseur doit afficher le contenu du répertoire avec des liens vers chaque élément contenu ; tous les visualiseurs ne font pas cela actuellement. KDE prend en charge les fichiers générés via l'URL <file:/cgi-bin>. Si le fichier donné n'est pas trouvé, les auteurs de navigateurs peuvent vouloir essayer d'étendre le nom de fichier par recherche de motif (voir glob(7) et glob(3)).

Le deuxième format (par exemple, <file:/etc/passwd>) est un format correct pour faire référence à un fichier local. Cependant, les anciennes normes ne permettaient pas ce format, et certains programmes ne le reconnaissent pas comme une URI. Une syntaxe plus portable consiste à utiliser une chaîne vide comme nom de serveur, par exemple, <file:///etc/passwd> ; cette forme fait la même chose et est facilement reconnue comme une URI par les analyseurs de motifs et les anciens programmes. Notez que si vous voulez vraiment dire « commencer à partir de l'emplacement actuel », ne spécifiez pas du tout le schéma ; utilisez une adresse relative comme <../test.txt>, qui a pour effet secondaire d'être indépendante du schéma. Un exemple de ce schéma est <file:///etc/passwd>.

man - Documentation des pages de manuel

man:nom_commande
man:nom_commande(section)

Ceci fait référence aux pages de référence manuelles en ligne locales (man). Le nom de la commande peut être facultativement suivi d'une parenthèse et d'un numéro de section ; voir man(7) pour plus d'informations sur la signification des numéros de section. Ce schéma d'URI est propre aux systèmes de type UNIX (comme Linux) et n'est actuellement pas enregistré par l'IETF. Un exemple est <man:ls(1)>.

info - Documentation des pages d'information

info:nom_fichier_virtuel
info:nom_fichier_virtuel#nom_nœud
info:(nom_fichier_virtuel)
info:(nom_fichier_virtuel)nom_nœud

Ce schéma fait référence aux pages d'information en ligne (générées à partir de fichiers texinfo), un format de documentation utilisé par des programmes tels que les outils GNU. Ce schéma d'URI est propre aux systèmes de type UNIX (comme Linux) et n'est actuellement pas enregistré par l'IETF. À l'heure actuelle, GNOME et KDE diffèrent dans leur syntaxe d'URI et n'acceptent pas la syntaxe de l'autre. Les deux premiers formats sont le format GNOME ; dans les noms de nœuds, tous les espaces sont écrits comme des underscores. Les deux derniers formats sont le format KDE ; les espaces dans les noms de nœuds doivent être écrits comme des espaces, même si cela est interdit par les normes URI. On espère qu'à l'avenir la plupart des outils comprendront tous ces formats et accepteront toujours les underscores pour les espaces dans les noms de nœuds. Dans GNOME et KDE, si la forme sans le nom du nœud est utilisée, le nom du nœud est supposé être « Top ». Des exemples du format GNOME sont <info:gcc> et <info:gcc#G++_and_GCC>. Des exemples du format KDE sont <info:(gcc)> et <info:(gcc)G++ and GCC>.

whatis - Recherche de documentation

whatis:chaîne

Ce schéma recherche dans la base de données des descriptions courtes (en une ligne) des commandes et renvoie une liste de descriptions contenant cette chaîne. Seules les correspondances de mots complets sont renvoyées. Voir whatis(1). Ce schéma d'URI est propre aux systèmes de type UNIX (comme Linux) et n'est actuellement pas enregistré par l'IETF.

ghelp - Documentation d'aide GNOME

ghelp:nom_application

Ceci charge l'aide GNOME pour l'application donnée. Notez qu'il n'existe pas beaucoup de documentation actuellement dans ce format.

ldap - Lightweight Directory Access Protocol

ldap://hoteport
ldap://hoteport/
ldap://hoteport/dn
ldap://hoteport/dn?attributs
ldap://hoteport/dn?attributs?portee
ldap://hoteport/dn?attributs?portee?filtre
ldap://hoteport/dn?attributs?portee?filtre?extensions

Ce schéma prend en charge les requêtes au protocole LDAP (Lightweight Directory Access Protocol), un protocole de requête à un ensemble de serveurs pour des informations organisées hiérarchiquement (telles que des personnes et des ressources informatiques). Voir RFC 2255 pour plus d'informations sur le schéma d'URL LDAP. Les composants de cette URL sont :

hoteport
le serveur LDAP à interroger, écrit comme un nom d'hôte éventuellement suivi d'un deux-points et du numéro de port. Le port LDAP par défaut est le port TCP 389. S'il est vide, le client détermine quel serveur LDAP utiliser.
dn
le nom distinctif LDAP (Distinguished Name), qui identifie l'objet de base de la recherche LDAP (voir RFC 2253 section 3).
attributs
une liste d'attributs séparés par des virgules à retourner ; voir RFC 2251 section 4.1.5. S'il est omis, tous les attributs doivent être retournés.
portee
spécifie la portée de la recherche, qui peut être l'une des valeurs suivantes : « base » (pour une recherche d'objet de base), « one » (pour une recherche à un niveau), ou « sub » (pour une recherche dans un sous-arbre). Si la portée est omise, « base » est supposé.
filtre
spécifie le filtre de recherche (sous-ensemble des entrées à retourner). S'il est omis, toutes les entrées doivent être retournées. Voir RFC 2254 section 4.
extensions
une liste de paires type=valeur séparées par des virgules, où la portion =valeur peut être omise pour les options qui n'en ont pas besoin. Une extension préfixée par « ! » est critique (doit être prise en charge pour être valide), sinon elle est non critique (facultative).

Les requêtes LDAP sont plus faciles à expliquer par l'exemple. Voici une requête qui demande à ldap.itd.umich.edu des informations sur l'Université du Michigan aux États-Unis :

ldap://ldap.itd.umich.edu/o=University%20of%20Michigan,c=US

Pour obtenir juste son attribut d'adresse postale, demandez :

ldap://ldap.itd.umich.edu/o=University%20of%20Michigan,c=US?postalAddress

Pour interroger un host.com au port 6666 pour des informations sur la personne dont le nom commun (cn) est « Babs Jensen » à l'Université du Michigan, demandez :

ldap://host.com:6666/o=University%20of%20Michigan,c=US??sub?(cn=Babs%20Jensen)

wais - Wide Area Information Servers

wais://hoteport/base_de_donnees
wais://hoteport/base_de_donnees?recherche
wais://hoteport/base_de_donnees/wtype/wpath

Ce schéma désigne une base de données WAIS, une recherche ou un document (voir IETF RFC 1625 pour plus d'informations sur WAIS). Hoteport est le nom d'hôte, éventuellement suivi d'un deux-points et d'un numéro de port (le numéro de port par défaut est 210).

La première forme désigne une base de données WAIS pour la recherche. La deuxième forme désigne une recherche particulière de la base de données WAIS base_de_donnees. La troisième forme désigne un document particulier dans une base de données WAIS à récupérer. wtype est la désignation WAIS du type de l'objet, et wpath est l'identifiant de document WAIS.

autres schémas

Il existe de nombreux autres schémas d'URI. La plupart des outils qui acceptent des URI prennent en charge un ensemble d'URI internes (par exemple, Mozilla a le schéma about: pour les informations internes, et le navigateur d'aide GNOME a le schéma toc: pour divers points de départ). Il existe de nombreux schémas qui ont été définis mais ne sont pas aussi largement utilisés actuellement (par exemple, prospero). Le schéma nntp: est déprécié en faveur du schéma news:. Les URN doivent être pris en charge par le schéma urn:, avec un espace de noms hiérarchique (par exemple, urn:ietf:... identifierait les documents IETF) ; à l'heure actuelle, les URN ne sont pas largement implémentés. Tous les outils ne prennent pas en charge tous les schémas.

Encodage des caractères

Les URI utilisent un nombre limité de caractères afin qu'ils puissent être saisis et utilisés dans une variété de situations.

Les caractères suivants sont réservés, c'est-à-dire qu'ils peuvent apparaître dans une URI mais leur utilisation est limitée à leur but réservé (les données conflictuelles doivent être échappées avant de former l'URI) :


; / ? : @ & = + $ ,

Les caractères non réservés peuvent être inclus dans une URI. Les caractères non réservés comprennent les lettres latines majuscules et minuscules, les chiffres décimaux et l'ensemble limité suivant de marques de ponctuation et de symboles :


- _ . ! ~ * ' ( )

Tous les autres caractères doivent être échappés. Un octet échappé est codé sous forme de triplet de caractères, composé du caractère pourcentage « % » suivi des deux chiffres hexadécimaux représentant le code de l'octet (vous pouvez utiliser des lettres majuscules ou minuscules pour les chiffres hexadécimaux). Par exemple, un espace doit être échappé sous la forme « %20 », un caractère de tabulation sous la forme « %09 », et le « & » sous la forme « %26 ». Parce que le caractère pourcentage « % » a toujours pour but réservé d'être l'indicateur d'échappement, il doit être échappé sous la forme « %25 ». Il est courant d'échapper les espaces sous la forme du symbole plus (+) dans le texte de requête ; cette pratique n'est pas uniformément définie dans les RFC pertinentes (qui recommandent %20 à la place) mais tout outil acceptant des URI avec du texte de requête doit être préparé à les gérer. NOM

uri - conventions d'encodage et d'écriture des URI

SYNOPSIS

URI

DESCRIPTION

Une URI (Uniform Resource Identifier) est une chaîne de caractères qui identifie une ressource de manière unique. Les URI sont utilisées dans un grand nombre de contextes, notamment sur le World Wide Web, où elles sont souvent appelées URL (Uniform Resource Locators) car elles spécifient à la fois l'emplacement et le moyen d'accès à une ressource. Les URI sont définies dans les documents suivants :

  • RFC 3986, Uniform Resource Identifier (URI): Generic Syntax
  • RFC 2396, Uniform Resource Identifiers (URI): Generic Syntax
  • RFC 1738, Uniform Resource Locators (URL)
  • RFC 1630, Universal Resource Identifiers in WWW

Les caractères autorisés dans une URI sont divisés en trois catégories :

caractères réservés
Ces caractères ont une signification spéciale dans le contexte d'une URI et peuvent être utilisés pour délimiter des composants de l'URI. Les caractères réservés incluent : ":", "/", "?", "#", "[", "]", "@", "!", "$", "&", "'", "(", ")", "*", "+", ",", ";", "=", "%", ":", "/", "?", "#", "[", "]", "@", "!", "$", "&", "'", "(", ")", "*", "+", ",", ";", "=".
caractères non réservés
Ces caractères n'ont aucune signification spéciale et peuvent être utilisés en toute sécurité dans une URI. Les caractères non réservés incluent les lettres majuscules et minuscules de l'alphabet ASCII (a-z, A-Z), les chiffres décimaux (0-9) et les caractères suivants : "-", ".", "_", "~".
caractères non sûrs
Ces caractères ont une signification spéciale ou ambiguë dans les URI et doivent être encodés sous forme de séquences %HH (où HH représente la valeur hexadécimale du caractère) lorsqu'ils apparaissent dans une URI. Les caractères non sûrs incluent la plupart des caractères réservés, ainsi que les caractères suivants : "<", ">", """, "%", "{", "}", "|", "\", "^", "~", "[ ", "] ", " ` ".

L'échappement des caractères réservés est nécessaire lorsque ces caractères ne sont pas utilisés dans leur rôle de délimiteur. Par exemple, le caractère "?" est utilisé pour séparer le chemin de la requête dans une URL. S'il doit apparaître dans le chemin lui-même, il doit être échappé sous la forme "%3F".

Les caractères non réservés peuvent être échappés sans modifier la sémantique de l'URI, mais cela ne devrait pas être fait à moins que l'URI ne soit utilisée dans un contexte qui n'autorise pas le caractère non échappé. Par exemple, "%7e" est parfois utilisé à la place de "~" dans un chemin d'URL HTTP, mais les deux sont équivalents pour une URL HTTP.

Pour les URI qui doivent gérer des caractères en dehors de l'ensemble de caractères US ASCII, la spécification HTML 4.01 (section B.2) et la RFC 3986 de l'IETF (dernier paragraphe de la section 2.5) recommandent l'approche suivante :

(1)
traduire les séquences de caractères en UTF-8 (RFC 3629 de l'IETF) — voir utf-8(7) — puis
(2)
utiliser le mécanisme d'encodage des URI, c'est-à-dire utiliser l'encodage %HH pour les octets non sûrs.

Écriture d'une URI

Lorsqu'elles sont écrites, les URI doivent être placées entre guillemets doubles (par exemple, "http://www.kernel.org"), entourées d'accolades (par exemple, http://lwn.net), ou placées sur une ligne à elles seules. Un avertissement pour ceux qui utilisent des guillemets doubles : ne jamais déplacer de ponctuation superflue (telle que le point final d'une phrase ou la virgule dans une liste) à l'intérieur d'une URI, car cela modifierait la valeur de l'URI. Utilisez plutôt des accolades, ou passez à un système de mise entre guillemets qui n'inclut jamais de caractères superflus à l'intérieur des guillemets. Ce dernier système, appelé système de mise entre guillemets « nouveau » ou « logique » par « Hart's Rules » et « Oxford Dictionary for Writers and Editors », est une pratique privilégiée en Grande-Bretagne et dans diverses langues européennes. Les documents plus anciens suggéraient d'insérer le préfixe "URL:" juste avant l'URI, mais cette forme n'a jamais pris.

La syntaxe des URI a été conçue pour être sans ambiguïté. Cependant, à mesure que les URI sont devenues courantes, les médias traditionnels (télévision, radio, journaux, panneaux publicitaires, etc.) ont de plus en plus utilisé des références d'URI abrégées composées uniquement de l'autorité et de la partie chemin de la ressource identifiée (par exemple, <www.w3.org/Addressing>). De telles références sont principalement destinées à l'interprétation humaine plutôt qu'à la machine, en supposant que des heuristiques basées sur le contexte sont suffisantes pour compléter l'URI (par exemple, les noms d'hôte commençant par "www" sont susceptibles d'avoir un préfixe d'URI "http://" et les noms d'hôte commençant par "ftp" un préfixe "ftp://"). De nombreuses implémentations clientes résolvent de manière heuristique ces références. Ces heuristiques peuvent changer avec le temps, en particulier lorsque de nouveaux schémas sont introduits. Étant donné qu'une URI abrégée a la même syntaxe qu'un chemin d'URL relatif, les références d'URI abrégées ne peuvent pas être utilisées là où les URI relatives sont autorisées, et ne peuvent être utilisées que lorsqu'il n'y a pas de base définie (comme dans les boîtes de dialogue). N'utilisez pas d'URI abrégées comme liens hypertextes à l'intérieur d'un document ; utilisez le format standard tel que décrit ici.

NOTES

Tout outil acceptant les URI (par exemple, un navigateur Web) sur un système Linux devrait être capable de gérer (directement ou indirectement) tous les schémas décrits ici, y compris les schémas man: et info:. Les gérer en invoquant un autre programme est acceptable et même encouragé.

Techniquement, le fragment ne fait pas partie de l'URI.

Pour savoir comment intégrer des URI (y compris des URL) dans un format de données, consultez la documentation de ce format. HTML utilise le format <A HREF="uri"> texte </A>. Les fichiers Texinfo utilisent le format @uref{uri}. Man et mdoc ont récemment ajouté la macro UR, ou incluent simplement l'URI dans le texte (les visualiseurs devraient pouvoir détecter :// comme faisant partie d'une URI).

Les environnements de bureau GNOME et KDE varient actuellement dans les URI qu'ils acceptent, en particulier dans leurs navigateurs d'aide respectifs. Pour lister les pages man, GNOME utilise <toc:man> tandis que KDE utilise <man:(index)>, et pour lister les pages info, GNOME utilise <toc:info> tandis que KDE utilise <info:(dir)> (l'auteur de cette page man préfère l'approche KDE ici, bien qu'un format plus régulier serait encore mieux). En général, KDE utilise <file:/cgi-bin/> comme préfixe pour un ensemble de fichiers générés. KDE préfère la documentation en HTML, accessible via <file:/cgi-bin/helpindex>. GNOME préfère le schéma ghelp pour stocker et trouver la documentation. Aucun des deux navigateurs ne gère les références file: aux répertoires au moment de la rédaction, ce qui rend difficile la référence à un répertoire entier avec une URI consultable. Comme indiqué ci-dessus, ces environnements diffèrent dans la manière dont ils gèrent le schéma info:, probablement la variation la plus importante. On s'attend à ce que GNOME et KDE convergent vers des formats d'URI communs, et une future version de cette page man décrira le résultat convergé. Les efforts pour aider à cette convergence sont encouragés.

Sécurité

Une URI ne constitue pas en soi une menace pour la sécurité. Il n'y a aucune garantie générale qu'une URL, qui à un moment donné référençait une ressource donnée, continuera de le faire. Il n'y a pas non plus de garantie qu'une URL ne référencera pas une ressource différente à un moment ultérieur ; une telle garantie ne peut être obtenue qu'auprès des personnes contrôlant cet espace de noms et la ressource en question.

Il est parfois possible de construire une URL de telle sorte qu'une tentative d'effectuer une opération apparemment inoffensive, telle que la récupération d'une entité associée à la ressource, entraîne en fait une opération à distance potentiellement dommageable. L'URL non sûre est généralement construite en spécifiant un numéro de port autre que celui réservé au protocole réseau en question. Le client contacte à son insu un site qui exécute en fait un protocole différent. Le contenu de l'URL contient des instructions qui, lorsqu'elles sont interprétées selon ce autre protocole, provoquent une opération inattendue. Un exemple a été l'utilisation d'une URL gopher pour provoquer l'envoi d'un message non intentionnel ou d'impersonation via un serveur SMTP.

La prudence doit être de mise lors de l'utilisation de toute URL spécifiant un numéro de port autre que celui par défaut pour le protocole ; en particulier, lorsqu'il s'agit d'un numéro dans l'espace réservé.

Il faut veiller à ce que, lorsqu'une URI contient des délimiteurs échappés pour un protocole donné (par exemple, les caractères CR et LF pour les protocoles telnet), ceux-ci ne soient pas déséchappés avant la transmission. Cela pourrait violer le protocole, mais évite le risque que de tels caractères soient utilisés pour simuler une opération ou un paramètre supplémentaire dans ce protocole, ce qui pourrait conduire à une opération à distance inattendue et potentiellement dangereuse.

Il est clairement déconseillé d'utiliser une URI contenant un mot de passe qui est destiné à rester secret. En particulier, l'utilisation d'un mot de passe dans le composant « userinfo » d'une URI est fortement déconseillée, sauf dans les rares cas où le paramètre « password » est destiné à être public.

BOGUES

La documentation peut être placée dans divers emplacements, il n'existe donc actuellement pas de bon schéma d'URI pour la documentation générale en ligne dans des formats arbitraires. Les références de la forme <file:///usr/doc/ZZZ> ne fonctionnent pas, car différentes distributions et exigences d'installation locales peuvent placer les fichiers dans des répertoires différents (il peut être dans /usr/doc, ou /usr/local/doc, ou /usr/share, ou ailleurs). De plus, le répertoire ZZZ change généralement lorsqu'une version change (bien que la recherche de noms de fichiers puisse partiellement surmonter cela). Enfin, l'utilisation du schéma file: ne prend pas facilement en charge les personnes qui chargent dynamiquement la documentation à partir d'Internet (au lieu de charger les fichiers sur un système de fichiers local). Un futur schéma d'URI pourra être ajouté (par exemple, "userdoc:") pour permettre aux programmes d'inclure des références croisées vers une documentation plus détaillée sans avoir à connaître l'emplacement exact de cette documentation. Alternativement, une future version de la spécification du système de fichiers pourra spécifier les emplacements de fichiers suffisamment pour que le schéma file: puisse localiser la documentation.

De nombreux programmes et formats de fichiers ne permettent pas d'intégrer ou d'implémenter des liens à l'aide d'URI.

De nombreux programmes ne peuvent pas gérer tous ces différents formats d'URI ; il devrait exister un mécanisme standard pour charger une URI arbitraire qui détecte automatiquement l'environnement de l'utilisateur (par exemple, texte ou graphique, environnement de bureau, préférences utilisateur locales et outils en cours d'exécution) et invoque le bon outil pour toute URI.
