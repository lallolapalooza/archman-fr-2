unlang(5) Langage de traitement unlang de FreeRADIUS unlang(5)

NOM

unlang - Langage de traitement unlang de FreeRADIUS

DESCRIPTION

FreeRADIUS supporte un langage de traitement simple dans ses fichiers de configuration. Nous l'appelons un « un-langage » car l'intention n'est PAS de créer un autre langage de programmation. Si vous avez besoin de quelque chose de plus complexe que ce qui est décrit ici, nous vous suggérons d'utiliser les modules Perl ou Python rlm_perl ou rlm_python.

L'objectif du langage est de permettre la rédaction de politiques simples avec un minimum d'effort. Ces politiques sont ensuite appliquées lors du traitement d'une requête. Les requêtes sont traitées via des serveurs virtuels (y compris celui par défaut), dans les sections intitulées « authorize », « authenticate », « post-auth », « preacct », « accounting », « pre-proxy », « post-proxy », et « session ».

Ces politiques ne peuvent pas être utilisées dans d'autres parties des fichiers de configuration, telles que la configuration des modules ou des clients.

MOTS-CLÉS

Les mots-clés du langage sont une combinaison de mots-clés prédéfinis et de références aux noms des modules chargeables. Nous ne documentons ici que les mots-clés prédéfinis.

Sous réserve de quelques limitations décrites ci-dessous, tout mot-clé peut apparaître dans n'importe quel contexte. Le langage se compose d'une série d'entrées, chacune sur une ligne. Chaque entrée commence par un mot-clé. Les entrées sont organisées en listes. Le traitement du langage se fait ligne par ligne, du début de la liste à la fin. Les actions sont exécutées par mot-clé.

nom-du-module[.nom-de-section]
Une référence au module nommé. Lorsque le traitement atteint ce point, le module précompilé est appelé. Le module peut réussir ou échouer, et renverra un statut à « unlang » le cas échéant. Ce statut peut être testé dans une condition. Voir le texte « Simple Conditions » dans la section CONDITIONS, et CODES DE RETOUR DE MODULE, ci-dessous. Si un nom de section est fourni, cela forcera le module à s'exécuter comme s'il était listé dans la section nommée. 
	chap  # appelle le module CHAP
	sql   # appelle le module SQL
	...
if

Vérifie une condition particulière. Si elle est vraie, le bloc après la condition est traité. Sinon, le bloc est ignoré. Voir CONDITIONS, ci-dessous, pour la documentation sur le format des conditions. 
	if (condition) {
		...
	}
else

Définit un bloc à exécuter uniquement si la condition « if » précédente a renvoyé faux. 
	else {
		...
	}
elsif

Définit un bloc à exécuter uniquement si la condition « if » précédente a renvoyé faux, et si la condition spécifiée évalue à vrai. 
	elsif (condition) {
		...
	}
foreach

Boucle sur les valeurs d'un attribut, exécutant le bloc pour chaque valeur. La valeur de retour du bloc est la valeur de retour de la dernière instruction exécutée. La boucle peut être interrompue prématurément en utilisant le mot-clé « break ». Contrairement à d'autres langages, « break » ici signifie « quitter la boucle à la prochaine itération », et non « quitter la boucle maintenant ». Le résultat est que toute instruction après le mot-clé « break » sera toujours exécutée. Nous recommandons d'utiliser « break » uniquement lorsqu'il s'agit de la dernière instruction dans un bloc « foreach ».

À l'intérieur du bloc « foreach », l'attribut sur lequel on boucle peut être référencé comme « Foreach-Variable-# ». Où « # » est la profondeur de la boucle, commençant à « 0 ». Par exemple, « Foreach-Variable-0 ». Les boucles peuvent être imbriquées jusqu'à huit (8) niveaux de profondeur, bien que cela ne soit pas recommandé.

	foreach &Référence-Attribut {
		...
	}
switch

Une instruction « switch » prend un argument et contient une série d'instructions « case ». Lorsqu'une instruction « switch » est rencontrée, l'argument du « switch » est évalué tour à tour par rapport à l'argument de chaque instruction « case ». La première instruction « case » qui correspond est exécutée. Toutes les autres instructions « case » sont ignorées. Une instruction « case » par défaut peut être définie en omettant son argument.

Si l'argument est une chaîne entre guillemets doubles (par ex. « %{exec:1 + 2} »), il est développé comme décrit dans la section TYPES DE DONNÉES, ci-dessous. La comparaison est ensuite effectuée sur la chaîne renvoyée par le développement. Si l'argument est une référence d'attribut (par ex. &User-Name), alors la comparaison est effectuée sur la valeur de cet attribut. Sinon, l'argument est considéré comme une chaîne littérale, et la comparaison est effectuée par simple égalité.

Aucune instruction autre que « case » ne peut apparaître dans un bloc « switch ».

	switch <argument> {
		...
	}
case

Fournit un espace réservé qui correspond à l'argument d'une instruction « switch » parente.

Une instruction « case » ne peut pas apparaître en dehors d'un bloc « switch ».

Si l'argument est une chaîne entre guillemets doubles (par ex. « %{exec:1 + 2} »), il est développé comme décrit dans la section TYPES DE DONNÉES, ci-dessous. La comparaison est ensuite effectuée sur la chaîne renvoyée par le développement. Si l'argument est une référence d'attribut (par ex. &User-Name), alors la comparaison est effectuée sur la valeur de cet attribut. Sinon, l'argument est considéré comme une chaîne littérale, et la comparaison est effectuée par simple égalité.

	case <argument> {
		...
	}

Une entrée par défaut peut être définie en omettant l'argument, comme indiqué ci-dessous. Cette entrée sera utilisée si aucune autre entrée « case » ne correspond. Une seule entrée par défaut peut exister dans une section « switch ».

	case {
		...
	}
update

Met à jour une liste d'attributs particulière, en fonction des attributs donnés dans le bloc actuel. 
	update <liste> {
		&Référence-Attribut = valeur
		...
	}

La <liste> peut être « request », « reply », « proxy-request », « proxy-reply », « coa », « disconnect », « session-state », ou « control ». À partir de la version 3, la <liste> peut être omise, auquel cas « request » est supposé.

La liste « control » est la liste des attributs maintenus interne par le serveur qui contrôle la manière dont le serveur traite la requête. Tout attribut qui n'est pas envoyé dans un paquet sur le réseau sera généralement placé dans la liste « control ».

Pour les méthodes EAP avec des sessions d'authentification tunnellisées (c'est-à-dire PEAP et EAP-TTLS), la session du tunnel intérieur peut également faire référence à « outer.request », « outer.reply », et « outer.control ». Ces références vous permettent de cibler la liste pertinente dans la session du tunnel extérieur.

Les sections « coa » et « disconnect » ne peuvent être utilisées que lorsque le serveur reçoit une Access-Request ou une Accounting-Request. Utilisez « request » et « reply » à la place de « coa » lorsque le serveur reçoit un paquet CoA-Request ou Disconnect-Request.

L'ajout d'un ou plusieurs attributs à l'une des listes « coa » ou « disconnect » provoque l'origine d'un paquet CoA-Request ou Disconnect-Request par le serveur. Ce paquet est envoyé une fois que la requête Access-Request ou Accounting-Request actuelle est terminée et qu'une réponse a été envoyée au NAS. Voir raddb/sites-available/originate-coa pour des informations supplémentaires.

La liste « session-state » est principalement utilisée pour EAP. Les attributs placés dans la liste « session-state » sont sauvegardés pour le paquet suivant de la session. Ils sont automatiquement récupérés lorsque le paquet suivant est reçu.

Les seuls contenus autorisés dans une section « update » sont les attributs et leurs valeurs. Le contenu de la section « update »

SECTIONS

sont décrits dans les sections ATTRIBUTE REFERENCE et ATTRIBUTE ASSIGNMENT ci-dessous.

redundant
Cette section contient une simple liste de modules. Le premier module est appelé lorsque la section est traitée. Si le premier module réussit dans son opération, alors le serveur arrête de traiter la section et retourne à la section parente.

Si, cependant, le module échoue, alors le module suivant dans la liste est essayé, comme décrit ci-dessus. Le traitement continue jusqu'à ce qu'un module réussisse, ou jusqu'à ce que la liste soit épuisée.

Les sections redondantes ne peuvent contenir qu'une liste de modules et ne peuvent pas contenir de mots-clés qui effectuent des opérations conditionnelles (if, else, etc.) ou qui mettent à jour une liste d'attributs.

	redundant {
		sql1	# essayer ceci
		sql2	# essayer ceci seulement si sql1 échoue.
		...
	}
load-balance
Cette section contient une simple liste de modules. Lorsque la section est entrée, un module est choisi au hasard pour traiter la requête. Tous les modules de la liste doivent être du même type (par exemple, ldap ou sql). Tous les modules de la liste doivent se comporter de manière identique, sinon la section load-balance retournera des résultats différents pour la même requête.

Les sections load-balance ne peuvent contenir qu'une liste de modules et ne peuvent pas contenir de mots-clés qui effectuent des opérations conditionnelles (if, else, etc.) ou qui mettent à jour une liste d'attributs.

	load-balance {
		ldap1	# 50% des requêtes vont ici
		ldap2	# 50% des requêtes vont ici
	}

En général, nous recommandons d'utiliser "redundant-load-balance" au lieu de "load-balance".

redundant-load-balance
Cette section contient une simple liste de modules. Lorsque la section est entrée, un module est choisi au hasard pour traiter la requête. Si ce module réussit, alors le serveur arrête de traiter la section. Si, cependant, le module échoue, alors un des modules restants est choisi au hasard pour traiter la requête. Ce processus se répète jusqu'à ce qu'un module réussisse, ou jusqu'à ce que la liste soit épuisée.

Tous les modules de la liste doivent être du même type (par exemple, ldap ou sql). Tous les modules de la liste doivent se comporter de manière identique, sinon la section load-balance retournera des résultats différents pour la même requête.

Les sections load-balance ne peuvent contenir qu'une liste de modules et ne peuvent pas contenir de mots-clés qui effectuent des opérations conditionnelles (if, else, etc.) ou qui mettent à jour une liste d'attributs. Veuillez consulter la section "instantiate" de raddb/radiusd.conf pour plus d'exemples de configuration.

	redundant-load-balance {
		ldap1	# 50%, sauf si ldap2 est en panne, alors 100%
		ldap2	# 50%, sauf si ldap1 est en panne, alors 100%
	}
return

Retourne de la section de premier niveau actuelle, par exemple "authorize" ou "authenticate". Ce mot-clé est principalement utilisé pour éviter les couches d'imbrication de "if" et "else". 
	authorize {
		if (...) {
			...
			return
		}
		...  # ceci n'est jamais atteint lorsque l'instruction "if"
		...  # est exécutée
	}

REFERENCES D'ATTRIBUTS

Les attributs peuvent être référencés via la syntaxe suivante :

&Nom-Attribut
&Nom-Attribut:TAG
&Nom-Attribut[NUM]
&<liste>:Nom-Attribut
&<liste>:Nom-Attribut:TAG[NUM]

Où <liste> est l'un de "request", "reply", "control", "proxy-request", "proxy-reply", ou "outer.request", "outer.reply", "outer.control", "outer.proxy-request", ou "outer.proxy-reply", tout comme avec la section "update", ci-dessus. Le préfixe "<liste>:" est facultatif, et s'il est omis, il est supposé faire référence à la liste "request".

La partie TAG est un entier décimal compris entre 1 et 31. Veuillez consulter la RFC 2868 pour plus d'informations sur les tags. Les tags ne peuvent être utilisés que pour les attributs qui sont marqués dans le dictionnaire comme "has_tag".

La partie NUM est utilisée lorsqu'il y a plusieurs attributs du même nom dans une liste. La référence "Nom-Attribut" retournera le premier attribut. L'utilisation d'un indice de tableau permet à la politique de faire référence au deuxième attribut et aux suivants.

Si '*' est utilisé dans la partie NUM, il s'évalue à toutes les instances de l'attribut dans la requête.

Si 'n' est utilisé dans la partie NUM, il s'évalue à la dernière instance de l'attribut dans la requête.

Lorsqu'un nom d'attribut est rencontré, la liste donnée est examinée pour un attribut du nom donné. Voici quelques exemples :

	User-Name
	request:User-Name # idem que ci-dessus
	reply:User-Name
	Tunnel-Password:1
	Cisco-AVPAir[2]
	outer.request:User-Name # depuis l'intérieur d'un tunnel TTLS/PEAP

Notez que contrairement à C, il n'y a aucun moyen de définir de nouveaux attributs à l'exécution. Ils DOIVENT être déclarés dans un fichier de dictionnaire et chargés au démarrage du serveur.

Tous les attributs sont définis dans les dictionnaires qui accompagnent le serveur. Ces définitions définissent uniquement le nom et le type, et ne définissent pas la valeur de l'attribut. Lorsque le serveur reçoit un paquet, il utilise le contenu du paquet pour rechercher des entrées dans le dictionnaire, et instancie des attributs avec un nom tiré des dictionnaires, et une valeur tirée du contenu du paquet. Ce processus signifie que si un attribut n'existe pas, c'est généralement parce qu'il n'était pas contenu dans un paquet que le serveur a reçu.

Une fois l'attribut instancié, il est ajouté à une liste. Il peut alors être référencé, mis à jour, remplacé, etc.

CONDITIONS

Les conditions sont similaires aux conditions C en syntaxe, bien que les chaînes de caractères entre guillemets soient supportées, comme dans le shell Unix.

Simples
conditions 
(foo)

S'évalue à vrai si 'foo' est une chaîne non vide (guillemets simples, doubles ou inversés). S'évalue également à vrai si 'foo' est un nombre non nul. Notez que le langage est faiblement typé, donc la chaîne "0000" peut être interprétée comme un zéro numérique. Ce problème peut être évité en comparant des chaînes à une chaîne vide, plutôt qu'en évaluant la chaîne par elle-même.

Si le mot 'foo' n'est pas une chaîne entre guillemets, il peut être interprété comme une référence à un attribut nommé. Voir "Références aux listes d'attributs", ci-dessous, pour des exemples de références d'attributs. La condition s'évalue à vrai si l'attribut nommé existe.

Sinon, si le mot 'foo' n'est pas une chaîne entre guillemets et n'est pas une référence d'attribut, alors il est interprété comme une référence à un code de retour de module. La condition s'évalue à vrai si le code de retour du module le plus récent correspond au nom donné ici. Les codes de retour de module valides sont donnés dans CODES DE RETOUR DE MODULE, ci-dessous.

Négation
(!foo)

S'évalue à vrai si 'foo' s'évalue à faux, et vice versa.

Opérateurs de court-circuit


	(foo || bar)
	(foo && bar)

"&&" et "||" sont des opérateurs de court-circuit. "&&" évalue la première condition, et évalue la deuxième condition si et seulement si le résultat de la première condition est vrai. "||" est similaire, mais exécute la deuxième commande si et seulement si le résultat de la première condition est faux.

Comparaisons
(foo == bar)

Compare 'foo' à 'bar', et s'évalue à vrai si la comparaison est vraie. Les opérateurs de comparaison valides sont "==", "!=", "<", "<=", ">", ">=", "=~", et "!~", tous avec leur signification habituelle. Les opérateurs ":=", "^=" et "=" sont des opérateurs d'affectation, et ne sont pas autorisés pour les comparaisons.

Les opérateurs "<", "<=", ">", et ">=" sont également autorisés pour vérifier qu'une adresse IP est contenue dans un réseau. Par exemple :

if (<ipaddr>192.0.2.1 < 192.0.2.0/24) {

Cette comparaison réussit, car l'adresse 192.0.2.1 est contenue dans le réseau 192.0.2.0/24.

Comparaisons d'attributs
Lors des comparaisons d'attributs, le type de données de l'attribut est utilisé pour déterminer le type de données de l'opérande de droite.
(&User-Name == "foo")

Compare la valeur de l'attribut User-Name à la chaîne 'foo', et s'évalue à vrai si la comparaison est vraie.

De même,

(&Framed-IP-Address == 192.0.2.1)

Compare la valeur de l'attribut Framed-IP-Address à l'adresse IP 192.0.2.1. Cette adresse IP n'a pas besoin d'être mise entre guillemets.

Comparaisons Inter-Attributs
(&User-Name == &Filter-Id)

Compare la valeur de l'attribut User-Name au contenu de l'attribut Filter-Id, et s'évalue à vrai si la comparaison est vraie. Contrairement à l'exemple précédent, cette comparaison est effectuée de manière type-safe. Par exemple, comparer les adresses IP 1.2.3.4 et 127.0.0.1 en tant que chaînes donnera des résultats différents que de les comparer en tant qu'adresses IP.

Le caractère "&" dans la condition signifie que la comparaison "fait référence" à l'attribut Filter-Id. S'il est omis, cela signifie que l'attribut User-Name est comparé à la chaîne littérale "Filter-Id".

Lorsque le côté gauche est un attribut, le caractère "&" peut être omis. Cependant, il est autorisé pour des raisons de compatibilité ascendante. Par exemple, la comparaison "(&User-Name == &Filter-Id)" est équivalente à l'exemple ci-dessus.

Nous recommandons d'utiliser des références d'attributs au lieu d'imprimer

CONDITIONNELLES

Les conditions sont utilisés pour contrôler le flux d'exécution du fichier de configuration. Elles sont utilisées dans les sections request, reply, update, post-auth, et post-proxy. Elles peuvent aussi être utilisées pour des tâches de journalisation dans la section log.

Les conditions sont des expressions qui sont évaluées à une valeur booléenne (vrai ou faux). Si une condition est vraie, alors les instructions contenues dans les accolades qui suivent la condition sont exécutées.

Les conditions peuvent être groupées en utilisant les parenthèses, comme dans l'exemple suivant:

( condition1 ) and ( condition2 )
( condition1 ) or ( condition2 )
not ( condition1 )

Les conditions sont faites de comparaisons. Les comparaisons sont formées de deux opérandes, séparés par un opérateur.

Opérateurs
Les opérateurs suivants sont supportés:
=, ==
Égal à.
<>, !=
Non égal à.
<
Inférieur à.
<=
Inférieur ou égal à.
>
Supérieur à.
>=
Supérieur ou égal à.
=~
Correspond à l'expression régulière.
!~
Ne correspond pas à l'expression régulière.

Les opérandes peuvent être des chaînes de caractères, des nombres, ou des références d'attributs. Les références d'attributs sont des noms d'attributs précédés par le caractère '&'. Par exemple, &User-Name fait référence à l'attribut User-Name.

Les comparaisons sont effectuées de manière sûre vis-à-vis des types. Les deux côtés de la comparaison sont analysés en attributs temporaires, et les attributs sont comparés en utilisant des méthodes spécifiques au type. Les attributs temporaires n'ont aucun autre effet et ne sont pas sauvegardés.

Si un attribut n'a pas de valeur, la comparaison échouera, sauf si l'opérateur est '=' ou '==', auquel cas elle sera considérée comme vraie.

Les références d'attributs peuvent être utilisées dans des conditions. Par exemple, pour vérifier si l'attribut User-Name est égal à "testuser", vous pouvez écrire:

(&User-Name == "testuser")

Les comparaisons entre attributs sont effectuées de manière sûre vis-à-vis des types. Par exemple, vous pouvez comparer des adresses IP.

(&Framed-IP-Address == "127.0.0.1")

Si vous avez besoin de comparer la valeur d'un attribut avec la valeur d'un autre attribut, vous pouvez utiliser la syntaxe suivante:

(&Attribute-1 == &Attribute-2)

Les comparaisons peuvent être effectuées sur la valeur brute d'un attribut. Cela est utile lorsque l'on a affaire à des attributs qui ont une valeur numérique mais qui sont stockés sous forme de chaînes. Par exemple, si un attribut Service-Type contient la valeur 1, l'expression (&Service-Type == 1) sera vraie.

Pour des raisons de performance, il est conseillé d'utiliser des références d'attributs dans les conditions lorsque cela est possible, par exemple:

(&User-Name == "%{Filter-Id}")

Les références d'attributs seront plus rapides et plus efficaces.

Les conditions ne vérifient que la première occurrence d'un attribut. S'il y a plus d'une instance d'un attribut, la syntaxe suivante doit être utilisée:

(&Nom-Attribut[*] == "foo")

L'utilisation de la syntaxe "[*]" signifie que toutes les instances de l'attribut nommé sont vérifiées. Si une instance correspond, la condition réussit. Si aucune ne correspond, la condition échoue.

Castages
(<type>foo == bar)

Le côté gauche d'une condition peut être "casté" vers un type de données spécifique. Le type de données doit être valide pour les dictionnaires. Par exemple, "integer", "ipaddr", etc.

La comparaison est effectuée de manière sûre vis-à-vis des types, comme avec les "Comparaisons inter-attributs", ci-dessus. Les deux côtés de la condition sont analysés en attributs temporaires, et les attributs sont comparés via des méthodes spécifiques au type. Les attributs temporaires n'ont aucun autre effet et ne sont sauvegardés nulle part.

Les castages permettent aux conditions d'effectuer des comparaisons spécifiques aux types. Dans les versions précédentes du serveur, les données auraient dû être placées manuellement dans un attribut intermédiaire (ou des attributs), puis comparées. L'utilisation d'un cast permet des politiques plus simples.

Les castages ne sont autorisés que sur l'opérande de gauche d'une condition.

Les conditions peuvent être imbriquées à n'importe quelle profondeur, sous réserve des limitations de longueur de ligne (8192 octets).

TYPES DE DONNÉES

Il n'y a que quelques types de données supportés dans le langage. Références aux attributs, nombres et chaînes de caractères. N'importe quel type de données peut apparaître dans une condition autonome, auquel cas il est évalué comme décrit dans "Conditions simples", ci-dessus. Ils peuvent aussi apparaître (avec quelques exceptions notées ci-dessous) sur le côté gauche ou droit d'une comparaison.

nombres
Les nombres sont composés de chiffres décimaux. Les nombres à virgule flottante, hexadécimaux et octaux ne sont pas supportés. La valeur maximale pour un nombre dépend de la machine, mais est généralement de 32 bits, y compris un bit pour la valeur de signe.

mot

Le texte qui n'est pas entre guillemets est interprété différemment selon l'endroit où il apparaît dans une condition. Sur le côté gauche d'une condition, il est interprété comme une référence à un attribut. Sur le côté droit, il est interprété comme une simple chaîne de caractères, de la même manière qu'une chaîne entre guillemets simples.

L'utilisation de références d'attributs permet des comparaisons limitées et spécifiques aux types, comme le montrent les exemples ci-dessous.

	if (&User-Name == "bob") {
		...
	if (&Framed-IP-Address > 127.0.0.1) {
		...
	if (&Service-Type == Login-User) {
"chaînes"
Les chaînes entre guillemets doubles sont développées en insérant la valeur de tous les attributs (voir RÉFÉRENCES D'ATTRIBUTS, ci-dessous) avant d'être évaluées. Si le résultat est un nombre, il est évalué dans un contexte numérique.

La longueur de la chaîne est limitée par la longueur de la ligne, généralement environ 8000 caractères. Un caractère de guillemet double peut être utilisé dans une chaîne via la méthode normale d'échappement par barre oblique inverse. ("comme \"ça\" !")

'chaînes'
Les chaînes entre guillemets simples sont évaluées telles quelles. Leurs valeurs ne sont pas développées comme avec les chaînes entre guillemets doubles ci-dessus, et elles ne sont pas interprétées comme des références d'attributs.
`chaînes`
Les chaînes entre guillemets inversés sont évaluées en développant le contenu de la chaîne, comme décrit ci-dessus pour les chaînes entre guillemets doubles. La commande résultante donnée dans la chaîne est exécutée dans un sous-shell, et la sortie est prise comme une chaîne. Ce comportement est très similaire à celui des shells Unix.

Notez que pour des raisons de sécurité, la chaîne d'entrée est divisée en commande et arguments avant que le développement de la chaîne ne soit effectué.

Pour des raisons de performance, nous suggérons de limiter l'utilisation des chaînes entre guillemets inversés. L'exécution de programmes externes est relativement coûteuse, et l'exécution d'un grand nombre de programmes pour chaque requête peut rapidement consommer tout le temps CPU d'un serveur. Si vous pensez avoir besoin d'exécuter de nombreux programmes, nous suggérons de trouver des moyens alternatifs pour obtenir le même résultat. Dans certains cas, l'utilisation d'un vrai langage peut suffire.

/regex/im
Ces chaînes ne sont valides que du côté droit d'une comparaison, et seulement lorsque l'opérateur de comparaison est "=~" ou "!~". Ce sont des expressions régulières, telles qu'implémentées par la bibliothèque locale d'expressions régulières du système. Ce sont généralement des expressions régulières Posix.

Le 'i' final est optionnel et indique que la correspondance de l'expression régulière doit être effectuée sans tenir compte de la casse.

Le 'm' final est également optionnel et indique que les ancres '^' et '$' doivent correspondre aux nouvelles lignes ainsi qu'au début et à la fin de la chaîne sujet.

Si l'opérateur de comparaison est "=~", alors les parenthèses dans l'expression régulière définiront des variables contenant le texte correspondant, comme décrit ci-dessous dans la section RÉFÉRENCES D'ATTRIBUTS.

EXPANSIONS

Les attributs sont développés en utilisant la syntaxe de RÉFÉRENCE D'ATTRIBUT décrite ci-dessus, et en entourant la référence de "%{...}"

%{Référence-Attribut}

Le résultat sera une chaîne qui contient la valeur de l'attribut qui a été référencé, sous forme de chaîne imprimable. Si l'attribut n'existe pas, le résultat sera une chaîne vide.

Résultats des correspondances d'expressions régulières

Si une correspondance d'expression régulière a été précédemment effectuée, alors la variable spéciale %{0} contiendra une copie de la partie correspondante de la chaîne d'entrée. Les variables %{1} à %{32} contiendront les sous-chaînes correspondantes, en commençant par le groupe de capture le plus à gauche, et ainsi de suite. S'il y a plus de 32 groupes de capture, les résultats supplémentaires ne seront pas accessibles. Si le serveur est construit avec libpcre, les résultats des groupes de capture nommés sont disponibles en utilisant l'expansion "%{regex:groupe de capture}". Ils seront également accessibles en utilisant les variables décrites ci-dessus. Chaque fois qu'une expression régulière est évaluée, qu'elle corresponde ou non, les valeurs des groupes de capture seront effacées.

Obtention de résultats de bases de données

Il est utile d'interroger une base de données pour obtenir des informations, et d'utiliser le résultat dans une condition. La syntaxe suivante appellera un module, lui passera la chaîne donnée, et remplacera l'expansion de chaîne par la chaîne résultante renvoyée par le module. 
%{module: chaîne ...}

La syntaxe de la chaîne est spécifique au module. Veuillez lire la documentation du module pour plus de détails.

Syntaxe conditionnelle

Une syntaxe conditionnelle similaire à celle utilisée dans les shells Unix peut également être utilisée.
%{%{Foo}:-bar}
Si %{Foo} a une valeur, retourne cette valeur.
Sinon, retourne la chaîne littérale "bar".
%{%{Foo}:-%{Bar}}
Si %{Foo} a une valeur, retourne cette valeur.
Sinon, retourne l'expansion de %{Bar}.

Ces expansions conditionnelles peuvent être imbriquées à presque n'importe quelle profondeur, comme avec %{%{One}:-%{%{Two}:-%{Three}}}

Longueurs de chaînes et tableaux

Similaire à un shell Unix, il existe des moyens de faire référence aux longueurs de chaînes, et à la deuxième instance ou plus d'un attribut dans une liste. Si vous avez besoin de plus que cette fonctionnalité, nous vous suggérons d'utiliser un vrai langage.
%{strlen:chaîne}
Le nombre de caractères dans "chaîne". Si "chaîne" n'existe pas, alors la longueur n'existe pas non plus, au lieu d'être zéro.

La "chaîne" est développée avant que la longueur ne soit prise.

%{integer:Nom-Attribut}
La valeur entière du Nom-Attribut, au lieu du nom énuméré.

Par exemple, si une requête contient "Service-Type = Login-User", l'expansion de %{integer:Service-Type} produira "1".

%{hex:Nom-Attribut}
La valeur hexadécimale du Nom-Attribut, sous forme d'une série de chiffres hexadécimaux.

Par exemple, si une requête contient "Framed-IP-Address = 127.0.0.1", l'expansion de %{hex:Framed-IP-Address} produira "0x7f000001".

%{Nom-Attribut[#]}
Le nombre d'instances de Nom-Attribut.

Par exemple, si une requête contient "User-Name = bob", l'expansion de %{User-Name[#]} produira "1".

%{Nom-Attribut[*]}
Toutes les valeurs de Nom-Attribut, concaténées ensemble avec ',' comme séparateur.
%{Nom-Liste:[#]}
Le nombre d'attributs dans la liste nommée.
%{Nom-Liste:[*]}
Toutes les valeurs des attributs dans la liste nommée, concaténées ensemble avec ',' comme séparateur. Utilisez le translatage %{pairs:} pour obtenir une liste d'attributs et de valeurs.

Par exemple, si une réponse contient "Reply-Message = 'Hello', Reply-Message = 'bob' l'expansion de "%{reply:Reply-Message[*]} produira "Hello\nbob"

ASSIGNATIONS D'ATTRIBUTS

Les listes d'attributs décrites ci-dessus peuvent être modifiées en listant un ou plusieurs attributs dans une section "update". Une fois les attributs définis, ils peuvent être référencés comme décrit ci-dessus dans la section RÉFÉRENCES D'ATTRIBUTS.

La syntaxe suivante définit les attributs dans une section "update". Chaque attribut et valeur doivent être sur une seule ligne dans le fichier de configuration. Il n'est pas nécessaire d'ajouter de virgules ou de points-virgules après la valeur.

Référence-Attribut = valeur

Référence d'attribut

La Référence-Attribut doit être une référence (voir ci-dessus), utilisant un nom précédemment défini dans un dictionnaire. Si un nom non défini est utilisé, le serveur renverra une erreur et ne démarrera pas.
Opérateurs
L'opérateur utilisé pour assigner la valeur de l'attribut peut être l'un des suivants, avec la signification donnée.
=
Ajoute l'attribut à la liste, si et seulement si un attribut du même nom n'est pas déjà présent dans cette liste.

ATTRIBUTE ASSIGNMENTS

The following operators are used to assign values to attributes.

:=
Ajouter l'attribut à la liste. Si un attribut du même nom est déjà présent dans cette liste, sa valeur est remplacée par la valeur de l'attribut courant.
+=
Ajouter l'attribut à la fin de la liste, même si des attributs du même nom sont déjà présents dans la liste. Lorsque la partie droite de l'expression donne plusieurs valeurs, cela signifie qu'il faut ajouter toutes les valeurs à la fin de la liste.
^=
Ajouter l'attribut au début de la liste, même si des attributs du même nom sont déjà présents dans la liste. Lorsque la partie droite de l'expression donne plusieurs valeurs, cela signifie qu'il faut ajouter toutes les valeurs au début de la liste.

Opérateurs d'application et de filtrage

Les opérateurs suivants peuvent également être utilisés en plus de ceux listés ci-dessus. Leur fonction est d'appliquer ou de filtrer les attributs d'une liste.
-=
Supprimer tous les attributs correspondants de la liste. Le nom de l'attribut et la valeur doivent correspondre pour que l'attribut soit supprimé de la liste.
==
Conserver tous les attributs correspondants. Le nom de l'attribut et la valeur doivent correspondre pour que l'attribut reste dans la liste.

Notez que cet opérateur est très différent de l'opérateur '=' listé ci-dessus !

!=
Conserver tous les attributs ayant un nom correspondant, et une valeur différente de celle donnée.
<
Conserver tous les attributs ayant des valeurs inférieures à la valeur donnée ici. Toute valeur supérieure sera remplacée par la valeur donnée ici. Si aucun attribut n'existe, il est ajouté avec la valeur donnée ici, comme avec "+=".
<=
Conserver tous les attributs ayant des valeurs inférieures ou égales à la valeur donnée ici. Toute valeur supérieure sera remplacée par la valeur donnée ici. Si aucun attribut n'existe, il est ajouté avec la valeur donnée ici, comme avec "+=".
>
Conserver tous les attributs ayant des valeurs supérieures à la valeur donnée ici. Toute valeur inférieure sera remplacée par la valeur donnée ici. Si aucun attribut n'existe, il est ajouté avec la valeur donnée ici, comme avec "+=".
>=
Conserver tous les attributs ayant des valeurs supérieures ou égales à la valeur donnée ici. Toute valeur inférieure sera remplacée par la valeur donnée ici. Si aucun attribut n'existe, il est ajouté avec la valeur donnée ici, comme avec "+=".
!*
Supprimer toutes les occurrences de l'attribut nommé, quelle que soit sa valeur.
=~
Conserver tous les attributs ayant des valeurs qui correspondent à l'expression régulière donnée. Si aucun attribut ne correspond, rien d'autre n'est fait.
!~
Conserver tous les attributs ayant des valeurs qui ne correspondent pas à l'expression régulière donnée. Si aucun attribut ne correspond, rien d'autre n'est fait.
Valeurs

La valeur peut être une référence d'attribut ou une chaîne spécifique à l'attribut.

Lorsque la valeur est une référence d'attribut, elle doit prendre la forme de "&Nom-Attribut". Le signe '&' initial indique que la valeur est une référence. "Nom-Attribut" est le nom d'un attribut, tel que "User-Name" ou "request:User-Name". Lorsqu'une référence d'attribut est utilisée, les deux attributs doivent avoir le même type de données. Par exemple, "User-Name := &NAS-Port" est invalide, car "User-Name" est une chaîne de caractères et "NAS-Port" est un entier.

Nous recommandons d'utiliser la forme "Attribut-1 = &Attribut-2" pour les mises à jour, au lieu de "Attribut-1 = "%{Attribut-2}"". La première version copiera les données de l'attribut, quelle que soit sa forme. La seconde version convertira Attribut-2 en chaîne de caractères, puis l'analysera pour créer la valeur de Attribut-1. Cette seconde version est plus lente et plus fragile que la première.

Lorsque la valeur est une chaîne spécifique à l'attribut, il peut s'agir d'une chaîne, d'un entier, d'une adresse IP, etc. La valeur peut être développée comme décrit ci-dessus dans la section TYPES DE DONNÉES. Par exemple, spécifier "Framed-IP-Address = 127.0.0.1" entraînera la définition de l'attribut "Framed-IP-Address" à l'adresse IP "127.0.0.1". Cependant, l'utilisation de "Framed-IP-Address := module à exécuter avec une chaîne "127.0.0.1". La sortie du module "echo" sera alors analysée comme une adresse IP et placée dans l'attribut Framed-IP-Address.

Cette flexibilité signifie que vous pouvez attribuer une adresse IP en la spécifiant directement, ou en la faisant retourner par une requête de base de données, ou en la faisant retourner comme sortie d'un programme exécuté.

Lorsque les valeurs de chaîne sont finalement attribuées à un attribut, elles peuvent avoir une longueur maximale de 253 caractères. Cette limite est due en partie aux exigences du protocole et du serveur interne. C'est-à-dire que les chaînes dans le langage peuvent avoir près de 8 ko de long, par exemple pour une longue requête SQL. Cependant, la sortie de cette requête SQL ne devrait pas dépasser 253 caractères.

AUTRES MOTS-CLÉS

Les autres mots-clés du langage proviennent des noms des modules chargés par le serveur. Ces mots-clés dépendent à la fois des modules et de la configuration locale.

Certains utilisent des mots-clés définis dans le fichier de configuration par défaut :

fail
Faire en sorte que la requête soit traitée comme si une défaillance de la base de données s'était produite.
noop
Ne rien faire. Ceci sert également d'instruction au système de suivi des défaillances configurable que rien n'a été fait dans la section courante.
ok
Indiquer au serveur que la requête a été traitée correctement. Ce mot-clé peut être utilisé pour remplacer les échecs précédents, si l'administrateur local détermine que les échecs ne sont pas catastrophiques.
reject
Provoquer le rejet immédiat de la requête.

CODES DE RETOUR DES MODULES

Lorsqu'un module est appelé, il renvoie l'un des codes suivants à "unlang", avec la signification suivante.

	notfound        informations non trouvées
	noop            le module n'a rien fait
	ok              le module a réussi
	updated         le module a mis à jour la requête
	fail            le module a échoué
	reject          le module a rejeté la requête
	userlock        l'utilisateur a été verrouillé
	invalid         la configuration est invalide
	handled         le module a géré la requête lui-même

Ces codes de retour peuvent être testés dans une condition, comme décrit ci-dessus dans la section CONDITIONS.

Voir également le fichier doc/configurable_failover pour des méthodes supplémentaires de capture et de modification des codes de retour des modules.
