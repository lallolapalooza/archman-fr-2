UPS.CONF(5) Manuel NUT UPS.CONF(5)

NOM

ups.conf - Définitions d'onduleurs pour Network UPS Tools

DESCRIPTION

Ce fichier est lu par le contrôleur de pilotes upsdrvctl(8), les pilotes d'onduleurs qui utilisent le noyau commun (voir nutupsdrv(8)), nut-driver-enumerator(8), et le serveur de données NUT upsd(8). Le fichier commence par des directives globales, puis chaque onduleur a une section qui contient un certain nombre de directives qui définissent les paramètres de cet onduleur.

Une section d'onduleur commence par le nom de l'onduleur entre crochets, et se poursuit jusqu'au prochain nom d'onduleur entre crochets ou jusqu'à la fin du fichier (EOF). Le nom "default" est utilisé en interne dans upsd(8), vous ne pouvez donc pas l'utiliser dans ce fichier.

Vous devez définir les éléments driver et port pour chaque entrée. Tout le reste dans une section est facultatif. Un exemple simple pourrait ressembler à ceci :

[mononduleur]
        driver = blazer_ser
        port = /dev/ttyS0
        desc = "Onduleur du serveur web"

Une version légèrement plus compliquée inclut quelques extras pour la partie spécifique au matériel du pilote :

[grandonduleur]
        driver = apcsmart
        port = /dev/cua00
        cable = 940-0095B
        sdtype = 2
        desc = "Onduleur du serveur de base de données"

Dans ce cas, le pilote apcsmart(8) recevra des variables appelées "cable" et "sdtype" qui ont une signification spéciale. Consultez les pages de manuel de vos pilotes pour savoir quelles variables sont prises en charge et ce qu'elles font.

Voici un autre exemple, lors de la connexion d'un onduleur série sous Windows :

[onduleur-windows]
        driver = mge-shut
        port = "\\\\.\\COM10"
        desc = "Onduleur sur une machine Windows"

NOTES IMPORTANTES

•Le contenu de ce fichier doit être en ASCII pur (les codes de caractères qui ne sont pas dans la plage seront ignorés avec un message d'avertissement).
•Équilibrez les permissions utilisateur d'exécution pour accéder au fichier (et peut-être au répertoire dans lequel il se trouve) afin que seuls upsd et les pilotes puissent le lire ; l'accès en écriture n'est pas nécessaire. Il est courant d'utiliser chown root:nut et chmod 640 pour définir des permissions de fichier acceptables.
•Les paquets (et les recettes de compilation) préparent généralement un ensemble de comptes utilisateur et de groupe pour NUT. Les compilations personnalisées avec une configuration minimale peuvent même utiliser nobody:nogroup ou similaire, ce qui est intrinsèquement non sécurisé.
•Sur les systèmes avec des préoccupations de sécurité supplémentaires, les pilotes NUT, le serveur de données doivent s'exécuter sous des comptes utilisateur distincts qui seraient membres d'un même groupe pour un accès partagé aux fichiers de socket Unix locaux et au répertoire dans lequel ils se trouvent, ainsi que pour la lecture de ups.conf, mais des groupes différents pour l'accès aux autres fichiers de configuration. Cela nécessiterait que certains démons utilisent des paramètres RUN_AS_USER et/ou RUN_AS_GROUP personnalisés pour remplacer la seule valeur intégrée.
•Notez que les clients de surveillance, de journalisation, etc. sont uniquement en réseau. Ils n'ont pas besoin d'accéder à ces fichiers et répertoires, et peuvent s'exécuter dans un groupe et un utilisateur totalement indépendants.
•Gardez à l'esprit la sécurité des éventuelles copies de sauvegarde de ce fichier, par exemple les fichiers d'archive dans lesquels il pourrait se retrouver.

DIRECTIVES GLOBALES

chroot

Facultatif. Le pilote effectuera un chroot(2) vers ce répertoire lors de l'initialisation. Cela peut être utile pour sécuriser les systèmes.

driverpath

Facultatif. Nom du chemin du répertoire dans lequel se trouvent les exécutables des pilotes d'onduleur. Si vous ne spécifiez pas cela, les programmes recherchent dans un répertoire par défaut intégré, qui est souvent /usr/local/ups/bin.

statepath

Facultatif. Nom du chemin du répertoire dans lequel les pilotes d'onduleur doivent placer leurs sockets d'état pour la communication locale avec le serveur de données upsd, plutôt que l'emplacement par défaut qui a été compilé dans le programme, qui est souvent /var/state/ups.

Notez que les pilotes doivent utiliser le même chemin que upsd, donc le serveur de données préférera ce réglage de la section globale de ups.conf, s'il est présent, à son propre réglage dans upsd.conf.

La variable d'environnement NUT_STATEPATH définie par l'appelant peut outrepasser ce réglage.

maxstartdelay

Facultatif. Identique au champ UPS du même nom, mais c'est la valeur par défaut pour les onduleurs qui n'ont pas le champ.

maxretry

Facultatif. Spécifiez le nombre de tentatives de démarrage du (des) pilote(s), en cas d'échec, avant d'abandonner. Un délai de retrydelay est inséré entre chaque tentative. La prudence est de mise lors de l'utilisation de cette option, car elle peut avoir un impact sur le temps de démarrage de votre système.

La valeur par défaut est 1 tentative.

nowait

Facultatif. Spécifiez à upsdrvctl de ne pas attendre du tout que le (les) pilote(s) exécute(nt) la commande demandée.

La valeur par défaut (omission) est d'attendre.

Elle peut être outrepassée par la variable d'environnement NUT_IGNORE_NOWAIT (par exemple, utilisée pour contourner certains problèmes avec systemd sinon).

retrydelay

Facultatif. Spécifiez le délai entre chaque tentative de redémarrage du (des) pilote(s), comme spécifié par maxretry. La prudence est de mise lors de l'utilisation de cette option, car elle peut avoir un impact sur le temps de démarrage de votre système.

La valeur par défaut est de 5 secondes.

pollinterval

Facultatif. L'état de l'onduleur sera rafraîchi après un délai maximum contrôlé par ce réglage. Il s'agit normalement de 2 secondes. Ce réglage peut être utile si le pilote crée trop de charge sur votre système de surveillance ou votre réseau.

Notez que certains pilotes (tels que usbhid-ups(8), snmp-ups(8) et nutdrv_qx(8)) ont également une option appelée pollfreq qui contrôle la fréquence à laquelle certains des paramètres moins critiques sont interrogés. Les détails sont fournis dans les pages de manuel des pilotes respectifs.

synchronous

Facultatif. Les pilotes fonctionnent par défaut en mode asynchrone initialement, mais peuvent revenir en mode synchrone si les écritures sur le socket serveur échouent (c'est-à-dire synchronous=auto). Cela signifie que toutes les données sont poussées par le pilote sur le socket de communication vers upsd (socket Unix sur Unix, pipe nommé sur Windows) sans attendre que ces données soient effectivement consommées. Avec certains matériels, tels que les ePDUs, qui peuvent produire beaucoup de données, le mode asynchrone peut provoquer une congestion, entraînant le remplissage du socket et l'apparence de déconnexion du pilote. Dans ce cas, le pilote fournira le message de débogage suivant : 
write XX bytes to socket Y failed

En activant le drapeau synchronous (valeur = yes), le pilote attendra que les données soient consommées par upsd, avant d'en publier davantage. Cela peut être activé globalement ou par pilote.

La valeur par défaut de auto agit comme no (c'est-à-dire mode asynchrone) pour la compatibilité ascendante du comportement du pilote, jusqu'à ce que les communications échouent avec une condition "Resource temporarily unavailable", qui se produit lorsque le pilote a de nombreux points de données à envoyer en rafale, et que le serveur ne peut pas les gérer assez rapidement, de sorte que le tampon se remplit.

user

Facultatif. Remplace le nom d'utilisateur non privilégié par défaut intégré pour tous les pilotes de périphériques NUT. Voir la discussion de l'option -u dans nutupsdrv(8) pour plus de détails.

group

Facultatif. Remplace le nom de groupe non privilégié par défaut intégré (et/ou de la section globale) pour tous les pilotes de périphériques NUT, utilisé pour l'accès au fichier socket. Voir la discussion de l'option -g dans nutupsdrv(8) pour plus de détails. Ceci peut être particulièrement utile pour garantir l'accès aux nœuds dynamiques du système de fichiers de périphériques, tels que le support de l'ajout/retrait à chaud USB (ou USB-série), ou avec les systèmes de fichiers de périphériques régénérés par un OS à chaque redémarrage.

debug_min INTEGER

Facultatif. Spécifiez un niveau de débogage minimum pour tous les démons pilotes, par exemple pour dépanner un déploiement, sans impacter directement le mode d'exécution en avant-plan ou en arrière-plan. L'option de ligne de commande -D ne peut qu'augmenter ce niveau de verbosité.

LIBUSB_DEBUG INTEGER

Facultatif. Pour le dépannagedes pilotes NUT compatibles USB à l'exécution, vous pouvez spécifier la verbosité du débogage spécifique à LibUSB sous forme de nu

CHAMPS UPS

driver

Requis. Cela spécifie quel programme surveillera cet UPS. Vous devez spécifier celui qui est compatible avec votre matériel. Voir nutupsdrv(8) pour plus d'informations sur les pilotes en général et des pointeurs vers les pages de manuel des pilotes spécifiques.

port

Requis. C'est le port série auquel l'UPS est connecté. Sur un système Linux, le premier port série est généralement /dev/ttyS0. Sur les systèmes FreeBSD et similaires, il s'agira probablement de /dev/cuaa0. Sur Windows, le premier port série sera "\\\\.\\COM1" (notez les barres obliques échappées).

user

Optionnel. Remplace le nom d'utilisateur non privilégié compilé (et/ou de la section globale) pour un pilote de périphérique NUT particulier. Voir la discussion de l'option -u dans nutupsdrv(8) pour les détails. Ceci peut être particulièrement utile pour assurer l'accès aux nœuds dynamiques du système de fichiers de périphériques, tels que le support de branchement à chaud USB (ou série via USB), ou avec des systèmes de fichiers de périphériques régénérés par un système d'exploitation à chaque redémarrage.

group

Optionnel. Remplace le nom de groupe non privilégié compilé (et/ou de la section globale) pour un pilote de périphérique NUT particulier, utilisé pour l'accès au fichier socket. Voir la discussion de l'option -g dans nutupsdrv(8) pour les détails. Ceci peut être particulièrement utile pour assurer l'accès aux nœuds dynamiques du système de fichiers de périphériques, tels que le support de branchement à chaud USB (ou série via USB), ou avec des systèmes de fichiers de périphériques régénérés par un système d'exploitation à chaque redémarrage.

sdorder

Optionnel. Lorsque vous avez plusieurs UPS sur votre système, vous devez généralement les éteindre dans un ordre précis. upsdrvctl éteint tous les 0, puis les 1, 2, et ainsi de suite. Pour exclure un UPS de la séquence d'arrêt, réglez ceci sur -1.

La valeur par défaut pour ce paramètre est 0.

sdcommands

Optionnel. Liste séparée par des virgules des noms de commandes instantanées à envoyer à l'UPS lors de la demande d'arrêt.

La logique par défaut est intégrée dans chaque pilote (lorsque pris en charge) et peut être référencée ici comme la valeur shutdown.default.

Le cas d'utilisation principal est pour les appareils dont les pilotes prennent en charge "nativement" l'essai de plusieurs commandes, mais l'ordre intégré de ces appels est une commande mal gérée par le modèle d'appareil spécifique (de sorte que la gestion est rapportée comme réussie et la boucle s'arrête, mais rien ne se passe en ce qui concerne l'alimentation de la charge).

Un autre cas d'utilisation est la différenciation des scénarios d'arrêt automatique où l'UPS et sa charge doivent rester "OFF" (par exemple, en construisant une coupure d'urgence) par rapport à ceux où la charge doit reprendre automatiquement le travail lorsqu'il est sûr de le faire. REMARQUE : Cela nécessiterait *actuellement* de modifier ups.conf pour de tels cas avant que nutshutdown ne voie le fichier ; mais pourrait être mieux automatisé dans les futures versions de NUT.


Note
Les commandes fournies par l'utilisateur peuvent être autres qu'un arrêt réel, par exemple, un bipeur pour tester que l'INSTCMD s'est produit tel quel et quand prévu, et que l'appareil a été contacté, sans impacter la charge alimentée par l'UPS.

allow_killpower

Optionnel. Ceci vous permet de demander la commande instantanée driver.killpower, pour appeler immédiatement l'implémentation par défaut spécifique au pilote de la méthode upsdrv_shutdown(), avec le même effet que lorsque un pilote NUT est démarré avec le drapeau de commande -k. Cette option peut être basculée avec upsrw(8) comme driver.flag.allow_killpower pendant l'exécution.

desc

Optionnel. Ceci vous permet de définir une brève description que upsd fournira aux clients qui demandent une liste des équipements connectés.

nolock

Optionnel. Lorsque vous spécifiez ceci, le pilote ignore les routines de verrouillage du port chaque fois qu'il démarre. Cela peut permettre à d'autres processus de s'emparer du port si vous en démarrez plus d'un accidentellement.

Vous ne devriez utiliser cela que si votre système ne fonctionne pas sans cela.

Cela peut être nécessaire sur les systèmes Mac OS X.

ignorelb

Optionnel. Lorsque vous spécifiez ceci, le pilote ignore un indicateur de batterie faible signalé par l'UPS (certains appareils s'éteignent presque immédiatement après avoir défini cet indicateur, ou le signalent dès que le secteur est coupé). Au lieu de cela, il utilisera l'une des conditions suivantes pour déterminer quand la batterie est faible : 
battery.charge < battery.charge.low
battery.runtime < battery.runtime.low

L'idée est de définir les niveaux battery.charge.low et/ou battery.runtime.low dans ups.conf à une valeur qui donne suffisamment de temps pour arrêter proprement votre système :

override.battery.charge.low = 30
override.battery.runtime.low = 180

Pour que cela fonctionne, votre UPS doit être capable de signaler (de manière fiable) la charge et/ou l'autonomie restante sur batterie. À utiliser avec prudence !

maxstartdelay

Optionnel. Ceci peut être défini comme une variable globale au-dessus de votre première définition d'UPS et peut également être défini dans une section UPS. Cette valeur contrôle combien de temps upsdrvctl attendra que le pilote ait fini de démarrer. Cela évite que votre système ne se bloque en raison d'un pilote ou d'un UPS défectueux.

Notez qu'après ce délai, upsdrvctl continuera ses affaires (qu'il s'agisse de réessayer le même pilote si maxretry>1, ou d'essayer un autre pilote s'il les démarre tous, ou simplement de sortir éventuellement) ; cependant, chaque processus de pilote "bloqué" le plus récemment démarré peut continuer à s'initialiser en arrière-plan, et pourrait même réussir éventuellement.

Ils ne seraient pas activement tués par upsdrvctl après l'expiration de ce délai.

La valeur par défaut est de 75 secondes.

maxretry

Optionnel. Ceci peut être défini comme une variable globale au-dessus de votre première définition d'UPS et peut également être défini dans une section UPS. Voir l'explication ci-dessus, dans la section globale.

retrydelay

Optionnel. Ceci peut être défini comme une variable globale au-dessus de votre première définition d'UPS et peut également être défini dans une section UPS. Voir l'explication ci-dessus, dans la section globale.

synchronous

Optionnel. Identique à la directive globale du même nom, mais ceci est pour un appareil spécifique.

usb_set_altinterface[=altinterface]

Optionnel. Force le code USB à appeler usb_set_altinterface(0), comme cela a été fait dans NUT 2.7.2 et les versions antérieures. Cela ne devrait pas être nécessaire, car la valeur par défaut pour bAlternateSetting (comme indiqué dans lsusb) est zéro sur tous les appareils USB observés à ce jour. Cependant, cet appel redondant à usb_set_altinterface() empêche certains UPS de fonctionner sur Mac OS X. Si votre UPS nécessite de définir explicitement l'interface alternative, incluez ce drapeau, et envoyez un e-mail à la liste nut-upsdev avec des détails sur votre UPS et votre système d'exploitation.

usb_config_index, usb_hid_rep_index, usb_hid_desc_index, usb_hid_ep_in, usb_hid_ep_out

Optionnel. Force l'utilisation d'index d'interface, de point de terminaison, de descripteur spécifiques, etc., plutôt que la valeur par défaut 0 (rarement d'autres valeurs dans certains pilotes pour certains appareils connus pour utiliser des nombres non nuls). Spécifié sous forme de nombre hexadécimal.

En règle générale pour la découverte de usb_hid_desc_index, vous pouvez voir des valeurs plus grandes de wDescriptorLength (environ 600+ octets) dans les rapports de lsusb ou d'outils similaires.

default.<variable>

Optionnel. Définit une valeur par défaut pour <variable> qui est utilisée au cas où l'UPS ne fournirait pas de valeur, mais sera écrasée si une valeur est disponible auprès de l'UPS : 
default.input.voltage.nominal = 230

Ce qui précède indiquera que la tension d'entrée nominale est de 230, sauf si l'UPS nous indique le contraire.

override.<variable>

Optionnel. Définit une valeur pour <value> qui remplace toute valeur pouvant être lue depuis l'UPS. Utilisé pour remplacer les valeurs de l'UPS qui sont manifestement incorrectes (certains appareils signalent des valeurs incorrectes pour la tension de la batterie par exemple) : 
override.battery.voltage.nominal = 12

À utiliser avec prudence ! Cela ne changera que l'apparence de la variable vis-à-vis du monde extérieur, intérieurement dans l'UPS, la valeur d'origine est utilisée.

Tous les autres champs sont transmis à la partie matérielle du pilote. Voir ces manuels pour la liste de ce qui est autorisé.

debug_min ENTIER

Optionnel. Spécifie un niveau de débogage minimum pour ce démon pilote, par exemple pour le dépannage d'un déploiement, sans impacter directement le mode de fonctionnement en avant-plan ou en arrière-plan. Si debug_min global est également défini, ce paramètre au niveau du pilote le remplace. L'option de ligne de commande -D ne peut qu'augmenter ce niveau de verbosité.

LIBUSB_DEBUG ENTIER

Optionnel. Pour le dépannage à l'exécution des pilotes NUT compatibles USB, vous pouvez spécifier la verbosité du débogage spécifique à LibUSB sous forme de valeur numérique telle que 4 ("Tous les messages sont émis").

Pour plus de détails, y compris les valeurs actuellement prises en charge pour votre version de la bibliothèque, consultez par exemple :

•https://libusb.sourceforge.io/api-1.0/
•https://libusb.sourceforge.io/api-1.0/group__libusb__lib.html

INTÉGRATION

upsdrvctl(8) utilise ce fichier pour démarrer et arrêter les pilotes.

Les pilotes eux-mêmes obtiennent également des données de configuration à partir de ce fichier. Chaque pilote recherche sa section et l'utilise pour se configurer.

upsd(8) apprend quels UPS sont installés sur ce système en lisant ce fichier. Si ce système est appelé "doghouse" et que vous avez défini un UPS dans votre ups.conf appelé "snoopy", alors vous pouvez le surveiller depuis upsc(8) ou similaire comme "snoopy@doghouse".

ups.conf(5) — Network UPS Tools 2.8.4

NAME

ups.conf — UPS driver configuration file

DESCRIPTION

The ups.conf file is used to configure the various drivers available in the Network UPS Tools (NUT) package.

This file is not a static text file. It is a database of UPS definitions. Each UPS definition is a section starting with [upsname], where upsname is the name of the UPS that you want to manage.

Within each section, you can specify a number of tags that control how the driver is loaded and what parameters are passed to it.

The following are the primary tags that can be specified within a ups.conf section:

driver
This is the critical directive. It tells the UPS driver which code to load. This is usually the name of the hardware interface you are using. For example, to use the serial driver, you would use driver = serial.
port
This specifies the communication port for the driver. The format of this parameter depends on the driver being used. For serial drivers, it's usually the device name of the serial port (e.g., /dev/ttyS0, /dev/ttyUSB0). For network drivers, it's the hostname or IP address of the UPS. Consult the man page for the specific driver you are using for its expected format.
desc
A descriptive string for the UPS. This is used for informational purposes and can be displayed by clients. For example, desc = "My primary office UPS".
synchronize
A boolean value (yes or no) that controls whether the UPS driver should attempt to synchronize with the UPS. This is useful for drivers that need to communicate with the UPS in a specific way to initiate a shutdown. For most drivers, this should be set to yes.
maxstartdelay
The maximum time (in seconds) that the driver will wait for the UPS to become available after it is started. The default is 45 seconds.
desc
A descriptive string for the UPS. This is used for informational purposes and can be displayed by clients. For example, desc = "My primary office UPS".
maxretry
The number of times the driver should retry communicating with the UPS before giving up. The default is 3.
offdelay
The delay (in seconds) before the driver attempts to turn the UPS off. This is typically used in conjunction with a shutdown command to allow connected systems time to shut down gracefully.
sdorder
The shutdown order for this UPS. This is used when multiple UPS systems are managed and need to be shut down in a specific sequence.
startup
Specifies how the UPS should be handled on system startup. Possible values are:
auto
Attempt to start the driver automatically.
manual
Do not start the driver automatically. It must be started manually.
stopdelay
The delay (in seconds) before the driver attempts to stop the UPS. This is used to allow connected systems time to shut down gracefully before the UPS itself is powered off.
pollfreq
The frequency (in seconds) at which the driver should poll the UPS for status updates. The default is 30 seconds.
pollinterval
The interval (in seconds) between status checks. This is similar to pollfreq but may be used by some drivers for different purposes. The default is 30 seconds.

This is a mandatory parameter for most drivers. It specifies the type of communication protocol or interface used by the UPS. For example, technology = usb, technology = snmp, technology = serial.

In addition to these primary directives, drivers may support additional, driver-specific directives. These are documented in the man pages for each individual driver.

IMPORTANT NOTES

  • The ups.conf file should be owned by root and have permissions set to 644 (read/write for owner, read for group and others). Sensitive information, such as passwords for network-based UPS systems, should be handled with care.
  • It is highly recommended to use the upsdrvctl utility to start, stop, and manage UPS drivers. Manually editing ups.conf and then starting the drivers without using upsdrvctl can lead to unexpected behavior.
  • Comments can be added to the ups.conf file by starting a line with a hash symbol (#).

GLOBAL DIRECTIVES

The ups.conf file can also contain global directives that apply to all UPS drivers unless overridden by a specific UPS section. These directives are typically placed at the beginning of the file, before any [upsname] sections.

upsmon
Specifies the upsmon configuration file to use. If not specified, the default is /etc/ups/upsmon.conf.
mondir
Specifies the directory where monitor files are stored. The default is /var/run/nut/.

UPS_FIELDS

Some drivers expose specific fields that can be monitored. These fields are typically listed in the man page for the individual driver. They can be accessed using the NUT client utilities like upsc. For example, to view the battery charge level of a UPS named "myups", you might use:

upsc myups battery.charge

INTEGRATION

The ups.conf file is central to the NUT system. It defines which UPS devices are managed and how they are connected to the system. The upsd daemon reads this file at startup to determine which drivers to load and monitor.
