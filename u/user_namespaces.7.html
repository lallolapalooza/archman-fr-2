NOM

user_namespaces - aperçu des espaces de noms utilisateur Linux

DESCRIPTION

Pour un aperçu des espaces de noms, voir namespaces(7).

Les espaces de noms utilisateur isolent les identifiants et attributs liés à la sécurité, en particulier les identifiants utilisateur et groupe (voir credentials(7)), le répertoire racine, les clés (voir keyrings(7)) et les capacités (voir capabilities(7)). Les identifiants utilisateur et groupe d'un processus peuvent être différents à l'intérieur et à l'extérieur d'un espace de noms utilisateur. En particulier, un processus peut avoir un identifiant utilisateur normal non privilégié en dehors d'un espace de noms utilisateur tout en ayant un identifiant utilisateur de 0 à l'intérieur de l'espace de noms ; en d'autres termes, le processus dispose de tous les privilèges pour les opérations à l'intérieur de l'espace de noms utilisateur, mais est non privilégié pour les opérations à l'extérieur de celui-ci.

Espaces de noms imbriqués, appartenance à un espace de noms

Les espaces de noms utilisateur peuvent être imbriqués ; c'est-à-dire que chaque espace de noms utilisateur —sauf l'espace de noms initial (« racine— a un espace de noms utilisateur parent, et peut avoir zéro ou plusieurs espaces de noms utilisateur enfants. L'espace de noms utilisateur parent est l'espace de noms utilisateur du processus qui crée l'espace de noms utilisateur via un appel à unshare(2) ou clone(2) avec le drapeau CLONE_NEWUSER.

Le noyau impose (depuis Linux 3.11) une limite de 32 niveaux d'imbrication d'espaces de noms utilisateur. Les appels à unshare(2) ou clone(2) qui dépasseraient cette limite échoueront avec l'erreur EUSERS.

Chaque processus est membre d'un seul espace de noms utilisateur. Un processus créé via fork(2) ou clone(2) sans le drapeau CLONE_NEWUSER est membre du même espace de noms utilisateur que son parent. Un processus mono-thread peut rejoindre un autre espace de noms utilisateur avec setns(2) s'il possède la capacité CAP_SYS_ADMIN dans cet espace de noms ; ce faisant, il obtient un ensemble complet de capacités dans cet espace de noms.

Un appel à clone(2) ou unshare(2) avec le drapeau CLONE_NEWUSER fait du nouveau processus enfant (pour clone(2)) ou de l'appelant (pour unshare(2)) un membre du nouvel espace de noms utilisateur créé par l'appel.

L'opération ioctl(2) NS_GET_PARENT peut être utilisée pour découvrir la relation parentale entre les espaces de noms utilisateur ; voir ioctl_nsfs(2).

Une tâche qui modifie l'un de ses identifiants effectifs verra sa capacité de dump réinitialisée à la valeur définie dans /proc/sys/fs/suid_dumpable. Cela peut affecter la propriété des fichiers proc des processus enfants et peut donc entraîner un manque de permissions pour le processus parent d'écrire dans les fichiers de mapping des processus enfants exécutés dans un nouvel espace de noms utilisateur. Dans de tels cas, rendre le processus parent dumpable, en utilisant PR_SET_DUMPABLE dans un appel à prctl(2), avant de créer un processus enfant dans un nouvel espace de noms utilisateur peut résoudre ce problème. Voir prctl(2) et proc(5) pour plus de détails sur la façon dont la propriété est affectée.

Capacités

Le processus enfant créé par clone(2) avec le drapeau CLONE_NEWUSER démarre avec un ensemble complet de capacités dans le nouvel espace de noms utilisateur. De même, un processus qui crée un nouvel espace de noms utilisateur en utilisant unshare(2) ou qui rejoint un espace de noms utilisateur existant en utilisant setns(2) obtient un ensemble complet de capacités dans cet espace de noms. En revanche, ce processus n'a aucune capacité dans l'espace de noms utilisateur parent (dans le cas de clone(2)) ou précédent (dans le cas de unshare(2) et setns(2)), même si le nouvel espace de noms est créé ou rejoint par l'utilisateur root (c'est-à-dire un processus avec l'identifiant utilisateur 0 dans l'espace de noms racine).

Notez qu'un appel à execve(2) provoquera le recalcul des capacités d'un processus de la manière habituelle (voir capabilities(7)). Par conséquent, à moins que le processus n'ait un identifiant utilisateur de 0 dans l'espace de noms, ou que le fichier exécutable n'ait un masque de capacités héritables non vide, le processus perdra toutes ses capacités. Voir la discussion sur les mappages d'identifiants utilisateur et groupe ci-dessous.

Un appel à clone(2) ou unshare(2) utilisant le drapeau CLONE_NEWUSER ou un appel à setns(2) qui déplace l'appelant vers un autre espace de noms utilisateur définit les indicateurs « securebits » (voir capabilities(7)) à leurs valeurs par défaut (tous les indicateurs désactivés) dans l'enfant (pour clone(2)) ou l'appelant (pour unshare(2) ou setns(2)). Notez que parce que l'appelant ne possède plus de capacités dans son espace de noms utilisateur d'origine après un appel à setns(2), il n'est pas possible pour un processus de réinitialiser ses indicateurs « securebits » tout en conservant son appartenance à l'espace de noms utilisateur en utilisant une paire d'appels setns(2) pour passer à un autre espace de noms utilisateur puis revenir à son espace de noms utilisateur d'origine.

Les règles pour déterminer si un processus possède une capacité dans un espace de noms utilisateur particulier sont les suivantes :

•
Un processus possède une capacité à l'intérieur d'un espace de noms utilisateur s'il en est membre et s'il possède la capacité dans son ensemble de capacités effectives. Un processus peut obtenir des capacités dans son ensemble de capacités effectives de diverses manières. Par exemple, il peut exécuter un programme set-user-ID ou un exécutable avec des capacités de fichier associées. De plus, un processus peut obtenir des capacités via l'effet de clone(2), unshare(2), ou setns(2), comme déjà décrit.
•
Si un processus possède une capacité dans un espace de noms utilisateur, alors il possède cette capacité dans tous les espaces de noms enfants (et plus éloignés) également.
•
Lorsqu'un espace de noms utilisateur est créé, le noyau enregistre l'identifiant utilisateur effectif du processus créateur comme étant le « propriétaire » de l'espace de noms. Un processus qui réside dans le parent de l'espace de noms utilisateur et dont l'identifiant utilisateur effectif correspond au propriétaire de l'espace de noms possède toutes les capacités dans l'espace de noms. En vertu de la règle précédente, cela signifie que le processus possède toutes les capacités dans tous les espaces de noms utilisateur descendants plus éloignés également. L'opération ioctl(2) NS_GET_OWNER_UID peut être utilisée pour découvrir l'identifiant utilisateur du propriétaire de l'espace de noms ; voir ioctl_nsfs(2).

Effet des capacités dans un espace de noms utilisateur

Posséder une capacité à l'intérieur d'un espace de noms utilisateur permet à un processus d'effectuer des opérations (qui nécessitent des privilèges) uniquement sur les ressources régies par cet espace de noms. En d'autres termes, posséder une capacité dans un espace de noms utilisateur permet à un processus d'effectuer des opérations privilégiées sur des ressources qui sont régies par des espaces de noms (non utilisateur) appartenant à (associés à) l'espace de noms utilisateur (voir la sous-section suivante).

D'autre part, il existe de nombreuses opérations privilégiées qui affectent des ressources qui ne sont associées à aucun type d'espace de noms, par exemple, modifier l'heure système (calendrier) (régie par CAP_SYS_TIME), charger un module noyau (régie par CAP_SYS_MODULE), et créer un périphérique (régie par CAP_MKNOD). Seul un processus disposant de privilèges dans l'espace de noms initial peut effectuer de telles opérations.

Détenir CAP_SYS_ADMIN dans l'espace de noms utilisateur qui possède l'espace de noms de montage d'un processus permet à ce processus de créer des montages de liaison et de monter les types de systèmes de fichiers suivants :

•
/proc (depuis Linux 3.8)
•
/sys (depuis Linux 3.8)
•
devpts (depuis Linux 3.9)
•
tmpfs(5) (depuis Linux 3.9)
•
ramfs (depuis Linux 3.9)
•
mqueue (depuis Linux 3.9)
•
bpf (depuis Linux 4.4)
•
overlayfs (depuis Linux 5.11)

Détenir CAP_SYS_ADMIN dans l'espace de noms utilisateur qui possède l'espace de noms cgroup d'un processus permet (depuis Linux 4.6) à ce processus de monter le système de fichiers cgroup version 2 et les hiérarchies nommées de cgroup version 1 (c'est-à-dire les systèmes de fichiers cgroup montés avec l'option "none,name=").

Détenir CAP_SYS_ADMIN dans l'espace de noms utilisateur qui possède l'espace de noms PID d'un processus permet (depuis Linux 3.8) à ce processus de monter les systèmes de fichiers /proc.

Cependant, le montage de systèmes de fichiers basés sur des blocs ne peut être effectué que par un processus qui détient CAP_SYS_ADMIN dans l'espace de noms utilisateur initial.

Interaction des espaces de noms utilisateur et d'autres types d'espaces de noms

Depuis Linux 3.8, les processus non privilégiés peuvent créer des espaces de noms utilisateur, et les autres types d'espaces de noms peuvent être créés avec simplement la capacité CAP_SYS_ADMIN dans l'espace de noms utilisateur de l'appelant.

Lorsqu'un espace de noms non utilisateur est créé, il est possédé par l'espace de noms utilisateur dont le processus créateur était membre au moment de la création de l'espace de noms. Les opérations privilégiées sur les ressources gérées par l'espace de noms non utilisateur nécessitent que le processus ait les capacités nécessaires dans l'espace de noms utilisateur qui possède l'espace de noms non utilisateur.

Si CLONE_NEWUSER est spécifié avec d'autres drapeaux CLONE_NEW* dans un seul appel clone(2) ou unshare(2), l'espace de noms utilisateur est garanti d'être créé en premier, donnant à l'enfant (clone(2)) ou à l'appelant (unshare(2)) des privilèges sur les espaces de noms restants créés par l'appel. Ainsi, il est possible pour un appelant non privilégié de spécifier cette combinaison de drapeaux.

Lorsqu'un nouvel espace de noms (autre qu'un espace de noms utilisateur) est créé via clone(2) ou unshare(2), le noyau enregistre l'espace de noms utilisateur du processus créateur comme propriétaire du nouvel espace de noms. (Cette association ne peut pas être modifiée.) Lorsqu'un processus dans le nouvel espace de noms effectue ensuite des opérations privilégiées qui agissent sur des ressources globales isolées par l'espace de noms, les vérifications d'autorisation sont effectuées selon les capacités du processus dans l'espace de noms utilisateur que le noyau a associé au nouvel espace de noms. Par exemple, supposons qu'un processus tente de changer le nom d'hôte (sethostname(2)), une ressource gérée par l'espace de noms UTS. Dans ce cas, le noyau déterminera quel espace de noms utilisateur possède l'espace de noms UTS du processus, et vérifiera si le processus a la capacité requise (CAP_SYS_ADMIN) dans cet espace de noms utilisateur.

L'opération NS_GET_USERNS ioctl(2) peut être utilisée pour découvrir l'espace de noms utilisateur qui possède un espace de noms non utilisateur ; voir ioctl_nsfs(2).

Mappages des ID utilisateur et groupe : uid_map et gid_map

Lorsqu'un espace de noms utilisateur est créé, il commence sans mappage des ID utilisateur (ID groupe) vers l'espace de noms utilisateur parent. Les fichiers /proc/pid/uid_map et /proc/pid/gid_map (disponibles depuis Linux 3.5) exposent les mappages des ID utilisateur et groupe à l'intérieur de l'espace de noms utilisateur pour le processus pid. Ces fichiers peuvent être lus pour afficher les mappages dans un espace de noms utilisateur et écrits (une seule fois) pour définir les mappages.

La description dans les paragraphes suivants explique les détails pour uid_map ; gid_map est exactement la même chose, mais chaque occurrence de "ID utilisateur" est remplacée par "ID groupe".

Le fichier uid_map expose le mappage des ID utilisateur de l'espace de noms utilisateur du processus pid vers l'espace de noms utilisateur du processus qui a ouvert uid_map (mais voir une qualification à ce point ci-dessous). En d'autres termes, les processus qui se trouvent dans des espaces de noms utilisateur différents verront potentiellement des valeurs différentes en lisant un fichier uid_map particulier, en fonction des mappages des ID utilisateur pour les espaces de noms utilisateur des processus lecteurs.

Chaque ligne dans le fichier uid_map spécifie un mappage 1 pour 1 d'une plage d'ID utilisateur contigus entre deux espaces de noms utilisateur. (Lorsqu'un espace de noms utilisateur est créé pour la première fois, ce fichier est vide.) La spécification dans chaque ligne prend la forme de trois nombres délimités par des espaces blancs. Les deux premiers nombres spécifient l'ID utilisateur de départ dans chacun des deux espaces de noms utilisateur. Le troisième nombre spécifie la taille de la plage mappée. En détail, les champs sont interprétés comme suit :

(1)
Le début de la plage d'ID utilisateur dans l'espace de noms utilisateur du processus pid.
(2)
Le début de la plage d'ID utilisateur vers laquelle les ID utilisateur spécifiés par le champ un sont mappés. L'interprétation du champ deux dépend si le processus qui a ouvert uid_map et le processus pid sont dans le même espace de noms utilisateur, comme suit :
(a)
Si les deux processus sont dans des espaces de noms utilisateur différents : le champ deux est le début d'une plage d'ID utilisateur dans l'espace de noms utilisateur du processus qui a ouvert uid_map.
(b)
Si les deux processus sont dans le même espace de noms utilisateur : le champ deux est le début de la plage d'ID utilisateur dans l'espace de noms utilisateur parent du processus pid. Ce cas permet à celui qui ouvre uid_map (le cas courant étant l'ouverture de /proc/self/uid_map) de voir le mappage des ID utilisateur dans l'espace de noms utilisateur du processus qui a créé cet espace de noms utilisateur.
(3)
La taille de la plage d'ID utilisateur qui est mappée entre les deux espaces de noms utilisateur.

Les appels système qui retournent des ID utilisateur (ID groupe) — par exemple, getuid(2), getgid(2), et les champs d'identification dans la structure retournée par stat(2) — retournent l'ID utilisateur (ID groupe) mappé dans l'espace de noms utilisateur de l'appelant.

Lorsqu'un processus accède à un fichier, ses ID utilisateur et groupe sont mappés dans l'espace de noms utilisateur initial à des fins de vérification d'autorisation et d'attribution d'ID lors de la création d'un fichier. Lorsqu'un processus récupère les ID utilisateur et groupe d'un fichier via stat(2), les ID sont mappés dans la direction opposée, pour produire des valeurs relatives aux mappages des ID utilisateur et groupe du processus.

L'espace de noms utilisateur initial n'a pas d'espace de noms parent, mais, par souci de cohérence, le noyau fournit des fichiers de mappage d'ID utilisateur et groupe factices pour cet espace de noms. L'examen du fichier uid_map (gid_map est identique) depuis un shell dans l'espace de noms initial montre :


$ cat /proc/$$/uid_map;
         0          0 4294967295

Ce mappage nous indique que la plage commençant à l'ID utilisateur 0 dans cet espace de noms est mappée à une plage commençant à 0 dans l'espace de noms parent (inexistant), et que la taille de la plage est le plus grand entier non signé sur 32 bits. Cela laisse 4294967295 (la valeur -1 signée sur 32 bits) non mappé. C'est intentionnel : (uid_t) -1 est utilisé dans plusieurs interfaces (par exemple, setreuid(2)) comme moyen de spécifier "aucun ID utilisateur". Laisser (uid_t) -1 non mappé et inutilisable garantit qu'il n'y aura pas de confusion lors de l'utilisation de ces interfaces.

Définition des mappages des ID utilisateur et groupe : écriture dans uid_map et gid_map

Après la création d'un nouvel espace de noms utilisateur, le fichier uid_map d' *un* des processus dans l'espace de noms peut être écrit *une seule fois* pour définir le mappage des ID utilisateur dans le nouvel espace de noms utilisateur. Une tentative d'écrire plus d'une fois dans un fichier uid_map dans un espace de noms utilisateur échoue avec l'erreur EPERM. Des règles similaires s'appliquent aux fichiers gid_map.

Les lignes écrites dans uid_map (gid_map) doivent être conformes aux règles de validité suivantes :

•
Les trois champs doivent être des nombres valides, et le dernier champ doit être supérieur à 0.
•
Les lignes sont terminées par des caractères de nouvelle ligne.
•
Il y a une limite au nombre de lignes dans le fichier. Jusqu'à Linux 4.14, cette limite était (arbitrairement) fixée à 5 lignes. Depuis Linux 4.16, la limite est de 340 lignes. De plus, le nombre d'octets écrits dans le fichier doit être inférieur à la taille de page système, et l'écriture doit être effectuée au début du fichier (c'est-à-dire que lseek(2) et pwrite(2) ne peuvent pas être utilisés pour écrire à des décalages non nuls dans le fichier).
•
La plage d'ID utilisateur (ID groupe) spécifiée dans chaque ligne ne peut pas chevaucher les plages dans d'autres lignes. Dans l'implémentation initiale (Linux 3.8), cette exigence était satisfaite par une implémentation simpliste qui imposait en outre que les valeurs dans les champs 1 et 2 des lignes successives soient dans l'ordre numérique croissant, ce qui empêchait la création de mappages autrement valides. Depuis Linux 3.9, cette limitation a été supprimée, permettant tout ensemble valide de mappages non chevauchants.
•
Au moins une ligne doit être écrite dans le fichier.

Les écritures qui violent les règles ci-dessus échouent avec l'erreur EINVAL.

Pour qu'un processus puisse écrire dans le fichier /proc/pid/uid_map (/proc/pid/gid_map), toutes les exigences d'autorisation suivantes doivent être remplies :

•
Le processus écrivant doit avoir la capacité CAP_SETUID (CAP_SETGID) dans l'espace de noms utilisateur du processus pid.
•
Le processus écrivant doit soit se trouver dans l'espace de noms utilisateur du processus pid, soit se trouver dans l'espace de noms utilisateur parent du processus pid.
•
Les ID utilisateur (ID groupe) mappés doivent à leur tour avoir un mappage dans l'espace de noms utilisateur parent.
•
Si la mise à jour de /proc/pid/uid_map vise à créer un mappage qui mappe l'UID 0 dans l'espace de noms parent, alors l'une des conditions suivantes doit être remplie :
(a)
si le processus écrivant se trouve dans l'espace de noms utilisateur parent, alors il doit avoir la capacité CAP_SETFCAP dans cet espace de noms utilisateur ; ou
(b)
si le processus écrivant se trouve dans l'espace de noms enfant
page, puis le processus qui a créé l'espace de noms utilisateur doit avoir eu la capacité CAP_SETFCAP lors de la création de l'espace de noms.
Cette règle est en place depuis Linux 5.12. Elle élimine un ancien bug de sécurité où un processus UID 0 qui ne possède pas la capacité CAP_SETFCAP, nécessaire pour créer un binaire avec des capacités de fichier nommées (comme décrit dans capabilities(7)), pouvait néanmoins créer un tel binaire, en suivant les étapes suivantes :
(1)
Créer un nouvel espace de noms utilisateur avec le mappage d'identité (c'est-à-dire que l'UID 0 dans le nouvel espace de noms utilisateur correspond à l'UID 0 dans l'espace de noms parent), de sorte que l'UID 0 dans les deux espaces de noms soit équivalent au même identifiant d'utilisateur root.
(2)
Étant donné que le processus enfant possède la capacité CAP_SETFCAP, il pourrait créer un binaire avec des capacités de fichier nommées qui seraient alors effectives dans l'espace de noms utilisateur parent (car les identifiants d'utilisateur root sont les mêmes dans les deux espaces de noms).
•
L'un des deux cas suivants s'applique :
(a)
Soit le processus d'écriture possède la capacité CAP_SETUID (CAP_SETGID) dans l'espace de noms utilisateur *parent*.
•
Aucune restriction supplémentaire ne s'applique : le processus peut créer des mappages vers des identifiants d'utilisateur (identifiants de groupe) arbitraires dans l'espace de noms utilisateur parent.
(b)
Soit sinon toutes les restrictions suivantes s'appliquent :
•
Les données écrites dans uid_map (gid_map) doivent consister en une seule ligne qui mappe l'identifiant d'utilisateur effectif du processus d'écriture (identifiant de groupe) dans l'espace de noms utilisateur parent à un identifiant d'utilisateur (identifiant de groupe) dans l'espace de noms utilisateur.
•
Le processus d'écriture doit avoir le même identifiant d'utilisateur effectif que le processus qui a créé l'espace de noms utilisateur.
•
Dans le cas de gid_map, l'utilisation de l'appel système setgroups(2) doit d'abord être refusée en écrivant "deny" dans le fichier /proc/pid/setgroups (voir ci-dessous) avant d'écrire dans gid_map.

Les écritures qui violent les règles ci-dessus échouent avec l'erreur EPERM.

Mappages d'identifiants de projet : projid_map

Similairement aux mappages d'identifiants utilisateur et de groupe, il est possible de créer des mappages d'identifiants de projet pour un espace de noms utilisateur. (Les identifiants de projet sont utilisés pour les quotas disque ; voir setquota(8) et quotactl(2).)

Les mappages d'identifiants de projet sont définis en écrivant dans le fichier /proc/pid/projid_map (présent depuis Linux 3.7).

Les règles de validité pour écrire dans le fichier /proc/pid/projid_map sont les mêmes que pour écrire dans le fichier uid_map ; la violation de ces règles entraîne l'échec de write(2) avec l'erreur EINVAL.

Les règles d'autorisation pour écrire dans le fichier /proc/pid/projid_map sont les suivantes :

•
Le processus d'écriture doit se trouver soit dans l'espace de noms utilisateur du processus pid, soit dans l'espace de noms utilisateur parent du processus pid.
•
Les identifiants de projet mappés doivent à leur tour avoir un mappage dans l'espace de noms utilisateur parent.

La violation de ces règles entraîne l'échec de write(2) avec l'erreur EPERM.

Interaction avec les appels système qui modifient les UID ou GID de processus

Dans un espace de noms utilisateur où le fichier uid_map n'a pas été écrit, les appels système qui modifient les identifiants utilisateur échoueront. De même, si le fichier gid_map n'a pas été écrit, les appels système qui modifient les identifiants de groupe échoueront. Une fois les fichiers uid_map et gid_map écrits, seules les valeurs mappées peuvent être utilisées dans les appels système qui modifient les identifiants utilisateur et de groupe.

Pour les identifiants utilisateur, les appels système pertinents incluent setuid(2), setfsuid(2), setreuid(2), et setresuid(2). Pour les identifiants de groupe, les appels système pertinents incluent setgid(2), setfsgid(2), setregid(2), setresgid(2), et setgroups(2).

Écrire "deny" dans le fichier /proc/pid/setgroups avant d'écrire dans /proc/pid/gid_map désactivera définitivement setgroups(2) dans un espace de noms utilisateur et permettra d'écrire dans /proc/pid/gid_map sans avoir la capacité CAP_SETGID dans l'espace de noms utilisateur parent.

Le fichier /proc/pid/setgroups

Le fichier /proc/pid/setgroups affiche la chaîne "allow" si les processus dans l'espace de noms utilisateur qui contient le processus pid sont autorisés à utiliser l'appel système setgroups(2) ; il affiche "deny" si setgroups(2) n'est pas autorisé dans cet espace de noms utilisateur. Notez que, quel que soit la valeur dans le fichier /proc/pid/setgroups (et indépendamment des capacités du processus), les appels à setgroups(2) ne sont pas non plus autorisés si /proc/pid/gid_map n'a pas encore été défini.

Un processus privilégié (celui ayant la capacité CAP_SYS_ADMIN dans l'espace de noms) peut écrire l'une ou l'autre des chaînes "allow" ou "deny" dans ce fichier *avant* d'écrire un mappage d'identifiant de groupe pour cet espace de noms utilisateur dans le fichier /proc/pid/gid_map. Écrire la chaîne "deny" empêche tout processus dans l'espace de noms utilisateur d'utiliser setgroups(2).

L'essence des restrictions décrites dans le paragraphe précédent est qu'il est permis d'écrire dans /proc/pid/setgroups uniquement tant que l'appel à setgroups(2) est interdit parce que /proc/pid/gid_map n'a pas été défini. Cela garantit qu'un processus ne peut pas passer d'un état où setgroups(2) est autorisé à un état où setgroups(2) est refusé ; un processus ne peut passer que de l'interdiction de setgroups(2) à l'autorisation de setgroups(2).

La valeur par défaut de ce fichier dans l'espace de noms utilisateur initial est "allow".

Une fois que /proc/pid/gid_map a été écrit (ce qui a pour effet d'activer setgroups(2) dans l'espace de noms utilisateur), il n'est plus possible d'interdire setgroups(2) en écrivant "deny" dans /proc/pid/setgroups (l'écriture échoue avec l'erreur EPERM).

Un espace de noms utilisateur enfant hérite du réglage /proc/pid/setgroups de son parent.

Si le fichier setgroups a la valeur "deny", alors l'appel système setgroups(2) ne peut pas ensuite être réactivé (en écrivant "allow" dans le fichier) dans cet espace de noms utilisateur. (Les tentatives de le faire échouent avec l'erreur EPERM.) Cette restriction se propage également à tous les espaces de noms utilisateur enfants de cet espace de noms utilisateur.

Le fichier /proc/pid/setgroups a été ajouté dans Linux 3.19, mais a été rétroporté dans de nombreuses séries de noyaux stables antérieures, car il résout un problème de sécurité. Le problème concernait les fichiers avec des permissions telles que "rwx---rwx". De tels fichiers accordent moins de permissions au "groupe" qu'à "les autres". Cela signifie que la suppression de groupes à l'aide de setgroups(2) pourrait permettre à un processus d'avoir un accès aux fichiers qu'il n'avait pas auparavant. Avant l'existence des espaces de noms utilisateur, cela ne posait pas de problème, car seul un processus privilégié (celui ayant la capacité CAP_SETGID) pouvait appeler setgroups(2). Cependant, avec l'introduction des espaces de noms utilisateur, il est devenu possible pour un processus non privilégié de créer un nouvel espace de noms dans lequel l'utilisateur avait tous les privilèges. Cela permettait alors aux utilisateurs précédemment non privilégiés de supprimer des groupes et ainsi d'obtenir un accès aux fichiers qu'ils n'avaient pas auparavant. Le fichier /proc/pid/setgroups a été ajouté pour résoudre ce problème de sécurité, en refusant toute voie permettant à un processus non privilégié de supprimer des groupes avec setgroups(2).

Identifiants utilisateur et de groupe non mappés

Il existe divers endroits où un identifiant utilisateur (identifiant de groupe) non mappé peut être exposé à l'espace utilisateur. Par exemple, le premier processus d'un nouvel espace de noms utilisateur peut appeler getuid(2) avant qu'un mappage d'identifiant utilisateur n'ait été défini pour l'espace de noms. Dans la plupart de ces cas, un identifiant utilisateur non mappé est converti en identifiant utilisateur (identifiant de groupe) de dépassement ; la valeur par défaut pour l'identifiant utilisateur (identifiant de groupe) de dépassement est 65534. Voir les descriptions de /proc/sys/kernel/overflowuid et /proc/sys/kernel/overflowgid dans proc(5).

Les cas où les identifiants non mappés sont mappés de cette manière incluent les appels système qui renvoient des identifiants utilisateur (getuid(2), getgid(2), et similaires), les informations d'identification transmises via un socket de domaine UNIX, les informations d'identification renvoyées par stat(2), waitid(2), et les opérations IPC_STAT de contrôle IPC System V, les informations d'identification exposées par /proc/pid/status et les fichiers dans /proc/sysvipc/*, les informations d'identification renvoyées via le champ si_uid dans siginfo_t reçu avec un signal (voir sigaction(2)), les informations d'identification écrites dans le fichier de comptabilité des processus (voir acct(5)), et les informations d'identification renvoyées avec les notifications de file d'attente de messages POSIX (voir mq_notify(3)).

Il y a un cas notable où les identifiants utilisateur et de groupe non mappés ne sont *pas* convertis en la valeur correspondante d'identifiant de dépassement. Lors de la visualisation d'un fichier uid_map ou gid_map dans lequel th

Il n'y a pas de correspondance pour le deuxième champ ; ce champ est affiché comme 4294967295 (-1 sous forme d'entier non signé).

Accès aux fichiers

Pour déterminer les permissions lorsqu'un processus non privilégié accède à un fichier, les identifiants du processus (UID, GID) et les identifiants du fichier sont effectivement rétro-mappés à ce qu'ils seraient dans l'espace de noms utilisateur initial, puis comparés pour déterminer les permissions que le processus a sur le fichier. Il en va de même pour d'autres objets qui utilisent le modèle d'accessibilité basé sur les identifiants plus un masque de permissions, tels que les objets IPC System V.

Fonctionnement des capacités liées aux fichiers

Certaines capacités permettent à un processus de contourner diverses restrictions appliquées par le noyau lors des opérations sur des fichiers appartenant à d'autres utilisateurs ou groupes. Ces capacités sont : CAP_CHOWN, CAP_DAC_OVERRIDE, CAP_DAC_READ_SEARCH, CAP_FOWNER et CAP_FSETID.

Dans un espace de noms utilisateur, ces capacités permettent à un processus de contourner les règles si le processus possède la capacité pertinente sur le fichier, ce qui signifie que :

•
le processus possède la capacité effective pertinente dans son espace de noms utilisateur ; et
•
l'identifiant utilisateur et l'identifiant de groupe du fichier ont tous deux des correspondances valides dans l'espace de noms utilisateur.

La capacité CAP_FOWNER est traitée de manière quelque peu exceptionnelle : elle permet à un processus de contourner les règles correspondantes tant qu'au moins l'identifiant utilisateur du fichier a une correspondance dans l'espace de noms utilisateur (c'est-à-dire que l'identifiant de groupe du fichier n'a pas besoin d'avoir une correspondance valide).

Programmes Set-user-ID et set-group-ID

Lorsqu'un processus à l'intérieur d'un espace de noms utilisateur exécute un programme set-user-ID (set-group-ID), l'identifiant utilisateur (groupe) effectif du processus à l'intérieur de l'espace de noms est changé pour la valeur qui est mappée pour l'identifiant utilisateur (groupe) du fichier. Cependant, si l'identifiant utilisateur *ou* l'identifiant de groupe du fichier n'a pas de correspondance à l'intérieur de l'espace de noms, le bit set-user-ID (set-group-ID) est silencieusement ignoré : le nouveau programme est exécuté, mais l'identifiant utilisateur (groupe) effectif du processus reste inchangé. (Cela reflète la sémantique de l'exécution d'un programme set-user-ID ou set-group-ID résidant sur un système de fichiers monté avec l'indicateur MS_NOSUID, comme décrit dans mount(2).)

Divers

Lorsque les identifiants utilisateur et groupe d'un processus sont transmis via un socket de domaine UNIX à un processus dans un espace de noms utilisateur différent (voir la description de SCM_CREDENTIALS dans unix(7)), ils sont traduits dans les valeurs correspondantes selon les mappages d'identifiants utilisateur et groupe du processus récepteur.

NOTES

Au fil des ans, de nombreuses fonctionnalités ont été ajoutées au noyau Linux et mises à disposition uniquement des utilisateurs privilégiés en raison de leur potentiel à perturber les applications set-user-ID-root. En général, il devient sûr d'autoriser l'utilisateur root dans un espace de noms utilisateur à utiliser ces fonctionnalités car il est impossible, tout en étant dans un espace de noms utilisateur, d'obtenir plus de privilèges que ce que possède l'utilisateur root d'un espace de noms utilisateur.

Root global

Le terme « root global » est parfois utilisé comme raccourci pour l'identifiant utilisateur 0 dans l'espace de noms utilisateur initial.

Disponibilité

L'utilisation des espaces de noms utilisateur nécessite un noyau configuré avec l'option CONFIG_USER_NS. Les espaces de noms utilisateur nécessitent un support dans un éventail de sous-systèmes du noyau. Lorsqu'un sous-système non pris en charge est configuré dans le noyau, il n'est pas possible de configurer le support des espaces de noms utilisateur.

À partir de Linux 3.8, la plupart des sous-systèmes pertinents supporternt les espaces de noms utilisateur, mais un certain nombre de systèmes de fichiers n'avaient pas l'infrastructure nécessaire pour mapper les identifiants utilisateur et groupe entre les espaces de noms utilisateur. Linux 3.9 a ajouté l'infrastructure nécessaire pour de nombreux systèmes de fichiers restants non pris en charge (Plan 9 (9P), Andrew File System (AFS), Ceph, CIFS, CODA, NFS et OCFS2). Linux 3.12 a ajouté le support pour le dernier des principaux systèmes de fichiers non pris en charge, XFS.

EXEMPLES

Le programme ci-dessous est conçu pour permettre l'expérimentation des espaces de noms utilisateur, ainsi que d'autres types d'espaces de noms. Il crée des espaces de noms comme spécifié par les options de la ligne de commande, puis exécute une commande à l'intérieur de ces espaces de noms. Les commentaires et la fonction usage() à l'intérieur du programme fournissent une explication complète du programme. La session shell suivante en démontre l'utilisation.

Tout d'abord, examinons l'environnement d'exécution :


$ uname -rs;     # Linux 3.8 ou plus récent requis
Linux 3.8.0
$ id -u;         # Exécution en tant qu'utilisateur non privilégié
1000
$ id -g;
1000

Démarrer maintenant un nouveau shell dans de nouveaux espaces de noms utilisateur (-U), montage (-m) et PID (-p), avec les identifiants utilisateur (-M) et groupe (-G) 1000 mappés à 0 à l'intérieur de l'espace de noms utilisateur :


$ ./userns_child_exec -p -m -U -M '0 1000 1' -G '0 1000 1' bash;

Le shell a le PID 1, car c'est le premier processus dans le nouvel espace de noms PID :


bash$ echo $$;
1

Montage d'un nouveau système de fichiers /proc et listage de tous les processus visibles dans le nouvel espace de noms PID montre que le shell ne peut pas voir de processus en dehors de l'espace de noms PID :


bash$ mount -t proc proc /proc;
bash$ ps ax;
  PID TTY      STAT   TIME COMMAND
    1 pts/3    S      0:00 bash
   22 pts/3    R+     0:00 ps ax

À l'intérieur de l'espace de noms utilisateur, le shell a les identifiants utilisateur et groupe 0, ainsi qu'un ensemble complet de capacités autorisées et effectives :


bash$ cat /proc/$$/status | egrep '^[UG]id';
Uid:	0	0	0	0
Gid:	0	0	0	0

CapInh:	0000000000000000
CapPrm:	0000001fffffffff
CapEff:	0000001fffffffff

/* userns_child_exec.c
   Licence selon la licence publique générale GNU v2 ou ultérieure
   Crée un processus enfant qui exécute une commande shell dans un nouvel
   espace de noms ; permet de spécifier des mappages UID et GID lors de
   la création d'un espace de noms utilisateur.
*/
#define _GNU_SOURCE
#include <err.h>
#include <sched.h>
#include <unistd.h>
#include <stdint.h>
#include <stdlib.h>
#include <sys/wait.h>
#include <signal.h>
#include <fcntl.h>
#include <stdio.h>
#include <string.h>
#include <limits.h>
#include <errno.h>
struct child_args {
    char **argv;        /* Commande à exécuter par l'enfant, avec arguments */
    int    pipe_fd[2];  /* Tube utilisé pour synchroniser le parent et l'enfant */
};
static int verbose;
static void
usage(char *pname)
{
    fprintf(stderr, "Usage: %s [options] cmd [arg...]\n\n", pname);
    fprintf(stderr, "Crée un processus enfant qui exécute une commande "
            "shell dans un nouvel espace de noms utilisateur,\n"
            "et éventuellement aussi d'autres nouveaux espaces de "
            "noms.\n\n");
    fprintf(stderr, "Les options peuvent être :\n\n");
#define fpe(str) fprintf(stderr, "    %s", str);
    fpe("-i          Nouvel espace de noms IPC\n");
    fpe("-m          Nouvel espace de noms de montage\n");
    fpe("-n          Nouvel espace de noms réseau\n");
    fpe("-p          Nouvel espace de noms PID\n");
    fpe("-u          Nouvel espace de noms UTS\n");
    fpe("-U          Nouvel espace de noms utilisateur\n");
    fpe("-M uid_map  Spécifie la carte UID pour l'espace de noms utilisateur\n");
    fpe("-G gid_map  Spécifie la carte GID pour l'espace de noms utilisateur\n");
    fpe("-z          Mappe l'UID et le GID de l'utilisateur à 0 dans l'espace de noms utilisateur\n");
    fpe("            (équivalent à : -M '0 <uid> 1' -G '0 <gid> 1')\n");
    fpe("-v          Affiche des messages verbeux\n");
    fpe("\n");
    fpe("Si -z, -M ou -G est spécifié, -U est requis.\n");
    fpe("Il n'est pas permis de spécifier à la fois -z et soit -M, soit -G.\n");
    fpe("\n");
    fpe("Les chaînes de mappage pour -M et -G consistent en des enregistrements de la forme :\n");
    fpe("\n");
    fpe("    ID-dans-ns   ID-hors-ns   taille\n");
    fpe("\n");
    fpe("Une chaîne de mappage peut contenir plusieurs enregistrements, séparés"
        " par des virgules ;\n");
    fpe("les virgules sont remplacées par des sauts de ligne avant l'écriture"
        " dans les fichiers de mappage.\n");
    exit(EXIT_FAILURE);
}
/* Met à jour le fichier de mappage 'map_file', avec la valeur fournie dans
   'mapping', une chaîne qui définit un mappage UID ou GID. Un mappage UID ou
   GID consiste en un ou plusieurs enregistrements délimités par des sauts de ligne
   de la forme :
       ID_dans-ns    ID-hors-ns   taille
   Obliger l'utilisateur à fournir une chaîne contenant des sauts de ligne est
   bien sûr peu pratique pour une utilisation en ligne de commande. Ainsi, nous
   autorisons l'utilisation de virgules pour délimiter les enregistrements dans
   cette chaîne, et nous les remplaçons par des sauts de ligne avant d'écrire la
   chaîne dans le fichier. */
static void
update_map(char *mapping, char *map_file)
{
    int fd;
    size_t map_len;     /* Longueur de 'mapping' */
    /* Remplace les virgules dans la chaîne de mappage par des sauts de ligne. */
    map_len = strlen(mapping);
    for (size_t j = 0; j < map_len; j++)
        if (mapping[j] == ',')
            mapping[j] = '\n';
    fd = open(map_file, O_RDWR);
    if (fd == -1) {
        fprintf(stderr, "ERREUR : open %s : %s\n", map_file,
                strerror(errno));
        exit(EXIT_FAILURE);
    }
    if (write(fd, mapping, map_len) != map_len) {
        fprintf(stderr, "ERREUR : write %s : %s\n", map_file,
                strerror(errno));
        exit(EXIT_FAILURE);
    }
    close(fd);
}
/* Linux 3.19 a apporté une modification dans la gestion de setgroups(2) et
   du fichier 'gid_map' pour résoudre un problème de sécurité. Le problème
   permettait aux utilisateurs *non privilégiés* d'utiliser les espaces de noms
   utilisateur afin de supprimer des groupes. La conséquence des changements de
   3.19 est que, pour mettre à jour le fichier 'gid_maps', l'utilisation de
   l'appel système setgroups() dans cet espace de noms utilisateur doit d'abord
   être désactivée en écrivant "deny" dans l'un des fichiers
   /proc/PID/setgroups de cet espace de noms. C'est le but de la fonction
   suivante. */
static void
proc_setgroups_write(pid_t child_pid, char *str)
{
    char setgroups_path[PATH_MAX];
    int fd;
    snprintf(setgroups_path, PATH_MAX, "/proc/%jd/setgroups",
            (intmax_t) child_pid);
    fd = open(setgroups_path, O_RDWR);
    if (fd == -1) {
        /* Nous sommes peut-être sur un système qui ne prend pas en charge
           /proc/PID/setgroups. Dans ce cas, le fichier n'existera pas,
           et le système n'imposera pas les restrictions ajoutées par Linux 3.19.
           C'est bien : nous n'avons rien à faire pour permettre la mise à jour de
           'gid_map'.
           Cependant, si l'erreur de open() était autre que
           l'erreur ENOENT attendue pour ce cas, informez l'utilisateur.  */
        if (errno != ENOENT)
            fprintf(stderr, "ERREUR : open %s : %s\n", setgroups_path,
                strerror(errno));
        return;
    }
    if (write(fd, str, strlen(str)) == -1)
        fprintf(stderr, "ERREUR : write %s : %s\n", setgroups_path,
            strerror(errno));
    close(fd);
}
static int              /* Fonction de démarrage pour le processus enfant cloné */
childFunc(void *arg)
{
    struct child_args *args = arg;
    char ch;
    /* Attendre que le processus parent ait mis à jour les mappings UID et GID.
       Voir le commentaire dans main(). Nous attendons la fin du fichier sur un
       pipe qui sera fermé par le processus parent une fois qu'il aura mis à jour
       les mappings.  */
    close(args->pipe_fd[1]);    /* Fermer notre descripteur pour l'extrémité d'écriture
                                   du pipe afin que nous recevions EOF lorsque le parent
                                   ferme son descripteur.  */
    if (read(args->pipe_fd[0], &ch, 1) != 0) {
        fprintf(stderr,
                "Échec dans l'enfant : read depuis le pipe a retourné != 0\n");
        exit(EXIT_FAILURE);
    }
    close(args->pipe_fd[0]);
    /* Exécuter une commande shell.  */
    printf("Sur le point d'exécuter %s\n", args->argv[0]);
    execvp(args->argv[0], args->argv);
    err(EXIT_FAILURE, "execvp");
}
#define STACK_SIZE (1024 * 1024)
static char child_stack[STACK_SIZE];    /* Espace pour la pile de l'enfant */
int
main(int argc, char *argv[])
{
    int flags, opt, map_zero;
    pid_t child_pid;
    struct child_args args;
    char *uid_map, *gid_map;
    const int MAP_BUF_SIZE = 100;
    char map_buf[MAP_BUF_SIZE];
    char map_path[PATH_MAX];
    /* Analyser les options de la ligne de commande. Le caractère '+' initial dans
       le dernier argument de getopt() empêche la permutation des options de la
       ligne de commande de style GNU. C'est utile, car parfois la 'commande' à
       exécuter par ce programme a elle-même des options de ligne de commande.
       Nous ne voulons pas que getopt() les traite comme des options pour ce programme.  */
    flags = 0;
    verbose = 0;
    gid_map = NULL;
    uid_map = NULL;
    map_zero = 0;
    while ((opt = getopt(argc, argv, "+imnpuUM:G:zv")) != -1) {
        switch (opt) {
        case 'i': flags |= CLONE_NEWIPC;        break;
        case 'm': flags |= CLONE_NEWNS;         break;
        case 'n': flags |= CLONE_NEWNET;        break;
        case 'p': flags |= CLONE_NEWPID;        break;
        case 'u': flags |= CLONE_NEWUTS;        break;
        case 'v': verbose = 1;                  break;
        case 'z': map_zero = 1;                 break;
        case 'M': uid_map = optarg;             break;
        case 'G': gid_map = optarg;             break;
        case 'U': flags |= CLONE_NEWUSER;       break;
        default:  usage(argv[0]);
        }
    }
    /* -M ou -G sans -U n'a pas de sens */
    if (((uid_map != NULL || gid_map != NULL || map_zero) &&
                !(flags & CLONE_NEWUSER)) ||
            (map_zero && (uid_map != NULL || gid_map != NULL)))
        usage(argv[0]);
    args.argv = &argv[optind];
    /* Nous utilisons un pipe pour synchroniser le parent et l'enfant, afin de
       s'assurer que le parent définit les mappings UID et GID avant que l'enfant
       n'appelle execve(). Cela garantit que l'enfant conserve ses
       capacités pendant execve() dans le cas courant où nous voulons mapper
       l'ID utilisateur effectif de l'enfant à 0 dans le nouvel espace de noms utilisateur.
       Sans cette synchronisation, l'enfant perdrait ses capacités s'il effectuait
       un execve() avec des identifiants utilisateur non nuls (voir la page de manuel
       capabilities(7) pour les détails de la transformation des capacités d'un
       processus pendant execve()).  */
    if (pipe(args.pipe_fd) == -1)
        err(EXIT_FAILURE, "pipe");
    /* Créer l'enfant dans de(s) nouveau(x) espace(s) de noms.  */
    child_pid = clone(childFunc, child_stack + STACK_SIZE,
                      flags | SIGCHLD, &args);
    if (child_pid == -1)
        err(EXIT_FAILURE, "clone");
    /* Le parent continue ici.  */
    if (verbose)
        printf("%s : PID de l'enfant créé par clone() est %jd\n",
                argv[0], (intmax_t) child_pid);
    /* Mettre à jour les mappings UID et GID dans l'enfant.  */
    if (uid_map != NULL || map_zero) {
        snprintf(map_path, PATH_MAX, "/proc/%jd/uid_map",
                (intmax_t) child_pid);
        if (map_zero) {
            snprintf(map_buf, MAP_BUF_SIZE, "0 %jd 1",
                    (intmax_t) getuid());
            uid_map = map_buf;
        }
        update_map(uid_map, map_path);
    }
    if (gid_map != NULL || map_zero) {
        proc_setgroups_write(child_pid, "deny");
        snprintf(map_path, PATH_MAX, "/proc/%jd/gid_map",
                (intmax_t) child_pid);
        if (map_zero) {
            snprintf(map_buf, MAP_BUF_SIZE, "0 %ld 1",
                    (intmax_t) getgid());
            gid_map = map_buf;
        }
        update_map(gid_map, map_path);
    }
    /* Fermer l'extrémité d'écriture du pipe, pour signaler à l'enfant que nous
       avons mis à jour les mappings UID et GID.  */
    close(args.pipe_fd[1]);
    if (waitpid(child_pid, NULL, 0) == -1)      /* Attendre l'enfant */
        err(EXIT_FAILURE, "waitpid");
    if (verbose)
        printf("%s : terminaison\n", argv[0]);
    exit(EXIT_SUCCESS);
}
