NOM

upsd.conf - Configuration du serveur de données upsd de Network UPS Tools

DESCRIPTION

upsd(8) utilise ce fichier pour contrôler l'accès au serveur et définir d'autres valeurs de configuration diverses. Ce fichier contient des détails sur les contrôles d'accès, alors gardez-le en sécurité. Idéalement, seul le processus upsd devrait pouvoir le lire.

NOTES IMPORTANTES

•Le contenu de ce fichier doit être en ASCII pur (les codes de caractères hors plage seront ignorés avec un message d'avertissement).
•Équilibrez les permissions de l'utilisateur lors de l'exécution pour accéder au fichier (et peut-être au répertoire qu'il contient) afin que seul upsd puisse le lire ; l'accès en écriture n'est pas nécessaire. Il est courant d'utiliser `chown root:nut` et `chmod 640` pour définir des permissions de fichiers acceptables.
•Les paquets (et leurs recettes de compilation) préparent généralement un ensemble d'utilisateurs et de groupes pour NUT. Les compilations personnalisées avec une configuration minimale peuvent même utiliser `nobody:nogroup` ou similaire, ce qui est intrinsèquement peu sûr.
•Sur les systèmes avec des préoccupations de sécurité supplémentaires, les pilotes NUT et le serveur de données devraient s'exécuter en tant que comptes utilisateurs séparés qui seraient membres d'un même groupe pour un accès partagé aux fichiers de socket Unix locaux et au répertoire qui les contient, mais de groupes différents pour l'accès aux fichiers de configuration. Cela nécessiterait que certains démons utilisent des paramètres `RUN_AS_USER` et/ou `RUN_AS_GROUP` personnalisés pour remplacer la valeur intégrée unique.
•Notez que les clients de surveillance, de journalisation, etc. sont uniquement réseau. Ils n'ont pas besoin d'accéder à ces fichiers et répertoires, et peuvent s'exécuter avec un utilisateur et un groupe complètement indépendants.
•Gardez à l'esprit la sécurité des éventuelles copies de sauvegarde de ce fichier, par exemple les fichiers d'archive dans lesquels il pourrait se retrouver.

DIRECTIVES DE CONFIGURATION

MAXAGE secondes

upsd permet généralement à un pilote de cesser de répondre pendant 15 secondes au maximum avant de déclarer les données "périmées". Si votre pilote prend beaucoup de temps à traiter les mises à jour mais est par ailleurs opérationnel, vous pouvez utiliser MAXAGE pour faire attendre upsd plus longtemps.

La plupart des utilisateurs devraient laisser cette valeur à sa valeur par défaut.

TRACKINGDELAY secondes

Lorsque le suivi instantané des commandes et des variables de statut est activé, les informations d'exécution du statut sont conservées pendant cette durée, puis nettoyées. La valeur par défaut est 3600 (1 heure).

ALLOW_NO_DEVICE Booléen

Normalement, upsd exige qu'au moins une section de périphérique soit définie dans ups.conf au démarrage du démon, pour servir ses données. Pour les services gérés automatiquement, il peut être préférable de maintenir upsd toujours en cours d'exécution et de recharger la configuration lorsque les périphériques d'alimentation sont définis.

Les valeurs booléennes `true`, `yes`, `on` et `1` signifient que le serveur ne refusera pas de démarrer si aucune section de périphérique n'est trouvée dans ups.conf.

Les valeurs booléennes `false`, `no`, `off` et `0` signifient que le serveur doit refuser de démarrer si aucune section de périphérique n'est trouvée dans ups.conf. C'est la valeur par défaut, sauf si l'environnement appelant définit une variable du même nom pour imposer une valeur pour l'exécution en cours. Une façon dont cela peut se produire est que quelqu'un décommente cela dans le fichier `nut.conf` utilisé par les scripts d'initialisation et les scripts de méthode de service.

ALLOW_NOT_ALL_LISTENERS Booléen

Normalement, upsd exige que toutes les directives LISTEN soient honorées au moment où le démon démarre. Si votre adresse IP LAN (ou nom d'hôte) utilisée dans une des directives LISTEN peut ne pas être toujours accessible, et que pour une raison quelconque vous ne souhaitez pas simplement écouter sur `*` (wildcard) sur l'interface, mais par exemple que vous souhaitez toujours utiliser upsmon sur localhost, cette option peut aider. Notez que vous devrez redémarrer upsd pour qu'il prenne en compte l'adresse IP écoutée si elle apparaît plus tard.

Les valeurs booléennes `true`, `yes`, `on` et `1` signifient que le serveur ne refusera pas de démarrer s'il peut écouter sur au moins une interface.

Les valeurs booléennes `false`, `no`, `off` et `0` signifient que le serveur doit refuser de démarrer s'il ne peut pas écouter sur chacune et toutes les interfaces (sauf localhost) trouvées dans upsd.conf. C'est la valeur par défaut, sauf si l'environnement appelant définit une variable du même nom pour imposer une valeur pour l'exécution en cours. Une façon dont cela peut se produire est que quelqu'un décommente cela dans le fichier `nut.conf` utilisé par les scripts d'initialisation et les scripts de méthode de service.

STATEPATH chemin

Indique à upsd de rechercher les sockets d'état des pilotes dans chemin plutôt que dans le chemin par défaut qui a été compilé dans le programme.

Notez que les pilotes doivent utiliser le même chemin, donc upsd préférera le paramètre du même nom de la section globale de ups.conf, s'il est présent, à son propre réglage.

La variable d'environnement NUT_STATEPATH définie par l'appelant (par exemple, script d'initialisation ou méthode de service) peut remplacer ce réglage.

LISTEN interface port

Lier un port d'écoute à l'interface spécifiée par son adresse Internet ou son nom. Cela peut être utile sur les hôtes avec plusieurs interfaces. Vous ne devriez pas vous fier exclusivement à cela pour la sécurité, car cela peut être contourné sur de nombreux systèmes.

Écouter éventuellement sur le port TCP port au lieu de la valeur par défaut qui a été compilée dans le code. Cela remplace toute valeur que vous auriez pu définir avec `configure --with-port`. Si vous ne la modifiez pas avec `configure` ou cette valeur, upsd écoutera sur le port 3493 pour cette interface.

Plusieurs adresses LISTEN peuvent être spécifiées. La valeur par défaut est d'écouter sur `127.0.0.1` si aucune adresse LISTEN n'est spécifiée (et aussi `::1` si le support IPv6 est compilé).

Pour écouter sur toutes les interfaces disponibles et toutes les adresses IP configurées de votre système, vous pouvez également utiliser `::` pour IPv6 et `0.0.0.0` pour IPv4, respectivement. Comme cas spécial, une seule directive `LISTEN * <port>` (avec un astérisque) tentera d'écouter sur les adresses IP wildcard IPv6 (`::0`) et IPv4 (`0.0.0.0`), sous réserve des arguments de ligne de commande de upsd ou de la configuration système. Notez que si le système prend en charge l'adressage IPv6 mappé IPv4 conformément à la RFC-3493, et ne permet pas de désactiver ce mode, il peut y avoir un seul socket d'écoute pour gérer les deux familles d'adresses.

LISTEN 127.0.0.1
LISTEN 192.168.50.1
LISTEN monhote.mondomaine
LISTEN ::1
LISTEN 2001:0db8:1234:08d3:1319:8a2e:0370:7344

Ce paramètre ne sera lu qu'au démarrage. Vous devrez redémarrer (plutôt que simplement recharger) upsd pour appliquer les modifications apportées ici.

Veuillez noter que les anciennes versions de NUT pouvaient utiliser le mode d'adressage IPv6 mappé IPv4 (parfois aussi appelé "double pile"), s'il était fourni par le système. Les versions actuelles (depuis la sortie de NUT v2.8.1) tentent explicitement de restreindre leurs sockets d'écoute pour ne supporter qu'une seule famille d'adresses par socket, et évitent ainsi le mode mappé IPv4 lorsque c'est possible.

MAXCONN connexions

La valeur par défaut est le nombre maximum autorisé sur votre système. Chaque UPS, chaque adresse d'écoute et chaque client compte comme une connexion. Si le serveur manque de connexions, il n'acceptera plus les nouvelles connexions clients entrantes. Ne définissez cette valeur que si vous savez exactement ce que vous faites.

CERTFILE fichier certificat

Lorsque compilé avec le support SSL avec backend OpenSSL, vous pouvez spécifier le fichier certificat ici.

Les certificats doivent être au format PEM et doivent être triés en commençant par le certificat du sujet (certificat serveur), suivi des certificats CA intermédiaires (si applicable) et du CA de plus haut niveau (racine). Il doit se terminer par la clé du serveur. Voir `docs/security.txt` dans les sources de NUT, ou le chapitre Sécurité du manuel utilisateur de NUT, pour plus d'informations sur le support SSL dans NUT.

CERTPATH base de données certificats

Lorsque compilé avec le support SSL avec backend NSS, vous pouvez spécifier le chemin de la base de données des certificats ici.

Les certificats sont stockés dans une base de données dédiée (données réparties en 3 fichiers). Spécifiez le chemin du répertoire de la base de données.

CERTIDENT nom certificat mot de passe base de données

Lorsque compilé avec le support SSL avec backend NSS, vous pouvez spécifier le nom du certificat à récupérer de la base de données pour s'authentifier, ainsi que le mot de passe requis pour accéder à la clé privée associée aux certificats.

Note
Assurez-vous d'encadrer le "nom certificat" avec des guillemets doubles si vous utilisez une valeur contenant des espaces.

CERT

REQUEST niveau de demande de certificat

Lors de la compilation avec prise en charge SSL avec le backend NSS et validation du certificat client (désactivée par défaut, voir « docs/security.txt » dans les sources de NUT), vous pouvez spécifier si upsd demande ou exige les certificats des clients.

Les valeurs possibles sont :

•0 pour ne pas demander aux clients de fournir de certificat
•1 pour exiger un certificat de tous les clients
•2 pour exiger un certificat valide de tous les clients

DISABLE_WEAK_SSL BOOLEAN

Indique à upsd de désactiver les protocoles et chiffrements SSL/TLS anciens/faibles. Avec des versions relativement récentes d'OpenSSL ou NSS, il sera limité à TLSv1.2 ou mieux.

À moins d'avoir des clients vraiment anciens, vous voudrez probablement activer cette option. Actuellement désactivée par défaut pour assurer la compatibilité avec les installations existantes.

DEBUG_MIN INTEGER

Spécifie éventuellement un niveau de débogage minimum pour le démon de données upsd, par exemple pour le dépannage d'un déploiement, sans impacter directement le mode de fonctionnement en avant-plan ou en arrière-plan. L'option de ligne de commande -D ne peut qu'augmenter ce niveau de verbosité.

Note
Si le démon en cours d'exécution reçoit une commande de rechargement, la présence de la valeur DEBUG_MIN NOMBRE dans le fichier de configuration peut être utilisée pour ajuster la verbosité du débogage dans le démon de service en cours d'exécution (il est recommandé de la commenter ou de régler le minimum à zéro explicite une fois terminé, afin d'éviter d'énormes journaux et un abus du système d'E/S). Gardez à l'esprit que pour ce réglage à l'exécution, la valeur DEBUG_MIN présente dans les fichiers de configuration rechargés est appliquée instantanément et remplace toute valeur définie précédemment, qu'elle provienne du fichier ou des options CLI, quel que soit le niveau de journalisation précédent plus élevé ou plus bas que le nouveau nombre trouvé ; une valeur manquante (ou commentée) ne modifie cependant pas la verbosité de journalisation précédemment active.
