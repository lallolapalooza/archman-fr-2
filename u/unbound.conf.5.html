NOM

unbound.conf - Fichier de configuration Unbound 1.24.2.

SYNTAXE

unbound.conf

DESCRIPTION

unbound.conf est utilisé pour configurer unbound(8). Le format du fichier contient des attributs et des valeurs. Certains attributs ont des attributs en leur sein. La notation est : attribut: valeur.

Les commentaires commencent par # et durent jusqu'à la fin de la ligne. Les lignes vides sont ignorées, tout comme les espaces en début de ligne.

L'utilitaire unbound-checkconf(8) peut être utilisé pour vérifier unbound.conf avant utilisation.

EXEMPLE

Un fichier de configuration d'exemple est présenté ci-dessous. Copiez-le dans /etc/unbound/unbound.conf et démarrez le serveur avec :

$ unbound -c /etc/unbound/unbound.conf

La plupart des réglages sont ceux par défaut. Arrêtez le serveur avec :

$ kill `cat /etc/unbound/unbound.pid`

Ci-dessous se trouve un fichier de configuration minimal. La distribution source contient un fichier example.conf détaillé avec toutes les options.

# Fichier de configuration unbound.conf(5) pour unbound(8).
serveur:
    repertoire: "/etc/unbound"
    utilisateur: unbound
    # assurez-vous qu'unbound peut accéder à l'entropie depuis l'intérieur du chroot.
    # par exemple sur linux utilisez ces commandes (sur BSD, devfs(8) est utilisé) :
    #      mount --bind -n /dev/urandom /etc/unbound/dev/urandom
    # et  mount --bind -n /dev/log /etc/unbound/dev/log
    chroot: "/etc/unbound"
    # fichier_log: "/etc/unbound/unbound.log"  # décommentez pour utiliser un fichier journal.
    pidfile: "/etc/unbound/unbound.pid"
    # verbosite: 1      # décommentez et augmentez pour obtenir plus de journaux.
    # écoute sur toutes les interfaces, répond aux requêtes du sous-réseau local.
    interface: 0.0.0.0
    interface: ::0
    controle-acces: 10.0.0.0/8 autoriser
    controle-acces: 2001:DB8::/64 autoriser

FORMAT DU FICHIER

Il doit y avoir un espace entre les mots-clés. Les mots-clés d'attribut se terminent par deux-points ':'. Un attribut est suivi d'une valeur, ou de ses attributs contenant dans quel cas il est appelé une clause. Les clauses peuvent être répétées tout au long du fichier (ou des fichiers inclus) pour regrouper les attributs sous la même clause.

Les fichiers peuvent être inclus en utilisant la directive include:. Elle peut apparaître n'importe où, elle accepte un nom de fichier unique comme argument. Le traitement se poursuit comme si le texte du fichier inclus était copié dans le fichier de configuration à cet endroit. Si vous utilisez également chroot, l'utilisation de noms de chemin complets pour les fichiers inclus fonctionne, les chemins relatifs pour les noms inclus fonctionnent si le répertoire où le démon est démarré correspond à son répertoire chroot/de travail ou est spécifié avant l'instruction include avec repertoire: dir. Les caractères génériques peuvent être utilisés pour inclure plusieurs fichiers, voir glob(7).

Pour une option d'inclusion plus structurelle, la directive include-toplevel: peut être utilisée. Cela ferme toute clause active (le cas échéant) et force l'utilisation des clauses dans les fichiers inclus et juste après cette directive.

OPTIONS DU SERVEUR

Ces options font partie de la clause server:.

verbosite: <nombre>
Le niveau de verbosité.
Niveau 0
Pas de verbosité, seulement les erreurs.
Niveau 1
Donne des informations opérationnelles.
Niveau 2
Donne des informations opérationnelles détaillées, y compris des informations courtes par requête.
Niveau 3
Donne des informations au niveau des requêtes, sortie par requête.
Niveau 4
Donne des informations au niveau de l'algorithme.
Niveau 5
Journalise l'identification du client pour les misses de cache.

La verbosité peut également être augmentée depuis la ligne de commande et pendant l'exécution via le contrôle à distance. Voir unbound(8) et unbound-control(8) respectivement.

Par défaut : 1

intervalle-statistiques: <secondes>
Le nombre de secondes entre l'impression des statistiques dans le journal pour chaque thread. Désactivé avec la valeur 0 ou "". Les statistiques de l'histogramme ne sont imprimées que si des réponses ont été envoyées pendant l'intervalle de statistiques, les statistiques de la liste de requêtes sont imprimées pour chaque intervalle (mais peuvent être 0). Ceci est dû au fait que le calcul de la médiane nécessite la présence de données.

Par défaut : 0 (désactivé)

statistiques-cumulatives: <oui ou non>
Si activé, les statistiques sont cumulatives depuis le démarrage d'Unbound, sans effacer les compteurs de statistiques après avoir consigné les statistiques.

Par défaut : non

statistiques-etendues: <oui ou non>
Si activé, des statistiques étendues sont imprimées depuis unbound-control(8). Les compteurs sont listés dans unbound-control(8). Le suivi de plus de statistiques prend du temps.

Par défaut : non

inhiber-zero: <oui ou non>
Si activé, certaines statistiques étendues avec une valeur de 0 sont inhibées de l'impression avec unbound-control(8). Il s'agit des types de requêtes, des classes de requêtes, des codes d'opération de requêtes, des codes de réponse (sauf NOERROR, FORMERR, SERVFAIL, NXDOMAIN, NOTIMPL, REFUSED) et des actions PRZ.

Par défaut : oui

nb-threads: <nombre>
Le nombre de threads à créer pour servir les clients. Utiliser 1 pour aucun thread.

Par défaut : 1

port: <numéro de port>
Le numéro de port sur lequel le serveur répond aux requêtes.

Par défaut : 53

interface: <adresse IP ou nom d'interface[@port]>
Interface à utiliser pour se connecter au réseau. Cette interface est écoutée pour les requêtes des clients, et les réponses aux clients sont données depuis celle-ci. Peut être donné plusieurs fois pour fonctionner sur plusieurs interfaces. Si aucune n'est donnée, par défaut, écoute sur localhost.

Si un nom d'interface est utilisé à la place d'une adresse IP, la liste des adresses IP de cette interface est utilisée. Les interfaces ne sont pas modifiées lors d'un rechargement (kill -HUP) mais seulement lors d'un redémarrage.

Un numéro de port peut être spécifié avec @port (sans espace entre l'interface et le numéro de port), sinon le port par défaut (issu de port) est utilisé.

adresse-ip: <adresse IP ou nom d'interface[@port]>
Identique à interface (pour faciliter la compatibilité avec nsd.conf(5)).
interface-automatique: <oui ou non>
Écoute sur toutes les adresses de toutes les interfaces (actuelles et futures), détecte l'interface source sur les requêtes UDP et les copie dans les réponses. Ceci est très similaire à ip-transparent, mais cette option dessert toutes les interfaces, tandis qu'avec ip-transparent, vous pouvez sélectionner les interfaces (futures) sur lesquelles Unbound fournit un service. Par défaut : non

interface-automatic-ports: "<chaîne>"
Liste les numéros de port sur lesquels interface-automatic écoute. Si elle est vide, le port par défaut est utilisé. Les numéros de port sont séparés par des espaces dans la chaîne.

Ceci peut être utilisé pour que l'interface automatique gère l'interface, et écoute sur le numéro de port normal, en l'incluant dans la liste, ainsi que les ports HTTPS ou DNS-over-TLS en les y ajoutant également.

Par défaut : ""

outgoing-interface: <adresse IPv4/IPv6 ou bloc réseau IPv6>
Interface à utiliser pour se connecter au réseau. Cette interface est utilisée pour envoyer des requêtes aux serveurs faisant autorité et recevoir leurs réponses. Peut être spécifiée plusieurs fois pour fonctionner sur plusieurs interfaces. Si aucune n'est spécifiée, la valeur par défaut (toutes) est utilisée. Vous pouvez spécifier les mêmes interfaces dans les lignes interface et outgoing-interface, les interfaces sont alors utilisées pour les deux objectifs. Les requêtes sortantes sont envoyées via une interface sortante aléatoire pour contrer le spoofing.

Si un bloc réseau IPv6 est spécifié au lieu d'une adresse IPv6 individuelle, les requêtes UDP sortantes utiliseront une adresse source aléatoire tirée du bloc réseau pour contrer le spoofing. Nécessite que le bloc réseau IPv6 soit routé vers l'hôte exécutant Unbound, et nécessite un support du système d'exploitation pour les liaisons non locales non privilégiées (actuellement uniquement pris en charge sous Linux). Plusieurs blocs réseau peuvent être spécifiés avec plusieurs options outgoing-interface, mais ne spécifiez pas à la fois une adresse IPv6 individuelle et un bloc réseau IPv6, sinon la randomisation sera compromise. Envisagez de combiner avec prefer-ip6: yes pour augmenter la probabilité que des serveurs DNS IPv6 soient sélectionnés pour les requêtes. Sous Linux, vous avez besoin des deux commandes suivantes pour pouvoir utiliser l'option de socket freebind afin de recevoir du trafic pour le bloc réseau ip6 :

ip -6 addr add monblocreseau/64 dev lo && \
ip -6 route add local monblocreseau/64 dev lo
outgoing-range: <nombre>
Nombre de ports à ouvrir. Ce nombre de descripteurs de fichiers peut être ouvert par thread. Doit être au moins 1. La valeur par défaut dépend des options de compilation. Des nombres plus grands nécessitent des ressources supplémentaires du système d'exploitation. Pour de bonnes performances, une très grande valeur est préférable, utilisez libevent pour rendre cela possible.

Par défaut : 4096 (libevent) / 960 (minievent) / 48 (windows)

outgoing-port-permit: <numéro de port ou plage>
Permet à Unbound d'ouvrir ce port ou cette plage de ports pour envoyer des requêtes. Un plus grand nombre de ports sortants autorisés augmente la résilience contre les tentatives de spoofing. Assurez-vous que ces ports ne sont pas nécessaires à d'autres démons. Par défaut, seuls les ports supérieurs à 1024 qui n'ont pas été attribués par l'IANA sont utilisés. Spécifiez un numéro de port ou une plage de la forme "bas-haut", sans espaces.

Les instructions outgoing-port-permit et outgoing-port-avoid sont traitées dans l'ordre des lignes du fichier de configuration, ajoutant les ports autorisés et soustrayant les ports évités de l'ensemble des ports autorisés. Le traitement commence avec les ports non alloués par l'IANA supérieurs à 1024 dans l'ensemble des ports autorisés.

outgoing-port-avoid: <numéro de port ou plage>
N'autorise pas Unbound à ouvrir ce port ou cette plage de ports pour envoyer des requêtes. Utilisez ceci pour vous assurer qu'Unbound ne s'approprie pas un port dont un autre démon a besoin. Le port est évité sur toutes les interfaces sortantes, IPv4 et IPv6. Par défaut, seuls les ports supérieurs à 1024 qui n'ont pas été attribués par l'IANA sont utilisés. Spécifiez un numéro de port ou une plage de la forme "bas-haut", sans espaces.
outgoing-num-tcp: <nombre>
Nombre de tampons TCP sortants à allouer par thread. S'il est défini sur 0, ou si do-tcp: no est défini, aucune requête TCP vers les serveurs faisant autorité n'est effectuée. Pour les installations plus importantes, augmenter cette valeur est une bonne idée.

Par défaut : 10

incoming-num-tcp: <nombre>
Nombre de tampons TCP entrants à allouer par thread. S'il est défini sur 0, ou si do-tcp: no est défini, aucune requête TCP des clients n'est acceptée. Pour les installations plus importantes, augmenter cette valeur est une bonne idée.

Par défaut : 10

edns-buffer-size: <nombre>
Taille en octets à annoncer comme taille du tampon de réassemblage EDNS. C'est la valeur mise dans les datagrammes sur UDP vers les pairs. La taille réelle du tampon est déterminée par msg-buffer-size (pour TCP et UDP). Ne pas régler plus haut que cette valeur. Le réglage à 512 contourne même les problèmes de MTU les plus stricts, mais est considéré comme extrême, car la quantité de réacheminement TCP générée est excessive (probablement aussi pour ce résolveur, envisagez de régler outgoing-num-tcp).

Par défaut : 1232 (Recommandation du DNS Flag Day 2020)

max-udp-size: <nombre>
Taille maximale de réponse UDP (non appliquée aux réponses TCP). 65536 désactive le maximum de taille de réponse UDP et utilise toujours le choix du client. Les valeurs suggérées vont de 512 à 4096.

Par défaut : 1232 (identique à edns-buffer-size)

stream-wait-size: <nombre>
Taille maximale en octets à utiliser pour les tampons de flux en attente. Un nombre simple est en octets, ajoutez 'k', 'm' ou 'g' pour les kilooctets, mégaoctets ou gigaoctets (1024*1024 octets dans un mégaoctet). Comme les flux TCP et TLS mettent en file d'attente plusieurs résultats, la quantité de mémoire utilisée pour ces tampons ne dépasse pas ce nombre, sinon les réponses sont abandonnées. Ceci gère l'utilisation totale de la mémoire du serveur (en cas d'utilisation intensive), le nombre de requêtes qui peuvent être mises en file d'attente par connexion est également limité, avec des requêtes supplémentaires en attente dans les tampons TCP.

Par défaut : 4m

msg-buffer-size: <nombre>
Taille en octets des tampons de message. La valeur par défaut est de 65552 octets, suffisant pour des paquets de 64 Ko, la taille maximale d'un message DNS. Aucun message plus grand que cela ne peut être envoyé ou reçu. Peut être réduit pour utiliser moins de mémoire, mais certaines requêtes de données DNS, comme pour d'énormes enregistrements de ressources, entraîneront une réponse SERVFAIL au client.

Par défaut : 65552

msg-cache-size: <nombre>
Taille en octets du cache de messages. Un nombre simple est en octets, ajoutez 'k', 'm' ou 'g' pour les kilooctets, mégaoctets ou gigaoctets (1024*1024 octets dans un mégaoctet).

Par défaut : 4m

msg-cache-slabs: <nombre>
Nombre de "slabs" dans le cache de messages. Les slabs réduisent la contention de verrouillage par les threads. Doit être un nombre qui est une puissance de 2. Régler sur un nombre proche du nombre de CPU est un réglage assez bon. S'il n'est pas configuré, il sera configuré automatiquement pour être une puissance de 2 proche du nombre de threads configurés dans les environnements multi-threads.

Par défaut : (non configuré)

num-queries-per-thread: <nombre>
Le nombre de requêtes que chaque thread traitera simultanément. Si plus de requêtes arrivent nécessitant un traitement, et qu'aucune requête ne peut être écartée (voir jostle-timeout), alors les requêtes sont abandonnées. Cela force le client à renvoyer après un délai d'attente; permettant au serveur de travailler sur les requêtes existantes. La valeur par défaut dépend des options de compilation.

Par défaut : 2048 (libevent) / 512 (minievent) / 24 (windows)

jostle-timeout: <ms>
Délai d'attente utilisé lorsque le serveur est très occupé. Réglez sur une valeur qui correspond généralement à un aller-retour vers les serveurs faisant autorité.

Si trop de requêtes arrivent, alors 50% des requêtes sont autorisées à se terminer, et les 50% restants sont remplacés par la nouvelle requête entrante si elles ont déjà passé plus de temps que leur temps alloué. Cela protège contre le déni de service par des requêtes lentes ou des taux de requêtes élevés.

L'effet est que le qps pour les requêtes de longue durée est d'environ :

(num-queries-per-thread / 2) / (temps moyen pour de telles requêtes longues) qps

Le qps pour les requêtes courtes peut être d'environ :

(num-queries-per-thread / 2) / (jostle-timeout en secondes entières) qps par thread

environ (2048/2)*5 = 5120 qps par défaut.

Par défaut : 200

delay-close: <ms>
Délai supplémentaire pour les ports UDP expirés avant leur fermeture, en ms. Cela évite que les paquets de réponse très retardés des serveurs en amont (récursifs) n'entrent en collision avec des ports fermés et ne déclenchent toutes sortes de compteurs de fermeture de port, avec par exemple 1500 ms. Lorsque des expirations se produisent, vous avez besoin de sockets supplémentaires, il vérifie l'ID et l'IP distante des paquets, et les paquets indésirables sont ajoutés au compteur de paquets indésirables.

Par défaut : 0 (désactivé)

udp-connect: <oui ou non>
Effectuer connect(2) pour les sockets UDP afin de limiter les fuites de canal secondaire ICMP.

Par défaut : oui

unknown-server-time-limit: <msec>
Le temps d'attente en millisecondes pour répondre à un serveur inconnu. Augmentez cette valeur si vous êtes derrière une liaison satellite lente, par exemple à 1128. Cela évitera ainsi de requêter à nouveau chaque requête initiale parce qu'elle atteint le délai d'attente.

Défaut : 376

discard-timeout: <msec>
Le temps d'attente en millisecondes pendant lequel les requêtes de récursion sont ignorées. Ceci afin d'éviter l'accumulation d'un grand nombre de réponses. Elles ne reçoivent pas de réponse, l'élément de travail continue de récursionner. Il est bon d'avoir une valeur légèrement supérieure à serve-expired-client-timeout si celle-ci est activée. Une valeur de 1900 millisecondes est suggérée. La valeur 0 la désactive.

Défaut : 1900

wait-limit: <nombre>
Le nombre de réponses qui peuvent attendre la récursion, pour une adresse IP. Ceci limite par adresse IP le nombre de réponses en attente de récursion. Cela empêche une très grande quantité de requêtes d'attendre d'être renvoyées à une seule destination. La valeur 0 désactive les limites d'attente.

Défaut : 1000

wait-limit-cookie: <nombre>
Le nombre de réponses qui peuvent attendre la récursion, pour une adresse IP qui a envoyé la requête avec un cookie DNS valide. Comme le cookie valide l'adresse du client, cette limite peut être plus élevée.

Défaut : 10000

wait-limit-netblock: <bloc_reseau> <nombre>
La limite d'attente pour le bloc réseau. Si non spécifié, la valeur de wait-limit est utilisée. Le bloc réseau le plus spécifique est utilisé pour déterminer la limite. Utile pour remplacer la valeur par défaut pour un serveur spécifique, un groupe ou un serveur individuel. La valeur -1 désactive les limites d'attente pour le bloc réseau. Par défaut, la boucle locale a une limite d'attente de bloc réseau de -1, elle n'est pas limitée, car elle est séparée du reste du réseau pour les paquets usurpés. Les adresses de boucle locale 127.0.0.0/8 et ::1/128 sont par défaut à -1.

Défaut : (aucun)

wait-limit-cookie-netblock: <bloc_reseau> <nombre>
La limite d'attente pour le bloc réseau, lorsque la requête contient un cookie DNS. Si non spécifié, la valeur de wait-limit-cookie est utilisée. La valeur -1 désactive les limites d'attente pour le bloc réseau. Les adresses de boucle locale 127.0.0.0/8 et ::1/128 sont par défaut à -1.

Défaut : (aucun)

so-rcvbuf: <nombre>
Si différent de 0, alors définit l'option de socket SO_RCVBUF pour obtenir plus d'espace tampon sur les requêtes entrantes UDP port 53. Ainsi, les pics courts sur les serveurs occupés ne font pas perdre de paquets (voir le compteur dans netstat -su). Sinon, le nombre d'octets à demander, essayez « 4m » sur un serveur occupé.

Le système d'exploitation le limite à un maximum, sous Linux, Unbound nécessite des privilèges root pour contourner la limite, ou l'administrateur peut utiliser sysctl net.core.rmem_max.

Sur BSD, modifiez kern.ipc.maxsockbuf dans /etc/sysctl.conf.

Sur OpenBSD, modifiez l'en-tête et recompilez le noyau.

Sur Solaris, exécutez ndd -set /dev/udp udp_max_buf 8388608.

Défaut : 0 (utilise la valeur système)

so-sndbuf: <nombre>
Si différent de 0, alors définit l'option de socket SO_SNDBUF pour obtenir plus d'espace tampon sur les requêtes sortantes UDP port 53. Ceci, pour les serveurs très occupés, gère les pics de trafic de réponse, sinon :
send: resource temporarily unavailable

peut être enregistré, le débordement du tampon est également visible avec netstat -su. S'il est défini sur 0, il utilise la valeur système. Spécifiez le nombre d'octets à demander, essayez « 8m » sur un serveur très occupé.

Il faut un peu d'espace pour pouvoir gérer les paquets qui attendent la résolution d'adresses locales, comme la découverte ARP et NDP, avant d'être envoyés, d'où son élévation au-dessus de la valeur par défaut du système.

Le système d'exploitation le limite à un maximum, sous Linux, Unbound nécessite des privilèges root pour contourner la limite, ou l'administrateur peut utiliser sysctl net.core.wmem_max.

Sur BSD, les modifications Solaris sont similaires à so-rcvbuf.

Défaut : 4m

so-reuseport: <oui ou non>
Si oui, alors ouvre des sockets d'écoute dédiés pour les requêtes entrantes pour chaque thread et essaie de définir l'option de socket SO_REUSEPORT sur chaque socket. Peut distribuer les requêtes entrantes plus uniformément entre les threads.

Sous Linux, c'est pris en charge dans les noyaux >= 3.9.

Sur d'autres systèmes, FreeBSD, OSX, cela peut également fonctionner.

Vous pouvez l'activer (sur n'importe quelle plateforme et noyau), il tente alors d'ouvrir le port et passe l'option si elle était disponible au moment de la compilation, si cela fonctionne, elle est utilisée, si cela échoue, il continue silencieusement (sauf verbosité 3) sans l'option.

À charge extrême, il peut être préférable de le désactiver pour distribuer les requêtes uniformément, signalé pour les systèmes Linux (4.4.x).

Défaut : oui

ip-transparent: <oui ou non>
Si oui, alors utilise l'option de socket IP_TRANSPARENT sur les sockets où Unbound écoute le trafic entrant. Permet de se lier à des interfaces non locales. Par exemple, pour des adresses IP inexistantes qui existeront plus tard, avec une configuration de basculement de serveur.

Ceci ressemble beaucoup à interface-automatic, mais cette dernière dessert toutes les interfaces et avec cette option, vous pouvez sélectionner les interfaces (futures) sur lesquelles Unbound fournit un service.

Cette option nécessite que Unbound soit démarré avec des privilèges root sur certains systèmes. L'option utilise IP_BINDANY sur les systèmes FreeBSD et SO_BINDANY sur les systèmes OpenBSD.

Défaut : non

ip-freebind: <oui ou non>
Si oui, alors utilise l'option de socket IP_FREEBIND sur les sockets où Unbound écoute le trafic entrant. Permet de se lier à des adresses IP non locales ou inexistantes, comme lorsque l'interface réseau ou l'adresse IP est inactive.

N'existe que sous Linux, où l'option similaire ip-transparent est également disponible.

Défaut : non

ip-dscp: <nombre>
La valeur du Codepoint des Services Différenciés (DSCP) dans le champ des services différenciés (DS) des en-têtes de paquets IP sortants. Le champ remplace l'ancien champ Type-Of-Service IPv4 et le champ de classe de trafic IPv6.
rrset-cache-size: <nombre>
Taille en octets du cache RRset. Un simple nombre est en octets, ajoutez 'k', 'm' ou 'g' pour les kilo-octets, méga-octets ou giga-octets (1024*1024 octets dans un méga-octet).

Défaut : 4m

rrset-cache-slabs: <nombre>
Nombre de "slabs" dans le cache RRset. Les "slabs" réduisent la contention de verrouillage par les threads. Doit être défini sur une puissance de 2. Définir (proche) du nombre de processeurs est un réglage assez bon. Si non configuré, il sera configuré automatiquement pour être une puissance de 2 proche du nombre de threads configurés dans les environnements multi-threads.

Défaut : (non configuré)

cache-max-ttl: <secondes>
Durée de vie maximale pour les RRsets et les messages dans le cache. Lorsque la durée de vie expire, l'élément du cache est expiré. Peut être réglé plus bas pour forcer le résolveur à interroger fréquemment les données, et à ne pas faire confiance aux valeurs TTL (très grandes). Les clients en aval voient également la durée de vie plus basse.

Défaut : 86400 (1 jour)

cache-min-ttl: <secondes>
Durée de vie minimale pour les RRsets et les messages dans le cache. Si la durée minimale s'applique, les données sont mises en cache plus longtemps que prévu par le propriétaire du domaine, et donc moins de requêtes sont effectuées pour rechercher les données. Zéro garantit que les données dans le cache correspondent à celles prévues par le propriétaire du domaine, des valeurs plus élevées, en particulier plus d'une heure environ, peuvent entraîner des problèmes car les données dans le cache ne correspondent plus aux données réelles.

Défaut : 0 (désactivé)

cache-max-negative-ttl: <secondes>
Durée de vie maximale pour les réponses négatives, celles-ci ont une SOA dans la section d'autorité dont la durée de vie est limitée. Cela s'applique aux réponses NXDOMAIN et NODATA.

Défaut : 3600

cache-min-negative-ttl: <secondes>
Durée de vie minimale pour les réponses négatives, celles-ci ont une SOA dans la section d'autorité dont la durée de vie est limitée. Si cela est désactivé et que cache-min-ttl est configuré, cela s'appliquera à la place. Dans ce cas, vous pouvez régler ceci à 1 pour respecter la durée de vie montante. Cela s'applique aux réponses NXDOMAIN et NODATA.

Défaut : 0 (désactivé)

access-control: <bloc réseau IP> <action>
Spécifie le traitement des requêtes entrantes à partir de leur adresse IP d'origine. Les requêtes peuvent être autorisées à accéder à ce serveur qui donne des réponses DNS, ou refusées, avec d'autres actions possibles. La plage d'adresses IP peut être spécifiée sous forme de bloc réseau, il est possible de donner plusieurs fois l'instruction afin de spécifier le traitement de différents blocs réseau. Le bloc réseau est donné sous forme d'adresse IPv4 ou IPv6 avec /taille ajoutée pour un bloc réseau sans classe. La correspondance de bloc réseau la plus spécifique est utilisée, si aucune ne correspond, refuse est utilisé. L'ordre des instructions access-control n'a donc pas d'importance. L'action peut être deny, refuse, allow, allow_setrd, allow_snoop, allow_cookie, deny_non_local ou refuse_non_local.
deny
Arrête les requêtes des hôtes de ce bloc réseau.
refuse
Arrête également les requêtes, mais renvoie un message d'erreur DNS rcode REFUSED.
allow
Donne accès aux clients de ce bloc réseau. Il ne donne accès qu'aux clients récursifs (ce dont la plupart des clients ont besoin). Les requêtes non récursives sont refusées.

L'action allow permet aux requêtes non récursives d'accéder aux données locales configurées. La raison est que cela n'implique pas l'algorithme de résolution récursive du serveur Unbound, et que les données statiques sont servies dans la réponse. Cela prend en charge les opérations normales où des requêtes non récursives sont effectuées pour les données faisant autorité. Pour les requêtes non récursives, toutes les réponses du cache dynamique sont refusées.

allow_setrd
Ignore le bit de récursion souhaitée (RD) et traite toutes les requêtes comme si le bit de récursion souhaitée était défini.

Notez que ce comportement viole la RFC 1034 qui stipule qu'un serveur de noms ne doit jamais effectuer de service récursif sauf si cela lui est demandé via le bit RD, car cela interfère avec le dépannage des serveurs de noms et de leurs bases de données. Ce comportement interdit peut être utile si un autre serveur DNS doit transférer les requêtes de zones spécifiques à un serveur DNS résolveur, mais ne prend en charge que les domaines stub et envoie des requêtes au serveur DNS résolveur avec le bit RD effacé.

allow_snoop
Donne également un accès non récursif. Cela donne un accès récursif et non récursif. Le nom allow_snoop fait référence au cache snooping, une technique permettant d'utiliser des requêtes non récursives pour examiner le contenu du cache (à des fins malveillantes). Cependant, les requêtes non récursives peuvent également être un outil de débogage précieux (lorsque vous souhaitez examiner le contenu du cache).

Dans ce cas, utilisez allow_snoop pour votre hôte d'administration.

allow_cookie
Autorise l'accès uniquement aux requêtes UDP qui contiennent un cookie DNS valide tel que spécifié dans la RFC 7873 et la RFC 9018, lorsque l'option answer-cookie est activée. Les requêtes UDP contenant uniquement un cookie client DNS et aucun cookie serveur, ou un cookie DNS invalide, recevront une réponse BADCOOKIE incluant un cookie DNS nouvellement généré, permettant aux clients de réessayer avec ce cookie DNS. L'action allow_cookie acceptera également les requêtes sur des transports avec état, indépendamment de la présence d'un cookie DNS et quel que soit le réglage de answer-cookie. Les requêtes UDP sans cookie DNS recevront des réponses REFUSED avec le drapeau TC défini, ce qui peut déclencher un retour à TCP pour ces clients.
deny_non_local
L'action deny_non_local est destinée aux hôtes qui ne sont autorisés qu'à interroger les données locales faisant autorité, ils ne sont pas autorisés à la récursion complète mais uniquement aux données statiques. Les messages qui sont rejetés sont ignorés.

L'action refuse_non_local est destinée aux hôtes qui ne sont autorisés qu'à interroger les données locales faisant autorité, ils ne sont pas autorisés à la récursion complète mais uniquement aux données statiques. Les messages qui sont rejetés reçoivent le code d'erreur REFUSED.

Par défaut, seul localhost (le bloc réseau IP 127.0.0.0/8, pas l'interface de bouclage) est implicitement autorisé, le reste est refusé. local-zone: <zone> <type>
Configure une zone locale. Le type détermine la réponse à donner s'il n'y a pas de correspondance dans local-data. Les types sont deny, refuse, static, transparent, redirect, nodefault, typetransparent, inform, inform_deny, inform_redirect, always_transparent, block_a, always_refuse, always_nxdomain, always_null, et sont expliqués ci-dessous. Ensuite, les paramètres par défaut sont listés. Utilisez local-data pour entrer des données dans la zone locale. Les réponses pour les zones locales sont des réponses DNS faisant autorité. Par défaut, les zones sont de classe IN.

Si vous avez besoin de données faisant autorité plus complexes, avec des renvois, des jokers, la prise en charge de CNAME/DNAME ou un service faisant autorité DNSSEC, configurez une stub-zone pour cela comme détaillé dans la section stub zone ci-dessous. Une stub-zone peut être utilisée pour que unbound envoie des requêtes à un autre serveur, un serveur faisant autorité, pour récupérer les informations. Avec une forward-zone, unbound envoie des requêtes à un serveur récursif pour récupérer les informations. Avec une auth-zone, une zone peut être chargée à partir d'un fichier et utilisée, elle peut être utilisée comme une zone locale pour les utilisateurs en aval, ou les informations auth-zone peuvent être utilisées pour récupérer des informations lors de la résolution comme s'il s'agissait d'un serveur en amont. Les options forward-zone et auth-zone sont décrites dans leurs sections ci-dessous. Si vous souhaitez filtrer les informations que les utilisateurs peuvent récupérer, les instructions local-zone et local-data le permettent, mais la fonctionnalité rpz peut également être utilisée, décrite dans la section RPZ.

deny
N'envoyer aucune réponse, abandonner la requête. S'il y a une correspondance dans les données locales, la requête reçoit une réponse.
refuse
Envoyer un message d'erreur, avec rcode REFUSED. S'il y a une correspondance dans les données locales, la requête reçoit une réponse.
static
S'il y a une correspondance dans les données locales, la requête reçoit une réponse. Sinon, la requête reçoit une réponse NODATA ou NXDOMAIN. Pour une réponse négative, un SOA est inclus dans la réponse s'il est présent en tant que local-data pour le domaine apex de la zone.
transparent
S'il y a une correspondance dans local-data, la requête reçoit une réponse. Sinon, si la requête concerne un nom différent, la requête est résolue normalement. Si la requête concerne un nom donné dans local-data mais qu'aucun type de données de ce type n'est donné dans les données locales, une réponse NOERROR NODATA est renvoyée. Si aucune local-zone n'est spécifiée, local-data crée une zone transparente par défaut.
typetransparent
S'il y a une correspondance dans les données locales, la requête reçoit une réponse. Si la requête concerne un nom différent, ou le même nom mais pour un type différent, la requête est résolue normalement. Ainsi, similaire à transparent, mais les types qui ne sont pas listés dans les données locales sont résolus normalement, donc si un enregistrement A se trouve dans les données locales, cela ne provoque pas de réponse NODATA pour les requêtes AAAA.
redirect
La requête reçoit une réponse à partir des données locales pour le nom de la zone. Il peut n'y avoir aucune donnée locale sous le nom de la zone. Cela répond aux requêtes pour la zone, et à tous les sous-domaines de la zone avec les données locales pour la zone. Il peut être utilisé pour rediriger un domaine afin qu'il renvoie un enregistrement d'adresse différent à l'utilisateur final, avec :
local-zone: "example.com." redirect
local-data: "example.com. A 127.0.0.1"

les requêtes pour www.example.com et www.foo.example.com sont redirigées, de sorte que les utilisateurs avec des navigateurs web ne peuvent pas accéder aux sites avec le suffixe example.com.

inform
La requête est résolue normalement, comme transparent. L'adresse IP du client (@port) est imprimée dans le fichier journal. Le message de journalisation est :
timestamp, unbound-pid, info: zonename inform IP@port queryname type class.

Cette option peut être utilisée pour une résolution normale, mais les machines interrogeant des noms infectés sont enregistrées, par exemple pour exécuter un antivirus dessus.

inform_deny
La requête est abandonnée, comme deny, et enregistrée, comme inform. C'est-à-dire trouver les machines infectées sans répondre aux requêtes.
inform_redirect
La requête est redirigée, comme redirect, et enregistrée, comme inform. C'est-à-dire répondre aux requêtes avec des données fixes et également enregistrer les machines qui posent la question.
always_transparent
Comme transparent, mais ignore les données locales et résout normalement.
block_a
Comme transparent, mais ignore les données locales et résout normalement tous les types de requêtes à l'exception de A. Pour les requêtes A, il renvoie inconditionnellement NODATA. Utile dans les cas où il est nécessaire de forcer explicitement toutes les applications à utiliser le protocole IPv6 et à éviter toute requête vers IPv4.
always_refuse
Comme refuse, mais ignore les données locales et refuse la requête.
always_nxdomain
Comme static, mais ignore les données locales et renvoie NXDOMAIN pour la requête.
always_nodata
Comme static, mais ignore les données locales et renvoie NODATA pour la requête.
always_deny
Comme deny, mais ignore les données locales et abandonne la requête.
always_null
Renvoie toujours 0.0.0.0 ou ::0 pour chaque nom de la zone. Comme redirect avec des données nulles pour A et AAAA. Ignore les données locales dans la zone. Utilisé pour certaines listes de blocage.
noview
Sort de cette vue et se dirige vers les zones locales globales pour la réponse à la requête. Si view-first est non, cela résoudra normalement. Si view-first est activé, cela interrompra cette étape et vérifiera les réponses globales. Pour les cas où la vue a des substitutions spécifiques à la vue, mais qu'une zone doit être répondue à partir du contenu de la zone locale globale.
nodefault
Utilisé pour désactiver le contenu par défaut des zones AS112. Les autres types désactivent également le contenu par défaut

ZONES LOCALES

Ceci décrit la configuration des zones locales.

Le système de zones locales de unbound permet de définir des réponses personnalisées pour certains domaines DNS. Ceci est utile pour le blocage de publicités, la redirection de domaines, ou pour fournir des réponses personnalisées pour des domaines spéciaux.

Il existe plusieurs types de zones locales:

local-zone: <zone> <type>
Définit le comportement pour une zone DNS donnée. Les types possibles sont:
refuse
Répond avec un code d'erreur REFUSED.
nodata
Répond avec un code d'erreur NOERROR, mais sans enregistrement trouvé. Ceci est le comportement par défaut pour les zones mentionnées ci-dessous, à l'exception de `localhost`.
deny
Identique à `refuse`.
static
Répond avec les données spécifiées par `local-data` ou `local-data-ptr`. Si aucune donnée n'est spécifiée, le comportement est identique à `nodata`.
redirect
Répond avec une réponse de type REFUSED ou une réponse DNAME vers une adresse spécifiée par `local-data`. Pour les zones non-PTR, il peut s'agir d'une réponse CNAME. Pour les zones PTR, il est utilisé pour rediriger la requête vers une autre adresse IP. Utile pour le blocage des publicités.
transparent
Permet la résolution normale, mais si le domaine demandé n'existe pas, il renvoie `nodata` ou `refuse`.
nodefault

Options de Zone Stub

Il peut y avoir plusieurs clauses stub-zone:. Chacune avec un name et zéro ou plusieurs noms d'hôtes ou adresses IP. Pour la zone stub, cette liste de serveurs de noms est utilisée. La classe IN est supposée. Les serveurs doivent être des serveurs d'autorité, pas des récursores ; Unbound effectue lui-même le traitement récursif pour les zones stub.

La zone stub peut être utilisée pour configurer des données faisant autorité à utiliser par le résolveur qui ne sont pas accessibles via les serveurs publics Internet. Ceci est utile pour les données internes à une entreprise ou les zones privées. Configurez un serveur faisant autorité sur un autre hôte (ou sur un port différent). Entrez une entrée de configuration pour Unbound avec :

stub-addr: <adresse IP de l'hôte[@port]>

Le résolveur Unbound peut alors accéder aux données, sans s'y référer via Internet.

Cette configuration permet de servir des zones signées DNSSEC par ce serveur faisant autorité, auquel cas une entrée de clé de confiance avec la clé publique peut être placée dans la configuration, afin qu'Unbound puisse valider les données et définir le bit AD sur les réponses pour la zone privée (les serveurs faisant autorité ne définissent pas le bit AD). Cette configuration rend Unbound capable de répondre aux requêtes pour la zone privée, et peut même définir le bit AD ('authentic'), mais le bit AA ('authoritative') n'est pas défini sur ces réponses.

Envisagez d'ajouter des instructions server pour domain-insecure et pour local-zone: <name> nodefault pour la zone si c'est une zone servie localement. La clause insecure empêche DNSSEC d'invalider la zone. La clause local-zone: nodefault (ou transparent) permet à la zone (inverse) de contourner le filtrage des zones RFC 1918 par Unbound.

name: <nom de domaine>
Nom de la zone stub. C'est le nom de domaine complet de la zone.
stub-host: <nom de domaine>
Nom du serveur de noms de la zone stub. Est résolu lui-même avant d'être utilisé.

Pour utiliser un port non standard pour la communication DNS, ajoutez '@' suivi du numéro de port.

Si TLS est activé, vous pouvez ajouter '#' suivi d'un nom, cela vérifiera alors les certificats d'authentification TLS avec ce nom.

Si vous combinez '@' et '#', le '@' vient en premier. Si seul '#' est utilisé, le port par défaut est le tls-port configuré.

stub-addr: <adresse IP>
Adresse IP du serveur de noms de la zone stub. Peut être IPv4 ou IPv6.

Pour utiliser un port non standard pour la communication DNS, ajoutez '@' suivi du numéro de port.

Si TLS est activé, vous pouvez ajouter '#' suivi d'un nom, cela vérifiera alors les certificats d'authentification TLS avec ce nom.

Si vous combinez '@' et '#', le '@' vient en premier. Si seul '#' est utilisé, le port par défaut est le tls-port configuré.

stub-prime: <oui ou non>
Si activé, effectue le "priming" des ensembles NS, ce qui est similaire aux indices racine, où il commence à utiliser la liste des serveurs de noms actuellement publiés par la zone. Ainsi, si la liste d'indices est légèrement obsolète, le résolveur récupère une liste correcte en ligne.

Par défaut : non

stub-first: <oui ou non>
Si activé, une requête est tentée sans la clause stub si elle échoue. Les données n'ont pas pu être récupérées et auraient provoqué SERVFAIL car les serveurs sont inaccessibles, au lieu de cela, elles sont essayées sans cette clause.

Par défaut : non

stub-tls-upstream: <oui ou non>
Active ou désactive si les requêtes vers cette zone stub utilisent TLS pour le transport.

Par défaut : non

stub-ssl-upstream: <oui ou non>
Syntaxe alternative pour stub-tls-upstream.
stub-tcp-upstream: <oui ou non>
S'il est défini sur "oui", les requêtes en amont utilisent TCP uniquement pour le transport, indépendamment de l'indicateur global tcp-upstream.

Par défaut : non

Options de Zone Locale

Les options de zone locale vous permettent de définir des règles spécifiques pour certains domaines. Cela peut être utilisé pour des zones privées, pour modifier le comportement de résolution de certains domaines, ou pour des raisons de sécurité.

Définit un type de zone locale pour le domaine spécifié. Les types de zone disponibles sont :

  • deny : Les requêtes pour ce domaine recevront une réponse NXDOMAIN (Name Error).

  • redirect : Les requêtes pour ce domaine seront redirigées vers une adresse IP spécifiée par l'option local-data-ptr.

  • transparent : Les requêtes pour ce domaine seront résolues normalement, mais elles ne seront pas mises en cache. Cela est utile pour contourner la mise en cache des zones RFC1918 ou des zones sensibles.

  • nodefault : Supprime la zone locale par défaut pour ce domaine. Utile pour désactiver des zones comme RFC1918 par défaut.

  • rpz-client-ip : L'adresse IP du client est utilisée pour les requêtes de zone dans le cadre du programme de réponse aux zones (RPZ).

Exemple : local-zone: "example.com" refuse

local-data: <enregistrement DNS>
Ajoute un enregistrement DNS local personnalisé. Cet enregistrement sera servi au lieu d'une requête externe. La syntaxe est celle d'un enregistrement DNS standard (par exemple, local-data: "host.example.com. IN A 192.168.1.10").

Vous pouvez utiliser le type de zone redirect avec local-data pour spécifier une adresse IP vers laquelle rediriger les requêtes. Par exemple : local-zone: "badsite.com" redirect local-data: "badsite.com A 127.0.0.1"

local-data-ptr: <enregistrement DNS PTR>
Ajoute un enregistrement DNS PTR (pointeur inversé) local personnalisé. Utile pour les zones de recherche DNS inversées. La syntaxe est celle d'un enregistrement PTR standard (par exemple, local-data-ptr: "10.1.168.192.in-addr.arpa. IN PTR host.example.com.").

Si vous utilisez le type de zone redirect, cet enregistrement sera utilisé pour les recherches PTR inversées pour l'IP spécifiée dans local-data.

local-zone-tag: <nom de domaine> <étiquette>
Associe une étiquette personnalisée à une zone locale. Cette étiquette peut ensuite être utilisée dans les règles de traitement des zones (RPZ) pour appliquer des actions spécifiques.

Exemple : local-zone-tag: "malware.com" malicious

local-zone-block-len: <oui ou non>
Si activé, Unbound bloquera les réponses contenant des enregistrements dont la longueur dépasse la longueur spécifiée par la longueur de bloc DNS (généralement 255 octets pour les enregistrements textuels). Ceci est utile pour se prémunir contre les attaques de type "buffer overflow" ou les réponses malveillantes.

Par défaut : oui

Options DNSSEC

Ces options configurent le comportement de la validation DNSSEC d'Unbound.

harden-dnssec-stripped: <oui ou non>
Si activé, Unbound tentera de détecter et de se prémunir contre les attaques qui tentent de supprimer les signatures DNSSEC des réponses DNS. Cela garantit que les réponses DNSSEC sont reçues avec leurs signatures intactes.

Par défaut : oui

harden-offline: <oui ou non>
Si activé, Unbound ne tentera pas de pré-récupérer les enregistrements lors de la validation DNSSEC si le serveur DNS est hors ligne. Cela évite des retards inutiles lors de la validation de zones qui ne sont pas accessibles.

Par défaut : non

harden-glue: <oui ou non>
Si activé, Unbound vérifiera la cohérence des enregistrements "glue" (enregistrements utilisés pour résoudre les noms d'hôtes dans la zone des serveurs de noms d'une autre zone). Cela aide à prévenir les attaques de type "cache poisoning" qui pourraient manipuler les enregistrements glue.

Par défaut : oui

harden-large-queries: <oui ou non>
Si activé, Unbound limitera la taille des requêtes qu'il envoie pour se prémunir contre les attaques par déni de service qui abusent des grandes requêtes DNS.

Par défaut : oui

dns64-activate-addr: <adresse IP>
Active la fonctionnalité DNS64 pour l'adresse IPv6 spécifiée. Le DNS64 est un mécanisme utilisé pour faire fonctionner le DNS sur IPv6 lorsque les serveurs de noms ne prennent en charge que IPv4. Les requêtes pour des noms sans enregistrement AAAA seront synthétisées avec un enregistrement AAAA pointant vers l'adresse IPv6 spécifiée.

Par défaut : (none)

dns64-prefix: <préfixe IPv6>
Définit le préfixe IPv6 à utiliser lors de la génération d'enregistrements AAAA synthétiques pour DNS64. Le préfixe doit être de la forme x:x:x:x::/x.

Par défaut : 64:ff9b::/96 (préfixe NAT64 standard)

dns64-exclude-internal: <oui ou non>
Si activé, Unbound n'appliquera pas le préfixe DNS64 aux adresses IPv6 qui sont déjà résolues pour des noms de domaine privés (par exemple, les adresses RFC1918).

Par défaut : oui

dns64-only-from-ipv4: <oui ou non>
Si activé, le DNS64 ne sera utilisé que pour les requêtes provenant d'adresses IPv4. Les requêtes provenant d'adresses IPv6 ne déclencheront pas de synthèse DNS64.

Par défaut : non

trust-anchor-file: <nom de fichier>
Spécifie un fichier contenant les ancres de confiance DNSSEC (par exemple, la clé de confiance racine). Ces ancres sont utilisées comme point de départ pour la validation DNSSEC. Si non spécifié, Unbound utilise une clé racine codée en dur. Vous pouvez obtenir des ancres de confiance à jour à partir de sources fiables comme l'IANA.

Par défaut : unbound_control.key

trust-anchor: <clé DNSSEC>
Permet de spécifier une ancre de confiance DNSSEC directement dans le fichier de configuration. La clé doit être au format BIND (par exemple, . IN DS 19036 8 2 E06D44B80289D570A6785533357F86B9F8488B4734746E65A98522E95C7F31BF).

Vous pouvez utiliser cette option plusieurs fois pour spécifier plusieurs ancres.

trust-anchor-update-freq: <jours>
Définit la fréquence (en jours) à laquelle Unbound vérifiera les mises à jour de ses ancres de confiance. Si une mise à jour est disponible, Unbound tentera de la télécharger et de l'installer.

Par défaut : 30

dns64-synth-record-ttl: <secondes>
Définit la durée de vie (TTL) pour les enregistrements AAAA synthétiques générés par DNS64.

Par défaut : 3600

Options de Module

Les modules permettent d'étendre les fonctionnalités d'Unbound. L'ordre des modules dans la configuration est important car ils sont exécutés en séquence.

module-config: <nom du module> <paramètres>
Charge et configure un module. Les modules disponibles et leurs paramètres dépendent de la manière dont Unbound a été compilé.

Exemples :

  • module-config: "validator iterator" : Charge le module valideur pour la validation DNSSEC et le module itérateur pour la résolution itérative.

  • module-config: "hint"' : Charge le module d'indice pour utiliser les serveurs racine.

  • module-config: "cachedb"' : Charge le module de base de données de cache.

L'ordre par défaut des modules est généralement : validator iterator hint cachedb.

module-depth: <nombre de niveaux>
Définit la profondeur maximale de la chaîne de résolution de noms que les modules peuvent gérer. Cela évite les boucles infinies dans les résolutions récursives.

Par défaut : 20

Options de Limitation de Débit

Ces options permettent de limiter le débit des requêtes DNS pour prévenir les abus et les attaques par déni de service.

ratelimit: <nombre de requêtes> <intervalle en secondes>
Définit la limite de débit pour les requêtes DNS. Par exemple, ratelimit: 1000 60 signifie que le serveur ne traitera pas plus de 1000 requêtes par minute. Les requêtes excédant cette limite seront rejetées ou mises en file d'attente.

Par défaut : (none)

ratelimit-below-nxdomain: <oui ou non>
Si activé, la limite de débit s'applique également aux réponses NXDOMAIN (non trouvées). Cela peut aider à atténuer les attaques qui exploitent les réponses NXDOMAIN.

Par défaut : non

ratelimit-below-nodata: <oui ou non>
Si activé, la limite de débit s'applique également aux réponses NODATA (aucun enregistrement trouvé pour un type de requête spécifique).

Par défaut : non

ratelimit-above-nxdomain: <oui ou non>
Si activé, les réponses NXDOMAIN sont autorisées même si la limite de débit est atteinte. Cela peut être utile pour garantir que les requêtes valides pour des domaines inexistants ne sont pas bloquées.

Par défaut : non

ratelimit-above-nodata: <oui ou non>
Si activé, les réponses NODATA sont autorisées même si la limite de débit est atteinte.

Par défaut : non

ratelimit-whitelist: <nom de fichier>
Spécifie un fichier contenant une liste d'adresses IP qui sont exemptées de la limitation de débit. Utile pour autoriser des clients ou des serveurs spécifiques à avoir un débit plus élevé.

Par défaut : (none)

ratelimit-ip-list: <adresse IP/masque>
Permet de spécifier des listes d'adresses IP ou des sous-réseaux qui sont exemptés de la limitation de débit. Peut être utilisé plusieurs fois.

Par défaut : (none)

Options RPZ

Les Options de RPZ (Response Policy Zones) permettent de définir des politiques de réponse personnalisées pour les requêtes DNS. Ceci est utilisé pour implémenter des listes de blocage, des redirections, ou d'autres politiques basées sur les noms de domaine.

rpz-zone: <nom de fichier de zone>
Spécifie un fichier contenant les définitions d'une Response Policy Zone (RPZ). Le fichier doit être au format de zone BIND. Vous pouvez utiliser cette option plusieurs fois pour spécifier plusieurs zones RPZ.

Exemple : rpz-zone: "/etc/unbound/rpz-blocklist.zone"

rpz-name: <nom de domaine>
Définit le nom de la RPZ pour laquelle les actions seront appliquées. Cela correspond au nom de domaine dans le fichier de zone RPZ.

Exemple : rpz-name: "rpz.local"

rpz-action-nxdomain: <nom de domaine>
Définit l'action à entreprendre lorsqu'une requête correspond à une entrée dans la RPZ et que l'action spécifiée est NXDOMAIN. L'argument est le nom de domaine qui sera retourné dans la réponse NXDOMAIN. Vous pouvez utiliser un joker (par exemple, *) pour que le nom de domaine d'origine soit retourné.

Exemple : rpz-action-nxdomain: "bad.example.com"

rpz-action-cname: <nom de domaine>
Définit l'action à entreprendre lorsqu'une requête correspond à une entrée dans la RPZ et que l'action spécifiée est CNAME. L'argument est le nom de domaine qui sera retourné dans la réponse CNAME.

Exemple : rpz-action-cname: "redirect.example.com"

rpz-action-passthru: <oui ou non>
Si activé, les requêtes qui correspondent à une entrée dans la RPZ avec l'action "passthru" seront traitées normalement par Unbound. Cela permet de ne pas appliquer de politique pour certaines entrées.

Par défaut : non

rpz-action-throttle: <oui ou non>
Si activé, les requêtes qui correspondent à une entrée dans la RPZ avec l'action "throttle" seront ralenties. Cela peut être utilisé pour limiter la fréquence des requêtes vers des domaines spécifiques.

Par défaut : non

rpz-action-drop: <oui ou non>
Si activé, les requêtes qui correspondent à une entrée dans la RPZ avec l'action "drop" seront silencieusement supprimées. Aucune réponse ne sera envoyée au client.

Par défaut : non

rpz-log: <oui ou non>
Si activé, Unbound enregistrera toutes les actions effectuées par les RPZ. Utile pour le débogage et la surveillance des politiques appliquées.

Par défaut : non

rpz-log-name: <nom de fichier>
Spécifie le fichier dans lequel les journaux RPZ doivent être écrits. Si non spécifié, les journaux RPZ seront écrits dans le fichier journal principal d'Unbound.

Par défaut : (none)

rpz-size: <nombre d'entrées>
Définit la taille maximale du cache pour les RPZ. Cela permet de limiter la quantité de mémoire utilisée pour stocker les règles RPZ.

Par défaut : 100000

Options de zone d'autorité

Les zones d'autorité sont configurées avec auth-zone:, et chacune doit avoir un name. Il peut y en avoir plusieurs, en listant plusieurs clauses auth-zone, chacune avec un nom différent, concernant cette partie de l'espace de noms. La zone d'autorité dont le nom est le plus proche du nom recherché est utilisée. Les zones d'autorité peuvent être traitées à deux stades distincts, non exclusifs et configurables.

Avec for-downstream: oui (par défaut), les zones d'autorité sont traitées après local-zones et avant le cache. Lorsqu'elles sont utilisées de cette manière, Unbound répond comme un serveur d'autorité sans aucun traitement supplémentaire autre que de renvoyer une réponse à partir du contenu de la zone. Un exemple notable, dans ce cas, est les enregistrements CNAME qui sont retournés tels quels aux clients en aval sans résolution supplémentaire.

Avec for-upstream: oui (par défaut), les zones d'autorité sont traitées après la recherche dans le cache, juste avant d'aller sur le réseau pour récupérer des informations pour la récursion. Lorsqu'elles sont utilisées de cette manière, elles fournissent une copie locale d'un serveur d'autorité qui accélère les recherches pour ces données lors de la résolution.

Si les deux options sont activées (par défaut), les requêtes clients pour une zone d'autorité sont traitées de manière faisant autorité par Unbound, tandis que les requêtes internes qui nécessitent des données de la zone d'autorité consultent les données de la zone locale au lieu d'aller sur le réseau.

Une configuration intéressante est for-downstream: non, for-upstream: oui qui permet un comportement hyperlocal où les requêtes clients et internes consultent les données de la zone locale lors de la résolution. Dans ce cas, l'exemple CNAME mentionné précédemment aboutira à une réponse entièrement résolue.

Les zones d'autorité peuvent être lues à partir d'un fichier de zone. Et peuvent être tenues à jour via AXFR et IXFR. Après la mise à jour, le fichier de zone est réécrit. Le mécanisme de mise à jour utilise les valeurs de temps du SOA et effectue des requêtes SOA UDP pour détecter les changements de zone.

Si la récupération de la mise à jour échoue, les minuteries du enregistrement SOA sont utilisées pour programmer une autre tentative de récupération. Jusqu'à ce que la minuterie d'expiration de la zone soit atteinte. La zone est alors expirée. Lorsqu'une zone est expirée, les requêtes sont SERVFAIL, et tout nouveau numéro de série est accepté du primaire (même s'il est plus ancien), et si le fallback est activé, le fallback s'active pour récupérer auprès de l'amont au lieu de SERVFAIL.

Où télécharger une copie de la zone, avec AXFR et IXFR. Plusieurs primaires peuvent être spécifiés. Ils sont tous essayés si l'un échoue.

Pour utiliser un port non par défaut pour la communication DNS, ajoutez '@' avec le numéro de port.

Vous pouvez ajouter un '#' et un nom, puis AXFR sur TLS peut être utilisé et les certificats d'authentification TLS seront vérifiés avec ce nom.

Si vous combinez le '@' et le '#', le '@' vient en premier. Si vous pointez vers une autre instance Unbound, cela ne fonctionnerait pas car elle ne prend pas en charge AXFR/IXFR pour la zone, mais si vous utilisiez url pour télécharger le fichier de zone sous forme de fichier texte à partir d'un serveur web, cela fonctionnerait.

Si vous spécifiez le nom d'hôte, vous ne pouvez pas utiliser le domaine du fichier de zone, car il pourrait ne pas l'avoir lors de la récupération de ces données. Utilisez plutôt une adresse IP simple pour éviter une dépendance circulaire lors de la récupération de cette adresse IP.

Syntaxe alternative pour primary.

Où télécharger un fichier de zone pour la zone. Avec HTTP ou HTTPS. Un exemple pour l'URL est :
http://www.example.com/example.org.zone

Si des primaires sont également répertoriés, les primaires sont d'abord sondés avec des requêtes SOA UDP pour voir si le numéro de série SOA a changé, réduisant ainsi le nombre de téléchargements. Si vous spécifiez un nom d'hôte dans l'URL, vous ne pouvez pas utiliser le domaine du fichier de zone, car il pourrait ne pas l'avoir lors de la récupération de ces données. Utilisez plutôt une adresse IP simple pour éviter une dépendance circulaire lors de la récupération de cette adresse IP.

Évitez les dépendances sur la résolution de noms en utilisant une notation telle que "http://192.0.2.1/unbound-primaries/example.com.zone", avec une adresse IP explicite.

Si activé, Unbound sert des réponses d'autorité aux clients en aval pour cette zone. Cette option fait qu'Unbound se comporte, pour les requêtes dont les noms sont dans cette zone, comme l'un des serveurs d'autorité pour cette zone.

Par défaut : oui

for-upstream: <oui ou non>
Si activé, Unbound récupère les données de cette collection de données pour répondre aux requêtes de récursion. Au lieu d'envoyer des requêtes sur Internet aux serveurs d'autorité pour cette zone, il récupère les données directement à partir des données de la zone.

Activez-la lorsque vous souhaitez qu'Unbound fournisse de la récursion aux clients en aval et utilise les données de la zone comme copie locale pour accélérer les recherches.

Par défaut : oui

Activez cette option pour vérifier les enregistrements ZONEMD dans la zone. L'enregistrement ZONEMD est une somme de contrôle des données de la zone. Cela inclut les glue records dans la zone et les données du fichier de zone, et exclut les commentaires du fichier de zone. Lorsqu'il existe une chaîne de confiance DNSSEC, les signatures DNSSEC sont également vérifiées.

Par défaut : non

zonemd-reject-absence: <oui ou non>
Activez cette option pour rejeter l'absence de l'enregistrement ZONEMD. Sans elle, lorsque ZONEMD n'est pas présent, il n'est pas vérifié.

Il est utile de l'activer pour une zone non signée par DNSSEC où l'opérateur souhaite exiger la vérification d'un ZONEMD, par conséquent, un ZONEMD manquant est un échec.

L'action en cas d'échec est contrôlée par

y l'option zonemd-permissive-mode, pour enregistrer seulement ou aussi bloquer la zone.

Sans l'option, l'absence d'un ZONEMD n'est un échec que si la zone est signée DNSSEC, que nous avons une ancre de confiance et que la vérification DNSSEC de l'absence du ZONEMD échoue. Avec l'option activée, l'absence d'un ZONEMD est toujours un échec, même pour les zones non signées DNSSEC.

Par défaut : no

Le nom du fichier où la zone est stockée. Si non spécifié, aucun fichier de zone n'est utilisé. Si le fichier n'existe pas ou est vide, Unbound tentera de récupérer les données de la zone (par exemple, auprès des serveurs principaux).

Le module ECS doit être configuré dans la directive module-config, par exemple :

NOTE :

Ces paramètres vont dans la section server:.

Si l'adresse de destination est autorisée dans la configuration, Unbound ajoutera l'option EDNS0 à la requête contenant la partie pertinente de l'adresse du client. L'utilisation du module subnetcache ne devrait être activée que dans les installations qui nécessitent une telle fonctionnalité, où le résolveur et les clients appartiennent à des réseaux différents. Un exemple de cela est une installation de résolveur ouvert.

Ce module n'interagit pas avec les options serve-expired* et prefetch.

Options du module de support Opportunistic IPsec

Le module IPsec doit être configuré dans la directive module-config, par exemple :

module-config: "ipsecmod validator iterator"

et compilé dans Unbound en utilisant --enable-ipsecmod pour être activé.

NOTE :

Ces paramètres vont dans la section server:.

Lorsque Unbound reçoit une requête A/AAAA qui n'est pas dans le cache et trouve une réponse valide, il retarde la restitution de la réponse et génère à la place une sous-requête IPSECKEY pour le même nom de domaine. Si une réponse a été trouvée, Unbound appelle un hook externe en passant les arguments suivants :

QNAME
Nom de domaine de la requête A/AAAA et IPSECKEY. Au format chaîne.
IPSECKEY TTL
TTL de l'ensemble d'enregistrements IPSECKEY.
A/AAAA
Chaîne d'adresses IP séparées par des espaces présentes dans l'ensemble d'enregistrements A/AAAA. Les adresses IP sont au format chaîne.
IPSECKEY
Chaîne de RDATA IPSECKEY séparées par des espaces présentes dans l'ensemble d'enregistrements IPSECKEY. Les RDATA IPSECKEY sont au format de présentation DNS.

La réponse A/AAAA est ensuite mise en cache et retournée au client. Si le hook externe a été appelé, le TTL est modifié pour s'assurer qu'il ne dépasse pas ipsecmod-max-ttl.

La même procédure est également suivie lorsque prefetch: yes est défini, mais la réponse A/AAAA est donnée au client avant l'appel du hook. ipsecmod-max-ttl garantit que la réponse A/AAAA donnée depuis le cache est toujours pertinente pour l'IPsec opportuniste.

ipsecmod-enabled: <oui ou non>
Spécifie si le module IPsec est activé ou non. Le module IPsec doit toujours être défini dans la directive module-config. Cette option facilite l'activation/désactivation du module sans redémarrer/recharger Unbound.

Défaut : oui

ipsecmod-hook: <nom de fichier>
Spécifie le hook externe qu'Unbound appellera avec system(3). Le fichier peut être spécifié par un chemin absolu ou relatif. Le fichier doit avoir les permissions appropriées pour être exécuté par le même utilisateur qui exécute Unbound. Il doit être présent lorsque le module IPsec est défini dans la directive module-config.
ipsecmod-strict: <oui ou non>
Si activé, Unbound exige que le hook externe renvoie une valeur de succès de 0. En cas d'échec, Unbound répondra par SERVFAIL. La réponse A/AAAA ne sera pas non plus mise en cache.

Défaut : non

ipsecmod-max-ttl: <secondes>
Durée de vie maximale pour les enregistrements A/AAAA mis en cache après l'appel du hook externe.

Défaut : 3600

ipsecmod-ignore-bogus: <oui ou non>
Spécifie le comportement d'Unbound lorsque la réponse IPSECKEY est invalide (bogus). Si défini sur oui, le hook sera appelé et la réponse A/AAAA sera renvoyée au client. Si défini sur non, le hook ne sera pas appelé et la réponse à la requête A/AAAA sera SERVFAIL. Principalement utilisé pour les tests.

Défaut : non

ipsecmod-allow: <domaine>
Autorise la fonctionnalité du module IPsec pour le domaine afin que la logique du module soit exécutée. Peut être spécifié plusieurs fois, pour différents domaines. Si l'option n'est pas spécifiée, tous les domaines sont traités comme autorisés (par défaut).
ipsecmod-whitelist: <domaine>
Syntaxe alternative pour ipsecmod-allow.

Options du module Cache DB

Le module Cache DB doit être configuré dans la directive module-config, par exemple :

module-config: "validator cachedb iterator"

et être compilé dans le démon avec --enable-cachedb.

Si ce module est activé et configuré, la base de données backend spécifiée fonctionne comme un cache de second niveau ; lorsque Unbound ne trouve pas de réponse à une requête dans son cache intégré en mémoire, il consulte le backend spécifié. S'il trouve une réponse valide dans le backend, Unbound l'utilise pour répondre à la requête sans effectuer de résolution DNS itérative. Si Unbound ne trouve même pas de réponse dans le backend, il résout la requête comme d'habitude et stocke la réponse dans le backend.

Ce module interagit avec les options serve-expired-* et répondra avec des données expirées si Unbound est configuré pour cela.

Si Unbound a été compilé avec --with-libhiredis sur un système qui a installé la bibliothèque client C hiredis de Redis, alors le backend redis peut être utilisé. Ce backend communique avec le serveur Redis spécifié via une connexion TCP pour stocker et récupérer des données de cache. Il peut être utilisé comme backend de cache persistant et/ou partagé.

NOTE :

Unbound ne supprime jamais les données stockées dans le serveur Redis, même si certaines données ont expiré en termes de TTL DNS ou si le serveur Redis a mis trop de données en cache ; si nécessaire, le serveur Redis doit être configuré pour limiter la taille du cache, de préférence avec une politique d'éviction de type « moins récemment utilisé » (LRU).

De plus, l'option redis-expire-records peut être utilisée pour définir le TTL DNS relatif du message comme délai d'expiration pour les enregistrements Redis ; gardez à l'esprit qu'une mémoire supplémentaire est utilisée par clé et que les informations d'expiration sont stockées sous forme de timestamps Unix absolus dans Redis (l'heure de l'ordinateur doit être stable).

Ce backend utilise une communication synchrone avec le serveur Redis, en supposant que la communication est stable et suffisamment rapide. Le thread attendant une réponse du serveur Redis ne peut pas traiter d'autres requêtes DNS. Bien que le backend ait la capacité de se reconnecter au serveur lorsque la connexion est fermée de manière inattendue et qu'il existe un délai d'attente configurable au cas où le serveur serait trop lent ou bloqué, ces cas sont supposés être très rares. Si la fermeture de la connexion ou le délai d'attente se produit trop souvent, Unbound deviendra effectivement inutilisable avec ce backend. Il incombe à l'administrateur de s'assurer que l'hypothèse est respectée.

Options de zone de politique de réponse

Les zones de politique de réponse (Response Policy Zones) sont configurées avec rpz:, et chacune doit avoir un attribut name. module-config: "respip validator iterator"

CONFIGURER UNBOUND

Le fichier de configuration par défaut est <unbound.conf>, et il est situé dans </etc/unbound>. Il peut être remplacé par l'option -c lors du lancement d'Unbound.

Toutes les configurations sont lues dans des blocs, nommés par le mot-clé des instructions du bloc, par exemple :

server:
    verbosity: 1

ou

remote-control:
    control-enable: yes

Les instructions de configuration peuvent être données plusieurs fois, elles sont lues et ajoutées dans une liste.

Les blocs peuvent être imbriqués. Par exemple, un bloc rpz: peut contenir plusieurs zones RPZ.

rpz:
    name: "rpz-example.com"
    zonefile: "rpz-example.com.zone"

    name: "malware.com"
    primary: 192.0.2.1
    allow-notify: 192.0.2.1

Le fichier de configuration est parsé, et les options sont validées.

Note : Si des instructions sont inconnues, elles sont ignorées, sans avertissement.

Pour des exemples de fichiers de configuration, voir EXAMPLES.

ZONES DE POLITIQUE DE RÉSOLUTION (RPZ)

Les zones de politique de résolution (Response Policy Zones - RPZ) permettent de renvoyer des réponses DNS spécifiques pour des requêtes, souvent utilisées pour le blocage de domaines malveillants ou pour le filtrage de contenu. Les zones RPZ sont appliquées avant toute autre zone locale ou autoritaire.

Les déclencheurs RPZ (triggers) sont appliqués après toute zone locale et avant toute zone autoritaire.

La zone RPZ est une zone DNS régulière formatée avec un enregistrement SOA de départ, comme d'habitude. Les éléments de la zone sont des entrées, qui spécifient sur quoi agir (le déclencheur) et quoi faire (l'action). Le déclencheur sur lequel agir est enregistré dans le nom, l'action à faire est enregistrée comme enregistrement de ressource. Les noms se terminent tous par le nom de la zone, vous pouvez donc taper les noms des déclencheurs sans point final dans le fichier de zone.

Un exemple d'enregistrement RPZ, qui répond à example.com avec NXDOMAIN :

example.com CNAME .

Les déclencheurs sont encodés dans le nom à gauche

name                          nom de la requête
netblock.rpz-client-ip        adresse IP du client
netblock.rpz-ip               adresse IP de réponse dans la réponse
name.rpz-nsdname              nom du serveur de noms
netblock.rpz-nsip             adresse IP du serveur de noms

Le bloc réseau est écrit comme <longueur>.<adresse IP inversée>. Pour IPv6, utilisez 'zz' pour '::'. Spécifiez des adresses individuelles avec une longueur de portée de 32 ou 128. Par exemple, 24.10.100.51.198.rpz-ip est 198.51.100.10/24 et 32.10.zz.db8.2001.rpz-ip est 2001:db8:0:0:0:0:0:10/32.

Les actions sont spécifiées avec l'enregistrement à droite

CNAME .                      réponse nxdomain
CNAME *.                     réponse nodata
CNAME rpz-passthru.          ne rien faire, continuer
CNAME rpz-drop.              la requête est ignorée
CNAME rpz-tcp-only.          répondre sur TCP
A 192.0.2.1                  répondre avec cette adresse IP

D'autres enregistrements comme AAAA, TXT et d'autres CNAME (pas rpz-..) peuvent également être utilisés pour répondre aux requêtes avec ce contenu.

Les zones RPZ peuvent être configurées dans le fichier de configuration avec ces paramètres dans le bloc rpz:.

name: <nom de la zone>
Nom de la zone autoritaire.
primary: <adresse IP ou nom d'hôte>
Où télécharger une copie de la zone, avec AXFR et IXFR. Plusieurs serveurs principaux peuvent être spécifiés. Ils sont tous essayés si l'un échoue.

Pour utiliser un port non par défaut pour la communication DNS, ajoutez '@' avec le numéro de port.

Vous pouvez ajouter un '#' et un nom, alors AXFR sur TLS peut être utilisé et les certificats d'authentification TLS seront vérifiés avec ce nom.

Si vous combinez le '@' et le '#', le '@' vient en premier. Si vous pointez vers une autre instance Unbound, cela ne fonctionnera pas car elle ne prend pas en charge AXFR/IXFR pour la zone, mais si vous utilisez url pour télécharger le fichier de zone sous forme de fichier texte depuis un serveur web, cela fonctionnerait.

Si vous spécifiez le nom d'hôte, vous ne pouvez pas utiliser le domaine du fichier de zone, car il pourrait ne pas l'avoir lors de la récupération de ces données, utilisez plutôt une adresse IP simple pour éviter une dépendance circulaire lors de la récupération de cette adresse IP.

master: <adresse IP ou nom d'hôte>
Syntaxe alternative pour primary.
url: <url du fichier de zone>
Où télécharger un fichier de zone pour la zone. Avec HTTP ou HTTPS. Un exemple d'url est :
http://www.example.com/example.org.zone

Plusieurs déclarations url peuvent être données, elles sont essayées à tour de rôle.

Si seules des urls sont données, le minuteur de rafraîchissement SOA est utilisé pour attendre la réalisation de nouveaux téléchargements. Si des serveurs principaux sont également listés, les serveurs principaux sont d'abord interrogés avec des requêtes SOA UDP pour voir si le numéro de série SOA a changé, réduisant ainsi le nombre de téléchargements. Si aucune des URLs ne fonctionne, les serveurs principaux sont essayés avec IXFR et AXFR.

Pour HTTPS, le tls-cert-bundle et le nom d'hôte de l'url sont utilisés pour authentifier la connexion.

allow-notify: <adresse IP ou nom d'hôte ou bloc IP/préfixe>
Avec allow-notify vous pouvez spécifier des sources supplémentaires de notifications. Lorsque notifié, le serveur tente d'abord d'interroger puis de transférer la zone. Si la notification provient d'un serveur principal, il tente d'abord ce serveur principal. Sinon, d'autres serveurs principaux sont tentés. S'il n'y a pas de serveurs principaux, mais seulement des urls, le fichier est téléchargé lors de la notification.

NOTE :

Les serveurs principaux des déclarations primary et url sont autorisés à notifier par défaut.
zonefile: <nom de fichier>
Le nom du fichier où la zone est stockée. S'il n'est pas donné, aucun fichier de zone n'est utilisé. Si le fichier n'existe pas ou est vide, Unbound tentera de récupérer les données de la zone (par exemple, des serveurs principaux).
rpz-action-override: <action>
Utiliser toujours cette action RPZ pour les déclencheurs correspondants de cette zone. Les actions possibles sont : nxdomain, nodata, passthru, drop, disabled et cname.
rpz-cname-override: <domaine>
Le domaine cible CNAME à utiliser si l'action cname est configurée pour rpz-action-override.
rpz-log: <oui ou non>
Enregistrer toutes les actions RPZ appliquées pour cette zone RPZ.

Par défaut : non

rpz-log-name: <nom>
Spécifier une chaîne à inclure dans la ligne de journalisation, pour faciliter la référence.
rpz-signal-nxdomain-ra: <oui ou non>
Signaler lorsqu'une requête est bloquée par la RPZ avec NXDOMAIN en utilisant un drapeau RA non défini. Cela permet à certains clients, comme dnsmasq, d'en déduire que le domaine est bloqué extérieurement.

Par défaut : non

for-downstream: <oui ou non>
Si activée, la zone est traitée de manière autoritaire et les requêtes d'informations sur la zone RPZ sont renvoyées aux clients en aval. Ceci est utile pour les scripts de surveillance, qui peuvent alors accéder aux informations SOA pour vérifier si les informations RPZ sont à jour.

Par défaut : non

tags: "<liste de tags>"
Limiter les politiques de cette clause RPZ aux clients avec un tag correspondant.

Les tags doivent être définis dans define-tag et peuvent être attribués à des adresses client en utilisant access-control-tag ou interface-tag. Encadrez la liste des tags entre guillemets ("") et séparez-les par des espaces.

Si aucun tag n'est spécifié, les politiques de cette clause seront appliquées à tous les clients.

EXEMPLE DE CONTRÔLE MÉMOIRE

Dans les exemples de paramètres de configuration ci-dessous, l'utilisation de la mémoire est réduite. Certains niveaux de service sont plus bas, notamment les données très volumineuses et une charge TCP élevée ne sont plus supportées. Les données très volumineuses et les charges TCP élevées sont exceptionnelles pour le DNS. La validation DNSSEC est activée, il suffit d'ajouter des ancres de confiance. Si vous n'avez pas à vous soucier que les programmes utilisent plus de 3 Mo de mémoire, l'exemple ci-dessous n'est pas pour vous. Utilisez les paramètres par défaut pour recevoir un service complet, qui sur BSD-32 bits peut atteindre 30-40 Mo après une utilisation intensive.

# exemples de paramètres qui réduisent l'utilisation de la mémoire
server:
    num-threads: 1
    outgoing-num-tcp: 1 # ceci limite le service TCP, utilise moins de tampons.
    incoming-num-tcp: 1
    outgoing-range: 60  # utilise moins de mémoire, mais moins de performance.
    msg-buffer-size: 8192   # notez que cela limite le service, 'pas de trucs énormes'.
    msg-cache-size: 100k
    msg-cache-slabs: 1
    rrset-cache-size: 100k
    rrset-cache-slabs: 1
    infra-cache-numhosts: 200
    infra-cache-slabs: 1
    key-cache-size: 100k
    key-cache-slabs: 1
    neg-cache-size: 10k
    num-queries-per-thread: 30
    target-fetch-policy: "2 1 0 0 0 0"
    harden-large-queries: "yes"
    harden-short-bufsize: "yes"
