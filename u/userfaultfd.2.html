userfaultfd(2) Manuel des appels système userfaultfd(2)

NOM

userfaultfd - créer un descripteur de fichier pour la gestion des fautes de page dans l'espace utilisateur

BIBLIOTHÈQUE

Bibliothèque C standard (libc, -lc)

SYNOPSIS

#include <fcntl.h>             /* Définition des constantes O_* */
#include <sys/syscall.h>       /* Définition des constantes SYS_* */
#include <linux/userfaultfd.h> /* Définition des constantes UFFD_* */
#include <unistd.h>
int syscall(SYS_userfaultfd, int flags);

Note : glibc ne fournit pas d'enveloppe pour userfaultfd(), nécessitant l'utilisation de syscall(2).

DESCRIPTION

userfaultfd() crée un nouvel objet userfaultfd qui peut être utilisé pour déléguer la gestion des fautes de page à une application en espace utilisateur, et retourne un descripteur de fichier qui référence le nouvel objet. Le nouvel objet userfaultfd est configuré à l'aide de ioctl(2).

Une fois l'objet userfaultfd configuré, l'application peut utiliser read(2) pour recevoir les notifications userfaultfd. Les lectures depuis userfaultfd peuvent être bloquantes ou non bloquantes, selon la valeur de flags utilisée pour la création de l'userfaultfd ou les appels ultérieurs à fcntl(2).

Les valeurs suivantes peuvent être combinées par OR bit à bit dans flags pour modifier le comportement de userfaultfd():

O_CLOEXEC
Active le drapeau close-on-exec pour le nouveau descripteur de fichier userfaultfd. Voir la description du drapeau O_CLOEXEC dans open(2).
O_NONBLOCK
Active le fonctionnement non bloquant pour l'objet userfaultfd. Voir la description du drapeau O_NONBLOCK dans open(2).
UFFD_USER_MODE_ONLY
C'est un drapeau spécifique à userfaultfd qui a été introduit dans Linux 5.11. Lorsqu'il est défini, l'objet userfaultfd ne pourra gérer que les fautes de page provenant de l'espace utilisateur sur les régions enregistrées. Lorsqu'une faute originaire du noyau était déclenchée sur la plage enregistrée avec cet userfaultfd, un signal SIGBUS sera délivré.

Lorsque le dernier descripteur de fichier faisant référence à un objet userfaultfd est fermé, toutes les plages mémoire qui étaient enregistrées avec l'objet sont désenregistrées et les événements non lus sont vidés.

Userfaultfd supporte trois modes d'enregistrement :

UFFDIO_REGISTER_MODE_MISSING (depuis Linux 4.10)
Lorsqu'il est enregistré avec le mode UFFDIO_REGISTER_MODE_MISSING, l'espace utilisateur recevra une notification de faute de page lorsqu'une page manquante est accédée. Le thread fautif sera arrêté avant l'exécution jusqu'à ce que la faute de page soit résolue depuis l'espace utilisateur par un ioctl UFFDIO_COPY ou UFFDIO_ZEROPAGE.
UFFDIO_REGISTER_MODE_MINOR (depuis Linux 5.13)
Lorsqu'il est enregistré avec le mode UFFDIO_REGISTER_MODE_MINOR, l'espace utilisateur recevra une notification de faute de page lors d'une faute de page mineure. C'est-à-dire, lorsqu'une page de support est dans le cache de pages, mais que les entrées de la table des pages n'existent pas encore. Le thread fautif sera arrêté avant l'exécution jusqu'à ce que la faute de page soit résolue depuis l'espace utilisateur par un ioctl UFFDIO_CONTINUE.
UFFDIO_REGISTER_MODE_WP (depuis Linux 5.7)
Lorsqu'il est enregistré avec le mode UFFDIO_REGISTER_MODE_WP, l'espace utilisateur recevra une notification de faute de page lorsqu'une page protégée en écriture est écrite. Le thread fautif sera arrêté avant l'exécution jusqu'à ce que l'espace utilisateur retire la protection en écriture de la page à l'aide d'un ioctl UFFDIO_WRITEPROTECT.

Plusieurs modes peuvent être activés en même temps pour la même plage mémoire.

Depuis Linux 4.14, une notification de faute de page userfaultfd peut intégrer sélectivement des informations d'identifiant de thread fautif dans la notification. Il faut activer explicitement cette fonctionnalité en utilisant le bit de fonctionnalité UFFD_FEATURE_THREAD_ID lors de l'initialisation du contexte userfaultfd. Par défaut, le rapport d'identifiant de thread est désactivé.

UTILISATION

Le mécanisme userfaultfd est conçu pour permettre à un thread dans un programme multithreadé d'effectuer la pagination en espace utilisateur pour les autres threads du processus. Lorsqu'une faute de page se produit pour l'une des régions enregistrées auprès de l'objet userfaultfd, le thread fautif est mis en sommeil et un événement est généré qui peut être lu via le descripteur de fichier userfaultfd. Le thread de gestion des fautes lit les événements depuis ce descripteur de fichier et les traite en utilisant les opérations décrites dans ioctl_userfaultfd(2). Lors du traitement des événements de faute de page, le thread de gestion des fautes peut déclencher un réveil pour le thread endormi.

Il est possible que les threads fautifs et les threads de gestion des fautes s'exécutent dans le contexte de processus différents. Dans ce cas, ces threads peuvent appartenir à des programmes différents, et le programme qui exécute les threads fautifs ne coopérera pas nécessairement avec le programme qui gère les fautes de page. Dans ce mode non coopératif, le processus qui surveille userfaultfd et gère les fautes de page doit être conscient des changements dans la disposition de la mémoire virtuelle du processus fautif pour éviter la corruption de la mémoire.

Depuis Linux 4.11, userfaultfd peut également notifier les threads de gestion des fautes des changements dans la disposition de la mémoire virtuelle du processus fautif. De plus, si le processus fautif invoque fork(2), les objets userfaultfd associés au parent peuvent être dupliqués dans le processus enfant et le moniteur userfaultfd sera notifié (via l'événement UFFD_EVENT_FORK décrit ci-dessous) du descripteur de fichier associé aux objets userfault créés pour le processus enfant, ce qui permet au moniteur userfaultfd d'effectuer la pagination en espace utilisateur pour le processus enfant. Contrairement aux fautes de page qui doivent être synchrones et nécessitent un réveil explicite ou implicite, tous les autres événements sont délivrés de manière asynchrone et le processus non coopératif reprend son exécution dès que le gestionnaire userfaultfd exécute read(2). Le gestionnaire userfaultfd doit soigneusement synchroniser les appels à UFFDIO_COPY avec le traitement des événements.

Le modèle asynchrone actuel de la livraison d'événements est optimal pour les implémentations de gestionnaires userfaultfd non coopératifs à thread unique.

Depuis Linux 5.7, userfaultfd est capable de suivre les pages sales de manière synchrone en utilisant le nouveau mode d'enregistrement de protection en écriture. Il faut vérifier la fonctionnalité UFFD_FEATURE_PAGEFAULT_FLAG_WP avant d'utiliser cette fonctionnalité. Similairement au mode d'origine de l'absence de page userfaultfd, le mode de protection en écriture générera une notification userfaultfd lorsque la page protégée est écrite. L'utilisateur doit résoudre la faute de page en retirant la protection de la page fautive et en incitant le thread fautif à continuer. Pour plus d'informations, veuillez vous reporter à la section "Userfaultfd write-protect mode".

Opération userfaultfd

Après la création de l'objet userfaultfd avec userfaultfd(), l'application doit l'activer en utilisant l'opération ioctl(2) UFFDIO_API. Cette opération permet une poignée de main en deux étapes entre le noyau et l'espace utilisateur pour déterminer quelle version de l'API et quelles fonctionnalités le noyau supporte, puis pour activer les fonctionnalités que l'espace utilisateur souhaite. Cette opération doit être effectuée avant toute autre opération ioctl(2) décrite ci-dessous (sinon ces opérations échoueront avec l'erreur EINVAL).

Après une opération réussie UFFDIO_API, l'application enregistre ensuite des plages d'adresses mémoire en utilisant l'opération ioctl(2) UFFDIO_REGISTER. Après l'achèvement réussi d'une opération UFFDIO_REGISTER, une faute de page se produisant dans la plage mémoire demandée, et satisfaisant le mode défini au moment de l'enregistrement, sera transmise par le noyau à l'application en espace utilisateur. L'application peut alors utiliser diverses opérations ioctl (par exemple, UFFDIO_COPY, UFFDIO_ZEROPAGE, ou UFFDIO_CONTINUE).

Depuis Linux 4.14, si l'application définit le bit de fonctionnalité UFFD_FEATURE_SIGBUS à l'aide de l'opération ioctl(2) UFFDIO_API, aucune notification de défaut de page ne sera transmise à l'espace utilisateur. À la place, un signal SIGBUS est délivré au processus en défaut. Avec cette fonctionnalité, userfaultfd peut être utilisé à des fins de robustesse pour simplement intercepter tout accès à des zones dans la plage d'adresses enregistrée pour lesquelles aucune page n'est allouée, sans avoir à écouter les événements userfaultfd. Aucun moniteur userfaultfd ne sera requis pour traiter de tels accès mémoire. Par exemple, cette fonctionnalité peut être utile pour les applications qui souhaitent empêcher le noyau d'allouer automatiquement des pages et de remplir les trous dans les fichiers épars lorsque le trou est accédé via un mappage mémoire.

La fonctionnalité UFFD_FEATURE_SIGBUS est implicitement héritée via fork(2) si elle est utilisée en combinaison avec UFFD_FEATURE_FORK.

Les détails des diverses opérations ioctl(2) se trouvent dans ioctl_userfaultfd(2).

Depuis Linux 4.11, des événements autres que les défauts de page peuvent être activés lors de l'opération UFFDIO_API.

Jusqu'à Linux 4.11, userfaultfd ne pouvait être utilisé qu'avec des mappages mémoire privés anonymes. Depuis Linux 4.11, userfaultfd peut également être utilisé avec les mappages hugetlbfs et de mémoire partagée.

Mode de protection en écriture userfaultfd (depuis Linux 5.7)

Depuis Linux 5.7, userfaultfd prend en charge le mode de protection en écriture pour la mémoire anonyme. L'utilisateur doit d'abord vérifier la disponibilité de cette fonctionnalité à l'aide de l'opération ioctl(2) UFFDIO_API contre le bit de fonctionnalité UFFD_FEATURE_PAGEFAULT_FLAG_WP avant d'utiliser cette fonctionnalité.

Depuis Linux 5.19, le mode de protection en écriture est également pris en charge sur les types de mémoire shmem et hugetlbfs. Il peut être détecté avec le bit de fonctionnalité UFFD_FEATURE_WP_HUGETLBFS_SHMEM.

Pour s'enregistrer avec le mode de protection en écriture userfaultfd, l'utilisateur doit initier l'opération ioctl(2) UFFDIO_REGISTER avec le mode UFFDIO_REGISTER_MODE_WP défini. Notez qu'il est légal de surveiller la même plage mémoire avec plusieurs modes. Par exemple, l'utilisateur peut effectuer un UFFDIO_REGISTER avec le mode défini sur UFFDIO_REGISTER_MODE_MISSING | UFFDIO_REGISTER_MODE_WP. Lorsqu'il n'y a que UFFDIO_REGISTER_MODE_WP enregistré, l'espace utilisateur ne recevra aucune notification lorsqu'une page manquante est écrite. Au lieu de cela, l'espace utilisateur recevra une notification de défaut de page en protection en écriture uniquement lorsqu'une page existante mais protégée en écriture est écrite.

Une fois que l'opération ioctl(2) UFFDIO_REGISTER s'est terminée avec le mode UFFDIO_REGISTER_MODE_WP défini, l'utilisateur peut protéger en écriture toute mémoire existante dans la plage à l'aide de l'opération ioctl(2) UFFDIO_WRITEPROTECT où uffdio_writeprotect.mode doit être défini sur UFFDIO_WRITEPROTECT_MODE_WP.

Lorsqu'un événement de protection en écriture se produit, l'espace utilisateur recevra une notification de défaut de page dont uffd_msg.pagefault.flags aura le drapeau UFFD_PAGEFAULT_FLAG_WP défini. Note : comme seules les écritures peuvent déclencher ce type de défaut, les notifications de protection en écriture auront toujours le bit UFFD_PAGEFAULT_FLAG_WRITE défini en plus du bit UFFD_PAGEFAULT_FLAG_WP.

Pour résoudre un défaut de page en protection en écriture, l'utilisateur devrait initier une autre opération ioctl(2) UFFDIO_WRITEPROTECT, dont uffd_msg.pagefault.flags devrait avoir le drapeau UFFDIO_WRITEPROTECT_MODE_WP effacé sur la page ou la plage en défaut.

Mode de défaut mineur userfaultfd (depuis Linux 5.13)

Depuis Linux 5.13, userfaultfd prend en charge le mode de défaut mineur. Dans ce mode, les messages de défaut sont produits non pas pour les défauts majeurs (où la page était manquante), mais pour les défauts mineurs, où une page existe dans le cache de pages, mais les entrées de la table de pages ne sont pas encore présentes. L'utilisateur doit d'abord vérifier la disponibilité de cette fonctionnalité à l'aide de l'opération ioctl(2) UFFDIO_API avec les bits de fonctionnalité appropriés définis avant d'utiliser cette fonctionnalité : UFFD_FEATURE_MINOR_HUGETLBFS depuis Linux 5.13, ou UFFD_FEATURE_MINOR_SHMEM depuis Linux 5.14.

Pour s'enregistrer avec le mode de défaut mineur userfaultfd, l'utilisateur doit initier l'opération ioctl(2) UFFDIO_REGISTER avec le mode UFFD_REGISTER_MODE_MINOR défini.

Lorsqu'un défaut mineur se produit, l'espace utilisateur recevra une notification de défaut de page dont uffd_msg.pagefault.flags aura le drapeau UFFD_PAGEFAULT_FLAG_MINOR défini.

Pour résoudre un défaut de page mineur, le gestionnaire doit décider si le contenu de la page existante doit être modifié au préalable. Si c'est le cas, cela doit être fait sur place via un deuxième mappage, non enregistré userfaultfd, vers la même page sous-jacente (par exemple, en mappant le même fichier shmem ou hugetlbfs deux fois). Une fois que la page est considérée comme "à jour", le défaut peut être résolu en initiant une opération ioctl(2) UFFDIO_CONTINUE, qui installe les entrées de la table de pages et (par défaut) réveille le(s) thread(s) en défaut.

Le mode de défaut mineur ne prend en charge que la mémoire basée sur hugetlbfs (depuis Linux 5.13) et shmem (depuis Linux 5.14).

Lecture de la structure userfaultfd

Chaque read(2) depuis le descripteur de fichier userfaultfd retourne une ou plusieurs structures uffd_msg, chacune décrivant un événement de défaut de page ou un événement requis pour l'utilisation non coopérative de userfaultfd :


struct uffd_msg {
    __u8  event;            /* Type d'événement */
    ...
    union {
        struct {
            __u64 flags;    /* Indicateurs décrivant le défaut */
            __u64 address;  /* Adresse du défaut */
            union {
                __u32 ptid; /* ID du thread du défaut */
            } feat;
        } pagefault;
        struct {            /* Depuis Linux 4.11 */
            __u32 ufd;      /* Descripteur de fichier
                               userfault du processus enfant */
        } fork;
        struct {            /* Depuis Linux 4.11 */
            __u64 from;     /* Ancienne adresse de la zone remappée */
            __u64 to;       /* Nouvelle adresse de la zone remappée */
            __u64 len;      /* Taille originale du mappage */
        } remap;
        struct {            /* Depuis Linux 4.11 */
            __u64 start;    /* Adresse de début de la zone supprimée */
            __u64 end;      /* Adresse de fin de la zone supprimée */
        } remove;
        ...
    } arg;
    /* Champs de remplissage omis */
} __packed;

Si plusieurs événements sont disponibles et que le tampon fourni est suffisamment grand, read(2) retourne autant d'événements qu'il peut en contenir dans le tampon fourni. Si le tampon fourni à read(2) est plus petit que la taille de la structure uffd_msg, la lecture échoue avec l'erreur EINVAL.

Les champs définis dans la structure uffd_msg sont les suivants :

event
Le type d'événement. Selon le type d'événement, différents champs de l'union arg représentent les détails requis pour le traitement de l'événement. Les événements autres que les défauts de page ne sont générés que lorsque la fonctionnalité appropriée est activée lors de la poignée de main API avec l'opération ioctl(2) UFFDIO_API.
Les valeurs suivantes peuvent apparaître dans le champ event :
UFFD_EVENT_PAGEFAULT (depuis Linux 4.3)
Un événement de défaut de page. Les détails du défaut de page sont disponibles dans le champ pagefault.
UFFD_EVENT_FORK (depuis Linux 4.11)
Généré lorsque le processus en défaut appelle fork(2) (ou clone(2) sans le drapeau CLONE_VM). Les détails de l'événement sont disponibles dans le champ fork.
UFFD_EVENT_REMAP (depuis Linux 4.11)
Généré lorsque le processus en défaut appelle mremap(2). Les détails de l'événement sont disponibles dans le champ remap.
UFFD_EVENT_REMOVE (depuis Linux 4.11)
Généré lorsque le processus en défaut appelle madvise(2) avec les conseils MADV_DONTNEED ou MADV_REMOVE. Les détails de l'événement sont disponibles dans le champ remove.
UFFD_EVENT_UNMAP (depuis Linux 4.11)
Généré lorsque le processus en défaut désannexe une plage mémoire, soit explicitement via munmap(2), soit implicitement lors de mmap(2) ou mremap(2). Les détails de l'événement sont disponibles dans le champ remove.
pagefault.address
L'adresse qui a déclenché le défaut de page.
pagefault.flags
Un masque de bits de drapeaux qui décrivent l'événement. Pour UFFD_EVENT_PAGEFAULT, le drapeau suivant peut apparaître :
UFFD_PAGEFAULT_FLAG_WP
Si ce drapeau est défini, alors le défaut était un défaut de protection en écriture.
UFFD_PAGEFAULT_FLAG_MINOR
Si ce drapeau est défini, alors le défaut était un défaut mineur.
UFFD_PAGEFAULT_FLAG_WRITE
Si ce drapeau est défini, alors le défaut était un défaut d'écriture.

Si ni UFFD_PAGEFAULT_FLAG_WP ni UFFD_PAGEFAULT_FLAG_MINOR ne sont définis, alors le défaut était un défaut manquant.

pagefault.feat.pid
L'ID du thread qui a déclenché le défaut de page.
fork.ufd
Le descripteur de fichier associé à l'objet userfault créé pour l'enfant créé par fork(2).
remap.from
L'adresse d'origine de la plage mémoire qui a été remappée à l'aide de mremap(2).
>
remap.to
La nouvelle adresse de la plage de mémoire qui a été remappée à l'aide de mremap(2).
remap.len
La taille d'origine de la plage de mémoire qui a été remappée à l'aide de mremap(2).
remove.start
L'adresse de début de la plage de mémoire qui a été libérée à l'aide de madvise(2) ou désactivée
remove.end
L'adresse de fin de la plage de mémoire qui a été libérée à l'aide de madvise(2) ou désactivée

Une lecture(2) sur un descripteur de fichier userfaultfd peut échouer avec les erreurs suivantes :

EINVAL
L'objet userfaultfd n'a pas encore été activé à l'aide de l'opération ioctl(2) UFFDIO_API

Si le drapeau O_NONBLOCK est activé dans la description de fichier ouverte associée, le descripteur de fichier userfaultfd peut être surveillé avec poll(2), select(2) et epoll(7). Lorsque des événements sont disponibles, le descripteur de fichier est indiqué comme lisible. Si le drapeau O_NONBLOCK n'est pas activé, alors poll(2) (toujours) indique le fichier comme ayant une condition POLLERR, et select(2) indique le descripteur de fichier comme étant à la fois lisible et écrivable.

VALEUR DE RETOUR

En cas de succès, userfaultfd() renvoie un nouveau descripteur de fichier qui fait référence à l'objet userfaultfd. En cas d'erreur, -1 est renvoyé, et errno est défini pour indiquer l'erreur.

ERREURS

EINVAL
Une valeur non prise en charge a été spécifiée dans flags.
EMFILE
La limite par processus sur le nombre de descripteurs de fichiers ouverts a été atteinte
ENFILE
La limite globale du système sur le nombre total de fichiers ouverts a été atteinte.
ENOMEM
Mémoire noyau insuffisante disponible.
EPERM (depuis Linux 5.2)
L'appelant n'est pas privilégié (n'a pas la capacité CAP_SYS_PTRACE dans l'espace de noms utilisateur initial), et /proc/sys/vm/unprivileged_userfaultfd a la valeur 0.

NORMES

Linux.

HISTORIQUE

Linux 4.3.

La prise en charge des zones hugetlbfs et de mémoire partagée, ainsi que des événements autres que les fautes de page, a été ajoutée dans Linux 4.11.

NOTES

Le mécanisme userfaultfd peut être utilisé comme alternative aux techniques de pagination traditionnelles en espace utilisateur basées sur l'utilisation du signal SIGSEGV et de mmap(2). Il peut également être utilisé pour implémenter la restauration différée pour les mécanismes de point de contrôle/restauration, ainsi que la migration post-copie pour autoriser une exécution (presque) ininterrompue lors du transfert de machines virtuelles et de conteneurs Linux d'un hôte à un autre.

BOGUES

Si UFFD_FEATURE_EVENT_FORK est activé et qu'un appel système de la famille fork(2) est interrompu par un signal ou échoue, un descripteur userfaultfd obsolète peut être créé. Dans ce cas, un UFFD_EVENT_FORK supplémentaire sera délivré au moniteur userfaultfd.

EXEMPLES

Le programme ci-dessous démontre l'utilisation du mécanisme userfaultfd. Le programme crée deux threads, dont l'un agit comme gestionnaire de fautes de page pour le processus, pour les pages d'une région zéro à demande créée à l'aide de mmap(2).

Le programme prend un argument de ligne de commande, qui est le nombre de pages qui seront créées dans un mappage dont les fautes de page seront gérées via userfaultfd. Après la création d'un objet userfaultfd, le programme crée ensuite un mappage privé anonyme de la taille spécifiée et enregistre la plage d'adresses de ce mappage à l'aide de l'opération ioctl(2) UFFDIO_REGISTER. Le programme crée ensuite un deuxième thread qui se chargera de gérer les fautes de page.

Le thread principal parcourt ensuite les pages du mappage en lisant des octets des pages successives. Étant donné que les pages n'ont pas encore été accédées, le premier accès à un octet de chaque page déclenchera un événement de faute de page sur le descripteur de fichier userfaultfd.

Chacun des événements de faute de page est géré par le deuxième thread, qui se trouve dans une boucle traitant les entrées du descripteur de fichier userfaultfd. À chaque itération de la boucle, le deuxième thread appelle d'abord poll(2) pour vérifier l'état du descripteur de fichier, puis lit un événement du descripteur de fichier. Tous ces événements devraient être des événements UFFD_EVENT_PAGEFAULT, que le thread gère en copiant une page de données dans la région fautive à l'aide de l'opération ioctl(2) UFFDIO_COPY.

#include <poll.h>
#include <pthread.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/ioctl.h>
#include <sys/mman.h>
#include <sys/syscall.h>
#include <unistd.h>
static int page_size;
static void *
fault_handler_thread(void *arg)
{
    int                 nready;
    long                uffd;   /* descripteur de fichier userfaultfd */
    ssize_t             nread;
    struct pollfd       pollfd;
    struct uffdio_copy  uffdio_copy;
    static int      fault_cnt = 0; /* Nombre de fautes gérées jusqu'à présent */
    static char     *page = NULL;
    static struct uffd_msg  msg;  /* Données lues depuis userfaultfd */
    uffd = (long) arg;
    /* Crée une page qui sera copiée dans la région fautive.  */
    if (page == NULL) {
        page = mmap(NULL, page_size, PROT_READ | PROT_WRITE,
                    MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);
        if (page == MAP_FAILED)
            err(EXIT_FAILURE, "mmap");
    }
    /* Boucle, traitant les événements entrants sur le descripteur de fichier
       userfaultfd.  */
    for (;;) {
        /* Voir ce que poll() nous dit sur userfaultfd.  */
        pollfd.fd = uffd;
        pollfd.events = POLLIN;
        nready = poll(&pollfd, 1, -1);
        if (nready == -1)
            err(EXIT_FAILURE, "poll");
        printf("\nfault_handler_thread():\n");
        printf("    poll() retourne : nready = %d; "
               "POLLIN = %d; POLLERR = %d\n", nready,
               (pollfd.revents & POLLIN) != 0,
               (pollfd.revents & POLLERR) != 0);
        /* Lit un événement depuis userfaultfd.  */
        nread = read(uffd, &msg, sizeof(msg));
        if (nread == 0) {
            printf("EOF sur userfaultfd!\n");
            exit(EXIT_FAILURE);
        }
        if (nread == -1)
            err(EXIT_FAILURE, "read");
        /* Nous attendons un seul type d'événement ; vérifions cette hypothèse.  */
        if (msg.event != UFFD_EVENT_PAGEFAULT) {
            fprintf(stderr, "Événement inattendu sur userfaultfd\n");
            exit(EXIT_FAILURE);
        }
        /* Affiche des informations sur l'événement de faute de page.  */
        printf("    Événement UFFD_EVENT_PAGEFAULT : ");
        printf("flags = %"PRIx64"; ", msg.arg.pagefault.flags);
        printf("adresse = %"PRIx64"\n", msg.arg.pagefault.address);
        /* Copie la page pointée par 'page' dans la région fautive.
           Varie le contenu copié, de sorte qu'il soit plus évident que chaque faute est gérée séparément.  */
        memset(page, 'A' + fault_cnt % 20, page_size);
        fault_cnt++;
        uffdio_copy.src = (unsigned long) page;
        /* Nous devons gérer les fautes de page par unités de pages(!).
           Donc, arrondit l'adresse fautive vers le bas jusqu'à la limite de page.  */
        uffdio_copy.dst = (unsigned long) msg.arg.pagefault.address &
                                           ~(page_size - 1);
        uffdio_copy.len = page_size;
        uffdio_copy.mode = 0;
        uffdio_copy.copy = 0;
        if (ioctl(uffd, UFFDIO_COPY, &uffdio_copy) == -1)
            err(EXIT_FAILURE, "ioctl-UFFDIO_COPY");
        printf("        (uffdio_copy.copy a retourné %"PRId64")\n",
               uffdio_copy.copy);
    }
}
int
main(int argc, char *argv[])
{
    int        s;
    char       c;
    char       *addr;   /* Début de la région gérée par userfaultfd */
    long       uffd;    /* descripteur de fichier userfaultfd */
    size_t     size, i;  /* Taille de la région gérée par userfaultfd */
    pthread_t  thr;     /* ID du thread qui gère les fautes de page */
    struct uffdio_api       uffdio_api;
    struct uffdio_register  uffdio_register;
    if (argc != 2) {
        fprintf(stderr, "Usage: %s num-pages\n", argv[0]);
        exit(EX
IT_FAILURE);
    }
    page_size = sysconf(_SC_PAGE_SIZE);
    size = strtoull(argv[1], NULL, 0) * page_size;
    /* Créer et activer un objet userfaultfd.  */
    uffd = syscall(SYS_userfaultfd, O_CLOEXEC | O_NONBLOCK);
    if (uffd == -1)
        err(EXIT_FAILURE, "userfaultfd");
    /* REMARQUE : Une négociation de fonctionnalités en deux étapes n'est pas nécessaire ici, car cet
       exemple ne nécessite aucune fonctionnalité spécifique.
       Les programmes qui *en* ont besoin devraient appeler UFFDIO_API deux fois : une fois avec
       `features = 0` pour détecter les fonctionnalités prises en charge par ce noyau, et
       à nouveau avec le sous-ensemble de fonctionnalités que le programme souhaite réellement activer.  */
    uffdio_api.api = UFFD_API;
    uffdio_api.features = 0;
    if (ioctl(uffd, UFFDIO_API, &uffdio_api) == -1)
        err(EXIT_FAILURE, "ioctl-UFFDIO_API");
    /* Créer un mappage anonyme privé.  La mémoire sera
       paginée zéro à la demande, c'est-à-dire pas encore allouée.  Lorsque nous
       touchons réellement la mémoire, elle sera allouée via
       le userfaultfd.  */
    addr = mmap(NULL, size, PROT_READ | PROT_WRITE,
                MAP_PRIVATE | MAP_ANONYMOUS, -1, 0);
    if (addr == MAP_FAILED)
        err(EXIT_FAILURE, "mmap");
    printf("Adresse retournée par mmap() = %p\n", addr);
    /* Enregistrer la plage de mémoire du mappage que nous venons de créer pour
       la gestion par l'objet userfaultfd.  En mode, nous demandons à suivre
       les pages manquantes (c'est-à-dire les pages qui n'ont pas encore été chargées).  */
    uffdio_register.range.start = (unsigned long) addr;
    uffdio_register.range.len = size;
    uffdio_register.mode = UFFDIO_REGISTER_MODE_MISSING;
    if (ioctl(uffd, UFFDIO_REGISTER, &uffdio_register) == -1)
        err(EXIT_FAILURE, "ioctl-UFFDIO_REGISTER");
    /* Créer un thread qui traitera les événements userfaultfd.  */
    s = pthread_create(&thr, NULL, fault_handler_thread, (void *) uffd);
    if (s != 0) {
        errc(EXIT_FAILURE, s, "pthread_create");
    }
    /* Le thread principal touche maintenant la mémoire dans le mappage, en touchant
       des emplacements espacés de 1024 octets.  Cela déclenchera des événements
       userfaultfd pour toutes les pages de la région.  */
    i = 0xf;    /* S'assurer que l'adresse de défaut n'est pas sur une
                   limite de page, afin de tester que nous la gérons
                   correctement dans fault_handling_thread().  */
    while (i < size) {
        c = addr[i];
        printf("Lecture de l'adresse %p dans %s() : ", addr + i, __func__);
        printf("%c\n", c);
        i += 1024;
        usleep(100000);         /* Ralentir un peu */
    }
    exit(EXIT_SUCCESS);
}
