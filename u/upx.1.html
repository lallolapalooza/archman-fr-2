NOM

upx - compresse ou décompresse des fichiers exécutables

SYNTAXE

upx [ commande ] [ options ] nom_fichier...

ABSTRAIT

                 The Ultimate Packer for eXecutables
Copyright (c) 1996-2025 Markus Oberhumer, Laszlo Molnar & John Reiser
                        https://upx.github.io

UPX est un compresseur d'exécutables portable, extensible et haute performance pour plusieurs formats d'exécutables différents. Il obtient un excellent taux de compression et offre une décompression *très* rapide. Vos exécutables ne souffrent d'aucun surcoût en mémoire ou d'autres inconvénients pour la plupart des formats pris en charge, grâce à la décompression en place.

CLAUSE DE NON-RESPONSABILITÉ

UPX est fourni SANS AUCUNE GARANTIE ; pour plus de détails, voir le fichier COPYING.

Merci de signaler tous les problèmes ou suggestions aux auteurs.

CONTEXTE DE SÉCURITÉ

NOTE IMPORTANTE : UPX hérite du contexte de sécurité de tous les fichiers qu'il traite.

Cela signifie que compresser, décompresser, ou même tester ou lister un fichier nécessite les mêmes considérations de sécurité que d'exécuter effectivement le fichier.

Utilisez UPX uniquement sur des fichiers de confiance !

DESCRIPTION

UPX est un compresseur d'exécutables polyvalent avec les fonctionnalités suivantes :

- sécurisé : UPX est open source documenté depuis de nombreuses années, tout
    logiciel de sécurité/antivirus pertinent peut donc l'examiner pour vérifier
    les applications compressées par UPX
- excellent taux de compression : compresse généralement mieux que Zip,
    utilisez UPX pour réduire la taille de votre distribution !
- décompression très rapide : plus de 500 Mo/sec sur toute machine raisonnablement
    moderne
- aucun surcoût en mémoire pour vos exécutables compressés pour la plupart des
    formats supportés grâce à la décompression en place
- sûr : vous pouvez lister, tester et décompresser vos exécutables.
    De plus, une somme de contrôle des fichiers compressé et décompressé est maintenue
    en interne.
- universel : UPX peut compresser un certain nombre de formats d'exécutables,
    y compris les programmes et DLL Windows, les applications macOS et les exécutables
    Linux
- portable : UPX est écrit en C++ portable et indépendant de l'endianness
- extensible : grâce à la conception orientée objet, il est très facile de prendre
    en charge de nouveaux formats d'exécutables ou d'ajouter de nouveaux algorithmes de
    compression
- gratuit : UPX est distribué avec le code source complet sous la licence GNU
    GPL v2+, avec des exceptions spéciales accordant l'usage gratuit pour les programmes
    commerciaux

Vous comprenez probablement maintenant pourquoi nous appelons UPX le compresseur d'exécutables "ultime".

COMMANDES

Compresser

C'est l'opération par défaut, par exemple upx monfichier.exe compressera le fichier spécifié sur la ligne de commande.

Décompresser

Tous les formats de fichiers supportés par UPX peuvent être décompressés en utilisant l'option -d, par exemple upx -d monfichier.exe décompressera le fichier que vous venez de compresser.

Tester

La commande -t teste l'intégrité des données compressées et décompressées, par exemple upx -t monfichier.exe vérifie si votre fichier peut être décompressé en toute sécurité. Notez que cette commande ne vérifie pas tout le fichier, seulement la partie qui sera décompressée pendant l'exécution du programme. Cela signifie que vous ne devriez pas utiliser cette commande à la place d'un antivirus.

Lister

La commande -l affiche des informations sur les fichiers compressés spécifiés en paramètres sur la ligne de commande, par exemple upx -l monfichier.exe montre la taille compressée / décompressée et le ratio de compression de monfichier.exe.

OPTIONS

-q : être discret, supprimer les avertissements

-q -q (ou -qq) : être très discret, supprimer les erreurs

-q -q -q (ou -qqq) : ne produire aucune sortie

--help : affiche l'aide

--version : affiche la version de UPX

--exact : lors de la compression, exige de pouvoir obtenir un fichier octet par octet identique après décompression avec l'option -d. [NOTE : ceci est en cours de développement et n'est pas encore supporté pour tous les formats. Si cela vous importe, comme solution de contournement, vous pouvez compresser puis décompresser votre programme une première fois - toute étape de compression-décompression supplémentaire devrait alors produire des résultats octet par octet identiques par rapport à la première version décompressée.]

-k : conserver les fichiers de sauvegarde

-o fichier : écrire la sortie dans fichier

[ ...plus de documentation à écrire... - tapez `upx --help' pour l'instant ]

NIVEAUX DE COMPRESSION & RÉGLAGE

UPX offre dix niveaux de compression différents de -1 à -9, et --best. Le niveau de compression par défaut est -8 pour les fichiers de moins de 512 KiB, et -7 sinon.

  • Les niveaux de compression 1, 2 et 3 sont assez rapides.
  • Les niveaux de compression 4, 5 et 6 obtiennent une bonne performance temps/ratio.
  • Les niveaux de compression 7, 8 et 9 privilégient le ratio de compression par rapport à la vitesse.
  • Le niveau de compression --best peut prendre beaucoup de temps.

Notez que le niveau de compression --best peut être un peu lent pour les gros fichiers, mais vous devriez absolument l'utiliser lors de la publication d'une version finale de votre programme.

Informations rapides pour obtenir le meilleur ratio de compression :

  • Essayez upx --brute --no-lzma monfichier.exe ou même upx --ultra-brute --no-lzma monfichier.exe.
  • L'option --lzma active la compression LZMA, qui compresse mieux mais est *significativement plus lente* à la décompression. Vous ne voudrez probablement pas l'utiliser pour les gros fichiers.

    (Notez que --lzma est automatiquement activé par --all-methods et --brute, utilisez --no-lzma pour annuler.)

  • Essayez si --overlay=strip fonctionne.
  • Pour les programmes win32/pe, il y a --strip-relocs=0. Voir les notes ci-dessous.

OPTIONS DE GESTION DES SUPERPOSITIONS

Info : Une "superposition" (overlay) signifie des données auxiliaires ajoutées après la fin logique d'un exécutable, et elle contient souvent des données spécifiques à l'application (c'est une pratique courante pour éviter un fichier de données supplémentaire, bien qu'il serait préférable d'utiliser des sections de ressources).

UPX gère les superpositions comme de nombreux autres compresseurs d'exécutables : il copie simplement la superposition après l'image compressée. Cela fonctionne avec certains fichiers, mais pas avec d'autres, en fonction de la manière dont une application accède réellement à ces données superposées.

--overlay=copy    Copie toute donnée supplémentaire attachée au fichier. [PAR DÉFAUT]
--overlay=strip   Supprime toute superposition du programme au lieu de la
                  copier. Attention, cela peut rendre le programme compressé
                  instable ou inutilisable.
--overlay=skip    Refuse de compresser tout programme ayant une superposition.

VARIABLE D'ENVIRONNEMENT

La variable d'environnement UPX peut contenir un ensemble d'options par défaut pour UPX. Ces options sont interprétées en premier et peuvent être écrasées par des paramètres explicites en ligne de commande. Par exemple :

pour DOS/Windows :   set UPX=-9 --compress-icons#0
pour sh/ksh/zsh :    UPX="-9 --compress-icons=0"; export UPX
pour csh/tcsh :      setenv UPX "-9 --compress-icons=0"

Sous DOS/Windows, vous devez utiliser '#' au lieu de '=' lors de la définition de la variable d'environnement en raison d'une limitation de COMMAND.COM.

Toutes les options ne sont pas valides dans la variable d'environnement - UPX vous en informera.

Vous pouvez explicitement utiliser l'option --no-env pour ignorer la variable d'environnement.

NOTES POUR LINUX [général]

Introduction

Le support Linux/386 dans UPX se compose de 3 formats exécutables différents,
un optimisé pour les exécutables ELF ("linux/elf386"), un optimisé
pour les scripts shell ("linux/sh386"), et un format générique
("linux/386").
Nous commencerons par une discussion générale, mais veuillez également
lire la documentation pertinente pour chacun des formats individuels.
De plus, il existe un support spécial pour les noyaux bootables - voir la
description du format vmlinuz/386.

Vue d'ensemble pour l'utilisateur général

L'exécution d'un programme exécutable compressé échange moins d'espace sur un
support de stockage "permanent" (tel qu'un disque dur, une disquette,
un CD-ROM, une mémoire flash, une EPROM, etc.) contre plus d'espace dans un ou
plusieurs supports de stockage "temporaires" (tels que la RAM, l'espace d'échange,
/tmp, etc.).
L'exécution d'un exécutable compressé nécessite également des cycles CPU
supplémentaires pour générer l'exécutable compressé en premier lieu,
et pour le décompresser à chaque invocation.
Quelle quantité d'espace est échangée ? Cela dépend de l'exécutable, mais de
nombreux programmes économisent 30 % à 50 % de l'espace disque permanent.
Quel est le surcoût CPU ? Encore une fois, cela dépend de l'exécutable, mais la
vitesse de décompression est généralement d'au moins plusieurs mégaoctets par
seconde, et est souvent limitée par la vitesse de l'E/S disque ou réseau sous-jacente.
En fonction des statistiques d'utilisation et d'accès, et des vitesses relatives du
CPU, de la RAM, de l'espace d'échange, de /tmp et du stockage du système de fichiers,
l'invocation et l'exécution d'un exécutable compressé peuvent être plus rapides
que l'exécution directe du programme non compressé correspondant.
Le système d'exploitation pourrait effectuer moins d'opérations d'E/S coûteuses
pour invoquer le programme compressé. La pagination vers ou depuis l'espace
d'échange ou /tmp pourrait être plus rapide que la pagination depuis le
système de fichiers général.
Les programmes de "taille moyenne" qui accèdent à environ 1/3 à 1/2 de leurs
octets de programme stockés peuvent bien bénéficier de la compression.
Les petits programmes n'en bénéficient généralement pas autant car l'économie
absolue est moindre. Les gros programmes n'en bénéficient généralement pas
proportionnellement car chaque invocation peut utiliser seulement une petite
fraction du programme, pourtant UPX décompresse l'intégralité du programme avant
de l'invoquer.
Mais dans les environnements où le stockage disque ou mémoire flash est limité,
la compression peut gagner de toute façon.
Actuellement, les exécutables compressés par UPX ne partagent pas la RAM à
l'exécution de la manière dont les exécutables mappés à partir d'un système de
fichiers le font. Par conséquent, si le même programme est exécuté simultanément
par plus d'un processus, l'utilisation de la version compressée nécessitera plus
de RAM et/ou d'espace d'échange. Ainsi, les programmes shell (bash, csh, etc.)
et "make" pourraient ne pas être de bons candidats à la compression.
UPX reconnaît trois formats exécutables pour Linux : Linux/elf386,
Linux/sh386 et Linux/386. Linux/386 est le format le plus générique ;
il prend en charge tout fichier exécutable. À l'exécution, le stub de décompression UPX
recrée dans /tmp une copie du fichier original, puis la copie est (re)exécutée
avec les mêmes arguments.
Les exécutables binaires ELF préfèrent le format Linux/elf386 par défaut,
car UPX les décompresse directement en RAM, n'utilise qu'un seul appel système
exec, n'utilise pas d'espace dans /tmp, et n'utilise pas /proc.
Les scripts shell où le shell sous-jacent accepte un argument "-c"
peuvent utiliser le format Linux/sh386. UPX décompresse le script shell
en basse mémoire, puis mappe le shell et passe l'intégralité du texte du
script comme argument avec un "-c" préfixé.

Avantages généraux :

- UPX peut compresser tous les exécutables, qu'il s'agisse de scripts AOUT, ELF, libc4, libc5,
  libc6, Shell/Perl/Python/..., de binaires Java autonomes .class, ou autre...
  Tous les scripts et programmes fonctionneront comme avant.
- Les programmes compressés sont entièrement autonomes. Aucun programme externe n'est nécessaire.
- UPX laisse votre programme original intact. Cela signifie qu'après décompression,
  vous obtiendrez une version identique octet par octet, et vous pouvez utiliser UPX
  comme un compresseur de fichiers comme gzip.
  [ Notez qu'UPX maintient une somme de contrôle du fichier en interne,
    c'est donc bien une alternative fiable. ]
- Comme le stub n'utilise que des appels système et n'est pas lié à libc, il
  devrait fonctionner sous n'importe quelle configuration Linux capable d'exécuter
  des binaires ELF.
- Pour la même raison, les exécutables compressés devraient fonctionner sous
  FreeBSD et d'autres systèmes capables d'exécuter des binaires Linux.
  [ Veuillez envoyer vos commentaires à ce sujet ]

Inconvénients généraux :

- Il n'est pas conseillé de compresser des programmes qui ont généralement de nombreuses
  instances en cours d'exécution (comme `sh' ou `make') car les segments communs
  des programmes compressés ne seront plus partagés entre les différents processus.
- `ldd' et `size' ne montreront rien d'utile car tout ce qu'ils voient est le stub
  statiquement lié. Depuis la version 0.82, les en-têtes de section sont supprimés
  du stub UPX et `size' ne reconnaît même pas le format de fichier. Le fichier
  patches/patch-elfcode.h contient un correctif pour résoudre ce bug dans `size'
  et d'autres programmes qui utilisent GNU BFD.

Notes générales :

- Comme UPX laisse votre programme original intact, il est avantageux
  de le dépouiller (strip) avant la compression.
- Si vous compressez un script, vous perdrez l'indépendance de la plateforme -
  cela pourrait être un problème si vous utilisez des disques montés via NFS.
- La compression des programmes suid, guid et sticky-bit est refusée
  en raison d'éventuelles implications de sécurité.
- Pour la même raison, il n'y a aucun intérêt à rendre un programme compressé suid.
- Évidemment, UPX ne fonctionnera pas avec les exécutables qui souhaitent lire des données
  à partir d'eux-mêmes. Par exemple, cela pourrait poser un problème pour les scripts Perl
  qui accèdent à leurs lignes __DATA__.
- En cas d'erreurs internes, le stub s'arrêtera avec le code de sortie 127.
  Les raisons typiques pour lesquelles cela se produit sont que le programme a été modifié
  d'une manière ou d'une autre après co
impression. Exécuter `strace -o strace.log fichier_compressé' vous en dira plus.

NOTES POUR LINUX/ELF386

Veuillez lire d'abord la description générale de Linux.

Le format linux/elf386 se décompresse directement en RAM, n'utilise qu'un seul exécutable, n'utilise pas d'espace dans /tmp et n'utilise pas /proc.

Linux/elf386 est automatiquement sélectionné pour les exécutables ELF Linux.

Les programmes compressés seront identiques à l'original après décompression.

Comment ça marche :

Pour les exécutables ELF, UPX se décompresse directement en mémoire, simulant
le mappage que le noyau du système d'exploitation utilise lors de l'exécution,
y compris l'interpréteur de programme PT_INTERP (le cas échéant).
Le brk() est défini par un segment PT_LOAD spécial dans l'exécutable compressé
lui-même. UPX efface ensuite la pile à l'exception des arguments, des variables
d'environnement et des entrées Elf_auxv (ceci est requis par des bugs dans le
code de démarrage de /lib/ld-linux.so en mai 2000), et transfère le contrôle à
l'interpréteur de programme ou à l'adresse e_entry de l'exécutable d'origine.
Le stub UPX fait environ 1700 octets, écrit en partie en assembleur et n'utilise
que des appels système du noyau. Il n'est lié à aucune libc.

Inconvénients spécifiques :

- Pour les formats linux/elf386 et linux/sh386, vous dépendrez de la RAM
  et de l'espace d'échange pour contenir tout le programme décompressé pendant
  la durée de vie du processus. Si vous utilisez déjà la majeure partie de votre
  espace d'échange, vous pourriez en manquer. Un système qui est "à court de
  mémoire" peut devenir fragile. De nombreux programmes ne réagissent pas
  gracieusement lorsque malloc() renvoie 0. Avec les noyaux Linux plus récents,
  le noyau peut décider de tuer certains processus pour récupérer de la mémoire,
  et vous pourriez ne pas aimer le choix du noyau quant à celui à tuer. Exécuter
  /usr/bin/top est un moyen de vérifier l'utilisation de l'espace d'échange.

Options supplémentaires disponibles pour ce format d'exécutable :

(aucune)

NOTES POUR LINUX/SH386

Veuillez lire d'abord la description générale de Linux.

Les scripts shell où le shell sous-jacent accepte un argument « -c » peuvent utiliser le format Linux/sh386. UPX décompresse le script shell dans la mémoire basse, puis mappe le shell et passe l'intégralité du texte du script comme argument avec un « -c » en préfixe. Il n'utilise pas d'espace dans /tmp et n'utilise pas /proc.

Linux/sh386 est automatiquement sélectionné pour les scripts shell qui utilisent un shell connu.

Les programmes compressés seront identiques à l'original après décompression.

Comment ça marche :

Pour les exécutables de scripts shell (fichiers commençant par "#!/" ou "#! /")
où le shell accepte l'argument "-c <commande>", UPX décompresse
le fichier en mémoire basse, puis mappe le shell (et son PT_INTERP),
et transfère le contrôle au shell avec le fichier décompressé entier
comme argument après "-c". Les shells connus sont sh, ash, bash, bsh, csh,
ksh, tcsh, pdksh. Restriction : UPX ne peut pas utiliser cette méthode
pour les scripts shell qui utilisent l'argument chaîne optionnel unique après
le nom du shell dans le script (exemple : "#! /bin/sh option3\n".).
Le stub UPX fait environ 1700 octets, écrit en partie en assembleur
et n'utilise que des appels système du noyau. Il n'est lié à aucune libc.

Inconvénients spécifiques :

- Pour les formats linux/elf386 et linux/sh386, vous dépendrez de la RAM
  et de l'espace d'échange pour contenir tout le programme décompressé pendant
  la durée de vie du processus. Si vous utilisez déjà la majeure partie de votre
  espace d'échange, vous pourriez en manquer. Un système qui est "à court de
  mémoire" peut devenir fragile. De nombreux programmes ne réagissent pas

  le noyau peut décider de tuer certains processus pour récupérer de la mémoire,

NOTES POUR LINUX/386

Veuillez lire d'abord la description générale de Linux.

Le format générique linux/386 se décompresse dans /tmp et nécessite le support du système de fichiers /proc. Il lance le programme décompressé via l'appel système execve().

Linux/386 n'est sélectionné que si les formats spécialisés linux/elf386 et linux/sh386 ne reconnaissent pas un fichier.

Les programmes compressés seront identiques à l'original après décompression.

Comment ça marche :

Pour les fichiers qui ne sont ni ELF ni un script pour un shell connu acceptant "-c",
UPX utilise l'appel système kernel execve(), qui nécessite d'abord de décompresser
vers un fichier temporaire dans le système de fichiers. Fait intéressant -
en raison de la bonne gestion de la mémoire du noyau Linux - cela n'introduit souvent
pas de délai notable, et en fait, il n'y aura aucun accès disque si vous avez
assez de mémoire libre, car tout le processus se déroule dans les tampons du
système de fichiers.
Un exécutable compressé se compose du stub UPX et d'une superposition qui contient
le programme d'origine sous forme compressée.
Le stub UPX est un exécutable ELF lié statiquement et fait ce qui suit au démarrage du programme :
  1) décompresser la superposition vers un emplacement temporaire dans /tmp
  2) ouvrir le fichier temporaire en lecture
  3) essayer de supprimer le fichier temporaire et de lancer (execve)
     le programme décompressé dans /tmp en utilisant /proc/<pid>/fd/X comme
     obtenu à l'étape 2)
  4) si cela échoue, créer un sous-processus pour nettoyer et
     lancer le programme dans /tmp entre-temps
Le stub UPX fait environ 1700 octets, écrit en partie en assembleur
et n'utilise que des appels système du noyau. Il n'est lié à aucune libc.

Inconvénients spécifiques :

- Vous avez besoin d'espace disque libre supplémentaire pour le programme décompressé
  dans votre répertoire /tmp. Ce programme est supprimé immédiatement après la
  décompression, mais vous en avez toujours besoin pendant toute la durée
  d'exécution du programme.
- Vous devez avoir le support du système de fichiers /proc car le stub souhaite ouvrir
  /proc/<pid>/exe et a besoin de /proc/<pid>/fd/X. Cela signifie également que vous
  ne pouvez pas compresser les programmes utilisés pendant la séquence de démarrage
  avant que /proc ne soit monté.
- Les utilitaires comme `top' afficheront des valeurs numériques dans le champ
  du nom du processus. C'est parce que Linux calcule le nom du processus à partir
  du premier argument du dernier appel système execve (qui est généralement quelque chose
  comme /proc/<pid>/fd/3).
- En raison de la décompression temporaire sur disque, la vitesse de décompression
  n'est pas aussi rapide qu'avec les autres formats exécutables. Pourtant, je ne vois
  aucun délai notable lors du lancement de programmes comme mon emacs de ~3 Mio
  (qui fait moins de 1 Mio compressé :-)).

Options supplémentaires disponibles pour ce format d'exécutable :

--force-execve      Force l'utilisation du format générique linux/386 "execve",
                    c'est-à-dire ne pas essayer les formats linux/elf386 et
                    linux/sh386.

NOTES POUR PS1/EXE

C'est le format exécutable utilisé par la Sony PlayStation (PSone), une console de jeu basée sur MIPS R3000 populaire depuis la fin des années 90. Le support de ce format est très similaire à celui d'Atari, en raison de sentiments nostalgiques d'un des auteurs.

Les programmes compressés seront identiques à l'original après décompression, jusqu'à nouvel ordre.

Taille maximale décompressée : ~1,89 / ~7,60 Mio.

Notes :

- UPX crée par défaut un exécutable adapté pour le CD-Mastering
  et le transfert sur console. Pour un exécutable principal de CD-Master, vous pouvez également essayer
  l'option spéciale "--boot-only" comme décrit ci-dessous.
  Il a été rapporté que les exécutables compressés par upx sont entièrement compatibles avec
  les Sony PlayStation 2 (PS2, PStwo) et Sony PlayStation Portable (PSP) en mode
  émulation Sony PlayStation (PSone).
- Normalement, les fichiers compressés utilisent les mêmes zones mémoire que les
  versions décompressées, ils ne remplaceront donc pas d'autres zones mémoire lors du déballage.
  Si cela n'est pas possible, UPX s'arrêtera en affichant une erreur 'packed data overlap'.
  Avec l'option "--force", UPX relocalisera l'adresse de chargement
  du fichier compressé, mais ce n'est pas un réel problème s'il s'agit d'un exécutable unique ou
  principal.

Options supplémentaires disponibles pour ce format d'exécutable :

--all-methods       Comprime le programme plusieurs fois, en utilisant toutes
                    les méthodes de compression disponibles. Cela peut améliorer
                    le ratio de compression dans certains cas, mais généralement
                    la méthode par défaut donne de toute façon les meilleurs résultats.
--8-bit             Utilise une compression de taille 8 bits [défaut : 32 bits]
--8mib-ram          PSone dispose de 8 Mio de RAM [défaut : 2 Mio]
--boot-only         Ce format est uniquement destiné aux exécutables principaux et au CD-Mastering !
                    Il peut légèrement améliorer le ratio de compression,
                    les routines de décompression sont plus rapides que celles par défaut.
                    Mais il ne peut pas être utilisé pour le transfert sur console !
--no-align          Cette option désactive l'alignement des secteurs de données du mode CD 2.
                    Peut légèrement améliorer le ratio de compression,
                    mais l'exécutable compressé ne démarrera pas à partir d'un CD.
                    Utilisez-le uniquement pour le transfert sur console !

NOTES POUR VMLINUZ/386

Les formats vmlinuz/386 et bvmlinuz/386 prennent une image de noyau Linux bootable compressée par gzip (« vmlinuz », « zImage », « bzImage »), la décompressent avec gzip et la recompressent avec la méthode de compression UPX.

vmlinuz/386 n'est absolument pas lié aux autres formats d'exécutables Linux, et il ne partage aucun de leurs inconvénients.

Notes :

- Assurez-vous que "vmlinuz/386" ou "bvmlinuz/386" est affiché
pendant la compression - sinon un mauvais format exécutable
a pu être utilisé, et le noyau ne démarrera pas.

Avantages :

- Meilleure compression (mais notez que le noyau était déjà compressé,
donc l'amélioration n'est pas aussi grande qu'avec d'autres formats).
Néanmoins, les octets économisés peuvent être essentiels pour des besoins spéciaux li
ke disques de démarrage. Par exemple, voici ce que j'obtiens pour mon noyau 2.2.16 : 1589708 vmlinux 641073 bzImage [original] 560755 bzImage.upx [compressé par "upx -9"] - Décompression beaucoup plus rapide au démarrage du noyau (mais la vitesse de décompression du noyau n'est plus vraiment un problème de nos jours).

Inconvénients :

(aucun)

--all-methods       Compresse le programme plusieurs fois, en utilisant toutes

                    le rapport de compression dans certains cas, mais généralement

--all-filters       Compresse le programme plusieurs fois, en utilisant tous les

                    le rapport de compression dans certains cas, mais généralement

NOTES POUR WIN32/PE

Le support PE dans UPX est maintenant assez stable, mais il y a probablement encore quelques incompatibilités avec certains fichiers.

En raison de la façon dont UPX (et d'autres packers pour ce format) fonctionne, vous pouvez constater une augmentation de l'utilisation de la mémoire de vos fichiers compressés car tout le programme est chargé en mémoire au démarrage. Si vous démarrez plusieurs instances de gros programmes compressés, vous gaspillez de la mémoire car les segments communs du programme ne seront pas partagés entre les instances. D'un autre côté, si vous ne compressez que des programmes plus petits, ou si vous n'exécutez qu'une seule instance de programmes plus grands, alors cette pénalité est plus faible, mais elle est toujours là.

Si vous exécutez des exécutables à partir du réseau, les programmes compressés se chargeront plus rapidement et nécessiteront moins de bande passante pendant l'exécution.

Les DLL sont prises en charge. Mais les DLL compressées par UPX ne peuvent pas partager de données et de code communs lorsqu'elles sont utilisées par plusieurs applications. Compresser msvcrt.dll est donc un gaspillage de mémoire, mais compresser les plugins DLL d'une application particulière peut être une meilleure idée.

Les économiseurs d'écran sont pris en charge, avec la restriction que le nom du fichier doit se terminer par ".scr" (car les économiseurs d'écran sont traités légèrement différemment des fichiers exe normaux).

Les fichiers PE compressés par UPX ont un léger surcoût mémoire (généralement de l'ordre de 10 à 30 KiB) qui peut être observé en spécifiant le commutateur de ligne de commande "-i" lors de la compression.

--compress-exports=1 Compresser la section d'exportation. [PAR DÉFAUT]
                     La compression de la section d'exportation peut améliorer
                     considérablement le rapport de compression, mais peut ne pas
                     fonctionner avec tous les programmes (comme winword.exe).
                     UPX ne compresse jamais la section d'exportation d'une DLL
                     quelle que soit cette option.
 --compress-icons=0  Ne pas compresser les icônes.
 --compress-icons=1  Compresser toutes les icônes sauf la première.
 --compress-icons=2  Compresser toutes les icônes qui ne sont pas dans le
                     premier répertoire d'icônes. [PAR DÉFAUT]
 --compress-icons=3  Compresser toutes les icônes.
 --compress-resources=0  Ne pas compresser du tout les ressources.
 --keep-resource=liste Ne pas compresser les ressources spécifiées par la liste.
                     Les membres de la liste sont séparés par des virgules.
                     Un membre de la liste a le format suivant : I<type[/nom]>.
                     I<Type> est le type de la ressource. Les types standards
                     doivent être spécifiés sous forme de nombres décimaux, les
                     types utilisateur peuvent être spécifiés par des identifiants
                     décimaux ou des chaînes. I<Nom> est l'identifiant de la
                     ressource. Il peut s'agir d'un nombre décimal ou d'une chaîne.
                     Par exemple :
                     --keep-resource=2/MYBITMAP,5,6/12345
                     UPX ne compressera pas la ressource bitmap nommée "MYBITMAP",
                     il laissera toutes les ressources de dialogue (5) non compressées,
                     et il ne touchera pas la table de chaînes avec l'identifiant
                     12345.
 --force             Forcer la compression même lorsqu'il y a une

 --strip-relocs=0    Ne pas supprimer les enregistrements de relocalisation.
 --strip-relocs=1    Supprimer les enregistrements de relocalisation. [PAR DÉFAUT]
                     Cette option ne fonctionne que sur les exécutables dont l'adresse
                     de base est supérieure ou égale à 0x400000. Généralement, les
                     fichiers compressés deviennent plus petits, mais certains fichiers
                     peuvent devenir plus grands. Notez que le fichier résultant ne
                     fonctionnera pas sous Windows 3.x (Win32s).
                     UPX ne supprime jamais les relocalisations d'une DLL
                     quelle que soit cette option.
 --all-methods       Compresse le programme plusieurs fois, en utilisant toutes
                     les méthodes de compression disponibles. Cela peut améliorer
                     le rapport de compression dans certains cas, mais généralement
                     la méthode par défaut donne les meilleurs résultats de toute façon.
 --all-filters       Compresse le programme plusieurs fois, en utilisant tous les
