SYSTEMD-SYSTEM.CONF(5) systemd-system.conf SYSTEMD-SYSTEM.CONF(5)

NOM

systemd-system.conf, system.conf.d, systemd-user.conf, user.conf.d - Fichiers de configuration du gestionnaire de services système et de session

SYNTAXE

/etc/systemd/system.conf, /run/systemd/system.conf, /usr/lib/systemd/system.conf, /etc/systemd/system.conf.d/*.conf, /run/systemd/system.conf.d/*.conf, /usr/lib/systemd/system.conf.d/*.conf

~/.config/systemd/user.conf, /etc/systemd/user.conf, /run/systemd/user.conf, /usr/lib/systemd/user.conf, /etc/systemd/user.conf.d/*.conf, /run/systemd/user.conf.d/*.conf, /usr/lib/systemd/user.conf.d/*.conf

DESCRIPTION

Lorsqu'il est exécuté en tant qu'instance système, systemd interprète le fichier de configuration system.conf et les fichiers des répertoires system.conf.d ; lorsqu'il est exécuté en tant qu'instance utilisateur, il interprète le fichier de configuration user.conf (dans l'ordre de priorité, dans le répertoire personnel de l'utilisateur et sous /etc/systemd/, /run/systemd/, et /usr/lib/systemd/) et les fichiers des répertoires user.conf.d. Ces fichiers de configuration contiennent quelques paramètres contrôlant les opérations de base du gestionnaire.

Voir systemd.syntax(7) pour une description générale de la syntaxe.

DIRECTORIES DE CONFIGURATION ET PRÉCÉDENCE

La configuration par défaut est définie lors de la compilation, donc la configuration n'est nécessaire que lorsqu'il est nécessaire de s'écarter de ces valeurs par défaut. Le fichier de configuration principal est chargé depuis l'un des répertoires listés par ordre de priorité, seul le premier fichier trouvé est utilisé : /etc/systemd/, /run/systemd/, /usr/local/lib/systemd/ [1], /usr/lib/systemd/. La version du fournisseur du fichier contient des entrées commentées montrant les valeurs par défaut comme guide pour l'administrateur. Des substitutions locales peuvent également être créées en créant des fichiers drop-in, comme décrit ci-dessous. Le fichier de configuration principal peut également être modifié à cette fin (ou une copie dans /etc/ s'il est livré sous /usr/), cependant, l'utilisation de fichiers drop-in pour la configuration locale est recommandée plutôt que les modifications du fichier de configuration principal.

En plus du fichier de configuration principal, des fragments de configuration drop-in sont lus depuis /usr/lib/systemd/*.conf.d/, /usr/local/lib/systemd/*.conf.d/, et /etc/systemd/*.conf.d/. Ces drop-ins ont une priorité plus élevée et remplacent le fichier de configuration principal. Les fichiers dans les sous-répertoires de configuration *.conf.d/ sont triés par leur nom de fichier dans l'ordre lexicographique, indépendamment des sous-répertoires dans lesquels ils résident. Lorsque plusieurs fichiers spécifient la même option, pour les options qui acceptent une seule valeur, l'entrée dans le fichier trié en dernier prend la priorité, et pour les options qui acceptent une liste de valeurs, les entrées sont collectées au fur et à mesure qu'elles apparaissent dans les fichiers triés.

Lorsque les paquets ont besoin de personnaliser la configuration, ils peuvent installer des drop-ins sous /usr/. Les fichiers dans /etc/ sont réservés à l'administrateur local, qui peut utiliser cette logique pour remplacer les fichiers de configuration installés par les paquets du fournisseur. Les drop-ins doivent être utilisés pour remplacer les drop-ins des paquets, car le fichier de configuration principal a une priorité plus faible. Il est recommandé de préfixer tous les noms de fichiers dans ces sous-répertoires avec un numéro à deux chiffres et un tiret, pour simplifier l'ordre. Cela définit également un concept de priorités de drop-in pour permettre aux fournisseurs de systèmes d'exploitation de livrer des drop-ins dans une plage spécifique inférieure à la plage utilisée par les utilisateurs. Cela devrait réduire le risque que les drop-ins de paquets remplacent accidentellement des drop-ins définis par les utilisateurs. Il est recommandé d'utiliser la plage 10-40 pour les drop-ins dans /usr/ et la plage 60-90 pour les drop-ins dans /etc/ et /run/, pour s'assurer que les drop-ins locaux et transitoires ont la priorité sur les drop-ins fournis par le fournisseur du système d'exploitation.

Pour désactiver un fichier de configuration fourni par le fournisseur, la méthode recommandée consiste à placer un lien symbolique vers /dev/null dans le répertoire de configuration dans /etc/, avec le même nom de fichier que le fichier de configuration du fournisseur.

OPTIONS

Toutes les options sont configurées dans la section [Manager] :

LogColor=, LogLevel=, LogLocation=, LogTarget=, LogTime=, DumpCore=yes, CrashChangeVT=no, CrashShell=no, CrashAction=freeze, ShowStatus=yes, DefaultStandardOutput=journal, DefaultStandardError=inherit

Configure divers paramètres des opérations de base du gestionnaire. Ces options peuvent être remplacées par les arguments respectifs du processus et de la ligne de commande du noyau. Voir systemd(1) pour plus de détails.

Ajouté dans la version 198.

CtrlAltDelBurstAction=

Définit l'action qui sera effectuée si l'utilisateur appuie sur Ctrl-Alt-Suppression plus de 7 fois en 2 secondes. Peut être défini sur "reboot-force", "poweroff-force", "reboot-immediate", "poweroff-immediate" ou désactivé avec "none". Par défaut "reboot-force".

Ajouté dans la version 232.

StatusUnitFormat=

Prend name, description ou combined comme valeur. Si name, le gestionnaire système utilisera les noms d'unités dans les messages d'état (par exemple, "systemd-journald.service"), au lieu des descriptions plus longues et plus informatives définies avec Description= (par exemple, "Journal Logging Service"). Si combined, le gestionnaire système utilisera à la fois les noms d'unités et les descriptions dans les messages d'état (par exemple, "systemd-journald.service - Journal Logging Service").

Voir systemd.unit(5) pour plus de détails sur les noms d'unités et Description=.

Ajouté dans la version 243.

DefaultTimerAccuracySec=

Définit la précision par défaut des unités de timer. Cela contrôle la valeur par défaut globale du paramètre AccuracySec= des unités de timer, voir systemd.timer(5) pour plus de détails. AccuracySec= défini dans les unités individuelles remplace la valeur par défaut globale pour l'unité spécifique. Par défaut 1 min. Notez que la précision des unités de timer est également affectée par le délai d'attente (slack) configuré pour PID 1, voir TimerSlackNSec= ci-dessus.

Ajouté dans la version 212.

GESTION DES RESSOURCES

TimerSlackNSec=

Définit le délai d'attente (slack) du timer en nanosecondes pour PID 1, qui est hérité par tous les processus exécutés, sauf indication contraire individuelle, par exemple avec le paramètre TimerSlackNSec= dans les unités de service (pour plus de détails voir systemd.exec(5)). Le délai d'attente du timer contrôle la précision des réveils déclenchés par les timers système. Voir prctl(2) pour plus d'informations. Notez que, contrairement à la plupart des autres définitions de périodes de temps, ce paramètre prend une valeur entière en nanosecondes si aucune unité n'est spécifiée. Les unités de temps habituelles sont également comprises.

Ajouté dans la version 198.

CPUAffinity=

Configure l'affinité CPU pour le gestionnaire de services ainsi que l'affinité CPU par défaut pour tous les processus démarrés. Prend une liste d'indices de CPU ou de plages séparées par des espaces blancs ou des virgules. Les plages de CPU sont spécifiées par les indices CPU inférieur et supérieur séparés par un tiret. Cette option peut être spécifiée plusieurs fois, auquel cas les masques d'affinité CPU spécifiés sont fusionnés. Si la chaîne vide est attribuée, le masque est réinitialisé, toutes les attributions précédentes n'auront aucun effet. Les services individuels peuvent remplacer l'affinité CPU pour leurs processus avec le paramètre CPUAffinity= dans les fichiers d'unité, voir systemd.exec(5).

Ajouté dans la version 198.

NUMAPolicy=

Configure la politique mémoire NUMA pour le gestionnaire de services et la politique mémoire NUMA par défaut pour tous les processus démarrés. Les services individuels peuvent remplacer la politique par défaut avec le paramètre NUMAPolicy= dans les fichiers d'unité, voir systemd.exec(5).

Ajouté dans la version 243.

NUMAMask=

Configure le masque de nœud NUMA qui sera associé à la politique NUMA sélectionnée. Notez que les politiques NUMA default et local ne nécessitent pas de masque de nœud NUMA explicite et la valeur de l'option peut être vide. De même que pour NUMAPolicy=, la valeur peut être remplacée par des services individuels dans les fichiers d'unité, voir systemd.exec(5).

Ajouté dans la version 243.

DefaultMemoryAccounting=, DefaultTasksAccounting=, DefaultIOAccounting=, DefaultIPAccounting=

Configure les paramètres de comptabilité des ressources par défaut, tels que configurés par unité avec Me

moryAccounting=, TasksAccounting=, IOAccounting= et IPAccounting=. Voir systemd.resource-control(5) pour les détails sur les paramètres par unité.

DefaultMemoryAccounting= vaut par défaut « yes ». DefaultTasksAccounting= vaut par défaut « yes ». Les autres paramètres valent par défaut « no ».

Ajouté dans la version 211.

DefaultTasksMax=

Configure la valeur par défaut du paramètre par unité TasksMax=. Voir systemd.resource-control(5) pour les détails. Ce paramètre s'applique à tous les types d'unités qui prennent en charge les paramètres de contrôle des ressources, à l'exception des unités de type « slice ». Par défaut, il vaut 15 % du minimum entre kernel.pid_max=, kernel.threads-max= et pids.max du cgroup racine. Le noyau a une valeur par défaut pour kernel.pid_max= et un algorithme de comptage dans le cas de plus de 32 cœurs. Par exemple, avec le kernel.pid_max= par défaut, DefaultTasksMax= vaut par défaut 4915, mais peut être supérieur sur d'autres systèmes ou inférieur dans les conteneurs OS.

Ajouté dans la version 228.

DefaultLimitCPU=, DefaultLimitFSIZE=, DefaultLimitDATA=, DefaultLimitSTACK=, DefaultLimitCORE=, DefaultLimitRSS=, DefaultLimitNOFILE=, DefaultLimitAS=, DefaultLimitNPROC=, DefaultLimitMEMLOCK=, DefaultLimitLOCKS=, DefaultLimitSIGPENDING=, DefaultLimitMSGQUEUE=, DefaultLimitNICE=, DefaultLimitRTPRIO=, DefaultLimitRTTIME=

Ces paramètres contrôlent diverses limites de ressources par défaut pour les processus exécutés par les unités. Voir setrlimit(2) pour les détails. Ces paramètres peuvent être remplacés dans des unités individuelles à l'aide des directives LimitXXX= correspondantes et ils acceptent la même syntaxe de paramètre, voir systemd.exec(5) pour les détails. Notez que ces limites de ressources ne sont que des valeurs par défaut pour les unités, elles ne s'appliquent pas au processus du gestionnaire de services (c'est-à-dire PID 1) lui-même.

La plupart de ces paramètres ne sont pas définis, ce qui signifie que les limites de ressources sont héritées du noyau ou, si invocés dans un conteneur, du gestionnaire de conteneur. Cependant, les suivants ont des valeurs par défaut :

•DefaultLimitNOFILE= vaut par défaut 1024:524288.
•DefaultLimitMEMLOCK= vaut par défaut 8M.
•DefaultLimitCORE= n'a pas de valeur par défaut, mais il est utile de mentionner que RLIMIT_CORE est défini sur « infinity » par PID 1, ce qui est hérité par ses enfants.

Notez que le gestionnaire de services, en interne dans PID 1, augmente RLIMIT_NOFILE et RLIMIT_MEMLOCK à des valeurs plus élevées, cependant la limite est rétablie aux valeurs par défaut mentionnées pour tous les processus enfants issus d'un fork.

Ajouté dans la version 198.

DefaultOOMPolicy=

Configure la politique par défaut pour réagir aux processus étant tués par le tueur Out-Of-Memory (OOM) de Linux ou par systemd-oomd. Ceci peut être utilisé pour choisir une valeur par défaut globale pour le paramètre par unité OOMPolicy=. Voir systemd.service(5) pour les détails. Notez que cette valeur par défaut n'est pas utilisée pour les services pour lesquels Delegate= est activé.

Ajouté dans la version 243.

DefaultOOMScoreAdjust=

Configure les ajustements de score OOM par défaut des processus exécutés par le gestionnaire de services. Ceci vaut par défaut « unset » (ce qui signifie que les processus issus d'un fork héritent de la valeur d'ajustement du score OOM du gestionnaire de services), sauf si le gestionnaire de services est exécuté pour un utilisateur non privilégié, auquel cas il vaut par défaut la valeur d'ajustement OOM du gestionnaire de services plus 100 (ce qui rend les processus de service légèrement plus susceptibles d'être tués sous pression mémoire que le gestionnaire lui-même). Ceci peut être utilisé pour choisir une valeur par défaut globale pour le paramètre par unité OOMScoreAdjust=. Voir systemd.exec(5) pour les détails. Notez que ce paramètre n'a aucun effet sur la valeur d'ajustement du score OOM du processus du gestionnaire de services lui-même, il conserve la valeur d'origine définie lors de son invocation.

Ajouté dans la version 250.

DefaultMemoryPressureWatch=, DefaultMemoryPressureThresholdSec=

Configure les paramètres par défaut pour les paramètres par unité MemoryPressureWatch= et MemoryPressureThresholdSec=. Voir systemd.resource-control(5) pour les détails. Vaut par défaut « auto » et « 200ms », respectivement. Ceci définit également le seuil de surveillance de la pression mémoire pour le gestionnaire de services lui-même.

Ajouté dans la version 254.

SURVEILLANCE MATÉRIELLE

RuntimeWatchdogSec=, RebootWatchdogSec=, KExecWatchdogSec=

Configure la surveillance matérielle à l'exécution et au redémarrage. Prend une valeur de délai d'attente en secondes (ou dans d'autres unités de temps si suffixée par « ms », « min », « h », « d », « w »), ou les chaînes spéciales « off » ou « default ». Si défini sur « off » (alternativement : « 0 »), la logique de surveillance est désactivée : aucun périphérique de surveillance n'est ouvert, configuré ou contacté. Si défini sur la chaîne spéciale « default », la surveillance est ouverte et contactée à intervalles réguliers, mais le délai d'attente n'est pas modifié par rapport à la valeur par défaut. Si défini sur toute autre valeur de temps, le délai d'attente de la surveillance est configuré à la valeur spécifiée (ou une valeur proche, selon les capacités matérielles).

Si RuntimeWatchdogSec= est défini sur une valeur non nulle, le matériel de surveillance (/dev/watchdog0 ou le chemin spécifié avec WatchdogDevice= ou l'option du noyau systemd.watchdog_device=) sera programmé pour redémarrer automatiquement le système s'il n'est pas contacté dans l'intervalle de délai d'attente spécifié. Le gestionnaire de système veillera à le contacter au moins une fois dans la moitié de l'intervalle de délai d'attente spécifié. Cette fonctionnalité nécessite un périphérique de surveillance matérielle, comme c'est souvent le cas dans les systèmes embarqués et serveur. Tous les périphériques de surveillance matérielle ne permettent pas la configuration de toutes les valeurs de délai de redémarrage possibles, auquel cas la valeur de délai la plus proche disponible est choisie.

RebootWatchdogSec= peut être utilisé pour configurer la surveillance matérielle lorsque le système est invité à redémarrer. Il sert de filet de sécurité pour garantir que le redémarrage a lieu même si une tentative de redémarrage propre expire. Notez que le délai d'attente RebootWatchdogSec= s'applique uniquement à la deuxième phase du redémarrage, c'est-à-dire après que tous les services réguliers ont été terminés, et après que le processus du système et du gestionnaire de services (PID 1) a été remplacé par le binaire systemd-shutdown, voir bootup(7) pour les détails. Pendant la première phase de l'opération de redémarrage, le système et le gestionnaire de services restent en cours d'exécution et donc RuntimeWatchdogSec= est toujours honoré. Afin de définir un délai d'attente pour cette première phase de l'arrêt du système, configurez JobTimeoutSec= et JobTimeoutAction= dans la section [Unit] de l'unité shutdown.target. Par défaut, RuntimeWatchdogSec= vaut 0 (désactivé), et RebootWatchdogSec= vaut 10 minutes.

KExecWatchdogSec= peut être utilisé pour activer supplémentairement la surveillance lors de l'exécution de kexec plutôt que lors du redémarrage. Notez que si le noyau ne réinitialise pas la surveillance lors de kexec (selon le matériel et/ou le pilote spécifique), dans ce cas la surveillance pourrait ne pas être désactivée après le succès de kexec et donc le système pourrait être redémarré, à moins que RuntimeWatchdogSec= ne soit également activé en même temps. Pour cette raison, il est recommandé d'activer KExecWatchdogSec= uniquement si RuntimeWatchdogSec= est également activé.

Ces paramètres n'ont aucun effet si un périphérique de surveillance matérielle n'est pas disponible.

Ajouté dans la version 198.

RuntimeWatchdogPreSec=

Configure la valeur de pré-délai d'attente du périphérique de surveillance matérielle. Prend une valeur de délai d'attente en secondes (ou dans d'autres unités de temps similaires à RuntimeWatchdogSec=). Un pré-délai d'attente de surveillance est une notification générée par la surveillance avant que la réinitialisation de la surveillance ne puisse se produire si la surveillance n'a pas été correctement gérée. Cette notification est gérée par le noyau et peut être configurée pour déclencher une action (c'est-à-dire générer une panique du noyau) à l'aide de RuntimeWatchdogPreGovernor=. Tous les matériels ou pilotes de surveillance ne prennent pas en charge la génération d'un pré-délai d'attente et, selon l'état du système, le noyau peut être incapable d'effectuer l'action configurée avant le redémarrage de la surveillance. La surveillance sera configurée pour générer l'événement de pré-délai d'attente à la durée spécifiée par RuntimeWatchdogPreSec= avant le délai d'attente de surveillance d'exécution (défini par RuntimeWatchdogSec=). Par exemple, si nous avons RuntimeWatchdogSec=30 et RuntimeWatchdogPreSec=10, alors l'événement de pré-délai d'attente se produira si la surveillance n'a pas été contactée pendant 20 secondes (10 secondes avant que la surveillance ne se déclenche). Par défaut, RuntimeWatchdogPreSec= vaut 0 (désactivé). La valeur définie pour RuntimeWatchdogPreSec= doit être inférieure à la valeur de délai d'attente pour RuntimeWatchdogSec=. Ce paramètre n'a aucun effet si un périphérique de surveillance matérielle n'est pas disponible ou si le périphérique de surveillance matérielle ne prend pas en charge le pré-délai d'attente et sera ignoré par le noyau si le paramètre est supérieur au délai d'attente de surveillance réel.

Ajouté dans la version 251.

RuntimeWatchdogPreGovernor=

Configure l'action entreprise par le périphérique de surveillance matérielle lorsque le pré-délai d'attente expire. L'action par défaut pour l'événement de pré-délai d'attente dépend de la configuration du noyau, mais il s'agit généralement d'un message de journalisation du noyau. Pour une liste des actions valides disponibles pour un périphérique de surveillance donné, consultez le contenu du fichier /sys/class/watchdog/watchdogX/pretimeout_available_governors. Typiquement, les types de gouverneurs disponibles sont noop et panic. La disponibilité, les noms et les fonctionnalités peuvent varier en fonction du pilote de périphérique spécifique utilisé. Si le fichier sysfs pretimeout_available_governors est vide, le gouverneur peut être intégré sous forme de module noyau et pourrait nécessiter d'être chargé manuellement (par exemple, pretimeout_noop.ko), ou le périphérique de surveillance pourrait ne pas prendre en charge les pré-délais d'attente.

Ajouté dans la version 251.

WatchdogDevice=

Configure le périphérique de surveillance matérielle que les minuteurs de surveillance d'exécution et d'arrêt ouvriront et utiliseront. Vaut par défaut /dev/watchdog0. Ce paramètre n'a aucun effet si un périphérique de surveillance matérielle n'est pas disponible.

Ajouté dans la version 236.

SÉCURITÉ

CapabilityBoundingSet=

Contrôle quelles capacités sont incluses dans l'ensemble de limitation des capacités pour PID 1 et ses enfants. Voir capabilities(7) pour les détails. Prend une liste de noms de capacités séparés par des espaces blancs, telle que lue par cap_from_name(3). Les capacités listées seront incluses dans l'ensemble de limitation, toutes les autres seront supprimées. Si la liste des capacités est précédée de ~, toutes les capacités sauf celles énumérées seront incluses, l'effet de l'assignation inversé. Notez que cette option affecte également les capacités respectives dans les ensembles de capacités effectives, autorisées et héritables. L'ensemble des limites de capacités peut également être configuré individuellement pour les unités en utilisant la directive CapabilityBoundingSet= pour les unités, mais notez que les capacités supprimées pour PID 1 ne peuvent pas être récupérées dans les unités individuelles, elles sont perdues pour toujours.

Ajouté dans la version 198.

NoNewPrivileges=

Prend un argument booléen. Si vrai, garantit que PID 1 et tous ses enfants ne pourront jamais acquérir de nouveaux privilèges via execve(2) (par exemple via les bits setuid ou setgid, ou les capacités du système de fichiers). Par défaut à faux. Les distributions à usage général s'appuient couramment sur des exécutables avec des bits setuid ou setgid et ne fonctionneront donc pas correctement avec cette option activée. Les unités individuelles ne peuvent pas désactiver cette option. Voir également No New Privileges Flag[2].

Ajouté dans la version 239.

ProtectSystem=

Prend un argument booléen ou la chaîne "auto". Si défini sur vrai, remonte /usr/ en lecture seule. Si défini sur "auto" (par défaut) et exécuté dans un initrd, équivalent à vrai, sinon faux. Cela implémente un sous-ensemble restreint du paramètre du même nom par unité, voir systemd.exec(5) pour les détails : actuellement, les valeurs "full" ou "strict" ne sont pas prises en charge.

Ajouté dans la version 256.

SystemCallArchitectures=

Prend une liste d'identifiants d'architecture séparés par des espaces. Sélectionne à partir de quelles architectures les appels système peuvent être invoqués sur ce système. Cela peut être utilisé comme un moyen efficace de désactiver l'invocation de binaires non natifs à l'échelle du système, par exemple pour interdire l'exécution de binaires x86 32 bits sur des systèmes x86-64 64 bits. Cette option fonctionne à l'échelle du système et agit de manière similaire au paramètre SystemCallArchitectures= des fichiers d'unité, voir systemd.exec(5) pour les détails. Ce paramètre est vide par défaut, auquel cas aucun filtrage d'appels système basé sur l'architecture n'est appliqué. Les identifiants d'architecture connus sont "x86", "x86-64", "x32", "arm" et l'identifiant spécial "native". Ce dernier correspond implicitement à l'architecture native du système (ou plus précisément, à l'architecture pour laquelle le gestionnaire système a été compilé). Définissez ce paramètre sur "native" pour interdire l'exécution de tout binaire non natif. Lorsqu'un binaire exécute un appel système d'une architecture qui n'est pas listée dans ce paramètre, il sera immédiatement terminé avec le signal SIGSYS.

Ajouté dans la version 209.

DefaultSmackProcessLabel=

Prend une étiquette de sécurité SMACK64 comme argument. Le processus exécuté par une unité sera démarré sous cette étiquette si SmackProcessLabel= n'est pas défini dans l'unité. Voir systemd.exec(5) pour les détails.

Si la valeur est "/", seules les étiquettes spécifiées avec SmackProcessLabel= sont attribuées et le défaut de compilation est ignoré.

Ajouté dans la version 252.

DefaultRestrictSUIDSGID=

Prend un argument booléen. Ceci est utilisé comme défaut pour les unités qui n'ont pas de définition explicite pour RestrictSUIDSGID=. Voir systemd.exec(5) pour les détails.

Ajouté dans la version 258.

TEMPORISATIONS ET LIMITES DE DÉBIT

DefaultTimeoutStartSec=, DefaultTimeoutStopSec=, DefaultTimeoutAbortSec=, DefaultRestartSec=

Configure les temporisations par défaut pour le démarrage, l'arrêt et l'abandon des unités, ainsi que le temps par défaut pour attendre entre les redémarrages automatiques des unités, tels que configurés par unité dans TimeoutStartSec=, TimeoutStopSec=, TimeoutAbortSec= et RestartSec= (pour les services, voir systemd.service(5) pour les détails sur les paramètres par unité). Pour les unités autres que les services, DefaultTimeoutStartSec= définit la valeur TimeoutSec= par défaut.

DefaultTimeoutStartSec= et DefaultTimeoutStopSec= valent 90 s par défaut dans le gestionnaire système et 90 s dans le gestionnaire utilisateur. DefaultTimeoutAbortSec= n'est pas défini par défaut afin que toutes les unités reviennent à TimeoutStopSec=. DefaultRestartSec= vaut 100 ms par défaut.

Ajouté dans la version 209.

DefaultDeviceTimeoutSec=

Configure le délai d'attente par défaut pour les périphériques. Il peut être modifié par périphérique via l'option x-systemd.device-timeout= dans /etc/fstab et /etc/crypttab (voir systemd.mount(5), crypttab(5)). Par défaut 90 s dans le gestionnaire système et 90 s dans le gestionnaire utilisateur.

Ajouté dans la version 252.

DefaultStartLimitIntervalSec=, DefaultStartLimitBurst=

Configure la limitation du débit de démarrage des unités par défaut, telle que configurée par service par StartLimitIntervalSec= et StartLimitBurst=. Voir systemd.service(5) pour les détails sur les paramètres par service. DefaultStartLimitIntervalSec= vaut 10s par défaut. DefaultStartLimitBurst= vaut 5 par défaut.

Ajouté dans la version 209.

ReloadLimitIntervalSec=, ReloadLimitBurst=

Limitation du débit pour les demandes de daemon-reload et (depuis la v256) de daemon-reexec. Le paramètre s'applique aux deux opérations, mais les limites de débit sont suivies séparément. Par défaut, non défini, et tout nombre d'opérations peut être demandé à tout moment. ReloadLimitIntervalSec= prend une valeur en secondes pour configurer la fenêtre de limite de débit, et ReloadLimitBurst= prend un entier positif pour configurer le nombre maximum d'opérations autorisées dans la fenêtre de temps configurée.

Ajouté dans la version 253.

ENVIRONNEMENT

DefaultEnvironment=

Configure les variables d'environnement transmises à tous les processus exécutés. Prend une liste de définitions de variables séparées par des espaces. Voir environ(7) pour les détails sur les variables d'environnement. Ce bloc d'environnement est interne, et les changements ne sont pas reflétés dans /proc/PID/environ du gestionnaire.

Une expansion simple des spécificateurs "%" est prise en charge, voir ci-dessous pour une liste des spécificateurs pris en charge.

Exemple :

DefaultEnvironment="VAR1=mot1 mot2" VAR2=mot3 "VAR3=mot 5 6"

Définit trois variables : "VAR1", "VAR2", "VAR3".

Ajouté dans la version 205.

ManagerEnvironment=

Définit les variables d'environnement pour le processus du gestionnaire lui-même. Prend une liste de définitions de variables séparées par des espaces dans le même format que DefaultEnvironment=, voir ci-dessus. Ces variables sont fusionnées dans le bloc d'environnement existant du processus du gestionnaire. En particulier, dans le cas du gestionnaire système, ce bloc inclut les variables définies par le noyau en fonction de la ligne de commande du noyau, et dans le cas du gestionnaire utilisateur, les variables transmises par le gestionnaire système. Après que ces variables aient été fusionnées, elles persisteront jusqu'à être remplacées, même si le gestionnaire est rechargé ou réexécuté. Dans le cas du gestionnaire utilisateur, ces variables sont également héritées par les processus lancés par le gestionnaire. Comme avec DefaultEnvironment=, ce bloc d'environnement est interne, et les changements ne sont pas reflétés dans /proc/PID/environ du gestionnaire.

La définition de variables d'environnement pour le processus du gestionnaire peut être utile pour modifier son comportement. Voir Known Environment Variables[3] pour une description de certaines variables comprises par systemd.

Une expansion simple des spécificateurs "%" est prise en charge, voir ci-dessous pour une liste des spécificateurs pris en charge.

Ajouté dans la version 248.

NAME

systemd.directives - List of important systemd directives

SYNOPSIS

systemd.unit(7), systemd.exec(5), systemd.service(5), systemd.timer(5), systemd.socket(5), systemd.swap(5), systemd.mount(5), systemd.path(5), systemd.slice(5), systemd.kill(5), systemd.resource-control(5), systemd.memcg(5), systemd.special(7)

DESCRIPTION

This document lists and describes the various configuration directives supported by systemd unit files and related configuration files. It is not intended to be exhaustive, but to cover the most important and commonly used directives, grouping them by functionality.

For a complete list of directives and their semantics, consult the manual pages for individual unit types (e.g. systemd.service(5)) and related configuration files (e.g. systemd.exec(5), systemd.resource-control(5)).

Directives are grouped into the following sections:

  • CONFIGURATION DIRECTORIES AND PRECEDENCE
  • OPTIONS
  • RESOURCE MANAGEMENT
  • HARDWARE WATCHDOG
  • SECURITY
  • TIMEOUTS AND RATE LIMITS
  • ENVIRONMENT
  • SPECIFIERS

CONFIGURATION DIRECTORIES AND PRECEDENCE

systemd looks for configuration files in several directories, with precedence given to files in directories listed earlier in the following list:

1.
/etc/systemd/system
2.
/run/systemd/system
3.
/usr/lib/systemd/system

For system-wide configuration files, precedence is given to files in directories listed earlier in the following list:

1.
/etc/systemd/user.conf
2.
/usr/lib/systemd/user.conf

Directory fragments are merged according to the rules described in systemd.unit(7).

It is recommended to place local configuration overrides in /etc/systemd/system, and distribution-provided defaults in /usr/lib/systemd/system.

Configuration files in /etc/systemd/system take precedence over files in /usr/lib/systemd/system. Configuration files in /run/systemd/system take precedence over files in /etc/systemd/system.

Note 1: ${DESTDIR} is used during installation.

OPTIONS

This section describes directives that control the general behavior of units.

[Unit] Section:

Description=
A human-readable name for the unit. This string is used in various output messages, and may be used by tools to identify the unit.
Documentation=
A space-separated list of URIs referring to the documentation for this system and service. URIs may be http:, https:, file:, or man: references.
Requires=
A space-separated list of unit names. If this unit is started, the units listed here are also started. If any of these units fail to start, this unit will not be started.
Wants=
A space-separated list of unit names. This is a weaker form of Requires=. If this unit is started, the units listed here are also started. If any of these units fail to start, this unit will still be started.
BindsTo=
Similar to Requires=, but also makes the units dependent on each other. If a unit listed here stops, this unit will also stop.
PartOf=
A space-separated list of unit names. Similar to BindsTo=, but only affects the stop/restart logic. If a unit listed here stops or restarts, this unit will also stop or restart.
Before=, After=
Controls the order in which units are started or stopped. For example, if `A.service` contains `After=B.service`, then `B.service` will be started before `A.service`.
Conflicts=
A space-separated list of unit names. If this unit is started, the units listed here will be stopped. If any of the units listed here are started, this unit will be stopped.
DefaultDependencies=
A boolean. If true (the default), systemd will automatically add dependencies to ensure basic functionality, such as starting after the required system initialization is complete. Set to false to disable these default dependencies.
RefuseManualStart=, RefuseManualStop=
A boolean. If true, the unit cannot be started or stopped manually using `systemctl start` or `systemctl stop`. However, it can still be started or stopped as a dependency of another unit.
AllowIsolate=
A boolean. If true, the unit may be used with `systemctl isolate`. Defaults to true for most unit types.

[Install] Section:

WantedBy=
A space-separated list of unit names. This directive is used to make the unit start automatically at boot. For example, if a service has `WantedBy=multi-user.target`, it will be started when the system reaches the multi-user runlevel.
RequiredBy=
Similar to WantedBy=, but makes the unit a hard requirement for the target.
Alias=
A space-separated list of alternative names for the unit. These aliases can be used with `systemctl` commands.
DefaultInstance=
For template units (e.g., `getty@.service`), this specifies the default instance to use when referring to the template unit without an instance name.

RESOURCE MANAGEMENT

These directives, primarily found in the systemd.resource-control(5) man page, control resource usage for units.

CPUQuota=, CPUWeight=, CPUQuotaPeriodSec=
Limit or weight CPU usage.
MemoryLimit=, MemoryMax=, MemoryHigh=, MemoryLow=
Limit or prioritize memory usage.
IOWeight=, PIOCount=, ROCount=, BlockIOQuota=
Control block I/O bandwidth.
DevicePolicy=
Control access to specific devices.
DeviceAllow=
Explicitly allow access to specific devices.
Slice=
Assign the unit to a specific slice for resource management.

HARDWARE WATCHDOG

Directives for interacting with hardware watchdogs.

WatchdogSec=
Sets the watchdog timeout for a service. The service must "pet" the watchdog timer within this interval, otherwise the system will reboot.
RuntimeWatchdogSec=
Similar to WatchdogSec=, but applies to the unit's runtime duration. If the unit runs longer than this, it will be terminated.

SECURITY

Directives related to security hardening and sandboxing.

CapabilityBoundingSet=
Restrict the set of Linux capabilities the unit can use.
AmbientCapabilities=
Grant specific capabilities to the unit's process.
ReadWritePaths=, ReadOnlyPaths=, InsecurePaths=
Control filesystem access for the unit.
SystemCallFilter=
Restrict the system calls the unit can make.
SystemCallArchitectures=
Restrict the architectures the unit can execute.
NoNewPrivileges=
Prevent the unit's process from gaining new privileges.
ProtectSystem=, ProtectHome=, ProtectKernelTunables=, ProtectKernelLogs=, ProtectControlGroups=
Apply various system protection measures.
PrivateTmp=, PrivateDevices=, PrivateNetwork=, PrivateUsers=, PrivateHost=
Create a more isolated environment for the unit.
LockPersonality=
Enable personality isolation.
Personality=
Set the personality for the unit.
RestrictAddressFamilies=, RestrictNamespaces=, RestrictRealtime=, RestrictSUidInstall=
Further restrict unit behavior.

TIMEOUTS AND RATE LIMITS

Directives for controlling timeouts and rate limiting.

TimeoutStartSec=, TimeoutStopSec=, TimeoutSec=
Set timeouts for starting, stopping, or general operations.
ReceiveTimeoutSec=, SendTimeoutSec=
Timeouts for socket units.
RestartSec=
Delay before restarting a service after it exits.
StartLimitIntervalSec=, StartLimitBurst=
Rate limit unit activation.

ENVIRONMENT

Directives for setting environment variables for units.

Environment=
Set individual environment variables.
EnvironmentFile=
Load environment variables from a file.
PassEnvironment=
Specify which environment variables from the service manager should be passed to the unit.
UnsetEnvironment=
Unset specific environment variables.

SPECIFIERS

Specifiers are placeholders that are expanded by systemd when processing unit files. They are often used in paths and commands.

"%a" Kernel architecture The kernel architecture name, as reported by uname -m.
"%b" Boot count The number of times the system has booted since the systemd journal was created.
"%C" CPU time consumed by the unit The total CPU time consumed by the unit, formatted as a string like "00:00:00".
"%d" Data directory The data directory of the system, usually /var/lib.
"%e" Instance name The instance name of a templated unit. For example, for getty@tty1.service, this is tty1. For units without an instance name, this is an empty string.
"%E" Configuration directory The configuration directory of the system, usually /etc.
"%f" Root directory The root directory, usually /.
"%h" User home directory The home directory of the user running the service manager instance.
"%H" Host name The hostname of the system.
"%i" Instance name (like %e) Same as %e.
"%k" Kernel name The kernel name, usually Linux.
"%L" Log directory The log directory of the system, usually /var/log.
"%m" Kernel machine The machine hardware name, as reported by uname -m.
"%M" Operating System Name The operating system name, as read from the PRETTY_NAME= field of /etc/os-release. If not set, resolves to an empty string. See os-release(5) for more information.
"%n" Node name The network node hostname. Same as %H.
"%N" Unit name The name of the unit file, without suffix. For example, for getty@tty1.service, this is getty@tty1.
"%o" Operating system flavor The operating system flavor, as read from the ID= field of /etc/os-release. If not set, resolves to an empty string. See os-release(5) for more information.
"%p" Process ID The process ID of the main process of the unit. Only available for service units.
"%P" PID file path The path to the PID file specified in the unit configuration. Only available for service units.
"%q" Mount point The mount point of the unit, if applicable.
"%r" Root directory for read-only access The root directory for read-only filesystem access, usually /usr.
"%R" Root directory for read-write access The root directory for read-write filesystem access, usually /.
"%s" User shell The shell of the user running the service manager instance.
"%S" Kernel release The kernel release, as reported by uname -r.
"%t" Runtime directory The runtime directory of the system, usually /run.
"%T" Directory for temporary files This is either /tmp or the path "$TMPDIR", "$TEMP" or "$TMP" are set to. (Note that the directory may be specified without a trailing slash.)
"%u" Username The username of the user running the service manager instance.
"%U" User id The user id of the user running the service manager instance.
"%v" Kernel version The kernel version, as reported by uname -v.
"%V" Directory for larger and persistent temporary files This is either /var/tmp or the path "$TMPDIR", "$TEMP" or "$TMP" are set to. (Note that the directory may be specified without a trailing slash.)
"%w" Timestamp of the last change The timestamp of the last change to the unit, formatted as YYYY-MM-DD HH:MM:SS.
"%W" Operating system variant ID The operating system variant identifier of the running system, as read from the VARIANT_ID= field of /etc/os-release. If not set, resolves to an empty string. See os-release(5) for more information.
"%x" System load average The system load average, formatted as a string like "0.00".
"%X" System uptime The system uptime, formatted as a string like "0d 00:00:00".
"%y" System up since The timestamp when the system was last booted.
"%Y" Unit activation timestamp The timestamp when the unit was last activated.
"%z" System serial number The system serial number, if available.
"%Z" Unit state change timestamp The timestamp when the unit last changed its state.
"%%" Single percent sign Use "%%" in place of "%" to specify a single percent sign.
