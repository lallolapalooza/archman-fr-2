PROLOGUE

Cette page de manuel fait partie du Manuel du programmeur POSIX. L'implémentation de cette interface sous Linux peut différer (consultez la page de manuel Linux correspondante pour les détails du comportement sous Linux), ou l'interface peut ne pas être implémentée sous Linux.

NOM

uuencode — encoder un fichier binaire

SYNTAXE

uuencode [-m] [fichier] chemin_de_decodage

DESCRIPTION

L'utilitaire uuencode écrira une version encodée du fichier d'entrée spécifié, ou de l'entrée standard si aucun fichier n'est spécifié, sur la sortie standard. La sortie sera encodée en utilisant l'un des algorithmes décrits dans la section STDOUT et inclura les bits de permission d'accès du fichier (en notation octale ou symbolique chmod) du fichier d'entrée et le chemin_de_decodage, pour la recréation du fichier sur un autre système conforme à ce volume de POSIX.1‐2017.

OPTIONS

L'utilitaire uuencode sera conforme aux directives de syntaxe des utilitaires du volume Base Definitions de POSIX.1‐2017, Section 12.2.

L'option suivante sera prise en charge par l'implémentation :

-m
Encode la sortie en utilisant l'algorithme Base64 MIME décrit dans STDOUT. Si -m n'est pas spécifié, l'algorithme historique décrit dans STDOUT sera utilisé.

OPÉRANDES

Les opérandes suivants seront pris en charge :

chemin_de_decodage

Le chemin du fichier dans lequel l'utilitaire uudecode placera le fichier décodé. La spécification d'un opérande chemin_de_decodage de /dev/stdout indiquera que uudecode doit utiliser la sortie standard. S'il y a des caractères dans chemin_de_decodage qui ne font pas partie de l'ensemble de caractères de nom de fichier portable, les résultats ne sont pas spécifiés.
fichier
Un chemin du fichier à encoder.

STDIN

Voir la section FICHIERS D'ENTRÉE.

FICHIERS D'ENTRÉE

Les fichiers d'entrée peuvent être des fichiers de tout type.

VARIABLES D'ENVIRONNEMENT

Les variables d'environnement suivantes affecteront l'exécution de uuencode :

LANG
Fournit une valeur par défaut pour les variables d'internationalisation qui sont non définies ou vides. (Voir le volume Base Definitions de POSIX.1‐2017, Section 8.2, Variables d'internationalisation pour la priorité des variables d'internationalisation utilisées pour déterminer les valeurs des catégories de locale.)
LC_ALL
Si définie à une chaîne non vide, remplace les valeurs de toutes les autres variables d'internationalisation.
LC_CTYPE
Détermine la locale pour l'interprétation des séquences d'octets de données textuelles en caractères (par exemple, caractères mono-octet par opposition à multi-octets dans les arguments et les fichiers d'entrée).
LC_MESSAGES

Détermine la locale qui doit être utilisée pour affecter le format et le contenu des messages de diagnostic écrits sur la sortie d'erreur standard.
NLSPATH
Détermine l'emplacement des catalogues de messages pour le traitement de LC_MESSAGES.

ÉVÉNEMENTS ASYNCHRONES

Par défaut.

STDOUT

Algorithme Base64 de uuencode

La sortie standard sera un fichier texte (encodé dans le jeu de caractères de la locale courante) qui commence par la ligne :

"begin-base64 %s %s\n", <mode>, <chemin_de_decodage>

et se termine par la ligne :

"====\n"

Dans les deux cas, les lignes ne doivent pas avoir de caractères <espace> précédents ou suivants.

Le processus d'encodage représente des groupes de 24 bits d'entrée sous forme de chaînes de sortie de quatre caractères encodés. En procédant de gauche à droite, un groupe d'entrée de 24 bits est formé en concaténant trois groupes d'entrée de 8 bits. Chaque groupe de 24 bits est ensuite traité comme quatre groupes concaténés de 6 bits, chacun étant traduit en un seul chiffre dans l'alphabet Base64. Lors de l'encodage d'un flux de bits via l'encodage Base64, le flux de bits est présumé être ordonné avec le bit le plus significatif en premier. C'est-à-dire que le premier bit du flux sera le bit de poids fort du premier octet, et le huitième bit sera le bit de poids faible du premier octet, et ainsi de suite. Chaque groupe de 6 bits est utilisé comme index dans un tableau de 64 caractères imprimables, comme illustré dans le Tableau 4-22, Valeurs Base64 de uuencode.


Tableau 4-22 : Valeurs Base64 de uuencode

NAME

base64, uudecode, uuencode - stream encoder/decoder for the Base64/UUencoding system

SYNOPSIS

base64 [-d|-u] [file]

uuencode [-m] [file output_file]

uudecode [file]

DESCRIPTION

The base64 utility is used to encode and decode files using the Base64 encoding method. The uuencode utility is used to encode files using the UUencode method. The uudecode utility is used to decode files encoded with UUencode.

The default mode of operation for base64 is encoding. The -d option selects decoding, and the -u option selects UUencoding decoding.

If no file is specified, the standard input shall be used. If the output file is not specified, the standard output shall be used.

The UUencode method is a more traditional method for encoding binary files for transmission over ASCII-based systems. It is generally less efficient than Base64.

The options are as follows:

-d
Decode.
-u
UUencode decode.
-m
Use the Base64 encoding method instead of the default UUencode method.

Base64 Encoding Algorithm

The Base64 encoding method is described in RFC 1521. It is used to represent binary data in an ASCII string format. The algorithm works by taking groups of 3 octets (24 bits) and representing them as 4 characters from a 64-character alphabet.

The Base64 alphabet is:

A-Z a-z 0-9 + /

The table below shows the mapping from the 6-bit values to the Base64 characters:

0 A 26 a 52 0 78 (null)
1 B 27 b 53 1 79 !
2 C 28 c 54 2 80 "
3 D 29 d 55 3 81 #
4 E 30 e 56 4 82 $
5 F 31 f 57 5 83 %
6 G 32 g 58 6 84 &
7 H 33 h 59 7 85 '
8 I 34 i 60 8 86 (
9 J 35 j 61 9 87 )
10 K 36 k 62 + 88 *
11 L 37 l 63 / 89 +
12 M 38 m (pad) = 90 ,
13 N 39 n (pad) = 91 -
14 O 40 o (pad) = 92 .
15 P 41 p (pad) = 93 /
16 Q 42 q (pad) = 94 0
17 R 43 r (pad) = 95 1
18 S 44 s (pad) = 96 2
19 T 45 t (pad) = 97 3
20 U 46 u (pad) = 98 4
21 V 47 v (pad) = 99 5
22 W 48 w (pad) = 100 6
23 X 49 x (pad) = 101 7
24 Y 50 y (pad) = 102 8
25 Z 51 z (pad) = 103 9

The character referenced by the index shall be placed in the output string.

The output stream (encoded bytes) shall be represented in lines of no more than 76 characters each. All line breaks or other characters not found in the table shall be ignored by decoding software (see uudecode).

Special processing shall be performed if fewer than 24 bits are available at the end of a message or encapsulated part of a message. A full encoding quantum shall always be completed at the end of a message. When fewer than 24 input bits are available in an input group, zero bits shall be added (on the right) to form an integral number of 6-bit groups. Output character positions that are not required to represent actual input data shall be set to the character '='. Since all Base64 input is an integral number of octets, only the following cases can arise:

1.
The final quantum of encoding input is an integral multiple of 24 bits; here, the final unit of encoded output shall be an integral multiple of 4 characters with no '=' padding.
2.
The final quantum of encoding input is exactly 16 bits; here, the final unit of encoded output shall be three characters followed by one '=' padding character.
3.
The final quantum of encoding input is exactly 8 bits; here, the final unit of encoded output shall be two characters followed by two '=' padding characters.

A terminating "====" evaluates to nothing and denotes the end of the encoded data.

uuencode Historical Algorithm

The standard output shall be a text file (encoded in the character set of the current locale) that begins with the line:

"begin %s %s\n" <mode>, <decode_pathname>

and ends with the line:

"end\n"

In both cases, the lines shall have no preceding or trailing <blank> characters.

The algorithm that shall be used for lines in between begin and end takes three octets as input and writes four characters of output by splitting the input at six-bit intervals into four octets, containing data in the lower six bits only. These octets shall be converted to characters by adding a value of 0x20 to each octet, so that each octet is in the range [0x20,0x5f], and then it shall be assumed to represent a printable character in the ISO/IEC 646:1991 standard encoded character set. It then shall be translated into the corresponding character codes for the codeset in use in the current locale. (For example, the octet 0x41, representing 'A', would be translated to 'A' in the current codeset, such as 0xc1 if it were EBCDIC.)

Where the bits of two octets are combined, the least significant bits of the first octet shall be shifted left and combined with the most significant bits of the second octet shifted right. Thus the three octets A, B, C shall be converted into the four octets:

0x20 + (( A >> 2                    ) & 0x3F)
0x20 + (((A << 4) |(aq ((B >> 4) & 0xF)) & 0x3F)
0x20 + (((B << 2) |(aq ((C >> 6) & 0x3)) & 0x3F)
0x20 + (( C                         ) & 0x3F)

These octets then shall be translated into the local character set.

Each encoded line contains a length character, equal to the number of characters to be decoded plus 0x20 translated to the local character set as described above, followed by the encoded characters. The maximum number of octets to be encoded on each line shall be 45.

NAME

uuencode, uudecode — encode a binary file, or decode its ASCII representation

SYNOPSIS

uuencode [-m] [input_file...] [output_file]

uuencode [-base64] [input_file...] [output_file]

uudecode [input_file...]

uudecode [-m] [input_file...]

DESCRIPTION

The uuencode utility reads binary data from the specified input_files or from standard input if no input_file is given, translates it into an ASCII representation, and writes it to the specified output_file or to standard output if no output_file is given. The ASCII representation is suitable for transmission over networks that may corrupt binary data, such as mail systems. The uudecode utility reads this ASCII representation from the specified input_files or from standard input if no input_file is given, translates it back into binary data, and writes it to standard output.

The encoding process translates each group of three 8-bit bytes into a group of four 7-bit ASCII characters. The first character of each line is a count of the number of bytes encoded on that line (plus 32). The characters used are the 64 characters starting with ASCII space (32), followed by ASCII underscore (95).

By default, uuencode uses the traditional Unix uuencode format. This format includes a header line defining the mode and name of the output file, and a trailer line named end.

The -m option enables the Base64 encoding method described in RFC 2045 (MIME). The output format is different from the traditional uuencode format. It does not include a header or trailer, and is often used for internet mail messages.

The uudecode utility determines the encoding method used by examining the input. If the input contains lines starting with begin 644 or begin base64, it uses the Base64 decoding method. Otherwise, it assumes the traditional uuencode format.

When decoding, uudecode creates files with the permissions and ownership specified in the header line, if available. The default permissions are 644.

OPTIONS

-m, --base64

Use the Base64 encoding method described in RFC 2045.

OPERANDS

input_file

The path to the input file. If omitted, standard input is used.

output_file

The path to the output file. If omitted, standard output is used.

STDIN

If no input_file operands are specified, uuencode reads the input data from standard input, and uudecode reads the encoded data from standard input.

INPUT FILES

The input files are read for encoding. For decoding, the input files are the encoded data streams.

ENVIRONMENT VARIABLES

BLOCKSIZE

See --block-size in cp(1).

ASYNCHRONOUS EVENTS

See SIGPIPE in cp(1).

STDOUT

The encoded data is written to standard output.

STDERR

The standard error is used only for diagnostic messages.

OUTPUT FILES

The decoded data is written to standard output.

EXTENDED DESCRIPTION

The file is expanded by 35 percent (each three octets become four, plus control information) causing it to take longer to transmit.

Since this utility is intended to create files to be used for data interchange between systems with possibly different codesets, and to represent binary data as a text file, the ISO/IEC 646:1991 standard was chosen for a midpoint in the algorithm as a known reference point. The output from uuencode is a text file on the local system. If the output were in the ISO/IEC 646:1991 standard codeset, it might not be a text file (at least because the <newline> characters might not match), and the goal of creating a text file would be defeated. If this text file was then carried to another machine with the same codeset, it would be perfectly compatible with that system's uudecode. If it was transmitted over a mail system or sent to a machine with a different codeset, it is assumed that, as for every other text file, some translation mechanism would convert it (by the time it reached a user on the other system) into an appropriate codeset. This translation only makes sense from the local codeset, not if the file has been put into a ISO/IEC 646:1991 standard representation first. Similarly, files processed by uuencode can be placed in pax archives, intermixed with other text files in the same codeset.

EXAMPLES

None.

RATIONALE

A new algorithm was added at the request of the international community to parallel work in RFC 2045 (MIME). As with the historical uuencode format, the Base64 Content-Transfer-Encoding is designed to represent arbitrary sequences of octets in a form that is not humanly readable. A 65-character subset of the ISO/IEC 646:1991 standard is used, enabling 6 bits to be represented per printable character. (The extra 65th character, '=', is used to signify a special processing function.)

This subset has the important property that it is represented identically in all versions of the ISO/IEC 646:1991 standard, including US ASCII, and all characters in the subset are also represented identically in all versions of EBCDIC. The historical uuencode algorithm does not share this property, which is the reason that a second algorithm was added to the ISO POSIX‐2 standard.

The string "====" was used for the termination instead of the end used in the original format because the latter is a string that could be valid encoded input.

In an early draft, the -m option was named -b (for Base64), but it was renamed to reflect its relationship to the RFC 2045. A -u was also present to invoke the default algorithm, but since this was not historical practice, it was omitted as being unnecessary.

See the RATIONALE section in uudecode for the derivation of the /dev/stdout symbol.
