NOM

userdbctl - Examiner les utilisateurs, groupes et appartenances à des groupes

SYNOPIS

userdbctl [OPTIONS...] {COMMANDE} [NOM...]

DESCRIPTION

userdbctl peut être utilisé pour examiner les utilisateurs et les groupes (ainsi que les appartenances à des groupes) du système. Cet utilitaire client interroge les informations utilisateur/groupe fournies par divers services système, à la fois ceux qui opèrent sur des enregistrements d'utilisateurs/groupes JSON (tels que définis par les définitions JSON User Records[1] et JSON Group Records[2]), et les enregistrements classiques d'utilisateurs et de groupes NSS/glibc. Cet outil est principalement un client de l'API de recherche d'enregistrements utilisateurs/groupes via Varlink[3], et peut également récupérer des enregistrements d'utilisateurs et de groupes JSON de substitution à partir de /etc/userdb/, /run/userdb/, /run/host/userdb/, /usr/lib/userdb/ (voir nss-systemd(8) pour plus de détails sur les enregistrements utilisateurs de substitution).

OPTIONS

Les options suivantes sont comprises :

--output=MODE

Choisit le mode de sortie. Accepte l'un des modes "classic", "friendly", "table" ou "json". Si "classic", une sortie très proche du format de /etc/passwd ou /etc/group est générée. Si "friendly", une sortie plus complète et conviviale, lisible par l'homme, est générée. Si "table", une sortie tabulaire minimale est générée. Si "json", une sortie au format JSON est générée. Par défaut, "friendly" si un utilisateur/groupe est spécifié sur la ligne de commande, "table" sinon.

Notez que la plupart des formats de sortie ne montrent pas toutes les informations disponibles. En particulier, "classic" et "table" ne montrent que les champs les plus importants. Divers modes ne montrent pas non plus les hachages de mots de passe. Utilisez "json" pour afficher tous les champs, y compris tous les champs d'authentification.

Ajouté dans la version 245.

--json=FORMAT

Sélectionne le mode de sortie JSON (comme --output=json) et sélectionne le mode d'affichage précis. Accepte "pretty" ou "short". Si "pretty", des espaces et des retours à la ligne conviviaux sont insérés dans la sortie pour rendre les données JSON plus lisibles. Si "short", tous les espaces superflus sont supprimés.

Ajouté dans la version 250.

--service=SERVICE[:SERVICE...], -s SERVICE:SERVICE...

Contrôle quels services interroger pour les utilisateurs/groupes. Accepte une liste d'un ou plusieurs noms de service, séparés par ":". Voir ci-dessous pour une liste des noms de service bien connus. Si non spécifié, tous les services disponibles sont interrogés simultanément.

Ajouté dans la version 245.

--with-nss=BOOL

Contrôle s'il faut inclure les recherches classiques glibc/NSS d'utilisateurs/groupes dans la sortie. Si --with-nss=no est utilisé, toute tentative de résolution ou d'énumération d'utilisateurs/groupes fournis uniquement via glibc NSS est supprimée. Si --with-nss=yes est spécifié, de tels utilisateurs/groupes sont inclus dans la sortie (ce qui est la valeur par défaut).

Ajouté dans la version 245.

--with-varlink=BOOL

Contrôle s'il faut inclure les recherches d'utilisateurs/groupes Varlink dans la sortie, c'est-à-dire celles effectuées via l'API de recherche d'enregistrements utilisateurs/groupes via Varlink[3]. Si --with-varlink=no est utilisé, toute tentative de résolution ou d'énumération d'utilisateurs/groupes fournis uniquement via Varlink est supprimée. Si --with-varlink=yes est spécifié, de tels utilisateurs/groupes sont inclus dans la sortie (ce qui est la valeur par défaut).

Ajouté dans la version 249.

--with-dropin=BOOL

Contrôle s'il faut inclure dans la sortie les recherches d'utilisateurs/groupes définies à l'aide de fichiers de substitution dans /etc/userdb/, /run/userdb/, /run/host/userdb/, /usr/lib/userdb/. Si --with-dropin=no est utilisé, ces enregistrements sont supprimés. Si --with-dropin=yes est spécifié, de tels utilisateurs/groupes sont inclus dans la sortie (ce qui est la valeur par défaut).

Ajouté dans la version 249.

--synthesize=BOOL

Contrôle s'il faut synthétiser des enregistrements pour les utilisateurs/groupes root et nobody s'ils ne sont pas définis autrement, ainsi que les utilisateurs/groupes pour la plage UID/GID "étrangère". Par défaut (ou avec "yes"), de tels enregistrements sont implicitement synthétisés s'ils sont autrement manquants car ils ont une signification spéciale pour le système d'exploitation. Lorsque "no", cette synthèse est désactivée.

Ajouté dans la version 245.

-N

Cette option est un raccourci pour --with-nss=no --synthesize=no. Utilisez cette option pour afficher uniquement les enregistrements qui sont nativement définis comme enregistrements d'utilisateurs ou de groupes JSON, avec toute compatibilité NSS/glibc et toute synthèse implicite désactivées.

Ajouté dans la version 245.

--multiplexer=BOOL

Contrôle s'il faut effectuer des recherches via le service multiplexeur (si spécifié comme vrai, par défaut) ou effectuer des recherches dans le client (si spécifié comme faux). L'utilisation du service multiplexeur est généralement préférable, car il s'exécute dans un environnement isolé et sécurisé.

Ajouté dans la version 250.

--chain

Lorsqu'utilisé avec la commande ssh-authorized-keys, cela permet de passer une ligne de commande supplémentaire après le nom d'utilisateur qui est exécutée en chaîne après la fin de la recherche. Cela permet de chaîner plusieurs outils affichant les clés autorisées SSH.

Ajouté dans la version 250.

--fuzzy, -z

Lorsqu'utilisé avec la commande user ou group, effectue une recherche de chaîne floue. Tous les arguments spécifiés seront comparés au nom d'utilisateur, au nom réel de l'enregistrement utilisateur, à l'adresse e-mail et à d'autres chaînes descriptives de l'enregistrement utilisateur ou groupe. De plus, au lieu d'une correspondance précise, une correspondance de sous-chaîne ou une correspondance permettant de légères déviations dans l'orthographe est appliquée.

Ajouté dans la version 257.

--disposition=

Lorsqu'utilisé avec la commande user ou group, filtre par disposition de l'enregistrement. Accepte l'un des éléments suivants : "intrinsic", "system", "regular", "dynamic", "container". Peut être utilisé plusieurs fois, auquel cas seuls les utilisateurs correspondant à l'une des dispositions spécifiées sont affichés.

Ajouté dans la version 257.

-I, -S, -R

Raccourcis pour --disposition=intrinsic, --disposition=system, --disposition=regular, respectivement.

Ajouté dans la version 257.

--uid-min=, --uid-max=

Lorsqu'utilisé avec la commande user ou group, filtre la sortie par plages d'UID/GID. Accepte des valeurs numériques minimales ou maximales d'UID/GID, respectivement. Affiche uniquement les enregistrements dans la plage spécifiée. Lorsqu'appliqué à la commande user, il correspond aux UID. Lorsqu'appliqué à la commande group, il correspond aux GID (malgré le nom de l'option). Si non spécifié, par défaut 0 (pour le minimum) et 4294967294 (pour le maximum), c'est-à-dire que par défaut, aucun filtrage n'est appliqué, car toute la plage d'UID/GID est couverte.

Ajouté dans la version 257.

--boundaries=

Lorsqu'utilisé avec la commande user ou group, contrôle s'il faut afficher les informations de limites de plage UID/GID pertinentes dans la sortie tabulaire. Accepte une valeur booléenne. Par défaut, la valeur est true.

Ajouté dans la version 257.

-B

Raccourci pour --boundaries=no.

Ajouté dans la version 257.

--from-file=PATH, -f

Lorsqu'utilisé avec la commande user ou group, lit la définition de l'utilisateur au format JSON depuis le fichier spécifié, au lieu de la rechercher auprès du système. Si le chemin est spécifié comme "-", lit les données JSON depuis l'entrée standard. Ceci est utile pour valider et introspecter rapidement les enregistrements d'utilisateurs ou de groupes JSON, et vérifier comment ils seraient interprétés sur le système local.

Ajouté dans la version 258.

--no-pager

Ne pas rediriger la sortie vers un pager.

--no-legend

Ne pas imprimer la légende, c'est-à-dire les en-têtes de colonnes et le pied de page avec des indications.

-h, --help

Imprimer un bref message d'aide et quitter.

--version

Imprimer une courte chaîne de version et quitter.

Liste les groupes dont les utilisateurs spécifiés sont membres. Si aucun utilisateur n'est spécifié, liste toutes les appartenances utilisateur/groupe définies (dans ce cas, groups-of-user et users-in-group sont équivalents). Utilisez --output= pour ajuster le mode de sortie.

Ajouté dans la version 245.

services

Liste tous les services fournissant actuellement des définitions d'utilisateurs/groupes au système. Voir ci-dessous pour une liste des services bien connus fournissant des informations sur les utilisateurs.

Ajouté dans la version 245.

ssh-authorized-keys

Affiche les clés SSH autorisées pour ce compte. Cette commande est destinée à permettre au démon SSH de récupérer les clés autorisées à partir des enregistrements d'utilisateurs, voir ci-dessous.

Ajouté dans la version 245.

load-credentials

Lorsqu'il est spécifié, les informations d'identification suivantes sont utilisées lorsqu'elles sont passées :

userdb.user.*, userdb.group.*

Ces informations d'identification doivent contenir des enregistrements JSON User[1] et JSON Group[2] valides. Pour chaque information d'identification correspondante, divers fichiers sont créés dans /etc/userdb/, implémentant l'interface décrite dans nss-systemd(8). Tous les enregistrements d'utilisateurs transmis doivent contenir les champs UID et GID valides. Tous les enregistrements de groupe transmis doivent contenir un champ GID (c'est-à-dire que l'allocation automatique d'UID/GID n'est pas prise en charge). Pour les enregistrements d'utilisateurs et de groupes, le suffixe de l'information d'identification (pour « userdb.user.foobar », le suffixe est « foobar ») doit correspondre au nom d'utilisateur ou de groupe codé dans l'enregistrement.

Ajouté dans la version 258.

SERVICES BIEN CONNUS

La commande userdbctl services liste tous les services en cours d'exécution qui fournissent des définitions d'utilisateurs ou de groupes au système. Les services bien connus suivants sont affichés dans cette liste :

io.systemd.DynamicUser

Ce service est fourni par le gestionnaire de services système lui-même (c'est-à-dire PID 1) et rend disponibles au système tous les utilisateurs (et leurs groupes) synthétisés par le paramètre DynamicUser= dans les fichiers d'unités de service (voir systemd.exec(5) pour plus de détails sur ce paramètre).

Ajouté dans la version 245.

io.systemd.Home

Ce service est fourni par systemd-homed.service(8) et rend disponibles au système tous les utilisateurs (et leurs groupes) appartenant aux répertoires personnels gérés par ce service.

Ajouté dans la version 245.

io.systemd.Machine

Ce service est fourni par systemd-machined.service(8) et synthétise des enregistrements pour tous les utilisateurs/groupes utilisés par un conteneur qui utilise l'espace de noms d'utilisateurs.

Ajouté dans la version 246.

io.systemd.Multiplexer

Ce service est fourni par systemd-userdbd.service(8) et multiplexe les recherches d'utilisateurs/groupes vers tous les autres services de recherche en cours d'exécution. C'est le point d'entrée principal pour les clients d'enregistrements d'utilisateurs/groupes, car il simplifie considérablement l'implémentation côté client, puisqu'ils peuvent interroger un seul service pour les recherches au lieu de demander à tous les services en cours d'exécution en parallèle. userdbctl utilise également ce service de préférence, sauf si --with-nss= ou --service= sont utilisés, auquel cas un contrôle plus fin sur les services à contacter est requis.

Ajouté dans la version 245.

io.systemd.NameServiceSwitch

Ce service est (également) fourni par systemd-userdbd.service(8) et convertit les enregistrements d'utilisateurs et de groupes NSS/glibc classiques en enregistrements d'utilisateurs/groupes JSON, offrant une compatibilité ascendante complète. Utilisez --with-nss=no pour désactiver cette compatibilité, voir ci-dessus. Notez que la compatibilité est effectivement fournie dans les deux sens : nss-systemd(8) synthétisera automatiquement les enregistrements d'utilisateurs/groupes NSS/glibc classiques à partir de tous les enregistrements d'utilisateurs/groupes JSON fournis au système, ainsi l'utilisation des deux API est principalement équivalente et donne accès aux mêmes données, cependant les API NSS/glibc exposent nécessairement un ensemble plus réduit de champs seulement.

Ajouté dans la version 245.

io.systemd.DropIn

Ce service est (également) fourni par systemd-userdbd.service(8) et récupère les enregistrements d'utilisateurs/groupes JSON à partir de /etc/userdb/, /run/userdb/, /run/host/userdb/, /usr/lib/userdb/.

Ajouté dans la version 249.

Notez que userdbctl prend également en charge les recherches basées sur NSS en interne. Cela signifie que si ni io.systemd.Multiplexer ni io.systemd.NameServiceSwitch ne sont en cours d'exécution, les recherches dans les bases de données d'utilisateurs/groupes de base fonctionneront toujours.

INTÉGRATION AVEC SSH

L'outil userdbctl peut être utilisé pour rendre la liste des clés SSH autorisées potentiellement contenues dans un enregistrement d'utilisateur disponible pour le démon SSH pour l'authentification. Pour cela, configurez ce qui suit dans sshd_config(5) :

...
AuthorizedKeysCommand /usr/bin/userdbctl ssh-authorized-keys %u
AuthorizedKeysCommandUser root
...

Parfois, il est utile d'autoriser l'invocation en chaîne d'un autre programme pour lister les clés SSH autorisées. En utilisant l'option --chain, un tel outil peut être exécuté en chaîne par userdbctl ssh-authorized-keys une fois qu'une recherche est terminée, que des clés SSH aient été trouvées ou non. Exemple :

...
AuthorizedKeysCommand /usr/bin/userdbctl ssh-authorized-keys %u --chain /usr/bin/othertool %u
AuthorizedKeysCommandUser root
...

Ce qui précède interrogera d'abord la base de données userdb pour les clés SSH, puis exécutera en chaîne /usr/bin/othertool pour qu'il soit également interrogé.

CODE DE SORTIE

En cas de succès, 0 est retourné, et un code d'échec non nul sinon.

ENVIRONNEMENT

$SYSTEMD_LOG_LEVEL

Le niveau de journalisation maximal des messages émis (les messages avec un niveau de journalisation plus élevé, c'est-à-dire moins importants, seront supprimés). Prend une liste de valeurs séparées par des virgules. Une valeur peut être l'une des suivantes (par ordre d'importance décroissante) : emerg, alert, crit, err, warning, notice, info, debug, ou un entier dans la plage 0...7. Voir syslog(3) pour plus d'informations. Chaque valeur peut éventuellement être préfixée par l'un des préfixes suivants : console, syslog, kmsg ou journal suivi d'un deux-points pour définir le niveau de journalisation maximal pour cette cible de journal spécifique (par exemple, SYSTEMD_LOG_LEVEL=debug,console:info spécifie de journaliser au niveau debug sauf lors de la journalisation sur la console qui devrait être au niveau info). Notez que le niveau de journalisation maximal global a priorité sur tous les niveaux de journalisation maximaux par cible.

$SYSTEMD_LOG_COLOR

Un booléen. Si vrai, les messages écrits sur le tty seront colorés en fonction de leur priorité.

Ce paramètre n'est utile que lorsque les messages sont écrits directement sur le terminal, car journalctl(1) et d'autres outils qui affichent les journaux coloreront les messages en fonction du niveau de journalisation par eux-mêmes.

$SYSTEMD_LOG_TIME

Un booléen. Si vrai, les messages de journalisation de console seront préfixés par un horodatage.

Ce paramètre n'est utile que lorsque les messages sont écrits directement sur le terminal ou dans un fichier, car journalctl(1) et d'autres outils qui affichent les journaux ajouteront des horodatages basés sur les métadonnées de l'entrée par eux-mêmes.

$SYSTEMD_LOG_LOCATION

Un booléen. Si vrai, les messages seront préfixés par un nom de fichier et un numéro de ligne dans le code source d'où provient le message.

Notez que l'emplacement du journal est souvent joint comme métadonnées aux entrées du journal de toute façon. L'inclure directement dans le texte du message peut néanmoins être pratique lors du débogage de programmes.

$SYSTEMD_LOG_TID

Un booléen. Si vrai, les messages seront préfixés par l'ID numérique actuel du thread (TID).

Notez que ces informations sont jointes comme métadonnées aux entrées du journal de toute façon. L'inclure directement dans le texte du message peut néanmoins être pratique lors du débogage de programmes.

$SYSTEMD_LOG_TARGET

La destination des messages de journalisation. L'une des options suivantes : console (journaliser sur le tty attaché), console-prefixed (journaliser sur le tty attaché mais avec des préfixes codant le niveau de journalisation et la « facilité », voir syslog(3), kmsg (journaliser dans le tampon de journal circulaire du noyau), journal (journaliser dans le journal), journal-or-kmsg (journaliser dans le journal si disponible, et dans kmsg sinon), auto (déterminer automatiquement la cible de journal appropriée, par défaut), null (désactiver la sortie du journal).

$SYSTEMD_LOG_RATELIMIT_KMSG

S'il faut limiter la fréquence des kmsg ou non. Prend une valeur booléenne. La valeur par défaut est « true ». Si désactivé, systemd ne limitera pas la fréquence des messages écrits dans kmsg.

$SYSTEMD_PAGER, $PAGER

Paginator à utiliser lorsque --no-pager n'est pas donné. $SYSTEMD_PAGER est utilisé s'il est défini ; sinon, $PAGER est utilisé. Si ni $SYSTEMD_PAGER ni $PAGER ne sont définis, une série d'implémentations de paginators bien connues sont essayées tour à tour, y compris less(1) et more(1), jusqu'à ce que l est trouvé. Si aucune implémentation de pager n'est découverte, aucun pager n'est invoqué. Définir ces variables d'environnement à une chaîne vide ou la valeur "cat" est équivalent à passer --no-pager.

Note : si $SYSTEMD_PAGERSECURE n'est pas défini, $SYSTEMD_PAGER et $PAGER ne peuvent être utilisés que pour désactiver le pager (avec "cat" ou ""), et sont sinon ignorés.

$SYSTEMD_LESS

Remplace les options passées à less (par défaut "FRSXMK").

Les utilisateurs pourraient vouloir modifier deux options en particulier :

K

Cette option indique au pager de quitter immédiatement lorsque Ctrl+C est pressé. Pour permettre à less de gérer Ctrl+C lui-même pour revenir à l'invite de commande du pager, supprimez cette option.

Si la valeur de $SYSTEMD_LESS n'inclut pas "K", et que le pager invoqué est less, Ctrl+C sera ignoré par l'exécutable, et devra être géré par le pager.

X

Cette option indique au pager de ne pas envoyer les chaînes d'initialisation et de désinitialisation termcap au terminal. Elle est définie par défaut pour permettre à la sortie de la commande de rester visible dans le terminal même après la sortie du pager. Néanmoins, cela empêche certaines fonctionnalités du pager de fonctionner, en particulier la sortie paginée ne peut pas être défilée avec la souris.

Notez que la définition de la variable d'environnement $LESS régulière n'a aucun effet sur les invocations de less par les outils systemd.

Voir less(1) pour une discussion plus approfondie.

$SYSTEMD_LESSCHARSET

Remplace le jeu de caractères passé à less (par défaut "utf-8", si le terminal appelant est déterminé comme compatible UTF-8).

Notez que la définition de la variable d'environnement $LESSCHARSET régulière n'a aucun effet sur les invocations de less par les outils systemd.

$SYSTEMD_PAGERSECURE

Les commandes de pager courantes comme less(1), en plus de la "pagination", c'est-à-dire du défilement de la sortie, supportent l'ouverture ou l'écriture d'autres fichiers et l'exécution de commandes shell arbitraires. Lorsque des commandes sont invoquées avec des privilèges élevés, par exemple sous sudo(8) ou pkexec(1), le pager devient une limite de sécurité. Il faut veiller à ce que seuls des programmes aux fonctionnalités strictement limitées soient utilisés comme pagers, et que les fonctionnalités interactives non intentionnelles telles que l'ouverture ou la création de nouveaux fichiers ou le démarrage de sous-processus ne soient pas autorisées. Le "mode sécurisé" pour le pager peut être activé comme décrit ci-dessous, si le pager le supporte (la plupart des pagers ne sont pas écrits de manière à prendre cela en considération). Il est recommandé soit d'activer explicitement le "mode sécurisé", soit de désactiver complètement le pager en utilisant --no-pager ou PAGER=cat lorsque des utilisateurs non fiables sont autorisés à exécuter des commandes avec des privilèges élevés.

Cette option prend un argument booléen. Lorsqu'elle est définie à vrai, le "mode sécurisé" du pager est activé. En "mode sécurisé", LESSSECURE=1 sera défini lors de l'invocation du pager, ce qui demande au pager de désactiver les commandes qui ouvrent ou créent de nouveaux fichiers ou lancent de nouveaux sous-processus. Actuellement, seul less(1) est connu pour comprendre cette variable et implémenter le "mode sécurisé".

Lorsqu'elle est définie à faux, aucune limitation n'est imposée au pager. Définir SYSTEMD_PAGERSECURE=0 ou ne pas le supprimer de l'environnement hérité peut permettre à l'utilisateur d'invoquer des commandes arbitraires.

Lorsque $SYSTEMD_PAGERSECURE n'est pas défini, les outils systemd tentent de déterminer automatiquement si le "mode sécurisé" doit être activé et si le pager le supporte. Le "mode sécurisé" est activé si l'UID effectif n'est pas le même que le propriétaire de la session de connexion, voir geteuid(2) et sd_pid_get_owner_uid(3), ou lors de l'exécution sous sudo(8) ou des outils similaires ($SUDO_UID est défini [4]). Dans ces cas, SYSTEMD_PAGERSECURE=1 sera défini et les pagers qui ne sont pas connus pour implémenter le "mode sécurisé" ne seront pas utilisés du tout. Notez que cette autodétection ne couvre que les mécanismes les plus courants pour élever les privilèges et est destinée à être pratique. Il est recommandé de définir explicitement $SYSTEMD_PAGERSECURE ou de désactiver le pager.

Notez que si les variables $SYSTEMD_PAGER ou $PAGER doivent être respectées, autre que pour désactiver le pager, $SYSTEMD_PAGERSECURE doit également être défini.

$SYSTEMD_COLORS

Prend un argument booléen. Lorsqu'il est vrai, systemd et les utilitaires associés utiliseront des couleurs dans leur sortie, sinon la sortie sera monochrome. De plus, la variable peut prendre l'une des valeurs spéciales suivantes : "16", "256" pour restreindre l'utilisation des couleurs aux 16 ou 256 couleurs ANSI de base, respectivement. Ceci peut être spécifié pour remplacer la décision automatique basée sur $TERM et ce à quoi la console est connectée.

$SYSTEMD_URLIFY

La valeur doit être un booléen. Contrôle si des liens cliquables doivent être générés dans la sortie pour les émulateurs de terminaux qui supportent cela. Ceci peut être spécifié pour remplacer la décision que systemd prend en fonction de $TERM et d'autres conditions.
