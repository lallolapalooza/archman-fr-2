unistd.h(0p) Manuel du programmeur POSIX unistd.h(0p)

PROLOGUE

Cette page de manuel fait partie du Manuel du programmeur POSIX. L'implémentation Linux de cette interface peut différer (consultez la page de manuel Linux correspondante pour les détails du comportement de Linux), ou l'interface peut ne pas être implémentée sous Linux.

NOM

unistd.h — constantes et types symboliques standard

SYNOPSIS

#include <unistd.h>

DESCRIPTION

L'en-tête <unistd.h> définit diverses constantes symboliques et types, et déclare diverses fonctions. Les valeurs réelles des constantes ne sont pas spécifiées sauf indication contraire. Le contenu de cet en-tête est montré ci-dessous.

Macros de test de version

L'en-tête <unistd.h> définira les constantes symboliques suivantes. Les valeurs devront être appropriées pour être utilisées dans des directives de préprocesseur #if.

_POSIX_VERSION

Valeur entière indiquant la version de cette norme (liaison langage C) à laquelle l'implémentation est conforme. Pour les implémentations conformes à POSIX.1-2008, la valeur sera 200809L.
_POSIX2_VERSION

Valeur entière indiquant la version du volume Shell et Utilitaires de POSIX.1 à laquelle l'implémentation est conforme. Pour les implémentations conformes à POSIX.1-2008, la valeur sera 200809L. Pour les implémentations de profil qui définissent _POSIX_SUBPROFILE (voir Section 2.1.5.1, Considérations sur le sous-profilage) dans <unistd.h>, _POSIX2_VERSION peut être laissée non définie ou être définie avec la valeur -1 pour indiquer que le volume Shell et Utilitaires de POSIX.1 n'est pas pris en charge. Dans ce cas, un appel à sysconf(_SC_2_VERSION) retournera soit 200809L, soit -1, indiquant que le volume Shell et Utilitaires de POSIX.1 est ou n'est pas, respectivement, pris en charge à l'exécution.

L'en-tête <unistd.h> définira la constante symbolique suivante uniquement si l'implémentation prend en charge l'option XSI ; voir Section 2.1.4, Conformité XSI. Si elle est définie, sa valeur devra être appropriée pour être utilisée dans des directives de préprocesseur #if.

_XOPEN_VERSION

Valeur entière indiquant la version du X/Open Portability Guide à laquelle l'implémentation est conforme. La valeur sera 700.

Constantes pour les Options et Groupes d'Options

Les constantes symboliques suivantes, si définies dans <unistd.h>, auront une valeur de -1, 0 ou supérieure, sauf indication contraire ci-dessous. Pour les implémentations de profil qui définissent _POSIX_SUBPROFILE (voir Section 2.1.5.1, Considérations sur le sous-profilage) dans <unistd.h>, les constantes décrites ci-dessous comme ayant toujours une valeur supérieure à zéro n'ont pas besoin d'être définies et, si elles sont définies, peuvent avoir une valeur de -1, 0 ou supérieure. Les valeurs devront être appropriées pour être utilisées dans des directives de préprocesseur #if.

Si une constante symbolique n'est pas définie ou est définie avec la valeur -1, l'option n'est pas prise en charge pour la compilation. Si elle est définie avec une valeur supérieure à zéro, l'option sera toujours prise en charge lors de l'exécution de l'application. Si elle est définie avec la valeur zéro, l'option sera prise en charge pour la compilation et pourra ou non être prise en charge à l'exécution. Voir Section 2.1.6, Options pour plus d'informations sur les exigences de conformité de ces trois catégories de prise en charge.

Constantes symboliques d'exécution

Si l'une des constantes symboliques suivantes n'est pas définie dans l'en-tête <unistd.h>, la valeur variera en fonction du fichier auquel elle est appliquée. Si elles sont définies, elles auront des valeurs appropriées pour être utilisées dans des directives de préprocesseur #if.

Si l'une des constantes symboliques suivantes est définie avec la valeur -1 dans l'en-tête <unistd.h>, l'implémentation ne fournira pas l'option sur aucun fichier ; si l'une d'entre elles est définie avec une valeur autre que -1 dans l'en-tête <unistd.h>, l'implémentation fournira l'option sur tous les fichiers applicables.

Toutes les valeurs suivantes, qu'elles soient définies comme constantes symboliques dans <unistd.h> ou non, peuvent être interrogées concernant un fichier spécifique en utilisant les fonctions pathconf() ou fpathconf():

_POSIX_ASYNC_IO

Des opérations d'entrée ou de sortie asynchrones peuvent être effectuées pour le fichier associé.
_POSIX_PRIO_IO

Des opérations d'entrée ou de sortie prioritaires peuvent être effectuées pour le fichier associé.
_POSIX_SYNC_IO

Des opérations d'entrée ou de sortie synchronisées peuvent être effectuées pour le fichier associé.

Si les constantes symboliques suivantes sont définies dans l'en-tête <unistd.h>, elles s'appliquent aux fichiers et à tous les chemins dans tous les systèmes de fichiers de l'implémentation :

_POSIX_TIMESTAMP_RESOLUTION

La résolution en nanosecondes pour tous les horodatages de fichiers.
_POSIX2_SYMLINKS

Les liens symboliques peuvent être créés.

L'en-tête <unistd.h> doit définir NULL tel que décrit dans <stddef.h>.

L'en-tête <unistd.h> doit définir les constantes symboliques suivantes pour une utilisation avec la fonction access(). Les valeurs doivent être appropriées pour être utilisées dans des directives de préprocesseur #if.

F_OK
Tester l'existence du fichier.
R_OK
Tester la permission de lecture.
W_OK
Tester la permission d'écriture.
X_OK

Les constantes F_OK, R_OK, W_OK et X_OK ainsi que les expressions R_OK|W_OK, R_OK|X_OK, et R_OK|W_OK|X_OK doivent toutes avoir des valeurs distinctes.

USAGE APPLICATIF

POSIX.1‐2008 ne décrit que le comportement des systèmes qui revendiquent leur conformité à celui-ci. Cependant, les développeurs d'applications qui souhaitent écrire des applications qui s'adaptent à d'autres versions de cette norme (ou à des systèmes qui ne sont pas conformes à une norme POSIX) peuvent trouver utile de

o codez-les de manière à compiler conditionnellement un code différent en fonction de la valeur de _POSIX_VERSION, par exemple :

#if _POSIX_VERSION >= 200112L
/* Utiliser la fonction plus récente qui gère les fichiers volumineux. */
off_t pos=ftello(fp);
#else
/* Soit c'est une ancienne version de POSIX, soit _POSIX_VERSION n'est même pas
   défini, donc utiliser la fonction traditionnelle. */
long pos=ftell(fp);
#endif

POSIX.1‐2008 ne fait aucune tentative pour définir l'interaction binaire des applications avec le système d'exploitation sous-jacent. Cependant, les développeurs d'applications peuvent trouver utile d'interroger _SC_VERSION à l'exécution via sysconf() pour déterminer si la version actuelle du système d'exploitation prend en charge les fonctionnalités nécessaires, comme dans le fragment de programme suivant :

if (sysconf(_SC_VERSION) < 200809L) {
    fprintf(stderr, "Un système POSIX.1-2008 est requis, arrêt \n");
    exit(1);
}

Les nouvelles applications ne doivent pas utiliser _XOPEN_SHM ou _XOPEN_ENH_I18N.

JUSTIFICATION

Au fur et à mesure de l'évolution de POSIX.1‐2008, certaines options sont devenues suffisamment standardisées qu'il a été conclu que le simple fait d'exiger l'un des choix d'options était plus simple que de conserver l'option. Cependant, pour des raisons de compatibilité ascendante, les indicateurs d'options (avec des valeurs constantes requises) sont conservés.

Macros de test de version

Les développeurs de la norme ont envisagé de modifier la définition de _POSIX_VERSION et de supprimer _SC_VERSION de la spécification de sysconf() étant donné que l'utilité pour une application était jugée minimale par certains, et que l'implémentation de la fonctionnalité était potentiellement problématique. Cependant, ils ont reconnu que la prise en charge des binaires d'applications existantes est une préoccupation pour les fabricants, les développeurs d'applications et les utilisateurs des implémentations conformes à POSIX.1‐2008.

Bien que l'exemple utilisant _SC_VERSION dans la section UTILISATION DES APPLICATIONS n'offre pas le plus haut degré d'utilité imaginable au développeur d'applications ou à l'utilisateur, il est discutable qu'il soit préférable à un fichier core ou à un autre résultat tout aussi obscur. (Il est également possible pour les implémentations d'encoder et de reconnaître des binaires d'applications compilés dans divers environnements conformes à POSIX.1, et de modifier les sémantiques du système sous-jacent pour se conformer aux attentes de l'application.) Pour les raisons décrites dans les paragraphes précédents et dans la section UTILISATION DES APPLICATIONS, les développeurs de la norme ont choisi de conserver la fonctionnalité _POSIX_VERSION et _SC_VERSION.

Constantes symboliques de compilation pour les options système

POSIX.1‐2008 inclut dans certains domaines la prise en charge de la nouvelle politique adoptée concernant les options et les stubs.

Cette politique offre une flexibilité aux implémentations dans la manière dont elles prennent en charge les options. Elle spécifie également comment les applications conformes peuvent s'adapter à différentes implémentations qui prennent en charge différents ensembles d'options. Elle permet ce qui suit :

1.
Si une implémentation n'a aucun intérêt à prendre en charge une option, elle n'a pas à fournir quoi que ce soit associé à cette option au-delà de l'annonce qu'elle ne la prend pas en charge.
2.
Une implémentation peut prendre en charge une version partielle ou incompatible d'une option (en tant qu'extension non standard) tant qu'elle ne prétend pas prendre en charge l'option.
3.
Une application peut déterminer si l'option est prise en charge. Une application strictement conforme doit vérifier ce mécanisme d'annonce avant d'utiliser quoi que ce soit associé à l'option.

Cette politique a une implication importante. POSIX.1‐2008 ne peut pas dicter le comportement des interfaces associées à une option lorsque l'implémentation ne prétend pas prendre en charge l'option. En particulier, elle ne peut pas exiger qu'une fonction associée à une option non prise en charge échoue si elle ne fonctionne pas comme spécifié. Cependant, cette politique n'empêche pas une norme d'exiger que certaines fonctions soient toujours présentes, mais qu'elles échouent toujours sur certaines implémentations. La fonction setpgid() dans la norme POSIX.1‐1990, par exemple, est considérée comme appropriée.

Les normes POSIX incluent diverses options, et la prise en charge de ces options en langage C implique que l'implémentation doit fournir des types de données et des interfaces de fonction. Une application doit pouvoir découvrir si l'implémentation prend en charge chaque option.

Toute application doit considérer les trois cas suivants pour chaque option :

1.
Option jamais prise en charge.

L'implémentation annonce à la compilation que l'option ne sera jamais prise en charge. Dans ce cas, il n'est pas nécessaire que l'implémentation fournisse les types de données ou les interfaces de fonction qui sont fournis uniquement dans le cadre de l'option. L'implémentation peut fournir des types de données et des fonctions similaires à ceux définis par POSIX.1‐2008, mais il n'y a aucune garantie de comportement particulier.

2.
Option toujours prise en charge.

L'implémentation annonce à la compilation que l'option sera toujours prise en charge. Dans ce cas, tous les types de données et interfaces de fonction doivent être disponibles et fonctionner comme spécifié.

3.
Option pouvant être prise en charge ou non.

Certaines implémentations peuvent ne pas fournir de mécanisme pour spécifier la prise en charge des options à la compilation. De plus, l'implémentation peut être incapable ou refuser de spécifier la prise en charge ou la non-prise en charge à la compilation. Dans l'un ou l'autre cas, toute application qui pourrait utiliser l'option à l'exécution doit pouvoir compiler et s'exécuter. L'implémentation doit fournir, à la compilation, tous les types de données et interfaces de fonction nécessaires pour le permettre. Dans cette situation, il doit exister un mécanisme permettant à l'application d'interroger, à l'exécution, si l'option est prise en charge. Si l'application tente d'utiliser l'option lorsqu'elle n'est pas prise en charge, le résultat n'est pas spécifié, sauf indication contraire explicite dans POSIX.1‐2008.
