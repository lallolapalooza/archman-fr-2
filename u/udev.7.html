NOM

udev - Gestion dynamique des périphériques

DESCRIPTION

udev fournit au logiciel système les événements de périphérique, gère les permissions des nœuds de périphérique et peut créer des liens symboliques supplémentaires dans le répertoire /dev/, ou renommer des interfaces réseau. Le noyau attribue généralement des noms de périphérique imprévisibles basés sur l'ordre de découverte. Des liens symboliques ou des noms d'appareils réseau significatifs fournissent un moyen d'identifier de manière fiable les périphériques en fonction de leurs propriétés ou de leur configuration actuelle.

Le démon udev, systemd-udevd.service(8), reçoit directement les uevents du noyau chaque fois qu'un périphérique est ajouté ou retiré du système, ou qu'il change d'état. Lorsque udev reçoit un événement de périphérique, il compare son ensemble de règles configurées par rapport à divers attributs de périphérique pour identifier le périphérique. Les règles qui correspondent peuvent fournir des informations supplémentaires sur le périphérique à stocker dans la base de données udev ou à utiliser pour créer des noms de liens symboliques significatifs.

Toutes les informations sur les périphériques traitées par udev sont stockées dans la base de données udev et envoyées aux éventuels abonnés aux événements. L'accès à toutes les données stockées et aux sources d'événements est assuré par la bibliothèque libudev.

FICHIERS DE RÈGLES

Les règles udev sont lues à partir des fichiers situés dans les répertoires de règles système /usr/lib/udev/rules.d et /usr/local/lib/udev/rules.d, le répertoire d'exécution volatile /run/udev/rules.d et le répertoire d'administration local /etc/udev/rules.d. Tous les fichiers de règles sont triés collectivement et traités dans l'ordre lexical, indépendamment des répertoires dans lesquels ils se trouvent. Cependant, les fichiers portant des noms de fichiers identiques se remplacent mutuellement. Les fichiers dans /etc/ ont la priorité la plus élevée, les fichiers dans /run/ prennent le pas sur les fichiers portant le même nom sous /usr/. Ceci peut être utilisé pour remplacer un fichier de règles fourni par le système par un fichier local si nécessaire ; un lien symbolique dans /etc/ portant le même nom qu'un fichier de règles dans /usr/lib/, pointant vers /dev/null, désactive entièrement le fichier de règles. Les fichiers de règles doivent avoir l'extension .rules ; les autres extensions sont ignorées.

Chaque ligne du fichier de règles contient au moins une paire clé-valeur. Sauf pour les lignes vides ou les lignes commençant par "#", qui sont ignorées. Il existe deux types de clés : de correspondance et d'affectation. Si toutes les clés de correspondance correspondent à leurs valeurs, la règle est appliquée et les clés d'affectation se voient attribuer les valeurs spécifiées.

Une règle correspondante peut renommer une interface réseau, ajouter des liens symboliques pointant vers le nœud du périphérique, ou exécuter un programme spécifié dans le cadre du traitement de l'événement.

Une règle se compose d'une liste séparée par des virgules d'une ou plusieurs expressions clé-opérateur-valeur. Chaque expression a un effet distinct, en fonction de la clé et de l'opérateur utilisés.

Opérateurs

"=="

Compare pour égalité. (La clé spécifiée a la valeur spécifiée.)

"!="

Compare pour inégalité. (La clé spécifiée n'a pas la valeur spécifiée, ou la clé spécifiée n'est pas présente du tout.)

"="

Attribue une valeur à une clé. Les clés qui représentent une liste sont réinitialisées et seule cette valeur unique est attribuée.

"+="

Ajoute la valeur à une clé qui contient une liste d'entrées.

"-="

Supprime la valeur d'une clé qui contient une liste d'entrées.

Ajouté dans la version 217.

":="

Attribue une valeur à une clé de manière définitive ; interdit toute modification ultérieure.

Ajouté dans la version 247.

Valeurs

Les valeurs sont écrites sous forme de chaînes entre guillemets doubles, par exemple ("chaîne"). Pour inclure un guillemet (") dans la valeur, faites-le précéder d'une barre oblique inverse (\"). Toute autre occurrence d'une barre oblique inverse suivie d'un caractère n'est pas déséchappée. Autrement dit, "\t\n" est traité comme quatre caractères : barre oblique inverse, t minuscule, barre oblique inverse, n minuscule.

La chaîne peut être préfixée par un e minuscule (e"chaîne\n") pour marquer la chaîne comme échappée au style C, voir Séquences d'échappement en C[1]. Par exemple, e"chaîne\n" est analysé comme 7 caractères : 6 lettres minuscules et un saut de ligne. Cela peut être utile pour écrire des caractères spéciaux lorsque le pilote du noyau en a besoin.

La chaîne peut être préfixée par un i minuscule (i"chaîne") pour indiquer que la chaîne ou le modèle correspondra sans respecter la casse. Par exemple, i"foo" correspondra à "foo", "FOO", "FoO" et ainsi de suite. Le préfixe ne peut être utilisé que pour les règles de correspondance ("==") ou de non-correspondance ("!="), par exemple ATTR{foo}==i"abcd".

Veuillez noter que le caractère NUL n'est autorisé dans aucune des deux variantes de chaîne.

Clés

Les noms de clés suivants peuvent être utilisés pour faire des correspondances avec les propriétés des périphériques. Certaines clés font également correspondre les propriétés des périphériques parents dans sysfs, pas seulement le périphérique qui a généré l'événement. Si plusieurs clés qui correspondent à un périphérique parent sont spécifiées dans une seule règle, toutes ces clés doivent correspondre sur le même périphérique parent.

ACTION

Correspond au nom de l'action de l'événement.

DEVPATH

Correspond au devpath du périphérique de l'événement.

KERNEL

Correspond au nom du périphérique de l'événement.

KERNELS

Recherche le devpath vers le haut pour un nom de périphérique correspondant.

NAME

Correspond au nom d'une interface réseau. Il peut être utilisé une fois que la clé NAME a été définie dans l'une des règles précédentes.

SYMLINK

Correspond au nom d'un lien symbolique pointant vers le nœud. Il peut être utilisé une fois qu'une clé SYMLINK a été définie dans l'une des règles précédentes. Il peut y avoir plusieurs liens symboliques ; un seul doit correspondre. Si l'opérateur est "!=", le jeton renvoie vrai seulement s'il n'y a pas de lien symbolique correspondant.

SUBSYSTEM

Correspond au sous-système du périphérique de l'événement.

SUBSYSTEMS

Recherche le devpath vers le haut pour un nom de sous-système de périphérique correspondant.

DRIVER

Correspond au nom du pilote du périphérique de l'événement. N'utilisez cette clé que pour les périphériques liés à un pilote au moment où l'événement est généré.

DRIVERS

Recherche le devpath vers le haut pour un nom de pilote de périphérique correspondant.

ATTR{nom_de_fichier}

Correspond à la valeur d'un attribut sysfs du périphérique de l'événement.

Les espaces de fin dans les valeurs d'attribut sont ignorés sauf si la valeur de correspondance spécifiée contient elle-même des espaces de fin.

ATTRS{nom_de_fichier}

Recherche le devpath vers le haut pour un périphérique avec des valeurs d'attributs sysfs correspondantes. Si plusieurs correspondances ATTRS sont spécifiées, elles doivent toutes correspondre sur le même périphérique.

Les espaces de fin dans les valeurs d'attribut sont ignorés sauf si la valeur de correspondance spécifiée contient elle-même des espaces de fin.

SYSCTL{paramètre_noyau}

Correspond à la valeur d'un paramètre du noyau.

Ajouté dans la version 240.

ENV{clé}

Correspond à la valeur d'une propriété de périphérique.

CONST{clé}

Correspond à une constante système. Les clés prises en charge sont :

"arch"

Architecture du système. Voir ConditionArchitecture= dans systemd.unit(5) pour les valeurs possibles.

Ajouté dans la version 244.

"virt"

Environnement de virtualisation du système. Voir systemd-detect-virt(1) pour les valeurs possibles.

Ajouté dans la version 244.

"cvm"

Technologie de virtualisation confidentielle du système. Voir systemd-detect-virt(1) pour les valeurs possibles.

Ajouté dans la version 254.

Les clés inconnues ne correspondront jamais.

Ajouté dans la version 244.

TAG

Correspond à l'une des balises du périphérique. Il peut être utilisé une fois qu'une clé TAG a été définie dans l'une des règles précédentes.

APPELS SYSTÈME ET FONCTIONS BIBLIOTHÈQUE

Les programmes peuvent être exécutés en tant que gestionnaires d'événements, soit directement en spécifiant un nom de programme dans une règle, soit via un script de démarrage système. Les programmes exécutés en tant que gestionnaires d'événements s'exécutent dans le même processus que systemd-udevd et ont accès à toutes les variables d'environnement fournies par udev. Dans la plupart des cas, systemd-udevd attendra que le programme se termine avant de passer à l'événement suivant. Des exceptions incluent les programmes marqués comme RUN+= ou program+=.

La plupart des programmes exécutés par udev sont des utilitaires qui créent des liens symboliques, définissent des permissions, ou informent d'autres démons de l'existence d'un nouveau périphérique. Lorsque ces programmes sont exécutés, toutes les variables d'environnement udev sont disponibles et peuvent être utilisées pour déterminer le comportement du programme. Les valeurs des périphériques sont disponibles sous forme de variables d'environnement, préfixées par DEV, par exemple $DEVNAME, $DEVPATH, $SUBSYSTEM, etc.

Si un programme doit être exécuté dans un environnement isolé, le paramètre TEST_PATH= dans les règles udev peut être utilisé pour spécifier un chemin de répertoire qui sera monté dans l'espace de nommage du périphérique.

Les programmes qui doivent interagir avec la base de données udev ou recevoir des événements de périphérique peuvent utiliser la bibliothèque libudev. Elle fournit une API C pour accéder aux informations sur les périphériques, recevoir des événements de périphériques et créer ou modifier des règles udev.

Les programmes qui doivent être exécutés en tant que processus distincts qui ne dépendent pas de la présence de udevd peuvent être lancés en utilisant RUN+= ou program+=. Ces commandes s'exécutent dans un environnement séparé et ont accès aux mêmes variables d'environnement que les programmes exécutés directement. Elles ne sont pas exécutées dans le même processus que udevd, et n'attendront pas la fin de leur exécution par udevd. Si plusieurs commandes sont spécifiées, elles sont exécutées dans l'ordre où elles apparaissent dans le fichier de règles.

Notez que les noms de périphériques peuvent changer entre les exécutions, donc il est préférable de ne pas utiliser les noms de périphériques directement, mais plutôt de se fier aux liens symboliques créés par udev.

VARIABLES D'ENVIRONNEMENT

Lorsqu'un programme est exécuté par udev, les variables d'environnement suivantes sont disponibles :

ACTION

Nom de l'action de l'événement (par exemple, "add", "remove", "change").

DEVPATH

Chemin complet du périphérique dans sysfs.

SUBSYSTEM

Nom du sous-système du périphérique (par exemple, "net", "block", "input").

KERNEL

Nom du périphérique noyau.

INTERFACE

Nom de l'interface du périphérique, s'il y en a une (par exemple, "mmc-pci-0000:03:00.0").

DRIVER

Nom du pilote associé au périphérique.

SEQNUM

Numéro de séquence de l'événement uevent.

PATH

Chemin de recherche des programmes binaires.

HOME

Répertoire personnel de l'utilisateur actuel.

TEMP

Répertoire temporaire.

TMPDIR

Répertoire temporaire.

Toutes les propriétés de périphérique disponibles dans la base de données udev sont également disponibles en tant que variables d'environnement, préfixées par DEV. Par exemple, DEVNAME, DEVPATH, SUBSYSTEM, KERNEL, MAJOR, MINOR, etc. Les attributs sysfs sont également disponibles sous la forme ATTRS{nom_attribut}. Les liens symboliques sont disponibles sous la forme SYMLINK. Les étiquettes sont disponibles sous la forme TAG.

Notez que les variables d'environnement sont définies une fois que les règles sont traitées. Si une règle modifie une propriété de périphérique, cette modification sera reflétée dans les variables d'environnement disponibles pour les règles suivantes.

EXEMPLE

Les règles udev sont souvent utilisées pour renommer les interfaces réseau. Par exemple, pour renommer une interface réseau nommée "eth0" en "lan0", vous pourriez avoir une règle comme celle-ci dans un fichier dans /etc/udev/rules.d/ :

SUBSYSTEM=="net", ACTION=="add", NAME=="eth0", NAME="lan0"

Cette règle correspond aux événements d'ajout de périphériques du sous-système "net". Si le nom de l'interface est "eth0", elle sera renommée en "lan0". Les noms de réseau peuvent également être créés en fonction de l'adresse MAC ou d'autres propriétés du matériel.

Une autre utilisation courante est la création de liens symboliques pour accéder facilement aux périphériques. Par exemple, pour créer un lien symbolique nommé /dev/myusb vers une clé USB spécifique, vous pourriez avoir une règle comme celle-ci :

SUBSYSTEM=="usb", ATTR{idVendor}=="1234", ATTR{idProduct}=="5678", SYMLINK+="myusb"

Cette règle fait correspondre un périphérique USB avec un ID fournisseur de "1234" et un ID produit de "5678", et crée un lien symbolique nommé /dev/myusb pointant vers le nœud du périphérique.

Les règles peuvent également être utilisées pour définir des permissions sur les nœuds de périphérique. Par exemple, pour rendre un périphérique lisible et inscriptible par tous les utilisateurs, vous pouvez utiliser :

SUBSYSTEM=="input", MODE="0666"

Cela définit le mode du nœud de périphérique sur 0666, ce qui permet à tous les utilisateurs de lire et d'écrire dans le périphérique.

Les règles udev peuvent être combinées pour créer des configurations complexes. Il est important de tester soigneusement vos règles pour vous assurer qu'elles fonctionnent comme prévu et qu'elles ne créent pas de problèmes de sécurité ou de stabilité.

RESULT

Correspond à la chaîne renvoyée par le dernier appel de PROGRAM. Cette clé peut être utilisée dans la même règle ou dans toute règle ultérieure après un appel de PROGRAM.

La plupart des champs prennent en charge la correspondance de modèles shell glob et les modèles alternatifs. Les caractères spéciaux suivants sont pris en charge :

"*"

Correspond à zéro ou plusieurs caractères.

"?"

Correspond à n'importe quel caractère unique.

"[]"

Correspond à n'importe quel caractère unique spécifié entre crochets. Par exemple, la chaîne de modèle "tty[SR]" correspondrait soit à "ttyS", soit à "ttyR". Les plages sont également prises en charge via le caractère "-". Par exemple, pour correspondre à la plage de tous les chiffres, le modèle "[0-9]" pourrait être utilisé. Si le premier caractère suivant le "[" est un "!", tout caractère non inclus est mis en correspondance.

"|"

Sépare les modèles alternatifs. Par exemple, la chaîne de modèle "abc|x*" correspondrait soit à "abc", soit à "x*".

Ajouté dans la version 217.

Les clés suivantes peuvent se voir attribuer des valeurs :

NAME

Le nom à utiliser pour une interface réseau. Voir systemd.link(5) pour un mécanisme de plus haut niveau pour définir le nom de l'interface. Le nom d'un nœud de périphérique ne peut pas être modifié par udev, seuls des liens symboliques supplémentaires peuvent être créés.

SYMLINK

Le nom d'un lien symbolique pointant vers le nœud. Chaque règle correspondante ajoute cette valeur à la liste des liens symboliques à créer.

L'ensemble des caractères pour nommer un lien symbolique est limité. Les caractères autorisés sont "0-9A-Za-z#+-.:=@_/", les séquences de caractères UTF-8 valides et le codage hexadécimal "\x00". Tous les autres caractères sont remplacés par un caractère "_".

Plusieurs liens symboliques peuvent être spécifiés en séparant les noms par un espace. Dans le cas où plusieurs périphériques revendiquent le même nom, le lien pointe toujours vers le périphérique ayant la priorité de lien la plus élevée. Si le périphérique actuel disparaît, les liens sont réévalués et le périphérique ayant la priorité de lien suivante la plus élevée devient le propriétaire du lien. Si aucune priorité de lien n'est spécifiée, l'ordre des périphériques (et lequel d'entre eux possède le lien) est indéfini.

Les noms de liens symboliques ne doivent jamais entrer en conflit avec les noms de nœuds de périphériques par défaut du noyau, car cela entraînerait un comportement imprévisible.

OWNER, GROUP, MODE

Les permissions pour le nœud de périphérique. Chaque valeur spécifiée remplace la valeur par défaut compilée.

SECLABEL{module}

Applique le label spécifié du Linux Security Module au nœud de périphérique.

Ajouté dans la version 209.

ATTR{clé}

La valeur qui doit être écrite dans un attribut sysfs du périphérique événementiel.

SYSCTL{paramètre du noyau}

La valeur qui doit être écrite dans le paramètre du noyau.

Ajouté dans la version 220.

ENV{clé}

Définit une valeur de propriété du périphérique. Les noms de propriétés commençant par "." ne sont ni stockés dans la base de données ni exportés vers les événements ou les outils externes (exécutés, par exemple, par la clé de correspondance PROGRAM).

TAG

Attache une balise à un périphérique. Ceci est utilisé pour filtrer les événements pour les utilisateurs de la fonctionnalité de surveillance de libudev, ou pour énumérer un groupe de périphériques balisés. L'implémentation ne peut fonctionner efficacement que si peu de balises sont attachées à un périphérique. Elle est uniquement destinée à être utilisée dans des contextes avec des exigences de filtrage de périphériques spécifiques, et non comme un drapeau à usage général. Une utilisation excessive peut entraîner une gestion inefficace des événements.

RUN{type}

Spécifie un programme à exécuter après le traitement de toutes les règles pour l'événement. Avec "+=", cette invocation est ajoutée à la liste, et avec "=" ou ":=", elle remplace tout contenu précédent de la liste. Veuillez noter que les types "program" et "builtin" décrits ci-dessous partagent une liste commune, donc la suppression de la liste avec ":=" et "=" affecte les deux types.

type peut être :

"program"

Exécute un programme externe spécifié comme valeur attribuée. Si aucun chemin absolu n'est donné, le programme est censé se trouver dans /usr/lib/udev ; sinon, le chemin absolu doit être spécifié.

C'est la valeur par défaut si aucun type n'est spécifié.

"builtin"

Similaire à program, mais utilise l'un des programmes intégrés plutôt qu'un programme externe.

Ajouté dans la version 199.

Le nom du programme et les arguments suivants sont séparés par des espaces. Les guillemets simples peuvent être utilisés pour spécifier des arguments avec des espaces.

Cela ne peut être utilisé que pour des tâches de premier plan très courtes. L'exécution d'un processus événementiel pendant une longue période peut bloquer tous les événements futurs pour ce périphérique ou un périphérique dépendant.

Notez que l'exécution de programmes qui accèdent au réseau ou montent/démontent des systèmes de fichiers n'est pas autorisée dans les règles udev, en raison du bac à sable par défaut qui est appliqué à systemd-udevd.service.

Le lancement de démons ou d'autres processus de longue durée n'est pas autorisé ; les processus forgés, détachés ou non, seront inconditionnellement tués après la fin du traitement de l'événement. Afin d'activer des processus de longue durée à partir de règles udev, fournissez une unité de service et tirez-la à partir d'un périphérique udev en utilisant la propriété de périphérique SYSTEMD_WANTS. Voir systemd.device(5) pour plus de détails.

LABEL

Une étiquette nommée vers laquelle un GOTO peut sauter.

GOTO

Saute vers la prochaine LABEL avec un nom correspondant.

IMPORT{type}

Importe un ensemble de variables comme propriétés de périphérique, en fonction du type :

"program"

Exécute un programme externe spécifié comme valeur attribuée et, s'il se termine avec succès, importe sa sortie, qui doit être au format clé d'environnement. La spécification du chemin, la séparation commande/arguments et le guillemet fonctionnent comme dans RUN.

Ajouté dans la version 199.

"builtin"

Similaire à "program", mais utilise l'un des programmes intégrés plutôt qu'un programme externe.

Ajouté dans la version 199.

"file"

Importe un fichier texte spécifié comme valeur attribuée, dont le contenu doit être au format clé d'environnement.

"db"

Importe une seule propriété spécifiée comme valeur attribuée de la base de données de périphériques actuelle. Cela ne fonctionne que si la base de données est déjà peuplée par un événement antérieur.

"cmdline"

Importe une seule propriété de la ligne de commande du noyau. Pour les indicateurs simples, la valeur de la propriété est définie sur "1".

"parent"

Importe les clés stockées du périphérique parent en lisant l'entrée de la base de données du périphérique parent. La valeur attribuée à IMPORT{parent} est utilisée comme filtre pour les noms de clés à importer (avec la même correspondance de modèle shell utilisée pour les comparaisons).

Cela ne peut être utilisé que pour des tâches de premier plan très courtes. Pour plus de détails, voir RUN.

Notez que plusieurs clés IMPORT{} peuvent être spécifiées dans une règle, et "=", ":=", et "+=" ont le même effet que "==". La clé est vraie si l'importation réussit, sauf si "!=" est utilisé comme opérateur, ce qui rend la clé vraie si l'importation échoue.

OPTIONS

Options de règle et de périphérique :

link_priority=valeur

Spécifie la priorité des liens symboliques créés. Les périphériques ayant des priorités plus élevées remplacent les liens symboliques existants d'autres périphériques. La valeur par défaut est 0.

string_escape=none|replace

Lorsque "replace", les caractères potentiellement dangereux dans les chaînes attribuées à NAME, SYMLINK et ENV{key} sont remplacés. Lorsque "none", aucun remplacement n'est effectué. Lorsque non défini, le remplacement est effectué pour NAME, SYMLINK, mais pas pour ENV{key}. Par défaut non défini.

static_node=

Applique les permissions spécifiées dans cette règle au nœud de périphérique statique portant le nom spécifié. De plus, pour chaque balise spécifiée dans cette règle, crée un lien symbolique dans le répertoire /run/udev/static_node-tags/tag pointant vers le nœud de périphérique statique portant le nom spécifié. La création de nœuds de périphériques statiques est effectuée par systemd-tmpfiles avant le démarrage de systemd-udevd. Les nœuds statiques peuvent ne pas avoir de périphérique noyau correspondant ; ils sont utilisés pour déclencher le chargement automatique des modules du noyau lorsqu'ils sont accédés.

watch

Surveille le nœud de périphérique avec inotify ; lorsque le nœud est fermé après avoir été ouvert en écriture, un événement de changement est synthétisé.

nowatch

Désactive la surveillance d'un nœud de périphérique avec inotify.

db_persist

Définit le drapeau (bit collant) sur l'entrée de la base de données udev du périphérique événementiel. Les propriétés du périphérique sont alors conservées dans la base de données même lorsque udevadm info --cleanup-db est appelé. Cette option peut être utile dans certains cas (par exemple, les périphériques Device Mapper) pour conserver l'état du périphérique lors de la transition depuis initrd.

Ajouté dans la version 241.

log_level=niveau

Prend un nom de niveau de journalisation comme quo
t;debug" ou "info", ou une valeur spéciale "reset". Lorsqu'un nom de niveau de journalisation est spécifié, le niveau de journalisation maximal est changé à ce niveau. Lorsque "reset" est défini, le niveau de journalisation précédemment spécifié est révoqué. Par défaut, le niveau de journalisation du processus principal de systemd-udevd.

Cela peut être utile lors du débogage d'événements pour certains périphériques. Notez que le niveau de journalisation est appliqué lorsque la ligne contenant cette règle est traitée. Donc, pour le débogage, il est recommandé de le spécifier à un endroit plus précoce, par exemple, la première ligne de 00-debug.rules.

Exemple pour le débogage du traitement des uevents pour les interfaces réseau:

# /etc/udev/rules.d/00-debug-net.rules
SUBSYSTEM=="net", OPTIONS="log_level=debug"

Ajouté dans la version 248.

dump

Affiche l'état de l'événement en cours de traitement. Il peut être utile pour déboguer les règles udev en insérant cette option.

Ajouté dans la version 258.

Les champs ENV, GROUP, MODE, NAME, OWNER, PROGRAM, RUN, SECLABEL et SYMLINK prennent en charge les substitutions de chaînes simples. Les substitutions pour RUN sont effectuées après le traitement de toutes les règles, juste avant l'exécution du programme, permettant l'utilisation des propriétés du périphérique définies par les règles correspondantes précédentes. Pour tous les autres champs, les substitutions sont effectuées lors du traitement de la règle individuelle. Les substitutions disponibles sont:

$kernel, %k

Le nom du noyau pour ce périphérique.

$number, %n

Le numéro du noyau pour ce périphérique. Par exemple, "sda3" a le numéro de noyau 3.

$devpath, %p

Le chemin de périphérique (devpath) du périphérique.

$id, %b

Le nom du périphérique trouvé lors de la recherche du devpath vers le haut pour SUBSYSTEMS, KERNELS, DRIVERS et ATTRS.

$driver

Le nom du pilote du périphérique trouvé lors de la recherche du devpath vers le haut pour SUBSYSTEMS, KERNELS, DRIVERS et ATTRS.

$attr{file}, %s{file}

La valeur d'un attribut sysfs trouvé au niveau du périphérique où toutes les clés de la règle ont correspondu. Si le périphérique correspondant n'a pas un tel attribut, et qu'un test KERNELS, SUBSYSTEMS, DRIVERS ou ATTRS précédent a sélectionné un périphérique parent, alors l'attribut de ce périphérique parent est utilisé.

Si l'attribut est un lien symbolique, le dernier élément de la cible du lien symbolique est renvoyé comme valeur.

$env{key}, %E{key}

Une valeur de propriété du périphérique.

$major, %M

Le numéro majeur du noyau pour le périphérique.

$minor, %m

Le numéro mineur du noyau pour le périphérique.

$result, %c

La chaîne renvoyée par le programme externe demandé avec PROGRAM. Une seule partie de la chaîne, séparée par un espace, peut être sélectionnée en spécifiant le numéro de partie comme attribut : "%c{N}". Si le numéro est suivi du caractère "+", cette partie ainsi que toutes les parties restantes de la chaîne de résultat sont substituées : "%c{N+}".

$parent, %P

Le nom du nœud du périphérique parent.

$name

Le nom actuel du périphérique. S'il n'est pas modifié par une règle, c'est le nom du périphérique du noyau.

$links

Une liste séparée par des espaces des liens symboliques actuels. La valeur n'est définie que lors d'un événement de suppression ou si une règle précédente a attribué une valeur.

$root, %r

La valeur udev_root.

$sys, %S

Le point de montage de sysfs.

$devnode, %N

Le nom du nœud de périphérique.

%%

Le caractère "%" lui-même.

$$

Le caractère "$" lui-même.
