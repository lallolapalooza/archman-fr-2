NOM

upsmon.conf - Configuration du client upsmon de Network UPS Tools

DESCRIPTION

Le rôle principal de ce fichier est de définir les systèmes que upsmon(8) surveillera, et de lui indiquer comment arrêter le système en cas de besoin. Il contiendra des mots de passe, il faut donc le sécuriser. Idéalement, seul le processus upsmon devrait pouvoir le lire.

Une configuration minimale devrait inclure au moins une instruction MONITOR, MINSUPPLIES (peut être 0 si ce système surveille uniquement d'autres serveurs NUT), et POWERDOWNFLAG si cette machine est un système « primaire » connecté à l'onduleur et déclenche sa commande d'arrêt tardif en cas d'urgence.

De plus, d'autres valeurs de configuration optionnelles peuvent être définies dans ce fichier.

NOTES IMPORTANTES

• Le contenu de ce fichier doit être en ASCII pur (les codes caractères hors plage seront ignorés avec un message d'avertissement).
• Équilibrez les permissions d'accès à ce fichier (et peut-être au répertoire qui le contient) pour l'utilisateur d'exécution afin que seul upsmon puisse le lire ; l'accès en écriture n'est pas nécessaire. Il est courant d'utiliser chown root:nut et chmod 640 pour définir des permissions de fichier acceptables.
• Les paquets (et les recettes de compilation) préparent généralement un ensemble de comptes utilisateurs et de groupes pour NUT. Les builds personnalisés avec une configuration minimale pourraient même utiliser nobody:nogroup ou similaire, ce qui est intrinsèquement peu sûr.
• Sur les systèmes avec des préoccupations de sécurité supplémentaires, les pilotes NUT, le serveur de données et tout autre client de surveillance, de journalisation, etc., devraient s'exécuter sous des comptes utilisateurs distincts. Cela nécessiterait que certains démons utilisent des paramètres personnalisés de USER, GROUP, RUN_AS_USER et/ou RUN_AS_GROUP pour remplacer la seule valeur intégrée.
• Gardez à l'esprit la sécurité de toute copie de sauvegarde de ce fichier, par exemple les fichiers d'archive dans lesquels il pourrait se retrouver.

DIRECTIVES DE CONFIGURATION

DEADTIME secondes

upsmon autorise un onduleur à être absent pendant ce nombre de secondes avant de le déclarer « mort ». La valeur par défaut est 15 secondes.

upsmon nécessite qu'un onduleur fournisse des informations de statut toutes les quelques secondes (voir POLLFREQ et POLLFREQALERT) pour maintenir les choses à jour. Si la récupération du statut échoue, l'onduleur est marqué comme obsolète. S'il reste obsolète pendant plus de DEADTIME secondes, l'onduleur est déclaré mort.

Un onduleur mort dont on sait qu'il était dernièrement sur batterie est supposé être passé à une condition de batterie faible. Cela peut forcer un arrêt s'il fournit une quantité critique d'énergie à votre système. Cela semble perturbateur, mais l'alternative est de continuer dans l'oubli et de planter lorsque vous tombez en panne de courant.

Remarque : DEADTIME doit être un multiple de POLLFREQ et POLLFREQALERT. Sinon, vous aurez des onduleurs « morts » simplement parce que upsmon ne les interroge pas assez rapidement. Règle générale : prenez la plus grande des deux valeurs POLLFREQ et multipliez par 3.

FINALDELAY secondes

Lorsqu'il fonctionne en mode primaire, upsmon attend ce délai après avoir envoyé NOTIFY_SHUTDOWN pour avertir les utilisateurs. Une fois le délai écoulé, il exécute votre SHUTDOWNCMD. Par défaut, cette valeur est réglée à 5 secondes.

Si vous avez besoin de laisser vos utilisateurs faire quelque chose entre ces événements, augmentez ce nombre. N'oubliez pas qu'à ce stade, la batterie de votre onduleur est presque épuisée, ne le rendez donc pas trop long.

Alternativement, vous pouvez régler cette valeur très bas pour ne pas attendre qu'il soit temps d'arrêter. Certains onduleurs donnent peu d'avertissement pour une batterie faible et nécessiteront une valeur de 0 ici pour un arrêt sûr.


Remarque
Si FINALDELAY sur le secondaire est supérieur à HOSTSYNC sur le primaire, le primaire abandonnera l'attente que le upsmon secondaire se déconnecte.

HOSTSYNC secondes

upsmon attendra jusqu'à ce nombre de secondes en mode primaire que les secondaires se déconnectent lors d'une situation d'arrêt. Par défaut, il s'agit de 15 secondes.

Lorsqu'un onduleur devient critique (sur batterie + batterie faible, ou « FSD » : arrêt forcé), les systèmes secondaires sont censés se déconnecter et s'arrêter immédiatement. Le timer HOSTSYNC empêche le upsmon primaire de rester là indéfiniment si l'un des secondaires est bloqué.

Cette valeur est également utilisée pour empêcher les systèmes secondaires de se bloquer si le primaire ne répond pas à temps. Une fois qu'un onduleur devient critique, le secondaire attendra jusqu'à HOSTSYNC secondes que le primaire définisse le drapeau FSD. Si ce délai expire, le upsmon secondaire supposera que le primaire (ou le chemin de communication vers celui-ci) est cassé et s'arrêtera de toute façon.

Cela empêche les secondaires de s'arrêter lors d'un changement de statut de courte durée à « OB LB » et retour que les secondaires voient mais que le primaire manque.

MINSUPPLIES num

Définissez le nombre d'alimentations qui doivent recevoir du courant pour que ce système continue de fonctionner. Les ordinateurs normaux n'ont qu'une seule alimentation, donc la valeur par défaut de 1 est acceptable.

Les systèmes de type serveur, grands/coûteux, en ont généralement plus et peuvent fonctionner avec quelques-uns en moins. Le HP NetServer LH4 peut fonctionner avec 2 sur 4, par exemple, vous le réglerez donc à 2. L'idée est de maintenir la machine en fonctionnement le plus longtemps possible, n'est-ce pas ?

Évidemment, vous devez placer les alimentations redondantes sur des circuits d'onduleurs différents pour que cela ait un sens ! Voir big-servers.txt dans le sous-répertoire docs pour plus d'informations et d'idées sur l'utilisation de cette fonctionnalité.

Voir également la section sur les « valeurs de puissance » dans upsmon(8).

MONITOR system powervalue username password type

Chaque onduleur que vous devez surveiller devrait avoir une ligne MONITOR. Tous ne doivent pas alimenter le système qui exécute upsmon. Vous pouvez surveiller d'autres systèmes si vous souhaitez pouvoir envoyer des notifications sur leurs changements de statut.

Vous devez avoir au moins une directive MONITOR dans upsmon.conf.

• system est un identifiant d'onduleur. Il se présente sous cette forme :

<nom_onduleur>[@<nom_hote>[:<port>]]

Le nom d'hôte par défaut est « localhost ». Quelques exemples :

• « su700@mybox » signifie un onduleur appelé « su700 » sur un système appelé « mybox ». C'est la forme normale.
• « fenton@bigbox:5678 » est un onduleur appelé « fenton » sur un système appelé « bigbox » qui exécute upsd(8) sur le port « 5678 ».
• powervalue est un entier représentant le nombre d'alimentations que l'onduleur alimente sur ce système. La plupart des ordinateurs normaux ont une alimentation, et l'onduleur l'alimente, donc cette valeur sera de 1. Il faut un système très grand ou spécial pour avoir quelque chose de plus élevé ici.

Vous pouvez définir powervalue à 0 si vous souhaitez surveiller un onduleur qui n'alimente pas réellement ce système. Ceci est utile lorsque vous souhaitez que upsmon effectue des notifications sur les changements de statut d'un onduleur sans l'arrêter lorsqu'il devient critique.

• Le nom d'utilisateur et le mot de passe sur cette ligne doivent correspondre à une entrée dans le fichier upsd.users(5) du système serveur upsd.

Si votre nom d'utilisateur est « observer » et votre mot de passe « abcd », la ligne MONITOR pourrait ressembler à ceci (probablement sur un système secondaire distant) :

MONITOR myups@bigserver 1 observer abcd secondary

Pendant ce temps, upsd.users sur bigserver ressemblerait à ceci :

[observer]
        password = abcd
        upsmon secondary
[upswired]
        password = blah
        upsmon primary

Et la copie de upsmon sur ce bigserver s'exécuterait avec la configuration primaire :

MONITOR myups@bigserver 1 upswired blah primary
• Le type fait référence à la relation avec upsd(8). Il peut s'agir de « primary » ou « secondary ». Voir upsmon(8) pour plus d'informations sur la signification de ces modes. Le mode que vous choisissez ici va également dans le fichier upsd.users, comme vu dans l'exemple ci-dessus.

POLLFAIL_LOG_THROTTLE_MAX count

upsmon signale normalement les échecs de scrutation pour chaque appareil présents pour chaque boucle POLLFREQ (par exemple, « Données obsolètes » ou « Pilote non connecté ») au journal système comme configuré. Si vos appareils sont censés être indisponibles pendant une longue période, vous pouvez utiliser ce limiteur pour réduire la charge sur le trafic syslog et le stockage, en publiant ces messages une seule fois toutes les quelques cycles de boucle, et lorsque la condition d'erreur a changé ou a été résolue.

Une valeur négative signifie un comportement standard (journalisation à chaque boucle, effectivement identique à max=1), et une valeur zéro signifie ne jamais répéter le message (journalisation uniquement au début et à la fin/changement de l'état d'erreur).

Notez que ce limiteur ne s'applique qu'à un seul état d'erreur actif le plus récent par appareil surveillé.

NOTIFYCMD commande

upsmon appelle ceci pour envoyer des messages lorsque des événements se produisent.

Cette commande est appelée avec le texte complet du message comme un argument. La chaîne d'environnement NOTIFYTYPE contiendra la chaîne de type de ce qui a causé cet événement.

Si vous avez besoin d'utiliser upssched(8), vous devez en faire votre NOTIFYCMD en le listant ici.

Notez que ceci n'est appelé que pour les événements NOTIFY pour lesquels EXEC est défini avec NOTIFYFLAG. Voir NOTIFYFLAG ci-dessous pour plus de détails.

Faire de ceci une sorte de script shell pourrait ne pas être une mauvaise idée. Pour plus d'informations et d'idées, voir docs/scheduling.txt

N'oubliez pas que cette commande doit également être un élément dans le fichier de configuration, donc si votre commande contient des espaces, alors mettez-la entre guillemets.

NOTIFYCMD "/chemin/vers/script --foo --bar"

Ce script est exécuté en arrière-plan, c'est-à-dire que upsmon fait un fork avant d'appeler pour le démarrer. Cela signifie que votre NOTIFYCMD peut avoir plusieurs instances en cours d'exécution simultanément si beaucoup de choses se produisent en même temps. Gardez cela à l'esprit lors de la conception de notificateurs compliqués.

NOTIFYMSG type message

upsmon est livré avec un ensemble de messages prédéfinis pour divers événements. Vous pouvez les modifier si vous le souhaitez. 
NOTIFYMSG ONLINE "L'onduleur %s récupère le courant secteur"
NOTIFYMSG ONBATT "Quelqu'un a débranché %s"

Notez que %s est remplacé par l'identifiant de l'onduleur concerné.

Le message doit être un élément dans le fichier de configuration, donc s'il contient des espaces, vous devez le mettre entre guillemets.

NOTIFYMSG NOCOMM "Quelqu'un a volé l'onduleur %s"

Valeurs possibles pour type :

ONLINE

L'onduleur est de retour sur le secteur

ONBATT

L'onduleur est sur batterie

LOWBATT

L'onduleur est sur batterie et a une batterie faible (est critique)

FSD

L'onduleur est arrêté par le primaire (FSD = « Arrêt Forcé »)

COMMOK

Communication établie avec l'onduleur

COMMBAD

Communication perdue avec l'onduleur

SHUTDOWN

Le système est en cours d'arrêt

REPLBATT

La batterie de l'onduleur est défectueuse et doit être remplacée

NOCOMM

Un onduleur est indisponible (impossible de le contacter pour la surveillance)

NOPARENT

Processus parent upsmon décédé - arrêt impossible

CAL

Calibration de l'onduleur en cours

NOTCAL

Calibration de l'onduleur terminée

OFF

Onduleur administrativement OFF ou en veille

NOTOFF

Onduleur plus administrativement OFF ou en veille

BYPASS

Onduleur sur le bypass (alimenté, non protecteur)

NOTBYPASS

Onduleur plus sur le bypass

ECO

Onduleur en mode ECO ou similaire (défini et nommé par le vendeur) ; pour plus de détails, voir upsmon(8).

NOTECO

Onduleur plus en mode ECO (voir ci-dessus)

ALARM

L'onduleur a un ou plusieurs alarmes actives (vérifier ups.alarm) ; pour cette notification, le message peut contenir un deuxième espace réservé %s pour substituer la valeur actuelle de ups.alarm.

NOTALARM

L'onduleur n'est plus en état d'alarme (pas d'alarmes actives)

OVER

L'onduleur est surchargé

NOTOVER

L'onduleur n'est plus surchargé

TRIM

L'onduleur stabilise la tension entrante

NOTTRIM

L'onduleur ne stabilise plus la tension entrante

BOOST

L'onduleur amplifie la tension entrante

NOTBOOST

L'onduleur n'amplifie plus la tension entrante

OTHER

L'onduleur a au moins un jeton ups.status non classifié ; pour cette notification, le message peut contenir un deuxième espace réservé %s pour substituer la collection actuelle de tels jetons.

NOTOTHER

L'onduleur n'a plus de jetons de statut non classifiés

SUSPEND_STARTING

Le système d'exploitation passe en mode veille/suspension/hibernation

SUSPEND_FINISHED

Le système d'exploitation vient de terminer le mode veille/suspension/hibernation, désactivant les lectures obsolètes de l'onduleur pour éviter un arrêt malencontreux

NOTIFYFLAG type flag[+flag]...

Par défaut, upsmon envoie des messages globaux à tous les utilisateurs connectés (via /bin/wall) et écrit dans le syslog lorsque des événements se produisent. Sauf sous Windows où upsmon écrit uniquement dans le journal des événements par défaut. Vous pouvez changer cela.

Exemples :

NOTIFYFLAG ONLINE SYSLOG
NOTIFYFLAG ONBATT SYSLOG+WALL+EXEC

Valeurs possibles pour les drapeaux :

SYSLOG

Écrire le message dans le syslog

WALL

Écrire le message à tous les utilisateurs avec /bin/wall

EXEC

Exécuter NOTIFYCMD (voir ci-dessus) avec le message

IGNORE

Ne rien faire

Si vous utilisez IGNORE, n'utilisez aucun autre drapeau sur la même ligne.

POLLFREQ secondes

Normalement, upsmon scrute le serveur upsd(8) toutes les 5 secondes. Si cela inonde votre réseau d'activité, vous pouvez augmenter cette valeur. Vous pouvez également la diminuer pour obtenir des mises à jour plus rapides dans certains cas.

Il y a quelques inconvénients. Premièrement, si vous réglez POLLFREQ trop haut, vous pourriez manquer complètement des événements de panne de courant de courte durée. Vous risquez également de déclencher DEADTIME (voir ci-dessus) si vous utilisez un nombre très élevé.

Deuxièmement, il y a un point de rendement décroissant si vous le réglez trop bas. Bien que upsd dispose normalement de toutes les données instantanément, la plupart des pilotes ne rafraîchissent l'état de l'onduleur que toutes les 2 secondes. Scrutiner plus que cela ne vous donne généralement pas l'information plus rapidement.


Note
Ce paramètre est différent du pollfreq pris en charge par certains programmes de pilotes NUT, tels que usbhid-ups(8) (sur la fréquence à laquelle le pilote scrute un appareil particulier).

POLLFREQALERT secondes

C'est l'intervalle que upsmon attend entre les scrutations si l'un de ses onduleurs est sur batterie. Vous pouvez utiliser cela en conjonction avec POLLFREQ ci-dessus pour ralentir les scrutations pendant le comportement normal, mais obtenir des mises à jour plus rapides lorsque quelque chose de mal arrive.

Cela doit toujours être égal ou inférieur à la valeur POLLFREQ. Par défaut, il est également réglé à 5 secondes.

Les avertissements de l'entrée POLLFREQ concernant les valeurs trop hautes et trop basses s'appliquent également ici.

POWERDOWNFLAG nom_de_fichier

upsmon crée ce fichier lorsqu'il fonctionne en mode primaire lorsque l'onduleur doit être éteint. Vous devriez vérifier la présence de ce fichier dans vos scripts d'arrêt tardifs et appeler upsdrvctl shutdown s'il existe ; notez que upsmon -K peut être appelé pour cet effet, si les fichiers de configuration NUT restent lisibles à ce stade (systèmes de fichiers principalement démontés ou passés en lecture seule).

Historiquement, c'était souvent /etc/killpower mais aujourd'hui, vous pourriez le vouloir dans un système de fichiers temporaire (par exemple, sous /run ou /run/nut).

Notez que des doubles barres obliques doivent être utilisées pour les chemins Windows, par exemple C:\\Temp\\killpower (Windows moderne peut également accepter des barres obliques comme C:/Temp/killpower, mais cela peut varier).

Ceci est fait pour réinitialiser de force les systèmes secondaires, afin qu'ils ne restent pas bloqués au stade « arrêté » même si l'alimentation revient pendant le processus d'arrêt. Cela ne fonctionne généralement pas bien sur les onduleurs à contact sec qui utilisent le pilote genericups.


Attention
Le programme binaire upsmon n'a pas de valeur par défaut intégrée, donc ce paramètre DOIT être spécifié dans la configuration, afin que l'intégration d'arrêt tardif fonctionne sur le système primaire particulier !
Voir le fichier config-notes.txt dans le sous-répertoire docs pour plus d'informations. Référez-vous à la section :

"Configuration des arrêts automatiques pour les événements de batterie faible", ou référez-vous à la version en ligne.

OFFDURATION secondes

NUT prend en charge un « OFF administratif » pour les appareils d'alimentation qui peuvent être gérés pour désactiver leur charge applicative, tandis que l'onduleur ou l'ePDU reste accessible pour la surveillance et la gestion. Ce commutateur permet de retarder la propagation de cet état vers une perte connue d'alimentation (déclenchant éventuellement FSD sur les clients upsmon qui MONITOR l'appareil et qui sont en fait toujours actifs — par exemple avec plusieurs sources d'alimentation ou parce qu'ils, en tant que charge, ne sont pas réellement éteints), car lorsque certains appareils commencent la calibration de la batterie, ils signalent « OFF » pendant quelques secondes, puis signalent « CAL » après avoir commuté tous les relais d'alimentation — provoquant ainsi de faux positifs pour le déclenchement FSD de upsmon.

Une valeur négative signifie désactiver la diminution du compteur d'alimentations fonctionnelles dans de tels cas, et zéro rend l'effet de l'état « OFF » détecté immédiat. La valeur par défaut intégrée est de 30 (secondes), pour mettre un état « OFF » en vigueur (diminuer le nombre d'alimentations connues) s'il persiste pendant autant de secondes.


Note
Jusqu'à présent, nous prenons en charge l'appareil signalant un état « OFF » qui signifie généralement l'extinction complète de la charge ; un problème a été enregistré dans le traqueur de bogues pour concevoir un support similaire pour seulement certaines prises gérables ou groupes de prises.

OVERDURATION secondes

Ce réglage gère comment un onduleur surchargé doit be traité dans des situations où il ne communique pas entièrement. Comme un ASI peut être dans un état potentiellement grave, certains utilisateurs peuvent souhaiter que leurs systèmes soient arrêtés immédiatement ou après l'expiration d'un délai défini. Le réglage OVERDURATION définit ce délai (en secondes), après lequel un ASI surchargé qui ne communique pas sera considéré comme critique.

Une valeur négative signifie qu'un ASI surchargé ne sera jamais considéré comme critique (du moins pas en raison de la surcharge elle-même). Une valeur de zéro signifie que l'ASI sera immédiatement considéré comme critique lorsqu'il est surchargé et qu'il ne communique pas. La valeur par défaut intégrée est -1 (secondes).


Note
Ce réglage n'affecte que le comportement lorsqu'un ASI est à la fois surchargé et qu'il ne communique pas. Lorsque l'ASI communique normalement, une condition de surcharge peut générer des notifications mais ne déclenchera pas un arrêt du système par elle-même.

OBLBDURATION secondes

NUT génère normalement des alarmes pour un arrêt immédiat (FSD) pour les consommateurs d'un ASI connu pour être sur batterie ("OB") et atteignant le statut de batterie faible ("LB"), si c'est leur dernière source d'alimentation restante pour satisfaire leur réglage MINSUPPLIES. Dans certains cas spéciaux, les utilisateurs peuvent souhaiter retarder le déclenchement de l'alarme (en utilisant l'option OBLBDURATION) à leur discrétion et au risque d'un arrêt brutal.

Une valeur positive met l'état "OB LB" en vigueur uniquement s'il persiste pendant ce nombre de secondes. Une valeur non positive rend l'effet FSD de l'état "OB LB" détecté immédiat. La valeur par défaut intégrée est 0 (secondes).


Note
Si les options OBLBDURATION et HOSTSYNC sont toutes deux définies sur le même système client upsmon (secondaire), et que HOSTSYNC est plus court, il sera effectivement ignoré : upsmon attendra jusqu'à OBLBDURATION secondes que l'état "OB LB" disparaisse, puis la logique du client secondaire passera à un arrêt immédiat. Si le système principal déclenche un FSD sur cet ASI, cela prendra un effet de priorité encore plus élevée dès qu'il sera vu.

RBWARNTIME secondes

Lorsqu'un ASI indique que sa batterie doit être remplacée, upsmon générera un événement NOTIFY_REPLBATT. Par défaut, cela se produit toutes les 43200 secondes (12 heures).

Si vous avez besoin d'une autre valeur, définissez-la ici.

ALARMCRITICAL 0 | 1

NUT considère normalement les ASI avec des alarmes actives comme volatils, ce qui signifie qu'ils sont observés de plus près et peuvent être considérés comme critiques/morts plus tôt que dans d'autres statuts ASI réguliers. Ceci est particulièrement vrai pour les situations sans communication, où un ASI en état d'ALARME sera considéré comme perdu et des arrêts de système peuvent être déclenchés en conséquence.

Comme il n'y a pas de norme commune pour ce qui constitue une alarme, ces états d'alarme peuvent en fait être d'une nature banale et le comportement ci-dessus indésirable en raison de la possibilité d'arrêts de système non justifiés.

Lorsque ce réglage est désactivé, upsmon considérera un ASI en état d'alarme comme non volatil et le traitera comme n'importe quel autre statut.

RUN_AS_USER nom d'utilisateur

upsmon se scinde normalement en deux processus, en gardant une petite partie qui reste la propriété de root pour initier l'arrêt du système en appelant SHUTDOWNCMD le cas échéant, et exécute la majeure partie des tâches de surveillance sous un autre ID utilisateur après avoir abandonné les privilèges root. Sur la plupart des systèmes personnalisés, cela signifie qu'il s'exécute en tant que "personne", car c'est la valeur par défaut au moment de la compilation ; les paquets livrent souvent un utilisateur "nut" ou "ups" pour exécuter les démons de service NUT.

Le problème est que le "personne" par défaut du système ne peut pas lire votre fichier upsmon.conf, car par défaut il est installé de manière à ce que seul root puisse l'ouvrir (car ce fichier peut contenir des données sensibles comme des identifiants de serveur de données NUT distants). Cela signifie que vous ne pourrez pas recharger le fichier de configuration, car il sera indisponible pour la partie non privilégiée du démon upsmon.

La solution consiste à créer un nouvel utilisateur juste pour upsmon, puis à le faire s'exécuter en tant que cet utilisateur. Il peut s'agir du même compte que celui utilisé pour les pilotes NUT ou le serveur de données, mais ce n'est pas obligatoire. Sur les systèmes ayant des préoccupations accrues en matière de sécurité et de séparation des privilèges, nous suggérons "nutmon", mais vous pouvez utiliser n'importe quoi qui n'est pas déjà pris sur votre système. Créez simplement un utilisateur régulier sans privilèges spéciaux et avec un mot de passe impossible.

Ensuite, dites à upsmon de s'exécuter en tant que cet utilisateur, et rendez upsmon.conf lisible par lui. Vos rechargements fonctionneront, et votre fichier de configuration restera sécurisé.

Ce fichier ne doit pas être inscriptible par l'utilisateur upsmon, car il serait possible d'exploiter une faille, de modifier SHUTDOWNCMD par quelque chose de malveillant, puis d'attendre le redémarrage d'upsmon. Ainsi, vous créeriez généralement un groupe pour les démons NUT (dont l'utilisateur serait membre) et accorderiez à ce groupe un accès en lecture seule aux fichiers de configuration appartenant à root.

Cela dit, d'autres variantes peuvent être possibles - par exemple, exécuter tout upsmon en tant qu'un seul processus initialement démarré et détenu par nut et appeler un script d'arrêt préfixé par sudo, pfexec ou d'autres outils RBAC. Cela ajoute cependant plus de "pièces mobiles" et de fragilité (par exemple, les paramètres sudoers peuvent être dans LDAP, et ce serveur pourrait être indisponible lors de l'arrêt lorsque le rack est à moitié éteint, juste au moment où vous en avez besoin ici), et n'est pas disponible sur toutes les plateformes - ainsi, de telles configurations sont quelque chose que les utilisateurs explorent par eux-mêmes jusqu'à présent (nous accueillerions des messages sur le Wiki NUT ou des liens vers des blogs cependant).

SHUTDOWNCMD commande

upsmon exécute cette commande lorsque le système doit être arrêté. S'il s'agit d'un secondaire, il le fera immédiatement chaque fois que la valeur globale de puissance actuelle tombe en dessous de la valeur MINSUPPLIES ci-dessus.

Lorsque upsmon est un primaire, il permettra aux secondaires de se déconnecter avant de lancer la procédure d'arrêt locale.

Notez que la commande doit être un seul élément dans le fichier de configuration. Si votre commande d'arrêt contient des espaces, mettez-la entre guillemets pour la maintenir ensemble, c'est-à-dire :

SHUTDOWNCMD "/sbin/shutdown -h +0"

SHUTDOWNEXIT booléen|nombre

Après avoir lancé l'arrêt, ce démon upsmon doit-il lui-même se terminer ? Ce faisant, les systèmes secondaires NUT peuvent informer le primaire NUT qu'il peut procéder à son propre arrêt et éventuellement indiquer à l'ASI de couper l'alimentation de la charge. ("Oui" par défaut)

Certains systèmes "secondaires" avec des charges de travail qui prennent un temps considérable pour s'arrêter (par exemple, des machines virtuelles ou de grandes bases de données) peuvent bénéficier de signaler (en se déconnectant du serveur de données) qu'ils sont prêts pour que le système "primaire" commence son propre arrêt et éventuellement pour que l'ASI coupe l'alimentation - pas dès qu'ils ont déclenché leur propre arrêt, mais plus tard (par exemple, lorsque le service upsmon est arrêté APRÈS les charges de travail plus lourdes).

Notez que la capacité réelle d'achever un tel arrêt dépend de l'autonomie restante de la batterie au moment où l'état d'alimentation de l'ASI est considéré comme critique et que les arrêts commencent. Vous devrez peut-être également ajuster HOSTSYNC sur le primaire NUT pour qu'il soit suffisamment long pour que ces secondaires arrêtent leurs services. En pratique, il peut être utile d'étudier des moyens de déclencher les arrêts plus tôt sur ces systèmes, par exemple en configurant l'intégration upssched, ou un pilote ups factice avec des remplacements pour des déclencheurs de batterie.charge ou de batterie.runtime plus stricts que ceux utilisés par le reste de vos serveurs.

Cette option prend en charge les chaînes de style booléen (oui/activé/vrai ou non/désactivé/faux) ou des nombres pour définir un délai (en secondes) entre l'appel de SHUTDOWNCMD et la fin du démon. Zéro signifie une sortie immédiate (par défaut), les valeurs négatives signifient ne jamais se terminer de sa propre initiative.

CERTPATH fichier de certificat ou base de données

Lorsqu'il est compilé avec le support SSL, vous pouvez entrer le chemin du certificat ici.

Avec NSS :

Les certificats sont stockés dans une base de données dédiée (données divisées en 3 fichiers). Spécifiez le chemin du répertoire de la base de données.

Avec OpenSSL :

Répertoire contenant les certificats CA au format PEM, utilisés pour vérifier le certificat serveur présenté par le serveur upsd. Les fichiers contiennent chacun un certificat CA. Les fichiers sont recherchés par la valeur de hachage du sujet CA, qui doit donc être disponible.

CERTIDENT nom du certificat mot de passe de la base de données

Lorsqu'il est compilé avec le support SSL avec NSS, vous pouvez spécifier le nom du certificat à récupérer de la base de données pour s'authentifier et le mot de passe requis pour accéder à la clé privée liée au certificat.

Note
Assurez-vous d'encadrer le "nom du certificat" entre guillemets doubles si vous utilisez une valeur contenant des espaces.

CERTHOST nom d'hôte nom du certificat certverify forcessl

Lorsqu'il est compilé avec le support SSL avec NSS, vous pouvez spécifier la directive de sécurité pour chaque serveur que vous pouvez contacter.

Chaque entrée mappe le nom du serveur avec le nom de certificat attendu et des drapeaux indiquant si le certificat serveur est vérifié et si la connexion doit être sécurisée.


Note
Assurez-vous d'encadrer le "nom du certificat" entre guillemets doubles si vous utilisez une valeur contenant des espaces.

CERTVERIFY 0 | 1

Lorsqu'il est compilé avec le support SSL, faites en sorte que upsmon vérifie toutes les connexions avec des certificats.

Sans cela, il n'y a aucune garantie que l'upsd est le bon hôte. L'activation de cela réduit considérablement le risque d'attaques de type homme du milieu. Cela force effectivement l'utilisation du SSL, alors n'utilisez pas cela à moins que tous vos hôtes upsd ne soient prêts pour le SSL et que leurs certificats soient en ordre.

Lorsqu'il est compilé avec le support NSS du SSL, peut être remplacé pour un hôte spécifié avec une directive CERTHOST.

FORCESSL 0 | 1

Lorsqu'il est compilé avec le support SSL, spécifiez qu'une connexion sécurisée doit être utilisée pour communiquer avec upsd.

Si vous n'utilisez pas *CERTVERIFY 1*, cela garantira au moins que personne ne pourra espionner vos sessions sans de gros efforts. La définition de cela fera abandonner les connexions par upsmon si l'upsd distant ne prend pas en charge le SSL, alors ne l'utilisez pas à moins qu'ils n'aient tous ce protocole activé.

Lorsqu'il est compilé avec le support NSS du SSL, peut être remplacé pour un hôte spécifié avec une directive CERTHOST.

NAME

upsmon.conf — configuration file for upsmon

DESCRIPTION

The upsmon.conf file is used to configure the upsmon daemon, the monitoring component of the NUT (Network UPS Tools) package.

This file contains directives that control how upsmon behaves, including which UPS systems it should monitor, how it should react to power events, and how it should communicate with the upsd daemon.

IMPORTANT NOTES

All directives are case-sensitive.

Directives can be placed in any order in the configuration file.

Lines starting with a # or ; character are considered comments and are ignored by upsmon.

Blank lines are ignored.

The upsmon daemon must be restarted for any changes made to this file to take effect, unless otherwise noted.

CONFIGURATION DIRECTIVES

MONITOR
This directive specifies a UPS system or an availability group to monitor. The syntax is:
MONITOR ups_name@upsd_host [delay_start [rem_delay]]
  • ups_name is the name of the UPS as registered with upsd.
  • upsd_host is the hostname or IP address of the upsd server. Use localhost or omit this parameter if upsd is running on the same machine as upsmon.
  • delay_start (optional) is the number of seconds upsmon should wait before starting to monitor this UPS. Defaults to 0.
  • rem_delay (optional) is the number of seconds upsmon should wait before attempting to bring the UPS back online after a power failure event. Defaults to 30 seconds.
POLLFREQ
Specifies the interval (in seconds) between checks of the UPS status by upsmon. The default is 30 seconds.
POLLJITTER
Adds a random delay (up to this value in seconds) to the polling interval. This helps to distribute the load on the upsd server. The default is 30 seconds.
HOSTSYNC
Specifies the interval (in seconds) between synchronization checks between multiple upsmon instances monitoring the same UPS. This is used to ensure that all monitors are reporting the same status. The default is 15 seconds.
DEADTIME
Specifies the time (in seconds) after which a UPS is considered dead if it has not responded to polls. If a UPS is considered dead, upsmon will stop trying to communicate with it. The default is 15 seconds.
OFFDELAY
Specifies the time (in seconds) to wait before shutting down the system after the UPS has gone on battery and the remaining battery time is below the configured shutdown threshold. The default is 20 seconds.
SHUTDOWNCMD
Specifies the command to execute when the system is to be shut down. This command should typically initiate a graceful system shutdown. The default is usually the system's shutdown command (e.g., /sbin/shutdown -h +1). This directive is often not needed as upsmon typically uses the system's init system to perform the shutdown.
RUNCMDS
Specifies commands to run when certain power events occur. The syntax is:
RUNCMDS command_path [argument ...]
  • command_path is the path to the script or executable to run.
  • argument are optional arguments to pass to the command.

Supported events are:

ONBATT
Executed when the UPS goes on battery power.
OFFBATT
Executed when the UPS returns to AC power.
LOWBATT
Executed when the battery is low.
OVERLOAD
Executed when the UPS is overloaded.
BATTDISCH
Executed when the battery is discharging.
BATTRECHG
Executed when the battery is recharging.
CAPFSD
Executed when the UPS capacity is full and charging is finished.
REGTEST
Executed during a regular test.
CONFIG
Executed when the UPS configuration changes.
FIRMWARE
Executed when the UPS firmware is updated.
USERDEF
Executed for any user-defined event.
TIMER
Executed periodically based on the TIMERVAL directive.
TIMERVAL
Specifies the interval (in seconds) for the TIMER event in RUNCMDS. The default is 60 seconds.
NOTIFYCMD
Specifies the command to execute for sending notifications. This command is typically used to send email or other alerts. The syntax is:
NOTIFYCMD command_path [argument ...]
NOTIFYMSG
Specifies the message to be sent with the notification. The message can contain variables that will be expanded by upsmon. The syntax is:
NOTIFYMSG event_name "message text"

Supported event names are the same as for RUNCMDS.

DEBUG
Sets the debugging level for upsmon. Higher values result in more verbose logging. The default is 0.
SYSADMINCMD
Specifies a command to send administrative messages. This is typically used for sending commands to the system administrator.
FINAL ফেCT
This directive, when set to 1, causes upsmon to wait for the UPS to be fully discharged before initiating a shutdown. This is generally not recommended as it risks data loss.
LOCALCMD
This directive is used to specify commands that should be executed locally on the machine where upsmon is running, based on specific UPS events. The syntax is:
LOCALCMD event_name command_path [argument ...]

This is similar to RUNCMDS but is intended for actions that are specific to the local system.

RBTHOLD
When set to 1, this directive prevents the system from shutting down if the UPS returns to AC power after having gone on battery, even if the remaining battery time is low. The default is 0.
MINSUPPLIES
This directive specifies the minimum number of power supplies required for the system to operate normally. If the number of available power supplies drops below this value, upsmon may trigger a shutdown or other actions. The default is 1.
BIGPOWEROFF
When set to 1, this directive enables a more aggressive shutdown procedure in case of critical power failure. This might involve shutting down non-essential services before initiating a full system shutdown. The default is 0.
REMOTEPOLLFREQ
This directive, for remote upsd servers, specifies the polling frequency in seconds. The default is 30 seconds.
REMOTEPOLLJITTER
Similar to POLLJITTER but for remote polling. The default is 30 seconds.
REMOTEHOSTSYNC
Similar to HOSTSYNC but for remote servers. The default is 15 seconds.
REMOTEDEADTIME
Similar to DEADTIME but for remote servers. The default is 15 seconds.
REMOTEPOLLCMD
Specifies a command to poll remote UPS systems. This is usually not needed as upsmon handles remote polling internally.
MAXLOGSIZE
Specifies the maximum size (in bytes) of the log file. If the log file exceeds this size, it will be rotated. A value of 0 means no limit. The default is 0.
SYSLOG
Enables or disables logging to syslog. Use YES to enable and NO to disable. The default is YES.
DEBUG_MIN
This directive controls the minimum debug level for logging. Any log message with a level equal to or higher than DEBUG_MIN will be logged. This allows for fine-grained control over the verbosity of the logs, especially when combined with the DEBUG directive. For example, setting DEBUG_MIN 3 will log messages with a debug level of 3 or higher. The value can be an integer ranging from 0 (no debug messages) to 9 (maximum debug messages). For example, setting this to a high value like 5 or n (it is recommended to comment it away or set the minimum to explicit zero when done, to avoid huge journals and I/O system abuse). Keep in mind that for this run-time tuning, the DEBUG_MIN value present in reloaded configuration files is applied instantly and overrides any previously set value, from file or CLI options, regardless of older logging level being higher or lower than the newly found number; a missing (or commented away) value however does not change the previously active logging verbosity.
