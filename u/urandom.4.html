random(4) Manuel des pilotes de périphériques random(4)

NOM

random, urandom - Périphériques de source de nombres aléatoires du noyau

SYNTAXE

#include <linux/random.h>
int ioctl(fd, RNDrequest, param);

DESCRIPTION

Les fichiers spéciaux de caractères /dev/random et /dev/urandom (présents depuis Linux 1.3.30) fournissent une interface au générateur de nombres aléatoires du noyau. Le fichier /dev/random a le numéro de périphérique majeur 1 et le numéro de périphérique mineur 8. Le fichier /dev/urandom a le numéro de périphérique majeur 1 et le numéro de périphérique mineur 9.

Le générateur de nombres aléatoires collecte le bruit ambiant des pilotes de périphériques et d'autres sources dans un pool d'entropie. Le générateur maintient également une estimation du nombre de bits de bruit dans le pool d'entropie. À partir de ce pool d'entropie, des nombres aléatoires sont créés.

Linux 3.17 et versions ultérieures fournissent l'interface plus simple et plus sûre getrandom(2) qui ne nécessite pas de fichiers spécifiques ; consultez la page de manuel getrandom(2) pour plus de détails.

Lors de la lecture, le périphérique /dev/urandom renvoie des octets aléatoires en utilisant un générateur de nombres pseudo-aléatoires amorcé à partir du pool d'entropie. Les lectures de ce périphérique ne se bloquent pas (c'est-à-dire que le CPU n'est pas cédé), mais peuvent entraîner un délai appréciable lors de la demande de grandes quantités de données.

Lors de la lecture au début du démarrage, /dev/urandom peut retourner des données avant que le pool d'entropie ne soit initialisé. Si cela vous préoccupe dans votre application, utilisez plutôt getrandom(2) ou /dev/random.

Le périphérique /dev/random est une interface héritée qui remonte à une époque où les primitives cryptographiques utilisées dans l'implémentation de /dev/urandom n'étaient pas largement fiables. Il ne renverra des octets aléatoires que dans la limite du nombre estimé de bits de bruit frais dans le pool d'entropie, en se bloquant si nécessaire. /dev/random convient aux applications qui nécessitent une grande qualité d'aléatoire et qui peuvent se permettre des délais indéterminés.

Lorsque le pool d'entropie est vide, les lectures de /dev/random se bloqueront jusqu'à ce que du bruit ambiant supplémentaire soit collecté. Depuis Linux 5.6, l'indicateur O_NONBLOCK est ignoré car /dev/random ne se bloquera plus sauf pendant le processus de démarrage précoce. Dans les versions antérieures, si open(2) est appelé pour /dev/random avec l'indicateur O_NONBLOCK, une lecture read(2) subséquente ne se bloquera pas si le nombre d'octets demandés n'est pas disponible. Au lieu de cela, les octets disponibles sont retournés. Si aucun octet n'est disponible, read(2) retournera -1 et errno sera défini à EAGAIN.

L'indicateur O_NONBLOCK n'a aucun effet lors de l'ouverture de /dev/urandom. Lors de l'appel à read(2) pour le périphérique /dev/urandom, les lectures jusqu'à 256 octets renverront autant d'octets que demandé et ne seront pas interrompues par un gestionnaire de signaux. Les lectures avec un tampon dépassant cette limite peuvent renvoyer moins d'octets que demandé ou échouer avec l'erreur EINTR, si interrompues par un gestionnaire de signaux.

Depuis Linux 3.16, une read(2) depuis /dev/urandom renverra au maximum 32 Mo. Une read(2) depuis /dev/random renverra au maximum 512 octets (340 octets avant Linux 2.6.12).

Écrire sur /dev/random ou /dev/urandom mettra à jour le pool d'entropie avec les données écrites, mais cela n'entraînera pas un compte d'entropie plus élevé. Cela signifie que cela affectera le contenu lu depuis les deux fichiers, mais cela n'accélérera pas les lectures depuis /dev/random.

Utilisation

L'interface /dev/random est considérée comme une interface héritée, et /dev/urandom est préférée et suffisante dans tous les cas d'utilisation, à l'exception des applications qui nécessitent de l'aléatoire pendant le démarrage précoce ; pour ces applications, getrandom(2) doit être utilisé à la place, car il se bloquera jusqu'à ce que le pool d'entropie soit initialisé.

Si un fichier de semence est sauvegardé lors des redémarrages comme recommandé ci-dessous, la sortie est cryptographiquement sécurisée contre les attaquants sans accès root local dès son rechargement dans la séquence de démarrage, et parfaitement adéquate pour les clés de session de chiffrement réseau. (Toutes les distributions Linux majeures ont sauvegardé le fichier de semence lors des redémarrages depuis 2000 au moins.) Comme les lectures depuis /dev/random peuvent se bloquer, les utilisateurs voudront généralement l'ouvrir en mode non bloquant (ou effectuer une lecture avec délai d'attente), et fournir une forme de notification utilisateur si l'entropie souhaitée n'est pas immédiatement disponible.

Configuration

Si votre système n'a pas déjà /dev/random et /dev/urandom créés, ils peuvent être créés avec les commandes suivantes :


mknod -m 666 /dev/random c 1 8
mknod -m 666 /dev/urandom c 1 9
chown root:root /dev/random /dev/urandom

Lorsqu'un système Linux démarre sans beaucoup d'interaction opérateur, le pool d'entropie peut être dans un état assez prévisible. Cela réduit la quantité réelle de bruit dans le pool d'entropie en dessous de l'estimation. Afin de contrer cet effet, il est utile de conserver les informations du pool d'entropie entre les arrêts et les démarrages. Pour ce faire, ajoutez les lignes à un script approprié qui est exécuté pendant la séquence de démarrage du système Linux :


echo "Initialisation du générateur de nombres aléatoires..."
random_seed=/var/run/random-seed
# Conserver une semence aléatoire du démarrage au démarrage
# Charger puis sauvegarder l'ensemble du pool d'entropie
if [ -f $random_seed ]; then
    cat $random_seed >/dev/urandom
else
    touch $random_seed
fi
chmod 600 $random_seed
poolfile=/proc/sys/kernel/random/poolsize
[ -r $poolfile ] && bits=$(cat $poolfile) || bits=4096
bytes=$(expr $bits / 8)
dd if=/dev/urandom of=$random_seed count=1 bs=$bytes

Ajoutez également les lignes suivantes dans un script approprié qui est exécuté pendant l'arrêt du système Linux :


# Conserver une semence aléatoire de l'arrêt au démarrage
# Sauvegarder l'ensemble du pool d'entropie
echo "Sauvegarde de la semence aléatoire..."
random_seed=/var/run/random-seed
touch $random_seed
chmod 600 $random_seed
poolfile=/proc/sys/kernel/random/poolsize
[ -r $poolfile ] && bits=$(cat $poolfile) || bits=4096
bytes=$(expr $bits / 8)
dd if=/dev/urandom of=$random_seed count=1 bs=$bytes

Dans les exemples ci-dessus, nous supposons Linux 2.6.0 ou plus récent, où /proc/sys/kernel/random/poolsize renvoie la taille du pool d'entropie en bits (voir ci-dessous).

Interfaces /proc

Les fichiers du répertoire /proc/sys/kernel/random (présents depuis Linux 2.3.16) fournissent des informations supplémentaires sur le périphérique /dev/random :

entropy_avail
Ce fichier en lecture seule donne l'entropie disponible, en bits. Ce sera un nombre dans la plage 0 à 4096.
poolsize
Ce fichier donne la taille du pool d'entropie. La sémantique de ce fichier varie selon les versions du noyau :
Linux 2.4 :
Ce fichier donne la taille du pool d'entropie en octets. Normalement, ce fichier aura la valeur 512, mais il est accessible en écriture et peut être modifié à n'importe quelle valeur pour laquelle un algorithme est disponible. Les choix sont 32, 64, 128, 256, 512, 1024 ou 2048.
Linux 2.6 et versions ultérieures :
Ce fichier est en lecture seule et donne la taille du pool d'entropie en bits. Il contient la valeur 4096.
read_wakeup_threshold
Ce fichier contient le nombre de bits d'entropie requis pour réveiller les processus qui dorment en attendant de l'entropie de /dev/random. La valeur par défaut est 64.
write_wakeup_threshold
Ce fichier contient le nombre de bits d'entropie en dessous duquel nous réveillons les processus qui font un select(2) ou un poll(2) pour un accès en écriture à /dev/random. Ces valeurs peuvent être modifiées en écrivant dans les fichiers.
uuid
boot_id
Ces fichiers en lecture seule contiennent des chaînes aléatoires comme 6fd5a44b-35f4-4ad4-a9

urandom(4) — manpages

NAME

urandom — non-blocking random number generator

SYNOPSIS

#include <unistd.h>

- rw files associated with /dev/random

- rw files associated with /dev/urandom

DESCRIPTION

These are character special files that provide an interface to the kernel's random number generator. The primary difference between them is how they behave when the generator's entropy pool is low.

When reads are performed on these files, the kernel generates random numbers. The numbers are derived from environmental noise sources (hardware interrupts, mouse movements, keyboard input, etc.).

The difference between random(4) and urandom(4) is in the blocking behavior:

  • /dev/random: When the entropy pool is low, reads from /dev/random will block until enough entropy has been gathered.
  • /dev/urandom: This device also provides random numbers, but it will not block. When the entropy pool is low, it uses a pseudo-random number generator (PRNG) seeded with the contents of the entropy pool. This PRNG is designed to be cryptographically secure.

The kernel maintains an internal entropy pool. Writes to these devices are generally ignored, but can be used to seed the pool if the user has root privileges. Specifically, writes to /dev/random (or /dev/urandom) are treated as input entropy, but they do not increment the entropy count. The entropy count is available via the RNDGETENTCNT ioctl request.

The RNDADDTOENTCNT ioctl request allows adding to or subtracting from the entropy count. This is used when an external source of entropy is added.

The RNDADDENTROPY ioctl request adds entropy directly to the pool, and increments the entropy count. This differs from writing to the device, which does not increment the entropy count.

The RNDZAPENTCNT and RNDCLEARPOOL ioctl requests reset the entropy count and clear the pool.

The RNDGETPOOL ioctl request was removed in Linux 2.6.9.

The primary difference between reading from /dev/random and /dev/urandom is when the entropy pool is depleted. The former is generated afresh for each read, the latter was generated once.

ioctl(2) interface

The following ioctl(2) requests are defined on file descriptors connected to either /dev/random or /dev/urandom. All requests performed will interact with the input entropy pool impacting both /dev/random and /dev/urandom. The CAP_SYS_ADMIN capability is required for all requests except RNDGETENTCNT.

RNDGETENTCNT
Retrieve the entropy count of the input pool, the contents will be the same as the entropy_avail file under proc. The result will be stored in the int pointed to by the argument.
RNDADDTOENTCNT
Increment or decrement the entropy count of the input pool by the value pointed to by the argument.
RNDGETPOOL
Removed in Linux 2.6.9.
RNDADDENTROPY
Add some additional entropy to the input pool, incrementing the entropy count. This differs from writing to /dev/random or /dev/urandom, which only adds some data but does not increment the entropy count. The following structure is used:

struct rand_pool_info {
    int    entropy_count;
    int    buf_size;
    __u32  buf[0];
};

Here entropy_count is the value added to (or subtracted from) the entropy count, and buf is the buffer of size buf_size which gets added to the entropy pool.
RNDZAPENTCNT
RNDCLEARPOOL
Zero the entropy count of all pools and add some system data (such as wall clock) to the pools.

FILES

/dev/random
/dev/urandom

NOTES

For an overview and comparison of the various interfaces that can be used to obtain randomness, see random(7).

BUGS

During early boot time, reads from /dev/urandom may return data prior to the entropy pool being initialized.

SEE ALSO

mknod(1), getrandom(2), random(7)
