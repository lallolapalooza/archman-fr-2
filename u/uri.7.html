uri(7) Manuel d'informations diverses uri(7)

NOM

uri, url, urn - identifiant uniforme de ressource (URI), y compris une URL ou une URN

SYNTAXE

URI = [ URIabsolue | URIrelative ] [ "#" fragment ]
URIabsolue = schéma ":" ( partie_hiérarchique | partie_opaque )
URIrelative = ( chemin_réseau | chemin_absolu | chemin_relatif ) [ "?" requête ]
schéma = "http" | "ftp" | "gopher" | "mailto" | "news" | "telnet" | "file" | "ftp" | "man" | "info" | "whatis" | "ldap" | "wais" | ...
partie_hiérarchique = ( chemin_réseau | chemin_absolu ) [ "?" requête ]
chemin_réseau = "//" autorité [ chemin_absolu ]
chemin_absolu = "/" segments_chemin
chemin_relatif = segment_relatif [ chemin_absolu ]

DESCRIPTION

Un Identifiant Uniforme de Ressource (URI) est une courte chaîne de caractères identifiant une ressource abstraite ou physique (par exemple, une page web). Une Localisation Uniforme de Ressource (URL) est un URI qui identifie une ressource par son mécanisme d'accès principal (par exemple, sa "localisation" réseau), plutôt que par son nom ou un autre attribut de cette ressource. Un Nom Uniforme de Ressource (URN) est un URI qui doit rester globalement unique et persistant, même lorsque la ressource cesse d'exister ou devient indisponible.

Les URI sont le moyen standard de nommer les destinations de liens hypertexte pour des outils tels que les navigateurs web. La chaîne "http://www.kernel.org" est une URL (et donc aussi un URI). Beaucoup de personnes utilisent le terme URL de manière informelle comme synonyme d'URI (bien que techniquement les URLs soient un sous-ensemble des URIs).

Les URIs peuvent être absolus ou relatifs. Un identifiant absolu fait référence à une ressource indépendamment du contexte, tandis qu'un identifiant relatif fait référence à une ressource en décrivant la différence par rapport au contexte actuel. Dans une référence de chemin relatif, les segments de chemin complets "." et ".." ont des significations spéciales : "le niveau de hiérarchie actuel" et "le niveau au-dessus de ce niveau de hiérarchie", respectivement, tout comme dans les systèmes de type UNIX. Un segment de chemin contenant un caractère deux-points ne peut pas être utilisé comme premier segment d'un chemin d'URI relatif (par exemple, "this:that"), car il serait confondu avec un nom de schéma ; précédez de tels segments avec ./ (par exemple, "./this:that"). Notez que les descendants de MS-DOS (par exemple, Microsoft Windows) remplacent les deux-points des noms de périphériques par la barre verticale ("|") dans les URIs, donc "C:" devient "C|".

Un identifiant de fragment, s'il est inclus, fait référence à une partie nommée spécifique (fragment) d'une ressource ; le texte après un '#' identifie le fragment. Un URI commençant par '#' fait référence à ce fragment dans la ressource actuelle.

UTILISATION

Il existe de nombreux schémas d'URI différents, chacun avec des règles et des significations spécifiques supplémentaires, mais ils sont intentionnellement conçus pour être aussi similaires que possible. Par exemple, de nombreux schémas d'URL permettent à l'autorité d'avoir le format suivant, appelé ici un serveur_ip (les crochets indiquent ce qui est optionnel) :

serveur_ip = [utilisateur [ : motdepasse ] @ ] hôte [ : port]

Ce format vous permet d'insérer éventuellement un nom d'utilisateur, un utilisateur plus un mot de passe, et/ou un numéro de port. L'hôte est le nom de l'ordinateur hôte, soit son nom tel que déterminé par DNS, soit une adresse IP (nombres séparés par des points). Ainsi, l'URI http://fred:fredpassword@example.com:8080/ se connecte à un serveur web sur l'hôte example.com en tant que fred (en utilisant fredpassword) via le port 8080. Évitez d'inclure un mot de passe dans un URI autant que possible en raison des nombreux risques de sécurité liés à un mot de passe écrit. Si l'URL fournit un nom d'utilisateur mais pas de mot de passe, et que le serveur distant en demande un, le programme interprétant l'URL devrait en demander un à l'utilisateur.

Voici quelques-uns des schémas les plus courants utilisés sur les systèmes de type UNIX et compris par de nombreux outils. Notez que de nombreux outils utilisant des URIs ont également des schémas internes ou spécialisés ; consultez la documentation de ces outils pour obtenir des informations sur ces schémas.

http - Serveur Web (HTTP)

http://serveur_ip/chemin
http://serveur_ip/chemin?requête

Ceci est une URL accédant à un serveur web (HTTP). Le port par défaut est 80. Si le chemin fait référence à un répertoire, le serveur web choisit quoi retourner ; généralement, s'il existe un fichier nommé "index.html" ou "index.htm", son contenu est retourné ; sinon, une liste des fichiers du répertoire courant (avec les liens appropriés) est générée et retournée. Un exemple est http://lwn.net.

Une requête peut être donnée dans le format archaïque "isindex", consistant en un mot ou une phrase et n'incluant pas de signe égal (=). Une requête peut également être dans le format plus long "GET", qui a une ou plusieurs entrées de requête de la forme clé=valeur séparées par le caractère esperluette (&). Notez que la clé peut être répétée plus d'une fois, bien qu'il appartienne au serveur web et à ses programmes d'application de déterminer si cela a un sens. Il y a une interaction malheureuse avec HTML/XML/SGML et le format de requête GET ; lorsque de tels URIs avec plus d'une clé sont intégrés dans des documents SGML/XML (y compris HTML), l'esperluette (&) doit être réécrite comme &amp;. Notez que toutes les requêtes n'utilisent pas ce format ; les formes plus grandes peuvent être trop longues pour être stockées en tant qu'URI, elles utilisent donc un mécanisme d'interaction différent (appelé POST) qui n'inclut pas les données dans l'URI. Voir la spécification Common Gateway Interface à http://www.w3.org/CGI pour plus d'informations.

ftp - Protocole de Transfert de Fichiers (FTP)

ftp://serveur_ip/chemin

Ceci est une URL accédant à un fichier via le protocole de transfert de fichiers (FTP). Le port par défaut (pour le contrôle) est 21. Si aucun nom d'utilisateur n'est inclus, le nom d'utilisateur "anonymous" est fourni, et dans ce cas de nombreux clients fournissent comme mot de passe l'adresse email Internet du demandeur. Un exemple est <ftp://ftp.is.co.za/rfc/rfc1808.txt>.

gopher - Serveur Gopher

gopher://serveur_ip/type_gopher sélecteur
gopher://serveur_ip/type_gopher sélecteur%09recherche
gopher://serveur_ip/type_gopher sélecteur%09recherche%09chaine_gopher+

Le port Gopher par défaut est 70. type_gopher est un champ d'un seul caractère pour indiquer le type Gopher de la ressource à laquelle l'URL fait référence. Le chemin entier peut également être vide, auquel cas le délmitateur "/" est également optionnel, et le type_gopher est par défaut "1".

sélecteur est la chaîne de sélection Gopher. Dans le protocole Gopher, les chaînes de sélection Gopher sont une séquence d'octets qui peuvent contenir tous les octets sauf 09 hexadécimal (HT ASCII ou tabulation), 0A hexadécimal (caractère LF ASCII) et 0D (caractère CR ASCII).

mailto - Adresse email

mailto:adresse-email

Ceci est une adresse email, généralement de la forme nom@nom_hote. Voir mailaddr(7).

news - Newsgroupe ou message News

news:nom-newsgroupe
news:identifiant-message

Un nom-newsgroupe est un nom hiérarchique délimité par des points, tel que « comp.infosystems.www.misc ». Si <nom-newsgroupe> est « * » (comme dans <news:*>), il est utilisé pour se référer à « toutes les newsgroupes disponibles ». Un exemple est <news:comp.lang.ada>.

Un identifiant-message correspond à l'identifiant de message de RFC 1036 de l'IETF, sans les guillemets « < » et « > » ; il prend la forme unique@nom_de_domaine_complet. Un identifiant de message peut être distingué d'un nom de newsgroupe par la présence du caractère « @ ».

telnet - Connexion Telnet

telnet://ip_serveur/

Le schéma d'URL Telnet est utilisé pour désigner des services textuels interactifs qui peuvent être accédés par le protocole Telnet. Le caractère « / » final peut être omis. Le port par défaut est 23. Un exemple est <telnet://melvyl.ucop.edu/>.

file - Fichier normal

file://ip_serveur/segments_chemin
file:segments_chemin

Ceci représente un fichier ou un répertoire accessible localement. Dans un cas spécial, ip_serveur peut être la chaîne « localhost » ou une chaîne vide ; ceci est interprété comme « la machine à partir de laquelle l'URL est interprétée ». Si le chemin mène à un répertoire, la visionneuse doit afficher le contenu du répertoire avec des liens vers chaque élément contenu ; toutes les visionneuses ne font pas cela actuellement. KDE prend en charge les fichiers générés via l'URL <file:/cgi-bin>. Si le fichier donné n'est pas trouvé, les développeurs de navigateurs peuvent vouloir essayer d'étendre le nom de fichier via le globbing de noms de fichiers (voir glob(7) et glob(3)).

Le deuxième format (par exemple, <file:/etc/passwd>) est un format correct pour faire référence à un fichier local. Cependant, les anciennes normes ne permettaient pas ce format, et certains programmes ne le reconnaissent pas comme une URI. Une syntaxe plus portable consiste à utiliser une chaîne vide comme nom de serveur, par exemple, <file:///etc/passwd> ; cette forme fait la même chose et est facilement reconnue comme une URI par les analyseurs de motifs et les anciens programmes. Notez que si vous voulez vraiment dire « commencer à partir de l'emplacement actuel », ne spécifiez pas du tout le schéma ; utilisez une adresse relative comme <../test.txt>, ce qui a pour effet secondaire d'être indépendante du schéma. Un exemple de ce schéma est <file:///etc/passwd>.

man - Documentation des pages man

man:nom-commande
man:nom-commande(section)

Ceci fait référence aux pages de référence man (manuelles en ligne) locales. Le nom de la commande peut être suivi facultativement d'une parenthèse et d'un numéro de section ; voir man(7) pour plus d'informations sur la signification des numéros de section. Ce schéma d'URI est unique aux systèmes de type UNIX (comme Linux) et n'est actuellement pas enregistré par l'IETF. Un exemple est <man:ls(1)>.

info - Documentation des pages info

info:nom-fichier-virtuel
info:nom-fichier-virtuel#nom-nœud
info:(nom-fichier-virtuel)
info:(nom-fichier-virtuel)nom-nœud

Ce schéma fait référence aux pages de référence info en ligne (générées à partir de fichiers texinfo), un format de documentation utilisé par des programmes tels que les outils GNU. Ce schéma d'URI est unique aux systèmes de type UNIX (comme Linux) et n'est actuellement pas enregistré par l'IETF. À l'heure actuelle, GNOME et KDE diffèrent dans leur syntaxe d'URI et n'acceptent pas la syntaxe de l'autre. Les deux premiers formats sont le format GNOME ; dans les noms de nœuds, tous les espaces sont écrits sous forme de tirets bas. Les deux derniers formats sont le format KDE ; les espaces dans les noms de nœuds doivent être écrits sous forme d'espaces, même si cela est interdit par les normes URI. On espère qu'à l'avenir, la plupart des outils comprendront tous ces formats et accepteront toujours les tirets bas pour les espaces dans les noms de nœuds. Dans GNOME et KDE, si le format sans nom de nœud est utilisé, le nom de nœud est supposé être « Top ». Des exemples du format GNOME sont <info:gcc> et <info:gcc#G++_et_GCC>. Des exemples du format KDE sont <info:(gcc)> et <info:(gcc)G++ et GCC>.

whatis - Recherche de documentation

whatis:chaîne

Ce schéma recherche dans la base de données de courtes descriptions (une ligne) de commandes et renvoie une liste de descriptions contenant cette chaîne. Seules les correspondances de mots entiers sont renvoyées. Voir whatis(1). Ce schéma d'URI est unique aux systèmes de type UNIX (comme Linux) et n'est actuellement pas enregistré par l'IETF.

ghelp - Documentation d'aide GNOME

ghelp:nom-application

Ceci charge l'aide GNOME pour l'application donnée. Notez que peu de documentation existe actuellement dans ce format.

ldap - Lightweight Directory Access Protocol

ldap://hôteport
ldap://hôteport/
ldap://hôteport/dn
ldap://hôteport/dn?attributs
ldap://hôteport/dn?attributs?portée
ldap://hôteport/dn?attributs?portée?filtre
ldap://hôteport/dn?attributs?portée?filtre?extensions

Ce schéma prend en charge les requêtes au Lightweight Directory Access Protocol (LDAP), un protocole pour interroger un ensemble de serveurs pour des informations organisées hiérarchiquement (telles que des personnes et des ressources informatiques). Voir RFC 2255 pour plus d'informations sur le schéma d'URL LDAP. Les composants de cette URL sont :

hôteport
le serveur LDAP à interroger, écrit comme un nom d'hôte suivi éventuellement d'un deux-points et du numéro de port. Le port LDAP par défaut est le port TCP 389. S'il est vide, le client détermine quel serveur LDAP utiliser.
dn
le Nom Distingué LDAP, qui identifie l'objet de base de la recherche LDAP (voir RFC 2253 section 3).
attributs
une liste d'attributs séparés par des virgules à renvoyer ; voir RFC 2251 section 4.1.5. S'il est omis, tous les attributs doivent être renvoyés.
portée
spécifie la portée de la recherche, qui peut être l'une des valeurs suivantes : « base » (pour une recherche d'objet de base), « one » (pour une recherche à un niveau), ou « sub » (pour une recherche dans un sous-arbre). Si la portée est omise, « base » est supposé.
filtre
spécifie le filtre de recherche (sous-ensemble des entrées à renvoyer). S'il est omis, toutes les entrées doivent être renvoyées. Voir RFC 2254 section 4.
extensions
une liste de paires type=valeur séparées par des virgules, où la partie =valeur peut être omise pour les options qui n'en ont pas besoin. Une extension préfixée par un « ! » est critique (doit être prise en charge pour être valide), sinon elle est non critique (facultative).

Les requêtes LDAP sont plus faciles à expliquer par l'exemple. Voici une requête qui demande à ldap.itd.umich.edu des informations sur l'Université du Michigan aux États-Unis :

ldap://ldap.itd.umich.edu/o=University%20of%20Michigan,c=US

Pour obtenir simplement son attribut d'adresse postale, demandez :

ldap://ldap.itd.umich.edu/o=University%20of%20Michigan,c=US?postalAddress

Pour demander à host.com au port 6666 des informations sur la personne dont le nom commun (cn) est « Babs Jensen » à l'Université du Michigan, demandez :

ldap://host.com:6666/o=University%20of%20Michigan,c=US??sub?(cn=Babs%20Jensen)

wais - Wide Area Information Servers

wais://hôteport/base-de-données
wais://hôteport/base-de-données?recherche
wais://hôteport/base-de-données/type-wais/chemin-wais

Ce schéma désigne une base de données WAIS, une recherche ou un document (voir RFC 1625 de l'IETF pour plus d'informations sur WAIS). Hôteport est le nom d'hôte, suivi éventuellement d'un deux-points et du numéro de port (le numéro de port par défaut est 210).

La première forme désigne une base de données WAIS pour la recherche. La deuxième forme désigne une recherche particulière dans la base de données WAIS base-de-données. La troisième forme désigne un document particulier dans une base de données WAIS à récupérer. type-wais est la désignation WAIS du type de l'objet, et chemin-wais est l'identifiant de document WAIS.

autres schémas

Il existe de nombreux autres schémas d'URI. La plupart des outils qui acceptent les URI prennent en charge un ensemble d'URI internes (par exemple, Mozilla a le schéma about: pour les informations internes, et le navigateur d'aide GNOME a le schéma toc: pour divers points de départ). Il existe de nombreux schémas qui ont été définis mais qui ne sont pas aussi largement utilisés actuellement (par exemple, prospero). Le schéma nntp: est déprécié au profit du schéma news:. Les URN doivent être pris en charge par le schéma urn:, avec un espace de noms hiérarchique (par exemple, urn:ietf:... identifierait les documents de l'IETF) ; à l'heure actuelle, les URN ne sont pas largement implémentés. Tous les outils ne prennent pas en charge tous les schémas.

Encodage des caractères

Les URI utilisent un nombre limité de caractères afin qu'ils puissent être saisis et utilisés dans diverses situations.

Les caractères suivants sont réservés, c'est-à-dire qu'ils peuvent apparaître dans une URI mais leur utilisation est limitée à leur objectif réservé (les données conflictuelles doivent être échappées avant de former l'URI) :


; / ? : @ & = + $ ,

Les caractères non réservés peuvent être inclus dans une URI. Les caractères non réservés incluent les lettres latines majuscules et minuscules, les chiffres décimaux, et l'ensemble limité de ponctuations et symboles suivant :


- _ . ! ~ * ' ( )

Tous les autres caractères doivent être échappés. Un octet échappé est encodé sous forme de triplet de caractères, composé du caractère pourcentage « % » suivi des deux chiffres hexadécimaux représentant le code de l'octet (vous pouvez utiliser des lettres majuscules ou minuscules pour les chiffres hexadécimaux). Par exemple, un espace doit être échappé en « %20 », un caractère de tabulation en « %09 », et le « & » en « %26 ». Parce que le caractère pourcentage « % » toujours

l'indicateur d'échappement, il doit être échappé sous la forme « %25 ». Il est courant de représenter les espaces par le symbole plus (+) dans le texte d'une requête ; cette pratique n'est pas uniformément définie dans les RFC pertinentes (qui recommandent %20 à la place), mais tout outil acceptant des URI avec du texte de requête doit être préparé à les gérer. Une URI est toujours affichée sous sa forme « échappée ».

Les caractères non réservés peuvent être échappés sans modifier la sémantique de l'URI, mais cela ne doit pas être fait à moins que l'URI ne soit utilisée dans un contexte qui n'autorise pas le caractère non échappé à apparaître. Par exemple, « %7e » est parfois utilisé à la place de « ~ » dans le chemin d'une URL HTTP, mais les deux sont équivalents pour une URL HTTP.

Pour les URI qui doivent gérer des caractères en dehors de la jeux de caractères US ASCII, la spécification HTML 4.01 (section B.2) et la RFC IETF 3986 (dernier paragraphe de la section 2.5) recommandent l'approche suivante :

(1)
traduire les séquences de caractères en UTF-8 (RFC IETF 3629) — voir utf-8(7) — puis
(2)
utiliser le mécanisme d'échappement d'URI, c'est-à-dire, utiliser l'encodage %HH pour les octets non sécurisés.

Écriture d'une URI

Lorsqu'elles sont écrites, les URI doivent être placées entre guillemets doubles (par exemple, « http://www.kernel.org »), entourées d'accolades (par exemple, http://lwn.net), ou placées sur une ligne à elles seules. Attention à ceux qui utilisent des guillemets doubles : ne déplacez jamais de ponctuation superflue (comme le point final d'une phrase ou la virgule d'une liste) à l'intérieur d'une URI, car cela modifierait la valeur de l'URI. Utilisez plutôt des accolades, ou passez à un système de guillemets qui n'inclut jamais de caractères superflus à l'intérieur des guillemets. Ce dernier système, appelé le système de guillemets « nouveau » ou « logique » par « Hart's Rules » et le « Oxford Dictionary for Writers and Editors », est la pratique privilégiée en Grande-Bretagne et dans diverses langues européennes. Les anciens documents suggéraient d'insérer le préfixe « URL: » juste avant l'URI, mais cette forme n'a jamais pris.

La syntaxe des URI a été conçue pour être sans ambiguïté. Cependant, à mesure que les URI sont devenues courantes, les médias traditionnels (télévision, radio, journaux, panneaux d'affichage, etc.) ont de plus en plus utilisé des références URI abrégées composées uniquement des parties autorité et chemin de la ressource identifiée (par exemple, <www.w3.org/Addressing>). Ces références sont principalement destinées à l'interprétation humaine plutôt qu'à la machine, avec l'hypothèse que des heuristiques basées sur le contexte sont suffisantes pour compléter l'URI (par exemple, les noms d'hôte commençant par « www » ont probablement un préfixe d'URI « http:// » et ceux commençant par « ftp » probablement un préfixe « ftp:// »). De nombreuses implémentations client résolvent heuristiquement ces références. Ces heuristiques peuvent changer avec le temps, en particulier lorsque de nouveaux schémas sont introduits. Étant donné qu'une URI abrégée a la même syntaxe qu'un chemin d'URL relatif, les références URI abrégées ne peuvent pas être utilisées là où les URI relatives sont autorisées, et ne peuvent être utilisées que lorsqu'il n'y a pas de base définie (comme dans les boîtes de dialogue). N'utilisez pas d'URI abrégées comme liens hypertextes à l'intérieur d'un document ; utilisez le format standard tel que décrit ici.

NOTES

Tout outil acceptant les URI (par exemple, un navigateur Web) sur un système Linux devrait pouvoir gérer (directement ou indirectement) tous les schémas décrits ici, y compris les schémas man: et info:. Leur gestion en invoquant un autre programme est acceptable et même encouragée.

Techniquement, le fragment ne fait pas partie de l'URI.

Pour savoir comment intégrer des URI (y compris des URL) dans un format de données, voir la documentation de ce format. HTML utilise le format <A HREF="uri"> texte </A>. Les fichiers Texinfo utilisent le format @uref{uri}. Man et mdoc ont la macro UR récemment ajoutée, ou incluent simplement l'URI dans le texte (les visualiseurs devraient pouvoir détecter :// comme faisant partie d'une URI).

Les environnements de bureau GNOME et KDE varient actuellement dans les URI qu'ils acceptent, en particulier dans leurs navigateurs d'aide respectifs. Pour lister les pages de manuel, GNOME utilise <toc:man> tandis que KDE utilise <man:(index)>, et pour lister les pages info, GNOME utilise <toc:info> tandis que KDE utilise <info:(dir)> (l'auteur de cette page man préfère l'approche KDE ici, bien qu'un format plus régulier serait encore mieux). En général, KDE utilise <file:/cgi-bin/> comme préfixe pour un ensemble de fichiers générés. KDE préfère la documentation en HTML, accessible via <file:/cgi-bin/helpindex>. GNOME préfère le schéma ghelp pour stocker et trouver la documentation. Aucun des deux navigateurs ne gère les références file: aux répertoires au moment de la rédaction, ce qui rend difficile de faire référence à un répertoire entier avec une URI consultable. Comme mentionné ci-dessus, ces environnements diffèrent dans la manière dont ils gèrent le schéma info:, probablement la variation la plus importante. On s'attend à ce que GNOME et KDE convergent vers des formats d'URI communs, et une future version de cette page man décrira le résultat convergé. Les efforts pour aider à cette convergence sont encouragés.

Sécurité

Une URI ne représente pas en soi une menace pour la sécurité. Il n'y a aucune garantie générale qu'une URL, qui à un moment donné localisait une ressource donnée, continuera de le faire. Il n'y a pas non plus de garantie qu'une URL ne localisera pas une ressource différente à un moment ultérieur ; une telle garantie ne peut être obtenue qu'auprès des personnes contrôlant cet espace de noms et la ressource en question.

Il est parfois possible de construire une URL telle qu'une tentative d'exécution d'une opération apparemment inoffensive, comme la récupération d'une entité associée à la ressource, déclenchera en fait une opération distante potentiellement dommageable. L'URL non sécurisée est généralement construite en spécifiant un numéro de port autre que celui réservé au protocole réseau en question. Le client contacte à l'insu un site qui exécute en réalité un protocole différent. Le contenu de l'URL contient des instructions qui, une fois interprétées selon ce protocole, déclenchent une opération inattendue. Un exemple a été l'utilisation d'une URL gopher pour envoyer un message involontaire ou d'usurpation via un serveur SMTP.

Il faut faire preuve de prudence lors de l'utilisation de toute URL spécifiant un numéro de port autre que celui par défaut pour le protocole ; en particulier, lorsqu'il s'agit d'un numéro dans l'espace réservé.

Il faut prendre garde lorsqu'une URI contient des délimiteurs échappés pour un protocole donné (par exemple, les caractères CR et LF pour les protocoles telnet) à ce que ceux-ci ne soient pas déséchappés avant transmission. Cela pourrait violer le protocole, mais éviterait que ces caractères soient utilisés pour simuler une opération ou un paramètre supplémentaire dans ce protocole, ce qui pourrait entraîner une opération distante inattendue et potentiellement dommageable.

Il est clairement déconseillé d'utiliser une URI contenant un mot de passe destiné à rester secret. En particulier, il est fortement déconseillé d'utiliser un mot de passe dans le composant « userinfo » d'une URI, sauf dans les rares cas où le paramètre « mot de passe » est destiné à être public.

BOGUES

La documentation peut être placée dans divers endroits, il n'existe donc actuellement pas de bon schéma d'URI pour la documentation en ligne générale dans des formats arbitraires. Les références de type <file:///usr/doc/ZZZ> ne fonctionnent pas, car différentes distributions et exigences d'installation locales peuvent placer les fichiers dans des répertoires différents (il peut être dans /usr/doc, ou /usr/local/doc, ou /usr/share, ou ailleurs). De plus, le répertoire ZZZ change généralement lorsqu'une version change (bien que le globage de noms de fichiers puisse partiellement compenser cela). Enfin, l'utilisation du schéma file: ne prend pas facilement en charge les personnes qui chargent dynamiquement la documentation à partir d'Internet (au lieu de charger les fichiers sur un système de fichiers local). Un futur schéma d'URI pourrait être ajouté (par exemple, « userdoc: ») pour permettre aux programmes d'inclure des références croisées vers une documentation plus détaillée sans avoir à connaître l'emplacement exact de cette documentation. Alternativement, une future version de la spécification du système de fichiers pourrait spécifier les emplacements des fichiers de manière suffisante pour que le schéma file: puisse localiser la documentation.

De nombreux programmes et formats de fichiers n'incluent pas de moyen d'incorporer ou d'implémenter des liens à l'aide d'URI.

De nombreux programmes ne peuvent pas gérer tous ces différents formats d'URI ; il devrait exister un mécanisme standard pour charger une URI arbitraire qui détecte automatiquement l'environnement de l'utilisateur (par exemple, texte ou graphique, environnement de bureau, préférences utilisateur locales et outils en cours d'exécution) et invoque le bon outil pour chaque URI.
