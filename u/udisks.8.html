UDISKS(8) Administration système UDISKS(8)

NOM

udisks - Gestionnaire de disques

DESCRIPTION

udisks fournit des interfaces pour énumérer et effectuer des opérations sur les disques et les périphériques de stockage. Toute application (y compris celles sans privilèges) peut accéder au démon udisksd(8) via le nom org.freedesktop.UDisks2 sur le bus de messages système[1]. En plus de l'API D-Bus, une bibliothèque, libudisks2, est également fournie. Cette bibliothèque peut être utilisée depuis C/C++ et tout langage de haut niveau avec le support de GObjectIntrospection[2], comme Javascript et Python. udisks n'est impliqué qu'indirectement dans ce qui est affiché dans l'interface utilisateur concernant les périphériques et les objets.

CONTRÔLE D'ACCÈS

Par défaut, les utilisateurs connectés dans des sessions actives sont autorisés à effectuer des opérations (par exemple, monter, déverrouiller ou modifier) sur les périphériques attachés au siège (seat) de leur session. Le contrôle d'accès est granulaire et basé sur polkit(8), voir le chapitre « Vérifications d'autorisation » dans la documentation d'udisks pour plus d'informations. Notez que l'option x-udisks-auth peut être utilisée dans les fichiers /etc/fstab et /etc/crypttab pour spécifier qu'une autorisation supplémentaire est requise pour monter ou déverrouiller le périphérique (nécessitant généralement l'authentification de l'utilisateur en tant qu'administrateur).

CONFIGURATION DES DISQUES

Au démarrage et lorsqu'un lecteur est connecté, udisksd(8) appliquera la configuration stockée dans le fichier /etc/udisks2/IDENTIFIANT.conf où IDENTIFIANT est la valeur de la propriété Drive:Id pour le lecteur. Si le fichier change sur le disque, son nouveau contenu sera également appliqué au lecteur. Typiquement, les utilisateurs ou les administrateurs n'auront jamais besoin de modifier les fichiers de configuration des lecteurs car ils sont gérés efficacement par des applications graphiques telles que gnome-disks(1). La modification manuelle des fichiers de configuration est cependant supportée — le format du fichier est un simple format « .ini » (voir la Spécification des entrées de bureau[3] pour la syntaxe exacte). De nouveaux groupes et clés pourront être ajoutés à l'avenir.

GROUPE ATA

Le groupe ATA concerne les paramètres qui s'appliquent aux lecteurs utilisant l'ensemble de commandes ATA. Les clés suivantes sont supportées :

StandbyTimeout

Le délai d'attente de veille. Une valeur de zéro signifie « les délais sont désactivés » : le périphérique n'entrera pas automatiquement en mode veille. Les valeurs de 1 à 240 spécifient des multiples de 5 secondes, donnant des délais de 5 secondes à 20 minutes. Les valeurs de 241 à 251 spécifient de 1 à 11 unités de 30 minutes, donnant des délais de 30 minutes à 5,5 heures. Une valeur de 252 signifie un délai de 21 minutes. Une valeur de 253 définit une période de délai définie par le fournisseur entre 8 heures et 12 heures, et la valeur 254 est réservée. 255 est interprété comme 21 minutes et 15 secondes. Notez que certains anciens lecteurs peuvent avoir des interprétations très différentes de ces valeurs. Ceci est similaire à l'option -S dans hdparm(8).

APMLevel

Le niveau de gestion avancée de l'énergie. Une faible valeur signifie une gestion agressive de l'énergie et une valeur élevée signifie de meilleures performances. Les réglages possibles vont de 1 à 127 (qui autorisent l'arrêt du disque) et de 128 à 254 (qui n'autorisent pas l'arrêt du disque). Le niveau le plus élevé de gestion de l'énergie est atteint avec un réglage de 1, et les performances d'E/S les plus élevées avec un réglage de 254. Une valeur de 255 peut être utilisée pour désactiver complètement la gestion avancée de l'énergie sur le disque (tous les disques ne supportent pas la désactivation, mais la plupart le font). Ceci est similaire à l'option -B dans hdparm(8).

AAMLevel

Le niveau de gestion acoustique automatique. La plupart des disques durs modernes ont la capacité de réduire la vitesse des mouvements de tête pour diminuer leur bruit. Les valeurs possibles sont comprises entre 0 et 254. 128 est le réglage le plus silencieux (et donc le plus lent) et 254 le plus rapide (et le plus bruyant). Certains disques n'ont que deux niveaux (silencieux / rapide), tandis que d'autres peuvent avoir des niveaux différents entre 128 et 254. Pour le moment, la plupart des disques ne supportent que 3 options : désactivé, silencieux et rapide. Celles-ci ont été assignées aux valeurs 0, 128 et 254 respectivement, mais l'espace des entiers a été intégré pour une expansion future, si cela change. Ceci est similaire à l'option -M dans hdparm(8).

WriteCacheEnabled

Une valeur booléenne spécifiant si le cache d'écriture doit être activé ou désactivé. Les valeurs valides pour cette clé sont « true » et « false ». Ceci est similaire à l'option -W dans hdparm(8). Cette clé a été ajoutée en 2.1.

ReadLookaheadEnabled

Une valeur booléenne spécifiant si la prélecture de lecture doit être activée ou désactivée. Les valeurs valides pour cette clé sont « true » et « false ». Ceci est similaire à l'option -A dans hdparm(8). Cette clé a été ajoutée en 2.6.0.

INFORMATIONS SUR LE PÉRIPHÉRIQUE

udisks repose sur des versions récentes de udev(7) et du noyau Linux. Les propriétés de périphérique influentes dans la base de données udev incluent :

UDISKS_SYSTEM

Si défini, cela remplace la valeur de la propriété HintSystem.

UDISKS_IGNORE

Si défini, cela remplace la valeur de la propriété HintIgnore.

UDISKS_AUTO

Si défini, cela remplace la valeur de la propriété HintAuto.

UDISKS_CAN_POWER_OFF

Si défini, cela remplace la valeur de la propriété CanPowerOff.

UDISKS_NAME

Le nom à utiliser pour le périphérique lors de sa présentation dans une interface utilisateur. Ceci correspond à la propriété HintName.

UDISKS_ICON_NAME

L'icône à utiliser pour le périphérique lors de sa présentation dans une interface utilisateur. Si définie, le nom doit respecter la spécification des thèmes d'icônes freedesktop.org[4]. Ceci correspond à la propriété HintIconName.

UDISKS_SYMBOLIC_ICON_NAME

L'icône à utiliser pour le périphérique lors de sa présentation dans une interface utilisateur à l'aide d'une icône symbolique. Si définie, le nom doit respecter la spécification des thèmes d'icônes freedesktop.org[4]. Ceci correspond à la propriété HintSymbolicIconName.

UDISKS_FILESYSTEM_SHARED

Si défini à 1, le système de fichiers sur le périphérique sera monté dans un répertoire partagé (par exemple, /media/NomVolume) au lieu d'un répertoire privé (par exemple, /run/media/$USER/NomVolume) lorsque la méthode Filesystem.Mount() est traitée.

ID_SEAT

Le siège physique auquel le périphérique est attaché. S'il n'est pas défini ou s'il est défini à une chaîne vide, « seat0 » (le premier siège) est supposé.

ID_ATA_SMART_ACCESS

Remplace la méthode d'accès pour la récupération des données SMART. Les valeurs valides incluent : sat16, sat12, linux-ide, sunplus, jmicron, none et auto (par défaut). Spécifiez none pour éviter toute E/S, dans ce cas la propriété SmartUpdated sera toujours égale à « 0 ».

STABILITÉ DE L'API

udisks garantit une API D-Bus stable au sein de la même version majeure et cette garantie s'étend également à la bibliothèque côté client libudisks2. De plus, plusieurs versions majeures d'udisks peuvent être installées et fonctionner en même temps bien que l'interopérabilité puisse être limitée - par exemple, un périphérique monté à l'aide de l'API udisks N.x peut nécessiter une autorisation supplémentaire si l'on tente de le démonter via l'API (N-1).x.

Les développeurs d'udisks n'anticipent pas de casser l'API mais se réservent le droit de le faire et si cela se produit, promettent d'incrémenter la version majeure et de s'assurer que la nouvelle version majeure d'udisks est parallélisable avec toute version majeure plus ancienne. Cependant, notez que les programmes, les pages de manuel et d'autres artefacts peuvent changer de nom (par exemple, adopter un suffixe « 2 ») pour faire place à la prochaine version majeure. Par conséquent, les applications ne peuvent pas compter sur la disponibilité d'outils tels que udisksctl(1). De plus, il n'y a aucune garantie que les options, les commutateurs en ligne de commande, etc. des outils en ligne de commande ou similaires resteront stables.

Au lieu de cela, les applications ne devraient utiliser que l'API D-Bus, la bibliothèque libudisks2 ou des outils tels que dbus-send(1) ou gdbus(1) pour interagir avec AUDIENCE

L'audience visée pour udisks comprend les développeurs de systèmes d'exploitation travaillant sur les couches supérieures du système, par exemple le shell de bureau (comme GNOME[5]) et les applications de gestion de disques (par exemple l'application Disks de GNOME[6]). Les logiciels à ce niveau dépendent généralement d'une version (majeure) spécifique d'udisks et peuvent même avoir un support pour les versions antérieures d'udisks ou des interfaces alternatives remplissant le même rôle qu'udisks.

Bien qu'udisks fournisse effectivement une API stable et un chemin de mise à niveau clair, il peut ne pas être une dépendance appropriée pour des applications tierces. Par exemple, si le système d'exploitation passe à la version N.x d'udisks et qu'une application utilise encore l'API (N-1).x d'udisks, l'application ne fonctionnera pas à moins qu'udisks (N-1).x ne soit installé. Bien que cette situation soit toujours gérable (puisque udisks N.x et udisks (N-1).x peuvent être installés), il peut ne pas être souhaitable de demander à l'utilisateur d'installer l'ancienne version - en fait, le fournisseur du système d'exploitation peut même ne pas fournir une version packagée de l'ancienne version. Par conséquent, si une application ne veut pas se lier à une version spécifique du système d'exploitation, elle ne devrait pas utiliser udisks.

Les alternatives viables à udisks sont des API garanties d'être disponibles sur de plus longues périodes, y compris :

•Les API et commandes de bas niveau telles que sysfs[7], libudev[8], /proc/self/mountinfo[9] et util-linux[10].
•Les API de haut niveau telles que GVolumeMonitor[11].

En particulier, pour les applications de bureau, il est beaucoup plus judicieux d'utiliser quelque chose comme GVolumeMonitor, car cela permettra à l'application d'afficher les mêmes périphériques que le shell de bureau (par exemple, le gestionnaire de fichiers, le sélecteur de fichiers, etc.).
