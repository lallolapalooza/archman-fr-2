udp(7) Manuel d'informations diverses udp(7)

NOM

udp - Protocole de datagramme utilisateur pour IPv4

SYNTAXE

#include <sys/socket.h>
#include <netinet/in.h>
#include <netinet/udp.h>
socket_udp = socket(AF_INET, SOCK_DGRAM, 0);

DESCRIPTION

Ceci est une implémentation du protocole de datagramme utilisateur décrit dans la RFC 768. Il implémente un service de paquets datagramme sans connexion et non fiable. Les paquets peuvent arriver dans le désordre ou être dupliqués avant d'arriver. UDP génère et vérifie des sommes de contrôle pour détecter les erreurs de transmission.

Lorsqu'un socket UDP est créé, ses adresses locale et distante ne sont pas spécifiées. Les datagrammes peuvent être envoyés immédiatement en utilisant sendto(2) ou sendmsg(2) avec une adresse de destination valide comme argument. Lorsque connect(2) est appelé sur le socket, l'adresse de destination par défaut est définie et les datagrammes peuvent maintenant être envoyés en utilisant send(2) ou write(2) sans spécifier d'adresse de destination. Il est toujours possible d'envoyer à d'autres destinations en passant une adresse à sendto(2) ou sendmsg(2). Afin de recevoir des paquets, le socket peut être lié à une adresse locale d'abord en utilisant bind(2). Sinon, la couche socket attribuera automatiquement un port local libre dans la plage définie par /proc/sys/net/ipv4/ip_local_port_range et liera le socket à INADDR_ANY.

Toutes les opérations de réception ne retournent qu'un seul paquet. Lorsque le paquet est plus petit que le tampon passé, seule cette quantité de données est retournée ; lorsqu'il est plus gros, le paquet est tronqué et le drapeau MSG_TRUNC est défini. MSG_WAITALL n'est pas pris en charge.

Les options IP peuvent être envoyées ou reçues en utilisant les options de socket décrites dans ip(7). Elles sont traitées par le noyau uniquement lorsque le paramètre /proc approprié est activé (mais toujours transmises à l'utilisateur même lorsqu'il est désactivé). Voir ip(7).

Lorsque le drapeau MSG_DONTROUTE est défini lors de l'envoi, l'adresse de destination doit faire référence à une adresse d'interface locale et le paquet est envoyé uniquement à cette interface.

Par défaut, Linux UDP effectue la découverte du MTU (Maximum Transmission Unit) du chemin. Cela signifie que le noyau gardera une trace du MTU vers une adresse IP cible spécifique et retournera EMSGSIZE lorsqu'une écriture de paquet UDP le dépasse. Dans ce cas, l'application doit réduire la taille du paquet. La découverte du MTU du chemin peut également être désactivée en utilisant l'option de socket IP_MTU_DISCOVER ou le fichier /proc/sys/net/ipv4/ip_no_pmtu_disc ; voir ip(7) pour plus de détails. Lorsqu'elle est désactivée, UDP fragmentera les paquets UDP sortants qui dépassent le MTU de l'interface. Cependant, il n'est pas recommandé de la désactiver pour des raisons de performance et de fiabilité.

Format d'adresse

UDP utilise le format d'adresse sockaddr_in IPv4 décrit dans ip(7).

Gestion des erreurs

Toutes les erreurs fatales seront transmises à l'utilisateur sous forme d'erreur de retour, même si le socket n'est pas connecté. Cela inclut les erreurs asynchrones reçues du réseau. Vous pourriez obtenir une erreur pour un paquet précédent qui a été envoyé sur le même socket. Ce comportement diffère de nombreuses autres implémentations de sockets BSD qui ne transmettent aucune erreur sauf si le socket est connecté. Le comportement de Linux est dicté par la RFC 1122.

Pour assurer la compatibilité avec le code hérité, sous Linux 2.0 et 2.2, il était possible de définir l'option SO_BSDCOMPAT SOL_SOCKET pour recevoir les erreurs distantes uniquement lorsque le socket avait été connecté (sauf pour EPROTO et EMSGSIZE). Les erreurs générées localement sont toujours transmises. Le support pour cette option de socket a été supprimé dans les noyaux ultérieurs ; voir socket(7) pour plus d'informations.

Lorsque l'option IP_RECVERR est activée, toutes les erreurs sont stockées dans la file d'attente d'erreurs du socket et peuvent être reçues par recvmsg(2) avec le drapeau MSG_ERRQUEUE défini.

Interfaces /proc

Les paramètres UDP au niveau du système peuvent être accédés via les fichiers dans le répertoire /proc/sys/net/ipv4/.

udp_mem (depuis Linux 2.6.25)
Ceci est un vecteur de trois entiers qui régissent le nombre de pages autorisées pour la mise en file d'attente par tous les sockets UDP.
min
En dessous de ce nombre de pages, UDP ne se préoccupe pas de son appétit en mémoire. Lorsque la quantité de mémoire allouée par UDP dépasse ce nombre, UDP commence à modérer son utilisation de la mémoire.
pressure
Cette valeur a été introduite pour suivre le format de tcp_mem (voir tcp(7)).
max
Nombre de pages autorisées pour la mise en file d'attente par tous les sockets UDP.
Les valeurs par défaut pour ces trois éléments sont calculées au démarrage à partir de la quantité de mémoire disponible.
udp_rmem_min (entier ; valeur par défaut : PAGE_SIZE ; depuis Linux 2.6.25)
Taille minimale, en octets, des tampons de réception utilisés par les sockets UDP en mode de modération. Chaque socket UDP peut utiliser cette taille pour recevoir des données, même si le nombre total de pages des sockets UDP dépasse la pression udp_mem.
udp_wmem_min (entier ; valeur par défaut : PAGE_SIZE ; depuis Linux 2.6.25)
Taille minimale, en octets, des tampons d'envoi utilisés par les sockets UDP en mode de modération. Chaque socket UDP peut utiliser cette taille pour envoyer des données, même si le nombre total de pages des sockets UDP dépasse la pression udp_mem.

Options de socket

Pour définir ou obtenir une option de socket UDP, appelez getsockopt(2) pour lire ou setsockopt(2) pour écrire l'option avec l'argument de niveau d'option défini sur IPPROTO_UDP. Sauf indication contraire, optval est un pointeur vers un int.

Voici une liste d'options de socket spécifiques à UDP. Pour plus de détails sur certaines autres options de socket qui s'appliquent également aux sockets UDP, voir socket(7).

UDP_CORK (depuis Linux 2.5.44)
Si cette option est activée, toutes les données envoyées sur ce socket sont accumulées en un seul datagramme qui est transmis lorsque l'option est désactivée. Cette option ne doit pas être utilisée dans du code destiné à être portable.
UDP_SEGMENT (depuis Linux 4.18)
Active la décharge de segmentation UDP. La décharge de segmentation réduit le coût de send(2) en transférant plusieurs datagrammes de données sous la forme d'un seul grand paquet via le chemin de transmission du noyau, même lorsque cela dépasse le MTU. Aussi tard que possible, le grand paquet est divisé par taille de segment en une série de datagrammes. Cette étape de décharge de segmentation est reportée au matériel si pris en charge, sinon effectuée en logiciel. Cette option prend une valeur dans la plage [0, USHRT_MAX] qui définit la taille du segment : la taille de la charge utile du datagramme, hors en-tête UDP. La taille du segment doit être choisie de telle sorte que pas plus de 64 datagrammes soient envoyés en un seul appel et que les datagrammes après segmentation respectent les mêmes règles MTU que celles qui s'appliquent aux datagrammes envoyés sans cette option. La décharge de segmentation dépend de la décharge de la somme de contrôle, car les sommes de contrôle des datagrammes sont calculées après la segmentation. L'option peut également être définie pour des appels individuels à sendmsg(2) en la passant comme cmsg(3). Une valeur de
zero désactive la fonctionnalité. Cette option ne doit pas être utilisée dans le code destiné à être portable.
UDP_GRO (depuis Linux 5.0)
Active la décharge de réception UDP. Si elle est activée, le socket peut recevoir plusieurs datagrammes de données sous forme d'un seul grand tampon, ainsi qu'un cmsg(3) contenant la taille du segment. Cette option est l'inverse de la décharge de segmentation. Elle réduit le coût de réception en traitant plusieurs datagrammes de données comme un seul grand paquet dans le chemin de réception du noyau, même lorsqu'il dépasse la MTU. Cette option ne doit pas être utilisée dans le code destiné à être portable.

Ioctls

Ces ioctls peuvent être accédés en utilisant ioctl(2). La syntaxe correcte est :

int valeur;
erreur = ioctl(socket_udp, type_ioctl, &valeur);
FIONREAD (SIOCINQ)
Reçoit un pointeur vers un entier comme argument. Renvoie la taille du prochain datagramme en attente dans l'entier en octets, ou 0 lorsqu'aucun datagramme n'est en attente. Attention : En utilisant FIONREAD, il est impossible de distinguer le cas où aucun datagramme n'est en attente du cas où le prochain datagramme en attente contient zéro octet de données. Il est plus sûr d'utiliser select(2), poll(2), ou epoll(7) pour distinguer ces cas.
TIOCOUTQ (SIOCOUTQ)
Renvoie le nombre d'octets de données dans la file d'attente d'envoi locale. Supporté uniquement avec Linux 2.4 et supérieur.

De plus, tous les ioctls documentés dans ip(7) et socket(7) sont supportés.

ERREURS

Toutes les erreurs documentées pour socket(7) ou ip(7) peuvent être renvoyées par un envoi ou une réception sur un socket UDP.

ECONNREFUSED
Aucun récepteur n'était associé à l'adresse de destination. Cela pourrait être causé par un paquet précédent envoyé sur le socket.

VERSIONS

IP_RECVERR est une nouvelle fonctionnalité dans Linux 2.2.
