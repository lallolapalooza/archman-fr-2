NOM

user@.service, user-runtime-dir@.service, systemd-user-runtime-dir - Unités système pour démarrer le gestionnaire utilisateur

SYNTAXE

user@UID.service

user-runtime-dir@UID.service

/usr/lib/systemd/systemd-user-runtime-dir

user-UID.slice

DESCRIPTION

Le gestionnaire système systemd(1) (PID 1) démarre des instances du gestionnaire utilisateur sous le nom user@UID.service, l'UID numérique de l'utilisateur étant utilisé comme identifiant d'instance. Ces instances utilisent le même exécutable que le gestionnaire système, mais en mode démarrant un ensemble différent d'unités. Chaque instance de systemd --user gère une hiérarchie d'unités spécifique à cet utilisateur. Voir systemd(1) pour une discussion sur les unités et systemd.special(7) pour une liste des unités qui forment la base des hiérarchies d'unités système et utilisateur.

user@UID.service est accompagné par l'unité système user-runtime-dir@UID.service, qui crée le répertoire d'exécution de l'utilisateur /run/user/UID lors de son démarrage et le supprime lorsqu'il est arrêté. Il peut également appliquer des paramètres de quota d'exécution sur /tmp/ et/ou /dev/shm/ pour l'utilisateur. user-runtime-dir@UID.service exécute le binaire systemd-user-runtime-dir pour effectuer le travail réel.

Les processus utilisateur peuvent être démarrés par l'instance user@.service, auquel cas ils feront partie de cette unité dans la hiérarchie système. Ils peuvent également être démarrés ailleurs, par exemple par sshd(8) ou un gestionnaire d'affichage comme gdm, auquel cas ils forment une unité .scope (voir systemd.scope(5)). Les deux, user@UID.service et les unités scope, sont regroupés sous user-UID.slice.

Les tranches individuelles user-UID.slice sont regroupées sous user.slice, voir systemd.special(7).

CONTRôLE DES RESSOURCES POUR LES UTILISATEURS CONNECTÉS

Les options qui contrôlent les ressources disponibles pour les utilisateurs connectés peuvent être configurées à plusieurs niveaux. Comme décrit dans la section précédente, user.slice contient les processus de tous les utilisateurs, de sorte que toutes les limites de ressources sur cette tranche s'appliquent à tous les utilisateurs ensemble. La manière habituelle de les configurer serait via des fichiers de configuration supplémentaires (drop-ins), par exemple /etc/systemd/system/user.slice.d/resources.conf.

Les processus d'un utilisateur unique sont regroupés sous user-UID.slice. Les limites de ressources pour cet utilisateur peuvent être configurées via des fichiers de configuration supplémentaires pour cette unité, par exemple /etc/systemd/system/user-1000.slice.d/resources.conf. Si les limites doivent s'appliquer à tous les utilisateurs à la place, elles peuvent être configurées via des fichiers de configuration supplémentaires pour le nom d'unité tronqué, user-.slice. Par exemple, la configuration dans /etc/systemd/system/user-.slice.d/resources.conf est incluse dans toutes les unités user-UID.slice, voir systemd.unit(5) pour une discussion sur le mécanisme des fichiers de configuration supplémentaires.

Lorsqu'un utilisateur se connecte et qu'une unité .scope est créée pour la session (voir section précédente), la création de la portée peut être gérée via pam_systemd(8). Ce module PAM communique avec systemd-logind(8) pour créer la portée de session et fournir un accès aux ressources matérielles. Les limites de ressources pour la portée peuvent être configurées via la configuration du module PAM, voir pam_systemd(8). Les configurer via la configuration d'unité normale est également possible, mais comme le nom de l'unité de tranche est généralement imprévisible, c'est moins utile.

En général, toutes les ressources applicables aux unités peuvent être définies pour user@UID.service et les unités de tranche mentionnées ci-dessus, voir systemd.resource-control(5) pour un aperçu.

EXEMPLES

Exemple 1. Hiérarchie des groupes de contrôle avec deux utilisateurs connectés

$ systemd-cgls
Control group /:
-.slice
├─user.slice
│ ├─user-1000.slice
│ │ ├─user@1000.service
│ │ │ ├─pulseaudio.service
│ │ │ │ └─2386 /usr/bin/pulseaudio --daemonize=no
│ │ │ └─gnome-terminal-server.service
│ │ │   └─init.scope
│ │ │     ├─ 4127 /usr/libexec/gnome-terminal-server
│ │ │     └─ 4198 zsh
│ │ │ ...
│ │ └─session-4.scope
│ │   ├─ 1264 gdm-session-worker [pam/gdm-password]
│ │   ├─ 2339 /usr/bin/gnome-shell
│ │   ...
│ │ ├─session-19.scope
│ │   ├─6497 sshd: zbyszek [priv]
│ │   ├─6502 sshd: zbyszek@pts/6
│ │   ├─6509 -zsh
│ │   └─6602 systemd-cgls --no-pager
│ ...
│ └─user-1001.slice
│   ├─session-20.scope
│   │ ├─6675 sshd: guest [priv]
│   │ ├─6708 sshd: guest@pts/6
│   │ └─6717 -bash
│   └─user@1001.service
│     ├─init.scope
│     │ ├─6680 /usr/lib/systemd/systemd --user
│     │ └─6688 (sd-pam)
│     └─sleep.service
│       └─6706 /usr/bin/sleep 30
...

L'utilisateur avec l'UID 1000 est connecté via gdm (session-4.scope) et ssh(1) (session-19.scope), et a également une instance de gestionnaire utilisateur en cours d'exécution (user@1000.service). L'utilisateur avec l'UID 1001 est connecté via ssh (session-20.scope) et a également une instance de gestionnaire utilisateur en cours d'exécution (user@1001.service). Ce sont toutes des unités système (feuilles), et elles font partie de la hiérarchie des tranches, avec user-1000.slice et user-1001.slice sous user.slice. Les unités utilisateur sont visibles sous les instances user@.service (pulseaudio.service, gnome-terminal-server.service, init.scope, sleep.service).

Exemple 2. Limites de ressources utilisateur par défaut

$ systemctl cat user-1000.slice
# /usr/lib/systemd/system/user-.slice.d/10-defaults.conf
# ...
[Unit]
Description=User Slice of UID %j
After=systemd-user-sessions.service
[Slice]
TasksMax=33%

Les unités user-UID.slice n'ont par défaut pas de fichier d'unité. Les limites de ressources sont définies via un fichier de configuration supplémentaire, qui peut être facilement remplacé ou étendu en suivant les mécanismes standard des fichiers de configuration supplémentaires décrits dans la première section.

user@.service

user@.service — Service pour les utilisateurs connectés.

SYNTHÈSE

user@.service

DESCRIPTION

Le fichier d'unité user@.service est utilisé pour contrôler le démarrage et l'arrêt des services pour les utilisateurs connectés. Il s'agit d'un modèle d'unité qui peut être instancié pour chaque utilisateur. Lorsque l'utilisateur se connecte, le système démarre une instance de ce service pour cet utilisateur. Lorsque l'utilisateur se déconnecte, le système arrête l'instance du service.

OPTIONS

Aucune option spécifique n'est configurée dans ce fichier d'unité par défaut. Les options de configuration pour le shell de connexion et le gestionnaire d'utilisateur sont généralement définies ailleurs.

SHELL DE CONNEXION

Le shell de connexion par défaut pour un utilisateur est généralement défini dans le fichier /etc/passwd. Le service user@.service démarre ce shell pour l'utilisateur.

MANAGER D'UTILISATEUR

Le système utilise systemd comme gestionnaire de système. Le service user@.service est une partie intégrante de la gestion des sessions utilisateur sous systemd.

MANAGER DE CONNEXION

Le gestionnaire de connexion (par exemple, GDM, LightDM, SDDM) est responsable du processus de connexion de l'utilisateur. Une fois que l'utilisateur est authentifié, le gestionnaire de connexion lance le service user@.service pour cet utilisateur.

SYSTÈME ENQUÊTÉ

Ce service est exécuté dans le contexte de l'utilisateur connecté, et non dans le contexte du système entier. Les privilèges et les ressources sont limités à ceux de l'utilisateur.

CONTRÔLE DES RESSOURCES POUR LES UTILISATEURS CONNECTÉS

Le service user@.service peut être utilisé conjointement avec d'autres mécanismes de systemd pour contrôler les ressources (CPU, mémoire, etc.) allouées aux processus des utilisateurs connectés. Cela peut être fait en configurant des fichiers d'unité supplémentaires ou en utilisant des cgroups.

EXEMPLES

Aucun exemple spécifique car il s'agit d'un service système par défaut.
