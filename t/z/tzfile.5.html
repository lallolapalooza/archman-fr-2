tzfile(5) Manuel des formats de fichiers tzfile(5)

NOM

tzfile - informations de fuseau horaire

DESCRIPTION

Les fichiers d'informations de fuseau horaire utilisés par tzset(3) se trouvent généralement sous un répertoire nommé par exemple /usr/share/zoneinfo. Ces fichiers utilisent le format décrit dans la RFC 9636 de l'Internet. Chaque fichier est une séquence d'octets de 8 bits. Dans un fichier, un entier binaire est représenté par une séquence d'un ou plusieurs octets en ordre réseau (big-endian, ou octet de poids fort en premier), avec tous les bits significatifs ; un entier binaire signé est représenté en complément à deux ; et un booléen est représenté par un entier binaire d'un octet qui est soit 0 (faux), soit 1 (vrai). Le format commence par un en-tête de 44 octets contenant les champs suivants :

  • La séquence magique de quatre octets ASCII « TZif » identifie le fichier comme un fichier d'informations de fuseau horaire.
  • Un octet identifiant la version du format du fichier (en 2021, soit un caractère NUL ASCII, « 2 », « 3 », ou « 4 »).
  • Quinze octets contenant des zéros réservés pour une utilisation future.
  • Six valeurs entières de quatre octets, dans l'ordre suivant :
tzh_ttisutcnt
Le nombre d'indicateurs UT/local stockés dans le fichier. (UT est le Temps Universel.)
tzh_ttisstdcnt
Le nombre d'indicateurs standard/heure locale stockés dans le fichier.
tzh_leapcnt
Le nombre de secondes intercalaires pour lesquelles des entrées de données sont stockées dans le fichier.
tzh_timecnt
Le nombre de temps de transition pour lesquels des entrées de données sont stockées dans le fichier.
tzh_typecnt
Le nombre de types d'heure locale pour lesquels des entrées de données sont stockées dans le fichier (ne doit pas être zéro).
tzh_charcnt
Le nombre d'octets des chaînes d'abréviations de fuseau horaire stockées dans le fichier.

L'en-tête ci-dessus est suivi des champs suivants, dont les longueurs dépendent du contenu de l'en-tête :

  • tzh_timecnt valeurs entières signées de quatre octets triées par ordre croissant. Ces valeurs sont écrites en ordre d'octets réseau. Chacune est utilisée comme un temps de transition (tel que retourné par time(2)) auquel les règles de calcul de l'heure locale changent.
  • tzh_timecnt valeurs d'octets non signés de un octet ; chacune sauf la dernière indique quel type d'heures locales différentes décrites dans le fichier est associé à la période de temps commençant par le temps de transition d'index identique et continuant jusqu'à, mais sans inclure, le prochain temps de transition. (Le dernier type de temps n'est présent que pour la vérification de cohérence avec la chaîne TZ proleptique décrite ci-dessous.) Ces valeurs servent d'indices dans le champ suivant.
  • tzh_typecnt entrées ttinfo, chacune définie comme suit : 
    struct ttinfo {
	int32_t	tt_utoff;
	unsigned char	tt_isdst;
	unsigned char	tt_desigidx;
};

    Chaque structure est écrite comme une valeur entière signée de quatre octets pour tt_utoff, en ordre d'octets réseau, suivie d'un booléen d'un octet pour tt_isdst et d'une valeur d'un octet pour tt_desigidx. Dans chaque structure, tt_utoff donne le nombre de secondes à ajouter à UT, tt_isdst indique si tm_isdst doit être défini par localtime(3), et tt_desigidx sert d'indice dans le tableau des octets d'abréviation de fuseau horaire qui suivent les entrées ttinfo dans le fichier ; si la chaîne désignée est « -00 », l'entrée ttinfo est un espace réservé indiquant que l'heure locale n'est pas spécifiée. La valeur tt_utoff n'est jamais égale à -2**31, pour permettre aux clients 32 bits de la négativer sans débordement. De plus, dans les applications réalistes, tt_utoff est dans la plage [-89999, 93599] (c'est-à-dire plus de -25 heures et moins de 26 heures) ; cela permet un support facile par les implémentations qui supportent déjà la plage requise par POSIX [-24:59:59, 25:59:59].

  • tzh_charcnt octets représentant les désignations de fuseau horaire, qui sont des chaînes d'octets terminées par un caractère nul, chacune indexée par les valeurs tt_desigidx mentionnées ci-dessus. Les chaînes d'octets peuvent se chevaucher si l'une est un suffixe de l'autre. L'encodage de ces chaînes n'est pas spécifié.
  • tzh_leapcnt paires de valeurs de quatre octets, écrites en ordre d'octets réseau ; la première valeur de chaque paire donne le temps non négatif (tel que retourné par time(2)) auquel une seconde intercalaire se produit ou auquel la table de secondes intercalaires expire ; la seconde est un entier signé spécifiant la correction, qui est le nombre total de secondes intercalaires à appliquer pendant la période commençant à l'heure donnée. Les paires de valeurs sont triées par ordre strictement croissant par temps. Chaque paire désigne une seconde intercalaire, positive ou négative, sauf que si la dernière paire a la même correction que la précédente, la dernière paire désigne le temps d'expiration de la table des secondes intercalaires. Chaque seconde intercalaire se trouve à la fin d'un mois de calendrier UTC. La première seconde intercalaire a un temps d'occurrence non négatif, et est une seconde intercalaire positive si et seulement si sa correction est positive ; la correction pour chaque seconde intercalaire après la première diffère de la seconde intercalaire précédente de 1 pour une seconde intercalaire positive, ou de -1 pour une seconde intercalaire négative. Si la table des secondes intercalaires est vide, la correction des secondes intercalaires est zéro pour toutes les timestamps ; sinon, pour les timestamps antérieures au premier temps d'occurrence, la correction des secondes intercalaires est zéro si la correction de la première paire est 1 ou -1, et est non spécifiée sinon (ce qui ne peut se produire que dans les fichiers tronqués au début).
  • tzh_ttisstdcnt indicateurs standard/heure locale, chacun stocké comme un booléen d'un octet ; ils indiquent si les temps de transition associés aux types d'heures locales ont été spécifiés comme heure standard ou heure locale (heure de l'horloge).
  • tzh_ttisutcnt indicateurs UT/local, chacun stocké comme un booléen d'un octet ; ils indiquent si les temps de transition associés aux types d'heures locales ont été spécifiés comme UT ou heure locale. Si un indicateur UT/local est défini, l'indicateur standard/heure locale correspondant doit également être défini.

Les indicateurs standard/heure locale et UT/local ont été conçus pour transformer les temps de transition d'un fichier TZif en transitions appropriées pour un autre fuseau horaire spécifié via une chaîne TZ proleptique qui manque de règles. Par exemple, lorsque TZ=« EET-2EEST » et qu'il n'y a pas de fichier TZif « EET-2EEST », l'idée était d'adapter les temps de transition d'un fichier TZif avec le nom bien connu « posixrules » qui n'est présent qu'à cette fin et est une copie du fichier « Europe/Brussels », un fichier avec un décalage UT différent. POSIX ne spécifie pas les détails de ce comportement transformationnel obsolète, les règles par défaut dépendent de l'installation, et aucune implémentation n'est connue pour supporter cette fonctionnalité pour les timestamps au-delà de 2037, donc les utilisateurs désirant (par exemple) l'heure grecque devraient plutôt spécifier TZ=« Europe/Athens » pour une meilleure couverture historique, se rabattant sur TZ=« EET-2EEST,M3.5.0/3,M10.5.0/4 » si la conformité POSIX est requise et que les timestamps plus anciens ne doivent pas être gérés avec précision.

La fonction localtime(3) utilise normalement la première structure ttinfo du fichier si tzh_timecnt est zéro ou si l'argument de temps est inférieur au premier temps de transition enregistré dans le fichier.

Format Version 2

Pour les fichiers de fuseau horaire au format version 2, l'en-tête et les données ci-dessus sont suivis d'un deuxième en-tête et de données, de format identique sauf que huit octets sont utilisés pour chaque temps de transition ou temps de seconde intercalaire. (Les décomptes de secondes intercalaires restent de quatre octets.) Après le deuxième en-tête et les données vient une chaîne délimitée par des sauts de ligne dans le style du contenu d'un TZ proleptique, pour être utilisée dans la gestion des instants après le dernier temps de transition stocké dans le fichier ou pour tous les instants si le fichier n'a pas de transitions. La chaîne TZ est vide (c'est-à-dire rien entre les sauts de ligne) s'il n'y a pas de représentation proleptique pour de tels instants. Si elle n'est pas vide, la chaîne TZ doit être cohérente avec le type d'heure locale après le dernier temps de transi

De plus, s'il y a au moins une transition, le type d'heure 0 est associé à la période de temps allant du passé indéfini jusqu'à, mais sans inclure, l'heure de la transition la plus ancienne.

Format de la version 3

Pour les fichiers d'heure au format version 3, une chaîne TZ (voir newtzset(3)) peut utiliser les extensions POSIX.1-2024 suivantes à POSIX.1-2017 : Premièrement, comme dans TZ="<-02>2<-01>,M3.5.0/-1,M10.5.0/0", la partie heures de ses heures de transition peut être signée et varier de -167 à 167 au lieu d'être limitée à des valeurs non signées de 0 à 24. Deuxièmement, comme dans TZ="XXX3EDT4,0/0,J365/23", l'heure d'été est en vigueur toute l'année si elle commence le 1er janvier à 00h00 et se termine le 31 décembre à 24h00 plus la différence entre l'heure d'été et l'heure standard.

Format de la version 4

Pour les fichiers TZif au format version 4, le premier enregistrement de seconde intercalaire peut avoir une correction qui n'est ni +1 ni -1, pour représenter la troncature du fichier TZif au début. De plus, si deux transitions de seconde intercalaire ou plus sont présentes et que la dernière entrée' correction est égale à la précédente, la dernière entrée désigne l'expiration de la table des secondes intercalaires au lieu d'une seconde intercalaire ; les horodatages après cette expiration ne sont pas fiables car les futures versions ajouteront probablement des entrées de seconde intercalaire après l'expiration, et les secondes intercalaires ajoutées modifieront la façon dont les horodatages post-expiration sont traités.

Considérations d'interopérabilité

Les futures modifications du format peuvent ajouter plus de données.

Les fichiers version 1 sont considérés comme un format hérité et ne doivent pas être générés, car ils ne prennent pas en charge les heures de transition après l'an 2038. Les lecteurs qui ne comprennent que la version 1 doivent ignorer toutes les données qui s'étendent au-delà de la fin calculée du bloc de données version 1.

Autre que la version 1, les générateurs doivent générer le numéro de version le plus bas requis par les données d'un fichier. Par exemple, un générateur ne doit générer un fichier version 4 que si sa table de secondes intercalaires expire ou est tronquée au début. De même, un générateur qui ne génère pas de fichier version 4 doit générer un fichier version 3 uniquement si les extensions de chaîne TZ sont nécessaires pour modéliser avec précision les heures de transition.

La séquence des changements d'heure définis par l'en-tête et le bloc de données version 1 doit être une sous-séquence contiguë des changements d'heure définis par l'en-tête et le bloc de données version 2+, ainsi que par le pied de page. Cette directive aide les lecteurs version 1 obsolètes à s'accorder avec les lecteurs actuels sur les horodatages dans la sous-séquence contiguë. Elle permet également aux générateurs ne prenant pas en charge les lecteurs obsolètes d'utiliser une valeur de tzh_timecnt de zéro dans le bloc de données version 1 pour économiser de l'espace.

Lorsqu'un fichier TZif contient une heure d'expiration de table de secondes intercalaires, les lecteurs TZif doivent soit refuser de traiter les horodatages post-expiration, soit les traiter comme si l'heure d'expiration n'existait pas (éventuellement avec une indication d'erreur).

Les désignations de fuseau horaire doivent se composer d'au moins trois (3) et au maximum six (6) caractères ASCII de l'ensemble des alphanumériques, “-” et “+”. Ceci est pour la compatibilité avec les exigences POSIX pour les abréviations de fuseaux horaires.

Lors de la lecture d'un fichier version 2 ou supérieur, les lecteurs doivent ignorer l'en-tête et le bloc de données version 1, sauf dans le but de les sauter.

Les lecteurs doivent calculer les longueurs totales des en-têtes et des blocs de données et vérifier qu'ils correspondent tous à la taille réelle du fichier, dans le cadre d'une vérification de validité du fichier.

Lorsqu'une seconde intercalaire positive se produit, les lecteurs doivent ajouter une seconde supplémentaire à la minute locale contenant la seconde juste avant la seconde intercalaire. Si cela se produit lorsque le décalage UTC n'est pas un multiple de 60 secondes, la seconde intercalaire se produit plus tôt que la dernière seconde de la minute locale et les secondes locales restantes de la minute sont numérotées jusqu'à 60 au lieu des 59 habituelles ; le décalage UTC n'est pas affecté.

Problèmes courants d'interopérabilité

Cette section documente les problèmes courants de lecture ou d'écriture des fichiers TZif. La plupart d'entre eux sont des problèmes de génération de fichiers TZif destinés à être utilisés par des lecteurs plus anciens. Les objectifs de cette section sont d'aider :

  • Les générateurs TZif à produire des fichiers qui évitent les écueils courants des lecteurs TZif anciens ou bogués,
  • Les lecteurs TZif à éviter les écueils courants lors de la lecture de fichiers générés par de futurs générateurs TZif, et
  • Les futurs auteurs de spécifications à voir quel type de problèmes survient lorsque le format TZif est modifié.

Lorsque de nouvelles versions du format TZif ont été définies, un objectif de conception a été qu'un lecteur puisse utiliser avec succès un fichier TZif même si le fichier est d'une version TZif ultérieure à celle pour laquelle le lecteur a été conçu. Lorsque la compatibilité complète n'a pas été atteinte, une tentative a été faite pour limiter les problèmes aux horodatages rarement utilisés et permettre des solutions de contournement partielles simples dans les générateurs conçus pour générer des données plus récentes utiles même pour les lecteurs de versions antérieures. Cette section tente de documenter ces problèmes de compatibilité et les solutions de contournement, ainsi que de documenter d'autres bogues courants dans les lecteurs.

Les problèmes d'interopérabilité avec TZif incluent les suivants :

  • Certains lecteurs n'examinent que les données de la version 1. À titre de solution de contournement partielle, un générateur peut produire autant de données version 1 que possible. Cependant, un lecteur doit ignorer les données version 1 et utiliser les données version 2+ même si les horodatages natifs du lecteur n'ont que 32 bits.
  • Certains lecteurs conçus pour la version 2 peuvent mal gérer les horodatages après la dernière transition d'un fichier version 3 ou supérieur, car ils ne peuvent pas analyser les extensions POSIX.1-2024 à POSIX.1-2017 dans la chaîne TZ proleptique. À titre de solution de contournement partielle, un générateur peut produire plus de transitions que nécessaire, de sorte que seuls les horodatages très futurs soient mal gérés par les lecteurs version 2.
  • Certains lecteurs conçus pour la version 2 ne prennent pas en charge l'heure d'été permanente avec des transitions après 24h00, par exemple, une chaîne TZ “EST5EDT,0/0,J365/25” désignant l'heure d'été de l'Est permanente (-04). Comme solution de contournement, un générateur peut substituer l'heure standard pour deux fuseaux horaires à l'est, par exemple, “XXX3EDT4,0/0,J365/23” pour un fuseau horaire avec une heure standard jamais utilisée (XXX, -03) et une heure d'été négative (EDT, -04) toute l'année. Alternativement, comme solution de contournement partielle, un générateur peut substituer l'heure standard pour le fuseau horaire suivant à l'est, par exemple, “AST4” pour l'heure standard de l'Atlantique permanente (-04).
  • Certains lecteurs conçus pour la version 2 ou 3 et qui exigent une stricte conformité à la RFC 9636 rejettent les fichiers version 4 dont les tables de secondes intercalaires sont tronquées au début ou à la fin par des heures d'expiration.
  • Certains lecteurs ignorent le pied de page et prédisent plutôt les horodatages futurs à partir du type d'heure de la dernière transition. À titre de solution de contournement partielle, un générateur peut produire plus de transitions que nécessaire.
  • Certains lecteurs simplifiés ignorent tout sauf le pied de page et utilisent sa chaîne TZ proleptique pour calculer tous les horodatages. Bien que cette approche fonctionne souvent pour les horodatages actuels et futurs, elle pose évidemment des problèmes avec les horodatages passés, et même pour les horodatages actuels, elle peut échouer pour des paramètres comme TZ="Africa/Casablanca". Ceci correspond à un fichier TZif contenant des transitions explicites jusqu'en 2087, suivies d'un pied de page contenant la chaîne TZ “<+01>-1”, qui ne doit être utilisée que pour les horodatages après la dernière transition explicite.
  • Certains lecteurs n'utilisent pas le type d'heure 0 pour les horodatages avant la première transition, car ils en déduisent un type d'heure à l'aide d'une heuristique qui ne sélectionne pas toujours le type d'heure 0. À titre de solution de contournement partielle, un générateur peut produire une transition factice (sans effet) à une heure précoce.
  • Certains lecteurs mal gèrent les horodatages avant la première transition dont l'horodatage n'est pas inférieur à -2**31. Les lecteurs ne prenant en charge que les horodatages 32 bits sont susceptibles d'être plus sujets à ce problème, par exemple, lorsqu'ils traitent des transitions 64 bits dont certaines seulement sont représentables en 32 bits. À titre de solution de contournement partielle, un générateur peut produire une transition factice à l'horodatage -2**31.
  • Certains lecteurs mal gèrent une transition si son horodatage a la valeur minimale possible pour un entier signé 64 bits. Les horodatages inférieurs à -2**59 ne sont pas recommandés.
  • Certains lecteurs mal gèrent les chaînes TZ proleptiques qui contiennent “<” ou “>”. À titre de solution de contournement partielle, un générateur peut éviter d'utiliser “<” ou “>” pour les abréviations de fuseaux horaires contenant uniquement des caractères alphabétiques.
  • De nombreux lecteurs mal gèrent les abréviations de fuseaux horaires contenant des caractères non ASCII. Ces caractères ne sont pas recommandés.
  • Certains lecteurs peuvent mal gérer les abréviations de fuseaux horaires qui contiennent moins de 3 ou plus de 6 caractères ou qui contiennent des caractères ASCII autres que les alphanumériques, “-” et “+”. Ces abréviations ne sont pas recommandées.
  • Certains lecteurs mal gèrent les fichiers TZif qui spécifient des décalages UTC d'heure d'été inférieurs aux décalages UTC pour l'heure standard correspondante. Ces lecteurs ne prennent pas en charge des emplacements comme l'Irlande, qui utilise l'équivalent de la chaîne TZ “IST-1GMT0,M10.5.0,M3.5.0/1”, observant l'heure standard (IST, +01) en été et l'heure d'été (GMT, +00) en hiver. À titre de solution de contournement partielle, un générateur peut produire des données pour l'équivalent de la chaîne TZ “GMT0IST,M3.5.0/1,M10.5.0”, échangeant ainsi l'heure standard et l'heure d'été. Bien que cette solution de contournement identifie mal la période de l'année où l'heure d'été est utilisée, elle enregistre correctement les décalages UTC et les abréviations de fuseaux horaires.
  • Certains lecteurs génèrent des horodatages ambigus pour des secondes intercalaires positives qui se produisent lorsque le décalage UTC n'est pas un multiple de 60 secondes. Par exemple, avec un décalage UTC de +01:23:45 et une seconde intercalaire positive 78796801 (1972-06-30 23:59:60 UTC), certains lecteurs mappent à la fois 78796800 et 78796801 à 01:23:45 heure locale le lendemain au lieu de mapper ce dernier à 01:23:46, et ils mappent 78796815 à 01:23:59 au lieu de 01:23:60. Cela n'a pas encore été un problème pratique, car aucune autorité civile n'a observé de tels décalages UTC depuis l'introduction des secondes intercalaires en 1972.

Certains problèmes d'interopérabilité sont des bogues de lecteur qui sont listés ici principalement comme avertissements aux développeurs de lecteurs.

tzfile(5) — Time Zone Database

NAME

tzfile

file format for time zone information

DESCRIPTION

This manual page describes the format of the time zone information files used by the tzset(3) function and related functions. These files are used to represent the past, present, and future values of local time, including the date and time of the introduction of the current standard time, the date and time of the introduction of the current daylight saving time, and the difference between them.

The time zone information files are binary files, and their format is described in detail in RFC 9636. The primary components of a time zone file are:

  • A header that identifies the version of the format.
  • A sequence of future time zone abbreviations.
  • A sequence of future standard time offsets.
  • A sequence of future daylight saving time offsets.
  • A sequence of transition times that specify when to switch between standard time and daylight saving time.
  • A sequence of flags indicating whether daylight saving time is in effect for each transition.
  • A sequence of area (e.g. "America/New_York") and abbreviation (e.g. "EST", "EDT") pairs that represent the name of the time zone and the abbreviation in effect at the time of each transition.

The following are some potential issues that developers of distributed applications should be aware of when dealing with time zone information:

  • Some readers mishandle timestamps before 1970 because they use signed 32-bit integers to store timestamps. This means they cannot represent negative timestamps. Developers of distributed applications should keep this in mind if they need to deal with pre-1970 data.
  • Some readers mishandle timestamps before the first transition that has a non-negative timestamp. Readers that do not support negative timestamps are likely to be more prone to this problem.
  • Some readers mishandle time zone abbreviations like “-08” that contain “+”, “-”, or digits.
  • Some readers mishandle UT offsets that are out of the traditional range of -12 through +12 hours, and so do not support locations like Kiritimati that are outside this range.
  • Some readers mishandle UT offsets in the range [-3599, -1] seconds from UT because they integer-divide the offset by 3600 to get 0 and then display the hour part as “+00”.
  • Some readers mishandle UT offsets that are not a multiple of one hour, or of 15 minutes, or of 1 minute.
