NOM

tm - Facilités pour localiser et charger les Modules Tcl

SYNOPIS

::tcl::tm::path add ?chemin...?
::tcl::tm::path remove ?chemin...?
::tcl::tm::path list
::tcl::tm::roots chemins

DESCRIPTION

Ce document décrit les facilités pour localiser et charger les Modules Tcl (voir DÉFINITION DE MODULE pour la définition d'un Module Tcl). Les commandes suivantes sont prises en charge :

::tcl::tm::path add ?chemin...?
Les chemins sont ajoutés en tête de liste des chemins de modules, dans l'ordre d'apparition. Cela signifie que le dernier argument devient la nouvelle tête de la liste.

La commande impose la restriction qu'aucun chemin ne peut être un répertoire parent d'un autre chemin de la liste. Si l'un des nouveaux chemins viole cette restriction, une erreur sera levée avant que l'un des chemins ne soit ajouté. Autrement dit, si un seul argument de chemin viole la restriction, aucun ne sera ajouté.

Si un chemin est déjà présent tel quel, aucune erreur ne sera levée et aucune action ne sera entreprise.

Les chemins sont recherchés ultérieurement dans l'ordre de leur apparition dans la liste. Comme ils sont ajoutés en tête de liste, ils sont recherchés dans l'ordre inverse de leur ajout. Autrement dit, les chemins ajoutés en dernier sont examinés en premier.

::tcl::tm::path remove ?chemin...?
Supprime les chemins de la liste des chemins de modules. La commande ignore silencieusement tous les chemins qui ne sont pas sur la liste.
::tcl::tm::path list
Retourne une liste contenant tous les chemins de modules enregistrés, dans l'ordre de recherche des modules.
::tcl::tm::roots chemins
Similaire à path add, et superposé à celui-ci. Cette commande prend un seul argument contenant une liste de chemins, les étend avec “tclX/site-tcl”, et “tclX/X.y”, pour la version majeure X de l'interpréteur Tcl et la version mineure y inférieure ou égale à la version mineure de l'interpréteur, et ajoute l'ensemble résultant de chemins à la liste des chemins à rechercher.

Cette commande est utilisée en interne par le système pour configurer les chemins par défaut spécifiques au système.

La commande a été exposée pour permettre à un système de construction de définir des chemins racines supplémentaires au-delà de ceux décrits dans ce document.

DÉFINITION DE MODULE

Un Module Tcl est un Paquet Tcl contenu dans un seul fichier, et aucun autre fichier requis par celui-ci. Ce fichier doit être sourceable. En d'autres termes, un Module Tcl est toujours importé via :

source chemin_module

La commande load n'est pas directement utilisée. Cette restriction n'est pas une limitation réelle, comme certains pourraient le croire. Depuis la version 8.4, la commande source de Tcl ne lit que jusqu'au premier caractère ^Z. Cela nous permet de combiner un script Tcl arbitraire avec des données binaires arbitraires dans un seul fichier, où le script traite les données jointes comme il le choisit pour importer et activer complètement le paquet.

Le nom d'un fichier module doit correspondre à l'expression régulière :

([_[:alpha:]][:_[:alnum:]]*)-([[:digit:]].*)\.tm

Les premières parenthèses capturantes fournissent le nom du paquet, la deuxième clause sa version. En plus de correspondre au motif, le numéro de version extrait ne doit pas générer d'erreur lorsqu'il est utilisé dans la commande :

package vcompare $version 0

RECHERCHE DE MODULES

L'arborescence des répertoires pour stocker les modules Tcl est distincte des autres parties du système de fichiers et indépendante de auto_path.

Les Modules Tcl sont recherchés dans tous les répertoires listés dans le résultat de la commande ::tcl::tm::path list. C'est ce qu'on appelle le chemin des modules. Ni la variable auto_path ni la variable tcl_pkgPath ne sont utilisées. Tous les répertoires du chemin des modules doivent respecter une restriction :

Pour deux répertoires quelconques, aucun n'est un répertoire parent de l'autre.

Ceci est requis pour éviter les ambiguïtés dans la dénomination des paquets. Si, par exemple, les deux répertoires “foo/” et “foo/cool” étaient sur le chemin, un paquet nommé cool::ice pourrait être trouvé via les noms cool::ice ou ice, ce dernier masquant potentiellement un paquet nommé ice, non qualifié.

Avant le début de la recherche, le nom du paquet demandé est traduit en un chemin partiel, en utilisant l'algorithme suivant :

Toutes les occurrences de “::” dans le nom du paquet sont remplacées par le caractère séparateur de répertoire approprié pour la plateforme sur laquelle nous nous trouvons. Sur Unix, par exemple, c'est “/”.

Exemple :

Le paquet demandé est encoding::base64. Le chemin partiel généré est “encoding/base64”.

Après cette traduction, le paquet est recherché dans tous les chemins de modules, en combinant ceux-ci un par un, du premier au dernier, avec le chemin partiel pour former un motif de recherche complet. Notez que l'algorithme de recherche rejette tous les fichiers dont le nom de fichier ne correspond pas à l'expression régulière donnée dans la section DÉFINITION DE MODULE. Pour les fichiers restants, des scripts de fourniture sont générés et ajoutés à la base de données ifneeded du paquet.

L'algorithme revient au gestionnaire d'inconnu précédent lorsque aucun des fichiers de module trouvés ne satisfait la demande. Si la demande a été satisfaite, le retour arrière est ignoré.

Notez que les paquets sous forme de modules n'ont *aucun* contrôle sur les scripts d'index et de fourniture qui sont entrés dans la base de données des paquets pour eux. Pour un fichier module MF, le script d'index est toujours :

package ifneeded NOM_PAQUET VERSION_PAQUET [list source MF]

et le script de fourniture intégré dans ce qui précède est :

source MF

Le nom du paquet NOM_PAQUET et la version du paquet VERSION_PAQUET sont tous deux extraits du nom de fichier MF conformément à la définition ci-dessous :

MF = /chemin_module/NOM_PAQUET_PARTIEL′-VERSION_PAQUET.tm

Où NOM_PAQUET_PARTIEL′ est le chemin partiel du module tel que défini dans la section RECHERCHE DE MODULES, et traduit en NOM_PAQUET en changeant tous les séparateurs de répertoire en “::”, et chemin_module est le chemin (parmi la liste des chemins à rechercher) sous lequel nous avons trouvé le fichier module.

Notez également que nous créons ici une connexion entre les noms de paquets et les chemins. Tcl est sensible à la casse pour comparer les noms de paquets, mais il existe des systèmes de fichiers qui ne le sont pas, comme NTFS. Heureusement, ces systèmes de fichiers stockent la casse du nom, malgré le fait qu'ils n'utilisent pas cette information lors de la comparaison.

Compte tenu de ce qui précède, nous autorisons les noms des paquets Tcl sous forme de modules à avoir une casse mixte, mais nous exigeons également qu'il n'y ait pas de collisions lors de la comparaison des noms d'une manière insensible à la casse. Autrement dit, si un paquet Foo est déployé sous la forme d'un Module Tcl, des paquets comme foo, fOo, etc. ne sont plus autorisés.

CHEMINS PAR DÉFAUT

La liste par défaut des chemins du chemin des modules est calculée par un tclsh comme suit, où X est la version majeure de l'interpréteur Tcl et y est inférieur ou égal à la version mineure de l'interpréteur Tcl.

Tous les chemins par défaut sont ajoutés au chemin des modules, même les chemins qui n'existent pas. Les chemins inexistants sont filtrés lors des recherches réelles. Cela permet à un utilisateur de créer l'un des chemins recherchés lorsque nécessaire et toutes les applications en cours d'exécution détecteront automatiquement les modules qui y sont placés.

Les chemins sont ajoutés dans l'ordre où ils sont listés ci-dessous, et pour les listes de chemins définies par une variable d'environnement dans l'ordre où ils sont trouvés dans la variable.

file normalize [info library]/../tclX/X.y

r versions sont inférieures ou égales à la version mineure de l'interpréteur.

Par exemple, pour Tcl 8.4, les chemins recherchés sont :

[info library]/../tcl8/8.4
[info library]/../tcl8/8.3
[info library]/../tcl8/8.2
[info library]/../tcl8/8.1
[info library]/../tcl8/8.0

Cette définition suppose qu'un package défini pour Tcl X.y peut également être utilisé par tous les interpréteurs qui ont le même numéro majeur X et un numéro mineur supérieur à y.

file normalize EXEC/tclX/X.y
Où EXEC est file normalize [info nameofexecutable]/../lib ou file normalize [::tcl::pkgconfig get libdir,runtime]

Cet ensemble de chemins est traité de manière équivalente à l'ensemble précédent, à l'exception qu'il est ancré dans EXEC_PREFIX. Pour une compilation avec PREFIX = EXEC_PREFIX, les deux ensembles sont identiques.

CHEMINS SPÉCIFIQUES AU SITE

file normalize [info library]/../tclX/site-tcl
Notez qu'il s'agit toujours d'une seule entrée car X est toujours une valeur spécifique (la version majeure actuelle de Tcl).

CHEMINS SPÉCIFIQUES UTILISATEUR

$::env(TCLX_y_TM_PATH)
Une liste de chemins, séparés par soit : (Unix) soit ; (Windows). Ceci est spécifique à l'utilisateur et au site, car cette variable d'environnement peut être définie non seulement par le profil de l'utilisateur, mais également par des scripts de configuration système.
$::env(TCLX.y_TM_PATH)
Même signification et contenu que la variable précédente. Cependant, l'utilisation du point '.' pour séparer le numéro de version majeure et mineure rend ce nom moins portable et son utilisation est déconseillée. La prise en charge de cette variable n'a été conservée que pour la compatibilité descendante avec la spécification d'origine, c'est-à-dire TIP 189.

Ces chemins sont vus et donc partagés par tous les shells Tcl dans le $::env(PATH) de l'utilisateur.

Notez que X et y suivent les règles générales énoncées ci-dessus. En d'autres termes, Tcl 8.4, par exemple, examinera ces 10 variables d'environnement :

$::env(TCL8.4_TM_PATH)  $::env(TCL8_4_TM_PATH)
$::env(TCL8.3_TM_PATH)  $::env(TCL8_3_TM_PATH)
$::env(TCL8.2_TM_PATH)  $::env(TCL8_2_TM_PATH)
$::env(TCL8.1_TM_PATH)  $::env(TCL8_1_TM_PATH)
$::env(TCL8.0_TM_PATH)  $::env(TCL8_0_TM_PATH)
