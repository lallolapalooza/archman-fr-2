TEST(1P) Manuel du programmeur POSIX TEST(1P)

PROLOGUE

Cette page de manuel fait partie du Manuel du programmeur POSIX. L'implémentation Linux de cette interface peut différer (consultez la page de manuel Linux correspondante pour les détails du comportement sous Linux), ou l'interface peut ne pas être implémentée sous Linux.

NOM

test — évaluer une expression

SYNTAXE

test [expression]
[ [expression] ]

DESCRIPTION

L'utilitaire test évalue l'expression et indique le résultat de l'évaluation par son statut de sortie. Un statut de sortie de zéro indique que l'expression a été évaluée comme vraie et un statut de sortie de 1 indique que l'expression a été évaluée comme fausse.

Dans la deuxième forme de l'utilitaire, où le nom de l'utilitaire utilisé est [ plutôt que test, l'application doit s'assurer que le crochet fermant est un argument séparé. Les utilitaires test et [ peuvent être implémentés comme un seul utilitaire lié qui examine le nom de base du nième argument de ligne de commande pour déterminer s'il doit se comporter comme la variante test ou [. Les applications utilisant la famille de fonctions exec() pour exécuter ces utilitaires doivent s'assurer que l'argument passé dans arg0 ou argv[0] est '[' lors de l'exécution de l'utilitaire [ et a un nom de base de "test" lors de l'exécution de l'utilitaire test.

OPTIONS

L'utilitaire test ne reconnaîtra pas l'argument "--" de la manière spécifiée par la Directive 10 dans le volume Base Definitions de POSIX.1‐2017, Section 12.2, Directives de syntaxe des utilitaires.

Aucune option ne sera prise en charge.

OPÉRANDES

L'application doit s'assurer que tous les opérateurs et éléments des primaires sont présentés comme des arguments séparés à l'utilitaire test.

Les éléments de expression peuvent être regroupés en utilisant les parenthèses. Les expressions doivent être échappées ou citées pour éviter qu'elles ne soient interprétées par le shell.

Les opérateurs suivants peuvent être utilisés pour construire expression:

Opérateurs unaires
Les opérateurs unaires peuvent être précédés de l'opérateur unaire logique NOT ! .
Opérateurs binaires
Les opérateurs binaires sont évalués de gauche à droite.

Les opérateurs suivants sont disponibles :

!
Vrai si l'expression qui suit est fausse. Faux si l'expression qui suit est vraie.
-a
Vrai si les deux expressions qui suivent sont vraies ; sinon, faux. Cet opérateur est moins prioritaire que les opérateurs de comparaison de chaînes et numériques.
-o
Vrai si l'une des expressions qui suit est vraie ; sinon, faux. Cet opérateur est moins prioritaire que les opérateurs de comparaison de chaînes et numériques.
(expression)
Vrai si l'expression entre parenthèses est vraie ; sinon, faux. Les parenthèses elles-mêmes doivent être protégées du shell.

L'utilitaire [ a été introduit pour permettre la construction de scripts de shell plus lisibles et est documenté dans la spécification POSIX. Le comportement de [ est identique à celui de test, à l'exception de la nécessité d'un argument ].

À l'exception des primaires -h pathname et -L pathname, si un argument pathname est un lien symbolique, test évalue l'expression en résolvant le lien symbolique et en utilisant le fichier référencé par le lien.

Ces primaires peuvent être combinés avec les opérateurs suivants :

! expression
True si expression est fausse. Faux si expression est vraie.
( expression )
True si expression est vraie. Faux si expression est fausse. Les parenthèses peuvent être utilisées pour modifier la priorité et l'associativité normales.

Les primaires à deux éléments de la forme :

-opérateur_primaire opérande_primaire

sont connus sous le nom de primaires unaires. Les primaires à trois éléments sous l'une ou l'autre des deux formes :

opérande_primaire -opérateur_primaire opérande_primaire
opérande_primaire opérateur_primaire opérande_primaire

sont connus sous le nom de primaires binaires. Des opérateurs et opérateur_primaires supplémentaires définis par l'implémentation peuvent être fournis. Ils doivent être de la forme -opérateur où le premier caractère de opérateur n'est pas un chiffre.

L'algorithme de détermination de la priorité des opérateurs et de la valeur de retour qui doit être générée est basé sur le nombre d'arguments présentés à test. (Cependant, lors de l'utilisation de la forme "[...]", le crochet right-square-bracket final ne doit pas être compté dans cet algorithme.)

Dans la liste suivante, $1, $2, $3 et $4 représentent les arguments présentés à test :

0 arguments :
Sortie fausse (1).
1 argument :
Sortie vraie (0) si $1 n'est pas nul ; sinon, sortie fausse.
2 arguments :
*
Si $1 est '!', sortie vraie si $2 est nul, fausse si $2 n'est pas nul.
*
Si $1 est un primaire unaire, sortie vraie si le test unaire est vrai, fausse si le test unaire est faux.
*
Sinon, résultats non spécifiés.
3 arguments :
*
Si $2 est un primaire binaire, effectue le test binaire de $1 et $3.
*
Si $1 est '!', nie le test à deux arguments de $2 et $3.
*
Si $1 est '(' et $3 est ')', effectue le test unaire de $2. Sur les systèmes qui ne prennent pas en charge l'option XSI, les résultats sont non spécifiés si $1 est '(' et $3 est ')'.
*
Sinon, résultats non spécifiés.
4 arguments :
*
Si $1 est '!', nie le test à trois arguments de $2, $3 et $4.
*
Si $1 est '(' et $4 est ')', effectue le test à deux arguments de $2 et $3. Sur les systèmes qui ne prennent pas en charge l'option XSI, les résultats sont non spécifiés si $1 est '(' et $4 est ')'.
*
Sinon, les résultats sont non spécifiés.
>4 arguments :
Les résultats sont non spécifiés.

Sur les systèmes conformes XSI, les combinaisons de primaires et d'opérateurs sont évaluées en utilisant les règles de priorité et d'associativité décrites précédemment. De plus, les primaires binaires de comparaison de chaînes '=' et "!=" ont une priorité plus élevée que tout primaire unaire.

UTILISATION PAR L'APPLICATION

Les extensions XSI spécifiant les primaires binaires -a et -o ainsi que les opérateurs '(' et ')' ont été marquées comme obsolètes. (De nombreuses expressions les utilisant sont ambiguës selon la grammaire, en fonction des expressions spécifiques évaluées.) Les scripts utilisant ces expressions devraient être convertis aux formes indiquées ci-dessous. Bien que de nombreuses implémentations continuent de prendre en charge ces formes obsolètes, les scripts doivent être extrêmement prudents lorsqu'ils traitent des entrées fournies par l'utilisateur qui pourraient être confondues avec ces primaires et opérateurs ou d'autres. Sauf si le développeur de l'application connaît tous les cas qui produisent des entrées pour le script, des invocations comme :

test "$1" -a "$2"

devraient être écrites comme suit :

test "$1" && test "$2"

pour éviter les problèmes si un utilisateur fournit des valeurs comme $1 défini sur '!' et $2 défini sur la chaîne nulle. C'est-à-dire que, dans les cas où la portabilité maximale est une préoccupation, remplacez :

test expr1 -a expr2

par :

test expr1 && test expr2

et remplacez :

test expr1 -o expr2

par :

test expr1 || test expr2

mais notez que, dans test, -a a une priorité plus élevée que -o tandis que "&&" et "||" ont une priorité égale dans le shell.

Les parenthèses ou les accolades peuvent être utilisées dans le langage de commande du shell pour effectuer un regroupement.

Les parenthèses doivent être échappées lors de l'utilisation de sh ; par exemple :

test \( expr1 -a expr2 \) -o expr3

Cette commande n'est pas toujours portable, même sur les systèmes conformes XSI, en fonction des expressions spécifiées par expr1, expr2 et expr3. La forme suivante peut être utilisée à la place :

( test expr1 &
p;& test expr2 ) || test expr3

Les deux commandes :

test "$1"
test ! "$1"

ne pouvaient pas être utilisées de manière fiable sur certains systèmes historiques. Des résultats inattendus se produiraient si une telle expression de string était utilisée et que $1 s'étendait à '!', '(', ou à un unaire primaire connu. De meilleures constructions sont :

test -n "$1"
test -z "$1"

respectivement.

Les systèmes historiques ont également été peu fiables étant donné la construction courante :

test "$response" = "expected string"

L'une des formes suivantes est une forme plus fiable :

test "X$response" = "Xexpected string"
test "expected string" = "$response"

Notez que la deuxième forme suppose que expected string ne pourrait pas être confondue avec un primaire unaire. Si expected string commence par '-', '(', '!', ou même '=', la première forme doit être utilisée à la place. En utilisant les règles précédentes sans les extensions marquées XSI, l'une des trois formes de comparaison est fiable, compte tenu de toute entrée. (Cependant, notez que les chaînes sont citées dans tous les cas.)

Étant donné que les primaires binaires de comparaison de chaînes, '=' et "!=", ont une priorité supérieure à celle de tout primaire unaire dans le cas de plus de 4 arguments, des résultats inattendus peuvent se produire si les arguments ne sont pas correctement préparés. Par exemple, dans :

test -d $1 -o -d $2

Si $1 s'évalue à un nom de répertoire possible de '=', les trois premiers arguments sont considérés comme une comparaison de chaînes, ce qui provoquera une erreur de syntaxe lors de la rencontre du deuxième -d. L'une des formes suivantes empêche cela ; la seconde est préférée :

test \( -d "$1" \) -o \( -d "$2" \)
test -d "$1" || test -d "$2"

Aussi dans le cas de plus de 4 arguments :

test "$1" = "bat" -a "$2" = "ball"

des erreurs de syntaxe se produisent si $1 s'évalue à '(' ou '!'. L'une des formes suivantes empêche cela ; la troisième est préférée :

test "X$1" = "Xbat" -a "X$2" = "Xball"
test "$1" = "bat" && test "$2" = "ball"
test "X$1" = "Xbat" && test "X$2" = "Xball"

Notez qu'aucun des exemples suivants n'est autorisé par la syntaxe décrite :

[-f file]
[-f file ]
[ -f file]
[ -f file
test -f file ]

Dans les deux premiers cas, si une utilité nommée [‐f existe, cette utilité serait invoquée, et non test. Dans les cas restants, les crochets sont déséquilibrés et le comportement n'est pas spécifié. Cependant :

test ! ]

a une signification définie et doit se terminer avec le statut 1. De même :

test ]

doit se terminer avec le statut 0.

EXEMPLES

1.
Sortir s'il n'y a pas deux ou trois arguments (deux variations) :
if [ $# -ne 2 ] && [ $# -ne 3 ]; then exit 1; fi
if [ $# -lt 2 ] || [ $# -gt 3 ]; then exit 1; fi
2.
Créer un répertoire s'il n'existe pas :
test ! -d tempdir && mkdir tempdir
3.
Attendre qu'un fichier devienne illisible :
while test -r thefile
do
    sleep 30
done
echo '"thefile" n’est plus lisible'
4.
Exécuter une commande si l'argument est l'une des trois chaînes (deux variations) :
if [ "$1" = "pear" ] || [ "$1" = "grape" ] || [ "$1" = "apple" ]
then
    command
fi
case "$1" in
    pear|grape|apple) command ;;
esac

JUSTIFICATION

La commande conditionnelle dérivée de KornShell (double crochet [[]]) a été retirée de la description du langage de commande du shell dans une première proposition. Des objections ont été soulevées selon lesquelles le vrai problème est une mauvaise utilisation de la commande test ([), et son intégration dans le shell est la mauvaise façon de résoudre le problème. Au lieu de cela, une documentation appropriée et un nouveau mot réservé du shell (!) sont suffisants.

Les tests qui nécessitent plusieurs opérations test peuvent être effectués au niveau du shell en utilisant des invocations individuelles de la commande test et des logiques de shell, plutôt que d'utiliser le flag -o de test, sujet aux erreurs.

Les systèmes conformes XSI prennent en charge plus de quatre arguments.

Les systèmes conformes XSI prennent en charge la combinaison de primaires avec les constructions suivantes :

expression1 -a expression2

Vrai si expression1 et expression2 sont toutes deux vraies.
expression1 -o expression2

Vrai si au moins l'une des expression1 et expression2 est vraie.
( expression )

Vrai si expression est vraie.

Dans l'évaluation de ces expressions combinées plus complexes, les règles de priorité suivantes sont utilisées :

*
Les primaires unaires ont une priorité supérieure aux primaires binaires algébriques.
*
Les primaires unaires ont une priorité inférieure aux primaires binaires de chaînes.
*
Les primaires unaires et binaires ont une priorité supérieure au primaire unaire string.
*
L'opérateur ! a une priorité supérieure à l'opérateur -a, et l'opérateur -a a une priorité supérieure à l'opérateur -o.
*
Les opérateurs -a et -o sont associatifs à gauche.
*
Les parenthèses peuvent être utilisées pour modifier la priorité et l'associativité normales.

Les versions BSD et System V de -f ne sont pas les mêmes. La définition BSD était :

-f file
Vrai si file existe et n'est pas un répertoire.

La version SVID (vrai si le fichier existe et est un fichier régulier) a été choisie pour ce volume de POSIX.1‐2017 car son utilisation est cohérente avec les opérandes -b, -c, -d et -p (file existe et est un type de fichier spécifique).

Le primaire -e, possédant des fonctionnalités similaires à celles fournies par le shell C, a été ajouté car il fournit le seul moyen pour un script shell de savoir si un fichier existe sans essayer d'ouvrir le fichier. Les implémentations étant autorisées à ajouter des types de fichiers supplémentaires, un script portable ne peut pas utiliser :

test -b foo -o -c foo -o -d foo -o -f foo -o -p foo

pour savoir si foo est un fichier existant. Sur les systèmes BSD historiques, l'existence d'un fichier pouvait être déterminée par :

test -f foo -o -d foo

mais il n'y avait pas de moyen facile de déterminer qu'un fichier existant était un fichier régulier. Une première proposition utilisait le primaire -a de KornShell (avec la même signification), mais cela a été changé en -e car il y avait des préoccupations concernant la forte probabilité que les humains confondent le primaire -a avec l'opérateur binaire -a.

Les options suivantes n'ont pas été incluses dans ce volume de POSIX.1‐2017, bien qu'elles soient fournies par certaines implémentations. Ces opérandes ne devraient pas être utilisés par les nouvelles implémentations à d'autres fins :

-k file
Vrai si file existe et que son bit collant est activé.
-C file
Vrai si file est un fichier contigu.
-V file
Vrai si file est un fichier versionné.

Les opérandes -b, -c, -g, -p, -u et -x sont dérivés du SVID ; les systèmes BSD historiques ne les fournissent pas. L'opérande -k est dérivé de System V ; les systèmes BSD historiques ne le fournissent pas.

Sur les systèmes BSD historiques, test -w directory retournait toujours faux car test essayait d'ouvrir le répertoire en écriture, ce qui échoue toujours.

Certains primaires supplémentaires nouvellement inventés ou issus de KornShell sont apparus dans une première proposition dans le cadre de la commande conditionnelle ([[]]) : s1 > s2, s1 < s2, str = pattern, str != pattern, f1 -nt f2, f1 -ot f2, et f1 -ef f2. Ils n'ont pas été transférés dans l'utilitaire test lorsque la commande conditionnelle a été retirée du shell car ils n'ont pas été inclus dans l'utilitaire test intégré dans les implémentations historiques de l'utilitaire sh.

Le primaire -t file_descriptor est montré avec un argument obligatoire car la grammaire est ambiguë s'il peut être omis. Les implémentations historiques l'ont permis d'être omis, fournissant une valeur par défaut de 1.

Il est à noter que '[' ne fait pas partie de l'ensemble de caractères de noms de fichiers portables ; cependant, puisqu'il doit être codé par un seul octet, et fait partie de l'ensemble de caractères portables, le nom de cette utilité forme une chaîne de caractères dans toutes les locales supportées.

NAME

test - condition command or function

SYNOPSIS

sh
   [ ! ] operand [ operator operand ]...
   [ operand ]

DESCRIPTION

The test utility shall evaluate the expression specified by its arguments and shall write one of the characters to standard output. The exit status shall be zero if the expression is true, and non-zero if the expression is false.

The test utility is a shell built-in or external utility. If test is a shell built-in utility, see sh utility.

The following operators shall be supported. Operators and their necessary operands shall be described by the context notation of the synopsis. The “[:class:]” constructs (where class is one of the POSIX character classes) shall be supported for portability. The “[:class:]” constructs shall expand to a pattern that matches any character in the specified class.

The expression shall be evaluated according to the precedence rules for the “sh” operators:

  • ! (logical NOT)

  • -a (logical AND)

  • -o (logical OR)

Parentheses ( operand ) shall be used for grouping. The parentheses shall be delimited by spaces and escaped from the shell.

The following operand types shall be supported:

  • String comparison:

    • s1 = s2

      True if the expanded value of s1 is identical to the expanded value of s2.

    • s1 != s2

      True if the expanded value of s1 is not identical to the expanded value of s2.

    • s1 < s2

      True if the expanded value of s1 lexicographically is less than the expanded value of s2.

    • s1 > s2

      True if the expanded value of s1 lexicographically is greater than the expanded value of s2.

    • -n s

      True if the expanded value of s is not a null string.

    • -z s

      True if the expanded value of s is a null string.

  • File attribute tests:

    • -b x

      True if x exists and is a block special file.

    • -c x

      True if x exists and is a character special file.

    • -d x

      True if x exists and is a directory.

    • -e x

      True if x exists.

    • -f x

      True if x exists and is a regular file.

    • -g x

      True if x exists and has the set-group-ID bit set.

    • -h x

      True if x exists and is a symbolic link.

    • -k x

      True if x exists and has the sticky bit set.

    • -L x

      True if x exists and is a symbolic link. (This is a synonym for “-h”.)

    • -p x

      True if x exists and is a first-in, first-out (FIFO) special file.

    • -r x

      True if x exists and is readable.

    • -S x

      True if x exists and is a socket.

    • -t fildes

      True if file descriptor fildes is open and refers to a terminal.

    • -u x

      True if x exists and has the set-user-ID bit set.

    • -w x

      True if x exists and is writable.

    • -x x

      True if x exists and is executable.

    • -O x

      True if x exists and is owned by the effective user ID.

    • -G x

      True if x exists and is owned by the effective group ID.

    • file - nt

      True if file exists and was modified more recently than nt.

    • file - ot

      True if file exists and was modified more recently than ot.

    • file - ef

      True if file and ef exist and refer to the same file.

  • Integer comparison:

    • n1 -eq n2

      True if the integer n1 is equal to the integer n2.

    • n1 -ne n2

      True if the integer n1 is not equal to the integer n2.

    • n1 -gt n2

      True if the integer n1 is greater than the integer n2.

    • n1 -ge n2

      True if the integer n1 is greater than or equal to the integer n2.

    • n1 -lt n2

      True if the integer n1 is less than the integer n2.

    • n1 -le n2

      True if the integer n1 is less than or equal to the integer n2.

If an operand is not present, the expression shall be evaluated as false, except for the “-n” and “-z” operators.

EXAMPLES

# Test if a file exists and is readable
if test -r file.txt; then
    echo "file.txt is readable"
fi

# Test if two strings are equal
if [ "$string1" = "$string2" ]; then
    echo "Strings are equal"
fi

# Test if an integer is greater than another
if [ $int1 -gt $int2 ]; then
    echo "$int1 is greater than $int2"
fi

# Test for multiple conditions
if [ -f "$file" -a -w "$file" ]; then
    echo "$file exists and is writable"
fi

RATIONALE

The test utility provides a way to evaluate conditional expressions within shell scripts. It is essential for controlling the flow of execution based on various conditions, such as file attributes, string comparisons, and integer comparisons.

The POSIX standard specifies a comprehensive set of operators for test to ensure portability across different systems. The use of “[:class:]” constructs further enhances portability by providing a locale-independent way to test character classes.

The recommendation to use [ expression ] instead of the test command is based on POSIX standardization. This syntax is often preferred for its conciseness and integration with shell scripting.
