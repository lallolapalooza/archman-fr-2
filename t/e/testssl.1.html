TESTSSL(1) Manuel des commandes générales TESTSSL(1)

NOM

testssl

NOM

testssl.sh -- vérifie le chiffrement des serveurs SSL/TLS

SYNTAXE

testssl.sh [OPTIONS] <URI>, testssl.sh [OPTIONS] --file <FICHIER>

ou

testssl.sh [OPTIONS BANNIÈRE]

DESCRIPTION

testssl.sh est un outil gratuit en ligne de commande qui vérifie le support des chiffrements, protocoles SSL/TLS ainsi que les failles cryptographiques et bien plus encore, sur le service d'un serveur sur n'importe quel port.

La sortie classe les résultats par couleur (écran) ou gravité (sortie fichier) afin que vous puissiez déterminer si quelque chose est bon ou mauvais. La sortie (écran) comporte plusieurs sections dans lesquelles des classes de vérifications sont effectuées. Pour faciliter la lisibilité à l'écran, elle aligne et indente correctement la sortie.

Seulement vous voyez le résultat. Vous pouvez également l'utiliser en interne sur votre réseau local. À l'exception des recherches DNS ou à moins que vous n'instruisiez testssl.sh de vérifier la révocation des certificats, il n'utilise aucun autre hôte ni même des tiers pour aucun test.

EXIGENCES

Testssl.sh est portable dès la sortie de la boîte : il fonctionne sous n'importe quelle pile de type Unix : Linux, *BSD, MacOS X, WSL=Windows Subsystem for Linux, Cygwin et MSYS2. bash est une prérequis, la version 3 est encore supportée. Les utilitaires standard comme awk, sed, tr et head sont également nécessaires. Ceux-ci peuvent être d'une saveur BSD, System 5 ou GNU, tandis que grep de System V n'est pas encore supporté.

Toute version d'OpenSSL ou LibreSSL est nécessaire comme aide. Contrairement aux versions précédentes de testssl.sh, presque toutes les vérifications sont effectuées via des sockets (TCP). De plus, des binaires OpenSSL liés statiquement pour les principaux systèmes d'exploitation sont fournis dans ./bin/.

GENERAL

testssl.sh URI comme invocation par défaut effectue ce qu'on appelle une exécution par défaut, qui effectue un certain nombre de vérifications et affiche les résultats en couleur (ANSI et termcap) à l'écran. Elle effectue chaque vérification listée ci-dessous, à l'exception de -E, qui sont (ordre d'apparition) :

0) affiche une bannière (voir ci-dessous), effectue une recherche DNS également pour d'autres adresses IP et effectue une recherche inverse pour l'adresse IP retournée. Enfin, une vérification de service est effectuée.

1) vérification du protocole SSL/TLS

2) catégories de chiffrements standard

3) préférences de chiffrements du serveur (ordre du serveur ?)

4) transmission sécurisée (forward secrecy) : chiffrements et courbes elliptiques

5) paramètres par défaut du serveur (informations sur le certificat, extensions TLS, informations de session)

6) en-tête HTTP (si HTTP détecté ou forcé via --assume-http)

7) vulnérabilités

8) test de chacun des 370 chiffrements préconfigurés

9) simulation client

10) notation

OPTIONS ET PARAMÈTRES

Les options sont soit des options courtes, soit des options longues. Toute option courte ou longue nécessitant une valeur peut être appelée avec ou sans signe égal. Par exemple, testssl.sh -t=smtp --wide --openssl=/usr/bin/openssl <URI> (options courtes avec signe égal) est équivalent à testssl.sh --starttls smtp --wide --openssl /usr/bin/openssl <URI> (option longue sans signe égal). Certaines options de ligne de commande peuvent également être prédéfinies via des variables d'environnement. WIDE=true OPENSSL=/usr/bin/openssl testssl.sh --starttls=smtp <URI> serait l'équivalent des exemples susmentionnés. La préférence va à la ligne de commande par rapport à toutes les variables d'environnement.

<URI> ou --file <FICHIER> doit toujours être le dernier paramètre.

OPTIONS BANNIÈRE (standalone)

--help (ou aucun argument) affiche l'aide de la ligne de commande

-b, --banner affiche la bannière de testssl.sh, y compris la licence, les conditions d'utilisation, la version de testssl.sh, la version d'openssl détectée, son chemin d'accès, le nombre de chiffrements d'openssl, sa date de compilation et l'architecture.

-v, --version identique à ce qui précède

-V [motif], --local [motif] imprime joliment tous les chiffrements locaux supportés par la version openssl. Si un motif est fourni, il effectue une correspondance (ignore la casse) sur l'une des chaînes fournies dans la sortie large (wide), voir ci-dessous. Le motif sera recherché dans n'importe quelle colonne : code hexadécimal, nom de suite de chiffrement (OpenSSL ou IANA), échange de clés, chiffrement, bits. Il effectue une correspondance de motif de mot pour les non-numériques, pour les nombres une correspondance normale s'applique. Les nombres ici sont définis comme [0-9,A-F]. Cela signifie (attention : attention) que le motif CBC est mis en correspondance comme non-mot, mais AES comme mot. Cette option accepte également --openssl=<chemin_vers_openssl>.

PARAMÈTRES D'ENTRÉE

URI peut être un nom d'hôte, une adresse IPv4 ou IPv6 (restriction voir ci-dessous) ou une URL. Les adresses IPv6 doivent être entre crochets. Pour tout paramètre donné, le port 443 est supposé sauf s'il est spécifié en ajoutant un deux-points et un numéro de port. Le seul spécificateur de protocole précédent autorisé est https. Vous devez être conscient que les vérifications pour une adresse IP pourraient ne pas atteindre le vhost souhaité. La résolution DNS (enregistrement A/AAAA) est effectuée sauf si vous avez une entrée /etc/hosts pour le nom d'hôte.

--file <nom_fichier> ou l'équivalent -iL <nom_fichier> sont des options de test de masse. Par défaut, il active implicitement --warnings batch sauf si les avertissements ont été désactivés au préalable. Dans sa première incarnation, l'option de test de masse lit les lignes de commande depuis nom_fichier. nom_fichier est composé de lignes de commande de testssl, une ligne par instance. Les commentaires après # sont ignorés, EOF signale la fin de nom_fichier, toutes les lignes subséquentes seront ignorées aussi. Vous pouvez également fournir des options supplémentaires qui seront héritées à chaque enfant, par exemple : lors de l'appel de testssl.sh --wide --log --file <nom_fichier>. Chaque ligne individuelle dans nom_fichier est analysée lors de l'exécution. S'il y a une option conflictuelle et que le test de masse séquentiel est en cours, la vérification sera interrompue au moment où elle se produit et, en fonction de l'option de sortie, pourrait vous laisser avec un fichier de sortie sans pied de page. En mode parallèle, les résultats varient, il est probable qu'une ligne ne soit pas analysée.

Alternativement, nom_fichier peut être au format de sortie grep(p)able de nmap (-oG). Seuls les ports ouverts seront pris en compte. Plusieurs ports par ligne sont autorisés. Les ports peuvent être différents et seront testés par testssl.sh conformément aux pratiques courantes sur Internet, c'est-à-dire si nmap montre dans sa sortie un port ouvert 25, automatiquement -t smtp sera ajouté avant l'URI, tandis que le port 465 sera traité comme un port TLS/SSL standard, ne nécessitant pas de handshake SMTP STARTTLS au préalable. Ceci est fait par une table interne qui corrèle le port ouvert détecté par nmap avec la décision STARTTLS/texte brut de testssl.sh.

La sortie Nmap retourne toujours des adresses IP et seulement s'il existe un enregistrement DNS PTR, un nom d'hôte. Comme nmap ne vérifie pas si le nom d'hôte correspond à l'IP (enregistrement A ou AAAA), testssl.sh le fait automatiquement pour vous. Si l'enregistrement A du nom d'hôte correspond à l'adresse IP, le nom d'hôte est utilisé et non l'adresse IP. Veuillez garder à l'esprit que les vérifications sur une adresse IP pourraient ne pas atteindre le vhost auquel vous visiez peut-être et ainsi conduire à des résultats différents.

Une conversion interne typique au format de fichier testssl.sh à partir du format grep(p)able de nmap pourrait ressembler à ceci :

10.10.12.16:443 10.10.12.16:1443 -t smtp host.example.com:25 host.example.com:443 host.example.com:631 -t ftp 10.10.12.11:21 10.10.12.11:8443 Notez que nom_fichier doit être au format Unix. Les retours chariot DOS ne seront pas acceptés. Au lieu du commutateur de ligne de commande, la variable d'environnement FNAME sera également prise en compte.

--reqheader <en-tête> Ceci peut être utilisé pour ajouter des en-têtes de requête HTTP supplémentaires dans le format correct Nom-en-tête: contenu-en-tête. Ce paramètre peut être appelé plusieurs fois si nécessaire. Par exemple : --reqheader 'Proxy-Authorization: Basic dGVzdHNzbDpydWxlcw==' --reqheader 'ClientID: 0xDEADBEAF'. INVOCATIONS SPÉCIALES

-t <protocole>, --starttls <protocole> effectue une exécution par défaut sur un protocole activé STARTTLS. protocole doit être l'un des éléments suivants : ftp, smtp, pop3, imap, xmpp, sieve, xmpp-server, telnet, ldap, irc, lmtp, nntp, postgres, mysql. Pour les quatre derniers, vous avez besoin, par exemple, d'OpenSSL fourni ou d'OpenSSL version 1.1.1. Veuillez noter : MongoDB n'offre pas de connexion STARTTLS, IRC ne fonctionne actuellement qu'avec --ssl-native. irc est en cours de développement.

--xmpphost <domaine_jabber> est une option supplémentaire pour XMPP activé STARTTLS : elle attend le domaine Jabber comme paramètre. Ceci n'est nécessaire que si le domaine est différent de l'URI fourni.

--mx <domaine|hôte> teste tous les enregistrements MX (STARTTLS sur le port 25) de haute à basse priorité, l'un après l'autre.

--ip <ip> teste soit l'adresse IPv4 ou IPv6 fournie au lieu de résoudre les hôtes dans <URI>. Les adresses IPv6 doivent être fournies entre crochets. --ip=one signifie : tester uniquement le premier enregistrement A renvoyé par DNS (utile pour plusieurs adresses IP). Si -6 et --ip=one ont été fournis, un enregistrement AAAA sera choisi s'il est disponible. L'option --ip peut également être utile si vous souhaitez résoudre le nom d'hôte fourni vers une adresse IP différente, similaire à ce que vous feriez en modifiant /etc/hosts ou /c/Windows/System32/drivers/etc/hosts. --ip=proxy tente une résolution DNS via proxy. --ip=proxy plus --nodns=min est utile pour les situations sans DNS local, car il n'y aura pas de timeouts DNS lors de la tentative de résolution des enregistrements CAA, TXT et MX.

--proxy <hôte>:<port> effectue TOUTES les vérifications via le proxy spécifié. --proxy=auto hérite du paramètre proxy de l'environnement. Tout nom d'hôte fourni sera résolu vers le premier enregistrement A, s'il n'existe pas, l'enregistrement AAAA est utilisé. Les adresses IPv4 et IPv6 peuvent également être fournies, ces dernières *également* avec la notation entre crochets. Veuillez noter que vous avez besoin d'une version plus récente d'OpenSSL ou de LibreSSL pour la fonctionnalité de proxy IPv6. De plus, si vous souhaitez des recherches via proxy, vous pouvez spécifier DNS_VIA_PROXY=true. La vérification de révocation OCSP (-S --phone-out) n'est pas prise en charge par OpenSSL via proxy. Comme la fourniture d'un proxy est un indicateur que les ports 80 et 443 sortants sont bloqués dans votre réseau, une vérification de révocation OCSP ne sera pas effectuée. Cependant, si IGN_OCSP_PROXY=true a été fourni, elle sera tentée directement. L'authentification auprès du proxy n'est pas prise en charge. Le proxy via des adresses IPv6 n'est pas pris en charge, ni les proxys HTTPS ou SOCKS.

-6 effectue (également) des vérifications IPv6. Veuillez noter que testssl.sh n'effectue pas de vérifications sur une adresse IPv6 automatiquement, pour deux raisons : testssl.sh n'effectue pas de vérifications de connectivité pour IPv6 et il ne peut pas déterminer de manière fiable si le binaire OpenSSL que vous utilisez prend en charge le s_client IPv6. -6 suppose que les deux sont le cas. Si les deux conditions sont remplies et que vous préférez généralement tester également les branches IPv6, vous pouvez ajouter HAS_IPv6 à votre environnement shell. Outre le binaire OpenSSL fourni, IPv6 est connu pour fonctionner avec OpenSSL standard >= 1.1.0 et les versions plus anciennes >=1.0.2 dans RHEL/CentOS/FC et Gentoo.

--ssl-native Au lieu d'utiliser un mélange de sockets bash et de quelques connexions openssl s_client, testssl.sh utilise ce dernier (presque) uniquement. C'est plus rapide mais fournit des résultats moins précis, en particulier pour la simulation client et le support des chiffrements. Pour toutes les vérifications, vous verrez un avertissement si testssl.sh ne peut pas dire si une vérification particulière ne peut pas être effectuée. Pour certaines vérifications, cependant, vous pourriez finir par obtenir de faux négatifs sans avertissement. Par conséquent, son utilisation n'est pas recommandée. Il ne doit être utilisé que si vous préférez la vitesse à la précision ou si vous savez que votre cible présente un chevauchement suffisant avec les protocoles et les chiffrements fournis par votre binaire openssl.

--openssl <chemin_vers_openssl> testssl.sh essaie très fort de trouver automatiquement le binaire fourni (où se trouve l'arborescence de testssl.sh, depuis le répertoire où testssl.sh a été lancé, etc.). Si tout cela ne fonctionne pas, il se rabat sur openssl fourni par le système d'exploitation ($PATH). Avec cette option, vous pouvez pointer testssl.sh vers le binaire de votre choix et outrepasser toute magie interne pour trouver le binaire openssl. (Environnement prédéfini via OPENSSL=<chemin_vers_openssl>).

OPTIONS DE REGLAGE

--bugs effectue des contournements pour des serveurs bogués comme le padding pour les anciens appareils F5. L'option est passée comme -bug à openssl si nécessaire, voir s_client(1), environnement prédéfini via BUGS="-bugs" (1 trait d'union). Pour la partie socket, testssl.sh a toujours des contournements en place pour faire face aux implémentations serveur défectueuses.

--assuming-http testssl.sh effectue normalement une détection de protocole d'application en amont. Dans les cas où HTTP ne peut pas être détecté automatiquement, vous pourriez vouloir utiliser cette option. Elle oblige testssl.sh à ne pas sauter les tests spécifiques à HTTP (en-tête HTTP) et à exécuter une simulation client basée sur le navigateur. Veuillez noter que la sévérité dépend parfois également du protocole d'application, par exemple, les certificats signés SHA1, l'absence de correspondance SAN et certaines vulnérabilités seront plus sévèrement punies lors de la vérification d'un serveur Web par rapport à un serveur de messagerie.

-n, --nodns <min|none> indique à testssl.sh quelles recherches DNS doivent être effectuées. min utilise uniquement la résolution DNS directe (enregistrement A et AAAA ou enregistrement MX) et saute les recherches CAA et les enregistrements PTR de l'adresse IP vers un nom DNS. none n'effectue aucune recherche DNS. Pour cette dernière, vous devez soit fournir l'adresse IP comme cible, soit utiliser --ip ou avoir l'adresse IP dans /etc/hosts. L'utilisation de ce commutateur n'est utile que si vous ne pouvez pas ou ne voulez pas effectuer de recherches DNS. Ce dernier peut s'appliquer, par exemple, à certains pentests. En général, cette option pourrait, par exemple, vous aider à éviter les timeouts dus aux recherches DNS. NODNS est la variable d'environnement correspondante. --nodns=min plus --ip=proxy est utile pour les situations sans DNS local, car il n'y aura pas de timeouts DNS lors de la tentative de résolution des enregistrements CAA, TXT et MX.

--sneaky Pour les vérifications d'en-têtes HTTP, testssl.sh utilise normalement l'agent utilisateur HTTP respectueux du serveur TLS tester from ${URL}. Avec cette option, vos traces sont moins verbeuses et un agent utilisateur Firefox est utilisé. Soyez conscient que cela ne cache pas vos activités. Ce n'est tout simplement pas possible (environnement prédéfini via SNEAKY=true).

--user-agent <agent utilisateur> indique à testssl.sh d'utiliser l'agent utilisateur HTTP fourni au lieu de l'agent utilisateur standard TLS tester from ${URL}.

--ids-friendly est un commutateur qui peut aider à terminer un scan qui serait autrement bloqué par un IDS côté serveur. Ce commutateur saute les tests pour les vulnérabilités suivantes : Heartbleed, CCS Injection, Ticketbleed et ROBOT. La variable d'environnement OFFENSIVE définie sur false donnera le même résultat. Veuillez noter qu'en alternative ou comme approche générale, vous pouvez essayer d'appliquer des techniques d'évasion en modifiant les variables USLEEP_SND et / ou USLEEP_REC et peut-être MAX_WAITSOCK.

--phone-out La vérification des certificats révoqués via CRL et OCSP n'est pas effectuée par défaut. Ce commutateur demande à testssl.sh d'interroger des URI externes -- dans le sens de l'exécution actuelle --. En utilisant ce commutateur, vous reconnaissez que la vérification peut avoir des problèmes de confidentialité, un téléchargement de plusieurs mégaoctets (fichier CRL) peut se produire et il peut y avoir des problèmes de connectivité réseau lors du contact avec le point de terminaison que testssl.sh ne gère pas. PHONE_OUT est la variable d'environnement correspondante qui doit être définie sur true si vous le souhaitez.

--add-ca <fichier_CA> vous permet d'ajouter vos propres CA au format PEM pour les vérifications de la chaîne de confiance. fichier_CA peut être un répertoire contenant des fichiers avec l'extension .pem, un seul fichier ou plusieurs fichiers sous forme de liste de CA racine séparées par des virgules. Internement, ils seront ajoutés pendant l'exécution à tous les magasins de CA. Ceci est (uniquement) utile pour les hôtes internes dont les certificats sont émis par des CA internes. Alternativement, ADDTL_CA_FILES est la variable d'environnement correspondante.

OPTIONS DE VÉRIFICATION UNIQUE

Tout commutateur de vérification unique fourni comme argument empêche testssl.sh d'effectuer une exécution par défaut. Il prend simplement cela et, si fourni, d'autres options et les exécute - dans l'ordre où elles apparaîtraient également dans l'exécution par défaut.

-e, --each-cipher vérifie chacun des chiffrements (actuellement configurés) 370 via openssl + sockets à distance sur le serveur et rapporte le résultat en mode large. Si vous souhaitez afficher chaque chiffre testé, vous avez besoin

pour ajouter --show-each. Par défaut, il liste les paramètres suivants : code hexadécimal, nom de la suite de chiffrement OpenSSL, échange de clés, bits de chiffrement, nom de la suite de chiffrement IANA/RFC. Veuillez noter que le paramètre --mapping modifie les noms des suites de chiffrement que vous verrez ici et dans quel ordre. Veuillez également noter que la longueur en bits pour le chiffrement est affichée et non la longueur de sécurité, bien qu'elle soit triée selon cette dernière. Pour 3DES, en raison du problème Meet-in-the-Middle, la taille en bits de 168 bits équivaut à une taille de sécurité de 112 bits.

-E, --cipher-per-proto est similaire à -e, --each-cipher. Il vérifie chaque chiffrement possible, ici : par protocole. Si vous souhaitez afficher chaque chiffrement testé, vous devez ajouter --show-each. La sortie est triée par force de sécurité, elle liste les bits de chiffrement.

-s, --std, --categories teste certaines listes de suites de chiffrement / catégories de chiffrement par force. (--standard est obsolète.) Ces listes sont (openssl ciphers $LIST, $LIST ci-dessous :)

○
Chiffrements de chiffrement NUL : 'NULL:eNULL'
○
Chiffrements NUL anonymes : 'aNULL:ADH'
○
Chiffrements d'exportation (sans les précédents) : 'EXPORT:!ADH:!NULL'
○
FAIBLE (64 bits + chiffrements DES, sans les chiffrements EXPORT) : 'LOW:DES:RC2:RC4:MD5:!ADH:!EXP:!NULL:!eNULL:!AECDH'
○
Chiffrements 3DES + IDEA : '3DES:IDEA:!aNULL:!ADH:!MD5'
○
Chiffrements CBC obsolètes : 'HIGH:MEDIUM:AES:CAMELLIA:ARIA:!IDEA:!CHACHA20:!3DES:!RC2:!RC4:!AESCCM8:!AESCCM:!AESGCM:!ARIAGCM:!aNULL:!MD5'
○
Chiffrements forts sans FS (AEAD) : 'AESGCM:CHACHA20:CamelliaGCM:AESCCM:ARIAGCM:!kEECDH:!kEDH:!kDHE:!kDHEPSK:!kECDHEPSK:!aNULL'
○
Chiffrements forts avec Secret Parfait (AEAD) : 'AESGCM:CHACHA20:CamelliaGCM:AESCCM:ARIAGCM:!kPSK:!kRSAPSK:!kRSA:!kDH:!kECDH:!aNULL'

-f, --fs, --nsa, --forward-secrecy vérifie un échange de clés robuste avec secret parfait. "Robuste" signifie que les chiffrements présentant de graves faiblesses intrinsèques telles que l'authentification ou le chiffrement nul, 3DES et RC4 ne seront pas pris en compte ici. Il ne faut pas donner l'impression qu'un échange de clés sécurisé a eu lieu et que tout va bien, alors qu'en réalité le chiffrement est médiocre. Cette section liste également les courbes elliptiques et les groupes Diffie Hellman disponibles, ainsi que les groupes FFDHE (TLS 1.2 et TLS 1.3).

-p, --protocols vérifie les protocoles TLS/SSL SSLv2, SSLv3, TLS 1.0 à TLS 1.3 et pour HTTP : SPDY (NPN) et ALPN, alias HTTP/2. Pour TLS 1.3, plusieurs versions préliminaires (à partir de la 18) et la version finale sont supportées et testées. Notez que la version fournie d'openssl-bad ne prend pas en charge TLS 1.3. Comme la vérification de TLS 1.3 se fera sur les sockets, cela ne pose normalement pas de problème. Cependant, si un hôte utilisant uniquement TLS 1.3 est rencontré et pour avoir une couverture de test complète (par exemple, vérifications d'en-têtes), /usr/bin/openssl (ou le contenu de OPENSSL2) est vérifié pour son existence et sa prise en charge de TLS 1.3, et si ces tests réussissent, le programme basculera sur ce binaire. Un message vous en informera.

-P, --server-preference, --preference affiche les préférences du serveur : ordre des chiffrements, avec le client openssl utilisé : protocole et chiffrement négociés. S'il existe un ordre de chiffrement imposé par le serveur, il l'affiche pour chaque protocole (openssl+sockets). Sinon, il affiche à la place les chiffrements du serveur qui ont été choisis avec chaque protocole.

-S, --server_defaults affiche les informations du "server hello(s)" :

○
Extensions TLS disponibles,
○
Informations/capacités sur les tickets TLS + ID de session,
○

VULNÉRABILITÉS

-U, --vulnerable, --vulnerabilities Teste simplement toutes (les) vulnérabilités (suivantes). La variable d'environnement VULN_THRESHLD détermine après quelle valeur un titre séparé pour chaque vulnérabilité est affiché. La valeur par défaut est 1, ce qui signifie que si vous vérifiez deux vulnérabilités, seul le titre général de la section vulnérabilités est affiché -- en plus de la vulnérabilité et du résultat. Sinon, chaque vulnérabilité ou section de vulnérabilité obtient son propre titre en plus de la sortie du nom de la vulnérabilité et du résultat du test. Une section de vulnérabilité comprend plus d'une vérification, par exemple, la vérification de la vulnérabilité de renégociation comporte deux vérifications, tout comme Logjam.

-H, --heartbleed Vérifie Heartbleed, une fuite de mémoire dans openssl. Sauf si le côté serveur ne prend pas en charge l'extension heartbeat, il est probable que cette vérification se termine par un délai d'attente. Les secondes d'attente d'une réponse peuvent être ajustées avec HEARTBLEED_MAX_WAITSOCK. La valeur par défaut est 8.

-I, --ccs, --ccs-injection Vérifie l'injection CCS, qui est une vulnérabilité openssl. Parfois, la vérification nécessite d'attendre une réponse. Le délai d'attente prédéfini de 5 secondes peut être modifié avec la variable d'environnement CCS_MAX_WAITSOCK.

-T, --ticketbleed Vérifie la fuite de mémoire Ticketbleed dans les équilibreurs de charge BigIP.

--BB, --robot Vérifie la vulnérabilité à l'attaque ROBOT / (Return Of Bleichenbacher's Oracle Threat).

--SI, --starttls-injection Vérifie les vulnérabilités d'injection STARTTLS (SMTP, IMAP, POP3 uniquement). socat et OpenSSL >=1.1.0 sont nécessaires.

-R, --renegotiation Teste les vulnérabilités de renégociation. Actuellement, il existe une vérification pour la Renégociation Sécurisée et pour la Renégociation Initiée par le Client Sécurisée. Veuillez noter que les serveurs vulnérables à cette dernière peuvent probablement être très facilement soumis à des attaques par déni de service (HTTP). Une vérification de la Renégociation Initiée par le Client Non Sécurisée n'est pas encore implémentée.

-C, --compression, --crime Vérifie la vulnérabilité CRIME (Compression Ratio Info-leak Made Easy) dans TLS. CRIME dans SPDY n'est pas encore vérifié.

-B, --breach Vérifie la vulnérabilité BREACH (Browser Reconnaissance and Exfiltration via Adaptive Compression of Hypertext). Comme la compression au niveau HTTP est une condition préalable à cette vulnérabilité, elle ne sera pas testée si HTTP ne peut pas être détecté ou si la détection n'est pas forcée via --assume-http. Veuillez noter que seule l'URL fournie (normalement "/") est testée.

-O, --poodle Teste la vulnérabilité SSL POODLE (Padding Oracle On Downgraded Legacy Encryption). Il vérifie essentiellement l'existence de chiffrements CBC dans SSLv3.

-Z, --tls-fallback Vérifie la mitigation TLS_FALLBACK_SCSV. TLS_FALLBACK_SCSV est essentiellement une suite de chiffrements ajoutée au Client Hello pour tenter d'empêcher les attaques de dégradation de protocole

ks par un homme de milieu.

-W, --sweet32 Vérifie la vulnérabilité à SWEET32 en testant les chiffrements à bloc de 64 bits (3DES, RC2 et IDEA).

-F, --freak Vérifie la vulnérabilité FREAK (Factoring RSA Export Keys) en testant les chiffrements RSA d'EXPORTATION

-D, --drown Vérifie la vulnérabilité DROWN (Decrypting RSA with Obsolete and Weakened eNcryption) en vérifiant si le protocole SSL 2 est disponible sur la cible. Veuillez noter que si vous utilisez le même certificat RSA ailleurs, vous pourriez également être vulnérable. testssl.sh ne vérifie pas cela mais fournit un lien utile sur censys.io qui offre ce service.

-J, --logjam Vérifie la vulnérabilité LOGJAM en recherchant les chiffrements DH EXPORT. Il recherche également les "primes communs" qui sont des clés DH préconfigurées. Les clés DH =< 1024 bits seront pénalisées. Les groupes FFDHE (TLS 1.2) seront également affichés ici.

-A, --beast Vérifie les vulnérabilités BEAST dans SSL 3 et TLS 1.0 en testant l'utilisation des chiffrements CBC.

-L, --lucky13 Vérifie la vulnérabilité LUCKY13. Il recherche la présence de chiffrements CBC dans les versions TLS 1.0 à 1.2.

-WS, --winshock Vérifie la vulnérabilité Winshock. Il teste l'absence d'un grand nombre de chiffrements, de certaines extensions TLS et de courbes elliptiques qui ont été introduites plus tard dans Windows. Enfin, la bannière du serveur est examinée.

-4, --rc4, --appelbaum Vérifie quels chiffrements de flux RC4 sont proposés.

-q, --quiet Normalement, testssl.sh affiche une bannière sur stdout avec diverses informations de version, les droits d'utilisation et un avertissement. Cette option le supprime. Veuillez noter qu'en choisissant cette option, vous reconnaissez les conditions d'utilisation et l'avertissement apparaissant normalement dans la bannière.

--wide Sauf pour la "sortie de chaque chiffrement", tous les tests affichent le nom du chiffrement unique (schéma ci-dessous). Cette option permet à testssl.sh d'afficher également pour les sections suivantes la même sortie que pour le test de chaque chiffrement : BEAST, FS, RC4. La simulation client a également un mode large. La différence ici est limitée à une sortie alignée en colonnes et à un en-tête approprié. ○

○
\n

○

RATING

\n

Ce programme a une implémentation quasi complète du 'SSL Server Rating Guide' de SSL Labs\n https://github.com/ssllabs/research/wiki/SSL-Server-Rating-Guide.

\n

Ce n'est pas une réimplémentation à 100% du 'SSL Server Test' de SSL Labs https://www.ssllabs.com/ssltest/analyze.html, mais une implémentation de la spécification de notation ci-dessus, des divergences mineures peuvent survenir. Veuillez noter que pour l'instant, nous nous en tenons à la notation SSL Labs aussi fidèlement que possible. Nous ne sommes pas responsables de leur notation. Avant de signaler des problèmes, veuillez consulter leur guide de notation.

\n

Avis de non-responsabilité : Avoir une bonne note ne signifie PAS nécessairement e" } ] qual to having good security! Don't start a competition for the best grade, at least not without monitoring the client handshakes and not without adding a portion of good sense to it. Please note STARTTLS always results in a grade cap to T. Anything else would lead to a false sense of security. Use TLS, see also RFC 8314. The security of STARTTLS is always client determined, i'.e. checking the certificate which for SMTP port 25 is often enough not the case. Also with DANE or MTA-STS no one can test on the server side whether a client makes use if it.

As of writing, these checks are missing: * GOLDENDOODLE - should be graded F if vulnerable * Insecure renegotiation - should be graded F if vulnerable * Padding oracle in AES-NI CBC MAC check (CVE-2016-2107) - should be graded F if vulnerable * Sleeping POODLE - should be graded F if vulnerable * Zero Length Padding Oracle (CVE-2019-1559) - should be graded F if vulnerable * Zombie POODLE - should be graded F if vulnerable * All remaining old Symantec PKI certificates are distrusted - should be graded T * Symantec certificates issued before June 2016 are distrusted - should be graded T * Anonymous key exchange - should give 0 points in set_key_str_score() * Exportable key exchange - should give 40 points in set_key_str_score() * Weak key (Debian OpenSSL Flaw) - should give 0 points in set_key_str_score()

To implement a new grading cap, simply call the set_grade_cap() function, with the grade and a reason: bash set_grade_cap "D" "Vulnerable to documentation" To implement a new grade warning, simply call the set_grade_warning() function, with a message: bash set_grade_warning "Documentation is always right" #### Implementing a new check which contains grade caps When implementing a new check (be it vulnerability or not) that sets grade caps, the set_rating_state() has to be updated (i.e. the $do_mycheck variable-name has to be added to the loop, and $nr_enabled if-statement has to be incremented)

The set_rating_state() automatically disables rating, if all the required checks are not enabled. This is to prevent giving out a misleading or wrong grade.

When a new revision of the rating specification comes around, the following has to be done: * New grade caps has to be either: 1. Added to the script wherever relevant, or 2. Added to the above list of missing checks (if above is not possible) * New grade warnings has to be added wherever relevant * The revision output in run_rating() function has to updated

EXAMPLES

  testssl.sh testssl.sh

does a default run on https://testssl.sh (protocols, standard cipher lists, server's cipher preferences, forward secrecy, server defaults, vulnerabilities, client simulation, and rating.

  testssl.sh testssl.net:443

does the same default run as above with the subtle difference that testssl.net has two IPv4 addresses. Both are tested.

  testssl.sh --ip=one --wide https://testssl.net:443

does the same checks as above, with the difference that one IP address is being picked randomly. Displayed is everything where possible in wide format.

  testssl.sh -6 https://testssl.net

As opposed to the first example it also tests the IPv6 part -- supposed you have an IPv6 network and your openssl supports IPv6 (see above).

  testssl.sh -t smtp smtp.gmail.com:25

Checks are done via a STARTTLS handshake on the plain text port 25. It checks every IP on smtp.gmail.com.

    testssl.sh --starttls=imap imap.gmx.net:143

does the same on the plain text IMAP port.

Please note that for plain TLS-encrypted ports you must not specify the protocol option when no STARTTLS handshake is offered: testssl.sh smtp.gmail.com:465 just checks the encryption on the SMTPS port, testssl.sh imap.gmx.net:993 on the IMAPS port. Also MongoDB which provides TLS support without STARTTLS can be tested directly.
