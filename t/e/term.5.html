term(5) Formats de fichiers term(5)

NOM

term - description compilée d'un terminal terminfo

SYNOPSIS

term

DESCRIPTION

Emplacement de stockage

Les descriptions terminfo compilées sont placées sous le répertoire /usr/share/terminfo. Deux configurations sont supportées (lors de la compilation des bibliothèques ncurses) :

arborescence de répertoires
Un schéma à deux niveaux est utilisé pour éviter une recherche linéaire dans un immense répertoire du système Unix : /usr/share/terminfo/c/nom où nom est le nom du terminal, et c est le premier caractère de nom. Ainsi, act4 peut être trouvé dans le fichier /usr/share/terminfo/a/act4. Les synonymes pour le même terminal sont implémentés par plusieurs liens vers le même fichier compilé.
base de données hachée
Utilisant une base de données Berkeley, deux types d'enregistrements sont stockés : les données terminfo dans le même format que celui stocké dans une arborescence de répertoires avec le nom primaire de terminfo comme clé, et des enregistrements ne contenant que des alias pointant vers le nom primaire.
Si compilé pour écrire des bases de données hachées, ncurses peut toujours lire les bases de données terminfo organisées en arborescence de répertoires, mais ne peut pas écrire d'entrées dans l'arborescence de répertoires. Il peut écrire (ou réécrire) des entrées dans la base de données hachée.
ncurses distingue les deux cas dans la variable d'environnement TERMINFO et TERMINFO_DIRS en considérant une arborescence de répertoires pour les entrées qui correspondent à un répertoire existant, et une base de données hachée sinon.

Format de stockage hérité

Le format a été choisi de telle sorte qu'il soit le même sur tous les matériels. Un octet à 8 bits ou plus est supposé, mais aucune hypothèse sur l'ordre des octets ou l'extension de signe n'est faite.

Le fichier compilé est créé par le programme tic, et lu par la routine setupterm(3X). Le fichier est divisé en six parties :

a) en-tête,
b) noms de terminal,
c) indicateurs booléens,
d) nombres,
e) chaînes de caractères, et
f) table des chaînes.

L'en-tête section débute le fichier. Cette section contient six entiers courts dans le format décrit ci-dessous. Ces entiers sont

(1) le nombre magique (octal 0432) ;
(2) la taille, en octets, de la section des noms de terminal ;
(3) le nombre d'octets dans la section des indicateurs booléens ;
(4) le nombre d'entiers courts dans la section des nombres ;
(5) le nombre d'offsets (entiers courts) dans la section des chaînes ;
(6) la taille, en octets, de la table des chaînes.

Les capacités dans les sections indicateurs booléens, nombres et chaînes sont dans le même ordre que dans le fichier <term.h>.

Les entiers courts sont signés, dans la plage de -32768 à 32767. Ils sont stockés sous forme de deux octets de 8 bits. Le premier octet contient les 8 bits les moins significatifs de la valeur, et le second octet contient les 8 bits les plus significatifs. (Ainsi, la valeur représentée est 256*second+first.) Ce format correspond au matériel des VAX et PDP-11 (c'est-à-dire les machines little-endian). Les machines où cela ne correspond pas au matériel doivent lire les entiers comme deux octets et calculer la valeur little-endian.

Les nombres dans une description de terminal, qu'il s'agisse d'entrées dans la table des nombres ou des chaînes, sont des entiers positifs. Les indicateurs booléens sont traités comme des entiers positifs d'un octet. Dans chaque cas, ces entiers positifs représentent une capacité de terminal. Le compilateur de terminal tic utilise des entiers négatifs pour gérer les cas où une capacité n'est pas disponible :

•
Si une capacité est absente de ce terminal, tic stocke -1 dans la table correspondante.
La valeur entière -1 est représentée par deux octets 0377, 0377.
Les valeurs booléennes absentes sont représentées par l'octet 0 (faux).
•
Si une capacité a été annulée pour ce terminal, tic stocke -2 dans la table correspondante.
La valeur entière -2 est représentée par deux octets 0377, 0376.
La valeur booléenne -2 est représentée par l'octet 0376.
•
D'autres valeurs négatives sont illégales.

La section des noms de terminal suit len-tête. Elle contient la première ligne de la description terminfo, listant les différents noms du terminal, séparés par le caractère “|”. La section des noms de terminal est terminée par un caractère NUL ASCII.

La section des indicateurs booléens a un octet pour chaque indicateur. Les capacités booléennes sont soit 1 soit 0 (vrai ou faux) selon que le terminal supporte ou non la capacité donnée.

Entre la section des indicateurs booléens et la section des nombres, un octet nul sera inséré, si nécessaire, pour garantir que la section des nombres commence sur un octet pair. Ceci est un vestige de l'architecture à adresses par mots du PDP-11, initialement conçue pour éviter les interruptions causées par l'adressage d'un mot sur une limite d'octet impair. Tous les entiers courts sont alignés sur une limite de mot court.

La section des nombres est similaire à la section des indicateurs booléens. Chaque capacité occupe deux octets et est stockée comme un entier court little-endian.

La section des chaînes est également similaire. Chaque capacité est stockée comme un entier court. La valeur de la capacité est un indice dans la table des chaînes.

La table des chaînes est la dernière section. Elle contient toutes les valeurs des capacités de chaînes référencées dans la section des chaînes. Chaque chaîne est terminée par un NUL. Les caractères spéciaux en notation ^X ou \c sont stockés sous leur forme interprétée, et non sous leur représentation imprimable. Les informations de remplissage $<nn> et les informations de paramètres %x sont stockées intactes sous forme non interprétée.

Format de stockage étendu

La section précédente décrit le format binaire conventionnel de terminfo. Avec quelques variations mineures des offsets (voir PORTABILITY), le même format binaire est utilisé sur tous les systèmes Unix modernes. Chaque système utilise un ensemble prédéfini de capacités booléennes, numériques ou de chaînes.

Les bibliothèques et applications ncurses supportent le format binaire terminfo étendu, permettant aux utilisateurs de définir des capacités qui sont chargées au moment de l'exécution. Cette extension est rendue possible en utilisant le fait que les autres implémentations arrêtent de lire les données terminfo lorsqu'elles atteignent la fin de la taille donnée dans l'en-tête. ncurses vérifie la taille et, si elle dépasse celle des données prédéfinies, continue d'analyser selon son propre schéma.

Premièrement, il lit l'en-tête étendu (5 entiers courts) :

(1)
nombre de capacités booléennes étendues
(2)
nombre de capacités numériques étendues
(3)
nombre de capacités de chaînes étendues
(4)
nombre d'éléments dans la table des chaînes étendues
(5)
taille de la table des chaînes étendues en octets

Les valeurs de nombre et de taille pour la table des chaînes étendues incluent les noms des capacités étendues ainsi que les valeurs des capacités étendues.

En utilisant les nombres et les tailles, ncurses alloue des tableaux et lit les données pour les capacités étendues dans le même ordre que les informations de l'en-tête.

La table des chaînes étendues contient les valeurs des capacités de chaînes. Après la fin de ces valeurs, elle contient les noms de chacune des capacités étendues dans l'ordre, par exemple, les booléens, puis les nombres, et enfin les chaînes.

terminfo(5) - ncurses

NAME

terminfo

terminal capability data base

SYNOPSIS

The compiled terminal capability database.

DESCRIPTION

The terminfo database is a directory tree of compiled files, each containing the capabilities for a particular terminal model. The database is typically located under /usr/share/terminfo.

The format of these files is described in terminfo(5).

The text data for terminfo capabilities is described in term_variables(3X). The compiled data structure is described in curses(3X).

Compiled Format

The compiled format is a binary format that is more efficient for the library to read than the text format.

The format is described in detail in the implementation notes for the curses library, often found in files like /usr/share/doc/ncurses/terminfo.html or similar.

The format includes:

  • A magic number that identifies the file type.
  • Offsets into the data for Boolean, number, and string capabilities.
  • Arrays of Boolean, number, and string capabilities.
  • A table of terminal names.

Extended formats, for larger numbers of capabilities or larger values, are supported by modern implementations such as ncurses.

LEGACY STORAGE FORMAT

The legacy format uses 16-bit signed integers for the number capabilities. This is sufficient for many older terminals, but may not be adequate for modern applications requiring more extensive terminal manipulation.

The legacy format includes a magic number (octal 0436) and uses 16-bit signed integers for the number array.

EXTENDED STORAGE FORMAT

This format, introduced in ncurses 5.0, extends the legacy format by:

  • Using a different magic number (octal 01037).
  • Adding more fields to the header for extended data.
  • Allowing for a larger number of capabilities.

The extended storage format can hold more capabilities than the legacy format. It is used for applications which need more than the predefined capabilities. See user_caps(5) for an overview of the way ncurses uses this extended information.

Applications which manipulate terminal data can use the definitions described in term_variables(3X) which associate the long capability names with members of a TERMTYPE structure.

Extended Number Format

On occasion, 16-bit signed integers are not large enough. With ncurses 6.1, a new format was introduced by making a few changes to the legacy format:

  • a different magic number (octal 01036)
  • changing the type for the number array from signed 16-bit integers to signed 32-bit integers.

To maintain compatibility, the library presents the same data structures to direct users of the TERMTYPE structure as in previous formats. However, that cannot provide callers with the extended numbers. The library uses a similar but hidden data structure TERMTYPE2 to provide data for the terminfo functions.

FILES

/usr/share/terminfo
compiled terminal description database

PORTABILITY

setupterm

Note that it is possible for setupterm to expect a different set of capabilities than are actually present in the file. Either the database may have been updated since setupterm was recompiled (resulting in extra unrecognized entries in the file) or the program may have been recompiled more recently than the database was updated (resulting in missing entries). The routine setupterm must be prepared for both possibilities - this is why the numbers and sizes are included. Also, new capabilities must always be added at the end of the lists of Boolean, number, and string capabilities.

Binary Format

X/Open Curses does not specify a format for the terminfo database. System V curses used a directory-tree of binary files, one per terminal description.

Despite the consistent use of little-endian for numbers and the otherwise self-describing format, it is not wise to count on portability of binary terminfo entries between commercial Unix versions. The problem is that there are at least three versions of terminfo (under HP-UX, AIX, and OSF/1) which diverged from System V terminfo after SVr1, and have added extension capabilities to the string table that (in the binary format) collide with System V and X/Open Curses extensions. See terminfo(5) for detailed discussion of terminfo source compatibility issues.

This implementation is by default compatible with the binary terminfo format used by Solaris curses, except in a few less-used details where it was found that the latter did not match X/Open Curses. The format used by the other Unix versions can be matched by building ncurses with different configuration options.

Magic Codes

The magic number in a binary terminfo file is the first 16-bits (two bytes). Besides making it more reliable for the library to check that a file is terminfo, utilities such as file(1) also use that to tell what the file-format is. System V defined more than one magic number, with 0433, 0435 as screen-dumps (see scr_dump(5)). This implementation uses 01036 as a continuation of that sequence, but with a different high-order byte to avoid confusion.

The TERMTYPE Structure

Direct access to the TERMTYPE structure is provided for legacy applications. Portable applications should use the tigetflag and related functions described in curs_terminfo(3X) for reading terminal capabilities.

Mixed-case Terminal Names

A small number of terminal descriptions use uppercase characters in their names. If the underlying filesystem ignores the difference between uppercase and lowercase, ncurses represents the “first character” of the terminal name used as the intermediate level of a directory tree in (two-character) hexadecimal form.

Limits

ncurses stores compiled terminal descriptions in three related formats, described in the sections

  • LEGACY STORAGE FORMAT, and
  • EXTENDED STORAGE FORMAT, and
  • EXTENDED NUMBER FORMAT.

The legacy storage format and the extended number format differ by the types of numeric capability which they can store (i.e., 16-bit versus 32-bit integers). The extended storage format introduced by ncurses 5.0 adds data to either of these formats.

Some limitations apply:

  • total compiled entries cannot exceed 4096 bytes in the legacy format.
  • total compiled entries cannot exceed 32768 bytes in the extended format.
  • the name field cannot exceed 128 bytes.

Compiled entries are limited to 32768 bytes because offsets into the strings table use two-byte integers. The legacy format could have supported 32768-byte entries, but was limited to a virtual memory page's 4096 bytes.

term est un fichier de base de données qui décrit les capacités des terminaux.

DESCRIPTION

Le fichier term contient des descriptions des terminaux disponibles et de leurs capacités. Chaque entrée du fichier décrit un terminal spécifique et comprend des informations telles que la taille de l'écran, les séquences d'échappement pour le positionnement du curseur, le nettoyage de l'écran, etc.

FORMAT

Le format du fichier term est défini par le projet Termcap (Terminal Capabilities). Chaque ligne du fichier représente une entrée de terminal, avec des champs séparés par des deux-points (:).

nom_terminal|alias1|alias2:cap1=valeur1:cap2=valeur2:\
              cap3=valeur3:cap4@:cap5^:cap6(valeur longue):
  • nom_terminal : Le nom principal du terminal.
  • alias : Des noms alternatifs pour le terminal.
  • cap : Codes des capacités du terminal (par exemple,co pour les colonnes,li pour les lignes,cm pour le positionnement du curseur).
  • valeur : La valeur associée à une capacité. Peut être une chaîne, un nombre, ou vide.
  • @ : Indique que la capacité est obsolète.
  • ^ : Indique que la capacité nécessite un argument.
  • (valeur longue) : Permet de définir des chaînes de capacités sur plusieurs lignes.

EMPLACEMENT

Le fichier term est généralement situé dans les répertoires suivants :

  • /etc/termcap
  • /usr/share/termcap

UTILISATION

Les programmes utilisent le fichier term pour déterminer comment interagir avec le terminal de l'utilisateur. La variable d'environnement TERM spécifie quel terminal est utilisé, et le programme recherche alors l'entrée correspondante dans le fichier term.
