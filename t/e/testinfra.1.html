DÉMARRAGE RAPIDE

Installez testinfra en utilisant pip :

$ pip install pytest-testinfra
# ou installez la version de développement
$ pip install 'git+https://github.com/pytest-dev/pytest-testinfra@main#egg=pytest-testinfra'

Écrivez votre premier fichier de tests dans test_myinfra.py :

def test_passwd_file(host):
    passwd = host.file("/etc/passwd")
    assert passwd.contains("root")
    assert passwd.user == "root"
    assert passwd.group == "root"
    assert passwd.mode == 0o644
def test_nginx_is_installed(host):
    nginx = host.package("nginx")
    assert nginx.is_installed
    assert nginx.version.startswith("1.2")
def test_nginx_running_and_enabled(host):
    nginx = host.service("nginx")
    assert nginx.is_running
    assert nginx.is_enabled

Backends de connexion

Testinfra est livré avec plusieurs backends de connexion pour l'exécution de commandes à distance.

Lors de l'installation, vous devriez sélectionner les backends que vous souhaitez en tant qu'extras pour garantir la satisfaction des dépendances Python (notez que divers outils empaquetés par le système peuvent encore être nécessaires). Par exemple :

$ pip install pytest-testinfra[ansible,salt]

Pour tous les backends, les commandes peuvent être exécutées en tant qu'utilisateur root avec l'option --sudo ou en tant qu'utilisateur spécifique avec l'option --sudo-user.

Spécification générale de l'hôte

Le paramètre --hosts dans Testinfra est utilisé pour spécifier les hôtes cibles pour les tests.

Vous pouvez spécifier plusieurs hôtes en séparant chaque cible par une virgule, ce qui vous permet d'exécuter des tests en utilisant différents backends sur différents environnements ou machines.

Les champs utilisateur, mot de passe et port sont facultatifs, offrant une flexibilité en fonction de vos exigences d'authentification et de connexion.

Veuillez également lire les détails pour les backends individuels, car la spécification de l'hôte est traitée légèrement différemment d'un backend à l'autre.

Syntaxe :

--hosts=<backend>://<user>:<password>@<host>:<port>

Composants :

  • <backend> : type de backend à utiliser (par exemple, ssh, docker, paramiko, local)
  • <user> : nom d'utilisateur pour l'authentification (facultatif)
  • <password> : mot de passe pour l'authentification (facultatif)
  • <host> : nom d'hôte ou adresse IP cible
  • <port> : numéro de port cible (facultatif)

Les caractères spéciaux (par exemple, ":") dans les champs utilisateur et mot de passe doivent être encodés en pourcentage selon la RFC 3986. Cela peut être fait en utilisant urllib.parse.quote() en Python.

Par exemple :

import urllib.parse
user = urllib.parse.quote('user:name')
password = urllib.parse.quote('p@ssw:rd')
host = 'hostname'
port = 22
host_spec = f"ssh://{user}:{password}@{host}:{port}"
print(host_spec)

Cela garantira que tous les caractères spéciaux sont correctement encodés, rendant la chaîne de connexion valide.

Exemples :

Backend SSH avec spécification complète :

testinfra --hosts=ssh://user:password@hostname:22

Backend Docker :

testinfra --hosts=docker://container_id

Backends mixtes :

testinfra --hosts=ssh://user:password@hostname:22,docker://container_id,local://

local

C'est le backend par défaut lorsqu'aucun hôte n'est fourni (via --hosts ou dans les modules). Les commandes sont exécutées localement dans un sous-processus sous l'utilisateur actuel :

Vous pouvez fournir un fichier ssh-config alternatif :

$ pytest --hosts='docker://[user@]container_id_or_name'

Voir aussi l'exemple Tester les images Docker.

podman

$ pytest --hosts='podman://[user@]container_id_or_name'

ssh

C'est un backend SSH pur utilisant la commande ssh. Exemple :

$ pytest --hosts='ssh://server'
$ pytest --ssh-config=/path/to/ssh_config --hosts='ssh://server'
$ pytest --ssh-identity-file=/path/to/key --hosts='ssh://server'
$ pytest --hosts='ssh://server?timeout=60&controlpersist=120'
$ pytest --hosts='ssh://server' --ssh-extra-args='-o StrictHostKeyChecking=no'

Par défaut, le délai d'attente est de 10 secondes et ControlPersist est de 60 secondes. Vous pouvez désactiver la connexion persistante en passant controlpersist=0 aux options.

salt

$ pytest --hosts='salt://*'
$ pytest --hosts='salt://minion1,salt://minion2'
$ pytest --hosts='salt://web*'
$ pytest --hosts='salt://G@os:Debian'

Testinfra utilisera le canal de connexion salt pour exécuter les commandes.

ansible

Les inventaires Ansible peuvent être utilisés pour décrire quels hôtes Testinfra doit utiliser et comment s'y connecter, en utilisant le backend Ansible de Testinfra.

Pour utiliser le backend Ansible, préfixez l'option --hosts avec ansible://, par exemple :

$ pytest --hosts='ansible://all' # teste tous les hôtes de l'inventaire
$ pytest --hosts='ansible://host1,ansible://host2'
$ pytest --hosts='ansible://web*'

Un inventaire peut être spécifié avec l'option --ansible-inventory, sinon le défaut (/etc/ansible/hosts) est utilisé.

La valeur ansible_connection dans votre inventaire sera utilisée pour déterminer quel backend utiliser pour les hôtes individuels : local, ssh, paramiko et docker sont des valeurs supportées. D'autres connexions (ou si vous utilisez l'option --force-ansible) entraîneront l'exécution de toutes les commandes par Testinfra via Ansible lui-même, ce qui est considérablement plus lent que les autres backends :

$ pytest --force-ansible --hosts='ansible://all'
$ pytest --hosts='ansible://host?force_ansible=True'

Par défaut, le backend de connexion Ansible essaiera d'abord d'utiliser ansible_ssh_private_key_file et ansible_private_key_file pour s'authentifier, puis se rabattra sur ansible_user avec les variables ansible_ssh_pass (les deux sont requis), avant de finalement se rabattre sur la configuration SSH de votre propre hôte.

Ce comportement peut être remplacé en spécifiant soit l'option --ssh-identity-file, soit l'option --ssh-config.

Enfin, ces variables d'environnement sont supportées et seront transmises à leur variable ansible correspondante (Voir la documentation Ansible) :

  • ANSIBLE_REMOTE_USER
  • ANSIBLE_SSH_EXTRA_ARGS
  • ANSIBLE_SSH_COMMON_ARGS
  • ANSIBLE_REMOTE_PORT
  • ANSIBLE_BECOME_USER
  • ANSIBLE_BECOME

kubectl

$ pytest --hosts='winrm://Administrator:Password@127.0.0.1'
$ pytest --hosts='winrm://vagrant@127.0.0.1:2200?no_ssl=true&no_verify_ssl=true'

Ansible

classe Ansible(module_name, module_args=None, check=True)
Exécute des fonctions de module Ansible

Ce module n'est disponible qu'avec le backend de connexion ansible.

Les arguments Ansible qui ne sont pas liés à l'inventaire ou à la connexion Ansible (tous deux gérés par testinfra) sont également acceptés via des arguments nommés :

  • become_method str sudo, su, doas, etc.
  • become_user str devient cet utilisateur.
  • diff bool : lors de la modification de fichiers (petits) et de modèles, afficher les différences dans ces fichiers.
  • extra_vars dict sérialisé en une chaîne JSON, passé à Ansible.
  • one_line bool : condenser la sortie.
  • user str se connecter en tant que cet utilisateur.
  • verbose int niveau de verbosité

Plusieurs filtres pour une clé donnée sont gérés en donnant une liste de chaînes comme valeur.

>>> master = host.process.get(user="root", comm="nginx")
# Voici le processus maître nginx (exécuté en tant que root)
>>> master.args
'nginx: master process /usr/sbin/nginx -g daemon on; master_process on;'
# Voici les processus ouvriers (PID parent = PID du maître)
>>> workers = host.process.filter(ppid=master.pid)
>>> len(workers)
4
# Nginx ne consomme pas de mémoire
>>> sum([w.pmem for w in workers])
0.8
# Mais PHP, si !
>>> sum([p.pmem for p in host.process.filter(comm="php5-fpm")])
19.2
filter(**filters)
Obtient une liste des processus correspondants. 
>>> host.process.filter(user="root", comm="zsh")
[<process zsh (pid=2715)>, <process zsh (pid=10502)>, ...]
get(**filters)
Récupérer un processus correspondant

Lève RuntimeError si aucun processus n'est trouvé ou si plusieurs processus correspondent aux filtres.

Socket

classe Socket(socketspec)
Tester les sockets tcp/udp et unix en écoute

socketspec doit être spécifié comme <protocole>://<hôte>:<port>

Ce module nécessite la commande netstat sur l'hôte cible.

Exemple :

  • Sockets Unix : unix:///var/run/docker.sock
  • Tous les sockets tcp ipv4 et ipv6 sur le port 22 : tcp://22
  • Tous les sockets ipv4 sur le port 22 : tcp://0.0.0.0:22
  • Tous les sockets ipv6 sur le port 22 : tcp://:::22
  • Socket udp sur 127.0.0.1 port 69 : udp://127.0.0.1:69
propriété is_listening
Tester si le socket est en écoute 
>>> host.socket("unix:///var/run/docker.sock").is_listening
False
>>> # Ce serveur HTTP écoute sur toutes les adresses ipv4 mais pas sur ipv6
>>> host.socket("tcp://0.0.0.0:80").is_listening
True
>>> host.socket("tcp://:::80").is_listening
False
>>> host.socket("tcp://80").is_listening
False

NOTE :

Si vous ne spécifiez pas d'hôte pour les sockets udp et tcp, alors le socket écoute si et seulement si le socket écoute sur à la fois toutes les adresses ipv4 et ipv6 (c'est-à-dire 0.0.0.0 et ::)
propriété clients: list[tuple[str, int] | None]
Retourne une liste des clients connectés à un socket en écoute

Pour les sockets tcp et udp, une liste de paires (adresse, port) est renvoyée. Pour les sockets unix, une liste de None est renvoyée (vous pouvez donc faire un len() pour compter les clients).

>>> host.socket("tcp://22").clients

>>> host.socket("unix:///var/run/docker.sock")

API de connexion

Vous pouvez utiliser testinfra en dehors de pytest. Vous pouvez obtenir dynamiquement une instance host et appeler des fonctions ou accéder aux membres des modules respectifs :

>>> import testinfra
>>> host = testinfra.get_host("paramiko://root@server:2222", sudo=True)
>>> host.file("/etc/shadow").mode == 0o640
True

Par exemple, vous pourriez créer un test pour comparer deux fichiers sur deux serveurs différents :

# MAUVAIS : Si le test échoue sur nginx, python n'est pas testé
def test_packages(host):
    for name, version in (
        ("nginx", "1.6"),
        ("python", "2.7"),
    ):
        pkg = host.package(name)
        assert pkg.is_installed
        assert pkg.version.startswith(version)
# BON : Chaque paquet est testé
# $ pytest -v test.py
# [...]
# test.py::test_package[local-nginx-1.6] PASSED
# test.py::test_package[local-python-2.7] PASSED
# [...]
import pytest
@pytest.mark.parametrize("name,version", [
    ("nginx", "1.6"),
    ("python", "2.7"),
])
def test_packages(host, name, version):
    pkg = host.package(name)
    assert pkg.is_installed
    assert pkg.version.startswith(version)

This page details how to use Testinfra with different tools. Testinfra is a set of Pytest plugins, enabling you to write automated valitations of your infrastructure state.

About

Testinfra is a python library that helps you to validate the state of your servers. It can be used to write automated tests that check if your servers are configured correctly.

Testinfra integrates with Pytest and provides a simple API to interact with servers using various backends like SSH, Docker, WinRM, or SaltStack.

License

Quick Start

Here's a minimal example of how to use Testinfra with Pytest to test an Nginx installation:

# test_nginx.py
import testinfra
# Connect to the server (adjust the connection string as needed)
host = testinfra.get_host("ssh://user@your-server-ip")
def test_nginx_is_installed():
    # Check if the nginx package is installed
    assert host.package("nginx").is_installed
def test_nginx_is_running():
    # Check if the nginx service is running
    service = host.service("nginx")
    assert service.is_running
    assert service.is_enabled
def test_nginx_config_is_valid():
    # Check if the nginx configuration is valid
    assert host.run("nginx -t").rc == 0

To run these tests, save the code above as `test_nginx.py` and execute the following command in your terminal:

$ pytest test_nginx.py

This will connect to your server via SSH and run the defined tests. If all tests pass, you'll see output indicating success.

Tester les images Docker

Docker est un moyen pratique de tester votre code d'infrastructure. Cette recette montre comment construire et exécuter des conteneurs Docker avec Testinfra en surchargeant le fixture host.

import pytest
import subprocess
import testinfra
# scope='session' utilise le même conteneur pour tous les tests ;
# scope='function' utilise un nouveau conteneur par fonction de test.
@pytest.fixture(scope='session')
def host(request):
    # construire le Dockerfile local ./
    subprocess.check_call(['docker', 'build', '-t', 'myimage', '.'])
    # exécuter un conteneur
    docker_id = subprocess.check_output(
        ['docker', 'run', '-d', 'myimage']).decode().strip()
    # retourner une connexion testinfra au conteneur
    yield testinfra.get_host("docker://" + docker_id)
    # à la fin de la suite de tests, détruire le conteneur
    subprocess.check_call(['docker', 'rm', '-f', docker_id])
def test_myimage(host):
    # 'host' est maintenant lié au conteneur
    assert host.check_output('myapp -v') == 'Myapp 1.0'
