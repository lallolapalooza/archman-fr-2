terminfo(5) Formats de fichiers terminfo(5)

NOM

terminfo — base de données des caractéristiques des terminaux

SYNTAXE

/usr/share/terminfo/*/*

DESCRIPTION

Terminfo est une base de données décrivant les terminaux, utilisée par les programmes orientés écran tels que nvi(1), lynx(1), mutt(1), et d'autres applications curses, en utilisant des appels de haut niveau vers des bibliothèques comme curses(3X). Elle est également utilisée via des appels de bas niveau par des applications non-curses qui peuvent être orientées écran (comme clear(1)) ou non-orientées écran (comme tabs(1)).

Terminfo décrit les terminaux en donnant un ensemble de caractéristiques qu'ils possèdent, en spécifiant comment effectuer les opérations d'écran, et en spécifiant les exigences de remplissage et les séquences d'initialisation.

Ce document décrit la version 6.5 (patch 20240427) de ncurses.

Syntaxe des entrées terminfo

Les entrées dans terminfo se composent d'une séquence de champs :

  • Chaque champ se termine par une virgule “,” (les virgules intégrées peuvent être échappées avec une barre oblique inverse ou écrites comme “\\054”).
  • L'espace blanc entre les champs est ignoré.
  • Le premier champ d'une entrée terminfo commence dans la première colonne.
  • Les sauts de ligne et les espaces blancs en tête (espaces ou tabulations) peuvent être utilisés pour formater les entrées pour une meilleure lisibilité. Ceux-ci sont supprimés des entrées analysées.
Les options infocmp -f et -W s'appuient sur cela pour formater les expressions si-alors-sinon, ou pour imposer une largeur de ligne maximale. La description du terminal formatée résultante peut être lue par tic.
•
Le premier champ pour chaque terminal donne les noms connus pour le terminal, séparés par des caractères “|”.
Le premier nom donné est le nom abrégé le plus courant pour le terminal (son nom primaire), le dernier nom donné doit être un nom long identifiant entièrement le terminal (voir longname(3X)), et tous les autres sont traités comme des synonymes (alias) pour le nom primaire du terminal.
X/Open Curses recommande que tous les noms, sauf le dernier, soient en minuscules et ne contiennent pas d'espaces ; le dernier nom peut contenir des majuscules et des espaces pour la lisibilité.
Cette implémentation n'est pas aussi stricte ; elle autorise les majuscules/minuscules dans le nom primaire et les alias. Si le dernier nom n'a pas d'espaces intégrés, cela peut être à la fois un alias et un nom détaillé (mais cela provoquera un avertissement concernant cette ambiguïté).
•
Les lignes commençant par un “#” dans la première colonne sont traitées comme des commentaires.
Bien que les lignes de commentaires soient valides à tout moment, la sortie de captoinfo et infotocap (alias pour tic) déplacera les commentaires afin qu'ils n'apparaissent qu'entre les entrées.

Les noms de terminaux (à l'exception de la dernière entrée détaillée) doivent être choisis en suivant les conventions suivantes. La pièce matérielle spécifique constituant le terminal devrait avoir un nom de base, ainsi “hp2621”. Ce nom ne devrait pas contenir de tirets. Les modes dans lesquels le matériel peut se trouver, ou les préférences utilisateur, doivent être indiqués en ajoutant un tiret et un suffixe de mode. Ainsi, un vt100 en mode 132 colonnes serait vt100-w.

Syntaxe des capacités terminfo

L'entrée terminfo se compose de plusieurs capacités, c'est-à-dire des caractéristiques que le terminal possède, ou des méthodes pour exercer les caractéristiques du terminal.

Après le premier champ (donnant le(s) nom(s) de l'entrée du terminal), il doit y avoir une ou plusieurs capacités. Ce sont des noms booléens, numériques ou de chaîne avec des valeurs correspondantes :

  • Les capacités booléennes sont vraies lorsqu'elles sont présentes, fausses lorsqu'elles sont absentes. Il n'y a pas de valeur explicite pour les capacités booléennes.
  • Les capacités numériques ont un “#” après le nom, suivi d'une valeur entière décimale non signée.
  • Les capacités de chaîne ont un “=” après le nom, suivi d'une chaîne de caractères formant la valeur de la capacité.
Les capacités de chaîne peuvent être réparties sur plusieurs lignes, tout comme les champs qui composent une entrée de terminal peuvent être répartis sur plusieurs lignes. Bien que les espaces entre les champs soient ignorés, les espaces intégrés dans une valeur de chaîne sont conservés, à l'exception des espaces en tête sur une ligne.

Toute capacité peut être annulée, c'est-à-dire supprimée de l'entrée du terminal, en plaçant “@” après son nom plutôt qu'une valeur de capacité.

Terminaux similaires

S'il existe deux terminaux très similaires, l'un (le variant) peut être défini comme étant identique à l'autre (la base) avec certaines exceptions. Dans la définition du variant, la capacité de chaîne use peut être donnée avec le nom du terminal de base :

  • Les capacités données avant use remplacent celles du type de base nommé par use.
  • S'il y a plusieurs références use, elles sont fusionnées dans l'ordre inverse. C'est-à-dire que la référence use la plus à droite est traitée en premier, puis celle à sa gauche, et ainsi de suite.
  • Les capacités données explicitement dans l'entrée remplacent celles apportées par les références use.

Une capacité peut être annulée en plaçant xx@ à gauche de la référence use qui l'importe, où xx est la capacité. Par exemple, l'entrée

2621-nl, smkx@, rmkx@, use=2621,

définit un 2621-nl qui ne possède pas les capacités smkx ou rmkx, et donc n'active pas les étiquettes des touches de fonction en mode visuel. Ceci est utile pour différents modes d'un terminal, ou pour différentes préférences utilisateur.

Une entrée incluse via use peut contenir des capacités annulées, ce qui a le même effet que si ces annulations étaient intégrées dans l'entrée du terminal qui l'utilise.

Capacités prédéfinies

Les tables de capacités reconnues par ncurses dans une description de type de terminal terminfo et disponibles pour le code utilisant terminfo suivent.

  • Le nom de la capacité identifie le symbole par lequel le programmeur utilisant l'API terminfo accède à la capacité.
  • Le code TI (terminfo) est le nom court utilisé par une personne qui compose ou met à jour une entrée de type de terminal.
Dans la mesure du possible, ces codes sont les mêmes ou similaires à ceux de la norme ANSI X3.64-1979 (maintenant remplacée par ECMA-48, qui utilise des noms identiques ou très similaires). Les sémantiques sont également destinées à correspondre à celles de la spécification.
Les codes terminfo n'ont pas de limite de longueur stricte

Fonctionnalités définies par l'utilisateur

La section précédente répertoriait les fonctionnalités prédéfinies. Elles concernent certaines fonctionnalités spéciales pour les terminaux qui ne sont plus (ou peut-être jamais) produits. Parfois, les fonctionnalités des terminaux plus récents sont difficiles ou impossibles à représenter en réutilisant les fonctionnalités prédéfinies.

ncurses répond à cette limitation en autorisant les fonctionnalités définies par l'utilisateur. Les programmes tic et infocmp fournissent l'option -x à cet effet. Lorsque -x est défini, tic traite les fonctionnalités inconnues comme étant définies par l'utilisateur. C'est-à-dire que si tic rencontre un nom de fonctionnalité qu'il ne reconnaît pas, il en déduit son type (booléen, numérique ou chaîne) à partir de la syntaxe et crée une entrée de table étendue pour cette fonctionnalité. La fonction use_extended_names(3X) rend ces informations conditionnellement disponibles aux applications. La bibliothèque ncurses fournit les données, laissant la majeure partie du comportement aux applications :

  • Les chaînes de fonctionnalités définies par l'utilisateur dont le nom commence par « k » sont traitées comme des touches de fonction.
  • Les types (booléen, numérique, chaîne) déterminés par tic peuvent être déduits par des appels réussis à tigetflag, etc.
  • Si le nom de la fonctionnalité est composé de deux caractères, la fonctionnalité est également disponible via l'interface termcap.

Bien que termcap soit dit extensible car il n'utilise pas un ensemble prédéfini de fonctionnalités, en pratique, il a été limité aux fonctionnalités définies par les implémentations terminfo. En règle générale, les fonctionnalités définies par l'utilisateur destinées à être utilisées par les applications termcap doivent être limitées aux booléens et aux nombres pour éviter de dépasser la limite de 1023 octets supposée par les implémentations termcap et leurs applications. En particulier, la fourniture d'ensembles étendus de touches de fonction (au-delà des 60 touches numérotées et de la poignée de touches spéciales nommées) se fait mieux en utilisant les noms plus longs disponibles avec terminfo.

La bibliothèque ncurses utilise quelques-unes de ces fonctionnalités définies par l'utilisateur, comme décrit dans user_caps(5). D'autres fonctionnalités définies par l'utilisateur (y compris les touches de fonction) sont décrites dans la base de données de terminaux, dans la section sur les FONCTIONNALITÉS DÉFINISSABLES PAR L'UTILISATEUR NCURSES.

Types de Capacités

Toutes les capacités ont des noms. Par exemple, le fait que les terminaux standard ANSI aient des marges automatiques (c'est-à-dire un retour chariot et un saut de ligne automatiques lorsque la fin d'une ligne est atteinte) est indiqué par la capacité am. La description de ansi inclut donc am. Les capacités numériques sont suivies du caractère “#” puis d'une valeur positive. Ainsi cols, qui indique le nombre de colonnes du terminal, donne la valeur “80” pour ansi. Les valeurs des capacités numériques peuvent être spécifiées en décimal, octal ou hexadécimal, en utilisant les conventions du langage de programmation C (par exemple, 255, 0377 et 0xff ou 0xFF).

Enfin, les capacités de type chaîne, telles que el (séquence pour effacer jusqu'à la fin de la ligne), sont données par le code à deux caractères, un “=”, puis une chaîne se terminant au prochain “,”.

Un certain nombre de séquences d'échappement sont fournies dans les capacités de type chaîne pour un encodage facile des caractères :

  • \E et \e correspondent tous deux à un caractère ESCAPE,
  • ^x correspond à un caractère de contrôle x pour tout x approprié, et
  • les séquences

\n, \l, \r, \t, \b, \f, et \s

produisent

nouvelle ligne, alimentation papier, retour chariot, tabulation, retour arrière, saut de page, et espace,

respectivement.

X/Open Curses ne précise pas ce qu'est un “x approprié”. En pratique, il s'agit d'un caractère graphique ASCII imprimable. Le cas spécial “^?” est interprété comme DEL (127). Dans tous les autres cas, la valeur du caractère est mise en relation logique (AND) avec 0x1f, ce qui correspond aux codes de contrôle ASCII dans la plage de 0 à 31.

D'autres échappements incluent

  • \^ pour ^,
  • \\ pour \,
  • \, pour une virgule,
  • \: pour :,
  • et \0 pour nul.
\0 produira \200, ce qui ne termine pas une chaîne mais se comporte comme un caractère nul sur la plupart des terminaux, à condition que CS7 soit spécifié. Voir stty(1).
La raison de cette bizarrerie est de maintenir la compatibilité binaire des fichiers terminfo compilés avec d'autres implémentations, par exemple, les systèmes SVr4, qui le documentent. Les fichiers terminfo compilés utilisent des chaînes terminées par NUL, sans longueur. Modifier cela nécessiterait un nouveau format binaire, qui ne fonctionnerait pas avec d'autres implémentations.

Enfin, les caractères peuvent être donnés sous forme de trois chiffres octaux après un \.

Un délai en millisecondes peut apparaître n'importe où dans une capacité de chaîne, délimité par des crochets $<..>, comme dans el=\EK$<5>, et des caractères de remplissage sont fournis par tputs(3X) pour fournir ce délai.

  • Le délai doit être un nombre avec au plus une décimale de précision ; il peut être suivi des suffixes “*” ou “/” ou les deux.
  • Un “*” indique que le remplissage requis est proportionnel au nombre de lignes affectées par l'opération, et la quantité donnée est le remplissage requis par unité affectée. (Dans le cas d'une insertion de caractère, le facteur est toujours le nombre de lignes affectées.)
Normalement, le remplissage est indicatif si le périphérique possède la capacité xon ; il est utilisé pour le calcul des coûts mais ne déclenche pas de délais.
•
Un suffixe “/” indique que le remplissage est obligatoire et force un délai du nombre de millisecondes donné, même sur les périphériques pour lesquels xon est présent pour indiquer le contrôle de flux.

Parfois, des capacités individuelles doivent être commentées. Pour ce faire, placez un point avant le nom de la capacité. Par exemple, voir le deuxième ind dans l'exemple ci-dessus.

Obtention des Descriptions Compilées

Les descriptions de terminaux dans ncurses sont stockées dans des bases de données de terminaux. Ces bases de données, trouvées par leur chemin d'accès, peuvent être configurées soit comme des arbres de répertoires, soit comme des bases de données hachées (voir term(5)).

La bibliothèque utilise une liste de chemins d'accès compilée en interne, qui peut être remplacée par des variables d'environnement. Avant de commencer la recherche, ncurses vérifie la liste de recherche, élimine les doublons et les chemins où aucune base de données de terminaux n'est trouvée. La bibliothèque ncurses lit la première description qui passe ses contrôles de cohérence.

  • La variable d'environnement TERMINFO est vérifiée en premier, pour une base de données de terminaux contenant la description du terminal.
  • Ensuite, ncurses recherche dans $HOME/.terminfo une description compilée.
Il s'agit d'une fonctionnalité facultative qui peut être entièrement omise de la bibliothèque, ou limitée pour éviter une utilisation accidentelle par des applications privilégiées.
•
Ensuite, si la variable d'environnement TERMINFO_DIRS est définie, ncurses interprète le contenu de cette variable comme une liste de chemins d'accès séparés par des deux-points de bases de données de terminaux à rechercher.
Un chemin d'accès vide (c'est-à-dire si la variable commence ou se termine par deux-points, ou contient des deux-points adjacents) est interprété comme l'emplacement système /usr/share/terminfo.
•
Enfin, ncurses recherche ces emplacements compilés en interne :
  • une liste de répertoires (/usr/share/terminfo), et
  • le répertoire système terminfo, /usr/share/terminfo

La variable TERMINFO peut contenir une description de terminal au lieu du chemin d'accès d'une base de données de terminaux. Si cette variable commence par “hex:” ou “b64:”, alors ncurses lit une description de terminal à partir de données encodées en hexadécimal ou en base64, et si cette description correspond au nom recherché, elle l'utilisera. Ces données encodées peuvent être définies à l'aide de l'option “-Q” de tic ou infocmp.

Ce qui précède concerne la configuration habituelle de ncurses, qui utilise des descriptions de terminaux préparées au format terminfo. Bien que termcap soit moins expressif, ncurses peut également être configuré pour lire des descriptions termcap. Dans cette configuration, il vérifie les variables TERMCAP et TERMPATH (pour le contenu et le chemin de recherche, respectivement) après la base de données de terminaux système.

Préparation des Descriptions

Nous décrivons maintenant comment préparer des descriptions de terminaux. La manière la plus efficace de préparer une description de terminal est d'imiter la description d'un terminal similaire dans terminfo et de construire une description progressivement, en utilisant des descriptions partielles avec vi ou un autre programme orienté écran pour vérifier qu'elles sont correctes. Sachez qu'un terminal très inhabituel peut révéler des lacunes dans la capacité du fichier terminfo à le décrire ou des bugs dans le code de gestion de l'écran du programme de test.

Pour obtenir un bon remplissage pour l'insertion de ligne (si le fabricant du terminal ne l'a pas documenté), un test rigoureux consiste à éditer un gros fichier à 9600 bauds, supprimer environ 16 lignes du milieu de l'écran, puis appuyer plusieurs fois rapidement sur la touche “u”. Si le terminal se désynchronise, un remplissage supplémentaire est généralement nécessaire. Un test similaire peut être utilisé pour l'insertion de caractère.

Capacités de Base

Le nombre de colonnes sur chaque ligne du terminal est donné par la capacité numérique cols. Si le terminal est une CRT, alors le nombre de lignes à l'écran est donné par la capacité lines. Si le terminal passe à la ligne suivante lorsqu'il atteint la marge droite, il doit avoir la capacité am. Si le terminal peut effacer son écran, en laissant le curseur en position initiale, alors cela est indiqué par la capacité chaîne clear. Si le terminal écrase (au lieu d'effacer une position lorsqu'un caractère est écrit par-dessus) alors il doit avoir la capacité os. Si le terminal est un terminal d'impression, sans unité d'affichage souple, donnez-lui à la fois hc et os. (os s'applique aux terminaux à portée de stockage, tels que la série TEKTRONIX 4010, ainsi qu'aux terminaux papier et APL.) S'il existe un code pour déplacer le curseur vers le bord gauche de la ligne courante, donnez-le comme cr. (Normalement, ce sera un retour chariot, contrôle/M.) S'il existe un code pour produire un signal sonore (cloche, bip, etc.), donnez-le comme bel.

S'il existe un code pour déplacer le curseur d'une position vers la gauche (comme un retour arrière), cette capacité doit être donnée comme cub1. De même, les codes pour se déplacer vers la droite, vers le haut et vers le bas doivent être donnés comme cuf1, cuu1, et cud1. Ces mouvements locaux du curseur ne doivent pas altérer le texte qu'ils traversent, par exemple, vous n'utiliseriez normalement pas “cuf1= ” car l'espace effacerait le caractère déplacé.

Un point très important ici est que les mouvements locaux du curseur encodés dans terminfo sont indéfinis sur les bords gauche et supérieur d'un terminal CRT. Les programmes ne doivent jamais tenter de revenir en arrière au-delà du bord gauche, sauf si bw est donné, et ne jamais tenter de monter localement au-delà du haut. Pour faire défiler le texte vers le haut, un programme

au coin inférieur gauche de l'écran et envoie la chaîne ind (index).

Pour faire défiler le texte vers le bas, un programme se rend dans le coin supérieur gauche de l'écran et envoie la chaîne ri (reverse index). Les chaînes ind et ri ne sont pas définies lorsqu'elles ne sont pas dans leurs coins respectifs de l'écran.

Les versions paramétrées des séquences de défilement sont indn et rin qui ont la même sémantique que ind et ri, sauf qu'elles prennent un seul paramètre et font défiler autant de lignes. Elles ne sont pas non plus définies, sauf au bord approprié de l'écran.

La capacité am indique si le curseur reste coincé sur le bord droit de l'écran lorsque du texte est affiché, mais cela ne s'applique pas nécessairement à un cuf1 depuis la dernière colonne. Le seul mouvement local qui est défini depuis le bord gauche est le suivant : si bw est donné, alors un cub1 depuis le bord gauche se déplacera vers le bord droit de la ligne précédente. Si bw n'est pas donné, l'effet est indéfini. Ceci est utile pour dessiner un cadre autour du bord de l'écran, par exemple. Si le terminal a des marges automatiques sélectionnables par commutateur, le fichier terminfo suppose généralement qu'elles sont activées ; c'est-à-dire, am. Si le terminal a une commande qui déplace le curseur vers la première colonne de la ligne suivante, cette commande peut être donnée sous le nom de nel (newline). Peu importe si la commande efface le reste de la ligne actuelle, donc si le terminal n'a pas de cr et lf, il peut encore être possible de créer un nel fonctionnel à partir d'un ou des deux.

Ces capacités suffisent à décrire les terminaux à papier et les terminaux « verre-tty ». Ainsi, le télétype modèle 33 est décrit comme suit :

33|tty33|tty|model 33 teletype,
        bel=^G, cols#72, cr=^M, cud1=^J, hc, ind=^J, os,

tandis que le Lear Siegler ADM-3 est décrit comme suit :

adm3|3|lsi adm3,
        am, bel=^G, clear=^Z, cols#80, cr=^M, cub1=^H, cud1=^J,
        ind=^J, lines#24,

Chaînes paramétrées

L'adressage du curseur et d'autres chaînes nécessitant des paramètres dans le terminal sont décrits par une capacité de chaîne paramétrée, avec des séquences d'échappement de type printf telles que %x. Par exemple, pour adresser le curseur, la capacité cup est donnée, utilisant deux paramètres : la ligne et la colonne à adresser. (Les lignes et colonnes sont numérotées à partir de zéro et se réfèrent à l'écran physique visible par l'utilisateur, pas à une mémoire invisible.) Si le terminal a un adressage de curseur relatif à la mémoire, cela peut être indiqué par mrcup.

Le mécanisme de paramètre utilise une pile et des codes % spéciaux pour la manipuler. Typiquement, une séquence poussera l'un des paramètres sur la pile, puis l'affichera dans un certain format. Afficher (par exemple, « %d ») est un cas spécial. D'autres opérations, y compris « %t », retirent leur opérande de la pile. Il est à noter que des opérations plus complexes sont souvent nécessaires, par exemple dans la chaîne sgr.

Les encodages % ont les significations suivantes :

%%
affiche « % »
%[[:]flags][width[.precision]][doxXs]
comme dans printf(3), les indicateurs sont [-+#] et espace. Utilisez un « : » pour permettre au caractère suivant d'être un indicateur « - », évitant ainsi d'interpréter « %- » comme un opérateur.
%c
affiche pop() comme %c dans printf
%s
affiche pop() comme %s dans printf
%p[1-9]
pousse le i-ème paramètre
%P[a-z]
définit la variable dynamique [a-z] à pop()
%g[a-z]
récupère la variable dynamique [a-z] et la pousse
%P[A-Z]
définit la variable statique [a-z] à pop()
%g[A-Z]
récupère la variable statique [a-z] et la pousse
Les termes « statique » et « dynamique » sont trompeurs. Historiquement, ce sont simplement deux ensembles différents de variables, dont les valeurs ne sont pas réinitialisées entre les appels à tparm(3X). Cependant, ce fait n'est pas documenté dans d'autres implémentations. S'y fier nuira à la portabilité vers d'autres implémentations :
  • La bibliothèque curses de SVr2 prenait en charge les variables dynamiques. Celles-ci sont définies uniquement par un opérateur %P. Un %g pour une variable donnée sans l'avoir d'abord définie avec %P donnera des résultats imprévisibles, car les variables dynamiques sont un tableau local non initialisé sur la pile dans la fonction tparm.
  • La bibliothèque curses de SVr3.2 prenait en charge les variables statiques. Celles-ci sont un tableau dans la structure TERMINAL (déclarée dans term.h) et sont mises à zéro automatiquement lorsque la fonction setupterm alloue les données.
  • La bibliothèque curses de SVr4 n'a apporté aucune amélioration supplémentaire à la fonctionnalité des variables dynamiques/statiques.
  • La bibliothèque curses de Solaris XPG4 ne fait pas de distinction entre les variables dynamiques et statiques. Elles sont identiques. Comme la bibliothèque curses de SVr4, celle de XPG4 n'initialise pas ces variables explicitement.
  • Avant la version 6.3, ncurses stocke les variables dynamiques et statiques dans un stockage persistant, initialisé à zéro.
  • À partir de la version 6.3, ncurses stocke les variables statiques et dynamiques de la même manière que SVr4.
  • Contrairement à d'autres implémentations, ncurses met à zéro les variables dynamiques avant le premier opérateur %g ou %P.
  • Comme SVr2, la portée des variables dynamiques dans ncurses est dans l'appel actuel à tparm. Utilisez des variables statiques si un stockage persistant est nécessaire.
%'c'
constante de caractère c
%{nn}
constante entière nn
%l
pousse strlen(pop)
%+, %-, %*, %/, %m
arithmétique (%m est mod) : push(pop() op pop())
%&, %|, %^
opérations bit à bit (ET, OU et OU exclusif) : push(pop() op pop())
%=, %>, %<
opérations logiques : push(pop() op pop())
%A, %O
opérations ET et OU logiques (pour les conditions)
%!, %~
opérations unaires (complément logique et bit à bit) : push(op pop())
%i
ajoute 1 aux deux premiers paramètres (pour les terminaux ANSI)
%? expr %t thenpart %e elsepart %;
Ceci forme un si-alors-sinon. La partie %e elsepart est optionnelle. Habituellement, la partie %? expr pousse une valeur sur la pile, et %t la retire de la pile, en testant si elle est non nulle (vrai). Si elle est nulle (faux), le contrôle passe à la partie %e (else).
Il est possible de former des « else-if » à la Algol 68 :
%? c1 %t b1 %e c2 %t b2 %e c3 %t b3 %e c4 %t b4 %e %;
où ci sont des conditions, bi sont des corps.
Utilisez l'option -f de tic ou infocmp pour voir la structure des « if-then-else ». Certaines chaînes, par exemple sgr, peuvent être très compliquées lorsqu'elles sont écrites sur une seule ligne. L'option -f divise la chaîne en lignes avec les parties indentées.

Les opérations binaires sont sous forme postfixée avec les opérandes dans l'ordre habituel. C'est-à-dire, pour obtenir x-5, on utiliserait « %gx%{5}%- ». Les variables %P et %g sont persistantes entre les évaluations des chaînes d'échappement.

Considérons le HP2645, qui, pour atteindre la ligne 3 et la colonne 12, nécessite l'envoi de \E&a12c03Y avec un délai de 6 millisecondes. L'ordre des lignes et des colonnes est inversé ici, et la ligne et la colonne sont imprimées sur deux chiffres. La description du terminal correspondante est exprimée ainsi :

cup=\E&a%p2%dc%p1%dY$<6>,

Le Microterm ACT-IV nécessite l'envoi de la ligne et de la colonne actuelles précédées d'un ^T, avec la ligne et la colonne simplement codées en binaire,

cup=^T%p1%c%p2%c

Les terminaux qui utilisent « %c » doivent pouvoir reculer le curseur (cub1), et remonter le curseur d'une ligne à l'écran (cuu1). Ceci est nécessaire car il n'est pas toujours sûr de transmettre \n ^D et \r, car le système peut les modifier ou les supprimer. (Les routines de bibliothèque traitant terminfo règlent les modes tty de sorte que les tabulations ne soient jamais développées, donc \t est sûr à envoyer. Cela s'avère essentiel pour l'Ann Arbor 4080.)

Un dernier exemple est le LSI ADM-3a, qui utilise un décalage de ligne et de colonne par rapport à un caractère d'espacement, ainsi

cup=\E=%p1%' '%+%c%p2%' '%+%c

Après avoir envoyé « \E= », ceci pousse le premier paramètre, pousse la valeur ASCII d'un espace (32), les additionne (poussant la somme sur la pile à la place des deux valeurs précédentes) et affiche cette valeur sous forme de caractère. Ensuite, la même chose est faite pour le deuxième paramètre. Des calculs plus complexes sont possibles en utilisant la pile.

Mouvements du curseur

Si le terminal dispose d'un moyen rapide de ramener le curseur à l'origine (au coin supérieur gauche de l'écran), cela peut être donné comme home ; de même, un moyen rapide d'atteindre le coin inférieur gauche peut être donné comme ll ; cela peut impliquer de monter avec cuu1 à partir de la position d'origine, mais un programme ne devrait jamais le faire lui-même (sauf si ll le fait) car il ne peut faire aucune hypothèse sur l'effet d'un déplacement vers le haut à partir de la position d'origine. Notez que la position d'origine est la même que l'adressage à (0,0) : le coin supérieur gauche de l'écran, pas de la mémoire. (Ainsi, la séquence \EH sur les terminaux HP ne peut pas être utilisée pour home.)

Si le terminal dispose d'un adressage absolu du curseur par ligne ou par colonne, celles-ci peuvent être données comme des capacités à un seul paramètre hpa (horizontal position absolute) et vpa (vertical position absolute). Parfois, elles sont plus courtes que la séquence à deux paramètres plus générale (comme avec le hp2645) et peuvent être utilisées de préférence à cup. S'il existe des mouvements locaux paramétrés (par exemple, déplacer n espaces vers la droite), ceux-ci peuvent être donnés comme cud, cub, cuf, et cuu avec un seul paramètre indiquant le nombre d'espaces à déplacer. Celles-ci sont principalement utiles si le terminal ne dispose pas de cup, comme le TEKTRONIX 4025.

Si le terminal doit être dans un mode spécial lors de l'exécution d'un programme utilisant ces capacités, les codes pour entrer et sortir de ce mode peuvent être donnés comme smcup et rmcup. Cela se produit, par exemple, avec des terminaux comme le Concept qui ont plus d'une page de mémoire. Si le terminal n'a que de la mémoire relative

adresses de curseur et non relatives à l'écran les adresses de curseur, une fenêtre de la taille d'un écran doit être fixe dans le terminal pour que les adresses de curseur fonctionnent correctement. Ceci est également utilisé pour le TEKTRONIX 4025, où smcup définit le caractère de commande comme celui utilisé par terminfo. Si la séquence smcup ne restaure pas l'écran après une séquence rmcup est sortie (à l'état précédent la sortie de rmcup), spécifiez nrrmc.

Marges

SVr4 (et X/Open Curses) listent plusieurs capacités de chaîne pour définir les marges. Deux étaient destinées à être utilisées avec des terminaux et six autres étaient destinées à être utilisées avec des imprimantes.

  • Les deux capacités de terminal supposent que le terminal peut avoir la capacité de définir la marge gauche et/ou droite à la position actuelle du curseur.
  • Les capacités d'imprimante supposent que l'imprimante peut avoir deux types de capacités :
  • la capacité de définir une marge supérieure et/ou inférieure à la position actuelle de la ligne, et
  • des capacités paramétrées pour définir les marges supérieure, inférieure, gauche, droite en donnant le nombre de lignes ou de colonnes.

En pratique, la catégorisation en « terminal » et « imprimante » n'est pas appropriée :

•
La base de données de terminaux AT&T SVr4 utilise smgl quatre fois, pour le matériel AT&T.
Trois des quatre sont des imprimantes. Elles n'ont pas la capacité de définir des marges gauche/droite en spécifiant la colonne.
•
D'autres terminaux (non-AT&T) peuvent prendre en charge les marges mais en utilisant des hypothèses différentes de celles d'AT&T.
Par exemple, le DEC VT420 prend en charge les marges gauche/droite, mais seulement en utilisant un paramètre de colonne. Pour compliquer les choses, le VT420 utilise deux réglages pour activer complètement les marges gauche/droite (mode marge gauche/droite et mode origine). Le premier active les marges, ce qui fait que le texte imprimé passe à la ligne à l'intérieur des marges, mais le second est nécessaire pour empêcher l'adressage du curseur en dehors de ces marges.
•
Les deux marges gauche/droite du DEC VT420 sont définies avec une seule séquence de contrôle. Si l'une d'elles est omise, la marge correspondante est définie sur le bord gauche ou droit de l'affichage (plutôt que de laisser la marge inchangée).

Voici les capacités liées aux marges :

Nom Description
smgl Définir la marge gauche à la colonne actuelle
smgr Définir la marge droite à la colonne actuelle
smgb Définir la marge inférieure à la ligne actuelle
smgt Définir la marge supérieure à la ligne actuelle
smgbp Définir la marge inférieure à la ligne N
smglp Définir la marge gauche à la colonne N
smgrp Définir la marge droite à la colonne N
smgtp Définir la marge supérieure à la ligne N
smglr Définir les marges gauche et droite à L et R
smgtb Définir les marges supérieure et inférieure à T et B

Lors de l'écriture d'une application qui utilise ces capacités de chaîne, les paires doivent d'abord être vérifiées pour voir si chaque capacité de la paire est définie ou si une seule est définie :

  • Si smglp et smgrp sont tous deux définis, chacun est utilisé avec un seul argument, N, qui donne le numéro de colonne de la marge gauche et droite, respectivement.
  • Si smgtp et smgbp sont tous deux définis, chacun est utilisé pour définir les marges supérieure et inférieure, respectivement :
  • smgtp est utilisé avec un seul argument, N, le numéro de ligne de la marge supérieure.
  • smgbp est utilisé avec deux arguments, N et M, qui donnent le numéro de ligne de la marge inférieure, le premier comptant à partir du haut de la page et le second comptant à partir du bas. Ceci permet de prendre en charge les deux styles de spécification de la marge inférieure dans les imprimantes de différents fabricants.
Lors de la conception d'une entrée terminfo pour une imprimante ayant une marge inférieure réglable, seul le premier ou le second argument doit être utilisé, en fonction de l'imprimante. Lors du développement d'une application utilisant smgbp pour définir la marge inférieure, les deux arguments doivent être fournis.

Inversement, lorsqu'une seule capacité de la paire est définie :

  • Si seulement l'un de smglp et smgrp est défini, alors il est utilisé avec deux arguments, les numéros de colonne des marges gauche et droite, dans cet ordre.
  • De même, si seulement l'un de smgtp et smgbp est défini, alors il est utilisé avec deux arguments qui donnent les marges supérieure et inférieure, dans cet ordre, en comptant à partir du haut de la page.
Lors de la conception d'une entrée terminfo pour une imprimante qui nécessite la définition simultanée des marges gauche et droite ou supérieure et inférieure, une seule capacité des paires smglp et smgrp ou smgtp et smgbp doit être définie, laissant l'autre non définie.

À l'exception des descriptions de terminaux très anciennes, par exemple celles développées pour SVr4, le schéma décrit ci-dessus doit être considéré comme obsolète. Un ensemble amélioré de capacités a été ajouté tardivement dans les versions SVr4 (smglr et smgtb), qui utilisent explicitement deux paramètres pour définir les marges gauche/droite ou supérieure/inférieure.

Lors de la définition des marges, les valeurs de ligne et de colonne sont basées sur zéro.

La capacité de chaîne mgc doit être définie. Les applications telles que tabs(1) s'appuient sur cela pour réinitialiser toutes les marges.

Effacements de zone

Si le terminal peut effacer de la position actuelle jusqu'à la fin de la ligne, laissant le curseur à sa place, cela doit être donné comme el. Si le terminal peut effacer du début de la ligne jusqu'à la position actuelle incluse, laissant le curseur à sa place, cela doit être donné comme el1. Si le terminal peut effacer de la position actuelle jusqu'à la fin de l'affichage, alors cela doit être donné comme ed. Ed n'est défini qu'à partir de la première colonne d'une ligne. (Ainsi, il peut être simulé par une demande de suppression d'un grand nombre de lignes, si un véritable ed n'est pas disponible.)

Insertion/Suppression de ligne et mouvements verticaux

Si le terminal peut ouvrir une nouvelle ligne vierge avant la ligne où se trouve le curseur, cela doit être donné comme il1 ; ceci est fait uniquement à partir de la première position d'une ligne. Le curseur doit alors apparaître sur la ligne nouvellement vierge. Si le terminal peut supprimer la ligne sur laquelle se trouve le curseur, alors cela doit être donné comme dl1 ; ceci est fait uniquement à partir de la première position sur la ligne à supprimer. Les versions de il1 et dl1 qui prennent un seul paramètre et insèrent ou suppriment ce nombre de lignes peuvent être données comme il et dl.

Si le terminal a une région de défilement réglable (comme le vt100), la commande pour la définir peut être décrite avec la capacité csr, qui prend deux paramètres : les lignes supérieure et inférieure de la région de défilement. La position du curseur est, hélas, indéfinie après l'utilisation de cette commande.

Il est possible d'obtenir l'effet d'insertion ou de suppression de ligne en utilisant csr sur une région correctement choisie ; les commandes sc et rc (sauvegarder et restaurer le curseur) peuvent être utiles pour garantir que votre chaîne d'insertion/suppression synthétisée ne déplace pas le curseur. (Notez que la bibliothèque ncurses(3X) effectue cette synthèse automatiquement, vous n'avez donc pas besoin de composer des chaînes d'insertion/suppression pour une entrée avec csr).

Une autre façon de construire l'insertion et la suppression pourrait être d'utiliser une combinaison d'index avec la fonction de verrouillage mémoire trouvée sur certains terminaux (comme la série HP-700/90, qui possède cependant aussi l'insertion/suppression).

L'insertion de lignes en haut ou en bas de l'écran peut également être effectuée à l'aide de ri ou ind sur de nombreux terminaux sans insertion/suppression de ligne réelle, et est souvent plus rapide même sur les terminaux dotés de ces fonctions.

Le booléen non_dest_scroll_region doit être défini si chaque fenêtre de défilement est effectivement une vue sur un canevas de la taille de l'écran. Pour tester cette capacité, créez une région de défilement au milieu de l'écran, écrivez quelque chose sur la dernière ligne, déplacez le curseur en haut de la région, et effectuez ri suivi de dl1 ou ind. Si les données défilées hors du bas de la région par le ri réapparaissent, alors le défilement n'est pas destructeur. System V et X/Open Curses s'attendent à ce que ind, ri, indn et rin simulent un défilement destructeur ; leur documentation vous met en garde de ne pas définir csr sauf si cela est vrai. Cette implémentation de curses est plus libérale et effectuera des effacements explicites après le défilement si ndsrc est défini.

Si le terminal a la capacité de définir une fenêtre comme partie de la mémoire, que toutes les commandes affectent, cela doit être donné comme la chaîne paramétrée wind. Les quatre paramètres sont les lignes de début et de fin en mémoire et les colonnes de début et de fin en mémoire, dans cet ordre.

Si le terminal peut conserver de la mémoire d'affichage au-dessus, alors la capacité da doit être donnée ; si de la mémoire d'affichage peut être conservée en dessous, alors db doit être donnée. Celles-ci indiquent que la suppression d'une ligne ou le défilement peut faire remonter des lignes non vierges par le bas ou que le défilement arrière avec ri peut faire descendre des lignes non vierges.

Insertion/Suppression de caractère

Il existe deux types de terminaux intelligents concernant l'insertion/suppression de caractères qui peuvent être décrits à l'aide de terminfo. Les opérations d'insertion/suppression de caractères les plus courantes affectent uniquement les caractères de la ligne actuelle et décalent les caractères rigidement vers la fin de la ligne. D'autres terminaux, tels que le Concept 100 et le Perkin Elmer Owl, font une distinction entre les espaces tapés et non tapés sur l'écran, en décalant lors d'une insertion ou suppression uniquement vers un espace non tapé sur l'écran qui est soit éliminé, soit étendu à deux espaces non tapés.

Vous pouvez déterminer le type de terminal dont vous disposez en effaçant l'écran, puis en tapant du texte séparé par des mouvements de curseur. Tapez « abc     def » en utilisant des mouvements de curseur locaux (pas des espaces) entre les

“abc” et les “def”. Ensuite, placez le curseur avant “abc” et mettez le terminal en mode insertion. Si la saisie de caractères provoque le déplacement rigide du reste de la ligne et que des caractères tombent à la fin, alors votre terminal ne fait pas la distinction entre les espaces et les positions non tapées. Si le “abc” se déplace vers le “def” qui se déplacent alors ensemble autour de la fin de la ligne actuelle et sur la suivante pendant que vous insérez, vous avez le deuxième type de terminal, et devriez donner la capacité in, qui signifie “insertion nulle”.

Bien que ces deux attributs soient logiquement distincts (mode d'insertion sur une ligne ou sur plusieurs lignes, et traitement spécial des espaces non tapés), nous n'avons vu aucun terminal dont le mode d'insertion ne puisse être décrit avec le seul attribut.

Terminfo peut décrire à la fois les terminaux qui ont un mode d'insertion, et les terminaux qui envoient une séquence simple pour ouvrir une position vide sur la ligne actuelle. Donnez comme smir la séquence pour entrer en mode insertion. Donnez comme rmir la séquence pour quitter le mode insertion. Donnez maintenant comme ich1 toute séquence nécessaire à envoyer juste avant d'envoyer le caractère à insérer. La plupart des terminaux avec un vrai mode d'insertion ne fourniront pas ich1 ; les terminaux qui envoient une séquence pour ouvrir une position d'écran devraient la donner ici.

Si votre terminal a les deux, le mode d'insertion est généralement préférable à ich1. Techniquement, vous ne devriez pas donner les deux, sauf si le terminal a réellement besoin des deux utilisés en combinaison. En conséquence, certaines applications non-curses sont confuses si les deux sont présents ; le symptôme est des caractères doublés dans une mise à jour utilisant l'insertion. Cette exigence est maintenant rare ; la plupart des séquences ich ne nécessitent pas de smir préalable, et la plupart des modes d'insertion smir ne nécessitent pas ich1 avant chaque caractère. Par conséquent, le nouveau curses suppose que c'est le cas et utilise soit rmir/smir, soit ich/ich1, selon le cas (mais pas les deux). Si vous devez écrire une entrée à utiliser sous le nouveau curses pour un terminal assez ancien pour avoir besoin des deux, incluez les séquences rmir/smir dans ich1.

Si un remplissage après insertion est nécessaire, donnez-le sous forme de nombre de millisecondes dans ip (une option de chaîne). Toute autre séquence qui pourrait devoir être envoyée après l'insertion d'un seul caractère peut également être donnée dans ip. Si votre terminal a besoin des deux pour être placé dans un « mode d'insertion » et d'un code spécial pour précéder chaque caractère inséré, alors smir/rmir et ich1 peuvent être donnés, et les deux seront utilisés. La capacité ich, avec un paramètre, n, répétera les effets de ich1 n fois.

Si un remplissage est nécessaire entre les caractères tapés en dehors du mode d'insertion, donnez-le sous forme de nombre de millisecondes de remplissage dans rmp.

Il est parfois nécessaire de se déplacer en mode d'insertion pour supprimer des caractères sur la même ligne (par exemple, s'il y a une tabulation après la position d'insertion). Si votre terminal permet le mouvement en mode d'insertion, vous pouvez donner la capacité mir pour accélérer l'insertion dans ce cas. Omettre mir n'affectera que la vitesse. Certains terminaux (notamment ceux de Datamedia) ne doivent pas avoir mir en raison de la façon dont leur mode d'insertion fonctionne.

Enfin, vous pouvez spécifier dch1 pour supprimer un seul caractère, dch avec un paramètre, n, pour supprimer n caractères, et le mode de suppression en donnant smdc et rmdc pour entrer et sortir du mode de suppression (tout mode dans lequel le terminal doit être placé pour que dch1 fonctionne).

Une commande pour effacer n caractères (équivalente à la sortie de n espaces sans déplacer le curseur) peut être donnée sous le nom ech avec un paramètre.

Mise en évidence, Soulignement et Bell Visuels

Si votre terminal a un ou plusieurs types d'attributs d'affichage, ceux-ci peuvent être représentés de différentes manières. Vous devriez choisir une forme d'affichage comme mode de surbrillance, représentant un format de bon contraste, agréable à l'œil, pour mettre en évidence les messages d'erreur et autres accrocheurs. (Si vous avez le choix, la vidéo inversée plus demi-luminosité est bien, ou la vidéo inversée seule.) Les séquences pour entrer et sortir du mode de surbrillance sont données comme smso et rmso, respectivement. Si le code pour passer en mode de surbrillance ou en sortir laisse un ou deux espaces vides à l'écran, comme le font le TVI 912 et le Teleray 1061, alors xmc devrait être donné pour indiquer combien d'espaces sont laissés.

Les codes pour commencer le soulignement et terminer le soulignement peuvent être donnés comme smul et rmul respectivement. Si le terminal a un code pour souligner le caractère actuel et déplacer le curseur d'un espace vers la droite, comme le Microterm Mime, celui-ci peut être donné comme uc.

Les autres capacités pour entrer dans divers modes de mise en évidence incluent blink (clignotant) bold (gras ou très lumineux) dim (faible ou demi-lumineux) invis (effacement ou texte invisible) prot (protégé) rev (vidéo inversée) sgr0 (désactiver tous les modes d'attribut) smacs (entrer en mode jeu de caractères alternatif) et rmacs (quitter le mode jeu de caractères alternatif). L'activation de l'un de ces modes individuellement peut ou peut ne pas désactiver d'autres modes.

S'il existe une séquence pour définir des combinaisons arbitraires de modes, elle doit être donnée comme sgr (définir les attributs), prenant 9 paramètres. Chaque paramètre est soit zéro (0), soit non nul, selon que l'attribut correspondant est activé ou désactivé. Les 9 paramètres sont, dans l'ordre : surbrillance, soulignement, inversé, clignotant, faible, gras, blanc, protégé, jeu de caractères alternatif. Tous les modes n'ont pas besoin d'être pris en charge par sgr, seulement ceux pour lesquels des commandes d'attribut séparées correspondantes existent.

Par exemple, le DEC vt220 prend en charge la plupart des modes :

Paramètre tparm Attribut Séquence d'échappement

p2 soulignement \E[0;4m
p3 inversé \E[0;7m
p4 clignotant \E[0;5m

Nous commençons chaque séquence d'échappement en désactivant tous les modes existants, car il n'y a pas de moyen rapide de déterminer s'ils sont actifs. La surbrillance est configurée pour être la combinaison de l'inversion et du gras. Le terminal vt220 a un mode de protection, bien qu'il ne soit pas couramment utilisé dans sgr car il protège les caractères à l'écran contre les effacements de l'hôte. Le mode de jeu de caractères alternatif est également différent en ce sens qu'il s'agit soit de ^O, soit de ^N, selon qu'il est désactivé ou activé. Si tous les modes sont activés, la séquence résultante est \E[0;1;4;5;7;8m^N.

Certaines séquences sont communes à différents modes. Par exemple, ;7 est émis lorsque p1 ou p3 est vrai, c'est-à-dire si les modes de surbrillance ou d'inversion sont activés.

N'oubliez pas que si vous spécifiez sgr, vous devez également spécifier sgr0. De plus, certaines implémentations dépendent de la présence de sgr si sgr0 est présent. Il n'y a cependant pas toujours de chaîne sgr dans toutes les entrées terminfo. De nombreuses entrées terminfo sont dérivées d'entrées termcap qui n'ont pas de chaîne sgr. Le seul inconvénient à ajouter une chaîne sgr est que termcap suppose également que sgr0 ne quitte pas le mode de jeu de caractères alternatif.

Les terminaux ayant l'anomalie des « cookies magiques » (xmc) déposent des « cookies » spéciaux lorsqu'ils reçoivent des séquences de réglage de mode, qui affectent l'algorithme d'affichage plutôt que d'avoir des bits supplémentaires pour chaque caractère. Certains terminaux, comme le HP 2621, quittent automatiquement le mode de surbrillance lorsqu'ils passent à une nouvelle ligne ou que le curseur est adressé. Les programmes utilisant le mode de surbrillance doivent quitter le mode de surbrillance avant de déplacer le curseur ou d'envoyer un retour à la ligne, à moins que la capacité msgr, affirmant qu'il est sûr de se déplacer en mode de surbrillance, ne soit présente.

Si le terminal a un moyen de faire clignoter l'écran pour indiquer une erreur silencieusement (un remplacement de la sonnerie), cela peut être donné comme flash ; il ne doit pas déplacer le curseur.

Si le curseur doit être rendu plus visible que la normale lorsqu'il n'est pas sur la dernière ligne (pour transformer, par exemple, un soulignement non clignotant en un bloc plus facile à trouver ou un soulignement clignotant) donnez cette séquence comme cvvis. S'il existe un moyen de rendre le curseur complètement invisible, donnez-le comme civis. La capacité cnorm doit être donnée pour annuler les effets de ces deux modes.

Si votre terminal génère correctement des caractères soulignés (sans codes spéciaux nécessaires) bien qu'il ne superpose pas, vous devez alors donner la capacité ul. Si un caractère superposé à un autre laisse les deux caractères à l'écran, spécifiez la capacité os. Si les superpositions sont effaçables avec un espace, cela doit alors être indiqué en donnant eo.

Clavier et Touches de Fonction

Si le terminal possède un clavier qui transmet des codes lorsque les touches sont pressées, ces informations peuvent être données. Notez qu'il n'est pas possible de gérer les terminaux où le clavier ne fonctionne qu'en local (cela s'applique, par exemple, aux touches non décalées du HP 2621). Si le clavier peut être configuré pour transmettre ou non, donnez ces codes comme smkx et rmkx. Sinon, le clavier est supposé toujours transmettre.

Les codes envoyés par les touches flèche gauche, flèche droite, flèche haut, flèche bas et accueil peuvent

be given as kcub1, kcuf1, kcuu1, kcud1, et khome respectivement. S'il existe des touches de fonction telles que f0, f1, ..., f10, les codes qu'elles envoient peuvent être donnés comme kf0, kf1, ..., kf10. Si ces touches ont des étiquettes autres que celles par défaut f0 à f10, les étiquettes peuvent être données comme lf0, lf1, ..., lf10.

Les codes transmis par certaines autres touches spéciales peuvent être donnés :

  • kll (home bas),
  • kbs (retour arrière),
  • ktbc (effacer toutes les tabulations),
  • kctab (effacer le taquet de tabulation dans cette colonne),
  • kclr (effacer l'écran ou touche d'effacement),
  • kdch1 (supprimer le caractère),
  • kdl1 (supprimer la ligne),
  • krmir (quitter le mode insertion),
  • kel (effacer jusqu'à la fin de la ligne),
  • ked (effacer jusqu'à la fin de l'écran),
  • kich1 (insérer le caractère ou entrer en mode insertion),
  • kil1 (insérer une ligne),
  • knp (page suivante),
  • kpp (page précédente),
  • kind (faire défiler vers l'avant/bas),
  • kri (faire défiler vers l'arrière/haut),
  • khts (définir un taquet de tabulation dans cette colonne).

En outre, si le pavé numérique possède un réseau de touches de 3 par 3 incluant les quatre touches fléchées, les cinq autres touches peuvent être données comme ka1, ka3, kb2, kc1 et kc3. Ces touches sont utiles lorsque les effets d'un pavé directionnel de 3 par 3 sont nécessaires.

Les chaînes pour programmer les touches de fonction peuvent être données comme pfkey, pfloc et pfx. Une chaîne pour programmer les étiquettes d'écran doit être spécifiée comme pln. Chacune de ces chaînes prend deux paramètres : le numéro de la touche de fonction à programmer (de 0 à 10) et la chaîne avec laquelle la programmer. Les numéros de touches de fonction en dehors de cette plage peuvent programmer des touches indéfinies d'une manière dépendante du terminal. La différence entre les capacités est que pfkey fait en sorte que l'appui sur la touche donnée soit identique à la frappe par l'utilisateur de la chaîne donnée ; pfloc fait exécuter la chaîne par le terminal en local ; et pfx fait transmettre la chaîne à l'ordinateur.

Les capacités nlab, lw et lh définissent le nombre d'étiquettes d'écran programmables ainsi que leur largeur et leur hauteur. S'il existe des commandes pour activer et désactiver les étiquettes, donnez-les dans smln et rmln. smln est normalement émis après une ou plusieurs séquences pln pour s'assurer que le changement devient visible.

Onglets et Initialisation

Quelques capacités sont utilisées uniquement pour les tabulations :

  • Si le terminal possède des tabulations matérielles, la commande pour avancer vers le taquet de tabulation suivant peut être donnée comme ht (généralement contrôle/I).
  • Une commande de « tabulation arrière » qui se déplace vers la gauche vers le taquet de tabulation précédent peut être donnée comme cbt.
Par convention, si les modes télégraphiques indiquent que les tabulations sont développées par l'ordinateur plutôt que d'être envoyées au terminal, les programmes ne devraient pas utiliser ht ou cbt même s'ils sont présents, car l'utilisateur peut ne pas avoir correctement configuré les taquets de tabulation.
•
Si le terminal possède des tabulations matérielles qui sont initialement réglées tous les n espaces lorsque le terminal est alimenté, le paramètre numérique it est donné, indiquant le nombre d'espaces auxquels les tabulations sont réglées.
La capacité it est normalement utilisée par la commande tset pour déterminer s'il faut activer le mode d'expansion des tabulations matérielles, et s'il faut régler les taquets de tabulation. Si le terminal possède des taquets de tabulation qui peuvent être sauvegardés dans la mémoire non volatile, la description terminfo peut supposer qu'ils sont correctement réglés.

D'autres capacités incluent

  • is1, is2 et is3, chaînes d'initialisation pour le terminal,
  • iprog, le nom du chemin d'un programme à exécuter pour initialiser le terminal,
  • et if, le nom d'un fichier contenant de longues chaînes d'initialisation.

Ces chaînes sont censées mettre le terminal dans des modes cohérents avec le reste de la description terminfo. Elles sont normalement envoyées au terminal, par l'option init du programme tput, chaque fois que l'utilisateur se connecte. Elles seront imprimées dans l'ordre suivant :

La plupart de l'initialisation est effectuée avec is2. Des modes de terminal spéciaux peuvent être configurés sans dupliquer les chaînes en plaçant les séquences communes dans is2 et les cas spéciaux dans is1 et is3.

Un ensemble de séquences qui effectue une réinitialisation plus complète à partir d'un état totalement inconnu peut être donné comme rs1, rs2, rf et rs3, analogues respectivement à is1, is2, if et is3. Ces chaînes sont émises par l'option reset de tput, ou par le programme reset (un alias de tset), qui est utilisé lorsque le terminal se retrouve dans un état bloqué. Les commandes sont normalement placées dans rs1, rs2, rs3 et rf uniquement si elles produisent des effets gênants sur l'écran et ne sont pas nécessaires lors de la connexion. Par exemple, la commande pour régler le vt100 en mode 80 colonnes serait normalement partie de is2, mais elle provoque un scintillement gênant de l'écran et n'est normalement pas nécessaire puisque le terminal est généralement déjà en mode 80 colonnes.

Le programme reset écrit des chaînes incluant iprog, etc., dans le même ordre que le programme init, en utilisant rs1, etc., au lieu de is1, etc. Si une des chaînes de capacité de réinitialisation rs1, rs2, rs3 ou rf est manquante, le programme reset se rabat sur la chaîne de capacité d'initialisation correspondante.

S'il existe des commandes pour définir et effacer les taquets de tabulation, elles peuvent être données comme tbc (effacer tous les taquets de tabulation) et hts (définir un taquet de tabulation dans la colonne actuelle de chaque ligne). Si une séquence plus complexe est nécessaire pour définir les tabulations que ce qui peut être décrit ici, la séquence peut être placée dans is2 ou if.

La commande tput reset utilise les mêmes chaînes de capacité que la commande reset, bien que les deux programmes (tput et reset) fournissent des options de ligne de commande différentes.

En pratique, ces capacités terminfo ne sont pas souvent utilisées dans l'initialisation des tabulations (bien qu'elles soient nécessaires pour le programme tabs) :

•
Presque tous les terminaux matériels (du moins ceux qui supportaient les tabulations) les initialisaient tous les huit colonnes :
La seule exception était la série AT&T 2300, qui réglait les tabulations tous les cinq colonnes.
  • En particulier, les développeurs des terminaux matériels qui sont couramment utilisés comme modèles pour les émulateurs de terminaux modernes ont fourni une documentation démontrant que huit colonnes étaient la norme.
  • Pour cette raison, les programmes d'initialisation de terminal tput et tset utilisent les capacités tbc (clear_all_tabs) et hts (set_tab) directement uniquement lorsque la capacité it (init_tabs) est définie sur une valeur autre que huit.

Délais et Rembourrage

De nombreux terminaux plus anciens et plus lents ne prennent pas en charge la gestion XON/XOFF ni la gestion du contrôle de flux DTR, y compris les terminaux à copie papier et certains CRT très archaïques (y compris, par exemple, les DEC VT100). Ceux-ci peuvent nécessiter des caractères de remplissage après certains mouvements de curseur et changements d'écran.

Si le terminal utilise la gestion xon/xoff pour le contrôle de flux (c'est-à-dire qu'il émet automatiquement ^S à l'hôte lorsque ses tampons d'entrée sont presque pleins), définissez xon. Cette capacité supprime l'émission de rembourrage. Vous pouvez également la définir pour les périphériques de console mappés en mémoire qui n'ont pas de limite de vitesse. Les informations de rembourrage doivent toujours être incluses afin que les routines puissent prendre de meilleures décisions concernant les coûts relatifs, mais aucun caractère de rembourrage ne sera transmis.

Si pb (padding baud rate) est donné, le rembourrage est supprimé aux débits en bauds inférieurs à la valeur de pb. Si l'entrée n'a pas de débit en bauds de rembourrage, alors que le rembourrage soit émis ou non est entièrement contrôlé par xon.

Si le terminal requiert autre chose qu'un caractère nul (zéro) comme rembourrage, alors cela peut être donné comme pad. Seul le premier caractère de la chaîne pad est utilisé.

Lignes de Statut

Certains terminaux ont une « ligne de statut » supplémentaire qui n'est normalement pas utilisée par le logiciel (et n'est donc pas comptée dans la capacité lines du terminal).

Le cas le plus simple est une ligne de statut qui est adressable par curseur mais ne fait pas partie de la région de défilement principale de l'écran ; le Heathkit H19 possède une ligne de statut de ce type, tout comme un VT100 de 24 lignes avec une région de défilement de 23 lignes configurée à l'initialisation. Cette situation est indiquée par la capacité hs.

Certains terminaux avec des lignes de statut nécessitent des séquences spéciales pour accéder à la ligne de statut. Celles-ci peuvent être exprimées sous forme de chaîne avec un paramètre unique tsl qui amène le curseur à une colonne donnée d'origine zéro sur la ligne de statut. La capacité fsl doit retourner aux positions du curseur de l'écran principal avant le dernier tsl. Vous pourriez avoir besoin d'intégrer les valeurs de chaîne de sc (sauvegarder le curseur) et rc (restaurer le curseur) dans tsl et fsl pour y parvenir.

La ligne de statut est normalement supposée avoir la même largeur que le terminal. Si ce n'est pas le cas, vous pouvez la spécifier avec la capacité numérique wsl.

Une commande pour effacer ou blanchir la ligne de statut peut être spécifiée comme dsl.

La capacité booléenne eslok spécifie que les séquences d'échappement, les tabulations, etc., fonctionnent normalement dans la ligne de statut.

L'implémentation ncurses n'utilise pas encore ces capacités. Elles sont documentées ici au cas où elles deviendraient importantes.

Gestion des couleurs

Les fonctions de la bibliothèque curses init_pair et init_color manipulent les *paires de couleurs* et les *valeurs de couleurs* discutées dans cette section (voir curs_color(3X) pour plus de détails sur ces fonctions et les fonctions associées).

La plupart des terminaux couleur sont soit de type « Tektronix », soit de type « HP » :

  • Les terminaux de type Tektronix ont un ensemble prédéfini de *N* couleurs (où *N* est généralement 8), et peuvent régler indépendamment les caractères avant et arrière pour chaque cellule de caractère, les mélangeant en *N* × *N* paires de couleurs.
  • Sur les terminaux de type HP, l'utilisateur doit configurer chaque paire de couleurs séparément (l'avant et l'arrière ne peuvent pas être réglés indépendamment). Jusqu'à *M* paires de couleurs peuvent être configurées à partir de 2×*M* couleurs différentes. Les terminaux compatibles ANSI sont de type Tektronix.

Certaines capacités de couleur de base sont indépendantes de la méthode de couleur. Les capacités numériques colors et pairs spécifient le nombre maximum de couleurs et de paires de couleurs qui peuvent être affichées simultanément. La chaîne op (original pair) réinitialise les couleurs avant et arrière à leurs valeurs par défaut pour le terminal. La chaîne oc réinitialise toutes les couleurs ou paires de couleurs à leurs valeurs par défaut pour le terminal. Certains terminaux (y compris de nombreux émulateurs de terminaux PC) effacent les zones de l'écran avec la couleur d'arrière-plan actuelle plutôt qu'avec la couleur d'arrière-plan par défaut à la mise sous tension ; ceux-ci devraient avoir la capacité booléenne bce.

Bien que la bibliothèque curses travaille avec des *paires de couleurs* (reflétant l'incapacité de certains terminaux à régler indépendamment les couleurs avant et arrière), il existe des capacités séparées pour régler ces fonctionnalités :

  • Pour changer la couleur avant ou arrière actuelle sur un terminal de type Tektronix, utilisez setaf (set ANSI foreground) et setab (set ANSI background) ou setf (set foreground) et setb (set background). Ceux-ci prennent un paramètre, le numéro de couleur. La documentation SVr4 ne décrit que setaf/setab ; le projet XPG4 indique que « Si le terminal prend en charge les séquences d'échappement ANSI pour régler l'arrière-plan et l'avant-plan, elles doivent être codées comme setaf et setab, respectivement.
  • Si le terminal prend en charge d'autres séquences d'échappement pour régler l'arrière-plan et l'avant-plan, elles doivent être codées comme setf et setb, respectivement. Les fonctions vidputs et refresh(3X) utilisent les capacités setaf et setab si elles sont définies.

Les capacités setaf/setab et setf/setb prennent chacune un seul argument numérique. Les valeurs d'argument 0-7 de setaf/setab sont définies de manière portable comme suit (la colonne du milieu est le #define symbolique disponible dans l'en-tête des bibliothèques curses ou ncurses). Divers

Si le terminal nécessite un caractère autre qu'un caractère nul (zéro) pour le remplissage, celui-ci peut être spécifié comme pad. Seul le premier caractère de la chaîne de remplissage est utilisé. Si le terminal n'a pas de caractère de remplissage, spécifiez npc. Notez que ncurses implémente la variable PC compatible avec termcap ; bien que l'application puisse définir cette valeur sur autre chose qu'un nul, ncurses testera d'abord npc et utilisera napms si le terminal n'a pas de caractère de remplissage.

Si le terminal peut monter ou descendre d'une demi-ligne, cela peut être indiqué par hu (half-line up) et hd (half-line down). Ceci est principalement utile pour les exposants et indices sur les terminaux papier. Si un terminal papier peut passer à la page suivante (avance papier), spécifiez-le comme ff (généralement contrôle/L).

S'il existe une commande pour répéter un caractère donné un nombre de fois donné (pour économiser du temps lors de la transmission d'un grand nombre de caractères identiques), cela peut être indiqué par la chaîne paramétrée rep. Le premier paramètre est le caractère à répéter et le second est le nombre de fois où il faut le répéter. Ainsi, tparm(repeat_char, 'x', 10) équivaut à “xxxxxxxxxx”.

Si le terminal a un caractère de commande réglable, comme le TEKTRONIX 4025, cela peut être indiqué par cmdch. Un caractère de commande prototype est choisi et utilisé dans toutes les capacités. Ce caractère est donné dans la capacité cmdch pour l'identifier. La convention suivante est prise en charge sur certains systèmes Unix : l'environnement doit être recherché pour une variable CC, et si elle est trouvée, toutes les occurrences du caractère prototype sont remplacées par le caractère de la variable d'environnement.

Les descriptions de terminal qui ne représentent pas un type de terminal connu, comme switch, dialup, patch et network, devraient inclure la capacité gn (générique) afin que les programmes puissent se plaindre qu'ils ne savent pas comment communiquer avec le terminal. (Cette capacité ne s'applique pas aux descriptions de terminal virtuel pour lesquelles les séquences d'échappement sont connues.)

Si le terminal dispose d'une touche « méta » qui agit comme une touche majuscule, définissant le 8ème bit de tout caractère transmis, ce fait peut être indiqué par km. Sinon, le logiciel supposera que le 8ème bit est la parité et il sera généralement effacé. S'il existe des chaînes pour activer et désactiver ce « mode méta », elles peuvent être spécifiées comme smm et rmm.

Si le terminal a plus de lignes de mémoire que ce qui peut tenir à l'écran en une fois, le nombre de lignes de mémoire peut être indiqué par lm. Une valeur de lm#0 indique que le nombre de lignes n'est pas fixe, mais qu'il y a toujours plus de mémoire que ce qui tient à l'écran.

Si le terminal fait partie de ceux pris en charge par le protocole de terminal virtuel Unix, le numéro de terminal peut être donné comme vt.

Les chaînes de copie de média qui contrôlent une imprimante auxiliaire connectée au terminal peuvent être spécifiées comme mc0 : imprimer le contenu de l'écran, mc4 : désactiver l'imprimante, et mc5 : activer l'imprimante. Lorsque l'imprimante est activée, tout le texte envoyé au terminal sera envoyé à l'imprimante. Il n'est pas défini si le texte est également affiché à l'écran du terminal lorsque l'imprimante est activée. Une variation mc5p prend un paramètre et laisse l'imprimante allumée pour autant de caractères que la valeur du paramètre, puis éteint l'imprimante. Le paramètre ne doit pas dépasser 255. Tout texte, y compris mc4, est transparentement transmis à l'imprimante pendant qu'un mc5p est actif.

Problèmes avec les entrées longues

Les longues entrées terminfo ne devraient pas poser de problème ; à ce jour, aucune entrée n'a approché le maximum de 4096 octets de la table de chaînes de terminfo. Malheureusement, les traductions termcap sont beaucoup plus strictement limitées (à 1023 octets), ainsi les traductions termcap des longues entrées terminfo peuvent causer des problèmes.

Les pages de manuel des versions 4.3BSD et antérieures de tgetent demandent à l'utilisateur d'allouer un tampon de 1024 octets pour l'entrée termcap. L'entrée est terminée par un caractère nul par la bibliothèque termcap, ce qui rend la longueur maximale sûre pour une entrée termcap de 1023 octets (1 Ko - 1). Selon ce que font l'application et la bibliothèque termcap utilisées, et où dans le fichier termcap se trouve le type de terminal recherché par tgetent, plusieurs choses peuvent mal se passer :

  • certaines bibliothèques termcap affichent un message d'avertissement,
  • certaines se terminent si elles trouvent une entrée de plus de 1023 octets,
  • certaines ne se terminent ni n'avertissent, ne faisant rien d'utile, et
  • certaines tronquent simplement les entrées à 1023 octets.

Certains programmes allouent plus que le 1 Ko recommandé pour l'entrée termcap ; d'autres non.

Chaque entrée termcap a deux tailles importantes associées : avant l'expansion « tc », et après l'expansion « tc ». « tc » est la capacité qui ajoute une autre entrée termcap à la fin de celle en cours, pour y ajouter ses capacités. Si une entrée termcap n'utilise pas la capacité « tc », alors bien sûr les deux longueurs sont identiques.

La longueur « avant l'expansion tc » est la plus importante, car elle affecte plus que les utilisateurs de ce terminal particulier. C'est la longueur de l'entrée telle qu'elle existe dans /etc/termcap, moins les paires de backslash-nouvelle ligne, que tgetent supprime en la lisant. Certaines bibliothèques termcap suppriment également la nouvelle ligne finale (GNU termcap ne le fait pas). Supposons maintenant :

  • une entrée termcap avant expansion fait plus de 1023 octets,
  • et l'application n'a alloué qu'un tampon de 1 Ko,
  • et la bibliothèque termcap (comme celle de BSD/OS 1.1 et GNU) lit l'intégralité de l'entrée dans le tampon, quelle que soit sa longueur, pour voir si c'est l'entrée qu'elle recherche,
  • et tgetent recherche un type de terminal qui est soit l'entrée longue, apparaît dans le fichier termcap après l'entrée longue, soit n'apparaît pas du tout dans le fichier (de sorte que tgetent doive rechercher tout le fichier termcap).

Alors tgetent écrasera la mémoire, peut-être sa pile, et fera probablement planter le programme (core dump). Des programmes comme telnet sont particulièrement vulnérables ; les tels modernes transmettent automatiquement des valeurs comme le type de terminal. Les résultats sont presque aussi indésirables avec une bibliothèque termcap, comme SunOS 4.1.3 et Ultrix 4.4, qui affiche des messages d'avertissement lorsqu'elle lit une entrée termcap trop longue. Si une bibliothèque termcap tronque les entrées longues, comme OSF/1 3.0, elle est immunisée contre la mort ici mais retournera des données incorrectes pour le terminal.

La longueur « après l'expansion tc » aura un effet similaire à ce qui précède, mais uniquement pour les personnes qui ont effectivement défini TERM à ce type de terminal, car tgetent ne fait l'expansion « tc » qu'une fois qu'il a trouvé le type de terminal qu'il recherchait, et non pendant la recherche.

En résumé, une entrée termcap de plus de 1023 octets peut causer, sur diverses combinaisons de bibliothèques termcap et d'applications, un crash (core dump), des avertissements ou un fonctionnement incorrect. Si elle est trop longue même avant l'expansion « tc », elle aura cet effet même pour les utilisateurs d'autres types de terminaux et les utilisateurs dont la variable TERM n'a pas d'entrée termcap.

En mode -C (traduire en termcap), l'implémentation ncurses de tic(1M) émet des messages d'avertissement lorsque la longueur pré-tc d'une traduction termcap est trop longue. L'option -c (vérifier) vérifie également les longueurs résolues (après expansion tc).

EXTENSIONS

La recherche de descriptions de terminaux dans $HOME/.terminfo et TERMINFO_DIRS n'est pas prise en charge par les anciennes implémentations.

Certaines implémentations curses de SVr4, et toutes celles antérieures à SVr4, n'interprètent pas les opérateurs %A et %O dans les chaînes de paramètres.

SVr4/XPG4 ne spécifient pas si msgr autorise le mouvement en mode jeu de caractères alternatif (de tels modes peuvent, entre autres choses, mapper CR et NL à des caractères qui ne déclenchent pas les mouvements locaux). L'implémentation ncurses ignore msgr en mode ALTCHARSET. Cela soulève la possibilité qu'une implémentation XPG4 faisant l'interprétation opposée ait besoin d'entrées terminfo faites pour ncurses pour avoir msgr désactivé.

La bibliothèque ncurses gère les modes d'insertion/suppression de caractères d'une manière légèrement non standard pour obtenir une meilleure efficacité de mise à jour. Voir la sous-section Insertion/Suppression de caractères ci-dessus.

Les substitutions de paramètres pour set_clock et display_clock ne sont pas documentées dans SVr4 ou X/Open Curses. Elles sont déduites de la documentation du terminal AT&T 505.

Soyez prudent lors de l'attribution de la capacité kmous. La bibliothèque ncurses souhaite l'interpréter comme KEY_MOUSE, pour être utilisée par des terminaux et émulateurs comme xterm qui peuvent retourner des informations de suivi de souris dans le flux d'entrée du clavier.

X/Open Curses ne mentionne pas les italiques. Les applications portables doivent supposer que les capacités numériques sont des valeurs signées sur 16 bits. Cela inclut la capacité no_color_video (ncv). La valeur de masque 32768 utilisée pour les italiques avec ncv peut être confondue avec un ncv absent ou annulé. Si les italiques doivent fonctionner avec des couleurs, alors la valeur ncv doit être spécifiée, même si elle est nulle.

Différents ports commerciaux de terminfo et curses prennent en charge différents sous-ensembles de X/Open Curses et (dans certains cas) différentes extensions. Voici un résumé, exact à partir d'octobre 1995, après quoi le marché Unix commercial s'est contracté et a perdu de sa diversité.

  • SVr4, Solaris et ncurses prennent en charge toutes les capacités SVr4.
  • IRIX prend en charge l'ensemble SVr4 et ajoute une capacité de chaîne étendue non documentée (set_pglen).
  • SVr1 et Ultrix prennent en charge un sous-ensemble restreint des capacités terminfo. Les booléens se terminent par xon_xoff ; les numériques par width_status_line ; et les chaînes par prtr_non.
  • HP/UX prend en charge le sous-ensemble SVr1, plus les numériques SVr[234] num_labels, label_height, label_width, plus les touches de fonction 11 à 63, plus plab_norm, label_on et label_off, plus un certain nombre d'extensions incompatibles de table de chaînes.
  • AIX prend en charge le sous-ensemble SVr1, plus les touches de fonction 11 à 63, plus un certain nombre d'extensions incompatibles de table de chaînes.
  • OSF/1 prend en charge l'ensemble SVr4 et les extensions AIX.

PORTABILITÉ

Ne comptez pas sur la portabilité des entrées terminfo compilées (binaires) entre les systèmes Unix commerciaux. Au moins deux implémentations de terminfo (celles de HP-UX et d'AIX) ont divergé de celles des autres Unix System V après SVr1, ajoutant des capacités d'extension à la table de chaînes qui (au format binaire) entrent en collision avec les extensions System V et X/Open Curses ultérieures.
