NAME

thread - Extension pour l'accès aux scripts Tcl à la gestion des threads

SYNOPSIS

DESCRIPTION

L'extension thread crée des threads contenant des interpréteurs Tcl et permet d'envoyer des scripts à ces threads pour évaluation. De plus, elle fournit un accès au niveau du script aux primitives de synchronisation de base des threads, comme les mutex et les variables de condition.

COMMANDS

Cette section décrit les commandes de création et de destruction de threads et d'envoi de scripts à des threads pour évaluation.

thread::create ?-joinable? ?-preserved? ?script?
Cette commande crée un thread qui contient un interpréteur Tcl. L'interpréteur Tcl évalue le script optionnel, s'il est spécifié, ou attend dans la boucle d'événements des scripts qui arrivent via la commande thread::send. Les deux actions se déroulent simultanément au retour de la commande thread::create à l'appelant. Ni l'appelant n'attend la fin du script optionnel, ni le résultat éventuel du script n'est retourné à l'appelant. Le résultat de thread::create est l'ID du thread. Il s'agit du handle opaque qui identifie le nouveau thread pour toutes les autres commandes du package. Le handle du thread devient hors portée automatiquement lorsque le thread est marqué pour sortie (voir la commande thread::release ci-dessous).

Si l'argument script optionnel contient la commande thread::wait, le thread entrera dans la boucle d'événements. Si une telle commande n'est pas trouvée dans le script, le thread exécutera le script jusqu'à la fin et se terminera. Dans ce cas, le handle peut être ignoré en toute sécurité car il fait référence à un thread qui n'existe plus au moment où la commande retourne.

En utilisant l'option -joinable, il est possible de créer un thread joignable, c'est-à-dire dont la sortie peut être attendue en utilisant la commande thread::join. Notez que l'échec de joindre un thread créé avec l'option -joinable entraîne des fuites de ressources et de mémoire.

Les threads créés par thread::create ne peuvent pas être détruits de force. Par conséquent, il n'y a pas de commande de destruction de thread correspondante. Un thread ne peut être libéré qu'en utilisant thread::release et si son compteur de références interne tombe à zéro, le thread est marqué pour sortie. Cela expulse le thread de la gestion de la boucle d'événements et le thread continue à exécuter les commandes passées dans l'argument script, suivant la commande thread::wait. Si c'était la dernière commande du script, comme c'est généralement le cas, le thread se terminera.

Il est possible de créer une situation dans laquelle il peut être impossible de terminer le thread, par exemple en plaçant une boucle infinie après thread::wait ou en entrant à nouveau dans la boucle d'événements en exécutant une commande de type vwait. Dans de tels cas, le thread peut ne jamais se terminer. Ceci est considéré comme une mauvaise pratique et doit être évité si possible. Ceci est mieux illustré par l'exemple ci-dessous :

    # Vous ne devriez jamais faire ...
    set tid [thread::create {
        package require Http
        thread::wait
        vwait forever ; # <-- ceci !
    }]
Le thread créé dans l'exemple ci-dessus ne pourra jamais se terminer. Après avoir été libéré avec le dernier appel correspondant à thread::release, le thread sortira de thread::wait et continuera à exécuter les commandes suivantes. Il entrera dans la commande vwait et attendra indéfiniment des événements. Il n'y a aucun moyen de terminer un tel thread, vous ne voudriez donc pas faire cela !

Chaque thread nouvellement créé a son compteur de références interne initialisé à 0 (zéro), c'est-à-dire qu'il est non réservé. Ce compteur est incrémenté par un appel à la commande thread::preserve et décrémenté par un appel à la commande thread::release. Ces deux commandes implémentent un système de réservation de thread simple mais efficace et offrent des capacités de terminaison de thread prévisibles et contrôlables. Il est cependant possible de créer des threads initialement réservés en utilisant l'option -preserved de la commande thread::create. Les threads créés avec cette option ont la valeur initiale du compteur de références de 1 (un) et sont donc initialement marqués comme réservés.

thread::preserve ?id?
Cette commande incrémente le compteur de références du thread. Chaque appel à cette commande incrémente le compteur de références de un (1). La commande retourne la valeur du compteur de références après l'incrémentation. Si elle est appelée avec l'id de thread optionnel, la commande préserve le thread donné. Sinon, le thread courant est préservé.

Avec le comptage de références, on peut implémenter un accès contrôlé à un thread Tcl partagé. En incrémentant le compteur de références, l'appelant signale qu'il souhaite utiliser le thread pendant une période de temps prolongée. En décrémentant le compteur, l'appelant signale qu'il a fini d'utiliser le thread.

thread::release ?-wait? ?id?
Cette commande décrémente le compteur de références du thread. Chaque appel à cette commande décrémente le compteur de références de un (1). Si elle est appelée avec l'id de thread optionnel, la commande libère le thread donné. Sinon, le thread courant est libéré. La commande retourne la valeur du compteur de références après le décrément. Lorsque le compteur de références atteint zéro (0), le thread cible est marqué pour terminaison. Vous ne devez pas référencer le thread après que la commande thread::release retourne zéro ou un entier négatif. Le handle du thread devient hors portée et ne doit plus être utilisé. Toute référence ultérieure au même handle de thread entraînera une erreur Tcl.

L'option -wait demande au thread appelant d'attendre que le thread cible se termine, si l'effet de la commande devait entraîner la terminaison du thread cible, c'est-à-dire si le résultat retourné est zéro (0). Sans cette option, le thread appelant n'attend pas que le thread cible se termine. Il faut faire attention lors de l'utilisation de -wait, car cela peut bloquer indéfiniment le thread appelant. Cette option a été implémentée pour certains usages spéciaux de l'extension et est dépréciée pour une utilisation régulière. Les utilisateurs réguliers devraient créer des threads joignables en utilisant l'option -joinable de la commande thread::create et thread::join pour attendre la fin du thread.

Pour les canaux déjà existants, la commande ne fait rien, c'est-à-dire qu'il n'y a pas d'erreur à attacher le même canal plus d'une fois. La première opération effectuera réellement l'opération, tandis que toutes les opérations ultérieures ne feront rien. La commande génère une erreur si le channel ne peut pas être trouvé dans la liste des canaux détachés et/ou dans l'interpréteur actuel.
thread::mutex
Les mutex sont les primitives de synchronisation de threads les plus courantes. Ils sont utilisés pour synchroniser l'accès de deux threads ou plus à une ou plusieurs ressources partagées. Cette commande fournit un accès au niveau du script aux mutex exclusifs et/ou récursifs. Les mutex exclusifs ne peuvent être verrouillés qu'une seule fois par un seul thread, tandis que les mutex récursifs peuvent être verrouillés plusieurs fois par le même thread. Pour les mutex récursifs, le nombre d'opérations de verrouillage et de déverrouillage doit correspondre, sinon le mutex ne sera jamais libéré, ce qui entraînerait diverses situations d'interblocage.

Il faut être prudent lors de l'utilisation de mutex dans un programme multithread. Une mauvaise utilisation des mutex peut entraîner diverses situations d'interblocage, en particulier lors de l'utilisation de mutex exclusifs.

La commande thread::mutex prend en charge les sous-commandes et options suivantes :

thread::mutex create ?-recursive?
Crée le mutex et renvoie son handle opaque. Ce handle doit être utilisé pour toute référence future au mutex nouvellement créé. Si aucun argument facultatif ?-recursive? n'a été spécifié, la commande crée le mutex exclusif. Avec l'argument ?-recursive ?, la commande crée un mutex récursif.
thread::mutex destroy mutex
Détruit le mutex. Le mutex doit être déverrouillé avant la tentative de destruction. Si le mutex est verrouillé, la commande générera une erreur Tcl.
thread::mutex lock mutex
Verrouille le mutex. Le verrouillage du mutex exclusif peut générer une erreur Tcl si l'on tente de verrouiller le même mutex deux fois à partir du même thread. Si la logique de votre programme vous oblige à verrouiller le même mutex deux fois ou plus à partir du même thread (cela peut arriver lors d'appels de procédures récursives), vous devriez envisager d'utiliser les mutex récursifs.
thread::mutex unlock mutex
Déverrouille le mutex afin qu'un autre thread puisse le verrouiller à nouveau. Tenter de déverrouiller un mutex déjà déverrouillé générera une erreur Tcl.
thread::rwmutex
Cette commande crée des mutex à plusieurs lecteurs/un écrivain. Les mutex lecteur/écrivain vous permettent de sérialiser l'accès à une ressource partagée de manière plus optimale. Dans les situations où une ressource partagée est principalement lue et rarement modifiée, vous pourriez gagner en performance en utilisant des mutex lecteur/écrivain plutôt que des mutex exclusifs ou récursifs.

Pour lire la ressource, le thread doit obtenir un verrou de lecture sur la ressource. Le verrou de lecture n'est pas exclusif, ce qui signifie que plusieurs threads peuvent obtenir un verrou de lecture sur la même ressource, sans attendre d'autres lecteurs. Pour modifier la ressource, cependant, un thread doit obtenir un verrou d'écriture exclusif. Ce verrou bloque efficacement tous les threads de l'obtention du verrou de lecture pendant que la ressource est modifiée par le thread écrivain. Ce n'est qu'après la libération du verrou d'écriture que la ressource peut être relockée en lecture.

La commande thread::rwmutex prend en charge les sous-commandes et options suivantes :

thread::rwmutex create
Crée le mutex lecteur/écrivain et renvoie son handle opaque. Ce handle doit être utilisé pour toute référence future au mutex nouvellement créé.
thread::rwmutex destroy mutex
Détruit le mutex lecteur/écrivain. Si le mutex est déjà verrouillé, la tentative de le détruire générera une erreur Tcl.
thread::rwmutex rlock mutex
Verrouille le mutex pour la lecture. Plusieurs threads peuvent verrouiller en lecture le même mutex en même temps.
thread::rwmutex wlock mutex
Verrouille le mutex pour l'écriture. Un seul thread peut verrouiller en écriture le même mutex en même temps. Tenter de verrouiller en écriture le même mutex deux fois depuis le même thread générera une erreur Tcl.
thread::rwmutex unlock mutex
Déverrouille le mutex afin qu'un autre thread puisse le verrouiller à nouveau. Tenter de déverrouiller un mutex déjà déverrouillé générera une erreur Tcl.
thread::cond
Cette commande fournit un accès au niveau du script aux variables de condition. Une variable de condition crée un environnement sûr pour que le programme teste une condition, se mette en veille lorsque celle-ci est fausse et soit réveillé lorsqu'elle pourrait être devenue vraie. Une variable de condition est toujours utilisée conjointement avec un mutex exclusif. Si vous tentez d'utiliser un autre type de mutex conjointement avec la variable de condition, une erreur Tcl sera générée.

La commande prend en charge les sous-commandes et options suivantes :

thread::cond create
Crée la variable de condition et renvoie son handle opaque. Ce handle doit être utilisé pour toute référence future à la variable de condition nouvellement créée.
thread::cond destroy cond
Détruit la variable de condition cond. Il faut prendre des précautions extrêmes pour que personne n'utilise (c'est-à-dire n'attende sur) la variable de condition, sinon des erreurs inattendues pourraient se produire.
thread::cond notify cond
Réveille tous les threads en attente sur la variable de condition cond.
thread::cond wait cond mutex ?ms?
Cette commande est utilisée pour suspendre l'exécution du programme jusqu'à ce que la variable de condition cond ait été signalée ou que le minuteur facultatif ait expiré. Le mutex exclusif doit être verrouillé par le thread appelant à l'entrée de cette commande. Si le mutex n'est pas verrouillé, une erreur Tcl est générée. Pendant l'attente sur cond, la commande libère le mutex. Avant de retourner au thread appelant, la commande réacquiert à nouveau le mutex. Le déverrouillage du mutex et l'attente sur la variable de condition cond sont effectués de manière atomique.

L'option de commande ms, si elle est fournie, doit être un entier spécifiant l'intervalle de temps en millisecondes pendant lequel la commande attend d'être signalée. Sinon, la commande attendra indéfiniment la notification de condition.

Dans les programmes multithreads, il existe de nombreuses situations où un thread doit attendre qu'un événement se produise avant d'être autorisé à continuer. Ceci est généralement accompli en testant de manière répétée une condition sous la protection du mutex et en attendant sur la variable de condition jusqu'à ce que la condition devienne vraie :

    set mutex [thread::mutex create]
    set cond  [thread::cond  create]
    thread::mutex lock $mutex
    while {<some_condition_is_true>} {
        thread::cond wait $cond $mutex
    }
    # Faire quelque chose sous protection mutex
    thread::mutex unlock $mutex
Le test répété de la condition est nécessaire car la variable de condition peut être signalée sans que la condition n'ait réellement changé (réveils de thread intempestifs, par exemple).

DISCUSSION

Le modèle de threading fondamental dans Tcl est qu'il peut y avoir un ou plusieurs interpréteurs Tcl par thread, mais chaque interpréteur Tcl ne doit être utilisé que par un seul thread qui l'a créé. Une abstraction de "mémoire partagée" est difficile à fournir en Tcl car Tcl fait des hypothèses sur la propriété des variables et des données. Par conséquent, cette extension prend en charge une forme simple de threading où le thread principal peut gérer plusieurs threads d'arrière-plan, ou "threads de travail". Par exemple, un serveur piloté par événement peut passer des requêtes aux threads de travail, puis attendre les réponses des threads de travail ou de nouvelles requêtes client. Tout passe par la boucle d'événements Tcl commune, de sorte que la messagerie entre threads fonctionne naturellement avec l'E/S pilotée par événement, vwait sur les variables, etc. Pour le transfert d'informations volumineuses, il est possible de déplacer des canaux entre les threads.

Pour les scripts multithreads avancés, un accès au niveau du script à deux primitives de synchronisation de base, les mutex et les variables de condition, est également pris en charge.

    Linux Programmer's Manual

    NAME

    thread - POSIX threads

    SYNOPSIS

    #include <pthread.h>

    DESCRIPTION

    POSIX threads (often called pthreads) are a set of APIs for creating and manipulating threads. Threads are lightweight execution contexts within a process. They share the same address space and resources as the parent process, but have their own execution stack, program counter, and registers.

    This manual page describes the pthreads API. For a detailed description of individual functions, refer to their respective manual pages.

    Key concepts in pthreads include:

    • Thread creation and termination: Functions like pthread_create, pthread_exit, pthread_join.
    • Thread attributes: Functions like pthread_attr_init, pthread_attr_destroy, pthread_attr_setstacksize, pthread_attr_getstacksize.
    • Synchronization primitives: Mutexes (pthread_mutex_init, pthread_mutex_lock, pthread_mutex_unlock, etc.), condition variables (pthread_cond_init, pthread_cond_signal, pthread_cond_broadcast, etc.), semaphores (not directly in pthreads, but often implemented using mutexes and condition variables or provided by other libraries).
    • Thread-specific data: Functions like pthread_key_create, pthread_setspecific, pthread_getspecific.
    • Cancellation: Functions like pthread_cancel, pthread_setcancelstate, pthread_setcanceltype.
    • Scheduling: Functions like pthread_setschedparam, pthread_getschedparam, pthread_setschedpolicy, pthread_getschedpolicy.

    COMMANDS

    This section is not applicable for API manual pages.

    DISCUSSION

    Multithreading allows a program to perform multiple tasks concurrently, which can improve performance and responsiveness. However, it also introduces complexity related to shared resources and potential race conditions.

    It is crucial to manage shared data carefully using synchronization mechanisms like mutexes to prevent data corruption. Deadlocks can occur if threads acquire locks in different orders. Care must also be taken with thread cancellation to ensure that resources are properly cleaned up.

    When compiling programs that use pthreads, you typically need to link with the -pthread flag.

    KEYWORDS

    thread, pthreads, concurrency, multithreading, synchronization, mutex, condition variable

    NOM

    thread - Threads POSIX

    SYNTAXE

    #include <pthread.h>

    DESCRIPTION

    Les threads POSIX (souvent appelés pthreads) sont un ensemble d'API pour la création et la manipulation de threads. Les threads sont des contextes d'exécution légers au sein d'un processus. Ils partagent le même espace d'adressage et les mêmes ressources que le processus parent, mais ont leur propre pile d'exécution, compteur de programme et registres.

    Cette page de manuel décrit l'API pthreads. Pour une description détaillée des fonctions individuelles, référez-vous à leurs pages de manuel respectives.

    Les concepts clés des pthreads incluent :

    • Création et terminaison de thread : Fonctions comme pthread_create, pthread_exit, pthread_join.
    • Attributs de thread : Fonctions comme pthread_attr_init, pthread_attr_destroy, pthread_attr_setstacksize, pthread_attr_getstacksize.
    • Primitives de synchronisation : Mutex (pthread_mutex_init, pthread_mutex_lock, pthread_mutex_unlock, etc.), variables de condition (pthread_cond_init, pthread_cond_signal, pthread_cond_broadcast, etc.), sémaphores (pas directement dans pthreads, mais souvent implémentés à l'aide de mutex et de variables de condition ou fournis par d'autres bibliothèques).
    • Données spécifiques au thread : Fonctions comme pthread_key_create, pthread_setspecific, pthread_getspecific.
    • Annulation : Fonctions comme pthread_cancel, pthread_setcancelstate, pthread_setcanceltype.
    • Ordonnancement : Fonctions comme pthread_setschedparam, pthread_getschedparam, pthread_setschedpolicy, pthread_getschedpolicy.

    Cette section n'est pas applicable aux pages de manuel d'API.

    DISCUSSION

    Le multithreading permet à un programme d'effectuer plusieurs tâches simultanément, ce qui peut améliorer les performances et la réactivité. Cependant, il introduit également une complexité liée aux ressources partagées et aux conditions de concurrence potentielles.

    Il est crucial de gérer soigneusement les données partagées à l'aide de mécanismes de synchronisation tels que les mutex pour éviter la corruption des données. Des interblocages peuvent survenir si les threads acquièrent les verrous dans un ordre différent. Il faut également faire attention à l'annulation des threads pour s'assurer que les ressources sont correctement nettoyées.

    Lors de la compilation de programmes utilisant des pthreads, vous devez généralement lier avec le drapeau -pthread.
