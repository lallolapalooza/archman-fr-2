threads(3perl) Guide du programmeur Perl threads(3perl)

NOM

threads - Threads basés sur l'interpréteur Perl

VERSION

Ce document décrit la version 2.43 du module threads

AVERTISSEMENT

Les « threads basés sur l'interpréteur » fournis par Perl ne sont pas le moyen rapide et léger de multitâche auquel on pourrait s'attendre ou espérer. Les threads sont implémentés d'une manière qui les rend faciles à mal utiliser. Peu de gens savent comment les utiliser correctement ou seront capables d'apporter de l'aide.

L'utilisation des threads basés sur l'interpréteur en Perl est officiellement déconseillée.

SYNTAXE

use threads ('yield',
             'stack_size' => 64*4096,
             'exit' => 'threads_only',
             'stringify');
sub start_thread {
    my @args = @_;
    print('Thread démarré : ', join(' ', @args), "\n");
}
my $thr = threads->create('start_thread', 'argument');
$thr->join();
threads->create(sub { print("Je suis un thread\n"); })->join();
my $thr2 = async { foreach (@files) { ... } };
$thr2->join();
if (my $err = $thr2->error()) {
    warn("Erreur de thread : $err\n");
}
# Appel de thread en contexte de liste (implicite) pour qu'il puisse retourner une liste
my ($thr) = threads->create(sub { return (qw/a b c/); });
# ou spécifier explicitement le contexte
my $thr = threads->create({'context' => 'list'},
                          sub { return (qw/a b c/); });
my @results = $thr->join();
$thr->detach();
# Obtenir l'objet d'un thread
$thr = threads->self();
$thr = threads->object($tid);
# Obtenir l'ID d'un thread
$tid = threads->tid();
$tid = $thr->tid();
$tid = "$thr";
# Donner une chance aux autres threads de s'exécuter
threads->yield();
yield();
# Listes des threads non détachés
my @threads = threads->list();
my $thread_count = threads->list();
my @running = threads->list(threads::running);
my @joinable = threads->list(threads::joinable);
# Tester les objets thread
if ($thr1 == $thr2) {
    ...
}
# Gérer la taille de la pile des threads
$stack_size = threads->get_stack_size();
$old_size = threads->set_stack_size(32*4096);
# Créer un thread avec un contexte et une taille de pile spécifiques
my $thr = threads->create({ 'context'    => 'list',
                            'stack_size' => 32*4096,
                            'exit'       => 'thread_only' },
                          \&foo);
# Obtenir le contexte du thread
my $wantarray = $thr->wantarray();
# Vérifier l'état du thread
if ($thr->is_running()) {
    sleep(1);
}
if ($thr->is_joinable()) {
    $thr->join();
}
# Envoyer un signal à un thread
$thr->kill('SIGUSR1');
# Quitter un thread
threads->exit();

DESCRIPTION

Depuis Perl 5.8, la programmation de threads est disponible en utilisant un modèle appelé threads d'interpréteur qui fournit un nouvel interpréteur Perl pour chaque thread, et, par défaut, aucune donnée ou information d'état n'est partagée entre les threads.

(Avant Perl 5.8, 5005threads était disponible via l'API "Thread.pm". Ce modèle de threading a été déprécié, et a été supprimé à partir de Perl 5.10.0.)

Comme mentionné précédemment, toutes les variables sont, par défaut, locales au thread. Pour utiliser des variables partagées, vous devez également charger threads::shared :

use threads;
use threads::shared;

Lors du chargement de threads::shared, vous devez utiliser "use threads" avant d'utiliser "use threads::shared". (Le module "threads" émettra un avertissement si vous faites l'inverse.)

Il est fortement recommandé d'activer les threads via "use threads" dès que possible dans votre script.

Si nécessaire, les scripts peuvent être écrits de manière à fonctionner avec des Perl threadés et non threadés :

my $can_use_threads = eval 'use threads; 1';
if ($can_use_threads) {
    # Faire le traitement en utilisant les threads
    ...
} else {
    # Le faire sans utiliser les threads
    ...
}
$thr = threads->create(FONCTION, ARGS)
Ceci crée un nouveau thread qui commencera son exécution avec la fonction d'entrée spécifiée, et lui donnera la liste ARGS comme paramètres. Il retournera l'objet threads correspondant, ou "undef" si la création du thread a échoué.

FONCTION peut être le nom d'une fonction, une sous-routine anonyme, ou une référence de code.

my $thr = threads->create('nom_func', ...);
    # ou
my $thr = threads->create(sub { ... }, ...);
    # ou
my $thr = threads->create(\&func, ...);

La méthode "->new()" est un alias pour "->create()".

$thr->join()
Ceci attendra que le thread correspondant termine son exécution. Quand le thread se termine, "->join()" retournera la ou les valeurs de retour de la fonction d'entrée.

Le contexte (vide, scalaire ou liste) pour la ou les valeurs de retour pour "->join()" est déterminé au moment de la création du thread.

# Créer un thread en contexte de liste (implicite)
my ($thr1) = threads->create(sub {
                                my @results = qw(a b c);
                                return (@results);
                             });
#   ou (explicite)
my $thr1 = threads->create({'context' => 'list'},
                           sub {
                                my @results = qw(a b c);
                                return (@results);
                           });
# Récupérer les résultats de liste du thread
my @res1 = $thr1->join();
# Créer un thread en contexte scalaire (implicite)
my $thr2 = threads->create(sub {
                                my $result = 42;
                                return ($result);
                             });
# Récupérer le résultat scalaire du thread
my $res2 = $thr2->join();
# Créer un thread en contexte vide (explicite)
my $thr3 = threads->create({'void' => 1},
                           sub { print("Bonjour, le monde\n"); });
# Joindre le thread en contexte vide (c'est-à-dire sans valeur de retour)
$thr3->join();

Voir "CONTEXTE DE THREAD" pour plus de détails.

Si le programme se termine sans que tous les threads aient été joints ou détachés, un avertissement sera émis.

Appeler "->join()" ou "->detach()" sur un thread déjà joint provoquera une erreur.

$thr->detach()
Rend le thread non joignable, et provoque le rejet de toute valeur de retour éventuelle. Lorsque le programme se termine, les threads détachés qui sont encore en cours d'exécution sont silencieusement terminés.

Si le programme se termine sans que tous les threads aient été joints ou détachés, un avertissement sera émis.

Appeler "->join()" ou "->detach()" sur un thread déjà détaché provoquera une erreur.

threads->detach()
Méthode de classe qui permet à un thread de se détacher.
threads->self()
Méthode de classe qui permet à un thread d'obtenir son propre objet threads.
$thr->tid()
Retourne l'ID du thread. Les ID de thread sont des entiers uniques, le thread principal d'un programme étant 0, et les autres s'incrémentant de 1 pour chaque thread créé.
threads->tid()
Méthode de classe qui permet à un thread d'obtenir son propre ID.
"$thr"
Si vous ajoutez l'option d'importation "stringify" à votre déclaration "use threads", alors l'utilisation d'un objet thread dans une chaîne de caractères ou un contexte de chaîne (par exemple, comme clé de hachage) provoquera l'utilisation de son ID comme valeur : 
use threads qw(stringify);
my $thr = threads->create(...);
print("Thread $thr démarré\n");  # Affiche : Thread 1 démarré
threads->object($tid)
Ceci retournera l'objet threads pour le thread actif associé à l'ID de thread spécifié. Si $tid est la valeur du thread courant, alors cet appel fonctionne de la même manière que "->self()". Sinon, retourne "undef" s'il n'y a pas de thread associé au TID, si le thread est joint ou détaché, si aucun TID n'est spécifié ou si le TID spécifié est undef.
threads->yield()
Ceci permet au thread courant de céder la main aux autres threads, leur donnant une chance de s'exécuter. Ceci est utile pour éviter que des threads ne monopolisent le CPU.
yield()
Fonction exportée qui permet au thread courant de céder la main aux autres threads.
threads->list()
Retourne une liste de tous les objets threads qui n'ont pas été détachés. Si un argument est fourni, il doit s'agir d'une des constantes suivantes :
threads::running
Retourne uniquement les threads qui sont actuellement en cours d'exécution.
threads::joinable
Retourne uniquement les threads qui peuvent être joints (c'est-à-dire non détachés et non déjà joints).
Si aucune liste n'est fournie, alors tous les threads non détachés sont renvoyés. Si un thread a déjà été joint, il ne sera pas renvoyé. S'il a été détaché, il ne sera pas renvoyé.

Si la liste des threads est demandée dans un contexte scalaire, le nombre de threads correspondants sera retourné.

my @all_threads = threads->list();
my $num_threads = threads->list(); # Numéro de tous les threads
my @running_threads = threads->list(threads::running);
my $num_running = threads->list(threads::running); # Numéro des threads en cours d'exécution
$thr->error()
Si la création d'un thread a échoué, ou si le thread a rencontré une exception non gérée, alors "->error()" retournera une chaîne de caractères décrivant l'erreur. Sinon, elle retournera "undef".

Il est important de noter que cette méthode ne doit être appelée qu'après que le thread ait été joint.

$thr->kill(SIGNAL)
Envoie le signal SIGNAL au thread représenté par $thr. Ceci est implémenté en utilisant le système d'exploitation sous-jacent, et donc les signaux disponibles et leur comportement peuvent varier selon le système d'exploitation. Si le signal ne peut pas être envoyé, alors une exception sera levée.
$thr->is_running()
Retourne vrai si le thread est en cours d'exécution.
$thr->is_joinable()
Retourne vrai si le thread peut être joint (c'est-à-dire qu'il n'est ni détaché, ni déjà joint).
threads->exit()
Ceci termine le thread courant. Il ne faut pas l'appeler depuis le thread principal.
$thr->wantarray()
Retourne le contexte sous lequel le thread sera joint. Les valeurs possibles sont void, scalar ou list.
threads->stack_size()
Cette méthode est un alias pour "threads->get_stack_size()".
threads->get_stack_size()
Retourne la taille de la pile par défaut pour les nouveaux threads. Si aucun thread n'a été créé, alors cette taille est celle qui sera utilisée pour le prochain thread créé. Si des threads ont déjà été créés, alors il s'agit de la taille de pile utilisée par le dernier thread créé.
threads->set_stack_size(SIZE)
Définit la taille de la pile par défaut pour les nouveaux threads à SIZE octets. Ceci ne change pas la taille de pile des threads déjà créés. La valeur retournée est l'ancienne taille de pile par défaut.
threads->exit(MODE)
Dans le bloc "use threads", vous pouvez spécifier la façon dont les threads doivent se terminer. Les modes possibles sont :
threads_only
Le programme se terminera uniquement lorsque tous les threads non détachés auront été joints. Les threads détachés seront silencieusement terminés.
threads_any
Le programme se terminera lorsque le thread principal se terminera, même s'il reste des threads non joints. Un avertissement sera émis.
La valeur par défaut est threads_any.
threads->create(ATTRIBUTES, FUNCTION, ARGS)
Les attributs sont un hachage qui peut contenir les clés suivantes :
stack_size
La taille de pile à utiliser pour ce thread en particulier. Ceci a priorité sur la taille de pile par défaut définie par "threads->set_stack_size()".
exit
Spécifie la façon dont le programme doit se terminer lorsque ce thread se termine. Les valeurs possibles sont les mêmes que celles décrites pour la méthode de classe "threads->exit()".
context
Spécifie le contexte sous lequel le thread sera joint. Les valeurs possibles sont void, scalar ou list. Ceci a priorité sur la façon dont le retour est géré par défaut (qui est basé sur le contexte dans lequel le thread est appelé).

CONTEXTE DE THREAD

Le contexte dans lequel une fonction d'entrée de thread retourne une valeur est déterminé à la création du thread. Les valeurs possibles sont void, scalar et list.

Si le contexte est void, alors aucune valeur n'est retournée par ->join().

Si le contexte est scalar, alors la première valeur retournée par la fonction d'entrée est retournée par ->join().

Si le contexte est list, alors toutes les valeurs retournées par la fonction d'entrée sont retournées par ->join().

Si le contexte n'est pas explicitement spécifié, alors il est déduit du contexte dans lequel le thread est créé. Par exemple, si vous faites ceci :

my $thr = threads->create(sub { return (1, 2, 3); });
my $result = $thr->join();

Alors $result recevra la valeur 1, car le contexte est scalaire. D'un autre côté, si vous faites ceci :

my ($thr) = threads->create(sub { return (1, 2, 3); });
my @results = $thr->join();

Alors @results contiendra (1, 2, 3), car le contexte est une liste.

Si vous voulez éviter toute ambiguïté, vous pouvez spécifier le contexte explicitement en utilisant le quatrième argument de threads->create:

my $thr = threads->create({'context' => 'list'}, sub { return (1, 2, 3); });
my @results = $thr->join(); # @results contiendra (1, 2, 3)

EXEMPLE

use threads;
my $thr = threads->create(sub {
    my $tid = threads->tid();
    my $master_tid = threads->tid($thr); # Obtenir l'ID du thread parent
    print("Hello from thread $tid (parent $master_tid)\n");
    sleep(1);
    return "Thread $tid finished";
});
print("Main thread waiting for child...\n");
my $result = $thr->join();
print("Child thread returned: '$result'\n");

PROBLÈMES CONNUS ET LIMITATIONS

Les limitations et les problèmes suivants sont connus :

  • Les threads Perl sont des threads d'interpréteur, pas des threads du système d'exploitation. Ils sont beaucoup plus lourds que les threads du système d'exploitation et ne devraient pas être utilisés pour des tâches qui nécessitent des centaines ou des milliers de threads.

  • Certains modules Perl ne sont pas thread-safe. Leur utilisation dans des threads peut entraîner des résultats inattendus ou des plantages.

  • Le partage de données entre les threads est complexe et sujet aux erreurs. Il faut utiliser le module threads::shared et des primitives de synchronisation appropriées (comme les mutex et les sémaphores) pour éviter les conditions de concurrence.

  • La gestion des signaux dans les environnements multithreadés peut être délicate. L'envoi de signaux aux threads peut avoir des effets imprévisibles.

  • La taille de la pile des threads est généralement plus petite que la taille de pile par défaut du thread principal. Si vous prévoyez d'avoir des appels de fonction récursifs profonds ou de grandes allocations sur la pile dans vos threads, vous devrez peut-être augmenter la taille de la pile en utilisant threads->set_stack_size().

  • Le débogage de code multithreadé est nettement plus difficile que le débogage de code monothreadé. Les outils de débogage traditionnels peuvent ne pas fonctionner correctement avec les threads.

yield()
Ceci est une suggestion au SE pour permettre à ce thread de céder le temps processeur à d'autres threads. Ce qui se passe réellement dépend fortement de l'implémentation sous-jacente des threads.

Vous pouvez écrire "use threads qw(yield)", puis simplement utiliser yield() dans votre code.

threads->list()
threads->list(threads::all)
threads->list(threads::running)
threads->list(threads::joinable)
Sans arguments (ou en utilisant "threads::all") et dans un contexte de liste, retourne une liste de tous les objets threads non joints et non détachés. Dans un contexte scalaire, retourne le nombre de ceux-ci.

Avec un argument vrai (en utilisant "threads::running"), retourne une liste de tous les objets threads non joints et non détachés qui sont encore en cours d'exécution.

Avec un argument faux (en utilisant "threads::joinable"), retourne une liste de tous les objets threads non joints et non détachés qui ont terminé leur exécution (c'est-à-dire, pour lesquels "->join()" ne bloquera pas).

$thr1->equal($thr2)
Teste si deux objets threads sont le même thread ou non. Ceci est surchargé pour les formes plus naturelles : 
if ($thr1 == $thr2) {
    print("Les threads sont les mêmes\n");
}
# ou
if ($thr1 != $thr2) {
    print("Les threads diffèrent\n");
}

(La comparaison des threads est basée sur les identifiants de thread.)

async BLOC;
"async" crée un thread pour exécuter le bloc qui le suit immédiatement. Ce bloc est traité comme une sous-routine anonyme et doit donc avoir un point-virgule après l'accolade fermante. Comme "threads->create()", "async" retourne un objet threads.
$thr->error()
Les threads sont exécutés dans un contexte "eval". Cette méthode retournera "undef" si le thread se termine normalement. Sinon, elle retourne la valeur de $@ associée à l'état d'exécution du thread dans son contexte "eval".
$thr->_handle()
Cette méthode privée retourne un pointeur (c'est-à-dire, l'adresse mémoire exprimée en entier non signé) vers la structure interne de thread associée à un objet threads. Pour Win32, c'est un pointeur vers la valeur "HANDLE" retournée par "CreateThread" (c'est-à-dire, "HANDLE *"); pour d'autres plateformes, c'est un pointeur vers la structure "pthread_t" utilisée dans l'appel "pthread_create" (c'est-à-dire, "pthread_t *").

Cette méthode n'est d'aucune utilité pour la programmation générale de threads Perl. Son intention est de fournir à d'autres modules de threads (basés sur XS) la capacité d'accéder, et éventuellement de manipuler, la structure de thread sous-jacente associée à un thread Perl.

threads->_handle()
Méthode de classe qui permet à un thread d'obtenir son propre handle.

TERMINER UN THREAD

La méthode habituelle pour terminer un thread est de return() depuis la fonction d'entrée avec la ou les valeurs de retour appropriées.

threads->exit()
Si nécessaire, un thread peut être terminé à tout moment en appelant "threads->exit()". Cela provoquera le retour de "undef" par le thread dans un contexte scalaire, ou de la liste vide dans un contexte de liste.

Lorsqu'elle est appelée depuis le thread principal, cela se comporte comme exit(0).

threads->exit(status)
Lorsqu'elle est appelée depuis un thread, cela se comporte comme "threads->exit()" (c'est-à-dire, le code de statut de sortie est ignoré).

Lorsqu'elle est appelée depuis le thread principal, cela se comporte comme exit(status).

die()
Appeler die() dans un thread indique une sortie anormale pour le thread. Tout gestionnaire $SIG{__DIE__} dans le thread sera appelé en premier, puis le thread se terminera avec un message d'avertissement contenant les arguments passés à l'appel die().
exit(status)
Appeler exit() à l'intérieur d'un thread provoque la terminaison de toute l'application. Pour cette raison, l'utilisation de exit() à l'intérieur de code threadé, ou dans des modules qui pourraient être utilisés dans des applications threadées, est fortement déconseillée.

Si exit() est vraiment nécessaire, envisagez d'utiliser ce qui suit :

threads->exit() if threads->can('exit');   # Thread friendly
exit(status);
use threads 'exit' => 'threads_only'
Ceci remplace globalement le comportement par défaut de l'appel exit() à l'intérieur d'un thread, et fait effectivement en sorte que de tels appels se comportent comme "threads->exit()". Autrement dit, avec ce réglage, appeler exit() ne termine que le thread.

En raison de son effet global, ce réglage ne doit pas être utilisé à l'intérieur de modules ou similaires.

Le thread principal n'est pas affecté par ce réglage.

threads->create({'exit' => 'thread_only'}, ...)
Ceci remplace le comportement par défaut de exit() à l'intérieur du thread nouvellement créé uniquement.
$thr->set_thread_exit_only(boolean)
Ceci peut être utilisé pour changer le comportement exit thread only pour un thread après sa création. Avec un argument vrai, exit() ne provoquera la sortie que du thread. Avec un argument faux, exit() terminera l'application.

Le thread principal n'est pas affecté par cet appel.

threads->set_thread_exit_only(boolean)
Méthode de classe à utiliser à l'intérieur d'un thread pour changer son propre comportement pour exit().

Le thread principal n'est pas affecté par cet appel.

ÉTAT DU THREAD

Les méthodes booléennes suivantes sont utiles pour déterminer l'état état d'un thread.

$thr->is_running()
Retourne vrai si un thread est toujours en cours d'exécution (c'est-à-dire, si sa fonction d'entrée n'est pas encore terminée ou terminée).
$thr->is_joinable()
Retourne vrai si le thread a terminé son exécution, n'est pas détaché et n'a pas encore été joint. En d'autres termes, le thread est prêt à être joint, et un appel à "$thr->join()" ne bloquera pas.
$thr->is_detached()
Retourne vrai si le thread a été détaché.
threads->is_detached()
Méthode de classe qui permet à un thread de déterminer s'il est détaché ou non.

CONTEXTE DU THREAD

Comme pour les sous-routines, le type de valeur retournée par la fonction d'entrée d'un thread peut être déterminé par le contexte du thread : liste, scalaire ou vide. Le contexte du thread est déterminé lors de la création du thread. Ceci est nécessaire pour que le contexte soit disponible à la fonction d'entrée via wantarray(). Le thread peut alors spécifier une valeur du type approprié à retourner depuis "->join()".

Contexte explicite

Étant donné que la création de thread et la jonction de thread peuvent se produire dans des contextes différents, il peut être souhaitable de spécifier explicitement le contexte à la fonction d'entrée du thread. Ceci peut être fait en appelant "->create()" avec une référence de hachage comme premier argument :

my $thr = threads->create({'context' => 'list'}, \&foo);
...
my @results = $thr->join();

Dans l'exemple ci-dessus, l'objet threads est retourné au thread parent dans un contexte scalaire, et la fonction d'entrée du thread "foo" sera appelée dans un contexte de liste (tableau) de telle sorte que le thread parent puisse recevoir une liste (tableau) de l'appel "->join()". ('array' est synonyme de 'list'.)

De même, si vous avez besoin de l'objet threads, mais que votre thread ne retournera pas de valeur (c'est-à-dire, contexte vide), vous feriez ce qui suit :

my $thr = threads->create({'context' => 'void'}, \&foo);
...
$thr->join();

Le type de contexte peut également être utilisé comme clé dans la référence de hachage suivie d'une valeur vraie :

threads->create({'scalar' => 1}, \&foo);
...
my ($thr) = threads->list();
my $result = $thr->join();

Contexte implicite

S'il n'est pas explicitement indiqué, le contexte du thread est implicite par le contexte de l'appel "->create()" :

# Créer un thread dans un contexte de liste
my ($thr) = threads->create(...);
# Créer un thread dans un contexte scalaire
my $thr = threads->create(...);
# Créer un thread dans un contexte vide
threads->create(...);

$thr->wantarray()

Ceci retourne le contexte du thread de la même manière que wantarray().

TAILLE_PILE_THREAD

La taille par défaut de la pile par thread pour différentes plateformes varie considérablement, et est presque toujours bien plus que ce qui est nécessaire pour la plupart des applications. Sur Win32, le makefile de Perl définit explicitement la pile par défaut à 16 Mo ; sur la plupart des autres plateformes, la valeur par défaut du système est utilisée, ce qui peut encore être beaucoup plus grand que nécessaire.

En ajustant la taille de la pile pour qu'elle reflète plus précisément les besoins de votre application, vous pouvez réduire considérablement l'utilisation de la mémoire de votre application et augmenter le nombre de threads exécutés simultanément.

Notez que sous Windows, la granularité d'allocation d'espace d'adressage est de 64 Ko, par conséquent, définir la pile à une taille inférieure à celle-ci sous Win32 Perl n'économisera pas plus de mémoire.

threads->get_stack_size();
Retourne la taille de pile par défaut actuelle par thread. La valeur par défaut est zéro, ce qui signifie que la taille de pile par défaut du système est actuellement utilisée.
$taille = $thr->get_stack_size();
Retourne la taille de la pile pour un thread particulier. Une valeur de retour de zéro indique que la taille de pile par défaut du système a été utilisée pour le thread.
$ancienne_taille = threads->set_stack_size($nouvelle_taille);
Définit une nouvelle taille de pile par défaut par thread et renvoie le paramètre précédent.

Certaines plateformes ont une taille minimale de pile de thread. Essayer de définir la taille de la pile en dessous de cette valeur entraînera un avertissement, et la taille minimale de la pile sera utilisée.

Certaines plateformes Linux ont une taille maximale de pile. Définir une taille de pile trop grande entraînera l'échec de la création du thread.

Si nécessaire, $nouvelle_taille sera arrondie au multiple suivant de la taille de page mémoire (généralement 4096 ou 8192).

Les threads créés après la définition de la taille de la pile appelleront alors pthread_attr_setstacksize() (pour les plateformes pthreads), ou fourniront la taille de la pile à CreateThread() (pour Win32 Perl).

(Évidemment, cet appel n'affecte aucun thread existant.)

use threads ('stack_size' => VALEUR);
Ceci définit la taille de pile par défaut par thread au début de l'application.
$ENV{'PERL5_ITHREADS_STACK_SIZE'}
La taille de pile par défaut par thread peut être définie au début de l'application en utilisant la variable d'environnement "PERL5_ITHREADS_STACK_SIZE" : 
PERL5_ITHREADS_STACK_SIZE=1048576
export PERL5_ITHREADS_STACK_SIZE
perl -e'use threads; print(threads->get_stack_size(), "\n")'

Cette valeur remplace tout paramètre "stack_size" donné à "use threads". Son objectif principal est de permettre la définition de la taille de pile par thread pour les applications multithread héritées.

threads->create({'stack_size' => VALEUR}, FONCTION, ARGUMENTS)
Pour spécifier une taille de pile particulière pour n'importe quel thread individuel, appelez "->create()" avec une référence de hachage comme premier argument : 
my $thr = threads->create({'stack_size' => 32*4096},
                          \&foo, @args);
$thr2 = $thr1->create(FONCTION, ARGUMENTS)
Ceci crée un nouveau thread ($thr2) qui hérite de la taille de pile d'un thread existant ($thr1). C'est une abréviation pour : 
my $stack_size = $thr1->get_stack_size();
my $thr2 = threads->create({'stack_size' => $stack_size},
                           FONCTION, ARGUMENTS);

SIGNALISATION_THREAD

Lorsque les signaux sûrs sont actifs (comportement par défaut - voir "Signaux non sûrs" pour plus de détails), les signaux peuvent être envoyés et traités par des threads individuels.

$thr->kill('SIG...');
Envoie le signal spécifié au thread. Les noms de signaux et les numéros de signaux (positifs) sont les mêmes que ceux pris en charge par kill(). Par exemple, 'SIGTERM', 'TERM' et (selon le système d'exploitation) 15 sont tous des arguments valides pour "->kill()".

Retourne l'objet thread pour permettre le chaînage de méthodes :

$thr->kill('SIG...')->join();

Les gestionnaires de signaux doivent être configurés dans les threads pour les signaux sur lesquels ils sont censés agir. Voici un exemple pour *annuler* un thread :

use threads;
sub thr_func
{
    # Gestionnaire de signal de 'annulation' de thread
    $SIG{'KILL'} = sub { threads->exit(); };
    ...
}
# Créer un thread
my $thr = threads->create('thr_func');
...
# Signaler au thread de se terminer, puis le détacher
# pour qu'il soit nettoyé automatiquement
$thr->kill('KILL')->detach();

Voici un autre exemple simplifié qui illustre l'utilisation de la signalisation de thread en conjonction avec un sémaphore pour fournir des capacités rudimentaires de *mise en pause* et de *reprise* :

use threads;
use Thread::Semaphore;
sub thr_func
{
    my $sema = shift;
    # Gestionnaire de signal de 'mise en pause/reprise' de thread
    $SIG{'STOP'} = sub {
        $sema->down();      # Thread mis en pause
        $sema->up();        # Thread reprend
    };
    ...
}
# Créer un sémaphore et le passer à un thread
my $sema = Thread::Semaphore->new();
my $thr = threads->create('thr_func', $sema);
# Mettre le thread en pause
$sema->down();
$thr->kill('STOP');
...
# Permettre au thread de continuer
$sema->up();

ATTENTION : La capacité de signalisation de thread fournie par ce module n'envoie pas réellement de signaux via le système d'exploitation. Elle *émule* les signaux au niveau de Perl de telle sorte que les gestionnaires de signaux soient appelés dans le thread approprié. Par exemple, envoyer "$thr->kill('STOP')" ne suspend pas réellement un thread (ou tout le processus), mais provoque l'appel d'un gestionnaire $SIG{'STOP'} dans ce thread (comme illustré ci-dessus).

En tant que tels, les signaux qui ne seraient normalement pas appropriés à utiliser dans la commande kill() (par exemple, "kill('KILL', $$)") sont acceptables à utiliser avec la méthode "->kill()" (encore une fois, comme illustré ci-dessus).

Par conséquent, envoyer un signal à un thread ne perturbe pas l'opération sur laquelle le thread travaille actuellement : le signal sera traité après la fin de l'opération en cours. Par exemple, si le thread est *bloqué* sur un appel d'E/S, lui envoyer un signal n'interrompra pas l'appel d'E/S de telle sorte que le signal soit traité immédiatement.

Envoyer un signal à un thread terminé/achevé est ignoré.

AVERTISSEMENTS

Perl s'est terminé avec des threads actifs :
Si le programme se termine sans que tous les threads aient été joints ou détachés, cet avertissement sera émis.

NOTE : Si le thread *principal* se termine, cet avertissement ne peut pas être supprimé en utilisant "no warnings 'threads';" comme suggéré ci-dessous.

Échec de la création du thread : pthread_create a retourné #
Voir la page de manuel appropriée pour "pthread_create" pour déterminer la cause réelle de l'échec.
Thread # terminé anormalement : ...
Un thread s'est terminé d'une manière autre que le simple retour de sa fonction de point d'entrée, ou en utilisant "threads->exit()". Par exemple, le thread peut s'être terminé en raison d'une erreur, ou en utilisant "die".
Utilisation de la taille minimale de pile de thread de #
Certaines plateformes ont une taille minimale de pile de thread. Essayer de définir la taille de la pile en dessous de cette valeur entraînera l'avertissement ci-dessus, et la taille de la pile sera définie à la valeur minimale.
Échec de la création du thread : pthread_attr_setstacksize(TAILLE) a retourné 22
La TAILLE spécifiée dépasse la taille maximale de pile du système. Utilisez une valeur plus petite pour la taille de la pile.

Si nécessaire, les avertissements de thread peuvent être supprimés en utilisant :

no warnings 'threads';

dans la portée appropriée.

ERREURS

Ce Perl n'est pas compilé pour supporter les threads
La copie particulière de Perl que vous essayez d'utiliser n'a pas été compilée avec l'option de configuration "useithreads".

Le support des threads nécessite que tout Perl et tous les modules XS de l'installation Perl soient reconstruits ; il ne s'agit pas simplement d'ajouter le module threads (c'est-à-dire que les Perl threadés et non threadés sont binaires incompatibles).

Impossible de changer la taille de la pile d'un thread existant
La taille de la pile des threads actuellement existants ne peut pas être modifiée, par conséquent, ce qui suit entraîne l'erreur ci-dessus : 
$thr->set_stack_size($taille);
Impossible de signaler les threads sans signaux sûrs
Les signaux sûrs doivent être actifs pour utiliser la méthode de signalisation "->kill()". Voir "Signaux non sûrs" pour plus de détails.
Nom de signal non reconnu : ...
La copie particulière de Perl que vous essayez d'utiliser ne prend pas en charge le signal spécifié utilisé dans un appel "->kill()".

BOGUES ET LIMITATIONS

Avant d'envisager de soumettre un rapport de bogue, veuillez consulter, et éventuellement poster un message sur le forum de discussion pour voir si ce que vous avez rencontré est un problème connu.

Modules thread-safe
Voir "Rendre votre module thread-safe" dans perlmod
lors de la création de modules qui peuvent être utilisés dans des applications multithreadées, en particulier si ces modules utilisent des données non-Perl ou du code XS.
Utilisation de modules non thread-safe
Malheureusement, vous pouvez rencontrer des modules Perl qui ne sont pas thread-safe. Par exemple, ils peuvent planter l'interpréteur Perl pendant leur exécution, ou planter (dump core) lors de la terminaison. Selon le module et les exigences de votre application, il peut être possible de contourner ces difficultés.

Si le module ne doit être utilisé qu'à l'intérieur d'un thread, vous pouvez essayer de charger le module depuis l'intérieur de la fonction d'entrée du thread en utilisant "require" (et "import" si nécessaire) :

sub thr_func
{
    require Unsafe::Module
    # Unsafe::Module->import(...);
    ....
}

Si le module est nécessaire dans le thread *principal*, essayez de modifier votre application de manière à ce que le module soit chargé (à nouveau en utilisant "require" et "->import()") après le démarrage de tous les threads, et de telle sorte qu'aucun autre thread ne soit démarré après.

Si ce qui précède ne fonctionne pas, ou n'est pas suffisant pour votre application, alors déposez un rapport de bug sur https://rt.cpan.org/Public/ contre le module problématique.

Consommation de mémoire
Sur la plupart des systèmes, la création et la destruction fréquentes et continues de threads peuvent entraîner une croissance continue de l'empreinte mémoire de l'interpréteur Perl. Bien qu'il soit simple de lancer des threads puis de les "->join()" ou de les "->detach()", pour les applications de longue durée, il est préférable de maintenir un pool de threads et de les réutiliser pour le travail nécessaire, en utilisant des files d'attente pour notifier les threads du travail en attente. La distribution CPAN de ce module contient un exemple simple (examples/pool_reuse.pl) illustrant la création, l'utilisation et la surveillance d'un pool de threads *réutilisables*.
Répertoire de travail actuel
Sur toutes les plateformes sauf MSWin32, le paramètre du répertoire de travail actuel est partagé entre tous les threads de telle sorte que sa modification dans un thread (par exemple, en utilisant chdir()) affectera tous les threads de l'application.

Sur MSWin32, chaque thread conserve son propre paramètre de répertoire de travail actuel.

Locales
Avant Perl 5.28, les locales ne pouvaient pas être utilisées avec les threads, en raison de diverses conditions de concurrence. À partir de cette version, sur les systèmes qui implémentent des fonctions de locale thread-safe, les threads peuvent être utilisés, avec quelques mises en garde. Cela inclut Windows à partir de Visual Studio 2005, et les systèmes compatibles avec POSIX 2008. Voir "Multi-threaded operation" dans perllocale.

Chaque thread (sauf le thread principal) est démarré en utilisant la locale C. Le thread principal est démarré comme tous les autres programmes Perl ; voir "ENVIRONMENT" dans perllocale. Vous pouvez changer de locale dans n'importe quel thread aussi souvent que vous le souhaitez.

Si vous souhaitez hériter de la locale du thread parent, vous pouvez, dans le parent, définir une variable comme suit :

$foo = POSIX::setlocale(LC_ALL, NULL);

et ensuite passer à threads->create() une sous-routine qui ferme sur $foo. Ensuite, dans l'enfant, vous dites

POSIX::setlocale(LC_ALL, $foo);

Ou vous pouvez utiliser les fonctionnalités de threads::shared pour passer $foo ; ou si l'environnement n'a pas changé, dans l'enfant, faites

POSIX::setlocale(LC_ALL, "");
Variables d'environnement
Actuellement, sur toutes les plateformes sauf MSWin32, tous les appels *système* (par exemple, en utilisant system() ou les back-ticks) effectués à partir des threads utilisent les paramètres des variables d'environnement du thread *principal*. En d'autres termes, les modifications apportées à %ENV dans un thread ne seront pas visibles dans les appels *système* effectués par ce thread.

Pour contourner cela, définissez les variables d'environnement dans le cadre de l'appel *système*. Par exemple :

my $msg = 'hello';
system("FOO=$msg; echo \$FOO");   # Affiche 'hello' sur STDOUT

Sur MSWin32, chaque thread conserve son propre ensemble de variables d'environnement.

Capture des signaux
Les signaux sont *capturés* par le thread principal (ID de thread = 0) d'un script. Par conséquent, la mise en place de gestionnaires de signaux dans les threads à des fins autres que la "SIGNALISATION DE THREAD" comme documenté ci-dessus n'accomplira pas ce qui est prévu.

C'est particulièrement vrai si vous essayez de capturer "SIGALRM" dans un thread. Pour gérer les alarmes dans les threads, mettez en place un gestionnaire de signaux dans le thread principal, puis utilisez la "SIGNALISATION DE THREAD" pour relayer le signal au thread :

# Crée un thread avec une tâche qui peut expirer
my $thr = threads->create(sub {
    threads->yield();
    eval {
        $SIG{ALRM} = sub { die("Timeout\n"); };
        alarm(10);
        ...  # Faire le travail ici
        alarm(0);
    };
    if ($@ =~ /Timeout/) {
        warn("La tâche dans le thread a expiré\n");
    }
};
# Définit le gestionnaire de signaux pour relayer SIGALRM au thread
$SIG{ALRM} = sub { $thr->kill('ALRM') };
... # Le thread principal continue de travailler
Threads parent-enfant
Sur certaines plateformes, il peut ne pas être possible de détruire les threads *parents* tant qu'il existe encore des threads *enfants*.
Signaux dangereux
Depuis Perl 5.8.0, les signaux ont été rendus plus sûrs dans Perl en reportant leur gestion jusqu'à ce que l'interpréteur soit dans un état *sûr*. Voir "Safe Signals" dans perl58delta et "Deferred Signals (Safe Signals)" dans perlipc pour plus de détails.

Les signaux sûrs sont le comportement par défaut, et l'ancien comportement de signalisation immédiat et dangereux n'est en vigueur que dans les situations suivantes :

  • Perl a été compilé avec "PERL_OLD_SIGNALS" (voir "perl -V").
  • La variable d'environnement "PERL_SIGNALS" est définie sur "unsafe" (voir "PERL_SIGNALS" dans perlrun).
  • Le module Perl::Unsafe::Signals est utilisé.

Si les signaux dangereux sont actifs, la gestion des signaux n'est pas thread-safe, et la méthode de signalisation "->kill()" ne peut pas être utilisée.

Identité des objets renvoyés par les threads
Lorsqu'une valeur est renvoyée par un thread via une opération "join", la valeur et tout ce à quoi elle fait référence sont copiés dans le thread de jonction, un peu de la même manière que les valeurs sont copiées lors de la création du thread. Cela fonctionne bien pour la plupart des types de valeurs, y compris les tableaux, les hachages et les sous-routines. La copie est récursive à travers les éléments de tableau, les scalaires de référence, les variables fermées par les sous-routines et d'autres types de références.

Cependant, tout ce à quoi la valeur renvoyée fait référence est une nouvelle copie dans le thread de jonction, même si un objet renvoyé était dans le thread enfant une copie de quelque chose qui existait précédemment dans le thread parent. Après la jonction, le parent aura donc un doublon de chacun de ces objets. Cela peut parfois poser problème, surtout si l'objet est modifié ; cela peut particulièrement poser problème pour les données privées auxquelles une sous-routine renvoyée donne accès.

Retour d'objets "blessés" depuis les threads
Le retour d'objets "blessés" (blessed objects) depuis les threads ne fonctionne pas. Selon les classes impliquées, vous pourrez peut-être contourner ce problème en retournant une version sérialisée de l'objet (par exemple, en utilisant Data::Dumper ou Storable), puis en la reconstituant dans le thread de jonction. Si vous utilisez Perl 5.10.0 ou une version ultérieure, et si la classe prend en charge les objets partagés, vous pouvez les passer via des files d'attente partagées.
Blocs END dans les threads
Il est possible d'ajouter des blocs END aux threads en utilisant require ou eval avec le code approprié. Ces blocs "END" seront alors exécutés lorsque l'interpréteur du thread sera détruit (c'est-à-dire, soit lors d'un appel "->join()", soit lors de la terminaison du programme).

Cependant, l'appel de toute méthode de threads dans un tel bloc "END" échouera très probablement (par exemple, l'application peut se bloquer ou générer une erreur) en raison des mutex nécessaires pour contrôler la fonctionnalité au sein du module threads.

Pour cette raison, l'utilisation de blocs "END" dans les threads est *fortement* déconseillée.

Descripteurs de répertoire ouverts
Dans perl 5.14 et supérieur, sur les systèmes autres que Windows qui ne prennent pas en charge la fonction C "fchdir", les descripteurs de répertoire (voir opendir) ne seront pas copiés vers les nouveaux threads. Vous pouvez utiliser la variable "d_fchdir" dans Config.pm pour déterminer si votre système la prend en charge.

Dans les versions précédentes de perl, le lancement de threads avec des descripteurs de répertoire ouverts plantait l'interpréteur. [perl #75154] https://rt.perl.org/rt3/Public/Bug/Display.html?id=75154

Threads détachés et destruction globale
Si le thread principal se termine alors qu'il y a des threads détachés qui sont toujours en cours d'exécution, alors la phase de destruction globale de Perl n'est pas exécutée car, sinon, certaines structures globales qui contrôlent le fonctionnement des threads et qui sont allouées dans la mémoire du thread principal pourraient être détruites avant que le thread détaché ne soit détruit.

Si vous utilisez du code qui nécessite l'exécution de la phase de destruction globale pour le nettoyage (par exemple, la suppression de fichiers temporaires), n'utilisez pas de threads détachés, mais plutôt joignez tous les threads avant de quitter le programme.

BUGS AND LIMITATIONS

Some Perl versions might have bugs that may manifest themselves despite using the latest version of threads from CPAN. There is no workaround for this other than upgrading to the latest version of Perl.

Even with the latest version of Perl, it is known that certain constructs with threads may result in warning messages concerning leaked scalars or unreferenced scalars. However, such warnings are harmless, and may safely be ignored.

You can search for threads related bug reports at https://rt.cpan.org/Public/. If needed submit any new bugs, problems, patches, etc. to: https://rt.cpan.org/Public/Dist/Display.html?Name=threads
