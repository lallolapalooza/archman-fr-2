ttrace - Initialisation d'interpréteur basée sur le traçage

DESCRIPTION

Ce paquet crée un framework pour la réplication à la demande de l'état de l'interpréteur à travers les threads dans une application multithread. Il repose sur les mécanismes de traçage des commandes Tcl et sur la commande et le mécanisme unknown de Tcl.

Le paquet nécessite l'extension de threading Tcl mais peut également être utilisé de manière autonome au sein d'AOLserver, un serveur web évolutif d'America Online.

En bref, un court exemple illustrant l'utilisation de ttrace avec l'extension de threading Tcl :

    % package require Ttrace
    2.8.0
    % set t1 [thread::create {package require Ttrace; thread::wait}]
    tid0x1802800
    % ttrace::eval {proc test args {return test-[thread::id]}}
    % thread::send $t1 test
    test-tid0x1802800
    % set t2 [thread::create {package require Ttrace; thread::wait}]
    tid0x1804000
    % thread::send $t2 test
    test-tid0x1804000

Comme vu ci-dessus, les commandes ttrace::eval et ttrace::update sont utilisées pour créer une définition à l'échelle du thread d'une procédure Tcl simple et répliquer cette définition à tous les threads déjà existants ou créés ultérieurement.

COMMANDES UTILISATEUR

Cette section décrit les commandes au niveau utilisateur. Ces commandes peuvent être utilisées par les auteurs de scripts pour contrôler l'exécution du framework de traçage.

ttrace::eval arg ?arg ...?
Cette commande concatène les arguments donnés et évalue la commande Tcl résultante avec le framework de traçage activé. Si l'exécution de la commande s'est déroulée correctement, elle prend les mesures nécessaires pour propager automatiquement le changement d'époque de traçage à tous les threads de l'application. Pour AOLserver, seuls les nouveaux threads créés reçoivent effectivement le changement d'époque. Pour l'extension de threading Tcl, tous les threads créés par l'extension sont automatiquement mis à jour. Si l'exécution de la commande a résulté en une erreur Tcl, aucune propagation d'état n'a lieu.

C'est la commande la plus importante au niveau utilisateur du paquet car elle encapsule la plupart des commandes décrites ci-dessous. Cela simplifie grandement les choses, car l'utilisateur n'a besoin d'apprendre que cette (une) commande pour utiliser efficacement le paquet. Les autres commandes, décrites ci-dessous, sont incluses principalement par souci de complétude.

ttrace::enable
Active tous les callbacks enregistrés dans le framework et démarre une nouvelle époque de traçage. L'époque de traçage encapsule toutes les modifications apportées à l'interpréteur pendant l'activation des traces.
ttrace::disable
Désactive tous les callbacks enregistrés dans le framework et clôt l'époque de traçage en cours.
ttrace::cleanup
Utilisé pour nettoyer toutes les ressources chargées à la demande dans l'interpréteur. Il ramène effectivement l'interpréteur Tcl à son état d'origine.
ttrace::update ?epoch?
Utilisé pour rafraîchir l'état de l'interpréteur afin qu'il corresponde à l'époque de traçage optionnelle ?epoch?. Si ?epoch? n'est pas fourni, il prend la dernière époque de traçage.
ttrace::getscript
Retourne un script Tcl synthétisé qui peut être sourcé dans n'importe quel interpréteur. Ce script prépare la commande unknown de Tcl afin qu'elle puisse charger les ressources tracées à partir de la base de données en mémoire. Normalement, cette commande est automatiquement invoquée par d'autres commandes de plus haut niveau comme ttrace::eval et ttrace::update.

COMMANDES DE CALLBACK

Un mot d'avance : le paquet inclut déjà des callbacks pour tracer les commandes Tcl suivantes : proc, namespace, variable, load, et rename. De plus, un ensemble de callbacks pour tracer les ressources (objets, classes) pour XOTcl v1.3.8+, une extension OO à Tcl, est également fourni. Cela offre une base solide pour résoudre la plupart des besoins réels et sert d'exemple aux personnes souhaitant personnaliser le paquet pour couvrir leurs besoins spécifiques.

Ci-dessous, vous trouverez les commandes pour enregistrer les callbacks dans le framework et pour écrire des scripts de callback. Ces callbacks sont invoqués par le framework afin de collecter les changements d'état de l'interpréteur, de construire une base de données en mémoire, d'effectuer des nettoyages personnalisés et diverses autres tâches.

ttrace::atenable cmd arglist body
Enregistre un callback Tcl à activer lors de ttrace::enable. Les callbacks enregistrés sont activés sur la base FIFO. La définition du callback inclut le nom du callback, cmd, une liste d'arguments de callback, arglist et le corps du callback. Efficacement, cela ressemble en fait à l'interface d'appel de la commande Tcl standard proc.
ttrace::atdisable cmd arglist body
Enregistre un callback Tcl à activer lors de ttrace::disable. Les callbacks enregistrés sont activés sur la base FIFO. La définition du callback inclut le nom du callback, cmd, une liste d'arguments de callback, arglist et le corps du callback. Efficacement, cela ressemble en fait à l'interface d'appel de la commande Tcl standard proc.
ttrace::addtrace cmd arglist body
Enregistre un callback Tcl à activer pour tracer la commande Tcl cmd. La définition du callback inclut le nom de la commande Tcl à tracer, cmd, une liste d'arguments de callback, arglist et le corps du callback. Efficacement, cela ressemble en fait à l'interface d'appel de la commande Tcl standard proc.
ttrace::addscript name body
Enregistre un callback Tcl à activer pour construire un script Tcl à passer à d'autres interpréteurs. Ce script est utilisé pour préparer la commande unknown de Tcl. Les callbacks enregistrés sont activés sur la base FIFO. La définition du callback inclut le nom du callback, name et le corps du callback.
ttrace::addresolver cmd arglist body
Enregistre un callback Tcl à activer par la commande Tcl surchargée unknown. Les callbacks enregistrés sont activés sur la base FIFO. Ce callback est utilisé pour résoudre la ressource et charger la ressource dans l'interpréteur courant.
ttrace::addcleanup body
Enregistre un callback Tcl à activer par trace::cleanup. Les callbacks enregistrés sont activés sur la base FIFO.
ttrace::addentry cmd var val
Ajoute une entrée à la base de données nommée en mémoire.
ttrace::getentry cmd var
Retourne la valeur de l'entrée de la base de données nommée en mémoire.
ttrace::getentries cmd ?pattern?
Retourne une liste de toutes les entrées correspondantes du nom de la base de données nommée. Si un modèle est donné, seul le sous-ensemble correspondant au modèle est retourné.
ttrace::delentry cmd
Supprime toutes les entrées de la base de données nommée.
ttrace::preload cmd
Enregistre une commande Tcl à exécuter avant le chargement de toute ressource. Le but est de permettre de charger des ressources qui ne sont pas gérées par les gestionnaires standards de trace.

DISCUSSION

Les approches courantes de réplication d'état introspectif utilisent un script Tcl personnalisé pour introspecter l'interpréteur en cours d'exécution et synthétiser un autre script Tcl pour répliquer cet état dans un autre interpréteur. Ce paquet, au contraire, utilise des traces de commandes Tcl. Les traces de commandes sont enregistrées sur des commandes Tcl sélectionnées, comme proc, namespace, load et d'autres commandes Tcl standard (et/ou définies par l'utilisateur). Lorsqu'elles sont activées, ces traces construisent une base de données en mémoire des ressources créées. Cette base de données est utilisée comme dépôt de ressources pour la commande Tcl unknown (surchargée) qui crée la ressource demandée dans l'interpréteur à la demande. De cette façon, les utilisateurs peuvent mettre à jour un seul interpréteur (maître) dans un thread et répliquer cet état d'interpréteur (ou une partie de celui-ci) à d'autres threads/interprètes dans le processus.

L'avantage immédiat d'une telle approche est l'empreinte mémoire beaucoup plus faible de l'application et la création de threads beaucoup plus rapide. En ne chargeant pas réellement toutes les procédures nécessaires (et autres ressources) dans chaque thread au moment de l'initialisation du thread, mais en différant cela au moment où la ressource est effectivement référencée, des améliorations significatives de la consommation de mémoire et du temps d'initialisation des threads peuvent être réalisées. Certains tests ont montré que l'empreinte mémoire d'une application Tcl multithread a été réduite de plus de trois fois et que le temps de démarrage des threads a été réduit d'environ 50 fois. Notez que vos résultats peuvent varier. D'autres avantages incluent un contrôle beaucoup plus fin sur ce qui (et quand) est répliqué du maître vers d'autres threads/interprètes Tcl.
