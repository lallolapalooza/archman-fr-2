NOM

u32 - filtre de contrôle de trafic universel 32 bits

SYNTAXE


tc filter ... [ handle HANDLE ] u32 LISTE_OPTIONS [ offset OFFSET ] [ hashkey HASHKEY ] [ classid CLASSID ] [ divisor valeur_uint ] [ order valeur_u32 ] [ ht HANDLE ] [ sample SELECTIONNEUR [ divisor valeur_uint ] ] [ link HANDLE ] [ indev ifname ] [ skip_hw | skip_sw ] [ help ]

HANDLE := { u12_hex_htid:[u8_hex_hash:[u12_hex_nodeid] | 0xvaleur_u32_hex }

LISTE_OPTIONS := [ LISTE_OPTIONS ] OPTION

HASHKEY := [ mask valeur_u32_hex ] [ at 4*valeur_int ]

CLASSID := { root | none | [u16_major]:u16_minor | valeur_u32_hex }

OFFSET := [ plus valeur_int ] [ at 2*valeur_int ] [ mask valeur_u16_hex ] [ shift valeur_int ] [ eat ]

OPTION := { match SELECTIONNEUR | action ACTION }

SELECTIONNEUR := { u32 VAL_MASQUE_32 | u16 VAL_MASQUE_16 | u8 VAL_MASQUE_8 | ip IP | ip6 IP6 | { tcp | udp } TCPUDP | icmp ICMP | mark VAL_MASQUE_32 | ether ETHER }

IP := { { src | dst } { default | any | all | adresse_ip [ / { longueur_prefixe | masque_reseau } ] } AT | { dsfield | ihl | protocol | precedence | icmp_type | icmp_code } VAL_MASQUE_8 | { sport | dport } VAL_MASQUE_16 | nofrag | firstfrag | df | mf }

IP6 := { { src | dst } { default | any | all | adresse_ip6 [/longueur_prefixe ] } AT | priority VAL_MASQUE_8 | { protocol | icmp_type | icmp_code } VAL_MASQUE_8 | flowlabel VAL_MASQUE_32 | { sport | dport } VAL_MASQUE_16 }

TCPUDP := { src | dst } VAL_MASQUE_16

ICMP := { type VAL_MASQUE_8 | code VAL_MASQUE_8 }

ETHER := { src | dst } adresse_ether AT

VAL_MASQUE_32 := valeur_u32 masque_u32_hex [ AT ]

VAL_MASQUE_16 := valeur_u16 masque_u16_hex [ AT ]

VAL_MASQUE_8 := valeur_u8 masque_u8_hex [ AT ]

AT := [ at [ nexthdr+ ] valeur_int ]

DESCRIPTION

Le filtre universel/moche 32 bits permet de faire correspondre des champs de bits arbitraires dans le paquet. En raison de la décomposition de tout en valeurs, masques et décalages, il est à la fois puissant et difficile à utiliser. Heureusement, de nombreuses directives d'abstraction sont présentes, permettant de définir des règles à un niveau supérieur et libérant ainsi l'utilisateur de la nécessité de manipuler des bits et des masques dans de nombreux cas.

Il existe deux modes d'invocation généraux : le premier mode crée un nouveau filtre pour déléguer les paquets vers différentes destinations. Outre les options évidentes, à savoir la classification du paquet en spécifiant un CLASSID ou en appelant une action, on peut link un filtre à un autre (ou même à une liste d'entre eux), organisant ainsi efficacement les filtres en une hiérarchie arborescente.

Typiquement, la délégation de filtres se fait au moyen d'une table de hachage, ce qui conduit au second mode d'invocation : il sert simplement à mettre en place ces tables de hachage. Les filtres peuvent sélectionner une table de hachage et fournir un sélecteur de clé à partir duquel un hachage sera calculé et utilisé comme clé pour rechercher le compartiment de la table contenant des filtres pour un traitement ultérieur. Ceci est utile si un grand nombre de filtres est utilisé, car le surcoût de l'opération de hachage et de la recherche dans la table devient négligeable dans ce cas. L'utilisation de tables de hachage avec u32 implique essentiellement le schéma suivant :

(1)
Créer une nouvelle table de hachage, en spécifiant sa taille à l'aide du paramètre divisor et idéalement un handle par lequel la table peut être identifiée. Si ce dernier n'est pas fourni, le noyau en choisit un de lui-même, qui doit être deviné plus tard.
(2)
Créer des filtres qui se lient à la table créée à l'étape (1) en utilisant le paramètre link et en définissant les données du paquet que le noyau utilisera pour calculer le hashkey.
(3)
Ajouter des filtres aux compartiments de la table de hachage de l'étape (1). Afin d'éviter d'avoir à savoir exactement comment le noyau crée la clé de hachage, il existe le paramètre sample, qui fournit des données d'exemple à hacher et définit ainsi le compartiment de la table auquel le filtre doit être ajouté.

En fait, même si ce n'est pas explicitement demandé, u32 crée une table de hachage pour chaque priority auquel un filtre est ajouté. La taille de la table est cependant de 1, il s'agit donc en fait simplement d'une liste chaînée.

VALEURS

Les options et les sélecteurs nécessitent que les valeurs soient spécifiées dans un format spécifique, souvent peu intuitif. Par conséquent, les terminaux dans la SYNTAXE ont reçu des noms descriptifs pour indiquer le format requis et/ou la valeur maximale autorisée : Les préfixes u32, u16 et u8 indiquent des valeurs non signées de quatre, deux et une octet respectivement. Par exemple, u16 indique une valeur de deux octets dans la plage de 0 à 65535 (0xFFFF) inclusivement. Un préfixe int indique une valeur signée de quatre octets. Une partie intermédiaire _hex_ indique que la valeur est analysée au format hexadécimal. Sinon, la base de la valeur est détectée automatiquement, c'est-à-dire que les valeurs préfixées par 0x sont considérées comme hexadécimales, un 0 initial indique le format octal et le format décimal sinon. Il existe également des valeurs avec un formatage spécial : adresse_ip et masque_reseau sont au format pointé-quad comme d'habitude pour les adresses IPv4. Une adresse_ip6 est spécifiée dans le format hexadécimal courant, séparé par des deux-points. Enfin, longueur_prefixe est une valeur entière décimale non signée dans la plage de 0 à la largeur d'adresse en bits (32 pour IPv4 et 128 pour IPv6).

Parfois, les valeurs doivent être divisibles par un certain nombre. Dans ce cas, un nom de la forme N*val a été choisi, indiquant que val doit être divisible par N. Ou l'inverse : la valeur résultante doit être un multiple de N.

OPTIONS

U32 reconnaît les options suivantes :

handle HANDLE
Le handle est utilisé pour référencer un filtre et doit donc être unique. Il se compose d'un identifiant de table de hachage htid et d'un hash optionnel (qui identifie le compartiment de la table de hachage) et d'un nodeid. Toutes ces valeurs sont analysées comme des nombres hexadécimaux non signés d'une longueur de 12 bits ( htid et nodeid) ou 8 bits ( hash). Alternativement, on peut spécifier un seul nombre hexadécimal de 32 bits qui contient les trois champs de bits concaténés. Outre les champs eux-mêmes, il doit être préfixé par 0x.
offset OFFSET
Définit un décalage qui détermine où les correspondances des filtres subséquents sont appliquées. Par conséquent, cette option n'est utile que lorsqu'elle est combinée avec link ou une combinaison de ht et sample. Le décalage peut être donné explicitement en utilisant le mot-clé plus, ou extrait des données du paquet avec at. Il est possible de le modifier à l'aide des mots-clés mask et/ou shift. Par défaut, ce décalage est enregistré mais pas appliqué implicitement. Il est utilisé uniquement pour substituer l'instruction nexthdr+. L'utilisation du mot-clé eat inverse cependant ce comportement : le décalage est toujours appliqué, et nexthdr+ reviendra à zéro.
hashkey HASHKEY
Spécifie quelles données du paquet utiliser pour calculer une clé de hachage pour la recherche de compartiment. Le noyau ajuste la valeur en fonction de la taille de la table de hachage. Pour que cela fonctionne, l'option link doit être fournie.
classid CLASSID
Classe les paquets correspondants dans le CLASSID donné, qui se compose soit de 16 bits major et

divisor u32_value
Spécifiez une valeur modulo. Utilisé lors de la création de tables de hachage pour définir leur taille ou pour déclarer un sample afin de calculer les clés de table de hachage à partir. Doit être une puissance de deux avec un exposant ne dépassant pas huit.
order u32_value
Une valeur pour ordonner les filtres, par ordre croissant. Entre en conflit avec handle qui remplit le même objectif.
sample SELECTOR
Utilisé conjointement avec ht pour spécifier dans quel bucket ajouter ce filtre. Cela permet d'éviter d'avoir à connaître le mode exact de calcul des hachages par le noyau. Le divisor supplémentaire est par défaut à 256, il doit donc être spécifié pour les tables de hachage de taille différente.
link HANDLE
Délègue les paquets correspondants aux filtres d'une table de hachage. HANDLE est utilisé pour spécifier uniquement la table de hachage, donc seul htid peut être donné, hash et nodeid doivent être omis. Par défaut, le bucket numéro 0 sera utilisé et peut être remplacé par l'option hashkey.
indev ifname
Filtre sur l'interface entrante du paquet. Ne fonctionne évidemment que pour le trafic acheminé.
skip_sw
Ne pas traiter le filtre par logiciel. Si le matériel n'a pas de support d'offload pour ce filtre, ou si l'offload TC n'est pas activé pour l'interface, l'opération échouera.
skip_hw
Ne pas traiter le filtre par matériel.
help
Imprimer un bref texte d'aide sur les options possibles.

SELECTORS

Fondamentalement, le seul vrai sélecteur est u32 . Tous les autres fournissent simplement une syntaxe de plus haut niveau et sont traduits en interne en u32 .

u32 VAL_MASK_32
u16 VAL_MASK_16
u8 VAL_MASK_8
Faire correspondre les données du paquet à une valeur donnée. Le nom du sélecteur définit la longueur de l'échantillon à extraire (32 bits pour u32, 16 bits pour u16 et 8 bits pour u8). Avant la comparaison, l'échantillon est combiné par un ET binaire avec le masque donné. De cette façon, les bits non pertinents peuvent être effacés avant la comparaison. La position de l'échantillon est définie par le décalage spécifié dans AT.
ip IP
ip6 IP6
Suppose que le paquet commence par un en-tête IPv4 (ip) ou IPv6 (ip6). IP/IP6 permet alors de faire correspondre divers champs d'en-tête :
src ADDR
dst ADDR
Comparer les champs d'adresse source ou destination avec la valeur de ADDR. Les mots réservés default, any et all correspondent effectivement à n'importe quelle adresse. Sinon, une adresse IP du protocole particulier est attendue, éventuellement suffixée par une longueur de préfixe pour faire correspondre des sous-réseaux entiers. Dans le cas d'IPv4, un masque réseau peut également être donné.
dsfield VAL_MASK_8
IPv4 uniquement. Fait correspondre le champ DSCP/ECN de l'en-tête du paquet. Les synonymes sont tos et precedence.
ihl VAL_MASK_8
IPv4 uniquement. Fait correspondre le champ Longueur de l'en-tête Internet. Notez que l'unité de la valeur est de 32 bits, donc pour faire correspondre un paquet avec un en-tête de 24 octets, u8_value doit être 6.
protocol VAL_MASK_8
Fait correspondre la valeur du champ Protocole (IPv4) ou En-tête suivant (IPv6), par exemple 6 pour TCP.
icmp_type VAL_MASK_8
icmp_code VAL_MASK_8
Suppose un protocole d'en-tête suivant icmp ou ipv6-icmp et fait correspondre les valeurs des champs Type ou Code. C'est dangereux, car le code suppose une taille d'en-tête minimale pour IPv4 et l'absence d'en-têtes d'extension pour IPv6.
sport VAL_MASK_16
dport VAL_MASK_16
Fait correspondre les ports source ou destination de couche 4. C'est également dangereux, car cela suppose qu'un protocole de couche 4 approprié est présent (qui a des champs de port source et destination juste au début de l'en-tête et d'une taille de 16 bits). De plus, une taille d'en-tête minimale pour IPv4 et l'absence d'en-têtes d'extension IPv6 sont supposées.
nofrag
firstfrag
df
mf
IPv4 uniquement, vérifie certains indicateurs et valeurs de décalage de fragment. Correspond si le paquet n'est pas un fragment (nofrag), le premier fragment d'un paquet fragmenté (firstfrag), si les bits Ne pas fragmenter (df) ou Plus de fragments (mf) sont définis.
priority VAL_MASK_8
IPv6 uniquement. Fait correspondre le champ Classe de trafic de l'en-tête, qui a le même objectif et sémantique que le champ ToS d'IPv4 depuis la RFC 3168 : les six bits supérieurs sont DSCP, les deux bits inférieurs ECN.
flowlabel VAL_MASK_32
IPv6 uniquement. Fait correspondre la valeur du champ Étiquette de flux. Notez que l'étiquette de flux elle-même ne fait que 20 octets de long, ce sont les octets les moins significatifs ici. Les 12 octets supérieurs restants correspondent aux champs Version et Classe de trafic.
tcp TCPUDP
udp TCPUDP
Fait correspondre les champs de l'en-tête suivant du protocole TCP ou UDP. Les valeurs possibles pour TCPDUP sont :
src VAL_MASK_16
Correspondance sur la valeur du champ Port source.
dst VALMASK_16
Correspondance sur la valeur du champ Port de destination.
icmp ICMP
Fait correspondre les champs de l'en-tête suivant du protocole ICMP. Les valeurs possibles pour ICMP sont :
type VAL_MASK_8
Correspondance sur le champ Type ICMP.
code VAL_MASK_8
Correspondance sur le champ Code ICMP.
mark VAL_MASK_32
Correspondance sur la valeur fwmark netfilter.
ether ETHER
Fait correspondre les champs de l'en-tête Ethernet. Les valeurs possibles pour ETHER sont :
src ether_address AT
dst ether_address AT
Correspondance sur l'adresse Ethernet source ou destination. Ceci est dangereux : il suppose qu'un en-tête Ethernet est présent au début du paquet. Cela conduira probablement à des résultats inattendus s'il est utilisé avec des interfaces de couche trois telles que tun ou ppp.

EXEMPLES

tc filter add dev eth0 parent 999:0 prio 99 protocol ip u32 \
        match ip src 192.168.8.0/24 classid 1:1

Ceci attache un filtre à la qdisc identifiée par 999:0. Sa priorité est 99, ce qui affecte l'ordre dans lequel plusieurs filtres attachés au même parent sont consultés (plus bas, plus tôt). Le filtre gère les paquets de type protocol ip, et match si l'adresse source de l'en-tête IP se trouve dans le sous-réseau 192.168.8.0/24. Les paquets correspondants sont classifiés dans la classe 1.1. L'effet de cette commande peut être surprenant à première vue :

filter parent 1: protocol ip pref 99 u32
filter parent 1: protocol ip pref 99 u32 \
        fh 800: ht divisor 1
filter parent 1: protocol ip pref 99 u32 \
        fh 800::800 order 2048 key ht 800 bkt 0 flowid 1:1 \
        match c0a80800/ffffff00 at 12

Donc, le parent 1: se voit attribuer un nouveau filtre u32, qui contient une table de hachage de taille 1 (comme l'indique le divisor). L'ID de la table est 800. La troisième ligne montre ensuite le filtre réel qui a été ajouté ci-dessus : il se trouve dans la table 800 et le bucket 0, classe les paquets dans l'ID de classe 1:1 et fait correspondre les trois octets supérieurs de la valeur de quatre octets au décalage 12 à 0xc0a808, ce qui correspond à 192, 168 et 8.

Maintenant, pour quelque chose de plus complexe, à savoir la création d'une table de hachage personnalisée :

tc filter add dev eth0 prio 99 handle 1: u32 divisor 256

Ceci crée une table de taille 256 avec le handle 1: en priorité 99. L'effet est le suivant :

filter parent 1: protocol all pref 99 u32
filter parent 1: protocol all pref 99 u32 fh 1: ht divisor 256
filter parent 1: protocol all pref 99 u32 fh 800: ht divisor 1

Donc, en plus de la table de hachage demandée (handle 1:), le noyau a créé sa propre table de taille 1 pour contenir d'autres filtres de la même priorité.

La prochaine étape consiste à créer un filtre qui se lie à la table de hachage créée :

tc filter add dev eth0 parent 1: prio 1 u32 \
        link 1: hashkey mask 0x0000ff00 at 12 \
        match ip src 192.168.0.0/16

Le filtre reçoit une priorité inférieure à celle de la table de hachage elle-même, de sorte que u32 la consulte avant de parcourir manuellement la table de hachage. Les options link et hashkey déterminent quelle table et quel bucket rediriger. Dans ce cas, la clé de hachage doit être construite à partir du deuxième octet au décalage 12, ce qui correspond à

responds to the third byte of the source address field of an IP packet. Coupled with the match statement, this effectively maps all class C networks below 192.168.0.0/16 to different buckets of the hash table.

Des filtres pour certains sous-réseaux peuvent être créés comme suit :

tc filter add dev eth0 parent 1: prio 99 u32 \
        ht 1: sample u32 0x00000800 0x0000ff00 at 12 \
        match ip src 192.168.8.0/24 classid 1:1

Le seau est défini en utilisant l'option sample : Dans ce cas, le deuxième octet à l'offset 12 doit être exactement 0x08. Dans ce cas, l'ID de seau résultant est évidemment 8, mais dès que sample sélectionne une quantité de données qui pourrait dépasser le divisor, il faudrait connaître l'algorithme interne du noyau pour déduire le seau de destination. L'instruction match de ce filtre est redondante dans ce cas, car l'entropie pour la clé de hachage ne dépasse pas la taille de la table et par conséquent aucune collision ne peut se produire. Sinon, il est nécessaire d'éviter de faire correspondre des paquets indésirables.

Faire correspondre des champs de couche supérieure est problématique car la longueur de l'en-tête IPv4 est variable et IPv6 prend en charge les en-têtes d'extension qui affectent le décalage de l'en-tête de couche supérieure. Pour surmonter cela, il est possible de spécifier nexthdr+ lors de la fourniture d'un décalage, et pour faciliter les choses, il existe les correspondances tcp et udp qui utilisent nexthdr+ implicitement. Ce décalage doit cependant être calculé à l'avance, et le seul moyen d'y parvenir est de le faire dans un filtre séparé qui se lie ensuite au filtre qui souhaite l'utiliser. Voici un exemple de la manière de procéder :

tc filter add dev eth0 parent 1:0 protocol ip handle 1: \
        u32 divisor 1
tc filter add dev eth0 parent 1:0 protocol ip \
        u32 ht 1: \
        match tcp src 22 FFFF \
        classid 1:2
tc filter add dev eth0 parent 1:0 protocol ip \
        u32 ht 800: \
        match ip protocol 6 FF \
        match u16 0 1fff at 6 \
        offset at 0 mask 0f00 shift 6 \
        link 1:

C'est ce qui est fait : Lors du premier appel, une table de hachage de taille d'un seul élément est créée afin qu'il y ait un endroit pour contenir le filtre lié et un identifiant connu (1:) pour y faire référence. Le deuxième appel ajoute ensuite le filtre réel, qui pousse les paquets avec le port source TCP 22 vers la classe 1:2. En utilisant ht, il est déplacé dans la table de hachage créée par le premier appel. Le troisième appel fait alors la véritable magie : il fait correspondre les paquets IPv4 avec le protocole de couche suivante 6 (TCP), uniquement s'il s'agit du premier fragment (généralement TCP définit le bit DF, mais s'il ne le fait pas et que le paquet est fragmenté, seul le premier contient l'en-tête TCP), puis définit le décalage en fonction du champ IHL de l'en-tête IP (un décalage vers la droite de 6 élimine le décalage du champ et convertit en même temps la valeur en unité d'octet). Enfin, en utilisant link, la table de hachage du premier appel est référencée, qui contient le filtre du deuxième appel.
