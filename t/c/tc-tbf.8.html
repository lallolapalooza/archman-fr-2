TC(8) Linux TC(8)

NOM

tbf - Token Bucket Filter

SYNTAXE

tc qdisc ... tbf rate taux burst octets/cellule ( latency ms | limit octets ) [ mpu octets [ peakrate taux mtu octets/cellule ] ]

burst est aussi connu sous le nom de buffer et maxburst. mtu est aussi connu sous le nom de minburst.

DESCRIPTION

Le Token Bucket Filter (TBF) est une discipline de mise en file d'attente (queueing discipline) qui peut être utilisée pour le contrôle de trafic avec la commande tc(8).

Le TBF est un façonneur (shaper) pur et ne planifie jamais le trafic. Il n'est pas "work-conserving" et peut se ralentir lui-même, même si des paquets sont disponibles, pour s'assurer que le taux configuré n'est pas dépassé. Il est capable de façonner jusqu'à 1mbit/s de trafic normal avec une आपल्याला (burstiness) minimale idéale, envoyant les données exactement aux taux configurés.

Des taux beaucoup plus élevés sont possibles mais au prix de la perte de la आपल्याला minimale. Dans ce cas, les données sont défilées en moyenne au taux configuré mais peuvent être envoyées beaucoup plus vite sur des échelles de temps de millisecondes. En raison des files d'attente supplémentaires dans les adaptateurs réseau, ce n'est souvent pas un problème.

ALGORITHME

Comme son nom l'indique, le trafic est filtré en fonction de la dépense de jetons (tokens). Les jetons correspondent approximativement aux octets, avec la contrainte supplémentaire que chaque paquet consomme quelques jetons, peu importe sa taille. Ceci reflète le fait que même un paquet de taille nulle consomme un certain temps sur la liaison.

Lors de la création, le TBF est rempli de jetons qui correspondent à la quantité de trafic pouvant être émise en une seule fois. Les jetons arrivent à un taux régulier, jusqu'à ce que le seau soit plein.

Si aucun jeton n'est disponible, les paquets sont mis en file d'attente, jusqu'à une limite configurée. Le TBF calcule alors le déficit de jetons, et ralentit jusqu'à ce que le premier paquet dans la file puisse être envoyé.

S'il n'est pas acceptable d'émettre les paquets à vitesse maximale, un taux de crête (peakrate) peut être configuré pour limiter la vitesse à laquelle le seau se vide. Ce taux de crête est implémenté comme un second TBF avec un seau très petit, de sorte qu'il ne puisse pas émettre en rafale.

Pour atteindre la perfection, le second seau ne peut contenir qu'un seul paquet, ce qui conduit à la limite de 1mbit/s mentionnée précédemment.

Cette limite est causée par le fait que le noyau ne peut ralentir que par minimum 1 'jiffy', qui dépend de HZ comme 1/HZ. Pour un façonnage parfait, un seul paquet peut être envoyé par jiffy - pour HZ=100, cela signifie 100 paquets d'en moyenne 1000 octets chacun, ce qui correspond approximativement à 1mbit/s.

PARAMETRES

Voir tc(8) pour savoir comment spécifier les unités de ces valeurs.

limit ou latency
Limit est le nombre d'octets qui peuvent être mis en file d'attente en attendant que des jetons deviennent disponibles. Vous pouvez aussi le spécifier dans l'autre sens en définissant le paramètre latency, qui spécifie la durée maximale pendant laquelle un paquet peut rester dans le TBF. Ce dernier calcul prend en compte la taille du seau, le taux et éventuellement le taux de crête (s'il est défini). Ces deux paramètres sont mutuellement exclusifs.
burst
Aussi connu sous le nom de buffer ou maxburst. Taille du seau, en octets. C'est la quantité maximale d'octets pour lesquels des jetons peuvent être disponibles instantanément. En général, des taux de façonnage plus élevés nécessitent un seau plus grand. Pour 10mbit/s sur Intel, vous avez besoin d'au moins 10kbyte de buffer si vous voulez atteindre votre taux configuré !

Si votre buffer est trop petit, des paquets peuvent être rejetés car plus de jetons arrivent par tick de timer qu'il n'en tient dans votre seau. La taille minimale du buffer peut être calculée en divisant le taux par HZ.

Les calculs d'utilisation des jetons sont effectués à l'aide d'une table qui, par défaut, a une résolution de 8 paquets. Cette résolution peut être modifiée en spécifiant la taille de la cellule avec burst. Par exemple, pour spécifier un buffer de 6000 octets avec une taille de cellule de 16 octets, définissez un burst de 6000/16. Vous n'aurez probablement jamais à le spécifier. Doit être une puissance entière de 2.

mpu
Un paquet de taille zéro ne consomme pas une bande passante nulle. Pour Ethernet, aucun paquet ne consomme moins de 64 octets. Le Minimum Packet Unit détermine l'utilisation minimale des jetons (spécifiée en octets) pour un paquet. Par défaut à zéro.
rate
Le bouton de vitesse. Voir les remarques ci-dessus sur les limites ! Voir tc(8) pour les unités.

De plus, si un taux de crête est souhaité, les paramètres suivants sont disponibles :

peakrate
Taux de déplétion maximal du seau. Le taux de crête n'a pas besoin d'être défini, il n'est nécessaire que si un façonnage parfait à l'échelle des millisecondes est requis.
mtu/minburst
Spécifie la taille du seau du taux de crête. Pour une précision parfaite, devrait être réglé sur l'MTU de l'interface. Si un taux de crête est nécessaire, mais qu'un peu de आपल्याला est acceptable, cette taille peut être augmentée. Un minburst de 3000 octets permet environ 3mbit/s de taux de crête, étant donné des paquets de 1000 octets.

Comme la taille normale du burst, vous pouvez aussi spécifier une taille de cellule.

EXEMPLE & UTILISATION

Pour attacher un TBF avec un taux maximal soutenu de 0.5mbit/s, un taux de crête de 1.0mbit/s, un buffer de 5kilooctets, avec une taille de file d'attente pré-seau calculée de sorte que le TBF cause au plus 70ms de latence, avec un comportement de taux de crête parfait, exécutez :

# tc qdisc add dev eth0 handle 10: root tbf rate 0.5mbit \
burst 5kb latency 70ms peakrate 1mbit \
minburst 1540

Pour attacher une qdisc interne, par exemple sfq, exécutez :

# tc qdisc add dev eth0 parent 10:1 handle 100: sfq

Sans qdisc interne, la file TBF agit comme une bfifo. Si la qdisc interne est modifiée, la limite/latence n'est plus effective.
