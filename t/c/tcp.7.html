tcp(7) Manuel d'informations diverses tcp(7)

NOM

tcp - Protocole TCP

SYNTAXIS

#include <sys/socket.h>
#include <netinet/in.h>
#include <netinet/tcp.h>
socket_tcp = socket(AF_INET, SOCK_STREAM, 0);

DESCRIPTION

Ceci est une implémentation du protocole TCP définie dans les RFC 793, RFC 1122 et RFC 2001 avec les extensions NewReno et SACK. Elle fournit une connexion fiable, orientée flux, full-duplex entre deux sockets par-dessus ip(7), pour les versions v4 et v6. TCP garantit que les données arrivent dans l'ordre et retransmet les paquets perdus. Il génère et vérifie une somme de contrôle par paquet pour détecter les erreurs de transmission. TCP ne préserve pas les frontières d'enregistrement.

Une socket TCP nouvellement créée n'a ni adresse locale ni distante et n'est pas entièrement spécifiée. Pour établir une connexion TCP sortante, utilisez connect(2) pour établir une connexion avec une autre socket TCP. Pour recevoir de nouvelles connexions entrantes, utilisez d'abord bind(2) sur la socket à une adresse et un port locaux, puis appelez listen(2) pour mettre la socket en état d'écoute. Après cela, une nouvelle socket pour chaque connexion entrante peut être acceptée à l'aide de accept(2). Une socket sur laquelle accept(2) ou connect(2) a été appelée avec succès est entièrement spécifiée et peut transmettre des données. Les données ne peuvent pas être transmises sur des sockets en écoute ou non encore connectées.

Linux prend en charge les extensions TCP haute performance RFC 1323. Celles-ci incluent la Protection contre les numéros de séquence enveloppés (PAWS), la mise à l'échelle de la fenêtre et les horodatages. La mise à l'échelle de la fenêtre permet l'utilisation de grandes fenêtres TCP (> 64 Ko) afin de prendre en charge les liaisons à latence ou bande passante élevée. Pour les utiliser, les tailles des tampons d'envoi et de réception doivent être augmentées. Elles peuvent être définies globalement avec les fichiers /proc/sys/net/ipv4/tcp_wmem et /proc/sys/net/ipv4/tcp_rmem, ou sur des sockets individuelles en utilisant les options de socket SO_SNDBUF et SO_RCVBUF avec l'appel setsockopt(2).

Les tailles maximales des tampons de socket déclarés via les mécanismes SO_SNDBUF et SO_RCVBUF sont limitées par les valeurs dans les fichiers /proc/sys/net/core/rmem_max et /proc/sys/net/core/wmem_max. Notez que TCP alloue en fait deux fois la taille du tampon demandé dans l'appel setsockopt(2), et donc un appel getsockopt(2) réussi ne retournera pas la même taille de tampon que celle demandée dans l'appel setsockopt(2). TCP utilise l'espace supplémentaire à des fins administratives et pour les structures internes du noyau, et les valeurs des fichiers /proc reflètent les tailles plus importantes par rapport aux fenêtres TCP réelles. Sur des connexions individuelles, la taille du tampon de socket doit être définie avant les appels listen(2) ou connect(2) pour qu'elle prenne effet. Voir socket(7) pour plus d'informations.

TCP prend en charge les données urgentes. Les données urgentes sont utilisées pour signaler au récepteur qu'un message important fait partie du flux de données et qu'il doit être traité dès que possible. Pour envoyer des données urgentes, spécifiez l'option MSG_OOB à send(2). Lorsque des données urgentes sont reçues, le noyau envoie un signal SIGURG au processus ou au groupe de processus qui a été défini comme « propriétaire » de la socket à l'aide des ioctls SIOCSPGRP ou FIOSETOWN (ou de l'opération F_SETOWN spécifiée par POSIX.1 fcntl(2)). Lorsque l'option de socket SO_OOBINLINE est activée, les données urgentes sont insérées dans le flux de données normal (un programme peut tester sa position à l'aide de l'ioctl SIOCATMARK décrit ci-dessous), sinon elles ne peuvent être reçues que lorsque le drapeau MSG_OOB est défini pour recv(2) ou recvmsg(2).

Lorsqu'il y a des données hors bande, select(2) indique le descripteur de fichier comme ayant une condition exceptionnelle et poll(2) indique un événement POLLPRI.

Linux 2.4 a introduit un certain nombre de modifications pour améliorer le débit et la mise à l'échelle, ainsi que des fonctionnalités améliorées. Certaines de ces fonctionnalités incluent la prise en charge du zéro-copie sendfile(2), la Notification Explicite de Congestion, une nouvelle gestion des sockets TIME_WAIT, des options de socket keep-alive et la prise en charge des extensions Duplicate SACK.

Formats d'adresse

TCP est construit par-dessus IP (voir ip(7)). Les formats d'adresse définis par ip(7) s'appliquent à TCP. TCP prend uniquement en charge la communication point à point ; la diffusion (broadcasting) et la multidiffusion (multicasting) ne sont pas prises en charge.

Interfaces /proc

Les paramètres TCP au niveau du système peuvent être accessibles via les fichiers du répertoire /proc/sys/net/ipv4/. De plus, la plupart des interfaces /proc d'IP s'appliquent également à TCP ; voir ip(7). Les variables décrites comme Booléennes acceptent une valeur entière, une valeur non nulle (« vrai ») signifiant que l'option correspondante est activée, et une valeur zéro (« faux ») signifiant que l'option est désactivée.

tcp_abc (Entier ; par défaut : 0 ; Linux 2.6.15 à Linux 3.8)
Contrôle le calcul de taille appropriée des octets (Appropriate Byte Count, ABC), défini dans la RFC 3465. L'ABC est un moyen d'augmenter la fenêtre de congestion (cwnd) plus lentement en réponse aux accusés de réception partiels. Les valeurs possibles sont :
0
incrémente cwnd une fois par accusé de réception (pas d'ABC)
1
incrémente cwnd une fois par accusé de réception d'un segment de taille complète
2
permet d'incrémenter cwnd par deux si l'accusé de réception concerne deux segments pour compenser les accusés de réception retardés.
tcp_abort_on_overflow (Booléen ; par défaut : désactivé ; depuis Linux 2.4)
Active la réinitialisation des connexions si le service d'écoute est trop lent et incapable de suivre et de les accepter. Cela signifie que si un débordement s'est produit en raison d'une rafale, la connexion se rétablira. Activez cette option *uniquement* si vous êtes vraiment sûr que le démon d'écoute ne peut pas être réglé pour accepter les connexions plus rapidement. L'activation de cette option peut nuire aux clients de votre serveur.
tcp_adv_win_scale (entier ; par défaut : 2 ; depuis Linux 2.4)
Compte la surcharge de mise en mémoire tampon comme octets/2^tcp_adv_win_scale, si tcp_adv_win_scale est supérieur à 0 ; ou octets-octets/2^(-tcp_adv_win_scale), si tcp_adv_win_scale est inférieur ou égal à zéro.
L'espace du tampon de réception de la socket est partagé entre l'application et le noyau. TCP maintient une partie du tampon comme fenêtre TCP, c'est la taille de la fenêtre de réception annoncée à l'autre extrémité. Le reste de l'espace est utilisé comme tampon « application », utilisé pour isoler le réseau des latences de planification et d'application. La valeur par défaut de tcp_adv_win_scale de 2 implique que l'espace utilisé pour le tampon de l'application est un quart du total.
tcp_allowed_congestion_control (Chaîne ; par défaut : voir texte ; depuis Linux 2.4.20)
Affiche/définit les choix d'algorithmes de contrôle de congestion disponibles pour les processus non privilégiés (voir la description de l'option de socket TCP_CONGESTION). Les éléments de la liste sont séparés par des espaces blancs et terminés par un caractère de nouvelle ligne. La liste est un sous-ensemble de ceux listés dans tcp_available_congestion_control. La valeur par défaut de cette liste est « reno » plus le réglage par défaut de tcp_congestion_control.
tcp_autocorking (Booléen ; par défaut : activé ; depuis Linux 3.14)

tcp_available_congestion_control (Chaîne de caractères ; lecture seule ; depuis Linux 2.4.20)
Affiche une liste des algorithmes de contrôle de congestion qui sont enregistrés. Les éléments de la liste sont séparés par des espaces et terminés par un caractère de nouvelle ligne. Cette liste est un ensemble limitant pour la liste dans tcp_allowed_congestion_control. D'autres algorithmes de contrôle de congestion peuvent être disponibles en tant que modules, mais ne sont pas chargés.
tcp_app_win (entier ; par défaut : 31 ; depuis Linux 2.4)
Cette variable définit combien d'octets de la fenêtre TCP sont réservés pour les frais généraux de mise en mémoire tampon.
Un maximum de (window/2^tcp_app_win, mss) octets dans la fenêtre sont réservés pour le tampon de l'application. Une valeur de 0 implique qu'aucune quantité n'est réservée.
tcp_base_mss (Entier ; par défaut : 512 ; depuis Linux 2.6.17)
La valeur initiale de search_low à utiliser par la découverte de la MTU du chemin (MTU probing) de la couche de paquetisation. Si la découverte de MTU est activée, c'est le MSS initial utilisé par la connexion.
tcp_bic (Booléen ; par défaut : désactivé ; Linux 2.4.27/2.6.6 à Linux 2.6.13)
Active l'algorithme de contrôle de congestion TCP BIC. BIC-TCP est une modification côté émetteur uniquement qui garantit une équité RTT linéaire sous de grandes fenêtres tout en offrant à la fois scalabilité et convivialité TCP bornée. Le protocole combine deux schémas appelés augmentation additive et augmentation par recherche binaire. Lorsque la fenêtre de congestion est grande, l'augmentation additive avec une grande incrémentation garantit une équité RTT linéaire ainsi qu'une bonne scalabilité. Sous de petites fenêtres de congestion, l'augmentation par recherche binaire fournit une convivialité TCP.
tcp_bic_low_window (entier ; par défaut : 14 ; Linux 2.4.27/2.6.6 à Linux 2.6.13)
Définit la fenêtre seuil (en paquets) à partir de laquelle TCP BIC commence à ajuster la fenêtre de congestion. En dessous de ce seuil, TCP BIC se comporte de la même manière que le TCP Reno par défaut.
tcp_bic_fast_convergence (Booléen ; par défaut : activé ; Linux 2.4.27/2.6.6 à Linux 2.6.13)
Force TCP BIC à répondre plus rapidement aux changements de la fenêtre de congestion. Permet à deux flux partageant la même connexion de converger plus rapidement.
tcp_congestion_control (Chaîne de caractères ; par défaut : voir texte ; depuis Linux 2.4.13)
Définit l'algorithme de contrôle de congestion par défaut à utiliser pour les nouvelles connexions. L'algorithme "reno" est toujours disponible, mais des choix supplémentaires peuvent être disponibles en fonction de la configuration du noyau. La valeur par défaut pour ce fichier est définie dans le cadre de la configuration du noyau.
tcp_dma_copybreak (entier ; par défaut : 4096 ; depuis Linux 2.6.24)
Limite inférieure, en octets, de la taille des lectures de socket qui seront déchargées sur un moteur de copie DMA, si un tel moteur est présent dans le système et que le noyau a été configuré avec l'option CONFIG_NET_DMA.
tcp_dsack (Booléen ; par défaut : activé ; depuis Linux 2.4)
Active le support TCP Duplicate SACK selon la RFC 2883.
tcp_fastopen (Masque de bits ; par défaut : 0x1 ; depuis Linux 3.7)
Active le support Fast Open selon la RFC 7413. Le drapeau est utilisé comme une table de correspondance (bitmap) avec les valeurs suivantes :
0x1
Active le support Fast Open côté client
0x2
Active le support Fast Open côté serveur
0x4
Permet au côté client de transmettre des données dans le SYN sans l'option Fast Open
0x200
Permet au côté serveur d'accepter des données SYN sans l'option Fast Open
0x400
Active Fast Open sur tous les écouteurs sans l'option de socket TCP_FASTOPEN
tcp_fastopen_key (depuis Linux 3.7)
Définit la clé Fast Open RFC 7413 du côté serveur pour générer le cookie Fast Open lorsque le support Fast Open côté serveur est activé.
tcp_ecn (Entier ; par défaut : voir ci-dessous ; depuis Linux 2.4)
Active la Notification Explicite de Congestion (ECN) RFC 3168.
Ce fichier peut avoir l'une des valeurs suivantes :
0
Désactive ECN. N'initie ni n'accepte ECN. C'était la valeur par défaut jusqu'à et y compris Linux 2.6.30.
1
Active ECN lorsque demandé par les connexions entrantes et demande également ECN lors des tentatives de connexion sortantes.
2
Active ECN lorsque demandé par les connexions entrantes, mais ne demande pas ECN lors des connexions sortantes. Cette valeur est supportée, et est la valeur par défaut, depuis Linux 2.6.31.
Lorsqu'il est activé, la connectivité avec certaines destinations pourrait être affectée en raison d'intermédiaires plus anciens et mal comportés sur le chemin, provoquant la chute des connexions. Cependant, pour faciliter et encourager le déploiement avec l'option 1, et pour contourner de tels équipements défectueux, l'option tcp_ecn_fallback a été introduite.
tcp_ecn_fallback (Booléen ; par défaut : activé ; depuis Linux 4.1)
Active le fallback RFC 3168, Section 6.1.1.1. Lorsqu'il est activé, les SYNs ECN-setup sortants qui expirent dans le délai de retransmission SYN normal seront renvoyés avec CWR et ECE effacés.
tcp_fack (Booléen ; par défaut : activé ; depuis Linux 2.2)
Active le support TCP Forward Acknowledgement.
tcp_fin_timeout (entier ; par défaut : 60 ; depuis Linux 2.2)
Ceci spécifie combien de secondes attendre un paquet FIN final avant que le socket ne soit fermé de force. Ceci est une violation stricte de la spécification TCP, mais est nécessaire pour prévenir les attaques par déni de service. Dans Linux 2.2, la valeur par défaut était 180.
tcp_frto (entier ; par défaut : voir ci-dessous ; depuis Linux 2.4.21/2.6)
Active F-RTO, un algorithme de récupération amélioré pour les temporisations de retransmission TCP (RTO). Il est particulièrement bénéfique dans les environnements sans fil où la perte de paquets est généralement due à des interférences radio aléatoires plutôt qu'à une congestion du routeur intermédiaire. Voir la RFC 4138 pour plus de détails.
Ce fichier peut avoir l'une des valeurs suivantes :
0
Désactivé. C'était la valeur par défaut jusqu'à et y compris Linux 2.6.23.
1
La version de base de l'algorithme F-RTO est activée.
2
Active F-RTO amélioré par SACK si le flux utilise SACK. La version de base peut également être utilisée lorsque SACK est utilisé, bien que dans ce cas, des scénarios existent où F-RTO interagit mal avec le comptage de paquets du flux TCP activé pour SACK. Cette valeur est la valeur par défaut depuis Linux 2.6.24.
Avant Linux 2.6.22, ce paramètre était une valeur booléenne, supportant uniquement les valeurs 0 et 1 ci-dessus.
tcp_frto_response (entier ; par défaut : 0 ; depuis Linux 2.6.22)
Lorsque F-RTO a détecté qu'une temporisation de retransmission TCP était erronée (c'est-à-dire que la temporisation aurait été évitée si TCP avait défini une temporisation de retransmission plus longue), TCP a plusieurs options concernant la suite. Les valeurs possibles sont :
0
Basé sur la division par deux du débit ; une réponse douce et conservatrice, résulte en une fenêtre de congestion (cwnd) et un seuil de démarrage lent (ssthresh) divisés par deux après un RTT.
1
Réponse très conservatrice ; non recommandée car, bien que valide, elle interagit mal avec le reste du TCP Linux ; divise immédiatement cwnd et ssthresh par deux.
2
Réponse agressive ; annule les mesures de contrôle de congestion qui sont maintenant connues pour être inutiles (ignorant la possibilité d'une retransmission perdue qui nécessiterait que TCP soit plus prudent) ; cwnd et ssthresh sont restaurés aux valeurs d'avant la temporisation.
tcp_keepalive_intvl (entier ; par défaut : 75 ; depuis Linux 2.4)
Le nombre de secondes entre les sondes TCP keep-alive.
tcp_keepalive_probes (entier ; par défaut : 9 ; depuis Linux 2.2)
Le nombre maximal de sondes TCP keep-alive à envoyer avant d'abandonner et de tuer la connexion si aucune réponse n'est obtenue de l'autre extrémité.
tcp_keepalive_time (entier ; par défaut : 7200 ; depuis Linux 2.2)
Le nombre de secondes pendant lesquelles une connexion doit être inactive avant que TCP ne commence à envoyer des sondes keep-alive. Les sondes keep-alive ne sont envoyées que lorsque l'option de socket SO_KEEPALIVE est activée. La valeur par défaut est de 7200 secondes (2 heures). Une connexion inactive est terminée après environ 11 minutes supplémentaires (9 sondes espacées de 75 secondes) lorsque keep-alive est activé.
Notez que les mécanismes de suivi de connexion sous-jacents et les temporisations d'application peuvent être beaucoup plus courts.
tcp_low_latency (Booléen ; par défaut : désactivé ; depuis Linux 2.4.21/2.6 ; obsolète depuis Linux 4.14)
Si activée, la pile TCP prend des décisions qui privilégient une latence plus faible par opposition à un débit plus élevé. Si cette option est désactivée, un débit plus élevé est privilégié. Un exemple d'application pour lequel ce défaut devrait être modifié serait un cluster de calcul Beowulf. Depuis Linux 4.14, ce fichier existe toujours, mais sa valeur est ignorée.
tcp_max_orphans (entier ; par défaut : voir ci-dessous ; depuis Linux 2.4)
Nombre maximal de sockets TCP orphelins (non attachés à un descripteur de fichier utilisateur) autorisés dans le système. Lorsque ce nombre est dépassé, la connexion orpheline est réinitialisée et un avertissement est imprimé. Cette limite n'existe que pour prévenir des attaques simples par déni de service. Il n'est pas recommandé de baisser cette limite. Les conditions réseau pourraient nécessiter d'augmenter le nombre d'orphelins autorisés, mais notez que chaque orphelin peut consommer jusqu'à environ 64 Ko de mémoire non paginable. La valeur initiale par défaut est égale au paramètre du noyau NR_FILE. Cette valeur par défaut initiale est ajustée en fonction de la mémoire du système.
tcp_max_syn_backlog (entier ; par défaut : voir ci-dessous ; depuis Linux 2.2)
Nombre maximal de requêtes de connexion mises en file d'attente qui n'ont pas encore reçu d'accusé de réception du client appelant. Si ce nombre est dépassé, le noyau commence à rejeter les requêtes. La valeur par défaut de 256 est augmentée à 1024 lorsque la mémoire présente dans le système est adéquate ou supérieure (>= 128 Mo), et réduite à 128 pour les systèmes avec très peu de mémoire (<= 32 Mo).
Avant Linux 2.6.20, il était recommandé que si cette valeur devait être augmentée au-delà de 1024, la taille de la table de hachage SYNACK (TCP_SYNQ_HSIZE) dans include/net/tcp.h soit modifiée pour que

TCP_SYNQ_HSIZE * 16 <= tcp_max_syn_backlog

et le noyau soit recompilé. Dans Linux 2.6.20, le TCP_SYNQ_HSIZE de taille fixe a été supprimé au profit d'un dimensionnement dynamique.
tcp_max_tw_buckets (entier ; par défaut : voir ci-dessous ; depuis Linux 2.4)
Nombre maximal de sockets en état TIME_WAIT autorisés dans le système. Cette limite n'existe que pour prévenir des attaques simples par déni de service. La valeur par défaut de NR_FILE*2 est ajustée en fonction de la mémoire du système. Si ce nombre est dépassé, le socket est fermé et un avertissement est imprimé.
tcp_moderate_rcvbuf (Booléen ; par défaut : activé ; depuis Linux 2.4.17/2.6.7)
Si activé, TCP effectue une optimisation automatique de la taille du tampon de réception, en essayant de dimensionner automatiquement le tampon (pas plus grand que tcp_rmem[2]) pour correspondre à la taille requise par le chemin pour un débit complet.
tcp_mem (depuis Linux 2.4)
Il s'agit d'un vecteur de 3 entiers : [bas, pression, haut]. Ces seuils, mesurés en unités de taille de page système, sont utilisés par TCP pour suivre son utilisation de mémoire. Les valeurs par défaut sont calculées au démarrage à partir de la quantité de mémoire disponible. (TCP ne peut utiliser que mémoire basse pour cela, ce qui est limité à environ 900 mégaoctets sur les systèmes 32 bits. Les systèmes 64 bits ne souffrent pas de cette limitation.)
bas
TCP ne régule pas son allocation de mémoire lorsque le nombre de pages qu'il a allouées globalement est inférieur à ce nombre.
pression
Lorsque la quantité de mémoire allouée par TCP dépasse ce nombre de pages, TCP modère sa consommation de mémoire. Cet état de pression mémoire est quitté une fois que le nombre de pages allouées descend en dessous du seuil bas.
haut
Nombre maximal de pages, globalement, que TCP allouera. Cette valeur remplace toutes les autres limites imposées par le noyau.
tcp_mtu_probing (entier ; par défaut : 0 ; depuis Linux 2.6.17)
Ce paramètre contrôle la découverte de la MTU (Maximum Transmission Unit) du chemin de la couche de paquetisation TCP. Les valeurs suivantes peuvent être attribuées au fichier :
0
Désactivé
1
Désactivé par défaut, activé lorsqu'un trou noir ICMP est détecté
2
Toujours activé, utilise le MSS initial de tcp_base_mss.
tcp_no_metrics_save (Booléen ; par défaut : désactivé ; depuis Linux 2.6.6)
Par défaut, TCP enregistre diverses métriques de connexion dans le cache de routage lorsque la connexion se ferme, afin que les connexions établies dans un avenir proche puissent les utiliser pour définir les conditions initiales. Généralement, cela augmente les performances globales, mais peut parfois entraîner une dégradation des performances. Si tcp_no_metrics_save est activé, TCP ne mettra pas en cache les métriques lors de la fermeture des connexions.
tcp_orphan_retries (entier ; par défaut : 8 ; depuis Linux 2.4)
Nombre maximal de tentatives effectuées pour sonder l'autre extrémité d'une connexion qui a été fermée par notre côté.
tcp_reordering (entier ; par défaut : 3 ; depuis Linux 2.4)
Quantité maximale de réordonnancement qu'un paquet peut subir dans un flux de paquets TCP avant que TCP ne suppose une perte de paquet et n'entre en phase de démarrage lent. Il n'est pas conseillé de modifier ce nombre. Il s'agit d'une métrique de détection de réordonnancement de paquets conçue pour minimiser les retards et les retransmissions inutiles provoqués par le réordonnancement des paquets sur une connexion.
tcp_retrans_collapse (Booléen ; par défaut : activé ; depuis Linux 2.2)
Essayer d'envoyer des paquets de pleine taille lors de la retransmission.
tcp_retries1 (entier ; par défaut : 3 ; depuis Linux 2.2)
Nombre de fois où TCP tentera de retransmettre un paquet sur une connexion établie normalement, sans l'effort supplémentaire d'impliquer les couches réseau. Une fois que nous dépassons ce nombre de retransmissions, nous demandons à la couche réseau de mettre à jour la route si possible avant chaque nouvelle retransmission. La valeur par défaut est le minimum spécifié par la RFC de 3.
tcp_retries2 (entier ; par défaut : 15 ; depuis Linux 2.2)
Nombre maximal de fois où un paquet TCP est retransmis en état établi avant d'abandonner. La valeur par défaut est 15, ce qui correspond à une durée d'environ 13 à 30 minutes, selon le délai de retransmission. Le minimum de 100 secondes spécifié par la RFC 1122 est généralement considéré comme trop court.
tcp_rfc1337 (Booléen ; par défaut : désactivé ; depuis Linux 2.2)
Activer le comportement TCP conforme à la RFC 1337. Lorsque désactivé, si un paquet RST est reçu en état TIME_WAIT, nous fermons le socket immédiatement sans attendre la fin de la période TIME_WAIT.
tcp_rmem (depuis Linux 2.4)
Il s'agit d'un vecteur de 3 entiers : [min, default, max]. Ces paramètres sont utilisés par TCP pour réguler la taille des tampons de réception. TCP ajuste dynamiquement la taille du tampon de réception par rapport aux valeurs par défaut listées ci-dessous, dans la plage de ces valeurs, en fonction de la mémoire disponible dans le système.
min
taille minimale du tampon de réception utilisé par chaque socket TCP. La valeur par défaut est la taille de page du système. (Sous Linux 2.4, la valeur par défaut est 4 Ko, réduite à PAGE_SIZE octets sur les systèmes à faible mémoire.) Elle est utilisée pour garantir que, en cas de pression mémoire, les allocations inférieures à cette taille réussissent toujours. Elle n'est pas utilisée pour limiter la taille du tampon de réception déclaré via SO_RCVBUF sur un socket.
default
taille par défaut du tampon de réception pour un socket TCP. Cette valeur remplace la taille initiale par défaut du tampon de net.core.rmem_default global défini pour tous les protocoles. La valeur par défaut est 87380 octets. (Sous Linux 2.4, cette valeur sera réduite à 43689 sur les systèmes à faible mémoire.) Si des tailles de tampon de réception plus grandes sont souhaitées, cette valeur doit être augmentée (pour affecter tous les sockets). Pour utiliser de grandes fenêtres TCP, net.ipv4.tcp_window_scaling doit être activé (par défaut).
max
taille maximale du tampon de réception utilisé par chaque socket TCP. Cette valeur ne remplace pas le net.core.rmem_max global. Elle n'est pas utilisée pour limiter la taille du tampon de réception déclaré via SO_RCVBUF sur un socket. La valeur par défaut est calculée selon la formule

max(87380, min(4 Mo, tcp_mem[1]*PAGE_SIZE/128))

(Sous Linux 2.4, la valeur par défaut est 87380*2 octets, réduite à 87380 sur les systèmes à faible mémoire).
tcp_sack (Booléen ; par défaut : activé ; depuis Linux 2.2)

tcp_syncookies (entier ; par défaut : 1 ; depuis Linux 2.2)
Activer les syncookies TCP. Le noyau doit être compilé avec CONFIG_SYN_COOKIES. La fonctionnalité syncookies tente de protéger une socket d'une attaque par déni de service SYN flood. Ceci ne devrait être utilisé qu'en dernier recours, voire pas du tout. Ceci constitue une violation du protocole TCP et entre en conflit avec d'autres aspects de TCP tels que les extensions TCP. 1
Envoyer des syncookies lorsque la file d'attente de backlog SYN d'une socket déborde.
2

Définir sur l'une des valeurs suivantes pour activer ou désactiver les horodatages TCP RFC 1323 :
0
Désactiver les horodatages.
1
Activer les horodatages tels que définis dans la RFC1323 et utiliser un décalage aléatoire pour chaque connexion plutôt que d'utiliser uniquement l'heure actuelle.

tcp_tso_win_divisor (entier ; par défaut : 3 ; depuis Linux 2.6.9)
Ce paramètre contrôle quel pourcentage de la fenêtre de congestion peut être consommé par une seule trame TCP Segmentation Offload (TSO). La définition de ce paramètre est un compromis entre l'éclatement et la création de trames TSO plus grandes.
tcp_tw_recycle (booléen ; par défaut : désactivé ; Linux 2.4 à Linux 4.11)
Activer le recyclage rapide des sockets TIME_WAIT. L'activation de cette option n'est pas recommandée car l'IP distante peut ne pas utiliser des horodatages monotones croissants (appareils derrière NAT, appareils avec des décalages d'horodatage par connexion). Voir RFC 1323 (PAWS) et RFC 6191.
tcp_tw_reuse (booléen ; par défaut : désactivé ; depuis Linux 2.4.19/2.6)
Permettre la réutilisation des sockets TIME_WAIT pour de nouvelles connexions lorsque cela est sûr du point de vue du protocole. Elle ne doit pas être modifiée sans l'avis/la demande d'experts techniques.
tcp_vegas_cong_avoid (booléen ; par défaut : désactivé ; Linux 2.2 à Linux 2.6.13)
Activer l'algorithme d'évitement de congestion TCP Vegas. TCP Vegas est une modification côté émetteur uniquement du protocole TCP qui anticipe l'apparition de congestion en estimant la bande passante. TCP Vegas ajuste le débit d'envoi en modifiant la fenêtre de congestion. TCP Vegas devrait entraîner moins de pertes de paquets, mais il n'est pas aussi agressif que TCP Reno.
tcp_westwood (booléen ; par défaut : désactivé ; Linux 2.4.26/2.6.3 à Linux 2.6.13)
Activer l'algorithme de contrôle de congestion TCP Westwood+. TCP Westwood+ est une modification côté émetteur uniquement de la pile de protocoles TCP Reno qui optimise les performances du contrôle de congestion TCP. Il est basé sur l'estimation de la bande passante de bout en bout pour définir la fenêtre de congestion et le seuil de démarrage lent après un épisode de congestion. En utilisant cette estimation, TCP Westwood+ définit de manière adaptative un seuil de démarrage lent et une fenêtre de congestion qui prennent en compte la bande passante utilisée au moment où la congestion est rencontrée. TCP Westwood+ augmente significativement l'équité par rapport à TCP Reno dans les réseaux câblés et le débit sur les liaisons sans fil.
tcp_window_scaling (booléen ; par défaut : activé ; depuis Linux 2.2)
Activer la mise à l'échelle de fenêtre TCP RFC 1323. Cette fonctionnalité permet l'utilisation d'une grande fenêtre (> 64 Ko) sur une connexion TCP, si l'autre extrémité la prend en charge. Normalement, le champ de longueur de fenêtre de 16 bits dans l'en-tête TCP limite la taille de la fenêtre à moins de 64 Ko. Si des fenêtres plus grandes sont souhaitées, les applications peuvent augmenter la taille de leurs tampons de socket et l'option de mise à l'échelle de fenêtre sera employée. Si tcp_window_scaling est désactivé, TCP ne négociera pas l'utilisation de la mise à l'échelle de fenêtre avec l'autre extrémité pendant l'établissement de la connexion.
tcp_wmem (depuis Linux 2.4)
Ceci est un vecteur de 3 entiers : [min, default, max]. Ces paramètres sont utilisés par TCP pour réguler la taille des tampons d'envoi. TCP ajuste dynamiquement la taille du tampon d'envoi à partir des valeurs par défaut listées ci-dessous, dans la plage de ces valeurs, en fonction de la mémoire disponible.
min
Taille minimale du tampon d'envoi utilisé par chaque socket TCP. La valeur par défaut est la taille de page du système. (Sous Linux 2.4, la valeur par défaut est 4 Ko.) Cette valeur est utilisée pour garantir que, en mode de pression mémoire, les allocations inférieures à cette taille réussissent toujours. Elle n'est pas utilisée pour limiter la taille du tampon d'envoi déclaré à l'aide de SO_SNDBUF sur une socket.
default
La taille par défaut du tampon d'envoi pour une socket TCP. Cette valeur remplace la taille de tampon par défaut initiale du global générique /proc/sys/net/core/wmem_default défini pour tous les protocoles. La valeur par défaut est 16 Ko. Si des tailles de tampon d'envoi plus grandes sont souhaitées, cette valeur doit être augmentée (pour affecter toutes les sockets). Pour utiliser de grandes fenêtres TCP, /proc/sys/net/ipv4/tcp_window_scaling doit être défini sur une valeur non nulle (par défaut).
max
La taille maximale du tampon d'envoi utilisé par chaque socket TCP. Cette valeur ne remplace pas la valeur dans /proc/sys/net/core/wmem_max. Elle n'est pas utilisée pour limiter la taille du tampon d'envoi déclaré à l'aide de SO_SNDBUF sur une socket. La valeur par défaut est calculée à l'aide de la formule

max(65536, min(4 Mo, tcp_mem[1]*PAGE_SIZE/128))

(Sous Linux 2.4, la valeur par défaut est 128 Ko, abaissée à 64 Ko selon les systèmes à faible mémoire.)
tcp_workaround_signed_windows (booléen ; par défaut : désactivé ; depuis Linux 2.6.26)
Si activé, supposer qu'aucune réception d'une option de mise à l'échelle de fenêtre ne signifie que le TCP distant est défectueux et traite la fenêtre comme une quantité signée. Si désactivé, supposer que le TCP distant n'est pas défectueux même si nous ne recevons pas d'option de mise à l'échelle de fenêtre de sa part.

Options de socket

Pour définir ou obtenir une option de socket TCP, appelez getsockopt(2) pour lire ou setsockopt(2) pour écrire l'option avec l'argument de niveau d'option défini sur IPPROTO_TCP. Sauf indication contraire, optval est un pointeur vers un int. De plus, la plupart des options de socket IPPROTO_IP sont valides sur les sockets TCP. Pour plus d'informations, voir ip(7).

Voici une liste des options de socket spécifiques à TCP. Pour les détails de certaines autres options de socket qui s'appliquent également aux sockets TCP, voir socket(7).

TCP_CONGESTION (depuis Linux 2.6.13)
L'argument de cette option est une chaîne. Cette option permet à l'appelant de définir l'algorithme de contrôle de congestion TCP à utiliser, sur une base par socket. Les processus non privilégiés sont limités au choix de l'un des algorithmes dans tcp_allowed_congestion_control (décrit ci-dessus). Les processus privilégiés (CAP_NET_ADMIN) peuvent choisir parmi n'importe lequel des algorithmes de contrôle de congestion disponibles (voir la description de tcp_available_congestion_control ci-dessus).
TCP_CORK (depuis Linux 2.2)
Si défini, n'envoyez pas de trames partielles. Toutes les trames partielles mises en file d'attente sont envoyées lorsque l'option est à nouveau effacée. Ceci est utile pour préfixer des en-têtes avant d'appeler sendfile(2), ou pour l'optimisation du débit. Telle qu'implémentée actuellement, il y a un plafond de 200 millisecondes sur le temps pendant lequel la sortie est "bouchée" par TCP_CORK. Si ce plafond est atteint, les données mises en file d'attente sont transmises automatiquement. Cette option peut être combinée avec TCP_NODELAY uniquement depuis Linux 2.5.71. Cette option ne doit pas être utilisée dans du code destiné à être portable.
TCP_DEFER_ACCEPT (depuis Linux 2.4)
Permettre à un écouteur de ne pas être réveillé tant que des données n'arrivent pas sur la socket. Prend une valeur entière (secondes), cela peut limiter le nombre maximum de tentatives que TCP fera pour finaliser la connexion. Cette option ne doit pas être utilisée dans du code destiné à être portable.
TCP_INFO (depuis Linux 2.4)
Utilisé pour collecter des informations sur cette socket. Le noyau renvoie une struct tcp_info telle que définie dans le fichier /usr/include/linux/tcp.h. Cette option ne doit pas être utilisée dans du code destiné à être portable.
TCP_KEEPCNT (depuis Linux 2.4)
Le nombre maximum de sondes keepalive que TCP doit envoyer avant de supprimer la connexion. Cette option ne doit pas être utilisée dans du code destiné à être portable.
TCP_KEEPIDLE (depuis Linux 2.4)
Le temps (en secondes) pendant lequel la connexion doit rester inactive avant que TCP ne commence à envoyer des sondes keepalive, si l'option de socket SO_KEEPALIVE a été définie sur cette socket. Cette option ne doit pas être utilisée dans du code destiné à être portable.
TCP_KEEPINTVL (depuis Linux 2.4)
Le temps (en secondes) entre les sondes keepalive individuelles. Cette option ne doit pas être utilisée dans du code destiné à être portable.

Options

TCP_DEFER_ACCEPT (depuis Linux 2.4)
La durée de vie des sockets orphelines en état FIN_WAIT2. Cette option peut être utilisée pour remplacer le réglage système global dans le fichier /proc/sys/net/ipv4/tcp_fin_timeout pour ce socket. Ne pas confondre avec l'option de niveau socket(7) SO_LINGER. Cette option ne doit pas être utilisée dans du code destiné à être portable.
TCP_MAXSEG
La taille maximale de segment pour les paquets TCP sortants. Sous Linux 2.2 et antérieur, et sous Linux 2.6.28 et ultérieur, si cette option est définie avant l'établissement de la connexion, elle modifie également la valeur MSS annoncée à l'autre extrémité dans le paquet initial. Les valeurs supérieures à l'avenir MTU de l'interface n'ont aucun effet. TCP imposera également ses limites minimale et maximale sur la valeur fournie.
TCP_NODELAY
Si défini, désactive l'algorithme de Nagle. Cela signifie que les segments sont toujours envoyés dès que possible, même s'il n'y a qu'une petite quantité de données. Lorsqu'il n'est pas défini, les données sont mises en tampon jusqu'à ce qu'il y en ait une quantité suffisante à envoyer, évitant ainsi l'envoi fréquent de petits paquets, ce qui entraîne une mauvaise utilisation du réseau. Cette option est remplacée par TCP_CORK ; cependant, la définition de cette option force une purge explicite de la sortie en attente, même si TCP_CORK est actuellement défini.
TCP_QUICKACK (depuis Linux 2.4.4)
Active le mode quickack si défini ou désactive le mode quickack si effacé. En mode quickack, les accusés de réception sont envoyés immédiatement, plutôt que retardés si nécessaire conformément au fonctionnement normal de TCP. Ce drapeau n'est pas permanent, il active uniquement un passage vers ou depuis le mode quickack. Le fonctionnement ultérieur du protocole TCP entrera/sortira à nouveau du mode quickack en fonction du traitement interne du protocole et de facteurs tels que les délais d'attente des accusés de réception retardés et le transfert de données. Cette option ne doit pas être utilisée dans du code destiné à être portable.
TCP_SYNCNT (depuis Linux 2.4)
Définit le nombre de retransmissions SYN que TCP doit envoyer avant d'avorter la tentative de connexion. Il ne peut pas dépasser 255. Cette option ne doit pas être utilisée dans du code destiné à être portable.
TCP_SAVE_SYN (depuis Linux 4.3)
Sauvegarde le contenu des paquets SYN entrants du socket d'écoute jusqu'à ce qu'il soit lu avec TCP_SAVED_SYN une seule fois. Peut être défini avant ou après l'appel listen(2).
TCP_SAVED_SYN (depuis Linux 4.3)
Lit le contenu des paquets SYN sauvegardé par TCP_SAVE_SYN. Les en-têtes SYN sauvegardés sont libérés après le premier appel. Les données retournées dans TCP_SAVED_SYN sont des en-têtes réseau (IPv4/IPv6) et TCP.
TCP_USER_TIMEOUT (depuis Linux 2.6.37)
Cette option prend un entier non signé unsigned int comme argument. Lorsque la valeur est supérieure à 0, elle spécifie la durée maximale en millisecondes pendant laquelle les données transmises peuvent rester non acquittées, ou les données mises en tampon peuvent rester non transmises (en raison d'une fenêtre de taille nulle) avant que TCP ne ferme de force la connexion correspondante et ne retourne ETIMEDOUT à l'application. Si la valeur de l'option est spécifiée comme 0, TCP utilisera la valeur par défaut du système.
Augmenter les délais d'attente utilisateur permet à une connexion TCP de survivre à des périodes prolongées sans connectivité de bout en bout. Diminuer les délais d'attente utilisateur permet aux applications de "échouer rapidement", si elles le souhaitent. Sinon, l'échec peut prendre jusqu'à 20 minutes avec les valeurs par défaut actuelles du système dans un environnement WAN normal.
Cette option peut être définie à n'importe quel état d'une connexion TCP, mais elle n'est effective que pendant les états synchronisés d'une connexion (ESTABLISHED, FIN-WAIT-1, FIN-WAIT-2, CLOSE-WAIT, CLOSING, et LAST-ACK). De plus, lorsqu'elle est utilisée avec l'option TCP keepalive (SO_KEEPALIVE), TCP_USER_TIMEOUT remplacera keepalive pour déterminer quand fermer une connexion en raison d'un échec keepalive.
L'option n'a aucun effet sur le moment où TCP retransmet un paquet, ni sur le moment où une sonde keepalive est envoyée.
Cette option, comme beaucoup d'autres, sera héritée par le socket retourné par accept(2), si elle a été définie sur le socket d'écoute.
Plus de détails sur la fonctionnalité de délai d'attente utilisateur peuvent être trouvés dans les RFC 793 et RFC 5482 ("TCP User Timeout Option").
TCP_WINDOW_CLAMP (depuis Linux 2.4)
Limite la taille de la fenêtre annoncée à cette valeur. Le noyau impose une taille minimale de SOCK_MIN_RCVBUF/2. Cette option ne doit pas être utilisée dans du code destiné à être portable.
TCP_FASTOPEN (depuis Linux 3.6)
Cette option active Fast Open (RFC 7413) sur le socket d'écoute. La valeur spécifie la longueur maximale des SYN en attente (similaire à l'argument de backlog dans listen(2)). Une fois activé, le socket d'écoute attribue le cookie TCP Fast Open lors d'un SYN entrant avec l'option TCP Fast Open.
Plus important encore, il accepte les données dans le SYN avec un cookie Fast Open valide et répond SYN-ACK accusant réception des données et de la séquence SYN. accept(2) renvoie un socket disponible pour la lecture et l'écriture quand la négociation n'est pas encore terminée. Ainsi, l'échange de données peut commencer avant que la négociation ne soit terminée. Cette option nécessite l'activation du support côté serveur sur sysctl net.ipv4.tcp_fastopen (voir ci-dessus). Pour le support côté client TCP Fast Open, voir send(2) MSG_FASTOPEN ou TCP_FASTOPEN_CONNECT ci-dessous.
TCP_FASTOPEN_CONNECT (depuis Linux 4.11)
Cette option active une manière alternative d'effectuer Fast Open côté actif (client). Lorsque cette option est activée, connect(2) se comportera différemment selon qu'un cookie Fast Open est disponible pour la destination.
Si aucun cookie n'est disponible (c'est-à-dire, premier contact avec la destination), connect(2) se comporte comme d'habitude en envoyant immédiatement un SYN, sauf que le SYN inclurait une option de cookie Fast Open vide pour solliciter un cookie.
Si un cookie est disponible, connect(2) retournera 0 immédiatement mais l'envoi du SYN sera différé. Un appel ultérieur à write(2) ou sendmsg(2) déclenchera un SYN avec des données plus le cookie dans l'option Fast Open. En d'autres termes, l'opération de connexion réelle sera différée jusqu'à ce que des données soient fournies.
Note : Bien que cette option soit conçue pour la commodité, l'activer modifie les comportements et certains appels système peuvent définir des valeurs errno différentes. Avec un cookie présent, write(2) ou sendmsg(2) doit être appelé juste après connect(2) afin d'envoyer le SYN+données pour compléter le 3WHS et établir la connexion. Appeler read(2) juste après connect(2) sans write(2) provoquera un blocage permanent du socket.
L'application doit soit définir l'option de socket TCP_FASTOPEN_CONNECT avant write(2) ou sendmsg(2), soit appeler write(2) ou sendmsg(2) directement avec le drapeau MSG_FASTOPEN, mais pas les deux sur la même connexion.
Voici le flux d'appel typique avec cette nouvelle option :

s = socket();
setsockopt(s, IPPROTO_TCP, TCP_FASTOPEN_CONNECT, 1, ...);
connect(s);
write(s);  /* write() doit toujours suivre connect()
            * pour déclencher l'envoi du SYN.  */
read(s)/write(s);
/* ... */
close(s);

API Sockets

TCP offre un support limité pour les données hors bande, sous la forme d'une donnée urgente (un seul octet). Sous Linux, cela signifie que si l'autre extrémité envoie des données hors bande plus récentes, les anciennes données urgentes sont insérées comme des données normales dans le flux (même lorsque SO_OOBINLINE n'est pas défini). Ceci diffère des piles basées sur BSD.

Linux utilise l'interprétation compatible BSD du champ pointeur urgent par défaut. Cela viole la RFC 1122, mais est nécessaire pour l'interopérabilité avec d'autres piles. Cela peut être modifié via /proc/sys/net/ipv4/tcp_stdurg.

Il est possible de lire les données hors bande en utilisant le drapeau MSG_PEEK de recv(2).

Depuis Linux 2.4, Linux supporte l'utilisation de MSG_TRUNC dans l'argument flags de recv(2) (et recvmsg(2)). Ce drapeau provoque la suppression des octets de données reçus, plutôt que leur passage à un tampon fourni par l'appelant. Depuis Linux 2.4.4, MSG_TRUNC a également cet effet lorsqu'il est utilisé conjointement avec MSG_OOB pour recevoir des données hors bande.

Ioctls

Les appels ioctl(2) suivants retournent des informations dans value. La syntaxe correcte est :

int value;
error = ioctl(tcp_socket, ioctl_type, &value);

ioctl_type est l'un des suivants :

SIOCINQ
Retourne la quantité de données mises en file d'attente non lues dans le tampon de réception. Le socket ne doit pas être en état LISTEN, sinon une erreur (EINVAL) est retournée. SIOCINQ est défini dans <linux/sockios.h>. Alternativement, vous pouvez utiliser le synonyme FIONREAD, défini dans <sys/ioctl.h>.
SIOCATMARK
Retourne vrai (c'est-à-dire, value est différent de zéro) si le flux de données entrant se trouve à la marque urgente.
Si l'option de socket SO_OOBINLINE est définie et que SIOCATMARK retourne vrai, alors la prochaine lecture du socket retournera les données urgentes. Si l'option de socket SO_OOBINLINE n'est pas définie et que SIOCATMARK retourne vrai, alors la prochaine lecture du socket retournera les octets suivant la marque urgente.
tcp.7 - The TCP protocol

NAME

tcp

The TCP protocol

SYNOPSIS

Include <sys/socket.h>.
A socket may be created with:
int s = socket(AF_INET, SOCK_STREAM, 0);

DESCRIPTION

TCP (Transmission Control Protocol) is a transport layer protocol that provides reliable, ordered, and error-checked delivery of a stream of bytes between applications running on hosts communicating via an Internet Protocol network.

TCP is connection-oriented. A connection must be established between the sender and receiver before any data can be transmitted. This connection setup is performed by the three-way handshake.

TCP uses sequence numbers and acknowledgments to ensure reliable delivery. Each byte of data is sequenced, and the receiver sends acknowledgments to confirm receipt. If the sender does not receive an acknowledgment within a certain time, it retransmits the data.

TCP provides flow control using a sliding window mechanism. The receiver advertises a window size, which indicates how much data it is currently able to accept. This prevents a fast sender from overwhelming a slow receiver.

TCP also implements congestion control algorithms to prevent network collapse under heavy load. These algorithms dynamically adjust the amount of data sent into the network based on perceived network congestion.

The following socket(2) options are supported for TCP sockets:

TCP_CORK
Enable or disable the TCP_CORK option. When enabled, this option prevents the caller from sending any TCP segments on the sending socket until the option is disabled. This allows the caller to accumulate data in the transmit buffer until it has a significant chunk to send, thus reducing the number of TCP segments. This is useful for protocols that send small amounts of data, like certain RPC protocols. Only the last write operation before disabling the option will cause data to be sent. The value is 0 for disable and non-zero for enable. The behavior is undefined if the socket is in non-blocking mode and the application blocks on the first write after enabling TCP_CORK.
TCP_DEFER_ACCEPT
Enable or disable the TCP_DEFER_ACCEPT option. When enabled, this option prevents the sender from sending any data on the socket until the connection is accepted by the receiver. This is useful for servers that accept connections from many clients, but only wish to service those that actually send data. The argument is the timeout in seconds. A value of 0 disables the timeout.
TCP_KEEPCNT
The number of unanswered keep-alive probes that will be sent before the kernel considers the connection dead. The default value is TCP_KEEPCNT.
TCP_KEEPIDLE
The time in seconds the connection must be idle before the first keep-alive probe is sent. The default value is TCP_KEEPIDLE.
TCP_KEEPINTVL
The interval in seconds between successive keep-alive probes, after the first one has been sent. The default value is TCP_KEEPINTVL.
TCP_NODELAY
Enable or disable the Nagle algorithm. The Nagle algorithm tries to minimize the number of small packets sent by TCP. It buffers small outgoing data until it receives an acknowledgment from the other end or the buffer is full. Disabling this option can improve latency in some applications, at the cost of potentially higher bandwidth usage. The argument is 1 to enable TCP_NODELAY (disabling Nagle's algorithm), and 0 to disable it (enabling Nagle's algorithm).
TCP_QUICKACK
Enable or disable fast, non-delayed acknowledgments. When enabled, TCP will immediately acknowledge received data, rather than waiting for delayed acknowledgments. This can improve throughput in certain scenarios, but may increase the amount of network traffic. The argument is 1 to enable TCP_QUICKACK, and 0 to disable it.
TCP_SYNCNT
The number of times the kernel will retransmit the initial SYN packet to establish a connection. The default value is TCP_SYNCNT.
TCP_USER_TIMEOUT
Specify a user-defined timeout in milliseconds for establishing a connection. If the connection is not established within this time, the connection will be aborted. This option can be used to detect dead peers more quickly than the default TCP timeout. A value of 0 disables the timeout.

The following socket(7) options are also relevant for TCP sockets:

SO_DEBUG
Enable or disable socket debugging. This option is not typically used by application programs.
SO_DONTROUTE
Don't use routing. Normally, outgoing packets are routed. If this option is set, use only the direct interface to the destination. This option can only be set by the privileged user.
SO_RCVBUF
Set or get the receive buffer size. This is the size of the buffer used to hold incoming data before it is read by the application. Doubling this size may improve throughput on high-latency networks.
SO_RCVLOWAT
Set or get the minimum number of bytes that must be received on the socket before a read operation returns. For TCP, this option is respected only when the socket is in the stream mode (i.e. not connected to a datagram socket).
SO_RCVTIMEO
Set or get a timeout value for input operations on the socket. This option specifies the amount of time that a read operation will block waiting for input. The value is a duration specified in seconds and microseconds. A value of zero means that read operations will block indefinitely.
SO_SNDBUF
Set or get the send buffer size. This is the size of the buffer used to hold outgoing data before it is sent by the kernel. Doubling this size may improve throughput on high-latency networks.
SO_SNDLOWAT
Set or get the minimum number of bytes that must be accepted into the socket's send buffer before a write operation returns. For TCP, this option is respected only when the socket is in the stream mode (i.e. not connected to a datagram socket).
SO_SNDTIMEO
Set or get a timeout value for output operations on the socket. This option specifies the amount of time that a write operation will block waiting for the socket to become writable. The value is a duration specified in seconds and microseconds. A value of zero means that write operations will block indefinitely.
SO_TIMESTAMP
Enable or disable the generation of timestamping information for received packets. When enabled, a timestamp is appended to the control information of each received packet. This can be used for performance measurements and other time-sensitive applications.

The following socket(7) ioctls are supported for TCP sockets:

SIOCATMARK
Check if the socket is at the urgent data mark. This ioctl returns true if the current read position is at the urgent data mark. This is useful for applications that need to process urgent data separately from normal data. The urgent data mark is set when urgent data is received. The urgent data itself can be read using the recv(2) call with the MSG_OOB flag.
Note that a read never reads across the urgent mark. If an application is informed of the presence of urgent data via select(2) (using the exceptfds argument) or through delivery of a SIGURG signal, then it can advance up to the mark using a loop which repeatedly tests SIOCATMARK and performs a read (requesting any number of bytes) as long as SIOCATMARK returns false.
SIOCOUTQ
Returns the amount of unsent data in the socket send queue. The socket must not be in LISTEN state, otherwise an error (EINVAL) is returned. SIOCOUTQ is defined in <linux/sockios.h>. Alternatively, you can use the synonymous TIOCOUTQ, defined in <sys/ioctl.h>.

Error handling

When a network error occurs, TCP tries to resend the packet. If it doesn't succeed after some time, either ETIMEDOUT or the last received error on this connection is reported.

Some applications require a quicker error notification. This can be enabled with the IPPROTO_IP level IP_RECVERR socket option. When this option is enabled, all incoming errors are immediately passed to the user program. Use this option with care — it makes TCP less tolerant to routing changes and other normal network conditions.

ERRORS

EAFNOTSUPPORT
Passed socket address type in sin_family was not AF_INET.
EPIPE
The other end closed the socket unexpectedly or a read is executed on a shut down socket.
ETIMEDOUT
The other end didn't acknowledge retransmitted data after some time.

Any errors defined for ip(7) or the generic socket layer may also be returned for TCP.

VERSIONS

Support for Explicit Congestion Notification, zero-copy sendfile(2), reordering support and some SACK extensions (DSACK) were introduced in Linux 2.4. Support for forward acknowledgement (FACK), TIME_WAIT recycling, and per-connection keepalive socket options were introduced in Linux 2.3.
