DESCRIPTION

Le package tcltest fournit plusieurs commandes utilitaires utiles dans la construction de bancs d'essai pour du code instrumenté à exécuter par l'évaluation de commandes Tcl. Notamment, les commandes intégrées de la bibliothèque Tcl elle-même sont testées par un banc d'essai utilisant le package tcltest.

Toutes les commandes fournies par le package tcltest sont définies dans et exportées depuis l'espace de noms ::tcltest, comme indiqué dans la SYNOPIS ci-dessus. Dans les sections suivantes, toutes les commandes seront décrites par leurs noms simples, par souci de brièveté.

La commande centrale de tcltest est test qui définit et exécute un test. Les tests avec test impliquent l'évaluation d'un script Tcl et la comparaison du résultat avec un résultat attendu, tel que configuré et contrôlé par un certain nombre d'options. Plusieurs autres commandes fournies par tcltest régissent la configuration de test et la collection de nombreuses commandes test en bancs d'essai.

Voir CRÉATION DE BANCS D'ESSAI AVEC TCLTEST ci-dessous pour un exemple étendu sur la façon d'utiliser les commandes de tcltest pour produire des bancs d'essai pour votre code compatible Tcl.

COMMANDES

test nom description ?-option valeur ...?
Définit et éventuellement exécute un test avec le nom nom et la description description. Le nom et la description d'un test sont utilisés dans les messages rapportés par test pendant le test, tels que configurés par les options de tcltest. Les arguments option valeur restants à test définissent le test, y compris les scripts à exécuter, les conditions dans lesquelles les exécuter, le résultat attendu, et les moyens par lesquels les résultats attendus et réels doivent être comparés. Voir TESTS ci-dessous pour une description complète des options valides et comment elles définissent un test. La commande test renvoie une chaîne vide.
test nom description ?contraintes? corps résultat
Cette forme de test est fournie pour supporter les bancs d'essai écrits pour la version 1 du package tcltest, ainsi qu'une interface plus simple pour un usage courant. C'est la même chose que « test nom description -constraints contraintes -body corps -result résultat ». Toutes les autres options à test prennent leurs valeurs par défaut. Lorsque contraintes est omis, cette forme de test peut être distinguée de la première car toutes les options commencent par « - ».
loadTestedCommands
Évalue dans le contexte de l'appelant le script spécifié par configure -load ou configure -loadfile. Renvoie le résultat de cette évaluation de script, y compris toute erreur soulevée par le script. Utilisez cette commande et les options de configuration associées pour fournir les commandes à tester à l'interpréteur exécutant le banc d'essai.
makeFile contenu nom ?répertoire?
Crée un fichier nommé nom relatif au répertoire répertoire et écrit contenu dans ce fichier en utilisant l'encodage encoding system. Si contenu ne se termine pas par une nouvelle ligne, une nouvelle ligne sera ajoutée afin que le fichier nommé nom se termine par une nouvelle ligne. Parce que l'encodage système est utilisé, cette commande ne convient que pour créer des fichiers texte. Le fichier sera supprimé par la prochaine évaluation de cleanupTests, à moins qu'il ne soit supprimé par removeFile auparavant. La valeur par défaut de répertoire est le répertoire configure -tmpdir. Renvoie le chemin complet du fichier créé. Utilisez cette commande pour créer tout fichier texte requis par un test avec le contenu nécessaire.
removeFile nom ?répertoire?
Force la suppression du fichier référencé par nom. Ce nom de fichier devrait être relatif au répertoire. La valeur par défaut du répertoire est le répertoire configure -tmpdir. Renvoie une chaîne vide. Utilisez cette commande pour supprimer les fichiers créés par makeFile.
makeDirectory nom ?répertoire?
Crée un répertoire nommé nom relatif au répertoire répertoire. Le répertoire sera supprimé par la prochaine évaluation de cleanupTests, à moins qu'il ne soit supprimé par removeDirectory auparavant. La valeur par défaut de répertoire est le répertoire configure -tmpdir. Renvoie le chemin complet du répertoire créé. Utilisez cette commande pour créer tous les répertoires qui doivent exister pour un test.
removeDirectory nom ?répertoire?
Force la suppression du répertoire référencé par nom. Ce répertoire devrait être relatif au répertoire. La valeur par défaut du répertoire est le répertoire configure -tmpdir. Renvoie une chaîne vide. Utilisez cette commande pour supprimer les répertoires créés par makeDirectory.
viewFile fichier ?répertoire?
Renvoie le contenu de fichier, à l'exception de toute nouvelle ligne finale, tout comme read -nonewline le ferait. Ce nom de fichier doit être relatif au répertoire. La valeur par défaut du répertoire est le répertoire configure -tmpdir. Utilisez cette commande comme un moyen pratique de transformer le contenu d'un fichier généré par un test en le résultat de ce test pour comparaison avec un résultat attendu. Le contenu du fichier est lu en utilisant l'encodage système, donc son utilité est limitée aux fichiers texte.
cleanupTests
Destinée à nettoyer et résumer après l'exécution de plusieurs tests. Généralement appelée une fois par fichier de test, à la fin du fichier après que tous les tests aient été complétés. Pour une meilleure efficacité, assurez-vous que cleanupTests est évaluée même si une erreur se produit plus tôt dans l'évaluation du fichier de test.

Imprime les statistiques sur les tests exécutés et supprime les fichiers qui ont été créés par makeDirectory et makeFile depuis le dernier cleanupTests. Les noms des fichiers et répertoires dans le répertoire configure -tmpdir créés depuis le dernier cleanupTests, mais non créés par makeFile ou makeDirectory sont imprimés sur outputChannel. Cette commande restaure également l'environnement shell d'origine, tel que décrit par la variable globale env.

CRÉATION DE BANCS D'ESSAI AVEC TCLTEST

L'exemple typique d'un fichier de test Tcl est présenté ci-dessous. Ce code exécute et évalue un certain nombre de tests d'une manière qui peut être comprise par un utilisateur de ce package, et en particulier, celui qui écrira et exécutera ce type de banc d'essai.

Un banc d'essai est une collection de commandes test. Toutes les commandes test d'un fichier sont regroupées dans un seul fichier de tests. Le banc d'essai est ensuite exécuté en chargeant le fichier dans l'interpréteur Tcl du banc d'essai.

Un fichier de test typique contient un certain nombre de commandes pour créer les tests, puis la commande runAllTests, et enfin la commande cleanupTests.

Par exemple, supposons que vous souhaitiez tester le comportement de la commande string de Tcl. Voici un exemple de fichier de test pour le test de la commande string.

# Fichier de test typique
#
# 1. Charger le package tcltest.
#
package require tcltest
#
# 2. Configurer le banc d'essai.
#    Notez que plusieurs options peuvent être configurées en une seule fois.
#
tcltest::configure -testdir    .
tcltest::configure -tmpdir     [pwd]/tmp
tcltest::configure -load      {
    # Charger le code à tester ici.
    # Vous pouvez aussi utiliser -loadfile.
    # Voici un exemple :
    set myvar 10
}
#
# 3. Définir les tests.
#    Voici quelques exemples de tests pour la commande string.
#
tcltest::test string1 {long string test} {
    -body {
        string length "this is a test"
    }
    -result {14}
}
#
#    Le test suivant est un peu plus compliqué.
#    Il nécessite de créer un fichier texte.
#
tcltest::test string2 {file test} {
    -body {
        set testfile [tcltest::makeFile {hello world
} hello.txt]
        set fid [open $testfile r]
        set contents [read $fid]
        close $fid
        string length $contents
    }
    -result {11}
}
#
#    Le test suivant est une évasion, donc il n'est pas exécuté.
#
tcltest::test string3 {skip test} {
    -body {
        string index "abc" 1
    }
    -result {b}
    -skip {
        # Juste pour l'exemple, on suppose que notre environnement
        # n'est pas approprié.
        #
        # Notez que la condition de saut doit être une condition Tcl
        # qui renvoie un booléen.
        #
        # Si le test est exécuté sur une plate-forme où ce test
        # n'est pas pertinent, le test sera ignoré.
        #
        # Ceci est juste pour démontrer l'utilisation de -skip.
        #
        if {1} {
            return true
        } else {
            return false
        }
    }
}
#
#    Test avec une condition qui ne passe pas, donc le test sera
#    exécuté sur toutes les plate-forme.
#
tcltest::test string4 {condition test} {
    -body {
        string index "abc" 1
    }
    -result {b}
    -constraints {
        # Une contrainte typique est la plate-forme.
        # Il pourrait s'agir d'une liste de plates-formes où
        # ce test peut être exécuté.
        #
        # Ceci est une contrainte fictive juste pour
        # montrer la syntaxe.
        #
        # Dans un environnement réel, vous pourriez tester
        # la version de Tcl, par exemple:
        #
        #   tcl_version >= 8.4
        #
        # ou une combinaison de plates-formes :
        #
        #   {linux macos windows}
        #
        # La contrainte par défaut est toujours vraie.
        #
        if {$tcl_platform(platform) eq "unix"} {
            return true
        } else {
            return false
        }
    }
}
#
#    Test qui utilise le format de résultat et de corps simplifié.
#
tcltest::test string5 {simplified form} {exact} {
    string length "test string"
} {11}
#
# 4. Exécuter tous les tests définis dans ce fichier.
#
tcltest::runAllTests
#
# 5. Nettoyer après les tests.
#    Supprimer les fichiers temporaires, imprimer les statistiques, etc.
#
tcltest::cleanupTests

Le banc d'essai s'attend à trouver les tests dans un répertoire de tests, indiqué par l'option configure -testdir. Le répertoire de tests est le répertoire contenant le fichier de banc d'essai, sauf indication contraire.

Les tests sont exécutés dans un interpréteur Tcl nouvellement créé. Le code à tester est chargé dans l'interpréteur à l'aide de l'option configure -load ou configure -loadfile. Le code à tester est ensuite appelé par les scripts dans le corps des tests.

Les tests sont exécutés en série, un par un. Les résultats de chaque test sont comparés aux résultats attendus pour déterminer si le test a réussi ou échoué. Les résultats sont rapportés sur le canal de sortie, qui par défaut est stdout.

Après l'exécution de tous les tests, la commande cleanupTests est appelée pour nettoyer les fichiers temporaires qui ont été créés pendant les tests, et pour imprimer un résumé des résultats des tests.

TESTS

Chaque test est défini par un appel à la commande test. Le premier argument est le nom du test, suivi d'une description textuelle du test. Le reste des arguments de la commande test définit le test. Ces arguments peuvent être des options sous forme de paires -option valeur, ou une forme simplifiée qui est un corps de script et un résultat attendu.

-body script
La commande test exécute le script Tcl spécifié par cet option. La valeur de retour de l'exécution de ce script est le résultat réel du test.
-result résultatAttendu
Le résultat réel du test (la valeur de retour de l'option -body) est comparé à résultatAttendu. Le test réussit si les deux sont identiques selon la méthode de comparaison spécifiée par l'option -match.
-match modeComparaison
Spécifie comment comparer le résultat réel du test à résultatAttendu. Les modes de comparaison disponibles sont:
exact
Les résultats doivent être identiques.
glob
Les résultats sont comparés en utilisant la correspondance de motifs glob. Ceci est la même chose que la commande Tcl string match.
regexp
Les résultats sont comparés en utilisant les expressions régulières Tcl. Ceci est la même chose que la commande Tcl regexp.
commandeValeur
Une commande spécifiée par l'utilisateur est utilisée pour comparer les deux chaînes. La commande doit accepter deux arguments (le résultat réel et le résultat attendu) et renvoyer un booléen.

L'option par défaut pour -match est exact.

-constraints contraintes
L'option -constraints spécifie une ou plusieurs contraintes sous lesquelles le test doit être exécuté. Si des contraintes sont spécifiées, le test n'est exécuté que si toutes les contraintes sont vraies. Les contraintes sont spécifiées comme une liste de chaînes Tcl, où chaque chaîne est une expression Tcl qui est évaluée. Si l'expression renvoie un résultat vrai, la contrainte est satisfaite. Les contraintes typiques incluent la vérification de la version de Tcl ou des caractéristiques de la plateforme.
-skip contraintesSaut
L'option -skip spécifie une ou plusieurs contraintes sous lesquelles le test doit être sauté. Si des contraintes sont spécifiées, le test n'est pas exécuté si l'une des contraintes est vraie. Le format est le même que pour l'option -constraints.
-directory répertoireTravail
Définit le répertoire de travail pour le test. Par défaut, il s'agit du répertoire de travail courant de l'interpréteur Tcl qui exécute le banc d'essai.
-auto booléen
Si cette option est définie sur true, la commande test tente d'inférer automatiquement les options -body, -result, et -match. Si vous utilisez l'option -auto, vous devez soit fournir un script d'initialisation pour le test (utilisant l'option -init), soit vous assurer que le résultat attendu est une chaîne vide et que le mode de correspondance par défaut est utilisé.
-init scriptInitialisation
Un script Tcl qui est exécuté avant que le corps du test ne soit exécuté. Ceci est utile pour configurer l'environnement du test, par exemple en créant des variables ou en chargeant des procédures.
-cleanup scriptNettoyage
Un script Tcl qui est exécuté après l'exécution du corps du test, que le test ait réussi ou échoué. Ceci est utile pour nettoyer les ressources utilisées par le test, par exemple en supprimant des fichiers ou des répertoires créés pendant le test.
-comment commentaire
Un commentaire texte qui sera inclus dans le rapport du test. Ceci peut être utilisé pour fournir des informations supplémentaires sur le test.
-returncode codeRetourAttendu
Spécifie le code de retour attendu de l'exécution du script du corps du test. Par défaut, il s'agit de 0 (succès). Les codes de retour typiques sont 0, 1 (erreur générale), ou 127 (commande non trouvée).
-catch booléen
Si cette option est définie sur true, la commande test capturera toute erreur ou exception levée pendant l'exécution du corps du test. Le résultat réel sera alors le message d'erreur.

La forme simplifiée de la commande test utilise les arguments suivants:

    test nom description ?contraintes? corps résultat

Dans cette forme, corps est le script Tcl à exécuter, et résultat est le résultat attendu. Les options -constraints, -body, -result, et -match sont définies implicitement. Si contraintes est présent, il est interprété comme une contrainte unique. Si contraintes est omis, alors le deuxième argument est traité comme le corps du test et le troisième argument comme le résultat attendu. Le mode de comparaison par défaut est exact.

CONFIGURATION

La commande configure est utilisée pour configurer le comportement du banc d'essai. Elle peut être appelée avec aucun argument pour afficher les options de configuration actuelles, avec une seule option pour afficher la valeur de cette option, ou avec des paires -option valeur pour définir de nouvelles valeurs.

Les options de configuration disponibles sont les suivantes:

-testdir répertoire
Le répertoire contenant le banc d'essai. La valeur par défaut est le répertoire courant.
-tmpdir répertoire
Le répertoire utilisé pour créer des fichiers et des répertoires temporaires pendant l'exécution des tests. La valeur par défaut est un sous-répertoire nommé tmp dans le répertoire de test.
-outputfile nomfichier
Un fichier où la sortie du banc d'essai sera redirigée. Par défaut, la sortie est envoyée à stdout.
-errorfile nomfichier
Un fichier où les erreurs du banc d'essai seront redirigées. Par défaut, les erreurs sont envoyées à stderr.
-verbose niveau
Définit le niveau de verbosité du banc d'essai. Les niveaux de verbosité plus élevés produiront plus de sortie. Les niveaux possibles sont 0 (silencieux), 1 (messages normaux), 2 (messages détaillés).
-debug niveau
Définit le niveau de débogage du banc d'essai. Les niveaux de débogage plus élevés fourniront des informations de débogage plus détaillées.
-load script
Un script Tcl qui sera exécuté dans l'interpréteur de test avant que les tests ne soient exécutés. Ceci est utile pour charger les commandes ou les paquets à tester.
-loadfile nomfichier
Un fichier contenant un script Tcl qui sera exécuté dans l'interpréteur de test avant que les tests ne soient exécutés. C'est une alternative à l'option -load.
-outputchannel canalID
Le canal Tcl où la sortie du banc d'essai sera envoyée. Par défaut, il s'agit de stdout.
-errorchannel canalID
Le canal Tcl où les erreurs du banc d'essai seront envoyées. Par défaut, il s'agit de stderr.
-interpreter interp
L'interpréteur Tcl à utiliser pour exécuter les tests. Par défaut, il s'agit de l'interpréteur courant.
-singleprocess booléen
Si défini sur true, tous les tests seront exécutés dans le même interpréteur. Si défini sur false, chaque test sera exécuté dans son propre interpréteur. La valeur par défaut est false.
-match modeComparaison
Le mode de comparaison par défaut à utiliser pour tous les tests, sauf s'il est explicitement spécifié dans la commande test.
-temporaryDirectory répertoire
Synonyme de -tmpdir.
-testsDirectory répertoire
Synonyme de -testdir.
-verbose niveau
Synonyme de -verbose.
-debug niveau
Synonyme de -debug.
-preserveCore niveau
Contrôle la préservation des fichiers core dumps en cas d'échec d'un test. Les niveaux possibles sont 0 (ne pas préserver), 1 (préserver les fichiers core dumps des tests qui échouent).
-limitConstraints booléen
Si défini sur true, les contraintes des tests seront vérifiées avant l'exécution du test. Si défini sur false, les contraintes seront ignorées. La valeur par défaut est true.

UTILITAIRES DIVERS

Le package tcltest fournit également un certain nombre de commandes utilitaires pour aider à la création et à l'exécution de bancs d'essai:

makeDirectory nom ?répertoire?
Crée un répertoire nommé nom dans le répertoire spécifié par répertoire (ou le répertoire temporaire par défaut si répertoire n'est pas spécifié). Le répertoire créé sera automatiquement supprimé lors de l'appel de cleanupTests, sauf s'il est explicitement supprimé par removeDirectory.
removeDirectory nom ?répertoire?
Supprime le répertoire nommé nom dans le répertoire spécifié par répertoire (ou le répertoire temporaire par défaut).
makeFile contenu nom ?répertoire?
Crée un fichier nommé nom dans le répertoire spécifié par répertoire (ou le répertoire temporaire par défaut) et écrit contenu dans le fichier. Le fichier sera automatiquement supprimé lors de l'appel de cleanupTests, sauf s'il est explicitement supprimé par removeFile.
removeFile nom ?répertoire?
Supprime le fichier nommé nom dans le répertoire spécifié par répertoire (ou le répertoire temporaire par défaut).
viewFile nom ?répertoire?
Renvoie le contenu du fichier nommé nom dans le répertoire spécifié par répertoire (ou le répertoire temporaire par défaut). Le contenu est lu sans la dernière nouvelle ligne.
loadTestedCommands
Charge les commandes à tester dans l'interpréteur. Le script à charger est défini par l'option configure -load ou configure -loadfile.
runAllTests
Exécute tous les tests qui ont été définis dans le banc d'essai courant.
cleanupTests ?runningMultipleTests?
Nettoie les ressources utilisées par le banc d'essai, supprime les fichiers et répertoires temporaires, et imprime un résumé des résultats des tests. L'argument optionnel runningMultipleTests est un booléen qui indique si plusieurs bancs d'essai sont en cours d'exécution. Si c'est le cas, cleanupTests ne supprime pas les fichiers temporaires.
customMatch mode commande
Permet de définir des modes de correspondance personnalisés pour les tests. mode est le nom du nouveau mode de correspondance, et commande est une commande Tcl qui sera appelée pour effectuer la comparaison.
testConstraint contrainte ?valeur?
Permet de définir ou de récupérer des valeurs pour les contraintes de test. Si valeur est spécifiée, elle définit la valeur de la contrainte. Sinon, elle renvoie la valeur actuelle de la contrainte.
bytestring chaine
Convertit une chaîne de caractères en une chaîne de type binaire. Utile pour tester des commandes qui manipulent des données binaires.
normalizeMsg msg
Normalise un message d'erreur en supprimant les informations spécifiques à l'environnement, telles que les chemins de fichiers absolus.
normalizePath varChemin
Normalise un chemin de fichier en remplaçant les chemins absolus par des chemins relatifs au répertoire de test.
workingDirectory ?dir?
Définit ou récupère le répertoire de travail courant pour les tests. Si dir est spécifié, il définit le répertoire de travail.

runAllTests
Ceci est une commande principale destinée à exécuter une suite entière de tests, couvrant plusieurs fichiers et/ou répertoires, comme régi par les options configurables de tcltest. Voir EXÉCUTION DE TOUS LES TESTS ci-dessous pour une description complète des nombreuses variations possibles avec runAllTests.

COMMANDES DE CONFIGURATION

configure
Renvoie la liste des options configurables prises en charge par tcltest. Voir OPTIONS CONFIGURABLES ci-dessous pour la liste complète des options, leurs valeurs valides et leur effet sur les opérations de tcltest.
configure option
Renvoie la valeur actuelle de l'option configurable prise en charge option. Lève une erreur si option n'est pas une option configurable prise en charge.
configure option valeur ?-option valeur ...?
Définit la valeur de chaque option configurable option à la valeur correspondante valeur, dans l'ordre. Lève une erreur si une option n'est pas une option configurable prise en charge, ou si valeur n'est pas une valeur valide pour l'option correspondante option, ou si une valeur n'est pas fournie. Lorsqu'une erreur est levée, l'opération de configure s'arrête, et les arguments option valeur suivants ne sont pas traités.

Si la variable d'environnement ::env(TCLTEST_OPTIONS) existe lorsque le package tcltest est chargé (par package require tcltest), alors sa valeur est considérée comme une liste d'arguments à passer à configure. Cela permet de définir les valeurs par défaut des options de configuration par l'environnement.

customMatch mode script
Enregistre mode comme une nouvelle valeur légale de l'option -match pour test. Lorsque l'option -match mode est passée à test, le script script sera évalué pour comparer le résultat réel de l'évaluation du corps du test au résultat attendu. Pour effectuer la comparaison, le script est complété avec deux mots supplémentaires, le résultat attendu et le résultat réel, et le script complété est évalué dans l'espace de noms global. Le script complété doit renvoyer une valeur booléenne indiquant si les résultats correspondent ou non. Les modes de comparaison intégrés de test sont exact, glob et regexp.
testConstraint contrainte ?booléen?
Définit ou renvoie la valeur booléenne associée à la contrainte nommée. Voir CONTRAINTES DE TEST ci-dessous pour plus d'informations.

Définit ou renvoie le nom de l'exécutable à executer par runAllTests pour exécuter chaque fichier de test lorsque configure -singleproc est faux. La valeur par défaut pour interpreter est le nom du programme actuellement en cours d'exécution tel que renvoyé par info nameofexecutable.

Définit ou renvoie l'ID du canal de sortie. Par défaut, c'est stdout. Tout test qui imprime une sortie liée aux tests doit envoyer cette sortie à outputChannel plutôt que de laisser cette sortie être dirigée par défaut vers stdout.
errorChannel ?idCanal?
Définit ou renvoie l'ID du canal d'erreur. Par défaut, c'est stderr. Tout test qui imprime des messages d'erreur doit envoyer cette sortie à errorChannel plutôt que d'imprimer directement sur stderr.

AUTRES COMMANDES

Les commandes restantes fournies par tcltest ont de meilleures alternatives fournies par tcltest ou Tcl lui-même. Elles sont conservées pour prendre en charge les suites de tests existantes, mais doivent être évitées dans le nouveau code.

test nom description listeOptions
Cette forme de test a été fournie pour permettre de passer de nombreuses options couvrant plusieurs lignes à test en tant qu'unique argument entouré d'accolades, plutôt que de devoir échapper les nouvelles lignes entre les arguments de test avec une barre oblique inverse. L'argument listeOptions est censé être une liste avec un nombre pair d'éléments représentant les arguments option et valeur à passer à test. Cependant, ces valeurs ne sont pas passées directement, comme dans les formes alternatives de switch. Au lieu de cela, cette forme tente malencontreusement de renverser les règles de substitution de Tcl en effectuant des substitutions sur certains éléments de la liste dans une tentative d'implémenter une interprétation « faites ce que je veux » d'un « bloc » entouré d'accolades. Le résultat est presque impossible à documenter clairement, et pour cette raison, cette forme n'est pas recommandée. Voir les exemples dans CRÉATION DE SUITES DE TESTS AVEC TCLTEST ci-dessous pour constater que cette forme n'est vraiment pas nécessaire pour éviter les nouvelles lignes échappées par une barre oblique inverse. Si vous insistez pour utiliser cette forme, examinez le code source de tcltest si vous souhaitez connaître les détails de substitution, ou entourez simplement le troisième argument jusqu'au dernier de test d'accolades et espérez le meilleur.
workingDirectory ?nomRépertoire?
Définit ou renvoie le répertoire de travail actuel lorsque la suite de tests est en cours d'exécution. La valeur par défaut de workingDirectory est le répertoire dans lequel la suite de tests a été lancée. Les commandes Tcl cd et pwd sont des remplacements suffisants.
normalizeMsg msg
Renvoie le résultat de la suppression des nouvelles lignes « supplémentaires » de msg, où « supplémentaire » est plutôt imprécis. Tcl offre de nombreuses commandes de traitement de chaînes pour modifier les chaînes comme vous le souhaitez, et customMatch permet une correspondance flexible des résultats réels et attendus.
normalizePath varChemin
Résout les liens symboliques dans un chemin, créant ainsi un chemin sans redirection interne. On suppose que varChemin est absolu. varChemin est modifié sur place. La commande Tcl file normalize est un remplacement suffisant.
bytestring chaîne
Construit une chaîne qui consiste en la séquence d'octets demandée, par opposition à une chaîne de caractères UTF-8 correctement formés en utilisant la valeur fournie dans chaîne. Cela permet au testeur de créer des chaînes dénormalisées ou mal formées à passer à des procédures C qui sont censées accepter des chaînes avec des types NULL intégrés et de confirmer qu'un résultat de chaîne correspond à un certain motif d'octets. Ceci est exactement équivalent à la commande Tcl encoding convertfrom identity. Cette fonction est obsolète.

TESTS

La commande test est le cœur du package tcltest. Sa fonction essentielle est

s pour évaluer un script Tcl et comparer le résultat avec un résultat attendu. Les options de test définissent le script de test, l'environnement dans lequel l'évaluer, le résultat attendu et comment comparer le résultat réel au résultat attendu. Certaines options de configuration de tcltest influencent également le fonctionnement de test.

Les options valides pour test sont résumées :

test nom description
        ?-constraints listeMotsCles|expression?
        ?-setup scriptConfiguration?
        ?-body scriptTest?
        ?-cleanup scriptNettoyage?
        ?-result reponseAttendue?
        ?-output sortieAttendue?
        ?-errorOutput erreurAttendue?
        ?-returnCodes listeCodes?
        ?-errorCode codeErreurAttendu?
        ?-match mode?

Le nom peut être n'importe quelle chaîne de caractères. Il est conventionnel de choisir un nom selon le modèle :

cible-numMaj.numMin

Pour les tests en boîte blanche (régression), la cible doit être le nom de la fonction C ou de la procédure Tcl testée. Pour les tests en boîte noire, la cible doit être le nom de la fonctionnalité testée. Certaines conventions exigent que les noms des tests en boîte noire aient le suffixe _bb. Les tests liés doivent partager un numéro majeur. Au fur et à mesure qu'une suite de tests évolue, il est préférable que le même nom de test corresponde toujours au même test, afin qu'il reste pertinent de dire des choses comme « Le test foo-1.3 a réussi dans toutes les versions jusqu'à la 3.4, mais a commencé à échouer dans la version 3.5. »

Lors de l'évaluation de test, le nom sera comparé aux listes de modèles de correspondance de chaînes renvoyées par configure -match et configure -skip. Le test ne sera exécuté que si le nom correspond à l'un des modèles de configure -match et ne correspond à aucun des modèles de configure -skip.

La description doit être une courte description textuelle du test. La description est incluse dans la sortie produite par le test, généralement les messages d'échec de test. Les bonnes valeurs de description doivent expliquer brièvement le but du test aux utilisateurs d'une suite de tests. Le nom d'une fonction Tcl ou C testée doit être inclus dans la description pour les tests de régression. Si le cas de test existe pour reproduire un bug, incluez l'identifiant du bug dans la description.

Les attributs valides et leurs valeurs associées sont :

-constraints listeMotsCles|expression
L'attribut optionnel -constraints peut être une liste d'un ou plusieurs mots clés ou une expression. Si la valeur de -constraints est une liste de mots clés, chacun de ces mots clés doit être le nom d'une contrainte définie par un appel à testConstraint. Si l'une des contraintes listées est fausse ou n'existe pas, le test est ignoré. Si la valeur de -constraints est une expression, cette expression est évaluée. Si l'expression évalue à vrai, le test est exécuté. Notez que la forme d'expression de -constraints peut interférer avec le fonctionnement de configure -constraints et configure -limitconstraints, et n'est pas recommandée. Des contraintes appropriées doivent être ajoutées à tous les tests qui ne doivent pas toujours être exécutés. C'est-à-dire que l'évaluation conditionnelle d'un test doit être réalisée par l'option -constraints, et non par l'évaluation conditionnelle de test. De cette façon, le même nombre de tests sont toujours rapportés par la suite de tests, bien que le nombre ignoré puisse changer en fonction de l'environnement de test. La valeur par défaut est une liste vide. Voir CONTRAINTES DES TESTS ci-dessous pour une liste des contraintes intégrées et des informations sur la façon d'ajouter vos propres contraintes.
-setup script
L'attribut optionnel -setup indique un script qui sera exécuté avant le script indiqué par l'attribut -body. Si l'évaluation du script lève une erreur, le test échouera. La valeur par défaut est un script vide.
-body script
L'attribut -body indique le script à exécuter pour effectuer le test, qui doit renvoyer un résultat dont la correction peut être vérifiée. Si l'évaluation du script lève une erreur, le test échouera (sauf si l'option -returnCodes est utilisée pour indiquer qu'une erreur est attendue). La valeur par défaut est un script vide.
-cleanup script
L'attribut optionnel -cleanup indique un script qui sera exécuté après le script indiqué par l'attribut -body. Si l'évaluation du script lève une erreur, le test échouera. La valeur par défaut est un script vide.
-match mode
L'attribut -match détermine comment les réponses attendues fournies par -result, -output et -errorOutput sont comparées. Les valeurs valides pour mode sont regexp, glob, exact, et toute valeur enregistrée par un appel antérieur à customMatch. La valeur par défaut est exact.
-result valeurAttendue
L'attribut -result fournit la valeurAttendue par rapport à laquelle la valeur de retour du script sera comparée. La valeur par défaut est une chaîne vide.
-output valeurAttendue
L'attribut -output fournit la valeurAttendue par rapport à laquelle toute sortie envoyée à stdout ou outputChannel pendant l'évaluation du (des) script(s) sera comparée. Notez que seule la sortie imprimée à l'aide de la commande globale puts est utilisée pour la comparaison. Si -output n'est pas spécifié, la sortie envoyée à stdout et outputChannel n'est pas traitée pour la comparaison.
-errorOutput valeurAttendue
L'attribut -errorOutput fournit la valeurAttendue par rapport à laquelle toute sortie envoyée à stderr ou errorChannel pendant l'évaluation du (des) script(s) sera comparée. Notez que seule la sortie imprimée à l'aide de la commande globale puts est utilisée pour la comparaison. Si -errorOutput n'est pas spécifié, la sortie envoyée à stderr et errorChannel n'est pas traitée pour la comparaison.
-returnCodes listeCodesAttendus
L'attribut optionnel -returnCodes fournit la listeCodesAttendus, une liste de codes de retour qui peuvent être acceptés de l'évaluation du script -body. Si l'évaluation du script -body renvoie un code qui n'est pas dans la listeCodesAttendus, le test échoue. Tous les codes de retour connus de return, sous forme numérique et symbolique, y compris les codes de retour étendus, sont des éléments acceptables dans la listeCodesAttendus. La valeur par défaut est « ok return ».
-errorCode codeErreurAttendu
L'attribut optionnel -errorCode fournit le codeErreurAttendu, un modèle glob qui doit correspondre au code d'erreur signalé par l'évaluation du script -body. Si l'évaluation du script -body renvoie un code qui ne correspond pas au codeErreurAttendu, le test échoue. La valeur par défaut est « * ». Si -returnCodes n'inclut pas error, il est défini sur error.

Pour réussir, un test doit évaluer avec succès ses scripts -setup, -body et -cleanup. Le code de retour du script -body et son résultat doivent correspondre aux valeurs attendues, et si spécifié, les données de sortie et d'erreur du test doivent correspondre aux valeurs -output et -errorOutput attendues. Si l'une de ces conditions n'est pas remplie, le test échoue. Notez que tous les scripts sont évalués dans le contexte de l'appelant de test.

Tant que test est appelé avec une syntaxe valide et des valeurs légales pour tous les attributs, il ne lèvera pas d'erreur. Les échecs de test sont plutôt signalés comme une sortie écrite sur outputChannel. En fonctionnement par défaut, un test réussi ne produit aucune sortie. Les messages de sortie produits par test sont contrôlés par l'option configure -verbose, comme décrit dans OPTIONS CONFIGURABLES ci-dessous. Toute sortie produite par les scripts de test eux-mêmes doit être produite à l'aide de puts vers outputChannel ou errorChannel, afin que les utilisateurs de la suite de tests puissent facilement capturer la sortie avec les options configure -outfile et configure -errfile, et afin que les attributs -output et -errorOutput fonctionnent correctement.

CONTRAINTES DES TESTS

Les contraintes sont utilisées pour déterminer si un test doit être ignoré ou non. Chaque contrainte a un nom, qui peut être n'importe quelle chaîne de caractères, et une valeur booléenne. Chaque test a une valeur -constraints qui est une liste de noms de contraintes. Il existe deux modes de contrôle des contraintes. Le plus souvent, le mode par défaut est utilisé, indiqué par un réglage de configure -limitconstraints sur faux. Le test ne sera exécuté que si toutes les contraintes de la liste ont une valeur vraie. Ainsi, l'option -constraints de test est un moyen symbolique pratique de définir toutes les conditions requises pour que le test soit possible ou significatif. Par exemple, un test avec -constraints unix ne sera exécuté que si la contrainte unix est vraie, ce qui indique que la suite de tests est exécutée sur une plateforme Unix.

Chaque test doit inclure les -constraints nécessaires pour le limiter à s'exécuter uniquement lorsqu'il convient. Plusieurs contraintes sont prédéfinies dans le package tcltest, listées ci-dessous. L'enregistrement des contraintes définies par l'utilisateur est effectué par la commande testConstraint. Les contraintes définies par l'utilisateur peuvent apparaître dans un fichier de test, ou dans le script spécifié par les options configure -load ou configure -loadfile.

Les tests de ce projet sont organisés sous forme de classes et d'individus. Les classes de tests sont des collections de tests qui nécessitent tous certaines conditions pour être exécutés. Les contraintes sont des noms qui décrivent les conditions qui doivent être remplies. Lorsqu'un test est exécuté, toutes les contraintes du test sont vérifiées. Si l'une des contraintes n'est pas satisfaite, le test est ignoré. Sinon, le test est exécuté. Les contraintes sont implémentées en utilisant la commande tcltest::configure de la manière suivante :

unix

win
Ce test ne peut être exécuté que sur une plateforme Windows.
macOnly
Ce test ne peut être exécuté que sur une plateforme Mac.

Ce test ne peut être exécuté que sur une plateforme Unix ou Windows.
macOrWin
Ce test ne peut être exécuté que sur une plateforme Mac ou Windows.
macOrUnix

Ce test ne peut pas être exécuté sous Windows. Ce drapeau est utilisé pour désactiver temporairement un test.
tempNotMac
Ce test ne peut pas être exécuté sur un Mac. Ce drapeau est utilisé pour désactiver temporairement un test.

Ce test plante s'il est exécuté sous Windows. Ce drapeau est utilisé pour désactiver temporairement un test.
macCrash
Ce test plante s'il est exécuté sur un Mac. Ce drapeau est utilisé pour désactiver temporairement un test.

Ce test est vide, et donc ne vaut pas la peine d'être exécuté, mais il reste comme espace réservé pour un test à écrire à l'avenir. Cette contrainte a la valeur false pour que les tests soient ignorés, sauf si l'utilisateur spécifie le contraire.

Ce test est connu pour échouer et le bogue n'est pas encore corrigé. Cette contrainte a la valeur false pour que les tests soient ignorés, sauf si l'utilisateur spécifie le contraire.

Ce test ne peut être exécuté que dans un environnement de développement connu. Certains tests ne sont intrinsèquement pas portables car ils dépendent de choses comme la longueur des mots, la configuration du système de fichiers, le gestionnaire de fenêtres, etc. Cette contrainte a la valeur false pour que les tests soient ignorés, sauf si l'utilisateur spécifie le contraire.

Ce test ne peut être exécuté que si la plateforme prend en charge le vidage asynchrone et la fermeture asynchrone d'un pipe.
unixExecs
Ce test ne peut être exécuté que si cette machine dispose des commandes de style Unix cat, echo, sh, wc, rm, sleep, fgrep, ps, chmod et mkdir.
hasIsoLocale
Ce test ne peut être exécuté que si on peut passer à une locale ISO.
root
Ce test ne peut être exécuté que si l'utilisateur Unix est root.
notRoot
Ce test ne peut être exécuté que si l'utilisateur Unix n'est pas root.
eformat
Ce test ne peut être exécuté que si l'application dispose d'une version fonctionnelle de sprintf par rapport au format "e" des nombres à virgule flottante.
stdio
Ce test ne peut être exécuté que si l'interpréteur peut être ouvert comme un pipe.

Le mode alternatif de contrôle des contraintes est activé en définissant configure -limitconstraints sur true. Avec ce paramètre de configuration, toutes les contraintes existantes autres que celles de la liste des contraintes retournées par configure -constraints sont définies sur false. Lorsque la valeur de configure -constraints est définie, toutes ces contraintes sont définies sur true. L'effet est que lorsque les deux options configure -constraints et configure -limitconstraints sont utilisées, seuls les tests incluant uniquement des contraintes de la liste configure -constraints sont exécutés ; tous les autres sont ignorés. Par exemple, on pourrait configurer avec

configure -constraints knownBug \
          -limitconstraints true \
          -verbose pass

pour exécuter exactement les tests qui couvrent les bogues connus, et découvrir si l'un d'entre eux passe, indiquant que le bogue a été corrigé.

EXÉCUTION DE TOUS LES TESTS

La commande unique runAllTests est évaluée pour exécuter une suite de tests complète, couvrant de nombreux fichiers et répertoires. Les options de configuration de tcltest contrôlent les opérations précises. La commande runAllTests commence par imprimer un résumé de sa configuration sur le canal de sortie.

Les fichiers de test à évaluer sont recherchés dans le répertoire configure -testdir. La liste des fichiers de ce répertoire qui correspondent à l'un des modèles de configure -file et qui ne correspondent à aucun des modèles de configure -notfile est générée et triée. Ensuite, chaque fichier est évalué à tour de rôle. Si configure -singleproc est vrai, chaque fichier sera sourcé dans le contexte de l'appelant. S'il est faux, une copie de l'interpréteur sera exécutée pour évaluer chaque fichier. L'opération multi-processus est utile lorsque les tests peuvent provoquer des erreurs si graves qu'un processus se termine. Bien qu'une telle erreur puisse mettre fin à un processus enfant évaluant un fichier, le processus principal peut continuer avec le reste de la suite de tests. En opération multi-processus, la configuration de tcltest dans le processus principal est transmise aux processus enfants sous forme d'arguments de ligne de commande, à l'exception de configure -outfile. La commande runAllTests dans le processus principal collecte toutes les sorties des processus enfants et compile leurs résultats en un rapport principal. Tous les rapports d'échecs de tests individuels, ou les messages demandés par un paramètre configure -verbose, sont transmis directement au canal de sortie par le processus principal.

Après avoir évalué tous les fichiers de test sélectionnés, un résumé des résultats est imprimé sur le canal de sortie. Le résumé comprend le nombre total de tests évalués, répartis entre ceux ignorés, ceux réussis et ceux échoués. Le résumé note également le nombre de fichiers évalués et les noms des fichiers ayant des tests échoués ou des erreurs. Une liste des contraintes qui ont entraîné l'ignorance des tests, et le nombre de tests ignorés pour chacune, est également imprimée. De plus, des messages sont imprimés s'il semble que l'évaluation d'un fichier de test ait laissé des fichiers temporaires dans configure -tmpdir.

Après avoir terminé et résumé tous les fichiers de test sélectionnés, runAllTests agit récursivement sur les sous-répertoires de configure -testdir. Tous les sous-répertoires qui correspondent à l'un des modèles de configure -relateddir et ne correspondent à aucun des modèles de configure -asidefromdir sont examinés. Si un fichier nommé all.tcl est trouvé dans un tel répertoire, il sera sourcé dans le contexte de l'appelant. Que le répertoire examiné contienne ou non un fichier all.tcl, ses sous-répertoires sont également analysés par rapport aux modèles configure -relateddir et configure -asidefromdir. De cette façon, de nombreux répertoires dans une arborescence de répertoires peuvent avoir tous leurs fichiers de test évalués par une seule commande runAllTests.

OPTIONS CONFIGURABLES

La commande configure est utilisée pour définir et interroger les options configurables de tcltest. Les options valides sont :

-singleproc booléen
Contrôle si runAllTests lance un processus enfant pour chaque fichier de test. Pas de lancement lorsque booléen est vrai. La valeur par défaut est fausse.
-debug niveau
Définit le niveau de débogage sur niveau, une valeur entière indiquant la quantité d'informations de débogage à afficher sur stdout. Notez que les messages de débogage vont toujours sur stdout, indépendamment de la valeur de configure -outfile. La valeur par défaut est 0. Les niveaux sont définis comme suit :
0
N'afficher aucune information de débogage.
1
Afficher les informations concernant le fait qu'un test soit ignoré car il ne correspond à aucun des tests spécifiés par configure -match (non correspondant spécifié par l'utilisateur) ou correspond à l'un des tests spécifiés par configure -skip (ignoré spécifié par l'utilisateur). Afficher également des avertissements sur un possible manque de nettoyage ou d'équilibre dans les fichiers de test. Afficher également des avertissements sur toute réutilisation de noms de test.
2
Afficher le tableau des drapeaux analysé par le processeur de ligne de commande, le contenu du tableau global env, et toutes les variables définies par l'utilisateur qui existent dans l'espace de noms actuel lorsqu'elles sont utilisées.
3
Afficher des informations sur ce que font les procédures individuelles du harnais de test.
-verbose niveau
Définit le type de verbosité de sortie souhaité sur niveau, une liste de zéro ou plusieurs des éléments body, pass, skip, start, error, line, msec et usec. La valeur par défaut est « body error ». Les niveaux sont définis comme suit :
body (b)
Afficher le corps des tests échoués
pass (p)
Afficher la sortie lorsqu'un test réussit
skip (s)
Afficher la sortie lorsqu'un test est ignoré
start (t)
Afficher la sortie chaque fois qu'un test démarre
error (e)
Afficher errorInfo et errorCode, s'ils existent, lorsqu'un code de retour de test ne correspond pas au code de retour attendu
line (l)
Afficher les informations sur la ligne du fichier source des tests échoués

Affiche le temps d'exécution de chaque test en millisecondes

Notez que les niveaux de verbosité msec et usec sont fournis à titre indicatif uniquement. Ils ne résolvent pas le problème de répétabilité qui devrait être pris en compte dans les tests de performance ou les benchmarks. Pour utiliser ces niveaux de verbosité afin de suivre de manière approfondie les dégradations de performance, envisagez d'encapsuler le corps de vos tests avec des commandes time.

Les abréviations d'une seule lettre notées ci-dessus sont également reconnues, de sorte que “configure -verbose pt” est identique à “configure -verbose {pass start}”.

-preservecore niveau
Définit le niveau de préservation des fichiers core dumps à niveau. Ce niveau détermine la rigueur des vérifications des fichiers core dumps. La valeur par défaut est 0. Les niveaux sont définis comme suit :
0
Aucune vérification — ne vérifie pas les fichiers core dumps à la fin de chaque commande de test, mais les vérifie dans runAllTests après l'évaluation de tous les fichiers de test.
1
Vérifie également les fichiers core dumps à la fin de chaque commande test.
2
Vérifie les fichiers core dumps dans tous les cas décrits ci-dessus et sauvegarde une copie de chaque fichier core dump produit dans configure -tmpdir.
-limitconstraints booléen
Définit le mode par lequel test respecte les contraintes décrites dans TESTS ci-dessus. La valeur par défaut est false.
-constraints liste
Définit toutes les contraintes de la liste à true. Également utilisé en combinaison avec configure -limitconstraints true pour contrôler un mode de contrainte alternatif tel que décrit dans TESTS ci-dessus. La valeur par défaut est une liste vide.
-tmpdir répertoire
Définit le répertoire temporaire à utiliser par makeFile, makeDirectory, viewFile, removeFile et removeDirectory comme répertoire par défaut où les fichiers et répertoires temporaires créés par les fichiers de test doivent être créés. La valeur par défaut est workingDirectory.
-testdir répertoire
Définit le répertoire recherché par runAllTests pour les fichiers de test et les sous-répertoires. La valeur par défaut est workingDirectory.
-file patternList
Définit la liste des motifs utilisés par runAllTests pour déterminer quels fichiers de test évaluer. La valeur par défaut est “*.test”.
-notfile patternList
Définit la liste des motifs utilisés par runAllTests pour déterminer quels fichiers de test ignorer. La valeur par défaut est “l.*.test”, de sorte que les fichiers de verrouillage SCCS soient ignorés.
-relateddir patternList
Définit la liste des motifs utilisés par runAllTests pour déterminer quels sous-répertoires rechercher un fichier all.tcl. La valeur par défaut est “*”.
-asidefromdir patternList
Définit la liste des motifs utilisés par runAllTests pour déterminer quels sous-répertoires ignorer lors de la recherche d'un fichier all.tcl. La valeur par défaut est une liste vide.
-match patternList
Définit la liste des motifs utilisés par test pour déterminer si un test doit être exécuté. La valeur par défaut est “*”.
-skip patternList
Définit la liste des motifs utilisés par test pour déterminer si un test doit être ignoré. La valeur par défaut est une liste vide.
-load script
Définit un script à évaluer par loadTestedCommands. La valeur par défaut est un script vide.
-loadfile nomfichier
Définit le nom du fichier à partir duquel lire un script à évaluer par loadTestedCommands. C'est une alternative à -load. Ils ne peuvent pas être utilisés ensemble.
-outfile nomfichier
Définit le fichier vers lequel toute la sortie produite par tcltest doit être écrite. Un fichier nommé nomfichier sera open pour écriture, et le canal résultant sera défini comme la valeur de outputChannel.
-errfile nomfichier
Définit le fichier vers lequel toute la sortie d'erreur produite par tcltest doit être écrite. Un fichier nommé nomfichier sera open pour écriture, et le canal résultant sera défini comme la valeur de errorChannel.

CRÉATION DES SUITES DE TESTS AVEC TCLTEST

L'élément fondamental d'une suite de tests est la commande individuelle test. Nous commençons par plusieurs exemples.

[1]
Test d'un script qui retourne normalement.
test exemple-1.0 {retour normal} {
    format %s valeur
} valeur
[2]
Test d'un script qui nécessite une configuration et un nettoyage du contexte. Notez le style d'accolades et d'indentation qui évite tout besoin de continuation de ligne.
test exemple-1.1 {existence du fichier de test} -setup {
    set fichier [makeFile {} test]
} -body {
    file exists $fichier
} -cleanup {
    removeFile test
} -result 1
[3]
Test d'un script qui déclenche une erreur.
test exemple-1.2 {retour d'erreur} -body {
    error message
} -returnCodes error -result message
[4]
Test avec une contrainte.
test exemple-1.3 {l'utilisateur possède les fichiers créés} -constraints {
    unix
} -setup {
    set fichier [makeFile {} test]
} -body {
    file attributes $fichier -owner
} -cleanup {
    removeFile test
} -result $::tcl_platform(user)

Au niveau d'organisation supérieur suivant, plusieurs commandes test sont regroupées dans un seul fichier de test. Les fichiers de test devraient avoir des noms avec l'extension “.test”, car c'est le motif par défaut utilisé par runAllTests pour trouver les fichiers de test. Il est de bon augure d'avoir un fichier de test pour chaque fichier source de votre projet. Il est de bonne pratique de modifier le fichier de test et le fichier source ensemble, en gardant les tests synchronisés avec les changements de code.

La majeure partie du code du fichier de test devrait être constituée des commandes test. Utilisez des contraintes pour ignorer les tests, plutôt que l'évaluation conditionnelle de test.

[5]
Système recommandé pour écrire des tests conditionnels, en utilisant des contraintes pour protéger :
testConstraint X [expr $myRequirement]
test bonTestConditionnel {} X {
    # corps
} resultat
[6]
Système déconseillé pour écrire des tests conditionnels, en utilisant if pour protéger :
if $myRequirement {
    test mauvaisTestConditionnel {} {
        # corps
    } resultat
}

Utilisez les options -setup et -cleanup pour établir et libérer toutes les exigences contextuelles du corps du test. Ne faites pas dépendre les tests des tests précédents dans le fichier. Ces tests précédents pourraient être ignorés. Si plusieurs tests consécutifs nécessitent le même contexte, les scripts de configuration et de nettoyage appropriés peuvent être stockés dans une variable pour être passés aux options -setup et -cleanup de chaque test. C'est une meilleure solution que d'effectuer la configuration en dehors des commandes test, car la configuration ne sera effectuée que si nécessaire, et toute erreur pendant la configuration sera signalée, sans provoquer l'abandon du fichier de test.

Un fichier de test devrait pouvoir être combiné avec d'autres fichiers de test et ne pas interférer avec eux, même lorsque configure -singleproc 1 provoque l'évaluation de tous les fichiers dans un interpréteur commun. Une façon simple d'y parvenir est d'avoir vos tests définir toutes leurs commandes et variables dans un espace de noms qui est supprimé à la fin de l'évaluation du fichier de test. Un bon espace de noms à utiliser est un espace de noms enfant test de l'espace de noms du module que vous testez.

Un fichier de test devrait également pouvoir être évalué directement en tant que script, sans dépendre d'être appelé par un runAllTests principal. Cela signifie que chaque fichier de test doit traiter les arguments de la ligne de commande pour donner au testeur tout le contrôle de configuration que tcltest fournit.

Après tous les tests dans un fichier de test, la commande cleanupTests doit être appelée.

[7]
Voici un schéma d'un exemple de fichier de test illustrant ces points :
package require tcltest 2.5
eval ::tcltest::configure $argv
package require example
namespace eval ::example::test {
    namespace import ::tcltest::*
    testConstraint X [expr {...}]
    variable SETUP {#code de configuration commun}
    variable CLEANUP {#code de nettoyage commun}
    test exemple-1 {} -setup $SETUP -body {
        # Premier test
    } -cleanup $CLEANUP -result {...}
    test exemple-2 {} -constraints X -setup $SETUP -body {
        # Deuxième test ; contraint
    } -cleanup $CLEANUP -result {...}
    test exemple-3 {} {
        # Troisième test ; aucun contexte requis
    } {...}
    cleanupTests
}
namespace delete ::example::test

Le niveau d'organisation suivant est une suite de tests complète, composée de plusieurs fichiers de test. Un script est utilisé pour contrôler l'ensemble de la suite. La fonction de base de ce script est d'appeler runAllTests après avoir effectué toute la configuration nécessaire. Ce script est généralement nommé all.tcl car c'est le nom par défaut utilisé par runAllTests lors de la combinaison de plusieurs suites de tests en une seule exécution de test.

[8]
Voici un schéma d'un exemple de script principal de suite de tests :
package require Tcl 8.6
package require tcltest 2.5
package require example
::tcltest::configure -testdir \
        [file dirname [file normalize [info script]]]
eval ::tcltest
::configure $argv
::tcltest::runAllTests

COMPATIBILITÉ

Un certain nombre de commandes et de variables dans le espace de noms ::tcltest fournis par les versions antérieures de tcltest n'ont pas été documentées ici. Elles ne font plus partie de l'interface publique prise en charge de tcltest et ne doivent pas être utilisées dans de nouvelles suites de tests. Cependant, afin de continuer à prendre en charge les suites de tests existantes écrites selon les spécifications des anciennes interfaces, nombre de ces commandes et variables dépréciées fonctionnent toujours comme avant. Par exemple, dans de nombreuses circonstances, configure sera automatiquement appelé peu après que package require tcltest 2.1 ait réussi avec des arguments provenant de la variable ::argv. Ceci afin de prendre en charge les suites de tests qui dépendent de l'ancien comportement selon lequel tcltest était automatiquement configuré à partir des arguments de la ligne de commande. Les nouveaux fichiers de tests ne doivent pas dépendre de cela, mais doivent inclure explicitement

eval ::tcltest::configure $::argv

ou

::tcltest::configure {*}$::argv

pour établir une configuration à partir des arguments de la ligne de commande.

PROBLÈMES CONNUS

Il existe deux problèmes connus liés aux évaluations imbriquées de test. Le premier problème concerne le niveau de pile dans lequel les scripts de test sont exécutés. Les tests imbriqués dans d'autres tests peuvent être exécutés au même niveau de pile que le test le plus externe. Par exemple, dans le code suivant :

test level-1.1 {niveau 1} {
    -body {
        test level-2.1 {niveau 2} {
        }
    }
}

tout script exécuté au niveau level-2.1 peut être exécuté au même niveau de pile que le script défini pour level-1.1.

De plus, bien que deux tests aient été exécutés, les résultats ne seront rapportés par cleanupTests que pour les tests au même niveau que test level-1.1. Cependant, les résultats des tests pour tous les tests exécutés avant level-1.1 seront disponibles lorsque test level-2.1 s'exécutera. Ce que cela signifie, c'est que si vous essayez d'accéder aux résultats du test pour test level-2.1, il peut indiquer que « m » tests ont été exécutés, « n » tests ont été ignorés, « o » tests ont réussi et « p » tests ont échoué, où « m », « n », « o » et « p » font référence aux tests qui ont été exécutés au même niveau de test que test level-1.1.

L'implémentation de la comparaison de sortie et d'erreur dans la commande test dépend de l'utilisation de puts dans votre code d'application. La sortie est interceptée en redéfinissant la commande globale puts pendant l'exécution du script de test défini. Les erreurs lancées par les procédures C ou imprimées directement depuis des applications C ne seront pas interceptées par la commande test. Par conséquent, l'utilisation des options -output et -errorOutput de test n'est utile que pour les applications Tcl pures qui utilisent puts pour produire de la sortie.
