NOM

BPF - Classifieur et actions BPF programmables pour les disciplines de mise en file d'attente d'entrée/sortie

SYNOPSIS

Classifieur (filtre) ou action eBPF :

tc filter ... bpf [ object-file FICHIER_OBJ ] [ section NOM_CLS ] [ export FICHIER_UDS ] [ verbose ] [ direct-action | da ] [ skip_hw | skip_sw ] [ police SPEC_POLICE ] [ action SPEC_ACTION ] [ classid CLASSID ]
tc action ... bpf [ object-file FICHIER_OBJ ] [ section NOM_CLS ] [ export FICHIER_UDS ] [ verbose ]

Classifieur (filtre) ou action cBPF :

tc filter ... bpf [ bytecode-file FICHIER_BPF | bytecode OCTETS_BPF ] [ police SPEC_POLICE ] [ action SPEC_ACTION ] [ classid CLASSID ]
tc action ... bpf [ bytecode-file FICHIER_BPF | bytecode OCTETS_BPF ]

DESCRIPTION

Extended Berkeley Packet Filter ( eBPF ) et classic Berkeley Packet Filter (originellement connu sous le nom de BPF, pour une meilleure distinction appelé cBPF ici) sont tous deux disponibles en tant que classifieurs et actions entièrement programmables et hautement efficaces. Ils offrent tous deux un ensemble d'instructions minimal pour implémenter de petits programmes qui peuvent être chargés en toute sécurité dans le noyau et donc exécutés dans une petite machine virtuelle depuis l'espace noyau. Un vérificateur intégré au noyau garantit qu'un programme spécifié se termine toujours et ne plante ni ne divulgue de données du noyau.

Sous Linux, on considère généralement qu'eBPF est le successeur de cBPF. Le noyau transforme en interne les expressions cBPF en expressions eBPF et exécute ces dernières. Leur exécution peut être effectuée dans un interpréteur ou, au moment de la configuration, ils peuvent être compilés à la volée (JIT) pour s'exécuter en code machine natif.

Actuellement, le compilateur JIT eBPF est disponible pour les architectures suivantes :

  • x86_64 (depuis Linux 3.18)
  • arm64 (depuis Linux 3.18)
  • s390 (depuis Linux 4.1)
  • ppc64 (depuis Linux 4.8)
  • sparc64 (depuis Linux 4.12)
  • mips64 (depuis Linux 4.13)
  • arm32 (depuis Linux 4.14)
  • x86_32 (depuis Linux 4.18)

Alors que les architectures suivantes disposent de cBPF, mais ne sont pas encore passées au support JIT eBPF :

  • ppc32
  • sparc32
  • mips32

L'ensemble d'instructions eBPF présente des principes sous-jacents similaires à ceux de cBPF, cependant, il est modélisé plus près de l'architecture sous-jacente afin de mieux imiter les ensembles d'instructions natifs dans le but d'atteindre de meilleures performances d'exécution. Il est conçu pour être JIT'é avec un mappage un à un, ce qui peut également ouvrir la possibilité aux compilateurs de générer du code eBPF optimisé via un backend eBPF qui fonctionne presque aussi vite que du code compilé nativement. Étant donné que LLVM fournit un tel backend eBPF, les programmes eBPF peuvent donc facilement être programmés dans un sous-ensemble du langage C. En dehors de cela, l'infrastructure eBPF est également dotée d'une structure appelée "maps". Les maps eBPF sont des stockages clé/valeur qui sont partagés entre plusieurs programmes eBPF, mais aussi entre les programmes eBPF et les applications en espace utilisateur.

Pour le sous-système de contrôle de trafic, les classifieurs et les actions qui peuvent être attachés aux qdiscs d'entrée et de sortie peuvent être écrits en eBPF ou cBPF. L'avantage par rapport aux autres classifieurs et actions est qu'eBPF/cBPF fournit le cadre générique, tandis que les utilisateurs peuvent implémenter leurs cas d'utilisation hautement spécialisés efficacement. Cela signifie que le classifieur ou l'action ainsi écrit ne souffrira pas d'un encombrement de fonctionnalités et pourra donc exécuter sa tâche de manière très efficace. Il permet une classification non linéaire et même la fusion de la partie action dans la classification. Combiné avec des structures de données eBPF map efficaces, l'espace utilisateur peut pousser de nouvelles politiques comme les classids dans le noyau sans recharger un classifieur, ou il peut collecter des statistiques qui sont poussées dans une map et en utiliser une autre pour équilibrer dynamiquement la charge en fonction de la charge déterminée, pour ne citer que quelques exemples.

PARAMETRES

object-file

pointe vers un fichier objet au format ELF (Executable and Linkable Format) contenant des opcodes eBPF et des définitions de maps eBPF. L'infrastructure du compilateur LLVM avec clang(1) comme frontend de langage C est un projet qui prend en charge l'émission de fichiers objets eBPF qui peuvent être passés au classifieur eBPF (plus de détails dans la section EXEMPLES). Cette option est obligatoire lorsqu'un classifieur ou une action eBPF doit être chargé.

section

est le nom de la section ELF du fichier objet, où se trouve le classifieur ou l'action eBPF. Par défaut, le nom de la section pour le classifieur est appelé "classifier", et pour l'action "action". Étant donné qu'un seul fichier objet peut contenir plusieurs classifieurs et actions, le nom de section correspondant doit être spécifié s'il diffère des valeurs par défaut.

export

pointe vers un fichier de socket de domaine Unix. Dans le cas où le fichier objet eBPF contient également une section nommée "maps" avec des spécifications de maps eBPF, les descripteurs de fichiers de map peuvent être transmis via le socket de domaine Unix à un "agent" eBPF qui gère tous les descripteurs après la durée de vie de tc. Il peut s'agir d'une application tierce implémentant le côté IPC pour l'importation, qui les utilise pour appeler l'appel système bpf(2) pour lire ou mettre à jour les données des maps eBPF depuis l'espace utilisateur, par exemple, à des fins de surveillance ou pour pousser de nouvelles politiques.

verbose

si défini, il affichera la sortie du vérificateur eBPF, même si le chargement du programme eBPF a réussi. Par défaut, le journal du vérificateur n'est émis à l'utilisateur qu'en cas d'erreur.

direct-action | da

indique au classifieur eBPF de ne pas invoquer d'actions TC externes, mais d'utiliser les codes de retour des actions TC ( TC_ACT_OK, TC_ACT_SHOT, etc.) pour les classifieurs.

skip_hw | skip_sw

indicateurs de contrôle de déchargement matériel. Par défaut, TC essaiera de décharger les filtres sur le matériel si possible. skip_hw désactive explicitement la tentative de déchargement. skip_sw force le déchargement et désactive l'exécution du programme eBPF dans le noyau. Si le déchargement matériel n'est pas possible et que cet indicateur a été défini, le noyau signalera une erreur et le filtre ne sera pas installé.

police

est un paramètre optionnel pour un classifieur eBPF/cBPF qui spécifie une police dans tc(1) qui est attachée au classifieur, par exemple, sur un qdisc d'entrée.

action

est un paramètre optionnel pour un classifieur eBPF/cBPF qui spécifie une action subséquente dans tc(1) qui est attachée à un classifieur.

classid

flowid

fournit l'identifiant de classe de contrôle de trafic par défaut pour ce classifieur eBPF/cBPF. L'identifiant de classe par défaut peut également être écrasé par le code de retour du programme eBPF/cBPF. Un code de retour par défaut de -1 spécifie que l'identifiant de classe par défaut fourni ici doit être utilisé. Un code de retour du programme eBPF/cBPF de 0 implique qu'aucun correspondance n'a eu lieu, et un code de retour différent de ces deux remplacera le classid par défaut. Cela permet une classification efficace et non linéaire avec un seul programme eBPF/cBPF au lieu de plusieurs programmes individuels pour divers identifiants de classe qui nécessiteraient une nouvelle analyse du contenu des paquets.

bytecode

Ce site n'est en aucun cas associé à Arch Linux ni affilié à ce projet. Le contenu est uniquement une traduction des pages de manuel d'Arch publiées sur man.archlinux.org.

a>

est utilisé pour charger uniquement le classificateur et les actions cBPF. Le code binaire cBPF est directement passé sous forme de chaîne de caractères sous la forme 's,c t f k,c t f k,c t f k,...' , où s représente le nombre de 4-tuples suivants. Un tel 4-tuple est composé de c t f k décimaux, où c représente l'opcode cBPF, t l'offset de saut vrai, f l'offset de saut faux et k la constante/littéral immédiat. Il existe divers outils qui génèrent du code dans ce format chargeable, par exemple, bpf_asm qui est fourni avec l'arborescence source du noyau Linux sous tools/net/ , il n'est donc certainement pas prévu de le modifier manuellement. L'option bytecode ou bytecode-file est obligatoire lorsqu'un classificateur ou une action cBPF doit être chargé.

bytecode-file

est également utilisé pour charger un classificateur ou une action cBPF. C'est essentiellement la même chose que bytecode, à la seule différence que le code binaire cBPF n'est pas passé directement via la ligne de commande, mais réside plutôt dans un fichier texte.

EXEMPLES

OUTILLAGE eBPF

Un exemple complet incluant le code de l'agent eBPF se trouve dans le paquet source d'iproute2 sous : examples/bpf/

Comme prérequis, le noyau doit avoir le système d'appels eBPF, à savoir bpf(2), activé et disposer des modules noyau cls_bpf et act_bpf pour le sous-système de contrôle de trafic. Pour activer le support eBPF/eBPF JIT, en fonction de ce que le processeur donné supporte :


echo 1 > /proc/sys/net/core/bpf_jit_enable

Un fichier C restreint donné peut être compilé via LLVM comme suit :


clang -O2 -emit-llvm -c bpf.c -o - | llc -march=bpf -filetype=obj -o bpf.o

L'invocation du compilateur pourrait encore être simplifiée à l'avenir, donc pour l'instant, il est très pratique de créer un alias pour cette construction d'une manière ou d'une autre, par exemple : 

__bcc() {
        clang -O2 -emit-llvm -c $1 -o - | \
        llc -march=bpf -filetype=obj -o "`basename $1 .c`.o"
}
alias bcc=__bcc

Une unité minimale et autonome, qui correspond à tout le trafic avec le classid par défaut (code de retour de -1), ressemble à ceci :


#include <linux/bpf.h>
#ifndef __section
# define __section(x)  __attribute__((section(x), used))
#endif
__section("classifier") int cls_main(struct __sk_buff *skb)
{
        return -1;
}
char __license[] __section("license") = "GPL";

Plus d'exemples peuvent être trouvés plus loin dans la sous-section PROGRAMMATION eBPF, car l'accent sera mis ici sur l'outillage.

Il peut y avoir diverses autres sections, par exemple, également pour les actions. Ainsi, un fichier objet en eBPF peut contenir plusieurs points d'entrée. Cependant, un point d'entrée spécifique doit toujours être spécifié lors de la configuration avec tc. Une licence doit faire partie du code C restreint et la syntaxe de la chaîne de licence est la même qu'avec les modules du noyau Linux. Le noyau se réserve le droit que certaines fonctions d'aide eBPF peuvent être restreintes aux licences compatibles GPL uniquement, et peut donc rejeter un programme du chargement dans le noyau lorsqu'un tel manque de licence survient.

Le fichier objet résultant de la compilation peut être inspecté avec l'ensemble habituel d'outils qui opèrent également sur des fichiers objets normaux, par exemple objdump(1) pour inspecter les en-têtes de section ELF :


objdump -h bpf.o
[...]

                CONTENTS, ALLOC, LOAD, RELOC, READONLY, CODE
4 action-mark   00000088  0000000000000000  0000000000000000  00000838  2**3
                CONTENTS, ALLOC, LOAD, RELOC, READONLY, CODE

                CONTENTS, ALLOC, LOAD, RELOC, READONLY, CODE

                CONTENTS, ALLOC, LOAD, DATA

Ajouter un classificateur eBPF à partir d'un fichier objet contenant un classificateur dans la section ELF par défaut est trivial (notez qu'au lieu de "object-file", des raccourcis tels que "obj" peuvent également être utilisés) :


bcc bpf.c
tc filter add dev em1 parent 1: bpf obj bpf.o flowid 1:1

Dans le cas où le classificateur réside dans la section ELF "mycls", alors la même commande doit être appelée comme suit :


tc filter add dev em1 parent 1: bpf obj bpf.o sec mycls flowid 1:1

Le vidage de la configuration du classificateur indiquera l'emplacement du classificateur, c'est-à-dire qu'il provient du fichier objet "bpf.o" sous la section "mycls" :


tc filter show dev em1
filter parent 1: protocol all pref 49152 bpf
filter parent 1: protocol all pref 49152 bpf handle 0x1 flowid 1:1 bpf.o:[mycls]

Le même programme peut également être installé du côté qdisc d'entrée par opposition à la sortie ...


tc qdisc add dev em1 handle ffff: ingress
tc filter add dev em1 parent ffff: bpf obj bpf.o sec mycls flowid ffff:1

... et à nouveau vidé à partir de là :


tc filter show dev em1 parent ffff:
filter protocol all pref 49152 bpf
filter protocol all pref 49152 bpf handle 0x1 flowid ffff:1 bpf.o:[mycls]

L'attachement d'un classificateur et d'une action à l'entrée a la restriction qu'il n'a pas de discipline de mise en file d'attente réelle. Ce que l'entrée peut faire est de classifier, manipuler, rediriger ou abandonner les paquets. Lorsqu'une mise en file d'attente est requise du côté de l'entrée, l'entrée doit rediriger les paquets vers le périphérique ifb, sinon la police peut être utilisée. De plus, l'entrée peut être utilisée pour avoir un point d'abandon précoce des paquets indésirables avant qu'ils n'atteignent les couches supérieures de la pile réseau, effectuer une comptabilité réseau avec des cartes eBPF qui pourraient être partagées avec la sortie, ou avoir un point de manipulation et/ou de redirection précoce vers différents périphériques réseau.

Plusieurs actions et classificateurs eBPF peuvent être placés dans un seul fichier objet au sein de diverses sections. Dans ce cas, les noms de sections non par défaut doivent être fournis, ce qui est le cas pour les deux actions dans cet exemple :


tc filter add dev em1 parent 1: bpf obj bpf.o flowid 1:1 \

action bpf obj bpf.o sec action-mark \
action bpf obj bpf.o sec action-rand ok

L'avantage est que le classificateur et les deux actions peuvent alors partager des cartes eBPF entre elles, si elles sont implémentées dans les programmes.

Afin d'accéder aux cartes eBPF depuis l'espace utilisateur au-delà de la durée de vie de la configuration tc(8), la propriété peut être transférée à un agent eBPF via des sockets de domaine Unix. Il existe deux possibilités pour implémenter cela :

1) Implémentation d'un propre agent eBPF qui s'occupe de la configuration du socket de domaine Unix et de l'implémentation du protocole que tc(8) dicte. Un exemple de code de ceci se trouve dans le paquet source d'iproute2 sous : examples/bpf/

2) Utilisation de tc exec pour transférer les descripteurs de fichiers de carte eBPF via un socket de domaine Unix, et pour lancer une application telle que sh(1). L'avantage de cette approche est que tc placera les descripteurs de fichiers dans l'environnement et les rendra ainsi disponibles, tout comme les descripteurs de fichiers stdin, stdout, stderr, ce qui signifie que dans le cas où des applications utilisateur s'exécutent à partir de ce shell propriétaire de fd, elles peuvent se terminer et redémarrer sans perdre les descripteurs de fichiers de cartes eBPF. Exemple d'invocation avec le mélange précédent de classificateur et d'action :


tc exec bpf imp /tmp/bpf
tc filter add dev em1 parent 1: bpf obj bpf.o exp /tmp/bpf flowid 1:1 \

action bpf obj bpf.o sec action-mark \
action bpf obj bpf.o sec action-rand ok

En supposant que les cartes eBPF soient partagées avec le classificateur et les actions, il suffit de les exporter une fois, par exemple, à partir de la commande du classificateur ou de l'action. tc configurera tous les descripteurs de fichiers de cartes eBPF au moment où le fichier objet est analysé pour la première fois.

Lorsqu'un shell est lancé, l'environnement contiendra quelques variables liées à eBPF. BPF_NUM_MAPS fournit le nombre total de cartes qui ont été transférées via le socket de domaine Unix. La valeur de BPF_MAP<X> est le numéro du descripteur de fichier qui peut être accédé dans les applications de l'agent eBPF, en d'autres termes, il peut être directement utilisé comme valeur de descripteur de fichier pour l'appel système bpf(2) pour récupérer ou modifier les valeurs des cartes eBPF. <X> désigne l'identifiant de la carte eBPF. Il correspond au membre id de struct bpf_elf_map de la spécification de carte eBPF de tc.

L'environnement dans cet exemple ressemble à ceci :


sh# env | grep BPF
    BPF_NUM_MAPS=3
    BPF_MAP1=6
    BPF_MAP0=5
    BPF_MAP2=7
sh# ls -la /proc/self/fd
    [...]
    lrwx------. 1 root root 64 Apr 14 16:46 5 -> anon_inode:bpf-map
    lrwx------. 1 root root 64 Apr 14 16:46 6 -> anon_inode:bpf-map
    lrwx------. 1 root root 64 Apr 14 16:46 7 -> anon_inode:bpf-map
sh# my_bpf_agent

Les agents eBPF sont très utiles car ils peuvent préremplir les cartes eBPF depuis l'espace utilisateur, surveiller les statistiques via les cartes et, en se basant sur ces retours, par exemple, réécrire les classids dans les valeurs des cartes eBPF pendant l'exécution. Étant donné que les agents eBPF sont implémentés comme des applications normales, ils peuvent également recevoir dynamiquement des politiques de contrôle de trafic de contrôleurs externes et ainsi les pousser dans les cartes eBPF pour s'adapter dynamiquement aux conditions du réseau. De plus, les cartes eBPF peuvent également être partagées avec d'autres types de programmes eBPF (par exemple, le traçage), une combinaison très puissante peut donc être implémentée.

NAME

tc-bpf - BPF packet classification and filtering

SYNOPSIS

tc [ OPTIONS ] filter add ... bpf [ PROG ]

tc [ OPTIONS ] action add ... bpf [ PROG ]

DESCRIPTION

BPF (Berkeley Packet Filter) is a technology that allows custom packet processing logic to be inserted into the network stack. Initially introduced for packet capture libraries like tcpdump(8), it has since evolved into a powerful mechanism for custom packet classification and mangling within the kernel.

The tc command exposes BPF programmability through the bpf keyword for both tc-filter(8) and tc-action(8). The primary advantage of using BPF within tc is its ability to execute complex packet matching and manipulation logic with near-native performance, as the BPF bytecode can be just-in-time (JIT) compiled into native machine code.

There are two main variants of BPF relevant here: classic BPF (cBPF) and extended BPF (eBPF). While cBPF is simpler, eBPF offers more features, better performance, and enhanced safety guarantees. For modern networking, eBPF is the recommended choice.

The general syntax for adding a BPF filter or action is:

tc filter add dev 
IFACE
 parent 
PARENT
 protocol 
PROTO
 prio 
PRIO
 bpf 
PROG

tc action add dev 
IFACE
 parent 
PARENT
 protocol 
PROTO
 prio 
PRIO
 bpf 
PROG

Where

PROG

can be either:

  • A filename containing BPF bytecode (e.g. bytecode-file).
  • A literal sequence of BPF opcodes (e.g. bytecode).
  • A C source file that will be compiled and loaded into the kernel (e.g. obj).

The following defines the return codes for classifiers:

  • TC_H_MAKESTORE(major, minor): Returns the classid that packet should be directed to. This is equivalent to returning a 32-bit integer where the upper 16 bits are the major handle and the lower 16 bits are the minor handle.
  • TC_H_INGRESS: Ingress traffic is classified using classid 1:. It is recommended to use this value for ingress classification.
  • 0: Packet is dropped.
  • -1: Packet is passed down to the next filter in the list. If this is the last filter, the packet is passed to the root qdisc.

The following defines the return codes for actions:

  • TC_ACT_OK (0): Terminates packet processing pipeline and allows the packet to proceed.
  • TC_ACT_SHOT (2): Terminates packet processing pipeline and drops the packet.
  • TC_ACT_UNSPEC (-1): Uses the default action configured from tc (similarly as returning -1 from a classifier).
  • TC_ACT_PIPE (3): Iterates to the next action, if available.
  • TC_ACT_RECLASSIFY (1): Terminates packet processing pipeline and reclassifies the packet from the beginning.
  • else: Everything else is an unspecified return code.

Both classifier and action return codes are supported in eBPF and cBPF programs.

To demonstrate restricted C syntax, a minimal toy classifier example is provided, which assumes that egress packets, for instance originating from a container, have previously been marked in interval [0, 255]. The program keeps statistics on different marks for user space and maps the classid to the root qdisc with the marking itself as the minor handle:

#include <stdint.h>
#include <asm/types.h>
#include <linux/bpf.h>
#include <linux/pkt_sched.h>
#include "helpers.h"
struct tuple {
        long packets;
        long bytes;
};
#define BPF_MAP_ID_STATS        1 /* agent's map identifier */
#define BPF_MAX_MARK            256
struct bpf_elf_map __section("maps") map_stats = {
        .type           =       BPF_MAP_TYPE_ARRAY,
        .id             =       BPF_MAP_ID_STATS,
        .size_key       =       sizeof(uint32_t),
        .size_value     =       sizeof(struct tuple),
        .max_elem       =       BPF_MAX_MARK,
        .pinning        =       PIN_GLOBAL_NS,
};
static inline void cls_update_stats(const struct __sk_buff *skb,
                                    uint32_t mark)
{
        struct tuple *tu;
        tu = bpf_map_lookup_elem(&map_stats, &mark);
        if (likely(tu)) {
                __sync_fetch_and_add(&tu->packets, 1);
                __sync_fetch_and_add(&tu->bytes, skb->len);
        }
}
__section("cls") int cls_main(struct __sk_buff *skb)
{
        uint32_t mark = skb->mark;
        if (unlikely(mark >= BPF_MAX_MARK))
                return 0;
        cls_update_stats(skb, mark);
        return TC_H_MAKE(TC_H_ROOT, mark);
}
char __license[] __section("license") = "GPL";

Another small example is a port redirector which demuxes destination port 80 into the interval [8080, 8087] steered by RSS, that can then be attached to ingress qdisc. The exercise of adding the egress counterpart and IPv6 support is left to the reader:

#include <asm/types.h>
#include <asm/byteorder.h>
#include <linux/bpf.h>
#include <linux/filter.h>
#include <linux/in.h>
#include <linux/if_ether.h>
#include <linux/ip.h>
#include <linux/tcp.h>
#include "helpers.h"
static inline void set_tcp_dport(struct __sk_buff *skb, int nh_off,
                                 __u16 old_port, __u16 new_port)
{
        bpf_l4_csum_replace(skb, nh_off + offsetof(struct tcphdr, check),
                            old_port, new_port, sizeof(new_port));
        bpf_skb_store_bytes(skb, nh_off + offsetof(struct tcphdr, dest),
                            &new_port, sizeof(new_port), 0);
}
static inline int lb_do_ipv4(struct __sk_buff *skb, int nh_off)
{
        __u16 dport, dport_new = 8080, off;
        __u8 ip_proto, ip_vl;
        ip_proto = load_byte(skb, nh_off +
                             offsetof(struct iphdr, protocol));
        if (ip_proto != IPPROTO_TCP)
                return 0;
        ip_vl = load_byte(skb, nh_off);
        if (likely(ip_vl == 0x45))
                nh_off += sizeof(struct iphdr);
        else
                nh_off += (ip_vl & 0xF) << 2;
        dport = load_half(skb, nh_off + offsetof(struct tcphdr, dest));
        if (dport != 80)
                return 0;
        off = skb->queue_mapping & 7;
        set_tcp_dport(skb, nh_off - BPF_LL_OFF, __constant_htons(80),
                      __cpu_to_be16(dport_new + off));
        return -1;
}
__section("lb") int lb_main(struct __sk_buff *skb)
{
        int ret = 0, nh_off = BPF_LL_OFF + ETH_HLEN;
        if (likely(skb->protocol == __constant_htons(ETH_P_IP)))
                ret = lb_do_ipv4(skb, nh_off);
        return ret;
}
char __license[] __section("license") = "GPL";

/* Object pinning settings */
#define PIN_NONE       0

/* ELF map definition */
struct bpf_elf_map {
    __u32 type;
    __u32 size_key;
    __u32 size_value;
    __u32 max_elem;
    __u32 flags;
    __u32 id;
    __u32 pinning;
    __u32 inner_id;
    __u32 inner_idx;
};
/* Some used BPF function calls. */
static int (*bpf_skb_store_bytes)(void *ctx, int off, void *from,
                                  int len, int flags) =
      (void *) BPF_FUNC_skb_store_bytes;
static int (*bpf_l4_csum_replace)(void *ctx, int off, int from,
                                  int to, int flags) =
      (void *) BPF_FUNC_l4_csum_replace;
static void *(*bpf_map_lookup_elem)(void *map, void *key) =
      (void *) BPF_FUNC_map_lookup_elem;
/* Some used BPF intrinsics. */
unsigned long long load_byte(void *skb, unsigned long long off)
    asm ("llvm.bpf.load.byte");
unsigned long long load_half(void *skb, unsigned long long off)
    asm ("llvm.bpf.load.half");

Best practice, we recommend to only have a single eBPF classifier loaded in tc and perform all necessary matching and mangling from there instead of a list of individual classifier and separate actions. Just a single classifier tailored for a given use-case will be most efficient to run.

eBPF DEBUGGING

Both tc filter and action commands for bpf support an optional verbose parameter that can be used to inspect the eBPF verifier log. It is dumped by default in case of an error.

In case the eBPF/cBPF JIT compiler has been enabled, it can also be instructed to emit a debug output of the resulting opcode image into the kernel log, which can be read via dmesg(1) :

echo 2 > /proc/sys/net/core/bpf_jit_enable

The Linux kernel source tree ships additionally under tools/net/ a small helper called bpf_jit_disasm that reads out the opcode image dump from the kernel log and dumps the resulting disassembly:

bpf_jit_disasm -o

Other than that, the Linux kernel also contains an extensive eBPF/cBPF test suite module called test_bpf . Upon ...

modprobe test_bpf

... it performs a diversity of test cases and dumps the results into the kernel log that can be inspected with dmesg(1) . The results can differ depending on whether the JIT compiler is enabled or not. In case of failed test cases, the module will fail to load. In such cases, we urge you to file a bug report to the related JIT authors, Linux kernel and networking mailing lists.

cBPF

Although we generally recommend switching to implementing eBPF classifier and actions, for the sake of completeness, a few words on how to program in cBPF will be lost here.

Likewise, the bpf_jit_enable switch can be enabled as mentioned already. Tooling such as bpf_jit_disasm is also independent whether eBPF or cBPF code is being loaded.

Unlike in eBPF, classifier and action are not implemented in restricted C, but rather in a minimal assembler-like language or with the help of other tooling.

The raw interface with tc takes opcodes directly. For example, the most minimal classifier matching on every packet resulting in the default classid of 1:1 looks like:

tc filter add dev em1 parent 1: bpf bytecode '1,6 0 0 4294967295,' flowid
    1:1

The first decimal of the bytecode sequence denotes the number of subsequent 4-tuples of cBPF opcodes. As mentioned, such a 4-tuple consists of c t f k decimals, where c represents the cBPF opcode, t the jump true offset target, f the jump false offset target and k the immediate constant/literal. Here, this denotes an unconditional return from the program with immediate value of -1.

Thus, for egress classification, Willem de Bruijn implemented a minimal stand-alone helper tool under the GNU General Public License version 2 for iptables(8) BPF extension, which abuses the libpcap internal classic BPF compiler, his code derived here for usage with tc(8) :

#include <pcap.h>
#include <stdio.h>
int main(int argc, char **argv)
{
        struct bpf_program prog;
        struct bpf_insn *ins;
        int i, ret, dlt = DLT_RAW;
        if (argc < 2 || argc > 3)
                return 1;
        if (argc == 3) {
                dlt = pcap_datalink_name_to_val(argv[1]);
                if (dlt == -1)
                        return 1;
        }
        ret = pcap_compile_nopcap(-1, dlt, &prog, argv[argc - 1],
                                  1, PCAP_NETMASK_UNKNOWN);
        if (ret)
                return 1;
        printf("%d,", prog.bf_len);
        ins = prog.bf_insns;
        for (i = 0; i < prog.bf_len - 1; ++ins, ++i)
                printf("%u %u %u %u,", ins->code,
                       ins->jt, ins->jf, ins->k);
        printf("%u %u %u %u",
               ins->code, ins->jt, ins->jf, ins->k);
        pcap_freecode(&prog);
        return 0;
}

Given this small helper, any tcpdump(8) filter expression can be abused as a classifier where a match will result in the default classid:

bpftool EN10MB 'tcp[tcpflags] & tcp-syn != 0' > /var/bpf/tcp-syn
tc filter add dev em1 parent 1: bpf bytecode-file /var/bpf/tcp-syn flowid
    1:1

Basically, such a minimal generator is equivalent to:

tcpdump -iem1 -ddd 'tcp[tcpflags] & tcp-syn != 0' | tr '  ','
    > /var/bpf/tcp-syn

Since libpcap does not support all Linux' specific cBPF extensions in its compiler, the Linux kernel also ship

sous tools/net/ un assembleur BPF minimal appelé bpf_asm pour permettre un contrôle total. Pour une syntaxe et une sémantique détaillées sur l'implémentation manuelle de tels programmes, voir les références sous LIRE AUSSI .

Exemple trivial dans bpf_asm pour classifier les paquets IPv4/TCP , sauvegardé dans un fichier texte appelé foobar :


ldh [12]
jne #0x800, drop
ldb [23]
jneq #6, drop
ret #-1
drop: ret #0

De même, un tel classificateur peut être chargé comme suit :


bpf_asm foobar > /var/bpf/tcp-syn
tc filter add dev em1 parent 1: bpf bytecode-file /var/bpf/tcp-syn flowid 1:1

Pour les classificateurs BPF, le noyau Linux fournit en outre sous tools/net/ un petit débogueur BPF appelé bpf_dbg , qui peut être utilisé pour tester un classificateur sur des fichiers pcap, effectuer un pas à pas ou ajouter divers points d'arrêt dans le programme classificateur et afficher le contenu des registres pendant l'exécution.

L'implémentation d'une action en BPF classique est plutôt limitée dans le sens où la manipulation de paquets n'est pas prise en charge. Par conséquent, il est généralement recommandé de passer à eBPF, lorsque cela est possible.
