tcl_wordchars(n)

Paquet: tcl

Licences: TCL

tclvars(n) Commandes intégrées Tcl tclvars(n)

NOM

argc, argv, argv0, auto_path, env, errorCode, errorInfo, tcl_interactive, tcl_library, tcl_nonwordchars, tcl_patchLevel, tcl_pkgPath, tcl_platform, tcl_precision, tcl_rcFileName, tcl_traceCompile, tcl_traceExec, tcl_wordchars, tcl_version - Variables utilisées par Tcl

DESCRIPTION

Les variables globales suivantes sont créées et gérées automatiquement par la bibliothèque Tcl. Sauf indication contraire ci-dessous, ces variables doivent normalement être considérées comme étant en lecture seule par le code spécifique à l'application et par les utilisateurs.

auto_path
Si elle est définie, elle doit contenir une liste Tcl valide donnant les répertoires à rechercher lors des opérations d'auto-chargement (y compris pour les fichiers d'index de paquets lors de l'utilisation du gestionnaire par défaut package unknown). Cette variable est initialisée au démarrage pour contenir, dans l'ordre : les répertoires listés dans la variable d'environnement TCLLIBPATH, le répertoire nommé par la variable globale tcl_library, le répertoire parent de tcl_library, [file dirname [file dirname [info nameofexecutable]]]/lib, les répertoires listés dans la variable tcl_pkgPath. Des emplacements supplémentaires pour rechercher des fichiers et des index de paquets doivent normalement être ajoutés à cette variable à l'aide de lappend.

D'autres variables relatives à la gestion des paquets existent. Plus de détails sont listés dans la section VARIABLES de la page de manuel library.

env
Cette variable est maintenue par Tcl comme un tableau dont les éléments sont les variables d'environnement du processus. La lecture d'un élément retournera la valeur de la variable d'environnement correspondante. La définition d'un élément du tableau modifiera la variable d'environnement correspondante ou en créera une nouvelle si elle n'existe pas déjà. La désinstallation d'un élément de env supprimera la variable d'environnement correspondante. Les modifications apportées au tableau env affecteront l'environnement passé aux enfants par des commandes comme exec. Si le tableau env dans son intégralité est désinstallé, Tcl cessera de surveiller les accès à env et ne mettra pas à jour les variables d'environnement.

Sous Windows, les variables d'environnement PATH et COMSPEC, quelle que soit leur capitalisation, sont automatiquement converties en majuscules. Par exemple, la variable PATH peut être exportée par le système d'exploitation sous les formes « path », « Path », « PaTh », etc., obligeant le code Tcl, autrement simple, à prendre en charge de nombreux cas particuliers. Toutes les autres variables d'environnement héritées par Tcl restent inchangées. Définir une variable du tableau env à une chaîne vide équivaut à la désinstaller, car c'est le comportement du système d'exploitation Windows sous-jacent. Il convient de noter que s'appuyer sur une variable d'environnement existante et vide ne fonctionnera pas sous Windows et est déconseillé pour une utilisation multiplateforme.

Les éléments suivants de env sont spéciaux pour Tcl :

env(HOME)
Cette variable d'environnement, si elle est définie, donne l'emplacement du répertoire considéré comme le répertoire personnel de l'utilisateur actuel, et vers lequel un appel à cd sans arguments ou avec seulement « ~ » comme argument se déplacera. La plupart des plateformes la définissent correctement par défaut ; elle n'a normalement pas besoin d'être définie par le code utilisateur.
env(TCL_LIBRARY)
Si elle est définie, elle spécifie l'emplacement du répertoire contenant les scripts de bibliothèque (la valeur de cette variable sera assignée à la variable tcl_library et sera donc retournée par la commande info library). Si cette variable n'est pas définie, une valeur par défaut est utilisée.

Notez que cette variable d'environnement ne doit *pas* normalement être définie.

env(TCLLIBPATH)
Si elle est définie, elle doit contenir une liste Tcl valide donnant les répertoires à rechercher lors des opérations d'auto-chargement. Les répertoires doivent être spécifiés au format Tcl, en utilisant « / » comme séparateur de chemin, quelle que soit la plateforme. Cette variable n'est utilisée que lors de l'initialisation de la variable auto_path.
env(TCL_TZ), env(TZ)
Celles-ci spécifient le fuseau horaire par défaut utilisé pour l'analyse et le formatage des heures et des dates dans la commande clock. Sur de nombreuses plateformes, la variable d'environnement TZ est configurée par le système d'exploitation.
env(LC_ALL), env(LC_MESSAGES), env(LANG)
Ces variables d'environnement sont utilisées par le paquet msgcat pour déterminer quelle locale utiliser pour le formatage des messages.
env(TCL_INTERP_DEBUG_FRAME)
Si elle existe, elle a le même effet que l'exécution de interp debug {} -frame 1 comme toute première commande de chaque nouvel interpréteur Tcl.
errorCode
Cette variable contient la valeur de l'option de retour -errorcode définie par la dernière erreur survenue dans cet interpréteur. Cette valeur de liste représente des informations supplémentaires sur l'erreur sous une forme facile à traiter par des programmes. Le premier élément de la liste identifie une classe générale d'erreurs et détermine le format du reste de la liste. Les formats suivants pour les options de retour -errorcode sont utilisés par le noyau Tcl ; les applications individuelles peuvent définir des formats supplémentaires.
ARITH code msg
Ce format est utilisé lorsqu'une erreur arithmétique se produit (par exemple, une tentative de division de zéro par zéro dans la commande expr). Code identifie l'erreur précise et msg fournit une description lisible par l'homme de l'erreur. Code sera soit DIVZERO (pour une tentative de division par zéro), DOMAIN (si un argument est en dehors du domaine d'une fonction, comme acos(-3)), IOVERFLOW (pour un débordement d'entier), OVERFLOW (pour un débordement en virgule flottante), soit UNKNOWN (si la cause de l'erreur ne peut être déterminée).

La détection de ces erreurs dépend en partie du matériel sous-jacent et des bibliothèques système.

CHILDKILLED pid sigName msg
Ce format est utilisé lorsqu'un processus enfant a été tué à cause d'un signal. L'élément pid sera l'identifiant du processus (en décimal). L'élément sigName sera le nom symbolique du signal qui a provoqué la terminaison du processus ; ce sera l'un des noms du fichier d'inclusion signal.h, tel que SIGPIPE. L'élément msg sera un court message lisible par l'homme décrivant le signal, tel que « write on pipe with no readers » pour SIGPIPE.
CHILDSTATUS pid code
Ce format est utilisé lorsqu'un processus enfant s'est terminé avec un code de sortie non nul. L'élément pid sera l'identifiant du processus (en décimal) et l'élément code sera le code de sortie renvoyé par le processus (également en décimal).
CHILDSUSP pid sigName msg
Ce format est utilisé lorsqu'un processus enfant a été suspendu à cause d'un signal. L'élément pid sera l'identifiant du processus, en décimal. L'élément sigName sera le nom symbolique du signal qui a provoqué la suspension du processus ; ce sera l'un des noms du fichier d'inclusion signal.h, tel que SIGTTIN. L'élément msg sera un court message lisible par l'homme décrivant le signal, tel que « background tty read » pour SIGTTIN.
NONE
Ce format est utilisé pour les erreurs pour lesquelles aucune information supplémentaire n'est disponible, à part le message renvoyé avec l'erreur. Dans ces cas, l'option de retour -errorcode consistera en une liste contenant un seul élément dont le contenu est NONE.
POSIX errName msg
Si le premier élément est POSIX, alors l'erreur s'est produite lors d'un appel noyau POSIX. L'élément errName contiendra le nom symbolique de l'erreur survenue, tel que ENOENT ; ce sera l'une des valeurs définies dans le fichier d'inclusion errno.h. L'élément msg

TCL ...
Indique une sorte de problème généré en relation avec Tcl lui-même, par exemple un échec de recherche d'un canal ou d'une variable.

Pour définir l'option de retour -errorcode, les applications doivent utiliser des procédures de bibliothèque telles que Tcl_SetObjErrorCode, Tcl_SetReturnOptions et Tcl_PosixError, ou elles peuvent invoquer l'option -errorcode de la commande return. Si aucune de ces méthodes de définition du code d'erreur n'a été utilisée, l'interpréteur Tcl réinitialisera la variable à NONE après la prochaine erreur.

errorInfo
Cette variable contient la valeur de l'option de retour -errorinfo définie par la dernière erreur survenue dans cet interpréteur. Cette chaîne de caractères contiendra une ou plusieurs lignes identifiant les commandes et procédures Tcl qui étaient en cours d'exécution lors de la dernière erreur. Son contenu prend la forme d'une trace de pile montrant les différentes commandes Tcl imbriquées qui avaient été appelées au moment de l'erreur.
tcl_library
Cette variable contient le nom d'un répertoire contenant la bibliothèque système de scripts Tcl, tels que ceux utilisés pour le chargement automatique. La valeur de cette variable est renvoyée par la commande info library. Voir l'entrée de manuel library pour les détails des installations fournies par la bibliothèque de scripts Tcl. Normalement, chaque application ou paquet aura sa propre bibliothèque de scripts spécifique en plus de la bibliothèque Tcl ; chaque application devrait définir une variable globale nommée comme $app_library (où app est le nom de l'application) pour contenir le nom du fichier réseau du répertoire de la bibliothèque de cette application. La valeur initiale de tcl_library est définie lors de la création d'un interpréteur en recherchant plusieurs répertoires différents jusqu'à en trouver un qui contient un script de démarrage Tcl approprié. Si la variable d'environnement TCL_LIBRARY existe, alors le répertoire qu'elle nomme est vérifié en premier. Si TCL_LIBRARY n'est pas définie ou ne pointe pas vers un répertoire approprié, Tcl vérifie plusieurs autres répertoires en fonction d'un emplacement par défaut compilé, de l'emplacement du binaire contenant l'application et du répertoire de travail actuel.
tcl_patchLevel
Lors de la création d'un interpréteur, Tcl initialise cette variable pour contenir une chaîne indiquant le niveau de correctif actuel pour Tcl, tel que 8.4.16 pour Tcl 8.4 avec les seize premiers correctifs officiels, ou 8.5b3 pour la troisième version bêta de Tcl 8.5. La valeur de cette variable est renvoyée par la commande info patchlevel.
tcl_pkgPath
Cette variable contient une liste de répertoires indiquant où les paquets sont normalement installés. Elle n'est pas utilisée sous Windows. Elle contient généralement une ou deux entrées ; si elle contient deux entrées, la première est normalement un répertoire pour les paquets dépendant de la plateforme (par exemple, les binaires de bibliothèques partagées) et la seconde est normalement un répertoire pour les paquets indépendants de la plateforme (par exemple, les fichiers de scripts). Typiquement, un paquet est installé comme un sous-répertoire de l'une des entrées de la variable tcl_pkgPath. Les répertoires de la variable tcl_pkgPath sont inclus par défaut dans la variable auto_path, de sorte qu'ils et leurs sous-répertoires immédiats sont automatiquement recherchés pour les paquets lors des commandes package require. Remarque : tcl_pkgPath n'est pas destiné à être modifié par l'application. Sa valeur est ajoutée à auto_path au démarrage ; les modifications apportées à tcl_pkgPath ne se reflètent pas dans auto_path. Si vous souhaitez que Tcl recherche des répertoires supplémentaires pour les paquets, vous devriez ajouter les noms de ces répertoires à auto_path, et non à tcl_pkgPath.
tcl_platform
Il s'agit d'un tableau associatif dont les éléments contiennent des informations sur la plateforme sur laquelle l'application s'exécute, telles que le nom du système d'exploitation, son numéro de version actuel et le jeu d'instructions de la machine. Les éléments listés ci-dessous seront toujours définis, mais ils peuvent avoir des chaînes vides comme valeurs si Tcl n'a pas pu récupérer d'informations pertinentes. De plus, les extensions et les applications peuvent ajouter des valeurs supplémentaires au tableau. Les éléments prédéfinis sont :
byteOrder
L'ordre des octets natif de cette machine : soit littleEndian, soit bigEndian.
debug
Si cette variable existe, alors l'interpréteur a été compilé avec et lié à un environnement d'exécution C prenant en charge le débogage. Cette variable n'existera que sous Windows, afin que les auteurs d'extensions puissent spécifier quel paquet charger en fonction de la bibliothèque d'exécution C utilisée. Ceci n'indique pas que ce noyau contient des symboles.
engine
Le nom de l'implémentation du langage Tcl. Lorsque l'interpréteur est créé pour la première fois, il est toujours défini sur la chaîne Tcl.
machine
Le jeu d'instructions exécuté par cette machine, tel que intel, PPC, 68k ou sun4m. Sur les machines UNIX, il s'agit de la valeur renvoyée par uname -m.
os
Le nom du système d'exploitation exécuté sur cette machine, tel que Windows NT ou SunOS. Sur les machines UNIX, il s'agit de la valeur renvoyée par uname -s.
osVersion
Le numéro de version du système d'exploitation exécuté sur cette machine. Sur les machines UNIX, il s'agit de la valeur renvoyée par uname -r.
pathSeparator
Le caractère qui doit être utilisé pour diviser les variables d'environnement de type PATH en leur liste correspondante de noms de répertoires.
platform
Soit windows, soit unix. Ceci identifie l'environnement d'exploitation général de la machine.
pointerSize
Donne la taille du pointeur natif de la machine en octets (strictement, c'est la même chose que le résultat de l'évaluation de sizeof(void*) en C).
threaded
Si cette variable existe, alors l'interpréteur a été compilé avec le support des threads.
user
Ceci identifie l'utilisateur actuel en fonction des informations de connexion disponibles sur la plateforme. Cette valeur provient des appels système getuid() et getpwuid() sur Unix, et de la valeur de l'appel système GetUserName() sous Windows.
wordSize
Donne la taille du mot natif de la machine en octets (strictement, c'est la même chose que le résultat de l'évaluation de sizeof(long) en C).
tcl_precision
Cette variable contrôle le nombre de chiffres à générer lors de la conversion de valeurs à virgule flottante en chaînes. Elle est initialisée à 0. Les applications ne doivent pas modifier cette valeur ; elle est fournie pour assurer la compatibilité avec du code hérité.
La valeur par défaut de 0 est spéciale, signifiant que Tcl doit convertir les nombres en utilisant le moins de chiffres possible tout en distinguant tout nombre à virgule flottante de ses voisins les plus proches. Elle diffère de l'utilisation d'une valeur arbitrairement élevée pour tcl_precision en ce sens qu'un nombre inexact comme 1.4 sera converti en 1.4 plutôt qu'en 1.3999999999999999, même si ce dernier est plus proche de la valeur exacte du nombre binaire.
Si tcl_precision n'est pas zéro, alors lorsque Tcl convertit un nombre à virgule flottante, il crée une représentation décimale d'au plus tcl_precision chiffres significatifs ; le résultat peut être plus court si le résultat plus court représente le nombre original exactement. Si aucun résultat d'au plus tcl_precision chiffres n'est une représentation exacte du nombre original, celui qui est le plus proche du nombre original est choisi. Si le nombre original se situe précisément entre deux représentations décimales de précision égale, alors celle qui a une valeur paire pour le chiffre le moins significatif est choisie ; par exemple, si tcl_precision est 3, alors 0.3125 sera converti en 0.312, et non en 0.313, tandis que 0.6875 sera converti en 0.688, et non en 0.687. Toute chaîne de zéros de fin qui subsiste est tronquée.
Une valeur de tcl_precision de 17 chiffres est « parfaite » pour la virgule flottante IEEE en ce sens qu'elle permet aux valeurs en double précision d'être converties en chaînes puis reconverties en binaire sans perte d'information. Pour cette raison, vous la verrez souvent comme une valeur dans du code hérité qui doit s'exécuter sur des versions de Tcl antérieures à 8.5. Elle n'est plus recommandée ; comme indiqué ci-dessus, une valeur zéro est la méthode préférée.
Tous les interpréteurs d'un thread partagent une seule valeur tcl_precision : la modifier dans un interpréteur affectera également tous les autres interpréteurs. Les interpréteurs sécurisés ne sont pas autorisés à modifier la variable.
Les valeurs valides pour tcl_precision vont de 0 à 17.
tcl_rcFileName
Cette variable est utilisée lors de l'initialisation pour indiquer le nom d'un fichier de démarrage spécifique à l'utilisateur. Si elle est définie par une initialisation spécifique à l'application, le code de démarrage Tcl vérifiera l'existence de ce fichier et le sourcera s'il existe. Par exemple, pour wish, la variable est définie sur ~/.wishrc pour Unix et ~/wishrc.tcl pour Windows.
tcl_traceCompile
La valeur de cette variable peut être définie pour contrôler la quantité d'informations de traçage affichées lors de la compilation en bytecode. Par défaut, tcl_traceCompile est zéro et aucune information n'est affichée. Définir tcl_traceCompile à 1 génère un résumé sur une seule ligne dans stdout chaque fois qu'une procédure ou une commande de haut niveau est compilée. La définir à 2 génère une liste détaillée dans stdout des instructions de bytecode émises lors de chaque compilation. Cette variable est utile pour traquer les problèmes suspectés avec le compilateur Tcl.
Cette variable et sa fonctionnalité n'existent que si TCL_COMPILE_DEBUG a été défini lors de la compilation de Tcl.
tcl_traceExec
La valeur de cette variable peut être définie pour contrôler la quantité d'informations de traçage affichées pendant l'exécution du bytecode. Par défaut, tcl_traceExec est à zéro et aucune information n'est affichée. Définir tcl_traceExec à 1 génère une trace d'une ligne sur stdout à chaque appel d'une procédure Tcl. La définir à 2 génère une ligne de sortie chaque fois qu'une commande Tcl est invoquée, contenant le nom de la commande et ses arguments. La définir à 3 produit une trace détaillée montrant le résultat de l'exécution de chaque instruction de bytecode. Notez que lorsque tcl_traceExec vaut 2 ou 3, les commandes telles que set et incr qui ont été entièrement remplacées par une séquence d'instructions de bytecode ne sont pas affichées. La définition de cette variable est utile pour traquer les problèmes suspects avec le compilateur et l'interpréteur de bytecode.
Cette variable et sa fonctionnalité n'existent que si TCL_COMPILE_DEBUG a été défini lors de la compilation de Tcl.
tcl_wordchars
La valeur de cette variable est une expression régulière qui peut être définie pour contrôler quels caractères sont considérés comme des caractères de « mot », par exemple pour la sélection d'un mot par double-clic dans le texte Tk. Elle dépend de la plateforme. Sous Windows, elle vaut par défaut \S, ce qui signifie tout ce qui n'est pas un espace Unicode. Sinon, elle vaut par défaut \w, qui correspond à tout caractère de mot Unicode (chiffre, lettre ou soulignement).
tcl_nonwordchars
La valeur de cette variable est une expression régulière qui peut être définie pour contrôler quels caractères sont considérés comme des « non-mots », par exemple pour la sélection d'un mot par double-clic dans le texte Tk. Elle dépend de la plateforme. Sous Windows, elle vaut par défaut \s, ce qui signifie tout espace Unicode. Sinon, elle vaut par défaut \W, qui correspond à tout ce qui n'est pas un caractère de mot Unicode (chiffre, lettre ou soulignement).
tcl_version
Lorsqu'un interpréteur est créé, Tcl initialise cette variable pour contenir le numéro de version de cette version de Tcl sous la forme x.y. Les changements de x représentent des changements majeurs avec des incompatibilités probables, et les changements de y représentent de petites améliorations et corrections de bugs qui conservent la compatibilité ascendante. La valeur de cette variable est retournée par la commande info tclversion.

AUTRES VARIABLES GLOBALES

Les variables suivantes sont garanties d'exister uniquement dans les exécutables tclsh et wish ; la bibliothèque Tcl ne les définit pas elle-même, mais de nombreux environnements Tcl le font.

argc
Le nombre d'arguments passés à tclsh ou wish.
argv
Liste Tcl des arguments passés à tclsh ou wish.
argv0
Le script que tclsh ou wish a commencé à exécuter (s'il a été spécifié) ou sinon le nom par lequel tclsh ou wish a été invoqué.
tcl_interactive
Contient 1 si tclsh ou wish s'exécute de manière interactive (aucun script n'a été spécifié et l'entrée standard est un périphérique de type terminal), 0 sinon.

EXEMPLES

Pour ajouter un répertoire à la collection d'emplacements recherchés par package require, par exemple, en raison de certains packages spécifiques à l'application utilisés, la variable auto_path doit être mise à jour :

lappend ::auto_path [file join [pwd] "theLibDir"]

Une manière simple, bien que peu robuste, de gérer les arguments de ligne de commande de la forme « -foo 1 -bar 2 » consiste à les charger dans un tableau après avoir d'abord chargé les paramètres par défaut :

array set arguments {-foo 0 -bar 0 -grill 0}
array set arguments $::argv
puts "foo is $arguments(-foo)"
puts "bar is $arguments(-bar)"
puts "grill is $arguments(-grill)"

La variable globale argv0 peut être utilisée (en conjonction avec la commande info script) pour déterminer si le script actuel est exécuté comme script principal ou chargé comme bibliothèque. Ceci est utile car cela permet à un seul script d'être utilisé à la fois comme bibliothèque et comme démonstration de cette bibliothèque :

if {$::argv0 eq [info script]} {
    # exécution comme : tclsh example.tcl
} else {
    package provide Example 1.0
}
