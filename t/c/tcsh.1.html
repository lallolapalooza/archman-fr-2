TCSH(1) Manuel des commandes générales TCSH(1)

NOM

tcsh — Shell C avec complétion de noms de fichiers et édition de ligne de commande

SYNTAXE

tcsh [-bcdefFimnqstvVxX] [-Dnom[=valeur]] [arg] ...

tcsh -l

DESCRIPTION

tcsh est une version améliorée mais complètement compatible du shell C de Berkeley UNIX, csh(1). C'est un interpréteur de langage de commande utilisable à la fois comme shell de connexion interactif et comme processeur de commandes de scripts shell. Il comprend un éditeur de ligne de commande (voir L'éditeur de ligne de commande (+)), la complétion programmable de mots (voir Complétion et listage (+)), la correction orthographique (voir Correction orthographique (+)), un mécanisme d'historique (voir Substitution d'historique), le contrôle de jobs (voir Jobs) et une syntaxe semblable au C. La section NOUVELLES FONCTIONNALITÉS (+) décrit les améliorations majeures de tcsh par rapport à csh(1). Tout au long de ce manuel, les fonctionnalités de tcsh qui ne se trouvent pas dans la plupart des implémentations de csh(1) (spécifiquement, le csh(1) de 4.4BSD) sont étiquetées avec ‘(+)’, et les fonctionnalités présentes dans csh(1) mais généralement non documentées sont étiquetées avec ‘(u)’.

Traitement de la liste d'arguments

Si le premier argument (argument 0) du shell est ‘-’, alors c'est un shell de connexion. Un shell de connexion peut également être spécifié en invoquant le shell avec le flag -l comme unique argument.

Les autres arguments de flag sont interprétés comme suit :

-b
Force une “coupure” dans le traitement des options, faisant que tous les arguments suivants soient traités comme des arguments non-options. Les arguments restants ne seront pas interprétés comme des options du shell. Ceci peut être utilisé pour passer des options à un script shell sans confusion ni possible subterfuge. Le shell n'exécutera pas un script set-user ID sans cette option.
-c
Les commandes sont lues à partir de l'argument suivant (qui doit être présent et doit être un seul argument), stockées dans la variable shell command pour référence, et exécutées. Tous les arguments restants sont placés dans la variable shell argv.
-d
Le shell charge la pile de répertoires depuis ~/.cshdirs comme décrit sous Démarrage et arrêt, qu'il s'agisse ou non d'un shell de connexion. (+)
-Dnom[=valeur]
Définit la variable d'environnement nom à valeur. (Uniquement Domain/OS) (+)
-e
Le shell se termine si une commande invoquée se termine anormalement ou produit un statut de sortie non nul.
-f
Le shell ne charge aucun fichier de ressources ou de démarrage, ni n'effectue de mise en cache des commandes, et démarre donc plus rapidement.
-F
Le shell utilise fork(2) au lieu de vfork(2) pour lancer les processus. (+)
-i
Le shell est interactif et demande son entrée de haut niveau, même s'il ne semble pas s'agir d'un terminal. Les shells sont interactifs sans cette option si leurs entrées et sorties sont des terminaux.
-l
Le shell est un shell de connexion. Applicable uniquement si -l est le seul flag spécifié.
-m
Le shell charge ~/.tcshrc même s'il n'appartient pas à l'utilisateur effectif. Les versions plus récentes de su(1) peuvent passer -m au shell. (+)
-n
Le shell analyse les commandes mais ne les exécute pas. Ceci aide à déboguer les scripts shell.
-q
Le shell accepte SIGQUIT (voir Gestion des signaux) et se comporte lorsqu'il est utilisé sous un débogueur. Le contrôle de jobs est désactivé. (u)
-s
L'entrée des commandes est prise depuis l'entrée standard.
-t
Le shell lit et exécute une seule ligne d'entrée. Un ‘\’ peut être utilisé pour échapper le saut de ligne à la fin de cette ligne et continuer sur une autre ligne.
-v
Définit la variable shell verbose, de sorte que l'entrée des commandes soit affichée après la substitution d'historique.
-x
Définit la variable shell echo, de sorte que les commandes soient affichées immédiatement avant leur exécution.
-V
Définit la variable shell verbose même avant l'exécution de ~/.tcshrc.
-X
Est à -x ce que -V est à -v.
--aide
Affiche un message d'aide sur la sortie standard et quitte. (+)
--version
Affiche la version/plateforme/options de compilation sur la sortie standard et quitte. Ces informations sont également contenues dans la variable shell version. (+)

Après le traitement des arguments de flag, s'il reste des arguments mais qu'aucun des options -c, -i, -s, ou -t n'a été donné, le premier argument est considéré comme le nom d'un fichier de commandes, ou de “script”, à exécuter. Le shell ouvre ce fichier et sauvegarde son nom pour une éventuelle resubstitution par ‘$0’. Étant donné que de nombreux systèmes utilisent soit le shell standard version 6, soit version 7, dont les scripts shell ne sont pas compatibles avec ce shell, le shell utilise un tel shell “standard” pour exécuter un script dont le premier caractère n'est pas un ‘#’, c'est-à-dire qui ne commence pas par un commentaire.

Les arguments restants sont placés dans la variable shell argv.

Démarrage et arrêt

Un shell de connexion commence par exécuter les commandes des fichiers système /etc/csh.cshrc et /etc/csh.login. Il exécute ensuite les commandes des fichiers dans le répertoire home de l'utilisateur : d'abord ~/.tcshrc (+) ou, si ~/.tcshrc n'est pas trouvé, ~/.cshrc, puis le contenu de ~/.history (ou la valeur de la variable shell histfile) est chargé en mémoire, puis ~/.login, et enfin ~/.cshdirs (ou la valeur de la variable shell dirsfile) (+). Le shell peut lire /etc/csh.login avant et non après /etc/csh.cshrc, et ~/.login

n> avant au lieu d'après ~/.tcshrc ou ~/.cshrc et ~/.history, si compilé ; voir la variable shell version. (+)

Les shells non-connexion ne lisent que /etc/csh.cshrc et ~/.tcshrc ou ~/.cshrc au démarrage.

Pour des exemples de fichiers de démarrage, veuillez consulter : http://tcshrc.sourceforge.net

Des commandes comme stty(1) et tset(1), qui doivent être exécutées une seule fois par connexion, vont généralement dans le fichier ~/.login. Les utilisateurs qui ont besoin d'utiliser le même ensemble de fichiers avec csh(1) et tcsh peuvent n'avoir qu'un ~/.cshrc qui vérifie l'existence de la variable shell tcsh avant d'utiliser des commandes spécifiques à tcsh, ou peuvent avoir à la fois un ~/.cshrc et un ~/.tcshrc qui source (voir la commande intégrée) ~/.cshrc. Le reste de ce manuel utilise ~/.tcshrc pour signifier ~/.tcshrc ou, si ~/.tcshrc n'est pas trouvé, ~/.cshrc.

Dans le cas normal, le shell commence à lire les commandes depuis le terminal, en affichant l'invite

> 

(Le traitement des arguments et l'utilisation du shell pour traiter les fichiers contenant des scripts de commandes sont décrits plus loin.) Le shell lit de manière répétée une ligne d'entrée de commande, la divise en mots, la place dans la liste d'historique des commandes, l'analyse et exécute chaque commande de la ligne.

On peut se déconnecter en tapant ^D sur une ligne vide, en tapant logout ou login, ou via le mécanisme de déconnexion automatique du shell (voir la variable shell autologout). Lorsqu'un shell de connexion se termine, il définit la variable shell logout à ‘normal’ ou ‘automatic’ selon le cas, puis exécute les commandes des fichiers /etc/csh.logout et ~/.logout. Le shell peut désactiver DTR lors de la déconnexion s'il est compilé ainsi ; voir la variable shell version.

Les noms des fichiers de connexion et de déconnexion système varient d'un système à l'autre pour assurer la compatibilité avec différentes variantes de csh(1) ; voir FICHIERS.

Édition

Nous décrivons d'abord l'éditeur de ligne de commande (+). Les sections Complétion et affichage (+) et Correction orthographique (+) décrivent deux ensembles de fonctionnalités qui sont implémentés en tant que commandes d'éditeur mais qui méritent leur propre traitement. Enfin, Commandes d'éditeur (+) liste et décrit les commandes d'éditeur spécifiques au shell et leurs associations par défaut.

L'éditeur de ligne de commande (+)

La saisie de ligne de commande peut être modifiée à l'aide de séquences de touches similaires à celles utilisées dans emacs(1) ou vi(1). L'éditeur n'est actif que lorsque la variable shell edit est définie, ce qui est le cas par défaut dans les shells interactifs. La commande intégrée bindkey peut afficher et modifier les associations de touches avec les commandes d'éditeur (voir Commandes d'éditeur (+)). Les associations de touches de style emacs(1) sont utilisées par défaut (sauf si le shell a été compilé différemment ; voir la variable shell version), mais bindkey peut modifier les associations de touches en associations de style vi(1) en masse.

Le shell associe toujours les touches fléchées (telles que définies dans la variable d'environnement TERMCAP) à des commandes d'éditeur :

down-history

left

forward-char

sauf si cela modifie une autre association de touche unique. On peut définir les séquences d'échappement des touches fléchées sur la chaîne vide avec settc pour éviter ces associations. Les séquences ANSI/VT100 pour les touches fléchées sont toujours associées.

Les autres associations de touches sont, pour la plupart, celles auxquelles les utilisateurs d'emacs(1) et vi(1) s'attendent et peuvent être facilement affichées par bindkey, il n'est donc pas nécessaire de les lister ici. De même, bindkey peut lister les commandes d'éditeur avec une courte description de chacune. Certaines associations de touches ont un comportement différent selon que les associations de style emacs(1) ou vi(1) sont utilisées ; voir vimode pour plus d'informations.

Notez que les commandes d'éditeur n'ont pas la même notion de « mot » que le shell. L'éditeur délimite les mots par tous les caractères non alphanumériques qui ne font pas partie de la variable shell wordchars, tandis que le shell ne reconnaît que les espaces blancs et certains des caractères ayant une signification spéciale pour lui, listés sous Structure lexicale.

Complétion et affichage (+)

Le shell est souvent capable de compléter des mots lorsqu'on lui donne une abréviation unique. Par exemple, taper une partie d'un mot

ls /usr/lost
et appuyer sur la touche tabulation pour exécuter la commande d'éditeur complete-word. Le shell complète le nom de fichier /usr/lost en /usr/lost+found/, remplaçant le mot incomplet par le mot complet dans le tampon d'entrée. (Notez le ‘/’ terminal ; la complétion ajoute un ‘/’ à la fin des répertoires complétés et un espace à la fin des autres mots complétés, pour accélérer la saisie et fournir un indicateur visuel de complétion réussie. La variable shell addsuffix peut être désactivée pour éviter cela.) Si aucune correspondance n'est trouvée (peut-être que /usr/lost+found n'existe pas), la sonnerie du terminal retentit. Si le mot est déjà complet (peut-être qu'il existe un /usr/lost sur votre système, ou peut-être pensiez-vous trop loin et avez tapé le tout) un ‘/’ ou un espace est ajouté à la fin s'il n'y est pas déjà.

La complétion fonctionne n'importe où sur la ligne, pas seulement à la fin ; le texte complété pousse le reste de la ligne vers la droite. La complétion au milieu d'un mot entraîne souvent des caractères restants à droite du curseur qui doivent être supprimés.

Les commandes et les variables peuvent être complétées de manière similaire. Par exemple, taper

em[tab]
compléterait ‘em’ en ‘emacs’ si ‘emacs’ était la seule commande de votre système commençant par ‘em’. La complétion peut trouver une commande dans n'importe quel répertoire de path ou si un chemin complet est donné.

Taper

echo $ar[tab]
compléterait ‘$ar’ en ‘$argv’ si aucune autre variable ne commençait par ‘ar’.

Le shell analyse le tampon d'entrée pour déterminer si le mot que vous souhaitez compléter doit être complété comme un nom de fichier, une commande ou une variable. Le premier mot du tampon et le premier mot suivant ‘;’, ‘|’, ‘|&’, ‘&&’, ou ‘||’ est considéré comme une commande. Un mot commençant par ‘$’ est considéré comme une variable. Tout le reste est un nom de fichier. Une ligne vide est « complétée » comme un nom de fichier.

Vous pouvez lister les complétions possibles d'un mot à tout moment en tapant ^D pour exécuter la commande d'éditeur delete-char-or-list-or-eof. Le shell liste les complétions possibles en utilisant la commande intégrée ls-F et réaffiche l'invite et la ligne de commande inachevée, par exemple :

> ls /usr/l[^D]
lbin/       lib/        local/      lost+found/
> ls /usr/l

Si la variable shell autolist est définie, le shell liste les choix restants (s'il y en a) chaque fois que la complétion échoue :

> set autolist
> nm /usr/lib/libt[tab]
libtermcap.a@ libtermlib.a@
> nm /usr/lib/libterm

Si la variable shell autolist est définie à ‘ambiguous’, les choix ne sont listés que lorsque la complétion échoue et n'ajoute aucun nouveau caractère au mot en cours de complétion.

Le shell peut compléter les noms de fichiers, les commandes et les variables. Dans le mode vi, on peut utiliser la touche esc suivie de control-d pour lister les choix possibles, et dans le mode emacs, on peut utiliser control-d. Dans les deux modes, la touche tab peut être utilisée pour compléter automatiquement un nom.

> ls ~k[^D]

> ls ~ke[tab]

Ou

Notez que les variables peuvent également être développées explicitement avec la commande d'éditeur expand-variables.

delete-char-or-list-or-eof liste à la fin de la ligne uniquement ; au milieu d'une ligne, il supprime le caractère sous le curseur et sur une ligne vide, il déconnecte l'utilisateur ou, si la variable ignoreeof est définie, ne fait rien. M-^D, liée à la commande d'éditeur list-choices, liste les possibilités de complétion n'importe où sur une ligne, et list-choices (ou l'une des commandes d'éditeur associées qui suppriment, listent et/ou déconnectent, listées sous delete-char-or-list-or-eof) peut être liée à ^D avec la commande intégrée bindkey si désiré.

Les commandes d'éditeur complete-word-fwd et complete-word-back (non liées à des touches par défaut) peuvent être utilisées pour parcourir la liste des complétions possibles, en remplaçant le mot courant par le mot suivant ou précédent dans la liste.

La variable shell fignore peut être définie avec une liste de suffixes à ignorer lors de la complétion. Considérons ce qui suit :

> ls
Makefile        condiments.h~   main.o          side.c
README          main.c          meal            side.o
condiments.h    main.c~
> set fignore = (.o \~)
> emacs ma[^D]
main.c   main.c~  main.o
> emacs ma[tab]
> emacs main.c

‘main.c~’ et ‘main.o’ sont ignorés par la complétion (mais pas par la liste), car ils se terminent par des suffixes présents dans fignore. Notez qu'un ‘\’ était nécessaire devant ‘~’ pour éviter son expansion en home comme décrit sous Substitution de noms de fichiers. fignore est ignoré s'il n'y a qu'une seule complétion possible.

Si la variable shell complete est définie sur ‘enhance’, la complétion 1) ignore la casse et 2) considère les points, les tirets et les underscores (‘.’, ‘-’ et ‘_’) comme des séparateurs de mots, et considère les tirets et les underscores comme équivalents. Si vous aviez les fichiers suivants

comp.lang.c      comp.lang.perl   comp.std.c++
comp.lang.c++    comp.std.c

et que vous tapez

mail -f c.l.c[tab]
ce serait complété en
mail -f comp.lang.c
et taper
mail -f c.l.c[^D]
listerait ‘comp.lang.c’ et ‘comp.lang.c++’.

Taper

mail -f c..c++[^D]
listerait ‘comp.lang.c++’ et ‘comp.std.c++’.

Taper

rm a--file[^D]
dans le répertoire suivant 
A_silly_file    a-hyphenated-file    another_silly_file
listerait les trois fichiers, car la casse est ignorée et les tirets et les underscores sont équivalents. Les points, cependant, ne sont pas équivalents aux tirets ou aux underscores.

Si la variable shell complete est définie sur ‘Enhance’, la complétion ignore la casse et les différences entre un séparateur de mot tiret et underscore uniquement lorsque l'utilisateur tape un caractère en minuscule ou un tiret. Entrer un caractère en majuscule ou un underscore ne correspondra pas au caractère en minuscule ou au séparateur de mot tiret correspondant.

Taper

rm a--file[^D]
dans le répertoire de l'exemple précédent listerait toujours les trois fichiers, mais taper
rm A--file
ne correspondrait qu'à ‘A_silly_file’ et taper
rm a__file[^D]
ne correspondrait qu'à ‘A_silly_file’ et ‘another_silly_file’ car l'utilisateur a explicitement utilisé un caractère majuscule ou un underscore.

La complétion et la liste sont affectées par plusieurs autres variables shell : recexact peut être définie pour compléter sur la correspondance unique la plus courte possible, même si plus de frappes pourraient aboutir à une correspondance plus longue :

> ls
fodder   foo      food     foonly
> set recexact
> rm fo[tab]

émet juste un bip, car ‘fo’ pourrait s'étendre en ‘fod’ ou ‘foo’, mais si nous tapons un autre ‘o’,

> rm foo[tab]
> rm foo

la complétion s'effectue sur ‘foo’, même si ‘food’ et ‘foonly’ correspondent également. autoexpand peut être définie pour exécuter la commande d'éditeur expand-history avant chaque tentative de complétion, autocorrect peut être définie pour corriger l'orthographe du mot à compléter (voir Correction orthographique (+)) avant chaque tentative de complétion et correct peut être définie pour compléter automatiquement les commandes après avoir frappé retour. matchbeep peut être définie pour activer ou désactiver le bip de complétion dans diverses situations, et nobeep peut être définie pour ne jamais émettre de bip. nostat peut être définie avec une liste de répertoires et/ou de motifs qui correspondent à des répertoires pour empêcher le mécanisme de complétion d'appeler stat(2) sur ces répertoires. listmax et listmaxrows peuvent être définies pour limiter le nombre d'éléments et de lignes (respectivement) qui sont listés sans demander au préalable. recognize_only_executables peut être définie pour que le shell ne liste que les exécutables lors de la liste des commandes, mais c'est assez lent.

Enfin, la commande intégrée complete peut être utilisée pour indiquer au shell comment compléter des mots autres que des noms de fichiers, des commandes et des variables. La complétion et la liste ne fonctionnent pas sur les glob-patterns (voir Substitution de noms de fichiers), mais les commandes d'éditeur list-glob et expand-glob effectuent des fonctions équivalentes pour les glob-patterns.

Correction orthographique (+)

Le shell peut parfois corriger l'orthographe des noms de fichiers, des commandes et des variables, ainsi que les compléter et les lister.

Les mots individuels peuvent être corrigés orthographiquement avec la commande d'éditeur spell-word (généralement liée à M-s et M-S) et le tampon d'entrée entier avec spell-line (généralement liée à M-$). La variable shell correct peut être définie sur ‘cmd’ pour corriger le nom de la commande ou ‘all’ pour corriger toute la ligne chaque fois que retour est tapé, et autocorrect peut être définie pour corriger le mot à compléter avant chaque tentative de complétion.

Lorsque la correction orthographique est invoquée de l'une de ces manières et que le shell pense qu'une partie de la ligne de commande est mal orthographiée, il invite l'utilisateur avec la ligne corrigée :

> set correct = cmd
> lz /usr/bin
CORRECT>ls /usr/bin (y|n|e|a)?

On peut répondre ‘y’ ou espace pour exécuter la ligne corrigée, ‘e’ pour laisser la commande non corrigée dans le tampon d'entrée, ‘a’ pour abandonner la commande comme si ^C avait été frappé, et toute autre chose pour exécuter la ligne originale inchangée.

La correction orthographique reconnaît les complétions définies par l'utilisateur (voir la commande intégrée complete). Si un mot d'entrée dans une position pour laquelle une complétion est définie ressemble à un mot de la liste de complétion, la correction orthographique enregistre une faute d'orthographe et suggère ce dernier mot comme correction. Cependant, si le mot d'entrée ne correspond à aucune des complétions possibles pour cette position, la correction orthographique n'enregistre pas de faute d'orthographe.

Comme la complétion, la correction orthographique fonctionne partout sur la ligne, poussant le reste de la ligne vers la droite et laissant potentiellement des caractères supplémentaires à droite du curseur.

Commandes d'éditeur (+)

bindkey liste les liaisons de touches et bindkey -l liste et décrit brièvement les commandes d'éditeur. Seules les commandes d'éditeur nouvelles ou particulièrement intéressantes sont décrites ici. Voir emacs(1) et vi(1) pour les descriptions des liaisons de touches de chaque éditeur.

Structure lexicale

Le shell divise les lignes d'entrée en mots aux blancs et aux tabulations. Les caractères spéciaux ‘&’, ‘|’, ‘;’, ‘<’, ‘>’, ‘(’ et ‘)’, ainsi que les caractères doublés ‘&&’, ‘||’, ‘<<’ et ‘>>’ sont toujours des mots séparés, qu'ils soient entourés d'espaces ou non.

Lorsque l'entrée du shell n'est pas un terminal, le caractère ‘#’ est considéré comme le début d'un commentaire. Chaque ‘#’ et le reste de la ligne d'entrée sur laquelle il apparaît est ignoré avant une analyse plus approfondie.

Un caractère spécial (y compris un blanc ou une tabulation) peut être empêché d'avoir sa signification spéciale, et éventuellement être intégré à un autre mot, en le précédant d'une barre oblique inverse (‘\’) ou en l'entourant de guillemets simples (‘'’), doubles (‘"’) ou inversés (‘`’). Lorsqu'il n'est pas cité autrement, un retour à la ligne précédé d'une ‘\’ est équivalent à un blanc, mais à l'intérieur des guillemets, cette séquence résulte en un retour à la ligne.

De plus, toutes les Substitutions, à l'exception de la Substitution d'historique, peuvent être empêchées en entourant les chaînes (ou parties de chaînes) dans lesquelles elles apparaissent de guillemets simples ou en citant les caractères cruciaux (par exemple, ‘$’ ou ‘`’ pour la Substitution de variable ou la Substitution de commande respectivement) avec une ‘\’. (La substitution d'alias ne fait pas exception : citer d'une manière ou d'une autre un caractère d'un mot pour lequel un alias a été défini empêche la substitution de l'alias. La manière habituelle de citer un alias est de le précéder d'une barre oblique inverse.) La substitution d'historique est empêchée par des barres obliques inverses mais pas par des guillemets simples. Les chaînes citées avec des guillemets doubles ou inversés subissent la substitution de variable et la substitution de commande, mais les autres substitutions sont empêchées.

Le texte à l'intérieur de guillemets simples ou doubles devient un seul mot (ou partie d'un mot). Les métacaractères dans ces chaînes, y compris les blancs et les tabulations, ne forment pas de mots séparés. Seulement dans un cas spécial (voir Substitution de commande) une chaîne entre guillemets doubles peut produire des parties de plus d'un mot ; les chaînes entre guillemets simples ne le font jamais. Les guillemets inversés sont spéciaux : ils signalent la Substitution de commande, ce qui peut résulter en plus d'un mot.

Les séquences d'échappement de style C peuvent être utilisées dans les chaînes entre guillemets simples en précédant le guillemet de début par un ‘$’. (+) Voir Séquences d'échappement (+) pour une liste complète des séquences d'échappement reconnues.

Citer des chaînes complexes, en particulier des chaînes qui contiennent elles-mêmes des caractères de citation, peut être déroutant. Rappelez-vous que les guillemets ne doivent pas nécessairement être utilisés comme en langage humain ! Il peut être plus facile de citer non pas une chaîne entière, mais seulement les parties de la chaîne qui nécessitent une citation, en utilisant différents types de citations pour le faire si nécessaire.

La variable shell backslash_quote peut être définie pour que les barres obliques inverses citent toujours ‘\’, ‘'’ et ‘"’ (+). Cela peut faciliter les tâches de citation complexes, mais peut entraîner des erreurs de syntaxe dans les scripts csh(1).

Substitution d'historique

Chaque commande, ou "événement", entrée depuis le terminal est sauvegardée dans la liste d'historique. La commande précédente est toujours sauvegardée, et la variable shell history peut être définie à un nombre pour sauvegarder ce nombre de commandes. La variable shell histdup peut être définie pour ne pas sauvegarder les événements dupliqués ou les événements dupliqués consécutifs.

Les commandes sauvegardées sont numérotées séquentiellement à partir de 1 et horodatées. Il n'est généralement pas nécessaire d'utiliser les numéros d'événement, mais le numéro d'événement actuel peut être inclus dans l'invite en plaçant un ‘!’ dans la variable shell prompt.

Par défaut, les entrées d'historique sont affichées en imprimant chaque jeton analysé séparé par un espace ; ainsi, l'opérateur de redirection ‘>&!’ sera affiché comme ‘> & !’. Le shell sauvegarde réellement l'historique sous forme développée et sous forme littérale (non développée). Si la variable shell histlit est définie, les commandes qui affichent et stockent l'historique utilisent la forme littérale.

La commande interne history peut imprimer, stocker dans un fichier, restaurer et effacer la liste d'historique à tout moment, et les variables shell savehist et histfile peuvent être définies pour stocker automatiquement la liste d'historique lors de la déconnexion et la restaurer lors de la connexion.

Les substitutions d'historique introduisent des mots de la liste d'historique dans le flux d'entrée, ce qui permet de répéter des commandes, de répéter des arguments d'une commande précédente dans la commande actuelle, ou de corriger des fautes d'orthographe dans la commande précédente avec peu de frappes et un haut degré de confiance.

Les substitutions d'historique commencent par le caractère ‘!’. Elles peuvent commencer n'importe où dans le flux d'entrée, mais elles ne s'imbriquent pas. Le ‘!’ peut être précédé d'une ‘\’ pour empêcher sa signification spéciale ; par souci de commodité, un ‘!’ est transmis inchangé lorsqu'il est suivi d'un blanc, d'une tabulation, d'un retour à la ligne, de ‘=’ ou de ‘(’.

Les substitutions d'historique se produisent également lorsqu'une ligne d'entrée commence par ‘^’ ; voir Abréviation de substitution d'historique.

Spécification d'événement de l'historique

Une référence d'historique peut spécifier un événement précédent en utilisant ‘!’ suivi de la spécification de l'événement. Par exemple, ‘!!’ fait référence à la commande précédente, et ‘!n’ fait référence à la n-ième commande. Les événements peuvent également être spécifiés par une chaîne de caractères, par exemple ‘!ls’ fait référence à la dernière commande commençant par ‘ls’. Un événement peut également être spécifié en référence à l'événement actuel, par exemple ‘!+1’ fait référence à la commande suivante.

Les arguments d'un événement précédent peuvent être référencés en utilisant les désignateurs de mots ‘^’ (premier argument), ‘$’ (dernier argument), ‘.’ (la commande elle-même), ‘*’ (tous les arguments), et ‘!’ (tous les arguments à l'exception du premier).

Par exemple, la commande diff (événement 12) aurait pu être tapée

diff !!^.old !!$
ou, de manière équivalente,
diff !!$.old !!$
Cependant, si ‘!!’ est abrégé en ‘!’, un sélecteur d'argument commençant par ‘-’ sera interprété comme une spécification d'événement.

Une référence d'historique peut avoir un désignateur de mot mais pas de spécification d'événement. Elle référence alors la commande précédente.

En continuant notre exemple de commande diff (événement 12), nous aurions pu taper simplement

diff !^.old !^
ou, pour obtenir les arguments dans l'ordre inverse, juste
diff !*

Supprime tous les composants de chemin de début, laissant la queue.
:r
Supprime une extension de nom de fichier ‘.xxx’, laissant le nom de base.
:e
Supprime tout sauf l'extension.
:u
Met en majuscule la première lettre minuscule.
:l
Met en minuscule la première lettre majuscule.
:s/l/r/
Remplace l par r. l est simplement une chaîne comme r, pas une expression régulière comme dans la commande éponyme de ed(1). N'importe quel caractère peut être utilisé comme délimiteur à la place de ‘/’; un ‘\’ peut être utilisé pour échapper le délimiteur à l'intérieur de l et r. Le caractère ‘&’ dans r est remplacé par l; ‘\’ échappe également ‘&’. Si l est vide (‘’), le l d'une substitution précédente ou le s d'une recherche précédente ou d'un numéro d'événement dans la spécification d'événement est utilisé. Le délimiteur final peut être omis s'il est immédiatement suivi d'un retour à la ligne.
:&
Répète la substitution précédente.
:g
Applique le modificateur suivant une fois à chaque mot.
:a (+)
Applique le modificateur suivant autant de fois que possible à un seul mot. ‘:a’ et ‘:g’ peuvent être utilisés ensemble pour appliquer un modificateur globalement. Avec le modificateur ‘:s’, seuls les motifs contenus dans le mot d'origine sont substitués, et non les motifs qui contiennent un résultat de substitution.
:p
Imprime la nouvelle ligne de commande mais ne l'exécute pas.
:q
Met entre guillemets les mots substitués, empêchant de nouvelles substitutions.
:Q
Identique à ‘:q’ mais en plus préserve les variables vides sous forme d'une chaîne contenant un NUL. Ceci est utile pour préserver les arguments positionnels par exemple : 
> set args=('arg 1' '' 'arg 3')
> tcsh -f -c 'echo ${#argv}' $args:gQ
3
:x
Comme ‘:q’, mais divise en mots aux espaces, tabulations et retours à la ligne.

Les modificateurs sont appliqués au premier mot modifiable (sauf si ‘:g’ est utilisé). C'est une erreur si aucun mot n'est modifiable.

Par exemple, la commande diff (événement 12) dans l'exemple d'historique dans Spécification d'événement de l'historique,

diff wumpus.man.old wumpus.man
aurait pu être tapée comme
diff wumpus.man.old !#^:r
en utilisant ‘:r’ pour supprimer ‘.old’ du premier argument sur la même ligne (‘!#^’).

Nous pourrions taper

echo hello out there
puis
echo !*:u
pour mettre en majuscule ‘hello’,
echo !*:au
pour mettre en majuscule le premier mot en ‘HELLO’, ou
echo !*:agu
pour mettre en majuscule tous les mots.

Nous pourrions suivre

mail -s "I forgot my password" rot
avec
!:s/rot/root
pour corriger l'orthographe de ‘root’ (voir Modificateurs de mots de l'historique et Correction orthographique (+) pour différentes approches).

(+) Dans csh(1) tel quel, un seul modificateur peut être appliqué à chaque expansion d'historique ou de variable. Dans tcsh, plusieurs peuvent être utilisés, par exemple

% mv wumpus.man /usr/share/man/man1/wumpus.1
% man !$:t:r
man wumpus

Dans csh(1), le résultat serait

wumpus.1:r

Une substitution suivie d'un ‘:’ peut nécessiter d'être isolée de celui-ci avec des accolades :

> mv a.out /usr/games/wumpus
> setenv PATH !$:h:$PATH
Bad ! modifier: $.
> setenv PATH !{-2$:h}:$PATH
setenv PATH /usr/games:/bin:/usr/bin:.

La première tentative réussirait dans csh(1) mais échoue dans tcsh, car tcsh attend un autre modificateur après le deuxième ‘:’ plutôt que ‘$’.

Abréviation de substitution d'historique

Il existe une abréviation spéciale pour les substitutions ; ‘^’, lorsqu'il est le premier caractère d'une ligne d'entrée, est équivalent à ‘!:s^’. Ainsi, nous pourrions suivre l'exemple de Modificateurs de mots de l'historique

mail -s "I forgot my password" rot
avec
^rot^root
pour effectuer la correction orthographique. C'est la seule substitution d'historique qui ne commence pas explicitement par ‘!’.

Commandes de l'éditeur d'historique

Enfin, l'historique peut être accédé via l'éditeur ainsi que par les substitutions décrites. Les commandes de l'éditeur up-history et down-history, history-search-backward et history-search-forward, i-search-back et i-search-fwd, vi-search-back et vi-search-fwd, copy-prev-word et insert-last-word recherchent des événements dans la liste d'historique et les copient dans le tampon d'entrée. La commande toggle-literal-history bascule entre les formes développées et littérales des lignes d'historique dans le tampon d'entrée. expand-history et expand-line développent les substitutions d'historique dans le mot courant et dans l'ensemble du tampon d'entrée respectivement.

Substitution d'alias

Le shell maintient une liste d'alias qui peuvent être définis, annulés et affichés par les commandes alias et unalias. Après qu'une ligne de commande est analysée en commandes simples (voir Commandes), le premier mot de chaque commande, de gauche à droite, est vérifié pour voir s'il a un alias. Si c'est le cas, le premier mot est remplacé par l'alias. Si l'alias contient une référence d'historique, il subit une Substitution d'historique comme si la commande d'origine était la ligne d'entrée précédente. Si l'alias ne contient pas de référence d'historique, la liste des arguments reste inchangée.

Ainsi, si l'alias de ‘ls’ était

ls -l
la commande
ls /usr
deviendrait
ls -l /usr
la liste des arguments n'étant pas perturbée.

Si l'alias de ‘lookup’ était

grep !^ /etc/passwd
alors
lookup bill
deviendrait
grep bill /e

tc/passwd

Les alias peuvent être utilisés pour introduire des métasyntaxes d'analyse. Par exemple,

alias print 'pr \!* | lpr'
définit une « commande » (« print ») qui traite ses arguments à l'aide de pr(1) vers l'imprimante ligne.

La substitution d'alias est répétée jusqu'à ce que le premier mot de la commande n'ait plus d'alias. Si une substitution d'alias ne modifie pas le premier mot (comme dans l'exemple précédent), elle est signalée pour éviter une boucle. D'autres boucles sont détectées et provoquent une erreur.

Certains alias sont référencés par le shell ; voir Alias spéciaux (+).

Substitution de variable

Le shell maintient une liste de variables, chacune ayant comme valeur une liste de zéro ou plusieurs mots. Les valeurs des variables shell peuvent être affichées et modifiées avec les commandes set et unset. Le système maintient sa propre liste de variables « d'environnement ». Celles-ci peuvent être affichées et modifiées avec printenv, setenv et unsetenv.

(+) Les variables peuvent être rendues en lecture seule avec

set -r
Les variables en lecture seule ne peuvent pas être modifiées ou désactivées ; toute tentative entraînera une erreur. Une fois rendue en lecture seule, une variable ne peut pas être rendue inscriptible, donc
set -r
doit être utilisé avec prudence. Les variables d'environnement ne peuvent pas être rendues en lecture seule.

Certaines variables sont définies par le shell ou référencées par celui-ci. Par exemple, la variable argv est une image de la liste d'arguments du shell, et les mots de la valeur de cette variable sont référencés de manière spéciale. Certaines des variables référencées par le shell sont des commutateurs ; le shell se soucie peu de leur valeur, seulement de savoir si elles sont définies ou non. Par exemple, la variable verbose est un commutateur qui provoque l'écho de l'entrée de commande. L'option de ligne de commande -v définit cette variable. Variables shell spéciales liste toutes les variables qui sont référencées par le shell.

D'autres opérations traitent les variables numériquement. La commande « @ » permet d'effectuer des calculs numériques et d'assigner le résultat à une variable. Les valeurs des variables sont cependant toujours représentées comme des chaînes (zéro ou plusieurs). Aux fins des opérations numériques, la chaîne nulle est considérée comme zéro, et le deuxième mot et les mots suivants des valeurs à plusieurs mots sont ignorés.

Après que la ligne d'entrée a été traitée par alias et analysée, et avant que chaque commande ne soit exécutée, une substitution de variable est effectuée à l'aide des caractères « $ ». Cette expansion peut être empêchée en faisant précéder le « $ » par un « \ », sauf à l'intérieur des paires « " » où elle se produit toujours, et à l'intérieur des paires « ' » où elle ne se produit jamais. Les chaînes citées par « ` » sont interprétées plus tard (voir Substitution de commande), donc la substitution « $ » ne s'y produit pas avant plus tard, le cas échéant. Un « $ » est transmis tel quel s'il est suivi d'un blanc, d'une tabulation ou de la fin de ligne.

Les redirections d'entrée/sortie sont reconnues avant l'expansion des variables, et sont développées séparément. Sinon, le nom de la commande et la liste complète des arguments sont développés ensemble. Il est ainsi possible que le premier mot (de la commande jusqu'à ce point) génère plus d'un mot, dont le premier devient le nom de la commande, et le reste devient des arguments.

Sauf si elles sont enfermées entre « " » ou qu'elles reçoivent le modificateur « :q », les résultats de la substitution de variable peuvent finalement être soumis à une substitution de commande et de nom de fichier. À l'intérieur de « " », une variable dont la valeur se compose de plusieurs mots s'étend à un (une partie d'un) seul mot, les mots de la valeur de la variable étant séparés par des blancs. Lorsque le modificateur « :q » est appliqué à une substitution, la variable s'étend à plusieurs mots avec chaque mot séparé par un blanc et mis entre guillemets pour empêcher une substitution ultérieure de commande ou de nom de fichier.

La commande d'édition expand-variables, normalement liée à ^X-$, peut être utilisée pour développer interactivement des variables individuelles.

Méta-séquences de substitution de variable

Les méta-séquences suivantes sont fournies pour introduire des valeurs de variables dans l'entrée du shell :

$name
 
${name}
Substitue les mots de la valeur de la variable name, chacun séparé par un blanc. Les accolades isolent name des caractères suivants qui en feraient autrement partie. Les variables shell ont des noms composés de lettres et de chiffres commençant par une lettre. Le caractère de soulignement est considéré comme une lettre. Si name n'est pas une variable shell, mais est défini dans l'environnement, alors cette valeur est renvoyée (mais certaines des autres formes données ci-dessous ne sont pas disponibles dans ce cas).
$name[selector]
 
${name[selector]}
Substitue uniquement les mots sélectionnés de la valeur de name. Le selector est soumis à la substitution « $ » et peut consister en un seul nombre ou deux nombres séparés par un « - ». Le premier mot de la valeur d'une variable est numéroté « 1 ». Si le premier nombre d'une plage est omis, il est par défaut « 1 ». Si le dernier membre d'une plage est omis, il est par défaut « $#name ». Le selector « * » sélectionne tous les mots. Ce n'est pas une erreur si une plage est vide si le deuxième argument est omis ou dans la plage.
$0
Substitue le nom du fichier à partir duquel l'entrée de commande est lue. Une erreur se produit si le nom n'est pas connu.
$number
 
${number}
Équivalent à « $argv[number] ».
$*
Équivalent à « $argv », ce qui est équivalent à « $argv[*] ».

Sauf indication contraire, il est erroné de référencer une variable qui n'est pas définie.

Les modificateurs « : » décrits sous Modificateurs de mots d'historique, à l'exception de « :p », peuvent être appliqués aux substitutions ci-dessus. Plus d'un peuvent être utilisés. (+) Des accolades peuvent être nécessaires pour isoler une substitution de variable d'un « : » littéral, tout comme avec les Modificateurs de mots d'historique ; tous les modificateurs doivent apparaître à l'intérieur des accolades.

Substitution de variable sans modificateurs

Les substitutions suivantes ne peuvent pas être modifiées avec des modificateurs « : » :

$?name
 
${?name}
Substitue la chaîne « 1 » si name est défini, « 0 » s'il ne l'est pas.
$?0
Substitue « 1 » si le nom du fichier d'entrée actuel est connu, « 0 » s'il ne l'est pas. Toujours « 0 » dans les shells interactifs.
$#name
 
${#name}
Substitue le nombre de mots dans name.
$#
Équivalent à « $#argv ». (+)
$%name
 
${%name}
Substitue le nombre de caractères dans name. (+)
$%number
 
${%number}
Substitue le nombre de caractères dans « $argv[number] ». (+)
$?
dt>
Équivalent à ‘$status’. (+)
$$
Remplace le numéro de processus (décimal) du shell (parent).
$!
Remplace le numéro de processus (décimal) du dernier processus en arrière-plan lancé par ce shell. (+)
$_
Remplace la ligne de commande de la dernière commande exécutée. (+)
$<
Remplace une ligne de l'entrée standard, sans autre interprétation par la suite. Elle peut être utilisée pour lire depuis le clavier dans un script shell. (+) Alors que csh(1) met toujours entre guillemets ‘$<’, comme s'il était équivalent à ‘$<:q’, tcsh ne le fait pas. De plus, lorsque tcsh attend une ligne à taper, l'utilisateur peut taper une interruption pour interrompre la séquence dans laquelle la ligne doit être substituée, mais csh(1) ne le permet pas.
$?<
Remplace le nombre d'octets disponibles de l'entrée standard. (Cette fonctionnalité peut être non portable.) (+)

Substitution de commande, de nom de fichier et de pile de répertoires

Les substitutions restantes sont appliquées sélectivement aux arguments des commandes intégrées. Cela signifie que les portions d'expressions qui ne sont pas évaluées ne sont pas soumises à ces expansions. Pour les commandes qui ne sont pas internes au shell, le nom de la commande est substitué séparément de la liste des arguments. Cela se produit très tard, après que la redirection d'entrée/sortie soit effectuée, et dans un fils du shell principal.

Substitution de commande

La substitution de commande est indiquée par une commande entourée de ‘`’. La sortie d'une telle commande est divisée en mots séparés par des espaces, des tabulations et des nouvelles lignes, et les mots nuls sont rejetés. La sortie est variable et substituée par la commande, puis placée à la place de la chaîne d'origine.

Les substitutions de commande à l'intérieur de guillemets doubles (‘"’) conservent les espaces et les tabulations ; seules les nouvelles lignes forcent de nouveaux mots. La seule nouvelle ligne finale ne force un nouveau mot dans aucun cas. Il est ainsi possible qu'une substitution de commande ne produise qu'une partie d'un mot, même si la commande produit une ligne complète.

Par défaut, le shell depuis la version 6.12 remplace toutes les nouvelles lignes et les retours chariot dans la commande par des espaces. Si cela est désactivé en désactivant csubstnonl, les nouvelles lignes séparent les commandes comme d'habitude.

Substitution de nom de fichier

Si un mot contient l'un des caractères ‘*’, ‘?’, ‘[’, ou ‘{’ ou commence par le caractère ‘~’, il est candidat à la substitution de nom de fichier, également connue sous le nom de « globbing ». Ce mot est alors considéré comme un modèle (« glob-pattern ») et remplacé par une liste triée alphabétiquement de noms de fichiers qui correspondent au modèle.

Dans les noms de fichiers correspondants, le caractère ‘.’ au début d'un nom de fichier ou immédiatement après un ‘/’, ainsi que le caractère ‘/’, doivent être explicitement mis en correspondance (sauf si globdot ou globstar ou les deux sont définis (+)). Le caractère ‘*’ correspond à toute chaîne de caractères, y compris la chaîne nulle. Le caractère ‘?’ correspond à un seul caractère. La séquence ‘[...]’ correspond à l'un des caractères qu'elle contient. À l'intérieur de ‘[...]’, une paire de caractères séparés par ‘-’ correspond à tout caractère lexicalement situé entre les deux.

(+) Certains glob-patterns peuvent être niés : La séquence ‘[^...]’ correspond à tout caractère unique ne faisant pas partie des caractères et/ou des plages de caractères entre les accolades.

Un glob-pattern entier peut également être nié avec ‘^’ :

> echo *
bang crash crunch ouch
> echo ^cr*
bang ouch

Les glob-patterns qui n'utilisent pas ‘?’, ‘*’, ou ‘[]’, ou qui utilisent ‘{}’ ou ‘~’ (ci-dessous) ne sont pas correctement niés.

La métanotation ‘a{b,c,d}e’ est une abréviation pour ‘abe ace ade’. L'ordre de gauche à droite est préservé :

/usr/source/s1/{oldls,ls}.c
se développe en
/usr/source/s1/oldls.c /usr/source/s1/ls.c
Les résultats des correspondances sont triés séparément à un bas niveau pour préserver cet ordre :
../{memo,*box}
peut se développer en
../memo ../box ../mbox
(Notez que ‘memo’ n'a pas été trié avec les résultats de la correspondance de ‘*box’.) Il n'est pas une erreur lorsque cette construction s'étend à des fichiers qui n'existent pas, mais il est possible d'obtenir une erreur d'une commande à laquelle la liste développée est passée. Cette construction peut être imbriquée. À titre de cas spécial, les mots ‘{’, ‘}’, et ‘{}’ sont transmis sans modification.

Le caractère ‘~’ au début d'un nom de fichier fait référence aux répertoires personnels. Seul, c'est-à-dire ‘~’, il se développe en répertoire personnel de l'invocateur tel qu'il est reflété dans la valeur de la variable shell home. Lorsqu'il est suivi d'un nom composé de lettres, de chiffres et de caractères ‘-’, le shell recherche un utilisateur portant ce nom et substitue son répertoire personnel ; ainsi

~ken
peut se développer en
/usr/ken
et
~ken/chmach
peut se développer en
/usr/ken/chmach
Si le caractère ‘~’ est suivi d'un caractère autre qu'une lettre ou ‘/’ ou apparaît ailleurs qu'au début d'un mot, il est laissé intact. Une commande comme
setenv MANPATH /usr/share/man:/usr/local/share/man:~/lib/man
ne fait donc pas de substitution de répertoire personnel comme on pourrait l'espérer.

Il est une erreur qu'un glob-pattern contenant ‘*’, ‘?’, ‘[’, ou ‘~’, avec ou sans ‘^’, ne corresponde à aucun fichier. Cependant, un seul modèle dans une liste de glob-patterns doit correspondre à un fichier (de sorte que, par exemple,

rm *.a *.c *.o
échouerait seulement s'il n'y avait aucun fichier dans le répertoire courant se terminant par ‘.a’, ‘.c’, ou ‘.o’), et si la variable shell nonomatch est définie, un modèle (ou une liste de modèles) qui ne correspond à rien est laissé inchangé plutôt que de provoquer une erreur.

La variable shell globstar peut être définie pour permettre ‘**’ ou ‘***’ comme modèle de glob de fichier qui correspond à toute chaîne de caractères y compris ‘/’, en parcourant récursivement tous les sous-répertoires existants. Par exemple,

ls **.c
listéra tous les fichiers .c dans l'arborescence du répertoire courant. S'il est utilisé seul, il correspondra à zéro ou plusieurs sous-répertoires. Par exemple
ls /usr/include/**/time.h
listéra tout fichier nommé ‘time.h’ dans l'arborescence du répertoire /usr/include ;
ls /usr/include/**time.h
correspondra à tout fichier dans l'arborescence du répertoire /usr/include se terminant par ‘time.h’ ; et
ls /usr/include/**time**.h
correspondra à tout fichier .h contenant ‘time’ soit dans un nom de sous-répertoire, soit dans le nom de fichier lui-même. Pour éviter les problèmes de récursion, le modèle de glob ‘**’ ne descendra pas dans un lien symbolique contenant un répertoire. Pour outrepasser cela, utilisez ‘***’ (+)

La variable shell noglob peut être définie pour empêcher la substitution de nom de fichier, et la commande d'édition expand-glob, normalement liée à ^X-*, peut être utilisée pour développer interactivement des substitutions de nom de fichier individuelles.

Substitution de pile de répertoires (+)

La pile de répertoires est une liste de répertoires, numérotés à partir de zéro, utilisés par les commandes intégrées pushd, popd et dirs. dirs peut imprimer, stocker dans un fichier, restaurer et effacer la pile de répertoires à tout moment, et les variables shell savedirs et dirsfile peuvent être définies pour stocker automatiquement la pile de répertoires lors de la déconnexion et la restaurer lors de la connexion. La variable shell dirstack peut être examinée pour voir la pile de répertoires et définie pour y placer des répertoires arbitraires.

Le caractère ‘=’ suivi d'un ou plusieurs chiffres

s'étend en une entrée dans la pile de répertoires. Le cas spécial « =- » s'étend au dernier répertoire de la pile. Par exemple, 

> dirs -v
0       /usr/bin
1       /usr/spool/uucp
2       /usr/accts/sys
> echo =1
/usr/spool/uucp
> echo =0/calendar
/usr/bin/calendar
> echo =-
/usr/accts/sys

Les variables shell noglob et nonomatch ainsi que la commande éditeur expand-glob s'appliquent à la pile de répertoires ainsi qu'aux substitutions de noms de fichiers.

Autres substitutions (+)

Il existe plusieurs autres transformations impliquant des noms de fichiers, qui ne sont pas strictement liées à ce qui précède mais sont mentionnées ici par souci d'exhaustivité. N'importe quel nom de fichier peut être développé en un chemin complet lorsque la variable symlinks est définie sur « expand ». La mise entre guillemets empêche cette expansion, et la commande éditeur normalize-path l'effectue à la demande. La commande éditeur normalize-command développe les commandes dans PATH en chemins complets à la demande. Enfin, cd et pushd interprètent « - » comme l'ancien répertoire courant (équivalent à la variable shell owd). Ce n'est pas une substitution du tout, mais une abréviation reconnue uniquement par ces commandes. Néanmoins, elle peut également être empêchée par la mise entre guillemets.

Commandes

Les trois sections suivantes décrivent comment le shell exécute les commandes et gère leur entrée et leur sortie.

Commandes simples, pipelines et séquences

Une commande simple est une séquence de mots, le premier spécifiant la commande à exécuter. Une série de commandes simples reliées par des caractères « | » forme un pipeline. La sortie de chaque commande d'un pipeline est connectée à l'entrée de la suivante.

Les commandes simples et les pipelines peuvent être joints en séquences avec « ; », et seront exécutés séquentiellement. Les commandes et les pipelines peuvent également être joints en séquences avec « || » ou « && », indiquant, comme dans le langage C, que le second doit être exécuté seulement si le premier échoue ou réussit respectivement.

Une commande simple, un pipeline ou une séquence peut être placé entre parenthèses (« ( » et « ) ») pour former une commande simple, qui peut à son tour être un composant d'un pipeline ou d'une séquence. Une commande, un pipeline ou une séquence peut être exécuté sans attendre sa terminaison en le faisant suivre d'un « & ».

Exécution des commandes internes et externes

Les commandes internes sont exécutées au sein du shell. Si une composante d'un pipeline autre que la dernière est une commande interne, le pipeline est exécuté dans un sous-shell.

Les commandes entre parenthèses sont toujours exécutées dans un sous-shell.

(cd; pwd); pwd

imprime ainsi le répertoire home, vous laissant là où vous étiez (imprimant ceci après le répertoire personnel), tandis que

cd; pwd

vous laisse dans le répertoire home. Les commandes entre parenthèses sont le plus souvent utilisées pour empêcher cd d'affecter le shell courant.

Lorsqu'une commande à exécuter n'est pas une commande interne, le shell tente de l'exécuter via execve(2). Chaque mot de la variable path nomme un répertoire dans lequel le shell recherchera la commande. Si le shell ne reçoit pas l'option -f, le shell utilise une table interne pour hacher les noms de ces répertoires afin de ne tenter un execve(2) que dans un répertoire où la commande pourrait se trouver. Cela accélère grandement la localisation des commandes lorsqu'un grand nombre de répertoires sont présents dans le chemin de recherche. Ce mécanisme de hachage n'est pas utilisé :

  1. Si le hachage est explicitement désactivé via unhash.
  2. Si le shell a reçu un -f argument.
  3. Pour chaque composante de répertoire de path qui ne commence pas par « / ».
  4. Si la commande contient un « / ».

Dans les quatre cas ci-dessus, le shell concatène chaque composante du vecteur de chemin avec le nom de commande donné pour former un nom de chemin d'un fichier qu'il tente ensuite d'exécuter. Si l'exécution réussit, la recherche s'arrête.

Si le fichier a des permissions d'exécution mais n'est pas un exécutable pour le système (c'est-à-dire qu'il ne s'agit ni d'un binaire exécutable ni d'un script spécifiant son interpréteur), il est supposé être un fichier contenant des commandes shell et un nouveau shell est lancé pour le lire. L'alias spécial shell peut être défini pour spécifier un interpréteur autre que le shell lui-même.

Sur les systèmes qui ne comprennent pas la convention d'interpréteur de script « #! », le shell peut être compilé pour l'émuler ; voir la variable shell version. Si c'est le cas, le shell vérifie la première ligne du fichier pour voir si elle est de la forme

#!interpréteur arg ...
Si c'est le cas, le shell démarre interpréteur avec les args donnés et lui transmet le fichier en entrée standard.

Entrée/sortie

L'entrée standard et la sortie standard d'une commande peuvent être redirigées avec la syntaxe suivante :

< nom
Ouvre le fichier nom (qui est d'abord développé en variable, commande et nom de fichier) comme entrée standard.
<< mot
Lit l'entrée du shell jusqu'à une ligne identique à mot. mot n'est pas soumis à des substitutions de variables, de noms de fichiers ou de commandes, et chaque ligne d'entrée est comparée à mot avant toute substitution sur cette ligne d'entrée. À moins qu'une échappement (« \ », « " », « ' » ou « ` ») n'apparaisse dans mot, les substitutions de variables et de commandes sont effectuées sur les lignes intermédiaires, permettant à « \ » d'échapper « $ », « \ » et « ` ». Les commandes qui sont substituées conservent tous les blancs, tabulations et sauts de ligne, à l'exception du dernier saut de ligne qui est supprimé. Le texte résultant est placé dans un fichier temporaire anonyme qui est donné à la commande comme entrée standard.
> nom
 
>! nom
 
>& nom
 
>&! nom
Le fichier nom est utilisé comme sortie standard. Si le fichier n'existe pas, il est créé ; s'il existe, il est tronqué, son contenu précédent étant perdu.

Si la variable shell noclobber est définie, le fichier ne doit pas exister ou être un fichier caractère spécial (par exemple, un terminal ou /dev/null), sinon une erreur se produit. Cela aide à prévenir la destruction accidentelle de fichiers. Dans ce cas, les formes « ! » peuvent être utilisées pour supprimer cette vérification. Si « notempty » est donné dans noclobber, « > » est autorisé sur les fichiers vides ; si « ask » est donné dans noclobber, une confirmation interactive est présentée, plutôt qu'une erreur.

Les formes impliquant « & » redirigent la sortie diagnostique dans le fichier spécifié ainsi que la sortie standard. nom est développé de la même manière que les noms de fichiers d'entrée « < » le sont.

>> nom
 
>>& nom
 
>>! nom
 
>>&! nom
Comme « > », mais ajoute la sortie à la fin de nom. Si la variable shell noclobber est définie, alors c'est une erreur pour le fichier de *ne pas* exister, à moins qu'une des formes « ! » ne soit donnée.

Une commande reçoit l'environnement dans lequel le shell a été invoqué tel que modifié par les paramètres d'entrée-sortie et la présence de la commande dans un pipeline. Ainsi, contrairement à certains shells précédents, les commandes exécutées à partir d'un fichier de commandes shell n'ont pas accès au texte des commandes par défaut ; elles reçoivent plutôt l'entrée standard d'origine du shell. Le mécanisme « << » doit être utilisé pour présenter des données en ligne. Cela permet aux scripts de commandes shell de fonctionner comme des composants de pipelines et permet au shell de

block read its input. Note that the default standard input for a command run detached is pas the empty file /dev/null, but the original standard input of the shell. If this is a terminal and if the process attempts to read from the terminal, then the process will block and the user will be notified (see Jobs).

Diagnostic output may be directed through a pipe with the standard output. Simply use the form ‘|&’ rather than just ‘|’.

The shell cannot presently redirect diagnostic output without also redirecting standard output, but

( command > output-file ) >& error-file
is often an acceptable workaround. Either output-file or error-file may be /dev/tty to send output to the terminal.

Fonctionnalités

Having described how the shell accepts, parses and executes command lines, we now turn to a variety of its useful features.

Flux de contrôle

The shell contains a number of commands which can be used to regulate the flow of control in command files (shell scripts) and (in limited but useful ways) from terminal input. These commands all operate by forcing the shell to reread or skip in its input and, due to the implementation, restrict the placement of some of the commands.

The foreach, switch, and while statements, as well as the if ... then ... else form of the if statement, require that the major keywords appear in a single simple command on an input line as shown below.

If the shell's input is not seekable, the shell buffers up input whenever a loop is being read and performs seeks in this internal buffer to accomplish the rereading implied by the loop. (To the extent that this allows, backward gotos will succeed on non-seekable inputs.)

Expressions

The if, while, and exit builtin commands use expressions with a common syntax. The expressions can include any of the operators described in the next three sections. Note that the @ builtin command has its own separate syntax.

Opérateurs logiques, arithmétiques et de comparaison

These operators are similar to those of C and have the same precedence.

The operators, in descending precedence, with equivalent precedence per line, are:

The ‘==’ ‘!=’ ‘=~’ and ‘!~’ operators compare their arguments as strings; all others operate on numbers. The operators ‘=~’ and ‘!~’ are like ‘==’ and ‘!=’ except that the right hand side is a glob-pattern (see Substitution de nom de fichier) against which the left hand operand is matched. This reduces the need for use of the switch builtin command in shell scripts when all that is really needed is pattern matching.

Null or missing arguments are considered ‘0’. The results of all expressions are strings, which represent decimal numbers. It is important to note that no two components of an expression can appear in the same word; except when adjacent to components of expressions which are syntactically significant to the parser (‘&’, ‘|’, ‘<’, ‘>’, ‘(’, ‘)’) they should be surrounded by spaces.

Statut de sortie des commandes

Commands can be executed in expressions and their exit status returned by enclosing them in braces (‘{’ and ‘}’). Remember that the braces should be separated from the words of the command by spaces. Command executions succeed, returning true, i.e., ‘1’, if the command exits with status 0, otherwise they fail, returning false, i.e., ‘0’. If more detailed status information is required then the command should be executed outside of an expression and the status shell variable examined.

Tâches (Jobs)

Le shell associe une tâche à chaque pipeline. Il maintient une table des tâches en cours, imprimée par la commande jobs, et leur attribue de petits numéros entiers. Lorsqu'une tâche est lancée de manière asynchrone avec « & », le shell affiche une ligne ressemblant à ceci :

[1] 1234

indiquant que la tâche lancée de manière asynchrone était la tâche numéro 1 et comportait un processus (de premier niveau), dont l'identifiant de processus était 1234.

Si vous exécutez une tâche et souhaitez faire autre chose, vous pouvez appuyer sur la touche de suspension (généralement ^Z), qui envoie un signal STOP à la tâche en cours. Le shell indiquera alors normalement que la tâche a été

Suspendue
et affichera une nouvelle invite. Si la variable shell listjobs est définie, toutes les tâches seront listées comme la commande interne jobs ; si elle est définie sur « long », la liste sera au format long, comme « jobs -l ». Vous pouvez alors manipuler l'état de la tâche suspendue. Vous pouvez la placer en « arrière-plan » avec la commande bg ou exécuter d'autres commandes et finalement ramener la tâche au « premier plan » avec fg. (Voir aussi la commande d'édition run-fg-editor.) Un ^Z prend effet immédiatement et est comme une interruption, les sorties en attente et les entrées non lues étant rejetées lorsqu'il est tapé. La commande interne wait fait en sorte que le shell attende la fin de toutes les tâches en arrière-plan.

La touche ^] envoie un signal de suspension différée, qui ne génère un signal STOP que lorsqu'un programme tente de lire(2), à la tâche en cours. Cela peut être utilement tapé à l'avance lorsque vous avez préparé des commandes pour une tâche que vous souhaitez arrêter après qu'elle les ait lues. La touche ^Y remplit cette fonction dans csh(1) ; dans tcsh, ^Y est une commande d'édition. (+)

Une tâche exécutée en arrière-plan s'arrête si elle tente de lire depuis le terminal. Les tâches en arrière-plan sont normalement autorisées à produire une sortie, mais cela peut être désactivé en donnant la commande

stty tostop
Si vous définissez cette option tty, les tâches en arrière-plan s'arrêteront lorsqu'elles essaieront de produire une sortie, de la même manière qu'elles le font lorsqu'elles essaient de lire une entrée.

Il existe plusieurs façons de faire référence aux tâches dans le shell. Le caractère « % » introduit un nom de tâche. Si vous souhaitez faire référence à la tâche numéro 1, vous pouvez la nommer ainsi :

%1
Nommer simplement une tâche la ramène au premier plan ; ainsi %1 est un synonyme de fg %1, ramenant la tâche 1 au premier plan. De même, taper %1 & reprend la tâche 1 en arrière-plan, tout comme bg %1. Une tâche peut également être nommée par une préfixe non ambigu de la chaîne tapée pour la démarrer : %ex redémarrerait normalement une tâche ex(1) suspendue, s'il n'y avait qu'une seule tâche suspendue dont le nom commence par la chaîne « ex ». Il est également possible de taper %?chaîne pour spécifier une tâche dont le texte contient chaîne, s'il n'y a qu'une seule telle tâche.

Le shell maintient une notion de tâche actuelle et précédente. Dans la sortie concernant les tâches, la tâche actuelle est marquée d'un « + » et la tâche précédente d'un « - ». Les abréviations « %+ », « % » et (par analogie avec la syntaxe du mécanisme history) « %% » font toutes référence à la tâche actuelle, et « %- » fait référence à la tâche précédente.

Le mécanisme de contrôle de tâche nécessite que l'option stty(1) « new » soit définie sur certains systèmes. C'est un artéfact d'une « nouvelle » implémentation du pilote tty qui permet la génération de in

terrupt characters from the keyboard to tell jobs to stop. See stty(1) and the setty builtin command for details on setting options in the new tty driver.

Rapport de statut

Le shell apprend immédiatement chaque fois qu'un processus change d'état. Il vous informe normalement chaque fois qu'un travail est bloqué, de sorte qu'aucun progrès supplémentaire n'est possible, mais seulement juste avant d'imprimer une invite. Ceci est fait afin de ne pas perturber votre travail. Si, cependant, vous définissez la variable shell notify, le shell vous informera immédiatement des changements de statut dans les tâches d'arrière-plan. Il existe également une commande intégrée notify qui marque un processus unique afin que ses changements de statut soient immédiatement signalés. Par défaut, notify marque le processus actuel ; entrez simplement

notify
après avoir démarré une tâche d'arrière-plan pour la marquer pour un rapport de statut immédiat.

Lorsque vous essayez de quitter le shell alors que des tâches sont arrêtées, vous serez averti que

Il y a des tâches suspendues.

Vous pouvez utiliser la commande jobs pour voir lesquelles. Si vous faites cela ou essayez de quitter immédiatement à nouveau, le shell ne vous avertira pas une deuxième fois, et les tâches suspendues seront terminées.

Événements automatiques, périodiques et programmés (+)

Il existe diverses façons d'exécuter des commandes et de prendre d'autres mesures automatiquement à différents moments du “cycle de vie” du shell. Ils sont résumés ici et décrits en détail sous les rubriques appropriées Commandes intégrées, Variables shell spéciales, et Alias spéciaux (+).

La commande intégrée sched place les commandes dans une liste d'événements planifiés, à exécuter par le shell à un moment donné.

Les alias spéciaux beepcmd, cwdcmd, jobcmd, periodic, precmd et postcmd (+) peuvent être définis, respectivement, pour exécuter des commandes : lorsque le shell souhaite faire sonner la cloche, lorsque le répertoire de travail change, lorsqu'une tâche est démarrée ou amenée au premier plan, toutes les tperiod minutes, avant chaque invite, et avant que chaque commande ne soit exécutée.

La variable shell autologout peut être définie pour se déconnecter ou verrouiller le shell après un nombre donné de minutes d'inactivité.

La variable shell mail peut être définie pour vérifier le nouveau courrier périodiquement.

La variable shell printexitvalue peut être définie pour imprimer le code de sortie des commandes qui se terminent avec un code différent de zéro.

La variable shell rmstar peut être définie pour demander à l'utilisateur, lorsque

rm *
est tapé, si c'est bien ce qui était prévu.

La variable shell time peut être définie pour exécuter la commande intégrée time après l'achèvement de tout processus qui prend plus d'un nombre donné de secondes CPU.

Les variables shell watch et who peuvent être définies pour signaler lorsque des utilisateurs sélectionnés se connectent ou se déconnectent, et la commande intégrée log signale ces utilisateurs à tout moment.

Support du système de langues natives (+)

Le shell est propre à huit bits (s'il a été compilé ainsi ; voir la variable shell version) et prend donc en charge les jeux de caractères qui nécessitent cette capacité. Le support NLS diffère selon que le shell a été compilé ou non pour utiliser le NLS du système (encore une fois, voir version). Dans les deux cas, ASCII 7 bits est le code de caractère par défaut (par exemple, la classification des caractères imprimables) et le tri, et la modification des variables d'environnement LANG ou LC_CTYPE entraîne une vérification des changements possibles à cet égard.

Lors de l'utilisation du NLS du système, la fonction setlocale(3) est appelée pour déterminer le code de caractère/classification et le tri appropriés (par exemple, ‘en_CA.UTF-8’ donnerait ‘UTF-8’ comme code de caractère). Cette fonction examine généralement les variables d'environnement LANG et LC_CTYPE ; référez-vous à la documentation du système pour plus de détails. Lorsqu'il n'utilise pas le NLS du système, le shell le simule en supposant que le jeu de caractères ISO 8859-1 est utilisé chaque fois que les variables LANG et LC_CTYPE sont définies, quelle que soit leur valeur. Le tri n'est pas affecté pour le NLS simulé.

De plus, avec les NLS réels et simulés, tous les caractères imprimables dans la plage \200-\377, c'est-à-dire ceux qui ont des liaisons M-char, sont automatiquement rejoints à self-insert-command. La liaison correspondante pour la séquence escape-char, le cas échéant, est laissée intacte. Ces caractères ne sont pas rejoints si la variable d'environnement NOREBIND est définie. Cela peut être utile pour le NLS simulé ou un NLS primitif qui suppose le ISO 8859-1 complet. Sinon, toutes les liaisons M-char dans la plage \240-\377 sont effectivement annulées. La re-liaison explicite des touches pertinentes avec bindkey est bien sûr toujours possible.

Les caractères inconnus (c'est-à-dire ceux qui ne sont ni imprimables ni des caractères de contrôle) sont imprimés au format \nnn. Si le tty n'est pas en mode 8 bits, d'autres caractères 8 bits sont imprimés en les convertissant en ASCII et en utilisant le mode standout. Le shell ne modifie jamais le mode 7/8 bits du tty et suit les changements de mode 7/8 bits initiés par l'utilisateur. Les utilisateurs de NLS (ou, pour cela, ceux qui veulent utiliser une touche méta) peuvent avoir besoin de définir explicitement le tty en mode 8 bits via la commande stty(1) appropriée dans, par exemple, le fichier ~/.login.

Support des variantes d'OS (+)

Un certain nombre de nouvelles commandes intégrées sont fournies pour prendre en charge les fonctionnalités de systèmes d'exploitation particuliers. Toutes sont décrites en détail dans la section Commandes intégrées.

Sur les systèmes qui prennent en charge TCF (aix-ibm370, aix-ps2), getspath et setspath obtiennent et définissent le chemin d'exécution du système, getxvers et setxvers obtiennent et définissent le préfixe de version expérimental et migrate migre les processus entre les sites. La commande intégrée jobs imprime le site sur lequel chaque tâche s'exécute.

Sous BS2000, bs2cmd exécute des commandes du système d'exploitation BS2000/OSD sous-jacent.

Sous Domain/OS, inlib ajoute des bibliothèques partagées à l'environnement actuel, rootnode change le nœud racine et ver change le systype.

Sous Mach, setpath est équivalent à setpath(1) de Mach.

Sous Masscomp/RTU et Harris CX/UX, universe définit l'univers.

Sous Harris CX/UX, ucb ou att exécute une commande sous l'univers spécifié.

Sous Convex/OS, warp imprime ou définit l'univers.

Les variables d'environnement VENDOR, OSTYPE et MACHTYPE indiquent respectivement le fournisseur, le système d'exploitation et le type de machine (classe de microprocesseur ou modèle de machine) sur lequel le shell pense s'exécuter. Celles-ci sont particulièrement utiles lors du partage de son répertoire personnel entre plusieurs types de machines ; on peut, par exemple,

set path = (~/bin.$MACHTYPE /usr/ucb /bin /usr/bin .)

dans son ~/.login et placer les exécutables compilés pour chaque machine dans le répertoire approprié.

La variable shell version indique les options qui ont été choisies lors de la compilation du shell.

Notez également la commande intégrée newgrp, les variables shell afsuser et echo_style et les emplacements spécifiques au système des fichiers d'entrée du shell (voir FICHIERS).

Gestion des signaux

Les shells de connexion ignorent les interruptions lors de la lecture du fichier ~/.logout. Le shell ignore les signaux de quit sauf s'il est lancé avec -q. Les shells de connexion interceptent le signal de terminaison, mais les shells non de connexion héritent du comportement de terminaison de leurs parents. Les autres signaux ont les valeurs que le shell a héritées de son parent.

Dans les scripts shell, la gestion des signaux d'interruption et de terminaison par le shell peut être contrôlée avec onintr, et sa gestion des accrochages peut être contrôlée avec hup et nohup.

Le shell se termine en cas d'accrochage (voir aussi la variable shell logout). Par défaut, les enfants du shell le font aussi, mais le shell ne leur envoie pas d'accrochage lorsqu'il se termine. hup fait en sorte que le shell envoie un accrochage à un enfant lorsqu'il se termine, et nohup configure un enfant pour ignorer les accrochages.

Gestion du terminal (+)

Le shell utilise trois ensembles de modes de terminal (“tty”) différents : ‘edit’, utilisé lors de l'édition ; ‘quote’, utilisé lors de la mise entre guillemets de caractères littéraux ; et ‘execute’, utilisé lors de l'exécution de commandes. Le shell maintient certaines configurations dans chaque mode constantes, de sorte que les commandes qui laissent le tty dans un état confus n'interfèrent pas avec le shell. Le shell correspond également aux changements de vitesse et de remplissage du tty. La liste des modes tty qui sont conservés

The setty builtin permet d'examiner et de modifier les constantes. Notez que bien que l'éditeur utilise le mode CBREAK (ou son équivalent), il prend en compte les caractères tapés à l'avance.

Les commandes echotc, settc, et telltc peuvent être utilisées pour manipuler et déboguer les capacités du terminal depuis la ligne de commande.

Sur les systèmes qui supportent SIGWINCH ou SIGWINDOW, le shell s'adapte automatiquement au redimensionnement de la fenêtre et ajuste les variables d'environnement LINES et COLUMNS si elles sont définies. La deuxième forme assigne la valeur de expr à name.

La troisième forme assigne la valeur de expr au composant d'index' de name; name et son composant d'index' doivent déjà exister.

Les quatrième et cinquième formes incrémentent (‘++’) ou décrémentent (‘--’) name ou son composant d'index.

Passons maintenant à quelques exemples. Certaines commandes ne prennent que des répertoires comme arguments, il est donc inutile de compléter des fichiers simples.

> complete cd 'p/1/d/'

complète uniquement le premier mot suivant ‘cd’ (‘p/1’) avec un répertoire. La complétion de type ‘p’ peut également être utilisée pour affiner la complétion des commandes :

> co[^D]
complete compress
> complete -co* 'p/0/(compress)/'
> co[^D]
> compress

Cette complétion complète les commandes (mots en position 0, ‘p/0’) qui commencent par ‘co’ (correspondant ainsi à ‘co*’) à ‘compress’ (le seul mot de la liste). Le tiret ‘-’ en tête indique que cette complétion doit être utilisée uniquement avec des commandes ambiguës.

> complete find 'n/-user/u/'

est un exemple de complétion de type ‘n’. Tout mot suivant ‘find’ et immédiatement suivant ‘-user’ est complété à partir de la liste des utilisateurs.

> complete cc 'c/-I/d/'

démontre la complétion de type ‘c’. Tout mot suivant ‘cc’ et commençant par ‘-I’ est complété comme un répertoire. ‘-I’ n'est pas considéré comme faisant partie du répertoire car nous avons utilisé un ‘c’ en minuscules.

Différentes listes sont utiles avec différentes commandes.

> complete alias 'p/1/a/'
> complete man 'p/*/c/'
> complete set 'p/1/s/'
> complete true 'p/1/x:Truth has no options./'

Ces commandes complètent les mots suivant ‘alias’ par des alias, ‘man’ par des commandes, et ‘set’ par des variables shell. true n'a pas d'options, donc ‘x’ ne fait rien lors de la tentative de complétion et affiche

Truth has no options.
lorsque les choix de complétion sont listés.

Notez que l'exemple ‘man’, et plusieurs autres exemples ci-dessous, auraient tout aussi bien pu utiliser ‘'c/*'’ ou ‘'n/*'’ comme ‘'p/*'’.

Les mots peuvent être complétés à partir d'une variable évaluée au moment de la complétion,

> complete ftp 'p/1/$hostnames/'
> set hostnames = (rtfm.mit.edu tesla.ee.cornell.edu)
> ftp [^D]
rtfm.mit.edu tesla.ee.cornell.edu
> ftp [^C]
> set hostnames = (rtfm.mit.edu tesla.ee.cornell.edu uunet.uu.net)
> ftp [^D]
rtfm.mit.edu tesla.ee.cornell.edu uunet.uu.net

ou à partir d'une commande exécutée au moment de la complétion :

> complete kill 'p/*/`ps | awk \{print\ \$1\}`/'
> kill -9 [^D]
23113 23377 23380 23406 23429 23529 23530 PID

Notez que la commande complete ne cite pas elle-même ses arguments, de sorte que les accolades, l'espace et ‘$’ dans ‘{print $1}’ doivent être cités explicitement.

Une commande peut avoir plusieurs complétions :

> complete dbx 'p/2/(core)/' 'p/*/c/'

complète le deuxième argument de ‘dbx’ avec le mot ‘core’ et tous les autres arguments avec des commandes. Notez que la complétion positionnelle est spécifiée avant la complétion du mot suivant. Comme les complétions sont évaluées de gauche à droite, si la complétion du mot suivant était spécifiée en premier, elle correspondrait toujours et la complétion positionnelle ne serait jamais exécutée. C'est une erreur courante lors de la définition d'une complétion.

Le motif select est utile lorsqu'une commande prend des fichiers avec seulement des formes particulières comme arguments. Par exemple,

> complete cc 'p/*/f:*.[cao]/'

complète les arguments de ‘cc’ en fichiers se terminant uniquement par ‘.c’, ‘.a’, ou ‘.o’. select peut également exclure des fichiers, en utilisant la négation d'un motif de glob tel que décrit dans la section Substitution de nom de fichier. On pourrait utiliser

> complete rm 'p/*/f:^*.{c,h,cc,C,tex,1,man,l,y}/'

pour exclure le code source précieux de la complétion de ‘rm’. Bien sûr, on pourrait toujours taper les noms exclus manuellement ou outrepasser le mécanisme de complétion en utilisant les commandes d'édition complete-word-raw ou list-choices-raw.

Les listes ‘C’, ‘D’, ‘F’, et ‘T’ sont comme ‘c’, ‘d’, ‘f’, et ‘t’ respectivement, mais elles utilisent l'argument select d'une manière différente : pour restreindre la complétion aux fichiers commençant par un préfixe de chemin particulier. Par exemple, le programme de messagerie Elm utilise ‘=’ comme abréviation pour son répertoire de messagerie. On pourrait utiliser

> complete elm c@=@F:$HOME/Mail/@

pour compléter

elm -f =
comme si c'était
elm -f ~/Mail/
Notez que nous avons utilisé le séparateur ‘@’ au lieu de ‘/’ pour éviter toute confusion avec l'argument select, et nous avons utilisé ‘$HOME’ au lieu de ‘~’ car la substitution du répertoire personnel ne fonctionne qu'au début d'un mot.

suffix est utilisé pour ajouter un suffixe non standard (pas un espace ou un ‘/’ pour les répertoires) aux mots complétés.

> complete finger 'c/*@/$hostnames/' 'p/1/u/@'

complète les arguments de ‘finger’ à partir de la liste des utilisateurs, ajoute un ‘@’, puis complète après le ‘@’ à partir de la variable ‘hostnames’. Notez encore l'ordre dans lequel les complétions sont spécifiées.

La première forme affiche la liste des événements planifiés. La variable shell sched peut être définie pour spécifier le format dans lequel la liste des événements planifiés est affichée.

Alias spéciaux (+)

S'ils sont définis, chacun de ces alias s'exécute automatiquement au moment indiqué. Ils sont tous initialement non définis.

Les alias spéciaux pris en charge sont :

beepcmd
S'exécute lorsque le shell veut faire sonner la cloche du terminal.
cwdcmd
S'exécute après chaque changement de répertoire de travail. Par exemple, si l'utilisateur travaille sur un système de fenêtrage X en utilisant xterm(1) et un gestionnaire de fenêtres re-parentant qui supporte les barres de titre comme twm(1) et que l'on fait 
> alias cwdcmd  'echo -n "^[]2;${HOST}:$cwd ^G"'

alors le shell changera le titre du xterm(1) en cours d'exécution pour qu'il soit le nom de l'hôte, un ‘:’, et le répertoire de travail courant complet. Une manière plus élaborée de faire cela est

> alias cwdcmd 'echo -n "^[]2;${HOST}:$cwd^G^[]1;${HOST}^G"'

Cela placera le nom de l'hôte et le répertoire de travail dans la barre de titre, mais seulement le nom de l'hôte dans le menu du gestionnaire d'icônes.

Notez que placer un cd, pushd, ou popd dans cwdcmd peut provoquer une boucle infinie. C'est l'opinion de l'auteur que quiconque le fera recevra ce qu'il mérite.

jobcmd
S'exécute avant que chaque commande ne soit exécutée, ou lorsque la commande change d'état. C'est similaire à postcmd, mais cela n'imprime pas les commandes internes. 
> alias jobcmd  'echo -n "^[]2;\!#:q^G"'

puis en exécutant

vi foo.c
mettra la chaîne de commande dans la barre de titre xterm.
helpcommand
Invoqué par la commande d'éditeur run-help. Le nom de la commande pour laquelle l'aide est recherchée est passé comme seul argument. Par exemple, si l'on fait 
> alias helpcommand '\!:1 --help'

alors l'affichage d'aide de la commande elle-même sera invoqué, en utilisant la convention d'appel d'aide de GNU.

Actuellement, il n'y a pas de moyen simple de tenir compte de diverses conventions d'appel (par exemple, le ‘-h’ habituel d'Unix), sauf en utilisant une table de nombreuses commandes.

periodic
S'exécute toutes les tperiod minutes. Ceci fournit un moyen pratique de vérifier les changements fréquents mais rares comme les nouveaux messages. Par exemple, si l'on fait 
> set tperiod = 30
> alias periodic checknews

alors le programme checknews(1) s'exécute toutes les 30 minutes.

Si periodic est défini mais tperiod est non défini ou défini à 0, periodic se comporte comme precmd.

precmd
S'exécute juste avant que chaque invite ne soit affichée. Par exemple, si l'on fait 
> alias precmd date

alors date(1) s'exécute juste avant que le shell ne demande chaque commande.

Il n'y a aucune limite à ce que precmd peut faire, mais la discrétion doit être utilisée.

postcmd
S'exécute avant que chaque commande ne soit exécutée. 
> alias postcmd  'echo -n "^[]2;\!#:q^G"'

puis en exécutant

vi foo.c
mettra la chaîne de commande dans la barre de titre xterm.

Spécifie l'interpréteur pour les scripts exécutables qui ne spécifient pas eux-mêmes d'interpréteur. Le premier mot doit être le chemin complet vers l'interpréteur souhaité (par exemple, ‘/bin/csh’ ou ‘/usr/local/bin/tcsh’).

You have n mails.
ou
You have n mails in name.
selon le cas. Cette fonctionnalité est principalement fournie pour les systèmes qui stockent le courrier de cette manière, comme le Andrew Mail System.

Si le premier mot de mail est numérique, il est interprété comme un intervalle de vérification de courrier différent, en secondes.

Dans des circonstances très rares, le shell peut afficher

You have mail.
au lieu de
You have new mail.

symlinks (+)
Peut être défini à plusieurs valeurs différentes pour contrôler la résolution des liens symboliques (‘symlink’) :

Si défini à ‘chase’, chaque fois que le répertoire courant change vers un répertoire contenant un lien symbolique, il est développé en nom réel du répertoire auquel le lien pointe. Cela ne fonctionne pas pour le répertoire personnel de l'utilisateur ; c'est un bug.

Si défini à ‘ignore’, le shell essaie de construire un répertoire courant relatif au répertoire courant avant que le lien n'ait été traversé. Cela signifie que

cd
à travers un lien symbolique puis
cd ..
revient au répertoire d'origine. Ceci n'affecte que les commandes intégrées et la complétion de noms de fichiers.

Si défini à ‘expand’, le shell essaie de corriger les liens symboliques en développant réellement les arguments qui ressemblent à des noms de chemins. Ceci affecte n'importe quelle commande, pas seulement les intégrées. Malheureusement, cela ne fonctionne pas pour les noms de fichiers difficiles à reconnaître, tels que ceux intégrés dans les options de commande. L'expansion peut être empêchée par des guillemets. Bien que ce paramètre soit généralement le plus pratique, il est parfois trompeur et parfois déroutant lorsqu'iln #symlinks">symlinks

Le comportement du shell avec les liens symboliques. Les valeurs possibles sont :
chase
Suivre les liens symboliques. Le répertoire courant est le répertoire pointé par le lien symbolique.
dots
Traiter les liens symboliques comme des répertoires normaux, sauf s'ils contiennent un « . » ou un « .. » dans leur nom.
expand
Comme chase, sauf que les noms de répertoires qui contiennent des liens symboliques sont développés.
ignore
Traiter les liens symboliques comme des fichiers normaux. Ceci est le défaut.
Il est possible que le shell ne reconnaisse pas correctement un argument qui doit être développé. Un compromis consiste à utiliser ignore et à utiliser la commande de l'éditeur normalize-path (associée par défaut à ^X-n) lorsque c'est nécessaire.

> cd /tmp/to/dst; echo $cwd

> cd ..; echo $cwd

Voici le comportement avec symlinks défini sur chase,

> cd /tmp/to/dst; echo $cwd
/tmp/from/src
> cd ..; echo $cwd
/tmp/from

Voici le comportement avec symlinks défini sur ignore,

> cd /tmp/to/dst; echo $cwd
/tmp/to/dst
> cd ..; echo $cwd
/tmp/to

Voici le comportement avec symlinks défini sur expand.

> cd /tmp/to/dst; echo $cwd
/tmp/to/dst
> cd ..; echo $cwd
/tmp/to
> cd /tmp/to/dst; echo $cwd
/tmp/to/dst
> cd ".."; echo $cwd
/tmp/from
> /bin/echo ..
/tmp/to
> /bin/echo ".."
..

  1. Fonctionne comme ignore pour les commandes intégrées comme cd.
  2. Est empêché par le retrait des guillemets.
  3. Se produit avant que les noms de fichiers ne soient passés aux commandes non intégrées.

LE T DANS TCSH

En 1964, DEC a produit le PDP-6. Le PDP-10 était une réimplémentation ultérieure. Il a été rebaptisé DECsystem-10 vers 1970 lorsque DEC a lancé le second modèle, le KI10.

TENEX a été créé chez Bolt, Beranek & Newman (un groupe de réflexion de Cambridge, Massachusetts) en 1972 dans le cadre d'une expérience sur les systèmes d'exploitation à mémoire virtuelle paginée à la demande. Ils ont construit un nouveau pagineur pour le PDP-10 de DEC et ont créé le SE pour l'accompagner. Il a connu un succès extrême dans le milieu universitaire.

En 1975, DEC a lancé un nouveau modèle de PDP-10, le KL10 ; ils avaient l'intention de ne proposer qu'une version de TENEX, qu'ils avaient sous licence de BBN, pour la nouvelle machine. Ils ont appelé leur version TOPS-20 (leur capitalisation est une marque déposée). Beaucoup d'utilisateurs de TOPS-10 (`The OPerating System for PDP-10') se sont opposés

LIMITATIONS

Le système limite les listes d'arguments à ARG_MAX caractères.

Le nombre d'arguments d'une commande impliquant l'expansion de noms de fichiers est limité à 1/6ème du nombre de caractères autorisés dans une liste d'arguments.

Les substitutions de commandes ne peuvent substituer plus de caractères que ceux autorisés dans une liste d'arguments.

Pour détecter les boucles, le shell restreint le nombre de substitutions d'alias sur une seule ligne à 20.

BOGUES

Lorsqu'une commande suspendue est redémarrée, le shell affiche le répertoire dans lequel elle a démarré si celui-ci est différent du répertoire courant. Cela peut être trompeur (c'est-à-dire incorrect), car le job peut avoir changé de répertoire en interne.

Les fonctions intégrées du shell ne peuvent pas être arrêtées/redémarrées. Les séquences de commandes de la forme

a ; b ; c
ne sont pas non plus gérées correctement lors d'une tentative d'arrêt. Si vous suspendez ‘b’, le shell exécutera alors immédiatement ‘c’. Ceci est particulièrement noticeable si cette expansion résulte d'un alias. Il suffit de placer la séquence de commandes entre parenthèses ‘()’ pour la forcer dans un sous-shell, c'est-à-dire :
( a ; b ; c )

Le contrôle de la sortie du tty après le démarrage des processus est primitif ; peut-être que cela inspirera quelqu'un à travailler sur une bonne interface de terminal virtuel. Dans une interface de terminal virtuel, beaucoup plus de choses intéressantes pourraient être faites avec le contrôle de la sortie.

La substitution d'alias est le plus souvent utilisée pour simuler maladroitement des procédures de shell ; des procédures de shell devraient être fournies plutôt que des alias.

Les structures de contrôle devraient être analysées plutôt que reconnues comme des commandes intégrées. Cela permettrait aux commandes de contrôle d'être placées n'importe où, d'être combinées avec '|', et d'être utilisées avec la métasyntaxe '&' et ';'.

foreach n'ignore pas les here documents lorsqu'il cherche son end.

Il devrait être possible d'utiliser les modificateurs ':' sur la sortie des substitutions de commande.

La mise à jour de l'écran pour les lignes plus longues que la largeur de l'écran est très médiocre si le terminal ne peut pas déplacer le curseur vers le haut (c'est-à-dire le type de terminal 'dumb').

HPATH et NOREBIND n'ont pas besoin d'être des variables d'environnement.

Les motifs globaux qui n'utilisent pas '?', '*', ou '[]', ou qui utilisent '{}' ou '~' ne sont pas correctement niés.

La forme de commande unique de if effectue une redirection de sortie même si l'expression est fausse et que la commande n'est pas exécutée.

ls-F inclut des caractères d'identification de fichier lors du tri des noms de fichiers et ne gère pas bien les caractères de contrôle dans les noms de fichiers. Il ne peut pas être interrompu.

La substitution de commande prend en charge plusieurs commandes et conditions, mais pas les cycles ni les goto arrière.
