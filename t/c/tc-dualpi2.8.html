DUALPI2(8) Linux DUALPI2(8)

NOM

DUALPI2 - Contrôleur intégral proportionnel à double file d'attente AQM - amélioré avec un carré

SYNTAXE


tc qdisc ... dualpi2
[ limit PAQUETS ]
[ memlimit OCTETS ]
[ coupling_factor NOMBRE ]
[ step_thresh TEMPS|PAQUETS ]
[ min_qlen_step PAQUETS ]
[ drop_on_overload | overflow ]
[ drop_enqueue | drop_dequeue ]
[ l4s_ect | any_ect ]
[ classic_protection POURCENTAGE ]
[ max_rtt TEMPS [ typical_rtt TEMPS ]]
[ target TEMPS ]
[ tupdate TEMPS ]
[ alpha flottant ]
[ beta flottant ]
[ split_gso | no_split_gso ]

DESCRIPTION

DUALPI2 AQM est une combinaison du DUALQ Coupled-AQM avec un AQM de base PI2. L'AQM PI2 (les détails peuvent être trouvés dans l'article cité ci-dessous) est à la fois une extension et une simplification de l'AQM PIE. PI2 rend inutiles de nombreuses heuristiques PIE, tout en étant capable de contrôler des contrôles de congestion évolutifs comme TCP-Prague. Avec PI2, Reno/Cubic peuvent être utilisés en parallèle avec Prague, en maintenant l'équité des fenêtres. DUALQ offre une séparation de latence entre les flux Prague à faible latence et les flux Reno/Cubic qui nécessitent une file d'attente plus grande. Les principaux objectifs de conception sont :

  • L4S - Support des contrôles de congestion à faible perte, faible latence et évolutifs
  • Option DualQ pour séparer le trafic L4S dans une file d'attente à faible latence (file L), sans nuire au trafic restant qui est planifié dans la file d'attente classique (file C) en raison du couplage de congestion
  • Stratégies de surcharge configurables
  • Utilisation du temps de séjour pour estimer de manière fiable le délai de la file d'attente
  • Implémentation simple
  • Stabilité garantie et réactivité rapide

Les paramètres PI2 détaillés (alpha, beta et tupdate) de DualPI2 sont difficiles à ajuster correctement et donnent généralement de mauvais résultats s'ils sont simplement essayés ou devinés. Ces paramètres doivent être calculés en un ensemble cohérent avec un objectif typique en tête. DualPI2 dispose d'un ensemble de paramètres par défaut qui peuvent être utilisés pour l'Internet général, où le RTT maximum est d'environ 100 ms et le RTT typique d'environ 15 ms. Il est fortement recommandé d'utiliser les paramètres d'aide max_rtt et typical_rtt (ou target) si votre déploiement s'écarte des objectifs ci-dessus (par exemple, dans un centre de données). Ces aides sont utilisées pour fournir les paramètres PI2 théoriquement optimaux (alpha, beta et tupdate) pour ces objectifs, et qui peuvent être utilisés comme base pour un réglage plus fin, l'expérimentation et les tests si désiré.

ALGORITHME

DUALPI2 est conçu pour fournir une faible perte et une faible latence au trafic L4S, sans nuire au trafic classique. À chaque intervalle de mise à jour, une nouvelle probabilité de base interne est calculée en fonction du délai de la file d'attente. La probabilité de base est mise à jour avec un delta basé sur la différence entre le délai actuel de la file d'attente et le délai cible, et la croissance de la file d'attente par rapport au délai de mise en file d'attente pendant l'intervalle tupdate précédent. Le facteur de gain intégral alpha est utilisé pour corriger lentement toute erreur persistante de file d'attente par rapport au délai cible spécifié par l'utilisateur, tandis que le facteur de gain proportionnel beta est utilisé pour compenser rapidement les changements de file d'attente (croissance ou diminution).

La probabilité de base mise à jour est utilisée comme entrée pour décider de marquer et de supprimer les paquets. DUALPI2 met à l'échelle la probabilité calculée pour chacune des deux files d'attente en conséquence. Pour la file L, la probabilité est multipliée par un coupling_factor, tandis que pour la file C, elle est élevée au carré pour compenser l'équation de taux à racine carrée de Reno/Cubic. L'identifiant ECT ( l4s_ect|any_ect ) est utilisé pour classer le trafic dans les files respectives.

Si DUALPI2 AQM a détecté une surcharge (lorsque du trafic excessif non réactif est envoyé), il peut signaler la congestion uniquement en utilisant drop, indépendamment du champ ECN, ou alternativement limiter la probabilité de suppression et laisser la file d'attente croître et éventuellement overflow (comme le tail-drop).

Des détails supplémentaires peuvent être trouvés dans la RFC citée ci-dessous.

PARAMETRES

limit PAQUETS
Limite le nombre de paquets pouvant être mis en file d'attente. Les paquets entrants seront supprimés une fois cette limite atteinte. Cette limite est commune pour les files L et C. Par défaut, 10000 paquets. Cela représente environ 125 ms de délai sur une liaison de 1 Gbps.
memlimit OCTETS
Limite la quantité totale de mémoire pouvant être utilisée. Les paquets entrants seront supprimés une fois cette limite de mémoire atteinte. Cette limite de mémoire est commune pour les files L et C. Par défaut, 10000 * MTU de l'interface en octets.
coupling_factor NOMBRE
Définit le facteur de taux de couplage entre Classic et L4S. Par défaut, 2
l4s_ect|any_ect
Configure le classificateur ECT. Les paquets dont le codepoint ECT correspond à cette valeur sont envoyés à la file L, où ils reçoivent un marquage évolutif. Par défaut, l4s_ect, c'est-à-dire l'identifiant L4S ECT(1). La définition sur any_ect fait que tous les paquets dont le champ ECN n'est pas nul sont envoyés à la file L. Cela permet la rétrocompatibilité avec, par exemple, DCTCP. Notez que DCTCP ne doit être utilisé que pour le trafic intra-DC avec des RTT très faibles et des cibles de délai AQM supérieures à ces RTT, séparé du trafic Internet (également si CC conforme à Prague), car il ne prend pas en charge toutes les exigences de Prague qui assurent qu'un contrôle de congestion peut bien fonctionner avec la gamme de RTTs sur Internet.
step_thresh TEMPS | PAQUETS
Définit le seuil d'étape pour la file L. Cela entraînera le marquage de tous les paquets dont le temps de séjour dépasse le seuil. Cette valeur peut être spécifiée en unités de temps (c'est-à-dire us, ms, s), ou en paquets (p, pkt, packet(s)). Une valeur sans unité est considérée comme étant en temps (us). Si vous définissez le seuil en paquets, assurez-vous de désactiver GRO sur les interfaces d'entrée. Par défaut, 1ms
min_qlen_step PAQUETS
Les paquets entrants mis en file d'attente L peuvent appliquer le seuil d'étape lorsque la longueur de la file L dépasse cette valeur. Par défaut, 0 paquets. Cela signifie que chaque paquet mis en file d'attente L avec un temps de séjour dépassant le seuil d'étape sera marqué.
drop_on_overload | overflow
Contrôle la stratégie de surcharge. drop_on_overload préserve le délai dans la file L en supprimant dans les deux files en cas de surcharge. overflow sacrifie le délai pour éviter les pertes, ce qui entraîne éventuellement un comportement de type taildrop une fois la limite atteinte. Par défaut, drop_on_overload
drop_enqueue | drop_dequeue
Décide quand les paquets sont supprimés ou marqués sur la base de PI. Le marquage L4S basé sur step_thresh se fait toujours à la sortie de file. Par défaut, drop_dequeue
classic_protection POURCENTAGE
Protège la file C contre le trafic non réactif dans la file L. Cela limite le délai de planification maximal dans la file C à être (100 - POURCENTAGE) fois supérieur à celui de la file L. Par défaut, 10
typical_rtt TEMPS
max_rtt TEMPS
Spécifie le temps de trajet aller-retour (RTT) maximum et/ou le RTT typique du trafic qui sera contrôlé par DUALPI2. Ces valeurs sont spécifiées à l'aide d'unités de temps (c'est-à-dire us, ms, s). Une valeur sans unité est supposée être en us. Si max_rtt ou typical_rtt n'est pas spécifié, la valeur manquante sera calculée à partir de la relation suivante : max_rtt = typical_rtt * 6. Si l'un de ces paramètres est fourni, il sera utilisé pour calculer automatiquement des valeurs appropriées pour alpha, beta, target, et tupdate, selon la relation de l'appendice A.1 dans la RFC IETF citée ci-dessous, afin d'obtenir un contrôle stable. Par conséquent, ces valeurs dérivées remplaceront celles fournies par l'utilisateur.

tc-dualpi2(8)

NAME

tc-dualpi2 — DUALPI2 algorithm

SYNOPSIS

tc … qdisc add | change | replace ... dualpi2 [ limit LIMIT ] [ max_len MAX_LEN ] [ min_len MIN_LEN ] [ depth DEPTH ] [ ecn ] [ nocwnd ] [ target TIME ] [ tupdate TIME ] [ alpha FLOAT ] [ beta FLOAT ] [ split_gso | no_split_gso ] [ any_ect ]

DESCRIPTION

DUALPI2 is an Active Queue Management (AQM) algorithm designed to provide low latency and high throughput for a variety of network conditions. It is an enhancement of the PIE (Proportional Integral controller Enhanced) algorithm, specifically adapted for dual-queue congestion control mechanisms like L4S (Low Latency, Low Loss, Scalable throughput).

It aims to maintain a target queue delay while adapting the packet drop probability based on the measured queueing delay and round-trip time (RTT).

ALGORITHM

DUALPI2 uses a Proportional-Integral (PI) controller to manage the packet drop probability. The controller adjusts the drop probability based on the difference between the current queue delay and the target queue delay.

Key features include:

  • Dual queue support: DUALPI2 can manage traffic across two queues, typically one for low latency (L-queue) and one for conventional traffic (C-queue).
  • ECN (Explicit Congestion Notification) support: It can utilize ECN markings to signal congestion without dropping packets.
  • Scalability: Designed to work well in high-speed networks and with various TCP congestion control algorithms.

PARAMETERS

limit BYTES
Maximum queue size in bytes. Defaults to the interface size if not specified.
max_len PACKETS
Maximum queue size in packets. Defaults to 2048.
min_len PACKETS
Minimum queue size in packets. Defaults to 0.
depth PACKETS
Maximum queue depth in packets. Defaults to 2048.
ecn
Enable ECN marking.
nocwnd
Do not treat ECN marking as congestion for the congestion window (cwin).
max_rtt TIME
Set the maximum round-trip time. The default range of operation for the qdisc uses max_rtt = 100ms and typical_rtt = 15ms , which is suited to controlling Internet traffic.
target TIME
Set the expected queue delay. Defaults to 15 ms. A value without units is assumed to be in us.
tupdate TIME
Set the frequency at which the system drop probability is calculated. Defaults to 16 ms. A value without units is assumed to be in microseconds. This should be less than one-third of the maximum RTT supported.
alpha float
beta float
Set alpha and beta, the integral and proportional gain factors in Hz for the PI controller. These can be calculated based on control theory. Defaults are 0.16 and 3.2 Hz, which provide stable control for RTT's up to 100ms with tupdate of 16ms. Be aware, unlike with PIE, these are the real unscaled gain factors. If not provided, they will be automatically derived from typical_rtt and max_rtt , if one of them or both are provided.
split_gso | no_split_gso
Decide how to handle aggregated packets. Either treat the aggregate as a single packet (thus all share fate with respect to marks and drops) with no_split_gso , trading some tail latency for CPU usage, or treat each packet individually (i.e., split them) with split_gso to enable fine-grained marking/dropping of packets to control queueing latencies. Defaults to split_gso

EXAMPLES

Setting DUALPI2 for the Internet with default parameters:
# sudo tc qdisc add dev eth0 root dualpi2

Setting DUALPI2 for datacenter with legacy DCTCP using ECT(0):
# sudo tc qdisc add dev eth0 root dualpi2 any_ect

FILTERS

This qdisc can be used in conjunction with tc-filters. More precisely, it will honor filters "stealing packets", as well as accept other classification schemes.

Packets whose priority/classid are set to
1 will be enqueued in the L-queue, alongside L4S traffic, and thus subject to the increased marking probability (or drops if they are marked not-ECT).
Packets whose priority/classid are set to
2 will also be enqueued in the L-queue, but will never be dropped if they are not-ECT (unless the qdisc is full and thus resorts to taildrop).
Finally, all the other classid/priority map to the C-queue.
