NOM

tc-stab - Manipulations génériques de tables de tailles

SYNTAXE

tc qdisc add ... stab
[ mtu OCTETS ] [ tsize BLOCS ]
[ mpu OCTETS ] [ overhead OCTETS ]
[ linklayer { adsl | atm | ethernet } ] ...

OPTIONS

Pour la description des OCTETS - veuillez vous référer à la section UNITÉS de tc(8).

mtu

taille maximale de paquet pour laquelle nous créons la table de tailles, supposée 2048 si non spécifiée explicitement
tsize

taille de table requise, supposée 512 si non spécifiée explicitement
mpu

taille minimale de paquet utilisée dans les calculs
overhead

surcharge par paquet (peut être négative) utilisée dans les calculs
linklayer

spécification de la couche de liaison requise.

DESCRIPTION

Les tables de tailles permettent la manipulation des tailles de paquets, telles qu'elles sont vues par le framework de planification complet (bien sûr, la taille réelle du paquet reste la même). La taille de paquet ajustée est calculée une seule fois - lorsqu'une qdisc met le paquet en file d'attente. La première mise en file d'attente de la racine l'initialise à la taille réelle du paquet.

Chaque qdisc peut utiliser une table de tailles différente, mais la taille ajustée est stockée dans une zone partagée par toute la hiérarchie des qdiscs attachés à l'interface. L'effet est que si vous avez une telle configuration, la dernière qdisc avec un stab dans une chaîne "gagne". Par exemple, considérez HFSC avec un pfifo simple attaché à l'une de ses classes feuilles. Si cette qdisc pfifo a un stab défini, elle remplacera les longueurs calculées lors de la mise en file d'attente de HFSC; et en retour, chaque fois que HFSC essaiera de retirer un paquet de la file d'attente, elle utilisera une taille potentiellement invalide dans ses calculs. Les configurations normales incluront généralement le stab défini uniquement sur la qdisc racine, mais des remplacements supplémentaires offrent une flexibilité supplémentaire pour des configurations moins habituelles.

La table de tailles initiale est calculée par l'outil tc en utilisant les paramètres mtu et tsize. L'algorithme définit la taille de chaque emplacement à la plus petite puissance de 2, de sorte que l'ensemble du mtu soit couvert par la table de tailles. Ni tsize, ni mtu n'ont besoin d'être des puissances de 2, donc la table de tailles supportera généralement plus que ce qui est requis par mtu.

Par exemple, avec mtu = 1500 et tsize = 128, une table avec 128 emplacements sera créée, où l'emplacement 0 correspondra aux tailles 0-16, l'emplacement 1 à 17 - 32, ..., l'emplacement 127 à 2033 - 2048. Les tailles attribuées à chaque emplacement dépendent du paramètre linklayer.

Le calcul de Stab est également sûr pour un cas inhabituel, lorsqu'une taille attribuée à un emplacement serait supérieure à 2^16-1 (vous perdrez cependant en précision).

Pendant la partie noyau de l'ajustement de la taille du paquet, overhead sera ajouté à la taille d'origine, puis l'emplacement sera calculé. Si la taille provoquait un dépassement, plus d'un emplacement serait utilisé pour obtenir la taille finale. Cela affectera bien sûr la précision, mais ce n'est qu'une garde contre les situations inhabituelles.

Actuellement, il existe deux méthodes pour créer les valeurs stockées dans la table de tailles - ethernet et atm (adsl):

ethernet

Il s'agit essentiellement d'un mappage 1 pour 1, donc en suivant notre exemple ci-dessus (en ignorant mpu pour un moment) l'emplacement 0 aurait 8, l'emplacement 1 aurait 16 et ainsi de suite, jusqu'à l'emplacement 127 avec 2048. Notez que mpu > 0 doit être spécifié, et les emplacements qui recevraient moins que ce qui est spécifié par mpu recevront mpu à la place. Si vous ne spécifiez pas mpu, la table de tailles ne sera pas créée du tout (cela ne ferait aucune différence), bien que toute valeur overhead soit respectée pendant les calculs.
atm, adsl

La couche de liaison ATM est constituée de cellules de 53 octets, chacune fournissant 48 octets de charge utile. De plus, toutes les cellules doivent être entièrement utilisées, donc la dernière est complétée si/quand nécessaire.

Lorsque la table de tailles est calculée, la taille ajustée qui s'inscrit correctement dans le plus petit nombre de cellules est attribuée à un emplacement. Par exemple, un paquet de 100 octets nécessite trois charges utiles de 48 octets, donc la taille finale nécessiterait 3 cellules ATM - 159 octets.

Pour les tables de tailles ATM, des emplacements de 16 octets sont parfaitement suffisants. Les valeurs par défaut de mtu et tsize créent des emplacements de 4 octets.

SURCHARGES TYPIQUES

Les valeurs suivantes sont typiques pour différents scénarios ADSL (basées sur [1] et [2]):

Basées sur LLC :
PPPoA - 14 (PPP - 2, ATM - 12)
PPPoE - 40+ (PPPoE - 8, ATM - 18, ethernet 14, potentiellement FCS - 4+rembourrage)
Bridged - 32 (ATM - 18, ethernet 14, potentiellement FCS - 4+rembourrage)
IPoA - 16 (ATM - 16)
Basées sur VC Mux :
PPPoA - 10 (PPP - 2, ATM - 8)
PPPoE - 32+ (PPPoE - 8, ATM - 10, ethernet 14, potentiellement FCS - 4+rembourrage)
Bridged - 24+ (ATM - 10, ethernet 14, potentiellement FCS - 4+rembourrage)
IPoA - 8 (ATM - 8)

Il y a quelques points importants concernant les surcharges ci-dessus :

  • IPoA dans le cas LLC nécessite SNAP, au lieu de LLC-NLPID (voir rfc2684) - c'est la raison pour laquelle il prend en fait plus de place que PPPoA.
  • Dans de rares cas, le FCS peut être conservé sur les protocoles qui incluent des trames Ethernet (Bridged et PPPoE). Dans ce cas, tout rembourrage spécifique Ethernet garantissant une taille de trame de 64 octets doit également être inclus (voir RFC2684). Autrement dit, cela garantit également que tout paquet que vous envoyez occupera au minimum 2 cellules ATM. Vous devriez définir mpu en conséquence.
  • Lorsque la table de tailles est consultée et que vous façonnez le trafic pour un autre modem/routeur, un en-tête Ethernet (sans rembourrage) sera déjà ajouté à la longueur initiale du paquet. Vous devriez compenser cela en soustrayant 14 des surcharges ci-dessus dans ce cas. Si vous façonnez directement sur le routeur (par exemple, avec un modem USB speedtouch) en utilisant un démon ppp, vous utilisez une interface ip brute sans couche sous-jacente, donc rien ne sera ajouté.

    Pour des explications plus approfondies, veuillez consulter [1] et [2].

CONSIDÉRATIONS CARTES ÉTHERNET

On oublie souvent que les cartes réseau modernes (même celles bon marché sur les cartes mères de bureau) et/ou leurs pilotes prennent souvent en charge différents mécanismes de déchargement. Dans le contexte du façonnage du trafic, 'tso' et 'gso' peuvent causer des effets indésirables, en raison des segments TCP massifs étant pris en compte lors du façonnage du trafic (y compris les calculs stab). Pour les interfaces de liaison montante lentes, il est bon d'utiliser ethtool pour désactiver les fonctionnalités de déchargement.
