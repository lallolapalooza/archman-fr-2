INFORMATIONS GÉNÉRALES

Le projet TURN Server contient le code source d'un serveur TURN et d'une bibliothèque de messagerie client TURN. Il inclut également quelques programmes supplémentaires, à des fins de test uniquement.

Voir le fichier INSTALL pour les instructions de compilation.

Après la compilation, vous aurez les binaires suivants :

1.
turnserver : Relais TURN Server. Le binaire compilé du programme TURN Server se trouve dans le sous-répertoire bin/.
2.
turnadmin : Outil d'administration TURN. Voir README.turnadmin et la page man turnadmin.
3.
turnutils_uclient. Voir README.turnutils et la page man turnutils.
4.
turnutils_peer. Voir README.turnutils et la page man turnutils.
5.
turnutils_stunclient. Voir README.turnutils et la page man turnutils.
6.
turnutils_rfc5769check. Voir README.turnutils et la page man turnutils.

Dans le sous-répertoire "examples/scripts", vous trouverez des exemples de lignes de commande pour exécuter les programmes. Les scripts sont destinés à être exécutés depuis le sous-répertoire examples/, par exemple :

$ cd examples $ ./scripts/secure_relay.sh

SYSTEMD

Si la bibliothèque de développement systemd est disponible, elle notifiera systemd de l'état du serveur.

EXÉCUTION DU SERVEUR TURN

Pour exécuter le serveur coturn en tant que démon, utilisez :

  $ turnserver -o
Notez que si vous apportez des modifications au fichier de configuration, le serveur doit être redémarré.

Note sur les options : turnserver a des noms d'options longs et courts pour la plupart des options. Certaines options n'ont que la forme longue, d'autres que la forme courte. Leur syntaxe est quelque peu différente si un argument est requis :

La forme courte doit être utilisée comme suit (par exemple) :

  $ turnserver -L 12.34.56.78
La forme longue équivalente doit utiliser le caractère "=" : 
  $ turnserver --listening-ip=12.34.56.78
S'il s'agit d'une option drapeau (aucun argument requis), alors leur utilisation est identique, par exemple : 
 $ turnserver -a
est équivalent à : 
 $ turnserver --lt-cred-mech

=====================================

NOM

turnserver - une implémentation de serveur relais TURN.

SYNOPSIS

$ turnserver [-n | -c <fichier-config> ] [options] [ --userdb=<fichier-db-utilisateur> | --psql-userdb=<chaîne-connexion-db> | --mysql-userdb=<chaîne-connexion-db> | --mongo-userdb=<chaîne-connexion-db> | --redis-userdb=<chaîne-connexion-db> ] [-z | --no-auth | -a | --lt-cred-mech ] [options]
$ turnserver -h

DESCRIPTION

Paramètres du fichier de configuration :

-n
N'utilise pas le fichier de configuration, utilise uniquement les paramètres de la ligne de commande.
-c
Nom du fichier de configuration (par défaut - turnserver.conf). Le format du fichier de configuration peut être consulté dans le fichier d'exemple examples/etc/turnserver.conf fourni. Les noms longs des options sont utilisés comme noms d'éléments de configuration dans le fichier. Si un chemin absolu n'est pas fourni, le fichier est recherché dans les répertoires suivants :
  • répertoire courant
  • répertoire courant sous-répertoire etc/
  • répertoire parent etc/
  • /etc/
  • /usr/local/etc/
  • répertoire d'installation /etc

Paramètres de la base de données utilisateur :

-b, --db, --userdb
Nom du fichier de la base de données utilisateur SQLite (par défaut - /var/db/turndb ou /usr/local/var/db/turndb ou /var/lib/turn/turndb).
-e, --psql-userdb
Chaîne de connexion à la base de données utilisateur pour PostgreSQL. Cette base de données peut être utilisée pour le mécanisme d'authentification à long terme et peut stocker la valeur secrète pour l'authentification basée sur un secret temporisé dans l'API TURN REST. Le format de la chaîne de connexion est le suivant :

"host=<hôte> dbname=<nom-db> user=<utilisateur-db> password=<mot-de-passe-utilisateur-db> connect_timeout=<secondes>" (pour Postgres 8.x ou plus récent).

Ou :

"postgresql://nomutilisateur:motdepasse@nomhote:port/nomdelabase" (pour Postgres 9.x ou plus récent).

Voir le fichier INSTALL pour plus d'explications et d'exemples.

Voir également http://www.PostgreSQL.org pour la documentation complète de PostgreSQL.

-M, --mysql-userdb
Chaîne de connexion à la base de données utilisateur pour MySQL ou MariaDB. Cette base de données peut être utilisée pour le mécanisme d'authentification à long terme et peut stocker la valeur secrète pour l'authentification basée sur un secret temporisé dans l'API TURN REST. Le format de la chaîne de connexion est le suivant :

"host=<hôte> dbname=<nom-db> user=<utilisateur-db> password=<mot-de-passe-utilisateur-db> connect_timeout=<secondes> read_timeout=<secondes>"

Voir le fichier INSTALL pour plus d'explications et d'exemples.

Voir également http://www.mysql.org ou http://mariadb.org pour la documentation complète de MySQL.

Paramètres facultatifs de la chaîne de connexion pour les communications sécurisées (SSL) : ca, capath, cert, key, cipher (voir http://dev.mysql.com/doc/refman/5.1/en/ssl-options.html pour la description des options de commande).

--secret-key-file
C'est le chemin du fichier qui contient la clé secrète de chiffrement AES lors de l'utilisation du chiffrement du mot de passe MySQL. Si vous souhaitez utiliser le mot de passe au format chiffré dans la chaîne de connexion MySQL, définissez dans cette option le chemin du fichier de la clé secrète. La clé utilisée pour chiffrer le mot de passe MySQL. Attention : Si cette option est définie, alors le mot de passe MySQL doit être défini dans l'option "mysql-userdb" au format chiffré ! Si vous souhaitez utiliser un mot de passe en clair, ne définissez pas cette option !
-J, --mongo-userdb
Chaîne de connexion à la base de données utilisateur pour MongoDB. Cette base de données peut être utilisée pour le mécanisme d'authentification à long terme et peut stocker la valeur secrète pour l'authentification basée sur un secret temporisé dans l'API TURN REST. Le format de la chaîne de connexion est le suivant :

"mongodb://nomutilisateur:motdepasse@hote:port/nomdelabase?options"

Voir le fichier INSTALL pour plus d'explications et d'exemples.

Voir également http://docs.mongodb.org/manual/ pour la documentation complète de MongoDB.

-N, --redis-userdb
Chaîne de connexion à la base de données utilisateur pour Redis. Cette base de données peut être utilisée pour le mécanisme d'authentification à long terme et peut stocker la valeur secrète pour l'authentification basée sur un secret temporisé dans l'API TURN REST. Le format de la chaîne de connexion est le suivant :

"ip=<adresse-ip> dbname=<numéro-db> password=<mot-de-passe-db> connect_timeout=<secondes>"

Voir le fichier INSTALL pour plus d'explications et d'exemples.

Voir également http://redis.io pour la documentation complète de Redis.

Options :

-v, --verbose
Mode verbeux modéré.
-V, --Verbose
Mode très verbeux, très ennuyeux et non recommandé.
-o, --daemon
Exécuter le serveur en tant que démon.

--no-software-attribute Mode production : masquer la version du logiciel.

<
-f, --fingerprint
Utilise les empreintes digitales dans les messages TURN. Si une requête entrante contient une empreinte digitale, le serveur TURN ajoutera toujours des empreintes digitales aux messages de cette session, indépendamment du paramètre par serveur.
-a, --lt-cred-mech
Utilise le mécanisme d'authentification à long terme (celui dont vous avez besoin pour l'utilisation WebRTC).
-z, --no-auth
N'utilise aucun mécanisme d'authentification, autorise l'accès anonyme. Contraire aux options -a et -A. C'est l'option par défaut lorsqu'aucune option liée à l'authentification n'est définie. Par défaut, aucun mécanisme d'authentification n'est utilisé - tout utilisateur est autorisé.
--use-auth-secret
Indicateur de l'API REST TURN. Indicateur qui définit une option d'autorisation WebRTC spéciale basée sur un secret d'authentification. Le but de cette fonctionnalité est de prendre en charge l'API REST du serveur TURN telle que décrite dans la section API REST TURN ci-dessous. Cette option utilise un horodatage comme partie d'un nom d'utilisateur combiné : usercombo -> "timestamp:username", utilisateur turn -> usercombo, mot de passe turn -> base64(hmac(buffer_entrée = usercombo, clé = secret_partagé)). Cela permet de comptabiliser les identifiants TURN pour un ID utilisateur spécifique. Si vous n'avez pas d'ID approprié, l'horodatage seul peut être utilisé. Cette option active simplement l'authentification basée sur un secret. La valeur réelle du secret est définie soit par l'option static-auth-secret, soit peut être trouvée dans la table turn_secret de la base de données.
--oauth
Prend en charge l'authentification oAuth, comme dans le RFC 7635 STUN/TURN tiers.
--dh566
Utilise une clé TLS DH prédéfinie de 566 bits. La taille par défaut de la clé est de 2066.
--dh1066
Utilise une clé TLS DH prédéfinie de 1066 bits. La taille par défaut de la clé est de 2066.
--tlsv1
Définit TLSv1 comme version minimale de protocole prise en charge.
--tlsv1_1
Définit TLSv1.1 comme version minimale de protocole prise en charge.
--no-tlsv1_2
Définit TLSv1.3 comme version minimale de protocole prise en charge.
--no-udp
Ne démarre pas les écouteurs clients UDP.
--no-tcp
Ne démarre pas les écouteurs clients TCP.
--no-tls
Ne démarre pas les écouteurs clients TLS.
--no-dtls
Ne démarre pas les écouteurs clients DTLS.
--no-udp-relay
N'autorise pas les points d'extrémité de relais UDP définis dans le RFC 5766, utilise uniquement les points d'extrémité de relais TCP tels que définis dans le RFC 6062.
--no-tcp-relay
N'autorise pas les points d'extrémité de relais TCP définis dans le RFC 6062, utilise uniquement les points d'extrémité de relais UDP tels que définis dans le RFC 5766.
--no-stdout-log
Indicateur pour empêcher les messages de journalisation sur la sortie standard. Par défaut, tous les messages de journalisation sont envoyés à la sortie standard et au fichier journal configuré. Avec cette option, tout sera envoyé uniquement au fichier journal (sauf si le fichier journal lui-même est la sortie standard).
--syslog
Avec cet indicateur, tous les journaux seront redirigés vers le journal système (syslog).
--simple-log
Cet indicateur signifie qu'aucun changement de fichier journal ne sera utilisé, et le nom du fichier journal sera construit tel quel, sans ajout du PID et de la date. Cette option peut être utilisée, par exemple, conjointement avec l'outil logrotate.
--new-log-timestamp
Active l'horodatage ISO-8601 complet dans tous les journaux.
--new-log-timestamp-format
<format> Définit le format de l'horodatage (au format strftime(1))
--log-binding
Journalise les requêtes de liaison STUN. Ceci est maintenant désactivé par défaut pour éviter les attaques par déni de service.
--secure-stun
Exige l'authentification de la requête de liaison STUN. Par défaut, les clients sont autorisés à accéder anonymement à la fonctionnalité de liaison STUN.
-S, --stun-only
Fonctionne uniquement en tant que serveur STUN, toutes les requêtes TURN seront ignorées. Option pour supprimer la fonctionnalité TURN, seules les requêtes STUN seront traitées.
--no-stun
Fonctionne uniquement en tant que serveur TURN, toutes les requêtes STUN seront ignorées. Option pour supprimer la fonctionnalité STUN, seules les requêtes TURN seront traitées.
--allow-loopback-peers
Autorise les pairs sur les adresses de bouclage (127.x.x.x et ::1). Autorisé uniquement pour les tests dans un environnement de développement ! En production, cela introduit une vulnérabilité de sécurité potentielle, et donc pour des raisons de sécurité, il n'est pas autorisé à l'utiliser conjointement avec un mot de passe CLI vide.
--no-multicast-peers
Interdit les pairs sur les adresses de diffusion connues (224.0.0.0 et supérieur, et FFXX:*).
--mobility
Support des spécifications de mobilité avec ICE (MICE).
--no-cli
Désactive le support CLI. Par défaut, il est toujours activé. Voir aussi les options --cli-ip et --cli-port.
--server-relay
Relais serveur. OPTION NON STANDARD ET DANGEREUSE. Uniquement pour les applications qui souhaitent exécuter des applications serveur sur les points d'extrémité de relais. Cette option élimine la vérification des permissions IP sur les paquets entrants vers les points d'extrémité de relais. Voir http://tools.ietf.org/search/rfc5766#section-17.2.3 .
--udp-self-balance
(recommandé uniquement pour les anciennes versions de Linux) Équilibre automatiquement le trafic UDP sur les serveurs auxiliaires (si configurés). L'équilibrage de charge utilise le mécanisme ALTERNATE-SERVER. Le client TURN doit prendre en charge la réponse 300 ALTERNATE-SERVER pour cette fonctionnalité.
--check-origin-consistency
Indicateur qui définit la vérification de la cohérence de l'origine : tout au long de la session, toutes les requêtes doivent avoir la même valeur d'attribut ORIGIN principale (si l'ORIGINE a été initialement utilisée par la session).
--prometheus
Active les métriques Prometheus. Par défaut, il est désactivé. Il écoutera sur le port 9641 sous le chemin /metrics. Le chemin / sur ce port peut également être utilisé comme contrôle de santé.
--prometheus-username-labels
Active l'étiquetage des métriques de trafic Prometheus avec les noms d'utilisateur des clients. L'étiquetage avec les noms d'utilisateur des clients est désactivé par défaut, car cela peut entraîner des fuites de mémoire lors de l'utilisation de l'authentification avec des noms d'utilisateur éphémères (par exemple, l'API REST TURN).
--prometheus-port
Port d'écoute Prometheus (Défaut : 9641).
-h
Aide.

Options avec valeurs :

--stale-nonce[=<valeur>]
Utilise une sécurité supplémentaire avec une valeur de nonce ayant une durée de vie limitée, en secondes (par défaut 600 secondes). Définissez-le à 0 pour une durée de vie de nonce illimitée.
--max-allocate-lifetime
Définit la valeur maximale pour la durée de vie de l'allocation. Par défaut à 3600 secondes.
--channel-lifetime
Définit la durée de vie de la liaison de canal, par défaut à 600 secondes. Cette valeur NE DOIT PAS être modifiée à des fins de production.
--permission-lifetime
Définit la durée de vie de la permission. Par défaut à 300 secondes. Cela NE DOIT PAS être modifié à des fins de production.
-d, --listening-device
Périphérique d'interface d'écoute. (NON RECOMMANDÉ. Fonctionnalité optionnelle, uniquement sous Linux). Le processus turnserver doit avoir des privilèges root pour lier le point d'écoute à un périphérique. Si turnserver doit être exécuté en tant que processus sans privilèges root, n'utilisez alors pas ce paramètre.
-L, --listening-ip
Adresse IP d'écoute du serveur de relais. Plusieurs écouteurs peuvent être spécifiés, par exemple : -L ip1 -L ip2 -L ip3 Si aucune IP n'est spécifiée, toutes les adresses IP système IPv4 et IPv6 seront utilisées pour l'écoute. Les mêmes IP peuvent être utilisées comme IP d'écoute et de relais.
-p, --listening-port
Port d'écoute TURN pour les écouteurs UDP et TCP (Défaut : 3478). Remarque : en fait, les sessions TLS et DTLS peuvent également se connecter aux ports TCP et UDP « en clair » - si autorisé par la configuration.
--tls-listening-port
Port d'écoute TURN pour les écouteurs TLS et DTLS (Défaut : 5349). Remarque : en fait, les sessions TCP et UDP « en clair » peuvent également se connecter aux ports TLS et DTLS - si autorisé par la configuration. Le serveur TURN reconnaît « automatiquement » le type de trafic. En fait, deux points d'écoute (celui « en clair » et celui « tls ») sont équivalents en termes de fonctionnalité ; mais nous conservons les deux points d'écoute pour satisfaire les spécifications RFC 5766. Pour les connexions TCP sécurisées, nous prenons actuellement en charge les versions TLS 1.2, 1.3. Pour les connexions UDP sécurisées, nous prenons en charge la version DTLS 1.
--alt-listening-port
Port d'écoute alternatif pour les écouteurs UDP et TCP ; la valeur par défaut (ou zéro) signifie « port d'écoute plus un ». Ceci est nécessaire pour STUN CHANGE_REQUEST - dans le sens RFC 5780 ou dans l'ancien sens RFC 3489 - pour NAT
discovery de comportement). Le serveur TURN ne prend en charge CHANGE_REQUEST que s'il est démarré avec plus d'une adresse IP d'écoute de la même famille (IPv4 ou IPv6). CHANGE_REQUEST n'est pris en charge que par le protocole UDP ; les autres protocoles écoutent sur ce point de terminaison uniquement pour la « symétrie ».
--alt-tls-listening-port
Port d'écoute alternatif pour les protocoles TLS et DTLS. La valeur par défaut (ou zéro) signifie « port d'écoute TLS plus un ».
--tcp-proxy-port
Prend en charge les connexions à partir d'un équilibreur de charge TCP sur ce port. L'équilibreur de charge doit utiliser le protocole proxy binaire. (https://www.haproxy.org/download/1.8/doc/proxy-protocol.txt)
--aux-server
Point de terminaison d'écoute de serveur STUN/TURN auxiliaire. Les serveurs auxiliaires disposent de fonctionnalités TURN et STUN quasi complètes. Les (mineures) limitations sont :
1)
Les serveurs auxiliaires n'ont pas de ports alternatifs et ne prennent pas en charge la fonctionnalité STUN RFC 5780 (CHANGE REQUEST).
2)
Les serveurs auxiliaires ne renvoient jamais de réponse ALTERNATIVE-SERVER.

Les formats valides sont 1.2.3.4:5555 pour IPv4 et [1:2::3:4]:5555 pour IPv6. Il peut y avoir plusieurs options aux-server, chacune sera utilisée pour écouter les requêtes des clients.

-i, --relay-device
Périphérique d'interface de relais pour les sockets de relais (NON RECOMMANDÉ. Facultatif, uniquement sous Linux).
-E, --relay-ip
Adresse de relais (l'adresse IP locale qui sera utilisée pour relayer les paquets vers le pair). Plusieurs adresses de relais peuvent être utilisées : -E ip1 -E ip2 -E ip3 Les mêmes adresses IP peuvent être utilisées à la fois comme adresses IP d'écoute et comme adresses IP de relais. Si aucune adresse IP de relais n'est spécifiée, le serveur turnserver appliquera la politique par défaut : il décidera lui-même des adresses de relais à utiliser, et utilisera toujours l'adresse IP du socket client comme adresse IP de relais de la session TURN (si l'adresse IP de relais demandée est de la même famille que la famille du socket client).
-X, --external-ip
Correspondance d'adresse publique/privée du serveur TURN, si le serveur est derrière un NAT. Dans cette situation, si un -X est utilisé sous la forme « -X <ip> », cette adresse ip sera signalée comme adresse IP de relais de toutes les allocations. Ce scénario ne fonctionne que dans le cas simple où une seule adresse de relais est utilisée, et aucune fonctionnalité CHANGE_REQUEST n'est requise. Cette adresse de relais unique doit être mappée par le NAT à l'adresse IP « externe ». La valeur « external-ip », si elle n'est pas vide, est renvoyée dans le champ XOR-RELAYED-ADDRESS. Pour cette adresse IP « externe », le NAT doit rediriger les ports directement (le port de relais 12345 doit toujours être mappé au même port « externe » 12345). Dans un cas plus complexe où plus d'une adresse IP est impliquée, cette option doit être utilisée plusieurs fois, chaque entrée devant avoir la forme « -X <ip-publique/ip-privée> », pour mapper toutes les adresses impliquées. La fonctionnalité de découverte NAT STUN CHANGE_REQUEST (RFC5780 ou RFC3489) fonctionnera correctement, si les adresses sont bien mappées, même si le serveur TURN lui-même est derrière un NAT. Par défaut, cette valeur est vide et aucun mappage d'adresse n'est utilisé.
-m, --relay-threads
Nombre de threads de relais pour gérer les connexions établies (en plus du thread d'authentification et du thread d'écoute). S'il est explicitement défini à 0, l'application exécute le processus de relais dans un seul thread, dans le même thread que le processus d'écoute (le thread d'authentification restera un thread séparé). S'il n'est pas défini, un algorithme optimal par défaut sera employé (dépendant du système d'exploitation). Dans les anciens systèmes Linux (avant le noyau Linux 3.9), le nombre de threads UDP est toujours un thread par point de terminaison d'écoute réseau, sauf si « -m 0 » ou « -m 1 » est défini.
--min-port
Borne inférieure de la plage de ports UDP pour l'allocation des points de terminaison de relais. La valeur par défaut est 49152, conformément à la RFC 5766.
--max-port
Borne supérieure de la plage de ports UDP pour l'allocation des points de terminaison de relais. La valeur par défaut est 65535, conformément à la RFC 5766.
-u, --user
Identifiants utilisateur pour le mécanisme de sécurité à long terme, sous la forme séparée par des deux-points : nom d'utilisateur:clé. Plusieurs comptes d'utilisateurs peuvent être utilisés en ligne de commande. La clé est soit le mot de passe de l'utilisateur, soit la clé est générée par la commande turnadmin. Dans ce dernier cas, la clé doit être précédée des symboles 0x. La clé est calculée sur le nom de l'utilisateur, le domaine de l'utilisateur et le mot de passe de l'utilisateur. Ce paramètre ne peut pas être utilisé avec l'API REST de TURN.
-r, --realm
Le domaine par défaut à utiliser pour les utilisateurs lorsqu'aucune relation origine/domaine explicite n'a été trouvée dans la base de données, ou si le serveur TURN n'utilise aucune base de données (uniquement les paramètres de la ligne de commande et le fichier userdb). Doit être utilisé avec le mécanisme d'identifiants à long terme ou avec l'API REST de TURN.
-C, --rest-api-separator
C'est le symbole (caractère) séparateur de timestamp/nom d'utilisateur dans l'API REST de TURN. La valeur par défaut est :.
-q, --user-quota
Quota d'allocations par utilisateur : combien d'allocations concurrentes un utilisateur peut créer. Cette option peut également être définie via la base de données, pour un domaine particulier.
-Q, --total-quota
Quota total d'allocations : limite globale sur les allocations concurrentes. Cette option peut également être définie via la base de données, pour un domaine particulier.
-s, --max-bps
Débit maximal en octets par seconde qu'une session TURN est autorisée à gérer (les flux réseau d'entrée et de sortie sont traités séparément). Tout ce qui dépasse cette limite sera abandonné ou temporairement supprimé (dans les limites du tampon disponible). Cette option peut également être définie via la base de données, pour un domaine particulier.
-B, --bps-capacity
Capacité maximale du serveur. Débit total en octets par seconde que le serveur TURN est autorisé à allouer pour les sessions, combiné (les flux réseau d'entrée et de sortie sont traités séparément).
--static-auth-secret
Valeur secrète d'authentification statique (une chaîne de caractères) pour l'API REST de TURN uniquement. Si elle n'est pas définie, le serveur TURN essaiera d'utiliser la valeur dynamique dans la table turn_secret de la base de données utilisateur (si elle est présente). La valeur stockée en base de données peut être modifiée à la volée par un programme séparé, c'est pourquoi cet autre mode est dynamique. Plusieurs secrets partagés peuvent être utilisés (à la fois stockés en base de données et en mode « statique »).
--no-auth-pings
Désactive les vérifications de santé périodiques des tables de secrets d'authentification « dynamiques ».
--no-dynamic-ip-list
N'utilise pas la liste dynamique d'adresses IP autorisées/refusées.
--no-dynamic-realms
N'utilise pas l'attribution dynamique de domaines et les options.
--server-name
Nom du serveur utilisé à des fins d'authentification OAuth. La valeur par défaut est le nom du domaine.
--cert
Fichier de certificat, format PEM. Les mêmes règles de recherche de fichiers s'appliquent qu'au fichier de configuration. Si les options --no-tls et --no-dtls sont toutes deux spécifiées, ce paramètre n'est pas nécessaire. La valeur par défaut est turn_server_cert.pem.
--pkey
Fichier de clé privée, format PEM. Les mêmes règles de recherche de fichiers s'appliquent qu'au fichier de configuration. Si les options --no-tls et --no-dtls sont toutes deux spécifiées, ce paramètre n'est pas nécessaire. La valeur par défaut est turn_server_pkey.pem.
--pkey-pwd
Si le fichier de clé privée est chiffré, alors ce mot de passe doit être utilisé.
--cipher-list

(courant) (le premier succès d'ouverture de fichier sera utilisé). Avec cette option, vous pouvez définir le nom du fichier journal définitif. la famille d'adresses du point de terminaison réseau du client. Voir RFC 5389 et RFC 5766 pour la description de la fonctionnalité ALTERNATE-SERVER. Pour atténuer ce conflit, les adresses IPv6 littérales sont entourées de crochets dans ces identificateurs de ressources, par exemple : [2001:db8:85a3:8d3:1319:8a2e:370:7348]:3478 . Par exemple, si nous avons 4 serveurs alternatifs, chaque serveur recevra 25 % de toutes les requêtes ALLOCATE. Une adresse de serveur TURN alternative peut être utilisée plus d'une fois avec l'option alternate-server, cela peut donc émuler une « pondération » des serveurs.

3)
S'il n'y a pas de règle « autorisée » qui correspond à l'adresse, et s'il y a une règle « refusée » qui correspond à l'adresse, alors elle est refusée.

API REST TURN

Dans WebRTC, le navigateur obtient les informations de connexion TURN à partir du serveur web. Ces informations sont sécurisées car elles contiennent les identifiants TURN nécessaires. Comme ces identifiants sont transmis sur les réseaux publics, il existe une faille de sécurité potentielle.

Si nous devons transmettre des informations de valeur sur le réseau public, ces informations doivent avoir une durée de vie limitée. Ainsi, la personne qui obtiendrait ces informations sans autorisation ne pourrait causer que des dommages limités.

C'est ainsi qu'est née l'idée de l'API REST TURN - des identifiants TURN à durée de vie limitée. Ce mécanisme de sécurité repose sur le mécanisme d'identifiants à long terme. L'idée principale de l'API REST est que le serveur web fournit les identifiants au client, mais ces identifiants ne peuvent être utilisés que pendant une durée limitée par une application qui doit établir une connexion au serveur TURN.

Le mécanisme d'identifiants à long terme ("classique") (LTCM) est décrit ici :

http://tools.ietf.org/html/rfc5389#section-10.2

http://tools.ietf.org/html/rfc5389#section-15.4

Pour l'authentification, chaque utilisateur doit connaître deux choses : le nom d'utilisateur et le mot de passe. Facultativement, l'utilisateur doit fournir la valeur ORIGIN, afin que le serveur puisse déterminer le royaume à utiliser pour l'utilisateur. Les valeurs nonce et realm sont fournies par le serveur TURN. Mais le LTCM ne dit rien sur la nature et la persistance du nom d'utilisateur et du mot de passe ; c'est ce qu'utilise l'API REST.

Dans l'API REST TURN, il n'y a pas de mots de passe persistants pour les utilisateurs. Un utilisateur n'a qu'un nom d'utilisateur. Le mot de passe est toujours temporaire, et il est généré par le serveur web à la demande, lorsque l'utilisateur accède à la page WebRTC. Et, en fait, pour une session temporaire unique, le nom d'utilisateur est également fourni à l'utilisateur.

L'utilisateur temporaire est généré comme suit :

nom-utilisateur-temporaire="horodatage" + ":" + "nom-utilisateur"

où nom-utilisateur est le nom d'utilisateur persistant, et le format de l'horodatage est simplement les secondes depuis 1970 - la même valeur que celle renvoyée par la fonction time(NULL).

Le mot de passe temporaire est obtenu en appliquant la fonction HMAC-SHA1 sur le nom d'utilisateur temporaire, avec le secret partagé comme clé HMAC, puis le résultat est encodé :

mot-de-passe-temporaire = base64_encode(hmac-sha1(secret-partage, nom-utilisateur-temporaire))

Le serveur TURN et le serveur web connaissent le même secret partagé. La manière dont le secret partagé est distribué entre les entités impliquées est laissée aux détails de déploiement de WebRTC - cela dépasse le cadre de l'API REST TURN.

Ainsi, un horodatage est utilisé pour le calcul du mot de passe temporaire, et cet horodatage peut être récupéré à partir du nom d'utilisateur temporaire. Ces informations sont précieuses, mais temporaires, tant que l'horodatage n'est pas expiré. Sans connaître le secret partagé, un nouveau mot de passe temporaire ne peut pas être généré.

Tout cela est formellement décrit dans le document sur l'API REST TURN de Justin Uberti, que l'on peut obtenir en suivant le lien "TURN REST API" sur la page du projet TURN Server : https://github.com/coturn/coturn/.

Une fois que le nom d'utilisateur et le mot de passe temporaires sont obtenus par l'application cliente (navigateur), le reste n'est que le mécanisme "classique" d'identifiants à long terme. Pour les développeurs, nous allons le décrire étape par étape ci-dessous :

  • un nouveau client TURN envoie une requête au serveur TURN. Facultativement, il ajoute le champ ORIGIN.
  • Le serveur TURN constate qu'il s'agit d'un nouveau client et que le message n'est pas authentifié.
  • Le serveur TURN génère une chaîne nonce aléatoire et renvoie une erreur 401 au client, avec le nonce et le realm inclus. Si le champ ORIGIN était présent dans la requête du client, cela peut affecter la valeur du realm que le serveur choisit pour le client.
  • Le client voit l'erreur 401 et extrait deux valeurs de la réponse d'erreur : le nonce et le realm.
  • Le client utilise le nom d'utilisateur, le realm et le mot de passe pour produire une clé :
         clé = MD5(nom-utilisateur ":" realm ":" SASLprep(mot-de-passe))
(SASLprep est décrit ici : http://tools.ietf.org/html/rfc4013)
  • Le client forme une nouvelle requête, ajoute le nom d'utilisateur, le realm et le nonce à la requête. Ensuite, le client calcule et ajoute le champ d'intégrité à la requête. C'est la partie la plus délicate du processus, et elle est décrite à la fin de la section 15.4 : http://tools.ietf.org/html/rfc5389#section-15.4
  • Le client ajoute facultativement le champ fingerprint. Cela peut également être une procédure délicate, décrite dans la section 15.5 du même document. WebRTC utilise généralement des messages TURN avec empreinte digitale.
  • Le serveur TURN reçoit la requête, lit le nom d'utilisateur.
  • Ensuite, le serveur TURN vérifie que le nonce et le realm dans la requête sont valides.
  • Ensuite, le serveur TURN calcule la clé.
  • Ensuite, le serveur TURN calcule le champ d'intégrité.
  • Ensuite, le serveur TURN compare le champ d'intégrité calculé avec celui reçu - ils doivent être identiques. Si les champs d'intégrité diffèrent, la requête est rejetée.

Lors des communications ultérieures, le client peut suivre exactement la même séquence, mais pour des raisons d'optimisation, le client, ayant déjà des informations sur le realm et le nonce, pré-calcule la chaîne d'intégrité pour chaque requête, de sorte que la réponse d'erreur 401 devienne inutile. Le serveur TURN peut utiliser l'option "--stale-nonce" pour une sécurité supplémentaire : au bout d'un certain temps, le nonce expire et le client obtiendra une réponse d'erreur 438 avec le nouveau nonce, et le client devra alors utiliser ce nouveau nonce.

Lors des communications ultérieures, le serveur et le client supposeront toujours le même mot de passe - le mot de passe d'origine devient un paramètre de session et n'expire jamais. Le mot de passe ne change donc pas tant que la session est valide et non expirée. Ainsi, si la session est correctement maintenue, elle peut durer indéfiniment, même si le mot de passe de l'utilisateur a déjà été modifié (dans la base de données). La session utilise simplement l'ancien mot de passe. Une fois la session déconnectée, le client devra utiliser le nouveau mot de passe pour se reconnecter (si le mot de passe a été modifié).

Un exemple où un nouveau secret partagé est généré toutes les heures par le serveur TURN et ensuite fourni au serveur web à distance est donné dans les exemples de scripts/scripts/restapi/shared_secret_maintainer.pl.

Il est très important que le nonce soit totalement aléatoire et qu'il soit différent pour chaque client et chaque session.

BASES DE DONNÉES

Pour la base de données utilisateur, le turnserver dispose des options suivantes :

1)
Les utilisateurs peuvent être définis en ligne de commande, avec plusieurs options -u ou --user. Évidemment, seuls quelques utilisateurs peuvent être ainsi définis, et leurs identifiants sont fixes pendant la durée de vie du processus turnserver.
2)
Les utilisateurs peuvent être stockés dans une base de données SQLite. Le fichier de base de données SQLite par défaut est /var/db/turndb ou /usr/local/var/db/turndb ou /var/lib/turn/turndb.
3)
Les utilisateurs peuvent être stockés dans une base de données PostgreSQL, si le turnserver a été compilé avec le support PostgreSQL. Chaque fois que turnserver vérifie les identifiants utilisateur, il lit la base de données (de manière asynchrone, bien sûr, afin que le flux de paquets actuel ne soit pas retardé), donc tout changement dans le contenu de la base de données est immédiatement visible par le turnserver. C'est la méthode si vous avez besoin de la meilleure scalabilité. Le schéma de la base de données se trouve dans le fichier schema.sql. Pour les identifiants à long terme, vous devez définir les "clés" pour les utilisateurs ; les "clés" sont générées par l'utilitaire turnadmin. Pour la génération de clés, vous avez besoin du nom d'utilisateur, du mot de passe et du realm. Tous les utilisateurs de la base de données doivent utiliser la même valeur de realm ; si vous décidez plus tard de changer le nom du realm, vous devrez régénérer toutes les clés utilisateur (ce qui peut être fait dans un script batch). Voir le fichier turndb/testsqldbsetup.sql comme exemple.
4)
Il en va de même pour la base de données MySQL. Le même fichier de schéma est applicable. Les mêmes considérations sont applicables.
5)
Il en va de même pour la base de données Redis, mais la base de données Redis a un schéma différent - on peut la trouver (sous forme d'explication) dans schema.userdb.redis. De plus, dans Redis, vous pouvez stocker à la fois des "clés" et des mots de passe ouverts (pour les identifiants à long terme) - l'option "mot de passe ouvert" est moins sécurisée mais plus pratique pour les environnements à faible sécurité. Voir le fichier turndb/testredisdbsetup.sh comme exemple.
6)
Si une base de données est utilisée, les utilisateurs peuvent être divisés en plusieurs realms indépendants. Chaque realm peut être administré séparément, et chaque realm peut avoir son propre ensemble d'utilisateurs et ses propres options de performance (max-bps, user-quota, total-quota).
7)
Si vous utilisez MongoDB, la base de données sera configurée automatiquement pour vous.
8)
Bien sûr, le turnserver peut être utilisé en mode non sécurisé, lorsque les utilisateurs sont autorisés à établir des sessions anonymement. Mais dans la plupart des cas (comme WebRTC), cela ne fonctionnera pas.

Pour la base de données de statut et de statistiques, il y a deux choix :

1)
Le choix le plus simple est de ne pas l'utiliser. Ne définissez pas l'option --redis-statsdb, et cette fonctionnalité sera simplement ignorée.
2)
Si vous choisissez de l'utiliser, définissez l'option --redis-statsdb. Il peut s'agir de la même base de données que dans l'option --redis-userdb, ou d'une base de données différente. Vous pourriez vouloir utiliser une base de données différente pour des raisons de sécurité ou de commodité. De plus, vous pouvez utiliser différents systèmes de gestion de bases de données pour la base de données utilisateur et pour la base de données de statut et de statistiques. Par exemple, vous pouvez utiliser MySQL comme base de données utilisateur, et utiliser redis pour les statistiques. Ou vous pouvez utiliser Redis pour les deux.

Ainsi, nous avons 6 choix pour la gestion des utilisateurs et 2 choix pour la gestion des statistiques. Ces deux choix sont totalement indépendants. Vous avez donc globalement 6 * 2 = 12 façons de gérer les informations persistantes, choisissez celle qui vous convient le mieux.

Vous n'avez pas à gérer les informations de la base de données "manuellement" - le programme turnadmin peut tout gérer pour vous. Pour PostgreSQL et MySQL, il vous suffira de créer une base de données vide avec le script SQL schema.sql. Wit

h Redis, vous n'avez même pas à faire cela : exécutez simplement turnadmin et il configurera les utilisateurs pour vous (voir les manuels de turnadmin). Si vous utilisez SQLite, alors turnserver ou turnadmin initialisera la base de données vide pour vous au démarrage. Le processus d'installation du serveur TURN crée une base de données SQLite vide et initialisée à l'emplacement par défaut (/var/db/turndb ou /usr/local/var/db/turndb ou /var/lib/turn/turndb, selon le système).

ALPN

Le serveur prend en charge les ALPN "stun.turn" et "stun.nat-discovery". Si le serveur reçoit un message TLS/DTLS ClientHello contenant l'un ou l'autre de ces ALPN, le serveur choisit le premier label stun.* et le renvoie (dans le ServerHello) dans le champ d'extension ALPN. Si aucun label stun.* n'est trouvé, le serveur n'inclut pas l'information ALPN dans le ServerHello.

  • /log/
  • /var/tmp
  • /tmp
  • répertoire courant

INTERFACE DE GESTION HTTPS

Le processus turnserver fournit un accès Web HTTPS comme interface de statistiques et de gestion de base. Le turnserver écoute les connexions d'administration HTTPS entrantes sur les mêmes ports que le listener TURN/STUN principal. Les pages d'administration Web sont basiques et auto-explicatives.

Pour activer l'interface HTTPS, la table de base de données admin_user doit être peuplée avec le(s) compte(s) d'utilisateur d'administration. Un utilisateur d'administration peut être un superutilisateur (s'il n'est pas assigné à un realm particulier) ou un utilisateur restreint (s'il est assigné à un realm). Les utilisateurs d'administration restreints ne peuvent effectuer que des actions limitées, dans leurs realms correspondants.

=================================

CLI TELNET

Le processus turnserver fournit un accès CLI telnet comme interface de statistiques et de gestion de base. Par défaut, le turnserver démarre un listener CLI telnet sur l'IP 127.0.0.1 et le port 5766. Cela peut être modifié par les options de ligne de commande du processus turnserver (voir les options --cli-ip et --cli-port). La liste complète des commandes CLI telnet est fournie dans la sortie de la commande "help" dans la CLI telnet.

=================================

CLUSTERS

Le **serveur TURN** peut faire partie d'une installation en cluster. Mais, pour supporter la fonctionnalité de "ports pairs" (paires de flux RTP/RTCP), les requêtes du client provenant d'une IP particulière doivent être livrées à la même instance du **serveur TURN**, ce qui nécessite une configuration réseau adaptée pour le cluster. La raison est que les points d'extrémité de relais RTP et RTCP doivent être alloués sur la même IP de relais. Il serait possible de concevoir un schéma avec le transfert des requêtes au niveau de l'application (et nous pourrions le faire plus tard), mais cela affecterait les performances.
