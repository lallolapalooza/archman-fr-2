INFORMATIONS GÉNÉRALES

Un ensemble de programmes turnutils_* fournit des fonctionnalités utilitaires pour les tests et la configuration du serveur TURN.

1.
turnutils_uclient : émule plusieurs clients UDP, TCP, TLS ou DTLS. (ce programme est fourni à des fins de test uniquement !) L'image binaire compilée de ce programme se trouve dans le sous-répertoire bin/.
2.
turnutils_peer : un serveur "écho" UDP simple et sans état, à utiliser comme serveur final dans le modèle de relais ("peer"). Pour chaque paquet UDP entrant, il le renvoie simplement. (ce programme est fourni à des fins de test uniquement !) Lorsque les clients de test communiquent en mode client-à-client (lorsque le programme "turnutils_uclient" est utilisé avec l'option "-y"), le programme turnutils_peer n'est pas nécessaire.

L'image binaire compilée de ce programme se trouve dans le sous-répertoire bin/.

3.
turnutils_stunclient : un exemple simple de client STUN. L'image binaire compilée de ce programme se trouve dans le sous-répertoire bin/.
4.
turnutils_rfc5769check : un utilitaire qui vérifie l'exactitude de l'implémentation des protocoles STUN/TURN. Cet utilitaire est utilisé uniquement pour la procédure de vérification de compilation, il n'est pas copié vers la destination d'installation.

Dans le sous-répertoire "examples/scripts", vous trouverez des exemples de lignes de commande à utiliser pour exécuter les programmes. Les scripts sont destinés à être exécutés depuis le sous-répertoire examples/, par exemple :

$ cd examples

$ ./scripts/secure_relay.sh

5.
turnutils_natdiscovery : un utilitaire qui fournit la découverte du comportement NAT conformément à la RFC5780. Cet utilitaire découvre le mappage NAT réel et le comportement de filtrage, etc. Sachez que du côté du serveur TURN, deux adresses IP d'écoute différentes doivent être configurées pour pouvoir fonctionner correctement !
6.
turnutils_oauth : un utilitaire qui fournit la génération (chiffrement AEAD), la validation et le déchiffrement de tokens d'accès OAuth. Cet utilitaire prend en entrée toutes les clés, les durées de vie et toute information connexe nécessaire à la création et à la validation d'un token d'accès. Il produit un JSON avec tous les paramètres OAuth PoP qui doivent être transmis au client. La sortie est générée conformément à la RFC7635 Annexe B, Figure 8.

Pour plus de détails, et pour la structure du token d'accès, lire la rfc7635, et voir le script dans examples/scripts/oauth.sh.

=====================================

NOM

turnutils_uclient - cette application d'émulation de client est fournie à des fins de test uniquement.

SYNOPSIS

$ turnutils_uclient [-tTSvsyhcxg] [options] <adresse-IP-du-serveur-TURN>

DESCRIPTION

Il a été conçu pour simuler plusieurs clients. Il utilise l'API d'E/S asynchrone de libevent pour gérer plusieurs clients. Un client se connecte au relais, négocie la session, et envoie plusieurs messages (nombre configuré) au serveur (relais), attendant le même nombre de réponses. La longueur des messages est configurable. Le message est un flux d'octets arbitraire. Le nombre de messages à envoyer est configurable.

Options :

-t
Utiliser TCP pour les communications entre le client et le serveur TURN (par défaut UDP).
-b
Utiliser SCTP pour les communications entre le client et le serveur TURN (par défaut UDP).
-T
Utiliser TCP pour le transport du relais (par défaut - UDP). Implique les options -t, -y, -c, et ignore les drapeaux et les options -s, -e, -r et -g. Peut être utilisé conjointement avec -b.
-P
TCP Passif (RFC6062 avec pair actif). Implique -T.
-S
Connexion SSL sécurisée : SSL/TLS pour TCP, DTLS pour UDP, TLS/SCTP pour SCTP.
-U
Connexion sécurisée non chiffrée (suite eNULL) : SSL/TLS pour TCP, DTLS pour UDP.
-v
Verbeux.
-s
Utiliser la méthode "Send" dans TURN ; par défaut, il utilise les canaux TURN.
-y
Utiliser des connexions client-à-client : paire de canaux RTP/RTCP vers une autre paire de canaux RTP/RTCP. Avec cette option, l'application turnutils_peer n'est pas utilisée, car les points d'extrémité de relais alloués communiquent entre eux.
-h
Rester indéfiniment après le dernier paquet envoyé.
-c
Ne pas créer de connexions rtcp.
-x
Demander une adresse de relais IPv6 (RFC6156).
-X
Adresse de relais IPv4 demandée explicitement.
-g
Définir le paramètre DONT_FRAGMENT dans les requêtes TURN.
-D
Effectuer un remplissage de canal obligatoire, même pour UDP (comme pjnath).
-N
Effectuer des tests négatifs (certains cas limités uniquement).
-R
Effectuer des tests de protocole négatifs.
-O
Mode attaque DOS.
-M
Utiliser la mobilité TURN ICE.
-I
Ne pas définir de permissions sur les points d'extrémité de relais TURN (pour tester la fonctionnalité de relais non standard du serveur).
-G
Générer des requêtes supplémentaires (créer des permissions, lier des canaux).
-B
Déconnexion aléatoire après quelques paquets initiaux.
-Z
Allocation double (SSODA). Implique l'option -c.
-J
Utiliser OAuth avec la clé de test par défaut kid='north'.

Options avec valeurs requises :

-l
Longueur du message (Défaut : 100 octets).
-i
Fichier certificat (pour les connexions sécurisées uniquement, facultatif).
-k
Fichier clé privée (pour les connexions sécurisées uniquement).
-E
Fichier CA pour la vérification du certificat du serveur, si le certificat du serveur doit être vérifié.
-p
Port du serveur TURN (Défauts : 3478 non sécurisé, 5349 sécurisé).
-n
Nombre de messages à envoyer (Défaut : 5).
-d
Interface locale (facultatif, Linux uniquement).
-L
Adresse IP locale (facultatif).
-m
Nombre de clients (Défaut : 1, 2 ou 4, selon les options).
-e
Adresse du pair.
-r
Port du pair (Défaut : 3480).
-z
Intervalle de paquets par session en millisecondes (Défaut : 20).
-u
Nom d'utilisateur STUN/TURN.
-w
Mot de passe utilisateur STUN/TURN.
-W
Secret de l'API REST TURN. Le secret en "texte brut", par exemple "north", qui est stocké dans la colonne de valeur du secret turn_
