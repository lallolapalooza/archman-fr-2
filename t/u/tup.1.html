NOM

tup - l'outil de mise à jour

SYNTAXE

tup [--debug-sql] [--debug-fuse] [COMMANDE_SECONDAIRE] [ARGS]

DESCRIPTION

Tup est un système de compilation basé sur les fichiers. Vous devriez utiliser tup si vous développez un logiciel qui doit être traduit à partir de fichiers d'entrée (écrits par vous) vers un format de sortie différent. Par exemple, si vous écrivez un programme C, vous pourriez utiliser tup pour déterminer quels fichiers doivent être recompilés, archivés et liés en fonction d'un graphe de dépendances.

Tup n'a pas de connaissance spécifique au domaine. Vous devez indiquer à tup comment construire votre programme, par exemple en disant que tous les fichiers .c sont convertis en fichiers .o en utilisant gcc. Ceci est fait en écrivant un ou plusieurs Tupfiles.

COMMANDE PRINCIPALE : tup

Vous pouvez effectuer tout votre développement en utilisant uniquement 'tup', ainsi qu'en écrivant des Tupfiles. Voir également les sections FICHIER INI, FICHIERS D'OPTIONS et TUPFILES ci-dessous.

tup [<sortie_1> ... <sortie_n>]
Met à jour l'ensemble des sorties en fonction du graphe de dépendances et de l'état actuel du système de fichiers. Si aucune sortie n'est spécifiée, alors tout le projet est mis à jour. C'est ce que vous exécutez chaque fois que vous apportez des modifications à votre logiciel pour le mettre à jour. Vous pouvez exécuter ceci n'importe où dans la hiérarchie tup, et il mettra toujours à jour la sortie demandée. Par défaut, la liste des fichiers modifiés est déterminée en parcourant le système de fichiers et en vérifiant les dates de modification. Pour les très grands projets, cela peut être lent, mais vous pouvez éviter le temps de parcours en exécutant le moniteur de fichiers (voir COMMANDES SECONDAIRES pour une description du moniteur).
-jN
Remplace temporairement l'option updater.num_jobs par 'N'. Cela exécutera jusqu'à N jobs en parallèle, sous réserve des contraintes du DAG. Par exemple : 'tup -j2' exécutera jusqu'à deux jobs en parallèle, tandis que 'tup' exécutera jusqu'à updater.num_jobs en parallèle. Voir la commande secondaire d'options ci-dessous.
--verbose
Induit tup à afficher la chaîne de commande complète au lieu de seulement la chaîne formatée pour les commandes utilisant le préfixe ^ TEXT^.
--quiet
Remplace temporairement l'option display.quiet par '1'. Voir la commande secondaire d'options ci-dessous.
-k
--keep-going
Remplace temporairement l'option updater.keep_going par '1'. Voir la commande secondaire d'options ci-dessous.
--no-keep-going
Remplace temporairement l'option updater.keep_going par '0'. Voir la commande secondaire d'options ci-dessous.
--no-scan
Ne scanne pas le projet à la recherche de fichiers modifiés. Ceci est uniquement destiné aux tests internes de tup et ne doit pas être utilisé pendant le développement normal.
--no-environ-check
Ne vérifie pas les mises à jour des variables d'environnement exportées aux sous-processus. Au lieu de cela, les variables d'environnement seront utilisées à partir de la base de données. Ceci est utilisé par le moniteur en mode autoupdate/autoparse afin que les variables d'environnement les plus récentes soient utilisées, plutôt que les paramètres lors de l'initialisation du moniteur.
-d
Affiche le journal de débogage à l'écran.
--debug-run
Affiche les règles :- générées par un script d'exécution. Voir la fonctionnalité 'run ./script args' dans la section TUPFILES. --debug-logging Sauvegarde une partie de la sortie de débogage et des graphes de construction dans .tup/log. Les graphes sont mis à jour à chaque invocation avec --debug-logging.

COMMANDES SECONDAIRES

Ces commandes sont utilisées pour modifier le comportement de tup ou examiner ses internes. Vous n'en aurez probablement pas très souvent besoin. Les commandes secondaires sont invoquées comme suit :

tup [--debug-sql] [--debug-fuse] COMMANDE_SECONDAIRE [ARG_COMMANDE_SECONDAIRE]

init [répertoire]
Crée un répertoire '.tup' dans le répertoire spécifié et initialise la base de données tup. Si aucun nom de répertoire n'est spécifié, il crée par défaut '.tup' dans le répertoire courant. Cela définit le haut de votre projet, tel que vu par tup. Tout ce qui se trouve dans le répertoire courant et ses sous-répertoires est appelé la « hiérarchie tup ».

Si vous souhaitez éviter d'avoir à exécuter 'tup init' à chaque fois que vous clonez votre dépôt dans un nouvel emplacement, vous pouvez plutôt créer un fichier vide appelé 'Tupfile.ini' à la racine du projet. Si 'tup' est exécuté sans le répertoire '.tup' présent, il en créera automatiquement un pour vous en tant que frère du fichier Tupfile.ini, comme si vous aviez exécuté 'tup init' dans ce répertoire. S'il existe plusieurs fichiers Tupfile.ini dans les chemins parents, celui le plus haut dans l'arbre sera choisi.

--no-sync
Définit l'option 'db.sync' du projet sur '0'. Par défaut, l'option 'db.sync' sera définie sur '1'. Ce drapeau est principalement utilisé pour les cas de test, mais vous pourriez également l'utiliser dans tout environnement où vous souhaitez scripter tup et ne pas utiliser de synchronisation par défaut.
refactor
ref
La commande refactor peut être utilisée pour aider à refactoriser les Tupfiles. Cela amènera tup à parcourir la phase d'analyse, mais sans exécuter de commandes. Si des Tupfiles analysés entraînent des modifications dans la base de données, celles-ci sont signalées comme des erreurs. Par exemple, nous pourrions avoir le Tupfile simple suivant : 
: foreach *.c |> gcc -c %f -o %o -Wall |> %B.o

Après un 'tup' initial, nous décidons de déplacer -Wall vers une variable appelée CFLAGS. Le Tupfile ressemble maintenant à ceci :

CFLAGS = -Wall
: foreach *.c |> gcc -c %f -o %o $(CFLAGS) |> %B.o

Exécuter 'tup refactor' amènera tup à analyser le Tupfile, et si nous avons fait des erreurs, un message d'erreur sera affiché. Les Tupfiles peuvent ensuite être modifiés pour corriger ces erreurs, et continuer à exécuter 'tup refactor' jusqu'à ce que tous les Tupfiles soient analysés avec succès.

Les erreurs sont signalées pour l'ajout ou la suppression de ce qui suit : commandes, entrées qui sont des fichiers générés, sorties, la directive .gitignore, <groupes> d'entrée ou de sortie, et les dépendances au niveau du répertoire. Sinon, vous êtes en mesure de déplacer n'importe quelles chaînes vers des variables $-, des macros !, et similaires, tant que le résultat final de l'ensemble des règles :- est le même.

monitor
*LINUX UNIQUEMENT* Lance le moniteur de fichiers basé sur inotify. Le moniteur doit analyser le système de fichiers une fois et initialiser des watchers sur chaque répertoire. Ensuite, lorsque vous apportez des modifications aux fichiers, le moniteur les voit et les écrit directement dans la base de données. Avec le moniteur en cours d'exécution, 'tup' n'a pas besoin d'effectuer l'analyse initiale, et peut commencer à construire le graphe de construction immédiatement. Le temps « Analyse du système de fichiers... » de 'tup' est approximativement égal au temps que vous économiseriez en exécutant le moniteur. Lorsque le moniteur est en cours d'exécution, un 'tup' sans modification de fichier ne devrait prendre que quelques millisecondes (sur mes machines, j'obtiens environ 2 ou 3 ms lorsque tout est dans le cache disque). Si vous redémarrez votre ordinateur, vous devrez redémarrer le moniteur. Les arguments suivants peuvent être donnés sur la ligne de commande. Tous les arguments supplémentaires non gérés par le moniteur seront transmis à l'outil de mise à jour si monitor.autoupdate ou monitor.autoparse sont activés. Par exemple, vous pourriez exécuter le moniteur comme 'tup monitor -f -a -j2' pour exécuter le moniteur au premier plan, et mettre à jour automatiquement avec 2 jobs lorsque des changements sont détectés. Voir également la commande secondaire d'options ci-dessous.
-d
Active le débogage du processus moniteur.
-f
--foreground
Remplace temporairement monitor.foreground
option pour 1. Le moniteur s'exécutera au premier plan (ne pas démoniser).
-b
--background
Remplace temporairement l'option monitor.foreground par 0. Le moniteur s'exécutera en arrière-plan (démonisation).
-a
--autoupdate
Remplace temporairement l'option monitor.autoupdate par 1. Ceci exécutera automatiquement une mise à jour lorsque des modifications de fichiers sont détectées.
-n
--no-autoupdate
Remplace temporairement l'option monitor.autoupdate par 0. Ceci empêchera le moniteur d'exécuter automatiquement une mise à jour lorsque des modifications de fichiers sont détectées.
--autoparse
Remplace temporairement l'option monitor.autoparse par 1. Ceci exécutera automatiquement l'analyseur lorsque des modifications de fichiers sont détectées.
--no-autoparse
Remplace temporairement l'option monitor.autoparse par 0. Ceci empêchera le moniteur d'exécuter automatiquement l'analyseur lorsque des modifications de fichiers sont détectées.
stop
Arrête le moniteur s'il est en cours d'exécution. En gros, cela vous évite de rechercher le PID et de l'arrêter de cette manière.
variant foo.config [bar.config] [...]
Pour chaque argument, cette commande crée un répertoire variant avec tup.config symboliquement lié au fichier de configuration spécifié. Par exemple, si un répertoire contenait plusieurs configurations de variantes, on pourrait facilement créer une variante pour chaque fichier de configuration : 
$ ls configs/
bar.config
foo.config
$ tup variant configs/*.config
tup: Ajout de la variante 'build-bar' utilisant le fichier de configuration 'configs/bar.config'
tup: Ajout de la variante 'build-foo' utilisant le fichier de configuration 'configs/foo.config'

Ceci est équivalent à ce qui suit :

$ mkdir build-bar
$ ln -s ../configs/bar.config build-bar/tup.config
$ mkdir build-foo
$ ln -s ../configs/foo.config build-foo/tup.config

Pour les projets qui utilisent couramment plusieurs variantes, les fichiers du répertoire configs/ pourraient être validés dans le contrôle de source. Chaque développeur exécuterait la commande 'tup variant' après 'tup init' lors du premier checkout du logiciel. Les variantes peuvent également être créées manuellement en créant un répertoire de build et en y créant un fichier tup.config (voir la section VARIANTS). Cette commande aide simplement à économiser quelques étapes, de sorte que vous n'ayez pas à créer chaque répertoire de build et le lien symbolique tup.config manuellement.

dbconfig
Affiche la configuration actuelle de la base de données tup. Ce sont des valeurs internes utilisées par tup.
options
Affiche toutes les options tup actuelles, ainsi que leur origine.

Pour plus de détails sur toutes les options disponibles et sur la façon de les définir, consultez la section FICHIERS D'OPTIONS ci-dessous.

graph [--dirs] [--ghosts] [--env] [--combine] [--stickies] [<output_1> ... <output_n>]
Affiche un graphique au format graphviz .dot de la base de données tup sur stdout. Par défaut, il n'affiche que les parties du graphique qui ont des changements. Si vous fournissez des arguments supplémentaires, ils sont supposés être des fichiers que vous souhaitez graphiquer. Cela opère directement sur la base de données tup, donc à moins que vous n'exécutiez le moniteur de fichiers, vous voudrez peut-être exécuter 'tup scan' au préalable. Ceci est généralement utilisé pour le débogage de tup - vous pourriez trouver utile ou non de regarder la structure de votre programme.
--dirs
Remplace temporairement l'option graph.dirs par '1'. Ceci affichera les nœuds de répertoire et les Tupfiles.
--ghosts
Remplace temporairement l'option graph.ghosts par '1'. Ceci affichera les nœuds fantômes (fichiers qu'une commande a tenté d'accéder, mais qui n'existent pas réellement).
--env
Remplace temporairement l'option graph.environment par '1'. Ceci affichera les variables d'environnement, telles que PATH.
todo [<output_1> ... <output_n>]
Affiche les prochaines étapes du processus tup qui s'exécuteront lors de la mise à jour des sorties données. Si aucune sortie n'est spécifiée, cela affiche les étapes nécessaires pour mettre à jour l'ensemble du projet. Similaire à la commande 'upd', 'todo' analysera automatiquement le projet pour les modifications de fichiers si un moniteur de fichiers n'est pas en cours d'exécution.
--no-scan
Ne pas analyser le projet pour les fichiers modifiés. Ceci est uniquement à des fins de test interne de tup, et ne doit pas être utilisé lors du développement normal.
--verbose
Fait en sorte que tup affiche la chaîne de commande complète au lieu de simplement la chaîne formatée pour les commandes qui utilisent le préfixe ^ TEXT^.
generate [--config config-file] [--builddir directory] script.sh (ou script.bat sous Windows) [<output_1> ... <output_n>]
La commande generate analysera tous les Tupfiles et créera un script shell qui pourra construire le programme sans s'exécuter dans un environnement tup. L'utilisation attendue est dans les environnements d'intégration continue qui ne sont pas compatibles avec la vérification des dépendances de tup (par exemple, si FUSE n'est pas pris en charge). Sous Windows, si le nom de fichier du script a une extension ".bat", la sortie sera un script batch au lieu d'un script shell. Par exemple : 
git clone ... myproj
cd myproj
tup generate build.sh
./build.sh
# Copier les artefacts de build / journaux ici
git clean -f -x -d
Le script shell ne fonctionne pas de manière incrémentielle, il est donc effectivement à usage unique. Vous devrez nettoyer l'arborescence avant la prochaine invocation de 'tup generate' et du script. Par défaut, le fichier tup.config de niveau supérieur est utilisé pour définir les variables de configuration. Facultativement, un fichier de configuration séparé peut être passé avec l'argument --config.

Si un argument --builddir est spécifié, le script shell est généré comme s'il s'agissait d'une variante de build. Tous les artefacts de build sont placés dans le répertoire spécifié. Sinon, le comportement par défaut est de placer tous les artefacts de build dans l'arborescence. Le répertoire de build ne doit pas déjà exister dans l'arborescence.

Après le nom du script, des fichiers de sortie individuels peuvent être listés afin de limiter la portée du script shell à la construction de ces sorties uniquement. Si aucune sortie n'est listée, le script shell construira toutes les sorties.


compiledb
La commande compiledb crée un fichier compile_commands.json à utiliser avec des outils tiers qui utilisent ce fichier comme référence pour déterminer comment les fichiers sont compilés. Le fichier est créé en haut de la hiérarchie tup, ou si vous utilisez des variantes, chaque variante obtient son propre compile_commands.json créé à la racine de la variante. Vous devez annoter les fichiers que vous souhaitez exporter avec le drapeau ^j. Par exemple, vous pourriez ajouter le drapeau ^j à vos invocations de compilateur : 
: foreach *.c |> ^j^ gcc -c %f -o %o |> %B.o

Tup analyse automatiquement tous les Tupfiles obsolètes (équivalent à 'tup parse') avant de générer la base de données.

En raison du coût de mise à jour de compile_commands.json pour les grands projets, le fichier n'est *pas* mis à jour automatiquement lorsque les Tupfiles changent. Vous devez réexécuter 'tup compiledb' manuellement lorsque vous souhaitez une version mise à jour.

Pour récupérer automatiquement la dernière ligne de commande directement à partir de la base de données au lieu d'utiliser compile_commands.json comme intermédiaire, consultez la commande 'commandline'.

Voir aussi : https://clang.llvm.org/docs/JSONCompilationDatabase.html


commandline <file_1> [<file_2> ... <file_n>]
La commande commandline affichera les informations nécessaires pour compiler le nom de fichier donné en argument. Les informations sont affichées sur stdout dans le même format JSON que le fichier compile_commands.json de 'tup compiledb'. Notez qu'à la différence de la commande compiledb, 'tup commandline' n'analyse pas automatiquement les Tupfiles avant de tenter de trouver la commande. Il interroge simplement la base de données directement.

Pour un exemple d'utilisation, consultez le fichier .ycm_extra_conf.py situé à la racine du dépôt git tup : https://github.com/gittup/tup/


varsed
La commande varsed est utilisée comme sous-programme dans un Tupfile ; vous ne l'exécuteriez pas manuellement en ligne de commande. Elle est utilisée pour lire un fichier, remplacer toutes les références de variables et écrire la sortie dans un second fichier. Les références de variables sont de la forme @VARIABLE@, et sont remplacées par la valeur correspondante de la variable @-variable. Par exemple, si foo.txt contient : 
L'architecture est réglée sur @ARCH@
Et si vous avez une règle :-dans un Tupfile comme suit : 
: foo.txt |> tup varsed %f %o |> foo-out.txt
Alors lors d'une mise à jour, le fichier de sortie sera identique au fichier d'entrée, sauf que la chaîne @ARCH@ sera remplacée par ce que CONFIG_ARCH est défini à dans tup.config. La commande varsed ajoute automatiquement la dépendance de CONFIG_ARCH au nœud de commande particulier qui l'a utilisée (donc si CONFIG_ARCH change, le fichier de sortie sera mis à jour avec la nouvelle valeur).
scan
Vous ne devriez jamais avoir besoin d'exécuter ceci, sauf si vous voulez que la base de données reflète le système de fichiers avant d'exécuter 'tup graph'. Scan est appelé automatiquement par 'upd' si le moniteur n'est pas en cours d'exécution.
upd
Ancienne commande secondaire. Appeler 'tup upd' équivaut simplement à appeler 'tup'.

La commande tup peut être exécutée depuis n'importe où dans l'arborescence source. Elle utilise les informations de tous les Tupfiles (voir la section TUPFILES) ainsi que ses propres informations dynamiques.

base de données, maintenue dans le répertoire .tup situé à la racine du projet. Le répertoire .tup peut être créé manuellement avec la commande 'tup init', ou vous pouvez le faire exécuter automatiquement en ajoutant un fichier Tupfile.ini vide à la racine du dépôt de contrôle de version du projet.

FICHIERS OPTIONS

Tup permet une variété de fichiers de configuration. Ces fichiers affectent le comportement de tup en tant que programme, mais pas tup en tant que système de build. C'est-à-dire, changer l'une de ces options ne devrait pas affecter le résultat final d'une build réussie, mais peut affecter la manière dont tup y parvient (par exemple, combien de jobs de compilation exécuter en parallèle).

Les options sont lues dans l'ordre de priorité suivant :

  substitutions en ligne de commande (par exemple : indicateur -j passé à 'tup')
  fichier .tup/options
  fichier ~/.tupoptions
  fichier /etc/tup/options
  paramètres par défaut compilés de tup

Pour Windows, les fichiers d'options sont lus comme suit :

  substitutions en ligne de commande
  fichier .tup/options
  tup.ini dans le chemin des données d'application (généralement C:\ProgramData\tup\tup.ini)
  paramètres par défaut compilés de tup

Pour une liste exacte des chemins sur votre plateforme, tapez 'tup options'.

Tous les fichiers utilisent la même syntaxe de style .ini. Un en-tête de section est entouré de crochets, comme suit :

[updater]

L'en-tête de section est suivi d'une ou plusieurs définitions de variables, de la forme 'variable = valeur'. Les commentaires commencent par un point-virgule et se poursuivent jusqu'à la fin de la ligne. Les définitions de variables peuvent toutes être définies sur des entiers. Pour les indicateurs booléens, « true »/« yes » et « false »/« no » sont des synonymes de 1 et 0, respectivement. Par exemple, si vous avez un fichier .tup/options qui contient :

[updater]
	num_jobs = 2
	keep_going = true

Alors 'tup' utilisera par défaut 2 jobs, et l'indicateur updater.keep_going sera activé. Les options listées ci-dessous sont de la forme 'section.variable', donc pour définir 'db.sync' vous auriez besoin d'une section '[db]' suivie de 'sync = 0', par exemple. Les valeurs par défaut listées ici sont les valeurs par défaut compilées.

db.sync (par défaut '1')
Défini sur '1' si la fonctionnalité de synchronisation SQLite est activée. Lorsqu'elle est activée, la base de données est correctement synchronisée sur le disque de manière à être toujours cohérente. Lorsqu'elle est désactivée, elle s'exécutera plus rapidement car les écritures resteront dans le cache du disque pendant un certain temps avant d'être écrites. Cependant, si votre ordinateur plante avant que tout ne soit écrit, la base de données tup peut être corrompue. Voir http://www.sqlite.org/pragma.html pour plus d'informations.
updater.num_jobs (par défaut au nombre de processeurs du système )
Défini sur le nombre maximum de commandes que tup exécutera simultanément. La valeur par défaut est déterminée dynamiquement comme étant le nombre de processeurs du système. Si updater.num_jobs est supérieur à 1, les commandes ne seront exécutées en parallèle que si elles sont indépendantes. Voir également l'option -j.
updater.keep_going (par défaut '0')
Défini sur '1' pour continuer la compilation autant que possible même si des erreurs sont rencontrées. Tout ce qui dépend d'une commande échouée ne sera pas exécuté, mais d'autres commandes indépendantes le seront. La valeur par défaut est '0', ce qui fera s'arrêter tup après la première commande échouée. Voir également l'option -k.
updater.full_deps (par défaut '0')
Défini sur '1' pour suivre les dépendances sur des fichiers en dehors de la hiérarchie tup. La valeur par défaut est '0', qui ne suit que les dépendances au sein de la hiérarchie tup. Par exemple, si vous voulez que tous les fichiers C soient recompilés lorsque gcc est mis à jour sur votre système, vous devriez définir cette option sur '1'. Sous Linux et OSX, l'utilisation de dépendances complètes nécessite que le binaire tup soit suid root afin qu'il puisse exécuter des sous-processus dans un environnement chroot. Alternativement sous Linux, si votre noyau prend en charge les espaces de noms utilisateur, alors vous n'avez pas besoin de rendre le binaire suid. Notez que si cette valeur est définie sur '1' depuis '0', tup reconstruira l'ensemble du projet. La désactivation de cette option lorsqu'elle était précédemment activée ne nécessite pas une reconstruction complète, mais prend un certain temps car les nœuds représentant les fichiers externes sont effacés. REMARQUE : Cela ne fonctionne pas actuellement avec ccache ou d'autres programmes qui peuvent écrire dans des fichiers externes en raison de problèmes de verrouillage. Cela pourrait être résolu à l'avenir.
updater.warnings (par défaut '1')
Défini sur '0' pour désactiver les avertissements concernant l'écriture dans des fichiers cachés. Tup ne suit pas les fichiers qui sont cachés. Si un sous-processus écrit dans un fichier caché, par défaut tup affichera un avertissement indiquant que ce fichier a été créé. En désactivant cette option, ces avertissements ne sont pas affichés. Les noms de fichiers (ou répertoires) cachés incluent : ., .., .tup, .git, .hg, .bzr, .svn.
display.color (par défaut 'auto')
Défini sur 'never' pour désactiver les codes d'échappement ANSI pour la sortie couleur, ou 'always' pour toujours utiliser les codes d'échappement ANSI pour la sortie couleur. La valeur par défaut est 'auto', qui affiche une sortie colorée si stdout est connecté à un tty, et n'utilise aucune couleur sinon (c'est-à-dire si stdout est redirigé vers un fichier).
display.width (par défaut la largeur du terminal)
Défini sur n'importe quel nombre de 10 ou plus pour forcer une largeur fixe pour la barre de progression. Celle-ci est supposée être la largeur totale, dont une partie est utilisée pour les espaces, les crochets et le pourcentage d'achèvement. Si cette valeur est inférieure à 10, la barre de progression est désactivée.
display.progress (par défaut '1' si stdout est un TTY)
Défini sur '1' pour activer la barre de progression, ou '0' pour la désactiver. Par défaut, elle est activée si stdout est un TTY, et désactivée si stdout n'est pas un TTY.
display.job_numbers (par défaut '1')
Défini sur '0' pour éviter d'afficher la chaîne « N) » avant les résultats d'un job. La valeur par défaut est d'afficher ce numéro.
display.job_time (par défaut '1')
Défini sur '0' pour éviter d'afficher le temps d'exécution d'un job avec les résultats. La valeur par défaut est d'afficher le temps d'exécution. Notez que le temps d'exécution affiché inclut le temps que tup prend pour sauvegarder les dépendances. Par conséquent, ce temps d'exécution sera probablement plus long que le temps d'exécution lors de l'exécution du même job manuellement dans le shell.
display.quiet (par défaut '0')
Défini sur '1' pour empêcher tup d'afficher la plupart des sorties. Tup affichera toujours une bannière et la sortie de tout job qui écrit sur stdout/stderr, ou tout job qui retourne un code de sortie non nul. La barre de progression est toujours affichée ; voir également display.progress pour une sortie vraiment silencieuse.
monitor.autoupdate (par défaut '0')
Défini sur '1' pour reconstruire automatiquement si un changement de fichier est détecté. Ceci n'a d'effet que si le moniteur est en cours d'exécution. La valeur par défaut est '0', ce qui signifie que vous devez taper 'tup' lorsque vous êtes prêt à mettre à jour.
monitor.autoparse (par défaut '0')
Défini sur '1' pour exécuter automatiquement l'analyseur si un changement de fichier est détecté. Ceci est similaire à monitor.autoupdate, sauf que la mise à jour s'arrête après l'étape d'analyse - aucune commande n'est exécutée tant que vous n'avez pas tapé manuellement 'tup'. Ceci n'a d'effet que si le moniteur est en cours d'exécution. Notez que si autoupdate et autoparse sont tous deux définis, alors autoupdate a la priorité.
monitor.foreground (par défaut '0')
Défini sur '1' pour exécuter le moniteur en premier plan, de sorte que le contrôle ne revienne pas au terminal tant que le moniteur n'est pas arrêté (soit par ctrl-C dans le terminal de contrôle, soit en exécutant 'tup stop' dans un autre terminal). La valeur par défaut est '0', ce qui signifie que le moniteur s'exécutera en arrière-plan.
graph.dirs (par défaut '0')
Défini sur '1' et la commande 'tup graph' affichera les nœuds de répertoire et leurs liens de propriété. Les Tupfiles sont également affichés, car ils pointent vers des nœuds de répertoire. Par défaut, les répertoires et les Tupfiles ne sont pas affichés car ils peuvent encombrer le graphique dans certains cas et ne sont pas toujours utiles.
graph.ghosts (par défaut '0')
Défini sur '1' pour afficher les nœuds fantômes. Certaines commandes peuvent essayer de lire de nombreux fichiers qui n'existent pas, provoquant la création de nœuds fantômes. Par défaut, les fantômes ne sont pas affichés pour rendre le graphique plus facile à comprendre.
graph.environment (par défaut '0')
Défini sur '1' pour afficher les nœuds d'environnement (comme PATH) et leurs dépendances. Par défaut, les variables d'environnement ne sont pas affichées car presque tout dépendra de PATH.
graph.combine (par défaut '0')
Défini sur '1' pour essayer de combiner les nœuds similaires dans le graphique. Par exemple, au lieu d'afficher 10 commandes de compilation distinctes qui ont toutes un fichier .c en entrée et un fichier .o en sortie, cela les combinera en une seule commande pour voir plus facilement la structure globale du graphique. Par défaut, tous les nœuds sont affichés séparément.

TUPFILES

Vous devez créer un fichier nommé "Tupfile" n'importe où dans la hiérarchie tup où vous souhaitez créer un fichier de sortie basé sur les fichiers d'entrée. Les fichiers d'entrée peuvent se trouver n'importe où ailleurs dans la hiérarchie tup, mais le(s) fichier(s) de sortie doivent être écrits dans le même répertoire que le Tupfile.

: [foreach] [entrées] [ | entrées en lecture seule] |> commande |> [sorties] [ | sorties supplémentaires] [<groupe>] [{bin}]
Les règles :- sont le principal moyen de créer des commandes et sont identifiées par le fait que le caractère ':' apparaît dans la première colonne du Tupfile. La syntaxe est censée ressembler à un pipeline, de sorte que les fichiers d'entrée à gauche entrent dans la commande au milieu, et les fichiers de sortie sortent à droite.
foreach
Il s'agit soit de la chaîne de caractères réelle "foreach", soit elle est vide. La distinction réside dans le nombre de commandes générées lorsqu'il y a m
multiple fichiers d'entrée. Si « foreach » est spécifié, une commande est créée pour chaque fichier de la section des entrées. Si elle n'est pas spécifiée, une commande est créée contenant tous les fichiers de la section des entrées. Par exemple, les Tupfiles suivants sont équivalents : 
# Tupfile 1
: foo.c |> gcc -c foo.c -o foo.o |> foo.o
: bar.c |> gcc -c bar.c -o bar.o |> bar.o
# Tupfile 2
: foreach foo.c bar.c |> gcc -c %f -o %o |> %B.o
De plus, l'utilisation de « foreach » permet l'utilisation de l'indicateur « %e » (voir ci-dessous).
inputs
Les fichiers d'entrée de la commande. Un fichier d'entrée peut se trouver n'importe où dans la hiérarchie de tup et est spécifié par rapport au répertoire courant. Les fichiers d'entrée affectent les indicateurs % (voir ci-dessous). Les caractères génériques sont pris en charge dans un répertoire en utilisant la fonction glob de SQLite. Les caractères spéciaux de glob sont '*', '?', et '[]'. Par exemple, « *.c » correspondrait à n'importe quel fichier .c, « fo?.c » correspondrait à n'importe quel fichier .c de 3 caractères dont les deux premiers caractères sont 'f' et 'o', et « fo[xyz].c » correspondrait à fox.c, foy.c et foz.c. Le globbing ne correspond pas aux répertoires, donc « src/*.c » fonctionnera, mais « */*.c » ne fonctionnera pas.

Toutes les entrées commençant par '^' sont des expressions régulières compatibles Perl utilisées pour exclure les fichiers qui ont été mis en correspondance dans un glob précédent. Par exemple, vous pouvez compiler tous les fichiers *.c sauf main.c avec le fragment suivant :

: foreach *.c ^main.c |> ... |>

Ces exclusions d'entrées sont gérées au moment de l'analyse syntaxique et sont distinctes des exclusions de dépendances dans la section des sorties.

order-only inputs
Ceux-ci sont également utilisés comme entrées pour la commande, mais n'apparaîtront dans aucun des indicateurs % sauf %i. Ils sont séparés des entrées régulières par le caractère '|'. En effet, ceux-ci peuvent être utilisés pour spécifier des entrées supplémentaires à une commande qui ne devrait pas apparaître dans la ligne de commande. Le globbing est pris en charge comme dans la section des entrées. Par exemple, une utilisation pour eux est de spécifier des dépendances d'en-têtes auto-générées : 
: |> echo "#define FOO 3" > %o |> foo.h
: foreach foo.c bar.c | foo.h |> gcc -c %f -o %o |> %B.o
Cela ajoutera la dépendance foo.h aux commandes gcc pour foo.c et bar.c, donc tup saura générer l'en-tête avant d'essayer de compiler. La commande foreach itérera sur les entrées régulières (ici, foo.c et bar.c), et non sur les entrées d'ordre uniquement (foo.h). Si vous oubliez d'ajouter une telle dépendance, tup signalera une erreur lors de l'exécution de la commande. Notez que la dépendance foo.h n'est répertoriée ici que parce qu'elle est créée par une autre commande - les en-têtes normaux n'ont pas besoin d'être spécifiés.
command
La chaîne de commande qui sera passée à l'appel système(3) par tup. Cette commande est autorisée à lire à partir de n'importe quel fichier spécifié comme entrée ou entrée d'ordre uniquement, ainsi que de tout autre fichier de la hiérarchie de tup qui n'est pas la sortie d'une autre commande. Autrement dit, une commande ne peut pas lire à partir de la sortie d'une autre commande, sauf si elle est spécifiée comme entrée. Cette restriction est ce qui permet à tup d'être parallèle sûr. De plus, la commande doit écrire dans tous les fichiers de sortie spécifiés par la section « outputs », le cas échéant.
Lors de l'exécution, les accès aux fichiers de la commande sont surveillés par tup pour s'assurer qu'ils sont conformes à ces règles. Tous les fichiers ouverts en lecture qui ont été générés par une autre commande mais non spécifiés comme entrées sont signalés comme des erreurs. De même, tous les fichiers ouverts en écriture qui ne sont pas spécifiés comme sorties sont signalés comme des erreurs. Tous les fichiers ouverts en lecture sont enregistrés comme dépendances de la commande. Si l'un de ces fichiers change, tup réexécutera la commande lors de la prochaine mise à jour. Notez que si une entrée répertoriée dans le Tupfile change, cela ne provoque pas nécessairement la réexécution de la commande, sauf si la commande a réellement lu cette entrée lors de l'exécution précédente. Les entrées répertoriées dans le Tupfile ne font qu'appliquer l'ordre entre les commandes, tandis que les accès aux fichiers pendant l'exécution déterminent quand les commandes sont réexécutées.
Une chaîne de commande peut commencer par la séquence spéciale ^ TEXT^, qui indique à tup de n'afficher que « TEXT » au lieu de la chaîne de commande entière lorsque la commande est exécutée. Cela évite d'avoir à utiliser echo pour formater joliment une longue commande. Le comportement d'affichage court peut être remplacé en passant l'indicateur --verbose à tup, ce qui amène tup à afficher la chaîne de commande réelle au lieu de « TEXT ». L'espace après le premier '^' est significatif. Tous les caractères immédiatement après le premier '^' sont traités comme des indicateurs. Voir la section ^-flags ci-dessous pour plus de détails. Par exemple, cette commande affichera « CC foo.c » lors de l'exécution de system(gcc -c foo.c -o foo.o) : 
: foo.c |> ^ CC %f^ gcc -c %f -o %o |> foo.o
Une chaîne de commande peut également commencer par le caractère spécial '!', auquel cas le macro ! spécifié sera substitué à la commande réelle. Voir la définition de macro ! plus loin. Les commandes peuvent également être vides, ce qui est utile pour placer tous les fichiers d'entrée dans un {bin} pour une règle ultérieure.
outputs
La section des sorties spécifie les fichiers qui seront écrits par la commande. Une seule commande peut écrire dans un fichier spécifique, mais une seule commande peut générer plusieurs fichiers (par exemple, une commande bison générera à la fois un fichier .c et un fichier .h). La sortie peut utiliser n'importe quel indicateur % sauf %o. Une fois qu'un fichier est spécifié dans une section de sortie, il est placé dans la base de données de tup. Toutes les règles suivantes peuvent utiliser ce fichier comme entrée, même s'il n'existe pas encore dans le système de fichiers.

Les sorties commençant par '^' sont utilisées pour ignorer les dépendances sur les fichiers. Ces exclusions sont des expressions régulières compatibles Perl qui sont stockées dans la base de données. Tous les fichiers lus ou écrits lors de l'exécution du sous-processus qui correspondent à ces modèles sont ignorés par tup. Par exemple, si votre compilateur écrit dans un 'license_file.txt', vous pouvez demander à tup d'ignorer les erreurs de dépendance sur ce fichier comme suit :

: foreach *.c |> ... |> %B.o ^license_file.txt

Notez que cela demande également à tup d'ignorer les dépendances d'entrée sur le fichier. Si vous souhaitez simplement ignorer des fichiers dans un glob, voir la syntaxe '^' similaire dans la section des entrées.

Une exclusion ne peut pas être utilisée pour faire correspondre un fichier généré par la même règle (c'est-à-dire un fichier répertorié comme sortie dans la commande). Le faire entraînera une erreur « Impossible d'exclure un fichier généré ».

Vous ne devriez ignorer les dépendances qu'avec une extrême prudence. Il est facile de faire en sorte que tup échoue à la mise à jour alors qu'il aurait dû le faire, car on lui a demandé d'ignorer les dépendances.

extra-outputs
La section extra-outputs est similaire à la section order-only inputs. Elle est séparée des sorties régulières par le caractère '|'. Les extra-outputs se comportent exactement comme les sorties régulières, sauf qu'elles n'apparaissent pas dans l'indicateur %o. Celles-ci peuvent être utilisées si une commande génère des fichiers dont les noms n'apparaissent pas réellement dans la ligne de commande. S'il y a exactement une sortie spécifiée par la règle, la section extra-outputs peut utiliser l'indicateur %O pour représenter le nom de base de la sortie. Cela peut être utile dans les extra-outputs pour les macros !.
<group>
Les fichiers de sortie peuvent être regroupés en groupes globaux en spécifiant un <group> après les sorties mais avant un bin. Les groupes permettent des dépendances d'ordre uniquement entre les dossiers. Notez que les groupes sont spécifiques aux répertoires, donc lors de la référence à un groupe, vous devez spécifier le chemin d'accès où il est attribué. Par exemple, si un projet principal dépend de la sortie de plusieurs sous-modules, vous pouvez structurer Tup comme suit pour vous assurer que les sous-modules sont construits avant le projet principal : 
#./submodules/sm1/Tupfile
: foo.c |> gcc -c %f -o %o |> %B.o ../<submodgroup>
#./submodules/sm2/Tupfile
: bar.c |> gcc -c %f -o %o |> %B.o ../<submodgroup>
#./project/Tupfile
: baz.c | ../submodules/<submodgroup> |> gcc -c %f -o %o |> %B.o
Remarquez comment les groupes sont spécifiques aux répertoires et que le chemin est spécifié à l'extérieur des <>. En spécifiant le <submodgroup> comme entrée d'ordre uniquement, Tup construira les sous-modules avant de tenter de construire l'ensemble du projet.
{bin}
Les sorties peuvent être regroupées dans un bin en utilisant la syntaxe « {bin} ». Une règle ultérieure peut utiliser « {bin} » comme entrée pour utiliser tous les fichiers de ce bin. Par exemple, la règle foreach place chaque fichier .o dans le bin objs, qui est utilisé comme entrée dans la règle de liaison : 
: foreach *.c |> gcc -c %f -o %o |> %B.o {objs}
: {objs} |> gcc %f -o %o |> program
Dans ce cas, on pourrait également utiliser *.o comme entrée, mais il est parfois utile de séparer les sorties en groupes même si elles ont la même extension (par exemple, si un répertoire crée plusieurs binaires, l'utilisation de *.o ne serait pas correcte). Si un {bin} est spécifié dans la section des sorties de plusieurs règles, le bin sera l'union de toutes les sorties. Vous ne pouvez pas supprimer des éléments d'un bin, et le bin disparaît après l'analyse du Tupfile courant.
^-flags
Dans une chaîne de commande qui utilise la séquence ^ TEXT^, les caractères d'indicateur peuvent être placés immédiatement après le ^ jusqu'au premier espace ou caret fermant. Par exemple : 
: foo.c |> ^c CC %f^ gcc --coverage %f -o %o |> foo | foo.gcno
: bar.c |> ^c^ gcc --coverage %f -o %o |> bar | bar.gcno
Dans le cas de foo.c, la commande nécessite des espaces de noms (ou suid) et affichera « CC foo.c ». Dans le cas de bar.c, la commande nécessite des espaces de noms (ou suid) et la chaîne « gcc --coverage bar.c -o bar » est affichée. Ce sont les caractères d'indicateur pris en charge :
b
L'indicateur 'b' fait que la commande est exécutée via « /usr/bin/env bash -e -o pipefail -c <commande> » au lieu de « /bin/sh -e -c <commande> » par défaut. En plus de permettre les extensions bash dans la règle :, « -o pipefail » stipule que « la valeur de retour d'un pipeline est la valeur du dernier (le plus à droite) commande à se terminer avec un statut non nul, ou zéro si toutes les commandes du pipeline se terminent avec succès. »
c
L'indicateur 'c' provoque l'échec de la commande si tup ne prend pas en charge les espaces de noms utilisateur (sur Linux) ou s'il n'est pas suid root. Dans ces cas, tup s'exécute dans un mode dégradé où les faux répertoires de travail sont visibles dans les sous-processus, et certaines dépendances peuvent être manquées. Si ces comportements dégradés nuisent à une parti cular command dans votre build, ajoutez le drapeau 'c' afin que les utilisateurs sachent qu'ils doivent ajouter le bit suid ou mettre à niveau leur noyau. Ce drapeau est ignoré sous Windows.
j
Le drapeau 'j' marque la commande pour exportation dans la commande 'tup compiledb'. Si vous souhaitez utiliser compile_commands.json, annotez les commandes que vous souhaitez exporter avec ^j, puis exécutez 'tup compiledb'. Voir la commande compiledb pour plus de détails.
o
Le drapeau 'o' amène la commande à comparer les nouveaux résultats avec les résultats de l'exécution précédente. Les résultats identiques ne déclencheront pas l'exécution des commandes dépendantes dans le DAG. Par exemple, l'ajout de ce drapeau à une commande de compilation ignorera l'étape d'édition des liens si le fichier objet est le même que la dernière fois qu'il a été exécuté. Le drapeau 'o' est incompatible avec le drapeau 't'.
s
Le drapeau 's' désactive la mise en mémoire tampon de stdout/stderr pour les sous-processus et active le « mode de diffusion en continu ». Lors de la diffusion en continu, stdout/stderr sont hérités du processus tup, de sorte que les messages s'afficheraient généralement sur le terminal pendant que le sous-processus s'exécute, dans l'ordre où ils sont générés. Notez que les processus avec le drapeau 's' activé peuvent afficher des messages entrelacés les uns avec les autres, ainsi qu'avec la barre de progression de tup ou d'autres messages de tup. Ce drapeau peut être utile pour les processus de longue durée où vous souhaitez voir la sortie au fur et à mesure qu'elle se produit, bien qu'il puisse rendre les journaux confus s'il est utilisé pour de nombreuses commandes bruyantes qui peuvent s'exécuter en parallèle.

Par défaut, tup mettra en mémoire tampon les messages d'une commande (par exemple, les messages d'avertissement du compilateur) et les affichera sous l'en-tête de la commande après son achèvement. Les messages provenant de commandes distinctes sont donc toujours distincts et associés à la commande qui les a créés.

t
Le drapeau 't' rend les sorties de la commande transitoires. Les sorties peuvent être utilisées comme entrées pour d'autres commandes, mais une fois que toutes les commandes dépendantes sont exécutées, les sorties transitoires seront supprimées du système de fichiers. Ceci peut être utilisé pour économiser de l'espace s'il y a de nombreuses étapes de traitement qui produisent chacune de grandes sorties, mais seule la sortie finale doit être conservée. Le drapeau 't' est incompatible avec le drapeau 'o'.

Un exemple où le drapeau 't' peut avoir du sens dans un pipeline de build est s'il y a de gros actifs qui passent par plusieurs étapes de traitement. Par exemple, un grand fichier audio ou vidéo sur lequel des étapes d'effets sont appliquées, chacune comme une étape distincte dans le Tupfile.

En revanche, le drapeau 't' n'a *pas* de sens pour les fichiers objets d'un programme C, même si ceux-ci pourraient théoriquement être supprimés une fois l'exécutable final lié. Si les fichiers objets étaient marqués comme transitoires dans ce cas, une modification de l'un des fichiers C d'entrée obligerait *tous* les fichiers objets à être reconstruits afin de produire l'exécutable, au lieu d'un seul fichier modifié.

%-flags
Dans une chaîne de commande ou une chaîne de sortie, les drapeaux %- suivants peuvent également être utilisés pour substituer des valeurs des entrées ou des sorties. En général, les drapeaux %- s'étendent à tous les noms de fichiers d'une liste. Par exemple, %o s'étend à tous les fichiers de sortie. Pour faire référence à un seul fichier, vous pouvez utiliser %1o, %2o, etc. pour faire référence au premier ou au deuxième (et ainsi de suite) nom de fichier de la liste.
%%
S'étend à un seul caractère « % » dans la chaîne de commande. Ceci doit être utilisé lorsque vous souhaitez que le caractère pourcentage soit interprété par la commande elle-même plutôt que par l'analyseur de tup.
%f
Les noms de fichiers de la section « inputs ». Cela inclut le chemin et l'extension. C'est plus utile dans une commande, car cela liste chaque nom de fichier d'entrée avec le chemin relatif au répertoire courant. Par exemple, « src/foo.c » serait copié exactement comme « src/foo.c ». Les fichiers individuels peuvent être référencés avec %1f, %2f, etc.
%i
Les noms de fichiers de la section « order-only inputs ». Cela inclut le chemin et l'extension. Les entrées d'ordre uniquement sont généralement utilisées pour les noms de fichiers qui ne doivent pas apparaître dans la ligne de commande, mais si vous avez besoin d'y faire référence, vous pouvez utiliser %i. Les fichiers individuels peuvent être référencés avec %1i, %2i, etc.
%b
Comme %f, mais ne représente que le nom de base du fichier. La partie répertoire est supprimée. Par exemple, « src/foo.c » deviendrait « foo.c ». Les fichiers individuels peuvent être référencés avec %1b, %2b, etc.
%B
Comme %b, mais supprime l'extension. C'est plus utile pour convertir un fichier d'entrée en un fichier de sortie du même nom mais avec une extension différente, car le fichier de sortie doit se trouver dans le même répertoire. Par exemple, « src/foo.c » deviendrait « foo ». Les fichiers individuels peuvent être référencés avec %1B, %2B, etc.
%e
L'extension de fichier du fichier actuel lorsqu'elle est utilisée dans une règle foreach. Cela peut être utilisé pour des variables qui peuvent avoir des valeurs différentes en fonction du suffixe du fichier. Par exemple, vous pourriez définir certains drapeaux pour les fichiers d'assemblage (.S) qui diffèrent de ceux des fichiers .c, puis utiliser une construction comme $(CFLAGS_%e) pour référencer la variable CFLAGS_S ou CFLAGS_c en fonction du type de fichier compilé. Par exemple, « src/foo.c » deviendrait « c », tandis que « src/foo.S » deviendrait « S ».
%o
Le nom du ou des fichiers de sortie. C'est utile dans une commande afin que le nom de fichier passé à une commande corresponde toujours à ce que tup considère comme la sortie. Cela ne fonctionne que dans la section « command », pas dans la section « outputs ». Les fichiers individuels peuvent être référencés avec %1o, %2o, etc.
%O
Le nom du fichier de sortie sans l'extension. Cela ne fonctionne que dans la section des sorties supplémentaires s'il n'y a qu'un seul fichier de sortie spécifié. Un cas d'utilisation pour cela est si vous avez un macro ! qui génère des fichiers non spécifiés sur la ligne de commande, mais qui sont basés sur la sortie nommée. Par exemple, si un éditeur de liens crée un fichier map en prenant la sortie spécifiée « foo.so », en supprimant « .so » et en ajoutant « .map », alors vous pourriez vouloir un macro ! comme suit : 
!ldmap = |> ld ... -o %o |> | %O.map
: foo1.o foo2.o |> !ldmap |> foo.so
%d
Le nom du niveau le plus bas du répertoire. Par exemple, dans foo/bar/Tupfile, ce serait la chaîne « bar ». Un cas où cela peut être utile est dans la dénomination des bibliothèques en fonction du répertoire dans lequel elles se trouvent, comme avec le macro ! suivant : 
!ar = |> ar crs %o %f |> lib%d.a
L'utilisation de ce macro dans foo/bar/Tupfile créerait alors foo/bar/libbar.a
%g
La chaîne qui a correspondu à un opérateur glob. Par exemple, avec les fichiers a_text.txt et b_text.txt, la règle : 
: foreach *_text.txt |> foo %f |> %g_binary.bin
produira les noms de fichiers a_binary.bin et b_binary.bin. Seul le premier glob développé sera substitué pour %g. %g n'est valide que lorsqu'il y a un seul fichier d'entrée ou lorsque foreach est utilisé.
%<group>
Tous les fichiers du « group ». Par exemple : 
#./submodules/sm1/Tupfile
: foo.c |> gcc -c %f -o %o |> %B.o ../<submodgroup>
#./submodules/sm2/Tupfile
: bar.c |> gcc -c %f -o %o |> %B.o ../<submodgroup>
#./project/Tupfile
: ../submodules/<submodgroup> |> echo '%f' > %o |> submodules_f.txt
: ../submodules/<submodgroup> |> echo '%<submodgroup>' > %o |> submodules_group.txt
produira « ../submodules/<submodgroup> » dans submodules_f.txt, mais « ../submodules/sm1/foo.o ../submodules/sm2/bar.o » dans submodules_group.txt. Si l'entrée contient plusieurs groupes du même nom mais dans des répertoires différents, %<group> sera développé pour tous les fichiers de chaque groupe listé.
var = valeur
var := valeur
Définit la variable « var » sur la valeur du côté droit. Les deux formes sont identiques et sont autorisées pour faciliter la conversion des anciens Makefiles. La variable « var » peut être référencée plus tard en utilisant « $(var) ». Les variables référencées ici sont toujours développées immédiatement. En tant que tel, définir une variable pour qu'elle contienne un drapeau % n'a pas de sens, car un drapeau % n'est valide que dans une règle :. La syntaxe $(var_%e) est autorisée dans une règle :. Les références de variables ne s'imbriquent pas, donc quelque chose comme $(var1_$(var2)) n'a pas de sens. Vous ne pouvez pas non plus passer de définitions de variables en ligne de commande ou via l'environnement. Toute référence à une variable dont la valeur n'a pas été définie renvoie une chaîne vide. 
CFLAGS = -Dfoo
: bar.c |> cc $(CFLAGS) $(other) -o %o -c %f |> %B.o
générera la commande « cc -Dfoo -o bar.o -c bar.c » lorsqu'elle sera exécutée.

Toute variable commençant par la chaîne « CONFIG_ » est automatiquement convertie en variable @ portant le même nom moins le préfixe « CONFIG_ ». En d'autres termes, $(CONFIG_FOO) et @(FOO) sont interchangeables. Tenter d'assigner une valeur à une variable CONFIG_ dans un Tupfile entraîne une erreur, car celles-ci ne peuvent être définies que dans le fichier tup.config.

Notez que vous pourriez voir une syntaxe utilisant des backticks lors de la définition de variables, telle que :

CFLAGS += `pkg-config fuse3 --cflags`
Tup n'effectue aucun traitement spécial pour les backticks, de sorte que la commande pkg-config n'est pas réellement exécutée lorsque la variable est définie dans cet exemple. Au lieu de cela, cela est passé tel quel à tout endroit qui l'utilise. Par conséquent, si une commande fait plus tard référence à $(CFLAGS), elle contiendra la chaîne `pkg-config fuse3 --cflags`, elle sera donc analysée par le shell.
var += valeur
Ajoute « valeur » à la fin de la valeur actuelle de « var ». Si « var » n'a pas été définie, cela équivaut à une instruction normale '='. Si « var » a déjà une valeur, un espace est ajouté à la variable avant que la nouvelle valeur ne soit ajoutée.
$(TUP_CWD)
[lua] tup.getcwd()
La variable spéciale $- TUP_CWD est toujours définie sur le chemin relatif au Tupfile actuellement analysé. Elle peut changer de valeur lors de l'inclusion d'un fichier dans un répertoire différent. Par exemple, si vous incluez « ../foo.tup », alors TUP_CWD sera défini sur « .. » lors de l'analyse de foo.tup. Cela permet à foo.tup de spécifier des drapeaux tels que « CFLAGS += -I$(TUP_CWD) », et CFLAGS contiendra toujours le répertoire -I où se trouve foo.tup, peu importe s'il a été inclus comme « ../foo.tup » ou « ../../foo.tup » ou « subdir/foo.tup ». Pour une alternative à $(TUP_CWD) lors de la référence à des fichiers, voir la section sur les variables &- ci-dessous.
$(TUP_VARIANTDIR)
[lua] tup.getvariantdir()
Similaire à $(TUP_CWD), $(TUP_VARIANTDIR) est défini pour être le chemin relatif au Tupfile actuellement analysé, mais pointe vers le répertoire correspondant dans la variante. À titre d'exemple où cela pourrait être utile, supposons que votre build génère des en-têtes communs dans un répertoire appelé "include/". Un Tuprules.tup au niveau de ce répertoire pourrait ajouter -I$(TUP_VARIANTDIR) à une variable de compilation. Si une variante est utilisée, cela sera évalué à un chemin tel que "../build/path/to/include", où "build" est le nom du répertoire de variantes. Si les variantes ne sont pas utilisées, TUP_VARIANTDIR est équivalent à TUP_CWD.
$(TUP_VARIANT_OUTPUTDIR)
[lua] tup.getvariantoutputdir()
$(TUP_VARIANT_OUTPUTDIR) pointe toujours vers le répertoire de sortie correspondant à la variante actuellement analysée. Contrairement à $(TUP_VARIANTDIR), il ne change pas lors de l'inclusion d'un autre fichier comme Tuprules.tup ou d'autres fichiers *.tup partiels. Sans variantes, cela est toujours évalué à la chaîne de caractères "." pour pointer vers le répertoire actuel .

Aucune autre variable spéciale $- n'existe pour le moment, mais par mesure de sécurité vous devriez supposer que toutes les variables nommées TUP_* sont réservées.

&var = fichier
&var := fichier
&var += fichier
Définit la variable & pour référencer le fichier ou le répertoire donné. Le fichier doit être un fichier normal, pas un fichier généré (une sortie d'une règle :-). Les variables & sont utilisées pour référencer des fichiers de manière similaire à $(TUP_CWD), sauf qu'au lieu de stocker le chemin relatif du fichier, les variables & stockent l'identifiant interne de tup du fichier. Cela signifie que le chemin relatif du fichier est déterminé lors de l'utilisation de la variable &, plutôt que lors de son affectation, comme c'est le cas avec $(TUP_CWD). Les variables & ne peuvent être utilisées qu'aux emplacements suivants : entrées de règles :-, entrées en ordre seulement de règles :-, commandes de règles :-, lignes d'inclusion, et lignes d'exécution de script, et elles peuvent être référencées plus tard en utilisant "&(var)". 
# Tuprules.tup
&libdir = src/lib
!cc = |> cc -I&(libdir) -c %f -o %o |> %B.o
# src/lib/Tupfile
: foreach *.c |> !cc |>
: *.o |> ar crs %o %f |> libstuff.a
# src/lib/test/Tupfile
: test_stuff.c |> !cc |>
: test_stuff.o &(libdir)/libstuff.a |> cc -o %o %f |> test_stuff
# src/Tupfile
: main.c |> !cc |> main.o
: main.o &(libdir)/libstuff.a |> cc -o %o %f |> main_app
générera les commandes build.sh suivantes (via "tup generate build.sh") : 
cd src/lib
cc -I. -c lib1.c -o lib1.o
cc -I. -c lib2.c -o lib2.o
ar crs libstuff.a lib1.o lib2.o
cd test
cc -I.. -c test_stuff.c -o test_stuff.o
cc -o test_stuff test_stuff.o ../libstuff.a
cd ../..
cc -Ilib -c main.c -o main.o
cc -o main_app main.o lib/libstuff.a
ifeq (lval,rval)
Évalue les paramètres 'lval' et 'rval' (c'est-à-dire : substitue toutes les variables $ et @), et effectue une comparaison de chaînes pour voir si elles correspondent. Si c'est le cas, toutes les lignes entre 'ifeq' et l'instruction 'endif' suivante sont traitées ; sinon, elles sont ignorées. Notez qu'aucun espace n'est élagué pour les valeurs - tout le texte entre '(' et ',' constitue 'lval', et tout le texte entre ',' et ')' constitue 'rval'. Cela signifie que ifeq (foo, foo) est faux, tandis que ifeq (foo,foo) est vrai. Ceci est pour la compatibilité avec les instructions if de Makefile. 
ifeq (@(FOO),y)
CFLAGS += -DFOO
else
CFLAGS += -g
endif
ifneq (lval,rval)
Identique à 'ifeq', mais avec la logique inversée.
ifdef VARIABLE
Teste si la variable @ nommée VARIABLE est définie du tout dans tup.config. Si c'est le cas, toutes les lignes entre 'ifdef' et l'instruction 'endif' suivante sont traitées ; sinon, elles sont ignorées. Par exemple, supposons que tup.config contienne : 
CONFIG_FOO=n
Alors 'ifdef FOO' sera évalué à vrai. Si tup.config n'existe pas, ou ne définit pas CONFIG_FOO d'une quelconque manière, alors 'ifdef FOO' sera faux.
ifndef VARIABLE
Identique à 'ifdef', mais avec la logique inversée.
else
Inverse la véracité de la condition précédente.
endif
Termine l'eq/ifdef/ifndef précédent. Notez que seuls 8 niveaux d'imbrication d'instructions if sont supportés.
error [message]
Provoque l'arrêt de l'analyse par tup et échoue, en affichant le message à l'utilisateur comme explication.
!macro = [entrées] | [entrées en ordre seulement] |> commande |> [sorties]
Définit le macro ! à la chaîne de commande donnée. Cette syntaxe est très similaire à la règle :-, car un macro ! est essentiellement un macro pour ces règles. Le macro ! n'est pas développé tant qu'il n'est pas utilisé dans la chaîne de commande d'une règle :-. Par conséquent, l'utilisation principale du macro ! est d'avoir un endroit pour stocker des chaînes de commandes avec des indicateurs % qui peuvent être réutilisés. Par exemple, nous pourrions avoir un macro !cc dans un fichier Tuprules.tup de niveau supérieur comme ceci : 
!cc = |> ^ CC %f^ gcc -c %f -o %o |>
Un Tupfile pourrait alors faire ceci : 
include_rules
: foreach *.c |> !cc |> %B.o
Vous ne voudrez spécifier le paramètre de sortie que dans le macro ! ou dans la règle :- qui l'utilise, mais pas les deux. Si vous spécifiez des entrées dans le macro !, elles seraient généralement des entrées en ordre seulement. Par exemple, si vous avez un macro !cc où vous utilisez un compilateur généré par tup, vous pouvez lister le fichier du compilateur dans la liste en ordre seulement du macro !. Le fichier du compilateur deviendra alors une dépendance d'entrée pour toute règle :- qui utilise le macro.
include fichier
Lit le fichier spécifié et continue l'analyse presque comme si ce fichier avait été collé en ligne dans le Tupfile actuel. Seuls les fichiers réguliers sont autorisés à être inclus -- tenter d'inclure un fichier généré est une erreur. Toutes les instructions d'inclusion qui se produisent dans le fichier inclus seront analysées par rapport au répertoire du fichier inclus.
include_rules
Lit les fichiers Tuprules.tup dans la chaîne de répertoires. Le premier fichier Tuprules.tup est lu en haut de la hiérarchie de tup, suivi du sous-répertoire suivant, et ainsi de suite jusqu'au fichier Tuprules.tup dans le répertoire actuel. De cette façon, le fichier Tuprules.tup de niveau supérieur peut spécifier des paramètres de variables généraux, et les sous-répertoires suivants peuvent les remplacer par des paramètres plus spécifiques. Vous spécifierez généralement include_rules comme première ligne du Tupfile. Le nom est un peu trompeur, car vous utiliseriez généralement Tuprules.tup pour définir des variables plutôt que des règles :-.
run ./script args
Exécute un script externe avec les arguments donnés pour générer des règles :-. C'est une fonctionnalité avancée qui peut être utilisée lorsque la syntaxe standard de Tupfile est trop simpliste pour un programme complexe. Le script est censé écrire les règles :- sur la sortie standard. Aucune autre commande Tupfile n'est autorisée - par exemple, le script ne peut pas créer de variables $- ou de macros !, mais il peut générer des règles :- qui utilisent ces fonctionnalités. Comme exemple simple, considérons qu'une commande doit être exécutée 5 fois, mais qu'il n'y a pas de fichiers d'entrée pour utiliser la boucle foreach de tup. Un script externe appelé 'build.sh' pourrait être écrit comme suit : 
#! /bin/sh -e
for i in `seq 1 5`; do
	echo ": |> echo $i > %o |> $i.txt"
done
Un Tupfile peut alors être utilisé pour obtenir ces règles : 
run ./build.sh
Tup traitera alors cela comme si un Tupfile était écrit avec 5 lignes comme suit : 
: |> echo 1 > %o |> 1.txt
: |> echo 2 > %o |> 2.txt
: |> echo 3 > %o |> 3.txt
: |> echo 4 > %o |> 4.txt
: |> echo 5 > %o |> 5.txt
Étant donné que l'étape d'analyse des Tupfiles est surveillée pour les dépendances, tous les fichiers que ce script accède dans la hiérarchie de tup entraîneront la réanalyse du Tupfile. Il y a cependant quelques limitations. Premièrement, l'appel readdir() est instrumenté pour retourner la liste des fichiers qui seraient accessibles au moment où le script d'exécution commence à s'exécuter. Cela signifie que les fichiers que vous voyez dans 'ls' sur la ligne de commande peuvent être différents des fichiers que votre script voit lorsqu'il est analysé. Tup fait semblant que les fichiers générés n'existent pas jusqu'à ce qu'il analyse une règle :- qui le liste comme sortie. Notez que toutes les règles :- exécutées par le script d'exécution lui-même ne seront pas analysées tant que le script ne s'exécute pas avec succès. Deuxièmement, en raison de certaines limitations structurelles dans tup, le script ne peut pas faire readdir() sur un répertoire autre que le répertoire du Tupfile. En d'autres termes, un script peut faire 'for i in *.c', mais pas 'for i in sub/*.c'. L'indicateur '--debug-run' peut être passé à 'tup' afin d'afficher la liste des règles :- que tup reçoit du script. En raison de l'instrumentation readdir(), cela peut être différent de la sortie du script lorsqu'il est exécuté manuellement depuis la ligne de commande.
preload répertoire
Par défaut, un script d'exécution ne peut utiliser readdir() (c'est-à-dire utiliser un joker) que sur le répertoire courant. Pour spécifier une liste d'autres répertoires joker autorisés, utilisez le mot-clé preload. Par exemple, si un script d'exécution doit examiner *.c et src/*.c, le répertoire src doit être préchargé : 
preload src
run ./build.sh *.c src/*.c
export VARIABLE
La directive export ajoute la variable d'environnement VARIABLE à la liste d'exportation pour les règles :- et les scripts d'exécution futurs. La valeur de la variable provient de l'environnement de tup, et non du Tupfile lui-même. Généralement, cela signifie que vous devrez définir la variable dans votre shell si vous souhaitez modifier la valeur utilisée par les commandes et les scripts. Par défaut, seul PATH est exporté. Windows exporte en outre plusieurs variables adaptées à la compilation avec la suite de compilateurs Visual Studio. Tup vérifiera les variables d'environnement exportées pour voir si leurs valeurs ont changé entre les mises à jour, et réexécutera toutes les commandes qui utilisent ces variables d'environnement. Notez que cela signifie que si PATH est modifié, toutes les commandes seront réexécutées. Par exemple : 
: |> command1 ... |>
export FOO
: |> command2 ... |>

Tup enregistrera la valeur actuelle de FOO et la transmettra à l'environnement lors de l'exécution de command2. Si FOO a une valeur différente lors de la prochaine mise à jour, alors command2 sera réexécutée avec la nouvelle valeur dans l'environnement. Dans cet exemple, command1 n'aura pas FOO dans son environnement et ne sera pas réexécutée lorsque sa valeur changera.

Notez que FOO ci-dessus est transmis à l'environnement ; il est

non fournies comme variables internes à tup. Ainsi, étant donné ce qui suit :

export FOO
: |> echo myFOO=$(FOO) envFOO=${FOO} > %o |> foo.txt
lorsqu'il est exécuté comme « $ FOO=silly tup », le contenu du fichier foo.txt serait « myFOO= envFOO=silly ». Si « export FOO » était supprimé du Tupfile, le contenu du fichier serait « myFOO= envFOO= » car tup ne propage pas les variables d'environnement sauf si elles sont explicitement exportées. Cela permet de préserver des compilations reproductibles et déterministes.

Si vous souhaitez exporter une variable vers une valeur spécifique plutôt que de récupérer la valeur de l'environnement, vous pouvez le faire dans votre shell plutôt qu'à travers tup. Par exemple, sous Linux, vous pouvez faire :

: |> FOO=valeur commande ... |>

Cette utilisation ne créera pas de dépendance vis-à-vis de la variable d'environnement FOO, car elle est contrôlée via le Tupfile.

import VARIABLE[=défaut]
La directive d'importation définit une variable dans le Tupfile qui a la valeur de la variable d'environnement. Si la variable d'environnement n'est pas définie, la valeur par défaut est utilisée à la place si elle est fournie. Cela introduit une dépendance de la variable d'environnement vers le Tupfile, de sorte que si la variable d'environnement change, le Tupfile est re-analysé. Par exemple :
import CC=gcc
: foreach *.c |> $(CC) -c %f -o %o |> %B.o
Ceci compilera tous les fichiers .c avec le compilateur défini dans la variable d'environnement CC. Si CC n'est pas défini dans l'environnement, gcc sera utilisé par défaut. Lors d'une compilation ultérieure, l'exécution de 'CC=clang tup' re-analysera ce Tupfile et reconstruira tous les fichiers .c avec clang à la place (puisque les lignes de commande ont changé).

Contrairement à 'export', la commande d'importation ne passe pas les variables à l'environnement du sous-processus. Dans l'exemple précédent, la variable d'environnement CC n'est donc pas définie dans le sous-processus, à moins que 'export CC' ne soit également présent dans le Tupfile.

.gitignore
Indique à tup de générer automatiquement un fichier .gitignore dans le répertoire courant contenant une liste des fichiers de sortie générés par tup. Cela peut être utile si vous utilisez git, car l'ensemble des fichiers générés par tup correspond exactement à l'ensemble des fichiers que vous souhaitez que git ignore. Si vous utilisez des fichiers Tuprules.tup, vous pourriez simplement spécifier .gitignore dans le Tuprules.tup de niveau supérieur, puis faire en sorte que tous les autres Tupfiles utilisent include_rules pour récupérer la définition de .gitignore. De cette façon, vous n'avez jamais à maintenir les fichiers .gitignore manuellement. Notez que vous pourriez souhaiter ignorer d'autres fichiers non créés par tup, tels que les fichiers temporaires créés par votre éditeur. Dans ce cas, vous voulez configurer un fichier gitignore global en utilisant une commande telle que 'git config --global core.excludesfile ~/.gitignore', puis configurer ~/.gitignore avec votre liste personnelle. Pour d'autres cas, vous pouvez également simplement ajouter des règles d'ignorance personnalisées au-dessus de la ligne « ##### TUP GITIGNORE ##### ».
#
Au début d'une ligne, un caractère '#' signifie un commentaire. Une ligne de commentaire est ignorée par l'analyseur. Le commentaire peut avoir des espaces blancs en tête qui sont également ignorés. S'il y a un caractère non blanc avant un caractère '#', la ligne n'est pas un commentaire. Cela signifie également que si une ligne précédente se terminait par '\' (saut de ligne), alors '#' est interprété comme un symbole ordinaire.

NOTES SUR TUPFILE

L'expansion des variables dans tup est immédiate dans tous les cas, sauf pour les macros !-. C'est-à-dire que si vous voyez une règle : ou une déclaration de variable, vous pouvez substituer les valeurs actuelles des variables. Les macros !- ne sont analysées que lorsqu'elles sont utilisées dans une règle :-. Dans ce cas, la règle :- réelle est une sorte d'union entre la règle :- telle qu'écrite et la valeur actuelle de la macro !-.

Lorsque tup analyse un Tupfile, il effectue une seule passe sur le fichier, analysant une ligne à la fois. À la fin du Tupfile, toutes les définitions de variables, de macros !- et de {bin} sont supprimées. Les seuls effets persistants de l'analyse d'un Tupfile sont les nœuds de commande et les dépendances qui existent désormais dans la base de données tup. De plus, un fichier .gitignore peut avoir été créé si demandé par le Tupfile.

@-VARIABLES

Les @-variables sont des variables spéciales dans tup. Elles sont utilisées comme variables de configuration et peuvent être lues par les Tupfiles ou utilisées par la commande varsed. Les commandes peuvent également les lire, mais le programme exécuté par la commande doit connaître directement les variables. Les @-variables sont spécifiées dans le fichier tup.config au sommet de la hiérarchie tup ou dans un répertoire de variantes. Par exemple, tup.config peut contenir :

CONFIG_FOO=y

Un Tupfile peut alors lire la @-variable comme ceci :

srcs-@(FOO) += foo.c
srcs-y += bar.c
: foreach $(srcs-y) |> gcc -c %f -o %o |> %B.o

Dans cet exemple, si CONFIG_FOO est défini sur 'y', alors le fichier foo.c sera inclus dans la liste d'entrée et donc compilé. Si CONFIG_FOO n'est pas spécifié ou est défini sur une autre valeur, foo.c ne sera pas inclus.

Les @-variables peuvent être utilisées de manière similaire aux $-variables, avec les distinctions suivantes : 1) les @-variables sont en lecture seule dans les Tupfiles, et 2) les @-variables sont dans le DAG, ce qui signifie que la lecture à partir d'elles crée une dépendance de la @-variable vers le Tupfile. Par conséquent, tout Tupfile qui lit @(FOO) comme dans l'exemple ci-dessus sera re-analysé si la valeur de CONFIG_FOO dans tup.config change.

La raison de préfixer avec « CONFIG_ » dans le fichier tup.config est de maintenir la compatibilité avec kconfig, qui peut être utilisé pour générer ce fichier.

Notez que la syntaxe de tup.config est assez stricte. Pour une instruction telle que « CONFIG_FOO=y », tup créera une @-variable en utilisant la chaîne commençant après « CONFIG_ » et jusqu'au signe « = ». La valeur est tout ce qui suit immédiatement le signe « = » jusqu'à la nouvelle ligne, mais s'il y a une paire de guillemets entourant, ils sont supprimés. Dans cet exemple, cela définirait « FOO » à « y ». Notez que si la ligne était plutôt « CONFIG_FOO = y », alors la variable « FOO » serait définie à « y ».

Dans tup.config, les commentaires sont déterminés par un caractère '#' dans la première colonne. Ceux-ci sont ignorés, sauf si le commentaire est de la forme :

# CONFIG_FOO is not set
Dans ce cas, la @-variable « FOO » est explicitement définie à « n ».
@(TUP_PLATFORM)
TUP_PLATFORM est une @-variable spéciale. Si CONFIG_TUP_PLATFORM n'est pas défini dans le fichier tup.config, il a une valeur par défaut selon la plateforme sur laquelle tup lui-même a été compilé. Actuellement, la valeur par défaut est l'une des suivantes : « linux », « solaris », « macosx », « win32 », « freebsd » ou « netbsd ».
@(TUP_ARCH)
TUP_ARCH est une autre @-variable spéciale. Si CONFIG_TUP_ARCH n'est pas défini dans le fichier tup.config, il a une valeur par défaut selon l'architecture du processeur sur laquelle tup lui-même a été compilé. Actuellement, la valeur par défaut est l'une des suivantes : « i386 », « x86_64 », « powerpc », « powerpc64 », « ia64 », « alpha », « sparc », « riscv32 », « riscv64 », « arm64 », « arm » ou « s390x ».

VARIANTS

Tup prend en charge les variantes, qui vous permettent de compiler votre projet plusieurs fois avec des configurations différentes. Le cas le plus courant est peut-être de construire une configuration de sortie et de débogage avec des indicateurs de compilateur différents, bien que n'importe quel nombre de variantes puisse être utilisé pour prendre en charge les configurations que vous souhaitez. Chaque variante est construite dans son propre répertoire, distinct des autres et de l'arborescence source. Lors de la construction avec des variantes, la construction dans l'arborescence est désactivée. Pour créer une variante, créez un nouveau répertoire au sommet de la hiérarchie tup et créez-y un fichier « tup.config ». Par exemple :

$ mkdir build-default
$ touch build-default/tup.config
$ tup

Ici, nous avons créé un répertoire appelé « build-default » et créé un tup.config vide à l'intérieur. Notez que le répertoire de build doit être au même niveau que le répertoire « .tup ». Lors de la mise à jour, tup analysera tous les Tupfiles en utilisant le fichier de configuration que nous avons créé, et placera tous les produits de construction dans des sous-répertoires de build-default qui reflètent l'arborescence source. Nous pourrions alors créer une autre variante comme ceci :

$ mkdir build-debug
$ echo "CONFIG_MYPROJ_DEBUG=y" > build-debug/tup.config
$ tup

Cette fois, tous les Tupfiles seront analysés avec @(MYPROJ_DEBUG) défini sur « y », et tous les produits de construction seront placés dans le répertoire build-debug. Notez que la définition de @(MYPROJ_DEBUG) n'a un effet que si la variable est réellement utilisée dans un Tupfile (peut-être en ajoutant des indicateurs de débogage à la ligne de commande du compilateur).

L'exécution de « tup » mettra à jour toutes les variantes. Par exemple, une mise à jour après modification d'un fichier C utilisé dans toutes les configurations entraînera sa re-compilation pour chaque variante. Comme pour toute commande exécutée, cela se fait en parallèle sous réserve des contraintes du DAG et du nombre de tâches spécifiées. Pour construire une seule variante (ou un sous-ensemble de variantes), spécifiez le répertoire de build comme cible pour « tup », comme pour toute mise à jour partielle. Par exemple :

$ tup build-default

Pour supprimer une variante, il suffit de supprimer le répertoire de build :

$ rm -rf build-debug

Si vous compilez avec des variantes, il est recommandé d'avoir toujours une variante par défaut contenant un fichier tup.config vide. Cela aide à vérifier que votre logiciel peut toujours être construit en le clonant simplement et en exécutant « tup init ; tup » sans dépendre d'une configuration spécifique.


Lors de l'utilisation de constructions dans l'arborescence, les résultats de construction peuvent dépendre de fichiers d'exécution, placés dans l'arborescence source et non traités par tup. Tup permet de copier ces fichiers verbatim dans le répertoire de construction de la variante en fournissant une macro intégrée « !tup_preserve » :

:foreach *.png |> !tup_preserve |>

Un lien symbolique ou une copie du fichier source sera créé, en fonction du système d'exploitation et du système de fichiers utilisés.

EXEMPLE

L'analyse d'une règle :- peut être un peu déroutante au début. Vous trouverez peut-être plus facile de considérer le Tupfile comme un script shell avec des annotations d'entrée/sortie supplémentaires pour les commandes. Par exemple, considérons ce Tupfile :

WARNINGS += -W
WARNINGS += -Wall
CFLAGS = $(WARNINGS) -O2
CFLAGS_foo.c = -DFOO
: |> echo '#define BAR 3' > %o |> foo.h
: foreach *.c | foo.h |> gcc -c %f -o %o $(CFLAGS) $(CFLAGS_%f) |> %B.o
: *.o |> gcc %f -o %o |> program

TUPFILES

Ce sont des fichiers qui décrivent le graphe de dépendances du projet. Ils sont écrits en utilisant une syntaxe simple et expressive.

Les fichiers Tupfile peuvent utiliser des variables de type chaîne de caractères, des règles et des instructions spéciales. Voici un aperçu des concepts clés utilisés dans les Tupfiles :

VARIABLES

Les variables sont déclarées et utilisées avec la syntaxe "VARIABLE = valeur".

Exemple :

CC = gcc
CFLAGS = -O2
LDFLAGS = -lm
TARGET = myprogram

Les variables peuvent également être utilisées dans d'autres variables, en utilisant la syntaxe $(VARIABLE).

Exemple :

WARNINGS = -W
WARNINGS += -Wall
CFLAGS += $(WARNINGS)
CFLAGS += -O2
CFLAGS_foo.c = -DFOO

Dans cet exemple, la variable WARNINGS est initialement vide. La première ligne "WARNINGS += -W" définit la variable WARNINGS à "-W". La deuxième ligne ajoute, donc WARNINGS sera défini à "-W -Wall". La troisième ligne référence cette valeur, donc CFLAGS sera maintenant égal à "-W -Wall -O2". La quatrième ligne définit une nouvelle variable, nommée CFLAGS_foo.c, et la définit à "-DFOO".

RÈGLES

Les règles définissent comment générer des fichiers à partir d'autres fichiers. La syntaxe générale est :

rule [nom_règle]
    inputs: [liste_des_entrées]
    outputs: [liste_des_sorties]
    command: [commande_à_exécuter]
endrule

Exemple :

rule compile
    inputs: %f.c foo.h
    outputs: %f.o
    command: $(CC) -c %f.c -o %f.o $(CFLAGS)
endrule

Dans cet exemple, la règle `compile` prend un fichier source `.c` et un fichier d'en-tête `foo.h` en entrée, et produit un fichier objet `.o` en sortie. La commande utilise la variable `$(CC)` pour le compilateur et `$(CFLAGS)` pour les options de compilation. `%f` est un substitut pour le nom de fichier de base (sans extension).

FOREACH

La directive `foreach` permet d'appliquer une règle à plusieurs fichiers qui correspondent à un motif.

Exemple :

foreach *.c
    $(CC) -c %f.c -o %o $(CFLAGS) $(CFLAGS_%f.c)
endforech

La première règle créera un nouveau nœud "foo.h" dans la base de données, ainsi que la commande correspondante pour le créer. Notez que ce fichier n'existera pas dans le système de fichiers tant que la commande ne sera pas réellement exécutée après l'analyse de tous les Tupfiles.

La règle `foreach` générera une commande pour compiler chaque fichier. D'abord, tup analysera la section d'entrée, et utilisera l'opération `glob` sur la base de données puisqu'un '*' est présent. Ce `glob` correspondra à `foo.c` et `bar.c`. Puisqu'il s'agit d'une règle `foreach`, tup exécutera la règle d'abord en utilisant l'entrée "foo.c", et à nouveau en utilisant l'entrée "bar.c". Le motif de sortie est analysé à chaque passage, suivi de la chaîne de commande.

Lors du passage pour `foo.c`, le motif de sortie "%B.o" est analysé, ce qui sera égal à "foo.o". Maintenant, la chaîne de commande est analysée, remplaçant "foo.c" par "%f" et "foo.o" par "%o". Les variables $ sont ensuite développées, donc $(CFLAGS) devient "-W -Wall -O2", et $(CFLAGS_foo.c)" devient "-DFOO". La chaîne de commande finale écrite dans la base de données est "gcc -c foo.c -o foo.o -W -Wall -O2 -DFOO". Un lien de sortie est écrit vers le fichier `foo.o`, et des liens d'entrée sont écrits depuis `foo.c` et `foo.h` (l'entrée ordonnée uniquement).

Lors du second passage dans la règle `foreach`, la seule différence est que "bar.c" est l'entrée. Par conséquent, le motif de sortie devient "bar.o", et la chaîne de commande finale devient "gcc -c bar.c -o bar.o -W -Wall -O2 " puisque $(CFLAGS_bar.c) n'était pas spécifié.

Pour plus d'exemples avec des DAG correspondants, voir http://gittup.org/tup/examples.html

AUTRES SYSTÈMES DE CONSTRUCTION

Tup est un peu différent des autres systèmes de construction. Il utilise une structure de graphe bien définie qui est maintenue dans une base de données séparée. Un ensemble d'algorithmes pour opérer sur ce graphe a été développé afin de gérer des cas tels que la modification d'un fichier existant, la création ou la suppression de fichiers, la modification des lignes de commande, etc. Ces algorithmes sont très efficaces - en particulier, pour le cas où un projet est déjà construit et où un ou plusieurs fichiers existants sont modifiés, tup est optimal parmi les systèmes de construction basés sur des fichiers. Pour d'autres cas, tup est au moins très rapide, mais l'optimalité n'a pas été prouvée.

La raison principale de la base de données de graphes est de permettre à l'algorithme de mise à jour de tup d'accéder facilement aux informations dont il a besoin. En tant qu'effet secondaire très utile de la structure de base de données bien définie, tup peut déterminer quand un fichier généré n'est plus nécessaire. Ce que cela signifie, c'est qu'il n'y a pas de cible `clean`. Il n'est pas non plus nécessaire de faire un "checkout frais" et de compiler votre logiciel à partir de zéro. N'importe quel nombre d'itérations de mises à jour produit toujours le même résultat que s'il avait tout reconstruit à neuf. Si vous trouvez le contraire, vous avez probablement trouvé un bug dans tup (pas dans vos Tupfiles), auquel cas vous devriez en informer la liste de diffusion (voir CONTACT).

Pour plus d'informations sur la théorie derrière tup, voir http://gittup.org/tup/build_system_rules_and_algorithms.pdf
