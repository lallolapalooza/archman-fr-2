NOM

trace-cmd.dat.v7 - format de fichier trace-cmd version 7

SYNTAXE

trace-cmd.dat ignorer

DESCRIPTION

L'utilitaire trace-cmd(1) produit un fichier "trace.dat". Le fichier peut également porter un autre nom si l'utilisateur spécifie un nom de sortie différent, mais il doit respecter un certain format binaire. Le fichier est utilisé par trace-cmd pour y enregistrer les traces du noyau et pouvoir en extraire la trace ultérieurement (voir trace-cmd-report(1)).

FORMAT INITIAL

Les trois premiers octets contiennent la valeur magique :
0x17 0x08  0x44
Les 7 octets suivants contiennent les caractères :
"tracing"
L'ensemble suivant de caractères contient une chaîne terminée par un octet nul
('\0') qui contient la version du fichier :
"7\0"
L'octet suivant contient les drapeaux de l'endianness du fichier :
0 = little endian
1 = big endian
L'octet suivant contient le nombre d'octets par valeur "long" :
4 - valeurs longues 32 bits
8 - valeurs longues 64 bits
Note : Il s'agit de la taille du type long de l'espace utilisateur de la cible.
Pas de la taille de l'espace noyau.
[ Tous les nombres sont maintenant écrits dans l'endianness défini par le fichier. ]
Les 4 octets suivants forment un mot de 32 bits qui définit la taille de page de la machine hôte tracée.
L'en-tête de l'algorithme de compression est écrit ensuite :
   "nom\0version\0"
où "nom" et "version" sont des chaînes de caractères, le nom et la version de l'algorithme
de compression utilisé pour compresser le fichier de trace. Si le nom est
"none", les données du fichier ne sont pas compressées.
Les 8 octets suivants sont un entier de 64 bits, représentant le décalage dans le fichier où se trouve la première section OPTIONS.
Le reste du fichier est constitué de différentes sections. La seule section obligatoire
est la première section OPTIONS, toutes les autres sont optionnelles. L'emplacement et
l'ordre des sections ne sont pas stricts. Chaque section commence par un en-tête :

FORMAT DE L'EN-TÊTE DE SECTION

<2 octets> entier non signé court, ID de la section.
<2 octets> entier non signé court, drapeaux de section :
  1 = la section est compressée.
<4 octets> ID d'une chaîne de caractères, description de la section.
<8 octets> entier non signé long long, taille de la section dans le fichier.
Si la section est compressée, ce qui précède représente la taille compressée.
La section doit être décompressée lors de la lecture. Le format décrit des
sections fait référence aux données décompressées.
FORMAT DE COMPRESSION DES SECTIONS DU FICHIER :
Certaines des sections du fichier peuvent être compressées avec l'algorithme de compression
spécifié dans l'en-tête de l'algorithme de compression. Les sections compressées ont un en-tête de compression, écrit après l'en-tête de section et juste avant les données compressées :
  <4 octets> entier non signé, taille des données compressées dans cette section.
  <4 octets> entier non signé, taille des données décompressées.
  <données> données binaires compressées, avec la taille spécifiée.

FORMAT DE COMPRESSION DES DONNÉES DE TRACE

Il existe deux sections spéciales, BUFFER FLYRECORD et BUFFER LATENCY, contenant
des données de trace. Ces sections peuvent être compressées avec l'algorithme de compression
spécifié dans l'en-tête de compression. Habituellement, la taille de ces sections est énorme, c'est pourquoi leur format de compression est différent des autres sections. Les données de trace sont compressées par
morceaux. La taille d'un morceau est spécifiée au moment de la création du fichier. Le format
des données de trace compressées est le suivant :
   <4 octets> entier non signé, nombre de morceaux.
   Suit les morceaux compressés du nombre donné. Pour chaque morceau :
      <4 octets> entier non signé, taille des données compressées dans ce morceau.
      <4 octets> entier non signé, taille des données décompressées, alignée sur la taille de page de trace.
      <données> données binaires compressées, avec la taille spécifiée.
Ces morceaux doivent être décompressés lors de la lecture. Le format décrit des
données de trace fait référence aux données décompressées.

SECTION OPTIONS

ID de section : 0
C'est la seule section obligatoire du fichier. Il peut y avoir plusieurs
sections d'options, la première est située au décalage spécifié juste après
l'en-tête de l'algorithme de compression. La section se compose de plusieurs
options de trace, chaque option a le format suivant :
  <2 octets> entier non signé court, ID de l'option.
  <4 octets> entier non signé, taille des données de l'option.
  <données binaires> octets de la taille spécifiée ci-dessus, données de l'option.
Options prises en charge par la version 7 du fichier de trace :
DONE: id 0, taille 8
  Cette option indique la fin de la section des options, elle est toujours
  écrite comme dernière option. Les données de l'option DONE sont :
     <8 octets> entier non signé long long, décalage dans le fichier de trace où
     se trouve la prochaine section d'options. Si ce décalage est 0, alors
     il n'y a plus de sections d'options.
DATE: id 1, taille variable
  Les données de l'option DATE sont une chaîne ASCII terminée par un octet nul,
  qui représente la différence de temps entre les horodatages des événements de trace
  et l'heure système générique (Generic Time of Day) du système.
CPUSTAT: id 2, taille variable
  Les données de l'option CPUSTAT sont une chaîne ASCII terminée par un octet nul, le contenu du
  fichier "per_cpu/cpu<id>/stats" du répertoire de trace. Il y a une option CPUSTAT
  pour chaque CPU.
BUFFER: id 3, taille variable
  L'option BUFFER décrit les données de trace flyrecord enregistrées dans le fichier, collectées
  à partir d'une instance de trace. Il y a une option BUFFER pour chaque instance de trace. Le format
  des données BUFFER est le suivant :
    <8 octets> entier non signé long long, décalage dans le fichier de trace où se trouve
    la section BUFFER FLYRECORD contenant les données de trace flyrecord.
    <chaîne> une chaîne ASCII terminée par un octet nul, nom de l'instance de trace. Une chaîne vide ""
    est enregistrée comme nom de l'instance parente.
    <chaîne> une chaîne ASCII terminée par un octet nul, horloge de trace utilisée pour les horodatages des événements dans
    cette instance de trace.
    <4 octets> entier non signé, taille de la page du tampon de trace.
    <4 octets> entier non signé, nombre de CPU ayant des données de trace.
    Pour chaque CPU du nombre ci-dessus :
       <4 octets> entier non signé, ID du CPU.
       <8 octets> entier non signé long long, décalage dans le fichier de trace où se trouvent les données de trace
       pour ce CPU.
       <8 octets> entier non signé long long, taille des données de trace pour ce CPU.
TRACECLOCK: id 4, taille variable
  Les données de l'option TRACECLOCK sont une chaîne ASCII terminée par un octet nul, le contenu du
  fichier "trace_clock" du répertoire de trace.
UNAME: id 5, taille variable
  Les données de l'option UNAME sont une chaîne ASCII terminée par un octet nul, identifiant le système où
  les données de trace sont collectées. La chaîne est récupérée par l'appel système uname().
HOOK: id 6, taille variable
  Les données de l'option HOOK sont une chaîne ASCII terminée par un octet nul, décrivant les hooks d'événements : une correspondance d'événements personnalisée pour connecter deux événements ensemble.
OFFSET: id 7, taille variable
  Les données de l'option OFFSET sont une chaîne ASCII terminée par un octet nul, représentant un temps fixe qui
  est ajouté à chaque horodatage d'événement lors de la lecture.
CPUCOUNT: id 8, taille 4
  Les données de l'option CPUCOUNT sont :
    <4 octets> entier non signé, nombre de CPU dans le système.
VERSION: id 9, taille variable
  Les données de l'option VERSION sont une chaîne ASCII terminée par un octet nul, représentant la version de
  l'application trace-cmd utilisée pour collecter ces journaux de trace.
PROCMAPS: id 10, taille variable

  de chaque processus filtré tracé. Le format de la chaîne est, pour cha

OPTION SECTION

This section contains options which store metadata about the trace session.
These options are saved in the trace file before the trace data.
There are two types of options: Fixed size and variable size.
The trace file structure is as follows:
    <8 bytes> option ID
    <8 bytes> option size
    <variable size> option data
The option ID and size are read first to determine how much data to read for the
option.
All multi-byte values are saved in little-endian format.
The following options are supported:
TRACE_OPTIONS: id 1, size vary
  The TRACE_OPTIONS option stores the enabled trace options. The format is a
  bitmask of the available trace options.
    <8 bytes> long long unsigned integer, trace options bitmask.
TRACE_SIZE: id 2, size 8
  The TRACE_SIZE option stores the size of the trace buffer in pages.
    <8 bytes> long long unsigned integer, trace buffer size in pages.
TRACE_MiB: id 3, size 8
  The TRACE_MiB option stores the size of the trace buffer in MiB.
    <8 bytes> long long unsigned integer, trace buffer size in MiB.
TRACE_TIME: id 4, size 8
  The TRACE_TIME option stores the time the trace session started.
    <8 bytes> long long unsigned integer, trace start time in nanoseconds.
TRACE_CPUS: id 5, size vary
  The TRACE_CPUS option stores the list of CPUs that are being traced.
    <4 bytes> unsigned integer, number of CPUs.
    <array of unsigned integers of the above count>, CPU IDs.
TRACE_BUF_SIZE: id 6, size 8
  The TRACE_BUF_SIZE option stores the size of the per-CPU trace buffers.
    <8 bytes> long long unsigned integer, per-CPU trace buffer size in bytes.
TRACE_FUNC: id 7, size vary
  The TRACE_FUNC option stores the list of functions that are being traced.
    <4 bytes> unsigned integer, number of functions.
    <array of null terminated ASCII strings of variable size>, function names.
TRACE_MCOUNT_SYM: id 8, size vary
  The TRACE_MCOUNT_SYM option stores the list of functions that are being profiled.
    <4 bytes> unsigned integer, number of functions.
    <array of null terminated ASCII strings of variable size>, function names.
TRACE_KTIME: id 9, size 8
  The TRACE_KTIME option stores the kernel's time reference.
    <8 bytes> long long unsigned integer, kernel time in nanoseconds.
TRACE_MAX_LAT: id 10, size 8
  The TRACE_MAX_LAT option stores the maximum latency recorded.
    <8 bytes> long long unsigned integer, maximum latency in nanoseconds.
CH FILTERED PROCESS: id 11, size vary
  The CH FILTERED PROCESS option stores information about processes that were filtered out.
  This is used to help reconstruct the full process list if needed.
    <procss ID> <libraries count> <process command> \n
      <memory start address> <memory end address> <full path of the mapped library file> \n
      ...
       separate line for each library, used by this process
      ...
    ...
TRACEID: id 11, size 8
  The TRACEID option data is a unique identifier of this tracing session:
    <8 bytes> long long unsigned integer, trace session identifier.
TIME_SHIFT: id 12, size vary
  The TIME_SHIFT option stores time synchronization information, collected during host and guest
  tracing session. Usually it is saved in the guest trace file. This information is used to
  synchronize guest with host events timestamps, when displaying all files from this tracing
  session. The format of the TIME_SHIFT option data is:
    <8 bytes> long long unsigned integer, trace identifier of the peer (usually the host).
    <4 bytes> unsigned integer, flags specific to the time synchronization protocol, used in this
    trace session.
    <4 bytes> unsigned integer, number of traced CPUs. For each CPU, timestamps corrections
    are recorded:
       <4 bytes> unsigned integer, count of the recorded timestamps corrections for this CPU.
       <array of unsigned long long integers of the above count>, times when the corrections are calculated
       <array of unsigned long long integers of the above count>, corrections offsets
       <array of unsigned long long integers of the above count>, corrections scaling ratio
GUEST: id 13, size vary
  The GUEST option stores information about traced guests in this tracing session. Usually it is
  saved in the host trace file. There is a separate GUEST option for each traced guest.
  The information is used when displaying all files from this tracing session. The format of
  the GUEST option data is:
     <string> a null terminated ASCII string, name of the guest.
     <8 bytes> long long unsigned integer, trace identifier of the guest for this session.
     <4 bytes> unsigned integer, number of guest's CPUs. For each CPU:
        <4 bytes> unsigned integer, ID of the CPU.
        <4 bytes> unsigned integer, PID of the host task, emulating this guest CPU.
TSC2NSEC: id 14, size 16
  The TSC2NSEC option stores information, used to convert TSC events timestamps to nanoseconds.
  The format of the TSC2NSEC option data is:
     <4 bytes> unsigned integer, time multiplier.
     <4 bytes> unsigned integer, time shift.
     <8 bytes> unsigned long long integer, time offset.
STRINGS: id 15, size vary
  The STRINGS option holds a list of nul terminated strings that holds the names of the
  other sections.
HEADER_INFO: id 16, size 8
  The HEADER_INFO option data is:
    <8 bytes> long long unsigned integer, offset into the trace file where the HEADER INFO
    section is located
FTRACE_EVENTS: id 17, size 8
  The FTRACE_EVENTS option data is:
    <8 bytes> long long unsigned integer, offset into the trace file where the
    FTRACE EVENT FORMATS section is located.
EVENT_FORMATS: id 18, size 8
  The EVENT_FORMATS option data is:
    <8 bytes> long long unsigned integer, offset into the trace file where the EVENT FORMATS
    section is located.
KALLSYMS: id 19, size 8
  The KALLSYMS option data is:
    <8 bytes> long long unsigned integer, offset into the trace file where the KALLSYMS
    section is located.
PRINTK: id 20, size 8
  The PRINTK option data is:
    <8 bytes> long long unsigned integer, offset into the trace file where the TRACE_PRINTK
    section is located.
CMDLINES: id 21, size 8
  The CMDLINES option data is:
    <8 bytes> long long unsigned integer, offset into the trace file where the
    SAVED COMMAND LINES section is located.
BUFFER_TEXT: id 22, size
  The BUFFER_LAT option describes the latency trace data saved in the file. The format
  of the BUFFER_LAT data is:
    <8 bytes> long long unsigned integer, offset in the trace file where the
    BUFFER LATENCY section is located, containing latency trace data.
    <string> a null terminated ASCII string, name of the trace instance. Empty string ""
    is saved as name of the top instance.
    <string> a null terminated ASCII string, trace clock used for events timestamps in
    this trace instance.

HEADER INFO SECTION

Section ID: 16
The first 12 bytes of the section, after the section header, contain the string:
"header_page\0"
The next 8 bytes are a 64-bit word containing the size of the
page header information stored next.
The next set of data is of the size read from the previous 8 bytes,
and contains the data retrieved from debugfs/tracing/events/header_page.
Note: The size of the second field \fBcommit\fR contains the target
kernel long size. For example:
field: local_t commit;        offset:8;       \fBsize:8;\fR   signed:1;
shows the kernel has a 64-bit long.
The next 13 bytes contain the string:
"header_event\0"
The next 8 bytes are a 64-bit word containing the size of the
event header information stored next.
The next set of data is of the size read from the previous 8 bytes
and contains the data retrieved from debugfs/tracing/events/header_event.
This data allows the trace-cmd tool to know if the ring buffer format
of the kernel made any changes.

FTRACE EVENT FORMATS SECTION

Section ID: 17
Directly after the section header comes the information about
the Ftrace specific events. These are the events used by the Ftrace plugins
and are not enabled by the event tracing.
The next 4 bytes contain a 32-bit word of the number of Ftrace event
format files that are stored in the file.
For the number of times defined by the previous 4 bytes is the
following:
8 bytes for the size of the Ftrace event format file.
The Ftrace event format file copied from the target machine:
debugfs/tracing/events/ftrace/<event>/format

EVENT FORMATS SECTION

Section ID: 18
Directly after the section header comes the information about
the event layout.
The next 4 bytes are a 32-bit word containing the number of
event systems that are stored in the file. These are the
directories in debugfs/tracing/events excluding the \fBftrace\fR
directory.
For the number of times defined by the previous 4 bytes is the
following:
A null-terminated string containing the system name.
4 bytes containing a 32-bit word containing the number
of events within the system.
For the number of times defined in the previous 4 bytes is the
following:
8 bytes for the size of the event format file.
The event format file copied from the target machine:
debugfs/tracing/events/<system>/<event>/format

KALLSYMS SECTION

Section ID: 19
Directly after the section header comes the information of the mapping
of function addresses to the function names.
The next 4 bytes are a 32-bit word containing the size of the
data holding the function mappings.
The next set of data is of the size defined by the previous 4 bytes
and contains the information from the target machine's file:
/proc/kallsyms

TRACE_PRINTK SECTION

Section ID: 20
If a developer used trace_printk() within the kernel, it may
store the format string outside the ring buffer.
This information can be found in:
debugfs/tracing/printk_formats
The next 4 bytes are a 32-bit word containing the size of the
data holding the printk formats.
The next set of data is of the size defined by the previous 4 bytes
and contains the information from debugfs/tracing/printk_formats.

SAVED COMMAND LINES SECTION

Section ID: 21
Directly after the section header comes the information mapping
a PID to a process name.
The next 8 bytes contain a 64-bit word that holds the size of the
data mapping the PID to a process name.
The next set of data is of the size defined by the previous 8 bytes
and contains the information from debugfs/tracing/saved_cmdlines.

BUFFER FLYRECORD SECTION

This section contains flyrecord tracing data, collected in one trace instance.
The data is saved per CPU. Each BUFFER FLYRECORD section has a corresponding BUFFER
option, containing information about saved CPU's trace data. Padding is placed between
the section header and the CPU data, placing the CPU data at a page aligned (target page)
position in the file.
This data is copied directly from the Ftrace ring buffer and is of the
same format as the ring buffer specified by the event header files
loaded in the header format file.
The trace-cmd tool will try to \fBmmap(2)\fR the data page by page with the
target's page size if possible. If it fails to mmap, it will just read the
data instead.

BUFFER TEXT SECTION

This section contains buffer text trace data, collected in one trace instance.
The data is saved per CPU. Each BUFFER TEXT section has a corresponding BUFFER
option, containing information about saved CPU's trace data. Padding is placed between
the section header and the CPU data, placing the CPU data at a page aligned (target page)
position in the file.
This data is copied directly from the Ftrace ring buffer and is of the
same format as the ring buffer specified by the event header files
loaded in the header format file.
The trace-cmd tool will try to \fBmmap(2)\fR the data page by page with the
target's page size if possible. If it fails to mmap, it will just read the
data instead.

  ID de section : 22
  Cette section contient des données de traçage de latence, du texte ASCII extrait du

SECTION DES CHAINES
.ft
ID de section : 15
Toutes les chaînes des métadonnées du fichier de traçage sont stockées dans une section de chaînes à l'intérieur du fichier. La section
contient une liste de chaînes ASCII terminées par un nul. Un ID de la chaîne est utilisé dans les métadonnées
du fichier, qui est le décalage de la chaîne réelle dans la section de chaînes. Les chaînes peuvent être stockées
dans plusieurs sections de chaînes dans le fichier.
