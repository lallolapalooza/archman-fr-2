NOM

trace-cmd.dat.v6 - format de fichier de trace-cmd version 6

SYNOPSIS

trace-cmd.dat ignorer

DESCRIPTION

L'utilitaire trace-cmd(1) produit un fichier "trace.dat". Le fichier peut également porter un autre nom si l'utilisateur spécifie un nom de sortie différent, mais il doit avoir un certain format binaire. Le fichier est utilisé par trace-cmd pour y enregistrer les traces du noyau et pouvoir en extraire la trace ultérieurement (voir trace-cmd-report(1)).

FORMAT INITIAL

Les trois premiers octets contiennent la valeur magique :
0x17 0x08  0x44
Les 7 octets suivants contiennent les caractères :
"tracing"
L'ensemble des caractères suivant contient une chaîne terminée par un octet nul
qui contient la version du fichier :
"6\0"
L'octet suivant contient les drapeaux de l'endianisme du fichier :
0 = little endian
1 = big endian
L'octet suivant contient le nombre d'octets par valeur "long" :
4 - valeurs long 32 bits
8 - valeurs long 64 bits
Note : Il s'agit de la taille des longs de l'espace utilisateur de la cible. Pas de
la taille de l'espace noyau.
[ Désormais, tous les nombres sont écrits selon l'endianisme défini dans le fichier. ]
Les 4 octets suivants sont un mot de 32 bits qui définit la taille de page de
l'hôte machine tracée.

FORMAT INFORMATIONS ENTETE

Directement après le format initial se trouvent des informations sur les
en-têtes de trace enregistrés depuis la machine cible.
Les 12 octets suivants contiennent la chaîne :
"header_page\0"
Les 8 octets suivants sont un mot de 64 bits contenant la taille des
informations d'en-tête de page stockées ensuite.
L'ensemble de données suivant est de la taille lue à partir des 8 octets précédents,
et contient les données récupérées depuis debugfs/tracing/events/header_page.
Note : La taille du second champ \fBcommit\fR contient la taille des longs du noyau
cible. Par exemple :
field: local_t commit;        offset:8;       \fBsize:8;\fR   signed:1;
montre que le noyau a des longs de 64 bits.
Les 13 octets suivants contiennent la chaîne :
"header_event\0"
Les 8 octets suivants sont un mot de 64 bits contenant la taille des
informations d'en-tête d'événement stockées ensuite.
L'ensemble de données suivant est de la taille lue à partir des 8 octets précédents
et contient les données récupérées depuis debugfs/tracing/events/header_event.
Ces données permettent à l'outil trace-cmd de savoir si le format de tampon annulaire
du noyau a subi des modifications.

FORMATS EVENEMENTS FTRACE

Directement après les informations d'en-tête viennent les informations sur les
événements spécifiques à Ftrace. Ce sont les événements utilisés par les plugins
Ftrace et qui ne sont pas activés par le traçage d'événements.
Les 4 octets suivants contiennent un mot de 32 bits du nombre de fichiers de format
d'événement Ftrace stockés dans le fichier.
Pour le nombre de fois défini par les 4 octets précédents, voici :
8 octets pour la taille du fichier de format d'événement Ftrace.
Le fichier de format d'événement Ftrace copié depuis la machine cible :
debugfs/tracing/events/ftrace/<event>/format

FORMATS EVENEMENTS

Directement après les formats Ftrace viennent les informations sur la
disposition des événements.
Les 4 octets suivants sont un mot de 32 bits contenant le nombre de
systèmes d'événements stockés dans le fichier. Ce sont les
répertoires dans debugfs/tracing/events, excluant le répertoire \fBftrace\fR.
Pour le nombre de fois défini par les 4 octets précédents, voici :
Une chaîne terminée par un octet nul contenant le nom du système.
4 octets contenant un mot de 32 bits et définissant le nombre
d'événements dans le système.
Pour le nombre de fois défini dans les 4 octets précédents, voici :
8 octets pour la taille du fichier de format d'événement.
Le fichier de format d'événement copié depuis la machine cible :
debugfs/tracing/events/<system>/<event>/format

INFORMATIONS KALLSYMS

Directement après les formats d'événements vient l'information de mappage
des adresses de fonctions vers les noms de fonctions.
Les 4 octets suivants sont un mot de 32 bits contenant la taille des
données contenant les mappages de fonctions.
L'ensemble de données suivant est de la taille définie par les 4 octets précédents
et contient les informations du fichier de la machine cible :
/proc/kallsyms

INFORMATIONS TRACE_PRINTK

Si un développeur a utilisé trace_printk() dans le noyau, il peut
stocker la chaîne de format en dehors du tampon annulaire.
Ces informations peuvent être trouvées dans :
debugfs/tracing/printk_formats
Les 4 octets suivants sont un mot de 32 bits contenant la taille des
données contenant les formats printk.
L'ensemble de données suivant est de la taille définie par les 4 octets précédents
et contient les informations de debugfs/tracing/printk_formats.

INFORMATIONS PROCESSUS

Directement après les formats trace_printk vient l'information de mappage
d'un PID vers un nom de processus.
Les 8 octets suivants contiennent un mot de 64 bits qui détient la taille des
données mappant le PID à un nom de processus.
L'ensemble de données suivant est de la taille définie par les 8 octets précédents
et contient les informations de debugfs/tracing/saved_cmdlines.

RESTE ENTETE TRACE-CMD

Directement après les informations de processus vient la dernière partie de
l'en-tête du fichier trace.dat.
Les 4 octets suivants sont un mot de 32 bits définissant le nombre de CPU qui
ont été découverts sur la machine cible (et pour lesquels il existe des données
de trace correspondantes).
Les 10 octets suivants sont l'une des chaînes suivantes :
"options  \0"
"latency  \0"
"flyrecord\0"
S'il s'agit de "options  \0", alors :
Les 2 octets suivants sont un mot de 16 bits définissant l'option actuelle.
Si la valeur est zéro, il n'y a plus d'options.
Sinon, les 4 octets suivants contiennent un mot de 32 bits définissant la
taille de l'option. Si le lecteur ne sait pas comment gérer l'option, il peut
simplement l'ignorer. Actuellement, aucune option n'est définie, mais ceci est là
pour étendre les données.
L'option suivante sera directement après l'option précédente, et
les options se terminent par un zéro dans le champ type d'option.
Les 10 octets suivants après les options sont l'une des chaînes suivantes :
"latency  \0"
"flyrecord\0"
qui suivraient de la même manière que si les options n'étaient pas présentes.

NAME

trace-cmd.dat

trace-cmd data file format

SYNOPSIS

The file created by trace-cmd(1) when running trace-cmd record.

DESCRIPTION

This file contains the data recorded by trace-cmd. The format of the file is composed of a header, followed by event data.

The header is divided into multiple sections. The beginning of the file is the trace-cmd header itself, describing the version and contents of the file.

INITIAL FORMAT

8 bytes: Magic number (trace-cmd-save)
4 bytes: Version of the header
4 bytes: Size of the header
8 bytes: Total size of the file
8 bytes: Offset into the file where the event formats start
8 bytes: Size of the event formats section
8 bytes: Offset into the file where the kallsyms information starts
8 bytes: Size of the kallsyms information section
8 bytes: Offset into the file where the trace_printk information starts
8 bytes: Size of the trace_printk information section
8 bytes: Offset into the file where the process information starts
8 bytes: Size of the process information section
8 bytes: Offset into the file where the rest of the header data is
8 bytes: Size of the rest of the header data
8 bytes: Offset into the file where the CPU data starts
8 bytes: Size of the CPU data section

HEADER INFO FORMAT

This section contains the event formats, kallsyms, trace_printk strings,
and process information.

FTRACE EVENT FORMATS

The event formats are what the kernel uses to know how to interpret the
trace data. The trace-cmd tool copies these directly from the trace
filesystem of the target.
The format is a null-terminated string. The string is the content of
debugfs/tracing/events/header_file.

EVENT FORMATS

This section contains the actual event data. The format depends on the
type of data saved. If the value is "latency \0", then the rest of the
file is simply ASCII text that was taken from the target's:
debugfs/tracing/trace

KALLSYMS INFORMATION

This section contains the kallsyms information from the target. It is
copied directly from the tracefs file
/sys/kernel/debug/kallsyms.
The format is the same as the kallsyms file on the target.

TRACE_PRINTK INFORMATION

This section contains the trace_printk strings from the target. It is
copied directly from the tracefs file
/sys/kernel/debug/tracing/trace_printk.
The format is the same as the trace_printk file on the target.

PROCESS INFORMATION

This section contains information about the processes running on the
target at the time of the trace. The format is a series of structures,
each describing a process.
The structure is as follows:
8 bytes: PID of the process
8 bytes: Parent PID of the process
Variable length: Name of the process (null-terminated string)

REST OF TRACE-CMD HEADER

This section contains miscellaneous information about the trace session.
The exact contents may vary depending on the version of trace-cmd.
If the value is "latency \0", then the rest of the file is
simply ASCII text that was taken from the target's:
debugfs/tracing/trace
If the value is "flyrecord\0", the following is present:
For the number of CPUs that were read earlier, the
following is present:
8 bytes that are a 64-bit word containing the offset into the file
that holds the data for the CPU.
8 bytes that are a 64-bit word containing the size of the CPU
data at that offset.

CPU DATA

The CPU data is located in the part of the file that is specified
in the end of the header. Padding is placed between the header and
the CPU data, placing the CPU data at a page aligned (target page) position
in the file.
This data is copied directly from the Ftrace ring buffer and is of the
same format as the ring buffer specified by the event header files
loaded in the header format file.
The trace-cmd tool will try to \fBmmap(2)\fR the data page by page with the
target's page size if possible. If it fails to mmap, it will just read the
data instead.
