NOM

trace-cmd-sqlhist - Utiliser le langage SQL pour créer/afficher la création d'histogrammes tracefs et d'événements synthétiques

SYNTAXE

trace-cmd sqlhist [OPTIONS] [COMMANDE-SELECT-SQL]

DESCRIPTION

trace-cmd sqlhist(1) prendra une instruction de type SQL pour créer des histogrammes tracefs et des événements synthétiques qui peuvent effectuer diverses actions pour différentes manipulations des données.

Le système de fichiers tracefs interagit avec l'infrastructure de traçage Linux qui possède divers événements dynamiques et statiques à travers le noyau. Chacun de ces événements peut avoir un « histogramme » attaché, où les champs de l'événement définiront les intervalles de l'histogramme.

Un événement synthétique est un moyen de relier deux événements distincts et d'utiliser les champs et les horodatages de ces événements pour créer un nouvel événement dynamique. Ce nouvel événement dynamique est appelé un événement synthétique. Les champs de chaque événement peuvent faire l'objet de calculs simples, où, par exemple, la différence entre un champ d'un événement et un champ de l'autre événement peut être calculée. Cela fonctionne également pour les horodatages des événements, où la différence temporelle entre les deux événements peut également être extraite et placée dans l'événement synthétique.

D'autres actions peuvent être effectuées à partir des champs des événements. Un instantané peut être pris du tampon circulaire du noyau lorsqu'une variable utilisée dans l'événement synthétique atteint un maximum, ou simplement lors de changements.

Les commandes pour créer des histogrammes et des événements synthétiques sont complexes et pas faciles à retenir. trace-cmd sqlhist est utilisé pour convertir la syntaxe SQL en commandes nécessaires pour créer l'histogramme ou l'événement synthétique.

La COMMANDE-SELECT-SQL est une chaîne SQL définie par tracefs_sqlhist(3).

Notez que cela doit être exécuté en tant que root (ou avec sudo) car l'interaction avec le répertoire tracefs nécessite des privilèges root, sauf si l'option -t est donnée avec une copie du répertoire tracefs et ses événements.

OPTIONS

-n nom

Le nom de l'événement synthétique à créer. Cet événement peut ensuite être utilisé comme tout autre événement, et activé via trace-cmd record(1).

-t répertoire-tracefs

Afin de tester ceci en tant qu'utilisateur non root, une copie du répertoire tracefs peut être utilisée, et passer ce répertoire avec cette option permettra au programme de fonctionner. Évidemment, -e ne fonctionnera pas en tant que non-root car il ne pourra pas exécuter. 
# mkdir /tmp/tracing
# cp -r /sys/kernel/tracing/events /tmp/tracing
# exit
$ trace-cmd sqlhist -t /tmp/tracing ...

-e

Non seulement afficher les commandes pour créer l'histogramme, mais aussi les exécuter. Cela nécessite des privilèges root.

-f fichier

Au lieu de lire les commandes SQL depuis la ligne de commande, les lire depuis fichier. Si fichier est -, alors lire depuis l'entrée standard.

-m var

Effectuer l'action donnée lorsque la variable var atteint un nouveau maximum. Ceci ne peut pas être utilisé avec -c. La var doit être définie dans la COMMANDE-SELECT-SQL.

-c var

Effectuer l'action donnée lorsque la variable var change de valeur. Ceci ne peut pas être utilisé avec -m. La var doit être définie dans la COMMANDE-SELECT-SQL.

-s

Effectuer un instantané au lieu d'appeler l'événement synthétique.

-T

Effectuer à la fois un instantané et tracer l'événement synthétique.

-S champs[,champs]

Sauvegarder les champs donnés. Les champs doivent être des champs de l'événement « fin » donné dans la COMMANDE-SELECT-SQL

-B instance

Pour les instructions simples qui ne produisent qu'un histogramme, l'instance donnée ici sera l'endroit où l'histogramme sera créé. Ceci est ignoré pour la création d'événements synthétiques complets, car les événements synthétiques ont un effet global sur toutes les instances de traçage, tandis que les histogrammes n'affectent qu'une seule instance.

EXEMPLES

Comme décrit ci-dessus, à des fins de test, faites une copie du répertoire d'événements :

   $ mkdir /tmp/tracing
   $ sudo cp -r /sys/kernel/tracing/events /tmp/tracing/
   $ sudo chmod -R 0644 /tmp/tracing/

Pour un exemple de sortie d'histogramme simple utilisant la copie du répertoire tracefs.

   $ trace-cmd sqlhist -t /tmp/tracing/ 'SELECT CAST(call_site as SYM-OFFSET), bytes_req, CAST(bytes_alloc AS _COUNTER_) FROM kmalloc'

   echo 'hist:keys=call_site.sym-offset,bytes_req:vals=bytes_alloc' > /sys/kernel/tracing/events/kmem/kmalloc/trigger

Voici les options expliquées pour l'exemple ci-dessus :

-n wakeup_lat

Nomme l'événement synthétique à utiliser wakeup_lat.

-e

Exécute les commandes qui sont affichées.

-T

Effectue à la fois une action de trace et une action de capture (échange le tampon dans le tampon statique snapshot).

-m lat

Déclenche les actions chaque fois que lat atteint une nouvelle valeur maximale.

Maintenant, une explication de l'instruction SQL :

 'SELECT end.next_comm AS comm, (end.TIMESTAMP_USECS - start.TIMESTAMP_USECS) AS lat FROM ' \
    'sched_waking AS start JOIN sched_switch AS end ON start.pid = end.next_pid WHERE end.next_prio < 100 && end.next_comm == "cyclictest"'

end.next_comm AS comm

Enregistre le champ sched_switch next_comm et le place dans le champ comm de l'événement synthétique wakeup_lat.

(end.TIMESTAMP_USECS - start.TIMESTAMP_USECS) AS lat

Prend la différence entre les horodatages de l'événement sched_switch et de l'événement sched_waking. Comme les horodatages sont généralement enregistrés en nanosecondes, TIMESTAMP donnerait l'horodatage complet en nanosecondes, mais ici, TIMESTAMP_USECS le tronquera en microsecondes. La valeur est enregistrée dans la variable lat, qui sera également enregistrée dans l'événement synthétique.

FROM sched_waking AS start JOIN sched_switch AS end ON start.pid = end.next_pid

Crée l'événement synthétique en joignant sched_waking à sched_switch, en faisant correspondre le champ pid de sched_waking avec le champ next_pid de sched_switch. Fait également de start un alias pour sched_waking et de end un alias pour sched_switch, puis utilise start et end comme substituts pour sched_waking et sched_switch respectivement dans le reste de l'instruction SQL.

WHERE end.next_prio < 100 && end.next_comm == "cyclictest"

Filtre la logique pour qu'elle ne s'exécute que si le champ next_prio de sched_waking est inférieur à 100. (Notez que dans le noyau, les priorités sont inversées, et les priorités temps réel sont représentées de 0 à 100, où 0 est la priorité la plus élevée). Trace également uniquement lorsque le champ next_comm (la tâche qui entre) de l'événement sched_switch a le nom "cyclictest".

Pour la commande trace-cmd(3) :

   trace-cmd start -e all -e wakeup_lat -R stacktrace

trace-cmd start

Active le traçage (n'enregistre pas dans un fichier).

-e all

Active tous les événements.

-e wakeup_lat -R stacktrace

fait en sorte que l'événement "wakeup_lat" (notre événement synthétique) active le déclencheur stacktrace, de sorte que pour chaque instance de l'événement "wakeup_lat", une trace de pile du noyau sera enregistrée dans le tampon circulaire.

Après avoir appelé cyclictest (un outil temps réel pour mesurer la latence de réveil), lisez le tampon de capture.

trace-cmd show -s

trace-cmd show lit le tampon circulaire du noyau, et l'option -s lira le tampon snapshot au lieu du tampon normal.
 <idle>-0       [002] d..4 23454.902256: wakeup_lat: next_comm=cyclictest lat=17
Nous voyons sur l'événement "wakeup_lat" qu'il s'est produit sur le CPU 2, avec une latence de réveil de 17 microsecondes.
