TRAFFIC_REPLAY(7) Commandes utilisateur TRAFFIC_REPLAY(7)

NOM

traffic_replay - Outil de génération de trafic Samba.

SYNOPSIS

traffic_replay [-F, --fixed-password <mot-de-passe-test>] [-T, --packets-per-second <nombre>] [-S, --scale-traffic <facteur-déechelle>] [-r, --replay-rate <facteur-déechelle>] [-D, --duration <secondes>] [--traffic-summary <fichier-sortie>] [-I, --instance-id <id>] [-K, --prefer-kerberos] [-B, --badpassword-frequency <fréquence>] [--dns-rate <taux>] [-t, --timing-data <fichier>] [--random-seed <graine>] [-U, --username utilisateur] [--password <mot-de-passe>] [-W --workgroup <domaine>] [--realm <domaine-kdc>] [-s, --config-file <fichier>] [-k, --kerberos <kerberos>] [--ipaddress <adresse>] [-P, --machine-pass] [--option <option>] [-d, --debuglevel <niveau-debug>] [--conversation-persistence <0-1>] [--latency-timeout <secondes>] [--stop-on-any-error] {fichier-résumé} {nom-hôte-dns}

traffic_replay [-G, --generate-users-only] [-F, --fixed-password <mot-de-passe-test>] [-n, --number-of-users <utilisateurs-totaux>] [--number-of-groups <groupes-totaux>] [--average-groups-per-user <nombre-moyen>] [--group-memberships <membres-totaux>] [--max-members <taille-groupe>] {nom-hôte-dns}

traffic_replay {-c|--clean-up} {nom-hôte-dns}

traffic_replay [-h, --help] [-V, --version]

DESCRIPTION

Cet outil fait partie de la suite samba(7).

Cet outil génère du trafic afin de mesurer les performances d'un DC Samba et de tester sa capacité à monter en charge avec l'augmentation de la taille du réseau. Il peut simuler plusieurs hôtes différents effectuant plusieurs types de requêtes à un DC.

Cet outil est conçu pour fonctionner contre un DC de test dédié (plutôt qu'un DC en direct gérant du trafic réseau réel).

Notez qu'un effet secondaire de l'exécution de cet outil est la création de comptes utilisateurs sur le DC, afin de tester diverses opérations Samba. La création de comptes pouvant prendre beaucoup de temps, ces utilisateurs resteront sur le DC par défaut. Pour supprimer ces comptes, utilisez l'option --clean-up.

OPTIONS

-h|--help

Affiche un résumé des options de la ligne de commande.

fichier-résumé

Fichier contenant le trafic réseau à rejouer. Il doit s'agir d'un modèle de trafic (généré par traffic_learner). Sur la base de ce fichier, cet outil générera des 'conversations' représentant l'activité Samba entre un hôte réseau et le DC.

nom-hôte-dns

Le nom d'hôte DNS complet du DC testé. L'activité Samba du fichier-résumé sera répliquée et dirigée vers ce DC. Il est recommandé d'utiliser un DC dédié pour les tests et de ne pas essayer d'exécuter cet outil contre un DC qui traite du trafic réseau en direct.

-F|--fixed-password <mot-de-passe-test>

Des utilisateurs de test sont créés lorsque cet outil est exécuté, afin que l'activité Samba réelle, telle que l'autorisation des utilisateurs, puisse être mimée. Cette option spécifie le mot de passe qui sera utilisé pour tous les utilisateurs de test créés.

Notez que tous les utilisateurs créés par cet outil resteront sur le DC jusqu'à ce que vous utilisiez l'option --clean-up. Par conséquent, l'option fixed-password doit être la même à chaque exécution de l'outil, sinon les utilisateurs de test ne s'authentifieront pas correctement.

random-seed

Un nombre pour initialiser le générateur de nombres aléatoires. Lorsque le trafic est généré à partir d'un fichier modèle, utilisez cette option pour maintenir la cohérence du trafic entre plusieurs exécutions de test. Cela vous permet de comparer les performances de Samba entre différentes versions.

Options du modèle de trafic

Lorsque le fichier-résumé est un modèle de trafic (produit par traffic_learner), utilisez ces options pour modifier le trafic généré.

-D|--duration <secondes>

Spécifie la durée approximative en secondes pendant laquelle générer du trafic. La valeur par défaut est de 60 secondes.

-T|--packets-per-second <nombre>

Génère ce nombre de paquets par seconde, quel que soit le taux de trafic de l'échantillon sur lequel le modèle a été basé. Ne peut pas être utilisé avec -S.

-S|--scale-traffic <facteur>

Augmente le nombre de conversations de ce facteur, par rapport à l'échantillon de trafic original sur lequel le modèle était basé. Cette option n'affectera pas le taux d'envoi des paquets (qui est toujours basé sur le modèle de trafic), mais elle entraînera la relecture de plus de conversations. Elle ne peut pas être combinée avec -T, qui définit le taux de trafic d'une manière différente.

-r|--replay-rate <facteur>

Rejoue le trafic plus rapidement de ce facteur. Cette option n'affectera pas le nombre de paquets envoyés, mais les compressera en moins de conversations, ce qui peut réduire l'utilisation des ressources.

--traffic-summary <fichier-sortie>

Au lieu de rejouer un modèle de trafic, cette option génère un fichier de résumé de trafic basé sur le trafic qui serait envoyé. L'utilisation d'un modèle de trafic vous permet d'ajuster le taux de paquets et le nombre de paquets envoyés. Cependant, l'utilisation d'un modèle de trafic introduit un peu d'aléatoire dans la génération de trafic. Ainsi, exécuter plusieurs fois la même commande traffic_replay en utilisant un fichier modèle peut entraîner des différences dans le trafic réel envoyé. Cependant, exécuter plusieurs fois la même commande traffic_replay avec un fichier de résumé de trafic entraînera toujours l'envoi du même trafic.

Pour effectuer des mesures de performance sur plusieurs séries de tests, il est recommandé d'utiliser cette option et de rejouer le trafic à partir d'un fichier de résumé de trafic, ou d'utiliser l'option --random-seed.

--stop-on-any-error

Toute erreur client provoque l'arrêt complet de l'exécution.

--conversation-persistence <0-1>

La terminaison de conversation (telle que décidée par le modèle) est réinterprétée comme une longue pause avec cette probabilité.

--latency-timeout <secondes>

Attend pendant ce temps à la fin de l'exécution les paquets de réponse en attente. Le nombre de conversations qui ne sont pas terminées à la fin du délai d'attente est une métrique d'échec.

--generate-users-only

Ajoute des utilisateurs/groupes supplémentaires sur le DC pour augmenter la taille de la base de données. Par défaut, cet outil crée automatiquement des utilisateurs de test qui correspondent aux conversations de trafic générées. Cette option permet de créer des utilisateurs supplémentaires en plus de ceux-ci. Notez que ces utilisateurs supplémentaires ne seront peut-être pas réellement utilisés pour la génération de trafic - la génération de trafic est toujours basée sur le nombre de conversations du fichier modèle/résumé.

La génération d'un grand nombre d'utilisateurs peut prendre du temps, cette option permet donc de le faire une seule fois.

Notez que les utilisateurs créés resteront sur le DC jusqu'à ce que l'outil soit exécuté avec l'option --clean-up. Cela signifie qu'il est préférable d'attribuer les appartenances aux groupes une seule fois, c'est-à-dire d'exécuter --clean-up avant d'attribuer une allocation différente d'appartenances aux groupes.

-n|--number-of-users <total-utilisateurs>

Spécifie le nombre total d'utilisateurs de test à créer (à l'exclusion de tout compte machine requis pour le trafic). Notez que ces utilisateurs supplémentaires peuplent simplement la base de données du DC - le trafic utilisateur réel généré est toujours basé sur le fichier-résumé.

--number-of-groups <groupes-totaux>

Crée le nombre spécifié de groupes pour attribuer les utilisateurs de test. Notez que les utilisateurs ne sont pas automatiquement attribués aux groupes - utilisez --average-groups-per-user ou --group-memberships pour ce faire.

--average-groups-per-user <groupes-moyens>

Attribue aléatoirement les utilisateurs de test aux groupes de test créés. Les appartenances aux groupes sont distribuées de manière à ce que le nombre moyen global de groupes dont un utilisateur est membre corresponde à ce nombre. Certains utilisateurs appartiendront à plus de groupes et d'autres à moins de groupes. Cette option est incompatible avec l'option --group-membership.

--group-memberships <membres-totaux>

Attribue aléatoirement les utilisateurs de test aux groupes de test créés. Les appartenances aux groupes sont distribuées de manière à ce que le nombre total de groupes dont un utilisateur est membre, sur tous les utilisateurs, corresponde à ce nombre. Par exemple, avec 100 utilisateurs
et 10 groupes, --group-memberships=300 affecterait un utilisateur à 3 groupes en moyenne. Certains utilisateurs appartiendront à plus de groupes et d'autres à moins de groupes, mais le total de tous les attributs liés aux membres serait de 300. Cette option est incompatible avec l'option --average-groups-per-user.

--max-members <taille du groupe>

Limite la taille du plus grand groupe à cette taille, même si les autres options de groupe indiquent le contraire.

--clean-up

Nettoie tous les utilisateurs et groupes qui ont été créés en exécutant précédemment cet outil. Il est recommandé de toujours nettoyer après avoir exécuté l'outil.

-I|--instance-id <id>

Utilisez cette option pour exécuter plusieurs instances de l'outil sur le même contrôleur de domaine en même temps. Cela ajoute un préfixe aux utilisateurs de test générés pour les séparer sur le contrôleur de domaine.

-K|--prefer-kerberos

Utilise Kerberos pour authentifier les utilisateurs de test.

-B|--badpassword-frequency <fréquence>

Utilisez cette option pour simuler des utilisateurs essayant de s'authentifier avec un mot de passe incorrect.

--dns-rate <taux>

Augmente la fréquence à laquelle les paquets DNS sont envoyés.

-t|--timing-data <fichier>

Ceci écrit des données de synchronisation supplémentaires dans le fichier spécifié. Ceci est principalement utilisé pour les options de rapport, telles que la génération de graphiques.

Options communes Samba

-d|--debuglevel=niveau

niveau est un entier de 0 à 10. La valeur par défaut si ce paramètre n'est pas spécifié est 1 pour les applications clientes.

Plus cette valeur est élevée, plus le détail sera consigné dans les fichiers journaux sur les activités du serveur. Au niveau 0, seules les erreurs critiques et les avertissements sérieux seront enregistrés. Le niveau 1 est un niveau raisonnable pour un fonctionnement quotidien - il génère une petite quantité d'informations sur les opérations effectuées.

Les niveaux supérieurs à 1 généreront des quantités considérables de données de journalisation et ne devraient être utilisés que lors de l'investigation d'un problème. Les niveaux supérieurs à 3 sont conçus pour être utilisés uniquement par les développeurs et génèrent d'énormes quantités de données de journalisation, dont la plupart sont extrêmement cryptiques.

Notez que la spécification de ce paramètre ici remplacera le paramètre niveau de journal dans le fichier /etc/samba/smb.conf.

--debug-stdout

Ceci redirigera la sortie de débogage vers STDOUT. Par défaut, tous les clients enregistrent sur STDERR.

--configfile=<fichier de configuration>

Le fichier spécifié contient les détails de configuration requis par le client. Les informations contenues dans ce fichier peuvent être générales pour le client et le serveur ou fournir uniquement des options spécifiques au client telles que client smb encrypt. Voir /etc/samba/smb.conf pour plus d'informations. Le nom du fichier de configuration par défaut est déterminé lors de la compilation.

--option=<nom>=<valeur>

Définit l'option smb.conf(5) nommée « <nom> » à la valeur « <valeur> » depuis la ligne de commande. Ceci remplace les valeurs par défaut intégrées et les options lues dans le fichier de configuration. Si un nom ou une valeur contient un espace, encadrez tout --option=nom=valeur entre guillemets.

--realm=REALM

Définit le nom du royaume

-V|--version

Affiche le numéro de version du programme.

Options d'identification

--simple-bind-dn=DN

DN à utiliser pour une liaison simple

--password=MOTDEPASSE

Mot de passe

-U NOMUTILISATEUR|--username=NOMUTILISATEUR

Nom d'utilisateur

-W GROUPEENTREPRISE|--workgroup=GROUPEENTREPRISE

Groupe d'entreprises

--use-kerberos=désiré|requis|désactivé

Ce paramètre détermine si les outils clients Samba tenteront de s'authentifier en utilisant Kerberos. Pour l'authentification Kerberos, vous devez utiliser des noms DNS au lieu d'adresses IP lors de la connexion à un service. Par défaut, les outils clients Samba essaieront d'utiliser le cache d'identification Kerberos par défaut (ccache). Si le ccache n'existe pas ou si l'option -U|--user a été spécifiée, les clients demanderont d'entrer un mot de passe et obtiendront un ticket Kerberos (kinit) pour vous. Si vous souhaitez utiliser un cache d'identification Kerberos alternatif, utilisez l'option --use-krb5-ccache.

Notez que la spécification de ce paramètre ici remplacera le paramètre client use kerberos dans le fichier /etc/samba/smb.conf.

--ipaddress=ADRESSEIP

Adresse IP du serveur

-P|--machine-pass

Utilise le mot de passe du compte machine stocké.

OPÉRATIONS

Génération d'un fichier traffic-summary

Pour utiliser cet outil, vous avez besoin soit d'un fichier traffic-summary, soit d'un fichier traffic-model. Pour générer l'un de ces fichiers, vous aurez besoin d'une capture de trafic de l'activité Samba réelle sur votre réseau.

Utilisez Wireshark pour effectuer une capture de trafic sur votre réseau du trafic que vous souhaitez générer. Par exemple, si vous souhaitez simuler de nombreux utilisateurs se connectant, effectuez une capture à 8h30 lorsque les utilisateurs se connectent.

Ensuite, vous devez convertir votre capture de trafic en un fichier traffic-summary, en utilisant traffic_summary.pl. Fondamentalement, cela supprime toute information sensible de la capture et résume quel type de paquet a été envoyé et quand.

Consultez l'aide de traffic_summary.pl --help pour plus de détails, mais la commande de base ressemblera à ceci :

tshark -r capture.pcapng -T pdml | traffic_summary.pl > traffic-summary.txt

Rejeu d'un fichier traffic-summary

Une fois que vous avez un fichier traffic-summary, vous pouvez l'utiliser pour générer du trafic. L'outil traffic_replay reçoit le fichier traffic-summary en argument, ainsi que le nom d'hôte DNS complet du contrôleur de domaine testé. Vous devez également fournir des informations d'identification utilisateur, et éventuellement le royaume et le groupe de travail Samba (bien que le royaume et le groupe de travail puissent être déterminés automatiquement, par exemple à partir du fichier /etc/smb.conf, si l'un est présent). Par exemple :

traffic_replay traffic-summary.txt mon-dc.samdom.example.com -UAdmin%motdepasse -W samdom --realm=samdom.example.com --fixed-password=blahblah123!

Ceci régénère simplement l'activité Samba observée dans le résumé de trafic. Le trafic est regroupé en « conversations » entre un hôte et le contrôleur de domaine. Un utilisateur et un compte machine sont créés sur le contrôleur de domaine pour chaque conversation, afin de permettre la connexion et d'autres opérations de réussir. Le script génère les mêmes types de paquets que ceux observés dans le résumé.

La création d'utilisateurs peut être un processus très long, surtout s'il y a beaucoup de conversations générées. Pour gagner du temps, les utilisateurs de test restent sur le contrôleur de domaine par défaut. Vous devrez exécuter l'option --clean-up pour les supprimer, une fois que vous avez fini de générer du trafic. Comme les mêmes utilisateurs de test sont utilisés lors de plusieurs exécutions de l'outil, un mot de passe cohérent pour ces utilisateurs doit être utilisé - ceci est spécifié par l'option --fixed-password.

L'avantage de cet outil par rapport à l'utilisation de tcprelay est que le trafic généré est indépendant de tout réseau spécifique. Aucune configuration n'est nécessaire au préalable sur le contrôleur de domaine de test. Le trafic ne contient plus de détails sensibles, de sorte que le résumé de trafic pourrait être potentiellement partagé avec d'autres développeurs Samba.

Cependant, le rejeu direct d'un traffic-summary est quelque peu limité dans ce que vous pouvez réellement faire. Une approche plus flexible consiste à générer le trafic à l'aide d'un fichier modèle.

Génération d'un fichier traffic-model

Pour créer un fichier traffic-model, passez simplement le fichier traffic-summary au script traffic_learner. Par exemple :

traffic_learner traffic-summary.txt -o traffic-model.txt

Ceci génère un modèle de l'activité Samba sur votre réseau. Ce fichier modèle peut maintenant être utilisé pour générer du trafic.

Rejeu du fichier traffic-model

La génération de paquets à l'aide d'un fichier traffic-model utilise la même commande qu'un fichier traffic-summary, par exemple :

traffic_replay traffic-model.txt mon-dc.samdom.example.com -UAdmin%motdepasse

Par défaut, cela générera 60 secondes de trafic basées sur le modèle. Vous pouvez spécifier une durée plus longue en utilisant le paramètre --duration.

Le trafic généré est une approximation de ce qui a été observé dans la capture réseau. La génération de trafic implique un certain aléatoire, de sorte que l'exécution de la même commande plusieurs fois peut entraîner la génération d'un trafic légèrement différent (bien que vous puissiez l'éviter en spécifiant l'option --random-seed).

En plus de modifier la durée d'exécution du modèle, vous pouvez également modifier le nombre de conversations générées et la vitesse à laquelle le trafic est rejoué. Pour doubler approximativement le nombre de conversations rejouées, utilisez --scale-traffic=2 ou pour le réduire approximativement de moitié, utilisez --scale-traffic=0.5. Pour doubler approximativement la vitesse à laquelle les conversations sont rejouées, utilisez --replay-rate=2, ou pour la réduire de moitié, utilisez --replay-rate=0.5

Par exemple, pour générer environ 10 fois la quantité de trafic observée sur une période de deux minutes (basée sur la capture réseau), utilisez :

traffic_replay traffic-model.txt mon-dc.samdom.example.com -UAdmin%motdepasse --fixed-password=blahblah123! --scale-traffic=10 --duration=120

Mise à l'échelle du nombre d'utilisateurs

Les performances d'un contrôleur de domaine Samba exécutant un petit sous-ensemble d'utilisateurs de test seront différentes de celles d'un contrôleur de domaine Samba entièrement peuplé fonctionnant sur un réseau. À mesure que le nombre d'utilisateurs augmente, la taille de la base de données augmente, et une base de données très volumineuse sera moins performante qu'une base de données plus petite.

Pour augmenter la taille de la base de données Samba, cet outil peut également créer des utilisateurs et des groupes supplémentaires. Ces utilisateurs supplémentaires sont essentiellement des « bourrages » pour la base de données. Ils ne seront pas réellement utilisés pour générer du trafic, mais ils peuvent ralentir l'authentification des utilisateurs de test.

Par exemple, pour peupler la base de données avec 5000 utilisateurs supplémentaires (notez que cela prendra un certain temps), utilisez la commande :

traffic_replay mon-dc.samdom.example.com -UAdmin%motdepasse --generate-users-only --fixed-password=blahblah123! --number-of-users=5000

Vous pouvez également créer des groupes et affecter des utilisateurs à des groupes. Les utilisateurs peuvent être affectés aléatoirement aux groupes - cela inclut tous les utilisateurs supplémentaires créés ainsi que les utilisateurs qui correspondent aux conversations. Utilisez soit --average-groups-per-user, soit --group-memberships pour spécifier combien d'appartenances à des groupes doivent être attribuées aux utilisateurs de test.

ers.

Par exemple, pour affecter les utilisateurs des conversations rejouées en 10 groupes en moyenne, utilisez une commande comme celle-ci :

traffic_replay traffic-model.txt my-dc.samdom.example.com -UAdmin%password --fixed-password=blahblah123! --generate-users-only --number-of-groups=25 --average-groups-per-user=10

Les utilisateurs créés par le test auront des noms comme STGU-0-xyz. Les groupes générés auront des noms comme STGG-0-xyz.
