DESCRIPTION

Le Linux Trace Toolkit: next generation (LTTng) est un ensemble de paquets logiciels open source utilisé pour le traçage corrélé du noyau Linux, des applications et des bibliothèques utilisateur.

LTTng-UST est le composant de traçage de l'espace utilisateur du projet LTTng. C'est un portage vers l'espace utilisateur des capacités de traçage à faible surcharge du traçeur du noyau Linux LTTng. La bibliothèque liblttng-ust est utilisée pour tracer les applications et bibliothèques utilisateur.


Note

Cette page man concerne la bibliothèque liblttng-ust. Le projet LTTng-UST fournit également des paquets Java et Python pour tracer les applications écrites dans ces langages. Comment instrumenter et tracer les applications Java et Python est documenté dans la documentation en ligne de LTTng : http://lttng.org/docs/.

Il y a trois façons d'utiliser liblttng-ust :

•Utiliser l'API lttng_ust_tracef(3), qui est similaire à printf(3).
•Utiliser l'API lttng_ust_tracelog(3), qui est lttng_ust_tracef(3) avec un paramètre de niveau de journalisation.
•Définir vos propres points de trace. Voir la section Création d'un fournisseur de points de trace ci-dessous.

Compatibilité avec les API précédentes

Depuis LTTng-UST 2.13, la définition LTTNG_UST_COMPAT_API_VERSION contrôle quelles API LTTng-UST sont disponibles (compilées) :

La création d'un fournisseur de points de trace est la première étape de l'utilisation de liblttng-ust. Les étapes suivantes sont :

•Instrumenter votre application avec des appels à lttng_ust_tracepoint()
•Compiler votre application avec le support LTTng-UST,

  • un statiquement ou dynamiquement.

    Un fournisseur de points de trace est un objet compilé contenant les sondes d'événements correspondant à vos définitions personnalisées de points de trace. Un fournisseur de points de trace contient le code pour obtenir la taille d'un événement et pour le sérialiser, entre autres choses.

    Pour créer un fournisseur de points de trace, commencez avec le modèle d'en-tête de fournisseur de points de trace suivant :

    #undef LTTNG_UST_TRACEPOINT_PROVIDER

#undef LTTNG_UST_TRACEPOINT_INCLUDE
#define LTTNG_UST_TRACEPOINT_INCLUDE "./tp.h"
#if !defined(_TP_H) || \
    defined(LTTNG_UST_TRACEPOINT_HEADER_MULTI_READ)
#define _TP_H
#include <lttng/tracepoint.h>
/*
 * LTTNG_UST_TRACEPOINT_EVENT(), LTTNG_UST_TRACEPOINT_EVENT_CLASS(),
 * LTTNG_UST_TRACEPOINT_EVENT_INSTANCE(),
 * LTTNG_UST_TRACEPOINT_LOGLEVEL(), et `LTTNG_UST_TRACEPOINT_ENUM()`
 * sont utilisés ici.
 */
#endif /* _TP_H */
#include <lttng/tracepoint-event.h>

    Dans ce modèle, le fournisseur de points de trace est nommé my_provider (définition LTTNG_UST_TRACEPOINT_PROVIDER). Le fichier doit porter le nom de la définition LTTNG_UST_TRACEPOINT_INCLUDE (tp.h dans ce cas). Entre #include <lttng/tracepoint.h> et #endif vont les invocations des macros LTTNG_UST_TRACEPOINT_EVENT(), LTTNG_UST_TRACEPOINT_EVENT_CLASS(), LTTNG_UST_TRACEPOINT_EVENT_INSTANCE(), LTTNG_UST_TRACEPOINT_LOGLEVEL(), et LTTNG_UST_TRACEPOINT_ENUM().

LTTNG-UST TRACEPOINTS

October 2022

LTTNG_UST_TRACEPOINT_EVENT() usage

This macro defines a tracepoint. A tracepoint is identified by its provider name and its event name. It is associated with a list of arguments (inputs) and a list of fields (outputs).

Tracepoint arguments are function arguments that are passed to the tracepoint definition function. They are available to the tracer when the tracepoint is hit. Tracepoint arguments are not part of the trace, they are used for filtering and for generating the tracepoint's output fields.

Tracepoint fields are the data which is actually written into the trace buffers. They are generated from the tracepoint arguments.

The LTTNG_UST_TRACEPOINT_EVENT() macro signature is:

LTTNG_UST_TRACEPOINT_EVENT(
    /* Tracepoint provider name */
    my_provider,
    /* Tracepoint/event name */
    my_tracepoint,
    /* List of tracepoint arguments (input) */
    LTTNG_UST_TP_ARGS(
        ...
    ),
    /* List of fields of eventual event (output) */
    LTTNG_UST_TP_FIELDS(
        ...
    )
)

LTTNG_UST_TP_ARGS() defines the input arguments of the tracepoint. Each argument is defined with its type and name:

LTTNG_UST_TP_ARG(type, name)

LTTNG_UST_TP_FIELDS() defines the output fields of the tracepoint. Fields can be of any type that C/C++ supports, as well as enumeration fields (see the LTTNG_UST_TRACEPOINT_ENUM() usage section).

A field is defined using the following macros:

LTTNG_UST_TP_FIELD_VALUE
LTTNG_UST_TP_FIELD_VALUE(type, name, value)
Defines a field named name of type type, whose value is given by value. The value is generally an argument defined in the LTTNG_UST_TP_ARGS() list.
LTTNG_UST_TP_FIELD_VALUE_NEXT
LTTNG_UST_TP_FIELD_VALUE_NEXT(type, name)
Same as LTTNG_UST_TP_FIELD_VALUE(), but the value is implicitly the next argument available in the tracepoint definition function. This is useful when the tracepoint argument list and fields list are identical.
LTTNG_UST_TP_FIELD_ENUM
LTTNG_UST_TP_FIELD_ENUM(type, name, enum_name, value)
Defines an enumeration field named name of type enum_name, whose value is given by value. type must be the underlying integer type of the enumeration enum_name.
LTTNG_UST_TP_FIELD_ENUM_NEXT
LTTNG_UST_TP_FIELD_ENUM_NEXT(type, name, enum_name)
Same as LTTNG_UST_TP_FIELD_ENUM(), but the value is implicitly the next argument available in the tracepoint definition function.

The value expression is evaluated only if the tracepoint is enabled. This means that you can safely use tracepoint arguments that might not be available in all cases (e.g. when filtering).

The tracepoint provider name and tracepoint name are used to uniquely identify a tracepoint. The provider name is typically the name of the library that defines the tracepoint.

The lttng-gen-event(1) utility generates C code from tracepoint definitions. It requires the trace definitions to be put in a header file (e.g. my_provider.h).

This header file must be included in any C/C++ source file that uses the defined tracepoints.

See the EXAMPLE section below for a complete example.

LTTNG_UST_TRACEPOINT_PROBE_FIELD() usage

The LTTNG_UST_TRACEPOINT_PROBE_FIELD() macro is similar to LTTNG_UST_TP_FIELD_VALUE(), except that the field is not committed to the sub-buffers. The field is directly passed to the event filters. This is useful for making some event context available to the event filters without having to commit the data to sub-buffers. The main difference between a field defined with LTTNG_UST_TP_FIELD_VALUE() and one defined with LTTNG_UST_TRACEPOINT_PROBE_FIELD() is that the latter is not part of the trace data. Both macros can take the same arguments, and are otherwise identical. Their primary purpose is to make some of the event context available to the event filters without having to commit the data to sub-buffers. See lttng-enable-event(1) to learn more about dynamic event filtering.

See the EXAMPLE section below for a complete example.

LTTNG_UST_TRACEPOINT_ENUM() usage

An enumeration field is a list of mappings between an integers, or a range of integers, and strings (sometimes called labels or enumerators). Enumeration fields can be used to have a more compact trace when the possible values for a field are limited.

An enumeration field is defined with the LTTNG_UST_TRACEPOINT_ENUM() macro:

LTTNG_UST_TRACEPOINT_ENUM(
    /* Tracepoint provider name */
    my_provider,
    /* Enumeration name (unique in the whole tracepoint provider) */
    my_enum,
    /* Enumeration mappings */
    LTTNG_UST_TP_ENUM_VALUES(
        ...
    )
)

LTTNG_UST_TP_ENUM_VALUES() contains a list of enumeration mappings, NOT separated by commas. Two macros can be used in the LTTNG_UST_TP_ENUM_VALUES(): lttng_ust_field_enum_value() and lttng_ust_field_enum_range().

lttng_ust_field_enum_value() is a single value mapping:

lttng_ust_field_enum_value(label, value)

This macro maps the given label string to the value value.

lttng_ust_field_enum_range() is a range mapping:

lttng_ust_field_enum_range(label, start, end)

This macro maps the given label string to the range of integers from start to end, inclusively. Range mappings may overlap, but the behaviour is implementation-defined: each trace reader handles overlapping ranges as it wishes.

See the EXAMPLE section below for a complete example.

LTTNG_UST_TRACEPOINT_EVENT_CLASS() usage

A tracepoint class is a class of tracepoints sharing the same field types and names. A tracepoint instance is one instance of such a declared tracepoint class, with its own event name.

LTTng-UST creates one event serialization function per tracepoint class. Using LTTNG_UST_TRACEPOINT_EVENT() creates one tracepoint class per tracepoint definition, whereas using LTTNG_UST_TRACEPOINT_EVENT_CLASS() and LTTNG_UST_TRACEPOINT_EVENT_INSTANCE() creates one tracepoint class, and one or more tracepoint instances of this class. In other words, many tracepoints can reuse the same serialization code. Reusing the same code, when possible, can reduce cache pollution, thus improve performance.

The LTTNG_UST_TRACEPOINT_EVENT_CLASS() macro accepts the same parameters as the LTTNG_UST_TRACEPOINT_EVENT() macro, except that instead of an event name, its second parameter is the tracepoint class name:

#define LTTNG_UST_TRACEPOINT_PROVIDER my_provider
/* ... */
LTTNG_UST_TRACEPOINT_EVENT_CLASS(
    /* Tracepoint class provider name */
    my_provider,
    /* Tracepoint class name */
    my_tracepoint_class,
    /* List of tracepoint arguments (input) */
    LTTNG_UST_TP_ARGS(
        ...
    ),
    /* List of fields of eventual event (output) */
    LTTNG_UST_TP_FIELDS(
        ...
    )
)

Once the tracepoint class is defined, you can create as many tracepoint instances as needed:

#define LTTNG_UST_TRACEPOINT_PROVIDER natality
/* ... */
LTTNG_UST_TRACEPOINT_EVENT_INSTANCE(
    /* Name of the tracepoint class provider */
    my_provider,
    /* Tracepoint class name */
    my_tracepoint_class,
    /* Name of the local (instance) tracepoint provider */
    natality,
    /* Tracepoint/event name */
    my_tracepoint,
    /* List of tracepoint arguments (input) */
    LTTNG_UST_TP_ARGS(
        ...
    )
)

As you can see, the LTTNG_UST_TRACEPOINT_EVENT_INSTANCE() does not contain the LTTNG_UST_TP_FIELDS() macro, because they are defined at the LTTNG_UST_TRACEPOINT_EVENT_CLASS() level.

Note that the LTTNG_UST_TRACEPOINT_EVENT_INSTANCE() macro requires two provider names:

•The name of the tracepoint class provider (my_provider in the example above).

This is the same as the first argument of the LTTNG_UST_TRACEPOINT_EVENT_CLASS() expansion to refer to.

•The name of the local, or instance, provider (natality in the example above).

This is the provider name which becomes the prefix part of the name of the events which such a tracepoint creates.

The two provider names may be different if the tracepoint class and the tracepoint instance macros are in two different translation units.

LTTNG_UST_TRACEPOINT_LOGLEVEL() usage

Optionally, a log level can be assigned to a defined tracepoint. Assigning different levels of severity to tracepoints can be useful: when controlling tracing sessions, you can choose to only enable events falling into a specific log level range using the --loglevel and --loglevel-only options of the lttng-enable-event(1) command.

Log levels are assigned to tracepoints that are already defined using the LTTNG_UST_TRACEPOINT_LOGLEVEL() macro. Instrumenting your application

Once the tracepoint provider is created (see the Creating a tracepoint provider section above), you can instrument your application with the defined tracepoints thanks to the lttng_ust_tracepoint() macro:

#define lttng_ust_tracepoint(prov_name, t_name, ...)

With:

prov_name

Tracepoint provider name.

t_name

Tracepoint/event name.

...

Tracepoint arguments, if any.

Make sure to include the tracepoint provider header file anywhere you use lttng_ust_tracepoint() for this provider.


Note

Even though LTTng-UST supports lttng_ust_tracepoint() call site duplicates having the same provider and tracepoint names, it is recommended to use a provider/tracepoint name pair only once within the application source code to help map events back to their call sites when analyzing the trace.

Sometimes, arguments to the tracepoint are expensive to compute (take call stack, for example). To avoid the computation when the tracepoint is disabled, you can use the lttng_ust_tracepoint_enabled() and lttng_ust_do_tracepoint() macros:

#define lttng_ust_tracepoint_enabled(prov_name, t_name)
#define lttng_ust_do_tracepoint(prov_name, t_name, ...)

lttng_ust_tracepoint_enabled() returns a non-zero value if the tracepoint named t_name from the provider named prov_name is enabled at run time.

lttng_ust_do_tracepoint() is like lttng_ust_tracepoint(), except that it doesn’t check if the tracepoint is enabled. Using lttng_ust_tracepoint() with lttng_ust_tracepoint_enabled() is dangerous since lttng_ust_tracepoint() also contains the lttng_ust_tracepoint_enabled() check, thus a race condition is possible in this situation:

if (lttng_ust_tracepoint_enabled(my_provider, my_tracepoint)) {
    stuff = prepare_stuff();
}
lttng_ust_tracepoint(my_provider, my_tracepoint, stuff);

If the tracepoint is enabled after the condition, then stuff is not prepared: the emitted event will either contain wrong data, or the whole application could crash (segmentation fault, for example).


Note

Neither lttng_ust_tracepoint_enabled() nor lttng_ust_do_tracepoint() have a STAP_PROBEV() call, so if you need it, you should emit this call yourself.

Tracing C/C++ code with stack backtraces

You can also instrument your application with stack backtraces. The stack trace is captured by the kernel, hence it can have a performance impact. Use it wisely.

Stack backtraces are enabled using the lttng-enable-event(1) command with the --stack option.

You can define tracepoints with stack backtraces by using the LTTNG_UST_TRACEPOINT_WITH_STACK() macro:

LTTNG_UST_TRACEPOINT_WITH_STACK(
    /* Tracepoint provider name */
    my_provider,
    /* Tracepoint/event name */
    my_tracepoint,
    /* List of tracepoint arguments (input) */
    LTTNG_UST_TP_ARGS(
        ...
    ),
    /* List of fields of eventual event (output) */
    LTTNG_UST_TP_FIELDS(
        ...
    )
)

This macro is identical to LTTNG_UST_TRACEPOINT_EVENT(), except that it adds a stack backtrace to the event data.

You can also define tracepoint classes with stack backtraces:

LTTNG_UST_TRACEPOINT_EVENT_CLASS_WITH_STACK(
    /* Tracepoint class provider name */
    my_provider,
    /* Tracepoint class name */
    my_tracepoint_class,
    /* List of tracepoint arguments (input) */
    LTTNG_UST_TP_ARGS(
        ...
    ),
    /* List of fields of eventual event (output) */
    LTTNG_UST_TP_FIELDS(
        ...
    )
)

And then use the LTTNG_UST_TRACEPOINT_EVENT_INSTANCE_WITH_STACK() macro:

LTTNG_UST_TRACEPOINT_EVENT_INSTANCE_WITH_STACK(
    /* Name of the tracepoint class provider */
    my_provider,
    /* Tracepoint class name */
    my_tracepoint_class,
    /* Name of the local (instance) tracepoint provider */
    natality,
    /* Tracepoint/event name */
    my_tracepoint,
    /* List of tracepoint arguments (input) */
    LTTNG_UST_TP_ARGS(
        ...
    )
)

All the macros suffixed with _WITH_STACK automatically add a stack backtrace to the event data.

EXAMPLE

The following example demonstrates how to define and use tracepoints in a C application.

First, create a header file (e.g. my_provider.h) for your tracepoint provider:

#undef LTTNG_TRACEPOINT_PROVIDER
#define LTTNG_TRACEPOINT_PROVIDER my_provider

/* Tracepoint definition */
LTTNG_UST_TRACEPOINT_EVENT(my_provider, my_event,
    LTTNG_UST_TP_ARGS(
        int level,
        const char *message
    ),
    LTTNG_UST_TP_FIELDS(
        LTTNG_UST_TP_FIELD_VALUE(int, level, level),
        LTTNG_UST_TP_FIELD_VALUE(const char *, message, message)
    )
)

/* Tracepoint with enum */
LTTNG_UST_TRACEPOINT_ENUM(my_provider, my_enum,
    LTTNG_UST_TP_ENUM_VALUES(
        lttng_ust_field_enum_value(ready, 0)
        lttng_ust_field_enum_value(running, 1)
        lttng_ust_field_enum_value(stopped, 2)
    )
)

LTTNG_UST_TRACEPOINT_EVENT(my_provider, my_event_with_enum,
    LTTNG_UST_TP_ARGS(
        int state
    ),
    LTTNG_UST_TP_FIELDS(
        LTTNG_UST_TP_FIELD_ENUM(int, state, my_enum, state)
    )
)

/* Tracepoint with stack trace */
LTTNG_UST_TRACEPOINT_WITH_STACK(my_provider, my_event_with_stack,
    LTTNG_UST_TP_ARGS(
        int value
    ),
    LTTNG_UST_TP_FIELDS(
        LTTNG_UST_TP_FIELD_VALUE(int, value, value)
    )
)

/* Tracepoint class definition */
LTTNG_UST_TRACEPOINT_EVENT_CLASS(my_provider, my_class,
    LTTNG_UST_TP_ARGS(
        int data
    ),
    LTTNG_UST_TP_FIELDS(
        LTTNG_UST_TP_FIELD_VALUE(int, data, data)
    )
)

/* Tracepoint instance definition */
LTTNG_UST_TRACEPOINT_EVENT_INSTANCE(my_provider, my_class, my_provider, my_instance_event,
    LTTNG_UST_TP_ARGS(
        int data
    )
)

/* Tracepoint instance with stack trace definition */
LTTNG_UST_TRACEPOINT_EVENT_INSTANCE_WITH_STACK(my_provider, my_class, my_provider, my_stack_instance_event,
    LTTNG_UST_TP_ARGS(
        int data
    )
)

/* Assign log level to a tracepoint */
LTTNG_UST_TRACEPOINT_LOGLEVEL(my_provider, my_event, LTTNG_UST_TRACEPOINT_LOGLEVEL_INFO)

Then, in your application source code (e.g. main.c):

#include <stdio.h>
#include "my_provider.h"

int main(void)
{
    int i = 42;
    const char *msg = "Hello world";
    int state = 1;

    /* Emit tracepoints */
    lttng_ust_tracepoint(my_provider, my_event, i, msg);
    lttng_ust_tracepoint(my_provider, my_event_with_enum, state);
    lttng_ust_tracepoint(my_provider, my_event_with_stack, 123);
    lttng_ust_tracepoint(my_provider, my_instance_event, 456);
    lttng_ust_tracepoint(my_provider, my_stack_instance_event, 789);

    /* Check if tracepoint is enabled before potentially expensive computation */
    if (lttng_ust_tracepoint_enabled(my_provider, my_event)) {
        /* Computation is potentially expensive */
        char *expensive_data = compute_expensive_data();
        lttng_ust_do_tracepoint(my_provider, my_event, 0, expensive_data);
    }

    return 0;
}

Compile the application:

$ gcc main.c -o my_app -I.

Then, create a tracing session and start tracing:

$ lttng create my_session --output=./bin
$ lttng enable-event -u my_provider:my_event
$ lttng enable-event -u my_provider:my_event_with_enum
$ lttng enable-event -u my_provider:my_event_with_stack --stack
$ lttng enable-event -u my_provider:my_instance_event
$ lttng enable-event -u my_provider:my_stack_instance_event --stack
$ lttng start

Run your application:

$ ./my_app

Stop tracing and destroy the session:

$ lttng stop
$ lttng destroy

Finally, analyze the trace:

$ lttng view --trace

Suivi des constructeurs et destructeurs C/C++

Si l'une des conditions suivantes est vraie :

•Vous compilez votre application C++ avec GCC  ≤ 4.8.
•Vous compilez votre application C/C++ avec un compilateur C++ et définissez LTTNG_UST_ALLOCATE_COMPOUND_LITERAL_ON_HEAP.

Alors LTTng ne tracera pas :

•Les constructeurs et destructeurs C de l'application elle-même ou des archives liées statiquement.
•Certains constructeurs et destructeurs C++ de l'application elle-même ou des archives liées statiquement.

Dans ce cas, les constructeurs et destructeurs C++ exacts qui ne seront pas tracés dépendent de l'ordre d'initialisation au sein de chaque unité de traduction et entre toutes les unités de traduction lorsqu'elles sont liées ensemble.

Liaison statique du fournisseur de points de trace

Avec la méthode de liaison statique, les fournisseurs de points de trace compilés sont copiés dans l'application cible.

Définissez la macro LTTNG_UST_TRACEPOINT_DEFINE sous la définition de LTTNG_UST_TRACEPOINT_CREATE_PROBES dans la source du fournisseur de points de trace :

#define LTTNG_UST_TRACEPOINT_CREATE_PROBES
#define LTTNG_UST_TRACEPOINT_DEFINE
#include "tp.h"

Créez le fichier objet du fournisseur de points de trace :

$ cc -c -I. tp.c

Note

Bien qu'une application instrumentée avec des points de trace LTTng-UST puisse être compilée avec un compilateur C++, les sondes de points de trace doivent être compilées avec un compilateur C.

À ce stade, vous *pouvez* archiver ce fichier objet de fournisseur de points de trace, éventuellement avec d'autres fichiers objets de votre application ou avec d'autres fichiers objets de fournisseurs de points de trace, en tant que bibliothèque statique :

$ ar rc tp.a tp.o

L'utilisation d'une bibliothèque statique a l'avantage de centraliser les objets du fournisseur de points de trace afin qu'ils puissent être partagés entre plusieurs applications. Ainsi, lorsque le fournisseur de points de trace est modifié, les changements de code source n'ont pas à être appliqués à l'arborescence du code source de chaque application. Les applications doivent être relinkées après chaque modification, mais n'ont pas besoin d'être recompilées autrement (sauf si l'API du fournisseur de points de trace change).

Ensuite, liez votre application avec ce fichier objet (ou avec la bibliothèque statique qui le contient) et avec liblttng-ust et libdl (libc sur un système BSD) :

$ cc -o app tp.o app.o -llttng-ust -ldl

Chargement dynamique du fournisseur de points de trace

La deuxième approche pour empaqueter le fournisseur de points de trace est d'utiliser le chargeur dynamique : la bibliothèque et ses fonctions membres sont explicitement recherchées, chargées à l'exécution.

Dans ce scénario, le fournisseur de points de trace est compilé en tant qu'objet partagé.

Le processus de création de l'objet partagé du fournisseur de points de trace est à peu près le même que la *méthode de liaison statique*, sauf que :

•Puisque le fournisseur de points de trace ne fait pas partie de l'application, LTTNG_UST_TRACEPOINT_DEFINE doit être défini, pour chaque fournisseur de points de trace, dans un seul fichier source de l'*application*.
•LTTNG_UST_TRACEPOINT_PROBE_DYNAMIC_LINKAGE doit être défini à côté de LTTNG_UST_TRACEPOINT_DEFINE.

Concernant LTTNG_UST_TRACEPOINT_DEFINE et LTTNG_UST_TRACEPOINT_PROBE_DYNAMIC_LINKAGE, la pratique recommandée est d'utiliser un fichier source C séparé dans votre application pour les définir, puis d'inclure les fichiers d'en-tête du fournisseur de points de trace par la suite. Par exemple, comme tp-define.c :

#define LTTNG_UST_TRACEPOINT_DEFINE
#define LTTNG_UST_TRACEPOINT_PROBE_DYNAMIC_LINKAGE
#include "tp.h"

Le fichier objet du fournisseur de points de trace utilisé pour créer la bibliothèque partagée est construit comme avec la méthode de liaison statique, mais avec l'option -fpic :

$ cc -c -fpic -I. tp.c

Il est ensuite lié en tant que bibliothèque partagée comme suit :

$ cc -shared -Wl,--no-as-needed -o tp.so tp.o -llttng-ust

Cet objet partagé de fournisseur de points de trace n'est pas lié à l'application utilisateur : il doit être chargé manuellement. C'est pourquoi l'application est construite sans mention de ce fournisseur de points de trace, mais nécessite toujours libdl :

$ cc -o app app.o tp-define.o -ldl

Il existe deux façons de charger dynamiquement l'objet partagé du fournisseur de points de trace :

•Le charger manuellement depuis l'application en utilisant dlopen(3)
•Demander au chargeur dynamique de le charger avec la variable d'environnement LD_PRELOAD (voir ld.so(8))

Si l'application ne charge pas dynamiquement l'objet partagé du fournisseur de points de trace en utilisant l'une des méthodes ci-dessus, le suivi est désactivé pour cette application, et les événements ne sont pas listés dans la sortie de lttng-list(1).

Notez qu'il n'est pas sûr d'utiliser dlclose(3) sur un objet partagé de fournisseur de points de trace qui est activement utilisé pour le suivi, en raison d'un manque de comptage de références de LTTng-UST vers l'objet partagé.

Par exemple, lier statiquement un fournisseur de points de trace à un objet partagé qui doit être chargé dynamiquement par une application (un plugin, par exemple) n'est pas sûr : l'objet partagé, qui contient le fournisseur de points de trace, pourrait être fermé dynamiquement (dlclose(3)) à tout moment par l'application.

Pour instrumenter un objet partagé, soit :

•Lier statiquement le fournisseur de points de trace à l'application, soit
•Compiler le fournisseur de points de trace en tant qu'objet partagé (en suivant la procédure décrite dans cette section), et le précharger lorsque le suivi est nécessaire en utilisant la variable d'environnement LD_PRELOAD.

Utilisation de LTTng-UST avec les démons

Des précautions supplémentaires sont nécessaires lors de l'utilisation de liblttng-ust avec des applications de démon qui appellent fork(2), clone(2), ou rfork(2) de BSD sans un appel système suivant de la famille exec(3). La bibliothèque liblttng-ust-fork.so doit être préchargée avant de démarrer l'application avec la variable d'environnement LD_PRELOAD (voir ld.so(8)).

Pour utiliser liblttng-ust avec une application de démon qui ferme des descripteurs de fichiers qui n'ont pas été ouverts par elle, préchargez la bibliothèque liblttng-ust-fd.so avant de démarrer l'application. Les cas d'utilisation typiques incluent les démons fermant tous les descripteurs de fichiers après fork(2), et les applications boguées effectuant des « doubles fermetures ».

Détecter si LTTng-UST est chargé

Pour détecter si liblttng-ust est chargé depuis une application :

1.Définissez le symbole faible lttng_ust_loaded globalement : 
int lttng_ust_loaded __attribute__((weak));

Ce symbole faible est défini par le constructeur de liblttng-ust.

2.Testez lttng_ust_loaded si nécessaire : 
/* ... */
if (lttng_ust_loaded) {
    /* LTTng-UST est chargé */
} else {
    /* LTTng-UST n'est PAS chargé */
}
/* ... */

$ cc -c -I. tp.c

$ cc -o app tp.o app.o -llttng-ust -ldl

En utilisant l'outil lttng(1), créez une session de traçage LTTng, activez tous les événements de ce fournisseur de points de trace, et démarrez le traçage :

$ lttng create my-session
$ lttng enable-event --userspace 'my_provider:*'
$ lttng start

$ lttng enable-event --userspace my_provider:big_event
$ lttng enable-event --userspace my_provider:event_instance2

Exécutez l'application :

$ ./app some arguments

Arrêtez la session de traçage actuelle et inspectez les événements enregistrés :

$ lttng stop
$ lttng view

#include <stdio.h>

    100, -35, 1, 23, 14, -6, 28, 1001, -3000,
};

{
    FILE *stream;
    struct app_struct app_struct;
    lttng_ust_tracepoint(my_provider, simple_event, argc, argv[0]);
    stream = fopen("/tmp/app.txt", "w");
    if (!stream) {
        fprintf(stderr,
                "Error: Cannot open /tmp/app.txt for writing\n");
        return EXIT_FAILURE;
    }
    if (fprintf(stream, "0123456789") != 10) {
        fclose(stream);
        fprintf(stderr, "Error: Cannot write to /tmp/app.txt\n");
        return EXIT_FAILURE;
    }
    lttng_ust_tracepoint(my_provider, big_event, 35,
                         "hello tracepoint", stream, -3.14,
                         array_of_ints);
    fclose(stream);
    app_struct.b = argc;
    app_struct.c = "[the string]";
    lttng_ust_tracepoint(my_provider, event_instance1, 23,

VARIABLES D'ENVIRONNEMENT

LTTNG_HOME

Répertoire personnel alternatif de l'utilisateur. Cette variable est utile lorsque l'utilisateur exécutant l'application instrumentée a un répertoire personnel non inscriptible. Ce chemin est l'emplacement des sockets Unix pour la communication avec le démon de session par utilisateur.

LTTNG_UST_ABORT_ON_CRITICAL

Si défini, avorter l'application instrumentée en cas de message d'erreur critique.

LTTNG_UST_ALLOW_BLOCKING

Si défini, autoriser l'application à retenter le traçage d'événements lorsqu'il n'y a plus d'espace pour l'enregistrement de l'événement dans le sous-buffer, bloquant ainsi effectivement l'application jusqu'à ce que de l'espace soit libéré ou que le délai d'attente configuré soit atteint.

Pour permettre à une application de se bloquer pendant le traçage, vous devez également spécifier un délai d'attente de blocage lorsque vous créez un canal avec l'option --blocking-timeout de la commande lttng-enable-channel(1).

Cette option peut être utile dans les charges de travail générant un débit de données de trace très important, où le blocage de l'application est un compromis acceptable pour éviter de rejeter les enregistrements d'événements.


Attention
Définir cette variable d'environnement peut affecter de manière significative les timings de l'application.

LTTNG_UST_APP_PATH

Chemin du répertoire où le démon de session LTTng est censé placer les fichiers suivants pour recevoir les requêtes de connexion des applications instrumentées :
•Le socket Unix d'enregistrement de l'application.
•Les fichiers de mémoire partagée "wait" pour réveiller les applications instrumentées qui attendent le démarrage d'un démon de session.
•Le fichier de port de l'agent.

Ce fichier contient le port TCP auquel les agents doivent se connecter pour activer le traçage LTTng.

Ce répertoire doit exister lorsque vous démarrez l'application pour que le traçage LTTng soit activé.

Lorsque LTTNG_UST_APP_PATH est défini, liblttng-ust :

•Considère uniquement ce chemin pour se connecter à un démon de session.
•Ne se connectera pas aux démons de session root et/ou utilisateur comme d'habitude.

Voir la variable d'environnement correspondante LTTNG_UST_CTL_PATH de lttng-sessiond(8).

LTTNG_UST_CLOCK_PLUGIN

Chemin de l'objet partagé servant de plugin de remplacement d'horloge. Un exemple d'un tel plugin se trouve dans la documentation de LTTng-UST sous examples/clock-override https://github.com/lttng/lttng-ust/tree/stable-2.14/doc/examples/clock-override.

LTTNG_UST_DEBUG

Si défini, active la sortie de débogage et d'erreur de liblttng-ust.

LTTNG_UST_GETCPU_PLUGIN

Chemin vers l'objet partagé qui agit comme plugin de remplacement de getcpu(). Un exemple d'un tel plugin se trouve dans la documentation LTTng-UST sous examples/getcpu-override https://github.com/lttng/lttng-ust/tree/stable-2.14/doc/examples/getcpu-override.

LTTNG_UST_MAP_POPULATE_POLICY

Si défini, remplace la politique utilisée pour remplir les pages de mémoire partagée dans l'application.

Les valeurs possibles sont :

none (par défaut)

Ne pré-remplit aucune page : prend des défauts mineurs lors du premier accès pendant le traçage.

cpu_possible

Pré-remplit les pages pour tous les CPUs possibles dans le système, comme indiqué dans /sys/devices/system/cpu/possible.

LTTNG_UST_REGISTER_TIMEOUT

Temps d'attente pour la commande de démon de session registration done avant de procéder à l'exécution du programme principal (millisecondes).

La valeur 0 signifie ne pas attendre. La valeur -1 signifie attendre indéfiniment. Il est recommandé de définir cette variable d'environnement à 0 pour les applications ayant des contraintes de temps sur le temps de démarrage du processus.

Par défaut : 3000.

LTTNG_UST_WITHOUT_BADDR_STATEDUMP

Si défini, empêche liblttng-ust d'effectuer un vidage d'état de l'adresse de base (voir la section vidage d'état LTTng-UST ci-dessus).

LTTNG_UST_WITHOUT_PROCNAME_STATEDUMP

Si défini, empêche liblttng-ust d'effectuer un vidage d'état du nom de processus (voir la section vidage d'état LTTng-UST ci-dessus).
