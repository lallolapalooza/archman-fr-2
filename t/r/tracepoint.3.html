DESCRIPTION

Linux Trace Toolkit: next generation http://lttng.org/ est un ensemble de logiciels libres utilisé pour le traçage corrélé du noyau Linux, des applications et des bibliothèques utilisateur.

LTTng-UST est le composant de traçage de l'espace utilisateur du projet LTTng. C'est un portage en espace utilisateur des capacités de traçage à faible surcharge du traceur noyau LTTng. La bibliothèque liblttng-ust est utilisée pour tracer les applications et bibliothèques utilisateur.


Note

Cette page de manuel concerne la bibliothèque liblttng-ust. Le projet LTTng-UST fournit également des paquets Java et Python pour tracer des applications écrites dans ces langages. Comment instrumenter et tracer des applications Java et Python est documenté dans la documentation en ligne LTTng http://lttng.org/docs/.

Il existe trois façons d'utiliser liblttng-ust :

•Utiliser l'API lttng_ust_tracef(3), qui est similaire à printf(3).
•Utiliser l'API lttng_ust_tracelog(3), qui est comme lttng_ust_tracef(3) avec un paramètre de niveau de journalisation.
•Définir vos propres points de trace. Voir la section Création d'un fournisseur de points de trace ci-dessous.

Compatibilité avec les anciennes API

Depuis LTTng-UST 2.13, la définition LTTNG_UST_COMPAT_API_VERSION contrôle quelles API LTTng-UST sont disponibles (compilées) :

Non définie

Toutes les API sont disponibles.

N (0 ou entier positif)

L'API version N, ainsi que toutes les API existantes suivantes, sont disponibles. Les API précédentes ne sont pas disponibles (non compilées).

Le tableau suivant montre la correspondance entre les versions LTTng-UST (jusqu'à LTTng-UST 2.14.0) et les versions d'API disponibles :

Version LTTng-UST Versions d'API disponibles
2.0 à 2.12 0
2.13 0 et 1

Cette page de manuel ne documente QUE la version 1 de l'API.

Si vous souhaitez avoir accès à la version 0 de l'API (par exemple, les macros tracepoint(), ctf_integer() et TRACEPOINT_EVENT()), alors ne définissez pas LTTNG_UST_COMPAT_API_VERSION, ou définissez-la à 0 avant d'inclure tout en-tête LTTng-UST.

Création d'un fournisseur de points de trace

La création d'un fournisseur de points de trace est la première étape de l'utilisation de liblttng-ust. Les étapes suivantes sont :

•Instrumentation de votre application avec les appels lttng_ust_tracepoint()
•Compilation de votre application avec le support LTTng-UST, soit
r statiquement ou dynamiquement.

Un fournisseur de points de trace est un objet compilé contenant les sondes d'événements correspondant à vos définitions de points de trace personnalisées. Un fournisseur de points de trace contient le code pour obtenir la taille d'un événement et pour le sérialiser, entre autres choses.

Pour créer un fournisseur de points de trace, commencez par le modèle suivant de en-tête de fournisseur de points de trace :

#undef LTTNG_UST_TRACEPOINT_PROVIDER
#define LTTNG_UST_TRACEPOINT_PROVIDER mon_fournisseur
#undef LTTNG_UST_TRACEPOINT_INCLUDE
#define LTTNG_UST_TRACEPOINT_INCLUDE "./tp.h"
#if !defined(_TP_H) || \
    defined(LTTNG_UST_TRACEPOINT_HEADER_MULTI_READ)
#define _TP_H
#include <lttng/tracepoint.h>
/*
 * LTTNG_UST_TRACEPOINT_EVENT(), LTTNG_UST_TRACEPOINT_EVENT_CLASS(),
 * LTTNG_UST_TRACEPOINT_EVENT_INSTANCE(),
 * LTTNG_UST_TRACEPOINT_LOGLEVEL(), et `LTTNG_UST_TRACEPOINT_ENUM()`
 * sont utilisés ici.
 */
#endif /* _TP_H */
#include <lttng/tracepoint-event.h>

Dans ce modèle, le fournisseur de points de trace est nommé mon_fournisseur (définition LTTNG_UST_TRACEPOINT_PROVIDER). Le fichier doit porter le nom de la définition LTTNG_UST_TRACEPOINT_INCLUDE (tp.h dans ce cas). Entre #include <lttng/tracepoint.h> et #endif se trouvent les invocations des macros LTTNG_UST_TRACEPOINT_EVENT(), LTTNG_UST_TRACEPOINT_EVENT_CLASS(), LTTNG_UST_TRACEPOINT_EVENT_INSTANCE(), LTTNG_UST_TRACEPOINT_LOGLEVEL(), et LTTNG_UST_TRACEPOINT_ENUM().


Note

Vous pouvez éviter d'écrire le prologue et l'épilogue du modèle ci-dessus en utilisant l'outil lttng-gen-tp(1) fourni avec LTTng-UST.

Le fichier d'en-tête du fournisseur de points de trace doit être inclus dans un fichier source qui ressemble à ceci :

#define LTTNG_UST_TRACEPOINT_CREATE_PROBES
#include "tp.h"

Ensemble, ces deux fichiers (appelons-les tp.h et tp.c) forment les sources du fournisseur de points de trace, prêts à être compilés.

Vous pouvez créer plusieurs fournisseurs de points de trace à utiliser dans une même application, mais chacun doit avoir son propre fichier d'en-tête.

La section d'utilisation de LTTNG_UST_TRACEPOINT_EVENT() ci-dessous montre comment utiliser la macro LTTNG_UST_TRACEPOINT_EVENT() pour définir les points de trace réels dans le fichier d'en-tête du fournisseur de points de trace.

Voir la section EXEMPLE ci-dessous pour un exemple complet.

Utilisation de LTTNG_UST_TRACEPOINT_EVENT()

La macro LTTNG_UST_TRACEPOINT_EVENT() est utilisée dans un fichier d'en-tête de fournisseur modèle (voir la section Création d'un fournisseur de points de trace ci-dessus) pour définir les points de trace LTTng-UST.

Le modèle d'utilisation de LTTNG_UST_TRACEPOINT_EVENT() est le suivant :

LTTNG_UST_TRACEPOINT_EVENT(
    /* Nom du fournisseur de points de trace */
    mon_fournisseur,
    /* Nom du point de trace/événement */
    mon_point_de_trace,
    /* Liste des arguments du point de trace (entrée) */
    LTTNG_UST_TP_ARGS(
        ...
    ),
    /* Liste des champs de l'éventuel événement (sortie) */
    LTTNG_UST_TP_FIELDS(
        ...
    )
)

La macro LTTNG_UST_TP_ARGS() contient les arguments d'entrée du point de trace. Ces arguments peuvent être utilisés dans les expressions des arguments des champs de sortie définis dans LTTNG_UST_TP_FIELDS().

Le format des paramètres de LTTNG_UST_TP_ARGS() est : type C, puis nom de l'argument ; répétez autant que nécessaire, jusqu'à dix fois. Par exemple :

LTTNG_UST_TP_ARGS(
    int, mon_entier,
    const char *, ma_chaine,
    FILE *, mon_fichier,
    double, mon_flottant,
    struct ma_donnee *, ma_donnee
)

La macro LTTNG_UST_TP_FIELDS() contient les champs de sortie du point de trace, c'est-à-dire les données réelles qui peuvent être enregistrées dans la charge utile d'un événement émis par ce point de trace.

La macro LTTNG_UST_TP_FIELDS() contient une liste de macros lttng_ust_field_*() NON séparées par des virgules. Les macros disponibles sont documentées dans la section ci-dessous sur les macros de types de champs Disponibles lttng_ust_field_*().

LTTNG_UST_TRACEPOINT_ENUM() usage

Un champ d'énumération est une liste de correspondances entre des entiers, ou une plage d'entiers, et des chaînes de caractères (parfois appelées libellés ou énumérateurs). Les champs d'énumération peuvent être utilisés pour avoir une trace plus compacte lorsque les valeurs possibles d'un champ sont limitées.

Un champ d'énumération est défini avec la macro LTTNG_UST_TRACEPOINT_ENUM() :

LTTNG_UST_TRACEPOINT_ENUM(
    /* Nom du fournisseur de tracepoint */
    mon_fournisseur,
    /* Nom de l'énumération (unique dans tout le fournisseur de tracepoint) */
    mon_enum,
    /* Correspondances d'énumération */
    LTTNG_UST_TP_ENUM_VALUES(
        ...
    )
)

LTTNG_UST_TP_ENUM_VALUES() contient une liste de correspondances d'énumération, NON séparées par des virgules. Deux macros peuvent être utilisées dans LTTNG_UST_TP_ENUM_VALUES() : lttng_ust_field_enum_value() et lttng_ust_field_enum_range().

lttng_ust_field_enum_value() est une correspondance de valeur unique :

lttng_ust_field_enum_value(libelle, valeur)

Cette macro fait correspondre la chaîne de caractères libellé donnée à la valeur valeur.

lttng_ust_field_enum_range() est une correspondance de plage :

lttng_ust_field_enum_range(libelle, debut, fin)

Cette macro fait correspondre la chaîne de caractères libellé donnée à la plage d'entiers de debut à fin, inclusivement. Les correspondances de plage peuvent se chevaucher, mais le comportement est défini par l'implémentation : chaque lecteur de trace gère les plages chevauchantes comme il le souhaite.

Voir la section EXEMPLE ci-dessous pour un exemple complet.

LTTNG_UST_TRACEPOINT_EVENT_CLASS() usage

Une classe de tracepoint est une classe de tracepoints partageant les mêmes types et noms de champs. Une instance de tracepoint est une instance d'une telle classe de tracepoint déclarée, avec son propre nom d'événement.

LTTng-UST crée une fonction de sérialisation d'événement par classe de tracepoint. L'utilisation de LTTNG_UST_TRACEPOINT_EVENT() crée une classe de tracepoint par définition de tracepoint, tandis que l'utilisation de LTTNG_UST_TRACEPOINT_EVENT_CLASS() et LTTNG_UST_TRACEPOINT_EVENT_INSTANCE() crée une classe de tracepoint, et une ou plusieurs instances de tracepoint de cette classe. En d'autres termes, de nombreux tracepoints peuvent réutiliser le même code de sérialisation. La réutilisation du même code, lorsque cela est possible, peut réduire la pollution du cache, améliorant ainsi les performances.

La macro LTTNG_UST_TRACEPOINT_EVENT_CLASS() accepte les mêmes paramètres que la macro LTTNG_UST_TRACEPOINT_EVENT(), sauf qu'au lieu d'un nom d'événement, son deuxième paramètre est le nom de la classe de tracepoint :

#define LTTNG_UST_TRACEPOINT_PROVIDER mon_fournisseur
/* ... */
LTTNG_UST_TRACEPOINT_EVENT_CLASS(
    /* Nom du fournisseur de la classe de tracepoint */
    mon_fournisseur,
    /* Nom de la classe de tracepoint */
    ma_classe_tracepoint,
    /* Liste des arguments de tracepoint (entrée) */
    LTTNG_UST_TP_ARGS(
        ...
    ),
    /* Liste des champs de l'événement éventuel (sortie) */
    LTTNG_UST_TP_FIELDS(
        ...
    )
)

Une fois la classe de tracepoint définie, vous pouvez créer autant d'instances de tracepoint que nécessaire :

#define LTTNG_UST_TRACEPOINT_PROVIDER natalite
/* ... */
LTTNG_UST_TRACEPOINT_EVENT_INSTANCE(
    /* Nom du fournisseur de la classe de tracepoint */
    mon_fournisseur,
    /* Nom de la classe de tracepoint */
    ma_classe_tracepoint,
    /* Nom du fournisseur local (instance) */
    natalite,
    /* Nom du tracepoint/événement */
    mon_tracepoint,
    /* Liste des arguments de tracepoint (entrée) */
    LTTNG_UST_TP_ARGS(
        ...
    )
)

Comme vous pouvez le voir, LTTNG_UST_TRACEPOINT_EVENT_INSTANCE() ne contient pas la macro LTTNG_UST_TP_FIELDS(), car ils sont définis au niveau de LTTNG_UST_TRACEPOINT_EVENT_CLASS().

Notez que la macro LTTNG_UST_TRACEPOINT_EVENT_INSTANCE() requiert deux noms de fournisseur :

•Le nom du fournisseur de la classe de tracepoint (mon_fournisseur dans l'exemple ci-dessus).

C'est le même que le premier argument de l'expansion de LTTNG_UST_TRACEPOINT_EVENT_CLASS() auquel se référer.

•Le nom du fournisseur local, ou d'instance (natalite dans l'exemple ci-dessus).

C'est le nom du fournisseur qui devient la partie préfixe du nom des événements que ce tracepoint crée.

Les deux noms de fournisseur peuvent être différents si la classe de tracepoint et les macros d'instance de tracepoint se trouvent dans deux unités de traduction différentes.

Voir la section EXEMPLE ci-dessous pour un exemple complet.

LTTNG_UST_TRACEPOINT_LOGLEVEL() usage

Optionnellement, un niveau de journal peut être assigné à un tracepoint défini. Attribuer différents niveaux de sévérité aux tracepoints peut être utile : lors du contrôle des sessions de traçage, vous pouvez choisir de n'activer que les événements tombant dans une plage de niveaux de journal spécifiques en utilisant les options --loglevel et --loglevel-only de la commande lttng-enable-event(1).

Les niveaux de journal sont assignés aux tracepoints déjà définis en utilisant la macro LTTNG_UST_TRACEPOINT_LOGLEVEL(). Cette dernière doit être utilisée après avoir utilisé LTTNG_UST_TRACEPOINT_EVENT() ou LTTNG_UST_TRACEPOINT_EVENT_INSTANCE() pour un tracepoint donné. La macro LTTNG_UST_TRACEPOINT_LOGLEVEL() est utilisée comme suit :

LTTNG_UST_TRACEPOINT_LOGLEVEL(
    /* Nom du fournisseur de tracepoint */
    mon_fournisseur,
    /* Nom du tracepoint/événement */
    mon_tracepoint,
    /* Niveau de journal */
    LTTNG_UST_TRACEPOINT_LOGLEVEL_INFO
)

Les définitions de niveau de journal disponibles sont :

LTTNG_UST_TRACEPOINT_LOGLEVEL_EMERG

Système inutilisable.

LTTNG_UST_TRACEPOINT_LOGLEVEL_ALERT

Une action doit être entreprise immédiatement.

LTTNG_UST_TRACEPOINT_LOGLEVEL_CRIT

Conditions critiques.

LTTNG_UST_TRACEPOINT_LOGLEVEL_ERR

Conditions d'erreur.

LTTNG_UST_TRACEPOINT_LOGLEVEL_WARNING

Conditions d'avertissement.

LTTNG_UST_TRACEPOINT_LOGLEVEL_NOTICE

Condition normale, mais significative.

LTTNG_UST_TRACEPOINT_LOGLEVEL_INFO

Message informatif.

LTTNG_UST_TRACEPOINT_LOGLEVEL_DEBUG_SYSTEM

Informations de débogage avec une portée au niveau du système (ensemble de programmes).

LTTNG_UST_TRACEPOINT_LOGLEVEL_DEBUG_PROGRAM

Informations de débogage avec une portée au niveau du programme (ensemble de processus).

LTTNG_UST_TRACEPOINT_LOGLEVEL_DEBUG_PROCESS

Informations de débogage avec une portée au niveau du processus (ensemble de modules).

LTTNG_UST_TRACEPOINT_LOGLEVEL_DEBUG_MODULE

Instrumenter votre application

Une fois le fournisseur de tracepoint créé (voir la section Création d'un fournisseur de tracepoint ci-dessus), vous pouvez instrumenter votre application avec les tracepoints définis grâce à la macro lttng_ust_tracepoint() :

#define lttng_ust_tracepoint(nom_fournisseur, nom_t, ...)

Avec :

nom_fournisseur

Nom du fournisseur de tracepoint.

nom_t

Nom du tracepoint/événement.

...

Arguments du tracepoint, le cas échéant.

Assurez-vous d'inclure le fichier d'en-tête du fournisseur de tracepoint partout où vous utilisez lttng_ust_tracepoint() pour ce fournisseur.


Note

Même si LTTng-UST prend en charge les duplications du site d'appel lttng_ust_tracepoint() ayant les mêmes noms de fournisseur et de tracepoint, il est recommandé d'utiliser une paire fournisseur/tracepoint une seule fois dans le code source de l'application pour aider à mapper les événements à leurs sites d'appel lors de l'analyse de la trace.

Parfois, les arguments du tracepoint sont coûteux à calculer (par exemple, prendre la pile d'appels). Pour éviter le calcul lorsque le tracepoint est désactivé, vous pouvez utiliser les macros lttng_ust_tracepoint_enabled() et lttng_ust_do_tracepoint() :

#define lttng_ust_tracepoint_enabled(nom_fournisseur, nom_t)
#define lttng_ust_do_tracepoint(nom_fournisseur, nom_t, ...)

lttng_ust_tracepoint_enabled() renvoie une valeur non nulle si le tracepoint nommé nom_t du fournisseur nommé nom_fournisseur est activé à l'exécution.

lttng_ust_do_tracepoint() est comme lttng_ust_tracepoint(), sauf qu'il ne vérifie pas si le tracepoint est activé. L'utilisation de lttng_ust_tracepoint() avec lttng_ust_tracepoint_enabled() est dangereuse car lttng_ust_tracepoint() contient également la vérification lttng_ust_tracepoint_enabled(), donc une condition de concurrence est possible dans cette situation :

if (lttng_ust_tracepoint_enabled(mon_fournisseur, mon_tracepoint)) {
    truc = preparer_truc();
}
lttng_ust_tracepoint(mon_fournisseur, mon_tracepoint, truc);

Si le tracepoint est activé après la condition, alors truc n'est pas préparé : l'événement émis contiendra soit des données incorrectes, soit l'application entière pourrait planter (segmentation fault, par exemple).


Note

Ni lttng_ust_tracepoint_enabled() ni lttng_ust_do_tracepoint() n'ont d'appel STAP_PROBEV(), donc si vous en avez besoin, vous devriez l'émettre vous-même.

Traçage des constructeurs/destructeurs C/C++

Rastreo de constructores y destructores C/C++

Si se cumple alguna de las siguientes condiciones:

Se compila la aplicación C++ con GCC ≤ 4.8.

Se compila la aplicación C/C++ con un compilador C++ y se define LTTNG_UST_ALLOCATE_COMPOUND_LITERAL_ON_HEAP.

Entonces LTTng no rastreará:

Constructores y destructores C en la propia aplicación o en archivos estáticamente enlazados.

Algunos constructores y destructores C++ en la propia aplicación o en archivos estáticamente enlazados.

En este caso, qué constructores y destructores C++ exactos no se rastrearán dependerá del orden de inicialización dentro de cada unidad de traducción y entre todas las unidades de traducción cuando se enlacen juntas.

Enlace estático del proveedor de tracepoints

Con el método de enlace estático, los proveedores de tracepoints compilados se copian en la aplicación destino.

Defina LTTNG_UST_TRACEPOINT_DEFINE debajo de la definición de LTTNG_UST_TRACEPOINT_CREATE_PROBES en el código fuente del proveedor de tracepoints:

#define LTTNG_UST_TRACEPOINT_CREATE_PROBES
#define LTTNG_UST_TRACEPOINT_DEFINE
#include "tp.h"

Cree el archivo objeto del proveedor de tracepoints:

$ cc -c -I. tp.c

Nota

Aunque una aplicación instrumentada con tracepoints LTTng-UST puede compilarse con un compilador C++, las sondas de tracepoints deben compilarse con un compilador C.

En este punto, *puede* archivar este archivo objeto del proveedor de tracepoints, posiblemente con otros archivos objeto de su aplicación o con otros archivos objeto de proveedores de tracepoints, como una biblioteca estática:

$ ar rc tp.a tp.o

El uso de una biblioteca estática tiene la ventaja de centralizar los objetos del proveedor de tracepoints para que puedan ser compartidos entre múltiples aplicaciones. De esta manera, cuando se modifica el proveedor de tracepoints, los cambios en el código fuente no tienen que ser aplicados al árbol de código fuente de cada aplicación. Las aplicaciones necesitan ser relinkeadas después de cada cambio, pero no necesitan ser recompiladas de otra manera (a menos que la API del proveedor de tracepoints cambie).

Luego, enlace su aplicación con este archivo objeto (o con la biblioteca estática que lo contiene) y con liblttng-ust y libdl (libc en un sistema BSD):

$ cc -o app tp.o app.o -llttng-ust -ldl

Carga dinámica del proveedor de tracepoints

El segundo enfoque para empaquetar el proveedor de tracepoints es usar el cargador dinámico: la biblioteca y sus funciones miembro se buscan explícitamente, se cargan en tiempo de ejecución.

En este escenario, el proveedor de tracepoints se compila como un objeto compartido.

El proceso para crear el objeto compartido del proveedor de tracepoints es prácticamente el mismo que el *método de enlace estático*, excepto que:

Dado que el proveedor de tracepoints no forma parte de la aplicación, LTTNG_UST_TRACEPOINT_DEFINE debe definirse, para cada proveedor de tracepoints, en exactamente un archivo fuente de la *aplicación*.

LTTNG_UST_TRACEPOINT_PROBE_DYNAMIC_LINKAGE debe definirse junto a LTTNG_UST_TRACEPOINT_DEFINE.

En cuanto a LTTNG_UST_TRACEPOINT_DEFINE y LTTNG_UST_TRACEPOINT_PROBE_DYNAMIC_LINKAGE, la práctica recomendada es usar un archivo fuente C separado en su aplicación para definirlos, y luego incluir los archivos de encabezado del proveedor de tracepoints. Por ejemplo, como tp-define.c:

#define LTTNG_UST_TRACEPOINT_DEFINE
#define LTTNG_UST_TRACEPOINT_PROBE_DYNAMIC_LINKAGE
#include "tp.h"

El archivo objeto del proveedor de tracepoints utilizado para crear la biblioteca compartida se construye como en el método de enlace estático, pero con la opción -fpic:

$ cc -c -fpic -I. tp.c

Luego se enlaza como una biblioteca compartida de la siguiente manera:

$ cc -shared -Wl,--no-as-needed -o tp.so tp.o -llttng-ust

Este objeto compartido del proveedor de tracepoints no se enlaza con la aplicación del usuario: debe cargarse manualmente. Es por eso que la aplicación se construye sin mención de este proveedor de tracepoints, pero aún necesita libdl:

$ cc -o app app.o tp-define.o -ldl

Hay dos formas de cargar dinámicamente el objeto compartido del proveedor de tracepoints:

Cargarlo manualmente desde la aplicación usando dlopen(3).

Hacer que el cargador dinámico lo cargue con la variable de entorno LD_PRELOAD (ver ld.so(8)).

Si la aplicación no carga dinámicamente el objeto compartido del proveedor de tracepoints utilizando uno de los métodos anteriores, el rastreo se deshabilita para esta aplicación y los eventos no se listan en la salida de lttng-list(1).

Tenga en cuenta que no es seguro usar dlclose(3) en un objeto compartido de proveedor de tracepoints que se está utilizando activamente para rastreo, debido a la falta de conteo de referencias de LTTng-UST al objeto compartido.

Por ejemplo, enlazar estáticamente un proveedor de tracepoints a un objeto compartido que será cargado dinámicamente por una aplicación (un plugin, por ejemplo) no es seguro: el objeto compartido, que contiene el proveedor de tracepoints, podría ser cerrado dinámicamente (dlclose(3)) en cualquier momento por la aplicación.

Para instrumentar un objeto compartido, elija una de las siguientes opciones:

Enlace estático del proveedor de tracepoints a la aplicación, o

Construya el proveedor de tracepoints como un objeto compartido (siguiendo el procedimiento que se muestra en esta sección) y cárguelo previamente cuando sea necesario el rastreo utilizando la variable de entorno LD_PRELOAD.

Uso de LTTng-UST con daemons

Se necesita un cuidado adicional al usar liblttng-ust con aplicaciones daemon que llaman a fork(2), clone(2), o rfork(2) de BSD sin una llamada posterior al sistema de la familia exec(3). La biblioteca liblttng-ust-fork.so necesita ser precargada antes de iniciar la aplicación con la variable de entorno LD_PRELOAD (ver ld.so(8)).

Para usar liblttng-ust con una aplicación daemon que cierra descriptores de archivo que no fueron abiertos por ella, precargue la biblioteca liblttng-ust-fd.so antes de iniciar la aplicación. Los casos de uso típicos incluyen daemons que cierran todos los descriptores de archivo después de fork(2), y aplicaciones defectuosas que realizan "dobles cierres".

Pour détecter si liblttng-ust est chargé à partir d'une application :

1.Définissez le symbole faible lttng_ust_loaded globalement : 
int lttng_ust_loaded __attribute__((weak));

2.Testez lttng_ust_loaded si nécessaire : 
/* ... */
if (lttng_ust_loaded) {
    /* LTTng-UST est chargé */
} else {
    /* LTTng-UST N'EST PAS chargé */
}
/* ... */

int main(int argc, char* argv[])
{
    FILE *stream;
    struct app_struct app_struct;
    lttng_ust_tracepoint(my_provider, simple_event, argc, argv[0]);
    stream = fopen("/tmp/app.txt", "w");

                "Erreur : Impossible d'ouvrir /tmp/app.txt en écriture\n");
        return EXIT_FAILURE;
    }
    if (fprintf(stream, "0123456789") != 10) {
        fclose(stream);
        fprintf(stderr, "Erreur : Impossible d'écrire dans /tmp/app.txt\n");
        return EXIT_FAILURE;
    }
    lttng_ust_tracepoint(my_provider, big_event, 35,
                         "hello tracepoint", stream, -3.14,
                         array_of_ints);
    fclose(stream);
    app_struct.b = argc;
    app_struct.c = "[the string]";
    lttng_ust_tracepoint(my_provider, event_instance1, 23,
                         &app_struct);
    app_struct.b = argc * 5;
    app_struct.c = "[other string]";

VARIABLES D'ENVIRONNEMENT

LTTNG_HOME

Répertoire personnel alternatif de l'utilisateur. Cette variable est utile lorsque l'utilisateur exécutant l'application instrumentée a un répertoire personnel non inscriptible. Ce chemin est l'emplacement des sockets Unix pour la communication avec le démon de session par utilisateur.

LTTNG_UST_ABORT_ON_CRITICAL

Si défini, l'application instrumentée sera abortée en cas de message d'erreur critique.

LTTNG_UST_ALLOW_BLOCKING

Si défini, permet à l'application de réessayer le traçage d'événements lorsqu'il n'y a plus d'espace pour l'enregistrement de l'événement dans le sous-buffer, bloquant ainsi effectivement l'application jusqu'à ce que de l'espace soit libéré ou que le délai d'attente configuré soit atteint.

Pour permettre à une application de bloquer pendant le traçage, vous devez également spécifier un délai d'attente de blocage lorsque vous créez un canal avec l'option --blocking-timeout de la commande lttng-enable-channel(1).

Cette option peut être utile pour les charges de travail générant un débit de données de trace très élevé, où le blocage de l'application est un compromis acceptable pour éviter de jeter des enregistrements d'événements.


Attention
La définition de cette variable d'environnement peut affecter considérablement les timings de l'application.

LTTNG_UST_APP_PATH

Chemin du répertoire où le démon de session LTTng est censé placer les fichiers suivants pour recevoir les demandes de connexion de l'application instrumentée :
•Le socket Unix d'enregistrement de l'application.
•Les fichiers de mémoire partagée "wait" pour réveiller les applications instrumentées qui attendent qu'un démon de session démarre.
•Le fichier de port de l'agent.

Ce fichier contient le port TCP auquel les agents doivent se connecter pour activer le traçage LTTng.

Ce répertoire doit exister lorsque vous démarrez l'application pour que le traçage LTTng soit activé.

Lorsque LTTNG_UST_APP_PATH est défini, liblttng-ust :

•Considère uniquement ce chemin pour se connecter à un démon de session.
•Ne se connectera pas aux démons de session root et/ou utilisateur comme d'habitude.

Voir la variable d'environnement correspondante LTTNG_UST_CTL_PATH de lttng-sessiond(8).

LTTNG_UST_CLOCK_PLUGIN

Chemin de l'objet partagé agissant comme plugin de substitution d'horloge. Un exemple d'un tel plugin peut être trouvé dans la documentation LTTng-UST sous examples/clock-override https://github.com/lttng/lttng-ust/tree/stable-2.14/doc/examples/clock-override.

LTTNG_UST_DEBUG

Si défini, activer la sortie de débogage et d'erreur de liblttng-ust.

LTTNG_UST_GETCPU_PLUGIN

Chemin vers l'objet partagé servant de plugin de remplacement de getcpu(). Un exemple de tel plugin se trouve dans la documentation LTTng-UST sous examples/getcpu-override https://github.com/lttng/lttng-ust/tree/stable-2.14/doc/examples/getcpu-override.

LTTNG_UST_MAP_POPULATE_POLICY

Si défini, remplacer la politique utilisée pour peupler les pages de mémoire partagée au sein de l'application.

Les valeurs possibles sont :

none (par défaut)

Ne pré-peupler aucune page : prendre des défauts mineurs lors du premier accès pendant le traçage.

cpu_possible

Pré-peupler les pages pour tous les CPU possibles du système, comme indiqué dans /sys/devices/system/cpu/possible.

LTTNG_UST_REGISTER_TIMEOUT

Temps d'attente pour la commande du démon de session registration done avant de continuer à exécuter le programme principal (millisecondes).

La valeur 0 signifie ne pas attendre. La valeur -1 signifie attendre indéfiniment. Il est recommandé de définir cette variable d'environnement à 0 pour les applications ayant des contraintes de temps sur le temps de démarrage du processus.

Par défaut : 3000.

LTTNG_UST_WITHOUT_BADDR_STATEDUMP

Si défini, empêche liblttng-ust d'effectuer un vidage d'état de l'adresse de base (voir la section Vidage d'état LTTng-UST ci-dessus).

LTTNG_UST_WITHOUT_PROCNAME_STATEDUMP

Si défini, empêche liblttng-ust d'effectuer un vidage d'état du nom du processus (voir la section Vidage d'état LTTng-UST ci-dessus).
