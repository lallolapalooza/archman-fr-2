TRAP(1P) Manuel du programmeur POSIX TRAP(1P)

PROLOGUE

Cette page de manuel fait partie du Manuel du programmeur POSIX. L'implémentation Linux de cette interface peut différer (consultez la page de manuel Linux correspondante pour les détails du comportement sous Linux), ou l'interface peut ne pas être implémentée sous Linux.

NOM

trap — intercepter les signaux

SYNTAXE

trap n [condition...]
trap [action condition...]

DESCRIPTION

Si le premier opérande est un entier décimal non signé, le shell traitera tous les opérandes comme des conditions et réinitialisera chaque condition à sa valeur par défaut. Sinon, s'il y a des opérandes, le premier est traité comme une action et les suivants comme des conditions.

Si action est '-', le shell réinitialisera chaque condition à la valeur par défaut. Si action est vide (""), le shell ignorera chaque condition spécifiée si elle se produit. Sinon, l'argument action sera lu et exécuté par le shell lorsqu'une des conditions correspondantes survient. L'action de trap remplacera une action précédente (action par défaut ou une action explicitement définie). La valeur de "$?" après l'achèvement de l'action trap sera la valeur qu'elle avait avant l'invocation de trap.

La condition peut être EXIT, 0 (équivalent à EXIT), ou un signal spécifié en utilisant un nom symbolique, sans le préfixe SIG, tel que listé dans les tableaux de noms de signaux dans l'en-tête <signal.h> défini dans le volume Base Definitions de POSIX.1‐2017, Chapitre 13, Headers ; par exemple, HUP, INT, QUIT, TERM. Les implémentations peuvent autoriser les noms avec le préfixe SIG ou ignorer la casse dans les noms de signaux comme extension. L'établissement d'un piège pour SIGKILL ou SIGSTOP produit des résultats indéfinis.

L'environnement dans lequel le shell exécute un trap sur EXIT sera identique à l'environnement immédiatement après la dernière commande exécutée avant que le trap sur EXIT ne soit pris.

Chaque fois que trap est invoqué, l'argument action sera traité d'une manière équivalente à :

eval action

Les signaux qui étaient ignorés à l'entrée d'un shell non interactif ne peuvent pas être interceptés ou réinitialisés, bien qu'aucune erreur ne doive être signalée lors d'une tentative de le faire. Un shell interactif peut réinitialiser ou attraper les signaux ignorés à l'entrée. Les pièges resteront en place pour un shell donné jusqu'à ce qu'ils soient explicitement modifiés avec une autre commande trap.

Lorsqu'un sous-shell est entré, les pièges qui ne sont pas ignorés seront définis sur les actions par défaut, sauf dans le cas d'une substitution de commande ne contenant qu'une seule commande trap, auquel cas les pièges n'ont pas besoin d'être modifiés. Les implémentations peuvent vérifier ce cas en utilisant uniquement une analyse lexicale ; par exemple, si `trap` et $( trap -- ) ne modifient pas les pièges dans le sous-shell, des cas tels que l'affectation de var=trap puis l'utilisation de $($var) peuvent toujours les modifier. Cela n'implique pas que la commande trap ne peut pas être utilisée dans le sous-shell pour définir de nouveaux pièges.

La commande trap sans opérandes écrira dans la sortie standard une liste de commandes associées à chaque condition. Si la commande est exécutée dans un sous-shell, que l'implémentation n'effectue pas la vérification optionnelle décrite ci-dessus pour une substitution de commande ne contenant qu'une seule commande trap, et qu'aucune commande trap avec des opérandes n'a été exécutée depuis l'entrée dans le sous-shell, la liste contiendra les commandes qui étaient associées à chaque condition immédiatement avant l'entrée dans l'environnement du sous-shell. Sinon, la liste contiendra les commandes actuellement associées à chaque condition. Le format sera :

"trap -- %s %s ...\n", <action>, <condition> ...

Le shell formatera la sortie, y compris l'utilisation correcte des guillemets, de manière à ce qu'elle soit appropriée pour être réinjectée au shell en tant que commandes réalisant les mêmes résultats d'interception. Par exemple :

save_traps=$(trap)
...
eval "$save_traps"

Les systèmes conformes XSI autorisent également les numéros de signaux numériques pour les conditions correspondant aux noms de signaux suivants :

1
SIGHUP
2
SIGINT
3
SIGQUIT
6
SIGABRT
9
SIGKILL
14
SIGALRM
15
SIGTERM

L'utilitaire spécial trap se conformera au volume Base Definitions de POSIX.1‐2017, Section 12.2, Directives de syntaxe des utilitaires.

STATUT DE SORTIE

Si le nom ou le numéro du piège est invalide, un statut de sortie non nul sera retourné ; sinon, zéro sera retourné. Pour les shells interactifs et non interactifs, les noms ou numéros de signaux invalides ne seront pas considérés comme une erreur de syntaxe et ne provoqueront pas l'arrêt du shell.

EXEMPLES

Écrire une liste de tous les pièges et actions :

trap

Définir un piège pour que l'utilitaire logout dans le répertoire référencé par la variable d'environnement HOME s'exécute lorsque le shell se termine :

trap '"$HOME"/logout' EXIT

ou :

trap '"$HOME"/logout' 0

Désactiver les pièges sur INT, QUIT, TERM et EXIT :

trap - INT QUIT TERM EXIT

RATIONNEL

Les implémentations peuvent autoriser les noms de signaux en minuscules comme extension. Les implémentations peuvent également accepter les noms avec le préfixe SIG ; aucune coquille historique connue ne le fait. Les utilitaires trap et kill dans ce volume de POSIX.1‐2017 sont maintenant cohérents dans leur omission du préfixe SIG pour les noms de signaux. Certaines implémentations de kill n'autorisent pas le préfixe, et kill -l liste les signaux sans préfixes.

L'interception de SIGKILL ou SIGSTOP est syntaxiquement acceptée par certaines implémentations historiques, mais elle n'a aucun effet. Les applications portables POSIX ne peuvent pas tenter d'intercepter ces signaux.

Le format de sortie ne correspond pas à la pratique historique. Étant donné que la sortie des commandes trap historiques n'est pas portable (car les valeurs numériques des signaux ne sont pas portables) et a dû changer pour le devenir, une opportunité a été saisie pour formater la sortie d'une manière qu'un script shell pourrait utiliser pour sauvegarder et réutiliser plus tard un piège si elle le souhaitait.

Le KornShell utilise un piège ERR qui est déclenché chaque fois que set -e provoquerait

trap(1p) — man pages

RATIONALE

The text about the environment for the EXIT trap invalidates the behavior of some historical versions of interactive shells which, for example, close the standard input before executing a trap on 0. For example, in some historical interactive shell sessions the following trap on 0 would always print "--":

trap 'read foo; echo "-$foo-"' 0

The command:

trap 'eval " $cmd"' 0

causes the contents of the shell variable cmd to be executed as a command when the shell exits. Using:

trap '$cmd' 0

does not work correctly if cmd contains any special characters such as quoting or redirections. Using:

trap " $cmd" 0

also works (the leading <space> character protects against unlikely cases where cmd is a decimal integer or begins with '-'), but it expands the cmd variable when the trap command is executed, not when the exit action is executed.
