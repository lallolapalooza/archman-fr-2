PROLOG

Cette page de manuel fait partie du Manuel du programmeur POSIX. L'implémentation Linux de cette interface peut différer (consultez la page de manuel Linux correspondante pour connaître les détails du comportement sous Linux), ou l'interface peut ne pas être implémentée sous Linux.

NOM

tgmath.h — macros génériques de type

SYNOPSIS

#include <tgmath.h>

DESCRIPTION

La fonctionnalité décrite sur cette page de référence est alignée sur la norme ISO C. Tout conflit entre les exigences décrites ici et la norme ISO C est involontaire. Ce volume de POSIX.1‐2017 s'en remet à la norme ISO C.

L'en-tête <tgmath.h> inclut les en-têtes <math.h> et <complex.h> et définit plusieurs macros génériques de type.

Parmi les fonctions contenues dans les en-têtes <math.h> et <complex.h> sans suffixe f (float) ou l (long double), plusieurs ont un ou plusieurs paramètres dont le type réel correspondant est double. Pour chacune de ces fonctions, à l'exception de modf(), j0(), j1(), jn(), y0(), y1(), et yn(), il existe une macro générique de type correspondante. Les paramètres dont le type réel correspondant est double dans le synopsis de la fonction sont des paramètres génériques. L'utilisation de la macro appelle une fonction dont le type réel correspondant et le domaine de type sont déterminés par les arguments des paramètres génériques.

L'utilisation de la macro appelle une fonction dont les paramètres génériques ont le type réel correspondant déterminé comme suit :

*
Premièrement, si un argument pour les paramètres génériques a le type long double, le type déterminé est long double.
*
Sinon, si un argument pour les paramètres génériques a le type double ou est de type entier, le type déterminé est double.
*
Sinon, le type déterminé est float.

Pour chaque fonction sans suffixe dans l'en-tête <math.h> pour laquelle il existe une fonction dans l'en-tête <complex.h> avec le même nom à l'exception d'un préfixe c, la macro générique de type correspondante (pour les deux fonctions) a le même nom que la fonction dans l'en-tête <math.h>. La macro générique de type correspondante pour fabs() et cabs() est fabs().

Si au moins un argument pour un paramètre générique est complexe, alors l'utilisation de la macro appelle une fonction complexe ; sinon, l'utilisation de la macro appelle une fonction réelle.

Pour chaque fonction sans suffixe dans l'en-tête <math.h> sans contrepartie préfixée par c dans l'en-tête <complex.h>, à l'exception de modf(), j0(), j1(), jn(), y0(), y1(), et yn(), la macro générique de type correspondante porte le même nom que la fonction. Ces macros génériques de type sont :

atan2() cbrt() ceil() copysign() erf() erfc() exp2() expm1() fdim() floor() fma() fmax() fmin() fmod() frexp() hypot() ilogb() ldexp() lgamma() llrint() llround() log10() log1p() log2() logb() lrint() lround() nearbyint() nextafter() nexttoward() remainder() remquo() rint() round() scalbln() scalbn() tgamma() trunc()

Si tous les arguments des paramètres génériques sont réels, alors l'utilisation de la macro appelle une fonction réelle ; sinon, l'utilisation de la macro entraîne un comportement indéfini.

Pour chaque fonction sans suffixe dans l'en-tête <complex.h> qui n'est pas une contrepartie préfixée par c à une fonction dans l'en-tête <math.h>, la macro générique de type correspondante porte le même nom que la fonction. Ces macros génériques de type sont :

carg() cimag() conj() cproj() creal()

L'utilisation de la macro avec n'importe quel argument réel ou complexe appelle une fonction complexe.

Notez que certaines fonctions sont présentes dans les deux listes. Les fonctions mathématiques qui ne sont pas complexes par nature peuvent quand même avoir des prototypes de fonction complexe : par exemple, fmax peut avoir un argument double complex.

L'utilisation de <tgmath.h> est similaire à l'utilisation de <math.h>, mais au lieu d'avoir des fonctions spécifiques à un type telles que sinf(), sin(), et sinl(), il existe une macro sin() qui choisit la bonne fonction en fonction du type de son argument.

Si le type de l'argument est un type entier, il est converti en double et la fonction double est appelée.

Si le type de l'argument est float, la fonction float est appelée.

Si le type de l'argument est double, la fonction double est appelée.

Si le type de l'argument est long double, la fonction long double est appelée.

Si le type de l'argument est un type complexe (par exemple, float complex), la fonction complexe correspondante est appelée (par exemple, sinf). Notez que les types complexes sont généralement gérés par le biais d'un ensemble distinct de fonctions mathématiques complexes fournies par <complex.h>.

Si un argument est un type complexe, tous les arguments doivent être de type complexe.

Si un argument est un type réel, tous les arguments doivent être de type réel.

RATIONALE

Les macros génériques par type permettent d'appeler une fonction dont le type est déterminé par le type de l'argument, comme c'est le cas pour les opérateurs C tels que '+' et '*'. Par exemple, avec une macro cos() générique par type, l'expression cos((float)x) sera de type float. Cette fonctionnalité permet d'écrire du code plus portable et plus efficace, et évite le besoin de conversions et d'suffixes maladroits lors du portage ou de l'ajustement de la précision. Les fonctions mathématiques génériques sont une fonctionnalité très appréciée de Fortran.

Les seuls arguments qui affectent la résolution du type sont les arguments correspondant aux paramètres qui ont le type double dans le synopsis. Par conséquent, le type d'un appel générique par type à nexttoward(), dont le second paramètre est long double dans le synopsis, est déterminé uniquement par le type du premier argument.

Le terme « générique par type » a été choisi plutôt que les alternatives proposées, « intrinsèque » et « surcharge ». Le terme est plus spécifique qu'intrinsèque, qui est déjà largement utilisé avec un sens plus général, et reflète une meilleure correspondance avec les fonctions génériques de Fortran qu'avec la surcharge de C++.

Les macros sont placées dans leur propre en-tête afin de ne pas casser silencieusement les anciens programmes qui incluent l'en-tête <math.h> ; par exemple, avec :

printf ("%e", sin(x))

modf(double, double *) est exclu car aucun moyen n'a été trouvé pour le rendre sûr sans compliquer la résolution des types.

L'implémentation peut, en tant qu'extension, doter certaines macros appropriées que POSIX.1-2017 ne spécifie que pour les arguments réels, de la capacité d'invoquer les fonctions complexes.

POSIX.1-2017 ne prescrit aucun mécanisme d'implémentation particulier pour les macros génériques. Elles pourraient être implémentées simplement avec des macros intégrées. La macro générique pour sqrt(), par exemple, pourrait être implémentée avec :

#undef sqrt
#define sqrt(x) __BUILTIN_GENERIC_sqrt(x)

Les macros génériques par type sont conçues pour un niveau utile de cohérence avec les fonctions mathématiques surchargées de C++.

La grande majorité des programmes C existants devraient ne pas être affectés lorsque l'en-tête <tgmath.h> est inclus au lieu des en-têtes <math.h> ou <complex.h>. Les macros génériques par type sont similaires aux macros de masquage de la bibliothèque standard ISO/IEC 9899:1999, bien que les types sémantiques des valeurs de retour diffèrent.

La capacité de surcharge sur les types entiers ainsi que flottants aurait été utile pour certaines fonctions ; par exemple, copysign(). La surcharge avec un nombre différent d'arguments aurait permis de réutiliser des noms ; par exemple, remainder() pour remquo(). Cependant, ces fonctionnalités auraient compliqué la spécification ; et leur utilisation naturelle et cohérente, comme pour un abs() flottant ou un atan() à deux arguments, aurait introduit des incohérences supplémentaires avec la norme ISO/IEC 9899:1999 pour un bénéfice insuffisant.

La norme ISO C ne limite en aucun cas les options d'efficacité de l'implémentation, y compris l'inlining des fonctions de bibliothèque.
