tags - Format de fichier tags Vi étendu dans les projets ctags

DESCRIPTION

Le contenu de la section suivante est une copie du fichier FORMAT du code source d'Exuberant Ctags dans son dépôt subversion sur sourceforge.net.

Les exceptions introduites dans Universal Ctags sont expliquées en ligne avec le marqueur "EXCEPTION". Les affirmations qui sont clarifiées dans Universal Ctags sont expliquées en ligne avec le marqueur "COMMENTAIRE".

Proposition pour un format de fichier tags Vi étendu

Version : 0.06 BROUILLON
Date : 8 fév 1998
Auteur : Bram Moolenaar <Bram at vim.org> et Darren Hiebert <dhiebert at users.sourceforge.net>

Introduction

Le format de fichier pour le fichier "tags", tel qu'utilisé par Vi et plusieurs de ses descendants, a des capacités limitées.

Cette fonctionnalité supplémentaire est souhaitée :

1.
Tags statiques ou locaux. La portée de ces tags est le fichier où ils sont définis. Le même tag peut apparaître dans plusieurs fichiers, sans être réellement un doublon.
2.
Tags dupliqués. Permettre au même tag d'apparaître plus d'une fois. Ils peuvent être situés dans un fichier différent et/ou avoir une commande différente.
3.
Support pour C++. Un tag n'est pas seulement spécifié par son nom, mais aussi par son contexte (le nom de la classe).
4.
Extension future. Lorsque des fonctionnalités supplémentaires sont encore souhaitées, il doit être possible de les ajouter ultérieurement, sans casser les programmes qui ne les prennent pas en charge.

Pour faire de cette proposition un standard pour les fichiers tags, elle doit être supportée par la plupart des personnes travaillant sur les versions de Vi, ctags, etc. Actuellement, ce standard est supporté par :

Compatibilité rétroactive

Un fichier tags généré dans le nouveau format devrait toujours être utilisable par Vi. Cela permet de distribuer des fichiers tags utilisables par toutes les versions et tous les descendants de Vi.

Cela restreint le format à ce que Vi peut gérer. Le format est :

1.
Le fichier tags est une liste de lignes, chaque ligne étant au format :
{nom_du_tag}<Tab>{fichier_du_tag}<Tab>{adresse_du_tag}
{nom_du_tag}
Tout identifiant, ne contenant pas d'espace blanc.

EXCEPTION : Universal Ctags viole cet élément de la proposition ; le nom du tag peut contenir des espaces. Cependant, les tabulations ne sont pas autorisées.

<Tab>
Exactement un caractère TAB (bien que de nombreuses versions de Vi puissent gérer n'importe quelle quantité d'espaces blancs).
{fichier_du_tag}
Le nom du fichier où {nom_du_tag} est défini, relatif au répertoire courant (ou à l'emplacement du fichier tags ?).
{adresse_du_tag}
Toute commande Ex. Lorsqu'elle est exécutée, elle se comporte comme si 'magic' n'était pas activé.
2.
Le fichier tags est trié sur {nom_du_tag}. Cela permet une recherche binaire dans le fichier.
3.
Les tags dupliqués sont autorisés, mais celui qui est effectivement utilisé est imprévisible (en raison de la recherche binaire).

La meilleure façon d'ajouter du texte supplémentaire à la ligne pour la nouvelle fonctionnalité, sans la casser pour Vi, est de mettre un commentaire dans {adresse_du_tag}. Cela donne la liberté d'utiliser n'importe quel texte, et devrait fonctionner dans n'importe quelle implémentation traditionnelle de Vi.

Par exemple, lorsque l'ancien fichier tags contient :

main    main.c  /^main(argc, argv)$/
DEBUG   defines.c       89

Les nouvelles lignes peuvent être :

main    main.c  /^main(argc, argv)$/;"texte additionnel quelconque
DEBUG   defines.c       89;"texte additionnel quelconque

Notez que le ';' est requis pour placer le curseur sur la bonne ligne, puis le '"' est reconnu comme le début d'un commentaire.

Pour les versions Vi conformes à Posix, cela NE fonctionnera PAS, car seul un numéro de ligne ou une commande de recherche est reconnu. J'espère que Posix pourra être ajusté. Nvi souffre de cela.

Sécurité

Vi autorise l'utilisation de toute commande Ex dans un fichier tags. Cela a le potentiel de fuite de sécurité de cheval de Troie.

La proposition est de n'autoriser que les commandes Ex qui positionnent le curseur dans un seul fichier. Les autres commandes, comme l'édition d'un autre fichier, la sortie de l'éditeur, la modification d'un fichier ou l'écriture d'un fichier, ne sont pas autorisées. Il est donc logique d'appeler la commande une adresse de tag.

Spécifiquement, ces deux commandes Ex sont autorisées :

•
Un numéro de ligne décimal :
89
•
Une commande de recherche. C'est un motif d'expression régulière, tel qu'utilisé par Vi, entouré de // ou ?? :
/^int c;$/
?main()?

Il existe deux combinaisons possibles :

•
Concaténation des éléments ci-dessus, avec ';' entre eux. La signification est que le premier numéro de ligne ou commande de recherche est utilisé, le curseur est positionné sur cette ligne, puis la seconde commande de recherche est utilisée (un numéro de ligne ne serait pas utile). Cela peut être fait plusieurs fois. Ceci est utile lorsque les informations d'une seule ligne ne sont pas uniques, et que la recherche doit commencer sur une ligne spécifiée.
/struct xyz {/;/int count;/
389;/struct foo/;/char *s;/
•
Un commentaire final peut être ajouté, commençant par ';"' (deux caractères : point-virgule et guillemet double). Ceci est utilisé ci-dessous.
89;" foo bar

Cela pourrait être étendu à l'avenir. Ce qui manque actuellement, c'est une façon de positionner le curseur dans une colonne spécifique.

Objectifs

Maintenant, l'utilisation du texte de commentaire doit être définie. Ce qui suit est visé :

1.
Garder le texte court, car :
  • La longueur de ligne que Vi peut gérer est limitée à 512 caractères.
  • Les fichiers tags peuvent contenir des milliers de tags. J'ai vu des fichiers tags de plusieurs Mo.
  • Plus de texte ralentit la recherche.
2.
Garder le texte lisible, car :
  • Il est souvent nécessaire de vérifier la sortie d'un nouveau programme ctags.
  • Pouvoir éditer le fichier à la main.
  • Faciliter l'écriture d'un programme pour produire ou
  • analyser le fichier.
3.
N'utilisez pas de caractères spéciaux, car :
•
Il devrait être possible de traiter un fichier de tags comme un fichier texte normal.

Proposition

Utilisez un commentaire après le champ {tagaddress}. Le format serait :

{nom_tag}<Tab>{fichier_tag}<Tab>{adresse_tag}[;"<Tab>{champ_tag}..]
{nom_tag}
N'importe quel identifiant, ne contenant pas d'espace blanc.

EXCEPTION : Universal Ctags viole ce point de la proposition ; le nom peut contenir des espaces. Cependant, les tabulations ne sont pas autorisées. Une conversion, pour certains caractères incluant <Tab> dans la "valeur", expliquée dans la dernière partie de cette section, est appliquée.

<Tab>
Exactement un caractère TAB (bien que de nombreuses versions de Vi puissent gérer n'importe quelle quantité d'espaces blancs).
{fichier_tag}
Le nom du fichier où {nom_tag} est défini, relatif au répertoire courant (ou à l'emplacement du fichier de tags ?).
{adresse_tag}
N'importe quelle commande Ex. Lorsqu'elle est exécutée, elle se comporte comme si 'magic' n'était pas défini. Elle peut être restreinte à un numéro de ligne ou à un motif de recherche (Posix).

COMMENTAIRE : {adresse_tag} pourrait contenir des caractères de tabulation. Voir ctags-client-tools(7) pour savoir comment extraire par programme {adresse_tag} (appelé "champ de motif" là-bas) et l'analyser.

Optionnellement :

;"
point-virgule + guillemet double : Termine l'adresse du tag d'une manière qui ressemble au début d'un commentaire pour Vi.
{champ_tag}
Voir ci-dessous.

Un champ de tag a un nom, un deux-points et une valeur : "nom:valeur".

  • Le nom est composé uniquement de caractères alphabétiques. Majuscules et minuscules sont autorisées. Les minuscules sont recommandées. La casse est importante ("kind:" et "Kind:" sont des champs de tag différents).

    EXCEPTION : Universal Ctags permet aux utilisateurs d'utiliser un caractère numérique dans le nom, autre que sa première lettre.

  • La valeur peut être vide. Elle ne peut pas contenir de <Tab>.
  • Lorsqu'une valeur contient un \t, cela représente une tabulation <Tab>.
  • Lorsqu'une valeur contient un \r, cela représente un retour chariot <CR>.
  • Lorsqu'une valeur contient un \n, cela représente un saut de ligne <NL>.
  • Lorsqu'une valeur contient un \\, cela représente un seul caractère \.

L'utilisation d'autres caractères pour le caractère backslash est réservée à une expansion future. Attention : Si la valeur d'un champ de tag contient un nom de fichier MS-DOS, les backslashes doivent être doublés !

EXCEPTION : Universal Ctags introduit des règles de conversion supplémentaires.

  • Lorsqu'une valeur contient un \a, cela représente un caractère BEL <BEL> (0x07).
  • Lorsqu'une valeur contient un \b, cela représente un caractère Backspace <BS> (0x08).
  • Lorsqu'une valeur contient un \v, cela représente un caractère Tabulation verticale <VT> (0x0b).
  • Lorsqu'une valeur contient un \f, cela représente un caractère Saut de page <FF> (0x0c).
  • Les caractères de la plage 0x01 à 0x1F inclus, et 0x7F, sont convertis en un nombre hexadécimal préfixé par \x si les caractères ne sont pas gérés dans les règles "valeur" ci-dessus.

EXCEPTION : Universal Ctags autorise toutes ces séquences d'échappement dans {nom_tag} et {fichier_tag} également. Cependant, concernant {fichier_tag}, une condition doit être remplie. Voir "Exceptions dans Universal Ctags" concernant la condition.

•
L'espace de tête (0x20) et ! (0x21) dans {nom_tag} sont convertis en un nombre hexadécimal préfixé par \x (\x20 et \x21) si le tag n'est pas un pseudo-tag. Comme décrit plus loin, un pseudo-tag commence par !. Ces règles servent à distinguer les pseudo-tags et les non pseudo-tags (tags réguliers) lorsque les lignes de tags dans un fichier de tags sont triées.

Noms de champs de tag proposés :

NOM-CHAMP DESCRIPTION
arity Nombre d'arguments pour un tag de fonction.
class Nom de la classe dont ce tag est un membre ou une méthode.
enum Nom de l'énumération dans laquelle ce tag est un énumérateur.
file Tag statique (local), avec une portée du fichier spécifié. Lorsque la valeur est vide, {fichier_tag} est utilisé.
function Fonction dans laquelle ce tag est défini. Utile pour les variables locales (et les fonctions). Lorsque les fonctions s'imbriquent (par exemple, en Pascal), les noms des fonctions sont concaténés, séparés par '/', ressemblant ainsi à un chemin.
kind Type de tag. La valeur dépend du langage. Pour C et C++, ces types sont recommandés : 0.0 c nom de classe d define (issu de #define XXX) e énumérateur f nom de fonction ou de méthode F nom de fichier g nom d'énumération m membre (de structure ou de classe) p prototype de fonction s nom de structure t typedef u nom d'union v variable 168u Lorsque ce champ est omis, le type de tag est indéfini.
struct Nom de la structure dans laquelle ce tag est un membre.
union Nom de l'union dans laquelle ce tag est un membre.

Notez que ceux-ci sont principalement pour C et C++. Lorsque des programmes de tags sont écrits pour d'autres langages, cette liste devrait être étendue pour inclure les noms de champs utilisés. Cela aidera les utilisateurs à être indépendants du programme de tags utilisé.

Exemples :

asdf    sub.cc  /^asdf()$/;"    new_field:some\svalue   file:
foo_t   sub.h   /^typedef foo_t$/;"     kind:t
func3   sub.p   /^func3()$/;"   function:/func1/func2   file:
getflag sub.c   /^getflag(arg)$/;"      kind:f  file:
inc     sub.cc  /^inc()$/;"     file: class:PipeBuf

Le nom du champ "kind:" peut être omis. Ceci afin de réduire la taille du fichier de tags d'environ 15 %. Un programme lisant le fichier de tags peut reconnaître le champ "kind:" par l'absence de ':'. Exemples :

foo_t   sub.h   /^typedef foo_t$/;"     t
getflag sub.c   /^getflag(arg)$/;"      f       file:

Remarques supplémentaires :

•
Lorsqu'un champ de tag apparaît deux fois dans une ligne de tag, seul le dernier est utilisé.

Note sur les séparateurs de ligne :

Vi fonctionne traditionnellement sur les systèmes Unix, où le séparateur de ligne est un simple caractère de saut de ligne <NL>. Sur les systèmes MS-DOS et compatibles, <CR><NL> est le séparateur de ligne standard. Pour augmenter la portabilité, ce séparateur de ligne est également pris en charge.

Sur Macintosh, un seul <CR> est utilisé comme séparateur de ligne. Le prendre en charge sur les systèmes Unix pose des problèmes, car la plupart des implémentations de fgets() ne considèrent pas le <CR> comme un séparateur de ligne. Par conséquent, la prise en charge d'un <CR> comme séparateur de ligne est limitée à Macintosh.

Résumé :

séparateur de ligne généré sur accepté sur
<LF> Unix Unix, MS-DOS, Macintosh
<CR> Macintosh Macintosh
<CR><LF> MS-DOS Unix, MS-DOS, Macintosh

Les caractères <CR> et <LF> ne peuvent pas être utilisés à l'intérieur d'une ligne de tag. Ceci n'est mentionné nulle part ailleurs (car c'est évident).

Note sur les espaces blancs :

Vi autorisait n'importe quel espace blanc pour séparer le nom du tag du fichier du tag, et le nom du fichier de l'adresse du tag. Cela devrait être autorisé pour la compatibilité ascendante. Cependant, tous les programmes connus qui génèrent des tags utilisent une seule tabulation <Tab> pour séparer les champs.

Il y a un problème d'utilisation de noms de fichiers avec des espaces blancs intégrés dans le champ du fichier de tags. Pour contourner cela, les mêmes caractères spéciaux que dans les nouveaux champs pourraient être utilisés, par exemple \s. Mais, malheureusement, sous MS-DOS, le caractère backslash est utilisé pour séparer les noms de fichiers. Le nom de fichier c:\vim\sap contient \s, mais ce n'est pas un <Espace>. Le nombre de backslashes pourrait être doublé, mais cela ajouterait beaucoup de caractères et rendrait l'analyse du fichier de tags plus lente et plus maladroite.

Pour éviter ces problèmes, nous n'autoriserons qu'une tabulation <Tab> pour séparer les champs, et nous ne prendrons pas en charge un nom de fichier ou un nom de tag contenant un caractère <Tab>. Cela signifie que nous ne sommes pas compatibles à 100 % avec Vi. Cependant, aucun programme de tags connu n'utilise autre chose qu'une tabulation <Tab> pour séparer les champs. Ce n'est que lorsqu'un utilisateur a tapé le fichier de tags lui-même, ou a créé son propre programme pour générer un fichier de tags, que nous pourrions rencontrer des problèmes. Pour résoudre cela, le fichier de tags devrait être filtré pour remplacer les espaces blancs arbitraires par une seule tabulation <Tab>. Cette commande Vi peut être utilisée :

:%s/^\([^ ^I]*\)[ ^I]*\([^ ^I]*\)[ ^I]*/\1^I\2^I/

(remplacez ^I par un vrai <Tab>).

COMMENTAIRE : Universal Ctags fonctionnant sous MS Windows convertit le séparateur \ en / par défaut, et autorise les séquences d'échappement même dans {fichier_tag} si une condition est remplie. Voir "Exceptions dans Universal Ctags" concernant la condition.

INFORMATIONS SUR LE FICHIER DE TAGS :

Les lignes de pseudo-tags peuvent être utilisées pour encoder des informations dans le fichier de tags concernant les détails de son contenu (par exemple, les tags ont-ils été triés ?, les champs de tags optionnels sont-ils présents ?), et concernant le programme utilisé pour générer le fichier de tags. Ces informations peuvent être utilisées à la fois pour optimiser l'utilisation du f

ile (par exemple, activer/désactiver la recherche binaire) et fournir des informations générales (quelle version du générateur a été utilisée).

Les noms des balises utilisés dans ces lignes peuvent être judicieusement choisis pour s'assurer que, lorsqu'elles sont triées, elles se situent toujours près des premières lignes du fichier de balises. L'utilisation de « !_TAG_ » est recommandée. Notez qu'une balise rare comme « ! » peut être triée avant ces lignes. Le programme lisant le fichier de balises doit être suffisamment intelligent pour ignorer ces balises.

Les lignes décrites ci-dessous ont été choisies pour transmettre un ensemble d'informations sélectionnées.

Lignes de balises fournissant des informations sur le contenu du fichier de balises :

!_TAG_FILE_FORMAT   {version-number}        /commentaire optionnel/
!_TAG_FILE_SORTED   {0|1}                   /0=non trié, 1=trié/

Le {version-number} utilisé dans la ligne du format de fichier de balises réserve la valeur « 1 » pour les fichiers de balises conformes au format original UNIX vi/ctags, et réserve la valeur « 2 » pour les fichiers de balises conformes à cette proposition. Cette valeur peut être utilisée pour déterminer si les fonctionnalités étendues décrites dans cette proposition sont présentes.

Lignes de balises fournissant des informations sur le programme utilisé pour générer le fichier de balises, et fournies uniquement à des fins de documentation :

!_TAG_PROGRAM_AUTHOR        {nom-auteur}   /{adresse-e-mail}/
!_TAG_PROGRAM_NAME  {nom-programme}  /commentaire optionnel/
!_TAG_PROGRAM_URL   {URL}   /commentaire optionnel/
!_TAG_PROGRAM_VERSION       {id-version}    /commentaire optionnel/

EXCEPTION : Universal Ctags introduit plus de types de pseudo-balises. Voir ctags-client-tools(7) à leur sujet.

COMMENTAIRE : Bien que les pseudo-balises soient sémantiquement différentes des balises régulières, elles utilisent le même format, qui est :

{nom-balise}<Tab>{fichier-balise}<Tab>{adresse-balise}

, et les séquences d'échappement et les caractères illégaux expliqués dans la section « Proposition » s'appliquent également aux pseudo-balises.

Exceptions dans Universal Ctags

Universal Ctags prend en charge cette proposition avec quelques exceptions.

Exceptions

1.
{nom-balise} dans le fichier de balises généré par Universal Ctags peut contenir des espaces et plusieurs séquences d'échappement. Les analyseurs pour des documents comme Tex et reStructuredText, ou des langages libéraux comme JavaScript ont besoin de ces exceptions. Voir {nom-balise} de la section Proposition pour plus de détails sur la conversion.
2.
{fichier-balise} dans le fichier de balises généré par Universal Ctags peut contenir des espaces et plusieurs séquences d'échappement si les caractères \ ne sont pas utilisés comme séparateurs de noms de fichiers. Les systèmes de type UNIX utilisent / à cette fin. Sur MS Windows, Universal Ctags convertit \ dans les noms de fichiers en / par défaut. Ainsi, en général, cette condition est satisfaite. Universal Ctags émet plusieurs pseudo-balises indiquant si la condition est satisfaite ou non. Voir ctags-client-tools(7) à propos de ces pseudo-balises.
3.
La partie « nom » de {champ-balise} dans une balise générée par Universal Ctags peut contenir des caractères numériques, mais le premier caractère du « nom » doit être alphabétique.

Sortie compatible et faiblesse

Le comportement par défaut (option --output-format=u-ctags) présente les exceptions. D'un autre côté, avec l'option --output-format=e-ctags, ctags n'a pas d'exception ; Universal Ctags peut utiliser le même format de fichier qu'Exuberant Ctags. Cependant, --output-format=e-ctags supprime une entrée de balise dont le nom inclut un espace ou un caractère de tabulation. La pseudo-balise TAG_OUTPUT_MODE indique quel format est utilisé lorsque ctags génère le fichier de balises.
