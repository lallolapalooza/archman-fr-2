TABLE(5) Manuel des formats de fichiers TABLE(5)

NOM

table — description du format pour les tables de smtpd

DESCRIPTION

Cette page de manuel documente le format des fichiers pour les diverses tables utilisées par le démon de messagerie smtpd(8).

Le format décrit ici s'applique aux tables telles que définies dans smtpd.conf(5).

TYPES DE TABLES

Il existe deux types de tables : les listes et les mappings. Une liste se compose d'une série de valeurs, tandis qu'un mapping se compose d'une série de clés et de leurs valeurs associées. Les exemples suivants illustrent comment les déclarer comme tables statiques :

table mylist { value1, value2, value3 }
table mymapping { key1 = value1, key2 = value2, key3 = value3 }

Lors de l'utilisation d'une table de type « file », une liste sera écrite avec chaque valeur sur une ligne séparée.

value1
value2
value3

Un mapping sera écrit avec chaque clé et valeur sur une ligne, les espaces blancs et un deux-points optionnel séparant les deux colonnes :

key1:	value1
key2	value2
key3	value3

Les lignes vides, les espaces et les tabulations en début et fin de ligne sont ignorés. Les lignes dont le premier caractère non-espace est une dièse (« # ») sont des commentaires et sont ignorés. Pour forcer l'analyse d'une table de fichier comme une liste plutôt qu'un mapping, utilisez ce commentaire spécial :

# @list

Une table de fichier peut être convertie en base de données Berkeley en utilisant l'utilitaire makemap(8) sans changement de syntaxe.

Les tables utilisant un backend de type « file » ou base de données Berkeley seront référencées comme suit :

table nom file:/chemin/vers/fichier
table nom db:/chemin/vers/fichier.db

Tables d'alias

Les tables d'alias sont des mappings qui associent un destinataire à une ou plusieurs destinations. Elles peuvent être utilisées dans deux contextes : les alias de domaine principal et le mapping de domaine virtuel.

action nom méthode alias <table>
action nom méthode virtual <table>

Dans un contexte de domaine principal, la clé est la partie utilisateur de l'adresse du destinataire, tandis que la valeur est un ou plusieurs destinataires tels que décrits dans aliases(5) :

user1	otheruser
user2	otheruser1,otheruser2
user3	otheruser@example.com

Dans un contexte de domaine virtuel, la clé est soit une partie utilisateur, une adresse email complète, soit un catch-all, suivant les règles de sélection décrites dans smtpd.conf(5), et la valeur est un ou plusieurs destinataires tels que décrits dans aliases(5) :

user1			otheruser
user2@example.org	otheruser1,otheruser2
@example.org		otheruser@example.com
@			catchall@example.com

La directive suivante utilise le même format de table, mais avec une signification différente. Ici, l'utilisateur est autorisé à envoyer des e-mails depuis les adresses listées :

listen on interface auth [...] senders <table>

Tables de domaines

Les tables de domaines sont de simples listes de domaines ou d'hôtes.

match for domain <table> action nom
match helo <table> [...] action nom

Dans ce contexte, la liste des domaines sera comparée au domaine du destinataire ou au nom HELO annoncé par l'hôte expéditeur, respectivement. Pour les backends « static », « file » et dbopen(3), un joker peut être utilisé de sorte que la table de domaines puisse contenir :

example.org
*.example.org

Tables d'identification

Les tables d'identification sont des mappings d'identifiants. Elles peuvent être utilisées dans deux contextes :

listen on interface tls [...] auth <table>
action nom relay host relay-url auth <table>

Dans un contexte d'écoute, les identifiants sont un mapping de nom d'utilisateur et de mots de passe cryptés :

user1	$2b$10$hIJ4QfMcp.90nJwKqGbKM.MybArjHOTpEtoTV.DgLYAiThuoYmTSe
user2	$2b$10$bwSmUOBGcZGamIfRuXGTvuTo3VLbPG9k5yeKNMBtULBhksV5KdGsK

Les mots de passe doivent être cryptés en utilisant la sous-commande encrypt de smtpctl(8).

Dans un contexte de relais, les identifiants sont un mapping d'étiquettes et de paires nom d'utilisateur:mot de passe :

label1	user:password

L'étiquette doit être unique et sert de sélecteur pour les identifiants corrects lorsque plusieurs identifiants sont valides pour une seule destination. Le mot de passe n'est pas crypté car il doit être fourni à l'hôte distant.

Tables Netaddr

Les tables Netaddr sont des listes d'adresses réseau IPv4 et IPv6. Elles ne peuvent être utilisées que dans le contexte suivant :

match from src <table> action nom

Lorsqu'elle est utilisée comme « source de provenance », l'adresse d'un client est comparée à la liste des adresses de la table jusqu'à ce qu'une correspondance soit trouvée.

Une table netaddr peut contenir des adresses exactes ou des masques de réseau, et se présente comme suit :

192.168.1.1
[::1]
192.168.1.0/24

Les adresses IPv6 doivent être entourées de crochets.

Tables Userinfo

Les tables Userinfo sont utilisées dans le contexte des règles pour spécifier une base d'utilisateurs alternative, mappant les utilisateurs virtuels aux utilisateurs système locaux par UID, GID et répertoire personnel.

action nom méthode userbase <table>

Une table userinfo ressemble à ceci :

joe	1000:100:/home/virtual/joe
jack	1000:100:/home/virtual/jack

Dans cet exemple, joe et jack sont des utilisateurs virtuels mappés à l'utilisateur système local avec UID 1000 et GID 100, mais avec des répertoires personnels différents. Ces répertoires peuvent contenir un fichier forward(5). Ceci peut être utilisé en conjonction avec une table d'alias qui mappe une adresse e-mail ou la partie domaine vers le nom d'utilisateur virtuel désiré. Par exemple :

joe@example.org     joe
jack@example.com    jack

Tables Source

Les tables Source sont des listes d'adresses IPv4 et IPv6. Elles ne peuvent être utilisées que dans le contexte suivant :

action nom relay src <table>

Des requêtes successives à la table source renverront les éléments un par un.

Une table source ressemble à ceci :

192.168.1.2
192.168.1.3
[::1]
[::2]

Les adresses IPv6 doivent être entourées de crochets.

Tables Mailaddr

Les tables Mailaddr sont des mappings d'adresses email.

match for mailaddr <table> action name
action name deliver to <table>

Dans le premier cas, l'adresse complète de l'expéditeur est comparée à la table. Cela peut être utilisé pour la réception de spam, où la table contient une liste d'adresses expéditeurs à rejeter ou à placer dans un dossier spécial.

spammer@example.com	REJECT
another@example.net	REJECT

Dans le second cas, l'adresse du destinataire est recherchée dans la table. S'il y a une correspondance, le processus de livraison est arrêté et le destinataire spécifié dans la table est utilisé.

user@example.org	localuser
admin@example.com	anotheruser@example.net

Les adresses email, à la fois dans les clés et les valeurs, doivent être sensibles à la casse.

Tables Pattern

Les tables Pattern sont des mappings de chaînes de caractères qui sont comparées à l'aide d'expressions régulières. Elles sont utilisées pour des correspondances complexes qui ne peuvent pas être exprimées avec des tables statiques ou de fichiers simples.

match for message header nom-en-tête <table> action name
match for message body <table> action name
action name rewrite <table>

Les clés des tables Pattern sont des expressions régulières, et les valeurs sont les chaînes de remplacement ou les actions à entreprendre. Les expressions régulières doivent être conformes à la syntaxe re_format(7).

Exemple d'utilisation pour l'en-tête d'un message :

Subject: .*promo.*	DISCARD
X-Spam-Score: \d+ > 5	REJECT

Exemple d'utilisation pour le corps d'un message :

http://.*\.example\.com/.*	REPLACE_WITH_LINK_REMOVED
<script>.*</script>	REPLACE_WITH_CODE_REMOVED

Exemple d'utilisation pour la réécriture d'adresses :

user@example.com	newuser@example.org
^.*@domain\.com$	virtual@{1}

Le caractère « @ » suivi d'un chiffre fait référence au groupe capturant correspondant dans l'expression régulière. Le caractère « @ » seul est interprété comme une substitution littérale.

smtpd.conf(5) — OpenSMTPD

NAME

smtpd.conf

configuration file for OpenSMTPD

DESCRIPTION

The OpenSMTPD SMTP server is configured by the means of a single file, smtpd.conf. This file is divided into several sections, each beginning with a keyword followed by its parameters.

Empty lines and lines starting with a # character are ignored.

The configuration file syntax is generally composed of a keyword, followed by a list of parameters. Some keywords may take a list of tables which are referenced using a colon : character, and a table name. Some keywords may also take a list of actions, which are also referenced using a colon : character, and an action name.

The configuration file is processed from top to bottom, and the first matching rule for a given context is applied.

TABLE TYPES

Mailaddr tables

Mailaddr tables are lists of email addresses. They can be used in the following contexts:

match mail-from <table> action name
match rcpt-to <table> action name

A mailaddr entry is used to match an email address against a username, a domain or a full email address. A "*" wildcard may be used in part of the domain name.

A mailaddr table looks as follow:

user
@domain
user@domain
user@*.domain

Addrname tables

Addrname tables are used to map IP addresses to hostnames. They can be used in both listen context and relay context:

listen on interface hostnames <table>
action name relay helo-src <table>

In listen context, the table is used to look up the server name to advertise depending on the local address of the socket on which a connection is accepted. In relay context, the table is used to determine the hostname for the HELO sequence of the SMTP protocol, depending on the local address used for the outgoing connection.

The format is a mapping from inet4 or inet6 addresses to hostnames:

[::1]		localhost
127.0.0.1	localhost
88.190.23.165	www.opensmtpd.org

IPv6 addresses must be enclosed in square brackets.
