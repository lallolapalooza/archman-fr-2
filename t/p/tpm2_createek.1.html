tpm2_createek(1) Manuel des commandes générales tpm2_createek(1)

NOM

tpm2_createek(1) - Génère une clé d'endossement conforme au profil TCG.

SYNOPSIS

tpm2_createek [OPTIONS]

DESCRIPTION

tpm2_createek(1) - Génère une clé d'endossement (EK) conforme au profil TCG, qui est l'objet principal de la hiérarchie d'endossement.

Si un objet transitoire est généré, l'outil génère un fichier de contexte spécifié avec -c.

Se référer à : http://www.trustedcomputinggroup.org/files/static_page_files/7CAA5687-1A4B-B294-D04080D058E86C5F

OPTIONS

•
-P, --eh-auth=AUTH:

La valeur d'autorisation pour la hiérarchie d'endossement.

•
-w, --owner-auth=AUTH

La valeur d'autorisation pour la hiérarchie du propriétaire.

•
-c, --ek-context=OBJECT ou FICHIER:

Soit un chemin de fichier, soit une valeur de handle persistant pour enregistrer la clé d'endossement.

Si une valeur de - est passée, l'outil trouvera un handle persistant vacant à utiliser et affichera le handle automatiquement sélectionné.

Si le fichier de contexte est enregistré via cette option et la clé publique via l'option -u, l'EK peut être restauré via un appel à tpm2_loadexternal(1).

•
-G, --key-algorithm=ALGORITHME:

L'algorithme de clé d'endossement. Supporte :

•
ecc - Une clé NIST_P256 par défaut. Des courbes alternatives peuvent être sélectionnées en utilisant des spécificateurs d'algorithme (par ex. ecc384 ou ecc_nist_p384).
•
rsa - Une clé RSA2048.
•
keyedhash - clé hmac.
•
-u, --public=FICHIER:

L'entrée optionnelle pour un fichier afin d'enregistrer la partie publique de la clé d'endossement.

•
-t, --template:

Le modèle optionnel de clé d'endossement défini par le fabricant et le nonce à partir d'indices NV fixes pour remplir la zone publique TPM2B_PUBLIC. Voir la spécification du profil de certificat EK TCG pour plus d'informations : https://trustedcomputinggroup.org/wp-content/uploads/ TCG_IWG_Credential_Profile_EK_V2.1_R13.pdf

•
-f, --format:

Sélection du format pour le fichier de sortie de la clé publique. `tss' (par défaut) produira un blob binaire conformément à la spécification TPM 2.0. `pem' produira une clé publique encodée PEM compatible OpenSSL. `der' produira une clé publique encodée DER compatible OpenSSL. `tpmt' produira un blob binaire de la structure TPMT_PUBLIC référencée par les spécifications TPM 2.0.

Format de la clé publique.

Références

Format de l'Objet de Contexte

Le type d'un objet de contexte, qu'il s'agisse d'un handle ou d'un nom de fichier, est déterminé selon la logique suivante dans l'ordre :

•
Si l'argument est un chemin de fichier, le fichier est chargé comme objet TPM transitoire restauré.
•
Si l'argument correspond à un préfixe de l'un des éléments suivants :
•
owner : la hiérarchie du propriétaire
•
platform : la hiérarchie de la plateforme
•
endorsement : la hiérarchie d'endossement
•
lockout : l'objet persistant de contrôle de verrouillage
•
Si l'argument peut être chargé comme un nombre, il sera traité comme un handle, par ex. 0x81010013 et utilisé directement._OBJECT_.

Formatage de l'Autorisation

L'autorisation pour l'utilisation d'un objet dans TPM2.0 peut prendre 3 formes différentes : 1. Mot de passe 2. HMAC 3. Sessions

NOTE : « Les autorisations utilisent le MOT DE PASSE VIDE par défaut lorsqu'elles ne sont pas spécifiées ».

Mots de passe

Les mots de passe sont interprétés sous les formes suivantes en utilisant des identifiants de préfixe.

Note : Par défaut, les mots de passe sont considérés comme étant sous forme de chaîne lorsqu'ils n'ont pas de préfixe.

Chaîne de caractères

Un mot de passe sous forme de chaîne, spécifié par le préfixe « str: » ou son absence (chaîne brute sans préfixe) n'est pas interprété et est directement utilisé pour l'autorisation.

Exemples

foobar
str:foobar

Chaîne hexadécimale

Un mot de passe sous forme de chaîne hexadécimale, spécifié par le préfixe « hex: », est converti d'une forme hexadécimale en un tableau d'octets, permettant ainsi les mots de passe contenant des caractères non imprimables et/ou peu pratiques pour le terminal.

Exemple

hex:1122334455667788

Fichier

Un mot de passe basé sur un fichier, spécifié par le préfixe « file: », doit être le chemin d'un fichier contenant le mot de passe à lire par l'outil, ou un « - » pour utiliser stdin. Stocker les mots de passe dans des fichiers empêche les fuites d'informations ; les mots de passe passés en tant qu'options peuvent être lus depuis la liste des processus ou les fonctionnalités courantes d'historique de shell.

Exemples

# Pour utiliser stdin et être invité
file:-
# Pour utiliser un fichier à partir d'un chemin
file:chemin/vers/fichier/mot_de_passe
# Pour écho un mot de passe via stdin :
echo foobar | tpm2_tool -p file:-
# Pour utiliser une chaîne ici bash via stdin :
tpm2_tool -p file:- <<< foobar

Sessions

Lors de l'utilisation d'une session de politique pour autoriser l'utilisation d'un objet, préfixez l'argument de l'option avec le mot-clé session. Indiquez ensuite un chemin vers un fichier de session qui a été créé avec tpm2_startauthsession(1). Optionnellement, si la session nécessite une valeur d'authentification à envoyer avec le handle de session (par ex. mot de passe de politique), ajoutez un + suivi d'une chaîne comme décrit dans la section Mots de passe.

Exemples

Pour utiliser un fichier de contexte de session appelé session.ctx.

session:session.ctx

Pour utiliser un fichier de contexte de session appelé session.ctx ET envoyer la valeur d'authentification mypassword.

session:session.ctx+mypassword

Pour utiliser un fichier de contexte de session appelé session.ctx ET envoyer la valeur d'authentification HEX 0x11223344.

session:session.ctx+hex:11223344

Autorisations PCR

Vous pouvez satisfaire une politique PCR en utilisant le préfixe « pcr: » et le mini-langage PCR. Le mini-langage PCR est le suivant : <spécificateur-pcr>=<fichier-pcr-brut>

Le spécificateur PCR est documenté dans la section « Spécificateurs de banque PCR ».

Le fichier-pcr-brut est une valeur optionnelle

argument qui contient le résultat des contenus bruts de PCR tels que retournés par tpm2_pcrread(1).

Spécificateurs de banque PCR

Exemples

Pour satisfaire une politique PCR de sha256 sur les banques 0, 1, 2 et 3, utilisez un spécificateur de :

pcr:sha256:0,1,2,3

spécifiant AUTH.

Spécificateurs complexes

Les objets, lorsqu'ils sont spécifiés pour la création par le TPM, ont de nombreux algorithmes à remplir dans les données publiques. Des choses comme le type, le schéma et les détails asymétriques, la taille de la clé, etc. Voici le format général pour spécifier ces données : <type>:<schéma>:<détails-symétriques>

Spécificateurs de type

Cette partie du spécificateur d'algorithme complexe est requise. Les schémas et les détails symétriques restants seront par défaut en fonction du type spécifié et du type de l'objet en cours de création.

•
aes - AES par défaut : aes128
•
aes128<mode> - AES 128 bits avec mode optionnel (ctr|ofb|cbc|cfb|ecb). Si le mode n'est pas spécifié, la valeur par défaut est null.
•
aes192<mode> - Identique à aes128<mode>, sauf pour une taille de clé de 192 bits.
•
aes256<mode> - Identique à aes128<mode>, sauf pour une taille de clé de 256 bits.
•
sm4 - SM4 par défaut : sm4128
•
sm4128 ou sm4_128 <mode> - SM4 128 bits avec mode optionnel (ctr|ofb|cbc|cfb|ecb). Si le mode n'est pas spécifié, la valeur par défaut est null.
•
ecc - Courbe elliptique, par défaut ecc256.
•
ecc192 ou ecc_nist_p192 - Courbe NIST ECC 192 bits
•
ecc224 ou ecc_nist_p224 - Courbe NIST ECC 224 bits
•
ecc256 ou ecc_nist_p256 - Courbe NIST ECC 256 bits
•
ecc384 ou ecc_nist_p384 - Courbe NIST ECC 384 bits
•
ecc521 ou ecc_nist_p521 - Courbe NIST ECC 521 bits
•
ecc_sm2 ou ecc_sm2_p256 - Courbe SM2 256 bits
•
rsa - RSA par défaut : rsa2048
•
rsa1024 - RSA avec une taille de clé de 1024 bits.
•
rsa2048 - RSA avec une taille de clé de 2048 bits.
•
rsa3072 - RSA avec une taille de clé de 3072 bits.
•
rsa4096 - RSA avec une taille de clé de 4096 bits.

Spécificateurs de schéma

Ensuite, il y a un champ optionnel, il peut être sauté.

Les schémas sont généralement des Schémas de signature ou des Schémas de chiffrement asymétrique. La plupart des schémas de signature prennent un algorithme de hachage directement après le schéma de signature. Si l'algorithme de hachage est manquant, il prend par défaut sha256. Certains ne prennent aucun argument, et d'autres en prennent plusieurs.

Spécificateurs de schéma optionnels par hachage

Ces spécificateurs de schéma sont suivis d'un tiret et d'un algorithme de hachage valide, par exemple : oaep-sha256.

Spécificateurs de schéma à options multiples

Ce spécificateur de schéma est suivi d'un compte (taille max UINT16) puis suivi d'un tiret (-) et d'un algorithme de hachage valide. * ecdaa Par exemple, ecdaa4-sha256. Si aucun compte n'est spécifié, il est par défaut à 4.

Spécificateurs de schéma sans option

Ce spécificateur de schéma ne prend AUCUN argument. * rsaes

Spécificateurs de détails symétriques

Ce champ est optionnel et prend par défaut en fonction du type d'objet créé et de ses attributs. Généralement, tout spécificateur Symétrique valide de la liste Type Spécificateurs devrait fonctionner. S'il n'est pas spécifié, les détails symétriques des objets asymétriques sont par défaut aes128cfb.

Exemples

Créer une clé rsa2048 avec un schéma de chiffrement asymétrique rsaes

tpm2_create -C parent.ctx -G rsa2048:rsaes -u key.pub -r key.priv

Créer une clé ecc256 avec un schéma de signature ecdaa avec un compte de 4 et un hachage sha384

/tpm2_create -C parent.ctx -G ecc256:ecdaa4-sha384 -u key.pub -r key.priv algorithmes cryptographiques ALGORITHM.

NAME

tpm2_createek - create an Endorsement Key (EK)

SYNOPSIS

tpm2_createek [OPTIONS] [--policy-file=POLICY] [--auth-policy-file=POLICY]

DESCRIPTION

The tpm2_createek command is used to create an Endorsement Key (EK) which is a primary key used for identifying the TPM. The EK is generated by the TPM and is signed by the manufacturer. The EK is created as a primary key which is loaded into the TPM, and thus it must be in the primary key list. The EK is used to generate other keys, such as Attestation Keys (AKs).

The EK can be created as either a persistent or transient key. When created as a transient key, the key is available only until the next TPM reset. When created as a persistent key, the key will remain in the TPM until explicitly flushed.

The tpm2_createek command returns the public key of the EK, and optionally the private key of the EK. The private key is also used to sign the EK certificate.

The EK can be created with different algorithms. The supported algorithms are RSA and ECC. For ECC, the supported curves are NIST_P192, NIST_P224, NIST_P256, NIST_P384, and NIST_P521.

The EK is created using the TPM's primary seed and the manufacturer's endorsement key certificate. The manufacturer's endorsement key certificate is used to sign the EK, and it is also used to verify the authenticity of the EK. The manufacturer's endorsement key certificate is typically provided by the TPM manufacturer.

The tpm2_createek command can be used to create an EK with different options, such as specifying the algorithm, the key size, and the passwords for the EK.

OPTIONS

A list of options that can be passed to the tpm2_createek command.

-u, --public
Output the public key of the EK to a file.
-r, --private
Output the private key of the EK to a file.
-c, --context
The context object for the primary key.
-p, --password
Password for the EK.
-P, --parent-password
Password for the primary key.
-G, --key-gen
The algorithm to use for the EK. Supported algorithms are rsa, ecc.
-L, --policy
Path to the policy digest file.
-I, --policy-file
Path to the policy file.
-S, --policy-auth-file
Path to the policy auth file.
-l, --policy-digest
Policy digest for the EK.
-f, --force
Force creation of the EK even if it already exists.
-t, --transient
Create a transient EK.
-e, --ecc-curve
The ECC curve to use for the EK. Supported curves are NIST_P192, NIST_P224, NIST_P256, NIST_P384, NIST_P521.
-a, --algorithm
The algorithm to use for the EK. Supported algorithms are rsa, ecc.
-s, --size
The key size for the EK. Supported key sizes are 2048, 3072, 4096 for RSA, and 256, 384, 521 for ECC.

Context Object Format

The context object is a string that specifies the context for the primary key. The context object can be in the following format:

<type>:<value>

The supported types are:

0x81000000
The primary key for the TPM.
0x81000001
The primary key for the storage.
0x81000002
The primary key for the endorsement.
0x81000003
The primary key for the null.

Authorization Formatting

The authorization is a string that specifies the authorization for the primary key. The authorization can be in the following format:

<type>:<value>

The supported types are:

o
Owner authorization.
s
Storage authorization.
e
Endorsement authorization.
n
Null authorization.

Algorithm Specifiers

The algorithm specifier is a string that specifies the algorithm to use for the key. The supported algorithms are:

rsa
RSA algorithm.
ecc
ECC algorithm.

COMMON OPTIONS

Common options shared by most tpm2-* tools.

-h, --help
Print the help message.
-v, --version
Print the version of the tool.
-V, --verbose
Enable verbose output.
-T, --tcti
The Tagged Command Transmission Interface (TCTI) used for communication with the TPM. The TCTI is a string that specifies the TCTI to use. The supported TCTIs are:
-
Use the default TCTI.
-
Use the device TCTI.
-
Use the mssim TCTI.
-
Use the tabrmd TCTI.

The TCTI can be specified with options in the format <tcti-name>:<tcti-option-config>. The options are TCTI specific.

TCTI Configuration

The TCTI or “Transmission Interface” is the communication mechanism with the TPM. TCTIs can be changed for communication with TPMs across different mediums.

To control the TCTI, the tools respect:

1.
The command line option -T or --tcti
2.
The environment variable: TPM2TOOLS_TCTI.

Note: The command line option always overrides the environment variable.

The current known TCTIs are:

•
tabrmd - The resource manager, called tabrmd. Note that tabrmd and abrmd as a tcti name are synonymous.
•
mssim - Typically used for communicating to the TPM software simulator.
•
device - Used when talking directly to a TPM device file.
•
none - Do not initalize a connection with the TPM. Some tools allow for off-tpm options and thus support not using a TCTI. Tools that do not support it will error when attempted to be used without a TCTI connection. Does not support ANY options and MUST BE presented as the exact text of “none”.

The arguments to either the command line option or the environment variable are in the form:

<tcti-name>:<tcti-option-config>

Specifying an empty string for either the <tcti-name> or <tcti-option-config> results in the default being used for that portion respectively.

TCTI Defaults

When a TCTI is not specified, the default TCTI is searched for using dlopen(3) semantics. The tools will search for tabrmd, device and mssim TCTIs IN THAT ORDER and USE THE FIRST ONE FOUND. You can query what TCTI will be chosen as the default by using the -v option to print the version information. The “default-tcti” key-value pair will indicate which of the aforementioned TCTIs is the default.

Custom TCTIs

Any TCTI that implements the dynamic TCTI interface can be loaded. The tools internally use dlopen(3), and the raw tcti-name value is used for the lookup. Thus, this could be a path to the shared library, or a library name as understood by dlopen(3) semantics.

TCTI OPTIONS

This collection of options are used to configure the various known TCTI modules available:

•
device: For the device TCTI, the TPM character device file for use by the device TCTI can be specified. The default is /dev/tpm0.

Example: -T device:/dev/tpm0 or export TPM2TOOLS_TCTI=“device:/dev/tpm0”

•
mssim: For the mssim TCTI, the domain name or IP address and port number used by the simulator can be specified. The default are 127.0.0.1 and 2321.

Example: -T mssim:host=localhost,port=2321 or export TPM2TOOLS_TCTI=“mssim:host=localhost,port=2321”

•
abrmd: For the abrmd TCTI, the configuration string format is a series of simple key value pairs separated by a `,' character. Each key and value string are separated by a `=' character.
•
TCTI abrmd supports two keys:
1.
`bus_name' : The name of the tabrmd service on the bus (a string).
2.
`bus_type' : The type of the dbus instance (a string) limited to `session' and `system'.

Specify the tabrmd tcti name and a config string of bus_name=com.example.FooBar:

\--tcti=tabrmd:bus_name=com.example.FooBar

Specify the default (abrmd) tcti and a config string of bus_type=session:

\--tcti:bus_type=session

NOTE: abrmd and tabrmd are synonymous. the various known TCTI modules.

EXAMPLES

Create an RSA Endorsement Key and make it persistent

tpm2_createek -P abc123 -w abc123 -c 0x81010001 -G rsa -u ek.pub

Create an ECC NIST_P384 Endorsement Key and make it persistent

tpm2_createek -G ecc384 -c 0x81010002

Create a transient Endorsement Key, flush it, and reload it.

Typically, when using the TPM, the interactions occur through a resource manager, like tpm2-abrmd(8). However, when interacting with the TPM directly, this scenario is possible. The below example assumes direct TPM access not brokered by a resource manager. Specifically we will use /dev/tpm0.

tpm2_createek -c ek.ctx -G rsa -u ek.pub -Tdevice:/dev/tpm0 
# Check that it is loaded in transient memory
tpm2_getcap handles-transient -Tdevice:/dev/tpm0 
- 0x80000000
# Flush the handle
tpm2_flushcontext 0x80000000 -Tdevice:/dev/tpm0
# Note that it is flushed
tpm2_getcap handles-transient -Tdevice:/dev/tpm0
<null output>
# Reload it via loadexternal
tpm2_loadexternal -C o -u ek.pub -c ek.ctx -Tdevice:/dev/tpm0
# Check that it is re-loaded in transient memory
tpm2_getcap handles-transient -Tdevice:/dev/tpm0
- 0x80000000
