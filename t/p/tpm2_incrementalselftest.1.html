tpm2_incrementalselftest(1) Manuel des commandes générales tpm2_incrementalselftest(1)

NOM

tpm2_incrementalselftest(1) - Demande de test de la liste d'algorithmes spécifiés

SYNOPSIS

tpm2_incrementalselftest [OPTIONS] LISTE_SPEC_ALG

DESCRIPTION

tpm2_incrementalselftest(1) Demande au TPM d'effectuer des tests sur l'algorithme spécifié et d'imprimer une liste d'algorithmes planifiés pour le test OU restant à tester mais non planifiés.

L'intérêt principal de cette commande est de réduire les délais qui pourraient survenir lors des opérations cryptographiques, car le TPM doit tester l'algorithme avant de l'utiliser.

LISTE_SPEC_ALG

Une liste d'ensembles d'algorithmes séparés par des espaces à tester. Les algorithmes doivent suivre les « normes de formatage », voir la section « Spécificateurs d'algorithmes ». Voir également la section « Algorithmes de hachage pris en charge » pour une liste des algorithmes de hachage pris en charge.

Si LISTE_SPEC_ALG est vide, tpm2_incrementalselftest(1) retournera la liste des algorithmes restants à tester. Veuillez noter que dans ce cas, ces algorithmes ne sont **PAS** planifiés pour être testés.

Si LISTE_SPEC_ALG n'est pas vide, tpm2_incrementalselftest(1) retournera la liste des algorithmes qui restent à tester. Cette liste contient les algorithmes planifiés pour le test **ET** les algorithmes qui restent à tester et qui n'ont pas encore été planifiés. Cela peut se produire par exemple si tous les modes AES n'ont pas encore été testés.

Sortie

La liste des algorithmes à tester (impliquant planifiés) ou restant à tester (non planifiés) est également imprimée au format YAML.

Si aucun des algorithmes spécifiés n'est imprimé, cela signifie qu'ils ont déjà été testés **ET** que ces algorithmes ne seront plus testés.

OPTIONS

Cet outil n'accepte aucune option spécifique à l'outil.

Spécificateurs complexes

Les objets, lorsqu'ils sont spécifiés pour la création par le TPM, ont de nombreux algorithmes à remplir dans les données publiques. Des éléments tels que le type, le schéma et les détails asymétriques, la taille de la clé, etc. Voici le format général pour spécifier ces données : <type>:<schéma>:<détails-symétriques>

Spécificateurs de type

Cette partie du spécificateur d'algorithme complexe est requise. Le schéma et les détails symétriques restants seront par défaut en fonction du type spécifié et du type de l'objet créé.

•
aes - AES par défaut : aes128
•
aes128<mode> - AES 128 bits avec mode optionnel (ctr|ofb|cbc|cfb|ecb). Si le mode n'est pas spécifié, il prend par défaut la valeur null.
•
aes192<mode> - Identique à aes128<mode>, sauf pour une taille de clé de 192 bits.
•
aes256<mode> - Identique à aes128<mode>, sauf pour une taille de clé de 256 bits.
•
sm4 - SM4 par défaut : sm4128
•
sm4128 ou sm4_128 <mode> - SM4 128 bits avec mode optionnel (ctr|ofb|cbc|cfb|ecb). Si le mode n'est pas spécifié, il prend par défaut la valeur null.
•
ecc - Courbe elliptique, par défaut ecc256.
•
ecc192 ou ecc_nist_p192 - Courbe NIST ECC 192 bits
•
ecc224 ou ecc_nist_p224 - Courbe NIST ECC 224 bits
•
ecc256 ou ecc_nist_p256 - Courbe NIST ECC 256 bits
•
ecc384 ou ecc_nist_p384 - Courbe NIST ECC 384 bits
•
ecc521 ou ecc_nist_p521 - Courbe NIST ECC 521 bits
•
ecc_sm2 ou ecc_sm2_p256 - Courbe SM2 256 bits
•
rsa - RSA par défaut : rsa2048
•
rsa1024 - RSA avec une taille de clé de 1024 bits.
•
rsa2048 - RSA avec une taille de clé de 2048 bits.
•
rsa3072 - RSA avec une taille de clé de 3072 bits.
•
rsa4096 - RSA avec une taille de clé de 4096 bits.

Spécificateurs de schéma

Ensuite, il y a un champ optionnel, il peut être ignoré.

Les schémas sont généralement des **schémas de signature** ou des **schémas de chiffrement asymétrique**. La plupart des schémas de signature prennent un algorithme de hachage directement après le schéma de signature. Si l'algorithme de hachage est manquant, il prend par défaut sha256. Certains ne prennent aucun argument et d'autres plusieurs arguments.

Spécificateurs de schéma avec hachage optionnel

Ces spécificateurs de schéma sont suivis d'un tiret et d'un algorithme de hachage valide. Par exemple : oaep-sha256.

Spécificateurs de schéma avec valeur

Ces schémas sont généralement des algorithmes de hachage ou des schémas de signature qui acceptent un paramètre supplémentaire, une valeur. Le format est : <schéma>-<hachage>-<valeur> ou simplement <schéma>-<valeur> : hmac-sha256-256 signifie HMAC avec SHA256 et une taille de clé de 256 bits.

Spécificateurs de détails symétriques

Ce champ est facultatif et est défini par défaut en fonction du type d'objet en cours de création et de ses attributs. Généralement, tout spécificateur Symmetric valide de la liste des spécificateurs de Type devrait fonctionner. S'il n'est pas spécifié, les détails symétriques des objets asymétriques sont par défaut aes128cfb.

Exemples

Créer une clé rsa2048 avec un schéma de chiffrement asymétrique rsaes

tpm2_create -C parent.ctx -G rsa2048:rsaes -u key.pub -r key.priv

Créer une clé ecc256 avec un schéma de signature ecdaa avec un compteur de 4 et un hachage sha384

/tpm2_create -C parent.ctx -G ecc256:ecdaa4-sha384 -u key.pub -r key.priv algorithmes cryptographiques ALGORITHM.

Cette collection d'options est commune à de nombreux programmes et fournit des informations que de nombreux utilisateurs peuvent attendre.

C'est le même comportement si l'argument d'option "man" est spécifié, cependant si "man" est explicitement demandé, l'outil fournira les erreurs de man sur stderr. Si l'option "no-man" est spécifiée, ou si le paginator de manuel échoue, les options courtes seront affichées sur stdout.

Pour utiliser avec succès la fonctionnalité de manuel, il faut que les manuels soient installés ou sur MANPATH. Voir man(1) pour plus de détails.

•
-v, --version : Affiche les informations de version pour cet outil, les tctis supportés et quitte.
•
-V, --verbose : Augmente les informations que l'outil imprime sur la console pendant son exécution. Lors de l'utilisation de cette option, le fichier et le numéro de ligne sont imprimés.
•
-Q, --quiet : Silence la sortie normale de l'outil sur stdout.
•
-Z, --enable-errata : Active l'application des corrections d'errata. Utile si une correction d'errata doit être appliquée aux commandes envoyées au TPM. La définition de la variable d'environnement TPM2TOOLS_ENABLE_ERRATA est équivalente.
•
-R, --autoflush : Active l'autoflush pour les objets transitoires créés par la commande. Si un objet parent est chargé à partir d'un fichier de contexte, l'objet parent transitoire sera également vidé. L'autoflush peut également être activé si la variable d'environnement TPM2TOOLS_AUTOFLUSH est définie sur yes ou true. informations que de nombreux utilisateurs peuvent attendre.

Configuration TCTI

Le TCTI ou "Interface de Transmission" est le mécanisme de communication avec le TPM. Les TCTIs peuvent être changés pour la communication avec les TPMs sur différents supports.

Pour contrôler le TCTI, les outils respectent :

1.
L'option de ligne de commande -T ou --tcti
2.
La variable d'environnement : TPM2TOOLS_TCTI.

Note : L'option de ligne de commande remplace toujours la variable d'environnement.

Les TCTIs actuellement connus sont :

•
tabrmd - Le gestionnaire de ressources, appelé tabrmd. Notez que tabrmd et abrmd en tant que nom tcti sont synonymes.
•
mssim - Généralement utilisé pour communiquer avec le simulateur logiciel TPM.
•
device - Utilisé lors de la communication directe avec le fichier de périphérique TPM.
•
none - N'initialise pas de connexion avec le TPM. Certains outils permettent des options hors TPM et supportent donc de ne pas utiliser de TCTI. Les outils qui ne le supportent pas généreront une erreur lorsqu'ils seront utilisés sans connexion TCTI. Ne supporte AUCUNE option et DOIT être présenté comme le texte exact de "none".

Les arguments de l'option de ligne de commande ou de la variable d'environnement sont sous la forme :

<tcti-name>:<tcti-option-config>

La spécification d'une chaîne vide pour <tcti-name> ou <tcti-option-config> entraîne l'utilisation de la valeur par défaut pour cette partie respectivement.

Valeurs par défaut TCTI

Lorsqu'un TCTI n'est pas spécifié, le TCTI par défaut est recherché en utilisant la sémantique de dlopen(3). Les outils rechercheront tabrmd, device et mssim TCTIs DANS CET ORDRE et UTILISERONT LE PREMIER TROUVÉ. Vous pouvez interroger quel TCTI sera choisi par défaut en utilisant l'option -v pour afficher les informations de version. La paire clé-valeur "default-tcti" indiquera lequel des TCTIs susmentionnés est par défaut.

TCTIs personnalisés

Tout TCTI qui implémente l'interface TCTI dynamique peut être chargé. Les outils utilisent en interne dlopen(3), et la valeur brute tcti-name est utilisée pour la recherche. Ainsi, cela pourrait être un chemin vers la bibliothèque partagée, ou un nom de bibliothèque tel que compris par la sémantique de dlopen(3).

OPTIONS TCTI

Cette collection d'options est utilisée pour configurer les divers modules TCTI connus disponibles :

•
device : Pour le TCTI device, le fichier de périphérique caractère TPM à utiliser par le TCTI device peut être spécifié. La valeur par défaut est /dev/tpm0.

Exemple : -T device:/dev/tpm0 ou export TPM2TOOLS_TCTI=“device:/dev/tpm0”

•
mssim : Pour le TCTI mssim, le nom de domaine ou l'adresse IP et le port utilisés par le simulateur peuvent être spécifiés. Les valeurs par défaut sont 127.0.0.1 et 2321.

Exemple : -T mssim:host=localhost,port=2321 ou export TPM2TOOLS_TCTI=“mssim:host=localhost,port=2321”

•
abrmd : Pour le TCTI abrmd, le format de la chaîne de configuration est une série de paires clé-valeur simples séparées par un caractère ','. Chaque chaîne de clé et de valeur est séparée par un caractère '='.
•
Le TCTI abrmd supporte deux clés :
1.
`bus_name' : Le nom du service tabrmd sur le bus (une chaîne de caractères).
2.
`bus_type' : Le type de l'instance dbus (une chaîne de caractères) limitée à `session' et `system'.

Spécifier le nom du TCTI tabrmd et une chaîne de configuration de bus_name=com.example.FooBar :

\--tcti=tabrmd:bus_name=com.example.FooBar

Spécifier le TCTI par défaut (abrmd) et une chaîne de configuration de bus_type=session :

\--tcti:bus_type=session

NOTE : abrmd et tabrmd sont synonymes. les différents modules TCTI connus.

EXEMPLES

Demander le test de l'algorithme RSA

tpm2_incrementalselftest rsa

Demander le test de plusieurs algorithmes

tpm2_incrementalselftest rsa ecc xor aes cbc

NOTES

La suite d'algorithmes spécifiée peut impliquer soit le test de la combinaison, soit la suite complète, selon l'implémentation du fabricant du TPM.

par ex. : Un TPM pourrait seulement tester AES avec le mode CTR si "aes ctr" est spécifié. Un autre pourrait également tester la liste complète des modes AES ET tester le mode CTR.

Si un algorithme a déjà été testé, cette commande ne permettra pas de réexécuter le test. Seule l'émission de tpm2_selftest(1) en mode test complet activé forcera le re-test.

Retours

Les outils peuvent retourner l'un des codes suivants :

•
0 - Succès.
•
1 - Erreur générale non spécifique.
•
2 - Erreur de gestion des options.
•
3 - Erreur d'authentification.
•
4 - Erreur liée au TCTI.
•
5 - Schéma non supporté. Applicable à tpm2_testparams.

tpm2_incrementalselftest(1)

NAME

tpm2_incrementalselftest – perform an incremental self-test on the TPM.

SYNOPSIS

tpm2_incrementalselftest [OPTIONS]—perform an incremental self-test on the TPM.

DESCRIPTION

The tpm2_incrementalselftest command is used to perform an incremental self-test on the TPM. This command will perform a subset of the TPM self-test commands, and update the TPM state accordingly. This is useful for systems that may not have the full time required to complete the entire TPM self-test during the boot process.

ALG_SPEC_LIST

This is a list of algorithms that the TPM supports. The list is provided as a comma separated string. The following table details the supported algorithms:

TPM_ALG_SHA1
SHA-1 hash algorithm.
TPM_ALG_SHA256
SHA-256 hash algorithm.
TPM_ALG_SHA384
SHA-384 hash algorithm.
TPM_ALG_SHA512
SHA-512 hash algorithm.
TPM_ALG_NULL
Null algorithm.
TPM_ALG_RSA
RSA asymmetric algorithm.
TPM_ALG_DES
DES symmetric algorithm.
TPM_ALG_3DES
3DES symmetric algorithm.
TPM_ALG_AES
AES symmetric algorithm.
TPM_ALG_KEYEDHASH
Keyed hash algorithm.
TPM_ALG_SM3_256
SM3-256 hash algorithm.
TPM_ALG_SM4
SM4 symmetric algorithm.
TPM_ALG_RSASSA
RSA signature-only algorithm.
TPM_ALG_PSS
RSA-PSS signature algorithm.
TPM_ALG_ECDSA
ECDSA signature algorithm.
TPM_ALG_ECDAA
ECDAA signature algorithm.
TPM_ALG_SM2
SM2 signature algorithm.
TPM_ALG_ECSCHNORR
ECSCHNORR signature algorithm.
TPM_ALG_HMAC
HMAC algorithm.
TPM_ALG_ANY
Any algorithm.

Output

The command returns the result of the self-test. The result is a bitmask indicating which parts of the self-test passed or failed. The specific meaning of the bits in the returned value depends on the TPM specification.

OPTIONS

A list of options that can be used with the tpm2_incrementalselftest command.

-h, --help
Prints the help information.
-v, --version
Prints the version information.
-c, --cancel
Cancels the ongoing incremental self-test.
-f, --force
Forces the TPM to start a new incremental self-test, even if one is already in progress.
-t, --timeout <ms>
Specifies the timeout in milliseconds for the self-test.
-l, --alg_spec_list <list>
Specifies a comma-separated list of algorithms to include in the incremental self-test. If not specified, all supported algorithms will be tested.

Algorithm Specifiers

The -l option accepts a comma-separated list of algorithm specifiers. These specifiers correspond to the TPM algorithms supported by the TPM. For a list of supported algorithms, see the ALG_SPEC_LIST section.

COMMON OPTIONS

These options are common to most tpm2-* tools.

-T, --tcti <name>[:<value>,...]
Specifies the Tagged Command Transmission Interface (TCTI) to use for communication with the TPM. The default TCTI is the `device` TCTI which uses the TPM device specified by the TPM2_DEVICE_PATH environment variable (defaulting to /dev/tpm0).

TCTI Configuration

The TCTI can be configured using a colon-separated list of key-value pairs. The available options depend on the TCTI implementation. Some common TCTI options include:

TCTI OPTIONS

device
Use the device TCTI. Options:
  • device_num: The device number to use (e.g., 0 for /dev/tpm0).
  • device_path: The path to the TPM device (e.g., /dev/tpmrm0).
mssim
Use the mssim TCTI (for Microsoft simulator). Options:
  • host: The host address of the simulator.
  • port: The port number of the simulator.
socket
Use the socket TCTI. Options:
  • host: The host address to connect to.
  • port: The port number to connect to.
stdin
Use the stdin TCTI. No options.
passthrough
Use the passthrough TCTI. No options.

EXAMPLES

To perform a full incremental self-test:

$ tpm2_incrementalselftest

To perform an incremental self-test including only SHA-1 and RSA algorithms:

$ tpm2_incrementalselftest -l SHA1,RSA

To cancel an ongoing incremental self-test:

$ tpm2_incrementalselftest -c

NOTES

The incremental self-test functionality and the specific meaning of the returned values are dependent on the TPM specification and implementation. Refer to the TPM specification for details.

Returns

Returns 0 on success, 1 on failure.
