tpm2_create(1) Manuel des commandes générales tpm2_create(1)

NOM

tpm2_create(1) - Crée un objet enfant.

SYNTAXE

tpm2_create [OPTIONS]

DESCRIPTION

tpm2_create(1) - Crée un objet enfant. L'objet peut être soit une clé, soit un objet de scellage. Un objet de scellage permet de sceller des données utilisateur au TPM, avec une taille maximale de 128 octets. De plus, il chargera l'objet créé si -c est spécifié.

OPTIONS

Ces options permettent de créer l'entité TPM :

•
-C, --parent-context=OBJET :

Le parent de l'objet à créer.

•
-P, --parent-auth=AUTH :

La valeur d'authentification de l'objet parent spécifié avec -C.

•
-p, --key-auth=AUTH :

La valeur d'authentification pour l'objet créé.

•
-g, --hash-algorithm=ALGORITHME :

L'algorithme de hachage pour générer le nom de l'objet. Ceci est optionnel et vaut par défaut sha256 lorsqu'il n'est pas spécifié.

•
-G, --key-algorithm=ALGORITHME :

L'algorithme de clé associé à cet objet. Il vaut par défaut « rsa » s'il n'est pas spécifié.

•
-a, --attributes=ATTRIBUTS :

Les attributs de l'objet, optionnel. La valeur par défaut pour les objets créés est :

TPMA_OBJECT_SIGN_ENCRYPT|TPMA_OBJECT_DECRYPT|TPMA_OBJECT_FIXEDTPM| TPMA_OBJECT_FIXEDPARENT|TPMA_OBJECT_SENSITIVEDATAORIGIN| TPMA_OBJECT_USERWITHAUTH

Lorsque -i est spécifié pour le scellage, TPMA_OBJECT_SIGN_ENCRYPT et TPMA_OBJECT_DECRYPT sont retirés de l'ensemble d'attributs par défaut. L'algorithme est défini de manière à ce que l'objet ne soit utilisable que pour le scellage et le déscellage. C'est-à-dire qu'on ne peut pas utiliser un objet pour le scellage et les opérations cryptographiques.

Lorsque -L est spécifié pour ajouter des informations d'authentification basées sur une politique ET qu'aucun mot de passe texte n'est spécifié, l'attribut TPMA_OBJECT_USERWITHAUTH est effacé, sauf si un choix explicite est fait en définissant l'attribut avec l'option -a. Cela empêche la création d'objets avec un modèle d'authentification involontaire où l'utilisateur avait l'intention d'appliquer une politique mais a accidentellement créé un objet avec une authentification vide qui peut être utilisée à la place de l'authentification par politique.

•
-i, --sealing-input=FICHIER ou STDIN :

Le fichier de données à sceller, optionnel. Si le fichier est -, lire depuis stdin. Lorsque des données de scellage sont utilisées, seul l'algorithme TPM_ALG_KEYEDHASH avec un schéma NULL est autorisé. Ainsi, -G ne peut pas être spécifié.

•
-L, --policy=FICHIER ou CHAINE_HEX :

Le fichier de politique d'entrée ou une chaîne hexadécimale, optionnel.

•
-u, --public=FICHIER :

Le fichier de sortie contenant la partie publique de l'objet créé, optionnel.

•
-r, --private=FICHIER :

Le fichier de sortie contenant la partie sensible de l'objet, optionnel. # Détails de la protection

Les objets qui peuvent sortir du TPM doivent être protégés (confidentialité et intégrité). Par exemple, les objets transitoires nécessitent que les données protégées par le TPM (clé ou matériau de scellage) soient stockées en dehors du TPM. C'est ce que l'on observe avec des outils comme tpm2_create(1), où l'option -r génère ces données protégées. Ce blob contient les parties sensibles de l'objet. Les parties sensibles de l'objet sont protégées par l'objet parent, en utilisant les détails de chiffrement symétrique du parent pour chiffrer les données sensibles et le hachage de celles-ci.

Des détails approfondis peuvent être trouvés dans les sections 23 de :

•
https://trustedcomputinggroup.org/wp-content/uploads/TPM-Rev-2.0-Part-1-Architecture-01.38.pdf

Notamment, la figure 20 est pertinente, même si elle fait spécifiquement référence aux blobs de duplication, le processus est identique.

Si la sortie provient de tpm2_duplicate(1), la sortie sera légèrement différente, comme décrit intégralement dans la section 23.

•
-c, --key-context=FICHIER :

Le fichier de sortie contenant le contexte de la clé, optionnel. Le contexte de clé est analogue au fichier de contexte produit par tpm2_load(1), cependant il est généré via une commande tpm2_createloaded(1). Cette option peut être utilisée pour éviter les séquences de commandes normales tpm2_create(1) et tpm2_load(1) et tout faire en une seule commande, de manière atomique.

•
--creation-data=FICHIER :

Un fichier de sortie optionnel qui enregistre les données de création pour la certification.

•
--template-data=FICHIER :

Un fichier de sortie optionnel qui enregistre les données du modèle de clé (TPM2B_PUBLIC) à utiliser dans tpm2_policytemplate.

•
-t, --creation-ticket=FICHIER :

Un fichier de sortie optionnel qui enregistre le ticket de création pour la certification.

•
-d, --creation-hash=FICHIER :

Un fichier de sortie optionnel qui enregistre le hachage de création pour la certification.

•
-q, --outside-info=CHAINE_HEX_OU_FICHIER :

Une chaîne hexadécimale optionnelle ou un chemin pour ajouter des données uniques aux données de création. Notez que cela ne contribue pas à la création d'un objet statistiquement unique.

•
-l, --pcr-list=PCR :

La liste des banques PCR et des identifiants des PCR sélectionnés pour chaque banque à inclure dans les données de création pour la certification.

•
--cphash=FICHIER

Chemin du fichier pour enregistrer le hachage des paramètres de la commande. Ceci est communément appelé cpHash. NOTE : Lorsque cette option est sélectionnée, l'outil n'exécutera pas réellement la commande, il retournera simplement un cpHash.

•
--rphash=FICHIER

Chemin du fichier pour enregistrer le hachage des paramètres de réponse. Ceci est communément appelé rpHash.

•
-S, --session=FICHIER :

La session créée à l'aide de tpm2_startauthsession. Plusieurs de ceux-ci peuvent être spécifiés. Par exemple, vous pouvez avoir une session pour l'audit et une autre pour le chiffrement/déchiffrement des paramètres.

•
-f, --format :

Sélection du format pour le fichier de sortie de la clé publique. `tss` (par défaut) produira un blob binaire conforme à la spécification TPM 2.0. `pem` produira une clé publique encodée PEM compatible avec OpenSSL. `der` produira une clé publique encodée DER compatible avec OpenSSL. `tpmt` produira un blob binaire de la structure TPMT_PUBLIC référencée par les spécifications TPM 2.0.

Format de la clé publique.

•
-o, --output=FICHIER :

Le chemin du fichier de sortie, enregistrant la partie publique de l'objet.

Références

Format de l'objet contexte

Ce site n'est en aucun cas associé à Arch Linux ni affilié à ce projet. Le contenu est uniquement une traduction des pages de manuel d'Arch publiées sur man.archlinux.org.

Format d'Objet

Le type d'un objet de contexte, qu'il s'agisse d'une poignée ou d'un nom de fichier, est déterminé selon la logique suivante, *dans l'ordre* :

•
Si l'argument est un chemin de fichier, le fichier est chargé comme un objet transitoire TPM restauré.
•
Si l'argument correspond à un préfixe d'un des éléments suivants :
•
owner : la hiérarchie propriétaire
•
platform : la hiérarchie de plateforme
•
endorsement : la hiérarchie d'approbation
•
lockout : l'objet persistant de contrôle de verrouillage
•
Si l'argument peut être chargé comme un nombre, il sera traité comme une poignée, par exemple 0x81010013, et utilisé directement._OBJECT_.

Formatage de l'Authorization

L'autorisation d'utilisation d'un objet dans TPM2.0 peut prendre 3 formes différentes : 1. Mot de passe 2. HMAC 3. Sessions

NOTE : « Les autorisations utilisent par défaut le MOT DE PASSE VIDE lorsqu'elles ne sont pas spécifiées ».

Mots de passe

Les mots de passe sont interprétés sous les formes suivantes à l'aide d'identificateurs de préfixes.

Note : Par défaut, les mots de passe sont supposés être sous forme de chaîne lorsqu'ils n'ont pas de préfixe.

Chaîne de caractères

Un mot de passe sous forme de chaîne, spécifié par le préfixe « str: » ou son absence (chaîne brute sans préfixe), n'est pas interprété et est directement utilisé pour l'autorisation.

Exemples

foobar
str:foobar

Chaîne hexadécimale

Un mot de passe sous forme de chaîne hexadécimale, spécifié par le préfixe « hex: », est converti d'une forme hexadécimale en une forme de tableau d'octets, permettant ainsi des mots de passe avec des caractères non imprimables et/ou peu pratiques pour le terminal.

Exemple

hex:1122334455667788

Fichier

Un mot de passe basé sur un fichier, spécifié par le préfixe « file: », doit être le chemin d'un fichier contenant le mot de passe à lire par l'outil, ou un « - » pour utiliser stdin. Le stockage des mots de passe dans des fichiers empêche les fuites d'informations, les mots de passe passés comme options pouvant être lus depuis la liste des processus ou les fonctions courantes d'historique du shell.

Exemples

# pour utiliser stdin et être invité
file:-
# pour utiliser un fichier depuis un chemin
file:chemin/vers/fichier/motdepasse
# pour faire un écho d'un mot de passe via stdin :
echo foobar | tpm2_tool -p file:-
# pour utiliser un here-string bash via stdin :
tpm2_tool -p file:- <<< foobar

Sessions

Lors de l'utilisation d'une session de stratégie pour autoriser l'utilisation d'un objet, préfixez l'argument de l'option avec le mot-clé session. Indiquez ensuite un chemin vers un fichier de session qui a été créé avec tpm2_startauthsession(1). Facultativement, si la session nécessite une valeur d'authentification à envoyer avec la poignée de session (par exemple, un mot de passe de stratégie), ajoutez un + suivi d'une chaîne telle que décrite dans la section Mots de passe.

Exemples

Pour utiliser un fichier de contexte de session appelé session.ctx.

session:session.ctx

Pour utiliser un fichier de contexte de session appelé session.ctx ET envoyer la valeur d'authentification mypassword.

session:session.ctx+mypassword

Pour utiliser un fichier de contexte de session appelé session.ctx ET envoyer la valeur d'authentification HEX 0x11223344.

session:session.ctx+hex:11223344

Autorisations PCR

Vous pouvez satisfaire une stratégie PCR en utilisant le préfixe « pcr: » et le mini-langage PCR. Le mini-langage PCR est le suivant : <spécificateur-pcr>=<fichier-pcr-brut>

Le spécificateur PCR est documenté dans la section « Spécificateurs de banque PCR ».

Le fichier-pcr-brut est un argument facultatif qui contient la sortie des contenus PCR bruts tels que retournés par tpm2_pcrread(1).

Spécificateurs de banque PCR

Exemples

Pour satisfaire une stratégie PCR de sha256 sur les banques 0, 1, 2 et 3, utilisez un spécificateur de :

pcr:sha256:0,1,2,3

spécifiant AUTH.

Spécificateurs complexes

Les objets, lorsqu'ils sont spécifiés pour la création par le TPM, ont de nombreux algorithmes à remplir dans les données publiques. Des choses comme le type, le schéma et les détails asymétriques, la taille de la clé, etc. Voici le format général pour spécifier ces données : <type>:<schéma>:<détails-symétriques>

Spécificateurs de type

Cette partie du spécificateur d'algorithme complexe est obligatoire. Les détails restants du schéma et du chiffrement symétrique seront par défaut en fonction du type spécifié et du type de l'objet en cours de création.

•
aes - AES par défaut : aes128
•
aes128<mode> - AES 128 bits avec mode optionnel (ctr|ofb|cbc|cfb|ecb). Si le mode n'est pas spécifié, il prend par défaut la valeur null.
•
aes192<mode> - Idem que aes128<mode>, sauf pour une taille de clé de 192 bits.
•
aes256<mode> - Idem que aes128<mode>, sauf pour une taille de clé de 256 bits.
•
sm4 - SM4 par défaut : sm4128
•
sm4128 ou sm4_128 <mode> - SM4 128 bits avec mode optionnel (ctr|ofb|cbc|cfb|ecb). Si le mode n'est pas spécifié, il prend par défaut la valeur null.
•
ecc - Courbe elliptique, prend par défaut ecc256.
•
ecc192 ou ecc_nist_p192 - Courbe NIST ECC 192 bits
•
ecc224 ou ecc_nist_p224 - Courbe NIST ECC 224 bits
•
ecc256 ou ecc_nist_p256 - Courbe NIST ECC 256 bits
•
ecc384 ou ecc_nist_p384 - Courbe NIST ECC 384 bits
•
ecc521 ou ecc_nist_p521 - Courbe NIST ECC 521 bits
•
ecc_sm2 ou ecc_sm2_p256 - Courbe SM2 256 bits
•
rsa - RSA par défaut : rsa2048
•
rsa1024 - RSA avec une taille de clé de 1024 bits.
•
rsa2048 - RSA avec une taille de clé de 2048 bits.
•
rsa3072 - RSA avec une taille de clé de 3072 bits.
•
rsa4096 - RSA avec une taille de clé de 4096 bits.

Spécificateurs de Schéma

Ensuite, il y a un champ facultatif, il peut être ignoré.

Les schémas sont généralement des Schémas de Signature ou des Schémas de Chiffrement Asymétrique. La plupart des schémas de signature prennent un algorithme de hachage directement après le schéma de signature. Si l'algorithme de hachage est manquant, il utilise par défaut sha256. Certains ne prennent aucun argument, et certains en prennent plusieurs.

Spécificateurs de Schéma Optionnels de Hachage

Spécificateurs de Schéma à Options Multiples

Ce spécificateur de schéma est suivi d'un nombre (taille maximale UINT16) puis d'un trait d'union (-) et d'un algorithme de hachage valide. * ecdaa Par exemple, ecdaa4-sha256. Si aucun nombre n'est spécifié, il utilise par défaut 4.

Spécificateurs de Schéma Sans Option

Ce spécificateur de schéma ne prend AUCUN argument. * rsaes

Spécificateurs de Détails Symétriques

Ce champ est facultatif et utilise par défaut des valeurs basées sur le type d'objet créé et ses attributs. Généralement, tout spécificateur Symétrique valide de la liste des spécificateurs de Type devrait fonctionner. S'il n'est pas spécifié, les détails symétriques d'un objet asymétrique utilisent par défaut aes128cfb.

Exemples

Créer une clé rsa2048 avec un schéma de chiffrement asymétrique rsaes

tpm2_create -C parent.ctx -G rsa2048:rsaes -u key.pub -r key.priv

Créer une clé ecc256 avec un schéma de signature ecdaa avec un nombre de 4 et un hachage sha384

/tpm2_create -C parent.ctx -G ecc256:ecdaa4-sha384 -u key.pub -r key.priv algorithmes cryptographiques ALGORITHM.

Attributs d'Objet

Les attributs d'objet sont utilisés pour contrôler diverses propriétés des objets créés. Lorsqu'ils sont spécifiés comme une option, le masque brut de champ binaire ou les « noms conviviaux » peuvent être utilisés. Les valeurs peuvent être trouvées dans le Tableau 31, Partie 2, de la spécification TPM2.0, qui peut être trouvée ici :

https://trustedcomputinggroup.org/wp-content/uploads/TPM-Rev-2.0-Part-2-Structures-01.38.pdf

Les noms conviviaux sont calculés en prenant le champ de nom du tableau 31 et en supprimant le préfixe TPMA_OBJECT_ et en mettant le résultat en minuscules. Ainsi, TPMA_OBJECT_FIXEDTPM devient fixedtpm. Les noms conviviaux peuvent être joints en utilisant l'opérateur OU binaire « | ».

Par exemple, pour définir les champs TPMA_OBJECT_FIXEDTPM, TPMA_OBJECT_NODA et TPMA_OBJECT_SIGN_ENCRYPT, l'argument serait :

fixedtpm|noda|sign spécifiant les attributs d'objet ATTRIBUTES.

Configuration TCTI

Le TCTI, ou « Interface de Transmission », est le mécanisme de communication avec le TPM. Les TCTI peuvent être modifiés pour communiquer avec des TPM sur différents supports.

Pour contrôler le TCTI, les outils respectent :

1.
L'option de ligne de commande -T ou --tcti
2.
La variable d'environnement : TPM2TOOLS_TCTI.

Note : L'option de ligne de commande a toujours priorité sur la variable d'environnement.

Les TCTI actuellement connus sont :

•
tabrmd - Le gestionnaire de ressources, appelé tabrmd. Notez que tabrmd et abrmd en tant que nom de tcti sont synonymes.
•
mssim - Généralement utilisé pour communiquer avec le simulateur logiciel TPM.
•
device - Utilisé pour parler directement au fichier de périphérique TPM.
•
none - N'initialise pas de connexion avec le TPM. Certains outils permettent des options hors-tpm et supportent donc de ne pas utiliser de TCTI. Les outils qui ne le supportent pas généreront une erreur lorsqu'ils tenteront d'être utilisés sans connexion TCTI. Ne supporte AUCUNE option et DOIT être présenté comme le texte exact de « none ».

Les arguments de l'option de ligne de commande ou de la variable d'environnement sont sous la forme :

<tcti-name>:<tcti-option-config>

Spécifier une chaîne vide pour le <tcti-name> ou le <tcti-option-config> utilise la valeur par défaut pour cette partie respective.

Valeurs par Défaut TCTI

Lorsqu'un TCTI n'est pas spécifié, le TCTI par défaut est recherché selon la sémantique de dlopen(3). Les outils rechercheront tabrmd, device et mssim DANS CET ORDRE et utiliseront le PREMIER TROUVÉ. Vous pouvez interroger quel TCTI sera choisi par défaut en utilisant l'option -v pour afficher les informations de version. La paire clé-valeur « default-tcti » indiquera quel TCTI parmi ceux mentionnés ci-dessus est le défaut.

TCTIs Personnalisés

Tout TCTI implémentant l'interface TCTI dynamique peut être chargé. Les outils utilisent en interne dlopen(3), et la valeur brute tcti-name est utilisée pour la recherche. Ainsi, cela pourrait être un chemin vers la bibliothèque partagée, ou un nom de bibliothèque tel que compris par la sémantique de dlopen(3).

OPTIONS TCTI

Cette collection d'options est utilisée pour configurer les divers modules TCTI connus disponibles :

•
device : Pour le TCTI `device`, le fichier périphérique TPM à utiliser par le TCTI `device` peut être spécifié. La valeur par défaut est /dev/tpm0.

Exemple : -T device:/dev/tpm0 ou export TPM2TOOLS_TCTI=“device:/dev/tpm0”

•
mssim : Pour le TCTI `mssim`, le nom de domaine ou l'adresse IP et le numéro de port utilisés par le simulateur peuvent être spécifiés. Les valeurs par défaut sont 127.0.0.1 et 2321.

Exemple : -T mssim:host=localhost,port=2321 ou export TPM2TOOLS_TCTI=“mssim:host=localhost,port=2321”

•
abrmd : Pour le TCTI `abrmd`, le format de la chaîne de configuration est une série de paires clé-valeur simples séparées par un caractère `,`. Chaque clé et valeur sont séparées par un caractère `=`.
•
Le TCTI abrmd prend en charge deux clés :
1.
`bus_name' : Le nom du service tabrmd sur le bus (une chaîne de caractères).
2.
`bus_type' : Le type de l'instance dbus (une chaîne de caractères) limitée à `session' et `system'.

Spécifier le nom du TCTI tabrmd et une chaîne de configuration de bus_name=com.example.FooBar :

\--tcti=tabrmd:bus_name=com.example.FooBar

Spécifier le TCTI par défaut (abrmd) et une chaîne de configuration de bus_type=session :

\--tcti:bus_type=session

NOTE : abrmd et tabrmdsont synonymes. les divers modules TCTI connus.

EXEMPLES

Configuration

Afin de créer un objet, nous devons d'abord créer une clé primaire comme son parent.

tpm2_createprimary -c primary.ctx

Créer un objet

Ceci créera un objet en utilisant toutes les valeurs par défaut et stockera les parties privées et publiques scellées par le TPM aux chemins spécifiés par -u et -r respectivement. L'outil utilise une clé RSA par défaut.

tpm2_create -C primary.ctx -u obj.pub -r obj.priv

Sceller des données au TPM

En dehors des objets clés, le TPM permet de sceller de petites quantités de données spécifiées par l'utilisateur au TPM.

echo "mes données scellées" > seal.dat
tpm2_create -C primary.ctx -i seal.dat -u obj.pub -r obj.priv

Créer un objet clé EC et le charger dans le TPM

Normalement, lors de la création d'un objet, seules les parties publique et privée de l'objet sont retournées et l'appelant doit utiliser tpm2_load(1) pour charger ces parties publique et privée dans le TPM avant de pouvoir utiliser l'objet. Cependant, cela peut être accompli dans cette commande également, lorsque le TPM le supporte. Vous pouvez vérifier que votre TPM supporte cette fonctionnalité en vérifiant que la commande tpm2_getcap(1) retourne TPM2_CC_CreateLoaded dans l'ensemble des commandes. Si votre TPM ne supporte pas TPM2_CC_CreateLoaded, une erreur de code de commande non supporté sera retournée. Si ce n'est pas supporté, il faut utiliser tpm2_load(1). Voir ce manpage pour les détails de son utilisation.

tpm2_create -C primary.ctx -G ecc -u obj.pub -r obj.priv -c ecc.ctx

Créer un objet et obtenir la clé publique sous forme de fichier PEM

Ceci créera un objet en utilisant toutes les valeurs par défaut, mais affichera également la clé publique sous forme de fichier PEM compatible avec des outils tels qu'OpenSSL et tout ce qui supporte les fichiers PEM.

tpm2_create -C primary.ctx -u obj.pub -r obj.priv -f pem -o obj.pem

Créer une clé de signature RSA restreinte

Pour une clé de signature restreinte, le schéma et null pour l'algorithme symétrique doivent être spécifiés.

tpm2_create -C primary.ctx -Grsa2048:rsapss:null  \
    -a "fixedtpm|fixedparen|sensitivedataorigin|userwithauth|restricted|sign" \
    -r obj.priv -u obj.pub

Retour

Les outils peuvent retourner l'un des codes suivants :

•
0 - Succès.
•
1 - Erreur générale non spécifique.
•
2 - Erreur de gestion des options.
•
3 - Erreur d'authentification.
•
4 - Erreur liée au TCTI.
•
5 - Schéma non supporté. Applicable à tpm2_testparams.
