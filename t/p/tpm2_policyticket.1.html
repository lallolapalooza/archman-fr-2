tpm2_policyticket(1) Manuel des commandes générales tpm2_policyticket(1)

NOM

tpm2_policyticket(1) - Permet l'autorisation de politique en vérifiant un ticket représentant une autorisation validée avec une date d'expiration associée.

SYNTAXE

tpm2_policyticket [OPTIONS]

DESCRIPTION

tpm2_policyticket(1) - Permet l'autorisation de politique en vérifiant un ticket représentant une autorisation validée avec une date d'expiration associée.

OPTIONS

•
-L, --policy=FICHIER:

Fichier pour enregistrer le résumé de politique composé.

•
-S, --session=FICHIER:

Le fichier de session de politique généré via l'option -S de tpm2_startauthsession(1).

•
-n, --name=FICHIER:

Nom de l'objet qui a validé l'autorisation.

•
--ticket=FICHIER:

Le fichier ticket pour enregistrer la structure du ticket d'autorisation.

•
--timeout=FICHIER:

Le chemin du fichier pour enregistrer la structure de délai d'expiration retournée.

•
-q, --qualification=FICHIER_OU_CHAINE_HEX:

Optionnel, les données de qualification de politique que le signataire peut choisir d'inclure dans la signature. Peut être une chaîne hexadécimale ou un chemin.

Configuration TCTI

Le TCTI ou “Transmission Interface” est le mécanisme de communication avec le TPM. Les TCTIs peuvent être modifiés pour la communication avec des TPMs via différents supports.

Pour contrôler le TCTI, les outils respectent :

1.
L'option de ligne de commande -T ou --tcti
2.
La variable d'environnement : TPM2TOOLS_TCTI.

Note : L'option de ligne de commande remplace toujours la variable d'environnement.

Les TCTIs actuellement connus sont :

•
tabrmd - Le gestionnaire de ressources, appelé tabrmd. Notez que tabrmd et abrmd en tant que nom de tcti sont synonymes.
•
mssim - Généralement utilisé pour communiquer avec le simulateur logiciel de TPM.
•
device - Utilisé lors de la communication directe avec un fichier de périphérique TPM.
•
none - Ne pas initialiser de connexion avec le TPM. Certains outils permettent des options hors TPM et prennent donc en charge la non-utilisation d'un TCTI. Les outils qui ne le prennent pas en charge généreront une erreur lorsqu'ils seront utilisés sans connexion TCTI. Ne prend pas en charge AUCUNE option et DOIT ÊTRE présenté comme le texte exact de “none”.

Les arguments de l'option de ligne de commande ou de la variable d'environnement sont sous la forme :

<nom-tcti>:<config-option-tcti>

Spécifier une chaîne vide pour <nom-tcti> ou <config-option-tcti> utilise la valeur par défaut pour cette partie respectivement.

Défauts TCTI

Lorsqu'un TCTI n'est pas spécifié, le TCTI par défaut est recherché en utilisant la sémantique de dlopen(3). Les outils rechercheront tabrmd, device et mssim TCTIs DANS CET ORDRE et UTILISERONT LE PREMIER TROUVÉ. Vous pouvez interroger quel TCTI sera choisi par défaut en utilisant l'option -v pour afficher les informations de version. La paire clé-valeur “default-tcti” indiquera lequel des TCTIs mentionnés ci-dessus est le défaut.

TCTIs Personnalisés

Tout TCTI qui implémente l'interface TCTI dynamique peut être chargé. Les outils utilisent en interne dlopen(3), et la valeur brute tcti-name est utilisée pour la recherche. Ainsi, cela pourrait être un chemin vers la bibliothèque partagée, ou un nom de bibliothèque tel qu'entendu par la sémantique de dlopen(3).

OPTIONS TCTI

Cette collection d'options est utilisée pour configurer les différents modules TCTI connus disponibles :

•
device : Pour le TCTI device, le fichier périphérique caractère TPM à utiliser par le TCTI device peut être spécifié. Le défaut est /dev/tpm0.

Exemple : -T device:/dev/tpm0 ou export TPM2TOOLS_TCTI=“device:/dev/tpm0”

•
mssim : Pour le TCTI mssim, le nom de domaine ou l'adresse IP et le numéro de port utilisés par le simulateur peuvent être spécifiés. Les défauts sont 127.0.0.1 et 2321.

Exemple : -T mssim:host=localhost,port=2321 ou export TPM2TOOLS_TCTI=“mssim:host=localhost,port=2321”

•
abrmd : Pour le TCTI abrmd, le format de la chaîne de configuration est une série de paires clé-valeur simples séparées par un caractère `,`. Chaque clé et valeur de chaîne sont séparées par un caractère `=`.
•
Le TCTI abrmd prend en charge deux clés :
1.
`bus_name' : Le nom du service tabrmd sur le bus (une chaîne).
2.
`bus_type' : Le type de l'instance dbus (une chaîne) limité à `session' et `system'.

Spécifiez le nom du tcti tabrmd et une chaîne de configuration de bus_name=com.example.FooBar :

\--tcti=tabrmd:bus_name=com.example.FooBar

Spécifiez le tcti par défaut (abrmd) et une chaîne de configuration de bus_type=session :

\--tcti=tabrmd:bus_type=session

NOM

tpm2_policyticket– pour créer une politique de ticket.

SYNOPSIS

tpm2_policyticket [OPTIONS] [POLICY_OPTIONS]
tpm2_policyticket -h

DESCRIPTION

Le programme tpm2_policyticket est utilisé pour construire une politique pour une session de politique TPM2. Cette politique vérifie qu'une authentification de ticket est fournie par le demandeur. Il est destiné à être utilisé dans le cadre d'une séquence de commandes qui construisent une politique complexe, telle que celle impliquant des politiques de signature.

La politique sera implémentée dans le TPM lorsque la commande tpm2_policycommand(1) sera appelée.

Le ticket est généré par le TPM lui-même, et devrait contenir un ensemble de paramètres qui sont nécessaires pour l'authentification. L'argument policy.signed est produit par la commande tpm2_policysigned(1). Le ticket fait référence à la politique du demandeur et est censé être vérifié par une commande ultérieure qui construit le chemin de politique.

La politique est appliquée par tpm2_policyauthvalue(1), tpm2_policysecret(1) ou tpm2_policyauthorize(1) pour générer une politique complexe pour les commandes de ressources.

Pour générer une politique de ticket, les étapes suivantes sont suivies:

  • Démarrer une session de politique avec tpm2_startauthsession(1).
  • Pour générer le ticket, vous devez utiliser --nonce-tpm de tpm2_startauthsession(1).
  • Une fois le ticket généré, utilisez tpm2_policyticket(1) pour appeler la commande de politique.

Pour le renforcement du ticket, utilisez tpm2_policyticket(1) pour obtenir le ticket. Il est alors utilisé comme argument pour la commande tpm2_policyauthorize(1) ou tpm2_policysigned(1).

OPTIONS

Le programme tpm2_policyticket accepte les options suivantes:

Les options communes au programme tpm2_policyticket.

POLICY OPTIONS

Les options de politique suivantes sont requises pour construire une politique.
-S SESSION
Le chemin du fichier contenant le contexte de la session de politique.
-n NAME
Le nom de l'objet que la signature du ticket sera évaluée contre. La taille du nom est de 32 octets.
-x NONCE
Le nonce qui sera utilisé pour la génération du ticket. Le fichier contient la valeur du nonce de la commande tpm2_startauthsession(1).
-t TIMEOUT
Une valeur de délai d'attente en octets. Il s'agit de la valeur de délai d'attente qui sera utilisée pour vérifier le ticket. Le délai d'attente est codé sur 4 octets.
-o TIMEOUT_FILE
Le chemin du fichier contenant la valeur de délai d'attente à utiliser pour la politique.
-c TICKET
Le chemin du fichier dans lequel le ticket sera écrit. Le ticket est de taille variable et ne sera pas nécessairement 32 octets.
-L POLICY_DIGEST
Le chemin du fichier dans lequel le résumé de la politique sera écrit.

COMMON OPTIONS

-h
Aide; imprime un message d'utilisation.
-v
Verbosité; augmente le niveau de journalisation des informations.

EXEMPLES

Autoriser une opération TPM sur un objet dont l'autorisation est liée à une autorité de signature spécifique.

Créer l'autorité de signature et charger la clé de vérification

openssl genrsa -out private.pem 2048
openssl rsa -in private.pem -outform PEM -pubout -out public.pem
tpm2_loadexternal -C o -G rsa -u public.pem -c signing_key.ctx \
-n signing_key.name

Générer signature avec l'heure d'expiration

EXPIRYTIME="FFFFFE0C"
echo $EXPIRYTIME | xxd -r -p | \
openssl dgst -sha256 -sign private.pem -out signature.dat

Créer la politique

tpm2_startauthsession -S session.ctx
tpm2_policysigned -S session.ctx -g sha256 -s signature.dat -f rsassa \
-c signing_key.ctx -L policy.signed
tpm2_flushcontext session.ctx

Créer un objet de scellement

tpm2_createprimary -C o -c prim.ctx -Q
echo "plaintext" > secret.dat
tpm2_create -u sealing_key.pub -r sealing_key.priv -c sealing_key.ctx \
-C prim.ctx -i secret.dat -L policy.signed -Q

Créer une politique scellable par ticket

tpm2_startauthsession -S session.ctx --nonce-tpm=nonce.test --policy-session
{ cat nonce.test & echo $EXPIRYTIME | xxd -r -p; } | \
openssl dgst -sha256 -sign private.pem -out signature.dat
tpm2_policysigned -S session.ctx -g sha256 -s signature.dat -f rsassa \
-c signing_key.ctx -x nonce.test --ticket tic.ket --timeout time.out \
-t 0xFFFFFE0C
tpm2_flushcontext session.ctx

##Test avec policyticket au lieu de policysigned

tpm2_startauthsession -S session.ctx --policy-session
tpm2_policyticket -S session.ctx -n signing_key.name --ticket tic.ket \
--timeout time.out
tpm2_unseal -p session:session.ctx -c sealing_key.ctx

Retour

Les outils peuvent retourner l'un des codes suivants:

•
0 - Succès.
•
1 - Erreur générale non spécifique.
•
2 - Erreur de gestion des options.
•
3 - Erreur d'authentification.
•
4 - Erreur liée au TCTI.
•
5 - Schéma non supporté. Applicable à tpm2_testparams.

Limitations

Il attend qu'une session soit déjà établie via tpm2_startauthsession(1) et nécessite l'un des éléments suivants:

•
accès direct au périphérique
•
prise en charge des sessions étendues avec tpm2-abrmd.

Sans cela, la plupart des gestionnaires de ressources ne sauvegarderont pas l'état de la session entre les invocations de commande.
