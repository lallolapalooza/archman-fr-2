NOM

tpool - Fait partie de l'extension de threading Tcl implémentant des pools de threads de travail.

SYNOPIS

package require Tcl 8.4

package require Thread ?2.8?

tpool::create ?options?

tpool::names

tpool::post ?-detached? ?-nowait? tpool script

tpool::wait tpool joblist ?varname?

tpool::cancel tpool joblist ?varname?

tpool::get tpool job

tpool::preserve tpool

tpool::release tpool

tpool::suspend tpool

tpool::resume tpool

DESCRIPTION

Ce package crée et gère des pools de threads de travail. Il permet de poster des tâches à des threads de travail et d'attendre leur achèvement. L'implémentation du pool de threads est consciente de la boucle d'événements Tcl. Cela signifie que chaque fois qu'un appelant est obligé d'attendre un événement (achèvement d'une tâche ou disponibilité/initialisation d'un thread de travail), l'implémentation entrera dans la boucle d'événements et permettra la gestion d'autres événements de fichier ou de minuteur (ou de tout autre événement pris en charge) en attente.

COMMANDES

tpool::create ?options?
Cette commande crée un nouveau pool de threads. Elle accepte plusieurs options sous forme de paires clé-valeur. Les options sont utilisées pour ajuster certains paramètres du pool de threads. La commande renvoie l'identifiant du pool de threads nouvellement créé.

Les options suivantes sont prises en charge :

-minworkers nombre
Nombre minimum de threads de travail requis pour cette instance de pool de threads. Lors de la création du pool de threads, l'implémentation créera autant de threads de travail d'avance et en gardera au moins ce nombre actif pendant la durée de vie de l'instance du pool de threads. La valeur par défaut de ce paramètre est 0 (zéro), ce qui signifie qu'un nouveau pool de threads n'aura initialement aucun thread de travail. Tous les threads de travail seront démarrés à la demande par les appelants exécutant la commande tpool::post et postant des tâches dans la file d'attente.
-maxworkers nombre
Nombre maximum de threads de travail autorisés pour cette instance de pool de threads. Si une nouvelle tâche est en attente et qu'aucun thread de travail inactif n'est disponible, l'implémentation essaiera de créer un nouveau thread de travail. Si le nombre de threads de travail disponibles est inférieur au nombre donné, un nouveau thread de travail démarrera. L'appelant entrera automatiquement dans la boucle d'événements et attendra que le thread de travail soit initialisé. Si, cependant, le nombre de threads de travail disponibles est égal au nombre donné, l'appelant entrera dans la boucle d'événements et attendra qu'un premier thread de travail devienne inactif, prêt à exécuter la tâche. La valeur par défaut de ce paramètre est 4 (quatre), ce qui signifie que l'instance du pool de threads autorisera un maximum de 4 threads de travail exécutant des tâches ou étant inactifs en attendant que de nouvelles tâches soient postées dans la file d'attente.
-idletime secondes
Temps en secondes pendant lequel un thread de travail inactif attend qu'une tâche soit postée dans la file d'attente. Si aucune tâche n'arrive pendant cet intervalle et que le temps expire, le thread de travail vérifiera le nombre de threads de travail actuellement disponibles et si ce nombre est supérieur à celui défini par l'option minthreads, il se terminera. Si un exitscript a été défini, le thread de travail sortant exécutera d'abord le script, puis se terminera. Les erreurs du script de sortie, le cas échéant, sont ignorées.

Le thread de travail inactif ne gère pas la boucle d'événements. Si vous mettez toutefois le thread de travail dans la boucle d'événements, en évaluant la commande vwait ou d'autres commandes Tcl associées, le thread de travail ne sera pas dans un état inactif, par conséquent, le minuteur d'inactivité ne sera pas pris en compte. La valeur par défaut pour cette option n'est pas spécifiée.

-initcmd script
Définit un script Tcl utilisé pour initialiser un nouveau thread de travail. Ceci est généralement utilisé pour charger des paquets et des commandes dans le worker, définir des variables par défaut, créer des espaces de noms, etc. Si le script passé rencontre une erreur Tcl, le worker ne sera pas créé et la commande initiatrice (soit tpool::create, soit tpool::post) générera une erreur. La valeur par défaut pour cette option n'est pas spécifiée, par conséquent, l'interpréteur Tcl du thread de travail ne contiendra que l'ensemble initial de commandes Tcl.
-exitcmd script
Définit un script Tcl exécuté lorsque le thread de travail inactif se termine. Ceci est normalement utilisé pour nettoyer l'état du thread de travail, libérer les ressources réservées, nettoyer la mémoire, etc. La valeur par défaut pour cette option n'est pas spécifiée, donc aucun script Tcl ne sera exécuté à la sortie du thread de travail.
tpool::names
Cette commande renvoie une liste d'identifiants de pools de threads créés avec la commande tpool::create. Si aucun pool de threads n'a été trouvé, la commande renvoie une liste vide.
tpool::post ?-detached? ?-nowait? tpool script
Cette commande envoie un script au pool de threads cible tpool pour exécution. Le script sera exécuté dans le premier thread de travail inactif disponible. S'il n'y a pas de threads de travail inactifs disponibles, la commande en créera un nouveau, entrera dans la boucle d'événements et traitera les événements jusqu'à ce que le thread nouvellement créé soit initialisé. Si le nombre actuel de threads de travail est égal au nombre maximum de threads de travail, tel que défini lors de la création du pool de threads, la commande entrera dans la boucle d'événements et traitera les événements en attendant qu'un des threads de travail devienne inactif. Si l'argument optionnel ?-nowait? est fourni, la commande n'attendra pas qu'un thread inactif soit disponible. Elle placera simplement la tâche dans la file d'attente du pool et retournera immédiatement.

La commande renvoie l'identifiant de la tâche postée. Cet identifiant est utilisé pour les commandes ultérieures tpool::wait, tpool::get et tpool::cancel afin d'attendre et de récupérer le résultat du script posté, ou d'annuler la tâche postée respectivement. Si l'argument optionnel ?-detached? est spécifié, la commande postera une tâche détachée. Une tâche détachée ne peut être ni annulée ni attendue et n'est pas identifiée par l'identifiant de tâche.

Si le pool de threads tpool n'est pas trouvé dans la liste des pools de threads actifs, la commande générera une erreur. L'erreur sera également déclenchée si le nouveau thread de travail échoue à s'initialiser.

tpool::wait tpool joblist ?varname?
Cette commande attend qu'une ou plusieurs tâches, dont les identifiants sont donnés dans la liste joblist, soient traitées par les threads de travail. Si aucune des tâches spécifiées n'est prête, la commande entrera dans la boucle d'événements, traitera les événements et attendra que la première tâche soit prête.

La commande renvoie la liste des identifiants des tâches terminées. Si la variable optionnelle ?varname? est donnée, elle sera définie avec la liste des tâches de joblist qui sont encore en attente. Si le pool de threads tpool n'est pas trouvé dans la liste des pools de threads actifs, la commande générera une erreur.

tpool::cancel tpool joblist ?varname?
Cette commande annule les tâches précédemment postées, données par la liste joblist, au pool tpool. L'annulation de tâche ne réussit que pour les tâches encore en attente de traitement. Si la tâche est déjà en cours d'exécution par un des threads de travail, la tâche ne sera pas annulée. La commande renvoie la liste des identifiants des tâches annulées. Si la variable optionnelle ?varname? est donnée, elle sera définie avec la liste des tâches de joblist qui n'ont pas été annulées. Si le pool de threads tpool n'est pas trouvé dans la liste des pools de threads actifs, la commande générera une erreur.
tpool::get tpool job

tpool::preserve tpool
Chaque appel à cette commande incrémente le compteur de références du pool de threads tpool de un (1). La commande retourne la valeur du compteur de références après l'incrémentation. En incrémentant le compteur de références, l'appelant signale qu'il souhaite utiliser la ressource plus longtemps.
tpool::release tpool
Chaque appel à cette commande décrémente le compteur de références du pool de threads tpool de un (1). La commande retourne la valeur du compteur de références après la décrémentation. Lorsque le compteur de références atteint zéro (0), le pool de threads tpool est marqué pour terminaison. Vous ne devriez pas référencer le pool de threads après que la commande tpool::release retourne zéro. Le handle tpool sort de sa portée et ne doit plus être utilisé. Toute référence ultérieure au même handle de pool de threads entraînera une erreur Tcl.
tpool::suspend tpool
Suspend le traitement du travail sur cette file d'attente. Tous les travailleurs du pool sont mis en pause mais d'autres travaux peuvent être ajoutés au pool. Notez que l'ajout de travail supplémentaire n'augmentera pas le nombre de travailleurs dynamiquement car le traitement du pool est suspendu. Le nombre de travailleurs est maintenu au compte trouvé avant la suspension de l'activité des travailleurs. Si vous souhaitez garantir un certain nombre de threads travailleurs, utilisez l'option minworkers de la commande tpool::create.
tpool::resume tpool
Reprend le traitement du travail sur cette file d'attente. Tous les travailleurs en pause (suspendus) sont libres de récupérer du travail dans le pool. Notez que la reprise de l'opération du pool permettra simplement aux travailleurs déjà créés de continuer. Elle ne créera pas de threads travailleurs supplémentaires pour gérer le travail posté dans la file d'attente de travail du pool.

DISCUSSION

Le pool de threads est l'un des paradigmes de threading les plus courants pour les applications serveur gérant un grand nombre de tâches relativement petites. Un modèle très simplifié pour construire une application serveur consisterait à créer un nouveau thread chaque fois qu'une requête arrive et à traiter la requête dans ce nouveau thread. L'un des inconvénients de cette approche est que la surcharge liée à la création d'un nouveau thread pour chaque requête est significative ; un serveur qui créerait un nouveau thread pour chaque requête passerait plus de temps et consommerait plus de ressources système à créer et détruire des threads qu'à traiter les requêtes réelles des utilisateurs. En plus de la surcharge de création et de destruction de threads, les threads actifs consomment des ressources système. La création de trop nombreux threads peut entraîner l'épuisement de la mémoire du système ou un "thrashing" (ralentissement extrême) dû à une consommation excessive de mémoire.

Un pool de threads offre une solution à la fois au problème de la surcharge du cycle de vie des threads et au problème du "thrashing" des ressources. En réutilisant les threads pour plusieurs tâches, la surcharge de création de threads est répartie sur de nombreuses tâches. De plus, comme le thread existe déjà lorsqu'une requête arrive, le délai introduit par la création du thread est éliminé. Ainsi, la requête peut être traitée immédiatement. De plus, en réglant correctement le nombre de threads dans le pool de threads, le "thrashing" des ressources peut également être éliminé en forçant toute requête à attendre qu'un thread soit disponible pour la traiter.
