tpm2_setprimarypolicy(1) Manuel des commandes générales tpm2_setprimarypolicy(1)

NOM

tpm2_setprimarypolicy(1) - Définit la politique d'autorisation pour la hiérarchie de verrouillage (lockoutPolicy), la hiérarchie de plateforme (platformPolicy), la hiérarchie de stockage (ownerPolicy) et la hiérarchie de caution (endorsementPolicy).

SYNOPSIS

tpm2_setprimarypolicy [OPTIONS]

DESCRIPTION

tpm2_setprimarypolicy(1) - Définit la politique d'autorisation pour la hiérarchie de verrouillage (lockoutPolicy), la hiérarchie de plateforme (platformPolicy), la hiérarchie de stockage (ownerPolicy) et la hiérarchie de caution (endorsementPolicy).

OPTIONS

Ces options contrôlent la création de la session d'autorisation de politique :

•
-C, --hierarchy=OBJET:

Spécifie la hiérarchie dont la politique d'autorisation doit être configurée. Elle peut être spécifiée comme o|p|e|l

•
-P, --auth=AUTH:

Spécifie la valeur d'autorisation pour la hiérarchie.

•
-L, --policy=FICHIER:

Le chemin d'accès au fichier des données de politique d'autorisation.

•
-g, --hash-algorithm=ALGORITHME:

L'algorithme de hachage utilisé dans le calcul de l'empreinte de la politique.

•
--cphash=FICHIER

Chemin d'accès au fichier pour enregistrer le hachage des paramètres de la commande. Ceci est couramment appelé cpHash. NOTE : Lorsque cette option est sélectionnée, l'outil n'exécute pas réellement la commande, il renvoie simplement un cpHash.

Références

Format de l'objet de contexte

Le type d'un objet de contexte, qu'il s'agisse d'un handle ou d'un nom de fichier, est déterminé selon la logique suivante, par ordre :

•
Si l'argument est un chemin de fichier, alors le fichier est chargé comme un objet transitoire TPM restauré.
•
Si l'argument correspond à un préfixe parmi :
•
owner : la hiérarchie du propriétaire
•
platform : la hiérarchie de la plateforme
•
endorsement : la hiérarchie de caution
•
lockout : l'objet persistant de contrôle de verrouillage
•
Si l'argument peut être chargé comme un nombre, il sera traité comme un handle, par exemple 0x81010013 et utilisé directement._OBJET_.

Formatage des autorisations

L'autorisation d'utilisation d'un objet en TPM2.0 peut prendre 3 formes différentes : 1. Mot de passe 2. HMAC 3. Sessions

NOTE : « Les autorisations utilisent par défaut le MOT DE PASSE VIDE lorsqu'elles ne sont pas spécifiées ».

Mots de passe

Les mots de passe sont interprétés sous les formes suivantes en utilisant des identifiants de préfixe.

Note : Par défaut, les mots de passe sont considérés comme étant sous forme de chaîne lorsqu'ils n'ont pas de préfixe.

Chaîne de caractères

Un mot de passe sous forme de chaîne, spécifié par le préfixe « str: » ou son absence (chaîne brute sans préfixe) n'est pas interprété et est directement utilisé pour l'autorisation.

Exemples

foobar
str:foobar

Chaîne hexadécimale

Un mot de passe sous forme de chaîne hexadécimale, spécifié par le préfixe « hex: », est converti d'une forme hexadécimale en une forme de tableau d'octets, permettant ainsi les mots de passe contenant des caractères non imprimables et/ou peu pratiques pour le terminal.

Exemple

hex:1122334455667788

Fichier

Un mot de passe basé sur un fichier, spécifié par le préfixe « file: », doit être le chemin d'un fichier contenant le mot de passe à lire par l'outil ou un « - » pour utiliser stdin. Le stockage des mots de passe dans des fichiers empêche les fuites d'informations, car les mots de passe transmis en tant qu'options peuvent être lus depuis la liste des processus ou via des fonctionnalités courantes d'historique de shell.

Exemples

# pour utiliser stdin et être invité
file:-
# pour utiliser un fichier depuis un chemin
file:chemin/vers/fichier/mot_de_passe
# pour écho un mot de passe via stdin :
echo foobar | tpm2_tool -p file:-
# pour utiliser un here-string bash via stdin :
tpm2_tool -p file:- <<< foobar

Sessions

Lors de l'utilisation d'une session de politique pour autoriser l'utilisation d'un objet, préfixez l'argument de l'option avec le mot-clé session. Indiquez ensuite le chemin d'un fichier de session qui a été créé avec tpm2_startauthsession(1). Optionnellement, si la session nécessite une valeur d'autorisation à envoyer avec le handle de la session (par exemple, un mot de passe de politique), ajoutez un + suivi d'une chaîne comme décrit dans la section Mots de passe.

Exemples

Pour utiliser un fichier de contexte de session appelé session.ctx.

session:session.ctx

Pour utiliser un fichier de contexte de session appelé session.ctx ET envoyer la valeur d'autorisation mypassword.

session:session.ctx+mypassword

Pour utiliser un fichier de contexte de session appelé session.ctx ET envoyer la valeur d'autorisation HEX 0x11223344.

session:session.ctx+hex:11223344

Autorisations PCR

Vous pouvez satisfaire une politique PCR en utilisant le préfixe « pcr: » et le mini-langage PCR. Le mini-langage PCR est le suivant : <spécificateur-pcr>=<fichier-pcr-brut>

Le spécificateur PCR est documenté dans la section « Spécificateurs de banques PCR ».

Le fichier-pcr-brut est un argument optionnel contenant la sortie du contenu PCR brut tel que retourné par tpm2_pcrread(1).

Spécificateurs de banques PCR

Exemples

Pour satisfaire une politique PCR de sha256 sur les banques 0, 1, 2 et 3, utilisez le spécificateur :

pcr:sha256:0,1,2,3

en spécifiant AUTH.

Spécificateurs d'algorithmes

Les options qui prennent des algorithmes supportent des « noms sympathiques ».

Il existe deux classes principales de chaînes de spécification d'algorithmes : simples et complexes. Seuls certains algorithmes seront acceptés par le TPM, en fonction de l'utilisation et des conditions.

Spécificateurs simples

Ce sont des chaînes sans données de spécification supplémentaires. Lors de la création d'objets, les portions non spécifiées d'un objet sont supposées être par défaut. Vous pouvez trouver la liste des « Spécificateurs Simples » connus ci-dessous.

Spécificateurs complexes

Ces spécificateurs d'algorithmes sont des chaînes qui demandent des informations supplémentaires pour spécifier complètement l'algorithme. Par exemple, pour spécifier un schéma de signature RSA, vous devez spécifier l'algorithme de hachage.

Schémas de signature

Par exemple, pour spécifier un schéma de signature RSA avec le hachage SHA256 et le remplissage PSS :

rsapss:256

Pour spécifier un schéma de signature RSA avec le hachage SHA256 et le remplissage PKCS1 :

rsapkcs15:256

Pour spécifier un schéma de signature ECC avec le hachage SHA256 :

ecdsa:256

Modes de chiffrement

Par exemple, pour spécifier AES en mode CBC :

cbc:aes

Pour spécifier AES en mode GCM :

gcm:aes

Spécificateurs Complexes

Les objets, lorsqu'ils sont spécifiés pour la création par le TPM, ont de nombreux algorithmes à remplir dans les données publiques. Des choses comme le type, le schéma et les détails asymétriques, la taille de la clé, etc. Voici le format général pour spécifier ces données : <type>:<schéma>:<détails-symétriques>

Spécificateurs de Type

Cette partie du spécificateur d'algorithme complexe est requise. Les schémas et les détails symétriques restants seront par défaut en fonction du type spécifié et du type de l'objet en cours de création.

•
aes - AES par défaut : aes128
•
aes128<mode> - AES 128 bits avec mode optionnel (ctr|ofb|cbc|cfb|ecb). Si le mode n'est pas spécifié, la valeur par défaut est null.
•
aes192<mode> - Identique à aes128<mode>, sauf pour une taille de clé de 192 bits.
•
aes256<mode> - Identique à aes128<mode>, sauf pour une taille de clé de 256 bits.
•
sm4 - SM4 par défaut : sm4128
•
sm4128 ou sm4_128 <mode> - SM4 128 bits avec mode optionnel (ctr|ofb|cbc|cfb|ecb). Si le mode n'est pas spécifié, la valeur par défaut est null.
•
ecc - Courbe elliptique, par défaut ecc256.
•
ecc192 ou ecc_nist_p192 - Courbe NIST ECC 192 bits
•
ecc224 ou ecc_nist_p224 - Courbe NIST ECC 224 bits
•
ecc256 ou ecc_nist_p256 - Courbe NIST ECC 256 bits
•
ecc384 ou ecc_nist_p384 - Courbe NIST ECC 384 bits
•
ecc521 ou ecc_nist_p521 - Courbe NIST ECC 521 bits
•
ecc_sm2 ou ecc_sm2_p256 - Courbe SM2 256 bits
•
rsa - RSA par défaut : rsa2048
•
rsa1024 - RSA avec une taille de clé de 1024 bits.
•
rsa2048 - RSA avec une taille de clé de 2048 bits.
•
rsa3072 - RSA avec une taille de clé de 3072 bits.
•
rsa4096 - RSA avec une taille de clé de 4096 bits.

Spécificateurs de Schéma

Ensuite, il y a un champ facultatif, il peut être ignoré.

Les schémas sont généralement des Schémas de Signature ou des Schémas de Chiffrement Asymétrique. La plupart des schémas de signature prennent un algorithme de hachage directement après le schéma de signature. Si l'algorithme de hachage est manquant, la valeur par défaut est sha256. Certains ne prennent aucun argument, et certains prennent plusieurs arguments.

Spécificateurs de Schéma Optionnels avec Hachage

Ces spécificateurs de schéma sont suivis d'un trait et d'un algorithme de hachage valide, par exemple : oaep-sha256.

•
oaep
•
ecdh
•
rsassa
•
rsapss
•
ecdsa
•
ecschnorr
•
sm2

Spécificateurs de Schéma à Options Multiples

Ce spécificateur de schéma est suivi d'un nombre (taille maximale UINT16) puis suivi d'un trait (-) et d'un algorithme de hachage valide. * ecdaa Par exemple, ecdaa4-sha256. Si aucun nombre n'est spécifié, il est par défaut à 4.

Spécificateurs de Schéma Sans Option

Ce spécificateur de schéma ne prend AUCUN argument. * rsaes

Spécificateurs de Détails Symétriques

Ce champ est facultatif et par défaut en fonction du type de l'objet en cours de création et de ses attributs. Généralement, tout spécificateur Symétrique valide de la liste des Spécificateurs de Type devrait fonctionner. S'il n'est pas spécifié, les détails symétriques d'un objet asymétrique sont par défaut à aes128cfb.

Exemples

Créer une clé rsa2048 avec un schéma de chiffrement asymétrique rsaes

tpm2_create -C parent.ctx -G rsa2048:rsaes -u key.pub -r key.priv

Créer une clé ecc256 avec un schéma de signature ecdaa avec un compte de 4 et un hachage sha384

/tpm2_create -C parent.ctx -G ecc256:ecdaa4-sha384 -u key.pub -r key.priv algorithmes cryptographiques ALGORITHM.

OPTIONS COMMUNES

Cette collection d'options est commune à de nombreux programmes et fournit des informations que de nombreux utilisateurs peuvent attendre.

•
-h, --help=[man|no-man] : Affiche le manuel de l'outil. Par défaut, il tente d'appeler le pager de manuel pour l'outil, cependant, en cas d'échec, il affichera un bref résumé de l'outil. C'est le même comportement si l'argument d'option « man » est spécifié, cependant si « man » est explicitement demandé, l'outil fournira les erreurs de man sur stderr. Si l'option « no-man » est spécifiée, ou si le pager de manuel échoue, les options courtes seront affichées sur stdout.

Pour utiliser correctement la fonctionnalité des manpages, il faut que les manpages soient installées ou sur MANPATH. Voir man(1) pour plus de détails.

•
-v, --version : Affiche les informations de version pour cet outil, les tctis supportés et quitte.
•
-V, --verbose : Augmente les informations que l'outil imprime sur la console pendant son exécution. En utilisant cette option, le fichier et le numéro de ligne sont imprimés.
•
-Q, --quiet : Silence la sortie normale de l'outil sur stdout.
•
-Z, --enable-errata : Active l'application des corrections d'errata. Utile si une correction d'errata doit être appliquée aux commandes envoyées au TPM. La définition de la variable d'environnement TPM2TOOLS_ENABLE_ERRATA est équivalente.
•
-R, --autoflush : Active l'autoflush pour les objets transitoires créés par la commande. Si un objet parent est chargé à partir d'un fichier de contexte, l'objet parent transitoire sera également vidé. L'autoflush peut également être activé si la variable d'environnement TPM2TOOLS_AUTOFLUSH est définie sur yes ou true. informations que de nombreux utilisateurs peuvent attendre.

Configuration TCTI

Le TCTI ou « Interface de Transmission » est le mécanisme de communication avec le TPM. Les TCTIs peuvent être modifiés pour la communication avec les TPM sur différents supports.

Pour contrôler le TCTI, les outils respectent :

1.
L'option de ligne de commande -T ou --tcti
2.
La variable d'environnement : TPM2TOOLS_TCTI.

Note : L'option de ligne de commande supplante toujours la variable d'environnement.

Les TCTIs actuellement connus sont :

•
tabrmd - Le gestionnaire de ressources, appelé tabrmd. Notez que tabrmd et abrmd en tant que nom de tcti sont synonymes.
•
mssim - Généralement utilisé pour communiquer avec le simulateur logiciel du TPM.
•
device - Utilisé lors de la communication directe avec un fichier de périphérique TPM.
•
none - N'initialise pas de connexion avec le TPM. Certains outils autorisent les options hors TPM et prennent donc en charge la non-utilisation d'un TCTI. Les outils qui ne le prennent pas en charge généreront une erreur lorsqu'ils seront tentés d'être utilisés sans connexion TCTI. Ne prend en charge AUCUNE option et DOIT être présenté comme le texte exact de « none ».

Les arguments de l'option de ligne de commande ou de la variable d'environnement sont sous la forme :

<tcti-nom<tcti-option-config>

Spécifier une chaîne vide pour l’<tcti-name> ou <tcti-option-config> entraîne l’utilisation de la valeur par défaut pour cette partie respectivement.

Défauts TCTI

Lorsqu’un TCTI n’est pas spécifié, le TCTI par défaut est recherché en utilisant les sémantiques de dlopen(3). Les outils recherchent les TCTIs tabrmd, device et mssim **DANS CET ORDRE** et **UTILISENT LE PREMIER TROUVÉ**. Vous pouvez interroger le TCTI qui sera choisi par défaut en utilisant l’option -v pour afficher les informations de version. La paire clé-valeur « default-tcti » indiquera lequel des TCTIs susmentionnés est le défaut.

TCTIs personnalisés

Tout TCTI implémentant l’interface TCTI dynamique peut être chargé. Les outils utilisent en interne dlopen(3), et la valeur brute tcti-name est utilisée pour la recherche. Ainsi, cela pourrait être un chemin vers la bibliothèque partagée, ou un nom de bibliothèque tel qu’entendu par les sémantiques de dlopen(3).

OPTIONS TCTI

Cette collection d’options est utilisée pour configurer les divers modules TCTI connus disponibles :

•
device: Pour le TCTI device, le fichier de périphérique caractère TPM à utiliser par le TCTI device peut être spécifié. Le défaut est /dev/tpm0.

Exemple : -T device:/dev/tpm0 ou export TPM2TOOLS_TCTI=“device:/dev/tpm0”

•
mssim: Pour le TCTI mssim, le nom de domaine ou l’adresse IP et le port utilisés par le simulateur peuvent être spécifiés. Les défauts sont 127.0.0.1 et 2321.

Exemple : -T mssim:host=localhost,port=2321 ou export TPM2TOOLS_TCTI=“mssim:host=localhost,port=2321”

•
abrmd: Pour le TCTI abrmd, le format de la chaîne de configuration est une série de paires clé-valeur simples séparées par un caractère `,`. Chaque chaîne de clé et de valeur est séparée par un caractère `=`.
•
Le TCTI abrmd prend en charge deux clés :
1.
`bus_name' : Le nom du service tabrmd sur le bus (une chaîne de caractères).
2.
`bus_type' : Le type de l’instance dbus (une chaîne de caractères) limitée à `session' et `system'.

Spécifier le nom du TCTI tabrmd et une chaîne de configuration de bus_name=com.example.FooBar :

\--tcti=tabrmd:bus_name=com.example.FooBar

Spécifier le TCTI par défaut (abrmd) et une chaîne de configuration de bus_type=session :

\--tcti:bus_type=session

NOTE : abrmd et tabrmd sont synonymes. les divers modules TCTI connus.

EXEMPLES

Définir une politique d’autorisation vide pour la hiérarchie d’approbation

tpm2_setprimarypolicy -C e

Retourne

Les outils peuvent retourner l'un des codes suivants :

•
0 - Succès.
•
1 - Erreur générale non spécifique.
•
2 - Erreur de gestion des options.
•
3 - Erreur d’authentification.
•
4 - Erreur liée au TCTI.
•
5 - Schéma non pris en charge. Applicable à tpm2_testparams.
