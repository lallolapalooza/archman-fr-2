tpm2_duplicate(1) Manuel des commandes générales tpm2_duplicate(1)

NOM

tpm2_duplicate(1) - Duplique un objet chargé afin qu'il puisse être utilisé dans une autre hiérarchie.

SYNOPIS

tpm2_duplicate [OPTIONS]

DESCRIPTION

tpm2_duplicate(1) - Cet outil duplique un objet chargé afin qu'il puisse être utilisé dans une autre hiérarchie. La nouvelle clé parente de la duplication peut se trouver sur le même TPM ou un autre, ou sur TPM_RH_NULL.

OPTIONS

Ces options contrôlent le processus d'importation de clé :

•
-G, --wrapper-algorithm=ALGORITHME:

L'algorithme symétrique à utiliser pour l'enveloppe intérieure si -U n'est pas utilisé. Prend en charge :

•
aes - AES 128 en mode CFB.
•
null - aucun L'algorithme de clé associé au parent public si -U est utilisé.
•
-G, --key-algorithm=ALGORITHME:

L'algorithme de clé associé au parent public si -U est utilisé.

•
-i, --encryptionkey-in=FICHIER:

Spécifie le nom du fichier de la clé symétrique (données 128 bits) à utiliser pour l'enveloppe intérieure. Valide uniquement lorsque l'algorithme symétrique spécifié n'est pas null

•
-o, --encryptionkey-out=FICHIER:

Spécifie le nom du fichier pour stocker la clé symétrique (données 128 bits) qui a été utilisée pour l'enveloppe intérieure. Valide uniquement lorsque l'algorithme symétrique spécifié n'est pas null et que --input-key-file n'est pas spécifié. Le TPM génère la clé dans ce cas.

•
-C, --parent-context=OBJET:

L'objet clé parente.

•
-U, --parent-public=FICHIER:

Spécifie le chemin du fichier vers la clé publique de l'objet parent sur le TPM de destination. Il doit s'agir d'un fichier au format TPM2B_PUBLIC. Cette clé publique est utilisée pour l'enveloppement d'une clé PEM ou DER qui sera exportée pour un TPM distant.

•
-k, --private-key=FICHIER:

Spécifie le chemin du fichier vers la clé privée externe à chiffrer pour le TPM distant. Il doit s'agir d'une clé privée au format PEM.

•
-r, --private=FICHIER:

Spécifie le chemin du fichier pour enregistrer la partie privée de l'objet dupliqué. # Détails de protection

Les objets qui peuvent sortir du TPM doivent être protégés (confidentialité et intégrité). Par exemple, les objets transitoires nécessitent que les données protégées par le TPM (clé ou matériau de scellage) soient stockées à l'extérieur du TPM. Ceci est observé dans des outils comme tpm2_create(1), où l'option -r produit ces données protégées. Ce blob contient les parties sensibles de l'objet. Les parties sensibles de l'objet sont protégées par l'objet parent, en utilisant les détails de chiffrement symétrique du parent pour chiffrer les données sensibles et les signer.

Des détails approfondis peuvent être trouvés dans les sections 23 de :

•
https://trustedcomputinggroup.org/wp-content/uploads/TPM-Rev-2.0-Part-1-Architecture-01.38.pdf

Notamment la Figure 20, est pertinente, même si elle fait spécifiquement référence aux blobs de duplication, le processus est identique.

Si la sortie provient de tpm2_duplicate(1), la sortie sera légèrement différente, comme décrit entièrement dans la section 23.

•
-u, --public=FICHIER:

Spécifie le chemin du fichier pour enregistrer la partie publique de l'objet dupliqué, si une clé externe est dupliquée.

•
-s, --encrypted-seed=FICHIER:

Le fichier pour enregistrer la graine chiffrée de l'objet dupliqué.

•
-p, --auth=AUTH:

La valeur d'autorisation pour la clé, facultative.

•
-L, --policy=FICHIER:

Le fichier de politique d'entrée, facultatif.

•
-c, --key-context=OBJET:

L'objet à dupliquer.

•
-a, --attributes=ATTRIBUTS:

Les attributs de l'objet, facultatif. La valeur par défaut pour les objets créés est :

TPMA_OBJECT_SIGN_ENCRYPT|TPMA_OBJECT_DECRYPT|TPMA_OBJECT_USERWITHAUTH

Note : Si une politique est spécifiée sans valeur d'authentification, TPMA_OBJECT_USERWITHAUTH est désactivé.

•
--cphash=FICHIER

Chemin du fichier pour enregistrer le hachage des paramètres de la commande. Ceci est communément appelé cpHash. REMARQUE : Lorsque cette option est sélectionnée, l'outil n'exécutera pas réellement la commande, il retournera simplement un cpHash.

Références

Format de l'objet de contexte

Le type d'un objet de contexte, qu'il s'agisse d'un handle ou d'un nom de fichier, est déterminé selon la logique suivante, *dans l'ordre* :

•
Si l'argument est un chemin de fichier, le fichier est chargé comme objet transitoire TPM restauré.
•
Si l'argument correspond à une correspondance *préfixée* avec l'un des éléments suivants :
•
owner : la hiérarchie propriétaire
•
platform : la hiérarchie de plateforme
•
endorsement : la hiérarchie d'approbation
•
lockout : l'objet persistant de contrôle de blocage
•
Si l'argument peut être chargé comme un nombre, il sera traité comme un handle, par exemple 0x81010013, et utilisé directement.

Format de l'autorisation

L'autorisation d'utilisation d'un objet dans TPM2.0 peut se présenter sous 3 formes différentes : 1. Mot de passe 2. HMAC 3. Sessions

REMARQUE : « Les autorisations utilisent par défaut le **MOT DE PASSE VIDE** lorsqu'elles ne sont pas spécifiées ».

Mots de passe

Les mots de passe sont interprétés sous les formes ci-dessous à l'aide d'identifiants de préfixe.

Remarque : Par défaut, les mots de passe sont considérés comme étant sous forme de chaîne lorsqu'ils n'ont pas de préfixe.

Chaîne

Un mot de passe sous forme de chaîne, spécifié par le préfixe « str: » ou son absence (chaîne brute sans préfixe) n'est pas interprété et est directement utilisé pour l'autorisation.

Exemples

foobar
str:foobar

Chaîne hexadécimale

Un mot de passe sous forme de chaîne hexadécimale, spécifié par le préfixe « hex: », est converti d'une forme hexadécimale en une forme de tableau d'octets, permettant ainsi les mots de passe contenant des caractères non imprimables et/ou peu pratiques pour le terminal.

Exemple

hex:1122334455667788

Fichier

Un mot de passe basé sur un fichier, spécifié par le préfixe « file: », doit être le chemin d'un fichier contenant

contenant le mot de passe à lire par l'outil ou un « - » pour utiliser stdin. Le stockage des mots de passe dans des fichiers évite fuites d'informations, les mots de passe passés en option peuvent être lus à partir de la liste de processus ou des fonctionnalités courantes de l'historique du shell.

Exemples

# pour utiliser stdin et être invité
file:-
# pour utiliser un fichier à partir d'un chemin
file:chemin/vers/fichier/motdepasse
# pour écho un mot de passe via stdin :
echo foobar | tpm2_tool -p file:-
# pour utiliser une chaîne ici bash via stdin :
tpm2_tool -p file:- <<< foobar

Sessions

Lors de l'utilisation d'une session de politique pour autoriser l'utilisation d'un objet, préfixez l'argument de l'option avec le mot-clé session. Indiquez ensuite un chemin vers un fichier de session créé avec tpm2_startauthsession(1). Optionnellement, si la session nécessite une valeur d'authentification à envoyer avec le handle de session (par exemple, mot de passe de politique), ajoutez un + et une chaîne comme décrit dans la section Mots de passe.

Exemples

Pour utiliser un fichier de contexte de session appelé session.ctx.

session:session.ctx

Pour utiliser un fichier de contexte de session appelé session.ctx ET envoyer la valeur d'authentification monmotdepasse.

session:session.ctx+monmotdepasse

Pour utiliser un fichier de contexte de session appelé session.ctx ET envoyer la valeur d'authentification HEX 0x11223344.

session:session.ctx+hex:11223344

Autorisations PCR

Vous pouvez satisfaire une politique PCR en utilisant le préfixe « pcr: » et le mini-langage PCR. Le mini-langage PCR est le suivant : <spécificateur-pcr>=<fichier-pcr-brut>

Le spécificateur PCR est documenté dans la section « Spécificateurs de banque PCR ».

Le fichier-pcr-brut est un argument optionnel qui contient la sortie du contenu brut du PCR tel que renvoyé par tpm2_pcrread(1).

Spécificateurs de banque PCR

Exemples

Pour satisfaire une politique PCR de sha256 sur les banques 0, 1, 2 et 3, utilisez un spécificateur de :

pcr:sha256:0,1,2,3

spécifiant AUTH.

Spécificateurs Complexes

Les objets, lorsqu'ils sont spécifiés pour la création par le TPM, ont de nombreux algorithmes à remplir dans les données publiques. Des choses comme le type, le schéma et les détails asymétriques, la taille de la clé, etc. Ci-dessous se trouve le format général pour spécifier ces données : <type>:<schéma>:<détails-symétriques>

Spécificateurs de Type

Cette partie du spécificateur d'algorithme complexe est requise. Les schémas et détails symétriques restants seront par défaut en fonction du type spécifié et du type de l'objet en cours de création.

•
aes - AES par défaut : aes128
•
aes128<mode> - AES 128 bits avec mode optionnel (ctr|ofb|cbc|cfb|ecb). Si le mode n'est pas spécifié, il est par défaut à null.
•
aes192<mode> - Identique à aes128<mode>, sauf pour une taille de clé de 192 bits.
•
aes256<mode> - Identique à aes128<mode>, sauf pour une taille de clé de 256 bits.
•
sm4 - SM4 par défaut : sm4128
•
sm4128 ou sm4_128 <mode> - SM4 128 bits avec mode optionnel (ctr|ofb|cbc|cfb|ecb). Si le mode n'est pas spécifié, il est par défaut à null.
•
ecc - Courbe elliptique, par défaut ecc256.
•
ecc192 ou ecc_nist_p192 - Courbe NIST ECC 192 bits
•
ecc224 ou ecc_nist_p224 - Courbe NIST ECC 224 bits
•
ecc256 ou ecc_nist_p256 - Courbe NIST ECC 256 bits
•
ecc384 ou ecc_nist_p384 - Courbe NIST ECC 384 bits
•
ecc521 ou ecc_nist_p521 - Courbe NIST ECC 521 bits
•
ecc_sm2 ou ecc_sm2_p256 - Courbe SM2 256 bits
•
rsa - RSA par défaut : rsa2048
•
rsa1024 - RSA avec une taille de clé de 1024 bits.
•
rsa2048 - RSA avec une taille de clé de 2048 bits.
•
rsa3072 - RSA avec une taille de clé de 3072 bits.
•
rsa4096 - RSA avec une taille de clé de 4096 bits.

Spécificateurs de Schéma

Ensuite, il y a un champ optionnel, il peut être sauté.

Les schémas sont généralement des Schémas de Signature ou des Schémas de Chiffrement Asymétrique. La plupart des schémas de signature prennent un algorithme de hachage directement après le schéma de signature. Si l'algorithme de hachage est manquant, il est par défaut à sha256. Certains ne prennent aucun argument, et d'autres en prennent plusieurs.

Spécificateurs de Schéma Optionnel de Hachage

Ces spécificateurs de schéma sont suivis d'un tiret et d'un algorithme de hachage valide. Par exemple : oaep-sha256.

Spécificateurs de Schéma Multiples Options

Ce spécificateur de schéma est suivi d'un compte (taille max UINT16) puis suivi d'un tiret (-) et d'un algorithme de hachage valide. * ecdaa Par exemple, ecdaa4-sha256. Si aucun compte n'est spécifié, il est par défaut à 4.

Spécificateurs de Schéma Sans Option

Ce spécificateur de schéma ne prend AUCUN argument. * rsaes

Spécificateurs de Détails Symétriques

Ce champ est optionnel et est par défaut en fonction du type d'objet créé et de ses attributs. Généralement, tout spécificateur Symétrique valide de la liste des Spécificateurs de Type devrait fonctionner. S'il n'est pas spécifié, les détails symétriques des objets asymétriques sont par défaut à aes128cfb.

Exemples

Créer une clé rsa2048 avec un schéma de chiffrement asymétrique rsaes

tpm2_create -C parent.ctx -G rsa2048:rsaes -u key.pub -r key.priv

Créer une clé ecc256 avec un schéma de signature ecdaa avec un compte de 4 et un hachage sha384

Créer une clé ecc256 avec un schéma de signature ecdaa avec un compte de 4 et un hachage sha384

/tpm2_create -C parent.ctx -G ecc256:ecdaa4-sha384 -u key.pub -r key.priv

OPTIONS COMMUNES

Cette collection d'options est commune à de nombreux programmes et fournit des informations que de nombreux utilisateurs peuvent s'attendre à trouver.

•
-h, --help=[man|no-man] : Affiche le manuel de l'outil. Par défaut, il tente d'appeler le pagineur de manuel pour l'outil, cependant, en cas d'échec, il affichera un bref résumé de l'outil. C'est le même comportement si l'argument d'option « man » est spécifié, cependant si « man » est explicitement demandé, l'outil fournira les erreurs de man sur stderr. Si l'option « no-man » est spécifiée, ou si le pagineur de manuel échoue, les options courtes seront affichées sur stdout.

Pour utiliser avec succès la fonctionnalité des pages de manuel, il faut que les pages de manuel soient installées ou présentes dans MANPATH. Voir man(1) pour plus de détails.

•
-v, --version : Affiche les informations de version pour cet outil, les tcti pris en charge et quitte.
•
-V, --verbose : Augmente les informations que l'outil affiche sur la console pendant son exécution. Lors de l'utilisation de cette option, le fichier et le numéro de ligne sont affichés.
•
-Q, --quiet : Supprime la sortie normale de l'outil sur stdout.
•
-Z, --enable-errata : Active l'application des corrections d'errata. Utile si une correction d'errata doit être appliquée aux commandes envoyées au TPM. La définition de la variable d'environnement TPM2TOOLS_ENABLE_ERRATA est équivalente.
•
-R, --autoflush : Active l'autoflush pour les objets transitoires créés par la commande. Si un objet parent est chargé à partir d'un fichier de contexte, l'objet parent transitoire sera également vidé. L'autoflush peut également être activé si la variable d'environnement TPM2TOOLS_AUTOFLUSH est définie sur yes ou true.

Configuration TCTI

Le TCTI ou « Transmission Interface » est le mécanisme de communication avec le TPM. Les TCTI peuvent être modifiés pour communiquer avec les TPM via différents supports.

Pour contrôler le TCTI, les outils respectent :

1.
L'option de ligne de commande -T ou --tcti
2.
La variable d'environnement : TPM2TOOLS_TCTI.

Note : L'option de ligne de commande remplace toujours la variable d'environnement.

Les TCTI actuellement connus sont :

•
tabrmd - Le gestionnaire de ressources, appelé tabrmd. Notez que tabrmd et abrmd en tant que nom tcti sont synonymes.
•
mssim - Généralement utilisé pour communiquer avec le simulateur logiciel TPM.
•
device - Utilisé lors de la communication directe avec le fichier de périphérique TPM.
•
none - Ne pas initialiser de connexion avec le TPM. Certains outils permettent des options hors TPM et prennent donc en charge l'absence d'utilisation d'un TCTI. Les outils qui ne le prennent pas en charge généreront une erreur lors de leur tentative d'utilisation sans connexion TCTI. Ne prend en charge AUCUNE option et DOIT ÊTRE présenté comme le texte exact de « none ».

Les arguments de l'option de ligne de commande ou de la variable d'environnement sont sous la forme :

<nom-tcti>:<config-option-tcti>

Spécifier une chaîne vide pour le <nom-tcti> ou le <config-option-tcti> entraîne l'utilisation de la valeur par défaut pour cette partie respectivement.

Défauts TCTI

Lorsqu'un TCTI n'est pas spécifié, le TCTI par défaut est recherché en utilisant la sémantique de dlopen(3). Les outils rechercheront les TCTI tabrmd, device et mssim DANS CET ORDRE et UTILISERONT LE PREMIER TROUVÉ. Vous pouvez interroger quel TCTI sera choisi par défaut en utilisant l'option -v pour afficher les informations de version. La paire clé-valeur « default-tcti » indiquera lequel des TCTI susmentionnés est le défaut.

TCTIs personnalisés

Tout TCTI qui implémente l'interface TCTI dynamique peut être chargé. Les outils utilisent en interne dlopen(3), et la valeur brute tcti-name est utilisée pour la recherche. Ainsi, il pourrait s'agir d'un chemin vers la bibliothèque partagée, ou d'un nom de bibliothèque tel que compris par la sémantique de dlopen(3).

OPTIONS TCTI

Cette collection d'options est utilisée pour configurer les différents modules TCTI connus disponibles :

•
device : Pour le TCTI device, le fichier périphérique caractère TPM à utiliser par le TCTI device peut être spécifié. Le défaut est /dev/tpm0.

Exemple : -T device:/dev/tpm0 ou export TPM2TOOLS_TCTI=“device:/dev/tpm0”

•
mssim : Pour le TCTI mssim, le nom de domaine ou l'adresse IP et le numéro de port utilisés par le simulateur peuvent être spécifiés. Les défauts sont 127.0.0.1 et 2321.

Exemple : -T mssim:host=localhost,port=2321 ou export TPM2TOOLS_TCTI=“mssim:host=localhost,port=2321”

•
abrmd : Pour le TCTI abrmd, le format de la chaîne de configuration est une série de paires clé-valeur simples séparées par un caractère `,`. Chaque clé et chaîne de valeur sont séparées par un caractère `=`.
•
Le TCTI abrmd prend en charge deux clés :
1.
`bus_name' : Le nom du service tabrmd sur le bus (une chaîne).
2.
`bus_type' : Le type de l'instance dbus (une chaîne) limitée à `session' et `system'.

Spécifier le nom du tcti tabrmd et une chaîne de configuration de bus_name=com.example.FooBar :

\--tcti=tabrmd:bus_name=com.example.FooBar

Spécifier le tcti par défaut (abrmd) et une chaîne de configuration de bus_type=session :

\--tcti:bus_type=session

NOTE : abrmd et tabrmd sont synonymes. les divers modules TCTI connus.

EXEMPLES

Exemple-1 : Dupliquer une clé créée avec une politique qui autorise la duplication :

tpm2_startauthsession -S session.dat
tpm2_policycommandcode -S session.dat -L policy.dat TPM2_CC_Duplicate
tpm2_flushcontext session.dat
tpm2_createprimary -C o -g sha256 -G rsa -c primary.ctxt
tpm2_create -C primary.ctxt -g sha256 -G rsa -r key.prv -u key.pub  -c key.ctxt \
-L policy.dat -a "sensitivedataorigin|userwithauth|decrypt|sign"
tpm2_createprimary -C o -g sha256 -G ecc -c new_parent.ctxt
tpm2_startauthsession \--policy-session -S session.dat
tpm2_policycommandcode -S session.dat -L policy.dat TPM2_CC_Duplicate
tpm2_duplicate -C new_parent.ctxt -c key.ctxt -G null -p "session:session.dat" \
-r duprv.bin -s seed.dat
tpm2_flushcontext session.dat

Exemple-2 : Comme exemple de bout en bout, ce qui suit transférera une clé RSA générée sur TPM-A à TPM-B

Sur TPM-B

Créez un objet parent qui sera utilisé pour encapsuler/transférer la clé.

tpm2_createprimary -C o -g sha256 -G rsa -c primary.ctx
tpm2_create  -C primary.ctx -g sha256 -G rsa \
-r new_parent.prv  -u new_parent.pub \
-a "restricted|sensitivedataorigin|decrypt|userwithauth"

Copiez new_parent.pub à TPM-A.

Sur TPM-A

Créez un objet racine et une politique d'authentification permettant uniquement la duplication

tpm2_createprimary -C o -g sha256 -G rsa -c primary.ctx
tpm2_startauthsession -S session.dat
tpm2_policycommandcode -S session.dat -L dpolicy.dat TPM2_CC_Duplicate
tpm2_flushcontext session.dat
rm session.dat

Générez une paire de clés RSA sur TPM-A qui sera dupliquée (notez que le mot de passe est `foo')

tpm2_create -C primary.ctx -g sha256 -G rsa -p foo -r key.prv \
-u key.pub  -L dpolicy.dat -a "sensitivedataorigin|userwithauth|decrypt|sign"
tpm2_load -C primary.ctx -r key.prv -u key.pub -c key.ctx
tpm2_readpublic -c key.ctx -o dup.pub

Testez la signature et le chiffrement localement (pour pouvoir comparer plus tard que la même clé a été transférée).

echo "meet me at.." >file.txt
tpm2_rsaencrypt -c key.ctx  -o data.encrypted file.txt
tpm2_sign -c key.ctx -g sha256 -f plain -p foo -o sign.raw file.txt

Comparez le hachage de signature (nous l'utiliserons plus tard pour confirmer que la clé a été transférée à TPM-B) :

sha256sum sign.raw
a1b4e3fbaa29e6e46d95cff498150b6b8e7d9fd21182622e8f5a3ddde257879e

Démarrez une session d'authentification et une commande de politique pour permettre la duplication

tpm2_startauthsession --policy-session -S session.dat
tpm2_policycommandcode -S session.dat -L dpolicy.dat TPM2_CC_Duplicate

NOM

tpm2_duplicate — dupliquer une clé TPM dans un autre TPM

SYNOPSIS

``
tpm2_duplicate [OPTIONS] -C parentHandle -c keyHandle -G algSpec -p password [-r privateBlob] [-s seedBlob] [-u publicBlob]
``
tpm2_duplicate [OPTIONS] -U parentHandle -G algSpec -k privateKey -p password [-r privateBlob] [-s seedBlob] [-u publicBlob]

DESCRIPTION

La commande tpm2_duplicate permet de dupliquer un objet clé TPM créé dans un TPM A vers un TPM B. La clé dupliquée ne peut être utilisée qu'avec le parentHandle spécifié, qui doit être un objet clé dans le TPM B.

L'opération de duplication est réalisée en deux parties. Un appel à tpm2_duplicate sur le TPM A génère les blobs privateBlob, seedBlob et publicBlob. Ces blobs sont ensuite transférés vers le TPM B, où ils sont utilisés par tpm2_import pour recréer l'objet clé. Le processus de duplication utilise un mot de passe pour chiffrer la clé privée.

OPTIONS

``
-C parentHandle
Le handle de l'objet de contexte du parent pour la clé à dupliquer. Il s'agit généralement du handle d'un objet de clé primaire créé dans le TPM source.
``
-c keyHandle
Le handle de l'objet de contexte de la clé à dupliquer.
``
-U parentHandle
Le handle de l'objet de contexte du parent pour la clé à dupliquer. Il s'agit généralement du handle d'un objet de clé primaire créé dans le TPM source.
``
-k privateKey
Spécifie le fichier contenant la clé privée au format PEM. Ceci est utilisé lors de la duplication d'une clé OpenSSL.
``
-G algSpec
Spécifie l'algorithme de chiffrement symétrique utilisé pour le chiffrement de la clé dupliquée. Les options valides sont aes, aes128, aes256, null. Pour dupliquer une clé OpenSSL, utilisez rsa.
``
-p password
Le mot de passe utilisé pour chiffrer la clé privée lors de la duplication. Pour les clés importées via tpm2_import, ce mot de passe sera nécessaire pour le déchiffrement.
``
-r privateBlob
Le fichier de sortie pour la clé privée dupliquée.
``
-s seedBlob
Le fichier de sortie pour le blob de graine (seed) de la duplication.
``
-u publicBlob
Le fichier de sortie pour la clé publique dupliquée.

Format de l'objet de contexte

Le format de l'objet de contexte est un entier de 32 bits qui peut être sous forme d'un handle, ou d'une chaîne de caractères représentant un chemin vers un fichier contenant un handle.

Formatage de l'autorisation

Le formatage de l'autorisation pour les entrées de mot de passe est la chaîne de caractères du mot de passe elle-même.

Spécificateurs d'algorithme

Les spécificateurs d'algorithme sont un ensemble de chaînes de caractères qui définissent l'algorithme de chiffrement symétrique utilisé pour la duplication.

aes
Utilise AES-256 par défaut.
aes128
Utilise AES-128.
aes256
Utilise AES-256.
null
Pas de chiffrement symétrique.
rsa
Utilisé pour dupliquer une clé OpenSSL RSA.

OPTIONS COMMUNES

Ces options sont communes à la plupart des outils tpm2-*.

-h
Affiche l'aide, puis quitte.
-V
Affiche les informations sur la version, puis quitte.
-d
Mode débogage.
--log-level NIVEAU
Définit le niveau de journalisation.
-t tcti
Spécifie le TCTI (Transport Layer Communication Transport Interface) à utiliser.

Configuration du TCTI

La configuration du TCTI se fait via la variable d'environnement TPM2_TCTI ou l'option -t.

OPTIONS TCTI

Les options TCTI suivantes sont disponibles :

device
: Utilise le périphérique de périphérique TPM spécifié par la variable d'environnement TPM2_DEVICE.
mssim
: Utilise le simulateur TPM mssim.
socket
: Utilise une connexion socket TPM spécifiée par la variable d'environnement TPM2_SOCKET.
pkgconf
: Utilise un fichier pkgconf pour spécifier le TCTI.
none
: Désactive toute connexion TCTI.

EXEMPLES

Les exemples suivants montrent comment utiliser la commande tpm2_duplicate pour dupliquer une clé.

Exemple 1 : Duplication d'une clé TPM

Cet exemple montre comment dupliquer une clé TPM d'un TPM A vers un TPM B.

Sur TPM-A :

# Charger le fichier new_parent.pub transféré depuis
    # TPM-B
tpm2_loadexternal -C o -u new_parent.pub -c new_parent.ctx

Démarrer la duplication

tpm2_duplicate -C new_parent.ctx -c key.ctx -G null  \
-p "session:session.dat" -r dup.dpriv -s dup.seed

Copier les fichiers suivants vers TPM-B : * dup.pub * dup.dpriv * dup.seed * (facultativement data.encrypted pour tester le déchiffrement)

Sur TPM-B

Démarrer une session d'authentification par politique

tpm2_startauthsession --policy-session -S session.dat
tpm2_policycommandcode -S session.dat -L dpolicy.dat TPM2_CC_Duplicate

Charger le contexte utilisé pour le transfert

tpm2_flushcontext --transient-object
tpm2_load -C primary.ctx -u new_parent.pub -r new_parent.prv -c new_parent.ctx

Importer le contexte dupliqué par rapport au parent utilisé

tpm2_import -C new_parent.ctx -u dup.pub -i dup.dpriv \
-r dup.prv -s dup.seed -L dpolicy.dat

Charger le contexte de clé dupliquée

tpm2_flushcontext --transient-object
tpm2_load -C new_parent.ctx -u dup.pub -r dup.prv -c dup.ctx

Tester la correspondance de la clé importée

•
Signer
echo "meet me at.." >file.txt
tpm2_sign -c dup.ctx -g sha256 -o sig.rss -p foo file.txt
dd if=sig.rss of=sign.raw bs=1 skip=6 count=256

Comparer le hachage du fichier de signature :

$ sha256sum sign.raw
a1b4e3fbaa29e6e46d95cff498150b6b8e7d9fd21182622e8f5a3ddde257879e
•
Déchiffrement
tpm2_flushcontext --transient-object
tpm2_rsadecrypt -p foo -c dup.ctx -o data.ptext data.encrypted
# cat data.ptext
meet me at..

Exemple 3 : Exportation d'une clé RSA OpenSSL pour un TPM distant

Pour envoyer en toute sécurité une clé RSA générée par OpenSSL à un TPM distant de telle sorte que seul ce TPM distant puisse la charger, et sans exposer la clé privée au système d'exploitation hôte sur la machine distante :

•
Sur le TPM-B de destination, créez un contexte primaire et lisez sa clé publique, puis envoyez primary.pub à la machine source :
tpm2_createprimary -c primary.ctx
tpm2_readpublic -c primary.ctx -o primary.pub
•
Sur la machine source, créez la clé privée RSA et enveloppez-la pour la clé publique du TPM de destination. Similaire à tpm2_makecredential, cette étape ne devrait pas nécessiter de TPM.
openssl genrsa -out rsa.pem
tpm2_duplicate -U primary.pub -G rsa -k rsa.pem -u rsa.pub -r rsa.dpriv -s rsa.seed
•
Envoyez rsa.pub, rsa.dpriv et rsa.seed au TPM-B de destination et importez les fichiers, ce qui les déchiffrera en utilisant primary.ctx pour produire rsa.priv, qui pourra ensuite être chargé et utilisé comme une clé TPM :
tpm2_import -C primary.ctx -G rsa -i rsa.dpriv -s rsa.seed -u rsa.pub -r rsa.priv
tpm2_load -C primary.ctx -c rsa.ctx -u rsa.pub -r rsa.priv

Retour

Les outils peuvent retourner l'un des codes suivants :

•
0 - Succès.
•
1 - Erreur générale non spécifique.
•
2 - Erreur de gestion des options.
•
3 - Erreur d'authentification.
•
4 - Erreur liée au TCTI.
•
5 - Schéma non supporté. Applicable à tpm2_testparams.
