tpm2_policyauthorize(1) Manuel des commandes générales tpm2_policyauthorize(1)

NOM

tpm2_policyauthorize(1) - Permet des politiques mutables en s'associant à une autorité de signature.

SYNTAXE

tpm2_policyauthorize [OPTIONS]

DESCRIPTION

tpm2_policyauthorize(1) - Cette commande permet de modifier les politiques en les associant à une autorité de signature et en permettant le changement du contenu de la politique.

1.
Si la session d'entrée est une session d'essai, cet outil génère un résumé de politique qui associe le nom de la clé publique d'une autorité de signature à la politique en cours d'autorisation.
2.
Si la session d'entrée est une session de politique réelle, tpm2_policyauthorize(1) recherche un ticket de vérification du TPM pour attester que le TPM a vérifié la signature sur le résumé de politique avant d'autoriser la politique dans le résumé de politique.

OPTIONS

•
-L, --policy=FICHIER:

Fichier pour enregistrer le résumé de politique.

•
-S, --session=FICHIER:

Le fichier de session de politique généré via l'option -S de tpm2_startauthsession(1).

•
-i, --input=FICHIER:

Le résumé de politique qui doit être autorisé.

•
-q, --qualification=FICHIER_OU_HEX:

Les données de qualification de politique signées conjointement avec le résumé de politique d'entrée. Ce sont des données uniques que le signataire peut choisir d'inclure dans la signature et qui peuvent être soit un chemin, soit une chaîne hexadécimale.

•
-n, --name=FICHIER:

Fichier contenant le nom de la clé publique de vérification. Cela lie le résumé de politique final à un signataire. Peut être récupéré avec tpm2_readpublic(1)

•
-t, --ticket=FICHIER:

Le fichier ticket pour enregistrer la structure de validation. Ceci est généré avec tpm2_verifysignature(1).

•
--cphash=FICHIER

Chemin du fichier pour enregistrer le hachage des paramètres de la commande. Ceci est communément appelé cpHash. NOTE: Lorsque cette option est sélectionnée, l'outil n'exécute pas réellement la commande, il renvoie simplement un cpHash.

Configuration TCTI

Le TCTI ou « Transmission Interface » est le mécanisme de communication avec le TPM. Les TCTIs peuvent être modifiés pour communiquer avec des TPM sur différents supports.

Pour contrôler le TCTI, les outils respectent :

1.
L'option de ligne de commande -T ou --tcti
2.
La variable d'environnement : TPM2TOOLS_TCTI.

Note : L'option de ligne de commande remplace toujours la variable d'environnement.

Les TCTIs actuellement connus sont :

•
tabrmd - Le gestionnaire de ressources, appelé tabrmd. Notez que tabrmd et abrmd en tant que nom tcti sont synonymes.
•
mssim - Généralement utilisé pour communiquer avec le simulateur logiciel du TPM.
•
device - Utilisé pour parler directement à un fichier de périphérique TPM.
•
none - Ne pas initialiser de connexion avec le TPM. Certains outils permettent des options hors TPM et prennent donc en charge le fait de ne pas utiliser de TCTI. Les outils qui ne le prennent pas en charge généreront une erreur lors de leur tentative d'utilisation sans connexion TCTI. Ne prend pas en charge AUCUNE option et DOIT être présenté comme le texte exact de « none ».

Les arguments de l'option de ligne de commande ou de la variable d'environnement sont sous la forme :

<nom-tcti>:<config-option-tcti>

Spécifier une chaîne vide pour le <nom-tcti> ou la <config-option-tcti> entraîne l'utilisation de la valeur par défaut pour cette partie respectivement.

Défauts TCTI

Lorsqu'un TCTI n'est pas spécifié, le TCTI par défaut est recherché en utilisant la sémantique de dlopen(3). Les outils rechercheront les TCTIs tabrmd, device et mssim DANS CET ORDRE et UTILISERONT LE PREMIER TROUVÉ. Vous pouvez interroger quel TCTI sera choisi par défaut en utilisant l'option -v pour afficher les informations de version. La paire clé-valeur « default-tcti » indiquera lequel des TCTIs susmentionnés est le défaut.

TCTIs Personnalisés

Tout TCTI qui implémente l'interface TCTI dynamique peut être chargé. Les outils utilisent en interne dlopen(3), et la valeur brute nom-tcti est utilisée pour la recherche. Ainsi, cela pourrait être un chemin vers la bibliothèque partagée, ou un nom de bibliothèque tel qu'entendu par la sémantique de dlopen(3).

OPTIONS TCTI

•

tpm2_policyauthorize(1) — tpm2-tools — Arch Linux

NAME

tpm2_policyauthorize - Allows authorization of a policy session by a signature of the policy digest.

SYNOPSIS

tpm2_policyauthorize [OPTIONS] -S [session.ctx] -L [policy.digest] -n [name.ctx]

tpm2_policyauthorize [OPTIONS] -S [session.ctx] -L [policy.digest] -n [name.ctx] -i [policy.digest] -t [ticket.tkt]

DESCRIPTION

The tpm2_policyauthorize command allows the caller to take ownership of the policy by demonstrating knowledge of the signing key. This is accomplished by having the signing key sign the policy digest. The signature is then provided to the TPM using this command.

This is useful for creating policies that are authorized by an external entity. For example, a policy could be created to require a specific PCR value to be met, and then that policy could be authorized by a signature from a trusted entity.

The TPM can be used as an external entity, via a TCTI module, to help manage the policy authorization. The TPM will store the policy digest and the signature of the policy digest.

The tpm2_policyauthorize command can be used to either:

  • authorize a policy session by creating a policy digest, and taking authorization from an external signing authority
  • verify a policy digest that was created using the external signing authority, and then use that authorized policy to authorize a policy session.

OPTIONS

The following options are available:

•
-S session.ctx
The path to the session context file. This is a required argument.
•
-L policy.digest
The path to the file containing the policy digest. This is a required argument.
•
-n name.ctx
The path to the file containing the name of the signing key. This is a required argument.
•
-i policy.digest
The path to the file containing the policy digest to be verified. This is only used when verifying a policy digest.
•
-t ticket.tkt
The path to the file containing the authorization ticket. This is only used when verifying a policy digest.
•
-f signing_alg
The signing algorithm to be used. This is only used when authorizing a policy session.

COMMON OPTIONS

See tpm2_options(7) for common options.

TCTI Configuration

The tpm2_policyauthorize utility can be configured to use different TCTI (TPM Command Transmission Interface) modules. The TCTI module determines how the utility communicates with the TPM. The following TCTI modules are supported:

mssim

The mssim TCTI module is used to connect to a TPM simulator. The configuration string format is a comma-separated list of key-value pairs. The following options are supported:

host
: The hostname or IP address of the TPM simulator.
port
: The port number of the TPM simulator.

Example configuration string:

mssim:host=localhost,port=2321

This configuration string can be set using the environment variable:

export TPM2TOOLS_TCTI=“mssim:host=localhost,port=2321”;

abrmd

For the abrmd TCTI, the configuration string format is a series of simple key value pairs separated by a `,` character. Each key and value string are separated by a `=` character.

TCTI OPTIONS

TCTI abrmd supports two keys:

1.
bus_name : The name of the tabrmd service on the bus (a string).
2.
bus_type : The type of the dbus instance (a string) limited to `session' and `system'.

Specify the tabrmd tcti name and a config string of bus_name=com.example.FooBar:

\--tcti=tabrmd:bus_name=com.example.FooBar

Specify the default (abrmd) tcti and a config string of bus_type=session:

\--tcti:bus_type=session

NOTE: abrmd and tabrmd are synonymous. the various known TCTI modules.

EXAMPLES

Starts a trial session, builds a PCR policy. This PCR policy digest is then an input to the tpm2_policyauthorize(1) along with policy qualifier data and a signer public. The resultant policy digest is then used in creation of objects.

Subsequently when the PCR change and so does the PCR policy digest, the actual policy digest from the tpm2_policyauthorize(1) used in creation of the object will not change. At runtime the new PCR policy needs to be satisfied along with verification of the signature on the PCR policy digest using tpm2_policyauthorize(1)

Create a signing authority

openssl genrsa -out signing_key_private.pem 2048
openssl rsa -in signing_key_private.pem -out signing_key_public.pem -pubout
tpm2_loadexternal -G rsa -C o -u signing_key_public.pem -c signing_key.ctx -n signing_key.name

Create the authorize policy digest

tpm2_startauthsession -S session.ctx
tpm2_policyauthorize -S session.ctx -L authorized.policy -n signing_key.name
tpm2_flushcontext session.ctx

Create a policy to be authorized like a PCR policy

tpm2_pcrread -opcr0.sha256 sha256:0
tpm2_startauthsession -S session.ctx
tpm2_policypcr -S session.ctx -l sha256:0 -f pcr0.sha256 -L pcr.policy_desired
tpm2_flushcontext session.ctx

Sign the policy

openssl dgst -sha256 -sign signing_key_private.pem -out pcr.signature pcr.policy_desired

Create a TPM object like a sealing object with the authorized policy based authentication

tpm2_createprimary -C o -g sha256 -G rsa -c prim.ctx
tpm2_create -g sha256 -u sealing_pubkey.pub -r sealing_prikey.pub -i- -C prim.ctx -L authorized.policy <<< "secret to seal"

Verify the desired policy digest comes from the signing authority, read the actual value of PCR and check that read policy and desired policy are equal.

tpm2_verifysignature -c signing_key.ctx -g sha256 -m pcr.policy_desired -s pcr.signature -t verification.tkt -f rsassa
tpm2_startauthsession \--policy-session -S session.ctx
tpm2_policypcr -S session.ctx -l sha256:0 -L pcr.policy_read
tpm2_policyauthorize -S session.ctx -L authorized.policy -i pcr.policy_desired -n signing_key.name -t verification.tkt
tpm2_load -C prim.ctx -u sealing_pubkey.pub -r sealing_prikey.pub -c sealing_key.ctx
unsealed=$(tpm2_unseal -p"session:session.ctx" -c sealing_key.ctx)
echo $unsealed
tpm2_flushcontext session.ctx

Returns

Tools can return any of the following codes:

•
0 - Success.
•
1 - General non-specific error.
•
2 - Options handling error.
•
3 - Authentication error.
•
4 - TCTI related error.
•
5 - Non supported scheme. Applicable to tpm2_testparams.

Limitations

It expects a session to be already established via tpm2_startauthsession(1) and requires one of the following:

•
direct device access
•
extended session support with tpm2-abrmd.

Without it, most resource managers will not save session state between command invocations.
