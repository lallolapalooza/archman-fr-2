tpm2_checkquote(1) Manuel des commandes générales tpm2_checkquote(1)

NOM

tpm2_checkquote(1) - Valide une citation fournie par un TPM.

SYNTAXE

tpm2_checkquote [OPTIONS]

DESCRIPTION

tpm2_checkquote(1) - Utilise la partie publique de la clé fournie pour valider une citation générée par un TPM. Cela validera la signature par rapport au message de citation et, si fourni, vérifiera que les données de qualification et les valeurs des PCR correspondent à celles de la citation. Les valeurs des PCR peuvent être fournies avec ou sans les informations de sélection des PCR (TPML_PCR_SELECTION). Un exemple de valeurs de PCR sans les informations de sélection des PCR est la sortie de tpm2_pcrread. Si la valeur du PCR est spécifiée sans les informations de sélection du PCR, alors la chaîne de sélection du PCR doit être spécifiée à l'aide de l'option -l pour interpréter les données du PCR.

OPTIONS

•
-u, --public=FICHIER:

Entrée fichier pour la partie publique de la clé de vérification de signature. Soit le fichier pem, soit le fichier de format public tss.

•
-g, --hash-algorithm=ALGORITHME:

L'algorithme de hachage utilisé pour digérer le message.

•
-m, --message=FICHIER:

Le fichier message de la citation qui constitue les données signées par le TPM.

•
-s, --signature=FICHIER:

Le fichier signature d'entrée de la signature à valider.

•
-f, --pcr=FICHIER:

Fichier d'entrée PCR optionnel pour enregistrer la liste des valeurs de PCR incluses dans la citation.

•
-l, --pcr-list=PCR:

La liste des banques de PCR et les identifiants des PCR sélectionnés pour chaque banque.

•
-q, --qualification=CHAINE_HEX_OU_CHEMIN:

Données de qualification pour la citation. Peut être une chaîne hexadécimale ou un chemin. Ceci est généralement utilisé pour ajouter un nonce contre les attaques par rejeu.

•
-F, --format=FORMAT:

OBSOLÈTE et IGNORÉE car superflue.

Spécificateurs complexes

Les objets, lorsqu'ils sont spécifiés pour la création par le TPM, ont de nombreux algorithmes à remplir dans les données publiques. Des choses comme le type, le schéma et les détails asymétriques, la taille de la clé, etc. Voici le format général pour spécifier ces données : <type>:<schéma>:<détails-symétriques>

Spécificateurs de type

Cette partie du spécificateur d'algorithme complexe est requise. Les schémas et les détails symétriques restants seront par défaut en fonction du type spécifié et du type de l'objet créé.

•
aes - AES par défaut : aes128
•
aes128<mode> - AES 128 bits avec mode optionnel (ctr|ofb|cbc|cfb|ecb). Si le mode n'est pas spécifié, il est par défaut à null.
•
aes192<mode> - Identique à aes128<mode>, sauf pour une taille de clé de 192 bits.
•
aes256<mode> - Identique à aes128<mode>, sauf pour une taille de clé de 256 bits.
•
sm4 - SM4 par défaut : sm4128
•
sm4128 ou sm4_128 <mode> - SM4 128 bits avec mode optionnel (ctr|ofb|cbc|cfb|ecb). Si le mode n'est pas spécifié, il est par défaut à null.
•
ecc - Courbe elliptique, par défaut ecc256.
•
ecc192 ou ecc_nist_p192 - Courbe NIST ECC 192 bits
•
ecc224 ou ecc_nist_p224 - Courbe NIST ECC 224 bits
•
ecc256 ou ecc_nist_p256 - Courbe NIST ECC 256 bits
•
ecc384 ou ecc_nist_p384 - Courbe NIST ECC 384 bits
•
ecc521 ou ecc_nist_p521 - Courbe NIST ECC 521 bits
•
ecc_sm2 ou ecc_sm2_p256 - Courbe SM2 256 bits
•
rsa - RSA par défaut : rsa2048
•
rsa1024 - RSA avec une taille de clé de 1024 bits.
•
rsa2048 - RSA avec une taille de clé de 2048 bits.
•
rsa3072 - RSA avec une taille de clé de 3072 bits.
•
rsa4096 - RSA avec une taille de clé de 4096 bits.

Spécificateurs de schéma

Ensuite, il y a un champ optionnel, il peut être sauté.

Les schémas sont généralement des Schémas de Signature ou des Schémas de Chiffrement Asymétrique. La plupart des schémas de signature prennent un algorithme de hachage directement après le schéma de signature. Si l'algorithme de hachage est manquant, il est par défaut à sha256. Certains ne prennent aucun argument, et d'autres en prennent plusieurs.

Option de hachage

Pour les schémas de signature et les schémas de chiffrement asymétrique, un algorithme de hachage peut être spécifié. Par exemple, les schémas de signature comme rsassa peuvent être suivis par un spécificateur de hachage tel que sha256. Si aucun hachage n'est spécifié, le comportement par défaut dépend du schéma de signature.

•
rsassa[:<hash-alg>] - Schéma de signature RSA avec remplissage RSA (RSASSA)
•
rsapss[:<hash-alg>] - Schéma de signature RSA avec remplissage PS (RSAPSS)
•
ecdsa[:<hash-alg>] - Schéma de signature DSA elliptique (ECDSA)
•
ecdaa[:<hash-alg>] - Schéma de signature DSA basé sur les attributs elliptiques (ECDAA)
•
ecschnorr[:<hash-alg>] - Schéma de signature Schnorr elliptique (ECSchnorr)
•
sm2[:<hash-alg>] - Schéma de signature SM2

Les schémas de chiffrement asymétrique tels que oaep, rsaes et ecdh peuvent également accepter des spécificateurs d'algorithmes de hachage.

•
oaep[:<hash-alg>] - Schéma de chiffrement à clé publique optimal avec remplissage asymétrique (OAEP)
•
rsaes[:<hash-alg>] - Schéma de chiffrement RSAES
•
ecdh[:<hash-alg>] - Accord de clé Diffie-Hellman elliptique (ECDH)

Si le spécificateur de hachage n'est pas fourni, le comportement par défaut dépend du schéma. Pour les schémas de signature, le défaut est généralement sha256. Pour les schémas de chiffrement, il n'y a pas de valeur par défaut et un hachage doit être spécifié.

La valeur null peut également être utilisée, par exemple rsassa:null. Cela indique qu'aucun schéma de hachage spécifique n'est appliqué.

Détails symétriques

Pour les algorithmes symétriques, des détails supplémentaires tels que le mode de fonctionnement peuvent être spécifiés. Par exemple : aes128:cbc. Le mode par défaut est null s'il n'est pas spécifié.

Exemples

Voici quelques exemples de spécificateurs d'algorithmes complexes :

•
rsa2048:rsapss:sha256 - Clé RSA 2048 bits utilisant le schéma de signature RSAPSS avec SHA256.
•
ecc384:ecdsa:sha384 - Clé ECC 384 bits utilisant le schéma de signature ECDSA avec SHA384.
•
aes256:cbc - Algorithme AES 256 bits en mode CBC.
•
sm4128:ctr - Algorithme SM4 128 bits en mode CTR.

EXEMPLE

Validez une citation avec une clé publique RSA 2048 bits, un message signé à l'aide de SHA256, et les données de qualification et les PCR fournis dans des fichiers séparés.

La clé publique est dans mykey.pem, le message est dans quote.msg, la signature est dans quote.sig, les données de qualification sont dans quote.qual, et les valeurs des PCR sont dans quote.pcr. L'algorithme de hachage utilisé pour la signature était SHA256.

$ tpm2_checkquote -u mykey.pem -m quote.msg -s quote.sig -q quote.qual -f quote.pcr -l sha256

Ce spécificateur de schéma est suivi d'un nombre (taille max UINT16) puis suivi d'un tiret (-) et d'un algorithme de hachage valide. * ecdaa Par exemple, ecdaa4-sha256. Si aucun nombre n'est spécifié, il est par défaut à 4.

Schémas de Spécification sans Option

Ce spécificateur de schéma ne prend AUCUN argument. * rsaes

Spécificateurs de Détails Symétriques

Ce champ est optionnel et est déterminé par défaut en fonction du *type* d'objet créé et de ses attributs. Généralement, tout spécificateur *symétrique* valide de la liste des spécificateurs de *Type* devrait fonctionner. S'il n'est pas spécifié, les détails symétriques d'un objet asymétrique sont par défaut *aes128cfb*.

Exemples

Créer une clé rsa2048 avec un schéma de chiffrement asymétrique rsaes

tpm2_create -C parent.ctx -G rsa2048:rsaes -u key.pub -r key.priv

Créer une clé ecc256 avec un schéma de signature ecdaa avec un nombre de 4 et un hachage sha384

/tpm2_create -C parent.ctx -G ecc256:ecdaa4-sha384 -u key.pub -r key.priv algorithmes cryptographiques *ALGORITHME*.

Format de Spécification de Signature

Sélection du format pour le fichier de sortie de la signature. *tss* (par défaut) produira un blob binaire conformément à la spécification TPM 2.0 et à tout remplissage potentiel du compilateur. L'option *plain* produira les données de signature brutes telles que définies par l'algorithme cryptographique utilisé. *FORMAT* de signature.

Configuration du TCTI

Le TCTI ou « Interface de Transmission » est le mécanisme de communication avec le TPM. Les TCTIs peuvent être modifiés pour communiquer avec des TPM sur différents supports.

Pour contrôler le TCTI, les outils respectent :

1.
L'option de ligne de commande -T ou --tcti
2.
La variable d'environnement : TPM2TOOLS_TCTI.

Remarque : L'option de ligne de commande remplace toujours la variable d'environnement.

Les TCTIs actuellement connus sont :

•
tabrmd - Le gestionnaire de ressources, appelé tabrmd. Notez que tabrmd et abrmd en tant que nom tcti sont synonymes.
•
mssim - Généralement utilisé pour communiquer avec le simulateur logiciel TPM.
•
device - Utilisé lors de la communication directe avec un fichier de périphérique TPM.
•
none - N'initialise pas de connexion avec le TPM. Certains outils permettent des options hors TPM et supportent donc de ne pas utiliser de TCTI. Les outils qui ne le supportent pas généreront une erreur lors de leur tentative d'utilisation sans connexion TCTI. Ne supporte *AUCUNE* option et *DOIT* être présenté comme le texte exact de « none ».

Les arguments de l'option de ligne de commande ou de la variable d'environnement sont sous la forme :

<nom_tcti>:<configuration_option_tcti>

Spécifier une chaîne vide pour <nom_tcti> ou <configuration_option_tcti> utilise la valeur par défaut pour cette partie respectivement.

Défauts du TCTI

Lorsqu'un TCTI n'est pas spécifié, le TCTI par défaut est recherché en utilisant la sémantique de dlopen(3). Les outils rechercheront *tabrmd*, *device* et *mssim* TCTIs **DANS CET ORDRE** et **UTILISERONT LE PREMIER TROUVÉ**. Vous pouvez interroger quel TCTI sera choisi par défaut en utilisant l'option **-v** pour afficher les informations de version. La paire clé-valeur « default-tcti » indiquera lequel des TCTIs susmentionnés est le défaut.

TCTIs Personnalisés

Tout TCTI qui implémente l'interface TCTI dynamique peut être chargé. Les outils utilisent en interne dlopen(3), et la valeur brute *nom_tcti* est utilisée pour la recherche. Ainsi, il pourrait s'agir d'un chemin vers la bibliothèque partagée, ou d'un nom de bibliothèque tel qu'interprété par la sémantique de dlopen(3).

OPTIONS TCTI

Cette collection d'options est utilisée pour configurer les divers modules TCTI connus disponibles :

•
device : Pour le TCTI device, le fichier de périphérique caractère TPM à utiliser par le TCTI device peut être spécifié. Le défaut est /dev/tpm0.

Exemple : -T device:/dev/tpm0 ou export TPM2TOOLS_TCTI=« device:/dev/tpm0 »

•
mssim : Pour le TCTI mssim, le nom de domaine ou l'adresse IP et le numéro de port utilisés par le simulateur peuvent être spécifiés. Les défauts sont 127.0.0.1 et 2321.

Exemple : -T mssim:host=localhost,port=2321 ou export TPM2TOOLS_TCTI=« mssim:host=localhost,port=2321 »

•
abrmd : Pour le TCTI abrmd, le format de la chaîne de configuration est une série de paires clé-valeur simples séparées par un caractère `,'. Chaque chaîne clé et valeur est séparée par un caractère `= '.
•
TCTI abrmd supporte deux clés :
1.
`bus_name' : Le nom du service tabrmd sur le bus (une chaîne de caractères).
2.
`bus_type' : Le type de l'instance dbus (une chaîne de caractères) limitée à `session' et `system'.

Spécifiez le nom tcti tabrmd et une chaîne de configuration de bus_name=com.example.FooBar :

\--tcti=tabrmd:bus_name=com.example.FooBar

Spécifiez le tcti par défaut (abrmd) et une chaîne de configuration de bus_type=session :

\--tcti:bus_type=session

REMARQUE : abrmd et tabrmd sont synonymes. les divers modules TCTI connus.

EXEMPLES

Générer une citation avec un TPM, puis la vérifier

tpm2_createek -c 0x81010001 -G rsa -u ekpub.pem -f pem
tpm2_createak -C 0x81010001 -c ak.ctx -G rsa -s rsassa -g sha256 \
-u akpub.pem -f pem -n ak.name
tpm2_quote -c ak.ctx -l sha256:15,16,22 -q abc123 -m quote.msg -s quote.sig \
  -o quote.pcrs -g sha256
tpm2_checkquote -u akpub.pem -m quote.msg -s quote.sig -f quote.pcrs -g sha256 \
  -q abc123
