tpm2_createak(1) Manuel des commandes générales tpm2_createak(1)

NOM

tpm2_createak(1) - Générer une clé d'attestation avec l'algorithme donné sous la hiérarchie d'endossement.

SYNOPSIS

tpm2_createak [OPTIONS]

DESCRIPTION

tpm2_createak(1) - Génère une clé d'attestation (AK) avec l'algorithme donné sous la hiérarchie d'endossement. Le contexte de la clé d'attestation est spécifié via -c.

L'outil produit en sortie standard une représentation YAML du nom de la clé chargée, par exemple :

loaded-key:
  name: 000bac149518baa05540a0678bd9b624f8a98d042e46c60f4d098ba394d36fc49268

OPTIONS

•
-P, --eh-auth=AUTH:

La valeur d'autorisation pour la hiérarchie d'endossement.

•
-p, --ak-auth=AUTH

La valeur d'autorisation pour l'objet clé d'attestation créé.

•
-C, --ek-context=OBJECT:

L'objet clé d'endossement.

•
-c, --ak-context=FILE:

Le chemin du fichier où sauvegarder le contexte de l'objet clé d'attestation.

•
-G, --key-algorithm=ALGORITHM:

Spécifie l'algorithme de la clé d'attestation. Supporte :

•
ecc - Une clé NIST_P256 par défaut. Des courbes alternatives peuvent être sélectionnées en utilisant des spécificateurs d'algorithme (par ex. ecc384 ou ecc_nist_p384).
•
rsa - Une clé RSA2048.
•
keyedhash - clé hmac.
•
-g, --hash-algorithm=ALGORITHM:

Spécifie l'algorithme de hachage utilisé pour la signature.

•
-s, --signing-algorithm=ALGORITHM:

L'algorithme de signature.

•
-u, --public=FILE:

Le fichier où sauvegarder la partie publique de la clé d'attestation.

•
-n, --ak-name=FILE:

Le fichier où sauvegarder le nom de la clé d'attestation, optionnel.

•
-r, --private=FILE:

Le fichier de sortie contenant la partie sensible de l'objet, optionnel. # Détails de protection

Les objets qui peuvent sortir du TPM doivent être protégés (confidentialité et intégrité). Par exemple, les objets transitoires nécessitent que des données protégées par le TPM (clé ou matériel de scellage) soient stockées à l'extérieur du TPM. Ceci est visible dans des outils comme tpm2_create(1), où l'option -r produit ces données protégées. Ce blob contient les parties sensibles de l'objet. Les parties sensibles de l'objet sont protégées par l'objet parent, en utilisant les détails de chiffrement symétrique du parent pour chiffrer et authentifier les données sensibles avec un HMAC.

Des détails approfondis peuvent être trouvés dans les sections 23 de :

•
https://trustedcomputinggroup.org/wp-content/uploads/TPM-Rev-2.0-Part-1-Architecture-01.38.pdf

Notamment la Figure 20, est pertinente, même si elle se réfère spécifiquement aux blobs de duplication, le processus est identique.

Si la sortie provient de tpm2_duplicate(1), la sortie sera légèrement différente, comme décrit entièrement dans la section 23.

•
-f, --format:

Sélection du format pour le fichier de sortie de la clé publique. 'tss' (par défaut) produira un blob binaire conformément à la spécification TPM 2.0. 'pem' produira une clé publique encodée en PEM compatible OpenSSL. 'der' produira une clé publique encodée en DER compatible OpenSSL. 'tpmt' produira un blob binaire de la structure TPMT_PUBLIC référencée par les spécifications TPM 2.0.

Sélection du format pour le fichier de sortie de signature.

•
-q, --ak-qualified-name=FILE:

Le nom qualifié de l'objet clé d'attestation. Le nom qualifié est le nom qualifié de l'objet parent (l'EK dans ce cas) et le nom de l'objet lui-même. Ainsi, le nom qualifié d'un objet sert à le lier à ses parents.

Références

Format de l'objet de contexte

Le type d'un objet de contexte, qu'il s'agisse d'un handle ou d'un nom de fichier, est déterminé selon la logique suivante *dans l'ordre* :

•
Si l'argument est un chemin de fichier, alors le fichier est chargé comme un objet transitoire TPM restauré.
•
Si l'argument correspond à un préfixe de l'un des éléments suivants :
•
owner: la hiérarchie propriétaire
•
platform: la hiérarchie de plateforme
•
endorsement: la hiérarchie d'endossement
•
lockout: l'objet persistant de contrôle de verrouillage
•
Si l'argument peut être chargé comme un nombre, il sera traité comme un handle, par ex. 0x81010013 et utilisé directement._OBJECT_.

Formatage de l'autorisation

L'autorisation d'utilisation d'un objet en TPM2.0 peut se présenter sous 3 formes différentes : 1. Mot de passe 2. HMAC 3. Sessions

NOTE : « Les autorisations utilisent par défaut le MOT DE PASSE VIDE lorsqu'elles ne sont pas spécifiées ».

Mots de passe

Les mots de passe sont interprétés sous les formes suivantes en utilisant des identifiants de préfixe.

Note : Par défaut, les mots de passe sont considérés comme étant sous forme de chaîne lorsqu'ils n'ont pas de préfixe.

Chaîne de caractères

Un mot de passe sous forme de chaîne de caractères, spécifié par le préfixe « str: » ou son absence (chaîne brute sans préfixe) n'est pas interprété et est directement utilisé pour l'autorisation.

Exemples

foobar
str:foobar

Chaîne hexadécimale

Un mot de passe sous forme de chaîne hexadécimale, spécifié par le préfixe « hex: », est converti d'une forme hexadécimale en une forme de tableau d'octets, permettant ainsi les mots de passe avec des caractères non imprimables et/ou peu pratiques pour le terminal.

Exemple

hex:1122334455667788

Fichier

Un mot de passe basé sur un fichier, spécifié par le préfixe « file: », doit être le chemin d'un fichier contenant le mot de passe à lire par l'outil, ou un « - » pour utiliser l'entrée standard. Stocker les mots de passe dans des fichiers empêche les fuites d'informations, les mots de passe passés en tant qu'options peuvent être lus depuis la liste des processus ou les fonctionnalités courantes de l'historique du shell.

Exemples

# pour utiliser l'entrée standard et être invité
file:-
# pour utiliser un fichier depuis un chemin
file:chemin/vers/fichier/motdepasse
# pour echo un mot de passe via l'entrée standard :
echo foobar | tpm2_tool -p file:-
# pour utiliser un here-string bash via l'entrée standard :
tpm2_tool -p file:- <<< foobar

Sessions de politique

Lorsque vous utilisez une session de politique pour autoriser l'utilisation d'un objet, préfixez l'argument de l'option avec le mot-clé session. Indiquez ensuite le chemin d'accès à un fichier de session qui a été créé avec tpm2_startauthsession(1). Facultativement, si la session nécessite une valeur d'authentification à envoyer avec le descripteur de session (par exemple, mot de passe de politique), ajoutez un + et une chaîne comme décrit dans la section Mots de passe.

Exemples

Pour utiliser un fichier de contexte de session appelé session.ctx.

session:session.ctx

Pour utiliser un fichier de contexte de session appelé session.ctx ET envoyer la valeur d'authentification mypassword.

session:session.ctx+mypassword

Pour utiliser un fichier de contexte de session appelé session.ctx ET envoyer la valeur d'authentification HEX 0x11223344.

session:session.ctx+hex:11223344

Autorisations PCR

Vous pouvez satisfaire une politique PCR en utilisant le préfixe “pcr:” et le mini-langage PCR. Le mini-langage PCR est le suivant : <pcr-spec>=<fichier-pcr-brut>

Le spécificateur PCR est documenté dans la section “Spécificateurs de banque PCR”.

Le fichier-pcr-brut est un argument optionnel qui contient la sortie des contenus PCR bruts tels que retournés par tpm2_pcrread(1).

Spécificateurs de banque PCR

Exemples

Pour satisfaire une politique PCR de sha256 sur les banques 0, 1, 2 et 3, utilisez un spécificateur de :

pcr:sha256:0,1,2,3

en spécifiant AUTH.

Spécificateurs complexes

Les objets, lorsqu'ils sont spécifiés pour la création par le TPM, ont de nombreux algorithmes à remplir dans les données publiques. Des éléments tels que le type, le schéma et les détails asymétriques, la taille de la clé, etc. Voici le format général pour spécifier ces données : <type>:<schéma>:<détails-symétriques>

Spécificateurs de type

Cette partie du spécificateur d'algorithme complexe est requise. Les schémas restants et les détails symétriques seront par défaut en fonction du type spécifié et du type de l'objet en cours de création.

•
aes - AES par défaut : aes128
•
aes128<mode> - AES 128 bits avec mode optionnel (ctr|ofb|cbc|cfb|ecb). Si le mode n'est pas spécifié, la valeur par défaut est null.
•
aes192<mode> - Identique à aes128<mode>, sauf pour une taille de clé de 192 bits.
•
aes256<mode> - Identique à aes128<mode>, sauf pour une taille de clé de 256 bits.
•
sm4 - SM4 par défaut : sm4128
•
sm4128 ou sm4_128 <mode> - SM4 128 bits avec mode optionnel (ctr|ofb|cbc|cfb|ecb). Si le mode n'est pas spécifié, la valeur par défaut est null.
•
ecc - Courbe elliptique, par défaut ecc256.
•
ecc192 ou ecc_nist_p192 - Courbe NIST ECC 192 bits
•
ecc224 ou ecc_nist_p224 - Courbe NIST ECC 224 bits
•
ecc256 ou ecc_nist_p256 - Courbe NIST ECC 256 bits
•
ecc384 ou ecc_nist_p384 - Courbe NIST ECC 384 bits
•
ecc521 ou ecc_nist_p521 - Courbe NIST ECC 521 bits
•
ecc_sm2 ou ecc_sm2_p256 - Courbe SM2 256 bits
•
rsa - RSA par défaut : rsa2048
•
rsa1024 - RSA avec une taille de clé de 1024 bits.
•
rsa2048 - RSA avec une taille de clé de 2048 bits.
•
rsa3072 - RSA avec une taille de clé de 3072 bits.
•
rsa4096 - RSA avec une taille de clé de 4096 bits.

Spécificateurs de schémas

Ensuite, il y a un champ optionnel, il peut être sauté.

Les schémas sont généralement des schémas de signature ou des schémas de chiffrement asymétrique. La plupart des schémas de signature prennent un algorithme de hachage directement après le schéma de signature. Si l'algorithme de hachage est manquant, il est par défaut sha256. Certains ne prennent aucun argument, et certains prennent plusieurs arguments.

Spécificateurs de schéma avec hachage optionnel

Ces spécificateurs de schéma sont suivis d'un trait et d'un algorithme de hachage valide, par exemple : oaep-sha256.

•
oaep
•
ecdh
•
rsassa
•
rsapss
•
ecdsa
•
ecschnorr
•
sm2

Spécificateurs de schéma à options multiples

Ce spécificateur de schéma est suivi d'un nombre (taille max UINT16) puis d'un trait (-) et d'un algorithme de hachage valide. * ecdaa Par exemple, ecdaa4-sha256. Si aucun nombre n'est spécifié, la valeur par défaut est 4.

Spécificateurs de schéma sans option

Ce spécificateur de schéma ne prend AUCUN argument. * rsaes

Spécificateurs de détails symétriques

Ce champ est facultatif et par défaut en fonction du type d'objet en cours de création et de ses attributs. Généralement, tout spécificateur symétrique valide de la liste des Spécificateurs de type devrait fonctionner. S'il n'est pas spécifié, les détails symétriques des objets asymétriques sont par défaut aes128cfb.

Exemples

Créer une clé rsa2048 avec un schéma de chiffrement asymétrique rsaes

tpm2_create -C parent.ctx -G rsa2048:rsaes -u key.pub -r key.priv

Créer une clé ecc256 avec un schéma de signature ecdaa avec un compte de 4 et un hachage sha384

/tpm2_create -C parent.ctx -G ecc256:ecdaa4-sha384 -u key.pub -r key.priv algorithmes cryptographiques ALGORITHME.

L'option plain produira les données de signature brutes telles que définies par l'algorithme cryptographique utilisé.

Configuration TCTI

Le TCTI ou « Interface de Transmission » est le mécanisme de communication avec le TPM. Les TCTIs peuvent être modifiés pour communiquer avec les TPMs sur différents supports.

Pour contrôler le TCTI, les outils respectent :

1.
L'option de ligne de commande -T ou --tcti
2.
La variable d'environnement : TPM2TOOLS_TCTI.

Note : L'option de ligne de commande remplace toujours la variable d'environnement.

Les TCTIs actuellement connus sont :

•
tabrmd - Le gestionnaire de ressources, appelé tabrmd. Notez que tabrmd et abrmd en tant que nom de tcti sont synonymes.
•
mssim - Typiquement utilisé pour communiquer avec le simulateur logiciel TPM.
•
device - Utilisé lors de la communication directe avec un fichier de périphérique TPM.
•
none - N'initialise pas de connexion avec le TPM. Certains outils permettent des options hors-tpm et supportent donc de ne pas utiliser de TCTI. Les outils qui ne le supportent pas généreront une erreur lorsqu'ils tenteront d'être utilisés sans connexion TCTI. Ne supporte *AUCUNE* option et *DOIT ÊTRE* présenté comme le texte exact de « none ».

Les arguments de l'option de ligne de commande ou de la variable d'environnement sont sous la forme :

<nom-tcti>:<config-option-tcti>

Spécifier une chaîne vide pour <nom-tcti> ou <config-option-tcti> entraîne l'utilisation de la valeur par défaut pour cette partie respectivement.

Défauts TCTI

Lorsqu'un TCTI n'est pas spécifié, le TCTI par défaut est recherché en utilisant les sémantiques de dlopen(3). Les outils rechercheront les TCTIs tabrmd, device et mssim **DANS CET ORDRE** et **UTILISERONT LE PREMIER TROUVÉ**. Vous pouvez interroger quel TCTI sera choisi par défaut en utilisant l'option -v pour afficher les informations de version. La paire clé-valeur « default-tcti » indiquera lequel des TCTIs susmentionnés est le défaut.

TCTIs Personnalisés

Tout TCTI qui implémente l'interface TCTI dynamique peut être chargé. Les outils utilisent en interne dlopen(3), et la valeur brute nom-tcti est utilisée pour la recherche. Ainsi, il pourrait s'agir d'un chemin vers la bibliothèque partagée, ou d'un nom de bibliothèque tel qu'interprété par les sémantiques de dlopen(3).

OPTIONS TCTI

Cette collection d'options est utilisée pour configurer les divers modules TCTI connus disponibles :

•
device: Pour le TCTI device, le fichier de périphérique caractère TPM à utiliser par le TCTI device peut être spécifié. Le défaut est /dev/tpm0.

Exemple : -T device:/dev/tpm0 ou export TPM2TOOLS_TCTI=“device:/dev/tpm0”

•
mssim: Pour le TCTI mssim, le nom de domaine ou l'adresse IP et le numéro de port utilisés par le simulateur peuvent être spécifiés. Les défauts sont 127.0.0.1 et 2321.

Exemple : -T mssim:host=localhost,port=2321 ou export TPM2TOOLS_TCTI=“mssim:host=localhost,port=2321”

•
abrmd: Pour le TCTI abrmd, le format de la chaîne de configuration est une série de paires clé-valeur simples séparées par un caractère `,'. Chaque clé et valeur sont séparées par un caractère `= '.
•
Le TCTI abrmd supporte deux clés :
1.
`bus_name' : Le nom du service tabrmd sur le bus (une chaîne).
2.
`bus_type' : Le type de l'instance dbus (une chaîne) limitée à `session' et `system'.

Spécifier le nom du TCTI tabrmd et une chaîne de configuration de bus_name=com.example.FooBar :

\--tcti=tabrmd:bus_name=com.example.FooBar

Spécifier le TCTI par défaut (abrmd) et une chaîne de configuration de bus_type=session :

\--tcti:bus_type=session

NOTE : abrmd et tabrmd sont synonymes. les divers modules TCTI connus.
