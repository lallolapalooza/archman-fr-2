NOM

tpm2_sign(1) - Signe un hachage ou un message en utilisant le TPM.

SYNTAXE

tpm2_sign [OPTIONS] [ARGUMENT]

DESCRIPTION

tpm2_sign(1) - Génère la signature du message spécifié ou de son condensé de message en utilisant la clé de signature symétrique ou asymétrique spécifiée.

Lors de la signature d'un message, l'utilitaire tpm2_sign calcule d'abord le condensé du message, similaire à la commande tpm2_hash. Il génère également un ticket de validation sous les hiérarchies TPM2_RH_NULL ou TPM2_RH_OWNER respectivement pour les clés de signature non restreintes ou restreintes.

Bien que la signature de messages soit une fonctionnalité de cet outil, il est recommandé d'utiliser d'abord l'outil tpm2_hash et de passer le condensé et le ticket de validation.

NOTE : Si la clé de signature est une clé de signature restreinte, la validation et le condensé doivent être fournis via l'entrée -t. Le ticket indique que le TPM a effectué le hachage du message.

OPTIONS

•
-c, --key-context=OBJET:

Objet contexte pointant vers la clé utilisée pour la signature. Soit un fichier, soit un numéro de descripteur. Voir la section « Format de l'objet contexte ».

•
-p, --auth_AUTH_:

Valeur d'autorisation optionnelle pour utiliser la clé spécifiée par -c. Les valeurs d'autorisation doivent suivre les « normes de formatage d'autorisation », voir la section « Formatage de l'autorisation ».

•
-g, --hash-algorithm=ALGORITHME:

L'algorithme de hachage utilisé pour le condensé du message. Les algorithmes doivent suivre les « normes de formatage », voir la section « Spécificateurs d'algorithmes ». Voir également la section « Algorithmes de hachage pris en charge » pour une liste des algorithmes de hachage pris en charge.

•
-s, --scheme=ALGORITHME:

Le schéma de signature utilisé pour signer le message. Optionnel.

Les schémas de signature doivent suivre les « normes de formatage », voir la section « Spécificateurs d'algorithmes ».

S'il est spécifié, le schéma de signature doit correspondre au type de clé. S'il est laissé non spécifié, un schéma de signature par défaut pour le type de clé sera utilisé.

•
-d, --digest:

Indique que FICHIER est un fichier contenant le condensé du message. Lorsque cette option et -t sont spécifiés, un avertissement est généré et le ticket de validation (-t) est ignoré. Vous ne pouvez pas utiliser cette option pour signer un condensé contre une clé de signature restreinte.

•
-t, --ticket=FICHIER:

Le fichier de ticket, contenant la structure de validation, optionnel.

•
-o, --signature=FICHIER:

Le fichier de signature, enregistre la structure de signature.

•
-f, --format=FORMAT:

Sélection du format pour le fichier de sortie de signature. Voir la section « Spécificateurs de format de signature ».

•
--cphash=FICHIER

Chemin du fichier pour enregistrer le hachage des paramètres de la commande. Ceci est couramment appelé cpHash. NOTE : Lorsque cette option est sélectionnée, l'outil n'exécute pas réellement la commande, il renvoie simplement un cpHash.

•
--commit-index=NOMBRE_NATUREL

La valeur du compteur d'engagement pour déterminer l'index de clé à utiliser dans un schéma de signature ECDAA. La valeur par défaut du compteur est 0.

•
ARGUMENT l'argument de ligne de commande spécifie les données du fichier à signer.

Références

Format de l'objet contexte

Le type d'un objet contexte, qu'il s'agisse d'un descripteur ou d'un nom de fichier, est déterminé selon la logique suivante, dans l'ordre :

•
Si l'argument est un chemin de fichier, alors le fichier est chargé comme un objet transitoire TPM restauré.
•
Si l'argument est une correspondance par préfixe avec l'un des éléments suivants :
•
owner : la hiérarchie propriétaire
•
platform : la hiérarchie de plateforme
•
endorsement : la hiérarchie d'approbation
•
lockout : l'objet persistant de contrôle de verrouillage
•
Si l'argument peut être chargé comme un nombre, il sera traité comme un descripteur, par exemple, 0x81010013 et utilisé directement.

Formatage de l'autorisation

L'autorisation d'utilisation d'un objet en TPM2.0 peut prendre 3 formes différentes : 1. Mot de passe 2. HMAC 3. Sessions

NOTE : Les autorisations par défaut sont le MOT DE PASSE VIDE lorsqu'elles ne sont pas spécifiées.

Mots de passe

Les mots de passe sont interprétés sous les formes suivantes en utilisant des identifiants de préfixe.

Note : Par défaut, les mots de passe sont supposés être sous forme de chaîne de caractères lorsqu'ils n'ont pas de préfixe.

Chaîne de caractères

Un mot de passe sous forme de chaîne de caractères, spécifié par le préfixe « str: » ou son absence (chaîne brute sans préfixe), n'est pas interprété et est directement utilisé pour l'autorisation.

Exemples

foobar
str:foobar

Chaîne hexadécimale

Un mot de passe sous forme de chaîne hexadécimale, spécifié par le préfixe « hex: », est converti d'une forme hexadécimale en une forme de tableau d'octets, permettant ainsi les mots de passe avec des caractères non imprimables et/ou peu conviviaux pour le terminal.

Exemple

hex:1122334455667788

Fichier

Un mot de passe basé sur un fichier, spécifié par le préfixe « file: », doit être le chemin d'un fichier contenant le mot de passe à lire par l'outil, ou un « - » pour utiliser stdin. Stocker les mots de passe dans des fichiers empêche les fuites d'informations ; les mots de passe passés en tant qu'options peuvent être lus à partir de la liste des processus ou des fonctionnalités d'historique du shell courantes.

Exemples

# pour utiliser stdin et être invité
file:-
# pour utiliser un fichier à partir d'un chemin
file:chemin/vers/fichier/motdepasse
# pour transmettre un mot de passe via stdin:
echo motdepasse | tpm2_tool -p file:-
# pour utiliser une here-string bash via stdin:
tpm2_tool -p file:- <<< motdepasse

Sessions

Lors de l'utilisation d'une session de politique pour autoriser l'utilisation d'un objet, préfixez l'argument de l'option avec le mot-clé session. Indiquez ensuite un chemin vers un fichier de session qui a été créé avec tpm2_startauthsession(1). Optionnellement, si la session nécessite une valeur d'authentification à envoyer avec le descripteur de session (par exemple, mot de passe de politique), ajoutez un + et une chaîne comme décrit dans la section Mots de passe.

Exemples

Pour utiliser un fichier de contexte de session appelé session.ctx.

session:session.ctx

    Vous pouvez satisfaire une politique PCR en utilisant le préfixe “pcr:” et le mini-langage PCR. Le mini-langage PCR est le suivant : <spec-pcr>=<fichier-pcr-brut>

    La spécification PCR est documentée dans la section “Spécificateurs de banque PCR”.

    Le fichier-pcr-brut est un argument optionnel qui contient la sortie des contenus PCR bruts tels que retournés par tpm2_pcrread(1).

    Spécificateurs de banque PCR

    Exemples

    Pour satisfaire une politique PCR de sha256 sur les banques 0, 1, 2 et 3, utilisez un spécificateur de :

    pcr:sha256:0,1,2,3

    en spécifiant AUTH.

    Configuration TCTI

    Le TCTI ou "Interface de Transmission" est le mécanisme de communication avec le TPM. Les TCTI peuvent être modifiés pour communiquer avec des TPM via différents médiums.

    Pour contrôler le TCTI, les outils respectent :

    1.
    L'option de ligne de commande -T ou --tcti
    2.
    La variable d'environnement : TPM2TOOLS_TCTI.

    Note : L'option de ligne de commande remplace toujours la variable d'environnement.

    Les TCTI actuellement connus sont :

    •
    tabrmd - Le gestionnaire de ressources, appelé tabrmd. Notez que tabrmd et abrmd en tant que nom tcti sont synonymes.
    •
    mssim - Généralement utilisé pour communiquer avec le simulateur logiciel du TPM.
    •
    device - Utilisé lors de la communication directe avec le fichier de périphérique TPM.
    •
    none - Ne pas initialiser de connexion avec le TPM. Certains outils permettent des options hors-TPM et supportent donc de ne pas utiliser de TCTI. Les outils qui ne le supportent pas généreront une erreur lors de leur tentative d'utilisation sans connexion TCTI. Ne supporte AUCUNE option et DOIT être présenté comme le texte exact de "none".

    Les arguments de l'option de ligne de commande ou de la variable d'environnement sont sous la forme :

    <nom-tcti>:<config-option-tcti>

    Spécifier une chaîne vide pour <nom-tcti> ou <config-option-tcti> entraîne l'utilisation de la valeur par défaut pour cette partie respectivement.

    Défauts TCTI

    Lorsqu'un TCTI n'est pas spécifié, le TCTI par défaut est recherché en utilisant la sémantique de dlopen(3). Les outils rechercheront les TCTI tabrmd, device et mssim DANS CET ORDRE et UTILISERONT LE PREMIER TROUVÉ. Vous pouvez interroger quel TCTI sera choisi par défaut en utilisant l'option -v pour afficher les informations de version. La paire clé-valeur "default-tcti" indiquera lequel des TCTI susmentionnés est le défaut.

    TCTIs personnalisés

    Tout TCTI qui implémente l'interface TCTI dynamique peut être chargé. Les outils utilisent en interne dlopen(3), et la valeur brute nom-tcti est utilisée pour la recherche. Ainsi, cela pourrait être un chemin vers la bibliothèque partagée, ou un nom de bibliothèque tel que compris par la sémantique de dlopen(3).

    OPTIONS TCTI

    Cette collection d'options est utilisée pour configurer les divers modules TCTI connus disponibles :

    •
    device : Pour le TCTI device, le fichier de périphérique caractère TPM à utiliser par le TCTI device peut être spécifié. Le défaut est /dev/tpm0.

    Exemple : -T device:/dev/tpm0 ou export TPM2TOOLS_TCTI=“device:/dev/tpm0”

    •
    mssim : Pour le TCTI mssim, le nom de domaine ou l'adresse IP et le numéro de port utilisés par le simulateur peuvent être spécifiés. Les défauts sont 127.0.0.1 et 2321.

    Exemple : -T mssim:host=localhost,port=2321 ou export TPM2TOOLS_TCTI=“mssim:host=localhost,port=2321”

    •
    abrmd : Pour le TCTI abrmd, le format de la chaîne de configuration est une série de paires clé-valeur simples séparées par un caractère `,'. Chaque chaîne de clé et de valeur est séparée par un caractère `=.
    •
    Le TCTI abrmd prend en charge deux clés :
    1.
    `bus_name' : Le nom du service tabrmd sur le bus (une chaîne).
    2.
    `bus_type' : Le type de l'instance dbus (une chaîne) limitée à `session' et `system'.

    Spécifiez le nom tcti tabrmd et une chaîne de configuration de bus_name=com.example.FooBar :

    \--tcti=tabrmd:bus_name=com.example.FooBar

    Spécifiez le tcti par défaut (abrmd) et une chaîne de configuration de bus_type=session :

    \--tcti:bus_type=session

    NOTE : abrmd et tabrmd sont synonymes. les divers modules TCTI connus.

    EXEMPLES

    Signer et vérifier avec le TPM en utilisant la hiérarchie endorsement

    tpm2_createprimary -C e -c primary.ctx
tpm2_create -G rsa -u rsa.pub -r rsa.priv -C primary.ctx
tpm2_load -C primary.ctx -u rsa.pub -r rsa.priv -c rsa.ctx
echo "my message" > message.dat
tpm2_sign -c rsa.ctx -g sha256 -o sig.rssa message.dat
tpm2_verifysignature -c rsa.ctx -g sha256 -s sig.rssa -m message.dat

    Signer avec le TPM et vérifier avec OSSL

    openssl ecparam -name prime256v1 -genkey -noout -out private.ecc.pem
openssl ec -in private.ecc.pem -out public.ecc.pem -pubout
# Générer un hash à signer
echo "data to sign" > data.in.raw
sha256sum data.in.raw | awk '{ print "000000 " $1 }' | \
xxd -r -c 32 > data.in.digest
# Charger la clé privée pour la signature
tpm2_loadexternal -Q -G ecc -r private.ecc.pem -c key.ctx
# Signer dans le TPM et vérifier avec OSSL
tpm2_sign -Q -c key.ctx -g sha256 -d -f plain -o data.out.signed data.in.digest
openssl dgst -verify public.ecc.pem -keyform pem -sha256 \
-signature data.out.signed data.in.raw
