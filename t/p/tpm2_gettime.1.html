tpm2_gettime(1) Manuel des commandes générales tpm2_gettime(1)

NOM

tpm2_gettime(1) - Obtenir l'heure et l'horloge actuelles du TPM sous une forme signée.

SYNTAXE

tpm2_gettime [OPTIONS] [ARGUMENT]

DESCRIPTION

tpm2_gettime(1) - Fournit une copie signée de l'heure et de l'horloge actuelles du TPM. Il renvoie à la fois une signature et les données sous la forme d'attestation TPM standard, une structure TPMS_ATTEST.

Il affiche sur la sortie standard, au format YAML, la structure TPMS_TIME_INFO du TPM. La structure contient le réglage actuel de l'heure (Time), de l'horloge (Clock), du compteur de réinitialisation (resetCount) et du compteur de redémarrage (restartCount). La structure est affichée sous forme de YAML défini comme suit :

time: 13673142     # valeur 64 bits du temps écoulé depuis la dernière initialisation (_TPM_Init ou TPM2_Startup)
                   # en ms.
clock_info:
  clock: 13673142  # valeur 64 bits du temps pendant lequel le TPM a été alimenté en ms.
  reset_count: 0   # valeur 32 bits du nombre de réinitialisations du TPM depuis la dernière
                   # commande TPM2_Clear.
  restart_count: 0 # valeur 32 bits du nombre de fois où TPM2_Shutdown ou
                   # _TPM_Hash_Start ont été exécutés depuis la dernière réinitialisation du TPM ou
                   # la dernière commande TPM2_Clear.
  safe: yes        # valeur booléenne oui|non indiquant si aucune valeur d'horloge supérieure
                   # à la valeur actuelle de l'horloge n'a été précédemment rapportée par
                   # le TPM.

OPTIONS

•
-c, --key-context=OBJET:

Objet de contexte pointant vers la clé utilisée pour la signature. Il peut s'agir d'un fichier ou d'un numéro de handle. Voir la section « Format de l'objet de contexte ».

•
-p, --auth_AUTH_:

Valeur d'autorisation optionnelle pour utiliser la clé spécifiée par -c. Les valeurs d'autorisation doivent suivre les « normes de formatage d'autorisation », voir la section « Formatage de l'autorisation ».

•
-P, --endorse-auth_AUTH_:

Valeur d'autorisation optionnelle pour la hiérarchie d'endossement. Les valeurs d'autorisation doivent suivre les « normes de formatage d'autorisation », voir la section « Formatage de l'autorisation ».

•
-g, --hash-algorithm=ALGORITHME:

L'algorithme de hachage utilisé pour digérer le message. Les algorithmes doivent suivre les « normes de formatage », voir la section « Spécificateurs d'algorithmes ». Voir également la section « Algorithmes de hachage pris en charge » pour une liste des algorithmes de hachage pris en charge.

•
-s, --scheme=ALGORITHME:

Le schéma de signature utilisé pour signer le message. Optionnel. Les schémas de signature doivent suivre les « normes de formatage », voir la section « Spécificateurs d'algorithmes ». Voir également la section « Schémas de signature pris en charge » pour une liste des schémas de signature pris en charge. Si spécifié, le schéma de signature doit correspondre au type de clé. S'il n'est pas spécifié, un schéma de signature par défaut pour le type de clé sera utilisé.

•
-q, --qualification=FICHIER_OU_CHAINE_HEX:

Optionnel, les données de politique qualifiante que le signataire peut choisir d'inclure dans la signature. Peut être une chaîne hexadécimale ou un chemin.

•
-o, --signature=FICHIER:

Le fichier de signature, enregistre la structure de signature.

•
-f, --format=FORMAT:

Sélection du format pour le fichier de sortie de la signature. Voir la section « Spécificateurs de format de signature ».

•
--attestation=FICHIER:

Les données d'attestation de type TPMS_ATTEST signées avec la clé de signature.

•
--cphash=FICHIER

Chemin du fichier pour enregistrer le hachage des paramètres de la commande. Ceci est communément appelé cpHash. REMARQUE : Lorsque cette option est sélectionnée, l'outil n'exécute pas réellement la commande, il renvoie simplement un cpHash.

•
ARGUMENT est l'argument de ligne de commande qui spécifie les données du fichier à signer.

Références

Format de l'objet de contexte

Le type d'un objet de contexte, qu'il s'agisse d'un handle ou d'un nom de fichier, est déterminé selon la logique suivante, *dans l'ordre* :

•
Si l'argument est un chemin de fichier, le fichier est chargé comme objet transitoire TPM restauré.
•
Si l'argument correspond *par préfixe* à l'un des éléments suivants :
•
owner : la hiérarchie propriétaire
•
platform : la hiérarchie de plateforme
•
endorsement : la hiérarchie d'endossement
•
lockout : l'objet persistant de contrôle de verrouillage
•
Si l'argument peut être chargé comme un nombre, il sera traité comme un handle, par exemple 0x81010013, et utilisé directement. *OBJET*.

Formatage de l'autorisation

L'autorisation d'utilisation d'un objet dans TPM2.0 peut prendre 3 formes différentes : 1. Mot de passe 2. HMAC 3. Sessions

NOTE : « Les autorisations utilisent le **MOT DE PASSE VIDE** par défaut lorsqu'elles ne sont pas spécifiées ».

Mots de passe

Les mots de passe sont interprétés sous les formes suivantes à l'aide d'identifiants de préfixe.

Note : Par défaut, les mots de passe sont considérés comme des chaînes de caractères lorsqu'ils n'ont pas de préfixe.

Chaîne de caractères

Un mot de passe sous forme de chaîne de caractères, spécifié par le préfixe « str: » ou son absence (chaîne brute sans préfixe), n'est pas interprété et est directement utilisé pour l'autorisation.

Exemples

foobar
str:foobar

Chaîne hexadécimale

Un mot de passe sous forme de chaîne hexadécimale, spécifié par le préfixe « hex: », est converti de sa forme hexadécimale en un tableau d'octets, permettant ainsi l'utilisation de mots de passe contenant des caractères non imprimables et/ou peu conviviaux pour le terminal.

Exemple

hex:1122334455667788

Fichier

Un mot de passe basé sur un fichier, spécifié par le préfixe « file: », doit être le chemin d'un fichier contenant le mot de passe à lire par l'outil, ou un « - » pour utiliser l'entrée standard. Le stockage des mots de passe dans des fichiers empêche les fuites d'informations, car les mots de passe passés en tant qu'options peuvent être lus depuis la liste des processus ou les fonctionnalités courantes de l'historique du shell.

Exemples

# pour utiliser l'entrée standard et être invité à saisir
file:-
# pour utiliser un fichier à partir d'un chemin
file:chemin/vers/fichier/mot_de_passe
# pour envoyer un mot de passe via l'entrée standard en écho :
echo monmotdepasse | tpm2_tool -p file:-
# pour utiliser une chaîne here-string bash via l'entrée standard :
tpm2_tool -p file:- <<< monmotdepasse

Sessions

Lors de l'utilisation d'une session de politique pour autoriser l'utilisation d'un objet, préfixez l'argument de l'option avec le mot-clé session. Indiquez ensuite un chemin vers un fichier de session qui a été créé avec tpm2_startauthsession(1). SPÉCIFICATEURS DE SESSION

Les utilitaires tpm2 peuvent utiliser une spécification de session pour alimenter l'authentification du programme TPM. Cette spécification est définie en utilisant le format session:filename. Le spécificateur de session est un chemin d'accès à un fichier de contexte de session.

Le fichier de contexte de session peut également être utilisé pour fournir une valeur d'authentification, qui sera utilisée par le module TPM. Pour ce faire, le nom de fichier est suivi d'un signe plus + et d'une chaîne de caractères comme décrit dans la section Mots de passe.

Exemples

Pour utiliser un fichier de contexte de session nommé session.ctx.

session:session.ctx

Pour utiliser un fichier de contexte de session nommé session.ctx ET envoyer la valeur d'authentification mypassword.

session:session.ctx+mypassword

Pour utiliser un fichier de contexte de session nommé session.ctx ET envoyer la valeur d'authentification HEX 0x11223344.

session:session.ctx+hex:11223344

Autorisations PCR

Vous pouvez satisfaire une politique PCR en utilisant le préfixe “pcr:” et le mini-langage PCR. Le mini-langage PCR est le suivant : <pcr-spec>=<fichier-pcr-brut>

La spécification PCR est documentée dans la section « Spécificateurs de banque PCR ».

Le fichier-pcr-brut est un argument optionnel qui contient la sortie des contenus PCR bruts tels que retournés par tpm2_pcrread(1).

Spécificateurs de banque PCR

Exemples

Pour satisfaire une politique PCR de sha256 sur les banques 0, 1, 2 et 3, utilisez le spécificateur suivant :

pcr:sha256:0,1,2,3

spécifiant AUTH.

Spécificateurs complexes

Les objets, lorsqu'ils sont spécifiés pour la création par le TPM, ont de nombreux algorithmes à peupler dans les données publiques. Des éléments tels que le type, le schéma et les détails asymétriques, la taille de la clé, etc. Voici le format général pour spécifier ces données : <type>:<schéma>:<détails-symétriques>

Spécificateurs de type

Cette partie du spécificateur d'algorithme complexe est requise. Le schéma restant et les détails symétriques seront par défaut en fonction du type spécifié et du type de l'objet en cours de création.

•
aes - AES par défaut : aes128
•
aes128<mode> - AES 128 bits avec mode optionnel (ctr|ofb|cbc|cfb|ecb). Si le mode n'est pas spécifié, la valeur par défaut est null.
•
aes192<mode> - Identique à aes128<mode>, sauf pour une taille de clé de 192 bits.
•
aes256<mode> - Identique à aes128<mode>, sauf pour une taille de clé de 256 bits.
•
sm4 - SM4 par défaut : sm4128
•
sm4128 ou sm4_128 <mode> - SM4 128 bits avec mode optionnel (ctr|ofb|cbc|cfb|ecb). Si le mode n'est pas spécifié, la valeur par défaut est null.
•
ecc - Courbe elliptique, par défaut ecc256.
•
ecc192 ou ecc_nist_p192 - Courbe NIST ECC 192 bits
•
ecc224 ou ecc_nist_p224 - Courbe NIST ECC 224 bits
•
ecc256 ou ecc_nist_p256 - Courbe NIST ECC 256 bits
•
ecc384 ou ecc_nist_p384 - Courbe NIST ECC 384 bits
•
ecc521 ou ecc_nist_p521 - Courbe NIST ECC 521 bits
•
ecc_sm2 ou ecc_sm2_p256 - Courbe SM2 256 bits
•
rsa - RSA par défaut : rsa2048
•
rsa1024 - RSA avec une taille de clé de 1024 bits.
•
rsa2048 - RSA avec une taille de clé de 2048 bits.
•
rsa3072 - RSA avec une taille de clé de 3072 bits.
•
rsa4096 - RSA avec une taille de clé de 4096 bits.

Spécificateurs de schéma

Ensuite, il y a un champ facultatif, il peut être omis.

Les schémas sont généralement des schémas de signature ou des schémas de chiffrement asymétrique. La plupart des schémas de signature prennent un algorithme de hachage directement après le schéma de signature. Si l'algorithme de hachage est manquant, la valeur par défaut est sha256. Certains ne prennent aucun argument, et d'autres en prennent plusieurs.

Spécificateurs de schéma optionnels avec hachage

Ces spécificateurs de schéma sont suivis d'un tiret et d'un algorithme de hachage valide. Par exemple : oaep-sha256.

Ce spécificateur de schéma est suivi d'un nombre (taille maximale UINT16) puis suivi d'un tiret (-) et d'un algorithme de hachage valide. * ecdaa Par exemple, ecdaa4-sha256. Si aucun nombre n'est spécifié, la valeur par défaut est 4.

Spécificateurs de schéma sans option

Ce spécificateur de schéma ne prend AUCUN argument. * rsaes

Spécificateurs de détails symétriques

Ce champ est facultatif et sera par défaut en fonction du type d'objet créé et de ses attributs. Généralement, tout spécificateur symétrique valide de la liste des spécificateurs de type devrait fonctionner. S'il n'est pas spécifié, les détails symétriques des objets asymétriques seront par défaut aes128cfb.

Exemples

Créer une clé rsa2048 avec un schéma de chiffrement asymétrique rsaes

tpm2_create -C parent.ctx -G rsa2048:rsaes -u key.pub -r key.priv

Créer une clé ecc256 avec un schéma de signature ecdaa avec un compte de 4 et un hachage sha384

/tpm2_create -C parent.ctx -G ecc256:ecdaa4-sha384 -u key.pub -r key.priv algorithmes cryptographiques ALGORITHME.

tpm2_gettime(1) — tpm2-tools

NAME

tpm2_gettime - Query TPM for the current time. TPM time is defined as the value of the TPM_GetTime command. It is used for attestation, as it cannot be manipulated by an attacker.

SYNOPSIS

tpm2_gettime [OPTIONS] [-c object-handle]

DESCRIPTION

The tpm2_gettime command queries the TPM for the current time. This time value is the TPM's internal clock value, which is maintained independently of the host system's clock. This allows for time-based attestation, where the TPM's time value can be certified by the TPM itself.

The command can optionally take a policy object handle (created using tpm2_createpolicy) to perform policy-based attestation. In this case, the time value will be attested using the policy.

The results of the command are written to standard output in a format determined by the --format option.

To successfully use the manpages feature requires the manpages to be installed or on MANPATH, See man(1) for more details.

•
-v, --version: Display version information for this tool, supported tctis and exit.
•
-V, --verbose: Increase the information that the tool prints to the console during its execution. When using this option the file and line number are printed.
•
-Q, --quiet: Silence normal tool output to stdout.
•
-Z, --enable-errata: Enable the application of errata fixups. Useful if an errata fixup needs to be applied to commands sent to the TPM. Defining the environment TPM2TOOLS_ENABLE_ERRATA is equivalent.
•
-R, --autoflush: Enable autoflush for transient objects created by the command. If a parent object is loaded from a context file also the transient parent object will be flushed. Autoflush can also be activated if the environment variable TPM2TOOLS_AUTOFLUSH is is set to yes or true. information many users may expect.

TCTI Configuration

The TCTI or “Transmission Interface” is the communication mechanism with the TPM. TCTIs can be changed for communication with TPMs across different mediums.

To control the TCTI, the tools respect:

1.
The command line option -T or --tcti
2.
The environment variable: TPM2TOOLS_TCTI.

Note: The command line option always overrides the environment variable.

The current known TCTIs are:

•
tabrmd - The resource manager, called tabrmd. Note that tabrmd and abrmd as a tcti name are synonymous.
•
mssim - Typically used for communicating to the TPM software simulator.
•
device - Used when talking directly to a TPM device file.
•
none - Do not initalize a connection with the TPM. Some tools allow for off-tpm options and thus support not using a TCTI. Tools that do not support it will error when attempted to be used without a TCTI connection. Does not support ANY options and MUST BE presented as the exact text of “none”.

The arguments to either the command line option or the environment variable are in the form:

<tcti-name>:<tcti-option-config>

Specifying an empty string for either the <tcti-name> or <tcti-option-config> results in the default being used for that portion respectively.

TCTI Defaults

When a TCTI is not specified, the default TCTI is searched for using dlopen(3) semantics. The tools will search for tabrmd, device and mssim TCTIs IN THAT ORDER and USE THE FIRST ONE FOUND. You can query what TCTI will be chosen as the default by using the -v option to print the version information. The “default-tcti” key-value pair will indicate which of the aforementioned TCTIs is the default.

Custom TCTIs

Any TCTI that implements the dynamic TCTI interface can be loaded. The tools internally use dlopen(3), and the raw tcti-name value is used for the lookup. Thus, this could be a path to the shared library, or a library name as understood by dlopen(3) semantics.

TCTI OPTIONS

This collection of options are used to configure the various known TCTI modules available:

•
device: For the device TCTI, the TPM character device file for use by the device TCTI can be specified. The default is /dev/tpm0.

Example: -T device:/dev/tpm0 or export TPM2TOOLS_TCTI=“device:/dev/tpm0”

•
mssim: For the mssim TCTI, the domain name or IP address and port number used by the simulator can be specified. The default are 127.0.0.1 and 2321.

Example: -T mssim:host=localhost,port=2321 or export TPM2TOOLS_TCTI=“mssim:host=localhost,port=2321”

•
abrmd: For the abrmd TCTI, the configuration string format is a series of simple key value pairs separated by a `,' character. Each key and value string are separated by a `=' character.
•
TCTI abrmd supports two keys:
1.
`bus_name' : The name of the tabrmd service on the bus (a string).
2.
`bus_type' : The type of the dbus instance (a string) limited to `session' and `system'.

Specify the tabrmd tcti name and a config string of bus_name=com.example.FooBar:

\--tcti=tabrmd:bus_name=com.example.FooBar

Specify the default (abrmd) tcti and a config string of bus_type=session:

\--tcti:bus_type=session

NOTE: abrmd and tabrmd are synonymous. the various known TCTI modules. # Signature Format Specifiers

Format selection for the signature output file. tss (the default) will output a binary blob according to the TPM 2.0 specification and any potential compiler padding. The option plain will output the plain signature data as defined by the used cryptographic algorithm.

Create a key and get attested TPM time

tpm2_create -G rsa -u rsa.pub -r rsa.priv -C primary.ctx

tpm2_gettime -c rsa.ctx -o attest.sig --attestation attest.data
