NOM

time_namespaces - aperçu des espaces de noms temporels Linux

DESCRIPTION

Les espaces de noms temporels virtualisent les valeurs de deux horloges système :

•
CLOCK_MONOTONIC (et de même CLOCK_MONOTONIC_COARSE et CLOCK_MONOTONIC_RAW), une horloge non modifiable qui représente le temps monotone depuis — tel que décrit par POSIX — "un point non spécifié dans le passé".
•
CLOCK_BOOTTIME (et de même CLOCK_BOOTTIME_ALARM), une horloge non modifiable qui est identique à CLOCK_MONOTONIC, sauf qu'elle inclut tout le temps pendant lequel le système est suspendu.

Ainsi, les processus d'un espace de noms temporel partagent des valeurs par espace de noms pour ces horloges. Cela affecte diverses API qui mesurent par rapport à ces horloges, y compris : clock_gettime(2), clock_nanosleep(2), nanosleep(2), timer_settime(2), timerfd_settime(2), et /proc/uptime.

Actuellement, le seul moyen de créer un espace de noms temporel est d'appeler unshare(2) avec le drapeau CLONE_NEWTIME. Cet appel crée un nouvel espace de noms temporel mais ne place pas le processus appelant dans le nouvel espace de noms. Au lieu de cela, les enfants créés ultérieurement par le processus appelant sont placés dans le nouvel espace de noms. Cela permet de définir les décalages d'horloge (voir ci-dessous) pour le nouvel espace de noms avant que le premier processus n'y soit placé. Le lien symbolique /proc/pid/ns/time_for_children montre l'espace de noms temporel dans lequel les enfants d'un processus seront créés. (Un processus peut utiliser un descripteur de fichier ouvert sur ce lien symbolique dans un appel à setns(2) afin de se déplacer dans l'espace de noms.)

/proc/pid/timens_offsets

Associés à chaque espace de noms temporel se trouvent des décalages, exprimés par rapport à l'espace de noms temporel initial, qui définissent les valeurs des horloges monotone et de temps de démarrage dans cet espace de noms. Ces décalages sont exposés via le fichier /proc/pid/timens_offsets. Dans ce fichier, les décalages sont exprimés sous forme de lignes composées de trois champs séparés par des espaces :


<clock-id> <offset-secs> <offset-nanosecs>

Le clock-id est une chaîne qui identifie l'horloge dont les décalages sont affichés. Ce champ est soit monotonic, pour CLOCK_MONOTONIC, soit boottime, pour CLOCK_BOOTTIME. Les champs restants expriment le décalage (secondes plus nanosecondes) pour l'horloge dans cet espace de noms temporel. Ces décalages sont exprimés par rapport aux valeurs de l'horloge dans l'espace de noms temporel initial. La valeur offset-secs peut être négative, sous réserve des restrictions indiquées ci-dessous ; offset-nanosecs est une valeur non signée.

Dans l'espace de noms temporel initial, le contenu du fichier timens_offsets est le suivant :


$ cat /proc/self/timens_offsets
monotonic           0         0
boottime            0         0

Dans un nouvel espace de noms temporel qui n'a eu aucun processus membre, les décalages d'horloge peuvent être modifiés en écrivant des enregistrements terminés par un saut de ligne de la même forme dans le fichier timens_offsets. Le fichier peut être écrit plusieurs fois, mais après que le premier processus ait été créé dans l'espace de noms ou y soit entré, les écritures dans ce fichier échouent avec l'erreur EACCES. Pour écrire dans le fichier timens_offsets, un processus doit posséder la capacité CAP_SYS_TIME dans l'espace de noms d'utilisateur qui possède l'espace de noms temporel.

Les écritures dans le fichier timens_offsets peuvent échouer avec les erreurs suivantes :

EINVAL
Une valeur offset-nanosecs est supérieure à 999 999 999.
EINVAL
Une valeur clock-id n'est pas valide.
EPERM
L'appelant ne possède pas la capacité CAP_SYS_TIME.
ERANGE
Une valeur offset-secs est hors limites. En particulier ;
•
offset-secs ne peut pas être défini sur une valeur qui rendrait le temps actuel sur l'horloge correspondante à l'intérieur de l'espace de noms négatif ; et
•
offset-secs ne peut pas être défini sur une valeur telle que le temps sur l'horloge correspondante à l'intérieur de l'espace de noms dépasserait la moitié de la valeur de la constante du noyau KTIME_SEC_MAX (cela limite la valeur de l'horloge à un maximum d'environ 146 ans).

Dans un nouvel espace de noms temporel créé par unshare(2), le contenu du fichier timens_offsets est hérité de l'espace de noms temporel du processus créateur.

NOTES

L'utilisation des espaces de noms temporels nécessite un noyau configuré avec l'option CONFIG_TIME_NS.

Notez que les espaces de noms temporels ne virtualisent pas l'horloge CLOCK_REALTIME. La virtualisation de cette horloge a été évitée pour des raisons de complexité et de surcharge au sein du noyau.

Par souci de compatibilité avec l'implémentation initiale, lors de l'écriture d'un clock-id dans le fichier /proc/pid/timens_offsets, les valeurs numériques des ID peuvent être écrites au lieu des noms symboliques ci-dessus ; c'est-à-dire 1 au lieu de monotonic, et 7 au lieu de boottime. Pour la lisibilité, l'utilisation des noms symboliques plutôt que des nombres est préférée.

La motivation pour l'ajout des espaces de noms temporels était de permettre aux horloges monotone et de temps de démarrage de maintenir des valeurs cohérentes lors de la migration de conteneurs et de la restauration à partir d'un point de contrôle.

EXEMPLES

La session shell suivante démontre le fonctionnement des espaces de noms temporels. Nous commençons par afficher le numéro d'inode de l'espace de noms temporel d'un shell dans l'espace de noms temporel initial :


$ readlink /proc/$$/ns/time
time:[4026531834]

En continuant dans l'espace de noms temporel initial, nous affichons le temps de disponibilité du système à l'aide de uptime(1) et utilisons le programme d'exemple clock_times montré dans clock_getres(2) pour afficher les valeurs de diverses horloges :


$ uptime --pretty
up 21 hours, 17 minutes
$ ./clock_times
CLOCK_REALTIME : 1585989401.971 (18356 days +  8h 36m 41s)
CLOCK_TAI      : 1585989438.972 (18356 days +  8h 37m 18s)
CLOCK_MONOTONIC:      56338.247 (15h 38m 58s)
CLOCK_BOOTTIME :      76633.544 (21h 17m 13s)

Nous utilisons ensuite unshare(1) pour créer un espace de noms temporel et exécuter un shell bash(1). Depuis le nouveau shell, nous utilisons la commande intégrée echo pour écrire des enregistrements dans le fichier timens_offsets, ajustant le décalage de l'horloge CLOCK_MONOTONIC de 2 jours et le décalage de l'horloge CLOCK_BOOTTIME de 7 jours :


$ PS1=ns2# sudo unshare -T -- bash --norc
ns2# echo monotonic$((2*24*60*60))0">/proc/$$/timens_offsets"
ns2# echo boottime$((7*24*60*60))0">/proc/$$/timens_offsets"

Ci-dessus, nous avons démarré le shell bash(1) avec l'option --norc afin qu'aucun script de démarrage ne soit exécuté. Cela garantit qu'aucun processus enfant n'est créé à partir du shell avant que nous ayons la possibilité de mettre à jour le fichier timens_offsets.

Nous utilisons ensuite cat(1) pour afficher le contenu du fichier timens_offsets. L'exécution de cat(1) crée le premier processus dans le nouvel espace de noms temporel, après quoi les tentatives ultérieures de mise à jour du fichier timens_offsets produisent une erreur.


ns2# cat /proc/$$/timens_offsets
monotonic      172800         0
boottime       604800         0
ns2# echo "boottime $((9*24*60*60)) 0" > /proc/$$/timens_offsets
bash: echo: write error: Permission denied

En continuant dans le nouvel espace de noms, nous exécutons uptime(1) et le programme d'exemple clock_times :


ns2# uptime --pretty
up 1

semaine, 21 heures, 18 minutes ns2# ./clock_times CLOCK_REALTIME : 1585989457.056 (18356 jours + 8h 37m 37s) CLOCK_TAI : 1585989494.057 (18356 jours + 8h 38m 14s) CLOCK_MONOTONIC: 229193.332 (2 jours + 15h 39m 53s) CLOCK_BOOTTIME : 681488.629 (7 jours + 21h 18m 8s)

D'après la sortie ci-dessus, nous pouvons voir que les horloges monotonique et de temps de démarrage ont des valeurs différentes dans le nouveau espace de noms temporel.

En examinant les liens symboliques /proc/pid/ns/time et /proc/pid/ns/time_for_children, nous voyons que le shell est membre de l'espace de noms temporel initial, mais que ses enfants sont créés dans le nouvel espace de noms.


ns2# readlink /proc/$$/ns/time
time:[4026531834]
ns2# readlink /proc/$$/ns/time_for_children
time:[4026532900]
ns2# readlink /proc/self/ns/time  # Crée un processus enfant
time:[4026532900]

En revenant au shell dans l'espace de noms temporel initial, nous voyons que les horloges monotonique et de temps de démarrage ne sont pas affectées par les modifications de timens_offsets qui ont été apportées dans l'autre espace de noms temporel :


$ uptime --pretty
up 21 heures, 19 minutes
$ ./clock_times
CLOCK_REALTIME : 1585989401.971 (18356 jours +  8h 38m 51s)
CLOCK_TAI      : 1585989438.972 (18356 jours +  8h 39m 28s)
CLOCK_MONOTONIC:      56338.247 (15h 41m  8s)
CLOCK_BOOTTIME :      76633.544 (21h 19m 23s)
