TIMER_CREATE(3P) Manuel du programmeur POSIX TIMER_CREATE(3P)

PROLOG

Cette page de manuel fait partie du Manuel du programmeur POSIX. L'implémentation Linux de cette interface peut différer (consultez la page de manuel Linux correspondante pour les détails du comportement sous Linux), ou l'interface peut ne pas être implémentée sous Linux.

NOM

timer_create — créer un minuteur par processus

SYNTAXE

#include <signal.h>
#include <time.h>
int timer_create(clockid_t clockid, struct sigevent *restrict evp,
    timer_t *restrict timerid);

DESCRIPTION

La fonction timer_create() crée un minuteur par processus en utilisant l'horloge spécifiée, clock_id, comme base de synchronisation. La fonction timer_create() retourne, dans l'emplacement référencé par timerid, un identifiant de minuteur de type timer_t utilisé pour identifier le minuteur dans les requêtes de minuteur. Cet identifiant de minuteur est unique au sein du processus appelant jusqu'à ce que le minuteur soit supprimé. L'horloge particulière, clock_id, est définie dans <time.h>. Le minuteur dont l'identifiant est retourné est dans un état désarmé lors du retour de timer_create().

L'argument evp, s'il n'est pas NULL, pointe vers une structure sigevent. Cette structure, allouée par l'application, définit la notification asynchrone à effectuer comme spécifié dans la Section 2.4.1, Génération et livraison de signaux lorsque le minuteur expire. Si l'argument evp est NULL, l'effet est comme si l'argument evp pointait vers une structure sigevent avec le membre sigev_notify ayant la valeur SIGEV_SIGNAL, le membre sigev_signo ayant un numéro de signal par défaut, et le membre sigev_value ayant la valeur de l'identifiant du minuteur.

Chaque implémentation doit définir un ensemble d'horloges qui peuvent être utilisées comme bases de synchronisation pour les minuteurs par processus. Toutes les implémentations doivent supporter un clock_id de CLOCK_REALTIME. Si l'option Horloge Monotone est supportée, les implémentations doivent supporter un clock_id de CLOCK_MONOTONIC.

Les minuteurs par processus ne doivent pas être hérités par un processus enfant lors d'un fork() et doivent être désarmés et supprimés par un exec.

Si _POSIX_CPUTIME est défini, les implémentations doivent supporter des valeurs de clock_id représentant l'horloge temps CPU du processus appelant.

Si _POSIX_THREAD_CPUTIME est défini, les implémentations doivent supporter des valeurs de clock_id représentant l'horloge temps CPU du thread appelant.

Il est défini par l'implémentation si une fonction timer_create() réussira si la valeur définie par clock_id correspond à l'horloge temps CPU d'un processus ou d'un thread différent de celui qui invoque la fonction.

Si evp->sigev_sigev_notify est SIGEV_THREAD et sev->sigev_notify_attributes n'est pas NULL, si l'attribut pointé par sev->sigev_notify_attributes a une adresse de pile de thread spécifiée par un appel à pthread_attr_setstack(), les résultats ne sont pas spécifiés si le signal est généré plus d'une fois.

VALEUR DE RETOUR

Si l'appel réussit, timer_create() retourne zéro et met à jour l'emplacement référencé par timerid avec un timer_t, qui peut être passé aux appels de minuteur par processus. Si une erreur se produit, la fonction retourne une valeur de -1 et définit errno pour indiquer l'erreur. La valeur de timerid est indéfinie en cas d'erreur.

ERREURS

La fonction timer_create() échouera si :

EAGAIN
Le système manque de ressources de mise en file d'attente de signaux suffisantes pour satisfaire la requête.
EAGAIN
Le processus appelant a déjà créé tous les minuteurs auxquels il est autorisé par cette implémentation.
EINVAL
L'identifiant d'horloge spécifié n'est pas défini.
ENOTSUP
L'implémentation ne supporte pas la création d'un minuteur attaché à l'horloge temps CPU spécifiée par clock_id et associée à un processus ou un thread différent du processus ou du thread qui invoque timer_create().

USAGE APPLICATIF

Si un minuteur est créé avec evp->sigev_sigev_notify défini à SIGEV_THREAD et que l'attribut pointé par evp->sigev_notify_attributes a une adresse de pile de thread spécifiée par un appel à pthread_attr_setstack(), la mémoire dédiée en tant que pile de thread ne peut pas être récupérée. La raison est que les threads créés en réponse à une expiration de minuteur sont créés détachés, ou d'une manière non spécifiée si l'état de détachement de l'attribut de thread est PTHREAD_CREATE_JOINABLE. Dans aucun des deux cas, il n'est valide d'appeler pthread_join(), ce qui rend impossible de déterminer la durée de vie du thread créé et donc la mémoire de pile ne peut pas être réutilisée.

RATIONALE

Dépassement périodique du minuteur et allocation des ressources

Les installations de minuteurs spécifiées peuvent livrer des signaux temps réel (c'est-à-dire des signaux mis en file d'attente) sur les implémentations qui supportent cette option. Étant donné que les applications temps réel ne peuvent pas se permettre de perdre des notifications d'événements asynchrones, comme les expirations de minuteurs ou les complétions d'E/S asynchrones, il doit être possible de s'assurer que des ressources suffisantes existent pour livrer le signal lorsque l'événement se produit. En général, ce n'est pas un problème car il existe une correspondance un à un entre une requête et une génération de signal ultérieure. Si la requête ne peut pas allouer les ressources de livraison de signal, elle peut échouer l'appel avec une erreur [EAGAIN].

Les minuteurs périodiques sont un cas particulier. Une seule requête peut générer un nombre non spécifié de signaux. Ce n'est pas un problème si le processus demandeur peut traiter les signaux aussi rapidement qu'ils sont générés, rendant ainsi les ressources de livraison de signal disponibles pour la livraison de signaux d'expiration de minuteur périodique ultérieurs. Mais, en général, cela ne peut être assuré ; le traitement des signaux d'expiration de minuteur périodique peut « dépasser » ; c'est-à-dire que des expirations de minuteur périodique ultérieures peuvent se produire avant que le signal en cours ne soit livré.

De plus, pour les signaux, selon la norme POSIX.1-1990, si des occurrences ultérieures d'un signal en attente sont générées, il est défini par l'implémentation si un signal est livré pour chaque occurrence. Ceci n'est pas suffisant pour certaines applications temps réel. Un mécanisme est donc requis pour permettre aux applications de détecter combien d'expirations de minuteur ont été retardées sans nécessiter une quantité indéfinie de ressources système pour stocker les expirations retardées.

Les installations spécifiées fournissent un compteur de dépassement. Le compteur de dépassement est défini comme le nombre d'expirations de minuteur supplémentaires qui se sont produites entre le moment où un signal d'expiration de minuteur est généré et le moment où le signal est livré. La fonction d'interception de signal, si elle est concernée par les dépassements, peut récupérer ce compteur à l'entrée. Avec cette méthode, un minuteur périodique n'a besoin que d'une seule « ressource de mise en file d'attente de signal » qui peut être allouée au moment de l'appel de la fonction timer_create().

Une fonction est définie pour récupérer le compteur de dépassement afin qu'une application n'ait pas besoin d'allouer de stockage statique pour contenir le compteur, et une implémentation n'a pas besoin de mettre à jour ce stockage de manière asynchrone lors des expirations de minuteur. Mais, pour certaines applications à haute fréquence périodique, la surcharge d'un appel système supplémentaire à chaque expiration de minuteur peut être prohibitive. Les fonctions, telles qu'elles sont définies, permettent à une implémentation de maintenir le compteur de dépassement dans l'espace utilisateur, associé au timerid. La fonction timer_getoverrun() peut alors être implémentée comme une macro qui utilise l'argument timerid (qui peut être simplement un pointeur vers une structure d'espace utilisateur contenant le compteur) pour localiser le compteur de dépassement sans surcharge d'appel système. RATIONALE

The Realtime Signals Extension option for timers supports delivering a value from the application to the signal handler. There are several ways that this could be achieved. One way is to simply pass the timer_id to the signal handler. This would require the application to maintain an array of timer_ids and associated application data. The signal handler would then need to search this array to find the data associated with the received timer_id.

A second approach is to allow the application to specify some data to be delivered with the signal. This avoids the need for the application to maintain a lookup table and thus simplifies the design of the signal handler. This approach is taken here, where the application may specify an integer or a pointer as the data to be delivered. This allows the application to either pass a constant value or a pointer to an application-defined data structure.

The RATIONALE section for timer_create() stated that the timer_id is the only piece of information that needs to be returned to the application. However, this is only true if the application wishes to use the timer_id as the case label of a switch statement or as a pointer to an application-defined data structure. If the application wants to pass some other data along with the signal, there is no way to do it without maintaining additional data structures.

The POSIX Realtime Signals Extension provides a mechanism for passing arbitrary data along with a signal. This extension is intended to be used with timers as well. The RATIONALE section for sigqueue() stated that the siginfo_t structure was extended to include a union member, si_value, which could hold an integer or a pointer. This structure is used by the timer functions to pass application-defined data.

This approach allows the application to specify data that is delivered with the timer expiration signal. This data can be either an integer or a pointer. The application can use this data to identify the timer or to pass additional information to the signal handler. This eliminates the need for the application to maintain a lookup table of timer IDs and associated data, thus simplifying the signal handler.

The choice of an integer or a pointer for the data allows for maximum flexibility. The application can pass a simple integer constant, or it can pass a pointer to a more complex data structure. This is useful for applications that need to maintain a significant amount of state information for each timer.

The use of the sigevent structure is consistent with the POSIX Realtime Signals Extension. This structure is used to specify the signal to be delivered, the signal number, and any application-defined data. By using this structure, the timer functions can be integrated seamlessly with the rest of the POSIX Realtime Signals Extension.

The decision to allow the application to specify the data to be delivered, rather than always sending the timer ID, was based on existing practice in non-POSIX realtime systems and realtime extensions to POSIX. These systems often provide a mechanism for passing application-specific data along with timer expiration signals. This allows applications to use the handler parameters as case labels in a switch statement or as pointers to data structures without the overhead of searching for the associated data.

This design choice prioritizes flexibility and ease of use for the application developer, especially in complex realtime scenarios. Paramètres du signal d'expiration du minuteur

L'option d'extension de signaux temps réel prend en charge une donnée spécifique à l'application qui est livrée au gestionnaire de signaux étendu. Cette valeur est explicitement spécifiée par l'application, ainsi que le numéro de signal à livrer, dans une structure sigevent. Le type de la valeur définie par l'application peut être soit une constante entière, soit un pointeur. Cette spécification explicite de la valeur, par opposition à l'envoi toujours de l'ID du minuteur, a été choisie en fonction de la pratique existante.

Il est courant pour les applications temps réel (sur des systèmes non-POSIX ou des systèmes POSIX étendus temps réel) d'utiliser les paramètres des gestionnaires d'événements comme étiquette de cas d'une instruction switch ou comme pointeur vers une structure de données définie par l'application. Étant donné que les timer_id sont alloués dynamiquement par la fonction timer_create(), ils ne peuvent être utilisés pour aucune de ces fonctions sans surcharge applicative supplémentaire dans le gestionnaire de signaux ; par exemple, pour rechercher dans un tableau de timer_id enregistrés afin d'associer l'ID à une constante ou à une structure de données applicative.
