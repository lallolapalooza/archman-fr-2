TIMER_GETOVERRUN(3P) Manuel du programmeur POSIX TIMER_GETOVERRUN(3P)

PROLOG

Cette page de manuel fait partie du Manuel du programmeur POSIX. L'implémentation Linux de cette interface peut différer (consultez la page de manuel Linux correspondante pour connaître les détails du comportement de Linux), ou l'interface peut ne pas être implémentée sous Linux.

NOM

timer_getoverrun, timer_gettime, timer_settime — timers par processus

SYNTAXE

#include <time.h>
int timer_getoverrun(timer_t timerid);
int timer_gettime(timer_t timerid, struct itimerspec *value);
int timer_settime(timer_t timerid, int flags,
    const struct itimerspec *restrict value,
    struct itimerspec *restrict ovalue);

DESCRIPTION

La fonction timer_gettime() doit stocker la durée avant l'expiration du timer spécifié, timerid, et la valeur de rechargement du timer dans l'espace pointé par l'argument value. Le membre it_value de cette structure doit contenir la durée avant l'expiration du timer, ou zéro si le timer est désarmé. Cette valeur est retournée comme l'intervalle jusqu'à l'expiration du timer, même si le timer était armé avec une heure absolue. Le membre it_interval de value doit contenir la valeur de rechargement définie pour la dernière fois par timer_settime().

La fonction timer_settime() doit définir le temps avant la prochaine expiration du timer spécifié par timerid à partir du membre it_value de l'argument value et armer le timer si le membre it_value de value n'est pas nul. Si le timer spécifié était déjà armé lors de l'appel à timer_settime(), cet appel doit réinitialiser le temps avant la prochaine expiration à la value spécifiée. Si le membre it_value de value est zéro, le timer doit être désarmé. L'effet de désarmer ou de réinitialiser un timer avec des notifications d'expiration en attente n'est pas spécifié.

Si le drapeau TIMER_ABSTIME n'est pas défini dans l'argument flags, timer_settime() doit se comporter comme si le temps avant la prochaine expiration était défini pour être égal à l'intervalle spécifié par le membre it_value de value. Autrement dit, le timer doit expirer dans it_value nanosecondes à partir du moment où l'appel est effectué. Si le drapeau TIMER_ABSTIME est défini dans l'argument flags, timer_settime() doit se comporter comme si le temps avant la prochaine expiration était défini pour être égal à la différence entre l'heure absolue spécifiée par le membre it_value de value et la valeur actuelle de l'horloge associée à timerid. Autrement dit, le timer doit expirer lorsque l'horloge atteint la valeur spécifiée par le membre it_value de value. Si l'heure spécifiée est déjà passée, la fonction doit réussir et la notification d'expiration doit être effectuée.

La valeur de rechargement du timer doit être définie sur la valeur spécifiée par le membre it_interval de value. Lorsqu'un timer est armé avec un it_interval non nul, un timer périodique (ou répétitif) est spécifié.

Les valeurs de temps qui se situent entre deux multiples entiers non négatifs consécutifs de la résolution du timer spécifié doivent être arrondies au multiple supérieur de la résolution. L'erreur de quantification ne doit pas entraîner l'expiration du timer avant la valeur de temps arrondie.

Si l'argument ovalue n'est pas NULL, la fonction timer_settime() doit stocker, à l'emplacement référencé par ovalue, une valeur représentant la durée précédente avant que le timer n'expire, ou zéro si le timer a été désarmé, ainsi que la valeur de rechargement précédente du timer. Les timers ne doivent pas expirer avant leur heure prévue.

Seul un signal doit être mis en file d'attente pour le processus pour un timer donné à tout moment. Lorsqu'un timer pour lequel un signal est toujours en attente expire, aucun signal ne doit être mis en file d'attente, et un dépassement de timer doit se produire. Lorsqu'un signal d'expiration de timer est délivré ou accepté par un processus, la fonction timer_getoverrun() doit retourner le nombre de dépassements d'expiration du timer pour le timer spécifié. Le compte de dépassements retourné contient le nombre d'expirations supplémentaires qui se sont produites entre le moment où le signal a été généré (mis en file d'attente) et le moment où il a été délivré ou accepté, jusqu'à un maximum défini par l'implémentation de {DELAYTIMER_MAX}, sans l'inclure. Si le nombre d'expirations supplémentaires est supérieur ou égal à {DELAYTIMER_MAX}, alors le compte de dépassements doit être défini sur {DELAYTIMER_MAX}. La valeur retournée par timer_getoverrun() doit s'appliquer à la livraison ou à l'acceptation la plus récente du signal d'expiration pour le timer. Si aucun signal d'expiration n'a été délivré pour le timer, la valeur de retour de timer_getoverrun() n'est pas spécifiée.

Le comportement n'est pas spécifié si la valeur spécifiée par l'argument timerid à timer_getoverrun(), timer_gettime(), ou timer_settime() ne correspond pas à un ID de timer retourné par timer_create() mais pas encore supprimé par timer_delete().

VALEUR DE RETOUR

Si la fonction timer_getoverrun() réussit, elle doit retourner le nombre de dépassements d'expiration du timer comme expliqué ci-dessus.

Si les fonctions timer_gettime() ou timer_settime() réussissent, une valeur de 0 doit être retournée.

Si une erreur se produit pour l'une de ces fonctions, la valeur -1 doit être retournée, et errno doit être définie pour indiquer l'erreur.

ERREURS

La fonction timer_settime() doit échouer si :

EINVAL
Une structure value a spécifié une valeur en nanosecondes inférieure à zéro ou supérieure ou égale à 1000 millions, et le membre it_value de cette structure n'a pas spécifié zéro seconde et nanosecondes.

La fonction timer_settime() peut échouer si :

EINVAL
Le membre it_interval de value n'est pas zéro et le timer a été créé avec une notification par création d'un nouveau thread (sigev_sigev_notify était SIGEV_THREAD) et une adresse de pile fixe a été définie dans l'attribut de thread pointé par sigev_notify_attributes.

UTILISATION APPLICATIVE

L'utilisation d'adresses de pile fixes pose problème lorsque l'expiration du timer est signalée par la création d'un nouveau thread. Comme il ne peut être supposé que le thread créé pour une expiration a terminé avant la prochaine expiration du timer, il pourrait arriver que deux threads utilisent la même mémoire comme pile en même temps. Ceci est invalide et produit des résultats indéfinis.

RATIONALE

Les horloges pratiques battent à une fréquence finie, avec des fréquences de 100 hertz et 1000 hertz étant courantes. L'inverse de cette fréquence de battement est la résolution de l'horloge, également appelée granularité de l'horloge, qui dans les deux cas est exprimée comme une durée, soit 10 millisecondes et 1 milliseconde respectivement pour ces taux courants. La granularité des horloges pratiques implique que si l'on lit une horloge donnée deux fois de suite rapidement, on peut obtenir la même valeur de temps deux fois ; et que les timers doivent attendre le prochain "tick" de l'horloge après l'heure d'expiration théorique, pour garantir qu'un timer ne retourne jamais trop tôt. Notez également que la granularité de l'horloge peut être nettement plus grossière que la résolution du format de données utilisé pour définir et obtenir les valeurs de temps et d'intervalle. Notez également que certaines implémentations peuvent choisir d'ajuster les valeurs de temps et/ou d'intervalle pour qu'elles correspondent exactement aux "ticks" de l'horloge sous-jacente.

Ce volume de POSIX.1‐2017 définit des fonctions qui permettent à une application de déterminer la résolution supportée par l'implémentation pour les horloges et exige qu'une implémentation documente la résolution supportée pour les timers et nanosleep() si elle diffère de la résolution d'horloge supportée. C'est davantage un problème de commande qu'un problème d'application à l'exécution.
