NOM

x509v3_config - Format de configuration des extensions de certificats X509 V3

DESCRIPTION

Plusieurs commandes OpenSSL peuvent ajouter des extensions à un certificat ou une demande de certificat en se basant sur le contenu d'un fichier de configuration et des options de ligne de commande telles que -addext. La syntaxe des fichiers de configuration est décrite dans config(5). Les commandes ont généralement une option pour spécifier le nom du fichier de configuration et une section dans ce fichier ; consultez la documentation de la commande individuelle pour plus de détails.

Cette page utilise extensions comme nom de section, lorsque cela est nécessaire dans les exemples.

Chaque entrée dans la section des extensions prend la forme :

nom = [critique, ]valeur(s)

Si critique est présent, l'extension sera marquée comme critique.

Si plusieurs entrées sont traitées pour le même nom d'extension, les entrées ultérieures remplacent les précédentes ayant le même nom.

Le format des valeurs dépend de la valeur de nom ; beaucoup ont un couplage type-valeur où le type et la valeur sont séparés par un deux-points. Il existe quatre types principaux d'extension :

chaîne
multi-valuée
brute
arbitraire

Chacun est décrit dans les paragraphes suivants.

Les extensions de type chaîne contiennent simplement une chaîne qui contient soit la valeur elle-même, soit comment elle est obtenue.

Les extensions multi-valuées ont une forme courte et une forme longue. La forme courte est une liste de noms et de valeurs séparés par des virgules :

basicConstraints = critical, CA:true, pathlen:1

La forme longue permet de placer les valeurs dans une section séparée :

[extensions]
basicConstraints = critical, @basic_constraints
[basic_constraints]
CA = true
pathlen = 1

Les deux formes sont équivalentes.

Si une extension est multi-valuée et qu'une valeur de champ doit contenir une virgule, la forme longue doit être utilisée, sinon la virgule serait mal interprétée comme un séparateur de champ. Par exemple :

subjectAltName = URI:ldap://somehost.com/CN=foo,OU=bar

provoquera une erreur, mais la forme équivalente :

[extensions]
subjectAltName = @subject_alt_section
[subject_alt_section]
subjectAltName = URI:ldap://somehost.com/CN=foo,OU=bar

est valide.

OpenSSL ne prend pas en charge les occurrences multiples du même champ au sein d'une section. Dans cet exemple :

[extensions]
subjectAltName = @alt_section
[alt_section]
email = steve@example.com
email = steve@example.org

ne reconnaîtra que la dernière valeur. Pour spécifier plusieurs valeurs, ajoutez un identifiant numérique, comme montré ici :

[extensions]
subjectAltName = @alt_section
[alt_section]
email.1 = steve@example.com
email.2 = steve@example.org

La syntaxe des extensions brutes est définie par le code source qui analyse l'extension, mais doit être documentée. Voir « Politiques de certificats » pour un exemple d'extension brute.

Si un type d'extension n'est pas pris en charge, la syntaxe d'extension arbitraire doit être utilisée, voir la section « EXTENSIONS ARBITRAIRES » pour plus de détails.

EXTENSIONS STANDARDS

Les sections suivantes décrivent la syntaxe de chaque extension prise en charge. Elles ne définissent pas la sémantique de l'extension.

Contraintes de base

Ceci est une extension multi-valuée qui indique si un certificat est un certificat d'AC. La première valeur est CA suivie de TRUE ou FALSE. Si CA est TRUE, alors un nom facultatif pathlen suivi d'une valeur non négative peut être inclus.

Par exemple :

basicConstraints = CA:TRUE
basicConstraints = CA:FALSE
basicConstraints = critical, CA:TRUE, pathlen:1

Un certificat d'AC doit inclure le nom basicConstraints avec le paramètre CA défini sur TRUE. Un certificat d'entité finale doit soit avoir CA:FALSE, soit omettre l'extension. Le paramètre pathlen spécifie le nombre maximum d'AC qui peuvent apparaître en dessous de celle-ci dans une chaîne. Un pathlen de zéro signifie que l'AC ne peut signer aucune sous-AC, et ne peut signer que des certificats d'entité finale.

Usage de la clé

L'usage de la clé est une extension multi-valuée composée d'une liste de noms des usages de clé autorisés. Les valeurs définies sont : "digitalSignature", "nonRepudiation" (avec un nom alternatif "contentCommitment"), "keyEncipherment", "dataEncipherment", "keyAgreement", "keyCertSign", "cRLSign", "encipherOnly", et "decipherOnly".

Exemples :

keyUsage = digitalSignature, nonRepudiation
keyUsage = digitalSignature, contentCommitment
keyUsage = critical, keyCertSign

Usage de la clé étendu

Cette extension se compose d'une liste de valeurs indiquant les finalités pour lesquelles la clé publique du certificat peut être utilisée. Chaque valeur peut être soit un nom textuel court, soit un OID. Les noms textuels suivants, et leur signification prévue, sont connus :

Valeur                  Signification selon RFC 5280 etc.
------                  ----------------------------------
serverAuth             Authentification de serveur WWW SSL/TLS
clientAuth             Authentification de client WWW SSL/TLS
codeSigning            Signature de code
emailProtection        Protection E-mail (S/MIME)
timeStamping           Horodatage de confiance
OCSPSigning            Signature OCSP
ipsecIKE               Échange de clés IPsec Internet
msCodeInd              Signature de code individuel Microsoft (authenticode)
msCodeCom              Signature de code commercial Microsoft (authenticode)
msCTLSign              Signature de liste de confiance Microsoft
msEFS                  Système de fichiers chiffré Microsoft

Bien que la RFC 5280 de l'IETF indique que id-kp-serverAuth et id-kp-clientAuth sont uniquement pour l'utilisation WWW, en pratique, ils sont utilisés pour toutes sortes de clients et serveurs TLS, et c'est ce que suppose également OpenSSL.

Exemples :

extendedKeyUsage = critical, codeSigning, 1.2.3.4
extendedKeyUsage = serverAuth, clientAuth

Identifiant de la clé du sujet

La spécification de l'extension SKID a une valeur avec trois choix.

aucun
Aucune extension SKID ne sera incluse.
hash
Le processus spécifié dans la section 4.2.1.2. (1) de la RFC 5280 est suivi : l'identifiant de clé est composé du hachage SHA-1 de 160 bits de la valeur de la chaîne BIT subjectPublicKey (excluant le tag, la longueur et le nombre de bits inutilisés).
Une chaîne hexadécimale (possiblement avec des ":" séparant les octets)
La valeur fournie est directement sortie. Ce choix est fortement déconseillé.

Par défaut, les applications x509, req et ca se comportent comme si hash avait été donné.

Exemple :

subjectKeyIdentifier = hash

Identifiant de la clé de l'autorité

La spécification de l'extension AKID peut avoir la valeur none indiquant qu'aucun AKID ne sera inclus. Sinon, elle peut avoir la valeur keyid ou issuer ou les deux, séparés par ",". L'un ou l'autre peut avoir l'option always, indiqué en plaçant un deux-points ":" entre la valeur et cette option. Pour les certificats auto-signés, l'AKID est supprimé à moins que always ne soit présent.

Par défaut, les applications x509, req et ca se comportent comme si none avait été donné pour les certificats auto-signés et keyid"," issuer sinon.

Si keyid est présent, une tentative est faite pour copier l'identifiant de clé du sujet (SKID) du certificat de l'émetteur, sauf si le certificat de l'émetteur est identique au certificat actuel et qu'il n'est pas auto-signé. Le hachage de la clé publique associée à la clé de signature est pris comme solution de repli si le certificat de l'émetteur est identique au certificat actuel. Si always est présent mais qu'aucune valeur ne peut être obtenue, une erreur est retournée.

ed.

Si issuer est présent, et en outre qu'il possède l'option always spécifiée ou que keyid n'est pas présent, alors le DN de l'émetteur et le numéro de série sont copiés du certificat de l'émetteur. Si cela échoue, une erreur est retournée.

Exemples :

authorityKeyIdentifier = keyid, issuer
authorityKeyIdentifier = keyid, issuer:always

Nom alternatif du sujet

Il s'agit d'une extension à valeurs multiples qui prend en charge plusieurs types d'identificateurs de nom, notamment email (une adresse e-mail), URI (un indicateur uniforme de ressource), DNS (un nom de domaine DNS), RID (un ID enregistré : OBJECT IDENTIFIER), IP (une adresse IP), dirName (un nom distinctif) et otherName. La syntaxe de chacun est décrite dans les paragraphes suivants.

L'option email a deux valeurs spéciales. "copy" inclura automatiquement toutes les adresses e-mail contenues dans le nom du sujet du certificat dans l'extension. "move" déplacera automatiquement toutes les adresses e-mail du nom du sujet du certificat vers l'extension.

L'adresse IP utilisée dans l'option IP peut être au format IPv4 ou IPv6.

La valeur de dirName spécifie la section de configuration contenant le nom distinctif à utiliser, sous forme d'un ensemble de paires nom-valeur. Les AVA à valeurs multiples peuvent être formées en faisant précéder le nom d'un caractère +.

La valeur de otherName peut inclure des données arbitraires associées à un OID ; la valeur doit être l'OID suivi d'un point-virgule et du contenu spécifié en utilisant la syntaxe de ASN1_generate_nconf(3).

Exemples :

subjectAltName = email:copy, email:my@example.com, URI:http://my.example.com/
subjectAltName = IP:192.168.7.1
subjectAltName = IP:13::17
subjectAltName = email:my@example.com, RID:1.2.3.4
subjectAltName = otherName:1.2.3.4;UTF8:some other identifier
[extensions]
subjectAltName = dirName:dir_sect
[dir_sect]
C = UK
O = My Organization
OU = My Unit
CN = My Name

Les adresses e-mail non-ASCII conformes à la syntaxe définie dans la section 3.3 de la RFC 6531 sont fournies comme otherName.SmtpUTF8Mailbox. Conformément à la RFC 8398, l'adresse e-mail doit être fournie sous forme de UTF8String. Pour garantir la représentation valide dans le certificat, SmtpUTF8Mailbox doit être fourni comme suit :

subjectAltName=@alts
[alts]
otherName = 1.3.6.1.5.5.7.8.9;FORMAT:UTF8,UTF8String:nonasciiname.example.com

Nom alternatif de l'émetteur

Cette extension prend en charge la plupart des options du nom alternatif du sujet ; elle ne prend pas en charge email:copy. Elle ajoute également issuer:copy comme valeur autorisée, qui copie tous les noms alternatifs du sujet du certificat de l'émetteur, si possible.

Exemple :

issuerAltName = issuer:copy

Accès aux informations de l'autorité

Cette extension donne des détails sur la manière de récupérer des informations relatives au certificat que l'AC rend disponible. La syntaxe est access_id;location, où access_id est un identificateur d'objet (bien que seules quelques valeurs soient connues) et location a la même syntaxe que le nom alternatif du sujet (sauf que email:copy n'est pas pris en charge).

Les valeurs possibles pour access_id incluent OCSP (répondeur OCSP), caIssuers (émetteurs d'AC), ad_timestamping (horodatage AD), AD_DVCS (dvcs AD), caRepository (répertoire d'AC).

Exemples :

authorityInfoAccess = OCSP;URI:http://ocsp.example.com/,caIssuers;URI:http://myca.example.com/ca.cer
authorityInfoAccess = OCSP;URI:http://ocsp.example.com/

Points de distribution des CRL

Il s'agit d'une extension à valeurs multiples dont les valeurs peuvent être soit une paire nom-valeur utilisant la même forme que le nom alternatif du sujet, soit une seule valeur spécifiant le nom de la section contenant toutes les valeurs du point de distribution.

Lorsqu'une paire nom-valeur est utilisée, une extension DistributionPoint sera définie avec la valeur donnée comme champ fullName et le point de distribution comme valeur, et les champs reasons et cRLIssuer seront omis.

Lorsqu'une seule option est utilisée, la valeur spécifie la section, et cette section peut contenir les éléments suivants :

fullname
Le nom complet du point de distribution, dans le même format que le nom alternatif du sujet.
relativename
La valeur est prise comme un fragment de nom distinctif qui est défini comme la valeur du champ nameRelativeToCRLIssuer.
CRLIssuer
La valeur doit être dans le même format que le nom alternatif du sujet.
reasons
Un champ à valeurs multiples qui contient les raisons de la révocation. Les valeurs reconnues sont : "keyCompromise", "CACompromise", "affiliationChanged", "superseded", "cessationOfOperation", "certificateHold", "privilegeWithdrawn", et "AACompromise".

Un seul des champs fullname ou relativename doit être spécifié.

Exemples simples :

crlDistributionPoints = URI:http://example.com/myca.crl
crlDistributionPoints = URI:http://example.com/myca.crl, URI:http://example.org/my.crl

Exemple complet de point de distribution :

[extensions]
crlDistributionPoints = crldp1_section
[crldp1_section]
fullname = URI:http://example.com/myca.crl
CRLissuer = dirName:issuer_sect
reasons = keyCompromise, CACompromise
[issuer_sect]
C = UK
O = Organisation
CN = Some Name

Point de distribution d'émission

Cette extension ne doit apparaître que dans les CRL. C'est une extension à valeurs multiples dont la syntaxe est similaire à la section pointée par l'extension des points de distribution des CRL. Les noms suivants ont un sens :

fullname
Le nom complet du point de distribution, dans le même format que le nom alternatif du sujet.
relativename
La valeur est prise comme un fragment de nom distinctif qui est défini comme la valeur du champ nameRelativeToCRLIssuer.
onlysomereasons
Un champ à valeurs multiples qui contient les raisons de la révocation. Les valeurs reconnues sont : "keyCompromise", "CACompromise", "affiliationChanged", "superseded", "cessationOfOperation", "certificateHold", "privilegeWithdrawn", et "AACompromise".
onlyuser, onlyCA, onlyAA, indirectCRL
La valeur pour chacun de ces noms est un booléen.

Exemple :

[extensions]
issuingDistributionPoint = critical, @idp_section
[idp_section]
fullname = URI:http://example.com/myca.crl
indirectCRL = TRUE
onlysomereasons = keyCompromise, CACompromise

Politiques de certificat

Il s'agit d'une extension brute qui prend en charge tous les champs définis de l'extension de certificat.

Les politiques sans qualificateurs sont spécifiées en donnant l'OID. Plusieurs politiques sont séparées par des virgules. Par exemple :

certificatePolicies = 1.2.4.5, 1.1.3.4

Pour inclure des qualificateurs de politique, utilisez la syntaxe "@section" pour pointer vers une section qui spécifie toutes les informations.

La section référencée doit inclure l'OID de politique en utilisant le nom policyIdentifier. Les qualificateurs cPSuri peuvent être inclus en utilisant la syntaxe :

CPS.nnn = value

où "nnn" est un nombre.

Les qualificateurs userNotice peuvent être définis en utilisant la syntaxe :

userNotice.nnn = @notice

La valeur du qualificateur userNotice est spécifiée dans la section pertinente. Cette section peut inclure les options explicitText, organization, et noticeNumbers. explicitText et organization sont des chaînes de texte, noticeNumbers est une liste de nombres séparés par des virgules. Les options organization et noticeNumbers (si incluses) doivent TOUTES DEUX être présentes. Certains logiciels peuvent nécessiter l'option ia5org au niveau supérieur ; cela change l'encodage de Displaytext en IA5String.

Exemple :

[extensions]
certificatePolicies = ia5org, 1.2.3.4, 1.5.6.7.8, @polsect
[polsect]
policyIdentifier = 1.3.5.8
CPS.1 = "http://my.host.example.com/"
CPS.2 = "http://my.your.example.com/"
userNotice.1 = @notice
[notice]
explicitText = "Explicit Text Here"
organization = "Organisation Name"
noticeNumbers = 1, 2, 3, 4

Le codage de caractères d'explicitText peut être spécifié en faisant précéder la valeur de UTF8, BMP, ou VISIBLE suivi de deux-points. Par exemple :

[notice]
explicitText = "UTF8:Explicit Text Here"

Contraintes de politique

Il s'agit d'une extension à valeurs multiples composée des noms requireExplicitPolicy ou inhibitPolicyMapping et d'une valeur entière non négative. Au moins un composant doit être présent.

Exemple :

policyConstraints = requireExplicitPolicy:3

Inhibition de toute politique

Il s'agit d'une extension de chaîne dont la valeur doit être un entier non négatif.

Exemple :

inhibitAnyPolicy = 2

Contraintes de nom

Il s'agit d'une extension à valeurs multiples. Le nom doit commencer par le mot permitted ou excluded suivi d'un ;. Le reste du nom et la valeur suivent la syntaxe de subjectAltName, sauf que email:copy n'est pas pris en charge et que la forme IP doit consister en une adresse IP et un masque de sous-réseau séparés par un /.

Exemples :

nameConstraints = permitted;IP:192.168.0.0/255.255.0.0
nameConstraints = permitted;email:.example.com
nameConstraints = excluded;email:.com

OCSP No Check

Il s'agit d'une extension de chaîne de caractères. Elle est analysée, mais ignorée.

Exemple :

noCheck = ignored

TLS Feature (aka Must Staple)

Il s'agit d'une extension multivaluée composée d'une liste d'identifiants d'extensions TLS. Chaque identifiant peut être un nombre (0..65535) ou un nom pris en charge. Lorsqu'un client TLS envoie une extension répertoriée, le serveur TLS est censé inclure cette extension dans sa réponse.

Les noms pris en charge sont : status_request et status_request_v2.

Exemple :

tlsfeature = status_request

EXTENSIONS OBSOLÈTES

Les extensions suivantes sont non standard, spécifiques à Netscape et largement obsolètes. Leur utilisation dans de nouvelles applications est déconseillée.

Extensions String Netscape

Netscape Comment (nsComment) est une extension de chaîne de caractères contenant un commentaire qui sera affiché lors de la visualisation du certificat dans certains navigateurs. Les autres extensions de ce type sont : nsBaseUrl, nsRevocationUrl, nsCaRevocationUrl, nsRenewalUrl, nsCaPolicyUrl et nsSslServerName.

Type de certificat Netscape

Il s'agit d'une extension multivaluée qui consiste en une liste de flags à inclure. Elle était utilisée pour indiquer les objectifs pour lesquels un certificat pouvait être utilisé. Les extensions basicConstraints, keyUsage et extended key usage sont maintenant utilisées à la place.

Les valeurs acceptables pour nsCertType sont : client, server, email, objsign, reserved, sslCA, emailCA, objCA.

EXTENSIONS ARBITRAIRES

Si une extension n'est pas prise en charge par le code OpenSSL, elle doit être encodée en utilisant le format d'extension arbitraire. Il est également possible d'utiliser le format arbitraire pour les extensions supportées. La plus grande prudence doit être exercée pour s'assurer que les données sont correctement formatées pour le type d'extension donné.

Il existe deux façons d'encoder des extensions arbitraires.

La première consiste à utiliser le mot ASN1 suivi du contenu de l'extension en utilisant la même syntaxe que ASN1_generate_nconf(3). Par exemple :

[extensions]
1.2.3.4 = critical, ASN1:UTF8String:Some random data
1.2.3.4.1 = ASN1:SEQUENCE:seq_sect
[seq_sect]
field1 = UTF8:field1
field2 = UTF8:field2

Il est également possible d'utiliser le mot DER pour inclure les données encodées brutes dans n'importe quelle extension.

1.2.3.4 = critical, DER:01:02:03:04
1.2.3.4.1 = DER:01020304

La valeur suivant DER est une décharge hexadécimale de l'encodage DER de l'extension. N'importe quelle extension peut être placée sous cette forme pour remplacer le comportement par défaut. Par exemple :

basicConstraints = critical, DER:00:01:02:03

AVERTISSEMENTS

Il n'y a aucune garantie qu'une implémentation spécifique traitera une extension donnée. Il peut donc parfois être possible d'utiliser des certificats à des fins interdites par leurs extensions parce qu'une application spécifique ne reconnaît pas ou n'honore pas les valeurs des extensions pertinentes.

Les options DER et ASN1 doivent être utilisées avec précaution. Il est possible de créer des extensions invalides si elles ne sont pas utilisées avec soin.
