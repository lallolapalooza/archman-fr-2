NOM

xml2dcm - Convertit un document XML en fichier ou jeu de données DICOM

SYNOPSIS

xml2dcm [options] fichier_xml_entree fichier_dcm_sortie

DESCRIPTION

L'utilitaire xml2dcm convertit le contenu d'un document XML (Extensible Markup Language) en un fichier ou un jeu de données DICOM. Le document XML doit être valide par rapport à la DTD (Document Type Definition) qui est décrite dans le fichier dcm2xml.dtd. Un fichier XML approprié peut être créé en utilisant l'outil dcm2xml (l'option +Wb est recommandée pour inclure les données binaires).

PARAMETRES

fichier_xml_entree   Nom du fichier XML d'entrée à convertir ("-" pour stdin)
fichier_dcm_sortie  Nom du fichier DICOM de sortie ("-" pour stdout)

OPTIONS

options générales

  -h   --help
         affiche ce texte d'aide et quitte
       --version
         affiche les informations de version et quitte
       --arguments
         affiche les arguments étendus de la ligne de commande
  -q   --quiet
         mode silencieux, n'affiche aucun avertissement ni erreur
  -v   --verbose
         mode verbeux, affiche les détails de traitement
  -d   --debug
         mode de débogage, affiche les informations de débogage
  -ll  --log-level  [l]evel: chaîne de caractères
         (fatal, error, warn, info, debug, trace)
         utilise le niveau l pour le logger
  -lc  --log-config  [f]ichier: chaîne
         utilise le fichier de configuration f pour le logger

options d'entrée

format de fichier d'entrée :
  +f   --read-meta-info
         lit les métadonnées si elles sont présentes (par défaut)
  -f   --ignore-meta-info
         ignore les métadonnées du fichier

options de traitement

validation :
  +Vd  --validate-document
         valide le document XML par rapport à la DTD
  +Vn  --check-namespace
         vérifie l'espace de noms XML dans la racine du document
identificateurs uniques :
  +Ug  --generate-new-uids
         génère de nouveaux UID d'étude/série/instance SOP
  -Uo  --dont-overwrite-uids
         ne pas écraser les UID existants (par défaut)
  +Uo  --overwrite-uids
         écraser les UID existants

options de sortie

format de fichier de sortie :
  +F   --write-file
         écrit au format fichier (par défaut)
  -F   --write-dataset
         écrit le jeu de données sans métadonnées de fichier
  +Fu  --update-meta-info
         met à jour des métadonnées de fichier spécifiques
syntaxe de transfert de sortie :
  +t=  --write-xfer-same
         écrit avec la même TS que l'entrée (par défaut)
  +te  --write-xfer-little
         écrit avec la TS explicite Little Endian
  +tb  --write-xfer-big
         écrit avec la TS explicite Big Endian
  +ti  --write-xfer-implicit
         écrit avec la TS implicite Little Endian
  +td  --write-xfer-deflated
         écrit avec la TS explicite Little Endian décompressée
gestion des erreurs :
  -E   --stop-on-error
         ne pas écrire si le document est invalide (par défaut)
  +E   --ignore-errors
         tente d'écrire même si le document est invalide
représentations de valeurs post-1993 :
  +u   --enable-new-vr
         active la prise en charge des nouvelles VR (UN/UT) (par défaut)
  -u   --disable-new-vr
         désactive la prise en charge des nouvelles VR, convertit en OB
encodage de la longueur des groupes :
  +g=  --group-length-recalc
         recalcule les longueurs de groupe si présentes (par défaut)
  +g   --group-length-create
         écrit toujours avec des éléments de longueur de groupe
  -g   --group-length-remove
         écrit toujours sans éléments de longueur de groupe
encodage de la longueur dans les séquences et les éléments :
  +e   --length-explicit
         écrit avec des longueurs explicites (par défaut)
  -e   --length-undefined
         écrit avec des longueurs indéfinies
remplissage final du jeu de données (pas avec --write-dataset) :
  -p=  --padding-retain
         ne pas modifier le remplissage (par défaut si pas --write-dataset)
  -p   --padding-off
         pas de remplissage (implicite si --write-dataset)
  +p   --padding-create  [f]ichier [i]élément: entier
         aligne le fichier sur un multiple de f octets et les éléments sur
         un multiple de i octets
niveau de compression deflate (uniquement avec --write-xfer-deflated) :
  +cl  --compression-level  [l]evel: entier (par défaut : 6)
         0=non compressé, 1=plus rapide, 9=meilleure compression

NOTES

La structure de base de l'entrée XML attendue ressemble à ce qui suit :

<?xml version="1.0" encoding="ISO-8859-1"?>
<!DOCTYPE file-format SYSTEM "dcm2xml.dtd">
<file-format xmlns="http://dicom.offis.de/dcmtk">
  <meta-header xfer="1.2.840.10008.1.2.1" name="Little Endian Explicit">
    <element tag="0002,0000" vr="UL" vm="1" len="4"
             name="MetaElementGroupLength">
      166
    </element>
    ...
    <element tag="0002,0013" vr="SH" vm="1" len="16"
             name="ImplementationVersionName">
      OFFIS_DCMTK_353
    </element>
  </meta-header>
  <data-set xfer="1.2.840.10008.1.2" name="Little Endian Implicit">
    <element tag="0008,0005" vr="CS" vm="1" len="10"
             name="SpecificCharacterSet">
      ISO_IR 100
    </element>
    ...
    <sequence tag="0028,3010" vr="SQ" card="2" name="VOILUTSequence">
      <item card="3">
        <element tag="0028,3002" vr="xs" vm="3" len="6"
                 name="LUTDescriptor">
          256\0\8
        </element>
        ...
      </item>
      ...
    </sequence>
    ...
    <element tag="7fe0,0010" vr="OW" vm="1" len="262144"
             name="PixelData" loaded="no" binary="hidden">
    </element>
  </data-set>
</file-format>

Les balises "file-format" et "meta-header" peuvent être absentes pour les jeux de données DICOM.

Encodage des caractères

L'encodage des caractères DICOM est déterminé automatiquement à partir de l'élément avec le tag "0008,0005" (Specific Character Set) - s'il est présent. Les jeux de caractères suivants sont actuellement pris en charge (nécessite que libxml inclue la prise en charge d'iconv, voir la sortie de --version) :

ASCII         (ISO_IR 6)    (UTF-8)
UTF-8         "ISO_IR 192"  (UTF-8)
ISO Latin 1   "ISO_IR 100"  (ISO-8859-1)
ISO Latin 2   "ISO_IR 101"  (ISO-8859-2)
ISO Latin 3   "ISO_IR 109"  (ISO-8859-3)
ISO Latin 4   "ISO_IR 110"  (ISO-8859-4)
ISO Latin 5   "ISO_IR 148"  (ISO-8859-9)
ISO Latin 9   "ISO_IR 203"  (ISO-8859-15)
Cyrillique    "ISO_IR 144"  (ISO-8859-5)
Arabe         "ISO_IR 127"  (ISO-8859-6)
Grec          "ISO_IR 126"  (ISO-8859-7)
Hébreu        "ISO_IR 138"  (ISO-8859-8)

Les jeux de caractères multiples ne sont pas pris en charge (seule la première valeur de "Specific Character Set" est utilisée pour l'encodage des caractères en cas de multiplicité de valeurs).

Voir la documentation de dcm2xml pour plus de détails sur la structure XML.

Données binaires

Les données binaires (*) peuvent être encodées soit comme une séquence de nombres hexadécimaux séparés par une barre oblique inversée "\" soit au format Base64 (binary="base64"). De plus, les données binaires peuvent également être lues depuis un fichier (binary="file"). Dans ce cas, le nom du fichier doit être spécifié comme valeur de l'élément, par exemple :

@verbatim <element tag="7fe0,0010" vr="OW" ... binary="file">subdir/pixeldata.raw</element> \endverbatim

Veuillez noter que le contenu du fichier sera lu tel quel. Les données OW sont attendues dans l'ordre Little Endian et seront échangées si nécessaire. Aucune vérification ne sera effectuée pour s'assurer que la quantité de données est raisonnable par rapport à d'autres attributs tels que Rows ou Columns.

(*) Veuillez noter qu'actuellement seuls les types de données OB et OW sont pris en charge, c'est-à-dire que les valeurs d'éléments avec une VR de OD, OF, OL et OV ne sont pas considérées comme des "données binaires" et sont traitées comme toutes les autres VR.

@subsection xml2dcm_compression Compression

Si libxml est compilé avec le support de zlib, le fichier d'entrée (\e fichier_xml_entree) peut également être compressé avec ZIP, ce qui résulte généralement en des fichiers beaucoup plus petits. Voir la sortie de l'option \e --version pour vérifier si le support de zlib est disponible.

@subsection xml2dcm_limitations Limitations

Ce site n'est en aucun cas associé à Arch Linux ni affilié à ce projet. Le contenu est uniquement une traduction des pages de manuel d'Arch publiées sur man.archlinux.org.

DESCRIPTION

Les différentes versions de libxml peuvent avoir des limites différentes concernant la longueur maximale d'une valeur d'élément XML. Par conséquent, il convient d'éviter d'utiliser des valeurs d'éléments très longues (par exemple, pour des données de pixels).

Veuillez noter que \b xml2dcm ne prend actuellement pas entièrement en charge les fichiers DICOMDIR. Plus précisément, la valeur des différents éléments de données de décalage n'est pas mise à jour automatiquement par cet outil.

@section xml2dcm_logging LOGGING

Le niveau de sortie de journalisation des différents outils en ligne de commande et des bibliothèques sous-jacentes peut être spécifié par l'utilisateur. Par défaut, seules les erreurs et les avertissements sont écrits dans le flux d'erreurs standard. L'utilisation de l'option \e --verbose permet également de signaler des messages d'information tels que les détails de traitement. L'option \e --debug peut être utilisée pour obtenir plus de détails sur l'activité interne, par exemple à des fins de débogage. D'autres niveaux de journalisation peuvent être sélectionnés à l'aide de l'option \e --log-level. En mode \e --quiet seuls les erreurs fatales sont signalées. Dans de tels événements d'erreur très graves, l'application se terminera généralement. Pour plus de détails sur les différents niveaux de journalisation, voir la documentation du module "oflog".

Si la sortie de journalisation doit être écrite dans un fichier (éventuellement avec rotation du fichier journal), dans syslog (Unix) ou dans le journal des événements (Windows), l'option \e --log-config peut être utilisée. Ce fichier de configuration permet également de diriger certains messages seulement vers un flux de sortie particulier et de filtrer certains messages en fonction du module ou de l'application où ils sont générés. Un exemple de fichier de configuration est fourni dans <em>\<etcdir\>/logger.cfg</em>.

@section xml2dcm_command_line COMMAND LINE

Tous les outils en ligne de commande utilisent la notation suivante pour les paramètres : les crochets indiquent des valeurs facultatives (0-1), les trois points indiquent que plusieurs valeurs sont autorisées (1-n), une combinaison des deux signifie 0 à n valeurs.

Les options de ligne de commande se distinguent des paramètres par un signe '+' ou '-' respectivement. Habituellement, l'ordre et la position des options de ligne de commande sont arbitraires (c'est-à-dire qu'elles peuvent apparaître n'importe où). Cependant, si les options sont mutuellement exclusives, l'apparition la plus à droite est utilisée. Ce comportement est conforme aux règles d'évaluation standard des shells Unix courants.

De plus, un ou plusieurs fichiers de commandes peuvent être spécifiés en utilisant un signe '@' comme préfixe du nom de fichier (par exemple, <em>\@command.txt</em>). Un tel argument de commande est remplacé par le contenu du fichier texte correspondant (les espaces multiples sont traités comme un seul séparateur, sauf s'ils apparaissent entre deux guillemets) avant toute évaluation supplémentaire. Veuillez noter qu'un fichier de commande ne peut pas contenir un autre fichier de commande. Cette approche simple mais efficace permet de résumer des combinaisons courantes d'options/paramètres et évite des lignes de commande trop longues et confuses (un exemple est fourni dans le fichier <em>\<datadir\>/dumppat.txt</em>).

@section xml2dcm_environment ENVIRONMENT

L'utilitaire \b xml2dcm tentera de charger les dictionnaires DICOM spécifiés dans la variable d'environnement \e DCMDICTPATH. Par défaut, c'est-à-dire si la variable d'environnement \e DCMDICTPATH n'est pas définie, le fichier <em>\<datadir\>/dicom.dic</em> sera chargé, sauf si le dictionnaire est intégré à l'application (par défaut pour Windows).

Le comportement par défaut doit être privilégié et la variable d'environnement \e DCMDICTPATH ne doit être utilisée que lorsque des dictionnaires de données alternatifs sont requis. La variable d'environnement \e DCMDICTPATH a le même format que la variable \e PATH des shells Unix, en ce sens qu'un deux-points (":") sépare les entrées. Sur les systèmes Windows, un point-virgule (";") est utilisé comme séparateur. Le code du dictionnaire de données tentera de charger chaque fichier spécifié dans la variable d'environnement DCMDICTPATH. Il est erroné si aucun dictionnaire de données ne peut être chargé.
