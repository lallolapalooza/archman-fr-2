NOM

xml2dsr - Convertit un document XML en fichier DICOM SR

SYNOPIS

xml2dsr [options] fichierxml-entree fichierdsr-sortie

DESCRIPTION

L'utilitaire xml2dsr convertit le contenu d'un document XML (Extensible Markup Language) au format DICOM Structured Reporting (SR) (format de fichier ou jeu de données brut). Le schéma XML dsr2xml.xsd ne suit pas encore de format standard. Cependant, l'application xml2dsr pourrait être améliorée à cet égard à l'avenir (par exemple, en prenant en charge HL7/CDA - Clinical Document Architecture).

Un fichier XML approprié peut être créé à l'aide de l'outil dsr2xml (option +Xn recommandée pour ajouter la déclaration d'espace de noms XML à l'élément racine).

PARAMETRES

fichierxml-entree   Nom du fichier d'entrée XML à convertir ("-" pour stdin)
fichierdsr-sortie  Nom du fichier de sortie DICOM SR ("-" pour stdout)

OPTIONS

options générales

  -h   --help
         imprimer ce texte d'aide et quitter
       --version
         imprimer les informations de version et quitter
       --arguments
         imprimer les arguments de la ligne de commande développés
  -q   --quiet
         mode silencieux, n'imprimer aucun avertissement ni erreur
  -v   --verbose
         mode verbeux, imprimer les détails du traitement
  -d   --debug
         mode de débogage, imprimer les informations de débogage
  -ll  --log-level  [n]iveau: constante de chaîne
         (fatal, error, warn, info, debug, trace)
         utiliser le niveau n pour le logger
  -lc  --log-config  [f]ichier: chaîne
         utiliser le fichier de configuration f pour le logger

options d'entrée

encodage:
  +Ee  --template-envelope
         l'élément template englobe les éléments de contenu

options de traitement

validation:
  +Vs  --validate-schema
         valider le document XML par rapport au schéma
         (pas avec --template-envelope)
  # nécessite que libxml soit compilé avec le support XML Schema
  +Vn  --check-namespace
         vérifier l'espace de noms XML dans la racine du document
identifiants uniques:
  +Ug  --generate-new-uids
         générer de nouveaux UID d'étude/série/instance SOP
  -Uo  --dont-overwrite-uids
         ne pas écraser les UID existants (par défaut)
  +Uo  --overwrite-uids
         écraser les UID existants

options de sortie

format de fichier de sortie:
  +F   --write-file
         écrire au format fichier (par défaut)
  -F   --write-dataset
         écrire le jeu de données sans méta-informations de fichier
syntaxe de transfert de sortie:
  +t=  --write-xfer-same
         écrire avec le même TS qu'en entrée (par défaut)
  +te  --write-xfer-little
         écrire avec le TS explicite little endian VR
  +tb  --write-xfer-big
         écrire avec le TS explicite big endian VR
  +ti  --write-xfer-implicit
         écrire avec le TS implicit VR little endian
  +td  --write-xfer-deflated
         écrire avec le TS explicite little endian VR déflaté
représentations de valeurs post-1993:
  +u   --enable-new-vr
         activer le support des nouveaux VR (UN/UT) (par défaut)
  -u   --disable-new-vr
         désactiver le support des nouveaux VR, convertir en OB
encodage de la longueur de groupe:
  +g=  --group-length-recalc
         recalculer les longueurs de groupe si présentes (par défaut)
  +g   --group-length-create
         écrire toujours avec des éléments de longueur de groupe
  -g   --group-length-remove
         écrire toujours sans éléments de longueur de groupe
encodage de la longueur dans les séquences et les éléments:
  +e   --length-explicit
         écrire avec des longueurs explicites (par défaut)
  -e   --length-undefined
         écrire avec des longueurs indéfinies
remplissage de fin de jeu de données (pas avec --write-dataset):
  -p=  --padding-retain
         ne pas modifier le remplissage (par défaut si pas --write-dataset)
  -p   --padding-off
         pas de remplissage (implicite si --write-dataset)
  +p   --padding-create  [f]ichier-remplissage [i]lément-remplissage: entier
         aligner le fichier sur un multiple de f octets
         et les éléments sur un multiple de i octets
niveau de compression deflate (uniquement avec --write-xfer-deflated):
  +cl  --compression-level  [n]iveau: entier (défaut: 6)
         0=non compressé, 1=le plus rapide, 9=meilleure compression

Compression

Si libxml est compilé avec le support zlib, le fichier d'entrée (fichierxml-entree) peut également être compressé avec ZIP, ce qui entraîne généralement des fichiers beaucoup plus petits. Voir la sortie de l'option --version pour vérifier si le support zlib est disponible.

Limitations

Le schéma XML dsr2xml.xsd ne prend pas en charge toutes les variations du format de sortie de dsr2xml. Cependant, le format de sortie par défaut (plus l'option --use-xml-namespace) devrait fonctionner.

Différentes versions de libxml semblent avoir des limites différentes pour la longueur maximale d'une valeur d'élément XML. Il faut donc éviter d'utiliser des valeurs d'élément très longues. Une limite typique pour libxml version 2.7.3 (et supérieures) est de 10 Mo pour une seule valeur d'élément.

JOURNALISATION

Le niveau de sortie de journalisation des différents outils en ligne de commande et des bibliothèques sous-jacentes peut être spécifié par l'utilisateur. Par défaut, seuls les erreurs et les avertissements sont écrits sur le flux d'erreurs standard. En utilisant l'option --verbose, des messages informationnels tels que les détails du traitement sont également signalés. L'option --debug peut être utilisée pour obtenir plus de détails sur l'activité interne, par exemple pour le débogage.

g. D'autres niveaux de journalisation peuvent être sélectionnés à l'aide de l'option --log-level. En mode --quiet, seules les erreurs fatales sont signalées. Dans de tels événements d'erreur très graves, l'application se terminera généralement. Pour plus de détails sur les différents niveaux de journalisation, voir la documentation du module "oflog".

Au cas où la sortie de journalisation devrait être écrite dans un fichier (avec éventuellement rotation de fichier journal), vers syslog (Unix) ou le journal des événements (Windows), l'option --log-config peut être utilisée. Ce fichier de configuration permet également de diriger uniquement certains messages vers un flux de sortie particulier et de filtrer certains messages en fonction du module ou de l'application où ils sont générés. Un exemple de fichier de configuration est fourni dans <etcdir>/logger.cfg.

LIGNE DE COMMANDE

Tous les outils en ligne de commande utilisent la notation suivante pour les paramètres : les crochets indiquent des valeurs optionnelles (0-1), trois points de suspension indiquent que plusieurs valeurs sont autorisées (1-n), une combinaison des deux signifie 0 à n valeurs.

Les options de ligne de commande se distinguent des paramètres par un signe '+' ou '-' respectivement. Habituellement, l'ordre et la position des options de ligne de commande sont arbitraires (c'est-à-dire qu'elles peuvent apparaître n'importe où). Cependant, si les options sont mutuellement exclusives, l'apparition la plus à droite est utilisée. Ce comportement est conforme aux règles d'évaluation standard des shells Unix courants.

En outre, un ou plusieurs fichiers de commande peuvent être spécifiés en utilisant un signe '@' comme préfixe du nom de fichier (par exemple, @command.txt). Un tel argument de commande est remplacé par le contenu du fichier texte correspondant (plusieurs espaces blancs sont traités comme un unique séparateur sauf s'ils apparaissent entre deux guillemets) avant toute évaluation ultérieure. Veuillez noter qu'un fichier de commande ne peut pas contenir un autre fichier de commande. Cette approche simple mais efficace permet de résumer des combinaisons courantes d'options/paramètres et d'éviter des lignes de commande trop longues et confuses (un exemple est fourni dans le fichier <datadir>/dumppat.txt).

ENVIRONNEMENT

L'utilitaire xml2dsr tentera de charger les dictionnaires de données DICOM spécifiés dans la variable d'environnement DCMDICTPATH. Par défaut, c'est-à-dire si la variable d'environnement DCMDICTPATH n'est pas définie, le fichier <datadir>/dicom.dic sera chargé, sauf si le dictionnaire est intégré à l'application (par défaut pour Windows).

Le comportement par défaut doit être préféré et la variable d'environnement DCMDICTPATH ne doit être utilisée que lorsque des dictionnaires de données alternatifs sont requis. La variable d'environnement DCMDICTPATH a le même format que la variable PATH du shell Unix, en ce sens qu'un deux-points (":") sépare les entrées. Sur les systèmes Windows, un point-virgule (";") est utilisé comme séparateur. Le code du dictionnaire de données tentera de charger chaque fichier spécifié dans la variable d'environnement DCMDICTPATH. Il s'agit d'une erreur si aucun dictionnaire de données ne peut être chargé.
