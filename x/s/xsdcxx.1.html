XSD(1) Manuel des commandes générales XSD(1)

NOM

xsd - Compilateur XML Schema vers C++

SYNTAXE

xsd commande [ options ] fichier [ fichier ...]
xsd help [ commande ]
xsd version

DESCRIPTION

xsd génère un mappage C++ statiquement typé et spécifique au vocabulaire à partir de définitions de schémas XML W3C. Le mappage spécifique à produire est sélectionné par une commande. Chaque mappage a un certain nombre d'options spécifiques au mappage qui doivent apparaître, le cas échéant, après la commande. Les fichiers d'entrée doivent être des définitions de schémas XML W3C. L'ensemble exact des fichiers générés dépend du mappage et des options sélectionnés.

COMMANDES

cxx-tree
Génère le mappage C++/Arbre. Pour chaque fichier d'entrée sous la forme nom.xsd, les fichiers C++ suivants sont générés : nom.hxx (fichier d'en-tête), nom.ixx (fichier inline, généré uniquement si l'option --generate-inline est spécifiée), nom.cxx (fichier source), et nom-fwd.hxx (fichier de déclaration anticipée, généré uniquement si l'option --generate-forward est spécifiée).
cxx-parser
Génère le mappage C++/Analyseur. Pour chaque fichier d'entrée sous la forme nom.xsd, les fichiers C++ suivants sont générés : nom-pskel.hxx (fichier d'en-tête squelette de l'analyseur), nom-pskel.ixx (fichier inline squelette de l'analyseur, généré uniquement si l'option --generate-inline est spécifiée), et nom-pskel.cxx (fichier source squelette de l'analyseur). Si l'option --generate-noop-impl ou --generate-print-impl est spécifiée, les fichiers d'implémentation d'exemple supplémentaires suivants sont générés : nom-pimpl.hxx (fichier d'en-tête d'implémentation de l'analyseur) et nom-pimpl.cxx (fichier source d'implémentation de l'analyseur). Si l'option --generate-test-driver est spécifiée, le fichier de pilote de test supplémentaire nom-driver.cxx est généré.
help
Affiche les informations d'utilisation et quitte. Utilisez
xsd help commande

pour obtenir de l'aide spécifique à la commande.

version
Affiche la version et quitte.

OPTIONS

Les options spécifiques à la commande, le cas échéant, doivent apparaître après la commande correspondante.

options communes

--std version
Spécifie la norme C++ à laquelle le code généré doit se conformer. Les valeurs valides sont c++98, c++11 (par défaut), c++14, c++17, c++20 et c++23.

La norme C++ affecte divers aspects du code généré qui sont discutés plus en détail dans la documentation spécifique à chaque mappage. Globalement, lorsque C++11 est sélectionné, le code généré repose sur la sémantique de déplacement et utilise std::unique_ptr au lieu de std::auto_ptr obsolète. Actuellement, il n'y a pas de différence entre les modes C++11 et les normes ultérieures.

Lorsque le mode C++11 est sélectionné, vous n'avez normalement pas besoin d'effectuer d'étapes supplémentaires autres que d'activer C++11 dans votre compilateur C++, si nécessaire. Le compilateur XSD ajoutera automatiquement les définitions de macros nécessaires aux fichiers d'en-tête générés qui basculeront la bibliothèque d'exécution XSD (libxsd) , uniquement sous forme de fichiers d'en-tête, en mode C++11. Cependant, si vous incluez directement des en-têtes d'exécution XSD dans votre application (normalement, vous n'incluez que les en-têtes générés), vous devrez définir la macro XSD_CXX11 pour l'ensemble de votre projet.

--char-type type
Génère du code en utilisant le type de caractère type fourni au lieu du type char par défaut. Les valeurs valides sont char et wchar_t.
--char-encoding enc
Spécifie le codage de caractères qui doit être utilisé dans le code généré. Les valeurs valides pour le type de caractère char sont utf8 (par défaut), iso8859-1, lcp (page de code locale de Xerces-C++) et custom. Si vous passez custom comme valeur, vous devrez inclure l'en-tête d'implémentation du transcoder pour votre encodage au début des fichiers d'en-tête générés (voir l'option --hxx-prologue).

Pour le type de caractère wchar_t, la seule valeur valide est auto et le codage est automatiquement sélectionné entre UTF-16 et UTF-32/UCS-4, en fonction de la taille du type wchar_t.

--output-dir dir
Écrit les fichiers générés dans dir au lieu du répertoire courant.
--generate-inline
Génère des fonctions simples en ligne. Cette option déclenche la création du fichier inline.
--generate-xml-schema
Génère un fichier d'en-tête C++ comme si le schéma compilé définissait l'espace de noms XML Schema. Pour le mappage C++/Arbre, le fichier résultant contiendra les définitions de tous les types intégrés du schéma XML. Pour le mappage C++/Analyseur, le fichier résultant contiendra les définitions de tous les squelettes d'analyseur et les implémentations correspondant aux types intégrés du schéma XML.

Le fichier de schéma fourni au compilateur n'a pas besoin d'exister et sert uniquement à dériver le nom du fichier d'en-tête résultant. Utilisez l'option --extern-xml-schema pour inclure ce fichier dans les fichiers générés pour d'autres schémas.

--extern-xml-schema fichier
Inclut un fichier d'en-tête dérivé de fichier au lieu de générer le mappage de l'espace de noms XML Schema en ligne. Le fichier fourni n'a pas besoin d'exister et sert uniquement à dériver le nom du fichier d'en-tête inclus. Utilisez l'option --generate-xml-schema pour générer ce fichier d'en-tête.
--namespace-map xns=cns
Mappe l'espace de noms XML Schema xns à l'espace de noms C++ cns. Répétez cette option pour spécifier le mappage pour plus d'un espace de noms XML Schema. Par exemple, l'option suivante :

--namespace-map http://example.com/foo/bar=foo::bar

Mapper l'espace de noms XML Schema http://example.com/foo/bar à l'espace de noms C++ foo::bar.

--namespace-regex regex
Ajoute regex à la liste des expressions régulières utilisées pour traduire les noms d'espaces de noms XML Schema en noms d'espaces de noms C++. regex est une expression régulière de type Perl sous la forme /motif/remplacement/. N'importe quel caractère peut être utilisé comme délimiteur à la place de '/'. L'échappement du caractère délimiteur dans motif ou remplacement n'est pas pris en charge.

Toutes les expressions régulières sont ajoutées à une pile, l'expression spécifiée en dernier étant considérée en premier. La première correspondance qui réussit est utilisée. Les expressions régulières sont appliquées à une chaîne sous la forme

nom_fichier espace_noms

Par exemple, si vous avez le fichier hello.xsd avec l'espace de noms http://example.com/hello et que vous exécutez xsd sur ce fichier, la chaîne en question sera :

hello.xsd. http://example.com/hello

Pour l'espace de noms intégré du schéma XML, la chaîne est :

XMLSchema.xsd http://www.w3.org/2001/XMLSchema

Les trois étapes suivantes sont effectuées pour chaque expression régulière jusqu'à ce que la correspondance soit trouvée :

1. L'expression est appliquée et si le résultat est vide, l'expression suivante est considérée.

2. Tous les '/' sont remplacés par '::'.

3. Le résultat est vérifié

doit être un nom d'espace de noms C++ valide (par exemple, foo::bar). Si ce test réussit, le résultat est utilisé comme nom d'espace de noms C++.

À titre d'exemple, l'expression suivante mappe les espaces de noms XML Schema sous la forme http://example.com/foo/bar vers des espaces de noms C++ sous la forme foo::bar :

%.* http://example.com/(.+)%$1%

Voir également la section EXPRESSIONS RÉGULIÈRES ET GUILLEMETS DE SHELL ci-dessous.

--namespace-regex-trace
Traiter le processus d'application des expressions régulières spécifiées avec l'option --namespace-regex. Utiliser cette option pour découvrir pourquoi vos expressions régulières ne font pas ce que vous attendiez.
--reserved-name n[=r]
Ajouter le nom n à la liste des noms qui ne doivent pas être utilisés comme identificateurs. Le nom peut éventuellement être suivi de = et du nom de remplacement r qui doit être utilisé à la place. Tous les mots-clés C++ sont déjà dans cette liste.
--include-with-brackets
Utiliser des chevrons (<>) au lieu de guillemets ("") dans les directives #include générées.
--include-prefix préfixe
Ajouter préfixe aux chemins des directives #include générées.

Par exemple, si vous aviez l'élément d'importation suivant dans votre schéma

<import namespace="..." schemaLocation="base.xsd"/>

et compiliez ce fragment avec --include-prefix schemas/, alors la directive d'inclusion dans le code généré serait :

#include "schemas/base.hxx"

--include-regex regex
Ajouter regex à la liste des expressions régulières utilisées pour transformer les chemins des directives #include. regex est une expression régulière de type Perl sous la forme /motif/remplacement/. Tout caractère peut être utilisé comme délimiteur au lieu de '/'. L'échappement du caractère délimiteur dans motif ou remplacement n'est pas pris en charge.

Toutes les expressions régulières sont empilées, la dernière expression spécifiée étant traitée en premier. La première correspondance réussie est utilisée.

Par exemple, l'expression suivante transforme les chemins sous la forme schemas/foo/bar en chemins sous la forme generated/foo/bar :

%schemas/(.+)%generated/$1%

Voir également la section EXPRESSIONS RÉGULIÈRES ET GUILLEMETS DE SHELL ci-dessous.

--include-regex-trace
Traiter le processus d'application des expressions régulières spécifiées avec l'option --include-regex. Utiliser cette option pour découvrir pourquoi vos expressions régulières ne font pas ce que vous attendiez.
--guard-prefix préfixe
Ajouter préfixe aux gardes d'inclusion d'en-tête générées. Le préfixe est transformé en majuscules et les caractères illégaux dans un nom de macro de préprocesseur sont remplacés par des underscores. Si cette option n'est pas spécifiée, la partie répertoire du fichier de schéma d'entrée est utilisée comme préfixe.
--hxx-suffix suffixe
Utiliser le suffixe fourni au lieu du .hxx par défaut pour construire le nom du fichier d'en-tête. Notez que ce suffixe est également utilisé pour construire les noms des fichiers d'en-tête correspondant aux schémas inclus/importés.
--ixx-suffix suffixe
Utiliser le suffixe fourni au lieu du .ixx par défaut pour construire le nom du fichier inline.
--cxx-suffix suffixe
Utiliser le suffixe fourni au lieu du .cxx par défaut pour construire le nom du fichier source.
--fwd-suffix suffixe
Utiliser le suffixe fourni au lieu du -fwd.hxx par défaut pour construire le nom du fichier de déclaration anticipée.
--hxx-regex regex
Utiliser l'expression fournie pour construire le nom du fichier d'en-tête. regex est une expression régulière de type Perl sous la forme /motif/remplacement/. Notez que cette expression est également utilisée pour construire les noms des fichiers d'en-tête correspondant aux schémas inclus/importés. Voir également la section EXPRESSIONS RÉGULIÈRES ET GUILLEMETS DE SHELL ci-dessous.
--ixx-regex regex
Utiliser l'expression fournie pour construire le nom du fichier inline. regex est une expression régulière de type Perl sous la forme /motif/remplacement/. Voir également la section EXPRESSIONS RÉGULIÈRES ET GUILLEMETS DE SHELL ci-dessous.
--cxx-regex regex
Utiliser l'expression fournie pour construire le nom du fichier source. regex est une expression régulière de type Perl sous la forme /motif/remplacement/. Voir également la section EXPRESSIONS RÉGULIÈRES ET GUILLEMETS DE SHELL ci-dessous.
--fwd-regex regex
Utiliser l'expression fournie pour construire le nom du fichier de déclaration anticipée. regex est une expression régulière de type Perl sous la forme /motif/remplacement/. Voir également la section EXPRESSIONS RÉGULIÈRES ET GUILLEMETS DE SHELL ci-dessous.
--hxx-prologue texte
Insérer texte au début du fichier d'en-tête.
--ixx-prologue texte
Insérer texte au début du fichier inline.
--cxx-prologue texte
Insérer texte au début du fichier source.
--fwd-prologue texte
Insérer texte au début du fichier de déclaration anticipée.
--prologue texte
Insérer texte au début de chaque fichier généré pour lequel il n'y a pas de prologue spécifique au fichier.
--hxx-epilogue texte
Insérer texte à la fin du fichier d'en-tête.
--ixx-epilogue texte
Insérer texte à la fin du fichier inline.
--cxx-epilogue texte
Insérer texte à la fin du fichier source.
--fwd-epilogue texte
Insérer texte à la fin du fichier de déclaration anticipée.
--epilogue texte
Insérer texte à la fin de chaque fichier généré pour lequel il n'y a pas de épilogue spécifique au fichier.
--hxx-prologue-file fichier
Insérer le contenu du fichier au début du fichier d'en-tête.
--ixx-prologue-file fichier
Insérer le contenu du fichier au début du fichier inline.
--cxx-prologue-file fichier
Insérer le contenu du fichier au début du fichier source.
--fwd-prologue-file fichier
Insérer le contenu du fichier au début du fichier de déclaration anticipée.
--prologue-file fichier
Insérer le contenu du fichier au début de chaque fichier généré pour lequel il n'y a pas de fichier de prologue spécifique.
--hxx-epilogue-file fichier
Insérer le contenu du fichier à la fin du fichier d'en-tête.
--ixx-epilogue-file fichier
Insérer le contenu du fichier à la fin du fichier inline.
--cxx-epilogue-file fichier
Insérer le contenu du fichier à la fin du fichier source.
--fwd-epilogue-file fichier
Insérer le contenu du fichier à la fin du fichier de déclaration anticipée.
--epilogue-file fichier
Insérer le contenu du fichier à la fin de chaque fichier généré pour lequel il n'y a pas de fichier d'épilogue spécifique.
--export-symbol symbole
Insérer symbole aux endroits où les instructions de contrôle d'exportation/importation de DLL (__declspec(dllexport/dllimport)) sont nécessaires.
--export-xml-schema
Exporter/importer les types dans l'espace de noms XML Schema en utilisant le symbole d'exportation fourni avec l'option --export-symbol. La macro XSD_NO_EXPORT peut être utilisée pour omettre ce code lors de la compilation C++, ce qui peut être utile si vous souhaitez utiliser le même code généré sur plusieurs plateformes.
--export-maps
Exporter les cartes de support de polymorphisme d'une DLL Win32 dans laquelle ce code généré est placé. Ceci est nécessaire lorsque votre hiérarchie de types est divisée sur plusieurs DLL, car sinon chaque DLL aura son propre ensemble de cartes. Dans cette situation, le code généré pour la DLL contenant les types de base et/ou les têtes de groupes de substitution doit être compilé avec cette option et le code généré pour toutes les autres DLL doit
uld be compiled with --import-maps. This option is only valid together with --generate-polymorphic. The XSD_NO_EXPORT macro can be used to omit this code during C++ compilation, which may be useful if you would like to use the same generated code across multiple platforms.
--import-maps
Import polymorphism support maps to a Win32 DLL or executable into which this generated code is linked. See the --export-maps option documentation for details. This options is only valid together with --generate-polymorphic. The XSD_NO_EXPORT macro can be used to omit this code during C++ compilation, which may be useful if you would like to use the same generated code across multiple platforms.
--generate-dep
Generate make dependency information. This option triggers the creation of the .d file containing the dependencies of the generated files on the main schema file as well as all the schema files that it includes/imports, transitively. This dependency file is then normally included into the main makefile to implement automatic dependency tracking. See also the --dep-* options.

Note also that automatic dependency generation is not supported in the file-per-type mode (--file-per-type). In this case, all the generated files are produced with a single compiler invocation and depend on all the schemas. As a result, it is easier to establish such a dependency manually, perhaps with the help of the --file-list* options.

--generate-dep-only
Generate make dependency information only.
--dep-phony
Generate phony targets for included/imported schema files, causing each to depend on nothing. Such dummy rules work around make errors caused by the removal of schema files without also updating the dependency file to match.
--dep-target cible
Change the target of the dependency rule. By default it contains all the generated C++ files as well as the dependency file itself, without any directory prefixes. If you require multiple targets, then you can specify them as a single, space-separated argument or you can repeat this option multiple times.
--dep-suffix suffixe
Use suffixe instead of the default .d to construct the name of the dependency file. See also --dep-file.
--dep-file chemin
Use chemin as the generated dependency file path instead of deriving it from the input file name. Write the dependency information to stdout if chemin is -. See also --dep-regex.
--dep-regex regex
Use the provided expression to construct the name of the dependency file. regex is a Perl-like regular expression in the form /motif/remplacement/. See also the section REGEX ET QUOTAGE DE SHELL ci-dessous.
--disable-warning avertissement
Disable printing warning with id avertissement. If all is specified for the warning id then all warnings are disabled.
--options-file fichier
Read additional options from fichier. Each option should appearing on a separate line optionally followed by space and an option value. Empty lines and lines starting with # are ignored. Option values can be enclosed in double (") or single (') quotes to preserve leading and trailing whitespaces as well as to specify empty values. If the value itself contains trailing or leading quotes, enclose it with an extra pair of quotes, for example '"x"'. Non-leading and non-trailing quotes are interpreted as being part of the option value.

The semantics of providing options in a file is equivalent to providing the same set of options in the same order on the command line at the point where the --options-file option is specified except that the shell escaping and quoting is not required. You can repeat this option to specify more than one options file.

--show-sloc
Show the number of generated physical source lines of code (SLOC).
--sloc-limit num
Check that the number of generated physical source lines of code (SLOC) does not exceed num.
--proprietary-license
Indicate that the generated code is licensed under a proprietary license instead of the GPL.
--custom-literals fichier
Load custom XML string to C++ literal mappings from fichier. This mechanism can be useful if you are using a custom character encoding and some of the strings in your schemas, for example element/attribute names or enumeration values, contain non-ASCII characters. In this case you will need to provide a custom mapping to C++ literals for such strings. The format of this file is specified in the custom-literals.xsd XML Schema file that can be found in the documentation directory.
--preserve-anonymous
Preserve anonymous types. By default anonymous types are automatically named with names derived from the enclosing elements/attributes. Because mappings implemented by this compiler require all types to be named, this option is only useful if you want to make sure your schemas don't have anonymous types.
--show-anonymous
Show elements and attributes that are of anonymous types. This option only makes sense together with the --preserve-anonymous option.
--anonymous-regex regex
Add regex to the list of regular expressions used to derive names for anonymous types from the enclosing attributes/elements. regex is a Perl-like regular expression in the form /motif/remplacement/. Any character can be used as a delimiter instead of '/'. Escaping of the delimiter character in motif or remplacement is not supported.

All the regular expressions are pushed into a stack with the last specified expression considered first. The first match that succeeds is used. Regular expressions are applied to a string in the form

nom-de-fichier espace-de-noms xpath

For instance:

hello.xsd http://example.com/hello element

hello.xsd http://example.com/hello type/element

As an example, the following expression makes all the derived names start with capital letters. This could be useful when your naming convention requires type names to start with capital letters:

%.* .* (.+/)*(.+)%\u$2%

See also the section REGEX ET QUOTAGE DE SHELL ci-dessous.

--anonymous-regex-trace
Trace the process of applying regular expressions specified with the --anonymous-regex option. Use this option to find out why your regular expressions don't do what you expected them to do.
--location-map ol=nl
Map the original schema location ol that is specified in the XML Schema include or import elements to new schema location nl. Repeat this option to map more than one schema location. For example, the following option maps the http://example.com/foo.xsd URL to the foo.xsd local file.

--location-map http://example.com/foo.xsd=foo.xsd

--location-regex regex
Add regex to the list of regular expressions used to map schema locations that are specified in the XML Schema include or import elements. regex is a Perl-like regular expression in the form /motif/remplacement/. Any character can be used as a delimiter instead of '/'. Escaping of the delimiter character in motif or remplacement is not supported. All the regular expressions are pushed into a stack with the last specified expression considered first. The first match that succeeds is used.

For example, the following expression maps URL locations in the form http://example.com/foo/bar.xsd to local files in the form bar.xsd:

%http://.+/(.+)%$1%

See also the section REGEX ET QUOTAGE DE SHELL ci-dessous.

--location-regex-trace
Trace the process of applying regular expressions specified with the --location-regex option. Use this option to find out why your regular expressions don't do what you expected them to do.
--file-per-type
Generate a separate set of C++ files for each type defined in XML Schema. Note that in this mode you only need to compile the root schema(s) and the code will be generated for all included and imported schemas. This compilation mode is primarily useful when some of your schemas cannot be compiled separately or have cyclic dependencies which involve type inheritance. Other options related to this mode are: --type-file-regex, --schema-file-regex, --fat-type-file, and --file-list.
--type-file-regex regex
Add regex to the list of regular expressions used to translate type names to file names when the --file-per-type option is specified. regex is a Perl-like regular expression sous la forme /pattern/replacement/. N'importe quel caractère peut être utilisé comme délimiteur au lieu de '/'. L'échappement du caractère délimiteur dans pattern ou replacement n'est pas pris en charge. Toutes les expressions régulières sont empilées, l'expression spécifiée en dernier étant considérée en premier. La première correspondance qui réussit est utilisée. Les expressions régulières sont appliquées à une chaîne sous la forme

namespace type-name

Par exemple, l'expression suivante mappe le type foo défini dans le namespace http://example.com/bar au nom de fichier bar-foo :

%http://example.com/(.+) (.+)%$1-$2%

Voir également la section REGEX AND SHELL QUOTING ci-dessous.

--type-file-regex-trace
Trace le processus d'application des expressions régulières spécifiées avec l'option --type-file-regex. Utilisez cette option pour découvrir pourquoi vos expressions régulières ne font pas ce que vous attendez.
--schema-file-regex regex
Ajoute regex à la liste des expressions régulières utilisées pour traduire les noms de fichiers de schéma lorsque l'option --file-per-type est spécifiée. regex est une expression régulière de type Perl sous la forme /pattern/replacement/. N'importe quel caractère peut être utilisé comme délimiteur au lieu de '/'. L'échappement du caractère délimiteur dans pattern ou replacement n'est pas pris en charge. Toutes les expressions régulières sont empilées, l'expression spécifiée en dernier étant considérée en premier. La première correspondance qui réussit est utilisée. Les expressions régulières sont appliquées au chemin absolu du système de fichiers d'un fichier de schéma et le résultat, y compris la partie répertoire, le cas échéant, est utilisé pour dériver les chemins de la directive #include ainsi que les chemins des fichiers C++ générés. Cette option, ainsi que --type-file-regex, sont principalement utiles pour placer les fichiers générés dans des sous-répertoires ou pour résoudre les conflits de noms de fichiers.

Par exemple, l'expression suivante mappe les fichiers de schéma du sous-répertoire foo/1.0.0/ aux fichiers du sous-répertoire foo/. En conséquence, les chemins des directives #include pour de tels schémas seront sous la forme foo/schema.hxx et les fichiers C++ générés seront placés dans le sous-répertoire foo/ :

%.*/foo/1.0.0/(.+)%foo/$1%

Voir également la section REGEX AND SHELL QUOTING ci-dessous.

--schema-file-regex-trace
Trace le processus d'application des expressions régulières spécifiées avec l'option --schema-file-regex. Utilisez cette option pour découvrir pourquoi vos expressions régulières ne font pas ce que vous attendez.
--fat-type-file
Génère le code correspondant aux éléments globaux dans des fichiers de type au lieu de fichiers de schéma lorsque l'option --type-file-regex est spécifiée. Cette option est principalement utile lorsque vous essayez de minimiser la quantité de code objet liée à un exécutable en empaquetant le code généré compilé dans une bibliothèque statique (archive).
--file-list file
Écrit une liste de fichiers C++ générés dans file ou dans stdout si file est -. Cette option est principalement utile en mode de compilation fichier par type (--file-per-type) pour créer une liste de fichiers C++ générés, par exemple, comme fragment de makefile.
--file-list-only
Écrit uniquement la liste des fichiers C++ qui seraient générés sans les générer réellement. Cette option n'a de sens qu'en conjonction avec --file-list.
--file-list-prologue text
Insère text au début de la liste des fichiers. Par commodité, toutes les occurrences de la séquence de caractères \n dans text sont remplacées par des nouvelles lignes. Cette option peut, par exemple, être utilisée pour assigner la liste de fichiers générée à une variable makefile.
--file-list-epilogue text
Insère text à la fin de la liste des fichiers. Par commodité, toutes les occurrences de la séquence de caractères \n dans text sont remplacées par des nouvelles lignes.
--file-list-delim text
Délimite les noms de fichiers écrits dans la liste de fichiers avec text au lieu de nouvelles lignes. Par commodité, toutes les occurrences de la séquence de caractères \n dans text sont remplacées par des nouvelles lignes.

options de commande cxx-tree

--generate-polymorphic
Génère du code conscient du polymorphisme. Spécifiez cette option si vous utilisez des groupes de substitution ou xsi:type. Utilisez l'option --polymorphic-type ou --polymorphic-type-all pour spécifier quelles hiérarchies de types sont polymorphes.
--polymorphic-type type
Indique que type est une racine d'une hiérarchie de types polymorphes. Le compilateur peut souvent déterminer automatiquement quels types sont polymorphes en se basant sur les déclarations de groupes de substitution. Cependant, vous pourriez avoir besoin d'utiliser cette option si vous n'utilisez pas de groupes de substitution ou si les groupes de substitution sont définis dans un autre schéma. Vous devez spécifier cette option lors de la compilation de chaque fichier de schéma qui référence type. L'argument type est un nom de type XML Schema qui peut être éventuellement qualifié avec un namespace sous la forme namespace#name.
--polymorphic-type-all
Indique que tous les types doivent être traités comme polymorphes.
--polymorphic-plate num
Spécifie la plaque de la carte polymorphe sur laquelle le code généré doit s'enregistrer. Cette fonctionnalité est principalement utile pour séparer plusieurs schémas qui définissent les mêmes types polymorphes.
--ordered-type type
Indique que l'ordre des éléments dans type est significatif. Un exemple serait un type complexe avec un choix illimité comme modèle de contenu où l'ordre des éléments dans le XML a une sémantique spécifique à l'application. Pour les types ordonnés, le compilateur génère un membre de conteneur spécial et un ensemble correspondant d'accesseurs et de modificateurs qui sont utilisés pour capturer l'ordre des éléments et, pour le contenu mixte, du texte.

L'argument type est un nom de type XML Schema qui peut être éventuellement qualifié avec un namespace sous la forme namespace#name. Notez également que vous devrez spécifier cette option lors de la compilation de chaque fichier de schéma qui a d'autres types ordonnés dérivés de ce type.

--ordered-type-derived
Traite automatiquement les types dérivés de bases ordonnées comme étant également ordonnés. Ceci est principalement utile si vous souhaitez pouvoir itérer sur le contenu complet à l'aide du conteneur d'ordre de contenu.
--ordered-type-mixed
Traite automatiquement les types complexes avec contenu mixte comme étant ordonnés.
--ordered-type-all
Indique que l'ordre des éléments dans tous les types est significatif.
--order-container type
Spécifie un modèle de classe personnalisé qui doit être utilisé comme conteneur pour l'ordre du contenu dans les types ordonnés au lieu du std::vector par défaut. Voir --ordered-type pour plus d'informations sur les types ordonnés. Cette option est principalement utile si vous avez besoin d'effectuer des recherches plus complexes dans le conteneur d'ordre de contenu, par exemple par ID d'élément. Dans ce cas, un conteneur comme Boost multi-index peut être plus pratique. Notez que si vous utilisez un conteneur personnalisé, vous devrez très probablement également inclure les en-têtes pertinents en utilisant les options --hxx-prologue*.
--generate-serialization
Génère des fonctions de sérialisation. Les fonctions de sérialisation convertissent le modèle objet en XML.
--generate-ostream
Génère des opérateurs d'insertion ostream (operator<<) pour les types générés. Cela permet d'imprimer facilement un fragment ou le modèle objet entier pour le débogage ou la journalisation.
--generate-doxygen
Génère des commentaires de documentation adaptés à l'extraction par le système de documentation Doxygen. La documentation des annotations est ajoutée aux commentaires si elle est présente dans le schéma.
--generate-comparison
Génère des opérateurs de comparaison (operator== et operator!=) pour les types complexes. La comparaison est effectuée membre par membre.
--generate-default-ctor
Génère des constructeurs par défaut même pour les types qui ont des membres requis. Les membres requis d'une instance construite à l'aide d'un tel constructeur ne sont pas initialisés et leur accès entraîne un comportement indéfini.

Génère des constructeurs qui attendent une instance d'un type de base suivie de tous les membres requis.

NAMING CONVENTION

The compiler can be instructed to use a particular naming convention in the generated code. A number of widely-used conventions can be selected using the --type-naming and --function-naming options. A custom naming convention can be achieved using the --type-regex, --accessor-regex, --one-accessor-regex, --opt-accessor-regex, --seq-accessor-regex, --modifier-regex, --one-modifier-regex, --opt-modifier-regex, --seq-modifier-regex, --parser-regex, --serializer-regex, --const-regex, --enumerator-regex, and --element-type-regex options.

The --type-naming option specifies the convention that should be used for naming C++ types. Possible values for this option are knr (default), ucc, and java. The knr value (stands for K&R) signifies the standard, lower-case naming convention with the underscore used as a word delimiter, for example: foo, foo_bar. The ucc (stands for upper-camel-case) and java values a synonyms for the same naming convention where the first letter of each word in the name is capitalized, for example: Foo, FooBar.

Similarly, the --function-naming option specifies the convention that should be used for naming C++ functions. Possible values for this option are knr (default), lcc, and java. The knr value (stands for K&R) signifies the standard, lower-case naming convention with the underscore used as a word delimiter, for example: foo(), foo_bar(). The lcc value (stands for lower-camel-case) signifies a naming convention where the first letter of each word except the first is capitalized, for example: foo(), fooBar(). The ucc value (stands for upper-camel-case) signifies a naming convention where the first letter of each word is capitalized, for example: Foo(), FooBar(). The java naming convention is similar to the lower-camel-case one except that accessor functions are prefixed with get, modifier functions are prefixed with set, parsing functions are prefixed with parse, and serialization functions are prefixed with serialize, for example: getFoo(), setFooBar(), parseRoot(), serializeRoot().

Note that the naming conventions specified with the --type-naming and --function-naming options perform only limited transformations on the names that come from the schema in the form of type, attribute, and element names. In other words, to get consistent results, your schemas should follow a similar naming convention as the one you would like to have in the generated code. Alternatively, you can use the --*-regex options (discussed below) to perform further transformations on the names that come from the schema.

The --type-regex, --accessor-regex, --one-accessor-regex, --opt-accessor-regex, --seq-accessor-regex, --modifier-regex, --one-modifier-regex, --opt-modifier-regex, --seq-modifier-regex, --parser-regex, --serializer-regex, --const-regex, --enumerator-regex, and --element-type-regex options allow you to specify extra regular expressions for each name category in addition to the predefined set that is added depending on the --type-naming and --function-naming options. Expressions that are provided with the --*-regex options are evaluated prior to any predefined expressions. This allows you to selectively override some or all of the predefined transformations. When debugging your own expressions, it is often useful to see which expressions match which names. The --name-regex-trace option allows you to trace the process of applying regular expressions to names.

The value for the --*-regex options should be a perl-like regular expression in the form /pattern/replacement/. Any character can be used as a delimiter instead of /. Escaping of the delimiter character in pattern or replacement is not supported. All the regular expressions for each category are pushed into a category-specific stack with the last specified expression considered first. The first match that succeeds is used. For the --one-accessor-regex (accessors with cardinality one), --opt-accessor-regex (accessors with cardinality optional), and --seq-accessor-regex (accessors with cardinality sequence) categories the --accessor-r egex sont utilisés comme solution de repli. Pour les catégories --one-modifier-regex, --opt-modifier-regex et --seq-modifier-regex, les expressions --modifier-regex sont utilisées comme solution de repli. Pour la catégorie --element-type-regex, les expressions --type-regex sont utilisées comme solution de repli.

Les expressions de nom de type (--type-regex) sont évaluées sur la chaîne de nom qui a le format suivant :

[espace de noms ]nom[,nom][,nom][,nom]

Les expressions de nom de type d'élément (--element-type-regex), effectives uniquement lorsque l'option --generate-element-type est spécifiée, sont évaluées sur la chaîne de nom qui a le format suivant :

espace de noms nom

Dans le format du nom de type, la partie espace de noms suivie d'un espace n'est présente que pour les noms de types globaux. Pour les types et éléments globaux définis dans des schémas sans espace de noms cible, la partie espace de noms est vide mais l'espace est toujours présent. Dans le format du nom de type, après le composant nom initial, jusqu'à trois composants nom supplémentaires peuvent être présents, séparés par des virgules. Par exemple :

http://example.com/hello type

foo

foo,iterator

foo,const,iterator

L'ensemble d'expressions régulières prédéfinies suivant est utilisé pour transformer les noms de types lorsque la convention de nommage en majuscules et minuscules est sélectionnée :

/(?:[^ ]* )?([^,]+)/\u$1/

/(?:[^ ]* )?([^,]+),([^,]+)/\u$1\u$2/

/(?:[^ ]* )?([^,]+),([^,]+),([^,]+)/\u$1\u$2\u$3/

/(?:[^ ]* )?([^,]+),([^,]+),([^,]+),([^,]+)/\u$1\u$2\u$3\u$4/

Les expressions d'accesseur et de modificateur (--*accessor-regex et --*modifier-regex) sont évaluées sur la chaîne de nom qui a le format suivant :

nom[,nom][,nom]

Après le composant nom initial, jusqu'à deux composants nom supplémentaires peuvent être présents, séparés par des virgules. Par exemple :

foo

dom,document

foo,default,value

L'ensemble d'expressions régulières prédéfinies suivant est utilisé pour transformer les noms d'accesseurs lorsque la convention de nommage java est sélectionnée :

/([^,]+)/get\u$1/

/([^,]+),([^,]+)/get\u$1\u$2/

/([^,]+),([^,]+),([^,]+)/get\u$1\u$2\u$3/

Pour les catégories analyseur, sérialiseur et énumérateur, les expressions régulières correspondantes sont évaluées sur les noms locaux des éléments et sur les valeurs d'énumération, respectivement. Par exemple, l'expression régulière prédéfinie suivante est utilisée pour transformer les noms de fonctions d'analyse lorsque la convention de nommage java est sélectionnée :

/(.+)/parse\u$1/

La catégorie const est utilisée pour créer des noms de constantes C++ pour les identifiants de contenu d'élément/générique/texte dans les types ordonnés.

Voir également la section REGEX ET QUOTAGE DE SHELL ci-dessous.

TABLEAU DE TYPES

Les fichiers de tableau de types sont utilisés en C++/Analyseur pour définir un mappage entre les schémas XML et les types C++. Le compilateur utilise ces informations pour déterminer les types de retour des fonctions post_* dans les squelettes d'analyseur correspondant aux types de schémas XML ainsi que les types d'arguments pour les rappels correspondant aux éléments et attributs de ces types.

Le compilateur dispose d'un ensemble de règles de mappage prédéfinies qui mappent les types de schémas XML intégrés à des types C++ appropriés (discutés ci-dessous) et tous les autres types à void. En fournissant vos propres tableaux de types, vous pouvez remplacer ces règles prédéfinies. Le format du fichier de tableau de types est présenté ci-dessous :

namespace espace de noms schéma [ espace de noms cxx ]
{
( include nom de fichier; )*
([ type ] type schéma type retour cxx [ type argument cxx ]; )*
}

Espace de noms schéma et type schéma sont des motifs regex tandis que espace de noms cxx, type retour cxx et type argument cxx sont des substitutions de motifs regex. Tous les noms peuvent être facultativement entourés de " ", par exemple, pour inclure des espaces blancs.

Espace de noms schéma détermine l'espace de noms du schéma XML. Espace de noms cxx, facultatif, est préfixé à chaque nom de type C++ dans cette déclaration d'espace de noms. Type retour cxx est un nom de type C++ utilisé comme type de retour pour les fonctions post_*. Type argument cxx, facultatif, est un type d'argument pour les fonctions de rappel correspondant aux éléments et attributs de ce type. Si type argument cxx n'est pas spécifié, il prend par défaut la valeur de type retour cxx si type retour cxx se termine par * ou & (c'est-à-dire s'il s'agit d'un pointeur ou d'une référence) et const type retour cxx& sinon. Nom de fichier est un nom de fichier au format " " ou < > et est ajouté avec la directive #include au code généré.

Le caractère # démarre un commentaire qui se termine par une nouvelle ligne ou la fin du fichier. Pour spécifier un nom contenant #, entourez-le de " ". Par exemple :

namespace http://www.example.com/xmlns/my my
{
include "my.hxx";


# Passer les pommes par valeur.
#
apple apple;


# Passer les oranges en tant que pointeurs.
#
orange orange_t*;
}

Dans l'exemple ci-dessus, pour le type de schéma XML http://www.example.com/xmlns/my#orange, le type C++ my::orange_t* sera utilisé comme type de retour et de type d'argument.

Plusieurs déclarations d'espaces de noms peuvent être spécifiées dans un seul fichier. La déclaration d'espace de noms peut également être complètement omise pour mapper les types dans un schéma sans espace de noms. Par exemple :

include "my.hxx";
apple apple;

namespace http://www.example.com/xmlns/my
{
orange "const orange_t*";
}

Le compilateur dispose d'un certain nombre de règles de mappage prédéfinies qui peuvent être présentées comme les fichiers de mappage suivants. Les types intégrés de schémas XML basés sur des chaînes sont mappés à std::string ou std::wstring en fonction du type de caractère sélectionné avec l'option --char-type (char par défaut). Les types binaires de schémas XML sont mappés à std::unique_ptr<xml_schema::buffer> ou std::auto_ptr<xml_schema::buffer> en fonction de la norme C++ sélectionnée avec l'option --std (c++11 par défaut).

}

REGEX ET QUOTAGE DE SHELL

Lors de la saisie d'un argument d'expression régulière dans la ligne de commande du shell, il est souvent nécessaire d'utiliser le quotage (entourer l'argument de " " ou de ' ') afin d'empêcher le shell d'interpréter certains caractères, par exemple, les espaces comme séparateurs d'arguments et $ comme expansions de variables.

Malheureusement, il est difficile d'y parvenir d'une manière portable entre les shells POSIX, tels que ceux trouvés sous GNU/Linux et UNIX, et le shell Windows. Par exemple, si vous utilisez " " pour le quotage, vous obtiendrez un résultat incorrect avec les shells POSIX si votre expression contient $. La manière standard de gérer cela sur les systèmes POSIX est d'utiliser ' ' à la place. Malheureusement, le shell Windows ne supprime pas ' ' des arguments lorsqu'ils sont transmis aux applications. Par conséquent, vous devrez peut-être utiliser ' ' pour POSIX et " " pour Windows ($ n'est pas traité comme un caractère spécial sous Windows).

Alternativement, vous pouvez enregistrer les options d'expressions régulières dans un fichier, une option par ligne, et utiliser ce fichier avec l'option --options-file. Avec cette approche, vous n'avez pas à vous soucier du quotage du shell.
