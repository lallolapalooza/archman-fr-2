LD(1) Outils de développement GNU LD(1)

NOM

ld - L'éditeur de liens GNU

SYNTAXE

ld [options] objfile ...

DESCRIPTION

ld combine un certain nombre de fichiers objets et d'archives, relocalise leurs données et résout les références symboliques. Habituellement, la dernière étape de la compilation d'un programme est l'exécution de ld.

ld accepte des fichiers de langage de commande de l'éditeur de liens écrits dans un sur-ensemble de la syntaxe du langage de commande de l'éditeur de liens AT&T, pour fournir un contrôle explicite et total sur le processus de liaison. La page man actuelle ne décrit pas le langage de commande ; voir l'entrée ld dans "info" pour tous les détails sur le langage de commande et sur d'autres aspects de l'éditeur de liens GNU.

Cette version de ld utilise les bibliothèques BFD à usage général pour opérer sur les fichiers objets. Cela permet à ld de lire, combiner et écrire des fichiers objets dans de nombreux formats différents, par exemple, COFF ou "a.out". Différents formats peuvent être liés ensemble pour produire n'importe quel type de fichier objet disponible.

Outre sa flexibilité, l'éditeur de liens GNU est plus utile que d'autres éditeurs de liens en fournissant des informations de diagnostic. De nombreux éditeurs de liens abandonnent l'exécution immédiatement lors de la rencontre d'une erreur ; lorsque cela est possible, ld continue l'exécution, vous permettant d'identifier d'autres erreurs (ou, dans certains cas, d'obtenir un fichier de sortie malgré l'erreur).

L'éditeur de liens GNU ld est conçu pour couvrir un large éventail de situations et pour être aussi compatible que possible avec d'autres éditeurs de liens. Par conséquent, vous avez de nombreux choix pour contrôler son comportement.

OPTIONS

L'éditeur de liens prend en charge une pléthore d'options en ligne de commande, mais en pratique, peu d'entre elles sont utilisées dans un contexte particulier. Par exemple, une utilisation fréquente de ld est de lier des fichiers objets Unix standard sur un système Unix standard et pris en charge. Sur un tel système, pour lier un fichier "hello.o" :

ld -o <sortie> /lib/crt0.o hello.o -lc

Cela indique à ld de produire un fichier appelé sortie comme résultat de la liaison du fichier "/lib/crt0.o" avec "hello.o" et la bibliothèque "libc.a", qui proviendra des répertoires de recherche standard. (Voir la discussion de l'option -l ci-dessous.)

Certaines des options en ligne de commande de ld peuvent être spécifiées à n'importe quel point de la ligne de commande. Cependant, les options qui font référence à des fichiers, telles que -l ou -T, provoquent la lecture du fichier au point où l'option apparaît dans la ligne de commande, par rapport aux fichiers objets et aux autres options de fichier. La répétition d'options non liées à des fichiers avec un argument différent n'aura soit aucun effet supplémentaire, soit remplacera les occurrences précédentes (celles plus à gauche sur la ligne de commande) de cette option. Les options qui peuvent être significativement spécifiées plus d'une fois sont notées dans les descriptions ci-dessous.

Les arguments non-options sont des fichiers objets ou des archives qui doivent être liés ensemble. Ils peuvent précéder, suivre ou être mélangés avec les options en ligne de commande, à l'exception qu'un argument de fichier objet ne peut pas être placé entre une option et son argument.

Habituellement, l'éditeur de liens est appelé avec au moins un fichier objet, mais vous pouvez spécifier d'autres formes d'entrées binaires à l'aide de -l, -R et du langage de commande des scripts. Si *aucun* fichier d'entrée binaire n'est spécifié, l'éditeur de liens ne produit aucune sortie et émet le message Aucun fichier d'entrée.

Si l'éditeur de liens ne peut pas reconnaître le format d'un fichier objet, il supposera qu'il s'agit d'un script d'éditeur de liens. Un script spécifié de cette manière complète le script d'éditeur de liens principal utilisé pour la liaison (soit le script d'éditeur de liens par défaut, soit celui spécifié à l'aide de -T). Cette fonctionnalité permet à l'éditeur de liens de se lier à un fichier qui ressemble à un objet ou à une archive, mais qui ne fait en réalité que définir certaines valeurs symboliques, ou utilise "INPUT" ou "GROUP" pour charger d'autres objets. La spécification d'un script de cette manière ne fait que compléter le script d'éditeur de liens principal, avec les commandes supplémentaires placées après le script principal ; utilisez l'option -T pour remplacer complètement le script d'éditeur de liens par défaut, mais notez l'effet de la commande "INSERT".

Pour les options dont les noms sont une seule lettre, les arguments des options doivent soit suivre la lettre de l'option sans espace blanc intermédiaire, soit être donnés comme arguments séparés immédiatement après l'option qui les exige.

Pour les options dont les noms sont plusieurs lettres, un tiret ou deux peuvent précéder le nom de l'option ; par exemple, -trace-symbol et --trace-symbol sont équivalents. Notez qu'il y a une exception à cette règle. Les options à plusieurs lettres commençant par une lettre minuscule 'o' ne peuvent être précédées que de deux tirets. Ceci est fait pour réduire la confusion avec l'option -o. Ainsi, par exemple, -omagic définit le nom du fichier de sortie à magic, tandis que --omagic définit l'indicateur NMAGIC sur la sortie.

Les arguments des options à plusieurs lettres doivent soit être séparés du nom de l'option par un signe égal, soit être donnés comme arguments séparés immédiatement après l'option qui les exige. Par exemple, --trace-symbol foo et --trace-symbol=foo sont équivalents. Les abréviations uniques des noms d'options à plusieurs lettres sont acceptées.

Notez que si l'éditeur de liens est appelé indirectement, via un pilote compilateur (par exemple, gcc), alors toutes les options de ligne de commande de l'éditeur de liens doivent être préfixées par -Wl, (ou ce qui est approprié pour le pilote compilateur particulier), comme ceci :

gcc -Wl,--start-group foo.o bar.o -Wl,--end-group

Ceci est important, car sinon le programme pilote du compilateur peut silencieusement ignorer les options de l'éditeur de liens, ce qui entraîne une mauvaise liaison. La confusion peut également survenir lors de la transmission d'options nécessitant des valeurs via un pilote, car l'utilisation d'un espace entre l'option et l'argument agit comme un séparateur, et amène le pilote à transmettre uniquement l'option à l'éditeur de liens et l'argument au compilateur. Dans ce cas, il est plus simple d'utiliser les formes jointes des options à une et plusieurs lettres, telles que :

gcc foo.o bar.o -Wl,-eENTRY -Wl,-Map=a.map

Voici un tableau des commutateurs génériques de ligne de commande acceptés par l'éditeur de liens GNU :

@fichier
Lire les options de la ligne de commande à partir de fichier. Les options lues sont insérées à la place de l'option @fichier originale. Si fichier n'existe pas ou ne peut pas être lu, alors l'option sera traitée littéralement, et non supprimée.

Les options dans fichier sont séparées par des espaces blancs. Un caractère d'espacement blanc peut être inclus dans une option en entourant l'option entière d'apostrophes simples ou doubles. N'importe quel caractère (y compris une barre oblique inverse) peut être inclus en faisant précéder le caractère à inclure par une barre oblique inverse. Le fichier peut lui-même contenir des options @fichier supplémentaires ; toutes ces options seront traitées récursivement.

-a mot-clé
Cette option est prise en charge pour la compatibilité HP/UX. L'argument mot-clé doit être l'une des chaînes archive, shared, ou default. -aarchive est fonctionnellement équivalent à -Bstatic, et les deux autres mots-clés sont fonctionnellement équivalents à -Bdynamic. Cette option peut être utilisée un nombre quelconque de fois.
--audit AUDITLIB
Ajoute AUDITLIB à l'entrée "DT_AUDIT" de la section dynamique. AUDITLIB n'est pas vérifié pour son existence, ni n'utilisera le DT_SONAME spécifié dans la bibliothèque. S'il est spécifié plusieurs fois, "DT_AUDIT" contiendra une liste d'interfaces d'audit à utiliser, séparée par des deux-points. Si l'éditeur de liens trouve un objet avec une entrée d'audit lors de la recherche de bibliothèques partagées, il ajoutera une entrée "DT_DEPAUDIT" correspondante dans le fichier de sortie. Cette option n'est significative que sur les plateformes ELF prenant en charge l'interface rtld-audit.

--format=format-entrée

Si votre ld est configuré de cette manière, vous pouvez utiliser l'option -b pour spécifier le format binaire des fichiers objets qui suivent cette option sur la ligne de commande. Pour assurer la compatibilité avec les éditeurs de liens produits par MRI, ld accepte les fichiers de script écrits dans un langage de commande alternatif et restreint, décrit dans la section Fichiers de script compatibles MRI de la documentation GNU ld. -d
-dc
-dp
Ces trois options sont équivalentes ; plusieurs formes sont prises en charge pour assurer la compatibilité avec d'autres éditeurs de liens. Elles attribuent de l'espace aux symboles communs même si un fichier de sortie déplaçable est spécifié (avec -r). La commande de script "FORCE_COMMON_ALLOCATION" a le même effet.
--depaudit BIBLIOAUDIT
-P BIBLIOAUDIT
Ajoute BIBLIOAUDIT à l'entrée "DT_DEPAUDIT" de la section dynamique. BIBLIOAUDIT n'est pas vérifié quant à son existence, et n'utilisera pas le DT_SONAME spécifié dans la bibliothèque. S'il est spécifié plusieurs fois, "DT_DEPAUDIT" contiendra une liste d'interfaces d'audit séparées par des deux-points à utiliser. Cette option n'est pertinente que sur les plateformes ELF prenant en charge l'interface rtld-audit. L'option -P est fournie pour la compatibilité Solaris.
--enable-linker-version
Active la directive de script d'éditeur de liens "LINKER_VERSION", décrite dans Données de section de sortie. Si cette directive est utilisée dans un script d'éditeur de liens et que cette option a été activée, une chaîne contenant la version de l'éditeur de liens sera insérée au point actuel.

Notez que l'emplacement de cette option sur la ligne de commande de l'éditeur de liens est significatif. Elle n'affectera que les scripts d'éditeur de liens qui la suivent sur la ligne de commande, ou qui sont intégrés à l'éditeur de liens.

--disable-linker-version
Désactive la directive de script d'éditeur de liens "LINKER_VERSION", de sorte qu'elle n'insère pas de chaîne de version. C'est le comportement par défaut.
--enable-non-contiguous-regions
Cette option évite de générer une erreur si une section d'entrée ne correspond pas à une section de sortie correspondante. L'éditeur de liens tente d'allouer la section d'entrée aux sections de sortie correspondantes suivantes, et ne génère une erreur que si aucune section de sortie n'est assez grande. Ceci est utile lorsque plusieurs régions mémoire non contiguës sont disponibles et que la section d'entrée n'en nécessite aucune en particulier. L'ordre dans lequel les sections d'entrée sont évaluées ne change pas, par exemple : 
MEMORY {
  MEM1 (rwx) : ORIGIN = 0x1000, LENGTH = 0x14
  MEM2 (rwx) : ORIGIN = 0x1000, LENGTH = 0x40
  MEM3 (rwx) : ORIGIN = 0x2000, LENGTH = 0x40
}
SECTIONS {
  mem1 : { *(.data.*); } > MEM1
  mem2 : { *(.data.*); } > MEM2
  mem3 : { *(.data.*); } > MEM3
}

avec les sections d'entrée :
.data.1: taille 8
.data.2: taille 0x10
.data.3: taille 4

résulte en .data.1 affecté à mem1, et .data.2 et .data.3
affectés à mem2, même si .data.3 tiendrait dans mem3.

Cette option est incompatible avec les instructions INSERT car elle modifie la manière dont les sections d'entrée sont mappées aux sections de sortie.

--enable-non-contiguous-regions-warnings
Cette option active les avertissements lorsque "--enable-non-contiguous-regions" autorise des correspondances potentiellement inattendues dans le mappage des sections, ce qui pourrait conduire à ignorer silencieusement une section au lieu d'échouer parce qu'elle ne correspond à aucune région de sortie.
-e point-entrée
--entry=point-entrée
Utilise point-entrée comme symbole explicite pour commencer l'exécution de votre programme, plutôt que le point d'entrée par défaut. S'il n'existe aucun symbole nommé point-entrée, l'éditeur de liens essaiera d'interpréter point-entrée comme un nombre, et l'utilisera comme adresse d'entrée (le nombre sera interprété en base 10 ; vous pouvez utiliser un préfixe 0x pour la base 16, ou un préfixe 0 pour la base 8). Pour i386 PE, point-entrée peut également être le nom de fonction d'origine (sans le tiret bas préfixant et/ou le stdcall suffixant @nombre le cas échéant).
--exclude-libs lib,lib,...
Spécifie une liste de bibliothèques d'archives à partir desquelles les symboles ne doivent pas être exportés automatiquement. Les noms de bibliothèques peuvent être délimités par des virgules ou des deux-points. La spécification de "--exclude-libs ALL" exclut l'exportation automatique des symboles de toutes les bibliothèques d'archives. Cette option n'est disponible que pour le port cible i386 PE de l'éditeur de liens et pour les ports cibles ELF. Pour i386 PE, les symboles explicitement listés dans un fichier .def sont toujours exportés, quelle que soit cette option. Pour les ports cibles ELF, les symboles affectés par cette option seront traités comme cachés.
--exclude-modules-for-implib module,module,...
Spécifie une liste de fichiers objets ou de membres d'archives, à partir desquels les symboles ne doivent pas être exportés automatiquement, mais qui doivent être copiés intégralement dans la bibliothèque d'importation générée lors de la liaison. Les noms de modules peuvent être délimités par des virgules ou des deux-points, et doivent correspondre exactement aux noms de fichiers utilisés par ld pour ouvrir les fichiers ; pour les membres d'archives, il s'agit simplement du nom du membre, mais pour les fichiers objets, le nom indiqué doit inclure et correspondre précisément à tout chemin utilisé pour spécifier le fichier d'entrée sur la ligne de commande de l'éditeur de liens. Cette option n'est disponible que pour le port cible i386 PE de l'éditeur de liens. Les symboles explicitement listés dans un fichier .def sont toujours exportés, quelle que soit cette option.
-E
--export-dynamic
--no-export-dynamic
Lors de la création d'un exécutable lié dynamiquement, l'utilisation de l'option -E ou de l'option --export-dynamic entraîne l'ajout de tous les symboles à la table des symboles dynamiques. La table des symboles dynamiques est l'ensemble des symboles qui sont visibles depuis les objets dynamiques au moment de l'exécution.

Si vous n'utilisez aucune de ces options (ou utilisez l'option --no-export-dynamic pour rétablir le comportement par défaut), la table des symboles dynamiques contiendra normalement uniquement les symboles qui sont référencés par un objet dynamique mentionné dans la liaison.

Si vous utilisez "dlopen" pour charger un objet dynamique qui doit faire référence aux symboles définis par le programme, plutôt qu'à un autre objet dynamique, vous devrez probablement utiliser cette option lors de la liaison du programme lui-même.

Vous pouvez également utiliser la liste dynamique pour contrôler quels symboles doivent être ajoutés à la table des symboles dynamiques si le format de sortie le prend en charge. Voir la description de --dynamic-list.

Notez que cette option est spécifique aux ports cibles ELF. Les cibles PE prennent en charge une fonction similaire pour exporter tous les symboles d'une DLL ou d'un EXE ; voir la description de --export-all-symbols ci-dessous.

--export-dynamic-symbol=glob
Lors de la création d'un exécutable lié dynamiquement, les symboles correspondant à glob seront ajoutés à la table des symboles dynamiques. Lors de la création d'une bibliothèque partagée, les références aux symboles correspondant à glob ne seront pas liées aux définitions dans la bibliothèque partagée. Cette option n'a aucun effet lors de la création d'une bibliothèque partagée et lorsque -Bsymbolic ou --dynamic-list ne sont pas spécifiés. Cette option n'est pertinente que sur les plateformes ELF qui prennent en charge les bibliothèques partagées.
--export-dynamic-symbol-list=fichier
Spécifie un --export-dynamic-symbol pour chaque modèle dans le fichier. Le format du fichier est identique au nœud de version sans portée ni nom de nœud. Voir VERSION pour plus d'informations.
-EB
Lie des objets big-endian. Ceci affecte le format de sortie par défaut.
-EL
Lie des objets little-endian. Ceci affecte le format de sortie par défaut.
-f nom
--auxiliary=nom
Lors de la création d'un objet partagé ELF, définit le champ interne DT_AUXILIARY sur le nom spécifié. Ceci indique à l'éditeur de liens dynamique que la table des symboles de l'objet partagé doit être utilisée comme filtre auxiliaire sur la table des symboles de l'objet partagé nom.

Si vous liez ultérieurement un programme à cet objet filtre, alors, lors de l'exécution du programme, l'éditeur de liens dynamique verra le champ DT_AUXILIARY. Si l'éditeur de liens dynamique résout des symboles à partir de l'objet filtre, il vérifiera d'abord s'il existe une définition dans l'objet partagé nom. S'il y en a une, elle sera utilisée à la place de la définition dans l'objet filtre. L'objet partagé nom n'a pas besoin d'exister. Ainsi, l'objet partagé nom peut être utilisé pour fournir une implémentation alternative de certaines fonctions, peut-être pour le débogage ou pour des performances spécifiques à la machine.

Cette option peut être spécifiée plusieurs fois. Les entrées DT_AUXILIARY seront créées dans

la commande en ligne.

-F nom
--filter=nom
Lors de la création d'un objet partagé ELF, définit le champ interne DT_FILTER sur le nom spécifié. Cela indique à l'éditeur de liens dynamique que la table des symboles de l'objet partagé en cours de création doit être utilisée comme filtre pour la table des symboles de l'objet partagé nom.

Si vous liez ultérieurement un programme à cet objet filtre, lors de l'exécution du programme, l'éditeur de liens dynamique verra le champ DT_FILTER. L'éditeur de liens dynamique résoudra les symboles selon la table des symboles de l'objet filtre comme d'habitude, mais il se liera effectivement aux définitions trouvées dans l'objet partagé nom. Ainsi, l'objet filtre peut être utilisé pour sélectionner un sous-ensemble des symboles fournis par l'objet nom.

Certains éditeurs de liens plus anciens utilisaient l'option -F dans toute une chaîne d'outils de compilation pour spécifier le format du fichier objet pour les fichiers objets d'entrée et de sortie. L'éditeur de liens GNU utilise d'autres mécanismes à cette fin : les options -b, --format, --oformat, la commande "TARGET" dans les scripts de l'éditeur de liens, et la variable d'environnement "GNUTARGET". L'éditeur de liens GNU ignorera l'option -F lorsqu'il ne créera pas d'objet partagé ELF.

-fini=nom
Lors de la création d'un exécutable ou d'un objet partagé ELF, appelle NOM lorsque l'exécutable ou l'objet partagé est déchargé, en définissant DT_FINI à l'adresse de la fonction. Par défaut, l'éditeur de liens utilise "_fini" comme fonction à appeler.
-g
Ignoré. Fourni pour la compatibilité avec d'autres outils.
-G valeur
--gpsize=valeur
Définit la taille maximale des objets à optimiser en utilisant le registre GP à taille. Ceci n'est pertinent que pour les formats de fichiers objets tels que MIPS ELF qui prennent en charge la mise de grands et petits objets dans différentes sections. Ceci est ignoré pour les autres formats de fichiers objets.
-h nom
-soname=nom
Lors de la création d'un objet partagé ELF, définit le champ interne DT_SONAME au nom spécifié. Lorsqu'un exécutable est lié à un objet partagé qui a un champ DT_SONAME, lors de l'exécution de l'exécutable, l'éditeur de liens dynamique tentera de charger l'objet partagé spécifié par le champ DT_SONAME au lieu d'utiliser le nom de fichier donné à l'éditeur de liens.
-i
Effectue une liaison incrémentale (identique à l'option -r).
-init=nom
Lors de la création d'un exécutable ou d'un objet partagé ELF, appelle NOM lorsque l'exécutable ou l'objet partagé est chargé, en définissant DT_INIT à l'adresse de la fonction. Par défaut, l'éditeur de liens utilise "_init" comme fonction à appeler.
-l spéc-nom
--library=spéc-nom
Ajoute l'archive ou le fichier objet spécifié par spéc-nom à la liste des fichiers à lier. Cette option peut être utilisée un nombre illimité de fois. Si spéc-nom est de la forme :nomfichier, ld recherchera dans le chemin des bibliothèques un fichier nommé nomfichier, sinon il recherchera dans le chemin des bibliothèques un fichier nommé libspéc-nom.a.

Sur les systèmes qui prennent en charge les bibliothèques partagées, ld peut également rechercher des fichiers autres que libspéc-nom.a. Spécifiquement, sur les systèmes ELF et SunOS, ld recherchera dans un répertoire une bibliothèque nommée libspéc-nom.so avant de rechercher une nommée libspéc-nom.a. (Par convention, une extension ".so" indique une bibliothèque partagée.) Notez que ce comportement ne s'applique pas à :nomfichier, qui spécifie toujours un fichier nommé nomfichier.

L'éditeur de liens ne recherche dans une archive qu'une seule fois, à l'emplacement où elle est spécifiée sur la ligne de commande. Si l'archive définit un symbole qui était indéfini dans un objet qui apparaissait avant l'archive sur la ligne de commande, l'éditeur de liens inclura les fichiers appropriés de l'archive. Cependant, un symbole indéfini dans un objet apparaissant plus tard sur la ligne de commande ne fera pas rechercher l'archive à nouveau par l'éditeur de liens.

Voir l'option -( pour forcer l'éditeur de liens à rechercher les archives plusieurs fois.

Vous pouvez lister la même archive plusieurs fois sur la ligne de commande.

Ce type de recherche d'archives est standard pour les éditeurs de liens Unix. Cependant, si vous utilisez ld sur AIX, notez qu'il est différent du comportement de l'éditeur de liens AIX.

-L repertoire-recherche
--library-path=repertoire-recherche
Ajoute le chemin repertoire-recherche à la liste des chemins que ld recherchera pour les bibliothèques d'archives et les scripts de contrôle de ld. Vous pouvez utiliser cette option un nombre illimité de fois. Les répertoires sont recherchés dans l'ordre où ils sont spécifiés sur la ligne de commande. Les répertoires spécifiés sur la ligne de commande sont recherchés avant les répertoires par défaut. Toutes les options -L s'appliquent à toutes les options -l, quel que soit l'ordre dans lequel les options apparaissent. Les options -L n'affectent pas la manière dont ld recherche un script de l'éditeur de liens à moins que l'option -T ne soit spécifiée.

Si repertoire-recherche commence par "=" ou $SYSROOT, alors ce préfixe sera remplacé par le préfixe sysroot, contrôlé par l'option --sysroot, ou spécifié lorsque l'éditeur de liens est configuré.

L'ensemble par défaut des chemins recherchés (sans être spécifié avec -L) dépend du mode d'émulation utilisé par ld, et dans certains cas également de la manière dont il a été configuré.

Les chemins peuvent également être spécifiés dans un script de liaison avec la commande "SEARCH_DIR". Les répertoires spécifiés de cette manière sont recherchés au point où le script de liaison apparaît sur la ligne de commande.

-m émulation
Émule l'éditeur de liens émulation. Vous pouvez lister les émulations disponibles avec les options --verbose ou -V.

Si l'option -m n'est pas utilisée, l'émulation est prise de la variable d'environnement "LDEMULATION", si elle est définie.

Sinon, l'émulation par défaut dépend de la manière dont l'éditeur de liens a été configuré.

--remap-inputs=motif=nomfichier
--remap-inputs-file=fichier
Ces options permettent de modifier les noms des fichiers d'entrée avant que l'éditeur de liens ne tente de les ouvrir. L'option --remap-inputs=foo.o=bar.o fera en sorte que toute tentative de charger un fichier nommé foo.o tente plutôt de charger un fichier nommé bar.o. Les motifs génériques sont autorisés dans le premier nom de fichier, ainsi --remap-inputs=foo*.o=bar.o renommera tout fichier d'entrée correspondant à foo*.o en bar.o.

Une forme alternative de l'option --remap-inputs-file=nomfichier permet de lire les renommages à partir d'un fichier. Chaque ligne du fichier peut contenir un seul renommage. Les lignes vides sont ignorées. Tout à partir d'un caractère dièse (#) jusqu'à la fin d'une ligne est considéré comme un commentaire et est également ignoré. Le motif de renommage peut être séparé du nom de fichier par un espace blanc ou un signe égal (=).

Les options peuvent être spécifiées plusieurs fois. Leur contenu s'accumule. Les renommages seront traités dans l'ordre où ils apparaissent sur la ligne de commande, et s'ils proviennent d'un fichier, dans l'ordre où ils apparaissent dans le fichier. Si une correspondance est trouvée, aucune vérification supplémentaire pour ce nom de fichier ne sera effectuée.

Si le nom de fichier de remplacement est /dev/null ou juste NUL, alors le renommage provoquera l'ignorance du fichier d'entrée. Cela peut être un moyen pratique d'expérimenter l'élimination de fichiers d'entrée d'un environnement de construction compliqué.

Notez que cette option dépend de la position et n'affecte que les noms de fichiers qui la suivent sur la ligne de commande. Ainsi :

ld foo.o --remap-inputs=foo.o=bar.o

N'aura aucun effet, alors que :

ld --remap-inputs=foo.o=bar.o foo.o

Renommera le fichier d'entrée foo.o en bar.o.

Notez que ces options affectent également les fichiers référencés par les instructions INPUT dans les scripts de l'éditeur de liens. Mais comme les scripts de l'éditeur de liens sont traités après que toute la ligne de commande a été lue, la position des options de renommage sur la ligne de commande n'est pas significative.

Si l'option verbose est activée, les renommages qui correspondent seront signalés, bien que là encore l'option verbose doive être activée sur la ligne de commande *avant* que les noms de fichiers renommés n'apparaissent.

Si les options -Map ou --print-map sont activées, la liste des renommages sera incluse dans la sortie de la carte.

-M
--print-map
Imprime une carte de liaison sur la sortie standard. Une carte de liaison fournit des informations sur la liaison, notamment :
  • Où les fichiers objets sont mappés en mémoire.
  • Comment les symboles communs sont alloués.
  • Tous les membres d'archive inclus dans la liaison, avec une mention du symbole qui a causé l'inclusion du membre d'archive.
  • Les valeurs attribuées aux symboles.

    Notez que les symboles dont les valeurs sont calculées par une expression impliquant une référence à une valeur précédente du même symbole peuvent ne pas avoir le résultat correct affiché dans la carte de liaison. En effet, l'éditeur de liens élimine les résultats intermédiaires et ne conserve que la valeur finale d'une expression. Dans de telles circonstances, l'éditeur de liens affichera la valeur finale entourée de crochets. Ainsi, par exemple, un script de l'éditeur de liens contenant :

    foo = 1
foo = foo * 4
foo = foo + 8

    produira la sortie suivante dans la carte de liaison si l'option -M

    utilisé :

    0x00000001                foo = 0x1
[0x0000000c]                foo = (foo * 0x4)
[0x0000000c]                foo = (foo + 0x8)

    Voir Expressions pour plus d'informations sur les expressions dans les scripts de liaison.

  • Comment les propriétés GNU sont fusionnées.

    Lorsque le lieur fusionne les sections .note.gnu.property d'entrée en une seule section .note.gnu.property de sortie, certaines propriétés sont supprimées ou mises à jour. Ces actions sont signalées dans la carte de liaison. Par exemple :

    Supprimé la propriété 0xc0000002 pour fusionner foo.o (0x1) et bar.o (non trouvé)

    Cela indique que la propriété 0xc0000002 est supprimée de la sortie lors de la fusion des propriétés de foo.o, dont la valeur de la propriété 0xc0000002 est 0x1, et de bar.o, qui n'a pas la propriété 0xc0000002.

    Propriété mise à jour 0xc0010001 (0x1) pour fusionner foo.o (0x1) et bar.o (0x1)

    Cela indique que la valeur de la propriété 0xc0010001 est mise à jour à 0x1 dans la sortie lors de la fusion des propriétés de foo.o, dont la valeur de la propriété 0xc0010001 est 0x1, et de bar.o, dont la valeur de la propriété 0xc0010001 est 0x1.

  • Sur certaines cibles ELF, une liste d'ajustements insérés par --relax 
    foo.o : Ajustement de la branche à 0x00000008 vers « far » dans la section .text

    Cela indique que la branche à 0x00000008 dans foo.o, ciblant le symbole « far » dans la section .text, a été remplacée par un trampoline.

--relocatable
Génère une sortie déplaçable — c'est-à-dire, génère un fichier de sortie qui peut à son tour servir d'entrée à ld. C'est souvent appelé liaison partielle. Les archives doivent être une liste de fichiers d'archives. Ils peuvent être soit des noms de fichiers explicites, soit des options -l.

Les archives spécifiées sont recherchées de manière répétée jusqu'à ce qu'aucun nouveau symbole non défini ne soit créé. Normalement, une archive n'est recherchée qu'une seule fois dans l'ordre où elle est spécifiée sur la ligne de commande. En groupant les archives, elles seront toutes recherchées de manière répétée jusqu'à ce que toutes les références possibles soient résolues.

Le format de la liste dynamique est le même que celui du nœud de version sans portée ni nom de nœud. Voir VERSION pour plus d'informations.

Normalement, l'éditeur de liens effectuera cette vérification et, s'il trouve des chevauchements, il produira des messages d'erreur appropriés. Cette option affecte le traitement des bibliothèques dynamiques référencées par les balises DT_NEEDED *à l'intérieur* des bibliothèques dynamiques ELF mentionnées sur la ligne de commande. Normalement, l'éditeur de liens n'ajoutera pas de balise DT_NEEDED au binaire de sortie pour chaque bibliothèque mentionnée dans une balise DT_NEEDED d'une bibliothèque dynamique d'entrée. Le comportement par défaut peut être restauré avec --no-copy-dt-needed-entries.

Cette option a également un effet sur la résolution des symboles dans les bibliothèques dynamiques. Avec --copy-dt-needed-entries, les bibliothèques dynamiques mentionnées sur la ligne de commande seront recherchées récursivement, en suivant leurs balises DT_NEEDED vers d'autres bibliothèques, afin de résoudre les symboles requis par le binaire de sortie. Cependant, avec le réglage par défaut, la recherche des bibliothèques dynamiques qui suivent s'arrêtera à la bibliothèque dynamique elle-même. Aucun lien DT_NEEDED ne sera parcouru pour résoudre les symboles.

--cref
Génère une table de références croisées. Si un fichier de carte de l'éditeur de liens est généré, la table de références croisées est imprimée dans le fichier de carte. Sinon, elle est imprimée sur la sortie standard.

Le format de la table est intentionnellement simple, de sorte qu'il puisse être facilement traité par un script si nécessaire. Les symboles sont imprimés, triés par nom. Pour chaque symbole, une liste de noms de fichiers est donnée. Si le symbole est défini, le premier fichier listé est l'emplacement de la définition. Si le symbole est défini comme une valeur commune, alors tous les fichiers où cela se produit apparaissent ensuite. Enfin, tous les fichiers qui référencent le symbole sont listés.

Différents compilateurs ont différents styles de "mangling". L'argument optionnel du style de démêlage peut être utilisé pour choisir un style de démêlage approprié pour votre compilateur. --gc-sections
--no-gc-sections
Activer le garbage collection des sections d'entrée inutilisées. Ceci est ignoré sur les cibles qui ne prennent pas en charge cette option. Le comportement par défaut (ne pas effectuer ce garbage collection) peut être restauré en spécifiant --no-gc-sections sur la ligne de commande. Notez que le garbage collection pour les formats COFF et PE est pris en charge, mais l'implémentation est actuellement considérée comme expérimentale.

--gc-sections décide quelles sections d'entrée sont utilisées en examinant les symboles et les relocations. La section contenant le symbole d'entrée et toutes les sections contenant des symboles indéfinis sur la ligne de commande seront conservées, tout comme les sections contenant des symboles référencés par les objets dynamiques. Notez que lors de la construction de bibliothèques partagées, le linker doit supposer que tout symbole visible est référencé. Une fois cet ensemble initial de sections déterminé, le linker marque récursivement comme utilisées toutes les sections référencées par leurs relocations. Voir --entry, --undefined, et --gc-keep-exported.

Cette option peut être définie lors d'un link partiel (activé avec l'option -r). Dans ce cas, la racine des symboles conservés doit être explicitement spécifiée soit par l'une des options --entry, --undefined, ou --gc-keep-exported, soit par une commande "ENTRY" dans le script du linker.

En tant qu'extension GNU, les sections d'entrée ELF marquées avec le drapeau "SHF_GNU_RETAIN" ne seront pas sujettes au garbage collection.

--gc-keep-exported
Lorsque --gc-sections est activé, cette option empêche le garbage collection des sections d'entrée inutilisées qui contiennent des symboles globaux ayant une visibilité par défaut ou protégée. Cette option est destinée à être utilisée pour les exécutables où les sections non référencées seraient autrement sujettes au garbage collection, quelle que soit la visibilité externe des symboles contenus. Notez que cette option n'a aucun effet lors du link d'objets partagés, car c'est déjà le comportement par défaut. Cette option n'est prise en charge que pour les cibles au format ELF.

Imprimer la taille utilisée, la taille totale et la taille utilisée des régions de mémoire créées avec la commande MEMORY. Ceci est utile sur les cibles embarquées pour avoir une vue rapide de la quantité de mémoire libre. Le format de la sortie comprend une ligne d'en-tête et une ligne par région. Imprimer une carte de link dans le fichier fichiercarte. Voir la description de l'option -M, ci-dessus. Si fichiercarte est juste le caractère "-", alors la carte sera écrite sur stdout.

Spécifier un répertoire comme fichiercarte oblige le linker à écrire la carte de link dans un fichier à l'intérieur du répertoire. Normalement, le nom du fichier à l'intérieur du répertoire est calculé en prenant le nom de base du fichier de sortie et en y ajoutant ".map". Si cependant le caractère spécial "%" est utilisé, alors il sera remplacé par le chemin complet du fichier de sortie. De plus, s'il y a des caractères après le symbole %, alors ".map" ne sera plus ajouté.

-o foo.exe -Map=bar                  [Crée ./bar]
-o ../dir/foo.exe -Map=bar           [Crée ./bar]
-o foo.exe -Map=../dir               [Crée ../dir/foo.exe.map]
-o ../dir2/foo.exe -Map=../dir       [Crée ../dir/foo.exe.map]
-o foo.exe -Map=%                    [Crée ./foo.exe.map]
-o ../dir/foo.exe -Map=%             [Crée ../dir/foo.exe.map]
-o foo.exe -Map=%.bar                [Crée ./foo.exe.bar]
-o ../dir/foo.exe -Map=%.bar         [Crée ../dir/foo.exe.bar]
-o ../dir2/foo.exe -
Map=../dir/% [Crée ../dir/../dir2/foo.exe.map] -o ../dir2/foo.exe -Map=../dir/%.bar [Crée ../dir/../dir2/foo.exe.bar]

Il est une erreur de spécifier plus d'un "%" caractère.

Si le fichier de carte existe déjà, il sera écrasé par cette opération.

Les raisons pour autoriser les références de symboles indéfinis dans les bibliothèques partagées spécifiées au moment de la liaison sont que :

  • Une bibliothèque partagée spécifiée au moment de la liaison peut ne pas être la même que celle disponible au moment du chargement, donc le symbole pourrait être résoluble au moment du chargement.
  • Il existe certains systèmes d'exploitation, par exemple BeOS et HPPA, où les symboles indéfinis dans les bibliothèques partagées sont normaux.

    Le noyau BeOS, par exemple, patch les bibliothèques partagées au moment du chargement pour sélectionner la fonction la plus appropriée pour l'architecture actuelle. Ceci est utilisé, par exemple, pour sélectionner dynamiquement une fonction memset appropriée.

Ajoute un répertoire au chemin de recherche des bibliothèques d'exécution. Ceci est utilisé lors de la liaison d'un exécutable ELF avec des objets partagés. L'option -rpath est également utilisée lors de la localisation des objets partagés nécessaires par les objets partagés explicitement inclus dans la liaison ; voir la description de l'option -rpath-link. La recherche de -rpath de cette manière n'est prise en charge que par les éditeurs de liens natifs et les éditeurs de liens croisés qui ont été configurés avec l'option --with-sysroot.

h n'est pas utilisé lors de la liaison d'un exécutable ELF, le contenu de la variable d'environnement "LD_RUN_PATH" sera utilisé s'il est défini.

L'option -rpath peut également être utilisée sur SunOS. Par défaut, sur SunOS, l'éditeur de liens construira un chemin de recherche d'exécution à partir de toutes les options -L qui lui sont données. -rpath-link=dir
Lors de l'utilisation d'ELF ou de SunOS, une bibliothèque partagée peut en nécessiter une autre. Cela se produit lorsqu'une liaison "ld -shared" inclut une bibliothèque partagée comme l'un des fichiers d'entrée.

Lorsque l'éditeur de liens rencontre une telle dépendance lors d'une liaison non partagée et non déplaçable, il tentera automatiquement de localiser la bibliothèque partagée requise et de l'inclure dans la liaison, si elle n'est pas explicitement incluse. Dans un tel cas, plusieurs répertoires sont recherchés comme décrit ci-dessous. L'option -rpath-link spécifie le premier ensemble de répertoires à rechercher. Cette option peut spécifier une séquence de noms de répertoires soit en fournissant une liste de noms séparés par des deux-points, soit en apparaissant plusieurs fois.

Les jetons $ORIGIN et $LIB peuvent apparaître dans ces répertoires de recherche. Ils seront remplacés par le chemin complet du répertoire contenant le programme ou l'objet partagé dans le cas de $ORIGIN et soit lib - pour les binaires 32 bits - soit lib64 - pour les binaires 64 bits - dans le cas de $LIB.

La forme alternative de ces jetons - ${ORIGIN} et ${LIB} peut également être utilisée. Le jeton $PLATFORM n'est pas pris en charge.

L'option --rpath-link doit être utilisée avec prudence car elle remplace le chemin de recherche qui peut avoir été codé en dur dans une bibliothèque partagée. Dans ce cas, il est possible d'utiliser involontairement un chemin de recherche différent de celui que le chargeur d'exécution aurait utilisé.

Lorsque des bibliothèques partagées supplémentaires sont requises, l'éditeur de liens recherche les répertoires dans l'ordre indiqué ci-dessous pour les trouver. Notez cependant que cela ne s'applique qu'aux bibliothèques supplémentaires nécessaires pour satisfaire les bibliothèques partagées déjà incluses. Cela ne s'applique pas aux bibliothèques qui sont incluses via l'option de ligne de commande -l. Les recherches des bibliothèques -l ne sont effectuées que dans les répertoires spécifiés par l'option -L.

1.
Tous les répertoires spécifiés par les options -rpath-link.
2.
Tous les répertoires spécifiés par les options -rpath. La différence entre -rpath et -rpath-link est que les répertoires spécifiés par les options -rpath sont inclus dans l'exécutable et utilisés à l'exécution, tandis que l'option -rpath-link n'est effective qu'au moment de la liaison. La recherche de -rpath de cette manière n'est prise en charge que par les éditeurs de liens natifs et les éditeurs de liens croisés qui ont été configurés avec l'option --with-sysroot.
3.
Sur un système ELF, pour les éditeurs de liens natifs, si les options -rpath et -rpath-link n'ont pas été utilisées, rechercher le contenu de la variable d'environnement "LD_RUN_PATH".
4.
Sur SunOS, si l'option -rpath n'a pas été utilisée, rechercher tous les répertoires spécifiés à l'aide des options -L.
5.
Pour un éditeur de liens natif, rechercher le contenu de la variable d'environnement "LD_LIBRARY_PATH".
6.
Pour un éditeur de liens ELF natif, les répertoires dans "DT_RUNPATH" ou "DT_RPATH" d'une bibliothèque partagée sont recherchés pour les bibliothèques partagées dont elle a besoin. Les entrées "DT_RPATH" sont ignorées si des entrées "DT_RUNPATH" existent.
7.
Pour un éditeur de liens d'un système Linux, si le fichier /etc/ld.so.conf existe, la liste des répertoires trouvés dans ce fichier. Remarque : le chemin vers ce fichier est précédé de la valeur "sysroot", si elle est définie, puis de toute chaîne "prefix" si l'éditeur de liens a été configuré avec l'option --prefix=<path>.
8.
Pour un éditeur de liens natif sur un système FreeBSD, tous les répertoires spécifiés par la macro "_PATH_ELF_HINTS" définie dans le fichier d'en-tête elf-hints.h.
9.
Tous les répertoires spécifiés par une commande "SEARCH_DIR" dans un script d'éditeur de liens donné sur la ligne de commande, y compris les scripts spécifiés par -T (mais pas -dT).
10.
Les répertoires par défaut, normalement /lib et /usr/lib.
11.
Tous les répertoires spécifiés par un plugin LDPT_SET_EXTRA_LIBRARY_PATH.
12.
Tous les répertoires spécifiés par une commande "SEARCH_DIR" dans un script d'éditeur de liens par défaut.

Notez cependant sur les systèmes basés sur Linux qu'il existe une mise en garde supplémentaire : Si l'option --as-needed est active et qu'une bibliothèque partagée est trouvée qui satisferait normalement la recherche et que cette bibliothèque n'a pas de tag DT_NEEDED pour libc.so et qu'il existe une bibliothèque partagée plus loin dans l'ensemble des répertoires de recherche qui satisfait également la recherche et que cette seconde bibliothèque partagée a un tag DT_NEEDED pour libc.so, alors la seconde bibliothèque sera sélectionnée à la place de la première.

Si la bibliothèque partagée requise n'est pas trouvée, l'éditeur de liens émettra un avertissement et continuera la liaison.

--section-ordering-file=script
Cette option est utilisée pour augmenter le script d'éditeur de liens actuel avec un mappage supplémentaire des sections d'entrée aux sections de sortie. Ce fichier doit utiliser la même syntaxe pour "SECTIONS" que celle utilisée dans les scripts d'éditeur de liens normaux, mais il ne doit rien faire d'autre que de placer les sections d'entrée dans les sections de sortie. @pxref{SECTIONS}

Une deuxième contrainte sur le script d'ordonnancement des sections est qu'il ne peut référencer que des sections de sortie déjà définies par le script d'éditeur de liens actuellement utilisé. (C'est-à-dire le script d'éditeur de liens par défaut ou un script spécifié sur la ligne de commande). L'avantage du script d'ordonnancement des sections est cependant qu'il peut être utilisé pour mapper les sections d'entrée au début des sections de sortie, afin qu'ils puissent assurer l'ordonnancement des sections dans la section de sortie. Par exemple, imaginons que le script d'éditeur de liens par défaut ressemble à ceci :

SECTIONS {
  .text : { *(.text.hot) ; *(.text .text.*) }
  .data : { *(.data.big) ; *(.data .data.*) }
  }

Ensuite, si un fichier d'ordonnancement de sections comme celui-ci est utilisé :

.text : { *(.text.first) ; *(.text.z*) }
.data : { foo.o(.data.first) ; *(.data.small) }

Ceci serait équivalent à un script d'éditeur de liens comme ceci :

SECTIONS {
  .text : { *(.text.first) ; *(.text.z*) ; *(.text.hot) ; *(.text .text.*) }
  .data : { foo.o(.data.first) ; *(.data.small) ; *(.data.big) ; *(.data .data.*) }
  }

L'avantage du fichier d'ordonnancement de sections est qu'il peut être utilisé pour ordonnancer les sections qui importent à l'utilisateur sans avoir à se soucier des autres sections, des régions mémoire, ou de quoi que ce soit d'autre.

--stats[=filename]
Calcule et affiche des statistiques sur le fonctionnement de l'éditeur de liens, telles que le temps d'exécution et l'utilisation de la mémoire.

Si l'argument optionnel nomfichier n'est pas fourni, seules des informations de base sont signalées et elles sont envoyées vers le flux de sortie d'erreur standard. Si l'argument nomfichier est fourni, des informations étendues sont écrites dans le fichier nommé. Si nomfichier est défini sur le symbole -, les informations étendues sont envoyées vers le flux de sortie standard. Si nomfichier commence par +, le fichier est ouvert en mode ajout plutôt qu'en mode écrasement.

Si l'option -Map a été activée, les informations sont également enregistrées dans le fichier de mappage. Notez que si les deux options --stats et -Map ont reçu des arguments nomfichier et qu'ils correspondent, les informations ne seront écrites qu'une seule fois, pas deux.

Si la variable d'environnement "LD_STATS" est définie, cela se comporte comme l'option --stats. Si la valeur de la variable est une chaîne de caractères, elle sera utilisée comme nom d'un fichier dans lequel les informations doivent être enregistrées. Sinon, les informations seront envoyées vers le flux de sortie standard. L'utilisation de la variable d'environnement permet d'enregistrer les statistiques sans avoir à modifier la ligne de commande de l'éditeur de liens. Notez que si la variable d'environnement et l'option --stats sont utilisées, l'option --stats a la priorité.

Les informations étendues signalées incluent le temps CPU utilisé et, si l'appel de bibliothèque système getrusage() est disponible, l'utilisation de la mémoire est également enregistrée. Ces informations sont signalées pour des parties individuelles du processus de liaison, appelées phases. De plus, les informations sont également signalées pour une phase spéciale appelée ALL, qui couvre l'ensemble du processus de liaison. Notez que les phases individuelles peuvent contenir ou chevaucher d'autres phases, il ne faut donc pas supposer que les ressources globales utilisées par l'éditeur de liens sont la somme des ressources utilisées par les phases individuelles.

De plus, lorsque des informations étendues sont signalées, la version de l'éditeur de liens, les arguments de la ligne de commande et l'heure de démarrage de l'éditeur de liens sont également inclus. Cela facilite la gestion des situations où plusieurs liaisons sont invoquées par un système de build et permet d'identifier exactement quels arguments ont été responsables de la production des statistiques signalées.

Pour certaines cibles, la sortie de ld diffère à certains égards de la sortie de certains éditeurs de liens existants. Ce commutateur demande à ld d'utiliser le format traditionnel à la place.

--warn-common
Avertit lorsqu'un symbole commun est combiné avec un autre symbole commun ou avec une définition de symbole. Les éditeurs de liens Unix autorisent cette pratique quelque peu laxiste, mais les éditeurs de liens sur certains autres systèmes d'exploitation ne le font pas. Cette option vous permet de trouver des problèmes potentiels liés à la combinaison de symboles globaux. Malheureusement, certaines bibliothèques C utilisent cette pratique, vous pourriez donc recevoir des avertissements concernant des symboles dans les bibliothèques ainsi que dans vos programmes.

Il existe trois types de symboles globaux, illustrés ici par des exemples C :

int i = 1;
Une définition, qui va dans la section de données initialisées du fichier de sortie.
extern int i;
Une référence indéfinie, qui n'alloue pas d'espace. Il doit y avoir soit
er une définition ou un symbole commun pour la variable quelque part.
int i;
Un symbole commun. S'il n'y a que (un ou plusieurs) symboles communs pour une variable, elle est placée dans la zone de données non initialisées du fichier de sortie. L'éditeur de liens fusionne plusieurs symboles communs pour la même variable en un seul symbole. S'ils sont de tailles différentes, il choisit la plus grande taille. L'éditeur de liens transforme un symbole commun en une déclaration, s'il existe une définition de la même variable.

L'option --warn-common peut produire cinq types d'avertissements. Chaque avertissement consiste en une paire de lignes : la première décrit le symbole qui vient d'être rencontré, et la seconde décrit le symbole précédent rencontré avec le même nom. L'un ou les deux symboles seront un symbole commun.

1.
Transformation d'un symbole commun en une référence, car il existe déjà une définition pour le symbole. 
<file>(<section>): warning: common of `<symbol>'
   overridden by definition
<file>(<section>): warning: defined here
2.
Transformation d'un symbole commun en une référence, car une définition ultérieure du symbole est rencontrée. Ceci est identique au cas précédent, sauf que les symboles sont rencontrés dans un ordre différent. 
<file>(<section>): warning: definition of `<symbol>'
   overriding common
<file>(<section>): warning: common is here
3.
Fusion d'un symbole commun avec un symbole commun précédent de même taille. 
<file>(<section>): warning: multiple common
   of `<symbol>'
<file>(<section>): warning: previous common is here
4.
Fusion d'un symbole commun avec un symbole commun précédent plus grand. 
<file>(<section>): warning: common of `<symbol>'
   overridden by larger common
<file>(<section>): warning: larger common is here
5.
Fusion d'un symbole commun avec un symbole commun précédent plus petit. Ceci est identique au cas précédent, sauf que les symboles sont rencontrés dans un ordre différent. 
<file>(<section>): warning: common of `<symbol>'
   overriding smaller common
<file>(<section>): warning: smaller common is here
--warn-constructors
Avertir si des constructeurs globaux sont utilisés. Ceci n'est utile que pour quelques formats de fichiers objets. Pour des formats tels que COFF ou ELF, l'éditeur de liens ne peut pas détecter l'utilisation de constructeurs globaux.
--warn-execstack
--warn-execstack-objects
--no-warn-execstack
Sur les plateformes ELF, l'éditeur de liens peut générer des messages d'avertissement s'il lui est demandé de créer un fichier de sortie contenant une pile exécutable. Il existe trois états possibles :
1.
Ne générer aucun avertissement.
2.
Générer toujours des avertissements, même si la pile exécutable est demandée via l'option de ligne de commande -z execstack.
3.
Générer un avertissement uniquement si un fichier objet demande une pile exécutable, mais pas si l'option -z execstack est utilisée.

L'état par défaut dépend de la manière dont l'éditeur de liens a été configuré lors de sa création. L'option --no-warn-execstack place toujours l'éditeur de liens dans l'état sans avertissement. L'option --warn-execstack place l'éditeur de liens dans l'état d'avertissement permanent. L'option --warn-execstack-objects place l'éditeur de liens dans l'état d'avertissement uniquement pour les fichiers objets.

Note : les fichiers d'entrée au format ELF peuvent spécifier qu'ils nécessitent une pile exécutable en ayant une section .note.GNU-stack avec le bit exécutable défini dans ses drapeaux de section. Ils peuvent spécifier qu'ils n'ont pas besoin d'une pile exécutable en ayant la même section, mais sans le bit de drapeau exécutable défini. Si un fichier d'entrée n'a pas de section .note.GNU-stack, alors le comportement par défaut est spécifique à la cible. Pour certaines cibles, l'absence d'une telle section implique qu'une pile exécutable est requise. C'est souvent un problème pour les fichiers assembleur créés manuellement.

--error-execstack
--no-error-execstack
Si l'éditeur de liens va générer un message d'avertissement concernant une pile exécutable, l'option --error-execstack transformera cet avertissement en une erreur. Notez que cette option ne modifie pas l'état de génération des avertissements de pile exécutable de l'éditeur de liens. Utilisez --warn-execstack ou --warn-execstack-objects pour définir un état d'avertissement spécifique.

L'option --no-error-execstack rétablira le comportement par défaut de génération de messages d'avertissement.

--warn-multiple-gp
Avertir si plusieurs valeurs de pointeur global sont requises dans le fichier de sortie. Ceci n'est pertinent que pour certains processeurs, tels que l'Alpha. Plus précisément, certains processeurs placent les constantes de grande valeur dans une section spéciale. Un registre spécial (le pointeur global) pointe vers le milieu de cette section, de sorte que les constantes puissent être chargées efficacement via un mode d'adressage relatif au registre de base. Étant donné que le décalage en mode relatif au registre de base est fixe et relativement petit (par exemple, 16 bits), cela limite la taille maximale du pool de constantes. Ainsi, dans les grands programmes, il est souvent nécessaire d'utiliser plusieurs valeurs de pointeur global afin de pouvoir adresser toutes les constantes possibles. Cette option provoque un avertissement chaque fois que ce cas se produit.
--warn-once
N'émettre qu'un seul avertissement par symbole non résolu, au lieu d'un par module qui y fait référence.
--warn-rwx-segments
--no-warn-rwx-segments
Avertir si l'éditeur de liens crée un segment chargeable, de taille non nulle, qui possède les trois drapeaux de permission de lecture, écriture et exécution définis. Un tel segment représente une vulnérabilité de sécurité potentielle. De plus, des avertissements seront générés si un segment de stockage local de thread est créé avec le drapeau de permission d'exécution défini, indépendamment du fait qu'il ait ou non les drapeaux de lecture et/ou d'écriture définis.

Ces avertissements sont activés par défaut. Ils peuvent être désactivés via l'option --no-warn-rwx-segments et réactivés via l'option --warn-rwx-segments.

--error-rwx-segments
--no-error-rwx-segments
Si l'éditeur de liens va générer un message d'avertissement concernant un segment exécutable et accessible en écriture, ou un segment TLS exécutable, alors l'option --error-rwx-segments transformera cet avertissement en une erreur à la place. L'option --no-error-rwx-segments rétablira le comportement par défaut consistant à générer uniquement un message d'avertissement.

Notez que l'option --error-rwx-segments n'active pas en soi les avertissements concernant ces segments. Ces avertissements sont soit activés par défaut, si l'éditeur de liens a été configuré ainsi, soit via l'option de ligne de commande --warn-rwx-segments.

--warn-section-align
Avertir si l'adresse d'une section de sortie est modifiée en raison de l'alignement. Typiquement, l'alignement sera défini par une section d'entrée. L'adresse ne sera modifiée que si elle n'est pas explicitement spécifiée ; c'est-à-dire si la commande "SECTIONS" ne spécifie pas d'adresse de départ pour la section.
--warn-textrel
Avertir si l'éditeur de liens ajoute DT_TEXTREL à un exécutable indépendant de la position ou à un objet partagé.
--warn-alternate-em
Avertir si un objet a un code machine ELF alternatif.
--warn-unresolved-symbols
Si l'éditeur de liens doit signaler un symbole non résolu (voir l'option --unresolved-symbols), il générera normalement une erreur. Cette option lui fait générer un avertissement à la place.
--error-unresolved-symbols
Ceci rétablit le comportement par défaut de l'éditeur de liens consistant à générer des erreurs lorsqu'il signale des symboles non résolus.
--whole-archive
Pour chaque archive mentionnée sur la ligne de commande après l'option --whole-archive, inclure chaque fichier objet de l'archive dans l'édition de liens, plutôt que de rechercher dans l'archive les fichiers objets requis. Ceci est normalement utilisé pour transformer un fichier archive en une bibliothèque partagée, forçant chaque objet à être inclus dans la bibliothèque partagée résultante. Cette option peut être utilisée plusieurs fois.

Deux notes lors de l'utilisation de cette option avec gcc : Premièrement, gcc ne connaît pas cette option, vous devez donc utiliser -Wl,-whole-archive. Deuxièmement, n'oubliez pas d'utiliser -Wl,-no-whole-archive après votre liste d'archives, car gcc ajoutera sa propre liste d'archives à votre édition de liens et vous pourriez ne pas vouloir que cet indicateur affecte celles-ci également.

--wrap=symbole
Utiliser une fonction d'encapsulation pour symbole. Toute référence indéfinie à symbole sera résolue en "__wrap_symbole". Toute référence indéfinie à "__real_symbole" sera résolue en symbole.

Ceci peut être utilisé pour fournir une fonction d'encapsulation pour une fonction système. La fonction d'encapsulation doit être appelée "__wrap_symbole". Si elle souhaite appeler la fonction système, elle doit appeler "__real_symbole".

Voici un exemple trivial :

void *
__wrap_malloc (size_t c)
{
  printf ("malloc appelé avec %zu\n", c);
  return __real_malloc (c);
}

Si vous liez d'autres codes avec ce fichier en utilisant --wrap malloc, alors tous les appels à "malloc" appelleront la fonction "__wrap_malloc" à la place. L'appel à "__real_malloc" dans "__wrap_malloc" appellera le vrai "malloc" .

Vous pouvez également souhaiter fournir une fonction "__real_malloc" , afin que les liens sans l'option --wrap réussissent. Si vous le faites, vous ne devez pas placer la définition de "__real_malloc" dans le même fichier que "__wrap_malloc" ; si vous le faites, l'assembleur peut résoudre l'appel avant que l'éditeur de liens n'ait la possibilité de l'envelopper vers "malloc".

Seules les références indéfinies sont remplacées par l'éditeur de liens. Ainsi, les références internes à l'unité de traduction à symbole ne sont pas résolues en "__wrap_symbole" . Dans l'exemple suivant, l'appel à "f" dans "g" n'est pas résolu en "__wrap_f" .

int
f (void)
{
  return 123;
}

int
g (void)
{
  return f();
}

Sur les plateformes ELF, ces options contrôlent comment les sections de débogage DWARF sont compressées à l'aide de zlib.

--compress-debug-sections=none ne compresse pas les sections de débogage DWARF. --compress-debug-sections=zlib-gnu compresse les sections de débogage DWARF et les renomme pour commencer par .zdebug au lieu de .debug. --compress-debug-sections=zlib-gabi compresse également les sections de débogage DWARF, mais au lieu de les renommer, il définit le drapeau SHF_COMPRESSED dans les en-têtes des sections.

--reduce-memory-overheads
Cette option réduit les besoins en mémoire à l'exécution de ld, au détriment de la vitesse de liaison. Elle a été introduite pour sélectionner l'ancien algorithme O(n^2) pour la génération de fichiers de carte de liaison, plutôt que le nouvel algorithme O(n) qui utilise environ 40% de mémoire en plus pour le stockage des symboles.

Un autre effet de ce commutateur est de définir la taille par défaut de la table de hachage sur 1021, ce qui économise de la mémoire au prix d'un temps d'exécution plus long pour l'éditeur de liens. Cela n'est cependant pas fait si le commutateur --hash-size a été utilisé.

Le commutateur --reduce-memory-overheads peut également être utilisé pour activer d'autres compromis dans les futures versions de l'éditeur de liens.

--build-id
--build-id=style
Demande la création d'une section de note ELF ".note.gnu.build-id" ou d'une section COFF ".buildid" . Le contenu de la note sont des bits uniques identifiant ce fichier lié. style peut être "uuid" pour utiliser 128 bits aléatoires ; "sha1" pour utiliser un hachage SHA1 de 160 bits, "md5" pour utiliser un hachage MD5 de 128 bits, ou "xx" pour utiliser un XXHASH de 128 bits sur les parties normatives du contenu de sortie ; ou "0xchaînehexadécimale" pour utiliser une chaîne de bits choisie spécifiée comme un nombre pair de chiffres hexadécimaux (les caractères "-" et ":" entre les paires de chiffres sont ignorés). Si style est omis, "sha1" est utilisé.

Les styles "md5" , "sha1" et "xx" produisent un identifiant qui est toujours le même dans un fichier de sortie identique, mais qui est presque certainement unique parmi tous les fichiers de sortie non identiques. Il n'est pas destiné à être comparé comme une somme de contrôle pour le contenu du fichier. Un fichier lié peut être modifié ultérieurement par d'autres outils, mais la chaîne de bits d'ID de construction identifiant le fichier lié d'origine ne change pas.

L'utilisation de 'auto-import' fonctionne généralement sans problème - mais parfois vous pouvez voir ce message :

"variable '<var>' ne peut pas être auto-importée. Veuillez lire la documentation de "--enable-auto-import" de ld pour plus de détails."

Ce message se produit lorsque certaines (sous)expressions accèdent à une adresse donnée finalement par la somme de deux constantes (les tables d'importation Win32 n'autorisent qu'une seule). Les instances où cela peut se produire incluent les accès aux champs membres de variables struct importées d'une DLL, ainsi que l'utilisation d'un indice constant dans un tableau variable importé d'une DLL. Toute variable multi-mots (tableaux, structs, long long, etc.) peut déclencher cette condition d'erreur. Cependant, quel que soit le type de données exact de la variable exportée fautive, ld la détectera toujours, émettra l'avertissement et s'arrêtera.

Il existe plusieurs façons de résoudre cette difficulté, quel que soit le type de données de la variable exportée :

Une façon est d'utiliser l'option --enable-runtime-pseudo-reloc. Cela laisse la tâche d'ajuster les références dans votre code client à l'environnement d'exécution, donc cette méthode ne fonctionne que lorsque l'environnement d'exécution prend en charge cette fonctionnalité.

Une deuxième solution consiste à forcer l'une des 'constantes' à être une variable - c'est-à-dire inconnue et non optimisable au moment de la compilation. Pour les tableaux, il y a deux possibilités : a) faire de l'indice (l'adresse du tableau) une variable, ou b) faire de l'indice 'constant' une variable. Ainsi :

extern type extern_array[];
extern_array[1] -->
   { volatile type *t=extern_array; t[1] }

ou

extern type extern_array[];
extern_array[1] -->
   { volatile int t=1; extern_array[t] }

Pour les structs (et la plupart des autres types de données multi-mots), la seule option est de faire de la struct elle-même (ou du long long, ou du ...) une variable :

extern struct s extern_struct;
extern_struct.field -->
   { volatile struct s *t=&extern_struct; t->field }

ou

extern long long extern_ll;
extern_ll -->
  { volatile long long * local_ll=&extern_ll; *local_ll }

Une troisième méthode pour traiter cette difficulté est d'abandonner 'auto-import' pour le symbole fautif et de le marquer avec "__declspec(dllimport)". Cependant, en pratique, cela nécessite d'utiliser des #defines au moment de la compilation pour indiquer si vous construisez une DLL, si vous construisez du code client qui sera lié à la DLL, ou simplement si vous construisez/liez une bibliothèque statique. En faisant le choix entre les différentes méthodes de résolution du problème 'adresse directe avec décalage constant', vous devriez considérer l'utilisation typique dans le monde réel :

Original :

--foo.h
extern int arr[];
--foo.c
#include "foo.h"
void main(int argc, char **argv){
  printf("%d\n",arr[1]);
}

Solution 1 :

--foo.h
extern int arr[];
--foo.c
#include "foo.h"
void main(int argc, char **argv){
  /* Ce contournement est pour win32 et cygwin; ne pas "optimiser" */
  volatile int *parr = arr;
  printf("%d\n",parr[1]);
}

Solution 2 :

--foo.h
/* Note : auto-export est supposé (pas de __declspec(dllexport)) */
#if (defined(_WIN32) || defined(__CYGWIN__)) && \
  !(defined(FOO_BUILD_DLL) || defined(FOO_STATIC))
#define FOO_IMPORT __declspec(dllimport)
#else
#define FOO_IMPORT
#endif
extern FOO_IMPORT int arr[];
--foo.c
#include "foo.h"
void main(int argc, char **argv){
  printf("%d\n",arr[1]);
}

Une quatrième façon d'éviter ce problème est de recoder votre bibliothèque pour utiliser une interface fonctionnelle plutôt qu'une interface de données pour les variables fautives (par exemple, les fonctions d'accès set_foo() et get_foo()).

--disable-auto-import
N'essaie pas d'effectuer une liaison sophistiquée de "_symbol" à "__imp__symbol" pour les importations de données depuis des DLL. [Cette option est spécifique au port cible i386 PE de l'éditeur de liens]
--enable-runtime-pseudo-reloc

[Cette option est spécifique au port cible i386 PE de l'éditeur de liens]
--disable-runtime-pseudo-reloc

--section-alignment
Définit l'alignement des sections. Les sections en mémoire commenceront toujours à des adresses qui sont un multiple de ce nombre. La valeur par défaut est 0x1000. [Cette option est spécifique au port cible i386 PE de l'éditeur de liens]
--stack réserve
--stack réserve,valide
Spécifie le nombre d'octets de mémoire à réserver (et éventuellement valider) pour être utilisés comme pile pour ce programme. La valeur par défaut est 2 Mo réservés, 4 Ko validés. [Cette option est spécifique au port cible i386 PE de l'éditeur de liens]
--subsystem quel
--subsystem quel:majeur
--subsystem quel:majeur.mineur

[Cette option est spécifique au port cible i386 PE de l'éditeur de liens]

--high-entropy-va
--disable-high-entropy-va

--dynamicbase
--disable-dynamicbase
L'adresse de base de l'image peut être relocalisée en utilisant la randomisation de l'espace d'adressage (ASLR). Cette fonctionnalité a été introduite avec MS Windows Vista pour les cibles PE i386. --forceinteg

--nxcompat

--no-isolation

Bien que l'image comprenne l'isolation, n'isole pas l'image. Cette option est désactivée par défaut.
--no-seh

--no-bind

Ne lie pas cette image. Cette option est désactivée par défaut.
--wdmdriver

--tsaware

L'image est consciente du serveur Terminal. Cette option est désactivée par défaut.
--insert-timestamp
--no-insert-timestamp
Insère un horodatage réel dans l'image. C'est le comportement par défaut car il correspond au code hérité et signifie que l'image fonctionnera avec d'autres outils propriétaires. Le problème avec cette valeur par défaut est qu'elle produira des images légèrement différentes à chaque fois que les mêmes sources sont liées. L'option --no-insert-timestamp peut être utilisée pour insérer une valeur nulle pour l'horodatage, garantissant ainsi que les binaires produits à partir de sources identiques se compareront de manière identique.

Si --insert-timestamp est actif, le temps inséré est soit le temps où la liaison s'effectue, soit, si la variable d'environnement "SOURCE_DATE_EPOCH" est définie, le nombre de secondes depuis l'époque Unix tel que spécifié par cette variable.

--enable-reloc-section
--disable-reloc-section
Crée la table de relocation de base, nécessaire si l'image est chargée à une base d'image différente de celle spécifiée dans l'en-tête PE. Cette option est activée par défaut.

La cible uClinux C6X utilise un format binaire appelé DSBT pour prendre en charge les bibliothèques partagées. Chaque bibliothèque partagée du système doit avoir un index unique ; tous les exécutables utilisent un index de 0.

--dsbt-size taille
Cette option définit le nombre d'entrées dans le DSBT de l'exécutable ou de la bibliothèque partagée actuelle à taille. La valeur par défaut consiste à créer une table de 64 entrées.
--dsbt-index index
Cette option définit l'index DSBT de l'exécutable ou de la bibliothèque partagée actuelle à index. La valeur par défaut est 0, ce qui convient à la génération d'exécutables. Si une bibliothèque partagée est générée avec un index DSBT de 0, les relocations "R_C6000_DSBT_INDEX" sont copiées dans le fichier de sortie.

Le commutateur --no-merge-exidx-entries désactive la fusion des entrées exidx adjacentes dans les informations de déroulement de pile.

--branch-stub
Cette option active la relaxation de branchement du lieur en insérant des sections de souche de branchement lorsque cela est nécessaire pour étendre la portée des branchements. Cette option n'est généralement pas requise car C-SKY prend en charge les instructions de branchement et d'appel qui peuvent accéder à toute la plage mémoire et la relaxation de branchement est normalement gérée par le compilateur ou l'assembleur.
--stub-group-size=N
Cette option permet un contrôle plus fin de la création de souches de branchement par le lieur. Elle définit la taille maximale d'un groupe de sections d'entrée qui peuvent être gérées par une seule section de souche. Une valeur négative de N place les sections de souche après leurs branchements, tandis qu'une valeur positive permet aux sections de souche d'apparaître avant ou après les branchements. Les valeurs 1 ou -1 indiquent que le lieur doit choisir les valeurs par défaut appropriées.

Les lieurs 68HC11 et 68HC12 prennent en charge des options spécifiques pour contrôler le mappage de commutation de banque mémoire et la génération de code de trampoline.

--no-trampoline
Cette option désactive la génération de trampoline. Par défaut, un trampoline est généré pour chaque fonction distante appelée à l'aide d'une instruction "jsr" (cela se produit lorsqu'un pointeur vers une fonction distante est pris).
--bank-window nom
Cette option indique au lieur le nom de la région mémoire dans la spécification MEMORY qui décrit la fenêtre de banque mémoire. La définition d'une telle région est ensuite utilisée par le lieur pour calculer la pagination et les adresses dans la fenêtre mémoire.

Les options suivantes sont prises en charge pour contrôler la génération du GOT lors de la liaison pour les cibles 68K.

--got=type
Cette option indique au lieur quel schéma de génération GOT utiliser. type doit être l'un des mots suivants : single, negative, multigot ou target. Pour plus d'informations, consultez l'entrée Info de ld.

Les options suivantes sont prises en charge pour contrôler la génération d'instructions microMIPS et les vérifications de relocation de branchement pour les transitions de mode ISA lors de la liaison pour les cibles MIPS.

--insn32
--no-insn32
Ces options contrôlent le choix des instructions microMIPS utilisées dans le code généré par le lieur, comme dans le PLT ou les souches de liaison paresseuse, ou dans la relaxation. Si --insn32 est utilisé, alors le lieur n'utilise que des encodages d'instructions de 32 bits. Par défaut ou si --no-insn32 est utilisé, tous les encodages d'instructions sont utilisés, y compris ceux de 16 bits si possible.
--ignore-branch-isa
--no-ignore-branch-isa
Ces options contrôlent les vérifications de relocation de branchement pour les transitions de mode ISA invalides. Si --ignore-branch-isa est utilisé, alors le lieur accepte toutes les relocations de branchement et toute transition de mode ISA requise est perdue dans le calcul de relocation, sauf dans certains cas d'instructions "BAL" qui satisfont aux conditions de relaxation et sont converties en instructions "JALX" équivalentes lorsque la relocation associée est calculée. Par défaut ou si --no-ignore-branch-isa est utilisé, une vérification est effectuée, provoquant la perte d'une transition de mode ISA pour produire une erreur.
--compact-branches
--no-compact-branches
Ces options contrôlent la génération d'instructions compactes par le lieur dans les entrées PLT pour MIPS R6.

Pour la cible pdp11-aout, trois variantes du format de sortie peuvent être produites comme sélectionnées par les options suivantes. La variante par défaut pour pdp11-aout est l'option --omagic, tandis que pour d'autres cibles --nmagic est la valeur par défaut. L'option --imagic n'est définie que pour la cible pdp11-aout, tandis que les autres sont décrites ici car elles s'appliquent à la cible pdp11-aout.

-N
--omagic
Marque la sortie comme "OMAGIC" (0407) dans l'en-tête a.out pour indiquer que le segment de texte ne doit pas être protégé en écriture et partagé. Comme les segments de texte et de données sont à la fois lisibles et inscriptibles, le segment de données est alloué immédiatement en continu après le segment de texte. C'est le format le plus ancien pour les programmes exécutables PDP11 et c'est la valeur par défaut pour ld sur les systèmes Unix PDP11 depuis le début jusqu'à 2.11BSD.
-n
--nmagic
Marque la sortie comme "NMAGIC" (0410) dans l'en-tête a.out pour indiquer que lorsque le fichier de sortie est exécuté, la portion de texte sera en lecture seule et partageable entre tous les processus exécutant le même fichier. Cela implique de déplacer les zones de données jusqu'à la première limite de page de 8 Ko possible suivant la fin du texte. Cette option crée un format exécutable pur.
-z
--imagic
Marque la sortie comme "IMAGIC" (0411) dans l'en-tête a.out pour indiquer que lorsque le fichier de sortie est exécuté, les zones de texte et de données du programme seront chargées dans des espaces d'adressage séparés en utilisant la fonctionnalité d'instruction et d'espace de données séparés de l'unité de gestion de la mémoire dans les modèles plus grands du PDP11. Cela double l'espace d'adressage disponible pour le programme. Le segment de texte est à nouveau pur, protégé en écriture et partageable. La seule différence dans le format de sortie entre cette option et les autres, outre le nombre magique, est que les segments de texte et de données commencent tous deux à l'emplacement 0. L'option -z sélectionnait ce format dans 2.11BSD. Cette option crée un format exécutable séparé.
--no-omagic
Équivalent à --nmagic pour pdp11-aout.

ENVIRONNEMENT

Vous pouvez modifier le comportement de ld avec les variables d'environnement "GNUTARGET", "LDEMULATION" et "COLLECT_NO_DEMANGLE".

"GNUTARGET" détermine le format d'objet du fichier d'entrée si vous n'utilisez pas -b (ou son synonyme --format). Sa valeur doit être l'un des noms BFD pour un format d'entrée. S'il n'y a pas de "GNUTARGET" dans l'environnement, ld utilise le format naturel de la cible. Si "GNUTARGET" est défini sur "default", alors BFD tente de découvrir le format d'entrée en examinant les fichiers d'entrée binaires ; cette méthode réussit souvent, mais il existe des ambiguïtés potentielles, car il n'existe aucun moyen de garantir que le nombre magique utilisé pour spécifier les formats de fichiers objet est unique. Cependant, la procédure de configuration de BFD sur chaque système place le format conventionnel pour ce système en premier dans la liste de recherche, de sorte que les ambiguïtés sont résolues en faveur de la convention.

"LDEMULATION" détermine l'émulation par défaut si vous n'utilisez pas l'option -m. L'émulation peut affecter divers aspects du comportement du lieur, en particulier le script de lieur par défaut. Vous pouvez lister les émulations disponibles avec les options --verbose ou -V. Si l'option -m n'est pas utilisée et que la variable d'environnement "LDEMULATION" n'est pas définie, l'émulation par défaut dépend de la manière dont le lieur a été configuré.

Normalement, le lieur ne démangle pas les symboles par défaut. Cependant, si "COLLECT_NO_DEMANGLE" est défini dans l'environnement, alors il ne démangle pas les symboles par défaut. Cette variable d'environnement est utilisée dans

de la même manière par le programme d'enchaînement « gcc ». La valeur par défaut peut être remplacée par les options --demangle et --no-demangle.

Si l'option --insert-timestamp spécifique à PE/COFF est active et que la variable d'environnement SOURCE_DATE_EPOCH est définie, alors la valeur d'horodatage de cette variable sera insérée dans l'en-tête COFF au lieu de l'heure actuelle.

Si la variable d'environnement « LD_STATS » est définie, alors les informations d'utilisation des ressources de l'éditeur de liens seront enregistrées, comme si l'option --stats avait été utilisée. Si la variable « LD_STATS » a une valeur de chaîne de caractères, celle-ci sera utilisée comme nom d'un fichier dans lequel les informations devront être stockées. Sinon, les informations seront envoyées au flux de sortie standard.
