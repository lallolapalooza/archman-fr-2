X11VNC(1) Commandes utilisateur X11VNC(1)

NOM

x11vnc - permettre des connexions VNC à de vrais affichages X11
version : 0.9.17, dernière modification : 2025-04-11

SYNTAXE

x11vnc [OPTION]...

DESCRIPTION

Utilisation typique :

Exécutez cette commande dans un shell sur la machine distante « far-host » avec la session X que vous souhaitez visualiser :
x11vnc -display :0
Ensuite, exécutez ceci dans une autre fenêtre sur la machine où vous êtes assis :
vncviewer far-host:0

Une fois que x11vnc établit des connexions avec le serveur X11 et commence à écouter en tant que serveur VNC, il imprimera une chaîne : PORT=XXXX où XXXX est typiquement 5900 (le port par défaut du serveur VNC). L'utilisateur exécuterait ensuite quelque chose comme ceci sur la machine locale : « vncviewer hostname:N » où « hostname » est le nom de la machine exécutant x11vnc et N est XXXX - 5900, c'est-à-dire généralement « vncviewer hostname:0 ».

Par défaut, x11vnc n'autorise pas le partage de l'écran et se termine dès que le client se déconnecte. Voir -shared et -forever ci-dessous pour outrepasser ces protections. Voir la FAQ pour des détails sur la façon de tunneliser la connexion VNC via un canal crypté tel que ssh(1). En bref :

ssh -t -L 5900:localhost:5900 far-host 'x11vnc -localhost -display :0'

% vncviewer -encodings 'copyrect tight zrle hextile' localhost:0

De plus, l'utilisation d'un mot de passe VNC (-rfbauth ou -passwdfile) est fortement recommandée.

Pour plus d'informations, voir : http://www.karlrunge.com/x11vnc/ et http://www.karlrunge.com/x11vnc/faq.html

Prise en charge des fichiers de configuration : si le fichier $HOME/.x11vncrc existe, alors chaque ligne qu'il contient est traitée comme une seule option de ligne de commande. Désactivé avec -norc. Pour chaque nom d'option, le caractère « - » en tête n'est pas requis. Par exemple, une ligne comme « forever » ou « -forever » peut être utilisée et sont des lignes équivalentes. De même « wait 100 » ou « -wait 100 » sont des lignes acceptables et équivalentes. Le caractère « # » commente jusqu'à la fin de la ligne comme d'habitude (échappez-le pour un caractère littéral). Les espaces blancs en début et fin de ligne sont supprimés. Les lignes peuvent être continuées avec un « \ » comme dernier caractère d'une ligne (il devient un espace).

OPTIONS

-display disp

Serveur X à connecter, généralement :0. Le processus serveur X doit être exécuté sur la même machine et supporter MIT-SHM. Équivalent à la définition de la variable d'environnement DISPLAY à disp.
Voir la description ci-dessous des extensions « -display WAIT:... », où l'alias « -find » trouvera automatiquement l'affichage de l'utilisateur, et « -create » créera une session Xvfb si aucune session n'est trouvée.

-auth file

Définit le fichier d'authentification X à file, équivalent à définir la variable d'environnement XAUTHORITY à file avant le démarrage. Identique à -xauth file. Voir les pages de manuel Xsecurity(7) , xauth(1) pour plus d'informations.
Utilisez « -auth guess » pour que x11vnc utilise son mécanisme -findauth (décrit ci-dessous) pour essayer de deviner le nom de fichier XAUTHORITY et l'utiliser.
XDM/GDM/KDM : si vous exécutez x11vnc en tant que root et que vous souhaitez trouver XAUTHORITY avant qu'une personne ne se connecte à une session X, utilisez : x11vnc -env FD_XDM=1 -auth guess ... (Cela trouvera aussi XAUTHORITY si un utilisateur est déjà connecté à la session X.) Lors de l'exécution en tant que root, FD_XDM=1 sera essayé si la première tentative de -auth guess échoue.

-N

Si l'affichage X est :N, essayez de définir l'affichage VNC pour qu'il soit aussi :N. Cela définit simplement l'option -rfbport à 5900+N. Le programme se terminera immédiatement si ce port n'est pas disponible. L'option -N ne fonctionne qu'avec l'utilisation normale de -display, par exemple :0 ou :8. -N est ignoré dans les modes -display WAIT:..., -create, -find, -svc, -redirect, etc.

-autoport n

Sonde automatiquement un port VNC libre à partir de n. Par défaut, la sonde commence à 5900. Utilisez ceci pour éviter les autres serveurs VNC proches de 5900.

-rfbport str

Le port VNC sur lequel écouter (une option LibVNCServer), par exemple 5900, 5901, etc. S'il est spécifié comme « -rfbport PROMPT », l'interface graphique -gui de x11vnc est utilisée pour demander à l'utilisateur de saisir le numéro de port.

-6

Prise en charge de l'écoute IPv6. En plus de l'IPv4, l'adresse IPv6 est écoutée pour les connexions entrantes. Le même numéro de port que pour l'IPv4 est utilisé.
NOTE : ce binaire x11vnc a été compilé pour avoir le mode d'écoute IPv6 « -6 » ACTIVÉ par défaut (CPPFLAGS -DX11VNC_LISTEN6=1). Donc, pour désactiver le mode d'écoute IPv6, vous DEVEZ fournir l'option « -no6 » (voir ci-dessous).
Le mode « -6 » fonctionne pour les connexions normales et celles cryptées avec -ssl. Presque tout est pris en charge pour le cas IPv6, mais il y a quelques exceptions. Voir -stunnel pour sa prise en charge IPv6.
Actuellement, pour que tout fonctionne correctement, la machine peut avoir besoin d'un certain support IPv4, au moins pour l'interface de bouclage. Cependant, pour presque tous les modes d'utilisation, aucun support IPv4 n'est requis. Voir -noipv4.
Si vous rencontrez des problèmes de compilation ou d'exécution en mode IPv6, définissez -DX11VNC_IPV6=0 dans CPPFLAGS lors de la configuration pour désactiver la prise en charge IPv6.

-no6

Désactive la prise en charge de l'écoute IPv6 (uniquement utile si le mode « -6 » est compilé par défaut ; voir la description X11VNC_LISTEN6 ci-dessus sous « -6 ».)

-noipv6

N'essaie pas d'utiliser IPv6 pour les sockets d'écoute ou de connexion. Cela inclut les ports de service d'écoute et les connexions sortantes de -connect, -connect_or_exit, ou -proxy. Utilisez ceci si vous rencontrez des problèmes dus à IPv6.

-noipv4

N'essaie pas d'utiliser IPv4 pour les sockets d'écoute ou de connexion. Ceci est principalement destiné à explorer le comportement de x11vnc sur un système uniquement IPv6, mais peut avoir d'autres utilisations.

-reopen

Si la connexion au serveur X est déconnectée, essayez de rouvrir l'affichage X (jusqu'à une fois). Ceci est utile pour les gestionnaires d'affichage comme GDM (option KillInitClients) qui tuent x11vnc juste après la connexion de l'utilisateur à la session X. Note : l'état rouvert peut être instable. Définissez X11VNC_REOPEN_DISPLAY=n pour rouvrir n fois et définissez X11VNC_REOPEN_SLEEP_MAX au nombre de secondes, par défaut 10, pour continuer à essayer de rouvrir l'affichage (une fois par seconde).
Mise à jour : à partir de la version 0.9.9, x11vnc essaie d'éviter automatiquement d'être tué par le gestionnaire d'affichage en retardant la création de fenêtres ou en utilisant XFIXES. Vous ne devriez donc pas avoir besoin d'utiliser KillInitClients=false tant que vous vous connectez assez rapidement (dans les 45 secondes après la connexion). Vous pouvez désactiver cela en définissant X11VNC_AVOID_WINDOWS=never. Vous pouvez également le définir au nombre de secondes de délai.

-reflect host:N

Au lieu de se connecter et d'interroger un affichage X, connectez-vous au serveur VNC distant host:N et agissez comme un réflecteur/répéteur pour celui-ci. Ceci est utile pour gérer le cas de nombreux spectateurs VNC simultanés (par exemple, diffusion en classe) où, par exemple, vous placez un répéteur sur chaque commutateur réseau, etc., pour améliorer les performances en distribuant la charge et le trafic réseau. Implique -shared (utilisez -noshared comme option ultérieure pour désactiver). Voir la discussion ci-dessous sous -rawfb vnc:host:N pour plus de détails.

-id windowid

Affiche la fenêtre X correspondant à windowid et non l'intégralité de l'affichage. Les nouvelles fenêtres comme les menus contextuels, les fenêtres supérieures transitoires, etc., peuvent ne pas être vues ou peuvent être coupées. Désactiver SaveUnders ou BackingStore dans le serveur X peut aider à les montrer. x11vnc peut planter si la fenêtre est initialement partiellement obstruée, change de taille.

, est iconisé, etc. Certaines étapes sont prises pour éviter cela et le mécanisme -xrandr est utilisé pour suivre les redimensionnements. Utilisez xwininfo(1) pour obtenir l'ID de la fenêtre, ou utilisez "-id pick" pour que x11vnc exécute xwininfo(1) pour vous et extrait l'ID. L'option -id est utile pour exporter des applications très simples (par exemple, la vue actuelle sur une webcam).

-sid windowid

Comme -id, mais au lieu d'utiliser la fenêtre directement, elle décale une vue racine vers celle-ci : cela affiche les menus SaveUnders, etc., bien qu'ils soient coupés s'ils dépassent la fenêtre.

-appshare

Partage d'application simple basé sur le mécanisme -id/-sid. Chaque nouvelle fenêtre de premier niveau créée par l'application induit une nouvelle fenêtre spectatrice via une connexion inverse. Les options -id/-sid et -connect sont requises. Exécutez 'x11vnc -appshare -help' pour plus d'informations.

-clip WxH+X+Y

N'affiche que la sous-région de l'affichage complet qui correspond à la géométrie du rectangle avec la taille WxH et le décalage +X+Y. L'affichage VNC a une taille WxH (c'est-à-dire plus petite que l'affichage complet). Cela fonctionne également pour le mode -id/-sid où le décalage est relatif au coin supérieur gauche de la fenêtre sélectionnée. Un exemple d'utilisation de cette option serait de diviser un grand affichage (par exemple, Xinerama) en deux parties à accéder via des spectateurs distincts en exécutant un x11vnc séparé sur chaque partie.
Utilisez '-clip xinerama0' pour découper le premier sous-écran xinerama (si xinerama est actif). xinerama1 pour le 2ème sous-écran, etc. De cette façon, vous n'avez pas besoin de déterminer le WxH+X+Y du sous-écran xinerama souhaité. Les écrans sont triés par distance croissante par rapport à l'origine (0,0) (c'est-à-dire pas dans l'ordre du Xserver).

-flashcmap

En couleur indexée 8bpp, laissez la palette de couleurs installée clignoter lorsque le pointeur se déplace d'une fenêtre à l'autre (lent). Essayez également l'option -8to24 pour éviter complètement le clignotement.

-shiftcmap n

Problème rare, mais certains affichages 8bpp utilisent moins de 256 cellules de couleur (par exemple, 16 couleurs en niveaux de gris, peut-être que les autres bits sont utilisés pour le double buffering) *et* nécessitent également de décaler les valeurs de pixels loin de 0, .., ncells. n indique le décalage à appliquer aux valeurs de pixels. Pour voir les valeurs de pixels, définissez DEBUG_CMAP=1 pour imprimer un histogramme de la palette de couleurs. Exemple : -shiftcmap 240

-notruecolor

Pour les affichages 8bpp, forcer la couleur indexée (c'est-à-dire une palette de couleurs) même si cela ressemble à de la TrueColor 8bpp (problème rare).

-advertise_truecolor

Si l'affichage X11 est en couleur indexée, mentez aux clients lorsqu'ils se connectent pour la première fois en leur disant qu'il s'agit de TrueColor. Pour contourner RealVNC : inPF a une colourMap mais pas 8bpp. Utilisez '-advertise_truecolor reset' pour réinitialiser également le fb du client.

-visual n

Cette option ne fait probablement pas ce que vous pensez. Elle *force* simplement le visuel utilisé pour le framebuffer ; cela peut être une mauvaise chose... (par exemple, perturber les couleurs ou provoquer un crash). Elle est utile pour les tests et pour certains contournements. n peut être un nombre décimal, ou 0x hexadécimal. Exécutez xdpyinfo(1) pour les valeurs. On peut également utiliser "TrueColor", etc. voir <X11/X.h> pour une liste. Si la chaîne se termine par ":m", alors pour le meilleur ou pour le pire, la profondeur du visuel est forcée à m. Vous voudrez peut-être utiliser -noshm lors de l'utilisation de cette option (afin que XGetImage puisse automatiquement traduire les données de pixels).

-overlay

Gère plusieurs visuels de profondeur sur un seul écran, par exemple les visuels superposés 8+24 et 24+8 (les 32 bits par pixel sont empilés avec 8 pour PseudoColor et 24 pour TrueColor).
Actuellement, -overlay ne fonctionne que sur Solaris via XReadScreen(3X11) et IRIX en utilisant XReadDisplay(3). Sur Solaris, il y a un problème de "fuite" d'image autour des menus contextuels transitoires (mais pas pour le menu lui-même) : un contournement consiste à désactiver SaveUnders en passant l'argument "-su" à Xsun (dans /etc/dt/config/Xservers).
Utilisez -overlay comme solution de contournement pour des situations comme celles-ci : Certaines applications héritées nécessitent que le visuel par défaut soit 8bpp (8+24), sinon elles utiliseront la PseudoColor 8bpp même lorsque le visuel par défaut est TrueColor de profondeur 24 (24+8). Dans ces cas, les couleurs de certaines fenêtres seront incorrectes dans x11vnc, sauf si -overlay est utilisé. Une autre utilisation de -overlay est de permettre l'affichage de la forme exacte du curseur de la souris (détails ci-dessous).
Sous -overlay, les performances seront un peu plus lentes en raison des transformations d'image supplémentaires requises. Pour des performances optimales, n'utilisez pas -overlay, mais configurez plutôt le serveur X de manière à ce que le visuel par défaut soit TrueColor de profondeur 24 et essayez d'avoir toutes les applications utilisant ce visuel (par exemple, certaines applications ont des options -use24 ou -visual).

-overlay_nocursor

Définit -overlay, mais n'essaie pas de dessiner la forme exacte du curseur de la souris en utilisant le mécanisme de superposition.

-8to24 [opts]

Essayez cette option si -overlay n'est pas pris en charge sur votre système d'exploitation, et que vous avez une application héritée 8bpp que vous souhaitez afficher sur un écran multi-profondeurs avec une profondeur par défaut de 24 (et qui est 32 bpp) OU que vous avez un écran par défaut de 8 avec des fenêtres superposées de profondeur 24 pour certaines applications. Cette option peut ne pas fonctionner sur tous les serveurs X et tout le matériel (testé sur le pilote XFree86/Xorg mga et Xsun). Les "opts" ne sont pas requis et sont décrits ci-dessous.
Ce mode active un hack où x11vnc surveille les fenêtres à moins de 3 niveaux de la fenêtre racine. S'il en trouve qui sont 8bpp, il extrait les valeurs de pixels en couleur indexée à l'aide de XGetImage() puis applique une transformation à l'aide de la (des) palette(s) de couleurs pour créer des valeurs RVB TrueColor qu'il insère ensuite dans les bits 1 à 24 du framebuffer. Cela crée une "vue" de profondeur 24 de l'affichage qui est ensuite exportée via VNC.
Inversement, pour les affichages par défaut en profondeur 8, les régions de profondeur 24 sont lues par XGetImage() et tout est transformé et inséré dans un framebuffer TrueColor de profondeur 24.
Notez que même s'il n'y a *aucun* visuel ou fenêtre de profondeur 24 (c'est-à-dire 8bpp pur), ce mode est potentiellement une amélioration par rapport à -flashcmap car il évite le clignotement et affiche chaque fenêtre avec la bonne couleur.
Cette méthode fonctionne bien, mais peut encore contenir des bugs et elle consomme des ressources. S'il y a plusieurs fenêtres 8bpp utilisant différentes palettes de couleurs, il faudra peut-être en icôner toutes sauf une pour que les couleurs soient correctes.
Il peut y avoir des erreurs de peinture lors du découpage et du passage entre des fenêtres de profondeurs 8 et 24. Des heuristiques sont appliquées pour essayer de minimiser les erreurs de peinture. On peut également appuyer 3 fois sur Alt_L pour rafraîchir l'écran si l'erreur ne se répare pas d'elle-même. L'option -fixscreen 8=3.0 ou -fixscreen V=3.0 peut également être utilisée pour rafraîchir périodiquement l'écran au détriment de la bande passante (toutes les 3 secondes pour cet exemple).
La chaîne [opts] peut contenir les paramètres suivants. Plusieurs paramètres sont séparés par des virgules.
Pour certains serveurs X avec une profondeur par défaut de 24, une accélération peut être obtenue via l'option "nogetimage". Cela active un schéma où XGetImage() n'est pas utilisé pour récupérer les données 8bpp. Au lieu de cela, il suppose que les données 8bpp se trouvent dans les bits 25-32 des pixels X 32 bits. Il n'est pas obligatoire que le serveur X place les données là pour nos requêtes de sondage, mais certains le font et donc les étapes supplémentaires pour les récupérer peuvent être ignorées. Testé avec le pilote mga avec XFree86/Xorg. Pour le cas de la profondeur 8 par défaut, cette option est ignorée.
Pour ajuster la fréquence à laquelle XGetImage() est utilisé pour sonder les régions de visuel non par défaut pour les changements, utilisez l'option "poll=t" où "t" est un temps à virgule flottante. (par défaut : 0.05)
Définir l'option "level2" limitera la recherche de fenêtres de visuel non par défaut à deux niveaux à partir de la fenêtre racine. Faites cela sur des machines lentes où vous savez que le gestionnaire de fenêtres n'impose qu'une seule fenêtre supplémentaire entre la fenêtre de l'application et la fenêtre racine.
Aussi pour les machines très lentes, utilisez "cachewin=t" où t est un temps à virgule flottante pour mettre en cache les résultats de XGetWindowAttributes. Par exemple, cachewin=5.0. Cela peut entraîner le fait que les fenêtres ne soient pas remarquées pendant ce laps de temps lors de la désicônisation, des erreurs de peinture, etc.
Lors des tests sur un très vieux SS20, ces options ont donné une réponse tolérable : -8to24 poll=0.2,cachewin=5.0. Pour cette machine, -overlay est pris en charge et donne une meilleure réponse.
Le débogage pour ce mode peut être activé en définissant "dbg=1", "dbg=2", ou "dbg=3".

-24to32

Problème très rare : si le framebuffer (affichage X ou -rawfb) est en 24bpp au lieu des 32bpp habituels, transformez dynamiquement les pixels en 32bpp. Ce sera plus lent, mais peut être utilisé pour contourner les problèmes où les spectateurs VNC ne peuvent pas gérer les 24bpp (par exemple, "main: setPF: pas 8, 16 ou 32 bpp ?"). Voir la FAQ pour plus d'informations.
Dans le cas de -rawfb, les pixels sont directement modifiés en insérant un octet 0 pour les compléter à 32bpp. Pour les affichages X, un bidule est fait qui équivaut à "-noshm -visual TrueColor:32". (Si de meilleures performances sont nécessaires pour ce dernier, n'hésitez pas à demander).

-scale fraction

Redimensionne le framebuffer par le facteur fraction. Les valeurs inférieures à 1 réduisent le fb, les plus grandes l'agrandissent. Note : l'image peut ne pas être nette et la réponse peut être plus lente. Si fraction contient un point décimal '.', il est traité comme un nombre à virgule flottante, alternativement la notation "m/n" peut être utilisée pour désigner des fractions exactement, par exemple, -scale 2/3
Pour redimensionner de manière asymétrique dans les directions horizontale et verticale, spécifiez une géométrie WxH à étirer : par exemple, '-scale 1024x768', ou aussi '-scale 0.9x0.75'
Options de redimensionnement : peuvent être ajoutées après fraction via ":", pour fournir plusieurs options ":", utilisez des virgules. Si vous voulez juste un redimensionnement rapide et approximatif sans mélange, ajoutez ":nb" à fraction (par exemple, -scale 1/3:nb). Le mélange est désactivé par défaut pour la couleur indexée 8bpp, pour forcer le mélange dans ce cas utilisez ":fb".
Pour désactiver -scrollcopyrect et -wirecopyrect sous -scale utilisez ":nocr
". Si vous avez besoin de les activer, utilisez ":cr" ou spécifiez-les explicitement sur la ligne de commande. Si un lien lent est détecté, ":nocr" peut être appliqué automatiquement. Défaut : :cr
Options plus ésotériques : pour la compatibilité avec les visionneuses vnc, la largeur mise à l'échelle est ajustée pour être un multiple de 4 : pour désactiver cela, utilisez ":n4". ":in" utilise le schéma d'interpolation même lors de la réduction, ":pad" ajoute un rembourrage à la largeur et à la hauteur mises à l'échelle pour qu'elles soient des multiples du dénominateur de mise à l'échelle (par exemple, 3 pour 2/3).

-geometry LxH

Identique à -scale LxH

-scale_cursor frac

Par défaut, si -scale est fourni, la forme du curseur est mise à l'échelle par le même facteur. Selon votre utilisation, vous voudrez peut-être mettre à l'échelle le curseur indépendamment de l'écran ou pas du tout. Si vous spécifiez -scale_cursor, le curseur sera mis à l'échelle par ce facteur. Lors de l'utilisation du mode -scale pour conserver au curseur sa taille "naturelle", utilisez "-scale_cursor 1". La plupart des options de mise à l'échelle ":" s'appliquent également ici.

-viewonly

Tous les clients VNC ne peuvent que regarder (désactivé par défaut).

-shared

L'affichage VNC est partagé, c'est-à-dire que plus d'un spectateur peut se connecter en même temps (désactivé par défaut).

-once

Sortir après la déconnexion du premier spectateur connecté avec succès, l'opposé de -forever. C'est la valeur par défaut.

-forever

Continuer à écouter les connexions supplémentaires plutôt que de quitter dès que le premier client (ou les premiers clients) se déconnecte. Identique à -many
Pour obtenir le comportement VNC standard non partagé où, lorsqu'un nouveau client VNC se connecte, le client VNC existant est déconnecté, utilisez : -nevershared -forever Cette méthode peut également être utilisée pour se protéger contre les connexions TCP bloquées qui ne disparaissent pas.

-loop

Crée une boucle externe redémarrant le processus x11vnc chaque fois qu'il se termine. -bg et -inetd sont ignorés dans ce mode (cependant, voir -loopbg ci-dessous).
Utile pour continuer même si le serveur X se termine et redémarre (à ce moment-là, le processus aura besoin de la permission de se reconnecter au nouveau serveur X, bien sûr).
Utilisez, par exemple, -loop100 pour attendre 100 millisecondes entre les redémarrages, etc. La valeur par défaut est 2000 ms (c'est-à-dire 2 secondes). Utilisez, par exemple, -loop300,5 pour attendre 300 ms et boucler seulement 5 fois.
Si -loopbg (plus d'éventuels nombres) est spécifié à la place, l'option "-bg" est implicite et le mode s'apparente à inetd(8) dans une certaine mesure. Dans ce cas, lorsqu'il passe en arrière-plan, tous les sockets d'écoute (c'est-à-dire les ports 5900, 5800) sont fermés, de sorte que le suivant dans la boucle puisse les utiliser. Ce mode ne sera utile que si un client VNC (le seul client pour ce processus) est déjà connecté avant que le processus ne passe en arrière-plan, par exemple, l'utilisation de -display WAIT:.., -svc, et -connect peut utiliser ce mode "pauvre" de inetd. Le temps d'attente par défaut est de 500 ms dans ce mode. Cette utilisation pourrait être utile : -svc -bg -loopbg

-timeout n

Quitte sauf si un client se connecte dans les n premières secondes après le démarrage.
S'il n'y a eu aucune tentative de connexion après n secondes, x11vnc se ferme immédiatement. Si un client essaie de se connecter mais n'a pas atteint l'état de fonctionnement normal, x11vnc lui accorde quelques secondes supplémentaires pour terminer et se ferme s'il n'atteint pas l'état normal.
Pour les connexions inverses via -connect ou -connect_or_exit, un délai de n secondes sera défini pour toutes les connexions inverses. Si l'alarme de délai de connexion se déclenche, x11vnc se ferme immédiatement.

-sleepin n

Au démarrage, attendez n secondes avant de continuer (par exemple, pour permettre aux redirections et aux clients en écoute de démarrer)
Si une plage est donnée : '-sleepin min-max', une valeur aléatoire entre min et max est attendue. Par exemple : '-sleepin 0-20' et '-sleepin 10-30'. Les nombres décimaux sont également autorisés.

-inetd

Lancé par inetd(8) : stdio au lieu d'un socket d'écoute. Note : si vous ne redirigez pas stderr vers un fichier journal (via shell 2> ou l'option -o ) vous DEVEZ également spécifier l'option -q, sinon stderr ira vers le spectateur ce qui provoquera son abandon. Spécifier à la fois -inetd et -q et aucun -o fermera automatiquement stderr.

-tightfilexfer

Active l'extension de transfert de fichiers TightVNC. Notez que lorsque l'option -viewonly est fournie, tous les transferts de fichiers sont désactivés. Les clients qui se connectent en mode viewonly ne peuvent pas non plus transférer de fichiers. Cependant, si le mécanisme de contrôle à distance est utilisé pour modifier l'état viewonly global ou par client, les permissions de transfert de fichiers NE changeront PAS.
IMPORTANT : veuillez comprendre que si -tightfilexfer est spécifié et que vous exécutez x11vnc en tant que root pour, par exemple, un accès inetd ou gestionnaire d'affichage (gdm, kdm, ...) et que vous ne lui demandez pas de changer d'utilisateur via l'option -users, alors les spectateurs VNC qui se connectent peuvent effectuer des lectures et écritures de fichiers en tant que *root*.
De plus, tightfilexfer est désactivé en mode -unixpw.

-ultrafilexfer

Note : pour activer le transfert de fichiers UltraVNC et pour qu'il fonctionne, vous devrez probablement fournir ces options LibVNCServer : "-rfbversion 3.6 -permitfiletransfer" "-ultrafilexfer" est un alias pour cette combinaison.
IMPORTANT : veuillez comprendre que si -ultrafilexfer est spécifié et que vous exécutez x11vnc en tant que root pour, par exemple, un accès inetd ou gestionnaire d'affichage (gdm, kdm, ...) et que vous ne lui demandez pas de changer d'utilisateur via l'option -users, alors les spectateurs VNC qui se connectent peuvent effectuer des lectures et écritures de fichiers en tant que *root*.
Notez qu'il n'est malheureusement pas possible d'utiliser à la fois -tightfilexfer et -ultrafilexfer car ce dernier nécessite de définir la version sur 3.6 et tightvnc ne fera pas de transfert de fichiers lorsqu'il verra ce numéro de version.

-http

Sous -ssl ou -stunnel, le sous-répertoire des classes ssl est recherché.

-http_ssl

-zeroconf

Identique à -avahi.

-connect string

Pour une utilisation avec les connexions inverses "vncviewer -listen". Si string a la forme "host" ou "host:port", la connexion est effectuée une fois au démarrage.
Utilisez des virgules pour une liste d'hôtes et d'hôtes:ports. Par exemple, -connect host1,host2 ou host1:0,host2:5678. Notez que pour se connecter en inverse à plusieurs hôtes simultanément, vous devrez probablement également fournir : -shared
Notez que contrairement à la plupart des serveurs vnc, x11vnc exigera un mot de passe pour les connexions inverses ainsi que pour les connexions directes. (si l'authentification par mot de passe a été activée, -rfbauth, etc.) Si vous ne souhaitez pas exiger de mot de passe pour les connexions inverses, définissez X11VNC_REVERSE_CONNECTION_NO_AUTH=1 dans votre environnement avant de démarrer x11vnc.
Si string contient "/", il est interprété comme un fichier à vérifier périodiquement pour de nouveaux hôtes. La première ligne est lue, puis le fichier est tronqué. Soyez prudent quant à l'emplacement de ce fichier si x11vnc s'exécute en tant que root (par exemple, via gdm(1) , etc.).
Mode répéteur : certains services fournissent un "répéteur vnc" intermédiaire : http://www.uvnc.com/addons/repeater.html (et aussi http://koti.mbnet.fi/jtko/ pour le port Linux) qui agit comme un proxy/passerelle. Les modes de ce type nécessitent l'envoi d'une chaîne initiale pour la connexion inverse avant le démarrage du protocole VNC. Voici les façons de faire :
-connect pre=chaîne_quelconque+host:port -connect pre128=chaîne_quelconque+host:port -connect repeater=ID:1234+host:port -connect repeater=23.45.67.89::5501+host:port
La notation SSVNC est également prise en charge :
-connect repeater://host:port+ID:1234
Comme pour l'utilisation normale de -connect, si le port du répéteur n'est pas fourni, 5500 est supposé.
L'idée de base est qu'entre la balise spéciale, par exemple "pre=" et "+", se trouve la chaîne préfixe à envoyer. Notez que dans ce cas, host:port est le serveur répéteur, ET NON le spectateur vnc. D'une manière ou d'une autre, la chaîne préfixe indique au serveur répéteur comment trouver le spectateur vnc et vous y connecter.
Dans le cas pre=chaîne_quelconque+host:port, "chaîne_quelconque" est simplement envoyée. Dans le cas preNNN=chaîne_quelconque+host:port, "chaîne_quelconque" est envoyée dans un tampon complété par des zéros d'une longueur NNN. repeater= est identique à pre250=, c'est la taille du tampon du répéteur ultravnc.
Les chaînes comme "\n" et "\r", etc. sont développées en nouvelle ligne et retour chariot. "\c" est développé en "," puisque la connexion
Bien sûr, voici le contenu traduit en français, en conservant la structure du fichier : t string est séparé par des virgules.
Voir aussi l'option -proxy ci-dessous pour des moyens supplémentaires de gérer les connexions inversées.
SSL inversé : utiliser -connect en mode -ssl fait que x11vnc agit comme un client SSL (initie la connexion SSL) plutôt qu'un serveur SSL. L'idée est que x11vnc pourrait se connecter à stunnel côté spectateur avec le spectateur en mode écoute. Si vous ne souhaitez pas ce comportement, utilisez -env X11VNC_DISABLE_SSL_CLIENT_MODE=1. Avec cela, le côté spectateur peut agir comme client SSL comme il le fait normalement pour les connexions avant.
Mode répéteur SSL inversé : Cela fonctionnera, mais notez que si le client VNC effectue une action de type 'Fetch Cert' avant de se connecter, le répéteur risque de laisser tomber la connexion et les deux côtés devront redémarrer. Envisagez l'utilisation de -connect_or_exit et -loop300,2 pour que x11vnc se reconnecte une fois au répéteur après la récupération. Vous voudrez probablement également fournir -sslonly pour éviter que x11vnc ne pense que le délai de réponse signifie que la connexion est VeNCrypt. La variable d'environnement X11VNC_DISABLE_SSL_CLIENT_MODE=1 discutée ci-dessus peut également être utile (c'est-à-dire que le spectateur peut effectuer une connexion avant comme il le fait normalement.)
IPv6 : à partir de x11vnc 0.9.10, l'option -connect devrait se connecter correctement aux hôtes IPv6. S'il y a des problèmes, vous pouvez désactiver IPv6 en définissant -DX11VNC_IPV6=0 dans CPPFLAGS lors de la configuration. S'il y a des problèmes de connexion aux hôtes IPv6, envisagez un relais comme le script inet6to4 inclus ou l'option -proxy.

-connect_or_exit str

Comme avec -connect, sauf si aucune des connexions inversées ne réussit, x11vnc s'arrête immédiatement.
Un alias plus facile à taper pour cette option est '-coe'
Soit dit en passant, si vous ne voulez pas que x11vnc écoute sur aucune interface, utilisez -rfbport 0, ce qui est pratique pour le mode -connect_or_exit.

-proxy string

Utilisez le proxy dans la chaîne (par exemple, hôte:port) comme proxy pour établir des connexions inversées (options -connect ou -connect_or_exit).
Les proxys web sont pris en charge, mais notez qu'en général, la plupart d'entre eux ne prennent en charge que les connexions de destination vers les ports 443 ou 563, donc cela pourrait ne pas être très utile (le spectateur devrait écouter sur ce port ou le routeur devrait effectuer une redirection de port).
Un proxy web peut être spécifié par "hôte:port" ou par "http://hôte:port" (le port est requis même s'il s'agit des choix courants 80 ou 8080).
SOCKS4, SOCKS4a et SOCKS5 sont également pris en charge. Les proxys SOCKS n'ont généralement pas de restrictions sur le numéro de port de destination.
Utilisez un format comme celui-ci : socks://hôte:port ou socks5://hôte:port. Notez que ssh -D ne prend pas en charge SOCKS4a, utilisez donc socks5://. Pour socks://, SOCKS4 est utilisé sur un IP numérique et "localhost", sinon SOCKS4a est utilisé (et donc le proxy essaie d'effectuer la recherche DNS).
Un mode expérimental est "-proxy http://hôte:port/..." Notez le "/" après le port qui le distingue d'un proxy web normal. Le port doit être fourni même s'il s'agit du port par défaut 80. Pour ce mode, un GET est effectué vers l'URL fournie avec la chaîne host=H&port=P ajoutée. H et P seront l'hôte et le port de connexion inversée de -connect. Utilisez la chaîne "__END__" pour désactiver l'ajout. L'idée de base est qu'un script cgi peut fournir le crochet de spectateur et le tunneling réels. La manière d'y parvenir concrètement dans cgi, php, etc. n'est pas claire... Un serveur web personnalisé ou un module apache serait simple.
Un autre mode expérimental est "-proxy ssh://utilisateur@hôte" auquel cas un tunnel SSH est utilisé pour le proxy. "utilisateur@" n'est pas nécessaire sauf si votre nom d'utilisateur unix est différent sur "hôte". Pour un port SSH non standard, utilisez ssh://utilisateur@hôte:port. Si les proxys sont chaînés (voir le paragraphe suivant), le proxy SSH doit être le premier. Si ssh-agent n'est pas actif, le mot de passe ssh doit être saisi dans le terminal où x11vnc est exécuté. Exemples :
-connect localhost:0 -proxy ssh://moi@amis-pc:2222
-connect snoopy:0 -proxy ssh://ssh.company.com
Plusieurs proxys peuvent être chaînés ensemble au cas où il faudrait faire ricochet sur un certain nombre d'hôtes pour atteindre finalement le spectateur VNC. Jusqu'à 3 peuvent être chaînés, séparez-les par des virgules dans l'ordre où ils doivent être connectés. Par exemple : http://hôte1:port1,socks5://hôte2:port2 ou trois comme : premier,deuxième,troisième
IPv6 : à partir de x11vnc 0.9.10, l'option -proxy devrait se connecter correctement aux hôtes IPv6. S'il y a des problèmes, vous pouvez désactiver IPv6 en définissant -DX11VNC_IPV6=0 dans CPPFLAGS lors de la configuration. S'il y a des problèmes de connexion aux hôtes IPv6, envisagez un relais comme le script inet6to4 inclus.

-vncconnect, -novncconnect

Surveiller la propriété X VNC_CONNECT définie par le programme VNC standard vncconnect(1). Lorsque la propriété est définie sur "hôte" ou "hôte:port", établir une connexion inversée. L'utilisation de xprop(1) au lieu de vncconnect peut fonctionner (voir la FAQ). Le mécanisme de contrôle -remote utilise le canal X11VNC_REMOTE, et cette option le désactive/active également. Par défaut : -vncconnect
Pour utiliser des noms différents pour ces propriétés X11 (par exemple, pour avoir des canaux de communication séparés pour plusieurs x11vnc sur le même affichage), définissez les variables d'environnement VNC_CONNECT ou X11VNC_REMOTE sur la chaîne souhaitée, par exemple : -env X11VNC_REMOTE=X11VNC_REMOTE_12345 Les deux côtés du canal doivent utiliser le même nom unique. Il en va de même pour la propriété interne X11VNC_TICKER (heartbeat et horodatage) si désiré.

-allow hôte1[,hôte2..]

Autoriser uniquement les connexions client provenant des hôtes correspondant à la liste séparée par des virgules de noms d'hôtes ou d'adresses IP. Peut également être un préfixe d'adresse IP numérique, par exemple, "192.168.100." pour correspondre à un sous-réseau simple. Pour un contrôle plus poussé, compilez LibVNCServer avec le support de libwrap (voir la FAQ). Si la liste contient un "/", elle est interprétée comme un fichier contenant des adresses ou des préfixes qui est relu chaque fois qu'un nouveau client se connecte. Les lignes peuvent être commentées avec le caractère "#" comme d'habitude.
-allow s'applique en mode -ssl, mais pas en mode -stunnel.
IPv6 : à partir de x11vnc 0.9.10, un hôte peut être spécifié au format numérique IPv6, par exemple, 2001:4860:b009::93.

-localhost

Essentiellement la même chose que "-allow 127.0.0.1".
Note : si vous souhaitez restreindre l'interface réseau sur laquelle x11vnc écoute, voir l'option -listen ci-dessous. Par exemple, "-listen localhost" ou "-listen 192.168.3.21". En tant que cas spécial, l'option "-localhost" implique "-listen localhost".
Un cas rare, mais pour une utilisation de -listen autre que localhost, si vous utilisez le mécanisme de contrôle à distance (-R) pour changer l'interface de -listen, vous devrez peut-être ajuster manuellement la liste -allow (et vice versa) pour éviter les situations où aucune connexion (ou trop de connexions) n'est autorisée.
Si vous ne voulez pas que x11vnc écoute sur aucune interface (manifestement, vous utilisez -connect ou -connect_or_exit, ou prévoyez d'utiliser le contrôle à distance : -R connect:hôte), utilisez -rfbport 0.
IPv6 : si IPv6 est pris en charge, cette option implique automatiquement l'adresse de bouclage IPv6 '::1' également.

-unixsock str

Écouter sur le socket Unix (AF_UNIX) 'str' pour les connexions. Ce mode est destiné aux connexions locales ou à un point d'extrémité de tunnel où l'on souhaite que la permission de fichier du socket Unix détermine ce qui peut s'y connecter. (Cela nécessite actuellement une modification de libvnserver/rfbserver.c : commentez les lignes 310 et 311, 'close(sock)' et 'return NULL' dans rfbserver.c après l'appel setsockopt().) Notez que pour désactiver tous les ports d'écoute tcp, spécifiez '-rfbport 0' et cela devrait être utile avec ce mode. Exemple : mkdir ~/s; chmod 700 ~/s; x11vnc -unixsock ~/s/mysock -rfbport 0 ... Le spectateur Unix SSVNC peut se connecter à des sockets Unix.

-listen6 str

En mode écoute IPv6 "-6", écouter uniquement sur l'interface réseau avec l'adresse str. Cela fonctionne également pour les adresses de portée de lien (fe80::219:dbff:fee5:3f92%eth0) et les chaînes de noms d'hôtes IPv6 (par exemple, ipv6.google.com.). Utilisez l'option -listen de LibVNCServer pour l'interface IPv4.

-nolookup

Ne pas utiliser gethostbyname() ou gethostbyaddr() pour rechercher les noms d'hôtes ou les numéros IP. Utilisez cette option si la résolution de noms est mal configurée et entraîne de longues pauses car les recherches de noms expirent, etc.

-input string

Ajustement fin de l'entrée utilisateur autorisée. Si string ne contient pas de virgule ",", le réglage ne s'applique qu'aux clients normaux. Sinon, la partie avant la virgule est pour les clients normaux et la partie après pour les clients en lecture seule. "K" est pour l'entrée clavier, "M" pour l'entrée de mouvement de souris, "B" pour l'entrée de clic de bouton, "C" pour l'entrée de presse-papiers et "F" pour le transfert de fichiers (ultravnc uniquement). Leur présence dans la chaîne active ce type d'entrée. Par exemple, "-input M" signifie que les utilisateurs normaux ne peuvent que déplacer la souris et "-input KMBCF,M" permet aux utilisateurs normaux de faire n'importe quoi et permet aux utilisateurs en lecture seule de déplacer la souris. Cette option est ignorée lorsqu'un -viewonly global est actif (toute entrée est alors ignorée).

-grabkbd

Lorsque des spectateurs VNC sont connectés, tenter de capturer le clavier afin qu'un utilisateur (non malveillant) assis devant l'écran physique ne puisse pas entrer de frappes. Cette méthode utilise XGrabKeyboard(3X11) et n'est donc pas sécurisée et n'empêche pas la personne à l'écran d'injecter des frappes en submergeant le serveur, en capturant le clavier lui-même, etc. Un certain degré de coopération de la personne à l'écran est supposé. Ceci est destiné aux modes d'aide à distance ou d'éducation. modes.
Note : sur certains serveurs X (12/2010) et/ou bureaux récents, -grabkbd ne fonctionne plus : il empêche le gestionnaire de fenêtres de redimensionner les fenêtres et autres actions similaires. Essayez -ungrabboth
ci-dessous (peut ne pas fonctionner.)

-grabptr

Comme -grabkbd, mais pour le pointeur de la souris en utilisant XGrabPointer(3X11). Malheureusement, en raison du fonctionnement du serveur X, la souris peut toujours être déplacée par l'utilisateur sur l'écran physique, mais il ne pourra pas changer le focus des fenêtres avec. De plus, certains gestionnaires de fenêtres qui appellent XGrabServer(3X11) pour les redimensionnements, etc., agiront sur les entrées de l'utilisateur local. Encore une fois, un certain degré de coopération de la part de la personne devant l'écran est supposé.

-ungrabboth

Chaque fois qu'il y a une entrée (clavier ou pointeur), désattrape *à la fois* le clavier et le pointeur tout en injectant l'entrée synthétique. Ceci afin de donner une chance aux gestionnaires de fenêtres, etc. de s'attraper.

-grabalways

Applique à la fois -grabkbd et -grabptr même lorsqu'aucun spectateur VNC n'est connecté. Si vous n'en voulez qu'un, utilisez la télécommande -R pour réactiver l'autre, par exemple -R nograbptr.

-viewpasswd chaîne

Fournit un 2ème mot de passe pour les connexions en lecture seule. Le mot de passe -passwd (accès complet) doit également être fourni.

-passwdfile nom_fichier

Spécifie le mot de passe LibVNCServer via la première ligne du fichier nom_fichier (au lieu de via -passwd sur la ligne de commande où d'autres pourraient le voir via ps(1) ).
Voir les descriptions ci-dessous pour savoir comment fournir plusieurs mots de passe, des mots de passe en lecture seule, pour spécifier des programmes externes pour l'authentification, et d'autres fonctionnalités.
Si le nom de fichier est préfixé par "rm:", il sera supprimé après avoir été lu. Ceci est peut-être utile pour limiter la lisibilité du fichier. En général, le fichier de mots de passe ne doit pas être lisible par des utilisateurs non fiables (au fait : le fichier -rfbauth de VNC ne doit pas l'être non plus : il n'est PAS crypté, seulement obscurci avec une clé fixe).
Si le nom de fichier est préfixé par "read:", il sera périodiquement vérifié pour les changements et relu. Il est garanti d'être relu juste avant qu'un nouveau client ne se connecte, afin que les derniers mots de passe soient utilisés.
Si nom_fichier est préfixé par "cmd:", alors la chaîne après le ":" est exécutée comme une commande externe : la sortie de la commande sera interprétée comme si elle était lue à partir d'un fichier de mots de passe (voir ci-dessous). Si la commande ne se termine pas avec 0, alors x11vnc s'arrête immédiatement. Pour spécifier plus de 1000 mots de passe de cette manière, définissez X11VNC_MAX_PASSWDS avant de démarrer x11vnc. Les variables d'environnement sont définies comme dans -accept.
Notez qu'en raison du protocole VNC, seuls les 8 premiers caractères d'un mot de passe sont utilisés (clé DES).
Si nom_fichier est préfixé par "custom:", alors un vérificateur de mot de passe personnalisé est fourni comme commande externe suivant le ":". La commande sera exécutée lorsqu'un client s'authentifie. Si la commande se termine par 0, le client est accepté, sinon il est rejeté. Les variables d'environnement sont définies comme dans -accept.
L'entrée standard de la commande personnalisée sera un chiffre décimal "len" suivi d'une nouvelle ligne. "len" spécifie la taille du défi et est généralement de 16 (la spécification VNC). Suivent ensuite len octets qui est la chaîne de défi aléatoire envoyée au client. Ceci est suivi par len octets supplémentaires contenant la réponse du client (c'est-à-dire la chaîne de défi cryptée via DES avec le mot de passe utilisateur dans la situation normale).
Le schéma "custom:" peut être utile pour implémenter des mots de passe dynamiques ou pour implémenter des méthodes où des mots de passe plus longs et/ou différents algorithmes de cryptage sont utilisés. Ce dernier nécessitera également de personnaliser le client VNC. On pourrait créer un schéma basé sur MD5SUM par exemple.
Format du fichier pour -passwdfile:
Si plusieurs lignes non vides existent dans le fichier, elles sont toutes considérées comme des mots de passe valides. Les lignes vides sont ignorées. Les lignes de mots de passe peuvent être "commentées" (ignorées) si elles commencent par le caractère "#" ou si la ligne contient la chaîne "__SKIP__". Les lignes peuvent être annotées en utilisant la chaîne "__COMM__": de là à la fin de la ligne est ignoré. Un mot de passe vide peut être spécifié via la chaîne "__EMPTY__" sur une ligne seule (notez que votre spectateur pourrait ne pas accepter les mots de passe vides).
Si la chaîne "__BEGIN_VIEWONLY__" apparaît sur une ligne seule, les mots de passe restants sont utilisés pour l'accès en lecture seule. Pour la compatibilité, à titre de cas spécial si le fichier ne contient que deux lignes de mot de passe, la 2ème est automatiquement considérée comme le mot de passe en lecture seule. Sinon, le jeton "__BEGIN_VIEWONLY__" doit être utilisé pour avoir des mots de passe en lecture seule. (astuce : faites de la 3ème et dernière ligne "__BEGIN_VIEWONLY__" pour avoir 2 mots de passe en accès complet)

-showrfbauth nom_fichier

Affiche à l'écran le mot de passe VNC obscurci conservé dans le fichier rfbauth nom_fichier puis quitte.

-unixpw [liste]

Utilise l'authentification par nom d'utilisateur et mot de passe Unix. x11vnc utilisera le programme su(1) pour vérifier le mot de passe de l'utilisateur. [liste] est une liste facultative séparée par des virgules de noms d'utilisateur Unix autorisés. Si la chaîne [liste] commence par le caractère "!", alors toute la liste est considérée comme une liste d'exclusion. Voir ci-dessous pour les options par utilisateur qui peuvent être appliquées.
Une boîte de dialogue familière "login:" et "Password:" est présentée à l'utilisateur sur un écran noir dans le vncviewer. La connexion est interrompue si l'utilisateur ne parvient pas à fournir le mot de passe correct en 3 tentatives ou n'en envoie pas avant un délai d'expiration de 45 secondes. Les clients existants sont en lecture seule pendant cette période.
Si le premier caractère reçu est "Échap", alors le nom d'utilisateur Unix ne sera pas affiché après "login:" lorsqu'il est tapé. Cela pourrait être utile pour les spectateurs VNC qui tapent automatiquement le nom d'utilisateur et le mot de passe.
Comme le comportement détaillé de su(1) peut varier d'un système d'exploitation à l'autre et selon les configurations locales, testez le mode avant le déploiement pour vous assurer qu'il fonctionne correctement. x11vnc tentera d'être conservateur et de rejeter une connexion si quelque chose d'anormal se produit.
Un cas à noter : FreeBSD et les autres BSD par défaut, il est impossible pour l'utilisateur exécutant x11vnc de valider son *propre* mot de passe via su(1) (commenter l'entrée pam_self.so dans /etc/pam.d/su élimine ce comportement). Donc, la connexion x11vnc échouera *toujours* dans ce cas (même lorsque le mot de passe correct est fourni).
Une solution possible à cela sur *BSD serait de démarrer x11vnc en tant que root avec l'option "-users +nobody" pour passer immédiatement à l'utilisateur nobody où l'appel à su se déroulera normalement.
Une autre source de problèmes potentiels sont les modules PAM qui demandent des informations supplémentaires, par exemple les modules d'expiration de mot de passe. Ces connexions échoueront également même lorsque le mot de passe correct est fourni.
**IMPORTANT** : pour empêcher que le mot de passe Unix ne soit envoyé en *texte clair* sur le réseau, l'un des deux schémas sera appliqué : 1) le mode SSL intégré -ssl, ou 2) exiger que -localhost et -stunnel soient activés.
La méthode 1) garantit que le trafic est crypté entre le spectateur et le serveur. Un fichier PEM sera requis, voir la discussion sous -ssl ci-dessous (dans certaines circonstances, un fichier temporaire peut être automatiquement généré).
La méthode 2) exige que la connexion du spectateur apparaisse comme provenant de la même machine sur laquelle x11vnc est exécuté (par exemple, à partir d'une redirection de port -L de ssh(1) ). Et que le mode SSL -stunnel soit utilisé pour le cryptage sur le réseau. (voir la description de -stunnel ci-dessous).
Note : par commodité, si vous vous connectez via ssh(1) et démarrez x11vnc, il vérifiera si la variable d'environnement SSH_CONNECTION est définie et semble raisonnable. Si c'est le cas, l'exigence -ssl ou -stunnel sera abandonnée car on suppose que vous utilisez ssh pour le tunnelement crypté. -localhost est toujours appliqué. Utilisez -ssl ou -stunnel pour forcer l'utilisation de SSL même si SSH_CONNECTION est défini.
Pour outrepasser les restrictions ci-dessus, vous pouvez définir des variables d'environnement avant de démarrer x11vnc :
Définissez UNIXPW_DISABLE_SSL=1 pour désactiver l'exigence de -ssl ou -stunnel (comme sous SSH_CONNECTION.) Évidemment, vous utiliserez une méthode différente pour crypter les données entre le vncviewer et x11vnc : peut-être ssh(1) ou un VPN IPSEC. -localhost est toujours appliqué (cependant, voir le paragraphe suivant.)
Définissez UNIXPW_DISABLE_LOCALHOST=1 pour désactiver l'exigence -localhost dans les modes -unixpw. Il ne faut jamais faire cela (c'est-à-dire autoriser le reniflage des mots de passe Unix sur le réseau.) Cela désactive également l'exigence de localhost pour les connexions inversées (voir ci-dessous.)
Notez que l'utilisation de -localhost avec ssh(1) (et sans -unixpw) est à peu près la même que l'exigence d'une connexion utilisateur Unix (car un mot de passe Unix ou l'authentification par clé publique de l'utilisateur est utilisée par sshd sur la machine où x11vnc s'exécute et seules les connexions locales depuis cette machine sont acceptées).
Concernant les connexions inversées (par exemple, -R connect:hôte et -connect hôte), lorsque la contrainte -localhost est en vigueur, les connexions inversées ne peuvent être utilisées que pour se connecter à la même machine sur laquelle x11vnc s'exécute (port par défaut 5500). Veuillez utiliser une redirection de port ssh ou stunnel vers la machine spectatrice pour tunneliser la connexion inversée via un canal crypté.
En mode -inetd, la méthode 1) sera appliquée (pas la méthode 2). Avec -ssl en vigueur, les connexions inversées sont désactivées. Si vous outrepasser cela via une variable d'environnement, assurez-vous également d'utiliser le cryptage entre le spectateur et inetd. Astuce : vous pouvez également faire démarrer votre propre stunnel x11vnc en mode -inetd (ce qui contourne inetd). Voir la FAQ pour détails.
Les noms d'utilisateur dans la [liste] séparée par des virgules peuvent avoir des options par utilisateur après un ":", par exemple "fred:opts" où "opts" est une liste séparée par "+" de "viewonly", "fullaccess", "input=XXXX", ou "deny", par exemple "karl,wally:viewonly,boss:input=M". Pour "input=", ce sont les K,M,B,C décrits sous -input.
Si un élément de la liste est "*", cela signifie que ces options s'appliquent à tous les utilisateurs. Cela implique ÉGALEMENT que tous les utilisateurs sont autorisés à se connecter après avoir fourni un mot de passe valide. Utilisez "deny" pour refuser explicitement certains utilisateurs si vous utilisez "*" pour définir une option globale. Si [liste] commence par le caractère "!" alors "*" est ignoré pour vérifier si l'utilisateur est autorisé, mais les valeurs d'options qui lui sont associées s'appliquent normalement. Il existe également des utilitaires pour vérifier les mots de passe si [liste] commence par le caractère "%". Voir la fonction quick_pw() pour plus de détails. Description : "%-" ou "%stdin" signifie lire une ligne depuis stdin. "%env" signifie qu'elle se trouve dans la variable d'environnement $UNIXPW. Un "%/" ou "%." en préfixe signifie lire la première ligne du nom de fichier qui suit le caractère %. % tout seul signifie inviter l'utilisateur à entrer le nom d'utilisateur et le mot de passe. Sinon : %utilisateur:motdepasse Par exemple, -unixpw %fred:swordfish Pour les autres cas, l'utilisateur:motdepasse est lu depuis la source indiquée. Si le mot de passe est correct, 'Y utilisateur' est affiché et le code de sortie du programme est 0. S'il est incorrect, il affiche 'N utilisateur' et le code de sortie est 1. En cas d'autre erreur, le code de sortie est 2. Cette fonctionnalité permet à x11vnc d'être un outil général de vérification de mot de passe d'utilisateur unix ; il peut être utilisé à partir de scripts ou d'autres programmes. Ces vérifications de mot de passe % s'appliquent également aux options -unixpw_nis et -unixpw_cmd. Dans le cas de la vérification de mot de passe %, si la variable d'environnement UNIXPW_CMD est définie sur une commande, celle-ci est exécutée en tant qu'utilisateur (en supposant que le mot de passe est correct.) La sortie de la commande n'est pas affichée, le programme ou le script doit la gérer par un autre moyen. Le code de sortie de x11vnc dépendra du code de sortie de la commande exécutée. Utilisez -nounixpw pour désactiver le mode unixpw s'il a été activé plus tôt dans la ligne de commande (par exemple, mode -svc). -unixpw_nis [liste] Comme -unixpw ci-dessus, cependant n'utilisez pas su(1) mais plutôt la méthode traditionnelle getpwnam(3) + crypt(3) pour vérifier les mots de passe. Toutes les options et contraintes de -unixpw ci-dessus s'appliquent. Ce mode nécessite que les mots de passe chiffrés soient lisibles. Les mots de passe chiffrés stockés dans /etc/shadow seront inaccessibles à moins que x11vnc ne soit exécuté en tant que root. Ce mode est appelé "mode NIS" simplement parce que dans la plupart des configurations NIS, les mots de passe chiffrés des utilisateurs sont accessibles (par exemple, "ypcat passwd") par un utilisateur ordinaire et cet utilisateur peut authentifier N'IMPORTE QUEL utilisateur. NIS n'est pas requis pour que ce mode fonctionne (seul getpwnam(3) retournant le mot de passe chiffré est requis), mais il est peu probable qu'il fonctionne (en tant qu'utilisateur ordinaire) pour la plupart des environnements modernes à moins que NIS ne soit disponible. D'un autre côté, lorsque x11vnc est exécuté en tant que root, il pourra accéder à /etc/shadow même si NIS n'est pas disponible (notez que l'exécution en tant que root est souvent faite lors de l'exécution de x11vnc depuis inetd et xdm/gdm/kdm). Vu autrement, si vous ne souhaitez pas utiliser la méthode su(1) fournie par -unixpw (c'est-à-dire su_verify()), vous pouvez exécuter x11vnc en tant que root et utiliser -unixpw_nis. Tous les utilisateurs dont les mots de passe sont dans /etc/shadow pourront alors être authentifiés. En mode -unixpw_nis, en aucun cas la fonction de vérification de mot de passe utilisateur de x11vnc basée sur su n'est appelée (c'est-à-dire la fonction su_verify() qui exécute /bin/su dans un pseudo-terminal pour vérifier les mots de passe.) Cependant, si -unixpw_nis est utilisé conjointement avec les modes -find et -create -display WAIT:..., alors, si x11vnc est exécuté en tant que root, /bin/su peut être appelé extérieurement pour exécuter les commandes find ou create. -unixpw_cmd cmd Comme -unixpw ci-dessus, cependant n'utilisez pas su(1) mais plutôt exécutez la commande fournie extérieurement cmd. La première ligne de son stdin sera le nom d'utilisateur et la deuxième ligne le mot de passe reçu. Si la commande se termine avec le statut 0 (succès), l'utilisateur VNC sera accepté. Il sera rejeté pour tout autre statut de retour. Les mots de passe dynamiques et les mots de passe non-unix, par exemple LDAP, peuvent être implémentés de cette manière en fournissant votre propre programme d'assistance personnalisé. Notez que le spectateur distant dispose de 3 tentatives pour entrer le mot de passe correct, et donc le programme peut être appelé plusieurs fois de suite autant (ou plus) de fois. Si une liste d'utilisateurs autorisés est nécessaire pour limiter qui peut se connecter, utilisez -unixpw [liste] en plus de cette option. Dans les modes FINDDISPLAY et FINDCREATEDISPLAY, cmd sera également exécuté avec la variable d'environnement RFB_UNIXPW_CMD_RUN non vide et définie sur la commande find/create d'affichage correspondante. Les deux premières lignes d'entrée sont le nom d'utilisateur et le mot de passe comme dans le cas normal décrit ci-dessus. Pour prendre en charge FINDDISPLAY et FINDCREATEDISPLAY, cmd doit exécuter la commande demandée en tant qu'utilisateur (et très probablement refuser de l'exécuter si le mot de passe n'est pas correct.) Voici un script d'exemple (notez qu'il a un mot de passe bidon codé en dur "abc" !) #!/bin/sh # Exemple de script x11vnc -unixpw_cmd. # Lire les deux premières lignes de stdin (utilisateur et mot de passe) lire utilisateur lire motdepasse debug=0 if [ $debug = 1 ]; then echo "utilisateur: $utilisateur" 1>&2 echo "motdepasse: $motdepasse" 1>&2 env | egrep -i 'rfb|vnc' 1>&2 fi # Vérifier si le mot de passe est valide. # (Un exemple réel utiliserait une recherche ldap, etc. !) if [ "X$motdepasse" != "Xabc" ]; then exit 1 # mot de passe incorrect fi if [ "X$RFB_UNIXPW_CMD_RUN" = "X" ]; then exit 0 # mot de passe correct else # Exécuter la commande demandée (finddisplay) if [ $debug = 1 ]; then echo "exécuter: $RFB_UNIXPW_CMD_RUN" 1>&2 fi exec /bin/su - "$utilisateur" -c "$RFB_UNIXPW_CMD_RUN" fi En mode -unixpw_cmd, en aucun cas la fonction de vérification de mot de passe utilisateur de x11vnc basée sur su n'est appelée (c'est-à-dire la fonction su_verify() qui exécute /bin/su dans un pseudo-terminal pour vérifier les mots de passe.) Il appartient à unixpw_cmd fourni de faire la commutation d'utilisateur si désiré et s'il en a les permissions. -find Trouver l'affichage de l'utilisateur à l'aide de FINDDISPLAY. C'est un alias pour "-display WAIT:cmd=FINDDISPLAY". Note : si un -display apparaît plus tard dans la ligne de commande, il remplacera le réglage -find. Pour cette option et les suivantes, voir -display WAIT:... ci-dessous pour tous les détails. -finddpy Exécuter le programme FINDDISPLAY, afficher l'affichage trouvé (s'il y en a un) et quitter. La sortie est comme suit : DISPLAY=:0.0 DISPLAY=:0.0,XPID=12345 ou DISPLAY=:0.0,VT=7. XPID est l'identifiant du processus du serveur X trouvé. VT est le terminal virtuel Linux du serveur X. -listdpy Faire en sorte que le programme FINDDISPLAY liste tous vos affichages (c'est-à-dire tous les affichages X sur la machine locale auxquels vous avez des droits d'accès). x11vnc quitte ensuite. -findauth [disp] Appliquer les heuristiques -find/-finddpy pour essayer de deviner le fichier XAUTHORITY pour DISPLAY 'disp'. Si 'disp' n'est pas fourni, alors la valeur dans -display sur la ligne de commande est utilisée ; sinon $DISPLAY est utilisé ; et sinon ":0" est utilisé. x11vnc se termine ensuite. Si rien n'est affiché, cela signifie qu'aucun XAUTHORITY n'a été trouvé pour 'disp' ; c'est-à-dire un échec. Si "XAUTHORITY=" est affiché, cela signifie qu'il faut utiliser la valeur par défaut (c'est-à-dire ne pas définir XAUTHORITY). Si "XAUTHORITY=/chemin/vers/fichier" est affiché, alors utiliser ce fichier. XDM/GDM/KDM : si vous exécutez x11vnc en tant que root et que vous souhaitez trouver le XAUTHORITY avant qu'un utilisateur ne se connecte à une session X, utilisez : x11vnc -env FD_XDM=1 -findauth ... (Cela trouvera également le XAUTHORITY si un utilisateur est déjà connecté à la session X.) Lors de l'exécution en tant que root, FD_XDM=1 sera essayé si le -findauth initial échoue. -create Essayer d'abord de trouver l'affichage de l'utilisateur à l'aide de FINDDISPLAY, si cela échoue, créer une session X via la méthode FINDCREATEDISPLAY. C'est un alias pour "-display WAIT:cmd=FINDCREATEDISPLAY-Xvfb". Note : si un -display apparaît plus tard dans la ligne de commande, il remplacera le réglage -create. NOTE SSH : pour -find et -create, vous pouvez (devez !) ajouter l'option "-localhost" pour forcer le tunneling SSH. -xdummy Comme dans -create, sauf Xdummy au lieu de Xvfb. -xvnc Comme dans -create, sauf Xvnc au lieu de Xvfb. -xvnc_redirect Comme dans -create, sauf Xvnc.redirect au lieu de Xvfb. -xdummy_xvfb Définit WAIT:cmd=FINDCREATEDISPLAY-Xdummy,Xvfb -create_xsrv str Définit WAIT:cmd=FINDCREATEDISPLAY-str Peut être sur la ligne de commande après tout ce qui définit WAIT:.. et d'autres choses (par exemple, -svc, -xdmsvc) pour ajuster la liste des serveurs X. Exemple : -svc ... -create_xsrv Xdummy,X -svc Mode services terminaux basé sur l'accès SSL. Alias pour -display WAIT:cmd=FINDCREATEDISPLAY-Xvfb -unixpw -users unixpw= -ssl SAVE Également "-service". Note : si un -display, -unixpw, -users, ou -ssl apparaît plus tard dans la ligne de commande, il remplacera le réglage -svc. -svc_xdummy Comme -svc sauf Xdummy au lieu de Xvfb. -svc_xvnc Comme -svc sauf Xvnc au lieu de Xvfb. -svc_xdummy_xvfb Comme -svc avec Xdummy,Xvfb. -xdmsvc Mode services terminaux de gestionnaire d'affichage basé sur SSL. Alias pour -display WAIT:cmd=FINDCREATEDISPLAY-Xvfb.xdmcp -unixpw -users unixpw= -ssl SAVE Également "-xdm_service". Note : si un -display, -unixpw, -users, ou -ssl apparaît plus tard dans la ligne de commande, il remplacera le réglage -xdmsvc. Pour créer une session, un utilisateur devra d'abord se connecter à la boîte de dialogue -unixpw, puis se connecter à nouveau à l'invite XDM/GDM/KDM. Les reconnexions ultérieures ne feront que require le mot de passe -unixpw. Voir la discussion sous -display WAIT:... pour plus de détails sur la configuration XDM, etc.
N'oubliez pas d'activer XDMCP dans le fichier de configuration xdm-config, gdm.conf ou kdmrc. Voir -display WAIT: pour plus d'informations.

-sshxdmsvc

Mode services Terminal du gestionnaire d'affichage basé sur SSH. Alias pour -display WAIT:cmd=FINDCREATEDISPLAY-Xvfb.xdmcp -localhost.
L'option -localhost limite les connexions aux tunnels SSH (qui nécessiteront une connexion). Pour créer une session, un utilisateur devra également se connecter à l'invite XDM GDM KDM. Les reconnexions ultérieures ne nécessiteront que la connexion SSH. Voir la discussion sous -display WAIT:... pour plus de détails sur la configuration XDM, etc.
N'oubliez pas d'activer XDMCP dans le fichier de configuration xdm-config, gdm.conf ou kdmrc. Voir -display WAIT: pour plus d'informations.

-unixpw_system_greeter

Présente une option « Appuyez sur 'Échap' pour le Greeter Système » au client VNC connecté en mode combiné -unixpw et xdmcp FINDCREATEDISPLAY (par exemple, -xdmsvc).
Normalement, en mode -unixpw, le client VNC doit fournir un nom d'utilisateur et un mot de passe valides pour obtenir l'accès. Cependant, si -unixpw_system_greeter est fourni ET que la commande FINDCREATEDISPLAY correspond à 'xdmcp', alors l'utilisateur a la possibilité d'appuyer sur Échap et d'obtenir à la place un panneau de connexion/greeter XDM/GDM/KDM. Ils fourniront alors un nom d'utilisateur et un mot de passe directement au greeter.
Sinon, en mode xdmcp FINDCREATEDISPLAY, l'utilisateur doit fournir son nom d'utilisateur et son mot de passe DEUX FOIS. D'abord à la boîte de dialogue de connexion unixpw initiale, puis au greeter XDM/GDM/KDM suivant. Notez que si l'utilisateur se reconnecte et fournit son nom d'utilisateur et son mot de passe dans la boîte de dialogue unixpw, le greeter xdmcp est ignoré et il est connecté directement à sa session X existante. Ainsi, l'option -unixpw_system_greeter évite le mot de passe supplémentaire au moment de la création de la session X.
Exemple : x11vnc -xdmsvc -unixpw_system_greeter Voir -unixpw et -display WAIT:... pour plus d'informations.
Les options spéciales après un deux-points à la fin du nom d'utilisateur (par exemple, user:solid) décrites sous -display WAIT: sont également appliquées dans ce mode s'ils sont saisis avant que l'utilisateur n'appuie sur Échap. Le nom d'utilisateur est ignoré mais les options des deux-points ne le sont pas.
Le message par défaut est de 2 lignes dans une petite police, définissez la variable d'environnement X11VNC_SYSTEM_GREETER1=true pour un message d'une ligne dans une police plus grande.
Si l'utilisateur a appuyé sur Échap, la commande FINDCREATEDISPLAY sera exécutée avec la variable d'environnement X11VNC_XDM_ONLY=1.
N'oubliez pas d'activer XDMCP dans le fichier de configuration xdm-config, gdm.conf ou kdmrc. Voir -display WAIT: pour plus d'informations.

-redirect port

Comme en mode FINDCREATEDISPLAY-Xvnc.redirect, sauf qu'il redirige immédiatement (c'est-à-dire sans recherche ou création de session X) vers un serveur VNC en écoute sur le port. Vous pouvez également spécifier hôte:port pour rediriger vers une machine différente.
Si 0 <= port < 200, il est considéré comme un écran VNC (5900 est ajouté pour obtenir le port réel), si port < 0, alors -port est utilisé.
La seule raison probable d'utiliser l'option -redirect est en conjonction avec le support SSL, par exemple -ssl SAVE. Cela fournit un moyen facile d'ajouter le chiffrement SSL à un serveur VNC qui ne prend pas en charge SSL (par exemple, Xvnc ou vnc.so). En fait, le protocole n'a même pas besoin d'être VNC, et donc "-rfbport port1 -ssl SAVE -redirect hôte:port2" peut remplacer stunnel(1).
Ce mode ne permet qu'une seule connexion redirigée. L'option -forever ne s'applique pas. Utilisez -inetd ou -loop pour un service persistant.

-display WAIT:...

Un mode d'utilisation spécial pour l'option normale -display. Utile avec -unixpw, mais peut être utilisé indépendamment. Si la chaîne d'affichage commence par WAIT:, alors x11vnc attend qu'un client VNC se connecte avant d'ouvrir l'écran X (ou le périphérique -rawfb).
Cela pourrait être utile pour retarder l'ouverture de l'affichage pour certains modes d'utilisation (par exemple, si x11vnc est démarré au démarrage et qu'aucun serveur X n'est en cours d'exécution ou que les utilisateurs ne sont pas encore connectés).
Si la chaîne est, par exemple, WAIT:0.0 ou WAIT:1, c'est-à-dire "WAIT" devant un écran X normal, alors l'écran indiqué est utilisé.
On peut également insérer une géométrie entre les deux-points, par exemple WAIT:1280x1024:... pour définir la taille de l'écran auquel le client VNC se connecte initialement, car certains visualiseurs VNC ne s'adapteront pas automatiquement à une nouvelle taille de framebuffer.
Un cas plus intéressant est le suivant :
WAIT:cmd=/usr/local/bin/find_display
dans ce cas, la commande après "cmd=" est exécutée pour déterminer dynamiquement les données DISPLAY et éventuellement XAUTHORITY. La première ligne de la sortie de la commande doit être de la forme DISPLAY=<xdisplay>. Sous Linux, si le terminal virtuel est connu, ajoutez ",VT=n" à cette chaîne et le programme chvt(1) sera également exécuté. Tout sortie restante est considérée comme des données XAUTHORITY. Il peut s'agir de la forme XAUTHORITY=<fichier> ou de données xauthority brutes pour l'affichage. Par exemple ;
xauth extract - $DISPLAY"
NOTE : Comme spécifié au paragraphe précédent, vous pouvez fournir votre propre programme ou script WAIT:cmd=..., MAIS il existe deux programmes *INTÉGRÉS* très utiles : FINDDISPLAY (alias -find ci-dessus) et FINDCREATEDISPLAY (alias -create ci-dessus.) La plupart des gens les utilisent au lieu de créer leur propre script. Lisez ce qui suit (en particulier les sections sur les modes INTÉGRÉS) pour savoir comment configurer ces deux modes utiles de -display WAIT:
Dans le cas de -unixpw (et -unixpw_nis uniquement si x11vnc est exécuté en tant que root), la commande cmd= sera exécutée en tant qu'utilisateur qui vient de s'authentifier via le nom d'utilisateur et le mot de passe.
Dans le cas de -unixpw_cmd, les commandes seront également exécutées en tant qu'utilisateur connecté, à condition que le programme d'assistance fourni par l'utilisateur prenne en charge RFB_UNIXPW_CMD_RUN (voir l'option -unixpw_cmd.)
Également dans le cas de -unixpw, l'utilisateur qui se connecte peut placer un deux-points à la fin de son nom d'utilisateur et fournir quelques options : scale=, scale_cursor= (ou sc=), solid (ou so), id=, clear_mods (ou cm), clear_keys (ou ck), clear_all (ou ca), repeat, speeds= (ou sp=), readtimeout= (ou rd=), viewonly (ou vo), nodisplay= (ou nd=), rotate= (ou ro=), ou noncache (ou nc), tous séparés par des virgules s'il y en a plus d'un. Après que l'utilisateur se soit connecté avec succès, ces options seront appliquées à l'écran VNC. Par exemple,
login: fred:scale=3/4,sc=1,repeat Mot de passe : ...
login: runge:sp=modem,rd=120,solid
pour plus de commodité, m/n implique scale= par exemple fred:3/4 Si vous tapez et entrez votre mot de passe incorrectement, pour récupérer votre longue ligne "login:", appuyez une fois sur la flèche vers le haut (avant de taper quoi que ce soit d'autre).
La plupart de ces options de deux-points ne s'appliquent qu'aux modes intégrés FINDDISPLAY et FINDCREATEDISPLAY, mais notez qu'elles sont également transmises à la commande externe dans l'environnement et pourraient donc être utilisées.
Dans le panneau de connexion, appuyez sur F1 pour obtenir une liste des options disponibles que vous pouvez ajouter après le nom d'utilisateur.
Une autre option est "geom=WxH" ou "geom=WxHxD" (ou ge=). Cela n'a d'effet qu'en mode FINDCREATEDISPLAY lorsqu'un serveur X virtuel tel que Xvfb va être créé. Il définit la largeur et la hauteur du nouvel écran, et éventuellement la profondeur de couleur.
Vous pouvez également spécifier "gnome", "kde", "twm", "fvwm", "mwm", "dtwm", "wmaker", "xfce", "lxde", "enlightenment", "Xsession", ou "failsafe" (identique à "xterm") pour que l'écran créé utilise ce mode pour la session utilisateur.
Spécifiez "tag=..." pour définir le tag de session de bureau unique FD_TAG décrit ci-dessous. Remarque : cette option sera ignorée si la variable d'environnement FD_TAG est déjà définie ou si la valeur fournie par le spectateur n'est pas entièrement composée de caractères alphanumériques, '_' ou '-'.
Fichier de préférences utilisateur : Au lieu que l'utilisateur tape geom=WxH,... etc. à chaque connexion pour trouver ou créer sa session X, si vous définissez FD_USERPREFS à une chaîne qui ne contient pas le caractère "/", alors le répertoire personnel de l'utilisateur est préfixé à cette chaîne et si le fichier existe, sa première ligne est lue et ajoutée à toutes les options qu'il a fournies à l'invite de connexion. Par exemple -env FD_USERPREFS=.x11vnc_create et l'utilisateur a mis "geom=1600x1200" dans son fichier ~/.x11vnc_create.
Pour désactiver l'option, définissez la variable d'environnement X11VNC_NO_UNIXPW_OPTS=1 avant de démarrer x11vnc. Pour définir d'autres options, l'utilisateur peut utiliser l'interface graphique (x11vnc -gui connect) ou la méthode de contrôle à distance (x11vnc -R opt:val) pendant sa session VNC.
Ainsi, la combinaison de -display WAIT:cmd=... et -unixpw permet l'association automatique d'un utilisateur VNC authentifié par Unix avec son bureau. Cela pourrait être très utile sur les SunRays et aussi sur tout système où plusieurs utilisateurs partagent une machine donnée. L'utilisateur n'a pas besoin de se souvenir des ports ou des mots de passe spéciaux configurés pour son bureau et VNC.
Une bonne façon d'utiliser WAIT:cmd=... est à partir de inetd(8) (il lance automatiquement un nouveau x11vnc pour chaque utilisateur). Vous pouvez faire en sorte que le processus x11vnc lancé par inetd s'exécute en tant que root ou nobody, par exemple. Lorsqu'il est exécuté en tant que root (pour inetd ou le gestionnaire d'affichage), vous pouvez également fournir l'option "-users unixpw=" pour que le processus x11vnc bascule également vers l'utilisateur. Remarque : il y aura un 2ème processus d'assistance SSL qui ne basculera pas, mais il ne fait qu'encoder et décoder le flux chiffré à ce point.
Modes intégrés :
-- Recherche automatique des sessions X utilisateur --
À titre spécial, WAIT:cmd=FINDDISPLAY exécutera un script qui fonctionne sur la plupart des Unix pour déterminer la variable DISPLAY d'un utilisateur et les données xauthority (voir who(1) ).
NOTE : L'option "-find" est un alias pour ce mode.
Pour que ce script par défaut soit imprimé sur stdout (par exemple, pour la personnalisation), exécutez avec WAIT:cmd=FINDDISPLAY-print Pour exécuter le script afin d'imprimer ce qu'il trouverait, utilisez "-finddpy" ou WAIT:cmd=FINDDISPLAY-run
Le script standard exécute xdpyinfo(1) exécuté sur des affichages potentiels. Si vos serveurs X ont un écran de connexion qui capture exclusivement le serveur X, alors xdpyinfo se bloque indéfiniment et ce mode ne fonctionnera pas. Voir www.karlrunge.com/x11vnc/faq.html#faq-display-manager pour désactiver cela pour dtgreet sur Solaris et potentiellement pour d'autres écrans de connexion.
En mode -find/cmd=FINDDISPLAY, si vous définissez FD_XDM=1, par exemple 'x11vnc -env FD_XDM=1 -find ...' et que x11vnc s'exécute en tant que root (par exemple inetd) alors il essaiera de trouver le fichier XAUTHORITY d'un écran de connexion XDM/GDM/KDM en cours d'exécution (c'est-à-dire qu'aucun utilisateur ne s'est encore connecté à une session X).
Comme autre cas spécial, WAIT:cmd=HTTPONCE permettra à x11vnc de traiter une requête http et de se terminer. Ceci est généralement fait en mode -inetd pour s'exécuter, par exemple, sur le port 5800 et permettre au vncviewer Java d'être téléchargé par les navigateurs web des clients. Par exemple :
5815 stream tcp nowait root /usr/sbin/tcpd /.../x11vnc \ -inetd -q -http_ssl -prog /.../x11vnc \ -display WAIT:cmd=HTTPONCE
Où /.../x11vnc est le chemin complet vers x11vnc. Il est utilisé dans l'exemple de portail SSL Apache (voir FAQ).
Dans ce mode, vous pouvez définir X11VNC_SKIP_DISPLAY à une liste d'affichages séparés par des virgules (par exemple, ":0,:1") à ignorer lors du processus de recherche. Le ":" est facultatif. Les plages n-m, par exemple 0-20, peuvent également être fournies. Cette chaîne peut également être définie par l'utilisateur connectant via "nd=" en utilisant "+" au lieu de ",". Si "nd=all" ou si vous définissez X11VNC_SKIP_DISPLAY=all, alors toute la recherche d'affichage échouera comme si vous aviez défini X11VNC_FINDDISPLAY_ALWAYS_FAILS=1 (ci-dessous).
Sur certains systèmes lsof(1) peut être très lent. Définissez la variable d'environnement FIND_DISPLAY_NO_LSOF=1 pour éviter d'utiliser lsof pour trouver le VT Linux sur lequel le serveur X s'exécute. Définissez FIND_DISPLAY_NO_VT_FIND=1 pour éviter de tout rechercher.
-- Création automatique de sessions X utilisateur --
Une option intéressante est WAIT:cmd=FINDCREATEDISPLAY, qui est similaire à FINDDISPLAY en ce qu'elle utilise la même méthode pour trouver un affichage existant. Cependant, si elle n'en trouve pas, elle essaiera de démarrer une session serveur X pour l'utilisateur. C'est la seule fois où x11vnc essaie réellement de démarrer un serveur X.
NOTE : L'option "-create" est un alias pour ce mode.
Elle commencera à chercher un numéro d'affichage ouvert à partir de :20. Remplacer via X11VNC_CREATE_STARTING_DISPLAY_NUMBER=n. Par défaut, 80 affichages X sont autorisés (c'est-à-dire jusqu'à :99). Remplacer via X11VNC_CREATE_MAX_DISPLAYS=n.
Pour ses heuristiques, le script de création d'affichage définit LC_ALL=C afin que la sortie de la commande soit uniforme. Par défaut, il essaiera de restaurer LC_ALL juste avant de démarrer la session utilisateur. Cependant, si cela ne vous dérange pas qu'il conserve LC_ALL=C, définissez la variable d'environnement : X11VNC_CREATE_LC_ALL_C_OK=1
Par défaut, FINDCREATEDISPLAY essaiera Xvfb puis Xdummy :
Le wrapper Xdummy fait partie du code source de x11vnc (x11vnc/misc/Xdummy). Il devrait être disponible dans PATH et avoir exécuté "Xdummy -install" une fois pour créer la bibliothèque partagée. Xdummy ne fonctionne que sous Linux. Depuis 12/2009, il n'est plus nécessaire de l'exécuter en tant que root, et la valeur par défaut est de ne pas l'exécuter en tant que root. Dans certaines circonstances, les autorisations peuvent requérir de l'exécuter en tant que root, dans ces cas, spécifiez FD_XDUMMY_RUN_AS_ROOT=1, ce qui équivaut à fournir -root à la ligne de commande Xdummy.
Xvfb est disponible sur la plupart des plateformes et ne nécessite pas de root.
Un avantage de Xdummy sur Xvfb est que Xdummy prend en charge le redimensionnement dynamique de l'écran RANDR.
Lorsque x11vnc se termine (c'est-à-dire que l'utilisateur se déconnecte), la session du serveur X reste active en arrière-plan. FINDDISPLAY la trouvera directement la prochaine fois. L'utilisateur doit terminer la session X de la manière habituelle pour qu'elle se termine (ou tuer le processus du serveur X si tout le reste échoue).
Pour dépanner le mécanisme FINDCREATEDISPLAY, définissez la variable d'environnement suivante vers un fichier journal de sortie, par exemple -env CREATE_DISPLAY_OUTPUT=/tmp/mydebug.txt
C'est donc un mode assez inhabituel pour x11vnc, car il démarrera et interrogera des serveurs X virtuels ! Cela peut être utilisé depuis, par exemple, inetd(8) pour fournir un moyen d'obtenir certainement un bureau (réel ou virtuel) sur la machine. Par exemple, un service de bureau :
5900 stream tcp nowait root /usr/sbin/tcpd /.../x11vnc -inetd -q -http -ssl SAVE -unixpw -users unixpw=\ -passwd secret -prog /.../x11vnc \ -display WAIT:cmd=FINDCREATEDISPLAY
Où /.../x11vnc est le chemin complet vers x11vnc.
Voir l'alias des options courtes -svc/-service ci-dessus.
Si, pour une raison quelconque, vous ne souhaitez pas que x11vnc essaie jamais de trouver un affichage existant, définissez la variable d'environnement X11VNC_FINDDISPLAY_ALWAYS_FAILS=1 (également -env ...) Ceci équivaut à définir X11VNC_SKIP_DISPLAY=all ou à fournir "nd=all" après "username:".
Utilisez WAIT:cmd=FINDCREATEDISPLAY-print pour afficher le script utilisé pour cela.
Vous pouvez spécifier l'ordre des serveurs X préférés, par exemple, WAIT:cmd=FINDCREATEDISPLAY-Xdummy,Xvfb,X et/ou omettre ceux que vous ne souhaitez pas. Le cas "X" signifie essayer de démarrer un serveur X réel, matériel, en utilisant xinit(1) ou startx(1). S'il y a déjà un serveur X en cours d'exécution, le cas X peut ne fonctionner que sous Linux (voir startx(1)).
"Xvnc" démarrera un serveur X VNC (real- ou tight-vnc, par exemple à utiliser si Xvfb n'est pas disponible). "Xsrv" démarrera le programme serveur dans la variable "FD_XSRV" s'il n'est pas vide. Vous pouvez en faire un script wrapper si vous le souhaitez (il doit gérer :N, -geometry, et -depth et d'autres options de serveur X).
Vous pouvez définir la variable d'environnement FD_GEOM (ou X11VNC_CREATE_GEOM) à WxH ou WxHxD pour définir la largeur, la hauteur et éventuellement la profondeur de couleur de l'affichage créé. Vous pouvez également définir FD_SESS pour qu'il soit la session (nom court du gestionnaire de fenêtres : kde, gnome, twm, failsafe, etc.). FD_OPTS contient des options supplémentaires à passer au serveur X. Vous pouvez également définir FD_PROG pour qu'il soit le chemin complet du programme de session/gestionnaire de fenêtres.
Plus d'astuces FD : FD_CUPS=port ou FD_CUPS=host:port définira l'environnement d'impression cups. De même pour FD_ESD=port ou FD_ESD=host:port pour la redirection sonore esddsp. Définissez FD_EXTRA à une commande à exécuter quelques secondes après le démarrage du serveur X. Définissez FD_TAG pour qu'il soit un nom unique pour la session, il est défini comme une propriété X, ce qui fait que FINDDISPLAY ne trouve que les sessions avec cette valeur de tag.
Définissez FD_XDMCP_IF sur l'interface réseau sur laquelle le gestionnaire d'affichage s'exécute ; par défaut, c'est 'localhost', mais vous devrez peut-être le définir sur '::1' sur certains systèmes IPv6 uniquement ou sur des gestionnaires d'affichage mal configurés.
Si vous souhaitez que la session FINDCREATEDISPLAY contacte un gestionnaire de connexion XDMCP (xdm/gdm/kdm) sur la même machine, utilisez alors "Xvfb.xdmcp" au lieu de "Xvfb", etc. L'utilisateur devra fournir à nouveau son nom d'utilisateur et son mot de passe (mais il pourra sélectionner son type de bureau, ce qui peut être utile). Pour que cela fonctionne, vous devrez activer XDMCP localhost (port udp 177) pour le gestionnaire d'affichage. Cela semble être :
pour gdm dans gdm.conf : Enable=true dans la section [xdmcp] pour kdm dans kdmrc : Enable=true dans la section [Xdmcp] pour xdm dans xdm-config : DisplayManager.requestPort: 177
Voir les options courtes ci-dessus "-svc", "-xdmsvc" et "-sshxdmsvc" qui spécifient les options ci-dessus pour certains cas utiles.
Si vous définissez la variable d'environnement WAITBG=1, x11vnc passera en arrière-plan une fois qu'il aura commencé à écouter en mode attente.
Un autre mode spécial est FINDCREATEDISPLAY-Xvnc.redirect, (ou FINDDISPLAY-Xvnc.redirect). Dans ce cas, il démarrera Xvnc si nécessaire, mais au lieu de l'interroger de manière normale, il effectue simplement une redirection de socket du spectateur VNC connecté vers Xvnc.
Ainsi, en Xvnc.redirect, x11vnc ne fait pas de VNC mais transfère simplement les données dans les deux sens. Cela devrait être plus rapide que la méthode d'interrogation de x11vnc, mais pas aussi rapide que de se connecter directement à Xvnc avec le spectateur VNC. L'idée ici est de tirer parti du schéma de recherche/création d'affichage de x11vnc, du SSL, et peut-être de quelques autres. La plupart des options de x11vnc ne s'appliquent pas dans ce mode.
Xvnc.redirect devrait également fonctionner pour le module serveur X vnc.so pour l'affichage matériel, mais il ne fonctionnera que pour trouver l'affichage et l'utilisateur doit déjà être connecté à la console X.

-vencrypt mode

L'extension VeNCrypt du protocole VNC permet les connexions SSL/TLS chiffrées. Si le mode -ssl est activé, alors VeNCrypt est également activé PAR DÉFAUT (ils utilisent tous les deux un tunnel SSL/TLS, seule la poignée de main du protocole est légèrement différente).
Pour contrôler quand et comment VeNCrypt est utilisé, spécifiez la chaîne de mode. Si le mode est "never", alors VeNCrypt n'est pas utilisé. Si le mode est "support" (par défaut), alors VeNCrypt est pris en charge. Si le mode est "only", alors le protocole ANONTLS similaire et plus ancien n'est pas simultanément pris en charge. Le mode SSL normal de x11vnc (vncs://) sera pris en charge sous -ssl sauf si vous définissez le mode sur "force".
Si le mode est préfixé par "nodh:", alors l'échange de clés anonyme Diffie Hellman est désactivé. Si le mode est préfixé par "nox509:", alors l'échange de clés X509 est désactivé.
Pour désactiver tout accès Anonymous Diffie-Hellman (susceptible à une attaque Man-In-The-Middle), vous devrez fournir "-vencrypt nodh:support -anontls never" ou "-vencrypt nodh:only".
Si le mode est préfixé par "newdh:", alors de nouveaux paramètres Diffie Hellman sont générés pour chaque connexion (cela peut prendre du temps : 1 à 60 secondes ; voir -dhparams ci-dessous pour une méthode plus rapide) au lieu d'utiliser les valeurs fixes du programme. L'utilisation de valeurs fixes et publiquement connues n'est pas connue pour être un problème de sécurité. Ce réglage s'applique également à ANONTLS.
Long exemple : -vencrypt newdh:nox509:support
De plus, si le mode est préfixé par "plain:", alors si le mode -unixpw est actif, la méthode "username+passwd" VeNCrypt "*Plain" est activée pour les connexions Unix. Sinon, en mode -unixpw, le panneau de connexion normal est fourni.
Vous DEVEZ fournir l'option -ssl pour que VeNCrypt soit actif. L'option -vencrypt ajuste uniquement son fonctionnement.

-anontls mode

L'extension ANONTLS du protocole VNC permet
ws chiffrées SSL/TLS connexions. Si le mode -ssl est activé, alors ANONTLS est activé également PAR DÉFAUT (ils utilisent tous les deux un tunnel SSL/TLS, seul le protocole de négociation est un peu différent.)
ANONTLS est un ancien mode SSL/TLS introduit par vino.
Il est désigné sous le nom de 'TLS' pour son nom de type de sécurité VNC enregistré, mais nous utilisons le terme plus descriptif 'ANONTLS' ici car il ne fournit que des connexions chiffrées Diffie-Hellman anonymes, et donc aucune possibilité d'authentification par certificat.
Pour contrôler quand et comment ANONTLS est utilisé, spécifiez la chaîne de mode. Si le mode est "never", alors ANONTLS n'est pas utilisé. Si le mode est "support" (la valeur par défaut), alors ANONTLS est supporté. Si le mode est "only", alors le protocole VeNCrypt similaire n'est pas simultanément supporté. Le mode SSL normal de x11vnc (vncs://) sera supporté sous -ssl à moins que vous ne régliez le mode sur "force".
Si le mode est préfixé par "newdh:", alors de nouveaux paramètres Diffie Hellman sont générés pour chaque connexion (cela peut prendre du temps : 1-60 secondes ; voir -dhparams ci-dessous pour une méthode plus rapide) plutôt que d'utiliser les valeurs fixes dans le programme. L'utilisation de valeurs fixes et publiquement connues n'est pas connue pour être un problème de sécurité. Ce réglage s'applique également à VeNCrypt. Voir la description de "plain:" sous -vencrypt.
Exemple long : -anontls newdh:plain:support
Vous DEVEZ fournir l'option -ssl pour que ANONTLS soit actif. L' option -anontls ne fait qu'affiner son fonctionnement.

-sslonly

Identique à : "-vencrypt never -anontls never" c'est-à-dire qu'il désactive les méthodes de chiffrement VeNCrypt et ANONTLS et autorise uniquement le tunneling SSL standard. Vous devez également fournir l'option -ssl ... (voir ci-dessous.)

-dhparams fichier

Pour certaines opérations, un ensemble de paramètres Diffie Hellman (nombre premier et générateur) est nécessaire. Si c'est le cas, utilisez les paramètres dans fichier. En particulier, le mode DH anonyme de VeNCrypt et ANONTLS en a besoin. Par défaut, un ensemble fixe est utilisé. Si vous ne souhaitez pas le faire, vous pouvez spécifier "newdh:" aux options -vencrypt et -anontls pour générer un nouvel ensemble à chaque session. Si cela est trop lent pour vous, utilisez -dhparams fichier pour un ensemble que vous avez créé manuellement via "openssl dhparam -out fichier 1024"

-nossl

Désactive l'option -ssl (voir ci-dessous). Comme -ssl est désactivé par défaut, -nossl ne serait utilisé en ligne de commande que pour désactiver toute option -ssl *précédente* (ou -svc...)

-ssl [pem]

Utilise la bibliothèque openssl (www.openssl.org) pour fournir un tunnel SSL/TLS chiffré intégré entre les visualiseurs VNC et x11vnc. Cela nécessite que le support libssl soit compilé dans x11vnc au moment de la construction. Si x11vnc n'est pas compilé avec le support libssl, il se terminera immédiatement lorsque -ssl sera prescrit. Voir l'option -stunnel ci-dessous pour une alternative.
Le côté VNC Viewer doit également supporter SSL/TLS. Voir cette URL et également la discussion ci-dessous pour des idées sur la façon d'activer le support SSL pour le visualiseur : http://www.karlrunge.com/x11vnc/faq.html#faq-ssl-tun . x11vnc fournit un applet de visualisation Java activé SSL dans le répertoire classes/ssl (options -http ou -httpdir.) Le package de visualisation SSVNC supporte également les tunnels SSL.
Si le VNC Viewer supporte VeNCrypt ou ANONTLS (le mode de chiffrement de vino), ils sont également supportés par le mode -ssl (voir les options -vencrypt et -anontls pour plus d'informations ; utilisez -sslonly pour désactiver les deux.)
Utilisez "-ssl /chemin/vers/moncert.pem" pour spécifier un fichier de certificat SSL au format PEM à utiliser pour identifier et fournir une clé pour ce serveur. Voir openssl(1) pour plus d'informations sur les PEM et les options -sslGenCert et "-ssl SAVE" ci-dessous pour savoir comment les créer.
Le tunnel SSL du VNC Viewer connecté peut (à sa discrétion) authentifier ce serveur s'il possède la partie clé publique du certificat (ou une autorité de certification, CA, commune est un moyen plus sophistiqué de vérifier le certificat de ce serveur, voir -sslGenCA ci-dessous). Cette authentification est effectuée pour prévenir les attaques de type Man-In-The-Middle. Sinon, si le VNC Viewer accepte simplement la clé de ce serveur SANS vérification, le trafic est protégé contre l'écoute passive sur le réseau, mais PAS contre les attaques de type Man-In-The-Middle. Il existe des outils de piratage comme dsniff/webmitm et cain qui implémentent des attaques de type Man-In-The-Middle SSL.
Si [pem] est vide ou la chaîne "SAVE", alors la commande openssl(1) doit être disponible pour générer le certificat la première fois. Un certificat auto-signé est généré (voir -sslGenCA et -sslGenCert pour l'utilisation d'une autorité de certification). Il sera sauvegardé dans le fichier ~/.vnc/certs/server.pem. Lors des appels suivants, si ce fichier existe déjà, il sera utilisé directement.
Utilisez "SAVE_NOPROMPT" pour éviter d'être invité à protéger la clé générée avec une phrase secrète. Cependant, dans les modes -inetd et -bg, aucune invite ne sera générée dans les deux cas.
Si [pem] est "SAVE_PROMPT", le certificat server.pem sera créé en fonction de vos réponses à ses invites pour toutes les informations telles que OrganizationalName, CommonName, etc.
Utilisez "SAVE-<chaîne>" et "SAVE_PROMPT-<chaîne>" pour faire référence au fichier ~/.vnc/certs/server-<chaîne>.pem à la place (il sera généré s'il n'existe pas déjà). Par exemple, "SAVE-charlie" sauvegardera dans le fichier ~/.vnc/certs/server-charlie.pem
Exemples : x11vnc -ssl SAVE -display :0 ... x11vnc -ssl SAVE-someother -display :0 ...
Si [pem] est "TMP" et que l'utilitaire openssl(1) existe dans PATH, alors un certificat temporaire auto-signé sera généré pour cette session. Si openssl(1) ne peut pas être utilisé pour générer un certificat temporaire, x11vnc se terminera immédiatement. Le certificat temporaire sera supprimé lorsque x11vnc se terminera.
En cas de succès dans l'utilisation de openssl(1) pour générer un certificat temporaire dans les modes de création "SAVE" ou "TMP", sa partie publique sera affichée sur stderr (par exemple, on pourrait la copier côté client pour authentifier le serveur auprès des visualiseurs VNC).
NOTE : En mode "TMP", à moins que vous ne copiez en toute sécurité la partie publique du certificat temporaire vers le visualiseur pour l'authentification *à chaque fois* (peu probable...), seules les attaques d'écoute passive sont évitées et vous restez exposé aux attaques de type Man-In-The-Middle. C'est pourquoi le mode "SAVE" par défaut est préféré (et le mode CA plus sophistiqué aussi). Ce n'est qu'avec des clés sauvegardées ET le VNC Viewer les authentifiant (via le certificat public) que les attaques de type Man-In-The-Middle sont évitées.
Si [pem] est "ANON", alors la méthode d'échange de clés anonyme Diffie-Hellman est utilisée. Dans ce mode, il n'y a *pas* de certificats SSL et il n'est donc pas possible d'authentifier le serveur VNC ou le client VNC. Par conséquent, seules les attaques d'écoute réseau passives sont évitées : la méthode "ANON" est susceptible aux attaques de type Man-In-The-Middle. "ANON" n'est pas recommandé ; utilisez plutôt un PEM SSL que vous avez créé ou la méthode par défaut "SAVE".
Voir -ssldir ci-dessous pour utiliser un répertoire autre que le répertoire par défaut ~/.vnc/certs
Si votre binaire x11vnc n'a pas été compilé avec le support de la bibliothèque OpenSSL, l'utilisation de l'option -ssl entraînera une défaillance immédiate et une sortie. Pour de tels binaires, envisagez d'utiliser l'option -stunnel pour les connexions chiffrées SSL.
Infos diverses : En mode création de certificat temporaire "TMP", définissez la variable d'environnement X11VNC_SHOW_TMP_PEM=1 pour que x11vnc affiche l'intégralité du certificat, y compris la partie CLÉ PRIVÉE, sur stderr. Il existe de meilleures façons d'obtenir/sauvegarder ces informations. Voir "SAVE" ci-dessus et "-sslGenCert" ci-dessous.

-ssltimeout n

Règle le délai d'attente de lecture SSL sur n secondes. Dans certaines situations (par exemple, un visualiseur iconisé sous Windows), le visualiseur arrête de communiquer et la connexion est interrompue après le délai d'attente par défaut (25s pendant environ la première minute, 43200s plus tard). Réglez sur zéro pour interroger indéfiniment. Réglez sur une valeur négative pour utiliser le réglage intégré.
Notez que cette valeur ne s'applique PAS à la connexion d'initialisation SSL *initiale*. Le délai d'attente par défaut pour cela est de 20 secondes. Utilisez -env SSL_INIT_TIMEOUT=n pour le modifier.

-sslnofail

Se termine à la première défaillance de connexion SSL. Utile lors de la scriptisation de connexions SSL (par exemple, x11vnc est démarré via ssh) et que vous ne voulez pas que x11vnc attende plus de connexions, occupant des ports, etc.

-ssldir dir

Utilisez dir comme répertoire de gestion de certificats et de clés SSL de niveau supérieur alternatif. Le répertoire par défaut est ~/.vnc/certs
Ce répertoire est utilisé pour stocker les certificats et clés du serveur et d'autres, ainsi que d'autres matériaux. Par exemple, dans le cas le plus simple, "-ssl SAVE" stockera le certificat du serveur x11vnc dans dir/server.pem
L'utilisation de répertoires alternatifs via -ssldir vous permet de gérer plusieurs clés d'autorité de certification VNC (CA). Une autre utilisation est si ~/.vnc/cert se trouve sur un partage NFS, vous pourriez vouloir que vos certificats et clés soient sur un système de fichiers local pour éviter l'espionnage réseau (par exemple -ssldir /var/lib/x11vnc-certs).
-ssldir affecte presque toutes les autres options -ssl*, par exemple -ssl SAVE, -sslGenCert, etc..

-sslverify chemin

Pour les modes -ssl ou -stunnel, utilisez chemin pour fournir des certificats afin d'authentifier les connexions VNC *Client* entrantes (normalement, seul le serveur est authentifié en SSL). Cela peut être utilisé comme méthode pour remplacer l'authentification standard par mot de passe des clients.
Si chemin est un répertoire, il contient les certificats client (ou CA) dans des fichiers séparés. Si chemin est un fichier, il contient un ou plusieurs certificats. Voir les jetons spéciaux ci-dessous. Ceux-ci correspondent aux options stunnel "CApath = dir" et "CAfile = file". Voir la page man de stunnel(8) pour plus de détails.
Exemples : x11vnc -ssl -sslverify ~/my.crt x11vnc -ssl
-sslverify path Notez que si le chemin est un répertoire, il doit contenir les certificats dans des fichiers séparés nommés comme <HASH>.0, où la valeur de <HASH> est trouvée en exécutant la commande "openssl x509 -hash -noout -in fichier.crt". Évidemment, on utilise <HASH>.1 s'il y a une collision... L'utilitaire de gestion de clés "-sslCertInfo HASHON" et "-sslCertInfo HASHOFF" créera/supprimera ces hashs pour vous automatiquement (via lien symbolique) dans les sous-répertoires HASH qu'il gère. Ensuite, vous pouvez pointer -sslverify vers le sous-répertoire HASH. Tokens spéciaux : en mode -ssl, si chemin n'est pas un fichier ou un répertoire, il est interprété comme une liste de tokens séparés par des virgules qui sont interprétés comme suit : Si un token est "CA", cela signifie charger le fichier CA/cacert.pem du répertoire ssl. Si un token est "clients", alors tous les fichiers clients/*.crt du répertoire ssl sont chargés. Sinon, le fichier clients/token.crt est tenté d'être chargé. Par astuce, utilisez un token comme ../server-foo pour charger un certificat serveur si vous le trouvez nécessaire. Utilisez -ssldir pour utiliser un répertoire différent de celui par défaut ~/.vnc/certs. Notez que si le certificat "CA" est chargé, vous n'avez pas besoin de charger aucun des certificats qui ont été signés par lui. Vous devrez cependant charger tous les certificats auto-signés supplémentaires. Exemples : x11vnc -ssl -sslverify CA x11vnc -ssl -sslverify self:fred,self:jim x11vnc -ssl -sslverify CA,clients Habituellement, "-sslverify CA" est le plus efficace. Voir les options -sslGenCA et -sslGenCert ci-dessous pour savoir comment configurer et gérer le framework CA. NOTE : les utilitaires suivants, -sslGenCA, -sslGenCert, -sslEncKey, -sslCertInfo, et -sslCRL sont fournis pour la complétude, mais pour une utilisation occasionnelle, ils sont excessifs. Ils fournissent la création de clés d'Autorité de Certification (CA) VNC et la génération et signature de clés serveur / client. Ils fournissent donc un framework de gestion de clés publiques de base pour VNC avec x11vnc. (notez qu'ils nécessitent que openssl(1) soit installé sur le système) Cependant, le mode d'utilisation le plus simple, "-ssl TMP" (où x11vnc génère automatiquement sa propre clé temporaire auto-signée et les visionneuses VNC l'acceptent toujours, par exemple en l'acceptant via une boîte de dialogue) est probablement suffisamment sûr pour la plupart des scénarios. Aucune gestion de CA n'est nécessaire. Pour se protéger contre les attaques Man-In-The-Middle, le mode "TMP" peut être amélioré en utilisant "-ssl SAVE" (identique à "-ssl", c'est-à-dire par défaut) pour que x11vnc crée un certificat auto-signé à plus long terme, puis copie (en toute sécurité) la clé publique correspondante vers les machines clientes souhaitées (des précautions doivent être prises pour que la clé privée ne soit pas volée ; vous serez invité à entrer une phrase secrète). Gardez donc à l'esprit qu'aucune création ou gestion de clé CA (-sslGenCA et -sslGenCert) n'est nécessaire pour aucun des deux modes d'utilisation courants mentionnés ci-dessus. On pourrait vouloir utiliser -sslGenCA et -sslGenCert si l'on avait un grand nombre de stations de travail clientes et serveurs VNC. De cette façon, l'administrateur pourrait générer une seule clé CA avec -sslGenCA et distribuer sa partie certificat à toutes les stations de travail. Ensuite, il pourrait créer des clés serveur VNC signées (-sslGenCert serveur ...) pour chaque station de travail ou utilisateur que x11vnc utiliserait alors pour s'authentifier auprès de tout client VNC possédant le certificat CA. Optionnellement, l'administrateur pourrait également faire en sorte que les clients VNC eux-mêmes soient authentifiés auprès de x11vnc (-sslGenCert client ...) Pour cela, -sslverify serait pointé vers le certificat CA (et/ou les certificats auto-signés). x11vnc sera capable d'utiliser tous ces fichiers de certificat et de clé. Du côté du client VNC, ils devront être "importés" d'une manière ou d'une autre. Les navigateurs Web ont des actions de "Gestion des certificats", tout comme le panneau de configuration du plugin d'applet Java. stunnel peut également utiliser ces fichiers (voir le script exemple ss_vncviewer dans la FAQ et SSVNC.)

-sslCRL chemin

Définit les listes de révocation de certificats (CRL) sur chemin. Ce réglage s'applique aux modes -ssl et -stunnel.
Si chemin est un fichier, le fichier contient une ou plusieurs CRL au format PEM. Si chemin est un répertoire, il contient des fichiers nommés par hash de CRL de la manière habituelle d'OpenSSL. Voir la documentation OpenSSL et stunnel(8) pour plus d'informations.
Cette option ne s'applique que si -sslverify a été fourni : elle vérifie la révocation le long de la chaîne de certificats utilisée pour vérifier le client VNC. Le réglage -sslCRL sera ignoré lorsque -sslverify n'est pas spécifié.
Notez que si la date d'expiration d'une CRL est dépassée, toutes les connexions SSL échoueront, qu'elles soient liées au sujet de la CRL ou non.
Il est rare que l'infrastructure -ssl de x11vnc soit suffisamment grande pour que cette option soit utile (car normalement, le maintien du contenu du fichier ou du répertoire -sslverify devrait suffire.) Cependant, lors de l'utilisation de x11vnc avec une Autorité de Certification (voir -sslGenCA) pour authentifier les clients via SSL/TLS, l'option -sslCRL peut être utile pour révoquer les certificats des utilisateurs dont les clés SSL privées ont été perdues ou volées (par exemple, un ordinateur portable.) Ainsi, une nouvelle clé CA+certificat CA n'a pas besoin d'être créée et de nouvelles clés clientes signées générées et distribuées à tous les utilisateurs.
Pour créer un fichier CRL avec des certificats révoqués, les commandes 'openssl ca -revoke ...' et 'openssl ca -gencrl ...' sont utiles. (Exécutez-les dans ~/.vnc/certs)

-sslGenCA [rép]

Génère votre propre clé privée d'Autorité de Certification, certificat et autres fichiers dans le répertoire [rép]. x11vnc se termine alors.
Si [rép] n'est pas fourni, un réglage -ssldir est utilisé, ou sinon ~/.vnc/certs est utilisé.
Cette commande crée également des répertoires où seront stockés les certificats et les clés serveur et client. Le programme openssl(1) doit être installé sur le système et disponible dans le PATH.
Après la création des fichiers et répertoires CA, la commande x11vnc se termine ; le serveur VNC n'est pas exécuté.
Il vous sera demandé des informations à mettre dans le certificat CA. Les informations n'ont pas besoin d'être exactes tant que les clients acceptent le certificat pour les connexions VNC. Vous devrez également fournir une phrase secrète d'au moins 4 caractères pour la clé privée CA.
Une fois que vous avez généré la CA, vous pouvez distribuer sa partie certificat, [rép]/CA/cacert.pem, à d'autres postes de travail où les visionneuses VNC seront exécutées. Il faudra "importer" ce certificat dans les applications, par exemple Navigateur Web, plugin d'applet Java, stunnel, etc. Ensuite, vous pourrez créer et signer des clés en utilisant la CA avec l'option -sslGenCert ci-dessous.
Exemples : x11vnc -sslGenCA x11vnc -sslGenCA ~/monRepCA x11vnc -ssldir ~/monRepCA -sslGenCA
(les deux dernières lignes sont équivalentes)

-sslGenCert type nom

Génère une paire de certificat et clé privée serveur ou client VNC signée par la CA créée précédemment avec -sslGenCA. Le programme openssl(1) doit être installé sur le système et disponible dans le PATH.
Après la génération du certificat, x11vnc se termine ; le serveur VNC n'est pas exécuté.
Le type de clé à générer est la chaîne type. C'est soit "server" (c'est-à-dire à utiliser par x11vnc) soit "client" (pour une visionneuse VNC). Notez que généralement seul "server" est utilisé : les clients VNC s'authentifient par une méthode non-clé publique (par exemple, mot de passe VNC ou unix). type est requis.
Un nom par défaut arbitraire que vous souhaitez associer à la clé est fourni par la chaîne nom. Vous pouvez le modifier aux diverses invites lors de la création de la clé. nom est optionnel.
Si nom est laissé vide pour les clés clientes, "nobody" est utilisé. S'il est laissé vide pour les clés serveur, la clé serveur principale : "server.pem" est créée (c'est la clé enregistrée référencée par "-ssl SAVE" lorsque le serveur est lancé)
Si nom commence par la chaîne "self:", alors un certificat auto-signé est créé au lieu d'un certificat signé par votre clé CA.
Si nom commence par la chaîne "req:", alors seulement une clé (.key) et une *demande* de signature de certificat (.req) sont générées. Vous pouvez ensuite envoyer le fichier .req à une CA externe (même une CA professionnelle, par exemple Thawte) et combiner le .key et le certificat reçu dans le fichier .pem avec le même nom de base.
La distinction entre "server" et "client" est simplement le choix des noms de fichiers et du sous-répertoire de sortie. Cela permet à l'option -ssl SAVE-nom de récupérer facilement le fichier PEM x11vnc généré par cette option. Et de même, permet à l'option -sslverify de récupérer facilement vos certificats clients.
Il n'y a rien de spécial dans le nom de fichier ou l'emplacement du répertoire des certificats "serveur" et "client". Vous pouvez renommer les fichiers ou les déplacer où vous le souhaitez.
Précédez cette option de -ssldir [rép] pour utiliser un répertoire autre que celui par défaut ~/.vnc/certs Vous devrez d'abord exécuter -sslGenCA sur ce répertoire avant de créer des clés -sslGenCert.
Notez que vous ne pouvez pas recréer un certificat avec un nom distinctif (DN) exactement identique à un certificat existant. Pour ce faire, vous devrez modifier le fichier [rép]/CA/index.txt pour supprimer la ligne.
Similaire à -sslGenCA, vous serez invité à fournir des informations qui seront enregistrées dans le certificat lors de sa création.
Astuce : si vous connaissez le nom d'hôte complet auquel les autres se connecteront, vous pouvez l'utiliser comme nom commun "CN" pour éviter que certaines applications (par exemple, les navigateurs Web et le plugin Java) ne se plaignent qu'il ne correspond pas au nom d'hôte.
Vous devrez également fournir la phrase secrète de la clé privée CA pour déverrouiller la clé privée créée à partir de -sslGenCA. Cette clé privée est utilisée pour signer le certificat serveur ou client.
Les certificats "serveur" peuvent être utilisés directement par x11vnc en les pointant via l'option -ssl [pem]. Le fichier par défaut sera ~/.vnc/certs/server.pem. Celui-ci serait utilisé en tapant simplement

-ssl [pem]

Active le chiffrement SSL/TLS pour la connexion VNC. Le programme utilise par défaut la clé privée et le certificat trouvés dans ~/.vnc/certs/server.pem. Si ce fichier n'existe pas, il est généré comme un certificat auto-signé temporaire.
Si pem est fourni, il est utilisé comme chemin vers le fichier PEM contenant à la fois la clé privée et le certificat serveur.
Les options supplémentaires comme -sslverify et -sslCRL peuvent être utilisées pour améliorer la sécurité. Voir ci-dessous.
Il est recommandé d'utiliser un certificat auto-signé qui n'expire pas, plutôt qu'un certificat temporaire, pour éviter les avertissements dans les clients VNC. Voir l'option -sslGenCert pour créer de tels certificats.
Pour une connexion VNC sécurisée sans gestion de CA, la commande de base est simplement : x11vnc -ssl. Le programme générera automatiquement un certificat auto-signé et vous devrez accepter le certificat dans votre client VNC lors de la première connexion.

-sslCRL path

Définit le chemin vers les listes de révocation de certificats (CRL). Cela s'applique aux modes -ssl et -stunnel.
Si path est un fichier, il contient une ou plusieurs CRL au format PEM. Si path est un répertoire, il contient des fichiers nommés par hash de CRL, comme le fait OpenSSL.
Cette option n'est pertinente que si -sslverify est utilisé. Elle permet de vérifier la révocation des certificats dans la chaîne de confiance.
Si la date d'expiration d'une CRL est dépassée, toutes les connexions SSL échoueront, indépendamment du certificat concerné.
Bien que rarement nécessaire dans la plupart des infrastructures x11vnc, cette option peut être utile lors de l'utilisation d'une autorité de certification (CA) pour authentifier les clients. Elle permet de révoquer les certificats des utilisateurs dont les clés privées auraient été perdues ou volées, évitant ainsi la création d'une nouvelle CA et la distribution de nouveaux certificats clients.
Pour créer un fichier CRL, les commandes 'openssl ca -revoke ...' et 'openssl ca -gencrl ...' sont utiles. (Exécutez-les dans le répertoire ~/.vnc/certs)

-sslGenCA [rép]

Génère une clé privée d'autorité de certification (CA) VNC, un certificat et d'autres fichiers dans le répertoire spécifié par [rép]. x11vnc se termine après cette opération.
Si [rép] n'est pas spécifié, le répertoire défini par -ssldir est utilisé, ou le répertoire par défaut ~/.vnc/certs.
Cette commande crée également les sous-répertoires nécessaires pour stocker les certificats et clés des serveurs et clients. Le programme openssl(1) doit être installé et accessible dans le PATH.
Après la création des fichiers et répertoires CA, x11vnc se termine sans démarrer le serveur VNC.
Vous serez invité à fournir des informations pour le certificat CA. Ces informations n'ont pas besoin d'être exactes, tant que les clients acceptent le certificat pour les connexions VNC. Vous devrez également définir une phrase secrète d'au moins 4 caractères pour la clé privée CA.
Une fois la CA générée, vous pouvez distribuer sa partie certificat ([rép]/CA/cacert.pem) aux autres postes de travail où les visionneuses VNC seront exécutées. Ce certificat devra être "importé" dans les applications clientes (navigateur Web, plugin d'applet Java, stunnel, etc.). Vous pourrez ensuite créer et signer des clés à l'aide de la CA en utilisant l'option -sslGenCert ci-dessous.
Exemples : x11vnc -sslGenCA x11vnc -sslGenCA ~/monRepCA x11vnc -ssldir ~/monRepCA -sslGenCA
(les deux dernières lignes sont équivalentes)

-sslGenCert type nom

Génère une paire de certificat et clé privée serveur ou client VNC, signée par la CA créée précédemment avec -sslGenCA. Le programme openssl(1) doit être installé et accessible dans le PATH.
Après la génération du certificat, x11vnc se termine sans démarrer le serveur VNC.
Le type de clé à générer est indiqué par la chaîne type. Il peut s'agir de "server" (pour utilisation par x11vnc) ou "client" (pour une visionneuse VNC). Notez que seul le type "server" est généralement utilisé, car les clients VNC s'authentifient par des méthodes autres que la clé publique (par exemple, mot de passe VNC ou unix). Le paramètre type est obligatoire.
Un nom arbitraire que vous souhaitez associer à la clé est fourni par la chaîne nom. Vous pouvez le modifier lors des différentes invites lors de la création de la clé. Le paramètre nom est optionnel.
Si nom est laissé vide pour les clés clientes, la valeur "nobody" est utilisée. Si nom est laissé vide pour les clés serveur, le fichier de clé serveur principal, "server.pem", est créé (il s'agit du fichier enregistré référencé par l'option "-ssl SAVE" lors du démarrage du serveur).
Si nom commence par la chaîne "self:", un certificat auto-signé est créé au lieu d'un certificat signé par votre clé CA.
Si nom commence par la chaîne "req:", seuls une clé (.key) et une *demande de signature de certificat* (.req) sont générées. Vous pouvez ensuite envoyer le fichier .req à une autorité de certification externe (même une autorité professionnelle, par exemple Thawte) et combiner le fichier .key et le certificat reçu dans le fichier .pem avec le même nom de base.
La distinction entre "server" et "client" réside simplement dans le choix des noms de fichiers et du sous-répertoire de sortie. Cela permet à l'option -ssl SAVE-nom de récupérer facilement le fichier PEM x11vnc généré par cette option. De même, cela permet à l'option -sslverify de récupérer facilement vos certificats clients.
Il n'y a rien de spécial dans le nom de fichier ou l'emplacement du répertoire des certificats "serveur" et "client". Vous pouvez renommer les fichiers ou les déplacer où vous le souhaitez.
Précédez cette option de -ssldir [rép] pour utiliser un répertoire autre que le répertoire par défaut ~/.vnc/certs. Vous devrez exécuter -sslGenCA sur ce répertoire avant de pouvoir créer des clés avec -sslGenCert.
Notez que vous ne pouvez pas recréer un certificat avec un nom distinctif (DN) identique à un certificat existant. Pour ce faire, vous devrez modifier le fichier [rép]/CA/index.txt afin de supprimer la ligne correspondante.
Semblable à -sslGenCA, vous serez invité à fournir des informations qui seront enregistrées dans le certificat lors de sa création.
Astuce : si vous connaissez le nom d'hôte complet auquel les autres se connecteront, vous pouvez l'utiliser comme nom commun (Common Name, "CN") pour éviter que certaines applications (par exemple, les navigateurs Web et le plugin Java) ne signalent une non-concordance avec le nom d'hôte.
Vous devrez également fournir la phrase secrète de la clé privée CA pour déverrouiller la clé privée créée avec -sslGenCA. Cette clé privée est utilisée pour signer le certificat serveur ou client.
Les certificats "serveur" peuvent être utilisés directement par x11vnc en les spécifiant via l'option -ssl [pem]. Le fichier par défaut sera ~/.vnc/certs/server.pem. Celui-ci serait utilisé en tapant simplement
-ssl SAUVEGARDE. Le fichier pem contient à la fois le certificat et la clé privée. Le fichier server.crt ne contient que le certificat.
Le fichier de certificat + clé privée du « client » devra être copié et importé dans les applications côté VNC viewer (navigateur Web, plugin Java, stunnel, etc.). Une fois cela fait, vous pourrez supprimer le fichier de clé privée du « client » sur cette machine, car il n'est nécessaire que du côté du VNC viewer. Le fichier, par exemple ~/.vnc/certs/clients/.pem contient à la fois le certificat et la clé privée. Le fichier .crt ne contient que le certificat.
NOTE : Il est très important de savoir qu'il faut générer de nouvelles clés avec une phrase secrète. Sinon, si un utilisateur non fiable vole le fichier de clé, il pourrait l'utiliser pour se faire passer pour le serveur x11vnc (ou le client VNC viewer). Vous serez invité à choisir de chiffrer la clé avec une phrase secrète ou non. Il est recommandé de le faire. Un inconvénient d'une phrase secrète est qu'elle doit être saisie CHAQUE FOIS que x11vnc ou l'application client est démarré.
Exemples :
x11vnc -sslGenCert serveur x11vnc -ssl SAUVEGARDE -display :0 ...
et ensuite côté viewer en utilisant le wrapper stunnel ss_vncviewer (voir la FAQ) : ss_vncviewer -verify ./cacert.crt hostname:0
(cela suppose que le certificat cacert.crt de -sslGenCA a été copié en toute sécurité sur la machine VNC viewer où ss_vncviewer est exécuté)
Exemple utilisant un nom :
x11vnc -sslGenCert serveur charlie x11vnc -ssl SAUVEGARDE-charlie -display :0 ...
Exemple pour un certificat client (rarement utilisé) :
x11vnc -sslGenCert client roger scp ~/.vnc/certs/clients/roger.pem somehost:. rm ~/.vnc/certs/clients/roger.pem
x11vnc est alors démarré avec l'option -sslverify ~/.vnc/certs/clients/roger.crt (ou simplement -sslverify roger), et côté viewer sur somehost on pourrait faire par exemple :
ss_vncviewer -mycert ./roger.pem hostname:0
Si vous définissez la variable d'environnement REQ_ARGS='...' elle sera passée à openssl req(1). Une utilisation courante serait REQ_ARGS='-days 1095' pour augmenter la date d'expiration (3 ans dans ce cas).

-sslEncKey pem

Utilitaires pour chiffrer un fichier PEM existant avec une phrase secrète que vous fournissez lors de la demande. Pour que cette clé soit utilisée (par exemple par x11vnc), la phrase secrète doit être fournie à chaque fois.
La notation « SAUVEGARDE » décrite sous -ssl s'applique également. (précéder cette option avec -ssldir [dir] pour faire référence à un répertoire autre que le répertoire par défaut ~/.vnc/certs)
Le programme openssl(1) doit être installé sur le système et disponible dans le PATH. Après le chiffrement du fichier clé, la commande x11vnc se termine ; le serveur VNC n'est pas démarré.
Exemples : x11vnc -sslEncKey /chemin/vers/foo.pem x11vnc -sslEncKey SAUVEGARDE x11vnc -sslEncKey SAUVEGARDE-charlie

-sslCertInfo pem

Affiche des informations sur un fichier PEM existant. De plus, le certificat public est également affiché. Le programme openssl(1) doit être dans le PATH. Essentiellement, la commande « openssl x509 -text » est exécutée sur le pem.
Après l'affichage des informations, la commande x11vnc se termine ; le serveur VNC n'est pas démarré.
La notation « SAUVEGARDE » décrite sous -ssl s'applique également.
Utiliser « LIST » affichera une liste de tous les certificats gérés (dans le répertoire ~/.vnc/certs, utilisez -ssldir pour faire référence à un autre répertoire). « ALL » affichera les informations pour chaque clé gérée (cela peut être très long). Donner un nom court de certificat client ou serveur tentera également une recherche (par exemple, -sslCertInfo charlie). Utilisez « LISTL » ou « LL » pour un affichage long (style ls -l).
Utiliser « HASHON » créera des sous-répertoires [dir]/HASH et [dir]/HASH avec des noms de fichiers hachés OpenSSL (par exemple, 0d5fbbf1.0) des liens symboliques pointant vers le fichier *.crt correspondant. ([dir] est ~/.vnc/certs ou celui spécifié par -ssldir.) C'est un moyen utile pour d'autres applications OpenSSL (par exemple, stunnel) d'accéder à tous les certificats sans avoir à les concaténer. x11vnc ne les utilisera pas à moins que vous ne les référenciez explicitement. « HASHOFF » supprime ces sous-répertoires HASH.
Les mots LIST, LISTL, LL, ALL, HASHON, HASHOFF peuvent également être en minuscules, par exemple, « list ».

-sslDelCert pem

Vous demandera de supprimer tous les fichiers .crt, .pem, .key, .req associés à [pem]. x11vnc se termine ensuite. Les notations « SAUVEGARDE » et les recherches comme dans -sslCertInfo s'appliquent également.

-sslScripts

Affiche les scripts wrapper openssl de x11vnc 'genCA' et 'genCert' pour que vous puissiez les examiner, modifier, etc. Les scripts sont affichés sur la sortie standard et ensuite le programme x11vnc se termine.

-stunnel [pem]

Utilise stunnel(8) (stunnel.mirt.net) pour fournir un tunnel SSL crypté entre les viewers et x11vnc.
Cette méthode de tunnel externe a été implémentée avant le chiffrement intégré -ssl décrit ci-dessus. Elle fonctionne toujours bien et évite l'obligation de lier avec les bibliothèques OpenSSL. Ce mode nécessite que stunnel soit installé sur le système et disponible via PATH (n.b. stunnel est souvent installé dans les répertoires sbin). La version 4.x de stunnel est supposée (mais voir -stunnel3 ci-dessous).
[pem] est facultatif, utilisez « -stunnel /chemin/vers/stunnel.pem » pour spécifier un fichier certificat PEM à passer à stunnel. Voir l'option -ssl pour plus d'informations sur les fichiers certificats.
Que votre stunnel ait son propre certificat ou non dépend de votre configuration stunnel ; stunnel en génère souvent un lors de l'installation. Voir votre documentation stunnel pour les détails. En tout cas, si vous souhaitez utiliser ce certificat, vous devez fournir le chemin complet vers celui-ci en tant que [pem]. Remarque : le fichier peut n'être lisible que par root.
[pem] peut également être les chaînes spéciales « TMP », « SAUVEGARDE » et « SAUVEGARDE... » comme décrit dans l'option -ssl. Si [pem] n'est pas fourni, « SAUVEGARDE » est supposé.
Notez que les modes VeNCrypt, ANONTLS et « ANON » ne sont pas pris en charge en mode -stunnel.
stunnel est démarré comme processus enfant de x11vnc et toutes les connexions SSL que stunnel reçoit sont déchiffrées et envoyées à x11vnc via un socket local. Les chaînes « The SSL VNC desktop is ... » et « SSLPORT=... » sont affichées au démarrage pour l'indiquer.
L'option -localhost est appliquée par défaut pour éviter que des personnes ne contournent le canal SSL. Utilisez -env STUNNEL_DISABLE_LOCALHOST=1 pour désactiver cette exigence de sécurité.
Définissez -env STUNNEL_DEBUG=1 pour plus de messages de débogage.
Définissez -env STUNNEL_PROG=xxx vers le chemin complet du programme stunnel que vous souhaitez utiliser (par exemple, /usr/bin/stunnel4).
Définissez -env STUNNEL_LISTEN=xxx vers l'adresse de l'interface réseau à écouter (par défaut, écouter sur toutes les interfaces), par exemple, STUNNEL_LISTEN=192.168.1.100.
Un moyen simple d'ajouter la prise en charge d'IPv6 est STUNNEL_LISTEN=::
Votre VNC viewer devra également pouvoir se connecter via SSL. Malheureusement, peu d'entre eux le font. Voir les informations sur les viewers SSL sous l'option -ssl. Le projet x11vnc SSVNC est une option.
De plus, dans la distribution x11vnc, des fichiers jar d'applet Java TightVNC et UltraVNC patchés sont fournis dans le répertoire classes/ssl qui effectuent des connexions SSL. Activez leur diffusion avec -http, -http_ssl, ou -httpdir (voir les descriptions d'options pour plus d'informations.)
Notez que pour l'utilisation de l'applet Java viewer, le « ?PORT=xxxx » dans les différentes URL affichées au démarrage devra être fourni au navigateur Web pour une connexion correcte.
Actuellement, le mode HTTPS automatique « port unique » de -ssl n'est pas entièrement pris en charge en mode -stunnel. Cependant, il peut être émulé via :
% x11vnc -stunnel -http_ssl -http_oneport ...
En général, il n'est pas trop difficile de configurer un stunnel ou un autre tunnel SSL du côté du viewer. Un exemple simple sous Unix utilisant stunnel 3.x est :
% stunnel -c -d localhost:5901 -r remotehost:5900 % vncviewer localhost:1
Pour Windows, stunnel a été porté et il existe probablement d'autres outils similaires disponibles. Voir la FAQ et SSVNC pour plus d'exemples.

-stunnel3 [pem]

Utilise la syntaxe de ligne de commande stunnel version 3.x au lieu de la version 4.x. La diffusion de l'applet Java -http/-httpdir n'est actuellement pas disponible dans ce mode.

-enc chiffrement:fichierclé

Utilise un chiffrement symétrique avec le chiffrement « chiffrement » et des données de clé secrète dans « fichierclé ». Si fichierclé est pw=<chaîne> alors « chaîne » est utilisée comme données de clé.
NOTE : Il est recommandé d'utiliser SSL via l'option -ssl au lieu de cette option car SSL est bien compris et prend grand soin d'établir des clés de session uniques et est plus compatible avec d'autres logiciels. Utilisez cette option si vous ne voulez pas traiter de certificats SSL pour l'authentification et que vous ne souhaitez pas utiliser SSH mais que vous voulez un certain chiffrement pour votre session VNC. Ou si vous devez interagir avec un tunnel à clé symétrique sur lequel vous n'avez pas de contrôle.
Notez que ce mode NE FONCTIONNERA PAS avec les plugins DSM d'UltraVNC car ils modifient le protocole RFB en plus du tunnel avec le chiffrement symétrique (un choix d'implémentation malheureux...)
chiffrement peut être l'un des suivants : arc4, aesv2, aes-cfb, blowfish, aes256, ou 3des. Voir la documentation OpenSSL pour plus d'informations. La taille de la clé est de 128 bits (sauf pour aes256). Voici une façon de créer un fichier clé avec autant de bits :
dd if=/dev/random of=./my.key bs=16 count=1
vous devrez partager cette clé en toute sécurité avec l'autre extrémité de la connexion VNC (Voir SSVNC pour des exemples).
Exemple : -enc blowfish:./my.key Exemple : -enc blowfish:pw=swordfish
Par défaut, 16 octets de sel aléatoire suivis de 16 octets de vecteur d'initialisation aléatoire sont envoyés au tout début du flux. L'autre extrémité doit les lire et initialiser son chiffrement avec. Ces valeurs rendent la clé de session unique (sans elles, la sécurité est minimale). De même, l'autre extrémité doit nous envoyer son aléatoire
salt et IV avec ces mêmes longueurs.
Le sel et les données de clé sont combinés pour créer une clé de session en utilisant un hachage md5 comme décrit dans EVP_BytesToKey(3).
L'appel exact est : EVP_BytesToKey(Cipher, EVP_md5(), salt, keydata, len, 1, keystr, NULL); où salt sont les données aléatoires comme décrit ci-dessus, et keydata sont les données de clé secrète partagée. keystr est la clé de session résultante. Le chiffrement est ensuite initialisé avec keystr et utilise le vecteur d'initialisation aléatoire comme premier bloc.
Pour modifier la quantité de sel aléatoire et de vecteur d'initialisation, utilisez cipher@n,m où n est la longueur du sel et m la longueur du vecteur d'initialisation. Par exemple :
-enc aes-cfb@8,16:./my.key
Il n'est pas conseillé de mettre l'un ou l'autre à zéro, bien que vous puissiez y être contraint si l'autre côté du tunnel n'est pas sous votre contrôle.
Pour ignorer complètement le sel et EVP_BytesToKey MD5 (aucun hachage n'est effectué : les données de clé sont directement insérées dans le chiffrement) spécifiez "-1" pour le sel, par exemple :
-enc blowfish@-1,16:./my.key
La somme de contrôle du message peut également être modifiée pour autre chose que le MD5 par défaut. Utilisez cipher@md+n,m où "md" peut être l'un de sha, sha1, md5, ou ripe. Par exemple :
-enc arc4@sha+8,16:./my.key
Le projet de visionneuse VNC SSVNC fournit un outil de chiffrement symétrique nommé "ultravnc_dsm_helper" qui peut être utilisé côté visionneuse. Par exemple :
ssvncviewer exec='ultravnc_dsm_helper arc4 my.key 0 h:p'
où h:p est le nom d'hôte et le port du serveur x11vnc. ultravnc_dsm_helper peut également être utilisé de manière autonome pour fournir un tunnel de chiffrement symétrique pour n'importe quelle visionneuse ou serveur (VNC ou autre.) Le chiffrement (1er argument) a essentiellement la même syntaxe que celle que nous utilisons ci-dessus.
Voir également l'option SSVNC 'Non-Ultra DSM' pour l'option avancée 'UltraVNC DSM Encryption Plugin'.
Pour les deux façons d'utiliser la visionneuse, vous pouvez spécifier les tailles du sel et de l'IV (dans l'interface graphique ou, par exemple, arc4@8,16).

-https [port]

Utilise un port HTTPS spécial et séparé (-ssl et modes -stunnel uniquement) pour le téléchargement de l'applet Java VNC Viewer HTTPS. C'est-à-dire pas 5900 et pas 5800 (les valeurs par défaut).
CONTEXTE : En mode -ssl, il s'avère que vous pouvez utiliser le port VNC unique (par exemple, 5900) pour les connexions VNC et HTTPS. (HTTPS est utilisé pour récupérer un VncViewer.jar applet compatible SSL qui est fourni avec x11vnc). Comme les deux utilisent SSL, l'implémentation a été étendue pour détecter si le trafic HTTP (c'est-à-dire GET) est en cours et le gérer en conséquence. L'URL serait, par exemple :
https://mymachine.org:5900/
C'est pratique pour les pare-feu, etc., car un seul port doit être autorisé. Cependant, cette heuristique ajoute quelques secondes de délai à chaque connexion et peut être peu fiable (surtout si l'utilisateur prend beaucoup de temps pour réfléchir aux dialogues de certificat dans son navigateur, sa machine virtuelle Java ou l'applet VNC Viewer. C'est bien ça, 3 dialogues séparés "Êtes-vous sûr de vouloir vous connecter ? !")
FIN DU CONTEXTE.
UTILISATION : Utilisez donc l'option -https pour fournir un port HTTPS séparé et plus fiable sur lequel x11vnc écoutera. Si [port] n'est pas fourni (ou est 0), un port est automatiquement sélectionné. L'URL à utiliser est affichée au démarrage.
Le répertoire de l'applet Java SSL est spécifié via l'option -httpdir. S'il n'est pas fourni, -https essaiera de deviner le répertoire comme si l'option -http avait été fournie.

-httpsredir [port]

En mode -ssl avec l'applet Java récupérée via HTTPS, lorsque le fichier HTML contenant les paramètres de l'applet ('index.vnc' ou 'proxy.vnc') est envoyé, ne définissez PAS le paramètre PORT de l'applet sur le port VNC réel, mais définissez-le sur "port" à la place. Si "port" n'est pas fourni, le numéro de port est deviné à partir de l'en-tête Host: HTTP.
Ceci est utile lorsqu'une redirection de connexion TCP entrante est effectuée par un routeur/passerelle/pare-feu d'un port vers une machine interne où x11vnc écoute sur un port différent. L'applet Java doit se connecter au port du pare-feu/routeur, et non au port VNC de la station de travail interne. Par exemple, on pourrait rediriger de mygateway.com:443 vers workstation:5900.
Cela évite à l'utilisateur d'avoir à taper https://mygateway.com/?PORT=443 dans son navigateur Web. Notez que le port 443 est le port https par défaut ; d'autres ports doivent être explicitement indiqués, par exemple : https://mygateway.com:8000/?PORT=8000. Pour éviter d'avoir à inclure PORT= dans l'URL du navigateur, il suffit de fournir ""-httpsredir"" à x11vnc.
Cette option ne fonctionne pas en mode -stunnel.
Plus d'astuces : définissez la variable d'environnement X11VNC_EXTRA_HTTPS_PARAMS pour les paramètres d'URL supplémentaires à utiliser. Ainsi, vous n'avez pas besoin de spécifier des PARAMS supplémentaires dans le fichier index.vnc. Par exemple : x11vnc -env X11VNC_EXTRA_HTTPS_PARAMS='?GET=1' ...
Si vous ne souhaitez pas exposer le port HTTP non SSL au réseau (c'est-à-dire que vous souhaitez uniquement que le port VNC/HTTPS unique, par exemple 5900, soit ouvert aux connexions), spécifiez alors l'option -env X11VNC_HTTP_LISTEN_LOCALHOST=1. De cette façon, la connexion au serveur httpd LibVNCServer ne sera disponible que sur localhost (notez qu'en mode -ssl, les requêtes HTTPS sont redirigées de SSL vers le serveur HTTP non SSL LibVNCServer).

-http_oneport

Pour le mode de connexion NON chiffré (c'est-à-dire sans les options -ssl, -stunnel, ou -enc), permettre le téléchargement de l'applet VNC Viewer Java via HTTP par le port VNC.
C'est-à-dire que vous pouvez utiliser un port unique pour les connexions de visionneuse d'applet Java en utilisant une URL dans votre navigateur Web comme celle-ci, par exemple :
http://hostname:5900
Le mode régulier à deux ports, l'URL http://hostname:5800 continuera également à fonctionner.
Comme mentionné ci-dessus, ce mode ne fonctionnera PAS avec les options de chiffrement -ssl, -stunnel, ou -enc. Notez qu'il est équivalent à '-enc none' (c'est-à-dire qu'il utilise le même mécanisme de détection que pour HTTPS, mais sans chiffrement).
Le port unique HTTPS est activé par défaut en mode chiffré -ssl (et -enc également), vous n'avez donc besoin de -http_oneport que lorsque vous effectuez des connexions non SSL chiffrées.
Ce mode pourrait également être utile pour les tunnels SSH car il signifie qu'un seul port doit être redirigé.
L'option -httpsredir peut également être utile pour ce mode lors de l'utilisation d'un tunnel SSH ainsi que pour les redirections de ports de routeur.
Notez que l'option -env X11VNC_HTTP_LISTEN_LOCALHOST=1 décrite ci-dessus sous -httpsredir s'applique au serveur httpd LibVNCServer dans tous les cas (ssl ou non).

-ssh user@host:disp

Crée un port d'écoute distant sur la machine "host" via un tunnel SSH en utilisant la méthode -R rport:localhost:lport. lport sera le port d'écoute local x11vnc, donc une connexion à rport (5900+disp) sur "host" atteindra x11vnc. Par exemple : fred@snoopy.com:0
Cela pourrait être utile si un pare-feu/routeur empêche les connexions entrantes vers la machine x11vnc, mais que la machine ssh "host" est accessible par la visionneuse VNC. "user@" n'est pas nécessaire sauf si le nom d'utilisateur unix distant diffère de l'actuel.
Par défaut, le démon ssh distant est généralement configuré pour écouter uniquement sur localhost pour rport, donc la visionneuse peut également avoir besoin de ssh -L redir vers "host" (Voir SSVNC pour automatiser cela). Le paramètre sshd GatewayPorts permet d'écouter sur toutes les interfaces pour rport ; les visionneuses peuvent y accéder plus facilement.
"disp" est l'affichage VNC pour le côté SSH distant, par exemple 0 correspond au port 5900, etc. Si disp est supérieur à 200, la valeur est utilisée comme port. Utilisez une valeur négative pour forcer un port bas, par exemple host:-80 utilisera le port 80.
Si ssh-agent n'est pas actif, alors le mot de passe ssh doit être saisi dans le terminal où x11vnc est en cours d'exécution.
Par défaut, le démon ssh distant émettra un 'sleep 300' pour attendre la connexion entrante pendant 5 minutes. Pour modifier cela, utilisez user@host:disp+secs.
Si le serveur SSH distant est sur un port non standard (c'est-à-dire pas 22) utilisez user@host:port:disp+secs.
Notez que le processus ssh PEUT NE PAS être arrêté lorsque x11vnc se termine. Il essaie en regardant la sortie de ps(1).

Il faut donc une personne assise devant l'affichage physique pour répondre à une invite contextuelle. (utilisez un 2ème x11vnc si vous vous enfermez). Plus d'astuces -accept : utilisez "popupmouse" pour n'autoriser que les clics de souris dans la fenêtre contextuelle intégrée à être reconnus. Exemple : -gone 'xlock &' -users list Si x11vnc est lancé en tant que root (par exemple, depuis inetd(8) ou depuis des gestionnaires d'affichage xdm(1) , gdm(1) , etc.), alors dès que possible après l'établissement des connexions à l'affichage X, essayez de basculer vers l'un des utilisateurs de la liste séparée par des virgules. Si x11vnc ne s'exécute pas en tant que root, cette option est ignorée. Pourquoi utiliser cette option ? En général, elle n'est pas nécessaire car x11vnc est déjà connecté à l'affichage X et peut remplir ses fonctions principales. L'option a été ajoutée pour que certaines des commandes utilitaires *externes* que x11vnc exécute occasionnellement fonctionnent correctement. En particulier sous GNOME et KDE pour implémenter la fonctionnalité "-solid couleur", les commandes externes (gconftool-2 et dcop) doivent malheureusement être exécutées en tant qu'utilisateur propriétaire de la session de bureau. Comme cette option change d'ID utilisateur, elle affecte également l'ID utilisateur utilisé pour exécuter les processus des options -accept et -gone. Elle affecte également la capacité de lire des fichiers pour des options telles que -connect, -allow, et -remap ainsi que la fonctionnalité de transfert de fichiers ultra et tight si activée. Notez que le fichier -connect est également parfois écrit. Soyez donc prudent avec cette option car dans certaines situations, son utilisation peut réduire la sécurité. En général, le passage à un utilisateur n'aura lieu que si l'affichage peut toujours être ouvert avec succès en tant que cet utilisateur (ceci vise principalement à essayer de deviner le propriétaire réel de la session). Exemple : "-users fred,wilma,betty". Notez qu'un utilisateur local malveillant "barney" en utilisant rapidement "xhost +" lors de la connexion peut potentiellement amener le processus x11vnc à basculer vers l'utilisateur "fred". Que se passe-t-il ensuite ? Sous les gestionnaires d'affichage, le basculement peut prendre beaucoup de temps avant de réussir (c'est-à-dire qu'un utilisateur se connecte). Pour basculer immédiatement, quel que soit le succès de la réouverture de l'affichage, préfixez le nom d'utilisateur avec le caractère "+". Par exemple, "-users +bob" ou "-users +nobody". Ce dernier (c'est-à-dire le basculement immédiat vers l'utilisateur "nobody") est la seule utilisation évidente de l'option -users qui augmente la sécurité. Utilisez la notation suivante pour associer un groupe à un utilisateur : user1.group1,user2.group2,... Notez que initgroups(2) sera toujours appelé en premier pour essayer de basculer vers TOUS les groupes d'un utilisateur (groupes primaires et supplémentaires). Seulement si cela échoue ou n'est pas disponible, le groupe unique spécifié ci-dessus (ou le groupe primaire de l'utilisateur s'il n'est pas spécifié) sera basculé avec setgid(2). Utilisez -env X11VNC_SINGLE_GROUP=1 pour empêcher l'appel à initgroups(2) et ne basculer que vers le groupe unique. Ce type de paramètre n'est vraiment nécessaire que pour que les permissions de transfert de fichiers ultra ou tight fonctionnent correctement. Ce format s'applique à toute liste d'utilisateurs séparée par des virgules, même aux modes "=" spéciaux décrits ci-dessous. En mode -unixpw, si "-users unixpw=" est fourni, alors après qu'un utilisateur s'est authentifié via le mécanisme -unixpw, x11vnc essaiera de basculer vers cet utilisateur comme si "-users +username" avait été fourni. Si vous souhaitez limiter les utilisateurs pour lesquels cela sera fait, fournissez-les sous forme de liste séparée par des virgules après "unixpw=". Les groupes peuvent également être spécifiés comme décrit ci-dessus. De même, en mode -ssl, si "-users sslpeer=" est fourni, alors après qu'un client SSL s'est authentifié avec son certificat (l'option -sslverify est requise pour cela), x11vnc extraira un nom d'utilisateur UNIX du champ "emailAddress" (username@hostname.com) du "Subject" du certificat SSL x509, puis essaiera de basculer vers cet utilisateur comme si "-users +username" avait été fourni. Si vous souhaitez limiter les utilisateurs pour lesquels cela sera fait, fournissez-les sous forme de liste séparée par des virgules après "sslpeer=". Définissez la variable d'environnement X11VNC_SSLPEER_CN pour utiliser le nom commun (normalement un nom d'hôte) au lieu du champ Email. NOTE : pour le mode sslpeer=, l'administrateur x11vnc doit s'assurer que tous les certificats clients qu'il ajoute à -sslverify ont le nom d'utilisateur UNIX souhaité dans le champ "emailAddress" du certificat. Sinon, un utilisateur peut se connecter en tant qu'un autre. Cette commande peut être utile pour vérifier : "openssl x509 -text -in file.crt", voir la ligne "Subject:". De plus, en plus des variables d'environnement RFB_* normales (voir -accept) passées aux commandes externes, RFB_SSL_CLIENT_CERT sera défini sur la chaîne du certificat x509 du client. Le mode sslpeer= peut aider à trouver des sessions X via les mécanismes FINDDISPLAY et FINDCREATEDISPLAY. Pour basculer immédiatement vers un utilisateur *avant* que les connexions à l'affichage X ne soient effectuées ou que des fichiers ne soient ouverts, utilisez le caractère "=" : "-users =bob". Cet utilisateur doit pouvoir ouvrir l'affichage X et tous les fichiers bien sûr. L'utilisateur spécial "guess=" signifie examiner la base de données utmpx (voir who(1) ) à la recherche d'un utilisateur attaché au numéro d'affichage (depuis l'option DISPLAY ou -display) et essayer cette personne. Pour limiter la liste des suppositions, utilisez : "-users guess=bob,betty". Encore plus sinistre est l'utilisateur spécial "lurk=" qui signifie essayer de deviner également le DISPLAY à partir de la base de données de connexion utmpx. Il "lurk" donc en attendant que quelqu'un se connecte à une session X, puis s'y connecte. Spécifiez une liste d'utilisateurs après le = pour limiter les utilisateurs qui seront essayés. Pour activer un mode de recherche différent, si le premier utilisateur de la liste est quelque chose comme ":0" ou ":0-2", cela indique une plage de numéros de DISPLAY qui seront essayés (indépendamment du fait qu'ils soient dans la base de données utmpx) pour tous les utilisateurs connectés. Voir également la fonctionnalité "-display WAIT:...". Exemples : "-users lurk=" et aussi "-users lurk=:0-1,bob,mary" Soyez particulièrement prudent lorsque vous utilisez les modes "guess=" et "lurk=". Ils ne sont pas recommandés pour une utilisation sur des machines avec des utilisateurs locaux non fiables. -noshm N'utilisez pas l'extension MIT-SHM pour le polling. Les affichages distants peuvent être interrogés de cette manière : attention, cela peut consommer une grande quantité de bande passante réseau. Ceci est également utile si la machine locale a un nombre limité de segments shm et que -onetile n'est pas suffisant. -flipbyteorder Parfois nécessaire si l'hôte interrogé à distance a un ordre d'octets différent. Ignoré sauf si -noshm est défini. -onetile N'utilisez pas le nouveau mécanisme de framebuffer copy_tiles(), utilisez simplement 1 tuile shm pour le polling. Limites shm segments utilisés jusqu'à 3.
Pour désactiver toute réduction automatique de shm, définissez la variable d'environnement X11VNC_NO_LIMIT_SHM.

Actuellement, cette option ne fonctionne que sur GNOME, KDE, CDE, XFCE et X classique (c'est-à-dire avec l'image d'arrière-plan sur la fenêtre racine). Les commandes externes "gconftool-2", "dcop" et "xfconf-query" sont exécutées pour GNOME, KDE et XFCE respectivement. Cela fonctionne également sur MacOSX natif. (Il n'y a pas de sélection de couleur pour MacOSX ou XFCE.) D'autres environnements de bureau ne fonctionneront pas (envoyez-nous les commandes correspondantes si vous les trouvez). Si x11vnc s'exécute en tant que root ( inetd(8) ou gdm(1) ), l'option -users peut être nécessaire pour GNOME, KDE, XFCE. Si x11vnc devine incorrectement votre environnement de bureau, vous pouvez le forcer en préfixant la couleur par "gnome:", "kde:", "cde:", "xfce:", ou "root:".
Mise à jour : -solid ne fonctionne plus sur KDE4.
Ce mode fonctionne de manière limitée sur la console Mac OS X avec une seule couleur ('kelp') en utilisant le économiseur d'écran qui écrit sur l'arrière-plan. Regardez dans "~/Library/Screen Savers" pour VncSolidColor.png pour changer la couleur.

-blackout chaîne

Noircir des rectangles sur l'écran. La chaîne est une liste d'ähännes séparées par des virgules de géométries de type LxF+X+Y pour chaque rectangle. Si l'un des éléments de la liste est la chaîne "noptr", le pointeur de la souris ne sera pas autorisé à entrer dans une zone noircie.

-xinerama, -noxinerama

Si votre écran est composé de plusieurs moniteurs collés ensemble via XINERAMA, et que cet écran n'est pas un rectangle, cette option essaiera de deviner les zones à masquer (si votre système dispose de libXinerama). Par défaut : -xinerama
En général, nous avons remarqué que sur les écrans XINERAMA, vous pourriez avoir besoin d'utiliser l'option "-xwarppointer" si le pointeur de la souris se comporte mal et qu'il est activé par défaut. Utilisez "-noxwarppointer" si vous ne le souhaitez pas.

-xtrap

Utiliser l'extension DEC-XTRAP pour l'insertion des entrées clavier et souris. Pour une utilisation sur des systèmes hérités, par exemple X11R5, exécutant une extension XTEST incomplète ou manquante. Par défaut, DEC-XTRAP sera utilisé si le contrôle de capture du serveur XTEST est manquant, utilisez -xtrap pour effectuer également l'insertion des frappes et des mouvements de souris via DEC-XTRAP.

-xrandr [mode]

Si l'affichage prend en charge l'extension XRANDR (X Resize, Rotate and Reflection), et que vous vous attendez à ce que des événements XRANDR se produisent sur l'affichage pendant que x11vnc est en cours d'exécution, cette option indique à x11vnc de tenter d'y répondre (par opposition à simplement planter en supposant l'ancienne taille de l'écran). Voir la page de manuel de xrandr(1) et exécuter 'xrandr -q' pour plus d'informations. Le [mode] est facultatif et décrit ci-dessous.
Étant donné que la surveillance des événements XRANDR et le piégeage des erreurs augmentent la surcharge d'interrogation, n'utilisez cette option que si des changements XRANDR sont attendus. Par exemple, sur un PDA ou un ordinateur portable avec écran rotatif, ou en utilisant un bureau compatible XRANDR où vous redimensionnez souvent. Il est préférable de visualiser avec un vncviewer qui prend en charge l'encodage NewFBSize, car il sait comment réagir aux changements de taille de l'écran. Sinon, LibVNCServer essaie de faire quelque chose de raisonnable pour les visionneuses qui ne peuvent pas le faire (des parties de l'écran peuvent être coupées, inutilisées, etc.).
Note : par défaut, il vérifie les événements XRANDR, mais ne capture pas tous les appels X qui pourraient échouer en raison d'un redimensionnement. Si un événement de redimensionnement est reçu, le mode complet -xrandr est activé. Pour désactiver même la vérification des événements, fournissez : -noxrandr.
"mode" vaut par défaut "resize", ce qui signifie créer un nouveau framebuffer redimensionné et espérer que tous les visionneuses puissent gérer le changement. "newfbsize" signifie d'abord déconnecter tous les visionneuses qui ne prennent pas en charge l'encodage VNC NewFBSize, puis redimensionner le framebuffer. "exit" signifie déconnecter tous les clients visionneuses, puis terminer x11vnc.

-rotate chaîne

Faire pivoter et/ou retourner la vue du framebuffer exportée par VNC. Cette transformation est indépendante de XRANDR et est effectuée par logiciel en mémoire principale et peut donc être plus lente. Ce mode pourrait être utile sur un appareil portable avec des modes portrait ou paysage qui ne correspondent pas à l'ordre des lignes de balayage du framebuffer réel. La chaîne peut être :
x retournement le long de l'axe x y retournement le long de l'axe y xy retournement le long des axes x et y +90 rotation de 90 degrés dans le sens des aiguilles d'une montre -90 rotation de 90 degrés dans le sens inverse des aiguilles d'une montre +90x rotation de 90 degrés dans le sens horaire, puis retournement le long de x +90y rotation de 90 degrés dans le sens horaire, puis retournement le long de y
ceux-ci donnent toutes les rotations et réflexions possibles.
Alias : identique à xy : yx, +180, -180, 180 identique à -90 : +270, 270 identique à +90 : 90, (idem pour 90x, 90y)
Comme -scale, cette transformation est appliquée à la toute fin de toute chaîne de transformations de framebuffer, donc toutes les options avec des géométries, par exemple -blackout, -clip, etc. sont relatives au X original (ou -rawfb) framebuffer, pas au dernier envoyé aux visionneuses VNC.
Si vous ne voulez pas que la forme du curseur soit tournée, préfixez la chaîne avec "nc:", par exemple "nc:+90", "nc:xy", etc.

-padgeom LxH

Chaque fois qu'un nouveau vncviewer se connecte, le framebuffer est remplacé par un faux framebuffer noir uni de géométrie LxF. Peu de temps après, le framebuffer est remplacé par le vrai. Ceci est destiné à être utilisé avec des vncviewers qui ne prennent pas en charge NewFBSize et dont on veut s'assurer que la géométrie initiale du visionneur sera suffisamment grande pour gérer tous les redimensionnements ultérieurs (par exemple, sous -xrandr, -remote id:windowid, mise à l'échelle, etc.)
En mode -unixpw, cela définit la taille de l'écran de connexion. Utilisez "once:LxH" pour ignorer padgeom une fois l'écran de connexion configuré.

-o journal

Écrire les messages stderr dans le fichier journal au lieu du terminal. Identique à "-logfile fichier". Pour ajouter au fichier, utilisez "-oa fichier" ou "-logappend fichier". Si journal contient la chaîne "%VNCDISPLAY", elle est développée en l'affichage vnc (le nom peut devoir être deviné.) "%HOME" fonctionne aussi.

-flag fichier

Écrire la chaîne "PORT=NNNN" (par exemple PORT=5900) dans fichier en plus de stdout. Cette option peut être utile à un script wrapper pour détecter quand x11vnc est prêt.

-rmflag fichier

Supprimer fichier à la sortie pour signaler quand x11vnc est terminé. Le fichier est créé au démarrage s'il n'existe pas déjà ou si fichier est préfixé par "create:". Si le fichier est créé, le PID de x11vnc y est placé. Sinon, le contenu du fichier n'est pas modifié. Utilisez le préfixe "nocreate:" pour empêcher la création.

-rc nomfichier

Utiliser nomfichier au lieu de $HOME/.x11vncrc comme fichier rc.

-norc

Ne pas traiter aucun fichier .x11vncrc pour les options.

-env VAR=VALEUR

Définir la variable d'environnement 'VAR' à la valeur 'VALEUR' au démarrage de x11vnc. C'est une utilité pratique pour éviter les scripts wrappers, etc. pour définir la variable d'environnement. Vous pouvez spécifier autant de ces options que nécessaire sur la ligne de commande.

-prog /chemin/vers/x11vnc

Définir le chemin complet du programme x11vnc pour les cas où il ne peut pas être déterminé à partir de argv[0] (par exemple, tcpd/inetd)

-h, -help

Afficher ce texte d'aide. -?, -opts N'afficher que les options x11vnc.

-V, -version

Afficher la version du programme et la date de dernière modification.

-license

Afficher les informations de licence. Identique à -copying et -warranty.

-dbg

Au lieu de quitter après le nettoyage, exécuter un simple "shell de débogage de crash" lorsque des erreurs fatales sont interceptées.

-q, -quiet

Être silencieux en imprimant moins d'informations sur stderr. (utiliser -noquiet pour annuler un précédent -quiet.)
L'option -quiet n'élimine pas toutes les informations, elle les réduit seulement. Elle est ignorée dans la plupart des modes d'utilisation auxiliaires, par exemple -storepasswd. Pour éliminer toute sortie, utilisez : 2>/dev/null 1>&2, etc.

-v, -verbose

Afficher plus d'informations sur stderr.

-bg

Passer en arrière-plan après la configuration de l'écran. Les messages sur stderr sont perdus sauf si -o logfile est utilisé. Quelque chose comme ceci pourrait être utile dans un script :
port=`ssh -t $host "x11vnc -display :0 -bg" | grep PORT`
port=`echo "$port" | sed -e 's/PORT=//'`
port=`expr $port - 5900`
vncviewer $host:$port

-modtweak, -nomodtweak

L'option -modtweak tente automatiquement d'ajuster les modificateurs AltGr et Shift pour les claviers de langues différentes entre le client et l'hôte. Sinon, seule une seule pression/relâchement de touche d'un code de touche est simulé (c'est-à-dire en ignorant l'état des modificateurs : cela fonctionne généralement pour des claviers identiques). Également utile pour résoudre les cas où un Keysym est lié à plusieurs touches (par exemple, "<" + ">" et "," + touches "<"). Par défaut : -modtweak
Si vous rencontrez des problèmes avec les touches et -xkb ou -noxkb, et que des choses similaires n'aident pas, essayez -nomodtweak.
Sur certains systèmes HP-UX, il a été noté qu'ils ont un mappage de touches étrange où un seul code de touche aura un Keysym, par exemple "#", jusqu'à trois fois. Vous pouvez vérifier via "xmodmap -pk" ou l'option -dk. L'échec se manifeste lorsque vous essayez de taper "#" et que vous obtenez "3". Si vous rencontrez ce problème, essayez de définir la variable d'environnement MODTWEAK_LOWEST=1 pour voir si cela aide.

-xkb, -noxkb

En mode modtweak, utilisez l'extension XKEYBOARD (si l'affichage X la prend en charge) pour ajuster les modificateurs. C'est puissant et devrait être essayé s'il y a encore des problèmes de mappage de clavier en utilisant -modtweak seul. Par défaut, on vérifie si certains keysyms courants, par exemple !, @, [, ne sont accessibles qu'en mode -xkb et, si c'est le cas, on active automatiquement le mode. Pour désactiver cette détection automatique, utilisez -noxkb.
Lorsque le mode -xkb est actif, vous pouvez définir ces variables d'environnement. Elles ne s'appliquent que lorsqu'il y a une ambiguïté quant à la touche à choisir (c'est-à-dire que le mappage n'est pas un à un). NOKEYHINTS=1 : pour les frappes ascii hautes, n'utilisez pas les indices de score enregistrés lorsque la touche a été enfoncée. NOANYDOWN=1 : pour les frappes hautes, ne cherchez pas parmi les touches actuellement enfoncées. KEYSDOWN=N : mémorisez les N dernières touches enfoncées pour le départage lorsqu'une frappe haute arrive.

-capslock

En mode -modtweak (par défaut) ou -xkb, si un keysym dans la plage A-Z arrive, vérifiez auprès du serveur X si le verrouillage majuscules (Caps_Lock) est activé. Si c'est le cas, n'appuyez pas artificiellement sur Maj pour générer le keysym. Cela permettra à la touche CapsLock de se comporter correctement dans certaines circonstances : notamment lorsque *à la fois* la machine cliente VNC et le serveur X x11vnc sont en état CapsLock activé. Si un côté a CapsLock activé et l'autre désactivé et que le clavier ne se comporte pas comme vous le pensez, vous devriez corriger les états de CapsLock (astuce : appuyer sur CapsLock à l'intérieur et à l'extérieur de la fenêtre du client peut aider à basculer les deux vers l'état correct). Cependant, pour de meilleurs résultats, n'utilisez pas cette option, mais plutôt *activez uniquement* CapsLock du côté du client VNC (c'est-à-dire en appuyant sur CapsLock en dehors de la fenêtre du client, voir aussi -skip_lockkeys ci-dessous). Essayez également -nomodtweak pour une solution de contournement possible.

-skip_lockkeys, -noskip_lockkeys

Faire en sorte que x11vnc ignore tous les keysyms Caps_Lock, Shift_Lock, Num_Lock, Scroll_Lock reçus des clients. L'idée est que vous appuyez sur Caps_Lock du côté du client VNC, mais que cela ne change pas l'état de verrouillage dans le serveur X de x11vnc. Néanmoins, vos lettres capitales arrivent via le réseau et sont appliquées correctement au serveur X de x11vnc. Notez que ce mode ne fera probablement pas ce que vous attendez en mode -nomodtweak. De plus, une astuce pour les chiffres KP_n est toujours effectuée dans ce mode : ils sont mappés sur des keysyms de chiffres normaux. Voir aussi -capslock ci-dessus. Par défaut : -noskip_lockkeys.

-skip_keycodes string

Ignorer la liste de keycodes décimaux séparés par des virgules. Peut-être s'agit-il de keycodes qui ne sont pas sur votre clavier, mais que votre serveur X pense exister. S'applique actuellement uniquement au mode -xkb. Utilisez cette option pour aider x11vnc dans le problème inverse qu'il essaie de résoudre : Keysym -> Keycode(s) lorsqu'il y a des ambiguïtés (plusieurs Keycodes par Keysym). Exécutez 'xmodmap -pk' pour voir votre mappage de clavier. Exemple : "-skip_keycodes 94,114"

-sloppy_keys

Option expérimentale qui tente de corriger certains comportements de frappe "imprécis". Par exemple, si vous appuyez sur Maj+Touche au client, puis que vous relâchez Maj avant la Touche, cela pourrait générer des caractères indésirables supplémentaires (généralement uniquement entre des claviers de langues différentes). Utilisez cette option uniquement si vous observez des problèmes avec certaines frappes.

-skip_dups, -noskip_dups

Certains clients VNC envoient des événements de touche répétés impossibles, par exemple, touche enfoncée, touche enfoncée, touche relâchée, touche relâchée, tous pour la même touche, ou 20 touches enfoncées d'affilée pour la même touche modificatrice ! Définir -skip_dups signifie ignorer ces doublons et traiter uniquement le premier événement. Remarque : certains clients VNC supposent qu'ils peuvent envoyer des touches enfoncées sans les touches relâchées correspondantes, vous ne devriez donc pas définir cette option pour ces clients (symptôme : certaines touches ne se répètent pas automatiquement). Par défaut : -noskip_dups

-add_keysyms, -noadd_keysyms

Si un Keysym est reçu d'un client VNC et que ce Keysym n'existe pas dans le serveur X, ajoutez le Keysym au mappage du clavier du serveur X sur une touche inutilisée. Les Keysyms ajoutés seront supprimés périodiquement et également lorsque x11vnc se terminera. Par défaut : -add_keysyms

-clear_mods

Au démarrage et à la sortie, effacez les touches modificatrices en envoyant KeyRelease pour chacune d'elles. Les modificateurs de verrouillage sont ignorés. Utilisé pour effacer l'état si l'affichage a accidentellement été laissé avec des touches enfoncées.

-clear_keys

Comme -clear_mods, sauf qu'il essaie de relâcher TOUTES les touches enfoncées. Notez que cette option et -clear_mods peuvent interférer avec une personne tapant sur le clavier physique.

-clear_all

Comme -clear_keys, sauf qu'il essaie également de relâcher les verrous CapsLock, NumLock, etc.

-remap string

Lire les remappages de Keysym à partir du fichier nommé string. Le format est une paire de Keysyms par ligne (peut être un nom ou une valeur hexadécimale) séparés par un espace. Si aucun fichier nommé string n'existe, il est interprété comme suit : key1-key2,key3-key4,... Voir le fichier d'en-tête <X11/keysymdef.h> pour une liste de noms de Keysym, ou utiliser xev(1).
Pour mapper une touche à un clic de bouton, utilisez les Keysyms fictifs "Button1", ..., etc. Par exemple : "-remap Super_R-Button2" (utile pour coller sur un ordinateur portable)
Je les utilise si la machine que je visualise depuis n'a pas de molette de défilement ou si je n'aime pas utiliser celle qu'elle a :
-remap Super_R-Button4,Menu-Button5 -remap KP_Add-Button4,KP_Enter-Button5
le premier serait utilisé sur un PC, le second sur un MacBook. De cette façon, ces touches peu utilisées peuvent être utilisées pour générer des sauts plus importants que ceux fournis par les flèches Haut et Bas. On peut ainsi parcourir plus rapidement du texte ou des pages Web (surtout si la détection de défilement de x11vnc est active.)
Utilisez Button44, Button12, etc. pour plusieurs clics.
Pour désactiver un keysym (c'est-à-dire le rendre impossible à injecter), remappez-le sur "NoSymbol" ou "None".
Touches mortes : les touches "mortes" (ou silencieuses, muettes) sont des touches qui ne produisent pas de caractère mais doivent être suivies d'une 2ème frappe. Ceci est souvent utilisé pour accentuer les caractères, par exemple pour mettre "`" au-dessus de "a" en appuyant sur la touche morte puis sur "a". Notez que cette interprétation ne fait pas partie du noyau X11, il appartient à la boîte à outils ou à l'application de décider comment réagir à la séquence. Les noms X11 pour ces keysyms sont "dead_grave", "dead_acute", etc. Cependant, certains clients VNC envoient les keysyms "grave", "acute" à la place, désactivant ainsi l'accentuation. Pour contourner cela, -remap peut être utilisé. Par exemple "-remap grave-dead_grave,acute-dead_acute"
Par commodité, "-remap DEAD" applique les remappages suivants :

g grave-dead_grave
a acute-dead_acute
c asciicircum-dead_circumflex
t asciitilde-dead_tilde
m macron-dead_macron
b breve-dead_breve
D abovedot-dead_abovedot
d diaeresis-dead_diaeresis
o degree-dead_abovering
A doubleacute-dead_doubleacute
r caron-dead_caron
e cedilla-dead_cedilla
Si vous ne voulez qu'un sous-ensemble, utilisez l'étiquette de la première lettre, par exemple "-remap DEAD=ga" pour obtenir les deux premiers. Des remappages supplémentaires peuvent également être fournis par des virgules, par exemple "-remap DEAD=ga,Super_R-Button2". Enfin, "DEAD=missing" signifie appliquer tous les remappages ci-dessus tant que le membre de gauche n'est pas déjà dans le mappage de touches X11.

-norepeat, -repeat

L'option -norepeat désactive la répétition automatique des touches du serveur X lorsque des clients VNC sont connectés et que l'entrée clavier VNC n'est pas inactive pendant plus de 5 minutes. Cela permet de contourner un bug de répétition de frappes (déclenché par de longs délais de traitement entre les événements de touche enfoncée et de touche relâchée : soit en raison de changements d'écran importants, soit d'une latence élevée). Par défaut : -norepeat
Vous pouvez définir la variable d'environnement X11VNC_IDLE_TIMEOUT au nombre de secondes d'inactivité souhaité (5 minutes = 300 secondes).
Remarque : votre côté client VNC fera probablement de la répétition automatique, donc ce n'est pas une perte à moins que quelqu'un ne soit simultanément sur l'affichage X réel.
Utilisez "-norepeat N" pour définir le nombre de fois que norepeat sera réinitialisé si quelque chose d'autre (par exemple, le gestionnaire de session X) l'annule. La valeur par défaut est 2. Utilisez une valeur négative pour des réinitialisations illimitées.

-nofb

Ignorer le framebuffer vidéo : traiter uniquement le clavier et le pointeur. Destiné à être utilisé avec les configurations double écran Win2VNC et x2vnc.

-nobell

Ne pas surveiller les événements XBell. (aucun bip ne sera entendu) Remarque : la surveillance XBell nécessite l'extension XKEYBOARD.

-nosel

Ne pas gérer l'échange de la sélection/buffer de copie X entre les clients VNC et le serveur X.

-noprimary

Ne pas interroger la sélection PRIMARY pour les changements à renvoyer aux clients. (PRIMARY est toujours défini sur les changements reçus, cependant).

-nosetprimary

Ne pas définir la sélection PRIMARY pour les changements reçus des clients VNC.

-noclipboard

Ne pas interroger la sélection CLIPBOARD pour les changements à renvoyer aux clients. (CLIPBOARD est toujours défini sur les changements reçus, cependant).

-nosetclipboard

Ne pas définir la sélection CLIPBOARD pour les changements reçus des clients VNC.

-seldir string

Si la chaîne de direction est "send", n'envoyer la sélection qu'aux clients, et si c'est "recv", ne la recevoir que des clients. Pour contourner le problème des applications qui définissent la sélection trop fréquemment et perturbent l'autre extrémité. Vous pouvez en fait fournir une liste de directions séparées par des virgules, y compris "debug" pour activer la sortie de débogage.

-cursor [mode], -nocursor

Définit la manière dont la forme du curseur de la souris (petite icône à l'emplacement du pointeur de la souris) doit être gérée. La chaîne « mode » est facultative et est décrite ci-dessous. Par défaut, une forme de curseur est affichée. La méthode dépend du spectateur VNC et du serveur X. Utilisez -nocursor pour désactiver complètement les formes de curseur.
Certains spectateurs VNC prennent en charge les extensions TightVNC CursorPosUpdates et CursorShapeUpdates (réduit le trafic réseau en n'ayant pas à envoyer l'image du curseur chaque fois que le pointeur est déplacé), auquel cas ces extensions sont utilisées (voir -nocursorshape et -nocursorpos ci-dessous pour désactiver). Pour les autres spectateurs, la forme du curseur est écrite directement dans la framebuffer chaque fois que le pointeur est déplacé ou modifié et est envoyée avec les autres mises à jour de la framebuffer. Dans ce cas, il y aura un décalage entre le pointeur du spectateur VNC et la position du curseur distant.
Si l'affichage X prend en charge la récupération des informations de forme du curseur à partir du serveur X, alors le mode par défaut est d'utiliser ce mode. Sur Solaris, cela peut être fait avec l'extension SUN_OVL en utilisant -overlay (voir également l'option -overlay_nocursor). Un schéma de superposition similaire est utilisé sur IRIX. Xorg (par exemple, Linux) et les serveurs Solaris Xsun récents prennent en charge l'extension XFIXES pour récupérer la forme exacte du curseur à partir du serveur X. Si XFIXES est présent, il est préféré à Overlay et est utilisé par défaut (voir -noxfixes ci-dessous). Cela peut être désactivé avec -nocursor, ainsi qu'avec certaines valeurs de l'option « mode » ci-dessous.
Notez que sous XFIXES, les curseurs avec transparence (canal alpha) ne seront généralement pas représentés exactement et vous pourriez préférer Overlay. Voir également les options -alphacut et -alphafrac ci-dessous comme facteurs de correction pour tenter d'améliorer la situation des curseurs avec transparence pour un thème donné.
La chaîne « mode » peut être utilisée pour affiner l'affichage des formes de curseur. Elle peut être utilisée de différentes manières :
« -cursor arrow » - affiche simplement la flèche standard, rien de plus, rien de moins.
« -cursor none » - identique à « -nocursor »
« -cursor X » - lorsque le curseur apparaît sur la fenêtre racine, dessine la forme X familière. Certains environnements de bureau comme GNOME masquent complètement la fenêtre racine, donc cela ne fonctionnera pas. Essayez « X1 », etc., pour tenter de décaler la profondeur de l'arbre. Sur des liaisons à latence élevée ou des machines lentes, il y aura un décalage temporel entre la position attendue et la position réelle du curseur.
« -cursor some » - comme « X », mais utilise des heuristiques supplémentaires pour tenter de deviner si la fenêtre devrait avoir un curseur de redimensionnement semblable à celui du gestionnaire de fenêtres ou un curseur de type « I-beam » pour la saisie de texte. C'est un hack complet, mais il peut être utile dans certaines situations car il fournit un peu plus d'informations sur la forme du curseur.
« -cursor most » - tente d'afficher autant de curseurs que possible. Souvent, cela sera identique à « some », sauf si l'affichage dispose de visuels de superposition ou d'extensions XFIXES. Sur Solaris et IRIX, si XFIXES n'est pas disponible, le mode -overlay sera tenté.

-cursor_drag

Affiche les changements de forme du curseur même lorsque la souris est déplacée avec un bouton de souris enfoncé. C'est utile si vous voulez pouvoir voir les icônes de curseur de type glisser-déposer, etc.

-arrow n

Choisit un curseur « flèche » alternatif parmi un ensemble d'options courantes. n peut être de 1 à 6. Par défaut : 1. Ignoré en mode de capture de curseur XFIXES.

-noxfixes

N'utilise pas l'extension XFIXES pour dessiner la forme exacte du curseur, même si elle est disponible.
Note : Pour contourner un crash dans Xorg 1.5 et versions ultérieures, certaines personnes ont eu besoin d'utiliser -noxfixes. Le crash de Xorg s'est produit juste après la connexion à un gestionnaire d'affichage (par exemple, GDM). À partir de x11vnc 0.9.9, il essaie d'éviter automatiquement d'utiliser XFIXES jusqu'à ce qu'il soit sûr qu'un gestionnaire de fenêtres est en cours d'exécution. Voir l'option -reopen pour plus d'informations et comment utiliser X11VNC_AVOID_WINDOWS=never pour la désactiver.

-alphacut n

Lors de l'utilisation de l'extension XFIXES pour la forme du curseur, les curseurs avec transparence ne seront généralement pas affichés exactement (mais les curseurs opaques le seront). Cette option définit n comme seuil pour les curseurs qui ont de la transparence (canal alpha avec des valeurs allant de 0 à 255). Tout pixel de curseur avec une valeur alpha inférieure à n devient complètement transparent. Sinon, le pixel est complètement opaque. Par défaut : 240

-alphafrac fraction

Avec le seuil de -alphacut, certains curseurs deviendront presque complètement transparents car leurs valeurs alpha ne sont pas suffisamment élevées. Pour ces curseurs, ajustez le seuil alpha jusqu'à ce que la fraction des pixels avec un canal alpha non nul devienne opaque. Par défaut : 0,33

-alpharemove

Par défaut, les pixels des curseurs XFIXES avec transparence ont le facteur alpha multiplié par les valeurs de couleur RVB (c'est-à-dire correspondant au mélange du curseur avec un arrière-plan noir). Spécifiez cette option pour supprimer le facteur alpha. (utile pour les curseurs semi-transparents de couleur claire).

-noalphablend

En mode XFIXES, n'envoyez pas les données du canal alpha du curseur à LibVNCServer. Par défaut, elles sont envoyées. L'effet d'alphablending ne sera visible qu'en mode -nocursorshape ou pour les clients dont CursorShapeUpdates est désactivé. (Cependant, il existe un hack pour 32bpp avec une profondeur de 24, il utilise les 8 bits supplémentaires pour stocker la transparence du curseur à utiliser avec un vncviewer piraté qui applique la transparence localement. Voir la FAQ pour plus d'informations).

-nocursorshape

N'utilise pas l'extension TightVNC CursorShapeUpdates, même si les clients la prennent en charge. Voir -cursor ci-dessus.

-cursorpos, -nocursorpos

L'option -cursorpos permet d'envoyer la position du curseur X à tous les clients vnc qui prennent en charge l'extension TightVNC CursorPosUpdates. Les autres clients pourront voir les mouvements du pointeur. Par défaut : -cursorpos

-xwarppointer, -noxwarppointer

Déplace le pointeur avec XWarpPointer(3X) au lieu de l'extension XTEST. Utilisez ceci comme solution de contournement si le mouvement du pointeur se comporte incorrectement, par exemple sur des écrans tactiles ou d'autres configurations non standard.
Il est également parfois nécessaire sur les écrans XINERAMA et est activé par défaut si XINERAMA est détecté comme actif. Pour empêcher cela, utilisez -noxwarppointer.

-always_inject

Même s'il n'y a pas de déplacement (dx = dy = 0) pour un événement de souris VNC, forcez le pointeur à la position x,y indiquée de toute façon. Les kits d'outils graphiques récents (2009) (gnome) ont des problèmes avec la méthode d'injection d'entrée de souris d'origine de x11vnc. La méthode d'injection d'entrée de souris de x11vnc a donc été modifiée. Pour retrouver le comportement ANCIEN, utilisez cette option : -always_inject. Ensuite, x11vnc forcera toujours le positionnement de la souris à la position x,y, même si cette position n'a pas changé depuis l'événement d'entrée VNC précédent.
Le premier endroit où ce problème a été remarqué était dans le terminal gnome : si vous appuyiez et relâchiez le bouton 3 de la souris, un menu apparaissait puis son premier élément « Nouvelle fenêtre de terminal » était activé. C'est parce que x11vnc injectait la position de la souris deux fois : une fois lors de ButtonPress et une fois lors de ButtonRelease. Le kit d'outils interprétait la deuxième fois comme un mouvement de souris, même si la souris n'avait pas bougé. Par défaut, x11vnc essaie donc d'éviter d'injecter la deuxième fois.
Notez qu'avec le nouveau comportement par défaut, x11vnc sera inconscient des applications qui déplacent le pointeur (warp) ou de l'utilisateur qui le déplace sur l'écran physique. Il pourrait donc, par exemple, injecter ButtonRelease à la mauvaise position. Si cela (ou des scénarios similaires) cause des problèmes dans votre environnement, spécifiez -always_inject pour l'ancienne méthode.

-buttonmap string

Chaîne pour remapper les boutons de la souris. Format : IJK-LMN, cela mappe les boutons I -> L, etc., par exemple, -buttonmap 13-31
Les pressions sur les boutons peuvent également être mappées sur des frappes : remplacez un chiffre de bouton à droite du trait d'union par :<sym>: ou :<sym1>+<sym2>: etc. pour plusieurs touches. Par exemple, si la machine de visualisation a une molette de souris (boutons 4 5) mais que le côté x11vnc n'en a pas, voici comment faire défiler :
-buttonmap 12345-123:Prior::Next:
-buttonmap 12345-123:Up+Up+Up::Down+Down+Down:
Voir le fichier d'en-tête <X11/keysymdef.h> pour une liste des Keysyms, ou utilisez le programme xev(1). Note : le mappage des clics de boutons sur des Keysyms peut ne pas fonctionner si -modtweak ou -xkb est nécessaire pour le Keysym.
Si vous incluez un modificateur comme "Shift_L", l'état haut/bas du modificateur est basculé, par exemple pour envoyer "The" utilisez :Shift_L+t+Shift_L+h+e: (le premier est shift enfoncé et le second est shift relâché). (note : l'état initial du modificateur est ignoré et non réinitialisé) Pour inclure des événements de bouton, utilisez "Button1", ... etc.
-buttonmap ne fonctionne actuellement pas sur la console MacOSX ou en mode -rawfb.
Solution : utilisez -buttonmap IJ...-LM...=n pour limiter le nombre de boutons de souris à n, par exemple 123-123=3. Cela empêchera x11vnc de planter si le serveur X signale qu'il y a 5 boutons (4/5 molette de défilement), mais qu'il n'y en a réellement que 3.

-nodragging

Ne met pas à jour l'affichage pendant les événements de glissement de souris (bouton de souris enfoncé). Améliore considérablement la réactivité sur les configurations lentes, mais vous perdez tout retour visuel pour les glissements, la sélection de texte et certaines traversées de menus. Cela remplace tout réglage de -pointer_mode.

-ncache n

Schéma de mise en cache côté client. Une mémoire de framebuffer n (un entier) fois supérieure à celle de l'affichage complet est allouée sous la framebuffer réelle pour mettre en cache le contenu de l'écran pour une récupération rapide. Ainsi, une framebuffer de L x H est étendue à une framebuffer de L x (n+1)*H. Utilisez 0 pour désactiver.
Le n est en fait facultatif, la valeur par défaut est 10.
Pour ceci et les autres options -ncache* ci-dessous, vous pouvez abréger « -ncache » en « -nc ». De plus, « -nonc » est identique à « -ncache 0 »
Ceci est une option expérimentale, actuellement implémentée de manière maladroite en ce sens que dans le Visionneur VNC, vous pouvez voir le contenu du cache de pixels si vous faites défiler, etc. Vous devrez donc configurer les choses de manière à ne pas voir cette zone. Si cette méthode réussit, les modifications nécessaires pour que les clients le fassent de manière moins maladroite seront étudiées.
Le visionneur SSVNC fait un bon travail pour masquer automatiquement la région du cache de pixels. Ou utilisez l'option -ycrop de SSVNC pour masquer explicitement la région.
Notez que ce mode consomme une énorme quantité de mémoire, tant du côté du serveur x11vnc que du côté du Visionneur VNC. Si n=2, la quantité de RAM utilisée est approximativement triplée pour x11vnc et le Visionneur VNC. En règle générale, notez que 1280x1024 avec une profondeur de 24 pèse environ 5 Mo de données de pixels.
Pour une réponse raisonnable lors du passage de 4 à 6 grandes fenêtres (par exemple, un navigateur Web) une valeur n de 6 à 12 est recommandée. (c'est exact : ~10 fois plus de mémoire...)
En raison de la manière dont le stockage de fond des fenêtres et les saveunders sont implémentés, n doit être pair. Il sera incrémenté de 1 s'il ne l'est pas.
Ce mode fonctionne également pour le MacOS X natif, mais peut ne pas être aussi efficace que la version X. Cela est dû à un certain nombre de facteurs, notamment le compositing avec ombre portée qui laisse des zones supplémentaires à réparer (voir -ncache_pad). Une autre raison est que les animations d'iconisation des fenêtres doivent être évitées (voir -macicontime). Il semble que le mode d'animation 'Scale' donne de meilleurs résultats que celui 'Genie'. De plus, la détection des événements de fenêtre n'est pas aussi précise que la version X.

-ncache_cr

En mode -ncache, essayez de réaliser des déplacements/glissements de fenêtres opaques en copyrect au lieu de cadres filaires (cela peut induire des erreurs de peinture). Le cadre filaire sera toujours utilisé lors du déplacement d'une fenêtre dont le save-under n'a pas encore été défini ou a été invalidé.
Certains visionneurs VNC offrent une meilleure réponse que d'autres avec cette option. Sur Unix, le visionneur realvnc offre des glissements plus fluides que le visionneur tightvnc. La réponse peut également être hachée si la machine côté serveur est trop lente.
Parfois, sur des connexions modem très lentes, cela apporte une amélioration car aucune donnée de pixels (pas même l'animation de la boîte) n'est envoyée pendant le glissement.

-ncache_no_moveraise

En mode -ncache, ne supposez pas que le déplacement d'une fenêtre entraînera sa mise au premier plan par le gestionnaire de fenêtres. Par défaut, on suppose que c'est le cas, et donc au début de tout déplacement de fenêtre en cadre filaire, etc., la fenêtre sera poussée au premier plan dans le visionneur VNC.

-ncache_no_dtchange

En mode -ncache, n'essayez pas de deviner quand le bureau (viewport) passe à un autre (c'est-à-dire une autre zone de travail). Par défaut, on essaie de deviner et, une fois détecté, on essaie de rendre la transition plus fluide.

-ncache_no_rootpixmap

En mode -ncache, n'essayez pas de capturer l'arrière-plan du bureau pour l'utiliser dans la prédiction ou la reconstruction des saveunders des fenêtres.

-ncache_keep_anims

En mode -ncache, n'essayez pas de désactiver les animations du gestionnaire de fenêtres et autres effets (qui dégradent généralement les performances de ncache ou provoquent des erreurs de peinture). Par défaut, on essaie de les désactiver sur KDE (mais pas sur GNOME) lorsque des clients VNC sont connectés.
Pour d'autres gestionnaires de fenêtres ou bureaux qui fournissent des animations, des effets, du compositing, de la translucidité, etc. qui interfèrent avec la méthode -ncache, vous devrez les désactiver manuellement.

-ncache_old_wm

En mode -ncache, activez certaines heuristiques pour les gestionnaires de fenêtres de style ancien tels que fvwm et twm.

-ncache_pad n

En mode -ncache, remplissez chaque fenêtre avec n pixels pour les rectangles de mise en cache. Cela peut être utilisé pour tenter d'améliorer la situation avec les ombres portées ou d'autres compositing (par exemple, le gestionnaire de fenêtres de MacOS X), bien que cela puisse aggraver les choses. La valeur par défaut est 0 sur Unix et 24 sur MacOS X.

-debug_ncache

Activez la sortie de débogage et de profilage sous -ncache.

-wireframe [str], -nowireframe

Essayez de détecter les déplacements ou redimensionnements de fenêtres lorsqu'un bouton de souris est maintenu enfoncé et affichez un cadre filaire au lieu de la fenêtre opaque complète. Ceci est basé entièrement sur des heuristiques et peut ne pas toujours fonctionner : cela dépend de votre gestionnaire de fenêtres et même de la manière dont vous déplacez les choses. Voir -pointer_mode ci-dessous pour une discussion sur le problème de "ralentissement" que cela tente d'éviter. Par défaut : -wireframe
Alias plus courts : -wf [str] et -nowf
La valeur "str" est facultative et, bien sûr, est remplie de nombreux paramètres réglables pour ce schéma :
Format : shade,linewidth,percent,T+B+L+R,mod,t1+t2+t3+t4 Par défaut : 0xff,2,0,32+8+8+8,all,0.15+0.30+5.0+0.125
Si vous ne laissez rien entre les virgules : ",," la valeur par défaut est utilisée. Si vous ne spécifiez pas assez de virgules, les paramètres de fin sont définis sur leurs valeurs par défaut.
"shade" indique la "couleur" du cadre filaire, généralement une échelle de gris : 0-255, cependant pour 16 et 32bpp vous pouvez spécifier une couleur X rgb.txt (par exemple, "dodgerblue") ou une valeur > 255 est traitée comme RVB (par exemple, le rouge est 0xff0000). "linewidth" définit la largeur du cadre filaire en pixels. "percent" indique de ne pas appliquer le schéma de cadre filaire aux fenêtres dont la surface est inférieure à ce pourcentage de l'écran complet.
"T+B+L+R" indique quatre entiers pour la distance en pixels entre le pointeur et les bords Supérieur, Inférieur, Gauche ou Droit de la fenêtre pour considérer un cadre filaire. C'est une optimisation pour exclure rapidement une fenêtre du cadrage : réglez-les tous à zéro pour ne pas essayer l'optimisation (le défilement et la sélection de texte seront probablement plus lents).
"mod" spécifie si un clic de bouton enfoncé à l'intérieur de la fenêtre avec une touche modificatrice (Alt, Maj, etc.) enfoncée doit indiquer une opportunité de cadre filaire. Il peut s'agir de "0" ou "none" pour l'ignorer, de "1" ou "all" pour l'appliquer à n'importe quel modificateur, ou de "Shift", "Alt", "Control", "Meta", "Super", ou "Hyper" pour l'appliquer uniquement pour ce type de touche modificatrice.
"t1+t2+t3+t4" spécifie quatre temps flottants en secondes : t1 est le temps d'attente avant que le pointeur ne bouge, t2 est le temps d'attente avant que la fenêtre ne commence à bouger ou à être redimensionnée (pour certains gestionnaires de fenêtres, cela peut être assez long), t3 est le temps pendant lequel un cadre filaire est déplacé avant de repeindre la fenêtre. t4 est le temps minimum entre l'envoi des "animations" de cadre filaire. Si une liaison lente est détectée, ces valeurs peuvent être automatiquement modifiées pour s'adapter à une liaison lente.

-nowireframelocal

Par défaut, les mouvements de souris et les clics de boutons d'un utilisateur assis à l'affichage LOCAL sont surveillés pour les opportunités de cadre filaire (afin que les modifications soient envoyées efficacement aux clients VNC). Utilisez cette option pour désactiver ce comportement.

-wirecopyrect mode, -nowirecopyrect

Étant donné que le mécanisme -wireframe suit apparemment les fenêtres en mouvement avec précision, une optimisation peut être obtenue en indiquant aux visionneurs VNC de copier localement la région de fenêtre traduite. Il s'agit de l'encodage VNC CopyRect : la mise à jour du frame buffer n'a pas besoin d'envoyer les données d'image réelles.
Alias plus courts : -wcr [mode] et -nowcr
"mode" peut être "never" (identique à -nowirecopyrect) pour ne jamais essayer le copyrect, "top" signifie le faire uniquement si la fenêtre n'était pas couverte par d'autres fenêtres, et "always" signifie traduire la région initialement non obstruée (cela peut paraître étrange lorsque les morceaux restants arrivent, mais aide sur une liaison lente). Par défaut : "always"
Note : il peut y avoir des erreurs de peinture ou une réponse lente lors de l'utilisation de -scale vous pouvez donc vouloir désactiver CopyRect dans ce cas ("-wirecopyrect never" sur la ligne de commande ou par contrôle à distance. Ou vous pouvez également utiliser l'option de mise à l'échelle "-scale xxx:nocr").

-debug_wireframe

Active l'affichage des informations de débogage pour les heuristiques de cadre filaire. "-dwf" est un alias. Spécifiez plusieurs fois pour plus de sortie.

-scrollcopyrect mode, -noscrollcopyrect

Comme -wirecopyrect, mais utilise des heuristiques pour essayer de deviner si une fenêtre a fait défiler son contenu (verticalement ou horizontalement). Cela nécessite l'extension RECORD X pour "espionner" les applications X (actuellement pour certaines requêtes de protocole XCopyArea et XConfigureWindow X). Exemples : Appuyer sur <Retour> dans une fenêtre de terminal lorsque le curseur était en bas, le texte défile vers le haut d'une ligne. Appuyer sur la flèche <Bas> dans une fenêtre de navigateur Web, la page Web défile légèrement vers le haut. Ou faire défiler avec une barre de défilement ou une molette de souris.
Alias plus courts : -scr [mode] et -noscr
Ce schéma ne détectera pas toujours les défilements, mais lorsqu'il le fait, il y a une belle optimisation grâce à l'utilisation de l'encodage VNC CopyRect (voir -wirecopyrect). L'optimisation réduit le trafic réseau et la mise en mémoire tampon/copie du frame buffer X. D'un autre côté, cela peut induire des artefacts indésirables (par exemple, un curseur de terminal qui défile vers le haut alors qu'il ne devrait pas) ou d'autres erreurs de peinture (déchirure de fenêtre, regroupement, etc.). Ceux-ci sont automatiquement réparés en peu de temps. Si cela est inacceptable, désactivez la fonctionnalité avec -noscrollcopyrect.
Ruses de nettoyage d'écran : au moins pour les tests, il existe des "séquences de touches magiques" (à réaliser en moins de 1 seconde) pour aider à réparer les erreurs de peinture qui peuvent être observées lors de l'utilisation de ce mode :
3 Alt_L consécutifs : renvoyer l'écran entier, 4 Alt_L consécutifs : relire et renvoyer l'écran entier, 3 Super_L consécutifs : marquer l'écran entier pour sondage, 4 Super_L consécutifs : réinitialiser le contexte RECORD, 5 Super_L consécutifs : essayer d'envoyer un écran noir
note : Alt_L est la touche "Alt" Gauche (une seule touche) Super_L est la touche "Super" Gauche (drapeau Windows). Ce sont toutes deux des touches modificatrices, et donc ne devraient pas générer de caractères lorsqu'elles sont pressées seules. De plus, votre visionneur VNC peut avoir sa propre combinaison de touches ou son propre bouton de rafraîchissement.
"mode" peut être "never" (identique à -nosc
rollcopyrect) pour ne jamais essayer le copyrect, « keys » signifie essayer en réponse aux frappes seulement, « mouse » signifie essayer en réponse aux événements de la souris seulement, « always » signifie faire les deux. Par défaut : « always »
Note : il peut y avoir des erreurs de peinture ou une réponse lente lors de l'utilisation de -scale, vous pourriez donc vouloir désactiver CopyRect dans ce cas en utilisant « -scrollcopyrect never » sur la ligne de commande ou via le contrôle à distance. Ou vous pouvez également utiliser l'option de mise à l'échelle « -scale xxx:nocr ».

-scr_area n

Définit la surface minimale en pixels pour qu'un rectangle soit pris en compte par le schéma de détection -scrollcopyrect. Ceci afin d'éviter de perdre du temps sur de petits rectangles qui seraient rapidement mis à jour normalement. Par exemple, supposons qu'une application mette d'abord à jour la position de sa barre de défilement fine, puis décale le grand panneau qu'elle contrôlait. Nous voulons nous assurer de sauter la petite barre de défilement et d'obtenir le grand panneau. Par défaut : 60000

-scr_skip liste

Ignore la détection de défilement pour les applications correspondant à la liste séparée par des virgules de chaînes dans liste. Certaines applications implémentent leur défilement de manière étrange où XCopyArea, etc., s'applique également aux portions invisibles de la fenêtre : si nous CopyRect ces zones, cela donne une apparence horrible pendant le défilement et il peut y avoir des erreurs de peinture après le défilement. Soffice.bin est le pire coupable connu.
Utilisez « ## » pour indiquer le début de la classe d'application (par exemple, « ##XTerm ») et « ++ » pour indiquer le début du nom d'instance de l'application (par exemple, « ++xterm »). La chaîne à laquelle votre liste est comparée est de la forme « ^^WM_NAME##Class++Instance<même-pour-toutes-sous-fenêtres> » La commande « xlsclients -la » fournira ces informations.
Si un modèle est précédé de « KEY: », il s'applique uniquement aux défilements générés par les frappes (par exemple, la touche flèche vers le haut). S'il est précédé de « MOUSE: », il s'applique uniquement aux défilements induits par la souris (par exemple, glisser sur une barre de défilement). Par défaut : ##Soffice.bin,##StarOffice,##OpenOffice

-scr_inc liste

L'inverse de -scr_skip : cette liste est consultée en premier et s'il y a une correspondance, la fenêtre sera surveillée via RECORD pour les défilements, indépendamment de -scr_skip. Utilisez « -scr_skip * » pour ignorer tout ce qui ne correspond pas à votre -scr_inc. Utilisez « -scr_inc * » pour inclure tout.

-scr_keys liste

Pour la détection de défilement par frappe, appliquez uniquement les heuristiques RECORD à la liste de keysyms séparés par des virgules dans liste. Vous pourriez trouver que la surcharge de RECORD pour chacune de vos frappes perturbe trop la saisie, mais vous ne voulez pas la désactiver complètement avec « -scr mouse » et -scr_parms ne fonctionne pas ou est trop confus.
Les keysyms listés peuvent être numériques ou les noms de keysyms dans le fichier d'en-tête <X11/keysymdef.h> ou provenant du programme xev(1). Exemple : « -scr_keys Up,Down,Return ». On voudra probablement avoir des listes spécifiques aux applications (par exemple, pour les terminaux, etc.), mais c'est trop délicat à envisager pour le moment...
Si liste commence par le caractère « - », la liste est considérée comme une liste d'exclusion : tous les keysyms sauf ceux listés seront pris en compte. La chaîne spéciale « builtin » se développe en une liste interne de keysyms qui sont susceptibles de provoquer des défilements. D'ailleurs, par défaut, les touches modificatrices, Shift_L, Control_R, etc., sont ignorées car elles n'induisent presque jamais de défilement par elles-mêmes.

-scr_term liste

Encore une autre solution de contournement cosmétique. Appliquez les heuristiques de shell/terminal aux applications correspondant à la liste séparée par des virgules (identique à -scr_skip/-scr_inc). Par exemple, un élément transitoire agaçant sous la détection de défilement se produit si vous appuyez sur Entrée dans un terminal avec une fenêtre de texte pleine, le bloc de curseur de texte solide sera défilé vers le haut. Ainsi, pendant un court instant, il y aura deux (ou plus) curseurs de bloc à l'écran. Il existe des scénarios similaires (par exemple, une ligne de sortie est dupliquée).
Ces éléments transitoires sont induits par l'approximation de la détection de défilement (par exemple, elle détecte le défilement, mais pas le fait que le curseur en bloc ait été effacé juste avant le défilement). Dans presque tous les cas, ces erreurs transitoires sont réparées lorsque le véritable framebuffer X est consulté par l'interrogation normale. Mais elles sont distrayantes, donc ce que cette option fournit est une « marge » supplémentaire près du bas de la fenêtre du terminal : quelques lignes supplémentaires près du bas ne seront pas défilées, mais plutôt mises à jour à partir du framebuffer X réel. Cela réduit généralement les artefacts agaçants. Utilisez « none » pour désactiver. Par défaut : « term »

-scr_keyrepeat lo-hi

Si une touche est maintenue enfoncée (ou se répète rapidement) et que cela induit une séquence rapide de défilements (par exemple, maintenir enfoncée une touche flèche), la détection et la surcharge « scrollcopyrect » pourraient ne pas suivre. Une estimation du temps par défilement est effectuée et si cette estimation prédit un débit de défilement durable de touches par seconde entre « lo » et « hi », alors les touches répétées seront IGNORÉES pour maintenir le débit de défilement. Par exemple, votre répétition automatique de touches peut être de 25 touches/seconde, mais pour une grande fenêtre ou un lien lent, seulement 8 défilements par seconde peuvent être maintenus, alors environ 2 touches répétées sur 3 seront ignorées pendant cette période. Par défaut : « 4-20 »

-scr_parms chaîne

Définit divers paramètres pour le mode scrollcopyrect. Le format est similaire à celui de -wireframe et rempli de nombreux paramètres :
Format : T+B+L+R,t1+t2+t3,s1+s2+s3+s4+s5 Par défaut : 0+64+32+32,0.02+0.10+0.9,0.03+0.06+0.5+0.1+5.0
Si vous ne laissez rien entre les virgules : « ,, », la valeur par défaut est utilisée. Si vous ne spécifiez pas assez de virgules, les paramètres suivants sont définis sur leurs valeurs par défaut.
« T+B+L+R » indique quatre entiers pour la distance en pixels à laquelle le pointeur doit se trouver du bord Supérieur, Inférieur, Gauche ou Droit de la fenêtre pour que scrollcopyrect soit pris en compte. Si -wireframe se superpose, il a la priorité. Ceci est une optimisation pour exclure rapidement une fenêtre de la surveillance de scrollcopyrect : réglez-les tous à zéro pour ne pas essayer l'optimisation (les choses comme la sélection de texte seront probablement plus lentes).
« t1+t2+t3 » spécifie trois temps flottants en secondes qui s'appliquent à la détection de scrollcopyrect avec une entrée par *frappe* : t1 est le temps d'attente après une frappe avant le premier défilement, t2 est le temps pendant lequel continuer à chercher d'autres défilements après un défilement par frappe. t3 est la fréquence à laquelle essayer de mettre à jour les barres de défilement environnantes en dehors de la zone de défilement (0.0 pour désactiver)
« s1+s2+s3+s4+s5 » spécifie cinq temps flottants en secondes qui s'appliquent à la détection de scrollcopyrect avec une entrée par *souris* : s1 est le temps d'attente après qu'un bouton de souris a été pressé pour le premier défilement, s2 est le temps pendant lequel continuer à attendre des défilements supplémentaires après la détection du premier défilement par souris. s3 est la fréquence à laquelle essayer de mettre à jour les barres de défilement environnantes en dehors de la zone de défilement (0.0 pour désactiver). s4 est le temps pendant lequel mettre en tampon le mouvement du pointeur (pour essayer d'obtenir moins de défilements de souris, mais plus grands). s5 est le temps maximum passé à simplement mettre à jour la fenêtre de défilement sans mettre à jour le reste de l'écran.

-fixscreen chaîne

« Répare » périodiquement l'écran en fonction des paramètres dans chaîne. Espérons que vous n'aurez pas besoin de cette option, elle est destinée aux cas où les fonctionnalités -scrollcopyrect ou -wirecopyrect laissent trop d'erreurs de peinture, mais elle peut être utilisée dans n'importe quel scénario. Cette option effectue périodiquement des opérations coûteuses et la réponse interactive peut donc être réduite lorsqu'elle est activée. Vous pouvez utiliser 3 appuis successifs sur Alt_L (la touche « Alt » gauche) (comme décrit sous -scrollcopyrect) pour demander manuellement une nouvelle peinture de l'écran lorsque cela est nécessaire.
chaîne est une liste séparée par des virgules d'une ou plusieurs des options suivantes : « V=t », « C=t », « X=t », et « 8=t ». Dans ces options, « t » représente un temps en secondes (c'est un nombre flottant, même si l'on devrait généralement utiliser des valeurs > 2 pour éviter de gaspiller des ressources). V définit la fréquence à laquelle l'écran entier doit être envoyé aux spectateurs (c'est comme les 3 Alt_L). C définit le temps d'attente après un CopyRect avant de repeindre l'écran complet. X définit la fréquence à laquelle le framebuffer X11 complet doit être relu depuis le serveur X et envoyé aux spectateurs connectés. L'utilisation de X devrait être rare, veuillez signaler un bogue si vous constatez que vous en avez besoin. 8= s'applique uniquement au mode -8to24 : il définit la fréquence à laquelle les régions non par défaut de l'écran (par exemple, les fenêtres 8bpp) sont rafraîchies. Exemples : -fixscreen V=10 -fixscreen C=10

-debug_scroll

Active l'affichage des informations de débogage pour les heuristiques de défilement. « -ds » est un alias. Spécifiez-le plusieurs fois pour plus de sortie.

-noxrecord

Désactive toute utilisation de l'extension RECORD. Elle est actuellement utilisée par le schéma -scrollcopyrect et pour surveiller les saisies du serveur X.

-grab_buster, -nograb_buster

Certaines utilisations de l'extension RECORD peuvent laisser une petite fenêtre pour un blocage XGrabServer. Ceci se produit uniquement si l'application qui effectue la saisie du serveur entier s'attend à une entrée de souris ou de clavier avant de relâcher la saisie. Il s'agit généralement d'un gestionnaire de fenêtres. x11vnc prend soin d'éviter le problème, mais s'il est pris, x11vnc se figera. Sans -grab_buster, la seule solution est d'aller sur l'affichage physique et de fournir une entrée pour satisfaire l'application qui saisit. Ou tuer et redémarrer manuellement le gestionnaire de fenêtres si cela est faisable. Avec -grab_buster, x11vnc lancera un thread auxiliaire et si x11vnc semble bloqué dans une saisie après un certain temps (20-30 secondes), il injectera une entrée utilisateur : clics de souris, Échap, mouvement de souris, etc. pour tenter de briser la saisie. Si vous rencontrez beaucoup de blocages de saisie, veuillez signaler un bogue.

-debug_grabs

Active l'affichage des informations de débogage concernant le blocage XGrabServer() pour le mode -scrollcopyrect.

-debug_sel

Active l'affichage des informations de débogage concernant les sélections PRIMARY, CLIPBOARD et CUTBUFFER0.

-pointer_mode n

Divers schémas de mise à jour du mouvement du pointeur. « -pm » est un alias.
Le problème est que le mouvement du pointeur peut provoquer des changements rapides à l'écran : considérez les changements rapides lorsque vous faites glisser une grande fenêtre de manière opaque. Ni les routines d'interrogation d'écran et de compression vnc de x11vnc ni la bande passante vers les vncviewers ne peuvent suivre ces changements d'écran rapides : tout ralentira lors du glissement ou du défilement. Un schéma doit donc être utilisé pour "consommer" une grande partie de ces entrées du pointeur avant de réinterroger l'écran et d'envoyer des mises à jour du framebuffer. Le numéro de mode n peut être de 0 à 4 et sélectionne l'un des schémas décrits ci-dessous.
Notez que -wireframe et -scrollcopyrect__mode_s complètent -pointer_mode en détectant (et en améliorant) certaines périodes de "changement d'écran rapide".
n=0 : fait la même chose que -nodragging. (toute interrogation d'écran est suspendue si un bouton de la souris est enfoncé.)
n=1 : était le schéma original utilisé jusqu'à environ janvier 2004 : il saute simplement -input_skip événements clavier ou pointeur avant de réinterroger l'écran.
n=2 est un schéma amélioré : en observant le taux actuel d'événements d'entrée, il essaie de détecter s'il doit essayer de "consommer" des événements de pointeur supplémentaires avant de continuer.
n=3 est essentiellement un mode -nodragging dynamique : il détecte lorsque le mouvement de la souris s'est arrêté et rafraîchit ensuite l'affichage.
n=4 tente de mesurer les taux de réseau et la latence, le taux de lecture de la carte vidéo, et le nombre de tuiles modifiées à l'écran. À partir de cela, il essaie agressivement de pousser des "images" d'écran lorsqu'il décide qu'il dispose de suffisamment de ressources pour le faire. PAS TERMINÉ.
La valeur par défaut de n est 2. Notez que les modes 2, 3, 4 sauteront les événements clavier -input_skip (mais ne compteront pas les événements pointeur). Notez également que ces modes ne sont pas disponibles en mode -threads qui a son propre mécanisme de gestion des événements pointeur.
Pour tester les différents modes de pointeur afin de voir lequel offre la meilleure réponse pour votre utilisation, il est pratique d'utiliser la fonction de télécommande, par exemple "x11vnc -R pm:4" ou l'interface graphique tcl/tk (Réglage -> pointeur_mode -> n).

-input_skip n

Pour la gestion du pointeur en mode non threadé : essayez de lire n événements d'entrée utilisateur avant de scanner l'affichage. n < 0 signifie agir comme s'il y avait toujours une entrée utilisateur. Par défaut : 10

-allinput

Faire en sorte que x11vnc lise et traite toutes les entrées client disponibles avant de continuer.

-input_eagerly

Similaire à -allinput mais utilise le mécanisme handleEventsEagerly intégré à LibVNCServer.

-multiptr

Active la prise en charge des périphériques d'entrée par client. Chaque client obtiendra son propre curseur et son propre focus clavier.

-speeds rd,bw,lat

x11vnc essaie d'estimer certains paramètres de vitesse qui sont utilisés pour optimiser la planification (par exemple, -pointer_mode 4, -wireframe, -scrollcopyrect) et d'autres éléments. Utilisez l'option -speeds pour les définir manuellement. Le triple rd,bw,lat correspond au taux de lecture du matériel vidéo en Mo/sec, à la bande passante réseau vers les clients en Ko/sec et à la latence réseau vers les clients en millisecondes, respectivement. Si une valeur est laissée vide, par exemple "-speeds ,100,15", alors le schéma interne est utilisé pour estimer la ou les valeurs vides.
Les cartes vidéo PC typiques ont des taux de lecture de 5 à 10 Mo/sec. Si le framebuffer est dans la mémoire principale au lieu du matériel vidéo (par exemple, SunRay, shadowfb, pilote dummy, Xvfb), le taux de lecture peut être beaucoup plus rapide. "x11perf -getimage500" peut être utilisé pour obtenir une borne inférieure (n'oubliez pas de prendre en compte les octets par pixel). Il vous appartient d'estimer la bande passante et la latence réseau vers les clients. Pour la latence, la commande ping(1) peut être utilisée.
Pour plus de commodité, des alias sont fournis, par exemple "-speeds modem". Les alias sont : "modem" pour 6,4,200 ; "dsl" pour 6,100,50 ; et "lan" pour 6,5000,1

-wmdt string

Pour certaines fonctionnalités, par exemple -wireframe et -scrollcopyrect, x11vnc doit contourner les problèmes de certains gestionnaires de fenêtres ou environnements de bureau (actuellement kde et xfce). Par défaut, il essaie de deviner lequel, mais il peut se tromper. Utilisez cette option pour indiquer quel gestionnaire de fenêtre/environnement de bureau. string peut être "gnome", "kde", "cde", "xfce", ou "root" (gestionnaire de fenêtres X classique). Tout autre texte est interprété comme "root".

-debug_pointer

Imprime des informations de débogage pour chaque événement de pointeur.

-debug_keyboard

Imprime des informations de débogage pour chaque événement clavier.

Identique à -dp et -dk, respectivement. Utiliser plusieurs fois pour plus de sortie.

-defer time

Temps en ms pour retarder l'envoi des mises à jour aux clients connectés (deferUpdateTime) Par défaut : 20

-wait time

Temps en ms pour faire une pause entre les interrogations d'écran. Utilisé pour réduire la charge. Par défaut : 20

-extra_fbur n

Effectue des vérifications supplémentaires de FrameBufferUpdateRequests pour essayer d'être mieux synchronisé avec les requêtes du client. Ce qu'il fait, c'est effectuer des interrogations supplémentaires du socket client à des moments critiques (avant les appels '-defer' et '-wait'). Le défaut est n=1. Réglez sur un nombre plus grand pour insérer plus de vérifications ou sur n=0 pour désactiver. Un inconvénient de ces appels supplémentaires est qu'une plus grande partie de l'entrée de la souris peut être traitée que désiré.

-wait_ui factor

Facteur par lequel réduire le temps d'attente -wait s'il y a eu une entrée utilisateur récente (pointeur ou clavier). Améliore la réponse, mais augmente la charge chaque fois que vous déplacez la souris ou tapez. Par défaut : 2.00

-setdefer n

Lorsque le mécanisme -wait_ui réduit le temps d'attente en ms, définissez le temps de report au même valeur en ms. n=1 pour activer, 0 pour désactiver, et -1 pour définir defer à 0 (pas de délai). De même, 2 et -2 indiquent que le mode 'urgent_update' doit être utilisé pour pousser les mises à jour encore plus tôt. Par défaut : 1

-nowait_bog

Ne pas détecter si l'interrogation de l'écran "ralentit" et dormir davantage. Certaines activités sans entrée utilisateur peuvent ralentir considérablement les choses : considérez une grande fenêtre de terminal avec une longue compilation en cours générant un flux continu de sortie texte. Par défaut, x11vnc essaiera de le détecter (3 interrogations d'écran consécutives chacune plus longue que 0,25 seconde sans entrée utilisateur) et dormira jusqu'à 1,5 seconde pour laisser les choses "rattraper leur retard". Utilisez cette option pour désactiver cette détection.

-slow_fb time

Temps en secondes à virgule flottante pour retarder toute interrogation d'écran. Pour une utilisation spéciale où une faible fréquence d'images est acceptable et souhaitable, mais où vous voulez que les entrées utilisateur soient traitées à la vitesse normale, vous ne pouvez donc pas utiliser -wait.

-xrefresh time

Temps en secondes à virgule flottante pour indiquer à quelle fréquence effectuer l'équivalent de xrefresh(1) pour forcer toutes les fenêtres (dans la zone visible si -id, -sid, ou -clip est utilisé) à se repeindre. Utilisez ceci uniquement si les applications se comportent mal en ne se repeignant pas correctement. Voir aussi -noxdamage.

-nap, -nonap

Surveille l'activité et si elle est faible, prend des pauses plus longues entre les interrogations d'écran pour vraiment réduire la charge lorsqu'elle est inactive. Par défaut : prend des pauses

-sb time

Temps en secondes après AUCUNE activité (par exemple, écran noir) pour réduire considérablement les interrogations d'écran (c'est-à-dire dormir pendant environ 1,5 seconde). Utiliser 0 pour désactiver. Par défaut : 60. Définissez la variable d'environnement X11VNC_SB_FACTOR pour l'ajuster.

-readtimeout n

Définit LibVNCServer rfbMaxClientWait à n secondes. Sur les liens lents qui prennent beaucoup de temps à afficher le premier écran, LibVNCServer peut atteindre le délai d'attente et interrompre la connexion. Par défaut : 20 secondes.

-ping n

Envoie une mise à jour de framebuffer 1x1 à tous les clients toutes les n secondes (par exemple, pour essayer de maintenir une connexion réseau active)

-nofbpm, -fbpm

Si le système prend en charge l'extension FBPM (Frame Buffer Power Management) (c'est-à-dire certains systèmes Sun), empêche le matériel vidéo d'entrer dans un état de faible consommation lorsque des clients VNC sont connectés.
Le matériel vidéo compatible FBPM économise de l'énergie lorsque le poste de travail est inactif en entrant dans des états de faible consommation (similaire à DPMS pour les moniteurs). Cela interfère avec l'interrogation par x11vnc des données du framebuffer.
"-nofbpm" signifie empêcher les états de faible consommation FBPM chaque fois que des clients VNC sont connectés, tandis que "-fbpm" signifie ne pas surveiller du tout l'état FBPM. Voir la page de manuel de xset(1) pour plus de détails. -nofbpm est essentiellement la même chose que d'exécuter "xset fbpm force on" périodiquement. Par défaut : -fbpm

-nodpms, -dpms

Si le système prend en charge l'extension DPMS (Display Power Management Signaling), empêche le moniteur d'entrer dans un état de faible consommation lorsque des clients VNC sont connectés.
Les états de faible consommation d'énergie des moniteurs DPMS sont une bonne chose et vous voulez normalement que l'extinction se produise (généralement x11vnc n'a pas de problème à exporter l'affichage dans cet état). Vous ne voudrez probablement utiliser "-nodpms" que pour contourner les problèmes avec les économiseurs d'écran qui se déclenchent dans les états de faible consommation DPMS. Il existe un problème connu avec kdesktop_lock sur KDE où l'économiseur d'écran continue de se déclencher chaque fois que l'entrée utilisateur s'arrête pendant une seconde ou deux. La spécification "-nodpms" le contourne.
"-nodpms" signifie empêcher les états de faible consommation DPMS chaque fois que des clients VNC sont connectés, tandis que "-dpms" signifie ne pas surveiller du tout l'état DPMS. Voir la page de manuel de xset(1) pour plus de détails. -nodpms est essentiellement la même chose que d'exécuter "xset dpms force on" périodiquement. Par défaut : -dpms

-forcedpms

Si le système prend en charge l'extension DPMS (Display Power Management Signaling), essaie de maintenir le moniteur dans un état éteint. Ceci
est de dissuader les personnes indiscrètes présentes à l'affichage physique de voir ce qui est à l'écran. Assurez-vous de verrouiller l'écran avant de vous déconnecter.
Cette méthode est loin d'être infaillible, par exemple, supposez que quelqu'un connecte un moniteur non-DPMS, ou charge la machine de telle sorte qu'il y ait un laps de temps avant que x11vnc ne rétablisse l'état éteint ? Sur de nombreuses machines, s'il est inondé d'entrées clavier et souris, il peut voir des éclairs de ce qui est à l'écran avant que l'état d'extinction DPMS ne soit rétabli. Pour que cela fonctionne en toute sécurité, il faudrait un support dans le serveur X pour faire cela exactement plutôt qu'approximativement avec DPMS.

-clientdpms

Comme -forcedpms mais uniquement lorsque les clients VNC sont connectés.

-noserverdpms

L'extension ServerInput d'UltraVNC est prise en charge. Cela permet au visionneur VNC de cliquer sur un bouton qui amènera le serveur (x11vnc) à essayer de désactiver les entrées clavier et souris à l'affichage physique et à mettre le moniteur en état d'extinction DPMS. Utilisez cette option pour éviter d'éteindre le moniteur.

-noultraext

Désactive les extensions UltraVNC suivantes : SingleWindow et ServerInput. Les autres gérées par LibVNCServer (textchat, mise à l'échelle 1/n, rfbEncodingUltra) ne le sont pas.

-chatwindow

Place une fenêtre de discussion locale UltraVNC sur l'affichage X11 que x11vnc interroge. Ainsi, la personne du côté du visionneur VNC peut discuter avec la personne à la console X11 physique. (par exemple, support technique sans téléphone)
Pour que cela fonctionne, le package SSVNC (version 1.0.21 ou ultérieure) DOIT être installé sur le système où x11vnc s'exécute et la commande 'ssvnc' doit être disponible dans $PATH. Le ssvncviewer est utilisé comme outil d'assistance pour la fenêtre de discussion. Voir http://www.karlrunge.com/x11vnc/ssvnc.html
Cette option implique '-rfbversion 3.6' pour tromper les visionneurs UltraVNC, sinon ils supposent que le chat n'est pas disponible. Pour spécifier une autre rfbversion, placez-la après l'option -chatwindow sur la ligne de commande.
Voir également les actions de contrôle à distance 'chaton' et 'chatoff'. Celles-ci peuvent également être définies à partir de l'interface graphique tkx11vnc.

-noxdamage

N'utilise pas l'extension X DAMAGE pour détecter les changements de framebuffer même si elle est disponible. Utilisez -xdamage si votre valeur par défaut est de l'avoir désactivée.
L'utilisation de l'extension DAMAGE par x11vnc : 1) réduit considérablement la charge lorsque l'écran ne change pas beaucoup, et 2) détecte les zones modifiées (petites par défaut) plus rapidement.
Actuellement, l'extension DAMAGE est trop conservatrice et signale souvent de grandes zones (par exemple, un terminal entier ou une fenêtre de navigateur) comme endommagées alors que la région réellement modifiée est beaucoup plus petite (parfois juste quelques pixels). Des heuristiques ont donc été introduites pour ignorer les grandes zones et utiliser les rectangles de dommage uniquement comme des « indices » pour l'interrogation traditionnelle des lignes de balayage. Les paramètres de réglage suivants sont introduits pour ajuster ce comportement :

-xd_area A

Définit la plus grande zone de rectangle DAMAGE A (en pixels : largeur * hauteur) à considérer comme réellement endommagée : le rectangle sera copié du framebuffer (lent) quoi qu'il arrive. Mettez à zéro pour faire confiance à *tous* les rectangles. Par défaut : 20000

-xd_mem f

Définit combien de temps les rectangles DAMAGE seront « mémorisés », f est un nombre à virgule flottante et est exprimé en unités du temps du cycle de répétition de ligne de balayage (32 itérations). La valeur par défaut (1.0) ne devrait poser aucun problème de peinture. Augmentez-la s'il y a des problèmes ou diminuez-la pour vivre dangereusement (peut-être utile sur une machine lente).

-sigpipe string

Gestion du tuyau cassé (SIGPIPE). string peut être "ignore" ou "exit". Pour "ignore", LibVNCServer gérera la perte abrupte d'un client et continuera ; pour "exit", x11vnc nettoiera et se terminera à la 1ère connexion rompue.
Cette option n'est pas vraiment nécessaire car LibVNCServer fait la bonne chose depuis un certain temps déjà. Cependant, pour plus de commodité, vous pouvez l'utiliser pour ignorer d'autres signaux, par exemple, « -sigpipe ignore:HUP,INT,TERM » au cas où cela serait utile pour une sorte d'application. Vous pouvez également mettre « exit:.. » dans la liste pour que x11vnc nettoie lors des signaux listés. « -sig » est un alias pour cette option si vous n'aimez pas le « pipe ». Exemple : -sig ignore:INT,TERM,exit:USR1

-threads, -nothreads

Si l'algorithme threaded LibVNCServer [rfbRunEventLoop] est utilisé ou non, si libpthread est disponible. Dans ce mode, de nouveaux threads (un pour l'entrée et un pour la sortie) sont créés pour gérer chaque nouveau client. Par défaut : -nothreads.
La stabilité des threads est bien améliorée dans la version 0.9.8.
Plusieurs clients en mode threaded devraient être stables pour le codage ZRLE sur toutes les plateformes. Les codages Tight et Zlib ne sont actuellement stables que sous Linux pour plusieurs clients. Compilez avec -DTLS=__thread si votre système d'exploitation, votre compilateur et votre lieur le supportent.
Pour les redimensionnements (randr, etc.), définissez cette variable d'environnement sur le nombre de millisecondes à attendre : X11VNC_THREADS_NEW_FB_SLEEP à divers endroits de l'action do_new_fb(). Ceci pour laisser le temps à diverses activités de se stabiliser. La valeur par défaut est d'environ 500 ms.
Plusieurs clients en mode threaded pourraient offrir de meilleures performances pour l'utilisation de diffusion de type « classe » ; également en mode de diffusion -appshare. Voir aussi l'option -reflect.

-fs f

Si la fraction de dalles modifiées lors d'un sondage est supérieure à f, l'ensemble de l'écran est mis à jour. Par défaut : 0.75

-gaps n

Heuristique pour combler les espaces dans les rangées ou les colonnes de n dalles ou moins. Utilisé pour améliorer la pagination du texte. Par défaut : 4

-grow n

Heuristique pour étendre les îles de dalles modifiées sur n ou plus de largeur en vérifiant la dalle près de la frontière. Par défaut : 3

-fuzz n

Tolérance en pixels pour marquer les bords d'une dalle comme modifiés. Par défaut : 2

-debug_tiles

Affiche les informations de débogage pour les dalles, les mises à jour de framebuffer, etc.

-snapfb

Au lieu d'interroger le framebuffer (fb) de l'affichage X pour les changements, copie périodiquement tout le fb de l'affichage X dans la mémoire principale et examine cette copie pour détecter les changements. (Ce paramètre s'applique également aux modes -rawfb non-X). Dans certaines circonstances, cela améliorera la réponse interactive, ou du moins rendra les choses plus fluides, mais dans d'autres (la plupart !) cela dégradera la réponse. Si le fb matériel vidéo est tel que la lecture de petites dalles est très lente, ce mode pourrait aider. Pour maintenir la "vitesse d'images", la taille de l'écran x bpp ne doit pas être trop grande. Notez que ce mode est très gourmand en ressources d'E/S mémoire (il effectue des copies plein écran même si rien ne change). Il peut être utile dans les applications de capture vidéo, les webcams, ou lorsque le déchirement de l'image est un problème.

-rawfb string

Au lieu d'interroger X, interroge l'objet mémoire spécifié dans string.
Pour l'interrogation de fichiers, pour mapper en mémoire mmap(2) un fichier, utilisez : « map:/chemin/vers/un/fichier@LxLxP » , avec la Largeur, la Hauteur et les bits par pixel du framebuffer. « mmap:... » est identique.
S'il y a des problèmes avec mmap, utilisez « file:/... » pour une lecture plus lente basée sur lseek(2).
Utilisez « snap:... » pour impliquer le mode -snapfb et l'accès « file: » (c'est pour les périphériques non consultables qui ne fournissent que le fb en une seule fois, par exemple, une caméra vidéo fournit l'image complète).
Pour les segments de mémoire partagée, la chaîne est de la forme : « shm:N@LxLxP » qui spécifie un shmid N et avec LxLxP comme ci-dessus. Voir shmat(1) et ipcs(1)
Si vous ne fournissez pas de type, « map » est supposé si le fichier existe (voir les paragraphes suivants pour quelques exceptions).
Si la chaîne est « setup:cmd », alors la commande « cmd » est exécutée et la première ligne en est lue et utilisée comme string. Cela permet d'initialiser le périphérique, de déterminer L, l et P, etc. Celles-ci sont souvent effectuées en tant que root, alors faites attention.
Si la chaîne commence par « video », voir la discussion VIDEO4LINUX ci-dessous où le périphérique peut être interrogé pour (et éventuellement définir) les paramètres du framebuffer.
Si la chaîne commence par « console », « /dev/fb », « fb », ou « vt », voir la discussion LINUX CONSOLE ci-dessous où le périphérique framebuffer est ouvert et les frappes clavier (et éventuellement les événements de souris) sont insérés dans la console.
Si la chaîne commence par « vnc », voir la discussion VNC HOST ci-dessous où le framebuffer est pris comme celui d'un autre serveur VNC distant.
Les suffixes optionnels sont « :R/G/B » et « +O » pour spécifier les masques rouge, vert et bleu (en hexadécimal) et un décalage dans l'objet mémoire. Si les masques ne sont pas fournis, x11vnc les devine en fonction du bpp (si les couleurs semblent incorrectes, vous devez fournir les masques.)
Un autre suffixe optionnel est les octets par ligne qui dans certains cas ne sont pas L*P/8. Spécifiez-le comme L*l*P-BPL par exemple 800x600x16-2048. Il pourrait s'agir d'une largeur normale de 1024 en 16bpp fb, mais seule une largeur de 800 apparaît.
Le format complet est donc : mode:fichier@LxLxP:R/G/B+O-BPL
Exemples :
-rawfb shm:210337933@800x600x32:ff/ff00/ff0000
-rawfb map:/dev/fb0@1024x768x32
-rawfb map:/tmp/Xvfb_screen0@640x480x8+3232
-rawfb file:/tmp/my.pnm@250x200x24+37
-rawfb file:/dev/urandom@128x128x8 -rawfb snap:/dev/video0@320x240x24 -24to32 -rawfb video0 -rawfb video -pipeinput VID -rawfb console -rawfb vt2 -rawfb vnc:somehost:0
(voir ipcs(1) et fbset(1) pour les deux premiers exemples)
En général, toute entrée utilisateur est ignorée par défaut (voir l'option -pipeinput pour savoir comment utiliser un programme d'assistance pour l'insertion). La plupart des options X11 (écran, clavier, souris) n'ont pas de sens et beaucoup feront planter ce mode, alors réfléchissez bien avant de les définir ou de les modifier dans
un x11vnc en cours d'exécution.
Si vous NE VOULEZ PAS que x11vnc ferme l'affichage X en mode rawfb, préfixez par un "+", par exemple +file:/dev/fb0... Laisser l'affichage ouvert active le canal de contrôle à distance par défaut, ce qui peut être utile. Alternativement, si vous spécifiez -noviewonly, alors les entrées de la souris et du clavier sont TOUJOURS envoyées à l'affichage X, cette utilisation devrait être très rare, c'est-à-dire faire quelque chose d'étrange avec /dev/fb0.
Si le périphérique n'est pas "recherchable" (par exemple, webcam), essayez de tout lire d'un coup en clichés complets via le mode "snap:" (note : cela consomme beaucoup de ressources). Si vous utilisez file: ou map: ET que le périphérique doit être rouvert pour CHAQUE instantané snapfb, définissez également la variable d'environnement : SNAPFB_RAWFB_RESET=1.
Si vous souhaitez que x11vnc transforme dynamiquement un rawfb 24bpp en 32bpp (notez que cela sera plus lent), fournissez également l'option -24to32. Cela serait utile, par exemple, pour une caméra vidéo qui fournit les données de pixels en RGB 24bpp packé. C'est le défaut en mode "video" si le bpp est de 24.
Normalement, les bits par pixel, B, sont 8, 16 ou 32 (ou rarement 24), cependant il y a aussi un certain support pour B < 8 (par exemple, anciens affichages graphiques 4 bpp ou 1 bpp). Dans ce cas, vous devez absolument fournir également les masques : WxHxB:R/G/B. Les pixels seront complétés à 8 bpp en utilisant une profondeur de 8 bits truecolor. Le schéma ne fonctionne actuellement pas avec snap fb (demandez si intéressé.) Exemple monochrome B=1 : file:/dev/urandom@128x128x1:1/1/1 D'autres du même type sont 128x128x2:3/3/3 128x128x4:7/7/7
Pour les framebuffers B < 8, vous pouvez également définir la variable d'environnement RAWFB_CGA=1 pour essayer un mappage CGA pour B=4 (par exemple, pilote linux vga16fb.) Notez qu'avec un faible bpp et/ou une faible résolution, les modes VGA et VGA16 sur la console Linux peuvent souvent être déjoués en raison de palettes de couleurs spéciales, de regroupements de pixels et même de tampons de dessin vidéo. D'un autre côté, expérimenter avec les masques RVB peut souvent donner quelque chose de reconnaissable.
VIDEO4LINUX : sous Linux, des tentatives sont faites pour gérer automatiquement les périphériques vidéo (webcams ou tuners TV). L'idée est que le WxHxB sera extrait du périphérique lui-même. Donc, si vous ne fournissez pas de paramètres "@WxHxB...", x11vnc essaiera de les déterminer. Il essaie d'abord l'API v4l si ce support a été compilé. Sinon, il exécutera le programme externe v4l- info(1) s'il est disponible.
Les exemples les plus simples sont "-rawfb video" et "-rawfb video1" qui impliquent le fichier périphérique /dev/video et /dev/video1, respectivement. Vous pouvez également fournir le /dev si vous le souhaitez, par exemple, "-rawfb /dev/video0"
Étant donné que le framebuffer du périphérique de capture vidéo change généralement continuellement (par exemple, fluctuations de luminosité), vous voudrez peut-être utiliser les options -wait, -slow_fb, ou -defer pour réduire le "framerate" afin de diminuer le trafic VNC réseau.
Un schéma de périphérique vidéo plus sophistiqué permet d'initialiser les paramètres du périphérique en utilisant :
-rawfb video:<paramètres>
Le préfixe pourrait également être, comme ci-dessus, par exemple, "video1:" pour spécifier le fichier périphérique. L'API v4l doit être disponible pour que cela fonctionne. Sinon, vous devrez essayer d'initialiser le périphérique avec un programme externe, par exemple, xawtv, spcaview, et espérer qu'ils persistent lorsque x11vnc rouvre le périphérique.
<paramètres> est une liste de paires clé=valeur séparées par des virgules. La luminosité, la couleur, le contraste et la teinte du périphérique peuvent être définis en pourcentages, par exemple, br=80,co=50,cn=44,hu=60.
Le nom de fichier du périphérique peut également être défini si nécessaire (s'il ne commence pas par "video"), par exemple, fn=/dev/qcam.
La largeur, la hauteur et le bpp du framebuffer peuvent être définis via, par exemple, w=160,h=120,bpp=16.
Lié au bpp ci-dessus, le format de pixel peut être défini via fmt=XXX, où XXX peut être l'un des suivants : GREY, HI240, RGB555, RGB565, RGB24 et RGB32 (avec bpp 8, 8, 16, 16, 24 et 32 respectivement). Voir http://www.linuxtv.org pour plus d'informations (API V4L).
Pour les cartes tuner TV/rf, vous pouvez définir le mode de syntonisation via tun=XXX où XXX peut être PAL, NTSC, SECAM ou AUTO.
Vous pouvez changer le canal d'entrée par le réglage inp=XXX, où XXX est le nom du canal d'entrée (Télévision, Composite1, S-Video, etc.). Utilisez le nom qui se trouve dans les informations sur le périphérique imprimées au démarrage.
Pour les canaux d'entrée avec tuner (par exemple, Télévision), vous pouvez changer la station sélectionnée par le réglage sta=XXX. XXX est le numéro de la station. Actuellement, seuls les canaux ntsc-cable-us (câble US) sont intégrés à x11vnc. Voir l'option -freqtab ci-dessous pour en fournir un depuis xawtv. Si XXX est supérieur à 500, il est interprété comme une fréquence brute en KHz.
Exemple :
-rawfb video:br=80,w=320,h=240,fmt=RGB32,tun=NTSC,sta=47
il pourrait être nécessaire d'ajouter inp=Television pour que le canal d'entrée soit TV si la carte ne démarre pas par défaut dans celui-ci.
Notez que tous les périphériques de capture vidéo ne prendront pas en charge tous les paramètres ci-dessus.
Voir l'option -pipeinput VID ci-dessous pour un moyen de contrôler les paramètres via le spectateur VNC via des frappes. Par raccourci, si la chaîne commence par "Video.." au lieu de "video..", alors -pipeinput VID est implicite.
Comme ci-dessus, si vous spécifiez un "@WxHxB..." après la chaîne <paramètres>, ils sont utilisés tels quels : le périphérique n'est pas interrogé pour les valeurs actuelles. Sinon, le périphérique sera interrogé.
CONSOLE LINUX : ce qui suit décrit quelques façons de visualiser et potentiellement d'interagir avec la console texte/graphique Linux (c'est-à-dire pas X11 XFree86/Xorg)
Note : Si le programme LinuxVNC de LibVNCServer est sur votre système, vous voudrez peut-être l'utiliser à la place de la méthode suivante car il sera plus rapide et plus précis pour la console texte Linux et inclut la prise en charge de la souris. Il existe cependant la fonctionnalité LinuxVNC de base dans x11vnc si vous remplacez "console" par "vt" dans les exemples ci-dessous.
Si la chaîne rawfb commence par "console", le périphérique framebuffer /dev/fb0 est ouvert et /dev/tty0 est également ouvert. Ce dernier est utilisé pour injecter des frappes (toutes ne sont pas prises en charge, mais les frappes de base le sont). Vous devrez être root pour injecter des frappes, mais pas nécessairement pour ouvrir /dev/fb0. /dev/tty0 fait référence au VT actif, pour en indiquer un explicitement, utilisez, par exemple, "console2" pour /dev/tty2, etc. en indiquant le numéro de VT spécifique.
Pour que le périphérique framebuffer Linux, /dev/fb0, (fb1, etc.) soit activé, les pilotes noyau appropriés doivent être chargés. Par exemple, vesafb ou vga16fb et également en définissant le paramètre de démarrage vga=0x301 (ou 0x314, 0x317, etc.) (la méthode vga=... est la méthode préférée ; configurez vos machines de cette façon.) Sinon, il y aura une erreur 'No such device'. Vous pouvez également charger un pilote framebuffer Linux spécifique à votre marque de carte vidéo pour plus de fonctionnalités. Une fois la machine démarrée, on peut souvent 'modprobe' le pilote fb en tant que root pour obtenir un périphérique framebuffer.
Si vous ne parvenez pas à faire fonctionner /dev/fb0 sous Linux, essayez d'utiliser le mode d'émulation LinuxVNC en "-rawfb vtN" où N = 1, ... 6 est le terminal virtuel Linux (alias console virtuelle) que vous souhaitez visualiser, par exemple, "-rawfb vt2". Contrairement au mode /dev/fb, il n'a pas besoin d'être le terminal virtuel actif. Notez que ce mode ne peut afficher que du texte et non des graphiques. x11vnc interroge le texte dans /dev/vcsaN
Définissez la variable d'environnement RAWFB_VCSA_BW=1 pour désactiver les couleurs en mode "vtN" (c'est-à-dire en noir et blanc uniquement.) Si vous ne préférez pas le 16bpp par défaut, définissez RAWFB_VCSA_BPP sur 8 ou 32. Si vous avez besoin de retoucher les paramètres rawfb en utilisant la chaîne 'console_guess' imprimée au démarrage, assurez-vous d'indiquer la méthode snap:.
uinput : Si la version Linux semble être 2.6 ou ultérieure et que le module "uinput" semble être présent (modprobe uinput), alors la méthode uinput sera utilisée à la place de /dev/ttyN. uinput permet l'insertion de FRA PPECASES ET d'entrées de souris et est donc préféré lors de l'accès aux applications de console Linux graphiques (par exemple, QT-embedded). Il fournit également une insertion de frappe plus précise. Voir -pipeinput UINPUT ci-dessous pour plus d'informations sur ce mode ; vous devrez utiliser -pipeinput si vous souhaitez retoucher des paramètres UINPUT. Vous pourriez également vouloir utiliser les options -nodragging et -cursor none. Utilisez "console0", etc. ou -pipeinput CONSOLE pour forcer la méthode /dev/ttyN.
Notez que vous pouvez changer le VT Linux à distance en utilisant la commande chvt(1) pour faire celui que vous voulez actif (par exemple, 'chvt 3'). Parfois, passer en dehors puis revenir corrige l'état graphique du framebuffer. Pour le mode "-rawfb vtN", il n'est pas nécessaire de changer les VT.
Pour ignorer entièrement l'injection d'entrée, utilisez "consolex" ou "vtx".
La chaîne "/dev/fb0" (1, etc.) peut être utilisée à la place de "console". Cela peut être utilisé pour spécifier un périphérique framebuffer différent, par exemple /dev/fb1. Par raccourci, le "/dev/" peut être supprimé. Si le nom est non standard, utilisez "console:/dev/foofb"
Si vous ne voulez pas que x11vnc devine automatiquement le WxHxB et les masques du framebuffer (parfois le noyau donne des informations incorrectes), spécifiez-les avec un @WxHxB (et des masques :R/G/B optionnels) à la fin de la chaîne.
Exemples : -rawfb console -rawfb /dev/fb0 (identique) -rawfb console3 (force /dev/tty3) -rawfb consolex (pas de frappes ou de souris) -rawfb console:/dev/nonstd -rawfb console -pipeinput UINPUT:accel=4.0 -rawfb vt3 (/dev/tty3 sans /dev/fb0)
HÔTE VNC : si la chaîne -rawfb est de la forme "vnc:hôte:N", alors l'affichage VNC "N" sur le serveur VNC distant "hôte" est connecté (c'est-à-dire que x11vnc agit lui-même comme un client VNC) et ce framebuffer est exporté.
Ce mode n'est vraiment utile que si vous essayez d'améliorer les performances dans le cas de nombreux spectateurs VNC simultanés (par exemple, > 10), et que vous essayez une stratégie de "diviser pour régner" pour réduire la bande passante et améliorer la réactivité. (Cependant, un autre utilisateur a trouvé ce mode utile pour exporter un affichage de démonstration via un lien lent : ensuite, plusieurs spectateurs de démonstration se sont connectés au x11vnc réfléchissant du côté rapide du lien, et ont ainsi évité que tous les spectateurs de démonstration ne passent par le lien lent.)
Par exemple, s'il y aura 64 spectateurs VNC simultanés, cela peut entraîner beaucoup de trafic VNC redondant vers et depuis l'hôte serveur :N, une utilisation supplémentaire du CPU, et la réponse de tous les spectateurs peut être réduite en attendant l'écri
es au client le plus lent à terminer. Cependant, si vous configurez 8 réflecteurs/répéteurs démarrés avec l'option -rawfb vnc:host:N, alors il n'y a que 8 connexions à host:N. Chaque répéteur gère alors 8 connexions de spectateur VNC, répartissant ainsi la charge. En utilisation de diffusion en classe, essayez de placer les répéteurs sur des commutateurs différents. Ce mode est identique à -reflect host:N. Remplacez "host:N" par "listen" ou "listen:port" pour une connexion inversée.
Les performances globales ne seront pas aussi bonnes qu'une seule connexion directe car, entre autres, il y a un niveau supplémentaire d'interrogation de la mémoire tampon d'image et le mouvement du pointeur peut toujours induire de nombreux changements par seconde qui doivent être propagés. Astuce : si le VNC distant est x11vnc qui fait du wireframing, ou un affichage X qui fait du wireframing, cela donne une bien meilleure réponse que le glisser-déposer de fenêtres opaques. Envisagez l'option -nodragging si le problème est grave.
La variable d'environnement X11VNC_REFLECT_PASSWORD peut être définie sur le mot de passe nécessaire pour se connecter au serveur hôte VNC, ou sur "file:chemin_vers_fichier" pour indiquer un fichier contenant le mot de passe sur sa première ligne.
Pour définir le format de pixel que x11vnc demande en tant que CLIENT VNC, définissez les variables d'environnement : X11VNC_REFLECT_bitsPerSample X11VNC_REFLECT_samplesPerPixel, et X11VNC_REFLECT_bytesPerPixel ; les valeurs par défaut sont 8, 3, 4. 2, 3, 1 donnerait un mode couleur bas. Voir la fonction rfbGetClient() dans libvncclient pour plus d'informations.
Le mode HÔTE VNC implique -shared. Utilisez -noshared comme option de ligne de commande suivante pour désactiver le partage.

-freqtab fichier

À utiliser avec "-rawfb vidéo" pour les périphériques de capture vidéo afin de spécifier les fréquences des stations. Au lieu d'utiliser la mise en correspondance intégrée ntsc-cable-us du numéro de station à la fréquence, utilisez les données du fichier. Pour les stations qui ne sont pas numériques, par exemple SE20, elles sont placées au-dessus de la station numérotée la plus élevée dans l'ordre où elles sont trouvées. Exemple : "-freqtab /usr/X11R6/share/xawtv/europe-west.list" Vous pouvez créer votre propre freqtab en copiant le format xawtv.

-pipeinput cmd

Cette option vous permet de fournir une commande externe dans cmd à laquelle x11vnc enverra tous les événements d'entrée utilisateur dans un format simple. En mode -pipeinput, x11vnc ne traitera par défaut aucun des événements d'entrée utilisateur. Si vous préfixez cmd par "tee:", il les enverra à la commande pipe et les traitera. Pour une description du format, exécutez "-pipeinput tee:/bin/cat". Un autre préfixe est "reopen" qui signifie rouvrir le pipe s'il se termine. Séparez plusieurs préfixes par des virgules.
En combinaison avec -rawfb, il pourrait être possible de faire des choses amusantes (par exemple, contrôler des appareils non-X). Pour faciliter cela, si -rawfb est en vigueur, la valeur est stockée dans X11VNC_RAWFB_STR pour que la commande pipe l'utilise si elle le souhaite. Faites 'env | grep X11VNC' pour en savoir plus.
Modes pipeinput intégrés (aucun programme externe requis) :
Si cmd est "VID" et que vous utilisez -rawfb pour un périphérique de capture vidéo, une liste interne de mappages de clavier est utilisée pour définir les paramètres de la vidéo. Les mappages sont :
"B" et "b" ajustent la luminosité vers le haut et vers le bas. "H" et "h" ajustent la teinte. "C" et "c" ajustent la couleur. "N" et "n" ajustent le contraste. "S" et "s" ajustent la taille de l'écran de capture. "I" et "i" parcourent les canaux d'entrée. Les flèches Haut et Bas ajustent la station (s'il s'agit d'un tuner). F1, F2, ..., F6 permettront de passer le format de pixel de capture vidéo à HI240, RGB565, RGB24, RGB32, RGB555 et GREY respectivement. Voir -rawfb video pour les détails.
Si cmd est "CONSOLE" ou "CONSOLEn" où n est un numéro de console Linux, alors l'insertion de frappes clavier de la console Linux vers /dev/ttyN (voir -rawfb console) est effectuée.
Si cmd commence par "UINPUT", alors le module uinput Linux est utilisé pour insérer les événements clavier et souris dans la console Linux (voir -rawfb ci-dessus). Il s'agit généralement du fichier de périphérique /dev/input/uinput (vous devrez peut-être le créer avec "mknod /dev/input/uinput c 10 223" et insérer le module avec "modprobe uinput").
Le mode UINPUT ne gère actuellement que les claviers américains (une option de code de balayage pourrait être ajoutée) et toutes les clésym ne sont pas supportées. Mais c'est probablement plus précis que la méthode "CONSOLE".
Vous voudrez peut-être utiliser les options -cursor none et -nodragging dans ce mode.
Des options de réglage supplémentaires peuvent être fournies via : UINPUT:opt1,opt2,... (une liste séparée par des virgules). Si une option commence par "/", elle est considérée comme le fichier de périphérique uinput.
Le quel uinput est injecté peut être contrôlé par une chaîne d'options composée des caractères "K", "M" et "B" (voir l'option -input), par exemple, "KM" permet les frappes et les mouvements mais pas les clics de bouton.
Une option UINPUT de la forme : accel=f, ou accel=fx+fy définit l'"accélération" du mouvement de la souris. Ceci est utilisé pour corriger le mouvement relatif brut de la souris en fonction de la façon dont le curseur de l'application se déplace (x11vnc n'a aucun contrôle ou connaissance de la façon dont l'application de fenêtrage interprète les mouvements bruts de la souris). Typiquement, l'accélération pour un affichage X est de 2 (voir l'option "m" de xset). "f" est un nombre flottant, par exemple 3.0. Utilisez "fx+fy" si vous devez fournir des corrections différentes pour x et y.
Note : l'accélération par défaut est de 2.0 car il semble que X et qt-embedded utilisent souvent (mais pas toujours) cette valeur.
Même avec un réglage d'accélération correct, la position de la souris se désynchronisera (probablement en raison d'un réglage de "seuil" de la souris où l'accélération ne s'applique pas, voir xset "m" ). L'option reset=N définit le nombre de ms (par défaut 150) après lequel le curseur est tenté d'être réinitialisé (en forçant la souris à (0, 0) par de petits incréments puis en revenant à (x, y) en 1 saut). Cette correction semble nécessaire mais peut entraîner des saccades ou des comportements inattendus avec les menus, etc. Utilisez reset=0 pour désactiver.
Si vous définissez la variable d'environnement X11VNC_UINPUT_THRESHOLDS, le mode thresh=n sera activé. Il ne fonctionne actuellement pas bien. Si |dx| <= thresh et |dy| < thresh, aucune accélération n'est appliquée. Utilisez "thresh=+n" |dx| + |dy| < thresh à la place (X11 ?).
Exemple : -pipeinput UINPUT:accel=4.0 -cursor none
Si le périphérique uinput a un pointeur absolu (par opposition à une souris normale qui est un pointeur relatif), vous pouvez spécifier l'option "abs". Notez qu'un pavé tactile sur un ordinateur portable est un appareil absolu à un certain degré. Cela évite (généralement) tous les problèmes d'accélération de la souris. Si x11vnc a des difficultés à déduire la taille de l'appareil, utilisez "abs=WxH". De plus, si l'appareil est un écran tactile (supposé avoir un pointeur absolu), utilisez "touch" ou "touch=WxH". Pour les écrans tactiles, lorsqu'un bouton de souris est enfoncé, une augmentation de pression est injectée, et lorsque le bouton est relâché, une pression de zéro est injectée.
Si touch a été défini, utilisez "touch_always=1" pour indiquer que chaque fois que la souris bouge sans bouton enfoncé, un événement tactile de pression zéro doit également être envoyé. Utilisez également "btn_touch=1" pour indiquer qu'une pression ou un relâchement de frappe BTN_TOUCH doit être envoyé au lieu d'un changement de pression. Définissez "dragskip=n" pour ignorer n touches de souris déplacées (avec pression appliquée) avant d'en injecter une. Pour indiquer la pression qui doit être envoyée lorsqu'un clic de bouton est effectué pour un appareil à écran tactile, spécifiez pressure=n, par exemple n=5. La valeur par défaut est n=1.
Si un écran tactile est utilisé ("touch" ci-dessus) et que son entrée est traitée par tslib, vous pouvez spécifier le fichier de calibration tslib via tslib_cal=<fichier>. Par exemple, tslib_cal=/etc/pointercal. Pour obtenir un positionnement précis, voire utilisable, c'est nécessaire lorsque tslib est utilisé.
Le mécanisme uinput Linux peut être contourné et l'on peut écrire les événements d'entrée DIRECTEMENT dans les périphériques à la place. Pour ce faire, spécifiez un ou plusieurs des éléments suivants pour les classes d'entrée : direct_rel=<périphérique> direct_abs=<périphérique> direct_btn=<périphérique> ou direct_key=<périphérique>. Le fichier <périphérique> est généralement quelque chose comme /dev/input/event1, mais vous pouvez spécifier n'importe quel fichier de périphérique ou pipe. Vous devez spécifier chacune des classes ci-dessus, même si elles correspondent au même fichier de périphérique (rel/abs et btn sont souvent les mêmes.) Regardez le fichier /proc/bus/input/devices pour avoir une idée de ce qui est disponible et des noms de fichiers des périphériques. Note : les périphériques /dev/input/mouse* ne semblent pas fonctionner, utilisez plutôt le fichier /dev/input/event* correspondant. Toute classe d'entrée non spécifiée directement ci-dessus sera gérée via le mécanisme uinput. Pour désactiver la création d'un périphérique uinput (et ainsi ignorer les entrées non gérées), spécifiez "nouinput".
Exemples :
-pipeinput UINPUT:direct_abs=/dev/input/event1
ceci a été utilisé sur un qtmoko Neo freerunner (armel) :
-pipeinput UINPUT:touch,tslib_cal=/etc/pointercal, direct_abs=/dev/input/event1,nouinput,dragskip=4
(où la longue ligne a été divisée en deux.)
Vous pouvez définir la variable d'environnement X11VNC_UINPUT_DEBUG=1 ou plus élevée pour obtenir une sortie de débogage pour le mode UINPUT.

-gui [gui-opts]

Lance une interface graphique tcl/tk simple basée sur les options de contrôle à distance -remote/-query décrites ci-dessous. Nécessite que le programme "wish" soit installé sur la machine. "gui-opts" n'est pas requis : par défaut, le lanceur démarre à la fois l'interface graphique complète et x11vnc, avec l'interface graphique apparaissant sur l'affichage X dans la variable d'environnement DISPLAY.
"gui-opts" peut être une liste d'éléments séparés par des virgules. Actuellement, il existe ces types d'éléments : 1) un mode d'interface graphique, 2) une "simplicité" d'interface graphique, 3) l'affichage X sur lequel l'interface graphique doit s'afficher, 4) un mode "tray" ou "icon", et 5) une géométrie d'interface graphique.
1) Le mode d'interface graphique peut être "start", "conn", ou "wait". "start" est le mode par défaut ci-dessus et n'est pas requis. "conn" signifie ne pas démarrer x11vnc automatiquement, mais essayer simplement de se connecter à un processus x11vnc existant. "wait" signifie juste démarrer l'interface graphique et rien d'autre (vous demanderez plus tard à l'interface graphique de démarrer x11vnc ou de se connecter à un existant.)
2) La simplicité de l'interface graphique est désactivée par défaut (une interface graphique pour utilisateurs avancés avec toutes les options est présentée). Pour commencer avec quelque chose de moins intimidant, fournissez la chaîne "simple" ("ez" est un alias pour cela). Une fois l'interface graphique démarrée, vous pouvez basculer entre les deux avec "Misc -> simple_gui".
3) Notez la possible confusion concernant les deux affichages X potentiellement différents : x11vnc en interroge un, mais vous pourriez vouloir que l'interface graphique apparaisse sur un autre. Par exemple, si vous vous connectez via ssh et que x11vnc n'est pas encore en cours d'exécution, vous pourriez vouloir que l'interface graphique vous revienne via votre affichage X redirigé par ssh (par exemple, localhost:10).
Si vous ne spécifiez pas d'affichage X pour l'interface graphique dans "gui-opts", alors la variable d'environnement DISPLAY et l'option -display sont essayées (dans cet ordre). En ce qui concerne l'affichage X de x11vnc que l'interface graphique essaiera de contacter, elle essaie d'abord -display puis DISPLAY. Par exemple, "x11vnc -display :0 -gui otherhost:0" contrôlera à distance un x11vnc interrogeant :0 et affichera l'interface graphique sur otherhost:0. Le mode "tray/icon" ci-dessous inverse cette préférence, préférant afficher sur l'affichage x11vnc.
4) Lorsque "tray" ou "icon" est spécifié, l'interface graphique se présente comme une petite icône avec un comportement typique d'un "tray système" ou d'une "applet de dock". La couleur de l'icône indique l'état (clients connectés) et il y a également une indication sous forme de bulle. Cliquer sur l'icône affiche un menu à partir duquel les propriétés, etc., peuvent être définies et l'interface graphique complète est disponible sous "Avancé". Pour être pleinement fonctionnel, le mode d'interface graphique doit être "start" (par défaut).
Notez que le mode tray ou icon impliquera l'option x11vnc -forever (si le serveur x11vnc est démarré en même temps que l'interface graphique) à moins que -connect ou -connect_or_exit n'ait été spécifié. Ainsi, x11vnc (et l'interface graphique tray/icon) attendra d'autres connexions après la déconnexion du premier client. Si vous ne souhaitez qu'une seule connexion spectateur, incluez l'option -once.
Pour "icon", l'interface graphique est juste une petite fenêtre autonome. Pour "tray", elle tentera de s'intégrer dans le "tray système" si possible. Si "=setpass" est ajouté, l'utilisateur X11 sera invité à définir le mot de passe de la session VNC au démarrage. Si =<nombre hexadécimal> est ajouté, cette icône tentera de s'intégrer dans la fenêtre donnée par le nombre hexadécimal. Utilisez =noadvanced pour désactiver l'interface graphique complète. (Pour fournir plus d'un, utilisez le signe "+"). Par exemple, -gui tray=setpass et -gui icon=0x3600028
Autres modes : "full", par défaut et pas besoin d'être spécifié. "-gui none", n'afficher aucune interface graphique, utile pour remplacer un paramètre ~/.x11vncrc, etc.
5) Lorsque "geom=+X+Y" est spécifié, cette géométrie est passée à la fenêtre principale de l'interface graphique. C'est l'icône en mode icon/tray, ou l'interface graphique complète sinon. Vous pouvez également spécifier la largeur et la hauteur, c'est-à-dire LxH+X+Y, mais ce n'est pas recommandé. En mode "tray", la géométrie est ignorée à moins que le gestionnaire de tray système ne semble pas s'exécuter. On pourrait imaginer utiliser quelque chose comme "-gui tray,geom=+4000+4000" avec un gestionnaire d'affichage pour garder l'interface graphique invisible jusqu'à ce que quelqu'un se connecte...
Plus d'astuces pour les icônes, "icon=minimal" donne une icône juste avec le numéro d'affichage VNC. Vous pouvez également définir la police avec "iconfont=...". Ce qui suit peut être utile : "-gui icon=minimal,iconfont=5x8,geom=24x10+0-0"
Exemples généraux de l'option -gui : "x11vnc -gui", "x11vnc -gui ez", "x11vnc -gui localhost:10", "x11vnc -gui conn,host:0", "x11vnc -gui tray,ez", "x11vnc -gui tray=setpass"
Si vous n'avez pas l'intention de démarrer x11vnc depuis l'interface graphique (c'est-à-dire simplement de contrôler à distance un serveur existant), alors le processus d'interface graphique peut s'exécuter sur une machine différente du serveur x11vnc tant que les permissions X, etc. permettent la communication entre les deux.
POLICES : Sur certains systèmes, les polices tk peuvent être trop petites, irrégulières ou autrement illisibles. Il y a 4 variables d'environnement que vous pouvez définir pour spécifier la police tk que vous préférez :
X11VNC_FONT_BOLD police principale pour les menus et boutons. X11VNC_FONT_FIXED police pour le texte à largeur fixe.
X11VNC_FONT_BOLD_SMALL police de l'icône du tray. X11VNC_FONT_REG_SMALL police du menu de l'icône du tray.
Les deux dernières s'appliquent uniquement au mode icône du tray.
Voici quelques exemples :
-env X11VNC_FONT_BOLD='Helvetica -16 bold' -env X11VNC_FONT_FIXED='Courier -14' -env X11VNC_FONT_REG_SMALL='Helvetica -12'
Vous pouvez placer des lignes comme celles ci-dessus (sans les guillemets) dans votre fichier ~/.x11vncrc pour éviter d'avoir à les spécifier sur la ligne de commande de x11vnc.

-remote commande

Contrôler à distance certains aspects d'un serveur x11vnc déjà en cours d'exécution. "-R" et "-r" sont des alias pour "-remote". Une fois la commande de contrôle à distance envoyée au serveur en cours d'exécution, la commande x11vnc 'x11vnc -remote ...' se termine. Vous pouvez souvent utiliser la commande -query (voir ci-dessous) pour voir si le serveur x11vnc a traité votre commande -remote.
Le canal de communication par défaut est celui des propriétés X (spécifiquement X11VNC_REMOTE), et donc cette commande doit être exécutée avec les paramètres corrects pour DISPLAY et éventuellement XAUTHORITY pour se connecter au serveur X et définir la propriété. Alternativement, utilisez les options -display et -auth pour les définir aux valeurs correctes. Le serveur en cours d'exécution ne peut pas utiliser l'option -novncconnect car cela désactive le canal de communication. Voir ci-dessous pour les canaux alternatifs.
Par exemple : 'x11vnc -remote stop' (ce qui est identique à 'x11vnc -R stop') arrêtera le serveur x11vnc. 'x11vnc -R shared' activera les connexions partagées, et 'x11vnc -R scale:3/4' redimensionnera le bureau.
Pour utiliser un nom différent pour la propriété X11 (par exemple, pour avoir des canaux de communication séparés pour plusieurs x11vnc sur le même affichage), définissez la variable d'environnement X11VNC_REMOTE sur la chaîne souhaitée, par exemple : -env X11VNC_REMOTE=X11VNC_REMOTE_12345 Les deux côtés du canal doivent utiliser le même nom unique.
Pour exécuter un ensemble de commandes en séquence, utilisez quelque chose comme : x11vnc -R 'script:premierecmd;deuxiemecmd;...'
Utilisez x11vnc -R script:file=/chemin/vers/fichier pour lire les commandes à partir d'un fichier (peut être multiligne et utiliser le caractère commentaire '#' normalement. Le séparateur ';' doit toujours être utilisé pour séparer chaque commande.)
Pour ne pas essayer de contacter un autre processus x11vnc et exécuter à la place la commande (ou la requête) directement, préfixez la commande avec la chaîne "DIRECT:"

bcx_xattach:str Cette commande de contrôle à distance est destinée à être utilisée avec le programme BARCO xattach ou le programme x2x. Ces deux programmes sont destinés au partage de 'pointeur et clavier' entre différents affichages X. En général, les deux affichages sont généralement à proximité, par exemple sur le même bureau, et cela permet à l'utilisateur de partager un seul pointeur et clavier entre eux. L'utilisateur déplace la souris vers un bord et le pointeur de la souris semble alors 'sauter' vers l'autre écran d'affichage. Ainsi, cela émule ce qu'un serveur X unique ferait pour deux écrans (par exemple :0.0 et :0.1). L'illusion d'un serveur X unique avec plusieurs écrans est obtenue en transférant les événements vers le second via l'extension XTEST.
Ce que fait la commande x11vnc bcx_xattach, c'est d'effectuer des mouvements de pointeur pour essayer de FORCER xattach/x2x à 'sauter' vers l'autre affichage. Dans ce qui suit, l'affichage 'maître' désigne celui qui, lorsqu'il a le 'focus', ne fait essentiellement rien d'autre que de surveiller le passage de la souris sur un bord. L'affichage 'esclave' désigne celui vers lequel la souris et le clavier sont redirigés une fois qu'un bord du maître a été franchi. Notez que le x11vnc exécutant la commande bcx_xattach DOIT être celui connecté à l'affichage *maître*.
Notez également que lorsque l'entrée est redirigée (via XTEST) du maître à l'esclave, le pointeur et le clavier de l'affichage maître sont *saisis* par xattach/x2x. x11vnc peut utiliser cette information pour vérifier que le changement de mode maître/esclave a eu lieu correctement. Si vous spécifiez l'option "ifneeded" (voir ci-dessous) et que l'état initial de la saisie est celui de l'état final souhaité, aucun mouvement de pointeur n'est injecté et "DONE,GRAB_OK" est renvoyé.
"str" doit contenir l'une des valeurs "up", "down", "left", ou "right" pour indiquer la direction du 'saut'. "str" doit également contenir l'une des valeurs "master_to_slave" ou "slave_to_master" pour indiquer le type de changement de mode induit par le saut. Utilisez "M2S" et "S2M" comme alias plus courts.
"str" peut être une liste d'options de réglage supplémentaires séparées par "+". L'option "shift=n" indique un décalage par rapport à (0,0) (par défaut 20). "final=x+y" spécifie la position finale du curseur à la fin de la séquence de mouvement normale ; par défaut 30+30. "extra_move=x+y" signifie d'effectuer un mouvement de pointeur supplémentaire après "final" vers x+y. "dt=n" définit le temps de veille en millisecondes entre les mouvements du pointeur (par défaut : 40 ms) "retry=n" spécifie le nombre maximal de tentatives si le changement d'état de la saisie échoue. "ifneeded" signifie de ne pas appliquer les mouvements du pointeur si l'état initial de la saisie est celui de l'état final souhaité. "nograbcheck" signifie de ne pas vérifier si l'état de la saisie a changé comme prévu et d'appliquer uniquement les mouvements du pointeur (par défaut, il faut vérifier les états de la saisie).
Si vous ne spécifiez pas "up", etc., à bcx_xattach, rien ne sera tenté et la commande renvoie la chaîne FAIL,NO_DIRECTION_SPECIFIED. Si vous ne spécifiez pas "master_to_slave" ou "M2S", etc., à bcx_xattach, rien ne sera tenté et la commande renvoie la chaîne FAIL,NO_MODE_CHANGE_SPECIFIED.
Sinon, la chaîne renvoyée contiendra "DONE". Ce sera "DONE,GRAB_OK" si l'état de la saisie a changé comme prévu (ou si "ifneeded" a été fourni et que l'état initial de la saisie était déjà celui souhaité.) Si l'état initial de la saisie était incorrect, mais que l'état final de la saisie était correct, alors c'est "DONE,GRAB_FAIL_INIT". Si l'état initial de la saisie était correct, mais que l'état final de la saisie était incorrect, alors c'est "DONE,GRAB_FAIL_FINAL". Si les deux sont incorrects, ce sera "DONE,GRAB_FAIL". En cas d'échec de saisie, la chaîne sera suivie de ":p1,k1-p2,k2" où p1,k1 indique les états initiaux de saisie du pointeur et du clavier et p2,k2 les états finaux. Si GRAB_FAIL ou GRAB_FAIL_FINAL se produit, l'action sera retentée jusqu'à 3 fois ; en essayant de réinitialiser l'état et en dormant un peu entre chaque tentative. Définissez retry=n pour ajuster le nombre de tentatives, zéro pour désactiver les tentatives.
Exemples : -R bcx_xattach:down+M2S -R bcx_xattach:up+S2M -R bcx_xattach:up+S2M+nograbcheck+dt=30 -R bcx_xattach:down+M2S+extra_move=100+100
ou utilisez -Q au lieu de -R pour récupérer le texte du résultat.

-sync

Par défaut, les commandes -remote sont exécutées de manière asynchrone, c'est-à-dire que la requête est postée et le programme se termine immédiatement. Utilisez -sync pour que le programme attende un accusé de réception du serveur x11vnc indiquant que la commande a été traitée (d'une manière ou d'une autre). D'autre part, les requêtes -query sont toujours traitées de manière synchrone car elles doivent attendre la réponse.
Notez également que si les requêtes -remote et -query sont fournies sur la ligne de commande, la commande -remote est traitée en premier (de manière synchrone : pas besoin de -sync), puis la requête -query est traitée normalement. Cela permet de vérifier de manière fiable si la commande -remote a été traitée en interrogeant les nouveaux paramètres. Notez cependant qu'il existe un délai d'attente de quelques secondes (voir le paragraphe suivant) ; si x11vnc met plus de temps que cela pour traiter les requêtes, le demandeur pensera qu'un échec s'est produit.
Par défaut, l'attente est de 3,5 secondes. Ou si cmd=stop, seulement 1,0 seconde. Si cmd correspond à 'script :', il attendra jusqu'à 10,0 secondes. Définissez X11VNC_SYNC_TIMEOUT au nombre de secondes pendant lesquelles vous souhaitez attendre.

-query_retries str

Si une requête échoue à obtenir une réponse d'un serveur x11vnc, retentez jusqu'à n fois. str est spécifié sous la forme n[:t][/match]. Optionnellement, le délai entre les tentatives peut être spécifié par "t", un temps flottant (par défaut 0,5 seconde). Remarque : la réponse n'est pas vérifiée quant à sa validité ou à sa correspondance avec la requête envoyée. La requête "ping:mystring" peut être utilisée pour aider à identifier de manière unique la requête. Optionnellement, une chaîne de correspondance après un "/" sera utilisée pour vérifier le texte résultat. Jusqu'à n tentatives auront lieu jusqu'à ce que la chaîne de correspondance soit trouvée dans le texte de sortie. Si la chaîne de correspondance n'est jamais trouvée, le code de sortie du programme est 1 ; si la correspondance est trouvée, il se termine avec 0. Notez qu'il peut y avoir une sortie standard imprimée pour chaque nouvelle tentative (c'est-à-dire plusieurs lignes imprimées sur la sortie standard). Exemple : -query_retries 4:1.5/grab_state
