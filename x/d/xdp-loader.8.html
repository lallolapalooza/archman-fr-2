xdp-loader(8) Chargeur de programme XDP xdp-loader(8)

NOM

xdp-loader - un chargeur de programme XDP

SYN。
OPSIS

xdp-loader est un chargeur simple pour les programmes XDP avec la prise en charge de l'attachement de plusieurs programmes à la même interface. Pour ce faire, il expose les mêmes sémantiques de chargement et de déchargement exposées par la bibliothèque libxdp. Consultez la page de manuel libxdp(3) pour plus de détails sur le fonctionnement et les fonctionnalités du noyau sur lesquelles il repose.

Exécution xdp-loader

La syntaxe pour exécuter xdp-loader est la suivante :

xdp-loader COMMANDE [options]
Où COMMANDE peut être l'une des suivantes :
       load        - charger un programme XDP sur une interface
       unload      - décharger un programme XDP d'une interface
       status      - afficher l'état actuel du programme XDP
       features    - afficher les fonctionnalités XDP prises en charge par la carte réseau
       clean       - nettoyer les liens de programme détachés dans le répertoire bpffs XDP
       help        - afficher la liste des commandes disponibles

Chaque commande et ses options sont expliquées ci-dessous. Ou utilisez xdp-loader COMMANDE --help pour voir les options de chaque commande.

La commande LOAD

La commande load charge un ou plusieurs programmes XDP sur une interface.

La syntaxe de la commande load est :

xdp-loader load [options] <ifname> <programmes>

Où <ifname> est le nom de l'interface sur laquelle charger les programmes, et <programmes> est un ou plusieurs noms de fichiers contenant des programmes XDP. Les programmes seront chargés sur l'interface dans l'ordre de leur préférence, tel que spécifié par les métadonnées du programme (voir libxdp(3)).

Les options prises en charge sont :

-m, --mode <mode>

Spécifie le mode dans lequel charger le programme XDP à charger. Les valeurs valides sont 'native', qui est le mode XDP par défaut dans le pilote, 'skb', qui provoque l'utilisation du soi-disant mode skb (également connu sous le nom de XDP générique), 'hw' qui provoque le déchargement du programme sur le matériel, ou 'unspecified' qui laisse le noyau choisir un mode (ce qu'il fera en choisissant le mode natif si le pilote le prend en charge, ou le mode générique sinon). Notez que l'utilisation de 'unspecified' peut rendre difficile la prédiction du mode dans lequel un programme sera chargé. Pour cette raison, la valeur par défaut est 'native'. Notez que le matériel prenant en charge le mode 'hw' est rare : les cartes Netronome/Corigine (utilisant le pilote 'nfp') sont les seuls appareils prenant en charge cela dans le noyau Linux principal.

-p, --pin-path <chemin>

Ceci spécifie un chemin racine sous lequel épingler toutes les cartes qui définissent l'attribut 'pinning' dans leurs définitions. Ce chemin doit être situé sur un système de fichiers bpffs. S'il n'est pas défini, les cartes ne seront pas épinglées, même si elles spécifient l'épinglage dans leurs définitions. Lors de l'épinglage des cartes, si l'emplacement épinglé pour une carte existe déjà, la carte épinglée là sera réutilisée si elle est compatible avec le type de la carte en cours de chargement.

-s, --section <section>

Spécifie quelle section ELF charger les programmes XDP depuis chaque fichier. Par défaut, le premier programme de chaque fichier est utilisé. Si cette option est définie, elle s'applique à tous les programmes chargés.

-n, --prog-name <nom_prog>

Spécifie quel programme BPF avec le nom charger les programmes XDP depuis chaque fichier. Par défaut, le premier programme de chaque fichier est utilisé. Une seule des options --section ou --prog-name peut être spécifiée. Si cette option est définie, elle s'applique à tous les programmes chargés.

-P, --prio <priorité>

Spécifie la priorité avec laquelle charger les programmes XDP (cela affecte l'ordre d'exécution des programmes sur l'interface). Par défaut, la valeur des métadonnées du fichier ELF du programme est utilisée, ou une valeur de 50 si le programme n'a pas de telles métadonnées. Si cette option est définie, elle s'applique à tous les programmes chargés.

-A, --actions <actions>

Spécifie les « actions d'appel en chaîne » des programmes XDP chargés. Ce sont les actions XDP qui provoqueront l'appel du programme suivant chargé sur l'interface, au lieu de retourner immédiatement. Par défaut, la valeur définie dans les métadonnées du fichier ELF du programme est utilisée, ou XDP_PASS si aucune métadonnée n'est définie. Si cette option est définie, elle s'applique à tous les programmes chargés.

-v, --verbose

Active la journalisation de débogage. Spécifiez deux fois pour une verborité encore plus grande.

-h, --help

Affiche un résumé des options disponibles

La commande UNLOAD

La commande unload est utilisée pour décharger les programmes d'une interface.

La syntaxe de la commande unload est :

xdp-loader unload [options] <ifname>

Où <ifname> est le nom de l'interface sur laquelle décharger les programmes. Les options --all ou --id doivent être utilisées pour spécifier quel(s) programme(s) décharger.

Les options prises en charge sont :

-i, --id <id>

Décharge un seul programme de l'interface par ID. Utilisez xdp-loader status pour obtenir l'ID du programme en cours de déchargement. Si ce programme est le dernier programme chargé sur l'interface, le programme de dispatch sera également supprimé, ce qui rend l'opération équivalente à la spécification de --all.

-a, --all

Décharge tous les programmes XDP sur l'interface, ainsi que le répartiteur multi-programmes.

-v, --verbose

Active la journalisation de débogage. Spécifiez deux fois pour une verborité encore plus grande.

-h, --help

Affiche un résumé des options disponibles

La commande STATUS

La commande status affiche une liste des interfaces du système et les programmes XDP chargés sur chaque interface. Pour chaque interface, une liste de programmes est affichée, avec la priorité d'exécution et les « actions de chaîne » pour chaque programme. Voir la section sur les métadonnées du programme pour la signification de ces métadonnées.

-v, --verbose

Active la journalisation de débogage. Spécifiez deux fois pour une verborité encore plus grande.

-h, --help

Affiche un résumé des options disponibles

La commande FEATURES

La commande features affiche les fonctionnalités XDP prises en charge par la carte réseau.

Les fonctionnalités XDP actuellement prises en charge sont :

NETDEV_XDP_ACT_BASIC

Le périphérique réseau prend en charge de manière basique l'exécution de programmes XDP et peut gérer l'ensemble de base des codes de retour (XDP_ABORTED, XDP_DROP, XDP_PASS, XDP_TX).

NETDEV_XDP_ACT_REDIRECT

Le périphérique réseau prend en charge la gestion du code de retour XDP_REDIRECT. Cela signifie que les paquets peuvent être redirigés depuis ce périphérique par XDP.

NETDEV_XDP_ACT_NDO_XMIT

Les interfaces réseau implémentent le rappel ndo_xdp_xmit. Cela signifie que les paquets peuvent être redirigés

xdp-loader(8) — Outils XDP

NAME

xdp-loader

utility to load and unload XDP programs

SYNOPSIS

xdp-loader command [options] [ifname]

The LOAD command

The syntax for the load command is:

xdp-loader load [options] ifname bpf_obj

The load command loads the BPF object file bpf_obj onto the network interface ifname. The program to load can be specified via the --prog-name option, otherwise the first program found in the object file will be loaded.

The supported options are:

-p, --pin-path

Pin the loaded program to the specified path. This is required for loading programs in native mode. The path must be under /sys/fs/bpf.

-N, --prog-name

Name of the program to load from the BPF object file. Defaults to the first program found.

-m, --mode

Load mode. Supported modes are:

skb
Load the program in skb mode. This mode works on all kernel versions but requires packets to be copied from kernel to user space.
native
Load the program in native mode. This mode offers the best performance but requires kernel support for native XDP.
offload
Load the program on the NIC hardware. This requires hardware support.

-c, --caller-info

Include caller information in the program, e.g. program name and file name. This requires kernel support.

-v, --verbose

Enable debug logging. Specify twice for even more verbosity.

-h, --help

Display a summary of the available options

The UNLOAD command

The syntax for the unload command is:

xdp-loader unload [options] [ifname]

The unload command unloads the XDP program from the network interface ifname. If ifname is not specified, all loaded XDP programs are unloaded.

The supported options are:

-v, --verbose

Enable debug logging. Specify twice for even more verbosity.

-h, --help

Display a summary of the available options

The STATUS command

The syntax for the status command is:

xdp-loader status [options] [ifname]

The status command displays the current XDP program status for the network interface ifname. If ifname is not specified, the status for all interfaces is displayed.

The supported options are:

-v, --verbose

Enable debug logging. Specify twice for even more verbosity.

-h, --help

Display a summary of the available options

The FEATURES command

The syntax for the features command is:

xdp-loader features [ifname]

The features command displays the supported XDP features for the network interface ifname. If ifname is not specified, the features for all interfaces are displayed.

The supported features are:

NETDEV_XDP_ACT_XSK_REDIRECT

The networking device supports redirection to AF_XDP sockets.

NETDEV_XDP_ACT_XSK_ZEROCOPY

The networking device supports AF_XDP in zero copy mode.

NETDEV_XDP_ACT_HW_OFFLOAD

The networking device supports XDP hw offloading.

NETDEV_XDP_ACT_RX_SG

The networking device supports non-linear XDP frames on the receive side. This means XDP can be used with big MTUs on this device (if the XDP program is compiled with fragments support)

NETDEV_XDP_ACT_NDO_XMIT_SG

The networking device supports non-linear XDP frames on the transmit side. This means non-linear frames can be redirected to this device.

The CLEAN command

The syntax for the clean command is:

xdp-loader clean [options] [ifname]

The clean command cleans up any detached program links in the XDP bpffs directory. When a network interface disappears, any programs loaded in software mode (e.g. skb, native) remain pinned in the bpffs directory, but become detached from the interface. These need to be unlinked from the filesystem. The clean command takes an optional interface parameter to only unlink detached programs corresponding to the interface. By default, all detached programs for all interfaces are unlinked.

The supported options are:

-v, --verbose

Enable debug logging. Specify twice for even more verbosity.

-h, --help

Display a summary of the available options

Examples

To load an XDP program on the eth0 interface simply do:

# xdp-loader load eth0 xdp_drop.o
# xdp-loader status
CURRENT XDP PROGRAM STATUS:
Interface        Prio  Program name     Mode     ID   Tag               Chain actions
-------------------------------------------------------------------------------------
lo               <no XDP program>
eth0                   xdp_dispatcher   native   50   d51e469e988d81da
 =>              50    xdp_drop                  55   57cd311f2e27366b  XDP_PASS

Which shows that a dispatcher program was loaded on the interface, and the xdp_drop program was installed as the first (and only) component program after it. In this instance, the program does not specify any of the metadata above, so the defaults (priority 50 and XDP_PASS as its chain call action) was used.

To use the automatic map pinning, include the pinning attribute into the map definition in the program, something like:

struct {
        __uint(type, BPF_MAP_TYPE_ARRAY);
        __uint(max_entries, 10);
        __type(key, __u32);
        __type(value, __u64);
        __uint(pinning, LIBBPF_PIN_BY_NAME);
} my_map SEC(".maps");

And load it with the --pin-path attribute:

# xdp-loader load eth0 my_prog.o --pin-path /sys/fs/bpf/my-prog

This will pin the map at /sys/fs/bpf/my-prog/my_map. If this already exists, the pinned map will be reused instead of creating a new one, which allows different BPF programs to share the map.

SEE ALSO

libxdp(3) for details on the XDP loading semantics and kernel compatibility requirements.
