NOM

XDP-bench - un outil simple de benchmarking XDP

SYNOPIS

XDP-bench est un utilitaire de benchmarking destiné à tester les différents modes de fonctionnement de XDP. Il est conçu pour être un programme simple démontrant les divers modes de fonctionnement ; ceux-ci incluent le rejet de paquets, le transfert en épingle à cheveux (hairpin forwarding) (en utilisant le code de retour XDP_TX), et la redirection en utilisant les diverses facilités de redirection de paquets du noyau.

Les modes de rejet et TX prennent en charge diverses options pour contrôler si les données du paquet sont touchées (lues ou écrites) avant d'être rejetées ou transmises. Les modes de redirection prennent en charge l'utilisation de l'aide bpf_redirect basée sur l'index d'interface, l'aide bpf_redirect_map utilisant un cpumap comme cible, l'aide bpf_redirect_map utilisant un devmap comme cible, et le mode de diffusion (broadcast) du devmap qui permet la redirection vers plusieurs interfaces.

Il y a plus d'informations sur la signification des résultats en mode de sortie par défaut (succinct) et en mode étendu, dans la section Description du format de sortie ci-dessous.

Exécution de xdp-bench

La syntaxe pour exécuter xdp-bench est :

Usage : xdp-bench COMMANDE [options]
La COMMANDE peut être l'une des suivantes :
       drop           - Rejeter tous les paquets sur une interface
       pass           - Transmettre tous les paquets à la pile réseau
       tx             - Transmettre les paquets en retour sur une interface (transfert en épingle à cheveux)
       redirect       - Redirection XDP utilisant l'aide bpf_redirect()
       redirect-cpu   - Redirection CPU XDP utilisant BPF_MAP_TYPE_CPUMAP
       redirect-map   - Redirection XDP utilisant BPF_MAP_TYPE_DEVMAP
       redirect-multi - Multi-redirection XDP utilisant BPF_MAP_TYPE_DEVMAP et le drapeau BPF_F_BROADCAST

Chaque commande et ses options sont expliquées ci-dessous. Ou utilisez xdp-bench COMMANDE --help pour voir les options de chaque commande.

La commande DROP

Dans ce mode, xdp-bench installe un programme XDP sur une interface qui rejette simplement tous les paquets. Il existe des options pour contrôler ce qu'il faut faire avec le paquet avant de le rejeter (toucher les données du paquet ou non), ainsi que quelles statistiques collecter. C'est un benchmark de base pour les performances de référence (cas le plus favorable) de XDP sur une interface.

La syntaxe pour la commande drop est :

xdp-bench drop [options] <nom_if>

Où <nom_if> est le nom de l'interface sur laquelle le programme XDP doit être installé.

Les options prises en charge sont :

-p, --operation-paquet <ACTION>

Spécifie quelle opération doit être effectuée sur le paquet avant de le rejeter. Les actions suivantes sont disponibles :

no-touch		- Rejeter le paquet sans toucher aux données du paquet
read-data		- Lire un champ dans l'en-tête du paquet avant de rejeter
parse-ip		- Analyser le champ d'en-tête IP avant de rejeter
swap-macs		- Échanger les adresses MAC source et destination avant de rejeter

Si le paquet est touché avant d'être rejeté peut avoir un impact significatif sur les performances car cela nécessite de charger les données du paquet dans le cache CPU (et de le vider si écriture).

La valeur par défaut pour cette option est no-touch.

-l, --mode-chargement <MODE>

Spécifie quel mécanisme xdp-bench doit utiliser pour charger (et stocker) les données du paquet. Les modes suivants sont disponibles :

dpa		- Utiliser l'accès direct aux paquets (Direct Packet Access) traditionnel depuis le programme XDP
load-bytes	- Utiliser les fonctions d'aide xdp_load_bytes() et xdp_store_bytes()

Ceci peut être utilisé pour tester les différents modes d'accès aux paquets pris en charge par le noyau.

La valeur par défaut pour cette option est dpa.

-r, --stats-rxq

Si défini, le programme XDP collectera également des statistiques sur l'index de la file de réception sur laquelle chaque paquet a été reçu. Ceci est affiché en mode de sortie étendu avec les données par CPU (qui, selon la configuration matérielle, peuvent être équivalentes ou non).

-i, --interval <SECONDES>

Définit l'intervalle d'interrogation pour collecter toutes les statistiques et les afficher en sortie. L'unité de l'intervalle est en secondes.

-e, --extended

Démarre xdp-bench en mode de sortie « étendu ». S'il n'est pas défini, xdp-bench démarrera en mode « succinct ». Le mode de sortie peut être changé en appuyant sur C-$ pendant que le programme s'exécute. Voir également la section Description du format de sortie ci-dessous.

-m, --mode

Sélectionne le mode du programme XDP (natif ou skb). Notez que le mode XDP natif est le mode par défaut, et charger le programme de redirection en mode skb n'est ni performant ni recommandé. Cependant, cette option est utile si le pilote de l'interface ne prend pas en charge XDP nativement, ou simplement pour tester l'outil.

-v, --verbose

Active la journalisation détaillée. Fournissez deux fois pour activer la journalisation détaillée des bibliothèques sous-jacentes libxdp et libbpf.

--version

Affiche la version de l'application et quitte.

-h, --help

Affiche un résumé des options disponibles

La commande TX

Dans ce mode, xdp-bench installe un programme XDP sur une interface qui effectue ce qu'on appelle le « hairpin forwarding », ce qui signifie que chaque paquet est retransmis sur la même interface (en utilisant le code de retour XDP_TX). Il existe des options pour contrôler ce qu'il faut faire du paquet avant de le transmettre (modifier ou non les données du paquet), ainsi que quelles statistiques collecter.

La syntaxe de la commande tx est la suivante :

xdp-bench tx [options] <ifname>

Où <ifname> est le nom de l'interface sur laquelle le programme XDP doit être installé.

Les options prises en charge sont les suivantes :

-p, --packet-operation <ACTION>

Spécifie quelle opération doit être effectuée sur le paquet avant de le transmettre. Les actions suivantes sont disponibles :

no-touch		- Transmettre le paquet sans toucher aux données du paquet
read-data		- Lire un champ dans l'en-tête du paquet avant de transmettre
parse-ip		- Analyser le champ d'en-tête IP avant de transmettre
swap-macs		- Échanger les adresses MAC source et destination avant de transmettre

Pour que le paquet puisse être correctement retransmis à l'expéditeur, les adresses MAC doivent être échangées, de sorte que la MAC source corresponde au périphérique réseau. Cependant, l'échange entraîne une surcharge de performance, cette option permet donc de désactiver cette fonctionnalité.

La valeur par défaut pour cette option est swap-macs.

-l, --load-mode <MODE>

Spécifie quel mécanisme xdp-bench doit utiliser pour charger (et stocker) les données des paquets. Les modes suivants sont disponibles :

dpa		- Utiliser l'accès direct aux paquets traditionnel depuis le programme XDP
load-bytes	- Utiliser les fonctions d'aide xdp_load_bytes() et xdp_store_bytes()

Ceci peut être utilisé pour évaluer les différents modes d'accès aux paquets pris en charge par le noyau.

La commande REDIRECT-CPU

Dans ce mode, xdp-bench configure la redirection de paquets en utilisant la fonction d'aide BPF bpf_redirect_map déclenchée à la réception d'un paquet sur l'interface d'entrée, en utilisant un cpumap comme cible. Par conséquent, cet outil peut être utilisé pour rediriger des paquets sur une interface d'un CPU à un autre. En plus de cela, l'outil permet ensuite de rediriger le paquet vers un autre périphérique de sortie lorsqu'il est traité sur le CPU cible.

La syntaxe de la commande redirect-cpu est la suivante :

xdp-bench redirect-cpu [options] <ifname> -c 0 ... -c N

Où <ifname> est le nom de l'interface d'entrée depuis laquelle les paquets seront redirigés vers la liste de CPU cibles spécifiée avec -c.

Les options prises en charge sont les suivantes :

-c, --cpu <CPU>

Spécifie un indice de CPU cible possible. Cette option doit être passée au moins une fois et peut être passée plusieurs fois pour spécifier une liste de CPU. Le CPU choisi pour un paquet donné dépend de la valeur de l'option --program-mode, décrite ci-dessous.

-p, --program-mode <MODE>

Spécifie un programme qui intègre une politique prédéfinie décidant comment les paquets sont redirigés vers différents CPU. Les options suivantes sont disponibles :

no-touch		- Rediriger sans toucher aux données du paquet
touch		- Lire les données du paquet avant de rediriger
round-robin	- Alterner entre les CPU cibles de manière cyclique (pour chaque paquet)
l4-proto		- Choisir le CPU cible en fonction du protocole de couche 4 du paquet
l4-filter		- Comme l4-proto, mais ignorer les paquets UDP avec port de destination 9 (utilisé par pktgen)
l4-hash		- Utiliser le hachage des adresses IP source et destination pour choisir le CPU cible
l4-sport		- Utiliser le modulo du port source pour choisir le CPU cible
l4-dport		- Utiliser le modulo du port de destination pour choisir le CPU cible

Les modes no-touch et touch redirigent toujours les paquets vers le même CPU (la première valeur fournie à --cpu). Les modes round-robin et l4-hash distribuent les paquets entre tous les CPU fournis comme arguments --cpu, tandis que l4-proto et l4-filter envoient les paquets TCP et non reconnus à l'indice de CPU 0, les paquets UDP à l'indice de CPU 1 et les paquets ICMP à l'indice de CPU 2 (où l'indice fait référence à l'ordre dans lequel les CPU réels sont donnés sur la ligne de commande).

La valeur par défaut pour cette option est l4-hash.

-r --remote-action <ACTION>

Si cette option est définie, un programme séparé est installé dans le cpumap, qui sera appelé sur le CPU distant après que le paquet y ait été traité. L'action peut être drop (ignorer) ou pass (transmettre) ce qui fera ignorer le paquet ou le transmettra à la pile réseau normale, respectivement. Ou ce peut être redirect, ce qui entraînera la redirection du paquet vers une autre interface et sa transmission hors de cette interface sur le CPU distant. Si cette option est définie sur redirect, le périphérique cible doit être spécifié en utilisant --redirect-device.

La valeur par défaut pour cette option est désactivé.

-r, --redirect-device <IFNAME>

Spécifie le périphérique vers lequel le paquet doit être redirigé lorsqu'il est reçu sur le CPU cible. Notez que cette option ne peut être spécifiée qu'avec --remote-action redirect.

-q, --qsize <PAQUETS>

Description du format de sortie

Par défaut, les statistiques de succès de redirection sont désactivées, utilisez --stats pour les activer. Le mode de sortie concis est le mode par défaut, le mode de sortie étendu peut être activé à l'aide de l'option de ligne de commande --extended.

SIGQUIT (Ctrl + \) peut être utilisé pour changer le mode dynamiquement pendant l'exécution.

Le mode concis affiche au plus les champs suivants :

rx/s		Nombre de paquets reçus par seconde
redir/s	Nombre de paquets redirigés avec succès par seconde
err,drop/s	Nombre agrégé d'erreurs par seconde (y compris les paquets abandonnés lorsque la commande drop n'est pas utilisée)
xmit/s	Nombre de paquets transmis sur le périphérique de sortie par seconde

Le mode de sortie étendu affiche au plus les champs suivants :

CHAMP		  DESCRIPTION
receive	       Affiche le nombre de paquets reçus et les erreurs rencontrées
                        Chaque fois qu'une erreur ou un abandon de paquet se produit, les détails des erreurs et des abandons par CPU
                        sont développés en ligne dans le mode concis.
                                        pkt/s		- Paquets reçus par seconde
                                        drop/s		- Paquets abandonnés par seconde
                                        error/s		- Erreurs rencontrées par seconde
                                        redirect	- Affiche le nombre de paquets redirigés avec succès
                       Les erreurs rencontrées sont développées sous le champ redirect_err
                       Notez que passer -s pour l'activer a un surcoût par paquet
                                        redir/s		- Paquets redirigés avec succès par seconde
redirect_err	  Affiche le nombre de paquets dont la redirection a échoué
                        L'errno est développé sous ce champ avec le compte par CPU
                       Les erreurs reconnues sont :
                                        EINVAL:		Redirection invalide
                                        ENETDOWN:	Périphérique vers lequel la redirection est effectuée est arrêté
                                        EMSGSIZE:	La taille du paquet est trop grande pour le périphérique
                                        EOPNOTSUPP:	Opération non prise en charge
                                        ENOSPC:		Pas d'espace dans le ptr_ring du kthread cpumap
                                        error/s		- Paquets dont la redirection a échoué par seconde
enqueue to cpu N Affiche le nombre de paquets mis en file d'attente dans la file d'attente groupée du CPU N
                       Se développe en cpu:FROM->N pour afficher les statistiques de mise en file d'attente pour chaque CPU qui met en file d'attente vers le CPU N
                       Les paquets reçus peuvent être associés au CPU vers lequel le programme de redirection met en file d'attente
                       les paquets.
                                        pkt/s		- Paquets mis en file d'attente par seconde depuis un autre CPU vers le CPU N
                                        drop/s		- Paquets abandonnés lors de la tentative de mise en file d'attente vers le CPU N
                                        bulk-avg	- Nombre moyen de paquets traités pour chaque événement
kthread	       Affiche le nombre de paquets traités dans le kthread CPUMAP pour chaque CPU
                       Les paquets consommés à partir du ptr_ring dans le kthread, et ses xdp_stats (après l'appel
                       du programme BPF CPUMAP) sont développés sous celui-ci. Les xdp_stats sont développés en tant que total puis
                       par CPU pour l'associer au kthread CPUMAP de chaque CPU.
                                        pkt/s		- Paquets consommés par seconde à partir du ptr_ring
                                        drop/s		- Paquets abandonnés par seconde dans le kthr
ead sched - Nombre de fois que kthread a appelé schedule() xdp_stats (s'étend également aux comptages par CPU) pass/s - Compte XDP_PASS pour l'exécution du programme CPUMAP drop/s - Compte XDP_DROP pour l'exécution du programme CPUMAP redir/s - Compte XDP_REDIRECT pour l'exécution du programme CPUMAP xdp_exception Affiche les événements du point de trace xdp_exception Cela peut se produire en raison d'erreurs internes du pilote, d'actions XDP non reconnues et en raison d'un déclenchement utilisateur explicite par l'utilisation de XDP_ABORTED. Chaque action est développée sous ce champ avec son compte. hit/s - Nombre de fois que le point de trace a été atteint par seconde devmap_xmit Affiche les événements du point de trace devmap_xmit Ce point de trace est appelé pour les transmissions réussies sur le périphérique de sortie, mais ces statistiques ne sont pas disponibles pour le mode XDP générique. Par conséquent, elles seront omises de la sortie lors de l'utilisation du mode SKB. xmit/s - Nombre de paquets transmis par seconde drop/s - Nombre de paquets dont la transmission a échoué par seconde drv_err/s - Nombre d'erreurs internes du pilote par seconde bulk-avg - Nombre moyen de paquets traités pour chaque événement
