NOM

xdm - Gestionnaire d'affichage X avec prise en charge de XDMCP, choix d'hôtes

SYNTAXE

xdm [ -config fichier_configuration ] [ -nodaemon ] [ -debug niveau_debug ] [ -error fichier_journal_erreurs ] [ -resources fichier_ressources ] [ -server entrée_serveur ] [ -session programme_session ]

DESCRIPTION

Xdm gère une collection d'affichages X, qui peuvent être sur la machine locale ou sur des serveurs distants. La conception de xdm a été guidée par les besoins des terminaux X ainsi que par le standard XDMCP de The Open Group, le X Display Manager Control Protocol. Xdm fournit des services similaires à ceux fournis par init, getty et login sur les terminaux caractères : demander le nom d'utilisateur et le mot de passe, authentifier l'utilisateur et exécuter une « session ».

Une « session » est définie par la durée de vie d'un processus particulier ; dans le monde traditionnel des terminaux caractères, c'est le shell de connexion de l'utilisateur. Dans le contexte de xdm, c'est un gestionnaire de session arbitraire. Ceci est dû au fait que dans un environnement graphique, le processus du shell de connexion de l'utilisateur n'a pas nécessairement d'interface de type terminal avec laquelle se connecter. Lorsqu'un véritable gestionnaire de session n'est pas disponible, un gestionnaire de fenêtres ou un émulateur de terminal est typiquement utilisé comme « gestionnaire de session », ce qui signifie que la terminaison de ce processus termine la session de l'utilisateur.

Lorsque la session est terminée, xdm réinitialise le serveur X et (facultativement) redémarre tout le processus.

Lorsque xdm reçoit une requête Indirecte via XDMCP, il peut exécuter un processus chooser pour effectuer une requête BroadcastQuery XDMCP (ou une requête Query XDMCP vers des hôtes spécifiés) pour le compte de l'affichage et proposer un menu des hôtes possibles qui offrent la gestion d'affichage XDMCP. Cette fonctionnalité est utile avec les terminaux X qui ne proposent pas eux-mêmes de menu d'hôtes.

Xdm peut être configuré pour ignorer les messages BroadcastQuery provenant d'hôtes sélectionnés. Ceci est utile lorsque vous ne voulez pas que l'hôte apparaisse dans les menus produits par chooser ou par les terminaux X eux-mêmes.

Étant donné que xdm fournit la première interface que les utilisateurs verront, il est conçu pour être simple à utiliser et facile à personnaliser selon les besoins d'un site particulier. Xdm a de nombreuses options, dont la plupart ont des valeurs par défaut raisonnables. Parcourez les différentes sections de ce manuel, en choisissant les éléments que vous souhaitez modifier. Portez une attention particulière à la section Programme de Session, qui décrira comment configurer le style de session désiré.

APERÇU

xdm est hautement configurable, et la plupart de ses comportements peuvent être contrôlés par des fichiers de ressources et des scripts shell. Les noms de ces fichiers eux-mêmes sont des ressources lues dans le fichier xdm-config ou le fichier nommé par l'option -config.

xdm offre la gestion d'affichage de deux manières différentes. Il peut gérer les serveurs X fonctionnant sur la machine locale et spécifiés dans Xservers, et il peut gérer les serveurs X distants (typiquement des terminaux X) en utilisant XDMCP (le protocole XDM Control Protocol) comme spécifié dans le fichier Xaccess.

Les ressources des clients X exécutés par xdm en dehors de la session de l'utilisateur, y compris la fenêtre de connexion de xdm elle-même, peuvent être affectées en définissant des ressources dans le fichier Xresources.

Pour les terminaux X qui n'offrent pas de menu d'hôtes pour obtenir la gestion d'affichage, xdm peut collecter les hôtes disposés et exécuter le programme chooser pour offrir à l'utilisateur un menu. Pour les affichages X connectés à un hôte, cette étape n'est généralement pas utilisée, car l'hôte local effectue la gestion de l'affichage.

Après avoir réinitialisé le serveur X, xdm exécute le script Xsetup pour aider à configurer l'écran que l'utilisateur voit avec le widget xlogin.

Le widget xlogin, que xdm présente, offre les invites de connexion et de mot de passe familières.

Après que l'utilisateur se soit connecté, xdm exécute le script Xstartup en tant que root.

Ensuite, xdm exécute le script Xsession en tant qu'utilisateur. Ce fichier de session système peut effectuer des démarrages supplémentaires et exécute typiquement le script .xsession dans le répertoire personnel de l'utilisateur. Lorsque le script Xsession se termine, la session est terminée.

À la fin de la session, le script Xreset est exécuté pour le nettoyage, le serveur X est réinitialisé et le cycle recommence.

Le fichier /var/log/xdm.log contiendra les messages d'erreur de xdm et tout ce qui est écrit sur stderr par Xsetup, Xstartup, Xsession ou Xreset. Lorsque vous rencontrez des problèmes pour faire fonctionner xdm, vérifiez ce fichier pour voir si xdm a des indices sur le problème.

OPTIONS

Toutes ces options, à l'exception de -config elle-même, spécifient des valeurs qui peuvent également être spécifiées dans le fichier de configuration en tant que ressources.

-config fichier_configuration
Nomme le fichier de configuration, qui spécifie les ressources pour contrôler le comportement de xdm. /etc/X11/xdm/xdm-config est le défaut. Voir la section Fichier de Configuration.
-nodaemon
Spécifie « false » comme valeur pour la ressource DisplayManager.daemonMode. Ceci supprime le comportement normal de daemon, qui consiste pour xdm à fermer tous les descripteurs de fichiers, à se détacher du terminal de contrôle et à se placer en arrière-plan dès son démarrage.
-debug niveau_debug
Spécifie la valeur numérique pour la ressource DisplayManager.debugLevel. Une valeur non nulle provoquera l'affichage par xdm de nombreux messages de débogage sur le terminal ; cela désactive également la ressource DisplayManager.daemonMode, forçant xdm à s'exécuter de manière synchrone. Pour interpréter ces messages de débogage, une copie du code source de xdm est presque indispensable. Aucune tentative n'a été faite pour rationaliser ou standardiser la sortie.
-error fichier_journal_erreurs
Spécifie la valeur pour la ressource DisplayManager.errorLogFile. Ce fichier contient les erreurs de xdm ainsi que tout ce qui est écrit sur stderr par les divers scripts et programmes exécutés au cours de la session.
-resources fichier_ressources
Spécifie la valeur pour la ressource DisplayManager*resources. Ce fichier est chargé en utilisant xrdb(1) pour spécifier les paramètres de configuration pour le widget d'authentification.
-server entrée_serveur
Spécifie la valeur pour la ressource DisplayManager.servers. Voir la section Spécification du Serveur Local pour une description de cette ressource.
-udpPort numéro_port
Spécifie la valeur pour la ressource DisplayManager.requestPort. Ceci définit le numéro de port sur lequel xdm surveillera les requêtes XDMCP. Si défini sur 0, xdm n'écoutera pas les requêtes XDMCP ou Chooser. Comme XDMCP utilise le port UDP bien connu enregistré 177, cette ressource ne doit pas être changée à une valeur autre que 0, sauf pour le débogage.
-session programme_session
Spécifie la valeur pour la ressource DisplayManager*session. Ceci indique le programme à exécuter en tant que session après la connexion de l'utilisateur.
-xrm spécification_ressource
Permet de spécifier une ressource arbitraire, comme pour la plupart des applications X Toolkit.

RESSOURCES

À de nombreuses étapes, les actions de xdm peuvent être contrôlées par l'utilisation de son fichier de configuration, qui est au format de ressource X. Certaines ressources modifient le comportement de xdm sur tous les affichages, tandis que d'autres modifient son comportement sur un seul affichage. Lorsque les actions concernent un affichage spécifique, le nom de l'affichage est inséré dans le nom de la ressource entre « DisplayManager » et le dernier segment du nom de la ressource.

Pour les affichages locaux, le nom de la ressource et la classe sont lus à partir du fichier Xservers.

Étant donné que le gestionnaire de ressources utilise des deux-points pour séparer le nom de la ressource de sa valeur et des points pour séparer les parties du nom de la ressource, xdm remplace les points et les deux-points par des traits de soulignement lors de la génération du nom de la ressource. Par exemple, DisplayManager.expo_x_org_0.startup est le nom de la ressource qui définit le fichier shell de démarrage pour l'écran « expo.x.org:0 ».

DisplayManager.servers
Cette ressource spécifie soit un nom de fichier contenant des entrées de serveur, une par ligne (si la valeur commence par un slash), soit une seule entrée de serveur. Voir la section Spécification du serveur local pour plus de détails.
DisplayManager.requestPort
Ceci indique le numéro de port UDP que xdm utilise pour écouter les requêtes XDMCP entrantes. Sauf si vous avez besoin de déboguer le système, laissez cette valeur à sa valeur par défaut de 177.
DisplayManager.errorLogFile
La sortie d'erreur est normalement dirigée vers la console système. Pour la rediriger, définissez cette ressource sur un nom de fichier. Une méthode pour envoyer ces messages à syslog devrait être développée pour les systèmes qui le prennent en charge ; cependant, la grande variété d'interfaces exclut toute implémentation indépendante du système. Ce fichier contient également toute sortie dirigée vers stderr par les fichiers Xsetup, Xstartup, Xsession et Xreset, il contiendra donc également des descriptions de problèmes dans ces scripts.
DisplayManager.debugLevel
Si la valeur entière de cette ressource est supérieure à zéro, des quantités énormes d'informations de débogage seront imprimées. Cela désactive également le mode démon, qui redirigerait les informations vers la corbeille, et permet aux utilisateurs non root d'exécuter xdm, ce qui ne serait normalement pas utile.
DisplayManager.daemonMode
Normalement, xdm tente de se transformer en un processus démon non associé à aucun terminal. Ceci est réalisé en créant un fork et en laissant le processus parent se terminer, puis en fermant les descripteurs de fichiers et en libérant le terminal de contrôle. Dans certains environnements, ce n'est pas souhaitable (en particulier lors du débogage). La définition de cette ressource sur « false » désactivera cette fonctionnalité.
DisplayManager.pidFile
Le nom de fichier spécifié sera créé pour contenir une représentation ASCII de l'identifiant du processus du processus principal xdm. Xdm utilise également le verrouillage de fichier sur ce fichier pour tenter d'éliminer l'exécution de plusieurs démons sur la même machine, ce qui causerait beaucoup de chaos.
DisplayManager.lockPidFile
C'est la ressource qui contrôle si xdm utilise le verrouillage de fichier pour empêcher plusieurs gestionnaires d'affichage de fonctionner de manière anarchique. Sur System V, cela utilise l'appel de bibliothèque lockf, tandis que sur BSD, il utilise flock.
DisplayManager.authDir
Ceci nomme un répertoire sous lequel xdm stocke les fichiers d'autorisation lors de l'initialisation de la session. La valeur par défaut est /var/lib/xdm. Peut être remplacé pour des écrans spécifiques par DisplayManager.DISPLAY.authFile.
DisplayManager.autoRescan
Ce booléen contrôle si xdm re-scanne les fichiers de configuration, de serveurs, de contrôle d'accès et de clés d'authentification après la fin d'une session et si les fichiers ont changé. Par défaut, il est « true ». Vous pouvez forcer xdm à relire ces fichiers en envoyant un SIGHUP au processus principal.
DisplayManager.removeDomainname
Lors du calcul du nom d'affichage pour les clients XDMCP, le résolveur de noms créera généralement un nom d'hôte qualifié complet pour le terminal. Comme cela est parfois déroutant, xdm supprimera la partie nom de domaine du nom d'hôte s'il est identique au nom de domaine de l'hôte local lorsque cette variable est définie. Par défaut, la valeur est « true ».
DisplayManager.keyFile
L'authentification XDMCP de style XDM-AUTHENTICATION-1 nécessite qu'une clé privée soit partagée entre xdm et le terminal. Cette ressource spécifie le fichier contenant ces valeurs. Chaque entrée dans le fichier se compose d'un nom d'affichage et de la clé partagée.
DisplayManager.accessFile
Pour empêcher le service XDMCP non autorisé et pour permettre le transfert des requêtes XDMCP IndirectQuery, ce fichier contient une base de données de noms d'hôtes qui sont soit autorisés à accéder directement à cette machine, soit qui ont une liste d'hôtes vers lesquels les requêtes doivent être transférées. Le format de ce fichier est décrit dans la section Contrôle d'accès XDMCP.
DisplayManager.exportList
Une liste de variables d'environnement supplémentaires, séparées par des espaces blancs, à passer aux programmes Xsetup, Xstartup, Xsession et Xreset.
DisplayManager.randomDevice
Un fichier à partir duquel lire 8 octets pour générer la graine des clés d'autorisation. Le défaut est /dev/urandom . Si ce fichier ne peut pas être lu, ou si une lecture bloque pendant plus de 5 secondes, xdm se rabat sur l'utilisation d'une somme de contrôle de DisplayManager.randomFile pour générer la graine.
DisplayManager.greeterLib
Sur les systèmes qui prennent en charge une bibliothèque de greeter chargeable dynamiquement, le nom de la bibliothèque. La valeur par défaut est /usr/lib/X11/xdm/libXdmGreet.so.
DisplayManager.choiceTimeout
Nombre de secondes à attendre pour que l'écran réponde après que l'utilisateur ait sélectionné un hôte dans le sélecteur. Si l'écran envoie une XDMCP IndirectQuery dans ce délai, la requête est transférée à l'hôte choisi. Sinon, elle est supposée provenir d'une nouvelle session et le sélecteur est proposé à nouveau. Par défaut, 15.
DisplayManager.sourceAddress
Utiliser l'adresse IP numérique de la connexion entrante sur les hôtes multihébergés au lieu du nom d'hôte. Ceci afin d'éviter d'essayer de se connecter sur la mauvaise interface qui pourrait être inactive à ce moment-là.
DisplayManager.willing
Ceci spécifie un programme qui est exécuté (en tant que root) lorsqu'une XDMCP BroadcastQuery est reçue et que cet hôte est configuré pour offrir la gestion d'écran XDMCP. La sortie de ce programme peut être affichée dans une fenêtre de sélecteur. Si aucun programme n'est spécifié, la chaîne Willing to manage est envoyée.
DisplayManager.DISPLAY.resources
Cette ressource spécifie le nom du fichier à charger par xrdb en tant que base de données de ressources sur la fenêtre racine de l'écran 0 de l'écran. Le programme Xsetup, le widget Login et chooser utiliseront les ressources définies dans ce fichier. Cette base de données de ressources est chargée juste avant le début de la procédure d'authentification, elle peut donc contrôler l'apparence de la fenêtre de connexion. Voir la section Widget d'authentification, qui décrit les différentes ressources appropriées à placer dans ce fichier. Il n'y a pas de valeur par défaut pour cette ressource, mais /etc/X11/xdm/Xresources est le nom conventionnel.
DisplayManager.DISPLAY.chooser
Spécifie le programme exécuté pour proposer un menu d'hôtes pour les requêtes Indirectes redirigées vers le nom d'hôte spécial CHOOSER. /usr/lib/X11/xdm/chooser est la valeur par défaut. Voir les sections Contrôle d'accès XDMCP et Sélecteur.
DisplayManager.DISPLAY.xrdb
Spécifie le programme utilisé pour charger les ressources. Par défaut, xdm utilise /usr/bin/xrdb.
DisplayManager.DISPLAY.setup
Ceci spécifie un programme qui est exécuté (en tant que root) avant de proposer la fenêtre Login. Ceci peut être utilisé pour changer l'apparence de l'écran autour de la fenêtre Login ou pour afficher d'autres fenêtres (par exemple, vous pouvez vouloir exécuter xconsole ici). Par défaut, aucun programme n'est exécuté. Le nom conventionnel d'un fichier utilisé ici est Xsetup. Voir la section Programme de configuration.
DisplayManager.DISPLAY.startup
Ceci spécifie un programme qui est exécuté (en tant que root) après que le processus d'authentification ait réussi. Par défaut, aucun programme n'est exécuté. Le nom conventionnel d'un fichier utilisé ici est Xstartup. Voir la section Programme de démarrage.
DisplayManager.DISPLAY.session
Ceci spécifie la session à exécuter (pas en tant que root). Par défaut, /usr/bin/xterm est exécuté. Le nom conventionnel est Xsession. Voir la section Programme de session.
DisplayManager.DISPLAY.reset
Ceci spécifie un programme qui est exécuté (en tant que root) après la fin de la session. Par défaut, aucun programme n'est exécuté. Le nom conventionnel est Xreset. Voir la section Programme de réinitialisation.
DisplayManager.DISPLAY.openDelay
DisplayManager.DISPLAY.openRepeat
DisplayManager.DISPLAY.openTimeout
DisplayManager.DISPLAY.startAttempts
DisplayManager.DISPLAY.reservAttempts
Ces ressources numériques contrôlent le comportement de xdm lors des tentatives d'ouverture de serveurs récalcitrants. openDelay est la durée de la pause en secondes entre les tentatives successives, openRepeat est le nombre de tentatives à effectuer, openTimeout est le temps d'attente lors de la tentative d'ouverture (c'est-à-dire le temps maximum passé dans l'appel système connect(2)) et startAttempts est le nombre de fois où tout ce processus est effectué avant d'abandonner le serveur. Après avoir effectué openRepeat tentatives, ou si openTimeout secondes s'écoulent lors d'une tentative particulière, xdm termine et redémarre le serveur, en essayant de se reconnecter. Ce processus est répété startAttempts fois, après quoi l'écran est déclaré mort et désactivé. Bien que ce comportement puisse sembler arbitraire, il a été développé empiriquement et fonctionne très bien sur la plupart des systèmes. La borne reservAttempts est le nombre de fois qu'une connexion réussie peut être suivie d'une erreur fatale. Lorsqu'elle est atteinte, l'écran est désactivé. Les valeurs par défaut sont openDelay : 15, openRepeat : 5, openTimeout : 120, startAttempts : 4 et reservAttempts : 2.
DisplayManager.DISPLAY.pingInterval
DisplayManager.DISPLAY.pingTimeout
Pour détecter la disparition des écrans distants, xdm les interroge périodiquement en utilisant une connexion X et des appels XSync. pingInterval spécifie le temps (en minutes) entre chaque tentative de ping, pingTimeout spécifie le temps maximum (en minutes) à attendre pour que le terminal réponde à la requête. Si le terminal ne répond pas, la session est déclarée morte et terminée. Par défaut, les deux sont réglés sur 5 minutes. Si vous utilisez fréquemment des terminaux X qui peuvent devenir isolés de l'hôte de gestion, vous pourriez vouloir augmenter cette valeur. Le seul souci est que les sessions continueront d'exister après que le terminal ait été accidentellement désactivé. xdm n'interrogera pas les écrans locaux. Bien que cela semble inoffensif, il est désagréable que la session du poste de travail soit terminée en raison d'un serveur bloqué pour le service NFS et ne répondant pas au ping.
DisplayManager.DISPLAY.terminateServer
Cette ressource booléenne spécifie si le serveur X doit être terminé lorsqu'une session se termine (au lieu de le réinitialiser). Cette option peut être utilisée lorsque le serveur a tendance à croître sans limite au fil du temps, afin de limiter le temps pendant lequel le serveur est exécuté. La valeur par défaut est ``false''.
DisplayManager.DISPLAY.userPath
Xdm définit la variable d'environnement PATH pour la session à cette valeur. Ce doit être une liste de répertoires séparés par des deux-points ; voir sh(1) pour une description complète. La valeur par défaut est ``/usr/local/bin:/usr/bin:/bin''.
DisplayManager.DISPLAY.systemPath
Xdm définit la variable d'environnement PATH pour les scripts de démarrage et de réinitialisation à la valeur de cette ressource. La valeur par défaut pour cette ressource est ``/usr/local/bin:/usr/bin:/bin''. Notez l'absence de ``.'' dans cette entrée. C'est une bonne pratique à suivre pour root ; cela évite de nombreux schémas de pénétration système Cheval de Troie courants.
DisplayManager.DISPLAY.systemShell
Xdm définit la variable d'environnement SHELL pour les scripts de démarrage et de réinitialisation à la valeur de cette ressource. Il s'agit de /bin/sh par défaut.
DisplayManager.DISPLAY.failsafeClient
Si la session par défaut ne parvient pas à s'exécuter, xdm se rabattra sur ce programme. Ce programme est exécuté sans arguments, mais s'exécute en utilisant les mêmes variables d'environnement que la session aurait eues (voir la section Programme de session). Par défaut, /usr/bin/xterm est utilisé.
DisplayManager.DISPLAY.grabServer
DisplayManager.DISPLAY.grabTimeout
Pour améliorer la sécurité, xdm s'empare du serveur et du clavier lors de la lecture du nom d'utilisateur et du mot de passe. La ressource grabServer spécifie si le serveur doit être conservé pendant la durée de lecture du nom/mot de passe. Lorsque ``false'', le serveur est libéré après que la saisie du clavier ait réussi, sinon le serveur est saisi jusqu'à juste avant le début de la session. La valeur par défaut est ``false''. La ressource grabTimeout spécifie le temps maximum pendant lequel xdm attendra que la saisie réussisse. La saisie peut échouer si un autre client a saisi le serveur, ou éventuellement si les latences réseau sont très élevées. Cette ressource a une valeur par défaut de 3 secondes ; vous devriez être prudent lorsque vous l'augmentez, car un utilisateur peut être usurpé par une fenêtre ressemblant à l'originale sur l'écran. Si la saisie échoue, xdm tue et redémarre le serveur (si possible) et la session.
DisplayManager.DISPLAY.authorize
DisplayManager.DISPLAY.authName
authorize est une ressource booléenne qui contrôle si xdm génère et utilise une authentification pour les connexions locales au serveur. Si l'authentification est utilisée, authName est une liste de mécanismes d'autorisation à utiliser, séparés par des espaces. Les connexions XDMCP spécifient dynamiquement quels mécanismes d'authentification sont pris en charge, donc authName est ignoré dans ce cas. Lorsque authorize est défini pour un écran et que l'authentification n'est pas disponible, l'utilisateur en est informé par l'affichage d'un message différent dans le widget de connexion. Par défaut, authorize est ``true'', authName est ``MIT-MAGIC-COOKIE-1'', ou, si XDM-AUTHORIZATION-1 est disponible, ``XDM-AUTHORIZATION-1 MIT-MAGIC-COOKIE-1.''
DisplayManager.DISPLAY.authFile
Ce fichier est utilisé pour communiquer les données d'authentification de xdm au serveur, en utilisant l'option de ligne de commande du serveur -auth. Il doit être conservé dans un répertoire qui n'est pas accessible en écriture par tous, car il pourrait être facilement supprimé, désactivant ainsi le mécanisme d'authentification du serveur. S'il n'est pas spécifié, un nom est généré à partir de DisplayManager.authDir et du nom de l'écran.
DisplayManager.DISPLAY.authComplain
S'il est défini sur ``false'', désactive l'utilisation du unsecureGreeting dans la fenêtre de connexion. Voir la section Widget d'authentification. La valeur par défaut est ``true''.
DisplayManager.DISPLAY.resetSignal
Le numéro du signal que xdm envoie pour réinitialiser le serveur. Voir la section Contrôle du serveur. La valeur par défaut est 1 (SIGHUP).
DisplayManager.DISPLAY.termSignal
Le numéro du signal que xdm envoie pour terminer le serveur. Voir la section Contrôle du serveur. La valeur par défaut est 15 (SIGTERM).
DisplayManager.DISPLAY.resetForAuth
L'implémentation originale de l'authentification dans le serveur d'exemple relisait le fichier d'authentification au moment de la réinitialisation du serveur, au lieu de lors de la vérification de la connexion initiale. Comme xdm génère les informations d'authentification juste avant de se connecter à l'écran, un ancien serveur ne recevrait pas les informations d'authentification à jour. Cette ressource fait en sorte que xdm envoie SIGHUP au serveur après avoir configuré le fichier, provoquant une réinitialisation supplémentaire du serveur, pendant laquelle les nouvelles informations d'authentification seront lues. La valeur par défaut est ``false'', ce qui fonctionnera pour tous les serveurs MIT.
DisplayManager.DISPLAY.userAuthDir
Lorsque xdm ne parvient pas à écrire dans le fichier d'authentification utilisateur habituel ($HOME/.Xauthority), il crée un nom de fichier unique dans ce répertoire et pointe la variable d'environnement XAUTHORITY vers le fichier créé. Il utilise /tmp par défaut.

FICHIER DE CONFIGURATION

Tout d'abord, le fichier de configuration de xdm doit être configuré. Créez un répertoire (généralement /etc/X11/xdm) pour contenir tous les fichiers pertinents.

Voici un fichier de configuration raisonnable, qui pourrait être nommé xdm-config :

DisplayManager.servers:         /etc/X11/xdm/Xservers
DisplayManager.errorLogFile:    /var/log/xdm.log
DisplayManager*resources:       /etc/X11/xdm/Xresources
DisplayManager*startup:         /etc/X11/xdm/Xstartup
DisplayManager*session:         /etc/X11/xdm/Xsession
DisplayManager.pidFile:         /var/run/xdm-pid
DisplayManager._0.authorize:    true
DisplayManager*authorize:       false

Notez que ce fichier contient principalement des références à d'autres fichiers. Notez également que certaines ressources sont spécifiées avec ``*'' séparant les composants. CONTRÔLE D'ACCÈS XDMCP

Le fichier de base de données spécifié par DisplayManager.accessFile fournit des informations que xdm utilise pour contrôler l'accès des écrans demandant le service XDMCP. Ce fichier contient trois types d'entrées : les entrées qui contrôlent la réponse aux requêtes Directes et de Diffusion, les entrées qui contrôlent la réponse aux requêtes Indirectes, et les définitions de macros.

Le format des entrées Directes est simple, soit un nom d'hôte, soit un modèle, qui se distingue d'un nom d'hôte par l'inclusion

n d'un ou plusieurs caractères génériques (`*' correspond à toute séquence de 0 caractères ou plus, et `?' correspond à tout caractère unique) qui sont comparés au nom d'hôte de l'appareil d'affichage. Si l'entrée est un nom d'hôte, toutes les comparaisons sont effectuées à l'aide d'adresses réseau, de sorte que tout nom converti en l'adresse réseau correcte peut être utilisé. Pour les motifs, seuls les noms d'hôtes canoniques sont utilisés dans la comparaison, alors assurez-vous de ne pas tenter de faire correspondre des alias. Précéder un nom d'hôte ou un motif du caractère `!' entraîne l'exclusion des hôtes qui correspondent à cette entrée.

Pour répondre uniquement aux requêtes Directes pour un hôte ou un motif, il peut être suivi du mot-clé optionnel « NOBROADCAST ». Ceci peut être utilisé pour empêcher un serveur xdm d'apparaître dans les menus basés sur des requêtes Broadcast.

Une entrée Indirecte contient également un nom d'hôte ou un motif, mais il est suivi d'une liste de noms d'hôtes ou de macros auxquels les requêtes indirectes doivent être envoyées.

Une définition de macro contient un nom de macro et une liste de noms d'hôtes et d'autres macros auxquelles la macro se développe. Pour distinguer les macros des noms d'hôtes, les noms de macros commencent par un caractère `%'. Les macros peuvent être imbriquées.

Les entrées Indirectes peuvent également spécifier que xdm exécute chooser pour proposer un menu d'hôtes auxquels se connecter. Voir la section Chooser.

Lors de la vérification de l'accès pour un hôte d'affichage particulier, chaque entrée est examinée tour à tour et la première entrée correspondante détermine la réponse. Les entrées Directes et Broadcast sont ignorées lors de la recherche d'une entrée Indirecte et vice-versa.

Les lignes vides sont ignorées, `#` est traité comme un délimiteur de commentaire entraînant l'ignorance du reste de cette ligne, et `\`nouvelle ligne` provoque l'ignorance de la nouvelle ligne, permettant aux listes d'hôtes indirectes de s'étendre sur plusieurs lignes.

Voici un exemple de fichier Xaccess :

#
# Xaccess - Fichier de contrôle d'accès XDMCP
#
#
# Entrées de requête Directe/Broadcast
#
!xtra.lcs.mit.edu       # refuser le service direct/broadcast pour xtra
bambi.ogi.edu           # autoriser l'accès depuis cet affichage particulier
*.lcs.mit.edu           # autoriser l'accès depuis n'importe quel affichage dans LCS
*.deshaw.com    NOBROADCAST     # autoriser uniquement l'accès direct
*.gw.com                        # autoriser direct et broadcast
#
# Entrées de requête Indirecte
#
%HOSTS  expo.lcs.mit.edu xenon.lcs.mit.edu \
        excess.lcs.mit.edu kanga.lcs.mit.edu
extract.lcs.mit.edu     xenon.lcs.mit.edu  # forcer extract à contacter xenon
!xtra.lcs.mit.edu       dummy              # refuser l'accès indirect
*.lcs.mit.edu           %HOSTS             # tous les autres peuvent choisir

Si compilé avec le support IPv6, les groupes d'adresses multicast peuvent également être inclus dans la liste des adresses auxquelles les requêtes indirectes sont envoyées. Les adresses multicast peuvent être suivies d'un caractère `/` optionnel et d'un nombre de sauts. Si aucun nombre de sauts n'est spécifié, le nombre de sauts multicast est par défaut de 1, maintenant le paquet sur le réseau local. Pour le multicast IPv4, le nombre de sauts est utilisé comme TTL.

Exemples :

rincewind.sample.net  ff02::1 # Multicast IPv6 vers ff02::1
                              # avec un nombre de sauts de 1
ponder.sample.net     CHOOSER 239.192.1.1/16  # Proposer un menu d'hôtes
                                              # qui répondent au Multicast IPv4
                                              # vers 239.192.1.1 avec un
                                              # TTL de 16

CHOOSER

Pour les terminaux X qui n'offrent pas de menu d'hôtes à utiliser avec les requêtes Broadcast ou Indirectes, le programme chooser peut le faire pour eux. Dans le fichier Xaccess, spécifiez « CHOOSER » comme première entrée dans la liste d'hôtes Indirecte. Chooser enverra une requête Query à chacun des noms d'hôtes restants dans la liste et proposera un menu de tous les hôtes qui répondent.

La liste peut consister en le mot « BROADCAST », auquel cas chooser enverra un Broadcast, proposant à nouveau un menu de tous les hôtes qui répondent. Notez que sur certains systèmes d'exploitation, les paquets UDP ne peuvent pas être diffusés, de sorte que cette fonctionnalité ne fonctionnera pas.

Exemple de fichier Xaccess utilisant chooser :

extract.lcs.mit.edu CHOOSER %HOSTS      # proposer un menu de ces hôtes
xtra.lcs.mit.edu    CHOOSER BROADCAST   # proposer un menu de tous les hôtes

Le programme à utiliser pour chooser est spécifié par la ressource DisplayManager.DISPLAY.chooser. Pour plus de flexibilité à cette étape, le chooser pourrait être un script shell. Chooser est le gestionnaire de session ici ; il est exécuté au lieu d'un enfant xdm pour gérer l'affichage.

Les ressources pour ce programme peuvent être placées dans le fichier nommé par DisplayManager.DISPLAY.resources.

Lorsque l'utilisateur sélectionne un hôte, chooser affiche l'hôte choisi, qui est lu par le parent xdm, et se termine. xdm ferme sa connexion au serveur X, et le serveur se réinitialise et envoie une autre requête Indirect XDMCP. xdm se souvient du choix de l'utilisateur (pendant DisplayManager.choiceTimeout secondes) et transmet la requête à l'hôte choisi, qui démarre une session sur cet affichage.

LISTEN

La directive de configuration suivante est également définie pour le fichier de configuration Xaccess :

LISTEN interface [liste d'adresses de groupe multicast]
interface peut être un nom d'hôte ou une adresse IP représentant une interface réseau sur cette machine, ou le caractère générique * pour représenter toutes les interfaces réseau disponibles.

Si une ou plusieurs lignes LISTEN sont spécifiées, xdm n'écoute que les connexions XDMCP sur les interfaces spécifiées. Si des adresses de groupe multicast sont listées sur une ligne listen, xdm rejoint les groupes multicast sur l'interface donnée.

Si aucune ligne LISTEN n'est donnée, le comportement initial d'écoute sur toutes les interfaces est préservé pour des raisons de compatibilité ascendante. De plus, si aucun LISTEN n'est spécifié, xdm rejoint le groupe multicast IPv6 XDMCP par défaut, lorsqu'il est compilé avec le support IPv6.

Pour désactiver complètement l'écoute des connexions XDMCP, une ligne LISTEN sans adresses peut être spécifiée, ou la méthode précédemment prise en charge de définition de DisplayManager.requestPort à 0 peut être utilisée.

Exemples :

LISTEN * ff02::1        # Écouter sur toutes les interfaces et sur le
                        # groupe multicast IPv6 ff02::1.
LISTEN 10.11.12.13      # Écouter uniquement sur cette interface, tant
                        # qu'aucune autre directive listen n'apparaît dans
                        # le fichier.

IPv6 SPÉCIFICATION D'ADRESSE MULTICAST

L'Internet Assigned Numbers Authority a attribué ff0X:0:0:0:0:0:0:12b comme plage d'adresses multicast assignée de manière permanente pour XDMCP. Le X dans le préfixe peut être remplacé par n'importe quel identifiant de portée valide, tel que 1 pour Interface-Local, 2 pour Link-Local, 5 pour Site-Local, etc. (Voir RFC 4291 de l'IETF ou son remplacement pour plus de détails et de définitions de portée.) xdm écoute par défaut sur l'adresse de portée Link-Local ff02:0:0:0:0:0:0:12b pour correspondre au mieux au comportement de broadcast de sous-réseau IPv4 précédent.

SPÉCIFICATION DU SERVEUR LOCAL

La ressource DisplayManager.servers donne une spécification de serveur ou, si les valeurs commencent par une barre oblique (/), le nom d'un fichier contenant des spécifications de serveur, une par ligne.

Chaque spécification indique un écran qui doit être constamment géré et qui n'utilise pas XDMCP. Cette méthode est généralement utilisée uniquement pour les serveurs locaux. Si la ressource ou le fichier nommé par la ressource est vide, xdm n'offrira le service XDMCP que.

Chaque spécification se compose d'au moins trois parties : un nom d'affichage, une classe d'affichage, un type d'affichage et (pour les serveurs locaux) une ligne de commande pour démarrer le serveur. Une entrée typique pour l'affichage local numéro 0 serait :

:0 Digital-QV local /usr/bin/X :0
Les types d'affichage sont :
local affichage local : xdm doit exécuter le serveur
foreign affichage distant : xdm établit une connexion X à un serveur en cours d'exécution

Le nom d'affichage doit être quelque chose qui peut être passé dans l'option -display à un programme X. Cette chaîne est utilisée pour générer les noms de ressources spécifiques à l'affichage, alors faites attention à faire correspondre les noms (par exemple, utilisez « :0 Sun-CG3 local /usr/bin/X :0 » au lieu de « localhost:0 Sun-CG3 local /usr/bin/X :0 » si vos autres ressources sont spécifiées comme « DisplayManager._0.session »). La partie classe d'affichage est également utilisée dans les ressources spécifiques à l'affichage, en tant que classe de la ressource. Ceci est utile si vous avez une grande collection d'affichages similaires (tels qu'un enclos de terminaux X) et que vous souhaitez définir des ressources pour des groupes d'entre eux. Lors de l'utilisation de XDMCP, l'affichage est tenu de spécifier la classe d'affichage, de sorte que le manuel de votre terminal X particulier devrait documenter la chaîne de classe d'affichage pour votre appareil. Si ce n'est pas le cas, vous pouvez exécuter xdm en mode débogage et examiner les chaînes de ressources qu'il génère pour cet appareil, qui incluront la chaîne de classe.

Lorsque xdm démarre une session, il met en place des données d'autorisation pour le serveur. Pour les serveurs locaux, xdm passe « -auth nom_fichier » sur la ligne de commande du serveur pour le pointer vers ses données d'autorisation. Pour les serveurs XDMCP, xdm transmet les données d'autorisation au serveur via la requête XDMCP Accept.

PROGRAMME D'INSTALLATION


Le fichier Xsetup est exécuté après la réinitialisation du serveur, mais avant que la fenêtre de connexion ne soit proposée. Le fichier est généralement un script shell. Il est exécuté en tant que root, il faut donc être prudent en matière de sécurité. C'est l'endroit idéal pour changer l'arrière-plan root ou afficher d'autres fenêtres qui devraient apparaître à l'écran avec le widget de connexion.


En plus de celles spécifiées par DisplayManager.exportList, les variables d'environnement suivantes sont transmises:



  

    DISPLAY
    le nom d'affichage associé
  

  

    PATH
    la valeur de DisplayManager.DISPLAY.systemPath
  

  

    SHELL
    la valeur de DisplayManager.DISPLAY.systemShell
  

  

    XAUTHORITY
    peut être défini sur un fichier d'autorité
  




Notez que comme xdm capture le clavier, toutes les autres fenêtres ne pourront pas recevoir d'entrée clavier. Elles pourront interagir avec la souris, cependant ; attention aux failles de sécurité potentielles ici. Si DisplayManager.DISPLAY.grabServer est défini, Xsetup ne pourra pas du tout se connecter à l'affichage. Les ressources pour ce programme peuvent être placées dans le fichier nommé par DisplayManager.DISPLAY.resources.


Voici un exemple de script Xsetup:

xcmsdb < /etc/X11/xdm/monitors/alex.0
xconsole -geometry 480x130-0-0 -notify -verbose -exitOnFail &








WIDGET D'AUTHENTIFICATION


Le widget d'authentification invite l'utilisateur à saisir le nom d'utilisateur, le mot de passe et/ou d'autres données d'authentification requises depuis le clavier. Presque tous les paramètres imaginables peuvent être contrôlés par une ressource. Les ressources pour ce widget doivent être placées dans le fichier nommé par DisplayManager.DISPLAY.resources. Toutes celles-ci ont des valeurs par défaut raisonnables, il n'est donc pas nécessaire de spécifier l'une d'entre elles.


Le fichier de ressources est chargé avec xrdb(1) il peut donc utiliser les substitutions définies par ce programme comme CLIENTHOST pour le nom d'hôte client dans le message de connexion, ou les instructions #ifdef du préprocesseur C pour produire des affichages différents en fonction de la profondeur de couleur ou d'autres variables.

PROGRAMME   DE   DÉMARRAGE


Le programme Xstartup est exécuté en tant que root lorsque l'utilisateur se connecte.
    C'est généralement un script shell. Comme il est exécuté en tant que root, Xstartup
    doit être très prudent en matière de sécurité. C'est l'endroit où placer les commandes
    qui ajoutent des entrées aux fichiers utmp ou wtmp (le programme sessreg
    peut être utile ici), montent les répertoires personnels des utilisateurs depuis des serveurs de fichiers, ou abandonnent la session si les connexions ne sont pas autorisées.


En plus de ceux spécifiés par DisplayManager.exportList,
    les variables d'environnement suivantes sont transmises :



  

    DISPLAY
    le nom d'affichage associé
  

  

    HOME
    le répertoire de travail initial de l'utilisateur
  

  

    LOGNAME
    le nom d'utilisateur
  

  

    USER
    le nom d'utilisateur
  

  

    PATH
    la valeur de DisplayManager.DISPLAY.systemPath
  

  

    SHELL
    la valeur de
      DisplayManager.DISPLAY.systemShell
  

  

    XAUTHORITY
    peut être défini sur un fichier d'autorité
  

  

    WINDOWPATH
    peut être défini sur le "chemin de fenêtre" menant au serveur X
  




Aucun argument n'est passé au script. Xdm attend que ce script se termine avant de démarrer la session utilisateur. Si la valeur de sortie de ce script est non nulle, xdm interrompt la session et lance un nouveau cycle d'authentification.


L'exemple de fichier Xstartup montré ici empêche la connexion tant que le fichier
    /etc/nologin existe. Il ne s'agit donc pas d'un exemple complet, mais simplement d'une démonstration des fonctionnalités disponibles.


Voici un exemple de script Xstartup :




#!/bin/sh
#
# Xstartup
#
# Ce programme est exécuté en tant que root après la vérification de l'utilisateur
#
if [ -f /etc/nologin ]; then
	xmessage -file /etc/nologin -timeout 30 -center
	exit 1
fi
sessreg -a -l $DISPLAY -x /etc/X11/xdm/Xservers $LOGNAME
/etc/X11/xdm/GiveConsole
exit 0








PROGRAMME   DE   SESSION


Le programme Xsession est la commande qui est exécutée en tant que session de l'utilisateur.
    Il est exécuté avec les permissions de l'utilisateur autorisé.


En plus de ceux spécifiés par DisplayManager.exportList,
    les variables d'environnement suivantes sont transmises :



  

    DISPLAY
    le nom d'affichage associé
  

  

    HOME
    le répertoire de travail initial de l'utilisateur
  

  

    LOGNAME
    le nom d'utilisateur
  

  

    USER
    le nom d'utilisateur
  

  

    PATH
    la valeur de DisplayManager.DISPLAY.userPath
  

  

    SHELL
    le shell par défaut de l'utilisateur (obtenu via getpwnam)
  

  

    XAUTHORITY
    peut être défini sur un fichier d'autorité non standard
  

  

    KRB5CCNAME
    peut être défini sur un nom de cache d'informations d'identification Kerberos
  

  

    WINDOWPATH
    peut être défini sur le "chemin de fenêtre" menant au serveur X
  




Dans la plupart des installations, Xsession devrait rechercher dans $HOME un fichier
    .xsession, qui contient les commandes que chaque utilisateur souhaiterait utiliser comme session. Xsession devrait également implémenter une session par défaut du système si aucune session spécifiée par l'utilisateur n'existe.


Un argument peut être passé à ce programme depuis le widget d'authentification en utilisant l'action `set-session-argument'. Ceci peut être utilisé pour sélectionner différents styles de session. Une bonne utilisation de cette fonctionnalité est de permettre à l'utilisateur d'échapper à la session ordinaire en cas d'échec. Cela permet aux utilisateurs de réparer leur propre .xsession en cas d'échec, sans nécessiter d'intervention administrative. L'exemple suivant illustre cette fonctionnalité.


Cet exemple reconnaît le mode spécial "failsafe", spécifié dans les traductions du fichier Xresources, pour fournir une échappatoire à la session ordinaire. Il exige également que le fichier .xsession soit exécutable afin que nous n'ayons pas à deviner quel shell il souhaite utiliser.




#!/bin/sh
#
# Xsession
#
# C'est le programme exécuté en tant que client
# pour le gestionnaire d'affichage.
case $# in
1)
	case $1 in
	failsafe)
		exec xterm -geometry 80x24-0-0
		;;
	esac
esac
startup=$HOME/.xsession
resources=$HOME/.Xresources
if [ -f "$startup"
; ]; then
	exec "$startup"
else
	if [ -f "$resources" ]; then
		xrdb -load "$resources"
	fi
	twm &
	xman -geometry +10-10 &
	exec xterm -geometry 80x24+10+10 -ls
fi




Le fichier .xsession de l'utilisateur pourrait ressembler à cet
    exemple. N'oubliez pas que le fichier doit avoir la permission d'exécution.




      #! /bin/csh
      # no -f in the previous line so .cshrc gets run to set $PATH
        twm &
        xrdb -merge "$HOME/.Xresources"
        emacs -geometry +0+50 &
        xbiff -geometry -430+5 &
        xterm -geometry -0+50 -ls








PROGRAMME   DE   RÉINITIALISATION


Symétrique avec Xstartup, le script Xreset est exécuté
    après la fin de la session utilisateur. Exécuté en tant que root, il doit
    contenir des commandes qui annulent les effets des commandes dans
    Xstartup, mettant à jour les entrées dans les fichiers utmp ou
    wtmp, ou démontant des répertoires de serveurs de fichiers. Les variables
    d'environnement qui ont été transmises à Xstartup sont également
    transmises à Xreset.


Un script Xreset exemple :




#!/bin/sh
#
# Xreset
#
# This program is run as root after the session ends
#
sessreg -d -l $DISPLAY -x /etc/X11/xdm/Xservers $LOGNAME
/etc/X11/xdm/TakeConsole
exit 0








CONTRÔLE   DU   SERVEUR


Xdm contrôle les serveurs locaux en utilisant les signaux POSIX.
    SIGHUP est censé réinitialiser le serveur, fermant toutes les connexions client
    et effectuant d'autres tâches de nettoyage. SIGTERM est censé terminer le
    serveur. Si ces signaux n'effectuent pas les actions attendues, les ressources
    DisplayManager.DISPLAY.resetSignal et
    DisplayManager.DISPLAY.termSignal peuvent spécifier des
    signaux alternatifs.


Pour contrôler les terminaux distants qui n'utilisent pas XDMCP,
    xdm parcourt la hiérarchie des fenêtres sur l'affichage et utilise la
    requête de protocole KillClient pour tenter de nettoyer le terminal pour la
    prochaine session. Cela peut ne pas réellement tuer tous les clients, car seuls
    ceux qui ont créé des fenêtres seront remarqués. XDMCP fournit un mécanisme
    plus sûr ; lorsque xdm ferme sa connexion initiale, la session est
    terminée et le terminal est tenu de fermer toutes les autres connexions.






CONTRÔLE   DE   XDM


Xdm répond à deux signaux : SIGHUP et SIGTERM. Lorsqu'il reçoit
    un SIGHUP, xdm relit le fichier de configuration, le fichier de contrôle
    d'accès et le fichier des serveurs. Pour le fichier des serveurs, il remarque si
    des entrées ont été ajoutées ou supprimées. Si une nouvelle entrée a été ajoutée,
    xdm démarre une session sur l'affichage associé. Les entrées qui ont été
    supprimées sont désactivées immédiatement, ce qui signifie que toute session en
    cours sera terminée sans préavis et aucune nouvelle session ne sera démarrée.


Lorsqu'il reçoit un SIGTERM, xdm termine toutes les sessions
    en cours et se termine. Ceci peut être utilisé lors de l'arrêt du système.


Xdm tente de marquer ses différents sous-processus pour
    ps(1) en modifiant la liste des arguments de la ligne de commande en place.
    Étant donné que xdm ne peut pas allouer d'espace supplémentaire pour cette
    tâche, il est utile de démarrer xdm avec une ligne de commande raisonnablement
    longue (utiliser le nom de chemin complet devrait suffire). Chaque processus qui
    sert un affichage est marqué -display.






AFFICHAGES   LOCAUX   SUPPLÉMENTAIRES


Pour ajouter un affichage local supplémentaire, ajoutez une ligne pour
    celui-ci au fichier Xservers. (Voir la section Spécification du
    serveur local.)


Examinez les ressources spécifiques à l'affichage dans
    xdm-config (par exemple, DisplayManager._0.authorize) et
    déterminez lesquelles d'entre elles doivent être copiées pour le nouvel
    affichage. Le xdm-config par défaut contient toutes les lignes
    appropriées pour les affichages :0 et :1.






AUTRES   POSSIBILITÉS


Vous pouvez utiliser xdm pour exécuter une seule session à la
    fois, en utilisant les options init de 4.3 ou un autre démon approprié en
    spécifiant le serveur sur la ligne de commande :


xdm -server “:0 SUN-3/60CG4 local /usr/bin/X :0”


Ou, vous pourriez avoir un serveur de fichiers et une collection de
    terminaux X. La configuration pour cela est identique à l'exemple ci-dessus,
    sauf que le fichier Xservers ressemblerait à


extol:0 VISUAL-19 foreign
exalt:0 NCD-19 foreign
explode:0 NCR-TOWERVIEW3000 foreign


Cela dirige xdm pour gérer les sessions sur ces trois terminaux.
    Voir la section Contrôle de Xdm pour une description de l'utilisation des
    signaux pour activer et désactiver ces terminaux d'une manière qui rappelle
    init(8).






LIMITATIONS


Une chose que xdm ne gère pas très bien est la coexistence avec
    d'autres systèmes de fenêtrage. Pour utiliser plusieurs systèmes de fenêtrage
    sur le même matériel, vous serez probablement plus intéressé par
    xinit.
