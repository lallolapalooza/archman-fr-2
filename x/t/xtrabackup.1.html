NOM

xtrabackup - Documentation Percona XtraBackup 8.0

Le binaire xtrabackup est un programme C compilé, lié aux bibliothèques InnoDB et aux bibliothèques client standard de MySQL.

xtrabackup permet de réaliser des sauvegardes à un instant donné des tables InnoDB / XtraDB, ainsi que des définitions de schéma, des tables MyISAM et d'autres parties du serveur.

Les bibliothèques InnoDB fournissent la fonctionnalité d'application d'un journal aux fichiers de données. Les bibliothèques client MySQL sont utilisées pour analyser les options de ligne de commande et les fichiers de configuration.

L'outil fonctionne soit en mode --backup, soit en mode --prepare, correspondant aux deux fonctions principales qu'il exécute. Il existe plusieurs variations de ces fonctions pour accomplir différentes tâches, ainsi que deux modes moins couramment utilisés : --stats et --print-param.

AUTRES TYPES DE SAUVEGARDES

Sauvegardes Incementielles

xtrabackup prend en charge les sauvegardes incrémentielles. Il ne copie que les données qui ont changé depuis la dernière sauvegarde complète. Vous pouvez effectuer plusieurs sauvegardes incrémentielles entre chaque sauvegarde complète, vous permettant ainsi de mettre en place un processus de sauvegarde tel qu'une sauvegarde complète une fois par semaine et une sauvegarde incrémentielle tous les jours, ou des sauvegardes complètes tous les jours et des sauvegardes incrémentielles toutes les heures.

NOTE :

Les sauvegardes incrémentielles sur le moteur de stockage MyRocks ne déterminent pas si une sauvegarde complète ou incrémentielle précédente contient les mêmes fichiers. Percona XtraBackup copie tous les fichiers MyRocks chaque fois qu'il effectue une sauvegarde.

Les sauvegardes incrémentielles fonctionnent car chaque page InnoDB (généralement de 16 Ko) contient un numéro de séquence de journal, ou LSN. Le LSN est le numéro de version du système pour l'ensemble de la base de données. Le LSN de chaque page indique à quel point elle a été modifiée récemment. Une sauvegarde incrémentielle copie chaque page dont le LSN est plus récent que le LSN de la sauvegarde incrémentielle ou complète précédente. Deux algorithmes sont utilisés pour trouver l'ensemble des pages à copier. Le premier, disponible avec tous les types et versions de serveur, consiste à vérifier directement le LSN de la page en lisant toutes les pages de données. Le second, disponible avec Percona Server for MySQL, consiste à activer la fonctionnalité de suivi des pages modifiées sur le serveur, qui notera les pages au fur et à mesure de leur modification. Ces informations seront ensuite écrites dans un fichier séparé compact, appelé fichier bitmap. Le binaire xtrabackup utilisera ce fichier pour ne lire que les pages de données nécessaires à la sauvegarde incrémentielle, économisant potentiellement de nombreuses requêtes de lecture. Ce dernier algorithme est activé par défaut si le binaire xtrabackup trouve le fichier bitmap. Il est possible de spécifier --incremental-force-scan pour lire toutes les pages même si les données du bitmap sont disponibles.

Les sauvegardes incrémentielles ne comparent pas réellement les fichiers de données avec les fichiers de la sauvegarde précédente. En fait, vous pouvez utiliser --incremental-lsn pour effectuer une sauvegarde incrémentielle sans même avoir la sauvegarde précédente, si vous connaissez son LSN. Les sauvegardes incrémentielles lisent simplement les pages et comparent leur LSN à celui de la dernière sauvegarde. Cependant, vous avez toujours besoin d'une sauvegarde complète pour restaurer les modifications incrémentielles ; sans sauvegarde complète comme base, les sauvegardes incrémentielles sont inutiles.

Création dune Sauvegarde Incrémentielle

Pour créer une sauvegarde incrémentielle, commencez par une sauvegarde complète comme d'habitude. Le binaire xtrabackup écrit un fichier appelé xtrabackup_checkpoints dans le répertoire cible de la sauvegarde. Ce fichier contient une ligne indiquant le to_lsn, qui est le LSN de la base de données à la fin de la sauvegarde. Créez la sauvegarde complète avec une commande telle que la suivante :

$ xtrabackup --backup --target-dir=/data/backups/base --datadir=/var/lib/mysql/

Si vous examinez le fichier xtrabackup_checkpoints, vous devriez voir un contenu similaire à ce qui suit :

backup_type = full-backuped
from_lsn = 0
to_lsn = 1291135

Maintenant que vous avez une sauvegarde complète, vous pouvez en créer une sauvegarde incrémentielle basée sur celle-ci. Utilisez une commande telle que la suivante :

$ xtrabackup --backup --target-dir=/data/backups/inc1 \
--incremental-basedir=/data/backups/base --datadir=/var/lib/mysql/

Le répertoire /data/backups/inc1/ devrait maintenant contenir des fichiers delta, tels que ibdata1.delta et test/table1.ibd.delta. Ceux-ci représentent les changements depuis le LSN 1291135. Si vous examinez le fichier xtrabackup_checkpoints dans ce répertoire, vous devriez voir quelque chose de similaire à ce qui suit :

backup_type = incremental
from_lsn = 1291135
to_lsn = 1291340

La signification devrait être évidente. Il est maintenant possible d'utiliser ce répertoire comme base pour une autre sauvegarde incrémentielle :

$ xtrabackup --backup --target-dir=/data/backups/inc2 \
--incremental-basedir=/data/backups/inc1 --datadir=/var/lib/mysql/

Préparation des Sauvegardes Incrémentielles

L'étape --prepare pour les sauvegardes incrémentielles n'est pas la même que pour les sauvegardes normales. Dans les sauvegardes normales, deux types d'opérations sont effectués pour rendre la base de données cohérente : les transactions validées sont rejouées à partir du fichier journal sur les fichiers de données, et les transactions non validées sont annulées. Vous devez sauter l'annulation des transactions non validées lors de la préparation d'une sauvegarde, car les transactions qui étaient non validées au moment de votre sauvegarde peuvent être en cours, et il est probable qu'elles seront validées dans la prochaine sauvegarde incrémentielle. Vous devriez utiliser l'option --apply-log-only pour empêcher la phase d'annulation.

NOTE :

Si vous n'utilisez pas l'option --apply-log-only pour empêcher la phase d'annulation, vos sauvegardes incrémentielles seront inutiles. Après l'annulation des transactions, les sauvegardes incrémentielles ultérieures ne pourront pas être appliquées.

En commençant par la sauvegarde complète que vous avez créée, vous pouvez la préparer, puis y appliquer les différences incrémentielles. Rappelez-vous que vous avez les sauvegardes suivantes :

/data/backups/base
/data/backups/inc1
/data/backups/inc2

Pour préparer la sauvegarde de base, vous devez exécuter --prepare comme d'habitude, mais empêcher la phase d'annulation :

xtrabackup --prepare --apply-log-only --target-dir=/data/backups/base

La sortie devrait se terminer par un texte tel que le suivant :

101107 20:49:43  InnoDB: Shutdown completed; log sequence number 1291135

Le numéro de séquence du journal devrait correspondre au to_lsn de la sauvegarde de base, que vous avez vu précédemment.

Cette sauvegarde est en fait sûre à restaurer telle quelle maintenant, même si la phase d'annulation a été sautée. Si vous la restaurez et démarrez MySQL, InnoDB détectera que la phase d'annulation n'a pas été effectuée, et le fera en arrière-plan, comme il le fait habituellement pour une récupération après incident au démarrage. Il vous notifiera que la base de données n'a pas été arrêtée normalement.

Pour appliquer la première sauvegarde incrémentielle à la sauvegarde complète, vous devriez utiliser la commande suivante :

xtrabackup --prepare --apply-log-only --target-dir=/data/backups/base \
--incremental-dir=/data/backups/inc1

Cela applique les fichiers delta aux fichiers dans /data/backups/base, les faisant avancer dans le temps jusqu'au moment de la sauvegarde incrémentielle. Il applique ensuite le journal de rejeu comme d'habitude au résultat. Les données finales se trouvent dans /data/backups/base, pas dans le répertoire incrémentiel. Vous devriez voir une sortie similaire à la suivante :

incremental backup from 1291135 is enabled.
xtrabackup: cd to /data/backups/base/
xtrabackup: This target seems to be already prepared.
xtrabackup: xtrabackup_logfile detected: size=2097152, start_lsn=(1291340)
Applying /data/backups/inc1/ibdata1.delta ...
Applying /data/backups/inc1/test/table1.ibd.delta ...
.... snip
101107 20:56:30  InnoDB: Shutdown completed; log sequence number 1291340

Encore une fois, le LSN devrait correspondre à ce que vous avez vu lors de votre inspection précédente de la première sauvegarde incrémentielle. Si vous restaurez les fichiers de /data/backups/base, vous devriez voir l'état des données

base comme point de départ la première sauvegarde incrémentielle.

La préparation de la deuxième sauvegarde incrémentielle est un processus similaire : appliquez les deltas à la sauvegarde de base (modifiée), et vous ferez avancer ses données dans le temps jusqu'au point de la deuxième sauvegarde incrémentielle :

xtrabackup --prepare --target-dir=/data/backups/base \
--incremental-dir=/data/backups/inc2

NOTE :

--apply-log-only doit être utilisé lors de la fusion de toutes les sauvegardes incrémentielles sauf la dernière. C'est pourquoi la ligne précédente ne contient pas l'option --apply-log-only. Même si --apply-log-only était utilisé lors de la dernière étape, la sauvegarde serait toujours cohérente, mais dans ce cas, le serveur effectuerait la phase de restauration.

Si vous souhaitez éviter l'avis que InnoDB n'a pas été arrêté normalement, lorsque vous avez appliqué les deltas souhaités à la sauvegarde de base, vous pouvez exécuter --prepare à nouveau sans désactiver la phase de restauration.

Restaurer les sauvegardes incrémentielles

Après avoir préparé les sauvegardes incrémentielles, le répertoire de base contient les mêmes données que la sauvegarde complète. Pour restaurer cette sauvegarde, vous pouvez utiliser cette commande : xtrabackup --copy-back --target-dir=BASE-DIR

Vous devrez peut-être changer la propriété comme détaillé dans restoring_a_backup.

Sauvegardes incrémentielles en flux avec xbstream

Les sauvegardes incrémentielles en flux peuvent être effectuées avec l'option de flux xbstream. Actuellement, les sauvegardes sont empaquetées dans le format personnalisé xbstream. Avec cette fonctionnalité, vous devez également effectuer une sauvegarde de BASE. Effectuer une sauvegarde de BASE.INDENT 0.0

$ xtrabackup --backup --target-dir=/data/backups


Effectuer une sauvegarde locale.INDENT 0.0 
$ xtrabackup --backup --incremental-lsn=LSN-number --stream=xbstream --target-dir=./ > incremental.xbstream


Décompresser la sauvegarde.INDENT 0.0 
$ xbstream -x < incremental.xbstream


Effectuer une sauvegarde locale et la diffuser sur le serveur distant et la décompresser.INDENT 0.0 
$ xtrabackup --backup --incremental-lsn=LSN-number --stream=xbstream --target-dir=./
$ ssh user@hostname " cat - | xbstream -x -C > /backup-dir/"


Sauvegardes partielles

xtrabackup prend en charge les sauvegardes partielles lorsque l'option innodb_file_per_table est activée. Il existe trois façons de créer des sauvegardes partielles :

1.
correspondance des noms de tables avec une expression régulière
2.
fournir une liste de noms de tables dans un fichier
3.
fournir une liste de bases de données

ATTENTION :

Ne copiez pas la sauvegarde préparée.

La restauration des sauvegardes partielles doit se faire en important les tables, et non en utilisant l'option --copy-back. Il n'est pas recommandé d'exécuter des sauvegardes incrémentielles après avoir exécuté une sauvegarde partielle.

Bien qu'il existe des scénarios où la restauration peut se faire en copiant les fichiers, cela peut entraîner des incohérences de base de données dans de nombreux cas et ce n'est pas une méthode recommandée.

Aux fins de cette page de manuel, nous supposerons qu'il existe une base de données nommée test qui contient les tables nommées t1 et t2.

ATTENTION :

Si l'une des tables correspondantes ou listées est supprimée pendant la sauvegarde, xtrabackup échouera.

Créer des sauvegardes partielles

Il existe plusieurs façons de spécifier quelle partie de l'ensemble des données est sauvegardée :

  • Utilisez l'option --tables pour lister les noms de tables
  • Utilisez l'option --tables-file pour lister les tables dans un fichier
  • Utilisez l'option --databases pour lister les bases de données
  • Utilisez l'option --databases-file pour lister les bases de données

L'option --tables

La première méthode utilise l'option --tables de xtrabackup. La valeur de l'option est une expression régulière qui est mise en correspondance avec le nom de la base de données et le nom de la table entièrement qualifiés en utilisant le format nom_base_de_données.nom_table.

Pour sauvegarder uniquement les tables de la base de données test, utilisez la commande suivante :

$ xtrabackup --backup --datadir=/var/lib/mysql --target-dir=/data/backups/ \
--tables="^test[.].*"

Pour sauvegarder uniquement la table test.t1, utilisez la commande suivante :

$ xtrabackup --backup --datadir=/var/lib/mysql --target-dir=/data/backups/ \
--tables="^test[.]t1"

L'option --tables-file

L'option --tables-file spécifie un fichier qui peut contenir plusieurs noms de tables, un nom de table par ligne dans le fichier. Seules les tables nommées dans le fichier seront sauvegardées. Les noms correspondent exactement, sensibles à la casse, sans aucune correspondance de modèle ou d'expression régulière. Les noms de tables doivent être entièrement qualifiés au format nom_base_de_données.nom_table.

$ echo "mydatabase.mytable" > /tmp/tables.txt
$ xtrabackup --backup --tables-file=/tmp/tables.txt

Les options --databases et --databases-file

L'option `--databases` accepte une liste de bases de données et de tables à sauvegarder, séparée par des espaces, au format nom_base_de_données[.nom_table]. En plus de cette liste, assurez-vous de spécifier les bases de données mysql, sys, et

performance_schema. Ces bases de données sont nécessaires lors de la restauration des bases de données à l'aide de xtrabackup --copy-back.

NOTE :

Les tables traitées pendant l'étape --prepare peuvent également être ajoutées à la sauvegarde même si elles ne sont pas explicitement listées par le paramètre si elles ont été créées après le début de la sauvegarde.
$ xtrabackup --databases='mysql sys performance_schema test ...'

L'option --databases-file

L'option --databases-file spécifie un fichier qui peut contenir plusieurs bases de données et tables au format nom_base_de_données[.nom_table], un nom d'élément par ligne dans le fichier. Les noms correspondent exactement, sensibles à la casse, sans correspondance de modèle ou d'expression régulière.

NOTE :

Les tables traitées pendant l'étape --prepare peuvent également être ajoutées à la sauvegarde même si elles ne sont pas explicitement listées par le paramètre si elles ont été créées après le début de la sauvegarde.

Préparer les sauvegardes partielles

La procédure est analogue à la restauration de tables individuelles : appliquez les journaux et utilisez l'option --export :

$ xtrabackup --prepare --export --target-dir=/path/to/partial/backup

Lorsque vous utilisez l'option --prepare sur une sauvegarde partielle, vous verrez des avertissements concernant des tables qui n'existent pas. C'est parce que ces tables existent dans le dictionnaire de données à l'intérieur d'InnoDB, mais les fichiers .ibd correspondants n'existent pas. Ils n'ont pas été copiés dans le répertoire de sauvegarde. Ces tables seront supprimées du dictionnaire de données, et lorsque vous restaurerez la sauvegarde et démarrerez InnoDB, elles n'existeront plus et ne provoqueront aucune erreur ni avertissement dans le fichier journal.

Impossible de trouver de fichier associé à l'ID d'espace de table : 5

Utilisez --innodb-directories pour trouver les fichiers d'espace de table. Si cela échoue, utilisez --innodb-force-recovery=1 pour ignorer cela et perdre définitivement toutes les modifications apportées aux espaces de table manquants.

Restaurer les sauvegardes partielles

La restauration doit se faire en restaurant des tables individuelles dans la sauvegarde partielle sur le serveur.

Elle peut également se faire en copiant la sauvegarde préparée dans un datadir "propre" (dans ce cas, assurez-vous d'inclure la base de données mysql) vers le datadir où vous déplacez la sauvegarde. Une base de données système peut être créée avec ce qui suit :

$ sudo mysql --initialize --user=mysql

Une fois que vous démarrez le serveur, vous pouvez voir mysql se plaindre d'espaces de table manquants :

2021-07-19T12:42:11.077200Z 1 [Warning] [MY-012351] [InnoDB] Tablespace 4, name 'test1/t1', file './d2/test1.ibd' is missing!
2021-07-19T12:42:11.077300Z 1 [Warning] [MY-012351] [InnoDB] Tablespace 4, name 'test1/t1', file './d2/test1.ibd' is missing!

Afin de nettoyer la base de données orpheline du dictionnaire de données, vous devez créer manuellement le répertoire de base de données manquant, puis DROP cette base de données du serveur.

Exemple de création de la base de données manquante :

$ mkdir /var/lib/mysql/test1/d2

Exemple de suppression de la base de données du serveur :

mysql> DROP DATABASE d2;
Query OK, 2 rows affected (0.5 sec)

FONCTIONNALITÉS AVANCÉES

Analyser les statistiques des tables

Le binaire xtrabackup peut analyser les fichiers de données InnoDB en mode lecture seule pour en fournir des statistiques. Pour ce faire, vous devriez utiliser l'option --stats. Vous pouvez la combiner avec l'option --tables pour limiter les fichiers à examiner. Elle utilise également l'option --use-memory.

Vous pouvez effectuer l'analyse sur un serveur en cours d'exécution, avec un certain risque d'erreurs dues au fait que les données sont modifiées pendant l'analyse. Ou, vous pouvez analyser une copie de sauvegarde de la base de données. Dans tous les cas, pour utiliser la fonctionnalité de statistiques, vous avez besoin d'une copie propre de la base de données, y compris des fichiers journaux de taille correcte.

oui, vous devez exécuter avec --prepare deux fois pour utiliser cette fonctionnalité sur une sauvegarde.

Le résultat de l'exécution sur une sauvegarde peut ressembler à ce qui suit :

<INDEX STATISTICS>
  table: test/table1, index: PRIMARY, space id: 12, root page 3
  estimated statistics in dictionary:
    key vals: 25265338, leaf pages 497839, size pages 498304
  real statistics:
     level 2 pages: pages=1, data=5395 bytes, data/pages=32%
     level 1 pages: pages=415, data=6471907 bytes, data/pages=95%
        leaf pages: recs=25958413, pages=497839, data=7492026403 bytes, data/pages=91%

Cela peut être interprété comme suit :

  • La première ligne affiche simplement le nom de la table et de l'index ainsi que ses identifiants internes. Si vous voyez un index nommé GEN_CLUST_INDEX, il s'agit de l'index clusterisé de la table, créé automatiquement car vous n'avez pas explicitement créé de PRIMARY KEY.
  • Les statistiques estimées dans les informations du dictionnaire sont similaires aux données collectées par ANALYZE TABLE dans InnoDB pour être stockées comme statistiques de cardinalité estimée et transmises à l'optimiseur de requêtes.
  • Les informations de statistiques réelles sont le résultat de l'analyse des pages de données et du calcul d'informations exactes sur l'index.
  • The level <X> pages : la sortie signifie que la ligne affiche des informations sur les pages à ce niveau dans l'arbre d'index. Plus <X> est grand, plus il est éloigné des pages feuilles, qui sont au niveau 0. La première ligne est la page racine.
  • La sortie leaf pages affiche les pages feuilles, bien sûr. C'est là que les données de la table sont stockées.
  • La sortie external pages (non affichée) montre les grandes pages externes qui contiennent des valeurs trop longues pour tenir dans la ligne elle-même, telles que les longues valeurs BLOB et TEXT.
  • recs est le nombre réel d'enregistrements (lignes) dans les pages feuilles.
  • pages est le nombre de pages.
  • data est la taille totale des données dans les pages, en octets.
  • data/pages est calculé comme (data / (pages * PAGE_SIZE)) * 100%. Il n'atteindra jamais 100% en raison de l'espace réservé aux en-têtes et pieds de page.

Un exemple plus détaillé est publié dans un article du blog MySQL Performance post.

Script pour formater la sortie

Le script suivant peut être utilisé pour résumer et tabuler la sortie des informations de statistiques :

tabulate-xtrabackup-stats.pl
#!/usr/bin/env perl
use strict;
use warnings FATAL => 'all';
my $script_version = "0.1";
my $PG_SIZE = 16_384; # InnoDB utilise par défaut des pages de 16 Ko, modifiez si nécessaire.
my ($cur_idx, $cur_tbl);
my (%idx_stats, %tbl_stats);
my ($max_tbl_len, $max_idx_len) = (0, 0);
while ( my $line = <> ) {
   if ( my ($t, $i) = $line =~ m/table: (.*), index: (.*), space id:/ ) {
      $t =~ s!/!.!;
      $cur_tbl = $t;
      $cur_idx = $i;
      if ( length($i) > $max_idx_len ) {
         $max_idx_len = length($i);
      }
      if ( length($t) > $max_tbl_len ) {
         $max_tbl_len = length($t);
      }
   }
   elsif ( my ($kv, $lp, $sp) = $line =~ m/key vals: (\d+), \D*(\d+), \D*(\d+)/ ) {
      @{$idx_stats{$cur_tbl}->{$cur_idx}}{qw(est_kv est_lp est_sp)} = ($kv, $lp, $sp);
      $tbl_stats{$cur_tbl}->{est_kv} += $kv;
      $tbl_stats{$cur_tbl}->{est_lp} += $lp;
      $tbl_stats{$cur_tbl}->{est_sp} += $sp;
   }
   elsif ( my ($l, $pages, $bytes) = $line =~ m/(?:level (\d+)|leaf) pages:.*pages=(\d+), data=(\d+) bytes/ ) {
      $l ||= 0;
      $idx_stats{$cur_tbl}->{$cur_idx}->{real_pages} += $pages;
      $idx_stats{$cur_tbl}->{$cur_idx}->{real_bytes} += $bytes;
      $tbl_stats{$cur_tbl}->{real_pages} += $pages;
      $tbl_stats{$cur_tbl}->{real_bytes} += $bytes;
   }
}
my $hdr_fmt = "%${max_tbl_len}s %${max_idx_len}s %9s %10s %10s\n";
my @headers = qw(TABLE INDEX TOT_PAGES FREE_PAGES PCT_FULL);
printf $hdr_fmt, @headers;
my $row_fmt = "%${max_tbl_len}s %${max_idx_len}s %9d %10d %9.1f%%\n";
foreach my $t ( sort keys %tbl_stats ) {
   my $tbl = $tbl_stats{$t};
   printf $row_fmt, $t, "", $tbl->{est_sp}, $tbl->{est_sp} - $tbl->{real_pages},
      $tbl->{real_bytes} / ($tbl->{real_pages} * $PG_SIZE) * 100;
   foreach my $i ( sort keys %{$idx_stats{$t}} ) {
      my $idx = $idx_stats{$t}->{$i};
      printf $row_fmt, $t, $i, $idx->{est_sp}, $idx->{est_sp} - $idx->{real_pages},
         $idx->{real_bytes} / ($idx->{real_pages} * $PG_SIZE) * 100;
   }
}

Utilisation des journaux binaires

L'exécutable xtrabackup s'intègre à la table log_status. Cette intégration permet à xtrabackup d'afficher la position du journal binaire correspondant à la sauvegarde, afin que vous puissiez utiliser cette position pour provisionner une nouvelle réplique ou effectuer une récupération à un point dans le temps.

Trouver la position du journal binaire

Vous pouvez trouver la position du journal binaire correspondant à une sauvegarde après qu'elle a été effectuée. Si votre sauvegarde provient d'un serveur avec la journalisation binaire activée, xtrabackup crée un fichier nommé xtrabackup_binlog_info dans le répertoire cible. Ce fichier contient le nom du fichier du journal binaire et la position exacte du moment où la sauvegarde a été prise.

La sortie est similaire à ce qui suit pendant la phase de sauvegarde :

210715 14:14:59 Backup created in directory '/backup/'
MySQL binlog position: filename 'binlog.000002', position '156'
. . .
210715 14:15:00 completed OK!

REMARQUE :

À partir de Percona XtraBackup 8.0.26-18.0, xtrabackup ne crée plus le fichier xtrabackup_binlog_pos_innodb. Ce changement est dû au fait que MySQL et Percona Server ne mettent plus à jour les informations du journal binaire sur la section globale du système de transactions de ibdata. Vous devez vous fier à xtrabackup_binlog_info quel que soit le moteur de stockage utilisé.

Configuration d'une nouvelle réplique de réplication

Pour configurer une nouvelle réplique, vous devez préparer la sauvegarde et la restaurer dans le répertoire de données de votre nouvelle réplique de réplication. Si vous utilisez la version 8.0.22 ou antérieure, dans votre commande CHANGE MASTER TO, utilisez le nom de fichier et la position du journal binaire indiqués dans le fichier xtrabackup_binlog_info pour démarrer la réplication.

Sauvegardes en flux

Percona XtraBackup prend en charge le mode flux. Le mode flux envoie une sauvegarde vers STDOUT au format xbstream au lieu de copier les fichiers dans le répertoire de sauvegarde.

Cette méthode vous permet d'utiliser d'autres programmes pour filtrer la sortie de la sauvegarde, offrant ainsi une plus grande flexibilité pour le stockage de la sauvegarde. Par exemple, la compression est obtenue en redirigeant la sortie vers un utilitaire de compression. L'un des avantages des sauvegardes en flux et de l'utilisation des pipes Unix est que les sauvegardes peuvent être automatiquement chiffrées.

Pour utiliser la fonctionnalité de flux, vous devez utiliser l'option --stream, en spécifiant le format du flux (xbstream) et où stocker les fichiers temporaires :

$ xtrabackup --stream=xbstream --target-dir=/tmp

xtrabackup utilise xbstream pour envoyer tous les fichiers de données vers STDOUT, dans un format spécial xbstream. Une fois qu'il a terminé l'envoi de tous les fichiers de données vers STDOUT, il arrête xtrabackup et envoie également le fichier journal sauvegardé.

Chiffrement des Sauvegardes

Percona XtraBackup prend en charge le chiffrement et le déchiffrement des sauvegardes locales et en flux avec l'option xbstream, ajoutant ainsi une couche de protection supplémentaire. Le chiffrement est implémenté à l'aide de la bibliothèque libgcrypt de GnuPG.

Création de Sauvegardes Chiffrées

Pour créer une sauvegarde chiffrée, les options suivantes doivent être spécifiées (les options --encrypt-key et --encrypt-key-file sont mutuellement exclusives, c'est-à-dire qu'une seule d'entre elles doit être fournie) :

  • --encrypt
  • :option:` --encrypt-key`
  • :option:` --encrypt-key-file`

Les options --encrypt-key et --encrypt-key-file peuvent être utilisées pour spécifier la clé de chiffrement. Une clé de chiffrement peut être générée avec une commande comme openssl rand -base64 32

Un exemple de sortie de cette commande devrait ressembler à ceci :

U2FsdGVkX19VPN7VM+lwNI0fePhjgnhgqmDBqbF3Bvs=

Cette valeur peut ensuite être utilisée comme clé de chiffrement.

L'option --encrypt-key

Un exemple de commande xtrabackup utilisant l'option --encrypt-key devrait ressembler à ceci :

> 
$  xtrabackup --backup --encrypt=AES256 --encrypt-key="U2FsdGVkX19VPN7VM+lwNI0fePhjgnhgqmDBqbF3Bvs=" --target-dir=/data/backup

L'option --encrypt-key-file

Utilisez l'option --encrypt-key-file comme suit:

$ xtrabackup --backup --encrypt=AES256 --encrypt-key-file=/data/backups/keyfile --target-dir=/data/backup

NOTE:

Selon l'éditeur de texte que vous utilisez pour créer le KEYFILE, l'éditeur peut insérer automatiquement le caractère CRLF (fin de ligne). Cela augmentera la taille de la clé, la rendant ainsi invalide. La méthode suggérée pour créer le fichier est d'utiliser la ligne de commande: echo -n "U2FsdGVkX19VPN7VM+lwNI0fePhjgnhgqmDBqbF3Bvs=" > /data/backups/keyfile.

Optimiser le processus de chiffrement

Deux nouvelles options sont disponibles pour les sauvegardes chiffrées qui peuvent être utilisées pour accélérer le processus de chiffrement. Il s'agit de --encrypt-threads et --encrypt-chunk-size. En utilisant l'option --encrypt-threads, plusieurs threads peuvent être spécifiés pour être utilisés pour le chiffrement en parallèle. L'option --encrypt-chunk-size peut être utilisée pour spécifier la taille (en octets) du tampon de chiffrement de travail pour chaque thread de chiffrement (par défaut 64K).

Déchiffrer les sauvegardes chiffrées

Les sauvegardes peuvent être déchiffrées avec xbcrypt. La commande suivante en une seule ligne peut être utilisée pour chiffrer tout le dossier:

$ for i in `find . -iname "*\.xbcrypt"`; do xbcrypt -d --encrypt-key-file=/root/secret_key --encrypt-algo=AES256 < $i > $(dirname $i)/$(basename $i .xbcrypt) && rm $i; done

L'option --decrypt de Percona XtraBackup a été implémentée et peut être utilisée pour déchiffrer les sauvegardes:

$ xtrabackup --decrypt=AES256 --encrypt-key="U2FsdGVkX19VPN7VM+lwNI0fePhjgnhgqmDBqbF3Bvs=" --target-dir=/data/backup/

Percona XtraBackup ne supprime pas automatiquement les fichiers chiffrés. Afin de nettoyer le répertoire de sauvegarde, les utilisateurs doivent supprimer les fichiers *.xbcrypt.

NOTE:

--parallel peut être utilisé avec l'option --decrypt pour déchiffrer plusieurs fichiers simultanément.

Une fois les fichiers déchiffrés, la sauvegarde peut être préparée.

Préparer les sauvegardes chiffrées

Après le déchiffrement des sauvegardes, elles peuvent être préparées de la même manière que les sauvegardes complètes standard avec l'option --prepare:

$ xtrabackup --prepare --target-dir=/data/backup/

Restaurer les sauvegardes chiffrées

xtrabackup offre l'option --copy-back pour restaurer une sauvegarde dans le datadir du serveur:

$ xtrabackup --copy-back --target-dir=/data/backup/

Cela copiera tous les fichiers liés aux données dans le datadir du serveur, déterminé par le fichier de configuration my.cnf du serveur. Vous devriez vérifier la dernière ligne de la sortie pour un message de succès:

150318 11:08:13  xtrabackup: completed OK!

Option FLUSH TABLES WITH READ LOCK

L'option FLUSH TABLES WITH READ LOCK fait ce qui suit avec un verrou de lecture global:

  • Ferme toutes les tables ouvertes
  • Verrouille toutes les tables pour toutes les bases de données

Libérez le verrou avec UNLOCK TABLES.

NOTE:

FLUSH TABLES WITH READ LOCK n'empêche pas l'insertion de lignes dans les tables de journaux.

Pour garantir des sauvegardes cohérentes, utilisez l'option FLUSH TABLES WITH READ LOCK avant d'effectuer une sauvegarde de fichiers non-InnoDB. L'option n'affecte pas les requêtes de longue durée.

Les requêtes de longue durée avec FLUSH TABLES WITH READ LOCK activé peuvent laisser le serveur en mode lecture seule jusqu'à ce que les requêtes soient terminées. Tuer FLUSH TABLES WITH READ LOCK n'aide pas si la base de données est dans l'état Waiting for table flush ou Waiting for master to send event. Pour revenir à un fonctionnement normal, vous devez tuer toutes les requêtes de longue durée.

NOTE:

Tout ce qui est décrit dans cette section n'a aucun effet lorsque les verrous de sauvegarde sont utilisés. Percona XtraBackup utilisera les verrous de sauvegarde lorsque disponibles comme alternative légère à FLUSH TABLES WITH READ LOCK. Cette fonctionnalité est disponible dans Percona Server for MySQL 5.6+. Percona XtraBackup l'utilise automatiquement pour copier les données non-InnoDB afin d'éviter de bloquer les requêtes DML qui modifient les tables InnoDB.

Pour éviter que cela ne se produise, deux choses ont été implémentées:

  • xtrabackup attend un moment propice pour émettre le verrou global
  • xtrabackup tue toutes les requêtes ou uniquement les requêtes SELECT qui empêchent l'acquisition du verrou global

Attendre la fin des requêtes

Vous devriez émettre un verrou global lorsqu'aucune requête longue n'est en cours d'exécution. Attendre pour émettre le verrou global pendant une période prolongée n'est pas une bonne méthode. L'attente peut prolonger le temps nécessaire à la sauvegarde. L'option --ftwrl-wait-timeout peut limiter le temps d'attente. Si le verrou ne peut pas être émis pendant ce temps, xtrabackup arrête l'option, se termine avec un message d'erreur et la sauvegarde n'est pas effectuée.

La valeur par défaut pour cette option est zéro (0), ce qui désactive l'option.

Une autre possibilité est de spécifier le type de requête sur lequel attendre. Dans ce cas --ftwrl-wait-query-type. Les valeurs possibles sont all (toutes) et update (mise à jour). Lorsque all est utilisé, xtrabackup attendra que toutes les requêtes de longue durée (durée d'exécution supérieure à celle autorisée par --ftwrl-wait-threshold) soient terminées avant d'exécuter FLUSH TABLES WITH READ LOCK. Lorsque update est utilisé, xtrabackup attendra que les requêtes UPDATE/ALTER/REPLACE/INSERT soient terminées.

Le temps nécessaire à la complétion d'une requête spécifique est difficile à prévoir. Nous supposons que les requêtes de longue durée ne se termineront pas dans un délai raisonnable. D'autres requêtes de courte durée se terminent rapidement. xtrabackup utilise la valeur de l'option --ftwrl-wait-threshold pour spécifier les requêtes de longue durée et bloquera un verrou global. Pour utiliser cette option, l'utilisateur xtrabackup doit avoir les privilèges PROCESS et SUPER.

Tuer les requêtes bloquantes

La deuxième option consiste à tuer toutes les requêtes qui empêchent l'acquisition du verrou global. Dans ce cas, toutes les requêtes qui s'exécutent plus longtemps que FLUSH TABLES WITH READ LOCK sont des bloqueurs potentiels. Bien que toutes les requêtes puissent être tuées, un temps supplémentaire peut être spécifié pour que les requêtes de courte durée se terminent en utilisant l'option --kill-long-queries-timeout. Cette option spécifie le temps imparti aux requêtes pour se terminer, après quoi toutes les requêtes en cours seront tuées. La valeur par défaut est zéro, ce qui désactive cette fonctionnalité.

L'option --kill-long-query-type peut être utilisée pour spécifier toutes les requêtes ou uniquement les requêtes SELECT qui empêchent l'acquisition du verrou global. Pour utiliser cette option, l'utilisateur xtrabackup doit avoir les privilèges PROCESS et SUPER.

Résumé des options

  • --ftwrl-wait-timeout (secondes) - combien de temps attendre un moment propice. Par défaut 0, ne pas attendre.
  • --ftwrl-wait-query-type - quelles requêtes longues doivent être terminées avant d'exécuter FLUSH TABLES WITH READ LOCK. Par défaut toutes.
  • --ftwrl-wait-threshold (secondes) - combien de temps une requête doit être exécutée avant que nous la considérions comme longue et potentiellement bloquante pour le verrou global.
  • --kill-long-queries-timeout (secondes) - combien de temps nous donnons aux requêtes pour se terminer après l'émission de FLUSH TABLES WITH READ LOCK avant de commencer à tuer. Par défaut 0, ne pas tuer.
  • --kill-long-query-type - quelles requêtes doivent être tuées une fois que kill-long-queries-timeout a expiré.

Exemple

L'exécution de xtrabackup avec les options suivantes entraînera xtrabackup à ne pas attendre plus de 3 minutes que toutes les requêtes plus anciennes que 40 secondes soient terminées.

$  xtrabackup --backup --ftwrl-wait-threshold=40 \
--ftwrl-wait-query-type=all --ftwrl-wait-timeout=180 \
--kill-long-queries-timeout=20 --kill-long-query-type=all \
--target-dir=/data/backups/

Après l'émission de FLUSH TABLES WITH READ LOCK, xtrabackup attendra 20 secondes pour que le verrou soit acquis. Si le verrou n'est toujours pas acquis après 20 secondes, il tuera toutes les requêtes qui s'exécutent plus longtemps que FLUSH TABLES WITH READ LOCK.

Accélérer le processus de sauvegarde

Copie avec les options --parallel et --compress-threads

Lors de la création d'une sauvegarde locale ou en streaming avec l'option xbstream, plusieurs fichiers peuvent être copiés en même temps en utilisant l'option --parallel. Cette option spécifie le nombre de threads créés par xtrabackup pour copier les fichiers de données.

Pour profiter de cette

en option soit les tablespaces multiples l'option doit être activée (innodb_file_per_table) soit le tablespace partagé doit être stocké dans plusieurs fichiers ibdata avec l'option innodb_data_file_path. Avoir plusieurs fichiers pour la base de données (ou en diviser un en plusieurs) n'a pas d'impact mesurable sur les performances.

Comme cette fonctionnalité est implémentée au niveau du fichier, le transfert de fichiers simultané peut parfois augmenter le débit d'E/S lors d'une sauvegarde sur des fichiers de données fortement fragmentés, en raison du chevauchement d'un plus grand nombre de requêtes de lecture aléatoire. Vous devriez également envisager d'optimiser le système de fichiers pour obtenir des performances maximales (par exemple, en vérifiant la fragmentation).

Si les données sont stockées dans un seul fichier, cette option n'aura aucun effet.

Pour utiliser cette fonctionnalité, ajoutez simplement l'option à une sauvegarde locale, par exemple :

$ xtrabackup --backup --parallel=4 --target-dir=/path/to/backup

En utilisant xbstream dans les sauvegardes en streaming, vous pouvez en plus accélérer le processus de compression avec l'option --compress-threads. Cette option spécifie le nombre de threads créés par xtrabackup pour la compression de données parallèle. La valeur par défaut pour cette option est 1.

Pour utiliser cette fonctionnalité, ajoutez simplement l'option à une sauvegarde locale, par exemple :

$ xtrabackup --backup --stream=xbstream --compress --compress-threads=4 --target-dir=./ > backup.xbstream

Avant d'appliquer les journaux, les fichiers compressés devront être décompressés.

L'option --rsync

Afin d'accélérer le processus de sauvegarde et de minimiser le temps pendant lequel FLUSH TABLES WITH READ LOCK bloque les écritures, l'option --rsync doit être utilisée. Lorsque cette option est spécifiée, xtrabackup utilise rsync pour copier tous les fichiers non-InnoDB au lieu de lancer un cp séparé pour chaque fichier, ce qui peut être beaucoup plus rapide pour les serveurs avec un grand nombre de bases de données ou de tables. xtrabackup appellera rsync deux fois, une fois avant le FLUSH TABLES WITH READ LOCK et une fois pendant pour minimiser le temps pendant lequel le verrou de lecture est maintenu. Lors du second appel à rsync, il ne synchronisera que les changements apportés aux données non transactionnelles (le cas échéant) depuis le premier appel effectué avant le FLUSH TABLES WITH READ LOCK. Notez que Percona XtraBackup utilisera les verrous de sauvegarde lorsque disponibles comme alternative légère à FLUSH TABLES WITH READ LOCK. Cette fonctionnalité est disponible dans Percona Server for MySQL 5.6+. Percona XtraBackup l'utilise automatiquement pour copier les données non-InnoDB afin d'éviter de bloquer les requêtes DML qui modifient les tables InnoDB.

NOTE :

Cette option ne peut pas être utilisée avec l'option --stream.

Pour savoir quelle est la situation de la journalisation binaire sur le serveur, exécutez les requêtes suivantes :

mysql> SHOW BINARY LOGS;
+------------------+-----------+
| Log_name         | File_size |
+------------------+-----------+
| mysql-bin.000001 |       126 |
| mysql-bin.000002 |      1306 |
| mysql-bin.000003 |       126 |
| mysql-bin.000004 |       497 |
+------------------+-----------+

et

mysql> SHOW MASTER STATUS;
+------------------+----------+--------------+------------------+
| File             | Position | Binlog_Do_DB | Binlog_Ignore_DB |
+------------------+----------+--------------+------------------+
| mysql-bin.000004 |      497 |              |                  |
+------------------+----------+--------------+------------------+

La première requête vous indiquera quels fichiers contiennent le journal binaire et la seconde quel fichier est actuellement utilisé pour enregistrer les modifications, ainsi que la position actuelle dans celui-ci. Ces fichiers sont généralement stockés dans le datadir (sauf si un autre emplacement est spécifié lors du démarrage du serveur avec l'option --log-bin=).

Pour connaître la position de l'instantané pris, consultez xtrabackup_binlog_info dans le répertoire de sauvegarde :

$ cat /path/to/backup/xtrabackup_binlog_info
mysql-bin.000003      57

Cela vous indiquera quel fichier a été utilisé au moment de la sauvegarde pour le journal binaire et sa position. Cette position sera celle effective lorsque vous restaurerez la sauvegarde :

$ xtrabackup --copy-back --target-dir=/path/to/backup

Comme la restauration n'affectera pas les fichiers du journal binaire (vous devrez peut-être ajuster les autorisations de fichiers, voir restoring_a_backup), l'étape suivante consiste à extraire les requêtes du journal binaire avec mysqlbinlog en commençant par la position de l'instantané et en les redirigeant vers un fichier

$ mysqlbinlog /path/to/datadir/mysql-bin.000003 /path/to/datadir/mysql-bin.000004 \
    --start-position=57 > mybinlog.sql

Notez que si vous avez plusieurs fichiers pour le journal binaire, comme dans l'exemple, vous devez extraire les requêtes avec un seul processus, comme indiqué ci-dessus.

Inspectez le fichier avec les requêtes pour déterminer quelle position ou date correspond au point dans le temps souhaité. Une fois déterminé, redirigez-le vers le serveur. En supposant que le point est 11-12-25 01:00:00 :

$ mysqlbinlog /path/to/datadir/mysql-bin.000003 /path/to/datadir/mysql-bin.000004 \
    --start-position=57 --stop-datetime="11-12-25 01:00:00" | mysql -u root -p

et la base de données sera remontée jusqu'à ce Point dans le temps.

Faire des sauvegardes dans des environnements de réplication

Il existe des options spécifiques pour sauvegarder à partir d'une réplique de réplication.

L'option --slave-info

Cette option est utile lors de la sauvegarde d'un serveur de réplication de réplique. Elle affiche la position du journal binaire et le nom du serveur source. Elle écrit également ces informations dans le fichier xtrabackup_slave_info sous forme d'instruction CHANGE MASTER.

Cette option est utile pour configurer une nouvelle réplique pour cette source. Vous pouvez démarrer un serveur de réplication avec cette sauvegarde et exécuter l'instruction enregistrée dans le fichier xtrabackup_slave_info. Plus de détails sur cette procédure se trouvent dans replication_howto.

L'option --safe-slave-backup

Afin d'assurer un état de réplication cohérent, cette option arrête le thread SQL de réplication et attend avant de commencer la sauvegarde jusqu'à ce que Slave_open_temp_tables dans SHOW STATUS soit égal à zéro. S'il n'y a pas de tables temporaires ouvertes, la sauvegarde aura lieu, sinon le thread SQL sera démarré et arrêté jusqu'à ce qu'il n'y ait plus de tables temporaires ouvertes. La sauvegarde échouera si Slave_open_temp_tables ne devient pas zéro après --safe-slave-backup-timeout secondes (par défaut 300 secondes). Le thread SQL de réplication sera redémarré lorsque la sauvegarde sera terminée.

L'utilisation de cette option est toujours recommandée lors de la sauvegarde à partir d'un serveur de réplique.

AVERTISSEMENT :

Assurez-vous que votre réplique est une réplique fidèle de la source avant de l'utiliser comme source pour la sauvegarde. Un bon outil pour valider une réplique est pt-table-checksum.

Stocker l'historique des sauvegardes sur le serveur

Percona XtraBackup prend en charge le stockage de l'historique des sauvegardes sur le serveur. Cette fonctionnalité a été implémentée dans Percona XtraBackup 2.2. Le stockage de l'historique des sauvegardes sur le serveur a été mis en œuvre pour fournir aux utilisateurs des informations supplémentaires sur les sauvegardes en cours. Les informations sur l'historique des sauvegardes seront stockées dans la table PERCONA_SCHEMA.XTRABACKUP_HISTORY.

Pour utiliser cette fonctionnalité, les options suivantes sont disponibles :

  • --history =<nom> : Cette option active la fonctionnalité d'historique et permet à l'utilisateur de spécifier un nom de série de sauvegarde qui sera placé dans l'enregistrement d'historique.
  • --incremental-history-name =<nom> : Cette option permet de créer une sauvegarde incrémentielle basée sur une série d'historique spécifique par nom. xtrabackup recherchera dans la table d'historique la sauvegarde la plus récente (avec le plus grand to_lsn) de la série et utilisera la valeur to_lsn comme lsn de départ. Ceci est mutuellement exclusif avec les options --incremental-history-uuid, --incremental-basedir et --incremental-lsn. Si aucun LSN valide ne peut être trouvé (pas de série portant ce nom), xtrabackup retournera une erreur.
  • --incremental-history-uuid =<uuid> : Permet de créer une sauvegarde incrémentielle basée sur un enregistrement d'historique spécifique identifié par un UUID. xtrabackup recherchera dans la table d'historique l'enregistrement correspondant à l'UUID et utilisera la valeur to_lsn comme LSN de départ. Cette option est mutuellement exclusive avec les options --incremental-basedir, --incremental-lsn et --incremental-history-name. Si aucun LSN valide ne peut être trouvé (pas d'enregistrement portant cet UUID ou to_lsn manquant), xtrabackup retournera une erreur.

NOTE :

La sauvegarde en cours d'exécution n'existera **PAS** dans la table xtrabackup_history dans le jeu de sauvegarde résultant, car l'enregistrement ne sera ajouté à cette table qu'après la prise de la sauvegarde.

Si vous souhaitez accéder à l'historique des sauvegardes en dehors de votre jeu de sauvegardes en cas d'événement catastrophique, vous devrez effectuer un mysqldump, une sauvegarde partielle ou un SELECT * sur la table d'historique après que xtrabackup ait terminé.

Limitations

The PERCONA_SCHEMA.XTRABACKUP_HISTORY table stores information about previous server backups. Backup information is only written to this table if the backup was created using the --history option.

IMPLÉMENTATION

Détails d'implémentation

Cette page contient des notes sur divers aspects internes du fonctionnement de l'outil xtrabackup.

Permissions des fichiers

xtrabackup ouvre les fichiers de données source en mode lecture-écriture, bien qu'il ne les modifie pas. Cela signifie que vous devez exécuter xtrabackup en tant qu'utilisateur disposant des permissions d'écriture sur les fichiers de données. La raison pour laquelle les fichiers sont ouverts en mode lecture-écriture est que xtrabackup utilise les bibliothèques embarquées InnoDB pour ouvrir et lire les fichiers, et InnoDB les ouvre en mode lecture-écriture car il suppose normalement qu'il va écrire dedans.

Réglage des tampons du système d'exploitation

Étant donné que xtrabackup lit de grandes quantités de données depuis le système de fichiers, il utilise posix_fadvise() lorsque cela est possible, pour indiquer au système d'exploitation de ne pas essayer de mettre en cache les blocs lus depuis le disque. Sans cet indice, le système d'exploitation préférerait mettre en cache les blocs, en supposant que xtrabackup en aura à nouveau besoin, ce qui n'est pas le cas. La mise en cache de fichiers aussi volumineux peut exercer une pression sur la mémoire virtuelle du système d'exploitation et entraîner le déplacement d'autres processus, tels que le serveur de base de données, hors de la mémoire. L'outil xtrabackup évite cela avec l'indice suivant sur les fichiers source et destination :

posix_fadvise(file, 0, 0, POSIX_FADV_DONTNEED)

De plus, xtrabackup demande au système d'exploitation d'effectuer des optimisations de prélecture plus agressives sur les fichiers source :

posix_fadvise(file, 0, 0, POSIX_FADV_SEQUENTIAL)

Copie des fichiers de données

Lors de la copie des fichiers de données vers le répertoire cible, xtrabackup lit et écrit 1 Mo de données à la fois. Ceci n'est pas configurable. Lors de la copie du fichier journal, xtrabackup lit et écrit 512 octets à la fois. Ceci n'est pas non plus configurable et correspond au comportement d'InnoDB (une solution de contournement existe dans Percona Server for MySQL car il dispose d'une option pour régler innodb_log_block_size pour XtraDB, et dans ce cas Percona XtraBackup correspondra au réglage).

Après la lecture des fichiers, xtrabackup itère sur le tampon de 1 Mo page par page, et vérifie la corruption de chaque page avec la fonction buf_page_is_corrupted() d'InnoDB. Si la page est corrompue, il la relit et réessaie jusqu'à 10 fois pour chaque page. Il ignore cette vérification sur le tampon de double écriture.

Codes de sortie de xtrabackup

Le binaire xtrabackup se termine avec la valeur de succès traditionnelle de 0 après une sauvegarde, en l'absence d'erreur. Si une erreur survient pendant la sauvegarde, la valeur de sortie est 1.

Dans certains cas, la valeur de sortie peut être différente de 0 ou 1, en raison du code d'option en ligne de commande inclus à partir des bibliothèques MySQL. Une option en ligne de commande inconnue, par exemple, provoquera un code de sortie de 255.

Modes de fonctionnement

Vous invoquez xtrabackup dans l'un des modes suivants :

  • Mode --backup pour effectuer une sauvegarde dans un répertoire cible.
  • Mode --prepare pour restaurer les données à partir d'une sauvegarde (créée en mode --backup).
  • Mode --copy-back pour copier les données d'une sauvegarde vers l'emplacement qui contenait les données d'origine ; pour déplacer les données au lieu de les copier, utilisez le mode alternatif --move-back.
  • Mode --stats pour scanner les fichiers de données spécifiés et afficher les statistiques d'index.

Lorsque vous avez l'intention d'exécuter xtrabackup dans l'un de ces modes, utilisez la syntaxe suivante :

$ xtrabackup [--defaults-file=#] --backup|--prepare|--copy-back|--stats [OPTIONS]

Par exemple, le mode --prepare s'applique comme suit :

$ xtrabackup --prepare --target-dir=/data/backup/mysql/

    Spécifie le répertoire qui sera utilisé pour stocker les fichiers temporaires pendant la sauvegarde.
    --transition-key=name
    Cette option est utilisée pour activer le traitement de la sauvegarde sans accéder au serveur de coffre-fort de clés (keyring). Dans ce cas, xtrabackup dérive la clé de chiffrement AES de la phrase secrète spécifiée et l'utilise pour chiffrer les clés des espaces de table (tablespaces) en cours de sauvegarde.

    Si --transition-key n'a pas de valeur, xtrabackup vous la demandera. La même phrase secrète doit être spécifiée pour la commande --prepare.

    --use-memory
    Cette option affecte la quantité de mémoire allouée pour préparer une sauvegarde avec --prepare, ou pour analyser les statistiques avec --stats. Son objectif est similaire à celui de innodb_buffer_pool_size. Elle ne fait pas la même chose que l'option du même nom dans l'outil InnoDB Hot Backup d'Oracle. La valeur par défaut est 100 Mo, et si vous avez suffisamment de mémoire disponible, 1 Go à 2 Go est une bonne valeur recommandée. Les multiples sont pris en charge en fournissant l'unité (par exemple, 1MB, 1M, 1GB, 1G).
    --user=USERNAME
    Cette option spécifie le nom d'utilisateur MySQL utilisé lors de la connexion au serveur, si ce n'est pas l'utilisateur actuel. L'option accepte un argument de type chaîne. Voir mysql --help pour plus de détails.
    -v
    Voir --version.
    --version
    Cette option affiche la version de xtrabackup et quitte.
    --xtrabackup-plugin-dir=DIRNAME
    Le chemin absolu vers le répertoire contenant le plugin keyring.
