NOM

xorrisofs - Émulation du programme mkisofs par le programme xorriso

SYNTAXE

xorrisofs [ options ] [-o nom_fichier ] spécification_chemin [spécifications_chemin ...]

DESCRIPTION

xorrisofs produit des systèmes de fichiers améliorés Rock Ridge ISO 9660 et des sessions supplémentaires à de tels systèmes de fichiers. Optionnellement, il peut aussi produire des arborescences de répertoires Joliet.

xorrisofs comprend les options du programme mkisofs de cdrtools par Joerg Schilling. Son implémentation fait partie du programme xorriso, qui ne partage aucun code source avec cdrtools.

ISO 9660, Rock Ridge, Joliet, HFS+ :

ISO 9660 (également connu sous le nom de ECMA-119) est un système de fichiers en lecture seule principalement utilisé pour les médias optiques (CD, DVD, BD), mais qui peut aussi résider sur d'autres périphériques de stockage comme des fichiers disque, des clés USB ou des partitions de disque. Il est largement lisible par de nombreux systèmes d'exploitation et par les installations de démarrage des ordinateurs personnels.
ISO 9660 décrit les répertoires et les fichiers de données par des noms de fichiers très restreints, sans distinction entre majuscules et minuscules. Ses métadonnées ne sont pas conformes aux spécifications POSIX fondamentales.
Rock Ridge est le nom d'un ensemble d'informations supplémentaires qui améliorent un système de fichiers ISO 9660 afin qu'il puisse représenter un système de fichiers conforme à POSIX avec la propriété, les permissions d'accès, les liens symboliques et d'autres attributs. Rock Ridge autorise des noms de fichiers allant jusqu'à 255 octets et des chemins allant jusqu'à 1024 octets.
xorrisofs produit des informations Rock Ridge par défaut. Il est fortement déconseillé de désactiver cette fonctionnalité.
Joliet est le nom d'une arborescence de répertoires supplémentaire qui fournit des noms de fichiers jusqu'à 64 caractères encodés en UTF-16. Une arborescence Joliet est principalement utile pour lire l'image ISO par les systèmes d'exploitation de Microsoft Corporation. La production de cette arborescence de répertoires peut être activée par l'option -J.
ISO 9660:1999 est le nom d'une arborescence de répertoires supplémentaire qui fournit des noms de fichiers plus longs. Elle autorise des noms de fichiers individuels de jusqu'à 207 caractères. Elle pourrait être utile avec certaines anciennes installations de démarrage de systèmes informatiques qui ne lisent ni Rock Ridge ni Joliet mais qui ont néanmoins besoin de noms de fichiers plus longs. La production de cette arborescence de répertoires peut être activée par l'option -iso-level 4.
HFS+ est le nom d'un système de fichiers normalement utilisé pour écrire et lire sur les disques durs et les périphériques similaires. Il est possible d'intégrer une partition HFS+ dans l'image ISO 9660 émergente et de la marquer avec des entrées de table de partition Apple. Cela interfère avec les options qui copient des données dans les 32 premiers Kio de l'image ISO, comme -G ou -isohybrid-mbr. Voir l'option -hfsplus.
Le but principal d'avoir une partition HFS+ intégrée est le démarrage de certains modèles d'ordinateurs Apple.

Insertion des fichiers dans l'image ISO :

xorrisofs traite deux types d'adresses de fichiers :
chemin_disque est un chemin vers un objet dans l'arborescence du système de fichiers local.
chemin_iso_rr est l'adresse Rock Ridge d'un objet fichier dans l'image ISO. Si aucune information Rock Ridge ne doit être stockée dans une image ISO émergente, les noms seront mappés à des noms ISO 9660 de longueur et jeu de caractères limités.

Un argument de programme est traité comme une spécification_chemin s'il n'est pas reconnu comme une option mkisofs originale ou une option supplémentaire de xorrisofs. Une spécification_chemin décrit un objet fichier d'entrée par un chemin_disque. Si l'option -graft-points n'est pas présente, alors le comportement dépend du type de fichier du chemin_disque. Les répertoires sont fusionnés avec le répertoire / de l'image ISO. Les fichiers d'autres types sont copiés dans le répertoire /.
Si -graft-points est présent, chaque spécification_chemin est divisée à la première occurrence du caractère =. La partie avant le = est considérée comme la cible, c'est-à-dire le chemin_iso_rr pour l'objet fichier dans l'image ISO. La partie après le premier = est considérée comme la source, c'est-à-dire le chemin_disque de l'objet d'entrée.
Il est possible d'inclure des caractères = dans le chemin_iso_rr en les faisant précéder d'un caractère \. La même chose doit être faite pour les caractères \ qui doivent faire partie du chemin_iso_rr.

Si la partie source de la spécification_chemin mène à un répertoire, tous les fichiers sous ce répertoire sont également insérés. Il est possible d'exclure des fichiers particuliers de l'insertion à l'aide de l'option -m.
Dans le cas où la cible existe déjà, les règles suivantes s'appliquent : les répertoires et autres fichiers peuvent remplacer des non-répertoires existants. Les répertoires sont fusionnés avec des répertoires existants. Les non-répertoires ne peuvent pas remplacer des répertoires existants.

Relation avec le programme xorriso :

xorrisofs est en fait un mode de commande du programme xorriso, auquel on accède soit par la commande xorriso "-as mkisofs" soit en démarrant le programme sous l'un des noms "xorrisofs", "mkisofs", "genisoimage", ou "genisofs".
Ce mode de commande peut être quitté par l'argument "--" qui mène au mode de commande générique xorriso. Voir man xorriso pour sa description.

xorriso effectue la lecture et l'écriture d'images à l'aide de libburn, qui est principalement destiné aux lecteurs optiques, mais fonctionne également sur tous les types de fichiers POSIX, à l'exception des répertoires.
Les messages du programme désignent tout fichier image comme un "lecteur". Les types de fichiers qui ne sont pas pris en charge en lecture sont signalés comme "vierges". L'espace média libre signalé peut être assez fictif.
Néanmoins, xorrisofs n'opère pas directement sur les lecteurs optiques, mais force plutôt libburn à les considérer comme des fichiers périphériques généraux. Ainsi, pour écrire des médias optiques séquentiels (CD, DVD-R, DVD+R, BD-R), il faudra utiliser un programme de gravure. Par exemple, l'émulation cdrecord de xorriso. Voir EXEMPLES.

OPTIONS

Chargement de l'image :

Les options suivantes contrôlent le chargement d'une image ISO existante dans le but de préparer une session supplémentaire appropriée. Si elles sont absentes, une nouvelle image est composée à partir de zéro.

-M chemin_disque
Définit le chemin à partir duquel charger l'arborescence de répertoire de l'image ISO existante sur laquelle baser la prochaine arborescence de répertoire en tant que session supplémentaire. Le chemin doit mener à un objet fichier lisible en accès aléatoire. Sur GNU/Linux : fichiers de données réguliers ou fichiers de périphérique bloc.
Un type spécial de chemin_disque pseudo a la forme "/dev/fd/"numéro. Il représente le descripteur de fichier ouvert avec le numéro donné, indépendamment du fait que le système d'exploitation prenne en charge cette fonctionnalité par des nœuds de fichiers dans /dev/fd ou non. Par exemple, /dev/fd/3 est le descripteur de fichier 3 qui a été ouvert par le programme qui a ensuite lancé xorriso.
-prev-session chemin_disque
Alias de -M.
-dev chemin_disque
Alias de -M.
-C debut_derniere_session,prochaine_adresse_ecriture
Définit l'adresse de bloc de 2 Kio debut_derniere_session à partir de laquelle lire l'image ISO depuis le fichier donné par l'option -M.
Séparé par une virgule, définit la prochaine_adresse_ecriture à laquelle la session supplémentaire sera finalement écrite. Décisif est en fait l'adresse de bloc que les lecteurs prévus devront utiliser comme adresse de superbloc sur le support prévu.
Les deux valeurs peuvent être interrogées sur les médias optiques à l'aide des programmes de gravure et de l'option -msinfo de cdrecord. xorriso lui-même peut l'obtenir dans son émulation cdrecord.
valeurs=$(xorriso -as cdrecord dev=/dev/... -msinfo)
echo $valeurs
L'option -C peut être utilisée sans l'option -M pour créer une image ISO à partir de zéro et la préparer à être finalement écrite à une adresse de bloc autre que 0. debut_derniere_session doit alors être défini à 0.
-cdrecord-params debut_derniere_session,prochaine_adresse_ecriture
Alias de -C.

--zisofs-version-2

Activer la reconnaissance et le traitement approprié des fichiers compressés zisofs expérimentaux version 2. Le noyau Linux (à partir de 5.9) ne connaît pas encore ce format et se plaindra comme suit :
isofs: Unknown ZF compression algorithm: PZ
Cette plainte peut être évitée par l'option --zisofs2-susp-z2 .
Les fichiers seront affichés par les noyaux non avertis tels qu'ils ont été soumis à xorriso, c'est-à-dire avec l'en-tête zisofs2, la liste des pointeurs de bloc et les données compressées.
--zisofs-version-2 active également -z.
--zisofs2-susp-z2
Activer la production d'entrées SUSP "Z2" plutôt que "ZF" avec les fichiers compressés zisofs2. Les noyaux Linux non avertis ignorent silencieusement les entrées "Z2".
--zisofs2-susp-zf
Activer la production d'entrées SUSP "ZF" plutôt que "Z2" avec les fichiers compressés zisofs2. Les noyaux Linux non avertis se plaignent de zisofs2 "ZF" avec "Unknown ZF compression algorithm" et laissent ainsi une marque dans le journal système.
-root iso_rr_path
Insérer tous les fichiers sous l'iso_rr_path donné. Si l'option -graft-points est donnée, alors iso_rr_path est ajouté au début de chaque partie cible d'une spécification de chemin.
La valeur par défaut pour -root est "/".
-old-root iso_rr_path
Activer l'insertion incrémentielle de fichiers dans l'image chargée. Les adresses cibles et sources effectives des spécifications de chemin données sont comparées pour vérifier si la cible existe déjà dans l'image ISO et est toujours identique à la source sur disque. Les métadonnées de l'image ISO seront ajustées si elles diffèrent de celles sur disque. Les nouveaux fichiers et les fichiers dont le contenu a changé seront ajoutés. Les fichiers cibles qui n'existent dans aucune des sources de spécification de chemin correspondantes seront supprimés de l'arborescence des répertoires ISO.
Si le réglage effectif de -root diffère de l'iso_rr_path donné avec -old-root, alors les fichiers sous le répertoire -old-root seront clonés sous le répertoire -root. Le clonage se produit avant la comparaison des fichiers.
--old-root-no-ino
Désactiver l'enregistrement et l'utilisation des numéros d'inode du disque. Si aucun numéro d'inode de disque n'est enregistré, alors l'option -old-root devra lire le contenu du fichier disque et le comparer avec la somme de contrôle MD5 enregistrée dans l'image ISO.
Avec les numéros d'inode de disque enregistrés et avec des ctime et mtime crédibles, il est possible de détecter des modifications potentielles du contenu sans le lire réellement. Une échappatoire subsiste si plusieurs systèmes de fichiers différents peuvent être montés au même répertoire, comme c'est l'habitude avec /mnt. Dans ce cas, il faut utiliser l'option --old-root-devno ou désactiver le raccourci des numéros d'inode avec --old-root-no-ino.
--old-root-devno
Activer la comparaison des numéros de périphérique enregistrés avec les numéros d'inode enregistrés. Cela ne fonctionne qu'avec les bons vieux numéros de périphérique stables qui deviennent regrettablement démodés. Si le disque dur a un numéro de périphérique différent après chaque redémarrage, alors cette comparaison verra tous les fichiers comme modifiés et empêchera ainsi toute économie de taille incrémentielle.
--old-root-no-md5
Désactiver l'enregistrement et l'utilisation des sommes de contrôle MD5 pour le contenu des fichiers de données. Si ni les sommes de contrôle ni les numéros d'inode de disque ne sont enregistrés, alors l'option -old-root devra lire le contenu du fichier image ISO lors de sa comparaison avec le contenu du fichier disque.
Paramètres de production de l'image :
-o disk_path
Définir l'adresse du fichier de sortie pour l'image ISO émergente. Si l'adresse existe en tant que fichier régulier, elle sera tronquée à la longueur 0 au début de la production de l'image. Elle ne doit pas déjà exister en tant que répertoire. Si elle n'existe pas encore, alors son répertoire parent doit exister et un fichier régulier sera créé.
Un type spécial de pseudo disk_path a la forme "/dev/fd/"nombre. Il représente le descripteur de fichier ouvert avec le numéro donné, que le système d'exploitation supporte cette fonctionnalité par des nœuds de fichier dans /dev/fd ou non. Par exemple, /dev/fd/4 est le descripteur de fichier 4 qui a été ouvert par le programme qui a ensuite lancé xorriso.
La valeur par défaut est la sortie standard (/dev/fd/1), qui peut également être définie par le disk_path "-".
-output disk_path
Alias de -o.
--stdio_sync "on"|"off"|"end"|nombre
Définir le nombre d'octets après lequel forcer la sortie sur disque afin de éviter que la mémoire ne soit encombrée par de nombreuses données en attente pour les périphériques lents. "on" est identique à "16m". La sortie forcée peut être désactivée par "off", ou retardée par "end" jusqu'à ce que toutes les données soient produites. Si un nombre est choisi, il doit être d'au moins 64k.
La valeur par défaut avec l'émulation xorriso mkisofs est --stdio_sync "off".
xorriso utilise un tampon fifo interne d'une taille par défaut de 4 MiB. Par conséquent, forcer le cache d'entrée/sortie du système d'exploitation sur disque ne bloque pas nécessairement la production simultanée de contenu d'image supplémentaire.
--emul-toc
Écrire un second superblock avec la première session dans des fichiers à accès aléatoire. Si des sessions supplémentaires sont ajoutées et que le premier superblock est mis à jour, le second superblock ne sera pas écrasé. Il sera donc toujours possible de monter la première session et de trouver les blocs de départ des sessions supplémentaires.
Le prix est de 64 KiB d'espace supplémentaire. Si -partition_offset est non nul, alors il est de 128 KiB plus deux fois la configuration de la partition.
--no-emul-toc
Ne pas écrire de second superblock avec la première session dans des fichiers à accès aléatoire.
C'est la valeur par défaut.
--sort-weight weight_number iso_rr_path
Attribuer un numéro de poids LBA aux fichiers réguliers. Si iso_rr_path mène à un répertoire, alors tous les fichiers réguliers en dessous recevront le weight_number.
Le weight_number peut varier de -2147483648 à 2147483647. Plus il est élevé, plus l'adresse de bloc des données du fichier dans l'image ISO émergente sera basse. Actuellement, le catalogue de démarrage El Torito a un poids codé en dur de 1 milliard. Normalement, il devrait occuper le bloc avec l'adresse la plus basse possible. Les fichiers de données sont ajoutés ou chargés avec un poids initial de 0. Les fichiers image de démarrage ont un poids par défaut de 2.
--sort-weight-list disk_path
Lire des paires de numéro de poids et iso_rr_path à partir d'un fichier du système de fichiers local. Appliquer chaque paire comme avec --sort-weight.
Seul le dernier --sort-weight-list ou --sort-weight-patterns d'une exécution xorrisofs prendra effet.
Le numéro de poids est lu depuis le début de la ligne. La partie iso_rr_path d'une ligne d'entrée commence immédiatement après le premier espace ou caractère de tabulation de la ligne.
Notes pour le cas où cette fonctionnalité est utilisée dans une séquence de commandes génériques xorriso (pas un problème avec une pure émulation mkisofs) :
Les fichiers adressés doivent déjà être dans le modèle de l'image ISO lorsque vous exécutez
-as mkisofs --sort-weight-list disk_path --
Plusieurs de ces commandes peuvent être utilisées pour appliquer plus d'un fichier de poids.
Les fichiers de données qui sont chargés par -indev ou -dev reçoivent un poids compris entre 1 et 2 exp 28 = 268 435 456, en fonction de leur adresse de bloc. Cela doit les maintenir approximativement dans le même ordre si la méthode d'écriture de modification est appliquée.
--sort-weight-patterns disk_path
Similaire à --sort-weight-list , mais en développant les iso_rr_paths comme des modèles d'analyseur shell et en appliquant --sort-weight à chaque fichier correspondant.
-uid nombre|nom
Utiliser le numéro ou le nom d'utilisateur local donné comme identifiant du propriétaire pour tous les fichiers et répertoires dans le système de fichiers émergent. Un nom vide ou le nom "-" annule cette fonctionnalité.
-gid nombre|nom
Utilise le nombre donné ou le nom de groupe existant localement comme identifiant de groupe pour tous les fichiers et répertoires du système de fichiers émergent. Un nom vide ou le nom "-" révoquent cette fonctionnalité.
-dir-mode mode
Définit les permissions d'accès pour tous les répertoires de l'image au mode donné, qui est soit un nombre octal commençant par "0", soit une liste d'instructions séparées par des virgules de la forme [ugoa]*[+-=][rwxst]*. Par exemple, ug=rx,a-rwx.
-file-mode mode
Identique à -dir-mode mais pour tous les fichiers de données réguliers de l'image.
-pad

Ajoute 300 KiB à la fin de l'image ISO produite. Cela contourne d'éventuelles erreurs de lecture des images ISO écrites sur des médias CD en mode TAO. Les octets supplémentaires sont revendiqués comme faisant partie de l'image ISO, sauf si --emul-toc est spécifié.
L'option -pad est activée par défaut.
-no-pad
Désactive le remplissage de 300 KiB à la fin de l'image ISO produite. Ceci est sûr si l'image n'est pas destinée à être gravée sur CD ou si elle est gravée sur CD en tant que seule piste en mode d'écriture SAO.
--old-empty
Utilise l'ancienne méthode pour donner des adresses de bloc dans la plage [0,31] aux fichiers sans contenu de données propre. La nouvelle méthode consiste à avoir un bloc dédié auquel tous ces fichiers pointeront.
Paramètres de conformité aux normes :
-iso-level nombre
Spécifie la version ISO 9660 qui définit les limitations de nommage des fichiers et de taille des fichiers de données. Les restrictions de nommage ne s'appliquent pas aux noms Rock Ridge mais uniquement aux noms ISO 9660 de bas niveau. Il existe trois niveaux de conformité :
Le niveau 1 autorise les noms ISO de forme 8.3 et une taille de fichier jusqu'à 4 Gio - 1.
Le niveau 2 autorise les noms ISO jusqu'à 32 caractères et une taille de fichier jusqu'à 4 Gio - 1.
Le niveau 3 autorise les noms ISO jusqu'à 32 caractères et une taille de fichier jusqu'à 400 Gio - 200 KiB. (Cette limitation de taille est définie par l'implémentation xorriso et non par ISO 9660 qui autoriserait près de 8 Tio.)
Le pseudo-niveau 4 permet la production d'un arbre de répertoires ISO 9660:1999 supplémentaire.
-disallow_dir_id_ext
Ne pas suivre la mauvaise habitude de mkisofs qui autorise les points dans les noms ISO des répertoires. D'un autre côté, certaines images GNU/Linux amorçables dépendent de cette mauvaise habitude.
-U

Cette option autorise les noms de fichiers ISO sans point et jusqu'à 37 caractères, les chemins de fichiers ISO de plus de 255 caractères, et tous les caractères ASCII dans les noms de fichiers. De plus, elle omet le point-virgule et les numéros de version à la fin des noms ISO.
Tout cela viole les spécifications ISO 9660.
-untranslated-filenames
Alias de -U.
-untranslated_name_len nombre
Autorise les noms de fichiers ISO jusqu'au nombre de caractères donné sans aucune conversion de caractères. Le nombre maximum est 96. Si un nom de fichier a plus de caractères, la production de l'image échouera délibérément.
Ceci viole les spécifications ISO 9660.
-allow-lowercase
Autorise les caractères minuscules dans les noms de fichiers ISO.
Ceci viole les spécifications ISO 9660.
-relaxed-filenames
Autorise presque tous les caractères 7 bits dans les noms de fichiers ISO. Ne sont pas autorisés 0x0 et '/'. Si l'option -allow-lowercase n'est pas donnée, les lettres minuscules sont converties en majuscules.
Ceci viole les spécifications ISO 9660.
-d

N'ajoute pas de point final aux noms de fichiers ISO sans point.
Ceci viole les spécifications ISO 9660.
-omit-period
Alias de -d.
-l

Autorise jusqu'à 31 caractères dans les noms de fichiers ISO.
-full-iso9660-filenames
Alias de -l.
-max-iso9660-filenames
Autorise jusqu'à 37 caractères dans les noms de fichiers ISO.
Ceci viole les spécifications ISO 9660.

Paramètres des extensions de normes :
-R

Avec mkisofs, cette option active les extensions Rock Ridge. **xorrisofs** les produit par défaut. Il est fortement déconseillé de les désactiver avec l'option --norock.
-rock

Alias de -R.
-r

Active Rock Ridge et définit l'identifiant utilisateur et groupe de tous les fichiers de l'image ISO à 0. Accorde les permissions r- à tous. Refuse toutes les permissions w-. Si une permission x est définie, accorde la permission x à tous. Supprime les bits s et t.
Ces changements d'attributs restent retardés jusqu'à la fin de l'émulation mkisofs. Dans la même commande d'émulation -as mkisofs, ils peuvent être révoqués par une option ultérieure --norock. Pour des raisons de compatibilité, l'option -R ne révoque pas les changements ordonnés par -r.
-rational-rock
Alias de -r.
--norock

Cette option désactive la production des extensions Rock Ridge pour les objets de fichier ISO 9660. Les capacités multi-sessions de **xorrisofs** dépendent fortement de la fidélité de nommage de Rock Ridge. Il est donc fortement déconseillé de la désactiver avec cette option, sauf pour le cas d'utilisation spécial de révoquer l'effet de -r par :
--norock -R
--set_all_file_dates chaîne_de_temps
Définit mtime, atime et ctime de tous les fichiers et répertoires à l'heure donnée.
Les formats de chaîne_de_temps valides sont : 'Nov 8 14:51:13 CET 2007', 110814512007.13, 2007110814511300. Voir aussi --modification-date= et man xorriso, Exemples de chaînes_de_temps en entrée.
Si la chaîne_de_temps est "set_to_mtime", alors atime et ctime de chaque fichier et répertoire sont définis à la valeur trouvée dans leur mtime.
Ces actions restent retardées jusqu'au début de la production ISO réelle. Jusqu'à lors, elles peuvent être révoquées par --set_all_file_dates avec une chaîne_de_temps vide ou la chaîne_de_temps "default".
Les horodatages du fichier catalogue de démarrage El Torito sont rafraîchis lorsque l'ISO est produite. Ils peuvent être influencés par --modification-date=.
-file_name_limit nombre
Définit la longueur maximale permissible pour les noms de fichiers dans la plage de 64 à 255. Les composants de chemin plus longs que le nombre donné seront tronqués et leurs 33 derniers octets seront écrasés par un deux-points ':' et la représentation hexadécimale du MD5 des 4095 premiers octets du nom entier surdimensionné. Les caractères potentiellement incomplets en UTF-8 verront leurs octets de début remplacés par '_'.
Les noyaux Linux jusqu'à au moins 4.1 représentent mal les noms de longueur 254 et 255. Si vous attendez de tels noms dans ou sous disk_paths et prévoyez de monter l'ISO par de tels noyaux Linux, envisagez de définir -file_name_limit 253.
-D
La norme ECMA-119 exige qu'aucun chemin dans l'image ne contienne plus de 8 composants de nom ou 255 caractères. Par conséquent, il serait nécessaire de déplacer les arbres de répertoires plus profonds vers un répertoire supérieur. Rock Ridge offre une opportunité de faire apparaître ces répertoires déplacés à leur position profonde d'origine, mais cette fonctionnalité peut ne pas être correctement implémentée par les systèmes d'exploitation qui montent l'image.
L'option -D désactive cette relocalisation de répertoires profonds, et viole donc les spécifications ISO 9660.
xorrisofs a -D activé par défaut. S'il est spécifié explicitement, il remplace les options -rr_reloc_dir et -hide-rr-moved.
-disable-deep-relocation
Alias de -D.
-rr_reloc_dir nom
Active la relocalisation des répertoires profonds et évite ainsi les chemins de fichiers ECMA-119 de plus de 8 composants de nom ou 255 caractères. Les répertoires qui mènent à de tels chemins de fichiers seront déplacés vers un répertoire dans le répertoire racine de l'image. Son nom sera défini par cette option. Il est permis d'utiliser le répertoire racine lui-même.
L'arbre de répertoires global apparaîtra profondément réorganisé lorsqu'il sera interprété comme un arbre Rock Ridge. Il apparaîtra réorganisé si seules les informations ECMA-119 sont prises en compte.
Si le répertoire cible de relocalisation donné n'existe pas encore lorsque la production de l'image commence, il sera créé et marqué comme artefact de relocalisation pour Rock Ridge. Au moins sous GNU/Linux, il ne sera pas affiché dans les images Rock Ridge montées.
Le nom ne doit pas contenir de caractère '/' après son premier caractère et il ne doit pas dépasser 255 octets.
Cette option n'a aucun effet si l'option -D est présente.

--md5

Active l'enregistrement des sommes de contrôle MD5 pour l'image ISO globale et pour chaque fichier de données individuel dans l'image. xorriso peut vérifier le contenu d'une image ISO avec ces sommes et émettre une alerte en cas d'inadéquation. -find / -exec get_md5
--hardlinks
Active le chargement et l'enregistrement des relations de liens physiques. Recherche les familles de fichiers iso_rr qui proviennent du même fichier disque, ont un filtrage de contenu identique et ont des propriétés identiques. Les membres de chaque famille reçoivent le même numéro d'inode dans l'image ISO.
Le respect de ces numéros au moment du montage dépend du système d'exploitation. xorriso peut créer des familles de liens physiques lors de l'extraction des fichiers depuis l'image ISO.
--scdbackup_tag disk_path record_name
Ajoute un enregistrement de somme de contrôle scdbackup à l'image. Cela ne fonctionne que si le paramètre next_writeable_address de l'option -C est 0 et que --md5 est activé. -joliet
Alias de -J.
-joliet-long
Autorise 103 caractères dans les noms de fichiers Joliet au lieu de 64, comme le prescrit la spécification. Autorise les chemins Joliet plus longs que la limite prescrite de 240 caractères.
Les noms trop longs sont tronqués. Sans cette option, les chemins trop longs sont exclus de l'arbre Joliet.
-joliet-utf16
Encode les noms de fichiers Joliet en UTF-16BE au lieu de UCS-2. La différence réside dans les caractères qui ne sont pas présents dans UCS-2 et qui sont encodés en UTF-16 par 2 mots de 16 bits chacun. Les deux mots proviennent alors d'un sous-ensemble réservé d'UCS-2.
-hfsplus
Active la production d'un système de fichiers HFS+ supplémentaire à l'intérieur de l'image ISO 9660 et le marque par des entrées Apple Partition Map (APM) dans la zone système, les 32 premiers Kio de l'image.
Cela peut entrer en collision avec des options comme -G ou -isohybrid-mbr qui soumettent des données utilisateur pour inclusion dans la même plage d'adresses. Les 8 premiers octets de la zone système sont écrasés par { 0x45, 0x52, 0x08 0x00, 0xeb, 0x02, 0xff, 0xff } qui peuvent être exécutés comme code machine x86 sans effets négatifs. Donc, si un MBR est combiné avec cette fonctionnalité, ses 8 premiers octets ne devraient contenir aucune commande essentielle.
Les blocs suivants de 2 Kio dans la zone système seront occupés par des entrées APM. Le premier couvre la partie de l'image ISO avant les métadonnées du système de fichiers HFS+. Le second marque la plage des métadonnées HFS+ jusqu'à la fin des données de contenu du fichier. Si d'autres données d'image ISO suivent, une troisième entrée de partition est produite. D'autres fonctionnalités de xorriso peuvent nécessiter plus d'entrées APM.
Soyez conscient que HFS+ est insensible à la casse bien qu'il puisse enregistrer les noms de fichiers avec des lettres majuscules et minuscules. Par conséquent, les noms de fichiers de l'arbre de noms iso_rr peuvent entrer en collision dans l'arbre de noms HFS+. Dans ce cas, ils sont modifiés par l'ajout de caractères de soulignement et de numéros. Dans le cas de noms très longs, il peut être nécessaire de les mapper sur "MANGLED_...".
ATTENTION :
L'implémentation HFS+ dans libisofs a une limite de 125 829 120 octets pour la taille de l'arbre de répertoires global. Cela suffit pour environ 300 000 fichiers de longueur de nom normale. Si la limite est dépassée, un événement d'ÉCHEC sera émis et la production de l'ISO n'aura pas lieu.
-hfsplus-serial-no
Définit une chaîne de 16 chiffres "0" à "9" et de lettres "a" à "f", qui sera utilisée comme numéro de série unique d'un système de fichiers HFS+ émergent.
-hfsplus-block-size number
Définit la taille de bloc d'allocation à utiliser lors de la production des systèmes de fichiers HFS+. Les valeurs autorisées sont 512, 2048 ou 0. Cette dernière option laisse le programme décider.
-apm-block-size number
Définit la taille de bloc à utiliser lors de la description des partitions par une table de partitions Apple (Apple Partition Map). Les valeurs autorisées sont 512, 2048 ou 0. Cette dernière option laisse le programme décider.
Notez que la taille 512 n'est pas compatible avec la production de GPT, et que la taille 2048 ne sera pas montable en tant que -t hfsplus par les anciens noyaux Linux au moins.
-hfsplus-file-creator-type creator type iso_rr_path
Définit les attributs créateur et type HFS+ d'un fichier dans l'image émergente. Ce sont deux codes de 4 caractères chacun.
-hfs-bless-by blessing iso_rr_path
Émet une bénédiction HFS+. Ce sont des rôles qui peuvent être attribués jusqu'à quatre répertoires et un fichier de données :
"ppc_bootdir", "intel_bootfile", "show_folder", "os9_folder", "osx_folder".
Ils peuvent être abrégés en "p", "i", "s", "9", et "x".
Chaque rôle peut être attribué à un seul objet fichier. "intel_bootfile" est celui qui s'applique à un fichier de données. Tous les autres s'appliquent aux répertoires. Aucun objet fichier ne peut porter plus d'une bénédiction.
-hfs-bless disk_path
Émet la bénédiction HFS+ "ppc_bootdir" pour le répertoire qui provient du répertoire disk_path dans l'arborescence du système de fichiers local.
Cela ne fonctionne que s'il y a au moins un fichier de données sous le répertoire. disk_path peut devenir ambigu si des fichiers provenant de différentes sous-arborescences de systèmes de fichiers locaux sont placés dans la même sous-arborescence de l'image ISO. Envisagez d'utiliser -hfs-bless-by "p" pour une adressage non ambigu via iso_rr_path.

Images ISO amorçables El Torito :

La condition préalable à une image ISO amorçable est d'avoir dans l'image ISO les fichiers d'un chargeur de démarrage. Les fonctions de démarrage des ordinateurs sont dirigées vers de tels fichiers, qui exécutent généralement d'autres fichiers programme à partir de l'image ISO. xorrisofs peut produire plusieurs types de blocs de démarrage ou d'enregistrements de démarrage, qui font partie de l'image ISO et sont interprétés par la fonction de démarrage correspondante.

Un enregistrement de démarrage El Torito pointe la facilité d'amorçage vers un catalogue de démarrage contenant une ou plusieurs images de démarrage, qui sont des fichiers programme binaires stockés dans l'image ISO. Le contenu des fichiers d'images de démarrage n'est pas dans le champ d'application d'El Torito.
xorriso compose le catalogue de démarrage selon les fichiers d'images de démarrage donnés et structurés par les options -b, -e, -eltorito-alt-boot et --efi-boot. Souvent, il ne contient qu'une seule entrée.
Normalement, les images de démarrage sont des fichiers de données à l'intérieur du système de fichiers ISO. Par le chemin spécial "--interval:appended_partition_NNN:all::", il est possible de faire référence à une partition ajoutée. Le nombre NNN donne le numéro de partition tel qu'utilisé avec l'option correspondante -append_partition. Par exemple :
-append_partition 2 0xef /tmp/efi.img
-e --interval:appended_partition_2:all::
El Torito est interprété par les fonctions de démarrage PC-BIOS et EFI. La plupart des CD GNU/Linux amorçables sont équipés d'images de démarrage ISOLINUX ou GRUB pour PC-BIOS.
xorrisofs prend en charge les options d'exemple du wiki ISOLINUX, les options utilisées dans le script GRUB grub-mkrescue, et l'exemple du wiki FreeBSD AvgLiveCD.

Pour le démarrage de CD via des fonctions de démarrage autres que PC-BIOS et EFI, et pour le démarrage à partir de clés USB ou de disques durs, voir la section suivante sur la Zone système.

-b chemin_iso_rr
Spécifie le fichier d'image de démarrage qui doit être mentionné dans l'entrée actuelle du catalogue de démarrage El Torito. Il sera marqué comme approprié pour PC-BIOS.
Avec les images de démarrage d'ISOLINUX et de GRUB, cette option doit être accompagnée des options -c, -no-emul-boot, -boot-load-size 4, -boot-info-table.

Toutes les options El Torito suivantes s'appliquent à la nouvelle entrée du catalogue. Jusqu'à 32 entrées de catalogue sont possibles.

Spécifie le fichier d'image de démarrage qui doit être mentionné dans l'entrée actuelle du catalogue de démarrage El Torito. Il sera marqué comme approprié pour EFI.

-eltorito-platform "x86"|"PPC"|"Mac"|"efi"|0xnn|nnn
Définit le numéro d'Identifiant de plateforme pour la prochaine option -b ou -eltorito-boot. Le numéro peut être choisi par un nom de plateforme ou par un nombre compris entre 0 et 255 (0x00 et 0xFF). "x86" = 0 est pour PC-BIOS, "PPC" = 1 pour certains systèmes PowerPC, "Mac" = 2 pour certains systèmes MacIntosh, "efi" = 0xEF pour EFI sur les PC modernes avec CPUs compatibles x86 ou autres.
Si le nouvel identifiant de plateforme diffère du précédent, -eltorito-alt-boot est exécuté.

Définit le nombre de blocs de 512 octets à charger au démarrage à partir de l'image de démarrage dans l'entrée de catalogue actuelle.
Les images de démarrage BIOS non émulées nécessitent généralement une taille de chargement de 4. Néanmoins, le réglage par défaut de mkisofs est d'utiliser la taille complète de l'image de démarrage arrondie à un multiple de 4 blocs de 512 octets. Cette valeur par défaut peut être explicitement appliquée par le mot "full" au lieu d'un nombre.
Les images de démarrage EFI reçoivent généralement le nombre de blocs occupés par le fichier image de démarrage.
El Torito ne peut pas représenter des tailles de chargement supérieures à 65535.
-hard-disk-boot
Marque l'image de démarrage dans l'entrée de catalogue actuelle comme disque dur émulé. (Ne convient à aucun chargeur de démarrage connu.)
-no-emul-boot
Marque l'image de démarrage dans l'entrée de catalogue actuelle comme n'émulant pas de disquette ou de disque dur. (Ceci doit être utilisé avec tous les chargeurs de démarrage connus.)
Si ni -hard-disk-boot ni -no-emul-boot n'est donné, l'image de démarrage sera marquée comme émulant une disquette. (Ne convient à aucun chargeur de démarrage connu.)

Définit la chaîne d'identifiant de la section du catalogue de démarrage où l'image de démarrage sera répertoriée. Si la valeur se compose de 56 caractères [0-9A-Fa-f], elle est convertie en 28 octets, sinon les 28 premiers caractères deviennent la chaîne d'identifiant. La chaîne d'identifiant de la première image de démarrage devient l'identifiant global du catalogue. Elle est limitée à 24 caractères. Les autres chaînes d'identifiant deviennent des identifiants de section.
-eltorito-selcrit chiffres_hex
Définit les Critères de sélection de l'image de démarrage. Jusqu'à 20 octets sont lus à partir des caractères [0-9A-Fa-f] donnés. Ils sont attribués à l'entrée de l'image de démarrage dans le catalogue.
-boot-info-table
Remplace les octets 8 à 63 de l'image de démarrage actuelle. Les informations seront fournies par xorriso lors de la production de l'image : adresse du bloc du descripteur de volume principal, adresse du bloc du fichier image de démarrage, taille du fichier image de démarrage.
--grub2-boot-info

-c chemin_iso_rr
Définit l'adresse du fichier catalogue de démarrage El Torito dans l'image. Cette adresse de fichier n'est pas significative pour le démarrage PC-BIOS ou EFI, mais elle peut être lue ultérieurement par d'autres programmes pour connaître les images de démarrage disponibles.
-eltorito-catalog chemin_iso_rr
Alias de -c.
--boot-catalog-hide
Empêche le catalogue de démarrage El Torito d'apparaître comme fichier dans les arborescences de répertoires de l'image.
Zone système, MBR, GPT, APM, autres blocs de démarrage :

Les 16 premiers blocs d'une image ISO constituent la Zone système. Elle est réservée aux logiciels de démarrage spécifiques au système. Il peut s'agir des fonctions de démarrage et des tables de partitions de architectures matérielles diverses.
Un MBR (Master Boot Record) contient le code de démarrage et une table de partitions. Il est lu par PC-BIOS lors du démarrage depuis une clé USB ou un disque dur, et par PowerPC CHRP ou PReP lors du démarrage. Une partition MBR de type 0xee indique la présence de GPT.
Une GPT (GUID Partition Table) marque les partitions de manière plus moderne. Elle est lue par EFI lors du démarrage depuis une clé USB ou un disque dur, et peut être utilisée pour trouver et monter une partition HFS+ à l'intérieur de l'image ISO.
Une APM (Apple Partition Map) marque la partition HFS+. Elle est lue par les Macs pour le démarrage et le montage.
MBR, GPT et APM sont combinables. APM occupe les 8 premiers octets du code de démarrage MBR. Les trois n'entravent pas le démarrage El Torito depuis un CDROM.
xorrisofs prend en charge des fonctionnalités de démarrage supplémentaires : MIPS Big Endian (SGI), MIPS Little Endian (DEC), SUN SPARC, HP-PA, DEC Alpha. Ceux-ci ne sont pas mutuellement combinables et ne sont pas non plus combinables avec MBR, GPT ou APM.

Plusieurs des options suivantes attendent des chemins de disque en entrée mais acceptent également des chaînes de description pour le lecteur d'intervalles libisofs, qui est capable d'extraire des données à partir de fichiers disque ou -indev et de zérotiser des parties du contenu : -G, -generic-boot, --embedded-boot, --grub2-mbr, -isohybrid-mbr, -efi-boot-part, -prep-boot-part, -B, -sparc-boot, -append_partition.
La chaîne de description se compose des éléments suivants, séparés par deux-points ':'
"--interval:"Flags":"Interval":"Zeroizers":"Source
L'élément "--interval" indique qu'il ne s'agit pas d'un chemin de disque simple mais plutôt d'une chaîne de description de lecteur d'intervalles.
L'élément Flags modifie l'interprétation ultérieure :
"local_fs" demande de lire à partir d'un fichier représenté par le chemin dans Source.
"imported_iso" demande de lire à partir de -indev. Cela fonctionne uniquement si -outdev n'est pas le même que -indev. L'élément Source est ignoré.
"appended_partition_NNN" avec un nombre décimal NNN ne fonctionne que pour les options qui annoncent des chemins d'image de démarrage El Torito : -b, -e, --efi-boot. Le nombre donne le numéro de partition tel qu'utilisé avec l'option correspondante -append_partition.
L'élément Interval se compose de deux nombres d'adresses d'octets séparés par un caractère "-". Par exemple, "0-429" signifie lire les octets 0 à 429.
L'élément Zeroizers se compose d'une ou plusieurs chaînes séparées par des virgules. Elles définissent quelle partie des données lues doit être zérotisée. L'octet numéro 0 signifie l'octet lu à partir de l'adresse de départ de l'Interval. Chaque chaîne peut être l'une des suivantes :
"zero_mbrpt" demande de zérotiser la table de partitions MBR si les octets 510 et 511 portent la signature MBR 0x55 0xaa.
"zero_gpt" demande de vérifier un en-tête GPT dans les octets 512 à 1023, de le zérotiser ainsi que ses blocs de table de partitions.
"zero_apm" demande de vérifier le bloc 0 APM et de zérotiser ses blocs de table de partitions.
Start_byte"-"End_byte demande de zérotiser les octets lus commençant par le numéro Start_byte et se terminant après End_byte.
L'élément Source est le chemin du fichier avec le drapeau "local_fs", et ignoré avec le drapeau "imported_iso".
Les numéros d'octets peuvent être mis à l'échelle par un suffixe parmi {k,m,g,t,s,d} signifiant une multiplication par {1024, 1024k, 1024m, 1024g, 2048, 512}. Une valeur mise à l'échelle, un nombre de fin représente le dernier octet de la plage mise à l'échelle.
Par exemple, "0d-0d" est "0-511".
Exemples :
"local_fs:0-32767:zero_mbrpt,zero_gpt,440-443:/tmp/template.iso"
"imported_iso:45056d-47103d::"

-G disk_path
Copie au maximum 32768 octets du fichier disque donné au tout début de l'image ISO.
Contrairement à une image de démarrage El Torito, le fichier disk_path n'a pas besoin d'être ajouté à l'image ISO. Il n'apparaîtra pas en tant que fichier dans les arborescences de répertoires.
Dans les situations multi-sessions, le chemin de disque spécial "." empêche la lecture d'un fichier disque mais provoque néanmoins les ajustements dans le MBR existant, qui ont été ordonnés par d'autres options.
-generic-boot disk_path
Alias de -G.
--embedded-boot disk_path
Alias de -G.
--grub2-mbr disk_path
Installe disk_path dans la zone système et le traite comme un MBR GRUB2 moderne. L'adresse de début du contenu de la première image de démarrage est convertie en un compte de blocs de 512 octets, et un décalage de 4 est ajouté. Le résultat est écrit sous forme d'un nombre de 64 bits little-endian à l'adresse d'octet 0x1b0.
-isohybrid-mbr disk_path
Installe disk_path comme MBR isohybrid ISOLINUX qui rend l'image de démarrage fournie par l'option -b amorçable depuis des clés USB et des disques durs via PC-BIOS. Cette préparation est normalement effectuée par le programme isohybrid de SYSLINUX sur l'image ISO déjà produite.
Le chemin du disque doit mener à l'un des fichiers Syslinux isohdp[fp]x*.bin. Le MBR est patché selon les besoins d'isohybrid. La première partition décrit la plage de l'image ISO. Son début est au bloc 0 par défaut, mais peut être défini à 64 blocs disque par l'option -partition_offset 16.
Pour la signification du chemin de disque spécial ".", voir l'option -G.
-isohybrid-gpt-basdat
Marque l'image de démarrage El Torito actuelle (voir les options -b et -e) dans une GPT actuellement invalide comme partition de type Basic Data. Cela ne fonctionne qu'avec -isohybrid-mbr et a le même impact sur la zone système que -efi-boot-part. Il ne peut pas être combiné avec -efi-boot-part ou -hfsplus.
Les trois premières images de démarrage qui sont marquées par GPT apparaîtront également comme entrées de partition dans le MBR. La partition MBR de type 0xEF est ce qui est réellement utilisé par le firmware EFI pour démarrer depuis une clé USB. La partition MBR pour PC-BIOS obtient le type 0x00 plutôt que 0x17 dans ce cas. Souvent, les entrées MBR supplémentaires sont celles qui sont réellement utilisées par EFI.
-isohybrid-gpt-hfsplus
Marque l'image de démarrage El Torito actuelle (voir les options -b et -e) dans la GPT comme partition de type HFS+. L'impact et les restrictions sont les mêmes qu'avec -isohybrid-gpt-basdat.
-isohybrid-apm-hfsplus
Marque l'image de démarrage El Torito actuelle (voir les options -b et -e) dans la carte de partition Apple comme partition de type HFS+. Cela ne fonctionne qu'avec -isohybrid-mbr et a un impact similaire sur la zone système que -hfsplus. Il ne peut pas être combiné avec -efi-boot-part ou -hfsplus.
Le fichier MBR isohybrid ISOLINUX doit commencer par un motif connu de 32 octets de code machine x86 qui ne fait essentiellement rien. Il sera écrasé par 32 octets d'un faux en-tête APM.
-part_like_isohybrid
Contrôle si -isohybrid-gpt-basdat, -isohybrid-gpt-hfsplus et -isohybrid-apm-hfsplus s'appliquent même si -isohybrid-mbr n'est pas présent. Aucun MBR de partition de type 0xee n'apparaît, même si une GPT est produite. Les espaces entre les partitions GPT et APM ne seront pas remplis par d'autres partitions. Les partitions ajoutées seront mentionnées dans APM si d'autres partitions APM apparaissent.
-iso_mbr_part_type "default"|number|type_guid
Définit le type de partition du MBR ou de la partition GPT qui représente l'ISO ou la protège au moins.
Le nombre peut être de 0x00 à 0xff. Le texte "default" réactive les types par défaut des différentes occasions de création d'une partition ISO MBR. Cela n'a aucun effet si aucune partition de ce type n'émerge par d'autres paramètres ou si le type de partition est prescrit obligatoirement comme 0xee pour MBR protecteur GPT ou 0x96 pour CHRP.
Si au lieu de cela un type_guid est donné par une chaîne hexadécimale de 32 chiffres comme a2a0d0ebe5b9334487c068b6b72699c7 ou par un texte structuré comme EBD0A0A2-B9E5-4433-87C0-68B6B72699C7, alors il sera utilisé comme type de partition si le système de fichiers ISO apparaît comme partition dans GPT. Dans MBR, C12A7328-F81F-11D2-BA4B-00A0C93EC93B sera mappé à 0xef. Tout autre GUID sera mappé à 0x83.
--protective-msdos-label
Patch la zone système avec une simple table de partitions PC-DOS où la partition 1 revendique la plage de l'image ISO mais laisse le premier bloc non revendiqué. Ceci est mutuellement exclusif avec l'option -isohybrid-mbr.
--mbr-force-bootable
Force une partition MBR avec le drapeau "bootable/active" si des options comme --protective-msdos-label ou --grub2-mbr sont données. Ces options entraînent normalement la définition du drapeau s'il existe une partition MBR d'un type autre que 0xee ou 0xef. S'il n'existe aucune partition de ce type, alors aucun drapeau de démarrage n'est défini, à moins que --mbr-force-bootable ne force la création d'une partition factice de type 0x00 qui ne couvre que le premier bloc de l'image ISO.
Si aucun MBR amorçable n'est indiqué par d'autres options et qu'une partition est créée par -append_partition, alors --mbr-force-bootable entraîne un drapeau de démarrage comme le ferait par exemple --protective-msdos-label.
--gpt-iso-bootable
Définit le bit 2 des drapeaux de partition GPT pour la partition ISO 9660 si une telle partition GPT émerge. Ce bit est spécifié comme "Legacy BIOS bootable" mais sa signification réelle est incertaine. Certains BIOS compatibles GPT pourraient vouloir le voir dans une partition.
--gpt-iso-not-ro
Ne définit pas le bit 60 des drapeaux de partition GPT pour la partition ISO 9660 si une telle partition GPT émerge. Ce bit est spécifié comme "Read-only" et est donc approprié. Mais il est inhabituel dans les partitions de disque GPT.
La valeur de décalage d'une image ISO est préservée lorsqu'une nouvelle session est ajoutée à une image chargée. La valeur définie ici n'est donc effective que si une nouvelle image ISO est écrite.
-partition_hd_cyl number
Définit le nombre de têtes par cylindre pour la table de partitions MBR. 0 choisit un
default. Le maximum est de 255.
-partition_sec_hd nombre
Définit le nombre de secteurs par tête pour la table de partition MBR. 0 choisit une valeur par défaut. Le maximum est 63.
Le produit partition_sec_hd * partition_hd_cyl * 512 est la taille du cylindre. Il doit être divisible par 2048 pour permettre un alignement exact. Avec des partitions ajoutées et -appended_part_as_gpt, il n'y a pas de limite au nombre de cylindres. Sinon, il ne peut y en avoir que 1024 au maximum. Si la taille du cylindre est trop petite pour rester en dessous de la limite, des valeurs appropriées de partition_hd_cyl sont choisies avec partition_sec_hd 32 ou 63. Si l'image est plus grande que 8 422 686 720 octets, les contraintes de taille de cylindre ne peuvent pas être satisfaites pour MBR. Elles ne semblent pas excessivement importantes de toute façon. Les adresses de blocs plates dans les tables de partition sont bonnes pour 1 Tio.
-partition_cyl_align mode
Contrôle l'alignement de la taille de l'image sur un nombre entier de cylindres. Il est prescrit par les spécifications isohybrid et semble satisfaire le programme fdisk. La taille du cylindre doit être divisible par 2048. Les images de plus de 8 323 596 288 octets ne peuvent pas être alignées dans la table de partition MBR.
Le mode "auto" est par défaut. Le remplissage pour l'alignement ne se produit que si l'option -isohybrid-mbr est donnée.
Le mode "on" provoque l'alignement par remplissage avec l'option --protective-msdos-label également. Le mode "all" est comme "on" mais remplit également les partitions de -append_partition à une taille alignée.
Le mode "off" désactive l'alignement de manière inconditionnelle.
-append_partition numéro_partition type_code chemin_disque
Provoque l'ajout d'une image de système de fichiers préparée à l'image ISO et sa description par une entrée de table de partition dans un bloc de démarrage au début de l'image ISO émergente. L'entrée de partition portera la taille du fichier soumis arrondie au multiple de 2048 octets supérieur ou au multiple de la taille du cylindre supérieur.
Attention aux exécutions multisessions ultérieures. La partition ajoutée sera écrasée.
numéro_partition peut être de 1 à 4. Le numéro 1 placera toute l'image ISO dans l'espace non réclamé avant la partition 1. Ainsi, avec la plupart des fonctionnalités MBR ou GPT de xorriso, le numéro 2 serait le choix le plus naturel.
Le type_code peut être "FAT12", "FAT16", "Linux", ou un nombre hexadécimal entre 0x00 et 0xff. Tous ces nombres ne donneront pas des résultats utilisables. Pour une liste de codes, recherchez sur Internet "Partition Types" ou exécutez la commande fdisk "L". Si la partition apparaît dans GPT, le type_code 0xef est mappé au GUID de type de partition du système EFI. Tous les autres sont mappés au GUID de type de données de base.
type_code peut également être un GUID de type sous forme de chaîne hexadécimale brute comme a2a0d0ebe5b9334487c068b6b72699c7 ou sous forme de texte structuré comme EBD0A0A2-B9E5-4433-87C0-68B6B72699C7. Il sera utilisé si la partition est mentionnée dans GPT. En MBR, C12A7328-F81F-11D2-BA4B-00A0C93EC93B sera mappé à 0xef. Tout autre GUID sera mappé à 0x83. En APM, 48465300-0000-11AA-AA11-00306543ECAC sera mappé au type de partition "Apple_HFS", tout autre à "Data".
Si une autre commande provoque la production de GPT, les partitions ajoutées y seront également mentionnées, même si -appended_part_as_gpt n'est pas donné.
-appended_part_as_gpt
Marque les partitions de -append_partition dans GPT plutôt que dans MBR. Dans ce cas, MBR affiche une seule partition de type 0xee qui couvre toutes les données de sortie.
Par défaut, les partitions ajoutées ne sont marquées dans GPT que si GPT est produit en raison d'autres options.
-appended_part_as_apm
Marque également les partitions de -append_partition dans la carte de partition Apple (APM).
Par défaut, les partitions ajoutées ne sont marquées dans APM que si APM est produit en raison d'autres options et que -part_like_isohybrid est activé.
-efi-boot-part chemin_disque
Copie un fichier du disque dans l'image ISO émergente et le marque par une entrée GPT comme partition système EFI. Le firmware de démarrage EFI est censé utiliser une image de système de fichiers FAT dans une telle partition pour démarrer depuis une clé USB ou un disque dur.
Au lieu d'un chemin_disque, le mot --efi-boot-image peut être donné. Il expose dans GPT le contenu de la première image de démarrage EFI El Torito comme partition système EFI. Les images de démarrage EFI sont introduites par les options -e ou --efi-boot. L'image de démarrage EFI affectée ne peut pas apparaître dans HFS+ car elle est stockée en dehors de la partition HFS+.
--gpt_disk_guid valeur
Contrôle si une GPT émergente obtiendra un GUID de disque généré aléatoirement ou si le GUID est fourni par l'utilisateur. La valeur "random" est par défaut. La valeur "modification-date" produit un GUID de faible qualité à partir de la valeur définie par l'option --modification-date=.
Une chaîne de 32 chiffres hexadécimaux, ou une chaîne GUID conforme à la RFC 4122 peut être utilisée pour définir directement le GUID du disque. UEFI prescrit que les trois premiers composants d'une chaîne GUID RFC 4122 soient échangés en octets dans la représentation binaire :
Par exemple, --gpt_disk_guid 2303cd2a-73c7-424a-a298-25632da7f446 équivaut à --gpt_disk_guid 2acd0323c7734a42a29825632da7f446
Les GUID de partition sont générés en variant minimalement le GUID du disque.
-chrp-boot-part
Marque la plage de blocs de toute l'image ISO émergente comme partition MBR de type 0x96. Ceci n'est pas compatible avec toute autre fonctionnalité qui produit des entrées de partition MBR. Cela rend GPT méconnaissable.
CHRP est souvent utilisé conjointement avec HFS. Il n'a pas encore été testé si les systèmes de fichiers HFS+ produits avec l'option -hfsplus démarreraient sur une machine compatible CHRP qui ne démarre pas uniquement en ISO 9660.
-chrp-boot
Alias de -chrp-boot-part.
-prep-boot-part chemin_disque
Copie un fichier du disque dans l'image ISO émergente et le marque par une entrée de partition MBR de type 0x41. Le firmware de démarrage PReP est censé lire le contenu de la partition comme un seul fichier exécutable ELF. Cette option est compatible avec d'autres partitions MBR et avec GPT.
-mips-boot iso_rr_path
Déclare un fichier de données dans l'image comme un fichier de démarrage MIPS Big Endian et provoque la production d'un en-tête de volume MIPS Big Endian. Ceci est mutuellement exclusif avec la production d'autres blocs de démarrage comme MBR. Il écrasera les 512 premiers octets de toute donnée fournie par -G. Jusqu'à 15 fichiers de démarrage peuvent être déclarés par plusieurs options -mips-boot.
-mipsel-boot iso_rr_path
Déclare un fichier de données dans l'image comme fichier de démarrage MIPS Little Endian. Ceci est mutuellement exclusif avec d'autres blocs de démarrage. Il écrasera les 512 premiers octets de toute donnée fournie par -G. Un seul fichier de démarrage peut être déclaré par -mipsel-boot.
-B chemin_disque[,chemin_disque ...]
Provoque l'écriture d'un ou plusieurs fichiers de données sur le disque après la fin de l'image ISO. Une étiquette de disque SUN sera écrite dans les 512 premiers octets de l'image ISO, qui liste cette image comme partition 1 et les chemins_disque donnés comme partitions 2 à 8.
Les fichiers disque devraient contenir des images de démarrage appropriées pour les systèmes SUN SPARC.
Le chemin_disque pseudo "..." provoque la copie de toutes les entrées de partition vides de la dernière entrée non vide. Si aucun autre chemin_disque n'est donné avant "..." alors toutes les partitions décrivent l'image ISO. Dans ce cas, le code du chargeur de démarrage doit être importé par l'option -G.
-sparc-boot chemin_disque[,chemin_disque ...]
Alias de -B.
-sparc-label texte
Définit le texte de l'étiquette ASCII d'une étiquette de disque SUN.
--grub2-sparc-core iso_rr_path
Provoque l'écriture de l'adresse et de la taille du contenu du fichier de données donné dans l'image après l'étiquette de disque SUN. Ces deux nombres sont comptés en octets. L'adresse est écrite comme un nombre de 64 bits big-endian à l'octet 0x228. La taille est écrite comme un nombre de 32 bits big-endian à l'octet 0x230.
-hppa-cmdline texte
Définit la ligne de commande PALO pour HP-PA. Jusqu'à 1023 caractères sont autorisés par défaut. Avec -hppa-hdrversion 4, la limite est de 127.
Notez que les cinq premières options -hppa sont obligatoires si l'une des options -hppa est donnée. Seule l'option -hppa-hdrversion est autorisée à être absente.
-hppa-bootloader iso_rr_path
Désigne le chemin donné comme fichier de chargeur de démarrage HP-PA.
-hppa-kernel-32 iso_rr_path
Désigne le chemin donné comme fichier noyau HP-PA 32 bits.
-hppa-kernel-64 iso_rr_path
Désigne le chemin donné comme fichier noyau HP-PA 64 bits.
-hppa-ramdisk iso_rr_path
Désigne le chemin donné comme fichier disque RAM HP-PA.
-hppa-hdrversion nombre
Choisit entre la version d'en-tête PALO 5 (par défaut) et la version 4. Pour la valeur appropriée, consultez le code source de PALO : PALOHDRVERSION.
-alpha-boot iso_rr_path
Déclare un fichier de données dans l'image comme chargeur de démarrage secondaire DEC Alpha SRM et provoque la production d'un secteur de démarrage qui y pointe. Ceci est mutuellement exclusif avec la production d'autres blocs de démarrage comme MBR.
Jeux de caractères :

Les jeux de caractères ne devraient pas avoir d'importance tant que seuls des caractères alphanumériques anglais sont utilisés pour les noms de fichiers ou tant que tous les auteurs et lecteurs du support utilisent le même jeu de caractères. En dehors de ces contraintes, il peut être nécessaire de laisser xorriso convertir les codes d'octets.
Une conversion du jeu de caractères d'entrée vers le jeu de caractères de sortie est effectuée lorsqu'une image ISO est écrite. Inversement, il y a une conversion du jeu de caractères de sortie vers le jeu de caractères d'entrée lorsqu'une image ISO est chargée. Les ensembles peuvent être définis. par les options -input-charset et -output-charset, si nécessaire.

-input-charset nom_jeu_caractères
Définit le jeu de caractères à partir duquel convertir les noms de fichiers sur disque lors de leur insertion dans l'image ISO.
-output-charset nom_jeu_caractères
Définit le jeu de caractères à partir duquel convertir les noms des images ISO chargées et vers lequel convertir les noms lors de l'écriture des images ISO.
Extraction de modèle Jigdo :

Extrait de man genisoimage : « Jigdo est un outil pour aider à la distribution de gros fichiers comme les images de CD et DVD ; voir http://atterer.net/jigdo/ pour plus de détails. Les images ISO des CD et DVD Debian sont publiées sur le web au format jigdo pour permettre aux utilisateurs finaux de les télécharger plus efficacement. »
Si l'utilisation de libjte a été activée lors de la compilation de xorriso, alors xorrisofs peut produire un fichier .jigdo et un fichier .template avec une image ISO en une seule session. Sinon, les options Jigdo provoqueront un événement FAILURE, qui conduit normalement à l'abandon du programme.
On peut déterminer la capacité Jigdo par :
$ xorrisofs -version 2>&1 | grep '^libjte' && echo OUI

Le fichier .jigdo contient des sommes de contrôle et des adresses de fichiers symboliques. Le fichier .template contient l'image ISO compressée avec des balises de référence au lieu des octets de contenu des fichiers listés.
L'entrée pour ce processus sont les arguments normaux pour une session xorrisofs sans image chargée, et un fichier de sommes de contrôle qui liste les fichiers de données qui peuvent être listés dans le fichier .jigdo et référencés extérieurement dans le fichier .template. Chaque fichier désigné est représenté dans le fichier de sommes de contrôle par une seule ligne de texte :
Somme de contrôle en chiffres hexadécimaux, 2 espaces, taille en 12 chiffres décimaux ou espaces, 2 espaces, adresse symbolique du fichier
Le type de somme de contrôle est choisi par -jigdo « checksum_algorithm » avec les valeurs « md5 » (32 chiffres hexadécimaux) ou « sha256 » (64 chiffres hexadécimaux). Il sera également utilisé pour les lignes d'adresses de fichiers dans le fichier .jigdo.
La valeur par défaut est « md5 ».
L'adresse du fichier dans une ligne du fichier de sommes de contrôle doit avoir le même nom de base que le chemin_disque du fichier auquel elle doit correspondre. Le chemin du répertoire de l'adresse du fichier est décisif pour le mappage To=From, pas pour la reconnaissance du fichier. Après le mappage To=From, l'adresse du fichier est écrite dans le fichier .jigdo. Les outils de restauration Jigdo convertiront ces adresses en adresses de sources de données réellement accessibles à partir desquelles ils peuvent lire.
Si la liste des paramètres jigdo n'est pas vide, le remplissage sera compté comme faisant partie de l'image ISO.

-jigdo-checksum-algorithm « md5 »|« sha256 »
Définit l'algorithme de somme de contrôle qui doit être utilisé pour les entrées de fichiers de données dans le fichier .jigdo et qui est attendu dans le fichier de sommes de contrôle. La valeur par défaut est « md5 ».
-jigdo-jigdo chemin_disque
Définit le chemin_disque pour le fichier .jigdo avec les sommes de contrôle et les adresses de téléchargement pour remplir les trous dans .template.
-jigdo-template chemin_disque
Définit le chemin_disque pour le fichier .template avec la copie de l'image ISO compressée et trouée.
-jigdo-min-file-size taille
Définit la taille minimale pour qu'un fichier de données soit listé dans le fichier .jigdo et soit un trou dans le fichier .template. La taille peut être un simple nombre comptant les octets, ou un nombre avec la lettre « k », « m », « g » ajoutée pour compter les KiB (1024 octets), MiB (1024 KiB), ou GiB (1024 MiB).
-jigdo-force-checksum motif_chemin_disque
Ajoute un motif d'expression régulière qui sera comparé au chemin_disque absolu de tout fichier de données qui n'a pas été trouvé dans le fichier de sommes de contrôle. Une correspondance provoque un événement MISHAP, qui n'interrompt normalement pas l'exécution du programme mais entraîne finalement une valeur de sortie non nulle du programme.
-jigdo-force-md5 motif_chemin_disque
Alias obsolète de -jigdo-force-checksum.
-jigdo-exclude motif_chemin_disque
Ajoute un motif d'expression régulière qui sera comparé au chemin_disque absolu de tout fichier de données. Une correspondance provoque le fait que le fichier reste dans .template dans tous les cas.
-jigdo-map Vers=Depuis
Ajoute une paire de chaînes de la forme Vers=Depuis à la liste des paramètres. Si un fichier de données est listé dans le fichier .jigdo, il est référencé par l'adresse du fichier de sa ligne dans le fichier de sommes de contrôle. Cette adresse de fichier est vérifiée pour voir si elle commence par la chaîne Depuis. Si c'est le cas, cette chaîne sera remplacée par la chaîne Vers et un caractère « : », avant d'entrer dans le fichier .jigdo. La chaîne Depuis doit se terminer par un caractère '/'.
-checksum-list chemin_disque
Définit le chemin_disque où trouver le fichier de sommes de contrôle avec les adresses de fichiers symboliques et les sommes de contrôle conformément à -jigdo-checksum-algorithm.
-md5-list chemin_disque
Alias obsolète de -checksum-list.
-jigdo-template-compress « gzip »|« bzip2 »
Choisit entre « bzip2 » ou « gzip » pour la compression du fichier modèle. Le fichier jigdo est sorti non compressé.
-checksum_algorithm_iso liste_de_noms
Choisit un ou plusieurs parmi « md5 », « sha1 », « sha256 », « sha512 » pour les sommes de contrôle auxiliaires « # Image Hex » dans le fichier .jigdo. La liste_de_noms peut par exemple ressembler à « md5,sha1,sha512 ». La valeur « all » choisit tous les algorithmes disponibles. Notez que MD5 reste toujours activé.
-checksum_algorithm_template liste_de_noms
Choisit les algorithmes pour les sommes de contrôle « # Template Hex » dans le fichier .jigdo. Les règles pour liste_de_noms sont les mêmes qu'avec -checksum_algorithm_iso.

Une exécution simple de production d'image

Un arbre de fichiers préparé dans le répertoire ./for_iso est copié dans le répertoire racine de l'image ISO. Les permissions des fichiers sont définies sur lecture seule pour tout le monde. Les attributs Joliet pour les systèmes Microsoft sont ajoutés. L'image résultante est écrite en tant que fichier de données ./image.iso sur le disque.
$ xorrisofs -r -J -o ./image.iso ./for_iso

Définir les chemins de l'image ISO par -graft-points

Sans l'option -graft-points, chaque fichier disque donné est copié dans le répertoire racine de l'image ISO, en conservant son nom. Si un répertoire est donné, ses fichiers et sous-répertoires sont copiés dans le répertoire racine, en conservant leurs noms.
$ xorrisofs ... /home/me/datafile /tmp/directory
donne dans le répertoire racine de l'image ISO :
/datafile
/fichier_1_du_directory
...
/fichier_N_du_directory

Avec l'option -graft-points, il est possible de placer des fichiers et des répertoires à des chemins arbitraires dans l'image ISO.
$ xorrisofs ... -graft-points /home/me/datafile /dir=/tmp/directory
donne dans le répertoire racine de l'image ISO

y:
/datafile
/dir
Les répertoires parents nécessaires à terme dans l'image seront créés automatiquement :
/datafiles/file1=/home/me/datafile
donne dans l'image ISO :
/datafiles/file1
Les attributs du répertoire /datafiles sont copiés depuis /home/me sur le disque.

Normalement, il faut éviter les caractères = et \ dans la partie ISO d'un spécificateur de chemin. Mais si c'est nécessaire, on peut les échapper :
/with_\=_and_\\/file=/tmp/directory/file
donne dans l'image ISO :
/with_=_and_\/file

Effectuer des exécutions multi-sessions

Cet exemple fonctionne uniquement pour les médias multi-sessions : CD-R[W], DVD-R[W], DVD+R, BD-R. Ajoutez l'option cdrskin --grow_overwriteable_iso à toutes les exécutions -as cdrecord afin d'activer l'émulation multi-session sur les médias réinscriptibles.
La première session est écrite comme suit :
$ xorrisofs -graft-points \
/tree1=prepared_for_iso/tree1 \
| xorriso -as cdrecord -v dev=/dev/sr0 blank=fast -multi -eject -
Les sessions suivantes sont écrites comme suit (l'exécution de dd sert uniquement à laisser aux démons une chance de la perturber) :
$ m=$(xorriso -as cdrecord dev=/dev/sr0 -msinfo)
$ dd if=/dev/sr0 count=1 >/dev/null 2>&1
$ xorrisofs -M /dev/sr0 -C $m -graft-points \
/tree2=prepared_for_iso/tree2 \
| xorriso -as cdrecord -v dev=/dev/sr0 -waiti -multi -eject -
Toujours éjecter le tiroir du lecteur entre les sessions.
L'exécution de xorriso -as mkisofs lira les anciennes sessions via le pilote CD-ROM de /dev/sr0. Ce pilote peut ne pas être conscient du contenu modifié tant que le média n'est pas rechargé. Dans ce cas, la session précédente ne serait pas correctement évaluée par xorriso et la nouvelle session ne contiendrait que les fichiers nouvellement ajoutés.
Certains systèmes manquent de patience avec le chargement automatique du tiroir et certains démons peuvent interférer avec une première tentative de lecture du pilote CD-ROM depuis un média fraîchement chargé.
Lors du chargement manuel du tiroir, attendez 10 secondes après que le lecteur ait arrêté de clignoter.
Une méthode automatique sûre semble être une exécution séparée de xorriso pour charger le tiroir avec une attente appropriée, et une exécution suivante de dd qui devrait offrir une opportunité à tout problème causé par des démons évaluant le statut modifié du lecteur. Si cela ne fonctionne pas, insérez une exécution de "sleep 10" entre xorriso et dd.

Laisser xorrisofs travailler sous growisofs

growisofs attend un programme de formatage ISO qui comprend les options -C et -M. Une variable est définie pour remplacer le nom par défaut codé en dur.
$ export MKISOFS="xorrisofs"
$ growisofs -Z /dev/dvd /some/files
$ growisofs -M /dev/dvd /more/files
Si aucun "xorrisofs" n'est disponible sur votre système, vous devrez créer un lien symbolique pointant vers le binaire xorriso et indiquer à growisofs de l'utiliser. Par exemple :
$ ln -s $(which xorriso) "$HOME/xorrisofs"
$ export MKISOFS="$HOME/xorrisofs"
On peut quitter l'émulation mkisofs par l'argument "--" et utiliser toutes les commandes xorriso. growisofs n'aime pas les options qui commencent par "-o", mais -outdev doit être défini sur "-". Utilisez donc "outdev" à la place :
$ growisofs -Z /dev/dvd --for_backup -- \
outdev - -update_r /my/files /files
$ growisofs -M /dev/dvd --for_backup -- \
outdev - -update_r /my/files /files
Notez que --for_backup est donné dans l'émulation mkisofs. Pour préserver les données supplémentaires enregistrées, il doit déjà être en vigueur lorsque l'émulation charge l'image.

Sauvegarde incrémentielle de quelques arbres de répertoires

Cela modifie les arbres de répertoires /open_source_project et /personal_mail dans l'image ISO pour qu'ils deviennent des copies exactes de leurs homologues sur disque. Des objets de fichiers ISO sont créés, supprimés ou leurs attributs sont ajustés en conséquence.
Les ACL, xattrs, liens matériels et sommes de contrôle MD5 seront enregistrés. On s'attend à ce que les numéros d'inode dans le système de fichiers disque soient persistants sur les cycles de montage et de redémarrage. Les fichiers dont le nom correspond à *.o ou *.swp sont explicitement exclus.

À utiliser plusieurs fois sur le même média, chaque fois qu'une mise à jour des deux arbres de disque vers le média est souhaitée. Commencez avec un média vierge et mettez-le à jour jusqu'à ce que l'exécution échoue gracieusement en raison d'un manque d'espace restant sur l'ancien.
Toujours éjecter le tiroir du lecteur entre les sessions. Une exécution de dd devrait permettre aux démons de perturber la première lecture sur un média fraîchement chargé.
$ msinfo=$(xorriso -as cdrecord dev=/dev/sr0 -msinfo)
$ dd if=/dev/sr0 count=1 >/dev/null 2>&1
$ load_opts=
$ test -n "$msinfo" && load_opts="-M /dev/sr0 -C $msinfo"
$ xorrisofs $load_opts -o - --for_backup -m '*.o' -m '*.swp' \
-V PROJ_MAIL_"$(date '+%Y_%m_%d_%H%M%S')" -graft-points \
-old-root / \
/projects=/home/thomas/projects \
/personal_mail=/home/thomas/personal_mail \
| xorriso -as cdrecord dev=/dev/sr0 -v -multi -waiti -eject -

Cela est logique si la sauvegarde complète laisse une capacité restante substantielle sur le média et si les modifications attendues sont beaucoup plus petites que la sauvegarde complète.

Mieux vaut ne pas utiliser votre sauvegarde la plus récente pour -old-root. Avoir au moins deux médias que vous utilisez en alternance. Ainsi, seules les sauvegardes plus anciennes sont mises en danger par la nouvelle opération d'écriture, tandis que la sauvegarde la plus récente est stockée en toute sécurité sur un autre média.
Toujours avoir un média vierge prêt pour effectuer une sauvegarde complète au cas où la tentative de mise à jour échouerait en raison d'une capacité restante insuffisante. Cette défaillance ne gâchera pas l'ancien média, bien sûr.

Si les numéros d'inode sur disque ne sont pas persistants, utilisez l'option --old-root-no-ino. Dans ce cas, une exécution de mise à jour comparera les sommes MD5 enregistrées au contenu actuel du fichier sur le disque dur.

Avec l'option de montage -o "sbsector=" sur GNU/Linux ou -s sur FreeBSD ou NetBSD, il est possible d'accéder aux arbres de session qui représentent les anciennes versions de sauvegarde. Avec les médias CD, mount GNU/Linux accepte directement les numéros de session par son option "session=".
Les médias multi-sessions et la plupart des médias réinscriptibles écrits par xorriso peuvent indiquer les sbsectors de leurs sessions par l'option xorriso -toc :
$ xorriso -dev /dev/sr0 -toc
xorriso peut imprimer la commande de montage correspondante pour un numéro de session :
$ xorriso -mount_cmd /dev/sr0 session 12 /mnt
ou pour un ID de volume qui correspond à une expression de recherche :
$ xorriso -mount_cmd /dev/sr0 volid '*2008_12_05*' /mnt
Les deux produisent sur la sortie standard quelque chose comme :
mount -t iso9660 -o nodev,noexec,nosuid,ro,sbsector=1460256 '/dev/sr0' '/mnt'
Le superutilisateur peut laisser xorriso exécuter la commande de montage directement :
# osirrox -mount /dev/sr0 "volid" '*2008_12_05*' /mnt

Sauvegarde incrémentielle avec arbres accumulés

Solaris n'offre pas l'option de monter d'anciennes sessions. Afin de les maintenir accessibles, on peut mapper tous les fichiers vers un arbre de fichiers sous un répertoire de session et accumuler ces répertoires de session en session. L'arbre -root est cloné à partir de l'arbre -old-root avant d'être comparé aux arbres appropriés sur le disque.
Cela exige de connaître le nom du répertoire de session précédemment utilisé.
Avec la première session :
$ xorrisofs -root /session1 \
-o - --for_backup -m '*.o' -m '*.swp' \
-V PROJ_MAIL_"$(date '+%Y_%m_%d_%H%M%S')" -graft-points \
/projects=/home/thomas/projects \
/personal_mail=/home/thomas/personal_mail \
| xorriso -as cdrecord dev=/dev/sr0 -v blank=as_needed \
-multi -waiti -eject -

Avec la deuxième session, l'option -old-root fait référence à /session1 et le nouveau -root est /session2.
Toujours éjecter le tiroir du lecteur entre les sessions. Une exécution de dd devrait permettre aux démons de perturber la première lecture sur un média fraîchement chargé.
$ msinfo=$(xorriso -as cdrecord dev=/dev/sr0 -msinfo)
$ dd if=/dev/sr0 count=1 >/dev/null 2>&1
$ load_opts=
$ test -n "$msinfo" && load_opts="-M /dev/sr0 -C $msinfo"
$ xorrisofs $load_opts -root /session2 -old-root /session1 \
-o - --for_backup -m '*.o' -m '*.swp' \
-V PROJ_MAIL_"$(date '+%Y_%m_%d_%H%M%S')" -graft-points \
/projects=/home/thomas/projects \
/personal_mail=/home/thomas/personal_mail \
| xorriso -as cdrecord dev=/dev/sr0 -v -multi -waiti -eject -
Avec la troisième session, l'option -old-root fait référence à /session2. Le nouveau -root est /session3. Et ainsi de suite.

Créer des images amorçables pour PC-BIOS et EFI

La suite de chargeurs d'amorçage SYSLINUX/ISOLINUX est populaire pour amorcer le PC-BIOS. Le wiki ISOLINUX prescrit de créer sur disque un répertoire ./CD_root et de copier tous les fichiers désirés sous ce répertoire. En particulier, le fichier isolinux.bin doit être copié dans ./CD_root/isolinux/isolinux.bin. C'est le fichier image d'amorçage.
Les options mkisofs prescrites peuvent être utilisées inchangées avec xorrisofs :
$ xorrisofs -o output.iso \
-b isolinux/isolinux.bin -c isolinux/boot.cat \
-no-emul-boot -boot-load-size 4 -boot-info-table \
./CD_root
Gravez-le sur CD à l'aide d'un programme de gravure. Par exemple :
$ xorriso -as cdrecord -v dev=/dev/sr0 blank=as_needed output.iso

L'image de l'exemple ci-dessus démarrera depuis un CD, DVD ou BD, mais pas depuis une clé USB ou d'autres périphériques de type disque dur. Cela peut être fait à l'aide d'un MBR isohybrid. Syslinux fournit des fichiers modèles correspondants comme isohdp[fp]x*.bin. Par exemple /usr/lib/syslinux/isohdpfx.bin.
Si quelques centaines de Ko de taille ne posent pas de problème, l'option -partition_offset peut être utilisée pour créer une table de partition où la partition 1 commence non pas au bloc 0. Cela facilite les manipulations ultérieures de la clé USB à l'aide d'outils de partitionnement et de formatage.
L'image de l'exemple suivant sera préparée pour l'amorçage via MBR et sa première partition commencera au bloc 64 du disque dur.
Elle démarrera également depuis un support optique.
$ xorrisofs -o output.iso \
-b isolinux/isolinux.bin -c isolinux/boot.cat \
-no-emul-boot -boot-load-size 4 -boot-info-table \
-isohybrid-mbr /usr/lib/syslinux/isohdpfx.bin

\
-partition_offset 16 \
./CD_root
Devenez superutilisateur et copiez l'image vers le fichier de périphérique de base non partitionné de la clé USB. Sur GNU/Linux, il s'agit par exemple de /dev/sdb, et non de /dev/sdb1.
ATTENTION : Cela écrasera tout partitionnement sur la clé USB et rendra les données restantes inaccessibles.
Assurez-vous donc d'abord d'avoir la bonne adresse du périphérique visé. Par exemple, en lisant 100 Mio de données et en surveillant son clignotement :
# dd bs=2K if=/dev/sdb count=50K >/dev/null
Maintenant, copiez l'image dessus
# dd bs=2K if=output.iso of=/dev/sdb

Maintenant pour l'EFI :
Le fichier image de démarrage doit être l'image d'une partition système EFI, c'est-à-dire un système de fichiers FAT avec le répertoire /EFI/BOOT et des fichiers de démarrage aux noms prescrits par l'EFI : BOOTIA32.EFI pour x86 32 bits, BOOTx64.EFI pour AMD/x86 64 bits (dans UEFI-2.4, il y a bien un "x" en minuscules), BOOTAA64.EFI pour ARM 64 bits. Le logiciel dans le système de fichiers FAT devrait être capable de trouver et d'inspecter le système de fichiers ISO pour la configuration du chargeur de démarrage et le démarrage du système d'exploitation. Le programme GRUB2 grub-mkimage peut produire un tel système de fichiers FAT avec le contenu approprié, qui utilise ensuite d'autres logiciels GRUB2 du système de fichiers ISO.
L'équipement de démarrage EFI peut être combiné avec l'isohybrid ISOLINUX ci-dessus pour PC-BIOS d'une manière qui n'est pas vraiment conforme à UEFI-2.4, ce qui fonctionne visiblement bien. Il produit des tables de partitions MBR et GPT, toutes deux avec des partitions imbriquées. En supposant que l'image de la partition système EFI est prête sous le nom ./CD_root/boot/grub/efi.img, ajoutez les options suivantes avant l'adresse du répertoire ./CD_root :
-eltorito-alt-boot -e 'boot/grub/efi.img' -no-emul-boot \
-isohybrid-gpt-basdat \
Plus conforme à UEFI-2.4 est de choisir MBR ou GPT et d'ajouter une copie de la partition système EFI afin d'éviter le chevauchement de la partition ISO et de la partition EFI. Voici pour MBR :
-eltorito-alt-boot -e 'boot/grub/efi.img' -no-emul-boot \
-append_partition 2 0xef ./CD_root/boot/grub/efi.img \
Les ISO résultantes sont censées démarrer à partir de supports optiques et de clés USB. On peut omettre l'option -eltorito-alt-boot si aucune option -b n'est utilisée pour rendre l'ISO démarrable via PC-BIOS.

Pour les ISO avec un équipement de démarrage GRUB2 pur, envisagez d'utiliser l'outil GRUB2 grub-mkrescue comme interface à xorrisofs.

Si vous avez un système de fichiers ISO démarrable et que vous souhaitez connaître son équipement ainsi qu'une proposition pour le reproduire, essayez :
$ xorriso -hfsplus on -indev IMAGE.iso \
-report_el_torito plain -report_system_area plain \
-print "" -print "======= Proposition d'options xorrisofs :" \
-report_el_torito as_mkisofs

FICHIERS

Fichiers de démarrage :

Si --no_rc n'est pas donné comme premier argument, xorrisofs tente au démarrage de lire et d'exécuter les lignes des fichiers suivants :
/etc/default/xorriso
/etc/opt/xorriso/rc
/etc/xorriso/xorriso.conf
$HOME/.xorrisorc
Les fichiers sont lus dans l'ordre indiqué, mais aucun d'entre eux n'est obligatoire. Les lignes ne sont pas interprétées comme des options xorrisofs mais comme des commandes xorriso génériques. Voir man xorriso.

Après les fichiers de démarrage xorriso, le programme essaie un par un d'ouvrir en lecture :
./.mkisofsrc
$MKISOFSRC
$HOME/.mkisofsrc
$(dirname $0)/.mkisofsrc
En cas de succès, il interprète le contenu du fichier et n'essaie pas d'autres fichiers. La dernière adresse n'est utilisée que si l'argument de démarrage 0 a un dirname non trivial.
Le lecteur interprète actuellement les paires NAME=VALEUR suivantes :
APPI par défaut pour -A
PUBL par défaut pour -publisher
SYSI par défaut pour -sysid
VOLI par défaut pour -V
VOLS par défaut pour -volset
Toutes les autres lignes sont ignorées silencieusement.

ENVIRONNEMENT

Les variables d'environnement suivantes influencent le comportement du programme :
HOME est utilisé pour trouver les fichiers de démarrage xorriso et mkisofs.
MKISOFSRC peut être utilisé pour indiquer au programme un fichier de démarrage mkisofs.
SOURCE_DATE_EPOCH appartient aux spécifications de reproducible-builds.org. Il est censé être soit indéfini, soit contenir un nombre décimal indiquant les secondes depuis le 1er janvier 1970. S'il contient un nombre, il est utilisé comme valeur temporelle pour définir la valeur par défaut de --modification-date=. --gpt_disk_guid prend par défaut la valeur "modification-date". La valeur par défaut de --set_all_file_dates est alors "set_to_mtime". De plus, l'heure "maintenant" pour les nœuds ISO sans source disque est alors définie à la valeur SOURCE_DATE_EPOCH.
Les fichiers de démarrage et les options de programme peuvent outrepasser l'effet de SOURCE_DATE_EPOCH.
