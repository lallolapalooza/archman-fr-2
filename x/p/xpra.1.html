NOM

xpra - visionneur d'applications X distantes et persistantes

SYNOPIS

xpra start [CHAINE_CONNEXION] | xpra start-desktop [CHAINE_CONNEXION] [OPTIONS..]

xpra attach [CHAINE_CONNEXION] [OPTIONS..]

xpra shadow [CHAINE_CONNEXION] [OPTIONS..]

xpra proxy [:AFFICHAGE] [OPTIONS..]

xpra stop | xpra exit | xpra detach | xpra screenshot nom_fichier | xpra version | xpra info [CHAINE_CONNEXION] | xpra top [CHAINE_CONNEXION] [OPTIONS..]

xpra control [CHAINE_CONNEXION] commande [arguments..] [--ssh=CMD] [--remote-xpra=CMD] [--socket-dir=REP] [--socket-dirs=REPS]

xpra displays [:AFFICHAGE]

xpra clean-displays [:AFFICHAGE]

xpra list [--socket-dir=REP]

xpra list-sessions [--socket-dir=REP]

xpra list-windows [--socket-dir=REP]

xpra shell [CHAINE_CONNEXION]

xpra showconfig [OPTIONS..]

xpra showsetting [PARAM1..]

xpra list-mdns

xpra docs

xpra html5

xpra upgrade [:AFFICHAGE] [...toute option acceptée par xpra start...]

xpra upgrade-desktop [:AFFICHAGE] [...toute option acceptée par xpra start-desktop...]

xpra recover [:AFFICHAGE] [...toute option acceptée par xpra start...]

DESCRIPTION

Xpra est un outil qui vous permet d'exécuter des applications X — généralement sur un hôte distant — puis de diriger leur affichage vers votre machine locale, de vous déconnecter de ces applications, et de vous reconnecter depuis la même machine ou une autre, le tout sans perdre d'état. Il diffère de la redirection X standard en ce qu'il permet la déconnexion et la reconnexion sans interrompre l'application redirigée ; il diffère de VNC et des technologies d'affichage distant similaires en ce que xpra peut s'exécuter sans fenêtre (rootless) : c'est-à-dire que les applications redirigées par xpra apparaissent sur votre bureau comme des fenêtres normales gérées par votre gestionnaire de fenêtres, plutôt que d'être toutes « piégées dans une boîte ensemble ». Xpra utilise également un protocole personnalisé qui s'auto-ajuste et est relativement insensible à la latence, et est donc utilisable sur des connexions réseau trop lentes ou peu fiables pour la redirection X standard. Xpra peut également être utilisé pour observer un affichage X11 existant, ou en mode bureau où il se comporte davantage comme VNC.

Par défaut, le serveur Xpra annonce les sessions disponibles (nom d'utilisateur et numéro d'affichage) via mDNS sur le réseau local. Utilisez mdns=no pour le désactiver.

CHAINES DE CONNEXION

Xpra prend en charge de nombreux types de chaînes de connexion (certains peuvent nécessiter l'installation de paquets supplémentaires) :

:AFFICHAGE[,OPTIONS]

Affichages locaux : c'est la forme la plus simple et elle n'est valide que pour les affichages locaux actuels de l'utilisateur actuel.

tcp://[[UTILISATEUR][:MOTDEPASSE]@]HOTE:PORT[/AFFICHAGE][?OPTIONS]

Le mode TCP utilise des numéros de port et non des numéros d'affichage. Si plusieurs affichages sont disponibles via un seul port TCP (par exemple, en utilisant un serveur proxy), alors on peut également spécifier le numéro d'affichage après le numéro de port.

ssl://[[UTILISATEUR][:MOTDEPASSE]@]HOTE:PORT[/AFFICHAGE][?OPTIONS]

SSL ajoute une couche de socket sécurisée par-dessus le mode TCP.

vsock://[[UTILISATEUR][:MOTDEPASSE]@]HOTE:PORT[/?OPTIONS]

Quasi identique au mode TCP, mais utilise AF_VSOCK pour le transport.

ws://[[UTILISATEUR][:MOTDEPASSE]@]HOTE:PORT/[AFFICHAGE][?OPTIONS]

Connexion utilisant le protocole websocket.

wss://[[UTILISATEUR][:MOTDEPASSE]@]HOTE:PORT/[AFFICHAGE][?OPTIONS]

Connexion utilisant le protocole websocket sécurisé. (websocket avec SSL)

ssh://[[UTILISATEUR][:MOTDEPASSE]@]HOTE[:SSH_PORT]/[AFFICHAGE][?OPTIONS]

Connexion utilisant le shell sécurisé. (SSH)

D'autres options SSH peuvent être spécifiées en utilisant l'option de ligne de commande --ssh. Les OPTIONS peuvent être utilisées pour spécifier un proxy ssh : ?proxy=ssh://[UTILISATEUR[:MOTDEPASSE]@]HOTE[:SSH_PORT] xpra établira alors une connexion SSH vers l'hôte « proxy » spécifié, et à partir de cet hôte, xpra établira une connexion SSH vers le serveur xpra.

Pour des raisons de compatibilité ascendante, le mode SSH prend également en charge la syntaxe : ssh:[UTILISATEUR[:MOTDEPASSE]@]HOTE:AFFICHAGE mais cette forme ne permet pas de spécifier le numéro de port SSH. Les anciennes versions utilisaient également la forme protocole:hôte:port, mais il est conseillé aux utilisateurs d'utiliser un format d'URI plus standard avec :// comme séparateur.

Le mot de passe ne doit être spécifié que lorsque le module d'authentification du serveur l'exige.

vnc://[[UTILISATEUR][:MOTDEPASSE]@]HOTE[:VNC_PORT]/

Connexion utilisant le protocole RFB. (aka VNC) Ce mode ne fonctionne qu'avec des serveurs VNC ou un serveur xpra en mode bureau ou shadow.

EXEMPLES

xpra start :7
Démarre un serveur xpra utilisant le numéro d'affichage :7. Remarque : utiliser DISPLAY=:7 xterm pour démarrer des applications sur un affichage spécifique n'est pas recommandé. Préférez toujours utiliser l'option de ligne de commande --start= de xpra. Voir l'exemple suivant :
xpra start --start=firefox
Démarre un serveur xpra, choisit automatiquement un affichage et lance firefox sur cet affichage virtuel. Aucune fenêtre n'apparaîtra tant que vous ne vous connecterez avec xpra attach. Les commandes enfants démarrées hériteront d'un environnement adapté pour être exécutées sous xpra.
xpra start ssh://bigbox/7 --start=xterm
Démarre un serveur xpra sur bigbox avec un xterm dedans, et s'y connecte.
xpra start-desktop --start=xfce4-session
Démarre une session xfce dans un serveur X11 imbriqué sur un numéro d'affichage attribué automatiquement.
xpra displays
Liste tous les affichages actuellement en cours d'exécution sur le système. Cela inclut les sessions de bureau interactives ainsi que tout affichage virtuel (xvfb) qu'il soit utilisé ou non par un serveur xpra. Les affichages dans l'état DEAD peuvent être récupérés en utilisant xpra recover.
xpra clean-displays
Termine tous les affichages laissés dans l'état DEAD.
xpra clean-sockets
Supprime tous les sockets de serveur appartenant à des serveurs morts.
xpra list
Affiche une liste

Remove stale xpra sockets. This is automatically run when you run xpra list.

Show a list of xpra servers, with extra information about each session if it can be collected.

Show a list of xpra servers you have running on the current host, including the session name and a list of windows. (only if the session can be queried using xpra info)
xpra list-mdns
Show a list of xpra servers found via mDNS. (local network)
xpra docs
Open the documentation in a web browser.
xpra html5
Open the html5 client in a web browser.
xpra shell
Start an interactive debug shell.

Shows the configuration that would be used with other sub-commands, taking into account the command line arguments.

Shows the value of a specific configuration setting and which configuration directory set this value.

Start an xpra server and a screen(1) session. If any of the applications inside screen attempt to use X, they will be directed to the xpra server.

AFFICHAGES

Comprendre l'idée de base des affichages est essentiel pour utiliser xpra avec succès.

L'idée provient du système X standard. Si vous avez plusieurs serveurs X en cours d'exécution sur le même hôte, il doit y avoir un moyen de les distinguer. X le fait en attribuant à chaque serveur un petit entier unique appelé (peut-être de manière confuse) son "affichage". Dans le cas courant d'une machine de bureau qui n'a qu'un seul serveur X en cours d'exécution, ce serveur utilise l'affichage ":0" (ou parfois vous verrez ":0.0", qui est effectivement la même chose). Lorsqu'une application démarre sous X, elle doit savoir comment trouver le bon serveur X à utiliser ; elle le fait en vérifiant la variable d'environnement $DISPLAY.

Xpra est confronté à un problème similaire — il peut y avoir plusieurs serveurs xpra en cours d'exécution sur le même hôte, ainsi que plusieurs serveurs X. Il résout ce problème en réutilisant la solution de X — chaque serveur xpra a un affichage associé. Cet affichage fonctionne à la fois comme un affichage X (pour lorsque xpra communique avec des applications X) et comme un identifiant par lequel les clients xpra (comme xpra attach) peuvent localiser le serveur xpra.

Vous pouvez omettre le numéro d'affichage lors de l'utilisation de xpra start : un affichage vous sera choisi automatiquement. Le numéro d'affichage choisi sera indiqué dans la sortie du journal, vous devriez également pouvoir le voir avec xpra list. Sur Microsoft Windows et Mac OSX, le numéro d'affichage doit être omis.

Sinon, lors du démarrage d'un serveur xpra, vous voudrez peut-être spécifier le nom de l'affichage à utiliser. Pour ce faire, choisissez simplement le numéro qui vous plaît et mettez un deux-points devant. Par exemple :7, :12 et :3117 sont tous des noms d'affichage valides. Gardez simplement à l'esprit que :

  • Chaque serveur X ou xpra qui s'exécute sur une seule machine doit utiliser un nom d'affichage différent. Si vous choisissez un numéro déjà utilisé, xpra ne fonctionnera pas.
  • Les quelques premiers numéros (0, 1, 2) sont couramment utilisés par les vrais serveurs X.
  • Toute personne se connectant à une machine donnée en utilisant ssh(1) avec le transfert X activé utilisera également un numéro d'affichage ; ssh choisit généralement des numéros proches de dix (10, 11, 12, ...).

Lors de la spécification d'un serveur xpra à un programme client tel que xpra attach, xpra detach, xpra stop, xpra exit, xpra version, xpra info, xpra list ou xpra screenshot, vous pouvez utiliser un affichage de la forme :AFFICHAGE pour faire référence à un serveur sur l'hôte local, ou de la forme ssh://[UTILISATEUR@]HOTE/AFFICHAGE pour faire référence à un serveur sur un hôte distant ; xpra se connectera automatiquement à l'hôte distant en utilisant ssh(1). Généralement, si vous n'avez qu'une seule session xpra en cours d'exécution sur une machine (ce que vous pouvez vérifier en exécutant xpra list sur cette machine), vous pouvez omettre complètement le numéro ; xpra attach seul se connectera au seul serveur xpra sur la machine actuelle, quel que soit son numéro, xpra attach ssh://frodo se connectera de même à la seule session xpra sur une machine distante.

La connexion en utilisant le numéro d'affichage suppose que le client et le serveur utilisent la même configuration pour les répertoires de sockets, ou du moins que le client peut trouver au moins l'un des répertoires utilisés par les sockets de domaine unix (voir bind, socket-dir et socket-dirs).

Si le serveur xpra a reçu l'option --bind-tcp=[HOTE]:PORT (ou --bind-ssl, --bind-ws, --bind-wss, --bind-vsock) lors de son démarrage, vous pouvez également vous y connecter en utilisant un affichage de la forme tcp://HOTE:PORT[/AFFICHAGE], ssl://HOTE:PORT[/AFFICHAGE], ws://HOTE:PORT[/AFFICHAGE], wss://HOTE:PORT[/AFFICHAGE] ou vsock://HOTE:PORT[/AFFICHAGE].

SOUS-COMMANDES

xpra start

Cette commande démarre un nouveau serveur xpra, y compris toute la configuration nécessaire. (Lors du démarrage d'un serveur distant avec la syntaxe ssh://HOTE/AFFICHAGE, la nouvelle session sera également attachée.)

xpra start-desktop

Démarre un serveur X11 imbriqué, toutes les commandes enfants seront démarrées dans le serveur X11 imbriqué.

xpra attach

Cette commande se connecte à un serveur xpra en cours d'exécution et transfère toutes les applications utilisant ce serveur pour qu'elles apparaissent sur votre écran actuel.

xpra detach

Détache l'affichage xpra spécifié.

xpra screenshot

Prend une capture d'écran et l'enregistre dans le nom de fichier spécifié. Note : les captures d'écran ne peuvent être prises que lorsqu'un client est attaché.

xpra version

Interroge la version du serveur et l'affiche. Note : les serveurs plus anciens peuvent ne pas prendre en charge cette fonctionnalité.

xpra info

Interroge le serveur pour la version, le statut et les statistiques.

xpra top

Affiche les attributs clés de santé du serveur.

xpra control

Modifie le serveur à l'exécution en émettant des commandes. La liste des commandes peut être obtenue en spécifiant "help" comme commande. Certaines de ces commandes peuvent également prendre en charge un mode "help".

xpra initenv

Cette commande interne crée le script run-xpra utilisé avec les connexions ssh.

xpra stop

Cette commande se connecte à un serveur xpra en cours d'exécution et demande qu'il se termine immédiatement. Cela entraîne généralement la terminaison de toutes les applications utilisant ce serveur.

xpra exit

Cette commande se connecte à un serveur xpra en cours d'exécution et demande qu'il se termine immédiatement. Contrairement à xpra stop, le processus Xvfb et ses clients X11 (le cas échéant) resteront en cours d'exécution.

xpra showconfig

Cette commande affiche la configuration qui serait utilisée compte tenu des arguments fournis. Vous pouvez également spécifier comme arguments supplémentaires les options spécifiques qui doivent être affichées, ou utiliser la valeur spéciale all pour afficher toutes les options, y compris celles qui ne sont normalement pas affichées parce qu'elles ne sont pas pertinentes sur le système donné.

xpra list

Cette commande trouve tous les serveurs xpra qui ont été démarrés par l'utilisateur actuel sur la machine actuelle et les liste.

xpra upgrade

Cette commande démarre un nouveau serveur xpra, mais au lieu de le créer à partir de zéro, elle se connecte à un autre serveur existant, lui dit de se terminer, et prend en charge la gestion des applications qu'il gérait auparavant. Comme son nom l'indique, le cas d'utilisation principal est de remplacer un serveur exécuté avec une ancienne version de xpra par une version plus récente, sans avoir à redémarrer votre session. Toute commande xpra attach en cours d'exécution se terminera et devra être redémarrée.

xpra upgrade-desktop

Identique à upgrade mais pour les serveurs démarrés avec start-desktop. Il est possible de mettre à niveau un serveur transparent en un serveur de bureau et vice versa.

xpra recover

Similaire à upgrade et upgrade-desktop : mais sans avoir besoin de spécifier si le ser

ver to recover est un serveur ou un serveur de bureau sans couture. Contrairement aux sous-commandes upgrade, recover peut également détecter quels affichages doivent être récupérés. C'est-à-dire, les affichages qui étaient précédemment utilisés par un serveur xpra mais que ce serveur a disparu.

xpra shadow

Cette commande met en miroir un affichage existant et est prise en charge sur les plateformes X11, MacOS et MS Windows. (ce n'est pas encore pris en charge sur Wayland)

S'il n'y a qu'un seul écran X11 actif et que son numéro est inférieur à 10, il peut être détecté automatiquement et l'écran peut être omis.

Notez que ce mode de fonctionnement utilise le screenscraping, qui n'est pas très efficace. Les encodeurs vidéo atténuent partiellement cet inconvénient.

Par défaut, le mode shadow expose tous les moniteurs connectés en tant que fenêtres individuelles. Mais il est également possible de ne mettre en miroir qu'une région ou un moniteur spécifique, ou de regrouper tous les moniteurs en une seule fenêtre en spécifiant des options d'affichage. Voici quelques exemples:

Pour exposer tous les moniteurs connectés à l'affichage :1 sous forme d'une seule fenêtre,
utilisez l'option multi-window :
xpra shadow :1,multi-window=no
Pour mettre en miroir une sortie spécifique en utilisant son nom (par exemple, DP-1) :

xpra shadow :1,DP-1
ou plus explicitement :
xpra shadow :1,plug=DP-1
Pour exposer une zone rectangulaire de taille 1920x1080 sous forme d'une seule fenêtre, utilisez :

xpra shadow :1,1920x1080
Vous voudrez peut-être également spécifier la position de ce rectangle (par exemple, 1280x0) :
xpra shadow :1,1920x1080@1280x0
ou en utilisant la syntaxe plus explicite :
xpra shadow :1,geometry=1920x1080@1280x0
Plusieurs zones peuvent être spécifiées en utilisant / comme séparateur, chacune sera exposée sous forme d'une fenêtre distincte :
xpra shadow :1,1920x1080@1280x0/1280x600@0x400

xpra proxy

Cette commande permet à un seul serveur de proxifier les connexions pour plusieurs autres, servant potentiellement de point d'entrée d'équilibrage de charge ou d'authentification pour de nombreuses sessions. Le serveur proxy lancera un nouveau processus pour chaque connexion proxy, ce processus proxy créera un socket de domaine Unix non authentifié qui peut être utilisé avec les sous-commandes info, version et stop.

Note importante

Certaines plateformes et gestionnaires de paquets peuvent choisir de ne compiler que le client et non le serveur. Dans ce cas, seule la sous-commande attach sera disponible.

OPTIONS

Options générales

--version
Affiche le numéro de version de xpra.
-h, --help
Affiche un résumé de l'utilisation de la ligne de commande.
--minimal
Désactive toutes les fonctionnalités non essentielles.
-d FILTRE1,FILTRE2,..., --debug=FILTRE1,FILTRE2,...
Active la journalisation de débogage. La valeur spéciale all active tous les débogages. Pour obtenir la liste complète des catégories de journalisation, exécutez xpra -d help. Pour cibler les journaux qui utilisent plus d'une catégorie de journalisation (car certaines catégories peuvent être assez larges), joignez-les avec un '+'. Par exemple, pour activer la journalisation pour server et keyboard, utilisez --debug server+keyboard. Vous pouvez également exclure une catégorie avec le préfixe '-'. Par exemple, pour activer le débogage shadow mais pas clipboard, utilisez : --debug shadow,-clipboard.
--mmap=oui|non|NOMDEFICHIERABSOLU|RÉPERTOIRE
Active ou désactive le transfert de données de pixels mappées en mémoire. Par défaut, il est normalement activé automatiquement si le serveur et le client résident dans le même espace de noms de fichiers. Cette méthode de transfert de données offre des surcoûts beaucoup plus faibles et réduit la consommation du CPU ainsi que le trafic réseau local. Lors de l'attachement, vous pouvez également spécifier un chemin absolu où le fichier mmap sera créé. Lors de son utilisation sur le serveur, on peut spécifier le nom de fichier exact que le client créera, ou juste le répertoire où le fichier sera créé afin que plusieurs clients puissent se connecter et utiliser mmap de manière concurrente.
--mmap-group=GROUPE
Définit le gid du fichier mmap sur le groupe spécifié, et définit les permissions sur 660. Ceci est nécessaire pour partager le fichier mmap entre les comptes utilisateurs. Vous pouvez également utiliser les valeurs spéciales GROUPE suivantes :
no
Désactive la fonctionnalité, le fichier mmap utilisera les permissions de fichier par défaut et la propriété de groupe par défaut.
SOCKET
Le groupe utilisé sera le même que celui trouvé sur le fichier de socket de domaine Unix auquel le client se connecte. Évidemment, cela ne peut fonctionner que lors de la connexion à des sockets de domaine Unix.
auto
Utilisera le groupe 'xpra' si l'utilisateur en est membre, sinon il se rabattra sur le même comportement que SOCKET.
--windows=oui|non
Active ou désactive le transfert des fenêtres. C'est généralement l'usage principal de xpra et il devrait être activé.
--min-size=LARGEURxHAUTEUR
Définit la taille minimale pour toutes les fenêtres décorées.
--max-size=LARGEURxHAUTEUR
Définit la taille maximale pour toutes les fenêtres.
--readonly=oui|non
Le mode lecture seule ignore toute activité du clavier et de la souris.
--clipboard=oui|non|type-clipboard
Active ou désactive la synchronisation du presse-papiers. S'il est désactivé sur le serveur, aucun client ne pourra utiliser la synchronisation du presse-papiers. S'il est désactivé sur le client, seule cette connexion particulière ignorera les données du presse-papiers provenant du serveur. Ceci peut également être utilisé pour spécifier une implémentation de presse-papiers différente. Les types de presse-papiers disponibles varieront d'une plateforme à l'autre et dépendront également de l'environnement et des options de compilation, il est donc préférable de laisser sur auto. D'autres types de presse-papiers disponibles peuvent inclure :
translated
Presse-papiers qui peut traduire d'un type de sélection à un autre
GDK
L'implémentation de presse-papiers la plus complète, incluant le support complet de X11
default
Presse-papiers de repli, avec un support X11 limité
OSX
Presse-papiers spécifique à OSX
--clipboard-direction=vers-serveur|vers-client|les-deux|désactivé
Choisit la direction de la synchronisation du presse-papiers.
--pulseaudio=oui|non
Active ou désactive le démarrage d'un serveur pulseaudio avec la session.
--pulseaudio-command=COMMANDE-DÉMARRAGE-SERVEUR
Spécifie la commande pulseaudio à utiliser pour démarrer le serveur pulseaudio, sauf s'il est désactivé avec pulseaudio=no.
--session-name=VALEUR
Définit le nom de cette session. Cette valeur peut être utilisée dans les notifications, les utilitaires, le menu du plateau, etc. Définir cette valeur sur le serveur fournit une valeur par défaut qui peut être remplacée sur le client.
--encoding=ENCODAGE
Définit l'encodage préféré à utiliser. Pour voir la liste des encodages disponibles, utilisez --encoding=help. Ceci peut être utilisé pour sélectionner des modes niveaux de gris ou des modes 8 bits comme png/P. Sur les connexions locales ou avec des liaisons réseau extrêmement rapides, le rgb simple est également une option viable. Pour tout le reste, la valeur par défaut auto sélectionnera le meilleur encodage automatiquement et vous devriez utiliser les options min-speed et min-quality à la place pour le réglage.
--encodings=ENCODAGE
Ceci spécifie les encodages d'image activés. C'est l'option de ligne de commande la plus mal utilisée et elle devrait être laissée seule. Le moteur serveur a besoin d'avoir plusieurs encodages disponibles pour fonctionner efficacement.
--video-scaling=on|off|SCALING
Quelle quantité de sous-échantillonnage vidéo automatique doit être utilisée, de 1 (rarement) à 100 (agressivement), 0 pour désactiver. Le sous-échantillonnage vidéo est normalement utilisé avec des régions vidéo ou des fenêtres très grandes (en particulier les fenêtres plein écran) pour essayer de maintenir un framerate décent. Le sous-échantillonnage vidéo affecte négativement la qualité visuelle et provoquera des rafraîchissements automatiques (si activés), il est le plus utile sur le contenu vidéo où il permet d'économiser une quantité considérable de bande passante.
--socket-dir=DIR
Emplacement où écrire et rechercher les fichiers de socket Xpra. L'emplacement par défaut varie d'une plateforme à l'autre ("~/.xpra" et "$XDG_RUNTIME_DIR/xpra" sur la plupart des systèmes Posix). Si non spécifié, la première valeur de socket-dirs sera utilisée. Il peut également être spécifié en utilisant la variable d'environnement XPRA_SOCKET_DIR.

En utilisant l'option socket-dir, il est généralement nécessaire de spécifier socket-dir ou socket-dirs sur toutes les commandes suivantes, pour que xpra fonctionne avec les sessions ouvertes.

En spécifiant un répertoire partagé, cela peut être couplé avec l'option mmap-group et socket-permissions pour connecter des sessions Xpra entre comptes utilisateurs avec une accélération par mémoire partagée.

Options pour start, start-desktop, upgrade et listen :

Dans les versions précédentes, l'authentification pour chaque type de connexion était configurée à l'aide d'une option de ligne de commande distincte qui s'appliquait à toutes les connexions du même type. Par exemple : tcp-auth pour bind-tcp. Bien que cela soit toujours pris en charge comme solution de repli, la méthode recommandée est de spécifier les options d'authentification à l'aide des propriétés de liaison. Par exemple : bind-tcp=0.0.0.0:14500,auth=file:filename=password.txt. Les propriétés peuvent également définir des options de configuration de socket supplémentaires.

--bind=EMPLACEMENT_LIAISON[,PROPRIETES] Crée un socket de domaine Unix local (sur Unix) ou un pipe nommé (sur MS Windows) pour chaque option bind spécifiée.

Cette option peut être spécifiée plusieurs fois pour définir plusieurs emplacements de socket. Ces sockets prennent en charge les connexions locales avec l'adresse d'affichage de style :7, et les connexions distantes avec l'adresse d'affichage de style ssh://frodo/7.

Les sockets locaux peuvent également traiter les connexions HTTP / Websocket si le commutateur html est activé.

L'emplacement peut prendre la forme :

none
ne crée pas de socket
auto
valeur par défaut rétrocompatible qui utilise le socket-dir actuel
REPERTOIRE/
crée un socket dans le répertoire spécifié, si le répertoire n'existe pas il sera créé - vous devriez inclure la barre oblique finale pour éviter la confusion avec la forme CHEMIN :
CHEMIN
crée le socket en utilisant le chemin spécifié
--bind-tcp=[HOTE]:PORT[,PROPRIETES]
Crée un socket TCP pour chaque option --bind-tcp spécifiée. Si la partie hôte est omise, alors 127.0.0.1 (localhost) sera utilisé. Si vous souhaitez accepter les connexions sur toutes les interfaces, passez 0.0.0.0 pour la partie hôte.

L'utilisation de ce commutateur sans définir l'option auth n'est pas recommandée et constitue un risque de sécurité majeur (surtout lors du passage de 0.0.0.0) ! N'importe qui peut se connecter à ce port et accéder à votre session.

Les sockets TCP peuvent également traiter les connexions HTTP / Websocket si le commutateur html est activé. Les sockets TCP peuvent également être mis à niveau vers des sockets SSL si le commutateur ssl est activé.

Crée un écouteur HTTPS / Secure Websocket. Voir bind-tcp pour les restrictions d'hôte, vous devriez utiliser auth-wss pour sécuriser l'accès.

Identique à --bind-tcp mais pour les sockets SSL. Voir ssl-auth et les autres options SSL.

Spécifie le module d'authentification à utiliser pour tous les sockets de domaine unix créés à l'aide du commutateur bind. Les modules d'authentification peuvent valider un nom d'utilisateur et un mot de passe par rapport à divers modules backend :
allow
autorise toujours l'authentification - c'est dangereux et ne devrait être utilisé que pour des tests
fail
échoue toujours à l'authentification, utile pour les tests
env
correspond à la variable d'environnement spécifiée par l'option name (qui par défaut est XPRA_PASSWORD). Par exemple : --auth=env:name=UNE_AUTRE_VARIABLE_ENV_NOM.

correspond au mot de passe
spécifié à l'aide de l'option value. Par exemple : --auth=password:value=VOTREMOTDEPASSEMENT. Note : cette option en ligne de commande peut être exposée à d'autres processus sur le même système.

vérifie le mot de passe par rapport aux données de mot de passe trouvées dans le fichier spécifié à l'aide de l'option filename. Par exemple : --auth=file:filename=./password.txt.

Le contenu de ce fichier sera traité comme des données binaires, il n'y a aucune restriction sur les encodages de caractères ou la taille des fichiers. Attention aux caractères de nouvelle ligne finaux qui seront inclus dans les données du mot de passe.

vérifie le nom d'utilisateur et le mot de passe par rapport au fichier spécifié à l'aide de l'option filename. Le fichier doit contenir les identifiants de chaque utilisateur sur une ligne de la forme :

nom_utilisateur|mot_de_passe|uid|gid|displays|env_opts|session_opts

sqlite
mysql

La commande doit retourner 0 pour autoriser l'accès, toute autre valeur refusera l'accès.

--modal-windows=yes|no
Respecter les fenêtres modales. Cela peut avoir des effets secondaires indésirables lorsque plusieurs applications sont transmises via le même serveur xpra : les fenêtres modales seront rendues modales pour toutes les applications transmises par xpra plutôt que pour la seule application qui possède cette fenêtre.

Remplace la barre de titre standard de la fenêtre par une barre personnalisée utilisée pour donner accès aux contrôles de fenêtre spécifiques à xpra. Cette fonctionnalité peut avoir des effets secondaires et est incompatible avec l'accélération OpenGL sur MS Windows.
--password-file=FILENAME
Fournit le mot de passe à utiliser pour se connecter à un serveur qui utilise l'authentification. Obsolète, utilisez les options d'authentification par socket.
--opengl=(yes|no|auto)[:backend]
Utilise le rendu accéléré OpenGL sur le client. Par défaut, il détecte si la carte graphique et les pilotes sont supportés (mode auto), mais on peut aussi désactiver OpenGL (no) ou forcer son activation (yes). Sur certaines plateformes, il est également possible de spécifier quels backends doivent être utilisés, seuls gtk et native sont actuellement supportés et uniquement sur les plateformes X11. par exemple : opengl=yes:native, ou opengl=auto:gtk,native.
--webcam=yes|no|/dev/deviceXXX|DEVICEID
Active ou désactive la transmission de la webcam. Le périphérique webcam à utiliser peut également être spécifié.
-zLEVEL, --compress=LEVEL
Sélectionne le niveau de compression que xpra utilisera lors de la transmission des données sur le réseau. Il n'y a que deux valeurs possibles : 0 (signifiant aucune compression) et 1 (compression activée).

Cette compression n'est pas utilisée sur les données pixel (sauf lors de l'utilisation de l'encodage rgb).

--quality=VALUE
Cette option définit une qualité de compression d'image fixe pour les encodages avec perte (jpeg, webp, h264/h265 et vp8/vp9). Tout d'abord, l'un de ces encodages avec perte doit être activé avec --encoding ou lors de l'utilisation du mode auto par défaut. Les valeurs vont de 1 (qualité la plus basse, compression élevée - généralement inutilisable) à 100 (qualité la plus élevée, compression faible). Spécifiez une valeur de zéro pour laisser le système ajuster la qualité dynamiquement afin d'obtenir la meilleure utilisation possible de la bande passante. Il est généralement préférable de ne pas utiliser cette option et d'utiliser plutôt min-quality.
--min-quality=MIN-QUALITY
Cette option définit la qualité d'encodage minimale autorisée lorsque l'option quality est réglée sur le mode automatique. Voir quality ci-dessus.
--speed=SPEED
Cette option définit la vitesse d'encodage, de 1 (la plus lente) à 100 (la plus rapide). Plus lent compresse mieux et utilisera moins de bande passante, plus rapide donnera une latence meilleure tant qu'il y a suffisamment de bande passante. Le système utilise normalement une vitesse variable, cette option force un réglage de vitesse fixe à être utilisé à la place. Il est généralement préférable de ne pas utiliser cette option et d'utiliser plutôt min-speed.
--min-speed=MIN-SPEED
Cette option définit la vitesse d'encodage minimale autorisée lorsque l'option speed est réglée sur le mode automatique. Voir speed ci-dessus.
--auto-refresh-delay=DELAY
Cette option définit un délai après lequel les fenêtres sont automatiquement rafraîchies en utilisant une image sans perte si leur contenu avait été mis à jour précédemment avec un encodage avec perte. Le délai est un nombre à virgule flottante et est en secondes. Cette option est activée par défaut avec un délai de 0.25 secondes. Cette option n'est pertinente que lors de l'utilisation d'un encodage avec perte.
--shortcut-modifiers=MODIFIERS
Définit les modificateurs de raccourcis par défaut requis par les key-shortcuts, ces modificateurs peuvent ensuite être référencés comme #. La valeur par défaut est 'auto' qui s'évalue à Meta+Shift sur la plupart des plateformes.

Peut être spécifié plusieurs fois pour ajouter plusieurs raccourcis clavier. Ces touches seront interceptées par le client et déclencheront l'action spécifiée, et les pressions de touche ne seront pas transmises au serveur.

La spécification KEY peut inclure des modificateurs de clavier sous la forme [modifier+]*key, par exemple : Shift+F10 ou Shift+Control+B. Vous pouvez référencer la valeur de l'option shorcut-modifers en utilisant #, c'est-à-dire : #+F1.

Les raccourcis définis sur la ligne de commande sont ajoutés aux raccourcis par défaut intégrés. Pour effacer la liste des raccourcis, utilisez key-shortcut=clear et définissez vos raccourcis après celui-ci.

Attention, les parenthèses et les guillemets doivent généralement être échappés lorsqu'ils sont utilisés à partir d'une ligne de commande shell. Options pour attach, stop, info, screenshot, version

--ssh=CMD
Lorsque vous utilisez une adresse ssh: pour vous connecter à un affichage distant, xpra exécute ssh(1) pour établir la connexion sous-jacente. La plupart des installations devraient maintenant utiliser paramiko comme commande backend par défaut. Une autre valeur courante pour CMD est ssh ou plink sous Microsoft Windows. Si votre programme ssh se trouve dans un emplacement inhabituel, a un nom inhabituel, ou si vous souhaitez passer des options spéciales pour modifier le comportement de ssh, vous pouvez utiliser le commutateur --ssh pour indiquer à xpra comment exécuter ssh.

Par exemple, si vous souhaitez utiliser le chiffrement arcfour, vous devriez exécuter

xpra attach --ssh="ssh -c arcfour" ssh://frodo/7
Note : Ne vous embêtez pas à activer la compression ssh ; c'est redondant avec la propre compression de xpra et cela ne fera que gaspiller votre CPU.

Sur MS Windows, où les barres obliques inverses sont utilisées pour séparer les éléments de chemin et où les espaces sont souvent utilisés dans les chemins, vous devez ajouter des guillemets autour des chemins. (c'est-à-dire : ssh="C:\Program Files\Xpra\Plink.exe" -ssh -agent)

--exit-ssh=oui|non
Choisissez si le processus client SSH doit être terminé de force lorsque xpra se déconnecte du serveur. Si vous utilisez le partage de connexion SSH, vous pourriez vouloir éviter d'arrêter l'instance du processus maître SSH lancée par xpra car elle pourrait être utilisée par d'autres sessions SSH. Note : exit-ssh=no détache le processus SSH du terminal, ce qui empêche le processus SSH d'interagir avec l'entrée du terminal, désactive l'interaction clavier requise pour la saisie du mot de passe, la vérification de la clé hôte, etc.
--remote-xpra=CMD
Lors de la connexion à un serveur distant via ssh, xpra doit pouvoir trouver et exécuter l'exécutable xpra sur l'hôte distant. Si cet exécutable se trouve dans un emplacement non standard, ou nécessite des variables d'environnement spéciales pour être défini avant de pouvoir s'exécuter, cela peut être non trivial. Si l'exécution de xpra attach ssh:quelquechose échoue car il ne trouve pas le xpra distant, vous pouvez utiliser cette option pour spécifier comment exécuter xpra sur l'hôte distant.

Cela dit, cette option ne devrait pas être nécessaire en usage normal, car xpra essaie très fort de contourner les problèmes mentionnés ci-dessus. Si vous la trouvez utile souvent, cela pourrait indiquer un bug dont nous aimerions être informés.

~/.xpra/:7.log
Lorsqu'il est exécuté en mode démon (par défaut), le serveur xpra dirige toutes les sorties vers ce fichier. Cela inclut toutes les sorties de débogage, si le débogage est activé.
~/.xpra/run-xpra
Un script shell qui, lorsqu'il est exécuté, démarre xpra avec l'interpréteur python correct, PYTHONPATH, PATH, l'emplacement du script xpra principal, etc. Généré automatiquement par xpra initenv, xpra start et utilisé par xpra attach (voir également la discussion sur --remote-xpra).

BOGUES

Xpra ne gère pas entièrement tous les aspects du protocole X ; par exemple, les fonctionnalités d'entrée sophistiquées comme la sensibilité à la pression sur les tablettes, certaines indications du gestionnaire de fenêtres, et probablement d'autres parties plus obscures du protocole X. Il se dégrade cependant gracieusement, et des correctifs pour chaque fonctionnalité seraient gracieusement acceptés.

Le serveur xpra alloue une framebuffer trop grande lors de l'utilisation d'Xvfb ; cela gaspille de la mémoire. Si Xvfb ne prend pas en charge RandR, cela peut également entraîner un mauvais comportement des applications (par exemple, en laissant les menus sortir de l'écran). Ce n'est pas un problème lors de l'utilisation d'Xdummy, voir le commutateur --xvfb pour les détails. Inversement, si la framebuffer est jamais insuffisante, les clients se comporteront mal d'autres manières (par exemple, les événements d'entrée seront mal dirigés).
