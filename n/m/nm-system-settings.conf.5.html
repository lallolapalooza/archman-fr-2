NETWORKMANAGER.CONF(5) Configuration NETWORKMANAGER.CONF(5)

NOM

NetworkManager.conf - Fichier de configuration de NetworkManager

SYNOPSIS

/etc/NetworkManager/NetworkManager.conf, /etc/NetworkManager/conf.d/nom.conf, /run/NetworkManager/conf.d/nom.conf, /usr/lib/NetworkManager/conf.d/nom.conf, /var/lib/NetworkManager/NetworkManager-intern.conf

DESCRIPTION

NetworkManager.conf est le fichier de configuration de NetworkManager. Il est utilisé pour configurer divers aspects du comportement de NetworkManager. L'emplacement du fichier principal et des répertoires de configuration peut être modifié en utilisant les arguments --config, --config-dir, --system-config-dir, et --intern-config pour NetworkManager, respectivement.

Si un fichier NetworkManager.conf par défaut est fourni par les paquets de votre distribution, vous ne devriez pas le modifier, car vos changements pourraient être écrasés par les mises à jour de paquets. Au lieu de cela, vous pouvez ajouter des fichiers .conf supplémentaires au répertoire /etc/NetworkManager/conf.d. Ceux-ci seront lus dans l'ordre, les fichiers ultérieurs remplaçant les précédents. Les paquets peuvent installer d'autres extraits de configuration dans /usr/lib/NetworkManager/conf.d. Ce répertoire est analysé en premier, avant même NetworkManager.conf. Les scripts peuvent également placer une configuration par démarrage dans /run/NetworkManager/conf.d. Ce répertoire est analysé en second, également avant NetworkManager.conf. Le chargement d'un fichier /run/NetworkManager/conf.d/nom.conf peut être empêché en ajoutant un fichier /etc/NetworkManager/conf.d/nom.conf. De même, un fichier /usr/lib/NetworkManager/conf.d/nom.conf peut être masqué en plaçant un fichier du même nom dans /etc/NetworkManager/conf.d ou /run/NetworkManager/conf.d.

NetworkManager peut écraser certaines options de configuration utilisateur via D-Bus ou d'autres opérations internes. Dans ce cas, il écrit ces changements dans /var/lib/NetworkManager/NetworkManager-intern.conf. Ce fichier n'est pas destiné à être modifié par l'utilisateur, mais il est lu en dernier et peut masquer la configuration utilisateur de NetworkManager.conf.

Certains paramètres de la configuration peuvent être rechargés à la volée soit en envoyant le signal SIGHUP, soit via l'appel D-Bus Reload.

NetworkManager ne nécessite aucune configuration dans NetworkManager.conf. Selon votre cas d'utilisation, vous pouvez supprimer tous les fichiers pour restaurer la configuration par défaut (réinitialisation d'usine). Mais notez que votre distribution ou d'autres paquets peuvent fournir des extraits de configuration pour NetworkManager, qui font partie de la configuration par défaut.

FORMAT DU FICHIER

Le format du fichier de configuration est le soi-disant fichier clé (genre de format type ini). Il se compose de sections (groupes) de paires clé-valeur. Les lignes commençant par '#' et les lignes vides sont considérées comme des commentaires. Les sections sont démarrées par une ligne d'en-tête contenant la section entre crochets '[' et ']', et se terminent implicitement par le début de la section suivante ou la fin du fichier. Chaque paire clé-valeur doit être contenue dans une section.

Pour les clés qui acceptent une liste d'appareils comme valeur, vous pouvez spécifier les appareils par leur adresse MAC ou leur nom d'interface, ou par "*" pour spécifier tous les appareils. Voir la section appelée « Format de liste d'appareils » ci-dessous.

Un fichier de configuration simple ressemble à ceci :

[main]
plugins=keyfile

En tant qu'extension au format de fichier clé normal, vous pouvez également ajouter une valeur à une clé à valeur de liste précédemment définie en faisant :

plugins+=autre-plugin
plugins-=supprimer-moi

SECTION PRINCIPALE

plugins

Liste les noms des plugins de paramètres système séparés par ','. Ces plugins sont utilisés pour lire et écrire les profils de connexion au niveau du système. Lorsque plusieurs plugins sont spécifiés, les connexions sont lues à partir de tous les plugins listés. Lors de l'écriture des connexions, les plugins seront invités à sauvegarder la connexion dans l'ordre indiqué ici ; si le premier plugin ne peut pas écrire ce type de connexion (ou ne peut écrire aucune connexion), le plugin suivant est essayé, etc. Si aucun des plugins ne peut sauvegarder la connexion, une erreur est renvoyée à l'utilisateur.

La valeur par défaut et le nombre de plugins disponibles sont spécifiques à la distribution. Voir la section appelée « PLUGINS » ci-dessous pour les plugins disponibles. Notez que le plugin de fichier clé natif de NetworkManager est toujours ajouté à la fin de cette liste (s'il n'y apparaît pas déjà plus tôt dans la liste).

monitor-connection-files

Ce paramètre est déprécié et n'a aucun effet. Les profils disques ne sont jamais rechargés automatiquement. Utilisez par exemple nmcli connection (re)load pour cela.

auth-polkit

Si le système utilise PolicyKit pour l'autorisation. Si true, les requêtes non root sont autorisées via PolicyKit. Les requêtes de root (utilisateur zéro) sont toujours accordées sans demander à PolicyKit. Si false, toutes les requêtes seront autorisées et PolicyKit ne sera pas utilisé. Si défini sur root-only, PolicyKit ne sera pas utilisé et toutes les requêtes sauf celles de root seront refusées. La valeur par défaut est true.

dhcp

Cette clé configure le client DHCP que NetworkManager utilisera. Les valeurs autorisées dépendent de la configuration de compilation ; cette version de NetworkManager a été compilée avec le support pour les clients suivants : interne, dhcpcd.

Le client interne est intégré, tandis que d'autres options peuvent nécessiter l'installation d'un client DHCP externe.

Si cette clé est manquante, le client interne est utilisé avec un retour aux autres clients pris en charge.

no-auto-default

Spécifie les appareils pour lesquels NetworkManager ne doit pas créer de connexion filaire par défaut (Auto eth0). Par défaut, NetworkManager crée une connexion filaire temporaire pour tout appareil Ethernet géré et n'ayant pas de connexion configurée. Listez un appareil dans cette option pour empêcher la création de la connexion par défaut pour cet appareil. Peut avoir la valeur spéciale * pour s'appliquer à tous les appareils.

Lorsque la connexion filaire par défaut est supprimée ou sauvegardée dans une nouvelle connexion persistante par un plugin, l'appareil est ajouté à une liste dans le fichier /var/lib/NetworkManager/no-auto-default.state pour empêcher la création de la connexion par défaut pour cet appareil à nouveau.

Voir la section appelée « Format de liste d'appareils » pour la syntaxe de spécification d'un appareil.

Exemple :

no-auto-default=00:22:68:5c:5d:c4,00:1e:65:ff:aa:ee
no-auto-default=eth0,eth1
no-auto-default=*

ignore-carrier

Ce paramètre est déprécié pour le paramètre par appareil ignore-carrier qui remplace ce paramètre s'il est spécifié (Voir ignore-carrier). Sinon, il s'agit d'une liste de correspondances pour spécifier pour quel appareil le transport doit être ignoré. Voir la section appelée « Format de liste d'appareils » pour la syntaxe de spécification d'un appareil. Notez que les types de contrôleurs comme bond, bridge et team ignorent le transport par défaut. Vous pouvez cependant annuler ce comportement par défaut en utilisant le spécificateur « except: » (ou mieux, utilisez le paramètre par appareil au lieu du paramètre déprécié).

assume-ipv6ll-only

Spécifie les appareils pour lesquels NetworkManager tentera de générer une connexion basée sur la configuration initiale lorsque l'appareil n'a qu'une adresse de lien local IPv6.

Voir la section appelée « Format de liste d'appareils » pour la syntaxe de spécification d'un appareil.

configure-and-quit

Cette option n'est plus utile à configurer dans le fichier NetworkManager.conf. Elle peut cependant être configurée sur la ligne de commande avec les mêmes valeurs, où elle a une certaine utilité.

Lorsqu'elle est définie sur 'initrd', NetworkManager ne se connecte pas à D-Bus et se termine après avoir configuré le réseau. C'est un détail d'implémentation sur la façon dont le module NetworkManager de dracut peut exécuter NetworkManager. Une alternative consiste à avoir NetworkManager comme service systemd avec D-Bus dans l'initrd.

La valeur 'true' n'est plus prise en charge depuis la version 1.36. Auparavant il s'agissait d'un mode où NetworkManager se terminait après avoir configuré le réseau et exécutait des processus auxiliaires pour DHCP et SLAAC.

Sinon, NetworkManager exécute un service système avec D-Bus et ne se termine pas pendant le fonctionnement normal.

hostname-mode

Définit le mode de gestion du nom d'hôte. Ce paramètre n'affectera que le nom d'hôte transitoire. Si un nom d'hôte statique valide est défini, NetworkManager ignorera la mise à jour du nom d'hôte malgré la valeur de cette option. Un nom d'hôte vide ou égal à '(none)' est considéré comme invalide.

default : NetworkManager mettra à jour le nom d'hôte avec celui fourni via DHCP ou la recherche DNS inversée de l'adresse IP sur la connexion avec la

default route ou sur toute connexion dont la propriété hostname.only-from-default est définie sur « false ». Les connexions sont examinées dans l'ordre de valeur croissante de la propriété hostname.priority. En cas de plusieurs connexions ayant la même priorité, les connexions activées plus tôt sont examinées en premier. Si aucun nom d'hôte ne peut être déterminé de cette manière, le nom d'hôte sera mis à jour vers le dernier défini en dehors de NetworkManager ou vers 'localhost.localdomain'.

dhcp : C'est similaire à « default », à la différence qu'après avoir essayé d'obtenir le nom d'hôte DHCP, aucune recherche DNS inverse n'est effectuée. Notez que la sélection de cette option équivaut à définir la propriété 'hostname.from-dns-lookup' sur 'false' globalement pour toutes les connexions dans NetworkManager.conf.

none : NetworkManager ne gérera pas le nom d'hôte transitoire et ne le définira jamais.

dns

Définit le mode de traitement DNS.

Si la clé n'est pas spécifiée, la valeur par défaut est utilisée, sauf si /etc/resolv.conf est un lien symbolique vers /run/systemd/resolve/stub-resolv.conf, /run/systemd/resolve/resolv.conf, /lib/systemd/resolv.conf ou /usr/lib/systemd/resolv.conf. Dans ce cas, systemd-resolved est choisi automatiquement.

default : NetworkManager mettra à jour /etc/resolv.conf pour refléter les serveurs de noms fournis par les connexions actuellement actives. Le paramètre rc-manager (ci-dessous) contrôle la manière dont cela est fait.

dnsmasq : NetworkManager exécutera dnsmasq en tant que serveur de noms de cache local, en utilisant le « Forwarding conditionnel » si vous êtes connecté à un VPN, puis mettra à jour resolv.conf pour pointer vers le serveur de noms local. Il est possible de passer des options personnalisées à l'instance dnsmasq en les ajoutant à des fichiers dans le répertoire « /etc/NetworkManager/dnsmasq.d/ ». Notez que lorsque plusieurs serveurs amont sont disponibles, dnsmasq les contactera initialement en parallèle, puis utilisera le plus rapide pour répondre, sondant à nouveau d'autres serveurs après un certain temps. Ce comportement peut être modifié en passant les options 'all-servers' ou 'strict-order' à dnsmasq (voir la page de manuel pour plus de détails).

systemd-resolved : NetworkManager poussera la configuration DNS vers systemd-resolved

dnsconfd : NetworkManager poussera la configuration DNS vers dnsconfd


et par défaut définira ipvX.routed-dns sur
yes, de sorte que les serveurs soient contactés via les bonnes interfaces.


none : NetworkManager ne modifiera pas resolv.conf. Cela implique rc-manager unmanaged

Notez que les plugins dnsmasq, systemd-resolved et dnsconfd sont des serveurs de noms locaux en cache. Par conséquent, lorsque NetworkManager écrit /run/NetworkManager/resolv.conf et /etc/resolv.conf (conformément au paramètre rc-manager ci-dessous), le serveur de noms sera uniquement localhost. NetworkManager écrit également un fichier /run/NetworkManager/no-stub-resolv.conf qui contient les serveurs de noms originaux transmis au plugin DNS.

Lors de l'utilisation de dnsmasq, systemd-resolved et dnsconfd, les serveurs DNS ajoutés par connexion seront toujours interrogés en utilisant le périphérique sur lequel la connexion a été activée.

rc-manager

Définit le mode de gestion de resolv.conf. Cette option concerne la manière dont NetworkManager écrit dans /etc/resolv.conf, si tant est qu'il le fasse. La valeur par défaut dépend des options de compilation de NetworkManager, et cette version de NetworkManager a été compilée avec une valeur par défaut de « symlink ». Indépendamment de ce paramètre, NetworkManager écrira toujours sa version de resolv.conf dans son répertoire d'état d'exécution sous /run/NetworkManager/resolv.conf.

Si vous configurez dns=none ou rendez /etc/resolv.conf immuable avec chattr +i, NetworkManager ignorera ce paramètre et choisira toujours unmanaged (ci-dessous).

auto : Si le plugin systemd-resolved est configuré via le paramètre dns ou s'il est détecté comme plugin DNS principal, NetworkManager mettra à jour systemd-resolved sans toucher à /etc/resolv.conf. Alternativement, si resolvconf ou netconfig sont activés lors de la compilation et que le binaire respectif est trouvé, NetworkManager l'utilisera automatiquement. Notez que si vous installez ou désinstallez ces binaires, vous devez recharger le paramètre rc-manager avec SIGHUP ou systemctl reload NetworkManager. En dernier recours, il utilise l'option symlink (voir la suivante).

symlink : Si /etc/resolv.conf est un fichier régulier ou n'existe pas, NetworkManager écrira le fichier directement. Si /etc/resolv.conf est au contraire un lien symbolique, NetworkManager le laissera tel quel. Sauf si le lien symbolique pointe vers le fichier interne /run/NetworkManager/resolv.conf, auquel cas le lien symbolique sera mis à jour pour émettre une notification inotify. Cela permet à l'utilisateur d'indiquer facilement à NetworkManager de ne pas gérer /etc/resolv.conf en le remplaçant par un lien symbolique.

file : NetworkManager écrira /etc/resolv.conf en tant que fichier régulier. S'il trouve un lien symbolique vers une cible existante, il suivra le lien et mettra à jour la cible à la place. Dans aucun cas un lien symbolique existant ne sera remplacé par un fichier. Notez que les anciennes versions de NetworkManager se comportaient différemment et remplaçaient les liens symboliques dangling par un fichier plat.

resolvconf : NetworkManager exécutera resolvconf pour mettre à jour la configuration DNS.

netconfig : NetworkManager exécutera netconfig pour mettre à jour la configuration DNS.

unmanaged : ne pas toucher à /etc/resolv.conf.

none : alias déprécié pour symlink.

systemd-resolved

En outre, envoyez la configuration DNS de la connexion à systemd-resolved. La valeur par défaut est « true ».

Notez que ce paramètre n'a aucun effet si le plugin DNS principal est déjà systemd-resolved. Il est complémentaire au paramètre DNS pour configurer systemd-resolved aux côtés du plugin principal.

Si systemd-resolved est activé, soit via ce paramètre, soit via le plugin DNS principal, la vérification de connectivité résout le nom d'hôte par appareil.

debug

Liste d'options séparées par des virgules pour aider au débogage. Cette valeur sera combinée avec la variable d'environnement NM_DEBUG. Actuellement, les valeurs suivantes sont prises en charge :

RLIMIT_CORE : définit ulimit -c unlimited pour écrire les vidages de mémoire (core dumps). Attention, un vidage de mémoire peut contenir des informations sensibles telles que des mots de passe ou des paramètres de configuration.

fatal-warnings : définit g_log_set_always_fatal() pour planter et générer un vidage de mémoire sur les messages d'avertissement de glib. Cela est équivalent à l'option de ligne de commande --g-fatal-warnings.

autoconnect-retries-default

Nombre de fois où une activation de connexion doit être tentée automatiquement avant de passer à une autre. Cette valeur s'applique uniquement aux connexions qui peuvent s'auto-connecter et dont la propriété connection.autoconnect-retries est définie sur -1. Si elle n'est pas spécifiée, les connexions seront tentées 4 fois. Définir cette valeur à 1 signifie tenter l'activation une fois, sans nouvelle tentative.

firewall-backend

Le backend de pare-feu pour configurer le masquage en mode partagé. Défini sur iptables, nftables ou none. iptables et nftables nécessitent les applications iptables et nft respectivement. none signifie ignorer la configuration du pare-feu si les utilisateurs souhaitent gérer le pare-feu eux-mêmes. Si non spécifié, il sera détecté automatiquement.

iwd-config-path

Si la valeur est « auto » (la valeur par défaut), IWD est interrogé pour son répertoire d'état actuel lorsqu'il apparaît sur D-Bus -- le répertoire où IWD conserve ses fichiers de configuration réseau -- généralement /var/lib/iwd. NetworkManager tentera alors d'écrire des copies des profils de connexion Wi-Fi nouveaux ou modifiés, convertis au format IWD, dans ce répertoire, rendant ainsi les propriétés de connexion IWD modifiables. NM écrasera les fichiers existants sans en préserver le contenu.

Le chemin peut également être remplacé en pointant vers un répertoire existant et inscriptible spécifique. D'un autre côté, définir ceci sur une chaîne vide ou toute autre valeur désactive le mécanisme de conversion de profil.

Ce mécanisme permet de modifier les paramètres du profil de connexion tels que la configuration 802.1x à l'aide des clients NetworkManager. Sans cela, de tels changements n'ont aucun effet sur IWD.

migrate-ifcfg-rh

Indique si NetworkManager tente de convertir automatiquement tout profil de connexion stocké au format ifcfg-rh au format keyfile. La prise en charge d'ifcfg-rh est dépréciée et sera éventuellement supprimée. Si activée, la migration est effectuée à chaque démarrage du démon. La valeur par défaut est false.

SECTION KEYFILE

Cette section contient des options spécifiques au plugin keyfile, et n'est normalement utilisée que si vous n'utilisez aucun autre plugin spécifique à la distribution.

hostname

Cette clé est dépréciée et n'a aucun effet car le nom d'hôte est désormais stocké dans /etc/hostname ou d'autres fichiers de configuration système selon les options de compilation.

path

Emplacement où les fichiers de clés sont lus et stockés. Par défaut, il s'agit de « /etc/NetworkManager/system-connections ».

rename

NetworkManager choisit automatiquement un nom de fichier lors de la sauvegarde d'un nouveau profil sur le disque. Ce nom dépend du nom du profil (connection.id). Lors de la mise à jour du nom d'un profil, le fichier n'est pas renommé pour ne pas casser les scripts qui dépendent du nom de fichier pour le profil. En définissant cette option sur « true », NetworkManager renomme le fichier de clés lors de la mise à jour du profil, afin de suivre le nom du profil. La valeur par défaut est « false ».

unmanaged-devices

Définit les périphériques qui doivent être ignorés par NetworkManager.

Un périphérique ignoré en raison de cette option est strictement ignoré et ne peut être outrepassé en utilisant l'API comme nmcli device set $IFNAME managed yes. De plus, un périphérique qui est ignoré pour d'autres raisons, comme une règle udev, ne peut pas être géré avec cette option (par exemple, en utilisant un spécificateur except:). Ces deux points le différencient de l'option device*.managed qui, pour cette raison, peut être un meilleur choix.

Voir la section intitulée « Format de la liste des périphériques » pour la syntaxe sur la manière de spécifier un périphérique.

Exemple :

unmanaged-devices=interface-name:em4
unmanaged-devices=mac:00:22:68:1c:59:b1;mac:00:1E:65:30:D1:C4;interface-name:eth2

SECTION IFUPDOWN

Cette section contient des options spécifiques à ifupdown et n'a donc d'effet que lors de l'utilisation du plugin ifupdown.

managed

Si défini sur true, les interfaces listées dans /etc/network/interfaces sont gérées par NetworkManager. Si défini sur false, toute interface listée dans /etc/network/interfaces sera ignorée par NetworkManager. N'oubliez pas que NetworkManager contrôle la route par défaut, donc parce que l'interface est ignorée, NetworkManager peut attribuer la route par défaut à une autre interface.

La valeur par défaut est false.

SECTION

Cette section contrôle la journalisation de NetworkManager. La journalisation est très importante pour comprendre ce que fait NetworkManager. Lorsque vous signalez un bug, ne filtrez ni ne limitez inutilement le fichier journal. Activez simplement level=TRACE et domains=ALL pour tout collecter.

La méthode recommandée pour activer la journalisation consiste à utiliser un fichier /etc/NetworkManager/conf.d/95-logging.conf qui contient

[logging]
level=TRACE
domains=ALL

et redémarrez le démon avec systemctl restart NetworkManager. Reproduisez ensuite le problème. Vous pouvez trouver les journaux dans syslog (par exemple, journalctl, ou journalctl -u NetworkManager pour afficher uniquement les journaux de NetworkManager).

Tous les paramètres ici sont remplacés par les options de ligne de commande --log-level et --log-domains. La journalisation peut également être reconfigurée à l'exécution avec nmcli general logging level "$LEVEL" domains "$DOMAINS". Cependant, il est souvent intéressant d'obtenir un journal complet dès le début. En particulier, lors du débogage d'un problème, activez la journalisation de débogage dans NetworkManager.conf et redémarrez le service pour activer la journalisation détaillée tôt.

En définissant nm.debug sur la ligne de commande du noyau (provenant de /run/NetworkManager/proc-cmdline ou /proc/cmdline), la journalisation de débogage est activée. Ceci remplace à la fois les options de ligne de commande et les paramètres de NetworkManager.conf.

La journalisation de NetworkManager vise à ne pas contenir de données privées sensibles et vous devriez pouvoir partager les journaux de débogage sans problème. Néanmoins, il y aura des adresses IP et votre configuration réseau, si vous considérez cela comme privé, examinez le journal avant de le partager. Cependant, essayez de ne pas déformer le fichier journal de manière à en distordre le sens.

NetworkManager utilise syslog ou systemd-journald, selon la configuration. Dans tous les cas, les journaux de débogage sont détaillés et peuvent être limités en débit ou filtrés par le démon de journalisation. Pour systemd-journald, consultez RateLimitIntervalSec et RateLimitBurst dans le manuel de journald.conf pour savoir comment désactiver cela.

level

Le niveau de verbosité de la journalisation par défaut. L'un des OFF, ERR, WARN, INFO, DEBUG, TRACE, par ordre de verbosité.

OFF désactive toute journalisation. INFO est la verbosité par défaut pour le fonctionnement normal. TRACE est pour le débogage.

Les autres niveaux ne sont dans la plupart des cas pas utiles. Par exemple, DEBUG est entre TRACE et INFO, mais il est trop verbeux pour le fonctionnement normal et manque de messages potentiellement intéressants pour le débogage. Presque toujours, lors du débogage d'un problème ou du signalement d'un bug, collectez des journaux TRACE complets pour obtenir une image complète.

domains

Filtre les messages par leur sujet. Lors du débogage d'un problème, il est préférable de collecter tous les journaux (domaine ALL) au préalable. Les parties inutiles peuvent toujours être ignorées plus tard.

Dans le cas peu fréquent où vous souhaitez exclure certains sujets, les domaines de journalisation suivants sont disponibles : PLATFORM, RFKILL, ETHER, WIFI, BT, MB, DHCP4, DHCP6, PPP, WIFI_SCAN, IP4, IP6, AUTOIP4, DNS, VPN, SHARING, SUPPLICANT, AGENTS, SETTINGS, SUSPEND, CORE, DEVICE, OLPC, WIMAX, INFINIBAND, FIREWALL, ADSL, BOND, VLAN, BRIDGE, DBUS_PROPS, TEAM, CONCHECK, DCB, DISPATCH, AUDIT, SYSTEMD, VPN_PLUGIN, PROXY.

De plus, ces domaines spéciaux peuvent être utilisés : NONE, ALL, DEFAULT, DHCP, IP.

Vous pouvez spécifier des remplacements de niveau de journalisation par domaine en ajoutant un deux-points et un niveau de journalisation à n'importe quel domaine. Par exemple, "WIFI:DEBUG,WIFI_SCAN:OFF". Un autre exemple est ALL,VPN_PLUGIN:TRACE pour activer toute la journalisation disponible (voir ci-dessous à propos de VPN_PLUGIN).

RFKILL : opérations du sous-système RFKill
ETHER : opérations du périphérique Ethernet
WIFI : opérations du périphérique Wi-Fi
BT : opérations Bluetooth

DHCP4 : DHCP pour IPv4
DHCP6 : DHCP pour IPv6
PPP : opérations du protocole point à point
WIFI_SCAN : opérations d'analyse Wi-Fi
IP4 : opérations liées à IPv4

AUTOIP4 : opérations AutoIP
DNS : opérations liées au système de noms de domaine
VPN : connexions et opérations de réseau privé virtuel
SHARING : partage de connexion. Avec le niveau TRACE, enregistre les requêtes pour l'instance dnsmasq
SUPPLICANT : opérations liées à WPA supplicant

SETTINGS : opérations du service de paramètres/configuration

SECTION DE CONNEXION

Spécifie les valeurs par défaut pour les connexions.

Ces valeurs par défaut ne sont consultées que si la propriété correspondante par connexion le permet explicitement. Cela signifie que toutes ces propriétés correspondent à une propriété du profil de connexion (par exemple, connection.mud-url). Ce n'est que si la propriété par profil est définie sur une valeur spéciale qui indique d'utiliser la valeur par défaut que la valeur par défaut de NetworkManager.conf est consultée. Cela dépend de la propriété, quelle est la valeur spéciale qui indique le retour à la valeur par défaut, mais il s'agit généralement de quelque chose comme des valeurs vides, non définies ou des valeurs numériques spéciales comme 0 ou -1. Cela signifie que la valeur effectivement utilisée peut toujours être configurée pour chaque profil, et ces valeurs par défaut n'ont d'importance que si les valeurs par profil indiquent explicitement d'utiliser la valeur par défaut de NetworkManager.conf.

Notez que, bien que nmcli prenne en charge divers alias et fonctionnalités pratiques pour configurer les propriétés, les paramètres de cette section ne le font pas. Par exemple, les valeurs énumérées ne peuvent généralement être configurées qu'à l'aide de leur nombre magique.

[connection]
ipv6.ip6-privacy=0

Sections

Vous pouvez configurer plusieurs sections de connexion, en ayant différentes sections avec un nom qui commence toutes par "connection". Exemple :

[connection]
ipv6.ip6-privacy=0
connection.autoconnect-ports=1
vpn.timeout=120
[connection-wifi-wlan0]
match-device=interface-name:wlan0
ipv4.route-metric=50
[connection-wifi-other]
match-device=type:wifi
ipv4.route-metric=55
ipv6.ip6-privacy=1

Les sections au sein d'un même fichier sont considérées dans l'ordre d'apparition, à l'exception de la section [connection] qui est toujours considérée en dernier. Dans l'exemple ci-dessus, cet ordre est : [connection-wifi-wlan0], [connection-wlan-other], et [connection]. Lors de la vérification d'une valeur de configuration par défaut, les sections sont recherchées jusqu'à ce que la valeur demandée soit trouvée. Dans l'exemple ci-dessus, "ipv4.route-metric" pour l'interface wlan0 est défini sur 50, et pour toutes les autres interfaces de type Wi-Fi à 55. De plus, les périphériques Wi-Fi auraient les adresses privées IPv6 activées par défaut, mais les autres périphériques les auraient désactivées. Notez que "wlan0" reçoit également "ipv6.ip6-privacy=1", car bien que la section "[connection-wifi-wlan0]" corresponde au périphérique, elle ne contient pas cette propriété et la recherche continue.

Lorsqu'il y a différentes sections dans plusieurs fichiers, les sections des fichiers lus ultérieurement ont une priorité plus élevée. Ainsi, au sein d'un même fichier, la priorité des sections est de haut en bas. Entre plusieurs fichiers, les définitions ultérieures ont la préséance.

Les propriétés suivantes contrôlent davantage comment une section de connexion s'applique.

match-device

Une spécification de périphérique optionnelle qui restreint quand la section s'applique. Voir la section intitulée “Format de la liste des périphériques” pour les valeurs possibles.

stop-match

Une valeur booléenne optionnelle qui est par défaut à no. Si la section correspond (basé sur match-device), les sections suivantes ne seront pas prises en compte même si la propriété en question est absente. Dans l'exemple ci-dessus, si [connection-wifi-wlan0] avait stop-match défini sur yes, le périphérique wlan0 aurait la propriété ipv6.ip6-privacy non spécifiée. C'est-à-dire que la recherche de la propriété ne continuerait pas dans les sections de connexion [connection-wifi-o
er] ou [connection].

SECTION DEVICE

Contient la configuration persistante par appareil.

Exemple :

[device]
match-device=interface-name:eth3
managed=1

Propriétés prises en charge

Les propriétés suivantes peuvent être configurées par appareil.

managed

Indique si l'appareil est géré ou non. Un appareil peut être marqué comme géré via des règles udev (ENV{NM_UNMANAGED}), ou via la configuration de plugins (keyfile.unmanaged-devices). Ceci est une autre façon de faire. Notez que cette configuration peut être remplacée à l'exécution via D-Bus. De plus, elle a une priorité plus élevée que les règles udev.

carrier-wait-timeout

Spécifie le délai d'attente du signal de port (carrier) en millisecondes. La valeur par défaut est de 6000 millisecondes. Ce réglage existe car certains pilotes/matériels peuvent prendre beaucoup de temps pour détecter si le câble est branché.

Lorsque l'appareil perd le signal de port, NetworkManager ne réagit pas immédiatement. Au lieu de cela, il attend ce délai avant de considérer le lien comme perdu.

De plus, au démarrage, NetworkManager considère l'appareil comme occupé pendant ce temps, tant que l'appareil n'a pas de signal de port. Cela retarde le signal de fin de démarrage et NetworkManager-wait-online. Configurer cette valeur trop haut signifie bloquer NetworkManager-wait-online plus longtemps que nécessaire lors du démarrage avec le câble débranché. La configurer trop bas signifie que NetworkManager déclarera la fin du démarrage trop tôt, bien que le signal de port soit sur le point d'arriver et que l'auto-activation soit sur le point de se produire. Notez que si un profil n'a qu'une configuration IP statique ou une configuration de couche 3 désactivée, il peut déjà se connecter automatiquement sans signal de port sur l'appareil. Une fois qu'un tel profil atteint l'état d'activation complète, la fin du démarrage est considérée comme atteinte même si l'appareil n'a pas encore de signal de port.

ignore-carrier

Spécifie les appareils pour lesquels NetworkManager ignorera (partiellement) l'état du signal de port. Normalement, pour les types d'appareils qui prennent en charge la détection du signal de port, tels qu'Ethernet et InfiniBand, NetworkManager n'autorisera l'activation d'une connexion sur l'appareil que si le signal de port est présent (c'est-à-dire si un câble est branché), et il désactivera l'appareil si le signal de port chute pendant plus de quelques secondes.

Un appareil dont le signal de port est ignoré permettra l'activation de connexions sur cet appareil même lorsqu'il n'a pas de signal de port, à condition que la connexion n'utilise que des adresses IP configurées statiquement. De plus, elle permettra à toute connexion active (statique ou dynamique) de rester active sur l'appareil lorsque le signal de port est perdu.

Notez que la propriété "carrier" des NMDevices et des interfaces D-Bus des appareils reflétera toujours l'état réel de l'appareil ; c'est juste que NetworkManager n'utilisera pas cette information.

Les types maîtres comme bond, bridge et team ignorent le signal de port par défaut, tandis que les autres types d'appareils réagissent aux changements de signal de port par défaut.

Ce réglage remplace le réglage obsolète main.ignore-carrier ci-dessus.

keep-configuration

Au démarrage, NetworkManager essaie de ne pas interférer avec les interfaces déjà configurées. Il le fait en générant une connexion en mémoire basée sur la configuration actuelle de l'interface.

Si cette connexion générée correspond à l'une des connexions persistantes existantes, la connexion persistante est activée. S'il n'y a pas de correspondance, la connexion générée est activée comme "externe", ce qui signifie que la connexion est considérée comme active, mais NetworkManager ne touche pas réellement à l'interface.

Il est possible de désactiver ce comportement en définissant keep-configuration sur no. De cette façon, au démarrage, NetworkManager essaie toujours d'activer la connexion persistante la plus appropriée (celle avec la priorité d'auto-connexion la plus élevée ou, en cas d'égalité, celle activée le plus récemment).

Notez que lorsque NetworkManager est redémarré, il stocke l'état précédent dans /run/NetworkManager ; en particulier, il sauvegarde l'UUID de la connexion qui était précédemment active afin qu'elle puisse être réactivée après le redémarrage. Par conséquent, keep-configuration n'a aucun effet sur le redémarrage du service.

allowed-connections

Une liste des connexions qui peuvent être activées sur l'appareil. Voir la section "Format de liste de connexions" pour la syntaxe de spécification d'une connexion. Si cette option n'est pas spécifiée, toutes les connexions peuvent potentiellement être activées sur l'appareil, à condition que le type de connexion et d'autres paramètres correspondent.

Un cas d'utilisation notable pour ceci est de filtrer les connexions qui peuvent être activées en fonction de la manière dont elles ont été créées ; voir le mot-clé origin dans la section "Format de liste de connexions".

wifi.scan-rand-mac-address

Configure la randomisation de l'adresse MAC d'un appareil Wi-Fi pendant le scan. La valeur par défaut est oui, auquel cas une adresse MAC aléatoire et administrée localement sera utilisée. Le réglage wifi.scan-generate-mac-address-mask peut être utilisé pour influencer l'adresse MAC générée afin d'utiliser certains OUI de vendeurs. Si désactivé, l'adresse MAC pendant le scan est laissée inchangée par rapport à ce qui est configuré. Pour l'adresse MAC configurée pendant que l'appareil est associé, voir plutôt le réglage par connexion wifi.cloned-mac-address.

wifi.backend

Spécifie le backend Wi-Fi utilisé pour l'appareil. Actuellement, les options prises en charge sont wpa_supplicant et iwd (expérimental). Si non spécifié, la valeur par défaut est "wpa_supplicant".

wifi.scan-generate-mac-address-mask

Comme les réglages par connexion ethernet.generate-mac-address-mask et wifi.generate-mac-address-mask, ceci peut être utilisé pour configurer les adresses MAC générées lors du scan. Voir nm-settings-nmcli(5) pour plus de détails.

wifi.iwd.autoconnect

Si wifi.backend est iwd, régler ceci sur false force la désactivation du mécanisme d'auto-connexion de IWD pour cet appareil, et les connexions ne seront initiées que par NetworkManager, qu'elles soient commandées par un client ou automatiques. Le laisser sur true (par défaut) empêche NetworkManager d'initier automatiquement les connexions et permet à IWD d'utiliser sa logique de classement et de scan de réseau pour décider des meilleurs réseaux auxquels se connecter automatiquement ensuite. Les paramètres autoconnect-priority et autoconnect-retries des connexions seront ignorés. D'autres paramètres comme les permissions ou multi-connect peuvent interférer avec les tentatives de connexion de IWD.

sriov-num-vfs

Spécifie le nombre de fonctions virtuelles (VF) à activer pour un périphérique PCI physique prenant en charge la virtualisation d'E/S à racine unique (SR-IOV).

Sections

La section [device] fonctionne de la même manière que la section [connection]. C'est-à-dire que plusieurs sections commençant toutes par le préfixe "device" peuvent être spécifiées. Les réglages "match-device" et "stop-match" sont disponibles pour faire correspondre une section d'appareil à un appareil. L'ordre des sections multiples est également de haut en bas dans le fichier et les fichiers ultérieurs écrasent les réglages précédents. Voir "Sections" dans la section "SECTION CONNECTION" pour plus de détails.

SECTION CONNECTIVITY

Cette section contrôle la fonctionnalité optionnelle de vérification de connectivité de NetworkManager. Cela permet à NetworkManager de détecter si le système peut réellement accéder à Internet ou s'il est derrière un portail captif.

La vérification de connectivité remplit deux objectifs. D'une part, elle expose un état de connectivité sur D-Bus, que d'autres applications peuvent utiliser. Par exemple, l'aide au portail de Gnome utilise cela comme signal pour afficher une page de connexion de portail captif. L'autre utilisation est que les routes par défaut des appareils sans connectivité globale reçoivent une pénalité de +20000 à la métrique de routage. Ceci a pour but de fournir une meilleure route par défaut aux appareils qui ont une connectivité globale. Par exemple, lorsqu'ils sont connectés à WWAN et à un réseau Wi-Fi qui est derrière un portail captif, WWAN reste préféré jusqu'à la connexion.

Notez que votre distribution peut définir /proc/sys/net/ipv4/conf/*/rp_filter sur un filtrage strict. Cela fonctionne mal avec la vérification de connectivité par appareil, qui utilise SO_BINDDEVICE pour envoyer des requêtes sur tous les appareils. Un réglage rp_filter strict rejettera toute réponse et la vérification de connectivité sur toutes les routes sauf la meilleure échouera.

enabled

Indique si la vérification de connectivité est activée. Notez que pour activer la vérification de connectivité, une URI valide doit également être configurée. La valeur est vraie par défaut, mais comme l'URI n'est pas définie par défaut, la vérification de connectivité peut être désactivée. Le but principal de cette option est d'avoir un seul indicateur pour désactiver la vérification de connectivité. Notez que ce réglage peut également être défini via l'API D-Bus à l'exécution. Dans ce cas, la valeur est stockée dans le fichier /var/lib/NetworkManager/NetworkManager-intern.conf.

uri

L'URI d'une page Web à demander périodiquement lors de la vérification de la connectivité. Cette page doit renvoyer l'en-tête "X-NetworkManager-Status" avec la valeur "online". Alternativement, le contenu de son corps doit être défini sur "NetworkManager is online". La vérification du contenu du corps peut être contrôlée par l'option de réponse. Si cette option est vide ou manquante, la vérification de connectivité est désactivée.

interval

Spécifié en secondes ; contrôle la fréquence de vérification de la connectivité lorsqu'une connexion réseau existe. S'il est défini sur 0, la vérification de connectivité est désactivée. S'il est manquant, la valeur par défaut est 300 secondes.

timeout

Spécifié en secondes ; contrôle le temps d'attente d'une réponse avant que la connectivité ne soit marquée comme limitée. S'il est manquant, la valeur par défaut est 20 secondes.

response

S'il est défini, contrôle le contenu du corps que NetworkManager vérifie lors de la demande de l'URI pour la vérification de connectivité. Notez que cela compare uniquement que la réponse HTTP commence par le texte spécifié, cela ne compare pas la chaîne exacte. Ce comportement pourrait changer à l'avenir, alors évitez de vous y fier. S'il est manquant, la réponse par défaut est "NetworkManager is online". S'il est défini sur vide, le serveur HTTP est censé répondre avec le code d'état 204 ou n'envoyer aucun données.

SECTION GLOBAL-DNS

Cette section spécifie les paramètres DNS qui sont appliqués globalement. Ils remplacent les options équivalentes définies dans les connexions individuelles, les rendant ainsi ignorées. Si une section [global-dns-domain-*] est définie, mais pas cette section, une section [global-dns] vide est supposée, écrasant ainsi également les configurations spécifiques aux connexions.

searches

Une liste de domaines de recherche à utiliser du
ring hostname lookup.

options

Une liste d'options à passer au résolveur de nom d'hôte.

resolve-mode

Chaîne indiquant comment les serveurs DNS récupérés de la configuration globale et des connexions doivent être utilisés. backup - Indique qu'ils peuvent être librement fusionnés et utilisés aux mêmes fins. prefer - Interdit que les serveurs DNS récupérés des connexions soient utilisés pour des requêtes générales qui ne sont pas des sous-domaines de domaines définis par la connexion. exclusive - Interdit l'utilisation des serveurs DNS de la connexion pour toute requête. Actuellement pertinent uniquement pour le plugin Dnsconfd.

certification-authority

Chaîne spécifiant le chemin absolu vers le paquet de certificats d'autorité de certification qui doit être utilisé pour la validation des certificats présentés par les serveurs DNS lorsque le DNS chiffré est utilisé. Actuellement pertinent uniquement pour le plugin Dnsconfd.

SECTIONS GLOBAL-DNS-DOMAIN

Les sections dont le nom commence par le préfixe "global-dns-domain-" permettent de définir la configuration DNS globale pour des domaines spécifiques. La partie du nom de section après "global-dns-domain-" spécifie le nom de domaine auquel s'applique une section (par exemple, une section pourrait être nommée "global-dns-domain-foobar.com"). Les domaines plus spécifiques ont la priorité sur ceux moins spécifiques, et le domaine par défaut est représenté par le caractère générique "*". Pour être valides, les domaines DNS globaux doivent inclure une section pour le domaine par défaut "*". Lorsque les domaines DNS globaux sont valides, les serveurs et domaines nommés globalement remplacent ceux des connexions actives. Si un domaine DNS global est défini mais qu'une section [global-dns] ne l'est pas, une section [global-dns] vide est supposée, écrasant ainsi également leurs configurations spécifiques aux connexions.

servers

Une liste d'adresses de serveurs DNS à utiliser pour le domaine donné. Chaque serveur peut être spécifié soit comme une adresse IP simple, soit avec une syntaxe d'URI. Lorsqu'il est spécifié comme URI, les formes suivantes sont prises en charge :
dns+udp://ADDRESS[:PORT] : DNS
dns+tls://ADDRESS[:PORT][#SERVERNAME] : DNS sur TLS

ADDRESS est une adresse IPv4 ou IPv6. Lorsqu'il s'agit d'IPv6, elle doit être entourée de crochets ('[' et ']'). Lorsqu'il s'agit d'une adresse locale de liaison IPv6, l'adresse doit être suivie d'un signe pourcentage ('%') et du nom d'une interface.

options

Une liste d'options DNS spécifiques au domaine. Non utilisées pour le moment.

SECTIONS .CONFIG

Ceci est une section spéciale qui contient des options s'appliquant au fichier de configuration qui contient l'option.

enable

Par défaut à "true". Si "false", le fichier de configuration sera ignoré lors du chargement. Notez que le fichier de configuration principal NetworkManager.conf ne peut pas être désactivé. 
# ignorer toujours le chargement du fichier de configuration
[.config]
enable=false

Vous pouvez également faire correspondre la version de NetworkManager. Par exemple, les configurations suivantes sont valides :

# charger uniquement sur la version 1.0.6
[.config]
enable=nm-version:1.0.6
# charger sur toutes les versions 1.0.x, mais pas 1.2.x
[.config]
enable=nm-version:1.0
# charger uniquement sur les versions >= 1.1.6. Cela ne correspond pas
# à la version 1.2.0 ou 1.4.4. Seul le dernier chiffre est pris en compte.
[.config]
enable=nm-version-min:1.1.6
# charger uniquement sur les versions >= 1.2. Contrairement à l'exemple précédent
# cela correspond également à 1.2.0, 1.2.10, 1.4.4, etc.
[.config]
enable=nm-version-min:1.2
# Faire correspondre la version maximale autorisée. L'exemple correspond
# aux versions 1.2.0, 1.2.2, 1.2.4. Encore une fois, seul le dernier chiffre de version
# est autorisé à être plus petit. Ainsi, cela ne correspondrait pas à 1.1.10.
[.config]
enable=nm-version-max:1.2.6

Vous pouvez également faire correspondre la valeur de la variable d'environnement NM_CONFIG_ENABLE_TAG, comme ceci :

# charger uniquement le fichier lors de l'exécution de NetworkManager avec
# la variable d'environnement "NM_CONFIG_ENABLE_TAG=TAG1"
[.config]
enable=env:TAG1

Plusieurs correspondances peuvent être spécifiées. La configuration sera activée si l'un des prédicats correspond ("ou"). Le préfixe spécial "except:" peut être utilisé pour nier la correspondance. Notez que si un prédicat d'exception correspond, la configuration entière sera désactivée. Autrement dit, un prédicat d'exception l'emporte toujours sur les autres prédicats. Si le paramètre ne consiste qu'en des correspondances "except:" et qu'aucune des conditions négatives n'est satisfaite, la configuration est toujours activée.

# activer la configuration soit lorsque la variable d'environnement
# est présente, soit lorsque la version est au moins 1.2.0.
[.config]
enable=env:TAG2,nm-version-min:1.2
# activer la configuration pour la version >= 1.2.0, mais la désactiver
# lorsque la variable d'environnement est définie sur "TAG3"
[.config]
enable=except:env:TAG3,nm-version-min:1.2
# activer la configuration sur >= 1.3, >= 1.2.6 et >= 1.0.16.
# Utile si une certaine fonctionnalité n'est présente que depuis ces versions.
[.config]
enable=nm-version-min:1.3,nm-version-min:1.2.6,nm-version-min:1.0.16

PLUGINS

Plugins de configuration pour la lecture et l'écriture des profils de connexion. Le nombre de plugins disponibles dépend de la distribution.

keyfile

Le plugin keyfile est le plugin générique qui prend en charge tous les types de connexion et toutes les fonctionnalités de NetworkManager. Il écrit les fichiers dans un format .ini dans /etc/NetworkManager/system-connections. Voir nm-settings-keyfile(5) pour plus de détails sur le format du fichier.

Le fichier de connexion stocké peut contenir des mots de passe, des secrets et des clés privées en texte brut, il sera donc rendu lisible uniquement par root, et le plugin ignorera les fichiers lisibles ou modifiables par tout utilisateur ou groupe autre que root. Voir "Secret flag types" dans nm-settings-nmcli(5) pour éviter de stocker des mots de passe en texte brut.

Ce plugin est toujours actif et sera automatiquement utilisé pour stocker toutes les connexions qui ne sont pas prises en charge par un autre plugin actif.

ifcfg-rh

Ce plugin est maintenant obsolète ; il peut être utilisé sur les distributions Fedora et Red Hat Enterprise Linux pour lire et écrire la configuration à partir des fichiers standard /etc/sysconfig/network-scripts/ifcfg-*. Il prend actuellement en charge la lecture des connexions Ethernet, Wi-Fi, InfiniBand, VLAN, Bond, Bridge et Team. L'activation de ifcfg-rh active implicitement le plugin ibft, s'il est disponible. Cela peut être désactivé en ajoutant no-ibft. Voir /usr/share/doc/initscripts/sysconfig.txt et nm-settings-ifcfg-rh(5) pour plus d'informations sur le format des fichiers ifcfg.

ifupdown

Ce plugin est utilisé sur les distributions Debian et Ubuntu, et lit les connexions Ethernet et Wi-Fi à partir de /etc/network/interfaces.

Ce plugin est en lecture seule ; toutes les connexions (de quelque type que ce soit) ajoutées depuis NetworkManager lorsque vous utilisez ce plugin seront enregistrées à l'aide du plugin keyfile à la place.

ibft, no-ibft

Ces plugins sont obsolètes et leur sélection n'a aucun effet. Ceci est maintenant géré par nm-initrd-generator.

ifcfg-suse, ifnet

Ces plugins sont obsolètes et leur sélection n'a aucun effet. Le plugin keyfile doit être utilisé à la place.

ANNEXE

Format de liste de périphériques

Les options de configuration main.no-auto-default, main.ignore-carrier, keyfile.unmanaged-devices, connection*.match-device et device*.match-device sélectionnent les périphériques en fonction d'une liste de correspondances. Les périphériques peuvent être spécifiés en utilisant le format suivant :

*

Correspond à chaque périphérique.

IFNAME

Correspondance sensible à la casse du nom d'interface du périphérique. Les caractères génériques ne sont pas pris en charge.

HWADDR

Correspond à l'adresse MAC permanente du périphérique. Les caractères génériques ne sont pas pris en charge

interface-name:IFNAME, interface-name:~IFNAME

Correspondance sensible à la casse du nom d'interface du périphérique. La substitution de caractères génériques simple est prise en charge avec * et ?. Les plages et les échappements ne sont pas pris en charge.

interface-name:=IFNAME

Correspondance sensible à la casse du nom d'interface du périphérique. La substitution de caractères génériques est désactivée et IFNAME est pris littéralement.

mac:HWADDR

Correspond à l'adresse MAC permanente du périphérique. Les caractères génériques ne sont pas pris en charge

s390-subchannels:HWADDR

Correspond au périphérique en fonction de l'adresse du sous-canal. Les caractères génériques ne sont pas pris en charge

type:TYPE

Correspond au type de périphérique. Les noms de type valides sont ceux rapportés par "nmcli -f GENERAL.TYPE device show". Les caractères génériques ne sont pas pris en charge.

driver:DRIVER

Correspond au pilote du périphérique tel que rapporté par "nmcli -f GENERAL.DRIVER,GENERAL.DRIVER-VERSION device show". "DRIVER" doit correspondre exactement au nom du pilote et ne prend pas en charge les caractères génériques. Facultativement, une version du pilote peut être spécifiée séparée par '/'. Les caractères génériques sont pris en charge pour la version.

dhcp-plugin:DHCP

Correspond au plugin DHCP configuré "main.dhcp".

except:SPEC

Correspondance négative d'un périphérique. SPEC doit être explicitement qualifié avec un préfixe tel que interface-name:. Une correspondance négative a une priorité plus élevée que les correspondances positives ci-dessus.

S'il existe une liste composée uniquement de correspondances négatives, le comportement est le même que s'il y avait également une correspondance universelle (*). Cela signifie que si aucune des correspondances négatives n'est satisfaite, le résultat global est toujours une correspondance positive. Cela signifie que "except:interface-name:eth0" est identique à "*,except:interface-name:eth0".

SPEC[,;]SPEC

Plusieurs spécifications peuvent être concaténées avec des virgules ou des points-virgules. L'ordre n'a pas d'importance car les correspondances sont soit inclusives, soit négatives (except:), les correspondances négatives ayant une priorité plus élevée.

Le caractère antislash est pris en charge pour échapper les séparateurs ';' et ',', et pour exprimer des caractères spéciaux tels que nouvelle ligne ('\n'), tabulation ('\t'), espace blanc ('\s') et antislash ('\\'). La substitution de caractères génériques des noms d'interface ne peut pas être échappée. Les espaces blancs ne sont pas des séparateurs mais seront supprimés entre deux spécifications (sauf s'ils sont échappés comme '\s').

Exemple :

interface-name:em4
mac:00:22:68:1c:59:b1;mac:00:1E:65:30:D1:C4;interface-name:eth2
interface-name:vboxnet*,sauf:interface-name:vboxnet2 *,sauf:mac:00:22:68:1c:59:b1

Format de la liste de connexions

Les connexions peuvent être spécifiées en utilisant le format suivant :

*

Correspond à toutes les connexions.

uuid:UUID

Correspond à la connexion par son UUID, par exemple "uuid:83037490-1d17-4986-a397-01f1db3a7fc2"

id:ID

Correspond à la connexion par son nom.

origin:ORIGIN

Correspond à la connexion par son origine, stockée dans la balise org.freedesktop.NetworkManager.origin des paramètres utilisateur. Par exemple, utilisez "sauf:origin:nm-initrd-generator" pour interdire l'activation des connexions créées par le générateur initrd.

sauf:SPEC

Correspondance négative d'une connexion. Une correspondance négative a une priorité plus élevée que les correspondances positives ci-dessus.

S'il existe une liste composée uniquement de correspondances négatives, le comportement est le même que s'il y avait également une correspondance globale (*). Cela signifie que si aucune des correspondances négatives n'est satisfaite, le résultat global reste une correspondance positive.

SPEC[,;]SPEC

Plusieurs spécifications peuvent être concaténées avec des virgules ou des points-virgules. L'ordre n'a pas d'importance car les correspondances sont soit inclusives, soit négatives (sauf:), les correspondances négatives ayant une priorité plus élevée.

La barre oblique inverse est prise en charge pour échapper les séparateurs ';' et ',', ainsi que pour exprimer des caractères spéciaux tels que le saut de ligne ('\n'), la tabulation ('\t'), l'espace blanc ('\s') et la barre oblique inverse ('\\'). L'espace blanc n'est pas un séparateur mais sera supprimé entre deux spécifications (sauf s'il est échappé en tant que '\s').
