NOM

nm-settings-nmcli - Description des paramètres et propriétés des profils de connexion NetworkManager pour nmcli

DESCRIPTION

NetworkManager est basé sur le concept de profils de connexion, parfois appelés simplement connexions. Ces profils de connexion contiennent une configuration réseau. Lorsque NetworkManager active un profil de connexion sur un périphérique réseau, la configuration est appliquée et une connexion réseau active est établie. Les utilisateurs sont libres de créer autant de profils de connexion qu'ils le jugent nécessaire. Ils disposent ainsi de configurations réseau flexibles pour différents besoins réseau.

NetworkManager fournit une API pour configurer les profils de connexion, pour les activer afin de configurer le réseau, et pour inspecter la configuration réseau actuelle. L'outil en ligne de commande nmcli est une application cliente pour NetworkManager qui utilise cette API. Voir nmcli(1) pour plus de détails.

Avec des commandes comme nmcli connection add, nmcli connection modify et nmcli connection show, les profils de connexion peuvent être créés, modifiés et inspectés. Un profil est constitué de propriétés. Sur D-Bus, cela suit le format décrit par nm-settings-dbus(5), tandis que cette page de manuel décrit le format des paramètres tel qu'il est attendu par nmcli.

Les paramètres et propriétés listés dans les tableaux ci-dessous décrivent toutes les options de configuration de connexion disponibles. Cependant, notez que tous les paramètres ne sont pas applicables à tous les types de connexion. L'éditeur de connexion nmcli connection dispose également d'une commande intégrée describe qui peut afficher la description des paramètres et propriétés particuliers de cette page.

Le paramètre et la propriété peuvent être abrégés à condition qu'ils soient uniques. La liste ci-dessous montre également les alias qui peuvent être utilisés sans qualification au lieu du nom complet. Par exemple, connection.interface-name et ifname font référence à la même propriété.

connection setting

Paramètres généraux du profil de connexion.

Propriétés :

connection.auth-retries

Le nombre de tentatives pour l'authentification. Zéro signifie essayer indéfiniment ; -1 signifie utiliser une valeur globale par défaut. Si la valeur globale par défaut n'est pas définie, les tentatives d'authentification sont faites 3 fois avant d'échouer la connexion.

Actuellement, cela ne s'applique qu'à l'authentification 802-1x.

Format : entier

Valeurs valides : -1 - 2147483647

connection.autoconnect

Alias : autoconnect

Indique si la connexion doit être automatiquement établie par NetworkManager lorsque les ressources nécessaires sont disponibles. VRAI pour activer automatiquement la connexion, FAUX pour nécessiter une intervention manuelle pour activer la connexion.

L'autoconnect se produit lorsque les circonstances sont appropriées. Cela signifie, par exemple, que le périphérique est actuellement géré et inactif. L'autoconnect ne remplace donc jamais ou n'entre pas en concurrence avec un profil déjà actif.

Notez que l'autoconnect n'est pas implémenté pour les profils VPN. Voir les « secondaries » comme alternative pour connecter automatiquement les profils VPN.

Si plusieurs profils sont prêts pour l'autoconnect sur le même périphérique, celui ayant la meilleure « connection.autoconnect-priority » est choisi. Si les priorités sont égales, alors le profil connecté le plus récemment est activé. Si les profils n'ont pas été connectés auparavant ou si leur « connection.timestamp » est identique, le choix est indéfini.

Selon « connection.multi-connect », un profil peut (s'auto)connecter une seule fois à la fois ou plusieurs fois.

Format : booléen

Valeurs valides : true/yes/on, false/no/off

connection.autoconnect-ports

Indique si les ports de cette connexion doivent être automatiquement activés lorsque NetworkManager active cette connexion. Cela n'a un effet réel que pour les connexions contrôleur. Les propriétés « autoconnect », « autoconnect-priority » et « autoconnect-retries » ne sont pas liées à ce paramètre. Les valeurs permises sont : 0 : laisser les connexions de port inchangées, 1 : activer toutes les connexions de port avec cette connexion, -1 : par défaut. Si -1 (par défaut) est défini, la valeur globale connection.autoconnect-ports est lue pour déterminer la valeur réelle. Si elle est également par défaut, cela revient à 0.

Format : choix (NMTernary)

Valeurs valides : default (-1), false (0), true (1)

connection.autoconnect-priority

La priorité d'autoconnect dans la plage -999 à 999. Si la connexion est configurée pour l'autoconnect, les connexions avec une priorité plus élevée seront préférées. Le nombre le plus élevé signifie une priorité plus élevée. La valeur par défaut est 0. Notez que cette propriété n'est pertinente que s'il y a plus d'un profil candidat à sélectionner pour l'autoconnect. En cas d'égalité de priorité, le profil utilisé le plus récemment est choisi.

Format : entier

Valeurs valides : -999 - 999

connection.autoconnect-retries

Le nombre de fois qu'une connexion doit être essayée lors de l'auto-activation avant d'abandonner. Zéro signifie indéfiniment, -1 signifie la valeur globale par défaut (4 fois si non redéfinie). Définir cette valeur à 1 signifie essayer l'activation une seule fois avant de bloquer l'autoconnect. Notez qu'après un délai d'attente, NetworkManager essaiera à nouveau l'autoconnect.

Format : entier

Valeurs valides : -1 - 2147483647

Valeurs spéciales : default (-1), forever (0)

connection.autoconnect-slaves

Indique si les ports de cette connexion doivent être automatiquement activés lorsque NetworkManager active cette connexion. Cela n'a un effet réel que pour les connexions contrôleur. Les propriétés « autoconnect », « autoconnect-priority » et « autoconnect-retries » ne sont pas liées à ce paramètre. Les valeurs permises sont : 0 : laisser les connexions de port inchangées, 1 : activer toutes les connexions de port avec cette connexion, -1 : par défaut. Si -1 (par défaut) est défini, la valeur globale connection.autoconnect-slaves est lue pour déterminer la valeur réelle. Si elle est également par défaut, cela revient à 0.

Déprécié depuis 1.46. Utilisez « autoconnect-ports » à la place, ceci n'est qu'un alias.

Format : choix (NMSettingConnectionAutoconnectSlaves)

Valeurs valides : default (-1), no (0), yes (1)

connection.controller

Alias : controller

Nom d'interface du périphérique contrôleur ou UUID de la connexion contrôleur.

Format : chaîne

connection.dns-over-tls

Indique si DNSOverTls (dns-over-tls) est activé pour la connexion. DNSOverTls est une technologie qui utilise TLS pour chiffrer le trafic DNS.

Les valeurs permises sont : « yes » (2) utiliser DNSOverTls et désactiver le fallback, « opportunistic » (1) utiliser DNSOverTls mais autoriser le fallback vers une résolution non chiffrée, « no » (0) ne jamais utiliser DNSOverTls. Si non spécifié, « default » dépend du plugin utilisé. Systemd-resolved utilise le paramètre global.

Cette fonctionnalité nécessite un plugin qui prend en charge DNSOverTls. Sinon, le paramètre n'a aucun effet. Un de ces plugins est dns-systemd-resolved.

Format : choix (NMSettingConnectionDnsOverTls)

Valeurs valides : default (-1), no (0), opportunistic (1), yes (2)

connection.down-on-poweroff

Indique si la connexion sera désactivée avant l'arrêt du système. La valeur par défaut est « default » (-1). Lorsque la valeur par défaut est spécifiée, la valeur globale de la configuration NetworkManager est recherchée ; si elle n'est pas définie, elle est considérée comme « no » (0).

Format : choix (NMSettingConnectionDownOnPoweroff)

Valeurs valides : default (-1), no (0), yes (1)

connection.gateway-ping-timeout

Si supérieur à zéro, retarde le succès de l'adressage IP jusqu'à ce que le délai soit atteint, ou qu'une passerelle IP réponde à un ping.

Format : entier

Valeurs valides : 0 - 600

connection.id

Alias : con-name

Un identifiant unique et lisible par l'homme pour la connexion, comme « Travail Wi-Fi » ou « T-Mobile 3G ».

Format : chaîne

connection.interface-name

Alias : ifname

Le nom de l'interface réseau à laquelle cette connexion est liée. Si non défini, la connexion peut être attachée à n'importe quelle interface du type approprié (sous réserve des restrictions imposées par d'autres paramètres).

Pour les périphériques logiciels, cela spécifie le nom du périphérique créé.

(par exemple, haut débit mobile ou Ethernet USB), cette propriété ne devrait pas être utilisée. La définition de cette propriété restreint les interfaces avec lesquelles une connexion peut être utilisée et, si les noms d'interface changent ou sont réorganisés, la connexion peut être appliquée à la mauvaise interface.

Format : chaîne de caractères

connection.ip-ping-addresses

La propriété spécifie une liste d'adresses IP cibles pour le ping. Lorsque plusieurs cibles sont définies, NetworkManager lancera plusieurs processus de ping en parallèle. Cette propriété ne peut être définie que si connection.ip-ping-timeout est défini. La valeur ip-ping-timeout est utilisée pour retarder le succès de l'adressage IP jusqu'à ce que soit le délai spécifié (en secondes) soit atteint, soit qu'une adresse IP cible réponde à un ping. La configuration de "ip-ping-addresses" peut retarder l'atteinte de network-online.target de systemd en raison de l'attente de la fin des opérations de ping ou de leur expiration.

Format : liste d'adresses IPv4 ou IPv6

connection.ip-ping-addresses-require-all

La propriété détermine s'il suffit qu'une vérification de ping réussisse parmi "ip-ping-addresses", ou si toutes les vérifications de ping doivent réussir pour "ip-ping-addresses".

Format : choix (NMTernary)

Valeurs valides : default (-1), false/no (0), true/yes (1)

connection.ip-ping-timeout

Si supérieur à zéro, retarde le succès de l'adressage IP jusqu'à ce que soit le délai spécifié (en secondes) soit atteint, soit qu'une adresse IP cible réponde à un ping. La propriété spécifie le délai d'attente pour "ip-ping-addresses". Cette propriété est incompatible avec "gateway-ping-timeout", vous ne pouvez pas définir ces deux propriétés en même temps.

Format : entier

Valeurs valides : 0 - 600

connection.lldp

Indique si LLDP est activé pour la connexion.

Format : choix (NMSettingConnectionLldp)

Valeurs valides : default (-1), disable (0), enable-rx/enable (1)

connection.llmnr

Indique si la résolution de noms multicast en lien local (LLMNR) est activée pour la connexion. LLMNR est un protocole basé sur le format de paquets du système de noms de domaine (DNS) qui permet aux hôtes IPv4 et IPv6 d'effectuer une résolution de noms pour les hôtes sur le même lien local.

Les valeurs autorisées sont : "yes" (2) enregistre le nom d'hôte et la résolution pour la connexion, "no" (0) désactive LLMNR pour l'interface, "resolve" (1) n'enregistre pas le nom d'hôte mais autorise la résolution des noms d'hôtes LLMNR. Si non spécifié, "default" dépend finalement du plugin DNS (qui, pour systemd-resolved, signifie actuellement "yes").

Cette fonctionnalité nécessite un plugin qui supporte LLMNR. Sinon, le réglage n'a aucun effet. Un de ces plugins est dns-systemd-resolved.

Format : choix (NMSettingConnectionLlmnr)

Valeurs valides : default (-1), no (0), resolve (1), yes (2)

connection.master

Alias : master

Nom d'interface du périphérique contrôleur ou UUID de la connexion contrôleur.

Déprécié depuis 1.46. Utilisez "controller" à la place, ceci est juste un alias.

Format : chaîne de caractères

connection.mdns

Indique si mDNS est activé pour la connexion.

Les valeurs autorisées sont : "yes" (2) enregistre le nom d'hôte et la résolution pour la connexion, "no" (0) désactive mDNS pour l'interface, "resolve" (1) n'enregistre pas le nom d'hôte mais autorise la résolution des noms d'hôtes mDNS et "default" (-1) pour autoriser la recherche d'une valeur globale par défaut dans NetworkManager.conf. Si non spécifié, "default" dépend finalement du plugin DNS.

Cette fonctionnalité nécessite un plugin qui supporte mDNS. Sinon, le réglage n'a aucun effet. Actuellement, le seul plugin DNS supporté est systemd-resolved. Pour systemd-resolved, la valeur par défaut est configurable via le réglage MulticastDNS= dans resolved.conf.

Format : choix (NMSettingConnectionMdns)

Valeurs valides : default (-1), no (0), resolve (1), yes (2)

connection.metered

Indique si la connexion est limitée en données (mesurée).

Lors de la mise à jour de cette propriété sur une connexion actuellement activée, le changement prend effet immédiatement.

Format : ternaire

Valeurs valides : true/yes/on, false/no/off, default/unknown

connection.mptcp-flags

Indique s'il faut configurer les points d'extrémité MPTCP et les drapeaux d'adresse. Si MPTCP est activé dans NetworkManager, il configurera les adresses de l'interface comme points d'extrémité MPTCP. Notez que les adresses de bouclage IPv4 (127.0.0.0/8), les adresses locales de lien IPv4 (169.254.0.0/16), l'adresse de bouclage IPv6 (::1), les adresses locales de lien IPv6 (fe80::/10), les adresses locales uniques IPv6 (ULA, fc00::/7) et les adresses d'extension de confidentialité IPv6 (rfc3041, ipv6.ip6-privacy) seront exclues de la configuration en tant que points d'extrémité.

Si "disabled" (0x1), le traitement MPTCP pour l'interface est désactivé et aucun point d'extrémité n'est enregistré.

Le drapeau "enabled" (0x2) signifie que le traitement MPTCP est activé. Ce drapeau peut également être implicitement défini par la présence d'autres drapeaux.

Même lorsqu'il est activé, le traitement MPTCP sera par défaut toujours désactivé sauf si le sysctl "/proc/sys/net/mptcp/enabled" est activé. NetworkManager ne modifie pas le sysctl et cela incombe à l'administrateur ou à la distribution. Pour configurer des points d'extrémité même si le sysctl est désactivé, le drapeau "also-without-sysctl" (0x4) peut être utilisé. Dans ce cas, NetworkManager ne regarde pas le sysctl et configure les points d'extrémité indépendamment.

Même lorsqu'il est activé, NetworkManager ne configurera des points d'extrémité MPTCP pour une famille d'adresses donnée que s'il existe une route par défaut unicast (0.0.0.0/0 ou ::/0) dans la table de routage principale. Le drapeau "also-without-default-route" (0x8) peut outrepasser cela.

Lorsque le traitement MPTCP est activé, les points d'extrémité sont configurés avec les drapeaux d'adresse spécifiés "signal" (0x10), "subflow" (0x20), "backup" (0x40), "fullmesh" (0x80). Voir le manuel ip-mptcp(8) pour des informations supplémentaires sur les drapeaux.

Si les drapeaux sont à zéro (0x0), la valeur par défaut globale de la connexion provenant de NetworkManager.conf est respectée. Si toujours non spécifié, le repli est "enabled,subflow". Notez que cela signifie que MPTCP est par défaut effectué en fonction du sysctl "/proc/sys/net/mptcp/enabled".

NetworkManager ne modifie pas les limites MPTCP ni n'active MPTCP via "/proc/sys/net/mptcp/enabled". Il s'agit d'une configuration d'hôte que l'administrateur peut modifier via sysctl et ip-mptcp.

Le filtrage de chemin inverse strict (rp_filter) interrompt de nombreux cas d'utilisation de MPTCP. Ainsi, lorsque le traitement MPTCP pour les adresses IPv4 sur l'interface est activé, NetworkManager assouplira le filtrage de chemin inverse strict (1) en réglage lâche (2).

Format : drapeaux (NMMptcpFlags)

Valeurs valides : none/default (0x0), disabled (0x1), enabled (0x2), also-without-sysctl (0x4), also-without-default-route (0x8), signal (0x10), subflow (0x20), backup (0x40), fullmesh (0x80)

connection.mud-url

Si configuré, définit l'URL de Description d'Utilisation par le Fabricant (MUD) qui pointe vers les politiques réseau recommandées par le fabricant pour les appareils IoT. Elle est transmise comme option DHCPv4 ou DHCPv6. La valeur doit être une URL valide commençant par "https://".

La valeur spéciale "none" est autorisée pour indiquer qu'aucun URL MUD n'est utilisé.

Si la valeur par profil n'est pas spécifiée (par défaut), une valeur globale par défaut de la connexion est consultée. Si toujours non spécifiée, la valeur par défaut finale est "none".

Format : chaîne de caractères

connection.multi-connect

Spécifie si le profil peut être actif plusieurs fois à un moment donné. La valeur est de type NMConnectionMultiConnect.

Format : choix (NMConnectionMultiConnect)

Valeurs valides : default (0), single (1), manual-multiple (2), multiple (3)

connection.permissions

Un tableau de chaînes définissant les droits d'accès qu'un utilisateur donné a sur cette connexion. Si c'est NULL ou vide, tous les utilisateurs sont autorisés à accéder à cette connexion ; sinon, les utilisateurs sont autorisés si et seulement s'ils sont dans cette liste. Lorsque ce n'est pas vide, la connexion ne peut être active que lorsqu'un des utilisateurs spécifiés est connecté à une session active. Chaque entrée est de la forme "[type]:[id]:[réservé]" ; par exemple, "user:dcbw:blah".

À l'heure actuelle, seul le type "user" est autorisé. Toute autre valeur est ignorée et réservée pour une utilisation future. [id] est le nom d'utilisateur auquel cette permission fait référence, et ne peut pas contenir le caractère ":". Toute information [réservé] présente doit être ignorée et est réservée pour une utilisation future. [type], [id] et [réservé] doivent tous être des UTF-8 valides.

Format : liste de chaînes de caractères

connection.port-type

Alias : port-type

Nom de réglage du type de périphérique de la connexion contrôleur de ce port (par exemple, "bond"), ou NULL si cette connexion n'est pas un port.

Format : chaîne de caractères

Valeurs valides : bond, bridge, ovs-bridge, ovs-port, team, vrf

connection.secondaries

Liste des UUID de connexions qui devraient être activées lorsque la connexion de base elle-même est activée. Actuellement, seules les connexions VPN sont supportées.

Format : liste de chaînes de caractères

connection.slave-type

Alias : slave-type

Nom de réglage du type de périphérique de la connexion contrôleur de ce port (par exemple, "bond"), ou NULL si cette connexion n'est pas un port.

Déprécié depuis 1.46. Utilisez "port-type" à la place, ceci est juste un alias.

Format : chaîne de caractères

Valeurs valides : bond, bridge, ovs-bridge, ovs-port, team, vrf

connection.stable-id

Ceci représente l'identité de la connexion utilisée à diverses fins. Il permet de configurer plusieurs profils pour partager l'identité. De plus, l'identifiant stable peut contenir des espaces réservés qui sont substitués dynamiquement et de manière déterministe en fonction du contexte.

L'identifiant stable est utilisé pour générer des adresses privées stables IPv6 avec ipv6.addr-gen-mode=stable-privacy. Il est également utilisé pour amorcer l'adresse MAC clonée générée pour ethernet.cloned-mac-address=stable et wifi.cloned-mac-address=stable. Il est également utilisé pour dériver l'identifiant client DHCP avec ipv4.dhcp-client-id=stable, le DUID DHCPv6 avec ipv6.dhcp-duid=stable-[llt,ll,uuid] et l'IAID DHCP avec ipv4.iaid=stable et ipv6.iaid=stable.

Notez que, en fonction du contexte dans lequel il est utilisé, d'autres paramètres sont également amorcés dans l'algorithme de génération. Par exemple, une clé par hôte est couramment incluse, de sorte que différents systèmes finissent par générer des identifiants différents. Ou avec ipv6.addr-gen-mode=stable-privacy, également le nom du périphérique

est inclus, de sorte que différentes interfaces produisent différentes adresses. La clé par hôte est l'identité de votre machine et est stockée dans /var/lib/NetworkManager/secret_key. Voir le manuel de NetworkManager(8) concernant la clé secrète et l'identité de l'hôte.

Le caractère '$' est traité de manière spéciale pour effectuer des substitutions dynamiques au moment de l'activation. Actuellement, sont supportés : "<tt>${CONNECTION}</tt>", "<tt>${DEVICE}</tt>", "<tt>${MAC}</tt>", "<tt>${NETWORK_SSID}</tt>", "<tt>${BOOT}</tt>", "<tt>${RANDOM}</tt>". Ceux-ci créent efficacement des identifiants uniques par connexion, par appareil, par SSID, par démarrage ou à chaque fois. <tt>${CONNECTION}</tt> utilise l'UUID de la connexion du profil, <tt>${DEVICE}</tt> utilise le nom de l'interface de l'appareil et <tt>${MAC}</tt> l'adresse MAC permanente de l'appareil. <tt>${NETWORK_SSID}</tt> utilise le SSID pour les réseaux Wi-Fi et se rabat sur <tt>${CONNECTION}</tt> pour les autres réseaux. Tous les modèles non reconnus suivant '$' sont traités littéralement, mais sont réservés pour un usage futur. Il est donc conseillé d'éviter '$' ou de l'échapper en tant que "$$". Par exemple, définissez-le sur "<tt>${CONNECTION}-${BOOT}-${DEVICE}</tt>" pour créer un identifiant unique pour cette connexion qui change à chaque redémarrage et diffère en fonction de l'interface où le profil s'active.

Si la valeur n'est pas définie, un défaut global de connexion est consulté. Si la valeur n'est toujours pas définie, le défaut est "<tt>default${CONNECTION}</tt>" pour générer un identifiant unique par profil de connexion.

Format : chaîne de caractères

connection.timestamp

L'heure, en secondes depuis l'Époque Unix, à laquelle la connexion a été _successfullement_ complètement activée pour la dernière fois.

NetworkManager met à jour l'horodatage de la connexion périodiquement lorsque la connexion est active pour s'assurer qu'une connexion active a le dernier horodatage. La propriété est uniquement destinée à la lecture (les modifications apportées à cette propriété ne seront pas préservées).

Format : lecture seule

connection.type

Alias : type

Type de base de la connexion. Pour les connexions dépendantes du matériel, il doit contenir le nom du paramètre spécifique au type de matériel (par exemple, "<tt>802-3-ethernet</tt>" ou "<tt>802-11-wireless</tt>" ou "<tt>bluetooth</tt>", etc.), et pour les connexions non dépendantes du matériel comme VPN ou autres, il doit contenir le nom du paramètre de ce type (par exemple, "<tt>vpn</tt>" ou "<tt>bridge</tt>", etc.).

Format : chaîne de caractères

Valeurs valides : 6lowpan, 802-11-olpc-mesh, 802-11-wireless, 802-3-ethernet, adsl, bluetooth, bond, bridge, cdma, dummy, generic, gsm, hsr, infiniband, ip-tunnel, ipvlan, loopback, macsec, macvlan, ovs-bridge, ovs-interface, ovs-port, pppoe, team, tun, veth, vlan, vpn, vrf, vxlan, wifi-p2p, wimax, wireguard, wpan

connection.uuid

L'UUID de la connexion est l'identifiant réel d'un profil. Il ne peut pas changer et doit être unique. Il est donc souvent préférable de faire référence à un profil par son UUID, par exemple avec `nmcli connection up uuid $UUID`.

L'UUID ne peut pas être modifié, sauf en mode hors ligne. Dans ce cas, les valeurs spéciales "new", "generate" et "" sont autorisées pour générer un nouvel UUID aléatoire.

Format : un identifiant universellement unique (UUID) conforme à la RFC4122.

connection.wait-activation-delay

Temps en millisecondes à attendre pour que la connexion soit considérée comme activée. L'attente commencera après l'événement du dispatcher pre-up.

La valeur 0 signifie pas de temps d'attente. La valeur par défaut est -1, qui a actuellement la même signification que pas de temps d'attente.

Format : entier

Valeurs valides : -1 - 2147483647

connection.wait-device-timeout

Délai en millisecondes pour attendre l'appareil au démarrage. Lors du démarrage, les appareils peuvent prendre du temps à être détectés par le pilote. Cette propriété retardera NetworkManager-wait-online.service et nm-online pour donner une chance à l'appareil d'apparaître. Cela fonctionne en attendant le délai spécifié jusqu'à ce qu'un appareil compatible pour le profil soit disponible et géré.

La valeur 0 signifie pas de temps d'attente. La valeur par défaut est -1, qui a actuellement la même signification que pas de temps d'attente.

Format : entier

Valeurs valides : -1 - 2147483647

connection.zone

Le niveau de confiance de la connexion. Chaîne de caractères libre insensible à la casse (par exemple "<tt>Home</tt>", "<tt>Work</tt>", "<tt>Public</tt>"). Une zone NULL ou non spécifiée signifie que la connexion sera placée dans la zone par défaut telle que définie par le pare-feu.

Lors de la mise à jour de cette propriété sur une connexion actuellement activée, le changement prend effet immédiatement.

Format : chaîne de caractères

Paramètre 6lowpan

Paramètres 6LoWPAN.

Propriétés :

Cette propriété est un masque de 16 bits, chacun correspondant à une adresse de groupe dans cette plage qui doit être transférée. Les valeurs négatives ont pour effet spécial d'exclure les autres configurations avec une valeur de priorité numérique plus élevée ; donc, en présence d'au moins une priorité négative, seuls les serveurs DNS des connexions avec la valeur de priorité la plus basse seront utilisés. Pour éviter toute fuite DNS, définissez la priorité du profil qui doit être utilisé sur la valeur la plus négative de tous les profils de connexion actifs.

Zéro sélectionne une valeur par défaut configurée globalement. Si cette dernière est manquante ou également à zéro, elle prend par défaut 50 pour les VPN (y compris WireGuard) et 100 pour les autres connexions.

Notez que la priorité sert à trier les paramètres DNS pour plusieurs connexions actives. Elle ne désambiguïse pas plusieurs serveurs DNS au sein du même profil de connexion.

Lorsque plusieurs périphériques ont des configurations avec la même priorité, les VPN seront considérés en premier, puis les périphériques avec la meilleure route par défaut (métrique la plus basse) et ensuite tous les autres périphériques.

Lors de l'utilisation de dns=default, les serveurs ayant une priorité plus élevée seront en haut de resolv.conf. Pour prioriser un serveur donné par rapport à un autre au sein de la même connexion, spécifiez-les simplement dans l'ordre souhaité. Notez qu'il est courant que le résolveur essaie les serveurs de noms dans /etc/resolv.conf dans l'ordre de liste, passant au serveur suivant dans la liste en cas d'échec. Voir par exemple l'option « rotate » du paramètre dns-options. S'il y a des priorités DNS négatives, alors seuls les serveurs de noms des périphériques ayant cette priorité la plus basse seront pris en compte.

Lors de l'utilisation d'un résolveur DNS qui prend en charge le routage conditionnel ou le DNS fractionné (avec les paramètres dns=dnsmasq ou dns=systemd-resolved), chaque connexion est utilisée pour interroger les domaines de sa liste de recherche. Les domaines de recherche déterminent quels serveurs de noms interroger, et la priorité DNS est utilisée pour prioriser les serveurs de noms en fonction du domaine. Les requêtes pour les domaines non présents dans une liste de recherche sont acheminées via les connexions ayant le domaine spécial wildcard '~.', qui est automatiquement ajouté aux connexions avec la route par défaut (ou peut être ajouté manuellement). Lorsque plusieurs connexions spécifient le même domaine, celle avec la meilleure priorité (valeur numérique la plus basse) l'emporte. Si un sous-domaine est configuré sur une autre interface, il sera accepté quelle que soit la priorité, sauf si le domaine parent sur l'autre interface a une priorité négative, ce qui fait que le sous-domaine est masqué. Avec le DNS fractionné, vous pouvez éviter les fuites DNS indésirables en configurant correctement les priorités DNS et les domaines de recherche, de sorte que seuls les serveurs de noms de l'interface souhaitée soient configurés.

Format : entier

Valeurs valides : -2147483648 - 2147483647

L'intervalle de temps minimum en millisecondes pendant lequel la configuration IP dynamique doit être essayée avant que la connexion ne réussisse.

Active le routage basé sur des politiques (routage source) et définit la table de routage utilisée lors de l'ajout de routes.

ipv6.addr-gen-mode

Configure la méthode de création de l'identifiant d'interface IPv6 des adresses avec l'autoconfiguration d'adresse IPv6 sans état RFC4862 et les adresses Link Local.

Les valeurs autorisées sont : "eui64" (0), "stable-privacy" (1), "default" (3) ou "default-or-eui64" (2).

Si la propriété est définie sur "eui64", les adresses seront générées en utilisant le jeton d'interface dérivé de l'adresse matérielle. Cela rend la partie hôte de l'adresse constante, ce qui permet de suivre la présence de l'hôte lorsqu'il change de réseau. L'adresse change lorsque le matériel de l'interface est remplacé. Si une adresse dupliquée est détectée, il n'y a pas de repli pour générer une autre adresse. Une fois configuré, le "ipv6.token" est utilisé au lieu de l'adresse MAC pour générer des adresses pour l'autoconfiguration sans état.

Si la propriété est définie sur "stable-privacy", l'identifiant d'interface est généré conformément à la RFC7217. Cela fonctionne en hachant une clé spécifique à l'hôte (voir le manuel de NetworkManager(8)), le nom de l'interface, la propriété "connection.stable-id" de la connexion et le préfixe d'adresse. Les valeurs spéciales "default" et "default-or-eui64" se replieront sur la valeur par défaut globale de la connexion, comme décrit dans le manuel de NetworkManager.conf(5). Si la valeur par défaut globale n'est pas spécifiée, la valeur de repli sera "stable-privacy" ou "eui64", respectivement.

Si elle n'est pas spécifiée, lors de la création d'un nouveau profil, la valeur par défaut est "default".

Notez que ce paramètre est distinct des extensions de confidentialité telles que configurées par la propriété "ip6-privacy" et n'affecte pas les adresses temporaires configurées avec cette option.

Lorsque la propriété n'est pas définie, la valeur de la configuration globale est utilisée ; si aucun défaut global n'est défini, l'IAID est supposé être "ifname".

Pour DHCPv4, l'IAID n'est utilisé qu'avec les valeurs "duid" et "ipv6-duid" de "ipv4.dhcp-client-id" pour générer l'id client.

Pour DHCPv6, notez qu'actuellement cette propriété n'est prise en charge que par le plugin DHCPv6 "internal". Le plugin DHCPv6 "dhclient" dérive toujours l'IAID de l'adresse MAC.

ipv6.dns-priority

Priorité des serveurs DNS.

La priorité relative des serveurs DNS spécifiés par ce paramètre. Une valeur numérique plus faible est meilleure (priorité plus élevée).

Les valeurs négatives ont pour effet spécial d'exclure d'autres configurations avec une valeur de priorité numérique supérieure ; ainsi, en présence d'au moins une priorité négative, seuls les serveurs DNS des connexions ayant la valeur de priorité la plus faible seront utilisés. Pour éviter toutes fuites DNS, définissez la priorité du profil qui doit être utilisé sur la valeur la plus négative de tous les profils de connexion actifs.

Zéro sélectionne une valeur par défaut configurée globalement. Si cette dernière est manquante ou nulle également, elle est par défaut à 50 pour les VPN (y compris WireGuard) et à 100 pour les autres connexions.

Notez que la priorité sert à ordonner les paramètres DNS pour plusieurs connexions actives. Elle ne désambiguïse pas plusieurs serveurs DNS au sein du même profil de connexion.

Lorsque plusieurs appareils ont des configurations avec la même priorité, les VPN sont considérés en premier, puis les appareils ayant la meilleure route par défaut (métrique la plus basse), puis tous les autres appareils.

Lors de l'utilisation de dns=default, les serveurs ayant une priorité plus élevée seront en haut de resolv.conf. Pour donner la priorité à un serveur donné par rapport à un autre au sein de la même connexion, spécifiez-les simplement dans l'ordre souhaité. Notez que généralement le résolveur essaie les serveurs de noms dans /etc/resolv.conf dans l'ordre de liste, passant au serveur suivant dans la liste en cas d'échec. Voir par exemple l'option « rotate » du paramètre dns-options. S'il y a des priorités DNS négatives, seuls les serveurs de noms des appareils ayant cette priorité la plus basse seront pris en compte.

Lors de l'utilisation d'un résolveur DNS prenant en charge la mise en correspondance conditionnelle ou le DNS fractionné (avec les paramètres dns=dnsmasq ou dns=systemd-resolved), chaque connexion est utilisée pour interroger les domaines de sa liste de recherche. Les domaines de recherche déterminent quels serveurs de noms interroger, et la priorité DNS est utilisée pour prioriser les serveurs de noms en fonction du domaine. Les requêtes pour les domaines non présents dans une liste de recherche sont acheminées via les connexions ayant le domaine joker spécial « ~. », qui est ajouté automatiquement aux connexions avec la route par défaut (ou peut être ajouté manuellement). Lorsque plusieurs connexions spécifient le même domaine, celle ayant la meilleure priorité (valeur numérique la plus faible) gagne. Si un sous-domaine est configuré sur une autre interface, il sera accepté quelle que soit la priorité, à moins que le domaine parent sur l'autre interface n'ait une priorité négative, ce qui entraîne l'ombrage du sous-domaine. Avec le DNS fractionné, vous pouvez éviter les fuites DNS indésirables en configurant correctement les priorités DNS et les domaines de recherche, de sorte que seuls les serveurs de noms de l'interface souhaitée soient configurés.

Format : entier

Valeurs valides : -2147483648 - 2147483647

match setting

Paramètres de correspondance.

Propriétés :

match.driver

Une liste de noms de pilotes à faire correspondre. Chaque élément est un modèle de caractères génériques shell.

Voir NMSettingMatch:interface-name pour savoir comment les caractères spéciaux '|', '&', '!' et '\\' sont utilisés pour les correspondances optionnelles et obligatoires et pour inverser le modèle.

Format : liste de chaînes

match.interface-name

Une liste de noms d'interfaces à faire correspondre. Chaque élément est un modèle de caractères génériques shell.

Un élément peut être préfixé par un symbole pipe (|) ou une esperluette (&). Le premier signifie que l'élément est optionnel et le second qu'il est obligatoire. S'il y a des éléments optionnels, la correspondance est vraie si au moins un des éléments optionnels correspond (OU logique). S'il y a des éléments obligatoires, alors ils doivent tous correspondre (ET logique). Par défaut, un élément est optionnel. Cela signifie qu'un élément "foo" se comporte de la même manière que "|foo". Un élément peut également être inversé avec un point d'exclamation (!) entre le symbole pipe (ou l'esperluette) et avant le modèle. Notez que "!foo" est un raccourci pour la correspondance obligatoire "&!foo". Enfin, une barre oblique inverse peut être utilisée au début de l'élément (après les caractères spéciaux optionnels) pour échapper le début du modèle. Par exemple, "&\\!a" est une correspondance obligatoire pour littéralement "!a".

Format : liste de chaînes

match.kernel-command-line

Une liste d'arguments de ligne de commande du noyau à faire correspondre. Ceci peut être utilisé pour vérifier si une option de ligne de commande spécifique du noyau est définie (ou non définie, si préfixée par le point d'exclamation). L'argument doit être soit un seul mot, soit une affectation (c'est-à-dire deux mots, joints par "="). Dans le premier cas, la ligne de commande du noyau est recherchée pour trouver le mot tel quel, ou comme partie gauche d'une affectation. Dans le second cas, l'affectation exacte est recherchée avec une correspondance de la partie droite et gauche. Les modèles de caractères génériques ne sont pas supportés.

Voir NMSettingMatch:interface-name pour savoir comment les caractères spéciaux '|', '&', '!' et '\\' sont utilisés pour les correspondances optionnelles et obligatoires et pour inverser la correspondance.

Format : liste de chaînes

Une liste de chemins à faire correspondre par rapport à la propriété udev ID_PATH des périphériques. ID_PATH représente le chemin topologique persistant d'un périphérique. Il contient généralement une chaîne de sous-système (pci, usb, platform, etc.) et un identifiant spécifique au sous-système.

Pour les périphériques PCI, le chemin a la forme "pci-$domain:$bus:$device.$function", où chaque variable est une valeur hexadécimale ; par exemple "pci-0000:0a:00.0".

Le chemin d'un périphérique peut être obtenu avec "udevadm info /sys/class/net/$dev | grep ID_PATH=" ou en examinant la propriété "path" exportée par NetworkManager ("nmcli -f general.path device show $dev").

sriov.vfs

Array of virtual function descriptors.

Each VF descriptor is a dictionary mapping attribute names to GVariant values. The 'index' entry is mandatory for each VF.

When represented as string a VF is in the form:

"INDEX [ATTR=VALUE[ ATTR=VALUE]...]".

for example:

"2 mac=00:11:22:33:44:55 spoof-check=true".

Multiple VFs can be specified using a comma as separator. Currently, the following attributes are supported: mac, spoof-check, trust, min-tx-rate, max-tx-rate, vlans.

The "vlans" attribute is represented as a semicolon-separated list of VLAN descriptors, where each descriptor has the form

"ID[.PRIORITY[.PROTO]]".

PROTO can be either 'q' for 802.1Q (the default) or 'ad' for 802.1ad.

Each qdisc can be specified by the following attributes:

Paramètres pour 'fq_codel' :

limit U32

la limite stricte de la taille réelle de la file d'attente. Lorsque cette limite est atteinte, les paquets entrants sont rejetés. Par défaut, 10240 paquets.

memory_limit U32

définit une limite sur le nombre total d'octets pouvant être mis en file d'attente dans cette instance FQ-CoDel. La plus petite des deux limites, celle des paquets du paramètre limit et celle de la mémoire, sera appliquée. Par défaut, 32 Mo.

flows U32

le nombre de flux dans lesquels les paquets entrants sont classifiés. En raison de la nature stochastique du hachage, plusieurs flux peuvent aboutir dans le même emplacement. Les flux plus récents ont la priorité sur les plus anciens. Ce paramètre ne peut être défini qu'au chargement, car de la mémoire doit être allouée pour la table de hachage. Valeur par défaut : 1024.

target U32

le délai minimal acceptable de mise en file d'attente persistante. Ce délai minimum est identifié en suivant le délai minimum local de la file d'attente que les paquets subissent. L'unité de mesure est la microseconde (us). Valeur par défaut : 5 ms.

interval U32

utilisé pour garantir que le délai minimum mesuré ne devienne pas trop obsolète. Le délai minimum doit être rencontré dans la dernière époque d'une longueur de .B interval. Il doit être défini à l'ordre de grandeur du RTT (Round Trip Time) dans le pire des cas sur le goulot d'étranglement afin de laisser suffisamment de temps aux points de terminaison pour réagir. Valeur par défaut : 100 ms.

quantum U32

le nombre d'octets utilisé comme « déficit » dans l'algorithme de file d'attente équitable (fair queuing). Par défaut, il est défini à 1514 octets, ce qui correspond à la MTU Ethernet plus l'en-tête matériel de 14 octets.

ecn BOOL

peut être utilisé pour marquer les paquets au lieu de les rejeter. ecn est activé par défaut.

ce_threshold U32

définit un seuil au-dessus duquel tous les paquets sont marqués avec ECN (Experienced Congestion). Ceci est utile pour les algorithmes de contrôle de congestion de type DCTCP qui nécessitent un marquage à des seuils de file d'attente très faibles.

Paramètres pour 'sfq' :

divisor U32

peut être utilisé pour définir une taille de table de hachage différente, disponible à partir du noyau 2.6.39. Le diviseur spécifié doit être une puissance de deux et ne peut pas être supérieur à 65536. Valeur par défaut : 1024.

limit U32

Limite supérieure du SFQ. Peut être utilisé pour réduire la longueur par défaut de 127 paquets.

depth U32

Limite de paquets par flux. Par défaut à 127 et peut être diminuée.

perturb_period U32

Intervalle en secondes pour la perturbation de l'algorithme de file d'attente. Par défaut à 0, ce qui signifie qu'aucune perturbation ne se produit. Ne pas régler trop bas car chaque perturbation peut entraîner un réordonnancement ou des pertes de paquets. Valeur conseillée : 60. Cette valeur n'a aucun effet lorsque la classification externe des flux est utilisée. Il est préférable d'augmenter la valeur du diviseur pour réduire le risque de collisions de hachage.

quantum U32

Quantité d'octets qu'un flux est autorisé à défiler pendant un tour du processus de rotation. Par défaut, correspond à la MTU de l'interface, ce qui est également la valeur conseillée et la valeur minimale.

flows U32

Valeur par défaut : 127.

Paramètres pour 'tbf' :

rate U64

Bande passante ou débit. Ces paramètres acceptent un nombre à virgule flottante, éventuellement suivi d'une unité (unités SI et IEC prises en charge), ou d'un flottant suivi d'un caractère de pourcentage pour spécifier le débit comme un pourcentage de la vitesse de l'appareil.

burst U32

Également connu sous le nom de buffer ou maxburst. Taille du seau, en octets. C'est la quantité maximale d'octets qui peuvent être disponibles instantanément sous forme de jetons. En général, des débits de façonnage plus élevés nécessitent un seau plus grand. Pour 10 Mbit/s sur Intel, vous avez besoin d'un tampon d'au moins 10 Ko si vous voulez atteindre le débit configuré !

Si votre tampon est trop petit, des paquets peuvent être rejetés car plus de jetons arrivent par tick de temporisation qu'il n'en rentre dans votre seau. La taille minimale du tampon peut être calculée en divisant le débit par HZ.

Les calculs d'utilisation des jetons sont effectués à l'aide d'une table qui, par défaut, a une résolution de 8 paquets. Cette résolution peut être modifiée en spécifiant la taille de cellule avec le paramètre burst. Par exemple, pour spécifier un tampon de 6000 octets avec une taille de cellule de 16 octets, définissez un burst de 6000/16. Vous n'aurez probablement jamais à le définir. Doit être une puissance entière de 2.

limit U32

Limit est le nombre d'octets pouvant être mis en file d'attente en attendant que des jetons soient disponibles.

latency U32

spécifie le temps maximum qu'un paquet peut passer dans le TBF. Le calcul de la latence prend en compte la taille du seau, le débit et éventuellement le débit de pointe (s'il est défini). La latence et la limite sont mutuellement exclusives.

Cette propriété permet de spécifier que certains bits sont fixes. Notez que le bit le moins significatif de la première adresse MAC sera toujours désactivé pour créer une adresse MAC universelle.

Notez que le marquage du réseau comme caché peut poser un problème de confidentialité pour vous (en mode infrastructure) ou pour les stations clients (en mode AP), car les analyses par sondage explicites sont clairement reconnaissables dans les airs.

Types de drapeaux secrets :

Chaque mot de passe ou propriété secrète dans un réglage a une propriété flags associée qui décrit comment gérer ce secret. La propriété flags est un champ de bits qui contient zéro ou plusieurs des valeurs suivantes combinées logiquement par un OR.

•0x0 (aucun) - le système est responsable de fournir et de stocker ce secret. Cela peut être nécessaire afin que les secrets soient déjà disponibles avant que l'utilisateur ne se connecte. Cela signifie également couramment que le secret sera stocké en texte brut sur le disque, accessible uniquement à l'utilisateur root. Par exemple, via le plugin de réglages de fichier de clés comme décrit dans la section "PLUGINS" de NetworkManager.conf(5).
•0x1 (propriété de l'agent) - un agent de session utilisateur est responsable de fournir et de stocker ce secret ; lorsqu'il est requis, les agents seront invités à le fournir.
•0x2 (non enregistré) - ce secret ne doit pas être enregistré mais doit être demandé à l'utilisateur chaque fois qu'il est requis. Ce drapeau doit être utilisé pour les secrets à usage unique, les codes PIN des jetons matériels, ou si l'utilisateur ne souhaite tout simplement pas enregistrer le secret.
•0x4 (non requis) - dans certaines situations, il ne peut pas être déterminé automatiquement si un secret est requis ou non. Ce drapeau indique que le secret n'est pas requis et ne doit pas être demandé à l'utilisateur.
