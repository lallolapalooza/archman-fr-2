NM-CLOUD-SETUP(8) Configuration Réseau Automatique NM-CLOUD-SETUP(8)

NOM

nm-cloud-setup - Vue d'ensemble de la configuration réseau automatique dans le cloud

VUE D'ENSEMBLE

Lors de l'exécution d'une machine virtuelle dans un environnement de cloud public, il est souhaitable de configurer automatiquement le réseau de cette VM. Dans les configurations simples, la VM n'a qu'une seule interface réseau et le cloud public prend en charge la configuration automatique via DHCP, DHCP6 ou l'autoconfiguration IPv6. Cependant, la machine virtuelle peut avoir plusieurs interfaces réseau, ou plusieurs adresses IP et sous-réseaux IP sur une seule interface qui ne peuvent pas être configurés via DHCP. De plus, l'administrateur peut reconfigurer le réseau pendant que la machine est en cours d'exécution. nm-cloud-setup de NetworkManager est un outil qui détecte automatiquement cette configuration dans les environnements cloud et met à jour la configuration réseau de l'hôte.

Plusieurs fournisseurs de cloud sont pris en charge. Voir la section « FOURNISSEURS DE CLOUD PRIS EN CHARGE ».

UTILISATION

L'objectif de nm-cloud-setup est de ne pas nécessiter de configuration et de fonctionner automatiquement. Il vous suffit de choisir les fournisseurs de cloud souhaités (voir la section « VARIABLES D'ENVIRONNEMENT ») et d'exécuter /usr/libexec/nm-cloud-setup.

Ceci est généralement fait en activant le service systemd nm-cloud-setup.service et en le laissant s'exécuter périodiquement. Pour cela, il existe à la fois une minuterie systemd nm-cloud-setup.timer et un script de distribution NetworkManager.

DÉTAILS

nm-cloud-setup configure le réseau en récupérant la configuration à partir du serveur de métadonnées bien connu du fournisseur de cloud. Cela signifie qu'il nécessite déjà que le réseau soit configuré au point de pouvoir atteindre le serveur de métadonnées. Généralement, cela signifie qu'un profil de connexion simple est activé qui utilise éventuellement DHCP pour obtenir l'adresse IP primaire. NetworkManager créera automatiquement un tel profil pour les périphériques Ethernet s'il n'est pas configuré autrement via le réglage « no-auto-default » dans NetworkManager.conf. Une alternative possible peut être de créer un tel profil initial avec nmcli device connect "$DEVICE" ou nmcli connection add type ethernet ....

En définissant la donnée utilisateur org.freedesktop.nm-cloud-setup.skip=yes sur le profil, nm-cloud-setup ignorera le périphérique.

nm-cloud-setup modifie la configuration d'exécution de manière similaire à nmcli device modify. Avec cette approche, la configuration n'est pas persistante et n'est conservée que jusqu'à ce que le périphérique se déconnecte.

/usr/libexec/nm-cloud-setup

Le binaire /usr/libexec/nm-cloud-setup fait la majeure partie du travail. Il ne prend pas en charge d'arguments en ligne de commande mais peut être configuré via des variables d'environnement. Voir la section « VARIABLES D'ENVIRONNEMENT » pour les variables d'environnement prises en charge.

Par défaut, tous les fournisseurs de cloud sont désactivés à moins que vous n'activiez un ou plusieurs fournisseurs. Si les fournisseurs de cloud sont activés, le programme tente de récupérer la configuration de l'hôte à partir d'un serveur de métadonnées du cloud via HTTP. Si la configuration n'a pas pu être récupérée, aucun fournisseur de cloud n'est détecté et le programme se quitte. Si la configuration de l'hôte est obtenue, le fournisseur de cloud correspondant est détecté avec succès. Ensuite, le réseau de l'hôte sera configuré.

Il est prévu de réexécuter nm-cloud-setup chaque fois que la configuration change (peut-être). L'outil est idempotent, il ne devrait donc pas y avoir de problème à l'exécuter plus souvent que nécessaire. Vous pouvez exécuter /usr/libexec/nm-cloud-setup directement. Cependant, il peut être préférable de redémarrer le service systemd nm-cloud-setup à la place ou d'utiliser la minuterie ou le script de distribution pour l'exécuter périodiquement (voir ci-dessous).

Unité systemd nm-cloud-setup.service

Généralement, /usr/libexec/nm-cloud-setup n'est pas exécuté directement, mais uniquement par systemctl restart nm-cloud-setup.service. Cela garantit que l'outil ne s'exécute qu'une seule fois à la fois. L'unité est également utilisée par la minuterie systemd nm-cloud-setup et permet d'activer/désactiver le service via systemd.

Comme vous devez définir des variables d'environnement pour configurer le binaire nm-cloud-setup, vous pouvez le faire via des fichiers de substitution systemd. Essayez systemctl edit nm-cloud-setup.service.

Minuterie systemd nm-cloud-setup.timer

/usr/libexec/nm-cloud-setup est destiné à s'exécuter chaque fois qu'une mise à jour est nécessaire. Par exemple, au démarrage ou lors de la modification de la configuration réseau de la machine virtuelle via le fournisseur de cloud.

Une façon de procéder consiste à activer la minuterie systemd nm-cloud-setup.timer avec systemctl enable --now nm-cloud-setup.timer.

/usr/lib/NetworkManager/dispatcher.d/90-nm-cloud-setup.sh

Il existe également un script de distribution NetworkManager qui s'exécutera par exemple lorsqu'une interface est activée par NetworkManager. En conjonction avec la minuterie systemd nm-cloud-setup.timer, ce script est destiné à récupérer automatiquement les modifications réseau.

Le script de distribution ne fera rien, à moins que le service systemd ne soit activé. Pour utiliser le script de distribution, vous devez donc exécuter systemctl enable nm-cloud-setup.service une fois.

VARIABLES D'ENVIRONNEMENT

Les variables d'environnement suivantes sont utilisées pour configurer /usr/libexec/nm-cloud-setup. Vous voudrez peut-être les configurer avec un fichier de substitution pour le service systemd. Par exemple, en appelant systemctl edit nm-cloud-setup.service et en configurant [Service] Environment=, comme décrit dans le manuel systemd.exec(5).

•NM_CLOUD_SETUP_LOG : contrôle la verbosité de la journalisation. Définissez-le sur l'une des valeurs TRACE, DEBUG, INFO, WARN, ERR ou OFF. Le programme imprimera des messages sur la sortie standard et le niveau par défaut est WARN. Lorsqu'il est exécuté en tant que service systemd, le journal sera collecté par journald et pourra être consulté avec journalctl.
•NM_CLOUD_SETUP_AZURE : booléen, si le support de Microsoft Azure est activé. Par défaut, non.
•NM_CLOUD_SETUP_EC2 : booléen, si le support d'Amazon EC2 (AWS) est activé. Par défaut, non.
•NM_CLOUD_SETUP_GCP : booléen, si le support de Google GCP est activé. Par défaut, non.
•NM_CLOUD_SETUP_ALIYUN : booléen, si le support d'Alibaba Cloud (Aliyun) est activé. Par défaut, non.
•NM_CLOUD_SETUP_OCI : booléen, si le support d'Oracle Cloud (OCI) est activé. Par défaut, non.

DÉBOGAGE

Activez la journalisation de débogage en définissant la variable d'environnement NM_CLOUD_SETUP_LOG sur TRACE.

Dans le cas courant où nm-cloud-setup est exécuté en tant que service systemd, cela peut être fait via systemctl edit nm-cloud-setup.service et en ajoutant Environment=NM_CLOUD_SETUP_LOG=TRACE à la section [Service]. Ensuite, le journal peut être trouvé dans syslog via journalctl. Vous voudrez peut-être également activer la journalisation de débogage dans NetworkManager, comme décrit dans la section DÉBOGAGE du manuel NetworkManager(5). Lors du partage de journaux, il est préférable de partager les journaux complets et de ne pas filtrer préventivement les journaux de NetworkManager ou de nm-cloud-setup.

EXEMPLE DE CONFIGURATION POUR CONFIGURER ET PRÉDÉPLOYER NM-CLOUD-SETUP

Comme détaillé précédemment, nm-cloud-setup doit être explicitement activé. Comme il s'exécute en tant que service et minuterie systemd, cela signifie essentiellement d'activer et de configurer ceux-ci. Cela peut être fait en plaçant les fichiers et liens symboliques corrects sur le disque.

L'exemple suivant active nm-cloud-setup pour le cloud Amazon EC2 :

dnf install -y NetworkManager-cloud-setup
mkdir -p /etc/systemd/system/nm-cloud-setup.service.d
cat > /etc/systemd/system/nm-cloud-setup.service.d/10-enable-ec2.conf << EOF
[Service]
Environment=NM_CLOUD_SETUP_EC2=yes
EOF
# systemctl enable nm-cloud-setup.service
mkdir -p /etc/systemd/system/NetworkManager.service.wants/
ln -s /usr/lib/systemd/system/nm-cloud-setup.service /etc/systemd/system/NetworkManager.service.wants/nm-cloud-setup.service
# systemctl enable nm-cloud-setup.timer
mkdir -p /etc/systemd/system/timers.target.wants/
ln -s /etc/systemd/system/timers.target.wants/nm-cloud-setup.timer /usr/lib/systemd/system/nm-cloud-setup.t
imer # systemctl daemon-reload

FOURNISSEURS DE CLOUD SUPPORTÉS

Amazon EC2 (AWS)

Pour AWS, les outils tentent de récupérer la configuration depuis http://169.254.169.254/. Actuellement, il ne configure que l'IPv4 et ne fait rien concernant l'IPv6. Il effectuera les actions suivantes.

•Premièrement, il récupère http://169.254.169.254/latest/meta-data/ pour déterminer si l'API attendue est présente. Cela détermine si l'environnement EC2 est détecté et s'il faut procéder à la configuration de l'hôte en utilisant les métadonnées EC2.
•Récupère http://169.254.169.254/2018-09-24/meta-data/network/interfaces/macs/ pour obtenir la liste des interfaces disponibles. Les interfaces sont identifiées par leur adresse MAC.
•Ensuite, pour chaque interface, il récupère http://169.254.169.254/2018-09-24/meta-data/network/interfaces/macs/$MAC/subnet-ipv4-cidr-block et http://169.254.169.254/2018-09-24/meta-data/network/interfaces/macs/$MAC/local-ipv4s. Ainsi, nous obtenons une liste d'adresses IPv4 locales et un bloc CIDR de sous-réseau.
•Ensuite, nm-cloud-setup itère sur toutes les interfaces pour lesquelles il a pu récupérer la configuration IP. Si aucun périphérique Ethernet n'est trouvé pour l'adresse MAC correspondante, il est ignoré. De plus, si le périphérique n'est pas actuellement activé dans NetworkManager ou si le profil activé actuellement a une donnée utilisateur org.freedesktop.nm-cloud-setup.skip=yes, il est ignoré.

Si une seule interface et une seule adresse sont configurées, l'outil ne fait rien et laisse la configuration automatique obtenue via DHCP.

Sinon, l'outil modifiera la configuration d'exécution du périphérique.

•Ajoute des adresses IPv4 statiques pour toutes les adresses configurées à partir de local-ipv4s avec une longueur de préfixe selon subnet-ipv4-cidr-block. Par exemple, nous pourrions avoir ici 2 adresses IP comme "172.16.5.3/24,172.16.5.4/24".
•Choisit une table de routage 30400 + l'index de l'interface et ajoute une route par défaut 0.0.0.0/0. La passerelle est la première adresse IP dans le bloc CIDR du sous-réseau. Par exemple, nous pourrions obtenir une route "0.0.0.0/0 172.16.5.1 10 table=30400".

Choisit également une table de routage 30200 + l'index de l'interface. Celle-ci contient des routes directes vers les sous-réseaux de cette interface.

•Enfin, ajoute une règle de routage par politique pour chaque adresse. Par exemple, "priority 30200 from 172.16.5.3/32 table 30200, priority 30200 from 172.16.5.4/32 table 30200". et "priority 30400 from 172.16.5.3/32 table 30400, priority 30400 from 172.16.5.4/32 table 30400". Les règles 30200+ sélectionnent la table pour atteindre directement le sous-réseau, tandis que les règles 30400+ utilisent la route par défaut. Ajoute également une règle "priority 30350 table main suppress_prefixlength 0". Celle-ci a une priorité entre les deux règles précédentes et provoque une recherche de routes dans la table principale tout en ignorant la route par défaut. Le but est de faire en sorte que d'autres routes spécifiques dans la table principale soient honorées plutôt que la route par défaut dans la table 30400+.

Avec l'exemple ci-dessus, cela correspond approximativement pour l'interface eth0 à nmcli device modify "eth0" ipv4.addresses "172.16.5.3/24,172.16.5.4/24" ipv4.routes "172.16.5.0/24 0.0.0.0 10 table=30200, 0.0.0.0/0 172.16.5.1 10 table=30400" ipv4.routing-rules "priority 30200 from 172.16.5.3/32 table 30200, priority 30200 from 172.16.5.4/32 table 30200, priority 20350 table main suppress_prefixlength 0, priority 30400 from 172.16.5.3/32 table 30400, priority 30400 from 172.16.5.4/32 table 30400". Notez que cela remplace les adresses, routes et règles précédentes par les nouvelles informations. Mais notez également que cela ne modifie que la configuration d'exécution du périphérique. Le profil de connexion sur disque n'est pas affecté.

Google Cloud Platform (GCP)

Pour GCP, les métadonnées sont récupérées depuis des URIs commençant par http://metadata.google.internal/computeMetadata/v1/ avec un en-tête HTTP "Metadata-Flavor: Google". Actuellement, l'outil ne configure que l'IPv4 et ne fait rien concernant l'IPv6. Il effectuera les actions suivantes.

•Premièrement, il récupère http://metadata.google.internal/computeMetadata/v1/instance/id pour détecter si l'outil s'exécute sur Google Cloud Platform. Ce n'est que si la plateforme est détectée qu'il continuera à récupérer la configuration.
•Récupère http://metadata.google.internal/computeMetadata/v1/instance/network-interfaces/ pour obtenir la liste des index d'interfaces disponibles. Ces index peuvent être utilisés pour des recherches ultérieures.
•Ensuite, pour chaque interface, il récupère http://metadata.google.internal/computeMetadata/v1/instance/network-interfaces/$IFACE_INDEX/mac pour obtenir l'adresse MAC correspondante des interfaces trouvées. L'adresse MAC est utilisée pour identifier le périphérique ultérieurement.
•Ensuite, pour chaque interface avec une adresse MAC, il récupère http://metadata.google.internal/computeMetadata/v1/instance/network-interfaces/$IFACE_INDEX/forwarded-ips/ puis toutes les adresses IP trouvées à http://metadata.google.internal/computeMetadata/v1/instance/network-interfaces/$IFACE_INDEX/forwarded-ips/$FIPS_INDEX.
•À ce stade, nous avons une liste de toutes les interfaces (par adresse MAC) et de leurs adresses IPv4 configurées.

Pour chaque périphérique, nous recherchons la connexion actuellement appliquée dans NetworkManager. Cela implique que le périphérique est actuellement activé dans NetworkManager. Si aucun périphérique de ce type n'était dans NetworkManager, ou si le profil a la donnée utilisateur org.freedesktop.nm-cloud-setup.skip=yes, nous ignorons le périphérique. Maintenant, pour chaque adresse IP trouvée, nous ajoutons une route statique "$FIPS_ADDR/32 0.0.0.0 100 type=local" et réappliquons la modification.

L'effet n'est pas différent de l'appel à nmcli device modify "$DEVICE" ipv4.routes "$FIPS_ADDR/32 0.0.0.0 100 type=local [,...]" pour tous les périphériques pertinents et toutes les adresses trouvées.

Microsoft Azure

Pour Azure, les métadonnées sont récupérées depuis des URIs commençant par http://169.254.169.254/metadata/instance avec un paramètre d'URL "?format=text&api-version=2017-04-02" et un en-tête HTTP "Metadata:true". Actuellement, l'outil ne configure que l'IPv4 et ne fait rien concernant l'IPv6. Il effectuera les actions suivantes.

•Premièrement, il récupère http://169.254.169.254/metadata/instance?format=text&api-version=2017-04-02 pour détecter si l'outil s'exécute sur Azure Cloud. Ce n'est que si la plateforme est détectée qu'il continuera à récupérer la configuration.
•Récupère http://169.254.169.254/metadata/instance/network/interface/?format=text&api-version=2017-04-02 pour obtenir la liste des index d'interfaces disponibles. Ces index peuvent être utilisés pour des recherches ultérieures.
•Ensuite, pour chaque interface, il récupère http://169.254.169.254/metadata/instance/network/interface/$IFACE_INDEX/macAddress?format=text&api-version=2017-04-02 pour obtenir l'adresse MAC correspondante des interfaces trouvées. L'adresse MAC est utilisée pour identifier le périphérique ultérieurement.
•Ensuite, pour chaque interface avec une adresse MAC, il récupère http://169.254.169.254/metadata/instance/network/interface/$IFACE_INDEX/ipv4/ipAddress/?format=text&api-version=2017-04-02 pour obtenir la liste des (index d') adresses IP sur cette interface.
•Ensuite, pour chaque index d'adresse IP, il récupère l'adresse à http://169.254.169.254/metadata/instance/network/interface/$IFACE_INDEX/ipv4/ipAddress/$ADDR_INDEX/privateIpAddress?format=text&api-version=2017-04-02. Il récupère également la taille du sous-réseau et le préfixe de l'interface depuis http://169.254.169.254/metadata/instance/network/interface/$IFACE_INDEX/ipv4/subnet/0/address/?format=text&api-version=2017-04-02. et http://169.254.169.254/metadata/instance/network/interface/$IFACE_INDEX/ipv4/subnet/0/prefix/?format=text&api-version=2017-04-02.
•À ce stade, nous avons une liste de toutes les interfaces (par adresse MAC) et de leurs adresses IPv4 configurées.

Ensuite, l'outil configure le système comme il le fait pour l'environnement AWS. C'est-à-dire, en utilisant le routage par politique basé sur la source avec les tables/règles 30200/30400.

Alibaba Cloud (Aliyun)

Pour Aliyun, les outils tentent de récupérer la configuration depuis http://100.100.100.200/. Actuellement, il ne configure que l'IPv4 et ne fait rien concernant l'IPv6. Il effectuera les actions suivantes.

•Premièrement, il récupère http://100.100.100.200/2016-01-01/meta-data/ pour déterminer si l'API attendue est présente. Cela détermine si l'environnement Aliyun est détecté et s'il faut procéder à la configuration de l'hôte en utilisant les métadonnées Aliyun.
•Récupère http://100.100.100.200/2016-01-01/meta-data/network/interfaces/macs/ pour obtenir la liste des interfaces disponibles. Les interfaces sont identifiées par leur adresse MAC.
•Ensuite, pour chaque interface, il récupère

Il prend en charge les environnements cloud suivants :

Amazon Web Services (AWS)
Oracle Cloud (OCI)

Le but est de configurer les interfaces réseau d'un système invité cloud, en utilisant les métadonnées fournies par le fournisseur cloud. Il peut configurer plusieurs interfaces réseau et plusieurs adresses IP par interface.

UTILISATION

Le service nm-cloud-setup est activé et démarré automatiquement via systemd au démarrage du système. Il n'est généralement pas nécessaire de l'appeler manuellement.

Si vous souhaitez désactiver la configuration automatique pour une interface particulière, vous pouvez définir la clé de propriété org.freedesktop.nm-cloud-setup.skip=yes dans le profil NetworkManager de cette interface.

DÉTAILS

Amazon Web Services (AWS)

Pour AWS, l'outil essaie de récupérer la configuration à partir de http://169.254.169.254/latest/meta-data/.

Il effectuera les opérations suivantes :

•Premièrement, il récupère les adresses MAC de toutes les interfaces réseau actives à partir de http://169.254.169.254/latest/meta-data/network/interfaces/macs/.

•Ensuite, pour chaque adresse MAC, il tente de récupérer la configuration IP privée correspondante à partir de :

http://100.100.100.200/2016-01-01/meta-data/network/interfaces/macs/$MAC/vpc-cidr-block, http://100.100.100.200/2016-01-01/meta-data/network/interfaces/macs/$MAC/private-ipv4s, http://100.100.100.200/2016-01-01/meta-data/network/interfaces/macs/$MAC/netmask et http://100.100.100.200/2016-01-01/meta-data/network/interfaces/macs/$MAC/gateway. Ainsi, nous obtenons une liste d'adresses IPv4 privées, un bloc de sous-réseau CIDR et le préfixe des adresses IPv4 privées.

•Ensuite, nm-cloud-setup itère sur toutes les interfaces pour lesquelles il a pu récupérer la configuration IP. Si aucun périphérique Ethernet pour l'adresse MAC respective n'est trouvé, il est ignoré. De plus, si le périphérique n'est pas actuellement activé dans NetworkManager ou si le profil actuellement activé a une donnée utilisateur org.freedesktop.nm-cloud-setup.skip=yes, il est ignoré. De plus, s'il n'y a qu'une seule interface et une seule adresse IP, l'outil ne fait rien.

Ensuite, l'outil configure le système comme il le fait pour l'environnement AWS. C'est-à-dire, en utilisant le routage de politique basé sur la source avec les tables/règles 30200/30400. Une différence avec AWS est que la passerelle est également récupérée via les métadonnées au lieu d'utiliser la première adresse IP du sous-réseau.

Oracle Cloud (OCI)

Pour OCI, l'outil tente de récupérer la configuration à partir de http://169.254.169.254/. Actuellement, il ne configure que l'IPv4 et ne fait rien pour l'IPv6. Il fera ce qui suit.

•Premièrement, il récupère http://169.254.169.254/opc/v2/instance pour déterminer si l'API attendue est présente. Cela détermine si l'environnement OCI est détecté et s'il faut procéder à la configuration de l'hôte en utilisant les métadonnées OCI.

•Récupère http://169.254.169.254/opc/v2/vnics pour obtenir la configuration de toutes les VNICs, en récupérant leur adresse MAC, leur adresse IP privée, leur passerelle et leur bloc de sous-réseau.

•Ensuite, nm-cloud-setup itère sur toutes les interfaces pour lesquelles il a pu récupérer une configuration. Si aucun périphérique Ethernet pour l'adresse MAC respective n'est trouvé, il est ignoré. De plus, si le périphérique n'est pas actuellement activé dans NetworkManager ou si le profil actuellement activé a une donnée utilisateur org.freedesktop.nm-cloud-setup.skip=yes, il est ignoré. De plus, s'il n'y a qu'une seule interface et une seule adresse IP, l'outil ne fait rien.

Ensuite, l'outil configure le système comme il le fait pour l'environnement AWS. C'est-à-dire, en utilisant le routage de politique basé sur la source avec les tables/règles 30200/30400.
