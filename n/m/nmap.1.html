NOM

nmap - Outil d'exploration réseau et scanner de sécurité/ports

SYNTAXE

nmap [Type de scan...] [Options] {spécification de cible}

DESCRIPTION

Nmap (“Network Mapper”) est un outil open source pour l'exploration réseau et l'audit de sécurité. Il a été conçu pour scanner rapidement de grands réseaux, bien qu'il fonctionne bien contre des hôtes uniques. Nmap utilise des paquets IP bruts de manière novatrice pour déterminer quels hôtes sont disponibles sur le réseau, quels services (nom de l'application et version) ces hôtes proposent, quels systèmes d'exploitation (et versions) ils utilisent, quel type de filtres de paquets/pare-feux est en usage, et des douzaines d'autres caractéristiques. Bien que Nmap soit couramment utilisé pour les audits de sécurité, de nombreux administrateurs systèmes et réseaux le trouvent utile pour des tâches routinières telles que l'inventaire réseau, la gestion des plannings de mise à niveau de services, et la surveillance de la disponibilité des hôtes ou des services.

La sortie de Nmap est une liste des cibles scannées, avec des informations supplémentaires sur chacune en fonction des options utilisées. L'information clé parmi celles-ci est le « tableau des ports intéressants ». Ce tableau liste le numéro de port et le protocole, le nom du service, et l'état. L'état est soit ouvert, filtré, fermé, ou non filtré. Ouvert signifie qu'une application sur la machine cible écoute les connexions/paquets sur ce port. Filtré signifie qu'un pare-feu, un filtre, ou un autre obstacle réseau bloque le port de sorte que Nmap ne peut pas dire s'il est ouvert ou fermé. Les ports fermés n'ont aucune application en écoute, bien qu'ils puissent s'ouvrir à tout moment. Les ports sont classés comme non filtrés lorsqu'ils répondent aux sondes de Nmap, mais Nmap ne peut pas déterminer s'ils sont ouverts ou fermés. Nmap signale les combinaisons d'états ouvert|filtré et fermé|filtré lorsqu'il ne peut pas déterminer lequel des deux états décrit un port. Le tableau des ports peut également inclure des détails sur la version logicielle lorsque la détection de version a été demandée. Lorsqu'un scan de protocole IP est demandé (-sO), Nmap fournit des informations sur les protocoles IP supportés plutôt que sur les ports d'écoute.

En plus du tableau des ports intéressants, Nmap peut fournir des informations supplémentaires sur les cibles, y compris les noms DNS inversés, des suppositions sur le système d'exploitation, les types d'appareils et les adresses MAC.

Un scan Nmap typique est montré dans l'Exemple 1. Les seuls arguments Nmap utilisés dans cet exemple sont -A, pour activer la détection du système d'exploitation et de la version, le scan par script, et traceroute ; -T4 pour une exécution plus rapide ; et ensuite le nom d'hôte.

OPTIONS

The first argument that is not an option or an option argument is treated as the beginning of the host specification list. All subsequent arguments are also treated as host specifications. When Nmap is run, it first scans the hosts specified on the command line, and then processes target specifications from the input file specified by the -iL option (if given), and finally adds randomly chosen hosts if the -iR option is given.

Nmap supports a number of options to control its behavior. Most options can be specified in either short form (a single hyphen followed by a letter, e.g. -v) or long form (two hyphens followed by a descriptive word, e.g. --verbose). Options that take an argument have a colon after the option name in the short form, or a space between the option name and the argument in the long form.

For example, the following are equivalent:

nmap -v -p 80-100 localhost
nmap --verbose --port 80-100 localhost

Options can be grouped. For example, -sS is the same as -S. If the option requires an argument, then the argument must follow the last option in the group. For example, -sS -p 80 is the same as -sSp 80.

Options not mentioned in this manual page are passed directly to the underlying scanning engine.

SCAN TYPES

Nmap offers a variety of scan types, each with different characteristics. The default scan type is -sS if the user is privileged (root or Administrator), and -sT otherwise.

-sS
TCP SYN scan (also known as half-open, clandestine, or stealth scan). This is the default scan type if the user has raw socket privileges. It works by sending a SYN packet to the target port, without establishing a full connection. If the port is open, the target responds with a SYN/ACK, indicating that it is ready to complete the connection. Nmap then sends an RST packet to tear down the connection, leaving the port in an open state but without completing the three-way handshake. This method is generally faster and more stealthy than a full TCP connect scan because it's less likely to be logged by the target system.
-sT
TCP connect scan. This is the default scan type when the user lacks raw socket privileges. It attempts to complete the three-way handshake for every port. If the connection is successful, the port is open. This scan is more detectable and slower than a SYN scan, as it involves a full connection for each port.
-sU
UDP scan. This scan sends a UDP packet to the target port. If an ICMP "port unreachable" message is returned, the port is closed. If a UDP response is received, the port is open. If no response is received after several retransmissions, the port is marked as open|filtered. UDP scanning is slower than TCP scanning because UDP is a connectionless protocol and requires retransmissions to increase confidence.
-sV
Service version detection. This option attempts to determine the service (e.g., Apache, Netcat) and version number running on the target port. It does this by sending specialized probes to the port and analyzing the responses.
-O
Enable OS detection. Nmap attempts to determine the operating system of the target host by sending a variety of probes and analyzing the responses. This feature relies on a database of OS "fingerprints."
-sC
Run default scripts. This option executes a set of default Nmap Scripting Engine (NSE) scripts against the target. These scripts can be used for various purposes, including vulnerability detection, further service enumeration, and more.
--script <scriptname>[,...]<category>[,...]<directory>[,...]
Run scripts. This option allows you to specify which NSE scripts to run. You can provide script names, categories (e.g., 'vuln', 'discovery'), or directories. Scripts can be separated by commas. Scripts are downloaded from the Nmap Scripting Engine repository.

PORT SPECIFICATION

By default, Nmap scans the 1000 most common TCP ports. The following options can be used to alter this behavior:

-p <portranges>
Specifies which ports to scan. The default is 1-1000. You can specify individual ports, ranges of ports, and comma-separated lists of ports. For example, -p 22,53,135-445. You can also use -p- to scan all 65535 ports, or -p T:80,U:53 to specify TCP and UDP ports separately.
-F
Fast scan. This option scans only the 100 most common ports instead of the default 1000. It's equivalent to -p 1-100.
--top-ports <number>
Scan the specified number of the most common ports. For example, --top-ports 20 scans the 20 most common ports.
-r
Skip randomization of ports. By default, Nmap randomizes the order in which ports are scanned. This option disables that randomization.

TIMING AND PERFORMANCE

These options control the speed and efficiency of the scan.

-T0
Paranoid level. Extremely slow, used to evade Intrusion Detection Systems. Will likely take longer than 10 minutes per host.
-T1
Sneaky level. Slow, used to evade Intrusion Detection Systems. Will likely take several minutes per host.
-T2
Polite level. Slows down the scan to consume less bandwidth and affect the target less. Will likely take about a minute per host.
-T3
Normal level. This is the default timing template. It's a balance between speed and accuracy.
-T4
Aggressive level. Speeds up the scan by making assumptions that network latency won't cause problems. Good for faster scans on reliable networks.
-T5
Insane level. Very aggressive. Assumes a lightning-fast network, and may miss open ports on slow or unreliable networks.
--min-rate <number>
Send packets no slower than <number> per second.
--max-rate <number>
Send packets no faster than <number> per second.
--max-scan-delay <time>
Adjust delay between probes.

FIREWALL/IDS EVASION AND SPOOFING

These options are used to evade firewalls, Intrusion Detection Systems (IDS), and spoof network information.

-f, --mtu <val>
Fragment packets. Optionally specify the Maximum Transmission Unit (MTU) size for fragmentation. Fragmentation can help bypass some firewalls that don't handle fragmented packets well.
-D <decoy1,decoy2[,ME],...>
Cloak a scan with decoys. Specify a comma-separated list of IP addresses or hostnames to use as decoys. Nmap will send probes to these decoys in addition to the target, making it harder to identify the source of the scan.
-S <IP_Address>
Spoof source address. Use the specified IP address as the source address in the probes sent. This is useful for making it appear as if the scan originated from a different IP.
-e <iface>
Use specified interface. Use the given network interface for sending and receiving packets.
-g, --source-port <portnum>
Use given source port number. Send probes from the specified source port. This can sometimes bypass firewall rules that only allow specific ports.
--proxies <url1,[url2],...>
Relay connections through HTTP/SOCKS4 proxies. Nmap will use the specified proxies to perform the scan.
--data <hex string>
Append a custom payload in hexadecimal format to sent packets.
--data-string <string>
Append a custom ASCII string to sent packets.
--data-length <num>
Append random data of the specified length to sent packets.
--ip-options <options>
Send packets with specified IP options. This allows for manipulating the IP header options, which can sometimes affect how routers and firewalls process the packets.
--ttl <val>
Set IP time-to-live field. This option allows you to control the TTL value in the IP header, which can influence how far packets travel across networks.
--spoof-mac <mac address/prefix/vendor name>
Spoof your MAC address. Specify a MAC address, a MAC address prefix, or a vendor name to use as the source MAC address. This can be useful for MAC-based filtering evasion.
--badsum
Send packets with a bogus TCP/UDP/SCTP checksum. This can cause some network devices to drop the packets, potentially leading to evasion.

TARGET SPECIFICATION

Everything on the Nmap command-line that isn't an option (or option argument) is treated as a target host specification. The simplest case is to specify a target IP address or hostname for scanning.

When a hostname is given as a target, it is resolved via the Domain Name System (DNS) to determine the IP address to scan. If the name resolves to more than one IP address, only the first one will be scanned. To make Nmap scan all the resolved addresses instead of only the first one, use the --resolve-all option.

Sometimes you wish to scan a whole network of adjacent hosts. For this, Nmap supports CIDR-style addressing. You can append /numbits to an IP address or hostname and Nmap will scan every IP address for which the first numbits are the same as for the reference IP or hostname given. For example, 192.168.10.0/24 would scan the 256 hosts between 192.168.10.0 (binary: 11000000 10101000 00001010 00000000) and 192.168.10.255 (binary: 11000000 10101000 00001010 11111111), inclusive. 192.168.10.40/24 would scan exactly the same targets. Given that the host scanme.nmap.org is at the IP address 64.13.134.52, the specification scanme.nmap.org/16 would scan the 65,536 IP addresses between 64.13.0.0 and 64.13.255.255. The smallest allowed value is /0, which targets the whole Internet. The largest value for IPv4 is /32, which scans just the named host or IP address because all address bits are fixed. The largest value for IPv6 is /128, which does the same thing.

CIDR notation is short but not always flexible enough. For example, you might want to scan 192.168.0.0/16 but skip any IPs ending with .0 or .255 because they may be used as subnet network and broadcast addresses. Nmap supports this through octet range addressing. Rather than specify a normal IP address, you can specify a comma-separated list of numbers or ranges for each octet. For example, 192.168.0-255.1-254 will skip all addresses in the range that end in .0 or .255, and 192.168.3-5,7.1 will scan the four addresses 192.168.3.1, 192.168.4.1, 192.168.5.1, and 192.168.7.1. Either side of a range may be omitted; the default values are 0 on the left and 255 on the right. Using - by itself is the same as 0-255, but remember to use 0- in the first octet so the target specification doesn't look like a command-line option. Ranges need not be limited to the final octets: the specifier 0-255.0-255.13.37 will perform an Internet-wide scan for all IP addresses ending in 13.37. This sort of broad sampling can be useful for Internet surveys and research.

IPv6 addresses can be specified by their fully qualified IPv6 address or hostname or with CIDR notation for subnets. Octet ranges aren't yet supported for IPv6.

IPv6 addresses with non-global scope need to have a zone ID suffix. On Unix systems, this is a percent sign followed by an interface name; a complete address might be fe80::a8bb:ccff:fedd:eeff%eth0. On Windows, use an interface index number in place of an interface name: fe80::a8bb:ccff:fedd:eeff%1. You can see a list of interface indexes by running the command netsh.exe interface ipv6 show interface.

Nmap accepts multiple host specifications on the command line, and they don't need to be the same type. The command nmap scanme.nmap.org 192.168.0.0/8 10.0.0,1,3-7.- does what you would expect.

While targets are usually specified on the command lines, the following options are also available to control target selection:

-iL inputfilename (Input from list)

Reads target specifications from inputfilename. Passing a huge list of hosts is often awkward on the command line, yet it is a common desire. For example, your DHCP server might export a list of 10,000 current leases that you wish to scan. Or maybe you want to scan all IP addresses except for those to locate hosts using unauthorized static IP addresses. Simply generate the list of hosts to scan and pass that filename to Nmap as an argument to the -iL option. Entries can be in any of the formats accepted by Nmap on the command line (IP address, hostname, CIDR, IPv6, or octet ranges). Each entry must be separated by one or more spaces, tabs, or newlines. You can specify a hyphen (-) as the filename if you want Nmap to read hosts from standard input rather than an actual file.

The input file may contain comments that start with # and extend to the end of the line.

-iR num hosts (Choose random targets)

For Internet-wide surveys and other research, you may want to choose targets at random. The num hosts argument tells Nmap how many IPs to generate. Undesirable IPs such as those in certain private, multicast, or unallocated address ranges are automatically skipped. The argument 0 can be specified for a never-ending scan. Keep in mind that some network administrators bristle at unauthorized scans of their networks and may complain. Use this option at your own risk! If you find yourself really bored one rainy afternoon, try the command nmap -Pn -sS -p 80 -iR 0 --open to locate random web servers for browsing.

--exclude host1[,host2[,...]] (Exclude hosts/networks)

Specifies a comma-separated list of targets to be excluded from the scan even if they are part of the overall network range you specify. The list you pass in uses normal Nmap syntax, so it can include hostnames, CIDR netblocks, octet ranges, etc. This can be useful when the network you wish to scan includes untouchable mission-critical servers, systems that are known to react adversely to port scans, or subnets administered by other people.

--excludefile exclude_file (Exclude list from file)

This offers the same functionality as the --exclude option, except that the excluded targets are provided in a newline-, space-, or tab-delimited exclude_file rather than on the command line.

The exclude file may contain comments that start with # and extend to the end of the line.

-n (No reverse DNS resolution)

Tells Nmap to never do reverse DNS resolution on the active IP addresses it finds. Since DNS can be slow even with Nmap's built-in parallel stub resolver, this option can slash scanning times.

-R (Reverse DNS resolution for all targets)

Tells Nmap to always do reverse DNS resolution on the target IP addresses. Normally reverse DNS is only performed against responsive (online) hosts.

--resolve-all (Scan each resolved address)

If a hostname target resolves to more than one address, scan all of them. The default behavior is to only scan the first resolved address. Regardless, only addresses in the appropriate address family will be scanned: IPv4 by default, IPv6 with -6.

--unique (Scan each address only once)

Scan each IP address only once. The default behavior is to scan each address as many times as it is specified in the target list, such as when network ranges overlap or different hostnames resolve to the same address.

--system-dns (Use system DNS resolver)

By default, Nmap resolves names to IP addresses (and IP addresses to names) by sending queries directly to the name servers configured on your host and then listening for responses. Many requests (often dozens) are performed in parallel to improve performance. Specify this option to use your system resolver instead (one IP at a time via the getnameinfo call). This is slower and rarely useful unless you find a bug in the Nmap parallel resolver (please let us know if you do).

--dns-servers server1[,server2[,...]] (Servers to use for DNS queries)

By default, Nmap determines your DNS servers from your resolv.conf file (Unix) or the Registry (Win32). Alternatively, you may use this option to specify alternate servers. This option is not honored if you are using --system-dns. Using multiple DNS servers is often faster, especially if you choose authoritative servers for your target IP space. This option can also improve stealth, as your requests can be bounced off just about any recursive DNS server on the Internet.

SPÉCIFICATION DE CIBLE

Tout sur la ligne de commande Nmap qui n'est pas une option (ou un argument d'option) est traité comme une spécification d'hôte cible. Le cas le plus simple est de spécifier une adresse IP cible ou un nom d'hôte pour le scan.

Lorsqu'un nom d'hôte est donné comme cible, il est résolu via le système de noms de domaine (DNS) pour déterminer l'adresse IP à scanner. Si le nom se résout en plusieurs adresses IP, seule la première sera scannée. Pour que Nmap scanne toutes les adresses résolues au lieu de seulement la première, utilisez l'option --resolve-all.

Parfois, vous souhaitez scanner tout un réseau d'hôtes adjacents. Pour cela, Nmap prend en charge l'adressage de style CIDR. Vous pouvez ajouter /numbits à une adresse IP ou à un nom d'hôte et Nmap scannera toutes les adresses IP pour lesquelles les numbits premiers sont les mêmes que pour l'IP ou le nom d'hôte de référence donné. Par exemple, 192.168.10.0/24 scannerait les 256 hôtes entre 192.168.10.0 (binaire: 11000000 10101000 00001010 00000000) et 192.168.10.255 (binaire: 11000000 10101000 00001010 11111111), inclus. 192.168.10.40/24 scannerait exactement les mêmes cibles. Étant donné que l'hôte scanme.nmap.org se trouve à l'adresse IP 64.13.134.52, la spécification scanme.nmap.org/16 scannerait les 65 536 adresses IP entre 64.13.0.0 et 64.13.255.255. La plus petite valeur autorisée est /0, qui cible l'Internet entier. La plus grande valeur pour IPv4 est /32, qui scanne uniquement l'hôte nommé ou l'adresse IP car tous les bits d'adresse sont fixés. La plus grande valeur pour IPv6 est /128, ce qui fait la même chose.

La notation CIDR est courte mais pas toujours assez flexible. Par exemple, vous pourriez vouloir scanner 192.168.0.0/16 mais ignorer toutes les adresses IP se terminant par .0 ou .255 car elles peuvent être utilisées comme adresses réseau et de diffusion de sous-réseau. Nmap prend en charge cela via l'adressage par plages d'octets. Au lieu de spécifier une adresse IP normale, vous pouvez spécifier une liste d'entiers ou de plages séparés par des virgules pour chaque octet. Par exemple, 192.168.0-255.1-254 ignorera toutes les adresses de la plage se terminant par .0 ou .255, et 192.168.3-5,7.1 scannera les quatre adresses 192.168.3.1, 192.168.4.1, 192.168.5.1 et 192.168.7.1. Un côté d'une plage peut être omis ; les valeurs par défaut sont 0 à gauche et 255 à droite. Utiliser - tout seul est la même chose que 0-255, mais n'oubliez pas d'utiliser 0- dans le premier octet afin que la spécification de cible ne ressemble pas à une option de ligne de commande. Les plages ne se limitent pas nécessairement aux octets finaux : le spécificateur 0-255.0-255.13.37 effectuera un scan de l'ensemble d'Internet pour toutes les adresses IP se terminant par 13.37. Ce type d'échantillonnage large peut être utile pour les enquêtes et la recherche sur Internet.

Les adresses IPv6 peuvent être spécifiées par leur adresse IPv6 complète qualifiée ou leur nom d'hôte ou avec la notation CIDR pour les sous-réseaux. Les plages d'octets ne sont pas encore prises en charge pour IPv6.

Les adresses IPv6 avec une portée non globale nécessitent un suffixe d'ID de zone. Sur les systèmes Unix, il s'agit d'un signe de pourcentage suivi d'un nom d'interface ; une adresse complète pourrait être fe80::a8bb:ccff:fedd:eeff%eth0. Sous Windows, utilisez un index d'interface à la place d'un nom d'interface : fe80::a8bb:ccff:fedd:eeff%1. Vous pouvez voir une liste des index d'interface en exécutant la commande netsh.exe interface ipv6 show interface.

Nmap accepte plusieurs spécifications d'hôtes sur la ligne de commande, et elles n'ont pas besoin d'être du même type. La commande nmap scanme.nmap.org 192.168.0.0/8 10.0.0,1,3-7.- fait ce que vous attendez.

Bien que les cibles soient généralement spécifiées sur les lignes de commande, les options suivantes sont également disponibles pour contrôler la sélection des cibles :

-iL inputfilename (Entrée depuis une liste)

Lit les spécifications de cible depuis inputfilename. Passer une liste d'hôtes énorme est souvent gênant sur la ligne de commande, pourtant c'est un désir courant. Par exemple, votre serveur DHCP pourrait exporter une liste de 10 000 baux actuels que vous souhaitez scanner. Ou peut-être voulez-vous scanner toutes les adresses IP sauf celles pour localiser des hôtes utilisant des adresses IP statiques non autorisées. Générez simplement la liste des hôtes à scanner et passez ce nom de fichier à Nmap comme argument de l'option -iL. Les entrées peuvent être dans l'un des formats acceptés par Nmap sur la ligne de commande (adresse IP, nom d'hôte, CIDR, IPv6 ou plages d'octets). Chaque entrée doit être séparée par un ou plusieurs espaces, tabulations ou sauts de ligne. Vous pouvez spécifier un tiret (-) comme nom de fichier si vous voulez que Nmap lise les hôtes depuis l'entrée standard plutôt qu'un fichier réel.

Le fichier d'entrée peut contenir des commentaires commençant par # et allant jusqu'à la fin de la ligne.

-iR num hosts (Choisir des cibles aléatoires)

Pour des enquêtes à l'échelle d'Internet et d'autres recherches, vous pourriez vouloir choisir des cibles au hasard. L'argument num hosts indique à Nmap combien d'adresses IP générer. Les adresses IP indésirables telles que celles de certaines plages privées, multicast ou non allouées sont automatiquement ignorées. L'argument 0 peut être spécifié pour un scan sans fin. Gardez à l'esprit que certains administrateurs réseau n'apprécient pas les scans non autorisés de leurs réseaux et peuvent se plaindre. Utilisez cette option à vos propres risques ! Si vous vous trouvez vraiment ennuyé un après-midi pluvieux, essayez la commande nmap -Pn -sS -p 80 -iR 0 --open pour localiser des serveurs web aléatoires à parcourir.

--exclude host1[,host2[,...]] (Exclure des hôtes/réseaux)

Spécifie une liste de cibles séparées par des virgules à exclure du scan, même si elles font partie de la plage réseau globale que vous spécifiez. La liste que vous passez utilise la syntaxe Nmap normale, elle peut donc inclure des noms d'hôtes, des blocs réseau CIDR, des plages d'octets, etc. Cela peut être utile lorsque le réseau que vous souhaitez scanner comprend des serveurs critiques intouchables, des systèmes connus pour réagir négativement aux scans de ports, ou des sous-réseaux administrés par d'autres personnes.

--excludefile exclude_file (Liste d'exclusion depuis un fichier)

Ceci offre la même fonctionnalité que l'option --exclude, sauf que les cibles exclues sont fournies dans un fichier exclude_file délimité par des sauts de ligne, des espaces ou des tabulations, plutôt que sur la ligne de commande.

Le fichier d'exclusion peut contenir des commentaires commençant par # et allant jusqu'à la fin de la ligne.

-n (Pas de résolution DNS inverse)

Indique à Nmap de ne jamais effectuer de résolution DNS inverse sur les adresses IP actives qu'il trouve. Comme le DNS peut être lent même avec le résolveur stub parallèle intégré de Nmap, cette option peut réduire considérablement les temps de scan.

-R (Résolution DNS inverse pour toutes les cibles)

Indique à Nmap d'effectuer toujours une résolution DNS inverse sur les adresses IP cibles. Normalement, la résolution DNS inverse n'est effectuée que sur les hôtes réactifs (en ligne).

--resolve-all (Scanner chaque adresse résolue)

Si une cible de nom d'hôte se résout en plusieurs adresses, scannez-les toutes. Le comportement par défaut est de scanner uniquement la première adresse résolue. Quoi qu'il en soit, seules les adresses de la famille d'adresses appropriée seront scannées : IPv4 par défaut, IPv6 avec -6.

--unique (Scanner chaque adresse une seule fois)

Scanne chaque adresse IP une seule fois. Le comportement par défaut est de scanner chaque adresse autant de fois qu'elle est spécifiée dans la liste des cibles, comme lorsque les plages réseau se chevauchent ou que différents noms d'hôtes se résolvent en la même adresse.

--system-dns (Utiliser le résolveur DNS du système)

Par défaut, Nmap résout les noms en adresses IP (et les adresses IP en noms) en envoyant des requêtes directement aux serveurs de noms configurés sur votre hôte, puis en écoutant les réponses. De nombreuses requêtes (souvent des dizaines) sont effectuées en parallèle pour améliorer les performances. Spécifiez cette option pour utiliser votre résolveur système à la place (une IP à la fois via l'appel getnameinfo). C'est plus lent et rarement utile, sauf si vous trouvez un bug dans le résolveur parallèle de Nmap (veuillez nous en informer si c'est le cas).

--dns-servers server1[,server2[,...]] (Serveurs à utiliser pour les requêtes DNS)

Par défaut, Nmap détermine vos serveurs DNS à partir de votre fichier resolv.conf (Unix) ou du Registre (Win32). Alternativement, vous pouvez utiliser cette option pour spécifier des serveurs alternatifs. Cette option n'est pas prise en compte si vous utilisez --system-dns. L'utilisation de plusieurs serveurs DNS est souvent plus rapide, surtout si vous choisissez des serveurs faisant autorité pour votre espace d'adresses IP cible. Cette option peut également améliorer la discrétion, car vos requêtes peuvent être transmises à presque n'importe quel serveur DNS récursif sur Internet.

Cette option est également utile lors du scan de réseaux privés. Parfois, seuls quelques serveurs de noms fournissent une résolution appropriée

DÉCOUVERTE D'HÔTES

L'une des toutes premières étapes de toute mission de reconnaissance réseau consiste à réduire un ensemble (parfois énorme) de plages d'adresses IP en une liste d'hôtes actifs ou intéressants. Scanner chaque port de chaque adresse IP est lent et généralement inutile. Bien sûr, ce qui rend un hôte intéressant dépend grandement des objectifs du scan. Les administrateurs réseau peuvent uniquement s'intéresser aux hôtes exécutant un certain service, tandis que les auditeurs de sécurité peuvent se soucier de chaque appareil doté d'une adresse IP. Un administrateur peut se contenter d'un simple ping ICMP pour localiser les hôtes sur son réseau interne, tandis qu'un testeur d'intrusion externe peut utiliser un ensemble diversifié de dizaines de sondes pour tenter de contourner les restrictions du pare-feu.

Comme les besoins en matière de découverte d'hôtes sont très diversifiés, Nmap offre une large gamme d'options pour personnaliser les techniques utilisées. La découverte d'hôtes est parfois appelée scan ping, mais elle va bien au-delà des simples paquets ICMP echo request associés à l'outil ping omniprésent. Les utilisateurs peuvent ignorer complètement l'étape de découverte avec un scan de liste (-sL) ou en désactivant la découverte d'hôtes (-Pn), ou engager le réseau avec des combinaisons arbitraires de sondes TCP SYN/ACK, UDP, SCTP INIT et ICMP multiples. Le but de ces sondes est d'obtenir des réponses qui démontrent qu'une adresse IP est effectivement active (utilisée par un hôte ou un appareil réseau). Sur de nombreux réseaux, seul un faible pourcentage d'adresses IP est actif à un moment donné. Ceci est particulièrement courant avec les espaces d'adresses privés tels que 10.0.0.0/8. Ce réseau compte 16 millions d'adresses IP, mais j'ai vu des entreprises l'utiliser avec moins d'un millier de machines. La découverte d'hôtes peut trouver ces machines dans une mer d'adresses IP sparsement allouées.

Si aucune option de découverte d'hôtes n'est fournie, Nmap envoie une requête ICMP echo, un paquet TCP SYN au port 443, un paquet TCP ACK au port 80 et une requête d'horodatage ICMP. (Pour IPv6, la requête d'horodatage ICMP est omise car elle ne fait pas partie d'ICMPv6.) Ces valeurs par défaut sont équivalentes aux options -PE -PS443 -PA80 -PP. Les exceptions sont les scans ARP (pour IPv4) et Neighbor Discovery (pour IPv6) qui sont utilisés pour toutes les cibles sur un réseau Ethernet local. Pour les utilisateurs de shell Unix non privilégiés, les sondes par défaut sont un paquet SYN aux ports 80 et 443 utilisant l'appel système connect. Cette découverte d'hôtes est souvent suffisante lors du scan de réseaux locaux, mais un ensemble plus complet de sondes de découverte est recommandé pour l'audit de sécurité.

Les options -P* (qui sélectionnent les types de ping) peuvent être combinées. Vous pouvez augmenter vos chances de pénétrer des pare-feux stricts en envoyant de nombreux types de sondes utilisant différents ports/flags TCP et codes ICMP. Notez également que la découverte ARP/Neighbor est effectuée par défaut contre les cibles sur un réseau Ethernet local, même si vous spécifiez d'autres options -P*, car elle est presque toujours plus rapide et plus efficace.

Par défaut, Nmap effectue la découverte d'hôtes, puis un scan de ports contre chaque hôte qu'il détermine comme étant en ligne. C'est vrai même si vous spécifiez des types de découverte d'hôtes non par défaut, tels que les sondes UDP (-PU). Lisez l'option -sn pour savoir comment effectuer uniquement la découverte d'hôtes, ou utilisez -Pn pour ignorer la découverte d'hôtes et scanner tous les adresses IP cibles. Les options suivantes contrôlent la découverte d'hôtes :

-sL (Scan de liste)

Le scan de liste est une forme dégénérée de découverte d'hôtes qui liste simplement chaque hôte du ou des réseaux spécifiés, sans envoyer de paquets aux hôtes cibles. Par défaut, Nmap effectue toujours une résolution DNS inversée sur les hôtes pour connaître leurs noms. Il est souvent surprenant de voir la quantité d'informations utiles que fournissent les noms d'hôtes simples. Par exemple, fw.chi est le nom du pare-feu de Chicago d'une entreprise.

Nmap affiche également le nombre total d'adresses IP à la fin. Le scan de liste est un bon contrôle de sanity pour s'assurer que vous avez les bonnes adresses IP pour vos cibles. Si les hôtes arborent des noms de domaine que vous ne reconnaissez pas, il vaut la peine d'approfondir pour éviter de scanner le réseau de la mauvaise entreprise.

Étant donné que l'objectif est simplement d'afficher une liste d'hôtes cibles, les options de fonctionnalités de niveau supérieur telles que le scan de ports, la détection d'OS ou la découverte d'hôtes ne peuvent pas être combinées avec celle-ci. Si vous souhaitez désactiver la découverte d'hôtes tout en effectuant ces fonctionnalités de niveau supérieur, lisez l'option -Pn (ignorer la découverte d'hôtes).

-sn (Pas de scan de ports)

Cette option indique à Nmap de ne pas effectuer de scan de ports après la découverte d'hôtes, et d'afficher uniquement les hôtes disponibles qui ont répondu aux sondes de découverte d'hôtes. Ceci est souvent appelé un « scan ping », mais vous pouvez également demander l'exécution de traceroute et de scripts hôtes NSE. C'est par défaut une étape plus intrusive que le scan de liste, et peut souvent être utilisé dans les mêmes buts. Il permet une reconnaissance légère d'un réseau cible sans attirer beaucoup d'attention. Savoir combien d'hôtes sont actifs est plus précieux pour les attaquants que la liste fournie par le scan de liste de chaque adresse IP et nom d'hôte.

Les administrateurs système trouvent également souvent cette option utile. Elle peut facilement être utilisée pour compter les machines disponibles sur un réseau ou surveiller la disponibilité des serveurs. Ceci est souvent appelé un balayage ping, et est plus fiable que de pinger l'adresse de diffusion car de nombreux hôtes ne répondent pas aux requêtes de diffusion.

La découverte d'hôtes par défaut effectuée avec -sn consiste en une requête ICMP echo, un SYN TCP au port 443, un ACK TCP au port 80 et une requête d'horodatage ICMP par défaut. Lors de l'exécution par un utilisateur non privilégié, seuls des paquets SYN sont envoyés (en utilisant un appel connect) aux ports 80 et 443 sur la cible. Lorsqu'un utilisateur privilégié essaie de scanner des cibles sur un réseau Ethernet local, des requêtes ARP sont utilisées, sauf si --send-ip a été spécifié. L'option -sn peut être combinée avec tous les types de sondes de découverte (les options -P*) pour une plus grande flexibilité. Si l'une de ces options de type de sonde et de numéro de port est utilisée, les sondes par défaut sont remplacées. Lorsque des pare-feux stricts sont en place entre l'hôte source exécutant Nmap et le réseau cible, l'utilisation de ces techniques avancées est recommandée. Sinon, des hôtes pourraient être manqués lorsque le pare-feu bloque les sondes ou leurs réponses.

Dans les versions précédentes de Nmap, -sn était connu sous le nom de -sP.

-Pn (Pas de ping)

Cette option ignore complètement l'étape de découverte d'hôtes. Normalement, Nmap utilise cette étape pour déterminer les machines actives pour des scans plus intensifs et pour évaluer la vitesse du réseau. Par défaut, Nmap n'effectue des sondes intensives telles que les scans de ports, la détection de version ou la détection d'OS que contre les hôtes trouvés comme étant en ligne. Désactiver la découverte d'hôtes avec -Pn oblige Nmap à tenter les fonctions de scan demandées contre *chaque* adresse IP cible spécifiée. Ainsi, si un réseau /16 est spécifié sur la ligne de commande, les 65 536 adresses IP sont scannées. La découverte d'hôtes appropriée est ignorée, comme avec le scan de liste, mais au lieu de s'arrêter et d'afficher la liste des cibles, Nmap continue d'effectuer les fonctions demandées comme si chaque adresse IP cible était active. Les paramètres de temporisation par défaut sont utilisés, ce qui peut entraîner des scans plus lents. Pour ignorer la découverte d'hôtes *et* le scan de ports, tout en permettant à NSE de s'exécuter, utilisez les deux options -Pn -sn ensemble.

Pour les machines sur un réseau Ethernet local, le scan ARP sera toujours effectué (sauf si --disable-arp-ping ou --send-ip est spécifié) car Nmap a besoin des adresses MAC pour scanner davantage les hôtes cibles. Dans les versions précédentes de Nmap, -Pn était -P0 et -PN.

-PS liste de ports (Ping TCP SYN)

Cette option envoie un paquet TCP vide avec le drapeau SYN défini. Le port de destination par défaut est 80 (configurable à la compilation en modifiant DEFAULT_TCP_PROBE_PORT_SPEC dans nmap.h). Des ports alternatifs peuvent être spécifiés en paramètre. La syntaxe est la même que pour -p, sauf que les spécificateurs de type de port comme T: ne sont pas autorisés. Exemples : -PS22 et -PS22-25,80,113,1050,35000. Notez qu'il ne peut y avoir d'espace entre -PS et la liste de ports. Si plusieurs sondes sont spécifiées, elles seront envoyées en parallèle.

Le drapeau SYN suggère au système distant que vous tentez d'établir une connexion. Normalement, le port de destination sera fermé, et un paquet RST (reset) sera renvoyé. Si le port se trouve être ouvert, la cible effectuera la deuxième étape d'une poignée de main TCP en trois temps en répondant par un paquet TCP SYN/ACK. La machine exécutant Nmap met alors fin à la connexion naissante en répondant par un RST plutôt qu'en envoyant un paquet ACK qui compléterait la poignée de main en trois temps et établirait une connexion complète. Le paquet RST est envoyé par le noyau de la machine exécutant Nmap en réponse au SYN/ACK inattendu, et non par Nmap lui-même.

Nmap se soucie peu de savoir si le port est ouvert ou fermé. Que ce soit la réponse RST ou SYN/ACK mentionnée précédemment indique à Nmap que l'hôte est disponible et réactif.

Sur les machines Unix, seul l'utilisateur privilégié root est généralement capable d'envoyer et de recevoir des paquets TCP bruts. Pour les utilisateurs non privilégiés, une solution de contournement est automatiquement employée : l'appel système connect est initié contre chaque port cible. Cela a pour effet d'envoyer un paquet SYN à l'hôte cible, dans une tentative d'établir une connexion. Si connect renvoie un succès rapide ou une erreur ECONNREFUSED, la pile TCP sous-jacente doit avoir reçu un SYN/ACK ou un RST et l'hôte est marqué comme disponible. Si la tentative de connexion est laissée en suspens jusqu'à ce qu'un délai d'attente soit atteint, l'hôte est marqué comme inactif.

-PA liste de ports (Ping TCP ACK)

Le ping TCP ACK est très similaire au ping SYN dont nous venons de parler. La différence, comme vous l'avez probablement deviné, est que le drapeau TCP ACK est défini au lieu du drapeau SYN. Un tel paquet ACK prétend accuser réception de données sur une connexion TCP établie, mais aucune telle connexion n'existe. Les hôtes distants devraient donc toujours répondre avec un paquet RST, révélant ainsi leur existence.

L'option -PA utilise le même port par défaut que la sonde SYN (80) et peut également accepter une liste de ports de destination dans le même format. Si un utilisateur non privilégié essaie ceci, la solution de contournement connect mentionnée précédemment est utilisée. Cette solution de contournement est imparfaite car connect envoie en réalité un paquet SYN plutôt qu'un ACK.

La raison pour laquelle on propose des sondes ping SYN et ACK est d'optimiser les chances de contourner les pare-feux. De nombreux administrateurs configurent les routeurs et autres pare-feux simples pour bloquer les paquets SYN entrants, sauf ceux

destinés aux services publics comme le site web de l'entreprise ou le serveur de messagerie. Cela empêche d'autres connexions entrantes vers l'organisation, tout en permettant aux utilisateurs d'établir des connexions sortantes non obstruées vers Internet. Cette approche sans état consomme peu de ressources sur le pare-feu/routeur et est largement prise en charge par les filtres matériels et logiciels. Le logiciel de pare-feu Linux Netfilter/iptables offre l'option pratique --syn pour implémenter cette approche sans état. Lorsque des règles de pare-feu sans état comme celle-ci sont en place, les sondes SYN ping (-PS) sont susceptibles d'être bloquées lorsqu'elles sont envoyées à des ports cibles fermés. Dans de tels cas, la sonde ACK brille car elle traverse ces règles.

Un autre type courant de pare-feu utilise des règles avec état qui rejettent les paquets inattendus. Cette fonctionnalité se trouvait initialement surtout sur les pare-feux haut de gamme, bien qu'elle soit devenue beaucoup plus courante au fil des années. Le système Linux Netfilter/iptables prend en charge cela via l'option --state, qui catégorise les paquets en fonction de l'état de la connexion. Une sonde SYN est plus susceptible de fonctionner contre un tel système, car les paquets ACK inattendus sont généralement reconnus comme invalides et rejetés. Une solution à cette énigme consiste à envoyer à la fois des sondes SYN et ACK en spécifiant -PS et -PA.

-PU liste de ports (UDP Ping)

Une autre option de découverte d'hôtes est le ping UDP, qui envoie un paquet UDP aux ports spécifiés. Pour la plupart des ports, le paquet sera vide, bien que certains utilisent une charge utile spécifique au protocole qui est plus susceptible de susciter une réponse.

Les charges utiles sont les mêmes sondes utilisées dans la détection de services et de versions et sont définies dans le fichier nmap-service-probes.

Le contenu du paquet peut également être affecté avec les options --data, --data-string et --data-length.

La liste de ports prend le même format qu'avec les options -PS et -PA discutées précédemment. Si aucun port n'est spécifié, la valeur par défaut est 40125. Cette valeur par défaut peut être configurée au moment de la compilation en modifiant DEFAULT_UDP_PROBE_PORT_SPEC dans nmap.h. Un port très peu commun est utilisé par défaut car l'envoi à des ports ouverts est souvent indésirable pour ce type de scan particulier.

Lorsqu'un port fermé sur la machine cible est atteint, la sonde UDP devrait retourner un paquet ICMP port unreachable en retour. Cela signifie pour Nmap que la machine est active et disponible. De nombreux autres types d'erreurs ICMP, tels que host/network unreachables ou TTL exceeded, indiquent un hôte inactif ou inaccessible. L'absence de réponse est également interprétée de cette manière. Si un port ouvert est atteint, la plupart des services ignorent simplement le paquet vide et ne renvoient aucune réponse. C'est pourquoi le port de sonde par défaut est 40125, qui est très peu susceptible d'être utilisé. Quelques services, tels que le protocole Character Generator (chargen), répondront à un paquet UDP vide, et révéleront ainsi à Nmap que la machine est disponible.

L'avantage principal de ce type de scan est qu'il contourne les pare-feux et les filtres qui ne filtrent que le TCP. Par exemple, j'ai possédé autrefois un routeur haut débit sans fil Linksys BEFW11S4. L'interface externe de cet appareil filtrait tous les ports TCP par défaut, mais les sondes UDP suscitaient toujours des messages port unreachable et révélaient ainsi l'appareil.

-PY liste de ports (SCTP INIT Ping)

Cette option envoie un paquet SCTP contenant un tronçon INIT minimal. Le port de destination par défaut est 80 (configurable à la compilation en modifiant DEFAULT_SCTP_PROBE_PORT_SPEC dans nmap.h). Des ports alternatifs peuvent être spécifiés comme paramètre. La syntaxe est la même qu'avec l'option -p, sauf que les spécificateurs de type de port comme S: ne sont pas autorisés. Les exemples sont -PY22 et -PY22,80,179,5060. Notez qu'il ne peut y avoir d'espace entre -PY et la liste des ports. Si plusieurs sondes sont spécifiées, elles seront envoyées en parallèle.

Le tronçon INIT suggère au système distant que vous tentez d'établir une association. Normalement, le port de destination sera fermé, et un tronçon ABORT sera renvoyé. Si le port est ouvert, la cible prendra la deuxième étape d'une poignée de main SCTP à quatre voies en répondant avec un tronçon INIT-ACK. Si la machine exécutant Nmap possède une pile SCTP fonctionnelle, alors elle met fin à l'association naissante en répondant avec un tronçon ABORT plutôt qu'en envoyant un tronçon COOKIE-ECHO, qui serait la prochaine étape de la poignée de main à quatre voies. Le paquet ABORT est envoyé par le noyau de la machine exécutant Nmap en réponse à l'INIT-ACK inattendu, et non par Nmap lui-même.

Nmap ne se soucie pas de savoir si le port est ouvert ou fermé. La réponse ABORT ou INIT-ACK discutée précédemment indique à Nmap que l'hôte est disponible et réactif.

Sur les machines Unix, seul l'utilisateur privilégié root est généralement capable d'envoyer et de recevoir des paquets SCTP bruts. L'utilisation des SCTP INIT Pings n'est actuellement pas possible pour les utilisateurs non privilégiés.

-PE; -PP; -PM (Types de Ping ICMP)

En plus des types de découverte d'hôtes TCP, UDP et SCTP inhabituels discutés précédemment, Nmap peut envoyer les paquets standard envoyés par le programme ping omniprésent. Nmap envoie un paquet ICMP de type 8 (echo request) aux adresses IP cibles, attendant une réponse de type 0 (echo reply) des hôtes disponibles. Malheureusement pour les explorateurs réseau, de nombreux hôtes et pare-feux bloquent désormais ces paquets, plutôt que de répondre comme requis par le RFC 1122[2]. Pour cette raison, les scans basés uniquement sur ICMP sont rarement suffisamment fiables contre des cibles inconnues sur Internet. Mais pour les administrateurs système surveillant un réseau interne, ils peuvent être une approche pratique et efficace. Utilisez l'option -PE pour activer ce comportement d'écho de requête.

Alors que l'écho de requête est la requête ping ICMP standard, Nmap ne s'arrête pas là. Les normes ICMP (RFC 792[3] et RFC 950[4]) spécifient également les requêtes de timestamp, les requêtes d'information et les requêtes de masque d'adresse comme codes 13, 15 et 17, respectivement. Bien que le but ostensible de ces requêtes soit d'obtenir des informations telles que les masques d'adresse et les heures actuelles, elles peuvent facilement être utilisées pour la découverte d'hôtes. Un système qui répond est actif et disponible. Nmap n'implémente actuellement pas les paquets d'information, car ils ne sont pas largement pris en charge. Le RFC 1122 insiste sur le fait qu'« un hôte NE DEVRAIT PAS implémenter ces messages ». Les requêtes de timestamp et de masque d'adresse peuvent être envoyées avec les options -PP et -PM, respectivement. Une réponse de timestamp (code ICMP 14) ou une réponse de masque d'adresse (code 18) révèle que l'hôte est disponible. Ces deux requêtes peuvent être précieuses lorsque les administrateurs bloquent spécifiquement les paquets d'écho de requête tout en oubliant que d'autres requêtes ICMP peuvent être utilisées dans le même but.

-PO liste de protocoles (IP Protocol Ping)

L'une des options de découverte d'hôtes les plus récentes est le ping IP protocol, qui envoie des paquets IP avec le numéro de protocole spécifié défini dans leur en-tête IP. La liste de protocoles prend le même format que les listes de ports dans les options de découverte d'hôtes TCP, UDP et SCTP discutées précédemment. Si aucun protocole n'est spécifié, la valeur par défaut est d'envoyer plusieurs paquets IP pour ICMP (protocole 1), IGMP (protocole 2) et IP-in-IP (protocole 4). Les protocoles par défaut peuvent être configurés à la compilation en modifiant DEFAULT_PROTO_PROBE_PORT_SPEC dans nmap.h. Notez que pour ICMP, IGMP, TCP (protocole 6), UDP (protocole 17) et SCTP (protocole 132), les paquets sont envoyés avec les en-têtes de protocole appropriés, tandis que les autres protocoles sont envoyés sans données supplémentaires au-delà de l'en-tête IP (sauf si les options --data, --data-string ou --data-length sont spécifiées).

Cette méthode de découverte d'hôtes recherche soit des réponses utilisant le même protocole qu'une sonde, soit des messages ICMP protocol unreachable qui signifient que le protocole donné n'est pas pris en charge sur l'hôte de destination. Tout type de réponse signifie que l'hôte cible est actif.

--disable-arp-ping (Pas de ping ARP ou ND)

Nmap effectue normalement la découverte ARP ou la découverte Neighbor Discovery (ND) IPv6 pour les hôtes connectés localement à Ethernet, même si d'autres options de découverte d'hôtes telles que -Pn ou -PE sont utilisées. Pour désactiver ce comportement implicite, utilisez l'option --disable-arp-ping.

Le comportement par défaut est normalement plus rapide, mais cette option est utile sur les réseaux utilisant l'ARP proxy, dans lesquels un routeur répond spéculativement à toutes les requêtes ARP, donnant l'impression que toutes les cibles sont actives selon le scan ARP.

--discovery-ignore-rst

Dans certains cas, les pare-feux peuvent usurper des réponses TCP reset (RST) en réponse à des sondes vers des adresses inoccupées ou non autorisées. Comme Nmap considère généralement les réponses RST comme une preuve que la cible est active, cela peut entraîner une perte de temps à scanner des cibles qui n'existent pas. L'utilisation de --discovery-ignore-rst empêchera Nmap de prendre en compte ces réponses pendant la découverte d'hôtes. Vous devrez peut-être sélectionner des options de découverte d'hôtes supplémentaires pour vous assurer de ne pas manquer de cibles dans ce cas.

--traceroute (Tracer le chemin vers l'hôte)

Les traceroutes sont effectuées après le scan en utilisant les informations des résultats du scan pour déterminer le port et le protocole les plus susceptibles d'atteindre la cible. Cela fonctionne avec tous les types de scan, sauf les scans de connexion (-sT) et les scans inactifs (-sI). Tous les tracages utilisent le modèle de synchronisation dynamique de Nmap et sont effectués en parallèle.

Traceroute fonctionne en envoyant des paquets avec un TTL (time-to-live) bas pour tenter de provoquer des messages ICMP Time Exceeded à partir des sauts intermédiaires entre le scanner et l'hôte cible. Les implémentations standard de traceroute commencent avec un TTL de 1 et incrémentent le TTL jusqu'à ce que l'hôte de destination soit atteint. Le traceroute de Nmap commence avec un TTL élevé, puis décrémente le TTL jusqu'à zéro. Faire cela à l'envers permet à Nmap d'employer des algorithmes de mise en cache intelligents pour accélérer les tracages sur plusieurs hôtes. En moyenne, Nmap envoie 5 à 10 paquets de moins par hôte, selon les conditions réseau. Si un seul sous-réseau est scanné (c'est-à-dire 192.168.0.0/24), Nmap peut n'avoir à envoyer que deux paquets à la plupart des hôtes.

BASES DE LA SCANIFICATION DE PORTS

Bien que Nmap ait gagné en fonctionnalités au fil des années, il a commencé comme un scanneur de ports efficace, et cela reste sa fonction principale. La commande simple nmap cible scanne 1 000 ports TCP sur l'hôte cible. Alors que de nombreux scanneurs de ports ont traditionnellement regroupé tous les ports dans les états ouverts ou fermés, Nmap est beaucoup plus granulaire. Il divise les ports en six états : ouverts, fermés, filtrés, non filtrés, ouverts|filtrés ou fermés|filtrés.

Ces états ne sont pas des propriétés intrinsèques du port lui-même, mais décrivent comment Nmap les voit. Par exemple, un scan Nmap depuis le même réseau que la cible peut montrer le port 135/tcp comme ouvert, tandis qu'un scan au même moment avec les mêmes options depuis Internet pourrait montrer ce port comme filtré.

Chaque port ouvert représente une voie d'attaque potentielle. Les attaquants et les testeurs d'intrusion cherchent à exploiter les ports ouverts, tandis que les administrateurs tentent de les fermer ou de les protéger à l'aide de pare-feu, sans pour autant gêner les utilisateurs légitimes. Les ports ouverts sont également intéressants pour les analyses autres que de sécurité, car ils indiquent les services disponibles sur le réseau.

open

Un port est considéré comme ouvert lorsqu'une application y écoute et répond aux paquets de sondage de Nmap. Chaque port ouvert représente une voie d'attaque potentielle. Les attaquants et les testeurs d'intrusion cherchent à exploiter les ports ouverts, tandis que les administrateurs tentent de les fermer ou de les protéger à l'aide de pare-feu, sans pour autant gêner les utilisateurs légitimes. Les ports ouverts sont également intéressants pour les analyses autres que de sécurité, car ils indiquent les services disponibles sur le réseau.

closed

Un port fermé est accessible (il reçoit et répond aux paquets de sondage de Nmap), mais aucune application n'y est en écoute. Ils peuvent être utiles pour indiquer qu'un hôte est actif à une adresse IP (découverte d'hôte ou scan ping), et dans le cadre de la détection de système d'exploitation. Les ports fermés étant joignables, il peut être utile de les scanner ultérieurement au cas où certains s'ouvriraient. Les administrateurs peuvent envisager de bloquer ces ports avec un pare-feu. Ils apparaîtraient alors dans l'état filtré, décrit ci-dessous.

filtered

Nmap ne peut pas déterminer si un port est ouvert car un filtrage de paquets empêche ses sondes d'atteindre le port. Le filtrage peut provenir d'un périphérique de pare-feu dédié, de règles de routeur ou d'un logiciel de pare-feu basé sur l'hôte. Ces ports frustrent les attaquants car ils fournissent très peu d'informations. Parfois, ils répondent avec des messages d'erreur ICMP tels que type 3 code 13 (destination inaccessible : communication administrativement interdite), mais les filtres qui rejettent simplement les sondes sans répondre sont beaucoup plus courants. Cela oblige Nmap à réessayer plusieurs fois, juste au cas où la sonde aurait été perdue en raison d'une congestion réseau plutôt que d'un filtrage. Cela ralentit considérablement l'analyse.

unfiltered

L'état non filtré signifie qu'un port est accessible, mais Nmap ne peut pas déterminer s'il est ouvert ou fermé. Seul le scan ACK, utilisé pour cartographier les règles de pare-feu, classe les ports dans cet état. L'analyse des ports non filtrés avec d'autres types d'analyse tels que le scan Window, le scan SYN ou le scan FIN peut aider à déterminer si le port est ouvert.

open|filtered

Nmap place les ports dans cet état lorsqu'il ne peut pas déterminer si un port est ouvert ou filtré. Cela se produit pour les types d'analyse pour lesquels les ports ouverts ne donnent aucune réponse. L'absence de réponse pourrait également signifier qu'un filtre de paquets a rejeté la sonde ou toute réponse qu'elle a suscitée. Nmap ne sait donc pas avec certitude si le port est ouvert ou s'il est filtré. Les scans UDP, protocole IP, FIN, NULL et Xmas classent les ports de cette manière.

closed|filtered

Cet état est utilisé lorsque Nmap ne peut pas déterminer si un port est fermé ou filtré. Il n'est utilisé que pour le scan IP ID idle.

TECHNIQUES DE SCAN DE PORTS

En tant que novice en réparation automobile, je peux passer des heures à essayer d'adapter mes outils rudimentaires (marteau, ruban adhésif, clé, etc.) à la tâche à accomplir. Quand j'échoue lamentablement et que je remorque ma guimbarde chez un vrai mécanicien, il fouille invariablement dans une immense boîte à outils jusqu'à en sortir le gadget parfait qui rend le travail facile. L'art du scan de ports est similaire. Les experts comprennent des dizaines de techniques d'analyse et choisissent celle (ou la combinaison) appropriée pour une tâche donnée. Les utilisateurs inexpérimentés et les script kiddies, en revanche, essaient de résoudre chaque problème avec le scan SYN par défaut. Nmap étant gratuit, la seule barrière à la maîtrise du scan de ports est la connaissance. Cela vaut mieux que le monde de l'automobile, où il peut falloir beaucoup de talent pour déterminer que vous avez besoin d'un compresseur de ressorts d'amortisseur, puis payer quand même des milliers d'euros pour l'obtenir.

La plupart des types de scans ne sont disponibles que pour les utilisateurs privilégiés. En effet, ils envoient et reçoivent des paquets bruts, ce qui nécessite un accès root sur les systèmes Unix. L'utilisation d'un compte administrateur sous Windows est recommandée, bien que Nmap fonctionne parfois pour les utilisateurs non privilégiés sur cette plateforme lorsque Npcap a déjà été chargé dans le système d'exploitation. L'exigence de privilèges root était une limitation sérieuse lorsque Nmap a été publié en 1997, car de nombreux utilisateurs n'avaient accès qu'à des comptes shell partagés. Le monde est différent maintenant. Les ordinateurs sont moins chers, beaucoup plus de gens ont un accès Internet direct permanent, et les systèmes Unix de bureau (y compris Linux et Mac OS X) sont prévalents. Une version Windows de Nmap est maintenant disponible, permettant de l'exécuter sur encore plus de postes de travail. Pour toutes ces raisons, les utilisateurs ont moins besoin d'exécuter Nmap à partir de comptes shell partagés limités. C'est une bonne chose, car les options privilégiées rendent Nmap beaucoup plus puissant et flexible.

Bien que Nmap tente de produire des résultats précis, gardez à l'esprit que toutes ses informations sont basées sur les paquets renvoyés par les machines cibles (ou les pare-feu qui les précèdent). Ces hôtes peuvent être peu fiables et envoyer des réponses destinées à tromper ou induire Nmap en erreur. Les hôtes non conformes aux RFC qui ne répondent pas comme ils le devraient aux sondes Nmap sont beaucoup plus courants. Les scans FIN, NULL et Xmas sont particulièrement sensibles à ce problème. Ces problèmes sont spécifiques à certains types de scans et sont donc discutés dans les entrées de scan individuelles.

Cette section documente la douzaine environ de techniques de scan de ports prises en charge par Nmap. Une seule méthode peut être utilisée à la fois, à l'exception du scan UDP (-sU) et de l'un des types de scan SCTP (-sY, -sZ) qui peuvent être combinés avec l'un des types de scan TCP. Pour aider à la mémorisation, les options de type de scan de ports sont de la forme -sC, où C est un caractère proéminent dans le nom du scan, généralement le premier. La seule exception est le scan de rebond FTP déprécié (-b). Par défaut, Nmap effectue un scan SYN, bien qu'il substitue un scan connect si l'utilisateur n'a pas les privilèges appropriés pour envoyer des paquets bruts (nécessite un accès root sous Unix). Parmi les scans listés dans cette section, seuls les scans connect et de rebond FTP peuvent être exécutés par des utilisateurs non privilégiés.

-sS (scan SYN TCP)

Le scan SYN est l'option de scan par défaut et la plus populaire pour de bonnes raisons. Il peut être effectué rapidement, analysant des milliers de ports par seconde sur un réseau rapide non entravé par des pare-feu restrictifs. Il est également relativement discret et furtif car il ne termine jamais les connexions TCP. Le scan SYN fonctionne avec n'importe quelle pile TCP conforme plutôt que de dépendre des idiosyncrasies de plateformes spécifiques comme le font les scans FIN/NULL/Xmas, Maimon et idle de Nmap. Il permet également une différenciation claire et fiable entre les états ouvert, fermé et filtré.

Cette technique est souvent appelée scan semi-ouvert, car vous n'ouvrez pas de connexion TCP complète. Vous envoyez un paquet SYN, comme si vous alliez ouvrir une connexion réelle, puis attendez une réponse. Un SYN/ACK indique que le port écoute (ouvert), tandis qu'un RST (reset) indique un non-auditeur. Si aucune réponse n'est reçue après plusieurs retransmissions, le port est marqué comme filtré. Le port est également marqué comme filtré si une erreur ICMP unreachable (type 3, code 0, 1, 2, 3, 9, 10 ou 13) est reçue. Le port est également considéré comme ouvert si un paquet SYN (sans le drapeau ACK) est reçu en réponse. Cela peut être dû à une fonctionnalité TCP extrêmement rare connue sous le nom d'ouverture simultanée ou de connexion à poignée de main divisée (voir https://nmap.org/misc/split-handshake.pdf).

-sT (scan connect TCP)

Le scan connect TCP est le type de scan TCP par défaut lorsque le scan SYN n'est pas une option. C'est le cas lorsqu'un utilisateur n'a pas les privilèges d'accès aux paquets bruts. Au lieu d'écrire des paquets bruts comme la plupart des autres types de scans, Nmap demande au système d'exploitation sous-jacent d'établir une connexion avec la machine cible et le port en émettant l'appel système connect. C'est le même appel système de haut niveau que les navigateurs Web, les clients P2P et la plupart des autres applications réseau utilisent pour établir une connexion. Il fait partie d'une interface de programmation connue sous le nom d'API Berkeley Sockets. Plutôt que de lire les réponses des paquets bruts sur le réseau, Nmap utilise cette API pour obtenir des informations de statut sur chaque tentative de connexion.

Lorsque le scan SYN est disponible, c'est généralement un meilleur choix. Nmap a moins de contrôle sur l'appel connect de haut niveau qu'avec les paquets bruts, ce qui le rend moins efficace. L'appel système complète les connexions aux ports cibles ouverts plutôt que d'effectuer la réinitialisation semi-ouverte que fait le scan SYN. Non seulement cela prend plus de temps et nécessite plus de paquets pour obtenir les mêmes informations, mais les machines cibles sont plus susceptibles d'enregistrer la connexion. Un IDS décent détectera l'un ou l'autre, mais la plupart des machines n'ont pas un tel système d'alarme. De nombreux services sur un système Unix moyen ajouteront une note à syslog, et parfois un message d'erreur cryptique, lorsque Nmap se connecte puis ferme la connexion sans envoyer de données. Des services vraiment pathétiques plantent lorsque cela se produit, bien que ce soit rare. Un administrateur qui voit une série de tentatives de connexion dans ses journaux provenant d'un seul système devrait savoir qu'il a été scanné par connect.

-sU (scans UDP)

Alors que la plupart des services populaires sur Internet fonctionnent sur le protocole TCP, les services UDP[5] sont largement déployés. DNS, SNMP et DHCP (ports enregistrés 53, 161/162 et 67/68) sont trois des plus courants. Comme le scan UDP est généralement plus lent et plus difficile que le scan TCP, certains auditeurs de sécurité ignorent ces ports. C'est une erreur, car les services UDP exploitables sont assez courants et les attaquants n'ignorent certainement pas tout le protocole. Heureusement, Nmap peut aider à inventorier les ports UDP.

Le scan UDP est activé avec l'option -sU. Il peut être combiné avec un type de scan TCP tel que le scan SYN (-sS) pour vérifier les deux protocoles lors de la même exécution.

Le scan UDP fonctionne en envoyant un paquet UDP à chaque port cible. Pour certains ports courants tels que 53 et 161, une charge utile spécifique au protocole est envoyée pour augmenter le taux de réponse, mais pour la plupart des ports, le paquet est vide, sauf si les options --data, --data-string ou --data-length sont spécifiées. Si une erreur ICMP port unreachable (type 3, code 3) est renvoyée, le port est fermé. D'autres erreurs ICMP unreachable (type 3, codes 0, 1, 2, 9, 10 ou 13) marquent le port comme filtré. Parfois, un service répond avec un paquet UDP, prouvant qu'il est ouvert. Si aucune réponse n'est reçue après les retransmissions, le port est classé comme open|filtered. Cela signifie que le port pourrait être ouvert, ou que des filtres de paquets bloquent la communication. La détection de version (-sV) peut être utilisée pour aider à différencier les ports véritablement ouverts des ports filtrés.

Un défi majeur dans le scan UDP est de le faire rapidement. Les ports ouverts et filtrés envoient rarement une réponse, laissant Nmap expirer puis effectuer des retransmissions, juste au cas où la sonde ou la réponse auraient été perdues. Les ports fermés sont souvent un problème encore plus grand. Ils renvoient généralement une erreur ICMP port unreachable. Mais contrairement aux paquets RST envoyés par les ports TCP fermés en réponse à un scan SYN ou connect, de nombreux hôtes limitent par défaut les messages ICMP port unreachable. Linux et Solaris sont particulièrement stricts à ce sujet. Par exemple, le noyau Linux 2.4.20 limite les messages de destination inaccessible à un par seconde (dans net/ipv4/icmp.c).

Nmap détecte la limitation de débit et ralentit en conséquence pour éviter de saturer le réseau de paquets inutiles que la machine cible rejettera. Malheureusement, une limite de type Linux d'un paquet par seconde rend un scan de 65 536 ports plus long que 18 heures.

-sY (Analyse SCTP INIT)

SCTP[6] est une alternative relativement nouvelle aux protocoles TCP et UDP, combinant la plupart des caractéristiques de TCP et UDP, et ajoutant également de nouvelles fonctionnalités telles que le multi-homing et le multi-streaming. Il est principalement utilisé pour les services liés à SS7/SIGTRAN, mais il a le potentiel d'être utilisé pour d'autres applications également. L'analyse SCTP INIT est l'équivalent SCTP d'une analyse TCP SYN. Elle peut être effectuée rapidement, analysant des milliers de ports par seconde sur un réseau rapide non gêné par des pare-feux restrictifs. Comme l'analyse SYN, l'analyse INIT est relativement discrète et furtive, car elle ne complète jamais les associations SCTP. Elle permet également une différenciation claire et fiable entre les états ouverts, fermés et filtrés.

Cette technique est souvent appelée analyse half-open (semi-ouverte), car vous n'ouvrez pas une association SCTP complète. Vous envoyez un segment INIT, comme si vous alliez ouvrir une association réelle, puis attendez une réponse. Un segment INIT-ACK indique que le port écoute (ouvert), tandis qu'un segment ABORT indique un port non-écouteur. Si aucune réponse n'est reçue après plusieurs retransmissions, le port est marqué comme filtré. Le port est également marqué filtré si une erreur ICMP unreachable (type 3, code 0, 1, 2, 3, 9, 10 ou 13) est reçue.

-sN ; -sF ; -sX (Analyses TCP NULL, FIN et Xmas)

Ces trois types d'analyse (encore plus sont possibles avec l'option --scanflags décrite dans la section suivante) exploitent une subtile faille dans la TCP RFC[7] pour différencier les ports ouverts des ports fermés. La page 65 de la RFC 793 indique que « si l'état du port [de destination] est FERMÉ... un segment entrant ne contenant pas de RST entraîne l'envoi d'un RST en réponse. » Puis la page suivante discute des paquets envoyés aux ports ouverts sans les bits SYN, RST ou ACK définis, indiquant que : « vous n'êtes probablement pas censé arriver ici, mais si c'est le cas, ignorez le segment et répondez. »

Lors de l'analyse de systèmes conformes à ce texte RFC, tout paquet ne contenant pas les bits SYN, RST ou ACK entraînera un RST renvoyé si le port est fermé et aucune réponse du tout si le port est ouvert. Tant qu'aucun de ces trois bits n'est inclus, toute combinaison des trois autres (FIN, PSH et URG) est acceptable. Nmap exploite cela avec trois types d'analyse :

Analyse NULL (-sN)

Ne définit aucun bit (en-tête de drapeau TCP est 0)

Analyse FIN (-sF)

Définit uniquement le bit TCP FIN.

Analyse Xmas (-sX)

Définit les drapeaux FIN, PSH et URG, illuminant le paquet comme un arbre de Noël.

Ces trois types d'analyse sont exactement identiques en comportement sauf pour les drapeaux TCP définis dans les paquets de sonde. Si un paquet RST est reçu, le port est considéré comme fermé, tandis qu'aucune réponse signifie qu'il est ouvert|filtré. Le port est marqué filtré si une erreur ICMP unreachable (type 3, code 0, 1, 2, 3, 9, 10 ou 13) est reçue.

L'avantage principal de ces types d'analyse est qu'ils peuvent passer inaperçus à travers certains pare-feux non-stateful et routeurs de filtrage de paquets. Un autre avantage est que ces types d'analyse sont un peu plus discrets qu'une analyse SYN. Ne comptez pas trop là-dessus cependant - la plupart des systèmes IDS modernes peuvent être configurés pour les détecter. Le principal inconvénient est que tous les systèmes ne suivent pas la RFC 793 à la lettre. Un certain nombre de systèmes envoient des réponses RST aux sondes, que le port soit ouvert ou non. Cela fait que tous les ports sont étiquetés comme fermés. Les principaux systèmes d'exploitation qui font cela sont Microsoft Windows, de nombreux appareils Cisco, BSDI et IBM OS/400. Cependant, cette analyse fonctionne contre la plupart des systèmes basés sur Unix. Un autre inconvénient de ces analyses est qu'elles ne peuvent pas distinguer les ports ouverts de certains ports filtrés, vous laissant avec la réponse ouvert|filtré.

-sA (Analyse TCP ACK)

Cette analyse est différente des autres discutées jusqu'à présent en ce sens qu'elle ne détermine jamais les ports ouverts (ni même ouverts|filtrés). Elle est utilisée pour cartographier les ensembles de règles de pare-feu, déterminant s'ils sont stateful ou non et quels ports sont filtrés.

Le paquet de sonde d'analyse ACK n'a que le drapeau ACK défini (sauf si vous utilisez --scanflags). Lors de l'analyse de systèmes non filtrés, les ports ouverts et fermés renverront tous deux un paquet RST. Nmap les étiquette alors comme non filtrés, ce qui signifie qu'ils sont joignables par le paquet ACK, mais que leur état ouvert ou fermé est indéterminé. Les ports qui ne répondent pas, ou qui renvoient certains messages d'erreur ICMP (type 3, code 0, 1, 2, 3, 9, 10 ou 13), sont étiquetés comme filtrés.

-sW (Analyse TCP Window)

L'analyse Window est exactement la même que l'analyse ACK, sauf qu'elle exploite un détail d'implémentation de certains systèmes pour différencier les ports ouverts des ports fermés, plutôt que d'afficher toujours "non filtré" lorsqu'un RST est renvoyé. Elle le fait en examinant le champ TCP Window des paquets RST renvoyés. Sur certains systèmes, les ports ouverts utilisent une taille de fenêtre positive (même pour les paquets RST) tandis que les ports fermés ont une fenêtre nulle. Donc, au lieu de toujours lister un port comme non filtré lorsqu'il reçoit un RST, l'analyse Window liste le port comme ouvert ou fermé si la valeur TCP Window dans cette réinitialisation est respectivement positive ou nulle.

Cette analyse repose sur un détail d'implémentation d'une minorité de systèmes sur Internet, vous ne pouvez donc pas toujours lui faire confiance. Les systèmes qui ne la supportent pas renverront généralement tous les ports comme fermés. Bien sûr, il est possible que la machine n'ait réellement aucun port ouvert. Si la plupart des ports analysés sont fermés mais que quelques numéros de port courants (tels que 22, 25, 53) sont filtrés, le système est très probablement vulnérable. Occasionnellement, les systèmes présenteront même le comportement exactement opposé. Si votre analyse montre 1 000 ports ouverts et trois ports fermés ou filtrés, ces trois pourraient très bien être les ports réellement ouverts.

-sM (Analyse TCP Maimon)

L'analyse Maimon porte le nom de son découvreur, Uriel Maimon. Il a décrit la technique dans le magazine Phrack numéro 49 (novembre 1996). Nmap, qui incluait cette technique, est sorti deux numéros plus tard. Cette technique est exactement la même que les analyses NULL, FIN et Xmas, sauf que la sonde est FIN/ACK. Selon la RFC 793[7] (TCP), un paquet RST devrait être généré en réponse à une telle sonde, que le port soit ouvert ou fermé. Cependant, Uriel a remarqué que de nombreux systèmes dérivés de BSD laissaient simplement tomber le paquet si le port était ouvert.

--scanflags (Analyse TCP personnalisée)

Les utilisateurs vraiment avancés de Nmap ne sont pas limités aux types d'analyse prédéfinis proposés. L'option --scanflags vous permet de concevoir votre propre analyse en spécifiant des drapeaux TCP arbitraires. Laissez libre cours à votre créativité, tout en contournant les systèmes de détection d'intrusion dont les vendeurs ont simplement parcouru la page man de Nmap en ajoutant des règles spécifiques !

L'argument --scanflags peut être une valeur numérique de drapeau telle que 9 (PSH et FIN), mais utiliser des noms symboliques est plus facile. Il suffit de combiner n'importe quelle combinaison de URG, ACK, PSH, RST, SYN et FIN. Par exemple, --scanflags URGACKPSHRSTSYNFIN définit tout, bien que ce ne soit pas très utile pour l'analyse. L'ordre dans lequel ils sont spécifiés n'a pas d'importance.

En plus de spécifier les drapeaux souhaités, vous pouvez spécifier un type d'analyse TCP (tel que -sA ou -sF). Ce type de base indique à Nmap comment interpréter les réponses. Par exemple, une analyse SYN considère l'absence de réponse comme indiquant un port filtré, tandis qu'une analyse FIN traite la même chose comme ouvert|filtré. Nmap se comportera de la même manière que pour le type d'analyse de base, sauf qu'il utilisera les drapeaux TCP que vous spécifiez à la place. Si vous ne spécifiez pas de type de base, l'analyse SYN est utilisée.

-sZ (Analyse SCTP COOKIE ECHO)

L'analyse SCTP COOKIE ECHO est une analyse SCTP plus avancée. Elle tire parti du fait que les implémentations SCTP devraient ignorer silencieusement les paquets contenant des segments COOKIE ECHO sur les ports ouverts, mais envoyer un ABORT si le port est fermé. L'avantage de ce type d'analyse est qu'elle est moins évidente qu'une analyse INIT. De plus, il peut y avoir des règles de pare-feu non-stateful bloquant les segments INIT, mais pas les segments COOKIE ECHO. Ne vous laissez pas tromper en pensant que cela rendra une analyse de port invisible ; un bon IDS sera capable de détecter les analyses SCTP COOKIE ECHO également. Le revers de la médaille est que les analyses SCTP COOKIE ECHO ne peuvent pas différencier les ports ouverts des ports filtrés, vous laissant avec l'état ouvert|filtré dans les deux cas.

-sI hôte zombie[:port de sonde] (analyse idle)

Cette méthode d'analyse avancée permet une analyse de port TCP véritablement aveugle de la cible (ce qui signifie qu'aucun paquet n'est envoyé à la cible depuis votre véritable adresse IP). Au lieu de cela, une attaque unique par canal secondaire exploite la génération prévisible de la séquence d'ID de fragmentation IP sur l'hôte zombie pour obtenir des informations sur les ports ouverts sur la cible. Les systèmes IDS afficheront l'analyse comme provenant de la machine zombie que vous spécifiez (qui doit être opérationnelle et répondre à certains critères). Ce type d'analyse fascinant est trop complexe pour être entièrement décrit dans ce guide de référence, j'ai donc rédigé et publié un article informel avec tous les détails à l'adresse https://nmap.org/book/idlescan.html.

En plus d'être extraordinairement furtive (en raison de sa nature aveugle), ce type d'analyse permet de cartographier les relations de confiance basées sur IP entre les machines. La liste des ports montre les ports ouverts *du point de vue de l'hôte zombie*. Vous pouvez donc essayer d'analyser une cible en utilisant divers zombies qui, selon vous, pourraient être considérés comme fiables (via les règles du routeur/filtre de paquets).

Vous pouvez ajouter deux-points suivis d'un numéro de port à l'hôte zombie si vous souhaitez sonder un port particulier sur le zombie pour des changements d'ID IP. Sinon, Nmap utilisera le port qu'il utilise par défaut pour les pings TCP (80).

-sO (Analyse de protocole IP)

L'analyse de protocole IP vous permet de déterminer quels protocoles IP (TCP, ICMP, IGMP, etc.) sont pris en charge par les machines cibles. Ce n'est techniquement pas une analyse de port, car elle parcourt les numéros de protocole IP plutôt que les numéros de port TCP ou UDP. Pourtant, elle utilise toujours l'option -p pour sélectionner les numéros de protocole analysés, rapporte ses résultats dans le format de table de ports normal, et utilise même le même moteur d'analyse sous-jacent que les méthodes d'analyse de port réelles. Elle est donc suffisamment proche d'une analyse de port pour appartenir à cette section.

En plus d'être utile en soi, l'analyse de protocole démontre la puissance des logiciels open-source. Bien que l'idée fondamentale soit assez simple, je n'avais pas pensé à l'ajouter ni reçu de demandes pour une telle fonctionnalité. Puis, à l'été 2000, Gerhard Rieger a conçu l'idée, écrit un excellent patch l'implémentant, et l'a envoyé à la liste de diffusion d'annonces (alors appelée nmap-hackers). J'ai incorporé ce patch dans l'arbre Nmap et publié une nouvelle version le lendemain. Peu de logiciels commerciaux ont des utilisateurs suffisamment enthousiastes pour concevoir et contribuer leurs propres améliorations !

L'analyse de protocole fonctionne de manière similaire à l'analyse UDP. Au lieu d'itérer à travers le champ du numéro de port d'un paquet UDP, elle envoie des en-têtes de paquets IP et itère à travers les huit

champ de protocole IP. Les en-têtes sont généralement vides, ne contenant aucune donnée et même pas l'en-tête approprié pour le protocole revendiqué. Les exceptions sont TCP, UDP, ICMP, SCTP et IGMP. Un en-tête de protocole approprié pour ceux-ci est inclus car certains systèmes ne les enverront pas autrement et car Nmap dispose déjà de fonctions pour les créer. Au lieu de rechercher les messages ICMP d'atteinte de port non valide, le scan de protocole recherche les messages ICMP d'atteinte de protocole non valide. Si Nmap reçoit une réponse dans n'importe quel protocole de l'hôte cible, Nmap marque ce protocole comme ouvert. Une erreur ICMP d'atteinte de protocole non valide (type 3, code 2) amène le protocole à être marqué comme fermé, tandis qu'une atteinte de port non valide (type 3, code 3) marque le protocole comme ouvert. D'autres erreurs ICMP d'atteinte non valide (type 3, codes 0, 1, 9, 10 ou 13) amènent le protocole à être marqué comme filtré (bien qu'elles prouvent en même temps qu'ICMP est ouvert). Si aucune réponse n'est reçue après les retransmissions, le protocole est marqué comme ouvert|filtré.

-b hôte de relais FTP (Scan par rebond FTP)

Une caractéristique intéressante du protocole FTP (RFC 959[8]) est la prise en charge des connexions FTP dites par proxy. Cela permet à un utilisateur de se connecter à un serveur FTP, puis de demander que des fichiers soient envoyés à un serveur tiers. Une telle fonctionnalité est sujette à des abus à de nombreux niveaux, de sorte que la plupart des serveurs ont cessé de la prendre en charge. L'une des utilisations abusives permises par cette fonctionnalité est de faire scanner des ports d'autres hôtes par le serveur FTP. Il suffit de demander au serveur FTP d'envoyer un fichier à chacun des ports intéressants d'un hôte cible à tour de rôle. Le message d'erreur décrira si le port est ouvert ou non. C'est un bon moyen de contourner les pare-feux car les serveurs FTP organisationnels sont souvent placés là où ils ont plus d'accès à d'autres hôtes internes que n'importe quel vieil hôte Internet. Nmap prend en charge le scan par rebond FTP avec l'option -b. Elle prend un argument de la forme nom d'utilisateur:mot de passe@serveur:port. Serveur est le nom ou l'adresse IP d'un serveur FTP vulnérable. Comme pour une URL normale, vous pouvez omettre nom d'utilisateur:mot de passe, auquel cas les informations d'identification de connexion anonyme (utilisateur : anonyme mot de passe : -wwwuser@) sont utilisées. Le numéro de port (et le deux-points qui le précède) peuvent également être omis, auquel cas le port FTP par défaut (21) sur serveur est utilisé.

Cette vulnérabilité était répandue en 1997 lors de la sortie de Nmap, mais elle a été largement corrigée. Les serveurs vulnérables existent toujours, il vaut donc la peine d'essayer lorsque tout le reste échoue. Si votre objectif est de contourner un pare-feu, scannez le réseau cible pour le port 21 (ou même pour tout service FTP si vous scannez tous les ports avec détection de version) et utilisez le script NSE ftp-bounce. Nmap vous indiquera si l'hôte est vulnérable ou non. Si vous essayez simplement de brouiller les pistes, vous n'avez pas besoin de (et en fait, ne devriez pas) vous limiter aux hôtes du réseau cible. Avant de commencer à scanner des adresses Internet aléatoires pour des serveurs FTP vulnérables, considérez que les administrateurs système pourraient ne pas apprécier que vous abusiez de leurs serveurs de cette manière.

SPÉCIFICATION ET ORDRE DE SCAN DES PORTS

En plus de toutes les méthodes de scan discutées précédemment, Nmap propose des options pour spécifier quels ports sont scannés et si l'ordre du scan est aléatoire ou séquentiel. Par défaut, Nmap scanne les 1 000 ports les plus courants pour chaque protocole.

-p plages de ports (Scanner uniquement les ports spécifiés)

Cette option spécifie les ports que vous souhaitez scanner et remplace la valeur par défaut. Les numéros de port individuels sont acceptés, tout comme les plages séparées par un trait d'union (par exemple, 1-1023). Les valeurs de début et/ou de fin d'une plage peuvent être omises, Nmap utilisant alors 1 et 65535 respectivement. Vous pouvez donc spécifier -p- pour scanner les ports de 1 à 65535. Le scan du port zéro est autorisé si vous le spécifiez explicitement. Pour le scan de protocoles IP (-sO), cette option spécifie les numéros de protocole pour lesquels vous souhaitez scanner (0 à 255).

Lors du scan d'une combinaison de protocoles (par exemple, TCP et UDP), vous pouvez spécifier un protocole particulier en faisant précéder les numéros de port par T : pour TCP, U : pour UDP, S : pour SCTP, ou P : pour Protocole IP. Le qualificateur dure jusqu'à ce que vous en spécifiiez un autre. Par exemple, l'argument -p U:53,111,137,T:21-25,80,139,8080 scannerait les ports UDP 53, 111 et 137, ainsi que les ports TCP listés. Notez que pour scanner à la fois UDP et TCP, vous devez spécifier -sU et au moins un type de scan TCP (tel que -sS, -sF ou -sT). Si aucun qualificateur de protocole n'est donné, les numéros de port sont ajoutés à toutes les listes de protocoles. Les ports peuvent également être spécifiés par leur nom, tel qu'ils sont désignés dans nmap-services. Vous pouvez même utiliser les caractères génériques * et ? avec les noms. Par exemple, pour scanner FTP et tous les ports dont les noms commencent par « http », utilisez -p ftp,http*. Faites attention aux expansions de shell et citez l'argument de -p en cas de doute.

Les plages de ports peuvent être entourées de crochets pour indiquer les ports de cette plage qui apparaissent dans nmap-services. Par exemple, la commande suivante scannera tous les ports de nmap-services inférieurs ou égaux à 1024 : -p [-1024]. Soyez prudent avec les expansions de shell et citez l'argument de -p en cas de doute.

--exclude-ports plages de ports (Exclure les ports spécifiés du scan)

Cette option spécifie les ports que vous souhaitez exclure du scan par Nmap. Les plages de ports sont spécifiées de manière similaire à -p. Pour le scan de protocoles IP (-sO), cette option spécifie les numéros de protocole que vous souhaitez exclure (0 à 255).

Lorsque des ports sont demandés à être exclus, ils sont exclus de tous les types de scans (c'est-à-dire qu'ils ne seront scannés sous aucun prétexte). Cela inclut également la phase de découverte.

-F (Scan rapide (ports limités))

Spécifie que vous souhaitez scanner moins de ports que la valeur par défaut. Normalement, Nmap scanne les 1 000 ports les plus courants pour chaque protocole scanné. Avec -F, ce nombre est réduit à 100.

Nmap a besoin d'un fichier nmap-services contenant des informations de fréquence pour savoir quels ports sont les plus courants. Si les informations de fréquence des ports ne sont pas disponibles, par exemple en raison de l'utilisation d'un fichier nmap-services personnalisé, Nmap scanne tous les ports nommés plus les ports 1 à 1024. Dans ce cas, -F signifie ne scanner que les ports nommés dans le fichier services.

-r (Ne pas aléatoriser les ports)

Par défaut, Nmap aléatorise l'ordre des ports scannés (sauf que certains ports couramment accessibles sont déplacés vers le début pour des raisons d'efficacité). Cette randomisation est normalement souhaitable, mais vous pouvez spécifier -r pour un scan de ports séquentiel (trié du plus bas au plus élevé) à la place.

--port-ratio ratio<nombre décimal entre 0 et 1>

Scanne tous les ports du fichier nmap-services dont le ratio est supérieur à celui donné. ratio doit être compris entre 0,0 et 1,0.

--top-ports n

Scanne les n ports les plus élevés trouvés dans le fichier nmap-services après exclusion de tous les ports spécifiés par --exclude-ports. n doit être supérieur ou égal à 1.

DÉTECTION DE SERVICE ET DE VERSION

Pointez Nmap vers une machine distante et il pourrait vous dire que les ports 25/tcp, 80/tcp et 53/udp sont ouverts. En utilisant sa base de données nmap-services d'environ 2 200 services bien connus, Nmap indiquerait que ces ports correspondent probablement respectivement à un serveur de messagerie (SMTP), un serveur web (HTTP) et un serveur de noms (DNS). Cette recherche est généralement précise : la grande majorité des démons écoutant sur le port TCP 25 sont, en fait, des serveurs de messagerie. Cependant, vous ne devriez pas parier votre sécurité là-dessus ! Les gens peuvent exécuter et exécutent des services sur des ports étranges.

Même si Nmap a raison, et que le serveur hypothétique ci-dessus exécute des serveurs SMTP, HTTP et DNS, ce n'est pas beaucoup d'informations. Lors de l'évaluation des vulnérabilités (ou même de l'inventaire réseau simple) de vos entreprises ou clients, vous voulez vraiment savoir quels serveurs de messagerie et DNS et quelles versions s'exécutent. Avoir un numéro de version précis aide considérablement à déterminer pour quelles exploitations un serveur est vulnérable. La détection de version vous aide à obtenir ces informations.

Une fois les ports TCP et/ou UDP découverts à l'aide d'une des autres méthodes de scan, la détection de version interroge ces ports pour en savoir plus sur ce qui s'exécute réellement. La base de données nmap-service-probes contient des sondes pour interroger divers services et des expressions de correspondance pour reconnaître et analyser les réponses. Nmap essaie de déterminer le protocole du service (par exemple, FTP, SSH, Telnet, HTTP), le nom de l'application (par exemple, ISC BIND, Apache httpd, Solaris telnetd), le numéro de version, le nom d'hôte, le type d'appareil (par exemple, imprimante, routeur), la famille du système d'exploitation (par exemple, Windows, Linux). Lorsque possible, Nmap obtient également la représentation Common Platform Enumeration (CPE) de ces informations. Parfois, des détails divers tels que la disponibilité d'un serveur X pour les connexions, la version du protocole SSH ou le nom d'utilisateur KaZaA sont disponibles. Bien sûr, la plupart des services ne fournissent pas toutes ces informations. Si Nmap a été compilé avec le support OpenSSL, il se connectera aux serveurs SSL pour déduire le service écoutant derrière cette couche de chiffrement. Certains ports UDP sont laissés à l'état ouvert|filtré après qu'un scan de ports UDP n'ait pas pu déterminer si le port est ouvert ou filtré. La détection de version essaiera d'obtenir une réponse de ces ports (tout comme elle le fait pour les ports ouverts), et modifiera l'état en ouvert si elle réussit. Les ports TCP ouverts|filtrés sont traités de la même manière. Notez que l'option -A de Nmap active la détection de version entre autres. Un article documentant le fonctionnement, l'utilisation et la personnalisation de la détection de version est disponible sur https://nmap.org/book/vscan.html.

Lorsque des services RPC sont découverts, le broyeur RPC de Nmap est automatiquement utilisé pour déterminer les numéros de programme et de version RPC. Il prend tous les ports TCP/UDP détectés comme RPC et les inonde de commandes NULL SunRPC afin de déterminer s'il s'agit de ports RPC, et si oui, quel programme et quelle version ils servent. Ainsi, vous pouvez obtenir efficacement les mêmes informations que rpcinfo -p même si le mappe-port de la cible est derrière un pare-feu (ou protégé par des wrappers TCP). Les leurres ne fonctionnent pas actuellement avec le scan RPC.

Lorsque Nmap reçoit des réponses d'un service mais ne peut pas les faire correspondre à sa base de données, il affiche une empreinte spéciale et une URL pour que vous la soumettiez si vous savez avec certitude ce qui s'exécute sur le port. Veuillez prendre quelques minutes pour faire la soumission afin que votre découverte puisse bénéficier à tous. Grâce à ces soumissions, Nmap dispose d'environ 6 500 correspondances de modèles pour plus de 650 protocoles tels que SMTP, FTP, HTTP, etc.

La détection de version est activée et contrôlée avec les options suivantes :

-sV (Détection de version)

Active la détection de version, comme expliqué ci-dessus. Alternativement, vous pouvez utiliser -A, qui active la détection de version entre autres.

-sR est un alias pour -sV. Avant mars 2011, il était utilisé pour activer le "grinder" RPC séparément de la détection de version, mais maintenant ces options sont toujours combinées.

--allports (Ne pas exclure de ports de la détection de version)

Par défaut, la détection de version de Nmap ignore le port TCP 9100 car certaines imprimantes impriment simplement tout ce qui est envoyé à ce port, ce qui conduit à des dizaines de pages de requêtes HTTP GET, de requêtes de session SSL binaires, etc. Ce comportement peut être modifié en changeant ou supprimant la directive Exclude dans nmap-service-probes, ou vous pouvez spécifier --allports pour scanner tous les ports indépendamment de toute directive Exclude.

--version-intensity intensity (Définir l'intensité du scan de version)

Lors de l'exécution d'un scan de version (-sV), Nmap envoie une série de sondes, chacune étant dotée d'une valeur de rareté entre un et neuf. Les sondes à faible indice sont efficaces contre une grande variété de services courants, tandis que celles à indice élevé sont rarement utiles. Le niveau d'intensité spécifie quelles sondes doivent être appliquées. Plus le chiffre est élevé, plus il est probable que le service soit correctement identifié. Cependant, les scans à haute intensité prennent plus de temps. L'intensité doit être comprise entre 0 et 9. La valeur par défaut est 7. Lorsqu'une sonde est enregistrée sur le port cible via la directive `nmap-service-probes ports`, cette sonde est essayée indépendamment du niveau d'intensité. Cela garantit que les sondes DNS seront toujours tentées sur tout port 53 ouvert, la sonde SSL sera effectuée sur 443, etc.

--version-light (Activer le mode léger)

C'est un alias pratique pour --version-intensity 2. Ce mode léger rend le scan de version beaucoup plus rapide, mais il est légèrement moins susceptible d'identifier les services.

--version-all (Essayer chaque sonde)

Un alias pour --version-intensity 9, garantissant que chaque sonde est tentée sur chaque port.

--version-trace (Tracer l'activité du scan de version)

Cela amène Nmap à imprimer des informations de débogage détaillées sur ce que fait le scan de version. C'est un sous-ensemble de ce que vous obtenez avec --packet-trace.

DETECTION DE OS

L'une des fonctionnalités les plus connues de Nmap est la détection de système d'exploitation à distance par empreinte digitale de la pile TCP/IP. Nmap envoie une série de paquets TCP et UDP à l'hôte distant et examine pratiquement chaque bit des réponses. Après avoir effectué des dizaines de tests tels que l'échantillonnage ISN TCP, la prise en charge et l'ordre des options TCP, l'échantillonnage ID IP et la vérification de la taille de la fenêtre initiale, Nmap compare les résultats à sa base de données `nmap-os-db` de plus de 2 600 empreintes d'OS connues et imprime les détails de l'OS s'il y a une correspondance. Chaque empreinte comprend une description textuelle libre de l'OS, et une classification qui fournit le nom du fournisseur (par exemple, Sun), l'OS sous-jacent (par exemple, Solaris), la génération de l'OS (par exemple, 10) et le type d'appareil (général, routeur, switch, console de jeu, etc.). La plupart des empreintes ont également une représentation CPE (Common Platform Enumeration), comme `cpe:/o:linux:linux_kernel:2.6`.

Si Nmap ne parvient pas à deviner l'OS d'une machine, et que les conditions sont bonnes (par exemple, au moins un port ouvert et un port fermé ont été trouvés), Nmap fournira une URL que vous pourrez utiliser pour soumettre l'empreinte si vous connaissez (avec certitude) l'OS exécuté sur la machine. En faisant cela, vous contribuez au pool de systèmes d'exploitation connus par Nmap et donc il sera plus précis pour tout le monde.

La détection d'OS active certaines autres tests qui utilisent les informations collectées pendant le processus de toute façon. L'une d'elles est la classification de la prédictibilité de la séquence TCP. Elle mesure approximativement la difficulté d'établir une connexion TCP forgée contre l'hôte distant. Elle est utile pour exploiter les relations de confiance basées sur l'adresse IP source (rlogin, filtres de pare-feu, etc.) ou pour masquer la source d'une attaque. Ce type d'usurpation est rarement effectué de nos jours, mais de nombreuses machines y sont toujours vulnérables. Le nombre de difficulté réel est basé sur un échantillonnage statistique et peut fluctuer. Il est généralement préférable d'utiliser la classification en anglais telle que "worthy challenge" ou "trivial joke". Ceci n'est rapporté dans la sortie normale qu'en mode verbeux (-v). Lorsque le mode verbeux est activé avec -O, la génération de séquence d'ID IP est également rapportée. La plupart des machines sont dans la classe "incremental", ce qui signifie qu'elles incrémentent le champ ID dans l'en-tête IP pour chaque paquet qu'elles envoient. Cela les rend vulnérables à plusieurs attaques avancées de collecte d'informations et d'usurpation.

Une autre information supplémentaire activée par la détection d'OS est une estimation de la disponibilité d'une cible. Elle utilise l'option de horodatage TCP (RFC 1323[9]) pour estimer quand une machine a été redémarrée pour la dernière fois. L'estimation peut être inexacte en raison du compteur d'horodatage qui n'est pas initialisé à zéro ou du dépassement du compteur et de son retour à zéro, elle n'est donc imprimée qu'en mode verbeux.

Un document détaillant le fonctionnement, l'utilisation et la personnalisation de la détection d'OS est disponible à https://nmap.org/book/osdetect.html.

La détection d'OS est activée et contrôlée avec les options suivantes :

-O (Activer la détection d'OS)

Active la détection d'OS, comme décrit ci-dessus. Alternativement, vous pouvez utiliser -A pour activer la détection d'OS en plus d'autres éléments.

--osscan-limit (Limiter la détection d'OS aux cibles prometteuses)

La détection d'OS est beaucoup plus efficace si au moins un port TCP ouvert et un port TCP fermé sont trouvés. Réglez cette option et Nmap n'essaiera même pas la détection d'OS sur les hôtes qui ne répondent pas à ces critères. Cela peut faire gagner un temps considérable, en particulier sur les scans -Pn contre de nombreux hôtes. Cela n'a d'importance que lorsque la détection d'OS est demandée avec -O ou -A.

--osscan-guess; --fuzzy (Deviner les résultats de détection d'OS)

Lorsque Nmap ne parvient pas à trouver une correspondance d'OS parfaite, il propose parfois des correspondances proches comme possibilités. La correspondance doit être très proche pour que Nmap le fasse par défaut. Chacune de ces options (équivalentes) permet à Nmap de deviner plus agressivement. Nmap vous indiquera toujours quand une correspondance imparfaite est imprimée et affichera son niveau de confiance (pourcentage) pour chaque supposition.

--max-os-tries (Définir le nombre maximum d'essais de détection d'OS contre une cible)

Lorsque Nmap effectue une détection d'OS contre une cible et ne parvient pas à trouver une correspondance parfaite, il répète généralement la tentative. Par défaut, Nmap essaie cinq fois si les conditions sont favorables à la soumission d'empreintes d'OS, et deux fois lorsque les conditions ne sont pas aussi bonnes. Spécifier une valeur plus faible pour --max-os-tries (comme 1) accélère Nmap, bien que vous manquiez les nouvelles tentatives qui pourraient potentiellement identifier l'OS. Alternativement, une valeur élevée peut être définie pour permettre encore plus de nouvelles tentatives lorsque les conditions sont favorables. Ceci est rarement fait, sauf pour générer de meilleures empreintes à soumettre et intégrer dans la base de données d'OS de Nmap.

MOTEUR DE SCRIPTS NMAP (NSE)

Le moteur de scripts Nmap (NSE) est l'une des fonctionnalités les plus puissantes et flexibles de Nmap. Il permet aux utilisateurs d'écrire (et de partager) des scripts simples (utilisant le langage de programmation Lua[10]) pour automatiser une grande variété de tâches réseau. Ces scripts sont exécutés en parallèle avec la vitesse et l'efficacité que vous attendez de Nmap. Les utilisateurs peuvent s'appuyer sur l'ensemble croissant et diversifié de scripts distribués avec Nmap, ou écrire les leurs pour répondre à des besoins personnalisés.

Les tâches que nous avions à l'esprit lors de la création du système comprennent la découverte de réseau, une détection de version plus sophistiquée, la détection de vulnérabilités. NSE peut même être utilisé pour l'exploitation de vulnérabilités.

Pour refléter ces différentes utilisations et simplifier le choix des scripts à exécuter, chaque script contient un champ l'associant à une ou plusieurs catégories. Les catégories actuellement définies sont auth, broadcast, default, discovery, dos, exploit, external, fuzzer, intrusive, malware, safe, version, et vuln. Celles-ci sont toutes décrites à https://nmap.org/book/nse-usage.html#nse-categories.

Les scripts ne sont pas exécutés dans un bac à sable et pourraient donc accidentellement ou malicieusement endommager votre système ou violer votre vie privée. Ne jamais exécuter de scripts de tiers à moins que vous ne fassiez confiance aux auteurs ou que vous n'ayez soigneusement audité les scripts vous-même.

Le moteur de scripts Nmap est décrit en détail à https://nmap.org/book/nse.html

et est contrôlé par les options suivantes :

-sC

Exécute un scan de scripts en utilisant l'ensemble par défaut des scripts. Il est équivalent à --script=default. Certains des scripts de cette catégorie sont considérés comme intrusifs et ne devraient pas être exécutés sur un réseau cible sans permission.

Notez que cette option abrégée est ignorée chaque fois qu'au moins un --script est également spécifié.

--script filename|category|directory/|expression[,...]

Exécute un scan de scripts en utilisant la liste séparée par des virgules de noms de fichiers, de catégories de scripts et de répertoires. Chaque élément de la liste peut également être une expression booléenne décrivant un ensemble de scripts plus complexe. Chaque élément est interprété d'abord comme une expression, puis comme une catégorie, et enfin comme un nom de fichier ou de répertoire.

Il existe deux fonctionnalités spéciales réservées aux utilisateurs avancés. L'une consiste à préfixer les noms de scripts et les expressions par + pour les forcer à s'exécuter même s'ils ne le feraient normalement pas (par exemple, si le service pertinent n'a pas été détecté sur le port cible). L'autre est que l'argument `all` peut être utilisé pour spécifier tous les scripts de la base de données Nmap. Soyez prudent avec cela car NSE contient des scripts dangereux tels que des exploits, des brouilleurs d'authentification par force brute et des attaques par déni de service.

Les noms de fichiers et de répertoires peuvent être relatifs ou absolus. Les noms absolus sont utilisés directement. Les chemins relatifs sont recherchés dans les scripts de chacun des emplacements suivants jusqu'à ce qu'ils soient trouvés :

--datadir
$NMAPDIR
~/.nmap (non recherché sur Windows)
APPDATA\nmap (uniquement sur Windows)
le répertoire contenant l'exécutable nmap
le répertoire contenant l'exécutable nmap, suivi de ../share/nmap (non recherché sur Windows)
NMAPDATADIR (non recherché sur Windows)
le répertoire courant.

Lorsqu'un nom de répertoire se terminant par / est donné, Nmap charge tous les fichiers du répertoire dont le nom se termine par .nse. Tous les autres fichiers sont ignorés et les répertoires ne sont pas recherchés de manière récursive. Lorsqu'un nom de fichier est donné, il n'a pas besoin d'avoir l'extension .nse ; elle sera ajoutée automatiquement si nécessaire. Les scripts Nmap sont stockés dans un sous-répertoire `scripts`

ANALYSE PAR SCRIPTS

Les scripts Nmap peuvent être sélectionnés de plusieurs manières.

Par défaut, Nmap exécute tous les scripts qui appartiennent à la catégorie default. Les scripts sont stockés dans le répertoire scripts/ du répertoire de données Nmap (voir https://nmap.org/book/data-files.html).

Pour des raisons d'efficacité, les scripts sont indexés dans une base de données stockée dans scripts/script.db, qui répertorie la ou les catégories auxquelles chaque script appartient. Lorsque vous faites référence à des scripts de script.db par leur nom, vous pouvez utiliser un joker de type shell « * ».

nmap --script "http-*"

Charge tous les scripts dont le nom commence par http-, comme http-auth et http-open-proxy. L'argument de --script doit être entre guillemets pour protéger le joker du shell.

Une sélection de scripts plus complexe peut être effectuée en utilisant les opérateurs and, or et not pour construire des expressions booléennes. Les opérateurs ont la même précédence[11] qu'en Lua : not est le plus élevé, suivi de and puis de or. Vous pouvez modifier la précédence en utilisant des parenthèses. Comme les expressions contiennent des espaces, il est nécessaire de les mettre entre guillemets.

nmap --script "not intrusive"

Charge tous les scripts sauf ceux de la catégorie intrusive.

nmap --script "default or safe"

Ceci est fonctionnellement équivalent à nmap --script "default,safe". Il charge tous les scripts qui sont dans la catégorie default ou dans la catégorie safe ou les deux.

nmap --script "default and safe"

Charge les scripts qui sont dans les catégories default et safe.

nmap --script "(default or safe or intrusive) and not http-*"

Charge les scripts des catégories default, safe ou intrusive, à l'exception de ceux dont le nom commence par http-.

ARGUMENTS DE SCRIPTS

--script-args n1=v1,n2={n3=v3},n4={v4,v5}

Permet de fournir des arguments aux scripts NSE. Les arguments sont une liste de paires nom=valeur séparées par des virgules. Les noms et les valeurs peuvent être des chaînes de caractères ne contenant pas d'espaces blancs ni les caractères « { », « } », « = », ou « , ». Pour inclure l'un de ces caractères dans une chaîne, entourez la chaîne de guillemets simples ou doubles. Dans une chaîne entre guillemets, « \ » échappe un guillemet. Une barre oblique inverse est utilisée uniquement pour échapper les marques de citation dans ce cas spécial ; dans tous les autres cas, une barre oblique inverse est interprétée littéralement. Les valeurs peuvent également être des tables entourées de {}, comme en Lua. Une table peut contenir des valeurs de chaînes simples ou plus de paires nom-valeur, y compris des tables imbriquées. De nombreux scripts qualifient leurs arguments avec le nom du script, comme dans xmpp-info.server_name. Vous pouvez utiliser cette version entièrement qualifiée pour n'affecter que le script spécifié, ou vous pouvez utiliser la version non qualifiée (server_name dans ce cas) pour affecter tous les scripts utilisant ce nom d'argument. Un script vérifiera d'abord son nom d'argument entièrement qualifié (le nom spécifié dans sa documentation) avant d'accepter un nom d'argument non qualifié. Un exemple complexe d'arguments de script est --script-args 'user=foo,pass=",{}=bar",whois={whodb=nofollow+ripe},xmpp-info.server_name=localhost'. Le portail de documentation NSE en ligne à https://nmap.org/nsedoc/ répertorie les arguments que chaque script accepte.

--script-args-file nom_fichier

Permet de charger les arguments des scripts NSE à partir d'un fichier. Tous les arguments de la ligne de commande remplacent ceux du fichier. Le fichier peut être un chemin absolu, ou un chemin relatif au chemin de recherche habituel de Nmap (NMAPDIR, etc.). Les arguments peuvent être séparés par des virgules ou par des sauts de ligne, mais suivent sinon les mêmes règles que pour --script-args, sans nécessiter de guillemets et d'échappement spéciaux, car ils ne sont pas analysés par le shell.

--script-help nom_fichier|catégorie|répertoire|expression|all[,...]

Affiche l'aide sur les scripts. Pour chaque script correspondant à la spécification donnée, Nmap imprime le nom du script, ses catégories et sa description. Les spécifications sont les mêmes que celles acceptées par --script ; ainsi, par exemple, si vous souhaitez obtenir de l'aide sur le script ftp-anon, vous exécuteriez nmap --script-help ftp-anon. En plus d'obtenir de l'aide pour des scripts individuels, vous pouvez l'utiliser comme aperçu de ce qui sera exécuté pour une spécification, par exemple avec nmap --script-help default.

--script-trace

Cette option fait ce que fait --packet-trace, juste une couche ISO plus haut. Si cette option est spécifiée, toute communication entrante et sortante effectuée par un script est affichée. Les informations affichées incluent le protocole de communication, la source, la cible et les données transmises. Si plus de 5 % de toutes les données transmises ne sont pas imprimables, la sortie de trace est au format dump hexadécimal. La spécification de --packet-trace active également le traçage des scripts.

--script-updatedb

Cette option met à jour la base de données des scripts trouvée dans scripts/script.db, qui est utilisée par Nmap pour déterminer les scripts et catégories par défaut disponibles. Il est seulement nécessaire de mettre à jour la base de données si vous avez ajouté ou supprimé des scripts NSE du répertoire des scripts par défaut ou si vous avez modifié les catégories d'un script. Cette option est généralement utilisée seule : nmap --script-updatedb.

TEMPORISATION ET PERFORMANCES

L'une de mes plus hautes priorités de développement Nmap a toujours été la performance. Un scan par défaut (nmap nom_hôte) d'un hôte sur mon réseau local prend un cinquième de seconde. C'est à peine le temps de cligner des yeux, mais cela s'accumule lorsque vous scannez des centaines ou des milliers d'hôtes. De plus, certaines options de scan comme le scan UDP et la détection de version peuvent considérablement augmenter les temps de scan. Il en va de même pour certaines configurations de pare-feu, en particulier la limitation du taux de réponse. Bien que Nmap utilise le parallélisme et de nombreux algorithmes avancés pour accélérer ces scans, l'utilisateur a le contrôle ultime sur le fonctionnement de Nmap. Les utilisateurs experts élaborent soigneusement les commandes Nmap pour obtenir uniquement les informations qui les intéressent tout en respectant leurs contraintes de temps.

Les techniques pour améliorer les temps de scan incluent l'omission des tests non critiques et la mise à niveau vers la dernière version de Nmap (des améliorations de performance sont faites fréquemment). L'optimisation des paramètres de temporisation peut également faire une différence substantielle. Ces options sont listées ci-dessous.

Certaines options acceptent un paramètre de temps. Il est spécifié en secondes par défaut, bien que vous puissiez ajouter « ms », « s », « m », ou « h » à la valeur pour spécifier des millisecondes, secondes, minutes ou heures. Ainsi, les arguments --host-timeout 900000ms, 900, 900s et 15m font tous la même chose.

--min-hostgroup nb_hotes; --max-hostgroup nb_hotes (Ajuster les tailles de groupes de scans parallèles)

Nmap a la capacité de scanner les ports ou de détecter la version de plusieurs hôtes en parallèle. Nmap le fait en divisant l'espace IP cible en groupes, puis en scannant un groupe à la fois. En général, des groupes plus grands sont plus efficaces. Le revers de la médaille est que les résultats des hôtes ne peuvent pas être fournis tant que tout le groupe n'est pas terminé. Ainsi, si Nmap commençait avec une taille de groupe de 50, l'utilisateur ne recevrait aucun rapport (sauf les mises à jour offertes en mode verbeux) tant que les 50 premiers hôtes ne seraient pas terminés.

Par défaut, Nmap adopte une approche de compromis à ce conflit. Il commence avec une taille de groupe aussi basse que cinq pour que les premiers résultats arrivent rapidement, puis augmente la taille du groupe jusqu'à 1024. Les nombres par défaut exacts dépendent des options données. Pour des raisons d'efficacité, Nmap utilise des tailles de groupe plus grandes pour les scans UDP ou TCP sur peu de ports.

Lorsqu'une taille de groupe maximale est spécifiée avec --max-hostgroup, Nmap ne dépassera jamais cette taille. Spécifiez une taille minimale avec --min-hostgroup et Nmap essaiera de maintenir les tailles de groupe au-dessus de ce niveau. Nmap pourrait avoir à utiliser des groupes plus petits que ceux que vous spécifiez s'il ne reste pas suffisamment d'hôtes cibles sur une interface donnée pour satisfaire le minimum spécifié. Les deux peuvent être définis pour maintenir la taille du groupe dans une plage spécifique, bien que cela soit rarement souhaitable.

Ces options n'ont pas d'effet pendant la phase de découverte d'hôtes d'un scan. Cela inclut les scans ping simples (-sn). La découverte d'hôtes fonctionne toujours par grands groupes d'hôtes pour améliorer la vitesse et la précision.

L'utilisation principale de ces options est de spécifier une grande taille de groupe minimale afin que le scan complet s'exécute plus rapidement. Un choix courant est 256 pour scanner un réseau par blocs de /24. Pour un scan avec de nombreux ports, dépasser ce nombre n'est pas susceptible d'aider beaucoup. Pour les scans de seulement quelques numéros de port, des tailles de groupe d'hôtes de 2048 ou plus peuvent être utiles.

--min-parallelism nb_sondes; --max-parallelism nb_sondes (Ajuster la parallélisation des sondes)

Ces options contrôlent le nombre total de sondes qui peuvent être en attente pour un groupe d'hôtes. Elles sont utilisées pour le scan de ports et la découverte d'hôtes. Par défaut, Nmap calcule une parallélisation idéale et en constante évolution basée sur les performances du réseau. Si des paquets sont perdus, Nmap ralentit et autorise moins de sondes en attente. Le nombre idéal de sondes augmente lentement à mesure que le réseau fait ses preuves. Ces options placent des limites minimales ou maximales à cette variable. Par défaut, la parallélisation idéale peut descendre à un si le réseau s'avère peu fiable et monter à plusieurs centaines dans des conditions parfaites.

L'utilisation la plus courante est de définir --min-parallelism à un nombre supérieur à un pour accélérer les scans d'hôtes ou de réseaux peu performants. C'est une option risquée avec laquelle jouer, car la régler trop haut peut affecter la précision. La définir réduit également la capacité de Nmap à contrôler la parallélisation dynamiquement en fonction des conditions du réseau. Une valeur de 10 pourrait être raisonnable, bien que je ne modifie cette valeur qu'en dernier recours.

L'option --max-parallelism est parfois définie à un pour empêcher Nmap d'envoyer plus d'une sonde à la fois aux hôtes. L'option --scan-delay, discutée plus tard, est une autre façon de le faire.

--min-rtt-timeout temps, --max-rtt-timeout temps, --initial-rtt-timeout temps (Ajuster les délais d'attente des sondes)

Nmap maintient une valeur de délai d'attente dynamique pour déterminer combien de temps il attendra une réponse à une sonde avant d'abandonner ou de retransmettre la sonde. Ceci est calculé sur la base des temps de réponse des sondes précédentes.

Si la latence du réseau s'avère significative et variable, ce délai peut atteindre plusieurs secondes. Il commence également à un niveau prudent (élevé) et peut le rester pendant un certain temps lorsque Nmap scanne des hôtes peu réactifs.

Spécifier un --max-rtt-timeout et un --initial-rtt-timeout inférieurs aux valeurs par défaut peut réduire significativement les temps de scan. C'est particulièrement vrai pour les scans sans ping (-Pn) et ceux contre des systèmes fortement filtrés.

Nmap Timing Options

Nmap offers many options to control the timing of a scan. This allows you to control the aggressiveness of the scan, and also to adapt it to specific network conditions. Nmap's default timing algorithm is quite effective, but sometimes you need to tune it.

--max-rtt-timeout time (Specify the maximum round trip time for probes)

This option specifies the maximum time that Nmap will wait for a probe response. If Nmap doesn't receive a response within this time, it will stop waiting and consider the probe lost. This is useful for speeding up scans on slow or unreliable networks. For example, --max-rtt-timeout 200ms tells Nmap to give up on a probe after 200 milliseconds.

The default value for this option depends on the timing template selected with the -T option. With the default timing template (-T0), the value is 10 minutes. With -T1, it's 10 seconds. With -T2, it's 2 seconds. With -T3, it's 1 second. With -T4, it's 400ms. With -T5, it's 50ms.

Don't set this value too low, especially on the internet. The scan can end up taking longer if you specify such a low value that many probes are timing out and retransmitting while the response is in transit.

If all the hosts are on a local network, 100 milliseconds (--max-rtt-timeout 100ms) is a reasonable aggressive value. If routing is involved, ping a host on the network first with the ICMP ping utility, or with a custom packet crafter such as Nping that is more likely to get through a firewall. Look at the maximum round trip time out of ten packets or so. You might want to double that for the --initial-rtt-timeout and triple or quadruple it for the --max-rtt-timeout. I generally do not set the maximum RTT below 100 ms, no matter what the ping times are. Nor do I exceed 1000 ms.

--min-rtt-timeout is a rarely used option that could be useful when a network is so unreliable that even Nmap's default is too aggressive. Since Nmap only reduces the timeout down to the minimum when the network seems to be reliable, this need is unusual and should be reported as a bug to the nmap-dev mailing list.

--max-retries numtries (Specify the maximum number of port scan probe retransmissions)

When Nmap receives no response to a port scan probe, it could mean the port is filtered. Or maybe the probe or response was simply lost on the network. It is also possible that the target host has rate limiting enabled that temporarily blocked the response. So Nmap tries again by retransmitting the initial probe. If Nmap detects poor network reliability, it may try many more times before giving up on a port. While this benefits accuracy, it also lengthens scan times. When performance is critical, scans may be sped up by limiting the number of retransmissions allowed. You can even specify --max-retries 0 to prevent any retransmissions, though that is only recommended for situations such as informal surveys where occasional missed ports and hosts are acceptable.

The default (with no -T template) is to allow ten retransmissions. If a network seems reliable and the target hosts aren't rate limiting, Nmap usually only does one retransmission. So most target scans aren't even affected by dropping --max-retries to a low value such as three. Such values can substantially speed scans of slow (rate limited) hosts. You usually lose some information when Nmap gives up on ports early, though that may be preferable to letting the --host-timeout expire and losing all information about the target.

--host-timeout time (Give up on slow target hosts)

Some hosts simply take a long time to scan. This may be due to poorly performing or unreliable networking hardware or software, packet rate limiting, or a restrictive firewall. The slowest few percent of the scanned hosts can eat up a majority of the scan time. Sometimes it is best to cut your losses and skip those hosts initially. Specify --host-timeout with the maximum amount of time you are willing to wait. For example, specify 30m to ensure that Nmap doesn't waste more than half an hour on a single host. Note that Nmap may be scanning other hosts at the same time during that half an hour, so it isn't a complete loss. A host that times out is skipped. No port table, OS detection, or version detection results are printed for that host.

The special value 0 can be used to mean “no timeout”, which can be used to override the T5 timing template, which sets the host timeout to 15 minutes.

--script-timeout time

While some scripts complete in fractions of a second, others can take hours or more depending on the nature of the script, arguments passed in, network and application conditions, and more. The --script-timeout option sets a ceiling on script execution time. Any script instance which exceeds that time will be terminated and no output will be shown. If debugging (-d) is enabled, Nmap will report on each timeout. For host and service scripts, a script instance only scans a single target host or port and the timeout period will be reset for the next instance.

The special value 0 can be used to mean “no timeout”, which can be used to override the T5 timing template, which sets the script timeout to 10 minutes.

--scan-delay time; --max-scan-delay time (Adjust delay between probes)

This option causes Nmap to wait at least the given amount of time between each probe it sends to a given host. This is particularly useful in the case of rate limiting. Solaris machines (among many others) will usually respond to UDP scan probe packets with only one ICMP message per second. Any more than that sent by Nmap will be wasteful. A --scan-delay of 1s will keep Nmap at that slow rate. Nmap tries to detect rate limiting and adjust the scan delay accordingly, but it doesn't hurt to specify it explicitly if you already know what rate works best.

When Nmap adjusts the scan delay upward to cope with rate limiting, the scan slows down dramatically. The --max-scan-delay option specifies the largest delay that Nmap will allow. A low --max-scan-delay can speed up Nmap, but it is risky. Setting this value too low can lead to wasteful packet retransmissions and possible missed ports when the target implements strict rate limiting.

Another use of --scan-delay is to evade threshold based intrusion detection and prevention systems (IDS/IPS).

--min-rate number; --max-rate number (Directly control the scanning rate)

Nmap's dynamic timing does a good job of finding an appropriate speed at which to scan. Sometimes, however, you may happen to know an appropriate scanning rate for a network, or you may have to guarantee that a scan will be finished by a certain time. Or perhaps you must keep Nmap from scanning too quickly. The --min-rate and --max-rate options are designed for these situations.

When the --min-rate option is given Nmap will do its best to send packets as fast as or faster than the given rate. The argument is a positive real number representing a packet rate in packets per second. For example, specifying --min-rate 300 means that Nmap will try to keep the sending rate at or above 300 packets per second. Specifying a minimum rate does not keep Nmap from going faster if conditions warrant.

Likewise, --max-rate limits a scan's sending rate to a given maximum. Use --max-rate 100, for example, to limit sending to 100 packets per second on a fast network. Use --max-rate 0.1 for a slow scan of one packet every ten seconds. Use --min-rate and --max-rate together to keep the rate inside a certain range.

These two options are global, affecting an entire scan, not individual hosts. They only affect port scans and host discovery scans. Other features like OS detection implement their own timing.

There are two conditions when the actual scanning rate may fall below the requested minimum. The first is if the minimum is faster than the fastest rate at which Nmap can send, which is dependent on hardware. In this case Nmap will simply send packets as fast as possible, but be aware that such high rates are likely to cause a loss of accuracy. The second case is when Nmap has nothing to send, for example at the end of a scan when the last probes have been sent and Nmap is waiting for them to time out or be responded to. It's normal to see the scanning rate drop at the end of a scan or in between hostgroups. The sending rate may temporarily exceed the maximum to make up for unpredictable delays, but on average the rate will stay at or below the maximum.

Specifying a minimum rate should be done with care. Scanning faster than a network can support may lead to a loss of accuracy. In some cases, using a faster rate can make a scan take longer than it would with a slower rate. This is because Nmap's adaptive retransmission algorithms will detect the network congestion caused by an excessive scanning rate and increase the number of retransmissions in order to improve accuracy. So even though packets are sent at a higher rate, more packets are sent overall. Cap the number of retransmissions with the --max-retries option if you need to set an upper limit on total scan time.

--defeat-rst-ratelimit

Many hosts have long used rate limiting to reduce the number of ICMP error messages (such as port-unreachable errors) they send. Some systems now apply similar rate limits to the RST (reset) packets they generate. This can slow Nmap down dramatically as it adjusts its timing to reflect those rate limits. You can tell Nmap to ignore those rate limits (for port scans such as SYN scan which don't treat non-responsive ports as open) by specifying --defeat-rst-ratelimit.

Using this option can reduce accuracy, as some ports will appear non-responsive because Nmap didn't wait long enough for a rate-limited RST response. With a SYN scan, the non-response results in the port being labeled filtered rather than the closed state we see when RST packets are received. This option is useful when you only care about open ports, and distinguishing between closed and filtered ports isn't worth the extra time.

--defeat-icmp-ratelimit

Similar to --defeat-rst-ratelimit, the --defeat-icmp-ratelimit option trades accuracy for speed, increasing UDP scanning speed against hosts that rate-limit ICMP error messages. Because this option causes Nmap to not delay in order to receive the port unreachable messages, a non-responsive port will be labeled closed|filtered instead of the default open|filtered. This has the effect of only treating ports which actually respond via UDP as open. Since many UDP services do not respond in this way, the chance for inaccuracy is greater with this option than with --defeat-rst-ratelimit.

--nsock-engine iocp|epoll|kqueue|poll|select

Enforce use of a given nsock IO multiplexing engine. Only the select(2)-based fallback engine is guaranteed to be available on your system. Engines are named after the name of the IO management facility they leverage. Engines currently implemented are epoll, kqueue, poll, and select, but not all will be present on any platform. By default, Nmap will use the "best" engine, i.e. the first one in this list that is supported. Use nmap -V to see which engines are supported on your platform.

-T paranoid|sneaky|polite|normal|aggressive|insane (Set a timing template)

While the fine-grained timing controls discussed in the previous section are powerful and effective, some people find them confusing. Moreover, choosing the appropriate values can sometimes take more time than the scan you are trying to optimize. Fortunately, Nmap offers a simpler approach, with six timing templates. You c

et et spécifiez-les avec l'option -T et leur numéro (0–5) ou leur nom. Les noms de modèles sont paranoid (0), sneaky (1), polite (2), normal (3), aggressive (4) et insane (5). Les deux premiers sont destinés à l'évasion de l'IDS. Le mode poli ralentit l'analyse pour utiliser moins de bande passante et de ressources machine cibles. Le mode normal est le défaut et donc -T3 ne fait rien. Le mode agressif accélère les analyses en supposant que vous êtes sur un réseau raisonnablement rapide et fiable. Enfin, le mode insensé suppose que vous êtes sur un réseau extraordinairement rapide ou que vous êtes prêt à sacrifier une certaine précision pour la vitesse.

Ces modèles permettent à l'utilisateur de spécifier son degré d'agressivité, tout en laissant à Nmap le soin de choisir les valeurs de temporisation exactes. Les modèles apportent également des ajustements de vitesse mineurs pour lesquels des options de contrôle fin n'existent pas actuellement. Par exemple, -T4 interdit au délai d'analyse dynamique de dépasser 10 ms pour les ports TCP et -T5 plafonne cette valeur à 5 ms. Les modèles peuvent être utilisés en combinaison avec des contrôles fins, et les contrôles fins que vous spécifiez auront la priorité sur le défaut du modèle de temporisation pour ce paramètre. Je recommande d'utiliser -T4 lors de l'analyse de réseaux raisonnablement modernes et fiables. Conservez cette option même lorsque vous ajoutez des contrôles fins afin de bénéficier de ces optimisations mineures supplémentaires qu'elle permet.

Si vous disposez d'une connexion haut débit ou Ethernet correcte, je recommande d'utiliser toujours -T4. Certaines personnes adorent -T5, bien qu'il soit trop agressif à mon goût. Les gens spécifient parfois -T2 parce qu'ils pensent qu'il est moins susceptible de faire planter les hôtes ou parce qu'ils se considèrent polis en général. Ils ne se rendent souvent pas compte à quel point -T polite est lent. Leur analyse peut prendre dix fois plus de temps qu'une analyse par défaut. Les plantages de machines et les problèmes de bande passante sont rares avec les options de temporisation par défaut (-T3) et je recommande donc normalement cela pour les analyseurs prudents. Omettre la détection de version est beaucoup plus efficace que de jouer avec les valeurs de temporisation pour réduire ces problèmes.

Bien que -T0 et -T1 puissent être utiles pour éviter les alertes IDS, ils prendront un temps extraordinairement long pour analyser des milliers de machines ou de ports. Pour une analyse aussi longue, vous pourriez préférer définir les valeurs de temporisation exactes dont vous avez besoin plutôt que de vous fier aux valeurs prédéfinies -T0 et -T1.

Les principaux effets de T0 sont la sérialisation de l'analyse, de sorte qu'un seul port est analysé à la fois, et une attente de cinq minutes entre l'envoi de chaque sonde. T1 et T2 sont similaires mais ils n'attendent que 15 secondes et 0,4 seconde, respectivement, entre les sondes. T3 est le comportement par défaut de Nmap, qui inclut la parallélisation. -T4 fait l'équivalent de --max-rtt-timeout 1250ms --min-rtt-timeout 100ms --initial-rtt-timeout 500ms --max-retries 6 et définit le délai d'analyse TCP et SCTP maximal à 10 ms. T5 fait l'équivalent de --max-rtt-timeout 300ms --min-rtt-timeout 50ms --initial-rtt-timeout 250ms --max-retries 2 --host-timeout 15m --script-timeout 10m ainsi que le délai d'analyse TCP et SCTP maximal à 5 ms. Le délai d'analyse UDP maximal n'est pas défini par T4 ou T5, mais il peut être défini avec l'option --max-scan-delay.

PARE-FEU/DETECTION D'INTRUSION ET USURPATION

De nombreux pionniers d'Internet ont imaginé un réseau ouvert mondial avec un espace d'adresses IP universel permettant des connexions virtuelles entre n'importe quels deux nœuds. Cela permet aux hôtes d'agir comme de véritables pairs, servant et récupérant des informations les uns des autres. Les gens pouvaient accéder à tous leurs systèmes domestiques depuis le travail, en modifiant les paramètres de contrôle du climat ou en déverrouillant les portes pour les premiers invités. Cette vision de connectivité universelle a été étouffée par les pénuries d'espace d'adresses et les préoccupations en matière de sécurité. Au début des années 1990, les organisations ont commencé à déployer des pare-feu dans le but exprès de réduire la connectivité. D'énormes réseaux ont été mis à l'écart de l'Internet non filtré par des proxys d'applications, la traduction d'adresses réseau et des filtres de paquets. Le flux non restreint d'informations a cédé la place à une réglementation stricte des canaux de communication approuvés et du contenu qui les traverse.

Les obstructions réseau telles que les pare-feu peuvent rendre la cartographie d'un réseau extrêmement difficile. Cela ne deviendra pas plus facile, car l'étouffement de la reconnaissance informelle est souvent un objectif clé de la mise en œuvre de ces appareils. Néanmoins, Nmap offre de nombreuses fonctionnalités pour aider à comprendre ces réseaux complexes et à vérifier que les filtres fonctionnent comme prévu. Il prend même en charge des mécanismes pour contourner les défenses mal implémentées. L'une des meilleures méthodes pour comprendre votre posture de sécurité réseau est d'essayer de la vaincre. Mettez-vous dans l'état d'esprit d'un attaquant et déployez les techniques de cette section contre vos réseaux. Lancez une analyse de rebond FTP, une analyse idle, une attaque par fragmentation, ou essayez de tunneliser à travers l'un de vos propres proxys.

En plus de restreindre l'activité réseau, les entreprises surveillent de plus en plus le trafic avec des systèmes de détection d'intrusion (IDS). Tous les principaux IDS sont livrés avec des règles conçues pour détecter les analyses Nmap, car les analyses sont parfois un précurseur d'attaques. Bon nombre de ces produits se sont récemment transformés en systèmes de prévention d'intrusion (IPS) qui bloquent activement le trafic jugé malveillant. Malheureusement pour les administrateurs réseau et les fournisseurs d'IDS, la détection fiable d'intentions malveillantes en analysant les données des paquets est un problème difficile. Les attaquants patients, compétents et aidés par certaines options de Nmap peuvent généralement passer inaperçus par les IDS. Pendant ce temps, les administrateurs doivent faire face à un grand nombre de faux positifs où une activité innocente est mal diagnostiquée et alertée ou bloquée.

Parfois, des gens suggèrent que Nmap ne devrait pas offrir de fonctionnalités pour échapper aux règles de pare-feu ou passer discrètement derrière les IDS. Ils soutiennent que ces fonctionnalités sont tout aussi susceptibles d'être mal utilisées par les attaquants que d'être utilisées par les administrateurs pour améliorer la sécurité. Le problème avec cette logique est que ces méthodes seraient toujours utilisées par les attaquants, qui trouveraient simplement d'autres outils ou intégreraient la fonctionnalité dans Nmap. Pendant ce temps, les administrateurs auraient beaucoup plus de mal à faire leur travail. Déployer uniquement des serveurs FTP modernes et patchés est une défense beaucoup plus puissante que d'essayer d'empêcher la distribution d'outils implémentant l'attaque par rebond FTP.

Il n'y a pas de solution miracle (ou d'option Nmap) pour détecter et subvertir les pare-feu et les systèmes IDS. Cela demande des compétences et de l'expérience. Un tutoriel dépasse le cadre de ce guide de référence, qui ne fait que lister les options pertinentes et décrire ce qu'elles font.

-f (fragmenter les paquets) ; --mtu (utiliser le MTU spécifié)

L'option -f fait que l'analyse demandée (y compris les analyses de découverte d'hôtes) utilise de minuscules paquets IP fragmentés. L'idée est de diviser l'en-tête TCP sur plusieurs paquets pour rendre plus difficile la détection de ce que vous faites par les filtres de paquets, les systèmes de détection d'intrusion et autres désagréments. Soyez prudent avec cela ! Certains programmes ont du mal à gérer ces minuscules paquets. Le renifleur old-school nommé Sniffit a immédiatement généré une faute de segmentation à la réception du premier fragment. Spécifiez cette option une fois, et Nmap divise les paquets en huit octets ou moins après l'en-tête IP. Ainsi, un en-tête TCP de 20 octets serait divisé en trois paquets. Deux avec huit octets de l'en-tête TCP, et un avec les quatre derniers. Bien sûr, chaque fragment a également un en-tête IP. Spécifiez -f à nouveau pour utiliser 16 octets par fragment (réduisant le nombre de fragments). Ou vous pouvez spécifier votre propre taille de décalage avec l'option --mtu. Ne spécifiez pas non plus -f si vous utilisez --mtu. Le décalage doit être un multiple de huit. Bien que les paquets fragmentés ne franchissent pas les filtres de paquets et les pare-feu qui mettent en file d'attente tous les fragments IP, comme l'option CONFIG_IP_ALWAYS_DEFRAG du noyau Linux, certains réseaux ne peuvent pas se permettre la perte de performance que cela entraîne et le laissent donc désactivé. D'autres ne peuvent pas l'activer car les fragments peuvent emprunter des chemins différents pour entrer dans leurs réseaux. Certains systèmes sources défragmentent les paquets sortants dans le noyau. Linux avec le module de suivi de connexion iptables en est un exemple. Effectuez une analyse pendant qu'un renifleur comme Wireshark est en cours d'exécution pour vous assurer que les paquets envoyés sont fragmentés. Si votre système d'exploitation hôte pose des problèmes, essayez l'option --send-eth pour contourner la couche IP et envoyer des trames Ethernet brutes.

La fragmentation n'est prise en charge que pour les fonctionnalités de paquets bruts de Nmap, qui incluent les analyses de ports TCP et UDP (sauf les analyses connect et FTP bounce) et la détection d'OS. Les fonctionnalités telles que la détection de version et le Nmap Scripting Engine ne prennent généralement pas en charge la fragmentation car elles reposent sur la pile TCP de votre hôte pour communiquer avec les services cibles.

-D decoy1[,decoy2][,ME][,...] (Masquer une analyse avec des leurres)

Provoque une analyse de leurre, qui fait croire à l'hôte distant que les hôtes que vous spécifiez comme leurres analysent également le réseau cible. Ainsi, leur IDS pourrait signaler 5 à 10 analyses de ports à partir d'adresses IP uniques, mais ils ne sauront pas quelle IP les scanne et quelles étaient des leurres innocents. Bien que cela puisse être contourné par la localisation des routeurs, la suppression des réponses et d'autres mécanismes actifs, c'est généralement une technique efficace pour masquer votre adresse IP.

Séparez chaque hôte leurre par des virgules, et vous pouvez facultativement utiliser ME comme l'un des leurres pour représenter la position de votre véritable adresse IP. Si vous placez ME en sixième position ou plus, certains détecteurs d'analyse de ports courants (comme l'excellent Scanlogd de Solar Designer) sont peu susceptibles d'afficher votre adresse IP. Si vous n'utilisez pas ME, Nmap vous placera dans une position aléatoire. Vous pouvez également utiliser RND pour générer une adresse IP aléatoire et non réservée, ou RND:nombre pour générer nombre adresses.

Notez que les hôtes que vous utilisez comme leurres doivent être en marche, sinon vous pourriez accidentellement inonder de SYN vos cibles. Il sera également assez facile de déterminer quel hôte scanne si un seul est réellement actif sur le réseau. Vous pourriez vouloir utiliser des adresses IP au lieu de noms (de sorte que les réseaux leurres ne vous voient pas dans leurs journaux de serveur de noms). Actuellement, la génération d'adresses IP aléatoires n'est prise en charge qu'avec IPv4.

Les leurres sont utilisés à la fois dans l'analyse initiale de découverte d'hôtes (en utilisant ICMP, SYN, ACK, ou quoi que ce soit) et pendant la phase d'analyse de ports réelle. Les leurres sont également utilisés lors de la détection d'OS à distance (-O). Les leurres ne fonctionnent pas avec la détection de version ou l'analyse connect TCP. Lorsqu'un délai d'analyse est en vigueur, le délai est appliqué entre chaque lot de sondes usurpées, et non entre chaque sonde individuelle. Comme les leurres sont envoyés en lot tout à la fois, ils peuvent temporairement violer les limites de contrôle de la congestion.

Il est à noter que l'utilisation d'un trop grand nombre de leurres peut ralentir votre analyse et potentiellement même la rendre moins précise. De plus, certains FAI filtreront vos paquets usurpés, mais beaucoup ne restreignent pas du tout les paquets IP usurpés.

-S Adresse_IP (Usurper l'adresse source)

Dans certaines circonstances, Nmap peut ne pas être en mesure
le pour déterminer votre adresse source (Nmap vous indiquera si c'est le cas). Dans cette situation, utilisez -S avec l'adresse IP de l'interface par laquelle vous souhaitez envoyer les paquets.

Une autre utilisation possible de ce drapeau est d'usurper l'analyse pour faire croire aux cibles que *quelqu'un d'autre* les analyse. Imaginez une entreprise qui est continuellement analysée par un concurrent ! L'option -e et -Pn sont généralement nécessaires pour ce type d'utilisation. Notez que vous ne recevrez généralement pas de paquets de réponse (ils seront adressés à l'IP que vous usurpez), Nmap ne produira donc pas de rapports utiles.

-e interface (Utiliser l'interface spécifiée)

Indique à Nmap quelle interface utiliser pour envoyer et recevoir des paquets. Nmap devrait être capable de le détecter automatiquement, mais il vous le dira s'il ne le peut pas.

--source-port numéro de port; -g numéro de port (Usurper le numéro de port source)

Une mauvaise configuration étonnamment courante consiste à faire confiance au trafic uniquement en fonction du numéro de port source. Il est facile de comprendre comment cela se produit. Un administrateur met en place un nouveau pare-feu, pour être submergé de plaintes d'utilisateurs ingrats dont les applications ont cessé de fonctionner. En particulier, le DNS peut être cassé car les réponses DNS UDP des serveurs externes ne peuvent plus entrer dans le réseau. Le FTP est un autre exemple courant. Dans les transferts FTP actifs, le serveur distant essaie d'établir une connexion avec le client pour transférer le fichier demandé.

Des solutions sécurisées à ces problèmes existent, souvent sous la forme de proxys au niveau applicatif ou de modules de pare-feu analysant les protocoles. Malheureusement, il existe également des solutions plus faciles et moins sécurisées. Constatant que les réponses DNS proviennent du port 53 et le FTP actif du port 20, de nombreux administrateurs sont tombés dans le piège de simplement autoriser le trafic entrant depuis ces ports. Ils supposent souvent qu'aucun attaquant ne remarquera et n'exploitera de telles brèches dans le pare-feu. Dans d'autres cas, les administrateurs considèrent cela comme une mesure temporaire jusqu'à ce qu'ils puissent mettre en œuvre une solution plus sécurisée. Puis ils oublient la mise à niveau de sécurité.

Les administrateurs réseau surmenés ne sont pas les seuls à tomber dans ce piège. De nombreux produits ont été livrés avec ces règles peu sûres. Même Microsoft s'est rendu coupable. Les filtres IPsec livrés avec Windows 2000 et Windows XP contiennent une règle implicite qui autorise tout trafic TCP ou UDP provenant du port 88 (Kerberos). Dans un autre cas bien connu, les versions du pare-feu personnel Zone Alarm jusqu'à 2.1.25 autorisaient tous les paquets UDP entrants avec le port source 53 (DNS) ou 67 (DHCP).

Nmap propose les options -g et --source-port (elles sont équivalentes) pour exploiter ces faiblesses. Fournissez simplement un numéro de port et Nmap enverra des paquets depuis ce port lorsque cela est possible. La plupart des opérations de scan utilisant des sockets bruts, y compris les scans SYN et UDP, prennent entièrement en charge l'option. L'option n'a notamment aucun effet sur les opérations utilisant les sockets normaux du système d'exploitation, y compris les requêtes DNS, le scan de connexion TCP, la détection de version et le scan par script. La définition du port source n'affecte pas non plus la détection de système d'exploitation, car Nmap doit utiliser des numéros de port différents pour que certains tests de détection de système d'exploitation fonctionnent correctement.

--data chaîne hexadécimale (Ajouter des données binaires personnalisées aux paquets envoyés)

Cette option vous permet d'inclure des données binaires en tant que charge utile dans les paquets envoyés. chaîne hexadécimale peut être spécifiée dans l'un des formats suivants : 0xAABBCCDDEEFF..., AABBCCDDEEFF... ou \xAA\xBB\xCC\xDD\xEE\xFF.... Exemples d'utilisation : --data 0xdeadbeef et --data \xCA\xFE\x09. Notez que si vous spécifiez un nombre comme 0x00ff, aucune conversion de l'ordre des octets n'est effectuée. Assurez-vous de spécifier les informations dans l'ordre des octets attendu par le destinataire.

--data-string chaîne (Ajouter une chaîne personnalisée aux paquets envoyés)

Cette option vous permet d'inclure une chaîne de caractères normale en tant que charge utile dans les paquets envoyés. chaîne peut contenir n'importe quelle chaîne. Cependant, notez que certains caractères peuvent dépendre de la locale de votre système et que le destinataire peut ne pas voir les mêmes informations. De plus, assurez-vous d'entourer la chaîne de guillemets doubles et d'échapper tous les caractères spéciaux du shell. Exemples : --data-string "Scan effectué par les Opérations de Sécurité, extension 7192" ou --data-string "Craignez mes compétences de l33t". Gardez à l'esprit que personne ne verra probablement les commentaires laissés par cette option, sauf s'ils surveillent attentivement le réseau avec un sniffer ou des règles IDS personnalisées.

--data-length nombre (Ajouter des données aléatoires aux paquets envoyés)

Normalement, Nmap envoie des paquets minimalistes ne contenant qu'un en-tête. Ses paquets TCP font donc généralement 40 octets et les requêtes echo ICMP seulement 28. Certains ports UDP et protocoles IP reçoivent une charge utile personnalisée par défaut. Cette option indique à Nmap d'ajouter le nombre d'octets aléatoires spécifié à la plupart des paquets qu'il envoie, et de ne pas utiliser de charges utiles spécifiques au protocole. (Utilisez --data-length 0 pour aucune charge utile aléatoire ou spécifique au protocole.) Les paquets de détection de système d'exploitation (-O) ne sont pas affectés car la précision nécessite la cohérence des sondes, mais la plupart des paquets de ping et de portscan prennent en charge cette option. Cela ralentit un peu, mais peut rendre un scan légèrement moins discret.

--ip-options R|S [route]|L [route]|T|U ... ; --ip-options chaîne hexadécimale (Envoyer des paquets avec des options IP spécifiées)

Le protocole IP[12] offre plusieurs options qui peuvent être placées dans les en-têtes de paquets. Contrairement aux options TCP omniprésentes, les options IP sont rarement utilisées en raison de préoccupations pratiques et de sécurité. En fait, de nombreux routeurs Internet bloquent les options les plus dangereuses, comme le routage source. Pourtant, les options peuvent encore être utiles dans certains cas pour déterminer et manipuler la route réseau vers les machines cibles. Par exemple, vous pourriez être en mesure d'utiliser l'option d'enregistrement de route pour déterminer un chemin vers une cible même lorsque les approches traditionnelles de type traceroute échouent. Ou si vos paquets sont bloqués par un certain pare-feu, vous pourriez être en mesure de spécifier une route différente avec les options de routage source strict ou lâche.

La manière la plus puissante de spécifier les options IP est de simplement fournir les valeurs en tant qu'argument à --ip-options. Préfixez chaque nombre hexadécimal par \x puis les deux chiffres. Vous pouvez répéter certains caractères en les faisant suivre d'un astérisque, puis du nombre de fois où vous souhaitez qu'ils se répètent. Par exemple, \x01\x07\x04\x00*36\x01 est une chaîne hexadécimale contenant 36 octets NUL.

Nmap offre également un mécanisme de raccourci pour spécifier les options. Donnez simplement les lettres R, T ou U pour demander respectivement les options d'enregistrement de route, d'enregistrement d'horodatage ou les deux combinées. Le routage source lâche ou strict peut être spécifié avec un L ou un S suivi d'un espace, puis d'une liste d'adresses IP séparées par des espaces.

Si vous souhaitez voir les options dans les paquets envoyés et reçus, spécifiez --packet-trace. Pour plus d'informations et d'exemples sur l'utilisation des options IP avec Nmap, consultez https://seclists.org/nmap-dev/2006/q3/52.

--ttl valeur (Définir le champ IP time-to-live)

Définit le champ IPv4 time-to-live des paquets envoyés à la valeur donnée.

--randomize-hosts (Randomiser l'ordre des hôtes cibles)

Indique à Nmap de mélanger chaque groupe de 16384 hôtes au maximum avant de les analyser. Cela peut rendre les analyses moins évidentes pour divers systèmes de surveillance réseau, surtout lorsque vous les combinez avec des options de temporisation lentes. Si vous souhaitez randomiser sur des groupes plus importants, augmentez PING_GROUP_SZ dans nmap.h et recompilez. Une solution alternative consiste à générer la liste des adresses IP cibles avec un scan de liste (-sL -n -oN nom de fichier), à la randomiser avec un script Perl, puis à fournir la liste entière à Nmap avec -iL.

--spoof-mac adresse MAC, préfixe ou nom de vendeur (Usurper l'adresse MAC)

Demande à Nmap d'utiliser l'adresse MAC donnée

pour toutes les trames Ethernet brutes qu'il envoie. Cette option implique --send-eth pour s'assurer que Nmap envoie réellement des paquets au niveau Ethernet. La MAC donnée peut prendre plusieurs formats. Si c'est simplement le nombre 0, Nmap choisit une adresse MAC complètement aléatoire pour la session. Si la chaîne donnée est un nombre pair de chiffres hexadécimaux (les paires étant éventuellement séparées par un deux-points), Nmap utilisera ceux-ci comme MAC. Si moins de 12 chiffres hexadécimaux sont fournis, Nmap remplit les six octets restants avec des valeurs aléatoires. Si l'argument n'est ni zéro ni une chaîne hexadécimale, Nmap parcourt nmap-mac-prefixes pour trouver un nom de vendeur contenant la chaîne donnée (il est insensible à la casse). Si une correspondance est trouvée, Nmap utilise l'OUI du vendeur (préfixe de trois octets) et remplit les trois octets restants de manière aléatoire. Les exemples valides d'arguments pour --spoof-mac sont Apple, 0, 01:02:03:04:05:06, deadbeefcafe, 0020F2 et Cisco. Cette option n'affecte que les analyses de paquets bruts comme le scan SYN ou la détection de système d'exploitation, pas les fonctionnalités orientées connexion comme la détection de version ou le moteur de script Nmap.

--proxies Liste d'URL de proxys séparées par des virgules (Relayer les connexions TCP via une chaîne de proxys)

Demande à Nmap d'établir des connexions TCP avec une cible finale via une chaîne fournie d'un ou plusieurs proxys HTTP ou SOCKS4. Les proxys peuvent aider à masquer la véritable source d'une analyse ou à contourner certaines restrictions de pare-feu, mais ils peuvent nuire aux performances de l'analyse en augmentant la latence. Les utilisateurs peuvent avoir besoin d'ajuster les délais d'attente de Nmap et d'autres paramètres d'analyse en conséquence. En particulier, un --max-parallelism plus faible peut aider car certains proxys refusent de gérer autant de connexions simultanées que Nmap ouvre par défaut.

Cette option prend une liste de proxys comme argument, exprimée sous forme d'URL au format proto://hôte:port. Utilisez des virgules pour séparer les URL des nœuds dans une chaîne. Aucune authentification n'est encore prise en charge. Les protocoles valides sont HTTP et SOCKS4.

Attention : cette fonctionnalité est encore en développement et présente des limitations. Elle est implémentée dans la bibliothèque nsock et n'a donc aucun effet sur les phases de ping, d'analyse de ports et de découverte de système d'exploitation d'un scan. Seuls NSE et la détection de version bénéficient de cette option jusqu'à présent ; d'autres fonctionnalités peuvent révéler votre véritable adresse. Les connexions SSL ne sont pas encore prises en charge, ni la résolution DNS côté proxy (les noms d'hôte sont toujours résolus par Nmap).

--badsum (Envoyer des paquets avec des sommes de contrôle TCP/UDP erronées)

Demande à Nmap d'utiliser une somme de contrôle TCP, UDP ou SCTP invalide pour les paquets envoyés aux hôtes cibles. Comme pratiquement toutes les piles IP des hôtes abandonnent correctement ces paquets, les réponses reçues proviennent probablement d'un pare-feu ou d'un IDS qui n'a pas pris la peine de vérifier la somme de contrôle. Pour plus de détails sur cette technique, consultez https://nmap.org/p60-12.html

--adler32 (Utiliser Adler32 obsolète au lieu de CRC32C pour les sommes de contrôle SCTP)

Demande à Nmap d'utiliser l'algorithme Adler32 obsolète pour calculer la somme de contrôle SCTP. Si --adler32 n'est pas donné, CRC-32C (Castagnoli) est utilisé. RFC 2960[13] définissait à l'origine Adler32 comme algorithme de somme de contrôle pour SCTP ; RFC 4960[6] a plus tard redéfini

SORTIE

Tout outil de sécurité n'est utile que par la sortie qu'il génère. Des tests et algorithmes complexes ont peu de valeur s'ils ne sont pas présentés de manière organisée et compréhensible. Compte tenu du nombre de façons dont Nmap est utilisé par les personnes et d'autres logiciels, aucun format unique ne peut satisfaire tout le monde. Nmap offre donc plusieurs formats, dont le mode interactif lisible directement par les humains et le format XML pour une analyse facile par les logiciels.

En plus d'offrir différents formats de sortie, Nmap fournit des options pour contrôler la verbosité de la sortie ainsi que les messages de débogage. Les types de sortie peuvent être envoyés à la sortie standard ou à des fichiers nommés, auxquels Nmap peut ajouter du contenu ou qu'il peut écraser. Les fichiers de sortie peuvent également être utilisés pour reprendre des analyses interrompues.

Nmap rend la sortie disponible en cinq formats différents. Le format par défaut est appelé sortie interactive, et elle est envoyée à la sortie standard (stdout). Il existe également une sortie normale, similaire à l'interactif sauf qu'elle affiche moins d'informations d'exécution et d'avertissements car elle est censée être analysée après la fin de l'analyse plutôt qu'interactivement.

La sortie XML est l'un des types de sortie les plus importants, car elle peut être convertie en HTML, facilement analysée par des programmes tels que les interfaces graphiques de Nmap, ou importée dans des bases de données.

Les deux types de sortie restants sont la sortie simple grepable qui inclut la plupart des informations d'un hôte cible sur une seule ligne, et la sortie sCRiPt KiDDi3 0utPUt pour les utilisateurs qui se considèrent comme des |<-r4d.

Alors que la sortie interactive est le format par défaut et n'a pas d'options de ligne de commande associées, les quatre autres options de format utilisent la même syntaxe. Elles prennent un argument, qui est le nom du fichier dans lequel les résultats doivent être stockés. Plusieurs formats peuvent être spécifiés, mais chaque format ne peut être spécifié qu'une seule fois. Par exemple, vous pourriez souhaiter enregistrer la sortie normale pour votre propre revue tout en enregistrant la sortie XML de la même analyse pour une analyse programmatique. Vous pourriez le faire avec les options -oX myscan.xml -oN myscan.nmap. Bien que ce chapitre utilise des noms simples comme myscan.xml par souci de brièveté, des noms plus descriptifs sont généralement recommandés. Les noms choisis relèvent de la préférence personnelle, bien que j'utilise des noms longs qui intègrent la date de l'analyse et un mot ou deux décrivant l'analyse, placés dans un répertoire portant le nom de l'entreprise que j'analyse.

Bien que ces options enregistrent les résultats dans des fichiers, Nmap affiche toujours la sortie interactive sur stdout comme d'habitude. Par exemple, la commande nmap -oX myscan.xml cible écrit du XML dans myscan.xml et remplit la sortie standard avec les mêmes résultats interactifs qu'elle aurait affichés si -oX n'avait pas été spécifié du tout. Vous pouvez changer cela en passant un caractère tiret comme argument à l'un des types de format. Cela amène Nmap à désactiver la sortie interactive et à afficher les résultats dans le format que vous avez spécifié sur le flux de sortie standard. Ainsi, la commande nmap -oX - cible n'enverra que la sortie XML à stdout. Les erreurs graves peuvent encore être affichées sur le flux d'erreurs normal, stderr.

Contrairement à certains arguments Nmap, l'espace entre le drapeau de l'option de fichier journal (comme -oX) et le nom de fichier ou le tiret est obligatoire. Si vous omettez les drapeaux et donnez des arguments tels que -oG- ou -oXscan.xml, une fonctionnalité de compatibilité ascendante de Nmap provoquera la création de fichiers de sortie au format normal nommés respectivement G- et Xscan.xml.

Tous ces arguments prennent en charge les conversions de type strftime dans le nom du fichier. %H, %M, %S, %m, %d, %y et %Y sont exactement les mêmes qu'en strftime. %T est identique à %H%M%S, %R est identique à %H%M, et %D est identique à %m%d%y. Un % suivi de tout autre caractère produit simplement ce caractère (%% donne un symbole de pourcentage). Ainsi, -oX 'scan-%T-%D.xml' utilisera un fichier XML avec un nom de la forme scan-144840-121307.xml.

Nmap propose également des options pour contrôler la verbosité de l'analyse et pour ajouter du contenu aux fichiers de sortie plutôt que de les écraser. Toutes ces options sont décrites ci-dessous.

Formats de sortie Nmap

-oN spéc_fichier (sortie normale)

Demande que la sortie normale soit dirigée vers le fichier donné. Comme discuté ci-dessus, cela diffère légèrement de la sortie interactive.

-oX spéc_fichier (sortie XML)

Demande que la sortie XML soit dirigée vers le fichier donné. Nmap inclut une définition de type de document (DTD) qui permet aux analyseurs XML de valider la sortie XML de Nmap. Bien qu'elle soit principalement destinée à une utilisation programmatique, elle peut également aider les humains à interpréter la sortie XML de Nmap. La DTD définit les éléments légaux du format, et énumère souvent les attributs et les valeurs qu'ils peuvent prendre. La dernière version est toujours disponible à l'adresse https://svn.nmap.org/nmap/docs/nmap.dtd.

Le XML offre un format stable qui est facilement analysable par des logiciels. Des analyseurs XML gratuits sont disponibles pour tous les principaux langages informatiques, y compris C/C++, Perl, Python et Java. Des liaisons ont même été écrites pour la plupart de ces langages afin de gérer spécifiquement la sortie et l'exécution de Nmap. Les exemples sont Nmap::Scanner[14] et Nmap::Parser[15] dans Perl CPAN. Dans presque tous les cas où une application non triviale interagit avec Nmap, le XML est le format préféré.

La sortie XML fait référence à une feuille de style XSL qui peut être utilisée pour formater les résultats en HTML. La manière la plus simple d'utiliser cela est simplement de charger la sortie XML dans un navigateur Web tel que Firefox ou IE. Par défaut, cela ne fonctionnera que sur la machine sur laquelle vous avez exécuté Nmap (ou une machine configurée similairement) en raison du chemin absolu nmap.xsl codé en dur. Utilisez les options --webxml ou --stylesheet pour créer des fichiers XML portables qui s'affichent en HTML sur n'importe quelle machine connectée au Web.

-oS spéc_fichier (ScRipT KIdd|3 oUTpuT)

La sortie Script kiddie est similaire à la sortie interactive, sauf qu'elle est post-traitée pour mieux convenir aux l33t HaXXorZ qui méprisaient auparavant Nmap en raison de sa capitalisation et de son orthographe cohérentes. Les personnes ayant peu d'humour noteront que cette option se moque des script kiddies avant de me flammer pour leur avoir prétendument "aidé".

-oG spéc_fichier (sortie grepable)

Ce format de sortie est couvert en dernier car il est déprécié. Le format de sortie XML est beaucoup plus puissant, et est presque aussi pratique pour les utilisateurs expérimentés. XML est une norme pour laquelle des dizaines d'excellents analyseurs sont disponibles, tandis que la sortie grepable est ma propre astuce simple. XML est extensible pour prendre en charge les nouvelles fonctionnalités de Nmap au fur et à mesure de leur publication, tandis que je dois souvent omettre ces fonctionnalités de la sortie grepable faute de place pour les y mettre.

Néanmoins, la sortie grepable reste très populaire. C'est un format simple qui liste chaque hôte sur une seule ligne et peut être trivialement recherché et analysé avec des outils Unix standard tels que grep, awk, cut, sed, diff et Perl. Même moi, je l'utilise généralement pour des tests ponctuels effectués en ligne de commande. Trouver tous les hôtes avec le port SSH ouvert ou qui exécutent Solaris ne nécessite qu'un simple grep pour identifier les hôtes, dirigé vers une commande awk ou cut pour imprimer les champs souhaités.

La sortie grepable se compose de commentaires (lignes commençant par un dièse (#)) et de lignes cibles. Une ligne cible comprend une combinaison de six champs étiquetés, séparés par des tabulations et suivis d'un deux-points. Les champs sont Hôte, Ports, Protocoles, État Ignoré, OS, Index de Séquence, ID IP et État.

Le plus important de ces champs est généralement Ports, qui donne des détails sur chaque port intéressant. C'est une liste séparée par des virgules d'entrées de port. Chaque entrée de port représente un port intéressant et prend la forme de sept sous-champs séparés par des barres obliques (/). Ces sous-champs sont : Numéro de port, État, Protocole, Propriétaire, Service, Informations SunRPC et Informations de version.

Comme pour la sortie XML, cette page de manuel ne permet pas de documenter l'intégralité du format. Un examen plus détaillé du format de sortie grepable de Nmap est disponible à l'adresse https://nmap.org/book/output-formats-grepable-output.html.

-oA nom_base (Sortie dans tous les formats)

Par commodité, vous pouvez spécifier -oA nom_base pour stocker les résultats de l'analyse dans les formats normal, XML et grepable à la fois. Ils sont stockés respectivement dans nom_base.nmap, nom_base.xml et nom_base.gnmap. Comme avec la plupart des programmes, vous pouvez préfixer les noms de fichiers avec un chemin de répertoire, tel que ~/nmaplogs/foocorp/ sur Unix ou c:\hacking\sco sous Windows.

Options de verbosité et de débogage

-v (Augmenter le niveau de verbosité), -vniveau (Définir le niveau de verbosité)

Augmente le niveau de verbosité, ce qui amène Nmap à afficher plus d'informations sur l'analyse en cours. Les ports ouverts sont affichés au fur et à mesure qu'ils sont trouvés et des estimations du temps d'achèvement sont fournies lorsque Nmap pense qu'une analyse prendra plus de quelques minutes. Utilisez-le deux fois ou plus pour une verbosité encore plus grande : -vv, ou donnez directement un niveau de verbosité, par exemple -v3.

La plupart des changements n'affectent que la sortie interactive, et certains affectent également la sortie normale et script kiddie. Les autres types de sortie sont destinés à être traités par des machines, Nmap peut donc fournir des détails substantiels par défaut dans ces formats sans fatiguer un utilisateur humain. Cependant, il existe quelques changements dans d'autres modes où la taille de la sortie peut être considérablement réduite en omettant certains détails. Par exemple, une ligne de commentaire dans la sortie grepable qui fournit une liste de tous les ports analysés n'est imprimée qu'en mode verbeux car elle peut être assez longue.

-d (Augmenter le niveau de débogage), -dniveau (Définir le niveau de débogage)

Lorsque même le mode verbeux ne fournit pas suffisamment de données pour vous, le débogage est disponible pour vous inonder de beaucoup plus ! Comme avec l'option de verbosité (-v), le débogage est activé avec un drapeau de ligne de commande (-d) et le niveau de débogage peut être augmenté en le spécifiant plusieurs fois, comme dans -dd, ou en définissant directement un niveau. Par exemple, -d9 définit le niveau neuf. C'est le niveau effectif le plus élevé et il produira des milliers de lignes à moins que vous n'exécutiez une analyse très simple avec très peu de ports et de cibles.

La sortie de débogage est utile lorsqu'un bug est suspecté dans Nmap, ou si vous êtes simplement confus quant à ce que fait Nmap et pourquoi. Comme cette fonctionnalité est principalement destinée aux développeurs, les lignes de débogage ne sont pas toujours autonomes. Vous pourriez obtenir quelque chose comme : Timeout vals: srtt: -1 rttvar: -1 to: 1000000 delta 14987 ==> srtt: 14987 rttvar: 14987 to: 100000. Si vous ne comprenez pas une ligne, vos seules solutions sont de l'ignorer, de la rechercher dans le code source, ou de demander de l'aide à la liste de développement (nmap-dev). Certaines lignes sont explicites, mais les messages deviennent plus obscurs à mesure que le niveau de débogage augmente.

--reason (Raisons de l'état des hôtes et des ports)

Montre t

la raison pour laquelle chaque port est défini sur un état spécifique et la raison pour laquelle chaque hôte est actif ou inactif. Cette option affiche le type de paquet qui a déterminé l'état d'un port ou d'un hôte. Par exemple, un paquet RST d'un port fermé ou une réponse d'écho d'un hôte actif. Les informations que Nmap peut fournir sont déterminées par le type d'analyse ou de ping. L'analyse SYN et le ping SYN (-sS et -PS) sont très détaillés, mais l'analyse de connexion TCP (-sT) est limitée par l'implémentation de l'appel système connect. Cette fonctionnalité est automatiquement activée par l'option de débogage (-d) et les résultats sont stockés dans des fichiers journaux XML même si cette option n'est pas spécifiée.

--stats-every time (Afficher les statistiques de temps périodiques)

Affiche périodiquement un message d'état de temps après chaque intervalle de time. Le temps est une spécification du genre décrit dans la section intitulée « TIMING AND PERFORMANCE » ; ainsi, par exemple, utilisez --stats-every 10s pour obtenir une mise à jour de l'état toutes les 10 secondes. Les mises à jour sont imprimées sur la sortie interactive (l'écran) et sur la sortie XML.

--packet-trace (Tracer les paquets et les données envoyés et reçus)

Demande à Nmap d'imprimer un résumé de chaque paquet envoyé ou reçu. Ceci est souvent utilisé pour le débogage, mais c'est aussi un moyen précieux pour les nouveaux utilisateurs de comprendre exactement ce que Nmap fait en coulisses. Pour éviter d'imprimer des milliers de lignes, vous pourriez vouloir spécifier un nombre limité de ports à analyser, tel que -p20-30. Si vous ne vous souciez que du fonctionnement du sous-système de détection de version, utilisez plutôt --version-trace. Si vous ne vous souciez que du traçage des scripts, spécifiez --script-trace. Avec --packet-trace, vous obtenez tout ce qui précède.

--open (Afficher uniquement les ports ouverts (ou potentiellement ouverts))

Parfois, vous ne vous souciez que des ports auxquels vous pouvez réellement vous connecter (ceux qui sont ouverts) et vous ne voulez pas que les résultats soient encombrés par des ports fermés, filtrés et fermés|filtrés. La personnalisation de la sortie se fait normalement après l'analyse à l'aide d'outils tels que grep, awk et Perl, mais cette fonctionnalité a été ajoutée suite à des demandes répétées. Spécifiez --open pour n'afficher que les hôtes avec au moins un port ouvert, ouvert|filtré ou non filtré, et pour n'afficher que les ports dans ces états. Ces trois états sont traités comme ils le seraient normalement, ce qui signifie que ouvert|filtré et non filtré peuvent être condensés en comptes s'il y en a un nombre excessif.

À partir de Nmap 7.40, l'option --open implique

--defeat-rst-ratelimit, car cette option n'affecte que les ports fermés et filtrés, qui sont masqués par --open.

--iflist (Lister les interfaces et les routes)

Affiche la liste des interfaces et les routes système telles que détectées par Nmap et quitte. Ceci est utile pour déboguer des problèmes de routage ou une mauvaise caractérisation des périphériques (comme Nmap traitant une connexion PPP comme une connexion ethernet).

Options de sortie diverses

--append-output (Ajouter aux fichiers de sortie au lieu de les écraser)

Lorsque vous spécifiez un nom de fichier pour un indicateur de format de sortie tel que -oX ou -oN, ce fichier est écrasé par défaut. Si vous préférez conserver le contenu existant du fichier et ajouter les nouveaux résultats, spécifiez l'option --append-output. Tous les noms de fichiers de sortie spécifiés dans cette exécution Nmap seront alors ajoutés au lieu d'être écrasés. Cela ne fonctionne pas bien pour les données d'analyse XML (-oX) car le fichier résultant ne sera généralement pas correctement analysable tant que vous ne l'aurez pas corrigé manuellement.

--resume filename (Reprendre une analyse interrompue)

Certaines exécutions étendues de Nmap prennent très longtemps, de l'ordre de plusieurs jours. Ces analyses ne se terminent pas toujours. Des restrictions peuvent empêcher Nmap d'être exécuté pendant les heures de travail, le réseau peut tomber, la machine sur laquelle Nmap est exécuté peut subir un redémarrage planifié ou non, ou Nmap lui-même peut planter. L'administrateur exécutant Nmap peut l'annuler pour toute autre raison, en appuyant sur ctrl-C. Redémarrer toute l'analyse depuis le début peut être indésirable. Heureusement, si les fichiers de sortie de l'analyse ont été conservés, l'utilisateur peut demander à Nmap de reprendre l'analyse avec la cible sur laquelle il travaillait lorsque l'exécution a cessé. Il suffit de spécifier l'option --resume et de passer le fichier de sortie comme argument. Aucun autre argument n'est permis, car Nmap analyse le fichier de sortie pour utiliser les mêmes que ceux spécifiés précédemment. Appelez simplement Nmap avec nmap --resume nomdufichierlog. Nmap ajoutera les nouveaux résultats aux fichiers de données spécifiés lors de l'exécution précédente. Les analyses peuvent être reprises à partir de l'un des 3 principaux formats de sortie : Normal, Grepable ou XML.

--noninteractive (Désactiver les interactions à l'exécution)

Parfois, par exemple lors de l'exécution de Nmap en tâche de fond dans un shell, il peut être indésirable que Nmap surveille et réponde aux entrées du clavier de l'utilisateur lorsqu'il s'exécute. (Voir la section intitulée « INTERACTION À L'EXÉCUTION » sur la manière de contrôler Nmap pendant une analyse.) Utilisez l'option --noninteractive pour empêcher Nmap de prendre le contrôle du terminal.

--stylesheet chemin ou URL (Définir la feuille de style XSL pour transformer la sortie XML)

Nmap est fourni avec une feuille de style XSL nommée nmap.xsl pour visualiser ou traduire la sortie XML en HTML. La sortie XML inclut une directive xml-stylesheet qui pointe vers nmap.xml là où elle a été initialement installée par Nmap. Exécutez le fichier XML à travers un processeur XSLT tel que xsltproc[16] pour produire un fichier HTML. Ouvrir directement le fichier XML dans un navigateur ne fonctionne plus bien car les navigateurs modernes limitent les emplacements à partir desquels une feuille de style peut être chargée. Si vous souhaitez utiliser une autre feuille de style, spécifiez-la comme argument de --stylesheet. Vous devez fournir le chemin d'accès complet ou l'URL. Une invocation courante est --stylesheet https://nmap.org/svn/docs/nmap.xsl. Cela indique à un processeur XSLT de charger la dernière version de la feuille de style à partir de Nmap.Org. L'option --webxml fait la même chose avec moins de frappes et de mémorisation. Charger la feuille de style XSL depuis Nmap.Org facilite la visualisation des résultats sur une machine qui n'a pas Nmap (et donc nmap.xsl) installé. L'URL est donc souvent plus utile, mais l'emplacement local du système de fichiers de nmap.xsl est utilisé par défaut pour des raisons de confidentialité.

--webxml (Charger la feuille de style depuis Nmap.Org)

Ceci est une option de commodité, rien de plus qu'un alias pour --stylesheet https://nmap.org/svn/docs/nmap.xsl.

--no-stylesheet (Omettre la déclaration de feuille de style XSL depuis XML)

Spécifiez cette option pour empêcher Nmap d'associer une feuille de style XSL à sa sortie XML. La directive xml-stylesheet est omise.

OPTIONS DIVERSES

Cette section décrit quelques options importantes (et moins importantes) qui ne correspondent pas vraiment ailleurs.

-6 (Activer l'analyse IPv6)

Nmap prend en charge IPv6 pour ses fonctionnalités les plus populaires. L'analyse par ping, l'analyse de ports, la détection de versions et le Nmap Scripting Engine prennent tous en charge IPv6. La syntaxe de la commande est la même que d'habitude, à l'exception de l'ajout de l'option -6. Bien entendu, vous devez utiliser la syntaxe IPv6 si vous spécifiez une adresse plutôt qu'un nom d'hôte. Une adresse peut ressembler à 3ffe:7501:4819:2000:210:f3ff:fe03:14d0, donc les noms d'hôte sont recommandés. La sortie ressemble à d'habitude, l'adresse IPv6 sur la ligne « ports intéressants » étant le seul indice IPv6.

Bien que l'IPv6 n'ait pas vraiment conquis le monde, il est largement utilisé dans certains pays (généralement asiatiques) et la plupart des systèmes d'exploitation modernes le prennent en charge. Pour utiliser Nmap avec IPv6, la source et la cible de votre analyse doivent être configurées pour IPv6. Si votre fournisseur d'accès à Internet (comme la plupart d'entre eux) ne vous alloue pas d'adresses IPv6, des brokers de tunnel gratuits sont largement disponibles et fonctionnent bien avec Nmap. J'utilise le service gratuit de broker de tunnel IPv6 à http://www.tunnelbroker.net. D'autres brokers de tunnel sont listés sur Wikipedia[17]. Les tunnels 6to4 sont une autre approche gratuite et populaire.

Sur Windows, les analyses IPv6 par sockets bruts ne sont prises en charge que sur les périphériques Ethernet (pas les tunnels), et uniquement sur Windows Vista et versions ultérieures. Utilisez l'option --unprivileged dans d'autres situations.

-A (Options d'analyse agressive)

Cette option active des options avancées et agressives supplémentaires. Actuellement, cela active la détection du système d'exploitation (-O), l'analyse des versions (-sV), l'analyse des scripts (-sC) et traceroute (--traceroute). D'autres fonctionnalités pourront être ajoutées à l'avenir. Le but est d'activer un ensemble complet d'options d'analyse sans que les utilisateurs aient à se souvenir d'un grand nombre d'indicateurs. Cependant, étant donné que l'analyse des scripts avec l'ensemble par défaut est considérée comme intrusive, vous ne devriez pas utiliser -A sur des réseaux cibles sans permission. Cette option active uniquement les fonctionnalités, et non les options de temporisation (telles que -T4) ou les options de verbosité (-v) que vous pourriez également souhaiter. Les options qui nécessitent des privilèges (par exemple, un accès root) tels que la détection du système d'exploitation et traceroute ne seront activées que si ces privilèges sont disponibles.

--datadir nomduchemin (Spécifier l'emplacement personnalisé des fichiers de données Nmap)

Nmap obtient des données spéciales à l'exécution dans des fichiers nommés nmap-service-probes, nmap-services, nmap-protocols, nmap-rpc, nmap-mac-prefixes et nmap-os-db. Si l'emplacement de l'un de ces fichiers a été spécifié (en utilisant les options --servicedb ou --versiondb), cet emplacement est utilisé pour ce fichier. Après cela, Nmap recherche ces fichiers dans le répertoire spécifié avec l'option --datadir (le cas échéant). Les fichiers qui n'y sont pas trouvés sont recherchés dans le répertoire spécifié par la variable d'environnement NMAPDIR. Vient ensuite ~/.nmap pour les UID réels et effectifs ; ou sur Windows, HOME\AppData\Roaming\nmap (où HOME est le répertoire personnel de l'utilisateur, comme C:\Users\utilisateur). Ceci est suivi par l'emplacement de l'exécutable nmap et le même emplacement avec ../share/nmap ajouté. Puis un emplacement intégré tel que /usr/local/share/nmap ou /usr/share/nmap.

--servicedb fichier_services (Spécifier le fichier personnalisé des services)

Demande à Nmap d'utiliser le fichier de services spécifié au lieu du fichier de données nmap-services fourni avec Nmap. L'utilisation de cette option déclenche également une analyse rapide (-F). Voir la description de --datadir pour plus d'informations sur les fichiers de données de Nmap.

--versiondb fichier_sondes_service (Spécifier le fichier personnalisé des sondes de service)

Demande à Nmap d'utiliser le fichier de sondes de service spécifié au lieu du fichier de données nmap-service-probes fourni avec Nmap. Voir la description de --datadir pour plus d'informations sur les fichiers de données de Nmap.

--send-eth (Utiliser l'envoi brut Ethernet)

Demande à Nmap d'envoyer des paquets au niveau de la couche Ethernet brute (liaison de données) plutôt qu'au niveau IP supérieur (réseau). Par défaut, Nmap choisit celui qui est généralement le meilleur pour la plateforme sur laquelle il s'exécute. Les sockets bruts (couche IP) sont généralement les plus efficaces pour les machines Unix, tandis que les trames ethernet
mes sont requis pour le fonctionnement sous Windows, car Microsoft a désactivé la prise en charge des sockets bruts. Nmap utilise toujours des paquets IP bruts sous Unix malgré cette option lorsqu'il n'y a pas d'autre choix (par exemple, les connexions non Ethernet).

--send-ip (Envoyer au niveau IP brut)

Demande à Nmap d'envoyer des paquets via des sockets IP bruts plutôt que d'envoyer des trames Ethernet de niveau inférieur. C'est le complément de l'option --send-eth discutée précédemment.

--privileged (Supposer que l'utilisateur est pleinement privilégié)

Indique à Nmap de supposer simplement qu'il dispose des privilèges suffisants pour envoyer des paquets via des sockets bruts, renifler des paquets et effectuer des opérations similaires qui nécessitent généralement des privilèges root sur les systèmes Unix. Par défaut, Nmap s'arrête si de telles opérations sont demandées mais que geteuid n'est pas zéro. --privileged est utile avec les capacités du noyau Linux et les systèmes similaires qui peuvent être configurés pour permettre aux utilisateurs non privilégiés d'effectuer des analyses de paquets bruts. Assurez-vous de fournir cet indicateur d'option avant tout indicateur pour les options qui nécessitent des privilèges (analyse SYN, détection d'OS, etc.). La variable d'environnement NMAP_PRIVILEGED peut être définie comme une alternative équivalente à --privileged.

--unprivileged (Supposer que l'utilisateur manque de privilèges de socket brut)

Cette option est l'opposé de --privileged. Elle indique à Nmap de traiter l'utilisateur comme n'ayant pas les privilèges de socket réseau brut et de reniflage. Ceci est utile pour les tests, le débogage ou lorsque la fonctionnalité réseau brute de votre système d'exploitation est défaillante. La variable d'environnement NMAP_UNPRIVILEGED peut être définie comme une alternative équivalente à --unprivileged.

--release-memory (Libérer la mémoire avant de quitter)

Cette option n'est utile que pour le débogage des fuites de mémoire. Elle amène Nmap à libérer la mémoire allouée juste avant de quitter, de sorte que les fuites de mémoire réelles soient plus faciles à repérer. Normalement, Nmap saute cela car le système d'exploitation le fait de toute façon lors de la terminaison du processus.

-V; --version (Afficher le numéro de version)

Affiche le numéro de version de Nmap et quitte.

-h; --help (Afficher la page de résumé d'aide)

Affiche un court écran d'aide avec les indicateurs de commande les plus courants. Lancer Nmap sans aucun argument fait de même.

EXEMPLES

Voici quelques exemples d'utilisation de Nmap, allant du simple et courant au plus complexe et ésotérique. Des adresses IP et des noms de domaine réels sont utilisés pour rendre les choses plus concrètes. À leur place, vous devriez substituer les adresses/noms de votre propre réseau. Bien que je ne pense pas que la numérisation de ports sur d'autres réseaux soit ou devrait être illégale, certains administrateurs réseau n'apprécient pas la numérisation non sollicitée de leurs réseaux et peuvent se plaindre. Obtenir la permission au préalable est la meilleure approche.

À des fins de test, vous avez la permission de scanner l'hôte scanme.nmap.org. Cette permission inclut uniquement la numérisation via Nmap et non le test d'exploits ou d'attaques par déni de service. Pour économiser de la bande passante, veuillez ne pas initier plus d'une douzaine de numérisations contre cet hôte par jour. Si ce service de cible de numérisation gratuite est utilisé abusivement, il sera désactivé et Nmap affichera "Échec de la résolution du nom d'hôte/IP donné : scanme.nmap.org". Ces permissions s'appliquent également aux hôtes scanme2.nmap.org, scanme3.nmap.org, et ainsi de suite, bien que ces hôtes n'existent pas actuellement.

nmap -v scanme.nmap.org

Cette option analyse tous les ports TCP réservés sur la machine scanme.nmap.org. L'option -v active le mode verbeux.

nmap -sS -O scanme.nmap.org/24

Lance une analyse SYN furtive sur chaque machine active parmi les 256 adresses IP du réseau de taille /24 où réside Scanme. Il tente également de déterminer quel système d'exploitation est en cours d'exécution sur chaque hôte actif. Cela nécessite des privilèges root en raison de l'analyse SYN et de la détection d'OS.

nmap -sV -p 22,53,110,143,4564 198.116.0-255.1-127

Lance une énumération d'hôtes et une analyse TCP sur la première moitié de chacun des 255 sous-réseaux possibles à 8 bits dans l'espace d'adresses 198.116.0.0/16. Cela vérifie si les systèmes exécutent SSH, DNS, POP3 ou IMAP sur leurs ports standard, ou quoi que ce soit sur le port 4564. Pour l'un de ces ports trouvés ouverts, la détection de version est utilisée pour déterminer quelle application est en cours d'exécution.

nmap -v -iR 100000 -Pn -p 80

Demande à Nmap de choisir 100 000 hôtes au hasard et de les analyser pour les serveurs web (port 80). L'énumération d'hôtes est désactivée avec -Pn car l'envoi préalable de quelques sondes pour déterminer si un hôte est actif est inutile lorsque vous n'interrogez qu'un seul port sur chaque hôte cible de toute façon.

nmap -Pn -p80 -oX logs/pb-port80scan.xml -oG logs/pb-port80scan.gnmap 216.163.128.20/20

Ceci analyse 4096 adresses IP pour trouver des serveurs web (sans les pinger) et enregistre la sortie dans des formats grepable et XML.

LIVRE NMAP

Alors que ce guide de référence détaille toutes les options matérielles de Nmap, il ne peut pas démontrer pleinement comment appliquer ces fonctionnalités pour résoudre rapidement des tâches du monde réel. Pour cela, nous avons publié Nmap Network Scanning : The Official Nmap Project Guide to Network Discovery and Security Scanning. Les sujets incluent la subversion des pare-feu et des systèmes de détection d'intrusion, l'optimisation des performances de Nmap et l'automatisation des tâches réseau courantes avec le Nmap Scripting Engine. Des astuces et des instructions sont fournies pour les tâches Nmap courantes telles que l'inventaire réseau, les tests d'intrusion, la détection des points d'accès sans fil non autorisés et l'éradication des épidémies de vers réseau. Des exemples et des diagrammes montrent la communication réelle sur le réseau. Plus de la moitié du livre est disponible gratuitement en ligne. Voir https://nmap.org/book pour plus d'informations.

BOGUES

Comme son auteur, Nmap n'est pas parfait. Mais vous pouvez aider à l'améliorer en envoyant des rapports de bogues ou même en écrivant des correctifs. Si Nmap ne se comporte pas comme prévu, mettez d'abord à jour vers la dernière version disponible sur https://nmap.org. Si le problème persiste, faites quelques recherches pour déterminer s'il a déjà été découvert et résolu. Essayez de rechercher le problème ou le message d'erreur sur Google, car cela agrège de nombreux forums. Si rien n'en ressort, créez un ticket sur notre suivi (http://issues.nmap.org) et/ou envoyez un rapport de bogue à <dev@nmap.org>. Si vous vous abonnez à la liste nmap-dev avant de poster, votre message passera la modération et sera traité plus rapidement. Abonnez-vous à https://nmap.org/mailman/listinfo/dev. Veuillez inclure tout ce que vous avez appris sur le problème, ainsi que la version de Nmap que vous utilisez et la version du système d'exploitation sur lequel il s'exécute. D'autres suggestions pour améliorer Nmap peuvent également être envoyées à la liste de développement Nmap.

Si vous êtes capable d'écrire un correctif améliorant Nmap ou corrigeant un bogue, c'est encore mieux ! Les instructions pour soumettre des correctifs ou des demandes de traction git sont disponibles sur https://github.com/nmap/nmap/blob/master/CONTRIBUTING.md

Les problèmes particulièrement sensibles tels que les rapports de sécurité peuvent être envoyés directement à l'auteur de Nmap, Fyodor, à l'adresse <fyodor@nmap.org>. Tous les autres rapports et commentaires doivent utiliser la liste de développement ou le suivi des problèmes à la place, car plus de personnes les lisent, les suivent et y répondent.
