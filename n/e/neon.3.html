NEON(3) Référence de l'API neon NEON(3)

NOM

neon - bibliothèque client HTTP et WebDAV

DESCRIPTION

neon est une bibliothèque client HTTP et WebDAV. Les abstractions majeures exposées sont la session HTTP, créée par ne_session_create ; et la requête HTTP, créée par ne_request_create. L'authentification HTTP est gérée de manière transparente pour les serveurs et les proxys, voir ne_set_server_auth ; un support SSL/TLS complet est également inclus, voir ne_ssl_set_verify.

CONVENTIONS

Certaines conventions sont utilisées dans toute l'API neon, pour fournir une interface cohérente et simple ; celles-ci sont documentées ci- dessous.

Thread-safeness et initialisation globale

neon est lui-même implémenté pour être thread-safe (évitant toute utilisation d'état global), mais repose sur le système d'exploitation pour fournir une interface de résolution thread-safe. Les systèmes d'exploitation modernes proposent l'interface thread-safe getaddrinfo, que neon supporte ; d'autres implémentent gethostbyname en utilisant le stockage local aux threads.

Pour permettre une utilisation thread-safe de SSL dans les bibliothèques OpenSSL et GnuTLS, neon doit être configuré avec --enable-threadsafe-ssl ; si cela est fait, des callbacks de verrouillage seront enregistrés par ne_sock_init ; notez qu'il faut être prudent si neon est utilisé conjointement avec une autre bibliothèque qui utilise OpenSSL ou GnuTLS.

Certaines plateformes et bibliothèques utilisées par neon nécessitent une initialisation globale avant utilisation ; notamment :

•La disposition du signal SIGPIPE doit être définie sur ignoré ou gérée autrement pour éviter la terminaison du processus lors de l'écriture sur un socket qui a été fermé par le pair.
•OpenSSL et GnuTLS nécessitent une initialisation globale pour charger les tables de recherche partagées.
•La bibliothèque de sockets Win32 nécessite une initialisation avant utilisation.

La fonction ne_sock_init doit être appelée avant toute autre utilisation de neon pour effectuer toute initialisation nécessaire à la plateforme particulière. Les applications souhaitant effectuer toutes les étapes d'initialisation globales nécessaires au processus elles-mêmes peuvent omettre d'appeler ne_sock_init (et ne_sock_exit) ; neon ne vérifie ni si ces fonctions sont appelées ni ne les appelle lui-même.

Pour certaines applications et configurations, il peut être nécessaire d'appeler ne_i18n_init pour initialiser le support de l'internationalisation dans neon.

Asynchronous signal safety

Aucune fonction dans neon n'est définie comme étant “async-signal safe” - c'est-à-dire, aucune fonction n'est sûre à appeler depuis un gestionnaire de signal. Tout appel à la bibliothèque neon depuis un gestionnaire de signal aura un comportement indéfini - en d'autres termes, cela peut planter le processus.

Fonctions utilisant l'état global

Toute fonction dans neon peut modifier la variable globale errno en effet secondaire. Sauf indication contraire explicite, la valeur d'errno est non spécifiée après tout appel de fonction neon.

En dehors de l'utilisation d'errno, les seules fonctions qui utilisent ou modifient l'état global du processus dans neon sont les suivantes :

•ne_sock_init, ne_i18n_init, et ne_sock_exit, comme décrit ci-dessus
•ne_debug_init et ne_debug, si activés à la compilation ; pour la sortie de débogage
•ne_oom_callback pour installer une fonction globale du processus à appeler en cas d'échec de malloc

Espaces de noms

Pour éviter d'éventuelles collisions entre les noms utilisés pour les symboles et les macros préprocesseur par une application et les bibliothèques qu'elle utilise, il est de bonne pratique pour chaque bibliothèque de réserver un préfixe d'espace de noms particulier. Une application qui s'assure de ne pas utiliser de noms avec ces préfixes est alors garantie d'éviter de telles collisions.

La bibliothèque neon réserve l'utilisation des préfixes d'espace de noms ne_ et NE_. Les bibliothèques utilisées par neon peuvent également réserver certains espaces de noms ; les collisions entre ces bibliothèques et une application basée sur neon ne seront pas détectées à la compilation, car les interfaces de bibliothèque sous-jacentes ne sont pas exposées via les fichiers d'en-tête de neon. De telles collisions ne peuvent être détectées qu'au moment de l'édition des liens, lorsque l'éditeur de liens tente de résoudre les symboles. La liste suivante documente certains des espaces de noms revendiqués par les bibliothèques utilisées par neon ; cette liste peut être incomplète.

SSL, ssl, TLS, tls, ERR_, BIO_, d2i_, i2d_, ASN1_

Certains des nombreux préfixes utilisés par la bibliothèque OpenSSL ; peu d'efforts ont été faits pour maintenir les symboles exportés dans des préfixes particuliers pour cette bibliothèque.

gnutls_, gcry_, gpg_

Espaces de noms utilisés par la bibliothèque GnuTLS (et ses dépendances).

XML_, Xml[A-Z]

Espaces de noms utilisés par la bibliothèque expat.

xml[A-Z], html[A-Z], docb[A-Z]

Espaces de noms utilisés par la bibliothèque libxml2 ; un nombre relativement faible de symboles sont utilisés sans ces préfixes.

inflate, deflate, crc32, compress, uncompress, adler32, zlib

Espaces de noms utilisés par la bibliothèque zlib ; un nombre relativement faible de symboles sont utilisés sans ces préfixes.

krb5, gss, GSS, asn1, decode_krb5, encode_krb5, profile, mit

Certains des préfixes utilisés par la bibliothèque MIT GSSAPI et ses dépendances ; un certain nombre de symboles se situent en dehors de ces préfixes.

pakchois_

Espace de noms utilisé par la bibliothèque pakchois.

px_

Espace de noms utilisé par la bibliothèque libproxy.

Validation des arguments

neon n'essaie pas de valider que les paramètres passés aux fonctions sont conformes à l'API (par exemple, en vérifiant que les arguments pointeurs ne sont pas NULL). Tout usage de l'API neon qui n'est pas documenté comme produisant un comportement donné est dit produire un comportement indéfini ; il est probable que neon plantera dans ces conditions.

Chemins URI, métadonnées WebDAV

Les chaînes de chemin passées à toute fonction doivent être encodées en URI par l'application ; neon n'effectue jamais d'encodage ou de décodage d'URI en interne. Les noms et valeurs de propriété WebDAV doivent être des chaînes Unicode valides encodées en UTF-8.

Interaction utilisateur

En tant qu'interface de bibliothèque pure, neon ne produira jamais de sortie sur stdout ou stderr ; toute interaction utilisateur est de la responsabilité de l'application.

Gestion de la mémoire

neon n'essaie pas de gérer gracieusement une situation de manque de mémoire ; au lieu de cela, par défaut, la fonction abort est appelée pour terminer immédiatement le processus. Une application peut enregistrer une fonction personnalisée qui sera appelée avant abort dans une telle situation ; voir ne_oom_callback.

Callbacks et userdata

Chaque fois qu'un callback est enregistré, un pointeur userdata est également utilisé pour permettre à l'application d'associer un contexte au callback. Le userdata est de type void *, permettant d'utiliser n'importe quel pointeur.

Support des grands fichiers

Depuis la version 0.27.0, neon utilise de manière transparente les interfaces « LFS transitional » dans les fonctions qui utilisent des descripteurs de fichiers. Cela permet l'utilisation de fichiers de plus de 2 Gio sur les plateformes avec un type off_t natif 32 bits, où le support LFS est disponible.

Certaines interfaces neon utilisent le type ne_off_t, qui est défini comme étant soit off_t, soit off64_t selon que le support LFS est détecté au moment de la construction. neon n'utilise ni ne requiert la définition du macro -D_FILE_OFFSET_BITS=64.
