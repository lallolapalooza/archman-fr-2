NOM

netplan - abstraction de configuration réseau YAML pour divers backends

SYNTAXE

netplan [COMMANDE|help]

COMMANDES

Voir netplan help pour une liste des commandes disponibles sur ce système.

DESCRIPTION

Les installateurs de distribution, l'instanciation cloud, les constructions d'images pour des appareils spécifiques, ou toute autre façon de déployer un système d'exploitation placent la configuration réseau souhaitée dans un ou plusieurs fichiers de configuration YAML. Pendant le démarrage précoce, le « network renderer » de Netplan s'exécute, lit les fichiers /{lib,etc,run}/netplan/*.yaml et écrit la configuration dans /run pour déléguer le contrôle des périphériques au démon réseau spécifié.

•
Les périphériques configurés sont gérés par systemd-networkd par défaut, sauf s'ils sont explicitement marqués comme gérés par un renderer spécifique (NetworkManager).
•
Les périphériques non couverts par la configuration réseau ne sont pas du tout touchés.
•
Utilisable dans l'initramfs (peu de dépendances et rapide)
•
Pas de configuration générée persistante, seulement la configuration YAML originale
•
Le parseur prend en charge plusieurs fichiers de configuration pour permettre à des applications comme libvirt ou lxd d'inclure la configuration réseau attendue (virbr0, lxdbr0), ou de changer la politique par défaut globale pour utiliser NetworkManager pour tout.
•
Conserve la flexibilité pour changer les backends/la politique plus tard ou s'adapter à la suppression de NetworkManager, car la configuration générée est éphémère.

Structure générale

Les fichiers de configuration Netplan utilisent le format YAML. Tous les fichiers /{lib,etc,run}/netplan/*.yaml sont pris en compte. Les fichiers lexicographiquement ultérieurs (quelle que soit leur répertoire) modifient (nouvelles clés de mappage) ou remplacent (mêmes clés de mappage) les précédents. Un fichier dans /run/netplan masque complètement un fichier du même nom dans /etc/netplan, et un fichier dans l'un de ces répertoires masque un fichier du même nom dans /lib/netplan.

Le nœud de plus haut niveau dans un fichier de configuration Netplan est un mappage network: qui contient version: 2 (le YAML actuellement utilisé par curtin, MAAS, etc. est la version 1), puis des définitions de périphériques regroupées par leur type, comme ethernets:, modems:, wifis:, ou bridges:. Ce sont les types que notre renderer peut comprendre et qui sont pris en charge par nos backends.

Chaque bloc de type contient des définitions de périphériques sous forme de map où les clés (appelées « IDs de configuration ») sont définies comme ci-dessous.

IDs de configuration de périphérique

Les noms de clés sous les maps de définition par périphérique (comme ethernets:) sont appelés « IDs ». Ils doivent être uniques dans l'ensemble des fichiers de configuration. Leur objectif principal est de servir de noms d'ancrage pour les périphériques composites, par exemple pour énumérer les membres d'un pont en cours de définition.

(Depuis 0.97) Si une interface est définie avec un ID dans un fichier de configuration ; elle sera activée par le renderer applicable. Pour ne pas qu'une interface soit touchée par Netplan, elle doit être complètement omise des fichiers de configuration Netplan.

Il existe deux classes de définitions de périphériques, physiquement/structurellement différentes, et le champ ID a une interprétation différente pour chacune d'elles :

Périphériques physiques

(Exemples : Ethernet, modem, Wi-Fi) Ceux-ci peuvent apparaître et disparaître dynamiquement entre les redémarrages et même pendant l'exécution (connexion à chaud). Dans le cas générique, ils peuvent être sélectionnés par des règles match: sur des propriétés désirées, telles que le nom/modèle de nom, l'adresse MAC, le pilote ou les chemins d'accès au périphérique. En général, ceux-ci correspondront à un nombre quelconque de périphériques (sauf s'ils font référence à des propriétés uniques telles que le chemin complet ou l'adresse MAC), donc sans connaissance supplémentaire du matériel, ceux-ci seront toujours considérés comme un groupe.

Il est valide de ne spécifier aucune règle de correspondance, auquel cas le champ ID est simplement le nom de l'interface à faire correspondre. Ceci est surtout utile si vous voulez que les cas simples restent simples, et c'est ainsi que la configuration des périphériques réseau a été faite pendant longtemps.

S'il y a des règles match:, alors le champ ID est un nom purement opaque qui n'est utilisé que pour les références provenant des définitions de périphériques composés dans la configuration.

Périphériques virtuels

(Exemples : veth, bridge, bond, vrf) Ceux-ci sont entièrement sous le contrôle du fichier (ou des fichiers) de configuration et de la pile réseau. C'est-à-dire que ces périphériques sont créés au lieu d'être mis en correspondance. Ainsi match: et set-name: ne sont pas applicables pour ceux-ci, et le champ ID est le nom du périphérique virtuel créé.

Configuration YAML

Structure de configuration de haut niveau

La structure générale d'un fichier YAML Netplan est montrée ci-dessous.

network:
  version: NOMBRE
  renderer: CHAÎNE
  bonds: MAPPE
  bridges: MAPPE
  dummy-devices: MAPPE
  ethernets: MAPPE
  modems: MAPPE
  tunnels: MAPPE
  virtual-ethernets: MAPPE
  vlans: MAPPE
  vrfs: MAPPE
  wifis: MAPPE
  nm-devices: MAPPE
•
version (nombre)

Définit quelle version du format de configuration est utilisée. La seule valeur prise en charge est 2. Par défaut à 2 si non défini.

•
renderer (scalaire)

Définit quel outil de configuration réseau sera utilisé pour configurer votre système. Les valeurs valides sont networkd et NetworkManager. Par défaut à networkd si non défini.

•
bonds (mappage)

Crée et configure des périphériques d'agrégation de liens (bonding).

•
bridges (mappage)

Crée et configure des périphériques de pont (bridge).

•
dummy-devices (mappage) – depuis 0.107

Crée et configure des périphériques virtuels.

•
ethernets (mappage)

Configure les interfaces Ethernet physiques.

•
modems (mappage)

Configure les modems.

•
tunnels (mappage)

Crée et configure différents types de tunnels virtuels.

•
virtual-ethernets (mappage) – depuis 0.107

Crée et configure des périphériques Ethernet virtuels (veth).

•
•
vlans (mapping)

Crée et configure des VLAN.

•
vrfs (mapping)

Configure les périphériques Virtual Routing and Forwarding (VRF).

•
wifis (mapping)

Configure les interfaces Wi-Fi physiques en tant que client, adhoc ou access point.

•
nm-devices (mapping)

nm-devices sont utilisés dans les situations où Netplan ne prend pas en charge le type de connexion. La configuration brute attendue par NetworkManager peut être définie et sera transmise telle quelle (passthrough) au fichier .nmconnection. Les utilisateurs n'utiliseront normalement pas ce type de périphérique.

Toutes les propriétés pour tous les types de périphériques seront décrites dans les sections suivantes.

Propriétés pour les types de périphériques physiques

Ces propriétés sont utilisées avec des périphériques physiques tels que les interfaces réseau Ethernet et Wi-Fi.

Note : Certaines options ne fonctionneront pas de manière fiable pour les périphériques identifiés uniquement par leur nom et rendus par networkd, en raison des interactions avec le renommage des périphériques dans udev. Identifiez les périphériques par leur MAC lors de la définition d'options telles que wakeonlan ou *-offload.

•
match (mapping)

Ceci sélectionne un sous-ensemble de périphériques physiques disponibles par diverses propriétés matérielles. La configuration suivante s'appliquera alors à tous les périphériques correspondants, dès leur apparition. Toutes les propriétés spécifiées doivent correspondre.

•
name (scalaire)

Nom d'interface actuel. Les jokers sont pris en charge, et le cas d'utilisation principal pour la correspondance sur les noms, car la sélection d'un nom fixe peut être plus facilement obtenue en n'ayant aucun match : du tout et en utilisant simplement l'ID (voir ci-dessus). (NetworkManager : à partir de la v1.14.0)

•
macaddress (scalaire)

Adresse MAC permanente de 6 octets du périphérique sous la forme XX:XX:XX:XX:XX:XX ou 20 octets pour les périphériques InfiniBand (IPoIB). Les jokers ne sont pas autorisés. Ceci ne correspond pas aux adresses MAC virtuelles pour veth, bridge, bond, vlan, ...

•
driver (scalaire ou séquence de scalaires) – séquence depuis 0.104

Nom du pilote du noyau, correspondant à la propriété udev DRIVER. Une séquence de jokers est prise en charge, dont l'un doit correspondre. La correspondance sur le pilote n'est uniquement prise en charge qu'avec networkd.

Exemples :

•
Toutes les cartes du deuxième bus PCI :
network:
  ethernets:
    myinterface:
      match:
        name: enp2*
•
Adresse MAC fixe :
network:
  ethernets:
    interface0:
      match:
        macaddress: 11:22:33:AA:BB:FF
•
Première carte du pilote ixgbe :
network:
  ethernets:
    nic0:
      match:
        driver: ixgbe
        name: en*s0
•
Première carte avec un pilote correspondant à bcmgenet ou smsc* :
network:
  ethernets:
    nic0:
      match:
        driver: ["bcmgenet", "smsc*"]
        name: en*
•
set-name (scalaire)

Lors de la correspondance sur des propriétés uniques telles que le chemin ou l'adresse MAC, ou avec des hypothèses supplémentaires telles que "il n'y aura qu'un seul périphérique Wi-Fi", les règles de correspondance peuvent être écrites de manière à ne correspondre qu'à un seul périphérique. Ensuite, cette propriété peut être utilisée pour donner à ce périphérique un nom plus spécifique ou souhaitable que celui par défaut d'udev si l'on utilise des ifnames. Tout périphérique supplémentaire qui satisfait aux règles de correspondance échouera à être renommé et conservera le nom du noyau d'origine (et dmesg affichera une erreur).

•
wakeonlan (booléen)

Active le démarrage par réseau (Wake on LAN). Désactivé par défaut.

•
emit-lldp (booléen) – depuis 0.99

(Backend networkd uniquement) Indique s'il faut émettre des paquets LLDP. Désactivé par défaut.

•
receive-checksum-offload (booléen) – depuis 0.104

(Backend networkd uniquement) Si défini sur true (false), la décharge matérielle pour le calcul de somme de contrôle des paquets réseau entrants est activée (désactivée). Lorsque non défini, le défaut du noyau sera utilisé.

•
transmit-checksum-offload (booléen) – depuis 0.104

(Backend networkd uniquement) Si défini sur true (false), la décharge matérielle pour le calcul de somme de contrôle des paquets réseau sortants est activée (désactivée). Lorsque non défini, le défaut du noyau sera utilisé.

•
tcp-segmentation-offload (booléen) – depuis 0.104

(Backend networkd uniquement) Si défini sur true (false), la décharge de segmentation TCP (TSO) est activée (désactivée). Lorsque non défini, le défaut du noyau sera utilisé.

•
tcp6-segmentation-offload (booléen) – depuis 0.104

(Backend networkd uniquement) Si défini sur true (false), la décharge de segmentation TCP6 (tx-tcp6-segmentation) est activée (désactivée). Lorsque non défini, le défaut du noyau sera utilisé.

•
generic-segmentation-offload (booléen) – depuis 0.104

(Backend networkd uniquement) Si défini sur true (false), la décharge de segmentation générique (GSO) est activée (désactivée). Lorsque non défini, le défaut du noyau sera utilisé.

•
generic-receive-offload (booléen) – depuis 0.104

(Backend networkd uniquement) Si défini sur true (false), la décharge de réception générique (GRO) est activée (désactivée). Lorsque non défini, le défaut du noyau sera utilisé.

•
large-receive-offload (booléen) – depuis 0.104

(Backend networkd uniquement) Si défini sur true (false), la décharge de réception volumineuse (LRO) est activée (désactivée). Lorsque non défini, le défaut du noyau sera utilisé.

•
openvswitch (mapping) – depuis 0.100

Ceci fournit une configuration supplémentaire pour le périphérique réseau openvswitch. Si Open vSwitch n'est pas disponible sur le système, Netplan traite la présence d'une configuration openvswitch comme une erreur.

Tout périphérique réseau pris en charge qui est déclaré avec le mapping openvswitch (ou toute liaison/pont incluant une interface avec une configuration openvswitch) sera créé dans openvswitch au lieu du renderer défini. Dans le cas d'une définition de vlan déclarée de la même manière, Netplan créera un faux pont VLAN dans openvswitch avec les propriétés vlan demandées.

•
external-ids (mapping) – depuis 0.100

Transmis directement à Open vSwitch

•
other-config (mapping) – depuis 0.100

Transmis directement à Open vSwitch

•
lacp (scalaire) – depuis 0.100

Valide pour les interfaces de liaison (bond). Accepte active, passive ou off (le

Valid for bridge interfaces. Accepts secure or standalone (the default).

•
mcast-snooping (booléen) – depuis 0.100

Valide pour les interfaces de pont. Faux par défaut.

•
protocols (séquence de scalaires) – depuis 0.100

Valide pour les interfaces de pont ou la section réseau. Liste des protocoles à utiliser lors de la négociation d'une connexion avec le contrôleur. Accepte OpenFlow10, OpenFlow11, OpenFlow12, OpenFlow13, OpenFlow14 et OpenFlow15.

•
rstp (booléen) – depuis 0.100

Valide pour les interfaces de pont. Faux par défaut.

•
controller (mapping) – depuis 0.100

Valide pour les interfaces de pont. Spécifiez un contrôleur OpenFlow externe.

•
addresses (séquence de scalaires)

Définissez la liste des adresses à utiliser pour les cibles du contrôleur. La syntaxe de ces adresses est telle que définie dans ovs-vsctl(8). Exemple : adresses : [tcp:127.0.0.1:6653, "ssl:[fe80::1234%eth0]:6653"].

•
connection-mode (scalaire)

Définissez le mode de connexion pour le contrôleur. Les options prises en charge sont in-band et out-of-band. La valeur par défaut est in-band.

•
ports (séquence de séquences de scalaires) – depuis 0.100

Ports de patch Open vSwitch. Chaque port est déclaré comme une paire de noms qui peuvent être référencés comme interfaces dans les périphériques virtuels dépendants (bonds, bridges).

Exemple :

openvswitch:
  ports:
    - [patch0-1, patch1-0]
•
ssl (mapping) – depuis 0.100

Valide pour les paramètres globaux openvswitch. Options pour configurer le point d'extrémité du serveur SSL pour le commutateur.

•
ca-cert (scalaire)

Chemin vers un fichier contenant le certificat CA à utiliser.

•
certificate (scalaire)

Chemin vers un fichier contenant le certificat du serveur.

•
private-key (scalaire)

Chemin vers un fichier contenant la clé privée du serveur.

Propriétés pour tous les types d'appareils

•
renderer (scalaire)

Utilisez le backend réseau donné pour cette définition. Actuellement pris en charge sont networkd et NetworkManager. Cette propriété peut être spécifiée globalement dans network:, pour un type d'appareil (par exemple dans ethernets:) ou pour une définition d'appareil particulière. La valeur par défaut est networkd.

(Depuis 0.99) La propriété renderer a une valeur acceptable supplémentaire pour les objets VLAN (c'est-à-dire définis dans vlans:) : sriov. Si un VLAN est défini avec le renderer sriov pour une interface de fonction virtuelle SR-IOV, cela amène Netplan à configurer un filtre VLAN matériel pour celui-ci. Il ne peut y en avoir qu'un défini par VF.

•
dhcp4 (booléen)

Activer DHCP pour IPv4. Désactivé par défaut.

•
dhcp6 (booléen)

Activer DHCP pour IPv6. Désactivé par défaut. Ceci couvre à la fois le DHCP sans état - où le serveur DHCP fournit des informations telles que les serveurs DNS mais pas l'adresse IP - et le DHCP avec état, où le serveur fournit à la fois l'adresse et les autres informations.

Si vous êtes dans un environnement IPv6 uniquement avec une configuration automatique sans état complète (SLAAC avec RDNSS), cette option peut être définie pour faire en sorte que l'interface soit activée. (Définir accept-ra seul n'est pas suffisant.) La configuration automatique respectera toujours le contenu de la publicité du routeur et n'utilisera le DHCP que si cela est demandé dans le RA.

Notez que rdnssd(8) est requis pour utiliser RDNSS avec networkd. Aucun logiciel supplémentaire n'est requis pour NetworkManager.

•
ipv6-mtu (scalaire) – depuis 0.98 > Définissez le MTU IPv6 (uniquement pris en charge avec le backend networkd). Notez que le besoin de définir cela est une exigence inhabituelle. > > Fonctionnalité requise :ipv6-mtu
•
ipv6-privacy (booléen)

Active les extensions de confidentialité IPv6 (RFC 4941) pour l'interface spécifiée et préfère les adresses temporaires. Par défaut à faux - pas d'extensions de confidentialité. Il n'existe actuellement aucun moyen d'avoir une adresse privée mais de préférer l'adresse publique.

•
link-local (séquence de scalaires)

Configure les adresses de lien local à activer. Les options valides sont ipv4 et ipv6, qui permettent respectivement d'activer l'adressage de lien local IPv4 et IPv6. Si ce champ n'est pas défini, la valeur par défaut est d'activer uniquement les adresses de lien local IPv6. Si le champ est défini mais configuré comme un ensemble vide, les adresses de lien local IPv6 sont désactivées ainsi que les adresses de lien local IPv4.

Cette fonctionnalité active ou désactive les adresses de lien local pour un protocole, mais l'implémentation réelle diffère selon le backend. Sur networkd, cela modifie directement le comportement et peut ajouter une adresse supplémentaire à une interface. Lors de l'utilisation du backend NetworkManager, l'activation du lien local n'a aucun effet si l'interface a également le DHCP activé.

Exemples :

•
Activer uniquement le lien local IPv4 : link-local: [ ipv4 ]
•
Activer toutes les adresses de lien local : link-local: [ ipv4, ipv6 ]
•
Désactiver toutes les adresses de lien local : link-local: [ ]
•
ignore-carrier (booléen) – depuis 0.104

(Backend networkd uniquement) Permet de configurer l'interface spécifiée même si elle n'a pas de porteuse.

•
critical (booléen)

Désigne la connexion comme "critique pour le système", ce qui signifie qu'une attention particulière sera portée pour ne pas libérer l'IP attribuée lors du redémarrage du démon. (non reconnu par NetworkManager)

•
dhcp-identifier (scalaire)

(Backend networkd uniquement) Définit la source de l'identifiant client DHCP (v4). Si mac est spécifié, l'adresse MAC du lien est utilisée. Si cette option est omise, ou si duid est spécifié, networkd générera un identifiant client conforme à la norme RFC4361 pour l'interface en combinant l'IAID et le DUID du lien.

•
dhcp4-overrides (mapping)

(Backend networkd uniquement) Remplace le comportement DHCP par défaut ; voir la section DHCP Overrides ci-dessous.

•
dhcp6-overrides (mapping)

(Backend networkd uniquement) Remplace le comportement DHCP par défaut ; voir la section DHCP Overrides ci-dessous.

•
accept-ra (booléen)

Accepte les publicités du routeur qui permettraient au noyau de configurer IPv6 par lui-même. Lorsqu'il est activé, accepte les publicités du routeur. Lorsqu'il est désactivé, ne répond pas aux publicités du routeur. Si non défini, utilise le paramètre par défaut du noyau de l'hôte.

•
ra-overrides (mapping) – depuis 1.1

(Backend networkd uniquement) Remplace le comportement par défaut des publicités de routeur IPv6 (RA) ; voir la section Publicités des routeurs IPv6 ci-dessous.

•
adresses (séquence de scalaires et de mappages)

Ajoute des adresses statiques à l'interface en plus de celles reçues via DHCP ou RA. Chaque entrée de séquence est en notation CIDR, c'est-à-dire de la forme addr/prefixlen. addr est une adresse IPv4 ou IPv6 reconnue par inet_pton(3) et prefixlen le nombre de bits du sous-réseau.

Pour les périphériques virtuels (bridges, bonds, VLAN) s'il n'y a pas d'adresse configurée et que DHCP est désactivé, l'interface peut toujours être mise en ligne, mais ne sera pas adressable depuis le réseau.

En plus des adresses elles-mêmes, on peut spécifier des paramètres de configuration sous forme de mappages. Les options actuellement prises en charge sont :

•
durée de vie (scalaire) – depuis 0.100

Par défaut : jamais. Peut être jamais ou 0 et correspond à l'option PreferredLifetime dans la section Address de systemd-networkd. Actuellement pris en charge uniquement sur le backend networkd.

•
label (scalaire) – depuis 0.100

Une étiquette d'adresse IP, équivalente à la commande ip address label. Actuellement pris en charge uniquement sur le backend networkd.

Exemples :

•
Simple : adresses : [192.168.14.2/24, "2001:1::1/64"]
•
Avancé :
network:
  ethernets:
    eth0:
      adresses:
        - "10.0.0.15/24":
            durée de vie: 0
            label: "maas"
        - "2001:1::1/64"
•
génération-d'adresses-ipv6 (scalaire) – depuis 0.99

Configure la méthode de création de l'adresse à utiliser avec la configuration automatique d'adresse sans état IPv6 RFC4862. Les valeurs possibles sont eui64 ou stable-privacy.

•
jeton-d'adresse-ipv6 (scalaire) – depuis 0.100

Définit un jeton d'adresse IPv6 pour la création d'un identifiant d'interface statique pour la configuration automatique d'adresse sans état IPv6. Ceci est mutuellement exclusif avec génération-d'adresses-ipv6.

•
passerelle4, passerelle6 (scalaire)

Obsolète, voir Routes par défaut. Définit la passerelle par défaut pour IPv4/6, pour la configuration manuelle des adresses. Ceci nécessite de définir également adresses. Les adresses IP de la passerelle doivent être dans un format reconnu par inet_pton(3). Il ne devrait y avoir qu'une seule passerelle par famille d'adresses IP définie dans votre configuration globale, pour la rendre non ambiguë. Si vous avez besoin de plusieurs routes par défaut, veuillez les définir via politique-de-routage.

Exemples

•
IPv4 : passerelle4 : 172.16.0.1
•
IPv6 : passerelle6 : "2001:4::1"
•
serveurs-noms (mappage)

Définit les serveurs DNS et les domaines de recherche, pour la configuration manuelle des adresses. Il y a deux champs pris en charge : adresses : est une liste d'adresses IPv4 ou IPv6 similaire à passerelle*, et recherche : est une liste de domaines de recherche.

Exemple :

network:
  ethernets:
    id0:
      [...]
      serveurs-noms:
        recherche: [lab, home]
        adresses: [8.8.8.8, "FEDC::1"]
•
adresse-mac (scalaire)

Définit l'adresse MAC du périphérique. L'adresse MAC doit être sous la forme "XX:XX:XX:XX:XX:XX". Les options spéciales suivantes sont également acceptées : permanent et aléatoire. En plus de ces options, le rendu NetworkManager accepte également stable, stable-ssid (Wi-Fi uniquement) et préserver.

Remarque : Cela ne fonctionnera pas de manière fiable pour les périphériques identifiés par leur nom seul et rendus par networkd, en raison des interactions avec le renommage des périphériques dans udev. Identifiez les périphériques par leur MAC lors de la définition des adresses MAC.

Exemple :

network:
  ethernets:
    id0:
      match:
        adresse-mac: 52:54:00:6b:3c:58
      [...]
      adresse-mac: 52:54:00:6b:3c:59
•
mtu (scalaire)

Définit l'Unité de Transmission Maximale (Maximum Transmission Unit) pour l'interface. La valeur par défaut est 1500. Les valeurs valides dépendent de votre interface réseau.

Remarque : Cela ne fonctionnera pas de manière fiable pour les périphériques identifiés par leur nom seul et rendus par networkd, en raison des interactions avec le renommage des périphériques dans udev. Identifiez les périphériques par leur MAC lors de la définition des MTU.

•
facultatif (booléen)

Un périphérique facultatif n'est pas requis pour le démarrage. Normalement, networkd attendra un certain temps que le périphérique soit configuré avant de poursuivre le démarrage. Cependant, si un périphérique est marqué comme facultatif, networkd n'attendra pas qu'il soit prêt. Ceci est *uniquement* pris en charge par networkd, et la valeur par défaut est false.

Exemple :

network:
  ethernets:
    eth7:
      # ceci est connecté à un réseau de test qui est souvent
      # hors ligne - ne pas attendre qu'il soit en ligne lors du démarrage.
      dhcp4: true
      facultatif: true
•
adresses-facultatives (séquence de scalaires)

Spécifie les types d'adresses qui ne sont pas requis pour qu'un périphérique soit considéré comme en ligne. Ceci modifie le comportement des backends au démarrage afin d'éviter d'attendre les adresses marquées comme facultatives, et ainsi de considérer l'interface comme "utilisable" plus rapidement. Cela ne désactive pas ces adresses, qui seront quand même activées.

Exemple :

network:
  ethernets:
    eth7:
      dhcp4: true
      dhcp6: true
      adresses-facultatives: [ ipv4-ll, dhcp6 ]
•
mode-activation (scalaire) – depuis 0.103

Permet de spécifier la politique de gestion de l'interface sélectionnée. Par défaut, Netplan active toute interface configurée si possible. En utilisant le paramètre mode-activation, les utilisateurs peuvent remplacer ce comportement en spécifiant manuel, pour confier le contrôle de l'état de l'interface à l'administrateur ou (pour le backend networkd *uniquement*) off pour forcer la liaison dans un état désactivé en permanence. Toute interface avec mode-activation défini est implicitement considérée comme facultative. Officiellement pris en charge à partir de networkd v248+.

Exemple :

network:
  ethernets:
    eth1:
      # cette interface ne sera pas mise à l'état UP automatiquement
      dhcp4: true
      mode-activation: manuel

routes (séquence de mappages)

Configure le routage statique pour le périphérique ; voir la section Routage ci-dessous.

•
politique-de-routage (séquence de mappages)

Configure la politique de routage pour le périphérique ; voir la section Routage ci-dessous.

•

Prend une valeur booléenne. Configure si la suppression des voisins ARP et ND est activée pour ce port de bridge. Si elle n'est pas définie, le défaut du noyau sera utilisé.

•

Prend une valeur booléenne. Configure si le trafic peut être renvoyé par le port de bridge sur lequel il a été reçu. Lorsque ce drapeau est faux, le bridge ne transmet pas le trafic sur le port de réception. S'il n'est pas défini, le backend par défaut est utilisé.

apprentissage-mac-port (scalaire) – depuis 1.0

Prend une valeur booléenne. Configure si l'apprentissage des adresses MAC est activé pour ce port de bridge. S'il n'est pas défini, le défaut du noyau est utilisé. Actuellement pris en charge uniquement sur le backend networkd.

DHCP Overrides

Several DHCP behaviour overrides are available. Most currently only have any effect when using the networkd back end, with the exception of use-routes and route-metric.

Overrides only have an effect if the corresponding dhcp4 or dhcp6 is set to true.

If both dhcp4 and dhcp6 are true, the networkd back end requires that dhcp4-overrides and dhcp6-overrides contain the same keys and values. If the values do not match, an error will be shown and the network configuration will not be applied.

When using the NetworkManager back end, different values may be specified for dhcp4-overrides and dhcp6-overrides, and will be applied to the DHCP client processes as specified in the Netplan YAML.

•
dhcp4-overrides, dhcp6-overrides (mapping)

The dhcp4-overrides and dhcp6-override mappings override the default DHCP behaviour.

•
use-dns (boolean)

Default: true. When true, the DNS servers received from the DHCP server will be used and take precedence over any statically configured ones. Currently only has an effect on the networkd back end.

•
use-ntp (boolean)

Default: true. When true, the NTP servers received from the DHCP server will be used by systemd-timesyncd and take precedence over any statically configured ones. Currently only has an effect on the networkd back end.

•
send-hostname (boolean)

Default: true. When true, the machine hostname will be sent to the DHCP server. Currently only has an effect on the networkd back end.

•
use-hostname (boolean)

Default: true. When true, the hostname received from the DHCP server will be set as the transient hostname of the system. Currently only has an effect on the networkd back end.

•
use-mtu (boolean)

Default: true. When true, the MTU received from the DHCP server will be set as the MTU of the network interface. When false, the MTU advertised by the DHCP server will be ignored. Currently only has an effect on the networkd back end.

•
hostname (scalar)

Use this value for the hostname which is sent to the DHCP server, instead of machine's hostname. Currently only has an effect on the networkd back end.

•
use-routes (boolean)

Default: true. When true, the routes received from the DHCP server will be installed in the routing table normally. When set to false, routes from the DHCP server will be ignored: in this case, the user is responsible for adding static routes if necessary for correct network operation. This allows users to avoid installing a default gateway for interfaces configured via DHCP. Available for both the networkd and NetworkManager back ends.

•
route-metric (scalar)

Use this value for default metric for automatically-added routes. Use this to prioritise routes for devices by setting a lower metric on a preferred interface. Available for both the networkd and NetworkManager back ends.

•
use-domains (scalar) – since 0.98

Takes a boolean, or the special value route. When true, the domain name received from the DHCP server will be used as DNS search domain over this link, similar to the effect of the Domains= setting. If set to route, the domain name received from the DHCP server will be used for routing DNS queries only, but not for searching, similar to the effect of the Domains= setting when the argument is prefixed with ~ (tilde).

Requires feature: dhcp-use-domains

IPv6 Router Advertisement Overrides

Overrides for IPv6 Router Advertisement (RA) behaviour (only supported with networkd back end).

•
ra-overrides (mapping) – since 1.1

The ra-overrides mappings override the default IPv6 Router Advertisement behaviour.

•
use-dns (boolean)

Default: true. When true, the DNS servers received from the Router Advertisement will be used. Currently only has an effect on the networkd back end.

•
use-domains (scalar)

Takes a boolean, or the special value route. When true, the domain name received from the Router Advertisement will be used as DNS search domain over this link. If set to route, the domain name received from the IPv6 RA will be used for routing DNS queries only, but not for searching. Defaults to false.

•
table (scalar)

The routing table number for routes received in the IPv6 RA. Allowed values are positive integers starting from 1. Some values are already in use to refer to specific routing tables: see {/etc,/usr/share}/iproute2/rt_tables.

Routing

Complex routing is possible with Netplan. Standard static routes as well as policy routing using routing tables are supported via the networkd back end.

These options are available for all types of interfaces.

Default routes

The most common need for routing concerns the definition of default routes to reach the wider internet. Those default routes can only defined once per IP family and routing table. A typical example would look like the following:

network:
  ethernets:
    eth0:
      [...]
      routes:
        - to: default # could be 0.0.0.0/0 optionally
          via: 10.0.0.1
          metric: 100
          on-link: true
          advertised-mss: 1400
        - to: default # could be ::/0 optionally
          via: cf02:de:ad:be:ef::2
    eth1:
      [...]
      routes:
        - to: default
          via: 172.134.67.1
          metric: 100
          on-link: true
          # Not on the main routing table,
          # does not conflict with the eth0 default route
      table: 76
•
routes (mapping)

The routes block defines standard static routes for an interface. At least to must be specified. If type is local or nat a default scope of host is assumed. If type is unicast and no gateway (via) is given or type is broadcast, multicast or anycast a default scope of link is assumed. Otherwise, a global scope is the default setting.

For from, to and via, both IPv4 and IPv6 addresses are recognised, and must be in the form addr/prefixlen or addr.

•
from (scalar)

Set a source IP address for traffic going through the route. (NetworkManager: as of v1.8.0)

•
to (scalar)

Destination address for the route.

•
via (scalar)

Address to the gateway to use for this route.

true, spécifie que la route est directement connectée à l'interface. (NetworkManager : à partir de v1.12.0 pour IPv4 et v1.18.0 pour IPv6)

•
metric (scalaire)

La priorité relative de la route. Doit être un entier positif.

•
type (scalaire)

Le type de route. Les options valides sont unicast (par défaut), anycast, blackhole, broadcast, local, multicast, nat, prohibit, throw, unreachable ou xresolve.

•
scope (scalaire)

La portée de la route, son étendue sur le réseau. Les valeurs possibles sont global, link, ou host. S'applique uniquement à IPv4.

•
table (scalaire)

Le numéro de table à utiliser pour la route. Dans certains scénarios, il peut être utile de définir des routes dans une table de routage séparée. Il peut également être utilisé pour faire référence à des règles de politique de routage qui acceptent également un paramètre table. Les valeurs autorisées sont des entiers positifs à partir de 1. Certaines valeurs sont déjà utilisées pour faire référence à des tables de routage spécifiques : voir /etc/iproute2/rt_tables. (NetworkManager : à partir de v1.10.0)

•
mtu (scalaire) – depuis 0.101

Le MTU à utiliser pour la route, en octets. Doit être un entier positif.

•
congestion-window (scalaire) – depuis 0.102

La fenêtre de congestion à utiliser pour la route, représentée par le nombre de segments. Doit être un entier positif.

•
advertised-receive-window (scalaire) – depuis 0.102

La fenêtre de réception à annoncer pour la route, représentée par le nombre de segments. Doit être un entier positif.

•
advertised-mss (scalaire) – depuis 1.1

La taille maximale de segment (MSS) à annoncer à ces destinations lors de l'établissement de connexions TCP. Si elle n'est pas spécifiée, Linux utilise une valeur par défaut calculée à partir du MTU de l'interface du premier saut. Doit être un entier positif.

•
routing-policy (mapping)

Le bloc routing-policy définit une politique de routage supplémentaire pour un réseau, où le trafic peut être traité spécialement en fonction de l'adresse IP source, du marquage du pare-feu, etc.

Pour from et to, les adresses IPv4 et IPv6 sont reconnues et doivent être au format addr/prefixlen ou addr.

•
from (scalaire)

Définit une adresse IP source pour faire correspondre le trafic à cette règle de politique.

•
to (scalaire)

Fait correspondre le trafic allant à la destination spécifiée.

•
table (scalaire)

Le numéro de table à faire correspondre pour la route. Dans certains scénarios, il peut être utile de définir des routes dans une table de routage séparée. Il peut également être utilisé pour faire référence à des routes qui acceptent également un paramètre table. Les valeurs autorisées sont des entiers positifs à partir de 1. Certaines valeurs sont déjà utilisées pour faire référence à des tables de routage spécifiques : voir /etc/iproute2/rt_tables.

•
priority (scalaire)

Définit une priorité pour la règle de politique de routage, afin d'influencer l'ordre dans lequel les règles de routage sont traitées. Un nombre plus élevé signifie une priorité plus faible : les règles sont traitées par ordre croissant de numéro de priorité. La spécification d'une priorité explicite et unique pour chaque règle de politique de routage est fortement recommandée et est obligatoire sur le backend NetworkManager.

•
mark (scalaire)

Fait correspondre cette règle de politique de routage au trafic qui a été marqué par le pare-feu iptables avec cette valeur. Les valeurs autorisées sont des entiers positifs à partir de 1.

•
type-of-service (scalaire)

Fait correspondre cette règle de politique en fonction du numéro de type de service appliqué au trafic.

Propriétés du type d'appareil ethernets

Status: Facultatif.

Purpose: Utilisez la clé ethernets pour configurer les interfaces Ethernet.

Structure: La clé se compose de# Traduction en français du contenu fourni

Appareils Ethernet

Un mappage des identifiants d'interface Ethernet. Chaque ethernet possède un certain nombre d'options de configuration. Vous n'avez pas besoin de définir chaque interface par son nom à l'intérieur du mappage ethernets. Vous pouvez utiliser n'importe quel identifiant qui décrit l'interface et faire correspondre la carte réseau réelle à l'aide de la clé match. La structure de configuration générale pour Ethernet est illustrée ci-dessous.

network:
  ethernets:
    device-id:
      ...

device-id est l'identifiant de l'interface. Si vous utilisez le nom de l'interface comme identifiant, Netplan fera correspondre cette interface.

Considérez l'exemple ci-dessous. Dans ce cas, une interface nommée eth0 sera configurée avec DHCP.

network:
  ethernets:
    eth0:
      dhcp4: true

device-id peut être n'importe quel nom descriptif que vous trouvez pertinent. Cependant, s'il ne correspond pas à un nom d'interface réel, vous devez utiliser la propriété match pour identifier le périphérique que vous souhaitez configurer.

L'exemple ci-dessous définit une connexion Ethernet nommée isp-interface (supposée être une interface externe connectée au fournisseur d'accès à Internet) et utilise match pour appliquer la configuration au périphérique physique dont l'adresse MAC est aa:bb:cc:00:11:22.

network:
  ethernets:
    isp-interface:
      match:
        macaddress: aa:bb:cc:00:11:22
      dhcp4: true

Les définitions de périphériques Ethernet, au-delà des plus courantes décrites ci-dessus, prennent également en charge certaines propriétés supplémentaires qui peuvent être utilisées pour les périphériques SR-IOV.

•
link (scalaire) – depuis 0.99

(Périphériques SR-IOV uniquement) La propriété link déclare le périphérique comme une Fonction Virtuelle du périphérique de Fonction Physique sélectionné, tel qu'identifié par l'ID Netplan donné.

Exemple :

network:
  ethernets:
    enp1: {...}
    enp1s16f1:
      link: enp1
•
virtual-function-count (scalaire) – depuis 0.99

(Périphériques SR-IOV uniquement) Dans certains cas spéciaux, les VFs peuvent devoir être configurées en dehors de Netplan. Pour de telles configurations, virtual-function-count peut être utilisé facultativement pour définir un nombre explicite de Fonctions Virtuelles pour la Fonction Physique donnée. Si non défini, la valeur par défaut est de créer autant de VFs que celles définies dans la configuration Netplan. Ceci ne doit être utilisé que dans des cas spéciaux.

Fonctionnalité requise : sriov

•
embedded-switch-mode (scalaire) – depuis 0.104

(Périphériques SR-IOV uniquement) Change le mode opérationnel du commutateur intégré d'un périphérique PCI SmartNIC pris en charge (par exemple, Mellanox ConnectX-5). Les valeurs possibles sont switchdev ou legacy ; si non spécifié, la configuration par défaut du fournisseur est utilisée.

Fonctionnalité requise : eswitch-mode

•
delay-virtual-functions-rebind (booléen) – depuis 0.104

(Périphériques SR-IOV uniquement) Retarde le re-liage des fonctions virtuelles SR-IOV à leur pilote après avoir modifié le paramètre embedded-switch-mode à une étape ultérieure. Peut être activé en cas d'utilisation de bonding/VF LAG. La valeur par défaut est false.

Fonctionnalité requise : eswitch-mode

•
infiniband-mode (scalaire) – depuis 0.105

(Périphériques InfiniBand uniquement) Change le mode opérationnel d'un périphérique IPoIB. Les valeurs possibles sont datagram ou connected. Si non spécifié, la configuration par défaut du noyau est utilisée.

Fonctionnalité requise : infiniband

network:

•
password (scalaire
)

Activez l'authentification WPA/WPA2 et définissez la phrase secrète pour celle-ci. Si ni celle-ci ni un bloc auth ne sont fournis, le réseau est supposé être ouvert. Le paramètre

auth:

mode (scalaire)

bssid (scalaire) – depuis 0.99

•
band (scalaire) – depuis 0.99

Les bandes possibles sont 5GHz (pour 802.11a 5GHz) et 2.4GHz (pour 802.11 2.4GHz), ne restreignez pas la bande de fréquence 802.11 du réseau si non définie (par défaut).

channel (scalaire) – depuis 0.99

Canal sans fil à utiliser pour la connexion Wi-Fi. Comme les numéros de canal se chevauchent entre les bandes, cette propriété ne prend effet que si la propriété band est également définie.

hidden (booléen) – depuis 0.100

Définir sur true pour modifier la technique d'analyse SSID pour la connexion aux réseaux Wi-Fi masqués. Notez que cela peut entraîner des performances plus lentes par rapport à false (par défaut) lors de la connexion aux SSID diffusés publiquement.

•
wakeonwlan (séquence de scalaires) – depuis 0.99

Cela active WakeOnWLan sur les appareils pris en charge. Tous les pilotes ne prennent pas en charge toutes les options. Peut être une combinaison de any, disconnect, magic_pkt, gtk_rekey_failure, eap_identity_req, four_way_handshake, rfkill_release ou tcp (NetworkManager uniquement). Ou le drapeau exclusif default (par défaut).

•
regulatory-domain (scalaire) – depuis 0.105

Cela peut être utilisé pour définir le domaine réglementaire de la radio, afin d'utiliser des canaux Wi-Fi supplémentaires en dehors du "domaine mondial". Prend un code de pays ISO/IEC 3166 (comme GB) ou 00 pour réinitialiser au "domaine mondial". Voir wireless-regdb pour les valeurs disponibles.

Nécessite une dépendance : iw, si elle doit être utilisée en dehors du backend networkd (wpasupplicant).

•
ageing-time, aging-time (scalaire)

Définit la période pendant laquelle une adresse MAC est conservée dans la base de données de transfert après la réception d'un paquet. Ceci correspond à la propriété AgeingTimeSec= lorsque le renderer networkd est utilisé. Si aucun suffixe temporel n'est spécifié, la valeur sera interprétée en secondes.

•
priority (scalaire)

Définit la valeur de priorité pour le bridge. Cette valeur doit être un nombre compris entre 0 et 65535. Des valeurs plus basses signifient une priorité plus élevée. Le bridge avec la priorité la plus élevée sera élu comme bridge racine.

•
port-priority (mappage)

Définit la priorité du port par interface. La valeur de priorité est un nombre compris entre 0 et 63. Cette métrique est utilisée dans les algorithmes de sélection des ports désignés et des ports racine.

Exemple :

network:
  ethernets:
    eth0:
      dhcp4: false
    eth1:
      dhcp4: false
  bridges:
    br0:
      interfaces: [eth0, eth1]
      parameters:
        port-priority:
          eth0: 10
          eth1: 20
•
forward-delay (scalaire)

Spécifie la période pendant laquelle le bridge restera dans les états Listening et Learning avant d'atteindre l'état Forwarding. Ce champ correspond à la propriété ForwardDelaySec= pour le renderer networkd. Si aucun suffixe temporel n'est spécifié, la valeur sera interprétée en secondes.

•
hello-time (scalaire)

Spécifie l'intervalle entre deux paquets de salutation envoyés par les bridges racine et désignés. Les paquets de salutation communiquent des informations sur la topologie du réseau. Lorsque le renderer networkd est utilisé, cela correspond à la propriété HelloTimeSec=. Si aucun suffixe temporel n'est spécifié, la valeur sera interprétée en secondes.

•
max-age (scalaire)

Définit l'âge maximum d'un paquet de salutation. Si le dernier paquet de salutation est plus ancien que cette valeur, le bridge tentera de devenir le bridge racine. Ceci correspond à la propriété MaxAgeSec= lorsque le renderer networkd est utilisé. Si aucun suffixe temporel n'est spécifié, la valeur sera interprétée en secondes.

•
path-cost (mappage)

Définit le coût par interface d'un chemin sur le bridge. Les interfaces plus rapides devraient avoir un coût inférieur. Cela permet un contrôle plus fin de la topologie du réseau afin que les chemins les plus rapides soient disponibles chaque fois que possible.

Exemple :

network:
  ethernets:
    eth0:
      dhcp4: false
    eth1:
      dhcp4: false
  bridges:
    br0:
      interfaces: [eth0, eth1]
      parameters:
        path-cost:
          eth0: 100
          eth1: 200
•
stp (booléen)

Définit si le bridge doit utiliser le protocole Spanning Tree. La valeur par défaut est true, ce qui signifie que Spanning Tree doit être utilisé.

Propriétés pour le type d'appareil bonds

Statut : Facultatif.

Objectif : Utiliser la clé bonds pour créer des interfaces Bond (Agrégation de liens).

Structure : La clé se compose d'une correspondance de noms d'interfaces Bond. Chaque bond a une liste facultative d'interfaces qui feront partie de l'agrégation. Les interfaces listées dans la clé interfaces doivent également être définies dans votre configuration Netplan. La structure générale de configuration pour les Bonds est montrée ci-dessous.

network:
  bonds:
    bond0:
      interfaces:
        - enp5s0
        - enp5s1
        - enp5s2
      parameters:
        mode: active-backup
      ...

Lors de l'application, une interface virtuelle de type bond nommée bond0 sera créée dans le système.

Les paramètres spécifiques pour les bonds sont définis ci-dessous.

•
interfaces (séquence de scalaires)

Tous les périphériques correspondant à cette liste d'identifiants seront ajoutés au bond.

Exemple :

network:
  ethernets:
    switchports:
      match: {name: "enp2*"}
  [...]
  bonds:
    bond0:
      interfaces: [switchports]
•
parameters (mappage)

Paramètres de personnalisation pour les options de bonding spéciales. Les intervalles de temps peuvent devoir être exprimés en secondes ou en millisecondes : la valeur par défaut est spécifiée ci-dessous. Si nécessaire, les intervalles de temps peuvent être qualifiés à l'aide d'un suffixe de temps (tel que s pour secondes, ms pour millisecondes) pour permettre un meilleur contrôle de son comportement.

•
mode (scalaire)

Définit le mode de bonding utilisé pour les interfaces. La valeur par défaut est balance-rr (round robin). Les valeurs possibles sont balance-rr, active-backup, balance-xor, broadcast, 802.3ad, balance-tlb et balance-alb. Pour Open vSwitch active-backup et les modes supplémentaires balance-tcp et balance-slb sont pris en charge.

•
lacp-rate (scalaire)

Définit la fréquence à laquelle les LACPDU sont transmis. Ceci n'est utile qu'en mode 802.3ad. Les valeurs possibles sont slow (30 secondes, par défaut) et fast (chaque seconde).

•
mii-monitor-interval (scalaire)

Spécifie l'intervalle de surveillance MII (vérification si une interface du bond a un signal). La valeur par défaut est 0, ce qui désactive la surveillance MII. Ceci est équivalent au champ MIIMonitorSec= pour le backend networkd. Si aucun suffixe de temps n'est spécifié, la valeur sera interprétée en millisecondes.

•
min-links (scalaire)

Le nombre minimum de liens actifs dans un bond pour que l'interface bond soit considérée comme active.

•
transmit-hash-policy (scalaire)

Spécifie la politique de hachage de transmission pour la sélection des ports. Ceci n'est utile qu'en modes balance-xor, 802.3ad et balance-tlb. Les valeurs possibles sont layer2, layer3+4, layer2+3, encap2+3 et encap3+4.

•
ad-select (scalaire)

Définit le mode de sélection de l'agrégation. Les valeurs possibles sont stable, bandwidth et count. Cette option n'est utilisée qu'en mode 802.3ad.

•
all-members-active (booléen) – depuis 0.106

Si le bond doit ignorer les trames dupliquées reçues sur des ports inactifs, définissez cette option sur false. Si elles doivent être livrées, définissez cette option sur true. La valeur par défaut est false et est le comportement souhaitable dans la plupart des situations.

Alias : all-slaves-active

•
arp-interval (scalaire)

Définit l'intervalle de temps pour la surveillance des liens ARP (à quelle fréquence la surveillance des liens ARP doit avoir lieu). La valeur par défaut est 0, ce qui désactive la surveillance ARP. Pour le backend networkd, cela correspond à la propriété ARPIntervalSec=. Si aucun suffixe de temps n'est spécifié, la valeur sera interprétée en millisecondes.

•
arp-ip-targets (séquence de scalaires)

Adresses IP d'autres hôtes sur le lien auxquels des requêtes ARP doivent être envoyées pour valider qu'un port est actif. Cette option n'est utilisée que lorsque arp-interval est défini sur une valeur autre que 0. Au moins une adresse IP doit être fournie pour que la surveillance des liens ARP fonctionne. Seules les adresses IPv4 sont prises en charge. Vous pouvez spécifier jusqu'à 16 adresses IP. La valeur par défaut est une liste vide.

•
arp-validate (scalaire)

Configure la manière dont les réponses ARP doivent être validées lors de l'utilisation de la surveillance des liens ARP. Les valeurs possibles sont none, active, backup et all.

•
arp-all-targets (scalaire)

Spécifie si un quelconque objectif IP ARP actif est suffisant pour qu'un port soit considéré comme actif ; ou si tous les objectifs doivent être actifs. Ceci n'est utilisé qu'en mode active-backup lorsque arp-validate est activé. Les valeurs possibles sont any et all.

•
up-delay (scalaire)

Spécifie le délai avant d'activer un lien une fois que le lien est physiquement actif. La valeur par défaut est 0. Ceci correspond à la propriété UpDelaySec= pour le rendu networkd. Cette option n'est valide que pour le moniteur de lien miimon. Si aucun suffixe de temps n'est spécifié, la valeur sera interprétée en millisecondes.

•
down-delay (scalaire)

Spécifie le délai avant de désactiver un lien une fois que le lien a été perdu. La valeur par défaut est 0. Ceci correspond à la propriété DownDelaySec= pour le rendu networkd. Cette option n'est valide que pour le moniteur de lien miimon. Si aucun suffixe de temps n'est spécifié, la valeur sera interprétée en millisecondes.

•
fail-over-mac-policy (scalaire)

Définit si tous les ports doivent avoir la même adresse MAC lors de leur ajout au bond, ou comment le système doit gérer les adresses MAC. Les valeurs possibles sont none, active et follow.

•
gratuitous-arp (scalaire)

Spécifie le nombre de paquets ARP à envoyer après un basculement. Une fois qu'un lien est actif sur un nouveau port, une notification est envoyée et éventuellement répétée si cette valeur est supérieure à 1. La valeur par défaut est 1 et les valeurs valides sont comprises entre 1 et 255. Ceci n'affecte que le mode active-backup.

Pour des raisons historiques, la faute d'orthographe gratuitious-arp est également acceptée et a la même fonction.

•
packets-per-member (scalaire) – depuis 0.106

En mode balance-rr, spécifie le nombre de paquets à transmettre sur un port avant de passer au suivant. Lorsque cette valeur est définie sur 0, les ports sont choisis au hasard. Les valeurs autorisées sont comprises entre 0 et 65535. La valeur par défaut est 1. Ce paramètre n'est utilisé qu'en mode balance-rr.

Alias : packets-per-slave

•
primary-reselect-policy (scalaire)

Définit la politique de re-sélection pour le port primaire. En cas de défaillance du port actif, le système utilise cette politique pour décider comment le nouveau port actif sera choisi et comment la récupération sera gérée. Les valeurs possibles sont always, better et failure.

•
resend-igmp (scalaire)

Dans les modes balance-rr, active-backup, balance-tlb et balance-alb, un basculement peut transférer le trafic IGMP d'un port à un autre.

Ce paramètre spécifie le nombre de rapports d'appartenance IGMP émis lors d'un événement de basculement. Les valeurs vont de 0 à 255. 0 désactive l'envoi des rapports d'appartenance. Sinon, le premier rapport d'appartenance est envoyé lors du basculement et les rapports suivants sont envoyés à intervalles de 200 ms.

•
learn-packet-interval (scalaire)

Spécifie l'intervalle entre l'envoi des paquets d'apprentissage à chaque port. La plage de valeurs est comprise entre 1 et 0x7fffffff. La valeur par défaut est 1. Cette option n'affecte que les modes balance-tlb et balance-alb. En utilisant le renderer networkd, ce champ est mappé à la propriété LearnPacketIntervalSec=. Si aucun suffixe de temps n'est spécifié, la valeur sera interprétée en secondes.

•
primary (scalaire)

Spécifie un périphérique à utiliser comme port primaire, ou le périphérique préféré à utiliser comme port pour la liaison (c'est-à-dire le périphérique préféré pour envoyer des données), tant qu'il est disponible. Ceci n'affecte que les modes active-backup, balance-alb et balance-tlb.

(yaml-tunnels)= ## Propriétés pour le type d'interface tunnels

Statut: Facultatif.

Objectif: Utiliser la clé tunnels pour créer des interfaces de tunnel virtuelles.

Structure: La clé se compose d'un mappage des noms d'interfaces de tunnel. Chaque tunnel nécessite l'identification du mode de tunnel (voir la section mode ci-dessous pour la liste des modes pris en charge). La structure générale de configuration pour les tunnels est présentée ci-dessous.

network:
  tunnels:
    tunnel0:
      mode: SCALAR
      ...

Lors de l'application, une interface virtuelle appelée tunnel0 sera créée dans le système. Son mode de fonctionnement est défini par la propriété mode.

Les tunnels permettent au trafic de passer comme s'il était entre des systèmes sur le même réseau local, bien que les systèmes puissent être éloignés les uns des autres mais accessibles via Internet. Ils peuvent être utilisés pour prendre en charge le trafic IPv6 sur un réseau où le FAI ne fournit pas le service, ou pour étendre et "connecter" des réseaux locaux distincts. Voir Tunneling_protocol pour plus d'informations générales sur les tunnels.

Les paramètres spécifiques pour les tunnels sont définis ci-dessous.

•
mode (scalaire)

Définit le mode du tunnel. Les options valides sont sit, gre, ip6gre, ipip, ipip6, ip6ip6, vti, vti6, wireguard, vxlan, gretap et ip6gretap. De plus, le backend NetworkManager prend en charge les tunnels isatap.

•
local (scalaire)

Définit l'adresse du point d'extrémité local du tunnel. (Pour VXLAN) Cela doit correspondre à l'une des adresses IP du parent ou utiliser les valeurs spéciales de networkd.

•
remote (scalaire)

Définit l'adresse du point d'extrémité distant du tunnel ou l'adresse IP du groupe multicast pour VXLAN.

•
ttl (scalaire) – depuis 0.103

Définit le Time To Live (TTL) du tunnel. Prend un nombre dans la plage 1..255.

•
key (scalaire ou mappage)

Définit les clés à utiliser pour le tunnel. La clé peut être un nombre ou un quad dotted (une adresse IPv4). Pour wireguard, il peut s'agir d'une clé privée encodée en base64 ou (à partir de networkd v242+) d'un chemin absolu vers un fichier contenant la clé privée (depuis 0.100). Elle est utilisée pour l'identification des transformations IP. Ceci n'est requis que pour vti et vti6 lors de l'utilisation du backend networkd.

Ce champ peut être utilisé comme un scalaire (signifiant qu'une seule clé est spécifiée et sera utilisée pour l'entrée, la sortie et la clé privée), ou comme un mappage, où vous pouvez spécifier davantage input/output/private.

•
input (scalaire)

La clé d'entrée pour le tunnel

•
output (scalaire)

La clé de sortie pour le tunnel

•
private (scalaire) – depuis 0.100

Une clé privée encodée en base64 requise pour les tunnels WireGuard. Lorsque le backend systemd-networkd (v242+) est utilisé, cela peut également être un chemin absolu vers un fichier contenant la clé privée.

•

Indicateurs de clé privée utilisés par NetworkManager. Les valeurs possibles sont : agent-owned, not-saved et not-required.

not-saved: ce secret ne doit pas être enregistré mais doit être demandé à l'utilisateur chaque fois qu'il est nécessaire.

not-required: cet indicateur suggère que le secret n'est pas requis et ne doit pas être demandé à l'utilisateur.

Exemple:

network:

•
peer (scalaire)

network:
  version: 2
  renderer: networkd
  virtual-ethernets:
    veth0-peer1:
      peer: veth0-peer2
    veth0-peer2:
      peer: veth0-peer1
  bridges:
    br0:
      interfaces:
        - veth0-peer1
    br1:
      interfaces:
        - veth0-peer2

NAME

netplan - YAML network configuration abstraction

SYNOPSIS

netplan [OPTIONS] SUBCOMMAND

COMMANDS

Available subcommands: generate, apply, try, get, set, info, ip, rebind, status, dbus.

DESCRIPTION

Netplan is an Ubuntu utility to configure network interfaces using YAML files. It generates configuration for an arbitrary backend (networkd or NetworkManager) from a frontend YAML description. The configuration files are located in {@code /etc/netplan/*.yaml}.

The generated configuration files are placed in {@code /run/systemd/network/} for networkd or managed by NetworkManager respectively.

The primary use of Netplan is to abstract the network configuration away from the user and to ensure that network configurations are portable across different systems, and across different network backends.

Netplan will fall back to {@code /etc/netplan/01-network-manager-all.yaml} if {@code /etc/netplan/networkd-all.yaml} does not exist and the configuration is intended for networkd.

YAML configuration

Netplan configurations are stored in YAML files located in {@code /etc/netplan/}. Files are processed in lexicographical order. The first file found to specify a particular configuration key will be used. Ensure that your configuration files end with {@code .yaml}.

Configuration files are typically named like {@code 01-network-manager-all.yaml}, {@code 00-installer-config.yaml}, etc.

The following structure is common to all configurations:

network:
  version: 2
  ethernets: { ... }
  wifis: { ... }
  vlans: { ... }
  tunnels: { ... }
  bridges: { ... }
  bonds: { ... }
  lookup: { ... }
  renderer: [networkd | NetworkManager]
version (scalar)
Required. Must be {@code 2}.
renderer (scalar)
Optional. Specifies which backend to use: {@code networkd} or {@code NetworkManager}. If not specified, Netplan will try to detect which renderer is most appropriate.
ethernets (mapping)
Defines static network interfaces.
wifis (mapping)
Defines WiFi network interfaces.
vlans (mapping)
Defines VLAN interfaces.
tunnels (mapping)
Defines tunnel interfaces.
bridges (mapping)
Defines bridge interfaces.
bonds (mapping)
Defines bond interfaces.
lookup (mapping)
Defines DNS configuration.

Properties for device type vlans

Status: Optional.

Purpose: Use the vlans key to define VLAN interfaces.

Structure: The key consists of a mapping of VLAN interface names. The interface used in the link option (enp5s0 in the example below) must also be defined in the Netplan configuration. The general configuration structure for VLANs is shown below.

network:
  vlans:
    vlan123:
      id: 123
      link: enp5s0
      dhcp4: yes

The specific settings for VLANs are defined below.

•
id (scalar)

VLAN ID, a number between 0 and 4094.

•
link (scalar)

Netplan ID of the underlying device definition on which this VLAN gets created.

Example:

network:
  ethernets:
    eno1: {...}
  vlans:
    en-intra:
      id: 1
      link: eno1
      dhcp4: yes
    en-vpn:
      id: 2
      link: eno1
      addresses: [...]

Properties for device type vrfs

Status: Optional.

Purpose: Use the vrfs key to create Virtual Routing and Forwarding (VRF) interfaces.

Structure: The key consists of a mapping of VRF interface names. The interface used in the link option (enp5s0 in the example below) must also be defined in the Netplan configuration. The general configuration structure for VRFs is shown below.

network:
  renderer: networkd
  vrfs:
    vrf1:
      table: 1
      interfaces:
        - enp5s0
      routes:
        - to: default
          via: 10.10.10.4
      routing-policy:
        - from: 10.10.10.42
•
table (scalar) – since 0.105

The numeric routing table identifier. This setting is compulsory.

•
interfaces (sequence of scalars) – since 0.105

All devices matching this ID list will be added to the VRF. This may be an empty list, in which case the VRF will be brought online with no member interfaces.

•
routes (sequence of mappings) – since 0.105

Configure static routing for the device; see the Routing section. The table value is implicitly set to the VRF table.

•
routing-policy (sequence of mappings) – since 0.105

Configure policy routing for the device; see the Routing section. The table value is implicitly set to the VRF table.

Example:

network:
  vrfs:
    vrf20:
      table: 20
      interfaces: [ br0 ]
      routes:
        - to: default
          via: 10.10.10.3
      routing-policy:
        - from: 10.10.10.42
    [...]
  bridges:
    br0:
      interfaces: []

Properties for device type nm-devices

Status: Optional. Its use is not recommended.

Purpose: Use the nm-devices key to configure device types that are not supported by Netplan. This is NetworkManager specific configuration.

Structure: The key consists of a mapping of NetworkManager connections. The nm-devices device type is for internal use only and should not be used in normal configuration files. It enables a fallback mode for unsupported settings, using the passthrough mapping. The general configuration structure for NM connections is shown below.

network:
  version: 2
  nm-devices:
    NM-db5f0f67-1f4c-4d59-8ab8-3d278389cf87:
      renderer: NetworkManager
      networkmanager:
        uuid: "db5f0f67-1f4c-4d59-8ab8-3d278389cf87"
        name: "myvpnconnection"
        passthrough:
          connection.type: "vpn"
          vpn.ca: "path to ca.crt"
          vpn.cert: "path to client.crt"
          vpn.cipher: "AES-256-GCM"
          vpn.connection-type: "tls"
          vpn.dev: "tun"
          vpn.key: "path to client.key"
          vpn.remote: "1.2.3.4:1194"
          vpn.service-type: "org.freedesktop.NetworkManager.openvpn"

Paramètres de configuration spécifiques au back-end

En plus des autres champs disponibles pour configurer les interfaces, certains back-ends peuvent nécessiter d'enregistrer certains de leurs propres paramètres dans Netplan, en particulier si les définitions Netplan sont générées automatiquement par le consommateur de ce back-end. Actuellement, cela n'est utilisé qu'avec NetworkManager.

•
networkmanager (mapping) – depuis 0.99

Conserve les paramètres de configuration spécifiques à NetworkManager utilisés par le démon pour reconnaître les connexions.

•
name (scalar) – depuis 0.99

Définit le nom d'affichage de la connexion.

•
uuid (scalar) – depuis 0.99

Définit l'UUID (identifiant unique) de cette connexion, tel que généré par NetworkManager lui-même.

•
stable-id (scalar) – depuis 0.99

Définit l'ID stable (une forme différente d'un nom de connexion) utilisé par NetworkManager au cas où le nom de la connexion pourrait changer, par exemple lors du partage de connexions entre utilisateurs.

•
device (scalar) – depuis 0.99

Définit le nom de l'interface à laquelle cette connexion s'applique.

•
passthrough (mapping) – depuis 0.102

Peut être utilisé comme mécanisme de secours pour les paramètres manquants du fichier de clé.
