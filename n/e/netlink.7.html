netlink(7) Manuel d'informations diverses netlink(7)

NOM

netlink - communication entre le noyau et l'espace utilisateur (AF_NETLINK)

SYNTAXE

#include <asm/types.h>
#include <sys/socket.h>
#include <linux/netlink.h>
socket_netlink = socket(AF_NETLINK, type_socket, famille_netlink);

DESCRIPTION

Netlink est utilisé pour transférer des informations entre le noyau et les processus de l'espace utilisateur. Il se compose d'une interface standard basée sur les sockets pour les processus de l'espace utilisateur et d'une API interne au noyau pour les modules du noyau. L'interface interne du noyau n'est pas documentée dans cette page de manuel. Il existe également une interface netlink obsolète via des périphériques de caractères netlink ; cette interface n'est pas documentée ici et n'est fournie que pour des raisons de compatibilité ascendante.

Netlink est un service orienté datagramme. SOCK_RAW et SOCK_DGRAM sont des valeurs valides pour type_socket. Cependant, le protocole netlink ne fait pas de distinction entre les sockets datagrammes et bruts.

famille_netlink sélectionne le module du noyau ou le groupe netlink avec lequel communiquer. Les familles netlink actuellement attribuées sont :

NETLINK_ROUTE
Reçoit les mises à jour de routage et de liaison et peut être utilisé pour modifier les tables de routage (IPv4 et IPv6), les adresses IP, les paramètres de liaison, les configurations de voisins, les disciplines de mise en file d'attente, les classes de trafic et les classificateurs de paquets (voir rtnetlink(7)).
NETLINK_W1 (Linux 2.6.13 à Linux 2.16.17)
Messages du sous-système 1-wire.
NETLINK_USERSOCK
Réservé aux protocoles de sockets en mode utilisateur.
NETLINK_FIREWALL (jusqu'à et y compris Linux 3.4)
Transporte les paquets IPv4 de netfilter vers l'espace utilisateur. Utilisé par le module noyau ip_queue. Après une longue période d'obsolescence (en faveur de la fonctionnalité plus avancée nfnetlink_queue), NETLINK_FIREWALL a été supprimé dans Linux 3.5.
NETLINK_SOCK_DIAG (depuis Linux 3.3)
Interroge le noyau sur les informations relatives aux sockets de diverses familles de protocoles (voir sock_diag(7)).
NETLINK_INET_DIAG (depuis Linux 2.6.14)
Un synonyme obsolète pour NETLINK_SOCK_DIAG.
NETLINK_NFLOG (jusqu'à et y compris Linux 3.16)
Netfilter/iptables ULOG.
NETLINK_XFRM
IPsec.
NETLINK_SELINUX (depuis Linux 2.6.4)
Notifications d'événements SELinux.
NETLINK_ISCSI (depuis Linux 2.6.15)
Open-iSCSI.
NETLINK_AUDIT (depuis Linux 2.6.6)
Audit.
NETLINK_FIB_LOOKUP (depuis Linux 2.6.13)
Accès à la recherche FIB depuis l'espace utilisateur.
NETLINK_CONNECTOR (depuis Linux 2.6.14)
Connecteur du noyau. Voir Documentation/driver-api/connector.rst (ou /Documentation/connector/connector.* dans les versions 5.2 et antérieures de Linux) dans l'arborescence des sources du noyau Linux pour plus d'informations.
NETLINK_NETFILTER (depuis Linux 2.6.14)
Sous-système Netfilter.
NETLINK_SCSITRANSPORT (depuis Linux 2.6.19)
Transports SCSI.
NETLINK_RDMA (depuis Linux 3.0)
Infiniband RDMA.
NETLINK_IP6_FW (jusqu'à et y compris Linux 3.4)
Transporte les paquets IPv6 de netfilter vers l'espace utilisateur. Utilisé par le module noyau ip6_queue.
NETLINK_DNRTMSG
Messages de routage DECnet.
NETLINK_KOBJECT_UEVENT (depuis Linux 2.6.10)
Messages du noyau vers l'espace utilisateur.
NETLINK_GENERIC (depuis Linux 2.6.15)
Famille générique netlink pour une utilisation simplifiée de netlink.
NETLINK_CRYPTO (depuis Linux 3.2)
Interface Netlink pour demander des informations sur les chiffrements enregistrés auprès de l'API cryptographique du noyau ainsi que pour permettre la configuration de l'API cryptographique du noyau.

Les messages Netlink consistent en un flux d'octets avec un ou plusieurs en-têtes nlmsghdr et une charge utile associée. Le flux d'octets ne doit être accédé qu'avec les macros standard NLMSG_*. Voir netlink(3) pour plus d'informations.

Dans les messages multipartites (plusieurs en-têtes nlmsghdr avec une charge utile associée dans un seul flux d'octets), le premier et tous les en-têtes suivants ont le drapeau NLM_F_MULTI défini, sauf pour le dernier en-tête qui a le type NLMSG_DONE.


struct nlmsghdr {
    __u32 nlmsg_len;    /* Taille du message, en-tête inclus */
    __u16 nlmsg_type;   /* Type de contenu du message */
    __u16 nlmsg_flags;  /* Indicateurs supplémentaires */
    __u32 nlmsg_seq;    /* Numéro de séquence */
    __u32 nlmsg_pid;    /* ID du port de l'expéditeur */
};

nlmsg_type peut être l'un des types de message standard : le message NLMSG_NOOP doit être ignoré, le message NLMSG_ERROR signale une erreur et la charge utile contient une structure nlmsgerr, le message NLMSG_DONE termine un message multipartite. Les messages d'erreur reçoivent la requête originale jointe, sauf si l'utilisateur demande de tronquer le message d'erreur, et reçoivent des données d'erreur supplémentaires si demandé.


struct nlmsgerr {
    int error;        /* Erreur errno négative ou 0 pour les accusés de réception */
    struct nlmsghdr msg;  /* En-tête du message ayant causé l'erreur */
    /*
     * suivi du contenu du message
     * sauf si NETLINK_CAP_ACK était défini
     * ou si l'accusé de réception indique un succès (error == 0).
     * Par exemple, message Generic Netlink avec attributs.
     * la taille du message est alignée avec NLMSG_ALIGN()
     */
    /*
     * suivi de TLV définis dans enum nlmsgerr_attrs
     * si NETLINK_EXT_ACK était défini
     */
};

Une famille netlink spécifie généralement des types de messages supplémentaires, voir les pages de manuel appropriées pour cela, par exemple, rtnetlink(7) pour NETLINK_ROUTE.

Bits d'indicateurs standard dans nlmsg_flags
NLM_F_REQUEST Doit être défini sur tous les messages de requête.
NLM_F_MULTI Le message fait partie d'un message multipartite terminé par NLMSG_DONE .
NLM_F_ACK Demande d'accusé de réception en cas de succès.
NLM_F_ECHO Fait écho à cette requête.
Bits d'indicateurs supplémentaires pour les requêtes GET
NLM_F_ROOT Retourne la table complète au lieu d'une seule entrée.
NLM_F_MATCH Retourne toutes les entrées correspondant aux critères passés dans le contenu du message. Pas encore implémenté.
NLM_F_ATOMIC Retourne un instantané atomique de la table.
NLM_F_DUMP Macro pratique ; équivalent à (NLM_F_ROOT|NLM_F_MATCH).

Notez que NLM_F_ATOMIC nécessite la capacité CAP_NET_ADMIN ou un UID effectif de 0.

NOM

netlink — API de communication inter-processus de Linux

DESCRIPTION

Netlink est un mécanisme de communication inter-processus (IPC) dans le noyau Linux. Il permet aux processus de l'espace utilisateur de communiquer avec le noyau et entre eux. Il est utilisé pour de nombreuses fonctionnalités du noyau, telles que la configuration réseau, la gestion des paquets, le contrôle des ressources, etc.

Les communications Netlink sont basées sur des sockets. Les sockets Netlink sont créés à l'aide de la famille d'adresses AF_NETLINK. Ils peuvent être utilisés pour la communication unicast (un à un), multicast (un à plusieurs) ou broadcast (un à tous).

Les messages Netlink sont structurés avec un en-tête nlmsghdr suivi de données spécifiques au protocole. L'en-tête contient des informations telles que la longueur du message, le type du message, le drapeau d'identification, le numéro de séquence et l'identifiant du port (PID) de l'expéditeur.

Les types de messages Netlink sont définis par le champ nlmsg_type. Les types commençant par NLMSG_ sont des types génériques utilisés par le sous-système Netlink lui-même. Les autres types sont spécifiques aux familles Netlink utilisées.

Les drapeaux de message Netlink sont définis dans le champ nlmsg_flags de l'en-tête nlmsghdr. Voici quelques drapeaux courants :

NLM_F_REQUEST Le message est une requête.
NLM_F_MULTIPART Le message fait partie d'un message multipart.
NLM_F_ACK Demander une accusé de réception.
NLM_F_ECHO Renvoyer le message à l'expéditeur.

Les drapeaux supplémentaires pour les nouvelles requêtes sont :

NLM_F_REPLACE Remplacer l'objet correspondant existant.
NLM_F_EXCL Ne pas remplacer si l'objet existe déjà.
NLM_F_CREATE Créer l'objet s'il n'existe pas déjà.
NLM_F_APPEND Ajouter à la fin de la liste des objets.

nlmsg_seq et nlmsg_pid sont utilisés pour suivre les messages. nlmsg_pid indique l'origine du message. Notez qu'il n'y a pas de relation 1:1 entre nlmsg_pid et le PID du processus si le message provient d'un socket netlink. Voir la section FORMATS D'ADRESSES pour plus d'informations.

nlmsg_seq et nlmsg_pid sont opaques pour le cœur de Netlink.

Netlink n'est pas un protocole fiable. Il fait de son mieux pour livrer un message à sa/ses destination(s), mais peut abandonner des messages en cas de condition de manque de mémoire ou d'autre erreur. Pour un transfert fiable, l'expéditeur peut demander un accusé de réception au destinataire en définissant le drapeau NLM_F_ACK. Un accusé de réception est un paquet NLMSG_ERROR avec le champ d'erreur défini à 0. L'application doit générer elle-même les accusés de réception pour les messages reçus. Le noyau essaie d'envoyer un message NLMSG_ERROR pour chaque paquet échoué. Un processus utilisateur devrait également suivre cette convention.

Cependant, les transmissions fiables du noyau vers l'espace utilisateur sont impossibles dans tous les cas. Le noyau ne peut pas envoyer de message netlink si le tampon de socket est plein : le message sera abandonné et le noyau et le processus de l'espace utilisateur n'auront plus la même vue de l'état du noyau. Il appartient à l'application de détecter quand cela se produit (via l'erreur ENOBUFS renvoyée par recvmsg(2)) et de se resynchroniser.

Formats d'adresses

La structure sockaddr_nl décrit un client netlink dans l'espace utilisateur ou dans le noyau. Un sockaddr_nl peut être unicast (envoyé uniquement à un pair) ou envoyé à des groupes multicast netlink (nl_groups différent de 0).


struct sockaddr_nl {
    sa_family_t     nl_family;  /* AF_NETLINK */
    unsigned short  nl_pad;     /* Zéro */
    pid_t           nl_pid;     /* Port ID */
    __u32           nl_groups;  /* Masque de groupes multicast */
};

nl_pid est l'adresse unicast du socket netlink. Il est toujours 0 si la destination est dans le noyau. Pour un processus de l'espace utilisateur, nl_pid est généralement le PID du processus propriétaire du socket de destination. Cependant, nl_pid identifie un socket netlink, pas un processus. Si un processus possède plusieurs sockets netlink, alors nl_pid peut être égal à l'identifiant du processus pour au plus un socket. Il existe deux façons d'attribuer nl_pid à un socket netlink. Si l'application définit nl_pid avant d'appeler bind(2), alors il appartient à l'application de s'assurer que nl_pid est unique. Si l'application le définit à 0, le noyau s'occupe de l'attribuer. Le noyau attribue l'identifiant du processus au premier socket netlink que le processus ouvre et attribue un nl_pid unique à chaque socket netlink que le processus crée ultérieurement.

nl_groups est un masque de bits où chaque bit représente un numéro de groupe netlink. Chaque famille netlink a un ensemble de 32 groupes multicast. Lorsque bind(2) est appelé sur le socket, le champ nl_groups dans le sockaddr_nl doit être défini sur un masque de bits des groupes auxquels il souhaite s'abonner. La valeur par défaut pour ce champ est zéro, ce qui signifie qu'aucun multicast ne sera reçu. Un socket peut envoyer des messages en multicast à n'importe lequel des groupes multicast en définissant nl_groups sur un masque de bits des groupes auxquels il souhaite envoyer lors de l'appel à sendmsg(2) ou lors d'un connect(2). Seuls les processus ayant un UID effectif de 0 ou la capacité CAP_NET_ADMIN peuvent envoyer ou s'abonner à un groupe multicast netlink. Depuis Linux 2.6.13, les messages ne peuvent pas être diffusés (broadcast) à plusieurs groupes. Toutes les réponses à un message reçu pour un groupe multicast doivent être renvoyées au PID de l'expéditeur et au groupe multicast. Certains sous-systèmes du noyau Linux peuvent éventuellement autoriser d'autres utilisateurs à envoyer et/ou recevoir des messages. Depuis Linux 3.0, les groupes NETLINK_KOBJECT_UEVENT, NETLINK_GENERIC, NETLINK_ROUTE, et NETLINK_SELINUX permettent à d'autres utilisateurs de recevoir des messages. Aucun groupe ne permet à d'autres utilisateurs d'envoyer des messages.

Options de socket

Pour définir ou obtenir une option de socket netlink, appelez getsockopt(2) pour lire ou setsockopt(2) pour écrire l'option avec l'argument de niveau d'option défini sur SOL_NETLINK. Sauf indication contraire, optval est un pointeur vers un int.

NETLINK_PKTINFO (depuis Linux 2.6.14)
Active les messages de contrôle nl_pktinfo pour les paquets reçus afin d'obtenir le numéro de groupe de destination étendu.
NETLINK_ADD_MEMBERSHIP
NETLINK_DROP_MEMBERSHIP (depuis Linux 2.6.14)
Rejoindre/quitter un groupe spécifié par optval.
NETLINK_LIST_MEMBERSHIPS (depuis Linux 4.2)
Récupère tous les groupes dont un socket est membre. optval est un pointeur vers __u32 et optlen est la taille du tableau. Le tableau est rempli avec l'ensemble complet des membres du socket, et la taille requise du tableau est renvoyée dans optlen.
NETLINK_BROADCAST_ERROR (depuis Linux 2.6.30)
Lorsque non défini, netlink_broadcast() ne signale que les erreurs ESRCH et ignore silencieusement les erreurs ENOBUFS.
NETLINK_NO_ENOBUFS (depuis Linux 2.6.30)
Ce drapeau peut être utilisé par les écouteurs unicast et broadcast pour éviter de recevoir des erreurs ENOBUFS.
NETLINK_LISTEN_ALL_NSID (depuis Linux 4.2)
Lorsqu'il est défini, ce socket recevra des notifications netlink de tous les espaces de noms réseau qui ont un nsid attribué dans l'espace de noms réseau où le socket a été ouvert. Le nsid est envoyé à l'espace utilisateur via des données auxiliaires.
NETLINK_CAP_ACK (depuis Linux 4.3)
Le noyau peut échouer à allouer l'espace nécessaire pour le message d'accusé de réception vers l'espace utilisateur. Cette option supprime la charge utile du message netlink d'origine. L'en-tête du message netlink est toujours inclus, de sorte que l'utilisateur puisse deviner à partir du numéro de séquence quel message a déclenché l'accusé de réception.

VERSIONS

L'interface socket de netlink est apparue pour la première fois sous Linux 2.2.

Linux 2.0 prenait en charge une interface netlink plus primitive basée sur des périphériques (qui est toujours disponible comme option de compatibilité). Cette interface obsolète n'est pas décrite ici.

NOTES

Il est souvent préférable d'utiliser netlink via libnetlink ou libnl plutôt qu'via l'interface noyau de bas niveau.

EXEMPLES

L'exemple suivant crée un socket netlink NETLINK_ROUTE qui s'abonnera aux groupes multicast RTMGRP_LINK (événements de création/suppression/activation/désactivation d'interface réseau) et RTMGRP_IPV4_IFADDR (événements d'ajout/suppression d'adresses IPv4).


struct sockaddr_nl sa;
memset(&sa, 0, sizeof(sa));
sa.nl_family = AF_NETLINK;
sa.nl_groups = RTMGRP_LINK | RTMGRP_IPV4_IFADDR;
fd = socket(AF_NETLINK, SOCK_RAW, NETLINK_ROUTE);
bind(fd, (struct sockaddr *) &sa, sizeof(sa));

L'exemple suivant montre comment envoyer un message netlink au noyau (pid 0). Notez que l'application doit gérer les numéros de séquence des messages afin de suivre de manière fiable les accusés de réception.


struct nlmsghdr *nh;    /* Le nlmsghdr avec la charge utile à envoyer */
struct sockaddr_nl sa;
struct iovec iov = { nh, nh->nlmsg_len };
struct msghdr msg;
msg = { &sa, sizeof(sa), &iov, 1, NULL, 0, 0 };
memset(&sa, 0, sizeof(sa));
sa.nl_family = AF_NETLINK;
nh->nlmsg_pid = 0;
nh->nlmsg_seq = ++sequence_number;
/* Demander un accusé de réception du noyau en définissant NLM_F_ACK */
nh->nlmsg_flags |= NLM_F_ACK;
sendmsg(fd, &msg, 0);

Et le dernier exemple concerne la lecture d'un message netlink.


int size;
/* 8192 pour éviter la troncature du message sur les plateformes avec
   une taille de page > 4096 */
struct nlmsghdr buf[8192/sizeof(struct nlmsghdr)];
struct iovec iov = { buf, sizeof(buf) };
struct sockaddr_nl sa;
struct msghdr msg;
struct nlmsghdr *nh;
msg = { &sa, sizeof(sa), &iov, 1, NULL, 0, 0 };
size = recvmsg(fd, &msg, 0);
for (nh = (struct nlmsghdr *) buf; NLMSG_OK (nh, size);
     nh = NLMSG_NEXT (nh, size)) {
    /* La fin du message multipart */
    if (nh->nlmsg_type == NLMSG_DONE)
        return;
    if (nh->nlmsg_type == NLMSG_ERROR)
        /* Faire une gestion d'erreur */
    ...
    /* Continuer avec l'analyse de la charge utile */
    ...
}
