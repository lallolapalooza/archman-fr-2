NETSNIFF-NG(8) Toolkit netsniff-ng NETSNIFF-NG(8)

NOM

netsniff-ng - la bête de capture de paquets

SYNTAXE

netsniff-ng { [options] [expression-de-filtre] }

DESCRIPTION

netsniff-ng est un outil rapide et minimal pour analyser les paquets réseau, capturer des fichiers pcap, rejouer des fichiers pcap et rediriger du trafic entre interfaces à l'aide de sockets de paquets (7) sans copie. netsniff-ng utilise les interfaces spécifiques Linux RX_RING et TX_RING pour effectuer le transfert sans copie. Ceci afin d'éviter la copie et la surcharge des appels système entre l'espace d'adressage du noyau et de l'utilisateur. Lorsque nous avons commencé à travailler sur netsniff-ng, la bibliothèque pcap(3) n'utilisait pas cette fonctionnalité sans copie.

netsniff-ng est spécifique à Linux, ce qui signifie qu'il n'y a pas de support pour d'autres systèmes d'exploitation. Par conséquent, nous pouvons maintenir l'empreinte du code assez minimale et ciblée. Les sockets de paquets (7) Linux et ses interfaces RX_RING et TX_RING contournent le chemin de traitement normal des paquets à travers la pile réseau. C'est la performance de capture ou de transmission la plus rapide que l'on puisse obtenir depuis l'espace utilisateur dès la sortie de la boîte, sans avoir à charger des modules noyau tiers non supportés ou non intégrés au noyau principal. Nous refusons explicitement de construire netsniff-ng sur ntop/PF_RING. Non pas parce que nous ne l'aimons pas (nous le trouvons intéressant), mais parce qu'il ne fait pas partie du noyau principal. Par conséquent, le projet ntop doit maintenir et synchroniser des pilotes hors arbre pour les adapter à son ADN. Finalement, nous avons opté pour un noyau Linux non altéré, car son code a un taux plus élevé de revue, de maintenance, de sécurité et de corrections de bugs.

netsniff-ng prend également en charge le filtrage précoce des paquets dans le noyau. Il supporte les filtres de paquets de bas niveau et de haut niveau qui sont traduits en instructions Berkeley Packet Filter.

netsniff-ng peut capturer des fichiers pcap dans plusieurs formats pcap différents qui sont interopérables avec d'autres outils. Les méthodes d'E/S pcap suivantes sont supportées pour une capture efficace sur disque : scatter-gather, mmap(2), read(2) et write(2). netsniff-ng est également capable de faire pivoter les fichiers pcap en fonction de la taille des données ou des intervalles de temps, ce qui en fait un outil backend utile pour une analyse de trafic ultérieure.

netsniff-ng prend également en charge l'analyse, la relecture et le dumpage des trames brutes 802.11. Pour l'analyse en ligne ou hors ligne, netsniff-ng dispose d'un disséctor de paquets intégré pour les 802.3 (Ethernet) actuels, 802.11* (WLAN), ARP, MPLS, 802.1Q (VLAN), 802.1QinQ, LLDP, IPv4, IPv6, ICMPv4, ICMPv6, IGMP, TCP et UDP, y compris l'analyse de localisation GeoIP. Comme netsniff-ng n'établit aucun état ni ne procède à un réassemblage lors de la dissection des paquets, son empreinte mémoire est assez faible, ce qui rend netsniff-ng très efficace pour l'analyse hors ligne de fichiers pcap volumineux.

Notez que netsniff-ng n'est actuellement pas multithreadé. Cependant, cela ne vous empêche pas de démarrer plusieurs instances de netsniff-ng ancrées sur des CPU différents et non chevauchants et, par exemple, avec des filtres BPF distincts. Il est probable qu'à un moment donné, votre disque dur devienne un goulot d'étranglement, en supposant que vous ne fassiez pas pivoter ces pcap en RAM (et de là, périodiquement déplacé vers des supports plus lents). Vous pouvez alors utiliser mergecap(1) pour transformer tous les fichiers pcap en un seul gros fichier pcap. Ainsi, netsniff-ng fonctionnera éventuellement en multithread.

netsniff-ng peut également être utilisé pour déboguer le trafic netlink.

OPTIONS

-i <dev|pcap|->, -d <dev|pcap|->, --in <dev|pcap|->, --dev <dev|pcap|->
Définit un périphérique d'entrée. Il peut s'agir d'un périphérique réseau, d'un fichier pcap ou de l'entrée standard ("-"). Dans le cas d'un fichier pcap, le type pcap (option -D) est déterminé automatiquement par le magic des fichiers pcap. Dans le cas de l'entrée standard, on suppose que le flux d'entrée est un fichier pcap. Si le type de lien pcap est Netlink et le type pcap est au format par défaut (usec ou nsec), chaque paquet sera enveloppé avec un en-tête cuisiné pcap [2].
-o <dev|pcap|dir|cfg|->, --out <dev|pcap|dir|cfg|->
Définit un périphérique de sortie. Il peut s'agir d'un périphérique réseau, d'un fichier pcap, d'un dossier, d'un fichier de configuration trafgen(8) ou de la sortie standard ("-"). Si le périphérique de sortie est un fichier pcap ou un fichier de configuration trafgen(8), il peut inclure un format horaire tel que défini par strfime(3). S'il est utilisé conjointement avec l'option -F, chaque fichier pivoté aura un horodatage unique. Dans le cas d'un fichier pcap qui ne devrait pas avoir le type pcap par défaut (0xa1b2c3d4), l'option supplémentaire -T doit être fournie. Si un répertoire est donné, alors, au lieu d'un seul fichier pcap, plusieurs fichiers pcap sont générés avec rotation basée sur la taille maximale du fichier ou un intervalle donné (option -F). Optionnellement, l'envoi du signal SIGHUP au processus netsniff-ng provoque une rotation prématurée du fichier. Un fichier de configuration trafgen ne peut actuellement être spécifié que si le périphérique d'entrée est un fichier pcap. Pour spécifier un fichier pcap comme périphérique de sortie, le nom du fichier doit avoir ".pcap" comme extension. Si la sortie standard est donnée comme périphérique, alors une configuration trafgen sera écrite sur la sortie standard si le périphérique d'entrée est un fichier pcap, ou un fichier pcap si le périphérique d'entrée est un périphérique réseau. Si le périphérique d'entrée est un périphérique de surveillance Netlink et que le type pcap est par défaut (usec ou nsec), chaque paquet sera enveloppé avec un en-tête cuisiné pcap [2] pour conserver le numéro de famille Netlink (les types pcap de Kuznetzov et netsniff-ng contiennent déjà le numéro de famille dans le champ du numéro de protocole).
-C <id>, --fanout-group <id>
Si plusieurs instances de netsniff-ng sont lancées et partagent le même identifiant de groupe de diffusion de paquets (fanout group id), le trafic réseau entrant capturé est distribué/équilibré entre ces participants du groupe. Cela permet une meilleure mise à l'échelle que l'exécution multiple de processus netsniff-ng sans paramètre de groupe de diffusion en parallèle, mais seulement avec un filtre BPF attaché, car un paquet devrait sinon être délivré à tous les processus capturant, au lieu d'une fois seulement à un membre de ce groupe de diffusion. Naturellement, chaque membre du groupe de diffusion peut avoir ses propres filtres BPF attachés.
-K <hash|lb|cpu|rnd|roll|qm>, --fanout-type <hash|lb|cpu|rnd|roll|qm>
Ce paramètre spécifie la discipline de diffusion (fanout discipline), en d'autres termes, comment le trafic réseau capturé est dispatché aux membres du groupe de diffusion. Les options sont de distribuer le trafic par hachage de paquet ("hash"), de manière circulaire ("lb"), par le CPU sur lequel le paquet est arrivé ("cpu"), de manière aléatoire ("rnd"), en faisant tourner les sockets ("roll") ce qui signifie que si la file d'attente d'un socket est pleine, on passe au suivant, ou par le mappage de la file d'attente matérielle de la carte réseau ("qm").
-L <defrag|roll>, --fanout-opts <defrag|roll>
Définit des options auxiliaires de diffusion à utiliser en plus d'un type de diffusion donné. Ces options s'appliquent à n'importe quel type de diffusion. Dans le cas de "defrag", le noyau est invité à défragmenter les paquets avant de les livrer à l'espace utilisateur, et "roll" fournit la même option de rotation que le type de diffusion "roll", de sorte que, avec tout autre type de diffusion utilisé (par exemple, "qm"), le socket peut temporairement passer au membre suivant du groupe de diffusion si celui d'origine a la file d'attente pleine.
-f, --filter <bpf-file|-|expr>
Spécifie de ne pas sauvegarder tout le trafic, mais de filtrer la "foin" des paquets réseau. Comme filtre, un fichier compilé par bpfc(8)/stdin peut être passé en paramètre ou une expression de type filtre tcpdump(1) entre guillemets. Pour plus de détails sur le fichier bpf, consultez bpfc(8), pour les détails sur un filtre de type tcpdump(1), consultez la section "exemple de filtre" ou pcap-filter(7). Une expression de filtre peut également être passée à netsniff-ng sans l'option -f au cas où aucune option ne suivrait après l'expression du filtre en ligne de commande.
-t, --type <type>
Ceci définit une sorte de mécanisme de filtrage en termes d'adressage. Les valeurs possibles pour type sont "host" (vers nous), "broadcast" (à tous), "multicast" (vers le groupe), “all” (à tout le monde).
« autres » (mode promiscuous) ou « sortant » (depuis nous).
-F, --interval <taille|temps>
Si le périphérique de sortie est un dossier, avec « -F », il est possible de définir l'intervalle de rotation des fichiers pcap, soit en termes de taille, soit en termes de temps. Ainsi, lorsque la limite d'intervalle est atteinte, un nouveau fichier pcap sera créé. Comme paramètre de taille, les valeurs suivantes sont acceptées : « <num>KiB/MiB/GiB » ; Comme paramètre de temps, il peut s'agir de « <num>s/sec/min/hrs ».
-J, --jumbo-support
Par défaut, en mode de relecture ou de redirection pcap, les trames de la mémoire tampon circulaire de netsniff-ng ont une taille fixe de 2048 octets. Cela signifie que si vous vous attendez à ce que des trames jumbo, voire des super trames jumbo, traversent votre réseau, vous devez activer la prise en charge de celles-ci en utilisant cette option. Cependant, cela a l'inconvénient d'une dégradation des performances et d'une empreinte mémoire plus importante pour la mémoire tampon circulaire. Notez que cela n'affecte pas le mode de capture (pcap), car tpacket en version 3 est utilisé !
-R, --rfraw
Dans le cas où le périphérique réseau d'entrée ou de sortie est un périphérique sans fil, il est possible avec netsniff-ng de le transformer en mode moniteur et de créer un périphérique mon<X> sur lequel netsniff-ng écoutera au lieu de wlan<X>, par exemple. Cela permet à netsniff-ng d'analyser, de sauvegarder, ou même de rejouer des trames 802.11 brutes.
-n <0|uint>, --num <0|uint>
Traiter un nombre de paquets puis quitter. Si le nombre de paquets est 0, cela équivaut à un nombre infini de paquets, c'est-à-dire un traitement jusqu'à interruption. Sinon, un nombre donné sous forme d'entier non signé limitera le traitement.
-O <N>, --overwrite <N>
Un nombre de 0 à N-1 sera utilisé dans le nom de fichier au lieu d'un horodatage Unix. Le fichier précédent sera écrasé lorsque le nombre fera un cycle. La valeur maximale est 2^32 - 1. Destiné à la rotation des fichiers de capture lorsqu'il est utilisé avec les options -F et -P.
-P <nom>, --prefix <nom>
Lors de la sauvegarde de fichiers pcap dans un dossier, un préfixe de nom de fichier peut être défini avec cette option. Sauf indication contraire, le préfixe par défaut est « dump- » suivi d'un horodatage Unix. Utilisez « --prefex "" » pour définir le nom de fichier comme les secondes depuis l'Époque Unix, par exemple 1369179203.pcap
-T <pcap-magic>, --magic <pcap-magic>
Spécifier un type pcap pour le stockage. Différents types pcap avec leurs diverses capacités de métadonnées sont affichés avec l'option -D. Sauf indication contraire, le pcap-magic 0xa1b2c3d4, également connu sous le nom de format pcap standard compatible tcpdump, est utilisé. Les fichiers Pcap avec endianness inversée sont également pris en charge.
-D, --dump-pcap-types
Sauvegarder tous les types pcap disponibles avec leurs capacités et leurs numéros magiques qui peuvent être utilisés avec l'option « -T » sur la sortie standard et quitter.
-B, --dump-bpf
Si un filtre de paquets Berkeley est fourni, par exemple via l'option « -f », alors désassembler et afficher le BPF sur la sortie standard lors de la configuration de la mémoire tampon circulaire. Ceci est uniquement à des fins d'information ou de vérification.
-r, --rand
Si le périphérique d'entrée et de sortie sont tous deux des périphériques réseau, alors cette option randomisera l'ordre des paquets dans la mémoire tampon circulaire de sortie.
-M, --no-promisc
L'interface réseau ne sera pas mise en mode promiscuous. Par défaut, le mode promiscuous est activé.
-N, --no-hwtimestamp
Désactiver la prise d'horodatages matériels pour les paquets RX. Par défaut, si le périphérique réseau prend en charge l'horodatage matériel, les horodatages matériels seront utilisés lors de l'écriture des paquets dans les fichiers pcap. Cette option désactive ce comportement et force l'utilisation d'horodatages logiciels (basés sur le noyau), même si des horodatages matériels sont disponibles.
-A, --no-sock-mem
Au démarrage et à l'arrêt, netsniff-ng tente d'augmenter les tampons de lecture et d'écriture des sockets si nécessaire. Cette option empêchera netsniff-ng de le faire.
-m, --mmap
Utiliser mmap(2) comme I/O de fichier pcap. C'est le comportement par défaut lors de la relecture de fichiers pcap.
-G, --sg
Utiliser le scatter-gather comme I/O de fichier pcap. C'est le comportement par défaut lors de la capture de fichiers pcap.
-c, --clrw
Utiliser une I/O read(2) et write(2) plus lente. Ce n'est pas le cas par défaut partout, mais dans certaines situations, cela pourrait être préférable car cela a une latence plus faible sur l'écriture sur disque.
-S <taille>, --ring-size <taille>
Définir manuellement la taille de la mémoire tampon circulaire RX ou TX en « <num>KiB/MiB/GiB ». Par défaut, la taille est déterminée en fonction du taux de connectivité réseau.
-k <uint>, --kernel-pull <uint>
Définir manuellement l'intervalle en microsecondes pendant lequel le noyau doit être déclenché pour traiter par lots les trames de la mémoire tampon circulaire. Par défaut, c'est toutes les 10 µs, mais cela peut être prolongé manuellement, par exemple.
-b <cpu>, --bind-cpu <cpu>
Ancrer netsniff-ng à un CPU spécifique et également ancrer ou migrer l'affinité CPU de l'IRQ de la carte réseau vers ce CPU. Cette option doit être préférée en combinaison avec -s dans le cas où un débit de paquets moyen à élevé est attendu.
-u <uid>, --user <uid> ou -g <gid>, --group <gid>
Après la configuration de la mémoire tampon circulaire, abandonner les privilèges à un utilisateur/groupe non root.
-H, --prio-high
Définir ce processus comme un processus à haute priorité afin d'obtenir un taux d'ordonnancement plus élevé ou un temps CPU plus important. Ce n'est cependant pas le réglage par défaut, car cela pourrait entraîner la famine d'autres processus, par exemple des threads du noyau à basse priorité.
-Q, --notouch-irq
Ne pas réaffecter les paramètres d'affinité CPU de l'IRQ de la carte réseau.
-s, --silent
Ne pas entrer du tout dans le décodeur de paquets et n'afficher aucune information de paquet dans le terminal. Tais-toi et sois silencieux. Cette option doit être préférée en combinaison avec l'enregistrement ou la relecture pcap, car elle ne saturera pas votre terminal, ce qui entraîne une dégradation significative des performances.
-q, --less
Afficher des informations moins détaillées sur une seule ligne pour chaque paquet dans le terminal.
-X, --hex
Afficher uniquement les paquets au format hexadécimal dans le terminal.
-l, --ascii
Afficher uniquement les caractères imprimables ASCII.
-U, --update
Si la localisation géographique IP est utilisée, le mécanisme de mise à jour de la base de données intégré sera invoqué pour obtenir la dernière base de données de Maxmind. Pour configurer les emplacements de recherche des bases de données, le fichier /etc/netsniff-ng/geoip.conf contient des adresses possibles. Ainsi, pour économiser de la bande passante ou pour miroiter les bases de données de Maxmind (pour contourner leur politique de limitation de trafic), différents hôtes ou adresses IP peuvent être placés dans geoip.conf, séparés par un saut de ligne.
-w, --cooked
Remplacer chaque en-tête de liaison de trame par un en-tête « cooked » de Linux [3] qui conserve des informations sur le type de liaison et le protocole. Il permet de sauvegarder et de décoder des trames capturées à partir de différents types de liaisons lorsque -i « any » a été spécifié, par exemple.
-V, --verbose
Être plus verbeux au démarrage, c'est-à-dire afficher des informations détaillées sur la configuration de la mémoire tampon circulaire.
-v, --version
Afficher les informations de version et quitter.
-h, --help
Afficher l'aide utilisateur et quitter.

EXEMPLE D' UTILISATION

netsniff-ng
La commande la plus simple est d'exécuter simplement « netsniff-ng ». Cela démarre l'écoute sur tous les périphériques réseau disponibles en mode promiscuous et affiche la sortie du décodeur de paquets dans le terminal. Aucun fichier ne sera enregistré.
netsniff-ng --in eth0 --out dump.pcap -s -T 0xa1e2cb12 -b 0 tcp or udp
Capturer le trafic TCP ou UDP du périphérique réseau eth0 dans le fichier pcap nommé dump.pcap, qui contient des extensions pcap spécifiques à netsniff-ng (voir « netsniff-ng -D » pour les capacités). De plus, ne pas afficher le contenu dans le terminal et ancrer le processus et l'affinité IRQ de la carte réseau au CPU 0. La méthode d'écriture pcap est le scatter-gather I/O.
netsniff-ng --in wlan0 --rfraw --out dump.pcap --silent --bind-cpu 0
Mettre le périphérique wlan0 en mode surveillance et capturer toutes les trames brutes 802.11 dans le fichier dump.pcap. Ne pas décoder et afficher le contenu dans le terminal et ancrer le processus et l'affinité IRQ de la carte réseau au CPU 0. La méthode d'écriture pcap est le scatter-gather I/O.
netsniff-ng --in dump.pcap --mmap --out eth0 -k1000 --silent --bind-cpu 0
Rejouer le fichier pcap dump.pcap qui est lu via l'I/O mmap(2) et envoyer les paquets via le périphérique réseau eth0. Ne pas décoder et afficher le contenu dans le terminal et ancrer le processus et l'affinité IRQ de la carte réseau au CPU 0. De plus, déclencher le noyau toutes les 1000 µs pour parcourir le TX_RING au lieu de toutes les 10 µs. Notez que le type magique pcap est détecté automatiquement à partir de l'en-tête du fichier pcap.
netsniff-ng --in eth0 --out eth1 --silent --bind-cpu 0 --type host -r
Rediriger le trafic réseau du périphérique réseau eth0 vers eth1 pour le trafic destiné à notre hôte, ignorant ainsi le trafic broadcast, multicast et promiscuous. Randomiser l'ordre des paquets pour le périphérique sortant et ne pas afficher le contenu des paquets dans le terminal. De plus, ancrer le processus et l'affinité IRQ de la carte réseau au CPU 0.
netsniff-ng --in team0 --out /opt/probe/ -s -m --interval 100MiB -b 0
Capturer sur un périphérique réseau agrégé team0 et sauvegarder les paquets dans plusieurs fichiers pcap qui sont divisés en 100 MiB chacun. Utiliser l'I/O mmap(2)

NAME

netsniff-ng

high performance, easy to use, fat free, offline network sniffer

SYNOPSIS

netsniff-ng [-a|-A|-g|-G|-i|-I|-p|-P] [-b buffersize] [-c packets] [-d cpu] [-e] [-f filter] [-l pcapdir] [-L] [-n] [-o pcapfile] [-s] [-S] [-T] [-t pid] [-u uid] [-v] [-w maxfiles] [-W maxsize] [-Z devidx] interface

DESCRIPTION

The netsniff-ng toolkit is a set of free and open-source tools for a network analysis. It's a feature-rich toolkit for the daily tasks of network protocol analysis. netsniff-ng is the packet capture daemon of the toolkit.

Its main focus is to provide a powerful packet capturing infrastructure which is suitable for a wide variety of use cases. This includes sniffing on a local machine, sniffing traffic across a LAN using ARP spoofing, or sniffing traffic from remote locations through the use of network taps or SPAN/mirror ports.

The netsniff-ng daemon itself is designed to be extremely fast and efficient. It uses modern Linux kernel features like AF_PACKET with zero-copy RX_RING support, TPACKET_V3, and BPF filters to achieve high capture rates with minimal CPU utilization.

By default, netsniff-ng captures packets from the specified network interface and writes them to standard output in pcap format. This output can be piped to other tools like text2pcap, mergecap (from Wireshark), or used to replay traffic with tcpreplay.

Optionally, netsniff-ng can write pcap files directly to disk, in a specified directory, potentially rotating them based on size or count.

OPTIONS

-a, --arp-spoof
Enables ARP spoofing mode. This will redirect all traffic from the specified network interface to the host running netsniff-ng. This is useful for sniffing traffic on a LAN without needing a dedicated network tap or SPAN port. Be careful, as incorrect usage can disrupt network connectivity.
-A, --arp-spoof-aggressive
Enables aggressive ARP spoofing mode. In this mode, netsniff-ng will continuously send ARP replies to both the target IP address and the gateway IP address, ensuring that the traffic is reliably redirected. This is more disruptive than standard ARP spoofing but can be more effective in certain network environments.
--buffersize buffersize
Sets the size of the packet capture buffer. A larger buffer can improve performance by reducing the chance of packet drops, especially under high load. The size is specified in bytes. Default is 1MB.
--count packets
Captures only the specified number of packets and then exits.
--cpu cpu
Binds the packet capture process to a specific CPU core. This can help reduce cache contention and improve performance by dedicating a core to packet capture. Use -1 to disable CPU affinity.
--etherbreak
When using ARP spoofing, this option will cause netsniff-ng to send an Ethernet Frame with length 0x0000. This may be used to break certain network equipment that might otherwise handle spoofed frames incorrectly.
--filter filter
Applies a BPF (Berkeley Packet Filter) filter to capture only the desired packets. This can significantly reduce the amount of data captured and improve performance. For more information on BPF filters, refer to the bpfc(8) man page.
-g, --gateway-redirect
Redirects all traffic destined for the gateway to the host running netsniff-ng. This is a simpler form of ARP spoofing that only targets the gateway, effectively making the sniffing machine act as a transparent proxy for outbound traffic.
-G, --gateway-redirect-aggressive
Aggressive version of --gateway-redirect. Continuously sends ARP replies to the gateway, ensuring traffic redirection.
-i, --inbound-only
Only capture inbound traffic on the specified interface. This is useful when you are only interested in packets coming *to* the machine and not leaving it.
-I, --outbound-only
Only capture outbound traffic on the specified interface. This is useful when you are only interested in packets going *from* the machine and not coming to it.
--pcapdir pcapdir
Specifies the directory where pcap files will be written. If this option is used, netsniff-ng will not write to standard output.
--log-stats
Logs statistics about packet capture to a file named netsniff-ng.stats in the current directory. These statistics include packet counts, byte counts, and packet drop counts.
--no-promisc
Disables promiscuous mode on the network interface. In promiscuous mode, the network interface captures all packets on the network segment, regardless of their intended destination. Disabling it means the interface will only capture packets specifically addressed to it or broadcast packets.
--out pcapfile
Specifies the output pcap file name. If this option is used, netsniff-ng will not write to standard output. If used in conjunction with --pcapdir, the file will be created inside the specified directory.
-p, --redirect-to
Redirects traffic from the specified network interface to the given IP address and port. This is useful for sending captured traffic to another machine or application for processing.
-P, --redirect-to-port
Redirects traffic from the specified network interface to the given port on the local machine. This is useful for sending captured traffic to a local application listening on that port.
--stats
Prints statistics about packet capture to standard error upon exit. These statistics include packet counts, byte counts, and packet drop counts.
--skip-bpf-filter
Disables the automatic BPF filter application that netsniff-ng typically performs for performance reasons. Use this option if you want to manually specify the BPF filter using -f or if you want to capture all packets without any filtering.
--timestamp-precision
Sets the timestamp precision for captured packets. Available options are: s (seconds), ms (milliseconds), us (microseconds), ns (nanoseconds). Default is microseconds.
--pidfile pid
Writes the PID of the netsniff-ng process to the specified file. This is useful for managing the daemon process.
--uid uid
Drop privileges to the specified user ID (UID) after opening the network interface and buffers. This is a security measure to reduce the potential impact if the netsniff-ng process is compromised.
--verbose
Enables verbose output, which provides more detailed information about the packet capture process. This can be helpful for debugging.
--max-files maxfiles
When writing pcap files to disk (using --pcapdir or --out), this option limits the maximum number of pcap files to create. Once the limit is reached, the oldest file will be overwritten. This is useful for managing disk space.
--max-size maxsize
When writing pcap files to disk, this option sets the maximum size of each pcap file in megabytes. When a file reaches this size, a new file will be created. If used with --max-files, the oldest file will be overwritten when the limit is reached.
--devidx devidx
Specifies the network device index to capture from, instead of the interface name. This can be useful in environments where interface names may change or are not consistently assigned.

USAGE EXAMPLE

To capture traffic on interface eth0 and save it to a file named capture.pcap:


netsniff-ng -i eth0 -o capture.pcap

To capture traffic on interface eth0, only inbound packets, and save them to a directory named /tmp/pcap:


netsniff-ng -i eth0 -I --pcapdir /tmp/pcap

To capture traffic on interface eth0 using ARP spoofing and save it to standard output:


netsniff-ng -i eth0 -a | some_analyzer

To capture traffic from interface eth0 with a BPF filter for TCP port 80, and write statistics to stderr upon exit:


netsniff-ng -i eth0 -f "tcp port 80" --stats

CONFIG FILES

None.

FILTER EXAMPLE

The following BPF filter examples can be used with the -f option:

  • Capture only IP traffic: "ip"
  • Capture only TCP traffic to or from port 80: "tcp port 80"
  • Capture only UDP traffic to or from port 53: "udp port 53"
  • Capture traffic between two specific IP addresses: "host 192.168.1.10 and host 192.168.1.20"
  • Capture traffic to a specific network: "net 192.168.1.0/24"
  • Capture ARP traffic: "arp"

For a comprehensive list of BPF filter syntax, please refer to the bpfc(8) man page.

PCAP FORMATS:

The easiest route is simply to impersonate the local gateway, stealing client traffic en route to some remote destination. Of course, the traffic must be forwarded by your attacking machine, either by enabling kernel IP forwarding or with a userland program that accomplishes the same (fragrouter -B1).

Several people have reportedly destroyed connectivity on their LAN to the outside world by ARP spoofing the gateway, and forgetting to enable IP forwarding on the attacking machine. Do not do this. You have been warned.

A safer option than ARP spoofing would be to use a "port mirror" function if your switch hardware supports it and if you have access to the switch.

If you do not need to dump all possible traffic, you have to consider running netsniff-ng with a BPF filter for the ingress path. For that purpose, read the bpfc(8) man page.

Also, to aggregate multiple NICs that you want to capture on, you should consider using team devices, further explained in libteam resp. teamd(8).

The following netsniff-ng pcap magic numbers are compatible with other tools, at least tcpdump or Wireshark:


0xa1b2c3d4 (tcpdump-capable pcap)
0xa1b23c4d (tcpdump-capable pcap with ns resolution)
0xa1b2cd34 (Alexey Kuznetzov's pcap)

Pcap files with different meta data endianness are supported by netsniff-ng as well.

NOTE

When replaying pcap files, the timing information from the pcap packet header is currently ignored.

Also, when replaying pcap files, demultiplexing traffic among multiple networking interfaces does not work. Currently, it is only sent via the interface that is given by the --out parameter.

When performing traffic capture on the Ethernet interface, the pcap file is created and packets are received but without a 802.1Q header. When one uses tshark, all headers are visible, but netsniff-ng removes 802.1Q headers. Is that normal behavior?

Yes and no. The way VLAN headers are handled in PF_PACKET sockets by the kernel is somewhat “problematic” [1]. The problem in the Linux kernel is that some drivers already handle VLANs, others do not. Those who handle it can have different implementations, such as hardware acceleration and so on. So in some cases the VLAN tag is even stripped before entering the protocol stack, in some cases probably not. The bottom line is that a "hack" was introduced in PF_PACKET so that a VLAN ID is visible in some helper data structure that is accessible from the RX_RING.

Then it gets really messy in the user space to artificially put the VLAN header back into the right place. Not to mention the resulting performance implications on all of libpcap(3) tools since parts of the packet need to be copied for reassembly via memmove(3).

A user reported the following, just to demonstrate this mess: some tests were made with two machines, and it seems that results depend on the driver ...


AR8131:
ethtool -k eth0 gives "rx-vlan-offload: on"
- wireshark gets the vlan header
- netsniff-ng doesn't get the vlan header
ethtool -K eth0 rxvlan off
- wireshark gets a QinQ header even though no one sent QinQ
- netsniff-ng gets the vlan header


RTL8111/8168B:
ethtool -k eth0 gives "rx-vlan-offload: on"
- wireshark gets the vlan header
- netsniff-ng doesn't get the vlan header
ethtool -K eth0 rxvlan off
- wireshark gets the vlan header
- netsniff-ng doesn't get the vlan header

Even if we agreed on doing the same workaround as libpcap, we still will not be able to see QinQ, for instance, due to the fact that only one VLAN tag is stored in the kernel helper data structure. We think that there should be a good consensus on the kernel space side about what gets transferred to userland first.

Update (28.11.2012): the Linux kernel and also bpfc(8) has built-in support for hardware accelerated VLAN filtering, even though tags might not be visible in the payload itself as reported here. However, the filtering for VLANs works reliable if your NIC supports it. See bpfc(8) for an example.
