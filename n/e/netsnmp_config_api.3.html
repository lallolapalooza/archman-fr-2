DESCRIPTION

Les fonctions constituent un système assez extensible pour analyser divers fichiers de configuration au moment de l'exécution d'une application. Le flux de fichiers de configuration est divisé dans les phases suivantes :

1.
Enregistrement des gestionnaires.
2.
Lecture des fichiers de configuration pour les besoins d'analyse pré-MIB.
3.
Lecture et analyse des fichiers MIB textuels.
4.
Lecture des fichiers de configuration pour les directives de configuration.
5.
Optionnellement, relecture des fichiers de configuration à une date ultérieure.

L'idée est que l'application appelante soit capable d'enregistrer des gestionnaires pour certains jetons spécifiés dans certains fichiers de configuration nommés. La fonction read_configs() peut alors être appelée pour rechercher tous les fichiers de configuration pertinents, faire correspondre le premier mot de chaque ligne avec la liste des jetons enregistrés et passer le reste de la ligne au gestionnaire enregistré approprié.

ENREGISTREMENT D'UN GESTIONNAIRE

register_config_handler()
Enregistre une routine de gestionnaire de configuration, qui doit être appelée pour traiter les directives de configuration commençant par le jeton spécifié. Par exemple :
register_config_handler("snmp", "exampleToken", example_handler, NULL, "ARG1 [ARG2]");
enregistrerait la fonction example_handler() afin qu'elle soit appelée chaque fois que le premier mot d'une ligne dans le fichier de configuration snmp.conf correspond à "exampleToken".
L'appel des gestionnaires appropriés pour traiter les directives du fichier de configuration est la responsabilité de read_configs() (voir ci-dessous).
register_const_config_handler()
Similaire à la fonction register_config_handler(), mais la routine d'analyse est explicitement limitée à ne pas modifier la chaîne analysée.
register_prenetsnmp_mib_handler()
Similaire à la fonction register_config_handler(), mais la routine de gestionnaire enregistrée sera appelée avant la lecture des MIB textuels. Ceci est généralement utilisé pour les jetons qui affecteront la configuration de l'analyseur MIB, et ne sera normalement utilisé qu'à l'intérieur de la bibliothèque SNMP elle-même.
register_mib_handlers()
Routine d'initialisation pour enregistrer les gestionnaires de configuration internes de la bibliothèque SNMP.
unregister_config_handler()
Supprime le gestionnaire de configuration enregistré pour le filePrefix et le token spécifiés.
unregister_all_config_handlers()
Supprime tous les gestionnaires de configuration enregistrés.

Gestionnaires de jetons

Les fonctions de gestionnaire doivent avoir la signature suivante :

void handler(const char *token, char *line);
ou
void handler(const char *token, const char *line); br (si enregistré en utilisant register_const_config_handler)

La fonction sera appelée avec deux arguments, le premier étant le jeton qui a déclenché l'appel à cette fonction (c'est-à-dire le jeton utilisé lors de l'enregistrement du gestionnaire), et le second étant le reste de la ligne du fichier de configuration (c'est-à-dire tout ce qui suit l'espace blanc après le jeton correspondant).

Libération des gestionnaires

Si la fonction de gestionnaire de jeton alloue dynamiquement des ressources lors du traitement d'une entrée de configuration, celles-ci peuvent devoir être libérées avant de relire les fichiers de configuration. Si le quatrième paramètre ( releaser ) passé à register_config_handler n'est pas NULL, il spécifie une fonction à appeler avant de relire les fichiers de configuration. Cette fonction doit libérer toutes les ressources allouées par la fonction de gestionnaire de jeton et réinitialiser sa notion de configuration à son état par défaut. La fonction de gestionnaire de jeton peut alors être appelée à nouveau en toute sécurité. Aucun argument n'est passé au gestionnaire de libération de ressources.
Notez que cette fonction n'est pas appelée lorsque le gestionnaire est désenregistré individuellement (mais elle est appelée dans le cadre de unregister_all_config_handlers() ).

Gestionnaires d'application

register_app_config_handler()
Enregistre une routine de gestionnaire de configuration d'application. Ce gestionnaire sera appelé pour le jeton spécifié, mais uniquement si le jeton est trouvé dans un fichier de configuration qui n'est pas préfixé par un nom de fichier de configuration (c'est-à-dire un fichier lu par l'application elle-même, par opposition à ceux lus par la bibliothèque SNMP elle-même).
register_app_prenetsnmp_mib_handler()
Similaire à register_app_config_handler(), mais ce gestionnaire sera appelé avant la lecture des MIB textuels.
unregister_app_config_handler()
Supprime le gestionnaire de configuration d'application enregistré pour le jeton spécifié.

Ces gestionnaires d'application sont utilisés pour les jetons qui ne sont pas associés à un fichier de configuration spécifique comme ceux gérés par register_config_handler(). Les jetons d'application ne sont traités que lors des appels à read_configs().

LECTURE DES FICHIERS DE CONFIGURATION

read_premib_configs()
Lit tous les fichiers de configuration configurés et applique les gestionnaires qui ont été enregistrés à l'aide de register_prenetsnmp_mib_handler() et register_app_prenetsnmp_mib_handler(). Ceci est généralement fait avant que la bibliothèque ne soit complètement initialisée.
read_configs()
Lit tous les fichiers de configuration configurés et applique les gestionnaires qui ont été enregistrés à l'aide de register_config_handler() et register_app_config_handler(). Cela inclut la relecture des fichiers qui ont été lus précédemment, en appelant d'abord la fonction de libération pour chaque gestionnaire enregistré.

RAPPORT D'ERREURS

read_config_print_usage()
Imprime les chaînes d'aide de tous les gestionnaires enregistrés. Le paramètre lead est une chaîne de caractères qui sera imprimée au début de chaque ligne d'aide.
config_pwarn()
Imprime un message d'avertissement formaté (en utilisant la même méthode que printf) sur la sortie d'erreur standard. Le message est préfixé par "Warning: ".
config_perror()
Imprime un message d'erreur formaté (en utilisant la même méthode que printf) sur la sortie d'erreur standard. Le message est préfixé par "Error: ".

EXEMPLE

Voici un exemple simple d'utilisation de l'API de configuration :

#include <net-snmp/config_api.h>
#include <net-snmp/net-snmp-config.h>
#include <stdio.h>

static int my_var = 0;

void my_handler(const char *token, char *line) {
    if (strcmp(token, "myToken") == 0) {
        my_var = atoi(line);
        printf("my_var set to: %d\n", my_var);
    }
}

void my_releaser(void) {
    my_var = 0;
    printf("my_var reset.\n");
}

void print_my_usage(char *lead) {
    printf("%smyToken VAL - Set my_var to VAL\n", lead);
}

int main() {
    // Register the handler
    register_config_handler("myapp", "myToken", my_handler, my_releaser, "VAL");

    // Read configuration files
    read_configs();

    // Print usage information
    read_config_print_usage("Usage:\n");

    // Unregister the handler (optional)
    unregister_config_handler("myapp", "myToken");

    return 0;
}

Si le fichier de configuration contient la ligne suivante :

myToken 123

Alors la sortie sera :

my_var set to: 123
Usage:
myToken VAL - Set my_var to VAL

Après l'appel à read_configs(), vous pouvez appeler read_configs() à nouveau pour relire les fichiers de configuration. Avant cela, la fonction my_releaser() sera appelée pour réinitialiser my_var.

LECTURE DES FICHIERS DE CONFIGURATION

read_premib_configs()
read_configs()
Ces routines traitent les fichiers de configuration trouvés dans le chemin de recherche de configuration (voir ci-dessous). Pour chaque entrée, le gestionnaire enregistré pour ce jeton de configuration est appelé.

read_premib_configs() est exécuté avant la lecture des fichiers MIB et traite les jetons de configuration enregistrés à l'aide de register_prenetsnmp_mib_handler() (ou register_app_prenetsnmp_mib_handler()). Toutes les autres entrées sont ignorées.

read_configs() est exécuté après la lecture des fichiers MIB et traite les jetons de configuration enregistrés à l'aide de register_config_handler() (ou register_app_config_handler()). S'il rencontre un jeton de configuration pour lequel aucun gestionnaire n'a été enregistré (avant ou après les MIB), il affichera un message d'avertissement et continuera le traitement avec la ligne suivante du fichier de configuration.

Chemin de recherche de configuration

Les fichiers de configuration à lire sont trouvés en recherchant dans une liste de répertoires de configuration des fichiers nommés de manière appropriée. Dans chaque répertoire, la bibliothèque recherchera les fichiers nommés snmp.conf, snmp.local.conf, app.conf, app.local.conf,
(où app est le préfixe de fichier spécifique à l'application utilisé pour enregistrer les gestionnaires de configuration). Il n'est pas nécessaire que ces fichiers soient présents dans chaque répertoire. Les fichiers manquants seront ignorés silencieusement.
L'idée derrière les deux suffixes différents est que le premier fichier peut être partagé (via rdist ou un montage NFS) sur un grand nombre de machines et que le second fichier peut être utilisé pour configurer les paramètres locaux d'une machine particulière.

La liste par défaut des répertoires à rechercher est /etc/snmp, suivi de /usr/share/snmp, suivi de /usr/lib/snmp, suivi de $HOME/.snmp. Cette liste peut être modifiée en définissant la variable d'environnement SNMPCONFPATH pour qu'elle soit une liste (séparée par des deux-points) de répertoires à rechercher.

init_snmp()

Le mode de fonctionnement normal consisterait à enregistrer les gestionnaires de configuration spécifiques à l'application, puis à appeler init_snmp(). Cela appellerait les routines listées ci-dessus pour enregistrer les gestionnaires de configuration internes de la bibliothèque, traiter tous les jetons de configuration enregistrés avec register_prenetsnmp_mib_handler(), lire les fichiers MIB textuels à l'aide de init_mib(), et enfin analyser les jetons de fichiers de configuration enregistrés avec register_config_handler().

Si la fonction init_snmp() est utilisée, aucune de ces fonctions ne doit être explicitement appelée par l'application.

CHAÎNES D'AIDE ET ERREURS

Le paramètre usageLine passé à register_config_handler() et aux appels similaires, est utilisé pour afficher des informations d'aide lorsque la fonction read_config_print_usage() est appelée. Cette fonction est utilisée par toutes les applications lorsque le drapeau -H est passé sur la ligne de commande. Elle affiche un résumé de toutes les lignes du fichier de configuration et des fichiers associés que le système de configuration comprend. Le paramètre usageLine doit être une liste d'arguments attendus après le jeton, et non une longue description (qui devrait plutôt aller dans une page de manuel). Le préfixe lead sera ajouté à chaque ligne que la fonction imprime sur stderr, où elle affiche sa sortie.

La fonction init_snmp() doit être appelée avant la fonction read_config_print_usage(), afin que la bibliothèque puisse également enregistrer ses directives de fichier de configuration pour que la fonction read_config_print_usage() les affiche.

Fonctions de gestion des erreurs

Les deux fonctions config_pwarn() et config_perror() prennent toutes deux une chaîne d'erreur comme argument et l'impriment sur stderr avec le fichier et le numéro de ligne qui ont causé l'erreur. Un appel à la seconde fonction forcera également read_configs() à retourner finalement avec un code d'erreur indiquant à la fonction appelante qu'elle doit abandonner l'opération de l'application.

VARIABLES D'ENVIRONNEMENT

SNMPCONFPATH
Une liste de répertoires séparés par des deux-points à rechercher pour trouver les fichiers de configuration. Par défaut :
/etc/snmp:/usr/share/snmp:/usr/lib/snmp:$HOME/.snmp
