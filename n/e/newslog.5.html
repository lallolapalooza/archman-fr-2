NOM

newslog - Description des fichiers journaux de INN

DESCRIPTION

La plupart des fichiers journaux créés par les programmes Usenet résident dans le répertoire pathlog défini dans inn.conf et ont une extension ".log". Plusieurs versions sont généralement conservées avec une extension supplémentaire comme .1, .2, etc. -- le chiffre le plus élevé indique la version la plus ancienne du journal. Ces anciennes versions sont stockées dans pathlog/OLD; elles peuvent être compressées et avoir ainsi une extension ".1.gz", ".2.gz", etc., jusqu'à ".nn.gz" où "nn" est le nombre d'anciens journaux conservés par scanlogs, défini par logcycles dans inn.conf.

Le script scanlogs et les utilitaires associés sont responsables de la rotation et de la compression de ces fichiers. Certains fichiers journaux contiennent toujours des données (comme news.notice), d'autres seulement en cas de problème (comme news.err), et d'autres ne sont créés que si un programme particulier est utilisé (comme send-uucp.log utilisé par send-uucp) ou si un paramètre de configuration est défini (comme innfeed.log utilisé par innfeed lorsque debug-level est défini dans innfeed.conf).

De plus, le script innstat surveille la taille de tous les fichiers journaux.

Voici les fichiers journaux utilisés par INN :

control.log
Ce fichier maintient un compte du nombre de messages de contrôle newgroup et rmgroup vus pour chaque groupe de nouvelles. Le compte correspond au nombre de messages de contrôle avec les arguments indiqués, qu'ils aient été traités ou non. Tous les arguments de contrôle, y compris les invalides, sont comptés. Voici un exemple de lignes que l'on peut trouver dans ce fichier journal : 
3 Control: newgroup foo.bar moderated
3 Control: rmgroup misc.removed
1 Control: newgroup misc.created

Ce fichier est mis à jour par tally.control, qui est appelé par scanlogs si l'un de ces deux fichiers journaux existe dans pathlog :

newgroup.log
rmgroup.log

Ces deux fichiers journaux contiennent une ligne de résumé décrivant le message de contrôle et l'action effectuée par controlchan, suivie de l'article indenté de quatre espaces, et une ligne vide. Alors que ces fichiers subissent une rotation, control.log n'en subit pas afin de conserver le compte des messages de contrôle vus.

Notez que d'autres fichiers journaux de contrôle sont également soumis à une rotation par scanlogs, s'ils existent, mais leur contenu n'est pas résumé. Voici leurs noms :

checkgroups.log
default.log
ihave.log
miscctl.log
sendme.log
sendsys.log
senduuname.log
version.log

Pour créer ces fichiers, les champs <type> et <action> des entrées pertinentes de control.ctl doivent être correctement définis. Par exemple :

Type            Action              Meaning
----            ------              -------
all             log=miscctl         Log all messages by default.
newgroup        doit=newgroup       Create group and log message.
newgroup        log=newgroup        Log message.
rmgroup         verify-*=rmgroup    PGP verify, remove group
                                    and log message.
checkgroups     doit=checkgroups    Process and log message.
controlbatch.log
Le programme controlbatch ajoute tous les messages de statut à ce fichier. Il est soumis à une rotation par scanlogs.
errlog
Ce fichier contient la sortie standard et l'erreur standard de tout programme lancé par innd, comme les flux de canaux configurés dans newsfeeds. Ce fichier doit normalement être vide. scanlogs imprimera les 50 premières lignes de ce fichier journal s'il n'est pas vide, afin qu'elles apparaissent dans les rapports quotidiens de Usenet générés par news.daily. Ensuite, scanlogs effectue une rotation de ce fichier journal.
expire.log
Par défaut, lorsque news.daily s'apprête à expirer de vieux articles de nouvelles, il écrit le nom du programme qu'il invoque, suivi de "start" et de l'heure de début. Toute sortie de ce programme est ensuite écrite, indentée de quatre espaces. Puis, le nom du programme est écrit, suivi de "end" et de l'heure de fin.

Les programmes appelés, si nécessaire, sont dans l'ordre : expireover, ctlinnd (avec l'option "lowmark"), expirerm et expire. Les articles supprimés sont listés dans expire.list et les marques basses pour chaque groupe de nouvelles (c'est-à-dire le numéro de l'article le plus ancien disponible dans le groupe de nouvelles) dans expire.lastlowmark.

Après le processus d'expiration, scanlogs effectue une rotation de expire.log.

innfeed.log
Lorsque debug-level est défini dans innfeed.conf, innfeed ajoute des messages de débogage à ce fichier. Notez que le nom de ce fichier peut être modifié avec le paramètre log-file dans innfeed.conf. Quoi qu'il en soit, le fichier journal approprié est soumis à une rotation par scanlogs.

De plus, le fichier innfeed-delayed.conf est également consulté pour trouver un autre fichier journal potentiel à faire pivoter lorsque delayer(8) est utilisé avec innfeed.

innfeed enregistre également son état dans innfeed.status (ou le nom défini dans status-file) si gen-html est défini sur false, mais ce fichier journal n'est pas traité par scanlogs.

news
Ce fichier enregistre les articles reçus par innd. Les lignes typiques sont : 
Aug 25 13:37:41.839 + news.server.fr <cancel.4066@foo.com>
    1658 a.peer other.server.org inpaths!
Aug 25 13:37:41.839 c news.server.fr <cancel.4066@foo.com>
    Cancelling <m070725@foo.com>
Aug 25 13:37:54.638 - a.peer <23k82@bar.net> 437 Poison newsgroup

La première indique qu'un article de "news.server.fr" a été accepté ("+"). Son Message-ID est "<cancel.4066@foo.com>" et nous enverrons l'article à deux pairs ("a.peer" et "other.server.org", comme spécifié dans newsfeeds) et "inpaths!" (voir ninpaths pour plus de détails à ce sujet). La deuxième ligne mentionne que l'article précédent est un message d'annulation ("c") pour "<m070725@foo.com>" et qu'il a été traité (en effet, controlchan traite tous les articles de contrôle sauf les annulations qui sont gérées par innd). La troisième ligne indique que l'article dont le Message-ID est "<23k82@bar.net>" a été rejeté ("-") car il a été posté dans un groupe de nouvelles empoisonné (un filtre Perl ou Python situé dans pathfilter doit avoir provoqué ce rejet).

Voir la section "LOGGING" de la page de manuel innd(8) pour plus d'informations sur le format de ce fichier journal.

innreport résume les articles rejetés signalés dans ce fichier et scanlogs le fait pivoter.

news.crit
Tous les messages d'erreur critiques émis par innd sont ajoutés à ce fichier via syslog. Ce fichier journal doit normalement être vide. scanlogs imprimera les 50 premières lignes de ce fichier journal s'il n'est pas vide, afin qu'elles apparaissent dans les rapports quotidiens de Usenet générés par news.daily. Ensuite, scanlogs effectue une rotation de ce fichier journal.

Vous devriez avoir la ligne suivante dans le fichier syslog.conf de votre système, en utilisant un caractère de tabulation comme délimiteur :

news.crit           <pathlog>/news.crit

(Une entrée typique est montrée ; elle doit correspondre à pathlog dans inn.conf et être délimitée par des tabulations.)

news.err
Tous les messages d'erreur majeurs émis par innd sont ajoutés à ce fichier via syslog. Ce fichier journal doit normalement être vide. scanlogs imprimera les 50 premières lignes de ce fichier journal s'il n'est pas vide, afin qu'elles apparaissent dans les rapports quotidiens de Usenet générés par news.daily. Ensuite, scanlogs effectue une rotation de
ce fichier journal.

Vous devriez avoir la ligne suivante dans votre fichier syslog.conf système, en utilisant un caractère de tabulation comme délimiteur:

news.err            <pathlog>/news.err

(Une entrée typique est montrée; elle devrait correspondre à pathlog dans inn.conf et être séparée par des tabulations.)

news.notice
Tous les messages d'erreur standard et les messages de statut émis par innd, innfeed, nnrpd et d'autres programmes sont ajoutés à ce fichier via syslog. scanlogs utilise le script Perl innreport pour résumer ce fichier. innreport imprimera également les max_unknown premières lignes inconnues de ce fichier journal si des lignes non reconnues sont trouvées dans news.notice afin qu'elles apparaissent dans les rapports quotidiens de Usenet générés par news.daily. Ce paramètre peut être configuré dans innreport.conf. Ensuite, scanlogs fait pivoter ce fichier journal.

Vous devriez avoir la ligne suivante dans votre fichier syslog.conf système, en utilisant un caractère de tabulation comme délimiteur:

news.notice         -<pathlog>/news.notice

(Une entrée typique est montrée; elle devrait correspondre à pathlog dans inn.conf et être séparée par des tabulations.)

Le signe moins comme premier caractère du chemin vers news.notice demande à syslogd de ne pas synchroniser le fichier journal sur le disque à chaque nouvelle entrée de journal (cela dégrade sinon les performances). Selon le démon syslog que vous utilisez, la synchronisation des journaux peut déjà être désactivée par défaut (c'est par exemple le cas pour rsyslogd ou syslog-ng).

nntpsend.log
Le programme nntpsend ajoute tous les messages de statut à ce fichier. Il est géré par rotation par scanlogs.
perl-nocem.log
Le programme perl-nocem ajoute tous les messages de statut à ce fichier si la facilité syslog n'est pas disponible ou si l'option -l est passée à perl-nocem (sinon, la facilité syslog est utilisée auquel cas les messages de statut sont ajoutés à un fichier nommé généralement news.notice dans pathlog). Le fichier perl-nocem.log est traité par innreport et géré par rotation par scanlogs.
send-ihave.log
Le programme send-ihave ajoute tous les messages de statut à ce fichier. Il est géré par rotation par scanlogs.
send-uucp.log
Le programme send-uucp ajoute tous les messages de statut à ce fichier. Il est géré par rotation par scanlogs.
unwanted.log
Ce journal maintient un décompte du nombre d'articles qui ont été rejetés parce qu'ils ont été postés dans des groupes de discussion qui n'existent pas sur le site local. Ce fichier est mis à jour par innreport lors du traitement du fichier journal news.notice et il est maintenu dans l'ordre numérique inversé (le groupe rejeté le plus populaire en premier). Ce fichier n'est pas géré par rotation afin de conserver le décompte des articles postés dans des groupes de discussion qui sont absents du fichier active du serveur de news.

Notez que logtrash doit être défini sur true dans inn.conf pour que ce fichier soit généré.

Enfin, ces fichiers sont également gérés par rotation par scanlogs, s'ils existent, mais leur contenu n'est pas résumé. Voici leurs noms:

badcontrol.log
badpgp.log
failedpgp.log

Ils peuvent être utilisés par les programmes qui vérifient les articles PGP.
