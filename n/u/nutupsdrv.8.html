NUTUPSDRV(8) Manuel NUT NUTUPSDRV(8)

NOM

nutupsdrv - Manuel générique pour les pilotes UPS unifiés

SYNTAXE

nutupsdrv -h

nutupsdrv [OPTIONS]

DESCRIPTION

nutupsdrv n'est pas réellement un pilote. Il s'agit d'une page de manuel combinée pour le code partagé qui constitue le cœur de nombreux pilotes au sein du package Network UPS Tools.

Pour plus d'informations sur les pilotes spécifiques, consultez leurs pages de manuel individuelles.

Les pilotes UPS fournissent un canal de communication entre le matériel UPS physique et le serveur upsd(8). Le pilote est responsable de la traduction du protocole natif de l'UPS vers le format commun utilisé par le reste de ce package.

Le noyau a trois modes de fonctionnement qui sont déterminés par les options de la ligne de commande. En mode normal, le pilote interrogera périodiquement l'UPS pour connaître son état et ses paramètres, conformément au paramètre pollinterval dans ups.conf(5). Les résultats de cette commande sont présentés à upsd. Le pilote gérera également la définition des variables et les commandes instantanées, le cas échéant.

Dans le second mode, en utilisant -k, le pilote peut demander à l'UPS de couper l'alimentation, éventuellement après un délai. Ce mode de fonctionnement est destiné aux cas où l'on sait que l'UPS est sur le point de manquer de batterie et que les systèmes connectés doivent être éteints pour garantir un redémarrage correct lors du retour de l'alimentation.

Dans le troisième mode, en utilisant -d, le pilote quittera après quelques boucles de mise à jour, en vidant l'arbre de données (dans un format similaire à upsc(8)) sur la sortie standard. Cela peut être utile pour compléter nut-scanner(8) afin de découvrir des périphériques, avec des données détaillées.


Note

Vous ne voudrez probablement pas utiliser ces options directement. Vous devriez utiliser upsdrvctl(8) (ou upsdrvsvcctl(8) sur les systèmes disposant d'un framework de gestion de services comme systemd ou SMF) pour contrôler vos pilotes, et ups.conf(5) pour les configurer. Le reste de ce manuel décrit des options et des paramètres qui ne sont généralement pas nécessaires aux utilisateurs normaux.

OPTIONS

-h

Affiche un message d'aide sans rien faire d'autre. Cela listera également les valeurs possibles pour -x dans ce pilote, ainsi que d'autres textes d'aide que l'auteur du pilote a pu fournir.

-a id

Configure automatiquement ce pilote en utilisant la section id de ups.conf(5). Cet argument est obligatoire lors de l'appel direct du pilote.

-s id

Configure ce pilote uniquement avec des arguments de ligne de commande au lieu de lire ups.conf(5). À utiliser à la place de l'option -a lorsqu'il est nécessaire d'exécuter un pilote non présent dans le fichier de configuration des pilotes. La configuration du pilote doit alors être définie avec des options -x directement dans la ligne de commande. En tant qu'instance de pilote ne pouvant pas être contrôlée par upsdrvctl(8) ou upsdrvsvcctl(8), cette option doit être utilisée uniquement pour des besoins spécifiques.

-D

Augmente le niveau de débogage. Utilisez-le plusieurs fois pour voir plus de détails. L'exécution d'un pilote en mode débogage l'empêchera (par défaut) de s'exécuter en arrière-plan après le démarrage. Il continuera à enregistrer des informations sur la console jusqu'à ce qu'il reçoive un signal SIGINT (généralement Ctrl-C) ou SIGTERM.

Le niveau de débogage nécessaire dépend à la fois du pilote et du problème que vous essayez de diagnostiquer. Par conséquent, expliquez d'abord le problème que vous rencontrez avec un pilote à un développeur/mainteneur, avant de lui envoyer des sorties de débogage. Le plus souvent, si vous choisissez simplement un niveau, la sortie peut être trop limitée ou trop verbeuse pour être utile.

-d nombre_de_mises_a_jour

Vide l'arbre de données (au format similaire à upsc(8)) sur la sortie standard après avoir exécuté la boucle de mise à jour du pilote pour le nombre spécifié de nombre_de_mises_a_jour et quitte.

Par défaut, cela empêche le processus du pilote de s'exécuter en arrière-plan après le démarrage. Notez que la bannière du pilote sera également imprimée, donc lorsque vous utilisez cette option dans des scripts, n'oubliez pas de supprimer la première ligne, ou d'utiliser la variable d'environnement NUT_QUIET_INIT_BANNER.

-q

Augmente le seuil du niveau de journalisation. Utilisez-le plusieurs fois pour enregistrer plus de détails.

Le commentaire de débogage ci-dessus s'applique également ici.

-c commande

Envoie la commande au processus en arrière-plan sous forme de signal. Les commandes valides sont :

reload

relire les fichiers de configuration, en ignorant les paramètres modifiés qui ne peuvent pas être appliqués « à la volée »

reload-or-error

relire les fichiers de configuration, en ignorant mais en comptant les valeurs modifiées qui nécessitent un redémarrage du pilote (ne peuvent pas être modifiées à la volée), et renvoyer un code de succès/échec basé sur ce compte, afin que l'appelant puisse décider du sort de l'instance de pilote en cours d'exécution

reload-or-exit

relire les fichiers de configuration, en quittant le processus de pilote existant s'il rencontre des paramètres modifiés qui ne peuvent pas être appliqués « à la volée » (afin que l'appelant comme systemd puisse lancer une autre copie du pilote)

exit

demande à l'instance de pilote en cours d'exécution de simplement quitter (afin qu'une copie externe comme la nouvelle instance de pilote, ou le framework systemd ou SMF en lance une autre)

Avec les versions récentes de NUT v2.8.x, de telles commandes peuvent être envoyées via le socket Unix pour l'interaction pilote-serveur. Par défaut, comme les versions plus anciennes, les signaux peuvent être envoyés au PID de l'ancienne instance du pilote (si possible).

-P pid

Envoie le signal de commande ci-dessus en utilisant le numéro PID spécifié, plutôt qu'en consultant le fichier PID. Cela peut aider à définir des unités de service qui démarrent chaque pilote NUT comme un processus au premier plan, de sorte qu'il ne crée pas de fichier PID. Voir également l'option -FF comme alternative.

-F

Force l'exécution du pilote en tant que processus au premier plan, indépendamment des paramètres de débogage ou de vidage de données. Spécifiez deux fois (-FF ou -F -F) pour enregistrer le fichier PID même dans ce mode.

-B

Force l'exécution du pilote en tant que processus en arrière-plan, indépendamment des paramètres de débogage ou de vidage de données.

-i intervalle

Définit l'intervalle d'interrogation du périphérique. La valeur par défaut est de 2 (en secondes).

-V

Affiche uniquement les informations sur la version, puis quitte.

-L

Affiche une liste analysable des variables du pilote. Utile principalement pour les programmes d'assistant de configuration.

-k

(Mise hors tension) Mode d'arrêt forcé. L'onduleur coupera l'alimentation de la charge connectée, si possible.

Vous devriez utiliser upsdrvctl shutdown lorsque c'est possible au lieu d'appeler ceci directement. Notez que le contexte restreint du système d'exploitation pour l'arrêt exclut généralement l'utilisation de upsdrvsvcctl shutdown.

-r répertoire

Le pilote appellera chroot(2) vers le répertoire lors de l'initialisation. Cela peut être utile lors de la sécurisation des systèmes.

En plus du chemin d'état, de nombreux systèmes nécessiteront que /dev/null existe dans le répertoire pour que cela fonctionne. Les ports série sont ouverts avant l'appel chroot, vous n'avez donc pas besoin de les créer à l'intérieur de la jail. En fait, il est quelque peu plus sûr de ne pas le faire (mais la reconnexion aux périphériques peut ne plus être possible et pourrait nécessiter un redémarrage complet du pilote).

-u nom_utilisateur

Remplace le nom d'utilisateur non privilégié que le pilote peut utiliser après le démarrage. S'il est démarré en tant que root, après l'ouverture des fichiers de configuration (et éventuellement l'appel à chroot(2), comme décrit dans l'option précédente), le pilote recherchera nom_utilisateur dans la base de données passwd, puis changera pour les identités utilisateur et groupe associées à nom_utilisateur. (S'il est démarré avec un UID ou un UID effectif non nul, le pilote ignorera silencieusement cette option.)

Lors de la compilation de NUT à partir des sources, le nom d'utilisateur par défaut est généralement nobody, et cela peut causer des erreurs de permission lorsque le pilote ouvre le nœud de périphérique UPS. Vous pouvez utiliser cette option pour remplacer temporairement les valeurs par défaut. OPTIONS

You will want to remove this option later in order to avoid permission conflicts between the driver and the unprivileged copy of upsd(8).

-g groupname

Override the unprivileged group name that the driver may use after startup to set permissions for the filesystem socket so upsd may still access it if the run-time user of the driver normally would deny that access.

-x var=val

Define a variable called var with the value of var in the driver. This varies from driver to driver — see their specific man pages for more information.

This is like setting var=val in ups.conf(5), but -x on command line overrides any settings from that file.

Note that for fallback values of NUT variables poorly supported by a specific device and/or its NUT driver, you can specify default.var.name=val to set a default value (may be replaced at run-time by a reading from the device, if one does arrive), or override.var.name=val to hard-code a value and ignore its readings from the device even if they are served. For example, this is often used with override.battery.voltage.nominal when the device reports a single cell in 2V range, and you are interested in a standard battery package in 12V range, for PbAc.

DIAGNOSTICS

Information about the startup process is printed to stdout and/or stderr. Additional messages after that point are only available in the syslog, unless the driver remains in foreground (e.g. due to raised debugging verbosity).

After upsd(8) starts, the UPS clients such as upsc(8) can be used to query the status of an UPS.

PROGRAM CONTROL

You should always use upsdrvctl(8) (or upsdrvsvcctl(8) on systems with a service management framework like systemd or SMF) to control the drivers. While drivers can be started by hand for testing purposes, it is not recommended for production use.

FILES

ups.conf

Required configuration file. This contains all details on which drivers to start and where the hardware is attached.

ENVIRONMENT VARIABLES

NUT_DEBUG_LEVEL sets default debug verbosity if no -D arguments were provided on command line, but does not request that the daemon runs in foreground mode.

NUT_CONFPATH is the path name of the directory that contains ups.conf and other configuration files. If this variable is not set, drivers use a built-in default, which is often /usr/local/ups/etc.

NUT_STATEPATH is the path name of the directory in which upsd and drivers keep shared state information. If this variable is not set, upsd and drivers use a built-in default, which is often /var/state/ups. The STATEPATH directive in upsd.conf(5) overrides this variable.

NUT_ALTPIDPATH is the path name of the directory in which upsd and drivers store .pid files. If this variable is not set, upsd and drivers use either NUT_STATEPATH if set, or ALTPIDPATH if set, or otherwise the built-in default STATEPATH.

NUT_QUIET_INIT_UPSNOTIFY=true can be used to prevent daemons which can notify service management frameworks (such as systemd) about passing their lifecycle milestones from emitting such notifications (including those about lack of system support for such modern features, once per run).

NUT_QUIET_INIT_BANNER=true can be used to suppress NUT tool name and version banner. NOT recommended for services due to adverse troubleshooting impact, but may be helpful in shell profiles or scripts which process NUT tool outputs.

BUGS

Some of the drivers may have bugs. See their manuals for more information.
