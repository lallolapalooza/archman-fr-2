nix-env --switch-profile(1) Manuel des commandes générales nix-env --switch-profile(1)

Nom

nix-env --switch-profile - définir l'environnement utilisateur sur le profil donné

Synopsis

nix-env {--switch-profile | -S} chemin

Description

Cette opération fait de chemin le profil actuel pour l'utilisateur. C'est-à-dire que le lien symbolique ~/.nix-profile pointe vers chemin.

Options

Les options suivantes sont autorisées pour toutes les opérations nix-env, mais peuvent ne pas toujours avoir un effet.

•
--file / -f chemin
Spécifie l'expression Nix (désignée ci-dessous comme l'expression Nix active) utilisée par les opérations --install, --upgrade et --query --available pour obtenir des dérivations. La valeur par défaut est ~/.nix-defexpr.
Si l'argument commence par http:// ou https://, il est interprété comme l'URL d'une archive qui sera téléchargée et décompressée dans un emplacement temporaire. L'archive doit inclure un seul répertoire de niveau supérieur contenant au moins un fichier nommé default.nix.
•
--profile / -p chemin
Spécifie le profil à utiliser par les opérations qui agissent sur un profil (désigné ci-dessous comme le profil actif). Un profil est une séquence d'environnements utilisateur appelés générations, dont l'une est la génération actuelle.
•
--dry-run
Pour les opérations --install, --upgrade, --uninstall, --switch-generation, --delete-generations et --rollback, ce drapeau fera que nix-env imprimera ce qui *serait* fait si ce drapeau n'avait pas été spécifié, sans le faire réellement.
--dry-run imprime également les chemins qui seront substitués (c'est-à-dire téléchargés) et ceux qui seront construits à partir de la source (car aucune substitut n'est disponible).
•
--system-filter système
Par défaut, les opérations telles que --query --available affichent les dérivations correspondant à n'importe quelle plateforme. Cette option vous permet d'utiliser les dérivations pour la plateforme spécifiée système.

Options courantes

La plupart des commandes Nix acceptent les options de ligne de commande suivantes :

•
--help
Imprime un résumé de la syntaxe de la commande et quitte.
•
--version
Imprime la version de Nix sur la sortie standard et quitte.
•
--verbose / -v
Augmente le niveau de verbosité des messages de diagnostic imprimés sur la sortie standard d'erreur. Pour chaque opération Nix, les informations imprimées sur la sortie standard sont bien définies ; toute information de diagnostic est imprimée sur la sortie standard d'erreur, jamais sur la sortie standard.
Cette option peut être spécifiée de manière répétée. Actuellement, les niveaux de verbosité suivants existent :
•
0 « Erreurs uniquement »
Imprime uniquement les messages expliquant pourquoi l'invocation Nix a échoué.
•
1 « Informatif »
Imprime des messages *utiles* sur ce que fait Nix. C'est la valeur par défaut.
•
2 « Bavard »
Imprime davantage de messages d'information.
•
3 « Loquace »
Imprime encore plus de messages d'information.
•
4 « Débogage »
Imprime des informations de débogage.
•
5 « Vomit »
Imprime d'énormes quantités d'informations de débogage.
•
--quiet
Diminue le niveau de verbosité des messages de diagnostic imprimés sur la sortie standard d'erreur. C'est l'option inverse de -v / --verbose.
Cette option peut être spécifiée de manière répétée. Voir la liste précédente des niveaux de verbosité.
•
--log-format format
Cette option peut être utilisée pour modifier le format de sortie du journal, format étant l'une des options suivantes :
•
raw
C'est le format brut, tel que généré par nix-build.
•
internal-json
Génère les journaux dans un format structuré.
Attention
Bien que le schéma lui-même soit relativement stable, le format des messages d'erreur (notamment du champ msg) peut changer entre les versions.
•
bar
N'affiche qu'une barre de progression pendant les compilations.
•
bar-with-logs
Affiche les journaux bruts, avec la barre de progression en bas.
•
--no-build-output / -Q
Par défaut, la sortie écrite par les constructeurs sur la sortie standard et la sortie standard d'erreur est renvoyée vers la sortie standard d'erreur de la commande Nix. Cette option supprime ce comportement. Notez que la sortie standard et l'erreur standard du constructeur sont toujours écrites dans un fichier journal dans prefix/nix/var/log/nix.
•
--max-jobs / -j nombre
Définit le nombre maximum de tâches de construction que Nix effectuera en parallèle au nombre spécifié. Spécifiez auto pour utiliser le nombre de CPU du système. La valeur par défaut est spécifiée par le paramètre de configuration max-jobs, qui par défaut est 1. Une valeur plus élevée est utile sur les systèmes SMP ou pour exploiter la latence des E/S.
Le régler à 0 interdit la construction sur la machine locale, ce qui est utile lorsque vous souhaitez que les constructions se produisent uniquement sur des constructeurs distants.
•
<--cores
Définit la valeur de la variable d'environnement NIX_BUILD_CORES lors de l'invocation des constructeurs. Les constructeurs peuvent utiliser cette variable à leur discrétion pour contrôler le niveau de parallélisme maximum. Par exemple, dans Nixpkgs, si l'attribut de dérivation enableParallelBuilding est défini sur true, le constructeur passe le drapeau -jN à GNU Make. Il est par défaut à la valeur du paramètre de configuration cores, s'il est défini, ou à 1 sinon. La valeur 0 signifie que le constructeur doit utiliser tous les cœurs de processeur disponibles sur le système.
•
--max-silent-time
Définit le nombre maximum de secondes pendant lesquelles un constructeur peut ne pas produire de sortie sur la sortie standard ou l'erreur standard. La valeur par défaut est spécifiée par le paramètre de configuration max-silent-time. 0 signifie aucun délai d'attente.
•
--timeout
Définit le nombre maximum de secondes pendant lesquelles un constructeur peut s'exécuter. La valeur par défaut est spécifiée par le paramètre de configuration timeout. 0 signifie aucun délai d'attente.
•
--keep-going / -k
Continuer en cas d'échec de construction, dans la plus grande mesure possible. C'est-à-dire, si la construction d'une entrée d'une dérivation échoue, Nix construira toujours les autres entrées, mais pas la dérivation elle-même. Sans cette option, Nix s'arrête si une construction échoue (sauf pour la construction de substituts), tuant potentiellement les constructions en cours (en cas de constructions parallèles ou distribuées).
•
--keep-failed / -K
Spécifie qu'en cas d'échec de construction, le répertoire temporaire (généralement dans /tmp) dans lequel la construction a lieu ne doit pas être supprimé. Le chemin du répertoire de construction est imprimé sous forme de message d'information.
•
--fallback
Chaque fois que Nix tente de construire une dérivation pour laquelle des substituts sont connus pour chaque chemin de sortie, mais que la réalisation des chemins de sortie via les substituts échoue, Nix se rabat sur la construction de la dérivation.
Le scénario le plus courant dans lequel cela est utile est lorsque nous avons enregistré des substituts afin d'effectuer la distribution binaire à partir, par exemple, d'un dépôt réseau. Si le dépôt est en panne, la réalisation de la dérivation échouera. Lorsque cette option est spécifiée, Nix construira la dérivation à la place. Ainsi, l'installation à partir de binaires se rabat sur l'installation à partir de la source. Cette option n'est pas la valeur par défaut car il n'est généralement pas souhaitable qu'un échec transitoire dans l'obtention des substituts entraîne une construction complète à partir de la source (avec la consommation de ressources associée).
•
--readonly-mode
Lorsque cette option est utilisée, aucune tentative n'est faite pour ouvrir la base de données Nix. La plupart des opérations Nix nécessitent un accès à la base de données, donc ces opérations échoueront.
•
--arg nom valeur
Cette option est acceptée par nix-env, nix-instantiate, nix-shell et nix-build. Lors de l'évaluation des expressions Nix, l'évaluateur d'expression tentera automatiquement d'appeler les fonctions qu'il rencontre. Il peut appeler automatiquement les fonctions pour lesquelles chaque argument a une valeur par défaut (par exemple, { argName ? defaultValue }: ...).
Avec --arg, vous pouvez également appeler des fonctions qui ont des arguments sans valeur par défaut (ou remplacer une valeur par défaut). C'est-à-dire, si l'évaluateur rencontre une fonction avec un argument nommé nom, il l'appellera avec la valeur valeur.
Par exemple, le default.nix de premier niveau dans Nixpkgs est en fait une fonction :
{ # Le système (par exemple, `i686-linux') pour lequel construire les paquets.
system ? builtins.currentSystem
...
}: ...
Donc, si vous appelez cette expression Nix (par exemple, lorsque vous faites nix-env --install --attr pkgname), la fonction sera appelée automatiquement en utilisant la valeur builtins.currentSystem pour l'argument system. Vous pouvez le remplacer en utilisant --arg, par exemple, nix-env --install --attr pkgname --arg system \"i686-freebsd\". (Notez que puisque l'argument est une chaîne littérale Nix, vous devez échapper les guillemets.)
•
--argstr nom valeur
Cette option est similaire à --arg, sauf que la valeur n'est pas une expression Nix mais une chaîne de caractères. Donc, au lieu de --arg system \"i686-linux\" (les guillemets extérieurs servent à satisfaire le shell), vous pouvez dire --argstr system i686-linux.
•
--attr / -A attrPath
Sélectionne un attribut de l'expression Nix de premier niveau en cours d'évaluation. (Seulement pour nix-env, nix-instantiate, nix-build et nix-shell.) Le chemin d'attribut attrPath est une séquence de noms d'attributs séparés par des points. Par exemple, étant donné une expression Nix de premier niveau e, le chemin d'attribut xorg.xorgserver entraînerait l'utilisation de l'expression e.xorg.xorgserver. Voir nix-env --install pour quelques exemples concrets.
En plus des noms d'attributs, vous pouvez également spécifier des indices de tableau. Par exemple, le chemin d'attribut foo.3.bar sélectionne l'attribut bar du quatrième élément du tableau dans l'attribut foo de l'expression de premier niveau.
•
--expr / -E
Interprète les arguments de la ligne de commande comme une liste d'expressions Nix à analyser et évaluer, plutôt que comme une liste de noms de fichiers d'expressions Nix. (Seulement pour nix-instantiate, nix-build et nix-shell.)
Pour nix-shell, cette option est couramment utilisée pour vous fournir un shell dans lequel vous pouvez construire les paquets retournés par l'expression. Si vous voulez obtenir un shell qui contient les paquets construits prêts à l'emploi, donnez votre expression au drapeau de commodité nix-shell --packages à la place.
•
-I / --include chemin
Ajoute une entrée à la liste des chemins de recherche utilisés pour résoudre les chemins de recherche. Cette option peut être donnée plusieurs fois.
Les chemins ajoutés via -I ont la priorité sur le paramètre de configuration nix-path et la variable d'environnement NIX_PATH.
•
--option nom valeur
Définit l'option de configuration Nix nom sur valeur. Ceci remplace les paramètres du fichier de configuration Nix (voir nix.conf5).
•
--repair
Corrige les chemins de magasin corrompus ou manquants en les redownloadant ou en les reconstruisant. Notez que cela est lent car cela nécessite de calculer un hachage cryptographique du contenu de chaque chemin dans la clôture de la construction. Notez également l'avertissement sous nix-store --repair-path.

Note

Voir man nix.conf pour remplacer les paramètres de configuration avec des drapeaux de ligne de commande.

Variables d'environnement

•
NIX_PROFILE
Emplacement du profil Nix. Par défaut, la cible du lien symbolique ~/.nix-profile, s'il existe, ou /nix/var/nix/profiles/default sinon.

This manual page lists the common options and environment variables for the Nix command-line tools.

These options are common to most Nix commands.
-h, --help
Display help message.
--version
Display Nix version information.
-I path, --option add-root path
Add an extra path to the search path for Nix expressions. This is often used to add paths to Nixpkgs, for example, by setting NIX_PATH like NIX_PATH=$NIX_PATH:/path/to/nixpkgs.
Multiple -I options can be provided to specify multiple search paths.
--option name=value
Set a Nix configuration option. This overrides settings in configuration.nix and environment variables.
For a complete list of options, see the Nix manual.
--impure
Allow Nix to perform "impure" operations, such as accessing the user's profile or environment variables. This is necessary for some commands, like nix-env, but should be used with caution.
--pure
Disallow Nix from performing "impure" operations. This ensures reproducible builds by preventing access to the user's profile or environment variables.
These environment variables affect the behavior of Nix commands.
•
NIX_PATH
A list of search paths used to resolve Nix expression imports. The paths are separated by colons (:). For example, NIX_PATH=~/nixpkgs=~/my-nixpkgs:/path/to/other/pkgs.
This environment variable overrides the value of the nix-path configuration setting.
It can be extended using the -I option.
Example
$ export NIX_PATH=`/home/eelco/Dev:nixos-config=/etc/nixos
If NIX_PATH is set to an empty string, resolving search paths will always fail.
Example
$ NIX_PATH= nix-instantiate --eval '<nixpkgs>'
error: file 'nixpkgs' was not found in the Nix search path (add it using $NIX_PATH or -I)
•
NIX_IGNORE_SYMLINK_STORE
Normally, the Nix store directory (typically /nix/store) is not allowed to contain any symlink components. This is to prevent “impure” builds. Builders sometimes “canonicalise” paths by resolving all symlink components. Thus, builds on different machines (with /nix/store resolving to different locations) could yield different results. This is generally not a problem, except when builds are deployed to machines where /nix/store resolves differently. If you are sure that you’re not going to do that, you can set NIX_IGNORE_SYMLINK_STORE to 1.
Note that if you’re symlinking the Nix store so that you can put it on another file system than the root file system, on Linux you’re better off using bind mount points, e.g.,
$ mkdir /nix
$ mount -o bind /mnt/otherdisk/nix /nix
Consult the mount 8 manual page for details.
•
NIX_STORE_DIR
Overrides the location of the Nix store (default prefix/store).
•
NIX_DATA_DIR
Overrides the location of the Nix static data directory (default prefix/share).
•
NIX_LOG_DIR
Overrides the location of the Nix log directory (default prefix/var/log/nix).
•
NIX_STATE_DIR
Overrides the location of the Nix state directory (default prefix/var/nix).
•
NIX_CONF_DIR
Overrides the location of the system Nix configuration directory (default prefix/etc/nix).
•
NIX_CONFIG
Applies settings from Nix configuration from the environment. The content is treated as if it was read from a Nix configuration file. Settings are separated by the newline character.
•
NIX_USER_CONF_FILES
Overrides the location of the Nix user configuration files to load from.
The default are the locations according to the XDG Base Directory Specification. See the XDG Base Directories sub-section for details.
The variable is treated as a list separated by the : token.
•
TMPDIR
Use the specified directory to store temporary files. In particular, this includes temporary build directories; these can take up substantial amounts of disk space. The default is /tmp.
•
NIX_REMOTE
This variable should be set to daemon if you want to use the Nix daemon to execute Nix operations. This is necessary in multi-user Nix installations. If the Nix daemon’s Unix socket is at some non-standard path, this variable should be set to unix://path/to/socket. Otherwise, it should be left unset.
•
NIX_SHOW_STATS
If set to 1, Nix will print some evaluation statistics, such as the number of values allocated.
•
NIX_COUNT_CALLS
If set to 1, Nix will print how often functions were called during Nix expression evaluation. This is useful for profiling your Nix expressions.
•
GC_INITIAL_HEAP_SIZE
If Nix has been configured to use the Boehm garbage collector, this variable sets the initial size of the heap in bytes. It defaults to 384 MiB. Setting it to a low value reduces memory consumption, but will increase runtime due to the overhead of garbage collection.

XDG Base Directories

Nix follows the XDG Base Directory Specification.

For backwards compatibility, Nix commands will follow the standard only when use-xdg-base-directories is enabled. New Nix commands (experimental) conform to the standard by default.

The following environment variables are used to determine locations of various state and configuration files:

  • [XDG_CONFIG_HOME]{#env-XDGCONFIGHOME} (default ~/.config)
  • [XDG_STATE_HOME]{#env-XDGSTATEHOME} (default ~/.local/state)
  • [XDG_CACHE_HOME]{#env-XDGCACHEHOME} (default ~/.cache)
