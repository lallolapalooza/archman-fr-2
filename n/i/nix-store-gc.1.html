nix-store --gc(1) Manuel des commandes générales nix-store --gc(1)

Nom

nix-store --gc - exécuter le ramasse-miettes

Synopsis

nix-store --gc [--print-roots | --print-live | --print-dead] [--max-freed octets]

Description

Sans options supplémentaires, l'opération --gc effectue un ramasse-miettes sur le magasin Nix. C'est-à-dire que tous les chemins du magasin Nix non accessibles par des références du système de fichiers à partir d'un ensemble de « racines » sont supprimés.

Les sous-opérations suivantes peuvent être spécifiées :

•
--print-roots
Cette opération imprime sur la sortie standard l'ensemble des racines utilisées par le ramasse-miettes.
•
--print-live
Cette opération imprime sur la sortie standard l'ensemble des chemins de magasin « vivants », qui sont tous les chemins de magasin accessibles depuis les racines. Les chemins vivants ne doivent jamais être supprimés, car cela briserait la cohérence — il deviendrait possible que des applications soient installées qui référencent des éléments qui ne sont plus présents dans le magasin.
•
--print-dead
Cette opération imprime sur la sortie standard l'ensemble des chemins de magasin « morts », qui est juste l'inverse de l'ensemble des chemins vivants : tout chemin dans le magasin qui n'est pas vivant (par rapport aux racines) est mort.

Par défaut, tous les chemins inaccessibles sont supprimés. Les options suivantes contrôlent ce qui est supprimé et dans quel ordre :

•
--max-freed octets
Continuer à supprimer des chemins jusqu'à ce qu'au moins octets octets aient été supprimés, puis s'arrêter. L'argument octets peut être suivi du suffixe multiplicateur K, M, G ou T, représentant les unités KiB, MiB, GiB ou TiB.

Le comportement du collecteur est également influencé par les paramètres keep-outputs et keep-derivations dans le fichier de configuration Nix.

Par défaut, le collecteur imprime le nombre total d'octets libérés lorsqu'il a terminé (ou lorsqu'il est interrompu). Avec --print-dead, il imprime le nombre d'octets qui seraient libérés.

Options

Les options suivantes sont autorisées pour toutes les opérations nix-store, mais peuvent ne pas toujours avoir un effet.

•
--add-root chemin
Fait en sorte que le résultat d'une réalisation (--realise et --force-realise) soit enregistré comme une racine du ramasse-miettes. chemin sera créé comme un lien symbolique vers le chemin de magasin résultant. De plus, un lien symbolique nommé de manière unique vers chemin sera créé dans /nix/var/nix/gcroots/auto/. Par exemple,
$ nix-store --add-root /home/eelco/bla/result --realise ...
$ ls -l /nix/var/nix/gcroots/auto
lrwxrwxrwx    1 ... 2005-03-13 21:10 dn54lcypm8f8... -> /home/eelco/bla/result
$ ls -l /home/eelco/bla/result
lrwxrwxrwx    1 ... 2005-03-13 21:10 /home/eelco/bla/result -> /nix/store/1r11343n6qd4...-f-spot-0.0.10
Ainsi, lorsque /home/eelco/bla/result est supprimé, la racine GC dans le répertoire auto devient un lien symbolique pendant et sera ignorée par le collecteur.
Attention
Notez qu'il n'est pas possible de déplacer ou renommer les racines GC, car le lien symbolique dans le répertoire auto pointera toujours vers l'ancien emplacement.
S'il y a plusieurs résultats, plusieurs liens symboliques seront créés en numérotant séquentiellement les liens symboliques au-delà du premier (par exemple, foo, foo-2, foo-3, et ainsi de suite).

Options communes

La plupart des commandes Nix acceptent les options de ligne de commande suivantes :

•
--help
Imprime un résumé de la syntaxe de la commande et quitte.
•
--version
Imprime le numéro de version de Nix sur la sortie standard et quitte.
•
--verbose / -v
Augmente le niveau de verbosité des messages de diagnostic imprimés sur la sortie d'erreur standard. Pour chaque opération Nix, les informations imprimées sur la sortie standard sont bien définies ; toute information de diagnostic est imprimée sur la sortie d'erreur standard, jamais sur la sortie standard.
Cette option peut être spécifiée de manière répétée. Actuellement, les niveaux de verbosité suivants existent :
•
0 « Erreurs seulement »
Imprime uniquement les messages expliquant pourquoi l'invocation Nix a échoué.
•
1 « Informatif »
Imprime des messages *utiles* sur ce que fait Nix. C'est le comportement par défaut.
•
2 « Bavard »
Imprime plus de messages informatifs.
•
3 « Très bavard »
Imprime encore plus de messages informatifs.
•
4 « Débogage »
Imprime des informations de débogage.
•
5 « Vomitif »
Imprime une quantité considérable d'informations de débogage.
•
--quiet
Diminue le niveau de verbosité des messages de diagnostic imprimés sur la sortie d'erreur standard. C'est l'option inverse de -v / --verbose.
Cette option peut être spécifiée de manière répétée. Voir la liste précédente des niveaux de verbosité.
•
--log-format format
Cette option peut être utilisée pour changer le format de sortie du journal, avec format étant l'un des suivants :
•
raw
C'est le format brut, tel qu'émis par nix-build.
•
internal-json
Émet les journaux dans un format structuré.
Attention
Bien que le schéma lui-même soit relativement stable, le format des messages d'erreur (notamment du champ msg) peut changer entre les versions.
•
bar
Affiche uniquement une barre de progression pendant les constructions.
•
bar-with-logs
Affiche les journaux bruts, avec la barre de progression en bas.
•
--no-build-output / -Q
Par défaut, la sortie écrite par les constructeurs vers la sortie standard et l'erreur standard est renvoyée vers l'erreur standard de la commande Nix. Cette option supprime ce comportement. Notez que la sortie standard et l'erreur standard du constructeur sont toujours écrites dans un fichier journal dans prefix/nix/var/log/nix.
•
--max-jobs / -j nombre
Définit le nombre maximum de tâches de construction que Nix effectuera en parallèle au nombre spécifié. Spécifiez auto pour utiliser le nombre de processeurs du système. La valeur par défaut est spécifiée par le paramètre de configuration max-jobs, qui est lui-même défini sur 1 par défaut. Une valeur plus élevée est utile sur les systèmes SMP ou pour exploiter la latence d'E/S.
Le régler sur 0 interdit la construction sur la machine locale, ce qui est utile lorsque vous souhaitez que les constructions se déroulent uniquement sur des constructeurs distants.
•
--cores
Définit la valeur de la variable d'environnement NIX_BUILD_CORES lors de l'invocation des constructeurs. Les constructeurs peuvent utiliser cette variable à leur discrétion pour contrôler le parallélisme maximal. Par exemple, dans Nixpkgs, si l'attribut de dérivation enableParallelBuilding est défini sur true, le constructeur transmet l'indicateur -jN à GNU Make. Il utilise par défaut la valeur du paramètre de configuration cores, s'il est défini, ou 1 sinon. La valeur 0 signifie que le constructeur doit utiliser tous les cœurs de processeur disponibles dans le système.
•
--max-silent-time
Définit le temps maximum en secondes pendant lequel un constructeur peut fonctionner sans produire aucune donnée sur la sortie standard ou l'erreur standard. La valeur par défaut est spécifiée par le paramètre de configuration max-silent-time. 0 signifie aucun délai d'expiration.
•
--timeout
Définit le temps maximum en secondes pendant lequel un constructeur peut s'exécuter. La valeur par défaut est spécifiée par le paramètre de configuration timeout. 0 signifie aucun délai d'expiration.
•
--keep-going / -k
Continuer en cas d'échec des constructions, dans la plus grande mesure possible. C'est-à-dire, si la construction d'une entrée d'une dérivation échoue, Nix construira toujours les autres entrées, mais pas la dérivation elle-même. Sans cette option, Nix s'arrête si une construction échoue (sauf pour les constructions de substituts), tuant potentiellement les constructions en cours (en cas de constructions parallèles ou distribuées).
•
--keep-failed / -K
Spécifie qu'en cas d'échec de construction, le répertoire temporaire (généralement dans /tmp) dans lequel la construction a lieu ne doit pas être supprimé. Le chemin du répertoire de construction est imprimé comme message d'information.
•
--fallback
Chaque fois que Nix tente de construire une dérivation pour laquelle des substituts sont connus pour chaque chemin de sortie, mais que la réalisation des chemins de sortie via les substituts échoue, il se rabat sur la construction de la dérivation.
Le scénario le plus courant dans lequel cela est utile est lorsque nous avons enregistré des substituts pour effectuer une distribution binaire à partir, par exemple, d'un dépôt réseau. Si le dépôt est en panne, la réalisation de la dérivation échouera. Lorsque cette option est spécifiée, Nix construira la dérivation à la place. Ainsi, l'installation à partir de binaires se rabat sur l'installation à partir de la source. Cette option n'est pas par défaut car il n'est généralement pas souhaitable qu'un échec transitoire dans l'obtention des substituts conduise à une construction complète à partir de la source (avec la consommation de ressources associée).
•
--readonly-mode
Lorsque cette option est utilisée, aucune tentative n'est faite pour ouvrir la base de données Nix. La plupart des opérations Nix nécessitent un accès à la base de données, de sorte que ces opérations échoueront.
•
--arg nom valeur
Cette option est acceptée par nix-env, nix-instantiate, nix-shell et nix-build. Lors de l'évaluation des expressions Nix, l'évaluateur d'expressions essaiera automatiquement d'appeler les fonctions qu'il rencontre. Il peut appeler automatiquement des fonctions pour lesquelles chaque argument a une valeur par défaut (par exemple, { argName ? defaultValue }: ...).
Avec --arg, vous pouvez également appeler des fonctions qui ont des arguments sans valeur par défaut (ou remplacer une valeur par défaut). C'est-à-dire, si l'évaluateur rencontre une fonction avec un argument nommé nom, il l'appellera avec la valeur valeur.
Par exemple, le default.nix de haut niveau dans Nixpkgs est en fait une fonction :
{ # Le système (par exemple, `i686-linux') pour lequel construire les paquets.
system ? builtins.currentSystem
...
}: ...
Donc, si vous appelez cette expression Nix (par exemple, lorsque vous faites nix-env --install --attr pkgname), la fonction sera appelée automatiquement en utilisant la valeur builtins.currentSystem pour l'argument system. Vous pouvez le remplacer en utilisant --arg, par exemple nix-env --install --attr pkgname --arg system \"i686-freebsd\". (Notez que comme l'argument est une chaîne littérale Nix, vous devez échapper les guillemets.)
•
--argstr nom valeur
Cette option est comme --arg, seule la valeur n'est pas une expression Nix mais une chaîne de caractères. Donc, au lieu de --arg system \"i686-linux\" (les guillemets extérieurs servent à garder le shell content, vous pouvez dire --argstr system i686-linux.
•
--attr / -A cheminAttr
Sélectionne un attribut de l'expression Nix de haut niveau en cours d'évaluation. (nix-env, nix-instantiate, nix-build et nix-shell uniquement.) Le chemin d'attribut cheminAttr est une séquence d'attributs noms séparés par des points. Par exemple, étant donné une expression Nix de haut niveau e, le chemin d'attribut xorg.xorgserver entraînerait l'utilisation de l'expression e.xorg.xorgserver. Voir nix-env --install pour des exemples concrets.
En plus des noms d'attributs, vous pouvez également spécifier des indices de tableau. Par exemple, le chemin d'attribut foo.3.bar sélectionne le attribut bar du quatrième élément du tableau dans le attribut foo de l'expression de haut niveau.
•
--expr / -E
Interprète les arguments de la ligne de commande comme une liste d'expressions Nix à analyser et évaluer, plutôt que comme une liste de noms de fichiers d'expressions Nix. (nix-instantiate, nix-build et nix-shell uniquement.)
Pour nix-shell, cette option est couramment utilisée pour vous donner un shell dans lequel vous pouvez construire les paquets retournés par l'expression. Si vous voulez obtenir un shell qui contient les paquets construits prêts à l'emploi, donnez votre expression à la l'indicateur de commodité nix-shell --packages plutôt.
•
-I / --include chemin
Ajoute une entrée à la liste des chemins de recherche utilisés pour résoudre les chemins de recherche. Cette option peut être donnée plusieurs fois.
Les chemins ajoutés via -I ont la priorité sur le paramètre de configuration nix-path et la variable d'environnement NIX_PATH .
•
--option nom valeur
Définit l'option de configuration Nix nom sur valeur. Ceci remplace les paramètres du fichier de configuration Nix (voir nix.conf5).
•
--repair
Corrige les chemins de magasin corrompus ou manquants en les redownloadant ou en les reconstruisant. Notez que cela est lent car cela nécessite de calculer un hachage cryptographique du contenu de chaque chemin dans la fermeture de la construction. Notez également l'avertissement sous nix-store --repair-path.

Name

nix-store, nix-store -- query and manipulate the Nix data store

Synopsis

nix-store [options] subcommand [args...]

Description

The nix-store command manipulates the Nix data store, a collection of files and directories in /nix/store (by default) that contains all the packages and other store paths managed by Nix.

The following subcommands are available:

query
Query the Nix data store.
build
Build one or more Nix expressions.
path
Convert a derivation path into a store path.
realise
Realise one or more derivations.
delete
Delete paths from the Nix store.
gc
Run the garbage collector.
optimise
Remove redundant data from the Nix store.
register
Register a path in the Nix store.
unregister
Unregister a path from the Nix store.
fix
Fix up a store path.
mount
Mount a store path.
check-db
Check the integrity of the Nix store database.
ping
Test connectivity to the Nix daemon.

Options

Most Nix commands interpret the following options:

--help
Display help message and exit.
--version
Display Nix version and exit.
--manpath
Set the path to search for manual pages.
--option <name><=>

name is the name of the option, and value is its value. For example, --option sandbox false.

See also man nix.conf for overriding configuration settings with command line flags.

Common Environment Variables

Most Nix commands interpret the following environment variables:

•
IN_NIX_SHELL
Indicator that tells if the current environment was set up by nix-shell. It can have the values pure or impure.
•
NIX_PATH
A colon-separated list of search path entries used to resolve lookup paths.
This environment variable overrides the value of the nix-path configuration setting.
It can be extended using the -I option.
Example
$ export NIX_PATH=`/home/eelco/Dev:nixos-config=/etc/nixos
If NIX_PATH is set to an empty string, resolving search paths will always fail.
Example
$ NIX_PATH= nix-instantiate --eval '<nixpkgs>'
error: file 'nixpkgs' was not found in the Nix search path (add it using $NIX_PATH or -I)
•
NIX_IGNORE_SYMLINK_STORE
Normally, the Nix store directory (typically /nix/store) is not allowed to contain any symlink components. This is to prevent “impure” builds. Builders sometimes “canonicalise” paths by resolving all symlink components. Thus, builds on different machines (with /nix/store resolving to different locations) could yield different results. This is generally not a problem, except when builds are deployed to machines where /nix/store resolves differently. If you are sure that you’re not going to do that, you can set NIX_IGNORE_SYMLINK_STORE to 1.
Note that if you’re symlinking the Nix store so that you can put it on another file system than the root file system, on Linux you’re better off using bind mount points, e.g.,
$ mkdir /nix
$ mount -o bind /mnt/otherdisk/nix /nix
Consult the mount 8 manual page for details.
•
NIX_STORE_DIR
Overrides the location of the Nix store (default prefix/store).
•
NIX_DATA_DIR
Overrides the location of the Nix static data directory (default prefix/share).
•
NIX_LOG_DIR
Overrides the location of the Nix log directory (default prefix/var/log/nix).
•
NIX_STATE_DIR
Overrides the location of the Nix state directory (default prefix/var/nix).
•
NIX_CONF_DIR
Overrides the location of the system Nix configuration directory (default prefix/etc/nix).
•
NIX_CONFIG
Applies settings from Nix configuration from the environment. The content is treated as if it was read from a Nix configuration file. Settings are separated by the newline character.
•
NIX_USER_CONF_FILES
Overrides the location of the Nix user configuration files to load from.
The default are the locations according to the XDG Base Directory Specification. See the XDG Base Directories sub-section for details.
The variable is treated as a list separated by the : token.
•
TMPDIR
Use the specified directory to store temporary files. In particular, this includes temporary build directories; these can take up substantial amounts of disk space. The default is /tmp.
•
NIX_REMOTE
This variable should be set to daemon if you want to use the Nix daemon to execute Nix operations. This is necessary in multi-user Nix installations. If the Nix daemon’s Unix socket is at some non-standard path, this variable should be set to unix://path/to/socket. Otherwise, it should be left unset.
•
NIX_SHOW_STATS
If set to 1, Nix will print some evaluation statistics, such as the number of values allocated.
•
NIX_COUNT_CALLS
If set to 1, Nix will print how often functions were called during Nix expression evaluation. This is useful for profiling your Nix expressions.
•
GC_INITIAL_HEAP_SIZE
If Nix has been configured to use the Boehm garbage collector, this variable sets the initial size of the heap in bytes. It defaults to 384 MiB. Setting it to a low value reduces memory consumption, but will increase runtime due to the overhead of garbage collection.

XDG Base Directories

Nix follows the XDG Base Directory Specification.

For backwards compatibility, Nix commands will follow the standard only when use-xdg-base-directories is enabled. New Nix commands (experimental) conform to the standard by default.

The following environment variables are used to determine locations of various state and configuration files:

  • [XDG_CONFIG_HOME]{#env-XDGCONFIGHOME} (default ~/.config)
  • [XDG_STATE_HOME]{#env-XDGSTATEHOME} (default ~/.local/state)
  • [XDG_CACHE_HOME]{#env-XDGCACHEHOME} (default ~/.cache)

Examples

To delete all unreachable paths, just do:

$ nix-store --gc
deleting `/nix/store/kq82idx6g0nyzsp2s14gfsc38npai7lf-cairo-1.0.4.tar.gz.drv'
...
8825586 bytes freed (8.42 MiB)

To delete at least 100 MiBs of unreachable paths:

$ nix-store --gc --max-freed $((100 * 1024 * 1024))
