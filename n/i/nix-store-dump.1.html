nix-store --dump(1) Manuel des commandes générales nix-store --dump(1)

Nom

nix-store --dump - écrire un chemin unique dans une Archive Nix

Synopsis

nix-store --dump chemin

Description

L'opération --dump produit un fichier Archive Nix (NAR) contenant le contenu de l'arbre du système de fichiers dont la racine est chemin. L'archive est écrite sur la sortie standard.

Une archive NAR est similaire à une archive TAR ou Zip, mais elle ne contient que les informations que Nix considère comme importantes. Par exemple, les horodatages sont supprimés car tous les fichiers dans le magasin Nix ont leur horodatage réglé à 0 de toute façon. De même, toutes les permissions sont laissées de côté à l'exception du bit d'exécution, car tous les fichiers dans le magasin Nix ont une permission de 444 ou 555.

En outre, une archive NAR est canonique, ce qui signifie que des chemins « égaux » produisent toujours la même archive NAR. Par exemple, les entrées de répertoire sont toujours triées afin que l'ordre réel sur le disque n'influence pas le résultat. Cela signifie que le hachage cryptographique d'un dump NAR d'un chemin peut être utilisé comme empreinte digitale du contenu du chemin. En effet, les hachages des chemins de magasin stockés dans la base de données de Nix (voir nix-store --query --hash) sont des hachages SHA-256 du dump NAR de chaque chemin de magasin.

Les archives NAR prennent en charge les noms de fichiers de longueur illimitée et les tailles de fichiers sur 64 bits. Elles peuvent contenir des fichiers réguliers, des répertoires et des liens symboliques, mais pas d'autres types de fichiers (comme des nœuds de périphérique).

Une archive Nix peut être décompressée en utilisant nix-store --restore.

Options

Les options suivantes sont autorisées pour toutes les opérations nix-store, mais peuvent ne pas toujours avoir un effet.

•
--add-root chemin
Fait en sorte que le résultat d'une réalisation (--realise et --force-realise) soit enregistré comme une racine du ramasse-miettes. chemin sera créé comme un lien symbolique vers le chemin de magasin résultant. De plus, un lien symbolique nommé de manière unique vers chemin sera créé dans /nix/var/nix/gcroots/auto/. Par exemple,
$ nix-store --add-root /home/eelco/bla/result --realise ...
$ ls -l /nix/var/nix/gcroots/auto
lrwxrwxrwx    1 ... 2005-03-13 21:10 dn54lcypm8f8... -> /home/eelco/bla/result
$ ls -l /home/eelco/bla/result
lrwxrwxrwx    1 ... 2005-03-13 21:10 /home/eelco/bla/result -> /nix/store/1r11343n6qd4...-f-spot-0.0.10
Ainsi, lorsque /home/eelco/bla/result est supprimé, la racine GC dans le répertoire auto devient un lien symbolique pendant et sera ignorée par le collecteur.
Attention
Notez qu'il n'est pas possible de déplacer ou de renommer les racines GC, car le lien symbolique dans le répertoire auto pointra toujours vers l'ancien emplacement.
S'il y a plusieurs résultats, plusieurs liens symboliques seront créés en numérotant séquentiellement les liens symboliques au-delà du premier (par exemple, foo, foo-2, foo-3, et ainsi de suite).

Options communes

La plupart des commandes Nix acceptent les options de ligne de commande suivantes :

•
--help
Affiche un résumé de la syntaxe de la commande et quitte.
•
--version
Affiche le numéro de version de Nix sur la sortie standard et quitte.
•
--verbose / -v
Augmente le niveau de verbosité des messages de diagnostic imprimés sur la sortie standard d'erreur. Pour chaque opération Nix, les informations imprimées sur la sortie standard sont bien définies ; toute information de diagnostic est imprimée sur la sortie standard d'erreur, jamais sur la sortie standard.
Cette option peut être spécifiée de manière répétée. Actuellement, les niveaux de verbosité suivants existent :
•
0 « Erreurs seulement »
Imprime uniquement les messages expliquant pourquoi l'invocation Nix a échoué.
•
1 « Informatif »
Imprime des messages *utiles* sur ce que Nix fait. C'est la valeur par défaut.
•
2 « Bavard »
Imprime des messages informatifs supplémentaires.
•
3 « Très bavard »
Imprime encore plus de messages informatifs.
•
4 « Débogage »
Imprime des informations de débogage.
•
5 « Vomir »
Imprime d'énormes quantités d'informations de débogage.
•
--quiet
Diminue le niveau de verbosité des messages de diagnostic imprimés sur la sortie standard d'erreur. C'est l'option inverse de -v / --verbose.
Cette option peut être spécifiée de manière répétée. Voir la liste précédente des niveaux de verbosité.
•
--log-format format
Cette option peut être utilisée pour modifier le format de sortie des logs, format étant l'une des options suivantes :
•
raw
C'est le format brut, tel que produit par nix-build.
•
internal-json
Affiche les logs de manière structurée.
Attention
Bien que le schéma lui-même soit relativement stable, le format des messages d'erreur (notamment le champ msg) peut changer entre les versions.
•
bar
Affiche uniquement une barre de progression pendant les compilations.
•
bar-with-logs
Affiche les logs bruts, avec la barre de progression en bas.
•
--no-build-output / -Q
Par défaut, la sortie produite par les constructeurs sur la sortie standard et la sortie standard d'erreur est également affichée sur la sortie standard d'erreur de la commande Nix. Cette option supprime ce comportement. Notez que la sortie standard et l'erreur standard du constructeur sont toujours écrites dans un fichier journal dans prefix/nix/var/log/nix.
•
--max-jobs / -j nombre
auto pour utiliser le nombre de processeurs du système. La valeur par défaut est définie par le paramètre de configuration max-jobs, qui est lui-même défini par défaut sur 1. Une valeur plus élevée est utile sur les systèmes SMP ou pour exploiter la latence d'E/S.
Le définir à 0 interdit la construction sur la machine locale, ce qui est utile lorsque vous souhaitez que les constructions n'aient lieu que sur des constructeurs distants.
•
--cores
Définit la valeur de la variable d'environnement NIX_BUILD_CORES lors de l'invocation des constructeurs. Les constructeurs peuvent utiliser cette variable à leur discrétion pour contrôler le parallélisme maximal. Par exemple, dans Nixpkgs, si l'attribut de dérivation enableParallelBuilding est défini sur true, le constructeur transmet le drapeau -jN à GNU Make. Par défaut, il prend la valeur du paramètre de configuration cores, s'il est défini, ou 1 sinon. La valeur 0 signifie que le constructeur doit utiliser tous les cœurs de processeur disponibles dans le système.
•
--max-silent-time
Définit le nombre maximum de secondes pendant lesquelles un constructeur peut s'exécuter sans produire de données sur la sortie standard ou la sortie d'erreur. La valeur par défaut est définie par le paramètre de configuration max-silent-time. 0 signifie pas de délai d'attente.
•
--timeout
Définit le nombre maximum de secondes pendant lesquelles un constructeur peut s'exécuter. La valeur par défaut est définie par le paramètre de configuration timeout. 0 signifie pas de délai d'attente.
•
--keep-going / -k
Continue en cas d'échec de constructions, dans la mesure du possible. C'est-à-dire que si la construction d'une entrée de certaines dérivations échoue, Nix construira toujours les autres entrées, mais pas la dérivation elle-même. Sans cette option, Nix s'arrête si une construction échoue (sauf pour les constructions de substituts), tuant potentiellement les constructions en cours (en cas de constructions parallèles ou distribuées).
•
--keep-failed / -K
Spécifie qu'en cas d'échec de construction, le répertoire temporaire (généralement dans /tmp) dans lequel la construction a lieu ne doit pas être supprimé. Le chemin du répertoire de construction est affiché sous forme de message informatif.
•
--fallback
Chaque fois que Nix tente de construire une dérivation pour laquelle des substituts sont connus pour chaque chemin de sortie, mais que la réalisation des chemins de sortie par le biais des substituts échoue, Nix se rabat sur la construction de la dérivation.
Le scénario le plus courant où cela est utile est lorsque nous avons enregistré des substituts afin d'effectuer une distribution binaire à partir, par exemple, d'un dépôt réseau. Si le dépôt est en panne, la réalisation de la dérivation échouera. Lorsque cette option est spécifiée, Nix construira la dérivation à la place. Ainsi, l'installation à partir de binaires se rabat sur l'installation à partir des sources. Cette option n'est pas activée par défaut car il n'est généralement pas souhaitable qu'un échec transitoire dans l'obtention des substituts conduise à une construction complète à partir des sources (avec la consommation de ressources associée).
•
--readonly-mode
Lorsque cette option est utilisée, aucune tentative n'est faite pour ouvrir la base de données Nix. La plupart des opérations Nix nécessitent un accès à la base de données, donc ces opérations échoueront.
•
--arg nom valeur
Cette option est acceptée par nix-env, nix-instantiate, nix-shell et nix-build. Lors de l'évaluation des expressions Nix, l'évaluateur d'expressions essaiera automatiquement d'appeler les fonctions qu'il rencontre. Il peut appeler automatiquement les fonctions pour lesquelles chaque argument a une valeur par défaut (par exemple, { argName ? defaultValue }: ...).
Avec --arg, vous pouvez également appeler des fonctions qui ont des arguments sans valeur par défaut (ou remplacer une valeur par défaut). C'est-à-dire que si l'évaluateur rencontre une fonction avec un argument nommé nom, il l'appellera avec la valeur valeur.
Par exemple, le default.nix de haut niveau dans Nixpkgs est en fait une fonction :
{ # Le système (par exemple, `i686-linux') pour lequel construire les paquets.
system ? builtins.currentSystem
...
}: ...
Ainsi, si vous appelez cette expression Nix (par exemple, lorsque vous faites nix-env --install --attr pkgname), la fonction sera appelée automatiquement en utilisant la valeur builtins.currentSystem pour l'argument system. Vous pouvez la remplacer en utilisant --arg, par exemple, nix-env --install --attr pkgname --arg system \"i686-freebsd\". (Notez que puisque l'argument est une chaîne de caractères littérale Nix, vous devez échapper les guillemets.)
•
--argstr nom valeur
Cette option est similaire à --arg, sauf que la valeur n'est pas une expression Nix mais une chaîne de caractères. Donc, au lieu de --arg system \"i686-linux\" (les guillemets extérieurs servent à contenter le shell), vous pouvez dire --argstr system i686-linux.
•
--attr / -A attrPath
Sélectionne un attribut de l'expression Nix de haut niveau en cours d'évaluation. (nix-env, nix-instantiate, nix-build et nix-shell uniquement.) Le chemin d'attribut attrPath est une séquence de noms d'attributs séparés par des points. Par exemple, étant donné une expression Nix de haut niveau e, le chemin d'attribut xorg.xorgserver utiliserait l'expression e.xorg.xorgserver. Voir nix-env --install pour des exemples concrets.
En plus des noms d'attributs, vous pouvez également spécifier des indices de tableau. Par exemple, le chemin d'attribut foo.3.bar sélectionne l'attribut bar du quatrième élément du tableau dans l'attribut foo de l'expression de haut niveau.
•
--expr / -E
Interprète les arguments de la ligne de commande comme une liste d'expressions Nix à analyser et évaluer, plutôt que comme une liste de noms de fichiers d'expressions Nix. (nix-instantiate, nix-build et nix-shell uniquement.)
Pour nix-shell, cette option est couramment utilisée pour vous fournir un shell dans lequel vous pouvez construire les paquets renvoyés par l'expression. Si vous souhaitez obtenir un shell contenant les paquets construits prêts à l'emploi, donnez plutôt votre expression à l'option de commodité nix-shell --packages.
•
-I / --include chemin
Ajoute une entrée à la liste des chemins de recherche utilisés pour résoudre les chemins de recherche. Cette option peut être donnée plusieurs fois.
Les chemins ajoutés via -I ont la priorité sur le paramètre de configuration nix-path et la variable d'environnement NIX_PATH .
•
--option nom valeur
Définit l'option de configuration Nix nom sur valeur. Ceci annule les paramètres du fichier de configuration Nix (voir nix.conf5).
•
--repair
Corrige les chemins de magasin corrompus ou manquants en les redownloadant ou en les reconstruisant. Notez que c'est lent car cela nécessite de calculer un hachage cryptographique du contenu de chaque chemin dans la fermeture de la construction. Notez également l'avertissement sous nix-store --repair-path.

Note

Voir man nix.conf pour annuler les paramètres de configuration avec des drapeaux de ligne de commande.

Variables d'environnement courantes

La plupart des commandes Nix interprètent les variables d'environnement suivantes :

•
IN_NIX_SHELL
Indicateur indiquant si l'environnement actuel a été configuré par nix-shell. Il peut avoir les valeurs pure ou impure.

Name

nix - An advanced application for managing resources.

SYNOPSIS

nix [option...] command [argument...]
nix-build [option...] [file]
nix-shell [option...] [file]
nix-env [option...] [argument...]
nix-store [option...] command [argument...]
nix-search [option...] query
nix-instantiate [option...] [file]
nix-collect-garbage [option...]
nix-channel [option...] command [argument...]
nix-daemon [option...]
nix-upgrade-store [option...]
nix-cat-store [option...] path...

Description

Nix is a powerful package manager for Linux and other Unix-like systems that focuses on reproducible builds and atomic upgrades. It provides a unique approach to package management by treating packages as first-class values in a purely functional language. This enables features like:

  • Reproducibility: Builds are guaranteed to be repeatable, regardless of the environment they are built in.
  • Atomic Upgrades: Upgrades are atomic, meaning they either succeed completely or fail, leaving the system in its previous state.
  • Rollbacks: Easy rollback to previous versions of packages or the entire system.
  • Multiple Versions: Multiple versions of the same package can be installed simultaneously without conflict.
  • Reliability: Builds are isolated and do not affect the rest of the system until explicitly installed.

This manual page describes the various commands and environment variables related to Nix.

Options

The main Nix command, nix, acts as a dispatcher to subcommands like nix-build, nix-shell, etc. Many options are common across these subcommands.

Common Options

The following options are available for most Nix commands:

•
NIX_PATH
Une liste d'entrées de chemin de recherche séparées par des deux-points utilisée pour résoudre les chemins de recherche.
Cette variable d'environnement remplace la valeur du paramètre de configuration nix-path.
Elle peut être étendue en utilisant l' option -I.
Exemple
$ export NIX_PATH=`/home/eelco/Dev:nixos-config=/etc/nixos`
Si NIX_PATH est défini sur une chaîne vide, la résolution des chemins de recherche échouera toujours.
Exemple
$ NIX_PATH= nix-instantiate --eval '<nixpkgs>'
error: file 'nixpkgs' was not found in the Nix search path (add it using $NIX_PATH or -I)
•
NIX_IGNORE_SYMLINK_STORE
Normalement, le répertoire du magasin Nix (typiquement /nix/store) ne peut pas contenir de composants de lien symbolique. Ceci est fait pour éviter les constructions « impures ». Les constructeurs « canonicalisent » parfois les chemins en résolvant tous les composants de lien symbolique. Ainsi, les constructions sur différentes machines (avec /nix/store résolvant vers différents emplacements) pourraient donner des résultats différents. Ceci n'est généralement pas un problème, sauf lorsque les constructions sont déployées sur des machines où /nix/store résout différemment. Si vous êtes sûr que vous n'allez pas faire cela, vous pouvez définir NIX_IGNORE_SYMLINK_STORE à 1.
Notez que si vous utilisez des liens symboliques vers le magasin Nix afin de le placer sur un autre système de fichiers que le système de fichiers racine, sous Linux, il est préférable d'utiliser des points de montage bind, par exemple :
$ mkdir /nix
$ mount -o bind /mnt/otherdisk/nix /nix
Consultez la page de manuel de mount 8 pour plus de détails.
•
NIX_STORE_DIR
Remplace l'emplacement du magasin Nix (par défaut prefix/store).
•
NIX_DATA_DIR
Remplace l'emplacement du répertoire de données statiques Nix (par défaut prefix/share).
•
NIX_LOG_DIR
Remplace l'emplacement du répertoire de journaux Nix (par défaut prefix/var/log/nix).
•
NIX_STATE_DIR
Remplace l'emplacement du répertoire d'état Nix (par défaut prefix/var/nix).
•
NIX_CONF_DIR
Remplace l'emplacement du répertoire de configuration système Nix (par défaut prefix/etc/nix).
•
NIX_CONFIG
Applique les paramètres de la configuration Nix depuis l'environnement. Le contenu est traité comme s'il était lu à partir d'un fichier de configuration Nix. Les paramètres sont séparés par un caractère de nouvelle ligne.
•
NIX_USER_CONF_FILES
Remplace l'emplacement des fichiers de configuration utilisateur Nix à charger depuis.
Les valeurs par défaut sont les emplacements conformes à la Spécification des répertoires de base XDG. Voir la sous-section Répertoires de base XDG pour plus de détails.
La variable est traitée comme une liste séparée par le jeton :.
•
TMPDIR
Utilise le répertoire spécifié pour stocker les fichiers temporaires. Notamment, cela inclut les répertoires de construction temporaires ; ceux-ci peuvent occuper une quantité substantielle d'espace disque. La valeur par défaut est /tmp.
•
NIX_REMOTE
Cette variable doit être définie sur daemon si vous souhaitez utiliser le démon Nix pour exécuter les opérations Nix. Ceci est nécessaire dans les installations Nix multi-utilisateurs. Si le socket Unix du démon Nix se trouve à un chemin non standard, cette variable doit être définie sur unix://path/to/socket. Sinon, elle doit être laissée non définie.
•
NIX_SHOW_STATS
Si elle est définie sur 1, Nix affichera certaines statistiques d'évaluation, telles que le nombre de valeurs allouées.
•
NIX_COUNT_CALLS
Si elle est définie sur 1, Nix affichera le nombre de fois que les fonctions ont été appelées lors de l'évaluation des expressions Nix. Ceci est utile pour profiler vos expressions Nix.
•
GC_INITIAL_HEAP_SIZE
Si Nix a été configuré pour utiliser le garbage collector de Boehm, cette variable définit la taille initiale du tas en octets. Elle est par défaut à 384 Mio. La définir sur une valeur faible réduit la consommation de mémoire, mais augmentera le temps d'exécution en raison du surcoût de la collecte de déchets.

Répertoires de base XDG

Nix suit la Spécification des répertoires de base XDG.

Pour des raisons de compatibilité ascendante, les commandes Nix ne suivront la norme que lorsque use-xdg-base-directories est activé. Les nouvelles commandes Nix (expérimentales) sont conformes à la norme par défaut.

Les variables d'environnement suivantes sont utilisées pour déterminer les emplacements des divers fichiers d'état et de configuration :

  • [XDG_CONFIG_HOME]{#env-XDGCONFIGHOME} (par défaut ~/.config)
  • [XDG_STATE_HOME]{#env-XDGSTATEHOME} (par défaut ~/.local/state)
  • [XDG_CACHE_HOME]{#env-XDGCACHEHOME} (par défaut ~/.cache)
