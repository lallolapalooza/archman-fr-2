Paquet: nix

nix-instantiate(1) Manuel des commandes générales nix-instantiate(1)

Nom

nix-instantiate - créer des dérivations du magasin à partir d'expressions Nix

Synopsis

nix-instantiate [--parse | --eval [--strict] [--json] [--xml] ] [--read-write-mode] [--arg nom valeur] [{--attr| -A} cheminAttribut] [--add-root chemin] [--expr | -E] fichiers…

nix-instantiate --find-file fichiers…

Description

La commande nix-instantiate produit des dérivations du magasin à partir d'expressions Nix (de haut niveau). Elle évalue les expressions Nix dans chacun des fichiers (qui par défaut est ./default.nix). Chaque expression de premier niveau doit s'évaluer en une dérivation, une liste de dérivations ou un ensemble de dérivations. Les chemins des dérivations du magasin résultantes sont imprimés sur la sortie standard.

Si fichiers est le caractère -, alors une expression Nix sera lue depuis l'entrée standard.

Options

•
--add-root chemin
Voir l'option correspondante dans nix-store.
•
--parse
Seulement analyser les fichiers d'entrée, et imprimer leurs arbres syntaxiques abstraits sur la sortie standard sous forme d'une expression Nix.
•
--eval
Seulement analyser et évaluer les fichiers d'entrée, et imprimer les valeurs résultantes sur la sortie standard. Aucune instanciation de dérivations du magasin n'a lieu.
Attention
Cette option produit une sortie qui peut être analysée comme une expression Nix qui produira un résultat différent de l'expression d'entrée lors de son évaluation. Par exemple, ces deux expressions Nix impriment le même résultat malgré des significations différentes :
$ nix-instantiate --eval --expr '{ a = {}; }'
{ a = <CODE>; }
$ nix-instantiate --eval --expr '{ a = <CODE>; }'
{ a = <CODE>; }
Pour une sortie lisible par l'homme, nix eval (expérimental) est plus informatif :
$ nix-instantiate --eval --expr 'a: a'
<LAMBDA>
$ nix eval --expr 'a: a'
«lambda @ «string»:1:1»
Pour une sortie lisible par machine, l'option --xml produit une sortie sans ambiguïté :
$ nix-instantiate --eval --xml --expr '{ foo = <CODE>; }'
<?xml version='1.0' encoding='utf-8'?>
<expr>
  <attrs>
    <attr column="3" line="1" name="foo">
      <unevaluated />
    </attr>
  </attrs>
</expr>
•
--find-file
Recherche les fichiers donnés dans le chemin de recherche de Nix (tel que spécifié par la variable d'environnement NIX_PATH). S'ils sont trouvés, imprime les chemins absolus correspondants sur la sortie standard. Par exemple, si NIX_PATH est nixpkgs=/home/alice/nixpkgs, alors nix-instantiate --find-file nixpkgs/default.nix imprimera /home/alice/nixpkgs/default.nix.
•
--strict
Lorsqu'il est utilisé avec --eval, évalue récursivement les éléments de liste et les attributs. Normalement, de telles sous-expressions sont laissées non évaluées (puisque le langage Nix est paresseux).
Attention
Cette option peut entraîner une non-terminaison, car les structures de données paresseuses peuvent être infinies.
•
--json
Lorsqu'il est utilisé avec --eval, imprime la valeur résultante sous forme de représentation JSON de l'arbre syntaxique abstrait plutôt que sous forme d'expression Nix.
•
--xml
Lorsqu'il est utilisé avec --eval, imprime la valeur résultante sous forme de représentation XML de l'arbre syntaxique abstrait plutôt que sous forme d'expression Nix. Le schéma est le même que celui utilisé par le built-in toXML.
•
--read-write-mode
Lorsqu'il est utilisé avec --eval, effectue l'évaluation en mode lecture/écriture afin que les fonctionnalités du langage Nix qui le nécessitent fonctionnent toujours (au prix de l'instanciation de chaque dérivation évaluée). Si cette option n'est pas activée, il peut y avoir des chemins de magasin non instanciés dans la sortie finale.

Options communes

La plupart des commandes Nix acceptent les options de ligne de commande suivantes :

•
--help
Imprime un résumé de la syntaxe de la commande et quitte.
•
--version
Imprime le numéro de version de Nix sur la sortie standard et quitte.
•
--verbose / -v
Augmente le niveau de verbosité des messages de diagnostic imprimés sur la sortie d'erreur standard. Pour chaque opération Nix, les informations imprimées sur la sortie standard sont bien définies ; toute information de diagnostic est imprimée sur la sortie d'erreur standard, jamais sur la sortie standard.
Cette option peut être spécifiée de manière répétée. Actuellement, les niveaux de verbosité suivants existent :
•
0 « Erreurs seulement »
Imprime uniquement les messages expliquant pourquoi l'invocation Nix a échoué.
•
1 « Informatif »
Imprime des messages *utiles* sur ce que Nix fait. C'est le comportement par défaut.
•
2 « Bavard »
Imprime plus de messages informatifs.
•
3 « Très bavard »
Imprime encore plus de messages informatifs.
•
4 « Débogage »
Imprime des informations de débogage.
•
5 « Vomitif »
Imprime une quantité énorme d'informations de débogage.
•
--quiet
Diminue le niveau de verbosité des messages de diagnostic imprimés sur la sortie d'erreur standard. C'est l'option inverse de -v / --verbose.
Cette option peut être spécifiée de manière répétée. Voir la liste précédente des niveaux de verbosité.
•
--log-format format

Ce site n'est en aucun cas associé à Arch Linux ni affilié à ce projet. Le contenu est uniquement une traduction des pages de manuel d'Arch publiées sur man.archlinux.org.

>
Cette option peut être utilisée pour modifier le format de sortie du journal, format étant l'un des éléments suivants :
•
raw
C'est le format brut, tel qu'il est produit par nix-build.
•
internal-json
Produit les journaux dans un format structuré.
Attention
Bien que le schéma soit relativement stable, le format des messages d'erreur (notamment du champ msg) peut changer d'une version à l'autre.
•
bar
Affiche uniquement une barre de progression pendant les builds.
•
bar-with-logs
Affiche les journaux bruts, avec la barre de progression en bas.
•
--no-build-output / -Q
Par défaut, la sortie écrite par les constructeurs vers la sortie standard et l'erreur standard est renvoyée vers l'erreur standard de la commande Nix. Cette option supprime ce comportement. Notez que la sortie standard et l'erreur standard du constructeur sont toujours écrites dans un fichier journal dans prefix/nix/var/log/nix.
•
--max-jobs / -j nombre
Définit le nombre maximum de travaux de build que Nix effectuera en parallèle au nombre spécifié. Spécifiez auto pour utiliser le nombre de CPU du système. La valeur par défaut est spécifiée par le paramètre de configuration max-jobs, qui est lui-même par défaut à 1. Une valeur plus élevée est utile sur les systèmes SMP ou pour exploiter la latence d'E/S.
La définir à 0 interdit la construction sur la machine locale, ce qui est utile lorsque vous souhaitez que les builds se produisent uniquement sur des constructeurs distants.
•
--cores
Définit la valeur de la variable d'environnement NIX_BUILD_CORES dans l'invocation des constructeurs. Les constructeurs peuvent utiliser cette variable à leur discrétion pour contrôler le parallélisme maximal. Par exemple, dans Nixpkgs, si l'attribut de dérivation enableParallelBuilding est défini sur true, le constructeur transmet le drapeau -jN à GNU Make. Il utilise par défaut la valeur du paramètre de configuration cores, s'il est défini, ou 1 sinon. La valeur 0 signifie que le constructeur doit utiliser tous les cœurs de CPU disponibles dans le système.
•
--max-silent-time
Définit le nombre maximum de secondes pendant lesquelles un constructeur peut rester sans produire de données sur la sortie standard ou l'erreur standard. La valeur par défaut est spécifiée par le paramètre de configuration max-silent-time. 0 signifie pas de délai d'expiration.
•
--timeout
Définit le nombre maximum de secondes pendant lesquelles un constructeur peut s'exécuter. La valeur par défaut est spécifiée par le paramètre de configuration timeout. 0 signifie pas de délai d'expiration.
•
--keep-going / -k
Continuer en cas d'échec des builds, dans la plus grande mesure possible. C'est-à-dire, si la construction d'une entrée de certaines dérivations échoue, Nix construira toujours les autres entrées, mais pas la dérivation elle-même. Sans cette option, Nix s'arrête si un build échoue (sauf pour les builds de substituts), tuant éventuellement les builds en cours (en cas de builds parallèles ou distribués).
•
--keep-failed / -K
Spécifie qu'en cas d'échec de construction, le répertoire temporaire (généralement dans /tmp) dans lequel la construction a lieu ne doit pas être supprimé. Le chemin du répertoire de build est imprimé comme message d'information.
•
--fallback
Chaque fois que Nix tente de construire une dérivation pour laquelle des substituts sont connus pour chaque chemin de sortie, mais que la réalisation des chemins de sortie par les substituts échoue, il tente de construire la dérivation.
Le scénario le plus courant pour lequel cela est utile est lorsque nous avons enregistré des substituts pour effectuer une distribution binaire à partir, par exemple, d'un dépôt réseau. Si le dépôt est en panne, la réalisation de la dérivation échouera. Lorsque cette option est spécifiée, Nix construira la dérivation à la place. Ainsi, l'installation à partir de binaires se rabat sur l'installation à partir des sources. Cette option n'est pas activée par défaut car il n'est généralement pas souhaitable qu'un échec transitoire dans l'obtention des substituts entraîne une construction complète à partir des sources (avec la consommation associée de ressources).
•
--readonly-mode
Lorsque cette option est utilisée, aucune tentative n'est faite pour ouvrir la base de données Nix. La plupart des opérations Nix nécessitent un accès à la base de données, donc ces opérations échoueront.
•
--arg nom valeur
Cette option est acceptée par nix-env, nix-instantiate, nix-shell et nix-build. Lors de l'évaluation des expressions Nix, l'évaluateur d'expressions tentera automatiquement d'appeler les fonctions qu'il rencontre. Il peut automatiquement appeler les fonctions pour lesquelles tous les arguments ont une valeur par défaut (par exemple, { argName ? defaultValue }: ...).
Avec --arg, vous pouvez également appeler des fonctions qui ont des arguments sans valeur par défaut (ou remplacer une valeur par défaut). C'est-à-dire, si l'évaluateur rencontre une fonction avec un argument nommé nom, il l'appellera avec la valeur valeur.
Par exemple, le default.nix de haut niveau dans Nixpkgs est en fait une fonction :
{ # Le système (par exemple, `i686-linux') pour lequel construire les paquets.
system ? builtins.currentSystem
...
}: ...
Ainsi, si vous appelez cette expression Nix (par exemple, lorsque vous faites nix-env --install --attr pkgname), la fonction sera appelée automatiquement en utilisant la valeur builtins.currentSystem pour l'argument system. Vous pouvez le remplacer en utilisant --arg, par exemple, nix-env --install --attr pkgname --arg system \"i686-freebsd\". (Notez que comme l'argument est une chaîne littérale Nix, vous devez échapper les guillemets.)
•
--argstr nom valeur
Cette option est comme --arg, seulement la valeur n'est pas une expression Nix mais une chaîne. Donc au lieu de --arg system \"i686-linux\" (les guillemets extérieurs sont pour que le shell soit content) vous pouvez dire --argstr system i686-linux.
•
--attr / -A attrPath
Sélectionne un attribut de l'expression Nix de haut niveau en cours d'évaluation. (Uniquement pour nix-env, nix-instantiate, nix-build et nix-shell.) Le chemin d'attribut attrPath est une séquence de noms d'attributs séparés par des points. Par exemple, étant donné une expression Nix de haut niveau e, le chemin d'attribut xorg.xorgserver entraînerait l'utilisation de l'expression e.xorg.xorgserver. Voir nix-env --install pour des exemples concrets.
En plus des noms d'attributs, vous pouvez également spécifier des indices de tableau. Par exemple, le chemin d'attribut foo.3.bar sélectionne l'attribut bar du quatrième élément du tableau dans l'attribut foo de l'expression de haut niveau.
•
--expr / -E
Interprète les arguments de la ligne de commande comme une liste d'expressions Nix à analyser et évaluer, plutôt que comme une liste de noms de fichiers d'expressions Nix. (Uniquement pour nix-instantiate, nix-build et nix-shell.)
Pour nix-shell, cette option est couramment utilisée pour vous donner un shell dans lequel vous pouvez construire les paquets renvoyés par l'expression. Si vous souhaitez obtenir un shell contenant les paquets *construits* prêts à l'emploi, donnez plutôt votre expression à l'option de commodité nix-shell --packages.
•
-I / --include chemin
Ajoute une entrée à la liste des chemins de recherche utilisés pour résoudre les chemins de recherche . Cette option peut être donnée plusieurs fois.
Les chemins ajoutés via -I ont la priorité sur le paramètre de configuration nix-path et la variable d'environnement NIX_PATH.
•
--option nom valeur
Définit l'option de configuration Nix nom sur valeur. Ceci remplace les paramètres du fichier de configuration Nix (voir nix.conf5).
•
--repair
Corrige les chemins de magasin corrompus ou manquants en les retéléchargeant ou les reconstruisant. Notez que cela est lent car cela nécessite de calculer un hachage cryptographique du contenu de chaque chemin dans la fermeture de la construction. Notez également l'avertissement sous nix-store --repair-path.

Note

Voir man nix.conf pour substituer les paramètres de configuration avec des indicateurs de ligne de commande.

Variables d'environnement communes

La plupart des commandes Nix interprètent les variables d'environnement suivantes :

•
IN_NIX_SHELL
Indicateur indiquant si l'environnement actuel a été configuré par nix-shell. Il peut avoir les valeurs pure ou impure.
•
NIX_PATH
Une liste d'entrées de chemins de recherche séparées par des deux-points, utilisée pour résoudre les chemins de recherche.
Cette variable d'environnement remplace la valeur du paramètre de configuration nix-path.
Elle peut être étendue en utilisant l'option -I.
Exemple
$ export NIX_PATH=`/home/eelco/Dev:nixos-config=/etc/nixos
Si NIX_PATH est défini sur une chaîne vide, la résolution des chemins de recherche échouera toujours.
Exemple
$ NIX_PATH= nix-instantiate --eval '<nixpkgs>'
error: file 'nixpkgs' was not found in the Nix search path (add it using $NIX_PATH or -I)
•
NIX_IGNORE_SYMLINK_STORE
Normalement, le répertoire du magasin Nix (typiquement /nix/store) n'est pas autorisé à contenir de composants de liens symboliques. Ceci est fait pour empêcher les constructions « impures ». Les constructeurs « canonicalisent » parfois les chemins en résolvant tous les composants de liens symboliques. Ainsi, des constructions sur différentes machines (avec /nix/store résolvant vers différents emplacements) pourraient donner des résultats différents. Ce n'est généralement pas un problème, sauf lorsque les constructions sont déployées sur des machines où /nix/store résout différemment. Si vous êtes sûr que vous n'allez pas faire cela, vous pouvez définir NIX_IGNORE_SYMLINK_STORE sur 1.
Notez que si vous utilisez des liens symboliques pour le magasin Nix afin de pouvoir le placer sur un autre système de fichiers que le système de fichiers racine, sous Linux, il est préférable d'utiliser des points de montage bind, par exemple :
$ mkdir /nix
$ mount -o bind /mnt/otherdisk/nix /nix
Consultez la page de manuel de mount 8 pour plus de détails.
•
NIX_STORE_DIR
Remplace l'emplacement du magasin Nix (par défaut prefix/store).
•
NIX_DATA_DIR
Remplace l'emplacement du répertoire de données statiques Nix (par défaut prefix/share).
•
NIX_LOG_DIR
Remplace l'emplacement du répertoire de journaux Nix (par défaut prefix/var/log/nix).
•
NIX_STATE_DIR
Remplace l'emplacement du répertoire d'état Nix (par défaut prefix/var/nix).
•
NIX_CONF_DIR
Remplace l'emplacement du répertoire de configuration Nix système (par défaut prefix/etc/nix).
•
NIX_CONFIG
Applique des paramètres de la configuration Nix depuis l'environnement. Le contenu est traité comme s'il était lu à partir d'un fichier de configuration Nix. Les paramètres sont séparés par le caractère de nouvelle ligne.
•
NIX_USER_CONF_FILES
Remplace l'emplacement des fichiers de configuration utilisateur Nix à charger.
Les valeurs par défaut sont les emplacements conformes aux spécifications du XDG Base Directory Specification. Voir la sous-section XDG Base Directories pour plus de détails.
La variable est traitée comme une liste séparée par le jeton :.
•
TMPDIR
Utilise le répertoire spécifié pour stocker les fichiers temporaires. En particulier, cela inclut les répertoires de construction temporaires ; ceux-ci peuvent consommer une quantité substantielle d'espace disque. La valeur par défaut est /tmp.
•
NIX_REMOTE
Cette variable doit être définie sur daemon si vous souhaitez utiliser le démon Nix pour exécuter les opérations Nix. C'est nécessaire dans les installations Nix multi-utilisateurs. Si le socket Unix du démon Nix se trouve à un chemin non standard, cette variable doit être définie sur unix://path/to/socket. Sinon, elle doit être laissée non définie.
•
NIX_SHOW_STATS
Si elle est définie sur 1, Nix affichera des statistiques d'évaluation, comme le nombre de valeurs allouées.
•
NIX_COUNT_CALLS
Si elle est définie sur 1, Nix affichera le nombre de fois où les fonctions ont été appelées pendant l'évaluation des expressions Nix. Ceci est utile pour profiler vos expressions Nix.
•
GC_INITIAL_HEAP_SIZE
Si Nix a été configuré pour utiliser le ramasse-miettes Boehm, cette variable définit la taille initiale du tas en octets. Elle est par défaut à 384 Mio. La définir sur une valeur faible réduit la consommation de mémoire, mais augmentera le temps d'exécution en raison de la surcharge de la collecte des déchets.

XDG Base Directories

Nix suit la XDG Base Directory Specification.

Pour des raisons de compatibilité ascendante, les commandes Nix ne suivront la norme que lorsque use-xdg-base-directories est activé. Les nouvelles commandes Nix (expérimentales) suivent la norme par défaut.

Les variables d'environnement suivantes sont utilisées pour déterminer les emplacements des divers fichiers d'état et de configuration :

  • [XDG_CONFIG_HOME]{#env-XDGCONFIGHOME} (par défaut ~/.config)
  • [XDG_STATE_HOME]{#env-XDGSTATEHOME} (par défaut ~/.local/state)
  • [XDG_CACHE_HOME]{#env-XDGCACHEHOME} (par défaut ~/.cache)

Exemples

Instancie des dérivations de magasin à partir d'une expression Nix, et construit-les en utilisant nix-store :

$ nix-instantiate test.nix (instancier)
/nix/store/cigxbmvy6dzix98dxxh9b6shg7ar5bvs-perl-BerkeleyDB-0.26.drv
$ nix-store --realise $(nix-instantiate test.nix) (construire)
...
/nix/store/qhqk4n8ci095g3sdp93x7rgwyh9rdvgk-perl-BerkeleyDB-0.26 (chemin de sortie)
$ ls -l /nix/store/qhqk4n8ci095g3sdp93x7rgwyh9rdvgk-perl-BerkeleyDB-0.26
dr-xr-xr-x    2 eelco    users        4096 1970-01-01 01:00 lib
...

Vous pouvez également donner une expression Nix sur la ligne de commande :

$ nix-instantiate --expr 'with import <nixpkgs> { }; hello'
/nix/store/j8s4zyv75a724q38cb0r87rlczaiag4y-hello-2.8.drv

Ceci est équivalent à :

$ nix-instantiate '<nixpkgs>' --attr hello

Analyser et évaluer des expressions Nix :

$ nix-instantiate --parse --expr '1
+ 2' 1 + 2 
$ nix-instantiate --eval --expr '1 + 2'
3
$ nix-instantiate --eval --xml --expr '1 + 2'
<?xml version='1.0' encoding='utf-8'?>
<expr>
  <int value="3" />
</expr>

La différence entre l'évaluation non stricte et l'évaluation stricte :

$ nix-instantiate --eval --xml --expr '{ x = {}; }'
<?xml version='1.0' encoding='utf-8'?>
<expr>
  <attrs>
    <attr column="3" line="1" name="x">
      <unevaluated />
    </attr>
  </attrs>
</expr>
$ nix-instantiate --eval --xml --strict --expr '{ x = {}; }'
<?xml version='1.0' encoding='utf-8'?>
<expr>
  <attrs>
    <attr column="3" line="1" name="x">
      <attrs>
      </attrs>
    </attr>
  </attrs>
</expr>
