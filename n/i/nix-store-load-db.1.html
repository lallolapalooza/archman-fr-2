nix-store --load-db(1) Manuel des commandes générales nix-store --load-db(1)

Nom

nix-store --load-db - importer la base de données Nix

Synopsis

nix-store --load-db

Description

L'opération --load-db lit une sauvegarde de la base de données Nix créée par --dump-db depuis l'entrée standard et l'importe dans la base de données Nix.

Options

Les options suivantes sont autorisées pour toutes les opérations nix-store, mais peuvent ne pas avoir d'effet.

•
--add-root chemin
Induit que le résultat d'une réalisation (--realise et --force-realise) soit enregistré comme une racine du collecteur de déchets (garbage collector). chemin sera créé comme un lien symbolique vers le chemin de magasin résultant. De plus, un lien symbolique au nom unique vers chemin sera créé dans /nix/var/nix/gcroots/auto/. Par exemple,
$ nix-store --add-root /home/eelco/bla/result --realise ...
$ ls -l /nix/var/nix/gcroots/auto
lrwxrwxrwx    1 ... 2005-03-13 21:10 dn54lcypm8f8... -> /home/eelco/bla/result
$ ls -l /home/eelco/bla/result
lrwxrwxrwx    1 ... 2005-03-13 21:10 /home/eelco/bla/result -> /nix/store/1r11343n6qd4...-f-spot-0.0.10
Ainsi, lorsque /home/eelco/bla/result est supprimé, la racine GC dans le répertoire auto devient un lien symbolique orphelin et sera ignorée par le collecteur.
Attention
Notez qu'il n'est pas possible de déplacer ou de renommer les racines GC, car le lien symbolique dans le répertoire auto pointera toujours vers l'ancien emplacement.
S'il y a plusieurs résultats, plusieurs liens symboliques seront créés en numérotant séquentiellement les liens symboliques au-delà du premier (par exemple, foo, foo-2, foo-3, et ainsi de suite).

Options communes

La plupart des commandes Nix acceptent les options de ligne de commande suivantes :

•
--help
Affiche un résumé de la syntaxe de la commande et quitte.
•
--version
Affiche le numéro de version de Nix sur la sortie standard et quitte.
•
--verbose / -v
Augmente le niveau de verbosité des messages de diagnostic affichés sur la sortie d'erreur standard. Pour chaque opération Nix, les informations affichées sur la sortie standard sont bien définies ; toute information de diagnostic est affichée sur la sortie d'erreur standard, jamais sur la sortie standard.
Cette option peut être spécifiée de manière répétée. Actuellement, les niveaux de verbosité suivants existent :
•
0 « Erreurs seulement »
Affiche uniquement les messages expliquant pourquoi l'invocation Nix a échoué.
•
1 « Informatif »
Affiche des messages *utiles* sur ce que Nix est en train de faire. C'est la valeur par défaut.
•
2 « Bavard »
Affiche plus de messages informatifs.
•
3 « Verbeux »
Affiche encore plus de messages informatifs.
•
4 « Débogage »
Affiche des informations de débogage.
•
5 « Vomir »
Affiche des quantités énormes d'informations de débogage.
•
--quiet
Diminue le niveau de verbosité des messages de diagnostic affichés sur la sortie d'erreur standard. C'est l'option inverse de -v / --verbose.
Cette option peut être spécifiée de manière répétée. Voir la liste des niveaux de verbosité précédents.
•
--log-format format
Cette option peut être utilisée pour modifier le format de sortie du log, avec format étant l'un des suivants :
•
raw
C'est le format brut, tel qu'il est produit par nix-build.
•
internal-json
Affiche les logs de manière structurée.
Attention
Bien que le schéma lui-même soit relativement stable, le format des messages d'erreur (notamment du champ msg) peut changer entre les versions.
•
bar
Affiche uniquement une barre de progression pendant les compilations.
•
bar-with-logs
Affiche les logs bruts, avec la barre de progression en bas.
•
--no-build-output / -Q
Par défaut, la sortie écrite par les constructeurs (builders) sur la sortie standard et l'erreur standard est répercutée sur la sortie d'erreur de la commande Nix. Cette option supprime ce comportement. Notez que la sortie standard et l'erreur standard du constructeur sont toujours écrites dans un fichier log dans prefix/nix/var/log/nix.
•
--max-jobs / -j nombre
Définit le nombre maximum de tâches de construction (build jobs) que Nix effectuera en parallèle au nombre spécifié. Spécifiez auto pour utiliser le nombre de CPU du système. La valeur par défaut est spécifiée par le paramètre de configuration max-jobs, qui définit par défaut à 1. Une valeur plus élevée est utile sur les systèmes SMP ou pour exploiter la latence d'E/S.
Le régler à 0 interdit la construction sur la machine locale, ce qui est utile lorsque vous souhaitez que les constructions se fassent uniquement sur des constructeurs distants.
•
--cores
Définit la valeur de la variable d'environnement NIX_BUILD_CORES dans l'invocation des constructeurs. Les constructeurs peuvent utiliser cette variable à leur discrétion pour contrôler le parallélisme maximum. Par exemple, dans Nixpkgs, si l'attribut de construction enableParallelBuilding est défini sur true, le constructeur passe le drapeau -jN à GNU Make. Il utilise par défaut la valeur du paramètre de configuration cores, si défini, ou 1 sinon. La valeur 0 signifie que le constructeur doit utiliser tous les cœurs de CPU disponibles dans le système.
•
--log-filter filtre
Définit le filtre de log.
•
--read-from-store chemin
N'est pas une option de nix-store, mais est utilisé par les commandes qui appellent nix-store.
•
--option nom valeur
Définit une option de configuration Nix.
•
--stdin
N'est pas une option de nix-store, mais est utilisé par les commandes qui appellent nix-store.

Exemples

Importer une base de données Nix depuis un fichier nommé my-db.dump :

$ nix-store --load-db < my-db.dump

Voir aussi

nix-store(1), nix-store(1) --dump-db.

OPTIONS

•
--max-silent-time
Définit le nombre maximal de secondes pendant lesquelles un constructeur peut rester sans produire de données sur la sortie standard ou la sortie d'erreur standard. La valeur par défaut est spécifiée par le paramètre de configuration max-silent-time. 0 signifie pas de délai d'attente.
•
--timeout
Définit le nombre maximal de secondes pendant lesquelles un constructeur peut s'exécuter. La valeur par défaut est spécifiée par le paramètre de configuration timeout. 0 signifie pas de délai d'attente.
•
--keep-going / -k
Continue en cas d'échec des constructions, dans la mesure du possible. C'est-à-dire que si la construction d'une entrée d'une certaine dérivation échoue, Nix construira toujours les autres entrées, mais pas la dérivation elle-même. Sans cette option, Nix s'arrête si une construction échoue (sauf pour les constructions de substituts), tuant potentiellement les constructions en cours (en cas de constructions parallèles ou distribuées).
•
--keep-failed / -K
Spécifie qu'en cas d'échec de construction, le répertoire temporaire (généralement dans /tmp) dans lequel la construction a lieu ne doit pas être supprimé. Le chemin du répertoire de construction est affiché comme un message d'information.
•
--fallback
Chaque fois que Nix tente de construire une dérivation pour laquelle des substituts sont connus pour chaque chemin de sortie, mais que la réalisation des chemins de sortie via les substituts échoue, Nix se rabat sur la construction de la dérivation.
Le scénario le plus courant pour lequel cela est utile est lorsque nous avons enregistré des substituts pour effectuer une distribution binaire à partir, par exemple, d'un dépôt réseau. Si le dépôt est en panne, la réalisation de la dérivation échouera. Lorsque cette option est spécifiée, Nix construira la dérivation à la place. Ainsi, l'installation à partir de binaires se rabat sur l'installation à partir de la source. Cette option n'est pas la valeur par défaut car il n'est généralement pas souhaitable qu'un échec transitoire dans l'obtention des substituts entraîne une construction complète à partir de la source (avec la consommation de ressources associée).
•
--readonly-mode
Lorsque cette option est utilisée, aucune tentative n'est faite pour ouvrir la base de données Nix. La plupart des opérations Nix nécessitent un accès à la base de données, donc ces opérations échoueront.
•
--arg name value
Cette option est acceptée par nix-env, nix-instantiate, nix-shell et nix-build. Lors de l'évaluation des expressions Nix, l'évaluateur d'expressions essaiera automatiquement d'appeler les fonctions qu'il rencontre. Il peut appeler automatiquement les fonctions pour lesquelles tous les arguments ont une valeur par défaut (par exemple, { argName ? defaultValue }: ...).
Avec --arg, vous pouvez également appeler des fonctions qui ont des arguments sans valeur par défaut (ou remplacer une valeur par défaut). C'est-à-dire que si l'évaluateur rencontre une fonction avec un argument nommé name, il l'appellera avec la valeur value.
Par exemple, le default.nix de haut niveau dans Nixpkgs est en fait une fonction :
{ # Le système (par exemple, `i686-linux') pour lequel construire les paquets.
system ? builtins.currentSystem
...
}: ...
Donc, si vous appelez cette expression Nix (par exemple, lorsque vous faites nix-env --install --attr pkgname), la fonction sera appelée automatiquement en utilisant la valeur builtins.currentSystem pour l'argument system. Vous pouvez remplacer cela en utilisant --arg, par exemple nix-env --install --attr pkgname --arg system \"i686-freebsd\". (Notez que comme l'argument est une chaîne littérale Nix, vous devez échapper les guillemets.)
•
--argstr name value
Cette option est comme --arg, sauf que la valeur n'est pas une expression Nix mais une chaîne. Donc, au lieu de --arg system \"i686-linux\" (les guillemets extérieurs servent à satisfaire le shell), vous pouvez dire --argstr system i686-linux.
•
--attr / -A attrPath
Sélectionne un attribut de l'expression Nix de haut niveau en cours d'évaluation. (Uniquement pour nix-env, nix-instantiate, nix-build et nix-shell.) Le chemin d'attribut attrPath est une séquence de noms d'attributs séparés par des points. Par exemple, étant donné une expression Nix de haut niveau e, le chemin d'attribut xorg.xorgserver provoquerait l'utilisation de l'expression e.xorg.xorgserver. Voir nix-env --install pour quelques exemples concrets.
En plus des noms d'attributs, vous pouvez également spécifier des indices de tableau. Par exemple, le chemin d'attribut foo.3.bar sélectionne l'attribut bar du quatrième élément du tableau dans l'attribut foo de l'expression de haut niveau.
•
--expr / -E
Interprète les arguments de la ligne de commande comme une liste d'expressions Nix à analyser et évaluer, plutôt que comme une liste de noms de fichiers d'expressions Nix. (Uniquement pour nix-instantiate, nix-build et nix-shell.)
Pour nix-shell, cette option est couramment utilisée pour vous donner un shell dans lequel vous pouvez construire les paquets retournés par l'expression. Si vous souhaitez obtenir un shell contenant les paquets construits prêts à l'emploi, donnez votre expression à l'indicateur de commodité nix-shell --packages à la place.
•
-I / --include path
Ajoute une entrée à la liste des chemins de recherche utilisés pour résoudre les chemins de recherche. Cette option peut être donnée plusieurs fois.
Les chemins ajoutés via -I ont la priorité sur le paramètre de configuration nix-path et la variable d'environnement NIX_PATH.
•
--option name value
Définit l'option de configuration Nix name sur value. Cela remplace les paramètres du fichier de configuration Nix (voir nix.conf5).
•
--repair
Corrige les chemins de magasin corrompus ou manquants en les redownloadant ou en les reconstruisant. Notez que c'est lent car cela nécessite de calculer un hash cryptographique du contenu de chaque chemin dans la fermeture de la construction. Notez également l'avertissement sous nix-store --repair-path.

Note

Voir man nix.conf pour remplacer les paramètres de configuration avec des indicateurs de ligne de commande.

Variables d'environnement courantes

La plupart des commandes Nix interprètent les variables d'environnement suivantes :

•
IN_NIX_SHELL
Indicateur qui signale si l'environnement actuel a été configuré par nix-shell. Il peut avoir les valeurs pure ou impure.
•
NIX_PATH
Une liste d'entrées de chemins de recherche séparées par des deux-points, utilisée pour résoudre les chemins de recherche.
Cette variable d'environnement remplace la valeur du paramètre de configuration nix-path.
Elle peut être étendue à l'aide de l'option -I.
Exemple
$ export NIX_PATH=`/home/eelco/Dev:nixos-config=/etc/nixos
Si NIX_PATH est défini sur une chaîne vide, la résolution des chemins de recherche échouera toujours.
Exemple
$ NIX_PATH= nix-instantiate --eval '<nixpkgs>'
error: file 'nixpkgs' was not found in the Nix search path (add it using $NIX_PATH or -I)
•
NIX_IGNORE_SYMLINK_STORE
Normalement, le répertoire du magasin Nix (typiquement

DESCRIPTION

Le chemin du magasin Nix (par exemple, /nix/store) n'est pas autorisé à contenir de composants de lien symbolique. Ceci est destiné à empêcher les constructions « impures ». Les constructeurs « canonicalisent » parfois les chemins en résolvant tous les composants de lien symbolique. Ainsi, les constructions sur différentes machines (avec /nix/store résolu à différents emplacements) pourraient donner des résultats différents. Ce n'est généralement pas un problème, sauf lorsque les constructions sont déployées sur des machines où /nix/store est résolu différemment. Si vous êtes sûr que vous n'allez pas le faire, vous pouvez définir NIX_IGNORE_SYMLINK_STORE sur 1.

Notez que si vous créez un lien symbolique vers le magasin Nix afin de pouvoir le placer sur un autre système de fichiers que le système de fichiers racine, sous Linux, il est préférable d'utiliser des points de montage bind, par exemple :

$ mkdir /nix
$ mount -o bind /mnt/otherdisk/nix /nix
Consultez la page man mount 8 pour plus de détails.
NIX_STORE_DIR
Remplace l'emplacement du magasin Nix (par défaut prefix/store).
NIX_DATA_DIR
Remplace l'emplacement du répertoire de données statiques de Nix (par défaut prefix/share).
NIX_LOG_DIR
Remplace l'emplacement du répertoire de logs de Nix (par défaut prefix/var/log/nix).
NIX_STATE_DIR
Remplace l'emplacement du répertoire d'état de Nix (par défaut prefix/var/nix).
NIX_CONF_DIR
Remplace l'emplacement du répertoire de configuration système de Nix (par défaut prefix/etc/nix).
NIX_CONFIG
Applique les paramètres de la configuration Nix depuis l'environnement. Le contenu est traité comme s'il était lu à partir d'un fichier de configuration Nix. Les paramètres sont séparés par le caractère de nouvelle ligne.
NIX_USER_CONF_FILES
Remplace l'emplacement des fichiers de configuration utilisateur Nix à charger.
Par défaut, ce sont les emplacements conformes à la spécification des répertoires de base XDG. Voir la sous-section Répertoires de base XDG pour plus de détails.
La variable est traitée comme une liste séparée par le jeton :.
TMPDIR
Utilise le répertoire spécifié pour stocker les fichiers temporaires. Notamment, cela inclut les répertoires de construction temporaires ; ceux-ci peuvent occuper une quantité substantielle d'espace disque. La valeur par défaut est /tmp.
NIX_REMOTE
Cette variable doit être définie sur daemon si vous souhaitez utiliser le démon Nix pour exécuter les opérations Nix. Ceci est nécessaire dans les installations Nix multi-utilisateurs. Si le socket Unix du démon Nix se trouve à un chemin non standard, cette variable doit être définie sur unix://chemin/vers/socket. Sinon, elle doit être laissée non définie.
NIX_SHOW_STATS
Si défini sur 1, Nix affichera des statistiques d'évaluation, telles que le nombre de valeurs allouées.
NIX_COUNT_CALLS
Si défini sur 1, Nix affichera la fréquence d'appel des fonctions lors de l'évaluation des expressions Nix. Ceci est utile pour profiler vos expressions Nix.
GC_INITIAL_HEAP_SIZE
Si Nix a été configuré pour utiliser le garbage collector de Boehm, cette variable définit la taille initiale du tas en octets. Elle est par défaut à 384 Mio. La définir à une valeur faible réduit la consommation de mémoire, mais augmentera le temps d'exécution en raison de la surcharge de la collecte de garbage.

Répertoires de base XDG

Nix suit la spécification des répertoires de base XDG.

Pour des raisons de compatibilité ascendante, les commandes Nix ne suivront la norme que lorsque use-xdg-base-directories sera activé. Les nouvelles commandes Nix (expérimentales) respectent la norme par défaut.

Les variables d'environnement suivantes sont utilisées pour déterminer les emplacements de divers fichiers d'état et de configuration :

  • [XDG_CONFIG_HOME]{#env-XDGCONFIGHOME} (par défaut ~/.config)
  • [XDG_STATE_HOME]{#env-XDGSTATEHOME} (par défaut ~/.local/state)
  • [XDG_CACHE_HOME]{#env-XDGCACHEHOME} (par défaut ~/.cache)
