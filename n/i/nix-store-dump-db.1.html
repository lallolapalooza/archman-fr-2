nix-store --dump-db(1) Manuel des commandes générales nix-store --dump-db(1)

Nom

nix-store --dump-db - exporter la base de données Nix

Synopsis

nix-store --dump-db [chemins…]

Description

L'opération --dump-db écrit une sauvegarde de la base de données Nix sur la sortie standard. Elle peut être chargée dans un magasin Nix vide à l'aide de --load-db. Ceci est utile pour effectuer des sauvegardes et lors de la migration vers différents schémas de base de données.

Par défaut, --dump-db exportera toute la base de données Nix. Lorsque un ou plusieurs chemins de magasin sont passés en argument, seul le sous-ensemble de la base de données Nix correspondant à ces chemins de magasin sera exporté. Comme avec --export, l'utilisateur est responsable de fournir tous les chemins de magasin d'une fermeture. Voir --export pour un exemple.

Options

Les options suivantes sont autorisées pour toutes les opérations nix-store, mais peuvent ne pas toujours avoir un effet.

•
--add-root chemin
Provoque l'enregistrement du résultat d'une réalisation (--realise et --force-realise) comme racine du collecteur de gaspillage. chemin sera créé comme un lien symbolique vers le chemin du magasin résultant. De plus, un lien symbolique au nom unique vers chemin sera créé dans /nix/var/nix/gcroots/auto/. Par exemple,
$ nix-store --add-root /home/eelco/bla/result --realise ...
$ ls -l /nix/var/nix/gcroots/auto
lrwxrwxrwx    1 ... 2005-03-13 21:10 dn54lcypm8f8... -> /home/eelco/bla/result
$ ls -l /home/eelco/bla/result
lrwxrwxrwx    1 ... 2005-03-13 21:10 /home/eelco/bla/result -> /nix/store/1r11343n6qd4...-f-spot-0.0.10
Ainsi, lorsque /home/eelco/bla/result est supprimé, la racine du GC dans le répertoire auto devient un lien symbolique orphelin et sera ignoré par le collecteur.
Attention
Notez qu'il n'est pas possible de déplacer ou renommer les racines de GC, car le lien symbolique dans le répertoire auto pointera toujours vers l'ancien emplacement.
S'il y a plusieurs résultats, plusieurs liens symboliques seront créés en numérotant séquentiellement les liens symboliques au-delà du premier (par exemple, foo, foo-2, foo-3, et ainsi de suite).

Options communes

La plupart des commandes Nix acceptent les options de ligne de commande suivantes :

•
--help
Affiche un résumé de la syntaxe de la commande et quitte.
•
--version
Affiche le numéro de version de Nix sur la sortie standard et quitte.
•
--verbose / -v
Augmente le niveau de verbosité des messages de diagnostic imprimés sur la sortie standard d'erreur. Pour chaque opération Nix, les informations imprimées sur la sortie standard sont bien définies ; toute information de diagnostic est imprimée sur la sortie standard d'erreur, jamais sur la sortie standard.
Cette option peut être spécifiée plusieurs fois. Actuellement, les niveaux de verbosité suivants existent :
•
0 « Erreurs seulement »
Imprime uniquement les messages expliquant pourquoi l'appel Nix a échoué.
•
1 « Informatif »
Imprime des messages *utiles* sur ce que fait Nix. C'est le comportement par défaut.
•
2 « Bavard »
Imprime davantage de messages informatifs.
•
3 « Très bavard »
Imprime encore plus de messages informatifs.
•
4 « Débogage »
Imprime des informations de débogage.
•
5 « Vomir »
Imprime une quantité énorme d'informations de débogage.
•
--quiet
Diminue le niveau de verbosité des messages de diagnostic imprimés sur la sortie standard d'erreur. C'est l'option inverse de -v / --verbose.
Cette option peut être spécifiée plusieurs fois. Voir la liste précédente des niveaux de verbosité.
•
--log-format format
Cette option peut être utilisée pour modifier le format de sortie des logs, format étant l'un des choix suivants :
•
raw
C'est le format brut, tel que produit par nix-build.
•
internal-json
Produit les journaux dans un format structuré.
Attention
Bien que le schéma lui-même soit relativement stable, le format des messages d'erreur (notamment le champ msg) peut changer entre les versions.
•
bar
Affiche uniquement une barre de progression pendant les constructions.
•
bar-with-logs
Affiche les journaux bruts, avec la barre de progression en bas.
•
--no-build-output / -Q
Par défaut, la sortie générée par les constructeurs vers la sortie standard et la sortie d'erreur standard est échoée vers la sortie d'erreur standard de la commande Nix. Cette option supprime ce comportement. Notez que la sortie et l'erreur standard du constructeur sont toujours écrites dans un fichier journal dans prefix/nix/var/log/nix.
•
--max-jobs / -j nombre
Définit le nombre maximum de tâches de construction que Nix effectuera en parallèle au nombre spécifié. Spécifiez auto pour utiliser le nombre de CPU du système. La valeur par défaut est spécifiée par le paramètre de configuration max-jobs, qui par défaut est 1. Une valeur plus élevée est utile sur les systèmes SMP ou pour exploiter la latence des E/S.
La définition à 0 interdit la construction sur la machine locale, ce qui est utile lorsque vous souhaitez que les constructions se produisent uniquement sur des constructeurs distants.
•
--cores
Définit la valeur de la variable d'environnement NIX_BUILD_CORES dans l'invocation des constructeurs. Les constructeurs peuvent utiliser cette variable à leur discrétion pour contrôler la quantité maximale de parallélisme. Par exemple, dans Nixpkgs, si l'attribut de dérivation

Flags de ligne de commande

•
--enable-parallel-building / -j N
Si enableParallelBuilding est défini sur true, le constructeur transmet l'indicateur -jN à GNU Make. Il utilise par défaut la valeur du paramètre de configuration cores, s'il est défini, ou 1 sinon. La valeur 0 signifie que le constructeur doit utiliser tous les cœurs CPU disponibles dans le système.
•
--max-silent-time
Définit le temps maximum en secondes pendant lequel un constructeur peut ne pas produire de données sur la sortie standard ou l'erreur standard. La valeur par défaut est spécifiée par le paramètre de configuration max-silent-time. 0 signifie aucun délai d'attente.
•
--timeout
Définit le temps maximum en secondes pendant lequel un constructeur peut s'exécuter. La valeur par défaut est spécifiée par le paramètre de configuration timeout. 0 signifie aucun délai d'attente.
•
--keep-going / -k
Continue en cas d'échecs de construction, dans la plus grande mesure possible. C'est-à-dire que si la construction d'une entrée d'une dérivation échoue, Nix construira toujours les autres entrées, mais pas la dérivation elle-même. Sans cette option, Nix s'arrête si une construction échoue (sauf pour les constructions de substituts), tuant potentiellement les constructions en cours (en cas de constructions parallèles ou distribuées).
•
--keep-failed / -K
Spécifie qu'en cas d'échec de construction, le répertoire temporaire (généralement dans /tmp) dans lequel la construction a lieu ne doit pas être supprimé. Le chemin du répertoire de construction est affiché comme un message informatif.
•
--fallback
Chaque fois que Nix tente de construire une dérivation pour laquelle des substituts sont connus pour chaque chemin de sortie, mais que la réalisation des chemins de sortie via les substituts échoue, Nix reconstruira la dérivation.
Le scénario le plus courant où cela est utile est lorsque nous avons enregistré des substituts pour effectuer une distribution binaire depuis, par exemple, un dépôt réseau. Si le dépôt est hors ligne, la réalisation de la dérivation échouera. Lorsque cette option est spécifiée, Nix construira la dérivation à la place. Ainsi, l'installation à partir de binaires se replie sur l'installation à partir des sources. Cette option n'est pas la valeur par défaut car il n'est généralement pas souhaitable qu'un échec transitoire dans l'obtention des substituts conduise à une construction complète à partir des sources (avec la consommation de ressources associée).
•
--readonly-mode
Lorsque cette option est utilisée, aucune tentative n'est faite pour ouvrir la base de données Nix. La plupart des opérations Nix nécessitent un accès à la base de données, donc ces opérations échoueront.
•
--arg nom valeur
Cette option est acceptée par nix-env, nix-instantiate, nix-shell et nix-build. Lors de l'évaluation des expressions Nix, l'évaluateur d'expressions tentera automatiquement d'appeler les fonctions qu'il rencontre. Il peut appeler automatiquement les fonctions pour lesquelles tous les arguments ont une valeur par défaut (par exemple, { argName ? defaultValue }: ...).
Avec --arg, vous pouvez également appeler des fonctions qui ont des arguments sans valeur par défaut (ou remplacer une valeur par défaut). C'est-à-dire que si l'évaluateur rencontre une fonction avec un argument nommé nom, il l'appellera avec la valeur valeur.
Par exemple, le default.nix de haut niveau dans Nixpkgs est en fait une fonction :
{ # Le système (par exemple, `i686-linux') pour lequel construire les paquets.
system ? builtins.currentSystem
...
}: ...
Ainsi, si vous appelez cette expression Nix (par exemple, lorsque vous faites nix-env --install --attr pkgname), la fonction sera appelée automatiquement en utilisant la valeur builtins.currentSystem pour l'argument system. Vous pouvez la remplacer en utilisant --arg, par exemple, nix-env --install --attr pkgname --arg system \"i686-freebsd\". (Notez que puisque l'argument est une chaîne littérale Nix, vous devez échapper les guillemets.)
•
--argstr nom valeur
Cette option est similaire à --arg, seulement la valeur n'est pas une expression Nix mais une chaîne. Donc au lieu de --arg system \"i686-linux\" (les guillemets externes sont là pour le shell) vous pouvez dire --argstr system i686-linux.
•
--attr / -A cheminAttr
Sélectionne un attribut de l'expression Nix de haut niveau en cours d'évaluation. (nix-env, nix-instantiate, nix-build et nix-shell uniquement.) Le chemin d'attribut cheminAttr est une séquence de noms d'attributs séparés par des points. Par exemple, étant donné une expression Nix de haut niveau e, le chemin d'attribut xorg.xorgserver provoquerait l'utilisation de l'expression e.xorg.xorgserver. Voir nix-env --install pour quelques exemples concrets.
En plus des noms d'attributs, vous pouvez également spécifier des indices de tableau. Par exemple, le chemin d'attribut foo.3.bar sélectionne l'attribut bar du quatrième élément du tableau dans l'attribut foo de l'expression de haut niveau.
•
--expr / -E
Interprète les arguments de la ligne de commande comme une liste d'expressions Nix à analyser et évaluer, plutôt que comme une liste de noms de fichiers d'expressions Nix. (nix-instantiate, nix-build et nix-shell uniquement.)
Pour nix-shell, cette option est couramment utilisée pour vous fournir un shell dans lequel vous pouvez construire les paquets renvoyés par l'expression. Si vous voulez obtenir un shell contenant les paquets *construits* prêts à être utilisés, donnez votre expression à l'option de commodité nix-shell --packages à la place.
•
-I / --include chemin
Ajoute une entrée à la liste des chemins de recherche utilisés pour résoudre les chemins de recherche. Cette option peut être donnée plusieurs fois.
Les chemins ajoutés via -I ont la priorité sur le paramètre de configuration nix-path et la variable d'environnement NIX_PATH.
•
--option nom valeur
Définit l'option de configuration Nix nom à valeur. Ceci remplace les paramètres du fichier de configuration Nix (voir nix.conf5).
•
--repair
Corrige les chemins de magasin corrompus ou manquants en les redownloadant ou en les reconstruisant. Notez que cela est lent car cela nécessite de calculer un hachage cryptographique du contenu de chaque chemin dans la clôture de la construction. Notez également l'avertissement sous nix-store --repair-path.

Remarque

Voir man nix.conf pour remplacer les paramètres de configuration avec des flags de ligne de commande.

Variables d'environnement courantes

La plupart des commandes Nix interprètent les variables d'environnement suivantes :

•
IN_NIX_SHELL
Indicateur qui indique si l'environnement actuel a été configuré par nix-shell. Il peut avoir les valeurs pure ou impure.
•
NIX_PATH
Une liste d'entrées de chemins de recherche séparées par des deux-points, utilisée pour résoudre les chemins de recherche.
Cette variable d'environnement remplace la valeur du paramètre de configuration nix-path.
Elle peut être étendue en utilisant l'option -I.
Exemple
$ export NIX_PATH=`/home/eelco/Dev:nixos-config=/etc/nixos
Si NIX_PATH est défini sur une chaîne vide, la résolution des chemins de recherche échouera toujours.

NAME

nix - The Nix package manager

SYNOPSIS

nix [options...] command [args...]

nix [options...] --version

nix [options...] --help

DESCRIPTION

Nix is a powerful package manager for Linux and other Unix-like systems that provides:

  • Transactional upgrades and rollbacks.
  • Reliable builds that don’t interfere with each other.
  • Unprivileged package management (no root access required).
  • Building multiple versions of the same package side-by-side.
  • Binary reproducibility.

The Nix package manager executable is simply named nix. It implements a large number of subcommands for managing packages, environments, Nix channels, the Nix store, and so forth.

This manual page lists common options and environment variables. For a full list of subcommands and their respective options, please refer to the Nix manual online.

OPTIONS

The following options are available:

--version
Show version information and exit.
--help
Show a list of available commands and their usage, and exit.
-I path
Add directory path to the Nix expression search path. The Nix search path is a list of directories containing Nix expressions. By default, it contains <nixpkgs>, which points to the Nixpkgs collection of packages. This option can be used multiple times to add multiple directories. The path ~/.nix-defexpr is implicitly added to the search path if it exists.
$ NIX_PATH= nix-instantiate --eval '<nixpkgs>'
error: file 'nixpkgs' was not found in the Nix search path (add it using $NIX_PATH or -I)

COMMON OPTIONS

--option name=value
Overrides a Nix configuration option. See nix.conf(5) for a list of available options.
--show-trace
Print a stack trace if an evaluation error occurs.
--debug
Enable debugging output.
--verbose
Print verbose output.

COMMON ENVIRONMENT VARIABLES

NIX_PATH
A list of Nix expression paths, separated by colons. For example, NIX_PATH=~/my-nixpkgs=~/nixpkgs:~/my-other-nixpkgs=~/other-nixpkgs defines two paths. If a path is not prefixed with a name (e.g., ~/nixpkgs), it is treated as if it were named nixpkgs. If NIX_PATH is set, it overrides the default search path.
NIX_IGNORE_SYMLINK_STORE
Normally, the Nix store directory (typically /nix/store) is not allowed to contain any symlink components. This is to prevent “impure” builds. Builders sometimes “canonicalise” paths by resolving all symlink components. Thus, builds on different machines (with /nix/store resolving to different locations) could yield different results. This is generally not a problem, except when builds are deployed to machines where /nix/store resolves differently. If you are sure that you’re not going to do that, you can set NIX_IGNORE_SYMLINK_STORE to 1.
Note that if you’re symlinking the Nix store so that you can put it on another file system than the root file system, on Linux you’re better off using bind mount points, e.g.,
$ mkdir /nix
$ mount -o bind /mnt/otherdisk/nix /nix
Consult the mount 8 manual page for details.
NIX_STORE_DIR
Overrides the location of the Nix store (default prefix/store).
NIX_DATA_DIR
Overrides the location of the Nix static data directory (default prefix/share).
NIX_LOG_DIR
Overrides the location of the Nix log directory (default prefix/var/log/nix).
NIX_STATE_DIR
Overrides the location of the Nix state directory (default prefix/var/nix).
NIX_CONF_DIR
Overrides the location of the system Nix configuration directory (default prefix/etc/nix).
NIX_CONFIG
Applies settings from Nix configuration from the environment. The content is treated as if it was read from a Nix configuration file. Settings are separated by the newline character.
NIX_USER_CONF_FILES
Overrides the location of the Nix user configuration files to load from.
The default are the locations according to the XDG Base Directory Specification. See the XDG Base Directories sub-section for details.
The variable is treated as a list separated by the : token.
TMPDIR
Use the specified directory to store temporary files. In particular, this includes temporary build directories; these can take up substantial amounts of disk space. The default is /tmp.
NIX_REMOTE
This variable should be set to daemon if you want to use the Nix daemon to execute Nix operations. This is necessary in multi-user Nix installations. If the Nix daemon’s Unix socket is at some non-standard path, this variable should be set to unix://path/to/socket. Otherwise, it should be left unset.
NIX_SHOW_STATS
If set to 1, Nix will print some evaluation statistics, such as the number of values allocated.
NIX_COUNT_CALLS
If set to 1, Nix will print how often functions were called during Nix expression evaluation. This is useful for profiling your Nix expressions.
GC_INITIAL_HEAP_SIZE
If Nix has been configured to use the Boehm garbage collector, this variable sets the initial size of the heap in bytes. It defaults to 384 MiB. Setting it to a low value reduces memory consumption, but will increase runtime due to the overhead of garbage collection.

XDG Base Directories

Nix follows the XDG Base Directory Specification.

For backwards compatibility, Nix commands will follow the standard only when use-xdg-base-directories is enabled. New Nix commands (experimental) conform to the standard by default.

The following environment variables are used to determine locations of various state and configuration files:

  • [XDG_CONFIG_HOME]{#env-XDGCONFIGHOME} (default ~/.config)
  • [XDG_STATE_HOME]{#env-XDGSTATEHOME} (default ~/.local/state)
  • [XDG_CACHE_HOME]{#env-XDGCACHEHOME} (default ~/.cache)
