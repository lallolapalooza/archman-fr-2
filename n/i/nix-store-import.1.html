nix-store --import(1) Manuel des commandes générales nix-store --import(1)

Nom

nix-store --import - importer une Archive Nix dans le store

Synopsis

nix-store --import

Description

L'opération --import lit une sérialisation d'un ensemble d'objets du store produite par nix-store --export depuis l'entrée standard, et ajoute ces objets du store au Nix store spécifié. Les chemins qui existent déjà dans le Nix store cible sont ignorés. Si un chemin fait référence à un autre chemin qui n'existe pas dans le Nix store cible, l'importation échoue.

Note

Pour un transfert efficace de fermetures vers des machines distantes via SSH, utilisez nix-copy-closure.

Options

Les options suivantes sont autorisées pour toutes les opérations nix-store, mais peuvent ne pas avoir d'effet systématique.

•
--add-root chemin
Crée le résultat d'une réalisation (--realise et --force-realise) comme racine du collecteur de corbeille. chemin sera créé comme un lien symbolique vers le chemin du store résultant. De plus, un lien symbolique nommé de manière unique vers chemin sera créé dans /nix/var/nix/gcroots/auto/. Par exemple,
$ nix-store --add-root /home/eelco/bla/result --realise ...
$ ls -l /nix/var/nix/gcroots/auto
lrwxrwxrwx    1 ... 2005-03-13 21:10 dn54lcypm8f8... -> /home/eelco/bla/result
$ ls -l /home/eelco/bla/result
lrwxrwxrwx    1 ... 2005-03-13 21:10 /home/eelco/bla/result -> /nix/store/1r11343n6qd4...-f-spot-0.0.10
Ainsi, lorsque /home/eelco/bla/result est supprimé, la racine GC dans le répertoire auto devient un lien symbolique pendant et sera ignorée par le collecteur.
Attention
Notez qu'il n'est pas possible de déplacer ou renommer des racines GC, car le lien symbolique dans le répertoire auto pointera toujours vers l'ancien emplacement.
S'il y a plusieurs résultats, plusieurs liens symboliques seront créés en numérotant séquentiellement les liens au-delà du premier (par exemple, foo, foo-2, foo-3, etc.).

Options communes

La plupart des commandes Nix acceptent les options de ligne de commande suivantes :

•
--help
Affiche un résumé de la syntaxe de la commande et quitte.
•
--version
Affiche le numéro de version de Nix sur la sortie standard et quitte.
•
--verbose / -v
Augmente le niveau de verbosité des messages diagnostiques imprimés sur la sortie d'erreur standard. Pour chaque opération Nix, les informations imprimées sur la sortie standard sont bien définies ; toute information diagnostique est imprimée sur la sortie d'erreur standard, jamais sur la sortie standard.
Cette option peut être spécifiée de manière répétée. Actuellement, les niveaux de verbosité suivants existent :
•
0 « Erreurs uniquement »
N'imprime que les messages expliquant pourquoi l'invocation Nix a échoué.
•
1 « Informationnel »
Imprime des messages utiles sur ce que fait Nix. C'est la valeur par défaut.
•
2 « Bavard »
Imprime plus de messages d'information.
•
3 « Disert »
Imprime encore plus de messages d'information.
•
4 « Débogage »
Imprime des informations de débogage.
•
5 « Vomir »
Imprime une quantité énorme d'informations de débogage.
•
--quiet
Diminue le niveau de verbosité des messages diagnostiques imprimés sur la sortie d'erreur standard. C'est l'option inverse de -v / --verbose.
Cette option peut être spécifiée de manière répétée. Voir la liste précédente des niveaux de verbosité.
•
--log-format format
Cette option peut être utilisée pour changer le format de sortie des journaux, avec format étant l'une des valeurs suivantes :
•
raw
C'est le format brut, tel que produit par nix-build.
•
internal-json
Produit les journaux dans un format structuré.
Attention
Bien que le schéma lui-même soit relativement stable, le format des messages d'erreur (notamment du champ msg) peut changer entre les versions.
•
bar
Affiche uniquement une barre de progression pendant les constructions.
•
bar-with-logs
Affiche les journaux bruts, avec la barre de progression en bas.
•
--no-build-output / -Q
Par défaut, la sortie écrite par les constructeurs sur la sortie standard et la sortie d'erreur standard est répercutée sur la sortie d'erreur standard de la commande Nix. Cette option supprime ce comportement. Notez que la sortie standard et l'erreur standard du constructeur sont toujours écrites dans un fichier journal dans prefix/nix/var/log/nix.
•
--max-jobs / -j nombre
Définit le nombre maximum de tâches de construction que Nix effectuera en parallèle au nombre spécifié. Spécifiez auto pour utiliser le nombre de CPU du système. La valeur par défaut est spécifiée par le réglage de configuration max-jobs, qui par défaut est 1. Une valeur plus élevée est utile sur les systèmes SMP ou pour exploiter la latence d'E/S.
La définition à 0 interdit la construction sur la machine locale, ce qui est utile lorsque vous souhaitez que les constructions se produisent uniquement sur des constructeurs distants.
•
--cores

Ce site n'est en aucun cas associé à Arch Linux ni affilié à ce projet. Le contenu est uniquement une traduction des pages de manuel d'Arch publiées sur man.archlinux.org.

Définit la valeur de la variable d'environnement NIX_BUILD_CORES lors de l'invocation des constructeurs. Les constructeurs peuvent utiliser cette variable à leur discrétion pour contrôler le parallélisme maximal. Par exemple, dans Nixpkgs, si l'attribut de dérivation enableParallelBuilding est défini sur true, le constructeur passe l'indicateur -jN à GNU Make. Il est par défaut à la valeur du paramètre de configuration cores, s'il est défini, ou 1 sinon. La valeur 0 signifie que le constructeur doit utiliser tous les cœurs de CPU disponibles sur le système.
•
--max-silent-time
Définit le nombre maximum de secondes pendant lesquelles un constructeur peut fonctionner sans produire de données sur la sortie standard ou la sortie d'erreur standard. La valeur par défaut est spécifiée par le paramètre de configuration max-silent-time. 0 signifie pas de délai d'attente.
•
--timeout
Définit le nombre maximum de secondes pendant lesquelles un constructeur peut s'exécuter. La valeur par défaut est spécifiée par le paramètre de configuration timeout. 0 signifie pas de délai d'attente.
•
--keep-going / -k
Continuer en cas d'échec des constructions, dans la mesure du possible. C'est-à-dire, si la construction d'une entrée d'une dérivation échoue, Nix construira toujours les autres entrées, mais pas la dérivation elle-même. Sans cette option, Nix s'arrête si une construction échoue (sauf pour les constructions de substituts), tuant potentiellement les constructions en cours (en cas de constructions parallèles ou distribuées).
•
--keep-failed / -K
Spécifie qu'en cas d'échec de construction, le répertoire temporaire (généralement dans /tmp) dans lequel la construction a lieu ne doit pas être supprimé. Le chemin du répertoire de construction est imprimé comme message d'information.
•
--fallback
Chaque fois que Nix tente de construire une dérivation pour laquelle des substituts sont connus pour chaque chemin de sortie, mais que la réalisation des chemins de sortie via les substituts échoue, il se rabat sur la construction de la dérivation.
Le scénario le plus courant dans lequel cela est utile est lorsque nous avons enregistré des substituts afin d'effectuer la distribution binaire à partir d'un dépôt réseau, par exemple. Si le dépôt est hors service, la réalisation de la dérivation échouera. Lorsque cette option est spécifiée, Nix construira la dérivation à la place. Ainsi, l'installation à partir de binaires se rabat sur l'installation à partir des sources. Cette option n'est pas la valeur par défaut car il n'est généralement pas souhaitable qu'un échec transitoire dans l'obtention des substituts conduise à une construction complète à partir des sources (avec la consommation de ressources associée).
•
--readonly-mode
Lorsque cette option est utilisée, aucune tentative n'est faite pour ouvrir la base de données Nix. La plupart des opérations Nix nécessitent un accès à la base de données, donc ces opérations échoueront.
•
--arg name value
Cette option est acceptée par nix-env, nix-instantiate, nix-shell et nix-build. Lors de l'évaluation des expressions Nix, l'évaluateur d'expressions tentera automatiquement d'appeler les fonctions qu'il rencontre. Il peut appeler automatiquement les fonctions pour lesquelles tous les arguments ont une valeur par défaut (par exemple, { argName ? defaultValue }: ...).
Avec --arg, vous pouvez également appeler des fonctions qui ont des arguments sans valeur par défaut (ou remplacer une valeur par défaut). C'est-à-dire, si l'évaluateur rencontre une fonction avec un argument nommé name, il l'appellera avec la valeur value.
Par exemple, le default.nix de haut niveau dans Nixpkgs est en fait une fonction :
{ # Le système (par exemple, `i686-linux') pour lequel construire les paquets.
system ? builtins.currentSystem
...
}: ...
Ainsi, si vous appelez cette expression Nix (par exemple, lorsque vous faites nix-env --install --attr pkgname), la fonction sera appelée automatiquement en utilisant la valeur builtins.currentSystem pour l'argument system. Vous pouvez remplacer cela en utilisant --arg, par exemple, nix-env --install --attr pkgname --arg system \"i686-freebsd\". (Notez que comme l'argument est une chaîne littérale Nix, vous devez échapper les guillemets.)
•
--argstr name value
Cette option est comme --arg, seulement la valeur n'est pas une expression Nix mais une chaîne. Donc, au lieu de --arg system \"i686-linux\" (les guillemets extérieurs servent à satisfaire le shell), vous pouvez dire --argstr system i686-linux.
•
--attr / -A attrPath
Sélectionne un attribut de l'expression Nix de haut niveau en cours d'évaluation. (nix-env, nix-instantiate, nix-build et nix-shell uniquement.) Le chemin d'attribut attrPath est une séquence de noms d'attributs séparés par des points. Par exemple, étant donné une expression Nix de haut niveau e, le chemin d'attribut xorg.xorgserver entraînerait l'utilisation de l'expression e.xorg.xorgserver. Voir nix-env --install pour quelques exemples concrets.
En plus des noms d'attributs, vous pouvez également spécifier des indices de tableau. Par exemple, le chemin d'attribut foo.3.bar sélectionne l'attribut bar du quatrième élément du tableau dans l'attribut foo de l'expression de haut niveau.
•
--expr / -E
Interprète les arguments de la ligne de commande comme une liste d'expressions Nix à analyser et à évaluer, plutôt que comme une liste de noms de fichiers d'expressions Nix. (nix-instantiate, nix-build et nix-shell uniquement.)
Pour nix-shell, cette option est couramment utilisée pour vous fournir un shell dans lequel vous pouvez construire les paquets retournés par l'expression. Si vous souhaitez obtenir un shell contenant les paquets *construits* prêts à l'emploi, donnez votre expression à l'indicateur de commodité nix-shell --packages à la place.
•
-I / --include path
Ajoute une entrée à la liste des chemins de recherche utilisés pour résoudre les chemins de recherche. Cette option peut être donnée plusieurs fois.
Les chemins ajoutés via -I ont la priorité sur le paramètre de configuration nix-path et la variable d'environnement NIX_PATH.
•
--option name value
Définit l'option de configuration Nix name à value. Cela remplace les paramètres du fichier de configuration Nix (voir nix.conf5).
•
--repair
Corrige les chemins de magasin corrompus ou manquants en les redownloadant ou en les reconstruisant. Notez que cela est lent car cela nécessite le calcul d'un hachage cryptographique du contenu de chaque chemin dans la fermeture de la construction. Notez également l'avertissement sous nix-store --repair-path.

Note

Voir man nix.conf pour remplacer les paramètres de configuration avec des indicateurs de ligne de commande.

Variables d'environnement courantes

La plupart des commandes Nix interprètent les variables d'environnement suivantes :

•
IN_NIX_SHELL
Indicateur qui indique si l'environnement actuel a été configuré par nix-shell. Il peut avoir les valeurs pure ou impure.
•
NIX_PATH
Une liste d'entrées de chemins de recherche séparées par des deux-points, utilisée pour résoudre les chemins de recherche.
Cette variable d'environnement remplace la valeur du paramètre de configuration nix-path.
Elle peut être étendue en utilisant l'option -I.
nix.conf(5) — Nix manual

NOM

nix.conf — configuration du fichier pour Nix

SYNOPTIS

~/.config/nix/nix.conf, /etc/nix/nix.conf

DESCRIPTION

Le fichier nix.conf contient des directives de configuration pour les commandes Nix.

Les directives sont spécifiées une par ligne, sous la forme clé = valeur. Les commentaires sont introduits par le caractère #.

Les directives sont recherchées dans les emplacements suivants, dans l'ordre :

  • ~/.config/nix/nix.conf (si le répertoire ~/.config/nix existe).
  • /etc/nix/nix.conf.

Les directives spécifiées dans les fichiers de configuration ultérieurs remplacent celles spécifiées dans les fichiers précédents.

DIRECTIVES

•
NIX_PATH
Définit les chemins de recherche pour les identificateurs de chemins comme <nixpkgs>. La valeur est une liste de chemins séparés par des deux-points. Par exemple :
Exemple
$ export NIX_PATH=`/home/eelco/Dev:nixos-config=/etc/nixos
Si NIX_PATH est défini sur une chaîne vide, la résolution des chemins de recherche échouera toujours.
Exemple
Exemple
$ NIX_PATH= nix-instantiate --eval '<nixpkgs>'
error: file 'nixpkgs' was not found in the Nix search path (add it using $NIX_PATH or -I)
•
NIX_IGNORE_SYMLINK_STORE
Normalement, le répertoire du magasin Nix (typiquement /nix/store) n'est pas autorisé à contenir de composants de liens symboliques. Ceci afin d'éviter les constructions « impures ». Les constructeurs « canonicalisent » parfois les chemins en résolvant tous les composants de liens symboliques. Ainsi, les constructions sur différentes machines (avec /nix/store résolu à des emplacements différents) pourraient produire des résultats différents. Ce n'est généralement pas un problème, sauf lorsque les constructions sont déployées sur des machines où /nix/store est résolu différemment. Si vous êtes sûr de ne pas faire cela, vous pouvez définir NIX_IGNORE_SYMLINK_STORE sur 1.
Notez que si vous créez un lien symbolique vers le magasin Nix afin de pouvoir le placer sur un autre système de fichiers que le système de fichiers racine, sous Linux, il est préférable d'utiliser des points de montage bind, par exemple :
$ mkdir /nix
$ mount -o bind /mnt/otherdisk/nix /nix
Consultez la page de manuel de mount 8 pour plus de détails.
•
NIX_STORE_DIR
Remplace l'emplacement du magasin Nix (par défaut prefix/store).
•
NIX_DATA_DIR
Remplace l'emplacement du répertoire de données statiques Nix (par défaut prefix/share).
•
NIX_LOG_DIR
Remplace l'emplacement du répertoire de journaux Nix (par défaut prefix/var/log/nix).
•
NIX_STATE_DIR
Remplace l'emplacement du répertoire d'état Nix (par défaut prefix/var/nix).
•
NIX_CONF_DIR
Remplace l'emplacement du répertoire de configuration système Nix (par défaut prefix/etc/nix).
•
NIX_CONFIG
Applique des paramètres de configuration Nix depuis l'environnement. Le contenu est traité comme s'il était lu à partir d'un fichier de configuration Nix. Les paramètres sont séparés par un caractère de nouvelle ligne.
•
NIX_USER_CONF_FILES
Remplace l'emplacement des fichiers de configuration utilisateur Nix à charger.
Par défaut, ce sont les emplacements conformes aux spécifications de répertoires de base XDG. Voir la sous-section des répertoires de base XDG pour plus de détails.
La variable est traitée comme une liste séparée par le jeton :.
•
TMPDIR
Utilise le répertoire spécifié pour stocker les fichiers temporaires. En particulier, cela inclut les répertoires de construction temporaires ; ceux-ci peuvent occuper une quantité substantielle d'espace disque. Par défaut, c'est /tmp.
•
NIX_REMOTE
Cette variable doit être définie sur daemon si vous souhaitez utiliser le démon Nix pour exécuter des opérations Nix. Ceci est nécessaire dans les installations Nix multi-utilisateurs. Si le socket Unix du démon Nix se trouve à un chemin non standard, cette variable doit être définie sur unix://chemin/vers/socket. Sinon, elle doit être laissée non définie.
•
NIX_SHOW_STATS
Si définie sur 1, Nix affichera certaines statistiques d'évaluation, comme le nombre de valeurs allouées.
•
NIX_COUNT_CALLS
Si définie sur 1, Nix affichera la fréquence d'appel des fonctions lors de l'évaluation des expressions Nix. Ceci est utile pour profiler vos expressions Nix.
•
GC_INITIAL_HEAP_SIZE
Si Nix a été configuré pour utiliser le garbage collector Boehm, cette variable définit la taille initiale du tas en octets. Elle est par défaut de 384 MiB. La définir sur une valeur basse réduit la consommation de mémoire, mais augmentera le temps d'exécution en raison de la surcharge de la collecte de garbage.

RÉPERTOIRES DE BASE XDG

Nix suit la spécification des répertoires de base XDG.

Par souci de compatibilité ascendante, les commandes Nix ne suivront la norme que lorsque use-xdg-base-directories est activé. Les nouvelles commandes Nix (expérimentales) respectent la norme par défaut.

Les variables d'environnement suivantes sont utilisées pour déterminer les emplacements des différents fichiers d'état et de configuration :

  • [XDG_CONFIG_HOME](#env-XDGCONFIGHOME) (par défaut ~/.config)
  • [XDG_STATE_HOME](#env-XDGSTATEHOME) (par défaut ~/.local/state)
  • [XDG_CACHE_HOME](#env-XDGCACHEHOME) (par défaut ~/.cache)

Exemples

Exemple

Étant donné une fermeture de GNU Hello sous forme de fichier :

$ storePath="$(nix-build '<nixpkgs>' -I nixpkgs=channel:nixpkgs-unstable -A hello --no-out-link)"
$ nix-store --export $(nix-store --query --requisites $storePath) > hello.closure

Importez la fermeture dans un magasin SSH distant en utilisant l'option --store :

$ nix-store --import --store ssh://alice@itchy.example.org < hello.closure
