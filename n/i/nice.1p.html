NICE(1P) Manuel du programmeur POSIX NICE(1P)

PROLOGUE

Cette page de manuel fait partie du Manuel du programmeur POSIX. L'implémentation Linux de cette interface peut différer (consultez la page de manuel Linux correspondante pour les détails du comportement sous Linux), ou l'interface peut ne pas être implémentée sous Linux.

NOM

nice — invoquer un utilitaire avec une valeur de priorité modifiée

SYNTAXE

nice [-n incrément] utilitaire [argument...]

DESCRIPTION

L'utilitaire nice invoque un utilitaire, demandant qu'il soit exécuté avec une valeur de priorité différente (voir le volume des Définitions de base de POSIX.1‐2017, Section 3.244, Valeur de priorité). Sans option, l'utilitaire exécuté doit être lancé avec une valeur de priorité supérieure ou égale à la valeur de priorité du processus courant, selon une quantité définie par l'implémentation. Si l'utilisateur ne dispose pas des privilèges appropriés pour affecter la valeur de priorité de la manière demandée, l'utilitaire nice n'affectera pas la valeur de priorité ; dans ce cas, un message d'avertissement peut être écrit sur la sortie standard d'erreur, mais cela n'empêchera pas l'invocation de l'utilitaire ni n'affectera son statut de sortie.

OPTIONS

L'utilitaire nice doit être conforme au volume des Définitions de base de POSIX.1‐2017, Section 12.2, Directives de syntaxe des utilitaires.

L'option suivante est prise en charge :

-n incrément
Un entier décimal positif ou négatif qui doit avoir le même effet sur l'exécution de l'utilitaire que si l'utilitaire avait appelé la fonction nice() avec la valeur numérique de l'argument d'option incrément.

OPÉRANDES

Les opérandes suivants doivent être pris en charge :

utilitaire
Le nom d'un utilitaire à invoquer. Si l'opérande utilitaire nomme l'un des utilitaires intégrés spéciaux de la Section 2.14, Utilitaires intégrés spéciaux, les résultats sont indéfinis.
argument
Toute chaîne de caractères à fournir comme argument lors de l'invocation de l'utilitaire nommé par l'opérande utilitaire.

ENTRÉE STANDARD

Non utilisé.

FICHIERS D'ENTRÉE

Aucun.

VARIABLES D'ENVIRONNEMENT

Les variables d'environnement suivantes doivent affecter l'exécution de nice :

LANG
Fournit une valeur par défaut pour les variables d'internationalisation qui sont non définies ou vides. (Voir le volume des Définitions de base de POSIX.1‐2017, Section 8.2, Variables d'internationalisation pour la précédence des variables d'internationalisation utilisées pour déterminer les valeurs des catégories de localisation.)
LC_ALL
Si définie à une chaîne de caractères non vide, remplace les valeurs de toutes les autres variables d'internationalisation.
LC_CTYPE
Détermine la localisation pour l'interprétation des séquences d'octets de données textuelles en caractères (par exemple, caractères mono-octet par opposition aux caractères multi-octets dans les arguments).
LC_MESSAGES

Détermine la localisation qui doit être utilisée pour affecter le format et le contenu des messages de diagnostic écrits sur la sortie standard d'erreur.
NLSPATH
Détermine l'emplacement des catalogues de messages pour le traitement de LC_MESSAGES.
PATH
Détermine le chemin de recherche utilisé pour localiser l'utilitaire à invoquer. Voir le volume des Définitions de base de POSIX.1‐2017, Chapitre 8, Variables d'environnement.

ÉVÉNEMENTS ASYNCHRONES

Par défaut.

SORTIE STANDARD

Non utilisé.

SORTIE STANDARD D'ERREUR

La sortie standard d'erreur ne doit être utilisée que pour les messages de diagnostic.

FICHIERS DE SORTIE

Aucun.

DESCRIPTION ÉTENDUE

Aucune.

STATUT DE SORTIE

Si l'utilitaire est invoqué, le statut de sortie de nice sera le statut de sortie de l'utilitaire ; sinon, l'utilitaire nice se terminera avec l'une des valeurs suivantes :

1‐125
Une erreur s'est produite dans l'utilitaire nice.
  126
L'utilitaire spécifié par utilitaire a été trouvé mais n'a pas pu être invoqué.
  127
L'utilitaire spécifié par utilitaire n'a pas pu être trouvé.

CONSÉQUENCES DES ERREURS

Par défaut.

Les sections suivantes sont informatives.

UTILISATION PAR L'APPLICATION

Les seules utilisations portables garanties de cet utilitaire sont :

nice utilitaire

Exécute l'utilitaire avec la valeur de priorité élevée ou égale par défaut.
nice -n <entier positif> utilitaire

Exécute l'utilitaire avec une valeur de priorité plus élevée.

Sur certaines implémentations, ils n'ont aucun effet perceptible sur l'utilitaire invoqué et sur d'autres, ils sont exactement équivalents.

Les systèmes historiques ont fréquemment pris en charge l'<entier positif> jusqu'à 20. Comme il n'y a pas de pénalité d'erreur associée à la supposition d'un nombre trop élevé, les utilisateurs n'ayant pas accès au document de conformité du système (pour voir quelles limites sont réellement en place) pourraient utiliser la plage historique de 1 à 20 ou tenter d'utiliser de très grands nombres si le travail doit être vraiment de faible priorité.

La valeur de priorité d'un processus peut être affichée à l'aide de la commande :

ps -o nice

Les utilitaires command, env, nice, nohup, time, et xargs ont été spécifiés pour utiliser le code de sortie 127 en cas d'erreur afin que les applications puissent distinguer une "échec de recherche d'un utilitaire" d'une "l'utilitaire invoqué s'est terminé avec une indication d'erreur". La valeur 127 a été choisie car elle n'est pas couramment utilisée pour d'autres significations ; la plupart des utilitaires utilisent de petites valeurs pour les "conditions d'erreur normales" et les valeurs supérieures à 128 peuvent être confondues avec une terminaison due à la réception d'un signal. La valeur 126 a été choisie de manière similaire pour indiquer que l'utilitaire a été trouvé, mais pas invoqué. Certains scripts produisent des messages d'erreur significatifs différenciant les cas 126 et 127. La distinction entre les codes de sortie 126 et 127 est basée sur la pratique de KornShell qui utilise 127 lorsque toutes les tentatives d'exécuter l'utilitaire échouent avec [ENOENT], et utilise 126 lorsque toute tentative d'exécuter l'utilitaire échoue pour toute autre raison.

JUSTIFICATION

La version 4.3 BSD de nice ne vérifie pas si l'incrément est un entier décimal valide. La commande nice -x utilitaire, par exemple, serait traitée de la même manière que la commande nice -- nice(1p) — POSIX standard man pages

RATIONALE

If the user does not have appropriate privileges, attempting to change the priority of a process results in an error. If the user attempts to lower the nice value (increase the real-time priority) without appropriate privileges, this is considered a bug. System V implementations treat a negative increment for a user without privileges as an attempt to increase priority, and they execute the utility with the default nice value (equivalent to nice -0 utility).

The 4.3 BSD implementation writes a "permission denied" message and does not run the utility. The standard specifies the System V behavior and mentions that an optional BSD-style "permission denied" message can also be written.

The C shell has a built-in nice utility with a different interface than the one described here. This volume of POSIX.1‐2017 describes the standard utility interface.

The term "utility" is used rather than "command" to indicate that shell compound commands, pipelines, and so on, cannot be used. Special built-ins also cannot be used. However, "utility" includes user application programs and shell scripts, not just utilities defined in this volume of POSIX.1‐2017.

Historical implementations of nice provided a nice value range of 40 or 41 discrete steps, with the default nice value being the midpoint of that range. By default, they raised the nice value of the executed utility by 10.

Some historical documentation states that the increment value must be within a fixed range. This is misleading because the valid increment values on any invocation are determined by the current process nice value, which is not always the default.

The definition of nice value is not intended to suggest that all processes in a system have priorities that are comparable. Scheduling policy extensions, such as the realtime priorities in the System Interfaces volume of POSIX.1‐2017, make the notion of a single underlying priority for all scheduling policies problematic. Some implementations may implement the nice-related features to affect all processes on the system, others to affect just the general time-sharing activities implied by this volume of POSIX.1‐2017, and others may have no effect at all. Because of the use of "implementation-defined" in nice and renice, a wide range of implementation strategies are possible.

Earlier versions of this standard allowed a -increment option. This form is no longer specified by POSIX.1‐2008 but may be present in some implementations.
