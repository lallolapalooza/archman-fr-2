nix-store --verify(1) Manuel des commandes générales nix-store --verify(1)

Nom

nix-store --verify - vérifier la cohérence de la base de données Nix

Synopsis

nix-store --verify [--check-contents] [--repair]

Description

L'opération --verify vérifie la cohérence interne de la base de données Nix et la cohérence entre la base de données Nix et le magasin Nix. Toute incohérence rencontrée est automatiquement réparée. Les incohérences résultent généralement de la modification du magasin ou de la base de données Nix par des outils autres que Nix, ou de bugs dans Nix lui-même.

Cette opération a les options suivantes :

•
--check-contents
Vérifie que le contenu de chaque chemin de magasin valide n'a pas été altéré en calculant un hash SHA-256 du contenu et en le comparant au hash stocké dans la base de données Nix au moment de la construction. Les chemins modifiés sont affichés. Pour les magasins volumineux, --check-contents est évidemment assez lent.
•
--repair
Si un chemin valide est manquant dans le magasin, ou (si --check-contents est donné) si le contenu d'un chemin valide a été modifié, alors essayez de réparer le chemin en le redownloadant. Voir nix-store --repair-path pour les détails.

Options

Les options suivantes sont autorisées pour toutes les opérations nix-store, mais peuvent ne pas avoir d'effet.

•
--add-root chemin
Enregistre le résultat d'une réalisation (--realise et --force-realise) comme une racine du collecteur de gaspillage (garbage collector). chemin sera créé comme un lien symbolique vers le chemin du magasin résultant. De plus, un lien symbolique portant un nom unique vers chemin sera créé dans /nix/var/nix/gcroots/auto/. Par exemple,
$ nix-store --add-root /home/eelco/bla/result --realise ...
$ ls -l /nix/var/nix/gcroots/auto
lrwxrwxrwx    1 ... 2005-03-13 21:10 dn54lcypm8f8... -> /home/eelco/bla/result
$ ls -l /home/eelco/bla/result
lrwxrwxrwx    1 ... 2005-03-13 21:10 /home/eelco/bla/result -> /nix/store/1r11343n6qd4...-f-spot-0.0.10
Ainsi, lorsque /home/eelco/bla/result est supprimé, la racine de GC du répertoire auto devient un lien symbolique orphelin et sera ignoré par le collecteur.
Attention
Notez qu'il n'est pas possible de déplacer ou de renommer les racines de GC, car le lien symbolique dans le répertoire auto pointera toujours vers l'ancien emplacement.
S'il y a plusieurs résultats, plusieurs liens symboliques seront créés en numérotant séquentiellement les liens symboliques après le premier (par exemple, foo, foo-2, foo-3, et ainsi de suite).

Options communes

La plupart des commandes Nix acceptent les options de ligne de commande suivantes :

•
--help
Affiche un résumé de la syntaxe de la commande et quitte.
•
--version
Affiche le numéro de version de Nix sur la sortie standard et quitte.
•
--verbose / -v
Augmente le niveau de verbosité des messages de diagnostic imprimés sur la sortie standard d'erreur. Pour chaque opération Nix, les informations imprimées sur la sortie standard sont bien définies ; toute information de diagnostic est imprimée sur la sortie standard d'erreur, jamais sur la sortie standard.
Cette option peut être spécifiée plusieurs fois. Actuellement, les niveaux de verbosité suivants existent :
•
0 « Erreurs uniquement »
Imprime uniquement les messages expliquant pourquoi l'invocation Nix a échoué.
•
1 « Informatif »
Imprime des messages utiles sur ce que Nix fait. C'est le comportement par défaut.
•
2 « Bavard »
Imprime plus de messages informatifs.
•
3 « Verbeux »
Imprime encore plus de messages informatifs.
•
4 « Débogage »
Imprime des informations de débogage.
•
5 « Vomir »
Imprime une quantité énorme d'informations de débogage.
•
--quiet
Diminue le niveau de verbosité des messages de diagnostic imprimés sur la sortie standard d'erreur. C'est l'option inverse de -v / --verbose.
Cette option peut être spécifiée plusieurs fois. Voir la liste précédente des niveaux de verbosité.
•
--log-format format
Cette option peut être utilisée pour changer le format de sortie des logs, avec format étant l'une des options suivantes :
•
raw
C'est le format brut, tel qu'affiché par nix-build.
•
internal-json
Affiche les logs de manière structurée.
Attention
Bien que le schéma lui-même soit relativement stable, le format des messages d'erreur (notamment le champ msg) peut changer entre les versions.
•
bar
Affiche uniquement une barre de progression pendant les constructions.
•
bar-with-logs
Affiche les logs bruts, avec la barre de progression en bas.
•
--no-build-output / -Q
Par défaut, la sortie produite par les constructeurs en sortie standard et en sortie d'erreur est renvoyée vers la sortie d'erreur de la commande Nix. Cette option supprime ce comportement. Notez que la sortie et l'erreur standard du constructeur sont toujours écrites dans un fichier journal dans prefix/nix/var/log/nix.
•
--max-jobs / -j nombre
Définit le nombre maximum de tâches de construction que Nix effectuera en parallèle au nombre spécifié. Spécifiez auto pour utiliser le nombre de processeurs du système. La valeur par défaut est spécifiée par le paramètre de configuration max-jobs, qui lui-même est par défaut à
lass="Li">1. Une valeur plus élevée est utile sur les systèmes SMP ou pour exploiter la latence des E/S.
Le définir à 0 interdit la compilation sur la machine locale, ce qui est utile lorsque vous souhaitez que les compilations se produisent uniquement sur des bâtisseurs distants.
•
--cores
Définit la valeur de la variable d'environnement NIX_BUILD_CORES dans l'invocation des bâtisseurs. Les bâtisseurs peuvent utiliser cette variable à leur discrétion pour contrôler le degré maximal de parallélisme. Par exemple, dans Nixpkgs, si l'attribut de dérivation enableParallelBuilding est défini à true, le bâtisseur passe le drapeau -jN à GNU Make. Par défaut, il utilise la valeur du paramètre de configuration cores, s'il est défini, ou 1 sinon. La valeur 0 signifie que le bâtisseur doit utiliser tous les cœurs de processeur disponibles dans le système.
•
--max-silent-time
Définit le nombre maximal de secondes pendant lesquelles un bâtisseur peut fonctionner sans produire aucune donnée sur la sortie standard ou l'erreur standard. La valeur par défaut est spécifiée par le paramètre de configuration max-silent-time. 0 signifie pas de délai d'attente.
•
--timeout
Définit le nombre maximal de secondes pendant lesquelles un bâtisseur peut s'exécuter. La valeur par défaut est spécifiée par le paramètre de configuration timeout. 0 signifie pas de délai d'attente.
•
--keep-going / -k
Continuer autant que possible en cas d'échecs de compilation. Autrement dit, si la compilation d'une entrée d'une dérivation échoue, Nix compilera toujours les autres entrées, mais pas la dérivation elle-même. Sans cette option, Nix s'arrête si une compilation échoue (sauf pour les compilations de substituts), tuant potentiellement les compilations en cours (en cas de compilations parallèles ou distribuées).
•
--keep-failed / -K
Spécifie qu'en cas d'échec de compilation, le répertoire temporaire (généralement dans /tmp) dans lequel la compilation a lieu ne doit pas être supprimé. Le chemin du répertoire de compilation est imprimé comme message d'information.
•
--fallback
Chaque fois que Nix tente de compiler une dérivation pour laquelle des substituts sont connus pour chaque chemin de sortie, mais que la réalisation des chemins de sortie via les substituts échoue, il se rabattra sur la compilation de la dérivation.
Le scénario le plus courant dans lequel cela est utile est lorsque nous avons enregistré des substituts pour effectuer une distribution binaire, disons, à partir d'un dépôt réseau. Si le dépôt est en panne, la réalisation de la dérivation échouera. Lorsque cette option est spécifiée, Nix compilera la dérivation à la place. Ainsi, l'installation à partir de binaires se rabattra sur l'installation à partir de sources. Cette option n'est pas la valeur par défaut car il n'est généralement pas souhaitable qu'un échec transitoire dans l'obtention des substituts entraîne une compilation complète à partir des sources (avec la consommation de ressources associée).
•
--readonly-mode
Lorsque cette option est utilisée, aucune tentative n'est faite pour ouvrir la base de données Nix. La plupart des opérations Nix nécessitent un accès à la base de données, donc ces opérations échoueront.
•
--arg name value
Cette option est acceptée par nix-env, nix-instantiate, nix-shell et nix-build. Lors de l'évaluation des expressions Nix, l'évaluateur d'expressions tentera automatiquement d'appeler les fonctions qu'il rencontre. Il peut appeler automatiquement les fonctions pour lesquelles chaque argument a une valeur par défaut (par exemple, { argName ? defaultValue }: ...).
Avec --arg, vous pouvez également appeler des fonctions qui ont des arguments sans valeur par défaut (ou remplacer une valeur par défaut). C'est-à-dire, si l'évaluateur rencontre une fonction avec un argument nommé name, il l'appellera avec la valeur value.
Par exemple, le default.nix de niveau supérieur dans Nixpkgs est en fait une fonction :
{ # Le système (par exemple, `i686-linux') pour lequel construire les paquets.
system ? builtins.currentSystem
...
}: ...
Ainsi, si vous appelez cette expression Nix (par exemple, lorsque vous faites nix-env --install --attr pkgname), la fonction sera appelée automatiquement en utilisant la valeur builtins.currentSystem pour l'argument system. Vous pouvez remplacer cela en utilisant --arg, par exemple, nix-env --install --attr pkgname --arg system \"i686-freebsd\". (Notez que comme l'argument est une chaîne littérale Nix, vous devez échapper les guillemets.)
•
--argstr name value
Cette option est similaire à --arg, sauf que la valeur n'est pas une expression Nix mais une chaîne. Donc, au lieu de --arg system \"i686-linux\" (les guillemets extérieurs servent à maintenir le shell heureux) vous pouvez dire --argstr system i686-linux.
•
--attr / -A attrPath
Sélectionne un attribut de l'expression Nix de niveau supérieur en cours d'évaluation. (nix-env, nix-instantiate, nix-build et nix-shell uniquement.) Le chemin d'attribut attrPath est une séquence de noms d'attributs séparés par des points. Par exemple, étant donné une expression Nix de niveau supérieur e, le chemin d'attribut xorg.xorgserver ferait en sorte que l'expression e.xorg.xorgserver soit utilisée. Voir nix-env --install pour quelques exemples concrets.
En plus des noms d'attributs, vous pouvez également spécifier des indices de tableau. Par exemple, le chemin d'attribut foo.3.bar sélectionne l'attribut bar du quatrième élément du tableau dans l'attribut foo de l'expression de niveau supérieur.
•
--expr / -E
Interprète les arguments de la ligne de commande comme une liste d'expressions Nix à analyser et à évaluer, plutôt que comme une liste de noms de fichiers d'expressions Nix. (nix-instantiate, nix-build et nix-shell uniquement.)
Pour nix-shell, cette option est couramment utilisée pour vous fournir un shell dans lequel vous pouvez compiler les paquets retournés par l'expression. Si vous souhaitez obtenir un shell contenant les paquets *compilés* prêts à l'emploi, donnez votre expression à l'indicateur pratique nix-shell --packages à la place.
•
-I / --include path
Ajoute une entrée à la liste des chemins de recherche utilisés pour résoudre les chemins de recherche. Cette option peut être donnée plusieurs fois.
Les chemins ajoutés via -I ont priorité sur le paramètre de configuration nix-path et la variable d'environnement NIX_PATH .
•
--option name value
Définit l'option de configuration Nix name à value. Cela remplace les paramètres du fichier de configuration Nix (voir nix.conf5).
•
--repair
Corrige les chemins de magasin corrompus ou manquants en les retéléchargeant ou en les recompilant. Notez que cela est lent car cela nécessite de calculer un hachage cryptographique du contenu de chaque chemin dans la fermeture de la compilation. Notez également l'avertissement sous nix-store --repair-path.

Remarque

Voir man nix.conf pour remplacer les paramètres de configuration avec des indicateurs de ligne de commande.

Variables d'environnement courantes

La plupart des commandes Nix interprètent les variables d'environnement suivantes :

•
IN_NIX_SHELL
Indicateur indiquant si l'environnement actuel a été configuré par nix-shell. Il peut avoir les valeurs pure ou impure.
•
NIX_PATH
Une liste d'entrées de chemin de recherche séparées par des deux-points utilisée pour résoudre les chemins de recherche
.
Cette variable d'environnement remplace la valeur du paramètre de configuration nix-path.
Elle peut être étendue en utilisant l'option -I.
Exemple
$ export NIX_PATH=`/home/eelco/Dev:nixos-config=/etc/nixos
Si NIX_PATH est défini sur une chaîne vide, la résolution des chemins de recherche échouera toujours.
Exemple
$ NIX_PATH= nix-instantiate --eval '<nixpkgs>'
error: file 'nixpkgs' was not found in the Nix search path (add it using $NIX_PATH or -I)
•
NIX_IGNORE_SYMLINK_STORE
Normalement, le répertoire du magasin Nix (typiquement /nix/store) ne doit pas contenir de composants de lien symbolique. Ceci afin d'empêcher les constructions « impures ». Les constructeurs « canonisent » parfois les chemins en résolvant tous les composants de lien symbolique. Ainsi, les constructions sur différentes machines (avec /nix/store résolu à des emplacements différents) pourraient donner des résultats différents. Ce n'est généralement pas un problème, sauf lorsque les constructions sont déployées sur des machines où /nix/store est résolu différemment. Si vous êtes sûr que vous n'allez pas faire cela, vous pouvez définir NIX_IGNORE_SYMLINK_STORE à 1.
Notez que si vous créez un lien symbolique vers le magasin Nix afin de le placer sur un système de fichiers autre que le système de fichiers racine, sous Linux, il est préférable d'utiliser des points de montage bind, par exemple :
$ mkdir /nix
$ mount -o bind /mnt/otherdisk/nix /nix
Consultez la page de manuel mount 8 pour plus de détails.
•
NIX_STORE_DIR
Remplace l'emplacement du magasin Nix (par défaut prefix/store).
•
NIX_DATA_DIR
Remplace l'emplacement du répertoire de données statiques Nix (par défaut prefix/share).
•
NIX_LOG_DIR
Remplace l'emplacement du répertoire de logs Nix (par défaut prefix/var/log/nix).
•
NIX_STATE_DIR
Remplace l'emplacement du répertoire d'état Nix (par défaut prefix/var/nix).
•
NIX_CONF_DIR
Remplace l'emplacement du répertoire de configuration système Nix (par défaut prefix/etc/nix).
•
NIX_CONFIG
Applique les paramètres de configuration Nix depuis l'environnement. Le contenu est traité comme s'il était lu à partir d'un fichier de configuration Nix. Les paramètres sont séparés par le caractère de nouvelle ligne.
•
NIX_USER_CONF_FILES
Remplace l'emplacement des fichiers de configuration utilisateur Nix à charger.
Les valeurs par défaut sont les emplacements conformément à la Spécification des répertoires de base XDG. Voir la sous-section Répertoires de base XDG pour plus de détails.
La variable est traitée comme une liste séparée par le jeton :.
•
TMPDIR
Utilise le répertoire spécifié pour stocker les fichiers temporaires. En particulier, cela inclut les répertoires de construction temporaires ; ceux-ci peuvent occuper une quantité substantielle d'espace disque. La valeur par défaut est /tmp.
•
NIX_REMOTE
Cette variable doit être définie sur daemon si vous souhaitez utiliser le démon Nix pour exécuter des opérations Nix. Ceci est nécessaire dans les installations Nix multi-utilisateurs. Si le socket Unix du démon Nix se trouve à un chemin non standard, cette variable doit être définie sur unix://chemin/vers/socket. Sinon, elle doit être laissée non définie.
•
NIX_SHOW_STATS
Si elle est définie sur 1, Nix affichera des statistiques d'évaluation, telles que le nombre de valeurs allouées.
•
NIX_COUNT_CALLS
Si elle est définie sur 1, Nix indiquera combien de fois les fonctions ont été appelées lors de l'évaluation des expressions Nix. Ceci est utile pour profiler vos expressions Nix.
•
GC_INITIAL_HEAP_SIZE
Si Nix a été configuré pour utiliser le garbage collector Boehm, cette variable définit la taille initiale du tas en octets. Sa valeur par défaut est de 384 MiB. La définir sur une valeur faible réduit la consommation de mémoire, mais augmente le temps d'exécution en raison de la surcharge du garbage collection.

Répertoires de base XDG

Nix suit la Spécification des répertoires de base XDG.

Pour des raisons de compatibilité ascendante, les commandes Nix suivront la norme uniquement lorsque use-xdg-base-directories est activé. Les nouvelles commandes Nix (expérimentales) sont conformes à la norme par défaut.

Les variables d'environnement suivantes sont utilisées pour déterminer les emplacements des divers fichiers d'état et de configuration :

  • [XDG_CONFIG_HOME]{#env-XDGCONFIGHOME} (par défaut ~/.config)
  • [XDG_STATE_HOME]{#env-XDGSTATEHOME} (par défaut ~/.local/state)
  • [XDG_CACHE_HOME]{#env-XDGCACHEHOME} (par défaut ~/.cache)
