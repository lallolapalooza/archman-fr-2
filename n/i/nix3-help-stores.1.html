Attention

Nom

nix help-stores - afficher l'aide sur les types de magasins et leurs paramètres

Synopsis

nix help-stores [option…]

Nix prend en charge différents types de magasins :

  • Magasin Dummy
  • Magasin expérimental d'overlay local
  • Magasin expérimental SSH
  • Magasin expérimental SSH avec système de fichiers monté
  • Magasin de cache binaire HTTP
  • Magasin de cache binaire local
  • Magasin de démon local
  • Magasin local
  • Magasin de cache binaire S3
  • Magasin SSH

Format URL de magasin

Les magasins sont spécifiés à l'aide d'une syntaxe similaire à une URL. Par exemple, la commande

# nix path-info --store https://cache.nixos.org/ --json \
  /nix/store/a7gvj343m05j2s32xcnwr35v31ynlypr-coreutils-9.1

récupère des informations sur un chemin de magasin dans le cache binaire HTTP situé à https://cache.nixos.org/, qui est un type de magasin.

Les URL de magasin peuvent spécifier des paramètres de magasin en utilisant des chaînes de requête d'URL, c'est-à-dire en ajoutant ?name1=value1&name2=value2&... à l'URL. Par exemple,

--store ssh://machine.example.org?ssh-key=/path/to/my/key

indique à Nix d'accéder au magasin sur une machine distante via le protocole SSH, en utilisant /path/to/my/key comme clé privée SSH. Les paramètres pris en charge pour chaque type de magasin sont documentés ci-dessous.

L'URL de magasin spéciale auto permet à Nix de sélectionner automatiquement un magasin comme suit :

  • Utiliser le magasin local /nix/store si /nix/var/nix est accessible en écriture par l'utilisateur actuel.
  • Sinon, si /nix/var/nix/daemon-socket/socket existe, se connecter au démon Nix écoutant sur ce socket.
  • Sinon, sur Linux uniquement, utiliser le magasin local chroot ~/.local/share/nix/root, qui sera créé automatiquement s'il n'existe pas.
  • Sinon, utiliser le magasin local /nix/store.

Magasin Dummy

Format d'URL de magasin : dummy://

Ce type de magasin représente un magasin qui ne contient aucun chemin de magasin et ne peut pas être écrit. Il est utile lorsque vous souhaitez utiliser l'évaluateur Nix sans qu'aucun magasin Nix réel n'existe, par exemple :

# nix eval --store dummy:// --expr '1 + 2'

Magasin expérimental d'overlay local

Attention

Ce magasin fait partie d'une fonctionnalité expérimentale.

Pour utiliser ce magasin, assurez-vous que la fonctionnalité expérimentale local-overlay-store est activée. Par exemple, incluez ce qui suit dans nix.conf :

extra-experimental-features = local-overlay-store

Format d'URL de magasin : local-overlay

Ce type de magasin est une variation du [magasin local] conçue pour tirer parti du système de fichiers Overlay (OverlayFS en abrégé) de Linux. Tout comme OverlayFS combine un système de fichiers inférieur et supérieur en traitant le supérieur comme un patch du inférieur, le magasin d'overlay local combine un magasin inférieur avec un magasin presque-[local supérieur]. (« Presque » car bien que les systèmes de fichiers supérieurs pour OverlayFS soient valides en eux-mêmes, le magasin supérieur presque-local n'est pas un magasin local valide en lui-même car certaines références seront orphelines.) Pour utiliser ce magasin, vous devrez d'abord configurer un point de montage OverlayFS approprié car Nix ne le fera pas pour vous (bien qu'il vérifie que le point de montage est correctement configuré).

Parties conceptuelles d'un magasin d'overlay local

Ceci est une description plus abstraite/conceptuelle des parties d'un magasin en couches, une référence faisant autorité. Pour des instructions plus « pratiques », voir l'exemple détaillé dans la sous-section suivante.

Les parties d'un magasin d'overlay local sont les suivantes :

•
Magasin inférieur :
Spécifié avec le paramètre lower-store.
Il s'agit de toute implémentation de magasin qui inclut un répertoire de magasin dans le cadre du système de fichiers natif du système d'exploitation. Par exemple, il pourrait s'agir d'un [magasin local], d'un [démon lo

mon magasin], ou même un autre magasin de superposition local.
Le magasin de superposition local n'essaie jamais de modifier le magasin inférieur de quelque manière que ce soit. Quelque chose d'autre pourrait modifier le magasin inférieur, mais il existe des restrictions à cela. Nix lui-même exige que ce magasin ne fasse que croître et ne change pas autrement. Par exemple, de nouveaux objets de magasin peuvent être ajoutés, mais la suppression ou la modification d'objets de magasin n'est généralement pas autorisée, car cela pourrait confondre et corrompre tout magasin de superposition local utilisant ces objets. (De plus, le mécanisme de superposition de système de fichiers sous-jacent peut imposer des restrictions supplémentaires, voir ci-dessous.)
Le magasin inférieur ne doit pas changer pendant qu'il est monté dans le cadre d'un magasin de superposition. Pour vous en assurer, vous pourriez vouloir monter le répertoire du magasin en lecture seule (ce qui nécessite alors que le paramètre [lecture seule] soit défini sur vrai).
•
Répertoire du magasin inférieur :
Spécifié avec le réglage lower-store.real.
C'est le répertoire utilisé/exposé par le magasin inférieur.
Comme spécifié ci-dessus, Nix exige que le magasin local ne puisse que croître et pas changer autrement. OverlayFS de Linux impose en outre l'exigence supplémentaire que ce répertoire ne puisse pas du tout changer. Cela signifie que, tant qu'un magasin de superposition local existe qui utilise ce magasin comme magasin inférieur, ce répertoire ne doit pas changer.
•
Source des métadonnées du magasin inférieur :
Pas spécifié directement. Une conséquence du réglage lower-store, en fonction du type de magasin inférieur choisi.
Ceci est abstrait, juste une manière de lire les métadonnées des objets de magasin inférieurs. Par exemple, cela pourrait être une base de données SQLite (pour le [magasin local]), ou une connexion socket (pour le [magasin de démon local]).
Cela n'a pas besoin d'être inscriptible. Comme indiqué ci-dessus, un magasin de superposition local n'essaie jamais de modifier son magasin inférieur. Les métadonnées du magasin inférieur sont considérées comme faisant partie du magasin inférieur, tout comme les objets du système de fichiers du magasin qui apparaissent dans le répertoire du magasin.
•
Presque magasin supérieur :
Pas spécifié directement. Au lieu de cela, les parties constitutives sont spécifiées indépendamment comme décrit ci-dessous.
Ceci est presque, mais pas tout à fait, un [magasin local]. C'est parce que pris isolément, pas dans le cadre d'un magasin de superposition local, il apparaîtrait corrompu. Mais combiné avec tout le reste dans le cadre d'un magasin local de superposition, il est valide.
•
Répertoire de la couche supérieure :
Spécifié avec le réglage upper-layer.
Ceci contient des objets de magasin supplémentaires (ou, plus strictement, leurs objets du système de fichiers avec lesquels le magasin de superposition local étendra le magasin inférieur).
•
Répertoire du magasin supérieur :
Spécifié avec le réglage real. C'est le même que le réglage de base du magasin local, et peut également être spécifié indirectement avec le réglage root.
Ceci contient tous les objets de magasin des deux répertoires.
Le répertoire du magasin inférieur et le répertoire de la couche supérieure sont combinés via OverlayFS pour créer ce répertoire. Nix ne le fait pas lui-même, car il n'aurait généralement pas les autorisations nécessaires pour le faire, c'est donc à l'utilisateur de le configurer d'abord. Nix peut cependant vérifier éventuellement que les réglages de montage OverlayFS apparaissent comme prévu, correspondant aux propres réglages de Nix.
•
Base de données SQLite supérieure :
Pas spécifié directement. L'emplacement de la base de données dépend plutôt du réglage state. C'est toujours ${state}/db.
Ceci contient les métadonnées de tous les objets de magasin de la couche supérieure (tout au-delà de leurs objets système de fichiers), et également des copies en double de certaines métadonnées d'objets de magasin de la couche inférieure. La duplication permet aux métadonnées de la fermeture des objets de magasin de la couche supérieure d'être trouvées entièrement dans la couche supérieure. (Cela nous permet d'utiliser le même schéma SQL que la base de données SQLite du [magasin local], car les clés étrangères de ce schéma garantissent que les métadonnées de fermeture sont autonomes de cette manière.)

Exemple de disposition de système de fichiers

Voici un exemple concret d'utilisation, suivant les concepts de la section précédente.

Supposons que nous ayons les chemins suivants :

  • /mnt/example/merged-store/nix/store
  • /mnt/example/store-a/nix/store
  • /mnt/example/store-b

Alors l'URI de magasin suivante peut être utilisée pour accéder à un magasin local-overlay à /mnt/example/merged-store :

local-overlay://?root=/mnt/example/merged-store&lower-store=/mnt/example/store-a&upper-layer=/mnt/example/store-b

Le répertoire du magasin inférieur est situé à /mnt/example/store-a/nix/store, tandis que la couche supérieure est à /mnt/example/store-b.

Avant d'accéder au magasin de superposition, vous devrez vous assurer que le montage OverlayFS est correctement configuré :

mount -t overlay overlay \
  -o lowerdir="/mnt/example/store-a/nix/store" \
  -o upperdir="/mnt/example/store-b" \
  -o workdir="/mnt/example/workdir" \
  "/mnt/example/merged-store/nix/store"

Notez qu'OverlayFS exige que /mnt/example/workdir se trouve sur le même volume que upperdir.

Par défaut, Nix vérifiera que le point de montage a été correctement configuré et échouera avec une erreur si ce n'est pas le cas. Vous pouvez outrepasser ce comportement en passant check-mount=false si vous en avez besoin.

Magasin SSH expérimental avec système de fichiers monté

Attention

Ce magasin fait partie d'une fonctionnalité expérimentale.

Pour utiliser ce magasin, assurez-vous que la fonctionnalité expérimentale mounted-ssh-store est activée. Par exemple, incluez ceci dans votre nix.conf :

extra-experimental-features = mounted-ssh-store

Format de l'URL du magasin : mounted-ssh-ng://[username@]hostname

Type de magasin expérimental qui permet un accès complet à un magasin Nix sur une machine distante, et qui exige en outre que ce magasin soit monté dans le système de fichiers local.

Le montage de ce magasin n'est pas géré par Nix, et doit être géré manuellement. Il pourrait être réalisé avec SSHFS ou NFS, par exemple.

Le système de fichiers local est utilisé pour optimiser certaines opérations. Par exemple, au lieu de sérialiser des archives Nix et de les envoyer via le canal Nix, nous pouvons accéder directement aux données du système de fichiers via le point de montage.

Le système de fichiers local est également utilisé pour rendre possibles certaines opérations qui ne le seraient pas autrement. Par exemple, des racines de GC persistantes peuvent être créées si elles résident sur le même système de fichiers que le magasin distant : le côté distant créera les liens symboliques nécessaires pour éviter les conditions de concurrence.

Store Local

Format d'URL du store : local, root

Ce type de store accède directement à un Nix store dans le système de fichiers local (c'est-à-dire pas via le démon Nix). root est un chemin absolu qui est préfixé à d'autres répertoires tels que le répertoire Nix store. L'URL pseudo-store local désigne un store qui utilise / comme répertoire racine.

Un store qui utilise une racine autre que / est appelé un store chroot. Avec de tels stores, le répertoire du store est « logiquement » toujours /nix/store, donc les programmes qui y sont stockés ne peuvent être construits et exécutés qu'en faisant un chroot dans root. Les stores chroot ne prennent en charge la construction et l'exécution que sous Linux lorsque les espaces de noms de montage et les espaces de noms d'utilisateur sont activés.

Par exemple, la commande suivante utilise /tmp/root comme environnement chroot pour construire ou télécharger nixpkgs#hello puis l'exécuter :

# nix run --store /tmp/root nixpkgs#hello
Hello, world!

Ici, l'emplacement « physique » du store est /tmp/root/nix/store, et les métadonnées du store de Nix se trouvent dans /tmp/root/nix/var/nix/db.

Il est également possible, mais non recommandé, de modifier l'emplacement « logique » du Nix store par rapport à son défaut de /nix/store. Cela rend impossible l'utilisation de substituts par défaut tels que https://cache.nixos.org/, et par conséquent, vous pourriez avoir à tout construire localement. Voici un exemple :

# nix build --store 'local?store=/tmp/my-nix/store&state=/tmp/my-nix/state&log=/tmp/my-nix/log' nixpkgs#hello

Store de Cache Binaire S3

Format d'URL du store : s3://nom-du-bucket

Ce store permet de lire et d'écrire un cache binaire stocké dans un bucket AWS S3 (ou un service compatible S3). Ce store partage de nombreux idiomes avec le Store de Cache Binaire HTTP.

Pour AWS S3, l'URL du cache binaire pour un bucket nommé example-nix-cache sera exactement s3://example-nix-cache. Pour les caches binaires compatibles S3, consultez la documentation de ce cache.

Lectures anonymes sur votre cache binaire compatible S3

Si votre cache binaire est accessible publiquement et ne nécessite pas d'authentification, il est plus simple d'utiliser le [Store de Cache Binaire HTTP] plutôt que le Store de Cache Binaire S3 avec https://example-nix-cache.s3.amazonaws.com au lieu de s3://example-nix-cache.

Votre bucket aura besoin d'une politique de bucket similaire à la suivante pour être accessible :

{
    "Id&{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Sid": "AllowDirectReads",
            "Action": [
                "s3:GetObject",
                "s3:GetBucketLocation"
            ],
            "Effect": "Allow",
            "Resource": [
                "arn:aws:s3:::example-nix-cache",
                "arn:aws:s3:::example-nix-cache/*"
            ],
            "Principal": "*"
        }
    ]
}
```




Authentification


Nix utilisera la
    chaîne de fournisseurs d'informations d'identification par défaut pour authentifier les requêtes à Amazon S3.


Notez que cela signifie que Nix lira les variables d'environnement et les fichiers avec des idiomes différents de ceux des propres paramètres de Nix, tels qu'implémentés par le SDK AWS. Consultez la documentation liée ci-dessus pour plus de détails.






Lectures authentifiées sur votre cache binaire S3


Votre compartiment aura besoin d'une politique de compartiment autorisant les utilisateurs souhaités à effectuer les actions s3:GetObject et s3:GetBucketLocation sur tous les objets du compartiment. La
    politique anonyme donnée ci-dessus peut être mise à jour pour avoir un
    Principal restreint afin de prendre en charge cela.






Écritures authentifiées sur votre cache binaire compatible S3


Votre compte aura besoin d'une politique IAM pour prendre en charge le téléchargement vers le compartiment :


{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "UploadToCache",
      "Effect": "Allow",
      "Action": [
        "s3:AbortMultipartUpload",
        "s3:GetBucketLocation",
        "s3:GetObject",
        "s3:ListBucket",
        "s3:ListBucketMultipartUploads",
        "s3:ListMultipartUploadParts",
        "s3:PutObject"
      ],
      "Resource": [
        "arn:aws:s3:::example-nix-cache",
        "arn:aws:s3:::example-nix-cache/*"
      ]
    }
  ]
}

This document describes the Nix configuration file syntax. Nix searches for configuration files in the following locations, in order:
                ~/.config/nix/nix.conf, /etc/nix/nix.conf, and

The configuration file consists of zero or more

Settings can be boolean, numerical, or strings. Boolean settings
                can be set to true or false.

                sequence of characters, but quotes may be necessary if the string
                contains whitespace or special characters.

            
Many settings have machine-specific defaults, specified as
                machine-specific. These defaults are determined by
                the Nix installation or the underlying operating system.

NAME

                
nix3-help-stores — Nix store types

                
                
DESCRIPTION

                
This page describes the different Nix store types. A Nix store is a directory that stores Nix packages. Nix packages are stored in a read-only directory, typically /nix/store. All packages are stored in subdirectories named after their hash and description.

                
For example, a package might be stored in /nix/store/xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx, where xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx is a cryptographic hash of the package's contents and build script.

                
                
SUPPORTED STORE TYPES

                
Nix supports a variety of store types:

                
                
    
                    
  • Binary Cache Store
    • 
                    
  • Cache Store
    • 
                    
  • GC Roots Store
    • 
                    
  • Local Binary Cache Store
    • 
                    
  • Local Daemon Store
    • 
                    
  • Local Store
    • 
                    
  • S3 Binary Cache Store
    • 
                    
  • SSH Store
    • 
                

                
                
Binary Cache Store

                
The Binary Cache Store is a read-only store that fetches packages from a binary cache. This is typically used for downloading pre-built packages from a Nix mirror.

                
                
Cache Store

                
The Cache Store is a read-only store that fetches packages from a cache. This is similar to the Binary Cache Store, but it can also fetch packages from local caches.

                
                
GC Roots Store

                
The GC Roots Store is a special store that stores garbage collection roots. Garbage collection roots are references to packages that should not be garbage collected. This store is typically used by Nix daemons.

                
                
Local Binary Cache Store

                
The Local Binary Cache Store is a read-only store that fetches packages from a local binary cache. This is typically used for caching packages that have been downloaded from a remote binary cache.

                
                
Local Daemon Store

                
The Local Daemon Store is a read-only store that fetches packages from a local Nix daemon. This is typically used for development environments.

                
                
Local Store

                
The Local Store is a read-write store that stores packages locally. This is the default store type for Nix installations.

                
                
S3 Binary Cache Store

                
The S3 Binary Cache Store is a read-only store that fetches packages from an Amazon S3 bucket. This is useful for hosting your own binary caches.

                
                
SSH Store

                
The SSH Store is a read-only store that fetches packages from a remote host over SSH. This is useful for accessing packages on remote machines.

                
                
OPTIONS

                
The Nix store can be configured with various options, including the store directory, the cache type, and the cache URL.
