nix-env --query(1) Manuel des commandes générales nix-env --query(1)

Nom

nix-env --query - afficher des informations sur les paquets

Synopsis

nix-env {--query | -q} noms• [--installed | --available | -a] [{--status | -s}] [{--attr-path | -P}] [--no-name] [{--compare-versions | -c}] [--system] [--drv-path] [--out-path] [--description] [--meta] [--xml] [--json] [{--prebuilt-only | -b}] [{--attr | -A} chemin-attribut]

Description

L'opération de requête affiche des informations sur les chemins du magasin (store paths) qui sont installés dans la génération actuelle du profil actif (--installed), ou sur les dérivations qui sont disponibles pour l'installation dans l'expression Nix active (--available). Elle n'affiche des informations que sur les dérivations dont le nom symbolique correspond à l'un des noms.

Les dérivations sont triées par leurs attributs name.

Sélection de la source

Les options suivantes spécifient l'ensemble des éléments sur lesquels la requête opère.

•
--installed
La requête opère sur les chemins du magasin qui sont installés dans la génération actuelle du profil actif. C'est le comportement par défaut.
•
--available / -a
La requête opère sur les dérivations disponibles dans l'expression Nix active.

Requêtes

Les options suivantes spécifient quelles informations afficher sur les dérivations sélectionnées. Plusieurs options peuvent être spécifiées, auquel cas les informations sont affichées dans l'ordre donné. Notez que le nom de la dérivation est affiché sauf si --no-name est spécifié.

•
--xml
Affiche le résultat dans une représentation XML adaptée au traitement automatique par d'autres outils. L'élément racine est appelé items, qui contient un élément item pour chaque dérivation disponible ou installée. Les champs discutés ci-dessous sont tous stockés dans des attributs des éléments item.
•
--json
Affiche le résultat dans une représentation JSON adaptée au traitement automatique par d'autres outils.
•
--prebuilt-only / -b
N'affiche que les dérivations pour lesquelles une substitution est enregistrée, c'est-à-dire, il existe un binaire précompilé disponible qui peut être téléchargé à la place de la construction de la dérivation. Ceci affiche donc tous les paquets qui peuvent probablement être installés rapidement.
•
--status / -s
Affiche le *statut* de la dérivation. Le statut se compose de trois caractères. Le premier est I ou -, indiquant si la dérivation est actuellement installée dans la génération actuelle du profil actif. C'est le cas par définition pour --installed, mais pas pour --available. Le second est P ou -, indiquant si la dérivation est présente sur le système. Ceci indique si l'installation d'une dérivation disponible nécessitera la construction de la dérivation. Le troisième est S ou -, indiquant si une substitution est disponible pour la dérivation.
•
--attr-path / -P
Affiche le *chemin d'attribut* de la dérivation, qui peut être utilisé pour la sélectionner sans ambiguïté en utilisant l'option --attr disponible dans les commandes qui installent des dérivations comme nix-env --install. Cette option ne fonctionne qu'avec --available
•
--no-name
Supprime l'affichage de l'attribut name de chaque dérivation.
•
--compare-versions / -c
Compare les versions installées aux versions disponibles, ou vice versa (si --available est donné). Ceci est utile pour voir rapidement si des mises à jour pour les paquets installés sont disponibles dans une expression Nix. Une colonne est ajoutée avec la signification suivante :
•
< version
Une version plus récente du paquet est disponible ou installée.
•
= version
Au plus la même version du paquet est disponible ou installée.
•
> version
Seules des versions plus anciennes du paquet sont disponibles ou installées.
•
- ?
Aucune version du paquet n'est disponible ou installée.
•
--system
Affiche l'attribut system de la dérivation.
•
--drv-path
Affiche le chemin de la dérivation du magasin.
•
--out-path
Affiche le chemin de sortie de la dérivation.
•
--description
Affiche une courte description (une ligne) de la dérivation, si elle est disponible. La description est tirée de l'attribut meta.description de la dérivation.
•
--meta
Affiche tous les métadonnées de la dérivation. Cette option n'est disponible qu'avec --xml ou --json.

Options

Les options suivantes sont autorisées pour toutes les opérations nix-env, mais peuvent ne pas avoir d'effet dans tous les cas.

•
--file / -f chemin
Spécifie l'expression Nix (désignée ci-dessous comme l'*expression Nix active*) utilisée par les opérations --install, --upgrade et --query --available pour obtenir les dérivations. La valeur par défaut est ~/.nix-defexpr.
Si l'argument commence par http:// ou https://, il est interprété comme l'URL d'une archive tar qui sera téléchargée et décompressée dans un emplacement temporaire. L'archive doit inclure un seul répertoire de niveau supérieur contenant au moins un fichier nommé default.nix.
<
•
--profile / -p chemin
Spécifie le profil à utiliser par les opérations qui opèrent sur un profil (désigné ci-dessous comme le profil actif). Un profil est une séquence d'environnements utilisateur appelés générations, dont l'une est la génération actuelle.
•
--dry-run
Pour les opérations --install, --upgrade, --uninstall, --switch-generation, --delete-generations et --rollback, ce drapeau amène nix-env à imprimer ce qui serait fait si ce drapeau n'avait pas été spécifié, sans réellement le faire.
--dry-run affiche également quels chemins seront substitués (c'est-à-dire téléchargés) et quels chemins seront construits à partir de la source (car aucune substitut n'est disponible).
•
--system-filter système
Par défaut, les opérations comme --query --available affichent les dérivations correspondant à n'importe quelle plateforme. Cette option vous permet d'utiliser les dérivations pour la plateforme spécifiée système.

Options communes

La plupart des commandes Nix acceptent les options de ligne de commande suivantes :

•
--help
Imprime un résumé de la syntaxe de la commande et quitte.
•
--version
Imprime le numéro de version de Nix sur la sortie standard et quitte.
•
--verbose / -v
Augmente le niveau de verbosité des messages de diagnostic imprimés sur la sortie d'erreur standard. Pour chaque opération Nix, les informations imprimées sur la sortie standard sont bien définies ; toute information de diagnostic est imprimée sur la sortie d'erreur standard, jamais sur la sortie standard.
Cette option peut être spécifiée plusieurs fois. Actuellement, les niveaux de verbosité suivants existent :
•
0 « Erreurs uniquement »
Imprime uniquement les messages expliquant pourquoi l'invocation Nix a échoué.
•
1 « Informatif »
Imprime des messages *utiles* sur ce que Nix fait. C'est le comportement par défaut.
•
2 « Bavard »
Imprime plus de messages informatifs.
•
3 « Très bavard »
Imprime encore plus de messages informatifs.
•
4 « Débogage »
Imprime des informations de débogage.
•
5 « Vomitif »
Imprime une quantité énorme d'informations de débogage.
•
--quiet
Diminue le niveau de verbosité des messages de diagnostic imprimés sur la sortie d'erreur standard. C'est l'option inverse de -v / --verbose.
Cette option peut être spécifiée plusieurs fois. Voir la liste précédente des niveaux de verbosité.
•
--log-format format
Cette option peut être utilisée pour modifier le format de sortie du journal, format étant l'une des options suivantes :
•
raw
C'est le format brut, tel qu'il est produit par nix-build.
•
internal-json
Produit les journaux dans un format structuré.
Avertissement
Bien que le schéma lui-même soit relativement stable, le format des messages d'erreur (notamment du champ msg) peut changer entre les versions.
•
bar
Affiche uniquement une barre de progression pendant les constructions.
•
bar-with-logs
Affiche les journaux bruts, avec la barre de progression en bas.
•
--no-build-output / -Q
Par défaut, la sortie générée par les constructeurs vers la sortie standard et la sortie d'erreur standard est redirigée vers la sortie d'erreur standard de la commande Nix. Cette option supprime ce comportement. Notez que la sortie standard et l'erreur standard du constructeur sont toujours écrites dans un fichier journal dans prefix/nix/var/log/nix.
•
--max-jobs / -j nombre
Définit le nombre maximum de tâches de construction que Nix effectuera en parallèle au nombre spécifié. Spécifiez auto pour utiliser le nombre de CPU du système. La valeur par défaut est spécifiée par le réglage de configuration max-jobs, qui par défaut est 1. Une valeur plus élevée est utile sur les systèmes SMP ou pour exploiter la latence d'E/S.
Le réglage à 0 interdit la construction sur la machine locale, ce qui est utile lorsque vous souhaitez que les constructions aient lieu uniquement sur des constructeurs distants.
•
--cores
Définit la valeur de la variable d'environnement NIX_BUILD_CORES dans l'invocation des constructeurs. Les constructeurs peuvent utiliser cette variable à leur discrétion pour contrôler la quantité maximale de parallélisme. Par exemple, dans Nixpkgs, si l'attribut de dérivation enableParallelBuilding est réglé sur true, le constructeur transmet le drapeau -jN à GNU Make. Par défaut, il prend la valeur du réglage de configuration cores, si elle est définie, sinon 1. La valeur 0 signifie que le constructeur doit utiliser tous les cœurs de CPU disponibles dans le système.
•
--max-silent-time
Définit le nombre maximum de secondes pendant lesquelles un constructeur peut fonctionner sans produire de données sur la sortie standard ou la sortie d'erreur standard. La valeur par défaut est spécifiée par le réglage de configuration max-silent-time. 0 signifie pas de délai d'attente.
•
--timeout
Définit le nombre maximum de secondes pendant lesquelles un constructeur peut s'exécuter. La valeur par défaut est spécifiée par le réglage de configuration timeout. 0 signifie pas de délai d'attente.
•
--keep-going / -k
Continuer autant que possible en cas d'échec de construction. C'est-à-dire que si la construction d'une entrée d'une dérivation échoue, Nix construira toujours les autres entrées, mais pas la dérivation elle-même. Sans cette option, Nix s'arrête si une construction échoue (sauf pour les constructions de substituts), tuant éventuellement les constructions en cours (en cas de constructions parallèles ou distribuées).
•
--keep-failed / -K
Spécifie qu'en cas d'échec de construction, le répertoire temporaire (généralement dans /tmp) dans lequel la construction a lieu ne doit pas être supprimé. Le chemin du répertoire de construction est imprimé sous forme de message informatif.
•
--fallback
Chaque fois que Nix tente de construire une dérivation pour laquelle des substituts sont connus pour chaque chemin de sortie, mais que la réalisation des chemins de sortie via les substituts échoue, Nix se rabattra sur la construction de la dérivation.
Le scénario le plus courant pour lequel cela est utile est lorsque nous avons enregistré des substituts afin d'effectuer une distribution binaire depuis, par exemple, un dépôt réseau. Si le dépôt est hors service, la réalisation de la dérivation échouera. Lorsque cette option est spécifiée, Nix construira la dérivation à la place. Ainsi, l'installation à partir de binaires se rabattra sur l'installation à partir de la source. Cette option n'est pas le comportement par défaut car il n'est généralement pas souhaitable qu'un échec transitoire dans l'obtention des substituts entraîne une construction complète à partir de la source (avec la consommation de ressources associée).
•
--readonly-mode
Lorsque cette option est utilisée, aucune tentative n'est faite pour ouvrir la base de données Nix. La plupart des opérations Nix nécessitent un accès à la base de données, donc ces opérations échoueront.
•
--arg nom valeur
Cette option est acceptée par nix-env, nix-instantiate, nix-shell et nix-build. Lors de l'évaluation d'expressions Nix, l'évaluateur d'expressions essaiera automatiquement d'appeler les fonctions qu'il rencontre. Il peut appeler automatiquement les fonctions pour lesquelles chaque argument possède une valeur par défaut (par exemple, { nomArg ? valeurParDefaut }: ...).
Avec --arg, vous pouvez également appeler des fonctions qui ont des arguments sans valeur par défaut (ou remplacer une valeur par défaut). C'est-à-dire que si l'évaluateur rencontre une fonction avec un argument nommé nom, il l'appellera avec la valeur valeur.
Par exemple, le fichier default.nix de Nixpkgs est en réalité une fonction :
{ # Le système (par ex., `i686-linux') pour lequel construire les paquets.
système ? builtins.currentSystem
...
}: ...
Ainsi, si vous appelez cette expression Nix (par exemple, lorsque vous faites nix-env --install --attr nomPaquet), la fonction sera appelée automatiquement en utilisant la valeur builtins.currentSystem pour l'argument système. Vous pouvez remplacer cela en utilisant --arg, par exemple, nix-env --install --attr nomPaquet --arg système \"i686-freebsd\". (Notez que puisque l'argument est une chaîne littérale Nix, vous devez échapper les guillemets.)
•
--argstr nom valeur
Cette option est similaire à --arg, sauf que la valeur n'est pas une expression Nix mais une chaîne. Donc, au lieu de --arg système \"i686-linux\" (les guillemets extérieurs servent à ne pas perturber le shell) vous pouvez dire --argstr système i686-linux.
•
--attr / -A cheminAttr
Sélectionne un attribut de l'expression Nix de haut niveau en cours d'évaluation. (Uniquement pour nix-env, nix-instantiate, nix-build et nix-shell.) Le chemin d'attribut cheminAttr est une séquence de noms d'attributs séparés par des points. Par exemple, étant donné une expression Nix de haut niveau e, le chemin d'attribut xorg.xorgserver provoquerait l'utilisation de l'expression e.xorg.xorgserver. Voir nix-env --install pour quelques exemples concrets.
En plus des noms d'attributs, vous pouvez également spécifier des indices de tableau. Par exemple, le chemin d'attribut foo.3.bar sélectionne l'attribut bar du quatrième élément du tableau dans l'attribut foo de l'expression de haut niveau.
•
--expr / -E
Interprète les arguments de la ligne de commande comme une liste d'expressions Nix à analyser et évaluer, plutôt que comme une liste de noms de fichiers d'expressions Nix. (Uniquement pour nix-instantiate, nix-build et nix-shell.)
Pour nix-shell, cette option est couramment utilisée pour vous fournir un shell dans lequel vous pouvez construire les paquets retournés par l'expression. Si vous souhaitez obtenir un shell contenant les paquets *construits* prêts à l'emploi, fournissez votre expression à l'indicateur de commodité nix-shell --packages à la place.
•
-I / --include chemin
Ajoute une entrée à la liste des chemins de recherche utilisés pour résoudre les chemins de recherche. Cette option peut être donnée plusieurs fois.
Les chemins ajoutés via -I ont la priorité sur le paramètre de configuration nix-path et la variable d'environnement NIX_PATH .
•
--option nom valeur
Définit l'option de configuration Nix nom à valeur. Cela remplace les paramètres du fichier de configuration Nix (voir nix.conf5).
•
--repair
Réparer les chemins de magasin corrompus ou manquants en les redownloadant ou les reconstruisant. Notez que cela est lent car cela nécessite le calcul d'un hachage cryptographique du contenu de chaque chemin dans la fermeture de la construction. Notez également l'avertissement sous nix-store --repair-path.

Note

Voir man nix.conf pour remplacer les paramètres de configuration avec des indicateurs de ligne de commande.

Variables d'environnement

•
NIX_PROFILE
Emplacement du profil Nix. Par défaut, le lien symbolique ~/.nix-profile, s'il existe, ou /nix/var/nix/profiles/default sinon.

Variables d'environnement communes

La plupart des commandes Nix interprètent les variables d'environnement suivantes :

•
IN_NIX_SHELL
Indicateur qui signale si l'environnement actuel a été configuré par nix-shell. Il peut avoir les valeurs pure ou impure.
•
NIX_PATH
Une liste d'entrées de chemins de recherche séparées par des deux-points, utilisée pour résoudre les chemins de recherche.
Cette variable d'environnement remplace la valeur du paramètre de configuration nix-path .
Elle peut être étendue en utilisant l'indicateur -I .
Exemple
$ export NIX_PATH=`/home/eelco/Dev:nixos-config=/etc/nixos
Si NIX_PATH est défini sur une chaîne vide, la résolution des chemins de recherche échouera toujours.
Exemple
$ NIX_PATH= nix-instantiate --eval '<nixpkgs>'
error: file 'nixpkgs' was not found in the Nix search path (add it using $NIX_PATH or -I)
•
NIX_IGNORE_SYMLINK_STORE
Normalement, le répertoire du magasin Nix (typiquement /nix/store) n'est pas autorisé à contenir de composants de lien symbolique. Ceci afin d'éviter les constructions "impures". Les constructeurs "canonicalisent" parfois les chemins en résolvant tous les composants de lien symbolique. Ainsi, les constructions sur différentes machines (avec /nix/store résolvant vers des emplacements différents) pourraient donner des résultats différents. Ce n'est généralement pas un problème, sauf lorsque les constructions sont déployées sur des machines où /nix/store se résout différemment. Si vous êtes sûr que vous n'allez pas faire cela, vous pouvez définir NIX_IGNORE_SYMLINK_STORE à 1.
Notez que si vous créez un lien symbolique vers le magasin Nix afin de pouvoir le placer sur un système de fichiers autre que le système de fichiers racine, sous Linux, il est préférable d'utiliser des points de montage bind, par exemple :
$ mkdir /nix
$ mount -o bind /mnt/otherdisk/nix /nix
Consultez la page de manuel de mount 8 pour plus de détails.
•
NIX_STORE_DIR
Remplace l'emplacement du magasin Nix (par défaut prefix/store).
•
NIX_DATA_DIR
Remplace l'emplacement du répertoire de données statiques Nix (par défaut prefix/share).
•
NIX_LOG_DIR
Remplace l'emplacement du répertoire de journaux Nix (par défaut prefix/var/log/nix).
•
NIX_STATE_DIR
Remplace l'emplacement du répertoire d'état Nix (par défaut prefix/var/nix).
•
NIX_CONF_DIR
Remplace l'emplacement du répertoire de configuration système Nix (par défaut prefix/etc/nix).
•
NIX_CONFIG
Applique les paramètres duLa configuration Nix à partir de l'environnement. Le contenu est traité comme s'il était lu à partir d'un fichier de configuration Nix. Les paramètres sont séparés par le caractère de nouvelle ligne.
•
NIX_USER_CONF_FILES
Remplace l'emplacement des fichiers de configuration utilisateur de Nix à charger depuis.
Par défaut, ce sont les emplacements selon la spécification XDG Base Directory Specification. Voir la sous-section XDG Base Directories pour plus de détails.
La variable est traitée comme une liste séparée par le jeton :.
•
TMPDIR
Utilise le répertoire spécifié pour stocker les fichiers temporaires. En particulier, cela inclut les répertoires de construction temporaires ; ceux-ci peuvent occuper une quantité importante d'espace disque. Par défaut, c'est /tmp.
•
NIX_REMOTE
Cette variable doit être définie sur daemon si vous souhaitez utiliser le démon Nix pour exécuter des opérations Nix. Ceci est nécessaire dans les installations Nix multi-utilisateurs. Si le socket Unix du démon Nix se trouve dans un chemin non standard, cette variable doit être définie sur unix://chemin/vers/socket. Sinon, elle doit être laissée non définie.
•
NIX_SHOW_STATS
Si elle est définie sur 1, Nix affichera quelques statistiques d'évaluation, telles que le nombre de valeurs allouées.
•
NIX_COUNT_CALLS
Si elle est définie sur 1, Nix affichera la fréquence d'appel des fonctions lors de l'évaluation des expressions Nix. Ceci est utile pour le profilage de vos expressions Nix.
•
GC_INITIAL_HEAP_SIZE
Si Nix a été configuré pour utiliser le garbage collector Boehm, cette variable définit la taille initiale du tas en octets. Elle est par défaut de 384 MiB. La définir sur une valeur faible réduit la consommation de mémoire, mais augmentera le temps d'exécution en raison du surcoût de la collecte de garbage.

XDG Base Directories

Nix suit la spécification XDG Base Directory Specification.

Par souci de compatibilité ascendante, les commandes Nix ne suivront la norme que lorsque use-xdg-base-directories est activé. Les nouvelles commandes Nix (expérimentales) respectent la norme par défaut.

Les variables d'environnement suivantes sont utilisées pour déterminer les emplacements des divers fichiers d'état et de configuration :

  • [XDG_CONFIG_HOME]{#env-XDGCONFIGHOME} (par défaut ~/.config)
  • [XDG_STATE_HOME]{#env-XDGSTATEHOME} (par défaut ~/.local/state)
  • [XDG_CACHE_HOME]{#env-XDGCACHEHOME} (par défaut ~/.cache)

Exemples

Pour afficher les paquets installés :

$ nix-env --query
bison-1.875c
docbook-xml-4.2
firefox-1.0.4
MPlayer-1.0pre7
ORBit2-2.8.3
…

Pour afficher les paquets disponibles :

$ nix-env --query --available
firefox-1.0.7
GConf-2.4.0.1
MPlayer-1.0pre7
ORBit2-2.8.3
…

Pour afficher l'état des paquets disponibles :

$ nix-env --query --available --status
-P- firefox-1.0.7   (non installé mais présent)
--S GConf-2.4.0.1   (non présent, mais il existe un substitut pour une installation rapide)
--S MPlayer-1.0pre3 (c'est-à-dire qu'il ne s'agit pas du MPlayer installé, même si la version est identique !)
IP- ORBit2-2.8.3    (installé et par définition présent)
…

Pour afficher les paquets disponibles dans l'expression Nix foo.nix :

$ nix-env --file ./foo.nix --query --available
foo-1.2.3

Pour comparer les versions installées à ce qui est disponible :

$ nix-env --query --compare-versions
...
acrobat-reader-7.0 - ?      (le paquet n'est pas disponible du tout)
autoconf-2.59      = 2.59   (même version)
firefox-1.0.4      < 1.0.7  (une version plus récente est disponible)
...

Pour afficher tous les paquets contenant « zip » dans leur nom :

$ nix-env --query --available '.*zip.*'
bzip2-1.0.6
gzip-1.6
zip-3.0
…

Pour afficher tous les paquets contenant « firefox » ou « chromium » dans leur nom :

$ nix-env --query --available '.*(firefox|chromium).*'
chromium-37.0.2062.94
chromium-beta-38.0.2125.24
firefox-32.0.3
firefox-with-plugins-13.0.1
…

Pour afficher tous les paquets dans la dernière révision du dépôt Nixpkgs :

$ nix-env --file https://github.com/NixOS/nixpkgs/archive/master.tar.gz --query --available
