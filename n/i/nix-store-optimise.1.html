Nom

nix-store --optimise - réduire l'utilisation de l'espace disque

Synopsis

nix-store --optimise

Description

L'opération --optimise réduit l'utilisation de l'espace disque du magasin Nix en trouvant des fichiers identiques dans le magasin et en les liant en dur les uns aux autres. Elle réduit généralement la taille du magasin d'environ 25 à 35 %. Seuls les fichiers réguliers et les liens symboliques sont liés en dur de cette manière. Les fichiers sont considérés comme identiques lorsqu'ils ont la même sérialisation Nix Archive (NAR) : c'est-à-dire que les fichiers réguliers doivent avoir le même contenu et la même permission (exécutable ou non), et les liens symboliques doivent avoir le même contenu.

Une fois terminée, ou lorsque la commande est interrompue, un rapport sur les économies réalisées est imprimé sur la sortie d'erreur standard.

Utilisez -vv ou -vvv pour obtenir une indication de la progression.

Options

Les options suivantes sont autorisées pour toutes les opérations nix-store, mais peuvent ne pas toujours avoir d'effet.

•
--add-root chemin
Indique que le résultat d'une réalisation (--realise et --force-realise) doit être enregistré comme racine du collecteur de garbage. chemin sera créé comme un lien symbolique vers le chemin de magasin résultant. De plus, un lien symbolique au nom unique vers chemin sera créé dans /nix/var/nix/gcroots/auto/. Par exemple,
$ nix-store --add-root /home/eelco/bla/result --realise ...
$ ls -l /nix/var/nix/gcroots/auto
lrwxrwxrwx    1 ... 2005-03-13 21:10 dn54lcypm8f8... -> /home/eelco/bla/result
$ ls -l /home/eelco/bla/result
lrwxrwxrwx    1 ... 2005-03-13 21:10 /home/eelco/bla/result -> /nix/store/1r11343n6qd4...-f-spot-0.0.10
Ainsi, lorsque /home/eelco/bla/result est supprimé, la racine de GC dans le répertoire auto devient un lien symbolique orphelin et sera ignorée par le collecteur.
Attention
Notez qu'il n'est pas possible de déplacer ou de renommer les racines de GC, car le lien symbolique dans le répertoire auto pointera toujours vers l'ancien emplacement.
S'il y a plusieurs résultats, plusieurs liens symboliques seront créés en numérotant séquentiellement les liens symboliques au-delà du premier (par exemple, foo, foo-2, foo-3, et ainsi de suite).

Options communes

La plupart des commandes Nix acceptent les options de ligne de commande suivantes :

•
--help
Affiche un résumé de la syntaxe de la commande et quitte.
•
--version
Affiche le numéro de version de Nix sur la sortie standard et quitte.
•
--verbose / -v
Augmente le niveau de verbosité des messages de diagnostic imprimés sur la sortie d'erreur standard. Pour chaque opération Nix, les informations imprimées sur la sortie standard sont bien définies ; toutes les informations de diagnostic sont imprimées sur la sortie d'erreur standard, jamais sur la sortie standard.
Cette option peut être spécifiée de manière répétée. Actuellement, les niveaux de verbosité suivants existent :
•
0 « Erreurs uniquement »
N'imprime que les messages expliquant pourquoi l'invocation Nix a échoué.
•
1 « Informatif »
Imprime des messages *utiles* sur ce que fait Nix. C'est la valeur par défaut.
•
2 « Bavard »
Imprime des messages d'information supplémentaires.
•
3 « Très bavard »
Imprime encore plus de messages d'information.
•
4 « Débogage »
Imprime des informations de débogage.
•
5 « Vomit »
Imprime une quantité énorme d'informations de débogage.
•
--quiet
Diminue le niveau de verbosité des messages de diagnostic imprimés sur la sortie d'erreur standard. C'est l'option inverse de -v / --verbose.
Cette option peut être spécifiée de manière répétée. Voir la liste précédente des niveaux de verbosité.
•
--log-format format
Cette option peut être utilisée pour changer le format de sortie des journaux, avec format étant l'un des suivants :
•
raw
C'est le format brut, tel qu'il est généré par nix-build.
•
internal-json
Génère les journaux dans un format structuré.
Attention
Bien que le schéma lui-même soit relativement stable, le format des messages d'erreur (notamment du champ msg) peut changer entre les versions.
•
bar
N'affiche qu'une barre de progression pendant les constructions.
•
bar-with-logs
Affiche les journaux bruts, avec la barre de progression en bas.
•
--no-build-output / -Q
Par défaut, la sortie écrite par les constructeurs sur la sortie standard et la sortie d'erreur est renvoyée vers la sortie d'erreur standard de la commande Nix. Cette option supprime ce comportement. Notez que la sortie standard et l'erreur du constructeur sont toujours écrites dans un fichier journal dans prefix/nix/var/log/nix.
•
--max-jobs / -j nombre
Définit le nombre maximum de tâches de construction que Nix effectuera en parallèle au nombre spécifié. Spécifiez auto pour utiliser le nombre de processeurs du système. La valeur par défaut est spécifiée par le paramètre de configuration max-jobs, qui par défaut est 1. Une valeur plus élevée est utile sur les systèmes SMP ou pour exploiter la latence des E/S.
Le définir à 0 interdit la construction sur la machine locale, ce qui est utile lorsque vous souhaitez que les constructions se déroulent uniquement sur des constructeurs distants.
•
--cores
Définit la valeur de l'environnement NIX_BUILD_CORES

Par exemple, dans Nixpkgs, si l'attribut de dérivation enableParallelBuilding est défini sur true, le générateur passe l'option -jN à GNU Make. Il prend par défaut la valeur du paramètre de configuration cores, si elle est définie, ou 1 sinon. La valeur 0 signifie que le générateur doit utiliser tous les cœurs CPU disponibles sur le système.
•
--max-silent-time
Définit le nombre maximum de secondes pendant lesquelles un générateur peut rester sans produire de données sur la sortie standard ou l'erreur standard. La valeur par défaut est spécifiée par le paramètre de configuration max-silent-time. 0 signifie aucun délai d'attente.
•
--timeout
Définit le nombre maximum de secondes pendant lesquelles un générateur peut s'exécuter. La valeur par défaut est spécifiée par le paramètre de configuration timeout. 0 signifie aucun délai d'attente.
•
--keep-going / -k
Continuer en cas d'échec des builds, dans la mesure du possible. C'est-à-dire que si la construction d'une entrée d'une dérivation échoue, Nix construira quand même les autres entrées, mais pas la dérivation elle-même. Sans cette option, Nix s'arrête si une construction échoue (sauf pour les constructions de substituts), tuant éventuellement les constructions en cours (en cas de constructions parallèles ou distribuées).
•
--keep-failed / -K
Spécifie qu'en cas d'échec de construction, le répertoire temporaire (généralement dans /tmp) dans lequel la construction a lieu ne doit pas être supprimé. Le chemin du répertoire de construction est affiché comme message d'information.
•
--fallback
Chaque fois que Nix tente de construire une dérivation pour laquelle des substituts sont connus pour chaque chemin de sortie, mais que la réalisation des chemins de sortie via les substituts échoue, Nix se rabat sur la construction de la dérivation.
Le scénario le plus courant dans lequel cela est utile est lorsque nous avons enregistré des substituts pour effectuer une distribution binaire depuis, par exemple, un dépôt réseau. Si le dépôt est hors service, la réalisation de la dérivation échouera. Lorsque cette option est spécifiée, Nix construira la dérivation à la place. Ainsi, l'installation à partir de binaires se rabat sur l'installation à partir de sources. Cette option n'est pas par défaut car il n'est généralement pas souhaitable qu'un échec transitoire dans l'obtention des substituts entraîne une construction complète à partir des sources (avec la consommation de ressources associée).
•
--readonly-mode
Lorsque cette option est utilisée, aucune tentative n'est faite pour ouvrir la base de données Nix. La plupart des opérations Nix nécessitent un accès à la base de données, donc ces opérations échoueront.
•
--arg name value
Cette option est acceptée par nix-env, nix-instantiate, nix-shell et nix-build. Lors de l'évaluation des expressions Nix, l'évaluateur d'expressions essaiera automatiquement d'appeler les fonctions qu'il rencontre. Il peut appeler automatiquement les fonctions pour lesquelles tous les arguments ont une valeur par défaut (par exemple, { argName ? defaultValue }: ...).
Avec --arg, vous pouvez également appeler des fonctions qui ont des arguments sans valeur par défaut (ou remplacer une valeur par défaut). C'est-à-dire, si l'évaluateur rencontre une fonction avec un argument nommé name, il l'appellera avec la valeur value.
Par exemple, le fichier default.nix de premier niveau dans Nixpkgs est en fait une fonction :
{ # Le système (par exemple, `i686-linux') pour lequel construire les paquets.
system ? builtins.currentSystem
...
}: ...
Ainsi, si vous appelez cette expression Nix (par exemple, lorsque vous faites nix-env --install --attr pkgname), la fonction sera appelée automatiquement en utilisant la valeur builtins.currentSystem pour l'argument system. Vous pouvez la remplacer en utilisant --arg, par exemple, nix-env --install --attr pkgname --arg system \"i686-freebsd\". (Notez que puisque l'argument est une chaîne littérale Nix, vous devez échapper les guillemets.)
•
--argstr name value
Cette option est similaire à --arg, sauf que la valeur n'est pas une expression Nix mais une chaîne de caractères. Donc, au lieu de --arg system \"i686-linux\" (les guillemets extérieurs servent à satisfaire le shell) vous pouvez dire --argstr system i686-linux.
•
--attr / -A attrPath
Sélectionne un attribut de l'expression Nix de premier niveau évaluée. (nix-env, nix-instantiate, nix-build et nix-shell uniquement.) Le chemin d'attribut attrPath est une séquence de noms d'attributs séparés par des points. Par exemple, étant donnée une expression Nix de premier niveau e, le chemin d'attribut xorg.xorgserver entraînerait l'utilisation de l'expression e.xorg.xorgserver. Voir nix-env --install pour quelques exemples concrets.
En plus des noms d'attributs, vous pouvez également spécifier des indices de tableaux. Par exemple, le chemin d'attribut foo.3.bar sélectionne l'attribut bar du quatrième élément du tableau dans l'attribut foo de l'expression de premier niveau.
•
--expr / -E
Interprète les arguments de la ligne de commande comme une liste d'expressions Nix à analyser et évaluer, plutôt qu'une liste de noms de fichiers d'expressions Nix. (nix-instantiate, nix-build et nix-shell uniquement.)
Pour nix-shell, cette option est couramment utilisée pour vous fournir un shell dans lequel vous pouvez construire les paquets retournés par l'expression. Si vous souhaitez obtenir un shell contenant les paquets *construits* prêts à l'emploi, donnez votre expression à l'option de commodité nix-shell --packages à la place.
•
-I / --include path
Ajoute une entrée à la liste des chemins de recherche utilisés pour résoudre les chemins de recherche. Cette option peut être donnée plusieurs fois.
Les chemins ajoutés via -I ont la priorité sur le paramètre de configuration nix-path et la variable d'environnement NIX_PATH.
•
--option name value
Définit l'option de configuration Nix name à value. Ceci remplace les paramètres du fichier de configuration Nix (voir nix.conf5).
•
--repair
Corrige les chemins de magasin corrompus ou manquants en les redownloadant ou en les reconstruisant. Notez que cela est lent car cela nécessite de calculer un hachage cryptographique du contenu de chaque chemin dans la clôture de la construction. Notez également l'avertissement sous nix-store --repair-path.

Note

Voir man nix.conf pour remplacer les paramètres de configuration avec des indicateurs de ligne de commande.

Variables d'environnement courantes

La plupart des commandes Nix interprètent les variables d'environnement suivantes :

•
IN_NIX_SHELL
Indicateur qui indique si l'environnement actuel a été configuré par nix-shell. Il peut avoir les valeurs pure ou impure.
•
NIX_PATH
Une liste d'entrées de chemin de recherche séparées par des deux-points, utilisée pour résoudre les chemins de recherche.
Cette variable d'environnement remplace la valeur du paramètre de configuration nix-path.
Elle peut être étendue en utilisant l'option -I.
Exemple
$ export NIX_PATH=`/home/eel

MANUAL • nix-store-optimise(1)





NAME


nix-store ‑ optimise the Nix store







SYNOPSIS


nix-store --optimise







DESCRIPTION


The command nix-store --optimise ensures that all paths in the
    Nix store are registered using hard links. This saves disk space by ensuring
    that files with identical content are stored only once.


This command is usually run automatically by the Nix garbage
    collector, but you can invoke it manually.







ENVIRONMENT


The behaviour of Nix commands is influenced by environment variables.
    Some are specific to nix-store --optimise,
    but most are general.






NIX_PATH





    Controls the search path for Nix expressions. It is a list of paths separated
    by colons. Each path is either a name or a path. For example,
    nixpkgs=somewhere/nixpkgs.




If NIX_PATH is set to an empty string, resolving
    search paths will always fail.










Example




$ NIX_PATH= nix-instantiate --eval '<nixpkgs>'
error: file 'nixpkgs' was not found in the Nix search path (add it using $NIX_PATH or -I)






•


NIX_IGNORE_SYMLINK_STORE








Normally, the Nix store directory (typically
    /nix/store) is not allowed to contain any symlink
    components. This is to prevent “impure” builds. Builders
    sometimes “canonicalise” paths by resolving all symlink
    components. Thus, builds on different machines (with
    /nix/store resolving to different locations) could
    yield different results. This is generally not a problem, except when
    builds are deployed to machines where /nix/store
    resolves differently. If you are sure that you’re not going to do
    that, you can set NIX_IGNORE_SYMLINK_STORE to
    1.




Note that if you’re symlinking the Nix store so that you can put it
    on another file system than the root file system, on Linux you’re
    better off using bind mount points, e.g.,




$ mkdir /nix
$ mount -o bind /mnt/otherdisk/nix /nix






Consult the mount 8 manual page for details.






•


NIX_STORE_DIR








Overrides the location of the Nix store (default
    prefix/store).






•


NIX_DATA_DIR








Overrides the location of the Nix static data directory (default
    prefix/share).






•


NIX_LOG_DIR








Overrides the location of the Nix log directory (default
    prefix/var/log/nix).






•


NIX_STATE_DIR








Overrides the location of the Nix state directory (default
    prefix/var/nix).






•


NIX_CONF_DIR








Overrides the location of the system Nix configuration directory (default
    prefix/etc/nix).






•


NIX_CONFIG








Applies settings from Nix configuration from the environment. The content
    is treated as if it was read from a Nix configuration file. Settings are
    separated by the newline character.






•


NIX_USER_CONF_FILES








Overrides the location of the Nix user configuration files to load
  from.




The default are the locations according to the
    XDG
    Base Directory Specification. See the
    XDG Base Directories
    sub-section for details.




The variable is treated as a list separated by the
    : token.






•


TMPDIR








Use the specified directory to store temporary files. In particular, this
    includes temporary build directories; these can take up substantial
    amounts of disk space. The default is /tmp.






•


NIX_REMOTE








This variable should be set to daemon if you want
    to use the Nix daemon to execute Nix operations. This is necessary in
    multi-user Nix
    installations. If the Nix daemon’s Unix socket is at some
    non-standard path, this variable should be set to
    unix://path/to/socket. Otherwise, it should be
    left unset.






•


NIX_SHOW_STATS








If set to 1, Nix will print some evaluation
    statistics, such as the number of values allocated.






•


NIX_COUNT_CALLS








If set to 1, Nix will print how often functions
    were called during Nix expression evaluation. This is useful for profiling
    your Nix expressions.






•


GC_INITIAL_HEAP_SIZE








If Nix has been configured to use the Boehm garbage collector, this
    variable sets the initial size of the heap in bytes. It defaults to 384
    MiB. Setting it to a low value reduces memory consumption, but will
    increase runtime due to the overhead of garbage collection.
