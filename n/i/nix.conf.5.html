nix.conf(5) Manuel des formats de fichiers nix.conf(5)

Nom

nix.conf - Fichier de configuration Nix

Description

Nix prend en charge une variété de paramètres de configuration, qui sont lus depuis des fichiers de configuration ou pris comme arguments de ligne de commande.

Fichier de configuration

Par défaut, Nix lit les paramètres depuis les endroits suivants, dans cet ordre :

1.
Le fichier de configuration système sysconfdir/nix/nix.conf (c'est-à-dire /etc/nix/nix.conf sur la plupart des systèmes), ou $NIX_CONF_DIR/nix.conf si NIX_CONF_DIR est défini.
Les valeurs chargées dans ce fichier ne sont pas transmises au démon Nix. Le client suppose que le démon les a déjà chargées.
2.
Si NIX_USER_CONF_FILES est défini, alors chaque chemin séparé par : sera chargé dans l'ordre inverse.
Sinon, il recherchera des fichiers nix/nix.conf dans XDG_CONFIG_DIRS et XDG_CONFIG_HOME. Si non définis, XDG_CONFIG_DIRS sera par défaut /etc/xdg, et XDG_CONFIG_HOME sera par défaut $HOME/.config conformément à la Spécification XDG des répertoires de base.
3.
Si NIX_CONFIG est défini, son contenu est traité comme le contenu d'un fichier de configuration.

Format du fichier

Les fichiers de configuration consistent en des paires nom = valeur, une par ligne. Les commentaires commencent par un caractère #.

Exemple :

keep-outputs = true       # Pratique pour les développeurs
keep-derivations = true   # Idem

D'autres fichiers peuvent être inclus avec une ligne telle que include <chemin>, où <chemin> est interprété par rapport au fichier de configuration actuel. Un fichier manquant est une erreur à moins que !include ne soit utilisé à la place.

Un paramètre de configuration remplace généralement toute valeur précédente. Cependant, pour les paramètres qui prennent une liste d'éléments, vous pouvez préfixer le nom du paramètre par extra- pour *ajouter* à la valeur précédente.

Par exemple,

substituters = a b
extra-substituters = c d

définit le paramètre substituters à a b c d.

Les noms d'options inconnus ne sont pas une erreur et sont simplement ignorés avec un avertissement.

Options en ligne de commande

Les options de configuration peuvent être définies en ligne de commande, remplaçant les valeurs définies dans le fichier de configuration :

•
Chaque paramètre de configuration a une option de ligne de commande correspondante (par exemple, --max-jobs 16). Les paramètres booléens n'ont pas besoin d'argument, et peuvent être explicitement désactivés avec le préfixe no- (par exemple, --keep-failed et --no-keep-failed).
Les noms d'options inconnus sont des drapeaux invalides (sauf s'il existe déjà un drapeau avec ce nom) et sont rejetés avec une erreur.
•
L'option --option <nom> <valeur> est interprétée exactement comme un <nom> = <valeur> dans un fichier de configuration.
Les noms d'options inconnus sont ignorés avec un avertissement.

Le préfixe extra- est pris en charge pour les paramètres qui acceptent une liste d'éléments (par exemple, --extra-trusted users alice ou --option extra-trusted-users alice).

Paramètres entiers

Les paramètres qui ont un type entier prennent en charge les suffixes K, M, G et T. Ceux-ci entraînent la multiplication de la valeur spécifiée par 2^10, 2^20, 2^30 et 2^40, respectivement. Par exemple, --min-free 1M équivaut à --min-free 1048576.

build-users-group
Cette option spécifie le groupe Unix contenant les comptes utilisateurs de construction Nix. Dans les installations Nix multi-utilisateurs, les constructions ne doivent pas être effectuées par le compte Nix car cela permettrait aux utilisateurs de modifier arbitrairement le magasin Nix et la base de données en fournissant des constructeurs spécialement conçus ; et elles ne peuvent pas être effectuées par l'utilisateur appelant car cela lui permettrait d'influencer le résultat de la construction.
Par conséquent, si cette option n'est pas vide et spécifie un groupe valide, les constructions seront effectuées sous les comptes utilisateurs qui sont membres du groupe spécifié ici (tels que listés dans /etc/group). Ces comptes utilisateurs ne doivent pas être utilisés à d'autres fins !
Nix n'exécutera jamais deux constructions sous le même compte utilisateur simultanément. Ceci afin d'éviter une faille de sécurité évidente : un utilisateur malveillant écrivant une expression Nix qui modifie le résultat de construction d'une expression Nix légitime en cours de construction par un autre utilisateur. Il est donc bon d'avoir autant de comptes utilisateurs de construction Nix que possible. (Rappelez-vous : les UID sont peu coûteux.)
Les utilisateurs de construction doivent avoir la permission de créer des fichiers dans le magasin Nix, mais pas de les supprimer. Par conséquent, /nix/store doit être la propriété du compte Nix, son groupe doit être le groupe spécifié ici, et son mode doit être 1775.
Si le groupe d'utilisateurs de construction est vide, les constructions seront effectuées sous l'UID du processus Nix (c'est-à-dire, l'UID de l'appelant si NIX_REMOTE est vide, l'UID sous lequel le démon Nix s'exécute si NIX_REMOTE est daemon). Évidemment, cela ne doit pas être utilisé avec un démon Nix accessible à des clients non fiables.
Par défaut nixbld lors de l'exécution en tant que root, vide sinon.
Par défaut : spécifique à la machine

builders
Une liste de machines de construction séparée par des points-virgules ou des sauts de ligne.
En plus des façons habituelles de définir les options de configuration, la valeur peut être lue à partir d'un fichier en préfixant son chemin absolu par @.
Exemple
C'est le réglage par défaut :
builders = @/etc/nix/machines
Chaque spécification de machine se compose des éléments suivants, séparés par des espaces. Seul le premier élément est requis. Pour laisser un champ à sa valeur par défaut, définissez-le sur -.
1.
L'URI du magasin distant dans le format ssh://[username@]hostname.
Exemple
ssh://nix@mac
Pour des raisons de compatibilité ascendante, ssh:// peut être omis. Le nom d'hôte peut être un alias défini dans ~/.ssh/config.
2.
Une liste de types de systèmes Nix séparée par des virgules. Si omis, cela prend par défaut le type de plateforme locale.
Exemple
aarch64-darwin
Il est possible qu'une machine prenne en charge plusieurs types de plateformes.
Exemple
i686-linux,x86_64-linux
3.
Le fichier d'identité SSH à utiliser pour se connecter à la machine distante. Si omis, SSH utilisera ses identités habituelles.
Exemple
/home/user/.ssh/id_mac
4.
Le nombre maximum de constructions que Nix exécutera en parallèle sur la machine. Cela devrait généralement être égal au nombre de cœurs de processeur.
5.
Le « facteur de vitesse », indiquant la vitesse relative de la machine sous forme d'entier positif. S'il existe plusieurs machines du bon type, Nix préférera la plus rapide, en tenant compte de la charge.
6.
Une liste séparée par des virgules de fonctionnalités système prises en charge.
Une machine ne sera utilisée pour construire une dérivation que si toutes les fonctionnalités de l'attribut requiredSystemFeatures de la dérivation sont prises en charge par cette machine.
7.
Une liste séparée par des virgules de fonctionnalités système requises.
Une machine ne sera utilisée pour construire une dérivation que si toutes les fonctionnalités requises de la machine apparaissent dans l'attribut requiredSystemFeatures de la dérivation.
8.
La clé d'hôte publique (encodée en base64) de la machine distante. Si omis, SSH utilisera son fichier known_hosts habituel.
La valeur de ce champ peut être obtenue via base64 -w0.
Exemple
Plusieurs constructeurs spécifiés sur la ligne de commande :
--builders 'ssh://mac x86_64-darwin ; ssh://beastie x86_64-freebsd'
Exemple
Ceci spécifie plusieurs machines qui peuvent effectuer des constructions i686-linux :
nix@scratchy.labs.cs.uu.nl i686-linux /home/nix/.ssh/id_scratchy 8 1 kvm
nix@itchy.labs.cs.uu.nl    i686-linux /home/nix/.ssh/id_scratchy 8 2
nix@poochie.labs.cs.uu.nl  i686-linux /home/nix/.ssh/id_scratchy 1 2 kvm benchmark
Cependant, poochie ne construira que les dérivations qui ont l'attribut
requiredSystemFeatures = [ "benchmark" ];
ou
requiredSystemFeatures = [ "benchmark" "kvm" ];
itchy ne peut pas effectuer de constructions nécessitant kvm, mais scratchy prend en charge de telles constructions. Pour les constructions régulières, itchy sera préféré à scratchy car il a un facteur de vitesse plus élevé.
Pour que Nix utilise des substituts, l'utilisateur appelant doit figurer dans la liste trusted-users.
Note
Une machine de construction doit être accessible via SSH et avoir Nix installé. nix doit être disponible dans $PATH pour l'utilisateur se connectant via SSH.
Avertissement
Si vous construisez via le démon Nix (par défaut), le compte utilisateur du démon Nix sur la machine locale (c'est-à-dire, root) nécessite l'accès à un compte utilisateur sur la machine distante (pas nécessairement root).
Si vous ne pouvez pas ou ne souhaitez pas configurer root pour accéder à la machine distante, définissez store sur n'importe quel magasin local , par exemple en passant --store /tmp à la commande sur la machine locale.
Pour construire uniquement sur des machines distantes et désactiver les constructions locales, définissez max-jobs sur 0.
Si vous souhaitez que les machines distantes utilisent des substituts, définissez builders-use-substituters sur true.
Par défaut : spécifique à la machine

diff-hook
Chemin absolu vers un exécutable capable de comparer les résultats de construction. Le hook est exécuté si run-diff-hook est vrai, et que le résultat d'une construction est connu pour ne pas être le même. Ce programme n'est pas exécuté pour déterminer si deux résultats sont identiques.
Le hook de différence est exécuté par le même utilisateur et le même groupe qui ont exécuté la construction. Cependant, le hook de différence n'a pas d'accès en écriture au chemin du magasin qui vient d'être construit.
Le programme hook de différence reçoit trois paramètres :
1.
Un chemin vers les résultats de la construction précédente
2.
Un chemin vers les résultats de la construction actuelle
3.
Le chemin vers la dérivation de la construction
4.
Le chemin vers le répertoire temporaire de la construction. Ce répertoire existera uniquement si la construction a été exécutée avec --keep-failed.
La sortie stderr et stdout du hook de différence ne sera pas affichée à l'utilisateur. Au lieu de cela, elle sera imprimée dans le journal du daemon nix.
Lors de l'utilisation du daemon Nix, diff-hook doit être défini dans le fichier de configuration nix.conf, et ne peut pas être passé en ligne de commande.

Vous pouvez utiliser la syntaxe cible=source pour monter un chemin dans un emplacement différent dans le bac à sable ; par exemple, /bin=/nix-bin montera le chemin /nix-bin comme /bin à l'intérieur du bac à sable. Si source est suivi de ?, alors ce n'est pas une erreur si source n'existe pas ; par exemple, /dev/nvidiactl? spécifie que /dev/nvidiactl ne sera monté dans le bac à sable que s'il existe dans le système de fichiers de l'hôte.
Si la source se trouve dans le magasin Nix, sa fermeture sera également ajoutée au bac à sable.
Selon la manière dont Nix a été construit, la valeur par défaut de cette option peut être vide ou fournir /bin/sh comme montage (bind-mount) de bash.
