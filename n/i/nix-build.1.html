nix-build(1) Manuel des commandes générales nix-build(1)

Nom

nix-build - construire une expression Nix

Synopsis

nix-build [chemins…] [--arg nom valeur] [--argstr nom valeur] [{--attr | -A} cheminAttr] [--no-out-link] [--dry-run] [{--out-link | -o} lienSortie]

Désambiguïsation

Cette page de manuel décrit la commande nix-build, qui est distincte de nix build. Pour la documentation de cette dernière, exécutez nix build --help ou consultez man nix3-build.

Description

La commande nix-build construit les dérivations décrites par les expressions Nix dans chemins. Si la construction réussit, elle place un lien symbolique vers le résultat dans le répertoire courant. Le lien symbolique est nommé result. S'il y a plusieurs expressions Nix, ou si les expressions Nix s'évaluent en plusieurs dérivations, plusieurs liens symboliques numérotés séquentiellement sont créés (result, result-2, et ainsi de suite).

Si aucun chemin n'est spécifié, alors nix-build utilisera default.nix dans le répertoire courant, s'il existe.

Si un élément de chemins commence par http:// ou https://, il est interprété comme l'URL d'une archive tar qui sera téléchargée et décompressée dans un emplacement temporaire. L'archive doit inclure un seul répertoire de niveau supérieur contenant au moins un fichier nommé default.nix.

nix-build est essentiellement un wrapper autour de nix-instantiate (pour traduire une expression Nix de haut niveau en une dérivation de store de bas niveau) et nix-store --realise (pour construire la dérivation de store).

Avertissement

Le résultat de la construction est automatiquement enregistré comme une racine du collecteur de garbage de Nix. Cette racine disparaît automatiquement lorsque le lien symbolique result est supprimé ou renommé. Ne renommez donc pas le lien symbolique.

Options

Toutes les options non listées ici sont passées à nix-store --realise, à l'exception de --arg et --attr / -A qui sont passées à nix-instantiate.

•
--no-out-link
Ne crée pas de lien symbolique vers le chemin de sortie. Notez qu'en conséquence, la sortie ne devient pas une racine du collecteur de garbage et pourrait donc être supprimée par nix-store --gc.
•
--dry-run
Affiche les chemins du store qui seraient construits ou téléchargés.
•
--out-link / -o lienSortie
Change le nom du lien symbolique vers le chemin de sortie créé de result à lienSortie.

Codes de sortie spéciaux en cas d'échec de construction

Les codes de statut 1xx sont utilisés lorsque les constructions demandées ont échoué. Les codes suivants sont utilisés :

•
100 Échec de construction générique
Le processus du constructeur s'est terminé avec un code de sortie non nul.
•
101 Dépassement du délai de construction
La construction a été interrompue car elle ne s'est pas terminée dans le délai imparti timeout.
•
102 Discordance de hachage
La sortie de construction a été rejetée car elle ne correspond pas à l'attribut outputHash de la dérivation.
•
104 Pas déterministe
La construction a réussi en mode vérification mais la sortie résultante n'est pas binaire reproductible.

Avec le drapeau --keep-going, il est possible que plusieurs échecs se produisent. Dans ce cas, les codes de statut 1xx sont combinés en utilisant OU bit à bit.

0b1100100
     ^^^^
     |||`- délai dépassé
     ||`-- discordance de hachage de sortie
     |`--- échec de construction
     `---- non déterministe

Options communes

La plupart des commandes Nix acceptent les options de ligne de commande suivantes :

•
--help
Imprime un résumé de la syntaxe de la commande et quitte.
•
--version
Imprime le numéro de version de Nix sur la sortie standard et quitte.
•
--verbose / -v
Augmente le niveau de verbosité des messages de diagnostic imprimés sur la sortie d'erreur standard. Pour chaque opération Nix, les informations imprimées sur la sortie standard sont bien définies ; toute information de diagnostic est imprimée sur la sortie d'erreur standard, jamais sur la sortie standard.
Cette option peut être spécifiée plusieurs fois. Actuellement, les niveaux de verbosité suivants existent :
•
0 « Erreurs seulement »
Imprime uniquement les messages expliquant pourquoi l'invocation de Nix a échoué.
•
1 « Informatif »
Imprime des messages *utiles* sur ce que Nix fait. C'est le comportement par défaut.
•
2 « Bavard »
Imprime des messages informatifs supplémentaires.
•
3 « Très bavard »
Imprime encore plus de messages informatifs.
•
4 « Debug »
Imprime des informations de débogage.
•
5 « Vomit »
Imprime une quantité massive d'informations de débogage.
•
--quiet
Diminue le niveau de verbosité des messages de diagnostic imprimés sur la sortie d'erreur standard. C'est l'option inverse de -v / --verbose.
Cette option peut être spécifiée plusieurs fois. Voir la liste précédente des niveaux de verbosité.
•
--log-format
format
Cette option permet de modifier la sortie du format des logs, format étant l'une des options suivantes :
•
raw
Ceci est le format brut, tel que produit par nix-build.
•
internal-json
Produit les logs dans un format structuré.
Attention
Bien que le schéma lui-même soit relativement stable, le format des messages d'erreur (notamment du champ msg) peut changer entre les versions.
•
bar
Affiche uniquement une barre de progression pendant les compilations.
•
bar-with-logs
Affiche les logs bruts, avec la barre de progression en bas.
•
--no-build-output / -Q
Par défaut, la sortie écrite par les builders sur la sortie standard et l'erreur standard est renvoyée sur la sortie d'erreur de la commande Nix. Cette option supprime ce comportement. Notez que la sortie standard et l'erreur standard du builder sont toujours écrites dans un fichier de log dans prefix/nix/var/log/nix.
•
--max-jobs / -j nombre
Définit le nombre maximum de jobs de compilation que Nix effectuera en parallèle au nombre spécifié. Spécifiez auto pour utiliser le nombre de cœurs du système. La valeur par défaut est définie par le paramètre de configuration max-jobs, qui est lui-même par défaut à 1. Une valeur plus élevée est utile sur les systèmes SMP ou pour exploiter la latence d'E/S.
La définir à 0 désactive la compilation sur la machine locale, ce qui est utile lorsque vous souhaitez que les compilations se déroulent uniquement sur des builders distants.
•
--cores
Définit la valeur de la variable d'environnement NIX_BUILD_CORES dans l'invocation des builders. Les builders peuvent utiliser cette variable à leur discrétion pour contrôler le parallélisme maximal. Par exemple, dans Nixpkgs, si l'attribut de dérivation enableParallelBuilding est défini à true, le builder passe le drapeau -jN à GNU Make. Il est par défaut à la valeur du paramètre de configuration cores, s'il est défini, ou à 1 sinon. La valeur 0 signifie que le builder doit utiliser tous les cœurs CPU disponibles dans le système.
•
--max-silent-time
Définit le nombre maximum de secondes pendant lesquelles un builder peut rester sans produire de données sur la sortie standard ou l'erreur standard. La valeur par défaut est définie par le paramètre de configuration max-silent-time. 0 signifie pas de délai d'attente.
•
--timeout
Définit le nombre maximum de secondes pendant lesquelles un builder peut s'exécuter. La valeur par défaut est définie par le paramètre de configuration timeout. 0 signifie pas de délai d'attente.
•
--keep-going / -k
Continuer en cas d'échecs de compilation, dans la mesure du possible. C'est-à-dire, si la compilation d'une entrée d'une dérivation échoue, Nix compilera toujours les autres entrées, mais pas la dérivation elle-même. Sans cette option, Nix s'arrête si une compilation échoue (sauf pour les substitutions), tuant éventuellement les compilations en cours (en cas de compilations parallèles ou distribuées).
•
--keep-failed / -K
Spécifie qu'en cas d'échec de compilation, le répertoire temporaire (généralement dans /tmp) dans lequel la compilation a lieu ne doit pas être supprimé. Le chemin du répertoire de compilation est affiché comme un message d'information.
•
--fallback
Chaque fois que Nix tente de compiler une dérivation pour laquelle des substituts sont connus pour chaque chemin de sortie, mais que la réalisation des chemins de sortie via les substituts échoue, il se rabat sur la compilation de la dérivation.
Le scénario le plus courant dans lequel ceci est utile est lorsque nous avons enregistré des substituts pour effectuer une distribution binaire à partir, par exemple, d'un dépôt réseau. Si le dépôt est en panne, la réalisation de la dérivation échouera. Lorsque cette option est spécifiée, Nix compilera la dérivation à la place. Ainsi, l'installation à partir de binaires se rabat sur l'installation à partir des sources. Cette option n'est pas la valeur par défaut car il n'est généralement pas souhaitable qu'un échec transitoire dans l'obtention des substituts conduise à une compilation complète à partir des sources (avec la consommation de ressources associée).
•
--readonly-mode
Lorsque cette option est utilisée, aucune tentative n'est faite pour ouvrir la base de données Nix. La plupart des opérations Nix nécessitent un accès à la base de données, donc ces opérations échoueront.
•
--arg nom valeur
Cette option est acceptée par nix-env, nix-instantiate, nix-shell et nix-build. Lors de l'évaluation des expressions Nix, l'évaluateur d'expressions essaiera automatiquement d'appeler les fonctions qu'il rencontre. Il peut appeler automatiquement les fonctions pour lesquelles tous les arguments ont une valeur par défaut (par exemple, { argName ? defaultValue }: ...).
Avec --arg, vous pouvez également appeler des fonctions qui ont des arguments sans valeur par défaut (ou remplacer une valeur par défaut). C'est-à-dire, si l'évaluateur rencontre une fonction avec un argument nommé nom, il l'appellera avec la valeur valeur.
Par exemple, le default.nix de niveau supérieur dans Nixpkgs est en réalité une fonction :
{ # Le système (par exemple, `i686-linux') pour lequel construire les paquets.
system ? builtins.currentSystem
...
}: ...
Ainsi, si vous appelez cette expression Nix (par exemple, lorsque vous faites nix-env --install --attr pkgname), la fonction sera appelée automatiquement en utilisant la valeur builtins.currentSystem pour l'argument system. Vous pouvez la remplacer en utilisant --arg, par exemple, nix-env --install --attr pkgname --arg system \"i686-freebsd\". (Notez que puisque l'argument est une chaîne de caractères littérale Nix, vous devez échapper les guillemets.)
•
--argstr nom valeur
Cette option est similaire à --arg, mais la valeur n'est pas une expression Nix mais une chaîne de caractères. Donc, au lieu de --arg system \"i686-linux\" (les guillemets extérieurs servent à maintenir la coque heureuse), vous pouvez dire --argstr system i686-linux.
•
--attr / -A attrPath
Sélectionne un attribut de l'expression Nix de niveau supérieur en cours d'évaluation. (Uniquement nix-env, nix-instantiate, nix-build et nix-shell.) Le chemin d'attribut attrPath est une séquence de noms d'attributs séparés par des points. Par exemple, étant donné une expression Nix de niveau supérieur e, le chemin d'attribut xorg.xorgserver aurait pour effet d'utiliser l'expression e.xorg.xorgserver. Voir nix-env --install pour quelques exemples concrets.
En plus des noms d'attributs, vous pouvez également spécifier des indices de tableau. Par exemple, le chemin d'attribut foo.3.bar sélectionne l'attribut bar du quatrième élément du tableau dans l'attribut foo de l'expression de niveau supérieur.
•
--expr / -E
Interprète les arguments de la ligne de commande comme une liste d'expressions Nix à analyser et évaluer, plutôt que comme une liste de noms de fichiers d'expressions Nix. (Uniquement nix-instantiate, nix-build et nix-shell.)
Pour nix-shell, cette option est couramment utilisée pour vous donner un shell dans lequel vous pouvez construire les paquets retournés par l'expression. Si vous voulez obtenir un shell qui contient les paquets *construits* prêts à l'emploi, donnez votre expression à l'option de commodité nix-shell --packages à la place.
•
-I / --include chemin
Ajoute une entrée à la liste des chemins de recherche utilisés pour résoudre les chemins de recherche. Cette option peut
be given multiple times.
Les chemins ajoutés via -I ont la priorité sur le paramètre de configuration nix-path et la variable d'environnement NIX_PATH .
•
--option nom valeur
Définit l'option de configuration Nix nom à valeur. Ceci remplace les paramètres du fichier de configuration Nix (voir nix.conf5).
•
--repair
Réparer les chemins de magasin corrompus ou manquants en les re-téléchargeant ou en les reconstruisant. Notez que cela est lent car cela nécessite le calcul d'un hachage cryptographique du contenu de chaque chemin dans la fermeture de la construction. Notez également l'avertissement sous nix-store --repair-path.

Note

Voir man nix.conf pour remplacer les paramètres de configuration avec des indicateurs de ligne de commande.

Variables d'environnement courantes

La plupart des commandes Nix interprètent les variables d'environnement suivantes :

•
IN_NIX_SHELL
Indicateur qui signale si l'environnement actuel a été configuré par nix-shell. Il peut avoir les valeurs pure ou impure.
•
NIX_PATH
Une liste d'entrées de chemin de recherche séparées par deux-points utilisée pour résoudre les chemins de recherche.
Cette variable d'environnement remplace la valeur du paramètre de configuration nix-path .
Elle peut être étendue en utilisant l'indicateur -I .
Exemple
$ export NIX_PATH=`/home/eelco/Dev:nixos-config=/etc/nixos
Si NIX_PATH est défini sur une chaîne vide, la résolution des chemins de recherche échouera toujours.
Exemple
$ NIX_PATH= nix-instantiate --eval '<nixpkgs>'
error: file 'nixpkgs' was not found in the Nix search path (add it using $NIX_PATH or -I)
•
NIX_IGNORE_SYMLINK_STORE
Normalement, le répertoire du magasin Nix (typiquement /nix/store) ne doit pas contenir de composants de lien symbolique. Ceci est pour éviter les constructions « impures ». Les constructeurs « canonicalisent » parfois les chemins en résolvant tous les composants de lien symbolique. Ainsi, les constructions sur différentes machines (avec /nix/store résolvant vers des emplacements différents) pourraient donner des résultats différents. Ce n'est généralement pas un problème, sauf lorsque les constructions sont déployées sur des machines où /nix/store résout différemment. Si vous êtes sûr de ne pas faire cela, vous pouvez définir NIX_IGNORE_SYMLINK_STORE à 1.
Notez que si vous utilisez des liens symboliques vers le magasin Nix afin de le placer sur un autre système de fichiers que le système de fichiers racine, sous Linux, il est préférable d'utiliser des points de montage bind, par exemple :
$ mkdir /nix
$ mount -o bind /mnt/otherdisk/nix /nix
Consultez la page de manuel mount 8 pour les détails.
•
NIX_STORE_DIR
Remplace l'emplacement du magasin Nix (par défaut prefix/store).
•
NIX_DATA_DIR
Remplace l'emplacement du répertoire de données statiques Nix (par défaut prefix/share).
•
NIX_LOG_DIR
Remplace l'emplacement du répertoire de logs Nix (par défaut prefix/var/log/nix).
•
NIX_STATE_DIR
Remplace l'emplacement du répertoire d'état Nix (par défaut prefix/var/nix).
•
NIX_CONF_DIR
Remplace l'emplacement du répertoire de configuration Nix du système (par défaut prefix/etc/nix).
•
NIX_CONFIG
Applique les paramètres de la configuration Nix depuis l'environnement. Le contenu est traité comme s'il était lu à partir d'un fichier de configuration Nix. Les paramètres sont séparés par le caractère de nouvelle ligne.
•
NIX_USER_CONF_FILES
Remplace l'emplacement des fichiers de configuration utilisateur Nix à charger depuis.
Par défaut, ce sont les emplacements selon la spécification XDG des répertoires de base (XDG Base Directory Specification). Voir la sous-section Répertoires de base XDG pour les détails.
La variable est traitée comme une liste séparée par le jeton :.
•
TMPDIR
Utilise le répertoire spécifié pour stocker les fichiers temporaires. En particulier, cela inclut les répertoires de construction temporaires ; ceux-ci peuvent consommer une quantité substantielle d'espace disque. Par défaut, c'est /tmp.
•
NIX_REMOTE
Cette variable doit être définie sur daemon si vous voulez utiliser le démon Nix pour exécuter des opérations Nix. Ceci est nécessaire dans les installations Nix multi-utilisateurs. Si le socket Unix du démon Nix se trouve à un chemin non standard, cette variable doit être définie sur unix://path/to/socket. Sinon, elle doit être laissée non définie.
•
NIX_SHOW_STATS
Si définie sur 1, Nix affichera certaines statistiques d'évaluation, comme le nombre de valeurs allouées.
•
NIX_COUNT_CALLS
Si définie sur 1, Nix affichera combien de fois les fonctions ont été appelées pendant l'évaluation des expressions Nix. Ceci est utile pour profiler vos expressions Nix.
•
GC_INITIAL_HEAP_SIZE
Si Nix a été configuré pour utiliser le ramasse-miettes Boehm, cette variable définit la taille initiale du tas en octets. Sa valeur par défaut est de 384 MiB. La définir sur une valeur faible réduit la consommation mémoire, mais augmentera le temps d'exécution en raison de la surcharge du ramasse-miettes.

Répertoires de base XDG

Nix suit la spécification XDG des répertoires de base.

Pour des raisons de compatibilité ascendante, les commandes Nix ne suivront la norme que lorsque use-xdg-base-directories est activé. Les nouvelles commandes Nix (expérimentales) se conforment à la norme par défaut.

Les variables d'environnement suivantes sont utilisées pour déterminer les emplacements de divers fichiers d'état et de configuration :

  • [XDG_CONFIG_HOME]{#env-XDGCONFIGHOME} (par défaut ~/.config)
  • [XDG_STATE_HOME]{#env-XDGSTATEHOME} (par défaut ~/.local/state)
  • [XDG_CACHE_HOME]{#env-XDGCACHEHOME} (par défaut ~/.cache)

Exemples

$ nix-build '<nixpkgs>' --attr firefox
store derivation is /nix/store/qybprl8sz2lc...-firefox-1.5.0.7.drv
/nix/store/d18hyl92g30l...-firefox-1.5.0.7
$ ls -l result
lrwxrwxrwx  ...  result -> /nix/store/d18hyl92g30l...-firefox-1.5.0.7
$ ls ./result/bin/
firefox  firefox-config

Si une dérivation a plusieurs sorties, nix-build construira la sortie par défaut (la première). Vous pouvez également construire toutes les sorties :

$ nix-build '<nixpkgs>' --attr openssl.all

Cela créera un lien symbolique pour chaque sortie nommé result-nomdesortie. Le suffixe est omis si le nom de la sortie est out. Donc, si openssl a les sorties out, bin et man, nix-build créera les liens symboliques result, resul

t-bin et result-man. Il est également possible de construire une sortie spécifique :

$ nix-build '<nixpkgs>' --attr openssl.man

Ceci créera un lien symbolique result-man.

Construire une expression Nix donnée en ligne de commande :

$ nix-build --expr 'with import <nixpkgs> { }; runCommand "foo" { } "echo bar > $out"'
$ cat ./result
bar

Construire le paquet GNU Hello à partir de la dernière révision de la branche master de Nixpkgs :

$ nix-build https://github.com/NixOS/nixpkgs/archive/master.tar.gz --attr hello
