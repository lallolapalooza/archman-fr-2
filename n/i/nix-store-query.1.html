nix-store-query(1)

Paquet: nix

Licences: LGPL-2.1-only

nix-store --query(1) Manuel des commandes générales nix-store --query(1)

Nom

nix-store --query - affiche des informations sur les chemins du store

Synopsis

nix-store {--query | -q} {--outputs | --requisites | -R | --references | --referrers | --referrers-closure | --deriver | -d | --valid-derivers | --graph | --tree | --binding nom | -b nom | --hash | --size | --roots} [--use-output] [-u] [--force-realise] [-f] chemins…

Description

L'opération --query affiche diverses informations sur les chemins du store. Les requêtes sont décrites ci-dessous. Au plus une requête peut être spécifiée. La requête par défaut est --outputs.

Les chemins chemins peuvent également être des liens symboliques provenant de l'extérieur du store Nix vers le store Nix. Dans ce cas, la requête est appliquée à la cible du lien symbolique.

Options de requête communes

•
--use-output / -u
Pour chaque argument de la requête qui est une dérivation du store, applique la requête au chemin de sortie de la dérivation à la place.
•
--force-realise / -f
Réalise d'abord chaque argument de la requête (voir nix-store --realise).

Requêtes

•
--outputs
Affiche les chemins de sortie des dérivations du store chemins. Ce sont les chemins qui seront produits lorsque la dérivation sera construite.
•
--requisites / -R
Affiche la fermeture du chemin du store chemins.
Cette requête a une option :
•
--include-outputs Inclut également les chemins de sortie existants des dérivations du store, ainsi que leurs fermetures.
Cette requête peut être utilisée pour implémenter divers types de déploiements. Un déploiement source est obtenu en distribuant la fermeture d'une dérivation du store. Un déploiement binaire est obtenu en distribuant la fermeture d'un chemin de sortie. Un déploiement de cache (déploiement source/binaire combiné, incluant les binaires des dépendances de compilation uniquement) est obtenu en distribuant la fermeture d'une dérivation du store et en spécifiant l'option --include-outputs.
•
--references
Affiche l'ensemble des références des chemins du store chemins, c'est-à-dire leurs dépendances immédiates. (Pour toutes les dépendances, utilisez --requisites.)
•
--referrers
Affiche l'ensemble des référents des chemins du store chemins, c'est-à-dire les chemins du store actuellement existants dans le store Nix qui font référence à l'un des chemins. Notez que, contrairement aux références, l'ensemble des référents n'est pas constant ; il peut changer à mesure que des chemins du store sont ajoutés ou supprimés.
•
--referrers-closure
Affiche la fermeture de l'ensemble des chemins du store chemins sous la relation de référents ; c'est-à-dire tous les chemins du store actuellement dans le store Nix qui font référence directement ou indirectement à l'un des chemins. Ce sont tous les chemins actuellement dans le store Nix qui dépendent des chemins.
•
--deriver / -d
Affiche le dérivateur qui a été utilisé pour construire les chemins du store chemins. Si le chemin n'a pas de dérivateur (par exemple, s'il s'agit d'un fichier source), ou si le dérivateur n'est pas connu (par exemple, dans le cas d'un déploiement binaire uniquement), la chaîne unknown-deriver est affichée. Le dérivateur retourné n'est pas garanti d'exister dans le store local, par exemple lorsque les chemins ont été substitués à partir d'un cache binaire. Utilisez plutôt --valid-derivers pour obtenir uniquement des chemins valides.
•
--valid-derivers
Affiche un ensemble de fichiers de dérivation (.drv) qui sont censés produire lesdits chemins lorsqu'ils sont réalisés. Peut ne rien imprimer, par exemple pour les chemins source ou les chemins substitués à partir d'un cache binaire.
•
--graph
Affiche le graphe des références des chemins du store chemins au format de l'outil dot du package Graphviz d'AT&T. Ceci peut être utilisé pour visualiser les graphes de dépendances. Pour obtenir un graphe de dépendances de compilation, appliquez ceci à une dérivation du store. Pour obtenir un graphe de dépendances d'exécution, appliquez-le à un chemin de sortie.
•
--tree
Affiche le graphe des références des chemins du store chemins sous forme d'arbre ASCII imbriqué. Les références sont triées par taille de fermeture décroissante ; cela a tendance à aplatir l'arbre, le rendant plus lisible. La requête ne se récursive que dans un chemin du store lorsqu'il est rencontré pour la première fois ; cela empêche une explosion de la représentation arborescente du graphe.
•
--graphml
Affiche le graphe des références des chemins du store chemins au format de fichier GraphML. Ceci peut être utilisé pour visualiser les graphes de dépendances. Pour obtenir un graphe de dépendances de compilation, appliquez ceci à une dérivation du store. Pour obtenir un graphe de dépendances d'exécution, appliquez-le à un chemin de sortie.
•
--binding nom / -b nom
Affiche la valeur de l'attribut nom (c'est-à-dire une variable d'environnement) des dérivations du store chemins. C'est une erreur si une dérivation n'a pas l'attribut spécifié.
•
--hash
Affiche le hachage SHA-256 du contenu des chemins du store chemins (c'est-à-dire le hachage de la sortie de nix-store --dump sur les chemins donnés). Comme le hachage est stocké dans la base de données Nix, il s'agit d'une opération rapide.
•
--size
Affiche la taille en octets du contenu des chemins du store chemins — plus précisément, la taille de la sortie de nix-store --dump sur les chemins donnés. Notez que l'espace disque réel requis par les chemins du store peut être supérieur, en particulier sur les systèmes de fichiers avec de grandes tailles de cluster.
•

SYNOPSIS

nix-store [options] subcommand [args]

DESCRIPTION

The nix-store utility is the primary interface to the Nix store. It provides commands for managing store paths, such as adding them to the garbage collector roots, realising them from Nix expressions, and querying information about them.

Subcommands

•
add
Adds one or more store paths to the Nix store. This is usually done implicitly by nix-build or other commands.
•
delete
Deletes one or more store paths from the Nix store. This command is generally not needed because the garbage collector automatically removes unreferenced paths.
•
force-delete
Deletes one or more store paths from the Nix store, even if they are referenced.
•
query
Queries information about store paths. The query string can be any valid derivation attribute set.
•
realise
Realises one or more store paths from Nix expressions. This command is usually used implicitly by other Nix commands.
•
force-realise
Realises one or more store paths from Nix expressions, even if they already exist in the Nix store.
•
path-info
Prints information about one or more store paths, such as their size, references, and whether they are valid.
•
roots
Prints the garbage collector roots that point, directly or indirectly, at the store paths paths.

Options

The following options are allowed for all nix-store operations, but may not always have an effect.

•
--add-root path
Causes the result of a realisation (--realise and --force-realise) to be registered as a root of the garbage collector. path will be created as a symlink to the resulting store path. In addition, a uniquely named symlink to path will be created in /nix/var/nix/gcroots/auto/. For instance,
$ nix-store --add-root /home/eelco/bla/result --realise ...
$ ls -l /nix/var/nix/gcroots/auto
lrwxrwxrwx    1 ... 2005-03-13 21:10 dn54lcypm8f8... -> /home/eelco/bla/result
$ ls -l /home/eelco/bla/result
lrwxrwxrwx    1 ... 2005-03-13 21:10 /home/eelco/bla/result -> /nix/store/1r11343n6qd4...-f-spot-0.0.10
Thus, when /home/eelco/bla/result is removed, the GC root in the auto directory becomes a dangling symlink and will be ignored by the collector.
Warning
Note that it is not possible to move or rename GC roots, since the symlink in the auto directory will still point to the old location.
If there are multiple results, then multiple symlinks will be created by sequentially numbering symlinks beyond the first one (e.g., foo, foo-2, foo-3, and so on).

Options Communes

La plupart des commandes Nix acceptent les options de ligne de commande suivantes :

•
--help
Affiche un résumé de la syntaxe de la commande et quitte.
•
--version
Affiche le numéro de version de Nix sur la sortie standard et quitte.
•
--verbose / -v
Augmente le niveau de verbosité des messages de diagnostic imprimés sur l'erreur standard. Pour chaque opération Nix, les informations imprimées sur la sortie standard sont bien définies ; toute information de diagnostic est imprimée sur l'erreur standard, jamais sur la sortie standard.
Cette option peut être spécifiée de manière répétée. Actuellement, les niveaux de verbosité suivants existent :
•
0 « Erreurs uniquement »
Imprime uniquement les messages expliquant pourquoi l'invocation Nix a échoué.
•
1 « Informatif »
Imprime des messages *utiles* sur ce que fait Nix. C'est la valeur par défaut.
•
2 « Bavard »
Imprime davantage de messages informatifs.
•
3 « Loquace »
Imprime encore plus de messages informatifs.
•
4 « Débogage »
Imprime des informations de débogage.
•
5 « Vomit »
Imprime une quantité énorme d'informations de débogage.
•
--quiet
Diminue le niveau de verbosité des messages de diagnostic imprimés sur l'erreur standard. C'est l'option inverse de -v / --verbose.
Cette option peut être spécifiée de manière répétée. Voir la liste précédente des niveaux de verbosité.
•
--log-format format
Cette option peut être utilisée pour modifier le format de sortie du log, avec format étant l'un des éléments suivants :
•
raw
C'est le format brut, tel qu'il est produit par nix-build.
•
internal-json
Sort les logs dans un format structuré.
Avertissement
Bien que le schéma lui-même soit relativement stable, le format des messages d'erreur (notamment du champ msg) peut changer entre les versions.
•
bar
Affiche uniquement une barre de progression pendant les builds.
•
bar-with-logs
Affiche les logs bruts, avec la barre de progression en bas.
•
--no-build-output / -Q
Par défaut, la sortie écrite par les constructeurs sur la sortie standard et l'erreur standard est échoée sur l'erreur standard de la commande Nix. Cette option supprime ce comportement. Notez que la sortie standard et l'erreur du constructeur sont toujours écrites dans un fichier log dans prefix/nix/var/log/nix.
•
--max-jobs / -j nombre
Définit le nombre maximum de travaux de construction que Nix effectuera en parallèle au nombre spécifié. Spécifiez auto pour utiliser le nombre de cœurs CPU du système. La valeur par défaut est spécifiée par le paramètre de configuration max-jobs, qui est lui-même par défaut à 1. Une valeur plus élevée est utile sur les systèmes SMP ou pour exploiter la latence d'E/S.
La définir à 0 interdit la construction sur la machine locale, ce qui est utile lorsque vous souhaitez que les builds se produisent uniquement sur des constructeurs distants.
•
--cores
Définit la valeur de la variable d'environnement NIX_BUILD_CORES dans l'invocation des constructeurs. Les constructeurs peuvent utiliser cette variable à leur discrétion pour contrôler le niveau de parallélisme maximal. Par exemple, dans Nixpkgs, si l'attribut de dérivation enableParallelBuilding est défini sur true, le constructeur transmet l'option -jN à GNU Make. Il prend par défaut la valeur du paramètre de configuration cores, s'il est défini, ou 1 sinon. La valeur 0 signifie que le constructeur doit utiliser tous les cœurs CPU disponibles dans le système.
•
--max-silent-time
Définit le nombre maximum de secondes pendant lesquelles un constructeur peut rester sans produire aucune donnée sur la sortie standard ou l'erreur standard. La valeur par défaut est spécifiée par le paramètre de configuration max-silent-time. 0 signifie aucun délai d'attente.
•
--timeout
Définit le nombre maximum de secondes pendant lesquelles un constructeur peut s'exécuter. La valeur par défaut est spécifiée par le paramètre de configuration timeout. 0 signifie aucun délai d'attente.
•
--keep-going / -k
Continue en cas d'échec des constructions, dans la mesure du possible. C'est-à-dire, si la construction d'une entrée pour une dérivation échoue, Nix construira toujours les autres entrées, mais pas la dérivation elle-même. Sans cette option, Nix s'arrête si une construction échoue (sauf pour les constructions de substituts), tuant potentiellement les constructions en cours (en cas de constructions parallèles ou distribuées).
•
--keep-failed / -K
Spécifie qu'en cas d'échec de construction, le répertoire temporaire (généralement dans /tmp) dans lequel la construction a lieu ne doit pas être supprimé. Le chemin du répertoire de construction est imprimé comme un message informatif.
•
--fallback
Chaque fois que Nix tente de construire une dérivation pour laquelle des substituts sont connus pour chaque chemin de sortie, mais que la réalisation des chemins de sortie via les substituts échoue, Nix se rabat sur la construction de la dérivation.
Le scénario le plus courant pour lequel cela est utile est lorsque nous avons enregistré des substituts afin d'effectuer une distribution binaire à partir, par exemple, d'un dépôt réseau. Si le dépôt est indisponible, la réalisation de la dérivation échouera. Lorsque cette option est spécifiée, Nix construira la dérivation à la place. Ainsi, l'installation à partir de binaires se rabat sur l'installation à partir des sources. Cette option n'est pas la valeur par défaut car
Il est généralement indésirable qu'une défaillance transitoire dans l'obtention des substituts conduise à une compilation complète à partir des sources (avec la consommation de ressources associée).
•
--readonly-mode
Lorsque cette option est utilisée, aucune tentative n'est faite pour ouvrir la base de données Nix. La plupart des opérations Nix nécessitent un accès à la base de données, de sorte que ces opérations échoueront.
•
--arg nom valeur
Cette option est acceptée par nix-env, nix-instantiate, nix-shell et nix-build. Lors de l'évaluation des expressions Nix, l'évaluateur d'expressions tentera automatiquement d'appeler les fonctions qu'il rencontre. Il peut appeler automatiquement les fonctions pour lesquelles chaque argument a une valeur par défaut (par exemple, { argName ? defaultValue }: ...).
Avec --arg, vous pouvez également appeler des fonctions qui ont des arguments sans valeur par défaut (ou remplacer une valeur par défaut). C'est-à-dire, si l'évaluateur rencontre une fonction avec un argument nommé nom, il l'appellera avec la valeur valeur.
Par exemple, le default.nix de niveau supérieur dans Nixpkgs est en réalité une fonction :
{ # Le système (par exemple, `i686-linux') pour lequel construire les paquets.
system ? builtins.currentSystem
...
}: ...
Ainsi, si vous appelez cette expression Nix (par exemple, lorsque vous faites nix-env --install --attr pkgname), la fonction sera appelée automatiquement en utilisant la valeur builtins.currentSystem pour l'argument system. Vous pouvez la remplacer en utilisant --arg, par exemple, nix-env --install --attr pkgname --arg system \"i686-freebsd\". (Notez que puisque l'argument est une chaîne de caractères littérale Nix, vous devez échapper les guillemets.)
•
--argstr nom valeur
Cette option est similaire à --arg, sauf que la valeur n'est pas une expression Nix mais une chaîne de caractères. Donc, au lieu de --arg system \"i686-linux\" (les guillemets extérieurs servent à satisfaire le shell) vous pouvez dire --argstr system i686-linux.
•
--attr / -A attrPath
Sélectionne un attribut de l'expression Nix de niveau supérieur en cours d'évaluation. (nix-env, nix-instantiate, nix-build et nix-shell uniquement.) Le chemin d'attribut attrPath est une séquence de noms d'attributs séparés par des points. Par exemple, étant donné une expression Nix de niveau supérieur e, le chemin d'attribut xorg.xorgserver entraînerait l'utilisation de l'expression e.xorg.xorgserver. Voir nix-env --install pour des exemples concrets.
En plus des noms d'attributs, vous pouvez également spécifier des indices de tableau. Par exemple, le chemin d'attribut foo.3.bar sélectionne l'attribut bar du quatrième élément du tableau dans l'attribut foo de l'expression de niveau supérieur.
•
--expr / -E
Interprète les arguments de la ligne de commande comme une liste d'expressions Nix à analyser et à évaluer, plutôt que comme une liste de noms de fichiers d'expressions Nix. (nix-instantiate, nix-build et nix-shell uniquement.)
Pour nix-shell, cette option est couramment utilisée pour vous donner un shell dans lequel vous pouvez construire les paquets retournés par l'expression. Si vous souhaitez obtenir un shell contenant les paquets construits prêts à l'emploi, donnez votre expression à l'option de commodité nix-shell --packages à la place.
•
-I / --include chemin
Ajoute une entrée à la liste des chemins de recherche utilisés pour résoudre les chemins de recherche. Cette option peut être donnée plusieurs fois.
Les chemins ajoutés via -I ont la priorité sur la paramètre de configuration nix-path et la variable d'environnement NIX_PATH .
•
--option nom valeur
Définit l'option de configuration Nix nom à valeur. Ceci remplace les paramètres du fichier de configuration Nix (voir nix.conf5).
•
--repair
Réparer les chemins de magasin corrompus ou manquants en les redownloadant ou en les reconstruisant. Notez que cela est lent car cela nécessite de calculer un hash cryptographique du contenu de chaque chemin dans la fermeture de la construction. Notez également l'avertissement sous nix-store --repair-path.

Note

Voir man nix.conf pour remplacer les paramètres de configuration avec des indicateurs de ligne de commande.

Variables d'environnement communes

La plupart des commandes Nix interprètent les variables d'environnement suivantes :

•
IN_NIX_SHELL
Indicateur indiquant si l'environnement actuel a été configuré par nix-shell. Il peut avoir les valeurs pure ou impure.
•
NIX_PATH
Une liste séparée par des deux-points d'entrées de chemin de recherche utilisées pour résoudre les chemins de recherche.
Cette variable d'environnement remplace la valeur du paramètre de configuration nix-path .
Elle peut être étendue en utilisant l'option -I .
Exemple
$ export NIX_PATH=`/home/eelco/Dev:nixos-config=/etc/nixos
Si NIX_PATH est défini sur une chaîne vide, la résolution des chemins de recherche échouera toujours.
Exemple
$ NIX_PATH= nix-instantiate --eval '<nixpkgs>'
error: file 'nixpkgs' was not found in the Nix search path (add it using $NIX_PATH or -I)
•
NIX_IGNORE_SYMLINK_STORE
Normalement, le répertoire du magasin Nix (typiquement /nix/store) n'est pas autorisé à contenir de composants de lien symbolique. Ceci afin d'empêcher les constructions « impures ». Les constructeurs « canonicalisent » parfois les chemins en résolvant tous les composants de lien symbolique. Ainsi, les constructions sur différentes machines (avec /nix/store résolvant vers différents emplacements) pourraient donner des résultats différents. Ce n'est généralement pas un problème, sauf lorsque les constructions sont déployées sur des machines où /nix/store se résout différemment. Si vous êtes sûr que vous n'allez pas faire cela, vous pouvez définir NIX_IGNORE_SYMLINK_STORE à 1.
Notez que si vous utilisez des liens symboliques vers le magasin Nix afin de pouvoir le placer sur un autre système de fichiers que le système de fichiers racine, sous Linux, vous feriez mieux d'utiliser des points de montage bind, par exemple :
$ mkdir /nix
$ mount -o bind /mnt/otherdisk/nix /nix
Consultez la page de manuel de mount 8 pour les détails.
•
NIX_STORE_DIR
Remplace l'emplacement du magasin Nix (par défaut prefix/store).
•
NIX_DATA_DIR
Remplace l'emplacement du répertoire de données statiques de Nix (par défaut prefix/share).
•
NIX_LOG_DIR
Remplace l'emplacement du répertoire de journaux Nix (par défaut prefix/var/log/nix).
•
NIX_STATE_DIR
Remplace l'emplacement du répertoire d'état de Nix (par défaut prefix/var/nix).
•
NIX_CONF_DIR
Remplace l'emplacement du répertoire de configuration système Nix (par défaut prefix/etc/nix).
•
NIX_CONFIG
Applique les paramètres de la configuration Nix à partir de l'environnement. Le contenu est traité comme s'il avait été lu à partir d'un fichier de configuration Nix. Les paramètres sont séparés par le caractère de nouvelle ligne.
•
NIX_USER_CONF_FILES
Remplace l'emplacement des fichiers de configuration utilisateur Nix à charger à partir de.
Par défaut, ce sont les emplacements conformes à la XDG Base Directory Specification. Voir la référence des répertoires de base XDG pour plus de détails.
La variable est traitée comme une liste séparée par le jeton :.
•
TMPDIR
Utilise le répertoire spécifié pour stocker les fichiers temporaires. En particulier, cela inclut les répertoires de construction temporaires ; ceux-ci peuvent occuper des quantités substantielles d'espace disque. La valeur par défaut est /tmp.
•
NIX_REMOTE
Cette variable doit être définie sur daemon si vous souhaitez utiliser le démon Nix pour exécuter les opérations Nix. Ceci est nécessaire dans les installations Nix multi-utilisateurs. Si le socket Unix du démon Nix se trouve à un chemin non standard, cette variable doit être définie sur unix://chemin/vers/socket. Sinon, elle doit être laissée non définie.
•
NIX_SHOW_STATS
Si elle est définie sur 1, Nix affichera quelques statistiques d'évaluation, comme le nombre de valeurs allouées.
•
NIX_COUNT_CALLS
Si elle est définie sur 1, Nix affichera la fréquence d'appel des fonctions pendant l'évaluation des expressions Nix. Ceci est utile pour profiler vos expressions Nix.
•
GC_INITIAL_HEAP_SIZE
Si Nix a été configuré pour utiliser le garbage collector Boehm, cette variable définit la taille initiale du tas en octets. La valeur par défaut est de 384 Mio. La définir sur une valeur basse réduit la consommation de mémoire, mais augmentera le temps d'exécution en raison de la surcharge de la collecte de garbage.

Répertoires de base XDG

Nix suit la XDG Base Directory Specification.

Pour des raisons de compatibilité ascendante, les commandes Nix ne suivront la norme que lorsque use-xdg-base-directories sera activé. Les nouvelles commandes Nix (expérimentales) se conforment à la norme par défaut.

Les variables d'environnement suivantes sont utilisées pour déterminer les emplacements des divers fichiers d'état et de configuration :

  • [XDG_CONFIG_HOME]{#env-XDGCONFIGHOME} (par défaut ~/.config)
  • [XDG_STATE_HOME]{#env-XDGSTATEHOME} (par défaut ~/.local/state)
  • [XDG_CACHE_HOME]{#env-XDGCACHEHOME} (par défaut ~/.cache)

Exemples

Affiche la fermeture (dépendances d'exécution) du programme svn dans l'environnement utilisateur actuel :

$ nix-store --query --requisites $(which svn)
/nix/store/5mbglq5ldqld8sj57273aljwkfvj22mc-subversion-1.1.4
/nix/store/9lz9yc6zgmc0vlqmn2ipcpkjlmbi51vv-glibc-2.3.4
...

Affiche les dépendances de construction de svn :

$ nix-store --query --requisites $(nix-store --query --deriver $(which svn))
/nix/store/02iizgn86m42q905rddvg4ja975bk2i4-grep-2.5.1.tar.bz2.drv
/nix/store/07a2bzxmzwz5hp58nf03pahrv2ygwgs3-gcc-wrapper.sh
/nix/store/0ma7c9wsbaxahwwl04gbw3fcd806ski4-glibc-2.3.4.drv
... beaucoup d'autres chemins ...

La différence avec l'exemple précédent est que nous demandons la fermeture de la dérivation (-qd), et non la fermeture du chemin de sortie qui contient svn.

Affiche les dépendances de construction sous forme d'arbre :

$ nix-store --query --tree $(nix-store --query --deriver $(which svn))
/nix/store/7i5082kfb6yjbqdbiwdhhza0am2xvh6c-subversion-1.1.4.drv
+---/nix/store/d8afh10z72n8l1cr5w42366abiblgn54-builder.sh
+---/nix/store/fmzxmpjx2lh849ph0l36snfj9zdibw67-bash-3.0.drv
|   +---/nix/store/570hmhmx3v57605cqg9yfvvyh0nnb8k8-bash
|   +---/nix/store/p3srsbd8dx44v2pg6nbnszab5mcwx03v-builder.sh
...

Affiche tous les chemins qui dépendent de la même bibliothèque OpenSSL que svn :

$ nix-store --query --referrers $(nix-store --query --binding openssl $(nix-store --query --deriver $(which svn)))
/nix/store/23ny9l9wixx21632y2wi4p585qhva1q8-sylpheed-1.0.0
/nix/store/5mbglq5ldqld8sj57273aljwkfvj22mc-subversion-1.1.4

Affiche tous les chemins qui dépendent directement ou indirectement de la Glibc (bibliothèque C) utilisée par svn :

$ nix-store --query --referrers-closure $(ldd $(which svn) | grep /libc.so | awk '{print $3}')
/nix/store/034a6h4vpz9kds5r6kzb9lhh81mscw43-libgnomeprintui-2.8.2
/nix/store/15l3yi0d45prm7a82pcrknxdh6nzmxza-gawk-3.1.4
...

Notez que ldd est une commande qui affiche les bibliothèques dynamiques utilisées par un exécutable ELF.

Crée une image du graphe de dépendances d'exécution de l'environnement utilisateur actuel :

$ nix-store --query --graph ~/.nix-profile | dot -Tps > graph.ps
$ gv graph.ps
