nix-store --export(1) Manuel des commandes générales nix-store --export(1)

Nom

nix-store --export - exporter les chemins du store vers une Archive Nix

Synopsis

nix-store --export chemins…

Description

L'opération --export écrit une sérialisation des objets de store donnés vers la sortie standard dans un format qui peut être importé dans un autre store Nix avec nix-store --import.

Attention

Cette commande ne produit pas une clôture des chemins de store spécifiés. Essayer d'importer un objet de store qui fait référence à des chemins de store non disponibles dans le store Nix cible échouera.

Utilisez nix-store --query pour obtenir la clôture d'un chemin de store.

Cette commande est différente de nix-store --dump, qui produit une archive Nix qui ne contient pas l'ensemble des références d'un chemin de store donné.

Note

Pour un transfert efficace des clôtures vers des machines distantes via SSH, utilisez nix-copy-closure.

Options

Les options suivantes sont autorisées pour toutes les opérations nix-store, mais peuvent ne pas toujours avoir un effet.

•
--add-root chemin
Fait que le résultat d'une réalisation (--realise et --force-realise) soit enregistré comme une racine du collecteur de garbage. chemin sera créé comme un lien symbolique vers le chemin de store résultant. De plus, un lien symbolique nommé de manière unique vers chemin sera créé dans /nix/var/nix/gcroots/auto/. Par exemple,
$ nix-store --add-root /home/eelco/bla/result --realise ...
$ ls -l /nix/var/nix/gcroots/auto
lrwxrwxrwx    1 ... 2005-03-13 21:10 dn54lcypm8f8... -> /home/eelco/bla/result
$ ls -l /home/eelco/bla/result
lrwxrwxrwx    1 ... 2005-03-13 21:10 /home/eelco/bla/result -> /nix/store/1r11343n6qd4...-f-spot-0.0.10
Ainsi, lorsque /home/eelco/bla/result est supprimé, la racine GC du répertoire auto devient un lien symbolique brisé et sera ignoré par le collecteur.
Attention
Notez qu'il n'est pas possible de déplacer ou renommer les racines GC, car le lien symbolique dans le répertoire auto pointera toujours vers l'ancien emplacement.
S'il y a plusieurs résultats, plusieurs liens symboliques seront créés en numérotant séquentiellement les liens symboliques après le premier (par exemple, foo, foo-2, foo-3, et ainsi de suite).

Options communes

La plupart des commandes Nix acceptent les options de ligne de commande suivantes :

•
--help
Affiche un résumé de la syntaxe de la commande et quitte.
•
--version
Affiche la version de Nix sur la sortie standard et quitte.
•
--verbose / -v
Augmente le niveau de verbosité des messages de diagnostic imprimés sur la sortie d'erreur standard. Pour chaque opération Nix, les informations imprimées sur la sortie standard sont bien définies ; toute information de diagnostic est imprimée sur la sortie d'erreur standard, jamais sur la sortie standard.
Cette option peut être spécifiée de manière répétée. Actuellement, les niveaux de verbosité suivants existent :
•
0 « Erreurs uniquement »
N'imprime que les messages expliquant pourquoi l'invocation Nix a échoué.
•
1 « Informatif »
Imprime des messages utiles sur ce que fait Nix. C'est le comportement par défaut.
•
2 « Bavard »
Imprime davantage de messages informatifs.
•
3 « Très bavard »
Imprime encore plus de messages informatifs.
•
4 « Débogage »
Imprime des informations de débogage.
•
5 « Vomit »
Imprime une quantité énorme d'informations de débogage.
•
--quiet
Diminue le niveau de verbosité des messages de diagnostic imprimés sur la sortie d'erreur standard. C'est l'option inverse de -v / --verbose.
Cette option peut être spécifiée de manière répétée. Voir la liste précédente des niveaux de verbosité.
•
--log-format format
Cette option peut être utilisée pour modifier le format de sortie des journaux, format étant l'une des options suivantes :
•
raw
C'est le format brut, tel que produit par nix-build.
•
internal-json
Produit les journaux dans un format structuré.
Attention
Bien que le schéma lui-même soit relativement stable, le format des messages d'erreur (notamment du champ msg) peut changer entre les versions.
•
bar
Affiche uniquement une barre de progression pendant les constructions.
•
bar-with-logs
Affiche les journaux bruts, avec la barre de progression en bas.
•
--no-build-output / -Q
Par défaut, la sortie écrite par les constructeurs vers la sortie standard et l'erreur standard est renvoyée vers la sortie d'erreur standard de la commande Nix. Cette option supprime ce comportement. Notez que la sortie standard et l'erreur de la sortie du constructeur sont toujours écrites dans un fichier journal dans prefix/nix/var/log/nix.
•
--max-jobs / -j nombre
Définit le nombre maximal de tâches de construction que Nix effectuera en parallèle à

le nombre spécifié. Spécifiez `auto` pour utiliser le nombre de CPU du système. La valeur par défaut est spécifiée par le paramètre de configuration `max-jobs`, qui est lui-même par défaut à `1`. Une valeur plus élevée est utile sur les systèmes SMP ou pour exploiter la latence d'E/S.
La définir à `0` interdit la construction sur la machine locale, ce qui est utile lorsque vous souhaitez que les constructions aient lieu uniquement sur des constructeurs distants.
•
--cores
Définit la valeur de la variable d'environnement `NIX_BUILD_CORES` lors de l'invocation des constructeurs. Les constructeurs peuvent utiliser cette variable à leur discrétion pour contrôler le niveau de parallélisme maximal. Par exemple, dans Nixpkgs, si l'attribut de dérivation `enableParallelBuilding` est défini à `true`, le constructeur passe le drapeau `-jN` à GNU Make. Il est par défaut à la valeur du paramètre de configuration `cores`, s'il est défini, ou à `1` sinon. La valeur `0` signifie que le constructeur doit utiliser tous les cœurs CPU disponibles dans le système.
•
--max-silent-time
Définit le nombre maximum de secondes pendant lesquelles un constructeur peut s'exécuter sans produire de données sur la sortie standard ou l'erreur standard. La valeur par défaut est spécifiée par le paramètre de configuration `max-silent-time`. `0` signifie aucun délai d'attente.
•
--timeout
Définit le nombre maximum de secondes pendant lesquelles un constructeur peut s'exécuter. La valeur par défaut est spécifiée par le paramètre de configuration `timeout`. `0` signifie aucun délai d'attente.
•
--keep-going / -k
Continuer en cas d'échec des constructions, dans la mesure du possible. C'est-à-dire, si la construction d'une entrée d'une dérivation échoue, Nix construira toujours les autres entrées, mais pas la dérivation elle-même. Sans cette option, Nix s'arrête si une construction échoue (sauf pour les constructions de substituts), tuant potentiellement les constructions en cours (en cas de constructions parallèles ou distribuées).
•
--keep-failed / -K
Spécifie qu'en cas d'échec de construction, le répertoire temporaire (généralement dans `/tmp`) dans lequel la construction a lieu ne doit pas être supprimé. Le chemin du répertoire de construction est affiché comme un message informatif.
•
--fallback
Chaque fois que Nix tente de construire une dérivation pour laquelle des substituts sont connus pour chaque chemin de sortie, mais que la réalisation des chemins de sortie via les substituts échoue, il se rabat sur la construction de la dérivation.
Le scénario le plus courant où cela est utile est lorsque nous avons enregistré des substituts afin d'effectuer une distribution binaire depuis, par exemple, un dépôt réseau. Si le dépôt est indisponible, la réalisation de la dérivation échouera. Lorsque cette option est spécifiée, Nix construira la dérivation à la place. Ainsi, l'installation à partir de binaires se rabat sur l'installation à partir de la source. Cette option n'est pas la valeur par défaut car il n'est généralement pas souhaitable qu'un échec transitoire dans l'obtention des substituts conduise à une construction complète à partir de la source (avec la consommation de ressources associée).
•
--readonly-mode
Lorsque cette option est utilisée, aucune tentative n'est faite pour ouvrir la base de données Nix. La plupart des opérations Nix nécessitent un accès à la base de données, donc ces opérations échoueront.
•
--arg nom valeur
Cette option est acceptée par `nix-env`, `nix-instantiate`, `nix-shell` et `nix-build`. Lors de l'évaluation des expressions Nix, l'évaluateur d'expressions tentera automatiquement d'appeler les fonctions qu'il rencontre. Il peut appeler automatiquement les fonctions pour lesquelles tous les arguments ont une valeur par défaut (par exemple, `{ argName ? defaultValue }: ...`).
Avec `--arg`, vous pouvez également appeler des fonctions qui ont des arguments sans valeur par défaut (ou outrepasser une valeur par défaut). C'est-à-dire, si l'évaluateur rencontre une fonction avec un argument nommé nom, il l'appellera avec la valeur valeur.
Par exemple, le `default.nix` de niveau supérieur dans Nixpkgs est en fait une fonction :
{ # Le système (par exemple, `i686-linux') pour lequel construire les paquets.
system ? builtins.currentSystem
...
}: ...
Ainsi, si vous appelez cette expression Nix (par exemple, lorsque vous faites `nix-env --install --attr pkgname`), la fonction sera appelée automatiquement en utilisant la valeur builtins.currentSystem pour l'argument `system`. Vous pouvez outrepasser cela en utilisant `--arg`, par exemple, `nix-env --install --attr pkgname --arg system \"i686-freebsd\"`. (Notez que comme l'argument est une chaîne littérale Nix, vous devez échapper les guillemets.)
•
--argstr nom valeur
Cette option est comme `--arg`, sauf que la valeur n'est pas une expression Nix mais une chaîne. Donc, au lieu de `--arg system \"i686-linux\"` (les guillemets extérieurs servent à maintenir le shell heureux), vous pouvez dire `--argstr system i686-linux`.
•
--attr / -A cheminAttr
Sélectionne un attribut de l'expression Nix de niveau supérieur évaluée. (`nix-env`, `nix-instantiate`, `nix-build` et `nix-shell` seulement.) Le chemin d'attribut cheminAttr est une séquence de noms d'attributs séparés par des points. Par exemple, étant donné une expression Nix de niveau supérieur e, le chemin d'attribut `xorg.xorgserver` entraînerait l'utilisation de l'expression `e.xorg.xorgserver`. Voir nix-env --install pour des exemples concrets.
En plus des noms d'attributs, vous pouvez également spécifier des indices de tableau. Par exemple, le chemin d'attribut `foo.3.bar` sélectionne l'attribut `bar` du quatrième élément du tableau dans l'attribut `foo` de l'expression de niveau supérieur.
•
--expr / -E
Interprète les arguments de la ligne de commande comme une liste d'expressions Nix à analyser et évaluer, plutôt que comme une liste de noms de fichiers d'expressions Nix. (`nix-instantiate`, `nix-build` et `nix-shell` seulement.)
Pour `nix-shell`, cette option est couramment utilisée pour vous donner un shell dans lequel vous pouvez construire les paquets retournés par l'expression. Si vous voulez obtenir un shell contenant les paquets *construits* prêts à l'emploi, donnez votre expression au drapeau de commodité `nix-shell --packages` à la place.
•
-I / --include chemin
Ajoute une entrée à la liste des chemins de recherche utilisés pour résoudre les chemins de recherche. Cette option peut être donnée plusieurs fois.
Les chemins ajoutés via `-I` ont la priorité sur le paramètre de configuration nix-path et la variable d'environnement NIX_PATH.
•
--option nom valeur
Définit l'option de configuration Nix nom à valeur. Ceci remplace les paramètres du fichier de configuration Nix (voir nix.conf5).
•
--repair
Corrige les chemins de magasin corrompus ou manquants en les redownloadant ou en les reconstruisant. Notez que cela est lent car cela nécessite le calcul d'un hachage cryptographique du contenu de chaque chemin dans la fermeture de la construction. Notez également l'avertissement sous `nix-store --repair-path`.

Note

Voir man nix.conf pour outrepasser les paramètres de configuration avec des drapeaux de ligne de commande.

NIX_PATH

A colon-separated list of search path entries used to resolve lookup paths.
This environment variable overrides the value of the nix-path configuration setting.
It can be extended using the -I option.
Example
$ export NIX_PATH=`/home/eelco/Dev:nixos-config=/etc/nixos
If NIX_PATH is set to an empty string, resolving search paths will always fail.
Example
$ NIX_PATH= nix-instantiate --eval '<nixpkgs>'
error: file 'nixpkgs' was not found in the Nix search path (add it using $NIX_PATH or -I)
•
NIX_IGNORE_SYMLINK_STORE
Normally, the Nix store directory (typically /nix/store) is not allowed to contain any symlink components. This is to prevent “impure” builds. Builders sometimes “canonicalise” paths by resolving all symlink components. Thus, builds on different machines (with /nix/store resolving to different locations) could yield different results. This is generally not a problem, except when builds are deployed to machines where /nix/store resolves differently. If you are sure that you’re not going to do that, you can set NIX_IGNORE_SYMLINK_STORE to 1.
Note that if you’re symlinking the Nix store so that you can put it on another file system than the root file system, on Linux you’re better off using bind mount points, e.g.,
$ mkdir /nix
$ mount -o bind /mnt/otherdisk/nix /nix
Consult the mount 8 manual page for details.

This variable should be set to daemon if you want to use the Nix daemon to execute Nix operations. This is necessary in multi-user Nix installations. If the Nix daemon’s Unix socket is at some non-standard path, this variable should be set to unix://path/to/socket. Otherwise, it should be left unset.

NIX_SHOW_STATS
If set to 1, Nix will print some evaluation statistics, such as the number of values allocated.
•
NIX_COUNT_CALLS
If set to 1, Nix will print how often functions were called during Nix expression evaluation. This is useful for profiling your Nix expressions.

GC_INITIAL_HEAP_SIZE
If Nix has been configured to use the Boehm garbage collector, this variable sets the initial size of the heap in bytes. It defaults to 384 MiB. Setting it to a low value reduces memory consumption, but will increase runtime due to the overhead of garbage collection.

XDG Base Directories

Nix follows the XDG Base Directory Specification.

For backwards compatibility, Nix commands will follow the standard only when use-xdg-base-directories is enabled. New Nix commands (experimental) conform to the standard by default.

The following environment variables are used to determine locations of various state and configuration files:

  • [XDG_CONFIG_HOME]{#env-XDGCONFIGHOME} (default ~/.config)
  • [XDG_STATE_HOME]{#env-XDGSTATEHOME} (default ~/.local/state)
  • [XDG_CACHE_HOME]{#env-XDGCACHEHOME} (default ~/.cache)

Examples

Example

Deploy GNU Hello to an airgapped machine via USB stick.

Write the closure to the block device on a machine with internet connection:

[alice@itchy]$ storePath=$(nix-build '<nixpkgs>' -I nixpkgs=channel:nixpkgs-unstable -A hello --no-out-link)
[alice@itchy]$ nix-store --export $(nix-store --query --requisites $storePath) | sudo dd of=/dev/usb

Read the closure from the block device on the machine without internet connection:

[bob@scratchy]$ hello=$(sudo dd if=/dev/usb | nix-store --import | tail -1)
[bob@scratchy]$ $hello/bin/hello
Hello, world!
