nix-env --install(1) Manuel des commandes générales nix-env --install(1)

Nom

nix-env --install - ajouter des paquets à l'environnement utilisateur

Synopsis

nix-env {--install | -i} arguments… [{--prebuilt-only | -b}] [{--attr | -A}] [--from-expression] [-E] [--from-profile chemin] [--preserve-installed | -P] [--remove-all | -r]

Description

L'opération --install crée un nouvel environnement utilisateur. Elle est basée sur la génération actuelle du profil actif, à laquelle un ensemble de chemins de magasin décrits par arguments est ajouté.

Les arguments arguments correspondent aux chemins de magasin de plusieurs manières possibles :

•
Par défaut, arguments est un ensemble de noms de dérivations qui désignent des dérivations dans l'expression Nix par défaut. Celles-ci sont réalisées, et les chemins de sortie résultants sont installés. Les dérivations actuellement installées dont le nom est identique au nom d'une dérivation en cours d'ajout sont supprimées, sauf si l'option --preserve-installed est spécifiée.
S'il existe plusieurs dérivations correspondant à un nom dans arguments et portant le même nom (par exemple, gcc-3.3.6 et gcc-4.1.1), alors la dérivation avec la priorité la plus élevée est utilisée. Une dérivation peut définir une priorité en déclarant l'attribut meta.priority. Cet attribut doit être un nombre, une valeur plus élevée indiquant une priorité plus faible. La priorité par défaut est 5.
S'il existe plusieurs dérivations correspondantes avec la même priorité, alors la dérivation avec la version la plus élevée sera installée.
Vous pouvez forcer l'installation de plusieurs dérivations portant le même nom en spécifiant les versions de manière précise. Par exemple, nix-env --install gcc-3.3.6 gcc-4.1.1 installera les deux versions de GCC (et provoquera probablement un conflit dans l'environnement utilisateur !).
•
Si --attr / -A est spécifié, les arguments sont des chemins d'attributs qui sélectionnent des attributs dans l'expression Nix par défaut. C'est plus rapide que d'utiliser les noms de dérivations et non ambigu. Affichez les chemins d'attributs des paquets disponibles avec nix-env --query :
nix-env --query --available --attr-path
  • Si --from-profile chemin est donné, arguments est un ensemble de noms désignant des chemins de magasin installés dans le profil chemin. C'est un moyen simple de copier des éléments d'environnement utilisateur d'un profil à un autre.
  • Si --from-expression est donné, arguments sont des fonctions du langage Nix qui sont appelées avec l'expression Nix par défaut comme unique argument. Les dérivations retournées par ces appels de fonction sont installées. Cela permet de spécifier les dérivations de manière non ambiguë, ce qui est nécessaire s'il existe plusieurs dérivations portant le même nom.
  • Si arguments sont des dérivations de magasin, elles sont alors réalisées, et les chemins de sortie résultants sont installés.
  • Si arguments sont des chemins de magasin qui ne sont pas des dérivations de magasin, ils sont alors réalisés et installés.
  • Par défaut, toutes les sorties sont installées pour chaque dérivation. Ceci peut être outrepassé en ajoutant un attribut meta.outputsToInstall à la dérivation, listant un sous-ensemble des noms de sorties.
Exemple :
Le fichier example.nix définit une dérivation avec deux sorties foo et bar, contenant chacune un fichier.
# example.nix
let
pkgs = import <nixpkgs> {};
command = ''
  ${pkgs.coreutils}/bin/mkdir -p $foo $bar
  echo foo > $foo/foo-file
  echo bar > $bar/bar-file
'';
in
derivation {
name = "example";
builder = "${pkgs.bash}/bin/bash";
args = [ "-c" command ];
outputs = [ "foo" "bar" ];
system = builtins.currentSystem;
}
Installer à partir de cette expression Nix rendra les fichiers des deux sorties visibles dans le profil actuel.
$ nix-env --install --file example.nix
installing 'example'
$ ls ~/.nix-profile
foo-file
bar-file
manifest.nix
Ajouter meta.outputsToInstall à cette dérivation permettra à nix-env d'installer uniquement les fichiers des sorties spécifiées.
# example-outputs.nix
import ./example.nix // { meta.outputsToInstall = [ "bar" ]; }
$ nix-env --install --file example-outputs.nix
installing 'example'
$ ls ~/.nix-profile
bar-file
manifest.nix

Options

•
--prebuilt-only / -b
Utiliser uniquement les dérivations pour lesquelles un substitut est enregistré, c'est-à-dire qu'il existe un binaire pré-compilé disponible qui peut être téléchargé au lieu de construire la dérivation. Ainsi, aucun paquet ne sera construit à partir de la source.
•
--preserve-installed / -P
Ne pas supprimer les dérivations dont le nom correspond à l'une des dérivations en cours d'installation. Habituellement, essayer d'avoir deux versions du même paquet installées dans la même génération d'un profil entraînera une erreur lors de la construction de la génération, en raison de conflits de noms de fichiers entre les deux versions. Cependant, ce n'est pas le cas pour tous les paquets.
•
--remove-all / -r
Supprimer d'abord tous les paquets précédemment installés. Cela équivaut à exécuter nix-env --uninstall '.*' d'abord, sauf que tout se déroule dans une seule transaction.

Options

Les options suivantes sont autorisées pour toutes les opérations nix-env, mais peuvent ne pas avoir d'effet dans tous les cas.

•
--file / -f chemin
Spécifie l'expression Nix (désignée ci-dessous comme l'expression Nix active) utilisée par les opérations --install, --upgrade et --query --available pour obtenir les dérivations. La valeur par défaut est ~/.nix-defexpr.
Si l'argument commence par http:// ou https://, il est interprété comme l'URL d'une archive tar qui sera téléchargée et décompressée dans un emplacement temporaire. L'archive doit inclure un seul répertoire de niveau supérieur contenant au moins un fichier nommé default.nix.
•
--profile / -p chemin
Spécifie le prof
ile à être utilisé par les opérations qui s'exécutent sur un profil (désigné ci-dessous comme le profil actif). Un profil est une séquence d'environnements utilisateur appelés générations, dont l'une est la génération actuelle.
•
--dry-run
Pour les opérations --install, --upgrade, --uninstall, --switch-generation, --delete-generations et --rollback, ce drapeau indiquera à nix-env ce qui serait fait si ce drapeau n'était pas spécifié, sans réellement l'exécuter.
--dry-run indique également quels chemins seront substitués (c'est-à-dire téléchargés) et quels chemins seront construits à partir de la source (car aucune substitution n'est disponible).
•
--system-filter system
Par défaut, les opérations telles que --query --available affichent les dérivations correspondant à n'importe quelle plateforme. Cette option vous permet d'utiliser les dérivations pour la plateforme system spécifiée.

Options communes

La plupart des commandes Nix acceptent les options de ligne de commande suivantes :

•
--help
Affiche un résumé de la syntaxe de la commande et quitte.
•
--version
Affiche le numéro de version de Nix sur la sortie standard et quitte.
•
--verbose / -v
Augmente le niveau de verbosité des messages de diagnostic affichés sur la sortie d'erreur standard. Pour chaque opération Nix, les informations affichées sur la sortie standard sont bien définies ; toutes les informations de diagnostic sont affichées sur la sortie d'erreur standard, jamais sur la sortie standard.
Cette option peut être spécifiée de manière répétée. Actuellement, les niveaux de verbosité suivants existent :
•
0 « Erreurs uniquement »
Affiche uniquement les messages expliquant pourquoi l'invocation Nix a échoué.
•
1 « Informatif »
Affiche des messages utiles sur ce que fait Nix. C'est le défaut.
•
2 « Bavard »
Affiche plus de messages d'information.
•
3 « Loquace »
Affiche encore plus de messages d'information.
•
4 « Débogage »
Affiche des informations de débogage.
•
5 « Vomit »
Affiche une grande quantité d'informations de débogage.
•
--quiet
Diminue le niveau de verbosité des messages de diagnostic affichés sur la sortie d'erreur standard. C'est l'option inverse de -v / --verbose.
Cette option peut être spécifiée de manière répétée. Voir la liste précédente des niveaux de verbosité.
•
--log-format format
Cette option peut être utilisée pour modifier la sortie du format de log, avec format étant l'une des options suivantes :
•
raw
C'est le format brut, tel qu'il est produit par nix-build.
•
internal-json
Affiche les journaux de manière structurée.
Attention
Bien que le schéma lui-même soit relativement stable, le format des messages d'erreur (notamment du champ msg) peut changer entre les versions.
•
bar
Affiche uniquement une barre de progression pendant les constructions.
•
bar-with-logs
Affiche les journaux bruts, avec la barre de progression en bas.
•
--no-build-output / -Q
Par défaut, la sortie écrite par les constructeurs sur la sortie standard et la sortie d'erreur standard est redirigée vers la sortie d'erreur standard de la commande Nix. Cette option supprime ce comportement. Notez que la sortie et l'erreur standard du constructeur sont toujours écrites dans un fichier journal dans prefix/nix/var/log/nix.
•
--max-jobs / -j nombre
Définit le nombre maximum de jobs de construction que Nix exécutera en parallèle au nombre spécifié. Spécifiez auto pour utiliser le nombre de CPU du système. La valeur par défaut est spécifiée par le paramètre de configuration max-jobs, qui vaut lui-même 1 par défaut. Une valeur plus élevée est utile sur les systèmes SMP ou pour exploiter la latence d'E/S.
Le régler à 0 interdit la construction sur la machine locale, ce qui est utile lorsque vous souhaitez que les constructions se déroulent uniquement sur des constructeurs distants.
•
--cores
Définit la valeur de la variable d'environnement NIX_BUILD_CORES dans l'invocation des constructeurs. Les constructeurs peuvent utiliser cette variable à leur discrétion pour contrôler le niveau maximal de parallélisme. Par exemple, dans Nixpkgs, si l'attribut de dérivation enableParallelBuilding est défini sur true, le constructeur transmet le drapeau -jN à GNU Make. Il est défini par défaut sur la valeur du paramètre de configuration cores, s'il est défini, ou sur 1 sinon. La valeur 0 signifie que le constructeur doit utiliser tous les cœurs de CPU disponibles dans le système.
•
--max-silent-time
Définit le nombre maximum de secondes pendant lesquelles un constructeur peut fonctionner sans produire aucune donnée sur la sortie standard ou la sortie d'erreur standard. La valeur par défaut est spécifiée par le paramètre de configuration max-silent-time. 0 signifie aucun délai d'expiration.
•
--timeout
Définit le nombre maximum de secondes pendant lesquelles un constructeur peut s'exécuter. La valeur par défaut est spécifiée par le paramètre de configuration timeout. 0 signifie aucun délai d'expiration.
•
--keep-going / -k
Continuer en cas d'échecs de construction, dans la mesure du possible. C'est-à-dire que si la construction d'une entrée pour une dérivation échoue, Nix construira toujours les autres entrées, mais pas la dérivation elle-même. Sans cette option, Nix s'arrête si une construction échoue (sauf pour les constructions de substitutions), tuant potentiellement les constructions en cours (en cas de constructions parallèles ou distribuées).
•
--keep-failed / -K
Spécifie qu'en cas d'échec de construction, le répertoire temporaire (généralement dans /tmp) dans lequel la construction a lieu ne doit pas être supprimé. Le chemin du répertoire de construction est affiché comme un message d'information.
•
--fallback
Chaque fois que Nix tente de construire une dérivation pour laquelle des substitutions sont connues pour chaque chemin de sortie, mais que la réalisation des chemins de sortie par les substitutions échoue, Nix se rabat sur la construction de la dérivation.
Le scénario le plus courant pour lequel cela est utile est lorsque nous avons enregistré des substitutions afin d'effectuer une distribution binaire à partir, par exemple, d'un dépôt réseau. Si le dépôt est hors service, la réalisation de la dérivation échouera. Lorsque cette option est spécifiée, Nix construira la dérivation à la place. Ainsi, l'installation à partir de binaires se rabat sur l'installation à partir de la source. Cette option n'est pas la valeur par défaut car il est généralement non souhaitable qu'un échec transitoire d'obtention des substitutions entraîne une construction complète à partir de la source (avec la consommation de ressources associée).
•
--readonly-mode
Lorsque cette option est utilisée, aucune tentative n'est faite pour ouvrir la base de données Nix. La plupart des opérations Nix nécessitent un accès à la base de données, donc ces opérations échoueront.
•
--arg nom valeur
Cette option est acceptée par
nix-env, nix-instantiate, nix-shell et nix-build. Lors de l'évaluation des expressions Nix, l'évaluateur d'expressions tentera automatiquement d'appeler les fonctions qu'il rencontre. Il peut appeler automatiquement les fonctions pour lesquelles tous les arguments ont une valeur par défaut (par exemple, { argName ? defaultValue }: ...).
Avec --arg, vous pouvez également appeler des fonctions qui ont des arguments sans valeur par défaut (ou remplacer une valeur par défaut). C'est-à-dire, si l'évaluateur rencontre une fonction avec un argument nommé nom, il l'appellera avec la valeur valeur.
Par exemple, le default.nix de haut niveau dans Nixpkgs est en fait une fonction :
{ # Le système (par exemple, `i686-linux') pour lequel construire les paquets.
system ? builtins.currentSystem
...
}: ...
Donc, si vous appelez cette expression Nix (par exemple, lorsque vous faites nix-env --install --attr pkgname), la fonction sera appelée automatiquement en utilisant la valeur builtins.currentSystem pour l'argument system. Vous pouvez remplacer cela en utilisant --arg, par exemple, nix-env --install --attr pkgname --arg system \"i686-freebsd\". (Notez que puisque l'argument est une chaîne de caractères littérale Nix, vous devez échapper les guillemets.)
•
--argstr nom valeur
Cette option est comme --arg, seule la valeur n'est pas une expression Nix mais une chaîne de caractères. Donc au lieu de --arg system \"i686-linux\" (les guillemets extérieurs servent à satisfaire le shell) vous pouvez dire --argstr system i686-linux.
•
--attr / -A attrPath
Sélectionne un attribut de l'expression Nix de haut niveau en cours d'évaluation. (nix-env, nix-instantiate, nix-build et nix-shell seulement.) Le chemin d'attribut attrPath est une séquence de noms d'attributs séparés par des points. Par exemple, étant donné une expression Nix de haut niveau e, le chemin d'attribut xorg.xorgserver entraînerait l'utilisation de l'expression e.xorg.xorgserver. Voir nix-env --install pour des exemples concrets.
En plus des noms d'attributs, vous pouvez également spécifier des indices de tableau. Par exemple, le chemin d'attribut foo.3.bar sélectionne l'attribut bar du quatrième élément du tableau dans l'attribut foo de l'expression de haut niveau.
•
--expr / -E
Interprète les arguments de la ligne de commande comme une liste d'expressions Nix à analyser et évaluer, plutôt que comme une liste de noms de fichiers d'expressions Nix. (nix-instantiate, nix-build et nix-shell seulement.)
Pour nix-shell, cette option est couramment utilisée pour vous fournir un shell dans lequel vous pouvez construire les paquets retournés par l'expression. Si vous voulez obtenir un shell contenant les paquets construits prêts à l'emploi, donnez votre expression à l'indicateur de commodité nix-shell --packages à la place.
•
-I / --include chemin
Ajoute une entrée à la liste des chemins de recherche utilisés pour résoudre les chemins de recherche. Cette option peut être donnée plusieurs fois.
Les chemins ajoutés via -I ont la priorité sur le paramètre de configuration nix-path et la variable d'environnement NIX_PATH .
•
--option nom valeur
Définit l'option de configuration Nix nom à valeur. Ceci remplace les paramètres du fichier de configuration Nix (voir nix.conf5).
•
--repair
Répare les chemins de magasin corrompus ou manquants en les téléchargeant ou en les reconstruisant. Notez que cela est lent car cela nécessite de calculer un hachage cryptographique du contenu de chaque chemin dans la fermeture de la construction. Notez également l'avertissement sous nix-store --repair-path.

Note

Voir man nix.conf pour remplacer les paramètres de configuration avec des options de ligne de commande.

Variables d'environnement

•
NIX_PROFILE
Emplacement du profil Nix. Par défaut, cible le lien symbolique ~/.nix-profile, s'il existe, ou /nix/var/nix/profiles/default sinon.

Variables d'environnement courantes

La plupart des commandes Nix interprètent les variables d'environnement suivantes :

•
IN_NIX_SHELL
Indicateur qui signale si l'environnement actuel a été configuré par nix-shell. Il peut avoir les valeurs pure ou impure.
•
NIX_PATH
Une liste d'entrées de chemins de recherche séparées par des deux-points, utilisée pour résoudre les chemins de recherche.
Cette variable d'environnement remplace la valeur du paramètre de configuration nix-path .
Elle peut être étendue en utilisant l'option -I .
Exemple
$ export NIX_PATH=`/home/eelco/Dev:nixos-config=/etc/nixos
Si NIX_PATH est défini sur une chaîne vide, la résolution des chemins de recherche échouera toujours.
Exemple
$ NIX_PATH= nix-instantiate --eval '<nixpkgs>'
error: file 'nixpkgs' was not found in the Nix search path (add it using $NIX_PATH or -I)
•
NIX_IGNORE_SYMLINK_STORE
Normalement, le répertoire de magasin Nix (typiquement /nix/store) n'est pas autorisé à contenir de composantes de liens symboliques. Ceci afin d'éviter les constructions « impures ». Les constructeurs « canonisent » parfois les chemins en résolvant toutes les composantes de liens symboliques. Ainsi, les constructions sur différentes machines (avec /nix/store résolvant vers différents emplacements) pourraient donner des résultats différents. Ce n'est généralement pas un problème, sauf lorsque les constructions sont déployées sur des machines où /nix/store se résout différemment. Si vous êtes sûr de ne pas faire cela, vous pouvez définir NIX_IGNORE_SYMLINK_STORE à 1.
Notez que si vous créez un lien symbolique vers le magasin Nix afin de pouvoir le placer sur un système de fichiers différent du système de fichiers racine, sous Linux, il est préférable d'utiliser des points de montage bind, par exemple :
$ mkdir /nix
$ mount -o bind /mnt/otherdisk/nix /nix
Consultez la page de manuel de mount 8 pour plus de détails.
•
NIX_STORE_DIR
Remplace l'emplacement du magasin Nix (par défaut prefix/store).
•
NIX_DATA_DIR
Remplace l'emplacement du répertoire de données statiques Nix (par défaut prefix/share).
•
NIX_LOG_DIR
Remplace l'emplacement du répertoire de logs Nix (par défaut prefix/var/log/nix).
•
NIX_STATE_DIR
Remplace l'emplacement du répertoire d'état Nix (par défaut prefix/var/nix).
•
NIX_CONF_DIR
Remplace l'emplacement du répertoire de configuration Nix du système (par défaut prefix/etc/nix).
•
NIX_CONFIG
Applique les paramètres de la configuration Nix depuis l'environnement. Le contenu est traité comme s'il était lu à partir d'un fichier de configuration Nix. Les paramètres sont séparés par le caractère de nouvelle ligne.
"Bl-tag">
•
NIX_USER_CONF_FILES
Remplace l'emplacement des fichiers de configuration utilisateur de Nix à charger.
Les valeurs par défaut sont les emplacements conformes à la Spécification des répertoires de base XDG. Voir la sous-section Répertoires de base XDG pour plus de détails.
La variable est traitée comme une liste séparée par le jeton :.
•
TMPDIR
Utilise le répertoire spécifié pour stocker les fichiers temporaires. En particulier, cela inclut les répertoires de construction temporaires ; ceux-ci peuvent occuper une quantité substantielle d'espace disque. La valeur par défaut est /tmp.
•
NIX_REMOTE
Cette variable doit être définie sur daemon si vous souhaitez utiliser le démon Nix pour exécuter les opérations Nix. Ceci est nécessaire dans les installations Nix multi-utilisateurs. Si le socket Unix du démon Nix se trouve à un chemin non standard, cette variable doit être définie sur unix://chemin/vers/socket. Sinon, elle doit être laissée non définie.
•
NIX_SHOW_STATS
Si elle est définie sur 1, Nix affichera quelques statistiques d'évaluation, comme le nombre de valeurs allouées.
•
NIX_COUNT_CALLS
Si elle est définie sur 1, Nix affichera la fréquence à laquelle les fonctions ont été appelées lors de l'évaluation des expressions Nix. Ceci est utile pour profiler vos expressions Nix.
•
GC_INITIAL_HEAP_SIZE
Si Nix a été configuré pour utiliser le ramasse-miettes Boehm, cette variable définit la taille initiale du tas en octets. Elle est par défaut à 384 MiB. La définir sur une petite valeur réduit la consommation de mémoire, mais augmente le temps d'exécution en raison de la surcharge du ramasse-miettes.

Répertoires de base XDG

Nix suit la Spécification des répertoires de base XDG.

Pour des raisons de compatibilité ascendante, les commandes Nix ne suivront la norme que lorsque use-xdg-base-directories sera activé. Les nouvelles commandes Nix (expérimentales) respectent la norme par défaut.

Les variables d'environnement suivantes sont utilisées pour déterminer les emplacements de divers fichiers d'état et de configuration :

  • [XDG_CONFIG_HOME]{#env-XDGCONFIGHOME} (par défaut ~/.config)
  • [XDG_STATE_HOME]{#env-XDGSTATEHOME} (par défaut ~/.local/state)
  • [XDG_CACHE_HOME]{#env-XDGCACHEHOME} (par défaut ~/.cache)

Exemples

Pour installer un paquet en utilisant un chemin d'attribut spécifique de l'expression Nix active :

$ nix-env --install --attr gcc40mips
installation de `gcc-4.0.2'
$ nix-env --install --attr xorg.xorgserver
installation de `xorg-server-1.2.0'

Pour installer une version spécifique de gcc en utilisant le nom de dérivation :

$ nix-env --install gcc-3.3.2
installation de `gcc-3.3.2'
désinstallation de `gcc-3.1'

L'utilisation du chemin d'attribut pour sélectionner un paquet est préférable, car elle est beaucoup plus rapide et il n'y aura pas de correspondances multiples.

Notez que la version précédemment installée est supprimée, car --preserve-installed n'a pas été spécifié.

Pour installer une version arbitraire :

$ nix-env --install gcc
installation de `gcc-3.3.2'

Pour installer toutes les dérivations dans l'expression Nix foo.nix :

$ nix-env --file ~/foo.nix --install '.*'

Pour copier le chemin du magasin avec le nom symbolique gcc d'un autre profil :

$ nix-env --install --from-profile /nix/var/nix/profiles/foo gcc

Pour installer une dérivation de magasin spécifique :

$ nix-env --install /nix/store/fibjb1bfbpm5mrsxc4mh2d8n37sxh91i-gcc-3.4.3.drv

Pour installer un chemin de sortie spécifique :

$ nix-env --install /nix/store/y3cgx0xj1p4iv9x0pnnmdhr8iyg741vk-gcc-3.4.3

Pour installer à partir d'une expression Nix spécifiée sur la ligne de commande :

$ nix-env --file ./foo.nix --install --expr \
    'f: (f {system = "i686-linux";}).subversionWithJava'

C'est-à-dire que cela s'évalue à (f: (f {system = "i686-linux";}).subversionWithJava) (import ./foo.nix), sélectionnant ainsi l'attribut subversionWithJava de l'ensemble retourné par l'appel de la fonction définie dans ./foo.nix.

Un essai à blanc vous indique quels chemins seront téléchargés ou construits à partir des sources :

$ nix-env --file '<nixpkgs>' --install --attr hello --dry-run
(essai à blanc ; ne fait rien)
installation de ‘hello-2.10’
ce chemin sera récupéré (0.04 Mio téléchargé, 0.19 Mio décompressé) :
  /nix/store/wkhdf9jinag5750mqlax6z2zbwhqb76n-hello-2.10
  ...

Pour installer Firefox à partir de la dernière révision du canal Nixpkgs/NixOS 14.12 :

$ nix-env --file https://github.com/NixOS/nixpkgs/archive/nixos-14.12.tar.gz --install --attr firefox
