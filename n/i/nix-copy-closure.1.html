Nom

nix-copy-closure - copie les objets du store vers ou depuis une machine distante via SSH

Synopsis

nix-copy-closure [--to | --from ] [--gzip] [--include-outputs] [--use-substitutes | -s] [-v] [utilisateur@]machine[:port] chemins

Description

Étant donné des chemins d'une machine, nix-copy-closure calcule la fermeture de ces chemins (c'est-à-dire toutes leurs dépendances dans le store Nix), et copie les objets du store dans cette fermeture vers une autre machine via SSH. Il ne copie pas les objets du store qui sont déjà présents sur l'autre machine.

Note

Alors que le store Nix à utiliser sur la machine locale peut être spécifié sur la ligne de commande avec l'option --store, le store Nix à accéder sur la machine distante ne peut être configuré statiquement sur cette machine distante.

Puisque nix-copy-closure appelle ssh, vous pourriez avoir besoin de vous authentifier auprès de la machine distante. En fait, vous pourriez être invité à vous authentifier deux fois car nix-copy-closure se connecte actuellement deux fois à la machine distante : d'abord pour obtenir l'ensemble des chemins manquants sur la machine cible, et ensuite pour envoyer le dump de ces chemins. Lorsque vous utilisez l'authentification par clé publique, vous pouvez éviter de taper le mot de passe avec ssh-agent.

Options

•
--to
Copie la fermeture des chemins d'un store Nix accessible depuis la machine locale vers le store Nix de la machine distante. C'est le comportement par défaut.
•
--from
Copie la fermeture des chemins depuis le store Nix de la machine distante vers le store Nix spécifié de la machine locale.
•
--gzip
Active la compression de la connexion SSH.
•
--include-outputs
Copie également les sorties des dérivations du store incluses dans la fermeture.
•
--use-substitutes / -s
Tente de télécharger les objets du store manquants sur la cible depuis les substituts. Tous les objets du store qui ne peuvent pas être substitués sur la cible sont toujours copiés normalement depuis la source. Ceci est utile, par exemple, si la connexion entre la machine source et cible est lente, mais que la connexion entre la machine cible et cache.nixos.org (le serveur de cache binaire par défaut) est rapide.

•

•
--max-jobs / -j nombre

--cores
Définit la valeur de la variable d'environnement NIX_BUILD_CORES dans l'invocation des constructeurs. Les constructeurs peuvent utiliser cette variable à leur discrétion pour contrôler la quantité maximale de parallélisme. Par exemple, dans Nixpkgs, si l'attribut de dérivation enableParallelBuilding est défini sur true, le constructeur transmet le drapeau -jN à GNU Make. Par défaut, il prend la valeur du paramètre de configuration cores, s'il est défini, ou 1 sinon. La valeur 0 signifie que le constructeur doit utiliser tous les cœurs de processeur disponibles dans le système.
•
--max-silent-time
Définit le nombre maximum de secondes pendant lesquelles un constructeur peut rester sans produire de données sur la sortie standard ou l'erreur standard. La valeur par défaut est spécifiée par le paramètre de configuration max-silent-time. 0 signifie pas de délai d'attente.
•
--timeout
Définit le nombre maximum de secondes pendant lesquelles un constructeur peut s'exécuter. La valeur par défaut est spécifiée par le paramètre de configuration timeout. 0 signifie pas de délai d'attente.
•
--keep-going / -k
Continuer en cas d'échecs de construction, dans la mesure du possible. C'est-à-dire, si la construction d'une entrée d'une dérivation échoue, Nix construira les autres entrées, mais pas la dérivation elle-même. Sans cette option, Nix s'arrête si une construction échoue (sauf pour les constructions de substituts), tuant potentiellement les constructions en cours (en cas de constructions parallèles ou distribuées).
•
--keep-failed / -K
Spécifie qu'en cas d'échec de construction, le répertoire temporaire (généralement dans /tmp) dans lequel la construction a lieu ne doit pas être supprimé. Le chemin du répertoire de construction est imprimé comme un message d'information.
•
--fallback
Chaque fois que Nix tente de construire une dérivation pour laquelle des substituts sont connus pour chaque chemin de sortie, mais que la réalisation des chemins de sortie via les substituts échoue, il se rabat sur la construction de la dérivation.
Le scénario le plus courant dans lequel cela est utile est lorsque nous avons enregistré des substituts afin d'effectuer une distribution binaire à partir, par exemple, d'un dépôt réseau. Si le dépôt est en panne, la réalisation de la dérivation échouera. Lorsque cette option est spécifiée, Nix construira la dérivation à la place. Ainsi, l'installation à partir de binaires se rabat sur l'installation à partir de la source. Cette option n'est pas la valeur par défaut car il n'est généralement pas souhaitable qu'un échec transitoire dans l'obtention des substituts conduise à une construction complète à partir de la source (avec la consommation de ressources associée).
•
--readonly-mode
Lorsque cette option est utilisée, aucune tentative n'est faite pour ouvrir la base de données Nix. La plupart des opérations Nix nécessitent un accès à la base de données, donc ces opérations échoueront.
•
--arg nom valeur
Cette option est acceptée par nix-env, nix-instantiate, nix-shell et nix-build. Lors de l'évaluation des expressions Nix, l'évaluateur d'expression essaiera automatiquement d'appeler les fonctions qu'il rencontre. Il peut appeler automatiquement des fonctions pour lesquelles chaque argument a une valeur par défaut (par exemple, { argName ? defaultValue }: ...).
Avec --arg, vous pouvez également appeler des fonctions qui ont des arguments sans valeur par défaut (ou remplacer une valeur par défaut). C'est-à-dire, si l'évaluateur rencontre une fonction avec un argument nommé nom, il l'appellera avec la valeur valeur.
Par exemple, le default.nix de haut niveau dans Nixpkgs est en fait une fonction :
{ # Le système (par exemple, `i686-linux') pour lequel construire les paquets.
system ? builtins.currentSystem
...
}: ...
Ainsi, si vous appelez cette expression Nix (par exemple, lorsque vous faites nix-env --install --attr nom_paquet), la fonction sera appelée automatiquement en utilisant la valeur builtins.currentSystem pour l'argument system. Vous pouvez le remplacer en utilisant --arg, par exemple, nix-env --install --attr nom_paquet --arg system \"i686-freebsd\". (Notez que comme l'argument est une chaîne de caractères Nix, vous devez échapper les guillemets.)
•
--argstr nom valeur
Cette option est comme --arg, seulement la valeur n'est pas une expression Nix mais une chaîne de caractères. Donc, au lieu de --arg system \"i686-linux\" (les guillemets extérieurs servent à la shell), vous pouvez dire --argstr system i686-linux.
•
--attr / -A cheminAttr
Sélectionne un attribut de l'expression Nix de haut niveau évaluée. (nix-env, nix-instantiate, nix-build et nix-shell uniquement.) Le chemin d'attribut cheminAttr est une séquence de noms d'attributs séparés par des points. Par exemple, étant donné une expression Nix de haut niveau e, le chemin d'attribut xorg.xorgserver utiliserait l'expression e.xorg.xorgserver. Voir nix-env --install pour des exemples concrets.
En plus des noms d'attributs, vous pouvez également spécifier des indices de tableau. Par exemple, le chemin d'attribut foo.3.bar sélectionne l'attribut bar du quatrième élément du tableau dans l'attribut foo de l'expression de haut niveau.
•
--expr / -E
Interprète les arguments de la ligne de commande comme une liste d'expressions Nix à analyser et évaluer, plutôt qu'une liste de noms de fichiers d'expressions Nix. (nix-instantiate, nix-build et nix-shell uniquement.)
Pour nix-shell, cette option est couramment utilisée pour vous donner un shell dans lequel vous pouvez construire les paquets retournés par l'expression. Si vous voulez obtenir un shell contenant les paquets *construits* prêts à l'emploi, donnez votre expression à l'indicateur pratique nix-shell --packages à la place.
•
-I / --include chemin
Ajoute une entrée à la liste des chemins de recherche utilisés pour résoudre les chemins de recherche. Cette option peut être donnée plusieurs fois.
Les chemins ajoutés via -I ont la priorité sur le paramètre de configuration nix-path et la variable d'environnement NIX_PATH.
•
--option nom valeur
Définit l'option de configuration Nix nom à valeur. Ceci écrase les paramètres du fichier de configuration Nix (voir nix.conf5).
•
--repair
Corrige les chemins de magasin corrompus ou manquants en les redownloadant ou en les reconstruisant. Notez que cela est lent car cela nécessite de calculer un hachage cryptographique du contenu de chaque chemin dans la fermeture de la construction. Notez également l'avertissement sous nix-store --repair-path.

Note

Voir man nix.conf pour remplacer les paramètres de configuration avec des drapeaux de ligne de commande.

Variables d'environnement courantes

La plupart des commandes Nix interprètent les variables d'environnement suivantes :

•
IN_NIX_SHELL
Indicateur qui signale si l'environnement actuel a été configuré par nix-shell. Il peut prendre les valeurs pure ou impure.
•
NIX_PATH
Une liste d'entrées de chemin de recherche séparées par des deux-points utilisée pour résoudre les chemins de recherche.
Cette variable d'environnement remplace la valeur du paramètre de configuration nix-path .
Elle peut être étendue en utilisant l' -I option.
Exemple
$ export NIX_PATH=`/home/eelco/Dev:nixos-config=/etc/nixos
Si NIX_PATH est défini sur une chaîne vide, la résolution des chemins de recherche échouera toujours.
Exemple
$ NIX_PATH= nix-instantiate --eval '<nixpkgs>'
error: file 'nixpkgs' was not found in the Nix search path (add it using $NIX_PATH or -I)
•
NIX_IGNORE_SYMLINK_STORE
Normalement, le répertoire du magasin Nix (typiquement /nix/store) ne peut pas contenir de composantes de liens symboliques. Ceci afin d'éviter les constructions « impures ». Les constructeurs « canonicalisent » parfois les chemins en résolvant toutes les composantes de liens symboliques. Ainsi, les constructions sur différentes machines (avec /nix/store résolu à des emplacements différents) pourraient produire des résultats différents. Ce n'est généralement pas un problème, sauf lorsque les constructions sont déployées sur des machines où /nix/store est résolu différemment. Si vous êtes sûr que vous n'allez pas faire cela, vous pouvez définir NIX_IGNORE_SYMLINK_STORE à 1.
Notez que si vous créez des liens symboliques vers le magasin Nix afin de le placer sur un autre système de fichiers que le système de fichiers racine, sous Linux, il est préférable d'utiliser des points de montage bind, par exemple :
$ mkdir /nix
$ mount -o bind /mnt/otherdisk/nix /nix
Consultez la page de manuel de mount 8 pour plus de détails.
•
NIX_STORE_DIR
Remplace l'emplacement du magasin Nix (par défaut prefix/store).
•
NIX_DATA_DIR
Remplace l'emplacement du répertoire de données statiques Nix (par défaut prefix/share).
•
NIX_LOG_DIR
Remplace l'emplacement du répertoire de logs Nix (par défaut prefix/var/log/nix).
•
NIX_STATE_DIR
Remplace l'emplacement du répertoire d'état Nix (par défaut prefix/var/nix).
•
NIX_CONF_DIR
Remplace l'emplacement du répertoire de configuration système Nix (par défaut prefix/etc/nix).
•
NIX_CONFIG
Applique les paramètres de configuration Nix depuis l'environnement. Le contenu est traité comme s'il était lu à partir d'un fichier de configuration Nix. Les paramètres sont séparés par le caractère de nouvelle ligne.
•
NIX_USER_CONF_FILES
Remplace l'emplacement des fichiers de configuration utilisateur Nix à charger depuis.
Les valeurs par défaut sont les emplacements conformément à la spécification des répertoires de base XDG. Voir la sous-section Répertoires de base XDG pour plus de détails.
La variable est traitée comme une liste séparée par le jeton :.
•
TMPDIR
Utilise le répertoire spécifié pour stocker les fichiers temporaires. En particulier, cela inclut les répertoires de construction temporaires ; ceux-ci peuvent occuper une quantité substantielle d'espace disque. La valeur par défaut est /tmp.
•
NIX_REMOTE
Cette variable doit être définie sur daemon si vous souhaitez utiliser le démon Nix pour exécuter des opérations Nix. Ceci est nécessaire dans les installations Nix multi-utilisateurs. Si la socket Unix du démon Nix se trouve à un chemin non standard, cette variable doit être définie sur unix://path/to/socket. Sinon, elle doit rester non définie.
•
NIX_SHOW_STATS
Si définie sur 1, Nix affichera des statistiques d'évaluation, telles que le nombre de valeurs allouées.
•
NIX_COUNT_CALLS
Si définie sur 1, Nix affichera la fréquence d'appel des fonctions pendant l'évaluation des expressions Nix. Ceci est utile pour profiler vos expressions Nix.
•
GC_INITIAL_HEAP_SIZE
Si Nix a été configuré pour utiliser le collecteur de déchets Boehm, cette variable définit la taille initiale du tas en octets. Elle est par défaut de 384 Mio. La définir sur une valeur faible réduit la consommation de mémoire, mais augmentera le temps d'exécution en raison de la surcharge de la collecte des déchets.

Répertoires de base XDG

Nix suit la spécification des répertoires de base XDG.

Pour des raisons de compatibilité ascendante, les commandes Nix suivront la norme uniquement lorsque use-xdg-base-directories est activé. Les nouvelles commandes Nix (expérimentales) sont conformes à la norme par défaut.

Les variables d'environnement suivantes sont utilisées pour déterminer les emplacements de divers fichiers d'état et de configuration :

  • [XDG_CONFIG_HOME]{#env-XDGCONFIGHOME} (par défaut ~/.config)
  • [XDG_STATE_HOME]{#env-XDGSTATEHOME} (par défaut ~/.local/state)
  • [XDG_CACHE_HOME]{#env-XDGCACHEHOME} (par défaut ~/.cache)

$ storePath="$(nix-build '<nixpkgs>' -I nixpkgs=channel:nixpkgs-unstable -A hello --no-out-link)"
$ nix-copy-closure --to alice@itchy.example.org "$storePath"

Exemple

Copier GNU Hello d'une machine distante en utilisant un chemin de magasin connu, puis l'exécuter :

$ storePath="$(nix-instantiate --eval '<nixpkgs>' -I nixpkgs=channel:nixpkgs-unstable -A hello.outPath | tr -d '"')"
$ nix-copy-closure --from alice@itchy.example.org "$storePath"
$ "$storePath"/bin/hello
Hello, world!

    Synopsis

    nix-copy-closure [options] ... <derivation>...

    Description

    Cette commande copie la fermeture de l'ensemble des derivations spécifiées vers un magasin Nix distant.

    Options

    • --to <host> : Spécifie le magasin Nix distant vers lequel copier les éléments. L'hôte peut être une URL ou un nom d'hôte avec un chemin vers le magasin Nix (par exemple, ssh://user@host/nix/store).
    • --from <host> : Spécifie le magasin Nix source à partir duquel copier les éléments.
    • --build-root <path> : Spécifie le répertoire racine des constructions pour le magasin distant.
    • --include-build-inputs : Inclut également les entrées de construction des derivations spécifiées.
    • --exclude-outputs : Exclut les sorties des derivations spécifiées (utile pour copier uniquement les métadonnées).
    • --json : Produit une sortie au format JSON.

    Variables d'environnement courantes

    • NIX_REMOTE_STORE : Spécifie le magasin Nix distant par défaut.
    • NIX_BUILD_ROOT : Spécifie le répertoire racine des constructions par défaut pour le magasin distant.

    Pour copier la fermeture d'une dérivation vers un magasin distant sur buildserver:

    nix-copy-closure --to ssh://user@buildserver /nix/store/abc-my-package
