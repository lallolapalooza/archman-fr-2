nix3-flake(1) Manuel des commandes générales nix3-flake(1)

Avertissement
Ce programme est expérimental et son interface est sujette à modification.

Nom

nix flake - gérer les flakes Nix

Synopsis

nix flake [option…] sous-commande

où sous-commande est l'une des suivantes :

  • nix flake archive - copier un flake et toutes ses entrées vers un magasin
  • nix flake check - vérifier si le flake s'évalue et exécuter ses tests
  • nix flake clone - cloner le dépôt du flake
  • nix flake info - afficher les métadonnées du flake
  • nix flake init - créer un flake dans le répertoire courant à partir d'un modèle
  • nix flake lock - créer les entrées manquantes du fichier de verrouillage
  • nix flake metadata - afficher les métadonnées du flake
  • nix flake new - créer un flake dans le répertoire spécifié à partir d'un modèle
  • nix flake prefetch - télécharger l'arborescence source désignée par une référence de flake dans le magasin Nix
  • nix flake show - afficher les sorties fournies par un flake
  • nix flake update - mettre à jour le fichier de verrouillage du flake

Description

nix flake fournit des sous-commandes pour créer, modifier et interroger des flakes Nix. Les flakes sont l'unité de conditionnement du code Nix de manière reproductible et découvrable. Ils peuvent avoir des dépendances sur d'autres flakes, ce qui permet des projets Nix multi-dépôts.

Un flake est une arborescence de fichiers (généralement récupérée depuis un dépôt Git ou une archive tar) qui contient un fichier nommé flake.nix dans le répertoire racine. flake.nix spécifie certaines métadonnées sur le flake, telles que les dépendances (appelées entrées), ainsi que ses sorties (les valeurs Nix telles que les paquets ou les modules NixOS fournis par le flake).

Références de flake

Les références de flake (flakerefs) sont un moyen de spécifier l'emplacement d'un flake. Celles-ci ont deux formes différentes :

Représentation par ensemble d'attributs

Exemple :

{
  type = "github";
  owner = "NixOS";
  repo = "nixpkgs";
}

L'attribut requis est uniquement type. Les types supportés sont listés ci-dessous.

Syntaxe type URL

Exemple :

github:NixOS/nixpkgs

Celles-ci sont utilisées en ligne de commande comme une alternative plus pratique à la représentation par ensemble d'attributs. Par exemple, dans la commande

# nix build github:NixOS/nixpkgs#hello

github:NixOS/nixpkgs est une référence de flake (tandis que hello est un attribut de sortie). Elles sont également autorisées dans l'attribut inputs d'un flake, par exemple.

inputs.nixpkgs.url = "github:NixOS/nixpkgs";

est équivalent à

inputs.nixpkgs = {
  type = "github";
  owner = "NixOS";
  repo = "nixpkgs";
};

Conformément à RFC 3986, les caractères en dehors de la plage autorisée (c'est-à-dire ni les caractères réservés ni les caractères non réservés) doivent être encodés en pourcentage.

Exemples

Voici quelques exemples de références de flakes dans leur représentation type URL :

  • nixpkgs : L'entrée nixpkgs dans le registre des flakes.
  • nixpkgs/a3a3dda3bacf61e8a39258a0ed9c924eeca8e293 : L'entrée nixpkgs dans le registre des flakes, avec sa révision Git remplacée par une valeur spécifique.
  • github:NixOS/nixpkgs : La branche master du dépôt NixOS/nixpkgs sur GitHub.
  • github:NixOS/nixpkgs/nixos-20.09 : La branche nixos-20.09 du dépôt nixpkgs.
  • github:NixOS/nixpkgs/a3a3dda3bacf61e8a39258a0ed9c924eeca8e293 : Une révision spécifique du dépôt nixpkgs.
  • github:edolstra/nix-warez?dir=blender : Un flake dans un sous-répertoire d'un dépôt GitHub.
  • git+https://github.com/NixOS/patchelf : Un dépôt Git.
  • git+https://github.com/NixOS/patchelf?ref=master : Une branche spécifique d'un dépôt Git.
  • git+https://github.com/NixOS/patchelf?ref=master&rev=f34751b88bd07d7f44f5cd3200fb4122bf916c7e : Une branche et une révision spécifiques d'un dépôt Git.
  • https://github.com/NixOS/patchelf/archive/master.tar.gz : Un flake sous forme d'archive tar.

Syntaxe type chemin

Les flakes correspondant à un chemin local peuvent également être référencés par une référence de chemin directe, soit /chemin/absolu/vers/le/flake soit./chemin/relatif/vers/le/flake. Notez que le préfixe ./ est obligatoire pour les chemins relatifs. S'il est omis, le chemin sera interprété comme une syntaxe type URL, ce qui entraînera des messages d'erreur comme ceci :

error: impossible de trouver le flake 'flake:chemin/relatif/vers/le/flake' dans les registres de flakes

La sémantique d'un tel chemin est la suivante :

  • Si le répertoire fait partie d'un dépôt Git, alors l'entrée sera traitée comme une URL git+file:, sinon elle sera traitée comme une URL path: ;
  • Si le répertoire ne contient pas de fichier flake.nix, alors Nix recherchera un tel fichier vers le haut dans la hiérarchie du système de fichiers jusqu'à ce qu'il trouve l'un des éléments suivants :
1.
La racine du dépôt Git, ou
2.
La racine du système de fichiers (/), ou
3.
Un dossier sur un point de montage différent.

Contrairement aux références type URL, les références de flake type chemin peuvent contenir des caractères Unicode arbitraires (sauf # et ?).

Exemples

  • . : Le flake auquel le répertoire courant appartient.
  • /home/alice/src/patchelf : Un flake dans un autre répertoire.
  • ./../répertoire/avec Ûñî©ôδ€ : Un flake dans un autre répertoire relatif dont le nom contient des caractères Unicode.

Attributs de référence de flake

Les attributs génériques de référence de flake suivants

Ce site n'est en aucun cas associé à Arch Linux ni affilié à ce projet. Le contenu est uniquement une traduction des pages de manuel d'Arch publiées sur man.archlinux.org.

Attributs de référence de flocon

Les attributs suivants sont pris en charge :

  • dir : Le sous-répertoire du flocon dans lequel se trouve flake.nix. Ce paramètre permet d'avoir plusieurs flocons dans un dépôt ou une archive tar. La valeur par défaut est le répertoire racine du flocon.
  • narHash : Le hachage de la sérialisation de l'archive Nix (NAR) (au format SRI) du contenu du flocon. Ceci est utile pour les types de flocons tels que les archives tar qui manquent d'un identifiant de contenu unique tel qu'un hachage de commit Git.

En outre, les attributs suivants sont communs à plusieurs types de références de flocons :

  • rev : Un hachage de commit Git ou Mercurial.
  • ref : Un nom de branche ou de tag Git ou Mercurial.

Enfin, certains attributs ne sont généralement pas spécifiés par l'utilisateur, mais peuvent apparaître dans les références de flocons verrouillées et sont disponibles pour le code Nix :

  • revCount : Le nombre d'ancêtres du commit rev.
  • lastModified : L'horodatage (en secondes depuis l'époque Unix) de la dernière modification de cette version du flocon. Pour les flocons Git/Mercurial, il s'agit de l'heure du commit rev, tandis que pour les flocons d'archive tar, il s'agit de l'horodatage le plus récent de n'importe quel fichier à l'intérieur de l'archive tar.

Types

Actuellement, l'attribut type peut être l'un des suivants :

•
indirect : Par défaut. Indirection via le registre des flocons. Ceux-ci ont la forme
[flake:]<flake-id>(/<rev-or-ref>(/rev)?)?
Ceux-ci effectuent une recherche de <flake-id> dans le registre des flocons. Par exemple, nixpkgs et nixpkgs/release-20.09 sont des références de flocons indirectes. Le rev et/ou ref spécifiés sont fusionnés avec l'entrée dans le registre ; voir registre nix pour plus de détails.
Par exemple, voici des références de flocons indirectes valides :
  • nixpkgs
  • nixpkgs/nixos-unstable
  • nixpkgs/a3a3dda3bacf61e8a39258a0ed9c924eeca8e293
  • nixpkgs/nixos-unstable/a3a3dda3bacf61e8a39258a0ed9c924eeca8e293
  • sub/dir (si un flocon nommé sub se trouve dans le registre)
•
path : répertoires locaux arbitraires. L'attribut requis path spécifie le chemin du flocon. La forme de l'URL est
path:<path>(\?<params>)?
où path est un chemin absolu vers un répertoire dans le système de fichiers contenant un fichier nommé flake.nix.
Si le flocon à path n'est pas à l'intérieur d'un dépôt git, le préfixe path: est implicite et peut être omis.
path doit généralement être un chemin absolu. Cependant, sur la ligne de commande, il peut s'agir d'un chemin relatif (par exemple, . ou ./foo) qui est interprété comme relatif au répertoire courant. Dans ce cas, il doit commencer par . pour éviter toute ambiguïté avec les recherches dans le registre (par exemple, nixpkgs est une recherche dans le registre ; ./nixpkgs est un chemin relatif).
Par exemple, voici des références de flocons de type chemin valides :
  • path:/home/user/sub/dir
  • /home/user/sub/dir (si dir/flake.nix n'est pas dans un dépôt git)
  • ./sub/dir (lorsqu'il est utilisé sur la ligne de commande et que dir/flake.nix n'est pas dans un dépôt git)
•
git : dépôts Git. L'emplacement du dépôt est spécifié par l'attribut url.
Ils ont la forme d'URL
git(+http|+https|+ssh|+git|+file):(//<server>)?<path>(\?<params>)?
Si path commence par / (ou ./ lorsqu'il est utilisé comme argument sur la ligne de commande) et est un chemin local vers un dépôt git, les préfixes git: ou +file sont implicites et peuvent être omis.
L'attribut ref vaut par défaut la résolution de la référence HEAD.
L'attribut rev doit désigner un commit qui existe dans la branche ou le tag spécifié par l'attribut ref, car Nix n'effectue pas de clonage complet du dépôt distant par défaut (et le protocole Git ne permet pas de récupérer un rev sans un ref connu). La valeur par défaut est le commit actuellement pointé par ref.
Lorsque git+file est utilisé sans spécifier ref ou rev, les fichiers sont récupérés directement depuis le path local tant qu'ils ont été ajoutés au dépôt Git. S'il y a des modifications non validées, la référence est traitée comme "sale" et un avertissement est affiché.
Par exemple, les références de flocons Git suivantes sont valides :
  • git:/home/user/sub/dir
  • /home/user/sub/dir (si dir/flake.nix est dans un dépôt git)
  • ./sub/dir (lorsqu'il est utilisé sur la ligne de commande et que dir/flake.nix est dans un dépôt git)
  • git+https://example.org/my/repo
  • git+https://example.org/my/repo?dir=flake1
  • git+ssh://git@github.com/NixOS/nix?ref=v1.2.3
  • git://github.com/edolstra/dwarffs?ref=unstable&rev=e486d8d40e626a20e06d792db8cc5ac5aba9a5b4
  • git+file:///home/my-user/some-repo/some-repo
  • mercurial : dépôts Mercurial. La forme de l'URL est similaire au type git, à la différence près que le schéma d'URL doit être l'un des suivants : hg+http, hg+https, hg+ssh ou hg+file.
  • tarball : archives tar. L'emplacement de l'archive tar est spécifié par l'attribut url.
En forme d'URL, le schéma doit être tarball+http://, tarball+https:// ou tarball+file://. Si l'extension correspond à un format d'archive connu (.zip, .tar, .tgz, .tar.gz, .tar.xz, .tar.bz2 ou .tar.zst), alors tarball+ peut être omis.
Ceci peut également être utilisé pour définir l'emplacement des branches gitea/forgejo. Voir ici
•
file : fichiers plats ou archives de répertoires, soit via http(s) soit depuis le disque local.
En forme d'URL, le schéma doit être file+http://, file+https:// ou file+file://. Si l'extension ne correspond pas à un format d'archive connu (tel que défini par le récupérateur tarball), alors le préfixe file+ peut être omis.
•
github : un moyen plus efficace de récupérer des dépôts de GitHub. Les attributs suivants sont requis :
  • owner : Le propriétaire du dépôt.
  • repo : Le nom du dépôt.
Ceux-ci sont téléchargés sous forme d'archives tar, plutôt que via Git. C'est souvent beaucoup plus rapide et utilise moins d'espace disque car cela ne nécessite pas de récupérer tout l'historique du dépôt. D'un autre côté, cela ne permet pas de récupération incrémentielle (mais les téléchargements complets sont souvent plus rapides que les récupérations incrémentielles !).
La syntaxe d'URL pour les flocons github est :
github:<owner>/<repo>(/<rev-or-ref>)?(\?<params>)?
<rev-or-ref> spécifie le nom d'une branche ou d'un tag (ref), ou un hachage de commit (rev). Notez que contrairement à Git, GitHub permet la récupération par hachage de commit sans spécifier de branche ou de tag.
Vous pouvez également spécifier host comme paramètre, pour pointer vers un serveur GitHub Enterprise personnalisé.
Quelques exemples :
  • github:edolstra/dwarffs
  • github:edolstra/dwarffs/unstable
  • github:edolstra/dwarffs/d3f2baba8f425779026c6ec04021b2e927f61e31
  • github:internal/project?host=company-github.example.org
•
gitlab : Similaire à github, c'est un moyen plus efficace de récupérer des dépôts GitLab. Les attributs suivants sont requis :
  • owner : Le propriétaire du dépôt.
  • repo : Le nom du dépôt.
Comme github, ceux-ci sont téléchargés sous forme d'archives tar.
La syntaxe d'URL pour les flocons gitlab est :
gitlab:<propriétaire>/<dépôt>(/<rév-ou-ref>)?(\?<params>)?
<rév-ou-ref> fonctionne de la même manière que github. Il peut s'agir du nom d'une branche ou d'une étiquette (ref), ou du hachage d'un commit (rev).
Comme GitLab permet l'auto-hébergement, vous pouvez spécifier host comme paramètre, pour pointer vers des instances autres que gitlab.com.
Quelques exemples :
  • gitlab:veloren/veloren
  • gitlab:veloren/veloren/master
  • gitlab:veloren/veloren/80a4d7f13492d916e47d6195be23acae8001985a
  • gitlab:openldap/openldap?host=git.openldap.org
Lorsque vous accédez à un dépôt dans un sous-groupe (imbriqué), assurez-vous d'encoder en URL les barres obliques, c'est-à-dire remplacez / par %2F :
•
gitlab:veloren%2Fdev/rfcs
•
sourcehut : Similaire à github, c'est un moyen plus efficace de récupérer les dépôts SourceHut. Les attributs suivants sont requis :
  • owner : Le propriétaire du dépôt (y compris le ~ initial).
  • repo : Le nom du dépôt.
Comme pour github, ceux-ci sont téléchargés sous forme d'archives tarball.
La syntaxe d'URL pour les flakes sourcehut est :
sourcehut:<propriétaire>/<dépôt>(/<rév-ou-ref>)?(\?<params>)?
<rév-ou-ref> fonctionne de la même manière que github. Il peut s'agir du nom d'une branche ou d'une étiquette (ref), ou du hachage d'un commit (rev).
Comme SourceHut permet l'auto-hébergement, vous pouvez spécifier host comme paramètre, pour pointer vers des instances autres que git.sr.ht.
Actuellement, la résolution des noms de ref ne fonctionne que pour les dépôts Git. Vous pouvez faire référence à des dépôts Mercurial en changeant simplement host en hg.sr.ht (ou toute autre instance Mercurial). À la condition que vous deviez spécifier explicitement un hachage de commit (rev).
Quelques exemples :
  • sourcehut:~misterio/nix-colors
  • sourcehut:~misterio/nix-colors/main
  • sourcehut:~misterio/nix-colors?host=git.example.org
  • sourcehut:~misterio/nix-colors/182b4b8709b8ffe4e9774a4c5d6877bf6bb9a21c
  • sourcehut:~misterio/nix-colors/21c1a380a6915d890d408e9f22203436a35bb2de?host=hg.sr.ht

Format des flakes

À titre d'exemple, voici un simple flake.nix qui dépend du flake Nixpkgs et fournit un seul paquet (c'est-à-dire une dérivation installable) :

{
  description = "Un flake pour construire Hello World";
  inputs.nixpkgs.url = "github:NixOS/nixpkgs/nixos-20.03";
  outputs = { self, nixpkgs }: {
    packages.x86_64-linux.default =
      # Remarquez la référence à nixpkgs ici.
      with import nixpkgs { system = "x86_64-linux"; };
      stdenv.mkDerivation {
        name = "hello";
        src = self;
        buildPhase = "gcc -o hello ./hello.c";
        installPhase = "mkdir -p $out/bin; install -t $out/bin hello";
      };
  };
}

Les attributs suivants sont pris en charge dans flake.nix :

  • description : Une description courte, sur une ligne, du flake.
  • inputs : Un attrset spécifiant les dépendances du flake (décrit ci-dessous).
  • outputs : Une fonction qui, étant donné un ensemble d'attributs contenant les sorties de chaque flake d'entrée indexé par son identifiant, produit les valeurs Nix fournies par ce flake. Ainsi, dans l'exemple ci-dessus, inputs.nixpkgs contient le résultat de l'appel à la fonction outputs du flake nixpkgs.
En plus des sorties de chaque entrée, chaque entrée dans inputs contient également des métadonnées sur les entrées. Ce sont :
  • outPath : Le chemin dans le magasin Nix de l'arborescence source du flake. De cette façon, l'ensemble d'attributs peut être passé à import comme s'il s'agissait d'un chemin, comme dans l'exemple ci-dessus (import nixpkgs).
  • rev : Le hachage du commit du dépôt du flake, le cas échéant.
  • revCount : Le nombre d'ancêtres de la révision rev. Ceci n'est pas disponible pour les dépôts github, car ils sont récupérés sous forme d'archives tarball plutôt que de dépôts Git.
  • lastModifiedDate : L'heure de commit de la révision rev, au format %Y%m%d%H%M%S (par exemple 20181231100934). Contrairement à revCount, ceci est disponible pour les dépôts Git et GitHub, il est donc utile pour générer des chaînes de version (espérons-le) monotones croissantes.
  • lastModified : L'heure de commit de la révision rev sous forme d'entier représentant le nombre de secondes depuis 1970.
  • narHash : Le SHA-256 (au format SRI) de la sérialisation d'archive Nix (NAR) de l'arborescence source du flake.
La valeur retournée par la fonction outputs doit être un ensemble d'attributs. Les attributs peuvent avoir des valeurs arbitraires ; cependant, divers sous-commandes de nix exigent que des attributs spécifiques aient une valeur spécifique (par exemple, packages.x86_64-linux doit être un ensemble d'attributs de dérivations construites pour la plateforme x86_64-linux).
•
nixConfig : Un ensemble d'options nix.conf à définir lors de l'évaluation de toute partie d'un flake. Pour des raisons de sécurité, seule une petite sélection d'options peut être définie sans confirmation tant que accept-flake-config n'est pas activé dans la configuration globale :
  • bash-prompt
  • bash-prompt-prefix
  • bash-prompt-suffix
  • flake-registry
  • commit-lock-file-summary

Entrées des flakes

L'attribut inputs spécifie les dépendances d'un flake, sous forme d'attrset mappant les noms d'entrée à des références de flake. Par exemple, ce qui suit spécifie une dépendance sur les dépôts nixpkgs et import-cargo :

# Un dépôt GitHub.
inputs.import-cargo = {
  type = "github";
  owner = "edolstra";
  repo = "import-cargo";
};
# Une indirection via le registre de flakes.
inputs.nixpkgs = {
  type = "indirect";
  id = "nixpkgs";
};

Alternativement, vous pouvez utiliser la syntaxe de type URL :

inputs.import-cargo.url = "github:edolstra/import-cargo";
inputs.nixpkgs.url = "nixpkgs";

Chaque entrée est récupérée, évaluée et passée à la fonction outputs sous forme d'un ensemble d'attributs portant le même nom que l'entrée correspondante. L'entrée spéciale nommée self fait référence aux sorties et à l'arborescence source de *ce* flake. Ainsi, une fonction outputs typique ressemble à ceci :

outputs = { self, nixpkgs, import-cargo }: {
  ... outputs ...
};

Il est également possible d'omettre complètement une entrée et de la lister *uniquement* comme argument de fonction attendu pour outputs. Ainsi,

outputs = { self, nixpkgs }: ...;

sans attribut inputs.nixpkgs est équivalent à

inputs.nixpkgs = {
  type = "indirect";
  id = "nixpkgs";
};

Les dépôts ne contenant pas de flake.nix peuvent également être utilisés comme entrées, en réglant l'attribut flake de l'entrée sur false :

inputs.grcov = {
  type = "github";
  owner = "mozilla";
  repo = "grcov";
  flake = false;
};
outputs = { self, nixpkgs, grcov }: {
  packages.x86_64-linux.grcov = stdenv.mkDerivation {
    src = grcov;
    ...
  };
};

Les entrées transitives peuvent être remplacées à partir d'un fichier flake.nix. Par exemple, ce qui suit remplace l'entrée nixpkgs de l'entrée nixops :

inputs.nixops.inputs.nixpkgs = {
  type = "github";
  owner = "my-org";
  repo = "nixpkgs";
};

Il est également possible "d'hériter" d'une entrée d'une autre entrée. Ceci est utile pour minimiser les dépendances des flakes. Par exemple, ce qui suit définit l'entrée nixpkgs du flake de niveau supérieur pour qu'elle soit égale à l'entrée nixpkgs de l'entrée dwarffs du flake de niveau supérieur :

inputs.nixpkgs.follows = "dwarffs/nixpkgs";

La valeur de l'attribut follows est une séquence de noms d'entrée séparés par des / indiquant le chemin des entrées à suivre depuis le flocon racine.

Les remplacements et follows peuvent être combinés, par exemple :

inputs.nixops.inputs.nixpkgs.follows = "dwarffs/nixpkgs";

définit l'entrée nixpkgs de nixops pour qu'elle soit la même que l'entrée nixpkgs de dwarffs. Il est cependant à noter qu'il est généralement inutile d'éliminer les entrées de flocon nixpkgs transitives de cette manière. La plupart des flocons fournissent leur fonctionnalité via des superpositions Nixpkgs ou des modules NixOS, qui sont composés dans l'entrée nixpkgs du flocon de niveau supérieur ; leur propre entrée nixpkgs est donc généralement sans importance.

Fichiers de verrouillage

Les entrées spécifiées dans flake.nix sont typiquement « non verrouillées » dans le sens où elles ne spécifient pas une révision exacte. Pour assurer la reproductibilité, Nix générera et utilisera automatiquement un *fichier de verrouillage* appelé flake.lock dans le répertoire du flocon. Le fichier de verrouillage contient une structure graphique isomorphe au graphe des dépendances du flocon racine. Chaque nœud du graphe (à l'exception du nœud racine) mappe les spécifications d'entrée (généralement non verrouillées) dans flake.nix à des spécifications d'entrée verrouillées. Chaque nœud contient également des métadonnées, telles que les dépendances (arêtes sortantes) du nœud.

Par exemple, si flake.nix a les entrées de l'exemple ci-dessus, le fichier de verrouillage résultant pourrait être :

{
  "version": 7,
  "root": "n1",
  "nodes": {
    "n1": {
      "inputs": {
        "nixpkgs": "n2",
        "import-cargo": "n3",
        "grcov": "n4"
      }
    },
    "n2": {
      "inputs": {},
      "locked": {
        "owner": "edolstra",
        "repo": "nixpkgs",
        "rev": "7f8d4b088e2df7fdb6b513bc2d6941f1d422a013",
        "type": "github",
        "lastModified": 1580555482,
        "narHash": "sha256-OnpEWzNxF/AU4KlqBXM2s5PWvfI5/BS6xQrPvkF5tO8="
      },
      "original": {
        "id": "nixpkgs",
        "type": "indirect"

Ce graphe comporte 4 nœuds : le flocon racine et ses 3 dépendances. Les nœuds ont des étiquettes arbitraires (par exemple, n1). L'étiquette du nœud racine du graphe est spécifiée par l'attribut root. Les nœuds contiennent les champs suivants :

  • inputs : Les dépendances de ce nœud, sous la forme d'une correspondance entre les noms d'entrée (par exemple, nixpkgs) et les étiquettes de nœud (par exemple, n2).
  • original : La spécification d'entrée d'origine de flake.lock, sous la forme d'un ensemble d'arguments de builtins.fetchTree.
  • locked : La spécification d'entrée verrouillée, sous la forme d'un ensemble d'arguments de builtins.fetchTree. Ainsi, dans l'exemple ci-dessus, lorsque nous construisons ce flocon, l'entrée nixpkgs est mappée à la révision 7f8d4b088e2df7fdb6b513bc2d6941f1d422a013 du dépôt edolstra/nixpkgs sur GitHub.
Il inclut également l'attribut narHash, spécifiant le contenu attendu de l'arbre dans le magasin Nix (calculé par nix hash-path), et peut inclure des attributs spécifiques au type d'entrée tels que lastModified ou revCount. La raison principale de ces attributs est de permettre la substitution des entrées de flocon à partir d'un cache binaire : narHash permet de calculer le chemin du magasin, tandis que les autres attributs sont nécessaires car ils fournissent des informations qui ne sont pas stockées dans le chemin du magasin.
•
flake : Un booléen indiquant s'il s'agit d'une dépendance de flocon ou non. Correspond à l'attribut flake dans l'attribut inputs de flake.nix.

Les attributs original et locked sont omis pour le nœud racine. En effet, nous ne pouvons pas enregistrer le hachage du commit ou le hachage du contenu du flocon racine, car la modification de flake.lock invaliderait ces derniers.

La représentation graphique des fichiers de verrouillage permet les dépendances circulaires entre les flocons. Par exemple, voici deux flocons qui se référencent mutuellement :

{
  inputs.b = ... emplacement du flocon B ...;
  # Indiquer au flocon 'b' de ne pas récupérer 'a' à nouveau, pour s'assurer que son 'a' est
  # bien *ce* 'a'.
  inputs.b.inputs.a.follows = "";
  outputs = { self, b }: {
    foo = 123 + b.bar;
    xyzzy = 1000;
  };
}

et

{
  inputs.a = ... emplacement du flocon A ...;
  inputs.a.inputs.b.follows = "";
  outputs = { self, a }: {
    bar = 456 + a.xyzzy;
  };
}

Les fichiers de verrouillage verrouillent transitivement les dépendances directes et indirectes. C'est-à-dire que si un fichier de verrouillage existe et est à jour, Nix ne consultera pas les fichiers de verrouillage des dépendances. Cependant, la génération du fichier de verrouillage elle-même *utilise* par défaut les fichiers de verrouillage des dépendances.

    Nom

    nix3-flake - Introduction aux flocons Nix

    Synopsis

    nix3-flake [OPTIONS...]

    Description

    Les flocons Nix sont un moyen expérimental d'organiser et de partager des configurations et des environnements Nix. Ils introduisent une structure reproductible pour les projets et les configurations système, en se basant sur des références vérifiables pour garantir la reproductibilité.

    Références des flocons

    Les flocons sont référencés par des chaînes de caractères spéciales qui indiquent leur emplacement et leur révision. Exemples :

    • flake:chemin/vers/le/flocon pour les flocons locaux.
    • github:utilisateur/repo pour les flocons sur GitHub.
    • git+https://... pour les dépôts Git.

    Format du flocon

    Un flocon est généralement un répertoire contenant un fichier flake.nix. Ce fichier définit les entrées et les sorties du flocon, telles que les paquets, les modules systèmes, ou les applications.

    Le fichier flake.nix utilise la syntaxe Nix et suit une structure spécifique, définissant des inputs (dépendances) et des outputs (ce que le flocon fournit).

    Fichiers de verrouillage

    Chaque flocon est associé à un fichier flake.lock. Ce fichier enregistre les révisions exactes de toutes les entrées du flocon, garantissant ainsi que le flocon sera construit de manière identique chaque fois qu'il sera utilisé, même si les entrées sont mises à jour.

    Options

    Cette commande peut accepter diverses options pour contrôler le comportement de Nix, bien que la commande nix3-flake elle-même soit plus une introduction conceptuelle qu'une commande d'exécution directe pour des tâches spécifiques. Les options typiques de Nix, telles que --option, --flake, etc., s'appliquent lorsque vous interagissez avec des flocons via d'autres commandes Nix comme nix build ou nix run.
