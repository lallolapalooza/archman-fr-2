nix-shell(1) Manuel des commandes générales nix-shell(1)

Nom

nix-shell - démarre un shell interactif basé sur une expression Nix

Synopsis

nix-shell [--arg nom valeur] [--argstr nom valeur] [{--attr | -A} cheminAttr] [--command cmd] [--run cmd] [--exclude regexp] [--pure] [--keep nom] {{--packages | -p} {paquets | expressions} … | [chemin]}

Désambiguïsation

Cette page de manuel décrit la commande nix-shell, qui est distincte de nix shell. Pour la documentation de cette dernière, exécutez nix shell --help ou consultez man nix3-shell.

Description

nix-shell construit les dépendances de la dérivation spécifiée, mais pas la dérivation elle-même. Elle démarre ensuite un shell interactif dans lequel toutes les variables d'environnement définies par la dérivation chemin ont été définies à leurs valeurs correspondantes, et le script $stdenv/setup a été sourcé. Ceci est utile pour reproduire l'environnement d'une dérivation pour le développement.

Si chemin n'est pas fourni, nix-shell utilise par défaut shell.nix s'il existe, et default.nix sinon.

Si chemin commence par http:// ou https://, il est interprété comme l'URL d'une archive tar qui sera téléchargée et décompressée dans un emplacement temporaire. L'archive tar doit inclure un seul répertoire de niveau supérieur contenant au moins un fichier nommé default.nix.

Si la dérivation définit la variable shellHook, elle sera exécutée après que $stdenv/setup ait été sourcé. Comme ce hook n'est pas exécuté par les constructions Nix classiques, il vous permet d'effectuer une initialisation spécifique à nix-shell. Par exemple, l'attribut de dérivation

shellHook =
  ''
    echo "Bonjour shell"
    export SOME_API_TOKEN="$(cat ~/.config/some-app/api-token)"
  '';

provoquera l'affichage de Bonjour shell par nix-shell et la définition de la variable d'environnement SOME_API_TOKEN à une valeur configurée par l'utilisateur.

Options

Toutes les options non listées ici sont passées à nix-store --realise, à l'exception de --arg et --attr / -A qui sont passées à nix-instantiate.

•
--command cmd
Dans l'environnement de la dérivation, exécute la commande shell cmd. Cette commande est exécutée dans un shell interactif. (Utilisez --run pour utiliser un shell non interactif à la place.) Cependant, un appel à exit est implicitement ajouté à la commande, de sorte que le shell se termine après l'exécution de la commande. Pour l'éviter, ajoutez return à la fin ; par exemple, --command "echo Bonjour; return" affichera Bonjour puis vous ramènera au shell interactif. Ceci peut être utile pour effectuer des initialisations supplémentaires.
•
--run cmd
Similaire à --command, mais exécute la commande dans un shell non interactif. Cela signifie (entre autres) qu'en cas d'appui sur Ctrl-C pendant l'exécution de la commande, le shell se termine.
•
--exclude regexp
Ne construit aucune dépendance dont le chemin de stockage correspond à l'expression régulière regexp. Cette option peut être spécifiée plusieurs fois.
•
--pure
Si ce drapeau est spécifié, l'environnement est presque entièrement effacé avant le démarrage du shell interactif, vous obtenez ainsi un environnement qui correspond davantage à la construction Nix “réelle”. Quelques variables, notamment HOME, USER et DISPLAY, sont conservées.
•
--packages / -p paquets…
Configure un environnement dans lequel les paquets spécifiés sont présents. Les arguments de la ligne de commande sont interprétés comme des noms d'attributs dans la collection Nix Packages. Ainsi, nix-shell --packages libjpeg openjdk démarrera un shell dans lequel les paquets désignés par les noms d'attributs libjpeg et openjdk sont présents.
•
-i interpreteur
L'interpréteur de script en chaîne à invoquer par nix-shell. Applicable uniquement dans les scripts #! (décrits ci-dessous).
•
--keep nom
Lorsqu'un shell --pure est démarré, conserve les variables d'environnement listées.

Options communes

La plupart des commandes Nix acceptent les options de ligne de commande suivantes :

•
--help
Affiche un résumé de la syntaxe de la commande et quitte.
•
--version
Affiche le numéro de version de Nix sur la sortie standard et quitte.
•
--verbose / -v
Augmente le niveau de verbosité des messages de diagnostic imprimés sur la sortie d'erreur standard. Pour chaque opération Nix, les informations imprimées sur la sortie standard sont bien définies ; toute information de diagnostic est imprimée sur la sortie d'erreur standard, jamais sur la sortie standard.
Cette option peut être spécifiée de manière répétée. Actuellement, les niveaux de verbosité suivants existent :
•
0 « Erreurs uniquement »
N'imprime que les messages expliquant pourquoi l'invocation Nix a échoué.
•
1 « Informatif »
Imprime des messages *utiles* sur ce que Nix fait. C'est la valeur par défaut.
•
2 « Bavard »
Imprime plus de messages informatifs.
•
3 « Verbeux »
Imprime encore plus de messages informatifs.
•
4 « Débogage »
Imprime des informations de débogage.
•
5 « Vomit »
Imprime une quantité énorme d'informations de débogage.
•
--quiet
Diminue le niveau de verbosité de

messages de diagnostic imprimés sur la sortie d'erreur standard. C'est l'option inverse de -v / --verbose.
Cette option peut être spécifiée plusieurs fois. Voir la liste des niveaux de verbosité précédents.
•
--log-format format
Cette option permet de modifier le format de sortie des logs, format étant l'un des suivants :
•
raw
C'est le format brut, tel que produit par nix-build.
•
internal-json
Affiche les logs de manière structurée.
Attention
Bien que le schéma lui-même soit relativement stable, le format des messages d'erreur (notamment du champ msg) peut changer entre les versions.
•
bar
Affiche uniquement une barre de progression pendant les constructions.
•
bar-with-logs
Affiche les logs bruts, avec la barre de progression en bas.
•
--no-build-output / -Q
Par défaut, la sortie écrite par les constructeurs sur la sortie standard et la sortie d'erreur standard est renvoyée sur la sortie d'erreur standard de la commande Nix. Cette option supprime ce comportement. Notez que la sortie standard et la sortie d'erreur du constructeur sont toujours écrites dans un fichier log dans prefix/nix/var/log/nix.
•
--max-jobs / -j nombre
Définit le nombre maximal de travaux de construction que Nix effectuera en parallèle au nombre spécifié. Spécifiez auto pour utiliser le nombre de cœurs CPU du système. La valeur par défaut est définie par le réglage de configuration max-jobs, qui est lui-même par défaut à 1. Une valeur plus élevée est utile sur les systèmes SMP ou pour exploiter la latence d'E/S.
Le régler à 0 interdit la construction sur la machine locale, ce qui est utile lorsque vous souhaitez que les constructions se déroulent uniquement sur des constructeurs distants.
•
--cores
Définit la valeur de la variable d'environnement NIX_BUILD_CORES lors de l'invocation des constructeurs. Les constructeurs peuvent utiliser cette variable à leur discrétion pour contrôler le parallélisme maximal. Par exemple, dans Nixpkgs, si l'attribut de dérivation enableParallelBuilding est défini sur true, le constructeur transmet l'indicateur -jN à GNU Make. Il prend par défaut la valeur du réglage de configuration cores, s'il est défini, ou 1 sinon. La valeur 0 signifie que le constructeur doit utiliser tous les cœurs CPU disponibles dans le système.
•
--max-silent-time
Définit le nombre maximum de secondes pendant lesquelles un constructeur peut rester sans produire de données sur la sortie standard ou la sortie d'erreur standard. La valeur par défaut est définie par le réglage de configuration max-silent-time. 0 signifie pas de délai d'attente.
•
--timeout
Définit le nombre maximum de secondes pendant lesquelles un constructeur peut s'exécuter. La valeur par défaut est définie par le réglage de configuration timeout. 0 signifie pas de délai d'attente.
•
--keep-going / -k
Continue en cas d'échecs de construction, dans la mesure du possible. C'est-à-dire, si la construction d'une entrée d'une dérivation échoue, Nix construira toujours les autres entrées, mais pas la dérivation elle-même. Sans cette option, Nix s'arrête si une construction échoue (sauf pour les constructions de substituts), tuant éventuellement les constructions en cours (en cas de constructions parallèles ou distribuées).
•
--keep-failed / -K
Spécifie qu'en cas d'échec de construction, le répertoire temporaire (généralement dans /tmp) dans lequel la construction a lieu ne doit pas être supprimé. Le chemin du répertoire de construction est affiché comme un message d'information.
•
--fallback
Chaque fois que Nix tente de construire une dérivation pour laquelle des substituts sont connus pour chaque chemin de sortie, mais que la réalisation des chemins de sortie via les substituts échoue, il se rabat sur la construction de la dérivation.
Le scénario le plus courant pour lequel cela est utile est lorsque nous avons enregistré des substituts afin d'effectuer une distribution binaire à partir d'un dépôt réseau, par exemple. Si le dépôt est en panne, la réalisation de la dérivation échouera. Lorsque cette option est spécifiée, Nix construira la dérivation à la place. Ainsi, l'installation à partir de binaires se rabat sur l'installation à partir des sources. Cette option n'est pas la valeur par défaut car il n'est généralement pas souhaitable qu'un échec transitoire dans l'obtention des substituts conduise à une construction complète à partir des sources (avec la consommation de ressources associée).
•
--readonly-mode
Lorsque cette option est utilisée, aucune tentative n'est faite pour ouvrir la base de données Nix. La plupart des opérations Nix nécessitent un accès à la base de données, donc ces opérations échoueront.
•
--arg nom valeur
Cette option est acceptée par nix-env, nix-instantiate, nix-shell et nix-build. Lors de l'évaluation des expressions Nix, l'évaluateur d'expressions tentera automatiquement d'appeler les fonctions qu'il rencontre. Il peut appeler automatiquement les fonctions pour lesquelles chaque argument a une valeur par défaut (par exemple, { argName ? defaultValue }: ...).
Avec --arg, vous pouvez également appeler des fonctions qui ont des arguments sans valeur par défaut (ou remplacer une valeur par défaut). C'est-à-dire, si l'évaluateur rencontre une fonction avec un argument nommé nom, il l'appellera avec la valeur valeur.
Par exemple, le default.nix de haut niveau dans Nixpkgs est en fait une fonction :
{ # Le système (par exemple, `i686-linux') pour lequel construire les paquets.
system ? builtins.currentSystem
...
}: ...
Ainsi, si vous appelez cette expression Nix (par exemple, lorsque vous faites nix-env --install --attr pkgname), la fonction sera appelée automatiquement en utilisant la valeur builtins.currentSystem pour l'argument system. Vous pouvez la remplacer en utilisant --arg, par exemple nix-env --install --attr pkgname --arg system \"i686-freebsd\". (Notez que comme l'argument est une chaîne littérale Nix, vous devez échapper les guillemets.)
•
--argstr nom valeur
Cette option est similaire à --arg, sauf que la valeur n'est pas une expression Nix mais une chaîne. Donc, au lieu de --arg system \"i686-linux\" (les guillemets extérieurs servent à conserver le shell) vous pouvez dire --argstr system i686-linux.
•
--attr / -A cheminAttr
Sélectionne un attribut de l'expression Nix de haut niveau en cours d'évaluation. (Seulement pour nix-env, nix-instantiate, nix-build et nix-shell.) Le chemin d'attribut cheminAttr est une séquence de noms d'attributs séparés par des points. Par exemple, étant donné une expression Nix de haut niveau e, le chemin d'attribut xorg.xorgserver entraînerait l'utilisation de l'expression e.xorg.xorgserver. Voir nix-env --install pour des exemples concrets.
En plus des noms d'attributs, vous pouvez également spécifier des indices de tableaux. Par exemple, le chemin d'attribut foo.3.bar sélectionne l'attribut bar du quatrième élément du tableau dans l'attribut foo de l'expression de haut niveau.
•
--expr / -E
Interprète les arguments de la ligne de commande comme une liste d'expressions Nix à analyser et évaluer, plutôt que comme une liste de noms de fichiers d'expressions Nix. (Seulement pour nix-instantiate, nix-build et nix-shell.)
Pour nix-shell, cette option est couramment utilisée pour vous donner un shell dans lequel vous pouvez construire les paquets retournés par l'expression. Si vous souhaitez obtenir un shell contenant les paquets *construits* prêts à l'emploi, donnez votre expression à l'indicateur de commodité nix-shell --packages à la place.
•
-I / --include chemin
Ajoute une entrée à la liste des chemins de recherche utilisés pour résoudre les chemins de recherche. Cette option peut être donnée plusieurs fois.
Les chemins ajoutés via -I ont la priorité sur le paramètre de configuration nix-path et la variable d'environnement NIX_PATH .
•
--option nom valeur
Définit l'option de configuration Nix nom sur valeur. Ceci remplace les paramètres du fichier de configuration Nix (voir nix.conf5).
•
--repair
Répare les chemins de magasin corrompus ou manquants en les redownloadant ou en les reconstruisant. Notez que cela est lent car cela nécessite de calculer un hachage cryptographique du contenu de chaque chemin dans la fermeture de la construction. Notez également l'avertissement sous nix-store --repair-path.

Note

Voir man nix.conf pour remplacer les paramètres de configuration avec des indicateurs de ligne de commande.

Variables d'environnement

•
NIX_BUILD_SHELL
Shell utilisé pour démarrer l'environnement interactif. Par défaut, le bash trouvé dans <nixpkgs>, se rabattant sur le bash trouvé dans PATH s'il n'est pas trouvé.

Variables d'environnement courantes

La plupart des commandes Nix interprètent les variables d'environnement suivantes :

•
IN_NIX_SHELL
Indicateur qui signale si l'environnement actuel a été configuré par nix-shell. Il peut avoir les valeurs pure ou impure.
•
NIX_PATH
Une liste d'entrées de chemins de recherche séparées par des deux-points, utilisée pour résoudre les chemins de recherche.
Cette variable d'environnement remplace la valeur du paramètre de configuration nix-path .
Elle peut être étendue en utilisant l'option -I .
Exemple
$ export NIX_PATH=`/home/eelco/Dev:nixos-config=/etc/nixos
Si NIX_PATH est défini sur une chaîne vide, la résolution des chemins de recherche échouera toujours.
Exemple
$ NIX_PATH= nix-instantiate --eval '<nixpkgs>'
error: file 'nixpkgs' was not found in the Nix search path (add it using $NIX_PATH or -I)
•
NIX_IGNORE_SYMLINK_STORE
Normalement, le répertoire du magasin Nix (typiquement /nix/store) n'est pas autorisé à contenir de composants de liens symboliques. Ceci afin d'éviter les constructions « impures ». Les constructeurs « canonicalisent » parfois les chemins en résolvant tous les composants de liens symboliques. Ainsi, les constructions sur différentes machines (avec /nix/store résolu vers des emplacements différents) pourraient produire des résultats différents. Ce n'est généralement pas un problème, sauf lorsque les constructions sont déployées sur des machines où /nix/store est résolu différemment. Si vous êtes sûr que vous n'allez pas faire cela, vous pouvez définir NIX_IGNORE_SYMLINK_STORE à 1.
Notez que si vous utilisez des liens symboliques vers le magasin Nix afin de le placer sur un autre système de fichiers que le système de fichiers racine, sous Linux, il est préférable d'utiliser des points de montage bind, par exemple :
$ mkdir /nix
$ mount -o bind /mnt/otherdisk/nix /nix
Consultez la page de manuel de mount 8 pour plus de détails.
•
NIX_STORE_DIR
Remplace l'emplacement du magasin Nix (par défaut prefix/store).
•
NIX_DATA_DIR
Remplace l'emplacement du répertoire de données statiques de Nix (par défaut prefix/share).
•
NIX_LOG_DIR
Remplace l'emplacement du répertoire de logs de Nix (par défaut prefix/var/log/nix).
•
NIX_STATE_DIR
Remplace l'emplacement du répertoire d'état de Nix (par défaut prefix/var/nix).
•
NIX_CONF_DIR
Remplace l'emplacement du répertoire de configuration système Nix (par défaut prefix/etc/nix).
•
NIX_CONFIG
Applique les paramètres de la configuration Nix à partir de l'environnement. Le contenu est traité comme s'il était lu à partir d'un fichier de configuration Nix. Les paramètres sont séparés par le caractère de nouvelle ligne.
•
NIX_USER_CONF_FILES
Remplace l'emplacement des fichiers de configuration utilisateur Nix à charger depuis.
Les valeurs par défaut sont les emplacements selon la Spécification des répertoires de base XDG . Voir la sous-section Répertoires de base XDG pour plus de détails.
La variable est traitée comme une liste séparée par le jeton :.
•
TMPDIR
Utilise le répertoire spécifié pour stocker les fichiers temporaires. En particulier, cela inclut les répertoires de construction temporaires ; ceux-ci peuvent occuper une quantité substantielle d'espace disque. La valeur par défaut est /tmp.
•
NIX_REMOTE
Cette variable doit être définie sur daemon si vous souhaitez utiliser le démon Nix pour exécuter les opérations Nix. Ceci est nécessaire dans les installations Nix multi-utilisateurs . Si le socket Unix du démon Nix se trouve à un chemin non standard, cette variable doit être définie sur unix://chemin/vers/socket. Sinon, elle doit être laissée non définie.
•
NIX_SHOW_STATS
Si défini sur 1, Nix affichera des statistiques d'évaluation, telles que le nombre de valeurs allouées.
•
NIX_COUNT_CALLS
Si défini sur 1, Nix affichera le nombre de fois que les fonctions ont été appelées pendant l'évaluation des expressions Nix. Ceci est utile pour profiler vos expressions Nix.
•
GC_INITIAL_HEAP_SIZE
Si Nix a été configuré pour utiliser le garbage collector de Boehm, cette variable définit la taille initiale du tas en octets. Elle est par défaut à 384 Mio. La définir sur une valeur faible réduit la consommation de mémoire, mais augmentera le temps d'exécution en raison de la surcharge de la collecte de garbage.

Répertoires de base XDG

Nix suit la Spécification des répertoires de base XDG .

Pour des raisons de compatibilité ascendante, les commandes Nix ne suivent la norme que lorsque use-xdg-base-directories est activé. Les nouvelles commandes Nix (expérimentales) respectent la norme par défaut.

Les variables d'environnement suivantes sont utilisées pour déterminer les emplacements des divers fichiers d'état et de configuration :

  • [XDG_CONFIG_HOME]{#env-XDGCONFIGHOME} (par défaut ~/.config)
  • [XDG_STATE_HOME]{#env-XDGSTATEHOME} (par défaut ~/.local/state)
  • [XDG_CACHE_HOME]{#env-XDGCACHEHOME} (par défaut ~/.cache)

Nom

nix-shell - Lance un shell avec les dépendances d'un paquet Nix

Synopsis

nix-shell [--arg nom valeur] [--argstr nom valeur] [--attr chemin] [-E expression] [-p paquets] [--packages paquets] [--pure] [--command commande] [--run commande] [--ix expression] [--expr expression] [-I chemin] [--show-trace] [--option nom valeur] [--help] [--version]

Désambiguïsation

Ceci est un manuel pour la commande nix-shell. Pour un shell interactif, voir nix-shell(1).

Description

La commande nix-shell crée un environnement interactif (shell) dans lequel les paquets spécifiés sont disponibles. Cela est utile pour construire des paquets, tester des configurations, ou simplement exécuter des programmes qui ont des dépendances spécifiques.

Options

Les options suivantes sont disponibles :

--arg nom valeur
Passe une valeur (de type Nix) à l'expression Nix chargée.
--argstr nom valeur
Passe une chaîne de caractères (de type Nix) à l'expression Nix chargée.
--attr chemin
Spécifie un attribut à extraire de l'expression Nix chargée. Utilisé pour sélectionner un paquet spécifique dans Nixpkgs.
-E, --expr expression
Charge une expression Nix directement depuis la ligne de commande. L'expression doit retourner un set de dérivation.
-p, --packages paquets
Spécifie une liste de paquets à inclure dans l'environnement du shell. Les paquets sont cherchés dans Nixpkgs. Cette option peut être répétée.
--pure
Crée un environnement « pur » en n'héritant d'aucune variable d'environnement de la part du shell parent, à l'exception de celles explicitement définies par Nix.
--command commande
Exécute une commande dans l'environnement créé par nix-shell, puis quitte. Ceci est utile pour l'automatisation.
--run commande
Similaire à --command, mais exécute la commande dans un shell interactif.
--ix expression
Utilise l'expression Nix spécifiée pour créer l'environnement. Ceci est une alternative à l'utilisation d'un chemin Nixpkgs et d'un attribut.
-I chemin
Ajoute un chemin au chemin de recherche de Nix. Utile pour spécifier une version différente de Nixpkgs.
--show-trace
Affiche la trace complète en cas d'erreur.
--option nom valeur
Définit une option de configuration Nix.
--help
Affiche l'aide et quitte.
--version
Affiche la version de Nix et quitte.

Options communes

Les options suivantes sont communes à de nombreuses commandes Nix :

--option nom valeur
Définit une option de configuration Nix (voir la configuration de Nix).
--show-trace
Affiche la trace complète en cas d'erreur.
--help
Affiche un message d'aide et quitte.
--version
Affiche la version de Nix et quitte.

Variables d'environnement

La commande nix-shell peut être influencée par certaines variables d'environnement, notamment :

NIX_PATH
Définit le chemin de recherche des magasins Nix, y compris Nixpkgs.
NIX_DEBUG
Active le débogage détaillé de Nix.
NIX_CORES
Définit le nombre de cœurs à utiliser pour les constructions parallèles.

Variables d'environnement communes

NIX_PATH, NIX_DEBUG, NIX_CORES.

Exemples

Pour construire les dépendances du paquet Pan, et démarrer un shell interactif dans lequel le construire :

$ nix-shell '<nixpkgs>' --attr pan
[nix-shell]$ eval ${unpackPhase:-unpackPhase}
[nix-shell]$ cd $sourceRoot
[nix-shell]$ eval ${patchPhase:-patchPhase}
[nix-shell]$ eval ${configurePhase:-configurePhase}
[nix-shell]$ eval ${buildPhase:-buildPhase}
[nix-shell]$ ./pan/gui/pan

La raison pour laquelle nous utilisons la forme eval ${configurePhase:-configurePhase} ici est que les paquets qui remplacent ces phases le font en exportant les valeurs remplacées dans la variable d'environnement du même nom. Ici, bash reçoit l'instruction d'évaluer soit le contenu de la variable ‘configurePhase’, si elle existe, soit la fonction configurePhase.

Pour effacer l'environnement d'abord, et effectuer une initialisation automatique supplémentaire du shell interactif :

$ nix-shell '<nixpkgs>' --attr pan --pure \
    --command 'export NIX_DEBUG=1; export NIX_CORES=8; return'

Les expressions Nix peuvent également être fournies en ligne de commande en utilisant les indicateurs -E et -p. Par exemple, ce qui suit démarre un shell contenant les paquets sqlite et libX11 :

$ nix-shell --expr 'with import <nixpkgs> { }; runCommand "dummy" { buildInputs = [ sqlite xorg.libX11 ]; } ""'

Une manière plus courte de faire la même chose est :

$ nix-shell --packages sqlite xorg.libX11
[nix-shell]$ echo $NIX_LDFLAGS
… -L/nix/store/j1zg5v…-sqlite-3.8.0.2/lib -L/nix/store/0gmcz9…-libX11-1.6.1/lib …

Notez que -p accepte plusieurs expressions Nix complètes valides dans le buildInputs = [ ... ] montré ci-dessus, pas seulement des noms de paquets. Donc, ce qui suit est également légal :

$ nix-shell --packages sqlite 'git.override { withManual = false; }'

L'indicateur -p recherche Nixpkgs dans le chemin de recherche Nix. Vous pouvez le remplacer en passant -I ou en définissant NIX_PATH. Par exemple, ce qui suit vous donne un shell contenant le paquet Pan d'une révision spécifique de Nixpkgs :

$ nix-shell --packages pan -I nixpkgs=https://github.com/NixOS/nixpkgs/archive/8a3eea054838b55aca962c3fbde9c83c102b8bf2.tar.gz
[nix-shell:~]$ pan --version
Pan 0.139

Utilisation comme interpréteur #!

Vous pouvez utiliser nix-shell comme interpréteur de script pour permettre aux scripts écrits dans des langages arbitraires d'obtenir leurs propres dépendances via Nix. Ceci est fait en démarrant le script avec les lignes suivantes :

#! /usr/bin/env nix-shell
#! nix-shell -i real-interpreter --packages packages

où real-interpreter est l'interpréteur de script « réel » qui sera invoqué par nix-shell après qu'il ait obtenu les dépendances et initialisé l'environnement, et packages sont les noms d'attributs des dépendances dans Nixpkgs.

Les lignes commençant par #! nix-shell spécifient les options de nix-shell (voir ci-dessus). Notez que vous ne pouvez pas écrire #! /usr/bin/env nix-shell -i ... car de nombreux systèmes d'exploitation n'autorisent qu'un seul argument dans les lignes #!.

Par exemple, voici un script Python qui dépend de Python et du paquet prettytable :

#! /usr/bin/env nix-shell
#! nix-shell -i python3 --packages python3 python3Packages.prettytable
import prettytable
# Affiche un tableau simple.
t = prettytable.PrettyTable(["N", "N^2"])
for n in range(1, 10): t.add_row([n, n * n])
print(t)

De même, voici un script Perl qui spécifie qu'il nécessite Perl et les paquets HTML::TokeParser::Simple et LWP :

#! /usr/bin/env nix-shell
#! nix-shell -i perl --packages perl perlPackages.HTMLTokeParserSimple perlPackages.LWP
use HTML::TokeParser::Simple;
# Récupère nixos.org et affiche tous les href.
my $p = HTML::TokeParser::Simple->new(url => 'http://nixos.org/');
while (my $token = $p->get_tag("a")) {
    my $href = $token->get_attr("href");
    print "$href\n" if $href;
}

Parfois, vous devez passer une expression Nix simple pour personnaliser un paquet comme Terraform :

#! /usr/bin/env nix-shell
#! nix-shell -i bash --packages 'terraform.withPlugins (plugins: [ plugins.openstack ])'
terraform apply

Note

Vous devez utiliser des guillemets simples ou doubles (', ") lorsque vous passez une expression Nix simple dans un shebang nix-shell.

Enfin, en utilisant la fusion de plusieurs shebangs nix-shell, le script Haskell suivant utilise une branche spécifique de Nixpkgs/NixOS (la branche stable 20.03) :

#! /usr/bin/env nix-shell
#! nix-shell -i runghc --packages 'haskellPackages.ghcWithPackages (ps: [ps.download-curl ps.tagsoup])'
#! nix-shell -I nixpkgs=https://github.com/NixOS/nixpkgs/archive/nixos-20.03.tar.gz
import Network.Curl.Download
import Text.HTML.TagSoup
import Data.Either
import Data.ByteString.Char8 (unpack)
-- Récupère nixos.org et affiche tous les href.
main = do
  resp <- openURI "https://nixos.org/"
  let tags = filter (isTagOpenName "a") $ parseTags $ unpack $ fromRight undefined resp
  let tags' = map (fromAttrib "href") tags
  mapM_ putStrLn $ filter (/= "") tags'

Si vous souhaitez être encore plus précis, vous pouvez spécifier une révision spécifique de Nixpkgs :

#! nix-shell -I nixpkgs=https://github.com/NixOS/nixpkgs/archive/0672315759b3e15e2121365f067c1c8c56bb4722.tar.gz

Les exemples ci-dessus ont tous utilisé -p pour obtenir les dépendances de Nixpkgs. Vous pouvez également utiliser une expression Nix pour construire vos propres dépendances. Par exemple, l'exemple Python aurait pu être écrit comme suit :

#! /usr/bin/env nix-shell
#! nix-shell deps.nix -i python

où le fichier deps.nix dans le même répertoire que le script #! contient :

with import <nixpkgs> {};
runCommand "dummy" { buildInputs = [ python pythonPackages.prettytable ]; } ""

Le nom de fichier du script est passé comme premier argument à l'interpréteur spécifié par l'indicateur -i.

En dehors de la toute première ligne, qui est une directive pour le système d'exploitation, les lignes supplémentaires #! nix-shell n'ont pas besoin d'être au début du fichier. Cela permet de les envelopper dans des commentaires de bloc pour les langages où # ne commence pas un commentaire, tels que ECMAScript, Erlang, PHP, ou Ruby.
