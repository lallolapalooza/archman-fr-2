nbd_block_status_64(3) LIBNBD nbd_block_status_64(3)

NOM

nbd_block_status_64 - envoie une commande de statut de bloc, avec rappel 64 bits

SYNTAXE

#include <libnbd.h>
typedef struct {
  int (*callback) (void *user_data,
                   const char *metacontext,
                   uint64_t offset, nbd_extent *entries,
                   size_t nr_entries, int *error);
  void *user_data;
  void (*free) (void *user_data);
} nbd_extent64_callback;
int nbd_block_status_64 (
      struct nbd_handle *h, uint64_t count,
      uint64_t offset,
      nbd_extent64_callback extent64_callback,
      uint32_t flags
    );

DESCRIPTION

Émet la commande de statut de bloc vers le serveur NBD. Si elle est prise en charge par le serveur, cela renvoie des informations de contexte de métadonnées sur les blocs à partir du décalage spécifié. Le paramètre "count" est une indication : le serveur peut choisir de renvoyer moins d'informations, ou le dernier bloc peut s'étendre au-delà de la plage demandée. Lorsque plusieurs contextes sont pris en charge, le nombre de blocs et la longueur cumulative de ces blocs ne doivent pas être identiques entre les contextes ; cette commande renvoie généralement le statut de tous les contextes négociés, tandis que certains serveurs prennent également en charge une requête filtrée (voir nbd_can_block_status_payload(3), nbd_block_status_filter(3)).

Notez que tous les serveurs ne peuvent pas prendre en charge un "count" de 4Gio ou plus ; nbd_get_extended_headers_negotiated(3) indique quels serveurs analyseront une requête supérieure à 32 bits. Le protocole NBD n'a pas encore de moyen pour un client de savoir si le serveur appliquera une taille maximale de statut de bloc encore plus petite, bien qu'une future extension puisse ajouter une contrainte visible dans nbd_get_block_size(3).

Selon les contextes de métadonnées qui ont été activés avant la connexion (voir nbd_add_meta_context(3)) et ceux pris en charge par le serveur (voir nbd_can_meta_context(3)), cet appel renvoie des informations sur les étendues en appelant la fonction "extent64". La fonction de rappel ne peut pas appeler les API "nbd_*" sur le même handle car elle détient le verrou du handle et provoquera un interblocage. Si la fonction de rappel renvoie -1, et qu'aucune erreur antérieure n'a été détectée, la commande de statut de bloc globale échouera avec toute valeur non nulle stockée dans le paramètre "error" de la fonction de rappel (avec une valeur par défaut de "EPROTO") ; mais tout contexte supplémentaire invoquera toujours la fonction de rappel.

La fonction "extent64" est appelée une fois par type de métadonnées disponibles, avec le "user_data" passé à cette fonction. Le paramètre "metacontext" est une chaîne telle que "base:allocation". Le tableau "entries" est un tableau de structures nbd_extent, contenant la longueur (en octets) du bloc et un champ de statut/indicateurs qui est spécifique au contexte de métadonnées. Le nombre d'entrées de tableau passées à la fonction est "nr_entries". Le document du protocole NBD dans la section concernant "NBD_REPLY_TYPE_BLOCK_STATUS" décrit la signification de ce tableau ; pour les contextes connus de libnbd, <libnbd.h> contient des constantes commençant par "LIBNBD_STATE_" qui peuvent aider à déchiffrer les valeurs. À l'entrée de la fonction de rappel, le paramètre "error" contient la valeur errno de toute erreur précédemment détectée.

Il est possible que la fonction d'extension soit appelée plus de fois que prévu (si le serveur est bogué), vérifiez donc toujours le champ "metacontext" pour vous assurer que vous recevez les données attendues. Il est également possible que la fonction d'extension ne soit pas appelée du tout, même pour des contextes de métadonnées que vous avez demandés. Cela indique soit que le serveur ne prend pas en charge le contexte, soit qu'il ne peut pour une autre raison pas renvoyer les données.

Le paramètre "flags" peut être 0 pour aucun drapeau, ou peut contenir "LIBNBD_CMD_FLAG_REQ_ONE" signifiant que le serveur doit renvoyer une seule extension par contexte de métadonnées où cette extension ne dépasse pas "count" octets ; cependant, libnbd ne valide pas que le serveur a respecté le drapeau.

Par défaut, libnbd rejettera les tentatives d'utilisation de cette fonction avec des paramètres susceptibles d'entraîner une défaillance du serveur, telles que la demande d'un drapeau de commande inconnu. La fonction nbd_set_strict_mode(3) peut être utilisée pour modifier les scénarios qui doivent attendre une réponse du serveur plutôt que d'échouer rapidement.

VALEUR DE RETOUR

Si l'appel réussit, la fonction renvoie 0.

ERREURS

En cas d'erreur, -1 est renvoyé.

Consultez « GESTION DES ERREURS » dans libnbd(3) pour savoir comment obtenir plus de détails sur l'erreur.

Les paramètres suivants ne doivent pas être NULL : "h". Pour plus d'informations, voir « Paramètres non NULL » dans libnbd(3).

ÉTAT DU HANDLE

nbd_block_status_64 peut être appelé lorsque le handle est dans l'état suivant :

┌─────────────────────────────────────┬─────────────────────────┐
│ Handle créé, avant la connexion   │ ❌ erreur                │
│ Connexion en cours                    │ ❌ erreur                │
│ Connexion & handshake (opt_mode) │ ❌ erreur                │
│ Connecté au serveur               │ ✅ autorisé             │
│ Connexion fermée                  │ ❌ erreur                │
│ Handle mort                        │ ❌ erreur                │
└─────────────────────────────────────┴─────────────────────────┘

VERSION

Cette fonction est apparue pour la première fois dans libnbd 1.18.

Si vous avez besoin de tester si cette fonction est disponible au moment de la compilation, vérifiez si la macro suivante est définie :

#define LIBNBD_HAVE_NBD_BLOCK_STATUS_64 1
