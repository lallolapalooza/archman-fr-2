NOM

nft - Outil d'administration du framework nftables pour le filtrage et la classification de paquets

SYNOPIS

nft [ -nNscaeSupyjtT ] [ -I répertoire ] [ -f fichier | -i | commande ...]
nft -h
nft -v

DESCRIPTION

nft est l'outil en ligne de commande utilisé pour configurer, maintenir et inspecter les règles de filtrage et de classification de paquets dans le noyau Linux, dans le framework nftables. Le sous-système du noyau Linux est connu sous le nom de nf_tables, et 'nf' signifie Netfilter.

OPTIONS

La commande accepte plusieurs options différentes qui sont documentées ici par groupes pour une meilleure compréhension de leur signification. Vous pouvez obtenir des informations sur les options en exécutant nft --help.

Options générales :

-h, --help

Afficher le message d'aide et toutes les options.

-v, --version

Afficher la version.

-V

Afficher des informations détaillées sur la version, y compris la configuration à la compilation.

Options de gestion des entrées de règles qui spécifient comment charger les ensembles de règles :

-f, --file fichier

Lire l'entrée depuis le fichier. Si fichier est -, lire depuis stdin. Le chemin du répertoire de ce fichier est inséré au début de la liste des répertoires à rechercher pour les fichiers inclus (voir -I/--includepath).

-D, --define nom=valeur

Définir une variable. Vous ne pouvez combiner cette option qu'avec -f.

-i, --interactive

Lire l'entrée depuis une interface utilisateur graphique interactive readline. Vous pouvez utiliser quit pour quitter, ou utiliser le marqueur EOF, normalement CTRL-D.

-I, --includepath répertoire

Ajouter le répertoire répertoire à la liste des répertoires à rechercher pour les fichiers inclus. Cette option peut être spécifiée plusieurs fois.

-c, --check

Vérifier la validité des commandes sans appliquer réellement les modifications.

-o, --optimize

Optimiser votre ensemble de règles. Vous pouvez combiner cette option avec -c pour inspecter les optimisations proposées.

Options de formatage de la sortie des ensembles de règles qui modifient la sortie de la commande list règles :

-a, --handle

Afficher les identificateurs d'objets dans la sortie.

-s, --stateless

Omettre les informations d'état des règles et des objets d'état.

-t, --terse

Omettre le contenu des ensembles de la sortie.

-S, --service

Traduire les ports en noms de service tels que définis par /etc/services.

-N, --reversedns

Traduire les adresses IP en noms via une recherche DNS inversée. Cela peut ralentir votre liste car cela génère du trafic réseau.

-u, --guid

Traduire les UID/GID numériques en noms tels que définis par /etc/passwd et /etc/group.

-n, --numeric

Afficher une sortie entièrement numérique.

-y, --numeric-priority

Afficher la priorité de la chaîne de base numériquement.

-p, --numeric-protocol

Afficher le protocole de couche 4 numériquement.

-T, --numeric-time

Afficher les valeurs de temps, jour et heure au format numérique.

Formatage de la sortie des commandes :

-e, --echo

Lors de l'insertion d'éléments dans l'ensemble de règles à l'aide des commandes add, insert ou replace, afficher des notifications comme nft monitor.

-j, --json

Formater la sortie en JSON. Voir libnftables-json(5) pour une description du schéma.

-d, --debug niveau

Activer la sortie de débogage. Le niveau de débogage peut être l'un des suivants : scanner, parser, eval, netlink, mnl, proto-ctx, segtree, all. Vous pouvez en combiner plusieurs en les séparant par le symbole ,, par exemple -d eval,mnl.

FORMATS DES FICHIERS D'ENTRÉE

CONVENTIONS LEXICALES

L'entrée est analysée ligne par ligne. Lorsque le dernier caractère d'une ligne, juste avant le caractère de nouvelle ligne, est une barre oblique inverse (\) non citée, la ligne suivante est traitée comme une continuation. Plusieurs commandes sur la même ligne peuvent être séparées par un point-virgule (;).

Un signe dièse (#) commence un commentaire. Tous les caractères suivants sur la même ligne sont ignorés.

Les identificateurs commencent par un caractère alphabétique (a-z, A-Z), suivi de zéro ou plusieurs caractères alphanumériques (a-z, A-Z, 0-9) et des caractères slash (/), barre oblique inverse (\), underscore (_) et point (.). Les identificateurs utilisant des caractères différents ou entrant en conflit avec un mot-clé doivent être entourés de guillemets doubles (").

FICHIERS INCLUS

include fichier

D'autres fichiers peuvent être inclus en utilisant l'instruction include. Les répertoires à rechercher pour les fichiers inclus peuvent être spécifiés en utilisant l'option -I/--includepath. Vous pouvez outrepasser ce comportement soit en préfixant votre chemin par ‘./’ pour forcer l'inclusion de fichiers situés dans le répertoire de travail courant (c'est-à-dire un chemin relatif), soit par / pour un emplacement de fichier exprimé comme un chemin absolu.

Si -I/--includepath n'est pas spécifié, alors nft utilise le répertoire par défaut spécifié lors de la compilation. Vous pouvez récupérer ce répertoire par défaut via l'option -h/--help.

Les instructions d'inclusion prennent en charge les symboles génériques habituels du shell (, ?, []). L'absence de correspondance pour une instruction d'inclusion n'est pas une erreur, si des symboles génériques sont utilisés dans l'instruction d'inclusion. Cela permet d'avoir des répertoires d'inclusion potentiellement vides pour des instructions telles queinclude "/etc/firewall/rules/". Les correspondances génériques sont chargées par ordre alphabétique. Les fichiers commençant par un point (.) ne sont pas mis en correspondance par les instructions d'inclusion.

VARIABLES SYMBOLiques

define variable = expression
undefine variable
redefine variable = expression
$variable

Les variables symboliques peuvent être définies à l'aide de l'instruction define. Les références de variables sont des expressions et peuvent être utilisées pour initialiser d'autres variables. La portée d'une définition est le bloc courant et tous les blocs qu'il contient. Les variables symboliques peuvent être annulées à l'aide de l'instruction undefine et modifiées à l'aide de l'instruction redefine.

Utilisation des variables symboliques.

define int_if1 = eth0
define int_if2 = eth1
define int_ifs = { $int_if1, $int_if2 }
redefine int_if2 = wlan0
undefine int_if2
filter input iif $int_ifs accept

FAMILLES D'ADRESSES

Les familles d'adresses déterminent le type de paquets qui sont traités. Pour chaque famille d'adresses, le noyau contient des points d'accroche (hooks) à des étapes spécifiques des chemins de traitement des paquets, qui invoquent nftables s'il existe des règles pour ces points d'accroche.

Tous les objets nftables existent dans des espaces de noms spécifiques aux familles d'adresses, par conséquent, tous les identifiants incluent une famille d'adresses. Si un identifiant est spécifié sans famille d'adresses, la famille ip est utilisée par défaut.

Familles d'adresses IPV4/IPV6/INET

Les familles d'adresses IPv4/IPv6/Inet traitent les paquets IPv4, IPv6 ou les deux types de paquets. Elles contiennent cinq points d'accroche à différents stades de traitement des paquets dans la pile réseau.

arp Famille d'adresses ARP, gérant les paquets ARP IPv4.
bridge Famille d'adresses Bridge, gérant les paquets qui traversent un périphérique de pont.
netdev Famille d'adresses Netdev, gérant les p
Point d'accroche Description
prerouting Tous les paquets entrant dans le système sont traités par le point d'accroche prerouting. Il est invoqué avant le processus de routage et est utilisé pour le filtrage précoce ou la modification des attributs des paquets qui affectent le routage.
input Les paquets livrés au système local sont traités par le point d'accroche input.

L'entrée (ingress) n'est disponible que pour la famille Inet (depuis le noyau Linux 5.10).

Famille d'adresse ARP

La famille d'adresses ARP traite les paquets ARP reçus et envoyés par le système. Elle est couramment utilisée pour manipuler les paquets ARP à des fins de clustering.

Tableau 2. Points d'accroche de la famille d'adresses ARP

Point d'accroche Description
input Les paquets livrés au système local sont traités par le point d'accroche input.
output Les paquets envoyés par le système local sont traités par le point d'accroche output.

Famille d'adresse BRIDGE

La famille d'adresses bridge traite les paquets Ethernet traversant les périphériques de pont.

La liste des points d'accroche pris en charge est identique à celle des familles d'adresses IPv4/IPv6/Inet ci-dessus.

Famille d'adresse NETDEV

La famille d'adresses Netdev traite les paquets provenant du chemin d'entrée et de sortie des périphériques. Cette famille vous permet de filtrer des paquets de n'importe quel ethertype tels que ARP, VLAN 802.1q, VLAN 802.1ad (Q-in-Q) ainsi que des paquets IPv4 et IPv6.

Tableau 3. Points d'accroche de la famille d'adresses Netdev

Point d'accroche Description
ingress Tous les paquets entrant dans le système sont traités par ce point d'accroche. Il est invoqué après les taps réseau (c'est-à-dire tcpdump), juste après l'entrée tc et avant les gestionnaires de protocoles de couche 3, il peut être utilisé pour le filtrage et le contrôle de flux précoces.
egress Tous les paquets quittant le système sont traités par ce point d'accroche. Il est invoqué après les gestionnaires de protocoles de couche 3 et avant la sortie tc. Il peut être utilisé pour le filtrage et le contrôle de flux tardifs.

Les paquets tunnelisés (tels que vxlan) sont traités par les points d'accroche de la famille netdev à la fois sous forme décapsulée et encapsulée (tunnelisée). Ainsi, un paquet peut être filtré sur le réseau de superposition ainsi que sur le réseau sous-jacent.

Notez que l'ordre de netfilter et de tc est inversé pour l'entrée par rapport à la sortie. Cela garantit la symétrie pour NAT et d'autres manipulations de paquets.

Les paquets d'entrée qui sont redirigés vers une autre interface ne sont traités par netfilter en sortie que s'ils ont déjà été traités par netfilter en entrée. Ainsi, les paquets d'entrée qui sont redirigés par tc ne sont pas soumis à netfilter. Mais ils le sont s'ils sont redirigés par netfilter en entrée. Conceptuellement, tc et netfilter peuvent être considérés comme des couches, netfilter étant superposé à tc : Si le paquet n'a pas été transmis de la couche tc à la couche netfilter, il n'est pas soumis à netfilter en sortie.

ENSEMBLE DE REGLES

{list | flush} ruleset [famille]

Le mot-clé ruleset est utilisé pour identifier l'ensemble des tables, chaînes, etc. actuellement en place dans le noyau. Les commandes ruleset suivantes existent :

list Affiche l'ensemble de règles dans un format lisible par l'homme.
flush Efface l'ensemble de règles. Notez que, contrairement à iptables, cela supprimera toutes les tables et leur contenu, conduisant effectivement à un ensemble de règles vide - aucun filtrage de paquet ne se produira plus, le noyau acceptera donc tout paquet valide qu'il reçoit.

Il est possible de limiter list et flush à une seule famille d'adresses. Pour une liste des noms de familles valides, voir la section appelée « FAMILLES D'ADRESSES » ci-dessus.

Par conception, la sortie de la commande list ruleset peut être utilisée comme entrée pour nft -f. Effectivement, c'est l'équivalent nft de iptables-save et iptables-restore.

TABLES

{add | create} table [famille] table [{ [comment commentaire ;] [flags drapeaux ;] }]
{delete | destroy | list | flush} table [famille] table
list tables [famille]
delete table [famille] handle handle
destroy table [famille] handle handle

Les tables sont des conteneurs pour les chaînes, les ensembles et les objets stateful. Elles sont identifiées par leur famille d'adresses et leur nom. La famille d'adresses doit être l'une des suivantes : ip, ip6, inet, arp, bridge, netdev. La famille d'adresses inet est une famille fictive utilisée pour créer des tables hybrides IPv4/IPv6. Le mot-clé d'expression meta nfproto peut être utilisé pour tester dans quel contexte familial (ipv4 ou ipv6) le paquet est en cours de traitement. Lorsqu'aucune famille d'adresses n'est spécifiée, ip est utilisée par défaut. La seule différence entre add et create est que la première ne renverra pas d'erreur si la table spécifiée existe déjà, tandis que create renverra une erreur.

Tableau 4. Drapeaux de table

Drapeau Description
dormant la table n'est plus évaluée (les chaînes de base sont désenregistrées).
owner la table appartient au processus créateur.
persist la table survivra au processus propriétaire.

La création d'une table avec le drapeau owner exclut les autres processus de sa manipulation ou de celle de son contenu. Par défaut, elle sera supprimée à la sortie du processus. La définition du drapeau persist empêchera cela et la table orpheline résultante acceptera un nouveau propriétaire, par exemple un démon redémarrant maintenant la table.

Ajouter, modifier, supprimer une table.

# démarrer nft en mode interactif
nft --interactive
# créer une nouvelle table.
create table inet mytable
# ajouter une nouvelle chaîne de base : recevoir les paquets d'entrée
add chain inet mytable myin { type filter hook input priority filter; }
# ajouter un compteur unique à la chaîne
add rule inet mytable myin counter
# désactiver temporairement la table -- les règles ne sont plus évaluées
add table inet mytable { flags dormant; }
# rendre la table active à nouveau :
add table inet mytable
add Ajoute une nouvelle table pour la famille donnée avec le nom donné.
delete Supprime la table spécifiée.
destroy Supprime la table spécifiée, elle ne retourne pas d'erreur si elle n'existe pas.
list Liste toutes les chaînes et règles de la table spécifiée.
flush Vide toutes les chaînes et règles de la table spécifiée.

CHAÎNES

{add | create} chain [famille] table chaîne [{ type type hook point d'accroche [device périphérique] priority priorité ; [policy politique ;] [comment commentaire ;] }]
{delete | destroy | list | flush} chain [famille] table chaîne
list chains [famille]
delete chain [famille] table handle handle
destroy chain [famille] table handle
handle renommer chaîne [famille] table chaîne nouveau_nom

Les chaînes sont des conteneurs pour les règles. Elles existent en deux types, chaînes de base et chaînes régulières. Une chaîne de base est un point d'entrée pour les paquets provenant de la pile réseau, une chaîne régulière peut être utilisée comme cible de saut et sert à une meilleure organisation des règles. Les chaînes régulières peuvent être anonymes, voir les exemples de VERDICT STATEMENT pour plus de détails.

ajouter Ajouter une nouvelle chaîne dans la table spécifiée. Lorsque un crochet et une valeur de priorité sont spécifiés, la chaîne est créée comme une chaîne de base et accrochée à la pile réseau.
créer Similaire à la commande ajouter, mais renvoie une erreur si la chaîne existe déjà.
supprimer Supprimer la chaîne spécifiée. La chaîne ne doit pas contenir de règles ou être utilisée comme cible de saut.
détruire Supprimer la chaîne spécifiée, elle ne échoue pas si elle n'existe pas. La chaîne ne doit pas contenir de règles ou être utilisée comme cible de saut.
renommer Renommer la chaîne spécifiée.
lister Lister toutes les règles de la chaîne spécifiée.
vider Vider toutes les règles de la chaîne spécifiée.

Pour les chaînes de base, les paramètres type, hook et priority sont obligatoires.

Tableau 5. Types de chaînes pris en charge

Type Familles Crochets Description
filter toutes tous Type de chaîne standard à utiliser en cas de doute.
nat ip, ip6, inet prerouting, input, output, postrouting Les chaînes de ce type effectuent la traduction d'adresses natives (NAT) basée sur les entrées conntrack. Seul le premier paquet d'une connexion traverse réellement cette chaîne - ses règles définissent généralement les détails de l'entrée conntrack créée (instructions NAT par exemple).
route ip, ip6, inet output Si un paquet a traversé une chaîne de ce type et est sur le point d'être accepté, une nouvelle recherche de route est effectuée si des parties pertinentes de l'en-tête IP ont été modifiées. Cela permet par exemple d'implémenter des sélecteurs de routage politique dans nftables.

Outre les cas spéciaux illustrés ci-dessus (par exemple, le type nat ne prenant pas en charge le crochet forward ou le type route ne prenant en charge que le crochet output), il y a trois autres particularités à noter :

•La famille netdev ne prend en charge que deux combinaisons, à savoir le type filter avec le crochet ingress et le type filter avec le crochet egress. Les chaînes de base de cette famille nécessitent également que le paramètre device soit présent car elles existent par interface uniquement.
•La famille arp ne prend en charge que les crochets input et output, tous deux dans des chaînes de type filter.
•La famille inet prend également en charge le crochet ingress (depuis le noyau Linux 5.10), pour filtrer les paquets IPv4 et IPv6 au même endroit que le crochet ingress de netdev. Ce crochet inet permet de partager des ensembles et des cartes entre les crochets habituels prerouting, input, forward, output, postrouting et ce crochet ingress.

Le paramètre device accepte le nom d'une interface réseau sous forme de chaîne de caractères, et est requis lors de l'ajout d'une chaîne de base qui filtre le trafic sur les crochets ingress ou egress. Toutes les chaînes ingress ou egress ne filtreront que le trafic de l'interface spécifiée dans le paramètre device.

Le paramètre priority accepte une valeur entière signée ou un nom de priorité standard qui spécifie l'ordre dans lequel les chaînes ayant la même valeur de hook sont parcourues. L'ordre est croissant, c'est-à-dire que les valeurs de priorité inférieures ont la préséance sur les valeurs supérieures.

Avec les chaînes de type nat, il existe une limite inférieure d'exclusion de -200 pour les valeurs de priority, car les crochets conntrack à cette priorité et le NAT l'exigent.

Les noms de priorité standard peuvent être remplacés par des noms faciles à mémoriser. Tous les noms n'ont pas de sens dans toutes les familles avec tous les crochets (voir les matrices de compatibilité ci-dessous), mais leur valeur numérique peut toujours être utilisée pour prioriser les chaînes.

Ces noms et valeurs sont définis et rendus disponibles en fonction des priorités utilisées par xtables lors de l'enregistrement de leurs chaînes par défaut.

La plupart des familles utilisent les mêmes valeurs, mais bridge en utilise de différentes des autres. Voir les tableaux suivants qui décrivent les valeurs et la compatibilité.

Les valeurs seront également imprimées de cette manière tant que la valeur n'est pas plus éloignée que 10 de la valeur standard.

Les chaînes de base permettent également de définir la politique de la chaîne, c'est-à-dire ce qui arrive aux paquets qui ne sont pas explicitement acceptés ou refusés dans les règles contenues. Les valeurs de politique prises en charge sont accept (qui est la valeur par défaut) ou drop.

RÈGLES

{ajouter | insérer} règle [famille] table chaîne [handle handle | index index] statement ... [comment comment]
remplacer règle [famille] table chaîne handle handle statement ... [comment comment]
{supprimer | réinitialiser} règle [famille] table chaîne handle handle
détruire règle [famille] table chaîne handle handle
réinitialiser règles [famille] [table [chaîne]]

Les règles sont ajoutées aux chaînes dans la table donnée. Si la famille n'est pas spécifiée, la famille ip est utilisée. Les règles sont construites à partir de deux types de composants selon un ensemble de règles grammaticales : expressions et instructions.

Les commandes ajouter et insérer prennent en charge un spécificateur de position optionnel, qui est soit un handle soit l'index (commençant à zéro) d'une règle existante. En interne, les positions des règles sont toujours identifiées par un handle et la traduction de l'index se fait dans l'espace utilisateur. Cela peut avoir deux implications en cas de modification concurrente des règles après la traduction : L'index de règle effectif peut changer si une règle a été insérée ou supprimée avant celle à laquelle il est fait référence. Si la règle référencée a été supprimée, la commande est rejetée par le noyau, comme si un handle invalide avait été donné.

Un comment est un seul mot ou une chaîne de plusieurs mots entre guillemets doubles (") qui peut être utilisée pour prendre des notes concernant la règle réelle. Note : Si vous utilisez bash pour ajouter des règles, vous devez échapper les guillemets, par exemple \"activer le ssh pour les serveurs\".

ajouter Ajouter une nouvelle règle décrite par la liste d'instructions. La règle est ajoutée à la fin de la chaîne donnée sauf si une position est spécifiée, auquel cas la règle est insérée après la règle spécifiée.
insérer Identique à ajouter sauf que la règle est insérée au début de la chaîne ou avant la règle spécifiée.
remplacer Similaire à ajouter, mais la ru
le remplace la règle spécifiée. delete Supprime la règle spécifiée. destroy Supprime la règle spécifiée, ne génère pas d'erreur si elle n'existe pas. reset Réinitialise l'état contenu dans la règle, par exemple les valeurs des compteurs et des quotas.

Ajoute une règle à la chaîne de sortie de la table ip.

nft add rule filter output ip daddr 192.168.0.0/24 accept # 'ip filter' est supposé
# même commande, légèrement plus verbeuse
nft add rule ip filter output ip daddr 192.168.0.0/24 accept

Supprime une règle de la table inet.

# nft -a list ruleset
table inet filter {
        chain input {
                type filter hook input priority filter; policy accept;
                ct state established,related accept # handle 4
                ip saddr 10.1.1.1 tcp dport ssh accept # handle 5
          ...
# supprime la règle avec le handle 5
nft delete rule inet filter input handle 5

SETS

Nftables offre deux types de concepts de set. Les sets anonymes sont des sets qui n'ont pas de nom spécifique. Les membres du set sont délimités par des accolades, avec des virgules pour séparer les éléments lors de la création de la règle dans laquelle le set est utilisé. Une fois cette règle supprimée, le set est également supprimé. Ils ne peuvent pas être mis à jour, c'est-à-dire qu'une fois qu'un set anonyme est déclaré, il ne peut plus être modifié, sauf en supprimant/modifiant la règle qui utilise le set anonyme.

Utilisation de sets anonymes pour accepter des sous-réseaux et des ports particuliers.

nft add rule filter input ip saddr { 10.0.0.0/8, 192.168.0.0/16 } tcp dport { 22, 443 } accept

Les sets nommés sont des sets qui doivent être définis avant de pouvoir être référencés dans les règles. Contrairement aux sets anonymes, les éléments peuvent être ajoutés ou supprimés d'un set nommé à tout moment. Les sets sont référencés depuis les règles en utilisant un @ préfixé au nom du set.

Utilisation de sets nommés pour accepter des adresses et des ports.

nft add rule filter input ip saddr @allowed_hosts tcp dport @allowed_ports accept

Les sets allowed_hosts et allowed_ports doivent être créés au préalable. La section suivante décrit la syntaxe des sets nft plus en détail.

add set [family] table set { type type | typeof expression ; [flags flags ;] [timeout timeout ;] [gc-interval gc-interval ;] [elements = { element[, ...] } ;] [size size ;] [comment comment ;] [policy 'policy ;] [auto-merge ;] }
{delete | destroy | list | flush | reset } set [family] table set

Le gc-interval n'affecte pas le timeout des éléments, mais il affecte la récupération de mémoire. Un grand set dont les éléments expirent rarement peut utiliser un ramasse-miettes plus fréquent (moins fréquent) pour économiser du temps CPU, tandis que les sets qui voient de nombreuses mises à jour avec des éléments de courte durée bénéficieront d'un intervalle plus faible. Des intervalles plus faibles garantissent que le set reste en dessous de sa taille maximale. En interne, une entrée expirée reste jusqu'à ce qu'elle soit supprimée par le ramasse-miettes, ce qui décrémente également le nombre d'éléments du set. Cela signifie également qu'il est possible qu'un set ne puisse plus accepter d'éléments, même si tous les éléments ont expiré, si le gc-interval est réglé trop haut.

La size définit la limite supérieure de la quantité d'éléments que le set peut supporter. Obligatoire pour les sets qui sont alimentés depuis le ruleset avec les mots-clés add et update. La fourniture du mot-clé size pour les sets qui ne sont alimentés que via nft add element permet une sélection d'implémentation de set plus compacte (économisant de la mémoire), mais ce n'est pas obligatoire.

Le mot-clé optionnel policy peut être utilisé pour demander une implémentation de set plus économe en mémoire.

auto-merge demande au frontend nftables de fusionner les intervalles adjacents et chevauchants. Exemple : Lorsque le set contient l'intervalle 1.2.3.1-1.2.3.4, l'ajout de l'élément 1.2.3.2 n'a aucun effet. L'ajout de 1.2.3.5 modifie l'intervalle existant pour couvrir 1.2.3.1-1.2.3.5. Sans ce flag, 1.2.3.2 ne peut pas être ajouté et 1.2.3.5 est inséré comme une nouvelle entrée.

TABLES DE FLUX

{add | create} flowtable [famille] table flowtable { hook hook priority priority ; devices = { device[, ...] } ; }

{delete | destroy | list} flowtable [famille] table flowtable

Les tables de flux vous permettent d'accélérer le transfert de paquets en logiciel. Les entrées des tables de flux sont représentées par un tuple composé de l'interface d'entrée, de l'adresse source et destination, du port source et destination ; et des protocoles de couche 3/4. Chaque entrée met en cache également l'interface de destination et l'adresse de passerelle - pour mettre à jour l'adresse de liaison de destination - afin de transférer les paquets. Les champs ttl et hoplimit sont également décrémentés. Par conséquent, les tables de flux fournissent un chemin alternatif qui permet aux paquets de contourner le chemin de transfert classique. Les tables de flux résident dans le hook d'entrée (ingress) qui est situé avant le hook de prerouting. Vous pouvez sélectionner les flux que vous souhaitez décharger via l'expression de flux de la chaîne forward. Les tables de flux sont identifiées par leur famille d'adresses et leur nom. La famille d'adresses doit être l'une des ip, ip6, ou inet. La famille d'adresses inet est une famille fictive utilisée pour créer des tables hybrides IPv4/IPv6. Lorsqu'aucune famille d'adresses n'est spécifiée, ip est utilisé par défaut.

La priority peut être un entier signé ou filter qui représente 0. L'addition et la soustraction peuvent être utilisées pour définir une priorité relative, par exemple filter + 5 est égal à 5.

delete Supprime la table de flux spécifiée.
destroy Supprime la table de flux spécifiée, ne échoue pas si elle n'existe pas.
list Liste toutes les tables de flux.

EXPRESSIONS

Les expressions représentent des valeurs, qu'il s'agisse de constantes comme les adresses réseau, les numéros de port, etc., ou de données collectées à partir du paquet lors de l'évaluation des règles. Les types de données déterminent la taille, l'analyse et la représentation des valeurs symboliques et la compatibilité des types des expressions. Un certain nombre de types de données globaux existent, de plus certains types d'expressions définissent d'autres types de données spécifiques au type d'expression. La plupart des types de données ont une taille fixe, certains peuvent cependant avoir une taille dynamique, par exemple le type chaîne de caractères. EXPRESSIONS PRIMAIRES

L'expression de plus bas niveau est une expression primaire, représentant soit une constante, soit une seule donnée du payload d'un paquet, des métadonnées ou un module d'état.

EXPRESSIONS META

meta {length | nfproto | l4proto | protocol | priority}
[meta] {mark | iif | iifname | iiftype | oif | oifname | oiftype | skuid | skgid | nftrace | rtclassid | ibrname | obrname | pkttype | cpu | iifgroup | oifgroup | cgroup | random | ipsec | iifkind | oifkind | time | hour | day }

Une expression meta fait référence à des métadonnées associées à un paquet.

Il existe deux types d'expressions meta : les expressions meta non qualifiées et qualifiées. Les expressions meta qualifiées nécessitent le mot-clé meta avant la clé meta, les expressions meta non qualifiées peuvent être spécifiées en utilisant directement la clé meta ou comme expressions meta qualifiées. Meta l4proto est utile pour faire correspondre un protocole de transport particulier qui fait partie d'un paquet IPv4 ou IPv6. Il ignorera également les en-têtes d'extension IPv6 présents dans un paquet IPv6.

meta iif, oif, iifname et oifname sont utilisées pour faire correspondre l'interface sur laquelle un paquet est arrivé ou est sur le point d'être envoyé.

iif et oif sont utilisées pour faire correspondre l'index de l'interface, tandis que iifname et oifname sont utilisées pour faire correspondre le nom de l'interface. Ce n'est pas la même chose — en supposant la règle

filter input meta iif "foo"

Alors cette règle ne peut être ajoutée que si l'interface "foo" existe. De plus, la règle continuera de correspondre même si l'interface "foo" est renommée en "bar".

Ceci est dû au fait que l'index de l'interface est utilisé en interne. Dans le cas des interfaces créées dynamiquement, comme les interfaces tun/tap ou dialup (ppp par exemple), il peut être préférable d'utiliser plutôt iifname ou oifname.

Dans ces cas, le nom est utilisé de sorte que l'interface n'a pas besoin d'exister pour ajouter une telle règle, elle cessera de correspondre si l'interface est renommée et elle correspondra à nouveau si l'interface est supprimée puis qu'une nouvelle interface portant le même nom est créée.

Comme avec iptables, la correspondance par caractère générique sur les préfixes de noms d'interface est disponible pour les correspondances iifname et oifname en ajoutant un astérisque (*) à la fin. Notez cependant que contrairement à iptables, nftables n'accepte pas les noms d'interface ne contenant que le caractère générique — les utilisateurs sont supposés simplement ignorer ces expressions qui correspondent toujours. Afin de faire correspondre un astérisque littéral, on peut l'échapper à l'aide d'une barre oblique inverse (\).

EXPRESSION SOCKET

L'expression socket peut être utilisée pour rechercher un socket TCP/UDP ouvert existant et ses attributs qui peuvent être associés à un paquet. Elle recherche un socket d'écoute établi ou lié à un port non nul (éventuellement avec une adresse non locale). Vous pouvez également l'utiliser pour faire correspondre le cgroupv2 du socket à un niveau ancêtre donné, par exemple si le socket appartient au cgroupv2 a/b, le niveau ancêtre 1 vérifie une correspondance sur le cgroup a et le niveau ancêtre 2 vérifie une correspondance sur le cgroup b.

# Marquer les paquets qui correspondent à un socket transparent. "socket wildcard 0"

L'expression osf effectue une empreinte passive du système d'exploitation. Cette expression compare certaines données (taille de la fenêtre, MSS, options et leur ordre, DF, et autres) des paquets avec le bit SYN défini.

EXPRESSIONS FIB

fib TUPLE_FIB RÉSULTAT_FIB
TUPLE_FIB := { saddr | daddr} [ . { iif | oif } . mark ]
RÉSULTAT_FIB  := { oif | oifname | check | type }

Une expression fib interroge la fib (base d'informations de routage) pour obtenir des informations telles que l'index de l'interface de sortie.

Les premiers arguments de l'expression fib sont les clés d'entrée à passer à la fonction de recherche fib. L'un des mots-clés saddr ou daddr est obligatoire, et ils sont mutuellement exclusifs.

Les mots-clés mark, iif et oif sont des modificateurs optionnels pour influencer le résultat de la recherche, voir le tableau des mots-clés TUPLE_FIB ci-dessous pour une description. Les mots-clés de tuple iif et oif sont également mutuellement exclusifs.

Le dernier argument de l'expression fib est le type de résultat souhaité.

oif demande à obtenir l'index de l'interface qui serait utilisé pour envoyer des paquets à l'adresse source (clé saddr) ou destination (clé daddr) des paquets. Si aucune entrée de routage n'est trouvée, l'index de l'interface retourné est 0.

oifname est similaire à oif, mais remplit le nom de l'interface à la place. Ceci est utile pour vérifier les interfaces dynamiques telles que les périphériques ppp. Si aucune entrée n'est trouvée, un nom d'interface vide est retourné.

type retourne le type d'adresse tel que unicast ou multicast. Une liste complète des types d'adresses pris en charge peut être affichée avec nft describe fib_addrtype.

Tableau 31. Mots-clés FIB_TUPLE

indicateur Description

saddr Effectuer une recherche de route inverse : rechercher dans la fib une route vers l'adresse source du paquet.
mark prendre en compte la marque du paquet (nfmark) lors de l'interrogation de la fib.
iif si les recherches fib fournissent une route, alors vérifier que son interface de sortie est identique à l'interface d'entrée du paquet.
oif si les recherches fib fournissent une route, alors vérifier que son interface de sortie est identique à l'interface de sortie du paquet. Cet indicateur ne peut être utilisé qu'avec le résultat type.

Le résultat oif et oifname n'est valide que dans les crochets prerouting, input et forward. Le type peut être interrogé à partir de l'un des crochets prerouting, input, forward output et postrouting.

Pour type, la présence du mot-clé iif dans les modificateurs FIB_TUPLE restreint les crochets disponibles à ceux où le paquet est associé à une interface entrante, c'est-à-dire prerouting, input et forward. De même, le mot-clé oif dans la liste des modificateurs FIB_TUPLE limitera les crochets disponibles à forward, output et postrouting.

Utilisation des expressions fib.

# supprimer les paquets sans chemin de retour
filter prerouting fib saddr . iif oif missing drop
Dans cet exemple, 'saddr . iif' recherche une route vers l'adresse *source* du paquet et restreint les résultats correspondants à l'interface sur laquelle le paquet est arrivé, puis stocke l'index de l'interface de sortie du résultat fib obtenu.
Si aucune route n'a été trouvée pour la combinaison adresse source/interface d'entrée, l'index de l'interface de sortie est zéro.
Par conséquent, cette règle supprimera tous les paquets qui n'ont pas de chemin de retour strict (le paquet de réponse hypothétique serait envoyé via l'interface sur laquelle le paquet testé est arrivé).
Si seul 'saddr oif' est utilisé comme clé d'entrée, alors cette règle ne supprimerait que les paquets pour lesquels la fib ne trouve pas de route. Dans la plupart des configurations, cela ne supprimera jamais de paquets car la route par défaut est retournée.
# supprimer les paquets si l'adresse IP de destination n'est pas configurée sur l'interface entrante
filter prerouting fib daddr . iif type != { local, broadcast, multicast } drop
Ceci interroge la fib en se basant sur l'adresse de destination du paquet actuel et l'interface entrante.
Si le paquet est envoyé à une adresse unicast configurée sur une autre interface, alors le paquet sera supprimé car une telle adresse serait classée comme de type 'unicast'.
Sans le modificateur 'iif', toute adresse configurée sur la machine locale est 'local', et les adresses unicast non configurées sur une interface retourneraient le type 'unicast'.
# effectuer une recherche dans une table spécifique 'blackhole' (0xdead, nécessite une règle ip appropriée)
filter prerouting meta mark set 0xdead fib daddr . mark type vmap { blackhole : drop, prohibit : jump prohibited, unreachable : drop }

EXPRESSION NUMGEN

numgen {inc | random} mod NUM [ offset NUM ]

Crée un générateur de nombres. Les mots-clés inc ou random contrôlent son mode de fonctionnement : en mode inc, la dernière valeur retournée est simplement incrémentée. L'option offset permet d'incrémenter la valeur retournée d'un décalage fixe.

Un cas d'utilisation typique pour numgen est l'équilibrage de charge :

Utilisation de l'expression numgen.

# round-robin entre 192.168.10.100 et 192.168.20.200 :
add rule nat prerouting dnat to numgen inc mod 2 map \
        { 0 : 192.168.10.100, 1 : 192.168.20.200 }
# basé sur la probabilité avec un biais impair en utilisant des intervalles :
add rule nat prerouting dnat to numgen random mod 10 map \
        { 0-2 : 192.168.10.100, 3-9 : 192.168.20.200 }

La fonction jhash nécessite une expression pour déterminer les paramètres de l'en-tête du paquet auxquels appliquer le hachage ; les concaténations sont également possibles. La valeur après le mot-clé mod spécifie une limite supérieure (c'est-à-dire le modulo) qui n'est pas atteinte par les nombres retournés. La valeur optionnelle seed est utilisée pour spécifier une valeur d'initialisation servant de graine à la fonction de hachage. La valeur optionnelle offset permet d'incrémenter la valeur retournée d'un décalage fixe.

Un cas d'utilisation typique pour jhash et symhash est l'équilibrage de charge :

# équilibre de charge basé sur l'adresse IP source entre 2 adresses IP :
add rule nat prerouting dnat to jhash ip saddr mod 2 map \
        { 0 : 192.168.10.100, 1 : 192.168.20.200 }
# équilibrage de charge symétrique entre 2 adresses IP :

EXPRESSION DE CHARGE UTILE BRUTE

@base,offset,length

L'expression de charge utile brute demande le chargement de length bits en commençant à offset bits. Le bit 0 fait référence au tout premier bit — en langage C, cela correspond au bit le plus significatif, c'est-à-dire 0x80 dans le cas d'un octet. Ils sont utiles pour faire correspondre des en-têtes qui n'ont pas encore d'expression de modèle lisible par l'homme. Notez que nft n'ajoutera pas de dépendances pour les expressions de charge utile brute. Si, par exemple, vous souhaitez faire correspondre les champs de protocole d'un en-tête de transport avec le numéro de protocole 5, vous devez exclure manuellement les paquets qui ont un en-tête de transport différent, par exemple en utilisant meta l4proto 5 avant l'expression brute.

Tableau 56. Bases de protocoles de charge utile pris en charge

Base Description
ll Couche de liaison, par exemple l'en-tête Ethernet
nh En-tête réseau, par exemple IPv4 ou IPv6
th En-tête de transport, par exemple TCP
ih En-tête interne / Charge utile, c'est-à-dire après l'en-tête de niveau L4 de transport

Correspondance du port de destination pour UDP et TCP.

inet filter input meta l4proto {tcp, udp} @th,16,16 { 53, 80 }

Ce qui précède peut également s'écrire

inet filter input meta l4proto {tcp, udp} th dport { 53, 80 }

c'est plus pratique, mais comme la notation d'expression brute, aucune dépendance n'est créée ou vérifiée. Il est de la responsabilité de l'utilisateur de restreindre la correspondance aux types d'en-têtes qui ont une notion de ports. Sinon, les règles utilisant des expressions brutes correspondent à tort à des paquets non liés, par exemple en interprétant mal le champ SPI des paquets ESP comme un port.

EXPRESSIONS DE COMPTEURS

Les expressions de compteurs peuvent être utilisées pour compter les paquets et les octets qui correspondent à une règle.

Il existe deux types de compteurs : packets et bytes. Ils peuvent être utilisés avec les opérateurs relationnels standards : =, !=, <, <=, >, >=.

counter [packets | bytes] [op value]

Exemple : Compter tous les paquets entrants.

filter input counter packets accept

Exemple : Compter les octets des paquets TCP sur le port 80.

inet filter input tcp dport 80 counter bytes accept

Exemple : Compter les paquets avec une taille supérieure à 1024 octets.

filter input counter packets > 1000 accept

EXPRESSIONS DE QUOTAS

Les expressions de quotas peuvent être utilisées pour limiter le nombre de paquets ou d'octets qui correspondent à une règle.

Il existe deux types de quotas : packets et bytes. Ils peuvent être utilisés avec les opérateurs relationnels standards : =, !=, <, <=, >, >=.

quota [packets | bytes] [op value]

Exemple : Limiter le nombre de paquets entrants à 100.

filter input quota packets 100 reject

Exemple : Limiter les octets des paquets UDP sur le port 53 à 1024.

inet filter input udp dport 53 quota bytes 1024 reject

INSTRUCTIONS

Les instructions représentent des actions à effectuer. Elles peuvent modifier le flux de contrôle (retourner, sauter vers une autre chaîne, accepter ou rejeter le paquet) ou effectuer des actions, telles que l'enregistrement, le rejet d'un paquet, etc.

Les instructions existent en deux types. Les instructions terminales mettent fin inconditionnellement à l'évaluation de la règle actuelle, les instructions non terminales terminent soit conditionnellement soit jamais l'évaluation de la règle actuelle, c'est-à-dire qu'elles sont passives du point de vue de l'évaluation de l'ensemble de règles. Il peut y avoir une quantité arbitraire d'instructions non terminales dans une règle, mais une seule instruction terminale comme dernière instruction.

INSTRUCTION VERDICT

L'instruction verdict modifie le flux de contrôle dans l'ensemble de règles et émet des décisions de politique pour les paquets.

{accept | drop | queue | continue | return}
{jump | goto} CHAIN
CHAIN := chain_name | { statement ... }

accept et drop sont des verdicts absolus — ils mettent fin immédiatement à l'évaluation de l'ensemble de règles.

accept Termine l'évaluation de l'ensemble de règles et accepte le paquet. Le paquet peut toujours être rejeté plus tard par un autre hook, par exemple, accept dans le hook forward permet toujours de rejeter le paquet plus tard dans le hook postrouting, ou une autre chaîne de base forward ayant un numéro de priorité plus élevé et évaluée ultérieurement dans le pipeline de traitement.
drop Termine l'évaluation de l'ensemble de règles et rejette le paquet. Le rejet se produit instantanément, aucune autre chaîne ou hook n'est évalué. Il n'est pas possible d'accepter le paquet dans une chaîne ultérieure, car celles-ci ne sont plus évaluées pour le paquet.
queue Termine l'évaluation de l'ensemble de règles et met le paquet en file d'attente dans l'espace utilisateur. L'espace utilisateur doit fournir un verdict de rejet ou d'acceptation. Dans le cas d'une acceptation, le traitement reprend avec le prochain hook de chaîne de base, pas la règle suivant le verdict de mise en file d'attente.
continue Continue l'évaluation de l'ensemble de règles avec la règle suivante. C'est le comportement par défaut si une règle n'émet aucun verdict.
return Retourne de la chaîne actuelle et continue l'évaluation à la règle suivante dans la dernière chaîne. Si émis dans une chaîne de base, cela équivaut à la politique de la chaîne de base.
jump CHAIN Continue l'évaluation à la première règle dans CHAIN. La position actuelle dans l'ensemble de règles est poussée dans une pile d'appels et l'évaluation continuera là quand la nouvelle chaîne sera entièrement évaluée ou qu'un verdict return sera émis. Si un verdict absolu est émis par une règle de la chaîne, l'évaluation de l'ensemble de règles se termine immédiatement et l'action spécifique est effectuée.
goto CHAIN Similaire à jump, mais la position actuelle n'est pas poussée dans la pile d'appels, ce qui signifie qu'après l'évaluation de la nouvelle chaîne, l'évaluation continuera dans la dernière chaîne au lieu de celle contenant l'instruction goto.

Une alternative à la spécification du nom d'une chaîne régulière existante dans CHAIN est de spécifier une chaîne anonyme ad-hoc. Comme pour les ensembles anonymes, elle ne peut pas être référencée depuis une autre règle et sera supprimée avec la règle qui la contient.

Utilisation des instructions verdict.

# traiter les paquets de eth0 et du réseau interne dans from_lan
# chaîne, rejeter tous les paquets provenant de eth0 avec des adresses sources différentes.
filter input iif eth0 ip saddr 192.168.0.0/24 jump from_lan
filter input iif eth0 drop
# les instructions jump et goto supportent la création de chaînes anonymes
filter input iif eth0 jump { ip saddr 192.168.0.0/24 drop ; udp dport domain drop; }

INSTRUCTION LOG

log [prefix quoted_string] [level syslog-level] [flags log-flags]
log group nflog_group [prefix quoted_string] [queue-threshold value] [snaplen size]
log level audit

L'instruction log active l'enregistrement des paquets correspondants. Lorsque cette instruction est utilisée à partir d'une règle, le noyau Linux imprimera quelques informations sur tous les paquets correspondants, tels que les champs d'en-tête, via le journal du noyau (où il peut être lu avec dmesg(1) ou lu dans syslog).

Dans la deuxième forme d'invocation (si nflog_group est spécifié), le noyau Linux transmettra le paquet à nfnetlink_log qui enverra le journal via un socket netlink au groupe spécifié. Un processus utilisateur peut s'abonner au groupe pour recevoir les journaux, voir man(8) ulogd pour le démon de journalisation de l'espace utilisateur Netfilter et la documentation libnetfilter_log si vous souhaitez développer un programme personnalisé pour traiter vos journaux.

Dans la troisième forme d'invocation (si level audit est spécifié), le noyau Linux écrit un message dans le tampon d'audit formaté de manière appropriée pour être lu avec auditd. Par conséquent, aucune option de formatage supplémentaire (telles que prefix ou flags) n'est autorisée dans ce mode.

Il s'agit d'une instruction non terminante, donc l'évaluation de la règle continue après que le paquet a été enregistré.

INSTRUCTION RATE

L'instruction rate permet de limiter la bande passante.

rate [ ingress | egress ] [ token | packets ]
     [ rate <rate> ] [ burst <burst> ]
rate := <number> / <time>
burst := <number>
time := sec | min | hour | day

L'instruction rate est un filtre qui permet de limiter le taux auquel les paquets peuvent passer. Elle est basée sur l'algorithme de la bille lâchée (leaky bucket).

Vous pouvez spécifier si la limite s'applique au trafic entrant (ingress) ou sortant (egress). Si vous ne spécifiez rien, la limite s'applique au trafic entrant.

Vous pouvez spécifier si la limite est basée sur le nombre d'octets (token) ou le nombre de paquets (packets). Par défaut, la limite est basée sur les octets.

Le paramètre rate spécifie le taux moyen auquel les paquets peuvent passer. Il est défini en nombre d'unités par unité de temps.

Le paramètre burst spécifie le nombre maximal d'unités qui peuvent passer en une seule fois.

Exemple.

# limiter le trafic entrant à 1 Mo/s avec un burst de 5 Mo
ip filter input rate ingress rate 1048576/sec burst 5242880

# limiter le trafic sortant à 100 paquets/seconde avec un burst de 500 paquets
ip filter output rate egress packets rate 100/sec burst 500

CHAÎNES

Les chaînes sont des conteneurs pour les règles. Elles sont organisées en tables et associées à des hooks de noyau.

Types de chaînes :

  • filter : Chaîne pour filtrer les paquets.
  • nat : Chaîne pour la traduction d'adresses réseau (NAT).
  • route : Chaîne pour la décision de routage.

Hooks : Les hooks définissent le point dans le chemin de traitement du noyau où une chaîne est appelée.

  • prerouting : Pour les paquets entrants, avant la décision de routage.
  • input : Pour les paquets destinés au système local, après la décision de routage.
  • forward : Pour les paquets transitant par le système, après la décision de routage.
  • output : Pour les paquets générés par le système local, avant la décision de routage.
  • postrouting : Pour les paquets sortants, après le routage (souvent utilisé pour le NAT sortant).

Priorités : Les priorités déterminent l'ordre d'exécution des chaînes lorsqu'elles sont associées au même hook. Des valeurs plus élevées signifient une exécution plus tardive.

Tableau 73. Priorités courantes des hooks

Hook Priorité Description
raw -300 Première étape de traitement, avant le suivi de connexion.
( ) -200
( ) -100
( ) 0 Priorité par défaut pour les chaînes de type filter.
( ) 100
( ) 200
mangle 250 Dernière étape de traitement pour les tables mangle.
nat 300 Dernière étape pour les tables nat.

Politiques par défaut :

  • accept : Accepte tous les paquets qui n'ont pas été explicitement rejetés ou laissés par une règle.
  • drop : Rejette tous les paquets qui n'ont pas été explicitement acceptés ou laissés par une règle.
  • reject : Rejette tous les paquets qui n'ont pas été explicitement acceptés ou laissés par une règle, et renvoie un message d'erreur au source.

Exemple de création de chaîne.

table inet filter {
  chain input {
    type filter hook input priority 0; policy drop;

    # accepter le trafic loopback
    ip saddr 127.0.0.1 accept
    ip6 saddr ::1 accept

    # accepter le trafic ICMPv6
    ip6 nexthdr icmpv6 accept
  }

  chain forward {
    type filter hook forward priority 0; policy drop;
  }

  chain output {
    type filter hook output priority 0; policy accept;
  }
}

Ajouter une règle à une chaîne existante.

add chain inet filter input { tcp dport 22 accept }

Supprimer une règle d'une chaîne.

delete chain inet filter input { tcp dport 22 }

Vider une chaîne (supprimer toutes les règles).

Supprimer une chaîne.

delete chain inet filter input

RÈGLES

Les règles sont les éléments de base qui définissent la politique de filtrage ou de manipulation des paquets. Une règle se compose d'un ensemble d'expressions de correspondance et d'une ou plusieurs instructions.

Structure générale d'une règle :

table chain match_expression statement
  • Table et Chaîne : Spécifie où la règle sera ajoutée.
  • Expression de correspondance : Un ensemble d'expressions qui doivent toutes correspondre pour que la règle s'applique. Si aucune expression n'est spécifiée, la règle correspond à tous les paquets.
  • Instruction : Une ou plusieurs actions à effectuer si la règle correspond. Si aucune instruction n'est spécifiée, l'action par défaut est accept.

Tableau 74. Actions des instructions courantes

Action Description
accept Accepte le paquet et arrête le traitement de la chaîne.
drop Rejette silencieusement le paquet et arrête le traitement de la chaîne.
reject Rejette le paquet et renvoie un message d'erreur au source. Arrête le traitement de la chaîne.
log Journalise le paquet. Le traitement continue.
counter Incrémente un compteur de paquets et d'octets. Le traitement continue.
jump Transfère le traitement à une autre chaîne. Le traitement continue dans la chaîne de destination.
goto Transfère le traitement à une autre chaîne. Le traitement ne reprend pas dans la chaîne actuelle.

Exemples de règles.

# dans la table inet, chaîne input, accepter tout le trafic SSH
inet filter input tcp dport 22 accept

# dans la table ip, chaîne forward, journaliser les paquets non autorisés
ip filter forward ip protocol 17 log prefix "DROP UDP: "

# dans la table inet, chaîne output, rejeter les paquets vers un port spécifique
inet filter output tcp dport 12345 reject

# dans la table bridge, chaîne input, utiliser un compteur
bridge filter input ether saddr 00:11:22:33:44:55 counter

# dans la table inet, chaîne prerouting, sauter vers une autre chaîne
inet raw prerouting ip daddr 192.168.1.0/24 jump jump_to_nat

STATEMENT TABLES

The following tables are available:

inet (all families)
ip (IPv4)
ip6 (IPv6)
link (Link layer)
raw (all families)
route (all families)
Mangle (all families)

These tables can contain chains, and chains contain rules. Rules consist of a set of matching criteria and a verdict. If all criteria match, the verdict is executed.

BASIC STATEMENTS

add chain [chain_type] [priority]
delete chain
flush [chain]
add rule [chain] [match_criteria] [verdict]
delete rule [chain] [rule_handle]
replace rule [chain] [rule_handle] [match_criteria] [verdict]
list [table] [chain]
save [file]
load [file]

The add statement creates a new chain or rule. If a chain exists, the rule is added to the end of the chain. Otherwise, the chain is created. The optional chain_type parameter specifies the chain type. If omitted, the type is inferred from the hook. For example, rules with hook prerouting must have chain type filter, nat, or route.

The optional priority parameter specifies the order in which chains are evaluated. Lower numbers indicate higher priority. For example, 0 has higher priority than 100.

The delete statement removes a chain or a rule. Rules can be identified by their handle or by their full matching criteria.

The flush statement removes all rules from a chain or all chains in a table.

The list statement shows the current configuration. If no table or chain is specified, all rules in all tables are listed.

The save and load statements allow you to save the current configuration to a file and restore it later.

Table 67. Basic statement values

Value Description Type
chain_type Type of chain (e.g., filter, nat, route). string
priority Priority of the chain. integer
rule_handle Unique identifier for a rule. integer

PACKET STATEMENT

mark [packet] MARK_SPEC
mark [override] [packet] MARK_SPEC
mark [delete] [packet] MARK_SPEC

The mark statement sets or deletes a mark on the packet. The mark is an arbitrary unsigned 32-bit integer value. Marks can be used to tag packets for later processing by other rules or external tools.

The optional override keyword forces the mark to be set even if the packet already has a mark set. The optional delete keyword removes the specified mark from the packet.

If the packet keyword is omitted, the mark is set on the connection instead of the packet. This is useful for tracking connections that match certain criteria.

LIMIT STATEMENT

limit rate [over] packet_number / TIME_UNIT [burst packet_number packets]
limit rate [over] byte_number BYTE_UNIT / TIME_UNIT [burst byte_number BYTE_UNIT]
TIME_UNIT := second | minute | hour | day
BYTE_UNIT := bytes | kbytes | mbytes

A limit statement matches at a limited rate using a token bucket filter. A rule using this statement will match until this limit is reached. It can be used in combination with the log statement to give limited logging. The optional over keyword makes it match over the specified rate.

The burst value influences the bucket size, i.e. jitter tolerance. With packet-based limit, the bucket holds exactly burst packets, by default five. If you specify packet burst, it must be a non-zero value. With byte-based limit, the bucket’s minimum size is the given rate’s byte value and the burst value adds to that, by default zero bytes.

byte_number Number of bytes unsigned integer (32 bit)

NAT STATEMENTS

snat [[ip | ip6] [ prefix ] to] TARGET_SPEC [FLAGS]
dnat [[ip | ip6] [ prefix ] to] TARGET_SPEC [FLAGS]
masquerade [to :PORT_SPEC] [FLAGS]
redirect [to :PORT_SPEC] [FLAGS]
TARGET_SPEC := ADDR_SPEC | [ADDR_SPEC] :PORT_SPEC
ADDR_SPEC := address | address - address
PORT_SPEC := port | port - port
FLAGS  := FLAG [, FLAGS]
FLAG  := persistent | random | fully-random

The nat statements are only valid from nat chain types.

The snat and masquerade statements specify that the source address/port of the packet should be modified. While snat is only valid in the postrouting and input chains, masquerade makes sense only in postrouting. The dnat and redirect statements are only valid in the prerouting and output chains, they specify that the destination address/port of the packet should be modified. You can use non-base chains which are called from base chains of nat chain type too. All future packets in this connection will also be mangled, and rules should cease being examined.

The masquerade statement is a special form of snat which always uses the outgoing interface’s IP address to translate to. It is particularly useful on gateways with dynamic (public) IP addresses.

The redirect statement is a special form of dnat which always translates the destination address to the local host’s one. It comes in handy to intercept traffic passing a router and feeding it to a locally running daemon, e.g. when building a transparent proxy or application-layer gateway.

For TARGET_SPEC, one may specify addresses, ports, or both. If no address or no port is specified, the respective packet header field remains unchanged.

When used in the inet family (available with kernel 5.2), the dnat and snat statements require the use of the ip and ip6 keyword in case an address is provided, see the examples below.

Before kernel 4.18 nat statements require both prerouting and postrouting base chains to be present since otherwise packets on the return path won’t be seen by netfilter and therefore no reverse translation will take place.

The optional prefix keyword allows to map n source addresses to n destination addresses. See Advanced NAT examples below.

If the address for dnat is an IPv4 loopback address (i.e. 127.0.0.0/8) the "net.ipv4.conf.*.route_localnet" sysctl for the input interface needs to be set to 1. Otherwise packets will be dropped by the routing code as "martians".

DÉCLARATION FWD

La déclaration fwd est utilisée pour rediriger un paquet brut vers une autre interface. Elle n'est disponible que dans les points d'entrée et de sortie de la famille netdev. Elle est similaire à la déclaration dup, sauf qu'aucune copie n'est effectuée.

Vous pouvez également spécifier l'adresse du prochain saut et le périphérique vers lequel transférer le paquet. Cela met à jour l'adresse MAC source et destination du paquet en le transmettant via la couche voisine. Cela décrémente également le champ ttl du paquet IP. Cela permet de contourner efficacement le chemin de transfert classique, sautant ainsi la recherche fib (base d'informations de transfert).

fwd vers périphérique
fwd [ip | ip6] vers adresse périphérique périphérique

Utilisation de la déclaration fwd.

# rediriger le paquet brut vers le périphérique
netdev ingress fwd vers "eth0"
# transférer le paquet vers le prochain saut 192.168.200.1 via le périphérique eth0
netdev ingress ether saddr set fwd ip vers 192.168.200.1 périphérique "eth0"

DÉCLARATION SET

La déclaration set est utilisée pour ajouter ou mettre à jour dynamiquement des éléments dans un ensemble à partir du chemin du paquet. L'ensemble setname doit déjà exister dans la table donnée et doit avoir été créé avec l'un ou les deux indicateurs dynamic et timeout. L'indicateur dynamic est requis si l'expression de la déclaration set inclut un objet stateful. L'indicateur timeout est implicite si l'ensemble est créé avec un timeout, et est requis si la déclaration set met à jour des éléments, plutôt que de les ajouter. De plus, ces ensembles doivent spécifier une taille maximale d'ensemble (pour éviter l'épuisement de la mémoire), et leurs éléments doivent avoir un timeout (afin que leur nombre ne croisse pas indéfiniment) soit à partir de la définition de l'ensemble, soit à partir de la déclaration qui les ajoute ou les met à jour. La déclaration set peut être utilisée, par exemple, pour créer des listes noires dynamiques.

Les mises à jour dynamiques sont également prises en charge avec les maps. Dans ce cas, la règle add ou update doit fournir à la fois la clé et l'élément de données (valeur), séparés par :.

{add | update} @nom_ensemble { expression [timeout délai] [comment chaîne] }

Exemple de liste noire simple.

# déclarer un ensemble, lié à la table "filter", dans la famille "ip".
# Le timeout et la taille sont obligatoires car nous ajouterons des éléments depuis le chemin du paquet.
# Les entrées expireront après une minute, après quoi elles pourraient être
# re-ajoutées si la condition de limite persiste.
nft add set ip filter blackhole \
    "{ type ipv4_addr; flags dynamic; timeout 1m; size 65536; }"
# déclarer un ensemble pour stocker la limite par saddr.
# Ceci doit être séparé de blackhole car le timeout est différent
nft add set ip filter flood \
    "{ type ipv4_addr; flags dynamic; timeout 10s; size 128000; }"
# autoriser l'interface interne.
nft add rule ip filter input meta iifname "internal" accept
# laisser tomber les paquets provenant d'adresses IP mises sur liste noire.
nft add rule ip filter input ip saddr @blackhole counter drop
# ajouter les adresses IP sources à la liste noire si plus de 10 connexions TCP
# demandes ont eu lieu par seconde et par adresse IP.
nft add rule ip filter input tcp flags syn tcp dport ssh \
    add @flood { ip saddr limit rate over 10/second } \
    add @blackhole { ip saddr } \
    drop
# inspecter l'état des ensembles.
nft list set ip filter flood
nft list set ip filter blackhole
# ajouter manuellement deux adresses à la liste noire.
nft add element filter blackhole { 10.2.3.4, 10.23.1.42 }

DÉCLARATION MAP

La déclaration map est utilisée pour rechercher des données basées sur une clé d'entrée spécifique.

expression map { ÉLÉMENTS_MAP }
ÉLÉMENTS_MAP := ÉLÉMENT_MAP [, ÉLÉMENTS_MAP]
ÉLÉMENT_MAP  := clé : valeur

La clé est une valeur retournée par expression.

Utilisation de la déclaration map.

# sélectionner la cible DNAT en fonction du dport TCP :
# les connexions au port 80 sont redirigées vers 192.168.1.100,
# les connexions au port 8888 sont redirigées vers 192.168.1.101
nft add rule ip nat prerouting dnat tcp dport map { 80 : 192.168.1.100, 8888 : 192.168.1.101 }
# SNAT basé sur l'adresse source :
# les paquets provenant du réseau 192.168.1.0/24 apparaîtront comme provenant de 10.0.0.1,
# les paquets provenant du réseau 192.168.2.0/24 apparaîtront comme provenant de 10.0.0.2
nft add rule ip nat postrouting snat to ip saddr map { 192.168.1.0/24 : 10.0.0.1, 192.168.2.0/24 : 10.0.0.2 }

DÉCLARATION VMAP

La déclaration de map de verdict (vmap) fonctionne de manière analogue à la déclaration map, mais contient des verdicts comme valeurs.

expression vmap { ÉLÉMENTS_VMAP }
ÉLÉMENTS_VMAP := ÉLÉMENT_VMAP [, ÉLÉMENTS_VMAP]
ÉLÉMENT_VMAP  := clé : verdict

Utilisation de la déclaration vmap.

# sauter vers différentes chaînes en fonction du type de protocole de couche 4 :
nft add rule ip filter input ip protocol vmap { tcp : jump tcp-chain, udp : jump udp-chain , icmp : jump icmp-chain }

DÉCLARATION XT

Ceci représente une déclaration xt de l'interface de compatibilité xtables. C'est un recours si la traduction n'est pas disponible ou n'est pas complète.

xt TYPE NOM
TYPE := match | target | watcher

Voir ceci signifie que l'ensemble de règles (ou des parties de celui-ci) a été créé par iptables-nft et qu'il faut utiliser cela pour le gérer.

ATTENTION : nftables ne restaurera pas ces déclarations.

COMMANDES ADDITIONNELLES

Voici quelques commandes supplémentaires incluses dans nft.

LISTER HOOKS

Ceci affiche la liste des fonctions qui ont été enregistrées pour la famille de protocoles donnée, y compris les fonctions qui ont été enregistrées implicitement par des modules du noyau tels que nf_conntrack.

list hooks [famille]
list hooks netdev [ périphérique NOM_PÉRIPHÉRIQUE ]

list hooks est suffisant pour afficher tout ce qui est actif sur le système. Les hooks de la famille netdev sont liés à un périphérique réseau. Si aucun nom de périphérique n'est donné, nft interrogera tous les périphériques réseau dans l'espace de noms réseau actuel. Exemple d'utilisation :

Lister tous les hooks netfilter actifs dans la pile ip ou ip6.

% nft list hooks inet
family ip {
        hook prerouting {
                -0000000400 ipv4_conntrack_defrag [nf_defrag_ipv4]
                -0000000200 ipv4_conntrack_in [nf_conntrack]
                -0000000100 nf_nat_ipv4_pre_routing [nf_nat]
        }
        hook input {
                 0000000000 chain inet filter input [nf_tables]
                +0000000100 nf_nat_ipv4_local_in [nf_nat]
[..]

Ce qui précède montre un hôte sur lequel nat, conntrack et la défragmentation de paquets ipv4 sont activées. Pour chaque emplacement de hook pour la famille interrogée, une liste des hooks actifs au format

priorité identifiant [nom_module]

sera affichée.

La valeur de priorité dicte l'ordre dans lequel les hooks sont appelés. La liste est triée, le plus petit nombre est exécuté en premier.

La valeur de priorité des hooks enregistrés par le noyau ne peut pas être modifiée. Pour les chaînes de base enregistrées par nftables, cette valeur correspond à la valeur de priorité spécifiée dans la définition de la chaîne de base.

Après la valeur numérique, des informations sur le hook sont affichées. Pour les chaînes de base définies dans nftables, cela inclut la famille de tables, le nom de la table et le nom de la chaîne de base. Pour les hooks provenant de modules du noyau, le nom de la fonction est utilisé à la place.

Si un nom_module est donné, le hook a été enregistré par le module du noyau portant ce nom. Vous pouvez utiliser modinfo nom_module pour obtenir plus d'informations sur le module.

Cette fonctionnalité nécessite un noyau compilé avec l'option CONFIG_NETFILTER_NETLINK_HOOK activée, soit en tant que module, soit en tant que intégré. Le module s'appelle nfnetlink_hook.

SURVEILLER

La commande monitor permet d'écouter les événements Netlink produits par le sous-système nf_tables. Ceux-ci sont liés soit à la création et à la suppression d'objets, soit à des paquets pour lesquels meta nftrace a été activé. Lorsqu'ils se produisent, nft affichera sur la sortie standard les événements surveillés au format JSON ou au format nft natif.

monitor [new | destroy] OBJET_MONITORÉ
monitor trace
OBJET_MONITORÉ := tables | chains | sets | rules | elements | ruleset

Pour filtrer les événements liés à un objet concret, utilisez l'un des mots-clés dans OBJET_MONITORÉ.

Pour filtrer les événements liés à une action concrète, utilisez le mot-clé new ou destroy.

La deuxième forme d'invocation ne prend pas d'autres options et affiche exclusivement les événements générés pour les paquets avec nftrace activé.

Appuyez sur ^C pour terminer l'opération de surveillance.

Écouter tous les événements, rapporter au format nft natif.

% nft monitor

Écouter les règles supprimées, rapporter au format JSON.

% nft -j monitor destroy rules

Écouter les chaînes nouvelles et supprimées, au format nft natif.

% nft monitor chains

Écouter les événements de jeu de règles tels que table, chaîne, règle, ensemble, compteurs et quotas, au format nft natif.

% nft monitor ruleset

Tracer les paquets entrants de l'hôte 10.0.0.1.

% nft add rule filter input ip saddr 10.0.0.1 meta nftrace set 1
% nft monitor trace

STATUT DE SORTIE

En cas de succès, nft se termine avec un statut de 0. Les erreurs non spécifiées provoquent une sortie avec un statut de 1, les erreurs d'allocation mémoire avec un statut de 2, et l'impossibilité d'ouvrir un socket Netlink avec un statut de 3.
