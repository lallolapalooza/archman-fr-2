NOM

nfsd - système de fichiers spécial pour contrôler le serveur NFS Linux

SYNPOSIS

mount -t nfsd nfsd /proc/fs/nfsd

DESCRIPTION

Le système de fichiers nfsd est un système de fichiers spécial qui fournit l'accès au serveur NFS Linux. L'écriture dans les fichiers de ce système de fichiers peut affecter le serveur. La lecture de ces fichiers peut fournir des informations sur le serveur.

En plus de ce système de fichiers, il existe une collection de fichiers dans le système de fichiers procfs (normalement monté sur /proc) qui sont utilisés pour contrôler le serveur NFS. Cette page de manuel décrit tous ces fichiers.

Les programmes exportfs et mountd (qui font partie du paquet nfs-utils) s'attendent à trouver ce système de fichiers monté sur /proc/fs/nfsd ou /proc/fs/nfs.

DÉTAILS

Les fichiers du système de fichiers nfsd incluent :

exports
Ce fichier contient une liste des systèmes de fichiers actuellement exportés et des clients auxquels chaque système de fichiers est exporté, ainsi qu'une liste d'options d'exportation pour cette paire client/système de fichiers. Ceci est similaire au fichier /proc/fs/nfs/exports dans le noyau 2.4. Une différence est qu'un client ne correspond pas nécessairement à un seul hôte. Il peut répondre à une grande collection d'hôtes traités de manière identique.

Chaque ligne du fichier contient un nom de chemin, un nom de client et un certain nombre d'options entre parenthèses. Tout espace, tabulation, nouvelle ligne ou caractère d'antislash dans le nom du chemin ou le nom du client sera remplacé par un antislash suivi du code ASCII octal de ce caractère.

threads
Ce fichier représente le nombre de threads nfsd actuellement en cours d'exécution. Le lire affichera le nombre de threads. Écrire un nombre décimal ASCII modifiera le nombre de threads (augmenté ou diminué si nécessaire) pour atteindre ce nombre.
filehandle
C'est un fichier quelque peu inhabituel en ce sens que ce qui est lu dépend de ce qui y a été écrit. Il fournit une interface transactionnelle où un programme peut ouvrir le fichier, écrire une requête et lire une réponse. Si deux programmes distincts ouvrent, écrivent et lisent en même temps, leurs requêtes ne seront pas mélangées.

La requête écrite dans filehandle doit être un nom de client, un nom de chemin et un nombre d'octets. Cela doit être suivi d'une nouvelle ligne, avec des espaces blancs séparant les champs, et un encodage octal des caractères spéciaux.

En écrivant cela, le programme pourra relire un descripteur de fichier pour ce chemin tel qu'exporté vers le client donné. La longueur du descripteur de fichier sera au maximum le nombre d'octets spécifié.

Le descripteur de fichier sera représenté en hexadécimal avec un préfixe '\x'.

clients/
Ce répertoire contient un sous-répertoire pour chaque client NFSv4. Chaque fichier sous ce sous-répertoire donne des détails sur le client au format YAML. De plus, écrire "expire\n" dans le fichier ctl forcera le serveur à révoquer immédiatement tout état détenu par ce client.

Le répertoire /proc/net/rpc dans le système de fichiers procfs contient un certain nombre de fichiers et de répertoires. Les fichiers contiennent des statistiques qui peuvent être affichées à l'aide du programme nfsstat. Les répertoires contiennent des informations sur divers caches que le serveur NFS maintient pour suivre les permissions d'accès que différents clients ont pour différents systèmes de fichiers. Les caches sont :

auth.unix.ip
Ce cache contient une correspondance entre une adresse IP et le nom du domaine d'authentification dont l'adresse IP doit être considérée comme faisant partie.
nfsd.export
Ce cache contient une correspondance entre un répertoire et un domaine et des options d'exportation.
nfsd.fh
Ce cache contient une correspondance entre un domaine et un identifiant de système de fichiers et un répertoire. L'identifiant de système de fichiers est stocké dans les descripteurs de fichiers et consiste en un nombre indiquant le type d'identifiant et un certain nombre d'octets hexadécimaux indiquant le contenu de l'identifiant.

Chaque répertoire représentant un cache peut contenir de 1 à 3 fichiers. Ce sont :

flush
Lorsqu'un nombre de secondes depuis l'époque (1er janvier 1970) est écrit dans ce fichier, toutes les entrées du cache qui ont été mises à jour pour la dernière fois avant ce fichier deviennent invalidées et seront purgées. Écrire une date future (en secondes depuis l'époque) purgera tout. C'est le seul fichier qui sera toujours présent.
content
Ce fichier, s'il est présent, contient une représentation textuelle de chaque entrée du cache, une par ligne. Si une entrée est toujours dans le cache (car elle est activement utilisée) mais a expiré ou est autrement invalide, elle sera présentée sous forme de commentaire (avec un caractère dièse en préfixe).
channel
Ce fichier, s'il est présent, agit comme un canal pour que les requêtes du serveur NFS basé sur le noyau soient transmises à un programme utilisateur pour traitement.

Lorsque le noyau a besoin d'informations qui ne sont pas dans le cache, il fait apparaître une ligne dans le fichier channel donnant la clé de l'information. Un programme utilisateur doit lire ceci, trouver la réponse et écrire une ligne contenant la clé, un délai d'expiration et le contenu. Par exemple, le noyau pourrait faire apparaître nfsd 127.0.0.1
dans le fichier auth.unix.ip/content. Le programme utilisateur pourrait alors écrire nfsd 127.0.0.1 1057206953 localhost
pour indiquer que 127.0.0.1 doit être mappé sur localhost, du moins pour le moment.

Si le programme utilise select(2) ou poll(2) pour découvrir s'il peut lire depuis le channel, il ne verra jamais de fin de fichier, mais lorsque toutes les requêtes auront été répondues, il se bloquera jusqu'à ce qu'une autre requête apparaisse.

Dans le système de fichiers /proc, il y a 4 fichiers qui peuvent être utilisés pour activer le traçage supplémentaire de nfsd et du code associé. Ce sont :
/proc/sys/sunrpc/nfs_debug
/proc/sys/sunrpc/nfsd_debug
/proc/sys/sunrpc/nlm_debug
/proc/sys/sunrpc/rpc_debug

Ils contrôlent le traçage pour le client NFS, le serveur NFS, le Network Lock Manager (lockd) et la couche RPC sous-jacente respectivement. Des nombres décimaux peuvent être lus ou écrits dans ces fichiers. Chaque nombre représente un masque de bits où les bits définis provoquent l'activation de certaines classes de traçage. Consultez les fichiers d'en-tête du noyau pour savoir quels nombres correspondent à quel traçage.

NOTES

Ce système de fichiers n'est disponible que dans les noyaux des séries Linux 2.6 et ultérieures (et dans les dernières parties de la série de développement 2.5 menant à la 2.6). Cette page de manuel ne s'applique pas aux versions 2.4 et antérieures.

Auparavant, l'appel système nfsctl était utilisé pour la communication entre nfsd et les utilitaires utilisateur. Cet appel système a été supprimé dans la version 3.1 du noyau. Les anciennes versions de nfs-utils étaient capables de se rabattre sur nfsctl si nécessaire ; cela a été supprimé de nfs-utils 1.3.5.
