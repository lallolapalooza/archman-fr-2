NFS(5) Manuel des formats de fichiers NFS(5)

NOM

nfs - format et options de fstab pour les systèmes de fichiers nfs

SYNOPIS

/etc/fstab

DESCRIPTION

NFS est un protocole Standard Internet créé par Sun Microsystems en 1984. NFS a été développé pour permettre le partage de fichiers entre des systèmes résidant sur un réseau local. Selon la configuration du noyau, le client NFS de Linux peut supporter les versions NFS 3, 4.0, 4.1 ou 4.2.

La commande mount(8) attache un système de fichiers à la hiérarchie de l'espace de noms du système à un point de montage donné. Le fichier /etc/fstab décrit comment mount(8) doit assembler la hiérarchie des noms de fichiers d'un système à partir de divers systèmes de fichiers indépendants (y compris les systèmes de fichiers exportés par les serveurs NFS). Chaque ligne dans le fichier /etc/fstab décrit un seul système de fichiers, son point de montage et un ensemble d'options de montage par défaut pour ce point de montage.

Pour les montages de systèmes de fichiers NFS, une ligne dans le fichier /etc/fstab spécifie le nom du serveur, le nom du chemin du répertoire serveur exporté à monter, le répertoire local qui est le point de montage, le type de système de fichiers qui est monté, et une liste d'options de montage qui contrôlent la façon dont le système de fichiers est monté et comment le client NFS se comporte lors de l'accès aux fichiers sur ce point de montage. Les cinquième et sixième champs sur chaque ligne ne sont pas utilisés par NFS, ils contiennent donc conventionnellement le chiffre zéro. Par exemple :

serveur:chemin	/pointdemontage	fstype	option,option,...	0 0

Le nom d'hôte du serveur et le chemin d'exportation sont séparés par un deux-points, tandis que les options de montage sont séparées par des virgules. Les champs restants sont séparés par des espaces ou des tabulations.

Le nom d'hôte du serveur peut être un nom d'hôte non qualifié, un nom de domaine entièrement qualifié, une adresse IPv4 en quad pointé, ou une adresse IPv6 entourée de crochets. Les adresses IPv6 lien-local et site-local doivent être accompagnées d'un identifiant d'interface. Voir ipv6(7) pour les détails sur la spécification des adresses IPv6 brutes.

Le champ fstype contient "nfs". L'utilisation du fstype "nfs4" dans /etc/fstab est dépréciée.

OPTIONS DE MONTAGE

Référez-vous à mount(8) pour une description des options de montage génériques disponibles pour tous les systèmes de fichiers. Si vous n'avez pas besoin de spécifier d'options de montage, utilisez l'option générique defaults dans /etc/fstab.

Options prise en charge par toutes les versions

Ces options sont valides pour toutes les versions de NFS.

nfsvers=n
Le numéro de version du protocole NFS utilisé pour contacter le service NFS du serveur. Si le serveur ne prend pas en charge la version demandée, la requête de montage échoue. Si cette option n'est pas spécifiée, le client essaie d'abord la version 4.2, puis négocie vers le bas jusqu'à ce qu'il trouve une version prise en charge par le serveur.
vers=n
Cette option est une alternative à l'option nfsvers. Elle est incluse pour la compatibilité avec d'autres systèmes d'exploitation.
soft / softerr / hard
Détermine le comportement de récupération du client NFS après l'expiration d'une requête NFS. Si aucune option n'est spécifiée (ou si l'option hard est spécifiée), les requêtes NFS sont retentées indéfiniment. Si l'option soft ou softerr est spécifiée, le client NFS échoue une requête NFS après que retrans retransmissions aient été envoyées, provoquant le retour de l'erreur EIO (pour l'option soft) ou ETIMEDOUT (pour l'option softerr) à l'application appelante.
NB : Une soi-disant expiration "soft" peut causer une corruption silencieuse des données dans certains cas. Par conséquent, n'utilisez l'option soft ou softerr que lorsque la réactivité du client est plus importante que l'intégrité des données. L'utilisation de NFS sur TCP ou l'augmentation de la valeur de l'option retrans peuvent atténuer certains des risques liés à l'utilisation de l'option soft ou softerr.
softreval / nosoftreval
Dans les cas où le serveur NFS est en panne, il peut être utile de permettre au client NFS de continuer à servir des chemins et des attributs depuis le cache après que retrans tentatives pour revalider ce cache aient expiré. Cela peut, par exemple, être utile lorsque l'on essaie de démonter une arborescence de fichiers d'un serveur qui est définitivement hors service.
Il est possible de combiner softreval avec l'option de montage soft, auquel cas les opérations qui ne peuvent pas être servies depuis le cache expireront et retourneront une erreur après retrans tentatives. La combinaison avec l'option de montage par défaut hard implique que les opérations non mises en cache continueront à être retentées jusqu'à ce qu'une réponse soit reçue du serveur.
Remarque : l'option de montage par défaut est nosoftreval qui interdit le retour au cache lorsque la revalidation échoue, et suit plutôt le comportement dicté par l'option de montage hard ou soft.
intr / nointr
Cette option est fournie pour des raisons de compatibilité ascendante. Elle est ignorée après le noyau 2.6.25.
timeo=n
Le temps en décisecondes (dixièmes de seconde) pendant lequel le client NFS attend une réponse avant de retenter une requête NFS.
Pour NFS sur TCP, la valeur timeo par défaut est 600 (60 secondes). Le client NFS effectue une exponentiation arithmétique linéaire : après chaque retransmission, le délai d'attente est augmenté de timeo jusqu'à un maximum de 600 secondes.
Cependant, pour NFS sur UDP, le client utilise un algorithme adaptatif pour estimer une valeur de délai d'attente appropriée pour les types de requêtes fréquemment utilisés (tels que les requêtes READ et WRITE), mais utilise le paramètre timeo pour les types de requêtes peu fréquemment utilisés (tels que les requêtes FSINFO). Si l'option timeo n'est pas spécifiée, les types de requêtes peu fréquemment utilisés sont retentés après 1,1 seconde. Après chaque retransmission, le client NFS double le délai d'attente pour cette requête, jusqu'à une durée maximale de délai d'attente de 60 secondes.
Toute valeur de timeo supérieure à la valeur par défaut sera définie à la valeur par défaut. Pour TCP et RDMA, la valeur par défaut est 600 (60 secondes). Pour UDP, la valeur par défaut est 60 (6 secondes).
retrans=n
Le nombre de fois où le client NFS retente une requête avant de tenter une action de récupération supplémentaire. Si l'option retrans n'est pas spécifiée, le client NFS essaie trois fois chaque requête UDP et deux fois chaque requête TCP.
Le client NFS génère un message "serveur non répondant" après retrans tentatives, puis tente une récupération supplémentaire (en fonction de si l'option de montage hard est activée).
rsize=n
Le nombre maximum d'octets dans chaque requête de lecture réseau que le client NFS peut recevoir lors de la lecture de données à partir d'un fichier sur un serveur NFS. La taille réelle de la charge utile des données de chaque requête NFS READ est égale ou inférieure au réglage rsize. La plus grande charge utile de lecture prise en charge par le client NFS Linux est de 1 048 576 octets (un mégaoctet).
La valeur autorisée de rsize est un multiple entier positif de la taille de page du système ou une puissance de deux si elle est inférieure à la taille de page du système. Les valeurs rsize spécifiées inférieures à 1024 sont remplacées par 4096 ; les valeurs supérieures à 1048576 sont remplacées par 1048576. Si une valeur spécifiée est dans la plage prise en charge mais n'est pas une valeur autorisée, elle est arrondie à la valeur autorisée la plus proche.
Si une valeur rsize n'est pas spécifiée, ou si la valeur rsize spécifiée est plus grande que le maximum que le client ou le serveur peuvent prendre en charge, le client et le serveur négocient la plus grande valeur rsize qu'ils peuvent tous deux prendre en charge.

wsize=n
Le nombre maximum d'octets par requête d'écriture réseau que le client NFS peut envoyer lors de l'écriture de données dans un fichier sur un serveur NFS. La taille réelle de la charge utile de données de chaque requête d'écriture NFS est égale ou inférieure au réglage wsize. La plus grande charge utile d'écriture prise en charge par le client NFS Linux est de 1 048 576 octets (un mégaoctet).
Similaire à rsize, la valeur wsize autorisée est un multiple entier positif de la taille de page du système ou une puissance de deux si elle est inférieure à la taille de page du système. Les valeurs wsize spécifiées inférieures à 1024 sont remplacées par 4096 ; les valeurs supérieures à 1048576 sont remplacées par 1048576. Si une valeur spécifiée est dans la plage prise en charge mais pas une valeur autorisée, elle est arrondie à la valeur autorisée la plus proche.
Si une valeur wsize n'est pas spécifiée, ou si la valeur wsize spécifiée est supérieure au maximum que le client ou le serveur peut prendre en charge, le client et le serveur négocient la plus grande valeur wsize qu'ils peuvent tous deux prendre en charge.
L'option de montage wsize spécifiée sur la ligne de commande mount(8) apparaît dans le fichier /etc/mtab. Cependant, la valeur wsize effective négociée par le client et le serveur est signalée dans le fichier /proc/mounts.
ac / noac
Sélectionne si le client peut mettre en cache les attributs de fichier. Si aucune des options n'est spécifiée (ou si ac est spécifié), le client met en cache les attributs de fichier.
Pour améliorer les performances, les clients NFS mettent en cache les attributs de fichier. Toutes les quelques secondes, un client NFS vérifie la version du serveur des attributs de chaque fichier pour les mises à jour. Les modifications qui se produisent sur le serveur pendant ces petits intervalles restent indétectées jusqu'à ce que le client vérifie à nouveau le serveur. L'option noac empêche les clients de mettre en cache les attributs de fichier afin que les applications puissent détecter plus rapidement les modifications de fichier sur le serveur.
En plus d'empêcher le client de mettre en cache les attributs de fichier, l'option noac force les écritures d'application à devenir synchrones, de sorte que les modifications locales d'un fichier deviennent immédiatement visibles sur le serveur. Ainsi, d'autres clients peuvent détecter rapidement les écritures récentes lorsqu'ils vérifient les attributs du fichier.
L'utilisation de l'option noac offre une meilleure cohérence de cache entre les clients NFS accédant aux mêmes fichiers, mais elle entraîne une pénalité de performance importante. Par conséquent, une utilisation judicieuse du verrouillage de fichier est encouragée à la place. La section COHÉRENCE DES DONNÉES ET DES MÉTADONNÉES contient une discussion détaillée de ces compromis.
acregmin=n
Le temps minimum (en secondes) pendant lequel le client NFS met en cache les attributs d'un fichier régulier avant de demander de nouvelles informations d'attributs à un serveur. Si cette option n'est pas spécifiée, le client NFS utilise un minimum de 3 secondes. Voir la section COHÉRENCE DES DONNÉES ET DES MÉTADONNÉES pour une discussion complète de la mise en cache des attributs.
acregmax=n
Le temps maximum (en secondes) pendant lequel le client NFS met en cache les attributs d'un fichier régulier avant de demander de nouvelles informations d'attributs à un serveur. Si cette option n'est pas spécifiée, le client NFS utilise un maximum de 60 secondes. Voir la section COHÉRENCE DES DONNÉES ET DES MÉTADONNÉES pour une discussion complète de la mise en cache des attributs.
acdirmin=n
Le temps minimum (en secondes) pendant lequel le client NFS met en cache les attributs d'un répertoire avant de demander de nouvelles informations d'attributs à un serveur. Si cette option n'est pas spécifiée, le client NFS utilise un minimum de 30 secondes. Voir la section COHÉRENCE DES DONNÉES ET DES MÉTADONNÉES pour une discussion complète de la mise en cache des attributs.
acdirmax=n
Le temps maximum (en secondes) pendant lequel le client NFS met en cache les attributs d'un répertoire avant de demander de nouvelles informations d'attributs à un serveur. Si cette option n'est pas spécifiée, le client NFS utilise un maximum de 60 secondes. Voir la section COHÉRENCE DES DONNÉES ET DES MÉTADONNÉES pour une discussion complète de la mise en cache des attributs.
actimeo=n
L'utilisation de actimeo définit acregmin, acregmax, acdirmin et acdirmax à la même valeur. Si cette option n'est pas spécifiée, le client NFS utilise les valeurs par défaut pour chacune de ces options listées ci-dessus.
bg / fg
Détermine le comportement de la commande mount(8) si une tentative de montage d'une exportation échoue. L'option fg fait que mount(8) se termine avec un statut d'erreur si une partie de la demande de montage expire ou échoue complètement. C'est ce qu'on appelle un montage "en avant", et c'est le comportement par défaut si ni l'option de montage fg ni bg n'est spécifiée.
Si l'option bg est spécifiée, une expiration ou une défaillance entraîne la création d'un processus enfant par la commande mount(8) qui continue de tenter de monter l'exportation. Le processus parent retourne immédiatement avec un code de sortie zéro. C'est ce qu'on appelle un montage "en arrière-plan".
Si le répertoire de point de montage local est manquant, la commande mount(8) agit comme si la demande de montage avait expiré. Cela permet aux montages NFS imbriqués spécifiés dans /etc/fstab de se dérouler dans n'importe quel ordre pendant l'initialisation du système, même si certains serveurs NFS ne sont pas encore disponibles. Alternativement, ces problèmes peuvent être résolus à l'aide d'un automonteur (voir automount(8) pour plus de détails).
nconnect=n
Lors de l'utilisation d'un protocole orienté connexion tel que TCP, il peut être avantageux de configurer plusieurs connexions entre le client et le serveur. Par exemple, si vos clients et/ou serveurs sont équipés de plusieurs cartes réseau (NIC), l'utilisation de plusieurs connexions pour répartir la charge peut améliorer les performances globales. Dans de tels cas, l'option nconnect permet à l'utilisateur de spécifier le nombre de connexions qui doivent être établies entre le client et le serveur, jusqu'à une limite de 16.
Notez que l'option nconnect peut également être utilisée par certains pilotes pNFS pour décider du nombre de connexions à établir avec les serveurs de données.
rdirplus / nordirplus
Sélectionne s'il faut utiliser les requêtes READDIRPLUS NFS v3 ou v4. Si cette option n'est pas spécifiée, le client NFS utilise une heuristique pour optimiser les performances en choisissant entre READDIR et READDIRPLUS en fonction de la fréquence à laquelle le processus appelant utilise les attributs supplémentaires renvoyés par READDIRPLUS. Certaines applications obtiennent de meilleures performances si le client utilise uniquement les requêtes READDIR pour tous les répertoires.
rdirplus={none|force}
Si réglé sur "force", le client NFS tente toujours d'utiliser les requêtes READDIRPLUS. S'il est réglé sur "none", le comportement est le même que nordirplus.
retry=n
Le nombre de minutes pendant lesquelles la commande mount(8) retente une opération de montage NFS en avant ou en arrière-plan avant d'abandonner. Si cette option n'est pas spécifiée, la valeur par défaut pour les montages en avant est de 2 minutes, et la valeur par défaut pour les montages en arrière-plan est de 10000 minutes (80 minutes avant une semaine). Si une valeur de zéro est spécifiée, la commande mount(8) se termine immédiatement après le premier échec.
Notez que cela n'affecte que le nombre de tentatives et non le délai causé par chaque tentative. Pour UDP, chaque tentative prend le temps déterminé par les options timeo et retrans, qui par défaut sera d'environ 7 secondes. Pour TCP, la valeur par défaut est de 3 minutes, mais les délais d'expiration des connexions TCP du système limiteront parfois le délai d'expiration de chaque retransmission à environ 2 minutes.
sec=flavors
Une liste de saveurs de sécurité, séparées par des deux-points, à utiliser pour accéder aux fichiers sur l'exportation montée. Si le serveur ne prend pas en charge l'une de ces saveurs, l'opération de montage échoue. Si sec= n'est pas spécifié, le client tente de trouver une saveur de sécurité que le client et le serveur prennent en charge. Les saveurs valides sont none, sys, krb5, krb5i et krb5p. Reportez-vous à la section CONSIDÉRATIONS DE SÉCURITÉ pour plus de détails.
sharecache / nosharecache
Détermine comment le cache de données et le cache d'attributs du client sont partagés lors du montage de la même exportation plus d'une fois simultanément. L'utilisation du même cache réduit les besoins en mémoire du client et présente un contenu de fichier identique aux applications lorsque le même fichier distant est accédé via différents points de montage.
Si aucune des options n'est spécifiée, ou si l'option sharecache est spécifiée, alors un seul cache est utilisé pour tous les points de montage qui accèdent à la même exportation. Si l'option nosharecache est spécifiée, alors ce point de montage obtient un cache unique. Notez que lorsque les caches de données et d'attributs sont partagés, les options de montage du premier point de montage prennent effet pour les montages simultanés ultérieurs de la même exportation.
À partir du noyau 2.6.18, le comportement spécifié par nosharecache est le comportement de mise en cache hérité. Ceci est considéré comme un risque de données car plusieurs copies mises en cache du même fichier sur le même client peuvent se désynchroniser suite à une mise à jour locale de l'une des copies.
resvport / noresvport
Spécifie si le client NFS doit utiliser un port source privilégié lors de la communication avec un serveur NFS pour ce point de montage. Si cette option n'est pas spécifiée, ou si l'option resvport est spécifiée, le client NFS utilise un port source privilégié. Si l'option noresvport est spécifiée, le client NFS utilise un port source non privilégié. Cette option est prise en charge dans les noyaux 2.6.28 et versions ultérieures.

Détermine le délai maximal avant expiration du cache des attributs du répertoire. La valeur par défaut est de 60 secondes.

Détermine le délai maximal avant expiration du cache des attributs du fichier régulier. La valeur par défaut est de 60 secondes.

Détermine le délai minimal avant expiration du cache des attributs du fichier régulier. La valeur par défaut est de 30 secondes.
acdirmin=n
Détermine le délai minimal avant expiration du cache des attributs du répertoire. La valeur par défaut est de 30 secondes.

Active/désactive le cache des attributs de fichier et de répertoire. Le cache des attributs est activé par défaut. Il est recommandé de ne pas désactiver le cache des attributs sauf si les raisons de performance sont évidentes.

Les opérations de lecture/écriture s'effectuent de manière asynchrone. C'est le comportement par défaut. L'utilisation de sync peut dégrader significativement les performances.

Contrôle la mise à jour des timestamps d'accès aux fichiers. Par défaut, les timestamps d'accès sont mis à jour (atime). L'utilisation de noatime peut améliorer les performances car elle évite d'écrire sur le serveur pour chaque lecture.

Spécifie le délai de grâce pour le montage après une panne. La valeur par défaut est de 15 secondes.
bsize=n
Spécifie la taille de bloc NFS. La valeur par défaut est de 1 Ko.

Spécifie le délai avant expiration du cache de données. La valeur par défaut est de 15 secondes.

Spécifie la taille maximale de données envoyées lors d'une opération de lecture (read). La valeur par défaut est de 8 Ko.
fattr=n
Spécifie la taille maximale des attributs de fichier. La valeur par défaut est de 1 Ko.
fgcolor3
Indique que le serveur utilise une couleur 3 pour les opérations de fichier. Cette option n'est pas prise en charge par le client NFS Linux.
filesize=n
Spécifie la taille maximale du fichier. La valeur par défaut est de 1 Go.
hard / soft
Spécifie si le client doit réessayer indéfiniment les requêtes en cas d'échec du serveur (hard) ou renvoyer une erreur après un certain nombre de tentatives (soft). Il est fortement recommandé d'utiliser hard pour éviter la perte de données. L'utilisation de soft peut entraîner des corruptions de données et est déconseillée, sauf pour les systèmes de fichiers en lecture seule.
intr / nointr
Permet d'interrompre une requête bloquée avec hard. Par défaut, les requêtes sont interrompues (intr). Si nointr est spécifié, les requêtes ne peuvent pas être interrompues.

Contrôle la mise à jour des timestamps d'accès aux fichiers en utilisant une méthode à faible latence. Par défaut, les timestamps d'accès sont mis à jour (llatime). L'utilisation de nollandtime peut améliorer les performances car elle évite d'écrire sur le serveur pour chaque lecture.
llock=n
Spécifie le type de verrouillage de fichier. La valeur par défaut est 0.
localplusverbs
Cette option est utilisée avec les connexions RDMA pour permettre aux clients de se connecter via des ports sources non privilégiés.
Reportez-vous à la section CONSIDÉRATIONS DE SÉCURITÉ pour des détails importants.
lookupcache=mode
Spécifie comment le noyau gère son cache des entrées de répertoire pour un point de montage donné. mode peut être l'un de all, none, pos, ou positive. Cette option est prise en charge dans les noyaux 2.6.28 et ultérieurs.
Le client NFS Linux met en cache le résultat de toutes les requêtes NFS LOOKUP. Si l'entrée de répertoire demandée existe sur le serveur, le résultat est appelé positif. Si l'entrée de répertoire demandée n'existe pas sur le serveur, le résultat est appelé négatif.
Si cette option n'est pas spécifiée, ou si all est spécifié, le client suppose que les deux types d'entrées de cache de répertoire sont valides jusqu'à l'expiration des attributs du répertoire parent mis en cache.
Si pos ou positive est spécifié, le client suppose que les entrées positives sont valides jusqu'à l'expiration des attributs du répertoire parent mis en cache, mais revalide toujours les entrées négatives avant qu'une application ne puisse les utiliser.
Si none est spécifié, le client revalide les deux types d'entrées de cache de répertoire avant qu'une application ne puisse les utiliser. Cela permet une détection rapide des fichiers créés ou supprimés par d'autres clients, mais peut avoir un impact sur les performances de l'application et du serveur.
La section COHÉRENCE DES DONNÉES ET DES MÉTADONNÉES contient une discussion détaillée de ces compromis.
fsc / nofsc
Active/Désactive le cache des pages de données (en lecture seule) sur le disque local en utilisant le mécanisme FS-Cache. Voir cachefilesd(8) et <kernel_source>/Documentation/filesystems/caching pour plus de détails sur la configuration du mécanisme FS-Cache. La valeur par défaut est nofsc.
sloppy
L'option sloppy est une alternative à la spécification de mount.nfs -s option.
xprtsec=politique
Spécifie l'utilisation de la sécurité de la couche de transport pour protéger le trafic réseau NFS au nom de ce point de montage. politique peut être none, tls, ou mtls.
Si none est spécifié, la sécurité de la couche de transport est forcée à désactivée, même si le serveur NFS prend en charge la sécurité de la couche de transport.
Si tls est spécifié, le client utilise RPC-with-TLS pour assurer la confidentialité en transit.
Si mtls est spécifié, le client utilise RPC-with-TLS pour s'authentifier et pour assurer la confidentialité en transit.
Si tls ou mtls est spécifié et que le serveur ne prend pas en charge RPC-with-TLS ou que l'authentification de l'homologue échoue, la tentative de montage échoue.
Si l'option xprtsec= n'est pas spécifiée, le comportement par défaut dépend de la version du noyau, mais est généralement équivalent à xprtsec=none.
noalignwrite
Cette option désactive le comportement par défaut d'extension des opérations d'écriture tamponnées aux limites de pages complètes.
Normalement, le client NFS arrondit les écritures tamponnées non alignées à la taille de page système, ce qui peut entraîner des "écritures perdues" lorsque plusieurs clients écrivent simultanément dans des régions distinctes et non chevauchantes. Utilisez cette option lorsque vos applications effectuent des écritures tamponnées non alignées et que vous pouvez garantir que les régions de fichiers ne se chevauchent pas, évitant ainsi le besoin de verrouillage de fichiers.

Options pour les versions NFS 2 et 3 uniquement

Utilisez ces options, ainsi que les options de la sous-section ci-dessus, pour les versions NFS 2 et 3 uniquement.

proto=netid
Le netid détermine le transport utilisé pour communiquer avec le serveur NFS. Les options disponibles sont udp, udp6, tcp, tcp6, rdma, et rdma6. Ceux qui se terminent par 6 utilisent des adresses IPv6 et ne sont disponibles que si le support de TI-RPC est intégré. Les autres utilisent des adresses IPv4.

MÉTHODES DE TRANSPORT

Les clients NFS envoient des requêtes aux serveurs NFS via des appels de procédure distante, ou RPC. Le client RPC découvre automatiquement les points d'accès des services distants, gère l'authentification par requête, ajuste les paramètres des requêtes pour différentes représentations d'octets entre le client et le serveur, et retransmet les requêtes qui ont pu être perdues par le réseau ou le serveur. Les requêtes et les réponses RPC transitent sur un transport réseau.

Dans la plupart des cas, la commande mount(8), le client NFS et le serveur NFS peuvent négocier automatiquement les paramètres de transport et de taille de transfert de données appropriés pour un point de montage. Dans certains cas, cependant, il est utile de spécifier ces paramètres explicitement à l'aide des options de montage.

Traditionnellement, les clients NFS utilisaient exclusivement le transport UDP pour transmettre les requêtes aux serveurs. Bien que son implémentation soit simple, NFS sur UDP présente de nombreuses limitations qui empêchent un fonctionnement fluide et de bonnes performances dans certains environnements de déploiement courants. Même un taux de perte de paquets insignifiant entraîne la perte de requêtes NFS entières ; par conséquent, les délais de retransmission sont généralement inférieurs à la seconde pour permettre aux clients de récupérer rapidement des requêtes abandonnées, mais cela peut entraîner un trafic réseau superflu et une charge serveur accrue.

Cependant, UDP peut être très efficace dans des contextes spécialisés où la MTU du réseau est grande par rapport à la taille du transfert de données de NFS (par exemple, les environnements réseau qui activent les trames Ethernet jumbo). Dans de tels environnements, il est conseillé de réduire les paramètres rsize et wsize afin que chaque requête de lecture ou d'écriture NFS tienne dans quelques trames réseau (ou même dans une seule trame). Cela réduit la probabilité que la perte d'une seule trame réseau de taille MTU entraîne la perte d'une requête de lecture ou d'écriture complète.

TCP est le protocole de transport par défaut utilisé pour toutes les implémentations NFS modernes. Il fonctionne bien dans presque tous les environnements réseau imaginables et offre d'excellentes garanties contre la corruption des données causée par l'imprudence du réseau. TCP est souvent une exigence pour monter un serveur via un pare-feu réseau.

Dans des circonstances normales, les réseaux perdent des paquets beaucoup plus fréquemment que les serveurs NFS n'abandonnent des requêtes. Par conséquent, un délai de retransmission agressif pour NFS sur TCP est inutile. Les délais typiques pour NFS sur TCP se situent entre une et dix minutes. Une fois que le client a épuisé ses retransmissions (la valeur de l'option de montage retrans), il suppose qu'une partition réseau s'est produite et tente de se reconnecter au serveur sur une nouvelle socket. Étant donné que TCP lui-même rend le transfert de données réseau fiable, rsize et wsize peuvent être autorisés à conserver leurs valeurs par défaut, les plus grandes prises en charge par le client et le serveur, indépendamment de la taille MTU du réseau.

Utilisation de l'option de montage mountproto

Cette section s'applique uniquement aux montages NFS version 3, car NFS version 4 n'utilise pas de protocole distinct pour les requêtes de montage.

Le client NFS sous Linux peut utiliser un transport différent pour contacter le service rpcbind du serveur NFS, son service mountd, son service Network Lock Manager (NLM) et son service NFS. Les transports exacts utilisés par le client NFS sous Linux pour chaque point de montage dépendent des paramètres des options de transport de montage, qui incluent proto, mountproto, udp et tcp.

Le client envoie des notifications Network Status Manager (NSM) via UDP, quel que soit le transport spécifié, mais écoute les notifications NSM du serveur sur UDP et TCP. Le protocole NFS Access Control List (NFSACL) partage le même transport que le service NFS principal.

Si aucune option de transport n'est spécifiée, le client NFS sous Linux utilise UDP pour contacter le service mountd du serveur et TCP pour contacter ses services NLM et NFS par défaut.

Si le serveur ne prend pas en charge ces transports pour ces services, la commande mount(8) tente de découvrir ce que le serveur prend en charge, puis réessaie la requête de montage une fois en utilisant les transports découverts. Si le serveur n'annonce aucun transport pris en charge par le client ou s'il est mal configuré, la requête de montage échoue. Si l'option bg est activée, la commande mount passe en arrière-plan et continue de tenter la requête de montage spécifiée.

Lorsque l'option proto, l'option udp, ou l'option tcp est spécifiée mais que l'option mountproto ne l'est pas, le transport spécifié est utilisé pour contacter le service mountd du serveur et pour les services NLM et NFS.

Si l'option mountproto est spécifiée mais que les options proto, udp ou tcp ne le sont pas, alors le transport spécifié est utilisé pour la requête mountd initiale, mais la commande mount tente de découvrir ce que le serveur prend en charge pour le protocole NFS, privilégiant TCP si les deux transports sont pris en charge.

Si les options mountproto et proto (ou udp ou tcp) sont toutes deux spécifiées, alors le transport spécifié par l'option mountproto est utilisé pour la requête mountd initiale, et le transport spécifié par l'option proto (ou les options udp ou tcp) est utilisé pour NFS, quel que soit l'ordre dans lequel ces options apparaissent. Aucune découverte automatique de service n'est effectuée si ces options sont spécifiées.

Si l'une des options proto, udp, tcp, ou mountproto est spécifiée plus d'une fois sur la même ligne de commande de montage, alors la valeur de la dernière occurrence de chacune de ces options prend effet.

Utilisation de NFS sur UDP sur des liaisons haute vitesse

L'utilisation de NFS sur UDP sur des liaisons haute vitesse comme le Gigabit peut causer une corruption silencieuse des données.

Le problème peut être déclenché sous forte charge et est causé par des problèmes de réassemblage de fragments IP. Les lectures et écritures NFS transmettent typiquement des paquets UDP de 4 Kilooctets ou plus, qui doivent être divisés en plusieurs fragments pour être envoyés sur la liaison Ethernet, qui limite par défaut les paquets à 1500 octets. Ce processus se produit au niveau réseau IP et est appelé fragmentation.

Afin d'identifier les fragments qui appartiennent ensemble, IP attribue une valeur ID IP de 16 bits à chaque paquet ; les fragments générés à partir du même paquet UDP auront le même ID IP. Le système récepteur collectera ces fragments et les combinera pour former le paquet UDP d'origine. Ce processus est appelé réassemblage. Le délai d'attente par défaut pour le réassemblage de paquets est de 30 secondes ; si la pile réseau ne reçoit pas tous les fragments d'un paquet donné dans cet intervalle, elle suppose que le ou les fragments manquants ont été perdus et écarte ceux qu'elle a déjà reçus.

Le problème créé sur les liaisons haute vitesse est qu'il est possible d'envoyer plus de 65536 paquets en 30 secondes. En fait, avec un trafic NFS intense, on peut observer que les ID IP se répètent après environ 5 secondes.

Cela a de graves conséquences sur le réassemblage : si un fragment est perdu, un autre fragment provenant d'un autre paquet mais ayant le même ID IP arrivera dans le délai de 30 secondes, et la pile réseau combinera ces fragments pour former un nouveau paquet. La plupart du temps, les couches réseau supérieures à IP détecteront ce réassemblage incorrect - dans le cas d'UDP, la somme de contrôle UDP, qui est une somme de contrôle de 16 bits sur la charge utile complète du paquet, ne correspondra généralement pas, et UDP écartera le paquet erroné.

Cependant, la somme de contrôle UDP n'a que 16 bits, il y a donc une chance sur 65536 qu'elle corresponde même si la charge utile du paquet est complètement aléatoire (ce qui n'est souvent pas le cas). Si tel est le cas, une corruption silencieuse des données se produira.

Ce potentiel doit être pris au sérieux, du moins sur Gigabit Ethernet. Les vitesses réseau de 100 Mbit/s devraient être considérées comme moins problématiques, car avec la plupart des schémas de trafic, l'enroulement de l'ID IP prendra beaucoup plus de temps que 30 secondes.

Il est donc fortement recommandé d'utiliser NFS sur TCP lorsque cela est possible, car TCP n'effectue pas de fragmentation.

Si vous devez absolument utiliser NFS sur UDP sur Gigabit Ethernet, certaines mesures peuvent être prises pour atténuer le problème et réduire la probabilité de corruption :

Trames jumbo :
De nombreuses cartes réseau Gigabit sont capables de transmettre des trames plus grandes que la limite de 1500 octets de l'Ethernet traditionnel, typiquement 9000 octets. L'utilisation de trames jumbo de 9000 octets vous permettra d'exécuter NFS sur UDP à une taille de page de 8 Ko sans fragmentation. Bien entendu, cela n'est réalisable que si toutes les stations impliquées prennent en charge les trames jumbo.
Pour permettre à une machine d'envoyer des trames jumbo sur des cartes qui le prennent en charge, il suffit de configurer l'interface pour une valeur MTU de 9000.
Délai de réassemblage inférieur :
En réduisant ce délai d'attente en dessous du temps nécessaire au compteur d'ID IP pour s'enrouler, le réassemblage incorrect des fragments peut également être évité. Pour ce faire, il suffit d'écrire la nouvelle valeur de délai d'attente (en secondes) dans le fichier /proc/sys/net/ipv4/ipfrag_time.
Une valeur de 2 secondes réduira considérablement la probabilité de conflits d'IPID sur une liaison Gigabit unique, tout en permettant un délai d'attente raisonnable lors de la réception de trafic fragmenté de pairs distants.

COHÉRENCE DES DONNÉES ET DES MÉTADONNÉES

Certains systèmes de fichiers en cluster modernes fournissent une cohérence de cache parfaite entre leurs clients. Une cohérence de cache parfaite entre des clients NFS disparates est coûteuse à obtenir, surtout sur les réseaux étendus. Ainsi, NFS se contente d'une cohérence de cache plus faible qui satisfait les exigences de la plupart des types de partage de fichiers.

Cohérence du cache Close-to-open

-to-open_cache_consistency'>Cohérence de cache fermer-ouvrir

Généralement, le partage de fichiers est entièrement séquentiel. Le client A ouvre un fichier, y écrit quelque chose, puis le ferme. Ensuite, le client B ouvre le même fichier et lit les modifications.

Lorsqu'une application ouvre un fichier stocké sur un serveur NFS version 3, le client NFS vérifie que le fichier existe sur le serveur et que l'ouvreur y est autorisé en envoyant une requête GETATTR ou ACCESS. Le client NFS envoie ces requêtes indépendamment de la fraîcheur des attributs mis en cache du fichier.

Lorsque l'application ferme le fichier, le client NFS renvoie toutes les modifications en attente au fichier afin que le prochain ouvreur puisse voir les modifications. Cela donne également au client NFS une occasion de signaler les erreurs d'écriture à l'application via le code de retour de close(2).

Le comportement de vérification à l'ouverture et de vidage à la fermeture est appelé cohérence de cache fermer-ouvrir, ou CTO. Il peut être désactivé pour un point de montage entier à l'aide de l'option de montage nocto.

Cohérence de cache faible

Il existe toujours des possibilités pour que le cache de données d'un client contienne des données obsolètes. Le protocole NFS version 3 a introduit la « cohérence de cache faible » (également connue sous le nom de WCC) qui fournit un moyen efficace de vérifier les attributs d'un fichier avant et après une seule requête. Cela permet à un client d'identifier les modifications qui auraient pu être effectuées par d'autres clients.

Lorsqu'un client utilise de nombreuses opérations concurrentes qui mettent à jour le même fichier en même temps (par exemple, lors d'une écriture différée asynchrone), il est toujours difficile de dire si ce sont les mises à jour de ce client ou celles d'un autre client qui ont modifié le fichier.

Mise en cache des attributs

Utilisez l'option de montage noac pour obtenir la cohérence du cache d'attributs entre plusieurs clients. Presque toutes les opérations du système de fichiers vérifient les informations d'attributs des fichiers. Le client conserve ces informations en cache pendant un certain temps afin de réduire la charge du réseau et du serveur. Lorsque noac est activé, le cache d'attributs de fichiers du client est désactivé, de sorte que chaque opération qui nécessite de vérifier les attributs d'un fichier est forcée de retourner au serveur. Cela permet à un client de voir les modifications apportées à un fichier très rapidement, au prix de nombreuses opérations réseau supplémentaires.

Veillez à ne pas confondre l'option noac avec « pas de mise en cache de données ». L'option de montage noac empêche le client de mettre en cache les métadonnées des fichiers, mais il existe toujours des courses qui peuvent entraîner une incohérence du cache de données entre le client et le serveur.

Le protocole NFS n'est pas conçu pour prendre en charge une véritable cohérence de cache de système de fichiers en cluster sans un certain type de sérialisation d'application. Si une cohérence de cache absolue entre les clients est requise, les applications doivent utiliser le verrouillage de fichiers. Alternativement, les applications peuvent également ouvrir leurs fichiers avec l'indicateur O_DIRECT pour désactiver complètement la mise en cache des données.

Maintenance des horodatages de fichiers

Les serveurs NFS sont responsables de la gestion des horodatages de fichiers et de répertoires (atime, ctime et mtime). Lorsqu'un fichier est accédé ou mis à jour sur un serveur NFS, les horodatages du fichier sont mis à jour comme ils le seraient sur un système de fichiers local à une application.

Les clients NFS mettent en cache les attributs des fichiers, y compris les horodatages. Les horodatages d'un fichier sont mis à jour sur les clients NFS lorsque ses attributs sont récupérés du serveur NFS. Il peut donc y avoir un certain délai avant que les mises à jour d'horodatage sur un serveur NFS n'apparaissent aux applications sur les clients NFS.

Pour se conformer à la norme POSIX des systèmes de fichiers, le client NFS de Linux s'appuie sur les serveurs NFS pour maintenir correctement à jour les horodatages mtime et ctime d'un fichier. Il le fait en vidant les modifications locales des données vers le serveur avant de renvoyer mtime aux applications via des appels système tels que stat(2).

Le client Linux gère les mises à jour de atime de manière plus souple, cependant. Les clients NFS maintiennent de bonnes performances en mettant en cache les données, mais cela signifie que les lectures d'applications, qui mettent normalement à jour atime, ne sont pas reflétées sur le serveur où le atime d'un fichier est réellement maintenu.

En raison de ce comportement de mise en cache, le client NFS de Linux ne prend pas en charge les options de montage génériques relatives à atime. Voir mount(8) pour plus de détails sur ces options.

En particulier, les options de montage atime/noatime, diratime/nodiratime, relatime/norelatime et strictatime/nostrictatime n'ont aucun effet sur les montages NFS.

/proc/mounts peut indiquer que l'option de montage relatime est définie sur les montages NFS, mais en fait, les sémantiques de atime sont toujours telles que décrites ici, et ne sont pas comme les sémantiques de relatime.

Mise en cache des entrées de répertoire

Le client NFS de Linux met en cache le résultat de toutes les requêtes LOOKUP NFS. Si l'entrée de répertoire demandée existe sur le serveur, le résultat est appelé un résultat de recherche positif. Si l'entrée de répertoire demandée n'existe pas sur le serveur (c'est-à-dire que le serveur a renvoyé ENOENT), le résultat est appelé un résultat de recherche négatif.

Pour détecter lorsque des entrées de répertoire ont été ajoutées ou supprimées sur le serveur, le client NFS de Linux surveille le mtime d'un répertoire. Si le client détecte un changement dans le mtime d'un répertoire, il abandonne tous les résultats LOOKUP mis en cache pour ce répertoire. Étant donné que le mtime du répertoire est un attribut mis en cache, il peut s'écouler un certain temps avant qu'un client ne remarque qu'il a changé. Voir les descriptions des options de montage acdirmin, acdirmax et noac pour plus d'informations sur la durée pendant laquelle le mtime d'un répertoire est mis en cache.

La mise en cache des entrées de répertoire améliore les performances des applications qui ne partagent pas de fichiers avec des applications sur d'autres clients. L'utilisation d'informations mises en cache sur les répertoires peut toutefois interférer avec les applications qui s'exécutent simultanément sur plusieurs clients et qui ont besoin de détecter rapidement la création ou la suppression de fichiers. L'option de montage lookupcache permet un certain réglage du comportement de mise en cache des entrées de répertoire.

Avant la version 2.6.28 du noyau, le client NFS de Linux ne suivait que les résultats de recherche positifs. Cela permettait aux applications de détecter rapidement les nouvelles entrées de répertoire créées par d'autres clients tout en offrant certains des avantages de performance de la mise en cache. Si une application dépend du comportement précédent de mise en cache des recherches du client NFS de Linux, vous pouvez utiliser lookupcache=positive.

Si le client ignore son cache et valide chaque requête de recherche d'application avec le serveur, ce client peut détecter immédiatement quand une nouvelle entrée de répertoire a été créée ou supprimée par un autre client. Vous pouvez spécifier ce comportement en utilisant lookupcache=none. Les requêtes NFS supplémentaires nécessaires si le client ne met pas en cache les entrées de répertoire peuvent entraîner une pénalité de performance. La désactivation de la mise en cache des recherches devrait entraîner une pénalité de performance moindre que l'utilisation de noac, et n'a aucun effet sur la façon dont le client NFS met en cache les attributs des fichiers.

L'option de montage sync

Le client NFS traite l'option de montage sync différemment des autres systèmes de fichiers (voir mount(8) pour une description des options de montage génériques sync et async). Si ni sync ni async n'est spécifié (ou si l'option async est spécifiée), le client NFS retarde l'envoi des écritures d'application au serveur jusqu'à ce que l'un des événements suivants se produise :

Une pression sur la mémoire force la récupération des ressources mémoire du système.
Une application vide les données du fichier explicitement avec sync(2), msync(2) ou fsync(3).
Une application ferme un fichier avec close(2).
Le fichier est verrouillé/déverrouillé via fcntl(2).

En d'autres termes, dans des circonstances normales, les données écrites par une application peuvent ne pas apparaître immédiatement sur le serveur qui héberge le fichier.

Si l'option sync est spécifiée sur un point de montage, tout appel système qui écrit des données dans les fichiers sur ce point de montage entraîne le vidage de ces données vers le serveur avant que l'appel système ne renvoie le contrôle à l'espace utilisateur. Cela offre une meilleure cohérence des caches de données entre les clients, mais au prix d'une performance significative.

Les applications peuvent utiliser l'indicateur d'ouverture O_SYNC pour forcer les écritures d'application sur des fichiers individuels à aller immédiatement sur le serveur sans utiliser l'option de montage sync.

Utilisation des verrous de fichiers avec NFS

Le protocole Network Lock Manager est un protocole auxiliaire distinct utilisé pour gérer les verrous de fichiers dans NFS version 3. Pour prendre en charge la récupération des verrous après un redémarrage du client ou du serveur, un second protocole auxiliaire - connu sous le nom de protocole Network Status Manager - est également requis. Dans NFS version 4, le verrouillage de fichiers est pris en charge directement dans le protocole NFS principal, et les protocoles auxiliaires NLM et NSM ne sont pas utilisés.

Dans la plupart des cas, les services NLM et NSM sont démarrés automatiquement, et aucune configuration supplémentaire n'est requise. Configurez tous les clients NFS avec des noms de domaine entièrement qualifiés pour garantir que les serveurs NFS puissent trouver les clients pour les informer des redémarrages de serveur.

NLM prend en charge uniquement les verrous de fichiers consultatifs. Pour verrouiller les fichiers NFS, utilisez fcntl(2) avec les commandes F_GETLK et F_SETLK. Le client NFS convertit les verrous de fichiers obtenus via flock(2) en verrous consultatifs.

Lors du montage de serveurs qui ne prennent pas en charge le protocole NLM, ou lors du montage d'un serveur NFS via un pare-feu qui bloque le port de service NLM, spécifiez l'option de montage nolock. Le verrouillage NLM doit être désactivé avec l'option nolock lors de l'utilisation de NFS pour monter /var car /var contient des fichiers utilisés par l'implémentation NLM sous Linux.

La spécification de l'option nolock peut également être conseillée pour améliorer les performances d'une application propriétaire qui s'exécute sur un seul client et utilise intensivement les verrous de fichiers.

Fonctionnalités de mise en cache de NFS version 4

Le comportement de mise en cache des données et des métadonnées des clients NFS version 4 est similaire à celui des versions antérieures. Cependant, NFS version 4 ajoute deux fonctionnalités qui améliorent le comportement du cache : les attributs de modification et la délégation de fichiers.

L'attribut de modification est une nouvelle partie des métadonnées de fichiers et de répertoires NFS qui suit les modifications des données. Il remplace l'utilisation des horodatages de modification et de changement d'un fichier pour permettre aux clients de valider le contenu de leurs caches. Les attributs de modification sont indépendants de la résolution des horodatages sur le serveur ou le client, cependant.

Une délégation de fichier est un contrat entre un client NFS version 4 et un serveur qui permet au client de traiter un fichier temporairement comme si aucun autre client n'y accédait. Le serveur promet de notifier le client (via une demande de rappel) si un autre client tente d'accéder à ce fichier. Une fois qu'un fichier a été délégué à un client, le client peut mettre en cache les données et les métadonnées de ce fichier de manière agressive sans contacter le serveur.

Les délégations de fichiers se présentent en deux versions : lecture et écriture. Une délégation de lecture signifie que le serveur notifie le client de tous les autres clients qui souhaitent écrire dans le fichier. Une délégation d'écriture signifie que le client est notifié des accesseurs en lecture ou en écriture.

Les serveurs accordent des délégations de fichiers lors de l'ouverture d'un fichier et peuvent rappeler les délégations à tout moment lorsqu'un autre client souhaite accéder au fichier d'une manière qui entre en conflit avec les délégations déjà accordées. Les délégations sur les répertoires ne sont pas prises en charge.

Afin de prendre en charge le rappel de délégation, le serveur vérifie le chemin de retour réseau vers le client lors du contact initial du client avec le serveur. Si un contact avec le client ne peut être établi, le serveur ne fait tout simplement aucune délégation à ce client.

CONSIDÉRATIONS DE SÉCURITÉ

Les serveurs NFS contrôlent l'accès aux données des fichiers, mais ils dépendent de leur implémentation RPC pour fournir l'authentification des requêtes NFS. Le contrôle d'accès traditionnel NFS imite le contrôle d'accès standard par bits de mode fourni dans les systèmes de fichiers locaux. L'authentification RPC traditionnelle utilise un nombre pour représenter chaque utilisateur (généralement l'uid de l'utilisateur), un nombre pour représenter le groupe de l'utilisateur (le gid de l'utilisateur) et un ensemble d'un maximum de 16 numéros de groupe auxiliaires pour représenter d'autres groupes dont l'utilisateur peut être membre.

En général, les données des fichiers et les valeurs d'ID utilisateur apparaissent en clair (c'est-à-dire « en clair ») sur le réseau. De plus, les versions 2 et 3 de NFS utilisent des protocoles de bande latérale distincts pour le montage, le verrouillage et le déverrouillage des fichiers, et le signalement de l'état système des clients et des serveurs. Ces protocoles auxiliaires n'utilisent aucune authentification.

En plus de combiner ces protocoles de bande latérale avec le protocole NFS principal, la version 4 de NFS introduit des formes plus avancées de contrôle d'accès, d'authentification et de protection des données en transit. La spécification NFS version 4 impose la prise en charge de l'authentification forte et des saveurs de sécurité qui fournissent une vérification d'intégrité et un chiffrement par RPC. Étant donné que NFS version 4 combine la fonctionnalité des protocoles de bande latérale dans le protocole NFS principal, les nouvelles fonctionnalités de sécurité s'appliquent à toutes les opérations NFS version 4, y compris le montage, le verrouillage de fichiers, etc. L'authentification RPCGSS peut également être utilisée avec les versions 2 et 3 de NFS, mais elle ne protège pas leurs protocoles de bande latérale.

L'option de montage sec spécifie la saveur de sécurité utilisée pour les opérations au nom des utilisateurs sur ce point de montage NFS. La spécification de sec=krb5 fournit une preuve cryptographique de l'identité d'un utilisateur dans chaque requête RPC. Cela fournit une vérification forte de l'identité des utilisateurs accédant aux données sur le serveur. Notez qu'une configuration supplémentaire au-delà de l'ajout de cette option de montage est nécessaire pour activer la sécurité Kerberos. Référez-vous à la page de manuel rpc.gssd(8) pour plus de détails.

Deux saveurs supplémentaires de sécurité Kerberos sont prises en charge : krb5i et krb5p. La saveur de sécurité krb5i fournit une garantie cryptographiquement forte que les données de chaque requête RPC n'ont pas été altérées. La saveur de sécurité krb5p chiffre chaque requête RPC pour éviter l'exposition des données pendant le transit sur le réseau ; cependant, attendez-vous à un certain impact sur les performances lors de l'utilisation de la vérification d'intégrité ou du chiffrement. Un support similaire pour d'autres formes de sécurité cryptographique est également disponible.

Passage de systèmes de fichiers NFS version 4

Le protocole NFS version 4 permet à un client de renégocier la saveur de sécurité lorsque le client entre dans un nouveau système de fichiers sur le serveur. La saveur nouvellement négociée n'affecte que les accès au nouveau système de fichiers.

Une telle négociation se produit généralement lorsqu'un client passe d'un pseudo-système de fichiers d'un serveur à l'un des systèmes de fichiers physiques exportés par le serveur, qui ont souvent des paramètres de sécurité plus restrictifs que le pseudo-système de fichiers.

Baux NFS version 4

Dans NFS version 4, un bail est une période pendant laquelle un serveur accorde irrévocablement des verrous de fichiers à un client. Une fois le bail expiré, le serveur peut révoquer ces verrous. Les clients renouvellent périodiquement leurs baux pour éviter la révocation des verrous.

Après le redémarrage d'un serveur NFS version 4, chaque client informe le serveur de l'état ouvert et verrouillé des fichiers sous son bail avant que l'opération ne puisse continuer. Si un client redémarre, le serveur libère tout état ouvert et verrouillé associé au bail de ce client.

Lors de l'établissement d'un bail, un client doit donc s'identifier auprès d'un serveur. Chaque client présente une chaîne de caractères arbitraire pour se distinguer des autres clients. L'administrateur du client peut compléter la chaîne d'identité par défaut à l'aide du paramètre de module nfs4.nfs4_unique_id pour éviter les collisions avec les chaînes d'identité d'autres clients.

Un client utilise également une saveur de sécurité et un principal uniques lors de l'établissement de son bail. Si deux clients présentent la même chaîne d'identité, un serveur peut utiliser les principaux du client pour les distinguer, empêchant ainsi en toute sécurité un client d'interférer avec le bail de l'autre.

Le client NFS Linux établit un bail sur chaque serveur NFS version 4. Les opérations de gestion des baux, telles que le renouvellement des baux, ne sont pas effectuées au nom d'un fichier, d'un verrou, d'un utilisateur ou d'un point de montage particulier, mais au nom du client qui possède ce bail. Un client utilise une chaîne d'identité, une saveur de sécurité et un principal cohérents à travers les redémarrages du client pour garantir que le serveur peut rapidement récupérer l'état des baux expirés.

Lorsque Kerberos est configuré sur un client NFS Linux (c'est-à-dire qu'il existe un fichier /etc/krb5.keytab sur ce client), le client tente d'utiliser une saveur de sécurité Kerberos pour ses opérations de gestion de bail. Kerberos assure une authentification sécurisée de chaque client. Par défaut, le client utilise le principal de service host/ ou nfs/ dans son fichier /etc/krb5.keytab à cet effet, comme décrit dans rpc.gssd(8).

Si le client a Kerberos configuré, mais pas le serveur, ou si le client n'a pas de fichier keytab ou les principaux de service requis, le client utilise AUTH_SYS et l'UID 0 pour la gestion des baux.

Utilisation de ports source non privilégiés

Les clients NFS communiquent généralement avec les serveurs NFS via des sockets réseau. Chaque extrémité d'un socket se voit attribuer une valeur de port, qui est simplement un nombre compris entre 1 et 65535 qui distingue les points d'extrémité des sockets à la même adresse IP. Un socket est défini de manière unique par un tuple qui comprend le protocole de transport (TCP ou UDP) et les valeurs de port et les adresses IP des deux extrémités.

Le client NFS peut choisir n'importe quelle valeur de port source pour ses sockets, mais choisit généralement un port privilégié. Un port privilégié est une valeur de port inférieure à 1024. Seul un processus doté de privilèges root peut créer un socket avec un port source privilégié.

La plage exacte des ports source privilégiés pouvant être choisis est définie par une paire de sysctls pour éviter de choisir un port bien connu, tel que le port utilisé par ssh. Cela signifie que le nombre de ports source disponibles pour le client NFS, et donc le nombre de connexions socket pouvant être utilisées simultanément, est pratiquement limité à quelques centaines.

Comme décrit ci-dessus, le schéma d'authentification NFS traditionnel par défaut, connu sous le nom d'AUTH_SYS, repose sur l'envoi de numéros UID et GID locaux pour identifier les utilisateurs effectuant des requêtes NFS. Un serveur NFS suppose que si une connexion provient d'un port privilégié, les numéros UID et GID des requêtes NFS sur cette connexion ont été vérifiés par le noyau du client ou une autre autorité locale. C'est un système facile à usurper, mais sur un réseau physique de confiance entre des hôtes de confiance, il est tout à fait adéquat.

Environ, un socket est utilisé pour chaque point de montage NFS. Si un client pouvait également utiliser des ports source non privilégiés, le nombre de sockets autorisés, et donc le nombre maximum de points de montage simultanés, serait beaucoup plus important.

L'utilisation de ports source non privilégiés peut compromettre quelque peu la sécurité du serveur, car tout utilisateur sur des points de montage AUTH_SYS peut désormais prétendre être un autre lors de l'envoi de requêtes NFS. Ainsi, les serveurs NFS ne prennent pas cela en charge par défaut. Ils l'autorisent explicitement généralement via une option d'exportation.

Pour conserver une bonne sécurité tout en autorisant autant de points de montage que possible, il est préférable d'autoriser les connexions client non privilégiées uniquement si le serveur et le client exigent tous deux une authentification forte, telle que Kerberos.

Montage à travers un pare-feu

Un pare-feu peut se trouver entre un client NFS et un serveur, ou le client ou le serveur peut bloquer certains de ses propres ports via des règles de filtrage IP. Il est toujours possible de monter un serveur NFS à travers un pare-feu, bien que certains des mécanismes de découverte de points de terminaison de service automatiques de la commande mount(8) puissent ne pas fonctionner ; cela nécessite de fournir des détails de point de terminaison spécifiques via des options de montage NFS.

Les serveurs NFS exécutent normalement un démon portmapper ou rpcbind pour annoncer leurs points de terminaison de service aux clients. Les clients utilisent le démon rpcbind pour déterminer :

Quel port réseau utilise chaque service basé sur RPC
Quels protocoles de transport chaque service basé sur RPC prend en charge

Le démon rpcbind utilise un numéro de port bien connu (111) pour aider les clients à trouver un point de terminaison de service. Bien que NFS utilise souvent un numéro de port standard (2049), des services auxiliaires tels que le service NLM peuvent choisir n'importe quel numéro de port inutilisé de manière aléatoire.

Les configurations de pare-feu courantes bloquent le port rpcbind bien connu. En l'absence de service rpcbind, l'administrateur du serveur corrige le numéro de port des services liés à NFS afin que le pare-feu puisse autoriser l'accès aux ports de service NFS spécifiques. Les administrateurs clients spécifient ensuite le numéro de port du service mountd via l'option mountport de la commande mount(8). Il peut également être nécessaire d'en

forcez l'utilisation de TCP ou UDP si le pare-feu bloque l'un de ces transports.

Listes de contrôle d'accès NFS

Solaris permet aux clients NFS version 3 d'accéder directement aux listes de contrôle d'accès POSIX stockées dans ses systèmes de fichiers locaux. Ce protocole secondaire propriétaire, connu sous le nom de NFSACL, offre un contrôle d'accès plus riche que les bits de mode. Linux implémente ce protocole pour assurer la compatibilité avec l'implémentation NFS de Solaris. Le protocole NFSACL n'est cependant jamais devenu une partie standard de la spécification NFS version 3.

La spécification NFS version 4 impose une nouvelle version de listes de contrôle d'accès qui sont sémantiquement plus riches que les ACL POSIX. Les ACL NFS version 4 ne sont pas entièrement compatibles avec les ACL POSIX ; ainsi, une certaine traduction entre les deux est nécessaire dans un environnement qui mélange des ACL POSIX et NFS version 4.

L'OPTION REMOUNT

Les options de montage génériques telles que rw et sync peuvent être modifiées sur les points de montage NFS en utilisant l'option remount. Voir mount(8) pour plus d'informations sur les options de montage génériques.

À quelques exceptions près, les options spécifiques à NFS ne peuvent pas être modifiées lors d'un remount. Le transport sous-jacent ou la version NFS ne peuvent pas être modifiés par un remount, par exemple.

Effectuer un remount sur un système de fichiers NFS monté avec l'option noac peut avoir des conséquences imprévues. L'option noac est une combinaison de l'option générique sync et de l'option spécifique NFS actimeo=0.

Démonter après un remount

Pour les points de montage qui utilisent les versions NFS 2 ou 3, la sous-commande de démontage NFS dépend de la connaissance de l'ensemble initial d'options de montage utilisées pour effectuer l'opération MNT. Ces options sont stockées sur disque par la sous-commande de montage NFS et peuvent être effacées par un remount.

Pour garantir que les options de montage sauvegardées ne soient pas effacées lors d'un remount, spécifiez soit le répertoire de montage local, soit le nom d'hôte du serveur et le chemin d'exportation, mais pas les deux, lors d'un remount. Par exemple,

mount -o remount,ro /mnt

fusionne l'option de montage ro avec les options de montage déjà sauvegardées sur disque pour le serveur NFS monté sur /mnt.

NOTES

Avant la version 2.4.7, le client NFS de Linux ne prenait pas en charge NFS sur TCP.

Avant la version 2.4.20, le client NFS de Linux utilisait une heuristique pour déterminer la validité des données de fichier mises en cache plutôt que d'utiliser la méthode standard de cohérence du cache de fermeture à ouverture décrite ci-dessus.

À partir de la version 2.4.22, le client NFS de Linux utilise un estimateur RTT basé sur Van Jacobsen pour déterminer les valeurs de délai de retransmission lors de l'utilisation de NFS sur UDP.

Avant la version 2.6.0, le client NFS de Linux ne prenait pas en charge NFS version 4.

Avant la version 2.6.8, le client NFS de Linux utilisait uniquement des lectures et écritures synchrones lorsque les paramètres rsize et wsize étaient inférieurs à la taille de page du système.

La prise en charge des versions de protocole par le client Linux dépend de la compilation du noyau avec les options CONFIG_NFS_V2, CONFIG_NFS_V3, CONFIG_NFS_V4, CONFIG_NFS_V4_1 et CONFIG_NFS_V4_2.
