NOM

nfsdcld - Démon de suivi des clients NFSv4

SYNTAXE

nfsdcld [-d] [-F] [-p chemin] [-s répertoire de stockage stable]

DESCRIPTION

nfsdcld est le démon de suivi des clients NFSv4. Il n'est pas nécessaire d'exécuter ce démon sur les machines qui n'agissent pas en tant que serveurs NFSv4.

Lorsqu'une partition réseau est combinée avec un redémarrage du serveur, il existe des conditions limites qui peuvent amener le serveur à accorder des récupérations de verrous alors que d'autres clients ont pris des verrous conflictuels dans l'intervalle. Une explication plus détaillée de ce problème est décrite dans la RFC 3530, section 8.6.3.

Afin de prévenir ces problèmes, le serveur doit suivre une petite quantité d'informations par client sur un stockage stable. Ce démon fournit la partie utilisateur de cette fonctionnalité.

OPTIONS

-d, --debug
Active la journalisation au niveau de débogage.
-F, --foreground
Exécute le démon au premier plan et affiche toute la sortie sur stderr.
-p chemin, --pipefsdir=chemin
Emplacement du système de fichiers rpc_pipefs. La valeur par défaut est /var/lib/nfs/rpc_pipefs.
-s répertoire_stockage, --storagedir=répertoire_stockage
Répertoire où les informations de stockage stable doivent être conservées. La valeur par défaut est /var/lib/nfs/nfsdcld.

FICHIER DE CONFIGURATION

Les valeurs suivantes sont reconnues dans la section [nfsdcld] du fichier de configuration /etc/nfs.conf :

storagedir
Équivalent à -s/--storagedir.
debug
Définir "debug = 1" est équivalent à -d/--debug.

De plus, la valeur suivante est reconnue dans la section [general] :

pipefs-directory
Équivalent à -p/--pipefsdir.

NOTES

Le serveur NFSv4 du noyau Linux a historiquement suivi ces informations sur un stockage stable en manipulant directement des informations dans le système de fichiers, dans le répertoire vers lequel pointe /proc/fs/nfsd/nfsv4recoverydir.

Cela a changé avec l'introduction initiale de l'appel externe nfsdcld dans la version 3.4 du noyau, qui a ensuite été déprécié au profit du programme usermodehelper nfsdcltrack(8), dont le support a été ajouté dans la version 3.8 du noyau. Cependant, comme l'appel externe usermodehelper ne fonctionne pas dans les conteneurs, le support d'une nouvelle version de l'appel externe nfsdcld a été ajouté dans la version 5.2 du noyau.

Ce démon nécessite un noyau qui supporte l'appel externe nfsdcld. Sur les noyaux plus anciens, si le code de suivi de nom de client hérité était utilisé, alors le noyau ne créerait pas le tube que nfsdcld utilise pour communiquer avec le noyau. Sur les noyaux plus récents, nfsd tente d'initialiser le suivi des clients dans l'ordre suivant : D'abord, l'appel externe nfsdcld. Deuxièmement, l'appel externe usermodehelper nfsdcltrack. Enfin, le suivi de client hérité.

Ce démon doit être exécuté en tant que root, car le tube qu'il utilise pour communiquer avec le noyau n'est accessible que par root. Le démon abandonne cependant toutes les capacités de superutilisateur après son démarrage. Pour cette raison, le répertoire_stockage doit appartenir à root et être lisible et inscriptible par le propriétaire.

Le démon prend désormais en charge différentes versions d'appels externes pour permettre au noyau de passer des données supplémentaires à stocker dans la base de données sur disque. Le noyau interrogera la version d'appel externe prise en charge par nfsdcld lors de l'initialisation du suivi des clients. Un redémarrage de nfsd n'est pas nécessaire après la mise à niveau de nfsdcld, cependant nfsd n'utilisera pas une version d'appel externe ultérieure avant redémarrage. Un redémarrage de nfsd est nécessaire après la rétrogradation de nfsdcld, pour s'assurer que nfsd n'utilise pas une version d'appel externe que nfsdcld ne prend pas en charge. De plus, une rétrogradation de nfsdcld nécessite également une rétrogradation du schéma de la base de données sur disque. Cela peut être réalisé à l'aide de l'utilitaire nfsdclddb(8).
