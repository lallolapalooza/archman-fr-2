NOM

nss-systemd, libnss_systemd.so.2 - Résolution des noms d'utilisateur et de groupes UNIX pour la recherche d'utilisateurs/groupes via Varlink

SYNTAXE

libnss_systemd.so.2

DESCRIPTION

nss-systemd est un module plug-in pour la fonctionnalité du GNU Name Service Switch (NSS) de la bibliothèque GNU C (glibc), fournissant la résolution des noms d'utilisateur et de groupes UNIX pour les services implémentant l'API de recherche d'enregistrements utilisateurs/groupes via Varlink[1], tels que le gestionnaire système et de services systemd(1) (pour sa fonctionnalité DynamicUser=, voir systemd.exec(5) pour les détails), systemd-homed.service(8), ou systemd-machined.service(8).

Ce module garantit également que les utilisateurs et groupes root et nobody (c'est-à-dire les utilisateurs/groupes avec les UID/GID 0 et 65534) restent résolvables à tout moment, même s'ils ne sont pas listés dans /etc/passwd ou /etc/group, ou si ces fichiers sont manquants.

Ce module utilise de préférence systemd-userdbd.service(8) pour la résolution des utilisateurs et des groupes, mais fonctionne également sans que le service ne soit en cours d'exécution.

Pour activer le module NSS, ajoutez "systemd" aux lignes commençant par "passwd:", "group:", "shadow:" et "gshadow:" dans /etc/nsswitch.conf.

Il est recommandé de placer "systemd" après l'entrée "files" des lignes /etc/nsswitch.conf afin que les correspondances basées sur /etc/passwd, /etc/group, /etc/shadow et /etc/gshadow aient la priorité.

ENREGISTREMENTS STATIQUES EN DROP-IN JSON UTILISATEUR/GROUPE

En plus des enregistrements d'utilisateurs/groupes acquis via les interfaces IPC Varlink mentionnées ci-dessus et les comptes root et nobody synthétisés, ce module met également à disposition du système des comptes utilisateurs et groupes définis dans des fichiers drop-in statiques dans les répertoires /etc/userdb/, /run/userdb/, /run/host/userdb/ et /usr/lib/userdb/.

Il s'agit d'un mécanisme simple pour fournir des enregistrements statiques d'utilisateurs et de groupes via des fichiers drop-in JSON. Ces enregistrements d'utilisateurs doivent être définis dans le format décrit par la spécification des Enregistrements Utilisateurs JSON[2] et être placés dans l'un des répertoires susmentionnés sous un nom de fichier composé du nom d'utilisateur suffixé par .user, avec un mode d'accès lisible par tous. Une lien symbolique nommé d'après l'UID de l'enregistrement utilisateur formaté en décimal et suffixé par .user pointant vers le fichier d'enregistrement principal doit également être créé, afin de permettre les recherches par nom d'utilisateur et par UID. Des données d'enregistrement utilisateur privilégiées (par exemple, mots de passe UNIX hachés) peuvent également être fournies en option, dans une paire de fichiers compagnons séparés avec le suffixe .user-privileged. Les données doivent être stockées dans un fichier régulier nommé d'après le nom d'utilisateur, suffixé par .user-privileged, et un lien symbolique y pointant, nommé d'après l'UID numérique utilisé formaté en décimal avec le même suffixe. Ces fichiers compagnons ne doivent pas être lisibles par quiconque sauf root. Exemple :

-rw-r--r--. 1 root root  723 Mai 10 foobar.user
-rw-------. 1 root root  123 Mai 10 foobar.user-privileged
lrwxrwxrwx. 1 root root   19 Mai 10 4711.user -> foobar.user
lrwxrwxrwx. 1 root root   19 Mai 10 4711.user-privileged -> foobar.user-privileged

De même, des enregistrements de groupes suivant le format décrit dans Enregistrement de Groupe JSON[3] peuvent être définis, en utilisant les suffixes de fichiers .group et .group-privileged.

Les fichiers d'enregistrement utilisateur/groupe principaux (c'est-à-dire ceux avec les suffixes .user et .group) ne doivent pas contenir la section "privileged" telle que décrite dans les spécifications. Les fichiers d'enregistrement utilisateur/groupe privilégiés (c'est-à-dire ceux avec les suffixes .user-privileged et .group-privileged) doivent contenir cette section, exclusivement.

En plus des deux types de fichiers d'enregistrement utilisateur et des deux types de fichiers d'enregistrement de groupe, il existe un cinquième type de fichier qui peut être placé dans les répertoires recherchés : des fichiers qui indiquent l'appartenance d'utilisateurs à des groupes. Spécifiquement, pour chaque paire utilisateur/groupe où l'utilisateur doit être membre d'un groupe, un fichier nommé "nomutilisateur:nomgroupe.membership" doit être créé, c'est-à-dire le nom d'utilisateur UNIX textuel, suivi d'un deux-points, suivi du nom de groupe UNIX textuel, suffixé par ".membership". Le contenu de ces fichiers n'est actuellement pas lu, et les fichiers doivent être créés vides. La simple existence de ces fichiers suffit à affecter une appartenance utilisateur/groupe. Si un programme fournit des fichiers d'enregistrement utilisateur et/ou groupe dans les répertoires recherchés, il doit toujours également créer de tels fichiers, tant pour les appartenances aux groupes principaux qu'aux groupes auxiliaires.

Notez que les enregistrements utilisateurs/groupes statiques ne remplacent généralement pas les enregistrements conflictuels dans /etc/passwd ou /etc/group ou d'autres bases de données de comptes. En fait, avant d'importer ces fichiers, il convient de prendre des précautions raisonnables pour éviter les conflits de noms d'utilisateur/groupe et d'UID/GID.

Le service systemd-userdb-load-credentials.service s'exécute automatiquement au démarrage et installe ces fichiers à partir des enregistrements utilisateurs passés via les identifiants système. Voir userdbctl(1) et systemd.system-credentials(7) pour les détails.

CONFIGURATION DANS /ETC/NSSWITCH.CONF

Voici un exemple de fichier /etc/nsswitch.conf qui active correctement nss-systemd :

passwd:         files systemd
group:          files [SUCCESS=merge] systemd
shadow:         files systemd
gshadow:        files systemd
hosts:          mymachines resolve [!UNAVAIL=return] files myhostname dns
networks:       files
protocols:      db files
services:       db files
ethers:         db files
rpc:            db files
netgroup:       nis

NAME

nss-systemd — Name Service Switch interface for systemd

SYNOPSIS

libnss-systemd.so

DESCRIPTION

The nss-systemd library provides Name Service Switch (NSS) modules which allow systemd services and applications to look up user and group information directly from systemd.

It implements the NSS interfaces for users (getpwnam(3), getpwuid(3), getpwent(3), setpwent(3), endpwent(3)) and groups (getgrnam(3), getgrgid(3), getgrent(3), setgrent(3), endgrent(3)).

This is primarily useful for services that need to manage users and groups dynamically or in a distributed manner, and want to integrate with systemd's user and group management features.

When enabled in /etc/nsswitch.conf, systemd's NSS modules will provide user and group information based on the following sources:

  1. Static JSON user/group records, as described in STATIC DROP-IN JSON USER/GROUP RECORDS.

  2. Dynamic user/group information provided by systemd services, such as systemd-machined.service.

The NSS modules will consult these sources in order. If a user or group is found in one source, it is returned, and subsequent sources are not consulted for that specific query.

STATIC DROP-IN JSON USER/GROUP RECORDS

systemd allows administrators to define static user and group records using JSON files. These files should be placed in /etc/userdb/ and /etc/groupdb/, respectively. The files should follow the JSON schema defined by the user/group record APIs.

1.
User Group API
https://systemd.io/USER_GROUP_API
2.
JSON User Records
https://systemd.io/USER_RECORD
3.
JSON Group Record
https://systemd.io/GROUP_RECORD

CONFIGURATION IN /ETC/NSSWITCH.CONF

To enable the nss-systemd modules, you need to add systemd to the corresponding lines in /etc/nsswitch.conf. For example:

passwd: files systemd
group: files systemd
shadow: files systemd
gshadow: files systemd

The order matters: files will be consulted first, then systemd. If a user or group is found in files, it will be returned without consulting systemd.

EXAMPLE: MAPPINGS PROVIDED BY SYSTEMD-MACHINED.SERVICE

systemd-machined.service can provide user and group mappings for containers and other systemd units. When nss-systemd is enabled, applications will be able to look up these users and groups as if they were local system users/groups.

For example, if systemd-machined.service is managing a container with a user named appuser, and the NSS module is enabled, a command like id appuser would resolve this user through the nss-systemd module.

SEE ALSO

nsswitch.conf(5), systemd-machined(8), systemd. OSError

NOTES

The nss-systemd module is experimental and may change in future versions. It is not intended to replace traditional user and group management methods for local users and groups, but rather to complement them by integrating with systemd's dynamic management capabilities.
