NOM

nsd-control, nsd-control-setup - Utilitaire de contrôle du serveur NSD à distance.

SYNTAXE

nsd-control [-c fichier_cfg] [-s serveur] commande

DESCRIPTION

nsd-control effectue l'administration à distance du serveur DNS nsd(8). Il lit le fichier de configuration, contacte le serveur nsd via SSL, envoie la commande et affiche le résultat. Les commandes qui nécessitent un rechargement sont mises en file d'attente et le résultat indique que la commande a été acceptée.

Les options disponibles sont :

-h
Affiche la version et l'aide des options de la ligne de commande.
-c fichier_cfg
Le fichier de configuration à lire avec les paramètres. Si non spécifié, le fichier de configuration par défaut //etc/nsd/nsd.conf est utilisé.
-s serveur[@port]
Adresse IPv4 ou IPv6 du serveur à contacter. Si non spécifiée, l'adresse est lue dans le fichier de configuration.

COMMANDES

Il existe plusieurs commandes que le serveur comprend.

start
Démarre le serveur. Exécute simplement nsd(8). L'exécutable nsd n'est pas recherché dans le PATH défini dans l'environnement. Au lieu de cela, il est lancé depuis son emplacement par défaut relatif au préfixe d'installation spécifié lors de la compilation. L'emplacement de l'exécutable peut être remplacé en définissant NSD_PATH dans l'environnement. Il est lancé avec le fichier de configuration spécifié via -c ou le fichier de configuration par défaut.
stop
Arrête le serveur. Le démon du serveur se termine.
reload [<zone>]
Recharge les fichiers de zone et rouvre le fichier journal. Sans argument, recharge les fichiers de zone modifiés. Avec un argument, recharge le fichier de zone pour la zone donnée et la charge.
reconfig
Recharge nsd.conf et applique les changements aux clés TSIG et aux modèles de configuration, et applique les changements pour ajouter et supprimer les zones mentionnées dans la configuration. D'autres changements ne sont pas appliqués, tels que l'adresse IP et le port d'écoute et le chroot. Les statistiques par zone ne sont pas non plus appliquées. Les mises à jour de modèles signifient que les options de configuration pour les zones (request-xfr, zonefile, notify, ...) sont mises à jour. De nouveaux modèles sont également disponibles pour une utilisation avec la commande addzone.
repattern
Identique à l'option reconfig.
log_reopen
Rouvre le fichier journal, pour la rotation des journaux qui souhaite déplacer le fichier journal et en créer un nouveau. Le journal peut également être rouvert avec kill -HUP (ce qui recharge également tous les fichiers de zone).
status
Affiche l'état du serveur. Code de sortie 3 si le serveur n'est pas en cours d'exécution (la connexion au port est refusée), 1 en cas d'erreur, 0 s'il est en cours d'exécution.
stats
Produit une séquence de lignes nom=valeur avec des informations statistiques, nécessite que NSD soit compilé avec cette option activée.
stats_noreset
Identique à stats, mais ne réinitialise pas les compteurs à zéro.
addzone <nom_zone> <nom_modèle>
Ajoute une nouvelle zone au serveur en cours d'exécution. La zone est ajoutée au fichier zonelist sur le disque, afin qu'elle subsiste après un redémarrage. Le nom du modèle détermine les options pour la nouvelle zone. Pour les zones secondaires, un transfert de zone est immédiatement tenté. Pour les zones avec un fichier de zone, une tentative de lecture du fichier de zone est effectuée.
delzone <nom_zone>
Supprime la zone du serveur en cours d'exécution. La zone est supprimée du fichier zonelist sur le disque, du fichier nsd.db et de la mémoire. Si elle avait un fichier de zone, celui-ci reste (mais peut être obsolète). Les zones configurées directement dans nsd.conf ne peuvent pas être supprimées de cette manière car le démon n'écrit pas dans le fichier nsd.conf. Vous devez ajouter ces zones au fichier zonelist pour pouvoir les supprimer avec la commande delzone.
changezone <nom_zone> <nom_modèle>
Change une zone pour utiliser le modèle d'options. La zone est supprimée et ajoutée en une seule opération, la faisant utiliser le nouveau modèle pour les options de zone. Les zones configurées dans nsd.conf ne peuvent pas être modifiées ainsi, modifiez plutôt nsd.conf (ou le fichier inclus dans nsd.conf) et utilisez reconfig.
addzones
Ajoute des zones lues depuis l'entrée standard de nsd-control. L'entrée est lue ligne par ligne, avec nom espace nom_modèle sur une ligne. Pour des ajouts en masse.
delzones
Supprime des zones lues depuis l'entrée standard de nsd-control. L'entrée est un nom par ligne. Pour des suppressions en masse.
write [<zone>]
Écrit les fichiers de zone sur le disque, ou le fichier de zone donné sur le disque. Les zones qui ont été modifiées (via AXFR ou IXFR) sont écrites, ou si le fichier de zone n'a pas encore été créé, il est alors créé. Les composants de répertoire du chemin du fichier de zone sont créés si nécessaire. Avec un argument, cette zone est écrite si elle a été modifiée ; sans argument, toutes les zones modifiées sont écrites.
notify [<zone>]
Envoie des messages NOTIFY aux serveurs secondaires. Envoie aux adresses IP configurées dans les listes 'notify:' pour les zones primaires hébergées sur ce serveur. Habituellement, NSD envoie des messages NOTIFY immédiatement lorsqu'un numéro de série de zone primaire est mis à jour. Si une zone est donnée, les notifications sont envoyées pour cette zone. Ces serveurs secondaires sont censés initier une requête de transfert de zone plus tard (vers ce serveur ou un autre primaire), cela peut être autorisé via la liste de contrôle d'accès 'provide-xfr:'. Avec un argument, cette zone est traitée ; sans argument, toutes les zones sont traitées.
transfer [<zone>]
Tente de mettre à jour les zones secondaires hébergées sur ce serveur en contactant les primaires. Les primaires sont configurés via les listes 'request-xfr:'. Si une zone est donnée, cette zone est mise à jour. Habituellement, NSD reçoit une notification des primaires (configurés via la liste de contrôle d'accès 'allow-notify:') qu'un nouveau numéro de série de zone doit être transféré. Pour les zones sans contenu, NSD peut avoir ralenti ses demandes car les primaires ne répondaient pas, mais cette commande réinitialisera ce ralentissement au délai initial, pour des tentatives fréquentes. Avec un argument, cette zone est transférée ; sans argument, toutes les zones sont transférées.
force_transfer [<zone>]
Force la mise à jour des zones secondaires hébergées sur ce serveur. Même si le primaire héberge le même numéro de série de la zone, un AXFR complet est effectué pour la récupérer. Si vous souhaitez utiliser IXFR et vérifier que le numéro de série augmente, utilisez la commande 'transfer'. Avec un argument, cette zone est transférée ; sans argument, toutes les zones sont transférées.
zonestatus [<zone>]
Affiche l'état de la zone, les numéros de série et depuis quand ils ont été acquis. Affiche également l'action de notification (vers quel serveur) et le transfert de zone (et depuis quel primaire) s'il y a une activité en cours. L'état de la zone est affiché comme : 'primary' (zones primaires), 'ok' (zone secondaire à jour), 'expired' (zone secondaire expirée), 'refreshing' (zone secondaire en cours de transfert). Les numéros de série affichés sont le 'served-serial' (actuellement actif), le 'commit-serial' (en cours de rechargement), le 'notified-serial' (notification reçue, en cours de téléchargement des données). Les numéros de série ne sont affichés que si un tel numéro de série est disponible. Avec un argument, l'état de cette zone est affiché ; sans argument, l'état de toutes les zones est affiché.
serverpid
Affiche le PID du processus serveur. Ceci est utilisé pour les statistiques (et ne fonctionne que lorsque NSD est compilé avec l'option de statistiques activée). Ce pid n'est pas destiné à l'envoi de signaux unix, utilisez le pid de nsd.pid pour cela, ce pid est également stable.
verbosity <nombre>
Change la verbosité de la journalisation.
print_tsig [<nom_clé>]
imprime le secret et l'algorithme pour la clé TSIG de ce nom. Ou liste toutes les clés tsig avec leur nom, secret et algorithme.
update_tsig <nom> <secret>
Modifie la clé TSIG existante nommée avec le nouveau secret. Le secret est une chaîne encodée en base64. Les modifications ne sont qu'en mémoire et disparaissent au prochain redémarrage, pour des changements durables, éditez le fichier nsd.conf ou un fichier qui y est inclus.
add_tsig <nom> <secret> [algo]
Ajoute une nouvelle clé TSIG avec le nom, le secret et l'algorithme donnés. Sans algorithme, un algorithme par défaut (hmac-sha256) est utilisé. Le secret est une chaîne encodée en base64. Les modifications ne sont qu'en mémoire et disparaissent au prochain redémarrage, pour des changements durables, éditez le fichier nsd.conf ou un fichier qui y est inclus.
assoc_tsig <zone> <nom_clé>
Associe la zone avec la tsig donnée. Les listes de contrôle d'accès pour notify, allow-notify, provide-xfr et request-xfr sont ajustées pour utiliser la clé donnée.
del_tsig <nom_clé>
Supprime la clé TSIG nommée. Affiche une erreur si la clé est toujours utilisée par une zone. Les modifications ne sont qu'en mémoire et disparaissent au prochain redémarrage, pour des changements durables, éditez le fichier nsd.conf ou un fichier qui y est inclus.
add_cookie_secret <secret>
Ajoute ou remplace un secret de cookie de manière persistante. <secret> doit être une chaîne hexadécimale de 128 bits.

Les secrets de cookie peuvent être soit actifs, soit en staging. Les secrets de cookie actifs sont utilisés pour créer des Cookies DNS, mais la vérification d'un Cookie DNS réussit avec n'importe lequel des secrets de cookie actifs ou en staging. L'état des secrets de cookie actuels peut être affiché avec la commande print_cookie_secrets.

Lorsqu'aucun secret de cookie n'est encore configuré, le <secret> est ajouté en tant qu'actif. S'il existe déjà un secret de cookie actif, le <secret> est ajouté en staging ou remplace un secret en staging existant.

Pour "faire pivoter" un secret de cookie utilisé dans un ensemble anycast. Le nouveau secret doit être ajouté en tant que secret de staging à tous les nœuds de l'ensemble anycast. Lorsque tous les nœuds peuvent vérifier les Cookies DNS avec le nouveau secret, le nouveau secret peut être activé avec la commande activate_cookie_secret. Après que tous les nœuds aient le nouveau secret actif pendant au moins une heure, le secret précédent peut être supprimé avec la commande drop_cookie_secret.

La persistance est réalisée en écrivant dans un fichier qui, s'il est configuré avec l'option cookie-secret-file dans la section serveur du fichier de configuration. La valeur par défaut est : //var/db/nsd/cookiesecrets.txt .

drop_cookie_secret
Supprime le secret de cookie en staging.
activate_cookie_secret
Rend le secret de cookie en staging actuel actif, et le secret de cookie actif actuel en staging.
print_cookie_secrets
Affiche les secrets de cookie actuellement configurés avec leur statut.

CODE DE SORTIE

Le programme nsd-control se termine avec le code de statut 1 en cas d'erreur, 0 en cas de succès.

MISE EN PLACE

La mise en place nécessite un certificat auto-signé et des clés privées pour le serveur et le client. Le script nsd-control-setup génère ceux-ci dans le répertoire d'exécution par défaut, ou avec -d dans un autre répertoire. Si vous modifiez les permissions de contrôle d'accès sur les fichiers clés, vous pouvez décider qui peut utiliser nsd-control, par défaut le propriétaire et le groupe, mais pas tous les utilisateurs. Le script conserve les clés privées présentes dans le répertoire. Après avoir exécuté le script en tant que root, activez control-enable dans nsd.conf.

COMPTEURS STATISTIQUES

La commande stats affiche un certain nombre de compteurs statistiques.

num.queries
nombre de requêtes reçues (les requêtes tls, tcp et udp additionnées).
serverX.queries
nombre de requêtes traitées par le processus serveur. Le nombre de processus serveurs est défini avec l'instruction de configuration server-count.
time.boot
temps de fonctionnement en secondes depuis le démarrage du serveur. Avec secondes fractionnaires.
time.elapsed
temps écoulé depuis le dernier rapport de statistiques, en secondes. Avec secondes fractionnaires. Peut être zéro si interrogé rapidement et si la commande de statistiques précédente réinitialise les compteurs, de sorte que la suivante obtienne un rapport complètement zéro, avec un temps écoulé nul.
size.db.disk
taille de nsd.db sur disque, en octets.
size.db.mem
taille de la base de données DNS en mémoire, en octets.
size.xfrd.mem
taille de la mémoire pour les transferts de zones et les notifications dans le processus xfrd, excluant les données TSIG, en octets.
size.config.disk
taille du fichier zonelist sur disque, excluant la taille de nsd.conf, en octets.
size.config.mem
taille des données de configuration en mémoire, conservée deux fois dans les processus serveur et xfrd, en octets.
num.type.X
nombre de requêtes avec ce type de requête.
num.opcode.X
nombre de requêtes avec cet opcode.
num.class.X
nombre de requêtes avec cette classe de requête.
num.rcode.X
nombre de réponses qui ont porté ce code de retour.
num.edns
nombre de requêtes avec EDNS OPT.
num.ednserr
nombre de requêtes dont l'analyse EDNS a échoué.
num.udp
nombre de requêtes sur UDP ip4.
num.udp6
nombre de requêtes sur UDP ip6.
num.tcp
nombre de connexions sur TCP ip4.
num.tcp6
nombre de connexions sur TCP ip6.
num.tls
nombre de connexions sur TLS ip4. Les requêtes TLS ne font pas partie de num.tcp.
num.tls6
nombre de connexions sur TLS ip6. Les requêtes TLS ne font pas partie de num.tcp6.
num.answer_wo_aa
nombre de réponses avec le code de retour NOERROR et sans le drapeau AA, cela inclut les renvois.
num.rxerr
nombre de requêtes pour lesquelles la réception a échoué.
num.txerr
nombre de réponses pour lesquelles la transmission a échoué.
num.raxfr
nombre de requêtes AXFR de clients (qui ont reçu une réponse).
num.rixfr
nombre de requêtes IXFR de clients (qui ont reçu une réponse).
num.truncated
nombre de réponses avec le drapeau TC défini.
num.dropped
nombre de requêtes qui ont été abandonnées car elles ont échoué à la vérification de cohérence.
zone.primary
nombre de zones primaires servies. Ce sont des zones sans entrées 'request-xfr:'. Également affiché sous 'zone.master' pour la compatibilité ascendante.
zone.secondary
nombre de zones secondaires servies. Ce sont des zones avec des entrées 'request-xfr'. Également affiché sous 'zone.slave' pour la compatibilité ascendante.

nsd-control — nsd(8) control utility

NAME

nsd-control — nsd(8) control utility

SYNOPSIS

nsd-control [-a address] [-c cfgfile] [-d] [-h] [-v] command [arguments]

DESCRIPTION

nsd-control is a utility to send commands to the nsd(8) name server. It is used to query the server's status, reload zones, and other administrative tasks.

The control is done via a control socket, by default /run/nsd/nsd.sock. The socket location can be changed with the -c option or the server/control-socket: directive in the configuration file.

COMMANDS

nstd-control reload [zone]
Reload zone data. If zone is specified, only that zone is reloaded. Otherwise, all zones are reloaded.
nstd-control rekey [zone]
Rekey zone data. If zone is specified, only that zone is rekeyed. Otherwise, all zones are rekeyed.
nstd-control stats
Print statistics counters.
nstd-control status
Print the server status.
nstd-control stop
Stop the server.
nstd-control restart
Restart the server. This is equivalent to sending a stop command followed by a start command.
nstd-control readhints
Read the root hints file.
nstd-control build zone
Build a zone from zone data.
nstd-control checkzone zone
Check zone data.
nstd-control monitor
Monitor the server's log output.

EXIT CODE

nsd-control exits with 0 on success, and a non-zero value on failure.

SET UP

To use nsd-control, the control socket must be enabled in the nsd configuration file (/etc/nsd/nsd.conf by default). Add the following lines to the configuration:

control:
    control-enable: yes

The control socket location is /run/nsd/nsd.sock by default. You can change this with the control-socket: directive:

control:
    control-enable: yes
    control-socket: "/var/run/nsd.sock"

Make sure that the user running nsd-control has write permissions to the control socket. Usually, this means adding the user to the nsd group.

STATISTIC COUNTERS

nsd-control stats displays a list of statistic counters that can be used to monitor the performance of the nsd server. The counters include:

  • num.queries: Total number of queries received.
  • num.answer: Total number of queries answered.
  • num.nxdomain: Total number of NXDOMAIN responses.
  • num.referral: Total number of referral responses.
  • num.SERVFAIL: Total number of SERVFAIL responses.
  • num.other: Total number of other responses.
  • num.udp: Total number of UDP queries.
  • num.tcp: Total number of TCP queries.
  • num.len.short: Total number of short queries.
  • num.len.long: Total number of long queries.
  • num.len.other: Total number of other length queries.
  • num.dropped: Total number of dropped queries.
  • num.invalid: Total number of invalid queries.
  • num.filter: Total number of filtered queries.
  • num.ratelimit: Total number of rate-limited queries.
  • num.dns64: Total number of DNS64 queries.
  • num.zero.ttl: Total number of zero TTL responses.
  • num.zero.answer: Total number of zero answer responses.
  • num.tcp.port.open: Total number of open TCP ports.
  • num.tcp.port.closed: Total number of closed TCP ports.
  • num.tcp.err: Total number of TCP errors.
  • num.zone.reloaded: Total number of zones reloaded.
  • num.zone.rekeyed: Total number of zones rekeyed.
  • num.zone.build: Total number of zones built.
  • num.zone.check: Total number of zones checked.

FILES

/etc/nsd/nsd.conf
nsd configuration file.
/run/nsd/nsd.sock
nsd control socket.
