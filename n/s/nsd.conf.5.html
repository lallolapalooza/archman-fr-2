NOM

nsd.conf - fichier de configuration de NSD

SYNTAXE

nsd.conf

DESCRIPTION

Ce fichier est utilisé pour configurer nsd(8). Il spécifie les options pour le serveur nsd, les fichiers de zone, les serveurs primaires et secondaires.

Le format du fichier contient des attributs et des valeurs. Certains attributs contiennent d'autres attributs. La notation est la suivante :

attribut: valeur

Les commentaires commencent par # et vont jusqu'à la fin de la ligne. Les lignes vides sont ignorées, tout comme les espaces blancs au début d'une ligne. Les guillemets doivent être utilisés pour les valeurs contenant des espaces, par exemple, "nom de fichier.zone".

EXEMPLE

Un exemple de fichier nsd.conf court est présenté ci-dessous.

# Exemple de fichier nsd.conf pour example.com.
# Ceci est un commentaire.

server:
	server-count: 1 # utiliser ce nombre de cœurs de processeur
	username: 
	zonelistfile: //var/db/nsd/zone.list
	logfile: //var/log/nsd.log
	pidfile: /run/nsd/nsd.pid
	xfrdfile: //var/db/nsd/xfrd.state

zone:
	name: example.com
	zonefile: //etc/nsd/example.com.zone

zone:
	# ce serveur est le primaire et 192.0.2.1 est le secondaire.
	name: primaryzone.com
	zonefile: //etc/nsd/primaryzone.com.zone
	notify: 192.0.2.1 NOKEY
	provide-xfr: 192.0.2.1 NOKEY

zone:
	# ce serveur est le secondaire et 192.0.2.2 est le primaire.
	zonefile: //etc/nsd/secondaryzone.com.zone
	name: secondaryzone.com
	allow-notify: 192.0.2.2 NOKEY
	request-xfr: 192.0.2.2 NOKEY

Ensuite, utilisez kill -HUP pour recharger les modifications à partir des fichiers de zone primaires. Et utilisez kill -TERM pour arrêter le serveur.

FORMAT DU FICHIER

Il doit y avoir des espaces blancs entre les mots-clés. Les mots-clés d'attribut se terminent par deux points ':'. Un attribut est suivi par ses attributs contenants, ou par une valeur.

Au niveau supérieur, seuls server:, verify:, key:, pattern:, zone:, tls-auth: et remote-control: sont autorisés. Ceux-ci sont suivis de leurs attributs ou d'un nouveau mot-clé de niveau supérieur. L'attribut zone: est suivi des options de zone. L'attribut server: est suivi des options globales pour le serveur NSD. L'attribut verify: est utilisé pour contrôler la vérification des zones. Un attribut key: est utilisé pour définir les clés d'authentification. L'attribut pattern: est suivi des options de zone pour les zones qui utilisent le motif. Un attribut tls-auth: est utilisé pour définir les attributs d'authentification pour les connexions TLS utilisées pour XFR-over-TLS.

Les fichiers peuvent être inclus en utilisant la directive include:. Elle peut apparaître n'importe où et prend un seul nom de fichier comme argument. Le traitement se poursuit comme si le texte du fichier inclus était copié dans le fichier de configuration à cet endroit. Si un chroot est utilisé, un nom de fichier absolu est nécessaire (avec le chroot préfixé), de sorte que l'inclusion puisse être analysée avant et après l'application du chroot (et la connaissance de ce qu'est ce chroot). Vous pouvez utiliser '*' pour inclure une correspondance de fichiers par joker, par exemple, "foo/nsd.d/*.conf". Aussi '?', '{}', '[]', et '~' fonctionnent, voir glob(7). Si aucun fichier ne correspond au modèle, ce n'est pas une erreur.

Options du serveur

Les options globales (si elles ne sont pas remplacées depuis la ligne de commande NSD) sont prises dans la clause server:. Il ne peut y avoir qu'une seule clause server:.

ip-address: <ip4 ou ip6>[@port] [serveurs] [bindtodevice] [setfib]
NSD se liera à l'adresse IP listée. Peut être donnée plusieurs fois pour lier plusieurs adresses IP. Optionnellement, un numéro de port peut être fourni. Si aucun n'est donné, NSD écoute sur l'interface wildcard. Identique à l'option en ligne de commande -a.

Pour limiter quels serveurs NSD écoutent sur l'interface donnée, spécifiez un ou plusieurs serveurs séparés par des espaces après <ip>[@port]. Les plages peuvent être utilisées comme raccourci pour spécifier plusieurs serveurs consécutifs. Par défaut, tous les serveurs écouteront.

Si un nom d'interface est utilisé à la place de ip4 ou ip6, la liste des adresses IP associées à cette interface sera récupérée et utilisée au démarrage du serveur.

Pour les serveurs ayant plusieurs adresses IP qui peuvent être utilisées pour envoyer du trafic vers Internet, listez-les une par une, ou l'adresse source des réponses pourrait être incorrecte. Ceci est dû au fait que si le socket udp associe une adresse source de 0.0.0.0, le noyau choisit une adresse IP avec laquelle envoyer vers Internet, et il choisit la mauvaise. Généralement nécessaire pour les instances anycast. Utilisez ip-transparent pour pouvoir lister des adresses qui s'activent plus tard (typique pour certains équilibrages de charge).

interface: <ip4 ou ip6>[@port] [serveurs] [bindtodevice] [setfib]
Identique à ip-address (pour la compatibilité avec unbound.conf).
ip-transparent: <oui ou non>
Permet à NSD de se lier à des adresses non locales. Ceci est utile pour que NSD écoute les adresses IP qui ne sont pas (encore) ajoutées à l'interface réseau, afin qu'il puisse répondre immédiatement lorsque l'adresse est ajoutée. Par défaut, non.
ip-freebind: <oui ou non>
Définit l'option IP_FREEBIND pour se lier à des adresses non locales et des interfaces qui sont inactives. Similaire à ip-transparent. Par défaut, non.
reuseport: <oui ou non>
Utilise l'option de socket SO_REUSEPORT et crée des descripteurs de fichiers pour chaque serveur dans server-count. Cela améliore les performances de la pile réseau. Utile uniquement si vous configurez également un server-count supérieur à 1 (par exemple, égal au nombre de CPU). Par défaut, non. Cela fonctionne sous Linux, mais pas sous FreeBSD, et probablement pas sous d'autres systèmes.
send-buffer-size: <nombre>
Définit la taille du tampon d'envoi pour les sockets de service de requêtes. Réglez sur 0 pour utiliser les paramètres par défaut.
receive-buffer-size: <nombre>
Définit la taille du tampon de réception pour les sockets de service de requêtes. Réglez sur 0 pour utiliser les paramètres par défaut.
debug-mode: <oui ou non>
Active le mode de débogage pour nsd, ne crée pas de processus démon. Par défaut, non. Identique à l'option en ligne de commande -d. Si réglé sur oui, il ne crée pas de processus et reste au premier plan, ce qui peut être utile pour le débogage en ligne de commande, mais est également utilisé par certains processus de supervision de serveur pour s'assurer que le serveur est en cours d'exécution.
do-ip4: <oui ou non>
Si oui, NSD écoute les connexions IPv4. Par défaut, oui.
do-ip6: <oui ou non>
Si oui, NSD écoute les connexions IPv6. Par défaut, oui.
database: <nom-de-fichier>
Cette option est ignorée par les versions 4.8.0 et plus récentes de NSD, car la fonctionnalité de base de données a été supprimée.
zonelistfile: <nom-de-fichier>
Par défaut, //var/db/nsd/zone.list est utilisé. Le fichier spécifié est utilisé pour stocker la liste des zones ajoutées dynamiquement. La liste est écrite par NSD pour ajouter et supprimer des zones. C'est un fichier texte avec un nom de zone et un nom de modèle sur chaque ligne. Ce fichier est utilisé pour les commandes nsd-control addzone et delzone.
identity: <chaine>
Retourne l'identité spécifiée lorsqu'on interroge CH TXT ID.SERVER. Par défaut, le nom renvoyé par gethostname(3). Identique à l'option en ligne de commande -i. Voir hide-identity pour configurer le serveur pour qu'il ne réponde pas à de telles requêtes.
version: <chaine>
Retourne la chaîne de version spécifiée lorsqu'on interroge version.server et version.bind. Par défaut, la version du paquet compilé. Voir hide-version pour configurer le serveur pour qu'il ne réponde pas à de telles requêtes.
nsid: <chaine>
Ajoute le nsid spécifié dans la section EDNS de la réponse lorsqu'on interroge avec un paquet activé NSID EDNS. Sous forme de séquence de caractères hexadécimaux ou avec le préfixe ascii_ suivi d'une chaîne ascii. Identique à l'option en ligne de commande -I.
logfile:

Ce site n'est en aucun cas associé à Arch Linux ni affilié à ce projet. Le contenu est uniquement une traduction des pages de manuel d'Arch publiées sur man.archlinux.org.

<nom de fichier>
Journaux de messages dans le fichier journal. Par défaut, enregistrement dans stderr et syslog (avec la facilité LOG_DAEMON). Identique à l'option de ligne de commande -l.
log-only-syslog: <oui ou non>
Enregistre les messages uniquement dans syslog. Utile avec systemd afin que l'impression vers stderr ne cause pas de doublons de chaînes de journal dans journald. Avant que syslog ne soit ouvert, le serveur utilise stderr. Stderr est également utilisé si syslog n'est pas disponible. Par défaut, non.
server-count: <nombre>
Démarre ce nombre de serveurs NSD. Par défaut, 1. Identique à l'option de ligne de commande -N.
cpu-affinity: <nombre> <nombre> ...
Affinité globale du processeur pour les serveurs NSD. Par défaut, aucune affinité.
server-N-cpu-affinity: <nombre>
Lie le serveur NSD spécifié par N à un cœur spécifique. Par défaut, l'affinité est définie sur tous les cœurs spécifiés dans cpu-affinity. Ce réglage n'est effectif que si cpu-affinity est activé.
xfrd-cpu-affinity: <nombre>
Lie xfrd à un cœur spécifique. Par défaut, l'affinité est définie sur tous les cœurs spécifiés dans cpu-affinity. Ce réglage n'est effectif que si cpu-affinity est activé.
tcp-count: <nombre>
Le nombre maximum de connexions TCP simultanées et actives par chaque serveur. Par défaut, 100. Identique à l'option de ligne de commande -n. C'est le nombre de requêtes des clients vers ce serveur.
tcp-reject-overflow: <oui ou non>
Si défini sur oui, les connexions TCP dépassant le maximum défini par tcp-count seront immédiatement rejetées (acceptées et fermées). Par défaut, non.
tcp-query-count: <nombre>
Le nombre maximum de requêtes servies sur une seule connexion TCP. Par défaut, 0, ce qui signifie qu'il n'y a pas de maximum.
tcp-timeout: <nombre>
Remplace le délai d'attente TCP par défaut. Cela affecte également les transferts de zone sur TCP. Par défaut, 120 secondes.
tcp-mss: <nombre>
Taille de segment maximale (MSS) du socket TCP sur lequel le serveur répond aux requêtes. Une valeur inférieure à la MSS courante sur Ethernet (1220 par exemple) résoudra le problème de MTU de chemin. Notez que toutes les plates-formes ne prennent pas en charge l'option de socket pour définir la MSS (TCP_MAXSEG). Par défaut, la MSS système par défaut est déterminée par la MTU de l'interface et la négociation entre le serveur et le client.
outgoing-tcp-mss: <nombre>
Taille de segment maximale (MSS) du socket TCP pour les requêtes XFR sortantes vers d'autres serveurs de noms. Une valeur inférieure à la MSS courante sur Ethernet (1220 par exemple) résoudra le problème de MTU de chemin. Notez que toutes les plates-formes ne prennent pas en charge l'option de socket pour définir la MSS (TCP_MAXSEG). Par défaut, la MSS système par défaut est déterminée par la MTU de l'interface et la négociation entre NSD et les autres serveurs.
xfrd-tcp-max: <nombre>
Nombre de sockets que xfrd utilise pour les transferts de zone sortants. Par défaut, 128. Augmentez-le pour permettre plus de sockets de transfert de zone, par exemple à 256. Ceci concerne les transferts de zone demandés par ce serveur à d'autres serveurs. Pour économiser de la mémoire, ceci peut être réduit, définissez-le plus bas avec d'autres réglages pour réduire l'empreinte mémoire de NSD. xfrd-tcp-max: 32 et xfrd-tcp-pipeline: 128 et rrl-size: 1000

Cela réduit l'empreinte mémoire, les autres utilisations de mémoire sont principalement causées par le réglage server-count, le nombre de processus serveur, et le réglage tcp-count, qui conserve des tampons par processus serveur, et par la taille des données de zone.

xfrd-tcp-pipeline: <nombre>
Nombre de transferts de zone sortants simultanés possibles sur les sockets TCP de xfrd. Le maximum est 65536, par défaut 128. Ceci concerne les transferts de zone demandés par ce serveur à d'autres serveurs.
ipv4-edns-size: <nombre>
Taille de tampon EDNS préférée pour IPv4. Par défaut, 1232.
ipv6-edns-size: <nombre>
Taille de tampon EDNS préférée pour IPv6. Par défaut, 1232.
pidfile: <nom de fichier>
Utilise le fichier pid au lieu de la valeur par défaut spécifique à la plate-forme, généralement "/run/nsd/nsd.pid". Identique à l'option de ligne de commande -P. Avec "", il n'y a pas de fichier pid, pour certains systèmes de gestion de démarrage où un fichier pid n'est pas utile. La valeur par défaut peut être définie lors de la compilation, parfois à "". Ensuite, l'option de configuration et l'option de ligne de commande peuvent être utilisées pour spécifier qu'un fichier pid est utilisé, différent de sa valeur par défaut lors de la compilation. Le fichier n'est pas chown au nom d'utilisateur de l'option username:, pour des raisons de sécurité des permissions. Il reste la propriété de l'utilisateur par lequel le serveur a été démarré. Le fichier peut ne pas être supprimé après la fin du serveur et son arrêt, car les permissions pour le nom d'utilisateur peuvent ne pas le permettre.
port: <nombre>
Répond aux requêtes sur le port spécifié. Par défaut, 53. Identique à l'option de ligne de commande -p.
statistics: <nombre>
Si absent, aucune statistique n'est exportée. Les statistiques sont produites toutes les nombre secondes. Identique à l'option de ligne de commande -s.
chroot: <répertoire>
NSD effectuera un chroot au démarrage dans le répertoire spécifié. Notez que si ailleurs dans la configuration vous spécifiez un chemin absolu vers un fichier à l'intérieur du chroot, vous devez préfixer le chemin du chroot. De cette façon, vous pouvez activer et désactiver l'option chroot sans avoir à modifier quoi que ce soit d'autre dans la configuration. Définissez la valeur sur "" (la chaîne vide) pour désactiver le chroot. Par défaut, "" est utilisé. Identique à l'option de ligne de commande -t.
username: <nom d'utilisateur>
Après avoir lié le socket, abandonne les privilèges utilisateur et prend le nom d'utilisateur. Peut être un nom d'utilisateur, un id ou id.gid. Identique à l'option de ligne de commande -u.
zonesdir: <répertoire>
Change le répertoire de travail vers le répertoire spécifié avant d'accéder aux fichiers de zone. De plus, NSD accédera à zonelistfile, logfile, pidfile, xfrdfile, xfrdir, server-key-file, server-cert-file, control-key-file et control-cert-file relativement à ce répertoire. Définissez la valeur sur "" (la chaîne vide) pour désactiver le changement de répertoire de travail. Par défaut, "//etc/nsd" est utilisé.
difffile: <nom de fichier>
Ignoré, pour la compatibilité avec les fichiers de configuration NSD3.
xfrdfile: <nom de fichier>
Le délai d'attente SOA et le démon de transfert de zone dans NSD sauvegarderont son état dans ce fichier. L'état est relu après un redémarrage. Le fichier d'état peut être supprimé sans trop de conséquences, mais les horodatages des zones seront perdus. S'il est configuré comme "", le fichier d'état n'est pas utilisé, toutes les zones secondaires sont vérifiées pour les mises à jour au démarrage. Pour plus de détails, voir la section sur le comportement d'expiration des zones de NSD. Par défaut, //var/db/nsd/xfrd.state.
xfrdir: <répertoire>
Les transferts de zone sont stockés ici avant d'être traités. Un répertoire est créé ici et est supprimé lorsque NSD se termine. Par défaut, /tmp.
xfrd-reload-timeout: <nombre>
Si cette valeur est -1, xfrd ne déclenchera pas de rechargement après un transfert de zone. Si positive, xfrd déclenchera un rechargement après un transfert de zone, puis attendra le nombre de secondes avant de déclencher un nouveau rechargement. Définir cette valeur limite les rechargements à une fois par le nombre de secondes. Par défaut, 1 seconde.
verbosity: <niveau>
Cette valeur spécifie le niveau de verbosité pour la journalisation (non-débogage). Par défaut, 0. 1 donne plus d'informations sur les notifications entrantes et les transferts de zone. 2 liste les avertissements doux rencontrés. 3 imprime plus d'informations. Identique à l'option de ligne de commande -V.

La verbosité 0 imprimera les avertissements et les erreurs, ainsi que d'autres événements qui sont importants pour le bon fonctionnement de NSD.

La verbosité 1 imprime en plus les messages d'intérêt. Notifications réussies, transferts de zone entrants réussis (la zone est mise à jour), transferts de zone entrants échoués ou impossibilité de traiter les mises à jour de zone.

La verbosité 2 imprime en plus les erreurs douces, comme les réinitialisations de connexion sur TCP. Et le refus de notification, et les refus de requêtes AXFR.

hide-version: <oui ou non>
Empêche NSD de répondre avec la chaîne de version lors des requêtes de classe CHAOS. Par défaut, non.
hide-identity: <oui ou non>
Empêche NSD de répondre avec la chaîne d'identité lors des requêtes de classe CHAOS. Par défaut, non.
drop-updates: <oui ou non>
Si défini sur oui, rejette les paquets reçus avec l'opcode UPDATE. Par défaut, non.
use-systemd: <oui ou non>
Cette option est obsolète et ignorée. Si compilé avec libsystemd, NSD signale sa disponibilité à systemd et l'utilisation de l'option n'est pas nécessaire.
log-time-ascii: <oui ou non>
Journalise l'heure en ASCII, si "non", alors en époque de secondes. Par défaut, oui. Ceci choisit le format lors de la journalisation dans un fichier. L'affichage via syslog a un horodatage formaté par syslog.
log-time-iso: <oui ou non>
Journalise l'heure au format ISO8601, si log-time-ascii: oui est également défini. Par défaut, non.
round-robin: <oui ou non>
Active la rotation en round-robin des enregistrements dans la réponse. Cela change l'ordre des enregistrements dans la réponse et peut équilibrer la charge entre eux. Par défaut, non.
minimal-responses: <oui ou non>
Active les réponses minimales pour les réponses plus petites. Cela rend les paquets plus petits. Des données supplémentaires ne sont ajoutées que pour les renvois, lorsque cela est vraiment nécessaire. Ceci est différent de l'option de configuration --enable-minimal-responses, qui réduit les paquets, mais exactement à la longueur de fragmentation, la option nsd.conf réduit les paquets autant que possible. La valeur par défaut est non.
confine-to-zone: <oui ou non>
Si défini sur oui, des informations supplémentaires ne seront pas ajoutées à la réponse si la zone apex des informations supplémentaires ne correspond pas à la zone apex de la requête initiale (par exemple, résolution CNAME). La valeur par défaut est non.
refuse-any: <oui ou non>
Refuse les requêtes de type ANY. Ceci est utile pour arrêter les inondations de requêtes essayant d'obtenir de grandes réponses. Notez que le limitation de débit rrl a également le type ANY comme type de limitation de débit. Il envoie une troncature en réponse aux requêtes UDP de type ANY, et il autorise les requêtes TCP de type ANY comme d'habitude. La valeur par défaut est non. Avec l'option désactivée, NSD se comporte conformément à la RFC 8482 4.1. Il minimise la réponse avec un seul jeu d'enregistrements. Les types populaires et pas trop grands, comme A, AAAA et MX, sont préférés, et les types volumineux, comme DNSKEY et RRSIG, sont sélectionnés avec une préférence plus faible que les autres types. Cela rend la réponse plus petite.
reload-config: <oui ou non>
Recharge le fichier de configuration et met à jour les clés TSIG et les zones sur SIGHUP. La valeur par défaut est non.
zonefiles-check: <oui ou non>
Fait vérifier à NSD le mtime des fichiers de zone au démarrage et lors de SIGHUP. Si vous le désactivez, il démarre plus rapidement (moins d'activité disque en cas de nombreuses zones). La valeur par défaut est oui. La commande nsd-control reload recharge les fichiers de zone indépendamment de cette option.
zonefiles-write: <secondes>
Écrit les zones secondaires mises à jour dans leur fichier de zone toutes les N secondes. Si le fichier de zone ou l'option "zonefile" du modèle est défini sur "" (chaîne vide), aucun fichier de zone n'est écrit. La valeur par défaut est 3600 (1 heure).
rrl-size: <nombuckets>
Cette option donne la taille de la table de hachage. La valeur par défaut est 1000000. Plus de buckets utilisent plus de mémoire et réduisent le risque de collisions de hachage.
rrl-ratelimit: <qps>
Le qps maximum autorisé (depuis une source de requête). La valeur par défaut est activée (avec une suggestion de 200 qps). S'il est défini sur 0, il est désactivé (taux illimité), définissez également whitelist-ratelimit sur 0 pour désactiver le traitement de la limitation de débit. Si vous définissez la verbosité sur 2, les sous-réseaux bloqués et débloqués sont enregistrés. Les requêtes bloquées sont refusées et certaines reçoivent des réponses de repli TCP. Une fois le taux limite atteint, NSD commence à abandonner les réponses. Cependant, une réponse sur "rrl-slip" est autorisée, avec le bit TC défini. Si slip est défini sur 2, le taux de réponse retourné sera divisé par deux. S'il est défini sur 3, le taux de réponse retourné sera d'un tiers, et ainsi de suite. Si vous définissez rrl-slip sur 10, le trafic est réduit à 1/10. Les options de limitation de débit rrl-ratelimit, rrl-size et rrl-whitelist-ratelimit sont mises à jour lors du reconfig de nsd-control (les options de limitation de débit spécifiques à la zone sont également mises à jour).
rrl-slip: <numpackets>
Cette option contrôle le nombre de paquets rejetés avant que nous n'envoyions une réponse SLIP (une réponse avec le bit "tronqué" défini sur un). 0 désactive l'envoi de paquets SLIP, 1 signifie que chaque requête recevra une réponse SLIP. La valeur par défaut est 2, réduit le trafic de moitié et permet aux utilisateurs légitimes d'avoir une chance raisonnable d'obtenir une réponse +TC.
rrl-ipv4-prefix-length: <subnet>
Longueur du préfixe IPv4. Les adresses sont regroupées par bloc réseau. La valeur par défaut est 24.
rrl-ipv6-prefix-length: <subnet>
Longueur du préfixe IPv6. Les adresses sont regroupées par bloc réseau. La valeur par défaut est 64.
rrl-whitelist-ratelimit: <qps>
Le qps maximum pour les tris de requêtes pour une source qui ont été mises sur liste blanche. La valeur par défaut est activée (avec une suggestion de 2000 qps). Avec l'option rrl-whitelist, vous pouvez définir des requêtes spécifiques pour recevoir cette limite de qps au lieu de la limite normale. Avec la valeur 0, le taux est illimité.
answer-cookie: <oui ou non>
Active la réponse aux requêtes contenant des DNS Cookies comme spécifié dans la RFC7873. La valeur par défaut est non.

Les DNS Cookies augmentent la sécurité des transactions et offrent une protection limitée contre les attaques par déni de service par amplification. Des cookies serveur seront créés et inclus dans les réponses. Les cookies serveur sont créés en fonction du cookie client dans la requête, de l'heure actuelle, de l'adresse IP du client et d'un secret. Lorsqu'un client inclut un cookie serveur valide dans les requêtes successives, le client ne sera pas soumis à la limitation de débit des requêtes (voir rrl-ratelimit).

Les serveurs dans un déploiement anycast doivent pouvoir vérifier les cookies serveur les uns des autres. Pour cela, ils doivent partager le secret utilisé pour construire et vérifier les cookies. Ces secrets de cookies peuvent être spécifiés dans les fichiers de configuration avec les options cookie-secret et cookie-staging-secret.

Si aucun secret de cookie n'est fourni via le fichier de configuration, des secrets de cookie serveur peuvent être ajoutés, supprimés et activés avec l'outil nsd-control(8). Ces secrets seront stockés de manière persistante dans le fichier de secrets de cookies dont l'emplacement peut être spécifié avec l'option cookie-secret-file.

Si aucun secret de cookie n'est fourni via le fichier de configuration, et qu'il n'y a pas de fichier de secrets de cookies ou qu'il est vide, un secret de cookie aléatoire est généré.

cookie-secret: <chaîne hexadécimale de 128 bits>
Le secret de cookie avec lequel les cookies serveur sont créés et peuvent être vérifiés. Si un cookie-secret est spécifié via le fichier de configuration, les secrets de cookies du fichier de secrets de cookies seront ignorés.
cookie-staging-secret: <chaîne hexadécimale de 128 bits>
Un secret de cookie avec lequel les cookies serveur peuvent être vérifiés, mais ne seront pas créés. Ceci est utile pour faire rouler les secrets de cookies dans les configurations anycast.

Un cookie-staging-secret ne peut être configuré que lorsqu'il existe également un cookie-secret configuré.

cookie-secret-file: <nom de fichier>
Fichier à partir duquel les secrets sont lus et utilisés dans les calculs de DNS Cookie. Les secrets ne seront lus à partir de ce fichier que si aucun secret de cookie n'est fourni dans le fichier de configuration via les options cookie-secret et cookie-staging-secret. La valeur par défaut est "//var/db/nsd/cookiesecrets.txt"

Dans la version 4.10.1 de NSD et les versions antérieures, l'emplacement par défaut du fichier de secrets de cookies était "//etc/nsd/nsd_cookiesecrets.txt". À des fins de migration, les secrets de cookies seront lus à cet emplacement si aucune valeur n'est donnée pour l'option cookie-secret-file et lorsque l'emplacement par défaut actuel ("//var/db/nsd/cookiesecrets.txt") n'existe pas.

Le contenu du fichier de secrets de cookies doit être manipulé avec les commandes add_cookie_secret, drop_cookie_secret et activate_cookie_secret de l'outil nsd-control(8). Veuillez consulter ce manuel pour savoir comment effectuer un roulement sécurisé des secrets de cookies.

tls-service-key: <nom de fichier>
Si activé, le serveur fournit un service TLS sur les sockets TCP avec le numéro de port du service TLS. Le numéro de port (853) est configuré avec tls-port. Pour l'activer, créez une interface : ligne d'option dans la configuration avec @port ajoutée à l'adresse IP. Cela crée le socket supplémentaire sur lequel le service DNS over TLS est fourni.

Le fichier est la clé privée pour la session TLS. Le certificat public se trouve dans le fichier tls-service-pem. La valeur par défaut est "", désactivé. Nécessite un redémarrage (un rechargement ne suffit pas) s'il est modifié, car la clé privée est lue pendant que les permissions root sont détenues et avant le chroot (le cas échéant).

tls-service-pem: <nom de fichier>
Le fichier de certificat de clé publique pem pour le service tls. La valeur par défaut est "", désactivé.
tls-service-ocsp: <nom de fichier>
Le fichier pem ocsp pour le service tls, pour le greffage OCSP. La valeur par défaut est "", désactivé. Un processus externe prépare et met à jour les données de greffage OCSP. Comme ceci, 
openssl ocsp -no_nonce \
	-respout /path/to/ocsp.pem \
	-CAfile /path/to/ca_and_any_intermediate.pem \
	-issuer /path/to/direct_issuer.pem \
	-cert /path/to/cert.pem \
	-url "$( openssl x509 -noout -ocsp_uri -in /path/to/cert.pem )"
tls-port: <nombre>
Le numéro de port sur lequel fournir le service TLS TCP, la valeur par défaut est 853, seules les interfaces configurées avec ce numéro de port comme @nombre recevront le service DNS over TLS.
tls-auth-port: <nombre>
Le numéro de port sur lequel fournir le service TLS TCP aux clients authentifiés uniquement. Si vous souhaitez utiliser l'authentification mutuelle TLS dans les connexions Transfer over TLS (XoT), c'est là que le serveur principal active un port dédié à cet effet. Les certificats dans tls-cert-bundle sont utilisés pour vérifier l'authenticité d'un client ou d'un serveur secondaire.

Le client (secondaire) doit activer tls-auth, configurer client-cert et client-key et activer tls-auth dans la configuration de zone afin de s'authentifier auprès d'un serveur (primaire) distant.

tls-auth-xfr-only: <oui ou non>
Autoriser les transferts de zone uniquement sur le port tls-auth-port et uniquement aux clients authentifiés. Cela fonctionne globalement pour toutes les zones. Une liste de contrôle d'accès provide-xfr avec tls-auth est également requise pour autoriser et vérifier une connexion. Les requêtes de transfert de zone sur d'autres ports sont refusées.
tls-cert-bundle: <nom de fichier>
Si nul ou "", les emplacements de vérification par défaut sont utilisés. Définissez-le sur le fichier de bundle de certificats, par exemple "/etc/pki/tls/certs/ca-bundle.crt". Ces certificats sont utilisés pour l'authentification
ating Transfer over TLS (XoT) connections.
proxy-protocol-port: <nombre>
Le numéro de port pour le service de protocole proxy. Si l'instruction est donnée plusieurs fois, des numéros de port supplémentaires peuvent être utilisés pour le service de protocole proxy. Les définitions d'interface qui utilisent ce numéro de port s'attendent au trafic du protocole proxy PROXYv2, pour UDP, TCP et pour le service TLS.
metrics-enable: <oui ou non>
Active le point de terminaison HTTP des métriques prometheus. Il expose les mêmes statistiques que la commande nsd-control(8) stats_noreset, mais avec des noms de métriques suivant la spécification prometheus. (Nécessite libevent2)

Attention, lorsque vous utilisez nsd-control(8) stats (au lieu de stats_noreset), les statistiques seront également réinitialisées pour le point de terminaison des métriques HTTP.

metrics-interface: <ip4 ou ip6 | nom d'interface>
NSD se connectera aux adresses ou interfaces listées pour servir les métriques prometheus. Peut être donné plusieurs fois pour se connecter à plusieurs adresses ip. Utilisez 0.0.0.0 et ::0 pour vous connecter à l'interface générique.

Si un nom d'interface est utilisé à la place de ip4 ou ip6, la liste des adresses IP associées à cette interface est récupérée et utilisée au démarrage du serveur.

Par défaut, 127.0.0.1 et ::1.

metrics-port: <nombre>
Le numéro de port pour le service HTTP. Par défaut, 9100.
metrics-path: <chaîne>
Le chemin HTTP pour exposer les métriques. Par défaut, "/metrics".

Contrôle à distance

La clause remote-control: est utilisée pour définir les options d'utilisation de l'outil nsd-control(8) pour envoyer des commandes au serveur NSD en cours d'exécution. Elle est désactivée par défaut et écoute par défaut sur localhost. Elle utilise TLS sur TCP où le serveur et le client s'authentifient mutuellement avec des certificats auto-signés. Les certificats auto-signés peuvent être générés avec l'outil nsd-control-setup. Les fichiers de clés sont lus par NSD avant le chroot et avant de réduire les privilèges utilisateur, ils peuvent donc être en dehors du chroot et être lisibles par le superutilisateur uniquement.

control-enable: <oui ou non>
Active le contrôle à distance, par défaut non.
control-interface: <ip4 ou ip6 | nom d'interface | chemin absolu>
NSD se connectera aux adresses listées pour traiter les requêtes de contrôle (sur TCP). Peut être donné plusieurs fois pour se connecter à plusieurs adresses ip. Utilisez 0.0.0.0 et ::0 pour servir l'interface générique. Si aucune n'est fournie, NSD écoute sur les interfaces localhost 127.0.0.1 et ::1 pour le contrôle, si le contrôle est activé avec control-enable.

Si un nom d'interface est utilisé à la place de ip4 ou ip6, la liste des adresses IP associées à cette interface est récupérée et utilisée au démarrage du serveur.

Avec un chemin absolu, un tube nommé local Unix est utilisé pour le contrôle. Le fichier est créé avec l'utilisateur et le groupe configurés et les bits d'accès sont définis pour permettre aux membres du groupe d'accéder. L'accès supplémentaire peut être contrôlé en définissant les permissions du répertoire contenant le fichier socket de contrôle. Les fichiers de clés et de certificats ne sont pas utilisés lorsque le contrôle s'effectue via le tube nommé, car le contrôle d'accès se fait par permission de fichier et de répertoire.

control-port: <nombre>
Le numéro de port pour le service de contrôle à distance. 8952 par défaut.
server-key-file: <nom de fichier>
Chemin vers la clé privée du serveur, par défaut //etc/nsd/nsd_server.key. Ce fichier est généré par l'utilitaire nsd-control-setup. Il est utilisé par le serveur nsd, mais pas par nsd-control.
server-cert-file: <nom de fichier>
Chemin vers le certificat auto-signé du serveur, par défaut //etc/nsd/nsd_server.pem. Ce fichier est généré par l'utilitaire nsd-control-setup. Il est utilisé par le serveur nsd, ainsi que par nsd-control.
control-key-file: <nom de fichier>
Chemin vers la clé privée du client de contrôle, par défaut //etc/nsd/nsd_control.key. Ce fichier est généré par l'utilitaire nsd-control-setup. Il est utilisé par nsd-control.
control-cert-file: <nom de fichier>
Chemin vers le certificat du client de contrôle, par défaut //etc/nsd/nsd_control.pem. Ce certificat doit être signé avec le certificat du serveur. Ce fichier est généré par l'utilitaire nsd-control-setup. Il est utilisé par nsd-control.

Options du vérificateur

La clause verify: est utilisée pour activer ou désactiver la vérification des zones, configurer les interfaces d'écoute et contrôler les valeurs par défaut globales.

enable: <oui ou non>
Active la vérification des zones. Par défaut, non.
port: <nombre>
Le port sur lequel répondre aux requêtes du vérificateur. Par défaut, 5347.
ip-address:
Interfaces pour se connecter pour la vérification des zones (par défaut, les interfaces localhost, généralement 127.0.0.1 et ::1). Pour se connecter à plusieurs adresses IP, listez-les une par une. Optionnellement, les options de socket ne peuvent pas être spécifiées pour verify ip-address
verify-zones: <oui ou non>
Vérifie les zones par défaut.
verifier: <commande>
Lorsqu'une mise à jour est reçue pour la zone (par IXFR ou AXFR), ce programme sera exécuté pour évaluer la zone avec la mise à jour. Si le programme se termine avec un code de sortie de 0, la zone est considérée comme valide et sera servie. Tout autre code de sortie désignera la zone comme invalide et la mise à jour reçue sera rejetée. La zone continuera d'être servie mais sans la mise à jour.

Les variables d'environnement suivantes sont disponibles pour les vérificateurs :

VERIFY_ZONE
Le nom de domaine de la zone à vérifier.

VERIFY_ZONE_ON_STDIN
Lorsque la zone peut être lue depuis l'entrée standard (stdin), cette variable est définie à "yes", sinon elle est définie à "no".

VERIFY_IP_ADDRESSES
La première adresse sur laquelle les zones à évaluer seront servies. Si IPv6 est disponible, une adresse IPv6 sera préférée à IPv4.

VERIFY_PORT
Le numéro de port pour VERIFY_IP_ADDRESS.

VERIFY_IPV6_ADDRESS
La première adresse IPv6 sur laquelle les zones à évaluer seront servies.

VERIFY_IPV6_PORT
Le numéro de port pour VERIFY_IPV6_ADDRESS.

VERIFY_IPV4_ADDRESS
La première adresse IPv4 sur laquelle les zones à évaluer seront servies.

VERIFY_IPV4_PORT
Le numéro de port pour VERIFY_IPV4_ADDRESS.

verifier-count: <nombre>
Nombre maximum de vérificateurs à exécuter simultanément. Par défaut, 1.
verifier-feed-zone: <oui ou non>
Alimente la zone mise à jour au vérificateur via l'entrée standard (stdin).
verifier-timeout: <secondes>
Le nombre maximum de secondes pendant lesquelles un vérificateur est autorisé à s'exécuter pour évaluer une zone. Si le vérificateur prend plus de temps, il sera terminé et la mise à jour de la zone sera rejetée. La valeur par défaut est 0 seconde, ce qui signifie que le vérificateur peut prendre autant de temps qu'il le faut.

Options de modèle

La clause pattern: est utilisée pour désigner un ensemble d'options à appliquer à certaines zones. Les mêmes options de zone que pour une zone sont autorisées.

name: <chaîne>
Le nom du modèle. C'est une chaîne de caractères (sensible à la casse). Les noms de modèles commençant par "_implicit_" sont utilisés en interne pour les zones qui n'ont pas de modèle (ils sont définis directement dans nsd.conf).
include-pattern: <nom du modèle>
Les options du modèle donné sont incluses à cet endroit dans ce modèle. Le modèle référencé doit être défini avant celui-ci.
<option de zone>: <valeur>
Les options de zone telles que zonefile, allow-query, allow-notify, request-xfr, allow-axfr-fallback, notify, notify-retry, provide-xfr, store-ixfr, ixfr-number, ixfr-size, create-ixfr, zonestats, outgoing-interface, verify-zone, verifier, verifier-feed-zone, verifier-timeout, catalog, et catalog-member-pattern peuvent être données. Elles sont appliquées aux modèles et aux zones qui incluent ce modèle.

Options de zone

Pour chaque zone, les options doivent être spécifiées dans une clause zone:. Les éléments de liste de contrôle d'accès peuvent être donnés plusieurs fois pour ajouter plusieurs serveurs. Ces éléments doivent être ajoutés explicitement.

Pour les zones configurées dans le fichier de configuration nsd.conf, leurs paramètres sont codés en dur (dans un modèle implicite pour elles seules) et elles ne peuvent pas être supprimées via delzone, mais supprimez-les du fichier de configuration et reconfigurez le modèle.

name: <chaîne>
Le nom de la zone. C'est le nom de domaine de l'apex de la zone. Peut se terminer par un '.' (en notation FQDN). Par exemple "example.com", "sub.example.net.". Cet attribut doit être présent dans chaque zone.
zonefile:
Le fichier contenant les informations de zone. Si cet attribut est présent, il est utilisé pour lire et écrire le contenu de la zone. Si l'attribut est absent, il empêche l'écriture de la zone.

La chaîne est traitée de manière à ce qu'une seule chaîne puisse être utilisée (dans un modèle) pour de nombreuses zones différentes. Si le label ou le caractère n'existe pas, le caractère pourcentage est remplacé par un point pour la sortie (c'est-à-dire pour le troisième caractère d'un nom de domaine à deux lettres).

%s est remplacé par le nom de la zone.

%1 est remplacé par le premier caractère du nom de la zone.

%2 est remplacé par le deuxième caractère du nom de la zone.

%3 est remplacé par le troisième caractère du nom de la zone.

%z est remplacé par le nom du domaine de premier niveau (tld) de la zone.

%y est remplacé par le label suivant sous le domaine de premier niveau.

%x est remplacé par le label avant-dernier sous le domaine de premier niveau.

allow-query: <ip-spec> <key-name | NOKEY | BLOCKED>
Liste de contrôle d'accès. Lorsqu'au moins une option allow-query est spécifiée, les adresses spécifiées dans les options allow-query sont autorisées à interroger le serveur pour la zone. Les requêtes provenant d'adresses non listées ou spécifiquement BLOQUÉES sont rejetées. Si NOKEY est spécifié, aucune signature TSIG n'est requise. BLOCKED supplante les autres entrées ; les autres entrées sont examinées pour une correspondance dans l'ordre des déclarations. Sans options allow-query, les requêtes sont autorisées depuis n'importe quelle adresse IP sans clé TSIG (ce qui est le comportement par défaut).

Le ip-spec est soit une adresse IP simple (IPv4 ou IPv6), soit un sous-réseau de la forme 1.2.3.4/24, soit masqué comme 1.2.3.4&255.255.255.0, soit une plage de la forme 1.2.3.4-1.2.3.25. Notez que les plages ip-spec n'utilisent pas d'espaces autour des symboles /, &, @ et -.

allow-notify: <ip-spec> <key-name | NOKEY | BLOCKED>
Liste de contrôle d'accès. L'adresse listée (primaire) est autorisée à envoyer des notifications à ce serveur (secondaire) via UDP ou TCP. Les notifications provenant d'adresses non listées ou spécifiquement BLOQUÉES sont rejetées. Si NOKEY est spécifié, aucune signature TSIG n'est requise. BLOCKED supplante les autres entrées ; les autres entrées sont examinées pour une correspondance dans l'ordre des déclarations.

Le ip-spec est soit une adresse IP simple (IPv4 ou IPv6), soit un sous-réseau de la forme 1.2.3.4/24, soit masqué comme 1.2.3.4&255.255.255.0, soit une plage de la forme 1.2.3.4-1.2.3.25. Un numéro de port peut être ajouté en utilisant un suffixe @numéro, par exemple 1.2.3.4@5300 ou 1.2.3.4/24@5300 pour le port 5300. Notez que les plages ip-spec n'utilisent pas d'espaces autour des symboles /, &, @ et -.


request-xfr: [AXFR|UDP] <ip-address> <key-name | NOKEY> [tls-auth-name]
Liste de contrôle d'accès. L'adresse listée (le primaire) est interrogée pour AXFR/IXFR lors des mises à jour. Un numéro de port peut être ajouté en utilisant un suffixe @numéro, par exemple 1.2.3.4@5300. La clé spécifiée est utilisée lors de AXFR/IXFR. Si tls-auth-name est inclus, la clause tls-auth spécifiée sera utilisée pour effectuer XFR-over-TLS authentifié.

Si l'option AXFR est spécifiée, le serveur ne sera pas contacté avec des requêtes IXFR, mais seules des requêtes AXFR seront envoyées au serveur. Cela permet à un secondaire NSD d'avoir un serveur primaire qui exécute NSD. Si l'option AXFR est omise, des requêtes IXFR et AXFR seront envoyées au serveur primaire.

Si l'option UDP est spécifiée, le secondaire utilisera UDP pour transmettre les requêtes IXFR. Vous devriez déployer TSIG lors de l'autorisation du transport UDP, pour authentifier les notifications et les transferts de zone. Sinon, NSD est plus vulnérable aux attaques de type Kaminsky. Si l'option UDP est omise, IXFR sera transmis via TCP.

Si un tls-auth-name est spécifié, TLS (par défaut sur le port 853) sera utilisé pour tous les transferts de zone pour la zone. Si l'authentification du primaire, basée sur les informations d'authentification tls-auth spécifiées, échoue, la requête XFR ne sera pas envoyée. La prise en charge de TLS 1.3 est requise pour XFR-over-TLS.

allow-axfr-fallback: <yes or no>
Cette option doit être accompagnée de request-xfr. Elle autorise (ou interdit) NSD (en tant que secondaire) à utiliser AXFR en dernier recours si le serveur de noms primaire ne prend pas en charge IXFR. La valeur par défaut est oui.
size-limit-xfr: <number>
Cette option doit être accompagnée de request-xfr. Elle spécifie la limite de taille du fichier temporaire XFR. Elle peut être utilisée pour arrêter la récupération de zones très volumineuses, qui autrement pourraient consommer beaucoup de mémoire et d'espace disque. Si cette option est à 0, illimité. La valeur par défaut est 0.
notify: <ip-address> <key-name | NOKEY>
Liste de contrôle d'accès. L'adresse listée (un secondaire) est notifiée des mises à jour de cette zone via UDP. Un numéro de port peut être ajouté en utilisant un suffixe @numéro, par exemple 1.2.3.4@5300. La clé spécifiée est utilisée pour signer la notification. Ce n'est que dans les configurations secondaires que NSD pourra détecter les mises à jour de zone (car il est lui-même notifié ou se rafraîchit après un certain temps).
notify-retry: <number>
Cette option doit être accompagnée de notify. Elle définit le nombre de nouvelles tentatives lors de l'envoi des notifications.
provide-xfr: <ip-spec> <key-name | NOKEY | BLOCKED> [tls-auth-name]
Liste de contrôle d'accès. L'adresse listée (un secondaire) est autorisée à demander XFR à ce serveur. Les données de zone seront fournies à l'adresse. La clé spécifiée est utilisée lors de XFR. Pour les adresses non listées ou BLOQUÉES, aucune donnée n'est fournie et les requêtes sont rejetées. BLOCKED supplante les autres entrées et les autres entrées sont examinées pour une correspondance dans l'ordre des déclarations.

Le ip-spec est soit une adresse IP simple (IPv4 ou IPv6), soit un sous-réseau de la forme 1.2.3.4/24, soit masqué comme 1.2.3.4&255.255.255.0, soit une plage de la forme 1.2.3.4-1.2.3.25. Un numéro de port peut être ajouté en utilisant un suffixe @numéro, par exemple 1.2.3.4@5300 ou 1.2.3.4/24@5300 pour le port 5300. Notez que les plages ip-spec n'utilisent pas d'espaces autour des symboles /, &, @ et -.

Si un tls-auth-name est spécifié, l'authentification TLS du secondaire sera effectuée pour les requêtes de transfert de zone pour la zone. L'extrémité distante doit se connecter au tls-auth-port et doit présenter un certificat avec une entrée SAN (Subject Alternative Name) DNS ou une entrée CN (Common Name) égale au auth-domain-name du tls-auth défini. La validité du certificat est également vérifiée avec tls-cert-bundle. Si l'authentification du secondaire, basée sur les informations d'authentification tls-auth spécifiées, échoue, le transfert de zone XFR sera refusé. Si la connexion est effectuée sur le tls-port, aucune authentification ne sera effectuée et le transfert ne sera pas refusé. Pour imposer uniquement les transferts de zone authentifiés, tls-auth-xfr-only doit également être activé. La prise en charge de TLS 1.3 est requise pour XFR-over-TLS.

outgoing-interface: <ip-address>
Liste de contrôle d'accès. L'adresse listée est utilisée pour demander AXFR|IXFR (dans le cas d'un secondaire) ou utilisée pour envoyer des notifications (dans le cas d'un primaire).

L'ip-address est une adresse IP simple (IPv4 ou IPv6). Un numéro de port peut être ajouté en utilisant un suffixe @numéro, par exemple 1.2.3.4@5300.

store-ixfr: <yes or no>
Si activé, le contenu IXFR est stocké et fourni à l'ensemble des clients spécifiés dans la déclaration provide-xfr. La valeur par défaut est non. Le contenu IXFR représente un ensemble plus restreint de modifications qui diffèrent entre les versions de zone, tandis qu'AXFR contient le contenu complet de la zone.
ixfr-number: <number>
Le nombre maximum de versions IXFR à stocker pour cette zone. La valeur par défaut est 5.
ixfr-size: <number>
La taille de stockage maximale à utiliser pour les versions IXFR de cette zone, en octets. La valeur par défaut est 1048576. Une valeur de 0 signifie illimité. Si vous souhaitez désactiver le stockage IXFR, définissez l'option store-ixfr sur no. NSD n'élide pas le contenu IXFR des versions qui ajoutent et suppriment les mêmes données. Il stocke et transmet les IXFR tels qu'ils ont été transmis par le serveur en amont.
create-ixfr: <yes or no>
Si activé, les données IXFR sont créées lorsque le fichier de zone est lu par le serveur. Cela nécessite que store-ixfr soit défini sur yes, afin que le contenu IXFR soit enregistré sur disque. La valeur par défaut est désactivé. Si le serveur ne fonctionne pas, l'option nsd-checkzone -i peut être utilisée pour créer un fichier IXFR. Lorsqu'un IXFR est créé, le serveur met en file d'attente une version de la zone dans un fichier temporaire, à l'emplacement où les fichiers ixfr sont stockés. Cela crée des données IXFR lorsque la zone est lue depuis le fichier, mais pas lorsqu'une zone est lue par transfert AXFR depuis un serveur, car alors le serveur de plus haut niveau qui origine les données est le seul endroit où les différences IXFR sont calculées et ces différences sont ensuite transmises telles quelles à tous les autres serveurs.
max-refresh-time: <seconds>
Limite le temps de rafraîchissement pour les zones secondaires. C'est le minuteur qui vérifie si la zone doit être rechargée lorsqu'elle expire. Normalement, la valeur du enregistrement SOA est utilisée, mais cette option limite cette valeur.
min-refresh-time: <seconds>
Limite le temps de rafraîchissement pour les zones secondaires.
max-retry-time: <seconds>
Limite le temps de nouvelle tentative pour les zones secondaires. C'est le minuteur qui effectue de nouvelles tentatives après une tentative de récupération échouée pour la zone. Normalement, la valeur du enregistrement SOA est utilisée, suivie d'une rétroaction exponentielle, mais cette option limite cette valeur.
min-retry-time: <seconds>
Limite le temps de nouvelle tentative pour les zones secondaires.
min-expire-time: <seconds or refresh+retry+1>
Limite le temps d'expiration pour les zones secondaires. La valeur peut être exprimée soit par un nombre de secondes, soit par la chaîne "refresh+retry+1". Avec cette dernière option, le temps d'expiration sera plafonné à la valeur de rafraîchissement plus la valeur de nouvelle tentative du enregistrement SOA, plus 1. Les valeurs de rafraîchissement et de nouvelle tentative seront soumises aux limites.
max-refresh-time: <seconds>
Max refresh time for the zone transfer. Default is 1 week. This is used when zone transfers from primary are disabled (e.g. by no TCP connection available, and the zone transfer times out). Or when the zone is obtained from a zone file, and the zone file does not specify a refresh time.
min-refresh-time: <seconds>
Min refresh time for the zone transfer. Default is 1 hour. This is used when zone transfers from primary are disabled (e.g. by no TCP connection available, and the zone transfer times out). Or when the zone is obtained from a zone file, and the zone file does not specify a refresh time.
max-retry-time: <seconds>
Max retry time for the zone transfer. Default is 1 day. This is used when zone transfers from primary are disabled.
min-retry-time: <seconds>
Min retry time for the zone transfer. Default is 1 hour. This is used when zone transfers from primary are disabled.
zonestats: <name>
Lorsque NSD est compilé avec --enable-zone-stats, il peut collecter des statistiques par zone. Ce nom donne le groupe auquel les statistiques sont ajoutées. Les groupes sont obtenus à partir de nsd-control stats et stats_noreset. La valeur par défaut est "". Vous pouvez utiliser "%s" pour utiliser le nom de la zone afin de suivre ses statistiques. Si la fonctionnalité n'est pas compilée, l'option peut être fournie mais sera ignorée.
include-pattern: <pattern-name>
Les options du modèle donné sont incluses à ce point. Le modèle référencé doit être défini avant cette zone.
rrl-whitelist: <rrltype>
Cette option permet de mettre sur liste blanche les requêtes de ce type rrltype, pour cette zone. Elles reçoivent la limite de débit de liste blanche. Vous pouvez fournir plusieurs lignes, chacune permettant d'ajouter un nouveau type rrltype à la liste blanche pour la zone. Par défaut, aucun type n'est mis sur liste blanche. Le rrltype est la classification des requêtes que le RRL de NSD utilise pour éviter que différents types n'interfèrent les uns avec les autres. Les types sont enregistrés dans les lignes de journal lorsque qu'un sous-réseau est bloqué (en verbosité 2). Les types de classification RRL sont : nxdomain, error, referral, any, rrsig, wildcard, nodata, dnskey, positive, all.
multi-primary-check: <yes or no>
Par défaut non. Si activé, vérifie toutes les sources principales pour la dernière version. Il utilise la version la plus élevée de toutes les sources principales configurées. Utile si vous avez plusieurs sources principales qui servent des numéros de version différents.
verify-zone: <yes or no>
Active ou désactive la vérification pour cette zone. Par défaut, la valeur est celle des zones configurées dans verify:.
verifier: <command>
Commande à exécuter pour évaluer cette zone. Par défaut, c'est le vérificateur configuré dans verify:.
verifier-feed-zone: <yes or no>
Alimente la zone mise à jour au vérificateur via l'entrée standard. Par défaut, c'est la valeur de verifier-feed-zone configurée dans verify:.
verifier-timeout: <seconds>
Nombre de secondes avant que le vérificateur ne soit terminé de force. Spécifiez 0 (zéro) pour ne pas utiliser de délai d'attente spécifique. Par défaut, c'est la valeur de verifier-timeout de verify:.
catalog: <consumer or producer>
Si défini sur consumer, le traitement des zones de catalogue est activé pour la zone. Une seule zone peut être configurée comme zone consommatrice de catalogue. Lorsque plus d'une zone consommatrice de catalogue est configurée, aucune d'entre elles ne sera traitée. Les zones membres du catalogue utiliseront le modèle spécifié par la propriété de groupe, ou si une propriété de groupe est manquante ou invalide, le modèle spécifié par l'option catalog-member-pattern sera utilisé. Les propriétés de groupe sont valides s'il n'y a qu'une seule valeur correspondant au nom d'un modèle valide pour les zones membres.

Une zone avec l'option définie sur producer peut être utilisée pour produire une zone de catalogue. Les zones membres pour les zones productrices de catalogue peuvent être ajoutées avec "nsd-control addzone <zone> <pattern>", où <pattern> a une option catalog-producer-zone pointant vers une zone productrice de catalogue. Les membres obtiendront une propriété de groupe avec le nom du modèle comme valeur. Les zones productrices de catalogue doivent être des zones primaires et ne peuvent pas avoir d'option request-xfr. Les zones productrices de catalogue ne liront pas le contenu des fichiers de zone, mais reconstruiront la zone au démarrage à partir des entrées des zones membres dans //var/db/nsd/zone.list, spécifié avec l'option zonelistfile.

L'état des zones consommatrices et productrices de catalogue peut être vérifié avec nsd-control zonestatus. Il affichera le nombre de zones membres et, si la zone de catalogue est invalide, la raison pour laquelle elle est invalide sera affichée. nsd-control zonestatus affichera également l'entrée d'une zone membre de catalogue dans la zone de catalogue (consommatrice ou productrice) sous la forme catalog-member-id:.

Une zone de catalogue peut être soit une zone consommatrice de catalogue, soit une zone productrice de catalogue, mais pas les deux. De même, les zones membres de catalogue peuvent être soit membres d'une zone consommatrice de catalogue, soit membres d'une zone productrice de catalogue, mais pas les deux.

Les zones de catalogue contiennent une liste de zones qui sont servies. Utilisez allow-query: 0.0.0.0/0 BLOCKED et allow-query: ::0/0 BLOCKED dans une clause de zone ou de modèle de catalogue pour éviter de révéler le catalogue. Envisagez également d'utiliser des transferts via TLS pour protéger davantage le catalogue contre les écoutes clandestines.

catalog-member-pattern: <pattern-name>
Si cette option est fournie pour une zone consommatrice de catalogue, les membres de ce catalogue qui ont une propriété de groupe manquante ou invalide seront ajoutés en utilisant le modèle <pattern-name>.
catalog-producer-zone: <zone-name>
Cette option ne peut être utilisée que dans un modèle. L'ajout d'une zone en utilisant "nsd-control addzone <zone> <pattern>" avec un <pattern> contenant cette option, créera une entrée de membre de catalogue dans la zone productrice de catalogue <zone-name>. <zone-name> doit exister et doit être une zone productrice de catalogue valide.

Déclarations de clé

La clause key: établit une clé à utiliser dans les listes de contrôle d'accès. Elle a les attributs suivants.

name: <string>
Le nom de la clé. Utilisé pour faire référence à cette clé dans la liste de contrôle d'accès. Le nom de la clé doit être correct pour que tsig fonctionne. Ceci est dû au fait que le nom de la clé est transmis sur le réseau.
algorithm: <string>
Algorithme d'authentification pour cette clé. Par exemple hmac-md5, hmac-sha1, hmac-sha224, hmac-sha256, hmac-sha384 et hmac-sha512. Peut également être abrégé en 'sha1', 'sha256'. La valeur par défaut est sha256. Les algorithmes ne sont disponibles que lorsqu'ils ont été compilés (disponibles dans la bibliothèque cryptographique).
secret: <base64 blob>
Le secret partagé encodé en base64. Il est possible de placer la déclaration secret: (et le blob base64) dans un fichier différent, puis d'include: ce fichier. De cette manière, le secret de la clé et le reste du fichier de configuration, qui peuvent avoir des politiques de sécurité différentes, peuvent être séparés. Le contenu du secret est le contenu secret convenu en base64. Pour le générer, entrez un mot de passe (sa longueur doit être un multiple de 4 caractères, A-Za-z0-9), ou utilisez la sortie de dev-random via un filtre d'encodage base64.

Déclarations d'authentification TLS

La clause tls-auth: établit les attributs à utiliser lors de l'authentification de l'extrémité distante d'une connexion TLS ainsi que pour définir les informations d'identification pour s'authentifier auprès d'un serveur distant. Elle est utilisée dans les listes de contrôle d'accès pour XFR-over-TLS. Elle a les attributs suivants.

name: <string>
Le nom de tls-auth. Utilisé pour faire référence à ces informations d'authentification TLS dans la liste de contrôle d'accès.
auth-domain-name: <string>
Le nom de domaine d'authentification tel que défini dans RFC8310. Utilisé pour vérifier le certificat du serveur distant qui se connecte. Lorsqu'il est utilisé par un serveur primaire dans provide-xfr, il vérifie le secondaire. Lorsqu'il est utilisé par un serveur secondaire dans request-xfr, il vérifie le primaire.
client-cert: <file name of clientcert.pem>
Si vous souhaitez utiliser l'authentification TLS mutuelle, c'est ici que les certificats clients que NSD utilise pour se connecter au serveur en amont pour télécharger la zone peuvent être configurés. Le fichier de certificat public du client pem peut être configuré ici. Configurez également une clé privée avec client-key.
client-key: <file name of clientkey.key>
Si vous souhaitez utiliser l'authentification TLS mutuelle, le fichier de clé privée peut être configuré ici pour l'authentification du client.
client-key-pw: <string>
Si le fichier client-key utilise un mot de passe pour déchiffrer la clé avant qu'elle ne puisse être utilisée, alors le mot de passe peut être spécifié ici sous forme de chaîne. Il est possible d'inclure d'autres fichiers de configuration avec l'option include :, et cela peut être utilisé pour déplacer ces données sensibles dans un autre fichier, si vous le souhaitez.

Options de journalisation DNSTAP

Le support de DNSTAP, lorsqu'il est compilé, est activé dans la section dnstap:. Cela démarre un processus collecteur qui écrit les informations de journalisation vers la destination.

dnstap-enable: <yes or no>
Si dnstap est activé. Par défaut non. Si oui, il se connecte au serveur dnstap et si l'une des options dnstap-log-..-messages est activée, il envoie les journaux pour ces messages au serveur.
dnstap-socket-path: <file name>
Définit le nom du fichier de socket Unix pour la connexion au serveur qui écoute sur ce socket. La valeur par défaut est "//var/run/nsd-dnstap.sock".
dnstap-ip: <"" or addr[@port]>
Si désactivé avec "", le chemin du socket est utilisé. Avec une valeur, comme une adresse ou une adresse@port, comme "127.0.0.1@3333", TCP ou TLS est utilisé. La valeur par défaut est "".
dnstap-tls: <yes or no>
Si activé, TLS est utilisé vers l'adresse spécifiée dans dnstap-ip. Sinon, TCP est utilisé. La valeur par défaut est oui.
dnstap-tls-server-name: <string>
Le nom pour authentifier le serveur en amont. Avec "" désactivé.
dnstap-tls-client-key-file: <file name of clientkey.key>
Fichier de clé privée pour l'authentification du client TLS.

Le fichier clé pour l'authentification client, ou "" pour désactiver.
dnstap-tls-client-cert-file: <nom de fichier>
Le fichier certificat pour l'authentification client, ou "" pour désactiver.
dnstap-send-identity: <oui ou non>
Si activé, l'identité du serveur est incluse dans les messages de journalisation. Par défaut, c'est non.
dnstap-send-version: <oui ou non>
Si activé, la version du serveur est incluse dans les messages de journalisation. Par défaut, c'est non.
dnstap-identity: <chaîne>
L'identité à envoyer avec les messages. Si c'est "", le nom d'hôte est utilisé. Par défaut, c'est "".
dnstap-version: <chaîne>
La version à envoyer avec les messages. Si c'est "", la version du paquet est utilisée. Par défaut, c'est "".
dnstap-log-auth-query-messages: <oui ou non>
Activer la journalisation des messages de requête d'authentification. Par défaut, c'est non. Ce sont les requêtes des clients vers NSD.
dnstap-log-auth-response-messages: <oui ou non>
Activer la journalisation des messages de réponse d'authentification. Par défaut, c'est non. Ce sont les réponses de NSD aux clients.

NSD CONFIGURATION POUR LES HACKERS DE BIND9

BIND9 est une implémentation de serveur de noms avec son propre format de fichier de configuration, named.conf(5). BIND9 classe les zones comme 'Primary' ou 'Secondary'.

Zones secondaires

Pour une zone secondaire, les serveurs primaires sont listés. Les serveurs primaires sont interrogés pour les données de zone, et sont écoutés pour les notifications de mise à jour. Dans NSD, ces deux propriétés doivent être configurées séparément, en listant l'adresse primaire dans les instructions allow-notify et request-xfr.

Dans BIND9, vous n'avez besoin de fournir des éléments allow-notify que pour les sources supplémentaires de notifications (c'est-à-dire les opérateurs), NSD a besoin d'avoir allow-notify pour les primaires et les opérateurs. BIND9 autorise des sources de transfert supplémentaires, dans NSD vous les listez comme request-xfr.

Voici un exemple de zone secondaire en syntaxe BIND9.

# Fichier de configuration pour example.org
options {
	dnssec-enable yes;
};

key tsig.example.org. {
	algorithm hmac-md5;
	secret "aaaaaabbbbbbccccccdddddd";
};

server 162.0.4.49 {
	keys { tsig.example.org. ; };
};

zone "example.org" {
	type secondary;
	file "secondary/example.org.signed";
	primaries { 162.0.4.49; };
};
Pour NSD, DNSSEC est activé automatiquement pour les zones qui sont signées. L'instruction dnssec-enable dans la clause options n'est pas nécessaire. Dans NSD, les clés sont associées à une adresse IP dans l'instruction de liste de contrôle d'accès, par conséquent l'instruction server{} n'est pas nécessaire. Ci-dessous, le même exemple dans un fichier de configuration NSD. 
# Fichier de configuration pour example.org
key:
	name: tsig.example.org.
	algorithm: hmac-md5
	secret: "aaaaaabbbbbbccccccdddddd"

zone:
	name: "example.org"
	zonefile: "secondary/example.org.signed"
	# le primaire est autorisé à notifier et fournira les données de zone.
	allow-notify: 162.0.4.49 NOKEY
	request-xfr: 162.0.4.49 tsig.example.org.

Notez que le primaire est listé deux fois, une fois pour lui permettre d'envoyer des notifications à ce serveur secondaire et une fois pour indiquer au serveur secondaire où chercher les données de zone mises à jour. Plus de lignes allow-notify et request-xfr peuvent être ajoutées pour spécifier d'autres primaires.

Il est possible de spécifier des lignes allow-notify supplémentaires pour les adresses qui sont également autorisées à envoyer des notifications à ce serveur secondaire.

Zones primaires

Pour une zone primaire dans BIND9, les serveurs secondaires sont listés. Ces serveurs secondaires reçoivent des notifications de mises à jour et sont autorisés à demander le transfert des données de zone. Dans NSD, ces deux propriétés doivent être configurées séparément.

Voici un exemple de zone primaire en syntaxe BIND9.

zone "example.nl" {
	type primary;
	file "example.nl";
};

En syntaxe NSD, cela devient :

zone:
	name: "example.nl"
	zonefile: "example.nl"
	# autorise n'importe qui à demander le transfert.
	provide-xfr: 0.0.0.0/0 NOKEY
	provide-xfr: ::0/0 NOKEY

# pour lister un serveur secondaire, vous donneriez généralement
# provide-xfr: 1.2.3.4 tsig-key.name.
# notify: 1.2.3.4 NOKEY

Autre

NSD est un serveur DNS faisant uniquement autorité. Cela signifie qu'il est destiné à être un serveur primaire ou secondaire pour les zones, fournissant des données DNS aux résolveurs et aux caches DNS. BIND9 peut fonctionner comme un serveur DNS faisant autorité, les options de configuration pour cela sont comparées à celles de NSD dans cette section. Cependant, BIND9 peut également fonctionner comme un résolveur ou un cache. Les options de configuration que BIND9 a pour le résolveur ou la mise en cache n'ont donc pas d'équivalents pour NSD.
