DESCRIPTION

gcov est un programme de couverture de test. Utilisez-le en concertation avec GCC pour analyser vos programmes afin de créer du code plus efficace et plus rapide, et pour découvrir les parties non testées de votre programme. Vous pouvez utiliser gcov comme outil de profilage pour identifier où vos efforts d'optimisation auront le plus d'impact sur votre code. Vous pouvez également utiliser gcov en conjonction avec l'autre outil de profilage, gprof, pour évaluer quelles parties de votre code utilisent le plus de temps de calcul.

Les outils de profilage vous aident à analyser les performances de votre code. En utilisant un profileur tel que gcov ou gprof, vous pouvez obtenir des statistiques de performance de base, telles que :

  • la fréquence d'exécution de chaque ligne de code
  • quelles lignes de code sont effectivement exécutées
  • la quantité de temps de calcul utilisée par chaque section de code

Une fois que vous connaissez ces informations sur le fonctionnement de votre code lorsqu'il est compilé, vous pouvez examiner chaque module pour déterminer lesquels doivent être optimisés. gcov vous aide à identifier où concentrer vos efforts d'optimisation.

Les développeurs de logiciels utilisent également les tests de couverture en concertation avec des suites de tests, pour s'assurer que le logiciel est suffisamment bon pour une publication. Les suites de tests peuvent vérifier qu'un programme fonctionne comme prévu ; un programme de couverture vérifie quelle partie du programme est exercée par la suite de tests. Les développeurs peuvent alors déterminer quels types de cas de test doivent être ajoutés aux suites de tests pour créer à la fois de meilleurs tests et un meilleur produit final.

Vous devriez compiler votre code sans optimisation si vous prévoyez d'utiliser gcov car l'optimisation, en combinant certaines lignes de code en une seule fonction, peut ne pas vous donner autant d'informations que nécessaire pour rechercher les « points chauds » où le code utilise beaucoup de temps de calcul. De même, comme gcov accumule les statistiques par ligne (au niveau de résolution le plus bas), il fonctionne mieux avec un style de programmation qui place une seule instruction par ligne. Si vous utilisez des macros complexes qui se déploient en boucles ou en d'autres structures de contrôle, les statistiques sont moins utiles — elles ne rapportent que la ligne où l'appel de macro apparaît. Si vos macros complexes se comportent comme des fonctions, vous pouvez les remplacer par des fonctions inline pour résoudre ce problème.

gcov crée un fichier journal appelé sourcefile.gcov qui indique combien de fois chaque ligne d'un fichier source sourcefile.c a été exécutée. Vous pouvez utiliser ces fichiers journaux avec gprof pour aider à affiner les performances de vos programmes. gprof fournit des informations de chronométrage que vous pouvez utiliser avec les informations obtenues de gcov.

gcov ne fonctionne qu'avec le code compilé par GCC. Il n'est compatible avec aucun autre mécanisme de profilage ou de couverture de test.

OPTIONS

-a
--all-blocks
Écrit les comptes d'exécution individuels pour chaque bloc de base. Normalement, gcov ne génère des comptes d'exécution que pour les blocs principaux d'une ligne. Avec cette option, vous pouvez déterminer si des blocs au sein d'une même ligne ne sont pas exécutés.
-b
--branch-probabilities
Écrit les fréquences de branchement dans le fichier de sortie, et écrit les informations récapitulatives des branchements sur la sortie standard. Cette option vous permet de voir à quelle fréquence chaque branche de votre programme a été prise. Les branchements inconditionnels ne seront pas affichés, sauf si l'option -u est donnée.
-c
--branch-counts
Écrit les fréquences de branchement sous forme de nombre de branchements pris, plutôt que de pourcentage de branchements pris.
-g
--conditions
Écrit la couverture des conditions dans le fichier de sortie, et écrit les informations récapitulatives des conditions sur la sortie standard. Cette option vous permet de voir si les conditions de votre programme ont eu au moins une fois un effet indépendant sur le résultat de l'expression booléenne (couverture de condition/décision modifiée). Cela nécessite de compiler la source avec -fcondition-coverage.
-d
--display-progress
Affiche la progression sur la sortie standard.
-f
--function-summaries
Génère des résumés pour chaque fonction en plus du résumé au niveau du fichier.
-h
--help
Affiche l'aide sur l'utilisation de gcov (sur la sortie standard), et quitte sans effectuer d'autres traitements.
-j
--json-format
Génère le fichier gcov dans un format JSON intermédiaire facile à analyser, qui ne nécessite pas le code source pour la génération. Le fichier JSON est compressé avec l'algorithme de compression gzip et les fichiers ont l'extension .gcov.json.gz.

La structure du JSON est la suivante :

{
  "current_working_directory": "foo/bar",
  "data_file": "a.out",
  "format_version": "2",
  "gcc_version": "11.1.1 20210510"
  "files": ["$file"]
}

Les champs de l'élément racine ont la sémantique suivante :

  • current_working_directory : répertoire de travail où une unité de compilation a été compilée
  • data_file : nom du fichier de données (GCDA)
  • format_version : version sémantique du format

    Changements dans la version 2 :

*
calls : informations sur les appels de fonction sont ajoutées
*
gcc_version : version du compilateur GCC

Chaque file a la forme suivante :

{
  "file": "a.c",
  "functions": ["$function"],
  "lines": ["$line"]
}

Les champs de l'élément file ont la sémantique suivante :

*
file_name : nom du fichier source

Chaque function a la forme suivante :

{
  "blocks": 2,
  "blocks_executed": 2,
  "demangled_name": "foo",
  "end_column": 1,
  "end_line": 4,
  "execution_count": 1,
  "name": "foo",
  "start_column": 5,
  "start_line": 1
}

Les champs de l'élément function ont la sémantique suivante :

  • blocks : nombre de blocs dans la fonction
  • blocks_executed : nombre de blocs exécutés de la fonction
  • demangled_name : nom démêlé de la fonction
  • end_column : colonne dans le fichier source où la fonction se termine
  • end_line : ligne dans le fichier source où la fonction se termine
  • execution_count : nombre d'exécutions de la fonction
  • name : nom de la fonction
  • start_column : colonne dans le

    • Notez que les numéros de ligne et de colonne commencent à 1. Dans l'implémentation actuelle, start_line et start_column n'incluent pas les paramètres de modèle et le type de retour préfixé, mais cela est susceptible d'être corrigé à l'avenir.

    Chaque line a la forme suivante :

    {
  "block_ids": ["$block_id"],
  "branches": ["$branch"],
  "calls": ["$call"],
  "count": 2,
  "conditions": ["$condition"],
  "line_number": 15,
  "unexecuted_block": false,
  "function_name": "foo",
}

    Les branches et les appels ne sont présents qu'avec l'option -b. Les champs de l'élément line ont la sémantique suivante :

    • block_ids : IDs des blocs de base appartenant à la ligne
    • count : nombre d'exécutions de la ligne
    • line_number : numéro de ligne
    • unexecuted_block : indicateur si la ligne contient un bloc non exécuté (toutes les instructions de la ligne ne sont pas exécutées)
    • function_name : nom d'une fonction à laquelle cette line appartient (peut ne pas être défini pour une ligne avec des instructions inline)

    Chaque branch a la forme suivante :

    {
  "count": 11,
  "destination_block_id": 17,
  "fallthrough": true,
  "source_block_id": 13,
  "throw": false
}

    Les champs de l'élément branch ont la sémantique suivante :

    • count : nombre d'exécutions de la branche
    • fallthrough : vrai si la branche est une branche de continuation
    • throw : vrai si la branche est une branche exceptionnelle
    • isource_block_id : ID du bloc de base où cette branche se produit
    • destination_block_id : ID du bloc de base vers lequel cette branche saute

    Chaque call a la forme suivante :

    {
  "destination_block_id": 1,
  "returned": 11,
  "source_block_id": 13
}

    Les champs de l'élément call ont la sémantique suivante :

    • returned : nombre de fois qu'un appel de fonction est retourné (le nombre d'appels est égal à line::count)
    • isource_block_id : ID du bloc de base où cet appel se produit
    • destination_block_id : ID du bloc de base où l'exécution reprend après le retour de l'appel

    Chaque condition a la forme suivante :

    {
  "count": 4,
  "covered": 2,
  "not_covered_false": [],
  "not_covered_true": [0, 1],
}

    Les champs de l'élément condition ont la sémantique suivante :

    • count : nombre d'issues de condition dans cette expression
    • covered : nombre d'issues de condition couvertes dans cette expression
    • not_covered_true : termes, par index, qui n'ont pas été vus comme vrais dans cette expression
    • not_covered_false : termes, par index, qui n'ont pas été vus comme faux dans cette expression
    -H
    --human-readable
    Écrit les comptes dans un format lisible par l'homme (comme 24,6k).
    -k
    --use-colors
    Utilise des couleurs pour les lignes de code qui ont une couverture nulle. Nous utilisons la couleur rouge pour les lignes non exceptionnelles et le cyan pour les lignes exceptionnelles. Les mêmes couleurs sont utilisées pour les blocs de base avec l'option -a.
    -l
    --long-file-names
    Crée des noms de fichiers longs pour les fichiers source inclus. Par exemple, si le fichier d'en-tête x.h contient du code et a été inclus dans le fichier a.c, alors exécuter gcov sur le fichier a.c produira un fichier de sortie appelé a.c##x.h.gcov au lieu de x.h.gcov. Ceci peut être utile si x.h est inclus dans plusieurs fichiers source et que vous souhaitez voir les contributions individuelles. Si vous utilisez l'option -p, les noms des fichiers incluant et inclus seront des chemins complets.
    -m
    --demangled-names
    Affiche les noms de fonctions démanglés dans la sortie. Par défaut, les noms de fonctions manglés sont affichés.
    -n
    --no-output
    Ne crée pas le fichier de sortie gcov.
    -o directory|file
    --object-directory directory
    --object-file file
    Spécifie le répertoire contenant les fichiers de données gcov, ou le nom du chemin de l'objet. Les fichiers de données .gcno et .gcda sont recherchés en utilisant cette option. Si un répertoire est spécifié, les fichiers de données se trouvent dans ce répertoire et portent le nom du fichier d'entrée, sans son extension. Si un fichier est spécifié ici, les fichiers de données portent le nom de ce fichier, sans son extension.
    -p
    --preserve-paths
    Conserve les informations de chemin complètes dans les noms des fichiers .gcov générés. Sans cette option, seule la composante nom de fichier est utilisée. Avec cette option, tous les répertoires sont utilisés, avec les caractères / traduits en caractères #, les composantes de répertoire . supprimées et les composantes .. non supprimables renommées en ^. Ceci est utile si les fichiers source se trouvent dans plusieurs répertoires différents.
    -q
    --use-hotness-colors
    Produit une sortie colorée de type perf pour les lignes chaudes. Une légende de l'échelle de couleurs est imprimée au tout début du fichier de sortie.
    -r
    --relative-only
    N'affiche que les informations sur les fichiers source avec un chemin relatif (après élision du préfixe source). Les chemins absolus sont généralement des fichiers d'en-tête système et la couverture des fonctions inline qui s'y trouvent n'est normalement pas intéressante.
    -s directory
    --source-prefix directory
    Un préfixe pour les noms de fichiers source à supprimer lors de la génération des fichiers de couverture de sortie. Cette option est utile lors de la compilation dans un répertoire séparé, et que le chemin du répertoire source ne doit pas être inclus lors de la détermination des noms de fichiers de sortie. Notez que cette détection de préfixe est appliquée avant de déterminer si le fichier source est absolu.
    -t
    --stdout
    Sortie vers la sortie standard au lieu de fichiers de sortie.
    -u
    --unconditional-branches
    Lorsque les probabilités de branche sont fournies, inclure celles des branches inconditionnelles. Les branches inconditionnelles ne sont normalement pas intéressantes.
    -v
    --version
    Affiche le numéro de version de gcov (sur la sortie standard) et quitte sans effectuer de traitement supplémentaire.
    -w
    --verbose
    Affiche des informations détaillées relatives aux blocs de base et aux arcs.
    -x
    --hash-filenames
    Lors de l'utilisation de --preserve-paths, gcov utilise le chemin complet des fichiers source pour créer un nom de fichier de sortie. Cela peut entraîner de longs noms de fichiers qui peuvent dépasser les limites du système de fichiers. Cette option crée des noms de la forme source-file##md5.gcov, où la composante source-file est la partie finale du nom de fichier et md5 est calculé à partir du nom manglé complet qui aurait été utilisé sinon. L'option est une alternative à --preserve-paths sur les systèmes qui ont une limite de système de fichiers.

    gcov doit être exécuté avec le répertoire courant identique à celui dans lequel vous avez invoqué le compilateur. Sinon, il ne pourra pas localiser les fichiers source. gcov produit des fichiers appelés mangledname.gcov dans le répertoire courant. Ceux-ci contiennent les informations de couverture du fichier source auquel ils correspondent. Un fichier .gcov est produit pour chaque fichier source (ou d'en-tête) contenant du code, qui a été compilé pour produire les fichiers de données. La partie mangledname du nom du fichier de sortie est généralement simplement le nom du fichier source, mais peut être quelque chose de plus complexe si les options -l ou -p sont données. Référez-vous à ces options pour plus de détails.

    Si vous invoquez gcov avec plusieurs fichiers d'entrée, les contributions de chaque fichier d'entrée sont additionnées. Typiquement, vous l'invoqueriez avec la même liste de fichiers que celle utilisée pour l'édition des liens finale de votre exécutable.

    Les fichiers .gcov contiennent des champs séparés par des : le long du code source du programme. Le format est

    <execution_count>:<line_number>:<source line text>

    Des informations supplémentaires sur les blocs peuvent suivre chaque ligne, lorsqu'elles sont demandées par une option de ligne de commande. L'execution_count est - pour les lignes ne contenant pas de code. Les lignes non exécutées sont marquées ##### ou =====, selon qu'elles sont accessibles par des chemins non exceptionnels ou seulement par des chemins exceptionnels tels que les gestionnaires d'exceptions C++, respectivement. Avec l'option -a, les blocs non exécutés sont marqués $$$$$ ou %%%%%, selon qu'un bloc de base est accessible via des chemins non exceptionnels ou exceptionnels. Les blocs de base exécutés ayant une instruction avec un execution_count nul se terminent par le caractère * et sont colorés en magenta avec l'option -k. Cette fonctionnalité n'est pas supportée en Ada.

    Notez que GCC peut supprimer complètement les corps de fonctions qui ne sont pas nécessaires -- par exemple, si elles sont inlinées partout. Ces fonctions sont marquées avec -, ce qui peut prêter à confusion. Utilisez l'option -fkeep-inline-f

    fonctions et les options -fkeep-static-functions pour conserver ces fonctions et permettre à gcov d'afficher correctement leur execution_count.

    Certaines lignes d'information au début ont un line_number de zéro. Ces lignes d'en-tête sont de la forme

    -:0:<tag>:<value>

    L'ordre et le nombre de ces lignes d'en-tête seront augmentés à mesure que le développement de gcov progressera --- ne vous fiez pas à leur maintien inchangé. Utilisez tag pour localiser une ligne d'en-tête particulière.

    Les informations supplémentaires sur les blocs sont de la forme

    <tag> <information>

    L'information est lisible par l'homme, mais conçue pour être assez simple pour être analysée par machine également.

    Lors de l'affichage des pourcentages, 0 % et 100 % ne sont affichés que lorsque les valeurs sont exactement 0 % et 100 % respectivement. D'autres valeurs qui seraient conventionnellement arrondies à 0 % ou 100 % sont au lieu de cela affichées comme la valeur non limite la plus proche.

    Lorsque vous utilisez gcov, vous devez d'abord compiler votre programme avec une option spéciale de GCC --coverage. Cela indique au compilateur de générer des informations supplémentaires nécessaires à gcov (essentiellement un graphe de flux du programme) et inclut également du code supplémentaire dans les fichiers objets pour générer les informations de profilage supplémentaires nécessaires à gcov. Ces fichiers supplémentaires sont placés dans le répertoire où se trouve le fichier objet.

    L'exécution du programme générera une sortie de profilage. Pour chaque fichier source compilé avec -fprofile-arcs, un fichier .gcda correspondant sera placé dans le répertoire du fichier objet.

    L'exécution de gcov avec les noms des fichiers sources de votre programme comme arguments produira désormais une liste du code accompagnée de la fréquence d'exécution pour chaque ligne. Par exemple, si votre programme s'appelle tmp.cpp, voici ce que vous voyez lorsque vous utilisez la fonctionnalité de base de gcov :

    $ g++ --coverage tmp.cpp -c
$ g++ --coverage tmp.o
$ a.out
$ gcov tmp.cpp -m

    Dans ce mode, chaque bloc de base n'est affiché que sur une seule ligne -- la dernière ligne du bloc. Un bloc multiligne ne contribuera qu'au compte d'exécution de cette dernière ligne, et les autres lignes ne seront pas affichées comme contenant du code, à moins que des blocs précédents ne se terminent sur ces lignes. Le compte d'exécution total d'une ligne est affiché et les lignes suivantes montrent les comptes d'exécution des blocs individuels qui se terminent sur cette ligne. Après chaque bloc, les comptes de branchement et d'appel du bloc seront affichés, si l'option -b est donnée.

    En raison de la façon dont GCC instrumente les appels, un compte d'appel peut être affiché après une ligne sans blocs individuels. Comme vous pouvez le voir, la ligne 33 contient un bloc de base qui n'a pas été exécuté.

    Pour chaque bloc de base, une ligne est affichée après la dernière ligne du bloc de base décrivant le branchement ou l'appel qui termine le bloc de base. Il peut y avoir plusieurs branchements et appels listés pour une seule ligne source s'il existe plusieurs blocs de base qui se terminent sur cette ligne. Dans ce cas, les branchements et les appels reçoivent chacun un numéro. Il n'y a pas de moyen simple de faire correspondre ces branchements et appels aux constructions sources. En général, cependant, le branchement ou l'appel numéroté le plus bas correspondra à la construction la plus à gauche sur la ligne source.

    Pour un branchement, s'il a été exécuté au moins une fois, un pourcentage indiquant le nombre de fois où le branchement a été pris divisé par le nombre de fois où le branchement a été exécuté sera affiché. Sinon, le message « jamais exécuté » est affiché.

    Pour un appel, s'il a été exécuté au moins une fois, un pourcentage indiquant le nombre de fois où l'appel a retourné divisé par le nombre de fois où l'appel a été exécuté sera affiché. Ce sera généralement 100 %, mais peut être inférieur pour les fonctions qui appellent "exit" ou "longjmp", et qui peuvent donc ne pas retourner à chaque fois qu'elles sont appelées.

    Les comptes d'exécution sont cumulatifs. Si le programme d'exemple était exécuté à nouveau sans supprimer le fichier .gcda, le compte du nombre de fois où chaque ligne du code source a été exécutée serait ajouté aux résultats de la ou des exécutions précédentes. Ceci est potentiellement utile de plusieurs manières. Par exemple, il pourrait être utilisé pour accumuler des données sur un certain nombre d'exécutions de programmes dans le cadre d'une suite de vérification de tests, ou pour fournir des informations plus précises à long terme sur un grand nombre d'exécutions de programmes.

    NAME

    gcov — GCC coverage testing tool

    SYNOPSIS

    gcov [option...] [-h|--help] [-v|--version] [sourcefile...])

    DESCRIPTION

    gcov is a tool to help you discover which parts of your program are, and are not, being executed. It can be used in conjunction with GCC to identify code that appears to have had no coverage during testing.

    When you compile your program with the GCC compiler, you can add the flag -fprofile-arcs. This flag tells GCC to instrument the code to collect coverage data. When you run your program, it will generate a .gcda file for each source file containing coverage data. This data can then be analyzed by gcov.

    If a source file is compiled with -fprofile-arcs, the profiling code first attempts to read an existing .gcda file; if the file doesn't match the executable (differing number of basic block counts), it will ignore the contents of the file. It then adds the new execution counts and finally writes the data to the file.

    Using gcov with GCC Optimization

    If you plan to use gcov to help optimize your code, you must first compile your program with a special GCC option --coverage. Aside from that, you can use any other GCC options; but if you want to prove that every single line in your program was executed, you should not compile with optimization at the same time. On some machines the optimizer can eliminate some simple code lines by combining them with other lines. For example, code like this:

    if (a != b)
  c = 1;
else
  c = 0;

    can be compiled into one instruction on some machines. In this case, there is no way for gcov to calculate separate execution counts for each line because there isn't separate code for each line. Hence the gcov output looks like this if you compiled the program with optimization:

    100:   12:if (a != b)
100:   13:  c = 1;
100:   14:else
100:   15:  c = 0;

    The output shows that this block of code, combined by optimization, executed 100 times. In one sense this result is correct, because there was only one instruction representing all four of these lines. However, the output does not indicate how many times the result was 0 and how many times the result was 1.

    Inlineable functions can create unexpected line counts. Line counts are shown for the source code of the inlineable function, but what is shown depends on where the function is inlined, or if it is not inlined at all.

    If the function is not inlined, the compiler must emit an out of line copy of the function, in any object file that needs it. If fileA.o and fileB.o both contain out of line bodies of a particular inlineable function, they will also both contain coverage counts for that function. When fileA.o and fileB.o are linked together, the linker will, on many systems, select one of those out of line bodies for all calls to that function, and remove or ignore the other. Unfortunately, it will not remove the coverage counters for the unused function body. Hence when instrumented, all but one use of that function will show zero counts.

    If the function is inlined in several places, the block structure in each location might not be the same. For instance, a condition might now be calculable at compile time in some instances. Because the coverage of all the uses of the inline function will be shown for the same source lines, the line counts themselves might seem inconsistent.

    Long-running applications can use the "__gcov_reset" and "__gcov_dump" facilities to restrict profile collection to the program region of interest. Calling "__gcov_reset(void)" will clear all run-time profile counters to zero, and calling "__gcov_dump(void)" will cause the profile information collected at that point to be dumped to .gcda output files. Instrumented applications use a static destructor with priority 99 to invoke the "__gcov_dump" function. Thus "__gcov_dump" is executed after all user defined static destructors, as well as handlers registered with "atexit".

    If an executable loads a dynamic shared object via dlopen functionality, -Wl,--dynamic-list-data is needed to dump all profile data.

    Profiling run-time library reports various errors related to profile manipulation and profile saving. Errors are printed into standard error output or GCOV_ERROR_FILE file, if environment variable is used. In order to terminate immediately after an errors occurs set GCOV_EXIT_AT_ERROR environment variable. That can help users to find profile clashing which leads to a misleading profile.
