LD(1) Outils de développement GNU LD(1)

NOM

ld - L'éditeur de liens GNU

SYNTAXE

ld [options] fichier-objet ...

DESCRIPTION

ld combine un certain nombre de fichiers objets et d'archives, relocalise leurs données et résout les références de symboles. Habituellement, la dernière étape de la compilation d'un programme est l'exécution de ld.

ld accepte des fichiers de langage de commande d'éditeur de liens écrits dans un sur-ensemble de la syntaxe du langage de commande d'éditeur de liens d'AT&T, afin de fournir un contrôle explicite et total sur le processus d'édition de liens.

Cette page de manuel ne décrit pas le langage de commande ; voir l'entrée ld dans "info" pour les détails complets sur le langage de commande et sur d'autres aspects de l'éditeur de liens GNU.

Cette version de ld utilise les bibliothèques génériques BFD pour opérer sur les fichiers objets. Cela permet à ld de lire, combiner et écrire des fichiers objets dans de nombreux formats différents — par exemple, COFF ou "a.out". Différents formats peuvent être liés ensemble pour produire tout type de fichier objet disponible.

Outre sa flexibilité, l'éditeur de liens GNU est plus utile que les autres éditeurs de liens en fournissant des informations de diagnostic. De nombreux éditeurs de liens abandonnent immédiatement l'exécution lors d'une erreur ; chaque fois que possible, ld continue l'exécution, vous permettant d'identifier d'autres erreurs (ou, dans certains cas, d'obtenir un fichier de sortie malgré l'erreur).

L'éditeur de liens GNU ld est conçu pour couvrir un large éventail de situations et pour être aussi compatible que possible avec les autres éditeurs de liens. Par conséquent, vous avez de nombreux choix pour contrôler son comportement.

OPTIONS

L'éditeur de liens prend en charge une pléthore d'options en ligne de commande, mais en pratique, peu d'entre elles sont utilisées dans un contexte particulier. Par exemple, une utilisation fréquente de ld est de lier des fichiers objets Unix standard sur un système Unix standard et pris en charge. Sur un tel système, pour lier un fichier "hello.o" :

ld -o <sortie> /lib/crt0.o hello.o -lc

Cela indique à ld de produire un fichier appelé sortie comme résultat de la liaison du fichier "/lib/crt0.o" avec "hello.o" et la bibliothèque "libc.a", qui proviendra des répertoires de recherche standard. (Voir la discussion de l'option -l ci-dessous.)

Certaines des options en ligne de commande de ld peuvent être spécifiées à n'importe quel point de la ligne de commande. Cependant, les options qui font référence à des fichiers, telles que -l ou -T, provoquent la lecture du fichier au point où l'option apparaît dans la ligne de commande, par rapport aux fichiers objets et aux autres options de fichier. La répétition d'options non liées à des fichiers avec un argument différent n'aura aucun effet supplémentaire, ou remplacera les occurrences précédentes (celles plus à gauche sur la ligne de commande) de cette option. Les options qui peuvent être spécifiées de manière significative plus d'une fois sont notées dans les descriptions ci-dessous.

Les arguments non-options sont des fichiers objets ou des archives qui doivent être liés ensemble. Ils peuvent suivre, précéder ou être mélangés avec les options de la ligne de commande, à l'exception du fait qu'un argument de fichier objet ne peut pas être placé entre une option et son argument.

Habituellement, l'éditeur de liens est invoqué avec au moins un fichier objet, mais vous pouvez spécifier d'autres formes de fichiers d'entrée binaires en utilisant -l, -R, et le langage de commande de script. Si *aucun* fichier d'entrée binaire n'est spécifié du tout, l'éditeur de liens ne produit aucune sortie et affiche le message No input files.

Si l'éditeur de liens ne parvient pas à reconnaître le format d'un fichier objet, il supposera qu'il s'agit d'un script d'éditeur de liens. Un script spécifié de cette manière augmente le script d'éditeur de liens principal utilisé pour la liaison (soit le script d'éditeur de liens par défaut, soit celui spécifié à l'aide de -T). Cette fonctionnalité permet à l'éditeur de liens de se lier à un fichier qui ressemble à un objet ou à une archive, mais qui ne fait en réalité que définir certaines valeurs de symbole, ou utilise "INPUT" ou "GROUP" pour charger d'autres objets. Spécifier un script de cette manière augmente simplement le script d'éditeur de liens principal, les commandes supplémentaires étant placées après le script principal ; utilisez l'option -T pour remplacer entièrement le script d'éditeur de liens par défaut, mais notez l'effet de la commande "INSERT".

Pour les options dont le nom est une seule lettre, les arguments des options doivent soit suivre la lettre de l'option sans espace blanc intermédiaire, soit être donnés comme arguments séparés immédiatement après l'option qui les requiert.

Pour les options dont le nom est constitué de plusieurs lettres, un seul tiret ou deux peuvent précéder le nom de l'option ; par exemple, -trace-symbol et --trace-symbol sont équivalents. Notez qu'il existe une exception à cette règle. Les options de plusieurs lettres qui commencent par une lettre minuscule 'o' ne peuvent être précédées que de deux tirets. Ceci afin de réduire la confusion avec l'option -o. Ainsi, par exemple, -omagic définit le nom du fichier de sortie sur magic tandis que --omagic définit le drapeau NMAGIC sur la sortie.

Les arguments des options de plusieurs lettres doivent être séparés du nom de l'option par un signe égal, ou être donnés comme arguments séparés immédiatement après l'option qui les requiert. Par exemple, --trace-symbol foo et --trace-symbol=foo sont équivalents. Des abréviations uniques des noms des options de plusieurs lettres sont acceptées.

Notez que si l'éditeur de liens est invoqué indirectement, via un pilote de compilateur (par exemple, gcc), alors toutes les options de la ligne de commande de l'éditeur de liens doivent être précédées de -Wl, (ou ce qui est approprié pour le pilote de compilateur particulier) comme suit :

gcc -Wl,--start-group foo.o bar.o -Wl,--end-group

Ceci est important, car sinon le programme pilote de compilation peut silencieusement ignorer les options de l'éditeur de liens, résultant en une liaison incorrecte. La confusion peut également survenir lors du passage d'options nécessitant des valeurs via un pilote, car l'utilisation d'un espace entre l'option et l'argument agit comme un séparateur, et fait que le pilote transmet uniquement l'option à l'éditeur de liens et l'argument au compilateur. Dans ce cas, il est plus simple d'utiliser les formes jointes des options à une seule lettre et à plusieurs lettres, telles que :

gcc foo.o bar.o -Wl,-eENTRY -Wl,-Map=a.map

Voici une table des commutateurs génériques en ligne de commande acceptés par l'éditeur de liens GNU :

@fichier
Lire les options de la ligne de commande depuis fichier. Les options lues sont insérées à la place de l'option @fichier originale. Si fichier n'existe pas, ou ne peut pas être lu, alors l'option sera traitée littéralement, et non supprimée.

Les options dans fichier sont séparées par des espaces. Un caractère d'espace blanc peut être inclus dans une option en entourant l'option entière avec des guillemets simples ou doubles. Tout caractère (y compris une barre oblique inverse) peut être inclus en faisant précéder le caractère à inclure d'une barre oblique inverse. Le fichier peut lui-même contenir d'autres options @fichier ; toutes ces options seront traitées récursivement.

-a mot-clé
Cette option est prise en charge pour la compatibilité HP/UX. L'argument mot-clé doit être l'une des chaînes archive, shared, ou default. -aarchive est fonctionnellement équivalent à -Bstatic, et les deux autres mots-clés sont fonctionnellement équivalents à -Bdynamic. Cette option peut être utilisée plusieurs fois.
--audit AUDITLIB
Ajoute AUDITLIB à l'entrée "DT_AUDIT" de la section dynamique. AUDITLIB n'est pas vérifiée pour son existence, ni n'utilisera le DT_SONAME spécifié dans la bibliothèque. Si elle est spécifiée plusieurs fois, "DT_AUDIT" contiendra une liste séparée par des deux-points des interfaces d'audit à utiliser. Si l'éditeur de liens trouve un objet avec une entrée d'audit lors de la recherche de bibliothèques partagées, il ajoutera une entrée "DT_DEPAUDIT" correspondante dans le fichier de sortie. Cette option n'est significative que sur les plateformes ELF prenant en charge l'interface rtld-audit.
-b format-entrée
--format=format-entrée
ld peut être configuré pour prendre en charge plus d'un type de fichier objet. Si votre ld est configuré de cette manière, vous pouvez utiliser l'option -b pour spécifier le format binaire pour les fichiers objets qui suivent cette option dans la ligne de commande. Vous pouvez vouloir utiliser cette option si vous liez des fichiers avec un format binaire inhabituel. Vous pouvez aussi utiliser -b pour basculer explicitement les formats (lors de la liaison de fichiers objets de formats différents), en incluant -b format-entrée avant chaque groupe de fichiers objets d'un format particulier.

Le format par défaut est pris de la variable d'environnement "GNUTARGET".

-c fichier-commande-MRI
--mri-script=fichier-commande-MRI
Pour la compatibilité avec les éditeurs de liens produits par MRI, ld accepte des fichiers de script écrits dans un langage de commande alternatif et restreint, décrit dans la section Fichiers de script compatibles MRI de la documentation GNU ld. Introduisez les fichiers de script MRI avec l'option -c ; utilisez l'option -T pour exécuter des scripts d'éditeur de liens écrits dans le langage de script polyvalent de ld. Si fichier-commande-MRI n'existe pas, ld le recherche dans les répertoires spécifiés par toute option -L.
-d
-dc
-dp
Ces trois options sont équivalentes ; plusieurs formes sont supportées pour la compatibilité avec d'autres éditeurs de liens. Elles attribuent de l'espace aux symboles communs même si un fichier de sortie relogeable est spécifié (avec -r). La commande de script "FORCE_COMMON_ALLOCATION" a le même effet.
--depaudit BIBLIO-AUDIT
-P BIBLIO-AUDIT
Ajoute BIBLIO-AUDIT à l'entrée "DT_DEPAUDIT" de la section dynamique. BIBLIO-AUDIT n'est pas vérifiée pour son existence, et n'utilisera pas non plus le DT_SONAME spécifié dans la bibliothèque. Si spécifié plusieurs fois, "DT_DEPAUDIT" contiendra une liste d'interfaces d'audit séparées par des deux-points à utiliser. Cette option n'est significative que sur les plates-formes ELF supportant l'interface rtld-audit. L'option -P est fournie pour la compatibilité Solaris.
--enable-linker-version
Active la directive de script d'éditeur de liens "LINKER_VERSION", décrite dans **Données de la section de sortie**. Si cette directive est utilisée dans un script d'éditeur de liens et que cette option a été activée, alors une chaîne contenant la version de l'éditeur de liens sera insérée au point actuel.

Note - l'emplacement de cette option sur la ligne de commande de l'éditeur de liens est significatif. Elle n'affectera que les scripts d'éditeur de liens qui viennent après elle sur la ligne de commande, ou qui sont intégrés dans l'éditeur de liens.

--disable-linker-version
Désactive la directive de script d'éditeur de liens "LINKER_VERSION", de sorte qu'elle n'insère pas de chaîne de version. C'est le comportement par défaut.
--enable-non-contiguous-regions
Cette option évite de générer une erreur si une section d'entrée ne correspond pas à une section de sortie correspondante. L'éditeur de liens tente d'allouer la section d'entrée aux sections de sortie correspondantes ultérieures, et ne génère une erreur que si aucune section de sortie n'est suffisamment grande. Ceci est utile lorsque plusieurs régions de mémoire non contiguës sont disponibles et que la section d'entrée ne nécessite pas une région particulière. L'ordre d'évaluation des sections d'entrée ne change pas, par exemple : 
MEMORY {
  MEM1 (rwx) : ORIGIN = 0x1000, LENGTH = 0x14
  MEM2 (rwx) : ORIGIN = 0x1000, LENGTH = 0x40
  MEM3 (rwx) : ORIGIN = 0x2000, LENGTH = 0x40
}
SECTIONS {
  mem1 : { *(.data.*); } > MEM1
  mem2 : { *(.data.*); } > MEM2
  mem3 : { *(.data.*); } > MEM3
}

avec les sections d'entrée :
.data.1: taille 8
.data.2: taille 0x10
.data.3: taille 4

résulte en .data.1 affecté à mem1, et .data.2 et .data.3
affectés à mem2, même si .data.3 pourrait tenir dans mem3.

Cette option est incompatible avec les instructions INSERT car elle modifie la manière dont les sections d'entrée sont mappées aux sections de sortie.

--enable-non-contiguous-regions-warnings
Cette option active les avertissements lorsque "--enable-non-contiguous-regions" permet des correspondances potentiellement inattendues dans le mappage des sections, conduisant potentiellement à ignorer silencieusement une section au lieu d'échouer parce qu'elle ne rentre dans aucune région de sortie.
-e point-entrée
--entry=point-entrée
Utilise point-entrée comme symbole explicite pour commencer l'exécution de votre programme, plutôt que le point d'entrée par défaut. S'il n'y a pas de symbole nommé point-entrée, l'éditeur de liens essaiera d'analyser point-entrée comme un nombre, et l'utilisera comme adresse d'entrée (le nombre sera interprété en base 10 ; vous pouvez utiliser un préfixe 0x pour la base 16, ou un préfixe 0 pour la base 8).
--exclude-libs bib,bib,...
Spécifie une liste de bibliothèques d'archives à partir desquelles les symboles ne doivent pas être automatiquement exportés. Les noms de bibliothèques peuvent être délimités par des virgules ou des deux-points. Spécifier "--exclude-libs ALL" exclut les symboles de toutes les bibliothèques d'archives de l'exportation automatique. Cette option n'est disponible que pour le port cible i386 PE de l'éditeur de liens et pour les ports cibles ELF. Pour i386 PE, les symboles listés explicitement dans un fichier .def sont toujours exportés, quelle que soit cette option. Pour les ports cibles ELF, les symboles affectés par cette option seront traités comme cachés.
--exclude-modules-for-implib module,module,...
Spécifie une liste de fichiers objets ou de membres d'archive, à partir desquels les symboles ne doivent pas être automatiquement exportés, mais qui doivent être copiés tels quels dans la bibliothèque d'importation générée pendant la liaison. Les noms de modules peuvent être délimités par des virgules ou des deux-points, et doivent correspondre exactement aux noms de fichiers utilisés par ld pour ouvrir les fichiers ; pour les membres d'archive, il s'agit simplement du nom du membre, mais pour les fichiers objets, le nom listé doit inclure et correspondre précisément à tout chemin utilisé pour spécifier le fichier d'entrée sur la ligne de commande de l'éditeur de liens. Cette option n'est disponible que pour le port cible i386 PE de l'éditeur de liens. Les symboles listés explicitement dans un fichier .def sont toujours exportés, quelle que soit cette option.
-E
--export-dynamic
--no-export-dynamic
Lors de la création d'un exécutable lié dynamiquement, l'utilisation de l'option -E ou de l'option --export-dynamic fait que l'éditeur de liens ajoute tous les symboles à la table des symboles dynamiques. La table des symboles dynamiques est l'ensemble des symboles qui sont visibles depuis les objets dynamiques à l'exécution.

Si vous n'utilisez aucune de ces options (ou utilisez l'option --no-export-dynamic pour rétablir le comportement par défaut), la table des symboles dynamiques contiendra normalement uniquement les symboles qui sont référencés par un objet dynamique mentionné dans la liaison.

Si vous utilisez "dlopen" pour charger un objet dynamique qui doit référencer les symboles définis par le programme, plutôt qu'un autre objet dynamique, alors vous aurez probablement besoin d'utiliser cette option lors de la liaison du programme lui-même.

Vous pouvez aussi utiliser la liste dynamique pour contrôler quels symboles doivent être ajoutés à la table des symboles dynamiques si le format de sortie le supporte. Voir la description de --dynamic-list.

Notez que cette option est spécifique aux ports cibles ELF. Les cibles PE supportent une fonction similaire pour exporter tous les symboles d'une DLL ou d'un EXE ; voir la description de --export-all-symbols ci-dessous.

--export-dynamic-symbol=glob
Lors de la création d'un exécutable lié dynamiquement, les symboles correspondant à glob seront ajoutés à la table des symboles dynamiques. Lors de la création d'une bibliothèque partagée, les références aux symboles correspondant à glob ne seront pas liées aux définitions contenues dans la bibliothèque partagée. Cette option est ignorée lors de la création d'une bibliothèque partagée et si -Bsymbolic ou --dynamic-list ne sont pas spécifiés. Cette option n'est significative que sur les plates-formes ELF supportant les bibliothèques partagées.
--export-dynamic-symbol-list=fichier
Spécifie un --export-dynamic-symbol pour chaque modèle dans le fichier. Le format du fichier est le même que le nœud de version sans portée ni nom de nœud. Voir VERSION pour plus d'informations.
-EB
Lier des objets big-endian. Ceci affecte le format de sortie par défaut.
-EL
Lier des objets little-endian. Ceci affecte le format de sortie par défaut.
-f nom
--auxiliary=nom
Lors de la création d'un objet partagé ELF, définit le champ interne DT_AUXILIARY sur le nom spécifié. Ceci indique à l'éditeur de liens dynamique que la table des symboles de l'objet partagé doit être utilisée comme filtre auxiliaire sur la table des symboles de l'objet partagé nom.

Si vous liez plus tard un programme contre cet objet filtre, alors, lorsque vous exécutez le programme, l'éditeur de liens dynamique verra le champ DT_AUXILIARY. Si l'éditeur de liens dynamique résout des symboles depuis l'objet filtre, il vérifiera d'abord s'il existe une définition dans l'objet partagé nom. S'il y en a une, elle sera utilisée à la place de la définition dans l'objet filtre. L'objet partagé nom n'a pas besoin d'exister. Ainsi, l'objet partagé nom peut être utilisé pour fournir une implémentation alternative de certaines fonctions, peut-être pour le débogage ou pour des performances spécifiques à la machine.

Cette option peut être spécifiée plus d'une fois. Les entrées DT_AUXILIARY seront créées dans l'ordre où elles apparaissent sur la ligne de commande.

-F nom
Si vous liez ultérieurement un programme à cet objet filtre, alors, lors de l'exécution du programme, l'éditeur de liens dynamique verra le champ DT_FILTER. L'éditeur de liens dynamique résoudra les symboles conformément à la table des symboles de l'objet filtre comme d'habitude, mais il se liera en fait aux définitions trouvées dans l'objet partagé name. Ainsi, l'objet filtre peut être utilisé pour sélectionner un sous-ensemble des symboles fournis par l'objet name.

Certains éditeurs de liens plus anciens utilisaient l'option -F tout au long d'une chaîne d'outils de compilation pour spécifier le format du fichier objet pour les fichiers objets d'entrée et de sortie. L'éditeur de liens GNU utilise d'autres mécanismes à cette fin : les options -b, --format, --oformat, la commande "TARGET" dans les scripts d'édition de liens, et la variable d'environnement "GNUTARGET". L'éditeur de liens GNU ignorera l'option -F lorsqu'il ne créera pas d'objet partagé ELF.

-fini=name
Lors de la création d'un exécutable ou d'un objet partagé ELF, appelle NAME lorsque l'exécutable ou l'objet partagé est déchargé, en définissant DT_FINI à l'adresse de la fonction. Par défaut, l'éditeur de liens utilise "_fini" comme fonction à appeler.
-g
Ignoré. Fourni pour la compatibilité avec d'autres outils.
-G valeur
--gpsize=valeur
Définit la taille maximale des objets à optimiser à l'aide du registre GP à taille. Ceci n'est significatif que pour les formats de fichiers objets tels que MIPS ELF qui prennent en charge la mise en place d'objets volumineux et petits dans des sections différentes. Ceci est ignoré pour les autres formats de fichiers objets.
-h name
-soname=name
Lors de la création d'un objet partagé ELF, définit le champ interne DT_SONAME sur le nom spécifié. Lorsqu'un exécutable est lié à un objet partagé qui possède un champ DT_SONAME, alors lors de l'exécution de l'exécutable, l'éditeur de liens dynamique tentera de charger l'objet partagé spécifié par le champ DT_SONAME plutôt que d'utiliser le nom de fichier donné à l'éditeur de liens.
-i
Effectue une liaison incrémentale (identique à l'option -r).
-init=name
Lors de la création d'un exécutable ou d'un objet partagé ELF, appelle NAME lorsque l'exécutable ou l'objet partagé est chargé, en définissant DT_INIT à l'adresse de la fonction. Par défaut, l'éditeur de liens utilise "_init" comme fonction à appeler.
-l namespec
--library=namespec
Ajoute l'archive ou le fichier objet spécifié par namespec à la liste des fichiers à lier. Cette option peut être utilisée un nombre quelconque de fois. Si namespec est de la forme :filename, ld recherchera dans le chemin de la bibliothèque un fichier nommé filename, sinon il recherchera dans le chemin de la bibliothèque un fichier nommé libnamespec.a.

Sur les systèmes qui prennent en charge les bibliothèques partagées, ld peut également rechercher des fichiers autres que libnamespec.a. Plus précisément, sur les systèmes ELF et SunOS, ld recherchera dans un répertoire une bibliothèque nommée libnamespec.so avant d'en rechercher une nommée libnamespec.a. (Par convention, une extension ".so" indique une bibliothèque partagée.) Notez que ce comportement ne s'applique pas à :filename, qui spécifie toujours un fichier nommé filename.

L'éditeur de liens recherchera dans une archive une seule fois, à l'emplacement où elle est spécifiée sur la ligne de commande. Si l'archive définit un symbole qui était indéfini dans un objet apparu avant l'archive sur la ligne de commande, l'éditeur de liens inclura les fichiers appropriés de l'archive. Cependant, un symbole indéfini dans un objet apparaissant plus tard sur la ligne de commande ne fera pas rechercher l'archive à nouveau par l'éditeur de liens.

Voir l'option -( pour une façon de forcer l'éditeur de liens à rechercher les archives plusieurs fois.

Vous pouvez lister la même archive plusieurs fois sur la ligne de commande.

Ce type de recherche d'archives est standard pour les éditeurs de liens Unix. Cependant, si vous utilisez ld sur AIX, notez qu'il diffère du comportement de l'éditeur de liens AIX.

-L searchdir
--library-path=searchdir
Ajoute le chemin searchdir à la liste des chemins que ld recherchera pour les bibliothèques d'archives et les scripts de contrôle ld. Vous pouvez utiliser cette option un nombre quelconque de fois. Les répertoires sont recherchés dans l'ordre où ils sont spécifiés sur la ligne de commande. Les répertoires spécifiés sur la ligne de commande sont recherchés avant les répertoires par défaut. Toutes les options -L s'appliquent à toutes les options -l, indépendamment de l'ordre dans lequel les options apparaissent. Les options -L n'affectent pas la façon dont ld recherche un script d'édition de liens, sauf si l'option -T est spécifiée.

Si searchdir commence par "=" ou $SYSROOT, alors ce préfixe sera remplacé par le préfixe sysroot, contrôlé par l'option --sysroot, ou spécifié lors de la configuration de l'éditeur de liens.

L'ensemble par défaut des chemins recherchés (sans être spécifiés avec -L) dépend du mode d'émulation que ld utilise, et dans certains cas également de la façon dont il a été configuré.

Les chemins peuvent également être spécifiés dans un script de liaison avec la commande "SEARCH_DIR". Les répertoires spécifiés de cette manière sont recherchés au point où le script de liaison apparaît sur la ligne de commande.

-m emulation
Émule l'éditeur de liens emulation. Vous pouvez lister les émulations disponibles avec les options --verbose ou -V.

Si l'option -m n'est pas utilisée, l'émulation est prise de la variable d'environnement "LDEMULATION", si celle-ci est définie.

Sinon, l'émulation par défaut dépend de la façon dont l'éditeur de liens a été configuré.

--remap-inputs=pattern=filename
--remap-inputs-file=file
Ces options permettent de modifier les noms des fichiers d'entrée avant que l'éditeur de liens ne tente de les ouvrir. L'option --remap-inputs=foo.o=bar.o entraînera la tentative de chargement d'un fichier nommé bar.o pour toute tentative de chargement d'un fichier nommé foo.o. Les motifs génériques sont autorisés dans le premier nom de fichier, ainsi --remap-inputs=foo*.o=bar.o renommera tout fichier d'entrée correspondant à foo*.o en bar.o.

Une forme alternative de l'option --remap-inputs-file=filename permet de lire les remappages à partir d'un fichier. Chaque ligne du fichier peut contenir un seul remappage. Les lignes vides sont ignorées. Tout ce qui commence par un caractère dièse (#) jusqu'à la fin d'une ligne est considéré comme un commentaire et est également ignoré. Le motif de remappage peut être séparé du nom de fichier par un espace blanc ou un signe égal (=).

Les options peuvent être spécifiées plusieurs fois. Leurs contenus s'accumulent. Les remappages seront traités dans l'ordre où ils apparaissent sur la ligne de commande, et s'ils proviennent d'un fichier, dans l'ordre où ils apparaissent dans le fichier. Si une correspondance est trouvée, aucune vérification supplémentaire pour ce nom de fichier ne sera effectuée.

Si le nom de fichier de remplacement est /dev/null ou simplement NUL, le remappage entraînera effectivement l'ignorance du fichier d'entrée. Cela peut être un moyen pratique d'expérimenter le retrait de fichiers d'entrée d'un environnement de construction complexe.

Notez que cette option dépend de la position et n'affecte que les noms de fichiers qui la suivent sur la ligne de commande. Ainsi :

ld foo.o --remap-inputs=foo.o=bar.o

N'aura aucun effet, alors que :

ld --remap-inputs=foo.o=bar.o foo.o

Renommera le fichier d'entrée foo.o en bar.o.

Notez que ces options affectent également les fichiers référencés par les instructions INPUT dans les scripts d'édition de liens. Mais comme les scripts d'édition de liens sont traités après la lecture complète de la ligne de commande, la position des options de remappage sur la ligne de commande n'est pas significative.

Si l'option verbose est activée, alors les remappages qui correspondent seront signalés, bien que là encore, l'option verbose doive être activée sur la ligne de commande *avant* que les noms de fichiers remappés n'apparaissent.

Si les options -Map ou --print-map sont activées, alors la liste des remappages sera incluse dans la sortie de la carte.

-M
--print-map
Imprime une carte de liaison sur la sortie standard. Une carte de liaison fournit des informations sur la liaison, notamment :
  • Où les fichiers objets sont mappés en mémoire.
  • Comment les symboles communs sont alloués.
  • Tous les membres d'archive inclus dans la liaison, avec mention du symbole qui a causé l'inclusion du membre d'archive.
  • Les valeurs attribuées aux symboles.

    Notez que les symboles dont les valeurs sont calculées par une expression impliquant une référence à une valeur précédente du même symbole peuvent ne pas avoir le résultat correct affiché dans la carte de liaison. En effet, l'éditeur de liens supprime les résultats intermédiaires et ne conserve que la valeur finale d'une expression. Dans de telles circonstances, l'éditeur de liens affichera la valeur finale entourée de crochets. Ainsi, par exemple, un script d'édition de liens contenant :

    foo = 1
foo = foo * 4
foo = foo + 8

    produira la sortie suivante dans la carte de liaison si l'option -M est utilisée :

    0x00000001                foo = 0x1
[0x0000000c]                foo = (foo * 0x4)
[0x0000000c]                foo = (foo + 0x8)

    Voir Expressions pour

plus d'informations sur les expressions dans les scripts d'édition de liens.

  • Comment les propriétés GNU sont fusionnées.

    Lorsque l'éditeur de liens fusionne les sections .note.gnu.property d'entrée en une seule section .note.gnu.property de sortie, certaines propriétés sont supprimées ou mises à jour. Ces actions sont signalées dans la carte d'édition de liens. Par exemple :

    Propriété supprimée 0xc0000002 pour fusionner foo.o (0x1) et bar.o (non trouvé)

    Cela indique que la propriété 0xc0000002 est supprimée de la sortie lors de la fusion des propriétés dans foo.o, dont la valeur de la propriété 0xc0000002 est 0x1, et bar.o, qui n'a pas la propriété 0xc0000002.

    Propriété mise à jour 0xc0010001 (0x1) pour fusionner foo.o (0x1) et bar.o (0x1)

    Cela indique que la valeur de la propriété 0xc0010001 est mise à jour à 0x1 en sortie lors de la fusion des propriétés dans foo.o, dont la valeur de la propriété 0xc0010001 est 0x1, et bar.o, dont la valeur de la propriété 0xc0010001 est 0x1.

  • Sur certaines cibles ELF, une liste de corrections insérées par --relax 
    foo.o : Ajustement du saut à 0x00000008 vers "far" dans la section .text

    Cela indique que le saut à 0x00000008 dans foo.o, ciblant le symbole "far" dans la section .text, a été remplacé par un trampoline.

    --nmagic
    Désactiver l'alignement des sections sur les pages et désactiver l'édition de liens avec des bibliothèques partagées. Si le format de sortie prend en charge les nombres magiques de style Unix, marquer la sortie comme "NMAGIC".
    -N
    --omagic
    Définir les sections de texte et de données comme lisibles et inscriptibles. De plus, ne pas aligner sur page le segment de données et désactiver l'édition de liens avec des bibliothèques partagées.     --output=sortie
    Utiliser sortie comme nom pour le programme produit par ld ; si cette option n'est pas spécifiée, le nom a.out est utilisé par défaut. La commande de script "OUTPUT" peut également spécifier le nom du fichier de sortie.
    --dependency-file=depfile
    Écrire un fichier de dépendance dans depfile. Ce fichier contient une règle adaptée à "make" décrivant le fichier de sortie et tous les fichiers d'entrée qui ont été lus pour le produire. La sortie est similaire à la sortie du compilateur avec -M -MP. Notez qu'il n'y a pas d'option comme le -MM du compilateur pour exclure les "fichiers système" (ce qui n'est pas un concept bien défini dans l'éditeur de liens, contrairement aux "en-têtes système" dans le compilateur). Ainsi, la sortie de --dependency-file est toujours spécifique à l'état exact de l'installation où elle a été produite, et ne doit pas être copiée dans des makefiles distribués sans édition minutieuse.
    -O niveau
    Si niveau est une valeur numérique supérieure à zéro, ld optimise la sortie. Cela peut prendre beaucoup plus de temps et devrait donc probablement n'être activé que pour le binaire final. Actuellement, cette option n'affecte que la génération de bibliothèques partagées ELF. Les futures versions de l'éditeur de liens pourront utiliser davantage cette option. De plus, il n'y a actuellement aucune différence dans le comportement de l'éditeur de liens pour différentes valeurs non nulles de cette option. Encore une fois, cela peut changer avec les futures versions.
    -plugin nom
    Impliquer un plugin dans le processus d'édition de liens. Le paramètre nom est le nom de fichier absolu du plugin. Habituellement, ce paramètre est automatiquement ajouté par le compilateur lors de l'utilisation de l'optimisation au moment de l'édition de liens, mais les utilisateurs peuvent également ajouter leurs propres plugins s'ils le souhaitent.

    Notez que l'emplacement des plugins d'origine du compilateur est différent de l'endroit où les programmes ar, nm et ranlib recherchent leurs plugins. Pour que ces commandes utilisent un plugin basé sur le compilateur, il doit d'abord être copié dans le répertoire ${libdir}/bfd-plugins. Tous les plugins d'édition de liens basés sur gcc sont rétrocompatibles, il suffit donc de copier le plus récent.

    --push-state
    L'option --push-state permet de préserver l'état actuel des drapeaux qui régissent la gestion des fichiers d'entrée afin qu'ils puissent tous être restaurés avec une option --pop-state correspondante.

    Les options couvertes sont : -Bdynamic, -Bstatic, -dn, -dy, -call_shared, -non_shared, -static, -N, -n, --whole-archive, --no-whole-archive, -r, -Ur, --copy-dt-needed-entries, --no-copy-dt-needed-entries, --as-needed, --no-as-needed, et -a.

    Une cible pour cette option sont les spécifications pour pkg-config. Lorsqu'elle est utilisée avec l'option --libs, toutes les bibliothèques potentiellement nécessaires sont listées puis éventuellement liées en permanence. Il est préférable de retourner quelque chose comme suit :

    -Wl,--push-state,--as-needed -libone -libtwo -Wl,--pop-state
    --pop-state
    Annule l'effet de --push-state, restaure les valeurs précédentes des drapeaux régissant la gestion des fichiers d'entrée.
    -q
    --emit-relocs
    Laisser les sections de relocations et leurs contenus dans les exécutables entièrement liés. Les outils d'analyse et d'optimisation post-édition de liens peuvent avoir besoin de ces informations pour effectuer des modifications correctes des exécutables. Cela entraîne des exécutables plus volumineux.

    Cette option n'est actuellement prise en charge que sur les plateformes ELF.

    --force-dynamic
    Forcer le fichier de sortie à avoir des sections dynamiques. Cette option est spécifique aux cibles VxWorks.
    -r
    --relocatable
    Générer une sortie déplaçable --- c'est-à-dire, générer un fichier de sortie qui peut à son tour servir d'entrée à ld. Ceci est souvent appelé édition de liens partielle. En tant qu'effet secondaire, dans les environnements qui prennent en charge les nombres magiques Unix standard, cette option définit également le nombre magique du fichier de sortie sur "OMAGIC". Si cette option n'est pas spécifiée, un fichier absolu est produit. Lors de l'édition de liens de programmes C++, cette option ne résoudra pas les références aux constructeurs ; pour ce faire, utilisez -Ur.

    Lorsqu'un fichier d'entrée n'a pas le même format que le fichier de sortie, l'édition de liens partielle n'est prise en charge que si ce fichier d'entrée ne contient aucune relocation. Différents formats de sortie peuvent avoir des restrictions supplémentaires ; par exemple, certains formats basés sur "a.out" ne prennent pas du tout en charge l'édition de liens partielle avec des fichiers d'entrée dans d'autres formats.

    Cette option fait la même chose que -i.

    -R nomfichier
    --just-symbols=nomfichier
    Lire les noms de symboles et leurs adresses à partir de nomfichier, mais ne pas les déplacer ni les inclure dans la sortie. Cela permet à votre fichier de sortie de faire référence symboliquement à des emplacements absolus de mémoire définis dans d'autres programmes. Vous pouvez utiliser cette option plusieurs fois.

    Pour assurer la compatibilité avec d'autres éditeurs de liens ELF, si l'option -R est suivie d'un nom de répertoire, plutôt que d'un nom de fichier, elle est traitée comme l'option -rpath.

    -s
    --strip-all
    Omettre toutes les informations de symboles du fichier de sortie.
    -S
    --strip-debug
    Omettre les informations de symboles du débogueur (mais pas tous les symboles) du fichier de sortie.
    --strip-discarded
    --no-strip-discarded
    Omettre (ou ne pas omettre) les symboles globaux définis dans les sections supprimées. Activé par défaut.
    -t
    --trace
    Imprimer les noms des fichiers d'entrée tels que ld les traite. Si -t est donné deux fois, les membres des archives sont également imprimés. La sortie de -t est utile pour générer une liste de tous les fichiers objets et scripts impliqués dans l'édition de liens, par exemple, lors de l'empaquetage de fichiers pour un rapport de bug d'éditeur de liens.
    -T fichier_script
    --script=fichier_script
    Utiliser fichier_script comme script d'édition de liens. Ce script remplace le script d'édition de liens par défaut de ld (plutôt que de s'y ajouter), sauf si le script contient "INSERT", donc fichier_commande doit spécifier tout ce qui est nécessaire pour describe la description du fichier de sortie. Si scriptfile n'existe pas dans le répertoire courant, "ld" le cherche dans les répertoires spécifiés par les options -L précédentes. Les options -T multiples s'accumulent.
    -dT scriptfile
    --default-script=scriptfile
    Utilise scriptfile comme script de liaison par défaut.

    Cette option est similaire à l'option --script, à la différence près que le traitement du script est retardé jusqu'à ce que le reste de la ligne de commande ait été traité. Cela permet aux options placées après l'option --default-script sur la ligne de commande d'affecter le comportement du script de liaison, ce qui peut être important lorsque la ligne de commande de liaison ne peut pas être contrôlée directement par l'utilisateur. (par exemple, parce que la ligne de commande est construite par un autre outil, tel que gcc).

    -u symbole
    --undefined=symbole
    Force symbole à être entré dans le fichier de sortie comme un symbole non défini. Faire cela peut, par exemple, déclencher la liaison de modules supplémentaires à partir des bibliothèques standard. -u peut être répété avec différents arguments d'option pour entrer des symboles non définis supplémentaires. Cette option est équivalente à la commande de script de liaison "EXTERN".

    Si cette option est utilisée pour forcer l'inclusion de modules supplémentaires dans la liaison, et s'il est erroné que le symbole reste non défini, alors l'option --require-defined doit être utilisée à la place.

    --require-defined=symbole
    Exige que symbole soit défini dans le fichier de sortie. Cette option est identique à l'option --undefined, à la différence près que si symbole n'est pas défini dans le fichier de sortie, l'éditeur de liens émettra une erreur et se terminera. Le même effet peut être obtenu dans un script de liaison en utilisant "EXTERN", "ASSERT" et "DEFINED" ensemble. Cette option peut être utilisée plusieurs fois pour exiger des symboles supplémentaires.
    -Ur
    Pour les programmes qui n'utilisent pas de constructeurs ou de destructeurs, ou pour les systèmes basés sur ELF, cette option est équivalente à -r : elle génère une sortie relocalisable, c'est-à-dire un fichier de sortie qui peut à son tour servir d'entrée à ld. Pour d'autres binaires cependant, l'option -Ur est similaire à -r mais elle résout également les références aux constructeurs et destructeurs.

    Pour les systèmes où -r et -Ur se comportent différemment, il ne fonctionne pas d'utiliser -Ur sur des fichiers qui ont eux-mêmes été liés avec -Ur ; une fois la table des constructeurs construite, elle ne peut plus être complétée. Utilisez -Ur uniquement pour la dernière liaison partielle, et -r pour les autres.

    --orphan-handling=MODE
    Contrôle la manière dont les sections orphelines sont traitées. Une section orpheline est une section qui n'est pas mentionnée spécifiquement dans un script de liaison.

    MODE peut prendre l'une des valeurs suivantes :

    "place"
    Les sections orphelines sont placées dans une section de sortie appropriée selon la stratégie décrite dans Orphan Sections. L'option --unique affecte également la manière dont les sections sont placées.
    "discard"
    Toutes les sections orphelines sont ignorées, en les plaçant dans la section /DISCARD/.
    "warn"
    L'éditeur de liens placera la section orpheline comme pour "place" et émettra également un avertissement.
    "error"
    L'éditeur de liens se terminera avec une erreur si une section orpheline est trouvée.

    La valeur par défaut si --orphan-handling n'est pas donnée est "place".

    --unique[=SECTION]
    Crée une section de sortie séparée pour chaque section d'entrée correspondant à SECTION, ou si l'argument générique optionnel SECTION est manquant, pour chaque section d'entrée orpheline. Une section orpheline est une section qui n'est pas mentionnée spécifiquement dans un script de liaison. Vous pouvez utiliser cette option plusieurs fois sur la ligne de commande ; elle empêche la fusion normale des sections d'entrée portant le même nom, remplaçant les affectations de section de sortie dans un script de liaison.

    --as-needed
    --no-as-needed
    This option affects ELF DT_NEEDED tags for dynamic libraries mentioned on the command line after the --as-needed option. Normally the linker will add a DT_NEEDED tag for each dynamic library mentioned on the command line, regardless of whether the library is actually needed or not. --as-needed causes a DT_NEEDED tag to only be emitted for a library that at that point in the link satisfies a non-weak undefined symbol reference from a regular object file or, if the library is not found in the DT_NEEDED lists of other needed libraries, a non-weak undefined symbol reference from another needed dynamic library. Object files or libraries appearing on the command line after the library in question do not affect whether the library is seen as needed. This is similar to the rules for extraction of object files from archives. --no-as-needed restores the default behaviour.

    Note: On Linux based systems the --as-needed option also has an affect on the behaviour of the --rpath and --rpath-link options. See the description of --rpath-link for more details.

    --no-add-needed
    These two options have been deprecated because of the similarity of their names to the --as-needed and --no-as-needed options. They have been replaced by --copy-dt-needed-entries and --no-copy-dt-needed-entries.
    -assert keyword
    This option is ignored for SunOS compatibility.
    -Bdynamic
    -dy
    -call_shared
    Link against dynamic libraries. This is only meaningful on platforms for which shared libraries are supported. This option is normally the default on such platforms. The different variants of this option are for compatibility with various systems. You may use this option multiple times on the command line: it affects library searching for -l options which follow it.
    -Bgroup
    Set the "DF_1_GROUP" flag in the "DT_FLAGS_1" entry in the dynamic section. This causes the runtime linker to handle lookups in this object and its dependencies to be performed only inside the group. --unresolved-symbols=report-all is implied. This option is only meaningful on ELF platforms which support shared libraries.
    -Bstatic
    -dn
    -non_shared
    -static
    Do not link against shared libraries. This is only meaningful on platforms for which shared libraries are supported. The different variants of this option are for compatibility with various systems. You may use this option multiple times on the command line: it affects library searching for -l options which follow it. This option also implies --unresolved-symbols=report-all. This option can be used with -shared. Doing so means that a shared library is being created but that all of the library's external references must be resolved by pulling in entries from static libraries.
    -Bsymbolic
    When creating a shared library, bind references to global symbols to the definition within the shared library, if any. Normally, it is possible for a program linked against a shared library to override the definition within the shared library.
    Cette option n'est significative que sur les plateformes ELF qui prennent en charge les bibliothèques partagées.
    -Bsymbolic-functions
    Lors de la création d'une bibliothèque partagée, lier les références aux symboles de fonction globaux à la définition dans la bibliothèque partagée, le cas échéant. Cette option n'est significative que sur les plateformes ELF qui prennent en charge les bibliothèques partagées.
    -Bno-symbolic
    Cette option peut annuler les options -Bsymbolic et -Bsymbolic-functions précédemment spécifiées.
    --dynamic-list=fichier-liste-dynamique
    Spécifie le nom d'un fichier de liste dynamique à l'éditeur de liens. Ceci est généralement utilisé lors de la création de bibliothèques partagées pour spécifier une liste de symboles globaux dont les références ne doivent pas être liées à la définition dans la bibliothèque partagée, ou lors de la création d'exécutables liés dynamiquement pour spécifier une liste de symboles qui doivent être ajoutés à la table des symboles dans l'exécutable. Cette option n'est significative que sur les plateformes ELF qui prennent en charge les bibliothèques partagées.

    Le format de la liste dynamique est le même que le nœud de version sans portée ni nom de nœud. Voir VERSION pour plus d'informations.

    --dynamic-list-data
    Inclut tous les symboles de données globaux dans la liste dynamique.
    --dynamic-list-cpp-new
    Fournit la liste dynamique intégrée pour les opérateurs new et delete de C++. C'est principalement utile pour la construction de la bibliothèque partagée libstdc++.
    --dynamic-list-cpp-typeinfo
    Fournit la liste dynamique intégrée pour l'identification des types d'exécution C++.
    --check-sections
    --no-check-sections
    Demande à l'éditeur de liens de *ne pas* vérifier les adresses des sections après qu'elles ont été attribuées pour voir s'il y a des chevauchements. Normalement, l'éditeur de liens effectuera cette vérification, et s'il trouve des chevauchements, il produira des messages d'erreur appropriés. L'éditeur de liens connaît les sections dans les overlays et en tient compte. Le comportement par défaut peut être restauré en utilisant le commutateur de ligne de commande --check-sections. Les chevauchements de sections ne sont généralement pas vérifiés pour les liens déplaçables. Vous pouvez forcer la vérification dans ce cas en utilisant l'option --check-sections.
    --copy-dt-needed-entries
    --no-copy-dt-needed-entries
    Cette option affecte le traitement des bibliothèques dynamiques référencées par les balises DT_NEEDED *à l'intérieur* des bibliothèques dynamiques ELF mentionnées sur la ligne de commande. Normalement, l'éditeur de liens n'ajoutera pas de balise DT_NEEDED au binaire de sortie pour chaque bibliothèque mentionnée dans une balise DT_NEEDED d'une bibliothèque dynamique d'entrée. Cependant, avec --copy-dt-needed-entries spécifié sur la ligne de commande, les entrées DT_NEEDED des bibliothèques dynamiques qui le suivent seront ajoutées. Le comportement par défaut peut être restauré avec --no-copy-dt-needed-entries.

    Cette option a également un effet sur la résolution des symboles dans les bibliothèques dynamiques. Avec --copy-dt-needed-entries, les bibliothèques dynamiques mentionnées sur la ligne de commande seront recherchées récursivement, en suivant leurs balises DT_NEEDED vers d'autres bibliothèques, afin de résoudre les symboles requis par le binaire de sortie. Avec le réglage par défaut, cependant, la recherche des bibliothèques dynamiques qui le suivent s'arrêtera avec la bibliothèque dynamique elle-même. Aucun lien DT_NEEDED ne sera parcouru pour résoudre les symboles.

    --cref
    Produit une table de références croisées. Si un fichier de carte de l'éditeur de liens est généré, la table de références croisées est imprimée dans le fichier de carte. Sinon, elle est imprimée sur la sortie standard.

    Le format de la table est intentionnellement simple, de sorte qu'il puisse être facilement traité par un script si nécessaire. Les symboles sont imprimés, triés par nom. Pour chaque symbole, une liste de noms de fichiers est donnée. Si le symbole est défini, le premier fichier listé est l'emplacement de la définition. Si le symbole est défini comme une valeur commune, alors tous les fichiers où cela se produit apparaissent ensuite. Enfin, tous les fichiers qui référencent le symbole sont listés.

    --ctf-variables
    --no-ctf-variables
    Le format d'informations de débogage CTF prend en charge une section qui encode les noms et les types des variables trouvées dans le programme qui n'apparaissent dans aucune table de symboles. Ces variables ne peuvent clairement pas être recherchées par adresse par les débogueurs conventionnels, donc l'espace utilisé pour leurs types et noms est généralement gaspillé : les types sont généralement petits mais les noms ne le sont souvent pas. --ctf-variables provoque la génération d'une telle section. Le comportement par défaut peut être restauré avec --no-ctf-variables.
    --ctf-share-types=méthode
    Ajuste la méthode utilisée pour partager les types entre les unités de traduction en CTF.
    share-unconflicted
    Place tous les types qui n'ont pas de définitions ambiguës dans le dictionnaire partagé, où les débogueurs peuvent y accéder facilement, même s'ils n'apparaissent que dans une seule unité de traduction. C'est le comportement par défaut.
    share-duplicated
    Place uniquement les types qui apparaissent dans plusieurs unités de traduction dans le dictionnaire partagé : les types avec une seule définition vont dans des dictionnaires par unité de traduction. Les types avec des définitions ambiguës dans plusieurs unités de traduction vont toujours dans des dictionnaires par unité de traduction. Cela a tendance à rendre le CTF plus volumineux, mais peut réduire la quantité de CTF dans le dictionnaire partagé. Pour les très grands projets, cela peut accélérer l'ouverture du CTF et économiser de la mémoire dans le consommateur CTF à l'exécution.
    --no-define-common
    Cette option empêche l'attribution d'adresses aux symboles communs. La commande de script "INHIBIT_COMMON_ALLOCATION" a le même effet.

    L'option --no-define-common permet de découpler la décision d'attribuer des adresses aux symboles communs du choix du type de fichier de sortie ; sinon, un type de sortie non déplaçable force l'attribution d'adresses aux symboles communs. L'utilisation de --no-define-common permet aux symboles communs référencés depuis une bibliothèque partagée d'être attribués à des adresses uniquement dans le programme principal. Cela élimine l'espace dupliqué inutilisé dans la bibliothèque partagée, et empêche également toute confusion potentielle sur la résolution vers le mauvais duplicata lorsqu'il existe de nombreux modules dynamiques avec des chemins de recherche spécialisés pour la résolution des symboles à l'exécution.

    --force-group-allocation
    Cette option oblige l'éditeur de liens à placer les membres de groupes de sections comme des sections d'entrée normales et à supprimer les groupes de sections. C'est le comportement par défaut pour un lien final, mais cette option peut être utilisée pour modifier le comportement d'un lien déplaçable (-r). La commande de script "FORCE_GROUP_ALLOCATION" a le même effet.
    --defsym=symbole=expression
    Crée un symbole global dans le fichier de sortie, contenant l'adresse absolue donnée par expression. Vous pouvez utiliser cette option autant de fois que nécessaire pour définir plusieurs symboles dans la ligne de commande. Une forme limitée d'arithmétique est prise en charge pour l'expression dans ce contexte : vous pouvez donner une constante hexadécimale ou le nom d'un symbole existant, ou utiliser "+" et "-" pour ajouter ou soustraire des constantes hexadécimales ou des symboles. Si vous avez besoin d'expressions plus élaborées, envisagez d'utiliser le langage de commande de l'éditeur de liens à partir d'un script. *Note :* il ne doit y avoir aucun espace blanc entre symbole, le signe égal ("="), et expression.

    L'éditeur de liens traite les arguments --defsym et -T dans l'ordre. Placer --defsym avant -T définira le symbole avant que le script de l'éditeur de liens de -T ne soit traité, tandis que placer --defsym après -T définira le symbole après que le script de l'éditeur de liens ait été traité. Cette différence a des conséquences pour les expressions dans le script de l'éditeur de liens qui utilisent les symboles --defsym ; l'ordre qui est correct dépendra de ce que vous essayez d'accomplir.

    --demangle[=style]
    --no-demangle
    Ces options contrôlent si les noms de symboles doivent être "démêlés" dans les messages d'erreur et autres sorties. Lorsque l'éditeur de liens est invité à démêler, il essaie de présenter les noms de symboles de manière lisible : il supprime les tirets bas initiaux s'ils sont utilisés par le format de fichier objet, et convertit les noms de symboles C++ "manglés" en noms lisibles par l'utilisateur. Différents compilateurs ont des styles de "mangling" différents. L'argument optionnel de style de démêlage peut être utilisé pour choisir un style de démêlage approprié pour votre compilateur. L'éditeur de liens démêlera par défaut, sauf si la variable d'environnement COLLECT_NO_DEMANGLE est définie. Ces options peuvent être utilisées pour remplacer le comportement par défaut.
    -Ifichier
    --dynamic-linker=fichier
    Définit le nom de l'éditeur de liens dynamique. Ceci n'est significatif que lors de la génération d'exécutables ELF liés dynamiquement. L'éditeur de liens dynamique par défaut est normalement correct ; n'utilisez pas cette option sauf si vous savez ce que vous faites.
    --no-dynamic-linker
    Lors de la production d'un fichier exécutable, omettre la demande d'utilisation d'un éditeur de liens dynamique au moment du chargement. Ceci n'est significatif que pour les exécutables ELF qui contiennent des relocations dynamiques, et nécessite généralement un code d'entrée capable de traiter ces relocations.
    --embedded-relocs
    Cette option est similaire à l'option --emit-relocs, sauf que les relocations sont stockées dans une section spécifique à la cible. Cette option n'est prise en charge que par les cibles BFIN, CR16 et M68K.
    --disable-multiple-abs-defs
    Ne pas autoriser les définitions multiples avec des symboles inclus dans le nom de fichier invoqué par -R ou --just-symbols
    ----fatal-warnings
    --no-fatal-warnings
    Traite tous les avertissements comme des erreurs. Le comportement par défaut peut être rétabli avec l'option --no-fatal-warnings.
    -w
    --no-warnings
    N'affiche aucun message d'avertissement ou d'erreur. Ceci remplace --fatal-warnings s'il a été activé. Cette option peut être utilisée lorsqu'il est connu que le binaire de sortie ne fonctionnera pas, mais qu'il est nécessaire de le créer quand même.
    --force-exe-suffix
    Assure qu'un fichier de sortie possède un suffixe .exe.

    Si un fichier de sortie entièrement lié et construit avec succès ne possède pas de suffixe ".exe" ou ".dll", cette option force l'éditeur de liens à copier le fichier de sortie vers un autre fichier du même nom avec un suffixe ".exe". Cette option est utile lorsque l'on utilise des makefiles Unix non modifiés sur un hôte Microsoft Windows, car certaines versions de Windows n'exécutent pas une image si elle ne se termine pas par un suffixe ".exe".

    --gc-sections
    --no-gc-sections
    Active la récupération de mémoire (garbage collection) des sections d'entrée inutilisées. Elle est ignorée sur les cibles qui ne supportent pas cette option. Le comportement par défaut (ne pas effectuer cette récupération de mémoire) peut être rétabli en spécifiant --no-gc-sections sur la ligne de commande. Notez que la récupération de mémoire pour les cibles au format COFF et PE est supportée, mais l'implémentation est actuellement considérée comme expérimentale.

    --gc-sections détermine quelles sections d'entrée sont utilisées en examinant les symboles et les relocations. La section contenant le symbole d'entrée et toutes les sections contenant des symboles indéfinis sur la ligne de commande seront conservées, tout comme les sections contenant des symboles référencés par des objets dynamiques. Notez que lors de la construction de bibliothèques partagées, l'éditeur de liens doit supposer que tout symbole visible est référencé. Une fois cet ensemble initial de sections déterminé, l'éditeur de liens marque récursivement comme utilisées toute section référencée par ses relocations. Voir --entry, --undefined, et --gc-keep-exported.

    Cette option peut être définie lors d'une liaison partielle (activée avec l'option -r). Dans ce cas, la racine des symboles conservés doit être explicitement spécifiée soit par l'une des options --entry, --undefined, ou --gc-keep-exported, soit par une commande "ENTRY" dans le script de l'éditeur de liens.

    En tant qu'extension GNU, les sections d'entrée ELF marquées avec le drapeau "SHF_GNU_RETAIN" ne seront pas collectées par le garbage collector.

    --print-gc-sections
    --no-print-gc-sections
    Liste toutes les sections supprimées par le garbage collection. La liste est imprimée sur stderr. Cette option n'est effective que si le garbage collection a été activé via l'option --gc-sections. Le comportement par défaut (ne pas lister les sections supprimées) peut être rétabli en spécifiant --no-print-gc-sections sur la ligne de commande.
    --gc-keep-exported
    Lorsque --gc-sections est activé, cette option empêche le garbage collection des sections d'entrée inutilisées qui contiennent des symboles globaux ayant une visibilité par défaut ou protégée. Cette option est destinée à être utilisée pour les exécutables où les sections non référencées seraient autrement collectées par le garbage collector, quelle que soit la visibilité externe des symboles contenus. Notez que cette option n'a aucun effet lors de la liaison d'objets partagés car c'est déjà le comportement par défaut. Cette option n'est supportée que pour les cibles au format ELF.
    --print-output-format
    Affiche le nom du format de sortie par défaut (potentiellement influencé par d'autres options de ligne de commande). Il s'agit de la chaîne qui apparaîtrait dans une commande de script d'éditeur de liens "OUTPUT_FORMAT".
    --print-memory-usage
    Affiche la taille utilisée, la taille totale et la taille utilisée des régions mémoire créées avec la commande MEMORY. Ceci est utile sur les cibles embarquées pour avoir une vue rapide de la quantité de mémoire libre. Le format de la sortie comporte un titre et une ligne par région. Il est à la fois lisible par l'homme et facilement analysable par des outils. Voici un exemple de sortie : 
    Région mémoire       Taille Utilisée  Taille Région  % Utilisé
             ROM:        256 Ko         1 Mo     25.00%
             RAM:          32 B         2 Go      0.00%
    --help
    Affiche un résumé des options de la ligne de commande sur la sortie standard et quitte.
    --target-help
    Affiche un résumé de toutes les options spécifiques à la cible sur la sortie standard et quitte.
    -Map=fichiercarte
    Affiche une carte de liaison dans le fichier fichiercarte. Voir la description de l'option -M, ci-dessus. Si fichiercarte est juste le caractère "-", alors la carte sera écrite sur la sortie standard.

    Spécifier un répertoire comme fichiercarte fait que la carte de l'éditeur de liens sera écrite dans un fichier à l'intérieur du répertoire. Normalement, le nom du fichier dans le répertoire est calculé comme le nom de base du fichier de sortie avec ".map" ajouté. Cependant, si le caractère spécial "%" est utilisé, il sera remplacé par le chemin complet du fichier de sortie. De plus, s'il y a des caractères après le symbole %, alors ".map" ne sera plus ajouté.

    -o foo.exe -Map=bar                  [Crée ./bar]
-o ../dir/foo.exe -Map=bar           [Crée ./bar]
-o foo.exe -Map=../dir               [Crée ../dir/foo.exe.map]
-o ../dir2/foo.exe -Map=../dir       [Crée ../dir/foo.exe.map]
-o foo.exe -Map=%                    [Crée ./foo.exe.map]
-o ../dir/foo.exe -Map=%             [Crée ../dir/foo.exe.map]
-o foo.exe -Map=%.bar                [Crée ./foo.exe.bar]
-o ../dir/foo.exe -Map=%.bar         [Crée ../dir/foo.exe.bar]
-o ../dir2/foo.exe -Map=../dir/%     [Crée ../dir/../dir2/foo.exe.map]
-o ../dir2/foo.exe -Map=../dir/%.bar [Crée ../dir/../dir2/foo.exe.bar]

    Il est erroné de spécifier plus d'un caractère "%".

    Si le fichier carte existe déjà, il sera écrasé par cette opération.

    --no-keep-memory
    ld optimise normalement la vitesse au détriment de l'utilisation de la mémoire en mettant en cache les tables de symboles des fichiers d'entrée en mémoire. Cette option indique à ld d'optimiser à la place l'utilisation de la mémoire, en relisant les tables de symboles si nécessaire. Cela peut être requis si ld manque de mémoire lors de la liaison d'un grand exécutable.
    --no-undefined
    -z defs
    Rapporte les références de symboles non résolues provenant de fichiers objets réguliers. Ceci est fait même si l'éditeur de liens crée une bibliothèque partagée non symbolique. Le commutateur --[no-]allow-shlib-undefined contrôle le comportement pour le signalement des références non résolues trouvées dans les bibliothèques partagées liées.

    Les effets de cette option peuvent être annulés en utilisant "-z undefs".

    --allow-multiple-definition
    -z muldefs
    Normalement, lorsqu'un symbole est défini plusieurs fois, l'éditeur de liens signale une erreur fatale. Ces options autorisent les définitions multiples et la première définition sera utilisée.
    --allow-shlib-undefined
    --no-allow-shlib-undefined
    Autorise ou interdit les symboles indéfinis dans les bibliothèques partagées. Ce commutateur est similaire à --no-undefined, sauf qu'il détermine le comportement lorsque les symboles indéfinis se trouvent dans une bibliothèque partagée plutôt que dans un fichier objet régulier. Il n'affecte pas la manière dont les symboles indéfinis dans les fichiers objets réguliers sont traités.

    Le comportement par défaut est de signaler des erreurs pour tout symbole indéfini référencé dans des bibliothèques partagées si l'éditeur de liens est utilisé pour créer un exécutable, mais de les autoriser si l'éditeur de liens est utilisé pour créer une bibliothèque partagée.

    Les raisons d'autoriser les références de symboles indéfinis dans les bibliothèques partagées spécifiées au moment de la liaison sont que :

    • Une bibliothèque partagée spécifiée au moment de la liaison peut ne pas être la même que celle disponible au moment du chargement, le symbole pourrait donc être résoluble au moment du chargement.
    • Certains systèmes d'exploitation, par exemple BeOS et HPPA, où les symboles indéfinis dans les bibliothèques partagées sont normaux.

      Le noyau BeOS, par exemple, patch les bibliothèques partagées au moment du chargement pour sélectionner la fonction la plus appropriée pour l'architecture actuelle. Ceci est utilisé, par exemple, pour sélectionner dynamiquement une fonction memset appropriée.

    --error-handling-script=nomscript
    Si cette option est fournie, l'éditeur de liens invoquera nomscript chaque fois qu'une erreur est rencontrée. Actuellement cependant, seuls deux types d'erreurs sont supportés : symboles manquants et bibliothèques manquantes. Deux arguments seront passés au script : le mot-clé "undefined-symbol" ou `missing-lib" et le nom du symbole indéfini ou de la bibliothèque manquante. L'intention est que le script fournisse des suggestions à l'utilisateur sur l'endroit où le symbole ou la bibliothèque pourrait être trouvé. Après que le script ait terminé, le message d'erreur normal de l'éditeur de liens sera affiché.

    La disponibilité de cette option est contrôlée par un commutateur de configuration, elle peut donc ne pas être présente dans des implémentations spécifiques.

    --no-undefined-version
    Normalement, lorsqu'un symbole a une version indéfinie, l'éditeur de liens l'ignore. Cette option interdit les symboles avec une version indéfinie et une erreur fatale sera émise à la place.
    --default-symver
    Crée et utilise une version de symbole par défaut (le soname) pour les symboles exportés non versionnés.
    -v
    Affiche le numéro de version de l'éditeur de liens sur la sortie standard et quitte.
    --version
    Affiche le numéro de version de l'éditeur de liens sur la sortie standard et quitte.
    dt id="default~3">--default-imported-symver
    Crée et utilise une version de symbole par défaut (le soname) pour les symboles importés non versionnés.
    --no-warn-mismatch
    Normalement, ld générera une erreur si vous essayez de lier ensemble des fichiers d'entrée qui sont incompatibles pour une raison quelconque, peut-être parce qu'ils ont été compilés pour des processeurs différents ou pour des endiannesses différentes. Cette option indique à ld de permettre silencieusement de telles erreurs potentielles. Cette option ne doit être utilisée qu'avec prudence, dans les cas où vous avez pris des mesures spéciales qui garantissent que les erreurs de l'éditeur de liens sont inappropriées.
    --no-warn-search-mismatch
    Normalement, ld émettra un avertissement s'il trouve une bibliothèque incompatible lors d'une recherche de bibliothèque. Cette option supprime l'avertissement.
    --no-whole-archive
    Désactive l'effet de l'option --whole-archive pour les fichiers d'archive suivants.
    --noinhibit-exec
    Conserve le fichier de sortie exécutable tant qu'il est utilisable. Normalement, l'éditeur de liens ne produira pas de fichier de sortie s'il rencontre des erreurs pendant le processus de liaison ; il se termine sans écrire de fichier de sortie lorsqu'il émet une erreur quelconque.
    -nostdlib
    Ne recherche les répertoires de bibliothèques que ceux explicitement spécifiés sur la ligne de commande. Les répertoires de bibliothèques spécifiés dans les scripts de l'éditeur de liens (y compris les scripts de l'éditeur de liens spécifiés sur la ligne de commande) sont ignorés.
    --oformat=format-sortie
    ld peut être configuré pour prendre en charge plus d'un type de fichier objet. Si votre ld est configuré de cette manière, vous pouvez utiliser l'option --oformat pour spécifier le format binaire pour le fichier objet de sortie. Même lorsque ld est configuré pour prendre en charge des formats d'objets alternatifs, vous n'avez généralement pas besoin de le spécifier, car ld devrait être configuré pour produire comme format de sortie par défaut le format le plus courant sur chaque machine. format-sortie est une chaîne de caractères, le nom d'un format particulier pris en charge par les bibliothèques BFD. (Vous pouvez lister les formats binaires disponibles avec objdump -i.) La commande de script "OUTPUT_FORMAT" peut également spécifier le format de sortie, mais cette option la remplace.
    --out-implib fichier
    Crée une bibliothèque d'importation dans fichier correspondant à l'exécutable que l'éditeur de liens génère (par exemple, un programme DLL ou ELF). Cette bibliothèque d'importation (qui devrait s'appeler "*.dll.a" ou "*.a" pour les DLL) peut être utilisée pour lier des clients à l'exécutable généré ; ce comportement permet de sauter une étape de création de bibliothèque d'importation distincte (par exemple, "dlltool" pour les DLL). Cette option n'est disponible que pour les ports de l'éditeur de liens ciblant i386 PE et ELF.
    -pie
    --pic-executable
    Crée un exécutable indépendant de la position. Ceci n'est actuellement pris en charge que sur les plateformes ELF. Les exécutables indépendants de la position sont similaires aux bibliothèques partagées en ce sens qu'ils sont déplacés par l'éditeur de liens dynamique à l'adresse virtuelle que le système d'exploitation leur choisit (ce qui peut varier entre les invocations). Comme les exécutables liés dynamiquement normaux, ils peuvent être exécutés et les symboles définis dans l'exécutable ne peuvent pas être remplacés par des bibliothèques partagées.
    -no-pie
    Crée un exécutable dépendant de la position. C'est le comportement par défaut.
    -qmagic
    Cette option est ignorée pour la compatibilité Linux.
    -Qy
    Cette option est ignorée pour la compatibilité SVR4.
    --relax
    --no-relax
    Une option avec des effets dépendants de la machine. Cette option n'est prise en charge que sur quelques cibles.

    Sur certaines plateformes, l'option --relax effectue des optimisations globales spécifiques à la cible qui deviennent possibles lorsque l'éditeur de liens résout l'adressage dans le programme, comme le relâchement des modes d'adressage, la synthèse de nouvelles instructions, la sélection de versions plus courtes des instructions actuelles et la combinaison de valeurs constantes.

    Sur certaines plateformes, ces optimisations globales au moment de la liaison peuvent rendre le débogage symbolique de l'exécutable résultant impossible. C'est le cas connu pour la famille de processeurs Matsushita MN10200 et MN10300.

    Sur les plateformes où la fonctionnalité est prise en charge, l'option --no-relax la désactivera.

    Sur les plateformes où la fonctionnalité n'est pas prise en charge, --relax et --no-relax sont acceptées, mais ignorées.

    --retain-symbols-file=nomfichier
    Conserve *uniquement* les symboles listés dans le fichier nomfichier, en rejetant tous les autres. nomfichier est simplement un fichier plat, avec un nom de symbole par ligne. Cette option est particulièrement utile dans les environnements (comme VxWorks) où une grande table de symboles globale est accumulée progressivement, afin de conserver la mémoire d'exécution.

    --retain-symbols-file ne rejette *pas* les symboles indéfinis, ni les symboles nécessaires aux relocalisations.

    Vous ne pouvez spécifier --retain-symbols-file qu'une seule fois sur la ligne de commande. Elle remplace -s et -S.

    -rpath=rep
    Ajoute un répertoire au chemin de recherche des bibliothèques d'exécution. Ceci est utilisé lors de la liaison d'un exécutable ELF avec des objets partagés. Tous les arguments -rpath sont concaténés et transmis à l'éditeur de liens d'exécution, qui les utilise pour localiser les objets partagés au moment de l'exécution.

    L'option -rpath est également utilisée lors de la localisation des objets partagés requis par des objets partagés explicitement inclus dans la liaison ; voir la description de l'option -rpath-link. La recherche de -rpath de cette manière n'est prise en charge que par les éditeurs de liens natifs et les éditeurs de liens croisés configurés avec l'option --with-sysroot.

    Si -rpath n'est pas utilisé lors de la liaison d'un exécutable ELF, le contenu de la variable d'environnement "LD_RUN_PATH" sera utilisé s'il est défini.

    L'option -rpath peut également être utilisée sur SunOS. Par défaut, sur SunOS, l'éditeur de liens forme un chemin de recherche d'exécution à partir de toutes les options -L qui lui sont données. Si une option -rpath est utilisée, le chemin de recherche d'exécution sera formé exclusivement à l'aide des options -rpath, ignorant les options -L. Cela peut être utile lors de l'utilisation de gcc, qui ajoute de nombreuses options -L qui peuvent se trouver sur des systèmes de fichiers montés NFS.

    Pour la compatibilité avec d'autres éditeurs de liens ELF, si l'option -R est suivie d'un nom de répertoire, plutôt que d'un nom de fichier, elle est traitée comme l'option -rpath.

    -rpath-link=rep
    Lors de l'utilisation d'ELF ou de SunOS, une bibliothèque partagée peut en nécessiter une autre. Cela se produit lorsqu'une liaison "ld -shared" inclut une bibliothèque partagée comme l'un des fichiers d'entrée.

    Lorsque l'éditeur de liens rencontre une telle dépendance lors d'une liaison non partagée et non déplaçable, il essaie automatiquement de localiser la bibliothèque partagée requise et de l'inclure dans la liaison, si elle n'est pas incluse explicitement. Dans un tel cas, l'option -rpath-link spécifie le premier ensemble de répertoires à rechercher. L'option -rpath-link peut spécifier une séquence de noms de répertoires soit en spécifiant une liste de noms séparés par des deux-points, soit en apparaissant plusieurs fois.

    Les jetons $ORIGIN et $LIB peuvent apparaître dans ces répertoires de recherche. Ils seront remplacés par le chemin complet du répertoire contenant le programme ou l'objet partagé dans le cas de $ORIGIN et soit lib - pour les binaires 32 bits - soit lib64 - pour les binaires 64 bits - dans le cas de $LIB.

    La forme alternative de ces jetons - ${ORIGIN} et ${LIB} - peut également être utilisée. Le jeton $PLATFORM n'est pas pris en charge.

    Cette option doit être utilisée avec prudence car elle remplace le chemin de recherche qui peut avoir été codé en dur dans une bibliothèque partagée. Dans un tel cas, il est possible d'utiliser involontairement un chemin de recherche différent de celui que l'éditeur de liens d'exécution utiliserait.

    L'éditeur de liens utilise les chemins de recherche suivants pour localiser les bibliothèques partagées requises :

    1.
    Tous les répertoires spécifiés par les options -rpath-link.
    2.
    Tous les répertoires spécifiés par les options -rpath. La différence entre -rpath et -rpath-link est que les répertoires spécifiés par les options -rpath sont inclus dans l'exécutable et utilisés au moment de l'exécution, tandis que l'option -rpath-link n'est effective qu'au moment de la liaison. La recherche de -rpath de cette manière n'est prise en charge que par les éditeurs de liens natifs et les éditeurs de liens croisés configurés avec l'option --with-sysroot.
    3.
    Sur un système ELF, pour les éditeurs de liens natifs, si les options -rpath et -rpath-link n'ont pas été utilisées, rechercher le contenu de la variable d'environnement "LD_RUN_PATH".
    4.
    Sur SunOS, si l'option -rpath n'a pas été utilisée, rechercher tous les répertoires spécifiés à l'aide des options -L.
    5.
    Pour un éditeur de liens natif, rechercher le contenu de la variable d'environnement "LD_LIBRARY_PATH".
    6.
    Pour un éditeur de liens ELF natif, les répertoires dans "DT_RUNPATH" ou "DT_RPATH" d'une bibliothèque partagée sont recherchés pour les bibliothèques partagées dont elle a besoin. Les entrées "DT_RPATH" sont ignorées si des entrées "DT_RUNPATH" existent.
    7.
    Pour un éditeur de liens d'un système Linux, si le fichier /etc/ld.so.conf existe, la liste des répertoires trouvés dans ce fichier. Remarque : le chemin vers ce fichier est préfixé par la valeur "sysroot", si elle est définie, puis par toute chaîne "prefix" si l'éditeur de liens a été configuré avec le
    --prefix=<chemin> option.
    8.
    Pour un lieur natif sur un système FreeBSD, tous les répertoires spécifiés par la macro "_PATH_ELF_HINTS" définie dans le fichier d'en-tête elf-hints.h.
    9.
    Tous les répertoires spécifiés par une commande "SEARCH_DIR" dans un script de lieur fourni sur la ligne de commande, y compris les scripts spécifiés par -T (mais pas -dT).
    10.
    Les répertoires par défaut, normalement /lib et /usr/lib.
    11.
    Tous les répertoires spécifiés par un plugin LDPT_SET_EXTRA_LIBRARY_PATH.
    12.
    Tous les répertoires spécifiés par une commande "SEARCH_DIR" dans un script de lieur par défaut.

    Notez cependant que sur les systèmes basés sur Linux, il y a une mise en garde supplémentaire : Si l'option --as-needed est active et qu'une bibliothèque partagée est localisée qui satisferait normalement la recherche et que cette bibliothèque n'a pas de tag DT_NEEDED pour libc.so et qu'il y a une bibliothèque partagée plus loin dans l'ensemble des répertoires de recherche qui satisfait également la recherche et que cette seconde bibliothèque partagée a un tag DT_NEEDED pour libc.so alors la seconde bibliothèque sera sélectionnée à la place de la première.

    Si la bibliothèque partagée requise n'est pas trouvée, le lieur affichera un avertissement et poursuivra la liaison.

    -shared
    -Bshareable
    Crée une bibliothèque partagée. Ceci n'est actuellement supporté que sur les plateformes ELF, XCOFF et SunOS. Sur SunOS, le lieur créera automatiquement une bibliothèque partagée si l'option -e n'est pas utilisée et qu'il y a des symboles indéfinis dans la liaison.
    --sort-common
    --sort-common=ascending
    --sort-common=descending
    Cette option indique à ld de trier les symboles communs par alignement en ordre croissant ou décroissant lorsqu'il les place dans les sections de sortie appropriées. Les alignements de symboles considérés sont de seize octets ou plus, huit octets, quatre octets, deux octets et un octet. Ceci est fait pour éviter les espaces entre les symboles dus aux contraintes d'alignement. Si aucun ordre de tri n'est spécifié, alors l'ordre décroissant est supposé.
    --sort-section=name
    Cette option appliquera "SORT_BY_NAME" à tous les motifs de section joker dans le script de lieur.
    --sort-section=alignment
    Cette option appliquera "SORT_BY_ALIGNMENT" à tous les motifs de section joker dans le script de lieur.
    --spare-dynamic-tags=nombre
    Cette option spécifie le nombre d'emplacements vides à laisser dans la section .dynamic des objets partagés ELF. Des emplacements vides peuvent être nécessaires aux outils de post-traitement, tels que le pré-lieur. La valeur par défaut est 5.
    --split-by-file[=taille]
    Similaire à --split-by-reloc mais crée une nouvelle section de sortie pour chaque fichier d'entrée lorsque taille est atteinte. taille vaut par défaut 1 si non spécifiée.
    --split-by-reloc[=nombre]
    Essaie de créer des sections supplémentaires dans le fichier de sortie de sorte qu'aucune section de sortie unique dans le fichier ne contienne plus de nombre relocations. Ceci est utile lors de la génération de fichiers relocalisables énormes pour le téléchargement dans certains noyaux temps réel avec le format de fichier objet COFF ; car COFF ne peut pas représenter plus de 65535 relocations dans une seule section. Notez que cela échouera avec les formats de fichiers objet qui ne supportent pas les sections arbitraires. Le lieur ne divisera pas les sections d'entrée individuelles pour la redistribution, donc si une seule section d'entrée contient plus de nombre relocations, une section de sortie contiendra ce nombre de relocations. nombre vaut par défaut 32768.
    --stats
    Calcule et affiche des statistiques sur le fonctionnement du lieur, telles que le temps d'exécution et l'utilisation de la mémoire.
    --sysroot=répertoire
    Utilise répertoire comme emplacement du sysroot, remplaçant la valeur par défaut configurée lors de la compilation. Cette option n'est supportée que par les lieurs configurés avec --with-sysroot.
    --task-link
    Ceci est utilisé par les cibles basées sur COFF/PE pour créer un fichier objet lié à la tâche où tous les symboles globaux ont été convertis en statiques.
    --traditional-format
    Pour certaines cibles, la sortie de ld diffère à certains égards de celle de certains lieurs existants. Ce commutateur demande à ld d'utiliser le format traditionnel à la place.

    Par exemple, sur SunOS, ld combine les entrées dupliquées dans la table des chaînes de symboles. Cela peut réduire la taille d'un fichier de sortie avec des informations de débogage complètes de plus de 30 %. Malheureusement, le programme "dbx" de SunOS ne peut pas lire le programme résultant ("gdb" n'a aucun problème). Le commutateur --traditional-format indique à ld de ne pas combiner les entrées dupliquées.

    --section-start=nomsection=origine
    Localise une section dans le fichier de sortie à l'adresse absolue donnée par origine. Vous pouvez utiliser cette option autant de fois que nécessaire pour localiser plusieurs sections sur la ligne de commande. origine doit être un entier hexadécimal unique ; pour la compatibilité avec d'autres lieurs, vous pouvez omettre le préfixe 0x généralement associé aux valeurs hexadécimales. Note : il ne doit pas y avoir d'espace blanc entre nomsection, le signe égal ("="), et origine.
    -Tbss=origine
    -Tdata=origine
    -Ttext=origine
    Identique à --section-start, avec ".bss", ".data" ou ".text" comme nomsection.
    -Ttext-segment=origine
    Lors de la création d'un exécutable ELF, il définit l'adresse du premier octet du segment de texte.
    -Trodata-segment=origine
    Lors de la création d'un exécutable ELF ou d'un objet partagé pour une cible où les données en lecture seule se trouvent dans leur propre segment séparé du texte exécutable, il définit l'adresse du premier octet du segment de données en lecture seule.
    -Tldata-segment=origine
    Lors de la création d'un exécutable ELF ou d'un objet partagé pour le modèle de mémoire moyenne x86-64, il définit l'adresse du premier octet du segment ldata.
    --unresolved-symbols=méthode
    Détermine comment gérer les symboles non résolus. Il existe quatre valeurs possibles pour méthode :
    ignore-all
    Ne pas signaler aucun symbole non résolu.
    report-all
    Signaler tous les symboles non résolus. C'est la valeur par défaut.
    ignore-in-object-files
    Signaler les symboles non résolus qui sont contenus dans des bibliothèques partagées, mais les ignorer s'ils proviennent de fichiers objet réguliers.
    ignore-in-shared-libs
    Signaler les symboles non résolus qui proviennent de fichiers objet réguliers, mais les ignorer s'ils proviennent de bibliothèques partagées. Ceci peut être utile lors de la création d'un binaire dynamique et lorsque l'on sait que toutes les bibliothèques partagées qu'il devrait référencer sont incluses dans la ligne de commande du lieur.

    Le comportement pour les bibliothèques partagées seules peut également être contrôlé par l'option --[no-]allow-shlib-undefined.

    Normalement, le lieur générera un message d'erreur pour chaque symbole non résolu signalé, mais l'option --warn-unresolved-symbols peut changer cela en un avertissement.

    --dll-verbose
    --verbose[=NOMBRE]
    Affiche le numéro de version de ld et liste les émulations de lieur supportées. Affiche quels fichiers d'entrée peuvent être ouverts et lesquels ne le peuvent pas. Affiche le script de lieur utilisé par le lieur. Si l'argument facultatif NOMBRE > 1, le statut des symboles des plugins sera également affiché.
    --version-script=fichier-script-version
    Spécifie le nom d'un script de version au lieur. Ceci est généralement utilisé lors de la création de bibliothèques partagées pour spécifier des informations supplémentaires sur la hiérarchie des versions de la bibliothèque créée. Cette option n'est entièrement supportée que sur les plateformes ELF qui supportent les bibliothèques partagées ; voir VERSION. Elle est partiellement supportée sur les plateformes PE, qui peuvent utiliser des scripts de version pour filtrer la visibilité des symboles en mode d'exportation automatique : tous les symboles marqués local dans le script de version ne seront pas exportés.
    --warn-common
    Avertit lorsqu'un symbole commun est combiné avec un autre symbole commun ou avec une définition de symbole. Les lieurs Unix autorisent cette pratique quelque peu laxiste, mais les lieurs sur certains autres systèmes d'exploitation ne le font pas. Cette option vous permet de détecter des problèmes potentiels liés à la combinaison de symboles globaux. Malheureusement, certaines bibliothèques C utilisent cette pratique, vous pourriez donc recevoir des avertissements concernant des symboles dans les bibliothèques ainsi que dans vos programmes.

    Il existe trois types de symboles globaux, illustrés ici par des exemples en C :

    int i = 1;
    Une définition, qui va dans la section des données initialisées du fichier de sortie.
    extern int i;
    Une référence indéfinie, qui
    h n'alloue pas d'espace. Il doit y avoir soit une définition, soit un symbole commun pour la variable quelque part.
    int i ;
    Un symbole commun. S'il n'y a que (un ou plusieurs) symboles communs pour une variable, elle va dans la zone de données non initialisées du fichier de sortie. L'éditeur de liens fusionne plusieurs symboles communs pour la même variable en un seul symbole. S'ils sont de tailles différentes, il choisit la plus grande taille. L'éditeur de liens transforme un symbole commun en une déclaration, s'il existe une définition de la même variable.

    L'option --warn-common peut produire cinq types d'avertissements. Chaque avertissement se compose d'une paire de lignes : la première décrit le symbole qui vient d'être rencontré, et la seconde décrit le symbole précédent rencontré avec le même nom. L'un ou les deux symboles seront un symbole commun.

    1.
    Transformation d'un symbole commun en une référence, car il existe déjà une définition pour le symbole. 
    <file>(<section>) : avertissement : symbole commun de `<symbol>'
   remplacé par une définition
<file>(<section>) : avertissement : défini ici
    2.
    Transformation d'un symbole commun en une référence, car une définition ultérieure du symbole est rencontrée. Ceci est identique au cas précédent, sauf que les symboles sont rencontrés dans un ordre différent. 
    <file>(<section>) : avertissement : définition de `<symbol>'
   remplaçant un symbole commun
<file>(<section>) : avertissement : symbole commun ici
    3.
    Fusion d'un symbole commun avec un symbole commun précédent de même taille. 
    <file>(<section>) : avertissement : symboles communs multiples
   de `<symbol>'
<file>(<section>) : avertissement : symbole commun précédent ici
    4.
    Fusion d'un symbole commun avec un symbole commun précédent plus grand. 
    <file>(<section>) : avertissement : symbole commun de `<symbol>'
   remplacé par un symbole commun plus grand
<file>(<section>) : avertissement : symbole commun plus grand ici
    5.
    Fusion d'un symbole commun avec un symbole commun précédent plus petit. Ceci est identique au cas précédent, sauf que les symboles sont rencontrés dans un ordre différent. 
    <file>(<section>) : avertissement : symbole commun de `<symbol>'
   remplaçant un symbole commun plus petit
<file>(<section>) : avertissement : symbole commun plus petit ici
    --warn-constructors
    Avertir si des constructeurs globaux sont utilisés. Ceci n'est utile que pour quelques formats de fichiers objets. Pour des formats comme COFF ou ELF, l'éditeur de liens ne peut pas détecter l'utilisation de constructeurs globaux.
    --warn-execstack
    --warn-execstack-objects
    --no-warn-execstack
    Sur les plateformes ELF, l'éditeur de liens peut générer des messages d'avertissement s'il est invité à créer un fichier de sortie contenant une pile exécutable. Il existe trois états possibles :
    1.
    Ne générer aucun avertissement.
    2.
    Générer toujours des avertissements, même si la pile exécutable est demandée via l'option de ligne de commande -z execstack.
    3.
    Ne générer un avertissement que si un fichier objet demande une pile exécutable, mais pas si l'option -z execstack est utilisée.

    L'état par défaut dépend de la manière dont l'éditeur de liens a été configuré lors de sa construction. L'option --no-warn-execstack place toujours l'éditeur de liens dans l'état sans avertissements. L'option --warn-execstack place l'éditeur de liens dans l'état d'avertissement permanent. L'option --warn-execstack-objects place l'éditeur de liens dans l'état d'avertissement uniquement pour les fichiers objets.

    Note : les fichiers d'entrée au format ELF peuvent spécifier qu'ils nécessitent une pile exécutable en ayant une section .note.GNU-stack avec le bit exécutable défini dans ses drapeaux de section. Ils peuvent spécifier qu'ils n'ont pas besoin d'une pile exécutable en ayant la même section, mais sans le bit exécutable défini. Si un fichier d'entrée n'a pas de section .note.GNU-stack, le comportement par défaut est spécifique à la cible. Pour certaines cibles, l'absence d'une telle section implique qu'une pile exécutable est requise. C'est souvent un problème pour les fichiers assembleurs fabriqués à la main.

    --error-execstack
    --no-error-execstack
    Si l'éditeur de liens doit générer un message d'avertissement concernant une pile exécutable, l'option --error-execstack transformera cet avertissement en une erreur. Notez que cette option ne modifie pas l'état de génération des avertissements execstack de l'éditeur de liens. Utilisez --warn-execstack ou --warn-execstack-objects pour définir un état d'avertissement spécifique.

    L'option --no-error-execstack rétablira le comportement par défaut de génération de messages d'avertissement.

    --warn-multiple-gp
    Avertir si plusieurs valeurs de pointeur global sont requises dans le fichier de sortie. Ceci n'est significatif que pour certains processeurs, tels que l'Alpha. Spécifiquement, certains processeurs placent les constantes de grande valeur dans une section spéciale. Un registre spécial (le pointeur global) pointe vers le milieu de cette section, de sorte que les constantes puissent être chargées efficacement via un mode d'adressage relatif au registre de base. Comme le décalage en mode relatif au registre de base est fixe et relativement petit (par exemple, 16 bits), cela limite la taille maximale du pool de constantes. Ainsi, dans les gros programmes, il est souvent nécessaire d'utiliser plusieurs valeurs de pointeur global afin de pouvoir adresser toutes les constantes possibles. Cette option provoque un avertissement chaque fois que ce cas se produit.
    --warn-once
    N'émettre un avertissement qu'une seule fois pour chaque symbole non résolu, plutôt qu'une fois par module qui y fait référence.
    --warn-rwx-segments
    --no-warn-rwx-segments
    Avertir si l'éditeur de liens crée un segment chargeable de taille non nulle qui possède les trois indicateurs d'autorisation de lecture, d'écriture et d'exécution définis. Un tel segment représente une vulnérabilité de sécurité potentielle. De plus, des avertissements seront générés si un segment de stockage local de thread est créé avec l'indicateur d'autorisation d'exécution défini, indépendamment du fait qu'il ait ou non les indicateurs de lecture et/ou d'écriture définis.

    Ces avertissements sont activés par défaut. Ils peuvent être désactivés via l'option --no-warn-rwx-segments et réactivés via l'option --warn-rwx-segments.

    --error-rwx-segments
    --no-error-rwx-segments
    Si l'éditeur de liens doit générer un message d'avertissement concernant un segment exécutable et inscriptible, ou un segment TLS exécutable, alors l'option --error-rwx-segments transformera cet avertissement en une erreur. L'option --no-error-rwx-segments rétablira le comportement par défaut consistant à simplement générer un message d'avertissement.

    Note : l'option --error-rwx-segments n'active pas par elle-même les avertissements concernant ces segments. Ces avertissements sont soit activés par défaut, si l'éditeur de liens a été configuré ainsi, soit via l'option de ligne de commande --warn-rwx-segments.

    --warn-section-align
    Avertir si l'adresse d'une section de sortie est modifiée en raison de l'alignement. Typiquement, l'alignement sera défini par une section d'entrée. L'adresse ne sera modifiée que si elle n'est pas explicitement spécifiée ; c'est-à-dire si la commande "SECTIONS" ne spécifie pas d'adresse de départ pour la section.
    --warn-textrel
    Avertir si l'éditeur de liens ajoute DT_TEXTREL à un exécutable indépendant de la position ou à un objet partagé.
    --warn-alternate-em
    Avertir si un objet a un code machine ELF alternatif.
    --warn-unresolved-symbols
    Si l'éditeur de liens doit signaler un symbole non résolu (voir l'option --unresolved-symbols), il générera normalement une erreur. Cette option lui fait générer un avertissement à la place.
    --error-unresolved-symbols
    Ceci rétablit le comportement par défaut de l'éditeur de liens consistant à générer des erreurs lorsqu'il signale des symboles non résolus.
    --whole-archive
    Pour chaque archive mentionnée sur la ligne de commande après l'option --whole-archive, inclure chaque fichier objet de l'archive dans la liaison, plutôt que de rechercher dans l'archive les fichiers objets requis. Ceci est normalement utilisé pour transformer un fichier archive en une bibliothèque partagée, forçant chaque objet à être inclus dans la bibliothèque partagée résultante. Cette option peut être utilisée plus d'une fois.

    Deux notes lors de l'utilisation de cette option avec gcc : Premièrement, gcc ne connaît pas cette option, vous devez donc utiliser -Wl,-whole-archive. Deuxièmement, n'oubliez pas d'utiliser -Wl,-no-whole-archive après votre liste d'archives, car gcc ajoutera sa propre liste d'archives à votre liaison et vous pourriez ne pas vouloir que cet indicateur affecte également celles-ci.

    --wrap=symbole
    Utiliser une fonction enveloppante pour symbole. Toute référence non définie à symbole sera résolue en "__wrap_symbole". Toute référence non définie à "__real_symbole" sera résolue en symbole.

    Ceci peut être utilisé pour fournir une enveloppe pour une fonction système. La fonction enveloppante doit être appelée "__wrap_symbole". Si elle souhaite appeler la fonction système, elle doit appeler "__real_symbole".

    Voici un exemple trivial :

    void *
__wrap_malloc (size_t c)
{
  printf ("malloc appelé avec %zu\n", c);
  return __real_malloc (c);
}

    Si vous liez d'autres codes avec ce fichier en utilisant --wrap malloc, alors tous les appels à "malloc" appelleront la fonction "__wrap_malloc" à la place. L'appel à "__real_malloc" dans "__wrap_malloc"<

    /span> appellera la fonction "malloc" réelle.

    Vous pouvez également souhaiter fournir une fonction "__real_malloc", afin que les liens sans l'option --wrap réussissent. Si vous le faites, vous ne devez pas mettre la définition de "__real_malloc" dans le même fichier que "__wrap_malloc" ; si vous le faites, l'assembleur peut résoudre l'appel avant que l'éditeur de liens ait la possibilité de le "wrapper" vers "malloc".

    Seules les références indéfinies sont remplacées par l'éditeur de liens. Ainsi, les références internes à l'unité de traduction vers symbol ne sont pas résolues en "__wrap_symbol". Dans l'exemple suivant, l'appel à "f" dans "g" n'est pas résolu en "__wrap_f".

    int
f (void)
{
  return 123;
}

int
g (void)
{
  return f();
}

    --compress-debug-sections=none
    --compress-debug-sections=zlib
    --compress-debug-sections=zlib-gnu
    --compress-debug-sections=zlib-gabi
    --compress-debug-sections=zstd
    Sur les plateformes ELF, ces options contrôlent la compression des sections de débogage DWARF à l'aide de zlib.

    --compress-debug-sections=none ne compresse pas les sections de débogage DWARF. --compress-debug-sections=zlib-gnu compresse les sections de débogage DWARF et les renomme pour qu'elles commencent par .zdebug au lieu de .debug. --compress-debug-sections=zlib-gabi compresse également les sections de débogage DWARF, mais au lieu de les renommer, il définit l'indicateur SHF_COMPRESSED dans les en-têtes des sections.

    L'option --compress-debug-sections=zlib est un alias pour --compress-debug-sections=zlib-gabi.

    --compress-debug-sections=zstd compresse les sections de débogage DWARF à l'aide de zstd.

    Notez que cette option remplace toute compression dans les sections de débogage d'entrée, donc si un binaire est lié avec --compress-debug-sections=none par exemple, alors toutes les sections de débogage compressées dans les fichiers d'entrée seront décompressées avant d'être copiées dans le binaire de sortie.

    Le comportement de compression par défaut varie en fonction de la cible concernée et des options de configuration utilisées pour construire la chaîne d'outils. La valeur par défaut peut être déterminée en examinant la sortie de l'option --help de l'éditeur de liens.

    --reduce-memory-overheads
    Cette option réduit les besoins en mémoire à l'exécution de ld, au détriment de la vitesse de liaison. Elle a été introduite pour sélectionner l'ancien algorithme O(n^2) pour la génération du fichier de carte de liaison, plutôt que le nouvel algorithme O(n) qui utilise environ 40% de mémoire en plus pour le stockage des symboles.

    Un autre effet de cette option est de définir la taille par défaut de la table de hachage à 1021, ce qui permet d'économiser de la mémoire au prix d'un temps d'exécution plus long pour l'éditeur de liens. Ceci n'est cependant pas fait si l'option --hash-size a été utilisée.

    L'option --reduce-memory-overheads peut également être utilisée pour activer d'autres compromis dans les futures versions de l'éditeur de liens.

    --max-cache-size=taille
    ld met normalement en cache les informations de relocalisation et les tables de symboles des fichiers d'entrée en mémoire avec une taille illimitée. Cette option définit la taille maximale du cache à taille.
    --build-id
    --build-id=style
    Demande la création d'une section de note ELF ".note.gnu.build-id" ou d'une section COFF ".buildid". Le contenu de la note identifie de manière unique ce fichier lié. style peut être "uuid" pour utiliser 128 bits aléatoires, "sha1" pour utiliser un hachage SHA1 de 160 bits sur les parties normatives du contenu de sortie, "md5" pour utiliser un hachage MD5 de 128 bits sur les parties normatives du contenu de sortie, ou "0xhexstring" pour utiliser une chaîne de bits choisie spécifiée sous forme de nombre pair de chiffres hexadécimaux (les caractères "-" et ":" entre les paires de chiffres sont ignorés). Si style est omis, "sha1" est utilisé.

    Les styles "md5" et "sha1" produisent un identifiant qui est toujours le même dans un fichier de sortie identique, mais qui sera unique parmi tous les fichiers de sortie non identiques. Il n'est pas destiné à être comparé comme une somme de contrôle du contenu du fichier. Un fichier lié peut être modifié ultérieurement par d'autres outils, mais la chaîne de bits d'identification de la construction du fichier lié d'origine ne change pas.

    Passer "none" comme valeur pour style désactive le réglage provenant de toute option "--build-id" précédente sur la ligne de commande.

    Note : L'utilisation de l'extension 'auto-import' rendra la section de texte du fichier image inscriptible. Cela n'est pas conforme à la spécification du format PE-COFF publiée par Microsoft.

    Note - l'utilisation de l'extension 'auto-import' placera également les données en lecture seule, qui seraient normalement placées dans la section .rdata, dans la section .data à la place. Ceci afin de contourner un problème avec les constantes décrit ici : http://www.cygwin.com/ml/cygwin/2004-09/msg01101.html

    L'utilisation de 'auto-import' fonctionnera généralement "comme prévu" -- mais parfois vous pourrez voir ce message :

    "la variable '<var>' ne peut pas être auto-importée. Veuillez lire la documentation de ld pour "--enable-auto-import" pour les détails."

    Ce message apparaît lorsqu'une (sous)expression accède à une adresse donnée ultimement par la somme de deux constantes (les tables d'importation Win32 n'en autorisent qu'une). Les cas où cela peut se produire incluent les accès aux champs membres de variables struct importées d'une DLL, ainsi que l'utilisation d'un indice constant dans une variable tableau importée d'une DLL. Toute variable multi-mot (tableaux, structures, long long, etc.) peut déclencher cette condition d'erreur. Cependant, quel que soit le type de données exact de la variable exportée fautive, ld la détectera toujours, émettra l'avertissement et s'arrêtera.

    Il existe plusieurs façons de résoudre cette difficulté, quel que soit le type de données de la variable exportée :

    Une façon est d'utiliser l'option --enable-runtime-pseudo-reloc. Cela laisse la tâche d'ajuster les références dans votre code client pour l'environnement d'exécution, donc cette méthode ne fonctionne que lorsque l'environnement d'exécution prend en charge cette fonctionnalité.

    Une deuxième solution consiste à forcer l'une des 'constantes' à être une variable -- c'est-à-dire, inconnue et non optimisable au moment de la compilation. Pour les tableaux, il y a deux possibilités : a) faire de l'élément indexé (l'adresse du tableau) une variable, ou b) faire de l'indice 'constant' une variable. Ainsi :

    extern type extern_array[];
extern_array[1] -->
   { volatile type *t=extern_array; t[1] }

    ou

    extern type extern_array[];
extern_array[1] -->
   { volatile int t=1; extern_array[t] }

    Pour les structures (et la plupart des autres types de données multi-mots), la seule option est de rendre la structure elle-même (ou le long long, ou le ...) variable :

    extern struct s extern_struct;
extern_struct.field -->
   { volatile struct s *t=&extern_struct; t->field }

    ou

    extern long long extern_ll;
extern_ll -->
  { volatile long long * local_ll=&extern_ll; *local_ll }

    Une troisième méthode pour traiter cette difficulté est d'abandonner 'auto-import' pour le symbole fautif et de le marquer avec "__declspec(dllimport)". Cependant, en pratique, cela nécessite d'utiliser des #defines au moment de la compilation pour indiquer si vous construisez une DLL, construisez du code client qui se liera à la DLL, ou simplement construisez/liez une bibliothèque statique. En faisant le choix entre les différentes méthodes de résolution du problème 'adresse directe avec décalage constant', vous devriez considérer l'usage typique en monde réel :

    Original :

    --foo.h
extern int arr[];
--foo.c
#include "foo.h"
void main(int argc, char **argv){
  printf("%d\n",arr[1]);
}

    Solution 1 :

    --foo.h
extern int arr[];
--foo.c
#include "foo.h"
void main(int argc, char **argv){
  /* Ce contournement est pour win32 et cygwin; ne pas "optimiser" */
  volatile int *parr = arr;
  printf("%d\n",parr[1]);
}

    Solution 2 :

    --foo.h
/* Note: auto-export est supposé (pas de __declspec(dllexport)) */
#if (defined(_WIN32) || defined(__CYGWIN__)) && \
  !(defined(FOO_BUILD_DLL) || defined(FOO_STATIC))
#define FOO_IMPORT __declspec(dllimport)
#else
#define FOO_IMPORT
#endif
extern FOO_IMPORT int arr[];
--foo.c
#include "foo.h"
void main(int argc, char **argv){
  printf("%d\n",arr[1]);
}

    Marquer la sortie comme "OMAGIC" (0407) dans l'en-tête a.out pour indiquer que le segment de texte ne doit pas être protégé en écriture et partagé. Comme les segments de texte et de données sont tous deux lisibles et inscriptibles, le segment de données est alloué immédiatement après le segment de texte. C'est le format le plus ancien pour les programmes exécutables PDP11 et c'est le défaut pour ld sur les systèmes Unix PDP11 depuis le début jusqu'à 2.11BSD.
    -n
    --nmagic
    Marquer la sortie comme "NMAGIC" (0410) dans l'en-tête a.out pour indiquer que lorsque le fichier de sortie est exécuté, la partie texte sera en lecture seule et partageable entre tous les processus exécutant le même fichier. Cela implique de déplacer les zones de données jusqu'à la première limite de page de 8 Ko possible après la fin du texte. Cette option crée un format d'exécutable pur.
    -z
    --imagic
    Marquer la sortie comme "IMAGIC" (0411) dans l'en-tête a.out pour indiquer que lorsque le fichier de sortie est exécuté, les zones de texte et de données du programme seront chargées dans des espaces d'adressage séparés en utilisant la fonctionnalité d'espace d'instructions et de données séparés de l'unité de gestion de mémoire dans les modèles plus grands du PDP11. Cela double l'espace d'adressage disponible pour le programme. Le segment de texte est à nouveau pur, protégé en écriture et partageable. La seule différence dans le format de sortie entre cette option et les autres, en dehors du nombre magique, est que les segments de texte et de données commencent tous deux à l'emplacement 0. L'option -z sélectionnait ce format dans 2.11BSD. Cette option crée un format d'exécutable séparé.
    --no-omagic
    Équivalent à --nmagic pour pdp11-aout.

    Vous pouvez modifier le comportement de ld avec les variables d'environnement "GNUTARGET", "LDEMULATION" et "COLLECT_NO_DEMANGLE".

    "GNUTARGET" détermine le format d'objet des fichiers d'entrée si vous n'utilisez pas -b (ou son synonyme --format). Sa valeur doit être l'un des noms BFD pour un format d'entrée. S'il n'y a pas de "GNUTARGET" dans l'environnement, ld utilise le format naturel de la cible. Si "GNUTARGET" est défini sur "default", alors BFD tente de découvrir le format d'entrée en examinant les fichiers d'entrée binaires ; cette méthode réussit souvent, mais il y a des ambiguïtés potentielles, car il n'y a pas de méthode pour garantir que le nombre magique utilisé pour spécifier les formats de fichiers objet est unique. Cependant, la procédure de configuration pour BFD sur chaque système place le format conventionnel pour ce système en premier dans la liste de recherche, de sorte que les ambiguïtés sont résolues en faveur de la convention.

L'émulation peut affecter divers aspects du comportement de l'éditeur de liens, en particulier le script de l'éditeur de liens par défaut. Vous pouvez lister les émulations disponibles avec les options --verbose ou -V.     NOM

    ld — l'éditeur de liens NDS32 LE ELF

    SYNTAXE

    ld [options] fichier...

    DESCRIPTION

    ld est l'éditeur de liens GNU. Il est utilisé pour lier ensemble un certain nombre de fichiers objets et d'archives afin de créer un exécutable, une image noyau, ou une bibliothèque partagée. Le comportement exact de ld dépend du système cible pour lequel il a été configuré.

    Ce document décrit le comportement de ld tel qu'il est utilisé pour lier des programmes pour l'architecture NDS32 LE. Pour la plupart des options, le comportement est le même que pour les autres architectures.

    OPTIONS

    ld prend en charge un grand nombre d'options. Les plus courantes sont :

    -A nom
    Spécifie le type de machine cible.
    -a
    Relink all objects.
    -d, --relocatable
    Produce a relocatable unadorned output file.
    -e symbole, --entry=symbole
    Use symbole as the name of the object file's entry point.
    -f
    Discard all but the first definition of each symbol.
    -g
    Same as -d.
    -i
    Link interactively.
    -l nom, --library=nom
    Add the archive library nom to the list of libraries to link.
    -m emulation
    Select emulation.
    -N, --nmagic
    Don't use a magic number in the output file.
    -n, --placemagict
    Don't page align any in the output file.
    -o fichier
    Use fichier for the name of the output file.
    -r
    Same as -d.
    -s
    Remove all symbol table information from the output file.
    -t
    Print the list of files being linked.
    -u symbole, --undefined=symbole
    Add symbole to the list of undefined symbols.
    -V, --version
    Display the version number of ld and exit.
    -x
    Output all symbols, not just the dynamic ones.
    -X
    Discard all undefined symbols.
    -Y préfixe
    Set the search prefix for libraries.
    -?, --help
    Display a list of options.

    Il existe également un grand nombre d'options spécifiques à la liaison ELF, qui sont détaillées dans la page man ld(1).

    ENVIRONNEMENT

    Si la variable d'environnement "LD_DEMANGLING" est définie, alors elle sera par défaut à ne pas démancher les symboles. Cette variable d'environnement est utilisée de manière similaire par le programme wrapper de l'éditeur de liens "gcc". La valeur par défaut peut être remplacée par les options --demangle et --no-demangle.
