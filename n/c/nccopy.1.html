NCCOPY(1) UTILITAIRES UNIDATA NCCOPY(1)

NOM

nccopy - Copie un fichier netCDF, changeant optionnellement le format, la compression ou le découpage dans la sortie.

SYNTAXE

nccopy [-k nom_type ] [-code_type] [-d n ] [-s] [-c spec_decoupage ] [-u] [-w] [-[v|V] var1,...] [-[g|G] grp1,...] [-m taille_tampon ] [-h cache_decoupage ] [-e elems_cache ] [-r] [-F spec_filtre ] [-L n ] [-M n ] fichier_entree fichier_sortie

DESCRIPTION

L'utilitaire nccopy copie un fichier netCDF d'entrée dans n'importe quel format supporté vers un fichier netCDF de sortie, le convertissant optionnellement vers n'importe quel format compatible, le compressant ou le réorganisant en segments (rechunking). Par exemple, si compilé avec la bibliothèque netCDF-3, un fichier netCDF classique peut être copié vers un fichier netCDF 64 bits offset, permettant des variables plus grandes. Si compilé avec la bibliothèque netCDF-4, un fichier netCDF classique peut être copié vers un fichier netCDF-4 ou vers un modèle classique netCDF-4, permettant la compression des données, des changements de schéma efficaces, des tailles de variables plus grandes et l'utilisation d'autres fonctionnalités netCDF-4.

Si aucun format de sortie n'est spécifié, avec soit -k nom_type soit -code_type, alors la sortie utilisera le même format que l'entrée, sauf si l'entrée est classique ou 64 bits offset et que le découpage ou la compression est spécifié, auquel cas la sortie sera au format modèle classique netCDF-4. Tenter certains types de conversion de format résultera en une erreur, si la conversion n'est pas possible. Par exemple, une tentative de copie d'un fichier netCDF-4 qui utilise des fonctionnalités du modèle étendu, comme les groupes ou les chaînes de caractères de longueur variable, vers n'importe quel autre type de format netCDF qui utilise le modèle classique résultera en une erreur.

nccopy sert également d'exemple de programme générique netCDF-4, avec sa capacité à lire n'importe quel fichier netCDF valide et à gérer les groupes imbriqués, les chaînes de caractères et les types définis par l'utilisateur, y compris les types composés arbitrairement imbriqués, les types de longueur variable et les données de n'importe quel type netCDF-4 valide.

Si le support DAP a été activé lors de la compilation de nccopy, le nom de fichier peut spécifier une URL DAP. Ceci peut être utilisé pour convertir des données sur des serveurs DAP en fichiers netCDF locaux.

OPTIONS

-k nom_type
Utilise le nom du format pour spécifier le type de fichier à créer et, par inférence, le modèle de données (c'est-à-dire netcdf-3 (classique) ou netcdf-4 (étendu)). Les arguments possibles sont :
'nc3' ou 'classic' => format netCDF classique
'nc6' ou '64-bit offset' => format netCDF 64 bits offset
'nc4' ou 'netCDF-4' => format netCDF-4 (modèle de données étendu)
'nc7' ou 'netCDF-4 classic model' => format modèle classique netCDF-4
Note : Les anciens numéros de format '1', '2', '3', '4', équivalents aux noms de format 'nc3', 'nc6', 'nc4', ou 'nc7' respectivement, sont aussi encore acceptés mais dépréciés, en raison de la confusion facile entre les numéros de format et les noms de format.
[-code_type]
Utilise le code numérique du format (au lieu du nom du format) pour spécifier le type de fichier à créer et, par inférence, le modèle de données (c'est-à-dire netcdf-3 (classique) versus netcdf-4 (étendu)). Les codes numériques sont :
3 => format netCDF classique
6 => format netCDF 64 bits offset
4 => format netCDF-4 (modèle de données étendu)
7 => format modèle classique netCDF-4

Le code numérique "7" est utilisé car "7=3+4", spécifiant le format qui utilise le modèle de données netCDF-3 pour la compatibilité avec le format de stockage netCDF-4 pour la performance. Le mérite revient à NCO pour l'utilisation de ces codes numériques au lieu des anciens numéros de format confusants.

-d n
Pour la sortie netCDF-4, y compris le modèle classique netCDF-4, spécifie le niveau de déflation (niveau de compression) pour la sortie des données de variable. 0 correspond à aucune compression et 9 à la compression maximale, les niveaux de compression plus élevés nécessitant marginalement plus de temps pour compresser ou décompresser que les niveaux inférieurs. En conséquence, la spécification d'un niveau de compression de 0 (via "-d 0") désactive effectivement toute déflation. La compression obtenue peut également dépendre des paramètres de découpage de la sortie. Si cette option est spécifiée pour un fichier d'entrée au format classique ou 64 bits offset, il n'est pas nécessaire de spécifier également que la sortie doit être au modèle classique netCDF-4, car ce sera le format par défaut. Si cette option n'est pas spécifiée et que le fichier d'entrée contient des variables compressées, la compression sera toujours conservée dans la sortie, en utilisant par défaut le même découpage que dans l'entrée.
Notez que nccopy exige que toutes les variables soient compressées avec le même niveau de compression, mais l'API n'a pas une telle restriction. Avec un programme, vous pouvez personnaliser la compression pour chaque variable indépendamment.
-s
Pour la sortie netCDF-4, y compris le modèle classique netCDF-4, spécifie le mélange (shuffling) des octets de données de variable avant la compression ou après la décompression. Le mélange fait référence à l'entrelacement des octets dans un bloc, de sorte que les premiers octets de toutes les valeurs soient contigus en stockage, suivis par tous les deuxièmes octets, et ainsi de suite, ce qui améliore souvent la compression. Cette option est ignorée à moins qu'un niveau de déflation non nul ne soit spécifié. Utiliser -d0 pour spécifier aucune déflation sur les données d'entrée qui ont été compressées et mélangées désactive à la fois la compression et le mélange dans la sortie.
-u
Convertit les dimensions illimitées de l'entrée en dimensions de taille fixe dans la sortie. Cela peut accélérer l'accès variable par variable, mais ralentir l'accès enregistrement par enregistrement à plusieurs variables le long d'une dimension illimitée.
-w
Conserve la sortie en mémoire (comme un fichier netCDF sans disque) jusqu'à la fermeture de la sortie, moment où le fichier de sortie est écrit sur le disque. Cela peut considérablement accélérer des opérations telles que la conversion de dimensions illimitées en dimensions fixes (option -u), le découpage, le ré-découpage ou la compression de l'entrée. Cela nécessite que la mémoire disponible soit suffisamment grande pour contenir le fichier de sortie. Cette option peut fournir une accélération plus importante que l'optimisation soignée des options -m, -h ou -e, et elle est certainement plus simple.
-c spec_decoupage
Pour la sortie netCDF-4, y compris le modèle classique netCDF-4, spécifie le découpage (tiling multidimensionnel) pour les données de variable dans la sortie. Ceci est utile pour spécifier les unités d'accès disque, la compression ou d'autres filtres tels que les sommes de contrôle. Changer le découpage dans un fichier netCDF peut également considérablement accélérer l'accès, en choisissant des formes de blocs appropriées pour les modèles d'accès les plus courants.
L'argument spec_decoupage a plusieurs formes. La première forme est la forme originale, dépréciée, et est une chaîne d'associations séparées par des virgules, chacune spécifiant un nom de dimension, un caractère '/', et optionnellement la longueur de bloc correspondante pour cette dimension. Aucun espace ne doit apparaître dans la chaîne spec_decoupage, sauf éventuellement des espaces échappés qui font partie d'un nom de dimension. Une spec_decoupage nomme au moins une dimension, et peut omettre les dimensions qui ne doivent pas être découpées ou pour lesquelles la longueur de bloc par défaut est souhaitée. Si un nom de dimension est suivi d'un caractère '/' mais sans longueur de bloc subséquente, la longueur réelle de la dimension est supposée. Si vous copiez un fichier au modèle classique vers un fichier de sortie netCDF-4 et que vous ne nommez pas toutes les dimensions dans la spec_decoupage, les dimensions sans nom utiliseront également la longueur réelle de la dimension pour la longueur du bloc. Un exemple de spec_decoupage pour des variables qui utilisent les dimensions 'm' et 'n' pourrait être 'm/100,n/200' pour spécifier des blocs de 100 par 200. Pour voir le découpage résultant de la copie avec une spec_decoupage, utilisez l'option '-s' de ncdump sur le fichier de sortie.
La spec_decoupage '/' qui omet tous les noms de dimensions et les longueurs de bloc correspondantes spécifie qu'aucun découpage ne doit avoir lieu dans la sortie, elle peut donc être utilisée pour défaire le découpage de toutes les variables découpées. Pour voir le découpage résultant de la copie avec une spec_decoupage, utilisez l'option '-s' de ncdump sur le fichier de sortie.
Comme optimisation des E/S, nccopy a un seuil pour la taille minimale des variables non enregistrées qui seront découpées, actuellement 8192 octets. L'option -M peut être utilisée pour remplacer cette valeur.

Si vous avez besoin de personnaliser le découpage pour des variables indépendamment, vous devrez utiliser la deuxième forme de `chunkspec`. Cette deuxième forme de `chunkspec` a cette syntaxe : var:n1,n2,...,nn . Ceci suppose que la variable nommée « var » a un rang n. Le découpage à appliquer à chaque dimension de la variable est spécifié par les valeurs de n1 à nn. Cette deuxième forme de spécification de découpage peut être répétée plusieurs fois pour spécifier le découpage exact pour différentes variables. Si la variable est spécifiée mais qu'aucune taille de bloc n'est spécifiée (c'est-à-dire -c var: ), alors le découpage est désactivé pour cette variable. Si la même variable est spécifiée plusieurs fois, la deuxième spécification et les suivantes sont ignorées. De plus, cette deuxième forme, le découpage par variable, a priorité sur tout découpage par dimension, sauf le cas simple « / ».
La troisième forme du chunkspec a la syntaxe : var:compact ou var:contiguous. Ceci tente explicitement de définir le type de stockage de la variable comme compact ou contigu, respectivement. Ceux-ci peuvent être remplacés si d'autres indicateurs exigent que la variable soit découpée.
-v var1,...
La sortie inclura les valeurs de données pour les variables spécifiées, en plus des déclarations de toutes les dimensions, variables et attributs. Une ou plusieurs variables doivent être spécifiées par leur nom dans la liste délimitée par des virgules suivant cette option. La liste doit être un seul argument pour la commande, elle ne peut donc pas contenir d'espaces ou d'autres caractères d'espacement non échappés. Les variables nommées doivent être des variables netCDF valides dans le fichier d'entrée. Une variable dans un groupe d'un fichier netCDF-4 peut être spécifiée avec un nom de chemin absolu, tel que « /GroupA/GroupA2/var ». L'utilisation d'un nom de chemin relatif tel que 'var' ou « grp/var » spécifie tous les noms de variables correspondants dans le fichier. Par défaut, sans cette option, les valeurs de données de toutes les variables sont incluses dans la sortie.
-V var1,...
La sortie inclura uniquement les variables spécifiées, mais toutes les dimensions et tous les attributs globaux ou de groupe. Une ou plusieurs variables doivent être spécifiées par leur nom dans la liste délimitée par des virgules suivant cette option. La liste doit être un seul argument pour la commande, elle ne peut donc pas contenir d'espaces ou d'autres caractères d'espacement non échappés. Les variables nommées doivent être des variables netCDF valides dans le fichier d'entrée. Une variable dans un groupe d'un fichier netCDF-4 peut être spécifiée avec un nom de chemin absolu, tel que '/GroupA/GroupA2/var'. L'utilisation d'un nom de chemin relatif tel que 'var' ou 'grp/var' spécifie tous les noms de variables correspondants dans le fichier. Par défaut, sans cette option, toutes les variables sont incluses dans la sortie.
-g grp1,...
La sortie inclura les valeurs de données uniquement pour les groupes spécifiés. Un ou plusieurs groupes doivent être spécifiés par leur nom dans la liste délimitée par des virgules suivant cette option. La liste doit être un seul argument pour la commande. Les groupes nommés doivent être des groupes netCDF valides dans le fichier d'entrée. Par défaut, sans cette option, les valeurs de données de tous les groupes sont incluses dans la sortie.
-G grp1,...
La sortie inclura uniquement les groupes spécifiés. Un ou plusieurs groupes doivent être spécifiés par leur nom dans la liste délimitée par des virgules suivant cette option. La liste doit être un seul argument pour la commande. Les groupes nommés doivent être des groupes netCDF valides dans le fichier d'entrée. Par défaut, sans cette option, tous les groupes sont inclus dans la sortie.
-m bufsize
Un nombre entier ou à virgule flottante qui spécifie la taille, en octets, du tampon de copie utilisé pour copier de grandes variables. Un suffixe K, M, G ou T multiplie la taille du tampon de copie par mille, million, milliard ou trillion, respectivement. La valeur par défaut est 5 Mo, mais elle sera augmentée si nécessaire pour contenir au moins un bloc de variables découpées netCDF-4 dans le fichier d'entrée. Vous pourriez vouloir spécifier une valeur supérieure à la valeur par défaut pour copier des fichiers volumineux sur des réseaux à latence élevée. L'utilisation de l'option « -w » peut offrir de meilleures performances si la sortie tient en mémoire.
-h chunk_cache
Pour la sortie netCDF-4, y compris le modèle classique netCDF-4, un nombre entier ou à virgule flottante qui spécifie la taille en octets du cache de blocs alloué pour chaque variable découpée. Ce n'est pas une propriété du fichier, mais simplement un paramètre d'optimisation des performances pour éviter de compresser ou décompresser plusieurs fois les mêmes données lors de la copie et de la modification des formes des blocs. Un suffixe K, M, G ou T multiplie la taille du cache de blocs par mille, million, milliard ou trillion, respectivement. La valeur par défaut est de 4,194304 Mo (ou ce qui a été spécifié pour la constante de configuration CHUNK_CACHE_SIZE lors de la compilation de la bibliothèque netCDF). Idéalement, l'utilitaire nccopy ne devrait accepter qu'une seule taille de tampon mémoire et la diviser de manière optimale entre un tampon de copie et un cache de blocs, mais aucun algorithme général pour calculer la taille optimale du cache de blocs n'a encore été implémenté. L'utilisation de l'option « -w » peut offrir de meilleures performances si la sortie tient en mémoire.
-e cache_elems
Pour la sortie netCDF-4, y compris le modèle classique netCDF-4, spécifie le nombre de blocs que le cache de blocs peut contenir. Un suffixe K, M, G ou T multiplie le nombre de blocs pouvant être stockés dans le cache par mille, million, milliard ou trillion, respectivement. Ce n'est pas une propriété du fichier, mais simplement un paramètre d'optimisation des performances pour éviter de compresser ou décompresser plusieurs fois les mêmes données lors de la copie et de la modification des formes des blocs. La valeur par défaut est 1009 (ou ce qui a été spécifié pour la constante de configuration CHUNK_CACHE_NELEMS lors de la compilation de la bibliothèque netCDF). Idéalement, l'utilitaire nccopy devrait déterminer une valeur optimale pour ce paramètre, mais aucun algorithme général pour calculer le nombre optimal d'éléments de cache de blocs n'a encore été implémenté.
-r
Lit un fichier d'entrée netCDF classique ou offset 64 bits dans un fichier netCDF sans disque en mémoire avant de copier. Nécessite que le fichier d'entrée soit suffisamment petit pour tenir en mémoire. Pour nccopy, cela ne semble pas apporter d'accélération significative, donc cela pourrait ne pas être une option utile.
-L n
Définit le niveau de journalisation ; utilisable uniquement si nccopy prend en charge netCDF-4 (amélioré).
-M n
Définit la taille minimale du bloc ; utilisable uniquement si nccopy prend en charge netCDF-4 (amélioré).
-F filterspec
Pour la sortie netCDF-4, y compris le modèle classique netCDF-4, spécifie un filtre à appliquer à un ensemble spécifié de variables dans la sortie. En règle générale, le filtre est un algorithme de compression/décompression avec un identifiant numérique unique attribué par HDF Group (voir https://support.hdfgroup.org/services/filters.html).
L'argument filterspec a cette forme générale.
fqn1|fqn2...,filterid,param1,param2...paramn ou *,filterid,param1,param2...paramn
Un fqn (nom pleinement qualifié) est le nom d'une variable précédé par ses groupes de confinement avec les noms de groupe séparés par une barre oblique ('/'). Un exemple pourrait être /g1/g2/var. Alternativement, seul le nom de la variable peut être donné s'il se trouve dans le groupe racine : par exemple, var. Des échappements de barre oblique inverse peuvent être utilisés si nécessaire. Une note d'avertissement : le séparateur '|' est un caractère réservé de bash, vous devrez donc probablement mettre la spécification du filtre entre guillemets ou l'échapper autrement.
L'identifiant du filtre est un entier non signé positif représentant l'identifiant attribué par HDFgroup au filtre. Après l'identifiant se trouve une séquence de paramètres définissant le fonctionnement du filtre. Chaque paramètre est un entier non signé de 32 bits.
Ce paramètre peut être répété plusieurs fois avec différents noms de variables.

EXEMPLES

Créez une copie de foo1.nc, un fichier netCDF de n'importe quel type, vers foo2.nc, un fichier netCDF du même type :

nccopy foo1.nc foo2.nc

Notez que la copie ci-dessus ne sera pas aussi rapide qu'avec cp ou un autre utilitaire de copie simple, car le fichier est copié en utilisant uniquement l'API netCDF. Si le fichier d'entrée contient des octets supplémentaires après la fin des données netCDF, ceux-ci ne seront pas copiés, car ils ne sont pas accessibles via l'interface netCDF. Si le fichier d'origine a été généré en mode « Pas de remplissage » de sorte que les valeurs de remplissage ne soient pas stockées pour le remplissage de l'alignement des données, le fichier de sortie peut avoir des octets de remplissage différents.

Convertissez un fichier netCDF-4 modèle classique, compressed.nc, qui utilise la compression, en un fichier netCDF-3 classique classic.nc :

nccopy -k classic compressed.nc classic.nc

Notez que 'nc3' pourrait être utilisé à la place de 'classic'.

Téléchargez la variable 'time_bnds' et ses attributs associés depuis un serveur OPeNDAP et copiez le résultat dans un fichier netCDF nommé 'tb.nc' :

nccopy 'http://test.opendap.org/opendap/data/nc/sst.mnmean.nc.gz?time_bnds' tb.nc

Notez que les URL qui nomment des variables spécifiques en tant qu'arguments de ligne de commande doivent généralement être mises entre guillemets, pour éviter que le shell n'interprète des caractères spéciaux tels que '?'.

Compressez toutes les variables du fichier d'entrée foo.nc, un fichier netCDF de n'importe quel type, vers le fichier de sortie bar.nc :

nccopy -d1 foo.nc bar.nc

Si foo.nc était un fichier netCDF classique ou offset 64 bits, bar.nc sera un fichier netCDF modèle classique netCDF-4, car les variantes de format classiques et offset 64 bits ne prennent pas en charge la compression. Si foo.nc était un fichier netCDF-4 avec certaines variables compressées à différents niveaux de déflation, la sortie sera également un fichier netCDF-4 du même type, mais toutes les variables, y compris celles décompressées dans l'entrée, utiliseront désormais le niveau de déflation 1.

Supposons que les données d'entrée incluent des variables gridded qui utilisent les dimensions temps, lat, lon, avec 1000 temps par 1000 latitudes par 1000 longitudes, et que la dimension temps varie le plus lentement. Supposons également que les utilisateurs souhaitent un accès rapide aux données pour un petit ensemble de points lat-lon pour tous les temps. L'accès aux données pour 1000 temps nécessiterait généralement l'accès à 1000 blocs de disque, ce qui peut être lent.

Réorganiser les données en blocs sur le disque qui ont

all the time dans chaque bloc pour quelques coordonnées lat et lon accélérerait considérablement un tel accès. Pour découper les données dans le fichier d'entrée slow.nc, un fichier netCDF de n'importe quel type, dans le fichier de sortie fast.nc, vous pouvez utiliser ;

nccopy -c time/1000,lat/40,lon/40 slow.nc fast.nc

pour spécifier des blocs de données de 1000 temps, 40 latitudes et 40 longitudes. Si vous aviez suffisamment de mémoire pour contenir le fichier de sortie, vous pourriez accélérer considérablement l'opération de reblocage en créant le fichier de sortie en mémoire avant de l'écrire sur disque à la fermeture (en utilisant l'indicateur -w) :

nccopy -w -c time/1000,lat/40,lon/40 slow.nc fast.nc

Alternativement, on pourrait écrire ceci en utilisant la spécification de découpage alternative et spécifique aux variables, en supposant que temps, lat et lon sont des variables.

nccopy -c time:1000 -c lat:40 -c lon:40 slow.nc fast.nc

Règles de découpage

L'ensemble complet des règles de découpage est capturé ici. En résumé, ces règles préservent toutes les propriétés de découpage du fichier d'entrée. Ces règles s'appliquent uniquement lorsque le format de sortie sélectionné prend en charge le découpage, c'est-à-dire pour les variantes netcdf-4.

La spécification de découpage spécifique à la variable doit être évidente et se traduit directement par l'appel API correspondant "nc_def_var_chunking".

La spécification de découpage par dimension d'origine nécessite une certaine interprétation par nccopy. Les règles suivantes sont appliquées dans l'ordre donné indépendamment pour chaque variable à copier de l'entrée à la sortie. Les règles sont écrites en supposant que nous essayons de déterminer le découpage pour une variable de sortie donnée Vout qui provient d'une variable d'entrée Vin.

1.
S'il n'y a pas d'option '-c' qui s'applique à une variable et que la variable d'entrée correspondante est contiguë ou que l'entrée est une variante netcdf-3, alors laissez la bibliothèque netcdf-c prendre toutes les décisions de découpage.
2.
Pour chaque dimension de Vout explicitement spécifiée sur la ligne de commande (en utilisant l'option '-c'), appliquez la valeur de découpage pour cette dimension, quel que soit le format d'entrée ou les propriétés d'entrée.
3.
Pour les dimensions de Vout non nommées sur la ligne de commande dans une option '-c', préservez les tailles de bloc de la variable d'entrée correspondante, si elle est découpée.
4.
Si Vin est contiguë, et aucune de ses dimensions n'est nommée sur la ligne de commande, et que le découpage n'est pas imposé par d'autres options, alors faites de Vout une variable contiguë.
5.
Si la variable d'entrée est contiguë (ou est une variante netcdf-3) et qu'il n'y a pas d'options nécessitant un découpage, ou si le cas spécial '/' pour l'option '-c' est spécifié, alors la variable de sortie V est marquée comme contiguë.
6.
Cas final par défaut : tout ou partie des tailles de bloc ne sont pas déterminées par la ligne de commande ou la variable d'entrée. Cela inclut les cas d'entrée non découpés tels que netcdf-3, cdf5 et DAP. Dans ces cas, conservez toutes les tailles de bloc déterminées par les règles précédentes, et utilisez la taille complète de la dimension comme valeur par défaut. L'exception concerne les dimensions illimitées, où la valeur par défaut est de 4 mégaoctets.
