ntp-keygen(1) Commandes utilisateur ntp-keygen(1)

NOM

ntp-keygen - Crée une clé d'hôte NTP

SYNTAXE

ntp-keygen [-flags] [-flag [valeur]] [--nom-option[[=| ]valeur]]

Tous les arguments doivent être des options.

DESCRIPTION

Ce programme génère des fichiers de données cryptographiques utilisés par les schémas d'authentification et d'identification de NTPv4. Il peut générer des clés de résumé de message utilisées en cryptographie à clé symétrique et, si la bibliothèque logicielle OpenSSL a été installée, il peut générer des clés d'hôte, des clés de signature, des certificats et des clés et paramètres d'identité utilisés en cryptographie à clé publique Autokey. Ces fichiers sont utilisés pour le chiffrement de cookies, la signature numérique et les algorithmes d'identification par défi/réponse compatibles avec l'infrastructure de sécurité standard d'Internet.

Le fichier de clés symétriques de résumé de message est généré dans un format compatible avec NTPv3. Tous les autres fichiers sont au format ASCII imprimable encodé en PEM, de sorte qu'ils puissent être intégrés comme pièces jointes MIME dans des e-mails à d'autres sites et autorités de certification. Par défaut, les fichiers ne sont pas chiffrés.

Lorsqu'il est utilisé pour générer des clés symétriques de résumé de message, le programme produit un fichier contenant dix chaînes ASCII imprimables pseudo-aléatoires adaptées à l'algorithme de résumé de message MD5 inclus dans la distribution. Si la bibliothèque OpenSSL est installée, elle produit dix chaînes de bits aléatoires supplémentaires encodées en hexadécimal adaptées à SHA1, AES-128-CMAC et d'autres algorithmes de résumé de message. Le fichier de clés symétriques de résumé de message doit être distribué et stocké par des moyens sécurisés au-delà de la portée de NTP lui-même. Outre les clés utilisées pour les associations NTP ordinaires, des clés supplémentaires peuvent être définies comme mots de passe pour les utilitaires ntpq(1) et ntpdc(1).

Les fichiers générés restants sont compatibles avec d'autres applications OpenSSL et d'autres ressources d'infrastructure à clé publique (PKI). Les certificats générés par ce programme sont compatibles avec les pratiques industrielles existantes, bien que certains utilisateurs puissent trouver l'interprétation des champs d'extension X509v3 un peu libérale. Cependant, les clés d'identité ne sont probablement pas compatibles avec autre chose que Autokey.

Certains fichiers utilisés par ce programme sont chiffrés à l'aide d'un mot de passe privé. L'option -p spécifie le mot de passe de lecture pour les fichiers locaux chiffrés et l'option -q le mot de passe d'écriture pour les fichiers chiffrés envoyés aux sites distants. Si aucun mot de passe n'est spécifié, le nom d'hôte renvoyé par la commande Unix hostname(1) , normalement le nom DNS de l'hôte, est utilisé comme mot de passe de lecture par défaut, pour des raisons de commodité. Le programme ntp-keygen demande le mot de passe s'il lit un fichier chiffré et que le mot de passe est manquant ou incorrect. Si un fichier chiffré est lu avec succès et qu'aucun mot de passe d'écriture n'est spécifié, le mot de passe de lecture est utilisé par défaut comme mot de passe d'écriture.

L'option pw de la commande de configuration de crypto ntpd(1) spécifie le mot de passe de lecture pour les fichiers locaux précédemment chiffrés. Il doit correspondre au mot de passe de lecture local utilisé par ce programme. S'il n'est pas spécifié, le nom d'hôte est utilisé. Ainsi, si les fichiers sont générés par ce programme sans mot de passe explicite, ils peuvent être relus par ntpd(1) sans spécifier de mot de passe explicite, mais uniquement sur le même hôte. Si le mot de passe d'écriture utilisé pour le chiffrement est spécifié comme nom d'hôte, ces fichiers peuvent être lus par cet hôte sans mot de passe explicite.

Normalement, les fichiers chiffrés pour chaque hôte sont générés par cet hôte et utilisés uniquement par cet hôte, bien qu'il existe des exceptions comme mentionné plus loin sur cette page. Le fichier de clés symétriques, normalement appelé ntp.keys, est généralement installé dans /etc. D'autres fichiers et liens sont généralement installés dans /usr/local/etc, qui se trouve normalement dans un système de fichiers partagé sur les réseaux montés via NFS et ne peut pas être modifié par les clients partagés. Dans ces cas, les clients NFS peuvent spécifier les fichiers dans un autre répertoire tel que /etc en utilisant la commande de configuration ntpd(1) keysdir.

Ce programme dirige les commentaires et les messages d'erreur vers le flux d'erreurs standard stderr et les fichiers distants vers le flux de sortie standard stdout où ils peuvent être redirigés vers d'autres applications ou vers des fichiers. Les noms utilisés pour les fichiers et les liens générés commencent tous par la chaîne ntpkey* et incluent le type de fichier, l'hôte générateur et la date de création du fichier, comme décrit dans la section Fichiers de données cryptographiques ci-dessous.

Exécution du programme

La manière la plus sûre d'exécuter le programme ntp-keygen est de se connecter directement en tant que root. La procédure recommandée est de se déplacer vers le répertoire keys, généralement /usr/local/etc, puis d'exécuter le programme.

Pour tester et acquérir de l'expérience avec les concepts Autokey, connectez-vous en tant que root et déplacez-vous vers le répertoire keys, généralement /usr/local/etc. Lors de la première exécution, ou si tous les fichiers commençant par ntpkey* ont été supprimés, utilisez la commande ntp-keygen sans arguments pour générer une clé d'hôte RSA par défaut et un fichier de certificat correspondant RSA-MD5 avec une date d'expiration un an plus tard, ce qui est tout ce qui est nécessaire dans de nombreux cas. Le programme génère également des liens symboliques des noms génériques vers les fichiers respectifs. S'il est exécuté à nouveau sans options, le programme utilise les clés et paramètres existants et génère un nouveau fichier de certificat avec une nouvelle date d'expiration un an plus tard, et un lien symbolique.

La clé d'hôte est utilisée pour chiffrer le cookie lorsque cela est nécessaire et doit donc être de type RSA. Par défaut, la clé d'hôte est également la clé de signature utilisée pour chiffrer les signatures. Lorsque nécessaire, une clé de signature différente peut être spécifiée et elle peut être de type RSA ou DSA. Par défaut, le type de résumé de message est MD5, mais toute combinaison de type de clé de signature et de type de résumé de message pris en charge par la bibliothèque OpenSSL peut être spécifiée, y compris ceux utilisant les algorithmes de résumé de message AES128CMAC, MD2, MD5, MDC2, SHA, SHA1 et RIPE160. Cependant, le schéma spécifié dans le certificat doit être compatible avec la clé de signature. Les certificats utilisant n'importe quel algorithme de résumé sont compatibles avec les clés de signature RSA ; cependant, seuls les certificats SHA et SHA1 sont compatibles avec les clés de signature DSA.

Les fichiers de clés/clés publiques privées et les certificats sont compatibles avec d'autres applications OpenSSL et très probablement d'autres bibliothèques également. Les certificats ou les demandes de certificats qui en sont dérivés devraient être compatibles avec les pratiques industrielles existantes, bien que certains utilisateurs puissent trouver l'interprétation des champs d'extension X509v3 quelque peu libérale. Cependant, les fichiers de paramètres d'identification, bien qu'encodés comme les autres fichiers, ne sont probablement pas compatibles avec autre chose que Autokey.

L'exécution du programme autrement qu'en tant que root et l'utilisation de la commande Unix su(1) pour assumer le rôle de root peut ne pas fonctionner correctement, car par défaut la bibliothèque OpenSSL recherche le fichier de semence aléatoire .rnd dans le répertoire personnel de l'utilisateur. Cependant, il ne devrait y avoir qu'un seul .rnd, le plus commodément dans le répertoire root, il est donc pratique de définir la variable d'environnement RANDFILE utilisée par la bibliothèque OpenSSL comme chemin d'accès à .rnd.

L'installation des clés en tant que root peut ne pas fonctionner sur les systèmes de fichiers partagés montés via NFS, car les clients NFS peuvent ne pas être en mesure d'écrire dans le répertoire de clés partagé, même en tant que root. Dans ce cas, les clients NFS peuvent spécifier les fichiers dans un autre répertoire tel que /etc en utilisant la commande de configuration de fichier keysdir ntpd(1) . Il n'est pas nécessaire qu'un client lise les clés et certificats d'autres clients ou serveurs, car ces données sont obtenues automatiquement par le protocole Autokey.

D'ordinaire, les fichiers cryptographiques sont générés par l'hôte qui les utilise, mais il est possible qu'un agent de confiance (TA) génère ces fichiers pour d'autres hôtes ; cependant, dans de tels cas, les fichiers doivent toujours être chiffrés. Le nom du sujet et le nom de confiance par défaut sont le nom d'hôte de l'hôte qui génère les fichiers, mais peuvent être modifiés par des options de ligne de commande. Il est pratique de désigner le nom du propriétaire et le nom de confiance comme champs du sujet et de l'émetteur, respectivement, du certificat. Le nom du propriétaire est également utilisé pour les fichiers de clés d'hôte et de signature, tandis que le nom de confiance est utilisé pour les fichiers d'identité.

Tous les fichiers sont installés par défaut dans le répertoire de clés /usr/local/etc, qui se trouve normalement dans un système de fichiers partagé sur les réseaux montés via NFS. L'emplacement réel du répertoire de clés et de chaque fichier peut être remplacé par une cofiguration.

Normalement, les fichiers contenant des valeurs privées, y compris la clé d'hôte, la clé de signature et les paramètres d'identification, sont autorisés en lecture/écriture uniquement par root ; tandis que les autres contenant des valeurs publiques sont autorisés en lecture par tout le monde. Alternativement, les fichiers contenant des valeurs privées peuvent être chiffrés et ces fichiers autorisés en lecture par tout le monde, ce qui simplifie la maintenance dans les systèmes de fichiers partagés. La garantie d'unicité étant assurée par les extensions de nom de fichier hostname et filestamp, les fichiers d'un serveur NTP et de ses clients dépendants peuvent tous être installés dans le même répertoire partagé.

La pratique recommandée est de conserver les extensions de nom de fichier lors de l'installation d'un fichier et d'installer un lien symbolique des noms génériques spécifiés ailleurs sur cette page vers les fichiers générés. Cela permet d'activer de nouvelles générations de fichiers simplement en modifiant le lien. Si un lien est présent, ntpd(1) suit le lien vers le nom du fichier pour extraire le filestamp. Si un lien n'est pas présent, ntpd(1) extrait le filestamp du fichier lui-même. Cela permet aux clients de vérifier que le fichier et les heures de génération sont toujours à jour. Le programme ntp-keygen utilise la même extension filestamp pour tous les fichiers générés à un moment donné, de sorte que chaque génération est distincte et peut être facilement reconnue dans les données de surveillance.

Exécutez la commande sur autant d'hôtes que nécessaire. Désignez l'un d'entre eux comme hôte de confiance (TH) en utilisant ntp-keygen avec l'option -T et configurez-le pour se synchroniser à partir de serveurs Internet fiables. Configurez ensuite les autres hôtes pour qu'ils se synchronisent directement ou indirectement avec le TH. Une chaîne de certificats est créée lorsque Autokey demande à l'hôte immédiatement ascendant vers le TH de signer son certificat, qui est ensuite fourni à l'hôte immédiatement descendant sur demande. Tous les hôtes du groupe doivent avoir des chaînes de certificats acycriques se terminant sur le TH.

La clé d'hôte est utilisée pour chiffrer le cookie si nécessaire et doit donc être de type RSA. Par défaut, la clé d'hôte est également la clé de signature utilisée pour chiffrer les signatures. Une clé de signature différente peut être assignée en utilisant l'option -S et celle-ci peut être de type RSA ou DSA. Par défaut, le type de résumé de message de signature est MD5, mais toute combinaison de type de clé de signature et de type de résumé de message prise en charge par la bibliothèque OpenSSL peut être spécifiée en utilisant l'option -c.

Les règles stipulent que les médias cryptographiques doivent être générés avec des horodatages de preuve, ce qui signifie que l'hôte doit déjà être synchronisé avant que ce programme ne soit exécuté. Cela crée évidemment un problème de poule et d'œuf lors du démarrage de l'hôte pour la première fois. Par conséquent, l'heure de l'hôte doit être définie par un autre moyen, tel que l'œil et la montre, au moins de sorte que la durée de vie du certificat soit dans l'année en cours. Après cela et lorsque l'hôte est synchronisé avec une source de preuve, le certificat doit être régénéré.

Des informations supplémentaires sur les groupes de confiance et les schémas d'identité se trouvent sur la page « Authentification par clé publique Autokey ».

Les noms de fichiers commencent par le préfixe ntpkey_ et se terminent par le suffixe _hostname. filestamp, où hostname est le nom du propriétaire, généralement la chaîne renvoyée par la commande Unix hostname(1), et filestamp est la seconde NTP à laquelle le fichier a été généré, en chiffres décimaux. Cela garantit l'unicité et simplifie les procédures de maintenance , car tous les fichiers peuvent être rapidement supprimés par une commande rm ntpkey* ou tous les fichiers générés à un moment donné peuvent être supprimés par une commande rm *filestamp . Pour réduire encore le risque de mauvaise configuration, les deux premières lignes d'un fichier contiennent le nom du fichier et la date et l'heure de génération sous forme de commentaires.

Hôtes et Groupes de Confiance

Chaque configuration cryptographique implique la sélection d'un schéma de signature et d'un schéma d'identification, appelé cryptotype, comme expliqué dans la section Options d'authentification de ntp.conf(5). Le cryptotype par défaut utilise le chiffrement RSA, un résumé de message MD5 et l'identification TC. Configurez d'abord un sous-réseau NTP incluant un ou plusieurs hôtes de confiance de faible strate à partir desquels tous les autres hôtes dérivent la synchronisation directement ou indirectement. Les hôtes de confiance ont des certificats de confiance ; tous les autres hôtes ont des certificats non fiables. Ces hôtes construiront automatiquement et dynamiquement des chaînes de certificats faisant autorité vers un ou plusieurs hôtes de confiance. Un groupe de confiance est l'ensemble de tous les hôtes qui ont, directement ou indirectement, une chaîne de certificats se terminant sur un hôte de confiance. La chaîne est définie par des entrées de fichier de configuration statique ou par des moyens dynamiques décrits dans la section Options de Configuration Automatique NTP de ntp.conf(5).

Sur chaque hôte de confiance en tant que root, passez au répertoire des clés. Pour assurer un nouvel ensemble de fichiers, supprimez tous les fichiers ntpkey. Exécutez ensuite ntp-keygen -T pour générer des clés et un certificat de confiance. Sur tous les autres hôtes, faites de même, mais omettez le drapeau -T pour générer des clés et des certificats non fiables. Une fois terminé, démarrez les démons NTP en commençant par la strate la plus basse et en remontant l'arbre. Il peut falloir un certain temps pour qu'Autokey instancie les chaînes de certificats dans tout le sous-réseau, mais la configuration de l'environnement est entièrement automatique.

S'il est nécessaire d'utiliser une clé de signature différente ou un schéma de résumé/signature différent de celui par défaut, exécutez ntp-keygen avec l'option -S type, où type est RSA ou DSA. Le besoin le plus fréquent de le faire est lorsqu'un certificat signé DSA est utilisé. S'il est nécessaire d'utiliser un schéma de certificat différent de celui par défaut, exécutez ntp-keygen avec l'option -c scheme et sélectionnez le scheme selon les besoins. Si ntp-keygen est exécuté à nouveau sans ces options, il génère un nouveau certificat en utilisant le même schéma et la même clé de signature, ainsi qu'un lien symbolique.

Après avoir configuré l'environnement, il est conseillé de mettre à jour les certificats de temps en temps, ne serait-ce que pour prolonger l'intervalle de validité. Exécutez simplement ntp-keygen avec les mêmes drapeaux qu'auparavant pour générer de nouveaux certificats en utilisant les clés existantes, et des liens symboliques. Cependant, si la clé d'hôte ou de signature est modifiée, ntpd(1) doit être redémarré. Lorsque ntpd(1) est redémarré, il charge les nouveaux fichiers et redémarre le protocole. Les autres hôtes dépendants continueront comme d'habitude jusqu'à ce que les signatures soient actualisées, moment auquel le protocole est redémarré.

Schémas d'Identité

Comme mentionné sur la page Authentification Autonome, le schéma d'identité TC par défaut est vulnérable à une attaque de l'homme du milieu. Cependant, il existe des schémas d'identité plus sécurisés, notamment les schémas PC, IFF, GQ et MV décrits ci-dessous. Ces schémas sont basés sur une TA, un ou plusieurs hôtes de confiance et un certain nombre d'hôtes non fiables. Les hôtes de confiance prouvent leur identité en utilisant les valeurs fournies par la TA, tandis que les hôtes restants prouvent leur identité en utilisant les valeurs fournies par un hôte de confiance et des chaînes de certificats se terminant sur cet hôte. Le nom d'un hôte de confiance est également le nom de son sous-groupe et aussi le nom du sujet et de l'émetteur sur son certificat de confiance. La TA n'est pas nécessairement un hôte de confiance au sens où l'entend, mais souvent.

Dans certains schémas, il existe des clés distinctes pour les serveurs et les clients. Un serveur peut également être client d'un autre serveur, mais un client ne peut jamais être serveur pour un autre client. En général, les hôtes de confiance et les hôtes non fiables qui fonctionnent à la fois comme serveur et client ont des fichiers de paramètres qui contiennent des clés serveur et client. Les hôtes qui fonctionnent uniquement comme clients ont des fichiers de clés qui ne contiennent que des clés clients.

Le schéma PC ne prend en charge qu'un seul hôte de confiance dans le groupe. Sur l'hôte de confiance alice, exécutez ntp-keygen -P -p mot_de_passe pour générer le fichier de clé d'hôte ntpkey_ RSA key_alice. filestamp et le fichier de certificat privé de confiance ntpkey_ RSA-MD5 _ cert_alice. filestamp, ainsi que des liens symboliques. Copiez les deux fichiers sur tous les hôtes du groupe ; ils remplacent les fichiers qui seraient générés dans d'autres schémas. Sur chaque hôte bob, installez un lien symbolique du nom générique ntpkey_host_bob vers le fichier de clé d'hôte et un lien symbolique ntpkey_cert_bob vers le fichier de certificat privé. Notez que les liens génériques sont sur bob, mais pointent vers des fichiers générés par l'hôte de confiance alice. Dans ce schéma, il n'est pas possible de rafraîchir les clés ou les certificats sans les copier sur tous les autres hôtes du groupe et recréer les liens symboliques.

Pour le schéma IFF, procédez comme pour le schéma TC pour générer les clés et les certificats pour tous les hôtes du groupe, puis pour chaque hôte de confiance du groupe, générez le fichier de paramètres IFF. Sur l'hôte de confiance alice, exécutez ntp-keygen -T -I -p mot_de_passe pour produire son fichier de paramètres ntpkey_IFFpar_alice.filestamp, qui comprend les clés serveur et client. Copiez ce fichier sur tous les hôtes du groupe qui fonctionnent à la fois comme serveurs et clients et installez un lien symbolique du nom générique ntpkey_iff_alice vers ce fichier. S'il n'y a pas d'hôtes restreints à fonctionner uniquement comme clients, il n'y a rien d'autre à faire. Comme le schéma IFF est indépendant des clés et des certificats, ces fichiers peuvent être actualisés si nécessaire.

Si un client non autorisé possède le fichier de paramètres, il pourrait se faire passer pour un serveur légitime et présenter une menace de l'homme du milieu. Pour éliminer cette menace, les clés du client peuvent être extraites du fichier de paramètres et distribuées à tous les clients restreints. Après avoir généré le fichier de paramètres, sur alice, exécutez ntp-keygen -e et redirigez la sortie vers un fichier ou un programme de messagerie. Copiez ou envoyez ce fichier par e-mail à tous les clients restreints. Sur ces clients, installez un lien symbolique du nom générique ntpkey_iff_alice vers ce fichier. Pour protéger davantage l'intégrité des clés, chaque fichier peut être chiffré avec un mot de passe secret.

Pour le schéma GQ, procédez comme pour le schéma TC pour générer les clés et les certificats pour tous les hôtes du groupe, puis pour chaque hôte de confiance du groupe, générez le fichier de paramètres IFF. Sur l'hôte de confiance alice, exécutez ntp-keygen -T -G -p mot_de_passe pour produire son fichier de paramètres ntpkey_GQpar_alice.filestamp, qui comprend les clés serveur et clie

nt keys. Copiez ce fichier sur tous les hôtes du groupe et installez un lien symbolique du nom générique ntpkey_gq_alice vers ce fichier. De plus, sur chaque hôte bob, installez un lien symbolique du nom générique ntpkey_gq_bob vers ce fichier. Comme le schéma GQ met à jour le fichier de paramètres GQ et le certificat en même temps, les clés et certificats peuvent être régénérés si nécessaire.

Pour le schéma MV, procédez comme pour le schéma TC afin de générer les clés et certificats pour tous les hôtes du groupe. À titre d'illustration, supposons que trish est l'autorité de certification (TA), alice l'un des plusieurs hôtes fiables et bob l'un de ses clients. Sur la TA trish, exécutez ntp-keygen -V n -p motdepasse, où n est le nombre de clés révocables (typiquement 5) pour produire le fichier de paramètres ntpkeys_MVpar_trish.horodatage et les fichiers de clés clients ntpkeys_MVkeyd _ trish. horodatage où d est le numéro de la clé (0 < d < n). Copiez le fichier de paramètres sur alice et installez un lien symbolique du nom générique ntpkey_mv_alice vers ce fichier. Copiez l'un des fichiers de clés clients sur alice pour une distribution ultérieure à ses clients. Peu importe quel fichier de clés client va sur alice, puisqu'ils fonctionnent tous de la même manière. Alice copie le fichier de clés client sur tous ses clients. Sur le client bob, installez un lien symbolique du nom générique ntpkey_mvkey_bob vers le fichier de clés client. Comme le schéma MV est indépendant des clés et certificats, ces fichiers peuvent être rafraîchis si nécessaire.

Options en ligne de commande

-b --imbits= modulus

Définit le nombre de bits dans le modulus d'identité pour la génération des clés d'identité à modulus bits. Le nombre de bits dans le modulus d'identité est de 256 par défaut, mais peut être réglé sur des valeurs allant de 256 à 2048 (32 à 256 octets). Utilisez les grands modulus avec prudence, car cela peut consommer des ressources de calcul considérables et augmente la taille des paquets authentifiés.
-c --certificate= scheme

Sélectionne le schéma de chiffrement de signature de certificat/digest de message. Le schéma peut être l'un des suivants : RSA-MD2, RSA-MD5, RSA-MDC2, RSA-SHA, RSA-SHA1, RSA-RIPEMD160, DSA-SHA, ou DSA-SHA1. Notez que les schémas RSA doivent être utilisés avec une clé de signature RSA et les schémas DSA doivent être utilisés avec une clé de signature DSA. Par défaut, sans cette option, c'est RSA-MD5. Si la compatibilité avec FIPS 140-2 est requise, le schéma DSA-SHA ou DSA-SHA1 doit être utilisé.
-C --cipher= cipher

Sélectionne le chiffrement OpenSSL pour chiffrer les fichiers contenant les clés privées. Par défaut, sans cette option, il s'agit du triple DES à trois clés en mode CBC, des-ede3-cbc. La commande openssl -h fournie avec OpenSSL affiche les chiffrements disponibles.
-d --debug-level

Augmente le niveau de verbosité du débogage. Cette option affiche les données cryptographiques produites dans des panneaux faciles à lire.
-D --set-debug-level= level

Définit la verbosité du débogage sur level. Cette option affiche les données cryptographiques produites dans des panneaux faciles à lire.
-e --id-key

Écrit les paramètres publics IFF ou GQ du fichier de clés client IFFkey ou GQkey précédemment spécifié comme données non chiffrées sur le flux de sortie standard stdout. Ceci est destiné à la distribution automatique de clés par courrier électronique.
-G --gq-params

Génère un nouveau fichier de paramètres et de clés GQ chiffré pour le schéma d'identité Guillou-Quisquater (GQ). Cette option est mutuellement exclusive avec les options -I et -V.
-H --host-key

Génère un nouveau fichier de clé hôte publique/privée RSA chiffré.
-I --iffkey

Génère un nouveau fichier de clé IFF chiffré pour le schéma d'identité Schnorr (IFF). Cette option est mutuellement exclusive avec les options -G et -V.
-i --ident= group

Définit le nom de groupe facultatif Autokey sur group. Ceci est utilisé dans les noms de fichiers de paramètres du schéma d'identité des fichiers de paramètres clients IFF, GQ et MV. Dans ce rôle, la valeur par défaut est le nom de l'hôte si aucun groupe n'est fourni. Le nom de groupe, s'il est spécifié à l'aide de -i ou de -s après un caractère ‘@@’, est également utilisé dans les noms de sujet et d'émetteur de certificat sous la forme host @@ group et doit correspondre au groupe spécifié via crypto ident ou server ident dans le fichier de configuration ntpd.
-l --lifetime= days

Définit la durée de vie pour l'expiration du certificat à days jours. La durée de vie par défaut est d'un an (365 jours).
-m --modulus= bits

Définit le nombre de bits dans le modulus premier pour la génération des fichiers sur bits. Le modulus est de 512 par défaut, mais peut être réglé de 256 à 2048 (32 à 256 octets). Utilisez les grands modulus avec prudence, car cela peut consommer des ressources de calcul considérables et augmente la taille des paquets authentifiés.
-M --md5key

Génère un nouveau fichier de clés symétriques contenant 10 clés MD5, et si OpenSSL est disponible, 10 clés SHA. Une clé MD5 est une chaîne de 20 caractères ASCII imprimables aléatoires, tandis qu'une clé SHA est une chaîne de 40 chiffres hexadécimaux aléatoires. Le fichier peut être modifié à l'aide d'un éditeur de texte pour changer le type de clé ou le contenu de la clé. Cette option est mutuellement exclusive avec toutes les autres options.
-p --password= passwd

Définit le mot de passe pour lire et écrire les fichiers chiffrés sur passwd. Cela inclut les fichiers de clés hôte, de signature et d'identification. Par défaut, le mot de passe est la chaîne renvoyée par la commande Unix hostname.
-P --pvt-cert

Génère un nouveau certificat privé utilisé par le schéma d'identité PC. Par défaut, le programme génère des certificats publics. Remarque : le schéma d'identité PC n'est pas recommandé pour les nouvelles installations.
-q --export-passwd= passwd

Définit le mot de passe pour écrire les fichiers d'identité IFF, GQ et MV chiffrés redirigés vers stdout sur passwd. En effet, ces fichiers sont déchiffrés avec le mot de passe -p, puis chiffrés avec le mot de passe -q. Par défaut, le mot de passe est la chaîne renvoyée par la commande Unix hostname.
-s --subject-key= [host] [@@ group]

Spécifie le nom d'hôte Autokey, où host est le nom d'hôte facultatif et group est le nom de groupe facultatif. Le nom d'hôte, et s'il est fourni, le nom de groupe sont utilisés sous la forme host @@ group comme sujet et émetteur de certificat. La spécification de -s -@@ group est autorisée, et a pour résultat de laisser le nom d'hôte inchangé, comme avec -i group. Le nom de groupe, ou si aucun groupe n'est fourni, le nom d'hôte sont également utilisés dans les noms de fichiers des fichiers de paramètres clients du schéma d'identité IFF, GQ et MV. Si host n'est pas spécifié, le nom d'hôte par défaut est la chaîne renvoyée par la commande Unix hostname.
-S --sign-key= [RSA | DSA]

Génère un nouveau fichier de clé de signature publique/privée chiffré du type spécifié. Par défaut, la clé de signature est la clé hôte et a le même type. Si la compatibilité avec FIPS 140-2 est requise, le type de clé de signature doit être DSA.
-T --trusted-cert

Génère un certificat de confiance. Par défaut, le programme génère un certificat non de confiance.
-V --mv-params nkeys

Génère nkeys clés et paramètres serveur chiffrés pour le schéma d'identité Mu-Varadharajan (MV). Cette option est mutuellement exclusive avec les options -I et -G. Remarque : la prise en charge de cette option est considérée comme en cours de développement.

Fichier de graine aléatoire

Tous les schémas de génération de clés cryptographiquement sûrs doivent disposer de moyens pour randomiser la graine d'entropie utilisée pour initialiser le générateur de nombres pseudo-aléatoires interne utilisé par les routines de bibliothèque. La bibliothèque OpenSSL utilise un fichier de graine aléatoire désigné à cet effet. Le fichier doit être disponible lors du démarrage du démon NTP et du programme ntp-keygen. Si un site prend en charge OpenSSL ou son compagnon OpenSSH, il est très probable que des moyens pour le faire soient déjà disponibles.

Il est important de comprendre que l'entropie doit évoluer pour chaque génération, sinon la séquence de nombres aléatoires serait prévisible. Divers moyens dépendants d'événements externes, tels que les intervalles de frappe au clavier, peuvent être utilisés à cette fin, et certains systèmes disposent de sources d'entropie intégrées. Des moyens appropriés sont décrits dans la documentation logicielle OpenSSL, mais sortent du cadre de cette page.

La graine d'entropie utilisée par la bibliothèque OpenSSL est contenue dans un fichier, généralement appelé .rnd, qui doit être disponible lors du démarrage du démon NTP ou du programme ntp-keygen. Le démon NTP recherchera d'abord le fichier en utilisant le chemin spécifié par la sous-commande randfile de la commande de configuration crypto. S'il n'est pas spécifié de cette manière, ou lors du démarrage du programme ntp-keygen, la bibliothèque OpenSSL recherchera le fichier en utilisant le chemin spécifié par la variable d'environnement RANDFILE dans le répertoire personnel de l'utilisateur, qu'il s'agisse de root ou d'un autre utilisateur. Si la variable d'environnement RANDFILE n'est pas présente, la bibliothèque recherchera le fichier .rnd dans le répertoire personnel de l'utilisateur. Comme le programme ntp-keygen et le démon ntpd(1) doivent s'exécuter en tant que root, l'endroit logique pour placer ce fichier est /.rnd ou /root/.rnd.<

/b> Si le fichier n'est pas disponible ou ne peut pas être écrit, le démon se ferme avec un message dans le journal système et le programme se ferme avec un message d'erreur approprié.

Fichiers de données cryptographiques

Tous les formats de fichier commencent par deux lignes non chiffrées. La première ligne contient le nom du fichier, incluant le nom d'hôte généré et le timestamp du fichier, au format ntpkey_clé _ nom. timestamp_fichier, où clé est le type de clé ou de paramètre, nom est le nom de l'hôte ou du groupe et timestamp_fichier est le timestamp du fichier (secondes NTP) lorsque le fichier a été créé. Par convention, les noms de clé dans les noms de fichiers générés incluent des caractères majuscules et minuscules, tandis que les noms de clé dans les noms de liens générés n'incluent que des caractères minuscules. Le timestamp du fichier n'est pas utilisé dans les noms de liens générés. La deuxième ligne contient le timestamp au format conventionnel Unix date. Les lignes commençant par ‘#’ sont considérées comme des commentaires et ignorées par le programme ntp-keygen et le démon ntpd(1).

Le reste du fichier contient des données cryptographiques, encodées d'abord selon les règles ASN.1, puis chiffrées si nécessaire, et enfin écrites en texte ASCII imprimable encodé en PEM, précédées et suivies de lignes identifiant le contenu MIME.

Le format du fichier de clés symétriques, nommé d'ordinaire ntp.keys, est quelque peu différent des autres fichiers dans un souci de compatibilité descendante. Normalement, le fichier est généré par ce programme, mais il peut être construit et édité à l'aide d'un éditeur de texte ordinaire.

Figure 1. Fichier de clés symétriques typique

La Figure 1 montre un fichier de clés symétriques typique utilisé par l'implémentation de référence. Après l'en-tête, les clés sont entrées une par ligne au format
numéro_clé type clé
où numéro_clé est un entier positif dans la plage 1-65535 ; type est le type de clé pour l'algorithme de résumé de message, qui en l'absence de la bibliothèque OpenSSL doit être MD5 pour désigner l'algorithme de résumé de message MD5 ; si la bibliothèque OpenSSL est installée, le type de clé peut être n'importe quel algorithme de résumé de message pris en charge par cette bibliothèque ; cependant, si la compatibilité avec FIPS 140-2 est requise, le type de clé doit être SHA ou SHA1 ; clé est la clé elle-même, qui est une chaîne ASCII imprimable de 20 caractères ou moins : chaque caractère est choisi parmi les 93 caractères imprimables de la plage 0x21 à 0x7e ( ‘’! à ‘~’ ) à l'exclusion de l'espace et du caractère ‘#’, et se termine par un espace blanc ou un caractère ‘#’. Une clé OpenSSL se compose d'une chaîne ASCII encodée en hexadécimal de 40 caractères, qui est tronquée si nécessaire.

Notez que les clés utilisées par les programmes ntpq(1) et ntpdc(1) sont vérifiées par rapport aux mots de passe demandés par les programmes et saisis manuellement, il est donc généralement approprié de spécifier ces clés au format ASCII lisible par l'homme.

Le programme ntp-keygen génère un fichier de clés symétriques ntpkey_MD5key_nomhote. timestamp_fichier. Comme le fichier contient des clés partagées privées, il ne doit être visible que par root et distribué par des moyens sécurisés aux autres hôtes du sous-réseau. Le démon NTP charge le fichier ntp.keys, donc ntp-keygen installe un lien symbolique de ce nom vers le fichier généré. Par la suite, des liens symboliques similaires doivent être installés manuellement ou automatiquement sur les autres hôtes du sous-réseau. Bien que ce fichier ne soit pas utilisé avec le protocole Autokey Version 2, il est nécessaire pour authentifier certaines commandes de configuration à distance utilisées par les utilitaires ntpq(1) et ntpdc(1).

NAME

ntp-keygen

generate keys and certificates for NTP

SYNOPSIS

ntp-keygen [options]

DESCRIPTION

The ntp-keygen program is used to generate the cryptographic keys and certificates which may be used for the authentication of NTP associations. This includes host keys, signed keys, and trusted certificates. If no options are specified, ntp-keygen generates host keys and certificates.

It is generally recommended to use the ntp-keygen utility to create and maintain cryptographic keys, rather than attempting to use program-generated keys.

OPTIONS

The options are explained below.

-A alg

specify the public-key algorithm for host keys. Valid values are RSA or DSA. The default is RSA.
-c num, --cert-keys=num

generate num certificate keys. This option takes an integer number as its argument.

Generate a number of certificate keys, used for the authentication of NTP associations.

-C alg

specify the public-key algorithm for certificate keys. Valid values are RSA or DSA. The default is RSA.
-g [group], --group [group]

generate group keys. This option takes an optional group name as its argument.

Generate a new group key, obsoleting any that may exist. By default, the program uses the host name as the group name. If a group name is provided, the host name will be appended to the group name and used in the file names of IFF, GQ, and MV client parameter files.

-G num, --gq-keys=num

generate num GQ keys. This option takes an integer number as its argument.

Generate parameters and keys for the Gong-Qian (GQ) identification scheme.

-h [group], --host [group]

generate host keys. This option takes an optional group name as its argument.

Generate a new host key, obsoleting any that may exist. By default, the program uses the host name as the group name. If a group name is provided, the host name will be appended to the group name and used in the file names of IFF, GQ, and MV client parameter files.

-i group, --issuer=group

specify issuer name for host certificate. This option takes a group name as its argument.

Set the issuer name field in the host certificate. By default, the issuer name is the same as the subject name.

-I group, --identity=group

specify identity name for host certificate. This option takes a group name as its argument.

Set the identity name field in the host certificate. By default, the identity name is the same as the host name.

-k num, --keys=num

generate num keys. This option takes an integer number as its argument.

Generate a number of symmetric keys, used for the authentication of NTP associations.

-K alg

specify the public-key algorithm for host keys. Valid values are RSA or DSA. The default is RSA.
-m num, --mv-keys=num

update num MV keys. This option takes an integer number as its argument.

This option has not been fully documented.

-s [group], --subject [group]

specify subject name for host certificate. This option takes an optional group name as its argument.

Set the subject name field in the host certificate. By default, the subject name is the same as the host name. Specifying '-s @@group' is allowed, and results in leaving the host name unchanged while appending @@group to the subject and issuer fields, as with -i group. The group name, or if not provided, the host name are also used in the file names of IFF, GQ, and MV client parameter files.

-S sign, --sign-key=sign

generate sign key (RSA or DSA).

Generate a new sign key of the designated type, obsoleting any that may exist. By default, the program uses the host key as the sign key.

-T, --trusted-cert

trusted certificate (TC scheme).

Generate a trusted certificate. By default, the program generates a non-trusted certificate.

-V num, --mv-params=num

generate <i>num</i> MV parameters. This option takes an integer number as its argument.

Generate parameters and keys for the Mu-Varadharajan (MV) identification scheme.

-v num, --mv-keys=num

update <i>num</i> MV keys. This option takes an integer number as its argument.

This option has not been fully documented.

Display usage information and exit.

Pass the extended usage information through a pager.

Load options from cfgfile. The no-load-opts form will disable the loading of earlier config/rc/ini files. --no-load-opts is handled early, out of order.
