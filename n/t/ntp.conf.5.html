ntp.conf(5) Formats de fichiers ntp.conf(5)

NOM

ntp.conf — Format du fichier de configuration du protocole NTP (Network Time Protocol)

SYNTAXE

ntp.conf [--nom-option] [--nom-option valeur]

Tous les arguments doivent être des options.

DESCRIPTION

Le fichier de configuration ntp.conf est lu au démarrage initial par le démon ntpd(1) afin de spécifier les sources de synchronisation, les modes et autres informations connexes. Généralement, il est installé dans le répertoire /etc, mais il peut être installé ailleurs (voir l'option de ligne de commande du démon -c).

Le format du fichier est similaire à celui des autres fichiers de configuration UNIX. Les commentaires commencent par un caractère ‘#’ et s'étendent jusqu'à la fin de la ligne ; les lignes vides sont ignorées. Les commandes de configuration consistent en un mot-clé initial suivi d'une liste d'arguments, dont certains peuvent être facultatifs, séparés par des espaces. Les commandes ne peuvent pas être étendues sur plusieurs lignes. Les arguments peuvent être des noms d'hôte, des adresses d'hôte écrites sous forme numérique, en quadruplets, des entiers, des nombres à virgule flottante (lorsqu'il s'agit de spécifier des temps en secondes) et des chaînes de caractères.

Le reste de cette page décrit les options de configuration et de contrôle. La page "Notes on Configuring NTP and Setting up an NTP Subnet" (disponible dans la documentation HTML fournie dans /usr/share/doc/ntp) contient une discussion détaillée de ces options. En plus de la discussion des Options de configuration générales, il y a des sections décrivant les fonctionnalités prises en charge suivantes et les options utilisées pour les contrôler :

Support de configuration

Suit une description des commandes de configuration dans NTPv4. Ces commandes ont les mêmes fonctions de base qu'en NTPv3 et, dans certains cas, de nouvelles fonctions et de nouveaux arguments. Il existe deux classes de commandes : les commandes de configuration qui configurent une association persistante avec un serveur distant ou un pair, ou une horloge de référence, et les commandes auxiliaires qui spécifient des variables d'environnement qui contrôlent diverses opérations connexes.

Commandes de configuration

Les différents modes sont déterminés par le mot-clé de la commande et le type de l'adresse IP requise. Les adresses sont classées par type comme suit : (s) un serveur distant ou un pair (classes A, B et C IPv4), (b) l'adresse de diffusion d'une interface locale, (m) une adresse multicast (classe D IPv4), ou (r) une adresse d'horloge de référence (127.127.x.x). Notez que seules les options applicables à chaque commande sont listées ci-dessous. L'utilisation d'options non listées peut ne pas être détectée comme une erreur, mais peut entraîner un comportement étrange, voire destructeur.

Si les extensions de l'interface socket de base pour IPv6 (RFC-2553) sont détectées, le support de la famille d'adresses IPv6 est généré en plus du support par défaut de la famille d'adresses IPv4. Dans certains cas, y compris la liste d'affichage reslist générée par ntpq(1) ou ntpdc(1), les adresses IPv6 sont générées automatiquement. Les adresses IPv6 peuvent être identifiées par la présence de deux-points “:” dans le champ d'adresse. Les adresses IPv6 peuvent être utilisées presque partout où les adresses IPv4 peuvent être utilisées, à l'exception des adresses d'horloge de référence, qui sont toujours IPv4.

Notez que dans les contextes où un nom d'hôte est attendu, un qualificatif -4 précédant le nom d'hôte force la résolution DNS dans l'espace de noms IPv4, tandis qu'un qualificatif -6 force la résolution DNS dans l'espace de noms IPv6. Voir les références IPv6 pour les classes équivalentes pour cette famille d'adresses.

pool adresse [burst] [iburst] [version version] [prefer] [minpoll minpoll] [maxpoll maxpoll] [xmtnonce]

server adresse [key clé | autokey] [burst] [iburst] [version version] [prefer] [minpoll minpoll] [maxpoll maxpoll] [true] [xmtnonce]

peer adresse [key clé | autokey] [version version] [prefer] [minpoll minpoll] [maxpoll maxpoll] [true] [xleave]

broadcast adresse [key clé | autokey] [version version] [prefer] [minpoll minpoll] [ttl ttl] [xleave]

manycastclient adresse [key clé | autokey] [version version] [prefer] [minpoll minpoll] [maxpoll maxpoll] [ttl ttl]

Ces cinq commandes spécifient le nom ou l'adresse du serveur de temps à utiliser et le mode de fonctionnement. L'adresse peut être un nom DNS ou une adresse IP en notation décimale avec points. Des informations supplémentaires sur le comportement des associations se trouvent sur la page "Association Management" (disponible dans la documentation HTML fournie dans /usr/share/doc/ntp).

pool

Pour les adresses de type s, cette commande active une association en mode client persistent avec un certain nombre de serveurs distants. Dans ce mode, l'horloge locale peut être synchronisée avec le serveur distant, mais le serveur distant ne peut jamais être synchronisé avec l'horloge locale.
server

Pour les adresses de type s et r, cette commande active une association en mode client persistent avec le serveur distant spécifié ou l'horloge radio locale. Dans ce mode, l'horloge locale peut être synchronisée avec le serveur distant, mais le serveur distant ne peut jamais être synchronisé avec l'horloge locale. Cette commande ne doit PAS être utilisée pour les adresses de type b ou m.
peer

Pour les adresses de type s (uniquement), cette commande active une association en mode symétrique actif persistent avec le pair distant spécifié. Dans ce mode, l'horloge locale peut être synchronisée avec le pair distant, ou le pair distant peut être synchronisé avec l'horloge locale. Ceci est utile dans un réseau de serveurs où, selon divers scénarios de défaillance, le pair local ou le pair distant peut être une meilleure source de temps. Cette commande ne doit PAS être utilisée pour les adresses de type b, m ou r.
broadcast

Pour les adresses de type b et m (uniquement), cette commande active une association en mode diffusion persistent. Plusieurs commandes peuvent être utilisées pour spécifier plusieurs interfaces de diffusion locales (sous-réseaux) et/ou plusieurs groupes multicast. Notez que les messages de diffusion locaux ne vont qu'à l'interface associée au sous-réseau spécifié, mais les messages multicast vont à toutes les interfaces. En mode diffusion, le serveur local envoie des messages de diffusion périodiques à une population de clients à l'adresse spécifiée, qui est généralement l'adresse de diffusion sur (l'un des) réseau(x) local(aux) ou une adresse multicast attribuée à NTP. L'IANA a attribué l'adresse du groupe multicast IPv4 224.0.1.1 et IPv6 ff05::101 (local au site) exclusivement à NTP, mais d'autres adresses non conflictuelles peuvent être utilisées pour contenir les messages dans les limites administratives. Ordinairement, cette spécification s'applique uniquement au serveur local agissant en tant qu'émetteur ; pour le fonctionnement en tant que client de diffusion, voir le broadcastc
lient ou multicastclient commandes ci-dessous.
manycastclient

Pour les adresses de type m (uniquement), cette commande mobilise une association en mode client manycast pour l'adresse multicast spécifiée. Dans ce cas, une adresse spécifique doit être fournie, qui correspond à l'adresse utilisée sur la commande manycastserver pour les serveurs manycast désignés. L'adresse multicast NTP 224.0.1.1 assignée par l'IANA ne doit PAS être utilisée, à moins que des mesures spécifiques ne soient prises pour éviter de disperser de vastes zones d'Internet avec ces messages et de provoquer une implosion potentiellement massive de réponses chez l'expéditeur. La commande manycastserver spécifie que le serveur local doit fonctionner en mode client avec les serveurs distants qui sont découverts suite à des messages broadcast/multicast. Le client diffuse un message de requête à l'adresse de groupe associée à l'adresse spécifiée address et les serveurs spécifiquement activés répondent à ces messages. Le client sélectionne les serveurs fournissant la meilleure heure et continue comme avec la commande server. Les serveurs restants sont écartés comme s'ils n'avaient jamais été entendus.

Options :

autokey

Tous les paquets envoyés au serveur ou au pair, et reçus de ceux-ci, doivent inclure des champs d'authentification cryptés à l'aide du schéma autokey décrit dans Options d'authentification.
burst

lorsque le serveur est accessible, envoyer une rafale de six paquets au lieu d'un seul. L'espacement des paquets est de 2 s. Ceci est conçu pour améliorer la qualité de la mesure du temps avec la commande server et les adresses s.
iburst

Lorsque le serveur est inaccessible, envoyer une rafale de huit paquets au lieu d'un seul. L'espacement des paquets est de 2 s. Ceci est conçu pour accélérer l'acquisition initiale de la synchronisation avec la commande server et les adresses s, et lorsque ntpd(1) est démarré avec l'option -q .
key key

Tous les paquets envoyés au serveur ou au pair, et reçus de ceux-ci, doivent inclure des champs d'authentification cryptés à l'aide de l'identifiant de clé key spécifié avec des valeurs de 1 à 65535, inclus. Par défaut, aucun champ de cryptage n'est inclus.
minpoll minpoll

maxpoll maxpoll

Ces options spécifient les intervalles de sondage minimum et maximum pour les messages NTP , sous forme de puissance de 2 en secondes. L'intervalle de sondage maximum est par défaut de 10 (1 024 s), mais peut être augmenté par l'option maxpoll jusqu'à une limite supérieure de 17 (36,4 h). L'intervalle de sondage minimum est par défaut de 6 (64 s), mais peut être diminué par l'option minpoll jusqu'à une limite inférieure de 4 (16 s).
noselect

Marque le serveur comme inutilisé, sauf pour l'affichage. Le serveur est rejeté par l'algorithme de sélection.
preempt

Indique que l'association peut être preemptée.
prefer

Marque le serveur comme préféré. Toutes choses étant égales par ailleurs, cet hôte sera choisi pour la synchronisation parmi un ensemble d'hôtes fonctionnant correctement. Voir la page "Règles d'atténuation et le mot-clé prefer" (disponible dans la documentation HTML fournie dans /usr/share/doc/ntp) pour plus d'informations.
true

Marque le serveur comme un truechimer, forçant l'association à survivre toujours aux algorithmes de sélection et de clustering. Cette option ne devrait presque jamais être utilisée que lors du test d'une association.
ttl ttl

Cette option est utilisée uniquement dans les modes serveur broadcast et client manycast. Elle spécifie la durée de vie ttl à utiliser pour les paquets des serveurs broadcast et multicast, et le ttl maximum pour l'anneau d'expansion de recherche avec les paquets client manycast. Le choix de la valeur appropriée, qui est par défaut 127, relève d'un art subtil et doit être coordonné avec l'administrateur réseau.
version version

Spécifie le numéro de version à utiliser pour les paquets NTP sortants. Les versions 1 à 4 sont les choix possibles, la version 4 étant la valeur par défaut.
xleave

Valide uniquement dans les modes peer et broadcast, ce drapeau active le mode entrelacé.
xmtnonce

Valide uniquement pour les modes server et pool, ce drapeau place un nombre aléatoire dans l'horodatage de transmission du paquet.

Commandes Auxiliaires

broadcastclient

Cette commande active la réception des messages de serveur broadcast sur n'importe quelle interface locale (type b) adresse. Lors de la réception d'un message pour la première fois, le client broadcast mesure le délai de propagation nominal du serveur à l'aide d'un bref échange client/serveur avec le serveur, puis entre en mode client broadcast, dans lequel il se synchronise avec les messages broadcast suivants. Notez que, afin d'éviter des perturbations accidentelles ou malveillantes dans ce mode, le serveur et le client doivent fonctionner en utilisant une authentification à clé symétrique ou à clé publique, comme décrit dans Options d'authentification.
manycastserver address ...

Cette commande active la réception des messages client manycast sur les adresses de groupe multicast (type m) spécifiées. Au moins une adresse est requise, mais l'adresse multicast NTP 224.0.1.1 assignée par l'IANA ne doit PAS être utilisée, à moins que des mesures spécifiques ne soient prises pour limiter la portée de la réponse et éviter une implosion potentiellement massive chez l'expéditeur d'origine. Notez que, afin d'éviter des perturbations accidentelles ou malveillantes dans ce mode, le serveur et le client doivent fonctionner en utilisant une authentification à clé symétrique ou à clé publique, comme décrit dans Options d'authentification.
multicastclient address ...

Cette commande active la réception des messages de serveur multicast sur les adresses de groupe multicast (type m) spécifiées. Lors de la réception d'un message pour la première fois, le client multicast mesure le délai de propagation nominal du serveur à l'aide d'un bref échange client/serveur avec le serveur, puis entre en mode client broadcast, dans lequel il se synchronise avec les messages multicast suivants. Notez que, afin d'éviter des perturbations accidentelles ou malveillantes dans ce mode, le serveur et le client doivent fonctionner en utilisant une authentification à clé symétrique ou à clé publique, comme décrit dans Options d'authentification.
mdnstries number

Si nous participons à mDNS, après notre première synchronisation, nous tentons de nous enregistrer auprès du système mDNS. Si cette tentative d'enregistrement échoue, nous essayons à nouveau à intervalles d'une minute jusqu'à mdnstries fois. Après tout, ntpd peut démarrer avant mDNS. La valeur par défaut pour mdnstries est 5.

Support d'Authentification

Le support d'authentification permet au client NTP de vérifier que le serveur est bien connu et de confiance, et non un intrus destiné à usurper accidentellement ou volontairement ce serveur. La spécification NTPv3 RFC-1305 définit un schéma qui fournit une authentification cryptographique des paquets NTP reçus. À l'origine, cela était fait en utilisant l'algorithme DES (Data Encryption Standard) fonctionnant en mode CBC (Cipher Block Chaining), communément appelé DES-CBC. Par la suite, cela a été remplacé par l'algorithme RSA Message Digest 5 (MD5) utilisant une clé privée, communément appelé keyed-MD5. Chaque algorithme calcule un résumé de message, ou hachage unidirectionnel, qui peut être utilisé pour vérifier que le serveur possède le bon identifiant et la bonne clé.

NTPv4 conserve le schéma NTPv3, correctement décrit comme une cryptographie à clé symétrique, et, en outre, fournit un nouveau schéma Autokey basé sur la cryptographie à clé publique. La cryptographie à clé publique est généralement considérée comme plus sécurisée que la cryptographie à clé symétrique, car la sécurité repose sur une valeur privée générée par chaque serveur et jamais révélée. Avec Autokey, toutes les fonctions de distribution et de gestion des clés impliquent uniquement des valeurs publiques, ce qui simplifie considérablement la distribution et le stockage des clés. La gestion des clés publiques est basée sur des certificats X.509, qui peuvent être fournis par des services commerciaux ou produits par des programmes utilitaires de la bibliothèque logicielle OpenSSL ou de la distribution NTPv4.

Bien que les algorithmes de cryptographie à clé symétrique soient inclus dans la distribution NTPv4, la cryptographie à clé publique nécessite que la bibliothèque logicielle OpenSSL soit installée avant de compiler la distribution NTP. Les instructions pour le faire se trouvent sur la page Construction et Installation de la Distribution.

L'authentification est configurée séparément pour chaque association à l'aide des sous-commandes key ou autokey sur les commandes de configuration peer, server, broadcast et manycastclient, comme décrit sur la page Options de configuration. Les options d'authentification décrites ci-dessous spécifient les emplacements des fichiers de clés, si différents de ceux par défaut, quelles clés symétriques sont approuvées et l'intervalle entre les différentes opérations, si différent de celui par défaut.

L'authentification est toujours activée, bien qu'inefficace si elle n'est pas configurée comme décrit ci-dessous. Si un paquet NTP arrive avec un code d'authentification de message (MAC), il n'est accepté que s'il passe toutes les vérifications cryptographiques. Les vérifications nécessitent un identifiant de clé, une valeur de clé et un résumé de message corrects. Si le paquet a été modifié d'une manière ou d'une autre ou rejoué par un intrus, il échouera à une ou plusieurs de ces vérifications et sera rejeté. De plus, le schéma Autokey nécessite un échange de protocole préliminaire pour obtenir le certificat du serveur, vérifier ses informations d'identification et initialiser le protocole.

Le drapeau auth contrôle si les nouvelles associations ou les commandes de configuration distantes nécessitent

re authentification cryptographique. Ce drapeau peut être défini ou réinitialisé par les commandes enable et disable ainsi que par les commandes de configuration à distance envoyées par un programme ntpdc(1) exécuté sur une autre machine. Si ce drapeau est activé, ce qui est le cas par défaut, les nouvelles associations de clients broadcast et passives symétriques et les commandes de configuration à distance doivent être cryptographiquement authentifiées en utilisant soit une clé symétrique, soit la cryptographie à clé publique. Si ce drapeau est désactivé, ces opérations sont effectives même si elles ne sont pas authentifiées cryptographiquement. Il faut comprendre qu'utiliser le drapeau auth désactivé introduit une vulnérabilité significative où un pirate malveillant peut usurper l'identité d'un fausse horloge et sérieusement perturber la synchronisation de l'heure du système. Il est important de noter que ce drapeau n'a aucun autre but que de permettre ou d'interdire une nouvelle association en réponse à de nouveaux messages broadcast et actifs symétriques et aux commandes de configuration à distance et, en particulier, le drapeau n'a aucun effet sur le processus d'authentification lui-même.

Une alternative attrayante là où le support multicast est disponible est le mode manycast, dans lequel les clients recherchent périodiquement des serveurs comme décrit dans la page Automatic NTP Configuration Options. L'authentification cryptographique par clé symétrique ou par clé publique peut être utilisée dans ce mode. L'avantage principal du mode manycast est que les serveurs potentiels n'ont pas besoin d'être configurés à l'avance, car le client les trouve lors du fonctionnement normal, et les fichiers de configuration de tous les clients peuvent être identiques.

Le modèle de sécurité et les schémas de protocole pour la cryptographie à clé symétrique et à clé publique sont résumés ci-dessous ; plus de détails se trouvent dans les notes d'information, les articles et les rapports sur la page du projet NTP liée depuis http://www.ntp.org/.

Cryptographie à Clé Symétrique

La spécification originale RFC-1305 permet à l'une des 65 535 clés possibles, chacune distinguée par un identifiant de clé de 32 bits, d'authentifier une association. Les serveurs et les clients impliqués doivent s'accorder sur la clé et l'identifiant de clé pour authentifier les paquets NTP. Les clés et les informations associées sont spécifiées dans un fichier de clés, généralement appelé ntp.keys, qui doit être distribué et stocké par des moyens sécurisés hors de portée du protocole NTP lui-même. Outre les clés utilisées pour les associations NTP ordinaires, des clés supplémentaires peuvent être utilisées comme mots de passe pour les utilitaires ntpq(1) et ntpdc(1).

Lorsque ntpd(1) est démarré pour la première fois, il lit le fichier de clés spécifié dans la commande de configuration keys et installe les clés dans le cache de clés. Cependant, les clés individuelles doivent être activées avec la commande trusted avant utilisation. Cela permet, par exemple, l'installation de plusieurs lots de clés et l'activation ou la désactivation de chaque lot à distance à l'aide de ntpdc(1). Cela offre également une capacité de révocation qui peut être utilisée si une clé est compromise. La commande requestkey sélectionne la clé utilisée comme mot de passe pour l'utilitaire ntpdc(1), tandis que la commande controlkey sélectionne la clé utilisée comme mot de passe pour l'utilitaire ntpq(1).

Cryptographie à Clé Publique

NTPv4 prend en charge le schéma de clé symétrique NTPv3 original décrit dans RFC-1305 et, en outre, le protocole Autokey, qui est basé sur la cryptographie à clé publique. Le protocole Autokey Version 2 décrit sur la page Autokey Protocol vérifie l'intégrité des paquets à l'aide de résumés de messages MD5 et vérifie la source avec des signatures numériques et n'importe lequel de plusieurs schémas de résumé/signature. Des schémas d'identité optionnels décrits sur la page Identity Schemes et basés sur des algorithmes de défi/réponse cryptographiques sont également disponibles. L'utilisation de tous ces schémas offre une sécurité robuste contre la relecture avec ou sans modification, l'usurpation, l'imposture et la plupart des formes d'attaques par engorgement.

Le protocole Autokey a plusieurs modes de fonctionnement correspondant aux différents modes NTP pris en charge. La plupart des modes utilisent un cookie spécial qui peut être calculé indépendamment par le client et le serveur, mais crypté lors de la transmission. Tous les modes utilisent en outre une variante du schéma S-KEY, dans laquelle une liste de clés pseudo-aléatoires est générée et utilisée dans l'ordre inverse. Ces schémas sont décrits avec un résumé exécutif, l'état actuel, des diapositives d'information et une liste de lecture sur la page Autonomous Authentication.

L'environnement cryptographique spécifique utilisé par les serveurs et clients Autokey est déterminé par un ensemble de fichiers et de liens symboliques générés par le programme ntp-keygen(1ntpkeygenmdoc). Cela comprend un fichier de clés hôte requis, un fichier de certificat requis et un fichier de clés de signature optionnel, un fichier de secondes intercalaires et des fichiers de schéma d'identité. Le schéma de résumé/signature est spécifié dans le certificat X.509 ainsi que la clé de signature correspondante. Il existe plusieurs schémas disponibles dans la bibliothèque logicielle OpenSSL, chacun identifié par une chaîne spécifique telle que md5WithRSAEncryption, qui représente le schéma de résumé de message MD5 avec chiffrement RSA. La distribution NTP actuelle prend en charge tous les schémas de la bibliothèque OpenSSL, y compris ceux basés sur les signatures numériques RSA et DSA.

Les groupes sécurisés NTP peuvent être utilisés pour définir des compartiments cryptographiques et des hiérarchies de sécurité. Il est important que chaque hôte du groupe puisse construire une chaîne de certificats vers un ou plusieurs hôtes de confiance du même groupe. Chaque hôte du groupe exécute le protocole Autokey pour obtenir les certificats de tous les hôtes le long de la chaîne vers un ou plusieurs hôtes de confiance. Cela nécessite que le fichier de configuration de tous les hôtes soit conçu de telle sorte que, même dans des conditions de défaillance prévues, le sous-réseau NTP se forme de manière à ce que chaque hôte du groupe puisse trouver une chaîne vers au moins un hôte de confiance.

Nommage et Adressage

Il est important de noter qu'Autokey n'utilise pas DNS pour résoudre les adresses, car le DNS ne peut pas être entièrement fiable tant que les serveurs de noms n'ont pas synchronisé leurs horloges. Le nom cryptographique utilisé par Autokey pour lier les identifiants d'hôtes et les valeurs cryptographiques doit être indépendant de l'interface, du réseau et de toute autre convention de nommage. Le nom apparaît dans le certificat de l'hôte dans les champs sujet et/ou émetteur, donc la protection contre le compromis du DNS est essentielle.

Par convention, le nom d'un hôte Autokey est le nom renvoyé par l'appel système Unix gethostname(2) ou son équivalent dans d'autres systèmes. Selon le modèle de conception du système, il n'y a pas de disposition pour autoriser des noms alternatifs ou des alias. Cependant, cela ne veut pas dire que les alias DNS, les noms différents pour chaque interface, etc., sont contraints de quelque manière que ce soit.

Il est également important de noter qu'Autokey vérifie l'authenticité à l'aide du nom d'hôte, de l'adresse réseau et des clés publiques, qui sont tous liés ensemble par le protocole spécifiquement pour déjouer les attaques d'usurpation. Pour cette raison, Autokey inclut les adresses IP source et destination dans les calculs de résumé de message et les mêmes adresses doivent donc être disponibles à la fois sur le serveur et sur le client. Pour cette raison, le fonctionnement avec des schémas de traduction d'adresses réseau n'est pas possible. Cela reflète le modèle de sécurité robuste prévu où les serveurs NTP gouvernementaux et d'entreprise sont exploités en dehors des périmètres pare-feu.

Opération

Une combinaison spécifique de schéma d'authentification (aucun, clé symétrique, clé publique) et de schéma d'identité est appelée un cryptotype, bien que toutes les combinaisons ne soient pas compatibles. Il peut y avoir des configurations de gestion où les clients, les serveurs et les pairs ne prennent pas tous en charge les mêmes cryptotypes. Un sous-réseau NTPv4 sécurisé peut être configuré de nombreuses manières tout en gardant à l'esprit les principes expliqués ci-dessus et dans cette section. Notez cependant que certaines combinaisons de cryptotypes peuvent interopérer avec succès, mais peuvent ne pas représenter de bonnes pratiques de sécurité.

Le cryptotype d'une association est déterminé au moment de la mobilisation, soit au moment de la configuration, soit plus tard lorsqu'un message du cryptotype approprié arrive. Lorsqu'il est mobilisé par une commande de configuration server ou peer et qu'aucune sous-commande key ou autokey n'est présente, l'association n'est pas authentifiée ; si la sous-commande key est présente, l'association est authentifiée en utilisant l'ID de clé symétrique spécifié ; si la sous-commande autokey est présente, l'association est authentifiée en utilisant Autokey.

Lorsque plusieurs schémas d'identité sont pris en charge dans le protocole Autokey, le premier échange de messages détermine celui qui est utilisé. Le message de demande du client contient des bits correspondant aux schémas qu'il a disponibles. Le message de réponse du serveur contient des bits correspondant aux schémas qu'il a disponibles. Le serveur et le client font correspondre les bits reçus avec les leurs et sélectionnent un schéma commun.

En suivant le principe que le temps est une valeur publique, un serveur répond à tout paquet client qui correspond à ses capacités de cryptotype. Ainsi, un serveur recevant un paquet non authentifié répondra avec un paquet non authentifié, tandis que le même serveur recevant un paquet d'un cryptotype qu'il prend en charge répondra avec des paquets de ce cryptotype. Cependant, les associations de clients broadcast ou manycast non configurées ou les associations passives symétriques ne seront pas mobilisées à moins que le serveur ne prenne en charge un cryptotype compatible avec le premier paquet reçu. Par défaut, les associations non authentifiées ne seront pas mobilisées, sauf si elles sont remplacées de manière décidément dangereuse.

Certains exemples peuvent aider à réduire la confusion. Le client Alice n'a pas de cryptotype spécifique sélectionné. Le serveur Bob possède à la fois un fichier de clés symétriques et des fichiers Autokey minimaux. Les messages non authentifiés d'Alice arrivent chez Bob, qui répond avec des messages non authentifiés. Cathy possède une copie du fichier de clés symétriques de Bob et a sélectionné l'ID de clé 4 dans les messages à Bob. Bob vérifie le message avec son ID de clé 4. Si c'est la même clé et que le message est vérifié, Bob envoie à Cathy une réponse authentifiée avec cette clé. Si la vérification échoue, Bob envoie à Cathy quelque chose appelé crypto-NAK, qui lui indique que quelque chose s'est mal passé. Elle peut voir les preuves en utilisant le programme ntpq(1).

Denise a créé sa propre clé hôte et son propre certificat. Elle utilise également l'un des schémas d'identité comme Bob. Elle envoie le premier message Autokey à Bob et ils exécutent tous deux les étapes d'authentification et d'identité du protocole. Si tout se passe bien, Den

ise et Bob continuent comme décrit ci-dessus.

Il devrait être clair d'après ce qui précède que Bob peut prendre en charge toutes les filles en même temps, tant qu'il dispose d'une authentification et d'identifiants compatibles. Maintenant, Bob peut agir comme les filles sur les serveurs de son choix ; il peut exécuter plusieurs associations configurées avec plusieurs serveurs différents (ou le même serveur, bien que cela puisse ne pas être utile). Mais, une politique de sécurité judicieuse pourrait exclure certaines combinaisons de cryptotypes ; par exemple, exécuter un schéma d'identité avec un serveur et aucune authentification avec un autre pourrait ne pas être judicieux.

Gestion des clés

Les valeurs cryptographiques utilisées par le protocole Autokey sont incorporées sous forme d'un ensemble de fichiers générés par l'utilitaire ntp-keygen(1ntpkeygenmdoc), y compris les fichiers de clé symétrique, de clé d'hôte et de certificat public, ainsi que les fichiers de clé de signature, les paramètres d'identité et les fichiers leapseconds. Alternativement, les clés d'hôte et de signature ainsi que les fichiers de certificat peuvent être générés par les utilitaires OpenSSL et les certificats peuvent être importés à partir d'autorités de certificat publiques. Notez que les clés symétriques sont nécessaires pour les programmes utilitaires ntpq(1) et ntpdc(1). Les fichiers restants ne sont nécessaires que pour le protocole Autokey.

Les certificats importés d'OpenSSL ou d'autorités de certificat publiques ont certaines limitations. Le certificat doit être en syntaxe ASN.1, au format X.509 Version 3 et encodé en PEM, qui est le même format utilisé par OpenSSL. La longueur totale du certificat encodé en ASN.1 ne doit pas dépasser 1024 octets. Le champ du nom distinctif du sujet (CN) est le nom de domaine qualifié complet de l'hôte sur lequel il est utilisé ; les autres champs du sujet sont ignorés. Les champs d'extension du certificat ne doivent contenir ni d'identifiant de clé du sujet ni d'identifiant de clé de l'émetteur ; cependant, un champ d'utilisation étendue de clé pour un hôte de confiance doit contenir la valeur trustRoot;. Les autres champs d'extension sont ignorés.

Commandes d'authentification

autokey [logsec]

Spécifie l'intervalle entre les régénérations de la liste des clés de session utilisée avec le protocole Autokey. Notez que la taille de la liste des clés pour chaque association dépend de cet intervalle et de l'intervalle de sondage actuel. La valeur par défaut est 12 (4096 s ou environ 1,1 heure). Pour les intervalles de sondage supérieurs à l'intervalle spécifié, une liste de clés de session avec une seule entrée sera régénérée pour chaque message envoyé.
controlkey key

Spécifie l'identifiant de clé à utiliser avec l'utilitaire ntpq(1), qui utilise le protocole standard défini dans RFC-1305. L'argument key est l'identifiant de clé d'une clé de confiance, où la valeur peut être comprise dans la plage de 1 à 65 535, inclusivement.

Cette commande nécessite la bibliothèque OpenSSL. Elle active la cryptographie à clé publique, sélectionne le schéma de chiffrement du résumé de message et de la signature, et charge les valeurs privées et publiques requises décrites ci-dessus. Si un ou plusieurs fichiers ne sont pas spécifiés, les noms par défaut sont utilisés comme décrit ci-dessus. Sauf si le chemin complet et le nom du fichier sont spécifiés, l'emplacement d'un fichier est relatif au répertoire des clés spécifié dans la commande keysdir ou par défaut /usr/local/etc. Voici les sous-commandes :
cert file

Spécifie l'emplacement du fichier de paramètres GQ optionnel. Cela remplace le lien ntpkey_gq_hostname dans le répertoire des clés.
host file

Spécifie l'emplacement du fichier de clé d'hôte requis. Cela remplace le lien ntpkey_key_hostname dans le répertoire des clés.
iffpar file

Spécifie l'emplacement du fichier de paramètres IFF optionnel. Cela remplace le lien ntpkey_iff_hostname dans le répertoire des clés.
leap file

Spécifie l'emplacement du fichier de seconde intercalaire optionnel. Cela remplace le lien ntpkey_leap dans le répertoire des clés.
mvpar file

Spécifie l'emplacement du fichier de paramètres MV optionnel. Cela remplace le lien ntpkey_mv_hostname dans le répertoire des clés.
pw password

Spécifie le mot de passe pour déchiffrer les fichiers contenant des clés privées et des paramètres d'identité. Ceci n'est requis que si ces fichiers ont été chiffrés.
randfile file

Spécifie l'emplacement du fichier de semence aléatoire utilisé par la bibliothèque OpenSSL. Les valeurs par défaut sont décrites dans le texte principal ci-dessus.

Spécifie le chemin complet et l'emplacement du fichier de clés MD5 contenant les clés et les identifiants de clé utilisés par ntpd(1), ntpq(1) et ntpdc(1) lors de l'opération avec la cryptographie à clé symétrique. Ceci est la même opération que l'option de ligne de commande -k.
keysdir path

Cette commande spécifie le chemin du répertoire par défaut pour les clés, paramètres et certificats cryptographiques. La valeur par défaut est /usr/local/etc/.
requestkey key

Spécifie l'identifiant de clé à utiliser avec l'utilitaire ntpdc(1), qui utilise un protocole propriétaire spécifique à cette implémentation de ntpd(1). L'argument key est un identifiant de clé pour la clé de confiance, où la valeur peut être comprise dans la plage de 1 à 65 535, inclusivement.
revoke logsec

Spécifie l'intervalle entre les ré-aléatorisations de certaines valeurs cryptographiques utilisées par le schéma Autokey, sous forme de puissance de 2 en secondes. Ces valeurs doivent être mises à jour fréquemment afin de déjouer les attaques par force brute sur les algorithmes du schéma ; cependant, la mise à jour de certaines valeurs est une opération relativement coûteuse. L'intervalle par défaut est 16 (65 536 s ou environ 18 heures). Pour les intervalles de sondage supérieurs à l'intervalle spécifié, les valeurs seront mises à jour pour chaque message envoyé.
trustedkey key ...

Spécifie les identifiants de clés qui sont de confiance pour l'authentification des pairs avec la cryptographie à clé symétrique, ainsi que les clés utilisées par les programmes ntpq(1) et ntpdc(1). Les procédures d'authentification exigent que les serveurs locaux et distants partagent la même clé et le même identifiant de clé à cet effet, bien que des clés différentes puissent être utilisées avec différents serveurs. Les arguments key sont des entiers non signés de 32 bits avec des valeurs allant de 1 à 65 535.

Codes d'erreur

Les codes d'erreur suivants sont rapportés via le mécanisme de piégeage du protocole de contrôle et de surveillance NTP.

101

(format ou longueur de champ incorrect) Le paquet a une version, une longueur ou un format invalide.
102

(horodatage incorrect) L'horodatage du paquet est le même ou plus ancien que le dernier reçu. Cela pourrait être dû à une relecture ou à un saut de temps de l'horloge du serveur.
103

(filestamp incorrect) Le filestamp du paquet est le même ou plus ancien que le dernier reçu. Cela pourrait être dû à une relecture ou à une erreur de génération du fichier de clés.
104

(clé publique incorrecte ou manquante) La clé publique est manquante, a un format incorrect ou est d'un type non pris en charge.
105

(type de résumé non pris en charge) Le serveur requiert un schéma de résumé/signature non pris en charge.
106

(types de résumé non concordants) Non utilisé.
107

(longueur de signature incorrecte) La longueur de la signature ne correspond pas à la clé publique actuelle.
108

(signature non vérifiée) Le message échoue à la vérification de la signature. Il pourrait être invalide ou signé avec une clé privée différente.
109

(certificat non vérifié) Le certificat est invalide ou signé avec la mauvaise clé.
110

(certificat non vérifié) Le certificat n'est pas encore valide ou a expiré, ou la signature n'a pas pu être vérifiée.
111

(cookie incorrect ou manquant) Le cookie est manquant, corrompu ou invalide.
112

(table de secondes intercalaires incorrecte ou manquante) La table des secondes intercalaires est manquante, corrompue ou invalide.
113

(certificat incorrect ou manquant) Le certificat est manquant, corrompu ou invalide.
114

(identité incorrecte ou manquante) La clé d'identité est manquante, corrompue ou invalide.

Configure la définition du nom de fichier de génération. Les ensembles de fichiers de génération offrent un moyen de gérer des fichiers qui augmentent continuellement pendant la durée de vie d'un serveur. Les statistiques du serveur sont un exemple typique de tels fichiers. Les ensembles de fichiers de génération fournissent un accès à un ensemble de fichiers utilisés pour stocker les données réelles. À tout moment, un seul élément de l'ensemble est en cours d'écriture. Le type spécifié indique quand et comment les données seront dirigées vers un nouvel élément de l'ensemble. De cette manière, les informations stockées dans les éléments d'un ensemble de fichiers actuellement inutilisés sont disponibles pour les opérations administratives sans risquer de perturber le fonctionnement de ntpd. (Le plus important : ils peuvent être supprimés pour libérer de l'espace pour les nouvelles données produites.)

Notez que cette commande peut être envoyée depuis le programme ntpdc(1) en cours d'exécution à distance.

name

C'est le type des enregistrements de statistiques, tel qu'indiqué dans la commande statistics.

C'est le nom du fichier pour les enregistrements de statistiques. Les noms de fichiers des membres de l'ensemble sont construits à partir de trois éléments concaténés : prefix, filename et suffix :
prefix

C'est un chemin de nom de fichier constant. Il n'est pas sujet à des modifications via l'option filegen. Il est défini par le serveur, généralement spécifié comme une constante de compilation. Il peut toutefois être configurable pour des ensembles de fichiers générés individuels via d'autres commandes. Par exemple, le préfixe utilisé avec les générations loopstats et peerstats peut être configuré à l'aide de l'option statsdir expliquée ci-dessus.
filename

Cette chaîne est directement concaténée au préfixe mentionné ci-dessus (aucun '/' intermédiaire). Elle peut être modifiée à l'aide de l'argument file de l'instruction filegen. Aucun élément .. n'est autorisé dans ce composant pour empêcher les noms de fichiers de faire référence à des parties extérieures à la hiérarchie du système de fichiers désignée par prefix.
suffix

Cette partie reflète les éléments individuels d'un ensemble de fichiers. Elle est générée selon le type d'un ensemble de fichiers.
type nom_du_type

Un ensemble de fichiers générés est caractérisé par son type. Les types suivants sont pris en charge :
none

L'ensemble de fichiers est en réalité un seul fichier ordinaire.
pid

Un élément de l'ensemble de fichiers est utilisé par incarnation d'un serveur ntpd. Ce type n'effectue aucune modification sur les membres de l'ensemble de fichiers pendant l'exécution, mais il offre un moyen simple de séparer les fichiers appartenant à différentes incarnations du serveur ntpd(1). Le nom du membre du fichier est construit en ajoutant un '.
time | date

One generation file set element is created per time interval. The file generation set element suffix consists of a dot, the letter t, and the decimal representation of the server's time value. This is created by concatenating prefix and filename strings, and appending the decimal representation of the process ID of the ntpd(1) server process.
day

Un élément de jeu de fichiers généré par jour. Un jour est défini comme la période entre 00:00 et 24:00 UTC. Le suffixe du membre du jeu de fichiers se compose d'un ‘.’ et d'une spécification de jour sous la forme AAAA MMJJ. AAAA est un numéro d'année à 4 chiffres (par exemple, 1992). MM est un numéro de mois à deux chiffres. JJ est un numéro de jour à deux chiffres. Ainsi, toutes les informations écrites le 10 décembre 1992 se retrouveraient dans un fichier nommé prefix filename.19921210.
week

Tout membre d'un jeu de fichiers contient des données relatives à une certaine semaine de l'année. Le terme semaine est défini en calculant le jour de l'année modulo 7. Les éléments d'un tel jeu de fichiers de génération sont distingués en ajoutant le suffixe suivant au nom de base du jeu de fichiers : un point, un numéro d'année à 4 chiffres, la lettre W et un numéro de semaine à 2 chiffres. Par exemple, les informations du 10 janvier 1992 se retrouveraient dans un fichier avec le suffixe
month

Un élément de jeu de fichiers de génération est généré par mois. Le suffixe du nom de fichier se compose d'un point, d'un numéro d'année à 4 chiffres et d'un mois à 2 chiffres.
year

Un élément de fichier de génération est généré par an. Le suffixe du nom de fichier se compose d'un point et d'un numéro d'année à 4 chiffres.
age

Ce type de jeu de fichiers de génération change pour un nouvel élément du jeu de fichiers toutes les 24 heures de fonctionnement du serveur. Le suffixe du nom de fichier se compose d'un point, de la lettre a et d'un nombre à 8 chiffres. Ce nombre est considéré comme le nombre de secondes pendant lesquelles le serveur fonctionne au début de la période de 24 heures correspondante. Les informations ne sont écrites dans un jeu de fichiers qu'en spécifiant enable ; la sortie est empêchée en spécifiant disable.
link | nolink

Il est pratique de pouvoir accéder à l'élément courant d'un jeu de fichiers par un nom fixe. Cette fonctionnalité est activée en spécifiant link et désactivée en utilisant nolink. Si link est spécifié, un lien physique du fichier courant du jeu de fichiers vers un fichier sans suffixe est créé. Lorsqu'il existe déjà un fichier portant ce nom et que le nombre de liens de ce fichier est de un, il est renommé en ajoutant un point, la lettre C et le pid du processus serveur ntpd(1). Lorsque le nombre de liens est supérieur à un, le fichier est désolidarisé. Ceci permet d'accéder au fichier courant par un nom constant.
enable | disable

Active ou désactive la fonction d'enregistrement.

Support de contrôle d'accès

Le démon ntpd(1) implémente une liste de restriction générale basée sur adresse/masque. La liste contient des entrées adresse/correspondance triées d'abord par ordre croissant des valeurs d'adresses, puis par ordre croissant des valeurs de masques. Une correspondance se produit lorsque le ET binaire du masque et de l'adresse source du paquet est égal au ET binaire du masque et de l'adresse dans la liste. La liste est parcourue dans l'ordre, la dernière correspondance trouvée définissant les drapeaux de restriction associés à l'entrée. Des informations et exemples supplémentaires peuvent être trouvés sur la page "Notes on Configuring NTP and Setting up a NTP Subnet" (disponible dans la documentation HTML fournie dans /usr/share/doc/ntp).

Le mécanisme de restriction a été implémenté conformément aux politiques d'accès des serveurs de temps du réseau dorsal NSFnet d'origine. Plus tard, le mécanisme a été étendu pour contrer les attaques cryptographiques et de ralentissement. Bien que ce mécanisme puisse être utile pour empêcher les clients indésirables, défectueux ou malveillants de surcharger des serveurs innocents, il ne doit pas être considéré comme une alternative aux mécanismes d'authentification NTP. Les restrictions basées sur l'adresse source peuvent être facilement contournées par un pirate déterminé.

Les clients peuvent se voir refuser le service car ils sont explicitement inclus dans la liste de restriction créée par la commande restrict ou implicitement à la suite de violations cryptographiques ou de limites de débit. Les violations cryptographiques incluent l'échec de la vérification du certificat ou de l'identité ; les violations de limites de débit résultent généralement d'implémentations NTP défectueuses qui envoient des paquets à des débits excessifs. Certaines violations entraînent le refus de service uniquement pour le paquet fautif, d'autres entraînent le refus de service pour une période limitée et d'autres encore entraînent le refus de service pour une période indéfinie. Lorsqu'un client ou un réseau se voit refuser l'accès pour une période indéfinie, la seule façon actuelle de lever les restrictions est de redémarrer le serveur.

Le paquet Kiss-of-Death

Normalement, les paquets auxquels le service est refusé sont simplement ignorés sans autre action que l'incrémentation des compteurs de statistiques. Parfois, une réponse plus proactive est nécessaire, comme un message du serveur demandant explicitement au client d'arrêter d'envoyer et de laisser un message à l'opérateur du système. Un format de paquet spécial a été créé à cette fin, appelé paquet "kiss-of-death" (KoD). Les paquets KoD ont les bits de saut non synchronisés et le stratum défini à zéro, et le champ identifiant de référence est défini sur un code ASCII de quatre octets. Si le drapeau noserve ou notrust de l'entrée de liste de restriction correspondante est défini, le code est "DENY" ; si le drapeau limited est défini et que la limite de débit est dépassée, le code est "RATE". Enfin, si une violation cryptographique se produit, le code est "CRYP".

Un client recevant un KoD effectue un ensemble de vérifications de validité pour minimiser les risques de sécurité, puis met à jour les variables de pair de stratum et d'identifiant de référence, définit le bit d'accès refusé (TEST4) dans la variable flash du pair et envoie un message au log. Tant que le bit TEST4 est défini, le client n'enverra plus de paquets au serveur. La seule façon actuelle de sortir de cette condition est de redémarrer le protocole côté client et côté serveur. Cela se produit automatiquement côté client lorsque l'association expire. Cela ne se produira côté serveur que si l'opérateur du serveur coopère.

Commandes de contrôle d'accès

discard [average avg] [minimum min] [monitor prob]

Définit les paramètres du mécanisme limited qui protège le serveur contre les abus des clients. La sous-commande average spécifie l'espacement moyen minimum des paquets en secondes log2, avec une valeur par défaut de 3 (8s), tandis que la sous-commande minimum spécifie l'espacement minimum des paquets en secondes, avec une valeur par défaut de 2. Les paquets qui violent ces minima sont ignorés et un paquet kiss-o'-death est renvoyé si activé. La sous-commande monitor spécifie indirectement la probabilité de remplacer la plus ancienne entrée de la liste des requêtes récentes (MRU - Most Recently Used) utilisée pour appliquer les contrôles de débit, lorsque cette liste est à sa taille maximale. La probabilité de remplacer la plus ancienne entrée est l'âge de cette entrée en secondes divisé par la valeur de monitor, par défaut 3000. Par exemple, si la plus ancienne entrée de la liste MRU représente une requête il y a 300 secondes, par défaut la probabilité de la remplacer par une entrée représentant la requête du client en cours de traitement est de 10%. Inversement, si la plus ancienne entrée a plus de 3000 secondes, la probabilité est de 100%.
restrict address [mask mask] [ippeerlimit int] [flag ...]

L'argument address, exprimé sous forme numérique, est l'adresse d'un hôte ou d'un réseau. Alternativement, l'argument address peut être un nom d'hôte valide. Lorsqu'un nom d'hôte est fourni, une entrée de restriction est créée pour chaque adresse à laquelle le nom d'hôte se résout, et tout mask fourni est ignoré et un masque d'hôte individuel est utilisé pour chaque entrée. L'argument mask, exprimé sous forme numérique, a pour valeur par défaut tous les bits allumés, ce qui signifie que l'address est traitée comme l'adresse d'un hôte individuel. Une entrée par défaut avec l'adresse et le masque tous à zéro est toujours incluse et est toujours la première entrée de la liste. Notez que la chaîne de texte default, sans option de masque, peut être utilisée pour indiquer l'entrée par défaut. La directive ippeerlimit limite le nombre de requêtes de pair pour chaque IP à int, où une valeur de -1 signifie "illimité", la valeur par défaut actuelle. Une valeur de 0 signifie "aucun". Il y aurait généralement au plus 1 requête de pair par IP, mais si les requêtes de pair distantes sont derrière un proxy, il pourrait bien y en avoir plus d'une par IP. Dans l'implémentation actuelle, flag restreint toujours l'accès, c'est-à-dire qu'une entrée sans drapeau indique que l'accès libre au serveur doit être accordé. Les drapeaux ne sont pas orthogonaux, en ce sens que des drapeaux plus restrictifs rendent souvent les moins restrictifs redondants. Les drapeaux peuvent généralement être classés en deux catégories, ceux qui restreignent le service temporel et ceux qui restreignent les requêtes d'information et les tentatives de reconfiguration du serveur en temps réel. Un ou plusieurs des drapeaux suivants peuvent être spécifiés :
ignore

Refuse les paquets de toutes sortes, y compris les requêtes ntpq(1) et ntpdc(1).
kod

Si ce drapeau est défini lors d'une violation de débit, un paquet kiss-o'-death (KoD) est parfois envoyé. Les paquets KoD sont limités à un par espacement inter-paquets moyen minimum, défini par discard average (valeur par défaut 8s). Sinon, aucune réponse n'est envoyée.
limited

Refuse le service si l'espacement des paquets viole les limites inférieures spécifiées dans la commande discard. Un historique des clients est conservé à l'aide de la capacité de surveillance de ntpd(1). Ainsi, la surveillance est toujours active tant qu'il existe une entrée de restriction avec le drapeau limited activé.
lowpriotrap

Déclare que les pièges (traps) définis par les hôtes correspondants sont de priorité basse. Le nombre de pièges qu'un serveur peut maintenir est limité (la limite actuelle est de 3). Les pièges sont généralement attribués selon le principe du premier arrivé, premier servi, les demandeurs de pièges ultérieurs se voyant refuser le service. Ce drapeau modifie l'algorithme d'attribution en permettant aux pièges de priorité basse d'être remplacés par des demandes ultérieures de pièges de priorité normale.
noepeer

Refuse les demandes de pair éphémère, même si elles proviennent d'une source authentifiée. Notez que la capacité à utiliser une clé symétrique pour l'authentification peut être restreinte à une ou plusieurs adresses IP ou sous-réseaux via le troisième champ du fichier ntp.keys. Cette restriction n'est pas activée par défaut, afin de maintenir la compatibilité ascendante. Il faut s'attendre à ce que noepeer devienne la valeur par défaut dans ntp-4.4.
nomodify

Refuse les requêtes ntpq(1) et ntpdc(1) qui tentent de modifier l'état du serveur (c'est-à-dire, la reconfiguration à chaud). Les requêtes qui renvoient des informations sont autorisées.
noquery

Refuse les requêtes ntpq(1) et ntpdc(1). Le service de temps n'est pas affecté.
nopeer

Refuse les paquets non authentifiés qui entraînement la mobilisation d'une nouvelle association. Cela inclut les paquets de diffusion (broadcast) et actifs symétriques lorsqu'une association configurée n'existe pas. Cela inclut également les associations pool. Ainsi, si vous souhaitez utiliser des serveurs d'une directive pool et utiliser également nopeer par défaut, vous voudrez également une ligne restrict source ... qui n'inclut *pas* la directive nopeer.
noserve

Refuse tous les paquets sauf les requêtes ntpq(1) et ntpdc(1).
notrap

Refuse de fournir le service de piège de message de contrôle mode 6 aux hôtes correspondants. Le service de piège est un sous-système du protocole de message de contrôle ntpq(1) qui est destiné à être utilisé par les programmes de journalisation d'événements à distance.
notrust

Refuse le service, sauf si le paquet est authentifié cryptographiquement.
ntpport

Ceci est en fait un modificateur d'algorithme de correspondance, plutôt qu'un drapeau de restriction. Sa présence provoque la correspondance de l'entrée de restriction uniquement si le port source dans le paquet est le port UDP standard NTP (123). Il peut y avoir deux entrées de restriction avec la même adresse IP si l'une spécifie ntpport et l'autre non. L'entrée ntpport est considérée comme plus spécifique et est triée plus tard dans la liste.
serverresponse fuzz

Lors de la réponse aux requêtes serveur, brouille les bits de poids faible de la reftime.
version

Refuse les paquets qui ne correspondent pas à la version NTP actuelle.

Des entrées de restriction par défaut avec les drapeaux ignore, interface, ntpport, pour chacune des adresses IP d'interface de l'hôte local sont insérées dans la table au démarrage pour empêcher ntpd de tenter de se synchroniser avec lui-même, par exemple avec manycastclient lorsque manycast est également spécifié avec la même adresse multicast. Une entrée par défaut est également toujours présente, bien que si elle n'est pas configurée autrement ; aucun drapeau n'est associé à l'entrée par défaut (c'est-à-dire que tout ce qui n'est pas votre propre serveur NTP n'est pas restreint).

delrestrict [source] adresse

Supprime une restriction précédemment définie. Ceci est utile pour la configuration à chaud via ntpq(1). source est spécifié, une restriction dynamique créée à partir du restrict source modèle au moment où une association a été ajoutée est supprimée. Sans source, une restriction statique est supprimée.

Options de configuration automatique NTP

Manycasting

Le manycasting est un paradigme de découverte et de configuration automatique nouveau dans NTPv4. Il est destiné à permettre à un client multicast de sonder le voisinage réseau proche pour trouver des serveurs manycast coopératifs, de les valider par des moyens cryptographiques et d'évaluer leurs valeurs de temps par rapport à d'autres serveurs qui pourraient se trouver à proximité. Le résultat escompté est que chaque client manycast mobilise des associations client avec un certain nombre des "meilleurs" serveurs manycast proches, tout en se reconfigurant automatiquement pour maintenir ce nombre de serveurs en cas de défaillance de l'un d'eux.

Notez que le paradigme manycast ne coïncide pas avec le paradigme anycast décrit dans la RFC-1546, qui est conçu pour trouver un seul serveur parmi un groupe de serveurs fournissant le même service. Le paradigme manycast est conçu pour trouver une pluralité de serveurs redondants satisfaisant des critères d'optimalité définis.

Le manycasting peut être utilisé avec la cryptographie à clé symétrique ou à clé publique. L'infrastructure à clé publique (PKI) offre la meilleure protection contre les clés compromises et est généralement considérée comme plus robuste, du moins avec des tailles de clés relativement grandes. Elle est implémentée à l'aide du protocole Autokey et de la bibliothèque cryptographique OpenSSL disponible à l'adresse http://www.openssl.org/. La bibliothèque peut également être utilisée avec d'autres modes NTPv4 ainsi qu'elle est fortement recommandée, en particulier pour les modes broadcast.

Une association client manycast persistante est configurée en utilisant la commande manycastclient, qui est similaire à la commande server mais avec une adresse de groupe multicast (classe IPv4 D ou préfixe IPv6 FF). L'IANA a désigné l'adresse IPv4 224.1.1.1 et l'adresse IPv6 FF05::101 (site local) pour NTP. Lorsque plus de serveurs sont nécessaires, il diffuse des messages client manycast à cette adresse au taux minimum réalisable et au temps de vie (TTL) minimum réalisable (sauts), en fonction du nombre de serveurs déjà trouvés. Il peut y avoir autant d'associations client manycast que d'adresses de groupe différentes, chacune servant de modèle pour une future association client/serveur unicast éphémère.

Les serveurs manycast configurés avec la commande manycastserver écoutent sur l'adresse de groupe spécifiée pour les messages client manycast. Notez la distinction entre le client manycast, qui diffuse activement des messages, et le serveur manycast, qui y répond passivement. Si un serveur manycast est à portée du TTL actuel, qu'il est lui-même synchronisé avec une source valide et qu'il fonctionne à un niveau de strate égal ou inférieur à celui du client manycast, il répond au message client manycast avec un message serveur unicast ordinaire.

Le client manycast recevant ce message mobilise une association client/serveur éphémère selon le modèle client manycast correspondant, mais uniquement si elle est authentifiée cryptographiquement et que la strate du serveur est inférieure ou égale à la strate du client. L'authentification est explicitement requise et soit la clé symétrique, soit la clé publique (Autokey) peuvent être utilisées. Ensuite, le client interroge le serveur à son adresse unicast en mode rafale afin de régler de manière fiable l'horloge de l'hôte et de valider la source. Ceci résulte normalement en une rafale de huit client/serveur à des intervalles de 2 secondes pendant lesquels les protocoles de synchronisation et cryptographiques s'exécutent simultanément. Suite à la rafale, le client exécute les algorithmes d'intersection et de clustering NTP, qui agissent pour rejeter toutes les associations sauf les "meilleures" selon la strate et la distance de synchronisation. Les associations survivantes continuent ensuite en mode client/serveur ordinaire.

La stratégie d'interrogation du client manycast est conçue pour réduire autant que possible le volume des messages client manycast et les effets d'implosion dus à l'arrivée quasi simultanée de messages serveur manycast. La stratégie est déterminée par les commandes de configuration manycastclient, tos et ttl. L'intervalle d'interrogation manycast est normalement huit fois l'intervalle d'interrogation système, qui commence par la valeur minpoll spécifiée dans la commande manycastclient et, dans des circonstances normales, s'incrémente jusqu'à la valeur maxpoll spécifiée dans cette commande. Initialement, le TTL est défini au minimum de sauts spécifié par la commande ttl. À chaque retransmission, le TTL est augmenté jusqu'à atteindre le maximum de sauts spécifié par cette commande ou jusqu'à ce qu'un nombre suffisant d'associations client soit trouvé. Les retransmissions ultérieures utilisent le même TTL.

La qualité et la fiabilité de la suite d'associations découvertes par le client manycast sont déterminées par les algorithmes d'atténuation NTP et les valeurs minclock et minsane spécifiées dans la commande de configuration tos. Au moins minsane serveurs candidats doivent être disponibles et les algorithmes d'atténuation doivent produire au moins minclock survivants afin de synchroniser l'horloge. Les principes d'accord byzantin exigent au moins quatre candidats afin de rejeter correctement un unique falseticker. Pour des raisons de compatibilité, minsane vaut par défaut 1 et minclock vaut par défaut 3. Pour le service manycast, minsane devrait être explicitement défini à 4, en supposant qu'au moins ce nombre de serveurs est disponible.

Si au moins minclock serveurs sont trouvés, l'intervalle d'interrogation manycast est immédiatement défini à huit fois maxpoll. Si moins de minclock serveurs sont trouvés lorsque le TTL a atteint le maximum de sauts, l'intervalle d'interrogation manycast est doublé. Pour chaque transmission suivante, l'intervalle d'interrogation est à nouveau doublé jusqu'à atteindre le maximum de huit fois maxpoll. Les transmissions ultérieures utilisent les mêmes valeurs d'intervalle d'interrogation et de TTL. Notez que pendant tout ce processus, chaque association client/serveur trouvée fonctionne normalement selon l'intervalle d'interrogation système.

Les limites multicast à portée administrative sont normalement spécifiées par la configuration du routeur réseau et, dans le cas d'IPv6, le préfixe de portée lien/site. Par défaut, l'incrément pour les sauts TTL est de 32 à partir de 31 ; cependant, la commande de configuration ttl peut être utilisée pour modifier les valeurs afin de correspondre aux règles de portée.

Il est souvent utile de restreindre la gamme des serveurs acceptables qui peuvent être trouvés par manycas

t associations de clients manycast. Parce que les serveurs manycast ne répondent que lorsque le stratum du client est égal ou supérieur au stratum du serveur, les serveurs principaux (stratum 1) ne trouveront que des serveurs principaux dans la plage TTL, ce qui est probablement l'objectif le plus courant. Cependant, sauf configuration contraire, tous les clients manycast dans la plage TTL finiront par trouver tous les serveurs principaux dans la plage TTL, ce qui n'est probablement pas l'objectif le plus courant dans les grands réseaux. La commande tos peut être utilisée pour modifier ce comportement. Les serveurs dont le stratum est inférieur à floor ou supérieur à ceiling spécifiés dans la commande tos sont fortement déconseillés pendant le processus de sélection ; cependant, ces serveurs peuvent être temporairement acceptés si le nombre de serveurs dans la plage TTL est inférieur à minclock.

Les actions ci-dessus se produisent pour chaque message client manycast, qui se répète à l'intervalle de sondage désigné. Cependant, une fois que l'association client éphémère est mobilisée, les réponses ultérieures du serveur manycast sont ignorées, car cela entraînerait une association dupliquée. Si, pendant un intervalle de sondage, le nombre d'associations clients tombe en dessous de minclock, toutes les associations prototypes clients manycast sont réinitialisées à l'intervalle de sondage et aux sauts TTL initiaux et l'opération reprend depuis le début. Il est important d'éviter les messages clients manycast fréquents, car chacun nécessite que tous les serveurs manycast dans la plage TTL répondent. Le résultat pourrait bien être une implosion, mineure ou majeure, en fonction du nombre de serveurs dans la plage. La valeur recommandée pour maxpoll est de 12 (4 096 s).

Il est possible et souvent utile de configurer un hôte à la fois comme client et comme serveur manycast. Un certain nombre d'hôtes configurés de cette manière et partageant une adresse de groupe commune s'organiseront automatiquement dans une configuration optimale basée sur le stratum et la distance de synchronisation. Par exemple, considérons un sous-réseau NTP de deux serveurs principaux et une centaine de clients dépendants ou plus. À deux exceptions près, tous les serveurs et clients ont des fichiers de configuration identiques, y compris les commandes multicastclient et multicastserver utilisant, par exemple, l'adresse de groupe multicast 239.1.1.1. La seule exception est que chaque fichier de configuration de serveur principal doit inclure des commandes pour la source de référence principale, telle qu'un récepteur GPS.

Les fichiers de configuration restants pour tous les serveurs secondaires et clients ont le même contenu, à l'exception de la commande tos, qui est spécifique à chaque niveau de stratum. Pour les serveurs stratum 1 et 2, cette commande n'est pas nécessaire. Pour les serveurs stratum 3 et supérieurs, la valeur floor est définie sur le numéro de stratum prévu. Ainsi, tous les fichiers de configuration stratum 3 sont identiques, tous les fichiers stratum 4 sont identiques, et ainsi de suite.

Une fois que les opérations se sont stabilisées dans ce scénario, les serveurs principaux trouveront la source de référence principale et s'entendront entre eux, car ils fonctionnent tous deux au même stratum (1), mais pas avec les serveurs secondaires ou les clients, car ceux-ci fonctionnent à un stratum supérieur. Les serveurs secondaires trouveront les serveurs au même niveau de stratum. Si l'un des serveurs principaux perd son récepteur GPS, il continuera à fonctionner comme client et les autres clients expireront l'association correspondante et se réassocieront en conséquence.

Certains administrateurs préfèrent éviter de faire fonctionner ntpd(1) en continu et utilisent soit sntp(1) soit ntpd(1) -q comme tâche cron. Dans les deux cas, les serveurs doivent être configurés à l'avance et le programme échoue si aucun n'est disponible lorsque la tâche cron s'exécute. Une application vraiment astucieuse de manycast est avec ntpd(1) -q. Le programme démarre, scanne le paysage local à la recherche des suspects habituels, sélectionne le meilleur parmi les vauriens, règle l'horloge, puis s'en va. Les serveurs n'ont pas besoin d'être configurés à l'avance et tous les clients du réseau peuvent avoir le même fichier de configuration.

Interactions Manycast avec Autokey

Chaque fois qu'un client manycast envoie un paquet en mode client à une adresse de groupe multicast, tous les serveurs manycast dans la portée génèrent une réponse incluant le nom d'hôte et le mot d'état. Les clients manycast exécutent ensuite le protocole Autokey, qui collecte et vérifie tous les certificats impliqués. Après l'intervalle de rafale, tous les survivants sauf trois sont rejetés, mais les certificats restent dans le cache local. Il arrive souvent que plusieurs chaînes de signature complètes du client aux serveurs principaux soient collectées de cette manière.

Environ une fois par heure, ou moins souvent si l'intervalle de sondage dépasse ce délai, le client régénère la liste des clés Autokey. Ceci est généralement transparent en mode client/serveur. Cependant, environ une fois par jour, la valeur privée du serveur utilisée pour générer les cookies est actualisée ainsi que toutes les associations clients manycast. Dans ce cas, toutes les valeurs cryptographiques, y compris les certificats, sont actualisées. Si un nouveau certificat a été généré depuis la dernière époque d'actualisation, il révoquera automatiquement tous les certificats précédents qui se trouvent dans le cache de certificats. Dans le même temps, le schéma manycast recommence depuis le début et l'anneau d'expansion se réduit au minimum et s'incrémente à partir de là tout en collectant tous les serveurs dans la portée.

Options de diffusion

tos [bcpollbstep gate]

Cette commande offre un moyen de retarder, du nombre spécifié d'intervalles de sondage de diffusion, les retours en arrière de temps provenant d'un serveur de diffusion. Les réseaux temporels diffusés sont censés être fiables. Dans le cas où le temps d'un serveur de diffusion est reculé, il est clairement avantageux que les clients remarquent ce changement dès que possible. Les attaques telles que les attaques par rejeu peuvent se produire, cependant, et même s'il existe un certain nombre de protections intégrées au mode de diffusion, des tentatives d'attaque par rejeu sont possibles. Cette valeur est par défaut à 0, mais peut être modifiée à tout nombre d'intervalles de sondage entre 0 et 4.

Options Manycast

tos [ceiling ceiling | cohort { 0 | 1 } | floor floor | minclock minclock | minsane minsane]

Cette commande affecte les algorithmes de sélection d'horloge et de clustering. Elle peut être utilisée pour sélectionner la qualité et la quantité des pairs utilisés pour synchroniser l'horloge système et est particulièrement utile en mode manycast. Les variables fonctionnent comme suit :
ceiling ceiling

Les pairs dont le stratum est supérieur à ceiling seront rejetés s'il reste au moins minclock pairs. Cette valeur est par défaut à 15, mais peut être modifiée à tout nombre compris entre 1 et 15.
cohort {0 | 1 }

Ceci est un indicateur binaire qui active (0) ou désactive (1) les réponses des serveurs manycast aux clients manycast ayant le même niveau de stratum. Ceci est utile pour réduire les implosions où un grand nombre de clients ayant le même niveau de stratum sont présents. La valeur par défaut est d'activer ces réponses.
floor floor

Les pairs dont le stratum est inférieur à floor seront rejetés s'il reste au moins minclock pairs. Cette valeur est par défaut à 1, mais peut être modifiée à tout nombre compris entre 1 et 15.
minclock minclock

L'algorithme de clustering rejette répétitivement les associations aberrantes jusqu'à ce qu'il en reste au maximum minclock. Cette valeur est par défaut à 3, mais peut être modifiée à tout nombre compris entre 1 et le nombre de sources configurées.
minsane minsane

C'est le nombre minimum de candidats disponibles pour l'algorithme de sélection d'horloge afin de produire un ou plusieurs "truechimers" pour l'algorithme de clustering. Si moins que ce nombre est disponible, l'horloge n'est pas disciplinée et est autorisée à fonctionner librement. La valeur par défaut est 1 pour des raisons d'héritage. Cependant, selon les principes de l'accord byzantin, minsane devrait être au moins 4 afin de détecter et de rejeter un seul "falseticker".
ttl hop ...

Cette commande spécifie une liste de valeurs TTL par ordre croissant, jusqu'à 8 valeurs peuvent être spécifiées. En mode manycast, ces valeurs sont utilisées tour à tour dans une recherche en anneau expansif. La valeur par défaut est huit multiples de 32 commençant à 31.

Support de l'horloge de référence

Le démon NTP Version 4 prend en charge une trentaine de récepteurs d'horloge radio, satellite et modem, plus un pseudo-horloge spécial utilisé pour la sauvegarde ou lorsqu'aucune autre source d'horloge n'est disponible. Des descriptions détaillées des pilotes de périphériques individuels et des options peuvent être trouvées sur la page "Référence Clock Drivers" (disponible dans la documentation HTML fournie dans /usr/share/doc/ntp). Des informations supplémentaires peuvent être trouvées sur les pages qui y sont liées, y compris les pages "Debugging Hints for Reference Clock Drivers" et "How To Write a Reference Clock Driver" (disponibles dans la documentation HTML fournie dans /usr/share/doc/ntp). De plus, le support d'un signal PPS est disponible comme décrit sur la page "Pulse-per-second (PPS) Signal Interfacing" (disponible dans la documentation HTML fournie dans /usr/share/doc/ntp). De nombreux pilotes prennent en charge des modules spéciaux de discipline/flux de ligne qui peuvent améliorer considérablement la précision en utilisant le pilote. Ceux-ci sont décrits sur la page "Line Disciplines and Streams Drivers" (disponible dans la documentation HTML fournie dans /usr/share/doc/ntp).

Une horloge de référence sera généralement (bien que pas toujours) un récepteur de code temporel radio synchronisé à une source de temps standard telle que les services offerts par le NRC au Canada et le NIST et l'USNO aux États-Unis. L'interface entre l'ordinateur et le récepteur de code temporel dépend du périphérique, mais il s'agit généralement d'un port série. Un pilote de périphérique spécifique à chaque horloge de référence doit être sélectionné et compilé dans la distribution ; cependant, la plupart des horloges radio, satellite et modem courantes sont incluses par défaut. Notez qu'une tentative de configuration d'une horloge de référence lorsque le pilote n'a pas été compilé ou que le port matériel n'a pas été approprié

ly configurés les résultats dans une remarque cinglante au fichier journal du système, mais n'est autrement pas dangereux.

Aux fins de configuration, ntpd(1) traite les horloges de référence d'une manière analogue aux pairs NTP normaux dans la mesure du possible. Les horloges de référence sont identifiées par une adresse IP syntaxiquement correcte mais invalide, afin de les distinguer des pairs NTP normaux. Les adresses des horloges de référence sont de la forme 127.127.t.u, où t est un entier indiquant le type d'horloge et u indique le numéro d'unité dans la plage 0-3. Bien que cela puisse sembler excessif, il est en fait parfois utile de configurer plusieurs horloges de référence du même type, auquel cas les numéros d'unité doivent être uniques.

La commande server est utilisée pour configurer une horloge de référence, où l'argument adresse de cette commande est l'adresse de l'horloge. Les options key, version et ttl ne sont pas utilisées pour le support des horloges de référence. L'option mode est ajoutée pour le support des horloges de référence, comme décrit ci-dessous. L'option prefer peut être utile pour persuader le serveur de chérir une horloge de référence avec un peu plus d'enthousiasme que les autres horloges de référence ou les pairs. Des informations supplémentaires sur cette option sont disponibles sur la page "Règles d'atténuation et le mot-clé prefer" (disponible dans la documentation HTML fournie dans /usr/share/doc/ntp). Les options minpoll et maxpoll n'ont de sens que pour certains pilotes d'horloge. Voir les pages de documentation individuelles des pilotes d'horloge pour des informations supplémentaires.

La commande fudge est utilisée pour fournir des informations supplémentaires pour les pilotes d'horloge individuels et suit normalement immédiatement la commande server. L'argument adresse spécifie l'adresse de l'horloge. Les options refid et stratum peuvent être utilisées pour remplacer les valeurs par défaut du périphérique. Il existe deux décalages temporels optionnels dépendant du périphérique et quatre indicateurs qui peuvent également être inclus dans la commande fudge.

Le numéro de strate d'une horloge de référence est par défaut zéro. Étant donné que le démon ntpd(1) ajoute un au nombre de strates de chaque pair, un serveur primaire affiche normalement une strate externe de un. Afin de fournir des sauvegardes conçues, il est souvent utile de spécifier la strate de l'horloge de référence comme étant supérieure à zéro. L'option stratum est utilisée à cette fin. De plus, dans les cas impliquant à la fois une horloge de référence et un signal de synchronisation par seconde (PPS), il est utile de spécifier l'identifiant de l'horloge de référence comme différent de la valeur par défaut, en fonction du pilote. L'option refid est utilisée à cette fin. Sauf indication contraire, ces options s'appliquent à tous les pilotes d'horloge.

Commandes d'horloge de référence

server 127.127.t.u [prefer] [mode int] [minpoll int] [maxpoll int]

Cette commande peut être utilisée pour configurer les horloges de référence de manière spéciale. Les options sont interprétées comme suit :
prefer

Marque l'horloge de référence comme préférée. Toutes choses égales par ailleurs, cet hôte sera choisi pour la synchronisation parmi un ensemble d'hôtes fonctionnant correctement. Voir la page "Règles d'atténuation et le mot-clé prefer" (disponible dans la documentation HTML fournie dans /usr/share/doc/ntp) pour plus d'informations.
mode int

Spécifie un numéro de mode qui est interprété d'une manière spécifique au périphérique. Par exemple, il sélectionne un protocole de numérotation dans le pilote ACTS et un sous-type de périphérique dans les pilotes d'analyse.
minpoll int

maxpoll int

Ces options spécifient l'intervalle de sondage minimum et maximum pour les messages d'horloge de référence, sous forme de puissance de 2 en secondes. Pour la plupart des horloges de référence directement connectées, minpoll et maxpoll sont par défaut à 6 (64 s). Pour les horloges de référence modem, minpoll est par défaut à 10 (17,1 m) et maxpoll est par défaut à 14 (4,5 h). La plage autorisée est de 4 (16 s) à 17 (36,4 h) inclus.
fudge 127.127.t.u [time1 sec] [time2 sec] [stratum int] [refid string] [mode int] [flag1 0 | 1] [flag2 0 | 1] [flag3 0 | 1] [flag4 0 | 1]

Cette commande peut être utilisée pour configurer les horloges de référence de manière spéciale. Elle doit suivre immédiatement la commande server qui configure le pilote. Notez que la même capacité est possible à l'exécution à l'aide du programme ntpdc(1). Les options sont interprétées comme suit :
time1 sec

Spécifie une constante à ajouter au décalage temporel produit par le pilote, un nombre décimal à virgule fixe en secondes. Ceci est utilisé comme constante de calibrage pour ajuster le décalage temporel nominal d'une horloge particulière pour correspondre à une norme externe, telle qu'un signal PPS de précision. Il fournit également un moyen de corriger une erreur systématique ou un biais dû aux latences du port série ou du système d'exploitation, à différentes longueurs de câble ou au délai interne du récepteur. Le décalage spécifié s'ajoute au délai de propagation fourni par d'autres moyens, tels que les commutateurs DIP internes. Lorsqu'un calibrage pour un système et un pilote individuels est disponible, une correction approximative est notée dans les pages de documentation du pilote. Remarque : afin de faciliter le calibrage lorsqu'il y a plus d'une horloge radio ou d'un signal PPS pris en charge, une fonctionnalité de calibrage spéciale est disponible. Elle prend la forme d'un argument à la commande enable décrite sur la page Options diverses et fonctionne comme décrit sur la page "Pilotes d'horloge de référence" (disponible dans la documentation HTML fournie dans /usr/share/doc/ntp).
time2 secs

Spécifie un nombre décimal à virgule fixe en secondes, qui est interprété d'une manière dépendante du pilote. Voir les descriptions des pilotes spécifiques sur la page "Pilotes d'horloge de référence" (disponible dans la documentation HTML fournie dans /usr/share/doc/ntp).
stratum int

Spécifie le numéro de strate attribué au pilote, un entier compris entre 0 et 15. Ce nombre remplace le numéro de strate par défaut normalement attribué par le pilote lui-même, généralement zéro.
refid string

Spécifie une chaîne ASCII d'un à quatre caractères qui définit l'identifiant de référence utilisé par le pilote. Cette chaîne remplace l'identifiant par défaut normalement attribué par le pilote lui-même.
mode int

Spécifie un numéro de mode qui est interprété d'une manière spécifique au périphérique. Par exemple, il sélectionne un protocole de numérotation dans le pilote ACTS et un sous-type de périphérique dans les pilotes d'analyse.
flag1 0 | 1

flag2 0 | 1

flag3 0 | 1

flag4 0 | 1

Ces quatre indicateurs sont utilisés pour personnaliser le pilote d'horloge. L'interprétation de ces valeurs, et si elles sont utilisées ou non, est fonction du pilote d'horloge particulier. Cependant, par convention, flag4 est utilisé pour activer l'enregistrement des données de surveillance dans le fichier clockstats configuré avec la commande filegen. Des informations supplémentaires sur la commande filegen se trouvent dans Options de surveillance.

Options diverses

broadcastdelay seconds

Les modes broadcast et multicast nécessitent un calibrage spécial pour déterminer le délai réseau entre les serveurs locaux et distants. Normalement, cela se fait automatiquement par les échanges de protocoles initiaux entre le client et le serveur. Dans certains cas, la procédure de calibrage peut échouer en raison de contrôles d'accès réseau ou serveur, par exemple. Cette commande spécifie le délai par défaut à utiliser dans ces circonstances. Typiquement (pour Ethernet), un nombre entre 0,003 et 0,007 secondes est approprié. La valeur par défaut lorsqu'une de ces commandes n'est pas utilisée est de 0,004 secondes.
driftfile driftfile

Cette commande spécifie le chemin d'accès complet et le nom du fichier utilisé pour enregistrer la fréquence de l'oscillateur d'horloge local. Il s'agit de la même opération que l'option de ligne de commande -f. Si le fichier existe, il est lu au démarrage afin de définir la fréquence initiale, puis mis à jour une fois par heure avec la fréquence actuelle calculée par le démon. Si le nom du fichier est spécifié, mais que le fichier lui-même n'existe pas, le démon commence avec une fréquence initiale de zéro et crée le fichier lors de sa première écriture. Si cette commande n'est pas donnée, le démon commencera toujours avec une fréquence initiale de zéro.

Le format du fichier se compose d'une seule ligne contenant un seul nombre à virgule flottante, qui enregistre le décalage de fréquence mesuré en parties par million (PPM). Le fichier est mis à jour en écrivant d'abord la valeur de dérive actuelle dans un fichier temporaire, puis en renommant ce fichier pour remplacer l'ancienne version.

. Ceci implique que ntpd(1) doit avoir les permissions d'écriture pour le répertoire où se trouve le fichier de dérive, et que les liens de système de fichiers, symboliques ou autres, doivent être évités.

dscp valeur

Cette option spécifie la valeur du Differentiated Services Control Point (DSCP), un code de 6 bits. La valeur par défaut est 46, signifiant Expedited Forwarding.

disable [auth | bclient | calibrate | kernel | mode7 | monitor | ntp | stats | peer_clear_digest_early | unpeer_crypto_early | unpeer_crypto_nak_early | unpeer_digest_early]

Permet d'activer ou de désactiver diverses options du serveur. Les indicateurs non mentionnés ne sont pas affectés. Notez que tous ces indicateurs peuvent être contrôlés à distance à l'aide de l'utilitaire ntpdc(1).
auth

Autorise le serveur à se synchroniser avec des pairs non configurés uniquement si le pair a été correctement authentifié à l'aide de la cryptographie à clé publique ou privée. La valeur par défaut de cet indicateur est enable.
bclient

Permet au serveur d'écouter un message d'un serveur de diffusion ou de multidiffusion, comme dans la commande multicastclient avec l'adresse par défaut. La valeur par défaut de cet indicateur est disable.
calibrate

Active la fonctionnalité de calibration pour les horloges de référence. La valeur par défaut de cet indicateur est disable.
kernel

Active la discipline de temps du noyau, si disponible. La valeur par défaut de cet indicateur est enable si le support est disponible, sinon disable.
mode7

Active le traitement des requêtes spécifiques à l'implémentation du mode NTP 7, qui sont utilisées par le programme obsolète ntpdc(1). La valeur par défaut de cet indicateur est disable. Cet indicateur est exclu de la configuration d'exécution à l'aide de ntpq(1). Le programme ntpq(1) fournit les mêmes capacités que ntpdc(1) en utilisant les requêtes standard de mode 6.
monitor

Active le module de surveillance. Voir le programme ntpd(1) et la commande monlist pour plus d'informations. La valeur par défaut de cet indicateur est enable.
ntp

Active la discipline de temps et de fréquence. En effet, ce commutateur ouvre et ferme la boucle de rétroaction, ce qui est utile pour les tests. La valeur par défaut de cet indicateur est enable.
peer_clear_digest_early

Par défaut, si ntpd(1) utilise autokey et reçoit un paquet crypto-NAK qui passe les vérifications de doublons et d'horodatage d'origine, les variables du pair sont immédiatement effacées. Bien que ce soit généralement une fonctionnalité car elle permet une récupération rapide si une clé de serveur a changé, un paquet crypto-NAK correctement forgé et délivré peut être utilisé dans une attaque DoS. Si vous avez des problèmes notables actifs avec ce type d'attaque DoS, vous devriez envisager de désactiver cette option. Vous pouvez consulter votre fichier peerstats pour des preuves de ces attaques. La valeur par défaut de cet indicateur est enable.
stats

Active le module de statistiques. Voir la section Options de surveillance pour plus d'informations. La valeur par défaut de cet indicateur est disable.
unpeer_crypto_early

Par défaut, si ntpd(1) reçoit un paquet autokey qui échoue au TEST9, une défaillance cryptographique, l'association est immédiatement fermée. C'est presque certainement une fonctionnalité, mais si, malgré la recommandation actuelle de ne pas utiliser autokey, vous utilisez toujours autokey et que vous constatez ce type d'attaque DoS, la désactivation de cet indicateur retardera la fermeture de l'association jusqu'à ce que le compteur de joignabilité atteigne zéro. Vous pouvez consulter votre fichier peerstats pour des preuves de ces attaques. La valeur par défaut de cet indicateur est enable.
unpeer_crypto_nak_early

Par défaut, si ntpd(1) reçoit un paquet crypto-NAK qui passe les vérifications de doublons et d'horodatage d'origine, l'association est immédiatement fermée. Bien que ce soit généralement une fonctionnalité car elle permet une récupération rapide si une clé de serveur a changé, un paquet crypto-NAK correctement forgé et délivré peut être utilisé dans une attaque DoS. Si vous avez des problèmes notables actifs avec ce type d'attaque DoS, vous devriez envisager de désactiver cette option. Vous pouvez consulter votre fichier peerstats pour des preuves de ces attaques. La valeur par défaut de cet indicateur est enable.
unpeer_digest_early

Par défaut, si ntpd(1) reçoit ce qui devrait être un paquet authentifié qui passe les autres vérifications de cohérence du paquet mais contient un digest invalide, l'association est immédiatement fermée. Bien que ce soit généralement une fonctionnalité car elle permet une récupération rapide, si ce type de paquet est soigneusement forgé et envoyé pendant une fenêtre appropriée, il peut être utilisé pour une attaque DoS. Si vous avez des problèmes notables actifs avec ce type d'attaque DoS, vous devriez envisager de désactiver cette option. Vous pouvez consulter votre fichier peerstats pour des preuves de ces attaques. La valeur par défaut de cet indicateur est enable.
includefile fichier_inclusion

Cette commande permet d'inclure des commandes de configuration supplémentaires à partir d'un fichier séparé. Les fichiers d'inclusion peuvent être imbriqués jusqu'à une profondeur de cinq ; à la fin de tout fichier d'inclusion, le traitement des commandes reprend dans le fichier de configuration précédent. Cette option est utile pour les sites qui exécutent ntpd(1) sur plusieurs hôtes, avec des options (presque) communes (par exemple, une liste de restriction).
interface [listen | ignore | drop] [all | ipv4 | ipv6 | wildcard nom | adresse [/ longueur_préfixe]]

La directive interface contrôle quelles adresses réseau ntpd(1) ouvre, et si les entrées sont ignorées sans traitement. Le premier paramètre détermine l'action pour les adresses qui correspondent au deuxième paramètre. Le deuxième paramètre spécifie une classe d'adresses, ou un nom d'interface spécifique, ou une adresse. Dans le cas d'une adresse, longueur_préfixe détermine combien de bits doivent correspondre pour que cette règle s'applique. ignore empêche l'ouverture des adresses correspondantes, drop fait en sorte que ntpd(1) ouvre l'adresse et ignore tous les paquets reçus sans examen. Plusieurs directives interface peuvent être utilisées. La dernière règle qui correspond à une adresse particulière détermine l'action pour celle-ci. Les directives interface sont désactivées si des options de ligne de commande -I, --interface, -L, ou --novirtualips sont spécifiées dans le fichier de configuration, toutes les adresses réseau disponibles sont ouvertes. La directive nic est un alias pour interface.

Cette commande charge le fichier des secondes intercalaires de l'IERS et initialise les valeurs des secondes intercalaires pour le prochain événement de seconde intercalaire, la date d'expiration du fichier de saut et le décalage TAI. Le fichier peut être obtenu directement auprès de l'IERS à l'adresse https://hpiers.obspm.fr/iers/bul/bulc/ntp/leap-seconds.list ou ftp://hpiers.obspm.fr/iers/bul/bulc/ntp/leap-seconds.list. Le fichier_de_saut est analysé lorsque ntpd(1) traite la directive fichier_de_saut ou lorsque ntpd détecte que le fichier_de_saut a changé. ntpd vérifie une fois par jour si le fichier_de_saut a changé. Le script update-leap(1update_leapmdoc) peut être exécuté pour voir si le fichier_de_saut doit être mis à jour.
leapsmearinterval secondes

Cette option EXPÉRIMENTALE n'est disponible que si ntpd(1) a été compilé avec l'option --enable-leap-smear pour le script configure. Elle spécifie l'intervalle sur lequel une correction de seconde intercalaire sera appliquée. Les valeurs recommandées pour cette option sont comprises entre 7200 (2 heures) et 86400 (24 heures). Voir http://bugs.ntp.org/2855 pour plus d'informations.
logconfig mot_clé_de_configuration

Cette commande contrôle la quantité et le type de sortie écrite dans le syslog du système(3) facility ou la solution de rechange logfile fichier journal. Par défaut, toutes les sorties sont activées. Tous les configkeyword mots-clés peuvent être préfixés par ‘=’, ‘+’ et ‘-’, où ‘=’ définit le masque de priorité syslog(3), ‘+’ ajoute et ‘-’ supprime les messages. syslog(3) les messages peuvent être contrôlés dans quatre classes (clock, peer, sys et sync). Au sein de ces classes, quatre types de messages peuvent être contrôlés : messages d'information (info), messages d'événement (events), messages de statistiques (statistics) et messages d'état (status).

Les mots-clés de configuration sont formés en concaténant la classe de message avec la classe d'événement. Le préfixe all peut être utilisé à la place d'une classe de message. Une classe de message peut également être suivie du mot-clé all pour activer/désactiver tous les messages de la classe de message respective. Ainsi, une configuration de journal minimale pourrait ressembler à ceci : 

logconfig =syncstatus +sysevents

Cela listerait simplement l'état de synchronisation de ntpd(1) et les événements système majeurs. Pour un serveur de référence simple, la configuration de message minimale suivante pourrait être utile : 

logconfig =syncall +clockall

Cette configuration listera toutes les informations d'horloge et les informations de synchronisation. Tous les autres événements et messages concernant les pairs, les événements système, etc., sont supprimés.

Cette commande spécifie l'emplacement d'un fichier journal alternatif à utiliser à la place de la facility syslog(3) par défaut du système. Cette opération est identique à l'option de ligne de commande -l.

Limites supérieures équivalentes pour la taille de la liste MRU, en termes d'entrées ou de kilo-octets. La limite réelle sera jusqu'à incalloc entrées ou incmem kilo-octets de plus. Une fois que la liste MRU contient mindepth entrées et qu'un client supplémentaire doit être ajouté à la liste, si la plus ancienne entrée a été mise à jour il y a plus de maxage secondes, cette entrée est supprimée et son stockage est réutilisé. Si la plus ancienne entrée a été mise à jour plus récemment, la liste MRU est agrandie, sous réserve de maxdepth / moxmem. La valeur par défaut est de 64 secondes.
initalloc count

initmem kilobytes

Allocation mémoire initiale au moment où la fonction de surveillance est activée pour la première fois, en termes de nombre d'entrées ou de kilo-octets. La valeur par défaut est de 4 kilo-octets.
incalloc count

incmem kilobytes

Taille des allocations mémoire supplémentaires lors de l'agrandissement de la liste MRU, en entrées ou en kilo-octets. La valeur par défaut est de 4 kilo-octets.

Spécifie le seuil delta en secondes avant qu'une modification horaire du driftfile (fichier de fréquence) ne soit écrite, avec une valeur par défaut de 1e-7 (0,1 PPM). Le fichier de fréquence est inspecté chaque heure. Si la différence entre la fréquence actuelle et la dernière valeur écrite dépasse le seuil, le fichier est écrit et le seuil devient la nouvelle valeur du seuil. Si le seuil n'est pas dépassé, il est divisé par deux. Ceci est destiné à réduire le nombre d'écritures de fichiers pour les systèmes embarqués avec mémoire non volatile.

Cette commande est utilisée conjointement avec le pilote modem ACTS (type 18) ou le pilote JJY (type 40, mode 100 - 180). Pour le pilote modem ACTS (type 18), les arguments consistent en un maximum de 10 numéros de téléphone utilisés pour composer le service horaire USNO, NIST ou européen. Pour le pilote JJY (type 40 mode 100 - 180), l'argument est un numéro de téléphone utilisé pour composer le service téléphonique JJY. tinker [allan allan | dispersion dispersion | freq freq | huffpuff huffpuff | panic panic | step step | stepback stepback | stepfwd stepfwd | stepout stepout]

Cette commande peut être utilisée pour modifier plusieurs variables système dans des circonstances très exceptionnelles. Elle doit apparaître dans le fichier de configuration avant toute autre option de configuration. Les valeurs par défaut de ces variables ont été soigneusement optimisées pour une large gamme de vitesses réseau et d'attentes de fiabilité. En général, elles interagissent de manière complexe et difficile à prévoir, et certaines combinaisons peuvent entraîner un comportement très désagréable. Il est très rarement nécessaire de modifier les valeurs par défaut ; cependant, certains ne résistent pas à l'envie de modifier les réglages et cette commande est pour eux. Mise en évidence ajoutée : ceux qui modifient sont seuls et ne doivent attendre aucune aide du groupe de support.

Les variables fonctionnent comme suit :

allan allan

L'argument devient la nouvelle valeur pour l'intercept d'Allan minimum, qui est un paramètre de l'algorithme de discipline d'horloge PLL/FLL. La valeur en log2 secondes est par défaut 7 (1024 s), ce qui est également la limite inférieure.
dispersion dispersion

L'argument devient la nouvelle valeur pour le taux d'augmentation de la dispersion, normalement de 0,000015 s/s.
freq freq

L'argument devient la valeur initiale du décalage de fréquence en parties par million. Ceci remplace la valeur du fichier de fréquence, si présente, et évite l'état d'apprentissage initial s'il n'y en a pas.
huffpuff huffpuff

L'argument devient la nouvelle valeur pour la portée expérimentale du filtre huff-n'-puff, qui détermine l'intervalle le plus récent pendant lequel l'algorithme recherchera un délai minimum. La limite inférieure est de 900 s (15 m), mais une valeur plus raisonnable est de 7200 s (2 heures). Il n'y a pas de valeur par défaut, car le filtre n'est pas activé à moins que cette commande ne soit donnée.
panic panic

L'argument est le seuil de panique, normalement de 1000 s. S'il est réglé à zéro, la vérification de sécurité de panique est désactivée et un décalage d'horloge de n'importe quelle valeur sera accepté.
step step

L'argument est le seuil de pas, qui par défaut est de 0,128 s. Il peut être réglé sur n'importe quel nombre positif en secondes. S'il est réglé à zéro, les ajustements de pas ne se produiront jamais. Note : La discipline d'horloge du noyau est désactivée si le seuil de pas est réglé à zéro ou supérieur à la valeur par défaut.
stepback stepback

L'argument est le seuil de pas pour la direction arrière, qui par défaut est de 0,128 s. Il peut être réglé sur n'importe quel nombre positif en secondes. Si les seuils de pas avant et arrière sont tous deux réglés à zéro, les ajustements de pas ne se produiront jamais. Note : La discipline d'horloge du noyau est désactivée si chaque direction de seuil de pas est réglée à zéro ou supérieure à 0,5 seconde.
stepfwd stepfwd

Comme pour stepback, mais pour la direction avant.
stepout stepout

L'argument est le délai d'attente de pas, qui par défaut est de 900 s. Il peut être réglé sur n'importe quel nombre positif en secondes. S'il est réglé à zéro, les impulsions de pas ne seront pas supprimées.
writevar assocID name = value [,...]

Écrit (crée ou met à jour) les variables spécifiées. Si le assocID est zéro, les variables proviennent de l'espace de noms des variables système, sinon elles proviennent de l'espace de noms des variables pair. Le assocID est requis, car le même nom peut apparaître dans les deux espaces de noms.
trap host_address [port port_number] [interface interface_address]

Cette commande configure un récepteur de piège à l'adresse hôte et au numéro de port donnés pour envoyer des messages avec l'adresse d'interface locale spécifiée. Si le numéro de port n'est pas spécifié, une valeur de 18447 est utilisée. Si l'adresse d'interface n'est pas spécifiée, le message est envoyé avec une adresse source de l'interface locale par laquelle le message est envoyé. Notez que sur un hôte multihomé, l'interface utilisée peut varier de temps à autre avec les changements de routage.
ttl hop ...

Cette commande spécifie une liste de valeurs TTL par ordre croissant. Jusqu'à 8 valeurs peuvent être spécifiées. En mode manycast, ces valeurs sont utilisées tour à tour dans une recherche à anneau expansif. La valeur par défaut est huit multiples de 32 commençant à 31.

Le récepteur de piège enregistrera généralement les messages d'événements et d'autres informations du serveur dans un fichier journal. Bien que ces programmes de surveillance puissent également demander leurs propres pièges dynamiquement, la configuration d'un récepteur de piège garantira qu'aucun message ne sera perdu au démarrage du serveur.

hop ...

Cette commande spécifie une liste de valeurs TTL par ordre croissant, jusqu'à 8 valeurs peuvent être spécifiées. En mode manycast, ces valeurs sont utilisées tour à tour dans une recherche à anneau expansif. La valeur par défaut est huit multiples de 32 commençant à 31.
