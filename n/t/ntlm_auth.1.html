NTLM_AUTH(1) Commandes utilisateur NTLM_AUTH(1)

NOM

ntlm_auth - outil pour permettre un accès externe à la fonction d'authentification NTLM de Winbind

SYNTAXE

ntlm_auth

DESCRIPTION

Cet outil fait partie de la suite samba(7).

ntlm_auth est un utilitaire d'aide qui authentifie les utilisateurs en utilisant l'authentification NT/LM. Il retourne 0 si l'utilisateur est authentifié avec succès et 1 si l'accès a été refusé. ntlm_auth utilise winbind pour accéder aux données utilisateur et d'authentification d'un domaine. Cet utilitaire est uniquement destiné à être utilisé par d'autres programmes (actuellement Squid et mod_ntlm_winbind).

EXIGENCES OPÉRATIONNELLES

Le démon winbindd(8) doit être opérationnel pour que bon nombre de ces commandes fonctionnent.

Certaines de ces commandes nécessitent également un accès au répertoire winbindd_privileged dans $LOCKDIR. Cela doit être fait soit en exécutant cette commande en tant que root, soit en accordant un accès de groupe au répertoire winbindd_privileged. Pour des raisons de sécurité, ce répertoire ne doit pas être accessible à tous.

OPTIONS

--helper-protocol=PROTO

Fonctionne comme une aide basée sur stdio. Les protocoles d'aide valides sont :

squid-2.4-basic

Aide côté serveur à utiliser avec l'authentification de base (texte brut) de Squid 2.4.

squid-2.5-basic

Aide côté serveur à utiliser avec l'authentification de base (texte brut) de Squid 2.5.

squid-2.5-ntlmssp

Aide côté serveur à utiliser avec l'authentification NTLMSSP de Squid 2.5.

Nécessite un accès au répertoire winbindd_privileged dans $LOCKDIR. Le protocole utilisé est décrit ici : http://devel.squid-cache.org/ntlm/squid_helper_protocol.html. Ce protocole a été étendu pour permettre au paquet NTLMSSP Negotiate d'être inclus comme argument de la commande YR. (Évitant ainsi la perte d'informations dans l'échange de protocole).

ntlmssp-client-1

Aide côté client à utiliser avec des programmes externes arbitraires qui souhaitent utiliser les connaissances d'authentification NTLMSSP de Samba.

Cette aide est un client, et en tant que tel peut être exécutée par n'importe quel utilisateur. Le protocole utilisé est effectivement l'inverse du protocole précédent. Une commande YR (sans aucun argument) démarre l'échange d'authentification.

gss-spnego

Aide côté serveur qui implémente GSS-SPNEGO. Cela utilise un protocole très similaire à squid-2.5-ntlmssp, mais présente des différences subtiles qui ne sont pas documentées en dehors du code source à ce stade.

Nécessite un accès au répertoire winbindd_privileged dans $LOCKDIR.

gss-spnego-client

Aide côté client qui implémente GSS-SPNEGO. Cela utilise également un protocole similaire aux aides ci-dessus, mais il n'est actuellement pas documenté.

ntlm-server-1

Protocole d'aide côté serveur, destiné à être utilisé par un serveur RADIUS ou le plugin 'winbind' pour pppd, pour la fourniture de l'authentification MSCHAP et MSCHAPv2.

Ce protocole se compose de lignes de la forme : Paramètre: valeur et Paramètre:: Valeur encodée en Base64. La présence d'un seul point . indique qu'un côté a fini de fournir des données à l'autre. (Ce qui, à son tour, pourrait amener l'aide à authentifier l'utilisateur).

Les paramètres actuellement implémentés du programme externe vers l'aide sont :

Username

Le nom d'utilisateur, attendu dans le charset unix de Samba.

Exemples :

Username: bob

Username:: Ym9i

NT-Domain

Le domaine de l'utilisateur, attendu dans le charset unix de Samba.

Exemples :

NT-Domain: WORKGROUP

NT-Domain:: V09SS0dST1VQ

Full-Username

Le nom d'utilisateur entièrement qualifié, attendu dans le charset unix de Samba et qualifié par le séparateur winbind.

Exemples :

Full-Username: WORKGROUP\bob

Full-Username:: V09SS0dST1VQYm9i

LANMAN-Challenge

La valeur de défi LANMAN de 8 octets, générée aléatoirement par le serveur, ou (dans des cas comme MSCHAPv2) générée d'une manière ou d'une autre par le serveur et le client.

Exemples :

LANMAN-Challenge: 0102030405060708

LANMAN-Response

La valeur de réponse LANMAN de 24 octets, calculée à partir du mot de passe de l'utilisateur et du défi LANMAN fourni. Typiquement, cela est fourni sur le réseau par un client souhaitant s'authentifier.

Exemples :

LANMAN-Response: 0102030405060708090A0B0C0D0E0F101112131415161718

NT-Response

La réponse NT de >= 24 octets calculée à partir du mot de passe de l'utilisateur et du défi LANMAN fourni. Typiquement, cela est fourni sur le réseau par un client souhaitant s'authentifier.

Exemples :

NT-Response: 0102030405060708090A0B0C0D0E0F10111213141516171

Password

Le mot de passe de l'utilisateur. Il serait fourni par un client réseau, si l'aide est utilisée dans une situation héritée qui expose les mots de passe en texte brut de cette manière.

Exemples :

Password: samba2

Password:: c2FtYmEy

Request-User-Session-Key

En cas d'authentification réussie, retourner la clé de session utilisateur associée à la connexion.

Exemples :

Request-User-Session-Key: Yes

Request-LanMan-Session-Key

En cas d'authentification réussie, retourner la clé de session LANMAN associée à la connexion.

Exemples :

Request-LanMan-Session-Key: Yes

Avertissement
Les implémenteurs doivent veiller à encoder en base64 toutes les données (telles que les noms d'utilisateur/mots de passe) qui pourraient contenir des données utilisateur malveillantes, telles qu'un saut de ligne. Ils pourraient également avoir besoin de décoder des chaînes provenant de l'aide, qui pourraient également avoir été encodées en base64.

--username=NOMUTILISATEUR

Spécifier le nom d'utilisateur à authentifier

--domain=DOMAINE

Spécifier le domaine de l'utilisateur à authentifier

--workstation=STATION

Spécifier la station de travail depuis laquelle l'utilisateur s'est authentifié

--challenge=CHAINE

Défi NTLM (en HEXADÉCIMAL)

--lm-response=REPONSE

Réponse LM au défi (en HEXADÉCIMAL)

--nt-response=REPONSE

Réponse NT ou NTLMv2 au défi (en HEXADÉCIMAL)

--password=MOTDEPASSE

Mot de passe en texte brut de l'utilisateur

S'il n'est pas spécifié sur la ligne de commande, il est demandé lorsque nécessaire.

Pour les rôles serveur basés sur NTLMSSP, ce paramètre spécifie le mot de passe attendu, permettant des tests sans que winbindd soit opérationnel.

--request-lm-key

Récupérer la clé de session LM

--request-nt-key

Demander la clé NT

--diagnostics

Effectuer des diagnostics sur la chaîne d'authentification. Utilise le mot de passe de --password ou en demande un.

--require-membership-of={SID|Nom}

Exiger qu'un utilisateur soit membre du groupe spécifié (nom ou SID) pour que l'authentification réussisse.

--pam-winbind-conf=NOMFICHIER

Définir le chemin vers le fichier pam_winbind.conf.

--target-hostname=NOMHOTE

Définir le nom d'hôte cible.

--target-service=SERVICE

Définir le service cible.

--use-cached-creds

Utiliser ou non les identifiants mis en cache par winbindd.

--allow-mschapv2

Autoriser explicitement MSCHAPv2.

--offline-logon

Autoriser les connexions hors ligne pour l'authentification en texte brut.

-?|--help

Afficher un résumé des options de la ligne de commande.

--usage

Afficher un bref message d'utilisation.

-d|--debuglevel=niveau

niveau est un entier de 0 à 10. La valeur par défaut si ce paramètre n'est pas spécifié est 1 pour les applications client.

Plus le niveau est élevé, plus les

his value, more detailed information will be logged to the log files about the server's activities. At level 0, only critical errors and serious warnings will be logged. Level 1 is a reasonable level for day-to-day operation - it generates a small amount of information about operations carried out.

Levels above 1 will generate considerable amounts of log data, and should only be used when investigating a problem. Levels above 3 are designed for use only by developers and generate HUGE amounts of log data, most of which is extremely cryptic.

--debug-stdout

This will redirect debug output to STDOUT. By default, all clients log to STDERR.

--configfile=<fichier de configuration>

The file specified contains the configuration details required by the client. The information in this file can be general for client and server or only provide client-specific options such as client smb encrypt. See /etc/samba/smb.conf for more information. The default configuration file name is determined at compile time.

--option=<name>=<value>

Set the smb.conf(5) option "<name>" to the value "<value>" from the command line. This overrides compiled-in defaults and options read from the configuration file. If a name or a value includes a space, wrap the whole --option=name=value into quotes.

-V|--version

Prints the program version number.

CONFIGURATION D'EXEMPLE

Pour configurer ntlm_auth pour une utilisation par squid 2.5, avec l'authentification de base et NTLMSSP, le code suivant doit être placé dans le fichier squid.conf.

auth_param ntlm program ntlm_auth --helper-protocol=squid-2.5-ntlmssp
auth_param basic program ntlm_auth --helper-protocol=squid-2.5-basic
auth_param basic children 5
auth_param basic realm Squid proxy-caching web server
auth_param basic credentialsttl 2 hours

Note

Cet exemple suppose que ntlm_auth a été installé dans votre PATH, et que les permissions de groupe sur winbindd_privileged sont telles que décrites ci-dessus.

Pour configurer ntlm_auth pour une utilisation par squid 2.5 avec limitation de groupe en plus de l'exemple ci-dessus, le code suivant doit être ajouté au fichier squid.conf.

auth_param ntlm program ntlm_auth --helper-protocol=squid-2.5-ntlmssp --require-membership-of='WORKGROUP\Domain Users'
auth_param basic program ntlm_auth --helper-protocol=squid-2.5-basic --require-membership-of='WORKGROUP\Domain Users'

DÉPANNAGE

If you're experiencing problems with authenticating Internet Explorer running under MS Windows 9X or Millennium Edition against ntlm_auth's NTLMSSP authentication helper (--helper-protocol=squid-2.5-ntlmssp), then please read the Microsoft Knowledge Base article #239869 and follow instructions described there.
