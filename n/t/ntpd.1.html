ntpd(1) Commandes utilisateur ntpd(1)

NOM

ntpd - Programme démon NTP

SYNTAXE

ntpd [-flags] [-flag [valeur]] [--nom-option[[=| ]valeur]] [ <serveur1> ... <serveurN> ]

DESCRIPTION

L'utilitaire ntpd est un démon du système d'exploitation qui règle et maintient l'heure système en synchronisation avec les serveurs de temps standard d'Internet. C'est une implémentation complète du Network Time Protocol (NTP) version 4, tel que défini par la RFC-5905, mais il conserve également la compatibilité avec la version 3, définie par la RFC-1305, et les versions 1 et 2, définies respectivement par les RFC-1059 et RFC-1119.

L'utilitaire ntpd effectue la plupart des calculs en arithmétique à virgule flottante 64 bits et effectue des opérations à point fixe 64 bits relativement maladroites uniquement lorsque cela est nécessaire pour préserver la précision ultime, environ 232 picosecondes. Bien que la précision ultime ne soit pas réalisable avec les stations de travail et les réseaux actuels, elle pourrait être requise avec de futures horloges CPU de gigahertz et des réseaux locaux (LAN) de gigabit.

Normalement, ntpd lit le fichier de configuration ntp.conf(5) au démarrage pour déterminer les sources de synchronisation et les modes de fonctionnement. Il est également possible de spécifier une configuration de travail, bien que limitée, entièrement sur la ligne de commande, ce qui évite le besoin d'un fichier de configuration. Cela peut être particulièrement utile lorsque l'hôte local doit être configuré comme un client broadcast/multicast, tous les pairs étant déterminés en écoutant les broadcasts au moment de l'exécution.

Si le support NetInfo est intégré à ntpd, alors ntpd tentera de lire sa configuration à partir de NetInfo si le fichier par défaut ntp.conf(5) ne peut pas être lu et qu'aucun fichier n'est spécifié par l'option -c.

Diverses variables internes de ntpd peuvent être affichées et les options de configuration modifiées pendant que ntpd est en exécution à l'aide des utilitaires ntpq(1) et ntpdc(1).

Lorsque ntpd démarre, il examine la valeur de umask(2), et si elle est nulle ntpd définira l'umask(2) à 022.

Permettre au premier ajustement d'être important. Cette option peut être utilisée un nombre illimité de fois.

Normalement, ntpd se termine avec un message dans le journal système si le décalage dépasse le seuil de panique, qui est de 1000 s par défaut. Cette option permet de régler l'heure à n'importe quelle valeur sans restriction ; cependant, cela ne peut se produire qu'une seule fois. Si le seuil est dépassé après cela, ntpd se terminera avec un message dans le journal système. Cette option peut être utilisée avec les options -q et -x. Voir la directive de fichier de configuration tinker pour d'autres options.

-G, --force-step-once

Appliquer un pas à toute correction de décalage initiale.

Normalement, ntpd ajuste l'heure par pas si le décalage d'heure dépasse le seuil de pas, qui est de 128 ms par défaut, et sinon, il fait glisser l'heure. Cette option force la correction du décalage initial à être appliquée par pas, afin que la plus haute précision temporelle puisse être atteinte rapidement. Cependant, cela peut aussi entraîner un recul de l'heure, donc cette option ne doit pas être utilisée si des applications nécessitant un temps de référence monotone sont en cours d'exécution. Voir la directive de fichier de configuration tinker pour d'autres options.

Répertoire de prison (chroot).

Chroot le serveur dans le répertoire jaildir. Cette option implique également que le serveur tente de renoncer aux privilèges root au démarrage. Vous pourriez avoir besoin de spécifier également une option -u. Cette option n'est disponible que si le système d'exploitation prend en charge l'ajustement de l'horloge sans privilèges root complets. Cette option est prise en charge sous NetBSD (configurer avec --enable-clockctl) ou Linux (configurer avec --enable-linuxcaps) ou Solaris (configurer avec --enable-solarisprivs).

Écouter sur un nom ou une adresse d'interface. Cette option peut être utilisée un nombre illimité de fois.

Ouvrir l'adresse réseau donnée, ou toutes les adresses associées au nom d'interface donné. Cette option peut apparaître plusieurs fois. Cette option implique également de ne pas ouvrir d'autres adresses, à l'exception de l'adresse générique et du localhost. Cette option est obsolète. Veuillez envisager d'utiliser la commande interface du fichier de configuration, qui est plus polyvalente.

Spécifier le nom et le chemin du fichier journal. Par défaut, il s'agit du fichier journal système. C'est la même opération que la directive de configuration logfile logfile.

-w nombre, --wait-sync=nombre

Secondes d'attente pour la première synchronisation de l'horloge. Cette option ne doit pas être combinée avec les options suivantes : nofork, quit, saveconfigquit. Cette option prend un nombre entier comme argument.

Si supérieur à zéro, modifie le comportement de ntpd lorsqu'il crée un processus fils pour devenir un démon. Au lieu de quitter avec le statut 0 immédiatement après la création du processus fils, le processus parent attend jusqu'au nombre de secondes spécifié que le processus fils synchronise l'horloge pour la première fois. Le statut de sortie est zéro (succès) si l'horloge a été synchronisée, sinon c'est ETIMEDOUT. Cela offre la possibilité à un script démarrant ntpd d'attendre facilement la première définition de l'horloge avant de continuer.

-x, --slew

Dépassement de 600 secondes.

Normalement, l'heure est corrigée si le décalage est inférieur au seuil de correction, qui est de 128 ms par défaut, et ajustée si supérieur au seuil. Cette option définit le seuil à 600 s, ce qui est bien dans la fenêtre de précision pour régler l'horloge manuellement. Note : Étant donné que le taux de correction des noyaux Unix typiques est limité à 0,5 ms/s, chaque seconde d'ajustement nécessite un intervalle d'amortissement de 2000 s. Ainsi, un ajustement de 600 s prendra près de 14 jours pour s'achever. Cette option peut être utilisée avec les options -g et -q. Voir la directive de configuration tinker pour d'autres options. Note : La discipline de l'horloge du noyau est désactivée avec cette option.

Tente de substituer le compteur CPU à QueryPerformanceCounter. Le compteur CPU et QueryPerformanceCounter sont comparés, et s'ils ont la même fréquence, le compteur CPU (RDTSC sur x86) est utilisé directement, évitant ainsi la surcharge d'un appel système.

--pccfreq=chaîne

Forcer l'utilisation du compteur de cycles CPU (Windows uniquement).

Force la substitution du compteur CPU pour QueryPerformanceCounter. Le compteur CPU (RDTSC sur x86) est utilisé inconditionnellement avec la fréquence donnée (en Hz).

-m, --mdns

S'enregistrer avec mDNS en tant que serveur NTP.

S'enregistre en tant que serveur NTP auprès du serveur mDNS local, ce qui permet au serveur d'être découvert via une recherche client mDNS.

UTILISATION

Comment NTP Fonctionne

L'utilitaire ntpd fonctionne en échangeant des messages avec un ou plusieurs serveurs configurés sur une plage d'intervalles de sondage désignés. Lors du démarrage, que ce soit pour la première ou les fois suivantes, le programme nécessite plusieurs échanges de la majorité de ces serveurs pour que le traitement du signal et les algorithmes d'atténuation puissent accumuler et nettoyer les données et régler l'horloge. Afin de protéger le réseau contre les rafales, l'intervalle de sondage initial pour chaque serveur est retardé d'un intervalle aléatoire sur quelques secondes. Avec un intervalle de sondage initial par défaut de 64 s, plusieurs minutes peuvent s'écouler avant que l'horloge ne soit réglée. Ce délai initial pour régler l'horloge peut être réduit de manière sûre et spectaculaire en utilisant le mot-clé iburst avec la commande de configuration server, comme décrit dans ntp.conf(5).

La plupart des systèmes d'exploitation et du matériel actuels intègrent une puce d'heure (TOY) pour maintenir l'heure pendant les périodes où l'alimentation est coupée. Lorsque la machine démarre, la puce est utilisée pour initialiser l'heure du système d'exploitation. Une fois la machine synchronisée avec un serveur NTP, le système d'exploitation corrige la puce de temps en temps. Dans le cas par défaut, si ntpd détecte que l'heure de l'hôte est à plus de 1000 s de l'heure du serveur, ntpd suppose qu'il y a un problème majeur et que la seule action fiable est que l'opérateur intervienne et règle l'horloge manuellement. (Les raisons de cela incluent l'absence de puce TOY, sa batterie morte, ou simplement une mauvaise qualité de la puce TOY.) Cela provoque la sortie de ntpd avec un message de panique dans le journal système. L'option -g remplace cette vérification et l'horloge sera réglée à l'heure du serveur, quel que soit l'heure de la puce (jusqu'à 68 ans dans le passé ou le futur – c'est une limitation du protocole NTPv4). Cependant, et pour protéger contre le matériel défectueux, comme lorsqu'une pile CMOS est défaillante ou qu'un compteur d'horloge devient défectueux, une fois l'horloge réglée, une erreur supérieure à 1000 s provoquera quand même la sortie de ntpd.

Dans des conditions normales, ntpd ajuste l'horloge par petits pas de manière à ce que l'échelle de temps soit effectivement continue et sans discontinuités. Dans des conditions de congestion extrême du réseau, le jitter du délai aller-retour peut dépasser trois secondes et la distance de synchronisation, qui est égale à la moitié du délai aller-retour plus les termes de budget d'erreur, peut devenir très grande. Les algorithmes de ntpd rejetent les décalages d'échantillons dépassant 128 ms, à moins que l'intervalle pendant lequel aucun décalage d'échantillon n'est inférieur à 128 ms ne dépasse 900 s. Le premier échantillon après cela, quel que soit le décalage, ajuste l'horloge à l'heure indiquée. En pratique

ce ceci réduit le taux de fausses alarmes où l'horloge est incrémentée par erreur à un incident d'une incidence négligeable.

En raison de ce comportement, une fois l'horloge réglée, elle s'écarte très rarement de plus de 128 ms, même dans des cas extrêmes de congestion et de gigue du chemin réseau. Parfois, en particulier lorsque ntpd est démarré pour la première fois sans fichier de dérive valide sur un système avec une dérive intrinsèque importante, l'erreur peut croître au point de dépasser 128 ms, ce qui amènerait l'horloge à être reculée si l'heure de l'horloge locale est plus de 128 s dans le futur par rapport au serveur. Dans certaines applications, ce comportement peut être inacceptable. Il existe cependant plusieurs solutions. Si l'option -x est incluse dans la ligne de commande, l'horloge ne sera jamais incrémentée et seules des corrections de lenteur seront utilisées. Mais ce choix a un coût qui doit être soigneusement étudié avant de décider d'utiliser l'option -x. Le taux de lenteur maximal possible est limité à 500 parties par million (PPM) en raison des principes de correction sur lesquels le protocole NTP et la conception de l'algorithme sont basés. En conséquence, l'horloge locale peut prendre beaucoup de temps à converger vers un décalage acceptable, environ 2 000 s pour chaque seconde où l'horloge est en dehors de la plage acceptable. Pendant cet intervalle, l'horloge locale ne sera pas cohérente avec toute autre horloge réseau et le système ne pourra pas être utilisé pour des applications distribuées qui nécessitent une heure réseau correctement synchronisée.

Malgré les précautions ci-dessus, il arrive que lorsque de grandes erreurs de fréquence sont présentes, les décalages temporels résultants s'écartent de la plage de 128 ms et qu'une correction de temps par incrémentation ou lenteur soit nécessaire. Si, après une telle correction, l'erreur de fréquence est telle que le premier échantillon est en dehors de la plage acceptable, ntpd entre dans le même état que lorsque le fichier ntp.drift n'est pas présent. L'intention de ce comportement est de corriger rapidement la fréquence et de rétablir le fonctionnement en mode de suivi normal. Dans les cas les plus extrêmes (l'hôte time.ien.it vient à l'esprit), il peut y avoir des corrections occasionnelles par incrémentation/lenteur et des corrections de fréquence ultérieures. Il est utile dans ces cas d'utiliser le mot-clé burst lors de la configuration du serveur, mais UNIQUEMENT lorsque vous avez la permission de le faire de la part du propriétaire de l'hôte cible.

Enfin, par le passé, de nombreux scripts de démarrage exécutaient ntpdate(1) ou sntp(1) pour rapprocher l'horloge système de la correction avant de démarrer ntpd(1), mais ce n'était jamais qu'un hack médiocre et n'est plus nécessaire. Si vous suivez les instructions dans Démarrage de NTP (Meilleure pratique actuelle) et que vous avez toujours besoin de régler l'heure système avant de démarrer ntpd, veuillez ouvrir un rapport de bug et documenter ce qui se passe, puis envisagez d'utiliser sntp(1) si vous avez vraiment besoin de régler l'horloge avant de démarrer ntpd .

Il existe une façon de démarrer ntpd(1) qui résout souvent tous les problèmes mentionnés ci-dessus.

Démarrage de NTP (Meilleure pratique actuelle)

Tout d'abord, utilisez l'option iburst sur vos entrées server.

Si vous pouvez également conserver un bon fichier ntp.drift, ntpd(1) redémarrera effectivement en mode "chaud" et l'horloge de votre système sera stable en moins de 11 secondes.

Dès que possible dans la séquence de démarrage, démarrez ntpd(1) avec au moins les options -g et éventuellement -N . Ensuite, démarrez le reste de vos processus "normaux". Cela donnera à ntpd(1) le plus de temps possible pour synchroniser et stabiliser l'horloge du système.

Enfin, si vous avez des processus comme dovecot ou des serveurs de base de données qui nécessitent un temps qui augmente de manière monotone, exécutez ntp-wait(1) le plus tard possible dans la séquence de démarrage (peut-être avec le drapeau -v) et après que ntp-wait(1) se soit terminé avec succès , il est aussi sûr qu'il le sera jamais de démarrer tout processus qui nécessite un temps stable.

Discipline de fréquence

Le comportement de ntpd au démarrage dépend de l'existence du fichier de fréquence, généralement ntp.drift. Ce fichier contient la dernière estimation de l'erreur de fréquence de l'horloge. Lorsque ntpd est démarré et que le fichier n'existe pas, ntpd entre dans un mode spécial conçu pour s'adapter rapidement à l'oscillateur d'horloge système spécifique et à son erreur de fréquence. Cela prend environ 15 minutes, après quoi l'heure et la fréquence sont réglées sur des valeurs nominales et ntpd entre en mode normal, où l'heure et la fréquence sont suivies en continu par rapport au serveur. Après une heure, le fichier de fréquence est créé et l'erreur de fréquence actuelle y est écrite. Lorsque ntpd est démarré et que le fichier existe, la fréquence de ntpd est initialisée à partir du fichier et il entre immédiatement en mode normal. Après cela, l'erreur de fréquence actuelle est écrite dans le fichier à intervalles horaires.

Modes de fonctionnement

L'utilitaire ntpd peut fonctionner dans plusieurs modes, notamment actif/passif symétrique, client/serveur diffusion/multidiffusion et manycast, tels que décrits sur la page "Gestion des associations" (disponible dans la documentation HTML fournie dans /usr/share/doc/ntp). Il fonctionne normalement en continu tout en surveillant les petits changements de fréquence et en ajustant l'horloge pour une précision ultime. Cependant, il peut fonctionner en mode unique où l'heure est réglée à partir d'un serveur externe et la fréquence est réglée à partir d'un fichier de fréquence enregistré précédemment. Un client de diffusion/multidiffusion ou manycast peut découvrir des serveurs distants, calculer des facteurs de correction de délai de propagation serveur-client et se configurer automatiquement. Cela permet de déployer un parc de postes de travail sans spécifier les détails de configuration spécifiques à l'environnement local.

Par défaut, ntpd fonctionne en mode continu où chacun des serveurs externes potentiels est interrogé à des intervalles déterminés par un automate complexe. L'automate mesure la gigue du délai aller-retour incident et la dérive de la fréquence de l'oscillateur et détermine le meilleur intervalle d'interrogation à l'aide d'un algorithme heuristique. Normalement, et dans la plupart des environnements d'exploitation, l'automate commencera avec des intervalles de 64 s et augmentera éventuellement par paliers jusqu'à 1024 s. Une petite quantité de variation aléatoire est introduite afin d'éviter le regroupement au niveau des serveurs. De plus, si un serveur devient inaccessible pendant un certain temps, l'intervalle d'interrogation est augmenté par paliers jusqu'à 1024 s afin de réduire la surcharge réseau.

Dans certains cas, il peut ne pas être pratique pour ntpd de fonctionner en continu. Une solution courante a été d'exécuter les programmes ntpdate(1) ou sntp(1) à partir d'une tâche cron(8) à des moments désignés. Cependant, ces programmes n'ont pas le traitement du signal, la vérification des erreurs ou les algorithmes d'atténuation sophistiqués de ntpd. L'option -q est destinée à cet usage. La définition de cette option amène ntpd à quitter juste après avoir réglé l'horloge pour la première fois. La procédure de réglage initial de l'horloge est la même qu'en mode continu ; la plupart des applications voudront probablement spécifier le mot-clé iburst avec la commande de configuration server. Avec ce mot-clé, une série de messages sont échangés pour affiner les données et l'horloge est réglée en environ 10 s. Si rien n'est entendu après quelques minutes, le démon expire et quitte. Après une période de deuil appropriée, le programme ntpdate(1) sera retiré.

Lorsque le support du noyau est disponible pour discipliner la fréquence de l'horloge, ce qui est le cas pour Solaris standard, Tru64, Linux et FreeBSD, une fonctionnalité utile est disponible pour discipliner la fréquence de l'horloge. Tout d'abord, ntpd est exécuté en mode continu avec des serveurs sélectionnés afin de mesurer et d'enregistrer l'erreur de fréquence intrinsèque de l'horloge dans le fichier de fréquence. Il peut falloir plusieurs heures pour que la fréquence et le décalage se stabilisent. Ensuite, ntpd est arrêté et exécuté en mode unique selon les besoins. À chaque démarrage, la fréquence est lue dans le fichier et initialise la fréquence du noyau.

Contrôle de l'intervalle d'interrogation

Cette version de NTP inclut un automate complexe pour réduire la charge réseau tout en maintenant une qualité de synchronisation cohérente avec la gigue et la dérive observées. Il existe plusieurs façons de personnaliser le fonctionnement pour améliorer la précision en réduisant l'intervalle ou pour réduire la charge réseau en l'augmentant. Cependant, l'utilisateur est conseillé de considérer attentivement les conséquences de la modification de la plage d'ajustement de l'interrogation, qui passe par défaut de 64 s à 1 024 s. Le minimum par défaut peut être modifié avec la commande tinker minpoll à une valeur d'au moins 16 s. Cette valeur est utilisée pour toutes les associations configurées, sauf si elle est remplacée par l'option minpoll sur la commande de configuration. Notez que la plupart des pilotes de périphériques ne fonctionneront pas correctement si l'intervalle d'interrogation est inférieur à 64 s et que les associations de serveurs de diffusion et de clients manycast utiliseront également la valeur par défaut, sauf indication contraire.

Dans certains cas impliquant des services commutés ou à péage, il peut être utile d'augmenter l'intervalle minimum à quelques dizaines de minutes et l'intervalle maximum à un jour environ. Dans des conditions de fonctionnement normales, une fois la boucle de discipline de l'horloge stabilisée, l'intervalle sera augmenté par paliers du minimum au maximum. Cependant, cela suppose que l'erreur de fréquence intrinsèque de l'horloge est suffisamment faible pour que la boucle de discipline puisse la corriger. La plage de capture de la boucle est de 500 PPM à un intervalle de 64 s, diminuant d'un facteur deux pour chaque doublement de l'intervalle. À un minimum de 1 024 s, par exemple, la plage de capture n'est que de 31 PPM. Si l'erreur intrinsèque est supérieure à celle-ci, le fichier de dérive ntp.drift devra être spécialement adapté pour réduire l'erreur résiduelle en dessous de cette limite. Une fois cela fait, le fichier de dérive est automatiquement mis à jour une fois par heure et est disponible pour initialiser la fréquence lors des redémarrages ultérieurs du démon.

Le filtre huff-n'-puff

Dans les scénarios où une quantité considérable de données doit être téléchargée ou téléversée sur des modems téléphoniques, la qualité de la mesure du temps peut être sérieusement dégradée. Cela se produit parce que les délais différentiels dans les deux directions de transmission peuvent être assez importants. Dans de nombreux cas, les erreurs de temps apparentes sont si importantes qu'elles dépassent le seuil d'incrémentation et une correction par incrémentation peut se produire pendant et après le transfert de données. DESCRIPTION

Le démon ntpd implémente le protocole NTP (Network Time Protocol) et doit être exécuté par l'administrateur du système pour synchroniser l'horloge du système. Il est conçu pour être un serveur NTP puissant et précis, mais il peut également être configuré pour agir comme un client. Il gère les décalages et les variations de fréquence du quartz de l'horloge de l'ordinateur.

Le protocole NTP est décrit dans la RFC 1305.

L'option -d active des messages de débogage et peut être spécifiée plusieurs fois pour augmenter le niveau de détail.

L'option -D définit le niveau de débogage global à un niveau spécifique. Les niveaux de débogage sont divisés en modules, chacun ayant un niveau de débogage séparé.

L'option -g permet de régler l'horloge même si le décalage initial est important.

L'option -p spécifie le fichier où écrire le PID du processus ntpd.

L'option -P définit la priorité du processus ntpd.

L'option -r spécifie un fichier qui contiendra le résultat du calcul de la dérive de l'horloge.

L'option -s affiche les statistiques des paquets NTP.

L'option -S désactive le réglage automatique de l'horloge.

L'option -t spécifie une adresse IPv4 ou IPv6 pour laquelle ntpd doit configurer des sources de temps.

L'option -V affiche la version de ntpd.

L'option -v affiche le message d'aide.

Le fichier de configuration ntp.conf peut être spécifié avec l'option -c.

L'option -i permet de spécifier un répertoire différent pour les fichiers de configuration.

L'option -k permet de spécifier un fichier différent pour les clés d'authentification.

L'option -l permet de spécifier un fichier différent pour les journaux.

L'option -a désactive la vérification de la mise à jour automatique de l'horloge.

L'option -A active la mise à jour automatique de l'horloge.

Le filtre huff-n'-puff est conçu pour corriger le décalage temporel apparent dans ces cas. Il dépend de la connaissance du délai de propagation lorsqu'aucun autre trafic n'est présent. Dans les scénarios courants, cela se produit en dehors des heures de travail. Le filtre maintient un registre à décalage qui mémorise le délai minimum sur l'intervalle le plus récent, généralement mesuré en heures. Dans des conditions de délai sévère, le filtre corrige le décalage apparent en utilisant le signe du décalage et la différence entre le délai apparent et le délai minimum. Le nom du filtre reflète la correction négative (huff) et positive (puff), qui dépend du signe du décalage.

Le filtre est activé par la commande tinker et le mot-clé huffpuff, comme décrit dans ntp.conf(5).
