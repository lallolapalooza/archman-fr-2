open_by_handle_at(2) Manuel des appels système open_by_handle_at(2)

NOM

name_to_handle_at, open_by_handle_at - obtenir un descripteur pour un chemin et ouvrir un fichier via un descripteur

BIBLIOTHÈQUE

Bibliothèque C standard (libc, -lc)

SYNTAXE

#define _GNU_SOURCE         /* Voir feature_test_macros(7) */
#include <fcntl.h>
int name_to_handle_at(int dirfd, const char *path,
                      struct file_handle *handle,
                      int *mount_id, int flags);
int open_by_handle_at(int mount_fd, struct file_handle *handle,
                      int flags);

DESCRIPTION

Les appels système name_to_handle_at() et open_by_handle_at() divisent la fonctionnalité de openat(2) en deux parties : name_to_handle_at() renvoie un descripteur opaque qui correspond à un fichier spécifié ; open_by_handle_at() ouvre le fichier correspondant à un descripteur renvoyé par un appel précédent à name_to_handle_at() et renvoie un descripteur de fichier ouvert.

name_to_handle_at()

L'appel système name_to_handle_at() renvoie un descripteur de fichier et un ID de montage correspondant au fichier spécifié par les arguments dirfd et path. Le descripteur de fichier est renvoyé via l'argument handle, qui est un pointeur vers une structure de la forme suivante :


struct file_handle {
    unsigned int  handle_bytes;   /* Taille de f_handle [in, out] */
    int           handle_type;    /* Type de descripteur [out] */
    unsigned char f_handle[0];    /* Identifiant de fichier (taille
                                     allouée par l'appelant) [out] */
};

Il incombe à l'appelant d'allouer la structure avec une taille suffisante pour contenir le descripteur renvoyé dans f_handle. Avant l'appel, le champ handle_bytes doit être initialisé pour contenir la taille allouée pour f_handle. (La constante MAX_HANDLE_SZ, définie dans <fcntl.h>, spécifie la taille maximale attendue pour un descripteur de fichier. Ce n'est pas une limite supérieure garantie car les futurs systèmes de fichiers peuvent nécessiter plus d'espace.) Après un retour réussi, le champ handle_bytes est mis à jour pour contenir le nombre d'octets effectivement écrits dans f_handle.

L'appelant peut découvrir la taille requise pour la structure file_handle en effectuant un appel où handle->handle_bytes est zéro ; dans ce cas, l'appel échoue avec l'erreur EOVERFLOW et handle->handle_bytes est défini pour indiquer la taille requise ; l'appelant peut alors utiliser ces informations pour allouer une structure de la bonne taille (voir EXEMPLES ci-dessous). Il faut être prudent ici car EOVERFLOW peut également indiquer qu'aucun descripteur de fichier n'est disponible pour ce nom particulier dans un système de fichiers qui prend normalement en charge la recherche de descripteurs de fichier. Ce cas peut être détecté lorsque l'erreur EOVERFLOW est renvoyée sans que handle_bytes n'ait été augmenté.

Autre que l'utilisation du champ handle_bytes, l'appelant doit traiter la structure file_handle comme un type de données opaque : les champs handle_type et f_handle peuvent être utilisés dans un appel ultérieur à open_by_handle_at(). L'appelant peut également utiliser le file_handle opaque pour comparer l'identité des objets du système de fichiers qui ont été interrogés à différents moments et potentiellement à différents chemins. Le sous-système fanotify(7) peut signaler des événements avec un enregistrement d'informations contenant un file_handle pour identifier l'objet du système de fichiers.

L'argument flags est un masque de bits construit en combinant par OR zéro ou plusieurs des drapeaux AT_HANDLE_FID, AT_HANDLE_MNT_ID_UNIQUE, AT_HANDLE_CONNECTABLE, AT_EMPTY_PATH et AT_SYMLINK_FOLLOW, décrits ci-dessous.

Lorsque flags contient le drapeau AT_HANDLE_FID (depuis Linux 6.5), l'appelant indique que le file_handle renvoyé est nécessaire pour identifier l'objet du système de fichiers, et non pour ouvrir le fichier ultérieurement, il faut donc s'attendre à ce qu'un appel ultérieur à open_by_handle_at() avec le file_handle renvoyé puisse échouer.

Lorsque flags contient le drapeau AT_HANDLE_MNT_ID_UNIQUE (depuis Linux 6.12), l'appelant indique que la largeur du tampon mount_id est d'au moins 64 bits, et ensuite l'ID de montage renvoyé dans ce tampon est l'ID de montage unique comme celui renvoyé par statx(2) avec le drapeau STATX_MNT_ID_UNIQUE.

Lorsque flags contient le drapeau AT_HANDLE_CONNECTABLE (depuis Linux 6.13), l'appelant indique que le file_handle renvoyé est nécessaire pour ouvrir un fichier avec un chemin connu plus tard, il faut donc s'attendre à ce qu'un appel ultérieur à open_by_handle_at() avec le file_handle renvoyé puisse échouer si le fichier a été déplacé, mais sinon, le chemin du fichier ouvert devrait être visible depuis le lien magique /proc/pid/fd/*. Ce drapeau ne peut pas être utilisé en combinaison avec les drapeaux AT_HANDLE_FID et/ou AT_EMPTY_PATH.

Ensemble, les arguments path et dirfd identifient le fichier pour lequel un descripteur doit être obtenu. Il existe quatre cas distincts :

•
Si path est une chaîne non vide contenant un chemin absolu, alors un descripteur est renvoyé pour le fichier auquel ce chemin fait référence. Dans ce cas, dirfd est ignoré.
•
Si path est une chaîne non vide contenant un chemin relatif et dirfd a la valeur spéciale AT_FDCWD, alors path est interprété par rapport au répertoire de travail actuel de l'appelant, et un descripteur est renvoyé pour le fichier auquel il fait référence.
•
Si path est une chaîne non vide contenant un chemin relatif et dirfd est un descripteur de fichier faisant référence à un répertoire, alors path est interprété par rapport au répertoire référencé par dirfd, et un descripteur est renvoyé pour le fichier auquel il fait référence. (Voir openat(2) pour une explication de l'utilité des "descripteurs de fichiers de répertoire".)
•
Si path est une chaîne vide et flags spécifie la valeur AT_EMPTY_PATH, alors dirfd peut être un descripteur de fichier ouvert faisant référence à n'importe quel type de fichier, ou AT_FDCWD, signifiant le répertoire de travail actuel, et un descripteur est renvoyé pour le fichier auquel il fait référence.

L'argument mount_id renvoie un identifiant pour le montage du système de fichiers qui correspond à path. Ceci correspond au premier champ dans l'un des enregistrements de /proc/self/mountinfo. Ouvrir le chemin dans le cinquième champ de cet enregistrement renvoie un descripteur de fichier pour le point de montage ; ce descripteur de fichier peut être utilisé dans un appel ultérieur à open_by_handle_at(). mount_id est renvoyé à la fois pour un appel réussi et pour un appel qui aboutit à l'erreur EOVERFLOW.

Par défaut, name_to_handle_at() ne déréférence pas path s'il s'agit d'un lien symbolique, et renvoie donc un descripteur pour le lien lui-même. Si AT_SYMLINK_FOLLOW est spécifié dans flags, path est déréférencé s'il s'agit d'un lien symbolique (afin que l'appel renvoie un descripteur pour le fichier auquel le lien fait référence).

name_to_handle_at() ne déclenche pas de montage lorsque le dernier composant du chemin est un point d'automontage. Lorsqu'un système de fichiers prend en charge à la fois les descripteurs de fichier et les points d'automontage, un appel name_to_handle_at() sur un point d'automontage renverra avec l'erreur EOVERFLOW sans avoir augmenté handle_bytes. Cela peut se produire depuis Linux 4.13 avec NFS lors de l'accès à un répertoire qui se trouve sur un système de fichiers séparé sur le serveur. Dans ce cas, l'automontage peut être déclenché en ajoutant un "/" à la fin du chemin.

open_by_handle_at()

L'appel système open_by_handle_at() ouvre le fichier référencé par handle, un descripteur de fichier renvoyé par un appel précédent à name_to_handle_at().

L'argument mount_fd est un descripteur de fichier pour tout objet (fichier, répertoire, etc.) dans le système de fichiers monté par rapport auquel handle doit être interprété. La valeur spéciale AT_FDCWD peut être spécifiée, signifiant le répertoire de travail actuel de l'appelant.

L'argument flags est le même que pour open(2). Si handle fait référence à un lien symbolique, l'appelant doit spécifier le drapeau O_PATH, et le s

  • Le lien symbolique n'est pas dés-référencé ; le drapeau O_NOFOLLOW, s'il est spécifié, est ignoré.

  • L'appelant doit posséder la capacité CAP_DAC_READ_SEARCH pour invoquer open_by_handle_at().

VALEUR DE RETOUR

En cas de succès, name_to_handle_at() renvoie 0, et open_by_handle_at() renvoie un descripteur de fichier (un entier non négatif).

En cas d'erreur, les deux appels système renvoient -1 et définissent errno pour indiquer l'erreur.

ERREURS

name_to_handle_at() et open_by_handle_at() peuvent échouer pour les mêmes erreurs que openat(2). De plus, elles peuvent échouer avec les erreurs notées ci-dessous.

name_to_handle_at() peut échouer avec les erreurs suivantes :

EFAULT
path, mount_id, ou handle pointe en dehors de votre espace d'adressage accessible.
EINVAL
flags inclut une valeur de bit invalide ou une combinaison de bits invalide.
EINVAL
handle->handle_bytes est supérieur à MAX_HANDLE_SZ.
ENOENT
path est une chaîne vide, mais AT_EMPTY_PATH n'a pas été spécifié dans flags.
ENOTDIR
Le descripteur de fichier fourni dans dirfd ne fait pas référence à un répertoire, et il n'est pas vrai que flags inclut AT_EMPTY_PATH et que path est une chaîne vide.
EOPNOTSUPP
Le système de fichiers ne prend pas en charge le décodage d'un nom de chemin en un handle de fichier.
EOVERFLOW
La valeur handle->handle_bytes passée à l'appel était trop petite. Lorsque cette erreur se produit, handle->handle_bytes est mis à jour pour indiquer la taille requise pour le handle.

open_by_handle_at() peut échouer avec les erreurs suivantes :

EBADF
mount_fd n'est pas un descripteur de fichier ouvert.
EBADF
path est relatif mais dirfd n'est ni AT_FDCWD ni un descripteur de fichier valide.
EFAULT
handle pointe en dehors de votre espace d'adressage accessible.
EINVAL
handle->handle_bytes est supérieur à MAX_HANDLE_SZ ou est égal à zéro.
ELOOP
handle fait référence à un lien symbolique, mais O_PATH n'a pas été spécifié dans flags.
EPERM
L'appelant ne possède pas la capacité CAP_DAC_READ_SEARCH.
ESTALE
Le handle spécifié n'est pas valide pour ouvrir un fichier. Cette erreur se produira si, par exemple, le fichier a été supprimé. Cette erreur peut également se produire si le handle a été acquis en utilisant le drapeau AT_HANDLE_FID et que le système de fichiers ne prend pas en charge open_by_handle_at(). Cette erreur peut également se produire si le handle a été acquis en utilisant le drapeau AT_HANDLE_CONNECTABLE et que le fichier a été déplacé vers un parent différent.

VERSIONS

FreeBSD possède une paire d'appels système largement similaire sous la forme de getfh() et fhopen().

NORMES

Linux.

HISTORIQUE

Linux 2.6.39, glibc 2.14.

NOTES

Un handle de fichier peut être généré dans un processus en utilisant name_to_handle_at() et utilisé plus tard dans un processus différent qui appelle open_by_handle_at().

Certains systèmes de fichiers ne prennent pas en charge la traduction des noms de chemin en handles de fichier, par exemple, /proc, /sys, et divers systèmes de fichiers réseau. Certains systèmes de fichiers prennent en charge la traduction des noms de chemin en handles de fichier, mais ne prennent pas en charge l'utilisation de ces handles de fichier dans open_by_handle_at().

Un handle de fichier peut devenir invalide ("périmé") si un fichier est supprimé, ou pour d'autres raisons spécifiques au système de fichiers. Les handles invalides sont signalés par une erreur ESTALE de open_by_handle_at().

Ces appels système sont conçus pour être utilisés par des serveurs de fichiers en espace utilisateur. Par exemple, un serveur NFS en espace utilisateur pourrait générer un handle de fichier et le transmettre à un client NFS. Plus tard, lorsque le client souhaite ouvrir le fichier, il peut renvoyer le handle au serveur. Ce type de fonctionnalité permet à un serveur de fichiers en espace utilisateur de fonctionner de manière sans état par rapport aux fichiers qu'il dessert.

Si path fait référence à un lien symbolique et que flags ne spécifie pas AT_SYMLINK_FOLLOW, alors name_to_handle_at() renvoie un handle pour le lien (plutôt que pour le fichier auquel il fait référence). Le processus recevant le handle peut ensuite effectuer des opérations sur le lien symbolique en convertissant le handle en descripteur de fichier à l'aide de open_by_handle_at() avec le drapeau O_PATH, puis en passant le descripteur de fichier comme argument dirfd dans des appels système tels que readlinkat(2) et fchownat(2).

Obtention d'un identifiant de système de fichiers persistant

Les identifiants de montage dans /proc/self/mountinfo peuvent être réutilisés lorsque les systèmes de fichiers sont démontés et remontés. Par conséquent, l'identifiant de montage renvoyé par name_to_handle_at() (dans *mount_id) ne doit pas être traité comme un identifiant persistant pour le système de fichiers monté correspondant. Cependant, une application peut utiliser les informations dans l'enregistrement mountinfo qui correspond à l'identifiant de montage pour dériver un identifiant persistant.

Par exemple, on peut utiliser le nom de périphérique dans le cinquième champ de l'enregistrement mountinfo pour rechercher l'UUID du périphérique correspondant via les liens symboliques dans /dev/disks/by-uuid. (Une manière plus confortable d'obtenir l'UUID est d'utiliser la bibliothèque libblkid(3).) Ce processus peut ensuite être inversé, en utilisant l'UUID pour rechercher le nom du périphérique, puis obtenir le point de montage correspondant, afin de produire l'argument mount_fd utilisé par open_by_handle_at().

EXEMPLES

Les deux programmes ci-dessous démontrent l'utilisation de name_to_handle_at() et open_by_handle_at(). Le premier programme (t_name_to_handle_at.c) utilise name_to_handle_at() pour obtenir le handle de fichier et l'identifiant de montage pour le fichier spécifié dans son argument de ligne de commande ; le handle et l'identifiant de montage sont écrits sur la sortie standard.

Le second programme (t_open_by_handle_at.c) lit un identifiant de montage et un handle de fichier depuis l'entrée standard. Le programme emploie ensuite open_by_handle_at() pour ouvrir le fichier en utilisant ce handle. Si un argument de ligne de commande optionnel est fourni, alors l'argument mount_fd pour open_by_handle_at() est obtenu en ouvrant le répertoire nommé dans cet argument. Sinon, mount_fd est obtenu en parcourant /proc/self/mountinfo pour trouver un enregistrement dont l'identifiant de montage correspond à l'identifiant de montage lu depuis l'entrée standard, et le répertoire de montage spécifié dans cet enregistrement est ouvert. (Ces programmes ne traitent pas le fait que les identifiants de montage ne sont pas persistants.)

La session shell suivante démontre l'utilisation de ces deux programmes :


$ echo 'Can you please think about it?' > cecilia.txt;
$ ./t_name_to_handle_at cecilia.txt > fh;
$ ./t_open_by_handle_at < fh;
open_by_handle_at: Operation not permitted
$ sudo ./t_open_by_handle_at < fh;      # Need CAP_SYS_ADMIN
Read 31 bytes
$ rm cecilia.txt;

Maintenant, nous supprimons et recréons (rapidement) le fichier de sorte qu'il ait le même contenu et (par hasard) le même inode. Néanmoins, open_by_handle_at() reconnaît que le fichier d'origine auquel le handle de fichier faisait référence n'existe plus.


$ stat --printf="%i\n" cecilia.txt;     # Display inode number
4072121
$ rm cecilia.txt;
$ echo 'Can you please think about it?' > cecilia.txt;
$ stat --printf="%i\n" cecilia.txt;     # Check inode number
4072121
$ sudo ./t_open_by_handle_at < fh;
open_by_handle_at: Stale NFS file handle

Source du programme: t_name_to_handle_at.c

#define _GNU_SOURCE
#include <err.h>
#include <errno.h>
#include <fcntl.h>
#include <stdio.h>
#include <stdlib.h>
int
main(int argc, char *argv[])
{
    int                 mount_id, fhsize, flags, dirfd;
    char                *path;
    struct file_handle  *fhp;
    if (argc != 2) {
        fprintf(stderr, "Usage: %s path\n", argv[0]);
        exit(EXIT_FAILURE);
    }
    path = argv[1];
    /* Allocate file_handle structure.  */
    fhsize = sizeof(*fhp);
    fhp = malloc(fhsize);
    if (fhp == NULL)
        err(EXIT_FAILURE, "malloc");
    /* Make an initial call to name_to_handle_at() to discover
       the size required for file handle.  */
    dirfd = AT_FDCWD;           /* For name_to_handle_at() calls */
    flags = 0;                  /* For name_to_handle_at() calls */
    fhp->handle_bytes = 0;
    if (name_to_handle_at(dirfd, path, fhp, &mount_id, flags) != -1
        || errno != EOVERFLOW)
    {
        fprintf(stderr, "Unexpected result from name_to_handle_at()\n");
        exit(EXIT_FAILURE);
    }
    /* Reallocate file_handle structure with correct size.  */
    fhsize = sizeof(*fhp) + fhp->handle_bytes;
    fhp = realloc(fhp, fhsize);         /* Copies fhp->handle_bytes */
    if (fhp == NULL)
        err(EXIT_FAILURE, "realloc");
    /* Get file handle from pathname supplied on command line.  */
    if (name_to_handle_at(dirfd, path, fhp, &mount_id, flags) == -1)
        err(EXIT_FAILURE, "name_to_handle_at");
    /* Write mount ID, file handle size, and file handle to stdout,
       for later reuse by t_open_by_handle_at.c.  */
    printf("
;%d\n", mount_id);
    printf("%u %d   ", fhp->handle_bytes, fhp->handle_type);
    for (size_t j = 0; j < fhp->handle_bytes; j++)
        printf(" %02x", fhp->f_handle[j]);
    printf("\n");
    exit(EXIT_SUCCESS);
}

Source du programme : t_open_by_handle_at.c

#define _GNU_SOURCE
#include <err.h>
#include <fcntl.h>
#include <limits.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/types.h>
#include <unistd.h>
/* Analyse /proc/self/mountinfo pour trouver la ligne dont l'ID de montage correspond
   à 'mount_id'.  (Une façon plus simple de le faire est d'installer et d'utiliser la
   bibliothèque 'libmount' fournie par le projet 'util-linux'.)
   Ouvre le chemin de montage correspondant et renvoie le descripteur de fichier résultant.  */
static int
open_mount_path_by_id(int mount_id)
{
    int      mi_mount_id, found;
    char     mount_path[PATH_MAX];
    char     *linep;
    FILE     *fp;
    size_t   lsize;
    ssize_t  nread;
    fp = fopen("/proc/self/mountinfo", "r");
    if (fp == NULL)
        err(EXIT_FAILURE, "fopen");
    found = 0;
    linep = NULL;
    while (!found) {
        nread = getline(&linep, &lsize, fp);
        if (nread == -1)
            break;
        nread = sscanf(linep, "%d %*d %*s %*s %s",
                       &mi_mount_id, mount_path);
        if (nread != 2) {
            fprintf(stderr, "Mauvais sscanf()\n");
            exit(EXIT_FAILURE);
        }
        if (mi_mount_id == mount_id)
            found = 1;
    }
    free(linep);
    fclose(fp);
    if (!found) {
        fprintf(stderr, "Impossible de trouver le point de montage\n");
        exit(EXIT_FAILURE);
    }
    return open(mount_path, O_RDONLY);
}
int
main(int argc, char *argv[])
{
    int                 mount_id, fd, mount_fd, handle_bytes;
    char                buf[1000];
#define LINE_SIZE 100
    char                line1[LINE_SIZE], line2[LINE_SIZE];
    char                *nextp;
    ssize_t             nread;
    struct file_handle  *fhp;
    if ((argc > 1 && strcmp(argv[1], "--help") == 0) || argc > 2) {
        fprintf(stderr, "Usage: %s [chemin-de-montage]\n", argv[0]);
        exit(EXIT_FAILURE);
    }
    /* L'entrée standard contient l'ID de montage et les informations sur le descripteur de fichier :
         Ligne 1 : <mount_id>
         Ligne 2 : <handle_bytes> <handle_type>   <octets du descripteur en hex>
    */
    if (fgets(line1, sizeof(line1), stdin) == NULL ||
        fgets(line2, sizeof(line2), stdin) == NULL)
    {
        fprintf(stderr, "ID de montage / descripteur de fichier manquant\n");
        exit(EXIT_FAILURE);
    }
    mount_id = atoi(line1);
    handle_bytes = strtoul(line2, &nextp, 0);
    /* Étant donné handle_bytes, nous pouvons maintenant allouer la structure file_handle.  */
    fhp = malloc(sizeof(*fhp) + handle_bytes);
    if (fhp == NULL)
        err(EXIT_FAILURE, "malloc");
    fhp->handle_bytes = handle_bytes;
    fhp->handle_type = strtoul(nextp, &nextp, 0);
    for (size_t j = 0; j < fhp->handle_bytes; j++)
        fhp->f_handle[j] = strtoul(nextp, &nextp, 16);
    /* Obtenir le descripteur de fichier pour le point de montage, soit en ouvrant
       le nom de chemin spécifié sur la ligne de commande, soit en analysant
       /proc/self/mounts pour trouver un montage qui correspond à 'mount_id'
       que nous avons reçu depuis stdin.  */
    if (argc > 1)
        mount_fd = open(argv[1], O_RDONLY);
    else
        mount_fd = open_mount_path_by_id(mount_id);
    if (mount_fd == -1)
        err(EXIT_FAILURE, "ouverture du descripteur de montage");
    /* Ouvrir le fichier en utilisant le descripteur et le point de montage.  */
    fd = open_by_handle_at(mount_fd, fhp, O_RDONLY);
    if (fd == -1)
        err(EXIT_FAILURE, "open_by_handle_at");
    /* Essayer de lire quelques octets du fichier.  */
    nread = read(fd, buf, sizeof(buf));
    if (nread == -1)
        err(EXIT_FAILURE, "read");
    printf("Lu %zd octets\n", nread);
    exit(EXIT_SUCCESS);
}
