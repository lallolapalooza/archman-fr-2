NOHUP(1P) Manuel du programmeur POSIX NOHUP(1P)

PROLOG

Cette page de manuel fait partie du Manuel du programmeur POSIX. L'implémentation Linux de cette interface peut différer (consultez la page de manuel Linux correspondante pour les détails du comportement Linux), ou l'interface peut ne pas être implémentée sous Linux.

NOM

nohup — invoquer un utilitaire insensible aux déconnexions

SYNOPSIS

nohup utilitaire [argument...]

DESCRIPTION

L' utilitaire nohup invoque l'utilitaire nommé par l'opérande utilitaire avec les arguments fournis sous forme d'opérandes argument. Au moment où l' utilitaire nommé est invoqué, le signal SIGHUP est configuré pour être ignoré.

Si l'entrée standard est associée à un terminal, l'utilitaire nohup peut rediriger l'entrée standard depuis un fichier non spécifié.

Si la sortie standard est un terminal, toutes les sorties écrites par l' utilitaire nommé vers sa sortie standard seront ajoutées à la fin du fichier nohup.out dans le répertoire courant. Si nohup.out ne peut pas être créé ou ouvert en mode ajout, la sortie sera ajoutée à la fin du fichier nohup.out dans le répertoire spécifié par la variable d'environnement HOME. Si aucun des fichiers ne peut être créé ou ouvert en mode ajout, l' utilitaire ne sera pas invoqué. Si un fichier est créé, les bits d'autorisation du fichier seront définis à S_IRUSR | S_IWUSR.

Si l'erreur standard est un terminal et que la sortie standard est ouverte mais n'est pas un terminal, toutes les sorties écrites par l'utilitaire nommé vers son erreur standard seront redirigées vers la même description de fichier ouverte que la sortie standard. Si l'erreur standard est un terminal et que la sortie standard est soit un terminal, soit fermée, la même sortie sera plutôt ajoutée à la fin du fichier nohup.out comme décrit ci-dessus.

OPTIONS

Aucune.

OPÉRANDES

Les opérandes suivants seront pris en charge :

utilitaire
Le nom d'un utilitaire à invoquer. Si l'opérande utilitaire nomme l'un des utilitaires intégrés spéciaux de la Section 2.14, Utilitaires intégrés spéciaux, les résultats sont indéfinis.
argument
Toute chaîne à fournir comme argument lors de l'invocation de l'utilitaire nommé par l'opérande utilitaire.

STDIN

Non utilisé.

FICHIERS D'ENTRÉE

Aucun.

VARIABLES D'ENVIRONNEMENT

Les variables d'environnement suivantes affecteront l'exécution de nohup :

HOME
Détermine le chemin du répertoire personnel de l'utilisateur : si le fichier de sortie nohup.out ne peut pas être créé dans le répertoire courant, l'utilitaire nohup utilisera le répertoire nommé par HOME pour créer le fichier.
LANG
Fournit une valeur par défaut pour les variables d'internationalisation qui sont non définies ou vides. (Voir le volume Définitions de base de POSIX.1‐2017, Section 8.2, Variables d'internationalisation pour la précédence des variables d'internationalisation utilisées pour déterminer les valeurs des catégories de locale.)
LC_ALL
Si défini à une chaîne non vide, remplace les valeurs de toutes les autres variables d'internationalisation.
LC_CTYPE
Détermine la locale pour l'interprétation des séquences d'octets de données textuelles en caractères (par exemple, caractères mono-octet par opposition à multi-octets dans les arguments).
LC_MESSAGES

Détermine la locale qui devrait être utilisée pour affecter le format et le contenu des messages de diagnostic écrits sur l'erreur standard.
NLSPATH
Détermine l'emplacement des catalogues de messages pour le traitement de LC_MESSAGES.
PATH
Détermine le chemin de recherche utilisé pour localiser l'utilitaire à invoquer. Voir le volume Définitions de base de POSIX.1‐2017, Chapitre 8, Variables d'environnement.

ÉVÉNEMENTS SYNCHRONES

L'utilitaire nohup prendra l'action standard pour tous les signaux, sauf que SIGHUP sera ignoré.

STDOUT

Si la sortie standard n'est pas un terminal, la sortie standard de nohup sera la sortie standard générée par l'exécution de l' utilitaire spécifié par les opérandes. Sinon, rien ne sera écrit sur la sortie standard.

STDERR

Si la sortie standard est un terminal, un message sera écrit sur l'erreur standard, indiquant le nom du fichier vers lequel la sortie est ajoutée. Le nom du fichier sera soit nohup.out, soit $HOME/nohup.out.

FICHIERS DE SORTIE

La sortie écrite par l'utilitaire nommé est ajoutée au fichier nohup.out (ou $HOME/nohup.out), si les conditions sont remplies comme décrit dans la DESCRIPTION.

DESCRIPTION ÉTENDUE

Aucune.

STATUT DE SORTIE

Les valeurs de sortie suivantes seront retournées :

126
L'utilitaire spécifié par utilitaire a été trouvé mais n'a pas pu être invoqué.
127
Une erreur s'est produite dans l'utilitaire nohup ou l'utilitaire spécifié par utilitaire n'a pas pu être trouvé.

Sinon, le statut de sortie de nohup sera celui de l' utilitaire spécifié par l'opérande utilitaire.

CONSÉQUENCES DES ERREURS

Par défaut.

Les sections suivantes sont informatives.

UTILISATION APPLICATIVE

Les utilitaires command, env, nice, nohup, time et xargs ont été spécifiés pour utiliser le code de sortie 126 en cas d'erreur afin que les applications puissent distinguer "échec de la recherche d'un utilitaire" de "l'utilitaire invoqué s'est terminé avec une indication d'erreur". La valeur 127 a été choisie car elle n'est pas couramment utilisée pour d'autres significations ; la plupart des utilitaires utilisent de petites valeurs pour les "conditions d'erreur normales" et les valeurs supérieures à 128 peuvent être confondues avec une terminaison due à la réception d'un signal. La valeur 126 a été choisie de manière similaire pour indiquer que l'utilitaire pouvait être trouvé, mais pas invoqué. Certains scripts produisent des messages d'erreur significatifs différenciant les cas 126 et 127. La distinction entre les codes de sortie 126 et 127 est basée sur la pratique du KornShell qui utilise 127 lorsque toutes les tentatives d' exécuter l'utilitaire échouent avec [ENOENT], et utilise 126 lorsque toute tentative d' exécuter l'utilitaire échoue pour toute autre raison.

EXEMPLES

Il est souvent souhaitable d'appliquer nohup à des pipelines ou des listes de commandes. Cela peut être fait en plaçant des pipelines et des listes de commandes dans un seul fichier ; ce fichier peut alors être invoqué comme un utilitaire, et nohup s'applique à tout ce qui se trouve dans le fichier.

Alternativement, la commande suivante peut être utilisée pour appliquer nohup à une commande complexe :

nohup sh -c 'ligne-de-commande-complexe' </dev/null

RAISON D'ÊTRE

La version 4.3 de BSD ignore SIGTERM et SIGHUP, et si ./nohup.out ne peut pas être utilisé, elle échoue au lieu d'essayer d'utiliser $HOME/nohup.out.

L'utilitaire csh possède une version intégrée de nohup qui agit différemment de nohup défini dans ce volume de POSIX.1‐2017.

Le terme utilitaire est utilisé, plutôt que commande, pour souligner le fait que les commandes composites de shell, les pipelines, les built-ins spéciaux, etc., ne peuvent pas être utilisés directement. Cependant, utilitaire inclut les programmes d'application utilisateur et les scripts de shell, pas seulement les utilitaires standard.

Les versions historiques de l'utilitaire nohup utilisent les sémantiques de création de fichiers par défaut. Certaines versions plus récentes utilisent les permissions spécifiées ici comme mesure de sécurité supplémentaire.

Certaines implémentations historiques ignorent SIGQUIT en plus de SIGHUP ; d'autres ignorent SIGTERM. Une proposition initiale permettait, mais n'exigeait pas, d'ignorer SIGQUIT. Plusieurs réviseurs se sont opposés à ce que nohup ne modifie que la gestion de SIGHUP, comme requis par ce volume de POSIX.1‐2017.

Les versions historiques de nohup n'affectaient pas l'entrée standard, mais cela pose des problèmes dans le scénario courant où l'utilisateur se connecte à un système, tape la commande :

nohup make &

à l'invite, puis se déconnecte. Si l'entrée standard n'est pas affectée par nohup, la session de connexion peut ne pas se terminer pendant un certain temps, car l'entrée standard reste ouverte jusqu'à ce que make se termine. Pour éviter ce problème, POSIX.1‐2008 permet aux implémentations de rediriger l'entrée standard si elle est un terminal. Comme le comportement est défini par l'implémentation, les applications portables qui pourraient rencontrer le problème devraient rediriger elles-mêmes l'entrée standard. Par exemple, au lieu de :

nohup make &

une application peut invoquer :

nohup make </dev/null &
