    notmuch_status_t notmuch_message_maildir_flags_to_tags (notmuch_message_t * message)

    Ajouter/supprimer des balises en fonction des indicateurs maildir dans les noms de fichiers du message. Cette fonction examine les noms de fichiers de 'message' pour les indicateurs maildir, et ajoute ou supprime des balises sur 'message' comme suit lorsqu'un de ces indicateurs est présent :

     Indicateur    Action s'il est présent
 ---------    ----------------------
 'D'        Ajoute la balise « draft » au message
 'F'        Ajoute la balise « flagged » au message
 'P'        Ajoute la balise « passed » au message
 'R'        Ajoute la balise « replied » au message
 'S'        Supprime la balise « unread » du message

    Pour chaque indicateur qui n'est pas présent, l'action opposée (ajouter/supprimer) est effectuée pour les balises correspondantes.

    Les indicateurs sont identifiés comme des composants suffixes du nom de fichier après une séquence de « :2, ».

    S'il y a plusieurs noms de fichiers associés à ce message, l'indicateur est considéré comme présent s'il apparaît dans un ou plusieurs noms de fichiers. (Autrement dit, les indicateurs des plusieurs noms de fichiers sont combinés avec l'opérateur logique OU.)

    Un client peut s'assurer que les balises de la base de données notmuch restent synchronisées avec les indicateurs maildir en appelant cette fonction après chaque appel à notmuch_database_index_file. Voir également notmuch_message_tags_to_maildir_flags pour synchroniser les changements de balises vers les indicateurs maildir.

    Renommer les noms de fichiers du message pour encoder les balises en indicateurs maildir. Plus précisément, pour chaque nom de fichier correspondant à ce message :

    Si le nom de fichier n'est pas dans un répertoire maildir, ne rien faire. (Un répertoire maildir est déterminé comme un répertoire nommé « new » ou « cur ».) De même, si le nom de fichier a des informations maildir invalides (caractères d'indicateur répétés ou hors de l'ordre ASCII après « :2, »), alors ne rien faire.

    Si le nom de fichier est dans un répertoire maildir, renommez le fichier de manière à ce que son nom de fichier se termine par la séquence « :2, » suivie de zéro ou plusieurs des indicateurs suivants à un seul caractère (par ordre ASCII) :

    • indicateur 'D' si et seulement si le message a la balise « draft »
    • indicateur 'F' si et seulement si le message a la balise « flagged »
    • indicateur 'P' si et seulement si le message a la balise « passed »
    • indicateur 'R' si et seulement si le message a la balise « replied »
    • indicateur 'S' si et seulement si le message n'a pas la balise « unread »

    Tous les indicateurs existants non mentionnés dans la liste ci-dessus seront préservés dans le renommage.

    De plus, si ce nom de fichier se trouve dans un répertoire nommé « new », renommez-le pour qu'il soit dans le répertoire voisin nommé « cur ».

    Un client peut s'assurer que les indicateurs de nom de fichier maildir restent synchronisés avec les balises de la base de données notmuch en appelant cette fonction après avoir modifié les balises, (après les appels à notmuch_message_add_tag, notmuch_message_remove_tag, ou notmuch_message_freeze/ notmuch_message_thaw). Voir également notmuch_message_maildir_flags_to_tags pour synchroniser les changements d'indicateurs maildir vers les balises.

    notmuch_status_t notmuch_message_freeze (notmuch_message_t * message)

    Gèle l'état actuel de 'message' dans la base de données. Cela signifie que les changements apportés à l'état du message (via notmuch_message_add_tag, notmuch_message_remove_tag, et notmuch_message_remove_all_tags) ne seront pas validés dans la base de données jusqu'à ce que le message soit dégelé avec notmuch_message_thaw.

    Plusieurs appels à freeze/thaw sont valides et ces appels s'empilent. Cela signifie qu'il doit y avoir autant d'appels à thaw qu'à freeze avant qu'un message ne soit effectivement dégé.

    La capacité de geler/dégéler permet des transactions sûres pour modifier les valeurs des balises. Par exemple, définir explicitement un message pour qu'il ait un ensemble donné de balises pourrait ressembler à ceci :

    notmuch_message_freeze (message);

    notmuch_message_remove_all_tags (message);

    for (i = 0; i < NUM_TAGS; i++) notmuch_message_add_tag (message, tags[i]);

    notmuch_message_thaw (message);

    Avec freeze/thaw utilisé de cette manière, le message dans la base de données est garanti d'avoir soit l'ensemble complet des valeurs de balises d'origine, soit l'ensemble complet des nouvelles valeurs de balises, mais rien entre les deux.

    Imaginez l'exemple ci-dessus sans freeze/thaw et l'opération interrompue d'une manière ou d'une autre. Cela pourrait entraîner que le message se retrouve sans balises si l'interruption se produisait après notmuch_message_remove_all_tags mais avant notmuch_message_add_tag.

    Valeur de retour :

    NOTMUCH_STATUS_SUCCESS : Message gelé avec succès.

    NOTMUCH_STATUS_READ_ONLY_DATABASE : La base de données a été ouverte en lecture seule, le message ne peut donc pas être modifié.

    notmuch_status_t notmuch_message_thaw (notmuch_message_t * message)

    Dégèle le 'message' actuel, synchronisant toutes les modifications qui auraient pu survenir pendant que 'message' était gelé dans la base de données notmuch. Voir notmuch_message_freeze pour un exemple d'utilisation de cette fonction pour fournir des changements de balises en toute sécurité.

    Plusieurs appels à freeze/thaw sont valides et ces appels s'empilent. Cela signifie qu'il doit y avoir autant d'appels à thaw qu'à freeze avant qu'un message ne soit effectivement dégé.

    Valeur de retour :

    NOTMUCH_STATUS_SUCCESS : Message dégé avec succès (ou du moins son compteur de gel a été réduit de 1 avec succès).

    NOTMUCH_STATUS_UNBALANCED_FREEZE_THAW : Une tentative a été faite pour dégéler un message non gelé. Autrement dit, il y a eu un nombre déséquilibré d'appels à notmuch_message_freeze et notmuch_message_thaw.

    notmuch_status_t notmuch_directory_set_mtime (notmuch_directory_t * directory, time_t mtime)

    Store an mtime within the database for 'directory'. The 'directory' should be an object retrieved from the database with notmuch_database_get_directory for a particular path.

    The intention is for the caller to use the mtime to allow efficient identification of new messages to be added to the database. The recommended usage is as follows:

    o Read the mtime of a directory from the filesystem

    o Call index_file for all mail files in the directory

    o Call notmuch_directory_set_mtime with the mtime read from the filesystem.

    Then, when wanting to check for updates to the directory in the future, the client can call notmuch_directory_get_mtime and know that it only needs to add files if the mtime of the directory and files are newer than the stored timestamp.
