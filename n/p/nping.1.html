NOM

nping - Outil de génération de paquets réseau / utilitaire ping

SYNTAXE

nping [Options] {cibles}

DESCRIPTION

Nping est un outil open-source de génération de paquets réseau, d'analyse des réponses et de mesure du temps de réponse. Nping permet aux utilisateurs de générer des paquets réseau pour une large gamme de protocoles, leur permettant de régler pratiquement n'importe quel champ des en-têtes de protocole. Bien que Nping puisse être utilisé comme un simple utilitaire ping pour détecter des hôtes actifs, il peut également être utilisé comme un générateur de paquets bruts pour des tests de stress de la pile réseau, de l'empoisonnement ARP, des attaques par déni de service, le traçage de routage et d'autres fins.

De plus, Nping offre un mode de fonctionnement spécial appelé « Mode Écho », qui permet aux utilisateurs de voir comment les sondes générées changent en transit, révélant les différences entre les paquets transmis et les paquets reçus à l'autre extrémité. Voir la section « Mode Écho » pour plus de détails.

La sortie de Nping est une liste des paquets qui sont envoyés et reçus. Le niveau de détail dépend des options utilisées.

Une exécution typique de Nping est montrée dans l'Exemple 1. Les seuls arguments de Nping utilisés dans cet exemple sont -c, pour spécifier le nombre de fois où cibler chaque hôte, --tcp pour spécifier le mode de sonde TCP, -p 80,433 pour spécifier les ports cibles ; et ensuite les deux noms d'hôtes cibles.

TARGET SPECIFICATION

Everything on the Nping command line that isn't an option or an option argument is treated as a target host specification. Nping uses the same syntax for target specifications that Nmap does. The simplest case is a single target given by IP address or hostname.

Nping supports CIDR-style addressing. You can append /numbits to an IPv4 address or hostname and Nping will send probes to every IP address for which the first numbits are the same as for the reference IP or hostname given. For example, 192.168.10.0/24 would send probes to the 256 hosts between 192.168.10.0 (binary: 11000000 10101000 00001010 00000000) and 192.168.10.255 (binary: 11000000 10101000 00001010 11111111), inclusive. 192.168.10.40/24 would ping exactly the same targets. Given that the host scanme.nmap.org is at the IP address 64.13.134.52, the specification scanme.nmap.org/16 would send probes to the 65,536 IP addresses between 64.13.0.0 and 64.13.255.255. The smallest allowed value is /0, which targets the whole Internet. The largest value is /32, which targets just the named host or IP address because all address bits are fixed.

CIDR notation is short but not always flexible enough. For example, you might want to send probes to 192.168.0.0/16 but skip any IPs ending with .0 or .255 because they may be used as subnet network and broadcast addresses. Nping supports this through octet range addressing. Rather than specify a normal IP address, you can specify a comma-separated list of numbers or ranges for each octet. For example, 192.168.0-255.1-254 will skip all addresses in the range that end in .0 or .255, and 192.168.3-5,7.1 will target the four addresses 192.168.3.1, 192.168.4.1, 192.168.5.1, and 192.168.7.1. Either side of a range may be omitted; the default values are 0 on the left and 255 on the right. Using - by itself is the same as 0-255, but remember to use 0- in the first octet so the target specification doesn't look like a command-line option. Ranges need not be limited to the final octets: the specifier 0-.-.13.37 will send probes to all IP addresses on the Internet ending in .13.37. This sort of broad sampling can be useful for Internet surveys and research.

IPv6 addresses can only be specified by their fully qualified IPv6 address or hostname. CIDR and octet ranges aren't supported for IPv6 because they are rarely useful.

Nping accepts multiple host specifications on the command line, and they don't need to be the same type. The command nping scanme.nmap.org 192.168.0.0/8 10.0.0,1,3-7.- does what you would expect.

OPTION SPECIFICATION

Nping is designed to be very flexible and fit a wide variety of needs. As with most command-line tools, its behavior can be adjusted using command-line options. These general principles apply to option arguments, unless stated otherwise.

Options that take integer numbers can accept values specified in decimal, octal or hexadecimal base. When a number starts with 0x, it will be treated as hexadecimal; when it simply starts with 0, it will be treated as octal. Otherwise, Nping will assume the number has been specified in base 10. Virtually all numbers that can be supplied from the command line are unsigned so, as a general rule, the minimum value is zero. Users may also specify the word random or rand to make Nping generate a random value within the expected range.

IP addresses may be given as IPv4 addresses (e.g. 192.168.1.1), IPv6 addresses (e.g. 2001:db8:85a3::8e4c:760:7146), or hostnames, which will be resolved using the default DNS server configured in the host system.

Options that take MAC addresses accept the usual colon-separated 6 hex byte format (e.g. 00:50:56:d4:01:98). Hyphens may also be used instead of colons (e.g. 00-50-56-c0-00-08). The special word random or rand sets a random address and the word broadcast or bcast sets ff:ff:ff:ff:ff:ff.

GENERAL OPERATION

Unlike other ping and packet generation tools, Nping supports multiple target host and port specifications. While this provides great flexibility, it is not obvious how Nping handles situations where there is more than one host and/or more than one port to send probes to. This section explains how Nping behaves in these cases.

When multiple target hosts are specified, Nping rotates among them in round-robin fashion. This gives slow hosts more time to send their responses before another probe is sent to them. Ports are also scheduled using round robin. So, unless only one port is specified, Nping never sends two probes to the same target host and port consecutively.

The loop around targets is the “inner loop” and the loop around ports is the “outer loop”. All targets will be sent a probe for a given port before moving on to the next port. Between probes, Nping waits a configurable amount of time called the “inter-probe delay”, which is controlled by the --delay option. These examples show how it works.

PROBE MODES

Nping supports a wide variety of protocols. Although in some cases Nping can automatically determine the mode from the options used, it is generally a good idea to specify it explicitly.

--tcp-connect (TCP Connect mode)

TCP connect mode is the default mode when a user does not have raw packet privileges. Instead of writing raw packets as most other modes do, Nping asks the underlying operating system to establish a connection with the target machine and port by issuing the connect system call. This is the same high-level system call that web browsers, P2P clients, and most other network-enabled applications use to establish a connection. It is part of a programming interface known as the Berkeley Sockets API. Rather than read raw packet responses off the wire, Nping uses this API to obtain status information on each connection attempt. For this reason, you will not be able to see the contents of the packets that are sent or received but only status information about the TCP connection establishment taking place.

--tcp (TCP mode)

TCP is the mode that lets users create and send any kind of TCP packet. TCP packets are sent embedded in IP packets that can also be tuned. This mode can be used for many different purposes. For example you could try to discover open ports by sending TCP SYN messages without completing the three-way handshake. This technique is often referred to as half-open scanning, because you don't open a full TCP connection. You send a SYN packet, as if you are going to open a real connection and then wait for a response. A SYN/ACK indicates the port is open, while a RST indicates it's closed. If no response is received one could assume that some intermediate network device is filtering the responses. Another use could be to see how a remote TCP/IP stack behaves when it receives a non-RFC-compliant packet, like one with both SYN and RST flags set. One could also do some evil by creating custom RST packets using an spoofed IP address with the intent of closing an active TCP connection.

--udp (UDP mode)

UDP mode can have two different behaviours. Under normal circumstances, it lets users create custom IP/UDP packets. However, if Nping is run by a user without raw packet privileges and no changes to the default protocol headers are requested, then Nping enters the unprivileged UDP mode which basically sends UDP packets to the specified target hosts and ports using the sendto system call. Note that in this unprivileged mode it is not possible to see low-level header information of the packets on the wire but only status information about the amount of bytes that are being transmitted and received. UDP mode can be used to interact with any UDP-based server. Examples are DNS servers, streaming servers, online gaming servers, and port knocking/single-packet authorization daemons.

--icmp (ICMP mode)

ICMP mode is the default mode when the user runs Nping with raw packet privileges. Any kind of ICMP message can be created. The default ICMP type is Echo, i.e., ping. ICMP mode can be used
pour de nombreux objectifs différents, d'une simple requête pour un horodatage ou un masque de réseau à la transmission de faux messages de destination inaccessible, de redirections personnalisées et d'annonces de routeur.

--arp (Mode ARP/RARP)

ARP vous permet de créer et d'envoyer différents paquets liés à ARP. Cela inclut les requêtes et les réponses ARP, RARP, DRARP et InARP. Ce mode peut être utilisé pour effectuer une découverte d'hôtes de bas niveau et mener des attaques de empoisonnement du cache ARP.

--traceroute (Mode Traceroute)

Traceroute n'est pas un mode en soi, mais un complément aux modes TCP, UDP et ICMP. Lorsque cette option est spécifiée, Nping définit la valeur TTL IP du premier paquet de sonde à 1. Lorsque le routeur suivant reçoit le paquet, il le rejette en raison de l'expiration du TTL et génère un message ICMP de destination inaccessible. Le paquet de sonde suivant aura un TTL de 2, donc le premier routeur transférera le paquet tandis que le second routeur sera celui qui rejettera le paquet et générera le message ICMP. Le troisième paquet de sonde aura une valeur TTL de 3, et ainsi de suite. En examinant les adresses source de tous ces messages ICMP Destination Unreachable, il est possible de déterminer le chemin emprunté par les paquets de sonde jusqu'à leur destination finale.

MODE CONNECT

-p spéc_port, --dest-port spéc_port (Ports cibles)

Cette option spécifie les ports auxquels vous souhaitez tenter de vous connecter. Il peut s'agir d'un port unique, d'une liste de ports séparés par des virgules (par exemple, 80,443,8080), d'une plage (par exemple, 1-1023) et de toute combinaison de ceux-ci (par exemple, 21-25,80,443,1024-2048). Les valeurs de début et/ou de fin d'une plage peuvent être omises, ce qui amène Nping à utiliser respectivement 1 et 65535. Vous pouvez donc spécifier -p- pour cibler les ports de 1 à 65535. L'utilisation du port zéro est autorisée si vous le spécifiez explicitement.

MODE TCP

-p spéc_port, --dest-port spéc_port (Ports cibles)

Cette option spécifie les ports de destination vers lesquels vous souhaitez envoyer des paquets. Il peut s'agir d'un port unique, d'une liste de ports séparés par des virgules (par exemple, 80,443,8080), d'une plage (par exemple, 1-1023) et de toute combinaison de ceux-ci (par exemple, 21-25,80,443,1024-2048). Les valeurs de début et/ou de fin d'une plage peuvent être omises, ce qui amène Nping à utiliser respectivement 1 et 65535. Vous pouvez donc spécifier -p- pour cibler les ports de 1 à 65535. L'utilisation du port zéro est autorisée si vous le spécifiez explicitement.

-g num_port, --source-port num_port (Usurper le port source)

Cette option demande à Nping d'utiliser le port spécifié comme port source pour les connexions TCP. Notez que cela peut ne pas fonctionner sur tous les systèmes ou peut nécessiter des privilèges root. La valeur spécifiée doit être un entier dans la plage [0–65535].

--seq num_seq (Numéro de séquence)

Spécifie le numéro de séquence TCP. Dans les paquets SYN, il s'agit du numéro de séquence initial (ISN). Dans une transmission normale, cela correspond au numéro de séquence du premier octet de données dans le segment. num_seq doit être un nombre dans la plage [0–4294967295].

--flags flags (Flags TCP)

Cette option spécifie quels indicateurs doivent être définis dans le paquet TCP. flags peut être spécifié de trois manières différentes :
1.Comme une liste d'indicateurs séparés par des virgules, par exemple, --flags syn,ack,rst
2.Comme une liste d'initiales d'indicateurs d'un seul caractère, par exemple, --flags SAR demande à Nping de définir les indicateurs SYN, ACK et RST.
3.Comme un nombre hexadécimal de 8 bits, où le nombre fourni est la valeur exacte qui sera placée dans le champ des indicateurs de l'en-tête TCP. Le nombre doit commencer par le préfixe 0x et être dans la plage [0x00–0xFF], par exemple, --flags 0x20 définit l'indicateur URG car 0x20 correspond au binaire 00100000 et l'indicateur URG est représenté par le troisième bit.

Il y a 8 indicateurs possibles à définir : CWR, ECN, URG, ACK, PSH, RST, SYN et FIN. La valeur spéciale ALL signifie définir tous les indicateurs. NONE signifie ne définir aucun indicateur. Il est important que si vous ne voulez aucun indicateur défini, vous le demandiez explicitement car dans certains cas, l'indicateur SYN peut être défini par défaut. Voici une brève description de la signification de chaque indicateur :

CWR (Congestion Window Reduced)

Défini par un expéditeur capable d'ECN lorsqu'il réduit sa fenêtre de congestion (suite à un délai de retransmission, une retransmission rapide ou en réponse à une notification ECN).

ECN (Explicit Congestion Notification)

Pendant la poignée de main en trois étapes, il indique que l'expéditeur est capable de réaliser une notification explicite de congestion. Normalement, cela signifie qu'un paquet avec l'indicateur IP Congestion Experienced défini a été reçu pendant la transmission normale. Voir RFC 3168 pour plus d'informations.

URG (Urgent)

Le segment est urgent et le champ de pointeur urgent contient des informations valides.

ACK (Acknowledgement)

Le segment transporte un accusé de réception et la valeur du champ de numéro d'accusé de réception est valide et contient le prochain numéro de séquence attendu du récepteur.

PSH (Push)

Les données de ce segment doivent être immédiatement transmises à la couche application à l'arrivée.

RST (Reset)

Il y a eu un problème et l'expéditeur veut interrompre la connexion.

SYN (Synchronize)

Le segment est une demande de synchronisation des numéros de séquence et d'établissement d'une connexion. Le champ numéro de séquence contient le numéro de séquence initial de l'expéditeur.

FIN (Finish)

L'expéditeur souhaite fermer la connexion.

--win taille (Taille de la fenêtre)

Spécifie la taille de la fenêtre TCP, c'est-à-dire le nombre d'octets que l'expéditeur du segment est prêt à accepter du récepteur à un moment donné. Il s'agit généralement de la taille du tampon de réception que le système d'exploitation alloue pour une connexion donnée. taille doit être un nombre dans la plage [0–65535].

--badsum (Checksum invalide)

Demande à Nping d'utiliser une somme de contrôle TCP invalide pour les paquets envoyés aux hôtes cibles. Comme pratiquement toutes les piles IP des hôtes rejettent correctement ces paquets, les réponses reçues proviennent probablement d'un pare-feu ou d'un IDS qui n'a pas pris la peine de vérifier la somme de contrôle. Pour plus de détails sur cette technique, voir https://nmap.org/p60-12.html.

MODE ICMP

--icmp-type type (Type ICMP)

Cette option spécifie quel type de messages ICMP doit être généré. type peut être fourni de deux manières. Vous pouvez utiliser les numéros de type officiels assignés par l'IANA[1] (par exemple, --icmp-type 8 pour ICMP Echo Request), ou vous pouvez utiliser l'un des mnémoniques listés dans la section « Types ICMP ».

--icmp-code code (Code ICMP)

Cette option spécifie quel code ICMP doit être inclus dans les messages ICMP générés. code peut être fourni de deux manières. Vous pouvez utiliser les numéros de code officiels assignés par l'IANA[1] (par exemple, --icmp-code 1 pour Fragment Reassembly Time Exceeded), ou vous pouvez utiliser l'un des mnémoniques listés dans la section « Codes ICMP ».

--icmp-id id (Identifiant ICMP)

Cette option spécifie la valeur de l'identifiant utilisé dans certains messages ICMP. En général, il est utilisé pour faire correspondre les messages de requête et de réponse. id doit être un nombre dans la plage [0–65535].

--icmp-seq seq (Séquence ICMP)

Cette option spécifie la valeur du champ numéro de séquence utilisé dans certains messages ICMP. En général, il est utilisé pour faire correspondre les messages de requête et de réponse. id doit être un nombre dans la plage [0–65535].

--icmp-redirect-addr addr (Adresse de redirection ICMP)

Cette option définit le champ d'adresse dans les messages de redirection ICMP. En d'autres termes, elle définit l'adresse IP du routeur qui doit être utilisée lors de l'envoi de datagrammes IP vers la destination d'origine. addr peut être une adresse IPv4 ou un nom d'hôte.

--icmp-param-pointer pointeur (Pointeur de problème de paramètre ICMP)

Cette option spécifie le pointeur qui indique l'emplacement du problème dans les messages ICMP Parameter Problem. pointeur doit être un nombre dans la plage [0–255]. Normalement, cette option n'est utilisée que lorsque le code ICMP est défini sur 0 (« Pointer indique l'erreur »).

--icmp-advert-lifetime ttl (Durée de vie de l'annonce de routeur ICMP)

Cette option spécifie la durée de vie de l'annonce de routeur, c'est-à-dire le nombre de secondes pendant lesquelles les informations transportées dans une annonce de routeur ICMP peuvent être considérées comme valides. ttl doit être un entier positif dans la plage [0–65535].

--icmp-advert-entry addr,pref (Entrée d'annonce de routeur ICMP)

Cette option ajoute une entrée d'annonce de routeur à un message d'annonce de routeur ICMP. Le paramètre doit être deux valeurs séparées par une virgule. addr est l'IP du routeur et peut être spécifiée comme une adresse IP en notation décimale pointée ou comme un nom d'hôte. pref est le niveau de préférence pour l'IP spécifiée. Il doit s'agir d'un nombre compris dans l'intervalle [0–4294967295]. Un exemple est --icmp-advert-entry 192.168.128.1,3.

--icmp-orig-time timestamp (Horodatage d'origine ICMP)

Cette option définit l'horodatage d'origine dans les messages ICMP Timestamp. L'horodatage d'origine est exprimé en millisecondes depuis minuit UTC et correspond au moment où l'expéditeur a touché pour la dernière fois le message Timestamp avant sa transmission. timestamp peut être spécifié comme une heure régulière (par exemple, 10s, 3h, 1000ms) ou la chaîne spéciale now. Vous pouvez ajouter ou soustraire des valeurs de now, par exemple --icmp-orig-time now-2s, --icmp-orig-time now+1h, --icmp-orig-time now+200ms.

--icmp-recv-time timestamp (Horodatage de réception ICMP)

Cette option définit l'horodatage de réception dans les messages ICMP Timestamp. L'horodatage de réception est exprimé en millisecondes depuis minuit UTC et correspond au moment où l'échoeur a touché pour la première fois le message Timestamp à la réception. timestamp est comme avec --icmp-orig-time.

--icmp-trans-time timestamp (Horodatage de transmission ICMP)

Cette option définit l'horodatage de transmission dans les messages ICMP Timestamp. L'horodatage de transmission est exprimé en millisecondes depuis minuit UTC et correspond au moment où l'échoeur a touché pour la dernière fois le message Timestamp avant sa transmission. timestamp est comme avec --icmp-orig-time.

Ces identifiants peuvent être utilisés comme mnémoniques pour les numéros de type ICMP donnés à l'option --icmp-type. ARP MODE

--arp-type type (ICMP Type)

This option specifies which type of ARP messages should be generated. type can be supplied in two different ways. You can use the official numbers assigned by IANA[2] (e.g. --arp-type 1 for ARP Request), or you can use one of the mnemonics from the section called “ARP Types”.

--arp-sender-mac mac (Sender MAC address)

This option sets the Sender Hardware Address field of the ARP header. Although ARP supports many types of link layer addresses, currently Nping only supports MAC addresses. mac must be specified using the traditional MAC notation (e.g. 00:0a:8a:32:f4:ae). You can also use hyphens as separators (e.g. 00-0a-8a-32-f4-ae).

--arp-sender-ip addr (Sender IP address)

This option sets the Sender IP field of the ARP header. addr can be given as an IPv4 address or a hostname.

--arp-target-mac mac (target MAC address)

This option sets the Target Hardware Address field of the ARP header.

--arp-target-ip addr (target ip address)

This option sets the Target IP field of the ARP header.

ARP Types

These identifiers may be used as mnemonics for the ARP type numbers given to the --arp-type option.

arp-request, arp, a

ARP Request (type 1). ARP requests are used to translate network layer addresses (normally IP addresses) to link layer addresses (usually MAC addresses). Basically, and ARP request is a broadcasted message that asks the host in the same network segment that has a given IP address to provide its MAC address.

arp-reply, arp-rep, ar

ARP Reply (type 2). An ARP reply is a message that a host sends in response to an ARP request to provide its link layer address.

rarp-request, rarp, r

RARP Requests (type 3). RARP requests are used to translate a link layer address (normally a MAC address) to a network layer address (usually an IP address). Basically a RARP request is a broadcasted message sent by a host that wants to know his own IP address because it doesn't have any. It was the first protocol designed to solve the bootstrapping problem. However, RARP is now obsolete and DHCP is used instead. For more information about RARP see RFC 903.

rarp-reply, rarp-rep, rr

RARP Reply (type 4). A RARP reply is a message sent in response to a RARP request to provide an IP address to the host that sent the RARP request in the first place.

drarp-request, drarp, d

Dynamic RARP Request (type 5). Dynamic RARP is an extension to RARP used to obtain or assign a network layer address from a fixed link layer address. DRARP was used mainly in Sun Microsystems platforms in the late 90's but now it's no longer used. See RFC 1931 for more information.

drarp-reply, drarp-rep, dr

Dynamic RARP Reply (type 6). A DRARP reply is a message sent in response to a RARP request to provide network layer address.

drarp-error, drarp-err, de

DRARP Error (type 7). DRARP Error messages are usually sent in response to DRARP requests to inform of some error. In DRARP Error messages, the Target Protocol Address field is used to carry an error code (usually in the first byte). The error code is intended to tell why no target protocol address is being returned. For more information see RFC 1931.

inarp-request, inarp, i

Inverse ARP Request (type 8). InARP requests are used to translate a link layer address to a network layer address. It is similar to RARP request but in this case, the sender of the InARP request wants to know the network layer address of another node, not its own address. InARP is mainly used in Frame Relay and ATM networks. For more information see RFC 2390.

inarp-reply, inarp-rep, ir

Inverse ARP Reply (type 9). InARP reply messages are sent in response to InARP requests to provide the network layer address associated with the host that has a given link layer address.

arp-nak, an

ARP NAK (type 10). ARP NAK messages are an extension to the ATMARP protocol and they are used to improve the robustness of the ATMARP server mechanism. With ARP NAK, a client can determine the difference between a catastrophic server failure and an ATMARP table lookup failure. See RFC 1577 for more information.

IPV4 OPTIONS

-S addr, --source-ip addr (Source IP Address)

Sets the source IP address. This option lets you specify a custom IP address to be used as source IP address in sent packets. This allows spoofing the sender of the packets. addr can be an IPv4 address or a hostname.

--dest-ip addr (Destination IP Address)

Adds a target to Nping's target list. This option is provided for consistency but its use is deprecated in favor of plain target specifications. See the section called “TARGET SPECIFICATION”.

--tos tos (Type of Service)

Sets the IP TOS field. The TOS field is used to carry information to provide quality of service features. It is normally used to support a technique called Differentiated Services. See RFC 2474 for more information. tos must be a number in the range [0–255].

--id id (Identification)

Sets the IPv4 Identification field. The Identification field is a 16-bit value that is common to all fragments belonging to a particular message. The value is used by the receiver to reassemble the original message from the fragments received. id must be a number in the range [0–65535].

--df (Don't Fragment)

Sets the Don't Fragment bit in sent packets. When an IP datagram has its DF flag set, intermediate devices are not allowed to fragment it so if it needs to travel across a network with a MTU smaller that datagram length the datagram will have to be dropped. Normally an ICMP Destination Unreachable message is generated and sent back to the sender.

--mf (More Fragments)

Sets the More Fragments bit in sent packets. The MF flag is set to indicate the receiver that the current datagram is a fragment of some larger datagram. When set to zero it indicates that the current datagram is either the last fragment in the set or that it is the only fragment.

--evil (Reserved / Evil)

Sets the Reserved / Evil bit in sent packets. The Evil flag helps firewalls and other network security systems to distinguish between datagrams that have malicious intent and those that are merely unusual. When set, it indicates that the datagram has evil intent, instructing insecure systems to succumb. Setting it to zero indicates no evil intent. The option is implied if environmental variable SCRIPT_KIDDIE is set to a non-zero value.

--ttl hops (Time To Live)

Sets the IPv4 Time-To-Live (TTL) field in sent packets to the given value. The TTL field specifies how long the datagram is allowed to exist on the network. It was originally intended to represent a number of seconds but it actually represents the number of hops a packet can traverse before being dropped. The TTL tries to avoid a situation in which undeliverable datagrams keep being forwarded from one router to another endlessly. hops must be a number in the range [0–255].

--badsum-ip (Invalid IP checksum)

Asks Nping to use an invalid IP checksum for packets sent to target hosts. Note that some systems (like most Linux kernels), may fix the checksum before placing the packet on the wire, so even if Nping shows the incorrect checksum in its output, the packets may be transparently corrected by the kernel.

--ip-options R|S [route]|L [route]|T|U ..., --ip-options hex string (IP Options)

The IP protocol offers several options which may be placed in packet headers. Unlike the ubiquitous TCP options, IP options are rarely seen due to practicality and security concerns. In fact, many Internet routers block the most dangerous options such as source routing. Yet options can still be useful in some cases for determining and manipulating the network route to target machines. For example, you may be able to use the record route option to determine a path to a target even when more traditional traceroute-style approaches fail. Or if your packets are being dropped by a certain firewall, you may be able to specify a different route with the strict or loose source routing options.

The most powerful way to specify IP options is to simply pass in hexadecimal data as the argument to --ip-options. Precede each hex byte value with \x. You may repeat certain characters by following them with an asterisk and then the number of times you wish them to repeat. For example, \x01\x07\x04\x00*4 is the same as \x01\x07\x04\x00\x00\x00\x00.

Note that if you specify a number of bytes that is not a multiple of four, an incorrect IP header length will be set in the IP packet. The reason for this is that the IP header length field can only express multiples of four. In those cases, the length is computed by dividing the header length by 4 and rounding down. This will affect the way the header that follows the IP header is interpreted, showing bogus information in Nping or in the output of any sniffer. Although this kind of situation might be useful for some stack stress tests, users would normally want to specify explicit padding, so the correct header length is set.

Nping also offers a shortcut mechanism for specifying options. Simply pass the letter R, T, or U to request record-route, record-timestamp, or both options together, respectively. Loose or strict source routing may be specified with an L or S followed by a space and then a space-separated list of IP addresses.

For more information and examples of using IP options with Nping, see the Nping book.

OPTIONS IPV6

-6, --ipv6 (Utiliser IPv6)

Indique à Nping d'utiliser la version 6 d'IP au lieu de la version 4 par défaut. Il est généralement conseillé de spécifier cette option le plus tôt possible dans la ligne de commande afin que Nping puisse l'analyser rapidement et savoir à l'avance que les paramètres restants se réfèrent à IPv6. La syntaxe de la commande est la même que d'habitude, à l'exception de l'ajout de l'option -6. Bien entendu, vous devez utiliser la syntaxe IPv6 si vous spécifiez une adresse plutôt qu'un nom d'hôte. Bien qu'IPv6 n'ait pas vraiment conquis le monde, il est largement utilisé dans certains pays (généralement asiatiques) et la plupart des systèmes d'exploitation modernes le prennent en charge. Pour utiliser Nping avec IPv6, la source et la destination de vos paquets doivent être configurées pour IPv6. Si votre FAI (comme la plupart d'entre eux) ne vous alloue pas d'adresses IPv6, des tunnels gratuits sont largement disponibles et fonctionnent bien avec Nping. Vous pouvez utiliser le service gratuit de tunnel broker IPv6 à l'adresse http://www.tunnelbroker.net.

Veuillez noter que la prise en charge d'IPv6 est encore très expérimentale et que de nombreux modes et options peuvent ne pas fonctionner avec.

Définit l'adresse IP source. Cette option vous permet de spécifier une adresse IP personnalisée à utiliser comme adresse IP source dans les paquets envoyés. Cela permet de usurper l'expéditeur des paquets. addr peut être une adresse IPv6 ou un nom d'hôte.

Ajoute une cible à la liste de cibles de Nping. Cette option est fournie pour la cohérence, mais son utilisation est déconseillée au profit des spécifications de cibles simples. Voir la section intitulée “SPÉCIFICATION DE CIBLE”.

Définit le label de flux IPv6. Le champ label de flux a 20 bits de long et est destiné à fournir certaines propriétés de qualité de service pour la livraison de datagrammes en temps réel. Cependant, il n'a pas été largement adopté et tous les routeurs ou points d'extrémité ne le prennent pas en charge. Définit la classe de trafic IPv6. OPTIONS ETHERNET

Dans la plupart des cas, Nping envoie des paquets au niveau IP brut. Cela signifie que Nping crée ses propres paquets IP et les transmet via une socket brute. Cependant, dans certains cas, il peut être nécessaire d'envoyer des paquets au niveau Ethernet brut. Cela se produit, par exemple, lorsque Nping est exécuté sous Windows (car Microsoft a désactivé la prise en charge des sockets brutes depuis Windows XP SP2), ou lorsque Nping est invité à envoyer des paquets ARP. Étant donné qu'il est parfois nécessaire de construire des trames Ethernet, Nping offre certaines options pour manipuler les différents champs.

--dest-mac mac (Adresse MAC de destination Ethernet)

Cette option définit l'adresse MAC de destination qui doit être définie dans les trames Ethernet sortantes. Ceci est utile au cas où Nping ne parviendrait pas à déterminer l'adresse MAC du prochain saut ou lorsque vous souhaitez acheminer des sondes via un routeur autre que la passerelle par défaut configurée. L'adresse MAC doit avoir le format habituel de six octets séparés par des deux-points, par exemple 00:50:56:d4:01:98. Alternativement, des tirets peuvent être utilisés à la place des deux-points. Si vous définissez une adresse MAC de destination erronée, vos sondes pourraient ne pas atteindre les cibles prévues.

Cette option définit l'adresse MAC source qui doit être définie dans les trames Ethernet sortantes. Ceci est utile au cas où Nping ne parviendrait pas à déterminer l'adresse MAC de votre interface réseau ou lorsque vous souhaitez injecter du trafic dans le réseau tout en masquant l'adresse réelle de votre carte réseau. MODE ÉCHO

Le "Mode Écho" est une technique novatrice implémentée par Nping qui permet aux utilisateurs de voir comment les paquets réseau changent en transit, de l'hôte d'origine à la machine cible. Essentiellement, le mode Écho transforme Nping en deux entités distinctes : le serveur Écho et le client Écho. Le serveur Écho est un service réseau capable de capturer des paquets du réseau et d'en envoyer une copie ("les échoer") au client d'origine via un canal TCP secondaire. Le client Écho est la partie qui génère ces paquets réseau, les transmet au serveur et reçoit leur version échoée via un canal TCP secondaire qu'il a précédemment établi avec le serveur Écho.

MODALITÉ ÉCHO

Le mode Écho de Nping est une fonctionnalité intéressante qui permet d'intercepter et d'analyser les paquets envoyés et reçus. En ayant le serveur renvoyer des copies des paquets reçus via le canal latéral, des éléments comme les périphériques NAT deviennent immédiatement apparents pour le client car il remarque les changements d'adresse IP source (et peut-être même de port source). D'autres périphériques comme ceux qui effectuent du façonnage de trafic, modifiant les tailles de fenêtre TCP ou ajoutant des options TCP transparencement entre les hôtes, se révèlent également.

Le mode Écho est également utile pour le dépannage des problèmes de routage et de pare-feu. Entre autres choses, il peut être utilisé pour déterminer si le trafic généré par le client Nping est abandonné en transit et n'atteint jamais sa destination, ou si ce sont les réponses qui ne reviennent pas au client.

En interne, le client et le serveur communiquent via un canal crypté et authentifié, utilisant le Protocole Écho Nping (NEP), dont la spécification technique se trouve à l'adresse https://nmap.org/svn/nping/docs/EchoProtoRFC.txt

Les paragraphes suivants décrivent les différentes options disponibles dans le mode Écho de Nping.

--ec phrase_de_passe, --echo-client phrase_de_passe (Exécuter le client Écho)

Cette option indique à Nping de s'exécuter en tant que client Écho. phrase_de_passe est une séquence de caractères ASCII qui est utilisée pour générer les clés cryptographiques nécessaires au chiffrement et à l'authentification dans une session donnée. La phrase de passe doit être un secret également connu du serveur, et elle peut contenir n'importe quel nombre de caractères ASCII imprimables. Les phrases de passe contenant des espaces ou des caractères spéciaux doivent être entourées de guillemets doubles.

Lors de l'exécution de Nping en tant que client Écho, la plupart des options des modes de sonde bruts réguliers s'appliquent. Le client peut être configuré pour envoyer des sondes spécifiques à l'aide d'indicateurs tels que --tcp, --icmp ou --udp. Les champs d'en-tête de protocole peuvent être manipulés normalement à l'aide des options appropriées (par exemple, --ttl, --seq, --icmp-type, etc.). Les seules exceptions sont les indicateurs liés à l'ARP, qui ne sont pas pris en charge en mode Écho, car les protocoles comme l'ARP sont étroitement liés à la couche de liaison de données et leurs sondes ne peuvent pas traverser différents segments réseau.

--es phrase_de_passe, --echo-server phrase_de_passe (Exécuter le serveur Écho)

Cette option indique à Nping de s'exécuter en tant que serveur Écho. phrase_de_passe est une séquence de caractères ASCII qui est utilisée pour générer les clés cryptographiques nécessaires au chiffrement et à l'authentification dans une session donnée. La phrase de passe doit être un secret également connu des clients, et elle peut contenir n'importe quel nombre de caractères ASCII imprimables. Les phrases de passe contenant des espaces ou des caractères spéciaux doivent être entourées de guillemets doubles. Notez que, bien que ce ne soit pas recommandé, il est possible d'utiliser des phrases de passe vides, en fournissant --echo-server "". Cependant, si ce que vous voulez est de configurer un serveur Écho ouvert, il est préférable d'utiliser l'option --no-crypto. Voir ci-dessous pour plus de détails.

--ep port, --echo-port port (Définir le numéro de port TCP Écho)

Cette option demande à Nping d'utiliser le numéro de port TCP spécifié pour la connexion du canal latéral Écho. Si cette option est utilisée avec --echo-server, elle spécifie le port sur lequel le serveur écoute les connexions. Si elle est utilisée avec --echo-client, elle spécifie le port auquel se connecter sur l'hôte distant. Par défaut, le numéro de port 9929 est utilisé.

--nc, --no-crypto (Désactiver le chiffrement et l'authentification)

Cette option demande à Nping de ne pas utiliser d'opérations cryptographiques pendant une session Écho. En pratique, cela signifie que les données de la session du canal latéral Écho seront transmises en clair, et aucune authentification ne sera effectuée par le serveur ou le client pendant la phase d'établissement de la session. Lorsque --no-crypto est utilisé, la phrase de passe fournie avec --echo-server ou --echo-client est ignorée.

Cette option doit être spécifiée si Nping a été compilé sans prise en charge d'openSSL. Notez que, pour des raisons techniques, une phrase de passe doit toujours être fournie après les indicateurs --echo-client ou --echo-server, même si elle sera ignorée.

L'indicateur --no-crypto peut être utile lors de la configuration d'un serveur Écho public, car il permet aux utilisateurs de se connecter au serveur Écho sans avoir besoin de phrase de passe ou de secret partagé. Cependant, il est fortement recommandé de ne pas utiliser --no-crypto sauf nécessité absolue. Les serveurs Écho publics doivent être configurés pour utiliser la phrase de passe "public" ou la phrase de passe vide (--echo-server "") car l'utilisation de la cryptographie fournit non seulement la confidentialité et l'authentification, mais aussi l'intégrité des messages.

--once (Servir un client et quitter)

Cette option demande au serveur Écho de quitter après avoir servi un client. Ceci est utile lorsqu'une seule session Écho doit être établie, car cela élimine la nécessité d'accéder à l'hôte distant pour arrêter le serveur.

--safe-payloads (Mettre à zéro les données d'application avant d'échoer un paquet)

Cette option demande au serveur Écho d'effacer toutes les données de la couche application trouvées dans les paquets clients avant de les échoer. Lorsque l'option est activée, le serveur Écho analyse les paquets reçus des clients Écho et essaie de déterminer s'ils contiennent des données au-delà de la couche transport. Si de telles données sont trouvées, elles sont écrasées par des zéros avant de transmettre les paquets au client Écho approprié.

Les serveurs Écho peuvent gérer plusieurs clients simultanés exécutant plusieurs sessions d'écho en parallèle. Afin de déterminer quel paquet doit être échoé à quel client et via quelle session, le serveur Écho utilise un algorithme heuristique. Bien que nous ayons pris toutes les mesures de sécurité imaginables pour éviter qu'un client ne reçoive un paquet échoé qu'il n'a pas généré, il existe toujours un risque que notre algorithme fasse une erreur et livre un paquet au mauvais client. L'option --safe-payloads est utile pour les serveurs d'écho publics ou les déploiements critiques où ce type d'erreur ne peut être toléré.

Dans cet exemple, la sortie est un peu plus délicate. L'absence de messages d'erreur montre que le client Écho a réussi à établir une session Écho avec le serveur. Cependant, aucun paquet CAPT ne peut être vu dans la sortie. Cela signifie qu'aucun des paquets transmis n'a atteint le serveur. Fait intéressant, un paquet TCP SYN-ACK a été reçu en réponse au premier paquet TCP-SYN (et on sait également que l'hôte cible n'a pas le port 80 ouvert). Ce comportement révèle la présence d'un serveur de cache proxy web transparent (qui dans ce cas est un ancien serveur MS ISA).

OPTIONS DE TEMPORISATION ET DE PERFORMANCE

--delay temps (Délai entre les sondes)

Cette option vous permet de contrôler le temps d'attente de Nping avant d'envoyer la sonde suivante. Comme dans de nombreux autres outils ping, le délai par défaut est d'une seconde. temps doit être un entier positif ou un nombre à virgule flottante. Par défaut, il est spécifié en secondes, cependant vous pouvez donner une unité explicite en ajoutant ms pour millisecondes, s pour secondes, m pour minutes, ou h pour heures (par exemple, 2.5s, 45m, 2h).

--rate débit (Envoyer les sondes à un débit donné)

Cette option spécifie le nombre de sondes que Nping doit envoyer par seconde. Cette option et --delay sont inverses ; --rate 20 équivaut à --delay 0.05. Si les deux options sont utilisées, seule la dernière dans la liste des paramètres compte.
