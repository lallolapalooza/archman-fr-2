DESCRIPTION

La fonction rcmd() est utilisée par le superutilisateur pour exécuter une commande sur une machine distante en utilisant un schéma d'authentification basé sur des numéros de port privilégiés. La fonction rresvport() renvoie un descripteur de fichier vers un socket avec une adresse dans l'espace des ports privilégiés. Les fonctions iruserok() et ruserok() sont utilisées par les serveurs pour authentifier les clients demandant un service avec rcmd(). Les quatre fonctions sont utilisées par le serveur rshd(8) (entre autres).

rcmd()

La fonction rcmd() recherche l'hôte *ahost en utilisant gethostbyname(3), renvoyant -1 si l'hôte n'existe pas. Sinon, *ahost est défini au nom standard de l'hôte et une connexion est établie vers un serveur résidant au port Internet bien connu inport.

Si la connexion réussit, un socket dans le domaine Internet de type SOCK_STREAM est retourné à l'appelant, et donné à la commande distante comme stdin et stdout. Si fd2p n'est pas nul, alors un canal auxiliaire vers un processus de contrôle sera configuré, et un descripteur de fichier pour celui-ci sera placé dans *fd2p. Le processus de contrôle renverra la sortie de diagnostic de la commande (unité 2) sur ce canal, et acceptera également des octets sur ce canal comme étant des numéros de signal UNIX, à transférer au groupe de processus de la commande. Si fd2p est 0, alors le stderr (unité 2 de la commande distante) sera identique au stdout et aucune disposition ne sera prise pour envoyer des signaux arbitraires au processus distant, bien que vous puissiez être en mesure d'attirer son attention en utilisant des données hors bande.

Le protocole est décrit en détail dans rshd(8).

rresvport()

La fonction rresvport() est utilisée pour obtenir un socket avec un port privilégié lié à celui-ci. Ce socket convient pour être utilisé par rcmd() et plusieurs autres fonctions. Les ports privilégiés sont ceux dans la plage 0 à 1023. Seul un processus privilégié (sous Linux, un processus ayant la capacité CAP_NET_BIND_SERVICE dans l'espace de noms utilisateur gouvernant son espace de noms réseau) est autorisé à se lier à un port privilégié. Dans l'implémentation glibc, cette fonction limite sa recherche aux ports de 512 à 1023. L'argument port est un argument valeur-résultat : sa valeur fournie à l'appel est utilisée comme point de départ pour une recherche circulaire de la plage de ports ; lors du retour (réussi), il contient le numéro de port qui a été lié.

iruserok() et ruserok()

Les fonctions iruserok() et ruserok() prennent l'adresse IP ou le nom de l'hôte distant, respectivement, deux noms d'utilisateur et un indicateur indiquant si le nom de l'utilisateur local est celui du superutilisateur. Ensuite, si l'utilisateur n'est *pas* le superutilisateur, elle vérifie le fichier /etc/hosts.equiv. Si cette recherche n'est pas effectuée, ou échoue, le fichier .rhosts dans le répertoire personnel de l'utilisateur local est vérifié pour voir si la demande de service est autorisée.

Si ce fichier n'existe pas, n'est pas un fichier régulier, appartient à quelqu'un d'autre que l'utilisateur ou le superutilisateur, est accessible en écriture par quelqu'un d'autre que le propriétaire, ou est lié par plusieurs noms (hardlinked) n'importe où, la vérification échoue automatiquement. Zéro est retourné si le nom de la machine est listé dans le fichier hosts.equiv, ou si le nom d'hôte et le nom d'utilisateur distant sont trouvés dans le fichier .rhosts ; sinon, iruserok() et ruserok() retournent -1. Si le domaine local (tel qu'obtenu par gethostname(2)) est le même que le domaine distant, seul le nom de la machine doit être spécifié.

Si l'adresse IP de l'hôte distant est connue, iruserok() devrait être préférée à ruserok(), car elle ne nécessite pas de faire confiance au serveur DNS pour le domaine de l'hôte distant.

Variantes *_af()

Toutes les fonctions décrites ci-dessus fonctionnent avec des sockets IPv4 (AF_INET). Les variantes "_af" prennent un argument supplémentaire qui permet de spécifier la famille d'adresses du socket. Pour ces fonctions, l'argument af peut être spécifié comme AF_INET ou AF_INET6. De plus, rcmd_af() prend en charge l'utilisation de AF_UNSPEC.

VALEUR DE RETOUR

La fonction rcmd() renvoie un descripteur de socket valide en cas de succès. Elle renvoie -1 en cas d'erreur et affiche un message diagnostique sur la sortie d'erreur standard.

La fonction rresvport() renvoie un descripteur de socket valide et lié en cas de succès. En cas d'échec, elle renvoie -1 et définit errno pour indiquer l'erreur. Le code d'erreur EAGAIN est surchargé pour signifier : "Tous les ports réseau sont utilisés".

Pour plus d'informations sur le retour de ruserok() et iruserok(), voir ci-dessus.

DESCRIPTION

Ces fonctions et les fonctions ruserok(3) sont utilisées pour exécuter des commandes à distance sur un autre système. Elles implémentent la convention de commande à distance, qui est une méthode d'authentification pour les processus permettant d'exécuter des programmes sur des machines distantes. La méthode d'authentification repose sur la confiance accordée aux ports sources et aux adresses IP des machines clientes.

Les fonctions rcmd_af(3) et rcmd(3) établissent une connexion TCP avec le démon rexecd(8) sur la machine distante (spécifiée par host). Si port n'est pas égal à zéro, ce port est utilisé ; sinon, le port pour la commande à distance est utilisé.

Les arguments sont les suivants :

  • domain : le domaine d'adresse pour le socket, par exemple AF_INET pour IPv4 ou AF_INET6 pour IPv6.
  • host : nom d'hôte ou adresse IP de la machine distante.
  • port : port de la machine distante. Si 0, le port par défaut pour les commandes à distance est utilisé.
  • user : nom d'utilisateur sur la machine distante.
  • aboutme : chaîne utilisée pour les requêtes de shell. Généralement, le nom de l'utilisateur local est utilisé.
  • cmd : commande à exécuter sur la machine distante.
  • fd2p : pointeur vers un entier. Si non NULL, le descripteur de fichier pour le canal de sortie d'erreur distant est stocké dans *fd2p.

Les fonctions rcmd_af(3) et rcmd(3) tentent de se connecter à un port éphémère sur la machine cliente. Elles effectuent ensuite une requête de service de nom (NS) pour trouver le service login ou cmd sur la machine distante. Après avoir établi une connexion avec le démon rexecd(8) sur la machine distante, elles négocient l'authentification en utilisant ruserok(3). Si l'authentification réussit, le démon rexecd(8) exécute la commande spécifiée.

La fonction rcmd(3) est une ancienne interface qui utilise par défaut le domaine d'adresse AF_INET.

VALEUR RENVOYÉE

En cas de succès, ces fonctions renvoient un descripteur de fichier qui représente la connexion à la commande à distance. La sortie standard de la commande distante sera lue à partir de ce descripteur de fichier, et l'entrée standard de la commande distante sera écrite dans ce descripteur de fichier. Les erreurs standard de la commande distante sont gérées séparément par le paramètre fd2p.

En cas d'échec, -1 est renvoyé et errno est défini pour indiquer l'erreur.
