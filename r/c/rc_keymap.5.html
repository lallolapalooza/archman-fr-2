NOM

rc_keymap - fichier toml décrivant une table de touches de télécommande

DESCRIPTION

Un rc_keymap décrit une télécommande. Il liste les protocoles utilisés et le mappage entre les IR décodés et les codes de touches Linux. Ce fichier est utilisé par ir-keytable(1) pour le décodage IR, et par ir-ctl(1) pour l'envoi d'IR.

Le format de fichier est toml. Comme une télécommande peut utiliser plusieurs protocoles, le niveau supérieur est un tableau de protocoles. La grande majorité des télécommandes n'utilise qu'un seul protocole.

ENTRÉE PROTOCOLE KEYMAP

Pour chaque protocole utilisé par la télécommande, il doit y avoir une entrée dans le tableau protocols de niveau supérieur.

Champ Nom

Chaque entrée de protocole a un champ name. Le nom n'est pas utilisé par ir-keytable ou ir-ctl, mais peut être utilisé pour donner à la télécommande un nom plus descriptif que le nom du fichier, par exemple, le numéro de modèle.

Champ Protocole

Le champ protocol spécifie le protocole. Il peut s'agir de l'un des décodeurs du noyau Linux, auquel cas il est nec, rc-5, rc-6, jvc, sony, sanyo, rc-5-sz, sharp, mce-kbd, xmp, imon, rc-mm, other ou unknown. S'il ne correspond à aucune de ces entrées, il est supposé être un décodeur basé sur BPF. unknown et other sont des protocoles décodés par des périphériques RC spécifiques où le protocole est inconnu ou propriétaire, respectivement.

Il existe quelques décodeurs de protocole BPF prédéfinis, qui sont listés ci-dessous. Voir https://lwn.net/Articles/759188/ pour savoir comment écrire le vôtre.

Champ Variante

Le champ variant spécifie quelle variante un protocole particulier utilise. Les protocoles sony, rc-5, rc-6 ont différentes variantes de longueur de bits, par exemple. Ce champ est utilisé par ir-ctl lors de l'envoi d'IR.

Les variantes suivantes sont actuellement définies :

Le protocole rc-5 a les variantes rc-5, rc-5x-20, rc-5-sz.

Le protocole nec a les variantes nec, nec-x, nec-32.

Le protocole sony a les variantes sony-12, sony-15, sony-20.

Le protocole rc-6 a les variantes rc-6-0, rc-6-6a-20, rc-6-6a-24, rc-6-6a-32, rc-6-mce.

Le protocole rc-mm a les variantes rc-mm-12, rc-mm-24, et rc-mm-32.

Champ Scancodes

Le tableau scancodes liste les codes de balayage et le mappage vers le code de touche d'entrée Linux. Plusieurs codes de balayage peuvent être mappés au même code de touche. Le champ scancodes n'est pas présent pour les protocoles raw.

Si le code de balayage commence par 0x, il est interprété comme un nombre hexadécimal. S'il commence par un 0, il est interprété comme un nombre octal.

Les codes de touches valides sont listés dans le fichier d'en-tête input-event-codes.h. Des exemples sont KEY_ENTER, KEY_ESC ou BTN_LEFT pour le bouton gauche de la souris. Notez que si la table des touches est uniquement utilisée pour l'envoi d'IR, la touche n'a pas besoin d'être un code de touche Linux valide. Elle peut être n'importe quelle chaîne sans espaces.

Champ Raw

Si le protocole est raw, le champ raw est un tableau de mappage code de touche vers brut. Pour chaque entrée, il y a un champ keycode et un champ raw. Le keycode est un code de touche d'entrée Linux, comme expliqué dans le champ scancodes ci-dessus.

Le champ raw est une chaîne, qui liste les valeurs d'impulsion et d'espace, séparées par des espaces. La première est une valeur d'impulsion en microsecondes, et la seconde un espace, la troisième une impulsion, etc. Les valeurs d'espace peuvent être précédées d'un signe - et la valeur d'impulsion peut être précédée d'un signe +. Il devrait y avoir un nombre impair de valeurs afin que la dernière entrée soit une impulsion.

Champs restants (paramètres BPF)

Si le protocole est un décodeur basé sur BPF, il peut avoir n'importe quel nombre de paramètres numériques. Ces paramètres sont utilisés pour prendre en charge les protocoles avec des longueurs de signalisation non standard pour les protocoles IR standard. Tout autre champ spécifié ici qui est requis par le décodeur BPF sélectionné sera utilisé. Tous les autres champs sont ignorés.

Les décodeurs de protocoles non-BPF basés sur le noyau n'ont aucun paramètre.

PROTOCOLES BPF

Certains des décodeurs de protocoles BPF sont génériques et nécessiteront des paramètres pour fonctionner. D'autres sont pour des télécommandes spécifiques et devraient fonctionner sans aucun paramètre. Les paramètres de temporisation sont tous en microsecondes (µs).

raw

Ce décodeur doit être utilisé lorsque la table des touches est brute ; pour chaque touche, il y a une entrée dans le tableau raw avec les valeurs d'impulsion et d'espace pour cette touche. Aucun décodage n'est effectué, l'IR entrant est simplement comparé aux différentes valeurs d'impulsion et d'espace.

imon_rsc

Ce décodeur est spécifiquement pour la télécommande iMON RSC, qui était livrée avec l'iMON Station (entre autres). Le décodeur est pour le joystick directionnel au milieu ; il les décodera en mouvements de souris. Les boutons sont tous codés en utilisant nec-x, donc la table des touches nécessite deux protocoles pour fonctionner correctement.

Ceci n'est pas lié au protocole imon.

margin
Définit la tolérance pour la longueur du message. Par défaut 200.

grundig

Ce décodeur est spécifiquement pour les anciennes télécommandes Grundig.

header_pulse
Longueur de la première impulsion, par défaut 900.
header_space
Longueur de l'espace suivant, par défaut 2900.
leader_pulse
Longueur de la deuxième impulsion, par défaut 1300.

xbox

Ce décodeur est spécifiquement pour la télécommande DVD de la XBox, qui est pour la XBox de première génération.

margin
Définit la tolérance pour la longueur du message. Par défaut 200.

manchester

La plupart des télécommandes codées en Manchester sont soit rc-5, rc-6, ou rc-mm. Certaines télécommandes utilisent une variante différente (par exemple, elles pourraient avoir une impulsion d'en-tête) et c'est pour cela que le décodeur est fait. Certains paramètres doivent être spécifiés, par défaut il est configuré pour rc-5.

margin
Définit la tolérance pour la longueur du message. Par défaut 200.
header_pulse
Définit la durée d'une impulsion de tête. Elle n'est pas toujours présente. Par défaut 0.
header_space
Définit la durée de l'espace après l'impulsion de tête. Doit être défini si header_pulse est défini.
zero_pulse, zero_space, one_pulse, one_space
Longueurs de signalisation pour les bits. Voir https://clearwater.com.au/code/rc5 pour la définition de ceux-ci.
bits
Nombre de bits. Par défaut 14.
scancode_mask
Bits à masquer du code de balayage résultant.
toggle_bit
Bit qui spécifie la commutation. Si cette valeur est supérieure au nombre de bits, aucune commutation n'est définie.

rc_keymap(5) — v4l-utils 1.32.0

NAME

rc_keymap - Linux Input subsystem RC keymap configuration file format

DESCRIPTION

The Linux Input subsystem rc_keymap(5) files are used to map IR-receiver events to key codes. They are a set of protocols, each having a set of key codes associated.

The file format is a list of protocols, with optional parameters, and a list of key codes associated to the protocol.

An entry is defined by a protocol name, optional parameters, and a list of key codes associated to the protocol.

Empty lines and lines starting with # are ignored.

[[protocols]]
name = "my_remote"
protocol = "nec"
variant = "variant_name"
param1 = value1
param2 = value2
[protocols.scancodes]
scancode1 = "KEY_0"
scancode2 = "KEY_1"
...
[[protocols]]
protocol = "my_other_remote"
param1 = value1
...

The first [[protocols]] section starts the definition of a new protocol. The name is optional, and it is used to identify the remote by name. If not specified, then the name is derived from the protocol name and possible variant.

The protocol field is mandatory and it specifies the protocol used. Available protocols are: pulse_distance, pulse_length, nec, sony, rc5, rc6, hauppauge, winlirc, imap, lgdtv, terratec, leadtek, d68, xmp, ms701, revox, denon, sharp, samsung, mce, coolix, itach, bocthk1, streamzap, tty, keytech, firetv, av_resume, rc_a800, tcl, p231, hde, firetv_dt, amc.

Some protocols have variants. The variant field is optional.

Parameters are protocol-specific. They are defined as parameter = value.

The [protocols.scancodes] section starts the definition of scancodes for the current protocol.

Scancodes are defined as scancode = "KEY_CODE".

The scancode can be a number (e.g. 0x1234) or a name (e.g. ABCD). The name is case-sensitive.

The KEY_CODE must be a valid Linux input event code. They can be found in input-event-codes.h.

KEYMAP PROTOCOL ENTRY

nec

This is a generic decoder for protocols that define bits by distance between pulses, and the pulses are always of the same length. The most well known protocol like this is nec. This decoder is cases where nec is not used. The parameters must be set.

margin
Define how much tolerance there is for message length. Default 200.
header_pulse
Length of the first leading pulse. Default 2125.
header_space
Length of the space after the leading pulse. Default 1875.
repeat_pulse
Length of the leading pulse for key repeat. Default 0.
repeat_space
Length of the space after the leading pulse for key repeat. Default 0.
bit_pulse
Length of the pulse for each bit. Default 625.
bit_0_space
Length of the space for a zero bit. Default 375.
bit_1_space
Length of the space for a one bit. Default 1625.
trailer_pulse
Length of the pulse after the last bit. Needed to bookend the last bit. Default 625.
bits
Number of bits. Default 4.
reverse
Should the bits be read in least significant bit first. Set to non-zero to enable. Default 0.
header_optional
Some remotes do not send the header pulse and space for key repeats, so set this to non-zero to make the header optional. Default 0.

An alternative implementation might only allow missing headers for repeat messages, but this would fail to decode key presses if the first message with the header did not decode correctly to due interference.

pulse_distance

This is a generic decoder for protocols that define bits by distance between pulses, and the pulses are always of the same length. The most well known protocol like this is nec. This decoder is cases where nec is not used. The parameters must be set.

margin
Define how much tolerance there is for message length. Default 200.
header_pulse
Length of the first leading pulse. Default 2125.
header_space
Length of the space after the leading pulse. Default 1875.
repeat_pulse
Length of the leading pulse for key repeat. Default 0.
repeat_space
Length of the space after the leading pulse for key repeat. Default 0.
bit_pulse
Length of the pulse for each bit. Default 625.
bit_0_space
Length of the space for a zero bit. Default 375.
bit_1_space
Length of the space for a one bit. Default 1625.
trailer_pulse
Length of the pulse after the last bit. Needed to bookend the last bit. Default 625.
bits
Number of bits. Default 4.
reverse
Should the bits be read in least significant bit first. Set to non-zero to enable. Default 0.
header_optional
Some remotes do not send the header pulse and space for key repeats, so set this to non-zero to make the header optional. Default 0.

An alternative implementation might only allow missing headers for repeat messages, but this would fail to decode key presses if the first message with the header did not decode correctly to due interference.

pulse_length

This is a generic decoder for protocols that define bits by length of pulses, and the spaces are always the same. The sony protocol is the most well-known protocol, but this decoder is for protocols which are not sony.

margin
Define how much tolerance there is for message length. Default 200.
header_pulse
Length of the first leading pulse. Default 2125.
header_space
Length of the space after the leading pulse. Default 1875.
repeat_pulse
Length of the leading pulse for key repeat. Default 0.
repeat_space
Length of the space after the leading pulse for key repeat. Default 0.
bit_space
Length of the space for each bit. Default 625.
bit_0_pulse
Length of the pulse for a zero bit. Default 375.
bit_1_pulse
Length of the pulse for a one bit. Default 1625.
trailer_pulse
Length of the pulse after the last bit. Optional. Default 0.
bits
Number of bits. Default 4.
reverse
Should the bits be read in least significant bit first. Set to non-zero to enable. Default 0.
header_optional
Some remotes do not send the header pulse and space for key repeats, so set this to non-zero to make the header optional. Default 0.

An alternative implementation might only allow missing headers for repeat messages, but this would fail to decode key presses if only the first message did not decode correctly to due interference.

BPF PROTOCOLS

The following protocols are implemented using BPF (Berkeley Packet Filter).

The parameters are similar to the ones above. The main difference is that the parameters are defined using a comma-separated list of name=value pairs.

nec
The NEC IR protocol. Parameters: margin, header_pulse, header_space, repeat_pulse, repeat_space, bit_pulse, bit_0_space, bit_1_space, trailer_pulse, bits, reverse, header_optional. All parameters are optional and use the default values.
rc5
The RC-5 IR protocol. Parameters: margin, header_pulse, header_space, bit_pulse, bit_0_pulse, bit_1_pulse, bits, reverse, header_optional. All parameters are optional and use the default values.
rc6
The RC-6 IR protocol. Parameters: margin, header_pulse, header_space, repeat_pulse, repeat_space, bit_pulse, bit_0_pulse, bit_1_pulse, trailer_pulse, bits, reverse, header_optional. All parameters are optional and use the default values.

sony
The Sony IR protocol. Parameters: margin, header_pulse, header_space, repeat_pulse, repeat_space, bit_space, bit_0_pulse, bit_1_pulse, trailer_pulse, bits, reverse, header_optional. All parameters are optional and use the default values.

mce
The Microsoft Windows Common Encoder (MCE) IR protocol. Parameters: margin, header_pulse, header_space, repeat_pulse, repeat_space, bit_pulse, bit_0_space, bit_1_space, trailer_pulse, bits, reverse, header_optional. All parameters are optional and use the default values.
lirc
This protocol uses a LIRCfile to define the protocol. This is useful for non-standard protocols. The parameters are:
lircfile
Path to the LIRCfile.
winlirc
This protocol uses a WinLIRC file to define the protocol. This is useful for non-standard protocols. The parameters are:
winlircfile
Path to the WinLIRC file.
commands
This protocol allows to define raw commands. This is useful for defining non-standard protocols. The parameters are:
command
A sequence of pulses and spaces. Example: command="1000,500,500,1500" defines a command with a pulse of 1000us and a space of 500us, followed by a pulse of 500us and a space of 1500us.
