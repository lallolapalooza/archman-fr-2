rmic(1) Outils d'invocation de méthode à distance (RMI) rmic(1)

NOM

rmic - Génère des classes stub, skeleton et tie pour les objets distants utilisant le protocole de méthode à distance Java (JRMP) ou le protocole Internet Inter-Orb (IIOP). Génère également le langage de définition d'interface (IDL) de l'Object Management Group (OMG)

SYNTAXE

rmic [ options ] noms-de-classes-qualifiés-par-paquet
options
Les options de la ligne de commande. Voir Options.
noms-de-classes-qualifiés-par-paquet
Noms de classes incluant leurs paquets, par exemple, java.awt.Color.

DESCRIPTION

Note de dépréciation : La prise en charge de la génération statique des stubs et skeletons du protocole de méthode à distance Java (JRMP) est dépréciée. Oracle recommande d'utiliser des stubs JRMP générés dynamiquement à la place, éliminant ainsi le besoin d'utiliser cet outil pour les applications basées sur JRMP. Voir la spécification java.rmi.server.UnicastRemoteObject à l'adresse http://docs.oracle.com/javase/8/docs/api/java/rmi/server/UnicastRemoteObject.html pour plus d'informations.

Le compilateur rmic génère des fichiers de classes stub et skeleton en utilisant le protocole de méthode à distance Java (JRMP) et des fichiers de classes stub et tie (protocole IIOP) pour les objets distants. Ces fichiers de classes sont générés à partir de classes Java compilées qui sont des classes d'implémentation d'objets distants. Une classe d'implémentation distante est une classe qui implémente l'interface java.rmi.Remote. Les noms de classes dans la commande rmic doivent être ceux de classes qui ont été compilées avec succès avec la commande javac et doivent être entièrement qualifiés par leur paquet. Par exemple, exécuter la commande rmic sur le nom de fichier de classe HelloImpl comme montré ici crée le fichier HelloImpl_Stub.class dans le sous-répertoire hello (nommé d'après le paquet de la classe) :

rmic hello.HelloImpl

Un skeleton pour un objet distant est une entité côté serveur du protocole JRMP qui possède une méthode qui distribue les appels à l'implémentation de l'objet distant.

Un tie pour un objet distant est une entité côté serveur similaire à un skeleton, mais qui communique avec le client en utilisant le protocole IIOP.

Un stub est un proxy côté client pour un objet distant, responsable de la communication des invocations de méthodes sur les objets distants vers le serveur où réside l'implémentation réelle de l'objet distant. Une référence d'un client à un objet distant est donc une référence à un stub local.

Par défaut, la commande rmic génère des classes stub qui utilisent uniquement la version 1.2 du protocole stub JRMP, comme si l'option -v1.2 était spécifiée. L'option -vcompat était le défaut dans les versions antérieures à la 5.0. Utilisez l'option -iiop pour générer des classes stub et tie pour le protocole IIOP. Voir Options.

Un stub implémente uniquement les interfaces distantes, et non les interfaces locales que l'objet distant implémente également. Comme un stub JRMP implémente le même ensemble d'interfaces distantes que l'objet distant, un client peut utiliser les opérateurs intégrés au langage de programmation Java pour le cast et la vérification de type. Pour IIOP, la méthode PortableRemoteObject.narrow doit être utilisée.

OPTIONS

-bootclasspath chemin

Remplace l'emplacement des fichiers de classes de démarrage.
-classpath chemin

Spécifie le chemin que la commande rmic utilise pour rechercher les classes. Cette option remplace le défaut ou la variable d'environnement CLASSPATH lorsqu'elle est définie. Les répertoires sont séparés par des deux-points. Le format général pour le chemin est : .:<votre_chemin>, par exemple : .:/usr/local/java/classes.
-d répertoire

Spécifie le répertoire de destination racine pour la hiérarchie de classes générée. Vous pouvez utiliser cette option pour spécifier un répertoire de destination pour les fichiers stub, skeleton et tie. Par exemple, la commande suivante place les classes stub et skeleton dérivées de MyClass dans le répertoire /java/classes/exampleclass. 
rmic -d /java/classes exampleclass.MyClass

Si l'option -d n'est pas spécifiée, alors le comportement par défaut est comme si -d . était spécifié. La hiérarchie de paquets de la classe cible est créée dans le répertoire courant, et les fichiers stub/tie/skeleton y sont placés. Dans certaines versions antérieures de la commande rmic, si l'option -d n'était pas spécifiée, la hiérarchie de paquets n'était pas créée et tous les fichiers de sortie étaient placés directement dans le répertoire courant.

-extdirs chemin

Remplace l'emplacement des extensions installées.
-g

Active la génération de toutes les informations de débogage, y compris les variables locales. Par défaut, seules les informations de numéro de ligne sont générées.
-idl

Demande à la commande rmic de générer du OMG IDL pour les classes spécifiées et toutes les classes référencées. L'IDL fournit une manière purement déclarative et indépendante du langage de programmation de spécifier une API pour un objet. L'IDL est utilisé comme une spécification pour les méthodes et les données qui peuvent être écrites dans et appelées depuis n'importe quel langage fournissant des liaisons CORBA. Cela inclut Java et C++ entre autres. Voir Java IDL: Java Language Mapping at http://docs.oracle.com/javase/8/docs/technotes/guides/idl/mapping/jidlMapping.html

Lorsque l'option -idl est utilisée, d'autres options incluent également :

•
Les options -always ou -alwaysgenerate forcent la régénération même lorsque les stubs/ties/IDL existants sont plus récents que la classe d'entrée.
•
L'option -factory utilise le mot-clé factory dans l'IDL généré.
•
L'option -idlModule de JavaPackage[.class]toIDLModule spécifie le mappage du paquet IDLEntity, par exemple : -idlModulemy.module my::real::idlmod.
•
-idlFilefromJavaPackage[.class] toIDLFile spécifie le mappage de fichier IDLEntity, par exemple : -idlFile test.pkg.X TEST16.idl.
-iiop

Demande à la commande rmic de générer des classes stub et tie IIOP, plutôt que des classes stub et skeleton JRMP. Une classe stub est un proxy local pour un objet distant et est utilisée par les clients pour envoyer des appels à un serveur. Chaque interface distante nécessite une classe stub, qui implémente cette interface distante. Une référence client à un objet distant est une référence à un stub. Les classes tie sont utilisées côté serveur pour traiter les appels entrants et distribuer les appels à la classe d'implémentation appropriée. Chaque classe d'implémentation nécessite une classe tie.

Si vous appelez la commande rmic avec -iiop, elle générera des stubs et des ties qui suivent cette convention de nommage :

_<nom_implémentation>_stub.class
_<nom_interface>_tie.class
•
Lorsque vous utilisez l'option -iiop, d'autres options incluent également :
•
Les options -always ou -alwaysgenerate forcent la régénération même lorsque les stubs/ties/IDL existants sont plus récents que la classe d'entrée.
•
L'option -nolocalstubs signifie ne pas créer de stubs optimisés pour les clients et serveurs dans le même processus.
•
L'option -noValueMethods doit être utilisée avec l'option -idl. L'option -noValueMethods empêche l'ajout des méthodes et initialisateurs valuetype à l'IDL émis. Ces méthodes et initialisateurs sont optionnels pour les valuetypes, et sont générés à moins que l'option -noValueMethods ne soit spécifiée avec l'option -idl.
•

NAME

rmic - Java Remote Method Invocation compiler

SYNOPSIS

rmic [options] fully-qualified-class-name ...

DESCRIPTION

rmic

The Java Remote Method Invocation (RMI) compiler, rmic, generates stub and skeleton files necessary for RMI applications. Stub and skeleton files are Java source files that are compiled into Java class files using the Java compiler, javac.

Stubs are client-side proxies for remote objects. When a client calls a method on a stub, the stub is responsible for marshaling the call parameters, sending the call to the remote object's skeleton, and returning the result.

Skeletons are server-side objects that receive calls from stubs, unmarshal the parameters, invoke the actual method on the remote object, and marshal the return value.

The rmic compiler generates stub and skeleton classes for remote objects. For a given remote object class, rmic generates a stub class and a skeleton class. The generated stub class has the same name as the remote object class, with _Stub appended. The generated skeleton class has the same name as the remote object class, with _Skel appended.

For example, if you have a remote object class named MyRemoteObject, rmic will generate MyRemoteObject_Stub.java and MyRemoteObject_Skel.java.

The org.omg.PortableServer.Servant. The PortableServer module for the Portable Object Adapter (POA) defines the native Servant type. In the Java programming language, the Servant type is mapped to the Java org.omg.PortableServer.Servant class. It serves as the base class for all POA servant implementations and provides a number of methods that can be called by the application programmer, and methods that are called by the POA and that can be overridden by the user to control aspects of servant behavior. Based on the OMG IDL to Java Language Mapping Specification, CORBA V 2.3.1 ptc/00-01-08.pdf.

OPTIONS

-J

Used with any Java command, the -J option passes the argument that follows the -J (no spaces between the -Jand the argument) to the Java interpreter
-keep or -keepgenerated

Retains the generated .java source files for the stub, skeleton, and tie classes and writes them to the same directory as the.class files.
-nowarn

Turns off warnings. When the -nowarn options is used. The compiler does not print out any warnings.
-nowrite

Does not write compiled classes to the file system.
-vcompat (deprecated)

Generates stub and skeleton classes that are compatible with both the 1.1 and 1.2 JRMP stub protocol versions. This option was the default in releases before 5.0. The generated stub classes use the 1.1 stub protocol version when loaded in a JDK 1.1 virtual machine and use the 1.2 stub protocol version when loaded into a 1.2 (or later) virtual machine. The generated skeleton classes support both 1.1 and 1.2 stub protocol versions. The generated classes are relatively large to support both modes of operation. Note: This option has been deprecated. See Description.
-verbose

Causes the compiler and linker to print out messages about what classes are being compiled and what class files are being loaded.
-v1.1 (deprecated)

Generates stub and skeleton classes for the 1.1 JRMP stub protocol version only. The -v1.1 option is only useful for generating stub classes that are serialization-compatible with preexisting, statically deployed stub classes that were generated by the rmic command from JDK 1.1 and that cannot be upgraded (and dynamic class loading is not being used). Note: This option has been deprecated. See Description.
-v1.2 (deprecated)

(Default) Generates stub classes for the 1.2 JRMP stub protocol version only. No skeleton classes are generated because skeleton classes are not used with the 1.2 stub protocol version. The generated stub classes do not work when they are loaded into a JDK 1.1 virtual machine. Note: This option has been deprecated. See Description.

CLASSPATH
Used to provide the system a path to user-defined classes. Directories are separated by colons, for example: .:/usr/local/java/classes.
