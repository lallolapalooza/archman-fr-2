rmic(1) Outils d'invocation de méthode distante (RMI) rmic(1)

NOM

rmic - Génère des classes stub, skeleton et tie pour les objets distants qui utilisent le protocole Java Remote Method Protocol (JRMP) ou le protocole Internet Inter-Orb (IIOP). Génère également le langage de définition d'interface (IDL) de l'Object Management Group (OMG)

SYNTAXE

rmic [ options ] noms-de-classes-qualifiés-par-paquet
options
Les options de la ligne de commande. Voir Options.
noms-de-classes-qualifiés-par-paquet
Noms de classes incluant leurs paquets, par exemple, java.awt.Color.

DESCRIPTION

Note de dépréciation : La prise en charge de la génération statique des stubs et skeletons du Java Remote Method Protocol (JRMP) est obsolète. Oracle recommande d'utiliser des stubs JRMP générés dynamiquement à la place, éliminant ainsi le besoin d'utiliser cet outil pour les applications basées sur JRMP. Voir la spécification java.rmi.server.UnicastRemoteObject à l'adresse http://docs.oracle.com/javase/8/docs/api/java/rmi/server/UnicastRemoteObject.html pour plus d'informations.

Le compilateur rmic génère des fichiers de classe stub et skeleton en utilisant le protocole Java Remote Method Protocol (JRMP) et des fichiers de classe stub et tie (protocole IIOP) pour les objets distants. Ces fichiers de classe sont générés à partir de classes Java compilées qui sont des classes d'implémentation d'objets distants. Une classe d'implémentation distante est une classe qui implémente l'interface java.rmi.Remote. Les noms de classes dans la commande rmic doivent correspondre à des classes qui ont été compilées avec succès avec la commande javac et doivent être entièrement qualifiés par leur paquet. Par exemple, exécuter la commande rmic sur le nom de fichier de classe HelloImpl comme indiqué ici crée le fichier HelloImpl_Stub.class dans le sous-répertoire hello (nommé d'après le paquet de la classe) :

rmic hello.HelloImpl

Un skeleton pour un objet distant est une entité côté serveur du protocole JRMP qui possède une méthode qui distribue les appels à l'implémentation de l'objet distant.

Un tie pour un objet distant est une entité côté serveur similaire à un skeleton, mais qui communique avec le client en utilisant le protocole IIOP.

Un stub est un proxy côté client pour un objet distant, responsable de la communication des invocations de méthodes sur les objets distants vers le serveur où réside l'implémentation réelle de l'objet distant. La référence d'un client à un objet distant est donc une référence à un stub local.

Par défaut, la commande rmic génère des classes stub qui utilisent uniquement la version 1.2 du protocole de stub JRMP, comme si l'option -v1.2 était spécifiée. L'option -vcompat était la valeur par défaut dans les versions antérieures à la 5.0. Utilisez l'option -iiop pour générer des classes stub et tie pour le protocole IIOP. Voir Options.

Un stub implémente uniquement les interfaces distantes, et non les interfaces locales que l'objet distant implémente également. Comme un stub JRMP implémente le même ensemble d'interfaces distantes que l'objet distant, un client peut utiliser les opérateurs intégrés du langage de programmation Java pour les conversions de type et la vérification de type. Pour IIOP, la méthode PortableRemoteObject.narrow doit être utilisée.

OPTIONS

-bootclasspath chemin

Remplace l'emplacement des fichiers de classes de démarrage.
-classpath chemin

Spécifie le chemin que la commande rmic utilise pour rechercher les classes. Cette option remplace la valeur par défaut ou la variable d'environnement CLASSPATH lorsqu'elle est définie. Les répertoires sont séparés par des deux-points. Le format général pour le chemin est : .:<votre_chemin>, par exemple : .:/usr/local/java/classes.
-d répertoire

Spécifie le répertoire racine de destination pour la hiérarchie de classes générée. Vous pouvez utiliser cette option pour spécifier un répertoire de destination pour les fichiers stub, skeleton et tie. Par exemple, la commande suivante place les classes stub et skeleton dérivées de MyClass dans le répertoire /java/classes/exampleclass. 
rmic -d /java/classes exampleclass.MyClass

Si l'option -d n'est pas spécifiée, le comportement par défaut est comme si -d . avait été spécifié. La hiérarchie de paquets de la classe cible est créée dans le répertoire courant, et les fichiers stub/tie/skeleton y sont placés. Dans certaines versions antérieures de la commande rmic, si l'option -d n'était pas spécifiée, la hiérarchie de paquets n'était pas créée et tous les fichiers de sortie étaient placés directement dans le répertoire courant.

-extdirs chemin

Remplace l'emplacement des extensions installées.
-g

Active la génération de toutes les informations de débogage, y compris les variables locales. Par défaut, seules les informations de numéro de ligne sont générées.
-idl

Fait en sorte que la commande rmic génère de l'IDL OMG pour les classes spécifiées et toutes les classes référencées. L'IDL fournit un moyen purement déclaratif et indépendant du langage de programmation de spécifier une API pour un objet. L'IDL est utilisé comme une spécification pour les méthodes et les données qui peuvent être écrites et appelées depuis n'importe quel langage qui fournit des liaisons CORBA. Cela inclut Java et C++ entre autres. Voir Java IDL: IDL to Java Language Mapping à l'adresse http://docs.oracle.com/javase/8/docs/technotes/guides/idl/mapping/jidlMapping.html

Lorsque l'option -idl est utilisée, d'autres options incluent également :

•
Les options -always ou -alwaysgenerate forcent la régénération même lorsque les stubs/ties/IDL existants sont plus récents que la classe d'entrée.
•
L'option -factory utilise le mot-clé factory dans l'IDL généré.
•
-idlModule de JavaPackage[.class]versIDLModule spécifie le mapping du paquet IDLEntity, par exemple : -idlModulemy.module my::real::idlmod.
•
-idlFiledeJavaPackage[.class] versIDLFile spécifie le mapping du fichier IDLEntity, par exemple : -idlFile test.pkg.X TEST16.idl.
-iiop

Fait en sorte que la commande rmic génère des classes stub et tie IIOP, plutôt que des classes stub et skeleton JRMP. Une classe stub est un proxy local pour un objet distant et est utilisée par les clients pour envoyer des appels à un serveur. Chaque interface distante nécessite une classe stub, qui implémente cette interface distante. La référence d'un client à un objet distant est une référence à un stub. Les classes tie sont utilisées côté serveur pour traiter les appels entrants et distribuer les appels à la classe d'implémentation appropriée. Chaque classe d'implémentation nécessite une classe tie.

Si vous appelez la commande rmic avec -iiop, elle génère des stubs et des ties qui respectent la convention de nommage suivante :

_<nom_implémentation>_stub.class
_<nom_interface>_tie.class
•
Lorsque vous utilisez l'option -iiop, d'autres options incluent également :
•
Les options -always ou -alwaysgenerate forcent la régénération même lorsque les stubs/ties/IDL existants sont plus récents que la classe d'entrée.
•
L'option -nolocalstubs signifie ne pas créer de stubs optimisés pour les clients et serveurs du même processus.
•
L'option -noValueMethods doit être utilisée avec l'option -idl. L'option -noValueMethods empêche l'ajout de méthodes et d'initialiseurs valuetype à l'IDL émis. Ces méthodes et initialiseurs sont facultatifs pour les valuetypes, et sont générés sauf si l'option -noValueMethods est spécifiée avec l'option -idl .
•

rmic-openjdk11.1 - Raccourci de compilation d'interface RMI

rmic-openjdk11(1) - rmic: compilateur d'interface RMI

NAME

rmic - compilateur d'interface RMI

SYNOPSIS

rmic [ options ] [ fully-qualified-class-name ... ]

DESCRIPTION

rmic génère des stubs d'interface RMI, des squelettes et des classes de liaison à partir des fichiers de classe compilés contenant des définiciones d'interface et de classe RMI. Rmic est utilisé pour la génération de code afin de permettre à Java d'être utilisé dans des applications clientes et serveur CORBA et RMI.

rmic utilise la spécification Java Remote Method Invocation (RMI) et la spécification de mappage du langage Java vers OMG IDL pour CORBA V2.3.1, ptc/00-01-08.pdf. Cette spécification de mappage est disponible sur le site Web de l'OMG.

Les stub et skeletons RMI CORBA sont générés par le compilateur rmic. Le compilateur rmic génère un fichier .java qui peut ensuite être compilé par le compilateur Java javac.

Par défaut, rmic génère des stubs et skeletons compatibles avec la version 1.2 de la spécification de mappage Java vers OMG IDL.

Le Portable Object Adapter (POA) définit le type natif Servant. Dans le langage de programmation Java, le type Servant est mappé à la classe Java org.omg.PortableServer.Servant. Elle sert de classe de base pour toutes les implémentations de servant POA et fournit un certain nombre de méthodes pouvant être appelées par le programmeur d'application, et des méthodes qui sont appelées par le POA et qui peuvent être remplacées par l'utilisateur pour contrôler les aspects du comportement du servant. Basé sur la spécification de mappage du langage Java vers OMG IDL, CORBA V 2.3.1 ptc/00-01-08.pdf.

OPTIONS

-J

Utilisé avec n'importe quelle commande Java, l'option -J passe l'argument qui suit -J (sans espace entre -J et l'argument) à l'interpréteur Java.
-keep ou -keepgenerated

Conserve les fichiers source .java générés pour les classes stub, skeleton et tie et les écrit dans le même répertoire que les fichiers .class.
-nowarn

Désactive les avertissements. Lorsque l'option -nowarn est utilisée, le compilateur n'affiche aucun avertissement.
-nowrite

N'écrit pas les classes compilées dans le système de fichiers.
-vcompat (obsolète)

Génère des classes stub et skeleton compatibles avec les versions 1.1 et 1.2 du protocole de stub JRMP. Cette option était la valeur par défaut dans les versions antérieures à 5.0. Les classes stub générées utilisent la version 1.1 du protocole de stub lorsqu'elles sont chargées dans une machine virtuelle JDK 1.1 et utilisent la version 1.2 du protocole de stub lorsqu'elles sont chargées dans une machine virtuelle 1.2 (ou ultérieure). Les classes skeleton générées prennent en charge les versions 1.1 et 1.2 du protocole de stub. Les classes générées sont relativement volumineuses pour prendre en charge les deux modes de fonctionnement. Remarque : Cette option est obsolète. Voir Description.
-verbose

Indique au compilateur et à l'éditeur de liens d'afficher des messages sur les classes en cours de compilation et les fichiers de classes en cours de chargement.
-v1.1 (obsolète)

Génère uniquement des classes stub et skeleton pour la version 1.1 du protocole de stub JRMP. L'option -v1.1 est uniquement utile pour générer des classes stub qui sont compatibles en sérialisation avec des classes stub préexistantes, déployées statiquement, qui ont été générées par la commande rmic à partir de JDK 1.1 et qui ne peuvent pas être mises à niveau (et le chargement dynamique de classes n'est pas utilisé). Remarque : Cette option est obsolète. Voir Description.
-v1.2 (obsolète)

(Par défaut) Génère uniquement des classes stub pour la version 1.2 du protocole de stub JRMP. Aucune classe skeleton n'est générée car les classes skeleton ne sont pas utilisées avec la version 1.2 du protocole de stub. Les classes stub générées ne fonctionnent pas lorsqu'elles sont chargées dans une machine virtuelle JDK 1.1. Remarque : Cette option est obsolète. Voir Description.

VARIABLES D'ENVIRONNEMENT

CLASSPATH
Utilisé pour fournir au système un chemin vers les classes définies par l'utilisateur. Les répertoires sont séparés par des deux-points, par exemple : .:/usr/local/java/classes.
