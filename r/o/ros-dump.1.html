ros-dump - créer une image vidée d'un script roswell

Synopsis

ros [OPTIONS1...] dump [OPTIONS2...] MODE args...

OPTIONS1 spécifie les options standard de roswell comme -L ou -m LISP. OPTIONS2 spécifie les options de réduction d'image que nous décrivons plus tard. MODE est soit output soit executable.

Description

ros-dump crée une image lisp vidée de l'état après traitement de toutes les options OPTIONS1.

Il a deux modes : output et executable. Dans les deux modes, l'environnement global (par ex. liaison globale aux variables spéciales comme *package*) de l'état juste après le redémarrage est l'environnement qui était effectif au moment où le script a été vidé.

L'image vidée n'est généralement pas compatible entre les différentes implémentations, ni entre les versions.

Modes de vidage

output [-f] [-o OUTPUT] NOM

Il charge le script roswell NOM et sauvegarde l'état lisp actuel dans une image.

Le fichier image est par défaut écrit dans un répertoire interne de roswell de manière organisée, c'est-à-dire quelque part sous $ROSWELL_INSTALL_DIR déduit par l'implémentation actuelle, sa version et le NOM donné.

Lorsque le fichier de sortie existe déjà, la commande échoue avec un code d'erreur.

L'image peut être chargée par ros -m IMAGE. Lors du redémarrage à partir de l'image, les sous-commandes roswell standard et les arguments supplémentaires pour le script sont également disponibles, par exemple ros run pour reprendre avec un repl, ou --restart FUNC pour appeler une fonction spécifique, en laissant une certaine flexibilité.

-o OUTPUT
L'image est écrite dans OUTPUT au lieu de l'emplacement par défaut.
-f
Force la sortie lorsque la sortie existe déjà.

executable NOM [-o OUTPUT]

Lorsqu'un script est vidé avec executable, l'image vidée devient un exécutable binaire autonome qui implique --restart main.

Si OUTPUT est donné, le binaire résultant est écrit dans ce fichier. Sinon, le nom du fichier de sortie est déduit de NOM et est écrit dans le même répertoire. Sous Windows et si SCRIPT a l'extension .ros, le nom du fichier sera SCRIPT.exe. Sur les autres systèmes, le résultat sera SCRIPT (sans extension).

Cette fonctionnalité est prise en charge sur SBCL, CCL, CMUCL, CLISP, ECL.

Options de réduction d'image

Ces options dissocient certaines références aux objets d'exécution et permettent au GC de récupérer de la mémoire, ce qui réduit finalement la taille de l'image vidée.

Il faut veiller à ce que le programme résultant fonctionne comme prévu, car certaines de ces opérations peuvent détruire les hypothèses communes des programmes conformes. Par exemple, les options de réduction relatives aux paquets peuvent empêcher les appels d'exécution à READ après le redémarrage.

Les options de réduction sont traitées de gauche à droite.

–disable-compression, –enable-compression, -c
Ces options désactivent/activent/activent la fonctionnalité de compression du noyau dans SBCL. Donc cette option n'a de sens que sur SBCL. La compression est activée par défaut.
–remove-docstrings
Cette option supprime toutes les chaînes de documentation de tous les symboles dans toute l'image lisp.
–delete-package PKG
Cette option peut être spécifiée plusieurs fois. Elle désinternes les symboles dans PACKAGE, appelle makeunbound et fmakeunbound sur chaque symbole et supprime le paquet. Les noms de paquets sont automatiquement convertis en majuscules.
–delete-all-packages
Cette option applique –delete-package PKG sur tous les paquets, sauf certains paquets mis en liste noire (keyword, roswell, ROS.SCRIPT.DUMP, et le paquet du symbole de la fonction principale).
–delete-packages-except PACKAGE
Cette option peut être spécifiée plusieurs fois. Elle est identique à –delete-all-packages sauf qu'elle ajoute PACKAGE à la liste noire. Les noms de paquets sont automatiquement convertis en majuscules.
–destroy-packages-sbcl
Ceci est une option spécifique à sbcl qui est encore plus agressive que les méthodes ci-dessus (> 10 Mo de réduction). Elle détruit le système de paquets en modifiant les tables internes des paquets, en nettoyant les caches pour package-use-list etc. La liste noire est partagée entre –delete-all-packages et –destroy-packages-sbcl. Cependant, cette méthode n'appelle pas fmakunbound/makunbound, donc combiner les deux méthodes peut entraîner une réduction plus agressive de la taille de l'image. Compte tenu de la nature de cette option, il est souhaitable de la spécifier comme dernière méthode (c'est-à-dire la plus à droite).
–purify, –no-purify
Ceci est commun à CCL, SBCL, CMUCL. Déplace tous les objets dans l'espace statique où le GC ne scanne pas, pour la performance ultérieure du GC. La purification est activée par défaut.
–impurify, –no-impurify
Ceci est une option spécifique à CCL (activée par défaut). Elle déplace tous les objets dans l'espace dynamique avant de sauvegarder l'image. Cela permet aux objets de l'espace statique d'être récupérés par le GC. Lorsque la purification est activée, elle désactive la purification de tous les objets avant d'exécuter le GC de purification.
–delete-docstrings
Ceci supprime les informations de débogage des fonctions (utilisées pour afficher la frame de pile etc), ainsi que les emplacements sources et les informations de dépréciation de divers symboles. Uniquement SBCL. Cette option a un impact important (+ 10 Mo de réduction).
–delete-macro-definitions, –delete-compiler-macro-definitions
Ceci supprime toutes les définitions de macros et de macro-compilateurs, en supposant qu'aucune compilation/interprétation de code à l'exécution ne sera effectuée. Cette option devrait être portable sur différentes implémentations. Elle réduit d'environ 2 Mo sur SBCL.
–delete-compiler-information-sbcl
Ceci est une option spécifique à SBCL qui est plus agressive que les méthodes ci-dessus (environ 4 Mo de réduction). En plus des définitions de macros et de macro-compilateurs, elle détruit les systèmes de compilateurs internes de SBCL en supprimant également les informations d'inlining, le transformateur IR1 et IR2 (VOP).
