getrlimit(2) Manuel des appels système getrlimit(2)

NOM

getrlimit, setrlimit, prlimit - obtenir/définir des limites de ressources

BIBLIOTHÈQUE

Bibliothèque C standard (libc, -lc)

SYNTAXE

#include <sys/resource.h>
int getrlimit(int resource, struct rlimit *rlim);
int setrlimit(int resource, const struct rlimit *rlim);
int prlimit(pid_t pid, int resource,
            const struct rlimit *_Nullable new_limit,
            struct rlimit *_Nullable old_limit);
struct rlimit {
    rlim_t  rlim_cur;  /* Limite douce */
    rlim_t  rlim_max;  /* Limite dure (plancher pour rlim_cur) */
};
typedef /* ... */  rlim_t;  /* Type entier non signé */

DESCRIPTION

Les appels système getrlimit() et setrlimit() obtiennent et définissent des limites de ressources. Chaque ressource a une limite douce et une limite dure associées, telles que définies par la structure rlimit.

La limite douce est la valeur que le noyau applique pour la ressource correspondante. La limite dure agit comme un plafond pour la limite douce : un processus non privilégié ne peut définir que sa limite douce à une valeur comprise entre 0 et la limite dure, et abaisser (de manière irréversible) sa limite dure. Un processus privilégié (sous Linux : celui possédant la capacité CAP_SYS_RESOURCE dans l'espace de noms utilisateur initial) peut apporter des modifications arbitraires à l'une ou l'autre des valeurs de limite.

La valeur RLIM_INFINITY signifie qu'il n'y a pas de limite sur une ressource (à la fois dans la structure renvoyée par getrlimit() et dans la structure passée à setrlimit()).

L'argument resource doit être l'une des valeurs suivantes :

RLIMIT_AS
Ceci est la taille maximale de la mémoire virtuelle du processus (espace d'adressage). La limite est spécifiée en octets et est arrondie à la taille de page système la plus proche. Cette limite affecte les appels à brk(2), mmap(2), et mremap(2), qui échouent avec l'erreur ENOMEM en cas de dépassement de cette limite. De plus, l'expansion automatique de la pile échoue (et génère un SIGSEGV qui tue le processus si aucune pile alternative n'a été rendue disponible via sigaltstack(2)). Étant donné que la valeur est un long, sur les machines avec un long de 32 bits, soit cette limite est au maximum de 2 Gio, soit cette ressource est illimitée.
RLIMIT_CORE
Ceci est la taille maximale d'un fichier de core dump (voir core(5)) en octets que le processus peut produire. Lorsque 0, aucun fichier de core dump n'est créé. Lorsque non nul, les dumps plus grands sont tronqués à cette taille.
RLIMIT_CPU
Ceci est une limite, en secondes, sur la quantité de temps CPU que le processus peut consommer. Lorsque le processus atteint la limite douce, il reçoit un signal SIGXCPU. L'action par défaut pour ce signal est de terminer le processus. Cependant, le signal peut être intercepté et le gestionnaire peut renvoyer le contrôle au programme principal. Si le processus continue à consommer du temps CPU, il recevra SIGXCPU une fois par seconde jusqu'à ce que la limite dure soit atteinte, moment où il reçoit SIGKILL. (Ce dernier point décrit le comportement sous Linux. Les implémentations varient quant à la manière dont elles traitent les processus qui continuent à consommer du temps CPU après avoir atteint la limite douce. Les applications portables qui doivent intercepter ce signal devraient effectuer une terminaison ordonnée lors de la première réception de SIGXCPU.)
RLIMIT_DATA
Ceci est la taille maximale du segment de données du processus (données initialisées, données non initialisées et tas). La limite est spécifiée en octets et est arrondie à la taille de page système la plus proche. Cette limite affecte les appels à brk(2), sbrk(2), et (depuis Linux 4.7) mmap(2), qui échouent avec l'erreur ENOMEM en cas de dépassement de la limite douce de cette ressource.
RLIMIT_FSIZE
Ceci est la taille maximale en octets des fichiers que le processus peut créer. Les tentatives d'extension d'un fichier au-delà de cette limite entraînent la délivrance d'un signal SIGXFSZ. Par défaut, ce signal termine un processus, mais un processus peut intercepter ce signal à la place, auquel cas l'appel système pertinent (par exemple, write(2), truncate(2)) échoue avec l'erreur EFBIG.
RLIMIT_LOCKS (Linux 2.4.0 à Linux 2.4.24)
Ceci est une limite sur le nombre combiné de verrous flock(2) et de baux fcntl(2) que ce processus peut établir.
RLIMIT_MEMLOCK
Ceci est le nombre maximum d'octets de mémoire qui peuvent être verrouillés en RAM. Cette limite est arrondie au multiple le plus proche de la taille de page système. Cette limite affecte mlock(2), mlockall(2), et l'opération mmap(2) MAP_LOCKED. Depuis Linux 2.6.9, elle affecte également l'opération shmctl(2) SHM_LOCK, où elle définit un maximum sur les octets totaux dans les segments de mémoire partagée (voir shmget(2)) qui peuvent être verrouillés par l'ID utilisateur réel du processus appelant. Les verrous shmctl(2) SHM_LOCK sont comptabilisés séparément des verrous mémoire par processus établis par mlock(2), mlockall(2), et l'opération MAP_LOCKED de mmap(2) ; un processus peut verrouiller des octets jusqu'à cette limite dans chacune de ces deux catégories.
Avant Linux 2.6.9, cette limite contrôlait la quantité de mémoire qui pouvait être verrouillée par un processus privilégié. Depuis Linux 2.6.9, aucune limite n'est imposée sur la quantité de mémoire qu'un processus privilégié peut verrouiller, et cette limite régit plutôt la quantité de mémoire qu'un processus non privilégié peut verrouiller.
RLIMIT_MSGQUEUE (depuis Linux 2.6.8)
Ceci est une limite sur le nombre d'octets qui peuvent être alloués pour les files d'attente de messages POSIX pour l'ID utilisateur réel du processus appelant. Cette limite est appliquée pour mq_open(3). Chaque file d'attente de messages que l'utilisateur crée est comptabilisée (jusqu'à sa suppression) contre cette limite selon la formule :
Depuis Linux 3.5 :

octets = attr.mq_maxmsg * sizeof(struct msg_msg) +
        MIN(attr.mq_maxmsg, MQ_PRIO_MAX) *
              sizeof(struct posix_msg_tree_node)+
                        /* Pour la surcharge */
        attr.mq_maxmsg * attr.mq_msgsize;
                        /* Pour les données des messages */

Linux 3.4 et versions antérieures :

octets = attr.mq_maxmsg * sizeof(struct msg_msg *) +
                        /* Pour la surcharge */
        attr.mq_maxmsg * attr.mq_msgsize;
                        /* Pour les données des messages */

où attr est la structure mq_attr spécifiée comme quatrième argument à mq_open(3), et les structures msg_msg et posix_msg_tree_node sont des structures internes au noyau.
La partie "surcharge" de la formule prend en compte les octets de surcharge requis par l'implémentation et garantit que l'utilisateur ne peut pas créer un nombre illimité de messages de longueur nulle (de tels messages consomment néanmoins une partie de la mémoire système pour la surcharge de gestion).
RLIMIT_NICE (depuis Linux 2.6.12, mais voir BUGS ci-dessous)
Ceci spécifie un plafond auquel la valeur de nice du processus peut être augmentée à l'aide de setpriority(2) ou nice(2). Le plafond réel pour la valeur de nice est calculé comme 20 - rlim_cur. L'utile r

Par exemple, RLIM_INFINITY est généralement équivalent à -1. Pour plus de détails sur la valeur agréable, voir sched(7).
RLIMIT_NOFILE
Ceci spécifie une valeur supérieure d'une unité au descripteur de fichier maximum pouvant être ouvert par ce processus. Les tentatives (open(2), pipe(2), dup(2), etc.) de dépasser cette limite entraînent l'erreur EMFILE. (Historiquement, cette limite était nommée RLIMIT_OFILE sur BSD.)
Depuis Linux 4.5, cette limite définit également le nombre maximum de descripteurs de fichiers qu'un processus non privilégié (sans la capacité CAP_SYS_RESOURCE) peut avoir « en transit » vers d'autres processus, en étant passé via des sockets de domaine UNIX. Cette limite s'applique à l'appel système sendmsg(2). Pour plus de détails, voir unix(7).
RLIMIT_NPROC
Ceci est une limite sur le nombre de processus (ou, plus précisément sous Linux, de threads) existants pour l'ID utilisateur réel du processus appelant. Tant que le nombre actuel de processus appartenant à l'ID utilisateur réel de ce processus est supérieur ou égal à cette limite, fork(2) échoue avec l'erreur EAGAIN.
La limite RLIMIT_NPROC n'est pas appliquée aux processus qui ont soit la capacité CAP_SYS_ADMIN, soit la capacité CAP_SYS_RESOURCE, ou qui s'exécutent avec l'ID utilisateur réel 0.
RLIMIT_RSS
Ceci est une limite (en octets) sur l'ensemble résident du processus (le nombre de pages virtuelles résidentes en RAM). Cette limite n'a d'effet que sous Linux 2.4.x, x < 30, et affecte uniquement les appels à madvise(2) spécifiant MADV_WILLNEED.
RLIMIT_RTPRIO (depuis Linux 2.6.12, mais voir BUGS)
Ceci spécifie un plafond sur la priorité temps réel qui peut être définie pour ce processus en utilisant sched_setscheduler(2) et sched_setparam(2).
Pour plus de détails sur les politiques de planification temps réel, voir sched(7)
RLIMIT_RTTIME (depuis Linux 2.6.25)
Ceci est une limite (en microsecondes) sur la quantité de temps CPU qu'un processus planifié selon une politique temps réel peut consommer sans effectuer d'appel système bloquant. Aux fins de cette limite, chaque fois qu'un processus effectue un appel système bloquant, le décompte de son temps CPU consommé est remis à zéro. Le décompte du temps CPU n'est pas réinitialisé si le processus continue d'essayer d'utiliser le CPU mais est préempté, si sa tranche de temps expire, ou s'il appelle sched_yield(2).
Lorsqu'il atteint la limite douce, le processus reçoit un signal SIGXCPU. Si le processus intercepte ou ignore ce signal et continue de consommer du temps CPU, alors SIGXCPU sera généré une fois par seconde jusqu'à ce que la limite dure soit atteinte, auquel cas le processus reçoit un signal SIGKILL.
L'utilisation prévue de cette limite est d'empêcher un processus temps réel déréglé de bloquer le système.
Pour plus de détails sur les politiques de planification temps réel, voir sched(7)
RLIMIT_SIGPENDING (depuis Linux 2.6.8)
Ceci est une limite sur le nombre de signaux qui peuvent être mis en file d'attente pour l'ID utilisateur réel du processus appelant. Les signaux standard et temps réel sont comptés aux fins de vérification de cette limite. Cependant, la limite n'est appliquée qu'à sigqueue(3); il est toujours possible d'utiliser kill(2) pour mettre en file d'attente une instance de l'un des signaux qui ne sont pas déjà mis en file d'attente pour le processus.
RLIMIT_STACK
Ceci est la taille maximale de la pile du processus, en octets. Lors de l'atteinte de cette limite, un signal SIGSEGV est généré. Pour gérer ce signal, un processus doit utiliser une pile de signaux alternative (sigaltstack(2)).
Depuis Linux 2.6.23, cette limite détermine également l'espace utilisé pour les arguments de ligne de commande et les variables d'environnement du processus ; pour plus de détails, voir execve(2).

prlimit()

L'appel système spécifique à Linux prlimit() combine et étend les fonctionnalités de setrlimit() et getrlimit(). Il peut être utilisé pour définir et obtenir les limites de ressources d'un processus arbitraire.

L'argument resource a la même signification que pour setrlimit() et getrlimit().

Si l'argument new_limit n'est pas NULL, alors la structure rlimit à laquelle il pointe est utilisée pour définir de nouvelles valeurs pour les limites douces et dures pour resource. Si l'argument old_limit n'est pas NULL, alors un appel réussi à prlimit() place les limites douces et dures précédentes pour resource dans la structure rlimit pointée par old_limit.

L'argument pid spécifie l'ID du processus sur lequel l'appel doit opérer. Si pid est 0, alors l'appel s'applique au processus appelant. Pour définir ou obtenir les ressources d'un processus autre que lui-même, l'appelant doit avoir la capacité CAP_SYS_RESOURCE dans l'espace utilisateur du processus dont les limites de ressources sont modifiées, ou les IDs utilisateur réels, effectifs et de sauvegarde du processus cible doivent correspondre à l'ID utilisateur réel de l'appelant *et* les IDs groupe réels, effectifs et de sauvegarde du processus cible doivent correspondre à l'ID groupe réel de l'appelant.

VALEUR DE RETOUR

En cas de succès, ces appels système retournent 0. En cas d'erreur, -1 est retourné, et errno est défini pour indiquer l'erreur.

ERREURS

EFAULT
Un argument pointeur pointe vers un emplacement en dehors de l'espace d'adressage accessible.
EINVAL
La valeur spécifiée dans resource n'est pas valide ; ou, pour setrlimit() ou prlimit() : rlim->rlim_cur était supérieur à rlim->rlim_max.
EPERM
Un processus non privilégié a tenté d'augmenter la limite dure ; la capacité CAP_SYS_RESOURCE est requise pour ce faire.
EPERM
L'appelant a tenté d'augmenter la limite dure RLIMIT_NOFILE au-delà de la valeur maximale définie par /proc/sys/fs/nr_open (voir proc(5))
EPERM
(prlimit()) Le processus appelant n'avait pas la permission de définir les limites pour le processus spécifié par pid.
ESRCH
Impossible de trouver un processus avec l'ID spécifié dans pid.

NOTES

Un processus enfant créé via fork(2) hérite des limites de ressources de son parent. Les limites de ressources sont préservées lors de execve(2).

Les limites de ressources sont des attributs par processus qui sont partagés par tous les threads d'un processus.

Baisser la limite douce d'une ressource en dessous de la consommation actuelle de cette ressource par le processus réussira (mais empêchera le processus d'augmenter davantage sa consommation de la ressource).

On peut définir les limites de ressources du shell en utilisant la commande intégrée ulimit (limit dans csh(1)). Les limites de ressources du shell sont héritées par les processus qu'il crée pour exécuter des commandes.

Depuis Linux 2.6.24, les limites de ressources de n'importe quel processus peuvent être inspectées via /proc/pid/limits ; voir proc(5).

Les anciens systèmes fournissaient une fonction vlimit() avec un but similaire à setrlimit(). Pour des raisons de compatibilité ascendante, glibc offre également vlimit(). Toutes les nouvelles applications doivent être écrites en utilisant setrlimit().

Différences ABI entre la bibliothèque C et le noyau

Depuis glibc 2.13, les fonctions d'encapsulation getrlimit() et setrlimit() de glibc n'invoquent plus les appels système correspondants, mais utilisent plutôt prlimit(), pour les raisons décrites dans BUGS.

Le nom de la fonction d'encapsulation de glibc est prlimit() ; l'appel système sous-jacent est prlimit64().

BUGS

Dans les anciens noyaux Linux, les signaux SIGXCPU et SIGKILL livrés lorsqu'un processus rencontrait les limites douces et dures de RLIMIT_CPU étaient livrés une (seconde CPU) plus tard que prévu. Ceci a été corrigé dans Linux 2.6.8.

Dans les noyaux Linux 2.6.x avant Linux 2.6.17, une limite RLIMIT_CPU de 0 est mal interprétée comme "pas de limite" (comme RLIM_INFINITY). Depuis Linux 2.6.17, définir une limite de 0 a un effet, mais est en fait interprété comme une limite de 1 seconde.

Un bug du noyau fait que RLIMIT_RTPRIO ne fonctionne pas dans Linux 2.6.12 ; le problème est corrigé dans Linux 2.6.13.

Dans Linux 2.6.12, il y avait une discordance d'un unité entre les plages de priorité renvoyées par getpriority(2) et RLIMIT_NICE. Cela avait pour effet que le plafond réel pour la valeur de "nice" était calculé comme 19 - rlim_cur. Ceci a été corrigé dans Linux 2.6.13.

Depuis Linux 2.6.12, si un processus atteint sa limite douce de RLIMIT_CPU et a un gestionnaire installé pour SIGXCPU, alors, en plus d'invoquer le gestionnaire de signal, le noyau augmente la limite douce d'une seconde. Ce comportement se répète si le processus continue de consommer du temps CPU, jusqu'à ce que la limite dure soit atteinte, moment auquel le processus est tué. D'autres implémentations ne modifient pas la limite douce de RLIMIT_CPU de cette manière, et le comportement de Linux n'est probablement pas conforme aux normes ; les applications portables devraient éviter de s'appuyer sur ce comportement spécifique à Linux. La limite spécifique à Linux RLIMIT_RTTIME présente le même comportement lorsque la limite douce est rencontrée.

Les noyaux avant Linux 2.4.22 ne diagnostiquaient pas l'erreur EINVAL pour setrlimit() lorsque rlim->rlim_cur était supérieur à rlim->rlim_max.

Linux ne renvoie pas d'erreur lorsqu'une tentative de définition de RLIMIT_CPU a échoué, pour des raisons de compatibilité.

Représentation des valeurs de limites de ressources "grandes" sur les plates-formes 32 bits

Les fonctions d'encapsulation getrlimit() et setrlimit() de glibc utilisent un type de données rlim_t de 64 bits, même sur les plates-formes 32 bits. Cependant, le type de données rlim_t utilisé dans les appels système getrlimit() et setrlimit() est un unsigned long (32 bits). De plus, sous Linux, le noyau représente les limites de ressources sur les plates-formes 32 bits sous forme d'unsigned long. Cependant, un type de données 32 bits n'est pas suffisamment large. La limite la plus pertinente ici est RLIMIT_FSIZE, qui spécifie la taille maximale à laquelle un fichier peut croître : pour être utile, cette limite doit être représentée à l'aide d'un type aussi large que le type utilisé pour représenter les décalages de fichiers — c'est-à-dire aussi large qu'un off_t de 64 bits (en supposant un programme compilé avec _FILE_OFFSET_BITS=64).

Pour contourner cette limitation du noyau, si un programme tentait de définir une limite de ressource à une valeur supérieure à celle qui peut être représentée dans un unsigned long de 32 bits, alors la fonction d'encapsulation setrlimit() de glibc convertissait silencieusement la valeur de la limite en RLIM_INFINITY. Autrement dit, le réglage de limite de ressource demandé était silencieusement ignoré.

Depuis glibc 2.13, glibc contourne les limitations des appels système getrlimit() et setrlimit() en implémentant setrlimit() et getrlimit() comme des fonctions d'encapsulation qui appellent prlimit().

EXEMPLES

Le programme ci-dessous démontre l'utilisation de prlimit().

#define _GNU_SOURCE
#define _FILE_OFFSET_BITS 64
#include <err.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
#include <sys/resource.h>
#include <time.h>
int
main(int argc, char *argv[])
{
    pid_t          pid;
    struct rlimit  old, new;
    struct rlimit  *newp;
    if (!(argc == 2 || argc == 4)) {
        fprintf(stderr, "Usage: %s <pid> [<limite-douce-nouvelle> "
                "<limite-dure-nouvelle>]\n", argv[0]);
        exit(EXIT_FAILURE);
    }
    pid = atoi(argv[1]);        /* PID du processus cible */
    newp = NULL;
    if (argc == 4) {
        new.rlim_cur = atoi(argv[2]);
        new.rlim_max = atoi(argv[3]);
        newp = &new;
    }
    /* Définir la limite de temps CPU du processus cible ; récupérer et afficher
       la limite précédente */
    if (prlimit(pid, RLIMIT_CPU, newp, &old) == -1)
        err(EXIT_FAILURE, "prlimit-1");
    printf("Limites précédentes : douce=%jd; dure=%jd\n",
           (intmax_t) old.rlim_cur, (intmax_t) old.rlim_max);
    /* Récupérer et afficher la nouvelle limite de temps CPU */
    if (prlimit(pid, RLIMIT_CPU, NULL, &old) == -1)
        err(EXIT_FAILURE, "prlimit-2");
    printf("Nouvelles limites : douce=%jd; dure=%jd\n",
           (intmax_t) old.rlim_cur, (intmax_t) old.rlim_max);
    exit(EXIT_SUCCESS);
}
