NOM

rabbitmqctl — outil de gestion des nœuds RabbitMQ

SYNTAXE

rabbitmqctl [-q] [-s] [-l] [-n nœud] [-t délai] commande [options_commande]

DESCRIPTION

RabbitMQ est un courtier de messagerie open-source multi-protocoles.

rabbitmqctl est l'outil principal en ligne de commande pour gérer un nœud serveur RabbitMQ, avec rabbitmq-diagnostics , rabbitmq-upgrade , et d'autres.

Il effectue toutes les actions en se connectant au nœud RabbitMQ cible sur un port de communication dédié pour les outils CLI et s'authentifie à l'aide d'un secret partagé (connu sous le nom de fichier cookie).

Les informations de diagnostic sont affichées si la connexion a échoué, si le nœud cible ne fonctionnait pas, ou si rabbitmqctl n'a pas pu s'authentifier avec succès auprès du nœud cible.

Pour en savoir plus, consultez le guide des outils CLI RabbitMQ

OPTIONS

-n nœud
Le nœud par défaut est "rabbit@nom-hôte-cible", où nom-hôte-cible est l'hôte local. Sur un hôte nommé "myserver.example.com", le nom du nœud sera généralement "rabbit@myserver" (sauf si RABBITMQ_NODENAME a été remplacé, auquel cas vous devrez utiliser
--longnames
). La sortie de "hostname -s" est généralement le nom d'hôte correct à utiliser après le signe "@". Voir rabbitmq-server(8) pour les détails de configuration d'un nœud RabbitMQ.
-q, --quiet
Mode de sortie silencieux sélectionné. Les messages d'information sont réduits en mode silencieux.
-s, --silent
Mode de sortie muet sélectionné. Les messages d'information sont réduits et les en-têtes de tableau sont supprimés en mode muet.
--no-table-headers
Ne pas afficher d'en-têtes pour les données tabulaires.
--dry-run
Ne pas exécuter la commande. Afficher uniquement les messages d'information.
-t délai, --timeout délai
Délai d'opération en secondes. Toutes les commandes ne prennent pas en charge les délais. La valeur par défaut est infinity.
-l, --longnames
Doit être spécifié lorsque le cluster est configuré pour utiliser des noms de nœuds longs (FQDN). Pour en savoir plus, consultez le guide de clustering RabbitMQ
--erlang-cookie cookie
Secret partagé à utiliser pour s'authentifier auprès du nœud cible. Préférez utiliser un fichier local ou la variable d'environnement RABBITMQ_ERLANG_COOKIE plutôt que de spécifier cette option dans la ligne de commande. Pour en savoir plus, consultez le guide des outils CLI RabbitMQ

Nœuds

await_startup

Attend que l'application RabbitMQ démarre sur le nœud cible

Par exemple, pour attendre le démarrage de l'application RabbitMQ :

rabbitmqctl await_startup
reset

Remet un nœud RabbitMQ dans son état vierge.

Retire le nœud de tout cluster auquel il appartient, supprime toutes les données de la base de données de gestion, telles que les utilisateurs et les vhosts configurés, et supprime tous les messages persistants.

Pour que reset et force_reset réussissent, l'application RabbitMQ doit avoir été arrêtée, par exemple avec stop_app.

Par exemple, pour réinitialiser le nœud RabbitMQ :

rabbitmqctl reset
rotate_logs

Demande au nœud RabbitMQ d'effectuer une rotation interne des journaux.

La rotation des journaux est effectuée conformément aux paramètres de journalisation spécifiés dans le fichier de configuration. L'opération de rotation est asynchrone, il n'y a aucune garantie qu'elle se termine avant que cette commande ne retourne.

Notez qu'il n'est pas nécessaire d'appeler cette commande en cas de rotation externe des journaux (par exemple, depuis logrotate(8)).

Par exemple, pour initialiser la rotation des journaux :

rabbitmqctl rotate_logs
shutdown

Arrête le nœud, à la fois RabbitMQ et son runtime. La commande est bloquante et retournera après la sortie du processus runtime. Si RabbitMQ échoue à s'arrêter, il retournera un code de sortie non nul. Cette commande infère le PID du système d'exploitation du nœud cible et ne peut donc être utilisée que pour arrêter les nœuds s'exécutant sur le même hôte (ou plus largement, dans le même système d'exploitation, par exemple dans la même VM ou conteneur)

Contrairement à la commande stop, la commande shutdown :

  • ne nécessite pas de pid_file pour attendre la fin du processus runtime
  • retourne un code de sortie non nul si le nœud RabbitMQ n'est pas en cours d'exécution

Par exemple, ceci arrêtera un nœud RabbitMQ local s'exécutant avec le nom de nœud par défaut :

rabbitmqctl shutdown
start_app

Démarre l'application RabbitMQ.

Cette commande est généralement exécutée après avoir effectué d'autres actions de gestion qui nécessitent l'arrêt de l'application RabbitMQ, par exemple reset.

Par exemple, pour demander au nœud RabbitMQ de démarrer l'application RabbitMQ :

rabbitmqctl start_app
stop [pid_file]

Arrête le nœud Erlang sur lequel RabbitMQ s'exécute. Pour redémarrer le nœud, suivez les instructions pour "Exécution du serveur" dans le guide d'installation.

Si un pid_file est spécifié, attend également la terminaison du processus qui y est spécifié.

Gestion de nœud

reset

Retourne un nœud RabbitMQ à son état initial. Cela supprime la base de données de gestion du nœud, y compris toutes les files d'attente, échanges, liaisons, utilisateurs et permissions, puis réinitialise le nom du cluster.

Cette commande est typiquement utilisée lorsqu'un nœud est retiré d'un cluster, ou lorsqu'un nœud est réinitialisé pour des raisons de dépannage. La base de données Mnesia ne sera pas supprimée, mais sera mise à jour pour refléter le fait qu'elle s'exécute en tant que nœud unique.

Pour que cette commande réussisse, l'application RabbitMQ doit être arrêtée, par exemple avec stop_app. Voir la description de la commande wait pour les détails sur ce fichier.

Par exemple, pour demander au nœud RabbitMQ de se réinitialiser :

rabbitmqctl reset
shutdown

Arrête le nœud RabbitMQ.

Par exemple, pour arrêter le nœud RabbitMQ :

rabbitmqctl shutdown
stop

Arrête le nœud RabbitMQ et l'exécution de l'Erlang VM.

Par exemple, pour arrêter le nœud RabbitMQ :

rabbitmqctl stop
stop_app

Arrête l'application RabbitMQ, laissant le runtime (VM Erlang) en cours d'exécution.

Cette commande est généralement exécutée avant d'effectuer d'autres actions de gestion qui nécessitent l'arrêt de l'application RabbitMQ, par exemple reset.

Par exemple, pour demander au nœud RabbitMQ d'arrêter l'application RabbitMQ :

rabbitmqctl stop_app
wait pid_file, wait --pid pid

Attend que l'application RabbitMQ démarre.

Cette commande attendra que l'application RabbitMQ démarre sur le nœud. Elle attendra que le fichier pid soit créé si pidfile est spécifié, puis qu'un processus avec un pid spécifié dans le fichier pid ou l'argument --pid, puis que l'application RabbitMQ démarre dans ce processus. Elle échouera si le processus se termine sans démarrer l'application RabbitMQ.

Si le fichier pid spécifié n'est pas créé ou si le nœud erlang n'est pas démarré dans le délai imparti par --timeout, la commande échouera. Le délai d'attente par défaut est de 10 secondes.

Un fichier pid approprié est créé par le script rabbitmq-server(8). Par défaut, il est situé dans le répertoire Mnesia. Modifiez la variable d'environnement RABBITMQ_PID_FILE pour changer l'emplacement.

Par exemple, cette commande retournera lorsque le nœud RabbitMQ aura démarré :

rabbitmqctl wait /var/run/rabbitmq/pid

Gestion de cluster

await_online_nodes count

Attend que count nœuds rejoignent le cluster

Par exemple, pour attendre le démarrage de deux nœuds RabbitMQ :

rabbitmqctl await_online_nodes 2
change_cluster_node_type type

Change le type du nœud du cluster.

Le type doit être l'un des suivants :

  • disc
  • ram

Le nœud doit être arrêté pour que cette opération réussisse, et lors de la transformation d'un nœud en nœud RAM, le nœud ne doit pas être le seul nœud disque du cluster.

Par exemple, cette commande transformera un nœud RAM en nœud disque :

rabbitmqctl change_cluster_node_type disc
cluster_status

Affiche tous les nœuds du cluster groupés par type de nœud, ainsi que les nœuds actuellement en cours d'exécution.

Par exemple, cette commande affiche les nœuds du cluster :

rabbitmqctl cluster_status
force_boot

Garantit que le nœud démarrera la prochaine fois, même s'il n'était pas le dernier à s'arrêter.

Normalement, lorsque vous arrêtez complètement un cluster RabbitMQ, le premier nœud que vous redémarrez devrait être celui qui s'est arrêté en dernier, car il a peut-être vu des choses que les autres nœuds n'ont pas vues. Mais parfois, ce n'est pas possible : par exemple, si tout le cluster perd l'alimentation, tous les nœuds peuvent penser qu'ils n'étaient pas les derniers à s'arrêter.

Dans un tel cas, vous pouvez appeler force_boot pendant que le nœud est arrêté. Cela indiquera au nœud de démarrer inconditionnellement la prochaine fois que vous le lui demanderez. Toutes les modifications apportées au cluster après l'arrêt de ce nœud seront perdues.

Si le dernier nœud à s'arrêter est perdu définitivement, vous devriez utiliser forget_cluster_node --offline au lieu de cette commande, car cela garantira que les files d'attente miroir dont la réplique principale se trouvait sur le nœud perdu seront promues.

Par exemple, ceci forcera le nœud à ne pas attendre les autres nœuds la prochaine fois qu'il sera démarré :

rabbitmqctl force_boot
force_reset (obsolète)

Force un nœud RabbitMQ à son état initial.

La commande force_reset diffère de reset en ce qu'elle réinitialise le nœud inconditionnellement, indépendamment de l'état actuel de la base de données de gestion et de la configuration du cluster. Elle ne doit être utilisée qu'en dernier recours si la base de données ou la configuration du cluster a été corrompue.

La commande force_reset est obsolète. Elle reste disponible lorsque le magasin de métadonnées Mnesia est utilisé. Elle n'est pas prise en charge avec le magasin de métadonnées Khepri.

Pour que reset et force_reset réussissent, l'application RabbitMQ doit avoir été arrêtée, par exemple avec stop_app.

Par exemple, pour réinitialiser le nœud RabbitMQ :

rabbitmqctl force_reset
forget_cluster_node [--offline]
--offline
Permet la suppression d'un nœud à partir d'un nœud hors ligne. Ceci n'est utile que dans la situation où tous les nœuds sont hors ligne et que le dernier nœud à s'arrêter ne peut pas être mis en ligne, empêchant ainsi le démarrage du cluster entier. Il ne doit pas être utilisé dans d'autres circonstances car il peut entraîner des incohérences.

Supprime un nœud de cluster à distance. Le nœud qui est supprimé doit être hors ligne, tandis que le nœud à partir duquel on supprime doit être en ligne, sauf lors de l'utilisation du drapeau --offline.

Lors de l'utilisation du drapeau --offline, rabbitmqctl n'essaiera pas de se connecter à un nœud normalement ; au lieu de cela, il deviendra temporairement le nœud afin d'effectuer le changement. Ceci est utile si le nœud ne peut pas être démarré normalement. Dans ce cas, le nœud deviendra la source canonique des métadonnées du cluster (par exemple, quelles files d'attente existent), même s'il ne l'était pas auparavant. Par conséquent, vous devriez utiliser cette commande sur le dernier nœud à s'arrêter si possible.

Par exemple, cette commande supprimera le nœud "rabbit@stringer" du nœud "hare@mcnulty" :

rabbitmqctl -n hare@mcnulty forget_cluster_node rabbit@stringer
join_cluster seed-node [--ram]
seed-node
Membre existant du cluster (nœud graine) avec lequel se mettre en cluster.
--ram
Si fourni, le nœud rejoindra le cluster en tant que nœud RAM. L'utilisation de nœuds RAM est déconseillée. Utilisez-les uniquement si vous comprenez pourquoi vous avez besoin de les utiliser.

Demande au nœud de devenir membre du cluster dont fait partie le nœud spécifié. Avant la mise en cluster, le nœud est réinitialisé, soyez donc prudent lorsque vous utilisez cette commande. Pour que cette commande réussisse, l'application RabbitMQ doit avoir été arrêtée, par exemple avec stop_app.

Les nœuds de cluster peuvent être de deux types : disque ou RAM. Les nœuds disque répliquent les données en RAM et sur disque, offrant ainsi une redondance en cas de défaillance du nœud et de récupération d'événements globaux tels qu'une panne de courant sur tous les nœuds. Les nœuds RAM ne répliquent les données qu'en RAM (sauf pour le contenu des files d'attente, qui peuvent résider sur disque si la file d'attente est persistante ou trop volumineuse pour tenir en mémoire) et sont principalement utilisés pour la scalabilité. Les nœuds RAM sont plus performants uniquement lors de la gestion des ressources (par exemple, ajout/suppression de files d'attente, d'échanges ou de liaisons). Un cluster doit toujours avoir au moins un nœud disque et devrait généralement en avoir plus d'un.

Le nœud sera un nœud disque par défaut. Si vous souhaitez créer un nœud RAM, fournissez le drapeau --ram.

Après avoir exécuté la commande join_cluster, chaque fois que l'application RabbitMQ sera démarrée sur le nœud actuel, elle tentera de se connecter aux nœuds qui étaient dans le cluster lorsque le nœud s'est arrêté.

Pour quitter un cluster, reset le nœud. Vous pouvez également supprimer des nœuds à distance avec la commande forget_cluster_node.

Par exemple, cette commande demande au nœud RabbitMQ de rejoindre le cluster dont "hare@elena" fait partie, en tant que nœud ram :

rabbitmqctl join_cluster hare@elena --ram

Pour en savoir plus, consultez le guide de clustering RabbitMQ.

Gestion des utilisateurs

Notez que toutes les commandes de gestion d'utilisateurs de rabbitmqctl ne peuvent gérer que les utilisateurs de la base de données interne de RabbitMQ. Les utilisateurs d'autres backends d'authentification alternatifs tels que LDAP ne peuvent pas être inspectés

Gestion des utilisateurs

Les commandes suivantes sont utilisées pour gérer les utilisateurs et leurs autorisations et peuvent être exécutées depuis la ligne de commande utilisant rabbitmqctl.

add_user nom_utilisateur mot_de_passe

Le nom de l'utilisateur à créer.
mot_de_passe
Le mot de passe que l'utilisateur créé utilisera pour se connecter au broker.

Par exemple, cette commande demande au broker RabbitMQ de créer un utilisateur (non administratif) nommé "janeway" avec le mot de passe (initial) "changeit" :

nom_utilisateur
Le nom de l'utilisateur.
mot_de_passe
Le mot de passe de l'utilisateur.

Par exemple, cette commande demande au broker RabbitMQ d'authentifier l'utilisateur nommé "janeway" avec le mot de passe "verifyit" :

rabbitmqctl authenticate_user janeway verifyit

nom_utilisateur
Le nom de l'utilisateur dont le mot de passe doit être modifié.
nouveau_mot_de_passe
Le nouveau mot de passe de l'utilisateur.

Par exemple, cette commande demande au broker RabbitMQ de modifier le mot de passe de l'utilisateur nommé "janeway" en "newpass" :

rabbitmqctl change_password janeway newpass
clear_password nom_utilisateur
nom_utilisateur
Le nom de l'utilisateur dont le mot de passe doit être effacé.

Par exemple, cette commande demande au broker RabbitMQ d'effacer le mot de passe de l'utilisateur nommé "janeway" :

rabbitmqctl clear_password janeway

hash_password texte_clair

Le mot de passe en texte clair à hacher.

delete_user nom_utilisateur
nom_utilisateur
Le nom de l'utilisateur à supprimer.

Par exemple, cette commande demande au broker RabbitMQ de supprimer l'utilisateur nommé "janeway" :

rabbitmqctl delete_user janeway
list_users

Liste les utilisateurs. Chaque ligne de résultat contiendra le nom d'utilisateur suivi d'une liste des tags attribués à cet utilisateur.

Par exemple, cette commande demande au broker RabbitMQ de lister tous les utilisateurs :

rabbitmqctl list_users
set_user_tags nom_utilisateur [tag ...]
nom_utilisateur
Le nom de l'utilisateur dont les tags doivent être définis.
tag
Zéro, un ou plusieurs tags à définir. Tous les tags existants seront supprimés.

Par exemple, cette commande demande au broker RabbitMQ de s'assurer que l'utilisateur nommé "janeway" est un administrateur :

rabbitmqctl set_user_tags janeway administrator

Cela n'a aucun effet lorsque l'utilisateur s'authentifie en utilisant un protocole de messagerie, mais peut être utilisé pour permettre à l'utilisateur de gérer les utilisateurs, les hôtes virtuels et les autorisations lorsque l'utilisateur se connecte par un autre moyen (par exemple avec le plugin de gestion).

Cette commande demande au broker RabbitMQ de supprimer tous les tags de l'utilisateur nommé "janeway" :

rabbitmqctl set_user_tags janeway

Returns a list of virtual hosts. The vhostinfoitem parameter is used to indicate which virtual host information items to include in the results. The column order in the results will match the order of the parameters. vhostinfoitem can take any value from the list that follows:

name
The name of the virtual host with non-ASCII characters escaped as in C.

Whether tracing is enabled for this virtual host.
default_queue_type
Default queue type for this vhost.
description
Virtual host description.
tags
Virtual host tags.
cluster_state
Virtual host state: nodedown, running, stopped.

For example, this command instructs the RabbitMQ broker to list all virtual hosts:

write
A regular expression matching resource names for which the user is granted write permissions.

vhost
The name of the virtual host to which to grant the user access, defaulting to "/".
user
The name of the user the permissions apply to in the target virtual host.
exchange
The name of the topic exchange to which the authorisation check will be applied.

Paramètres d'exécution et Politiques

Certaines fonctionnalités de RabbitMQ (comme le plugin Federation) sont contrôlées par des paramètres. dynamiques et globaux du cluster. Il existe 2 types de paramètres : les paramètres limités à un hôte virtuel et les paramètres globaux. Chaque paramètre limité à un vhost se compose d'un nom de composant, d'un nom et d'une valeur. Le nom du composant et le nom sont des chaînes de caractères, et la valeur est un document JSON valide. Un paramètre global se compose d'un nom et d'une valeur. Le nom est une chaîne de caractères et la valeur est une structure de données Erlang arbitraire. Les paramètres peuvent être définis, effacés et listés. En général, vous devriez vous référer à la documentation de la fonctionnalité en question pour savoir comment définir les paramètres.

Les politiques sont une fonctionnalité basée sur les paramètres d'exécution. Les politiques sont utilisées pour contrôler et modifier le comportement des files d'attente et des échanges à l'échelle du cluster. Les politiques s'appliquent au sein d'un vhost donné et se composent d'un nom, d'un modèle, d'une définition et d'une priorité facultative. Les politiques peuvent être définies, effacées et listées.

    NOM

    rabbitmqctl — utilitaire de gestion pour RabbitMQ

    SYNOPSIS

    rabbitmqctl [-q] [-n NODE] COMMAND [ARG ...]

    DESCRIPTION

    rabbitmqctl est un utilitaire en ligne de commande pour la gestion de nœuds et de clusters RabbitMQ. Il permet de visualiser l'état, de gérer les objets (échanges, files d'attente, etc.), de redémarrer les nœuds et de migrer les données. La plupart des commandes sont destinées à un nœud spécifique, spécifié par l'-n option. Si le nœud n'est pas spécifié, la commande s'exécute sur le nœud par défaut (par exemple, rabbit@localhost).

    Pour les commandes qui modifient le serveur, il est possible de se connecter à des serveurs distants à l'aide des variables d'environnement RABBITMQ_NODENAME, RABBITMQ_USER, RABBITMQ_PASSWORD et RABBITMQ_HOST.

    Par exemple, cette commande supprimera le nœud rabbit@stringer:

    rabbitmqctl decommission_mqtt_node rabbit@stringer

    Plugin STOMP

    list_stomp_connections [stomp_connectioninfoitem]
    Similaire à la commande list_connections, mais renvoie des champs pertinents pour les connexions STOMP. Le paramètre stomp_connectioninfoitem est utilisé pour indiquer quels éléments d'information de connexion inclure dans les résultats. L'ordre des colonnes dans les résultats correspondra à l'ordre des paramètres. stomp_connectioninfoitem peut prendre n'importe quelle valeur de la liste suivante:
    conn_name
    Nom lisible pour la connexion.
    connection
    ID du processus Erlang associé à la connexion directe AMQP interne.
    connection_state
    État de la connexion ; l'un des suivants:
    • running
    • blocking
    • blocked
    session_id
    Identifiant de session du protocole STOMP
    channel
    Canal AMQP associé à la connexion
    version
    Version du protocole STOMP négociée pour la connexion.
    implicit_connect
    Indique si la connexion a été établie en utilisant la connexion implicite (sans trame CONNECT)
    auth_login
    Nom d'utilisateur effectif pour la connexion.
    auth_mechanism
    Mécanisme d'autorisation STOMP. Peut être l'un des suivants:
    • config
    • ssl
    • stomp_headers
    port
    Port du serveur.
    host
    Nom d'hôte du serveur obtenu par DNS inversé, ou son adresse IP si le DNS inversé a échoué ou n'était pas activé.
    peer_port
    Port distant.
    peer_host
    Nom d'hôte distant obtenu par DNS inversé, ou son adresse IP si le DNS inversé a échoué ou n'était pas activé.
    protocol
    Version du protocole STOMP, qui peut être l'une des suivantes:
    • {'STOMP', 0}
    • {'STOMP', 1}
    • {'STOMP', 2}
    channels
    Le nombre de canaux utilisant la connexion.
    channel_max
    Nombre maximum de canaux sur cette connexion.
    frame_max
    Taille maximale de la trame (octets).
    client_properties
    Propriétés informationnelles transmises par le client lors de la connexion
    ssl
    Booléen indiquant si la connexion est sécurisée avec SSL.
    ssl_protocol
    Protocole TLS (par exemple, "tlsv1").
    ssl_key_exchange
    Algorithme d'échange de clés TLS (par exemple, "rsa").
    ssl_cipher
    Algorithme de chiffrement TLS (par exemple, "aes_256_cbc").
    ssl_hash
    Fonction de hachage SSL (par exemple, "sha").
