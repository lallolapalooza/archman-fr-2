NOM

rawshark - Extraire et analyser des données pcap brutes

SYNTAXE

rawshark [ -d <encap:linktype>|<proto:protoname> ] [ -F <champ à afficher> ] [ -l ] [ -m <octets> ] [ -o <paramètre de préférence> ] ... [ -p ] [ -r <tube>|- ] [ -R <filtre de lecture (affichage)> ] [ -s ] [ -S <format de champ> ] [ options ]

rawshark -h|--help

rawshark -v|--version

DESCRIPTION

Rawshark lit un flux de paquets à partir d'un fichier ou d'un tube, et affiche une ligne décrivant sa sortie, suivie d'un ensemble de champs correspondants pour chaque paquet sur la sortie standard.

ENTRÉE

Contrairement à TShark, Rawshark ne fait aucune hypothèse sur l'encapsulation ou l'entrée. Les indicateurs -d et -r doivent être spécifiés pour qu'il fonctionne. Un ou plusieurs indicateurs -F devraient être spécifiés pour que la sortie soit utile. Les autres indicateurs listés ci-dessus suivent les mêmes conventions que Wireshark et TShark.

Rawshark attend par défaut des enregistrements d'entrée avec le format suivant. Il correspond au format de l'en-tête de paquet et des données de paquet dans un fichier au format pcap sur disque.

struct rawshark_rec_s {
    uint32_t ts_sec;      /* Horodatage (secondes) */
    uint32_t ts_usec;     /* Horodatage (microsecondes) */
    uint32_t caplen;      /* Longueur du tampon de paquet */
    uint32_t len;         /* Longueur du paquet "sur le fil" */
    uint8_t data[caplen]; /* Données du paquet */
};

Si -p est fourni, rawshark attend le format suivant. Il correspond à la structure struct pcap_pkthdr et aux données de paquet utilisées dans libpcap ou Npcap. Le format de cette structure dépend de la plateforme ; la taille du champ tv_sec dans la structure struct timeval peut être de 32 bits ou 64 bits. Pour que rawshark fonctionne, la disposition de la structure dans l'entrée doit correspondre à la disposition de la structure dans rawshark. Notez que ce format sera probablement le même que le format précédent si rawshark est un programme 32 bits, mais ne sera pas nécessairement le même si rawshark est un programme 64 bits.

struct rawshark_rec_s {
    struct timeval ts;    /* Horodatage */
    uint32_t caplen;      /* Longueur du tampon de paquet */
    uint32_t len;         /* Longueur du paquet "sur le fil" */
    uint8_t data[caplen]; /* Données du paquet */
};

Dans les deux cas, l'endianness (ordre des octets) de chaque entier doit correspondre au système sur lequel rawshark s'exécute.

SORTIE

Si un ou plusieurs champs sont spécifiés via l'indicateur -F, Rawshark imprime le nombre, le type de champ et le format d'affichage pour chaque champ sur la première ligne en tant que numéro de paquet 0. Pour chaque enregistrement, le numéro de paquet, les champs correspondants et un "1" ou un "0" sont imprimés pour indiquer si le champ correspondait à un filtre d'affichage fourni. Un "-" est utilisé pour signaler la fin d'une description de champ et à la fin de chaque ligne de paquet. Par exemple, les indicateurs -F ip.src -F dns.qry.type pourraient générer la sortie suivante:

0 FT_IPv4 BASE_NONE - 1 FT_UINT16 BASE_HEX -
1 1="1" 0="192.168.77.10" 1 -
2 1="1" 0="192.168.77.250" 1 -
3 0="192.168.77.10" 1 -
4 0="74.125.19.104" 1 -

Notez que les paquets 1 et 2 sont des requêtes DNS, et 3 et 4 ne le sont pas. L'ajout de -R "not dns" imprime toujours chaque ligne, mais il y a une indication que les paquets 1 et 2 n'ont pas passé le filtre :

0 FT_IPv4 BASE_NONE - 1 FT_UINT16 BASE_HEX -
1 1="1" 0="192.168.77.10" 0 -
2 1="1" 0="192.168.77.250" 0 -
3 0="192.168.77.10" 1 -
4 0="74.125.19.104" 1 -

Notez également que la sortie peut être dans n'importe quel ordre, et que plusieurs champs correspondants peuvent être affichés.

OPTIONS

-d <encapsulation>

Spécifie comment les données du paquet doivent être disséquées. L'encapsulation est de la forme type:valeur, où type est l'un des suivants :

encap:nom Les données du paquet doivent être disséquées en utilisant le type de lien de données (DLT) libpcap/Npcap nom, par exemple encap:EN10MB pour Ethernet. Les noms sont convertis à l'aide de pcap_datalink_name_to_val(). Une liste complète des DLTs se trouve sur https://www.tcpdump.org/linktypes.html.

encap:nombre Les données du paquet doivent être disséquées en utilisant le LINKTYPE_ nombre de libpcap/Npcap, par exemple encap:105 pour le IEEE 802.11 brut ou encap:101 pour IP brut.

proto:protocole Les données du paquet doivent être transmises au disséqueur de protocole Wireshark spécifié, par exemple proto:http pour les données HTTP.

-F <champ à afficher>

Ajoute le champ correspondant à la sortie. Les champs sont tous les champs de filtre d'affichage valides. Plus d'un indicateur -F peut être spécifié, et chaque champ peut correspondre plusieurs fois dans un paquet donné. Un seul champ peut être spécifié par indicateur -F. Si vous souhaitez appliquer un filtre d'affichage, utilisez l'indicateur -R.

-h|--help

Affiche le numéro de version et les options, puis quitte.

-l

Vide la sortie standard après l'impression des informations pour chaque paquet. (Ce n'est pas, strictement parlant, en mode buffer par ligne si -V a été spécifié ; cependant, c'est le même qu'en mode buffer par ligne si -V n'a pas été spécifié, car une seule ligne est imprimée pour chaque paquet, et, comme -l est normalement utilisé lors du piping d'une capture en direct vers un programme ou un script, de sorte que la sortie d'un paquet s'affiche dès que le paquet est vu et disséqué, cela fonctionnera aussi bien qu'un vrai buffer par ligne. Nous faisons cela comme solution de contournement pour une lacune dans la bibliothèque C de Microsoft Visual C++.)

Cela peut être utile lors du piping de la sortie de TShark vers un autre programme, car cela signifie que le programme vers lequel la sortie est pipée verra les données disséquées d'un paquet dès que TShark verra le paquet et générera cette sortie, plutôt que de la voir seulement lorsque le tampon de sortie standard contenant ces données se remplit.

-m <limite de mémoire en octets>

Limite l'utilisation de la mémoire de rawshark au nombre d'octets spécifié. POSIX (hors Windows) uniquement.

-o <préférence>:<valeur>

Définit une valeur de préférence, remplaçant la valeur par défaut et toute valeur lue à partir d'un fichier de préférences. L'argument de l'option est une chaîne de la forme nom_préférence:valeur, où nom_préférence est le nom de la préférence (qui est le même nom qui apparaîtrait dans le fichier de préférences), et valeur est la valeur à laquelle elle doit être définie.

-p

Suppose que les données du paquet sont précédées d'une structure pcap_pkthdr telle que définie dans pcap.h. Sur certains systèmes, la taille des données d'horodatage sera différente des données écrites sur le disque. Sur d'autres systèmes, elles sont identiques et cet indicateur n'a aucun effet.

-r <tube>|-

Lit les données des paquets depuis la source d'entrée. Il peut s'agir du nom d'un FIFO (tube nommé) ou de ``-'' pour lire les données depuis l'entrée standard, et doit avoir le format d'enregistrement spécifié ci-dessus.

Si vous envoyez des données à rawshark depuis un processus parent sous Windows, vous ne devez pas fermer le descripteur d'entrée standard de rawshark prématurément, sinon le runtime C pourrait déclencher une exception.

-R|--read-filter <filtre de lecture (affichage)>

Fait en sorte que le filtre spécifié (qui utilise la syntaxe des filtres de lecture/affichage, plutôt que celle des filtres de capture) soit appliqué avant d'imprimer la sortie. Les filtres de lecture et les filtres d'affichage sont synonymes dans rawshark.

-s

Permet d'utiliser les fichiers pcap standard en entrée, en sautant l'en-tête de fichier pcap de 24 octets.

-S

Utilise la chaîne de format spécifiée pour imprimer chaque champ. Les formats suivants sont

Ce site n'est en aucun cas associé à Arch Linux ni affilié à ce projet. Le contenu est uniquement une traduction des pages de manuel d'Arch publiées sur man.archlinux.org.

pris en charge :

%D Nom ou description du champ, par exemple « Type » pour dns.qry.type.

%N Valeur numérique du champ en base 10.

%S Valeur chaîne du champ.

Pour quelque chose de similaire à l'affichage standard de Wireshark ("Type : A (1)"), vous pourriez utiliser %D: %S (%N).

-v|--version

Affiche les informations complètes de version et quitte.

-Y|--display-filter <filtre de lecture (affichage)>

Applique le filtre spécifié (qui utilise la syntaxe des filtres de lecture/affichage, plutôt que celle des filtres de capture) avant d'afficher la sortie. Les filtres de lecture et les filtres d'affichage sont synonymes dans rawshark.

OPTIONS DE DECODAGE

--disable-all-protocols

Désactive le décodage de tous les protocoles.

--disable-protocol <nom_proto>[,<nom_proto>,...]

Désactive le décodage de nom_proto. Utilisez un nom_proto de ALL pour remplacer la liste des protocoles activés par défaut de votre profil choisi et désactiver temporairement tous les protocoles.

--disable-heuristic <nom_court>

Désactive le décodage du protocole heuristique.

--enable-protocol <nom_proto>[,<nom_proto>,...]

Active le décodage de nom_proto. Utilisez un nom_proto de ALL pour remplacer la liste des protocoles désactivés par défaut de votre profil choisi et activer temporairement tous les protocoles qui sont activés par défaut.

Si un protocole est impliqué à la fois dans --disable-protocol et --enable-protocol, le protocole est activé. Cela vous permet de désactiver temporairement tous les protocoles à l'exception d'une liste d'exceptions. Exemple : --disable-protocol ALL --enable-protocol eth,ip

--enable-heuristic <nom_court>

Active le décodage du protocole heuristique.

-K <keytab>

Charge les clés de chiffrement Kerberos à partir du fichier keytab spécifié. Cette option peut être utilisée plusieurs fois pour charger des clés à partir de plusieurs fichiers.

Exemple : -K krb5.keytab

-n

Désactive la résolution des noms d'objets réseau (tels que les noms d'hôtes, les ports TCP et UDP) ; l'option -N peut remplacer celle-ci.

-N <indicateurs de résolution de noms>

Active la résolution de noms uniquement pour des types d'adresses et de numéros de port spécifiques, et désactive la résolution de noms pour d'autres types d'adresses et de numéros de port. Cette option (ainsi que -n) peut être spécifiée plusieurs fois ; la dernière valeur donnée remplace les précédentes. Cette option et -n remplacent les options des préférences, y compris les préférences définies via l'option -o. Si les options -N et -n ne sont pas présentes, les valeurs des préférences sont utilisées, qui par défaut sont -N dmN.

L'argument est une chaîne qui peut contenir les lettres :

d pour activer la résolution à partir des paquets DNS capturés.

g pour activer la recherche d'informations de géolocalisation d'adresses IP à partir des bases de données MaxMind configurées.

m pour activer la résolution d'adresses MAC.

n pour activer la résolution d'adresses réseau.

N pour activer l'utilisation de résolveurs externes (par exemple, DNS) pour la résolution d'adresses réseau ; aucun effet sans que n soit également activé.

s pour activer la résolution d'adresses en utilisant les informations SNI trouvées dans les paquets de handshake capturés.

t pour activer la résolution des numéros de port de la couche de transport.

v pour activer la résolution des ID VLAN en noms.

--only-protocols <protocoles>

N'active le décodage que pour ces protocoles, séparés par des virgules. Désactive tout le reste.

-t (a|ad|adoy|d|dd|e|r|u|ud|udoy)[.[N]]|.[N]

Définit le format de l'horodatage des paquets affiché dans la colonne de temps par défaut. Le format peut être l'un des suivants :

a absolu : L'heure absolue, en heure locale de votre fuseau horaire, est l'heure réelle à laquelle le paquet a été capturé, sans afficher la date.

ad absolu avec date : La date absolue, affichée sous la forme AAAA-MM-JJ, et l'heure, en heure locale de votre fuseau horaire, sont l'heure et la date réelles auxquelles le paquet a été capturé.

adoy absolu avec date utilisant le jour de l'année : La date absolue, affichée sous la forme AAAA/DOY, et l'heure, en heure locale de votre fuseau horaire, sont l'heure et la date réelles auxquelles le paquet a été capturé.

d delta : Le temps delta est le temps écoulé depuis la capture du paquet précédent.

dd delta_affiché : Le temps delta_affiché est le temps écoulé depuis la capture du paquet précédent affiché.

e époque : Le temps en secondes depuis l'époque (1er janvier 1970, 00:00:00).

r relatif : Le temps relatif est le temps écoulé entre le premier paquet et le paquet actuel.

u UTC : L'heure absolue, en UTC avec un suffixe "Z", est l'heure réelle à laquelle le paquet a été capturé, sans afficher la date.

ud UTC avec date : La date absolue, affichée sous la forme AAAA-MM-JJ, et l'heure, en UTC avec un suffixe "Z", sont l'heure et la date réelles auxquelles le paquet a été capturé.

udoy UTC avec date utilisant le jour de l'année : La date absolue, affichée sous la forme AAAA/DOY, et l'heure, en UTC avec un suffixe "Z", sont l'heure et la date réelles auxquelles le paquet a été capturé.

.[N] Définit la précision : N est le nombre de décimales (0 à 9). Si vous utilisez "." sans N, la précision est déterminée automatiquement à partir de la trace.

Le format par défaut est relatif avec une précision basée sur le format de capture.

-u <s|hms>

Spécifie comment les formats d'horodatage des paquets dans -t qui sont des temps relatifs (c'est-à-dire relatif, delta, et delta_affiché) sont affichés. Les choix valides sont :

s pour les secondes.

hms pour les heures, minutes et secondes.

Le format par défaut est les secondes.

OPTIONS DE DIAGNOSTIC

--log-level <niveau>

Définit le niveau de journalisation actif. Les niveaux pris en charge, de bas en haut, sont « noisy », « debug », « info », « message », « warning », « critical » et « error ». Les messages à chaque niveau et supérieur seront affichés, par exemple « warning » affiche les messages « warning », « critical » et « error », et « noisy » affiche tous les messages. Les niveaux ne sont pas sensibles à la casse.

--log-fatal <niveau>

Arrête le programme si des messages sont enregistrés au niveau spécifié ou supérieur. Par exemple, « warning » arrête le programme en cas de messages « warning », « critical » ou « error ».

--log-domains <liste>

N'affiche les messages que pour les domaines de journalisation spécifiés, par exemple « GUI,Epan,sshdump ». La liste des domaines doit être séparée par des virgules. Peut être niée avec « ! » comme premier caractère (inverse la correspondance).

--log-debug <liste>

Force les domaines spécifiés à enregistrer au niveau « debug ». La liste des domaines doit être séparée par des virgules. Peut être niée avec « ! » comme premier caractère (inverse la correspondance).

--log-noisy <liste>

Force les domaines spécifiés à enregistrer au niveau « noisy ». La liste des domaines doit être séparée par des virgules. Peut être niée avec « ! » comme premier caractère (inverse la correspondance).

--log-fatal-domains <liste>

Arrête le programme si des messages sont enregistrés pour les domaines de journalisation spécifiés. La liste des domaines doit être séparée par des virgules.

--log-file <chemin>

Écrit les messages de journalisation et la sortie stderr dans le fichier spécifié.

SYNTAXE DES FILTRES DE LECTURE

Pour une table complète des protocoles et des champs de protocoles filtrables dans Rawshark, consultez la page de manuel wireshark-filter(4).

FICHIERS

Ces fichiers contiennent divers paramètres de configuration de Wireshark.

Préférences

Les fichiers de préférences contiennent les paramètres de préférence globaux (système) et personnels. Si le fichier de préférence système existe, il est lu en premier, remplaçant les paramètres par défaut. Si le fichier de préférences personnel existe, il est lu ensuite, remplaçant toutes les valeurs précédentes. Remarque : Si le drapeau de ligne de commande -o est utilisé (éventuellement plusieurs fois), il remplacera à son tour les valeurs des fichiers de préférences.

Les paramètres de préférence sont sous la forme nompref:valeur, un par ligne, où nompref est le nom de la préférence et valeur est la valeur à laquelle elle doit être définie ; les espaces blancs sont autorisés entre : et valeur. Un paramètre de préférence peut être poursuivi sur les lignes suivantes en indiquant les lignes de continuation avec des espaces blancs. Un caractère # démarre un commentaire qui court jusqu'à la fin de la ligne :

# Les barres de défilement verticales doivent-elles être à droite ?
# VRAI ou FAUX (insensible à la casse).
gui.scrollbar_on_right: TRUE

Le fichier de préférences global est recherché dans le répertoire wireshark sous le sous-répertoire share du répertoire d'installation principal. Sur macOS, ce serait généralement /Application/Wireshark.app/Contents/Resources/share ; sur d'autres systèmes compatibles UNIX, tels que Linux, \*BSD, Solaris et AIX, ce serait généralement /usr/share/wireshark/preferences pour les paquets installés par le système et /usr/local/share/wireshark/preferences pour les paquets installés localement ; sous Windows, ce serait généralement C:\Program Files\Wireshark\preferences.

Sur les systèmes compatibles UNIX, le fichier de préférences personnel est recherché dans $XDG_CONFIG_HOME/wireshark/preferences, (ou, si $XDG_CONFIG_HOME/wireshark n'existe pas alors que $HOME/.wireshark existe, $HOME/.wireshark/preferences) ; il s'agit généralement de $HOME/.config/wireshark/preferences. Sous Windows, le fichier de préférences personnel est recherché dans %APPDATA%\Wireshark\preferences (ou, si %APPDATA% n'est pas défini, %USERPROFILE%\Application Data\Wireshark\preferences).

Protocoles désactivés (activés)

Les fichiers disabled_protos contiennent des listes système et personnelles de protocoles qui ont été désactivés, de sorte que leurs dissecteurs ne sont jamais appelés. Les fichiers contiennent des noms de protocoles, un par ligne, où le nom du protocole est le même nom

me qui serait utilisé dans un filtre d'affichage pour le protocole :

http
tcp     # un commentaire

Si un protocole est répertorié dans le fichier global disabled_protos, il ne peut pas être activé par l'utilisateur.

Le fichier global disabled_protos utilise le même répertoire que le fichier de préférences global.

Le fichier personnel disabled_protos utilise le même répertoire que le fichier de préférences personnel.

Les fichiers disabled_protos ne répertorient que les protocoles qui sont activés par défaut mais qui ont été désactivés ; les protocoles qui sont désactivés par défaut (comme certains postdissecteurs) ne sont pas répertoriés. Il existe des fichiers analogues enabled_protos pour les protocoles qui sont désactivés par défaut mais qui ont été activés.

Désassembleurs heuristiques

Les fichiers heuristic_protos contiennent des listes système et personnelles de désassembleurs heuristiques et indiquent s'ils sont activés ou désactivés. Les fichiers contiennent des noms courts uniques de désassembleurs heuristiques, un par ligne, suivi d'une virgule et de 0 pour désactivé et de 1 pour activé :

quic,1
rtcp_stun,1
rtcp_udp,1
rtp_stun,0
rtp_udp,0
tls_tcp,1

Le fichier global heuristic_protos utilise le même répertoire que le fichier de préférences global.

Le fichier personnel heuristic_protos utilise le même répertoire que le fichier de préférences personnel.

Résolution de noms (hosts)

Les entrées dans les fichiers hosts des répertoires de préférences globaux et personnels sont utilisées pour résoudre les adresses IPv4 et IPv6 avant toute autre tentative de résolution. Le fichier a la syntaxe standard des fichiers hosts ; chaque ligne contient une adresse IP et un nom, séparés par des espaces blancs. Le fichier personnel hosts, s'il existe, remplace celui du répertoire global.

La résolution de noms des filtres de capture est gérée par libpcap sur les systèmes compatibles UNIX, tels que Linux, macOS, \*BSD, Solaris et AIX, et par Npcap sous Windows. Par conséquent, le fichier personnel hosts de Wireshark ne sera pas consulté pour la résolution de noms des filtres de capture.

Résolution de noms (subnets)

Si une adresse IPv4 ne peut pas être traduite par résolution de nom (aucune correspondance exacte n'est trouvée), une correspondance partielle est tentée via le fichier subnets. Les fichiers globaux subnets et personnels subnets sont utilisés s'ils existent.

Chaque ligne de ce fichier se compose d'une adresse IPv4, d'une longueur de masque de sous-réseau séparée uniquement par un / et d'un nom séparé par des espaces blancs. Bien que l'adresse doive être une adresse IPv4 complète, toutes les valeurs au-delà de la longueur du masque sont ensuite ignorées.

Un exemple est :

# Les commentaires doivent être précédés du signe # ! 192.168.0.0/24 ws_test_network

Un nom partiellement correspondant sera affiché sous la forme "nom-sous-réseau.adresse-restante". Par exemple, "192.168.0.1" sous le sous-réseau ci-dessus serait affiché comme "ws_test_network.1" ; si la longueur du masque était de 16 plutôt que 24 ci-dessus, l'adresse affichée serait "ws_test_network.0.1".

Résolution de noms (ethers)

Les fichiers ethers sont consultés pour faire correspondre les adresses matérielles EUI-48 de 6 octets et EUI-64 de 8 octets à des noms. D'abord, le fichier personnel ethers est essayé et si une adresse n'y est pas trouvée, le fichier global ethers est essayé ensuite.

Le fichier a un format similaire à celui défini par ethers(5) sur certains systèmes de type UNIX. Chaque ligne contient une adresse matérielle et un nom, séparés par des espaces blancs (tabulations ou espaces). Les chiffres hexadécimaux de l'adresse matérielle sont séparés par des deux-points (:), des tirets (-) ou des points (.). Le même caractère séparateur doit être utilisé de manière cohérente dans une adresse. Un # indique un commentaire qui s'étend jusqu'à la fin de la ligne. Les adresses MAC de 6 octets et EUI-64 de 8 octets sont prises en charge. Les quatre lignes suivantes sont des lignes valides d'un fichier ethers :

ff:ff:ff:ff:ff:ff          Diffusion
c0-00-ff-ff-ff-ff          TR_broadcast
00.00.00.00.00.00          Diffusion_zéro
00:00:00:00:00:00:00:00    Diffusion_zéro_EUI64

Notez que cela accepte une plus grande variété de formats que le fichier défini par ethers(5) sur la plupart des systèmes UN*X.

Le fichier global ethers est recherché dans le répertoire /etc sur les systèmes compatibles UNIX, tels que Linux, macOS, \*BSD, Solaris et AIX, et dans le répertoire d'installation principal (par exemple, C:\Program Files\Wireshark) sur les systèmes Windows.

Le fichier personnel ethers est recherché dans le même répertoire que le fichier de préférences personnel.

La résolution de noms des filtres de capture est gérée par libpcap sur les systèmes compatibles UNIX et par Npcap sous Windows. Par conséquent, le fichier personnel ethers de Wireshark ne sera pas consulté pour la résolution de noms des filtres de capture.

Résolution de noms (manuf)

Le fichier manuf est utilisé pour faire correspondre la partie fournisseur de 3 octets d'une adresse matérielle de 6 octets avec le nom du fabricant ; il peut également contenir des adresses MAC bien connues et des plages d'adresses spécifiées avec un masque réseau. Le format du fichier est similaire aux fichiers ethers, à l'exception du fait que les entrées telles que :

00:00:0C      Cisco     Cisco Systems, Inc

peuvent être fournies, avec l'OUI de 3 octets et un nom abrégé et un nom long pour un fournisseur, et des entrées telles que :

00-00-0C-07-AC/40     All-HSRP-routers

peuvent être spécifiées, avec une adresse MAC et un masque indiquant combien de bits de l'adresse doivent correspondre. L'entrée ci-dessus, par exemple, a 40 bits significatifs, soit 5 octets, et correspondra aux adresses de 00-00-0C-07-AC-00 à 00-00-0C-07-AC-FF. Le masque n'a pas besoin d'être un multiple de 8.

Un fichier global manuf est recherché dans le même répertoire que le fichier de préférences global, et un fichier personnel manuf est recherché dans le même répertoire que le fichier de préférences personnel.

Dans les versions antérieures de Wireshark, les informations officielles de l'IEEE Registration Authority étaient distribuées dans ce format en tant que fichier global manuf. Ces informations sont maintenant compilées pour accélérer le démarrage du programme, mais les informations internes peuvent être exportées dans ce format avec tshark -G manuf.

En plus du fichier manuf, un autre fichier du même format, wka, est recherché dans le répertoire global. Ce fichier est distribué avec Wireshark et contient des données sur les adresses MAC et les plages d'adresses bien connues, assemblées à partir de diverses sources non IEEE mais respectées.

Résolution de noms (services)

Le fichier services est utilisé pour traduire les numéros de port en noms. Les fichiers globaux services et personnels services sont utilisés s'ils existent.

Le fichier a la syntaxe standard des fichiers services ; chaque ligne contient un nom (de service) et un identifiant de transport séparés par des espaces blancs. L'identifiant de transport comprend un numéro de port et un nom de protocole de transport (généralement tcp, udp ou sctp) séparés par un /.

Un exemple est :

mydns 5045/udp # Mon propre serveur de noms de domaine mydns 5045/tcp # Mon propre serveur de noms de domaine

Dans les versions antérieures de Wireshark, les informations officielles du registre IANA étaient distribuées dans ce format en tant que fichier global services. Ces informations sont maintenant compilées pour accélérer le démarrage du programme, mais les informations internes peuvent être exportées dans ce format avec tshark -G services.

Résolution de noms (ipxnets)

Les fichiers ipxnets sont utilisés pour faire correspondre les numéros de réseau IPX de 4 octets à des noms. D'abord, le fichier global ipxnets est essayé et si cette adresse n'y est pas trouvée, le fichier personnel est essayé ensuite.

Le format est le même que celui du fichier ethers, sauf que chaque adresse est de quatre octets au lieu de six. De plus, l'adresse peut être représentée comme un nombre hexadécimal unique, comme c'est plus courant dans le monde IPX, plutôt que quatre octets hexadécimaux. Par exemple, ces quatre lignes sont des lignes valides d'un fichier ipxnets :

C0.A8.2C.00              HR
c0-a8-1c-00              CEO
00:00:BE:EF              IT_Server1
110f                     FileServer3

Le fichier global ipxnets est recherché dans le répertoire /etc sur les systèmes compatibles UNIX, tels que Linux, macOS, \*BSD, Solaris et AIX, et dans le répertoire d'installation principal (par exemple, C:\Program Files\Wireshark) sur les systèmes Windows.

Le fichier personnel ipxnets est recherché dans le même répertoire que le fichier de préférences personnel.

Résolution de noms (ss7pcs)

Le fichier ss7pcs est utilisé pour traduire les codes de point SS7 en noms. Il est lu à partir du répertoire de configuration personnel.

Chaque ligne de ce fichier se compose d'un indicateur de réseau suivi d'un tiret suivi d'un code de point en décimal et d'un nom de nœud séparés par des espaces blancs. Un exemple est :

2-1234 MyPointCode1

Résolution de noms (vlans)

Le fichier vlans est utilisé pour traduire les identifiants de balise VLAN en noms. Il est lu à partir du répertoire de configuration personnel.

Chaque ligne de ce fichier se compose d'un identifiant de balise VLAN séparé par des espaces blancs d'un nom. Un exemple est :

123    Server-Lan
2049   HR-Client-LAN

Filtres de couleur (Règles de coloration)

Les fichiers colorfilters contiennent des filtres de couleur système et personnels. Chaque ligne contient un filtre, commençant par la chaîne affichée dans la boîte de dialogue, suivie du filtre d'affichage correspondant. Les couleurs d'arrière-plan et de premier plan sont ensuite ajoutées :

# un commentaire
@tcp@tcp@[59345,58980,65534][0,0,0]
@udp@udp@[28834,57427,65533][0,0,0]

Le fichier global colorfilters utilise le même répertoire que le fichier de préférences global.

Le fichier personnel colorfilters utilise le même répertoire que le fichier de préférences personnel. Il est écrit via la boîte de dialogue Affichage : Règles de coloration.

Si le fichier global colorfilters existe, il n'est utilisé que si le fichier personnel colorfilters n'existe pas ; les filtres de couleur globaux et personnels ne sont pas fusionnés.

Plugins

Wireshark recherche les plugins dans un dossier de plugins personnel et un dossier de plugins global.

Sur les systèmes compatibles UNIX, tels que Linux, macOS, \*BSD, Solaris et AIX, le répertoire des plugins globaux est lib/wireshark/plugins/ (sur certains systèmes, remplacez lib64 par lib) sous le répertoire d'installation principal (par exemple, /usr/local/lib/wireshark/plugins/). Le répertoire des plugins personnels est $HOME/.local/lib/wireshark/plugins.

Sur macOS, si Wireshark est installé en tant que paquet d'application, le dossier global des plugins est à la place %APPDIR%/Contents/PlugIns/wireshark.

Sous Windows, le dossier global des plugins est plugins/ sous le répertoire d'installation principal (par exemple, C:\Program Files\Wireshark\plugins\). Le dossier personnel des plugins est %APPDATA%\Wireshark\plugins (ou, si %APPDATA% n’est pas défini, %USERPROFILE%\Application Data\Wireshark\plugins).

Les plugins Lua sont stockés dans les dossiers de plugins ; les plugins compilés sont stockés dans des sous-dossiers des dossiers de plugins, le nom du sous-dossier étant le numéro de version mineure de Wireshark (X.Y). Il existe un autre niveau hiérarchique pour chaque type de plugin Wireshark (libwireshark, libwiretap et codecs). Par exemple, l'emplacement d'un plugin libwireshark foo.so (foo.dll sous Windows) serait PLUGINDIR/X.Y/epan (libwireshark s'appelait auparavant libepan ; les autres noms de dossiers sont codecs et wiretap).


Note

Sur les systèmes compatibles UNIX, les plugins Lua (mais pas les plugins binaires) peuvent également
être placés dans $XDG_CONFIG_HOME/wireshark/plugins, (ou, si $XDG_CONFIG_HOME/wireshark n'existe pas tandis que $HOME/.wireshark existe, $HOME/.wireshark/plugins.)

Notez qu'un module de plugin de dissector peut prendre en charge plus d'un protocole ; il n'y a pas nécessairement de correspondance un à un entre les modules de plugin de dissector et les protocoles. Les protocoles pris en charge par un module de plugin de dissector sont activés et désactivés de la même manière que les protocoles intégrés à Wireshark.

VARIABLES D'ENVIRONNEMENT

WIRESHARK_CONFIG_DIR

Cette variable d'environnement remplace l'emplacement des fichiers de configuration personnels. Sur les systèmes compatibles UNIX, tels que Linux, macOS, \*BSD, Solaris et AIX, elle est par défaut $XDG_CONFIG_HOME/wireshark (ou, si ce répertoire n'existe pas mais que $HOME/.wireshark existe, $HOME/.wireshark) ; il s'agit généralement de $HOME/.config/wireshark. Sous Windows, elle est par défaut %APPDATA%\Wireshark (ou, si %APPDATA% n'est pas défini, %USERPROFILE%\Application Data\Wireshark). Disponible depuis Wireshark 3.0.

WIRESHARK_DEBUG_WMEM_OVERRIDE

Définir cette variable d'environnement force le framework wmem à utiliser le backend d'allocateur spécifié pour toutes les allocations, quel que soit le backend normalement spécifié par le code. Ceci est principalement utile aux développeurs lors des tests ou du débogage. Voir README.wmem dans la distribution source pour plus de détails.

WIRESHARK_RUN_FROM_BUILD_DIRECTORY

Cette variable d'environnement fait que les plugins et autres fichiers de données sont chargés depuis le répertoire de construction (où le programme a été compilé) plutôt que depuis les emplacements standard. Elle n'a aucun effet lorsque le programme en question s'exécute avec des permissions root (ou setuid) sur les systèmes compatibles UNIX, tels que Linux, macOS, \*BSD, Solaris et AIX.

WIRESHARK_DATA_DIR

Cette variable d'environnement fait que divers fichiers de données sont chargés depuis un répertoire autre que les emplacements standard. Elle n'a aucun effet lorsque le programme en question s'exécute avec des permissions root (ou setuid) sur les systèmes compatibles UNIX.

ERF_RECORDS_TO_CHECK

Cette variable d'environnement contrôle le nombre d'enregistrements ERF vérifiés lors de la décision si un fichier est réellement au format ERF. Définir cette variable d'environnement à un nombre supérieur à la valeur par défaut (20) rendrait les faux positifs moins probables.

IPFIX_RECORDS_TO_CHECK

Cette variable d'environnement contrôle le nombre d'enregistrements IPFIX vérifiés lors de la décision si un fichier est réellement au format IPFIX. Définir cette variable d'environnement à un nombre supérieur à la valeur par défaut (20) rendrait les faux positifs moins probables.

WIRESHARK_ABORT_ON_DISSECTOR_BUG

Si cette variable d'environnement est définie, Rawshark appellera abort(3) lorsqu'un bug de dissector est rencontré. abort(3) provoquera une sortie anormale du programme ; si vous exécutez Rawshark dans un débogueur, il devrait s'arrêter dans le débogueur et permettre l'inspection du processus, et, si vous ne l'exécutez pas dans un débogueur, il générera, sur certains systèmes d'exploitation, en supposant que votre environnement est correctement configuré, un fichier de vidage mémoire (core dump). Ceci peut être utile aux développeurs tentant de résoudre un problème avec un dissector de protocole.

WIRESHARK_ABORT_ON_TOO_MANY_ITEMS

Si cette variable d'environnement est définie, Rawshark appellera abort(3) si un dissector essaie d'ajouter trop d'éléments à un arbre (généralement, c'est une indication que le dissector ne sort pas d'une boucle assez rapidement). abort(3) provoquera une sortie anormale du programme ; si vous exécutez Rawshark dans un débogueur, il devrait s'arrêter dans le débogueur et permettre l'inspection du processus, et, si vous ne l'exécutez pas dans un débogueur, il générera, sur certains systèmes d'exploitation, en supposant que votre environnement est correctement configuré, un fichier de vidage mémoire (core dump). Ceci peut être utile aux développeurs tentant de résoudre un problème avec un dissector de protocole.
