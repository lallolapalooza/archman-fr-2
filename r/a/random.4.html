random(4) Manuel des pilotes de périphériques random(4)

NOM

random, urandom - périphériques source de nombres aléatoires du noyau

SYNOPIS

#include <linux/random.h>
int ioctl(fd, RNDrequest, param);

DESCRIPTION

Les fichiers spéciaux de caractères /dev/random et /dev/urandom (présents depuis Linux 1.3.30) fournissent une interface au générateur de nombres aléatoires du noyau. Le fichier /dev/random a le numéro de périphérique majeur 1 et le numéro de périphérique mineur 8. Le fichier /dev/urandom a le numéro de périphérique majeur 1 et le numéro de périphérique mineur 9.

Le générateur de nombres aléatoires collecte le bruit ambiant des pilotes de périphériques et d'autres sources dans un pool d'entropie. Le générateur maintient également une estimation du nombre de bits de bruit dans le pool d'entropie. Des nombres aléatoires sont créés à partir de ce pool d'entropie.

Linux 3.17 et versions ultérieures fournissent l'interface getrandom(2), plus simple et plus sûre, qui ne nécessite aucun fichier spécial ; consultez la page de manuel de getrandom(2) pour plus de détails.

Lors de la lecture, le périphérique /dev/urandom renvoie des octets aléatoires en utilisant un générateur de nombres pseudo-aléatoires amorcé à partir du pool d'entropie. Les lectures de ce périphérique ne se bloquent pas (c'est-à-dire que le processeur n'est pas cédé), mais peuvent entraîner un délai appréciable lors de la demande de grandes quantités de données.

Lors de la lecture pendant le démarrage précoce, /dev/urandom peut renvoyer des données avant l'initialisation du pool d'entropie. Si cela pose problème dans votre application, utilisez getrandom(2) ou /dev/random à la place.

Le périphérique /dev/random est une interface héritée qui date d'une époque où les primitives cryptographiques utilisées dans l'implémentation de /dev/urandom n'étaient pas largement fiables. Il renverra des octets aléatoires uniquement dans la limite du nombre estimé de bits de bruit frais dans le pool d'entropie, en se bloquant si nécessaire. /dev/random convient aux applications qui nécessitent une grande qualité d'aléatoire et qui peuvent se permettre des délais indéterminés.

Lorsque le pool d'entropie est vide, les lectures de /dev/random se bloquent jusqu'à ce que du bruit ambiant supplémentaire soit collecté. Depuis Linux 5.6, le drapeau O_NONBLOCK est ignoré car /dev/random ne se bloquera plus, sauf pendant le processus de démarrage précoce. Dans les versions antérieures, si open(2) est appelé pour /dev/random avec le drapeau O_NONBLOCK, une lecture ultérieure (read(2)) ne se bloquera pas si le nombre d'octets demandé n'est pas disponible. Les octets disponibles sont plutôt renvoyés. Si aucun octet n'est disponible, read(2) renverra -1 et errno sera défini sur EAGAIN.

Le drapeau O_NONBLOCK n'a aucun effet lors de l'ouverture de /dev/urandom. Lors de l'appel à read(2) pour le périphérique /dev/urandom, les lectures allant jusqu'à 256 octets renverront autant d'octets que demandé et ne seront pas interrompues par un gestionnaire de signal. Les lectures avec un tampon dépassant cette limite peuvent renvoyer moins d'octets que demandé ou échouer avec l'erreur EINTR, si interrompues par un gestionnaire de signal.

Depuis Linux 3.16, une lecture (read(2)) de /dev/urandom renverra au maximum 32 mégaoctets. Une lecture (read(2)) de /dev/random renverra au maximum 512 octets (340 octets avant Linux 2.6.12).

L'écriture dans /dev/random ou /dev/urandom mettra à jour le pool d'entropie avec les données écrites, mais cela n'entraînera pas un comptage d'entropie plus élevé. Cela signifie que cela affectera le contenu lu des deux fichiers, mais cela ne rendra pas les lectures de /dev/random plus rapides.

Utilisation

L'interface /dev/random est considérée comme une interface héritée, et /dev/urandom est préférée et suffisante dans tous les cas d'utilisation, à l'exception des applications qui nécessitent de l'aléatoire pendant le démarrage précoce ; pour ces applications, getrandom(2) doit être utilisé à la place, car il se bloquera jusqu'à ce que le pool d'entropie soit initialisé.

Si un fichier de graine est sauvegardé entre les redémarrages comme recommandé ci-dessous, la sortie est cryptographiquement sécurisée contre les attaquants sans accès root local dès son rechargement dans la séquence de démarrage, et parfaitement adéquate pour les clés de session de chiffrement réseau. (Toutes les distributions Linux majeures sauvegardent le fichier de graine entre les redémarrages depuis 2000 au moins.) Étant donné que les lectures de /dev/random peuvent se bloquer, les utilisateurs voudront généralement l'ouvrir en mode non bloquant (ou effectuer une lecture avec timeout), et fournir une notification à l'utilisateur si l'entropie souhaitée n'est pas immédiatement disponible.

Configuration

Si votre système ne dispose pas déjà de /dev/random et /dev/urandom, ils peuvent être créés avec les commandes suivantes :


mknod -m 666 /dev/random c 1 8
mknod -m 666 /dev/urandom c 1 9
chown root:root /dev/random /dev/urandom

Lorsqu'un système Linux démarre sans beaucoup d'interaction de l'opérateur, le pool d'entropie peut être dans un état assez prévisible. Cela réduit la quantité réelle de bruit dans le pool d'entropie en dessous de l'estimation. Pour contrer cet effet, il est utile de conserver les informations du pool d'entropie entre les arrêts et les démarrages. Pour ce faire, ajoutez les lignes suivantes à un script approprié qui est exécuté pendant la séquence de démarrage du système Linux :


echo "Initialisation du générateur de nombres aléatoires..."
random_seed=/var/run/random-seed
# Conserver une graine aléatoire d'un démarrage à l'autre
# Charger puis sauvegarder tout le pool d'entropie
if [ -f $random_seed ]; then
    cat $random_seed >/dev/urandom
else
    touch $random_seed
fi
chmod 600 $random_seed
poolfile=/proc/sys/kernel/random/poolsize
[ -r $poolfile ] && bits=$(cat $poolfile) || bits=4096
bytes=$(expr $bits / 8)
dd if=/dev/urandom of=$random_seed count=1 bs=$bytes

Ajoutez également les lignes suivantes dans un script approprié qui est exécuté pendant l'arrêt du système Linux :


# Conserver une graine aléatoire de l'arrêt au démarrage
# Sauvegarder tout le pool d'entropie
echo "Sauvegarde de la graine aléatoire..."
random_seed=/var/run/random-seed
touch $random_seed
chmod 600 $random_seed
poolfile=/proc/sys/kernel/random/poolsize
[ -r $poolfile ] && bits=$(cat $poolfile) || bits=4096
bytes=$(expr $bits / 8)
dd if=/dev/urandom of=$random_seed count=1 bs=$bytes

Dans les exemples ci-dessus, nous supposons Linux 2.6.0 ou version ultérieure, où /proc/sys/kernel/random/poolsize renvoie la taille du pool d'entropie en bits (voir ci-dessous).

Interfaces /proc

Les fichiers du répertoire /proc/sys/kernel/random (présents depuis Linux 2.3.16) fournissent des informations supplémentaires sur le périphérique /dev/random :

entropy_avail
Ce fichier en lecture seule donne l'entropie disponible, en bits. Ce sera un nombre dans la plage 0 à 4096.
poolsize
Ce fichier donne la taille du pool d'entropie. La sémantique de ce fichier varie selon les versions du noyau :
Linux 2.4 :
Ce fichier donne la taille du pool d'entropie en *octets*. Normalement, ce fichier aura la valeur 512, mais il est accessible en écriture et peut être modifié à toute valeur pour laquelle un algorithme est disponible. Les choix sont 32, 64, 128, 256, 512, 1024 ou 2048.
Linux 2.6 et versions ultérieures :
Ce fichier est en lecture seule et donne la taille du pool d'entropie en *bits*. Il contient la valeur 4096.
read_wakeup_threshold
Ce fichier contient le nombre de bits d'entropie requis pour réveiller les processus qui dorment en attendant de l'entropie de /dev/random. La valeur par défaut est 64.

random(4) — Arch Linux

NAME

random, urandom - random number generator devices

SYNOPSIS

#include <sys/types.h>
#include <sys/ioctl.h>
#include <linux/random.h>

/* ioctl() requests */
int fd;
unsigned int ui;
struct rand_pool_info rpi;

ioctl(fd, RNDGETENTCNT, &ui);
ioctl(fd, RNDADDTOENTCNT, &ui);
ioctl(fd, RNDADDENTROPY, &rpi);
ioctl(fd, RNDZAPENTCNT, NULL);
ioctl(fd, RNDCLEARPOOL, NULL);

/* read() */
read(fd, buffer, count);

/* write() */
write(fd, buffer, count);

DESCRIPTION

The character special files /dev/random and /dev/urandom are special files in the /dev directory which act as pseudorandom number generators. The device drivers in the kernel maintain an entropy pool, which is a collection of random bits gathered from hardware and environmental noise. The quality of the random numbers generated by these devices depends on the amount of entropy in the pool.

The primary difference between /dev/random and /dev/urandom is the way they handle the situation where the entropy pool is depleted.

/dev/random
When reading from /dev/random, the operation blocks if insufficient entropy is available in the pool. The amount of entropy required is determined by the algorithm used by the kernel, but it is typically related to the number of bits of randomness generated.
/dev/urandom
When reading from /dev/urandom, the operation does not block if insufficient entropy is available. Instead, it uses a cryptographically secure pseudorandom number generator (CSPRNG) seeded from the entropy pool. This means that /dev/urandom will always return data immediately and is suitable for most applications, including cryptographic use.

Both devices provide a stream of random bytes. The number of bytes read is the number of bytes supplied. Writes to these devices are ignored, except for certain sysctl(8) values which can be modified.

The following sysctl(8) values can be inspected and modified:

entropy_avail
This file, typically found under /proc/sys/kernel/, contains the number of bits of entropy currently available in the pool. This value can be decreased by writing to the file. Decreasing this value can be used to signal that the entropy pool has been artificially filled. Conversely, writing a higher value will increase the entropy count. A value larger than the maximum entropy available will be capped.
poolsize
This file contains the size, in bits, of the entropy pool. This value cannot be changed.
read_wakeup_threshold
This file contains the number of bits of entropy below which we wake up processes that do a select(2) or poll(2) for read access to /dev/random. These values can be changed by writing to the files.
write_wakeup_threshold
This file contains the number of bits of entropy below which we wake up processes that do a select(2) or poll(2) for write access to /dev/random. These values can be changed by writing to the files.
uuid
boot_id
These read-only files contain random strings like 6fd5a44b-35f4-4ad4-a9b9-6b9be13e1fe9. The former is generated afresh for each read, the latter was generated once.

ioctl(2) interface

The following ioctl(2) requests are defined on file descriptors connected to either /dev/random or /dev/urandom. All requests performed will interact with the input entropy pool impacting both /dev/random and /dev/urandom. The CAP_SYS_ADMIN capability is required for all requests except RNDGETENTCNT.

RNDGETENTCNT
Retrieve the entropy count of the input pool, the contents will be the same as the entropy_avail file under proc. The result will be stored in the int pointed to by the argument.
RNDADDTOENTCNT
Increment or decrement the entropy count of the input pool by the value pointed to by the argument.
RNDGETPOOL
Removed in Linux 2.6.9.
RNDADDENTROPY
Add some additional entropy to the input pool, incrementing the entropy count. This differs from writing to /dev/random or /dev/urandom, which only adds some data but does not increment the entropy count. The following structure is used:

struct rand_pool_info {
    int    entropy_count;
    int    buf_size;
    __u32  buf[0];
};

Here entropy_count is the value added to (or subtracted from) the entropy count, and buf is the buffer of size buf_size which gets added to the entropy pool.
RNDZAPENTCNT
RNDCLEARPOOL
Zero the entropy count of all pools and add some system data (such as wall clock) to the pools.

FILES

/dev/random
/dev/urandom

NOTES

For an overview and comparison of the various interfaces that can be used to obtain randomness, see random(7).

BUGS

During early boot time, reads from /dev/urandom may return data prior to the entropy pool being initialized.
