RADRELAY(8) Démon FreeRADIUS RADRELAY(8)

NOM

radrelay -- Commande obsolète.

DESCRIPTION

Les fonctions de radrelay ont été ajoutées à radiusd. Un des avantages est qu'une seule instance de radiusd peut lire plusieurs fichiers de détails, entre autres.

Le module rlm_sql_log fait quelque chose de similaire, mais pour les requêtes SQL. Voir sa page de manuel pour les détails.

RÉPLICATION POUR SAUVEGARDE

De nombreux sites exécutent plusieurs serveurs radius ; au moins un serveur principal et un serveur de secours. Lorsque le serveur principal tombe en panne, la plupart des NAS le détectent et basculent sur le serveur de secours.

Cela aura pour conséquence que vos paquets de comptabilisation iront sur le serveur de secours - et certains NAS ne basculent même pas sur le serveur principal lorsqu'il revient en ligne.

Le résultat est que les enregistrements de comptabilisation sont manqués, et/ou l'administrateur doit faire des acrobaties pour combiner les différents fichiers de détails de plusieurs serveurs. Cela signifie également que la base de données de session ("radutmp", utilisée pour radwho et la détection d'utilisation simultanée) se désynchronise.

Nous résolvons ce problème en "relaisant" les paquets d'un serveur à un autre, afin qu'ils aient tous deux le même ensemble de données de comptabilisation.

Voir raddb/sites-available/buffered-sql pour plus d'informations.

MISE EN TAMPON POUR LES SERVEURS À FORTE CHARGE

Si le serveur RADIUS reçoit soudainement un grand nombre de paquets de comptabilisation, il se peut qu'il n'y ait pas assez de puissance CPU pour les traiter tous en temps voulu. Ce problème est particulièrement notable lorsque les paquets de comptabilisation vont vers une base de données backend.

De même, vous pouvez avoir une base de données qui suit les sessions "en direct" et une autre qui suit les données de comptabilisation historiques. Dans ce cas, l'accès à la première base de données est rapide, car elle est petite. L'accès à la seconde base de données peut être plus lent, car elle peut contenir plusieurs gigaoctets de données. De plus, l'écriture dans la première base de données en temps voulu est importante, tandis que les données peuvent être écrites dans la seconde base de données avec quelques minutes de retard, sans aucun inconvénient.

Voir raddb/sites-available/copy-to-home-server pour plus d'informations.
