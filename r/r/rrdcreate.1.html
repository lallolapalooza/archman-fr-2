RRDCREATE(1) rrdtool RRDCREATE(1)

NOM

rrdcreate - Configurer une nouvelle base de données Round Robin

SYNOPIS

rrdtool create nom-fichier [--start|-b heure-de-début] [--step|-s pas] [--template|-t fichier-modèle] [--source|-r fichier-source] [--no-overwrite|-O] [--daemon|-d adresse] [DS:nom-ds[=nom-ds-mappé[[index-source]]]:DST:arguments-dst] [RRA:CF:arguments-cf]

DESCRIPTION

La fonction create de RRDtool vous permet de configurer de nouveaux fichiers de base de données Round Robin (RRD). Le fichier est créé à sa taille finale et rempli de données *UNKNOWN*, sauf si un ou plusieurs fichiers RRD source ont été spécifiés et qu'ils contiennent des données appropriées pour "pré-remplir" le nouveau fichier RRD.

nom-fichier

Le nom du RRD que vous souhaitez créer. Les fichiers RRD devraient se terminer par l'extension .rrd. Cependant, RRDtool acceptera n'importe quel nom de fichier.

--start|-b heure-de-début (défaut : maintenant - 10s)

Spécifie l'heure, en secondes depuis le 1er janvier 1970 UTC, à laquelle la première valeur doit être ajoutée au RRD. RRDtool n'acceptera aucune donnée datée avant ou à l'heure spécifiée.

Voir aussi "SPÉCIFICATION DE TEMPS STYLE AT" dans rrdfetch pour d'autres façons de spécifier le temps.

Si un ou plusieurs fichiers source sont utilisés pour pré-remplir le nouveau RRD, l'option --start peut être omise. Dans ce cas, l'heure de dernière mise à jour parmi tous les fichiers source sera utilisée comme dernière heure de mise à jour du nouveau fichier RRD, définissant ainsi l'heure de début.

--step|-s pas (défaut : 300 secondes)

Spécifie l'intervalle de base en secondes auquel les données seront fournies au RRD. Un facteur d'échelle peut être présent en suffixe de l'entier ; voir "PAS, HEARTBEAT, et Lignes comme Durées".

--no-overwrite|-O

Ne pas écraser un fichier existant du même nom.

--daemon|-d adresse

Adresse du démon rrdcached. Pour une liste des formats acceptés, voir l'option -l dans le manuel de rrdcached.

rrdtool create --daemon unix:/var/run/rrdcached.sock /var/lib/rrd/foo.rrd I<autres options>

[--template|-t fichier-modèle]

Spécifie un fichier RRD modèle à partir duquel prendre les définitions de pas, DS et RRA. Cela permet de baser la structure d'un nouveau fichier sur un fichier existant. Les données du fichier modèle ne sont PAS utilisées pour le pré-remplissage, mais il est possible de spécifier le même fichier comme fichier source (voir ci-dessous).

Des définitions DS et RRA supplémentaires sont permises et seront ajoutées à celles prises du modèle.

--source|-r fichier-source

Un ou plusieurs fichiers RRD source peuvent être nommés sur la ligne de commande. Les données de ces fichiers source seront utilisées pour pré-remplir le fichier RRD créé. Le fichier de sortie et un fichier source peuvent faire référence au même nom de fichier. Cela remplacera effectivement le fichier source par le nouveau fichier RRD. Bien qu'il y ait un risque de perdre le fichier source car il est remplacé, il n'y a aucun risque que le fichier source et le nouveau fichier puissent être "mélangés" à un moment donné, car le nouveau fichier sera toujours créé d'abord sous forme de fichier temporaire et ne sera déplacé vers sa destination finale une fois qu'il aura été entièrement écrit.

Le pré-remplissage se fait en faisant correspondre les noms DS, les RRA et les fonctions de consolidation, et en choisissant la meilleure résolution de données disponible lors de ce processus. Le pré-remplissage peut ne pas être mathématiquement correct dans tous les cas (par exemple, si les résolutions doivent changer en raison de pas modifiés du RRD cible et que les anciennes et nouvelles résolutions ne correspondent pas aux limites de bacs anciennes/nouvelles dans les RRAs).

En d'autres termes : un effort est fait pour préserver les données pendant le pré-remplissage. De plus, le pré-remplissage des RRAs peut seulement être possible pour certains types de DS. Le pré-remplissage peut également avoir des effets étranges sur les RRAs de prévision Holt-Winters. En d'autres termes : il n'y a aucune garantie de correction des données.

Lorsque l'on "pré-remplit" un fichier RRD, la structure du nouveau fichier doit être spécifiée comme d'habitude en utilisant les spécifications DS et RRA décrites ci-dessous. Les données seront prises des fichiers source en fonction des noms et types DS et dans l'ordre où les fichiers source sont spécifiés. Les sources de données portant le même nom provenant de différents fichiers source seront combinées pour former une nouvelle source de données. Généralement, pour tout point dans le temps couvert par le nouveau fichier RRD après sa création, les données d'un seul fichier source auront été utilisées pour le pré-remplissage. Cependant, les données de plusieurs sources peuvent être combinées si elles se réfèrent à des temps différents ou si un fichier source nommé précédemment contient des données inconnues pour un temps où un fichier ultérieur contient des données connues.

Si cette sélection automatique de données n'est pas souhaitée, la syntaxe DS permet de spécifier un mappage de sources de données cibles et sources pour le pré-remplissage. Cette syntaxe permet de renommer les sources de données et de restreindre le pré-remplissage d'un DS à n'utiliser que les données d'un seul fichier source.

Le pré-remplissage ne fonctionne actuellement de manière fiable que pour les RRAs utilisant l'une des fonctions de consolidation classiques, c'est-à-dire l'une des suivantes : AVERAGE, MIN, MAX, LAST. Il peut également avoir des problèmes avec les sources de données COMPUTE.

Notez que l'acte de pré-remplissage lors de la commande create est similaire à bon nombre des opérations disponibles via la commande tune, mais utilise la syntaxe create.

DS:nom-ds[=nom-ds-mappé[[index-source]]]:DST:arguments-dst

Un seul RRD peut accepter des entrées de plusieurs sources de données (DS), par exemple le trafic entrant et sortant sur une ligne de communication spécifique. Avec l'option de configuration DS, vous devez définir certaines propriétés de base de chaque source de données que vous souhaitez stocker dans le RRD.

nom-ds est le nom que vous utiliserez pour référencer cette source de données particulière à partir d'un RRD. Un nom-ds doit avoir une longueur de 1 à 19 caractères parmi [a-zA-Z0-9_].

DST définit le Type de Source de Données. Les arguments restants d'une entrée de source de données dépendent du type de source de données. Pour GAUGE, COUNTER, DERIVE, DCOUNTER, DDERIVE et ABSOLUTE, le format d'une entrée de source de données est :

DS:nom-ds:{GAUGE | COUNTER | DERIVE | DCOUNTER | DDERIVE | ABSOLUTE}:heartbeat:min:max

Pour les sources de données COMPUTE, le format est :

DS:nom-ds:COMPUTE:expression-rpn

Afin de décider quel type de source de données utiliser, examinez les définitions qui suivent. Consultez également la section sur "COMMENT MESURER" pour un éclairage supplémentaire.

GAUGE
est pour des choses comme les températures ou le nombre de personnes dans une pièce ou la valeur d'une action RedHat.
COUNTER
est pour les compteurs à incrémentation continue comme le compteur ifInOctets d'un routeur. La source de données COUNTER suppose que le compteur ne diminue jamais, sauf lors d'un dépassement de capacité du compteur. La fonction de mise à jour tient compte du dépassement. Le compteur est stocké en tant que taux par seconde. Lorsque le compteur dépasse sa capacité, RRDtool vérifie si le dépassement s'est produit à la limite 32 bits ou 64 bits et agit en conséquence en ajoutant une valeur appropriée au résultat.
DCOUNTER
est identique à COUNTER, mais pour des quantités exprimées en nombre à virgule flottante double précision. Pourrait être utilisé pour suivre des quantités qui s'incrémentent par des nombres non entiers, c'est-à-dire le nombre de secondes qu'une routine a pris pour s'exécuter, le poids total traité par un équipement technologique, etc. La seule différence substantielle est que DCOUNTER peut être soit en comptage ascendant, soit en comptage descendant, mais pas les deux en même temps. La direction actuelle est détectée automatiquement lors de la deuxième mise à jour de compteur non indéfinie et toute modification ultérieure de la direc
tion est considérée comme une réinitialisation. La nouvelle direction est déterminée et verrouillée par la deuxième mise à jour après la réinitialisation et sa différence par rapport à la valeur à la réinitialisation.
DERIVE
stockera la dérivée de la ligne allant de la dernière à la valeur actuelle de la source de données. Cela peut être utile pour les jauges, par exemple, pour mesurer le taux de personnes entrant ou sortant d'une pièce. En interne, derive fonctionne exactement comme COUNTER mais sans vérifications de dépassement. Donc, si votre compteur ne se réinitialise pas sur 32 ou 64 bits, vous pourriez vouloir utiliser DERIVE et le combiner avec une valeur MIN de 0.
DDERIVE
identique à DERIVE, mais pour les quantités exprimées en nombre à virgule flottante double précision.

NOTE sur COUNTER vs DERIVE

par Don Baarda <don.baarda@baesystems.com>

Si vous ne pouvez pas tolérer de confondre occasionnellement une réinitialisation de compteur avec un enroulement légitime du compteur, et préféreriez des "Inconnus" pour tous les enroulements et réinitialisations légitimes de compteur, utilisez toujours DERIVE avec min=0. Sinon, utiliser COUNTER avec un max approprié retournera des valeurs correctes pour tous les enroulements légitimes de compteur, marquera certaines réinitialisations de compteur comme "Inconnues", mais peut confondre certaines réinitialisations de compteur avec un enroulement légitime de compteur.

Pour un intervalle de 5 minutes et un compteur 32 bits, la probabilité de confondre une réinitialisation de compteur avec un enroulement légitime est sans doute d'environ 0,8% par Mbps de bande passante maximale. Notez que cela équivaut à 80% pour les interfaces 100 Mbps, donc pour les interfaces à haute bande passante et un compteur 32 bits, DERIVE avec min=0 est probablement préférable. Si vous utilisez un compteur 64 bits, à peu près tous les réglages max élimineront la possibilité de confondre une réinitialisation avec un enroulement de compteur.

ABSOLUTE
est pour les compteurs qui sont réinitialisés à la lecture. Ceci est utilisé pour les compteurs rapides qui ont tendance à déborder. Donc, au lieu de les lire normalement, vous les réinitialisez après chaque lecture pour vous assurer d'avoir un temps maximum disponible avant le prochain débordement. Une autre utilisation est pour les choses que vous comptez comme le nombre de messages depuis la dernière mise à jour.
COMPUTE
est pour stocker le résultat d'une formule appliquée à d'autres sources de données dans le RRD. Cette source de données ne reçoit pas de valeur lors de la mise à jour, mais ses Points de Données Primaires (PDP) sont plutôt calculés à partir des PDP des sources de données selon l'expression rpn qui définit la formule. Les fonctions de consolidation sont ensuite appliquées normalement aux PDP de la source de données COMPUTE (c'est-à-dire que l'expression rpn n'est appliquée que pour générer des PDP). Dans les logiciels de base de données, de tels ensembles de données sont appelés colonnes "virtuelles" ou "calculées".

heartbeat définit le nombre maximum de secondes qui peuvent s'écouler entre deux mises à jour de cette source de données avant que la valeur de la source de données ne soit supposée être *INCONNUE*.

min et max définissent la plage attendue des valeurs pour les données fournies par une source de données. Si min et/ou max sont spécifiés, toute valeur en dehors de la plage définie sera considérée comme *INCONNUE*. Si vous ne connaissez pas ou ne vous souciez pas de min et max, réglez-les sur U pour inconnu. Notez que min et max font toujours référence aux valeurs traitées de la DS. Pour une DS de type COUNTER de trafic, ce serait le débit maximal et minimal attendu de l'appareil.

Si des informations sur les valeurs minimales/maximales attendues sont disponibles, définissez toujours les propriétés min et/ou max. Cela aidera RRDtool à effectuer une simple vérification de la validité des données fournies lors de l'exécution de la mise à jour.

rpn-expression définit la formule utilisée pour calculer les PDP d'une source de données COMPUTE à partir d'autres sources de données dans le même <RRD>. Elle est similaire à la définition d'un argument CDEF pour la commande graph. Veuillez vous référer à cette page man pour une liste et une description des opérations RPN prises en charge. Pour les sources de données COMPUTE, les opérations RPN suivantes ne sont pas prises en charge : COUNT, PREV, TIME et LTIME. De plus, lors de la définition de l'expression RPN, la source de données COMPUTE ne peut faire référence qu'aux noms des sources de données listées précédemment dans la commande create. Ceci est similaire à la restriction que les CDEF ne doivent faire référence qu'aux DEF et CDEF précédemment définis dans la même commande graph.

Lors du pré-remplissage du nouveau fichier RRD à l'aide d'une ou plusieurs RRD sources, la spécification DS peut contenir un mappage optionnel après le nom DS. Il prend la forme d'un signe égal suivi d'un nom de DS mappé et d'un index de source optionnel entre crochets.

Par exemple, la DS

DS:a=b[2]:GAUGE:120:0:U

spécifie que la DS nommée a doit être pré-remplie à partir de la DS nommée b dans le deuxième fichier source listé (les index de source sont basés sur 1).

RRA:CF:arguments de cf

Le but d'un RRD est de stocker des données dans les archives rondes (RRA). Une archive se compose d'un certain nombre de valeurs de données ou de statistiques pour chacune des sources de données (DS) définies et est définie avec une ligne RRA.

Lorsque les données sont entrées dans un RRD, elles sont d'abord intégrées dans des créneaux horaires de la longueur définie avec l'option -s, devenant ainsi un point de données primaire.

Les données sont également traitées avec la fonction de consolidation (CF) de l'archive. Il existe plusieurs fonctions de consolidation qui consolident les points de données primaires via une fonction d'agrégation : AVERAGE, MIN, MAX, LAST.

AVERAGE
la moyenne des points de données est stockée.
MIN
le plus petit des points de données est stocké.
MAX
le plus grand des points de données est stocké.
LAST
le dernier point de données est utilisé.

Notez que l'agrégation de données entraîne inévitablement une perte de précision et d'informations. L'astuce consiste à choisir la fonction d'agrégation de telle sorte que les propriétés intéressantes de vos données soient conservées tout au long du processus d'agrégation.

Le format de la ligne RRA pour ces fonctions de consolidation est :

RRA:{AVERAGE | MIN | MAX | LAST}:xff:steps:rows

xff Le facteur xfiles définit quelle partie d'un intervalle de consolidation peut être composée de données *INCONNUES* tant que la valeur consolidée est toujours considérée comme connue. Il est donné comme le ratio des PDP *INCONNU* autorisés au nombre de PDP dans l'intervalle. Ainsi, il varie de 0 à 1 (exclus).

steps définit combien de ces points de données primaires sont utilisés pour construire un point de données consolidé qui va ensuite dans l'archive. Voir aussi "STEP, HEARTBEAT, et Rows As Durations".

rows définit combien de générations de valeurs de données sont conservées dans un RRA. Évidemment, cela doit être supérieur à zéro. Voir aussi "STEP, HEARTBEAT, et Rows As Durations".

Détection de Comportement Aberrant avec Prévisions Holt-Winters

En plus des fonctions d'agrégation, il existe un ensemble de fonctions spécialisées qui permettent à RRDtool de fournir lissage de données (via l'algorithme de prévision Holt-Winters), bandes de confiance, et le signalement de comportements aberrants dans la série temporelle des sources de données :

  • RRA:HWPREDICT:rows:alpha:beta:période saisonnière[:rra-num]
  • RRA:MHWPREDICT:rows:alpha:beta:période saisonnière[:rra-num]
  • RRA:SEASONAL:période saisonnière:gamma:rra-num[:smoothing-window=fraction]
  • RRA:DEVSEASONAL:période saisonnière:gamma:rra-num[:smoothing-window=fraction]
  • RRA:DEVPREDICT:rows:rra-num
  • RRA:FAILURES:rows:seuil:longueur de fenêtre:rra-num

Ces RRAs diffèrent des fonctions de consolidation réelles de plusieurs manières. Premièrement, chacun des RRA est mis à jour une fois pour chaque point de données primaire. Deuxièmement, ces RRAs sont interdépendants. Pour générer des intervalles de confiance en temps réel, un ensemble correspondant de SEASONAL, DEVSEASONAL, DEVPREDICT, et soit HWPREDICT soit MHWPREDICT doit exister. La génération de valeurs lissées des points de données primaires nécessite un RRA SEASONAL et soit un RRA HWPREDICT soit MHWPREDICT. La détection de comportements aberrants nécessite FAILURES, DEVSEASONAL, SEASONAL, et soit HWPREDICT soit MHWPREDICT.

Les valeurs prédites ou lissées sont stockées dans le RRA HWPREDICT ou MHWPREDICT. HWPREDICT et MHWPREDICT sont en fait deux variations de la méthode Holt-Winters. Ils sont interchangeables. Tous deux tentent de décomposer les données en trois composantes : une ligne de base, une tendance et un coefficient saisonnier. HWPREDICT ajoute son coefficient saisonnier à la ligne de base pour former une prédiction, tandis que MHWPREDICT multiplie son coefficient saisonnier par la ligne de base pour former une prédiction. La différence est notable lorsque la ligne de base change significativement au cours d'une saison ; HWPREDICT prédira que la saisonnalité reste constante lorsque la ligne de base change, mais MHWPREDICT prédira que la saisonnalité augmente ou diminue proportionnellement à la ligne de base. Le choix approprié de la méthode dépend de ce qui est modélisé. Pour simplifier, le reste de cette discussion fera référence à HWPREDICT, mais MHWPREDICT peut être substitué à sa place.

Les écarts prédits sont stockés dans DEVPREDICT (pensez à un écart type qui peut être mis à l'échelle pour donner une bande de confiance). Le RRA FAILURES stocke des indicateurs binaires. Un 1 marque l'observation indexée comme un échec ; c'est-à-dire que le nombre de violations des intervalles de confiance dans la fenêtre d'observations précédente a atteint ou dépassé un seuil spécifié. Un exemple d'utilisation de ces RRAs pour tracer les intervalles de confiance et les échecs apparaît dans rrdgraph.

Les RRAs SEASONAL et DEVSEASONAL stockent les coefficients saisonniers pour l'algorithme de prévision Holt-Winters et les écarts saisonniers, respectivement. Il y a une entrée par point de temps d'observation dans le cycle saisonnier. Par exemple, si les points de données primaires sont générés toutes les cinq minutes et que le cycle saisonnier est de 1 jour, SEASONAL et DEVSEASONAL auront 288 lignes.

Afin de simplifier la création pour l'utilisateur novice, en plus de prendre en charge

rting la création explicite des RRA HWPREDICT, SEASONAL, DEVPREDICT, DEVSEASONAL et FAILURES, la commande RRDtool create prend en charge la création implicite des quatre autres lorsque HWPREDICT est spécifié seul et que l'argument final rra-num est omis.

rows spécifie la longueur du RRA avant le retour à la ligne. N'oubliez pas qu'il existe une correspondance un-à-un entre les points de données primaires et les entrées de ces RRA. Pour le CF HWPREDICT, rows doit être supérieur à la période saisonnière. Si le RRA DEVPREDICT est créé implicitement, le nombre de lignes par défaut est le même que l'argument rows de HWPREDICT. Si le RRA FAILURES est créé implicitement, rows sera défini sur l'argument période saisonnière du RRA HWPREDICT. Bien sûr, la commande RRDtool resize est disponible si ces valeurs par défaut ne sont pas suffisantes et que le créateur souhaite éviter la création explicite des autres RRA de fonction spécialisés.

seasonal period spécifie le nombre de points de données primaires dans un cycle saisonnier. Si SEASONAL et DEVSEASONAL sont créés implicitement, cet argument pour ces RRA est automatiquement défini sur la valeur spécifiée par HWPREDICT. S'ils sont créés explicitement, le créateur doit vérifier que les trois arguments seasonal period correspondent.

alpha est le paramètre d'adaptation du coefficient d'intercept (ou de base) dans l'algorithme de prévision de Holt-Winters. Voir rrdtool pour une description de cet algorithme. alpha doit être compris entre 0 et 1. Une valeur plus proche de 1 signifie que les observations les plus récentes portent plus de poids dans la prévision de la composante de base des prévisions. Une valeur plus proche de 0 signifie que l'historique porte plus de poids dans la prévision de la composante de base.

beta est le paramètre d'adaptation du coefficient de pente (ou de tendance linéaire) dans l'algorithme de prévision de Holt-Winters. beta doit être compris entre 0 et 1 et joue le même rôle qu'alpha par rapport à la tendance linéaire prédite.

gamma est le paramètre d'adaptation des coefficients saisonniers dans l'algorithme de prévision de Holt-Winters (HWPREDICT) ou le paramètre d'adaptation de la mise à jour par lissage exponentiel des écarts saisonniers. Il doit être compris entre 0 et 1. Si les RRA SEASONAL et DEVSEASONAL sont créés implicitement, ils auront tous deux la même valeur pour gamma : la valeur spécifiée pour l'argument alpha de HWPREDICT. Notez que, comme il y a un coefficient saisonnier (ou un écart) pour chaque point temporel du cycle saisonnier, le taux d'adaptation est beaucoup plus lent que celui de la base. Chaque coefficient saisonnier n'est mis à jour (ou n'adapte) que lorsque la valeur observée se produit au décalage dans le cycle saisonnier correspondant à ce coefficient.

Si les RRA SEASONAL et DEVSEASONAL sont créés explicitement, gamma n'a pas besoin d'être le même pour les deux. Notez que gamma peut également être modifié via la commande RRDtool tune.

smoothing-window spécifie la fraction d'une saison qui doit être moyennée autour de chaque point. Par défaut, la valeur de smoothing-window est de 0,05, ce qui signifie que chaque valeur dans SEASONAL et DEVSEASONAL sera occasionnellement remplacée par la moyenne avec ses voisins les plus proches (*seasonal period* * 0,05). Le réglage de smoothing-window sur zéro désactivera complètement le lisseur de moyenne mobile.

rra-num établit les liens entre les RRA apparentés. Si HWPREDICT est spécifié seul et que les autres RRA sont créés implicitement, il n'y a pas lieu de s'inquiéter de cet argument. Si les RRA sont créés explicitement, portez une attention particulière à cet argument. Pour chaque RRA qui inclut cet argument, il existe une dépendance entre ce RRA et un autre RRA. L'argument rra-num est l'index basé sur 1 dans l'ordre de création des RRA (c'est-à-dire l'ordre dans lequel ils apparaissent dans la commande create). Le RRA dépendant pour chaque RRA nécessitant l'argument rra-num est listé ici :

  • HWPREDICT rra-num est l'index du RRA SEASONAL.
  • SEASONAL rra-num est l'index du RRA HWPREDICT.
  • DEVPREDICT rra-num est l'index du RRA DEVSEASONAL.
  • DEVSEASONAL rra-num est l'index du RRA HWPREDICT.
  • FAILURES rra-num est l'index du RRA DEVSEASONAL.

threshold est le nombre minimum de violations (valeurs observées en dehors des limites de confiance) dans une fenêtre qui constitue un échec. Si le RRA FAILURES est créé implicitement, la valeur par défaut est 7.

window length est le nombre de points temporels dans la fenêtre. Spécifiez un entier supérieur ou égal au seuil et inférieur ou égal à 28. L'intervalle de temps que cette fenêtre représente dépend de l'intervalle entre les points de données primaires. Si le RRA FAILURES est créé implicitement, la valeur par défaut est 9.

STEP, HEARTBEAT, et Rows en tant que Durées

Traditionnellement, RRDtool spécifiait les intervalles PDP en secondes, et la plupart des autres valeurs comme des secondes ou des comptes PDP. Cela rendait la spécification des bases de données plutôt opaque ; par exemple

rrdtool create power.rrd \
  --start now-2h --step 1 \
  DS:watts:GAUGE:300:0:24000 \
  RRA:AVERAGE:0.5:1:864000 \
  RRA:AVERAGE:0.5:60:129600 \
  RRA:AVERAGE:0.5:3600:13392 \
  RRA:AVERAGE:0.5:86400:3660

crée une base de données de valeurs de puissance collectées une fois par seconde, avec un heartbeat de cinq minutes (300 secondes), et quatre RRA : dix jours d'une seconde, 90 jours d'une minute, 18 mois d'une heure, et dix ans de moyennes journalières.

Les étapes, les heartbeats, et les comptes PDP et les lignes peuvent également être spécifiés comme des durées, qui sont des entiers positifs avec un suffixe d'un seul caractère qui spécifie un facteur d'échelle. Voir "rrd_scaled_duration" dans librrd pour les facteurs d'échelle des suffixes pris en charge : "s" (secondes), "m" (minutes), "h" (heures), "d" (jours), "w" (semaines), "M" (mois), et "y" (années).

Les valeurs d'étape et de heartbeat mises à l'échelle (qui sont nativement des durées en secondes) sont utilisées directement, tandis que les arguments de ligne de la fonction de consolidation sont divisés par leur étape pour produire le nombre de lignes.

Avec cette fonctionnalité, la même spécification que ci-dessus peut être écrite comme suit :

rrdtool create power.rrd \
  --start now-2h --step 1s \
  DS:watts:GAUGE:5m:0:24000 \
  RRA:AVERAGE:0.5:1s:10d \
  RRA:AVERAGE:0.5:1m:90d \
  RRA:AVERAGE:0.5:1h:18M \
  RRA:AVERAGE:0.5:1d:10y

Le HEARTBEAT et le STEP

Voici une explication de Don Baarda sur le fonctionnement interne de RRDtool. Cela pourrait vous aider à comprendre pourquoi toutes ces données *UNKNOWN* apparaissent dans vos bases de données :

RRDtool reçoit des échantillons/mises à jour à des moments arbitraires. À partir de ceux-ci, il construit des Points de Données Primaires (PDP) à chaque intervalle de "step". Les PDP sont ensuite accumulés dans les RRA.

Le "heartbeat" définit l'intervalle maximum acceptable entre les échantillons/mises à jour. Si l'intervalle entre les échantillons est inférieur au "heartbeat", un taux moyen est calculé et appliqué pour cet intervalle. Si l'intervalle entre les échantillons est supérieur au "heartbeat", cet intervalle entier est considéré comme "inconnu". Notez que d'autres choses peuvent rendre un intervalle d'échantillon "inconnu", comme le dépassement des limites du taux, ou un échantillon qui a été explicitement marqué comme inconnu.

Les taux connus pendant l'intervalle de "step" d'un PDP sont utilisés pour calculer un taux moyen pour ce PDP. Si le temps total "inconnu" représente plus de la moitié du "step", le PDP entier est marqué comme "inconnu". Cela signifie qu'un mélange de temps d'échantillons connus et "inconnus" dans un seul "step" de PDP peut ou non s'additionner à suffisamment de temps "connu" pour justifier un PDP connu.

Le "heartbeat" peut être court (inhabituel) ou long (typique) par rapport à l'intervalle de "step" entre les PDP. Un "heartbeat" court signifie que vous exigez plusieurs échantillons par PDP, et si vous ne les obtenez pas, vous marquez le PDP comme inconnu. Un heartbeat long peut couvrir plusieurs "steps", ce qui signifie qu'il est acceptable d'avoir plusieurs PDP calculés à partir d'un seul échantillon. Un exemple extrême pourrait être un "step" de 5 minutes et un "heartbeat" d'une journée, auquel cas un seul échantillon par jour entraînera la définition de tous les PDP de cette journée entière au même taux moyen. -- Don Baarda <don.baarda@baesystems.com>

rrdcreate(1) — Arch Linux man pages

NAME

rrdcreate

create Round Robin Database files

SYNOPSIS

rrdtool create filename [options] [data-source definitions] [round-robin-archive definitions]

DESCRIPTION

The rrdcreate command is used to create a new Round Robin Database (RRD) file. An RRD file stores time-series data. This command initializes the file and defines the data sources and archives that will store the data.

--step step: This option specifies the time interval in seconds between data points. All data points are expected to arrive at intervals that are multiples of this step size. The default is 300 seconds (5 minutes).

--start start: This option specifies the start time for the RRD file, in Unix timestamp format. If not specified, the current time is used.

DS:name:type:heartbeat:min:max This defines a data source.

  • name: The name of the data source (e.g., 'cpu_usage', 'network_traffic').
  • type: The type of data. Common types include:
    • GAUGE: A value that can go up and down (e.g., temperature, memory usage).
    • COUNTER: A value that always increases (e.g., bytes sent, packets received). It is assumed that the counter wraps around to zero when it reaches its maximum value.
    • DERIVE: Similar to COUNTER, but it is assumed that the counter might be reset to zero (e.g., a counter that is reset when a process is restarted).
    • ABSOLUTE: A counter that is reset to zero for each update.
  • heartbeat: The maximum time in seconds allowed between updates for this data source. If this interval is exceeded, the data is considered *UNKNOWN*.
  • min: The minimum acceptable value for this data source. 'U' (or 'u') means undefined (no minimum).
  • max: The maximum acceptable value for this data source. 'U' (or 'u') means undefined (no maximum).

RRA:type:xff:steps:rows This defines a Round Robin Archive.

  • type: The type of consolidation function. Common types include:
    • AVERAGE: Stores the average of the data points that fall into the archive interval.
    • MINIMUM: Stores the minimum of the data points.
    • MAXIMUM: Stores the maximum of the data points.
    • LAST: Stores the last data point.
    • HWPREDICT: Holt-Winters forecasting parameters.
    • SEASONAL: Seasonal components for Holt-Winters.
    • DEVSEASONAL: Seasonal deviation for Holt-Winters.
    • DEVPREDICT: Predicted deviation for Holt-Winters.
    • FAILURES: Count of failures for Holt-Winters.
  • xff: The "xFiles Factor", a value between 0 and 1 (exclusive). This defines the percentage of data points that must be known (not *UNKNOWN*) for the consolidated value to be considered known. If the percentage of *UNKNOWN* data is greater than (1 - xff), the consolidated value will be *UNKNOWN*. A value of 0.5 is common.
  • steps: This parameter determines the interval over which data is consolidated. It is the number of step intervals from the data source definition. For example, if the step is 300 seconds and steps is 12, then data is consolidated every 12 * 300 = 3600 seconds (1 hour).
  • rows: The number of data points to store in this archive. The total time covered by the archive is rows * steps * step.

COMPUTE:name:rpn_expression This defines a computed data source. The value of this data source is calculated using an RPN (Reverse Polish Notation) expression based on other data sources. The expression can use standard arithmetic operators and functions.

Aberrant Behavior Detection with Holt-Winters Forecasting

RRDtool includes support for forecasting and detecting aberrant behavior using the Holt-Winters method. This is achieved through specialized RRA types like HWPREDICT, SEASONAL, DEVSEASONAL, DEVPREDICT, and FAILURES. These RRAs allow you to predict future values and identify significant deviations from the expected pattern. The parameters for these RRAs control the adaptation rate, seasonal cycle length, and prediction horizons.

STEP, HEARTBEAT, and Rows As Durations

The --step option defines the basic time interval for data collection. The heartbeat parameter for each data source defines the maximum allowed time between updates before the data is considered unknown. The rows parameter in RRA definitions, when multiplied by steps and step, determines the total duration covered by the archive.

The HEARTBEAT and the STEP

The relationship between the data source heartbeat and the --step interval is crucial. The heartbeat should generally be set to a multiple of the step size, often twice the step size. This allows for some flexibility in data arrival times without immediately marking data as unknown.

HOW TO MEASURE

When working with RRDtool, it's important to understand how it stores data. RRDtool primarily stores rates (amount per second) for COUNTER, DERIVE, and ABSOLUTE data types. To obtain absolute values for a given period (e.g., total messages in a day), you can retrieve the average rate per second for that day from RRDtool and multiply it by the number of seconds in the day. Since calculations are performed using doubles, the precision is generally sufficient.

It's important to note that RRDtool is designed for plotting rates and trends, not necessarily for absolute totals like "total bytes sent". For plotting absolute amounts, especially where the time delta is critical for interpretation (like daily totals), using a different tool that explicitly visualizes time intervals might be more appropriate.

EXAMPLE

rrdtool create temperature.rrd --step 300 \
 DS:temp:GAUGE:600:-273:5000 \
 RRA:AVERAGE:0.5:1:1200 \
 RRA:MIN:0.5:12:2400 \
 RRA:MAX:0.5:12:2400 \
 RRA:AVERAGE:0.5:12:2400

This sets up an RRD called temperature.rrd which accepts one temperature value every 300 seconds. If no new data is supplied for more than 600 seconds, the temperature becomes *UNKNOWN*. The minimum acceptable value is -273 and the maximum is 5'000.

A few archive areas are also defined. The first stores the temperatures supplied for 100 hours (1'200 * 300 seconds = 100 hours). The second RRA stores the minimum temperature recorded over every hour (12 * 300 seconds = 1 hour), for 100 days (2'400 hours). The third and the fourth RRA's do the same for the maximum and average temperature, respectively.

EXAMPLE 2

rrdtool create monitor.rrd --step 300        \
  DS:ifOutOctets:COUNTER:1800:0:4294967295   \
  RRA:AVERAGE:0.5:1:2016                     \
  RRA:HWPREDICT:1440:0.1:0.0035:288

This example is a monitor of a router interface. The first RRA tracks the traffic flow in octets; the second RRA generates the specialized functions RRAs for aberrant behavior detection. Note that the rra-num argument of HWPREDICT is missing, so the other RRAs will implicitly be created with default parameter values. In this example, the forecasting algorithm baseline adapts quickly; in fact the most recent one hour of observations (each at 5 minute intervals) accounts for 75% of the baseline prediction. The linear trend forecast adapts much more slowly. Observations made during the last day (at 288 observations per day) account for only 65% of the predicted linear trend. Note: these computations rely on an exponential smoothing formula described in the LISA 2000 paper.

The seasonal cycle is one day (288 data points at 300 second intervals), and the seasonal adaption parameter will be set to 0.1. The RRD file will store 5 days (1'440 data points) of forecasts and deviation predictions before wrap around. The file will store 1 day (a seasonal cycle) of 0-1 indicators in the FAILURES RRA.

The same RRD file and RRAs are created with the following command, which explicitly creates all specialized function RRAs using "STEP, HEARTBEAT, and Rows As Durations".

rrdtool create monitor.rrd --step 5m \
  DS:ifOutOctets:COUNTER:30m:0:4294967295 \
  RRA:AVERAGE:0.5:1:2016 \
  RRA:HWPREDICT:5d:0.1:0.0035:1d:3 \
  RRA:SEASONAL:1d:0.1:2 \
  RRA:DEVSEASONAL:1d:0.1:2 \
  RRA:DEVPREDICT:5d:5 \
  RRA:FAILURES:1d:7:9:5

Of course, explicit creation need not replicate implicit create, a number of arguments could be changed.

EXAMPLE 3

rrdtool create proxy.rrd --step 300 \
  DS:Requests:DERIVE:1800:0:U  \
  DS:Duration:DERIVE:1800:0:U  \
  DS:AvgReqDur:COMPUTE:Duration,Requests,0,EQ,1,Requests,IF,/ \
  RRA:AVERAGE:0.5:1:2016

This example is monitoring the average request duration during each 300 sec interval for requests processed by a web proxy during the interval. In this case, the proxy exposes two counters, the number of requests processed since boot and the total cumulative duration of all processed requests. Clearly these counters both have some rollover point, but using the DERIVE data source also handles the reset that occurs when the web proxy is stopped and restarted.

In the RRD, the first data source stores the requests per second rate during the interval. The second data source stores the total duration of all requests processed during the interval divided by 300. The COMPUTE data source divides each PDP of the AccumDuration by the corresponding PDP of TotalRequests and stores the average request duration. The remainder of the RPN expression handles the divide by zero case.

SECURITY

Note that new rrd files will have the permission 0644 regardless of your umask setting. If a file with the same name previously exists, its permission settings will be copied to the new file.
