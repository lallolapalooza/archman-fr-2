NOM

rrdcached - Démon de mise en cache des données pour rrdtool

SYNOPSIS

rrdcached [-a taille_alloc] [-b rép_base [-B]] [-F] [-f délai] [-G groupe]] [-g] [-j rép_journal] [-L] [-l adresse] [-m mode] [-O] [-o fichier_log] [-P permissions] [-p fichier_pid] [-R] [-s groupe] [-t threads_écriture] [-U utilisateur]] [-V niveau_log] [-w délai] [-z retard]

DESCRIPTION

rrdcached est un démon qui reçoit les mises à jour des fichiers RRD existants, les accumule et, si suffisamment de mises à jour ont été reçues ou si un temps défini s'est écoulé, écrit les mises à jour dans le fichier RRD. Une commande flush peut être utilisée pour forcer l'écriture des valeurs sur disque, afin que les installations de graphiques et similaires puissent travailler avec des données à jour.

Le démon a été écrit en pensant aux grandes configurations. Ces configurations rencontrent généralement des problèmes liés aux E/S tôt ou tard pour des raisons qui sortent du cadre de ce document. Consultez le wiki sur la page d'accueil de RRDtool pour plus de détails. Lisez également "CONSIDÉRATIONS DE SÉCURITÉ" ci-dessous avant d'utiliser ce démon ! Une description détaillée du fonctionnement du démon se trouve dans la section "COMMENT ÇA MARCHE" ci-dessous.

OPTIONS

-l adresse
Indique au démon de se lier à adresse et d'accepter les connexions TCP entrantes sur ce socket. Si adresse commence par "unix:", tout ce qui suit ce préfixe est interprété comme le chemin d'un socket de domaine UNIX. Sinon, l'adresse ou le nom d'hôte sont résolus à l'aide de "getaddrinfo()".

Pour les sockets réseau, un port peut être spécifié en utilisant le format "[adresse]:port". Si l'adresse est une adresse IPv4 ou un nom de domaine entièrement qualifié (c.-à-d. que l'adresse contient au moins un point (".")), les crochets peuvent être omis, résultant en le modèle (plus simple) "adresse:port". Le port par défaut est 42217. Si vous spécifiez un socket réseau, il est impératif de lire la section "CONSIDÉRATIONS DE SÉCURITÉ".

Les formats suivants sont acceptés. Veuillez noter que l'adresse du socket UNIX doit commencer par un slash dans le second cas !

unix:</chemin/vers/unix.sock>
/<chemin/vers/unix.sock>
<nom_hote_ou_ip>
[<nom_hote_ou_ip>]:<port>
<nom_hote_ou_ipv4>:<port>

Si un port est spécifié sans hôte (par exemple "-l :42217"), le démon écoutera sur ce port sur toutes les interfaces réseau. Utilisez "-L" pour éviter d'avoir à spécifier explicitement le port si le port par défaut est souhaité.

Si aucune option -l n'est spécifiée, l'adresse par défaut, "unix:/tmp/rrdcached.sock", sera utilisée. Plusieurs options -l peuvent être fournies.

-L
Indique au démon de se lier au port TCP par défaut sur toutes les interfaces disponibles. Ceci est équivalent à "-l ''" sans la confusion du paramètre de chaîne vide.
-s nom_groupe|gid
Définit les permissions du groupe d'un socket de domaine UNIX. L'option accepte soit un identifiant de groupe numérique, soit un nom de groupe. Ce groupe aura alors les permissions de lecture et d'écriture (le socket aura les permissions de fichier 0760) et sera donc capable d'envoyer des commandes au démon. Cela peut être utile dans les cas où vous ne pouvez pas facilement exécuter tous les processus RRD avec les mêmes privilèges utilisateur (par exemple, les scripts CGI générant des graphiques qui s'exécutent généralement dans le contexte de permissions du serveur web).

Cette option affecte les adresses de socket UNIX suivantes (les options -l suivantes) ou le socket par défaut (si aucune option -l n'a été spécifiée), c'est-à-dire que vous pouvez spécifier des paramètres différents pour différents sockets.

Par défaut, l'appartenance ou les permissions du socket ne sont pas modifiées et utilisent donc les paramètres par défaut du système.

-m mode
Définit les permissions du fichier d'un socket de domaine UNIX. L'option accepte un nombre octal représentant le motif binaire du mode (voir chmod(1) pour plus de détails).

Veuillez noter que tous les systèmes ne respectent pas ce paramètre. Sous Linux, les permissions de lecture/écriture sont requises pour se connecter à un socket UNIX. Cependant, de nombreux systèmes dérivés de BSD ignorent les permissions pour les sockets UNIX. Voir unix(7) pour plus de détails.

Cette option affecte les adresses de socket UNIX suivantes (les options -l suivantes) ou le socket par défaut (si aucune option -l n'a été spécifiée), c'est-à-dire que vous pouvez spécifier des paramètres différents pour différents sockets.

Par défaut, l'appartenance ou les permissions du socket ne sont pas modifiées et utilisent donc les paramètres par défaut du système.

-P commande[,commande[,...]]
Spécifie les commandes acceptées via un socket réseau et un socket UNIX. Cela permet aux administrateurs de RRDCacheD de contrôler les actions acceptées depuis différentes sources.

Les arguments fournis à l'option -P sont une liste de commandes séparées par des virgules. Par exemple, pour autoriser les commandes "FLUSH" et "PENDING", on pourrait spécifier :

rrdcached -P FLUSH,PENDING $PLUS_ARGUMENTS

L'option -P affecte les adresses de socket suivantes (les options -l suivantes) ou le socket par défaut (si aucune option -l n'a été spécifiée). Dans l'exemple suivant, seul le socket réseau IPv4 (adresse 10.0.0.1) sera limité aux commandes "FLUSH" et "PENDING" :

rrdcached -l unix:/chemin/quelconque -P FLUSH,PENDING -l 10.0.0.1

Une liste complète des commandes disponibles se trouve dans la section "Commandes valides" ci-dessous. Il y a deux exceptions mineures :

  • Les commandes "HELP" et "QUIT" sont toujours autorisées.
  • Si la commande "BATCH" est acceptée, la commande . sera automatiquement acceptée aussi.

Veuillez également lire "CONSIDÉRATIONS DE SÉCURITÉ" ci-dessous.

-V niveau_log
rrdcached sous forte charge peut inonder les journaux. Cette option en ligne de commande spécifie le niveau de journalisation maximum à utiliser, ce qui signifie qu'un message dont la verbosité est supérieure au niveau_log est masqué (LOG_EMERG étant le plus bas et LOG_DEBUG le plus haut).

Valeurs acceptées pour "niveau_log" (de la moins à la plus verbosité) : LOG_EMERG, LOG_ALERT, LOG_CRIT, LOG_ERR, LOG_WARNING, LOG_NOTICE, LOG_INFO, LOG_DEBUG

Niveau de journalisation par défaut lorsque cet indicateur est ABSENT : LOG_ERR

Voir aussi : syslog.h

-o fichier_log
Journalise dans le fichier donné au lieu de syslog.
-w délai
Les données sont écrites sur disque toutes les délai secondes. Un suffixe optionnel peut être utilisé (par exemple "5m" au lieu de 300 secondes). Si cette option n'est pas spécifiée, l'intervalle par défaut de 300 secondes sera utilisé.
-z retard
Si spéci

OPTIONS

-w timeout
rrdcached retardera l'écriture de chaque RRD d'un nombre aléatoire de secondes dans l'intervalle [0,delay). Cela évite que trop d'écritures soient mises en file d'attente simultanément. Cette valeur ne devrait pas dépasser la valeur spécifiée avec -w. Un suffixe optionnel peut être utilisé (par exemple, "3m" au lieu de 180 secondes). Par défaut, il n'y a aucun délai.
-f timeout
Toutes les timeout secondes, le cache entier est recherché pour y trouver de vieilles valeurs qui sont écrites sur le disque. Cela ne concerne que les fichiers auxquels les mises à jour ont cessé d'être appliquées, donc régler cette valeur à un grand nombre, tel que 3600 secondes, est acceptable dans la plupart des cas. Un suffixe optionnel peut être utilisé (par exemple, "1h" au lieu de 3600 secondes). Ce délai d'expiration est de 3600 secondes par défaut.
-p fichier
Définit le nom et l'emplacement du fichier PID. Si non spécifié, le fichier par défaut, "$localstatedir/run/rrdcached.pid" sera utilisé.
-t threads_ecriture
Spécifie le nombre de threads utilisés pour écrire les fichiers RRD. La valeur par défaut est 4. Augmenter ce nombre permettra à rrdcached d'avoir plus de requêtes d'E/S simultanées vers le noyau. Cela peut permettre au noyau de réorganiser les écritures sur disque, résultant en un meilleur débit disque.
-j rep
Écrit les mises à jour dans un journal dans le répertoire rep. En cas de crash du programme ou du système, cela permettra au démon d'écrire toutes les mises à jour en attente au moment du crash.

Au démarrage, le démon vérifiera la présence de fichiers journaux dans ce répertoire. S'ils sont trouvés, toutes les mises à jour qu'ils contiennent seront lues en mémoire avant que le démon ne commence à accepter de nouvelles connexions.

Le journal sera utilisé de manière cyclique avec la même fréquence que le minuteur de vidage spécifié par -f.

Lorsque la journalisation est activée, le démon utilisera une procédure d'arrêt rapide. Au lieu de vider tous les fichiers sur le disque, il s'assurera que le journal est correctement écrit et se terminera immédiatement. Bien que les fichiers de données RRD ne soient pas complètement à jour, aucune information n'est perdue ; toutes les mises à jour en attente seront rejouées à partir du journal la prochaine fois que le démon démarrera.

Pour désactiver l'arrêt rapide, utilisez l'option -F.

-F
Vider TOUJOURS toutes les mises à jour vers les fichiers de données RRD lors de l'arrêt du démon, quel que soit le réglage du journal.
-g
Exécuter en premier plan. Le démon ne fera pas de fork().
-b rep
Le démon changera de répertoire au démarrage. Tous les fichiers passés au démon, spécifiés par un chemin relatif, seront interprétés comme étant relatifs à ce répertoire. Si non spécifié, le répertoire par défaut, "/tmp", sera utilisé. 
+------------------------+------------------------+
! Commande ligne         ! Fichier mis à jour     !
+------------------------+------------------------+
! foo.rrd                ! /tmp/foo.rrd           !
! foo/bar.rrd            ! /tmp/foo/bar.rrd       !
! /var/lib/rrd/foo.rrd   ! /var/lib/rrd/foo.rrd   !
+------------------------+------------------------+
Chemins donnés en ligne de commande et chemins réellement
mis à jour par le démon, en supposant le répertoire de base
"/tmp".

ATTENTION : Les chemins jusqu'au répertoire de base inclus NE DOIVENT PAS ÊTRE de liens symboliques. En d'autres termes, si le répertoire de base est spécifié comme suit :

-b /base/dir/somewhere

... alors AUCUN des éléments suivants ne doit être un lien symbolique :

/base
/base/dir
/base/dir/somewhere
-B
N'autoriser que les écritures dans le répertoire de base spécifié avec -b (et tous les sous-répertoires). Cela ne détecte PAS les liens symboliques. Les chemins contenant "../" seront également bloqués.
-R
Autoriser la création récursive de sous-répertoires dans le répertoire de base spécifié avec -b (et tous les sous-répertoires). Ne peut être utilisé que lorsque -B est également défini.
-a taille_alloc
Alloue des pointeurs de valeurs par blocs de taille_alloc. Cela peut améliorer l'utilisation du CPU sur les machines avec des implémentations "realloc()" lentes, au détriment d'une utilisation mémoire légèrement plus élevée. La valeur par défaut est 1. Ne réglez pas cette valeur plus haut que la valeur de -w divisée par la taille moyenne de l'étape RRD.
-O
Empêcher la commande CREATE de réécraser les fichiers existants, même lorsqu'elle y est invitée. C'est pour une sécurité accrue.
-G -groupe
Lorsqu'il s'exécute en tant que démon et qu'il est invoqué depuis un compte privilégié, réinitialise les privilèges de groupe à ceux de groupe. Le groupe peut être spécifié par son nom ou par son ID de groupe. Le démon se terminera avec un message de diagnostic s'il ne parvient pas à passer au groupe spécifié.
-U -utilisateur
Lorsqu'il s'exécute en tant que démon et qu'il est invoqué depuis un compte privilégié, réinitialise les privilèges utilisateur à ceux de utilisateur. L'utilisateur peut être spécifié par son nom ou par son ID utilisateur. Le démon se terminera avec un message de diagnostic s'il ne parvient pas à passer à l'utilisateur spécifié.

La commande update peut envoyer des valeurs au démon au lieu de les écrire sur le disque elle-même. Toutes les autres commandes peuvent envoyer une commande FLUSH (voir ci-dessous) au démon avant d'accéder aux fichiers, afin qu'elles fonctionnent avec des données à jour même si le délai d'expiration du cache est important.

SIGNALEMENT DES ERREURS

Le démon signale les erreurs de deux manières : Au démarrage, les messages d'erreur sont imprimés sur "STDERR". Une des étapes du démarrage consiste à se séparer en arrière-plan et à fermer "STDERR" - après cela, écrire directement à l'utilisateur n'est plus possible. Une fois cela fait, le démon enverra des messages de journalisation au démon de journalisation système en utilisant syslog(3). Le service utilisé est "LOG_DAEMON".

COMMENT ÇA MARCHE

Lorsqu'il reçoit une mise à jour, rrdcached n'écrit pas sur le disque mais recherche une entrée pour ce fichier dans son arbre interne. Si aucune entrée n'est trouvée, une entrée est créée incluant l'heure actuelle (appelée "First" dans le schéma ci-dessous). Cette heure n'est pas l'heure spécifiée dans la ligne de commande, mais l'heure que le système d'exploitation considère comme "maintenant". La valeur et l'heure de la valeur (appelées "Time" dans le schéma ci-dessous) sont ajoutées au nœud de l'arbre.

Lors de l'ajout d'une valeur à un nœud d'arbre, on vérifie s'il est temps d'écrire les valeurs sur disque. Les valeurs sont écrites sur disque si "maintenant() - First >= timeout", où "timeout" est le délai spécifié à l'aide de l'option -w, voir "OPTIONS". Si les valeurs sont "assez vieilles", elles seront mises en file d'attente dans la "file de mise à jour", c'est-à-dire qu'elles seront ajoutées à la liste chaînée illustrée ci-dessous. Étant donné que les nœuds de l'arbre et les éléments de la liste chaînée sont les mêmes structures de données en mémoire, toute mise à jour d'un fichier déjà mis en file d'attente sera également écrite lors de la prochaine écriture dans le fichier RRD.

Un "thread de mise à jour" distinct retire constamment le premier élément de la file de mise à jour et écrit toutes ses valeurs dans le fichier approprié. Ainsi, tant que la file de mise à jour n'est pas vide, les fichiers sont écrits au taux le plus élevé possible.

Étant donné que le délai d'expiration des fichiers n'est vérifié que lorsque de nouvelles valeurs sont ajoutées au fichier, les fichiers "morts", c'est-à-dire les fichiers qui ne sont plus mis à jour, ne seraient jamais écrits sur disque. Par conséquent, de temps en temps, contrôlé par l'option -f, l'arbre entier est parcouru et toutes les valeurs "anciennes" sont mises en file d'attente. Comme cela n'affecte que les fichiers "morts" et que le parcours de l'arbre est relativement coûteux, vous devriez définir "l'intervalle de vidage" à une valeur raisonnablement élevée. La valeur par défaut est 3600 secondes (une heure).

Le revers de la mise en cache des valeurs est qu'elles n'apparaîtront pas dans les graphiques générés à partir des fichiers RRD. Pour contourner cela, le démon fournit la "commande de vidage" pour vider des fichiers spécifiques. Cela signifie que le fichier est inséré en tête de la file de mise à jour ou déplacé là s'il est déjà en file d'attente. La commande de vidage ne retournera qu'après que les mises à jour en attente du fichier auront été écrites sur disque.

CONSIDÉRATIONS DE SÉCURITÉ

Authentification

Si votre installation rrdtool a été compilée sans libwrap, il n'y a aucune forme d'authentification pour les clients se connectant au démon rrdcache !

Si votre installation rrdtool a été compilée avec libwrap, vous pouvez utiliser hosts_access pour restreindre l'accès des clients au démon rrdcache (rrdcached). Pour plus d'informations sur la façon d'utiliser hosts_access pour restreindre l'accès au démon rrdcache, vous devriez lire les pages de manuel hosts_access(5).

Il est toujours fortement recommandé d'installer un filtre de paquets ou un mécanisme similaire pour empêcher les connexions non autorisées. À moins que vous n'ayez un VLAN ou un VPN dédié pour cela, l'utilisation de sockets réseau est probablement une mauvaise idée !

Autorisation

Il y a une autorisation minimale par socket.

L'autorisation est actuellement effectuée par socket. Cela signifie que chaque socket a une liste de commandes qu'il acceptera. Il n'acceptera que les commandes explicitement listées, mais il acceptera (actuellement) ces commandes de quiconque accède au socket.

Si les sockets réseau doivent être utilisés, il est nécessaire de restreindre les commandes acceptées à celles dont les clients externes ont besoin. Si, par exemple, les clients externes souhaitent dessiner des graphiques des données mises en cache, ils ne devraient être autorisés à utiliser que la commande "FLUSH".

L'autorisation ne fonctionne pas lorsque rrdcached est activé par socket par systemd.

Chiffrement

Il n'y a pas de chiffrement.

Encore une fois, cela pourrait être ajouté à l'avenir, mais pour le moment, il vous appartient de garder vos données privées. Installez un VPN ou un tunnel chiffré si vos statistiques sont confidentielles !

Vérification de validité

Il n'y a pas de vérification de validité.

Le démon écrira aveuglément dans n'importe quel fichier qui lui est indiqué, vous devriez donc vraiment créer un utilisateur distinct juste pour ce démon. De plus, il n'effectue aucune vérification de validité, donc s'il reçoit l'ordre d'écrire des valeurs pour un temps très futur, vos fichiers seront bien corrompus !

Conclusion

  • La sécurité est le travail de l'administrateur.
  • Nous recommandons d'autoriser l'accès en écriture uniquement via les sockets de domaine UNIX.
  • Vous avez été prévenu.

PROTOCOLE

Le démon communique avec les clients à l'aide d'un protocole ASCII basé sur des lignes, facile à lire et facile à taper. Cela permet aux scripts d'implémenter facilement le protocole et aux utilisateurs de se connecter au démon avec telnet pour tester des choses « à la main ».

Le protocole est basé sur des lignes, ce qui signifie que chaque enregistrement se compose d'une ou plusieurs lignes. Une ligne est terminée par le caractère de saut de ligne 0x0A, couramment écrit comme "\n". Dans les exemples ci-dessous, ce caractère sera écrit comme "<LF>" (saut de ligne).

Après l'établissement de la connexion, le client est censé envoyer une « commande ». Une commande se compose du mot-clé de la commande, éventuellement de certains arguments, et d'un caractère de nouvelle ligne de terminaison. Pour une liste de commandes, voir « Commandes valides » ci-dessous.

Exemple :

FLUSH /tmp/foo.rrd<LF>

Le démon répond avec une ligne composée d'un code de statut et d'un court message de statut, séparés par un ou plusieurs espaces. Un code de statut négatif signale une erreur, un code de statut positif ou zéro signale un succès. Si le code de statut est supérieur à zéro, il indique le nombre de lignes qui suivent la ligne de statut.

Exemples :

0 Succès<LF>
2 Deux lignes suivent<LF>
Ceci est la première ligne<LF>
Et ceci est la deuxième ligne<LF>

Commandes valides

Les commandes suivantes sont comprises par le démon :

FLUSH nom_fichier
Force le démon à placer nom_fichier à la tête de la file d'attente de mise à jour (le déplaçant éventuellement là s'il est déjà en file d'attente). La réponse sera envoyée après que le nœud ait été retiré de la file d'attente.
FLUSHALL
Force le démon à commencer à vider TOUTES les valeurs en attente sur disque. Cela retourne immédiatement, même si les écritures peuvent prendre beaucoup de temps.
PENDING nom_fichier
Affiche les mises à jour « en attente » pour un fichier, dans l'ordre. Les mises à jour affichées n'ont pas encore été écrites dans le fichier RRD sous-jacent.
FETCH nom_fichier CF [début [fin] [ds ...]]
Appelle "rrd_fetch" avec les arguments spécifiés et renvoie le résultat sous forme de texte. Si nécessaire, le fichier est vidé sur disque au préalable. La fonction côté client "rrdc_fetch" (déclarée dans "rrd_client.h") analyse la sortie et se comporte exactement comme "rrd_fetch_r" pour une intégration facile des requêtes à distance. ds définit les colonnes à exporter - si aucune n'est donnée, toutes sont renvoyées.
FETCHBIN nom_fichier CF [début [fin] [ds ...]]
Appelle "rrd_fetch" avec les arguments spécifiés et renvoie le résultat sous forme texte/binaire pour éviter une surcharge inutile de sérialisation/désérialisation. Si nécessaire, le fichier est vidé sur disque au préalable. La fonction côté client "rrdc_fetch" (déclarée dans "rrd_client.h") analyse la sortie et se comporte exactement comme "rrd_fetch_r" pour une intégration facile des requêtes à distance. ds définit les colonnes à exporter - si aucune n'est donnée, toutes sont renvoyées.
FORGET nom_fichier
Supprime nom_fichier du cache. Toutes les mises à jour en attente SERONT PERDUES.
QUEUE
Affiche les fichiers qui sont dans la file d'attente de sortie. Renvoie zéro ou plusieurs lignes au format suivant, où <nb_valeurs> est le nombre de valeurs à écrire pour le <fichier> : 
<nb_valeurs> <fichier>
HELP [commande]
Renvoie un court message d'utilisation. Si aucune commande n'est donnée, ou si commande est HELP, une liste des commandes prises en charge par le démon est renvoyée. Sinon, une courte description, pouvant contenir un pointeur vers une page de manuel, est renvoyée. Évidemment, ceci est destiné à une utilisation interactive et le format dans lequel les commandes et les résumés d'utilisation sont renvoyés n'est pas bien défini.
STATS
Renvoie une liste de métriques qui peuvent être utilisées pour mesurer les performances du démon et vérifier son état. Pour une description des valeurs renvoyées, voir « Valeurs de performance » ci-dessous.

Le format dans lequel les valeurs sont renvoyées est similaire à de nombreux autres protocoles basés sur des lignes : chaque valeur est imprimée sur une ligne distincte, chacune composée du nom de la valeur, d'un deux-points, d'un ou plusieurs espaces et de la valeur réelle.

Exemple :

9 Statistiques suivent
QueueLength: 0
UpdatesReceived: 30
FlushesReceived: 2
UpdatesWritten: 13
DataSetsWritten: 390
TreeNodesNumber: 13
TreeDepth: 4
JournalBytes: 190
JournalRotate: 0
PING
PING-PONG, c'est très utile lors de l'utilisation d'un pool de connexions entre le client utilisateur et RRDCACHED.

Exemple :

0 PONG
UPDATE nom_fichier valeurs [valeurs ...]
Ajoute des données supplémentaires à un nom de fichier. C'est l'opération pour laquelle le démon a été conçu, il est donc inutile de décrire à nouveau le mécanisme. Lisez « COMMENT ÇA MARCHE » ci-dessus pour une explication détaillée.

Notez que rrdcached n'accepte que les horodatages absolus dans les valeurs de mise à jour. Les chaînes de mise à jour telles que « N:1:2:3 » sont automatiquement converties en heure absolue par la bibliothèque cliente RRD avant d'être envoyées à rrdcached.

WROTE nom_fichier
Cette commande est écrite dans le journal après qu'un fichier a été écrit avec succès sur disque. Elle est utilisée lors de la relecture du journal pour déterminer quelles mises à jour ont déjà été appliquées. Elle est uniquement valide dans le journal ; elle n'est pas acceptée par les autres canaux de commande.
FIRST nom_fichier [num_rra]
Renvoie l'horodatage du premier CDP dans le RRA spécifié. Par défaut, utilise le RRA zéro si aucun n'est spécifié.
LAST nom_fichier
Renvoie l'horodatage de la dernière mise à jour du RRD spécifié. Notez que le cache n'est pas vidé avant la vérification, car le client est censé demander cela séparément s'il est nécessaire.
INFO nom_fichier
Renvoie les informations de configuration pour le RRD spécifié. Notez que le cache n'est pas vidé avant la vérification, car le client est censé demander cela séparément s'il est nécessaire.

Les informations sont renvoyées, un élément par ligne, avec le format :

I<nom_clé> I<type> I<valeur>
rrdcached(8) — rrdtool

NOM

rrdcached - un démon pour mettre en cache les mises à jour RRD

SYNTAXE

rrdcached [-b base_dir] [-f pidfile] [-j journal_dir] [-l [familly:]address] [-p command_pipe] [-F] [-O] [-R] [-w write_timeout] [-k cleanup_interval] [-U undecided_timeout] [-d] [-v]

DESCRIPTION

rrdcached est un démon qui gère les fichiers RRD. Il accepte les commandes via un socket réseau ou un pipe nommé. Les commandes traitées sont similaires à celles fournies par l'outil en ligne de commande rrdtool(1).

Le démon essaie d'améliorer les performances en regroupant les écritures sur disque. Lorsque le démon reçoit une commande UPDATE, il n'écrit pas immédiatement les données sur le disque. Au lieu de cela, il les met en cache en mémoire. Il écrit les données sur le disque de manière moins fréquente et plus efficace, ce qui permet d'éviter les problèmes causés par trop d'écritures simultanées sur le disque.

Le démon peut être contrôlé en lui envoyant des commandes. Cela peut être fait via le socket réseau (défini par l'option -l) ou via un pipe nommé (défini par l'option -p).

Les commandes suivantes sont disponibles:

CREATE nom_fichier [-s taille_pas] [-b heure_debut] [-r fichier_source ...] [-t fichier_modele] [-O] DefinitionsDS ... DefinitionsRRA ...
Crée le fichier RRD selon les paramètres fournis, à condition que ces paramètres soient valides, et (si l'option -O est donnée ou si le rrdcached a été démarré avec le drapeau -O) que le nom_fichier spécifié n'existe pas déjà.
BATCH
Cette commande initie le chargement en masse de commandes multiples. Ceci est conçu pour les installations avec des taux de mise à jour extrêmement élevés, car cela permet d'émettre plus d'une commande par read() et write().

Toutes les commandes sont exécutées comme si elles étaient données individuellement, sauf pour la sortie vers l'utilisateur. Les messages indiquant le succès sont supprimés et les messages d'erreur sont retardés jusqu'à ce que le client ait terminé.

Le traitement des commandes se termine lorsque le client envoie un point (".") sur sa propre ligne. Une fois que le client a terminé, le serveur répond avec un nombre d'erreurs et la liste des messages d'erreur (s'il y en a). Chaque message d'erreur indique le numéro de la commande à laquelle il correspond, et le message d'erreur lui-même. La première commande utilisateur après BATCH est la commande numéro un.

client:  BATCH
server:  0 Go ahead.  End with dot '.' on its own line.
client:  UPDATE x.rrd 1223661439:1:2:3            <--- commande #1
client:  UPDATE y.rrd 1223661440:3:4:5            <--- commande #2
client:  et ainsi de suite...
client:  .
server:  2 Erreurs
server:  1 message pour la commande 1
server:  12 message pour la commande 12
LIST [RECURSIVE] I/<chemin>
Cette commande permet de lister les répertoires et les bases de données rrd telles que vues par le démon. Le répertoire racine est le base_dir (voir '-b dir'). Lors de l'invocation avec 'LIST RECURSIVE /<chemin>' elle se comportera de manière similaire à 'ls -R' mais limitée aux fichiers rrd (listant toutes les bases rrd dans le sous-arbre de <chemin>, en sautant les répertoires vides).
SUSPEND nom_fichier
Suspendre l'écriture dans un fichier RRD. Pendant qu'un fichier est suspendu, toutes les métriques le concernant sont mises en cache en mémoire jusqu'à ce que RESUME soit appelé pour ce fichier ou que RESUMEALL soit appelé.
RESUME nom_fichier
Reprendre l'écriture dans un fichier RRD précédemment suspendu par SUSPEND ou SUSPENDALL.
SUSPENDALL
Suspendre l'écriture dans tous les fichiers RRD. Pendant qu'un fichier est suspendu, toutes les métriques le concernant sont mises en cache en mémoire jusqu'à ce que RESUME soit appelé pour ce fichier ou que RESUMEALL soit appelé.
RESUMEALL
Reprendre l'écriture dans tous les fichiers RRD précédemment suspendus par SUSPEND ou SUSPENDALL.
QUIT
Se déconnecter de rrdcached.

Valeurs de Performance

Les compteurs suivants sont retournés par la commande STATS:

QueueLength (entier 64 bits sans signe)
Nombre de nœuds actuellement en file d'attente pour la mise à jour.
UpdatesReceived (entier 64 bits sans signe)
Nombre de commandes UPDATE reçues.
FlushesReceived (entier 64 bits sans signe)
Nombre de commandes FLUSH reçues.
UpdatesWritten (entier 64 bits sans signe)
Nombre total de mises à jour, c'est-à-dire d'appels à "rrd_update_r", depuis le démarrage du démon.
DataSetsWritten (entier 64 bits sans signe)
Nombre total de "jeux de données" écrits sur disque depuis le démarrage du démon. Un jeu de données est une ou plusieurs valeurs passées à la commande UPDATE. Par exemple : "1223661439:123:456" est un jeu de données avec deux valeurs. Le terme "jeu de données" est utilisé pour éviter la confusion quant à savoir si les valeurs individuelles ou les groupes de valeurs sont comptés.
TreeNodesNumber (entier 64 bits sans signe)
Nombre de nœuds dans le cache.
TreeDepth (entier 64 bits sans signe)
Profondeur de l'arbre utilisé pour une recherche rapide de clés.
JournalBytes (entier 64 bits sans signe)
Nombre total d'octets écrits dans le journal depuis le démarrage.
JournalRotate (entier 64 bits sans signe)
Nombre de fois où le journal a été pivoté depuis le démarrage.

SIGNALS

SIGINT et SIGTERM
Le démon se termine normalement à la réception de l'un de ces signaux. Les mises à jour en attente sont traitées conformément aux options -j et -F.
SIGUSR1
Le démon se termine APRÈS avoir vidé toutes les mises à jour sur le disque. Cela peut prendre un certain temps.
SIGUSR2
Le démon se termine immédiatement, sans vider les mises à jour sur le disque. Les mises à jour en attente seront rejouées depuis le journal lors du prochain démarrage du démon. ATTENTION : si le journal (journaling) (-j) n'est PAS activé, toutes les mises à jour en attente SERONT PERDUES.
