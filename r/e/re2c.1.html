NOM

re2c - générer des analyseurs lexicaux rapides pour C/C++

SYNOPSIS

Note : certains exemples sont en C++ (mais peuvent être adaptés en C).

re2c [ OPTIONS ] [ AVERTISSEMENTS ] ENTRÉE

L'entrée peut être un fichier ou - pour stdin.

INTRODUCTION

re2c fonctionne comme un préprocesseur. Il lit le fichier d'entrée (qui est généralement un programme en C/C++, mais peut être n'importe quoi) et recherche des blocs de code délimités par des marqueurs de début/fin de forme spéciale. Le texte en dehors de ces blocs est copié tel quel dans le fichier de sortie. Le contenu des blocs est traité par re2c. Il le traduit en code C/C++ et génère le code résultant à la place du bloc.

Voici un exemple de petit programme qui vérifie si une chaîne donnée contient un nombre décimal :

// re2c $INPUT -o $OUTPUT -i --case-ranges
#include <assert.h>
int lex(const char *s) {
    const char *YYCURSOR = s;
    /*!re2c
        re2c:yyfill:enable = 0;
        re2c:define:YYCTYPE = char;
        [1-9][0-9]* { return 0; }
        *           { return 1; }
    */
}
int main() {
    assert(lex("1234") == 0);
    return 0;
}

Dans la sortie, re2c a remplacé le bloc du milieu par le code généré :

/* Généré par re2c */
// re2c $INPUT -o $OUTPUT -i --case-ranges
#include <assert.h>
int lex(const char *s) {
    const char *YYCURSOR = s;
{
    char yych;
    yych = *YYCURSOR;
    switch (yych) {
        case '1' ... '9': goto yy2;
        default: goto yy1;
    }
yy1:
    ++YYCURSOR;
    { return 1; }
yy2:
    yych = *++YYCURSOR;
    switch (yych) {
        case '0' ... '9': goto yy2;
        default: goto yy3;
    }
yy3:
    { return 0; }
}
}
int main() {
    assert(lex("1234") == 0);
    return 0;
}

BASES

Un programme re2c se compose d'une séquence de blocs entrelacés avec du code dans le langage cible. Un bloc peut contenir des définitions, des configurations, des règles, des actions et des directives dans n'importe quel ordre :

nom = expression-régulière ;
Une définition lie nom à expression-régulière. Les noms peuvent contenir des caractères alphanumériques et des traits de soulignement. La section expressions régulières donne un aperçu de la syntaxe de re2c pour les expressions régulières. Une fois défini, le nom peut être utilisé dans d'autres expressions régulières et dans les règles. La récursion dans les définitions nommées n'est pas autorisée, et chaque nom doit être défini avant d'être utilisé. Un bloc hérite des définitions nommées de la portée globale. Redéfinir un nom qui existe dans la portée actuelle est une erreur.
configuration = valeur ;
Une configuration permet de modifier le comportement de re2c et de personnaliser le code généré. Pour une liste complète des configurations prises en charge par re2c, voir la section configurations. Selon la configuration, la valeur peut être un mot-clé, un nombre entier non négatif ou une chaîne d'une seule ligne qui doit être entourée de guillemets doubles ou simples, sauf si elle est composée de caractères alphanumériques. Un bloc hérite des configurations de la portée globale et peut les redéfinir ou en ajouter de nouvelles. Les configurations définies à l'intérieur d'un bloc affectent l'ensemble du bloc, même si elles apparaissent à la fin de celui-ci.
expression-régulière code
Une règle lie une expression-régulière à son action sémantique (un bloc de code entre accolades, ou un bloc de code qui commence par := et se termine par un retour à la ligne suivi de n'importe quel caractère non blanc). Si l'expression-régulière correspond, le code associé est exécuté. Si plusieurs règles correspondent, la correspondance la plus longue a la priorité. Si plusieurs règles correspondent à la même chaîne, la première apparue a la priorité. Il existe deux règles spéciales : la règle par défaut * et la règle de fin d'entrée $. La règle par défaut doit toujours être définie, elle a la plus basse priorité quelle que soit sa place dans le bloc, et elle correspond à n'importe quelle unité de code (pas nécessairement un caractère valide, voir la section support des encodages). La règle de fin d'entrée doit être définie si la méthode correspondante pour la gestion de la fin d'entrée est utilisée. Avec les conditions de départ, les règles ont une syntaxe plus complexe.
!action code
Une action lie un bloc de code défini par l'utilisateur à un endroit particulier dans la machine à états finis générée (de la même manière que les actions sémantiques lient du code aux états finaux). Voir la section actions pour une liste complète des actions prédéfinies.
!directive ;
Une directive est l'une des instructions prédéfinies spéciales. Chaque directive a un but unique. Voir la section directives pour plus de détails.

Blocs

Les marqueurs de début et de fin de bloc sont soit /*!re2c et */, soit %{ et %} (les deux styles sont pris en charge). À partir de la version 2.2, les blocs peuvent avoir des noms optionnels qui permettent de les référencer dans d'autres blocs. Il existe différents types de blocs :

/*!re2c[:<nom>] ... */ ou %{[:<nom>] ... %}
Un bloc global contient des définitions, des configurations, des règles et des directives. re2c compile les expressions régulières associées à chaque règle en un automate fini déterministe, l'encode sous forme de sauts conditionnels dans le langage cible et remplace le bloc par le code généré. Les noms et configurations définis dans un bloc global sont ajoutés à la portée globale et deviennent visibles pour les blocs suivants. Au début du programme, la portée globale est initialisée avec les options de la ligne de commande.
/*!local:re2c[:<nom>] ... */ ou %{local[:<nom>] ... %}
Un bloc local est similaire à un bloc global, mais les noms et configurations qu'il contient ont une portée locale (ils n'affectent pas les autres blocs).
/*!rules:re2c[:<nom>] ... */ ou %{rules[:<nom>] ... %}
Un bloc de règles est similaire à un bloc local, mais il ne génère aucun code par lui-même, ni n'ajoute de définitions à la portée globale -- il est destiné à être réutilisé dans d'autres blocs. C'est une façon de partager du code (plus de détails dans la section blocs réutilisables). Avant la version 2.2 de re2c, les blocs de règles nécessitaient l'option -r --reusable.
/*!use:re2c[:<nom>] ... */ ou %{use[:<nom>] ... %}
Un bloc d'utilisation qui référence un bloc de règles défini précédemment. Si le nom est spécifié, re2c recherche des blocs de règles portant ce nom. Sinon, le bloc de règles le plus récent est utilisé (qu'il soit nommé ou non). Un bloc d'utilisation peut ajouter ses propres définitions, configurations et règles, qui sont ajoutées à celles du bloc de règles référencé. Avant la version 2.2 de re2c, les blocs d'utilisation nécessitaient l'option -r --reusable.
/*!max:re2c[:<nom1>[:<nom2>...]] ... */ ou %{max[:<nom1>[:<nom2>...]] ... %}
Un bloc qui génère la définition YYMAXFILL. Une liste optionnelle de noms de blocs spécifie quels blocs doivent être inclus lors du calcul de la valeur YYMAXFILL (si la liste est vide, tous les blocs sont inclus). Par défaut, le code généré est une macro-définition pour C (#define YYMAXFILL <n>), ou une variable globale pour Go (var YYMAXFILL int = <n>). Il peut être personnalisé avec une configuration optionnelle format qui spécifie une chaîne de modèle où @@{max} (ou @@ pour faire court) est remplacé par la valeur numérique de YYMAXFILL.
/*!maxnmatch:re2c[:<nom1>[:<nom2>...]] ... */ ou %{maxnmatch[:<nom1>[:<nom2>...]] ... %}

Blocs

Les blocs sont des sections de code délimitées par des commentaires spéciaux, qui peuvent être utilisés pour configurer la génération de code de re2c.

/*!stags[:<nom1>[:<nom2>...]] ... */, /*!mtags:re2c[:<nom1>[:<nom2>...]] ... */ ou %{stags[:<nom1>[:<nom2>...]] ... %}, %{mtags[:<nom1>[:<nom2>...]] ... %{
Blocs qui spécifient un modèle de code qui est développé pour chaque variable de balise s/m générée par re2c. Une liste optionnelle de noms de blocs spécifie quels blocs doivent être inclus lors du calcul de l'ensemble des variables de balise (si la liste est vide, tous les blocs sont inclus). Il existe deux configurations optionnelles : format et separator. La configuration format spécifie une chaîne de modèle où @@{balise} (ou @@ pour faire court) est remplacé par le nom de chaque variable de balise. La configuration separator spécifie un morceau de code utilisé pour joindre les pièces format générées pour différentes variables de balise.
/*!svars:re2c[:<nom1>[:<nom2>...]] ... */, /*!mvars:re2c[:<nom1>[:<nom2>...]] ... */ ou %{svars[:<nom1>[:<nom2>...]] ... %}, %{mvars[:<nom1>[:<nom2>...]] ... %{
Blocs qui spécifient un modèle de code qui est développé pour chaque s-balise/m-balise qui est soit explicitement mentionnée par les règles (avec l'option --tags) soit générée implicitement par re2c (avec les options --captvars ou --posix-captvars). Une liste optionnelle de noms de blocs spécifie quels blocs doivent être inclus lors du calcul de l'ensemble des balises (si la liste est vide, tous les blocs sont inclus). Il existe deux configurations optionnelles : format et separator. La configuration format spécifie une chaîne de modèle où @@{balise} (ou @@ pour faire court) est remplacé par le nom de chaque balise. La configuration separator spécifie un morceau de code utilisé pour joindre les pièces format générées pour différentes balises.
/*!getstate:re2c[:<nom1>[:<nom2>...]] ... */ ou %{getstate[:<nom1>[:<nom2>...]] ... %}
Un bloc qui génère un dispatch conditionnel sur l'état de l'analyseur lexical (il nécessite l'option --storable-state). Une liste optionnelle de noms de blocs spécifie quels blocs doivent être inclus dans le dispatch d'état. La transition par défaut va à l'étiquette de départ du premier bloc de la liste. Si la liste est vide, tous les blocs sont inclus, et la transition par défaut va au premier bloc du fichier qui a une étiquette de départ. Ce type de bloc est incompatible avec l'option --loop-switch, car il nécessite des transitions inter-blocs qui ne sont pas prises en charge sans goto ou appels de fonction.
/*!conditions:re2c[:<nom1>[:<nom2>...]] ... */, /*!types:re2c... */ ou %{conditions[:<nom1>[:<nom2>...]] ... %}, %{types... %}
Un bloc qui génère une énumération de conditions (il nécessite l'option --conditions). Une liste optionnelle de noms de blocs spécifie quels blocs doivent être inclus lors du calcul de l'ensemble des conditions (si la liste est vide, tous les blocs sont inclus). Par défaut, le code généré est une énumération YYCONDTYPE. Il peut être personnalisé avec les configurations optionnelles format et separator. La configuration format spécifie une chaîne de modèle où @@{cond} (ou @@ pour faire court) est remplacé par le nom de chaque condition, et @@{num} est remplacé par un index numérique de cette condition. La configuration separator spécifie un morceau de code utilisé pour joindre les pièces format générées pour différentes conditions.
/*!include:re2c <fichier> */ ou %{include <fichier> %}
Ce bloc permet d'inclure <fichier>, qui doit être un chemin de fichier entre guillemets doubles. Le contenu du fichier est littéralement substitué à la place du bloc, de la même manière que #include fonctionne en C/C++. Ce bloc peut être utilisé conjointement avec l'option --depfile pour générer des dépendances du système de build sur les fichiers inclus.
/*!header:re2c:on*/ ou %{header:on %}
Ce bloc marque le début du fichier d'en-tête. Tout ce qui suit et jusqu'au bloc header:off suivant est traité par re2c et écrit dans le fichier d'en-tête spécifié avec l'option -t --type-header.
/*!header:re2c:off*/ ou %{header:off %}
Ce bloc marque la fin du fichier d'en-tête commencé avec le bloc header:on*/.
/*!ignore:re2c ... */ ou %{ignore ... %}
Un bloc dont le contenu est ignoré et supprimé du fichier de sortie.

Configurations

Voici une liste complète des configurations prises en charge par re2c :

re2c:api, re2c:input
Identique à l'option --api.
re2c:api:sigil
Spécifie le marqueur ("sigil") utilisé pour les espaces réservés d'arguments dans les primitives de l'API. La valeur par défaut est @@. Un espace réservé commence par le sigil suivi du nom de l'argument entre accolades. Par exemple, si le sigil est défini sur $, alors les espaces réservés auront la forme ${nom}. Les API à argument unique peuvent utiliser une notation abrégée sans le nom entre accolades. Cette option peut être remplacée par des options pour des primitives d'API individuelles, par exemple re2c:YYFILL@len pour YYFILL.
re2c:api:style
Spécifie le style de l'API. Les valeurs possibles sont functions (la valeur par défaut pour C) et free-form (la valeur par défaut pour Go et Rust). Dans le style functions, les primitives de l'API sont générées avec une liste d'arguments entre parenthèses suivant le nom de la primitive. Les arguments ne sont fournis que pour les paramètres autogénérés (tels que le nombre de caractères passés à YYFILL), mais pas pour le contexte général de l'analyseur lexical, de sorte que les primitives se comportent davantage comme des macros en C/C++ ou des fermetures en Go et Rust. Dans le style free-form, les primitives de l'API n'ont pas de forme fixe : elles doivent être définies comme des chaînes contenant des morceaux de code libres avec des variables interpolées de la forme @@{var} ou @@ (elles correspondent aux arguments du style fonctionnel). Cette configuration peut être remplacée pour des primitives d'API individuelles, voir par exemple la configuration re2c:YYFILL:naked pour YYFILL.

Expressions régulières

re2c utilise la syntaxe suivante pour les expressions régulières :

"foo"
Littéral de chaîne sensible à la casse.
'foo'
Littéral de chaîne insensible à la casse.
[a-xyz], [^a-xyz]
Classe de caractères (éventuellement négativée).
.
N'importe quel caractère sauf le saut de ligne.
R \ S
Différence des classes de caractères R et S.
R*
Zéro occurrence ou plus de R.
R+
Une occurrence ou plus de R.
R?
R optionnel.
R{n}
Répétition de R exactement n fois.
R{n,}
Répétition de R au moins n fois.
R{n,m}
Répétition de R de n à m fois.
(R)
Juste R ; les parenthèses sont utilisées pour outrepasser la priorité. Si l'extraction de sous-correspondance est activée, (R) est un groupe de capture ou un groupe sans capture selon l'option --invert-captures.
(!R)
Si l'extraction de sous-correspondance est activée, (!R) est un groupe sans capture ou un groupe de capture selon l'option --invert-captures.
R S
Concaténation : R suivi de S.
R | S
Alternative : R ou S.
R / S
Lookahead : R suivi de S, mais S n'est pas consommé.
name
Expression régulière définie comme name (ou chaîne littérale "name" en mode de compatibilité Flex).
{name}
Expression régulière définie comme name en mode de compatibilité Flex.
@stag
Un s-tag : sauvegarde la dernière position d'entrée où @stag correspond dans une variable nommée stag.
#mtag
Un m-tag : sauvegarde toutes les positions d'entrée où #mtag correspond dans une variable nommée mtag.

Les classes de caractères et les littéraux de chaînes peuvent contenir les séquences d'échappement suivantes : \a, \b, \f, \n, \r, \t, \v, \\, les échappements octaux \ooo et les échappements hexadécimaux \xhh, \uhhhh et \Uhhhhhhhh.

Actions

Voici une liste d'actions prédéfinies prises en charge par re2c :

!entry code
L'action d'entrée lie un bloc de code défini par l'utilisateur à l'état de départ de la machine à états finis actuelle. Si des conditions de départ sont utilisées, l'action d'entrée peut être définie individuellement pour chaque condition. Cette action peut être utilisée pour effectuer l'initialisation, par exemple, pour sauvegarder la position de départ d'un lexème.
!pre_rule code
L'action pré-règle ajoute un bloc de code défini par l'utilisateur avant les actions sémantiques de toutes les règles du bloc actuel (ou condition, si des conditions de départ sont utilisées). Cette action peut être utilisée pour factoriser la partie commune de toutes les actions sémantiques (par exemple, sauvegarder la position de fin d'un lexème).
!post_rule code
L'action post-règle ajoute un bloc de code défini par l'utilisateur après les actions sémantiques de toutes les règles du bloc actuel (ou condition, si des conditions de départ sont utilisées). Cette action peut être utilisée pour émettre des instructions de piège qui protègent contre les flux de contrôle involontaires.

Directives

Voici une liste complète des directives prises en charge par re2c :

!use:name ;
Une directive `use` intra-bloc qui fusionne un bloc de règles précédemment défini avec le name spécifié dans le bloc actuel. Les définitions nommées, les configurations et les règles du bloc référencé sont ajoutées aux actuels. Les conflits entre les règles et les configurations qui se chevauchent sont résolus de la manière habituelle : la première règle a la priorité, et la dernière configuration remplace les précédentes. Une exception concerne les règles spéciales *, $ et <!> pour lesquelles une définition locale au bloc a toujours la priorité. Une directive `use` peut être placée n'importe où à l'intérieur d'un bloc, et plusieurs directives `use` sont autorisées.
!include file ;
Cette directive est identique au bloc include : elle insère le contenu de file tel quel à la place de la directive.

Interface du programme

Le code généré interagit avec le programme externe à l'aide de primitives, collectivement appelées API. Les primitives nécessaires pour un programme particulier dépendent de plusieurs facteurs, notamment la complexité des expressions régulières, la représentation de l'entrée, la mise en mémoire tampon et l'utilisation de diverses fonctionnalités. Toutes les primitives nécessaires doivent être définies par l'utilisateur sous forme de macros, de fonctions, de variables ou toute autre forme appropriée qui rend le code généré syntaxiquement et sémantiquement correct. re2c ne vérifie pas (et ne peut pas vérifier) les définitions, donc si quelque chose manque ou est mal défini, le programme généré peut avoir des erreurs de compilation ou d'exécution. Ce manuel fournit des exemples de définitions d'API dans les cas les plus courants.

re2c propose trois saveurs d'API qui définissent l'ensemble de base des primitives utilisées par un programme :

API Simple
C'est l'API par défaut pour le backend C/C++. Elle se compose des primitives YYCURSOR, YYMARKER, YYCTXMARKER et YYLIMIT, qui doivent être définies comme des pointeurs de type YYCTYPE*.
API Record
(ajouté dans la version 4.0) L'API Record est utile dans les cas où l'état du lexer doit être stocké dans une structure. Elle est activée avec l'option --api record ou la configuration re2c:api = record. Cette API se compose d'une variable yyrecord (dont le nom peut être remplacé par re2c:yyrecord) qui doit être définie comme une structure avec les champs yycursor, yymarker, yyctxmarker, yylimit (seuls les champs utilisés par le code généré doivent être définis, et leurs noms peuvent être configurés).
API Générique
(ajouté dans la version 0.14) C'est l'API la plus flexible. Elle est activée avec l'option --api generic ou la configuration re2c:api = generic. Cette API contient des primitives pour les opérations génériques : YYPEEK, YYSKIP, YYBACKUP, YYBACKUPCTX, YYSTAGP, YYSTAGN, YYMTAGP, YYMTAGN, YYRESTORE, YYRESTORECTX, YYRESTORETAG, YYSHIFT, YYSHIFTSTAG, YYSHIFTMTAG, YYLESSTHAN. L'API générique prend en charge deux styles qui déterminent la forme sous laquelle les primitives doivent être définies :
Format libre
Le style format libre est activé avec la configuration re2c:api:style = free-form. Dans ce style, les primitives d'interface doivent être définies comme des morceaux de code format libre avec des variables interpolées sous la forme @@{var} ou éventuellement juste @@ s'il y a une seule variable. L'ensemble des variables est spécifique à chaque primitive. Voici comment l'API générique format libre peut être définie en termes de pointeurs cursor, limit, marker et ctxmarker :
/*!re2c
  re2c:YYPEEK       = "*cursor";
  re2c:YYSKIP       = "++cursor;";
  re2c:YYBACKUP     = "marker = cursor;";
  re2c:YYRESTORE    = "cursor = marker;";
  re2c:YYBACKUPCTX  = "ctxmarker = cursor;";
  re2c:YYRESTORECTX = "cursor = ctxmarker;";
  re2c:YYRESTORETAG = "cursor = ${tag};";
  re2c:YYLESSTHAN   = "limit - cursor < @@{len}";
  re2c:YYSTAGP      = "@@{tag} = cursor;";
  re2c:YYSTAGN      = "@@{tag} = NULL;";
  re2c:YYSHIFT      = "cursor += @@{shift};";
  re2c:YYSHIFTSTAG  = "@@{tag} += @@{shift};";
*/
Type fonction
Historiquement, le style type fonction est celui par défaut. Il peut également être activé avec la configuration re2c:api:style = functions. Dans ce style, les primitives doivent être définies comme des fonctions ou des macros avec des parenthèses, acceptant les arguments nécessaires. Voici comment l'API générique type fonction peut être définie en termes de pointeurs cursor, limit, marker et ctxmarker en utilisant des macros préprocesseur :
#define  YYPEEK()                 *cursor
#define  YYSKIP()                 ++cursor
#define  YYBACKUP()               marker = cursor
#define  YYRESTORE()              cursor = marker
#define  YYBACKUPCTX()            ctxmarker = cursor
#define  YYRESTORECTX()           cursor = ctxmarker
#define  YYRESTORETAG(tag)        cursor = tag
#define  YYLESSTHAN(len)          limit - cursor < len
#define  YYSTAGP(tag)             tag = cursor
#define  YYSTAGN(tag)             tag = NULL
#define  YYSHIFT(shift)           cursor += shift
#define  YYSHIFTSTAG(tag, shift)  tag += shift

Voici une liste complète des primitives d'API qui peuvent être utilisées par le code généré pour interagir avec le programme externe.

YYCTYPE
Le type des caractères d'entrée (unités de code). Pour les encodages ASCII, EBCDIC et UTF-8 il doit s'agir d'un entier non signé de 1 octet. Pour UTF-16 ou UCS-2 il doit s'agir d'un entier non signé de 2 octets. Pour UTF-32 il doit s'agir d'un entier non signé de 4 octets.
YYCURSOR
Une l-value qui stocke la position d'entrée actuelle (un pointeur ou un décalage entier dans YYINPUT). Initialement, YYCURSOR doit pointer vers le premier caractère d'entrée, et plus tard il est avancé par le code généré. Lorsqu'une règle correspond, la position YYCURSOR est celle après le dernier caractère correspondant.
YYLIMIT
Une r-value qui stocke la position de fin d'entrée (un pointeur ou un décalage entier dans YYINPUT). Initialement, YYLIMIT doit pointer vers la position après le dernier caractère d'entrée disponible. Il n'est pas modifié par le code généré. Le lexer compare YYCURSOR à YYLIMIT afin de déterminer s'il reste suffisamment de caractères d'entrée.
YYMARKER
Une valeur l-value qui stocke la position de la dernière règle correspondante (un pointeur ou un décalage entier dans YYINPUT). Elle est utilisée pour restaurer la position YYCURSOR si la correspondance la plus longue échoue et que le lexer a besoin de revenir en arrière. Aucune initialisation n'est nécessaire.
YYCTXMARKER
Une valeur l-value qui stocke la position du contexte de fin (un pointeur ou un décalage entier dans YYINPUT). Aucune initialisation n'est nécessaire. YYCTXMARKER n'est nécessaire que si l'opérateur de regard en avant / est utilisé.
YYFILL
Une primitive d'API générique avec une variable len. YYFILL doit fournir au moins len caractères d'entrée supplémentaires ou échouer. Si re2c:eof est utilisé, alors len vaut toujours 1 et YYFILL doit toujours retourner à la fonction appelante ; une valeur de retour zéro indique le succès. Si re2c:eof n'est pas utilisé, alors la valeur de retour de YYFILL est ignorée et il ne doit pas retourner en cas d'échec. La valeur maximale de len est YYMAXFILL.
YYFN
Une primitive qui définit le prototype de fonction dans le modèle de code --recursive-functions. Sa valeur doit être un tableau d'une ou plusieurs chaînes de caractères, où chaque chaîne contient deux ou trois composants séparés par la chaîne spécifiée dans la configuration re2c:fn:sep (généralement un point-virgule). Le premier élément du tableau définit le nom de la fonction et son type de retour (vide pour une fonction void). Les éléments suivants définissent les arguments de la fonction : d'abord, l'expression pour l'argument utilisée dans le corps de la fonction (généralement juste un nom) ; ensuite, le type de l'argument ; enfin, un paramètre formel optionnel (il vaut par défaut le premier composant - généralement l'argument et le paramètre sont le même identifiant).
YYINPUT
Une valeur r-value qui stocke la séquence de caractères d'entrée actuelle (chaîne, buffer, etc.).
YYMAXFILL
Une constante entière égale à la valeur maximale de l'argument de YYFILL. Elle peut être générée avec un bloc max.
YYLESSTHAN
Une primitive d'API générique avec une variable len. Elle doit être définie comme une valeur r-value de type booléen qui est égale à true si et seulement s'il reste moins de len caractères d'entrée.
YYPEEK
Une primitive d'API générique sans variables. Elle doit être définie comme une valeur r-value de type YYCTYPE qui est égale au caractère à la position d'entrée actuelle.
YYSKIP
Une primitive d'API générique qui doit avancer la position d'entrée actuelle d'une unité de code.
YYBACKUP
Une primitive d'API générique qui doit sauvegarder la position d'entrée actuelle (pour être restaurée plus tard avec YYRESTORE).
YYRESTORE
Une primitive d'API générique qui doit restaurer la position d'entrée actuelle à la valeur sauvegardée par YYBACKUP.
YYBACKUPCTX
Une primitive d'API générique qui doit sauvegarder la position d'entrée actuelle comme la position du contexte de fin (pour être restaurée plus tard avec YYRESTORECTX).
YYRESTORECTX
Une primitive d'API générique qui doit restaurer la position du contexte de fin sauvegardée avec YYBACKUPCTX.
YYRESTORETAG
Une primitive d'API générique avec une variable tag qui doit restaurer la position du contexte de fin à la valeur de tag.
YYSTAGP
Une primitive d'API générique avec une variable tag, où tag peut être un pointeur ou un décalage dans YYINPUT (voir la section sur l'extraction des sous-correspondances pour plus de détails). YYSTAGP doit définir tag à la position d'entrée actuelle.
YYSTAGN
Une primitive d'API générique avec une variable tag, où tag peut être un pointeur ou un décalage dans YYINPUT (voir la section sur l'extraction des sous-correspondances pour plus de détails). YYSTAGN doit définir tag à une valeur qui représente une position d'entrée inexistante.
YYMTAGP
Une primitive d'API générique avec une variable tag. YYMTAGP doit ajouter la position actuelle à l'historique des sous-correspondances de tag (voir la section sur l'extraction des sous-correspondances pour plus de détails.)
YYMTAGN
Une primitive d'API générique avec une variable tag. YYMTAGN doit ajouter une valeur qui représente une position d'entrée inexistante à l'historique des sous-correspondances de tag (voir la section sur l'extraction des sous-correspondances pour plus de détails.)
YYSHIFT
Une primitive d'API générique avec une variable shift qui doit décaler la position d'entrée actuelle de shift caractères (la valeur du décalage peut être négative).
YYCOPYSTAG
Une primitive d'API générique avec deux variables, lhs et rhs qui doit copier la variable s-tag de droite rhs vers la variable s-tag de gauche lhs. Pour la plupart des langages, cette primitive a une définition par défaut qui assigne lhs à rhs.
YYCOPYMTAG
Une primitive d'API générique avec deux variables, lhs et rhs qui doit copier la variable m-tag de droite rhs vers la variable m-tag de gauche lhs. Pour la plupart des langages, cette primitive a une définition par défaut qui assigne lhs à rhs.
YYSHIFTSTAG
Une primitive d'API générique avec deux variables, tag et shift qui doit décaler tag de shift unités de code (la valeur du décalage peut être négative).
YYSHIFTMTAG
Une primitive d'API générique avec deux variables, tag et shift qui doit décaler la dernière valeur de l'historique de tag de shift unités de code (la valeur du décalage peut être négative).
YYMAXNMATCH
Une constante entière égale au nombre maximal de groupes de capture POSIX dans une règle. Elle est générée avec un bloc maxnmatch.
YYCONDTYPE
Le type de l'énumération de condition. Il peut être généré soit avec le bloc conditions, soit avec l'option --header.
YYGETACCEPT
Une primitive avec une variable var qui stocke le sélecteur numérique de la règle acceptée. Pour la plupart des langages, cette primitive a une définition par défaut qui lit depuis var.
YYSETACCEPT
Une primitive avec deux variables : var (une valeur l-value qui stocke le sélecteur numérique de la règle acceptée) et val (la valeur du sélecteur). Pour la plupart des langages, cette primitive a une définition par défaut qui assigne var à val.
YYGETCOND
Une valeur r-value de type YYCONDTYPE qui est égale à l'identifiant de condition actuel.
YYSETCOND
Une primitive avec une variable cond qui doit définir l'identifiant de condition actuel à cond.
YYGETSTATE
Une valeur r-value de type entier qui est égale à l'état actuel du lexer. Elle devrait être initialisée à -1.
YYSETSTATE
Une primitive avec une variable state qui doit définir l'état actuel du lexer à state.
YYDEBUG
Cette primitive est générée uniquement avec l'option -d, --debug-output. Son objectif est d'ajouter une journalisation au code généré (la définition typique de YYDEBUG est une instruction d'impression). Les instructions YYDEBUG sont générées dans chaque état et ont deux variables : state (soit un index d'état DFA, soit -1) et symbol (le symbole d'entrée actuel).
yyaccept
Une valeur l-value de type entier non signé qui stocke le numéro de la dernière règle correspondante. La définition par l'utilisateur n'est nécessaire qu'avec l'option --storable-state.
yybm

Elle peut être facilement corrigée en ajoutant la règle par défaut * qui a la priorité la plus basse, correspond à n'importe quelle unité de code et consomme toujours une seule unité de code.
-Wunreachable-rules
Avertit sur les règles qui sont masquées par d'autres règles et qui ne correspondront jamais.
-Wdeprecated-eof_rule
Avertit sur les règles de fin de fichier autonomes $ qui seront rompues par les changements futurs et nécessiteront une correction. À l'heure actuelle, ces règles ont la priorité lorsqu'elles entrent en conflit avec d'autres règles, mais après l'introduction du symbole de fin de fichier généralisé $, l'ordre de priorité changera et ces règles seront masquées par d'autres règles.
-Wuseless-escape
Avertit si un symbole est échappé alors qu'il ne devrait pas l'être. Par défaut, re2c ignore silencieusement de tels échappements, mais cela peut aussi indiquer une faute de frappe ou une erreur dans la séquence d'échappement.
-Wnondeterministic-tags
Avertit si une balise a un degré de non-déterminisme n, où n est supérieur à 1.
-Wsentinel-in-midrule
Avertit si le symbole sentinelle apparaît au milieu d'une règle --- cela peut provoquer des lectures au-delà de la fin du tampon, des plantages ou une corruption de mémoire dans le lexer généré. Cet avertissement ne s'applique que si la méthode sentinelle de vérification de la fin de l'entrée est utilisée. Il est défini comme une erreur si la configuration re2c:sentinel est utilisée.
-Wundefined-syntax-config
Avertit si le fichier de syntaxe spécifié avec l'option --syntax manque de définitions pour certaines configurations. Cela permet de maintenir les fichiers de syntaxe définis par l'utilisateur : si une nouvelle version ajoute des configurations, l'ancien fichier de syntaxe déclenchera un avertissement, et l'utilisateur sera notifié. Si certaines configurations ne sont pas utilisées et n'ont pas besoin de définition, elles doivent être explicitement définies sur <undefined>.

Fichiers de syntaxe

Le support des différents langages dans re2c repose sur l'idée des fichiers de syntaxe. Un fichier de syntaxe est un fichier de configuration qui définit la syntaxe du langage cible -- pas l'intégralité du langage, mais une petite partie de celui-ci qui est utilisée par le code généré. Les fichiers de syntaxe rendent re2c très flexible, mais ils ne doivent pas être utilisés comme remplacement des configurations re2c: : leur but est de définir la syntaxe du langage cible, et non de personnaliser un lexer particulier. Tous les langages supportés ont des fichiers de syntaxe par défaut qui font partie de la distribution (voir le sous-répertoire include/syntax) ; ils sont également intégrés dans le binaire re2c. Les utilisateurs peuvent fournir un fichier de syntaxe personnalisé qui remplace quelques configurations pour l'un des langages supportés, ou ils peuvent choisir de redéfinir toutes les configurations (dans ce cas, l'option --lang none devrait être utilisée). Les fichiers de syntaxe contiennent des configurations de quatre types différents : listes de fonctionnalités, configurations de langage, configurations "in-place" et modèles de code.

Modèles de code

Les modèles de code définissent la syntaxe du langage cible. Ils sont écrits dans un langage simple spécifique à un domaine avec la grammaire formelle suivante : 
code-template ::
      name '=' code-exprs ';'
    | CODE_TEMPLATE ';'
    | '<undefined>' ';'
code-exprs ::
      <EMPTY>
    | code-exprs code-expr
code-expr ::
      STRING
    | VARIABLE
    | optional
    | list
optional ::
      '(' CONDITIONAL '?' code-exprs ')'
    | '(' CONDITIONAL '?' code-exprs ':' code-exprs ')'
list ::
      '[' VARIABLE ':' code-exprs ']'
    | '[' VARIABLE '{' NUMBER '}' ':' code-exprs ']'
    | '[' VARIABLE '{' NUMBER ',' NUMBER '}' ':' code-exprs ']'

Un modèle de code est une séquence de littéraux de chaîne, de variables, d'éléments optionnels et de listes, ou une référence à un autre modèle de code, ou une valeur spéciale <undefined>. Les variables sont des espaces réservés qui sont substitués pendant la phase de génération de code. Les variables de liste sont spéciales : lors de l'expansion des modèles de liste, re2c répète les expressions du côté droit de la colonne plusieurs fois, remplaçant à chaque fois les occurrences de la variable de liste par une valeur spécifique à cette répétition. Les listes ont des limites optionnelles (les valeurs négatives sont comptées à partir de la fin, par exemple -1 signifie le dernier élément). Les noms conditionnels commencent par un point. Les conditionnels et les variables peuvent être locaux (spécifiques au modèle de code donné) ou globaux (autorisés dans tous les modèles de code). Lorsque re2c lit le fichier de syntaxe, il vérifie que chaque modèle de code n'utilise que les variables et les conditionnels qui y sont autorisés.

Par exemple, le modèle de code suivant définit une structure if-then-else pour un langage de type C :

code:if_then_else =
    [branch{0}: topindent "if " cond " {" nl
        indent [stmt: stmt] dedent]
    [branch{1:-1}: topindent "} else" (.cond ? " if " cond) " {" nl
        indent [stmt: stmt] dedent]
    topindent "}" nl;

Ici, branch est une variable de liste : branch{0} s'étend à la première branche (qui est spéciale, car il n'y a pas de partie else), branch{1:-1} s'étend à toutes les branches restantes (s'il y en a). stmt est également une variable de liste : [stmt: stmt] est une liste imbriquée qui s'étend à une liste d'instructions dans le corps de la branche actuelle. topindent, indent, dedent et nl sont des variables globales, et .cond est un conditionnel local (leur signification est décrite ci-dessous). Ce modèle de code pourrait produire le code suivant :

if x {
    // faire quelque chose
} else if y {
    // faire autre chose
} else {
    // ne rien faire
}

GESTION DE LA FIN DE L'ENTRÉE

L'un des principaux problèmes pour le lexer est de savoir quand s'arrêter. Il existe quelques conditions de terminaison :

  • le lexer peut correspondre à une règle (y compris la règle par défaut *) et atteindre un état final
  • le lexer peut ne pas correspondre à une règle et atteindre un état par défaut
  • le lexer peut atteindre la fin de l'entrée

Les deux premières conditions terminent le lexer d'une manière "naturelle" : il atteint un état sans transitions sortantes, et la correspondance s'arrête automatiquement. La troisième condition, la fin de l'entrée, est différente : elle peut survenir dans n'importe quel état, et le lexer doit pouvoir la gérer. La vérification de la fin de l'entrée interrompt le flux normal du lexer et ajoute des branches conditionnelles au programme généré, il est donc nécessaire de minimiser le nombre de telles vérifications. re2c prend en charge plusieurs méthodes pour gérer la fin de l'entrée. Le choix dépend de la complexité des expressions régulières, du besoin de mise en tampon, des considérations de performance et d'autres facteurs. Voici une liste de méthodes :

  • Sentinel. Cette méthode élimine le besoin de vérifications de fin d'entrée. Elle est simple et efficace, mais limitée au cas où il existe un caractère "sentinelle" naturel qui ne peut jamais se produire dans une entrée valide. Ce caractère peut toujours apparaître dans une entrée invalide, mais il ne devrait pas être autorisé par les expressions régulières, sauf peut-être comme dernier caractère d'une règle. Le sentinelle est ajouté à la fin de l'entrée et sert de signal d'arrêt : lorsque le lexer lit ce caractère, il s'agit soit d'une erreur de syntaxe, soit de la fin de l'entrée. Dans les deux cas, le lexer doit s'arrêter. Cette méthode est utilisée si YYFILL est désactivé avec re2c:yyfill:enable = 0; et que re2c:eof a la valeur par défaut -1.
  • Sentinel avec vérifications de limites. Cette méthode est générique : elle permet de gérer n'importe quelle entrée sans restrictions sur les expressions régulières. L'idée est de réduire le nombre de vérifications de fin d'entrée en ne les effectuant que sur certains caractères. Similaire à la méthode "sentinelle", l'un des caractères est choisi comme "sentinelle" et ajouté à la fin de l'entrée. Cependant, il n'y a aucune restriction quant à l'endroit où le sentinelle peut apparaître (en fait, n'importe quel caractère peut être choisi comme sentinelle). Lorsque le lexer lit ce caractère, il effectue en plus une vérification de limites. Si la position actuelle est dans les limites, le lexer reprend la correspondance et traite le sentinelle comme un caractère normal. Sinon, il invoque YYFILL (sauf s'il est désactivé). Si davantage d'entrée est fournie, le lexer réanalysera le dernier caractère et continuera comme si le sentinelle n'était pas là. Sinon, ce doit être la vraie fin de l'entrée, et le lexer s'arrête. Cette méthode est utilisée lorsque re2c:eof a une valeur non négative (elle doit être définie à la valeur numérique du sentinelle). YYFILL est facultatif.
  • Vérifications de limites avec remplissage. Cette méthode est générique et peut être plus rapide que la méthode "sentinelle avec vérifications de limites", mais elle est aussi plus complexe. L'idée est de partitionner les états du DFA en composantes fortement connexes (SCC) et de générer une seule vérification par SCC pour suffisamment de caractères pour couvrir le chemin non bouclé le plus long dans cette SCC. Cela réduit le nombre de vérifications, mais il y a un problème avec les lexèmes courts à la fin de l'entrée, car la vérification nécessite suffisamment de caractères pour couvrir le lexème le plus long. Cela peut être corrigé en remplissant l'entrée avec quelques caractères factices qui ne forment pas un suffixe de lexème valide (de sorte que le lexer ne puisse pas les faire correspondre). La longueur du remplissage doit être YYMAXFILL, générée avec un bloc max. S'il n'y a pas assez d'entrée, le lexer invoque YYFILL qui doit fournir au moins le nombre de caractères requis ou ne pas revenir. Cette méthode est utilisée si YYFILL est activé et que re2c:eof est -1 (c'est la configuration par défaut).
  • Vérifications personnalisées. L'API générique permet de remplacer les opérations de base comme la lecture d'un caractère, ce qui permet d'inclure les vérifications de fin d'entrée comme faisant partie d'elles. Cette approche est sujette aux erreurs et doit être utilisée avec prudence. Pour utiliser une méthode personnalisée, activez l'API générique avec --api custom ou re2c:api = custom; et désactivez les vérifications de limites par défaut avec re2c:yyfill:enable = 0; ou re2c:yyfill:check = 0;.

Sentinel

Cet exemple utilise un caractère sentinelle pour gérer la fin de l'entrée. Le programme compte les mots séparés par des espaces dans une chaîne terminée par un caractère nul. Le sentinelle est le caractère nul : c'est le dernier caractère de chaque chaîne d'entrée, et il n'est autorisé dans le milieu d'un lexème par aucune des règles (en particulier, il n'est pas inclus dans les plages de caractères où il est facile de le manquer). Si un caractère nul se produit au milieu d'une chaîne, il s'agit d'une erreur de syntaxe et le lexer correspondra à la règle par défaut *, mais il ne lira pas au-delà de la fin de l'entrée ni ne plantera (utilisez l'avertissement -Wsentinel-in-midrule et la configuration re2c:sentinel pour vérifier cela). La configuration re2c:yyfill:enable = 0; supprime la génération des vérifications de limites et des invocations de YYFILL.

// re2c $INPUT -o $OUTPUT
#include <assert.h>
// Attend une chaîne terminée par un caractère nul.
static int lex(const char *YYCURSOR) {
    int count = 0;
    for (;;) {
    /*!re2c
        re2c:define:YYCTYPE = char;
        re2c:yyfill:enable = 0;
        *      { return -1; }
        [\x00] { return count; }
        [a-z]+ { ++count; continue; }
        [ ]+   { continue; }
    */
    }
}
int main() {
    assert(lex("") == 0);
    assert(lex("one two three") == 3);
    assert(lex("f0ur") == -1);
    return 0;
}

Sentinel avec vérifications de limites

Cet exemple utilise un sentinelle avec vérifications de limites pour gérer la fin de l'entrée (cette méthode a été ajoutée dans la version 1.2). Le programme compte les chaînes de caractères d'un seul guillemet séparées par des espaces. Le caractère sentinelle est le caractère nul, spécifié avec la configuration re2c:eof = 0;. Comme dans la méthode sentinel, le caractère nul est le dernier caractère de chaque chaîne d'entrée

, mais il est autorisé au milieu d'une règle (par exemple, 'aaa\0aa'\0 est une entrée valide, mais 'aaa\0 est une erreur de syntaxe). Des vérifications de limites sont générées dans chaque état qui correspond à un caractère d'entrée, mais elles sont limitées à la branche qui gère le caractère nul. Les vérifications de limites sont de la forme YYLIMIT <= YYCURSOR ou YYLESSTHAN(1) avec l'API générique. Si la condition de vérification est vraie, le lexer a atteint la fin de l'entrée et doit s'arrêter (YYFILL est désactivé avec re2c:yyfill:enable = 0; car l'entrée tient dans un seul tampon, voir la section YYFILL avec sentinelle pour un exemple qui utilise YYFILL). Atteindre la fin de l'entrée ouvre trois possibilités : si le lexer est dans l'état initial, il correspondra à la règle de fin d'entrée $, sinon il peut revenir à une règle précédemment correspondante (y compris la règle par défaut *) ou aller à un état par défaut, provoquant -Wundefined-control-flow.

// re2c $INPUT -o $OUTPUT
#include <assert.h>
// Attend une chaîne terminée par un caractère nul.
static int lex(const char *str, unsigned int len) {
    const char *YYCURSOR = str, *YYLIMIT = str + len, *YYMARKER;
    int count = 0;
    for (;;) {
    /*!re2c
        re2c:define:YYCTYPE = char;
        re2c:yyfill:enable = 0;
        re2c:eof = 0;
        str = ['] ([^'\\] | [\\][^])* ['];
        *    { return -1; }
        $    { return count; }
        str  { ++count; continue; }
        [ ]+ { continue; }
    */
    }
}
#define TEST(s, r) assert(lex(s, sizeof(s) - 1) == r)
int main() {
    TEST("", 0);
    TEST("'qu\0tes' 'are' 'fine: \\'' ", 3);
    TEST("'unterminated\\'", -1);
    return 0;
}

Vérifications de limites avec remplissage

Cet exemple utilise des vérifications de limites avec remplissage pour gérer la fin de l'entrée (cette méthode est activée par défaut). Le programme compte les chaînes entre guillemets simples séparées par des espaces. Il y a un remplissage de YYMAXFILL caractères nuls ajoutés à la fin de l'entrée, où la valeur de YYMAXFILL est générée automatiquement avec un bloc max. Il n'est pas nécessaire d'utiliser le caractère nul pour le remplissage --- n'importe quels caractères peuvent être utilisés tant qu'ils ne forment pas un suffixe de lexème valide (dans cet exemple, le remplissage ne doit pas contenir de guillemets simples, car ils pourraient être confondus avec un suffixe d'une chaîne entre guillemets simples). Il existe une règle "stop" qui correspond au premier caractère de remplissage (nul) et termine le lexer (notez qu'elle vérifie si le caractère nul est au début du remplissage, sinon c'est une erreur de syntaxe). Des vérifications de limites ne sont générées que dans certains états déterminés par les composantes fortement connexes de l'automate sous-jacent. Les vérifications sont de la forme (YYLIMIT - YYCURSOR) < n ou YYLESSTHAN(n) avec l'API générique, où n est le nombre minimum de caractères nécessaires au lexer pour continuer (cela signifie également que la prochaine vérification de limite se produira dans au plus n caractères). Si la condition de vérification est vraie, le lexer a atteint la fin de l'entrée et invoquera YYFILL(n) qui doit soit fournir au moins n caractères d'entrée, soit ne pas retourner. Dans cet exemple, YYFILL échoue toujours et termine le lexer avec une erreur (ce qui est acceptable car l'entrée tient dans un seul tampon). Voir la section YYFILL avec remplissage pour un exemple qui recharge le tampon d'entrée avec YYFILL.

// re2c $INPUT -o $OUTPUT
#include <assert.h>
#include <stdlib.h>
#include <string.h>
/*!max:re2c*/
static int lex(const char *str, unsigned int len) {
    // Pour l'exemple, crée une copie de la chaîne avec YYMAXFILL zéros à la fin.
    char *buf = (char*) malloc(len + YYMAXFILL);
    memcpy(buf, str, len);
    memset(buf + len, 0, YYMAXFILL);
    const char *YYCURSOR = buf, *YYLIMIT = buf + len + YYMAXFILL;
    int count = 0;
loop:
    /*!re2c
        re2c:api:style = free-form;
        re2c:define:YYCTYPE = char;
        re2c:define:YYFILL = "goto fail;";
        str = ['] ([^'\\] | [\\][^])* ['];
        [\x00] {
            // Vérifie qu'il s'agit du sentinelle, pas d'un nul inattendu.
            if (YYCURSOR - 1 == buf + len) goto exit; else goto fail;
        }
        str  { ++count; goto loop; }
        [ ]+ { goto loop; }
        *    { goto fail; }
    */
fail:
    count = -1;
exit:
    free(buf);
    return count;
}
#define TEST(s, r) assert(lex(s, sizeof(s) - 1) == r)
int main() {
    TEST("", 0);
    TEST("'qu\0tes' 'are' 'fine: \\'' ", 3);
    TEST("'unterminated\\'", -1);
    TEST("'unexpected \0 null\\'", -1);
    return 0;
}

Vérifications personnalisées

Cet exemple utilise une méthode personnalisée de gestion de la fin d'entrée basée sur l'API générique. Le programme compte les chaînes entre guillemets simples séparées par des espaces. C'est identique à l'exemple sentinelle, sauf que l'entrée n'est pas terminée par un caractère nul. Pour compenser l'absence d'un caractère sentinelle en fin d'entrée, YYPEEK est redéfini pour effectuer une vérification de limites avant de lire le prochain caractère d'entrée. Ceci est inefficace car les vérifications sont effectuées très souvent. Si la condition de vérification échoue, YYPEEK retourne le caractère réel, sinon il retourne un faux caractère sentinelle.

// re2c $INPUT -o $OUTPUT
#include <assert.h>
#include <stdlib.h>
#include <string.h>
static int lex(const char *str, unsigned int len) {
    // Pour l'exemple, crée une chaîne sans caractère nul de terminaison.
    char *buf = (char*) malloc(len);
    memcpy(buf, str, len);
    const char *cur = buf, *lim = buf + len;
    int count = 0;
    for (;;) {
    /*!re2c
        re2c:yyfill:enable = 0;
        re2c:api = custom;
        re2c:api:style = free-form;
        re2c:define:YYCTYPE = char;
        re2c:define:YYPEEK = "cur < lim ? *cur : 0";  // faux nul
        re2c:define:YYSKIP = "++cur;";
        *      { count = -1; break; }
        [\x00] { break;; }
        [a-z]+ { ++count; continue;; }
        [ ]+   { continue; }
    */
    }
    free(buf);
    return count;
}
#define TEST(s, r) assert(lex(s, sizeof(s) - 1) == r)
int main() {
    TEST("", 0);
    TEST("one two three ", 3);
    TEST("f0ur", -1);
    return 0;
}

RECHARGE DE TAMPON

Le besoin de mise en tampon survient lorsque l'entrée ne peut pas être mappée en mémoire d'un seul coup : soit elle est trop grande, soit elle arrive de manière séquentielle (comme la lecture depuis un socket). La technique habituelle dans de tels cas est d'allouer un tampon de mémoire de taille fixe et de traiter l'entrée par morceaux qui tiennent dans le tampon. Lorsque le morceau actuel est traité, il est déplacé et de nouvelles données sont chargées. En pratique, c'est un peu plus complexe, car l'état du lexer ne consiste pas en une seule position d'entrée, mais en un ensemble de positions interdépendantes :

  • curseur : le prochain caractère d'entrée à lire (YYCURSOR dans l'API pointeur C ou YYSKIP/YYPEEK dans l'API générique)
  • limite : la position après le dernier caractère d'entrée disponible (YYLIMIT dans l'API pointeur C, géré implicitement par YYLESSTHAN dans l'API générique)
  • marqueur : la position de la correspondance la plus récente, le cas échéant (YYMARKER dans l'API par défaut ou YYBACKUP/YYRESTORE dans l'API générique)
  • jeton : le début du lexème actuel (implicite dans l'API re2c, car il n'est pas nécessaire pour le fonctionnement normal du lexer et peut être défini et mis à jour par l'utilisateur)
  • marqueur de contexte : la position du contexte de fin (YYCTXMARKER dans l'API pointeur C ou YYBACKUPCTX/YYRESTORECTX dans l'API générique)
  • variables de balises : positions de sous-correspondance (définies avec les blocs stags et mtags et les primitives d'API générique YYSTAGP/YYSTAGN/YYMTAGP/YYMTAGN)

Toutes ces positions ne sont pas utilisées dans tous les cas, mais si elles le sont, elles doivent être mises à jour par YYFILL. Toutes les positions actives sont contenues dans le segment entre le jeton et le curseur, par conséquent tout ce qui se trouve entre le début du tampon et le jeton peut être écarté, le segment allant du jeton jusqu'à la limite doit être déplacé au début du tampon, et l'espace libre à la fin du tampon doit être rempli avec de nouvelles données. Afin d'éviter des appels fréquents à YYFILL, il est préférable de charger autant de caractères d'entrée que possible (même si moins de caractères pourraient suffire à reprendre le lexer). Les détails de l'implémentation de YYFILL diffèrent légèrement en fonction de la méthode de gestion de la fin de fichier utilisée : le cas de la règle EOF est quelque peu plus simple que le cas des vérifications de limites avec remplissage. Notez également que si l'option -f --storable-state est utilisée, YYFILL a une sémantique légèrement différente (décrite dans la section sur l'état stockable).

YYFILL avec sentinelle

Si la règle EOF est utilisée, YYFILL est une primitive de type fonction qui n'accepte aucun argument et retourne une valeur qui est comparée à zéro. L'invocation de YYFILL est déclenchée par la condition YYLIMIT <= YYCURSOR dans l'API pointeur C et YYLESSTHAN() dans l'API générique. Une valeur de retour non nulle signifie que YYFILL a échoué. Un appel réussi à YYFILL doit fournir au moins un caractère et ajuster les positions d'entrée en conséquence. La limite doit toujours être définie à un après la dernière position d'entrée dans le tampon, et le caractère à la position de limite doit être le symbole sentinelle spécifié par la configuration re2c:eof. Les schémas ci-dessous montrent les positions relatives des positions d'entrée dans le tampon avant et après l'appel à YYFILL (le symbole sentinelle est marqué par #, et le second schéma montre le cas où il n'y a pas assez d'entrée pour remplir tout le tampon).

} Input;

    if (in->eof) return 1;
    const size_t shift = in->tok - in->buf;
    const size_t static int fill(Input *in) {
    // Error: lexeme too long. In real life could reallocate a larger buffer.
    if (in->shift == 0) return 2;
    // Shift buffer contents (discard everything up to the current token).
    memmove(in->buf, in->tok, in->used);
    in->lim -= in->shift;
    in->cur -= in->shift;
    in->mar -= in->shift;
    in->tok -= in->shift;
    // Fill free space at the end of buffer with new data from file.
    in->lim += fread(in->lim, 1, BUFSIZE - in->used, in->file);
    in->lim[0] = 0;
    in->eof = in->lim < in->buf + BUFSIZE;
    return 0;
}
static int lex(Input *in) {
    int count = 0;
loop:
        in->tok = in->cur;
    /*!re2c
        re2c:api:style = free-form;
        re2c:define:YYCTYPE = char;
        re2c:define:YYCURSOR = in->cur;
        re2c:define:YYMARKER = in->mar;
        re2c:define:YYLIMIT = in->lim;
        re2c:define:YYFILL = "fill(in) == 0";
        re2c:eof = 0;
        str = ['"] ([^'\\] | [\\][^])* ['"];
        *    { return -1; }
        $    { return count; }
        str  { ++count; goto loop; }
        [ ]+ { goto loop; }
    */
}
int main() {
    const char *fname = "input";
    const char content[] = "'qu\0tes' 'are' 'fine: \\'' ";
    // Prepare input file: a few times the size of the buffer, containing
    // strings with zeroes and escaped quotes.
    FILE *f = fopen(fname, "w");
    for (int i = 0; i < BUFSIZE; ++i) {
        fwrite(content, 1, sizeof(content) - 1, f);
    }
    fclose(f);
    int count = 3 * BUFSIZE; // number of quoted strings written to file
    // Initialize lexer state: all pointers are at the end of buffer.
    Input in;
    in.file = fopen(fname, "r");
    in.cur = in.mar = in.tok = in.lim = in.buf + BUFSIZE;
    in.eof = 0;
    // Sentinel (at YYLIMIT pointer) is set to zero, which triggers YYFILL.
    in.lim[0] = 0;
    // Run the lexer.
    assert(lex(&in) == count);
    // Cleanup: remove input file.
    fclose(in.file);
    remove(fname);
    return 0;
}

    for (int i = 0; i < BUFSIZE; ++i) {
        fwrite(content, 1, sizeof(content) - 1, f);
    }
    fclose(f);
    int count = 3 * BUFSIZE; // number of quoted strings written to file
    // Initialize lexer state: all pointers are at the end of buffer.
    // This immediately triggers YYFILL, as the check `in->cur < in->lim` fails.
    Input in;
    in.file = fopen(fname, "r");
    in.cur = in.tok = in.lim = in.buf + BUFSIZE;
    in.eof = 0;
    // Run the lexer.
    assert(lex(&in) == count);
    // Cleanup: remove input file.
    fclose(in.file);
    remove(fname);
    return 0;
}

Le code généré par re2c pour les conditions dépend de l'approche utilisée par re2c : approche goto/label ou approche boucle/switch pour coder les automates.

Dans les langages qui ont une instruction goto (comme C/C++ et Go), les conditions sont naturellement implémentées comme des blocs de code préfixés par des étiquettes de la forme yyc_<cond>, où cond est le nom d'une condition (le préfixe de l'étiquette peut être modifié avec re2c:cond:prefix). Les transitions entre conditions sont implémentées en utilisant goto et des étiquettes de condition. Avant toutes les conditions, re2c génère un switch initial sur YYGETSTATE qui saute vers l'état de départ de la condition courante. Les règles de raccourci :=> contournent le switch initial et sautent directement vers la condition spécifiée (re2c:cond:goto peut être utilisé pour changer le comportement par défaut). Les règles avec des actions sémantiques ne sautent pas automatiquement vers la condition suivante ; cela doit être fait par le code d'action défini par l'utilisateur.

Dans les langages qui n'ont pas de goto (comme Rust), re2c réutilise la variable yystate pour stocker les numéros de condition. Chaque condition reçoit un identifiant numérique égal au numéro de son état de départ, et un switch entre conditions n'est pas différent d'un switch entre états DFA d'une seule condition. Il n'y a pas besoin d'un switch de condition initial séparé. (Étant donné que la même approche est utilisée pour implémenter les états stockables, YYGETCOND/YYSETCOND sont redondants si les états stockables et les conditions sont utilisés).

Il y a un seul bloc où chaque base a sa propre condition, et la condition initiale est connectée à toutes. La variable définie par l'utilisateur cond stocke le numéro de la condition actuelle ; elle est initialisée au numéro de la condition initiale générée avec le bloc conditions.

État stockable

Avec l'option --storable-state, re2c génère un lexer qui peut stocker son état actuel, retourner à l'appelant, et plus tard reprendre les opérations exactement là où il s'est arrêté. Le mode de fonctionnement par défaut dans re2c est un modèle "pull" (tirer), dans lequel le lexer "tire" plus d'entrée dès qu'il en a besoin. Cela peut être inacceptable dans les cas où l'entrée devient disponible morceau par morceau (par exemple, si le lexer est appelé par le parser, ou si le programme lexer communique via un protocole de socket avec un autre programme qui doit attendre une réponse du lexer avant de transmettre le prochain message). La fonctionnalité d'état stockable est destinée exactement à ces cas : elle permet de générer des lexers qui fonctionnent dans un modèle "push" (pousser). Lorsque le lexer a besoin de plus d'entrée, il stocke son état et retourne à l'appelant. Plus tard, lorsque plus d'entrée devient disponible, l'appelant reprend le lexer exactement là où il s'est arrêté. Il y a quelques changements nécessaires par rapport au modèle "pull" :

  • Définir les primitives YYSETSTATE() et YYGETSTATE(state).
  • Définir les variables yych, yyaccept (si utilisé) et state comme faisant partie de l'état persistant du lexer. La variable state doit être initialisée à -1.
  • YYFILL doit retourner au programme externe au lieu d'essayer de fournir plus d'entrée. Le code de retour doit indiquer que le lexer a besoin de plus d'entrée.
  • Le programme externe doit reconnaître les situations où le lexer a besoin de plus d'entrée et répondre de manière appropriée.
  • Utiliser optionnellement le bloc getstate pour générer un switch YYGETSTATE détaché du lexer principal. Cela ne fonctionne que pour les langages qui ont goto (pas en mode --loop-switch).
  • Utiliser re2c:eof et la méthode sentinelle avec vérifications des limites pour gérer la fin de l'entrée. La méthode basée sur le padding peut ne pas fonctionner car il n'est pas clair quand ajouter le padding : la fin actuelle de l'entrée peut ne pas être la fin ultime de l'entrée, et ajouter le padding trop tôt peut couper un lexème gourmand partiellement lu. De plus, en raison de la logique du programme de haut niveau, obtenir plus d'entrée peut dépendre du traitement du lexème à la fin du buffer (qui est déjà bloqué en raison de la condition de fin d'entrée).

Voici un exemple de lexer en modèle "push" qui simule la lecture de paquets depuis un socket. Le lexer boucle jusqu'à ce qu'il rencontre la fin de l'entrée et retourne à la fonction appelante. La fonction appelante fournit plus d'entrée en "envoyant" le paquet suivant et reprend l'analyse. Ce processus s'arrête lorsque tous les paquets ont été envoyés, ou lorsqu'il y a une erreur.

// re2c $INPUT -o $OUTPUT -f
#include <assert.h>
#include <stdio.h>
#include <string.h>
#define DEBUG 0
#define LOG(...) if (DEBUG) fprintf(stderr, __VA_ARGS__);
// Utiliser un petit buffer pour couvrir le cas où un lexème ne rentre pas.
// Dans la vie réelle, utiliser un buffer plus grand.
#define BUFSIZE 10
typedef struct {
    FILE *file;
    char buf[BUFSIZE + 1], *lim, *cur, *mar, *tok;
    int state;
} State;
typedef enum {END, READY, WAITING, BAD_PACKET, BIG_PACKET} Status;
static Status fill(State *st) {
    const size_t shift = st->tok - st->buf;
    const size_t used = st->lim - st->tok;
    const size_t free = BUFSIZE - used;
    // Erreur : pas d'espace. Dans la vie réelle, on peut réallouer un buffer plus grand.
    if (free < 1) return BIG_PACKET;
    // Décaler le contenu du buffer (ignorer les données déjà traitées).
    memmove(st->buf, st->tok, used);
    st->lim -= shift;
    st->cur -= shift;
    st->mar -= shift;
    st->tok -= shift;
    // Remplir l'espace libre à la fin du buffer avec de nouvelles données.
    const size_t read = fread(st->lim, 1, free, st->file);
    st->lim += read;
    st->lim[0] = 0; // ajouter le symbole sentinelle
    return READY;
}
static Status lex(State *st, unsigned int *recv) {
    char yych;
    /*!getstate:re2c*/
    for (;;) {
        st->tok = st->cur;
    /*!re2c
        re2c:api:style = free-form;
        re2c:define:YYCTYPE = "char";
        re2c:define:YYCURSOR = "st->cur";
        re2c:define:YYMARKER = "st->mar";
        re2c:define:YYLIMIT = "st->lim";
        re2c:define:YYGETSTATE = "st->state";
        re2c:define:YYSETSTATE = "st->state = @@;";
        re2c:define:YYFILL = "return WAITING;";
        re2c:eof = 0;
        packet = [a-z]+[;];
        *      { return BAD_PACKET; }
        $      { return END; }
        packet { *recv = *recv + 1; continue; }
    */
    }
}
void test(const char **packets, Status expect) {
    // Créer un "socket" (ouvrir le même fichier en lecture et en écriture).
    const char *fname = "pipe";
    FILE *fw = fopen(fname, "w");
    FILE *fr = fopen(fname, "r");
    setvbuf(fw, NULL, _IONBF, 0);
    setvbuf(fr, NULL, _IONBF, 0);
    // Initialiser l'état du lexer : la valeur de `state` est -1, tous les pointeurs sont à la fin
    // du buffer.
    State st;
    st.file = fr;
    st.cur = st.mar = st.tok = st.lim = st.buf + BUFSIZE;
    // La sentinelle (au pointeur YYLIMIT) est mise à zéro, ce qui déclenche YYFILL.
    st.lim[0] = 0;
    st.state = -1;
    // Boucle principale. Le buffer contient des données incomplètes qui apparaissent paquet par
    // paquet. Lorsque le lexer a besoin de plus d'entrée, il sauvegarde son état interne et
    // retourne à l'appelant qui doit fournir plus d'entrée et reprendre l'analyse.
    Status status;
    unsigned int send = 0, recv = 0;
    for (;;) {
        status = lex(&st, &recv);
        if (status == END) {
            LOG("done: got %u packets\n", recv);
            break;
        } else if (status == WAITING) {
            LOG("waiting...\n");
            if (*packets) {
                LOG("paquet envoyé %u\n", send);
                fprintf(fw, "%s", *packets++);
                ++send;
            }
            status = fill(&st);
            LOG("file d'attente : '%s'\n", st.buf);
            if (status == BIG_PACKET) {
                LOG("erreur : paquet trop gros\n");
                break;
            }
            assert(status == READY);
        } else {
            assert(status == BAD_PACKET);
            LOG("erreur : paquet mal formé\n");
            break;
        }
    }
    // Vérifier les résultats.
    assert(status == expect);
    if (status == END) assert(recv == send);
    // Nettoyage : supprimer le fichier d'entrée.
    fclose(fw);
    fclose(fr);
    remove(fname);
}
int main() {
    const char *packets1[] = {0};
    const char *packets2[] = {"zéro;", "un;", "deux;", "trois;", "quatre;", 0};
    const char *packets3[] = {"zéor0;", 0};
    const char *packets4[] = {"lonnnnnnnnnng;", 0};
    test(packets1, END);
    test(packets2, END);
    test(packets3, BAD_PACKET);
    test(packets4, BIG_PACKET);
    return 0;
}

Blocs réutilisables

Les blocs réutilisables de la forme /*!rules:re2c[:<nom>] ... */ ou %{règles[:<nom>] ... %} peuvent être réutilisés un nombre quelconque de fois et combinés avec d'autres blocs re2c. Le <nom> est facultatif. Un bloc de règles peut être utilisé dans un bloc ou une directive use. Le code d'un bloc de règles est généré à chaque point d'utilisation.

Les blocs use sont définis avec /*!use:re2c[:<nom>] ... */ ou %{use[:<nom>] ... %}. Le <nom> est facultatif : s'il n'est pas spécifié, le bloc de règles associé est le plus récent (nommé ou anonyme). Un bloc use peut ajouter ses propres définitions nommées, configurations et règles. Un cas d'utilisation important des blocs use est un analyseur lexical qui prend en charge plusieurs encodages d'entrée : le même bloc de règles est réutilisé plusieurs fois avec des configurations spécifiques à l'encodage (voir l'exemple ci-dessous).

La directive in-block !use:<nom>; peut être utilisée à l'intérieur d'un bloc re2c. Elle fusionne le bloc référencé <nom> dans le bloc actuel. Si certaines des règles et configurations fusionnées chevauchent celles précédemment définies, les conflits sont résolus de la manière habituelle : la première règle a la priorité, et la dernière configuration remplace les précédentes. Une exception concerne les règles spéciales *, $ et (en mode condition) <!>, pour lesquelles une définition locale au bloc a la priorité sur toute définition héritée. La directive use permet de combiner différents blocs re2c au sein d'un même bloc (voir l'exemple ci-dessous).

Les blocs nommés et la directive in-block use ont été ajoutés dans re2c version 2.2. Depuis cette version, les blocs réutilisables sont autorisés par défaut (aucune option spéciale n'est nécessaire). Avant la version 2.2, le mode de réutilisation était activé avec l'option -r --reusable. Avant la version 1.2, les blocs réutilisables ne pouvaient pas être mélangés avec des blocs normaux.

Exemple d'une directive !use

// re2c $INPUT -o $OUTPUT
#include <assert.h>
// Cet exemple montre comment combiner des blocs re2c réutilisables : deux blocs
// ('colors' et 'fish') sont fusionnés en un seul. La règle 'salmon' apparaît dans les deux blocs ; le bloc 'fish' a la priorité car il est utilisé plus tôt. La règle par défaut * apparaît dans les trois blocs ; la définition locale (non héritée) a la priorité.
typedef enum { COLOR, FISH, DUNNO } What;
/*!rules:re2c:colors
    *                            { assert(false); }
    "rouge" | "saumon" | "magenta" { return COLOR; }
*/
/*!rules:re2c:fish
    *                            { assert(false); }
    "églefin" | "saumon" | "anguille" { return FISH; }
*/
static What lex(const char *s) {
    const char *YYCURSOR = s, *YYMARKER;
    /*!re2c
        re2c:yyfill:enable = 0;
        re2c:define:YYCTYPE = char;
        !use:fish;
        !use:colors;
        * { return DUNNO; }  // remplace les règles '*' héritées
    */
}
int main() {
    assert(lex("saumon") == FISH);
    assert(lex("quoi ?") == DUNNO);
    return 0;
}

Extraction de sous-correspondances

re2c dispose de deux options pour l'extraction de sous-correspondances.

Tags
La première option consiste à utiliser des tags autonomes de la forme @stag ou #mtag, où stag et mtag sont des noms arbitraires définis par l'utilisateur. Les tags sont activés avec l'option -T --tags ou la configuration re2c:tags = 1. Sémantiquement, les tags sont des marqueurs de position : ils peuvent être insérés n'importe où dans une expression régulière et sont liés à la position correspondante (ou aux positions multiples) dans la chaîne d'entrée. Les tags-S sont liés à la dernière position correspondante, et les tags-m sont liés à une liste de positions (ils peuvent être utilisés dans des sous-expressions répétitives, où une seule position dans une expression régulière correspond à plusieurs positions dans la chaîne d'entrée). Tous les tags doivent être définis par l'utilisateur, soit manuellement, soit à l'aide de blocs svars et mvars. S'il existe plus d'une façon de faire correspondre les tags à l'entrée, l'ambiguïté est résolue en utilisant une stratégie de désambiguïsation gloutonne la plus à gauche.
Captures
La deuxième option consiste à utiliser des groupes de capture. Ils sont activés avec l'option --captures ou la configuration re2c:captures = 1. Il existe deux variantes pour différentes politiques de désambiguïsation : --leftmost-captures (par défaut) pour la politique gloutonne la plus à gauche, et --posix-captures pour la politique de correspondance la plus longue POSIX. Dans ce mode, toutes les sous-expressions entre parenthèses sont considérées comme des groupes de capture, et un point d'exclamation peut être utilisé pour marquer les groupes non capturants : (! ... ). Avec l'option --invert-captures ou la configuration re2c:invert-captures = 1, le sens du point d'exclamation est inversé. Le nombre de groupes pour la règle correspondante est stocké dans une variable yynmatch (l'expression régulière entière est le groupe numéro zéro), et les résultats des sous-correspondances sont stockés dans le tableau yypmatch. yynmatch et yypmatch doivent être définis par l'utilisateur, et la taille de yypmatch doit être au moins de [yynmatch * 2]. Utilisez le bloc maxnmatch pour définir YYMAXNMATCH, une constante égale à la valeur maximale de yynmatch parmi toutes les règles.
Captvars
Une autre façon d'utiliser les groupes de capture est l'option --captvars ou la configuration re2c:captvars = 1. La seule différence avec --captures réside dans la manière dont le code généré stocke les résultats des sous-correspondances : au lieu de yynmatch et yypmatch, re2c génère les variables yytl<k> et yytr<k> pour le k-ième groupe de capture (l'utilisateur doit les déclarer à l'aide d'un bloc svars). Les captures avec variables prennent en charge deux politiques de désambiguïsation : --leftmost-captvars ou re2c:leftmost-captvars = 1 pour la politique gloutonne la plus à gauche (par défaut) et --posix-captvars ou re2c:posix-captvars pour la politique de correspondance la plus longue POSIX.

Sous le capot, toutes ces options se traduisent par des tags et des automates finis déterministes tagués avec anticipation (TDFA). L'idée principale des TDFA est de minimiser la surcharge liée à l'extraction de sous-correspondances. Dans le cas extrême, s'il n'y a pas de tags ou de captures dans une expression régulière, un TDFA est simplement un DFA ordinaire. Si le nombre de tags est modéré, la surcharge est à peine perceptible. Le TDFA généré utilise un certain nombre de variables de tag qui ne correspondent pas directement aux tags : une seule variable peut être utilisée pour différents tags, et un tag peut nécessiter plusieurs variables pour contenir toutes ses valeurs possibles. Finalement, l'ambiguïté est résolue, et une seule variable finale par tag survit. Les variables de tag doivent être définies à l'aide des blocs stags ou mtags. Si l'état de l'analyseur lexical est stocké, les variables de tag doivent en faire partie. Elles doivent également être mises à jour par YYFILL.

Les tags-S prennent en charge les opérations suivantes :

  • sauvegarder la position d'entrée dans un tag-S : t = YYCURSOR avec l'API pointeur C ou une opération définie par l'utilisateur YYSTAGP(t) avec l'API générique
  • sauvegarder la valeur par défaut dans un tag-S : t = NULL avec l'API pointeur C ou une opération définie par l'utilisateur YYSTAGN(t) avec l'API générique
  • copier un tag-S dans un autre : t1 = t2

Les tags-m prennent en charge les opérations suivantes :

  • ajouter la position d'entrée à un tag-m : une opération définie par l'utilisateur YYMTAGP(t) avec l'API par défaut et générique
  • ajouter la valeur par défaut à un tag-m : une opération définie par l'utilisateur YYMTAGN(t) avec l'API par défaut et générique
  • copier un tag-m dans un autre : t1 = t2

Les tags-S peuvent être implémentés comme des valeurs scalaires (pointeurs ou décalages). Les tags-m nécessitent une représentation plus complexe, car ils doivent stocker une séquence de valeurs de tag. La représentation la plus naïve et la moins efficace d'un tag-m est une liste (tableau, vecteur) de valeurs de tag ; une représentation plus efficace consiste à stocker tous les tags-m dans un arbre préfixe représenté par un tableau de nœuds (v, p), où v est la valeur du tag et p est un pointeur vers le nœud parent.

Voici un exemple plus complexe d'utilisation des balises s avec YYFILL pour analyser un fichier avec des versions sémantiques séparées par des sauts de ligne. Les variables de balise font partie de l'état de l'analyseur lexical et sont ajustées dans YYFILL comme d'autres positions d'entrée. Notez que c'est nécessaire pour les balises s car leurs valeurs sont invalidées après le décalage du contenu du tampon. Cela peut ne pas être nécessaire dans une implémentation personnalisée où les variables de balise stockent des décalages par rapport au début de la chaîne d'entrée plutôt qu'au tampon, ce qui peut être le cas avec les balises m.

// re2c $INPUT -o $OUTPUT --tags
#include <assert.h>
#include <stddef.h>
#include <stdio.h>
#include <string.h>
#include <vector>
#define BUFSIZE 4095
struct Input {
    FILE *file;
    char buf[BUFSIZE + 1], *lim, *cur, *mar, *tok;
    // Les variables de balise doivent faire partie de l'état de l'analyseur lexical passé à YYFILL.
    // Elles ne correspondent pas aux balises et doivent être auto-générées par re2c.
    /*!stags:re2c format = 'const char *@@;'; */
    bool eof;
};
struct SemVer { int major, minor, patch; };
static bool operator==(const SemVer &x, const SemVer &y) {
    return x.major == y.major && x.minor == y.minor && x.patch == y.patch;
}
static int s2n(const char *s, const char *e) { // chaîne pré-analysée en nombre
    int n = 0;
    for (; s < e; ++s) n = n * 10 + (*s - '0');
    return n;
}
static int fill(Input &in) {
    if (in.eof) return 1;
    const size_t shift = in.tok - in.buf;
    const size_t used = in.lim - in.tok;
    // Erreur : lexème trop long. Dans la vraie vie, on pourrait réallouer un tampon plus grand.
    if (shift < 1) return 2;
    // Décaler le contenu du tampon (ignorer tout ce qui précède le jeton actuel).
    memmove(in.buf, in.tok, used);
    in.lim -= shift;
    in.cur -= shift;
    in.mar -= shift;
    in.tok -= shift;
    // Les variables de balise doivent être décalées comme les autres positions d'entrée. La vérification
    // de non-NULL n'est nécessaire que si certaines balises sont imbriquées à l'intérieur d'alternatives
    // ou de répétitions, afin qu'elles puissent avoir une valeur NULL.
    /*!stags:re2c format = "if (in.@@) in.@@ -= shift;\n"; */
    // Remplir l'espace libre à la fin du tampon avec de nouvelles données du fichier.
    in.lim += fread(in.lim, 1, BUFSIZE - used, in.file);
    in.lim[0] = 0;
    in.eof = in.lim < in.buf + BUFSIZE;
    return 0;
}
static bool lex(Input &in, std::vector<SemVer> &vers) {
    // Variables locales définies par l'utilisateur qui stockent les valeurs finales des balises.
    // Elles sont différentes des variables de balise auto-générées avec `stags:re2c`,
    // car elles sont définies à la fin de la correspondance et utilisées uniquement dans les actions sémantiques.
    const char *t1, *t2, *t3, *t4;
    for (;;) {
        in.tok = in.cur;
    /*!re2c
        re2c:eof = 0;
        re2c:api:style = free-form;
        re2c:define:YYCTYPE = char;
        re2c:define:YYCURSOR = in.cur;
        re2c:define:YYMARKER = in.mar;
        re2c:define:YYLIMIT = in.lim;
        re2c:define:YYFILL = "fill(in) == 0";
        re2c:tags:expression = "in.@@";
        num = [0-9]+;
        num @t1 "." @t2 num @t3 ("." @t4 num)? [\n] {
            int major = s2n(in.tok, t1);
            int minor = s2n(t2, t3);
            int patch = t4 != NULL ? s2n(t4, in.cur - 1) : 0;
            SemVer ver = {major, minor, patch};
            vers.push_back(ver);
            continue;
        }
        $ { return true; }
        * { return false; }
    */}
}
int main() {
    const char *fname = "input";
    const SemVer semver = {1, 22, 333};
    std::vector<SemVer> expect(BUFSIZE, semver), actual;
    // Préparer le fichier d'entrée (s'assurer qu'il dépasse la taille du tampon).
    FILE *f = fopen(fname, "w");
    for (int i = 0; i < BUFSIZE; ++i) fprintf(f, "1.22.333\n");
    fclose(f);
    // Rouvrir le fichier d'entrée en lecture.
    f = fopen(fname, "r");
    // Initialiser l'état de l'analyseur lexical : tous les pointeurs sont à la fin du tampon.
    Input in;
    in.file = f;
    in.cur = in.mar = in.tok = in.lim = in.buf + BUFSIZE;
    /*!stags:re2c format = "in.@@ = in.lim;\n"; */
    in.eof = false;
    // Le sentinelle (au pointeur YYLIMIT) est défini à zéro, ce qui déclenche YYFILL.
    *in.lim = 0;
    // Exécuter l'analyseur lexical et vérifier les résultats.
    assert(lex(in, actual) && expect == actual);
    // Nettoyage : supprimer le fichier d'entrée.
    fclose(f);
    remove(fname);
    return 0;
}

Voici un exemple d'utilisation des balises m pour analyser une version avec un nombre variable de composants. Les variables de balise sont stockées dans un trie.

// re2c $INPUT -o $OUTPUT
#include <assert.h>
#include <stddef.h>
#include <vector>
static const int MTAG_ROOT = -1;
// Un arbre de balises m est un moyen de stocker des historiques avec une opération de copie en O(1).
// Les historiques forment naturellement un arbre, car ils ont un début commun et se bifurquent à un moment donné.
// L'arbre est stocké sous forme de tableau de paires (valeur de la balise, lien vers le parent).
// Une balise m est représentée par un seul lien dans l'arbre (index du tableau).
struct Mtag {
    const char *elem; // valeur de la balise
    int pred; // index du nœud prédécesseur ou de la racine
};
typedef std::vector<Mtag> MtagTrie;
typedef std::vector<int> Ver; // nombre illimité de composants de version
static int s2n(const char *s, const char *e) { // chaîne pré-analysée en nombre
    int n = 0;
    for (; s < e; ++s) n = n * 10 + (*s - '0');
    return n;
}
// Ajouter une seule valeur à un historique de balises m.
static void add_mtag(MtagTrie &trie, int &mtag, const char *value) {
    Mtag m = {value, mtag};
    mtag = (int)trie.size();
    trie.push_back(m);
}
// Dérouler récursivement les historiques de balises et collecter les composants de version.
static void unfold(const MtagTrie &trie, int x, int y, Ver &ver) {
    // Atteint la racine de l'arbre de balises m, arrêter la récursion.
    if (x == MTAG_ROOT && y == MTAG_ROOT) return;
    // Dérouler davantage l'historique.
    unfold(trie, trie[x].pred, trie[y].pred, ver);
    // Obtenir les valeurs des balises. Les historiques de balises doivent avoir la même longueur.
    assert(x != MTAG_ROOT && y != MTAG_ROOT);
    const char *ex = trie[x].elem, *ey = trie[y].elem;
    if (ex != NULL && ey != NULL) {
        // Les deux balises sont des pointeurs valides, extraire le composant.
        ver.push_back(s2n(ex, ey));
    } else {
        // Les deux balises sont NULL (cela correspond à zéro répétition).
        assert(ex == NULL && ey == NULL);
    }
}
static bool parse(const char *str, Ver &ver) {
    const char *YYCURSOR = str, *YYMARKER;
    MtagTrie mt;
    // Variables de balise définies par l'utilisateur disponibles dans l'action sémantique.
    const char *t1, *t2;
    int t3, t4;
    // Variables de balise auto-générées utilisées par l'analyseur lexical pour suivre les valeurs des balises.
    /*!stags:re2c format = 'const char *@@ = NULL;'; */
    /*!mtags:re2c format = 'int @@ = MTAG_ROOT;'; */
    /*!re2c
        re2c:api:style = free-form;
        re2c:define:YYCTYPE = char;
        re2c:define:YYSTAGP = "@@ = YYCURSOR;";
        re2c:define:YYSTAGN = "@@ = NULL;";
        re2c:define:YYMTAGP = "add_mtag(mt, @@, YYCURSOR);";
        re2c:define:YYMTAGN = "add_mtag(mt, @@, NULL);";
        re2c:yyfill:enable = 0;
        re2c:tags = 1;
        num = [0-9]+;
        @t1 num @t2 ("." #t3 num #t4)* [\x00] {
            ver.clear();
            ver.push_back(s2n(t1, t2));
            unfold(mt, t3, t4, ver);
            return true;
        }
        * { return false; }
    */
}
int main() {
    Ver v;
    assert(parse("1", v) && v == Ver({1}));
    assert(parse("1.2.3.4.5.6.7", v) && v == Ver({1, 2, 3, 4, 5, 6, 7}));
    assert(!parse("1.2.", v));
    return 0;
}

Support d'encodage

Il est nécessaire de comprendre la différence entre les points de code et les unités de code. Un point de code est un identifiant numérique d'un symbole. Une unité de code est la plus petite unité de stockage dans le texte encodé. Un seul point de code peut être représenté par une ou plusieurs unités de code. Dans un encodage de longueur fixe, tous les points de code sont représentés par le même nombre d'unités de code. Dans un encodage de longueur variable, les points de code peuvent être représentés par un nombre différent d'unités de code. Notez que la règle "tout" [^] correspond à n'importe quel point de code, mais pas nécessairement à n'importe quelle unité de code (la seule façon de correspondre à n'importe quelle unité de code, quel que soit l'encodage, est la règle par défaut *). L'analyseur lexical généré fonctionne avec un flux d'unités de code : yych stocke une unité de code, et YYCTYPE est le type de l'unité de code. Les expressions régulières, en revanche, sont spécifiées en termes de points de code. Lorsque re2c compile des expressions régulières en automates, il traduit les points de code en unités de code. Ce n'est généralement pas un mappage simple : dans les encodages à longueur variable, une seule plage de points de code peut être traduite en un comportement complexe.

  • ASCII (activé par défaut). C'est un encodage à longueur fixe avec un espace de code [0-255] et des points de code et des unités de code de 1 octet.
  • EBCDIC (activé avec --ebcdic ou re2c:encoding:ebcdic). C'est un encodage à longueur fixe avec un espace de code [0-255] et des points de code et des unités de code de 1 octet.
  • UCS2 (activé avec --ucs2 ou re2c:encoding:ucs2). C'est un encodage à longueur fixe avec un espace de code [0-0xFFFF] et des points de code et des unités de code de 2 octets.
  • UTF8 (activé avec --utf8 ou re2c:encoding:utf8). C'est un encodage Unicode à longueur variable. La taille de l'unité de code est de 1 octet. Les points de code sont représentés avec 1 à 4 unités de code.
  • UTF16 (activé avec --utf16 ou re2c:encoding:utf16). C'est un encodage Unicode à longueur variable. La taille de l'unité de code est de 2 octets. Les points de code sont représentés avec 1 à 2 unités de code.
  • UTF32 (activé avec --utf32 ou re2c:encoding:utf32). C'est un encodage Unicode à longueur fixe avec un espace de code [0-0x10FFFF] et des points de code et des unités de code de 4 octets.

Le fichier d'inclusion include/unicode_categories.re fournit les définitions re2c pour les catégories Unicode standard.

L'option --input-encoding spécifie l'encodage du fichier source, qui peut être utilisé pour activer les littéraux Unicode dans les expressions régulières. Par exemple, --input-encoding utf8 indique à re2c que le fichier source est en UTF8 (cela diffère de --utf8 qui définit l'encodage du texte d'entrée). L'option --encoding-policy spécifie la manière dont re2c gère les substituts Unicode (points de code dans la plage [0xD800-0xDFFF]).

re2c permet d'inclure d'autres fichiers en utilisant un bloc de la forme /*!include:re2c FILE */ ou %{include FILE %}, ou une directive dans le bloc !include FILE ;, où FILE est le chemin d'accès au fichier à inclure. re2c recherche les fichiers d'inclusion dans le répertoire du fichier incluant et dans les emplacements d'inclusion, qui peuvent être spécifiés avec l'option -I. Programmes squelettes

Avec l'option -S, --skeleton, re2c ignore tout le code non-re2c et génère un programme C autonome qui peut être compilé et exécuté ultérieurement. Le programme se compose du code du lexer et des données d'entrée. Pour chaque DFA construit (bloc ou condition), re2c génère un lexer autonome et deux fichiers : un fichier .input avec des chaînes dérivées du DFA et un fichier .keys avec les résultats de correspondance attendus. Le programme exécute chaque lexer sur le fichier .input correspondant et compare les résultats avec les attentes. Les programmes squelettes sont très utiles pour plusieurs raisons :

  • Ils peuvent vérifier la correction de diverses optimisations re2c (les données sont générées tôt dans le processus, avant toute transformation du DFA).
  • La génération d'un ensemble de données d'entrée avec une bonne couverture peut être utile pour les tests et le benchmarking.
  • La génération de programmes exécutables autonomes permet d'obtenir des cas de test minimisés (le code d'origine peut être volumineux ou avoir beaucoup de dépendances).

La difficulté de générer des données d'entrée est que, pour tous les cas sauf les plus triviaux, le nombre de chaînes d'entrée possibles est trop grand (même si la longueur de la chaîne est limitée). re2c résout cette difficulté en générant suffisamment de chaînes pour couvrir la quasi-totalité des transitions du DFA. Il utilise l'algorithme suivant. Premièrement, il construit un squelette du DFA. Pour les encodages avec une taille d'unité de code de 1 octet (comme ASCII, UTF-8 et EBCDIC), le squelette est une copie exacte du DFA original. Pour les encodages avec des unités de code multibytes, le squelette est une copie du DFA avec certaines transitions omises : re2c prend au maximum 256 unités de code pour chaque plage continue disjointes qui correspond à une transition du DFA. Les valeurs choisies sont réparties uniformément et incluent les limites des plages. Au lieu d'essayer de couvrir tous les chemins possibles dans le squelette (ce qui est infaisable), re2c génère suffisamment de chemins pour couvrir toutes les transitions du squelette, et ainsi déclencher les sauts conditionnels correspondants dans le lexer. L'implémentation de l'algorithme est limitée à environ 1 Go de transitions et consomme une quantité constante de mémoire (re2c écrit les données dans le fichier dès qu'elles sont générées).

Visualisation et débogage

Avec l'option -D, --emit-dot, re2c ne génère pas de code. Au lieu de cela, il déverse le DFA généré au format DOT. On peut convertir ce déversement en une image du DFA à l'aide de Graphviz ou d'une autre bibliothèque. Notez que cette option montre le DFA final après qu'il a subi un certain nombre d'optimisations et de transformations. Les étapes précédentes peuvent être déversées avec diverses options de débogage, telles que --dump-nfa, --dump-dfa-raw, etc. (voir la liste complète des options).

RE2C — générateur d'analyseurs lexicaux

NAME

re2c — générateur d'analyseurs lexicaux

SYNOPSIS

re2c [options] [fichier...]

INTRODUCTION

re2c est un outil qui génère des analyseurs lexicaux (scanners) à partir de grammaires régulières. Il est conçu pour être rapide, efficace et facile à utiliser. Il produit du code C/C++ qui peut être intégré dans des applications existantes.

BASICS

La syntaxe de base de re2c consiste à spécifier des règles de correspondance régulières associées à des actions. Par exemple : 

"abc" { /* action */ }
[a-z]+ { /* action */ }

re2c prend en entrée un fichier contenant ces règles et génère du code C/C++ qui implémente un analyseur lexical basé sur ces règles.

HANDLING THE END OF INPUT

re2c fournit des mécanismes pour gérer la fin de l'entrée. Le marqueur EOF peut être utilisé pour détecter la fin de la chaîne d'entrée. 

$ { /* action à la fin de l'entrée */ }

BUFFER REFILLING

Pour traiter de grandes entrées, re2c prend en charge le remplissage de tampons. Cela permet à l'analyseur lexical de lire des données par morceaux sans avoir à tout charger en mémoire.

FEATURES

  • Génération de code C/C++ optimisé.
  • Support des expressions régulières POSIX.
  • Gestion de la fin de l'entrée.
  • Mécanismes de remplissage de tampon.
  • Flexibilité dans la définition des actions.
  • Options de configuration étendues.
