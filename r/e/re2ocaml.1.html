NOM

re2ocaml - générer des analyseurs lexicaux rapides pour OCaml

SYNOPSIS

re2ocaml [ OPTIONS ] [ AVERTISSEMENTS ] ENTRÉE

L'entrée peut être un fichier ou - pour l'entrée standard.

INTRODUCTION

re2ocaml fonctionne comme un préprocesseur. Il lit le fichier d'entrée (qui est généralement un programme en OCaml, mais peut être n'importe quoi) et recherche des blocs de code délimités par des marqueurs de début/fin de forme spéciale. Le texte en dehors de ces blocs est copié tel quel dans le fichier de sortie. Le contenu des blocs est traité par re2ocaml. Il le traduit en code OCaml et génère le code en remplacement du bloc.

Voici un exemple d'un petit programme qui vérifie si une chaîne donnée contient un nombre décimal :

(* re2ocaml $INPUT -o $OUTPUT -i *)
open String
type state = {
    yyinput: string;
    mutable yycursor: int;
}
%{
    re2c:YYFN = ["lex;bool", "yyrecord;state"];
    re2c:yyfill:enable = 0;
    [1-9][0-9]* { true }
    *           { false }
%}
let main () =
    let st = {yyinput = "1234"; yycursor = 0}
    in if not (lex st) then raise (Failure "error")
let _ = main ()

Dans la sortie, re2ocaml a remplacé le bloc du milieu par le code généré :

(* Généré par re2ocaml *)
(* re2ocaml $INPUT -o $OUTPUT -i *)
open String
type state = {
    yyinput: string;
    mutable yycursor: int;
}
let rec yy0 (yyrecord : state) : bool =
    let yych = unsafe_get yyrecord.yyinput yyrecord.yycursor in
    yyrecord.yycursor <- yyrecord.yycursor + 1;
    match yych with
        | '1'..'9' -> (yy2 [@tailcall]) yyrecord
        | _ -> (yy1 [@tailcall]) yyrecord
and yy1 (yyrecord : state) : bool =
    false
and yy2 (yyrecord : state) : bool =
    let yych = unsafe_get yyrecord.yyinput yyrecord.yycursor in
    match yych with
        | '0'..'9' ->
            yyrecord.yycursor <- yyrecord.yycursor + 1;
            (yy2 [@tailcall]) yyrecord
        | _ -> (yy3 [@tailcall]) yyrecord
and yy3 (yyrecord : state) : bool =
    true
and lex (yyrecord : state) : bool =
    (yy0 [@tailcall]) yyrecord
let main () =
    let st = {yyinput = "1234"; yycursor = 0}
    in if not (lex st) then raise (Failure "error")
let _ = main ()

BASES

Un programme re2ocaml consiste en une séquence de blocs entremêlés de code dans le langage cible. Un bloc peut contenir des définitions, des configurations, des règles, des actions et des directives dans n'importe quel ordre :

nom = expression-régulière ;
Une définition lie nom à expression-régulière. Les noms peuvent contenir des caractères alphanumériques et des underscores. La section expressions régulières donne un aperçu de la syntaxe re2ocaml pour les expressions régulières. Une fois défini, le nom peut être utilisé dans d'autres expressions régulières et dans les règles. La récursion dans les définitions nommées n'est pas autorisée, et chaque nom doit être défini avant d'être utilisé. Un bloc hérite des définitions nommées de la portée globale. Redéfinir un nom qui existe dans la portée actuelle est une erreur.
configuration = valeur ;
Une configuration permet de modifier le comportement de re2ocaml et de personnaliser le code généré. Pour une liste complète des configurations supportées par re2ocaml, consultez la section configurations. Selon la configuration, la valeur peut être un mot-clé, un nombre entier non négatif ou une chaîne de caractères sur une seule ligne qui doit être délimitée par des guillemets doubles ou simples, sauf si elle ne contient que des caractères alphanumériques. Un bloc hérite des configurations de la portée globale et peut les redéfinir ou en ajouter de nouvelles. Les configurations définies à l'intérieur d'un bloc affectent l'ensemble du bloc, même si elles apparaissent à la fin de celui-ci.
expression-régulière code
Une règle lie une expression-régulière à son action sémantique (un bloc de code entre accolades, ou un bloc de code commençant par := et se terminant à la fin de la ligne suivie d'un caractère non blanc). Si l'expression-régulière correspond, le code associé est exécuté. Si plusieurs règles correspondent, la correspondance la plus longue a la priorité. Si plusieurs règles correspondent à la même chaîne, la première d'entre elles a la priorité. Il existe deux règles spéciales : la règle par défaut * et la règle de fin d'entrée $. La règle par défaut doit toujours être définie, elle a la priorité la plus basse quelle que soit sa place dans le bloc, et elle correspond à toute unité de code (pas nécessairement un caractère valide, voir la section prise en charge de l'encodage). La règle de fin d'entrée doit être définie si la méthode correspondante pour la gestion de la fin d'entrée est utilisée. Avec les conditions initiales, les règles ont une syntaxe plus complexe.
!action code
Une action lie un bloc de code défini par l'utilisateur à un endroit particulier dans la machine à états finis générée (de la même manière que les actions sémantiques lient le code aux états finaux). Voir la section actions pour une liste complète des actions prédéfinies.
!directive ;
Une directive est l'une des instructions spéciales prédéfinies. Chaque directive a un objectif unique. Voir la section directives pour plus de détails.

Blocs

Les marqueurs de début et de fin de bloc sont soit /*!re2c et */, soit %{ et %} (les deux styles sont supportés). Depuis la version 2.2, les blocs peuvent avoir des noms optionnels qui permettent de les référencer dans d'autres blocs. Il existe différents types de blocs :

/*!re2c[:<nom>] ... */ ou %{[:<nom>] ... %}
Un bloc global contient des définitions, des configurations, des règles et des directives. re2ocaml compile les expressions régulières associées à chaque règle en un automate fini déterministe, l'encode sous forme de sauts conditionnels dans le langage cible et remplace le bloc par le code généré. Les noms et configurations définis dans un bloc global sont ajoutés à la portée globale et deviennent visibles pour les blocs suivants. Au début du programme, la portée globale est initialisée avec les options de la ligne de commande.
/*!local:re2c[:<nom>] ... */ ou %{local[:<nom>] ... %}
Un bloc local est similaire à un bloc global, mais les noms et configurations qu'il contient ont une portée locale (ils n'affectent pas les autres blocs).
/*!rules:re2c[:<nom>] ... */ ou %{rules[:<nom>] ... %}
Un bloc de règles est similaire à un bloc local, mais il ne génère aucun code en soi, ni n'ajoute de définitions à la portée globale -- il est destiné à être réutilisé dans d'autres blocs. C'est une façon de partager du code (plus de détails dans la section blocs réutilisables). Avant la version 2.2 de re2ocaml, les blocs de règles nécessitaient l'option -r --reusable.
/*!use:re2c[:<nom>] ... */ ou %{use[:<nom>] ... %}
Un bloc d'utilisation qui référence un bloc de règles défini précédemment. Si le nom est spécifié, re2ocaml recherche les blocs de règles portant ce nom. Sinon, le bloc de règles le plus récent est utilisé (qu'il soit nommé ou non. Un bloc d'utilisation peut ajouter ses propres définitions, configurations et règles, qui sont ajoutées à celles du bloc de règles référencé. Avant la version 2.2 de re2ocaml, les blocs d'utilisation nécessitaient l'option -r --reusable.
/*!max:re2c[:<nom1>[:<nom2>...]] ... */ ou %{max[:<nom1>[:<nom2>...]] ... %}
Un bloc qui génère la définition YYMAXFILL. Une liste optionnelle de noms de blocs spécifie quels blocs doivent être inclus lors du calcul de la valeur YYMAXFILL (si la liste est vide, tous les blocs sont inclus). Par défaut, le code généré est une macro-définition pour C (#define YYMAXFILL <n>), ou une variable globale pour Go (var YYMAXFILL int = <n>). Il peut être personnalisé avec une configuration optionnelle format qui spécifie une chaîne de modèle où @@{max} (ou @@ en abrégé) est remplacé par la valeur numérique de YYMAXFILL.
/*!maxnmatch:re2c[:<nom1>[:<nom2>...]] ... */ ou %{maxnmatch[:<nom1>[:<nom2>...]] ... %}
Un bloc qui génère la définition YYMAXNMATCH (nécessite l'option -P --posix-captures). Une liste optionnelle de noms de blocs spécifie quels blocs doivent être inclus lors du calcul de Y
YMAXNMATCH (si la liste est vide, tous les blocs sont inclus). Par défaut, le code généré est une macro-définition pour C (#define YYMAXNMATCH <n>), ou une variable globale pour Go (var YYMAXNMATCH int = <n>). Il peut être personnalisé avec une configuration optionnelle format qui spécifie une chaîne modèle où @@{max} (ou @@ en abrégé) est remplacé par la valeur numérique de YYMAXNMATCH.
/*!stags:re2c[:<nom1>[:<nom2>...]] ... */, /*!mtags:re2c[:<nom1>[:<nom2>...]] ... */ ou %{stags[:<nom1>[:<nom2>...]] ... %}, %{mtags[:<nom1>[:<nom2>...]] ... %{
Blocs qui spécifient un fragment de code modèle qui est développé pour chaque variable s-tag/m-tag générée par re2ocaml. Une liste optionnelle de noms de blocs spécifie quels blocs doivent être inclus lors du calcul de l'ensemble des variables de tags (si la liste est vide, tous les blocs sont inclus). Il existe deux configurations optionnelles : format et separator. La configuration format spécifie une chaîne modèle où @@{tag} (ou @@ en abrégé) est remplacé par le nom de chaque variable de tag. La configuration separator spécifie un fragment de code utilisé pour joindre les fragments format générés pour différentes variables de tags.
/*!svars:re2c[:<nom1>[:<nom2>...]] ... */, /*!mvars:re2c[:<nom1>[:<nom2>...]] ... */ ou %{svars[:<nom1>[:<nom2>...]] ... %}, %{mvars[:<nom1>[:<nom2>...]] ... %{
Blocs qui spécifient un fragment de code modèle qui est développé pour chaque s-tag/m-tag qui est soit explicitement mentionnée par les règles (avec l'option --tags) soit implicitement générée par re2ocaml (avec les options --captvars ou --posix-captvars). Une liste optionnelle de noms de blocs spécifie quels blocs doivent être inclus lors du calcul de l'ensemble des tags (si la liste est vide, tous les blocs sont inclus). Il existe deux configurations optionnelles : format et separator. La configuration format spécifie une chaîne modèle où @@{tag} (ou @@ en abrégé) est remplacé par le nom de chaque tag. La configuration separator spécifie un fragment de code utilisé pour joindre les fragments format générés pour différents tags.
/*!getstate:re2c[:<nom1>[:<nom2>...]] ... */ ou %{getstate[:<nom1>[:<nom2>...]] ... %}
Un bloc qui génère une répartition conditionnelle sur l'état de l'analyseur lexical (il nécessite l'option --storable-state). Une liste optionnelle de noms de blocs spécifie quels blocs doivent être inclus dans la répartition d'état. La transition par défaut va au label de départ du premier bloc de la liste. Si la liste est vide, tous les blocs sont inclus, et la transition par défaut va au premier bloc du fichier qui a un label de départ. Ce type de bloc est incompatible avec l'option --loop-switch, car il nécessite des transitions inter-blocs qui ne sont pas prises en charge sans goto ou appels de fonction.
/*!conditions:re2c[:<nom1>[:<nom2>...]] ... */, /*!types:re2c... */ ou %{conditions[:<nom1>[:<nom2>...]] ... %}, %{types... %}
Un bloc qui génère une énumération de conditions (il nécessite l'option --conditions). Une liste optionnelle de noms de blocs spécifie quels blocs doivent être inclus lors du calcul de l'ensemble des conditions (si la liste est vide, tous les blocs sont inclus). Par défaut, le code généré est une énumération YYCONDTYPE. Il peut être personnalisé avec les configurations optionnelles format et separator. La configuration format spécifie une chaîne modèle où @@{cond} (ou @@ en abrégé) est remplacé par le nom de chaque condition, et @@{num} est remplacé par un indice numérique de cette condition. La configuration separator spécifie un fragment de code utilisé pour joindre les fragments format générés pour différentes conditions.
/*!include:re2c <fichier> */ ou %{include <fichier> %}
Ce bloc permet d'inclure <fichier>, qui doit être un chemin de fichier entre guillemets doubles. Le contenu du fichier est substitué littéralement à la place du bloc, de la même manière que fonctionne #include en C/C++. Ce bloc peut être utilisé conjointement avec l'option --depfile pour générer des dépendances du système de build sur les fichiers inclus.
/*!header:re2c:on*/ ou %{header:on %}
Ce bloc marque le début du fichier d'en-tête. Tout ce qui suit et jusqu'au bloc header:off suivant est traité par re2ocaml et écrit dans le fichier d'en-tête spécifié avec l'option -t --type-header.
/*!header:re2c:off*/ ou %{header:off %}
Ce bloc marque la fin du fichier d'en-tête commencé avec le bloc header:on*/.
/*!ignore:re2c ... */ ou %{ignore ... %}
Un bloc dont le contenu est ignoré et supprimé du fichier de sortie.

Configurations

Voici une liste complète des configurations prises en charge par re2ocaml :

re2c:api, re2c:input
Identique à l'option --api.
re2c:api:sigil
Spécifie le marqueur ("sigil") utilisé pour les espaces réservés d'arguments dans les primitives d'API. Par défaut, c'est @@. Un espace réservé commence par le sigil suivi du nom de l'argument entre accolades. Par exemple, si le sigil est défini sur $, les espaces réservés auront la forme ${nom}. Les API à argument unique peuvent utiliser une notation abrégée sans le nom entre accolades. Cette option peut être remplacée par des options pour les primitives d'API individuelles, par exemple re2c:YYFILL@len pour YYFILL.
re2c:api:style
Spécifie le style de l'API. Les valeurs possibles sont functions (par défaut pour C) et free-form (par défaut pour Go et Rust). En style functions, les primitives d'API sont générées avec une liste d'arguments entre parenthèses suivant le nom de la primitive. Les arguments ne sont fournis que pour les paramètres auto-générés (comme le nombre de caractères passés à YYFILL), mais pas pour le contexte général de l'analyseur lexical, de sorte que les primitives se comportent davantage comme des macros en C/C++ ou des closures en Go et Rust. En style free-form, les primitives d'API n'ont pas de forme fixe : elles doivent être définies comme des chaînes contenant des fragments de code libre avec des variables interpolées de la forme @@{var} ou @@ (elles correspondent aux arguments du style fonctionnel). Cette configuration peut être remplacée pour les primitives d'API individuelles, voir par exemple la configuration re2c:YYFILL:naked pour YYFILL.
re2c:bit-vectors, re2c:flags:bit-vectors, re2c:flags:b
Identique à l'option --bit-vectors, mais peut être configuré bloc par bloc.
re2c:captures, re2c:leftmost-captures
Identique à l'option --leftmost-captures, mais peut être configuré bloc par bloc.
re2c:captvars, re2c:leftmost-captvars
Identique à l'option --leftmost-captvars, mais peut être configuré bloc par bloc.
re2c:case-insensitive, re2c:flags:case-insensitive
Identique à l'option --case-insensitive, mais peut être configuré bloc par bloc.
re2c:case-inverted, re2c:flags:case-inverted
Identique à l'option --case-inverted, mais peut être configuré bloc par bloc.
re2c:case-ranges, re2c:flags:case-ranges
Identique à l'option --case-ranges, mais peut être configuré bloc par bloc.
re2c:computed-gotos, re2c:flags:computed-gotos, re2c:flags:g
Identique à l'option --computed-gotos, mais peut être configuré bloc par bloc.
re2c:computed-gotos:relative, re2c:cgoto:relative
Identique à l'option --computed-gotos-relative, mais peut être configuré bloc par bloc.
re2c:computed-gotos:threshold, re2c:cgoto:threshold
Si les goto calculés sont utilisés, cette configuration spécifie le seuil de complexité qui déclenche la génération de tables de sauts au lieu de déclarations if imbriquées et de bitmaps. La valeur par défaut est 9.
re2c:cond:abort
Si définie à une valeur entière positive, le cas par défaut dans la répartition de conditions générée interrompt l'exécution du programme.
re2c:cond:goto
Spécifie un fragment de code utilisé pour les raccourcis automatiques :=> dans les conditions. Par défaut, c'est goto @@;. L'espace réservé @@ est substitué par le nom de la condition (voir les configurations re2c:api:sigil et re2c:cond:goto@cond).
re2c:cond:goto@cond
Spécifie le sigil utilisé pour la substitution d'arguments dans la définition de re2c:cond:goto. La valeur par défaut est @@. Remplace la configuration plus générique re2c:api:sigil.
re2c:cond:divider
Définit le séparateur pour les blocs de conditions. La valeur par défaut est /* *********************************** */. Les espaces réservés sont substitués par le nom de la condition (voir re2c:api;sigil et re2c:cond:divider@cond).
re2c:cond:divider@cond
Spécifie le sigil utilisé pour la substitution d'arguments dans la définition de re2c:cond:divider. La valeur par défaut est @@. Remplace la configuration plus générique re2c:api:sigil.
re2c:cond:prefix, re2c:condprefix
Spécifie le préfixe utilisé pour les labels de condition. La valeur par défaut est yyc_.
re2c:cond:enumprefix, re2c:condenumprefix
Spécifie le préfixe utilisé pour les identificateurs de condition. La valeur par défaut est yyc.
re2c:debug-output, re2c:flags:debug-output, re2c:flags:d
Identique à l'option --debug-output, mais peut être configuré par bloc.
re2c:empty-class, re2c:flags:empty-class
Identique à l'option --empty-class, mais peut être configuré par bloc.
re2c:encoding:ebcdic, re2c:flags:ecb, re2c:flags:e
Identique à l'option --ebcdic, mais peut être configuré par bloc.
re2c:encoding:ucs2, re2c:flags:wide-chars, re2c:flags:w
Identique à l'option --ucs2, mais peut être configuré par bloc.
re2c:encoding:utf8, re2c:flags:utf-8, re2c:flags:8
Identique à l'option --utf8, mais peut être configuré par bloc.
re2c:encoding:utf16, re2c:flags:utf-16, re2c:flags:x

re2c:encoding:utf32, re2c:flags:unicode, re2c:flags:u
Identique à l'option --utf32, mais peut être configuré par bloc.
re2c:encoding-policy, re2c:flags:encoding-policy
Identique à l'option --encoding-policy, mais peut être configuré par bloc.
re2c:eof
Spécifie le symbole sentinelle utilisé avec la règle de fin d'entrée $. La valeur par défaut est -1 (la règle $ n'est pas utilisée). D'autres valeurs possibles incluent toutes les unités de code valides. Seuls les nombres décimaux sont reconnus.
re2c:header, re2c:flags:type-header, re2c:flags:t
Spécifie le nom du fichier d'en-tête généré par rapport au répertoire du fichier de sortie. Identique à l'option --header, sauf que le chemin du fichier est relatif.
re2c:indent:string
Spécifie la chaîne utilisée pour l'indentation. La valeur par défaut est un seul caractère de tabulation "\t". La chaîne d'indentation ne doit contenir que des caractères d'espacement. Pour désactiver entièrement l'indentation, définissez cette configuration sur une chaîne vide.
re2c:indent:top
Spécifie le montant minimum d'indentation à utiliser. La valeur par défaut est zéro. La valeur doit être un nombre entier non négatif.
re2c:invert-captures
Identique à l'option --invert-captures, mais peut être configuré par bloc.
re2c:label:prefix, re2c:labelprefix
Spécifie le préfixe utilisé pour les étiquettes d'état du DFA. La valeur par défaut est yy.
re2c:label:start, re2c:startlabel
Contrôle la génération d'une étiquette de début de bloc. La valeur par défaut est zéro, ce qui signifie que l'étiquette de début est générée uniquement si elle est utilisée. Une valeur entière supérieure à zéro force la génération de l'étiquette de début même si elle n'est pas utilisée par l'analyseur lexical. Une valeur de chaîne force également la génération de l'étiquette de début et définit le nom de l'étiquette sur la chaîne spécifiée. Cette configuration ne s'applique qu'au bloc actuel (elle est réinitialisée à la valeur par défaut pour le bloc suivant).
re2c:label:yyFillLabel
Spécifie le préfixe des étiquettes YYFILL utilisées avec re2c:eof et en mode état stockable.
re2c:label:yyloop
Spécifie le nom de l'étiquette marquant le début de la boucle de l'analyseur lexical avec l'option --loop-switch. La valeur par défaut est yyloop.
re2c:label:yyNext
Spécifie le nom de l'étiquette optionnelle qui suit le switch YYGETSTATE en mode état stockable (activé avec re2c:state:nextlabel). La valeur par défaut est yyNext.
re2c:lookahead, re2c:flags:lookahead
Obsolète (voir l'option obsolète --no-lookahead).
re2c:monadic
Si défini sur une valeur non nulle, l'analyseur lexical généré utilisera la notation monadique (cette configuration est spécifique à Haskell).
re2c:nested-ifs, re2c:flags:nested-ifs, re2c:flags:s
Identique à l'option --nested-ifs, mais peut être configuré par bloc.
re2c:posix-captures, re2c:flags:posix-captures, re2c:flags:P
Identique à l'option --posix-captures, mais peut être configuré par bloc.
re2c:posix-captvars
Identique à l'option --posix-captvars, mais peut être configuré par bloc.
re2c:tags, re2c:flags:tags, re2c:flags:T
Identique à l'option --tags, mais peut être configuré par bloc.
re2c:tags:expression
Spécifie l'expression utilisée pour les variables de tag. Par défaut, re2ocaml génère des expressions de la forme yyt<N>. Cela peut être gênant, par exemple si les variables de tag sont définies comme des champs dans une structure. Toutes les occurrences de @@{tag} ou @@ sont remplacées par le nom de tag réel. Par exemple, re2c:tags:expression = "s.@@"; aboutit à des expressions de la forme s.yyt<N> dans le code généré. Voir également la configuration re2c:api:sigil.
re2c:tags:negative
Spécifie l'expression constante utilisée pour la valeur de tag négative (il s'agirait typiquement de -1 si les tags sont des décalages entiers dans la chaîne d'entrée, ou d'un pointeur nul s'il s'agit de pointeurs).
re2c:tags:prefix
Spécifie le préfixe pour les noms de variables de tag. La valeur par défaut est yyt.
re2c:sentinel
Spécifie le symbole sentinelle utilisé pour les vérifications de fin d'entrée (lorsque les vérifications de limites sont désactivées avec re2c:yyfill:enable = 0; et que re2c:eof n'est pas défini). Cette configuration n'affecte pas la génération de code : son objectif est de vérifier que le sentinelle n'est pas autorisé au milieu d'une règle et de s'assurer que l'analyseur lexical ne lira pas au-delà de la fin du tampon. La valeur par défaut est -1` (dans ce cas, re2ocaml suppose que le sentinelle est zéro, ce qui est le cas le plus courant). Seuls les nombres décimaux sont reconnus.
re2c:state:abort
Si défini sur une valeur entière positive, le cas par défaut dans la répartition d'état générée abandonne l'exécution du programme, et un cas explicite -1 contient une transition vers le début du bloc.
re2c:state:nextlabel
Contrôle si le switch YYGETSTATE est suivi d'une étiquette yyNext (la valeur par défaut est zéro, ce qui correspond à aucune étiquette). Alternativement, on peut utiliser re2c:label:start pour générer une étiquette de début spécifique, ou un bloc getstate explicite pour générer le switch YYGETSTATE séparément du bloc de l'analyseur lexical.
re2c:unsafe, re2c:flags:unsafe
Identique à l'option --no-unsafe, mais peut être configuré par bloc. Si défini sur zéro, il supprime la génération de wrappers unsafe autour de YYPEEK. La valeur par défaut est non nulle (les wrappers sont générés). Cette configuration est spécifique à Rust.
re2c:YYBACKUP, re2c:define:YYBACKUP
Définit la primitive d'API générique YYBACKUP.
re2c:YYBACKUPCTX, re2c:define:YYBACKUPCTX
Définit la primitive d'API générique YYBACKUPCTX.
re2c:YYCONDTYPE, re2c:define:YYCONDTYPE
Définit la primitive d'API YYCONDTYPE.
re2c:YYCTYPE, re2c:define:YYCTYPE
Définit la primitive d'API YYCTYPE.
re2c:YYCTXMARKER, re2c:define:YYCTXMARKER
Définit la primitive d'API YYCTXMARKER.
re2c:YYCURSOR, re2c:define:YYCURSOR

Expressions régulières

re2ocaml utilise la syntaxe suivante pour les expressions régulières :

"foo"
Littéral de chaîne sensible à la casse.
'foo'
Littéral de chaîne insensible à la casse.
[a-xyz], [^a-xyz]
Classe de caractères (éventuellement niée).
.
N'importe quel caractère sauf le saut de ligne.
R \ S
Différence des classes de caractères R et S.
R*
Zéro ou plusieurs occurrences de R.
R+
Une ou plusieurs occurrences de R.
R?
R optionnel.
R{n}
Répétition de R exactement n fois.
R{n,}
Répétition de R au moins n fois.
R{n,m}
Répétition de R de n à m fois.
(R)
Juste R ; les parenthèses sont utilisées pour remplacer la priorité. Si l'extraction de sous-correspondance est activée, (R) est un groupe de capture ou un groupe non-capturant selon l'option --invert-captures.
(!R)
Si l'extraction de sous-correspondance est activée, (!R) est un groupe non-capturant ou un groupe capturant selon l'option --invert-captures.
R S
Concaténation : R suivi de S.
R | S
Alternative : R ou S.
R / S
Lookahead : R suivi de S, mais S n'est pas consommé.
name
Expression régulière définie comme name (ou chaîne littérale "name" en mode compatibilité Flex).
{name}
Expression régulière définie comme name en mode compatibilité Flex.
@stag
Un *s-tag* : enregistre la dernière position d'entrée où @stag correspond dans une variable nommée stag.
#mtag
Un *m-tag* : enregistre toutes les positions d'entrée où #mtag correspond dans une variable nommée mtag.

Les classes de caractères et les littéraux de chaînes peuvent contenir les séquences d'échappement suivantes : \a, \b, \f, \n, \r, \t, \v, \\, échappements octaux \ooo et échappements hexadécimaux \xhh, \uhhhh et \Uhhhhhhhh.

Actions

Voici une liste des actions prédéfinies prises en charge par re2ocaml :

!entry code
L'action d'entrée lie un bloc de code défini par l'utilisateur à l'état de départ de la machine à états finis actuelle. Si des *conditions de départ* sont utilisées, l'action d'entrée peut être définie individuellement pour chaque condition. Cette action peut être utilisée pour effectuer l'initialisation, par exemple pour enregistrer la position de départ d'un lexème.
!pre_rule code
L'action de pré-règle ajoute un bloc de code défini par l'utilisateur au début des actions sémantiques de toutes les règles du bloc actuel (ou de la condition, si des *conditions de départ* sont utilisées). Cette action peut être utilisée pour factoriser la partie commune de toutes les actions sémantiques (par exemple, enregistrer la position de fin d'un lexeme).
!post_rule code
L'action de post-règle ajoute un bloc de code défini par l'utilisateur à la fin des actions sémantiques de toutes les règles du bloc actuel (ou de la condition, si des *conditions de départ* sont utilisées). Cette action peut être utilisée pour émettre des instructions de piège qui protègent contre les flux de contrôle involontaires.

Directives

Voici une liste complète des directives prises en charge par re2ocaml :

!use:name ;
Une directive `use` intégrée qui fusionne un bloc de règles précédemment défini avec le nom spécifié dans le bloc actuel. Les définitions nommées, les configurations et les règles du bloc référencé sont ajoutées aux règles actuelles. Les conflits entre les règles et les configurations qui se chevauchent sont résolus de la manière habituelle : la première règle a la priorité, et la dernière configuration remplace les précédentes. Une exception concerne les règles spéciales *, $ et <!> pour lesquelles une définition locale au bloc a toujours la priorité. Une directive `use` peut être placée n'importe où à l'intérieur d'un bloc, et plusieurs directives `use` sont autorisées.
!include file ;
Cette directive est identique au bloc include : elle insère le contenu de file verbatim à la place de la directive.

Interface du programme

Le code généré interagit avec le programme externe à l'aide de *primitives*, collectivement appelées l'*API*. Les primitives qui doivent être définies pour un programme particulier dépendent de plusieurs facteurs, notamment la complexité des expressions régulières, la représentation de l'entrée, la mise en mémoire tampon et l'utilisation de diverses fonctionnalités. Toutes les primitives nécessaires doivent être définies par l'utilisateur sous forme de macros, de fonctions, de variables ou de toute autre forme appropriée qui rend le code généré syntaxiquement et sémantiquement correct. re2ocaml ne vérifie pas (et ne peut pas vérifier) les définitions, donc si quelque chose manque ou est mal défini, le programme généré peut avoir des erreurs de compilation ou d'exécution. Ce manuel fournit des exemples de définitions d'API dans les cas les plus courants.

re2ocaml dispose de deux saveurs d'API qui définissent l'ensemble de base des primitives utilisées par un programme :

API d'enregistrement
L'API d'enregistrement est l'API par défaut pour le backend OCaml. Cette API se compose d'une variable yyrecord (le nom peut être remplacé par re2c:yyrecord) qui doit être définie comme un enregistrement avec les champs _yyinput, _yycursor, _yymarker, _yyctxmarker, _yylimit. Seuls les champs utilisés par le code généré doivent être définis, et leurs noms peuvent être configurés.
API générique
C'est l'API la plus flexible. Elle est activée avec l'option --api generic ou la configuration re2c:api = generic. Elle contient des primitives pour les opérations génériques : YYPEEK, YYSKIP, YYBACKUP, YYBACKUPCTX, YYSTAGP, YYSTAGN, YYMTAGP, YYMTAGN, YYRESTORE, YYRESTORECTX, YYRESTORETAG, YYSHIFT, YYSHIFTSTAG, YYSHIFTMTAG, YYLESSTHAN.

Initialement, YYCURSOR doit pointer vers le premier caractère d'entrée, et plus tard, il est avancé par le code généré. Lorsqu'une règle correspond, la position YYCURSOR est celle après le dernier caractère correspondant.

Une r-valeur qui stocke la fin de la position d'entrée (un pointeur ou un décalage d'entier dans YYINPUT). Initialement, YYLIMIT doit pointer vers la position après le dernier caractère d'entrée disponible. Il n'est pas modifié par le code généré. Le lexer compare YYCURSOR à YYLIMIT pour déterminer s'il reste suffisamment de caractères d'entrée.

Une l-valeur qui stocke la position de la dernière règle correspondante (un pointeur ou un décalage d'entier dans YYINPUT). Elle est utilisée pour restaurer la position YYCURSOR si la correspondance la plus longue échoue et que le lexer doit revenir en arrière. Aucune initialisation n'est nécessaire.
YYCTXMARKER
Une l-valeur qui stocke la position du contexte de suffixe (un pointeur ou un décalage d'entier dans YYINPUT). Aucune initialisation n'est nécessaire. YYCTXMARKER n'est nécessaire que si l'opérateur de lookahead / est utilisé.

Une primitive d'API générique avec une variable len. YYFILL doit fournir au moins len caractères d'entrée supplémentaires ou échouer. Si re2c:eof est utilisé, alors len est toujours 1 et YYFILL doit toujours retourner à la fonction appelante ; une valeur de retour zéro indique le succès. Si re2c:eof n'est pas utilisé, alors la valeur de retour de YYFILL est ignorée et elle ne doit pas retourner en cas d'échec. La valeur maximale de len est YYMAXFILL.

Une primitive qui définit le prototype de fonction dans le modèle de code --recursive-functions. YYINPUT
Une r-valeur qui stocke la séquence d'entrée actuelle (chaîne, tampon, etc.).

PRIMITIFS DE L'API

Les primitives d'API sont des blocs de code générés par re2c qui fournissent une interface entre le code généré et le code utilisateur. Elles peuvent être définies par l'utilisateur ou fournies par re2c avec des définitions par défaut.

YYACCEPT
Une primitive générique sans variable. Elle doit être définie comme une instruction qui termine l'analyse en cours et renvoie la valeur de la règle acceptée.
YYBACKUP
Une primitive d'API générique qui doit sauvegarder la position actuelle de l'entrée (pour être restaurée plus tard avec YYRESTORE).
YYBACKUPCTX
Une primitive d'API générique qui doit sauvegarder la position actuelle de l'entrée comme la position du contexte de fin (pour être restaurée plus tard avec YYRESTORECTX).
YYCONDTYPE
Le type de l'énumération de condition. Il peut être généré soit avec le bloc conditions, soit avec l'option --header.
YYDEBUG
Cette primitive est générée uniquement avec l'option -d, --debug-output. Son but est d'ajouter de la journalisation au code généré (une définition typique de YYDEBUG est une instruction d'impression). Les instructions YYDEBUG sont générées dans chaque état et ont deux variables : state (soit un index d'état DFA, soit -1) et symbol (le symbole d'entrée actuel).
YYFILL
Une primitive générique qui doit être appelée lorsque la mémoire tampon d'entrée est épuisée. Elle doit renvoyer un entier : zéro si la mémoire tampon a été remplie avec succès, et un si la fin de l'entrée a été atteinte et que la mémoire tampon ne peut pas être remplie.
YYGETACCEPT
Une primitive avec une variable var qui stocke le sélecteur numérique de la règle acceptée. Pour la plupart des langages, cette primitive a une définition par défaut qui lit à partir de var.
YYGETCOND
Une r-value de type YYCONDTYPE qui est égale à l'identifiant de la condition actuelle.
YYGETSTATE
Une r-value de type entier qui est égale à l'état actuel de l'analyseur lexical. Elle doit être initialisée à -1.
YYLESSTHAN
Une primitive d'API générique avec une variable len. Elle doit être définie comme une r-value de type booléen qui est égale à true si et seulement s'il reste moins de len caractères d'entrée.
YYMAXNMATCH
Une constante entière égale au nombre maximal de groupes de capture POSIX dans une règle. Elle est générée avec un bloc maxnmatch.
YYMTAGN
Une primitive d'API générique avec une variable tag. YYMTAGN doit ajouter à l'historique des sous-correspondances de tag une valeur qui représente une position d'entrée inexistante (voir la section d'extraction des sous-correspondances pour plus de détails).
YYMTAGP
Une primitive d'API générique avec une variable tag. YYMTAGP doit ajouter la position actuelle à l'historique des sous-correspondances de tag (voir la section d'extraction des sous-correspondances pour plus de détails).
YYPICC
Une primitive d'API générique avec une variable n. Elle doit être définie comme une instruction qui accepte l'entrée courante.
YYPEEK
Une primitive d'API générique sans variable. Elle doit être définie comme une r-value de type YYCTYPE qui est égale au caractère à la position actuelle de l'entrée.
YYRESTORE
Une primitive d'API générique qui doit restaurer la position actuelle de l'entrée à la valeur sauvegardée par YYBACKUP.
YYRESTORECTX
Une primitive d'API générique qui doit restaurer la position du contexte de fin sauvegardée avec YYBACKUPCTX.
YYRESTORETAG
Une primitive d'API générique avec une variable tag qui doit restaurer la position du contexte de fin à la valeur de tag.
YYSETACCEPT
Une primitive avec deux variables : var (une l-value qui stocke le sélecteur numérique de la règle acceptée) et val (la valeur du sélecteur). Pour la plupart des langages, cette primitive a une définition par défaut qui assigne var à val.
YYSETCOND
Une primitive avec une variable cond qui doit définir l'identifiant de la condition actuelle à cond.
YYSETSTATE
Une primitive avec une variable state qui doit définir l'état actuel de l'analyseur lexical à state.
YYSHIFT
Une primitive d'API générique avec une variable shift qui doit décaler la position actuelle de l'entrée de shift caractères (la valeur du décalage peut être négative).
YYSHIFTSTAG
Une primitive d'API générique avec deux variables, tag et shift, qui doit décaler tag de shift unités de code (la valeur du décalage peut être négative).
YYSHIFTMTAG
Une primitive d'API générique avec deux variables, tag et shift, qui doit décaler la dernière valeur de l'historique de tag de shift unités de code (la valeur du décalage peut être négative).
YYSKIP
Une primitive d'API générique qui doit avancer la position actuelle de l'entrée d'une unité de code.
YYSTAGN
Une primitive d'API générique avec une variable tag, où tag peut être un pointeur ou un décalage dans YYINPUT (voir la section d'extraction des sous-correspondances pour plus de détails). YYSTAGN doit définir tag à une valeur qui représente une position d'entrée inexistante.
YYSTAGP
Une primitive d'API générique avec une variable tag, où tag peut être un pointeur ou un décalage dans YYINPUT (voir la section d'extraction des sous-correspondances pour plus de détails). YYSTAGP doit définir tag à la position actuelle de l'entrée.
YYCOPYSTAG
Une primitive d'API générique avec deux variables, lhs et rhs, qui doit copier la variable s-tag de droite rhs à la variable s-tag de gauche lhs. Pour la plupart des langages, cette primitive a une définition par défaut qui assigne lhs à rhs.
YYCOPYMTAG
Une primitive d'API générique avec deux variables, lhs et rhs, qui doit copier la variable m-tag de droite rhs à la variable m-tag de gauche lhs. Pour la plupart des langages, cette primitive a une définition par défaut qui assigne lhs à rhs.

Certaines des options ont des configurations correspondantes, d'autres sont globales et ne peuvent pas être modifiées après que re2c commence à lire le fichier d'entrée. Les options de débogage nécessitent généralement la compilation de re2c dans une configuration de débogage. Les options internes sont utiles pour expérimenter avec les algorithmes utilisés dans re2c.

GESTION DE LA FIN DE L'ENTRÉE

L'un des principaux problèmes pour le lexer est de savoir quand s'arrêter. Il existe plusieurs conditions de terminaison :

  • le lexer peut correspondre à une règle (y compris la règle par défaut *) et arriver à un état final
  • le lexer peut ne pas correspondre à aucune règle et arriver à un état par défaut
  • le lexer peut atteindre la fin de l'entrée

Les deux premières conditions terminent le lexer d'une manière "naturelle" : il arrive à un état sans transitions sortantes, et la correspondance s'arrête automatiquement. La troisième condition, la fin de l'entrée, est différente : elle peut se produire dans n'importe quel état, et le lexer doit être capable de la gérer. La vérification de la fin de l'entrée interrompt le flux normal du lexer et ajoute des branches conditionnelles au programme généré, il est donc nécessaire de minimiser le nombre de ces vérifications. re2c prend en charge plusieurs méthodes différentes pour gérer la fin de l'entrée. Le choix dépend de la complexité des expressions régulières, du besoin de mise en tampon, des considérations de performance et d'autres facteurs. Voici une liste de méthodes :

  • Sentinelle. Cette méthode élimine le besoin de vérifications de fin d'entrée. Elle est simple et efficace, mais limitée au cas où il existe un caractère "sentinelle" naturel qui ne peut jamais se produire dans une entrée valide. Ce caractère peut toujours se produire dans une entrée invalide, mais il ne devrait pas être autorisé par les expressions régulières, sauf peut-être comme dernier caractère d'une règle. La sentinelle est ajoutée à la fin de l'entrée et sert de signal d'arrêt : lorsque le lexer lit ce caractère, il s'agit soit d'une erreur de syntaxe, soit de la fin de l'entrée. Dans les deux cas, le lexer doit s'arrêter. Cette méthode est utilisée si YYFILL est désactivé avec re2c:yyfill:enable = 0; et si re2c:eof a la valeur par défaut -1.
  • Sentinelle avec vérifications de limites. Cette méthode est générique : elle permet de gérer n'importe quelle entrée sans restrictions sur les expressions régulières. L'idée est de réduire le nombre de vérifications de fin d'entrée en les effectuant uniquement sur certains caractères. Similaire à la méthode "sentinelle", l'un des caractères est choisi comme "sentinelle" et ajouté à la fin de l'entrée. Cependant, il n'y a aucune restriction sur l'endroit où la sentinelle peut se produire (en fait, n'importe quel caractère peut être choisi pour une sentinelle). Lorsque le lexer lit ce caractère, il effectue en plus une vérification de limites. Si la position actuelle est dans les limites, le lexer reprend la correspondance et traite la sentinelle comme un caractère normal. Sinon, il appelle YYFILL (sauf si elle est désactivée). Si davantage d'entrée est fournie, le lexer réanalysera le dernier caractère et continuera comme si la sentinelle n'était pas là. Sinon, ce doit être la véritable fin de l'entrée, et le lexer s'arrête. Cette méthode est utilisée lorsque re2c:eof a une valeur non négative (elle doit être définie sur la valeur numérique de la sentinelle). YYFILL est facultatif.
  • Vérifications de limites avec remplissage. Cette méthode est générique, et peut être plus rapide que la méthode "sentinelle avec vérifications de limites", mais elle est aussi plus complexe. L'idée est de partitionner les états du DFA en composantes fortement connexes (SCC) et de générer une seule vérification par SCC pour suffisamment de caractères pour couvrir le chemin non répétitif le plus long dans cette SCC. Cela réduit le nombre de vérifications, mais il y a un problème avec les lexèmes courts en fin d'entrée, car la vérification nécessite suffisamment de caractères pour couvrir le lexème le plus long. Cela peut être corrigé en remplissant l'entrée avec quelques caractères factices qui ne forment pas un suffixe de lexème valide (de sorte que le lexer ne puisse pas les correspondre). La longueur du remplissage doit être YYMAXFILL, générée avec un bloc max. S'il n'y a pas assez d'entrée, le lexer appelle YYFILL qui doit fournir au moins le nombre requis de caractères ou ne pas retourner. Cette méthode est utilisée si YYFILL est activé et si re2c:eof est -1 (c'est la configuration par défaut).
  • Vérifications personnalisées. L'API générique permet de remplacer les opérations de base comme la lecture d'un caractère, ce qui rend possible d'inclure les vérifications de fin d'entrée comme faisant partie d'elles. Cette approche est sujette aux erreurs et doit être utilisée avec prudence. Pour utiliser une méthode personnalisée, activez l'API générique avec --api custom ou re2c:api = custom; et désactivez les vérifications par défaut des limites avec re2c:yyfill:enable = 0; ou re2c:yyfill:check = 0;.

Sentinelle

Cet exemple utilise un caractère sentinelle pour gérer la fin de l'entrée. Le programme compte les mots séparés par des espaces dans une chaîne terminée par un caractère nul. La sentinelle est le caractère nul : c'est le dernier caractère de chaque chaîne d'entrée, et il n'est autorisé dans le milieu d'un lexème par aucune des règles (en particulier, il n'est pas inclus dans les plages de caractères où il est facile de le manquer). Si un caractère nul se produit au milieu d'une chaîne, c'est une erreur de syntaxe et le lexer correspondra à la règle par défaut *, mais il ne lira pas au-delà de la fin de l'entrée et ne plantera pas (utilisez l'avertissement -Wsentinel-in-midrule et la configuration re2c:sentinelle pour vérifier cela). La configuration re2c:yyfill:enable = 0; supprime la génération des vérifications de limites et des appels à YYFILL.

(* re2ocaml $INPUT -o $OUTPUT *)
open String
type state = {
    yyinput: string;
    mutable yycursor: int;
}
(* attend une chaîne terminée par un caractère nul *)
%{
    re2c:YYFN = ["lex;int", "yyrecord;state", "count;int"];
    re2c:yyfill:enable = 0;
    *      { -1 }
    [\x00] { count }
    [a-z]+ { lex yyrecord (count + 1) }
    [ ]+   { lex yyrecord count }
%}
let test(yyinput, count) =
    let st = {yyinput = yyinput; yycursor = 0}
    in if not (lex st 0 = count) then raise (Failure "erreur")
let main () =
    test("", 0);
    test("un deux trois", 3);
    test("q4uatre", -1)
let _ = main ()

Sentinelle avec vérifications de limites

Cet exemple utilise une sentinelle avec vérifications de limites pour gérer la fin de l'entrée (cette méthode a été ajoutée dans la version 1.2). Le programme compte les chaînes d'un seul guillemet séparées par des espaces. Le caractère sentinelle est le caractère nul, spécifié avec la configuration re2c:eof = 0;. Comme dans la méthode sentinelle, le caractère nul est le dernier caractère de chaque chaîne d'entrée, mais il est autorisé au milieu d'une règle (par exemple, 'aaa\0aa'\0 est une entrée valide, mais 'aaa\0 est une erreur de syntaxe). Les vérifications de limites sont générées dans chaque état qui correspond à un caractère d'entrée, mais elles sont limitées à la branche qui gère le caractère nul. Les vérifications de limites sont de la forme YYLIMIT <= YYCURSOR ou YYLESSTHAN(1) avec l'API générique. Si la condition de vérification est vraie, le lexer a atteint la fin de l'entrée et doit s'arrêter (YYFILL est désactivé avec re2c:yyfill:enable = 0; car l'entrée tient dans un seul tampon, voir la section YYFILL avec sentinelle pour un exemple utilisant YYFILL). Atteindre la fin de l'entrée ouvre trois possibilités : si le lexer est dans l'état initial, il correspondra à la règle de fin d'entrée $, sinon il peut revenir à une règle précédemment correspondue (y compris la règle par défaut *) ou aller à un état par défaut, provoquant -Wundefined-control-flow.

(* re2ocaml $INPUT -o $OUTPUT *)
open String
type state = {
    yyinput: string;
    mutable yycursor: int;
    mutable yymarker: int;
    yylimit: int;
}
(* attend une chaîne terminée par un caractère nul *)
%{
    re2c:YYFN = ["lex;int", "yyrecord;state", "count;int"];
    re2c:yyfill:enable = 0;
    re2c:eof = 0;
    str = ['] ([^'\\] | [\\][^])* ['];
    *    { -1 }
    $    { count }
    str  { lex yyrecord (count + 1) }
    [ ]+ { lex yyrecord count }
%}
let test(str, count) =
    let st = {
        yyinput = str;
        yycursor = 0;
        yymarker = 0;
        yylimit = length str - 1; (* nul de terminaison non inclus *)
    }
    in if not (lex st 0 = count) then raise (Failure "erreur")
let main () =
    test("", 0);
    test("'guillemets\x00' 'sont' 'bien : \\'' ", 3);
    test("'nonterminé\\'", -1)
let _ = main ()

Vérifications de limites avec remplissage

Cet exemple utilise des vérifications de limites avec remplissage pour gérer la fin de l'entrée (cette méthode est activée par défaut). Le programme compte les chaînes d'un seul guillemet séparées par des espaces. Il y a un remplissage de caractères nuls YYMAXFILL qui appe

nded at the end of input, where YYMAXFILL value is autogenerated with a max block. It is not necessary to use null for padding --- any characters can be used as long as they do not form a valid lexeme suffix (in this example padding should not contain single quotes, as they may be mistaken for a suffix of a single-quoted string). There is a "stop" rule that matches the first padding character (null) and terminates the lexer (note that it checks if null is at the beginning of padding, otherwise it is a syntax error). Bounds checks are generated only in some states that are determined by the strongly connected components of the underlying automaton. Checks have the form (YYLIMIT - YYCURSOR) < n or YYLESSTHAN(n) with generic API, where n is the minimum number of characters that are needed for the lexer to proceed (it also means that the next bounds check will occur in at most n characters). If the check condition is true, the lexer has reached the end of input and will invoke YYFILL(n) that should either supply at least n input characters or not return. In this example YYFILL always fails and terminates the lexer with an error (which is fine because the input fits into one buffer). See the YYFILL with padding section for an example that refills the input buffer with YYFILL.

(* re2ocaml $INPUT -o $OUTPUT *)
open String
exception Fill
type state = {
    yyinput: string;
    mutable yycursor: int;
    yylimit: int;
}
%{max %}
%{
    re2c:YYFN = ["lex;int", "yyrecord;state", "count;int"];
    re2c:YYFILL = "raise Fill;";
    str = ['] ([^'\\] | [\\][^])* ['];
    [\x00] {
        (* check that it is the sentinel, not some unexpected null *)
        if yyrecord.yycursor = length yyrecord.yyinput - yymaxfill + 1 then count else -1
    }
    str  { lex yyrecord (count + 1) }
    [ ]+ { lex yyrecord count }
    *    { -1 }
%}
let test(str, count) =
    let buf = cat str (make yymaxfill '\x00') in
    let st = {yyinput = buf; yycursor = 0; yylimit = length buf} in
    let result = try lex st 0 with Fill -> -1 in
    if not (result = count) then raise (Failure "error")
let main () =
    test("", 0);
    test("'unterminated\\'", -1);
    test("'qu\x00tes' 'are' 'fine: \\'' ", 3);
    test("'unexpected \x00 null", -1)
let _ = main ()

Vérifications personnalisées

Cet exemple utilise une méthode personnalisée de gestion de la fin d'entrée basée sur l'API générique. Le programme compte les chaînes de caractères entre apostrophes séparées par des espaces. C'est le même exemple que le sentinel, à ceci près que l'entrée n'est pas terminée par un null. Pour compenser l'absence d'un caractère sentinelle en fin d'entrée, YYPEEK est redéfini pour effectuer une vérification de limites avant de lire le prochain caractère d'entrée. Ceci est inefficace car les vérifications sont effectuées très souvent. Si la condition de vérification échoue, YYPEEK renvoie le caractère réel, sinon il renvoie un caractère sentinelle factice.

(* re2ocaml $INPUT -o $OUTPUT *)
type state = {
    str: string;
    mutable cur: int;
    lim: int;
}
(* expect a string without terminating null *)
%{
    re2c:api = generic;
    re2c:YYFN = ["lex;int", "st;state", "count;int"];
    re2c:YYPEEK = "if st.cur < st.lim then st.str.[st.cur] else '\\x00'";
    re2c:YYSKIP = "st.cur <- st.cur + 1;";
    re2c:yyfill:enable = 0;
    *      { -1 }
    [\x00] { count }
    [a-z]+ { lex st (count + 1) }
    [ ]+   { lex st count }
%}
let test(str, count) =
    let st = {str = str; cur = 0; lim = String.length str}
    in if not (lex st 0 = count) then raise (Failure "error")
let main () =
    test("", 0);
    test("one two three", 3);
    test("f0ur", -1)
let _ = main ()

REMplISSAGE DE TAMPON

Le besoin de mise en tampon survient lorsque l'entrée ne peut pas être mappée en mémoire d'un seul coup : soit elle est trop grande, soit elle arrive de manière séquentielle (comme lors de la lecture depuis un socket). La technique habituelle dans de tels cas consiste à allouer un tampon de taille fixe et à traiter l'entrée par morceaux qui tiennent dans le tampon. Lorsque le morceau courant est traité, il est déplacé et de nouvelles données sont chargées. En pratique, c'est un peu plus complexe, car l'état du lexer ne consiste pas en une seule position d'entrée, mais en un ensemble de positions interdépendantes :

  • curseur : le prochain caractère d'entrée à lire (YYCURSOR dans l'API de pointeur C ou YYSKIP/YYPEEK dans l'API générique)
  • limite : la position après le dernier caractère d'entrée disponible (YYLIMIT dans l'API de pointeur C, implicitement gérée par YYLESSTHAN dans l'API générique)
  • marqueur : la position de la correspondance la plus récente, le cas échéant (YYMARKER dans l'API par défaut ou YYBACKUP/YYRESTORE dans l'API générique)
  • token : le début du lexème courant (implicite dans l'API re2ocaml, car il n'est pas nécessaire pour le fonctionnement normal du lexer et peut être défini et mis à jour par l'utilisateur)
  • marqueur de contexte : la position du contexte en retrait (YYCTXMARKER dans l'API de pointeur C ou YYBACKUPCTX/YYRESTORECTX dans l'API générique)
  • variables de balises : positions de sous-correspondances (définies avec les blocs stags et mtags et les primitives d'API générique YYSTAGP/YYSTAGN/YYMTAGP/YYMTAGN)

Tous ces éléments ne sont pas utilisés dans tous les cas, mais s'ils le sont, ils doivent être mis à jour par YYFILL. Toutes les positions actives sont contenues dans le segment entre le token et le curseur, donc tout ce qui se trouve entre le début du tampon et le token peut être éliminé, le segment allant du token jusqu'à la limite doit être déplacé au début du tampon, et l'espace libre à la fin du tampon doit être rempli avec de nouvelles données. Afin d'éviter des appels fréquents à YYFILL, il est préférable de charger autant de caractères d'entrée que possible (même si moins de caractères suffiraient à reprendre le lexer). Les détails de l'implémentation de YYFILL diffèrent légèrement selon la méthode de gestion de la fin de fichier utilisée : le cas de la règle EOF est un peu plus simple que le cas de la vérification des limites avec remplissage. Notez également que si l'option -f --storable-state est utilisée, YYFILL a une sémantique légèrement différente (décrite dans la section sur l'état stockable).

YYFILL avec sentinelle

Si la règle EOF est utilisée, YYFILL est une primitive de type fonction qui n'accepte aucun argument et renvoie une valeur qui est vérifiée par rapport à zéro. L'invocation de YYFILL est déclenchée par la condition YYLIMIT <= YYCURSOR dans l'API de pointeur C et YYLESSTHAN() dans l'API générique. Une valeur de retour non nulle signifie que YYFILL a échoué. Un appel réussi à YYFILL doit fournir au moins un caractère et ajuster les positions d'entrée en conséquence. La limite doit toujours être définie à un après la dernière position d'entrée dans le tampon, et le caractère à la position de la limite doit être le symbole sentinelle spécifié par la configuration re2c:eof. Les schémas ci-dessous montrent les emplacements relatifs des positions d'entrée dans le tampon avant et après l'appel YYFILL (le symbole sentinelle est marqué par #, et le deuxième schéma montre le cas où il n'y a pas assez d'entrée pour remplir tout le tampon).

               <-- décalage -->
             >-A------------B---------C-------------D#-----------E->
             tampon       token    marqueur      limite,
                                                  curseur
>-A------------B---------C-------------D------------E#->
             tampon,  marqueur      curseur       limite
             token
               <-- décalage -->
             >-A------------B---------C-------------D#--E
             tampon       token    marqueur      limite,
                                                  curseur
>-A------------B---------C-------------D---E#........
             tampon,  marqueur       curseur limite
             token

Voici un exemple de programme qui lit le fichier d'entrée input.txt par morceaux de 4096 octets et utilise la règle EOF.

(* re2ocaml $INPUT -o $OUTPUT *)
open Bytes
let bufsize = 4096
type state = {
    file: in_channel;
    yyinput: bytes;
    mutable yycursor: int;
    mutable yymarker: int;
    mutable yylimit: int;
    mutable token: int;
    mutable eof: bool;
}
type status = Ok | Eof | LongLexeme
let fill(st: state) : status =
    if st.eof then Eof else
    (* Error: lexeme too long. In real life could reallocate a larger buffer. *)
    if st.token < 1 then LongLexeme else (
    (* Shift buffer contents (discard everything up to the current token). *)
    blit st.yyinput st.token st.yyinput 0 (st.yylimit - st.token);
    st.yycursor <- st.yycursor - st.token;
    st.yymarker <- st.yymarker - st.token;
    st.yylimit <- st.yylimit - st.token;
    st.token <- 0;
    (* Fill free space at the end of buffer with new data from file. *)
    let n = input st.file st.yyinput st.yylimit (bufsize - st.yylimit - 1) in (* -1 for sentinel *)
    st.yylimit <- st.yylimit + n;
    if n = 0 then
        st.eof <- true; (* end of file *)
        set st.yyinput st.yylimit '\x00'; (* append sentinel *)
    Ok)
%{
    re2c:YYFN = ["lex;int", "yyrecord;state", "count;int"];
    re2c:YYFILL = "fill yyrecord = Ok";
    re2c:eof = 0;
    str = ['] ([^'\\] | [\\][^])* ['];
    *    { -1 }
    $    { count }
    str  { lex_loop yyrecord (count + 1) }
    [ ]+ { lex_loop yyrecord count }
%}
and lex_loop st count =
    st.token <- st.yycursor;
    lex st count
let main () =
    let fname = "input" in
    (* Prepare input file. *)
    Out_channel.with_open_bin fname
        (fun oc -> for i = 1 to bufsize do
            output_string oc "'qu\x00tes' 'are' 'fine: \\'' "
        done);
    (* Run lexer on the prepared file. *)
    In_channel.with_open_bin fname
        (fun ic ->
            let yylimit = bufsize - 1 in
            let st = {
                file = ic;
                yyinput = create bufsize;
                yycursor = yylimit;
                yymarker = yylimit;
                yylimit = yylimit;
                token = yylimit;
                eof = false;
            } in if not (lex_loop st 0 = 3 * bufsize) then
                raise (Failure "error"));
    (* Cleanup. *)
    Sys.remove fname
let _ = main ()

YYFILL avec remplissage

Dans le cas par défaut (lorsque la règle EOF n'est pas utilisée), YYFILL est une primitive de type fonction qui accepte un seul argument et ne renvoie aucune valeur. L'invocation de YYFILL est déclenchée par la condition (YYLIMIT - YYCURSOR) < n dans l'API de pointeur C et YYLESSTHAN(n) dans l'API générique. L'argument passé à YYFILL est le nombre minimal de caractères qui doivent être fournis. S'il ne parvient pas à le faire

o, YYFILL ne doit pas retourner à l'analyseur lexical (c'est pourquoi il est préférable qu'il soit implémenté comme une macro qui retourne de la fonction appelante en cas d'échec). En cas d'invocation réussie de YYFILL, la position limite doit être définie soit à un après la dernière position d'entrée dans le tampon, soit à la fin du remplissage YYMAXFILL (si YYFILL a lu avec succès au moins n caractères, mais pas assez pour remplir tout le tampon). Les schémas ci-dessous montrent les emplacements relatifs des positions d'entrée dans le tampon avant et après l'invocation de YYFILL (le remplissage YYMAXFILL dans le second schéma est marqué par des symboles #).

               <-- décalage -->                 <-- besoin -->
             >-A------------B---------C-----D-------E---F--------G->
             tampon       jeton    marqueur curseur  limite
>-A------------B---------C-----D-------E---F--------G->
             tampon,  marqueur curseur               limite
             jeton
               <-- décalage -->                 <-- besoin -->
             >-A------------B---------C-----D-------E-F        (EOF)
             tampon       jeton    marqueur curseur  limite
>-A------------B---------C-----D-------E-F###############
             tampon,  marqueur curseur                   limite
             jeton                        <- YYMAXFILL ->

Voici un exemple de programme qui lit le fichier d'entrée input.txt par blocs de 4096 octets et utilise la vérification des limites avec remplissage.

(* re2ocaml $INPUT -o $OUTPUT *)
open Bytes
%{max %}
let bufsize = 4096
exception Fill
type state = {
    file: in_channel;
    yyinput: bytes;
    mutable yycursor: int;
    mutable yymarker: int;
    mutable yylimit: int;
    mutable token: int;
    mutable eof: bool;
}
type status = Ok | Eof | LongLexeme
let fill (st: state) (need: int) : status =
    if st.eof then Eof else
    (* Erreur : lexème trop long. Dans la vraie vie, on pourrait réallouer un tampon plus grand. *)
    if st.token < need then LongLexeme else (
    (* Décale le contenu du tampon (rejette tout ce qui précède le jeton courant). *)
    blit st.yyinput st.token st.yyinput 0 (st.yylimit - st.token);
    st.yycursor <- st.yycursor - st.token;
    st.yymarker <- st.yymarker - st.token;
    st.yylimit <- st.yylimit - st.token;
    st.token <- 0;
    (* Remplit l'espace libre à la fin du tampon avec de nouvelles données du fichier. *)
    let n = input st.file st.yyinput st.yylimit (bufsize - st.yylimit - 1) in (* -1 pour le sentinelle *)
    st.yylimit <- st.yylimit + n;
    (* Si zéro caractère a été lu, c'est la fin de l'entrée => ajoute un remplissage zéro
       pour que l'analyseur puisse accéder aux caractères à la fin du tampon. *)
    if n = 0 then
        st.eof <- true; (* fin de fichier *)
        for i = 0 to (yymaxfill - 1) do
            set st.yyinput (st.yylimit + i) '\x00';
            st.yylimit <- st.yylimit + yymaxfill
        done;
    Ok)
%{
    re2c:YYFN = ["lex;int", "yyrecord;state", "count;int"];
    re2c:YYFILL = "if not (fill yyrecord @@ = Ok) then raise Fill;";
    str = ['] ([^'\\] | [\\][^])* ['];
    [\x00] {
        (* vérifie qu'il s'agit du sentinelle, pas d'un caractère nul inattendu *)
        if yyrecord.token = yyrecord.yylimit - yymaxfill then count else -1
    }
    str  { lex_loop yyrecord (count + 1) }
    [ ]+ { lex_loop yyrecord count }
    *    { -1 }
%}
and lex_loop st count =
    st.token <- st.yycursor;
    try lex st count with Fill -> -1
let main () =
    let fname = "input" in
    (* Préparation du fichier d'entrée. *)
    Out_channel.with_open_bin fname
        (fun oc -> for i = 1 to bufsize do
            output_string oc "'qu\x00tes' 'are' 'fine: \\'' "
        done);
    (* Exécution de l'analyseur lexical sur le fichier préparé. *)
    In_channel.with_open_bin fname
        (fun ic ->
            let yylimit = bufsize - yymaxfill in
            let st = {
                file = ic;
                yyinput = create bufsize;
                yycursor = yylimit;
                yymarker = yylimit;
                yylimit = yylimit;
                token = yylimit;
                eof = false;
            } in if not (lex_loop st 0 = 3 * bufsize) then
                raise (Failure "error"));
    (* Nettoyage. *)
    Sys.remove fname

FONCTIONNALITÉS

Blocs multiples

Il est parfois nécessaire d'avoir plusieurs analyseurs lexicaux interdépendants (par exemple, s'il existe une machine à états de haut niveau qui passe d'un mode d'analyseur lexical à un autre). Cela peut être implémenté en utilisant plusieurs blocs re2ocaml connectés. Une autre option consiste à utiliser des *conditions de départ*.

L'implémentation des connexions entre les blocs dépend de la langue cible. Dans les langages qui ont une instruction goto (comme C/C++ et Go), on peut avoir tous les blocs dans une seule fonction, chacun étant préfixé par une étiquette. La transition d'un bloc à un autre est un simple goto. Dans les langages qui n'ont pas de goto (comme Rust), il est nécessaire d'utiliser une boucle avec un commutateur sur une variable d'état, similaire à la boucle/commutateur yystate générée par re2ocaml, ou bien d'encapsuler chaque bloc dans une fonction et d'utiliser des appels de fonction.

L'exemple ci-dessous utilise plusieurs blocs pour analyser les nombres binaires, octaux, décimaux et hexadécimaux. Chaque base a son propre bloc. Le bloc initial détermine la base et redirige vers les autres blocs. Les configurations communes sont définies dans un bloc séparé au début du programme ; elles sont héritées par les autres blocs.

(* re2ocaml $INPUT -o $OUTPUT -i *)
open Int64
open Option
open String
type state = {
    yyinput: string;
    mutable yycursor: int;
    mutable yymarker: int;
}
let add (num: int option) (dgt: int) (base: int) : int option =
    match num with
        | None -> None
        | Some n ->
            let n' = add (mul (of_int n) (of_int base)) (of_int dgt)
            in if n' > (of_int32 Int32.max_int) then None else Some (to_int n')
%{
    re2c:yyrecord = "st";
    re2c:yyfill:enable = 0;
%}
%{local
    re2c:YYFN = ["parse_bin;int option", "st;state", "num;int option"];
    [01] { parse_bin st (add num (Char.code st.yyinput.[st.yycursor - 1] - 48) 2) }
    *    { num }
%}
%{local
    re2c:YYFN = ["parse_oct;int option", "st;state", "num;int option"];
    [0-7] { parse_oct st (add num (Char.code st.yyinput.[st.yycursor - 1] - 48) 8) }
    *     { num }
%}
%{local
    re2c:YYFN = ["parse_dec;int option", "st;state", "num;int option"];
    [0-9] { parse_dec st (add num (Char.code st.yyinput.[st.yycursor - 1] - 48) 10) }
    *     { num }
%}
%{local
    re2c:YYFN = ["parse_hex;int option", "st;state", "num;int option"];
    [0-9] { parse_hex st (add num (Char.code st.yyinput.[st.yycursor - 1] - 48) 16) }
    [a-f] { parse_hex st (add num (Char.code st.yyinput.[st.yycursor - 1] - 87) 16) }
    [A-F] { parse_hex st (add num (Char.code st.yyinput.[st.yycursor - 1] - 55) 16) }
    *     { num }
%}
%{local
    re2c:YYFN = ["parse;int option", "st;state"];
    '0b' / [01]        { parse_bin st (Some 0) }
    "0"                { parse_oct st (Some 0) }
    "" / [1-9]         { parse_dec st (Some 0) }
    '0x' / [0-9a-fA-F] { parse_hex st (Some 0) }
    *                  { None }
%}
let test (yyinput: string) (result: int option) =
    let st = {yyinput = yyinput; yycursor = 0; yymarker = 0} in
    if not (parse st = result) then raise (Failure "error")
let main () =
    test "\x00" None;
    test "1234567890\x00" (Some 1234567890);
    test "0b1101\x00" (Some 13);
    test "0x7Fe\x00" (Some 2046);
    test "0644\x00" (Some 420);
    test "9999999999\x00" None
let _ = main ()

Conditions de départ

Les conditions de départ sont activées avec l'option --start-conditions. Elles fournissent un moyen d'encoder plusieurs automates interdépendants au sein du même bloc re2ocaml.

Chaque condition correspond à un automate unique et a un nom unique spécifié par l'utilisateur et un numéro interne unique défini par re2ocaml. Les numéros sont utilisés pour basculer entre les conditions : le code généré utilise les primitives YYGETCOND et YYSETCOND pour obtenir la condition actuelle ou la définir sur le numéro donné. Utilisez le bloc conditions, l'option --header ou la configuration re2c:header pour générer des identifiants de condition numériques. La configuration re2c:cond:enumprefix spécifie le préfixe de l'identifiant généré.

En mode condition, chaque règle doit être préfixée par une liste de noms de conditions séparés par des virgules entre chevrons, ou par un joker <*> pour désigner toutes les conditions. La syntaxe des règles est étendue comme suit :

< liste-conditions > expression-régulière code
Une règle qui est fusionnée à chaque condition de la liste-conditions. Elle correspond à expression-régulière et exécute le code associé.
< liste-conditions > expression-régulière => condition code
Une règle qui est fusionnée à chaque condition de la liste-conditions. Elle correspond à expression-régulière, définit la condition courante sur condition et exécute le code associé.
< liste-conditions > expression-régulière :=> condition
Une règle qui est fusionnée à chaque condition de la liste-conditions. Elle correspond à expression-régulière et passe immédiatement à condition (il n'y a pas d'action sémantique).
< liste-conditions > !action code
Une règle qui lie le code à l'emplacement défini par action dans chaque condition de la liste-conditions (voir la section *actions* pour divers types d'actions).
<! liste-conditions > code
Une règle qui ajoute le code au début des actions sémantiques de toutes les règles pour chaque condition de la liste-conditions. Cette syntaxe est obsolète et l'action !pre_rule devrait être utilisée à la place (elle fait exactement la même chose).
< > code
Une règle qui crée une condition d'entrée spéciale avec le numéro zéro et le nom "0" qui exécute le code avant de sauter vers d'autres conditions. Cette syntaxe est obsolète, et l'action !entry devrait être utilisée à la place (elle offre un contrôle plus fin, car le code peut être spécifié par condition, et on peut sauter directement au début de la condition sans passer par la distribution des conditions).
< > => condition code
Identique à la règle précédente, sauf qu'elle définit la condition suivante.
< > :=> condition
Identique à la règle précédente, sauf qu'elle n'a pas de code associé et saute immédiatement à condition.

Le code que re2ocaml génère pour les conditions dépend de la façon dont

ther re2ocaml utilise une approche goto/label ou une approche boucle/switch pour encoder les automates.

Dans les langages qui possèdent l'instruction goto (comme C/C++ et Go), les conditions sont naturellement implémentées comme des blocs de code préfixés par des labels de la forme yyc_<cond>, où cond est un nom de condition (le préfixe du label peut être modifié avec re2c:cond:prefix). Les transitions entre conditions sont implémentées à l'aide de goto et des labels de conditions. Avant toutes les conditions, re2ocaml génère un switch initial sur YYGETSTATE qui saute à l'état de départ de la condition actuelle. Les règles de raccourci :=> contournent le switch initial et sautent directement à la condition spécifiée (re2c:cond:goto peut être utilisé pour modifier le comportement par défaut). Les règles avec des actions sémantiques ne sautent pas automatiquement à la condition suivante ; cela doit être fait par le code d'action défini par l'utilisateur.

Dans les langages qui ne possèdent pas goto (comme Rust), re2ocaml réutilise la variable yystate pour stocker les numéros de condition. Chaque condition obtient un identifiant numérique égal au nombre de son état de départ, et un switch entre les conditions n'est pas différent d'un switch entre les états d'un DFA d'une seule condition. Il n'y a pas besoin d'un switch de condition initial séparé. (Étant donné que la même approche est utilisée pour implémenter les états stockables, YYGETCOND/YYSETCOND sont redondants si les états stockables et les conditions sont tous deux utilisés).

Le programme ci-dessous utilise des conditions de départ pour analyser les nombres binaires, octaux, décimaux et hexadécimaux. Il y a un seul bloc où chaque base a sa propre condition, et la condition initiale est connectée à toutes. La variable définie par l'utilisateur cond stocke le numéro de la condition actuelle ; elle est initialisée au numéro de la condition initiale générée avec le bloc conditions.

(* re2ocaml $INPUT -o $OUTPUT -ci *)
open Int64
open Option
open String
%{conditions %}
type state = {
    yyinput: string;
    mutable yycursor: int;
    mutable yymarker: int;
    mutable yycond: yycondtype;
} 
let add (num: int option) (dgt: int) (base: int) : int option =
    match num with
        | None -> None
        | Some n ->
            let n' = add (mul (of_int n) (of_int base)) (of_int dgt)
            in if n' > (of_int32 Int32.max_int) then None else Some (to_int n')
%{
    re2c:YYFN = ["parse;int option", "st;state", "num;int option"];
    re2c:yyrecord = "st";
    re2c:yyfill:enable = 0;
    <init> '0b' / [01]        :=> bin
    <init> "0"                :=> oct
    <init> "" / [1-9]         :=> dec
    <init> '0x' / [0-9a-fA-F] :=> hex

    <dec> [0-9] { yyfndec st (add num (Char.code st.yyinput.[st.yycursor - 1] - 48) 10) }

    <hex> [A-F] { yyfnhex st (add num (Char.code st.yyinput.[st.yycursor - 1] - 55) 16) }
    <bin, oct, dec, hex> * { num }
%}
let test (yyinput: string) (result: int option) =
    let st = {yyinput = yyinput; yycursor = 0; yymarker = 0; yycond = YYC_init} in

État stockable

Avec l'option --storable-state, re2ocaml génère un lexer capable de stocker son état actuel, de retourner à l'appelant, puis de reprendre les opérations exactement là où il s'est arrêté. Le mode d'opération par défaut dans re2ocaml est un modèle "pull" (tirer), dans lequel le lexer "tire" plus d'entrée lorsqu'il en a besoin. Cela peut être inacceptable dans les cas où l'entrée est disponible par morceaux (par exemple, si le lexer est appelé par le parseur, ou si le programme lexer communique via un protocole socket avec un autre programme qui doit attendre une réponse du lexer avant de transmettre le prochain message). La fonctionnalité d'état stockable est précisément destinée à de tels cas : elle permet de générer des lexers qui fonctionnent selon un modèle "push" (pousser). Lorsque le lexer a besoin de plus d'entrée, il stocke son état et retourne à l'appelant. Plus tard, lorsque davantage d'entrée est disponible, l'appelant reprend le lexer exactement là où il s'est arrêté. Quelques changements sont nécessaires par rapport au modèle "pull" :

  • Définir les primitives YYSETSTATE() et YYGETSTATE(state).
  • Définir les variables yych, yyaccept (si utilisé) et state comme faisant partie de l'état persistant du lexer. La variable state doit être initialisée à -1.
  • YYFILL doit retourner au programme externe au lieu d'essayer de fournir plus d'entrée. Le code de retour doit indiquer que le lexer a besoin de plus d'entrée.
  • Le programme externe doit reconnaître les situations où le lexer a besoin de plus d'entrée et répondre de manière appropriée.
  • Utiliser éventuellement le bloc getstate pour générer un switch YYGETSTATE détaché du lexer principal. Cela ne fonctionne que pour les langages qui possèdent goto (pas en mode --loop-switch).
  • Utiliser re2c:eof et la méthode du *sentinelle avec vérifications de limites* pour gérer la fin de l'entrée. La méthode basée sur le remplissage peut ne pas fonctionner car il n'est pas clair quand ajouter le remplissage : la fin actuelle de l'entrée peut ne pas être la fin ultime de l'entrée, et l'ajout de remplissage trop tôt peut couper un lexème gourmand partiellement lu. De plus, en raison de la logique du programme de haut niveau, obtenir plus d'entrée peut dépendre du traitement du lexème à la fin du tampon (qui est déjà bloqué en raison de la condition de fin d'entrée).

Voici un exemple de lexer en mode "push" qui simule la lecture de paquets depuis un socket. Le lexer boucle jusqu'à ce qu'il rencontre la fin de l'entrée et retourne à la fonction appelante. La fonction appelante fournit plus d'entrée en "envoyant" le paquet suivant et reprend l'analyse lexicale. Ce processus s'arrête lorsque tous les paquets ont été envoyés, ou lorsqu'il y a une erreur.

(* re2ocaml $INPUT -o $OUTPUT -fi *)
open Bytes
(* Utiliser un petit tampon pour couvrir le cas où un lexème ne rentre pas.
   Dans la vie réelle, utiliser un tampon plus grand. *)
let bufsize = 10
let debug = false
let log format = (if debug then Printf.eprintf else Printf.ifprintf stderr) format
type state = {
    file: in_channel;
    yyinput: bytes;
    mutable yycursor: int;
    mutable yymarker: int;
    mutable yylimit: int;
    mutable token: int;
    mutable yystate: int;
    mutable recv: int;
}
type status = End | Ready | Waiting | BadPacket | BigPacket
let fill(st: state) : status =
    (* Erreur : lexème trop long. Dans la vie réelle, on pourrait réallouer un tampon plus grand. *)
    if st.token < 1 then BigPacket else (
    (* Décaler le contenu du tampon (tout supprimer jusqu'au jeton actuel). *)
    blit st.yyinput st.token st.yyinput 0 (st.yylimit - st.token);
    st.yycursor <- st.yycursor - st.token;
    st.yymarker <- st.yymarker - st.token;
    st.yylimit <- st.yylimit - st.token;
    st.token <- 0;
    (* Remplir l'espace libre à la fin du tampon avec de nouvelles données du fichier. *)
    let n = In_channel.input st.file st.yyinput st.yylimit (bufsize - st.yylimit - 1) in
    st.yylimit <- st.yylimit + n;
    set st.yyinput st.yylimit '\x00'; (* ajouter un sentinelle *)
    Ready)
%{
    re2c:YYFN = ["lex;status", "yyrecord;state"];
    re2c:YYFILL = "Waiting";
    re2c:eof = 0;
    packet = [a-z]+[;];
    *      { BadPacket }
    $      { End }
    packet { yyrecord.recv <- yyrecord.recv + 1; lex_loop yyrecord }
%}
and lex_loop st =
    st.token <- st.yycursor;
    lex st
let test (packets: string list) (sts: status) =
    let fname = "pipe" in
    let oc = Out_channel.open_bin fname in
    let ic = In_channel.open_bin fname in
    let yylimit = bufsize - 1 in
    let st = {
        file = ic;
        (* Le sentinelle (à l'offset `yylimit`) est défini à null, ce qui déclenche YYFILL. *)
        yyinput = create bufsize;
        yycursor = yylimit;
        yymarker = yylimit;
        yylimit = yylimit;
        token = yylimit;
        yystate = -1;
        recv = 0;
    } in
    let rec loop packets = match lex_loop st with
        | End ->
            log "done: got %d packets\n" st.recv;
            End
        | Waiting ->
            log "waiting...\n";
            let packets' = match packets with
                | [] -> []
                | p :: ps ->
                    log "sent packet '%s'\n" p;
                    Out_channel.output_string oc p;
                    Out_channel.flush oc; (* sans `flush`, l'écriture se produit trop tard *)
                    ps
            in (match fill st with
                | BigPacket ->
                    log "error: packet too big\n";
                    BigPacket
                | Ready -> loop packets'
                | _ -> raise (Failure "unexpected status after fill"))
        | BadPacket ->
            log "error: ill-formed packet\n";
            BadPacket
        | _ -> raise (Failure "unexpected status")
    in if not (loop packets = sts) then
        raise (Failure "error");
    In_channel.close ic;
    Out_channel.close oc;
    Sys.remove fname
let main () =
    test [] End;
    test ["zero;"; "one;"; "two;"; "three;"; "four;"] End;
    test ["zer0;"] BadPacket;
    test ["goooooooooogle;"] BigPacket
let _ = main ()

Blocs réutilisables

Les blocs réutilisables de la forme /*!rules:re2c[:<name>] ... */ ou %{rules[:<name>] ... %} peuvent être réutilisés un nombre quelconque de fois et combinés avec d'autres blocs re2ocaml. Le <name> est facultatif. Un bloc de règles peut être utilisé dans un bloc use ou une directive. Le code d'un bloc de règles est généré à chaque point d'utilisation.

Les blocs d'utilisation sont définis avec /*!use:re2c[:<name>] ... */ ou %{use[:<name>] ... %}. Le <name> est facultatif : s'il n'est pas spécifié, le bloc de règles associé est le plus récent (nommé ou non nommé). Un bloc d'utilisation peut ajouter des définitions nommées, des configurations et ses propres règles. Un cas d'utilisation important pour les blocs d'utilisation est un lexer qui prend en charge plusieurs encodages d'entrée : le même bloc de règles est réutilisé plusieurs fois avec des configurations spécifiques à l'encodage (voir l'exemple ci-dessous).

Un point de code est un identifiant numérique d'un symbole. Une unité de code est la plus petite unité de stockage dans le texte encodé. Un seul point de code peut être représenté par une ou plusieurs unités de code. Dans un encodage à longueur fixe, tous les points de code sont représentés avec le même nombre d'unités de code. Dans un encodage à longueur variable, les points de code peuvent être représentés avec un nombre différent d'unités de code. Notez que la règle "tout" **[^]** correspond à n'importe quel point de code, mais pas nécessairement à n'importe quelle unité de code (la seule façon de correspondre à n'importe quelle unité de code, quel que soit l'encodage, est la règle par défaut **\***). Le lexer généré fonctionne avec un flux d'unités de code : **yych** stocke une unité de code, et **YYCTYPE** est le type de l'unité de code. Les expressions régulières, en revanche, sont spécifiées en termes de points de code. Lorsque re2ocaml compile les expressions régulières en automates, il traduit les points de code en unités de code. Ce n'est généralement pas une correspondance simple : dans les encodages à longueur variable, une seule plage de points de code peut être traduite en un graphe complexe d'unités de code. Les encodages suivants sont pris en charge : * **ASCII** (activé par défaut). C'est un encodage à longueur fixe avec un espace de code **[0-255]** et des points de code et des unités de code de 1 octet. * **EBCDIC** (activé avec **--ebcdic** ou **re2c:encoding:ebcdic**). C'est un encodage à longueur fixe avec un espace de code **[0-255]** et des points de code et des unités de code de 1 octet. * **UCS2** (activé avec **--ucs2** ou **re2c:encoding:ucs2**). C'est un encodage à longueur fixe avec un espace de code **[0-0xFFFF]** et des points de code et des unités de code de 2 octets. * **UTF8** (activé avec **--utf8** ou **re2c:encoding:utf8**). C'est un encodage Unicode à longueur variable. La taille de l'unité de code est de 1 octet. Les points de code sont représentés avec 1 à 4 unités de code. * **UTF16** (activé avec **--utf16** ou **re2c:encoding:utf16**). C'est un encodage Unicode à longueur variable. La taille de l'unité de code est de 2 octets. Les points de code sont représentés avec 1 à 2 unités de code. * **UTF32** (activé avec **--utf32** ou **re2c:encoding:utf32**). C'est un encodage Unicode à longueur fixe avec un espace de code **[0-0x10FFFF]** et des points de code et des unités de code de 4 octets. Le fichier d'inclusion **include/unicode_categories.re** fournit les définitions re2ocaml pour les catégories Unicode standard. L'option **--input-encoding** spécifie l'encodage du fichier source, qui peut être utilisé pour activer les littéraux Unicode dans les expressions régulières. Par exemple, **--input-encoding utf8** indique à re2ocaml que le fichier source est en UTF8 (cela diffère de **--utf8** qui définit l'encodage du texte d'entrée). L'option **--encoding-policy** spécifie la manière dont re2ocaml gère les substituts Unicode (points de code dans la plage **[0xD800-0xDFFF]**). Fichiers d'en-tête

re2ocaml permet de générer un fichier d'en-tête à partir du fichier .re d'entrée en utilisant l'option --header ou la configuration re2c:header et des paires de blocs de la forme /*!header:re2c:on*/ et /*!header:re2c:off*/, ou %{header:on%} et %{header:off%}. Le premier bloc marque le début du fichier d'en-tête, et le second bloc marque la fin. Tout ce qui se trouve entre ces blocs est traité par re2ocaml, et le code généré est écrit dans le fichier spécifié par l'option --header ou la configuration re2c:header (ou stdout si ni l'option ni la configuration ne sont utilisées). Un fichier d'en-tête auto-généré peut être nécessaire dans les cas où re2ocaml est utilisé pour générer des définitions qui doivent être visibles depuis d'autres unités de traduction.

Programmes squelettes

Avec l'option -S, --skeleton, re2ocaml ignore tout le code non-re2ocaml et génère un programme C autonome qui peut être compilé et exécuté. Le programme se compose du code du lexer et des données d'entrée. Pour chaque DFA construit (bloc ou condition), re2ocaml génère un lexer autonome et deux fichiers : un fichier .input contenant des chaînes dérivées du DFA et un fichier .keys contenant les résultats de correspondance attendus. Le programme exécute chaque lexer sur le fichier .input correspondant et compare les résultats avec les attentes. Les programmes squelettes sont très utiles pour plusieurs raisons :

  • Ils peuvent vérifier la correction de diverses optimisations de re2ocaml (les données sont générées tôt dans le processus, avant toute transformation du DFA).
  • La génération d'un ensemble de données d'entrée avec une bonne couverture peut être utile à la fois pour les tests et les benchmarks.
  • La génération de programmes exécutables autonomes permet d'obtenir des cas de test minimisés (le code original peut être volumineux ou avoir beaucoup de dépendances).

La difficulté avec la génération de données d'entrée est que, pour tous les cas sauf les plus triviaux, le nombre de chaînes d'entrée possibles est trop grand (même si la longueur de la chaîne est limitée). re2ocaml résout cette difficulté en générant suffisamment de chaînes pour couvrir presque toutes les transitions du DFA. Il utilise l'algorithme suivant. Premièrement, il construit un squelette du DFA. Pour les codages avec une taille d'unité de code de 1 octet (tels que ASCII, UTF-8 et EBCDIC), le squelette est juste une copie exacte du DFA original. Pour les codages avec des unités de code multibytes, le squelette est une copie du DFA avec certaines transitions omises : à savoir, re2ocaml prend au maximum 256 unités de code pour chaque plage continue disjointes correspondant à une transition de DFA. Les valeurs choisies sont réparties uniformément et incluent les bornes des plages. Au lieu d'essayer de couvrir tous les chemins possibles dans le squelette (ce qui est infaisable), re2ocaml génère suffisamment de chemins pour couvrir toutes les transitions du squelette, et ainsi déclencher les sauts conditionnels correspondants dans le lexer. L'implémentation de l'algorithme est limitée à environ 1 Go de transitions et consomme une quantité constante de mémoire (re2ocaml écrit les données dans un fichier dès qu'elles sont générées).

Visualisation et débogage

Avec l'option -D, --emit-dot, re2ocaml ne génère pas de code. Au lieu de cela, il affiche le DFA généré au format DOT. On peut convertir cet affichage en une image du DFA en utilisant Graphviz ou une autre bibliothèque. Notez que cette option montre le DFA final après qu'il ait subi un certain nombre d'optimisations et de transformations. Les étapes antérieures peuvent être affichées avec diverses options de débogage, telles que --dump-nfa, --dump-dfa-raw, etc. (voir la liste complète des options).
