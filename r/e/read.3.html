Description détaillée

Une interface i/o abstraite.

Attention

C'est du matériel avancé, très technique. Vous n'en avez pas besoin à moins de savoir vraiment ce que vous faites. La plupart des applications n'en auront pas besoin.

Historiquement, PhysicsFS fournissait un accès au système de fichiers physique et aux archives à l'intérieur de ce système de fichiers. Cependant, parfois, vous avez besoin de plus de puissance que cela. Peut-être avez-vous besoin de fournir une archive entièrement contenue en RAM, ou vous devez faire le pont avec une autre API d'i/o de fichiers à PhysicsFS, ou vous devez traduire les bits (peut-être avez-vous un fichier .zip standard chiffré, et vous devez le déchiffrer à la volée pour l'archiveur zip inconscient).

Un PHYSFS_Io est l'interface que les Archiveurs utilisent pour obtenir des données d'archive. Historiquement, cela correspondait aux i/o de fichiers vers le système de fichiers physique, mais depuis PhysicsFS 2.1, les applications peuvent fournir leurs propres implémentations d'i/o à l'exécution.

Cette interface n'est pas nécessairement un bon ajustement universel pour les i/o. Il y a quelques exigences à noter :

  • Ils ne font que des i/o bloquants (du moins, pour l'instant).
  • Ils doivent être capables de se dupliquer. Si vous avez un descripteur de fichier provenant de fopen(), vous devez être capable de créer un clone unique de celui-ci (afin que nous ayons deux descripteurs pour le même fichier qui peuvent tous deux chercher/lire/etc. sans se gêner).
  • Ils doivent connaître la taille de l'ensemble de leurs données.
  • Ils doivent être capables de rechercher et de rembobiner à la demande.

...en bref, vous n'allez probablement pas écrire une implémentation HTTP.

Sécurité des threads : Les implémentations de PHYSFS_Io ne sont pas garanties d'être sûres pour les threads en elles-mêmes. Sous le capot, là où PhysicsFS les utilise, la bibliothèque fournit ses propres verrous. Si vous prévoyez de les utiliser directement à partir de threads séparés, vous devriez soit utiliser des mutex pour les protéger, soit ne pas utiliser le même PHYSFS_Io à partir de deux threads en même temps.

Documentation des champs

void(* PHYSFS_Io::destroy) (struct PHYSFS_Io *io)

Nettoyer et désallouer l'instance d'i/o. Libérer les ressources associées, y compris (opaque) le cas échéant.

Cette fonction doit toujours réussir : à ce titre, elle retourne void. Le système peut appeler votre méthode flush() avant cela. Vous pouvez signaler une erreur là si nécessaire. Cette méthode peut toujours être appelée si flush() échoue, auquel cas vous devrez abandonner les données non vidées et d'autres conditions d'échec et nettoyer.

Une fois cette méthode appelée pour une instance donnée, le système supposera qu'il est dangereux de toucher à nouveau cette instance et supprimera toute référence à celle-ci.

Paramètres

s L'instance d'i/o à détruire.

struct PHYSFS_Io *(* PHYSFS_Io::duplicate) (struct PHYSFS_Io *io)

Dupliquer cette instance d'i/o. Cela doit aboutir à une copie complète de ce PHYSFS_Io, qui peut vivre de manière complètement indépendante. La copie doit être capable d'effectuer toutes ses opérations sans altérer l'original, y compris le fait que l'un ou l'autre objet puisse être détruit séparément (donc, par exemple : ils ne peuvent pas partager un descripteur de fichier ; chacun a besoin du sien).

Si vous ne pouvez pas dupliquer un descripteur, il est légal de retourner NULL, mais vous avez presque certainement besoin de cette fonctionnalité si vous voulez utiliser ce PHYSFS_Io pour servir d'archive.

Paramètres

io L'instance d'i/o à dupliquer.

Retours

Une nouvelle valeur pour le champ (opaque) d'un flux, ou NULL en cas d'erreur.

int(* PHYSFS_Io::flush) (struct PHYSFS_Io *io)

Vider les ressources vers le média, ou ailleurs. C'est l'occasion de signaler une erreur pour les écritures qui avaient prétendu réussir auparavant, mais qui avaient encore une chance d'échouer réellement. Cette méthode peut être NULL si le vidage n'est pas nécessaire.

Cette fonction peut être appelée avant destroy(), car elle peut signaler une erreur et destroy() ne le peut pas. Elle peut être appelée à d'autres moments également.

Paramètres

io L'instance d'i/o à vider.

Retours

Zéro en cas d'erreur, non zéro en cas de succès.

PHYSFS_sint64(* PHYSFS_Io::length) (struct PHYSFS_Io *io)

Déterminer la taille de l'ensemble de données de l'instance d'i/o. Retourne le nombre d'octets disponibles dans le fichier, ou -1 si vous ne pouvez pas le déterminer. Un échec sera presque certainement fatal à une utilisation ultérieure de ce flux, vous ne pouvez donc pas laisser cela non implémenté.

Paramètres

io L'instance d'i/o à interroger.

Retours

Taille totale, en octets, de l'ensemble de données.

void* PHYSFS_Io::opaque

Données d'instance pour cette structure. Chaque instance a un pointeur associé qu'elle peut utiliser pour stocker ce qu'elle veut. Ce pointeur est par instance de flux, donc il changera probablement lors de l'appel à duplicate(). Il peut être désalloué pendant la méthode destroy().

PHYSFS_sint64(* PHYSFS_Io::read) (struct PHYSFS_Io *io, void *buf, PHYSFS_uint64 len)

Lire plus de données. Lire (len) octets de l'interface, à la position actuelle d'i/o, et les stocker dans (buffer). La position actuelle d'i/o devrait avancer du nombre d'octets lus avec succès.

Vous n'avez pas à implémenter cela ; définissez-le à NULL si non implémenté. Ceci ne sera utilisé que si le fichier est ouvert en lecture. S'il est défini à NULL, une implémentation par défaut qui signale immédiatement un échec sera utilisée.

Paramètres

io L'instance d'i/o à lire.
buf Le tampon pour stocker les données. Il doit être d'au moins (len) octets et ne peut pas être NULL.
len Le nombre d'octets à lire de l'interface.

Retours

nombre d'octets lus depuis le fichier, 0 en fin de fichier, -1 en cas d'échec complet.

PHYSFS_sint64(* PHYSFS_Io::tell) (struct PHYSFS_Io *io)

Signaler la position actuelle d'entrée/sortie. Retourne l'offset en octets, ou -1 si vous ne parvenez pas à le déterminer. Un échec sera presque certainement fatal à toute utilisation ultérieure de ce flux, vous ne pouvez donc pas laisser cette méthode non implémentée.

PHYSFS_uint32 PHYSFS_Io::version

Informations sur la compatibilité binaire. Doit être défini à zéro pour le moment. Les versions futures de cette structure incrémenteront ce champ, nous saurons ainsi ce qu'une implémentation donnée prend en charge. Nous continuerons probablement à prendre en charge les anciennes versions à mesure que nous proposerons de nouvelles fonctionnalités.

PHYSFS_sint64(* PHYSFS_Io::write) (struct PHYSFS_Io *io, const void *buffer, PHYSFS_uint64 len)

Écrire des données supplémentaires. Écrit (len) octets depuis (buffer) vers l'interface à la position d'entrée/sortie actuelle. La position d'entrée/sortie actuelle doit avancer du nombre d'octets écrits avec succès.

Vous n'avez pas à implémenter ceci; définissez-le à NULL si non implémenté. Ceci ne sera utilisé que si le fichier est ouvert en écriture. S'il est défini à NULL, une implémentation par défaut qui signale immédiatement un échec sera utilisée.

Vous êtes autorisé à mettre en mémoire tampon; une écriture peut réussir ici et échouer plus tard lors de la vidange. Notez que PHYSFS_setBuffer() peut fonctionner à un niveau supérieur à votre entrée/sortie, vous ne devriez donc généralement pas implémenter vos propres routines de mise en mémoire tampon.

Paramètres

io L'instance d'entrée/sortie à laquelle écrire.
buffer Le tampon à partir duquel lire les données. Il doit avoir au moins (len) octets et ne peut pas être NULL.
len Le nombre d'octets à lire depuis (buffer).

Retourne

nombre d'octets écrits dans le fichier, -1 en cas d'échec complet.
