resolv.conf(5) Manuel des formats de fichiers resolv.conf(5)

NOM

resolv.conf - fichier de configuration du résolveur

SYNOPIS

/etc/resolv.conf

DESCRIPTION

Le résolveur est un ensemble de routines dans la bibliothèque C qui fournissent un accès au Domain Name System (DNS) d'Internet. Le fichier de configuration du résolveur contient des informations qui sont lues par les routines du résolveur lors de leur première invocation par un processus. Le fichier est conçu pour être lisible par l'homme et contient une liste de mots-clés avec des valeurs qui fournissent divers types d'informations de résolution. Le fichier de configuration est considéré comme une source fiable d'informations DNS ; voir l'option trust-ad ci-dessous pour plus de détails.

Si ce fichier n'existe pas, seul le serveur de noms sur la machine locale sera interrogé, et la liste de recherche contient le nom de domaine local déterminé à partir du nom d'hôte.

Les différentes options de configuration sont :

nameserver Adresse IP du serveur de noms
Adresse Internet d'un serveur de noms que le résolveur doit interroger, soit une adresse IPv4 (en notation décimale), soit une adresse IPv6 en notation deux-points (et éventuellement points) selon la RFC 2373. Jusqu'à MAXNS (actuellement 3, voir <resolv.h>) serveurs de noms peuvent être listés, un par mot-clé. S'il y a plusieurs serveurs, la bibliothèque du résolveur les interroge dans l'ordre de la liste. Si aucune entrée nameserver n'est présente, la valeur par défaut est d'utiliser le serveur de noms sur la machine locale. (L'algorithme utilisé est d'essayer un serveur de noms, et si la requête expire, d'essayer le suivant, jusqu'à épuisement des serveurs de noms, puis de répéter l'essai avec tous les serveurs de noms jusqu'à ce qu'un nombre maximum de tentatives soit effectué.)
search Liste de recherche pour la résolution de nom d'hôte.
Par défaut, la liste de recherche contient une entrée, le nom de domaine local. Il est déterminé à partir du nom d'hôte local retourné par gethostname(2) ; le nom de domaine local est considéré comme tout ce qui suit le premier '.'. Enfin, si le nom d'hôte ne contient pas de '.', le domaine racine est supposé être le nom de domaine local.
Cela peut être modifié en listant le chemin de recherche de domaine souhaité après le mot-clé search, en séparant les noms par des espaces ou des tabulations. Les requêtes de résolution ayant moins de ndots points (la valeur par défaut est 1) seront tentées en utilisant chaque composant du chemin de recherche tour à tour jusqu'à ce qu'une correspondance soit trouvée. Pour les environnements avec plusieurs sous-domaines, veuillez lire options ndots:n ci-dessous pour éviter les attaques de type « man-in-the-middle » et le trafic inutile vers les serveurs DNS racine. Notez que ce processus peut être lent et générer beaucoup de trafic réseau si les serveurs pour les domaines listés ne sont pas locaux, et que les requêtes expireront si aucun serveur n'est disponible pour l'un des domaines.
S'il y a plusieurs directives search, seule la liste de recherche de la dernière instance est utilisée.
Dans glibc 2.25 et versions antérieures, la liste de recherche est limitée à six domaines avec un total de 256 caractères. Depuis glibc 2.26, la liste de recherche est illimitée.
La directive domain est un nom obsolète pour la directive search qui ne gère qu'une seule entrée de liste de recherche.
sortlist
Cette option permet de trier les adresses retournées par gethostbyname(3). Une liste de tri est spécifiée par des paires adresse IP-masque réseau. Le masque réseau est facultatif et prend par défaut le masque naturel du réseau. Les paires d'adresses IP et les réseaux facultatifs sont séparés par des barres obliques. Jusqu'à 10 paires peuvent être spécifiées. Voici un exemple :

sortlist 130.155.160.0/255.255.240.0 130.155.0.0
options
Les options permettent de modifier certaines variables internes du résolveur. La syntaxe est
options option ...

où option est l'une des suivantes :

debug
Définit RES_DEBUG dans _res.options (efficace uniquement si glibc a été compilé avec le support de débogage ; voir resolver(3)).
ndots:n
Définit un seuil pour le nombre de points qui doivent apparaître dans un nom donné à res_query(3) (voir resolver(3)) avant qu'une requête absolue initiale ne soit effectuée. La valeur par défaut pour n est 1, ce qui signifie que s'il y a des points dans un nom, le nom sera d'abord essayé comme un nom absolu avant que tout élément de la liste de recherche ne lui soit ajouté. La valeur de cette option est silencieusement plafonnée à 15.
timeout:n
Définit le temps pendant lequel le résolveur attendra une réponse d'un serveur de noms distant avant de retenter la requête via un autre serveur de noms. Ceci ne peut pas être le temps total pris par un appel d'API du résolveur et il n'y a aucune garantie qu'un seul appel d'API du résolveur corresponde à un seul timeout. Mesuré en secondes, la valeur par défaut est RES_TIMEOUT (actuellement 5, voir <resolv.h>). La valeur de cette option est silencieusement plafonnée à 30.
attempts:n
Définit le nombre de fois où le résolveur enverra une requête à ses serveurs de noms avant d'abandonner et de retourner une erreur à l'application appelante. La valeur par défaut est RES_DFLRETRY (actuellement 2, voir <resolv.h>). La valeur de cette option est silencieusement plafonnée à 5.
rotate
Définit RES_ROTATE dans _res.options, ce qui provoque une sélection en rotation des serveurs de noms parmi ceux listés. Cela a pour effet de répartir la charge des requêtes entre tous les serveurs listés, plutôt que d'avoir tous les clients qui essaient systématiquement le premier serveur listé.
no-aaaa (depuis glibc 2.36)
Définit RES_NOAAAA dans _res.options, ce qui supprime les requêtes AAAA effectuées par le résolveur stub, y compris les recherches AAAA déclenchées par des interfaces basées sur NSS comme getaddrinfo(3). Seules les recherches DNS sont affectées : les données IPv6 dans hosts(5) sont toujours utilisées, getaddrinfo(3) avec AI_PASSIVE produira toujours des adresses IPv6, et les serveurs de noms IPv6 configurés sont toujours utilisés. Pour produire des résultats corrects de type Name Error (NXDOMAIN), les requêtes AAAA sont traduites en requêtes A. Cette option est destinée principalement à des fins de diagnostic, pour exclure que les requêtes DNS AAAA aient un impact négatif. Elle est incompatible avec l'utilisation d'EDNS0 et la validation DNSSEC par les applications.
no-check-names
Définit RES_NOCHECKNAME dans _res.options, ce qui désactive la vérification moderne par BIND des noms d'hôtes et des noms de messagerie entrants pour les caractères invalides tels que le tiret bas (_), les non-ASCII ou les caractères de contrôle.
inet6
Définit RES_USE_INET6 dans _res.options. Cela a pour effet d'essayer une requête AAAA avant une requête A dans la fonction gethostbyname(3), et de mapper les réponses IPv4 sous forme "tunneled" IPv6 si aucun enregistrement AAAA n'est trouvé mais qu'un ensemble d'enregistrements A existe. Depuis glibc 2.25, cette option est obsolète ; les applications doivent utiliser getaddrinfo(3), plutôt que gethostbyname(3).
ip6-bytestring (depuis glibc 2.3.4 jusqu'à glibc 2.24)
Définit RES_USEBSTRING dans _res.options. Cela provoque la réalisation des requêtes IPv6 inversées en utilisant le format de bit-label décrit dans la RFC 2673 ; si cette option n'est pas définie (ce qui est la valeur par défaut), alors le format nibble est utilisé. Cette option a été supprimée dans glibc 2.25, car elle reposait sur une extension DNS incompatible avec les versions antérieures qui n'a jamais été déployée sur Internet.
ip6-dotint/no-ip6-dotint (glibc 2.3.4 jusqu'à glibc 2.24)
Efface/définit RES_NOIP6DOTINT dans _res.options. Lorsque cette option est effacée (ip6-dotint
b>), des recherches inversées IPv6 sont effectuées dans la zone ip6.int (obsolète) ; lorsque cette option est définie (no-ip6-dotint), les recherches inversées IPv6 sont effectuées par défaut dans la zone ip6.arpa. Ces options sont disponibles jusqu'à glibc 2.24, où no-ip6-dotint est la valeur par défaut. Comme le support de ip6-dotint a cessé d'être disponible depuis longtemps sur Internet, ces options ont été supprimées dans glibc 2.25.
edns0 (depuis glibc 2.6)
Définit RES_USE_EDNS0 dans _res.options. Ceci active le support des extensions DNS décrites dans la RFC 2671.
single-request (depuis glibc 2.10)
Définit RES_SNGLKUP dans _res.options. Par défaut, glibc effectue les recherches IPv4 et IPv6 en parallèle depuis glibc 2.9. Certains serveurs DNS d'appareils ne peuvent pas gérer ces requêtes correctement et provoquent des délais d'attente. Cette option désactive ce comportement et fait en sorte que glibc effectue les requêtes IPv6 et IPv4 séquentiellement (au détriment d'un certain ralentissement du processus de résolution).
single-request-reopen (depuis glibc 2.9)
Définit RES_SNGLKUPREOP dans _res.options. Le résolveur utilise le même socket pour les requêtes A et AAAA. Certains matériels renvoient à tort une seule réponse. Lorsque cela se produit, le système client attend la deuxième réponse. L'activation de cette option modifie ce comportement de sorte que si deux requêtes provenant du même port ne sont pas gérées correctement, le socket sera fermé et un nouveau sera ouvert avant l'envoi de la deuxième requête.
no-tld-query (depuis glibc 2.14)
Définit RES_NOTLDQUERY dans _res.options. Cette option empêche res_nsearch() de tenter de résoudre un nom non qualifié comme s'il s'agissait d'un domaine de premier niveau (TLD). Cette option peut causer des problèmes si le site a "localhost" comme TLD au lieu d'avoir localhost sur un ou plusieurs éléments de la liste de recherche. Cette option n'a aucun effet si RES_DEFNAMES ou RES_DNSRCH n'est pas défini.
use-vc (depuis glibc 2.14)
Définit RES_USEVC dans _res.options. Cette option force l'utilisation de TCP pour les résolutions DNS.
no-reload (depuis glibc 2.26)
Définit RES_NORELOAD dans _res.options. Cette option désactive le rechargement automatique d'un fichier de configuration modifié.
trust-ad (depuis glibc 2.31)
Définit RES_TRUSTAD dans _res.options. Cette option contrôle le comportement du bit AD du résolveur stub. Si un résolveur validant définit le bit AD dans une réponse, cela indique que les données de la réponse ont été vérifiées conformément au protocole DNSSEC. Afin de se fier au bit AD, le système local doit faire confiance au résolveur validant DNSSEC et au chemin réseau qui y mène, c'est pourquoi une activation explicite est requise. Si l'option trust-ad est active, le résolveur stub définit le bit AD dans les requêtes DNS sortantes (pour activer le support du bit AD) et préserve le bit AD dans les réponses. Sans cette option, le bit AD n'est pas défini dans les requêtes, et il est toujours supprimé des réponses avant qu'elles ne soient renvoyées à l'application. Cela signifie que les applications peuvent se fier au bit AD dans les réponses si l'option trust-ad a été correctement définie.
Dans glibc 2.30 et versions antérieures, le bit AD n'est pas défini automatiquement dans les requêtes et est transmis inchangé aux applications dans les réponses.

Le mot-clé search du fichier resolv.conf d'un système peut être remplacé par processus en définissant la variable d'environnement LOCALDOMAIN à une liste de domaines de recherche séparés par des espaces.

Le mot-clé options du fichier resolv.conf d'un système peut être complété par processus en définissant la variable d'environnement RES_OPTIONS à une liste d'options du résolveur séparés par des espaces, comme expliqué ci-dessus sous options.

Le mot-clé et la valeur doivent apparaître sur une seule ligne, et le mot-clé (par exemple, nameserver) doit commencer la ligne. La valeur suit le mot-clé, séparée par des espaces blancs.

Les lignes contenant un point-virgule (;) ou un dièse (#) dans la première colonne sont traitées comme des commentaires.
