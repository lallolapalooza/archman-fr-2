RESOLVED.CONF(5) resolved.conf RESOLVED.CONF(5)

NOM

resolved.conf, resolved.conf.d — Fichiers de configuration de la résolution de noms réseau

SYNOPIS

/etc/systemd/resolved.conf
/run/systemd/resolved.conf
/usr/local/lib/systemd/resolved.conf
/usr/lib/systemd/resolved.conf
/etc/systemd/resolved.conf.d/*.conf
/run/systemd/resolved.conf.d/*.conf
/usr/local/lib/systemd/resolved.conf.d/*.conf
/usr/lib/systemd/resolved.conf.d/*.conf

DESCRIPTION

Ces fichiers de configuration contrôlent la résolution des noms DNS et LLMNR locaux.

RÉPERTOIRES DE CONFIGURATION ET PRÉCÉDENCE

La configuration par défaut est définie lors de la compilation, donc aucune configuration n'est nécessaire sauf s'il est nécessaire de déroger à ces valeurs par défaut. Le fichier de configuration principal est chargé depuis l'un des répertoires listés par ordre de priorité, seul le premier fichier trouvé est utilisé : /etc/systemd/, /run/systemd/, /usr/local/lib/systemd/ [1], /usr/lib/systemd/. La version fournie par le vendeur du fichier contient des entrées commentées montrant les valeurs par défaut comme guide pour l'administrateur. Des substitutions locales peuvent également être créées en créant des fichiers de configuration supplémentaires (drop-ins), comme décrit ci-dessous. Le fichier de configuration principal peut également être modifié à cette fin (ou une copie dans /etc/ s'il est livré sous /etc/), cependant l'utilisation de fichiers de configuration supplémentaires pour la configuration locale est recommandée plutôt que les modifications du fichier de configuration principal.

En plus du fichier de configuration principal, des fragments de configuration supplémentaires sont lus depuis /usr/lib/systemd/*.conf.d/, /usr/local/lib/systemd/*.conf.d/, et /etc/systemd/*.conf.d/. Ces fichiers supplémentaires ont une priorité plus élevée et remplacent le fichier de configuration principal. Les fichiers dans les sous-répertoires de configuration *.conf.d/ sont triés par leur nom de fichier par ordre lexicographique, quelle que soit la sous-répertoire dans lequel ils résident. Lorsque plusieurs fichiers spécifient la même option, pour les options qui n'acceptent qu'une seule valeur, l'entrée dans le fichier trié en dernier prend la priorité, et pour les options qui acceptent une liste de valeurs, les entrées sont collectées dans l'ordre où elles apparaissent dans les fichiers triés.

Lorsque les paquets doivent personnaliser la configuration, ils peuvent installer des fichiers supplémentaires sous /usr/. Les fichiers dans /etc/ sont réservés à l'administrateur local, qui peut utiliser cette logique pour remplacer les fichiers de configuration installés par les paquets du vendeur. Les fichiers supplémentaires doivent être utilisés pour remplacer les fichiers supplémentaires des paquets, car le fichier de configuration principal a une priorité inférieure. Il est recommandé de préfixer tous les noms de fichiers dans ces sous-répertoires avec un nombre à deux chiffres et un trait d'union, pour simplifier le tri. Cela définit également un concept de priorités de fichiers supplémentaires pour permettre aux fournisseurs de systèmes d'exploitation de livrer des fichiers supplémentaires dans une plage spécifique inférieure à celle utilisée par les utilisateurs. Cela devrait réduire le risque que les fichiers supplémentaires des paquets remplacent accidentellement les fichiers supplémentaires définis par les utilisateurs. Il est recommandé d'utiliser la plage 10-40 pour les fichiers supplémentaires dans /usr/ et la plage 60-90 pour les fichiers supplémentaires dans /etc/ et /run/, pour s'assurer que les fichiers supplémentaires locaux et transitoires prennent la priorité sur les fichiers supplémentaires livrés par le fournisseur du système d'exploitation.

Pour désactiver un fichier de configuration fourni par le vendeur, la méthode recommandée est de placer un lien symbolique vers /dev/null dans le répertoire de configuration de /etc/, avec le même nom de fichier que le fichier de configuration du vendeur.

OPTIONS

Les options suivantes sont disponibles dans la section [Resolve] :

DNS=

Une liste séparée par des espaces d'adresses IPv4 et IPv6 à utiliser comme serveurs DNS système. Chaque adresse peut éventuellement prendre un numéro de port séparé par ":", un nom ou un index d'interface réseau séparé par "%", et un nom d'indication de serveur (SNI) séparé par "#". Lorsque l'adresse IPv6 est spécifiée avec un numéro de port, l'adresse doit être entre crochets. C'est-à-dire que les formats complets acceptables sont "111.222.333.444:9953%ifname#example.com" pour IPv4 et "[1111:2222::3333]:9953%ifname#example.com" pour IPv6. Les requêtes DNS sont envoyées en parallèle à l'un des serveurs DNS listés vers des serveurs DNS appropriés par lien obtenus depuis systemd-networkd.service(8) ou définis à l'exécution par des applications externes. Pour des raisons de compatibilité, si ce paramètre n'est pas spécifié, les serveurs DNS listés dans /etc/resolv.conf sont utilisés à la place, si ce fichier existe et si des serveurs y sont configurés. Ce paramètre est par défaut une liste vide.

Ajouté dans la version 213.

FallbackDNS=

Une liste séparée par des espaces d'adresses IPv4 et IPv6 à utiliser comme serveurs DNS de secours. Veuillez consulter DNS= pour le format acceptable des adresses. Tous les serveurs DNS par lien obtenus depuis systemd-networkd.service(8) ont la priorité sur ce paramètre, tout comme les serveurs définis via DNS= ci-dessus ou /etc/resolv.conf. Ce paramètre n'est donc utilisé que si aucune autre information de serveur DNS n'est connue. Si cette option n'est pas donnée, une liste de serveurs DNS compilée dans le programme est utilisée à la place.

Ajouté dans la version 216.

Domains=

Une liste séparée par des espaces de domaines, éventuellement préfixée par "~", utilisée pour deux objectifs distincts décrits ci-dessous. Par défaut, une liste vide.

Tous les domaines *non* préfixés par "~" sont utilisés comme suffixes de recherche lors de la résolution de noms d'hôtes à étiquette unique (noms de domaine qui ne contiennent pas de point), afin de les qualifier en noms de domaine entièrement qualifiés (FQDN). Ces "domaines de recherche" sont strictement traités dans l'ordre où ils sont spécifiés, jusqu'à ce que le nom avec le suffixe ajouté soit trouvé. Pour des raisons de compatibilité, si ce paramètre n'est pas spécifié, les domaines de recherche listés dans /etc/resolv.conf avec le mot-clé search sont utilisés à la place, si ce fichier existe et si des domaines y sont configurés.

Les domaines préfixés par "~" sont appelés "domaines de routage uniquement". Tous les domaines listés ici ( *domaines de recherche et domaines de routage uniquement* après suppression du préfixe "~") définissent un chemin de recherche qui dirige de préférence les requêtes DNS vers cette interface. Ce chemin de recherche n'a d'effet que lorsque des serveurs DNS appropriés par lien sont connus. De tels serveurs peuvent être définis via le paramètre DNS= (voir ci-dessus) et dynamiquement à l'exécution, par exemple à partir de baux DHCP. Si aucun serveur DNS par lien n'est connu, les domaines de routage uniquement n'ont aucun effet.

Utilisez la construction "~." (qui est composée de "~" pour indiquer un domaine de routage uniquement et "." pour indiquer le domaine racine DNS qui est le suffixe implicite de tous les domaines DNS) pour utiliser de préférence les serveurs DNS définis pour ce lien pour tous les domaines.

Voir "Protocoles et Routage" dans systemd-resolved.service(8) pour les détails sur la façon dont les domaines de recherche et de routage sont utilisés.

Notez que la configuration du domaine MulticastDNS "local" comme domaine de recherche ou de routage a pour effet de router les recherches pour ce domaine vers le DNS unicast classique. Cela peut être utilisé pour assurer la compatibilité avec les installations héritées qui utilisent ce domaine dans un contexte DNS unicast, à l'encontre de l'attribution par l'IANA de ce domaine à des fins de MulticastDNS pures. Les domaines de recherche et de routage sont un concept du DNS unicast, ils *ne peuvent pas* être utilisés pour résoudre des recherches à étiquette unique via MulticastDNS.

Ajouté dans la version 229.

LLMNR=

Accepte un argument booléen ou "resolve". Contrôle la prise en charge de la résolution de noms multicast en lien local (RFC 4795[2]) sur l'hôte local. Si vrai, active la prise en charge complète de l'intercepteur et du résolveur LLMNR. Si faux, désactive les deux. Si défini sur "resolve", seule la prise en charge de la résolution est activée, mais la réponse est désactivée. Notez que systemd-networkd.service(8) maintient également des paramètres LLMNR par lien. LLMNR sera activé sur un lien uniquement si le paramètre par lien et le paramètre global sont activés.

Ajouté dans la version 216.

MulticastDNS=

Accepte un argument booléen ou "resolve". Contrôle la prise en charge du DNS multicast (RFC 6762[3]) sur l'hôte local. Si vrai, active la prise en charge complète de l'intercepteur et du résolveur DNS multicast. Si faux, désactive les deux. Si défini sur "resolve", seule la prise en charge de la résolution est activée, mais la réponse est désactivée. Notez que systemd-networkd.service(8) maintient également des paramètres DNS multicast par lien. Le DNS multicast sera activé sur un lien uniquement si le paramètre par lien et le paramètre global sont activés. activé sur une liaison uniquement si le paramètre par liaison et le paramètre global sont activés.

Ajouté dans la version 234.

DNSSEC=

Accepte un argument booléen ou « allow-downgrade ».

Si défini sur true, toutes les recherches DNS sont validées DNSSEC localement (à l'exclusion de LLMNR et Multicast DNS). Si la réponse à une requête de recherche est détectée comme invalide, un échec de recherche est renvoyé aux applications. Notez que ce mode nécessite un serveur DNS prenant en charge DNSSEC. Si le serveur DNS ne prend pas correctement en charge DNSSEC, toutes les validations échoueront.

Si défini sur « allow-downgrade », la validation DNSSEC est tentée, mais si le serveur ne prend pas correctement en charge DNSSEC, le mode DNSSEC est automatiquement désactivé. Notez que ce mode rend la validation DNSSEC vulnérable aux attaques de « downgrade », où un attaquant pourrait être en mesure de déclencher une rétrogradation vers le mode non-DNSSEC en synthétisant une réponse DNS suggérant que DNSSEC n'était pas pris en charge.

Si défini sur false, les recherches DNS ne sont pas validées par DNSSEC.

Notez que la validation DNSSEC nécessite la récupération de données DNS supplémentaires, et entraîne donc une légère pénalité de temps de recherche DNS.

DNSSEC nécessite la connaissance des « ancres de confiance » pour prouver l'intégrité des données. L'ancre de confiance pour le domaine racine Internet est intégrée au résolveur, des ancres de confiance supplémentaires peuvent être définies avec dnssec-trust-anchors.d(5). Les ancres de confiance peuvent changer à intervalles réguliers, et les anciennes ancres de confiance peuvent être révoquées. Dans un tel cas, la validation DNSSEC n'est pas possible tant que de nouvelles ancres de confiance ne sont pas configurées localement ou que le paquet logiciel du résolveur n'est pas mis à jour avec la nouvelle ancre de confiance racine. En fait, lorsque l'ancre de confiance intégrée est révoquée et que DNSSEC= est true, toutes les recherches ultérieures échoueront, car il ne sera plus possible de prouver si les recherches sont correctement signées ou valablement non signées. Si DNSSEC= est défini sur « allow-downgrade », le résolveur désactivera automatiquement la validation DNSSEC dans un tel cas.

Les programmes clients recherchant des données DNS seront informés si les recherches ont pu être vérifiées à l'aide de DNSSEC, ou si les données renvoyées n'ont pas pu être vérifiées (soit parce que les données ont été trouvées non signées dans le DNS, soit parce que le serveur DNS ne prenait pas en charge DNSSEC ou qu'aucune ancre de confiance appropriée n'était connue). Dans ce dernier cas, il est supposé que les programmes clients utilisent un schéma secondaire pour valider les données DNS renvoyées, si cela est requis.

Il est recommandé de définir DNSSEC= sur true sur les systèmes où l'on sait que le serveur DNS prend correctement en charge DNSSEC, et où les mises à jour logicielles ou d'ancres de confiance sont régulières. Sur d'autres systèmes, il est recommandé de définir DNSSEC= sur « allow-downgrade ».

En plus de ce paramètre DNSSEC global, systemd-networkd.service(8) gère également les paramètres DNSSEC par liaison. Pour les serveurs DNS système (voir ci-dessus), seul le paramètre DNSSEC global est actif. Pour les serveurs DNS par liaison, le paramètre par liaison est actif, sauf s'il est non défini, auquel cas le paramètre global est utilisé à la place.

Les zones DNS privées du site entrent généralement en conflit avec le fonctionnement de DNSSEC, à moins qu'une ancre de confiance négative (si la zone privée n'est pas signée) ou positive (si la zone privée est signée) ne soit configurée pour elles. Si le mode « allow-downgrade » est sélectionné, une tentative est faite pour détecter les zones DNS privées du site en utilisant des domaines de premier niveau (TLD) qui ne sont pas connus du serveur racine DNS. Cette logique ne fonctionne pas dans toutes les configurations de zones privées.

Par défaut : « no ».

Ajouté dans la version 229.

DNSOverTLS=

Accepte un argument booléen ou « opportunistic ». Si true, toutes les connexions au serveur seront cryptées. Notez que ce mode nécessite un serveur DNS prenant en charge DNS-over-TLS et disposant d'un certificat valide. Si le nom d'hôte a été spécifié dans DNS= en utilisant le format « address#server_name », il est utilisé pour valider son certificat et également pour activer l'indication du nom du serveur (SNI) lors de l'ouverture d'une connexion TLS. Sinon, le certificat est vérifié par rapport à l'adresse IP du serveur. Si le serveur DNS ne prend pas en charge DNS-over-TLS, toutes les requêtes DNS échoueront.

Lorsque défini sur « opportunistic », les requêtes DNS sont tentées d'être envoyées cryptées avec DNS-over-TLS. Si le serveur DNS ne prend pas en charge TLS, DNS-over-TLS est désactivé. Notez que ce mode rend DNS-over-TLS vulnérable aux attaques de « downgrade », où un attaquant pourrait être en mesure de déclencher une rétrogradation vers le mode non crypté en synthétisant une réponse suggérant que DNS-over-TLS n'était pas pris en charge. Si défini sur false, les recherches DNS sont envoyées sur UDP.

Notez que DNS-over-TLS nécessite des données supplémentaires à envoyer pour établir une connexion cryptée, et entraîne donc une légère pénalité de temps de recherche DNS.

Notez qu'en mode « opportunistic », le résolveur n'est pas capable d'authentifier le serveur, il est donc vulnérable aux attaques de « homme du milieu ».

En plus de ce paramètre global DNSOverTLS=, systemd-networkd.service(8) maintient également des paramètres DNSOverTLS= par liaison. Pour les serveurs DNS système (voir ci-dessus), seul le paramètre global DNSOverTLS= est actif. Pour les serveurs DNS par liaison, le paramètre par liaison est actif, sauf s'il est non défini, auquel cas le paramètre global est utilisé à la place.

Par défaut : « no ».

Ajouté dans la version 239.

Cache=

Accepte un argument booléen ou « no-negative ». Si « yes » (par défaut), résoudre un nom de domaine qui a déjà été interrogé précédemment renverra le résultat précédent tant qu'il est encore valide, et n'entraînera donc pas de nouvelle requête réseau. Soyez conscient que désactiver la mise en cache entraîne une pénalité de performance, qui est particulièrement élevée lorsque DNSSEC est utilisé. Si « no-negative », seules les réponses positives sont mises en cache.

Notez que la mise en cache est désactivée par défaut pour les serveurs DNS locaux (host-local). Voir CacheFromLocalhost= pour plus de détails.

Ajouté dans la version 231.

CacheFromLocalhost=

Accepte un argument booléen. Si « no » (par défaut), et que la réponse provient d'une adresse IP locale (telle que 127.0.0.1 ou ::1), le résultat ne sera pas mis en cache afin d'éviter une mise en cache locale potentiellement double.

Ajouté dans la version 248.

DNSStubListener=

Accepte un argument booléen ou l'un des « udp » et « tcp ». Si « udp », un résolveur stub DNS écoutera les requêtes UDP sur les adresses 127.0.0.53 et 127.0.0.54, port 53. Si « tcp », le stub écoutera les requêtes TCP sur les mêmes adresses et port. Si « yes » (par défaut), le stub écoute les requêtes UDP et TCP. Si « no », l'écouteur stub est désactivé.

Le résolveur stub DNS sur 127.0.0.53 fournit l'ensemble complet des fonctionnalités du résolveur local, qui comprend l'offre de résolution LLMNR/MulticastDNS. Le résolveur stub DNS sur 127.0.0.54 fournit un résolveur plus limité, qui fonctionne uniquement en mode « proxy », c'est-à-dire qu'il transmettra la plupart des messages DNS relativement sans modification aux serveurs DNS amont actuels et en arrière, mais n'essaiera pas de traiter les messages localement, et par conséquent ne valide pas DNSSEC, ni n'offre LLMNR/MulticastDNS. (Il traduira en communication DNS-over-TLS si nécessaire.)

Notez que l'écouteur stub DNS est désactivé implicitement lorsque son adresse et son port d'écoute sont déjà utilisés.

Ajouté dans la version 232.

RefuseRecordTypes=

Accepte une liste de types d'enregistrements DNS séparés par des espaces. Les types d'enregistrements spécifiés dans chaque requête seront refusés. Cette option peut être spécifiée plusieurs fois. Si une chaîne vide est spécifiée, alors toutes les affectations précédentes sont effacées.

Exemples :

RefuseRecordTypes=AAAA SRV TXT

Notez que pour refuser complètement les enregistrements AAAA (contrairement à SRV, TXT, etc.), veuillez également désactiver la pile IPv6 dans le noyau avec « sysctl -w net.ipv6.conf.all.disable_ipv6=1 ».

Ajouté dans la version 258.

DNSStubListenerExtra=

Accepte une adresse IPv4 ou IPv6 sur laquelle écouter. L'adresse peut être éventuellement préfixée par un nom de protocole (« udp » ou « tcp ») séparé par « : ». Si le protocole n'est pas spécifié, le service écoutera sur UDP et TCP. Il peut également être éventuellement suffixé par un numéro de port numérique avec le séparateur « : ». Lorsqu'une adresse IPv6 est spécifiée avec un numéro de port, l'adresse doit être entre crochets. Si le port n'est pas spécifié, le service utilise le port 53. Notez que ceci est indépendant du stub DNS principal configuré avec DNSStubListener=, et ne configure que des sockets *supplémentaires* sur lesquels écouter. Cette option peut être spécifiée plusieurs fois. Si une chaîne vide est affectée, alors toutes les affectations précédentes sont effacées. Valeur par défaut : non définie.

Exemples :

DNSStubListenerExtra=192.168.10.10
DNSStubListenerExtra=2001:db8:0:f102::10
DNSStubListenerExtra=192.168.10.11:9953
DNSStubListenerExtra=[2001:db8:0:f102::11]:9953
DNSStubListenerExtra=tcp:192.168.10.12
DNSStubListenerExtra=udp:2001:db8:0:f102::12
DNSStubListenerExtra=tcp:192.168.10.13:9953
DNSStubListenerExtra=udp:[2001:db8:0:f102::13]:9953

Ajouté dans la version 247.

ReadEtcHosts=

Accepte un argument booléen. Si « yes » (par défaut), systemd-resolved lira /etc/hosts, et essaiera de résoudre des hôtes ou des adresses en utilisant les entrées du fichier avant d'envoyer une requête aux serveurs DNS.

Ajouté dans la version 240.

ResolveUnicastSingleLabel=

Accepte un argument booléen. Lorsque false (par défaut), systemd-resolved ne résoudra pas les requêtes A et AAAA pour les noms à étiquette unique via le DNS classique. Notez que de tels noms peuvent toujours être résolus si des domaines de recherche sont spécifiés (voir Domains= ci-dessus), ou via d'autres mécanismes, en particulier via LLMNR ou depuis /etc/hosts. Lorsqu'il est vrai, les requêtes pour les noms à étiquette unique seront transmises aux serveurs DNS globaux même si aucun domaine de recherche n'est défini.

Cette option est fournie pour la compatibilité avec les configurations où les serveurs DNS publics ne sont pas utilisés. Transmettre les noms à étiquette unique à des serveurs qui ne sont pas sous votre contrôle n'est pas conforme aux normes, voir l' **Déclaration de l'IAB**[4], et peut créer un risque pour la vie privée et la sécurité.

Ajouté dans la version 246.

StaleRetentionSec=SECONDS

Accepte une valeur de durée, qui détermine la durée pendant laquelle les enregistrements de ressources DNS peuvent être conservés dans le cache au-delà de leur durée de vie (TTL). Cela permet à ces enregistrements d'être renvoyés en tant qu'enregistrements obsolètes. Par défaut, cette valeur est définie sur zéro, ce qui signifie que les enregistrements de ressources DNS ne sont pas stockés dans le cache après l'expiration de leur TTL.

resolved.conf.d(5)

NAME

resolved.conf.d — Configuration directory for systemd-resolved.service(8)

SYNOPSIS

/etc/systemd/resolved.conf.d/
/run/systemd/resolved.conf.d/
/usr/lib/systemd/resolved.conf.d/

DESCRIPTION

The configuration files are read from a directory as listed in CONFIGURATION DIRECTORIES AND PRECEDENCE. The main configuration file is resolved.conf(5). This directory provides a way to add configuration snippets, which are parsed in lexicographical order, after the main configuration file. This allows for system administrators and package vendors to override and extend the main configuration file.

The snippets are dropped in the .conf file extension, and the rest of the filename is ignored. They are parsed after the main configuration file, and have the same format. They are parsed in lexicographical order.

The configuration snippets are useful for options that need to be set globally, but should not be in the main configuration file. For example, to enable a DNSSEC-related feature, you might add a configuration snippet to /etc/systemd/resolved.conf.d/dnssec.conf.

Note that the configuration files in /etc/ and /run/ are used to control the system-wide daemon instance, while the configuration files in /usr/lib/ are used to configure the default behavior of the service. Any configuration snippet placed in /etc/ will override a snippet with the same name in /run/ or /usr/lib/. Similarly, a snippet in /run/ will override a snippet with the same name in /usr/lib/.

CONFIGURATION DIRECTORIES AND PRECEDENCE

The main configuration file is resolved.conf(5). Additional configuration snippets may be placed in snippet directories. These are read in the following order:

  1. /usr/lib/systemd/resolved.conf.d/
  2. /run/systemd/resolved.conf.d/
  3. /etc/systemd/resolved.conf.d/

All files are scanned in each directory, and sorted lexicographically. Files starting with “.”, or ending with “~” or “.bak” are ignored. If multiple files specify the same option, the value specified in the file that is read later takes precedence.

OPTIONS

The configuration snippets follow the same format as resolved.conf(5). The following options are supported:

DNSOverTLS=
Configures the DNS over TLS mode. Can be one of no, opportunistic, or yes. When set to opportunistic or yes, DNS queries are sent over DNS over TLS. When set to yes, DNS over TLS is enforced and will fail if it cannot be established. When set to opportunistic, DNS over TLS is used if available, but will fall back to plain DNS if it is not. Default is no.
DNSSEC=
Configures the DNSSEC validation mode. Can be one of no, allow-downgrade, or yes. When set to yes, DNSSEC validation is enabled and will cause DNS queries to fail if validation fails. When set to allow-downgrade, DNSSEC validation is enabled but will not cause DNS queries to fail if validation fails (e.g., due to the server not supporting DNSSEC). Default is no.
DNSSECSettingTime=
Configures the DNSSEC settle time. This is the time in seconds that systemd-resolved will wait before considering DNSSEC settings to be stable. During this time, it will not reconfigure DNSSEC settings. Default is 30 seconds.
Cache=
When enabled, systemd-resolved will cache DNS responses. This can improve performance by reducing the number of DNS queries sent to upstream servers. Default is enabled.
Cache-Max-TTL=
Sets the maximum Time-To-Live (TTL) for cached DNS records. Any cached record with a TTL greater than this value will be effectively capped at this value. This helps prevent stale data from residing in the cache for too long. This option only applies if Cache= is enabled. Default is 3600 seconds (1 hour).
Cache-Negative-TTL=
Sets the TTL for negative DNS responses (e.g., NXDOMAIN). This controls how long non-existent domain names are remembered in the cache. This option only applies if Cache= is enabled. Default is 300 seconds (5 minutes).
Unicast-TTLs=
Controls the TTLs for unicast DNS queries. This option allows to specify a list of TTL values that systemd-resolved will use for unicast DNS queries. If this option is set, systemd-resolved will use these TTL values instead of the ones provided by the DNS server. This feature enhances resilience against DNS infrastructure failures and outages. Added in version 254.
Multicast-TTLs=
Controls the TTLs for multicast DNS queries. Similar to Unicast-TTLs=, but applies to multicast DNS queries. Added in version 254.

This feature, which allows specifying unicast and multicast TTLs, enhances resilience against DNS infrastructure failures and outages. It works by allowing systemd-resolved to use cached responses for a longer duration when upstream DNS servers are unreachable. However, this does not apply to NXDOMAIN responses, as those are still perfectly valid responses. systemd-resolved always attempts to reach the upstream DNS servers first, before providing the client application with any stale data. If this feature is enabled, the cache will not be flushed when changing servers.

Added in version 254.
