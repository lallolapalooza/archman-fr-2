DESCRIPTION

Les fonctions constituent un système assez extensible pour l'analyse de divers fichiers de configuration au moment de l'exécution d'une application. Le flux de fichiers de configuration est décomposé dans les phases suivantes :

1.
Enregistrement des gestionnaires.
2.
Lecture des fichiers de configuration pour les besoins de l'analyse avant MIB.
3.
Lecture et analyse des fichiers MIB textuels.
4.
Lecture des fichiers de configuration pour les directives de configuration.
5.
Optionnellement, relecture des fichiers de configuration à une date ultérieure.

L'idée est que l'application appelante soit capable d'enregistrer des gestionnaires pour certains tokens spécifiés dans certains fichiers de configuration nommés. La fonction read_configs() peut alors être appelée pour rechercher tous les fichiers de configuration pertinents, faire correspondre le premier mot de chaque ligne avec la liste des tokens enregistrés et passer le reste de la ligne au gestionnaire enregistré approprié.

ENREGISTREMENT D'UN GESTIONNAIRE

register_config_handler()
Enregistre une routine de gestion de configuration, qui doit être appelée pour traiter les directives de configuration commençant par le token spécifié. Par exemple :
register_config_handler("snmp", "exampleToken", example_handler, NULL, "ARG1 [ARG2]");
enregistrerait la fonction example_handler() afin qu'elle soit appelée chaque fois que le premier mot d'une ligne dans le(s) fichier(s) de configuration snmp.conf correspond à "exampleToken".
L'appel des gestionnaires appropriés pour traiter les directives du fichier de configuration relève de la responsabilité de read_configs() (voir ci-dessous).
register_const_config_handler()
Similaire à la fonction register_config_handler(), mais la routine de l'analyseur est explicitement contrainte de ne pas modifier la chaîne analysée.
register_prenetsnmp_mib_handler()
Similaire à la fonction register_config_handler(), mais la routine du gestionnaire enregistré sera appelée avant la lecture des MIB textuelles. Ceci est généralement utilisé pour les tokens qui affecteront la configuration de l'analyseur MIB, et ne sera normalement utilisé qu'à l'intérieur de la bibliothèque SNMP elle-même.
register_mib_handlers()
Routine d'initialisation pour enregistrer les gestionnaires de configuration internes de la bibliothèque SNMP.
unregister_config_handler()
Supprime le gestionnaire de configuration enregistré pour le filePrefix et le token spécifiés.
unregister_all_config_handlers()
Supprime tous les gestionnaires de configuration enregistrés.

Gestionnaires de tokens

Les fonctions de gestionnaire doivent avoir la signature suivante :

void handler(const char *token, char *line);
ou
void handler(const char *token, const char *line); br (si enregistré via register_const_config_handler)

La fonction sera appelée avec deux arguments, le premier étant le token qui a déclenché l'appel à cette fonction (c'est-à-dire le token utilisé lors de l'enregistrement du gestionnaire), et le second étant le reste de la ligne du fichier de configuration (c'est-à-dire tout ce qui suit l'espace blanc après le token correspondant).

Gestionnaires de libération

Si la fonction de gestionnaire de token alloue dynamiquement des ressources lors du traitement d'une entrée de configuration, celles-ci pourront devoir être libérées avant de relire les fichiers de configuration. Si le quatrième paramètre (releaser) passé à register_config_handler n'est pas NULL, alors il spécifie une fonction à appeler avant de relire les fichiers de configuration. Cette fonction doit libérer toutes les ressources allouées par la fonction de gestionnaire de token et réinitialiser sa notion de configuration à sa valeur par défaut. La fonction de gestionnaire de token pourra alors être appelée à nouveau en toute sécurité. Aucun argument n'est passé au gestionnaire de libération de ressources.
Notez que cette fonction n'est pas appelée lorsque le gestionnaire est désenregistré individuellement (mais elle est appelée dans le cadre de unregister_all_config_handlers() ).

Gestionnaires d'application

register_app_config_handler()
register_app_prenetsnmp_mib_handler()
unregister_app_config_handler()
Ces fonctions sont analogues à register_config_handler(), register_prenetsnmp_mib_handler() et unregister_config_handler() mais ne nécessitent pas l'argument du type de fichier (qui est rempli par l'application). Il est prévu que les modules MIB écrits pour l'agent utilisent ces fonctions pour permettre à l'agent d'avoir plus de contrôle sur les fichiers de configuration qui sont lus (typiquement les fichiers snmpd.conf).

LECTURE DES FICHIERS DE CONFIGURATION

read_premib_configs()
read_configs()
Ces routines traitent les fichiers de configuration trouvés dans le chemin de recherche de configuration (voir ci-dessous). Pour chaque entrée, le gestionnaire enregistré pour ce jeton de configuration est appelé.

read_premib_configs() est exécuté avant que les fichiers MIB ne soient lus, et traite les jetons de configuration enregistrés à l'aide de register_prenetsnmp_mib_handler() (ou register_app_prenetsnmp_mib_handler()). Toutes les autres entrées sont ignorées.

read_configs() est exécuté après la lecture des fichiers MIB, et traite les jetons de configuration enregistrés à l'aide de register_config_handler() (ou register_app_config_handler()). S'il rencontre un jeton de configuration pour lequel aucun gestionnaire n'a été enregistré (pré- ou post-mib), il affichera un message d'avertissement et continuera le traitement avec la ligne suivante du fichier de configuration.

Chemin de recherche de configuration

Les fichiers de configuration à lire sont trouvés en parcourant une liste de répertoires de configuration pour les fichiers portant les noms appropriés. Dans chaque répertoire, la bibliothèque recherchera les fichiers nommés snmp.conf, snmp.local.conf, app.conf, app.local.conf,
(où app est le préfixe de fichier spécifique à l'application utilisé pour enregistrer les gestionnaires de configuration). Il n'est pas nécessaire que ces fichiers soient présents dans chaque répertoire. Les fichiers manquants seront ignorés silencieusement.
L'idée derrière les deux suffixes différents est que le premier fichier peut être partagé (via rdist ou un montage NFS) sur un grand nombre de machines et le second fichier peut être utilisé pour configurer les paramètres locaux d'une machine particulière.

La liste par défaut des répertoires à rechercher est /etc/snmp, suivi de /usr/share/snmp, suivi de /usr/lib/snmp, suivi de $HOME/.snmp. Cette liste peut être modifiée en définissant la variable d'environnement SNMPCONFPATH sur une liste de répertoires (séparés par des deux-points) à rechercher.

init_snmp()

Le mode de fonctionnement normal consisterait à enregistrer les gestionnaires de configuration spécifiques à l'application, puis à appeler init_snmp(). Cela appellerait les routines listées ci-dessus pour enregistrer les gestionnaires de configuration internes de la bibliothèque, traiter les jetons de configuration enregistrés avec register_prenetsnmp_mib_handler(), lire les fichiers MIB textuels à l'aide de init_mib(), et enfin analyser les jetons de fichier de configuration enregistrés avec register_config_handler().

Si la fonction init_snmp() est utilisée, aucune de ces fonctions ne doit être explicitement appelée par l'application.

CHAÎNES D'AIDE ET ERREURS

Le paramètre usageLine passé à register_config_handler() et aux appels similaires, est utilisé pour afficher des informations d'aide lorsque la fonction read_config_print_usage() est appelée. Cette fonction est utilisée par toutes les applications lorsque l'option -H est passée sur la ligne de commande. Elle affiche un résumé de toutes les lignes de fichier de configuration et des fichiers associés que le système de configuration comprend. Le paramètre usageLine doit être une liste d'arguments attendus après le jeton, et non une description détaillée (qui devrait plutôt figurer dans une page de manuel). Le préfixe lead sera ajouté à chaque ligne que la fonction imprime sur stderr, où elle affiche sa sortie.

La fonction init_snmp() doit être appelée avant la fonction read_config_print_usage() afin que la bibliothèque puisse également enregistrer ses directives de fichier de configuration pour que la fonction read_config_print_usage() les affiche.

Fonctions de gestion des erreurs

Les deux fonctions config_pwarn() et config_perror() prennent toutes deux une chaîne d'erreur comme argument et l'impriment sur stderr avec le fichier et le numéro de ligne qui ont causé l'erreur. Un appel à la deuxième fonction forcera également read_configs() à retourner finalement avec un code d'erreur indiquant à la fonction appelante qu'elle doit abandonner l'opération de l'application.

VARIABLES D'ENVIRONNEMENT

SNMPCONFPATH
Une liste de répertoires séparés par des deux-points à rechercher pour les fichiers de configuration. Par défaut :
/etc/snmp:/usr/share/snmp:/usr/lib/snmp:$HOME/.snmp
