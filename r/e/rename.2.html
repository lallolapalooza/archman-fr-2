rename(2) Manuel des appels système rename(2)

NOM

rename, renameat, renameat2 - changer le nom ou l'emplacement d'un fichier

BIBLIOTHEQUE

Bibliothèque C standard (libc, -lc)

SYNOPSIS

#include <stdio.h>
int rename(const char *oldpath, const char *newpath);
#include <fcntl.h>           /* Définition des constantes AT_* */
#include <stdio.h>
int renameat(int olddirfd, const char *oldpath,
             int newdirfd, const char *newpath);
int renameat2(int olddirfd, const char *oldpath,
             int newdirfd, const char *newpath, unsigned int flags);
Conditions de test des fonctionnalités pour glibc (voir feature_test_macros(7)) :

renameat2() :

DESCRIPTION

rename() renomme un fichier, le déplaçant entre répertoires si nécessaire. Tous les autres liens physiques vers le fichier (créés avec link(2)) ne sont pas affectés. Les descripteurs de fichiers ouverts pour oldpath ne sont pas non plus affectés.

Diverses restrictions déterminent si l'opération de renommage réussit ou échoue : voir ERREURS ci-dessous.

Si newpath existe déjà, il sera remplacé de manière atomique, de sorte qu'il n'y aura aucun moment où un autre processus essayant d'accéder à newpath le trouvera manquant. Cependant, il y aura probablement une fenêtre pendant laquelle oldpath et newpath font tous deux référence au fichier en cours de renommage.

Si oldpath et newpath sont des liens physiques existants faisant référence au même fichier, alors rename() ne fait rien et renvoie un statut de succès.

Si newpath existe mais que l'opération échoue pour une raison quelconque, rename() garantit de laisser une instance de newpath en place.

oldpath peut spécifier un répertoire. Dans ce cas, newpath doit soit ne pas exister, soit spécifier un répertoire vide.

Si oldpath fait référence à un lien symbolique, le lien est renommé ; si newpath fait référence à un lien symbolique, le lien sera écrasé.

renameat()

L'appel système renameat() fonctionne exactement de la même manière que rename(), sauf pour les différences décrites ici.

Si le chemin spécifié dans oldpath est relatif, il est interprété par rapport au répertoire référencé par le descripteur de fichier olddirfd (plutôt que par rapport au répertoire de travail courant du processus appelant, comme le fait rename() pour un chemin relatif).

Si oldpath est relatif et olddirfd est la valeur spéciale AT_FDCWD, alors oldpath est interprété par rapport au répertoire de travail courant du processus appelant (comme rename()).

Si oldpath est absolu, alors olddirfd est ignoré.

L'interprétation de newpath est la même que pour oldpath, sauf qu'un chemin relatif est interprété par rapport au répertoire référencé par le descripteur de fichier newdirfd.

Voir openat(2) pour une explication de la nécessité de renameat().

renameat2()

renameat2() a un argument supplémentaire flags. Un appel renameat2() avec un argument flags nul est équivalent à renameat().

L'argument flags est un masque de bits composé de zéro ou plus des drapeaux suivants :

RENAME_EXCHANGE
Échange atomiquement oldpath et newpath. Les deux chemins doivent exister mais peuvent être de types différents (par exemple, l'un pourrait être un répertoire non vide et l'autre un lien symbolique).
RENAME_NOREPLACE
Ne pas écraser newpath lors du renommage. Renvoie une erreur si newpath existe déjà.
RENAME_NOREPLACE ne peut pas être utilisé avec RENAME_EXCHANGE.
RENAME_NOREPLACE nécessite le support du système de fichiers sous-jacent. Le support pour divers systèmes de fichiers a été ajouté comme suit :
•
ext4 (Linux 3.15) ;
•
btrfs, tmpfs et cifs (Linux 3.17) ;
•
xfs (Linux 4.0) ;
•
Le support de nombreux autres systèmes de fichiers a été ajouté dans Linux 4.9, y compris ext2, minix, reiserfs, jfs, vfat et bpf.
RENAME_WHITEOUT (depuis Linux 3.18)
Cette opération n'a de sens que pour les implémentations de systèmes de fichiers overlay/union.
Spécifier RENAME_WHITEOUT crée un objet "whiteout" à la source du renommage en même temps qu'il effectue le renommage. L'opération entière est atomique, de sorte que si le renommage réussit, le whiteout aura également été créé.
Un "whiteout" est un objet qui a une signification spéciale dans les constructions de systèmes de fichiers union/overlay. Dans ces constructions, plusieurs couches existent et seule la couche supérieure est jamais modifiée. Un whiteout sur une couche supérieure masquera efficacement un fichier correspondant dans la couche inférieure, donnant l'impression que le fichier n'existe pas.
Lorsqu'un fichier qui existe dans la couche inférieure est renommé, le fichier est d'abord copié vers le haut (s'il n'est pas déjà dans la couche supérieure), puis renommé dans la couche supérieure en lecture-écriture. En même temps, le fichier source doit être "whiteouté" (de sorte que la version du fichier source dans la couche inférieure soit rendue invisible). L'opération entière doit être effectuée de manière atomique.
Lorsqu'il ne fait pas partie d'une union/overlay, le whiteout apparaît comme un périphérique de caractères avec un numéro de périphérique {0,0}. (Notez que d'autres implémentations d'union/overlay peuvent utiliser des méthodes différentes pour stocker les entrées de whiteout ; en particulier, l'union mount BSD utilise un type d'inode séparé, DT_WHT, qui, bien que pris en charge par certains systèmes de fichiers disponibles sous Linux, tels que CODA et XFS, est ignoré par le code de prise en charge des whiteouts du noyau, à partir de Linux 4.19, au moins.)
RENAME_WHITEOUT nécessite les mêmes privilèges que la création d'un nœud de périphérique (c'est-à-dire la capacité CAP_MKNOD).
RENAME_WHITEOUT ne peut pas être utilisé avec RENAME_EXCHANGE.
RENAME_WHITEOUT nécessite le support du système de fichiers sous-jacent. Parmi les systèmes de fichiers qui le prennent en charge, on trouve tmpfs (depuis Linux 3.18), ext4 (depuis Linux 3.18), XFS (depuis Linux 4.1), f2fs (depuis Linux 4.2), btrfs (depuis Linux 4.7) et ubifs (depuis Linux 4.9).

VALEUR RENVOYEE

En cas de succès, zéro est renvoyé. En cas d'erreur, -1 est renvoyé, et errno est défini pour indiquer l'erreur.

ERREURS

EACCES
L'autorisation d'écriture est refusée pour le répertoire contenant oldpath ou newpath, ou bien l'autorisation de recherche est refusée pour l'un des répertoires du préfixe de chemin de oldpath ou newpath, ou bien oldpath est un répertoire et ne permet pas l'autorisation d'écriture (nécessaire pour mettre à jour l'entrée ..). ERREURS

En cas de succès, rename() renvoie zéro. En cas d'échec, il renvoie -1 et errno est défini pour indiquer l'erreur.

EBUSY
La nouvelle oldpath pointe vers un point de montage, tandis que le système considère cela comme une erreur. (Notez qu'il n'est pas obligatoire de renvoyer EBUSY dans de tels cas — il n'y a rien de mal à effectuer le renommage de toute façon — mais il est permis de renvoyer EBUSY si le système ne peut pas gérer de telles situations autrement.)
EDQUOT
Le quota de blocs disque de l'utilisateur sur le système de fichiers a été épuisé.
EFAULT
oldpath ou newpath pointe en dehors de votre espace d'adressage accessible.
EINVAL
Le nouveau chemin contenait un préfixe du chemin précédent, ou, plus généralement, une tentative a été faite pour faire d'un répertoire un sous-répertoire de lui-même.
EISDIR
newpath est un répertoire existant, mais oldpath n'est pas un répertoire.
ELOOP
Trop de liens symboliques ont été rencontrés lors de la résolution de oldpath ou newpath.
EMLINK
oldpath a déjà le nombre maximum de liens pointant vers lui, ou c'était un répertoire et le répertoire contenant newpath a le nombre maximum de liens.
ENAMETOOLONG
oldpath ou newpath était trop long.
ENOENT
Le lien nommé par oldpath n'existe pas ; ou, un composant de répertoire dans newpath n'existe pas ; ou, oldpath ou newpath est une chaîne vide.
ENOMEM
La mémoire noyau insuffisante était disponible.
ENOSPC
Le périphérique contenant le fichier n'a plus de place pour la nouvelle entrée de répertoire.
ENOTDIR
Un composant utilisé comme répertoire dans oldpath ou newpath n'est pas, en fait, un répertoire. Ou, oldpath est un répertoire, et newpath existe mais n'est pas un répertoire.
ENOTEMPTY ou EEXIST
newpath est un répertoire non vide, c'est-à-dire qu'il contient des entrées autres que "." et "..".
EPERM ou EACCES
Le répertoire contenant oldpath a le bit spécial (S_ISVTX) activé et l'ID utilisateur effectif du processus n'est ni l'ID utilisateur du fichier à supprimer ni celui du répertoire qui le contient, et le processus n'est pas privilégié (Linux : n'a pas la capacité CAP_FOWNER) ; ou newpath est un fichier existant et le répertoire qui le contient a le bit spécial activé et l'ID utilisateur effectif du processus n'est ni l'ID utilisateur du fichier à remplacer ni celui du répertoire qui le contient, et le processus n'est pas privilégié (Linux : n'a pas la capacité CAP_FOWNER) ; ou le système de fichiers contenant oldpath ne prend pas en charge le renommage du type demandé.
EROFS
Le fichier se trouve sur un système de fichiers en lecture seule.
EXDEV
oldpath et newpath ne sont pas sur le même système de fichiers monté. (Linux autorise le montage d'un système de fichiers en plusieurs points, mais rename() ne fonctionne pas entre différents points de montage, même si le même système de fichiers est monté sur les deux.)

Les erreurs supplémentaires suivantes peuvent survenir pour renameat() et renameat2():

EBADF
oldpath (newpath) est relatif mais olddirfd (newdirfd) n'est pas un descripteur de fichier valide.
ENOTDIR
oldpath est relatif et olddirfd est un descripteur de fichier faisant référence à autre chose qu'un répertoire ; ou similaire pour newpath et newdirfd

Les erreurs supplémentaires suivantes peuvent survenir pour renameat2():

EEXIST
flags contient RENAME_NOREPLACE et newpath existe déjà.
EINVAL
Un indicateur invalide a été spécifié dans flags.
EINVAL
Les deux RENAME_NOREPLACE et RENAME_EXCHANGE ont été spécifiés dans flags.
EINVAL
Les deux RENAME_WHITEOUT et RENAME_EXCHANGE ont été spécifiés dans flags.
EINVAL
Le système de fichiers ne prend pas en charge l'un des indicateurs dans flags.
ENOENT
flags contient RENAME_EXCHANGE et newpath n'existe pas.
EPERM
RENAME_WHITEOUT a été spécifié dans flags, mais l'appelant n'a pas la capacité CAP_MKNOD.

Notes glibc

Sur les anciens noyaux où renameat() n'est pas disponible, la fonction d'encapsulation glibc se rabat sur l'utilisation de rename(). Lorsque oldpath et newpath sont des chemins relatifs, glibc construit des chemins basés sur les liens symboliques dans /proc/self/fd qui correspondent aux arguments olddirfd et newdirfd.

BUGS

Sur les systèmes de fichiers NFS, vous ne pouvez pas supposer que si l'opération a échoué, le fichier n'a pas été renommé. Si le serveur effectue l'opération de renommage puis plante, la requête RPC retransmise qui sera traitée lorsque le serveur sera à nouveau opérationnel provoquera une erreur. L'application est censée gérer cela. Voir link(2) pour un problème similaire.
