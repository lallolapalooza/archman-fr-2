refchan(n) Commandes intégrées Tcl refchan(n)

NOM

refchan - API du gestionnaire de commandes des canaux réfléchis

SYNOPSIS

préfixeCmd option ?arg arg ...?

DESCRIPTION

Le gestionnaire au niveau Tcl pour un canal réfléchi doit être une commande avec des sous-commandes (appelées un ensemble, car c'est une commande telle que créée par namespace ensemble create, bien que l'implémentation des gestionnaires pour les canaux réfléchis *ne soit pas* liée aux ensembles namespace d'une quelconque manière ; voir l'EXEMPLE ci-dessous pour savoir comment construire une classe oo:: qui prend en charge l'API). Notez que préfixeCmd est ce qui a été spécifié dans l'appel à chan create, et peut consister en plusieurs arguments ; ceci sera développé en plusieurs mots à la place du préfixe.

Parmi toutes les sous-commandes possibles, le gestionnaire *doit* prendre en charge initialize, finalize et watch. La prise en charge des autres sous-commandes est facultative.

SOUS-COMMANDES OBLIGATOIRES

préfixeCmd initialize canalId mode
Une invocation de cette sous-commande sera le premier appel que préfixeCmd recevra pour le nouveau canalId spécifié. Il incombe à cette sous-commande de configurer toutes les structures de données internes nécessaires pour suivre le canal et son état.

La valeur de retour de la méthode doit être une liste contenant les noms de toutes les sous-commandes prises en charge par préfixeCmd. Cela indique également au noyau Tcl quelle version de l'API pour les canaux réfléchis est utilisée par ce gestionnaire de commande.

Toute erreur générée par la méthode annulera la création du canal et aucun canal ne sera créé. L'erreur générée apparaîtra comme une erreur générée par chan create. Toute exception autre qu'une error (par ex. break, etc.) est traitée comme (et convertie en) une erreur.

Note : Si la création du canal a été annulée en raison d'échecs ici, la sous-commande finalize ne sera pas appelée.

L'argument mode indique au gestionnaire si le canal a été ouvert en lecture, en écriture ou les deux. C'est une liste contenant les chaînes read ou write. La liste peut être vide, mais contiendra généralement au moins un élément.

La sous-commande doit générer une erreur si le mode choisi n'est pas pris en charge par préfixeCmd.

préfixeCmd finalize canalId
Une invocation de cette sous-commande sera le dernier appel que préfixeCmd recevra pour le canalId spécifié. Elle sera générée juste avant la destruction des structures de données du canal détenues par le noyau Tcl. Le gestionnaire de commande *ne doit plus* accéder au canalId d'aucune manière. Lors de l'appel de cette sous-commande, toutes les ressources internes allouées à ce canal doivent être nettoyées.

La valeur de retour de cette sous-commande est ignorée.

Si la sous-commande génère une erreur, la commande qui a provoqué son invocation (généralement chan close) semblera avoir généré cette erreur. Toute exception au-delà d'une error (par ex. break, etc.) est traitée comme (et convertie en) une erreur.

Cette sous-commande n'est pas appelée si la création du canal a été annulée lors de initialize (Voir ci-dessus).

préfixeCmd watch canalId specEvenement
Cette sous-commande notifie préfixeCmd que le canalId spécifié s'intéresse aux événements listés dans specEvenement. Cet argument est une liste contenant read et/ou write. La liste peut être vide, ce qui indique que le canal ne souhaite pas être notifié d'événements. Dans ce cas, le gestionnaire doit désactiver la génération d'événements.

Attention : Toute valeur de retour de la sous-commande est ignorée. Cela inclut toutes les erreurs générées par la sous-commande, break, continue et les codes de retour personnalisés.

Cette sous-commande interagit avec chan postevent. Essayer de publier un événement qui ne figurait pas dans le dernier appel à watch provoquera une erreur de la part de chan postevent.

SOUS-COMMANDES FACULTATIVES

préfixeCmd read canalId compte
Cette sous-commande *facultative* est appelée lorsque l'utilisateur demande des données du canal canalId. compte spécifie combien d' *octets* ont été demandés. Si la sous-commande n'est pas prise en charge, il n'est pas possible de lire à partir du canal géré par la commande.

La valeur de retour de cette sous-commande est considérée comme les octets de données demandés. Si les données retournées contiennent plus d'octets que demandé, une erreur sera signalée et lancée ultérieurement par la commande qui a effectué la lecture (généralement gets ou read). Cependant, retourner moins d'octets que demandé est acceptable.

Notez que retourner rien (0 octets) est un signal aux couches supérieures que la fin de fichier (EOF) a été atteinte sur le canal. Pour signaler que le canal n'a plus de données pour le moment, mais n'a pas encore atteint la fin de fichier (EOF), il est nécessaire de générer l'erreur "EAGAIN", c'est-à-dire soit

return -code error EAGAIN
ou 
error EAGAIN

Pour des raisons d'extensibilité, toute erreur dont la valeur est un nombre entier négatif amènera les couches supérieures à définir la variable C "errno" à la valeur absolue de ce nombre, signalant une erreur système. Cependant, notez que la correspondance exacte entre ces numéros d'erreur et leurs significations dépend du système d'exploitation.

Par exemple, alors que sous Linux, les deux

return -code error -11
et 
error -11

sont équivalents aux exemples ci-dessus, en utilisant la chaîne plus lisible "EAGAIN", ce n'est pas le cas pour BSD, où le nombre équivalent est -35.

Cependant, la chaîne symbolique est la même sur tous les systèmes et est traduite en interne au bon numéro. Aucune autre valeur d'erreur n'a une telle correspondance avec une chaîne symbolique.

Si la sous-commande génère une autre erreur, la commande qui a causé son invocation (généralement gets ou read) semblera avoir généré cette erreur. Toute exception au-delà d'une error (par ex. break, etc.) est traitée et convertie en erreur.

préfixeCmd write canalId données
Cette sous-commande *facultative* est appelée lorsque l'utilisateur écrit des données dans le canal canalId. L'argument données contient des *octets*, pas des caractères. Tout type de transformation (EOL, encodage) configuré pour le canal a déjà été appliqué à ce stade. Si cette sous-commande n'est pas prise en charge, il n'est pas possible d'écrire dans le canal géré par la commande.

La valeur de retour de la sous-commande est considérée comme le nombre d'octets écrits par le canal. Toute valeur non numérique provoquera une erreur signalée et lancée ultérieurement par la commande qui a effectué l'écriture. Une valeur négative implique que l'écriture a échoué. Retourner une valeur supérieure au nombre d'octets transmis au gestionnaire, ou zéro, est interdit et provoquera une erreur du noyau Tcl.

Pour signaler que le canal ne peut pas accepter de données en écriture pour le moment, il est nécessaire de générer l'erreur "EAGAIN", c'est-à-dire soit

return -code error EAGAIN
ou 
error EAGAIN

Pour des raisons d'extensibilité, toute erreur dont la valeur est un nombre entier négatif amènera les couches supérieures à définir la variable C "errno" à la valeur absolue de ce nombre, signalant une erreur système. Cependant, notez que la correspondance exacte entre ces numéros d'erreur et leurs significations dépend du système d'exploitation.

Par exemple, alors que sous Linux, les deux

return -code error -11
et 
error -11

sont équivalents aux exemples ci-dessus, en utilisant la chaîne plus lisible "EAGAIN", ce n'est pas le cas pour BS

refchan(n) — Tcl

NAME

refchan — Driver for channels exposed to Tcl via the Tcl channel driver API

SYNOPSIS

chan create read
chan create write
chan create readwrite
cmdPrefixinitialize channelId mode
cmdPrefixfinalize channelId
cmdPrefixwatch channelId events
cmdPrefixread channelId count
cmdPrefixwrite channelId data
cmdPrefixseek channelId offset base
cmdPrefixconfigure channelId option value
cmdPrefixcget channelId option
cmdPrefixcgetall channelId
cmdPrefixblocking channelId mode

DESCRIPTION

This manual page describes the Tcl channel driver used for channels created via the C API (Tcl_OpenChannel). Such channels are commonly used to reflect Tcl commands into channels, or to expose C functions as channels.

The driver is invoked implicitly by the Tcl core when channels are created using the chan create command. The syntax for creating such channels is:

chan create accessMode ?args...?

where accessMode is one of read, write, or readwrite, and args are arguments passed to the command that creates the channel. The command that creates the channel must return a Tcl object which is a dictionary of channel driver procedures. The keys of the dictionary are the names of the driver procedures (like initialize, read, etc.) and the values are Tcl commands to be invoked when the driver procedures are called.

The cmdPrefix in the command names above is the command used to invoke the driver procedure in question. This command is generated by the Tcl core and is unique for each channel.

cmdPrefixinitialize channelId mode
This subcommand is called when the channel is created. It is responsible for initializing the channel driver. The channelId argument is the name of the channel. The mode argument is a string indicating the access mode of the channel (e.g., “read”, “write”, “readwrite”). The subcommand should return a string specifying which driver procedures are supported by this channel. Currently supported procedures are: initialize, finalize, watch, read, write, seek, configure, cget, cgetall, blocking.

If the subcommand throws an error, the command which caused its invocation (usually chan create) will appear to have thrown this error. Any exception beyond error (e.g., break, etc.) is treated as and converted to an error.

cmdPrefixfinalize channelId
This subcommand is called when the channel is destroyed. It is responsible for any cleanup actions needed by the channel driver.

The return value of the subcommand is ignored.

If the subcommand throws an error, the command which caused its invocation (usually chan close or chan destroy) will appear to have thrown this error. Any exception beyond error (e.g., break, etc.) is treated as and converted to an error.

cmdPrefixwatch channelId events
This subcommand is called when the channel is registered for event notification. The events argument is a string indicating the type of events to watch for (e.g., “read”, “write”, “exception”). This subcommand is optional. If it is not supported, the channel will not be able to participate in event loops.

The return value of the subcommand is ignored.

If the subcommand throws an error, the command which caused its invocation (usually chan watch) will appear to have thrown this error. Any exception beyond error (e.g., break, etc.) is treated as and converted to an error.

cmdPrefixread channelId count
This subcommand is called when data is read from the channel. The count argument is the maximum number of bytes to read. The subcommand should return the data read from the channel.

If the subcommand throws an error, the command which caused its invocation (usually read or gets) will appear to have thrown this error. Any exception beyond error (e.g., break, etc.) is treated as and converted to an error.

cmdPrefixwrite channelId data
This subcommand is called when data is written to the channel. The data argument is the string to be written. The subcommand should return the number of bytes actually written. Tcl automatically handles retries if the subcommand returns fewer bytes than requested.

The symbolic string however is the same across systems, and internally translated to the correct number. No other error value has such a mapping to a symbolic string.

If the subcommand throws any other error the command which caused its invocation (usually puts) will appear to have thrown this error. Any exception beyond error (e.g., break, etc.) is treated as and converted to an error.

cmdPrefix seek channelId offset base
This optional subcommand is responsible for the handling of chan seek and chan tell requests on the channel channelId. If it is not supported then seeking will not be possible for the channel.

The base argument is the same as the equivalent argument of the builtin chan seek, namely:

start
Seeking is relative to the beginning of the channel.
current
Seeking is relative to the current seek position.
end
Seeking is relative to the end of the channel.

The offset is an integer number specifying the amount of bytes to seek forward or backward. A positive number should seek forward, and a negative number should seek backward. A channel may provide only limited seeking. For example sockets can seek forward, but not backward.

The return value of the subcommand is taken as the (new) location of the channel, counted from the start. This has to be an integer number greater than or equal to zero. If the subcommand throws an error the command which caused its invocation (usually chan seek, or chan tell) will appear to have thrown this error. Any exception beyond error (e.g., break, etc.) is treated as and converted to an error.

The offset/base combination of 0/current signals a chan tell request, i.e., seek nothing relative to the current location, making the new location identical to the current one, which is then returned.

cmdPrefix configure channelId option value
This optional subcommand is for setting the type-specific options of channel channelId. The option argument indicates the option to be written, and the value argument indicates the value to set the option to.

This subcommand will never try to update more than one option at a time; that is behavior implemented in the Tcl channel core.

The return value of the subcommand is ignored.

If the subcommand throws an error the command which performed the (re)configuration or query (usually fconfigure or chan configure) will appear to have thrown this error. Any exception beyond error (e.g., break, etc.) is treated as and converted to an error.

cmdPrefix cget channelId option
This optional subcommand is used when reading a single type-specific option of channel channelId. If this subcommand is supported then the subcommand cgetall must be supported as well.

The subcommand should return the value of the specified option.

If the subcommand throws an error, the command which performed the (re)configuration or query (usually fconfigure or chan configure) will appear to have thrown this error. Any exception beyond error (e.g., break, etc.) is treated as and converted to an error.

cmdPrefix cgetall channelId
This optional subcommand is used for reading all type-specific options of channel channelId. If this subcommand is supported then the subcommand cget has to be supported as well.

The subcommand should return a list of all options and their values. This list must have an even number of elements.

If the subcommand throws an error the command which performed the (re)configuration or query (usually fconfigure or chan configure) will appear to have thrown this error. Any exception beyond error (e.g., break, etc.) is treated as and converted to an error.

cmdPrefix blocking channelId mode
This optional subcommand handles changes to the blocking mode of the channel channelId. The mode is a boolean flag. A true value means that the channel has to be set to blocking, and a false value means that the channel should be non-blocking.

The return value of the subcommand is ignored.

If the subcommand throws an error the command which caused its invocation (usually fconfigure or chan configure) will appear to have thrown this error. Any exception beyond error (e.g., break, etc.) is treated as and converted to an error.

NOTES

Some of the functions supported in channels defined in Tcl's C interface are not available to channels reflected to the Tcl level.

The function Tcl_DriverGetHandleProc is not supported; i.e., reflected channels do not have OS specific handles.

The function Tcl_DriverHandlerProc is not supported. This driver function is relevant only for stacked channels, i.e., transformations. Reflected channels are always base channels, not transformations.

The function Tcl_DriverFlushProc is not supported. This is because the current generic I/O layer of Tcl does not use this function anywhere at all. Therefore support at the Tcl level makes no sense either. This may be altered in the future (through extending the API defined here and changing its version number) should the function be used at some time in the future.

EXAMPLE

This demonstrates how to make a channel that reads from a string.

oo::class create stringchan {
    variable data pos
    constructor {string {encoding {}}} {
        if {$encoding eq ""} {set encoding [encoding system]}
        set data [encoding convertto $encoding $string]
        set pos 0
    }
    method initialize {ch mode} {
        return "initialize finalize watch read seek"
    }
    method finalize {ch} {
        my destroy
    }
    method watch {ch events} {
        # Must be present but we ignore it because we do not
        # post any events
    }
    # Must be present on a readable channel
    method read {ch count} {
        set d [string range $data $pos [expr {$pos+$count-1}]]
        incr pos [string length $d]
        return $d
    }
    # This method is optional, but useful for the example below
    method seek {ch offset base} {
        switch $base {
            start {
                set pos $offset
            }
            current {
                incr pos $offset
            }
            end {
                set pos [string length $data]
                incr pos $offset
            }
        }
        if {$pos < 0} {
            set pos 0
        } elseif {$pos > [string length $data]} {
            set pos [string length $data]
        }
        return $pos
    }
}
# Now we create an instance...
set string "The quick brown fox jumps over the lazy dog.\n"
set ch [chan create read [stringchan new $string]]
puts [gets $ch];   # Prints the whole string
seek $ch -5 end;
puts [read $ch];   # Prints just the last word
