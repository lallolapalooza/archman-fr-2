DESCRIPTION

Les fonctions constituent un système assez extensible pour analyser divers fichiers de configuration au moment de l'exécution d'une application. Le flux de configuration des fichiers est divisé en phases suivantes :

1.
Enregistrement des gestionnaires.
2.
Lecture des fichiers de configuration pour les besoins de l'analyse pré-MIB.
3.
Lecture et analyse des fichiers MIB textuels.
4.
Lecture des fichiers de configuration pour les directives de configuration.
5.
Relecture éventuelle des fichiers de configuration à une date ultérieure.

L'idée est que l'application appelante soit capable d'enregistrer des gestionnaires pour certains tokens spécifiés dans certains fichiers de configuration nommés. La fonction read_configs() peut ensuite être appelée pour rechercher tous les fichiers de configuration pertinents, faire correspondre le premier mot de chaque ligne à la liste des tokens enregistrés et passer le reste de la ligne au gestionnaire enregistré approprié.

ENREGISTREMENT D'UN GESTIONNAIRE

register_config_handler()
Enregistre une routine de gestion de la configuration, qui devrait être appelée pour traiter les directives de configuration commençant par le token spécifié. Par exemple :
register_config_handler("snmp", "exampleToken", example_handler, NULL, "ARG1 [ARG2]");
enregistrerait la fonction example_handler() de manière à ce qu'elle soit appelée chaque fois que le premier mot d'une ligne dans le(s) fichier(s) de configuration snmp.conf correspond à "exampleToken".
L'appel des gestionnaires appropriés pour traiter les directives du fichier de configuration est de la responsabilité de read_configs() (voir ci-dessous).
register_const_config_handler()
Similaire à la fonction register_config_handler(), mais la routine d'analyse est explicitement limitée à ne pas modifier la chaîne en cours d'analyse.
register_prenetsnmp_mib_handler()
Similaire à la fonction register_config_handler(), mais la routine de gestionnaire enregistrée sera appelée *avant* la lecture des MIB textuels. Ceci est généralement utilisé pour les tokens qui affecteront la configuration de l'analyseur MIB, et ne sera normalement utilisé qu'à l'intérieur de la bibliothèque SNMP elle-même.
register_mib_handlers()
Routine d'initialisation pour enregistrer les gestionnaires de configuration internes de la bibliothèque SNMP.
unregister_config_handler()
Supprime le gestionnaire de configuration enregistré pour le filePrefix et le token spécifiés.
unregister_all_config_handlers()
Supprime tous les gestionnaires de configuration enregistrés.

Gestionnaires de tokens

Les fonctions de gestionnaire doivent avoir la signature suivante :

void handler(const char *token, char *line);
ou
void handler(const char *token, const char *line); br (si enregistré via register_const_config_handler)

La fonction sera appelée avec deux arguments, le premier étant le token qui a déclenché l'appel à cette fonction (c'est-à-dire le token utilisé lors de l'enregistrement du gestionnaire), et le second étant le reste de la ligne du fichier de configuration (c'est-à-dire tout ce qui suit l'espace blanc après le token correspondant).

Gestionnaires de libération

Si la fonction de gestionnaire de token alloue dynamiquement des ressources lors du traitement d'une entrée de configuration, celles-ci peuvent devoir être libérées avant de relire les fichiers de configuration. Si le quatrième paramètre (releaser) passé à register_config_handler n'est pas NULL, il spécifie une fonction à appeler avant de relire les fichiers de configuration. Cette fonction doit libérer toutes les ressources allouées par la fonction de gestionnaire de token et réinitialiser sa notion de configuration à sa valeur par défaut. La fonction de gestionnaire de token peut alors être appelée à nouveau en toute sécurité. Aucun argument n'est passé au gestionnaire de libération des ressources.
Notez que cette fonction n'est pas appelée lorsque le gestionnaire est désenregistré individuellement (mais elle est appelée dans le cadre de unregister_all_config_handlers()).

Gestionnaires d'application

register_app_config_handler()
register_app_prenetsnmp_mib_handler()
unregister_app_config_handler()

Ces fonctions sont similaires aux fonctions register_config_handler() et register_prenetsnmp_mib_handler(), mais elles enregistrent des gestionnaires pour les tokens qui doivent être traités directement par l'application, plutôt que par la bibliothèque Net-SNMP. Elles ne nécessitent pas de filePrefix car le système de configuration ne distingue pas les fichiers dans ce contexte.

LECTURE DES FICHIERS DE CONFIGURATION

read_configs()
Lit tous les fichiers de configuration actuellement reconnus par le système Net-SNMP (par exemple, $ENV{NETSNMP_CONFIG}, $HOME/.snmp/snmp.conf, et les fichiers spécifiés dans les MIBs). Pour chaque ligne non vide dans ces fichiers, le premier mot est utilisé comme token et le reste de la ligne est passé à la routine de gestionnaire correspondante pour traitement. Ceci est typiquement appelé après l'initialisation de la bibliothèque.
read_premib_configs()
Similaire à read_configs(), mais ne lit que les fichiers de configuration qui sont marqués comme nécessitant une lecture avant le chargement des MIBs. Ceci est généralement utilisé pour configurer le chargeur MIB lui-même.

AIDE ET ERREURS

read_config_print_usage()
Parcourt tous les gestionnaires enregistrés et imprime leur chaîne d'utilisation (le dernier argument passé à la fonction d'enregistrement) au flux de sortie standard. Le paramètre lead est imprimé avant chaque ligne d'utilisation.
config_pwarn()
Imprime un message d'avertissement formaté au flux d'erreurs standard (stderr). Le message est préfixé par "Warning: ".
config_perror()
Imprime un message d'erreur formaté au flux d'erreurs standard (stderr). Le message est préfixé par "Error: ".

EXEMPLE

Voici un exemple simple de la façon d'enregistrer un gestionnaire de configuration :

#include <net-snmp/net-snmp-config.h>
#include <net-snmp/config_api.h>

static void
my_log_handler(const char *token, char *cptr)
{
    char log_file[1024];
    FILE *log_fp;

    /* Get the log file name from the configuration line */
    snprintf(log_file, sizeof(log_file), "%s/%s",
             snmp_get_configuration_directory(), cptr);

    /* Open the log file */
    log_fp = fopen(log_file, "a");
    if (!log_fp) {
        config_perror("Failed to open log file");
        return;
    }

    /* Do something with the log file pointer, e.g., store it globally */
    /* global_log_fp = log_fp; */

    /* Optionally, register a releaser function to close the file later */
    /* register_config_release_handler("myapp", "logFile", my_log_release); */
}

/* ... later in the code ... */

void init_my_app(void) {
    /* Register the handler for the "logFile" token in the "myapp.conf" file */
    struct config_line *cl = register_config_handler("myapp", "logFile",
                                                     my_log_handler, NULL,
                                                     "logFile PATH");
    if (!cl) {
        fprintf(stderr, "Error registering logFile handler\n");
    }

    /* Now, when read_configs() is called, it will look for myapp.conf */
    /* and if it finds a line like "logFile /var/log/myapp.log", */
    /* it will call my_log_handler with token="logFile" and cptr="/var/log/myapp.log" */
}

DESCRIPTION

These functions are used internally by the Net-SNMP library to parse configuration files. It is intended that MIB modules written for the agent use these functions to allow the agent to have more control over which configuration files are read (typically the snmpd.conf files).

The configuration system supports two phases for processing configuration directives, corresponding to the two function calls read_premib_configs() and read_configs(). The first processes directives that should be handled before the MIB modules are loaded, and the second processes those that should be handled after.

Registering and Unregistering Handlers

A configuration handler is a function that is called when a specific token is encountered in a configuration file. The handler function takes two arguments: the number of tokens on the line (including the token itself), and an array of strings containing the tokens. It should return 0 on success, and non-zero on failure.

register_mib_handlers()
This function is used to register handlers for configuration tokens that are specific to MIB modules. The prefix argument is used to distinguish handlers registered by different MIB modules. A single MIB module should use a unique prefix (e.g., its module name).
unregister_mib_handlers()
This function is used to unregister handlers that were previously registered with register_mib_handlers().
register_prenetsnmp_mib_handler()
This function registers a handler for a configuration token that should be processed before the MIB files are read in. The token is the configuration directive name (e.g., "mibdirs"), usage is a string describing the expected arguments for the token (used for help messages), handler is the function to call when the token is encountered, and prefix is an optional string used to group handlers.
unregister_prenetsnmp_mib_handler()
This function unregisters a handler previously registered with register_prenetsnmp_mib_handler().
register_app_config_handler()
Similar to register_prenetsnmp_mib_handler(), but this function registers a handler for a configuration token that should be processed after the MIB files are read in. It also does not require the file type argument.
unregister_app_config_handler()
These functions are analagous to register_config_handler(), register_prenetsnmp_mib_handler() and unregister_config_handler() but do not require the file type argument (which is filled in by the application). It is intended that MIB modules written for the agent use these functions to allow the agent to have more control over which configuration files are read (typically the snmpd.conf files).

READING CONFIGURATION FILES

read_premib_configs()
read_configs()
These routines process the configuration files found in the configuration search path (see below). For each entry, the handler registered for that configuration token is called.

read_premib_configs() is run before the MIB files are read in, and processes those configuration tokens registered using register_prenetsnmp_mib_handler() (or register_app_prenetsnmp_mib_handler() ). All other entries are ignored.

read_configs() is run after the MIB files have been read in, and processes those configuration tokens registered using register_config_handler() (or register_app_config_handler() ). If it encounters a configuration token for which no handler has been registered (either pre- or post-mib), then it will display a warning message, and continue processing with the next line of the configuration file.

Configuration Search Path

The configuration files to be read are found by searching a list of configuration directories for appropriately named files. In each such directory, the library will look for files named snmp.conf, snmp.local.conf, app.conf, app.local.conf,
(where app is the appication-specific filePrefix used to register configuration handlers). It is not necessary for any or all of these files to be present in each directory. Missing files will be silently skipped.
The idea behind the two different suffixes is that the first file can be shared (via rdist or an NFS mount) across a large number of machines and the second file can be used to configure local settings for one particular machine.

The default list of directories to search is /etc/snmp, followed by /usr/share/snmp, followed by /usr/lib/snmp, followed by $HOME/.snmp. This list can be changed by setting the environmental variable SNMPCONFPATH to be a (colon separated) list of directories to search.

init_snmp()

The normal mode of operation would be to register the application-specific configuration handlers, and then invoke init_snmp(). This would call the routines listed above to register the internal library configuration handlers, process any configuration tokens registered with register_prenetsnmp_mib_handler(), read in the textual MIB files using init_mib(), and finally parse the configuration file tokens registered with register_config_handler().

If the init_snmp() function is used, none of these functions need to be explicitly called by the application.

HELP STRINGS AND ERRORS

The usageLine parameter passed to register_config_handler() and similar calls, is used to display help information when the read_config_print_usage() function is called. This function is used by all of the applications when the -H flag is passed on the command line. It prints a summary of all of the configuration file lines, and the associated files, that the configuration system understands. The usageLine parameter should be a list of arguments expected after the token, and not a lengthy description (which should go into a manual page instead). The lead prefix will be prepended to each line that the function prints to stderr, where it displays its output.

The init_snmp() function should be called before the read_config_print_usage() function is called, so that the library can register its configuration file directives as well for the read_config_print_usage() function to display.

Error Handling Functions

The two functions config_pwarn() and config_perror() both take an error string as an argument and print it to stderr along with the file and line number that caused the error. A call to the second function will also force read_configs() to eventually return with an error code indicating to it's calling function that it should abort the operation of the application.

ENVIRONMENT VARIABLES

SNMPCONFPATH
A colon separated list of directories to search for configuration files in. Default:
/etc/snmp:/usr/share/snmp:/usr/lib/snmp:$HOME/.snmp
