NOM

re2hs - génère des analyseurs lexicaux rapides pour Haskell

SYNOPSIS

re2hs [ OPTIONS ] [ WARNEMENTS ] ENTRÉE

L'entrée peut être un fichier ou - pour l'entrée standard.

INTRODUCTION

re2hs fonctionne comme un préprocesseur. Il lit le fichier d'entrée (qui est généralement un programme en Haskell, mais peut être n'importe quoi) et recherche des blocs de code délimités par des marqueurs de début/fin de forme spéciale. Le texte en dehors de ces blocs est copié tel quel dans le fichier de sortie. Le contenu des blocs est traité par re2hs. Il les traduit en code Haskell et génère le code dans le fichier de sortie à la place du bloc.

Voici un exemple de petit programme qui vérifie si une chaîne donnée contient un nombre décimal :

-- re2hs $INPUT -o $OUTPUT -i
{-# LANGUAGE OverloadedStrings #-}
{-# OPTIONS_GHC -Wno-unused-record-wildcards #-}
import Data.ByteString (ByteString, index)
data State = State {
    _yyinput :: ByteString,
    _yycursor :: Int
}
%{
    re2c:YYFN = ["lexer;Bool", "State{..};State"];
    re2c:yyfill:enable = 0;
    [1-9][0-9]* { True }
    *           { False }
%}
main :: IO ()
main = case lexer State{_yyinput = "1234\0", _yycursor = 0} of
    True -> return ()
    False -> error "lexer failed!"

En sortie, re2hs a remplacé le bloc du milieu par le code généré :

-- Généré par re2hs
{-# LANGUAGE RecordWildCards #-}
-- re2hs $INPUT -o $OUTPUT -i
{-# LANGUAGE OverloadedStrings #-}
{-# OPTIONS_GHC -Wno-unused-record-wildcards #-}
import Data.ByteString (ByteString, index)
data State = State {
    _yyinput :: ByteString,
    _yycursor :: Int
}
yy0 :: State -> Bool
yy0 State{..} =
    let yych = index _yyinput _yycursor in
    let __ = _yycursor + 1 in let _yycursor = __ in
    case yych of
        _c | 0x31 <= _c && _c <= 0x39 ->
            yy2 State{..}
        _c | True ->
            yy1 State{..}
yy1 :: State -> Bool
yy1 State{..} =
    False
yy2 :: State -> Bool
yy2 State{..} =
    let yych = index _yyinput _yycursor in
    case yych of
        _c | 0x30 <= _c && _c <= 0x39 ->
            let __ = _yycursor + 1 in let _yycursor = __ in
            yy2 State{..}
        _c | True ->
            yy3 State{..}
yy3 :: State -> Bool
yy3 State{..} =
    True
lexer :: State -> Bool
lexer State{..} =
    yy0 State{..}
main :: IO ()
main = case lexer State{_yyinput = "1234\0", _yycursor = 0} of
    True -> return ()
    False -> error "lexer failed!"

BASES

Un programme re2hs se compose d'une séquence de blocs entrecoupés de code dans le langage cible. Un bloc peut contenir des définitions, des configurations, des règles, des actions et des directives dans n'importe quel ordre :

nom = expression-régulière ;
Une définition lie nom à expression-régulière. Les noms peuvent contenir des caractères alphanumériques et le trait de soulignement. La section expressions régulières donne un aperçu de la syntaxe de re2hs pour les expressions régulières. Une fois définie, le nom peut être utilisé dans d'autres expressions régulières et dans les règles. La récursion dans les définitions nommées n'est pas autorisée, et chaque nom doit être défini avant d'être utilisé. Un bloc hérite des définitions nommées de la portée globale. Redéfinir un nom existant dans la portée actuelle est une erreur.
configuration = valeur ;
Une configuration permet de modifier le comportement de re2hs et de personnaliser le code généré. Pour une liste complète des configurations supportées par re2hs, voir la section configurations. Selon la configuration, la valeur peut être un mot-clé, un nombre entier non négatif, ou une chaîne d'une seule ligne qui doit être entourée de guillemets doubles ou simples, sauf si elle ne contient que des caractères alphanumériques. Un bloc hérite des configurations de la portée globale et peut les redéfinir ou en ajouter de nouvelles. Les configurations définies à l'intérieur d'un bloc affectent l'ensemble du bloc, même si elles apparaissent à la fin de celui-ci.
expression-régulière code
Une règle lie une expression-régulière à son action sémantique (un bloc de code entre accolades, ou un bloc de code commençant par := et se terminant sur un saut de ligne suivi d'un caractère non blanc). Si l'expression-régulière correspond, le code associé est exécuté. Si plusieurs règles correspondent, la correspondance la plus longue a la priorité. Si plusieurs règles correspondent à la même chaîne, la première d'entre elles a la priorité. Il existe deux règles spéciales : la règle par défaut * et la règle de fin d'entrée $. La règle par défaut doit toujours être définie, elle a la plus basse priorité indépendamment de sa place dans le bloc, et elle correspond à toute unité de code (pas nécessairement un caractère valide, voir la section prise en charge de l'encodage). La règle de fin d'entrée doit être définie si la méthode correspondante pour gérer la fin de l'entrée est utilisée. Avec les conditions de départ, les règles ont une syntaxe plus complexe.
!action code
Une action lie un bloc de code défini par l'utilisateur à un endroit particulier dans la machine à états finis générée (de la même manière que les actions sémantiques lient du code aux états finaux). Voir la section actions pour une liste complète des actions prédéfinies.
!directive ;
Une directive est l'une des instructions prédéfinies spéciales. Chaque directive a un but unique. Voir la section directives pour plus de détails.

Blocs

Les marqueurs de début et de fin de bloc sont soit /*!re2c et */, soit %{ et %} (les deux styles sont supportés). À partir de la version 2.2, les blocs peuvent avoir des noms optionnels qui permettent de les référencer dans d'autres blocs. Il existe différents types de blocs :

/*!re2c[:<nom>] ... */ ou %{[:<nom>] ... %}
Un bloc global contient des définitions, des configurations, des règles et des directives. re2hs compile les expressions régulières associées à chaque règle en un automate fini déterministe, l'encode sous forme de sauts conditionnels dans le langage cible et remplace le bloc par le code généré. Les noms et configurations définis dans un bloc global sont ajoutés à la portée globale et deviennent visibles aux blocs suivants. Au début du programme, la portée globale est initialisée avec les options de la ligne de commande.
/*!local:re2c[:<nom>] ... */ ou %{local[:<nom>] ... %}
Un bloc local est similaire à un bloc global, mais les noms et configurations qu'il contient ont une portée locale (ils n'affectent pas les autres blocs).
/*!rules:re2c[:<nom>] ... */ ou %{rules[:<nom>] ... %}
Un bloc de règles est similaire à un bloc local, mais il ne génère aucun code en soi, ni n'ajoute de définitions à la portée globale -- il est conçu pour être réutilisé dans d'autres blocs. C'est une façon de partager du code (plus de détails dans la section blocs réutilisables). Avant la version 2.2 de re2hs, les blocs de règles nécessitaient l'option -r --reusable.
/*!use:re2c[:<nom>] ... */ ou %{use[:<nom>] ... %}
Un bloc d'utilisation qui référence un bloc de règles défini précédemment. Si le nom est spécifié, re2hs recherche des blocs de règles portant ce nom. Sinon, le bloc de règles le plus récent est utilisé (nommé ou non nommé). Un bloc d'utilisation peut ajouter ses propres définitions, configurations et règles, qui sont ajoutées à celles du bloc de règles référencé. Avant la version 2.2 de re2hs, les blocs d'utilisation nécessitaient l'option -r --reusable.
/*!max:re2c[:<nom1>[:<nom2>...]] ... */ ou %{max[:<nom1>[:<nom2>...]] ... %}
Un bloc qui génère la définition YYMAXFILL. Une liste optionnelle de noms de blocs spécifie quels blocs doivent être inclus lors du calcul de la valeur de YYMAXFILL (si la liste est vide, tous les blocs sont inclus). Par défaut, le code généré est une macro-définition pour C (#define YYMAXFILL <n>), ou une variable globale pour Go (var YYMAXFILL int = <n>). Il peut être personnalisé avec une configuration optionnelle format qui spécifie une chaîne modèle où @@{max} (ou @@ pour faire court) est remplacé par la valeur numérique de YYMAXFILL.
/*!maxnmatch:re2c[:<nom1>[:<nom2>...]] ... */ ou %{m

Blocs

/*!maxnmatch:re2c[:<nom1>[:<nom2>...]] ... %}
Un bloc qui génère la définition YYMAXNMATCH (il nécessite l'option -P --posix-captures). Une liste optionnelle de noms de blocs spécifie quels blocs doivent être inclus lors du calcul de la valeur YYMAXNMATCH (si la liste est vide, tous les blocs sont inclus). Par défaut, le code généré est une définition de macro pour C (#define YYMAXNMATCH <n>), ou une variable globale pour Go (var YYMAXNMATCH int = <n>). Il peut être personnalisé avec une configuration optionnelle format qui spécifie une chaîne de modèle où @@{max} (ou @@ pour faire court) est remplacé par la valeur numérique de YYMAXNMATCH.
/*!stags:re2c[:<nom1>[:<nom2>...]] ... */, /*!mtags:re2c[:<nom1>[:<nom2>...]] ... */ ou %{stags[:<nom1>[:<nom2>...]] ... %}, %{mtags[:<nom1>[:<nom2>...]] ... %{
Blocs qui spécifient un fragment de code modèle qui est développé pour chaque variable s-tag/m-tag générée par re2hs. Une liste optionnelle de noms de blocs spécifie quels blocs doivent être inclus lors du calcul de l'ensemble des variables tag (si la liste est vide, tous les blocs sont inclus). Il existe deux configurations optionnelles : format et separator. La configuration format spécifie une chaîne de modèle où @@{tag} (ou @@ pour faire court) est remplacé par le nom de chaque variable tag. La configuration separator spécifie un fragment de code utilisé pour joindre les fragments format générés pour différentes variables tag.
/*!svars:re2c[:<nom1>[:<nom2>...]] ... */, /*!mvars:re2c[:<nom1>[:<nom2>...]] ... */ ou %{svars[:<nom1>[:<nom2>...]] ... %}, %{mvars[:<nom1>[:<nom2>...]] ... %{
Blocs qui spécifient un fragment de code modèle qui est développé pour chaque s-tag/m-tag qui est soit explicitement mentionné par les règles (avec l'option --tags) soit implicitement généré par re2hs (avec les options --captvars ou --posix-captvars). Une liste optionnelle de noms de blocs spécifie quels blocs doivent être inclus lors du calcul de l'ensemble des tags (si la liste est vide, tous les blocs sont inclus). Il existe deux configurations optionnelles : format et separator. La configuration format spécifie une chaîne de modèle où @@{tag} (ou @@ pour faire court) est remplacé par le nom de chaque tag. La configuration separator spécifie un fragment de code utilisé pour joindre les fragments format générés pour différentes tags.
/*!getstate:re2c[:<nom1>[:<nom2>...]] ... */ ou %{getstate[:<nom1>[:<nom2>...]] ... %}
Un bloc qui génère une répartition conditionnelle de l'état de l'analyseur lexical (il nécessite l'option --storable-state). Une liste optionnelle de noms de blocs spécifie quels blocs doivent être inclus dans la répartition par état. La transition par défaut va à l'étiquette de début du premier bloc de la liste. Si la liste est vide, tous les blocs sont inclus, et la transition par défaut va au premier bloc du fichier qui a une étiquette de début. Ce type de bloc est incompatible avec l'option --loop-switch, car il nécessite des transitions inter-blocs qui ne sont pas prises en charge sans goto ou appels de fonction.
/*!conditions:re2c[:<nom1>[:<nom2>...]] ... */, /*!types:re2c... */ ou %{conditions[:<nom1>[:<nom2>...]] ... %}, %{types... %}
Un bloc qui génère une énumération de conditions (il nécessite l'option --conditions). Une liste optionnelle de noms de blocs spécifie quels blocs doivent être inclus lors du calcul de l'ensemble des conditions (si la liste est vide, tous les blocs sont inclus). Par défaut, le code généré est une énumération YYCONDTYPE. Il peut être personnalisé avec les configurations optionnelles format et separator. La configuration format spécifie une chaîne de modèle où @@{cond} (ou @@ pour faire court) est remplacé par le nom de chaque condition, et @@{num} est remplacé par un indice numérique de cette condition. La configuration separator spécifie un fragment de code utilisé pour joindre les fragments format générés pour différentes conditions.
/*!include:re2c <fichier> */ ou %{include <fichier> %}
Ce bloc permet d'inclure <fichier>, qui doit être un chemin de fichier entre guillemets doubles. Le contenu du fichier est littéralement substitué à la place du bloc, de la même manière que fonctionne #include en C/C++. Ce bloc peut être utilisé conjointement avec l'option --depfile pour générer des dépendances de système de construction sur les fichiers inclus.
/*!header:re2c:on*/ ou %{header:on %}
Ce bloc marque le début du fichier d'en-tête. Tout ce qui suit et jusqu'au bloc header:off suivant est traité par re2hs et écrit dans le fichier d'en-tête spécifié avec l'option -t --type-header.
/*!header:re2c:off*/ ou %{header:off %}
Ce bloc marque la fin du fichier d'en-tête commencé avec le bloc header:on*/.
/*!ignore:re2c ... */ ou %{ignore ... %}
Un bloc dont le contenu est ignoré et supprimé du fichier de sortie.

Configurations

Voici une liste complète des configurations prises en charge par re2hs:

re2c:api, re2c:input
Identique à l'option --api.
re2c:api:sigil
Spécifie le marqueur ("sigil") utilisé pour les espaces réservés aux arguments dans les primitives de l'API. La valeur par défaut est @@. Un espace réservé commence par le sigil suivi du nom de l'argument entre accolades. Par exemple, si le sigil est défini sur $, les espaces réservés auront la forme ${nom}. Les API à argument unique peuvent utiliser une notation abrégée sans le nom entre accolades. Cette option peut être remplacée par des options pour les primitives d'API individuelles, par exemple re2c:YYFILL@len pour YYFILL.
re2c:api:style
Spécifie le style de l'API. Les valeurs possibles sont functions (par défaut pour C) et free-form (par défaut pour Go et Rust). Dans le style functions, les primitives de l'API sont générées avec une liste d'arguments entre parenthèses suivant le nom de la primitive. Les arguments ne sont fournis que pour les paramètres autogénérés (tels que le nombre de caractères passés à YYFILL), mais pas pour le contexte général de l'analyseur lexical, de sorte que les primitives se comportent davantage comme des macros en C/C++ ou des fermetures en Go et Rust. Dans le style free-form, les primitives de l'API n'ont pas de forme fixe : elles doivent être définies comme des chaînes contenant des fragments de code libre avec des variables interpolées sous la forme @@{var} ou @@ (elles correspondent aux arguments du style fonctionnel). Cette configuration peut être remplacée pour les primitives d'API individuelles, voir par exemple la configuration re2c:YYFILL:naked pour YYFILL.
re2c:bit-vectors, re2c:flags:bit-vectors, re2c:flags:b
Identique à l'option --bit-vectors, mais peut être configuré par bloc.
re2c:captures, re2c:leftmost-captures
Identique à l'option --leftmost-captures, mais peut être configuré par bloc.
re2c:captvars, re2c:leftmost-captvars
Identique à l'option --leftmost-captvars, mais peut être configuré par bloc.
re2c:case-insensitive, re2c:flags:case-insensitive
Identique à l'option --case-insensitive, mais peut être configuré par bloc.
re2c:case-inverted, re2c:flags:case-inverted
Identique à l'option --case-inverted, mais peut être configuré par bloc.
re2c:case-ranges, re2c:flags:case-ranges
Identique à l'option --case-ranges, mais peut être configuré par bloc.
re2c:computed-gotos, re2c:flags:computed-gotos, re2c:flags:g
Identique à l'option --computed-gotos, mais peut être configuré par bloc.
re2c:computed-gotos:relative, re2c:cgoto:relative
Identique à l'option --computed-gotos-relative, mais peut être configuré par bloc.
re2c:computed-gotos:threshold, re2c:cgoto:threshold
Si les goto calculés sont utilisés, cette configuration spécifie le seuil de complexité qui déclenche la génération de tables de sauts au lieu de boucles if imbriquées et de bitmaps. La valeur par défaut est 9.
re2c:cond:abort
Si défini sur une valeur entière positive, le cas par défaut dans la répartition conditionnelle générée interrompt l'exécution du programme.
re2c:cond:goto
Spécifie un fragment de code utilisé pour les règles de raccourci autogénérées :=> dans les conditions. La valeur par défaut est goto @@;. L'espace réservé @@ est substitué par le nom de la condition (voir les configurations re2c:api:sigil et re2c:cond:goto@cond).
re2c:cond:goto@cond
Spécifie le sigil utilisé pour la substitution d'arguments dans la définition de re2c:cond:goto. La valeur par défaut est @@. Remplace la configuration plus générique re2c:api:sigil.
re2c:cond:divider
Définit le séparateur pour les blocs de conditions. La valeur par défaut est /* *********************************** */. Les espaces réservés sont substitués par le nom de la condition (voir re2c:api;sigil et re2c:cond:divider@cond).
re2c:cond:divider@cond
Spécifie le sigil utilisé pour la substitution d'arguments dans la définition de re2c:cond:divider. La valeur par défaut est @@. Remplace la configuration plus générique re2c:api:sigil.
re2c:cond:pr
re2c:condprefix
Spécifie le préfixe utilisé pour les étiquettes de condition. Par défaut, c'est yyc_.
re2c:cond:enumprefix, re2c:condenumprefix
Spécifie le préfixe utilisé pour les identificateurs de condition. Par défaut, c'est yyc.
re2c:debug-output, re2c:flags:debug-output, re2c:flags:d
Identique à l'option --debug-output, mais peut être configuré par bloc.
re2c:empty-class, re2c:flags:empty-class
Identique à l'option --empty-class, mais peut être configuré par bloc.
re2c:encoding:ebcdic, re2c:flags:ecb, re2c:flags:e
Identique à l'option --ebcdic, mais peut être configuré par bloc.
re2c:encoding:ucs2, re2c:flags:wide-chars, re2c:flags:w
Identique à l'option --ucs2, mais peut être configuré par bloc.
re2c:encoding:utf8, re2c:flags:utf-8, re2c:flags:8
Identique à l'option --utf8, mais peut être configuré par bloc.
re2c:encoding:utf16, re2c:flags:utf-16, re2c:flags:x
Identique à l'option --utf16, mais peut être configuré par bloc.
re2c:encoding:utf32, re2c:flags:unicode, re2c:flags:u
Identique à l'option --utf32, mais peut être configuré par bloc.
re2c:encoding-policy, re2c:flags:encoding-policy
Identique à l'option --encoding-policy, mais peut être configuré par bloc.
re2c:eof
Spécifie le symbole sentinelle utilisé avec la règle de fin de fichier $. La valeur par défaut est -1 (la règle $ n'est pas utilisée). D'autres valeurs possibles incluent toutes les unités de code valides. Seuls les nombres décimaux sont reconnus.
re2c:header, re2c:flags:type-header, re2c:flags:t
Spécifie le nom du fichier d'en-tête généré par rapport au répertoire du fichier de sortie. Identique à l'option --header, sauf que le chemin du fichier est relatif.
re2c:indent:string
Spécifie la chaîne utilisée pour l'indentation. Par défaut, c'est un seul caractère de tabulation "\t". La chaîne d'indentation ne doit contenir que des espaces blancs. Pour désactiver complètement l'indentation, définissez cette configuration sur une chaîne vide.
re2c:indent:top
Spécifie la quantité minimale d'indentation à utiliser. La valeur par défaut est zéro. La valeur doit être un nombre entier non négatif.
re2c:invert-captures
Identique à l'option --invert-captures, mais peut être configuré par bloc.
re2c:label:prefix, re2c:labelprefix
Spécifie le préfixe utilisé pour les étiquettes d'état DFA. Par défaut, c'est yy.
re2c:label:start, re2c:startlabel
Contrôle la génération d'une étiquette de début de bloc. La valeur par défaut est zéro, ce qui signifie que l'étiquette de début est générée uniquement si elle est utilisée. Une valeur entière supérieure à zéro force la génération de l'étiquette de début même si elle n'est pas utilisée par l'analyseur lexical. Une valeur de chaîne force également la génération de l'étiquette de début et définit le nom de l'étiquette à la chaîne spécifiée. Cette configuration ne s'applique qu'au bloc actuel (elle est réinitialisée à la valeur par défaut pour le bloc suivant).
re2c:label:yyFillLabel
Spécifie le préfixe des étiquettes YYFILL utilisées avec re2c:eof et en mode état stockable.
re2c:label:yyloop
Spécifie le nom de l'étiquette marquant le début de la boucle de l'analyseur lexical avec l'option --loop-switch. Par défaut, c'est yyloop.
re2c:label:yyNext
Spécifie le nom de l'étiquette optionnelle qui suit le commutateur YYGETSTATE en mode état stockable (activé avec re2c:state:nextlabel). Par défaut, c'est yyNext.
re2c:lookahead, re2c:flags:lookahead
Obsolète (voir l'option obsolète --no-lookahead).
re2c:monadic
Si défini sur une valeur non nulle, l'analyseur lexical généré utilisera la notation monadique (cette configuration est spécifique à Haskell).
re2c:nested-ifs, re2c:flags:nested-ifs, re2c:flags:s
Identique à l'option --nested-ifs, mais peut être configuré par bloc.
re2c:posix-captures, re2c:flags:posix-captures, re2c:flags:P
Identique à l'option --posix-captures, mais peut être configuré par bloc.
re2c:posix-captvars
Identique à l'option --posix-captvars, mais peut être configuré par bloc.
re2c:tags, re2c:flags:tags, re2c:flags:T
Identique à l'option --tags, mais peut être configuré par bloc.
re2c:tags:expression
Spécifie l'expression utilisée pour les variables de balise. Par défaut, re2hs génère des expressions de la forme yyt<N>. Cela peut être incommode, par exemple si les variables de balise sont définies comme des champs dans une structure. Toutes les occurrences de @@{tag} ou @@ sont remplacées par le nom de balise réel. Par exemple, re2c:tags:expression = "s.@@"; génère des expressions de la forme s.yyt<N> dans le code généré. Voir également la configuration re2c:api:sigil.
re2c:tags:negative
Spécifie l'expression constante utilisée pour la valeur négative de la balise (typiquement ce serait -1 si les balises sont des décalages entiers dans la chaîne d'entrée, ou un pointeur nul si ce sont des pointeurs).
re2c:tags:prefix
Spécifie le préfixe des noms de variables de balise. Par défaut, c'est yyt.
re2c:sentinel
Spécifie le symbole sentinelle utilisé pour les vérifications de fin de fichier (lorsque les vérifications de limites sont désactivées avec re2c:yyfill:enable = 0; et que re2c:eof n'est pas défini). Cette configuration n'affecte pas la génération de code : son objectif est de vérifier que le sentinelle n'est pas autorisé au milieu d'une règle, et de s'assurer que l'analyseur lexical ne lira pas au-delà de la fin du tampon. La valeur par défaut est -1` (dans ce cas, re2hs suppose que le sentinelle est zéro, ce qui est le cas le plus courant). Seuls les nombres décimaux sont reconnus.
re2c:state:abort
Si défini sur une valeur entière positive, le cas par défaut dans la répartition d'état générée interrompt l'exécution du programme, et un cas -1 explicite contient une transition vers le début du bloc.
re2c:state:nextlabel
Contrôle si le commutateur YYGETSTATE est suivi d'une étiquette yyNext (la valeur par défaut est zéro, ce qui correspond à aucune étiquette). Alternativement, on peut utiliser re2c:label:start pour générer une étiquette de début spécifique, ou un bloc getstate explicite pour générer le commutateur YYGETSTATE séparément du bloc de l'analyseur lexical.
re2c:unsafe, re2c:flags:unsafe
Identique à l'option --no-unsafe, mais peut être configuré par bloc. Si défini sur zéro, il supprime la génération de wrappers unsafe autour de YYPEEK. Par défaut, c'est non nul (les wrappers sont générés). Cette configuration est spécifique à Rust.
re2c:YYBACKUP, re2c:define:YYBACKUP
Définit la primitive d'API générique YYBACKUP.

Expressions régulières

re2hs utilise la syntaxe suivante pour les expressions régulières :

"foo"
Littéral de chaîne sensible à la casse.
'foo'
Littéral de chaîne insensible à la casse.
[a-xyz], [^a-xyz]
Classe de caractères (potentiellement niée).
.
N'importe quel caractère sauf une nouvelle ligne.
R \ S
Différence des classes de caractères R et S.
R*
Zéro occurrence ou plus de R.
R+
Une occurrence ou plus de R.
R?
Occurrence optionnelle de R.
R{n}
Répétition de R exactement n fois.
R{n,}
Répétition de R au moins n fois.
R{n,m}
Répétition de R de n à m fois.
(R)
Juste R ; les parenthèses sont utilisées pour outrepasser la précédence. Si l'extraction de sous-correspondance est activée, (R) est un groupe de capture ou un groupe sans capture selon l'option --invert-captures.
(!R)
Si l'extraction de sous-correspondance est activée, (!R) est un groupe sans capture ou un groupe de capture selon l'option --invert-captures.
R S
Concaténation : R suivi de S.
R | S
Alternative : R ou S.
R / S
Lookahead : R suivi de S, mais S n'est pas consommé.
name
Expression régulière définie comme name (ou littéral de chaîne "name" en mode compatibilité Flex).
{name}
Expression régulière définie comme name en mode compatibilité Flex.
@stag
Un s-tag : sauvegarde la dernière position d'entrée à laquelle @stag correspond dans une variable nommée stag.
#mtag
Un m-tag : sauvegarde toutes les positions d'entrée auxquelles #mtag correspond dans une variable nommée mtag.

Les classes de caractères et les littéraux de chaînes peuvent contenir les séquences d'échappement suivantes : \a, \b, \f, \n, \r, \t, \v, \\, échappements octaux \ooo et échappements hexadécimaux \xhh, \uhhhh et \Uhhhhhhhh.

Actions

Voici une liste des actions prédéfinies prises en charge par re2hs :

!entry code
L'action d'entrée lie un bloc de code défini par l'utilisateur à l'état de départ de la machine à états finis actuelle. Si des conditions de départ sont utilisées, l'action d'entrée peut être définie individuellement pour chaque condition. Cette action peut être utilisée pour effectuer une initialisation, par exemple pour sauvegarder la position de départ d'un lexème.
!pre_rule code
L'action pré-règle ajoute un bloc de code défini par l'utilisateur au début des actions sémantiques de toutes les règles du bloc actuel (ou condition, si des conditions de départ sont utilisées). Cette action peut être utilisée pour factoriser la partie commune de toutes les actions sémantiques (par exemple, la sauvegarde de la position de fin d'un lexème).
!post_rule code
L'action post-règle ajoute un bloc de code défini par l'utilisateur à la fin des actions sémantiques de toutes les règles du bloc actuel (ou condition, si des conditions de départ sont utilisées). Cette action peut être utilisée pour émettre des instructions de piège qui protègent contre les flux de contrôle involontaires.

Directives

Voici une liste complète des directives prises en charge par re2hs :

!use:name ;
Une directive d'utilisation intra-bloc qui fusionne un bloc de règles précédemment défini avec le nom spécifié dans le bloc actuel. Les définitions nommées, les configurations et les règles du bloc référencé sont ajoutées aux règles actuelles. Les conflits entre les règles et les configurations qui se chevauchent sont résolus de la manière habituelle : la première règle a la priorité, et la dernière configuration remplace les précédentes. Une exception concerne les règles spéciales *, $ et <!> pour lesquelles une définition locale au bloc a toujours la priorité. Une directive d'utilisation peut être placée n'importe où à l'intérieur d'un bloc, et plusieurs directives d'utilisation sont autorisées.
!include file ;
Cette directive est identique au bloc include : elle insère le contenu du fichier verbatim à la place de la directive.

Interface du programme

Le code généré interagit avec le programme externe à l'aide de primitives, collectivement appelées API. Les primitives qui doivent être définies pour un programme particulier dépendent de plusieurs facteurs, notamment la complexité des expressions régulières, la représentation de l'entrée, la mise en tampon et l'utilisation de diverses fonctionnalités. Toutes les primitives nécessaires doivent être définies par l'utilisateur sous forme de macros, de fonctions, de variables ou de toute autre forme appropriée qui rend le code généré syntaxiquement et sémantiquement correct. re2hs ne vérifie pas (et ne peut pas vérifier) les définitions, donc si quelque chose manque ou est mal défini, le programme généré peut avoir des erreurs de compilation ou d'exécution. Ce manuel fournit des exemples de définitions d'API dans les cas les plus courants.

re2hs a deux saveurs d'API qui définissent l'ensemble de base des primitives utilisées par un programme :

API d'enregistrement
L'API d'enregistrement est l'API par défaut pour le backend Haskell. Cette API se compose d'une liaison yyrecord (le nom peut être remplacé par re2c:yyrecord) qui doit être définie comme un enregistrement avec les champs _yyinput, _yycursor, _yymarker, _yyctxmarker, _yylimit. Seuls les champs utilisés par le code généré doivent être définis, et leurs noms peuvent être configurés.
API générique
C'est l'API la plus flexible. Elle est activée avec l'option --api generic ou la configuration re2c:api = generic. Elle contient des primitives pour les opérations génériques : YYPEEK, YYSKIP, YYBACKUP, YYBACKUPCTX, YYSTAGP, YYSTAGN, YYMTAGP, YYMTAGN, YYRESTORE, YYRESTORECTX, YYRESTORETAG, YYCOPYSTAG, YYCOPYMTAG, YYSHIFT, YYSHIFTSTAG, YYSHIFTMTAG, YYLESSTHAN.

Voici une liste complète des primitives d'API qui peuvent être utilisées par le code généré pour interagir avec le programme externe.

YYCTYPE
Le type des caractères d'entrée (unités de code). Pour les encodages ASCII, EBCDIC et UTF-8, il doit s'agir d'un entier non signé sur 1 octet. Pour UTF-16 ou UCS-2, il doit s'agir d'un entier non signé sur 2 octets. Pour UTF-32, il doit s'agir d'un entier non signé sur 4 octets.
YYCURSOR
Une valeur l-value qui stocke la position actuelle de l'entrée (un pointeur ou un décalage entier dans YYINPUT). Initialement, YYCURSOR doit pointer vers le premier caractère d'entrée, et plus tard, il est avancé par le code généré. Lorsqu'une règle correspond, la position de YYCURSOR est celle qui suit le dernier caractère correspondant.
YYLIMIT
Une valeur r-value qui stocke la fin de la position d'entrée (un pointeur ou un décalage entier dans YYINPUT). Initialement, YYLIMIT doit pointer vers la position après le dernier caractère d'entrée disponible. Il n'est pas modifié par le code généré. Le lexer compare YYCURSOR à YYLIMIT pour déterminer s'il reste suffisamment de caractères d'entrée.
YYMARKER
Une valeur l-value qui stocke la position de la dernière règle correspondante (un pointeur ou un décalage entier dans YYINPUT). Elle est utilisée pour restaurer la position de YYCURSOR si la correspondance la plus longue échoue et que le lexer doit revenir en arrière. Aucune initialisation n'est nécessaire.
YYCTXMARKER
Une valeur l-value qui stocke la position du contexte de fin (un pointeur ou un décalage entier dans YYINPUT). Aucune initialisation n'est nécessaire. YYCTXMARKER n'est nécessaire que si l'opérateur de lookahead / est utilisé.
YYFILL
Une primitive d'API générique avec une variable len. YYFILL doit fournir au moins len caractères d'entrée supplémentaires ou échouer. Si re2c:eof est utilisé, alors len est toujours 1 et YYFILL doit toujours retourner à la fonction appelante ; une valeur de retour de zéro indique le succès. Si re2c:eof n'est pas utilisé, alors la valeur de retour de YYFILL est ignorée et il ne doit pas retourner en cas d'échec. La valeur maximale de len est YYMAXFILL.
YYFN
Une primitive qui définit le prototype de fonction dans le modèle de code --recursive-functions. Sa valeur doit être un tableau d'une ou plusieurs chaînes, où chaque chaîne contient deux ou trois composantes séparées par la chaîne spécifiée dans la configuration re2c:fn:sep (généralement un point-virgule). Le premier élément du tableau définit le nom de la fonction et le type de retour (vide pour une fonction void). Les éléments suivants définissent les arguments de la fonction : d'abord, l'expression de l'argument utilisée dans le corps de la fonction (généralement juste un nom) ; ensuite, le type de l'argument ; enfin, un paramètre formel optionnel (qui par défaut est la première composante - généralement, l'argument et le paramètre sont le même identifiant).
YYINPUT
Une valeur r-value qui
stores la séquence de caractères d'entrée actuelle (chaîne, tampon, etc.).
YYMAXFILL
Une constante entière égale à la valeur maximale de l'argument de YYFILL. Elle peut être générée avec un bloc max.
YYLESSTHAN
Une primitive d'API générique avec une variable len. Elle doit être définie comme une valeur r de type booléen qui est égale à true si et seulement si il reste moins de len caractères d'entrée.
YYPEEK
Une primitive d'API générique sans variables. Elle doit être définie comme une valeur r de type YYCTYPE qui est égale au caractère à la position d'entrée actuelle.
YYSKIP
Une primitive d'API générique qui doit avancer la position d'entrée actuelle d'une unité de code.
YYBACKUP
Une primitive d'API générique qui doit sauvegarder la position d'entrée actuelle (pour être restaurée plus tard avec YYRESTORE).
YYRESTORE
Une primitive d'API générique qui doit restaurer la position d'entrée actuelle à la valeur sauvegardée par YYBACKUP.
YYBACKUPCTX
Une primitive d'API générique qui doit sauvegarder la position d'entrée actuelle comme la position du contexte suffixe (pour être restaurée plus tard avec YYRESTORECTX).
YYRESTORECTX
Une primitive d'API générique qui doit restaurer la position du contexte suffixe sauvegardée avec YYBACKUPCTX.
YYRESTORETAG
Une primitive d'API générique avec une variable tag qui doit restaurer la position du contexte suffixe à la valeur de tag.
YYSTAGP
Une primitive d'API générique avec une variable tag, où tag peut être un pointeur ou un décalage dans YYINPUT (voir la section d'extraction des sous-correspondances pour plus de détails). YYSTAGP doit définir tag à la position d'entrée actuelle.
YYSTAGN
Une primitive d'API générique avec une variable tag, où tag peut être un pointeur ou un décalage dans YYINPUT (voir la section d'extraction des sous-correspondances pour plus de détails). YYSTAGN doit définir tag à une valeur qui représente une position d'entrée inexistante.
YYMTAGP
Une primitive d'API générique avec une variable tag. YYMTAGP doit ajouter la position actuelle à l'historique des sous-correspondances de tag (voir la section d'extraction des sous-correspondances pour plus de détails.)
YYMTAGN
Une primitive d'API générique avec une variable tag. YYMTAGN doit ajouter une valeur qui représente une position d'entrée inexistante à l'historique des sous-correspondances de tag (voir la section d'extraction des sous-correspondances pour plus de détails.)
YYSHIFT
Une primitive d'API générique avec une variable shift qui doit décaler la position d'entrée actuelle de shift caractères (la valeur de décalage peut être négative).
YYCOPYSTAG
Une primitive d'API générique avec deux variables, lhs et rhs qui doit copier la variable s-tag de droite rhs à la variable s-tag de gauche lhs. Pour la plupart des langages, cette primitive a une définition par défaut qui assigne lhs à rhs.
YYCOPYMTAG
Une primitive d'API générique avec deux variables, lhs et rhs qui doit copier la variable m-tag de droite rhs à la variable m-tag de gauche lhs. Pour la plupart des langages, cette primitive a une définition par défaut qui assigne lhs à rhs.
YYSHIFTSTAG
Une primitive d'API générique avec deux variables, tag et shift qui doit décaler tag de shift unités de code (la valeur de décalage peut être négative).
YYSHIFTMTAG
Une primitive d'API générique avec deux variables, tag et shift qui doit décaler la dernière valeur de l'historique de tag de shift unités de code (la valeur de décalage peut être négative).
YYMAXNMATCH
Une constante entière égale au nombre maximal de groupes de capture POSIX dans une règle. Elle est générée avec un bloc maxnmatch.
YYCONDTYPE
Le type de l'énumération de condition. Il peut être généré soit avec le bloc conditions, soit avec l'option --header.
YYGETACCEPT
Une primitive avec une variable var qui stocke le sélecteur numérique de la règle acceptée. Pour la plupart des langages, cette primitive a une définition par défaut qui lit depuis var.
YYSETACCEPT
Une primitive avec deux variables : var (une l-value qui stocke le sélecteur numérique de la règle acceptée) et val (la valeur du sélecteur). Pour la plupart des langages, cette primitive a une définition par défaut qui assigne var à val.
YYGETCOND
Une valeur r de type YYCONDTYPE qui est égale à l'identifiant de la condition actuelle.
YYSETCOND
Une primitive avec une variable cond qui doit définir l'identifiant de la condition actuelle à cond.
YYGETSTATE
Une valeur r de type entier qui est égale à l'état actuel du lexer. Elle doit être initialisée à -1.
YYSETSTATE
Une primitive avec une variable state qui doit définir l'état actuel du lexer à state.
YYDEBUG
Cette primitive est générée uniquement avec l'option -d, --debug-output. Son but est d'ajouter des journaux au code généré (la définition typique de YYDEBUG est une instruction d'impression). Les instructions YYDEBUG sont générées dans chaque état et ont deux variables : state (soit un index d'état DFA, soit -1) et symbol (le symbole d'entrée actuel).
yyaccept
Une l-value de type entier non signé qui stocke le numéro de la dernière règle correspondante. La définition par l'utilisateur n'est nécessaire qu'avec l'option --storable-state.
yybm
Une table contenant des bitmaps compressées pour jusqu'à 8 transitions (utilisée avec l'option --bitmaps). La table contient 256 éléments et est indexée par des unités de code sur 1 octet. Chaque élément de 8 bits combine des valeurs booléennes pour jusqu'à 8 transitions. Le k-ième bit du n-ième élément est vrai si et seulement si la n-ième unité de code est dans la plage de la k-ième transition. L'idée de cette bitmap est de remplacer de nombreuses branches if ou cas switch par une seule vérification d'un seul bit dans la table.
yych
Une l-value de type YYCTYPE qui stocke le caractère d'entrée actuel. La définition par l'utilisateur n'est nécessaire qu'avec les options -f --storable-state.
yyctable
Table de sauts générée pour la dispersion initiale des conditions (activée avec la combinaison des options --conditions et --computed-gotos).
yyfill
Une l-value qui stocke le résultat de l'appel à YYFILL (cela peut être nécessaire pour les langages purement fonctionnels, où YYFILL est une fonction monadique avec une valeur de retour complexe).
yynmatch
Une l-value de type entier non signé qui stocke le nombre de groupes de capture POSIX dans la règle correspondante. Utilisée uniquement avec l'option -P --posix-captures.
yypmatch
Un tableau de l-values qui sont utilisées pour contenir les valeurs de balises correspondant aux parenthèses de capture dans la règle correspondante. La longueur du tableau doit être d'au moins yynmatch * 2 (généralement YYMAXNMATCH * 2 est un bon choix). Utilisé uniquement avec l'option -P --posix-captures.
yystable
Obsolète.
yystate
Une l-value utilisée avec l'option --loop-switch pour stocker l'état DFA actuel.
yytarget
Table de sauts qui contient les cibles de sauts (adresses d'étiquettes) pour toutes les transitions d'un état. Cette table est locale à chaque état. La génération des tables yytarget est activée avec l'option --computed-gotos.

Options

Certaines options ont des configurations correspondantes, tandis que d'autres sont globales et ne peuvent pas être modifiées après que re2c commence à lire le fichier d'entrée. Les options de débogage nécessitent généralement la construction de re2c dans une configuration de débogage. Les options internes sont utiles pour expérimenter avec les algorithmes utilisés dans re2c.

-? --help -h
Afficher le message d'aide.
--api <simple | record | generic>
Spécifier l'API utilisée par le code généré pour l'interface avec le code défini par l'utilisateur. L'option simple doit être utilisée dans des cas simples lorsqu'il n'y a pas besoin de rechargement de tampon et de stockage de l'état du lexer. L'option record doit être utilisée lorsque l'état du lexer doit être stocké dans un enregistrement (struct, classe, etc.). L'option generic doit être utilisée dans des cas complexes lorsque les deux autres API ne sont pas suffisamment flexibles.

Optimiser les sauts conditionnels à l'aide de masques de bits. Cette option implique
--nested-ifs.

Active l'extraction des sous-correspondances avec des groupes de capture gourmands de gauche à droite. Le résultat est collecté dans les variables yytl<k>, yytr<k> pour le k-ième groupe de capture.

Traite les chaînes entre guillemets simples et doubles comme insensibles à la casse.

Inverse le sens des chaînes entre guillemets simples et doubles : traite les chaînes entre guillemets simples comme sensibles à la casse et les chaînes entre guillemets doubles comme insensibles à la casse.

Réduit les cas consécutifs dans les instructions switch en une plage de la forme low ... high. Cette syntaxe est une extension du langage C/C++ qui est prise en charge par des compilateurs tels que GCC, Clang et Tcc. L'avantage principal par rapport à l'utilisation de cas individuels est un code généré plus petit et un temps de génération plus rapide, bien que pour certains compilateurs comme Tcc, cela entraîne également une taille binaire plus petite.

Cette option implique --bit-vectors.

Similaire à --computed-gotos mais génère des décalages relatifs pour les tables de sauts à la place (ce qui doit être pris en charge par le compilateur). Cette option implique --computed-gotos.
--conditions --start-conditions -c
Active le support des "conditions" de type Flex : plusieurs analyseurs lexicals interconnectés dans un seul bloc. Ceci est une alternative à la spécification manuelle de différents blocs re2hs connectés avec goto ou des appels de fonction.

Écrit les informations de dépendance dans FILE sous la forme d'une règle Makefile <output-file> : <input-file> [include-file ...]. Ceci permet de suivre les dépendances de construction en présence de blocs/directives include, de sorte que la mise à jour des fichiers d'inclusion déclenche la régénération du fichier de sortie. Cette option dépend de l'option --output.
--ebcdic --ecb -e
Génère un analyseur lexical qui lit l'entrée en encodage EBCDIC. re2hs suppose que la plage de caractères est 0 -- 0xFF et que la taille des caractères est de 1 octet.
--empty-class <match-empty | match-none | error>
Définit la manière dont re2hs traite les classes de caractères vides. Avec match-empty (par défaut), une classe vide correspond à une entrée vide (ce qui est illogique, mais rétrocompatible). Avec match-none, une classe vide échoue toujours à correspondre. Avec error, une classe vide génère une erreur de compilation.
--encoding-policy <fail | substitute | ignore>
Définit la manière dont re2hs traite les surrogates Unicode. Avec fail, re2hs s'arrête avec une erreur lorsqu'un surrogate est rencontré. Avec substitute, re2hs remplace silencieusement les surrogates par le point de code d'erreur 0xFFFD. Avec ignore (par défaut), re2hs traite les surrogates comme des points de code normaux. La norme Unicode stipule que les surrogates autonomes sont invalides, mais les bibliothèques et programmes du monde réel se comportent différemment.
--flex-syntax -F
Support partiel de la syntaxe Flex : dans ce mode, les définitions nommées n'ont pas besoin de signe égal ni de point-virgule final, et lorsqu'elles sont utilisées, elles doivent être entourées d'accolades. Les noms sans accolades sont traités comme des chaînes entre guillemets doubles.
--goto-label
Utilise le modèle de code "goto/label" : encode le DFA sous forme de blocs de code étiquetés connectés par des transitions goto entre les blocs. Ceci n'est pris en charge que pour les langages qui ont une instruction goto.
--header --type-header -t HEADER
Génère un fichier HEADER. Le contenu du fichier peut être spécifié en utilisant les blocs spéciaux header:on et header:off. S'il y a des conditions, l'en-tête généré aura un énumérateur de conditions automatiquement ajouté (sauf s'il y a un bloc conditions explicite).
-I PATH
Ajoute PATH à la liste des emplacements utilisés lors de la recherche de fichiers d'inclusion. Cette option est utile en combinaison avec le bloc ou la directive include. re2hs recherche FILE dans le répertoire du fichier parent et dans les emplacements d'inclusion spécifiés avec l'option -I.
--input <default | custom>
Alias obsolète pour --api. L'option default correspond à simple (c'est en fait le défaut pour la plupart des backends, mais pas pour tous). L'option custom correspond à generic.
--input-encoding <ascii | utf8>
Spécifie la manière dont re2hs analyse les expressions régulières. Avec ascii (par défaut), re2hs traite l'entrée comme encodée en ASCII : toute séquence d'unités de code est une séquence de caractères autonomes d'un octet. Avec utf8, re2hs traite l'entrée comme encodée en UTF8 et reconnaît les caractères multibytes.
--invert-captures
Inverse le sens des groupes de capture et des groupes non-capture. Par défaut, (...) capture et (! ...) ne capture pas. Avec cette option, (! ...) capture et (...) ne capture pas.
--lang <none | c | d | go | haskell | java | js | ocaml | python | rust | swift | v | zig>
Spécifie le langage cible. Les langages pris en charge sont C, D, Go, Haskell, Java, JS, OCaml, Python, Rust, Swift, V, Zig (d'autres langages peuvent être ajoutés via des fichiers de syntaxe définis par l'utilisateur, voir l'option --syntax). --location-format <gnu | msvc>
Spécifie le format de localisation dans les messages. Avec gnu, les localisations sont imprimées comme 'filename:line:column: ...'. Avec msvc, les localisations sont imprimées comme 'filename(line,column) ...'. Le défaut est gnu.
--loop-switch
Utilise le modèle de code "loop/switch" : encode le DFA sous forme de boucle sur une instruction switch, où les états individuels sont des cas de switch. L'état est stocké dans une variable yystate. Les transitions entre états mettent à jour yystate vers l'étiquette de cas de l'état de destination et continuent l'exécution vers la tête de la boucle.
--nested-ifs -s
Utilise des instructions if imbriquées au lieu d'instructions switch dans les sauts conditionnels. Cela produit généralement un code plus efficace avec les compilateurs non optimisants.
--no-debug-info -i

--no-generation-date

--no-version
Supprime la sortie de la version dans le fichier généré.
--no-unsafe

--output -o OUTPUT
Spécifie le fichier OUTPUT.
--posix-captures, -P

--dfa-minimization <moore | table>
Option interne : algorithme de minimisation du DFA utilisé par re2hs. L'option moore est l'algorithme de Moore (c'est le comportement par défaut). L'option table est l'algorithme de « remplissage de table ». Les deux algorithmes devraient produire le même DFA jusqu'au re-labellage des états ; le remplissage de table est plus simple et beaucoup plus lent, et sert d'implémentation de référence.
--eager-skip
Option interne : fait avancer le lexer généré de manière anticipée sur la position d'entrée -- immédiatement après la lecture du symbole d'entrée. Cela modifie le comportement par défaut où la position d'entrée est avancée de manière différée -- après la transition vers le nouvel état.
--no-lookahead
Option interne, obsolète. Elle permettait d'activer l'algorithme TDFA(0). Contrairement à TDFA(1), l'algorithme TDFA(0) n'utilise pas d'anticipation d'un symbole. Il applique des opérations de registre aux transitions entrantes plutôt qu'aux transitions sortantes. Des benchmarks ont montré que l'algorithme TDFA(0) est moins performant que TDFA(1).
--no-optimize-tags
Option interne : supprime l'optimisation des variables de balise (utile pour le débogage).
--posix-closure <gor1 | gtop>
Option interne : spécifie l'algorithme de plus court chemin utilisé pour la construction de la fermeture epsilon avec des sémantiques de désambiguïsation POSIX : gor1 (le défaut) représente l'algorithme de Goldberg-Radzik, et gtop représente l'algorithme « d'ordre topologique global ».
--posix-prectable <complex | naive>
Option interne : spécifie l'algorithme utilisé pour calculer la table de précédence POSIX. L'algorithme complex calcule la table de précédence en un seul parcours de l'arbre d'historique des balises et a une complexité quadratique par rapport au nombre d'états TNFA ; c'est le comportement par défaut. L'algorithme naive a une complexité cubique dans le pire des cas par rapport au nombre d'états TNFA, mais il est beaucoup plus simple que complex et peut être légèrement plus rapide dans les cas non pathologiques.
--stadfa
Option interne, obsolète. Elle permettait d'activer l'algorithme staDFA, qui diffère de TDFA en ce que les opérations de registre sont placées dans les états plutôt que sur les transitions. Des benchmarks ont montré que l'algorithme staDFA est moins performant que TDFA.
--fixed-tags <none | toplevel | all>
Option interne : spécifie si l'optimisation des balises fixes doit être appliquée à toutes les balises (all), à aucune d'entre elles (none), ou seulement à celles dans la concaténation de premier niveau (toplevel). Le comportement par défaut est all. Les balises « fixes » sont celles qui sont situées à une distance fixe d'une autre balise (appelée « base »). Dans de tels cas, seule la balise de base doit être suivie, et la valeur de la balise fixe peut être calculée comme la valeur de la balise de base plus un décalage statique. Pour les balises qui sont sous alternative ou répétition, il est également nécessaire de vérifier si la balise de base a une valeur de non-correspondance (auquel cas la balise fixe devrait également être définie sur non-correspondance, ignorant le décalage). Pour les balises dans une concaténation de premier niveau, la vérification n'est pas nécessaire, car elles correspondent toujours.

Avertissements

Les avertissements peuvent être activés, désactivés individuellement et transformés en erreur.

-W
Active tous les avertissements.
-Werror
Transforme les avertissements en erreurs. Notez que cette option seule n'active aucun avertissement ; elle n'affecte que les avertissements qui ont été activés jusqu'à présent ou qui seront activés plus tard.
-W<avertissement>
Active l'avertissement.
-Wno-<avertissement>
Désactive l'avertissement.
-Werror-<avertissement>
Active l'avertissement et le traite comme une erreur (cela implique -W<avertissement>).
-Wno-error-<avertissement>
Ne traite pas cet avertissement particulier comme une erreur. Cela ne désactive pas l'avertissement lui-même.
-Wcondition-order
Avertit si le programme généré fait des suppositions implicites sur la numérotation des conditions. Il faut utiliser soit l'option --header, soit le bloc conditions pour générer un mappage des noms de conditions aux numéros, puis utiliser les noms de conditions générés automatiquement.
-Wempty-character-class
Avertit si une expression régulière contient une classe de caractères vide. Essayer de faire correspondre une classe de caractères vide n'a aucun sens : elle devrait toujours échouer. Cependant, pour des raisons de compatibilité descendante, re2hs autorise les classes de caractères vides et les traite comme des chaînes vides. Utilisez l'option --empty-class pour modifier le comportement par défaut.
-Wmatch-empty-string
Avertit si une règle est nullable (correspond à une chaîne vide). Si le lexer s'exécute en boucle et que la correspondance vide est involontaire, le lexer peut se bloquer de manière inattendue dans une boucle infinie.
-Wswapped-range
Avertit si la borne inférieure d'une plage est supérieure à sa borne supérieure. Le comportement par défaut est d'échanger silencieusement les bornes de la plage.
-Wundefined-control-flow
Avertit si certaines chaînes d'entrée provoquent un flux de contrôle indéfini dans le lexer (les motifs défectueux sont signalés). C'est une erreur dangereuse et courante. Elle peut être facilement corrigée en ajoutant la règle par défaut * qui a la priorité la plus basse, correspond à n'importe quelle unité de code,
unité de code unique.
-Wunreachable-rules
Avertir des règles qui sont masquées par d'autres règles et qui ne correspondra jamais.
-Wdeprecated-eof_rule
Avertir des règles autonomes de fin d'entrée $ qui seront rompues par les changements futurs et nécessiteront une correction. Pour le moment, ces règles prennent la priorité lorsqu'elles entrent en conflit avec d'autres règles, mais après l'introduction du symbole de fin d'entrée généralisé $, l'ordre de priorité changera et ces règles seront masquées par d'autres règles.

Avertir si un symbole est échappé alors qu'il ne devrait pas l'être. Par défaut, re2hs ignore silencieusement de tels échappements, mais cela peut aussi indiquer une faute de frappe ou une erreur dans la séquence d'échappement.
-Wnondeterministic-tags
Avertir si une balise a un degré de nondéterminisme n, où n est supérieur à 1.
-Wsentinel-in-midrule
Avertir si le symbole sentinelle apparaît au milieu d'une règle --- cela peut entraîner des lectures au-delà de la fin du tampon, des plantages ou une corruption de mémoire dans le lexer généré. Avertir si le fichier de syntaxe spécifié avec l'option --syntax est manquant des définitions de certaines configurations. Si certaines configurations sont inutilisées et n'ont pas besoin de définition, elles doivent être explicitement définies sur <undefined>.

Fichiers de syntaxe

Le support des différents langages dans re2c est basé sur l'idée de fichiers de syntaxe. Un fichier de syntaxe est un fichier de configuration qui définit la syntaxe du langage cible -- pas l'intégralité du langage, mais une petite partie de celui-ci qui est utilisée par le code généré. Les fichiers de syntaxe rendent re2c très flexible, mais ils ne doivent pas être utilisés comme un remplacement pour les configurations re2c: : leur objectif est de définir la syntaxe du langage cible, et non de personnaliser un lexer particulier. Tous les langages pris en charge ont des fichiers de syntaxe par défaut qui font partie de la distribution (voir le sous-répertoire include/syntax) ; ils sont également intégrés dans le binaire re2hs. Les utilisateurs peuvent fournir un fichier de syntaxe personnalisé qui remplace quelques configurations pour l'un des langages pris en charge, ou ils peuvent choisir de redéfinir toutes les configurations (auquel cas l'option --lang none doit être utilisée). Les fichiers de syntaxe contiennent des configurations de quatre types différents : listes de fonctionnalités, configurations de langue, configurations sur place et modèles de code.

Listes de fonctionnalités

Quelques configurations de listes définissent diverses fonctionnalités prises en charge par un backend donné, afin que re2hs puisse générer une erreur claire si l'utilisateur tente d'activer une fonctionnalité non prise en charge :
supported_apis
Une liste d'API prises en charge avec des éléments possibles simple, record, generic.
supported_api_styles
Une liste de styles d'API pris en charge avec des éléments possibles functions, free-form.
supported_code_models
Une liste de modèles de code pris en charge avec des éléments possibles goto-label, loop-switch, recursive-functions.
supported_targets
Une liste de cibles de génération de code prises en charge avec des éléments possibles code, dot, skeleton.
supported_features
Une liste de fonctionnalités prises en charge avec des éléments possibles nested-ifs, bitmaps, computed-gotos, case-ranges, monadic, unsafe, tags, captures, captvars.

Configurations de langue

Quelques configurations booléennes décrivent les fonctionnalités du langage cible qui affectent l'analyseur et le générateur de code de re2hs :
semicolons
Non nul si le langage utilise des points-virgules après les instructions.
backtick_quoted_strings
Non nul si le langage a des chaînes de caractères entre guillemets inversés.
single_quoted_strings
Non nul si le langage a des chaînes de caractères entre guillemets simples.
indentation_sensitive
Non nul si le langage est sensible à l'indentation.
wrap_blocks_in_braces
Non nul si les blocs d'instructions composés doivent être entourés d'accolades.

Configurations sur place

Les fichiers de syntaxe définissent les valeurs initiales de toutes les configurations re2c:, car elles peuvent différer pour différents langages. Voir la section des configurations pour une liste complète de toutes les configurations sur place et leur signification.

Modèles de code

Les modèles de code définissent la syntaxe du langage cible. Ils sont écrits dans un langage simple et spécifique au domaine avec la grammaire formelle suivante : 
code-template ::
      name '=' code-exprs ';'
    | CODE_TEMPLATE ';'
    | '<undefined>' ';'
code-exprs ::
      <EMPTY>
    | code-exprs code-expr
code-expr ::
      STRING
    | VARIABLE
    | optional
    | list
optional ::
      '(' CONDITIONAL '?' code-exprs ')'
    | '(' CONDITIONAL '?' code-exprs ':' code-exprs ')'
list ::
      '[' VARIABLE ':' code-exprs ']'
    | '[' VARIABLE '{' NUMBER '}' ':' code-exprs ']'
    | '[' VARIABLE '{' NUMBER ',' NUMBER '}' ':' code-exprs ']'

Un modèle de code est une séquence de littéraux de chaîne, de variables, d'éléments optionnels et de listes, ou une référence à un autre modèle de code, ou une valeur spéciale <undefined>. Les variables sont des espaces réservés qui sont substitués lors de la phase de génération de code. Les variables de liste sont spéciales : lors de l'expansion de modèles de liste, re2hs répète les expressions de la partie droite de la colonne plusieurs fois, remplaçant à chaque fois les occurrences de la variable de liste par une valeur spécifique à cette répétition. Les listes ont des bornes optionnelles (les valeurs négatives sont comptées à partir de la fin, par exemple, -1 signifie le dernier élément). Les noms conditionnels commencent par un point. Les conditions et les variables peuvent être locales (spécifiques au modèle de code donné) ou globales (autorisées dans tous les modèles de code). Lorsque re2hs lit le fichier de syntaxe, il vérifie que chaque modèle de code n'utilise que les variables et les conditions qui lui sont autorisées.

Par exemple, le modèle de code suivant définit une construction si-alors-sinon pour un langage de type C :

code:if_then_else =
    [branch{0}: topindent "if " cond " {" nl
        indent [stmt: stmt] dedent]
    [branch{1:-1}: topindent "} else" (.cond ? " if " cond) " {" nl
        indent [stmt: stmt] dedent]
    topindent "}" nl;

Ici, branch est une variable de liste : branch{0} s'étend à la première branche (qui est spéciale, car il n'y a pas de partie else), branch{1:-1} s'étend à toutes les branches restantes (s'il y en a). stmt est également une variable de liste : [stmt: stmt] est une liste imbriquée qui s'étend à une liste d'instructions dans le corps de la branche actuelle. topindent, indent, dedent et nl sont des variables globales, et .cond est une condition locale (leur signification est décrite ci-dessous). Ce modèle de code pourrait produire le code suivant :

if x {
    // do something
} else if y {
    // do something else
} else {
    // don't do anything
}

GESTION DE LA FIN DE L'ENTRÉE

L'un des principaux problèmes pour le lexer est de savoir quand s'arrêter. Il existe quelques conditions de terminaison :

  • le lexer peut correspondre à une règle (y compris la règle par défaut *) et arriver à un état final
  • le lexer peut ne correspondre à aucune règle et arriver à un état par défaut
  • le lexer peut atteindre la fin de l'entrée

Les deux premières conditions terminent le lexer d'une manière "naturelle" : il arrive à un état sans transitions sortantes, et la correspondance s'arrête automatiquement. La troisième condition, la fin de l'entrée, est différente : elle peut se produire dans n'importe quel état, et le lexer doit être capable de la gérer. La vérification de la fin de l'entrée interrompt le flux de travail normal du lexer et ajoute des branches conditionnelles au programme généré, il est donc nécessaire de minimiser le nombre de ces vérifications. re2hs prend en charge quelques méthodes différentes pour gérer la fin de l'entrée. Laquelle utiliser dépend de la complexité des expressions régulières, du besoin de mise en tampon, des considérations de performance et d'autres facteurs. Voici une liste de méthodes :

  • Sentinelle. Cette méthode élimine le besoin de vérifications de fin d'entrée. Elle est simple et efficace, mais limitée au cas où il existe un caractère de "sentinelle" naturel qui ne peut jamais apparaître dans une entrée valide. Ce caractère peut toujours apparaître dans une entrée invalide, mais il ne doit pas être autorisé par les expressions régulières, sauf peut-être comme dernier caractère d'une règle. La sentinelle est ajoutée à la fin de l'entrée et sert de signal d'arrêt : lorsque le lexer lit ce caractère, il s'agit soit d'une erreur de syntaxe, soit de la fin de l'entrée. Dans les deux cas, le lexer doit s'arrêter. Cette méthode est utilisée si YYFILL est désactivé avec re2c:yyfill:enable = 0; et re2c:eof a la valeur par défaut -1.
  • Sentinelle avec vérifications de limites. Cette méthode est générique : elle permet de gérer n'importe quelle entrée sans restrictions sur les expressions régulières. L'idée est de réduire le nombre de vérifications de fin d'entrée en les effectuant uniquement sur certains caractères. Similaire à la méthode "sentinelle", l'un des caractères est choisi comme "sentinelle" et ajouté à la fin de l'entrée. Cependant, il n'y a aucune restriction sur l'endroit où la sentinelle peut apparaître (en fait, n'importe quel caractère peut être choisi pour une sentinelle). Lorsque le lexer lit ce caractère, il effectue en plus une vérification de limites. Si la position actuelle est dans les limites, le lexer reprend la correspondance et traite la sentinelle comme un caractère normal. Sinon, il appelle YYFILL (sauf si elle est désactivée). Si davantage d'entrée est fournie, le lexer rematchera le dernier caractère et continuera comme si la sentinelle n'était pas là. Sinon, ce doit être la vraie fin de l'entrée, et le lexer s'arrête. Cette méthode est utilisée lorsque re2c:eof a une valeur non négative (elle doit être définie sur la valeur numérique de la sentinelle). YYFILL est facultatif.
  • Vérifications de limites avec remplissage. Cette méthode est générique et peut être plus rapide que la méthode "sentinelle avec vérifications de limites", mais elle est également plus complexe. L'idée est de partitionner les états du DFA en composantes fortement connexes (SCC) et de générer une seule vérification par SCC pour suffisamment de caractères pour couvrir le chemin non cyclique le plus long dans cette SCC. Cela réduit le nombre de vérifications, mais il y a un problème avec les lexèmes courts en fin d'entrée, car la vérification nécessite suffisamment de caractères pour couvrir le lexème le plus long. Ceci peut être corrigé en remplissant l'entrée avec quelques caractères factices qui ne forment pas un suffixe de lexème valide (afin que le lexer ne puisse pas les faire correspondre). La longueur du remplissage doit être YYMAXFILL, généré avec un bloc max. S'il n'y a pas assez d'entrée, le lexer appelle YYFILL qui doit fournir au moins le nombre requis de caractères ou ne pas revenir. Cette méthode est utilisée si YYFILL est activé et re2c:eof est -1 (c'est la configuration par défaut).
  • Vérifications personnalisées. L'API générique permet de remplacer les opérations de base comme la lecture d'un caractère, ce qui permet d'inclure les vérifications de fin d'entrée comme faisant partie de celles-ci. Cette approche est sujette aux erreurs et doit être utilisée avec prudence. Pour utiliser une méthode personnalisée, activez l'API générique avec --api custom ou re2c:api = custom; et désactivez les vérifications de limites par défaut avec re2c:yyfill:enable = 0; ou re2c:yyfill:check = 0;.

Sentinelle

Cet exemple utilise un caractère sentinelle pour gérer la fin de l'entrée. Le programme compte les mots séparés par des espaces dans une chaîne terminée par null. La sentinelle est le caractère null : c'est le dernier caractère de chaque chaîne d'entrée, et il n'est autorisé au milieu d'un lexème par aucune des règles (en particulier, il n'est pas inclus dans les plages de caractères où il est facile de l'oublier). Si un null se produit au milieu d'une chaîne, c'est une erreur de syntaxe et le lexer fera correspondre la règle par défaut *, mais il ne lira pas au-delà de la fin de l'entrée et ne plantera pas (utilisez l'avertissement -Wsentinel-in-midrule et la configuration re2c:sentinel pour vérifier cela). La configuration re2c:yyfill:enable = 0; supprime la génération de vérifications de limites et les appels YYFILL.

-- re2hs $INPUT -o $OUTPUT
{-# OPTIONS_GHC -Wno-unused-record-wildcards #-}
{-# LANGUAGE OverloadedStrings #-}
import Control.Monad (when)
import Data.ByteString (ByteString, index)
data State = State {
    _yyinput :: ByteString,
    _yycursor :: Int,
    _count :: Int
}
-- attend une chaîne terminée par null
%{
    re2c:YYFN = ["lexer;Int", "State{..};State"];
    re2c:yyfill:enable = 0;
    *      { (-1) }
    [\x00] { _count }
    [a-z]+ { lexer State{_count = _count + 1, ..} }
    [ ]+   { lexer State{..} }
%}
main :: IO ()
main = do
    let test s n = when (lexer st  /= n) $ error "failed"
                   where st = State{_yyinput = s, _yycursor = 0, _count = 0}
    test "\0" 0
    test "one two three\0" 3
    test "f0ur\0" (-1)

Sentinelle avec vérifications de limites

Cet exemple utilise une sentinelle avec vérifications de limites pour gérer la fin de l'entrée (cette méthode a été ajoutée dans la version 1.2). Le programme compte les chaînes d'un seul guillemet séparées par des espaces. Le caractère sentinelle est le caractère null, spécifié avec la configuration re2c:eof = 0;. Comme dans la méthode sentinelle, le null est le dernier caractère de chaque chaîne d'entrée, mais il est autorisé au milieu d'une règle (par exemple, 'aaa\0aa'\0 est une entrée valide, mais 'aaa\0 est une erreur de syntaxe). Les vérifications de limites sont générées dans chaque état qui correspond à un caractère d'entrée, mais elles sont limitées à la branche qui gère le null. Les vérifications de limites sont de la forme YYLIMIT <= YYCURSOR ou YYLESSTHAN(1) avec l'API générique. Si la condition de vérification est vraie, le lexer a atteint la fin de l'entrée et doit s'arrêter (YYFILL est désactivé avec re2c:yyfill:enable = 0; car l'entrée tient dans un seul tampon, voir la section YYFILL avec sentinelle pour un exemple utilisant YYFILL). Atteindre la fin de l'entrée ouvre trois possibilités : si le lexer est dans l'état initial, il fera correspondre la règle de fin d'entrée $, sinon il peut revenir à une règle précédemment correspondue (y compris la règle par défaut *) ou aller à un état par défaut, entraînant -Wundefined-control-flow.

-- re2hs $INPUT -o $OUTPUT
{-# OPTIONS_GHC -Wno-unused-record-wildcards #-}
{-# LANGUAGE OverloadedStrings #-}
import Control.Monad (when)
import qualified Data.ByteString as BS
import Data.Word
data State = State {
    _yyinput :: BS.ByteString,
    _yycursor :: Int,
    _yymarker :: Int,
    _yylimit :: Int,
    _count :: Int
}
-- attend une chaîne terminée par null
%{
    re2c:YYFN = ["lexer;Int", "State{..};State"];
    re2c:YYCTYPE = "Word8";
    re2c:YYPEEK = "BS.index";
    re2c:eof = 0;
    re2c:yyfill:enable = 0;
    str = ['] ([^'\\] | [\\][^])* ['];
    *    { (-1) }
    $    { _count }
    str  { lexer State{_count = _count + 1, ..} }
    [ ]+ { lexer State{..} }
%}
main :: IO ()
main = do
    let test s n = do
            let st = State {
                    _yyinput = s,
                    _yycursor = 0, 
                    _yymarker = 0,
                    _yylimit = BS.length s - 1, -- le null terminal n'est pas inclus
                    _count = 0}
           quand (lexer st /= n) $ erreur "échec"
    test "\0" 0
    test "'qu\0tes' 'are' 'fine: \\'' \0" 3
    test "'unterminated\\'\0" (-1)

Vérifications de limites avec rembourrage

Cet exemple utilise des vérifications de limites avec rembourrage pour gérer la fin de l'entrée (cette méthode est activée par défaut). Le programme compte les chaînes de caractères délimitées par des apostrophes, séparées par des espaces. Il y a un rembourrage de YYMAXFILL caractères nuls ajoutés à la fin de l'entrée, où la valeur de YYMAXFILL est auto-générée avec un bloc max. Il n'est pas nécessaire d'utiliser des nuls pour le rembourrage --- tout caractère peut être utilisé tant qu'il ne forme pas un suffixe de lexème valide (dans cet exemple, le rembourrage ne doit pas contenir d'apostrophes, car elles pourraient être confondues avec un suffixe d'une chaîne entre apostrophes). Il y a une règle "stop" qui correspond au premier caractère de rembourrage (nul) et termine le lexer (notez qu'elle vérifie si le nul est au début du rembourrage, sinon c'est une erreur de syntaxe). Les vérifications de limites ne sont générées que dans certains états déterminés par les composantes fortement connexes de l'automate sous-jacent. Les vérifications prennent la forme (YYLIMIT - YYCURSOR) < n ou YYLESSTHAN(n) avec l'API générique, où n est le nombre minimum de caractères nécessaires au lexer pour continuer (cela signifie également que la prochaine vérification de limite se produira dans au plus n caractères). Si la condition de vérification est vraie, le lexer a atteint la fin de l'entrée et invoquera YYFILL(n) qui devrait fournir au moins n caractères d'entrée ou ne pas retourner. Dans cet exemple, YYFILL échoue toujours et termine le lexer avec une erreur (ce qui est acceptable car l'entrée tient dans un seul tampon). Voir la section YYFILL avec rembourrage pour un exemple qui recharge le tampon d'entrée avec YYFILL.

-- re2hs $INPUT -o $OUTPUT
{-# OPTIONS_GHC -Wno-unused-record-wildcards #-}
{-# LANGUAGE OverloadedStrings #-}
import Control.Exception
import Control.Monad (when)
import qualified Data.ByteString as BS
data State = State {
    _yyinput :: BS.ByteString,
    _yycursor :: Int,
    _yylimit :: Int,
    _count :: Int
}
data FillException = UnexpectedFill deriving (Show)
instance Exception FillException
yymaxfill :: Int
%{max %}
%{
    re2c:YYFN  = ["lexer;IO Int", "State{..};State"];
    re2c:YYPEEK = "BS.index";
    re2c:YYFILL = "throw UnexpectedFill";
    re2c:monadic = 1; // YYFILL requires monadic do-notation for `when` conditions
    str = ['] ([^'\\] | [\\][^])* ['];
    [\x00] {
        -- check that it is the sentinel, not some unexpected null
        return $ if _yycursor == BS.length _yyinput - yymaxfill + 1 then _count else (-1)
    }
    str  { lexer State{_count = _count + 1, ..} }
    [ ]+ { lexer State{..} }
    *    { return (-1) }
%}
main :: IO ()
main = do
    let test s n = do
            let buf = BS.concat [s, BS.replicate yymaxfill 0]
            let st = State {
                    _yyinput = buf,
                    _yycursor = 0,
                    _yylimit = BS.length buf,
                    _count = 0}
            m <- catch (lexer st) (\(_ :: FillException) -> return (-2))
            when (m /= n) $ error "failed"
    test "" 0
    test "'unterminated\\'" (-2)
    test "'qu\0tes' 'are' 'fine: \\'' " 3
    test "'unexpected' \0 'null'" (-1)

Vérifications personnalisées

Cet exemple utilise une méthode personnalisée de gestion de la fin de l'entrée basée sur l'API générique. Le programme compte les chaînes de caractères entre apostrophes, séparées par des espaces. C'est le même que l'exemple sentinelle, sauf que l'entrée n'est pas terminée par un nul. Pour compenser l'absence d'un caractère sentinelle à la fin de l'entrée, YYPEEK est redéfini pour effectuer une vérification de limites avant de lire le prochain caractère d'entrée. Ceci est inefficace car les vérifications sont effectuées très souvent. Si la condition de vérification échoue, YYPEEK renvoie le caractère réel, sinon il renvoie un caractère sentinelle factice.

-- re2hs $INPUT -o $OUTPUT
{-# OPTIONS_GHC -Wno-unused-record-wildcards #-}
{-# LANGUAGE OverloadedStrings #-}
import Control.Monad (when)
import qualified Data.ByteString as BS
data State = State {
    _str :: BS.ByteString,
    _cur :: Int,
    _lim :: Int,
    _cnt :: Int
}
-- Expect a string without terminating null.
%{
    re2c:api = generic;
    re2c:YYFN = ["lexer;Int", "State{..};State"];
    re2c:YYPEEK = "if _cur < _lim then BS.index _str _cur else 0";
    re2c:YYSKIP = "let cur = _cur + 1 in let _cur = cur in";
    re2c:yyfill:enable = 0;
    *      { (-1) }
    [\x00] { _cnt }
    [a-z]+ { lexer State{_cnt = _cnt + 1, ..} }
    [ ]+   { lexer State{..} }
%}
main :: IO ()
main = do
    let test s n =
            let st = State {_str = s, _cur = 0, _lim = BS.length s, _cnt = 0}
            in when (lexer st /= n) $ error "failed"
    test "" 0
    test "one two three " 3
    test "f0ur" (-1)

RECHARGE DU TAMPON

Le besoin de mise en tampon survient lorsque l'entrée ne peut pas être mappée en mémoire d'un coup : soit elle est trop grande, soit elle arrive sous forme de flux (comme une lecture depuis un socket). La technique habituelle dans de tels cas consiste à allouer un tampon de mémoire de taille fixe et à traiter l'entrée par morceaux qui tiennent dans le tampon. Lorsque le morceau courant est traité, il est déplacé et de nouvelles données sont chargées. En pratique, c'est un peu plus complexe, car l'état du lexer ne se compose pas d'une seule position d'entrée, mais d'un ensemble de positions interdépendantes :

  • curseur : le prochain caractère d'entrée à lire (YYCURSOR dans l'API de pointeur C ou YYSKIP/YYPEEK dans l'API générique)
  • limite : la position après le dernier caractère d'entrée disponible (YYLIMIT dans l'API de pointeur C, géré implicitement par YYLESSTHAN dans l'API générique)
  • marqueur : la position de la correspondance la plus récente, le cas échéant (YYMARKER dans l'API par défaut ou YYBACKUP/YYRESTORE dans l'API générique)
  • jeton : le début du lexème courant (implicite dans l'API re2hs, car il n'est pas nécessaire pour le fonctionnement normal du lexer et peut être défini et mis à jour par l'utilisateur)
  • marqueur de contexte : la position du contexte de fin (YYCTXMARKER dans l'API de pointeur C ou YYBACKUPCTX/YYRESTORECTX dans l'API générique)
  • variables de balise : positions de sous-correspondance (définies avec les blocs stags et mtags et les primitives d'API générique YYSTAGP/YYSTAGN/YYMTAGP/YYMTAGN)

Tous ces éléments ne sont pas utilisés dans tous les cas, mais s'ils le sont, ils doivent être mis à jour par YYFILL. Toutes les positions actives sont contenues dans le segment entre le jeton et le curseur, par conséquent tout ce qui se trouve entre le début du tampon et le jeton peut être éliminé, le segment du jeton jusqu'à la limite doit être déplacé au début du tampon, et l'espace libre à la fin du tampon doit être rempli avec de nouvelles données. Afin d'éviter des appels fréquents à YYFILL, il est préférable de remplir autant de caractères d'entrée que possible (même si moins de caractères pourraient suffire à reprendre le lexer). Les détails de l'implémentation de YYFILL varient légèrement en fonction de la méthode de gestion de la fin de fichier utilisée : le cas de la règle EOF est un peu plus simple que le cas de la vérification de limites avec rembourrage. Notez également que si l'option -f --storable-state est utilisée, YYFILL a une sémantique légèrement différente (décrite dans la section sur l'état stockable).

YYFILL avec sentinelle

Si la règle EOF est utilisée, YYFILL est une primitive de type fonction qui n'accepte aucun argument et renvoie une valeur qui est vérifiée par rapport à zéro. L'invocation de YYFILL est déclenchée par la condition YYLIMIT <= YYCURSOR dans l'API de pointeur C et YYLESSTHAN() dans l'API générique. Une valeur de retour non nulle signifie que YYFILL a échoué. Un appel réussi à YYFILL doit fournir au moins un caractère et ajuster les positions d'entrée en conséquence. La limite doit toujours être définie à un après la dernière position d'entrée dans le tampon, et le caractère à la position limite doit être le symbole sentinelle spécifié par la configuration re2c:eof. Les schémas ci-dessous montrent les emplacements relatifs des positions d'entrée dans le tampon avant et après l'appel à YYFILL (le symbole sentinelle est marqué par #, et le second schéma montre le cas où il n'y a pas assez d'entrée pour remplir tout le tampon).

               <-- décalage -->
             >-A------------B---------C-------------D#-----------E->
             tampon       jeton    marqueur        limite,
                                                  curseur
>-A------------B---------C-------------D------------E#->
             tampon,  marqueur        curseur        limite
             jeton
               <-- décalage -->
             >-A------------B---------C-------------D#--E
             tampon       jeton    marqueur        limite,
                                                  curseur
>-A------------B---------C-------------D---E#........
             tampon,  marqueur       curseur limite
             jeton

Voici un exemple de programme qui lit le fichier d'entrée input.txt par morceaux de 4096 octets et utilise la règle EOF.

-- re2hs $INPUT -o $OUTPUT
{-# OPTIONS_GHC -Wno-unused-record-wildcards #-}
{-# LANGUAGE OverloadedStrings #-}
import Control.Monad
import Data.ByteString as BS
import Data.Word
import GHC.IO.Handle
import System.Directory
import System.IO
chunk_size :: Int
chunk_size = 4096
data State = State {
    _file :: !Handle,
    _yyinput :: !BS.ByteString,
    _yycursor :: !Int,
    _yymarker :: !Int,
    _yylimit :: !Int,
    _token :: !Int,
    _eof :: !Bool,
    _count :: !Int
}
%{
    re2c:YYFN = ["lexer;IO Int", "State{..};State;!State{..}"];
    re2c:YYCTYPE = "Word8";
    re2c:YYPEEK = "BS.index";
    re2c:YYFILL = "(State{..}, yyfill) <- fill State{..}";
    re2c:eof = 0;
    re2c:monadic = 1;
    str = ['] ([^'\\] | [\\][^])* ['];
    *    { return (-1) }
    $    { return _count }
    str  { lexer State{_token = _yycursor, _count = _count + 1, ..} }
    [ ]+ { lexer State{_token = _yycursor, ..} }
%}
fill :: State -> IO (State, Bool)
fill State{..} = do
    case _eof of
        True -> return (State{..}, False)
        False -> do
            -- Discard everything up to the current token, cut off terminating null,
            -- read new chunk from file and reappend terminating null at the end.
            chunk <- BS.hGet _file chunk_size
            return (State {
                _yyinput = BS.concat [(BS.init . BS.drop _token) _yyinput, chunk, "\0"],
                _yycursor = _yycursor - _token,
                _yymarker = _yymarker - _token,
                _yylimit = _yylimit - _token + BS.length chun
k, -- exclure le nul de terminaison
                _token = 0,
                _eof = BS.null chunk, -- fin de fichier ?
                ..}, True)
main :: IO ()
main = do
    let fname = "input"
    -- Préparer le fichier d'entrée.
    BS.writeFile fname $ BS.concat ["'qu\0tes' 'are' 'fine: \\'' " | _ <- [1..chunk_size]]
    let expect = 3 * chunk_size -- le nombre total de chaînes dans le fichier
    -- Exécuter le lexer sur le fichier préparé.
    fh <- openFile fname ReadMode
    let st = State {
        _file = fh,
        _yyinput = BS.singleton 0,
        _yycursor = 0,
        _yymarker = 0,
        _token = 0,
        _yylimit = 0,
        _eof = False,
        _count = 0
    }
    result <- lexer st
    hClose fh
    -- Nettoyage.
    removeFile fname
    -- Vérifier le résultat.
    when (result /= expect) $ error $ "attendu " ++ show expect ++ ", obtenu " ++ show result
    return ()

YYFILL avec remplissage

Dans le cas par défaut (lorsque la règle EOF n'est pas utilisée), YYFILL est une primitive de type fonction qui accepte un seul argument et ne retourne aucune valeur. L'invocation de YYFILL est déclenchée par la condition (YYLIMIT - YYCURSOR) < n dans l'API pointeur C et YYLESSTHAN(n) dans l'API générique. L'argument passé à YYFILL est le nombre minimal de caractères qui doivent être fournis. S'il ne parvient pas à le faire, YYFILL ne doit pas retourner au lexer (pour cette raison, il est préférable de l'implémenter comme une macro qui retourne de la fonction appelante en cas d'échec). En cas d'invocation réussie de YYFILL, la position limite doit être définie soit à un après la dernière position d'entrée dans le tampon, soit à la fin du remplissage YYMAXFILL (dans le cas où YYFILL a lu avec succès au moins n caractères, mais pas assez pour remplir tout le tampon). {-# LANGUAGE OverloadedStrings #-}
import Control.Monad
import qualified Data.ByteString as BS
import GHC.IO.Handle
import System.Directory
import System.IO
chunk_size :: Int
chunk_size = 4096
data State = State {
    _file :: !Handle,
    _yyinput :: !BS.ByteString,
    _yycursor :: !Int,
    _yylimit :: !Int,
    _token :: !Int,
    _eof :: !Bool,
    _count :: !Int
}
%{
    re2c:YYFN = ["lexer;IO Int", "State{..};State;!State{..}"];
    re2c:YYPEEK = "BS.index";
    // Nous devons désactiver la vérification YFILL générée automatiquement et l'écrire manuellement dans le cadre de l'implémentation de YYFILL,
    // afin de pouvoir propager l'état mis à jour en dehors de celui-ci.
    re2c:yyfill:check = 0;
    re2c:YYFILL = "State{..} <- fill State{..} @@";
    re2c:monadic = 1;
    str = ['] ([^'\\] | [\\][^])* ['];
    *      { return (-1) }
    [\x00] { return $ if _yycursor == _yylimit - yymaxfill + 1 then _count else (-1) }
    str    { lexer State{_token = _yycursor, _count = _count + 1, ..} }
    [ ]+   { lexer State{_token = _yycursor, ..} }
%}
yymaxfill :: Int
%{max %}
fill :: State -> Int -> IO State
fill !st@State{..} !need =
    if _yylimit - _yycursor >= need then
        return st
    else case _eof of
        True -> error "fill failed"
        False -> do
            -- Ignorer tout jusqu au jeton actuel, couper le nul de terminaison,
            -- lire un nouveau bloc du fichier et rajouter le nul de terminaison à la fin.
            chunk <- BS.hGet _file chunk_size
            let !eof = BS.length chunk < need -- fin du fichier ?
            let !buf = BS.concat [
                    BS.drop _token _yyinput,
                    chunk,
                    if eof then (BS.replicate yymaxfill 0) else BS.empty]
            return State {
                _yyinput = buf,
                _yycursor = _yycursor - _token,
                _yylimit = BS.length buf,
                _token = 0,
                _eof = eof,
                ..}
main :: IO ()
main = do
    let fname = "input"
    -- Préparer le fichier d'entrée.
    BS.writeFile fname $ BS.concat ["'qu\0tes' 'are' 'fine: \\'' " | _ <- [1..chunk_size]]
    let expect = 3 * chunk_size -- le nombre total de chaînes dans le fichier
    -- Exécuter le lexer sur le fichier préparé.
    fh <- openFile fname ReadMode
    let st = State {
        _file = fh,
        _yyinput = BS.empty,
        _yycursor = 0,
        _token = 0,
        _yylimit = 0,
        _eof = False,
        _count = 0
    }
    result <- lexer st
    hClose fh
    -- Nettoyage.
    removeFile fname
    -- Vérifier le résultat.
    when (result /= expect) $ error $ "attendu " ++ show expect ++ ", obtenu " ++ show result
    return ()

FONCTIONNALITÉS

Multiples blocs

Parfois, il est nécessaire d'avoir plusieurs lexers interdépendants (par exemple, s'il existe une machine à états de haut niveau qui effectue des transitions entre les modes du lexer). Ceci peut être implémenté en utilisant plusieurs blocs re2hs connectés. Une autre option consiste à utiliser des conditions de départ.

L'implémentation des connexions entre les blocs dépend de la langue cible. Dans les langages qui ont une instruction goto (comme C/C++ et Go), on peut avoir tous les blocs dans une seule fonction, chacun précédé d'une étiquette. La transition d'un bloc à un autre est un simple goto. Dans les langages qui n'ont pas de goto (comme Rust), il est nécessaire d'utiliser une boucle avec un switch sur une variable d'état, similaire à la boucle/switch yystate générée par re2hs, ou alors d'encapsuler chaque bloc dans une fonction et d'utiliser des appels de fonction.

L'exemple ci-dessous utilise plusieurs blocs pour analyser des nombres binaires, octaux, décimaux et hexadécimaux. Chaque base a son propre bloc. Le bloc initial détermine la base et distribue vers les autres blocs. Les configurations communes sont définies dans un bloc séparé au début du programme ; elles sont héritées par les autres blocs.

-- re2hs $INPUT -o $OUTPUT -i
{-# OPTIONS_GHC -Wno-unused-record-wildcards #-}
{-# LANGUAGE OverloadedStrings #-}
import Control.Monad (when)
import Data.ByteString (ByteString, index)
data State = State {
    _yyinput :: !ByteString,
    _yycursor :: !Int,
    _yymarker :: !Int
}
peek_digit :: ByteString -> Int -> Int -> Int
peek_digit str idx offs = fromIntegral (index str (idx - 1)) - offs
%{
    re2c:yyfill:enable = 0;
%}
%{local
    re2c:YYFN = ["parse_bin;Int", "State{..};State", "num;Int"];
    [01] { parse_bin State{..} $ num * 2 + (peek_digit _yyinput _yycursor 48) }
    *    { num }
%}
%{local
    re2c:YYFN = ["parse_oct;Int", "State{..};State", "num;Int"];
    [0-7] { parse_oct State{..} $ num * 8 + (peek_digit _yyinput _yycursor 48) }
    *     { num }
%}
%{local
    re2c:YYFN = ["parse_dec;Int", "State{..};State", "num;Int"];
    [0-9] { parse_dec State{..} $ num * 10 + (peek_digit _yyinput _yycursor 48) }
    *     { num }
%}
%{local

Conditions de départ

Les conditions de départ sont activées avec l'option --start-conditions. Elles fournissent un moyen d'encoder plusieurs automates interdépendants au sein du même bloc re2hs.

Chaque condition correspond à un seul automate et a un nom unique spécifié par l'utilisateur et un numéro interne unique défini par re2hs. Les numéros sont utilisés pour basculer entre les conditions : le code généré utilise les primitives YYGETCOND et YYSETCOND pour obtenir la condition actuelle ou la définir à un nombre donné. Utilisez le bloc conditions, l'option --header ou la configuration re2c:header pour générer des identificateurs de condition numériques. La configuration re2c:cond:enumprefix spécifie le préfixe d'identificateur généré.

En mode condition, chaque règle doit être préfixée par une liste de noms de condition séparés par des virgules entre chevrons, ou un caractère générique <*> pour désigner toutes les conditions. La syntaxe de la règle est étendue comme suit :

< liste-condition > expression-régulière code
Une règle qui est fusionnée à chaque condition de la liste-condition. Elle correspond à expression-régulière et exécute le code associé.
< liste-condition > expression-régulière => condition code
Une règle qui est fusionnée à chaque condition de la liste-condition. Elle correspond à expression-régulière, définit la condition actuelle à condition et exécute le code associé.
< liste-condition > expression-régulière :=> condition
Une règle qui est fusionnée à chaque condition de la liste-condition. Elle correspond à expression-régulière et passe immédiatement à condition (il n'y a pas d'action sémantique).
< con
dition-list > !action code
Une règle qui lie code à l'endroit défini par action dans chaque condition de la condition-list (voir la section actions pour les différents types d'actions).
<! condition-list > code
Une règle qui ajoute code au début des actions sémantiques de toutes les règles pour chaque condition de la condition-list. Cette syntaxe est obsolète et l'action !pre_rule doit être utilisée à la place (elle fait exactement la même chose).
< > code
Une règle qui crée une condition d'entrée spéciale avec le numéro zéro et le nom "0" qui exécute code avant de sauter vers d'autres conditions. Cette syntaxe est obsolète et l'action !entry doit être utilisée à la place (elle fournit un contrôle plus fin, car le code peut être spécifié condition par condition, et on peut sauter directement au début de la condition sans passer par la distribution des conditions).
< > => condition code
Identique à la règle précédente, sauf qu'elle définit la prochaine condition.
< > :=> condition
Identique à la règle précédente, sauf qu'elle n'a pas de code associé et saute immédiatement à condition.

Le code généré par re2hs pour les conditions dépend de savoir si re2hs utilise l'approche goto/label ou l'approche boucle/switch pour encoder les automates.

Dans les langages qui ont une instruction goto (comme C/C++ et Go), les conditions sont naturellement implémentées sous forme de blocs de code préfixés par des labels de la forme yyc_<cond>, où cond est un nom de condition (le préfixe du label peut être modifié avec re2c:cond:prefix). Les transitions entre conditions sont implémentées à l'aide de goto et de labels de conditions. Avant toutes les conditions, re2hs génère un switch initial sur YYGETSTATE qui saute à l'état de départ de la condition actuelle. Les règles de raccourci :=> contournent le switch initial et sautent directement à la condition spécifiée (re2c:cond:goto peut être utilisé pour modifier le comportement par défaut). Les règles avec actions sémantiques ne sautent pas automatiquement à la condition suivante ; cela doit être fait par le code d'action défini par l'utilisateur.

Dans les langages qui n'ont pas de goto (comme Rust), re2hs réutilise la variable yystate pour stocker les numéros de condition. Chaque condition reçoit un identifiant numérique égal au nombre de son état de départ, et un switch entre conditions n'est pas différent d'un switch entre états de DFA d'une seule condition. Il n'y a pas besoin d'un switch de condition initial séparé. (Étant donné que la même approche est utilisée pour implémenter les états stockables, YYGETCOND/YYSETCOND sont redondants si les états stockables et les conditions sont utilisés).

Le programme ci-dessous utilise des conditions de départ pour analyser des nombres binaires, octaux, décimaux et hexadécimaux. Il y a un seul bloc où chaque base a sa propre condition, et la condition initiale est connectée à toutes. La variable définie par l'utilisateur cond stocke le numéro de la condition actuelle ; elle est initialisée au numéro de la condition initiale générée avec le bloc conditions.

État stockable

Avec l'option --storable-state, re2hs génère un lexer qui peut stocker son état actuel, retourner à l'appelant, et reprendre plus tard les opérations exactement là où il s'est arrêté. Le mode de fonctionnement par défaut dans re2hs est un modèle de type "pull", dans lequel le lexer "tire" plus d'entrée lorsqu'il en a besoin. Cela peut être inacceptable dans les cas où l'entrée devient disponible par morceaux (par exemple, si le lexer est appelé par l'analyseur syntaxique, ou si le programme lexer communique via un protocole de socket avec un autre programme qui doit attendre une réponse du lexer avant de transmettre le message suivant). La fonctionnalité d'état stockable est destinée précisément à de tels cas : elle permet de générer des lexers qui fonctionnent selon un modèle de type "push". Lorsque le lexer a besoin de plus d'entrée, il stocke son état et retourne à l'appelant. Plus tard, lorsque plus d'entrée est disponible, l'appelant reprend le lexer exactement là où il s'est arrêté. Il y a quelques changements nécessaires par rapport au modèle "pull" :

  • Définir les primitives YYSETSTATE() et YYGETSTATE(state).
  • Définir les variables yych, yyaccept (si utilisées) et state comme faisant partie de l'état persistant du lexer. La variable state doit être initialisée à -1.
  • YYFILL doit retourner au programme externe au lieu d'essayer de fournir plus d'entrée. Le code de retour doit indiquer que le lexer a besoin de plus d'entrée.
  • Le programme externe doit reconnaître les situations où le lexer a besoin de plus d'entrée et répondre de manière appropriée.
  • Utiliser optionnellement le bloc getstate pour générer un switch YYGETSTATE détaché du lexer principal. Cela ne fonctionne que pour les langages qui ont goto (pas en mode --loop-switch).
  • Utiliser re2c:eof et la méthode du sentinelle avec vérifications de limites pour gérer la fin de l'entrée. La méthode basée sur le remplissage peut ne pas fonctionner car il n'est pas clair quand ajouter le remplissage : la fin actuelle de l'entrée peut ne pas être la fin ultime de l'entrée, et ajouter le remplissage trop tôt peut couper un lexème gourmand lu partiellement. De plus, en raison de la logique du programme de haut niveau, obtenir plus d'entrée peut dépendre du traitement du lexème à la fin du tampon (qui est déjà bloqué en raison de la condition de fin d'entrée).

Voici un exemple de lexer en mode "push" qui simule la lecture de paquets depuis un socket. Le lexer boucle jusqu'à ce qu'il rencontre la fin de l'entrée et retourne à la fonction appelante. La fonction appelante fournit plus d'entrée en "envoyant" le paquet suivant et reprend l'analyse lexicale. Ce processus s'arrête lorsque tous les paquets ont été envoyés, ou lorsqu'il y a une erreur.

-- re2hs $INPUT -o $OUTPUT -fi
{-# OPTIONS_GHC -Wno-unused-record-wildcards #-}
{-# LANGUAGE OverloadedStrings #-}
import Control.Concurrent.Chan
import Control.Monad
import Data.ByteString as BS
import Text.Printf
debug :: IO () -> IO ()
debug = when False
data State = State {
    _pipe :: !(Chan BS.ByteString),
    _yyinput :: !BS.ByteString,
    _yycursor :: !Int,
    _yymarker :: !Int,
    _yylimit :: !Int,
    _token :: !Int,
    _eof :: !Bool,
    _yystate :: !Int,
    _recv :: !Int
}
data Status = End | Ready | Waiting | BadPacket deriving (Eq)
%{
    re2c:YYFN = ["lexer;IO (State, Status)", "State{..};State;!State{..}"];
    re2c:YYPEEK = "BS.index";
    re2c:YYFILL = "return (State{..}, Waiting)";
    re2c:eof = 0;
    re2c:monadic = 1;
    packet = [a-z]+[;];
    *      { return (State{..}, BadPacket) }
    $      { return (State{..}, End) }
    packet { lexer State{_token = _yycursor, _recv = _recv + 1, ..} }
%}
fill :: State -> IO (State, Status)
fill st@State{..} = do
    case _eof of
        True -> return (st, End)
        False -> do
            -- Discard everything up to the current token, cut off terminating null,
            -- read new chunk from file and reappend terminating null at the end.
            chunk <- readChan _pipe
            return (State {
                _yyinput = BS.concat [(BS.init . BS.drop _token) _yyinput, chunk, "\0"],
                _yycursor = _yycursor - _token,
                _yymarker = _yymarker - _token,
                _yylimit = _yylimit - _token + BS.length chunk, -- exclude terminating null
                _token = 0,
                _eof = BS.null chunk, -- end of file?
                ..}, Ready)
loop :: State -> [BS.ByteString] -> IO Status
loop State{..} packets = do
    (State{..}, status) <- lexer State{..}
    case status of
        End -> do
            debug $ printf "done: got %d packets\n" _recv
            return End
        Waiting -> do
            debug $ printf "waiting...\n"
            packets' <- case packets of
                [] -> do
                    writeChan _pipe BS.empty
                    return []
                p:ps -> do
                    debug $ printf "sent packet '%s'\n" (show p)
                    writeChan _pipe p
                    return ps
            (State{..}, status') <- fill State{..}
            case status' of
                Ready -> loop State{..} packets'
                _ -> error "unexpected status after fill"
        BadPacket -> do
            debug $ printf "error: ill-formed packet\n"
            return BadPacket
        _ -> error "unexpected status"
test :: [BS.ByteString] -> Status -> IO ()
test packets expect = do
    pipe <- newChan -- emulate pipe using a chan of bytestrings
    let st = State {
        _pipe = pipe,
        _yyinput = BS.singleton 0, -- null sentinel triggers YYFILL
        _yycursor = 0,
        _yymarker = 0,
        _token = 0,
        _yylimit = 0,
        _eof = False,
        _yystate = -1,
        _recv = 0
    }
    status <- loop st packets
    when (status /= expect) $ error "failed"
    return ()
main :: IO ()
main = do
    test [] End
    test ["ze", "ro;o", "ne", ";t", "wo;thr", "e", "e", ";", "four;"] End
    test ["zer0;&qu
ot;] BadPacket

Blocs réutilisables

Les blocs réutilisables de la forme /*!rules:re2c[:<nom>] ... */ ou %{rules[:<nom>] ... %} peuvent être réutilisés un nombre illimité de fois et combinés avec d'autres blocs re2hs. Le <nom> est facultatif. Un bloc de règles peut être utilisé dans un bloc ou une directive use. Le code d'un bloc de règles est généré à chaque point d'utilisation.

Les blocs d'utilisation sont définis avec /*!use:re2c[:<nom>] ... */ ou %{use[:<nom>] ... %}. Le <nom> est facultatif : s'il n'est pas spécifié, le bloc de règles associé est le plus récent (nommé ou non). Un bloc d'utilisation peut ajouter ses propres définitions nommées, configurations et règles. Un cas d'utilisation important pour les blocs d'utilisation est un analyseur lexical qui prend en charge plusieurs encodages d'entrée : le même bloc de règles est réutilisé plusieurs fois avec des configurations spécifiques à l'encodage (voir l'exemple ci-dessous).

La directive d'utilisation dans le bloc !use:<nom>; peut être utilisée à l'intérieur d'un bloc re2hs. Elle fusionne le bloc référencé <nom> dans le bloc actuel. Si certaines des règles et configurations fusionnées chevauchent celles définies précédemment, les conflits sont résolus de la manière habituelle : la règle la plus ancienne a la priorité, et la configuration la plus récente remplace les précédentes. Une exception concerne les règles spéciales *, $ et (en mode conditionnel) <!>, pour lesquelles une définition locale au bloc a priorité sur toutes les définitions héritées. La directive d'utilisation permet de combiner différents blocs re2hs dans un seul bloc (voir l'exemple ci-dessous).

Les blocs nommés et la directive d'utilisation dans le bloc ont été ajoutés dans la version 2.2 de re2hs. Depuis cette version, les blocs réutilisables sont autorisés par défaut (aucune option spéciale n'est nécessaire). Avant la version 2.2, le mode de réutilisation était activé avec l'option -r --reusable. Avant la version 1.2, les blocs réutilisables ne pouvaient pas être mélangés avec des blocs normaux.

Exemple d'une directive !use

-- re2hs $INPUT -o $OUTPUT
{-# OPTIONS_GHC -Wno-unused-record-wildcards #-}
{-# LANGUAGE OverloadedStrings #-}
-- Cet exemple montre comment combiner des blocs re2c réutilisables : deux blocs
-- ('colors' et 'fish') sont fusionnés en un seul. La règle 'salmon' apparaît
-- dans les deux blocs ; le bloc 'fish' a la priorité car il est utilisé
-- plus tôt. La règle par défaut * apparaît dans les trois blocs ; la définition locale (non
-- héritée) a la priorité.
import Control.Monad (when)
import Data.ByteString (ByteString, index)
data Answer = Color | Fish | Dunno deriving (Eq)
data State = State {
    _yyinput :: ByteString,
    _yycursor :: Int,
    _yymarker :: Int
}
%{rules:colors
    *                            { error "ah" }
    "red" | "salmon" | "magenta" { Color }
%}
%{rules:fish
    *                            { error "oh" }
    "haddock" | "salmon" | "eel" { Fish }
%}
%{
    re2c:YYFN = ["lexer;Answer", "State{..};State"];
    re2c:yyfill:enable = 0;
    !use:fish;
    !use:colors;
    * { Dunno } // remplace les règles '*' héritées
%}
main :: IO ()
main = do
    let test str ans = do
            let st = State {_yyinput = str, _yycursor = 0, _yymarker = 0}
            when (lexer st /= ans) $ error "failed"
    test "salmon" Fish
    test "what?" Dunno

-- re2hs $INPUT -o $OUTPUT --input-encoding utf8
{-# OPTIONS_GHC -Wno-unused-record-wildcards #-}
{-# LANGUAGE OverloadedStrings #-}
-- Cet exemple prend en charge plusieurs encodages d'entrée : UTF-8 et UTF-32.

Extraction des sous-correspondances

re2hs propose deux options pour l'extraction des sous-correspondances.

Tags
La première option consiste à utiliser des tags autonomes de la forme @stag ou #mtag, où stag et mtag sont des noms arbitraires définis par l'utilisateur. Les tags sont activés avec l'option -T --tags ou la configuration re2c:tags = 1. Sémantiquement, les tags sont des marqueurs de position : ils peuvent être insérés n'importe où dans une expression régulière, et ils se lient à la position (ou aux positions) correspondante(s) dans la chaîne d'entrée. Les tags s se lient à la dernière position correspondante, et les tags m se lient à une liste de positions (ils peuvent être utilisés dans des sous-expressions de répétition, où une seule position dans une expression régulière correspond à plusieurs positions dans la chaîne d'entrée). Tous les tags doivent être définis par l'utilisateur, soit manuellement, soit à l'aide des blocs svars et mvars. S'il existe plus d'une façon de faire correspondre les tags à l'entrée, l'ambiguïté est résolue en utilisant la stratégie de désambiguïsation gloutonne la plus à gauche.
Captures
La deuxième option consiste à utiliser des groupes de capture. Ils sont activés avec l'option --captures ou la configuration re2c:captures = 1. Il existe deux variantes pour différentes politiques de désambiguïsation : --leftmost-captures (par défaut) pour la politique gloutonne la plus à gauche, et --posix-captures pour la politique de correspondance la plus longue POSIX. Dans ce mode, toutes les sous-expressions entre parenthèses sont considérées comme des groupes de capture, et un point d'exclamation peut être utilisé pour marquer les groupes non capturants : (! ... ). Avec l'option --invert-captures ou la configuration re2c:invert-captures = 1 , le sens du point d'exclamation est inversé. Le nombre de groupes pour la règle correspondante est stocké dans une variable yynmatch (l'expression régulière entière est le groupe numéro zéro), et les résultats des sous-correspondances sont stockés dans le tableau yypmatch. Les deux yynmatch et yypmatch doivent être définis par l'utilisateur, et la taille de yypmatch doit être d'au moins [yynmatch * 2]. Utilisez le bloc maxnmatch pour définir YYMAXNMATCH, une constante égale à la valeur maximale de yynmatch parmi toutes les règles.
Captvars
Une autre façon d'utiliser les groupes de capture est l'option --captvars ou la configuration re2c:captvars = 1. La seule différence avec --captures réside dans la manière dont le code généré stocke les résultats des sous-correspondances : au lieu de yynmatch et yypmatch, re2hs génère les variables yytl<k> et yytr<k> pour le k-ième groupe de capture (l'utilisateur doit les déclarer à l'aide d'un bloc svars). Les captures avec variables prennent en charge deux politiques de désambiguïsation : --leftmost-captvars ou re2c:leftmost-captvars = 1 pour la politique gloutonne la plus à gauche (par défaut) et --posix-captvars ou re2c:posix-captvars pour la politique de correspondance la plus longue POSIX.

Sous le capot, toutes ces options se traduisent par des tags et des Automates Finis Déterministes Etiquetés avec Anticipation (TDFA). L'idée principale des TDFA est de minimiser la surcharge liée à l'extraction des sous-correspondances. Dans l'extrême, s'il n'y a pas de tags ou de captures dans une expression régulière, le TDFA est simplement un DFA ordinaire. Si le nombre de tags est modéré, la surcharge est à peine perceptible. Le TDFA généré utilise un certain nombre de variables de tags qui ne correspondent pas directement aux tags : une seule variable peut être utilisée pour différents tags, et un tag peut nécessiter plusieurs variables pour contenir toutes ses valeurs possibles. Finalement, l'ambiguïté est résolue, et une seule variable finale par tag survit. Les variables de tags doivent être définies à l'aide des blocs stags ou mtags. Si l'état de l'analyseur est stocké, les variables de tags doivent en faire partie. Elles doivent également être mises à jour par YYFILL.

Les tags s prennent en charge les opérations suivantes :

  • sauvegarder la position d'entrée dans un tag s : t = YYCURSOR avec l'API de pointeur C ou une opération définie par l'utilisateur YYSTAGP(t) avec l'API générique
  • sauvegarder une valeur par défaut dans un tag s : t = NULL avec l'API de pointeur C ou une opération définie par l'utilisateur YYSTAGN(t) avec l'API générique
  • copier un tag s dans un autre : t1 = t2

Les tags m prennent en charge les opérations suivantes :

  • ajouter une position d'entrée à un tag m : une opération définie par l'utilisateur YYMTAGP(t) avec l'API par défaut et générique
  • ajouter une valeur par défaut à un tag m : une opération définie par l'utilisateur YYMTAGN(t) avec l'API par défaut et générique
  • copier un tag m dans un autre : t1 = t2

Les tags s peuvent être implémentés comme des valeurs scalaires (pointeurs ou décalages). Les tags m nécessitent une représentation plus complexe, car ils doivent stocker une séquence de valeurs de tags. La représentation la plus naïve et inefficace d'un tag m est une liste (tableau, vecteur) de valeurs de tags ; une représentation plus efficace consiste à stocker tous les tags m dans un arbre préfixe représenté comme un tableau de nœuds (v, p), où v est la valeur du tag et p est un pointeur vers le nœud parent.

Les variables de balise font partie de l'état du lexer et sont ajustées dans YYFILL comme d'autres positions d'entrée. Il est nécessaire de le faire pour les s-tags car leurs valeurs sont invalidées après le décalage du contenu du tampon. Cela peut ne pas être nécessaire dans une implémentation personnalisée où les variables de balise stockent des décalages par rapport au début de la chaîne d'entrée plutôt qu'au tampon, ce qui peut être le cas avec les m-tags.

-- re2hs $INPUT -o $OUTPUT
{-# OPTIONS_GHC -Wno-unused-record-wildcards #-}
{-# LANGUAGE OverloadedStrings #-}
import Control.Monad
import Data.ByteString as BS
import GHC.IO.Handle
import System.Directory
import System.IO
chunk_size :: Int
chunk_size = 4096
data State = State {
    _file :: !Handle,
    _yyinput :: !BS.ByteString,
    _yycursor :: !Int,
    _yymarker :: !Int,
    _yylimit :: !Int,
    _token :: !Int,
    -- Final tag bindings available in semantic action.
    %{svars format = "\n@@ :: !Int,"; %}
    -- Intermediate tag bindings used by the lexer (must be autogenerated).
    %{stags format = "\n@@ :: !Int,"; %}
    _eof :: !Bool
}
data SemVer = SemVer {
    major :: !Int,
    minor :: !Int,
    patch :: !Int
} deriving (Eq, Show)
s2n :: BS.ByteString -> Int -> Int -> Int
s2n s i j = f i 0 where
    f k n = if k >= j then n else f (k + 1) (n * 10 + (fromIntegral (BS.index s k) - 48))
%{
    re2c:YYFN = ["lexer;IO [SemVer]", "State{..};State", "_vers;[SemVer]"];
    re2c:YYPEEK = "BS.index";
    re2c:YYFILL = "(State{..}, yyfill) <- fill State{..}";
    re2c:eof = 0;
    re2c:monadic = 1;
    re2c:tags = 1;
    num = [0-9]+;
    @_1 num @_2 "." @_3 num @_4 ("." @_5 num)? [\n] {
        let ver = SemVer {
            major = s2n _yyinput _1 _2,
            minor = s2n _yyinput _3 _4,
            patch = if _5 == (-1) then 0 else s2n _yyinput _5 (_yycursor - 1)
        }
        lexer State{..} (ver: _vers)
    }
    $ { return _vers }
    * { error "lexer failed" }
%}
fill :: State -> IO (State, Bool)
fill State{..} = do
    case _eof of
        True -> return (State{..}, False)
        False -> do
            -- Discard everything up to the current token, cut off terminating null,
            -- read new chunk from file and reappend terminating null at the end.
            chunk <- BS.hGet _file chunk_size
            return (State{
                _yyinput = BS.concat [(BS.init . BS.drop _token) _yyinput, chunk, "\0"],
                _yycursor = _yycursor - _token,
                _yymarker = _yymarker - _token,
                _yylimit = _yylimit - _token + BS.length chunk, -- exclude terminating null
                _token = 0,
                _eof = BS.null chunk, -- end of file?
                ..}, True)
main :: IO ()
main = do
    let fname = "input"
    -- Prepare input file.
    BS.writeFile fname $ BS.concat ["1.22.333\n" | _ <- [1..chunk_size]]
    let expect = [SemVer {major = 1, minor = 22, patch = 333} | _ <- [1..chunk_size]]
    -- Run lexer on the prepared file.
    fh <- openFile fname ReadMode
    let st = State {
        _file = fh,
        _yyinput = BS.singleton 0,
        _yycursor = 0,
        _yymarker = 0,
        _yylimit = 0,
        _token = 0,
        %{svars format = "\n@@ = (-1),"; %}
        %{stags format = "\n@@ = (-1),"; %}
        _eof = False
    }
    result <- lexer st []
    hClose fh
    -- Cleanup.
    removeFile fname
    -- Check result.
    when (result /= expect) $ error $ "expected " ++ show expect ++ ", got " ++ show result
    return ()

Prise en charge de l'encodage

Il est nécessaire de comprendre la différence entre les points de code et les unités de code. Un point de code est un identifiant numérique d'un symbole. Une unité de code est la plus petite unité de stockage dans le texte encodé. Un point de code unique peut être représenté par une ou plusieurs unités de code. Dans un encodage à longueur fixe, tous les points de code sont représentés avec le même nombre d'unités de code. Dans un encodage à longueur variable, les points de code peuvent être représentés avec un nombre différent d'unités de code. Notez que la règle "tout" [^] correspond à n'importe quel point de code, mais pas nécessairement à n'importe quelle unité de code (la seule façon de correspondre à n'importe quelle unité de code, quel que soit l'encodage, est la règle par défaut *). Le lexer généré fonctionne avec un flux d'unités de code : yych stocke une unité de code, et YYCTYPE est le type de l'unité de code. Les expressions régulières, en revanche, sont spécifiées en termes de points de code. Lorsque re2hs compile les expressions régulières en automates, il traduit les points de code en unités de code. Ce n'est généralement pas un mappage simple : dans les encodages à longueur variable, une plage de points de code unique peut être traduite en un graphe complexe d'unités de code. Les encodages suivants sont pris en charge :

  • ASCII (activé par défaut). C'est un encodage à longueur fixe avec un espace de code [0-255] et des points de code et des unités de code de 1 octet.
  • EBCDIC (activé avec --ebcdic ou re2c:encoding:ebcdic). C'est un encodage à longueur fixe avec un espace de code [0-255] et des points de code et des unités de code de 1 octet.
  • UCS2 (activé avec --ucs2 ou re2c:encoding:ucs2). C'est un encodage à longueur fixe avec un espace de code [0-0xFFFF] et des points de code et des unités de code de 2 octets.
  • UTF8 (activé avec --utf8 ou re2c:encoding:utf8). C'est un encodage Unicode à longueur variable. La taille de l'unité de code est de 1 octet. Les points de code sont représentés avec 1 à 4 unités de code.
  • UTF16 (activé avec --utf16 ou re2c:encoding:utf16). C'est un encodage Unicode à longueur variable. La taille de l'unité de code est de 2 octets. Les points de code sont représentés avec 1 à 2 unités de code.
  • UTF32 (activé avec --utf32 ou re2c:encoding:utf32). C'est un encodage Unicode à longueur fixe avec un espace de code [0-0x10FFFF] et des points de code et des unités de code de 4 octets.

Le fichier d'inclusion include/unicode_categories.re fournit les définitions re2hs pour les catégories Unicode standard.

L'option --input-encoding spécifie l'encodage du fichier source, qui peut être utilisé pour activer Unico

de littéraux dans les expressions régulières. Par exemple, --input-encoding utf8 indique à re2hs que le fichier source est en UTF8 (cela diffère de --utf8 qui définit le codage du texte d'entrée). L'option --encoding-policy spécifie la manière dont re2hs gère les surrogates Unicode (points de code dans la plage [0xD800-0xDFFF]).

Fichiers inclus

re2hs permet d'inclure d'autres fichiers à l'aide d'un bloc de la forme /*!include:re2c FILE */ ou %{include FILE %}, ou une directive dans un bloc !include FILE ;, où FILE est le chemin d'accès au fichier à inclure. re2hs recherche les fichiers inclus dans le répertoire du fichier incluant et dans les emplacements d'inclusion, qui peuvent être spécifiés avec l'option -I. Les blocs/directives d'inclusion dans re2hs fonctionnent de la même manière que #include en C/C++ : le contenu de FILE est copié tel quel à la place du bloc/directive. Les fichiers inclus peuvent contenir d'autres inclusions. Utilisez l'option --depfile pour suivre les dépendances de build du fichier de sortie par rapport aux fichiers inclus. re2hs fournit des fichiers inclus prédéfinis qui peuvent être trouvés dans le sous-répertoire include/ du projet. Ces fichiers contiennent des définitions qui peuvent être utiles à d'autres projets (telles que les catégories Unicode) et constituent une sorte de bibliothèque standard pour re2hs. Programmes squelettes

Avec l'option -S, --skeleton, re2hs ignore tout le code non-re2hs et génère un programme C autonome qui peut être compilé et exécuté ultérieurement. Le programme se compose du code de l'analyseur lexical et des données d'entrée. Pour chaque automate fini déterministe (AFD) construit (bloc ou condition), re2hs génère un analyseur lexical autonome et deux fichiers : un fichier .input avec des chaînes dérivées de l'AFD et un fichier .keys avec les résultats de correspondance attendus. Le programme exécute chaque analyseur lexical sur le fichier .input correspondant et compare les résultats avec les attentes. Les programmes squelettes sont très utiles pour plusieurs raisons :

  • Ils peuvent vérifier l'exactitude de diverses optimisations de re2hs (les données sont générées tôt dans le processus, avant toute transformation d'AFD).
  • La génération d'un ensemble de données d'entrée avec une bonne couverture peut être utile pour les tests et les benchmarks.
  • La génération de programmes exécutables autonomes permet d'obtenir des cas de test minimisés (le code original peut être volumineux ou avoir beaucoup de dépendances).

La difficulté de générer des données d'entrée réside dans le fait que, sauf pour les cas les plus triviaux, le nombre de chaînes d'entrée possibles est trop grand (même si la longueur de la chaîne est limitée). re2hs résout cette difficulté en générant suffisamment de chaînes pour couvrir la quasi-totalité des transitions de l'AFD. Il utilise l'algorithme suivant. Tout d'abord, il construit un squelette de l'AFD. Pour les codages avec une taille d'unité de code de 1 octet (comme ASCII, UTF-8 et EBCDIC), le squelette est juste une copie exacte de l'AFD d'origine. Pour les codages avec des unités de code multibytes, le squelette est une copie de l'AFD avec certaines transitions omises : à savoir, re2hs prend au plus 256 unités de code pour chaque plage continue discontinue qui correspond à une transition d'AFD. Les valeurs choisies sont réparties uniformément et incluent les limites de plage. Au lieu d'essayer de couvrir tous les chemins possibles dans le squelette (ce qui est irréalisable), re2hs génère suffisamment de chemins pour couvrir toutes les transitions du squelette, et ainsi déclencher les sauts conditionnels correspondants dans l'analyseur lexical. L'implémentation de l'algorithme est limitée à environ 1 Go de transitions et consomme une quantité constante de mémoire (re2hs écrit les données dans un fichier dès qu'elles sont générées).

Visualisation et débogage

Avec l'option -D, --emit-dot, re2hs ne génère pas de code. Au lieu de cela, il publie l'AFD généré au format DOT. Vous pouvez convertir cette publication en une image de l'AFD à l'aide de Graphviz ou d'une autre bibliothèque. Notez que cette option affiche l'AFD final après qu'il a subi un certain nombre d'optimisations et de transformations. Les étapes antérieures peuvent être publiées à l'aide de diverses options de débogage, telles que --dump-nfa, --dump-dfa-raw, etc. (voir la liste complète des options).
