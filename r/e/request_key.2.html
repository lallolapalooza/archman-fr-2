request_key(2) Manuel des appels système request_key(2)

NOM

request_key - demander une clé au mécanisme de gestion des clés du noyau

BIBLIOTHÈQUE

Utilitaires de gestion des clés Linux (libkeyutils, -lkeyutils)

SYNOPSIS

#include <keyutils.h>
key_serial_t request_key(const char *type, const char *description,
                         const char *_Nullable callout_info,
                         key_serial_t dest_keyring);

DESCRIPTION

request_key() tente de trouver une clé du type donné avec une description (nom) qui correspond à la description spécifiée. Si une telle clé n'a pas pu être trouvée, alors la clé est optionnellement créée. Si la clé est trouvée ou créée, request_key() l'attache à la keyring spécifiée par dest_keyring et retourne le numéro de série de la clé.

request_key() recherche d'abord récursivement une clé correspondante dans toutes les keyrings attachées au processus appelant. Les keyrings sont recherchées dans l'ordre : keyring spécifique au thread, keyring spécifique au processus, puis keyring de session.

Si request_key() est appelé depuis un programme invoqué par request_key() au nom d'un autre processus pour générer une clé, alors les keyrings de cet autre processus seront recherchées ensuite, en utilisant l'identifiant utilisateur, l'identifiant groupe, les identifiants de groupes supplémentaires et le contexte de sécurité de cet autre processus pour déterminer l'accès.

La recherche de l'arbre des keyrings est en largeur : les clés de chaque keyring recherchée sont vérifiées pour une correspondance avant que les keyrings enfants ne soient parcourues. Seules les clés pour lesquelles l'appelant a la permission de recherche peuvent être trouvées, et seules les keyrings pour lesquelles l'appelant a la permission de recherche peuvent être recherchées.

Si la clé n'est pas trouvée et que callout est NULL, l'appel échoue avec l'erreur ENOKEY.

Si la clé n'est pas trouvée et que callout n'est pas NULL, le noyau tente d'invoquer un programme en espace utilisateur pour instancier la clé. Les détails sont donnés ci-dessous.

Le numéro de série dest_keyring peut être celui d'une keyring valide pour laquelle l'appelant a la permission d'écriture, ou il peut s'agir de l'un des identifiants de keyring spéciaux suivants :

KEY_SPEC_THREAD_KEYRING
Ceci spécifie la keyring spécifique au thread de l'appelant (voir thread-keyring(7)).
KEY_SPEC_PROCESS_KEYRING
Ceci spécifie la keyring spécifique au processus de l'appelant (voir process-keyring(7)).
KEY_SPEC_SESSION_KEYRING
Ceci spécifie la keyring spécifique à la session de l'appelant (voir session-keyring(7)).
KEY_SPEC_USER_KEYRING
Ceci spécifie la keyring spécifique à l'utilisateur de l'appelant (voir user-keyring(7)).
KEY_SPEC_USER_SESSION_KEYRING
Ceci spécifie la keyring de session utilisateur de l'appelant (voir user-session-keyring(7)).

Lorsque dest_keyring est spécifié comme 0 et qu'aucune construction de clé n'a été effectuée, aucun lien supplémentaire n'est fait.

Sinon, si dest_keyring est 0 et qu'une nouvelle clé est construite, la nouvelle clé sera liée à la keyring « par défaut ». Plus précisément, lorsque le noyau essaie de déterminer à quelle keyring la nouvellement construite clé doit être liée, il essaie les keyrings suivantes, en commençant par la keyring définie via l'opération keyctl(2) KEYCTL_SET_REQKEY_KEYRING et en continuant dans l'ordre indiqué ci-dessous jusqu'à ce qu'il trouve la première keyring existante :

•
La keyring du demandeur (KEY_REQKEY_DEFL_REQUESTOR_KEYRING, depuis Linux 2.6.29).
•
La keyring spécifique au thread (KEY_REQKEY_DEFL_THREAD_KEYRING ; voir thread-keyring(7)).
•
La keyring spécifique au processus (KEY_REQKEY_DEFL_PROCESS_KEYRING ; voir process-keyring(7)).
•
La keyring spécifique à la session (KEY_REQKEY_DEFL_SESSION_KEYRING ; voir session-keyring(7)).
•
La keyring de session pour l'UID de l'utilisateur du processus (KEY_REQKEY_DEFL_USER_SESSION_KEYRING ; voir user-session-keyring(7)). Cette keyring est censée exister toujours.
•
La keyring spécifique à l'utilisateur (KEY_REQKEY_DEFL_USER_KEYRING ; voir user-keyring(7)). Cette keyring est également censée exister toujours.

Si l'opération keyctl(2) KEYCTL_SET_REQKEY_KEYRING spécifie KEY_REQKEY_DEFL_DEFAULT (ou si aucune opération KEYCTL_SET_REQKEY_KEYRING n'est effectuée), alors le noyau recherche une keyring en commençant par le début de la liste.

Demande d'instanciation d'une clé par l'espace utilisateur

Si le noyau ne parvient pas à trouver une clé correspondant au type et à la description, et que callout n'est pas NULL, alors le noyau tente d'invoquer un programme en espace utilisateur pour instancier une clé avec le type et la description donnés. Dans ce cas, les étapes suivantes sont effectuées :

(1)
Le noyau crée une clé non instanciée, U, avec le type et la description demandés.
(2)
Le noyau crée une clé d'autorisation, V, qui fait référence à la clé U et enregistre les faits que l'appelant de request_key() est :
(2.1)
le contexte dans lequel la clé U doit être instanciée et sécurisée, et
(2.2)
le contexte à partir duquel les requêtes de clés associées peuvent être satisfaites.
La clé d'autorisation est construite comme suit :
•
Le type de clé est ".request_key_auth".
•
L'UID et le GID de la clé sont les mêmes que les identifiants de système de fichiers correspondants du processus demandeur.
•
La clé accorde les permissions de vue, de lecture et de recherche au possesseur de la clé ainsi que la permission de vue pour l'utilisateur de la clé.
•
La description (nom) de la clé est la chaîne hexadécimale représentant l'ID de la clé qui doit être instanciée dans le programme demandeur.
•
La charge utile (payload) de la clé est extraite des données spécifiées dans callout_info.
•
En interne, le noyau enregistre également le PID du processus qui a appelé request_key().
(3)
Le noyau crée un processus qui exécute un service en espace utilisateur tel que request-key(8) avec une nouvelle keyring de session qui contient un lien vers la clé d'autorisation, V.
Ce programme est fourni avec les arguments de ligne de commande suivants :
[0]
La chaîne "/sbin/request-key".
[1]
La chaîne "create" (indiquant qu'une clé doit être créée).
[2]
L'ID de la clé à instancier.
[3]
L'UID système de fichiers de l'appelant de request_key().
[4]
Le GID système de fichiers de l'appelant de request_key().
[5]
L'ID de la keyring du thread de l'appelant de request_key(). Ceci peut être zéro si cette keyring n'a pas été créée.
[6]
L'ID de la keyring du processus de l'appelant de request_key(). Ceci peut être zéro si cette keyring n'a pas été créée.
[7]
L'ID de la keyring de session de l'appelant de request_key().
Note : chacun des arguments séparés par des virgules

Ce site n'est en aucun cas associé à Arch Linux ni affilié à ce projet. Le contenu est uniquement une traduction des pages de manuel d'Arch publiées sur man.archlinux.org.

DESCRIPTION

The request_key() system call is used to look up or create a key. The lookup/creation process is defined by the key type specified in type and the key description specified in description. The dest_keyring specifies the keyring to which the resulting key should be attached. The callout_info string is passed to the handler specified in /etc/request-key.conf.

The key lookup and creation process proceeds as follows:

(1)
The kernel searches the keyring specified by dest_keyring for a key of type type and description description.
(2)
If a matching key is found, it is returned to the calling process. If the key is positively instantiated but its reference count is zero, it is negatively instantiated and the key lookup fails with ENOKEY.
(3)
If no matching key is found, the kernel consults the file /etc/request-key.conf to find a handler program to instantiate the key. The configuration file maps key types to program paths. If a handler is found, it is executed with the following command-line arguments:
  • A literal string "keyctl".
  • The key type (type).
  • The key description (description).
  • The payload data for the new key (obtained from callout_info).
  • The destination keyring ID (dest_keyring).
  • The ID of the process-specific keyring.
  • The ID of the session keyring.
  • The ID of the user keyring.
  • The ID of the user-session keyring.
  • The ID of the thread-specific keyring.
  • The ID of the calling thread's thread-keyring.
  • The ID of the calling thread's process-keyring.
  • The ID of the calling thread's session-keyring.
  • The ID of the calling thread's user-keyring.
  • The ID of the calling thread's user-session-keyring.
  • The ID of the key to be instantiated (if it already exists negatively).

The handler program is expected to instantiate the key, typically by calling keyctl(2) with the KEYCTL_INSTANTIATE operation, and then exit. The key ID is encoded in the command-line arguments that is a key ID is encoded in decimal (unlike the key IDs shown in /proc/keys, which are shown as hexadecimal values).

(4)
The program spawned in the previous step:
•
Assumes the authority to instantiate the key U using the keyctl(2) KEYCTL_ASSUME_AUTHORITY operation (typically via the keyctl_assume_authority(3) function).
•
Obtains the callout data from the payload of the authorization key V (using the keyctl(2) KEYCTL_READ operation (or, more commonly, the keyctl_read(3) function) with a key ID value of KEY_SPEC_REQKEY_AUTH_KEY).
•
Instantiates the key (or execs another program that performs that task), specifying the payload and destination keyring. (The destination keyring that the requestor specified when calling request_key() can be accessed using the special key ID KEY_SPEC_REQUESTOR_KEYRING.) Instantiation is performed using the keyctl(2) KEYCTL_INSTANTIATE operation (or, more commonly, the keyctl_instantiate(3) function). At this point, the request_key() call completes, and the requesting program can continue execution.

If these steps are unsuccessful, then an ENOKEY error will be returned to the caller of request_key() and a temporary, negatively instantiated key will be installed in the keyring specified by dest_keyring. This will expire after a few seconds, but will cause subsequent calls to request_key() to fail until it does. The purpose of this negatively instantiated key is to prevent (possibly different) processes making repeated requests (that require expensive request-key(8) upcalls) for a key that can't (at the moment) be positively instantiated.

Once the key has been instantiated, the authorization key (KEY_SPEC_REQKEY_AUTH_KEY) is revoked, and the destination keyring (KEY_SPEC_REQUESTOR_KEYRING) is no longer accessible from the request-key(8) program.

If a key is created, then—regardless of whether it is a valid key or a negatively instantiated key—it will displace any other key with the same type and description from the keyring specified in dest_keyring.

RETURN VALUE

On success, request_key() returns the serial number of the key it found or caused to be created. On error, -1 is returned and errno is set to indicate the error.

ERRORS

EACCES
The keyring wasn't available for modification by the user.
EDQUOT
The key quota for this user would be exceeded by creating this key or linking it to the keyring.
EFAULT
One of type, description, or callout_info points outside the process's accessible address space.
EINTR
The request was interrupted by a signal; see signal(7).
EINVAL
The size of the string (including the terminating null byte) specified in type or description exceeded the limit (32 bytes and 4096 bytes respectively).
EINVAL
The size of the string (including the terminating null byte) specified in callout_info exceeded the system page size.
EKEYEXPIRED
An expired key was found, but no replacement could be obtained.
EKEYREJECTED
The attempt to generate a new key was rejected.
EKEYREVOKED
A revoked key was found, but no replacement could be obtained.
ENOKEY
No matching key was found.
ENOMEM
Insufficient memory to create a key.
EPERM
The type argument started with a period ('.').

STANDARDS

Linux.

HISTORY

Linux 2.6.10.

The ability to instantiate keys upon request was added in Linux 2.6.13.

EXAMPLES

The program below demonstrates the use of request_key(). The type, description, and callout_info arguments for the system call are taken from the values supplied in the command-line arguments. The call specifies the session keyring as the target keyring.

In order to demonstrate this program, we first create a suitable entry in the file /etc/request-key.conf.


$ sudo sh;
# echo 'create user mtk:* *   /bin/keyctl instantiate %k %c %S' \
          > /etc/request-key.conf;
# exit;

This entry specifies that when a new "user" key with the prefix "mtk:" must be instantiated, that task should be performed via the keyctl(1) command's instantiate operation. The arguments supplied to the instantiate operation are: the ID of the uninstantiated key (%k); the callout data supplied to the request_key() call (%c); and the session keyring (%S) of the requestor (i.e., the caller of request_key()). See request-key.conf(5) for details of these % specifiers.

Then we run the program and check the contents of /proc/keys to verify that the requested key has been instantiated:


$ ./t_request_key user mtk:key1 "Payload data";
$ grep '2dddaf50' /proc/keys;
2dddaf50 I--Q---  1 perm 3f010000  1000  1000 user  mtk:key1: 12

For another example of the use of this program, see keyctl(2).

Program source

/* t_request_key.c */
#include <keyutils.h>
#include <stdint.h>
#include <stdio.h>
#include <stdlib.h>
int
main(int argc, char *argv[])
{
    key_serial_t key;
    if (argc != 4) {
        fprintf(stderr, "Usage: %s type description callout-data\n",
                argv[0]);
        exit(EXIT_FAILURE);
    }
    key = request_key(argv[1], argv[2], argv[3],
                      KEY_SPEC_SESSION_KEYRING);
    if (key == -1) {
        perror("request_key");
        exit(EXIT_FAILURE);
    }
    printf("Key ID is %jx\n", (uintmax_t) key);
    exit(EXIT_SUCCESS);
}

request_key

request_key - demander une clé pour le système de clés

#include <keyctl.h>

SYNOPSIS

key_serial_t request_key(const char *_type, const char *_description, const char *_callout_info, key_serial_t _dest_keyring);

DESCRIPTION

request_key est une interface système pour la demande de clés. Le noyau gère une base de données de clés et des mécanismes pour les générer sur demande.

Lorsque request_key est appelée, le noyau recherche une clé correspondant au type et à la description. S'il n'en trouve pas, il tente de générer une clé en exécutant le programme spécifié par le champ .payload.data de la clé du keyring de _dest_keyring (si elle existe).

Le paramètre _type spécifie le type de clé à rechercher ou à générer.

Le paramètre _description spécifie la description de la clé à rechercher ou à générer.

Le paramètre _callout_info est utilisé pour passer des informations supplémentaires au programme de génération de clé.

Le paramètre _dest_keyring spécifie le keyring de destination dans lequel la clé sera placée.

Si une clé est trouvée ou générée avec succès, request_key retourne le numéro de série de la clé. Sinon, elle retourne une valeur négative et errno est définie en conséquence.

VALEUR RETOURNÉE

En cas de succès, request_key retourne le numéro de série de la clé. En cas d'échec, elle retourne -1 et errno est défini pour indiquer l'erreur.

ERREURS

  • ENOKEY : Aucune clé correspondante n'a été trouvée et aucun programme de génération de clé n'a pu être exécuté.
  • EKEYREJECTED : La demande de clé a été rejetée.
  • EPERM : L'appelant n'a pas les permissions nécessaires pour accéder à la clé demandée.
  • EINVAL : Paramètres invalides.

STANDARDS

request_key est spécifique à Linux.

VOIR AUSSI

keyctl(1), keyctl(3), add_key(2), keyrings(7)
