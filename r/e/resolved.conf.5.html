RESOLVED.CONF(5) resolved.conf RESOLVED.CONF(5)

NOM

resolved.conf, resolved.conf.d — Fichiers de configuration de la résolution de noms réseau

SYNOPSIS

/etc/systemd/resolved.conf
/run/systemd/resolved.conf
/usr/local/lib/systemd/resolved.conf
/usr/lib/systemd/resolved.conf
/etc/systemd/resolved.conf.d/*.conf
/run/systemd/resolved.conf.d/*.conf
/usr/local/lib/systemd/resolved.conf.d/*.conf
/usr/lib/systemd/resolved.conf.d/*.conf

DESCRIPTION

Ces fichiers de configuration contrôlent la résolution des noms DNS et LLMNR locaux.

DIRECTORIES DE CONFIGURATION ET PRÉCÉDENCE

La configuration par défaut est définie lors de la compilation, donc la configuration n'est nécessaire que lorsqu'il est nécessaire de s'écarter de ces défauts. Le fichier de configuration principal est chargé à partir de l'un des répertoires listés par ordre de priorité, seul le premier fichier trouvé est utilisé : /etc/systemd/, /run/systemd/, /usr/local/lib/systemd/ [1], /usr/lib/systemd/. La version du fournisseur du fichier contient des entrées commentées montrant les valeurs par défaut comme guide pour l'administrateur. Des remplacements locaux peuvent également être créés en créant des fichiers "drop-in", comme décrit ci-dessous. Le fichier de configuration principal peut également être modifié à cette fin (ou une copie dans /etc/ s'il est distribué sous /usr/), cependant, l'utilisation de fichiers "drop-in" pour la configuration locale est recommandée par rapport aux modifications du fichier de configuration principal.

En plus du fichier de configuration principal, des fragments de configuration "drop-in" sont lus à partir de /usr/lib/systemd/*.conf.d/, /usr/local/lib/systemd/*.conf.d/, et /etc/systemd/*.conf.d/. Ces fichiers "drop-in" ont une priorité plus élevée et remplacent le fichier de configuration principal. Les fichiers dans les sous-répertoires de configuration *.conf.d/ sont triés par leur nom de fichier par ordre lexicographique, quel que soit le sous-répertoire dans lequel ils résident. Lorsque plusieurs fichiers spécifient la même option, pour les options qui n'acceptent qu'une seule valeur, l'entrée dans le fichier trié en dernier a la priorité, et pour les options qui acceptent une liste de valeurs, les entrées sont collectées au fur et à mesure qu'elles apparaissent dans les fichiers triés.

Lorsque des paquets nécessitent de personnaliser la configuration, ils peuvent installer des fichiers "drop-in" sous /usr/. Les fichiers dans /etc/ sont réservés à l'administrateur local, qui peut utiliser cette logique pour remplacer les fichiers de configuration installés par les paquets du fournisseur. Les fichiers "drop-in" doivent être utilisés pour remplacer les fichiers "drop-in" des paquets, car le fichier de configuration principal a une priorité inférieure. Il est recommandé de préfixer tous les noms de fichiers dans ces sous-répertoires avec un numéro à deux chiffres et un tiret, pour simplifier l'ordre. Cela définit également un concept de priorités pour les fichiers "drop-in" afin de permettre aux fournisseurs d'OS de distribuer des fichiers "drop-in" dans une plage spécifique inférieure à la plage utilisée par les utilisateurs. Cela devrait réduire le risque que les fichiers "drop-in" des paquets remplacent accidentellement les fichiers "drop-in" définis par les utilisateurs. Il est recommandé d'utiliser la plage 10-40 pour les fichiers "drop-in" dans /usr/ et la plage 60-90 pour les fichiers "drop-in" dans /etc/ et /run/, afin de garantir que les fichiers "drop-in" locaux et transitoires prennent la priorité sur les fichiers "drop-in" distribués par le fournisseur de l'OS.

Pour désactiver un fichier de configuration fourni par le fournisseur, la méthode recommandée consiste à placer un lien symbolique vers /dev/null dans le répertoire de configuration de /etc/, avec le même nom de fichier que le fichier de configuration du fournisseur.

OPTIONS

Les options suivantes sont disponibles dans la section [Resolve] :

DNS=

Une liste séparée par des espaces d'adresses IPv4 et IPv6 à utiliser comme serveurs DNS système. Chaque adresse peut éventuellement prendre un numéro de port séparé par ":", un nom ou un index d'interface réseau séparé par "%", et un nom d'indication de serveur (SNI) séparé par "#". Lorsque l'adresse IPv6 est spécifiée avec un numéro de port, l'adresse doit être entre crochets. C'est-à-dire que les formats complets acceptables sont "111.222.333.444:9953%ifname#example.com" pour IPv4 et "[1111:2222::3333]:9953%ifname#example.com" pour IPv6. Les requêtes DNS sont envoyées en parallèle à l'un des serveurs DNS listés vers des serveurs DNS appropriés par lien acquis auprès de systemd-networkd.service(8) ou définis à l'exécution par des applications externes. Pour des raisons de compatibilité, si ce paramètre n'est pas spécifié, les serveurs DNS listés dans /etc/resolv.conf sont utilisés à la place, si ce fichier existe et si des serveurs y sont configurés. Ce paramètre est par défaut une liste vide.

Ajouté dans la version 213.

FallbackDNS=

Une liste séparée par des espaces d'adresses IPv4 et IPv6 à utiliser comme serveurs DNS de secours. Veuillez consulter DNS= pour le format acceptable des adresses. Tous les serveurs DNS par lien obtenus à partir de systemd-networkd.service(8) ont la priorité sur ce paramètre, tout comme les serveurs définis via DNS= ci-dessus ou /etc/resolv.conf. Ce paramètre n'est donc utilisé que si aucune autre information de serveur DNS n'est connue. Si cette option n'est pas donnée, une liste de serveurs DNS compilée en interne est utilisée à la place.

Ajouté dans la version 216.

Domains=

Une liste séparée par des espaces de domaines, éventuellement préfixée par "~", utilisée pour deux objectifs distincts décrits ci-dessous. Par défaut, la liste est vide.

Tous les domaines non préfixés par "~" sont utilisés comme suffixes de recherche lors de la résolution de noms d'hôtes à étiquette unique (noms de domaine ne contenant aucun point), afin de les qualifier en noms de domaine entièrement qualifiés (FQDN). Ces "domaines de recherche" sont strictement traités dans l'ordre où ils sont spécifiés, jusqu'à ce que le nom avec le suffixe ajouté soit trouvé. Pour des raisons de compatibilité, si ce paramètre n'est pas spécifié, les domaines de recherche listés dans /etc/resolv.conf avec le mot-clé search sont utilisés à la place, si ce fichier existe et si des domaines y sont configurés.

Les domaines préfixés par "~" sont appelés "domaines de routage uniquement". Tous les domaines listés ici (à la fois les domaines de recherche et les domaines de routage uniquement après suppression du préfixe "~") définissent un chemin de recherche qui dirige de préférence les requêtes DNS vers cette interface. Ce chemin de recherche n'a d'effet que lorsque des serveurs DNS appropriés par lien sont connus. Ces serveurs peuvent être définis via le paramètre DNS= (voir ci-dessus) et dynamiquement au moment de l'exécution, par exemple à partir de baux DHCP. Si aucun serveur DNS par lien n'est connu, les domaines de routage uniquement n'ont aucun effet.

Utilisez la construction "~." (qui est composée de "~" pour indiquer un domaine de routage uniquement et "." pour indiquer le domaine racine DNS qui est le suffixe implicite de tous les domaines DNS) pour utiliser de préférence les serveurs DNS définis pour ce lien pour tous les domaines.

Voir "Protocoles et Routage" dans systemd-resolved.service(8) pour les détails sur la façon dont les domaines de recherche et de routage sont utilisés.

Notez que la configuration du domaine MulticastDNS "local" en tant que domaine de recherche ou de routage a pour effet de router les recherches pour ce domaine vers le DNS unicast classique. Cela peut être utilisé pour assurer la compatibilité avec les installations héritées qui utilisent ce domaine dans un contexte DNS unicast, contre l'attribution IANA de ce domaine à des fins de MulticastDNS pures. Les domaines de recherche et de routage sont un concept du DNS unicast, ils ne peuvent pas être utilisés pour résoudre des recherches à étiquette unique via MulticastDNS.

Ajouté dans la version 229.

LLMNR=

Prend un argument booléen ou "resolve". Contrôle le support de la résolution de noms multicast en lien local (LLMNR) (RFC 4795[2]) sur l'hôte local. Si vrai, active le support complet de réponseur et de résolveur LLMNR. Si faux, désactive les deux. Si défini sur "resolve", seul le support de résolution est activé, mais la réponse est désactivée. Notez que systemd-networkd.service(8) maintient également les paramètres LLMNR par lien. LLMNR sera activé sur un lien uniquement si le paramètre par lien et le paramètre global sont activés.

Ajouté dans la version 216.

MulticastDNS=

Prend un argument booléen ou "resolve". Contrôle le support de Multicast DNS (RFC 6762[3]) sur l'hôte local. Si vrai, active le support complet de réponseur et de résolveur Multicast DNS. Si faux, désactive les deux. Si défini sur "resolve", seul le support de résolution est activé, mais la réponse est désactivée. Notez que systemd-networkd.service(8)

DNSSEC=

Accepte un argument booléen ou « allow-downgrade ».

Si défini sur true, toutes les recherches DNS sont validées localement par DNSSEC (à l'exclusion de LLMNR et Multicast DNS). Si la réponse à une requête de recherche est détectée comme invalide, un échec de recherche est renvoyé aux applications. Notez que ce mode nécessite un serveur DNS qui prend en charge DNSSEC. Si le serveur DNS ne prend pas correctement en charge DNSSEC, toutes les validations échoueront.

Si défini sur « allow-downgrade », la validation DNSSEC est tentée, mais si le serveur ne prend pas correctement en charge DNSSEC, le mode DNSSEC est automatiquement désactivé. Notez que ce mode rend la validation DNSSEC vulnérable aux attaques par « downgrade », où un attaquant pourrait être capable de déclencher un passage au mode non-DNSSEC en synthétisant une réponse DNS suggérant que DNSSEC n'était pas pris en charge.

Si défini sur false, les recherches DNS ne sont pas validées par DNSSEC.

Notez que la validation DNSSEC nécessite la récupération de données DNS supplémentaires, et entraîne donc une légère pénalité de temps de recherche DNS.

DNSSEC nécessite la connaissance des « trust anchors » pour prouver l'intégrité des données. Le trust anchor pour le domaine racine d'Internet est intégré dans le résolveur, d'autres trust anchors peuvent être définis avec dnssec-trust-anchors.d(5). Les trust anchors peuvent changer à intervalles réguliers, et les anciens trust anchors peuvent être révoqués. Dans un tel cas, la validation DNSSEC n'est pas possible tant que de nouveaux trust anchors ne sont pas configurés localement ou que le paquet logiciel du résolveur n'est pas mis à jour avec le nouveau trust anchor racine. En effet, lorsque le trust anchor intégré est révoqué et que DNSSEC= est true, toutes les recherches ultérieures échoueront, car il ne sera plus possible de prouver si les recherches sont correctement signées ou valablement non signées. Si DNSSEC= est défini sur « allow-downgrade », le résolveur désactivera automatiquement la validation DNSSEC dans un tel cas.

Les programmes clients qui recherchent des données DNS seront informés si les recherches ont pu être vérifiées à l'aide de DNSSEC, ou si les données renvoyées n'ont pas pu être vérifiées (soit parce que les données ont été trouvées non signées dans le DNS, soit parce que le serveur DNS ne prenait pas en charge DNSSEC ou qu'aucun trust anchors approprié n'était connu). Dans ce dernier cas, il est supposé que les programmes clients emploient un schéma secondaire pour valider les données DNS renvoyées, si cela est requis.

Il est recommandé de définir DNSSEC= sur true sur les systèmes où il est connu que le serveur DNS prend correctement en charge DNSSEC, et où les mises à jour logicielles ou des trust anchors ont lieu régulièrement. Sur les autres systèmes, il est recommandé de définir DNSSEC= sur « allow-downgrade ».

En plus de ce réglage global DNSSEC, systemd-networkd.service(8) maintient également des réglages DNSSEC par lien. Pour les serveurs DNS système (voir ci-dessus), seul le réglage global DNSSEC est effectif. Pour les serveurs DNS par lien, le réglage par lien est effectif, sauf s'il n'est pas défini, auquel cas le réglage global est utilisé à la place.

Les zones DNS privées de site entrent généralement en conflit avec le fonctionnement de DNSSEC, à moins qu'un trust anchor négatif (si la zone privée n'est pas signée) ou positif (si la zone privée est signée) ne soit configuré pour elles. Si le mode « allow-downgrade » est sélectionné, une tentative est faite pour détecter les zones DNS privées de site à l'aide de domaines de premier niveau (TLD) qui ne sont pas connus par le serveur racine DNS. Cette logique ne fonctionne pas dans toutes les configurations de zones privées.

Par défaut : « no ».

Ajouté dans la version 229.

DNSOverTLS=

Accepte un argument booléen ou « opportunistic ». Si true, toutes les connexions au serveur seront chiffrées. Notez que ce mode nécessite un serveur DNS qui prend en charge DNS-over-TLS et possède un certificat valide. Si le nom d'hôte a été spécifié dans DNS= en utilisant le format « address#server_name », il est utilisé pour valider son certificat et également pour activer l'indication du nom du serveur (SNI) lors de l'ouverture d'une connexion TLS. Sinon, le certificat est vérifié par rapport à l'adresse IP du serveur. Si le serveur DNS ne prend pas en charge DNS-over-TLS, toutes les requêtes DNS échoueront.

Lorsqu'il est défini sur « opportunistic », les requêtes DNS sont tentées d'être envoyées chiffrées avec DNS-over-TLS. Si le serveur DNS ne prend pas en charge TLS, DNS-over-TLS est désactivé. Notez que ce mode rend DNS-over-TLS vulnérable aux attaques par « downgrade », où un attaquant pourrait être capable de déclencher un passage au mode non chiffré en synthétisant une réponse suggérant que DNS-over-TLS n'était pas pris en charge. Si défini sur false, les recherches DNS sont envoyées sur UDP.

Notez que DNS-over-TLS nécessite l'envoi de données supplémentaires pour établir une connexion chiffrée, et entraîne donc une légère pénalité de temps de recherche DNS.

Notez que dans le mode « opportunistic », le résolveur n'est pas capable d'authentifier le serveur, il est donc vulnérable aux attaques de type « man-in-the-middle ».

En plus de ce réglage global DNSOverTLS=, systemd-networkd.service(8) maintient également des réglages DNSOverTLS= par lien. Pour les serveurs DNS système (voir ci-dessus), seul le réglage global DNSOverTLS= est effectif. Pour les serveurs DNS par lien, le réglage par lien est effectif, sauf s'il n'est pas défini, auquel cas le réglage global est utilisé à la place.

Par défaut : « no ».

Ajouté dans la version 239.

Cache=

Accepte un booléen ou « no-negative » comme argument. Si « yes » (par défaut), la résolution d'un nom de domaine déjà interrogé précédemment renverra le résultat précédent tant qu'il est toujours valide, et n'entraînera donc pas une nouvelle requête réseau. Soyez conscient que désactiver la mise en cache entraîne une pénalité de performance, particulièrement élevée lorsque DNSSEC est utilisé. Si « no-negative », seules les réponses positives sont mises en cache.

Notez que la mise en cache est désactivée par défaut pour les serveurs DNS locaux à l'hôte. Voir CacheFromLocalhost= pour plus de détails.

Ajouté dans la version 231.

CacheFromLocalhost=

Accepte un argument booléen. Si « no » (par défaut), et que la réponse provient d'une adresse IP locale à l'hôte (telle que 127.0.0.1 ou ::1), le résultat ne sera pas mis en cache afin d'éviter une duplication potentielle de la mise en cache locale.

Ajouté dans la version 248.

DNSStubListener=

Accepte un argument booléen ou l'un des termes « udp » et « tcp ». Si « udp », un stub resolver DNS écoutera les requêtes UDP sur les adresses 127.0.0.53 et 127.0.0.54, port 53. Si « tcp », le stub écoutera les requêtes TCP sur les mêmes adresses et port. Si « yes » (par défaut), le stub écoute les requêtes UDP et TCP. Si « no », l'écouteur stub est désactivé.

Le stub resolver DNS sur 127.0.0.53 fournit l'ensemble complet des fonctionnalités du résolveur local, y compris l'offre de résolution LLMNR/MulticastDNS. Le stub resolver DNS sur 127.0.0.54 fournit un résolveur plus limité, qui fonctionne uniquement en mode « proxy », c'est-à-dire qu'il transmettra la plupart des messages DNS relativement inchangés aux serveurs DNS en amont actuels et retour, mais n'essaiera pas de traiter les messages localement, et par conséquent ne valide pas DNSSEC, ni n'offre LLMNR/MulticastDNS. (Il se traduira par une communication DNS-over-TLS si nécessaire.)

Notez que l'écouteur stub DNS est désactivé implicitement lorsque son adresse et son port d'écoute sont déjà utilisés.

Ajouté dans la version 232.

RefuseRecordTypes=

Accepte une liste de types d'enregistrements DNS séparés par des espaces. Les types d'enregistrements spécifiés dans chaque requête seront refusés. Cette option peut être spécifiée plusieurs fois. Si une chaîne vide est spécifiée, toutes les affectations précédentes sont effacées.

Exemples :

RefuseRecordTypes=AAAA SRV TXT

Notez que pour refuser complètement l'enregistrement AAAA (contrairement à SRV, TXT, etc.), veuillez également désactiver la pile IPv6 dans le noyau avec « sysctl -w net.ipv6.conf.all.disable_ipv6=1 ».

Ajouté dans la version 258.

DNSStubListenerExtra=

Accepte une adresse IPv4 ou IPv6 sur laquelle écouter. L'adresse peut être éventuellement préfixée par un nom de protocole (« udp » ou « tcp ») séparé par « : ». Si le protocole n'est pas spécifié, le service écoutera sur UDP et TCP. Il peut également être éventuellement suffixé par un numéro de port numérique avec le séparateur « : ». Lorsqu'une adresse IPv6 est spécifiée avec un numéro de port, l'adresse doit être entre crochets. Si le port n'est pas spécifié, le service utilise le port 53. Notez que ceci est indépendant du stub DNS principal configuré avec DNSStubListener=, et configure seulement des sockets **supplémentaires** sur lesquels écouter. Cette option peut être spécifiée plusieurs fois. Si une chaîne vide est affectée, toutes les affectations précédentes sont effacées. Par défaut, non défini.

Exemples :

DNSStubListenerExtra=192.168.10.10
DNSStubListenerExtra=2001:db8:0:f102::10
DNSStubListenerExtra=192.168.10.11:9953
DNSStubListenerExtra=[2001:db8:0:f102::11]:9953
DNSStubListenerExtra=tcp:192.168.10.12
DNSStubListenerExtra=udp:2001:db8:0:f102::12
DNSStubListenerExtra=tcp:192.168.10.13:9953
DNSStubListenerExtra=udp:[2001:db8:0:f102::13]:9953

Ajouté dans la version 247.

ReadEtcHosts=

Accepte un argument booléen. Si « yes » (par défaut), systemd-resolved lira le fichier /etc/hosts, et essaiera de résoudre les hôtes ou adresses en utilisant les entrées du fichier avant d'envoyer une requête aux serveurs DNS.

Ajouté dans la version 240.

ResolveUnicastSingleLabel=

Accepte un argument booléen. Lorsque false (par défaut), systemd-resolved ne résoudra pas les requêtes A et AAAA pour les noms à étiquette unique via le DNS classique. Notez que de tels noms peuvent encore être résolus si des domaines de recherche sont spécifiés (voir Domains= ci-dessus), ou via d'autres mécanismes, en particulier via LLMNR ou depuis /etc/hosts. Lorsqu'il est true, les requêtes pour les noms à étiquette unique seront transmises aux serveurs DNS globaux même si aucun domaine de recherche n'est défini.

Cette option est fournie pour la compatibilité avec les configurations où les serveurs DNS publics ne sont pas utilisés. La transmission des noms à étiquette unique à des serveurs hors de votre contrôle n'est pas conforme aux normes, voir **Déclaration IAB**[4], et peut créer un risque pour la vie privée et la sécurité.

Ajouté dans la version 246.

StaleRetentionSec=SECONDES

Accepte une valeur de durée, qui détermine la durée pendant laquelle les enregistrements de ressources DNS peuvent être conservés dans le cache au-delà de leur Durée de Vie (TTL). Cela permet à ces enregistrements d'être renvoyés comme enregistrements obsolètes. Par défaut, cette valeur est fixée à zéro, ce qui signifie que les enregistrements de ressources DNS ne sont pas stockés dans le cache une fois que leur TTL a expiré.

Ceci est utile lorsqu'une défaillance du serveur DNS se produit ou devient inaccessible. Dans de tels cas, systemd-resolved(8) continue d'utiliser les enregistrements obsolètes pour répondre aux requêtes DNS, particulièrement lorsqu'aucune réponse valide ne peut être obtenue auprès des serveurs DNS en amont. Cependant, cela ne s'applique pas aux réponses NXDOMAIN, car celles-ci sont toujours des réponses parfaitement valides. Cette fonctionnalité améliore la résilience face aux défaillances et aux pannes de l'infrastructure DNS.

systemd-resolved tente toujours d'atteindre les serveurs DNS en amont en premier, avant de fournir des données obsolètes à l'application cliente. Si cette fonctionnalité est activée, le cache ne sera pas vidé lors du changement de serveurs.

Ajouté dans la version 254.
