NOM

re2v - générer des analyseurs lexicaux rapides pour V

SYNOPSIS

re2v [ OPTIONS ] [ AVERTISSEMENTS ] ENTRÉE

L'entrée peut être un fichier ou - pour l'entrée standard.

INTRODUCTION

re2v fonctionne comme un préprocesseur. Il lit le fichier d'entrée (qui est généralement un programme en V, mais peut être n'importe quoi) et recherche des blocs de code encadrés par des marqueurs spéciaux de début et de fin. Le texte en dehors de ces blocs est copié tel quel dans le fichier de sortie. Le contenu des blocs est traité par re2v. Il les traduit en code V et édite le code généré à la place du bloc.

Voici un exemple de petit programme qui vérifie si une chaîne donnée contient un nombre décimal :

// re2v $INPUT -o $OUTPUT -i
fn lex(yyinput string) {
    mut yycursor := 0
    /*!re2c
        re2c:yyfill:enable = 0;
        [1-9][0-9]* { return }
        *           { panic("erreur !") }
    */
}
fn main() {
    lex("1234\x00")
}

Dans la sortie, re2v a remplacé le bloc du milieu par le code généré :

// Code généré par re2v, NE PAS MODIFIER.
// re2v $INPUT -o $OUTPUT -i
fn lex(yyinput string) {
    mut yycursor := 0
    mut yych := 0
    yych = yyinput[yycursor]
    match yych {
        0x31...0x39 { unsafe { goto yy2 } }
        else { unsafe { goto yy1 } }
    }
yy1:
    yycursor += 1
    panic("erreur !")
yy2:
    yycursor += 1
    yych = yyinput[yycursor]
    match yych {
        0x30...0x39 { unsafe { goto yy2 } }
        else { unsafe { goto yy3 } }
    }
yy3:
    return
}
fn main() {
    lex("1234\x00")
}

BASES

Un programme re2v se compose d'une séquence de blocs entrecoupés de code dans le langage cible. Un bloc peut contenir des définitions, des configurations, des règles, des actions et des directives dans n'importe quel ordre :

nom = expression-régulière ;
Une définition lie nom à expression-régulière. Les noms peuvent contenir des caractères alphanumériques et le trait de soulignement. La section expressions régulières donne un aperçu de la syntaxe de re2v pour les expressions régulières. Une fois défini, le nom peut être utilisé dans d'autres expressions régulières et dans les règles. La récursion dans les définitions nommées n'est pas autorisée, et chaque nom devrait être défini avant d'être utilisé. Un bloc hérite des définitions nommées du portée globale. Redéfinir un nom qui existe dans la portée actuelle est une erreur.
configuration = valeur ;
Une configuration permet de modifier le comportement de re2v et de personnaliser le code généré. Pour une liste complète des configurations supportées par re2v, consultez la section configurations. Selon la configuration, la valeur peut être un mot-clé, un nombre entier non négatif ou une chaîne de caractères sur une seule ligne qui doit être entourée de guillemets doubles ou simples, sauf si elle est composée de caractères alphanumériques. Un bloc hérite des configurations de la portée globale et peut les redéfinir ou en ajouter de nouvelles. Les configurations définies à l'intérieur d'un bloc affectent tout le bloc, même si elles apparaissent à la fin de celui-ci.
expression-régulière code
Une règle lie une expression-régulière à son action sémantique (un bloc de code entre accolades, ou un bloc de code qui commence par := et se termine sur une nouvelle ligne suivie d'un caractère non blanc). Si l'expression-régulière correspond, le code associé est exécuté. Si plusieurs règles correspondent, la correspondance la plus longue a la priorité. Si plusieurs règles correspondent à la même chaîne, la première occurrence a la priorité. Il existe deux règles spéciales : la règle par défaut * et la règle de fin d'entrée $. La règle par défaut devrait toujours être définie ; elle a la priorité la plus basse, quel que soit son emplacement dans le bloc, et elle correspond à n'importe quel unité de code (pas nécessairement un caractère valide, voir la section support de l'encodage). La règle de fin d'entrée devrait être définie si la méthode correspondante pour la gestion de la fin d'entrée est utilisée. Avec les conditions de départ, les règles ont une syntaxe plus complexe.
!action code
Une action lie un bloc de code défini par l'utilisateur à un endroit particulier dans la machine à états finis générée (de la même manière que les actions sémantiques lient du code aux états finaux). Voir la section actions pour une liste complète des actions prédéfinies.
!directive ;
Une directive est l'une des instructions spéciales prédéfinies. Chaque directive a un but unique. Voir la section directives pour plus de détails.

Blocs

Les marqueurs de début et de fin de bloc sont soit /*!re2c et */, soit %{ et %} (les deux styles sont supportés). À partir de la version 2.2, les blocs peuvent avoir des noms optionnels qui permettent de les référencer dans d'autres blocs. Il existe différents types de blocs :

/*!re2c[:<nom>] ... */ ou %{[:<nom>] ... %}
Un bloc global contient des définitions, des configurations, des règles et des directives. re2v compile les expressions régulières associées à chaque règle en un automate fini déterministe, l'encode sous forme de sauts conditionnels dans le langage cible et remplace le bloc par le code généré. Les noms et les configurations définis dans un bloc global sont ajoutés à la portée globale et deviennent visibles pour les blocs ultérieurs. Au début du programme, la portée globale est initialisée avec les options de la ligne de commande.
/*!local:re2c[:<nom>] ... */ ou %{local[:<nom>] ... %}
Un bloc local est similaire à un bloc global, mais les noms et les configurations qu'il contient ont une portée locale (ils n'affectent pas les autres blocs).
/*!rules:re2c[:<nom>] ... */ ou %{rules[:<nom>] ... %}
Un bloc de règles est similaire à un bloc local, mais il ne génère aucun code par lui-même, ni n'ajoute de définitions à la portée globale - il est destiné à être réutilisé dans d'autres blocs. C'est une façon de partager du code (plus de détails dans la section blocs réutilisables). Avant la version 2.2 de re2v, les blocs de règles nécessitaient l'option -r --reusable.
/*!use:re2c[:<nom>] ... */ ou %{use[:<nom>] ... %}
Un bloc d'utilisation qui référence un bloc de règles défini précédemment. Si un nom est spécifié, re2v recherche des blocs de règles portant ce nom. Sinon, le bloc de règles le plus récent est utilisé (nommé ou non nommé). Un bloc d'utilisation peut ajouter ses propres définitions, configurations et règles, qui sont ajoutées à celles du bloc de règles référencé. Avant la version 2.2 de re2v, les blocs d'utilisation nécessitaient l'option -r --reusable.
/*!max:re2c[:<nom1>[:<nom2>...]] ... */ ou %{max[:<nom1>[:<nom2>...]] ... %}
Un bloc qui génère la définition YYMAXFILL. Une liste optionnelle de noms de blocs spécifie quels blocs doivent être inclus lors du calcul de la valeur YYMAXFILL (si la liste est vide, tous les blocs sont inclus). Par défaut, le code généré est une macro-définition pour C (#define YYMAXFILL <n>), ou une variable globale pour Go (var YYMAXFILL int = <n>). Il peut être personnalisé avec une configuration optionnelle format qui spécifie une chaîne de modèle où @@{max} (ou @@ en abrégé) est remplacé par la valeur numérique de YYMAXFILL.
/*!maxnmatch:re2c[:<nom1>[:<nom2>...]] ... */ ou %{maxnmatch[:<nom1>[:<nom2>...]] ... %}
Un bloc qui génère la définition YYMAXNMATCH (nécessite l'option -P --posix-captures). Une liste optionnelle de noms de blocs spécifie quels blocs doivent être inclus lors du calcul de la valeur YYMAXNMATCH (si la liste est vide, tous les blocs sont inclus). Par défaut, le code généré est une macro-définition pour C (#define YYMAXNMATCH <n>), ou une variable globale pour Go (var YYMAXNMATCH int = <n>). Il peut être personnalisé avec une configuration optionnelle format qui spécifie une chaîne de modèle où @@{max} (ou @@ en abrégé) est remplacé par la valeur numérique de YYMAXNMATCH.

Blocs

Les blocs sont des portions de code qui sont soit des instructions pour re2c, soit des fragments de code à inclure dans le fichier de sortie.

/*!variable:re2c[:<nom1>[:<nom2>...]] ... %{
Blocs qui spécifient un morceau de code modèle qui est développé pour chaque variable de balise s/m générée par re2v. Une liste facultative de noms de blocs spécifie quels blocs doivent être inclus lors du calcul de l'ensemble des variables de balise (si la liste est vide, tous les blocs sont inclus). Il existe deux configurations facultatives : format et séparateur. La configuration format spécifie une chaîne modèle où @@{balise} (ou @@ en abrégé) est remplacé par le nom de chaque variable de balise. La configuration séparateur spécifie un morceau de code utilisé pour joindre les morceaux de format générés pour différentes variables de balise.
/*!svars:re2c[:<nom1>[:<nom2>...]] ... */, /*!mvars:re2c[:<nom1>[:<nom2>...]] ... */ ou %{svars[:<nom1>[:<nom2>...]] ... %}, %{mvars[:<nom1>[:<nom2>...]] ... %{
Blocs qui spécifient un morceau de code modèle qui est développé pour chaque balise s/m qui est soit explicitement mentionnée par les règles (avec l'option --tags), soit implicitement générée par re2v (avec les options --captvars ou --posix-captvars). Une liste facultative de noms de blocs spécifie quels blocs doivent être inclus lors du calcul de l'ensemble des balises (si la liste est vide, toutes les balises sont incluses). Il existe deux configurations facultatives : format et séparateur. La configuration format spécifie une chaîne modèle où @@{balise} (ou @@ en abrégé) est remplacé par le nom de chaque balise. La configuration séparateur spécifie un morceau de code utilisé pour joindre les morceaux de format générés pour différentes balises.
/*!getstate:re2c[:<nom1>[:<nom2>...]] ... */ ou %{getstate[:<nom1>[:<nom2>...]] ... %}
Un bloc qui génère un dispatch conditionnel sur l'état du lexer (il nécessite l'option --storable-state). Une liste facultative de noms de blocs spécifie quels blocs doivent être inclus dans le dispatch d'état. La transition par défaut va à l'étiquette de départ du premier bloc de la liste. Si la liste est vide, tous les blocs sont inclus et la transition par défaut va au premier bloc du fichier qui a une étiquette de départ. Ce type de bloc est incompatible avec l'option --loop-switch, car il nécessite des transitions inter-blocs qui ne sont pas prises en charge sans goto ou appels de fonction.
/*!conditions:re2c[:<nom1>[:<nom2>...]] ... */, /*!types:re2c... */ ou %{conditions[:<nom1>[:<nom2>...]] ... %}, %{types... %}
Un bloc qui génère une énumération de conditions (il nécessite l'option --conditions). Une liste facultative de noms de blocs spécifie quels blocs doivent être inclus lors du calcul de l'ensemble des conditions (si la liste est vide, toutes les conditions sont incluses). Par défaut, le code généré est une énumération YYCONDTYPE. Il peut être personnalisé avec les configurations facultatives format et séparateur. La configuration format spécifie une chaîne modèle où @@{cond} (ou @@ en abrégé) est remplacé par le nom de chaque condition, et @@{num} est remplacé par un index numérique de cette condition. La configuration séparateur spécifie un morceau de code utilisé pour joindre les morceaux de format générés pour différentes conditions.
/*!include:re2c <fichier> */ ou %{include <fichier> %}
Ce bloc permet d'inclure <fichier>, qui doit être un chemin de fichier entre guillemets doubles. Le contenu du fichier est substitué littéralement à la place du bloc, de la même manière que #include fonctionne en C/C++. Ce bloc peut être utilisé conjointement avec l'option --depfile pour générer des dépendances du système de construction sur les fichiers inclus.
/*!header:re2c:on*/ ou %{header:on %}
Ce bloc marque le début d'un fichier d'en-tête. Tout ce qui suit et jusqu'au bloc header:off suivant est traité par re2v et écrit dans le fichier d'en-tête spécifié avec l'option -t --type-header.
/*!header:re2c:off*/ ou %{header:off %}
Ce bloc marque la fin d'un fichier d'en-tête commencé avec le bloc header:on*/.
/*!ignore:re2c ... */ ou %{ignore ... %}
Un bloc dont le contenu est ignoré et supprimé du fichier de sortie.

Configurations

Voici une liste complète des configurations prises en charge par re2v :

re2c:api, re2c:input
Identique à l'option --api.
re2c:api:sigil
Spécifie le marqueur (« sigil ») utilisé pour les espaces réservés d'arguments dans les primitives de l'API. Le défaut est @@. Un espace réservé commence par le sigil suivi du nom de l'argument entre accolades. Par exemple, si le sigil est défini sur $, les espaces réservés auront la forme ${nom}. Les API à argument unique peuvent utiliser une notation abrégée sans le nom entre accolades. Cette option peut être remplacée par des options pour des primitives d'API individuelles, par exemple re2c:YYFILL@len pour YYFILL.
re2c:api:style
Spécifie le style de l'API. Les valeurs possibles sont functions (le défaut pour C) et free-form (le défaut pour Go et Rust). Dans le style functions, les primitives de l'API sont générées avec une liste d'arguments entre parenthèses suivant le nom de la primitive. Les arguments ne sont fournis que pour les paramètres auto-générés (comme le nombre de caractères passés à YYFILL), mais pas pour le contexte général du lexer, de sorte que les primitives se comportent davantage comme des macros en C/C++ ou des fermetures en Go et Rust. Dans le style free-form, les primitives de l'API n'ont pas de forme fixe : elles doivent être définies comme des chaînes contenant des morceaux de code libres avec des variables interpolées de la forme @@{var} ou @@ (elles correspondent aux arguments dans le style fonctionnel). Cette configuration peut être remplacée pour des primitives d'API individuelles, voir par exemple la configuration re2c:YYFILL:naked pour YYFILL.
re2c:bit-vectors, re2c:flags:bit-vectors, re2c:flags:b
Identique à l'option --bit-vectors, mais peut être configuré par bloc.

Identique à l'option --leftmost-captvars, mais peut être configuré par bloc.
re2c:case-insensitive, re2c:flags:case-insensitive
Identique à l'option --case-insensitive, mais peut être configuré par bloc.
re2c:case-inverted, re2c:flags:case-inverted
Identique à l'option --case-inverted, mais peut être configuré par bloc.
re2c:case-ranges, re2c:flags:case-ranges
Identique à l'option --case-ranges, mais peut être configuré par bloc.
re2c:computed-gotos, re2c:flags:computed-gotos, re2c:flags:g
Identique à l'option --computed-gotos, mais peut être configuré par bloc.
re2c:computed-gotos:relative, re2c:cgoto:relative
Identique à l'option --computed-gotos-relative, mais peut être configuré par bloc.
re2c:computed-gotos:threshold, re2c:cgoto:threshold
Si le goto calculé est utilisé, cette configuration spécifie le seuil de complexité qui déclenche la génération de tables de saut au lieu de structures if imbriquées et de bitmaps. La valeur par défaut est 9.
re2c:cond:abort
Si réglé sur une valeur entière positive, le cas par défaut dans le dispatch de condition généré interrompt l'exécution du programme.
re2c:cond:goto
Spécifie un morceau de code utilisé pour les règles de raccourci auto-générées :=> dans les conditions. Le défaut est goto @@;. L'espace réservé @@ est substitué par le nom de la condition (voir les configurations re2c:api:sigil et re2c:cond:goto@cond).
re2c:cond:goto@cond
Spécifie le sigil utilisé pour la substitution d'arguments dans la définition de re2c:cond:goto. La valeur par défaut est @@. Remplace la configuration plus générique re2c:api:sigil.
re2c:cond:divider
Définit le diviseur pour les blocs de conditions. La valeur par défaut est /* *********************************** */. Les espaces réservés sont substitués par le nom de la condition (voir re2c:api;sigil et re2c:cond:divider@cond).
re2c:cond:divider@cond
Spécifie le sigil utilisé pour la substitution d'arguments dans la définition de re2c:cond:divider. Le défaut est @@. Remplace la configuration plus générique re2c:api:sigil.
re2c:cond:prefix, re2c:condprefix
Spécifie le préfixe utilisé pour les étiquettes de conditions. Le défaut est yyc_.
re2c:cond:enumprefix, re2c:condenumprefix
Spécifie le préfixe utilisé pour les identificateurs de conditions. Le défaut est yyc.
re2c:debug-output, re2c:flags:debug-output, re2c:flags:d
Identique à l'option --debug-output, mais peut être configuré par bloc.
re2c:empty-class, re2c:flags:empty-class

Spécifie le symbole sentinelle utilisé avec la règle de fin d'entrée $. La valeur par défaut est -1 (la règle $ n'est pas utilisée). D'autres valeurs possibles incluent toutes les unités de code valides. Seuls les nombres décimaux sont reconnus.
re2c:header, re2c:flags:type-header, re2c:flags:t
Spécifie le nom du fichier d'en-tête généré par rapport au répertoire du fichier de sortie. Identique à l'option --header, sauf que le chemin du fichier est relatif.
re2c:indent:string
Spécifie la chaîne utilisée pour l'indentation. Par défaut, il s'agit d'une tabulation unique "\t". La chaîne d'indentation ne doit contenir que des caractères d'espacement. Pour désactiver complètement l'indentation, définissez cette configuration sur une chaîne vide.
re2c:indent:top
Spécifie le montant minimum d'indentation à utiliser. La valeur par défaut est zéro. La valeur doit être un nombre entier non négatif.
re2c:invert-captures
Identique à l'option --invert-captures, mais peut être configuré par bloc.
re2c:label:prefix, re2c:labelprefix
Spécifie le préfixe utilisé pour les étiquettes d'état DFA. Par défaut, il est yy.
re2c:label:start, re2c:startlabel
Contrôle la génération d'une étiquette de début de bloc. La valeur par défaut est zéro, ce qui signifie que l'étiquette de début est générée uniquement si elle est utilisée. Une valeur entière supérieure à zéro force la génération de l'étiquette de début même si elle n'est pas utilisée par le lexer. Une valeur de chaîne force également la génération de l'étiquette de début et définit le nom de l'étiquette sur la chaîne spécifiée. Cette configuration s'applique uniquement au bloc actuel (elle est réinitialisée à la valeur par défaut pour le bloc suivant).
re2c:label:yyFillLabel
Spécifie le préfixe des étiquettes YYFILL utilisées avec re2c:eof et en mode état stockable.
re2c:label:yyloop
Spécifie le nom de l'étiquette marquant le début de la boucle du lexer avec l'option --loop-switch. Par défaut, il s'agit de yyloop.
re2c:label:yyNext
Spécifie le nom de l'étiquette optionnelle qui suit le switch YYGETSTATE en mode état stockable (activé avec re2c:state:nextlabel). Par défaut, il s'agit de yyNext.
re2c:lookahead, re2c:flags:lookahead
Obsolète (voir l'option obsolète --no-lookahead).
re2c:monadic
Si défini à une valeur non nulle, le lexer généré utilisera la notation monadique (cette configuration est spécifique à Haskell).
re2c:nested-ifs, re2c:flags:nested-ifs, re2c:flags:s
Identique à l'option --nested-ifs, mais peut être configuré par bloc.
re2c:posix-captures, re2c:flags:posix-captures, re2c:flags:P
Identique à l'option --posix-captures, mais peut être configuré par bloc.
re2c:posix-captvars
Identique à l'option --posix-captvars, mais peut être configuré par bloc.
re2c:tags, re2c:flags:tags, re2c:flags:T
Identique à l'option --tags, mais peut être configuré par bloc.
re2c:tags:expression
Spécifie l'expression utilisée pour les variables de tag. Par défaut, re2v génère des expressions de la forme yyt<N>. Cela peut être gênant, par exemple si les variables de tag sont définies comme des champs dans une structure. Toutes les occurrences de @@{tag} ou @@ sont remplacées par le nom de tag réel. Par exemple, re2c:tags:expression = "s.@@"; résulte en des expressions de la forme s.yyt<N> dans le code généré. Voir également la configuration re2c:api:sigil.
re2c:tags:negative
Spécifie l'expression constante utilisée pour la valeur de tag négative (typiquement ce serait -1 si les tags sont des décalages entiers dans la chaîne d'entrée, ou un pointeur nul s'il s'agit de pointeurs).
re2c:tags:prefix
Spécifie le préfixe pour les noms de variables de tag. Par défaut, il est yyt.
re2c:sentinel
Spécifie le symbole sentinelle utilisé pour les vérifications de fin d'entrée (lorsque les vérifications de limites sont désactivées avec re2c:yyfill:enable = 0; et que re2c:eof n'est pas défini). Cette configuration n'affecte pas la génération de code : son but est de vérifier que le sentinelle n'est pas autorisé au milieu d'une règle, et de s'assurer que le lexer ne lira pas au-delà de la fin du buffer. La valeur par défaut est -1` (dans ce cas, re2v suppose que le sentinelle est zéro, ce qui est le cas le plus courant). Seuls les nombres décimaux sont reconnus.
re2c:state:abort
Si défini à une valeur entière positive, le cas par défaut dans la dispatch de état générée arrête l'exécution du programme, et un cas -1 explicite contient une transition vers le début du bloc.
re2c:state:nextlabel
Contrôle si le switch YYGETSTATE est suivi d'une étiquette yyNext (la valeur par défaut est zéro, ce qui correspond à aucune étiquette). Alternativement, on peut utiliser re2c:label:start pour générer une étiquette de départ spécifique, ou un bloc getstate explicite pour générer le switch YYGETSTATE séparément du bloc lexer.
re2c:unsafe, re2c:flags:unsafe
Identique à l'option --no-unsafe, mais peut être configuré par bloc. Si défini à zéro, il supprime la génération d'enveloppes unsafe autour de YYPEEK. La valeur par défaut est non nulle (les enveloppes sont générées). Cette configuration est spécifique à Rust.

Expressions régulières

re2v utilise la syntaxe suivante pour les expressions régulières :

"foo"
Littéral de chaîne sensible à la casse.
'foo'
Littéral de chaîne insensible à la casse.
[a-xyz], [^a-xyz]
Classe de caractères (éventuellement niée).
.
N'importe quel caractère sauf une nouvelle ligne.
R
Définit l'expression régulière R.
\ S
Différence entre les classes de caractères R et S.
R*
Zéro ou plusieurs occurrences de R.
R+
Une ou plusieurs occurrences de R.
R?
R optionnel.
R{n}
Répétition de R exactement n fois.
R{n,}
Répétition de R au moins n fois.
R{n,m}
Répétition de R de n à m fois.
(R)
Juste R; les parenthèses sont utilisées pour outrepasser la précédence. Si l'extraction de sous-correspondances est activée, (R) est un groupe capturant ou non capturant selon l'option --invert-captures.
(!R)
Si l'extraction de sous-correspondances est activée, (!R) est un groupe non capturant ou capturant selon l'option --invert-captures.
R S
Concaténation : R suivi de S.
R | S
Alternative : R ou S.
R / S
Lookahead : R suivi de S, mais S n'est pas consommé.
name
Expression régulière définie comme name (ou chaîne littérale "name" en mode compatibilité Flex).
{name}
Expression régulière définie comme name en mode compatibilité Flex.
@stag
Un s-tag: sauvegarde la dernière position d'entrée à laquelle @stag correspond dans une variable nommée stag.
#mtag
Un m-tag: sauvegarde toutes les positions d'entrée auxquelles #mtag correspond dans une variable nommée mtag.

Les classes de caractères et les littéraux de chaînes peuvent contenir les séquences d'échappement suivantes : \a, \b, \f, \n, \r, \t, \v, \\, les échappements octaux \ooo et les échappements hexadécimaux \xhh, \uhhhh et \Uhhhhhhhh.

Actions

Voici une liste des actions prédéfinies prises en charge par re2v :

!entry code
L'action d'entrée lie un bloc de code défini par l'utilisateur à l'état de départ de la machine à états finis actuelle. Si des conditions de départ sont utilisées, l'action d'entrée peut être définie individuellement pour chaque condition. Cette action peut être utilisée pour effectuer une initialisation, par exemple pour sauvegarder la position de départ d'un lexème.
!pre_rule code
L'action pré-règle préfixe un bloc de code défini par l'utilisateur aux actions sémantiques de toutes les règles du bloc actuel (ou de la condition, si des conditions de départ sont utilisées). Cette action peut être utilisée pour factoriser la partie commune de toutes les actions sémantiques (par exemple, sauvegarder la position de fin d'un lexème).
!post_rule code
L'action post-règle ajoute un bloc de code défini par l'utilisateur aux actions sémantiques de toutes les règles du bloc actuel (ou de la condition, si des conditions de départ sont utilisées). Cette action peut être utilisée pour émettre des instructions de piège qui protègent contre les flux de contrôle involontaires.

Directives

Voici une liste complète des directives prises en charge par re2v :

!use:name ;
Une directive d'utilisation intra-bloc qui fusionne un bloc de règles précédemment défini avec le name spécifié dans le bloc actuel. Les définitions nommées, les configurations et les règles du bloc référencé sont ajoutées aux actuels. Les conflits entre les règles et configurations qui se chevauchent sont résolus de la manière habituelle : la première règle a la priorité, et la dernière configuration remplace les précédentes. Une exception concerne les règles spéciales *, $ et <!> pour lesquelles une définition locale au bloc a toujours la priorité. Une directive d'utilisation peut être placée n'importe où à l'intérieur d'un bloc, et plusieurs directives d'utilisation sont autorisées.
!include file ;
Cette directive est identique à la directive de bloc include : elle insère le contenu de file tel quel à la place de la directive.

Interface du programme

Le code généré interagit avec le programme externe à l'aide de primitives, collectivement appelées l'API. Les primitives qui doivent être définies pour un programme particulier dépendent de plusieurs facteurs, notamment la complexité des expressions régulières, la représentation de l'entrée, la mise en tampon et l'utilisation de diverses fonctionnalités. Toutes les primitives nécessaires doivent être définies par l'utilisateur sous forme de macros, de fonctions, de variables ou de toute autre forme appropriée qui rend le code généré syntaxiquement et sémantiquement correct. re2v ne vérifie pas (et ne peut pas vérifier) les définitions, donc si quelque chose manque ou est défini incorrectement, le programme généré peut présenter des erreurs de compilation ou d'exécution. Ce manuel fournit des exemples de définitions d'API dans les cas les plus courants.

re2v a trois types d'API qui définissent l'ensemble de base des primitives utilisées par un programme :

API Simple
C'est l'API par défaut pour le backend V. Elle se compose des primitives suivantes : YYINPUT (qui doit être défini comme une séquence d'unités de code, par exemple une chaîne) et YYCURSOR, YYMARKER, YYCTXMARKER, YYLIMIT (qui doivent être définis comme des indices dans YYINPUT).
API Enregistrement
L'API Enregistrement est utile dans les cas où l'état du lexer doit être stocké dans une structure. Elle est activée avec l'option --api record ou la configuration re2c:api = record. Cette API se compose d'une variable yyrecord (le nom peut être remplacé par re2c:yyrecord) qui doit être définie comme une structure avec les champs yyinput, yycursor, yymarker, yyctxmarker, yylimit (seuls les champs utilisés par le code généré doivent être définis, et leurs noms peuvent être configurés).
API Générique
C'est l'API la plus flexible. Elle est activée avec l'option --api generic ou la configuration re2c:api = generic. Elle contient des primitives pour les opérations génériques : YYPEEK, YYSKIP, YYBACKUP, YYBACKUPCTX, YYSTAGP, YYSTAGN, YYMTAGP, YYMTAGN, YYRESTORE, YYRESTORECTX, YYRESTORETAG, YYSHIFT, YYSHIFTSTAG, YYSHIFTMTAG, YYLESSTHAN.

Voici une liste complète des primitives d'API qui peuvent être utilisées par le code généré pour interagir avec le programme externe.

YYCTYPE
Le type des caractères d'entrée (unités de code). Pour les encodages ASCII, EBCDIC et UTF-8, il doit s'agir d'un entier non signé de 1 octet. Pour UTF-16 ou UCS-2, il doit s'agir d'un entier non signé de 2 octets. Pour UTF-32, il doit s'agir d'un entier non signé de 4 octets.
YYCURSOR
Une valeur l-value qui stocke la position actuelle de l'entrée (un pointeur ou un décalage d'entier dans YYINPUT). Initialement, YYCURSOR doit pointer vers le premier caractère d'entrée, et plus tard, il est avancé par le code généré. Lorsqu'une règle correspond, la position YYCURSOR est celle après le dernier caractère correspondant.
YYLIMIT
Une valeur r-value qui stocke la fin de la position d'entrée (un pointeur ou un décalage d'entier dans YYINPUT). Initialement, YYLIMIT doit pointer vers la position après le dernier caractère d'entrée disponible. Il n'est pas modifié par le code généré. Le lexer compare YYCURSOR à YYLIMIT pour déterminer s'il reste suffisamment de caractères d'entrée.
YYMARKER
Une valeur l-value qui stocke la position de la dernière règle correspondante (un pointeur ou un décalage d'entier dans YYINPUT). Elle est utilisée pour restaurer la position YYCURSOR si la correspondance la plus longue échoue et que le lexer doit revenir en arrière. Aucune initialisation n'est nécessaire.
YYCTXMARKER
Une valeur l-value qui stocke la position du contexte de traînée (un pointeur ou un décalage d'entier dans YYINPUT). Aucune initialisation n'est nécessaire. YYCTXMARKER n'est nécessaire que si l'opérateur de lookahead / est utilisé.
YYFILL
Une primitive d'API générique avec une variable len. YYFILL doit fournir au moins len caractères d'entrée supplémentaires ou échouer. Si re2c:eof est utilisé, alors len vaut toujours 1 et YYFILL doit toujours retourner à la fonction appelante ; une valeur de retour zéro indique le succès. Si re2c:eof n'est pas utilisé, alors la valeur de retour de YYFILL est ignorée et elle ne doit pas retourner en cas d'échec. La valeur maximale de len est YYMAXFILL.
YYFN
Une primitive qui définit le prototype de fonction dans le modèle de code --recursive-functions. Sa valeur doit être un tableau d'une ou plusieurs chaînes, où chaque chaîne contient deux ou trois composants séparés par la chaîne spécifiée dans la configuration re2c:fn:sep (généralement un point-virgule). Le premier élément du tableau définit le nom de la fonction et le type de retour (vide pour une fonction vide). Les éléments suivants définissent les arguments de la fonction : d'abord, l'expression de l'argument utilisée dans le corps de la fonction (généralement juste un nom) ; ensuite, le type de l'argument ; enfin, un paramètre formel optionnel (il est par défaut le premier composant - généralement, l'argument et le paramètre sont le même identifiant).
YYINPUT
Une valeur r-value qui stocke la séquence d'entrée actuelle (chaîne, tampon, etc.).
YYMAXFILL
Une constante entière égale à la valeur maximale de l'argument de YYFILL. Elle peut être générée avec un bloc max.
YYLESSTHAN
Une primitive d'API générique avec une variable len. Elle doit être
définie comme une valeur r de type booléen qui est égale à true si et seulement s'il reste moins de len caractères d'entrée.
YYPEEK
Une primitive d'API générique sans variables. Elle doit être définie comme une valeur r de type YYCTYPE égale au caractère à la position d'entrée actuelle.
YYSKIP
Une primitive d'API générique qui doit avancer la position d'entrée actuelle d'une unité de code.
YYBACKUP
Une primitive d'API générique qui doit sauvegarder la position d'entrée actuelle (à restaurer plus tard avec YYRESTORE).
YYRESTORE
Une primitive d'API générique qui doit restaurer la position d'entrée actuelle à la valeur sauvegardée par YYBACKUP.
YYBACKUPCTX
Une primitive d'API générique qui doit sauvegarder la position d'entrée actuelle comme la position du contexte de traînée (à restaurer plus tard avec YYRESTORECTX).
YYRESTORECTX
Une primitive d'API générique qui doit restaurer la position du contexte de traînée sauvegardée avec YYBACKUPCTX.
YYRESTORETAG
Une primitive d'API générique avec une variable tag qui doit restaurer la position du contexte de traînée à la valeur de tag.
YYSTAGP
Une primitive d'API générique avec une variable tag, où tag peut être un pointeur ou un décalage dans YYINPUT (voir la section d'extraction de sous-correspondance pour plus de détails). YYSTAGP doit définir tag à la position d'entrée actuelle.
YYSTAGN
Une primitive d'API générique avec une variable tag, où tag peut être un pointeur ou un décalage dans YYINPUT (voir la section d'extraction de sous-correspondance pour plus de détails). YYSTAGN doit définir tag à une valeur représentant une position d'entrée inexistante.
YYMTAGP
Une primitive d'API générique avec une variable tag. YYMTAGP doit ajouter la position actuelle à l'historique de sous-correspondance de tag (voir la section d'extraction de sous-correspondance pour plus de détails).
YYMTAGN
Une primitive d'API générique avec une variable tag. YYMTAGN doit ajouter une valeur représentant une position d'entrée inexistante à l'historique de sous-correspondance de tag (voir la section d'extraction de sous-correspondance pour plus de détails).
YYSHIFT
Une primitive d'API générique avec une variable shift qui doit décaler la position d'entrée actuelle de shift caractères (la valeur de décalage peut être négative).
YYCOPYSTAG
Une primitive d'API générique avec deux variables, lhs et rhs, qui doit copier la variable s-tag de droite rhs dans la variable s-tag de gauche lhs. Pour la plupart des langages, cette primitive a une définition par défaut qui assigne lhs à rhs.
YYCOPYMTAG
Une primitive d'API générique avec deux variables, lhs et rhs, qui doit copier la variable m-tag de droite rhs dans la variable m-tag de gauche lhs. Pour la plupart des langages, cette primitive a une définition par défaut qui assigne lhs à rhs.
YYSHIFTSTAG
Une primitive d'API générique avec deux variables, tag et shift, qui doit décaler tag de shift unités de code (la valeur de décalage peut être négative).
YYSHIFTMTAG
Une primitive d'API générique avec deux variables, tag et shift, qui doit décaler la dernière valeur de l'historique de tag de shift unités de code (la valeur de décalage peut être négative).
YYMAXNMATCH
Une constante entière égale au nombre maximal de groupes de capture POSIX dans une règle. Elle est générée avec un bloc maxnmatch.
YYCONDTYPE
Le type de l'énumération de condition. Il peut être généré soit avec le bloc conditions, soit avec l'option --header.
YYGETACCEPT
Une primitive avec une variable var qui stocke le sélecteur numérique de la règle acceptée. Pour la plupart des langages, cette primitive a une définition par défaut qui lit à partir de var.
YYSETACCEPT
Une primitive avec deux variables : var (une valeur l (l-value) qui stocke le sélecteur numérique de la règle acceptée) et val (la valeur du sélecteur). Pour la plupart des langages, cette primitive a une définition par défaut qui assigne var à val.
YYGETCOND
Une valeur r de type YYCONDTYPE égale à l'identifiant de condition actuel.
YYSETCOND
Une primitive avec une variable cond qui doit définir l'identifiant de condition actuel à cond.
YYGETSTATE
Une valeur r de type entier égale à l'état actuel du lexer. Elle doit être initialisée à -1.
YYSETSTATE
Une primitive avec une variable state qui doit définir l'état actuel du lexer à state.
YYDEBUG
Cette primitive n'est générée qu'avec l'option -d, --debug-output. Son objectif est d'ajouter de la journalisation au code généré (la définition typique de YYDEBUG est une instruction d'impression). Les instructions YYDEBUG sont générées dans chaque état et ont deux variables : state (soit un index d'état DFA, soit -1) et symbol (le symbole d'entrée actuel).
yyaccept
Une valeur l de type entier non signé qui stocke le numéro de la dernière règle correspondante. Une définition par l'utilisateur n'est nécessaire qu'avec l'option --storable-state.
yybm
Une table contenant des bitmaps compressées pour jusqu'à 8 transitions (utilisé avec l'option --bitmaps). La table contient 256 éléments et est indexée par des unités de code sur 1 octet. Chaque élément de 8 bits combine des valeurs booléennes pour jusqu'à 8 transitions. Le k-ième bit du n-ième élément est vrai si et seulement si le n-ième unité de code est dans la plage de la k-ième transition. L'idée de cette bitmap est de remplacer de nombreuses branches if ou cas switch par une seule vérification d'un bit unique dans la table.
yych
Une valeur l de type YYCTYPE qui stocke le caractère d'entrée actuel. Une définition par l'utilisateur n'est nécessaire qu'avec l'option -f --storable-state.
yyctable
Table de saut générée pour la distribution initiale des conditions (activée par la combinaison des options --conditions et --computed-gotos).
yyfill
Une valeur l qui stocke le résultat de l'appel YYFILL (cela peut être nécessaire pour les langages purement fonctionnels, où YYFILL est une fonction monadique avec une valeur de retour complexe).
yynmatch
Une valeur l de type entier non signé qui stocke le nombre de groupes de capture POSIX dans la règle correspondante. Utilisé uniquement avec l'option -P --posix-captures.
yypmatch
Un tableau de valeurs l utilisées pour contenir les valeurs de balises correspondant aux parenthèses de capture dans la règle correspondante. La longueur du tableau doit être au moins yynmatch * 2 (généralement YYMAXNMATCH * 2 est un bon choix). Utilisé uniquement avec l'option -P --posix-captures.
yystable
Déprécié.
yystate
Une valeur l utilisée avec l'option --loop-switch pour stocker l'état DFA actuel.
yytarget
Table de saut contenant les cibles de saut (adresses d'étiquettes) pour toutes les transitions depuis un état. Cette table est locale à chaque état. La génération des tables yytarget est activée avec l'option --computed-gotos.

Avec utf8, re2v traite l'entrée comme encodée en UTF8 et reconnaît les caractères multibytes.
--invert-captures
Inverser la signification des groupes de capture et des groupes non capturants. Par défaut, (...) est capturant et (! ...) est non capturant. Avec cette option, (! ...) est capturant et (...) est non capturant.
--lang <none | c | d | go | haskell | java | js | ocaml | python | rust | swift | v | zig>
Spécifier la langue cible. --location-format <gnu | msvc>
Spécifier le format d'emplacement dans les messages. Avec gnu, les emplacements sont imprimés sous la forme 'filename:line:column: ...'. Avec msvc, les emplacements sont imprimés sous la forme 'filename(line,column) ...'. La valeur par défaut est gnu.
--loop-switch
Utiliser le modèle de code "loop/switch" : encoder le DFA sous forme d'une boucle sur une instruction switch, où les états individuels sont des cas de switch. L'état est stocké dans une variable yystate. Les transitions entre les états mettent à jour yystate vers l'étiquette du cas de l'état de destination et continuent l'exécution jusqu'au début de la boucle.
--nested-ifs -s

--no-debug-info -i
Ne pas générer de directives de ligne. Cela peut être utile lorsque le code généré est stocké dans un système de contrôle de version (pour éviter d'énormes différences automatiques lors de petits changements).

--no-version
Supprimer la version de sortie dans le fichier généré.
--no-unsafe

--output -o OUTPUT
Spécifier le fichier OUTPUT.
--posix-captures, -P
Activer l'extraction de sous-correspondances avec des groupes de capture de style POSIX. Le résultat est collecté dans un tableau yybmatch de capacité 2 * YYMAXNMATCH, et yynmatch est défini sur le nombre de groupes pour la règle correspondante.

--recursive-functions
Utiliser le modèle de code basé sur des fonctions co-récursives, où chaque état de DFA est une fonction distincte qui peut appeler d'autres fonctions d'état ou elle-même.
--reusable -r

Option interne : algorithme de minimisation de DFA utilisé par re2v. L'option moore est l'algorithme de Moore (c'est la valeur par défaut). L'option table est l'algorithme de remplissage de table. Les deux algorithmes devraient produire le même DFA jusqu'au re-étiquetage des états ; le remplissage de table est plus simple et beaucoup plus lent, servant d'implémentation de référence.
--eager-skip
Option interne : faire avancer le lexer généré la position d'entrée avidement -- immédiatement après avoir lu le symbole d'entrée. Ceci change le comportement par défaut lorsque la position d'entrée est avancée paresseusement -- après la transition vers le nouvel état.
--no-lookahead
Option interne, obsolète. Elle activait auparavant l'algorithme TDFA(0). Contrairement à TDFA(1), l'algorithme TDFA(0) n'utilise pas d'anticipation d'un seul symbole. Il applique des opérations de registre aux transitions entrantes plutôt qu'aux transitions sortantes. Les benchmarks ont montré que l'algorithme TDFA(0) est moins efficace que TDFA(1).
--no-optimize-tags
Option interne : supprimer l'optimisation des variables de balises (utile pour le débogage).
--posix-closure <gor1 | gtop>
Option interne : spécifier l'algorithme de plus court chemin utilisé pour la construction de la clôture epsilon avec des sémantiques de désambiguïsation POSIX : gor1 (par défaut) signifie l'algorithme de Goldberg-Radzik, et gtop signifie « ordre topologique global ».
--posix-prectable <complex | naive>
Option interne : spécifier l'algorithme utilisé pour calculer la table de précedence POSIX. L'algorithme complex calcule la table de précedence en un seul parcours de l'arbre d'historique des balises et a une complexité quadratique par rapport au nombre d'états TNFA ; c'est la valeur par défaut. L'algorithme naive a une complexité cubique dans le pire des cas par rapport au nombre d'états TNFA, mais il est beaucoup plus simple que complex et peut être légèrement plus rapide dans les cas non pathologiques.
--stadfa
Option interne, obsolète. Elle activait l'algorithme staDFA, qui diffère de TDFA en ce que les opérations de registre sont placées dans les états plutôt que sur les transitions. Les benchmarks ont montré que l'algorithme staDFA est moins efficace que TDFA.
--fixed-tags <none | toplevel | all>
Option interne : spécifier si l'optimisation des balises fixes doit être appliquée à toutes les balises (all), à aucune d'entre elles (none), ou seulement à celles de la concaténation de premier niveau (toplevel). La valeur par défaut est all. Les balises « fixes » sont celles qui sont situées à une distance fixe d'une autre balise (appelée « base »). Dans de tels cas, seule la balise de base doit être suivie, et la valeur de la balise fixe peut être calculée comme la valeur de la balise de base plus un décalage statique. Pour les balises sous alternative ou répétition, il est également nécessaire de vérifier si la balise de base a une valeur de non-correspondance (dans ce cas, la balise fixe doit également être définie sur non-correspondance, ignorant le décalage). Pour les balises dans la concaténation de premier niveau, la vérification n'est pas nécessaire, car elles correspondent toujours.

Avertissements

Les avertissements peuvent être activés, désactivés et transformés en erreur individuellement.

-W
Activer tous les avertissements.
-Werror
Transformer les avertissements en erreurs. Notez que cette option seule n'active aucun avertissement ; elle affecte uniquement les avertissements qui ont été activés jusqu'à présent ou qui le seront plus tard.
-W<warning>
Activer warning.
-Wno-<warning>
Désactiver warning.
-Werror-<warning>
Activer warning et le traiter comme une erreur (ceci implique -W<warning>).
-Wno-error-<warning>
Ne pas traiter ce warning particulier comme une erreur. Ceci ne désactive pas l'avertissement lui-même.
-Wcondition-order
Avertir si le programme généré fait des suppositions implicites sur la numérotation des conditions. Il faut utiliser soit l'option --header soit le bloc conditions pour générer une correspondance des noms de conditions aux numéros, puis utiliser les noms de conditions autogénérés.
-Wempty-character-class
Avertir si une expression régulière contient une classe de caractères vide. Essayer de faire correspondre une classe de caractères vide n'a aucun sens : elle devrait toujours échouer. Cependant, pour des raisons de compatibilité ascendante, re2v autorise les classes de caractères vides et les traite comme des chaînes vides. Utilisez l'option --empty-class pour modifier le comportement par défaut.
-Wmatch-empty-string
Avertir si une règle est nullable (correspond à une chaîne vide). Si le lexer s'exécute en boucle et que la correspondance vide est involontaire, le lexer peut se bloquer de manière inattendue dans une boucle infinie.
-Wswapped-range
Avertir si la borne inférieure d'une plage est supérieure à sa borne supérieure. Le comportement par défaut est d'échanger silencieusement les bornes de la plage.
-Wundefined-control-flow
Avertir si certaines chaînes d'entrée provoquent un flux de contrôle indéfini dans le lexer (les motifs défectueux sont signalés). C'est une erreur dangereuse et courante. Elle peut être facilement corrigée en ajoutant la règle par défaut * qui a la priorité la plus basse, correspond à toute unité de code et consomme toujours une seule unité de code.
-Wunreachable-rules
Avertir sur les règles qui sont masquées par d'autres règles et qui ne correspondent jamais.
-Wdeprecated-eof_rule
Avertir sur les règles de fin d'entrée autonomes $ qui seront rompues par les futurs changements et nécessiteront une correction. Pour le moment, ces règles prennent
e précedence lorsqu'elles entrent en conflit avec d'autres règles, mais après l'introduction du symbole généralisé de fin d'entrée $, l'ordre de priorité changera et ces règles seront masquées par d'autres règles.
-Wuseless-escape
Avertir si un symbole est échappé alors qu'il ne devrait pas l'être. Par défaut, re2v ignore silencieusement de tels échappements, mais cela peut aussi indiquer une faute de frappe ou une erreur dans la séquence d'échappement.
-Wnondeterministic-tags
Avertir si une étiquette a un degré de nondéterminisme de n, où n est supérieur à 1.
-Wsentinel-in-midrule
Avertir si le symbole sentinelle apparaît au milieu d'une règle --- cela peut entraîner des lectures au-delà de la fin du tampon, des plantages ou une corruption de mémoire dans le lexer généré. Cet avertissement ne s'applique que si la méthode sentinelle pour vérifier la fin de l'entrée est utilisée. Il est défini comme une erreur si la configuration re2c:sentinel est utilisée.
-Wundefined-syntax-config
Avertir si le fichier de syntaxe spécifié avec l'option --syntax manque de définitions pour certaines configurations. Cela permet de maintenir les fichiers de syntaxe définis par l'utilisateur : si une nouvelle version ajoute des configurations, l'ancien fichier de syntaxe provoquera un avertissement, et l'utilisateur en sera informé. Si certaines configurations sont inutilisées et n'ont pas besoin de définition, elles doivent être explicitement définies sur <undefined>.

Fichiers de syntaxe

Le support des différents langages dans re2c repose sur l'idée de fichiers de syntaxe. Un fichier de syntaxe est un fichier de configuration qui définit la syntaxe du langage cible -- pas le langage entier, mais une petite partie de celui-ci qui est utilisée par le code généré. Les fichiers de syntaxe rendent re2c très flexible, mais ils ne doivent pas être utilisés comme un remplacement pour les configurations re2c: : leur objectif est de définir la syntaxe du langage cible, et non de personnaliser un lexer particulier. Tous les langages supportés ont des fichiers de syntaxe par défaut qui font partie de la distribution (voir le sous-répertoire include/syntax) ; ils sont également intégrés dans le binaire re2v. Les utilisateurs peuvent fournir un fichier de syntaxe personnalisé qui remplace quelques configurations pour l'un des langages supportés, ou ils peuvent choisir de redéfinir toutes les configurations (dans ce cas, l'option --lang none doit être utilisée). Les fichiers de syntaxe contiennent des configurations de quatre types différents : listes de fonctionnalités, configurations de langage, configurations en ligne et modèles de code.

Une liste des API supportées avec les éléments possibles simple, record, generic.
supported_api_styles
Une liste des styles d'API supportés avec les éléments possibles functions, free-form.
supported_code_models
Une liste des modèles de code supportés avec les éléments possibles goto-label, loop-switch, recursive-functions.
supported_targets
Une liste des cibles de génération de code supportées avec les éléments possibles code, dot, skeleton.
supported_features
Une liste des fonctionnalités supportées avec les éléments possibles nested-ifs, bitmaps, computed-gotos, case-ranges, monadic, unsafe, tags, captures, captvars.

Non nul si le langage a des chaînes entre apostrophes inversées.

Modèles de code

Les modèles de code définissent la syntaxe du langage cible. Ils sont écrits dans un langage simple spécifique à un domaine avec la grammaire formelle suivante : 
code-template ::
      name '=' code-exprs ';'
    | CODE_TEMPLATE ';'
    | '<undefined>' ';'
code-exprs ::
      <EMPTY>
    | code-exprs code-expr
code-expr ::
      STRING
    | VARIABLE
    | optional
    | list
optional ::
      '(' CONDITIONAL '?' code-exprs ')'
    | '(' CONDITIONAL '?' code-exprs ':' code-exprs ')'
list ::
      '[' VARIABLE ':' code-exprs ']'
    | '[' VARIABLE '{' NUMBER '}' ':' code-exprs ']'
    | '[' VARIABLE '{' NUMBER ',' NUMBER '}' ':' code-exprs ']'

Un modèle de code est une séquence de littéraux de chaîne, de variables, d'éléments optionnels et de listes, ou une référence à un autre modèle de code, ou une valeur spéciale <undefined>. Les variables sont des espaces réservés qui sont substitués pendant la phase de génération de code. Les variables de liste sont spéciales : lors de l'expansion des modèles de liste, re2v répète les expressions du côté droit de la colonne plusieurs fois, remplaçant à chaque fois les occurrences de la variable de liste par une valeur spécifique à cette répétition. Les listes ont des bornes optionnelles (les valeurs négatives sont comptées à partir de la fin, par exemple -1 signifie le dernier élément). Les noms conditionnels commencent par un point. Les conditions et les variables peuvent être locales (spécifiques au modèle de code donné) ou globales (autorisées dans tous les modèles de code). Lorsque re2v lit le fichier de syntaxe, il vérifie que chaque modèle de code utilise uniquement les variables et les conditions qui y sont autorisées.

Par exemple, le modèle de code suivant définit la structure if-then-else pour un langage de type C :

code:if_then_else =
    [branch{0}: topindent "if " cond " {" nl
        indent [stmt: stmt] dedent]
    [branch{1:-1}: topindent "} else" (.cond ? " if " cond) " {" nl
        indent [stmt: stmt] dedent]
    topindent "}" nl;

Ici, branch est une variable de liste : branch{0} s'étend à la première branche (qui est spéciale, car il n'y a pas de partie else), branch{1:-1} s'étend à toutes les branches restantes (le cas échéant). stmt est également une variable de liste : [stmt: stmt] est une liste imbriquée qui s'étend à une liste d'instructions dans le corps de la branche actuelle. topindent, indent, dedent et nl sont des variables globales, et .cond est une condition locale (leur signification est décrite ci-dessous). Ce modèle de code pourrait produire le code suivant :

if x {
    // faire quelque chose
} else if y {
    // faire autre chose
} else {
    // ne rien faire
}

GESTION DE LA FIN DE L'ENTRÉE

L'un des principaux problèmes pour le lexer est de savoir quand s'arrêter. Il existe quelques conditions de terminaison :

  • le lexer peut correspondre à une règle (y compris la règle par défaut *) et parvenir à un état final
  • le lexer peut ne pas correspondre à une règle et parvenir à un état par défaut
  • le lexer peut atteindre la fin de l'entrée

Les deux premières conditions terminent le lexer d'une manière "naturelle" : il parvient à un état sans transitions sortantes, et la correspondance s'arrête automatiquement. La troisième condition, la fin de l'entrée, est différente : elle peut se produire dans n'importe quel état, et le lexer doit être capable de la gérer. La vérification de la fin de l'entrée interrompt le flux normal du lexer et ajoute des branches conditionnelles au programme généré, il est donc nécessaire de minimiser le nombre de ces vérifications. re2v prend en charge quelques méthodes différentes pour gérer la fin de l'entrée. Laquelle utiliser dépend de la complexité des expressions régulières, du besoin de mise en tampon, des considérations de performance et d'autres facteurs. Voici une liste de méthodes :

  • Sentinel. Cette méthode élimine le besoin de vérifications de fin d'entrée. Elle est simple et efficace, mais limitée au cas où il existe un caractère "sentinelle" naturel qui ne peut jamais apparaître dans une entrée valide. Ce caractère peut toujours apparaître dans une entrée invalide, mais il ne devrait pas être autorisé par les expressions régulières, sauf peut-être comme dernier caractère d'une règle. La sentinelle est ajoutée à la fin de l'entrée et sert de signal d'arrêt : lorsque le lexer lit ce caractère, il s'agit soit d'une erreur de syntaxe, soit de la fin de l'entrée. Dans les deux cas, le lexer doit s'arrêter. Cette méthode est utilisée si YYFILL est désactivé avec re2c:yyfill:enable = 0; et re2c:eof a la valeur par défaut -1.
  • Sentinel avec vérifications de limites. Cette méthode est générique : elle permet de gérer n'importe quelle entrée sans restrictions sur les expressions régulières. L'idée est de réduire le nombre de vérifications de fin d'entrée en les effectuant uniquement sur certains caractères. Similaire à la méthode "sentinelle", l'un des caractères est choisi comme "sentinelle" et ajouté à la fin de l'entrée. Cependant, il n'y a aucune restriction quant à l'endroit où la sentinelle peut apparaître (en fait, n'importe quel caractère peut être choisi pour une sentinelle). Lorsque le lexer lit ce caractère, il effectue en plus une vérification de limites. Si la position actuelle est dans les limites, le lexer reprend la correspondance et gère la sentinelle comme un caractère ordinaire. Sinon, il invoque YYFILL (sauf si elle est désactivée). Si plus d'entrée est fournie, le lexer re-correspondra au dernier caractère et continuera comme si la sentinelle n'y était pas. Sinon, ce doit être la fin réelle de l'entrée, et le lexer s'arrête. Cette méthode est utilisée lorsque re2c:eof a une valeur non négative (elle doit être définie à la valeur numérique de la sentinelle). YYFILL est facultatif.
  • Vérifications de limites avec remplissage. Cette méthode est générique, et elle peut être plus rapide que la méthode "sentinelle avec vérifications de limites", mais elle est aussi plus complexe. L'idée est de partitionner les états du DFA en composantes fortement connexes (SCC) et de générer une seule vérification par SCC pour suffisamment de caractères afin de couvrir le chemin non cyclique le plus long dans cette SCC. Cela réduit le nombre de vérifications, mais il y a un problème avec les lexèmes courts en fin d'entrée, car la vérification nécessite suffisamment de caractères pour couvrir le lexème le plus long. Cela peut être corrigé en remplissant l'entrée avec quelques caractères factices qui ne forment pas un suffixe de lexème valide (de sorte que le lexer ne puisse pas les faire correspondre). La longueur du remplissage doit être YYMAXFILL, générée avec un bloc max. S'il n'y a pas assez d'entrée, le lexer invoque YYFILL qui doit fournir au moins le nombre requis de caractères ou ne pas retourner. Cette méthode est utilisée si YYFILL est activé et re2c:eof est -1 (c'est la configuration par défaut).
  • Vérifications personnalisées. L'API générique permet de remplacer les opérations de base comme la lecture d'un caractère, ce qui rend possible l'inclusion des vérifications de fin d'entrée comme faisant partie d'elles. Cette approche est sujette aux erreurs et doit être utilisée avec prudence. Pour utiliser une méthode personnalisée, activez l'API générique avec --api custom ou re2c:api = custom; et désactivez les vérifications de limites par défaut avec re2c:yyfill:enable = 0; ou re2c:yyfill:check = 0;.

Sentinel

Cet exemple utilise un caractère sentinelle pour gérer la fin de l'entrée. Le programme compte les mots séparés par des espaces dans une chaîne terminée par un caractère nul. La sentinelle est le caractère nul : c'est le dernier caractère de chaque chaîne d'entrée, et il n'est autorisé dans le milieu d'un lexème par aucune des règles (en particulier, il n'est pas inclus dans les plages de caractères où il est facile à ignorer). Si un caractère nul apparaît au milieu d'une chaîne, c'est une erreur de syntaxe et le lexer correspondra à la règle par défaut *, mais il ne lira pas au-delà de la fin de l'entrée et ne plantera pas (utilisez l'avertissement -Wsentinel-in-midrule et la configuration re2c:sentinel pour vérifier cela). La configuration re2c:yyfill:enable = 0; supprime la génération des vérifications de limites et des invocations YYFILL.

// re2v $INPUT -o $OUTPUT
// Attend une chaîne terminée par un caractère nul.
fn lex(yyinput string) int {

    mut count := 0
loop: /*!re2c
    re2c:yyfill:enable = 0;

Sentinel avec vérifications de limites

Cet exemple utilise la sentinelle avec vérifications de limites pour gérer la fin de l'entrée (cette méthode a été ajoutée dans la version 1.2). Le programme compte les chaînes entre apostrophes séparées par des espaces. La sentinelle est le caractère nul, spécifié par la configuration re2c:eof = 0;. Comme dans la méthode sentinel, le caractère nul est le dernier caractère de chaque chaîne d'entrée, mais il est autorisé au milieu d'une règle (par exemple, 'aaa\0aa'\0 est une entrée valide, mais 'aaa\0 est une erreur de syntaxe). Les vérifications de limites sont générées dans chaque état qui correspond à un caractère d'entrée, mais elles sont limitées à la branche qui gère le caractère nul. Les vérifications de limites sont de la forme YYLIMIT <= YYCURSOR ou YYLESSTHAN(1) avec l'API générique. Si la condition de vérification est vraie, le lexer a atteint la fin de l'entrée et doit s'arrêter (YYFILL est désactivé avec re2c:yyfill:enable = 0; car l'entrée tient dans un seul tampon, voir la section YYFILL avec sentinelle pour un exemple utilisant YYFILL). Atteindre la fin de l'entrée ouvre trois possibilités : si le lexer est dans l'état initial, il correspondra à la règle de fin d'entrée $, sinon il pourra revenir à une règle précédemment correspondue (y compris la règle par défaut *) ou aller à un état par défaut, provoquant -Wundefined-control-flow.

// re2v $INPUT -o $OUTPUT
// Attend une chaîne terminée par un caractère nul.
fn lex(yyinput string) int {
    mut yycursor, mut yymarker := 0, 0
    yylimit := yyinput.len - 1 // yylimit pointe sur le caractère nul de terminaison
    mut count := 0
loop: /*!re2c
    re2c:eof = 0;
    re2c:yyfill:enable = 0;
    str = ['] ([^'\\] | [\\][^])* ['];
    *    { return -1 }
    $    { return count }
    str  { count += 1; unsafe { goto loop } }
    [ ]+ { unsafe { goto loop } }
    */
}
fn main() {
    assert lex("\0") == 0
    assert lex("'qu\0tes' 'are' 'fine: \\'' \0") == 3
    assert lex("'unterminated\\'\0") == -1
}

Vérifications de limites avec remplissage

Cet exemple utilise des vérifications de limites avec remplissage pour gérer la fin de l'entrée (cette méthode est activée par défaut). Le programme compte les chaînes entre apostrophes séparées par des espaces. Il y a un remplissage de caractères nuls YYMAXFILL ajoutés à la fin de l'entrée, où la valeur de YYMAXFILL est générée automatiquement avec un bloc max. Il n'est pas nécessaire d'utiliser le caractère nul pour le remplissage --- n'importe quels caractères peuvent être utilisés tant qu'ils ne forment pas un suffixe de lexème valide (dans cet exemple, le remplissage ne doit pas contenir d'apostrophes, car elles pourraient être confondues avec un suffixe d'une chaîne entre apostrophes). Il y a une règle "stop" qui correspond au premier caractère de remplissage (nul) et termine le lexer (notez qu'elle vérifie si le nul est au début du remplissage, sinon c'est une erreur de syntaxe). Les vérifications de limites ne sont générées que dans certains états déterminés par les composantes fortement connexes de l'automate sous-jacent. Les vérifications sont de la forme (YYLIMIT - YYCURSOR) < n ou YYLESSTHAN(n) avec l'API générique

, où n est le nombre minimum de caractères nécessaires au lexer pour continuer (cela signifie également que la prochaine vérification des limites se produira dans au plus n caractères). Si la condition de vérification est vraie, le lexer a atteint la fin de l'entrée et appellera YYFILL(n) qui devra fournir au moins n caractères d'entrée ou ne pas retourner. Dans cet exemple, YYFILL échoue toujours et termine le lexer avec une erreur (ce qui est correct car l'entrée tient dans un seul tampon). Voir la section YYFILL avec remplissage pour un exemple qui recharge le tampon d'entrée avec YYFILL.

// re2v $INPUT -o $OUTPUT
/*!max:re2c*/
// Attend une chaîne remplie par yymaxfill.
fn lex(str string) int {
    // Remplit la chaîne avec yymaxfill zéros à la fin.
    mut yyinput := []u8{len: str.len + yymaxfill}
    copy(mut &yyinput, str.bytes())
    mut yycursor := 0
    yylimit := yyinput.len
    mut count := 0
loop: /*!re2c
    re2c:YYFILL = "return -1";
    str = ['] ([^'\\] | [\\][^])* ['];
    [\x00] {
        // Vérifie qu'il s'agit du sentinelle, pas d'un nul inattendu.
        if yycursor - 1 == str.len { return count } else { return -1 }
    }
    str  { count += 1; unsafe { goto loop } }
    [ ]+ { unsafe { goto loop } }
    *    { return -1 }
    */
}
fn main() {
    assert lex("") == 0
    assert lex("'qu\0tes' 'are' 'fine: \\'' ") == 3
    assert lex("'unterminated\\'") == -1
    assert lex("'unexpected \00 null\\'") == -1
}

Vérifications personnalisées

Cet exemple utilise une méthode personnalisée de gestion de la fin de l'entrée basée sur l'API générique. Le programme compte les chaînes entre guillemets simples séparées par des espaces. C'est le même exemple que le sentinelle, à l'exception près que l'entrée n'est pas terminée par un nul. Pour compenser l'absence d'un caractère sentinelle à la fin de l'entrée, YYPEEK est redéfini pour effectuer une vérification des limites avant de lire le prochain caractère d'entrée. Ceci est inefficace car les vérifications sont effectuées très souvent. Si la condition de vérification échoue, YYPEEK retourne le vrai caractère, sinon il retourne un faux caractère sentinelle.

// re2v $INPUT -o $OUTPUT
// Retourne un nul "faux" terminateur si le curseur a atteint la limite.
fn peek(str string, cur int) u8 {
    return if cur >= str.len { u8(0) } /* faux nul */ else { return str[cur] }
}
// Attend une chaîne sans nul terminateur.
fn lex(str string) int {
    mut cur := 0
    mut count := 0
loop: /*!re2c
    re2c:api = generic;
    re2c:yyfill:enable = 0;
    re2c:YYPEEK = "peek(str, cur)";
    re2c:YYSKIP = "cur += 1";
    *      { return -1 }
    [\x00] { return count }
    [a-z]+ { count += 1; unsafe { goto loop } }
    [ ]+   { unsafe { goto loop } }
    */
}
fn main() {
    assert lex("") == 0
    assert lex("one two three") == 3
    assert lex("f0ur") == -1
}

REMPLISSAGE DU TAMPON

Le besoin de mise en tampon survient lorsque l'entrée ne peut pas être mappée en mémoire d'un seul coup : soit elle est trop grande, soit elle provient d'un flux (comme la lecture depuis une socket). La technique habituelle dans de tels cas est d'allouer un tampon de mémoire de taille fixe et de traiter l'entrée par morceaux qui tiennent dans le tampon. Lorsque le morceau actuel est traité, il est déplacé et de nouvelles données sont chargées. En pratique, c'est un peu plus complexe, car l'état du lexer ne consiste pas en une seule position d'entrée, mais en un ensemble de positions interdépendantes :

  • curseur : le prochain caractère d'entrée à lire (YYCURSOR dans l'API des pointeurs C ou YYSKIP/YYPEEK dans l'API générique)
  • limite : la position après le dernier caractère d'entrée disponible (YYLIMIT dans l'API des pointeurs C, géré implicitement par YYLESSTHAN dans l'API générique)
  • marqueur : la position de la correspondance la plus récente, le cas échéant (YYMARKER dans l'API par défaut ou YYBACKUP/YYRESTORE dans l'API générique)
  • token : le début du lexème courant (implicite dans l'API re2v, car il n'est pas nécessaire pour le fonctionnement normal du lexer et peut être défini et mis à jour par l'utilisateur)
  • marqueur de contexte : la position du contexte de fin (YYCTXMARKER dans l'API des pointeurs C ou YYBACKUPCTX/YYRESTORECTX dans l'API générique)
  • variables de balise : positions de sous-correspondance (définies avec les blocs stags et mtags et les primitives de l'API générique YYSTAGP/YYSTAGN/YYMTAGP/YYMTAGN)

Tous ces éléments ne sont pas utilisés dans tous les cas, mais s'ils le sont, ils doivent être mis à jour par YYFILL. Toutes les positions actives sont contenues dans le segment entre le token et le curseur, par conséquent tout ce qui se trouve entre le début du tampon et le token peut être rejeté, le segment allant du token jusqu'à la limite doit être déplacé au début du tampon, et l'espace libre à la fin du tampon doit être rempli avec de nouvelles données. Afin d'éviter des appels fréquents à YYFILL, il est préférable de charger autant de caractères d'entrée que possible (même si moins de caractères pourraient suffire pour reprendre le lexer). Les détails de l'implémentation de YYFILL diffèrent légèrement selon la méthode de gestion de la fin de fichier utilisée : le cas de la règle EOF est un peu plus simple que le cas de la vérification des limites avec remplissage. Notez également que si l'option -f --storable-state est utilisée, YYFILL a une sémantique légèrement différente (décrite dans la section sur l'état stockable).

YYFILL avec sentinelle

Si la règle EOF est utilisée, YYFILL est une primitive de type fonction qui n'accepte aucun argument et retourne une valeur qui est comparée à zéro. L'invocation de YYFILL est déclenchée par la condition YYLIMIT <= YYCURSOR dans l'API des pointeurs C et YYLESSTHAN() dans l'API générique. Une valeur de retour non nulle signifie que YYFILL a échoué. Un appel réussi à YYFILL doit fournir au moins un caractère et ajuster les positions d'entrée en conséquence. La limite doit toujours être définie à une position après la dernière position d'entrée dans le tampon, et le caractère à la position limite doit être le symbole sentinelle spécifié par la configuration re2c:eof. Les schémas ci-dessous montrent les emplacements relatifs des positions d'entrée dans le tampon avant et après l'appel à YYFILL (le symbole sentinelle est marqué par #, et le second schéma montre le cas où il n'y a pas assez d'entrée pour remplir tout le tampon).

               <-- décalage -->
             >-A------------B---------C-------------D#-----------E->
             tampon       token    marqueur      limite,
                                                  curseur
>-A------------B---------C-------------D------------E#->
             tampon,  marqueur      curseur       limite
             token
               <-- décalage -->
             >-A------------B---------C-------------D#--E (EOF)
             tampon       token    marqueur      limite,
                                                  curseur
>-A------------B---------C-------------D---E#........
             tampon,  marqueur       curseur limite
             token

Voici un exemple de programme qui lit le fichier d'entrée input.txt par morceaux de 4096 octets et utilise la règle EOF.

// re2v $INPUT -o $OUTPUT
import os
import strings
const bufsize = 4096
struct State {
    file     os.File
mut:
    yyinput  []u8
    yycursor int
    yymarker int
    yylimit  int
    token    int
    eof      bool
}
fn fill(mut st &State) int {
    if st.eof { return -1 } // EOF inattendu
    // Erreur : lexème trop long. Dans la réalité, on peut réallouer un tampon plus grand.
    if st.token < 1 { return -2 }
    // Décale le contenu du tampon (rejette tout jusqu'au token courant).
    copy(mut &st.yyinput, st.yyinput[st.token..st.yylimit])
    st.yycursor -= st.token
    st.yymarker -= st.token
    st.yylimit -= st.token
    st.token = 0
    // Remplit l'espace libre à la fin du tampon avec de nouvelles données du fichier.
    pos := st.file.tell() or { 0 }
    if n := st.file.read_bytes_into(u64(pos), mut st.yyinput[st.yylimit..bufsize]) {
        st.yylimit += n
    }
    st.yyinput[st.yylimit] = 0 // ajoute le symbole sentinelle
    // Si moins que prévu a été lu, c'est la fin de l'entrée.
    st.eof = st.yylimit < bufsize
    return 0
}
fn lex(mut yyrecord &State) int {
    mut count := 0
loop:
    yyrecord.token = yyrecord.yycursor
    /*!re2c
        re2c:api = record;
        re2c:eof = 0;
        re2c:YYFILL = "fill(mut yyrecord) == 0";
        str = ['] ([^'\\] | [\\][^])* ['];
        *    { return -1 }
        $    { return count }
        str  { count += 1; unsafe { goto loop } }
        [ ]+ { unsafe { goto loop } }
    */
}
fn main() {
    fname := "input"
    content := "'qu\0tes' 'are' 'fine: \\'' ";
    // Prépare le fichier d'entrée : quelques fois la taille du tampon, contenant
    // des chaînes avec des zéros et des guillemets échappés.
    mut fw := os.create(fname)!
    fw.write_string(strings.repeat_string(content, bufsize))!
    fw.close()
    count := 3 * bufsize // nombre de chaînes entre guillemets écrites dans le fichier
    // Prépare l'état du lexer : tous les décalages sont à la fin du tampon.
    mut fr := os.open(fname)!
    mut st := &State{
        file:     fr,
        // Le sentinelle à l'offset `yylimit` est mis à zéro, ce qui déclenche YYFILL.
        yyinput:  []u8{len: bufsize + 1},
        yycursor: bufsize,
        yymarker: bufsize,
        yylimit:  bufsize,
        token:    bufsize,
        eof:      false,
    }
    // Lance le lexer.
    n := lex(mut st)
    if n != count { panic("expected $count, got $n") }
    // Nettoyage : supprime le fichier d'entrée.
    fr.close()
    os.rm(fname)!
}

YYFILL avec remplissage

Dans le cas par défaut (lorsque la règle EOF n'est pas utilisée), YYFILL est une primitive de type fonction qui accepte un seul argument et ne retourne aucune valeur. L'invocation de YYFILL est déclenchée par la condition (YYLIMIT - YYCURSOR) < n dans l'API des pointeurs C et YYLESSTHAN(n) dans l'API générique. L'argument passé à YYFILL est le nombre minimum de caractères qui doivent être fournis. S'il ne parvient pas à le faire, YYFILL ne doit pas retourner au lexer (c'est pourquoi il est préférable de l'implémenter comme une macro qui retourne de la fonction appelante en cas d'échec). En cas d'invocation réussie de YYFILL, la position limite doit être définie soit à une position après la dernière position d'entrée dans le tampon, soit à la fin du remplissage YYMAXFILL (si YYFILL a lu avec succès au moins n caractères, mais pas assez pour remplir tout le tampon). Les schémas ci-dessous montrent les emplacements relatifs des positions d'entrée dans le tampon avant et après l'invocation de YYFILL (le remplissage YYMAXFILL dans le second schéma est marqué par des symboles #).

               <-- décalage -->                 <-- besoin -->
             >-A------------B---------C-----D-------E---F--------G->
             tampon       token    marqueur curseur
limite >-A------------B---------C-----D-------E---F--------G-> tampon, curseur marqueur limite jeton <-- décalage --> <-- besoin --> >-A------------B---------C-----D-------E-F (EOF) tampon jeton curseur marqueur limite >-A------------B---------C-----D-------E-F############### tampon, curseur marqueur limite jeton <- YYMAXFILL ->

Voici un exemple de programme qui lit le fichier d'entrée input.txt par blocs de 4096 octets et utilise le contrôle des limites avec remplissage.

// re2v $INPUT -o $OUTPUT
import os
import strings
/*!max:re2c*/
const bufsize = 4096
struct State {
    file     os.File
mut:
    yyinput  []u8
    yycursor int
    yylimit  int
    token    int
    eof      bool
}
fn fill(mut st &State, need int) int {
    if st.eof { return -1 } // EOF inattendu
    // Erreur : lexème trop long. Dans la vie réelle, on peut réallouer un tampon plus grand.
    if st.token < need { return -2 }
    // Décalage du contenu du tampon (tout ignorer jusqu'au jeton courant).
    copy(mut &st.yyinput, st.yyinput[st.token..st.yylimit])
    st.yycursor -= st.token
    st.yylimit -= st.token
    st.token = 0
    // Remplissage de l'espace libre à la fin du tampon avec de nouvelles données du fichier.
    pos := st.file.tell() or { 0 }
    if n := st.file.read_bytes_into(u64(pos), mut st.yyinput[st.yylimit..bufsize]) {
        st.yylimit += n
    }
    // Si moins qu'attendu a été lu, c'est la fin de l'entrée.
    if st.yylimit < bufsize {
        st.eof = true
        for i := 0; i < yymaxfill; i += 1 { st.yyinput[st.yylimit + i] = 0 }
        st.yylimit += yymaxfill
    }
    return 0
}
fn lex(mut yyrecord &State) int {
    mut count := 0
loop:
    yyrecord.token = yyrecord.yycursor
    /*!re2c
        re2c:api = record;
        re2c:YYFILL = "r := fill(mut yyrecord, @@); if r != 0 { return r }";
        str = ['] ([^'\\] | [\\][^])* ['];
        [\x00] {
            // Vérifier qu'il s'agit du sentinelle, pas d'un zéro inattendu.
            return if yyrecord.token == (yyrecord.yylimit - yymaxfill) { count } else { -1 }
        }
        str  { count += 1; unsafe { goto loop } }
        [ ]+ { unsafe { goto loop } }
        *    { return -1 }
    */
}
fn main() {
    fname := "input"
    content := "'qu\0tes' 'are' 'fine: \\'' ";
    // Préparation du fichier d'entrée : plusieurs fois la taille du tampon, contenant
    // des chaînes avec des zéros et des guillemets échappés.
    mut fw := os.create(fname)!
    fw.write_string(strings.repeat_string(content, bufsize))!
    fw.close()
    count := 3 * bufsize // nombre de chaînes entre guillemets écrites dans le fichier
    // Préparation de l'état du lexer : tous les décalages sont à la fin du tampon.
    // Cela déclenche immédiatement YYFILL, car la condition YYLESSTHAN est vraie.
    mut fr := os.open(fname)!
    mut st := &State{
        file:     fr,
        yyinput:  []u8{len: bufsize + yymaxfill},
        yycursor: bufsize,
        yylimit:  bufsize,
        token:    bufsize,
        eof:      false,
    }
    // Exécution du lexer.
    n := lex(mut st)
    if n != count { panic("attendu $count, obtenu $n") }
    // Nettoyage : suppression du fichier d'entrée.
    fr.close()
    os.rm(fname)!
}

FONCTIONNALITÉS

Blocs multiples

Il est parfois nécessaire d'avoir plusieurs lexers interconnectés (par exemple, s'il existe une machine d'état de haut niveau qui transite entre les modes du lexer). Ceci peut être implémenté en utilisant plusieurs blocs re2v connectés. Une autre option est d'utiliser des conditions de départ.

L'implémentation des connexions entre les blocs dépend du langage cible. Dans les langages qui ont une instruction goto (comme C/C++ et Go), on peut avoir tous les blocs dans une seule fonction, chacun préfixé par une étiquette. La transition d'un bloc à un autre est un simple goto. Dans les langages qui n'ont pas de goto (comme Rust), il est nécessaire d'utiliser une boucle avec un switch sur une variable d'état, similaire à la boucle/switch yystate générée par re2v, ou d'encapsuler chaque bloc dans une fonction et d'utiliser des appels de fonction.

L'exemple ci-dessous utilise plusieurs blocs pour analyser des nombres binaires, octaux, décimaux et hexadécimaux. Chaque base a son propre bloc. Le bloc initial détermine la base et distribue vers les autres blocs. Les configurations communes sont définies dans un bloc séparé au début du programme ; elles sont héritées par les autres blocs.

// re2v $INPUT -o $OUTPUT -i
const u32_lim = u64(1) << 32
fn parse_u32(yyinput string) ?u32 {
    mut yycursor, mut yymarker := 0, 0
    mut n := u64(0)
    mut yych := 0
    adddgt := fn (num u64, base u64, digit u8) u64 {
        n := num * base + u64(digit)
        return if n >= u32_lim { u32_lim } else { n }
    }
    /*!re2c
        re2c:yyfill:enable = 0;
        re2c:yych:emit = 0;
        end = "\x00";
        '0b' / [01]        { unsafe{ goto bin } }
        "0"                { unsafe{ goto oct } }
        ""   / [1-9]       { unsafe{ goto dec } }
        '0x' / [0-9a-fA-F] { unsafe{ goto hex } }
        *                  { return none }
    */
bin:
    /*!re2c
        end   { unsafe{ goto end } }
        [01]  { n = adddgt(n, 2, yyinput[yycursor-1] - 48); unsafe{ goto bin } }
        *     { return none }
    */
oct:
    /*!re2c
        end   { unsafe{ goto end } }
        [0-7] { n = adddgt(n, 8, yyinput[yycursor-1] - 48); unsafe{ goto oct } }
        *     { return none }
    */
dec:
    /*!re2c
        end   { unsafe{ goto end } }
        [0-9] { n = adddgt(n, 10, yyinput[yycursor-1] - 48); unsafe{ goto dec } }
        *     { return none }
    */
hex:
    /*!re2c
        end   { unsafe{ goto end } }
        [0-9] { n = adddgt(n, 16, yyinput[yycursor-1] - 48); unsafe{ goto hex } }
        [a-f] { n = adddgt(n, 16, yyinput[yycursor-1] - 87); unsafe{ goto hex } }
        [A-F] { n = adddgt(n, 16, yyinput[yycursor-1] - 55); unsafe{ goto hex } }
        *     { return none }
    */
end:
    if n < u32_lim {
        return u32(n)
    }
    return none
}
fn main() {
    test := fn (num ?u32, str string) {
        if n := parse_u32(str) {
            if m := num { if n != m { panic("nombre incorrect") } }
        } else {
            if _ := num { panic("attendu none") }
        }
    }
    test(1234567890, "1234567890\0")
    test(13, "0b1101\0")
    test(0x7fe, "0x007Fe\0")
    test(0o644, "0644\0")
    test(none, "9999999999\0")
    test(none, "123??\0")
}

Conditions de démarrage

Les conditions de départ sont activées avec l'option --start-conditions. Elles fournissent un moyen d'encoder plusieurs automates interconnectés au sein du même bloc re2v.

Chaque condition correspond à un automate unique et porte un nom unique spécifié par l'utilisateur et un numéro interne unique défini par re2v. Les numéros sont utilisés pour basculer entre les conditions : le code généré utilise les primitives YYGETCOND et YYSETCOND pour obtenir la condition actuelle ou la définir à un numéro donné. Utilisez le bloc conditions, l'option --header ou la configuration re2c:header pour générer des identifiants de condition numériques. La configuration re2c:cond:enumprefix spécifie le préfixe de l'identifiant généré.

En mode condition, chaque règle doit être préfixée par une liste de noms de conditions séparés par des virgules entre chevrons, ou un caractère joker <*> pour désigner toutes les conditions. La syntaxe de la règle est étendue comme suit :

< liste-conditions > expression-régulière code
Une règle qui est fusionnée à chaque condition de la liste-conditions. Elle correspond à l'expression-régulière et exécute le code associé.
< liste-conditions > expression-régulière => condition code
Une règle qui est fusionnée à chaque condition de la liste-conditions. Elle correspond à l'expression-régulière, définit la condition actuelle à condition et exécute le code associé.
< liste-conditions > expression-régulière :=> condition

État mémorisable

Avec l'option --storable-state, re2v génère un lexer qui peut stocker son état actuel, retourner à l'appelant et reprendre plus tard les opérations exactement là où il s'était arrêté. Le mode de fonctionnement par défaut de re2v est un modèle "pull" (tirer), dans lequel le lexer demande plus d'entrée chaque fois qu'il en a besoin. Cela peut être inacceptable dans les cas où l'entrée devient disponible morceau par morceau (par exemple, si le lexer est appelé par l'analyseur, ou si le programme lexer communique via un protocole socket avec un autre programme qui doit attendre une réponse du lexer avant de transmettre le message suivant). La fonctionnalité d'état mémorisable est conçue exactement pour de tels cas : elle permet de générer des lexers qui fonctionnent selon un modèle "push" (pousser). Lorsque le lexer a besoin de plus d'entrée, il stocke son état et retourne à l'appelant. Plus tard, lorsque plus d'entrée est disponible, l'appelant reprend le lexer exactement là où il s'était arrêté. Il y a quelques modifications nécessaires par rapport au modèle "pull" :

  • Définir les primitives YYSETSTATE() et YYGETSTATE(state).
  • Définir les variables yych, yyaccept (si utilisées) et state comme faisant partie de l'état persistant du lexer. La variable state doit être initialisée à -1.
  • YYFILL doit retourner au programme externe au lieu d'essayer de fournir plus d'entrée. Le code de retour doit indiquer que le lexer a besoin de plus d'entrée.
  • Le programme externe doit reconnaître les situations où le lexer a besoin de plus d'entrée et répondre de manière appropriée.
  • Optionnellement, utiliser le bloc getstate pour générer un commutateur YYGETSTATE détaché du lexer principal. Cela ne fonctionne que pour les langages qui ont goto (pas en mode --loop-switch).
  • Utiliser re2c:eof et la méthode du *sentinelle avec vérifications de limites* pour gérer la fin de l'entrée. La méthode basée sur le remplissage peut ne pas fonctionner car il est difficile de savoir quand ajouter le remplissage : la fin actuelle de l'entrée peut ne pas être la fin ultime de l'entrée, et ajouter le remplissage trop tôt peut couper un lexème gourmand lu partiellement. De plus, en raison de la logique du programme de haut niveau, obtenir plus d'entrée peut dépendre du traitement du lexème à la fin du tampon (qui est déjà bloqué en raison de la condition de fin d'entrée).

Voici un exemple de lexer "push" qui simule la lecture de paquets depuis un socket. Le lexer boucle jusqu'à ce qu'il rencontre la fin de l'entrée et retourne à la fonction appelante. La fonction appelante fournit plus d'entrée en "envoyant" le paquet suivant et reprend l'analyse. Ce processus s'arrête lorsque tous les paquets ont été envoyés, ou en cas d'erreur.

    // du tampon.

                break
            }

            break

        panic("expected $expect with $send packet(s), got $status with $recv packet(s)")
    }
    // Nettoyage : supprimer le fichier d'entrée.
    fr.close()
    fw.close()
    os.rm(fname) or { panic("cannot remove file") }
}

Les blocs réutilisables de la forme /*!rules:re2c[:<name>] ... */ ou %{rules[:<name>] ... %} peuvent être réutilisés un nombre quelconque de fois et combinés avec d'autres blocs re2v. Le <name> est facultatif. Un bloc de règles peut être utilisé dans un bloc ou une directive use. Le code d'un bloc de règles est généré à chaque point d'utilisation.

Les blocs d'utilisation sont définis avec /*!use:re2c[:<name>] ... */ ou %{use[:<name>] ... %}. Le <name> est facultatif : s'il n'est pas spécifié, le bloc de règles associé est le plus récent (nommé ou non). Un bloc d'utilisation peut ajouter des définitions nommées, des configurations et des règles propres. Un cas d'utilisation important pour les blocs d'utilisation est un lexer qui prend en charge plusieurs encodages d'entrée : le même bloc de règles est réutilisé plusieurs fois avec des configurations spécifiques à l'encodage (voir l'exemple ci-dessous).

La directive d'utilisation en bloc !use:<name>; peut être utilisée à l'intérieur d'un bloc re2c. Elle fusionne le bloc référencé <name> dans celui actuel. Si certaines des règles et configurations fusionnées chevauchent celles définies précédemment, les conflits sont résolus de la manière habituelle : la première règle rencontrée a la priorité, et la dernière configuration écrase les précédentes. Une exception concerne les règles spéciales *, $ et (en mode condition) <!>, pour lesquelles une définition locale au bloc remplace toutes les définitions héritées. La directive d'utilisation permet de combiner différents blocs re2c dans un seul bloc (voir l'exemple ci-dessous).

Les blocs nommés et la directive d'utilisation en bloc ont été ajoutés dans la version 2.2 de re2c. Depuis cette version, les blocs réutilisables sont autorisés par défaut (aucune option spéciale n'est nécessaire). Avant la version 2.2, le mode réutilisable était activé avec l'option -r --reusable. Avant la version 1.2, les blocs réutilisables ne pouvaient pas être mélangés avec des blocs normaux.

    versions.
    

    

    

    // re2v $INPUT -o $OUTPUT
struct SemVer {
    major int
    minor int
    patch int
}
fn s2n(s string) int { // convert pre-parsed string to number
    mut n := 0
    for c in s { n = n * 10 + int(c - 48) }
    return n
}
fn parse(yyinput string) ?SemVer {
    mut yycursor, mut yymarker := 0, 0
    // Final tag variables available in semantic action.
    /*!svars:re2c format = 'mut @@ := 0\n'; */
    // Intermediate tag variables used by the lexer (must be autogenerated).
    /*!stags:re2c format = 'mut @@ := 0\n'; */
    /*!re2c
        re2c:yyfill:enable = 0;
        re2c:captvars = 1;
        num = [0-9]+;
        (num) "." (num) ("." num)? [\x00] {
            _ := yytl0; _ := yytr0 // some variables are unused
            return SemVer {
                major: s2n(yyinput[yytl1..yytr1]),
                minor: s2n(yyinput[yytl2..yytr2]),
                patch: if yytl3 == -1 {0} else {s2n(yyinput[yytl3 + 1..yytr3])}
            }
        }
        * { return none }
    */
}
fn main() {
    test := fn (result ?SemVer, expect ?SemVer) {
        if r := result {
            if e := expect { if r != e { panic("expected $e, got $r") } }
        } else {
            if _ := result { panic("expected none") }
        }
    }
    test(parse("23.34\0"), SemVer{23, 34, 0})
    test(parse("1.2.9999\0"), SemVer{1, 2, 9999})
    test(parse("1.a\0"), none)
}
    

    

    

    Here is an example of using m-tags to parse a version with a
    variable number of components. Tag variables are stored in a trie.
    

    

    

    // re2v $INPUT -o $OUTPUT
import arrays
const mtag_root = -1
const tag_none = -1
// An m-tag tree is a way to store histories with an O(1) copy operation.
// Histories naturally form a tree, as they have common start and fork at some
// point. The tree is stored as an array of pairs (tag value, link to parent).
// An m-tag is represented with a single link in the tree (array index).
struct MtagElem {
    elem int
    pred int
}
type MtagTrie = []MtagElem
// Append a single value to an m-tag history.
fn add_mtag(mut trie &MtagTrie, mtag int, value int) int {
    trie = arrays.concat(trie, MtagElem{value, mtag})
    return trie.len - 1
}
// Recursively unwind tag histories and collect version components.
fn unwind(trie MtagTrie, x int, y int, str string) []int {
    // Reached the root of the m-tag tree, stop recursion.
    if x == mtag_root && y == mtag_root {
        return []
    }
    // Unwind history further.
    mut result := unwind(trie, trie[x].pred, trie[y].pred, str)
    // Get tag values. Tag histories must have equal length.
    if x == mtag_root || y == mtag_root {
        panic("tag histories have different length")
    }
    ex := trie[x].elem
    ey := trie[y].elem
    if ex != tag_none && ey != tag_none {
        // Both tags are valid string indices, extract component.
        result = arrays.concat(result, s2n(str[ex..ey]))
    } else if !(ex == tag_none && ey == tag_none) {
        panic("both tags should be tag_none")
    }
    return result
}
fn s2n(s string) int { // convert pre-parsed string to number
    mut n := 0
    for c in s { n = n * 10 + int(c - 48) }
    return n
}
fn parse(yyinput string) ?[]int {
    mut yycursor, mut yymarker := 0, 0
    mut trie := []MtagElem{}
    // Final tag variables available in semantic action.
    /*!svars:re2c format = 'mut @@ := tag_none\n'; */
    /*!mvars:re2c format = "mut @@ := mtag_root\n"; */
    // Intermediate tag variables used by the lexer (must be autogenerated).
    /*!stags:re2c format = 'mut @@ := tag_none\n'; */
    /*!mtags:re2c format = "mut @@ := mtag_root\n"; */
    /*!re2c
        re2c:tags = 1;
        re2c:yyfill:enable = 0;
        re2c:YYMTAGP = "@@ = add_mtag(mut &trie, @@, yycursor)";
        re2c:YYMTAGN = "@@ = add_mtag(mut &trie, @@, tag_none)";
        num = [0-9]+;
        @t1 num @t2 ("." #t3 num #t4)* [\x00] {
            mut ver := []int{}
            ver = arrays.concat(ver, s2n(yyinput[t1..t2]))
            ver = arrays.append(ver, unwind(trie, t3, t4, yyinput))
            return ver
        }
        * { return none }
    */
}
fn main() {
    test := fn (result ?[]int, expect ?[]int) {
        if r := result {
            if e := expect { if r != e { panic("expected $e, got $r") } }
        } else {
            if _ := result { panic("expected none") }
        }
    }
    test(parse("1\0"), [1])
    test(parse("1.2.3.4.5.6.7\0"), [1, 2, 3, 4, 5, 6, 7])
    test(parse("1.\0"), none)
}
    

    

    

    

    

    Encoding   support
    

    It is necessary to understand the difference between code
    points and code units. A code point is a numeric identifier of a
    symbol. A code unit is the smallest unit of storage in the encoded text. A
    single code point may be represented with one or more code units. In a
    fixed-length encoding all code points are represented with the same number
    of code units. In a variable-length encoding code points may be represented
    with a different number of code units. Note that the "any" rule
    [^] matches any code point, but not necessarily any code unit (the
    only way to match any code unit regardless of the encoding is the default
    rule *). The generated lexer works with a stream of code units:
    yych stores a code unit, and YYCTYPE is the code unit type.
    Regular expressions, on the other hand, are specified in terms of code
    points. When re2v compiles regular expressions to automata it translates
    code points to code units. This is generally not a simple mapping: in
    variable-length encodings a single code point range may get translated to a
    complex code unit graph. The following encodings are supported:
    

    

      
  
    • ASCII (enabled by default). It is a fixed-length encoding with code
      space [0-255] and 1-byte code points and code units.
      • 
  
    • EBCDIC (enabled with --ebcdic or
      re2c:encoding:ebcdic). It is a fixed-length encoding with code
      space [0-255] and 1-byte code points and code units.
      • 
  
    • UCS2 (enabled with --ucs2 or re2c:encoding:ucs2). It
      is a fixed-length encoding with code space [0-0xFFFF] and 2-byte
      code points and code units.
      • 
  
    • UTF8 (enabled with --utf8 or re2c:encoding:utf8). It
      is a variable-length Unicode encoding. Code unit size is 1 byte. Code
      points are represented with 1 -- 4 code units.
      • 
  
    • UTF16 (enabled with --utf16 or re2c:encoding:utf16).
      It is a variable-length Unicode encoding. Code unit size is 2 bytes. Code
      points are represented with 1 -- 2 code units.
      • 
  
    • UTF32 (enabled with --utf32 or re2c:encoding:utf32).
      It is a fixed-length Unicode encoding with code space [0-0x10FFFF]
      and 4-byte code points and code units.
      • 

    

    

    Include file include/unicode_categories.re provides re2v
    definitions for the standard Unicode categories.
    

    Option --input-encoding specifies source file encoding,
    which can be used to enable Unicode literals in regular expressions. For
    example --input-encoding utf8 tells re2v that the source file is in
    UTF8 (it differs from --utf8 which sets input text encoding). Option
    --encoding-policy specifies the way re2v handles Unicode surrogates
    (code points in range [0xD800-0xDFFF]).
    

    Below is an example of a lexer for UTF8 encoded Unicode
    identifiers.
    

    

    

    // re2v $INPUT -o $OUTPUT --utf8 -si
/*!include:re2c "unicode_categories.re" */
fn lex(yyinput string) int {
    mut yycursor, mut yymarker := 0, 0
    /*!re2c
        re2c:yyfill:enable = 0;
        // Simplified "Unicode Identifier and Pattern Syntax"
        // (see https://unicode.org/reports/tr31)
        id_start    = L | Nl | [$_];
        id_continue = id_start | Mn | Mc | Nd | Pc | [\u200D\u05F3];
        identifier  = id_start id_continue*;
        identifier { return 0 }
        *          { return 1 }
    */
}
fn main() {
    if lex("_Ыдентификатор\0") != 0 {
        panic("error")
    }
}
    

    

    

    

    

    Include   files
    

    re2v allows one to include other files using a block of the form
    /*!include:re2c FILE */ or %{include FILE %}, or an in-block
    directive !include FILE ;, where FILE is a path to the file to
    be included. re2v looks for include files in the directory of the including
    file and in include locations, which can be specified with the -I
    option. Include blocks/directives in re2v work in the same way as C/C++
    #include: FILE contents are copy-pasted verbatim in place of
    the block/directive. Include files may have further includes of their own.
    Use --depfile option to track build dependencies of the output file
    on include files. re2v provides some predefined include files that can be
    found in the include/ subdirectory of the project. These files
    contain definitions that may be useful to other projects (such as Unicode
    categories) and form something like a standard library for re2v. Below is an
    example of using include files.

Input file

// re2c $INPUT -o $OUTPUT -i
/*!include:re2c "definitions.v" */
fn lex(yyinput string) Result {
    mut yycursor, mut yymarker := 0, 0
    /*!re2c
        re2c:yyfill:enable = 0;
        *      { return .fail }
        number { return .ok }
        !include "extra_rules.re.inc";
    */
}
fn main() {
    assert lex("123\0") == .ok
    assert lex("123.4567\0") == .ok
}

Header files

re2v allows one to generate header file from the input .re file using --header option or re2c:header configuration and block pairs of the form /*!header:re2c:on*/ and /*!header:re2c:off*/, or %{header:on%} and %{header:off%}. The first block marks the beginning of header file, and the second block marks the end of it. Everything between these blocks is processed by re2v, and the generated code is written to the file specified with --header option or re2c:header configuration (or stdout if neither option nor configuration is used). Autogenerated header file may be needed in cases when re2v is used to generate definitions that must be visible from other translation units.

Here is an example of generating a header file that contains definition of the lexer state with tag variables (the number variables depends on the regular grammar and is unknown to the programmer).

Input file

// re2v $INPUT -o $OUTPUT -i --header lexer/state.v
module main
import lexer // the package is generated by re2c
/*!header:re2c:on*/
module lexer
pub struct State {
pub mut:
    yyinput string
    yycursor int
    /*!stags:re2c format="@@ int\n"; */
}
/*!header:re2c:off*/
fn lex(mut yyrecord &lexer.State) int {
    mut t := 0
    /*!re2c
        re2c:header = "lexer/state.v";
        re2c:api = record;
        re2c:yyfill:enable = 0;
        re2c:tags = 1;
        [a]* @t [b]* { return t }
    */
}
fn main() {
    mut st := &lexer.State{yyinput:"ab\0",}
    if lex(mut st) != 1 {
        panic("error")
    }
}

Skeleton programs

With the -S, --skeleton option, re2v ignores all non-re2v code and generates a self-contained C program that can be further compiled and executed. The program consists of lexer code and input data. For each constructed DFA (block or condition) re2v generates a standalone lexer and two files: an .input file with strings derived from the DFA and a .keys file with expected match results. The program runs each lexer on the corresponding .input file and compares results with the expectations. Skeleton programs are very useful for a number of reasons:

  • They can check correctness of various re2v optimizations (the data is generated early in the process, before any DFA transformations have taken place).
  • Generating a set of input data with good coverage may be useful for both testing and benchmarking.
  • Generating self-contained executable programs allows one to get minimized test cases (the original code may be large or have a lot of dependencies).

The difficulty with generating input data is that for all but the most trivial cases the number of possible input strings is too large (even if the string length is limited). re2v solves this difficulty by generating sufficiently many strings to cover almost all DFA transitions. It uses the following algorithm. First, it constructs a skeleton of the DFA. For encodings with 1-byte code unit size (such as ASCII, UTF-8 and EBCDIC) skeleton is just an exact copy of the original DFA. For encodings with multibyte code units skeleton is a copy of DFA with certain transitions omitted: namely, re2v takes at most 256 code units for each disjoint continuous range that corresponds to a DFA transition. The chosen values are evenly distributed and include range bounds. Instead of trying to cover all possible paths in the skeleton (which is infeasible) re2v generates sufficiently many paths to cover all skeleton transitions, and thus trigger the corresponding conditional jumps in the lexer. The algorithm implementation is limited by ~1Gb of transitions and consumes constant amount of memory (re2v writes data to file as soon as it is generated).

Visualization and debug

With the -D, --emit-dot option, re2v does not generate code. Instead, it dumps the generated DFA in DOT format. One can convert this dump to an image of the DFA using Graphviz or another library. Note that this option shows the final DFA after it has gone through a number of optimizations and transformations. Earlier stages can be dumped with various debug options, such as --dump-nfa, --dump-dfa-raw etc. (see the full list of options).
