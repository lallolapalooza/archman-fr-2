NOM

re2d - générer des analyseurs lexicaux rapides pour D

SYNTAXE

re2d [ OPTIONS ] [ AVERTISSEMENTS ] ENTREE

L'entrée peut être un fichier ou - pour l'entrée standard.

INTRODUCTION

re2d fonctionne comme un préprocesseur. Il lit le fichier d'entrée (qui est généralement un programme en D, mais peut être n'importe quoi) et recherche des blocs de code délimités par des marqueurs de début/fin de forme spéciale. Le texte en dehors de ces blocs est copié tel quel dans le fichier de sortie. Le contenu des blocs est traité par re2d. Il les traduit en code D et génère le code résultant à la place du bloc.

Voici un exemple de petit programme qui vérifie si une chaîne donnée contient un nombre décimal :

// re2d $INPUT -o $OUTPUT -i
module main;
private bool lex(const(char)* yycursor) {
    /*!re2c
        re2c:YYCTYPE = char;
        re2c:yyfill:enable = 0;
        [1-9][0-9]* { return true; }
        *           { return false; }
    */
}
void main() {
    assert(lex("1234"));
}

Dans la sortie, re2d a remplacé le bloc du milieu par le code généré :

/* Généré par re2d */
// re2d $INPUT -o $OUTPUT -i
module main;
private bool lex(const(char)* yycursor) {
{
    char yych;
    yych = *yycursor;
    switch (yych) {
        case '1': .. case '9': goto yy2;
        default: goto yy1;
    }
yy1:
    ++yycursor;
    { return false; }
yy2:
    yych = *++yycursor;
    switch (yych) {
        case '0': .. case '9': goto yy2;
        default: goto yy3;
    }
yy3:
    { return true; }
}
}
void main() {
    assert(lex("1234"));
}

BASES

Un programme re2d consiste en une séquence de blocs entremêlés avec du code dans le langage cible. Un bloc peut contenir des définitions, des configurations, des règles, des actions et des directives dans n'importe quel ordre :

nom = expression-régulière ;
Une définition lie nom à expression-régulière. Les noms peuvent contenir des caractères alphanumériques et le trait de soulignement. La section expressions-régulières donne un aperçu de la syntaxe de re2d pour les expressions régulières. Une fois défini, le nom peut être utilisé dans d'autres expressions régulières et dans des règles. La récursion dans les définitions nommées n'est pas autorisée, et chaque nom doit être défini avant d'être utilisé. Un bloc hérite des définitions nommées de la portée globale. Redéfinir un nom qui existe dans la portée actuelle est une erreur.
configuration = valeur ;
Une configuration permet de modifier le comportement de re2d et de personnaliser le code généré. Pour une liste complète des configurations supportées par re2d, voir la section configurations. Selon la configuration, la valeur peut être un mot-clé, un nombre entier non négatif ou une chaîne de caractères sur une seule ligne qui doit être entre guillemets doubles ou simples, sauf si elle est composée de caractères alphanumériques. Un bloc hérite des configurations de la portée globale et peut les redéfinir ou en ajouter de nouvelles. Les configurations définies à l'intérieur d'un bloc affectent tout le bloc, même si elles apparaissent à la fin de celui-ci.
expression-régulière code
Une règle lie une expression-régulière à son action sémantique (un bloc de code entre accolades, ou un bloc de code commençant par := et se terminant par un retour à la ligne suivi d'un caractère non blanc). Si l'expression-régulière correspond, le code associé est exécuté. Si plusieurs règles correspondent, la correspondance la plus longue a la priorité. Si plusieurs règles correspondent à la même chaîne, la première d'entre elles a la priorité. Il existe deux règles spéciales : la règle par défaut * et la règle de fin d'entrée $. La règle par défaut doit toujours être définie, elle a la priorité la plus basse quelle que soit sa place dans le bloc, et elle correspond à n'importe quelle unité de code (pas nécessairement un caractère valide, voir la section support de l'encodage). La règle de fin d'entrée doit être définie si la méthode correspondante pour la gestion de la fin d'entrée est utilisée. Avec les conditions de départ, les règles ont une syntaxe plus complexe.
!action code
Une action lie un bloc de code défini par l'utilisateur à un endroit particulier dans la machine à états finis générée (de la même manière que les actions sémantiques lient du code aux états finaux). Voir la section actions pour une liste complète des actions prédéfinies.
!directive ;
Une directive est l'une des instructions prédéfinies spéciales. Chaque directive a un but unique. Voir la section directives pour plus de détails.

Blocs

Les marqueurs de début et de fin de bloc sont soit /*!re2c et */, soit %{ et %} (les deux styles sont pris en charge). Depuis la version 2.2, les blocs peuvent avoir des noms optionnels qui permettent de les référencer dans d'autres blocs. Il existe différents types de blocs :

/*!re2c[:<nom>] ... */ ou %{[:<nom>] ... %}
Un bloc global contient des définitions, des configurations, des règles et des directives. re2d compile les expressions régulières associées à chaque règle en un automate fini déterministe, l'encode sous forme de sauts conditionnels dans le langage cible et remplace le bloc par le code généré. Les noms et configurations définis dans un bloc global sont ajoutés à la portée globale et deviennent visibles pour les blocs suivants. Au début du programme, la portée globale est initialisée avec les options de la ligne de commande.
/*!local:re2c[:<nom>] ... */ ou %{local[:<nom>] ... %}
Un bloc local est similaire à un bloc global, mais les noms et configurations qu'il contient ont une portée locale (ils n'affectent pas les autres blocs).
/*!rules:re2c[:<nom>] ... */ ou %{rules[:<nom>] ... %}
Un bloc de règles est similaire à un bloc local, mais il ne génère aucun code en soi, ni n'ajoute de définitions à la portée globale -- il est destiné à être réutilisé dans d'autres blocs. C'est une façon de partager du code (plus de détails dans la section blocs réutilisables). Avant la version 2.2 de re2d, les blocs de règles nécessitaient l'option -r --reusable.
/*!use:re2c[:<nom>] ... */ ou %{use[:<nom>] ... %}
Un bloc d'utilisation qui référence un bloc de règles défini précédemment. Si un nom est spécifié, re2d recherche des blocs de règles portant ce nom. Sinon, le bloc de règles le plus récent est utilisé (nommé ou non nommé). Un bloc d'utilisation peut ajouter ses propres définitions, configurations et règles, qui sont ajoutées à celles du bloc de règles référencé. Avant la version 2.2 de re2d, les blocs d'utilisation nécessitaient l'option -r --reusable.
/*!max:re2c[:<nom1>[:<nom2>...]] ... */ ou %{max[:<nom1>[:<nom2>...]] ... %}
Un bloc qui génère la définition YYMAXFILL. Une liste optionnelle de noms de blocs spécifie quels blocs doivent être inclus lors du calcul de la valeur YYMAXFILL (si la liste est vide, tous les blocs sont inclus). Par défaut, le code généré est une macro-définition pour C (#define YYMAXFILL <n>), ou une variable globale pour Go (var YYMAXFILL int = <n>). Il peut être personnalisé avec une configuration optionnelle format qui spécifie une chaîne de modèle où @@{max} (ou @@ pour faire court) est remplacé par la valeur numérique de YYMAXFILL.
/*!maxnmatch:re2c[:<nom1>[:<nom2>...]] ... */ ou %{maxnmatch[:<nom1>[:<nom2>...]] ... %}
Un bloc qui génère la définition YYMAXNMATCH (nécessite l'option -P --posix-captures). Une liste optionnelle de noms de blocs spécifie quels blocs doivent être inclus lors du calcul de la valeur YYMAXNMATCH (si la liste est vide, tous les blocs sont inclus). Par défaut, le code généré est une macro-définition pour C (#define YYMAXNMATCH <n>), ou une variable globale pour Go (var YYMAXNMATCH int = <n>). Il peut être personnalisé avec une configuration optionnelle format qui spécifie une chaîne de modèle où @@{max} (ou @@ pour faire court) est remplacé par la valeur numérique de YYMAXNMATCH.
/*!stags:re2c[:<nom1>[:<nom2>...]] ... */, /*!mtags:re2c[:<nom1>[:<nom2>...]] ... */ ou %{stags[:<nom1>[:<nom2>...]] ... %}, %{mtags[:<nom1>
gt;[:<nom2>...]] ... %{
Blocs qui spécifient un morceau de code modèle qui est étendu pour chaque variable de balise s/m générée par re2d. Une liste optionnelle de noms de blocs spécifie quels blocs doivent être inclus lors du calcul de l'ensemble des variables de balise (si la liste est vide, tous les blocs sont inclus). Il existe deux configurations optionnelles : format et séparateur. La configuration format spécifie une chaîne de modèle où @@{balise} (ou @@ en abrégé) est remplacé par le nom de chaque variable de balise. La configuration séparateur spécifie un morceau de code utilisé pour joindre les morceaux de format générés pour différentes variables de balise.
/*!svars:re2c[:<nom1>[:<nom2>...]] ... */, /*!mvars:re2c[:<nom1>[:<nom2>...]] ... */ ou %{svars[:<nom1>[:<nom2>...]] ... %}, %{mvars[:<nom1>[:<nom2>...]] ... %{
Blocs qui spécifient un morceau de code modèle qui est étendu pour chaque balise s/m qui est soit explicitement mentionnée par les règles (avec l'option --tags) soit implicitement générée par re2d (avec les options --captvars ou --posix-captvars). Une liste optionnelle de noms de blocs spécifie quels blocs doivent être inclus lors du calcul de l'ensemble des balises (si la liste est vide, tous les blocs sont inclus). Il existe deux configurations optionnelles : format et séparateur. La configuration format spécifie une chaîne de modèle où @@{balise} (ou @@ en abrégé) est remplacé par le nom de chaque balise. La configuration séparateur spécifie un morceau de code utilisé pour joindre les morceaux de format générés pour différentes balises.
/*!getstate:re2c[:<nom1>[:<nom2>...]] ... */ ou %{getstate[:<nom1>[:<nom2>...]] ... %}
Un bloc qui génère une répartition conditionnelle sur l'état de l'analyseur lexical (cela nécessite l'option --storable-state). Une liste optionnelle de noms de blocs spécifie quels blocs doivent être inclus dans la répartition d'état. La transition par défaut va au label de début du premier bloc de la liste. Si la liste est vide, tous les blocs sont inclus, et la transition par défaut va au premier bloc du fichier qui a un label de début. Ce type de bloc est incompatible avec l'option --loop-switch, car il nécessite des transitions inter-blocs qui ne sont pas prises en charge sans goto ou appels de fonction.
/*!conditions:re2c[:<nom1>[:<nom2>...]] ... */, /*!types:re2c... */ ou %{conditions[:<nom1>[:<nom2>...]] ... %}, %{types... %}
Un bloc qui génère une énumération de conditions (cela nécessite l'option --conditions). Une liste optionnelle de noms de blocs spécifie quels blocs doivent être inclus lors du calcul de l'ensemble des conditions (si la liste est vide, tous les blocs sont inclus). Par défaut, le code généré est une énumération YYCONDTYPE. Il peut être personnalisé avec les configurations optionnelles format et séparateur. La configuration format spécifie une chaîne de modèle où @@{cond} (ou @@ en abrégé) est remplacé par le nom de chaque condition, et @@{num} est remplacé par un index numérique de cette condition. La configuration séparateur spécifie un morceau de code utilisé pour joindre les morceaux de format générés pour différentes conditions.
/*!include:re2c <fichier> */ ou %{include <fichier> %}
Ce bloc permet d'inclure <fichier>, qui doit être un chemin de fichier entre guillemets doubles. Le contenu du fichier est littéralement substitué à la place du bloc, de la même manière que #include fonctionne en C/C++. Ce bloc peut être utilisé conjointement avec l'option --depfile pour générer des dépendances de système de construction sur les fichiers inclus.
/*!header:re2c:on*/ ou %{header:on %}
Ce bloc marque le début du fichier d'en-tête. Tout ce qui suit et jusqu'au bloc header:off suivant est traité par re2d et écrit dans le fichier d'en-tête spécifié avec l'option -t --type-header.
/*!header:re2c:off*/ ou %{header:off %}
Ce bloc marque la fin du fichier d'en-tête commencé avec le bloc header:on*/.
/*!ignore:re2c ... */ ou %{ignore ... %}
Un bloc dont le contenu est ignoré et supprimé du fichier de sortie.

Configurations

Voici une liste complète des configurations prises en charge par re2d :

re2c:api, re2c:input
Identique à l'option --api.
re2c:api:sigil
Spécifie le marqueur ("sigil") utilisé pour les espaces réservés d'arguments dans les primitives d'API. La valeur par défaut est @@. Un espace réservé commence par un sigil suivi du nom de l'argument entre accolades. Par exemple, si le sigil est défini sur $, les espaces réservés auront la forme ${nom}. Les API à argument unique peuvent utiliser une notation abrégée sans le nom entre accolades. Cette option peut être remplacée par des options pour les primitives d'API individuelles, par exemple re2c:YYFILL@len pour YYFILL.
re2c:api:style
Spécifie le style de l'API. Les valeurs possibles sont functions (par défaut pour C) et free-form (par défaut pour Go et Rust). En style functions, les primitives d'API sont générées avec une liste d'arguments entre parenthèses suivant le nom de la primitive. Les arguments sont fournis uniquement pour les paramètres autogénérés (tels que le nombre de caractères passés à YYFILL), mais pas pour le contexte général de l'analyseur lexical, de sorte que les primitives se comportent davantage comme des macros en C/C++ ou des fermetures en Go et Rust. En style free-form, les primitives d'API n'ont pas de forme fixe : elles doivent être définies comme des chaînes contenant des morceaux de code libres avec des variables interpolées de la forme @@{var} ou @@ (elles correspondent aux arguments en style fonctionnel). Cette configuration peut être remplacée pour des primitives d'API individuelles, voir par exemple la configuration re2c:YYFILL:naked pour YYFILL.
re2c:bit-vectors, re2c:flags:bit-vectors, re2c:flags:b
Identique à l'option --bit-vectors, mais peut être configuré par bloc.
re2c:captures, re2c:leftmost-captures
Identique à l'option --leftmost-captures, mais peut être configuré par bloc.
re2c:captvars, re2c:leftmost-captvars
Identique à l'option --leftmost-captvars, mais peut être configuré par bloc.
re2c:case-insensitive, re2c:flags:case-insensitive
Identique à l'option --case-insensitive, mais peut être configuré par bloc.
re2c:case-inverted, re2c:flags:case-inverted
Identique à l'option --case-inverted, mais peut être configuré par bloc.
re2c:case-ranges, re2c:flags:case-ranges
Identique à l'option --case-ranges, mais peut être configuré par bloc.
re2c:computed-gotos, re2c:flags:computed-gotos, re2c:flags:g
Identique à l'option --computed-gotos, mais peut être configuré par bloc.
re2c:computed-gotos:relative, re2c:cgoto:relative
Identique à l'option --computed-gotos-relative, mais peut être configuré par bloc.
re2c:computed-gotos:threshold, re2c:cgoto:threshold
Si les goto calculés sont utilisés, cette configuration spécifie le seuil de complexité qui déclenche la génération de tables de sauts au lieu de structures if imbriquées et de bitmaps. La valeur par défaut est 9.
re2c:cond:abort
Si défini sur une valeur entière positive, le cas par défaut dans la répartition de conditions générée interrompt l'exécution du programme.
re2c:cond:goto
Spécifie un morceau de code utilisé pour les règles de raccourci auto-générées :=> dans les conditions. Par défaut, c'est goto @@;. L'espace réservé @@ est substitué par le nom de la condition (voir les configurations re2c:api:sigil et re2c:cond:goto@cond).
re2c:cond:goto@cond
Spécifie le sigil utilisé pour la substitution d'arguments dans la définition de re2c:cond:goto. La valeur par défaut est @@. Remplace la configuration plus générique re2c:api:sigil.
re2c:cond:divider
Définit le diviseur pour les blocs de conditions. La valeur par défaut est /* *********************************** */. Les espaces réservés sont substitués par le nom de la condition (voir re2c:api;sigil et re2c:cond:divider@cond).
re2c:cond:divider@cond
Spécifie le sigil utilisé pour la substitution d'arguments dans la définition de re2c:cond:divider. La valeur par défaut est @@. Remplace la configuration plus générique re2c:api:sigil.
re2c:cond:prefix, re2c:condprefix
Spécifie le préfixe utilisé pour les labels de condition. La valeur par défaut est yyc_.
re2c:cond:enumprefix, re2c:condenumprefix
Spécifie le préfixe utilisé pour les identifiants de condition. La valeur par défaut est yyc.
re2c:debug-output, re2c:flags:debug-output, re2c:flags:d
Identique à l'option --debug-output, mais peut être configuré par bloc.
re2c:empty-class, re2c:flags:empty-class
Identique à l'option --empty-class, mais peut être configuré par bloc.
re2c:en coding:ebcdic, re2c:flags:ecb, re2c:flags:e
Identique à l'option --ebcdic, mais peut être configuré par bloc.
re2c:encoding:ucs2, re2c:flags:wide-chars, re2c:flags:w
Identique à l'option --ucs2, mais peut être configuré par bloc.
re2c:encoding:utf8, re2c:flags:utf-8, re2c:flags:8
Identique à l'option --utf8, mais peut être configuré par bloc.
re2c:encoding:utf16, re2c:flags:utf-16, re2c:flags:x
Identique à l'option --utf16, mais peut être configuré par bloc.
re2c:encoding:utf32, re2c:flags:unicode, re2c:flags:u
Identique à l'option --utf32, mais peut être configuré par bloc.
re2c:encoding-policy, re2c:flags:encoding-policy
Identique à l'option --encoding-policy, mais peut être configuré par bloc.
re2c:eof
Spécifie le symbole sentinelle utilisé avec la règle de fin de fichier $. La valeur par défaut est -1 (la règle $ n'est pas utilisée). D'autres valeurs possibles incluent toutes les unités de code valides. Seuls les nombres décimaux sont reconnus.
re2c:header, re2c:flags:type-header, re2c:flags:t
Spécifie le nom du fichier d'en-tête généré par rapport au répertoire du fichier de sortie. Identique à l'option --header, sauf que le chemin du fichier est relatif.
re2c:indent:string
Spécifie la chaîne utilisée pour l'indentation. La valeur par défaut est un seul caractère tabulation "\t". La chaîne d'indentation doit contenir uniquement des caractères d'espacement. Pour désactiver complètement l'indentation, définissez cette configuration sur une chaîne vide.
re2c:indent:top
Spécifie le montant minimum d'indentation à utiliser. La valeur par défaut est zéro. La valeur doit être un nombre entier non négatif.
re2c:invert-captures
Identique à l'option --invert-captures, mais peut être configuré par bloc.
re2c:label:prefix, re2c:labelprefix
Spécifie le préfixe utilisé pour les étiquettes d'état DFA. La valeur par défaut est yy.
re2c:label:start, re2c:startlabel
Contrôle la génération d'une étiquette de début de bloc. La valeur par défaut est zéro, ce qui signifie que l'étiquette de début est générée uniquement si elle est utilisée. Une valeur entière supérieure à zéro force la génération de l'étiquette de début même si elle n'est pas utilisée par le lexer. Une valeur de chaîne force également la génération de l'étiquette de début et définit le nom de l'étiquette sur la chaîne spécifiée. Cette configuration s'applique uniquement au bloc actuel (elle est réinitialisée à la valeur par défaut pour le bloc suivant).
re2c:label:yyFillLabel
Spécifie le préfixe des étiquettes YYFILL utilisées avec re2c:eof et en mode état stockable.
re2c:label:yyloop
Spécifie le nom de l'étiquette marquant le début de la boucle du lexer avec l'option --loop-switch. La valeur par défaut est yyloop.
re2c:label:yyNext
Spécifie le nom de l'étiquette optionnelle qui suit le switch YYGETSTATE en mode état stockable (activé avec re2c:state:nextlabel). La valeur par défaut est yyNext.
re2c:lookahead, re2c:flags:lookahead
Obsolète (voir l'option obsolète --no-lookahead).
re2c:monadic
Si défini sur une valeur non nulle, le lexer généré utilisera la notation monadique (cette configuration est spécifique à Haskell).
re2c:nested-ifs, re2c:flags:nested-ifs, re2c:flags:s
Identique à l'option --nested-ifs, mais peut être configuré par bloc.
re2c:posix-captures, re2c:flags:posix-captures, re2c:flags:P
Identique à l'option --posix-captures, mais peut être configuré par bloc.
re2c:posix-captvars
Identique à l'option --posix-captvars, mais peut être configuré par bloc.
re2c:tags, re2c:flags:tags, re2c:flags:T
Identique à l'option --tags, mais peut être configuré par bloc.
re2c:tags:expression
Spécifie l'expression utilisée pour les variables de balise. Par défaut, re2d génère des expressions de la forme yyt<N>. Cela peut être gênant, par exemple si les variables de balise sont définies comme des champs dans une structure. Toutes les occurrences de @@{tag} ou @@ sont remplacées par le nom de balise réel. Par exemple, re2c:tags:expression = "s.@@"; donne des expressions de la forme s.yyt<N> dans le code généré. Voir également la configuration re2c:api:sigil.
re2c:tags:negative
Spécifie l'expression constante utilisée pour la valeur négative de la balise (typiquement ce serait -1 si les balises sont des décalages d'entiers dans la chaîne d'entrée, ou un pointeur nul si ce sont des pointeurs).
re2c:tags:prefix
Spécifie le préfixe pour les noms de variables de balise. La valeur par défaut est yyt.
re2c:sentinel
Spécifie le symbole sentinelle utilisé pour les vérifications de fin de fichier (lorsque les vérifications de limites sont désactivées avec re2c:yyfill:enable = 0; et que re2c:eof n'est pas défini). Cette configuration n'affecte pas la génération de code : son but est de vérifier que la sentinelle n'est pas autorisée au milieu d'une règle, et de s'assurer que le lexer ne lira pas au-delà de la fin du tampon. La valeur par défaut est -1` (dans ce cas, re2d suppose que la sentinelle est zéro, ce qui est le cas le plus courant). Seuls les nombres décimaux sont reconnus.
re2c:state:abort
Si défini sur une valeur entière positive, le cas par défaut dans la distribution d'état générée avorte l'exécution du programme, et un cas explicite -1 contient une transition vers le début du bloc.
re2c:state:nextlabel
Contrôle si le switch YYGETSTATE est suivi d'une étiquette yyNext (la valeur par défaut est zéro, ce qui correspond à aucune étiquette). Alternativement, on peut utiliser re2c:label:start pour générer une étiquette de début spécifique, ou un bloc getstate explicite pour générer le switch YYGETSTATE séparément du bloc lexer.
re2c:unsafe, re2c:flags:unsafe
Identique à l'option --no-unsafe, mais peut être configuré par bloc. Si défini sur zéro, il supprime la génération d'enveloppes unsafe autour de YYPEEK. La valeur par défaut est non nulle (les enveloppes sont générées). Cette configuration est spécifique à Rust.
re2c:YYBACKUP, re2c:define:YYBACKUP
Définit la primitive API générique YYBACKUP.
re2c:YYBACKUPCTX, re2c:define:YYBACKUPCTX
Définit la primitive API générique YYBACKUPCTX.
re2c:YYCONDTYPE, re2c:define:YYCONDTYPE
Définit la primitive API YYCONDTYPE.
re2c:YYCTYPE, re2c:define:YYCTYPE
Définit la primitive API YYCTYPE.
re2c:YYCTXMARKER, re2c:define:YYCTXMARKER
Définit la primitive API YYCTXMARKER.
re2c:YYCURSOR, re2c:define:YYCURSOR
Définit la primitive API YYCURSOR.
re2c:YYDEBUG, re2c:define:YYDEBUG
Définit la primitive API YYDEBUG.
re2c:YYFILL, re2c:define:YYFILL
Définit la primitive API YYFILL.
re2c:YYFILL@len, re2c:define:YYFILL@len
Spécifie le sigil utilisé pour la substitution d'arguments dans la définition de YYFILL. La valeur par défaut est @@. Remplace la configuration plus générique re2c:api:sigil.
re2c:YYFILL:naked, re2c:define:YYFILL:naked
Remplace la configuration plus générique re2c:api:style pour YYFILL. Une valeur de zéro correspond au style d'API libre.

Expressions régulières

re2d utilise la syntaxe suivante pour les expressions régulières :

"foo"
Littéral de chaîne sensible à la casse.
'foo'
Littéral de chaîne insensible à la casse.
[a-xyz], [^a-xyz]
Classe de caractères (éventuellement niée).
.
Tout caractère sauf le retour à la ligne.
R \ S
>
Différence entre les classes de caractères R et S.
R*
Zéro ou plusieurs occurrences de R.
R+
Une ou plusieurs occurrences de R.
R?
R optionnel.
R{n}
Répétition de R exactement n fois.
R{n,}
Répétition de R au moins n fois.
R{n,m}
Répétition de R de n à m fois.
(R)
Juste R ; les parenthèses sont utilisées pour outrepasser la priorité. Si l'extraction de sous-correspondances est activée, (R) est un groupe capturant ou non capturant selon l'option --invert-captures.
(!R)
Si l'extraction de sous-correspondances est activée, (!R) est un groupe non capturant ou capturant selon l'option --invert-captures.
R S
Concaténation : R suivi de S.
R | S
Alternative : R ou S.
R / S
Lookahead : R suivi de S, mais S n'est pas consommé.
name
Expression régulière définie comme name (ou chaîne littérale "name" en mode compatibilité Flex).
{name}
Expression régulière définie comme name en mode compatibilité Flex.
@stag
Un s-tag : sauvegarde la dernière position d'entrée où @stag correspond dans une variable nommée stag.
#mtag
Un m-tag : sauvegarde toutes les positions d'entrée où #mtag correspond dans une variable nommée mtag.

Les classes de caractères et les littéraux de chaînes peuvent contenir les séquences d'échappement suivantes : \a, \b, \f, \n, \r, \t, \v, \\, échappements octaux \ooo et échappements hexadécimaux \xhh, \uhhhh et \Uhhhhhhhh.

Actions

Voici une liste des actions prédéfinies prises en charge par re2d :

!entry code
L'action d'entrée lie un bloc de code défini par l'utilisateur à l'état de départ de la machine à états finis actuelle. Si des conditions de départ sont utilisées, l'action d'entrée peut être définie individuellement pour chaque condition. Cette action peut être utilisée pour effectuer une initialisation, par exemple pour sauvegarder la position de départ d'un lexème.
!pre_rule code
L'action pré-règle ajoute un bloc de code défini par l'utilisateur aux actions sémantiques de toutes les règles du bloc actuel (ou de la condition, si des conditions de départ sont utilisées). Cette action peut être utilisée pour factoriser la partie commune de toutes les actions sémantiques (par exemple, sauvegarder la position de fin d'un lexème).
!post_rule code
L'action post-règle ajoute un bloc de code défini par l'utilisateur aux actions sémantiques de toutes les règles du bloc actuel (ou de la condition, si des conditions de départ sont utilisées). Cette action peut être utilisée pour émettre des instructions de piège qui protègent contre les flux de contrôle involontaires.

Directives

Voici une liste complète des directives prises en charge par re2d :

!use:name ;
Une directive d'utilisation dans le bloc qui fusionne un bloc de règles précédemment défini avec le nom spécifié dans le bloc actuel. Les définitions nommées, les configurations et les règles du bloc référencé sont ajoutées aux règles actuelles. Les conflits entre les règles et les configurations qui se chevauchent sont résolus de la manière habituelle : la première règle a la priorité, et la dernière configuration remplace les précédentes. Une exception concerne les règles spéciales *, $ et <!> pour lesquelles une définition locale au bloc a toujours la priorité. Une directive d'utilisation peut être placée n'importe où à l'intérieur d'un bloc, et plusieurs directives d'utilisation sont autorisées.
!include file ;
Cette directive est identique au bloc include : elle insère le contenu du fichier tel quel à la place de la directive.

Interface du programme

Le code généré interagit avec le programme externe à l'aide de primitives, collectivement appelées API. Les primitives qui doivent être définies pour un programme particulier dépendent de plusieurs facteurs, notamment la complexité des expressions régulières, la représentation de l'entrée, la mise en mémoire tampon et l'utilisation de diverses fonctionnalités. Toutes les primitives nécessaires doivent être définies par l'utilisateur sous forme de macros, de fonctions, de variables ou de toute autre forme appropriée qui rend le code généré syntaxiquement et sémantiquement correct. re2d ne vérifie pas (et ne peut pas vérifier) les définitions, donc si quelque chose manque ou est défini de manière incorrecte, le programme généré peut présenter des erreurs de compilation ou d'exécution. Ce manuel fournit des exemples de définitions d'API dans les cas les plus courants.

re2d propose trois types d'API qui définissent l'ensemble de base des primitives utilisées par un programme :

API Simple
C'est l'API par défaut pour le backend D. Elle se compose des primitives YYCURSOR, YYMARKER, YYCTXMARKER et YYLIMIT, qui doivent être définies comme des pointeurs de type YYCTYPE*.
API Enregistrement
L'API Enregistrement est utile dans les cas où l'état du lexer doit être stocké dans une structure. Elle est activée avec l'option --api record ou la configuration re2c:api = record. Cette API se compose d'une variable yyrecord (le nom peut être remplacé par re2c:yyrecord) qui doit être définie comme une structure avec les champs yycursor, yymmarker, yyctxmarker, yylimit (seuls les champs utilisés par le code généré doivent être définis, et leurs noms peuvent être configurés).
API Générique
C'est l'API la plus flexible. Elle est activée avec l'option --api generic ou la configuration re2c:api = generic. Elle contient des primitives pour les opérations génériques : YYPEEK, YYSKIP, YYBACKUP, YYBACKUPCTX, YYSTAGP, YYSTAGN, YYMTAGP, YYMTAGN, YYRESTORE, YYRESTORECTX, YYRESTORETAG, YYSHIFT, YYSHIFTSTAG, YYSHIFTMTAG, YYLESSTHAN.

Voici une liste complète des primitives d'API qui peuvent être utilisées par le code généré pour interagir avec le programme externe.

YYCTYPE
Le type des caractères d'entrée (unités de code). Pour les encodages ASCII, EBCDIC et UTF-8, il doit s'agir d'un entier non signé d'un octet. Pour UTF-16 ou UCS-2, il doit s'agir d'un entier non signé de 2 octets. Pour UTF-32, il doit s'agir d'un entier non signé de 4 octets.
YYCURSOR
Une l-value qui stocke la position actuelle de l'entrée (un pointeur ou un décalage d'entier dans YYINPUT). Initialement, YYCURSOR doit pointer vers le premier caractère d'entrée, et plus tard, il est avancé par le code généré. Lorsqu'une règle correspond, la position de YYCURSOR est celle après le dernier caractère correspondant.
YYLIMIT
Une r-value qui stocke la position de fin d'entrée (un pointeur ou un décalage d'entier dans YYINPUT). Initialement, YYLIMIT doit pointer vers la position après le dernier caractère d'entrée disponible. Il n'est pas modifié par le code généré. Le lexer compare YYCURSOR à YYLIMIT pour déterminer s'il reste suffisamment de caractères d'entrée.
YYMARKER
Une l-value qui stocke la position de la dernière règle correspondante (un pointeur ou un décalage d'entier dans YYINPUT). Elle est utilisée pour restaurer la position de YYCURSOR si la correspondance la plus longue échoue et que le lexer doit revenir en arrière. Aucune initialisation n'est nécessaire.
YYCTXMARKER
Une l-value qui stocke la position du contexte de fin (un pointeur ou un décalage d'entier dans YYINPUT). Aucune initialisation n'est nécessaire. YYCTXMARKER n'est nécessaire que si l'opérateur de lookahead / est utilisé.
YYFILL
Une primitive d'API générique avec une variable len. YYFILL doit fournir au moins len caractères d'entrée supplémentaires ou échouer. Si re2c:eof est utilisé, alors len est toujours 1 et YYFILL doit toujours retourner à la fonction appelante ; une valeur de retour de zéro indique le succès. Si re2c:eof n'est pas utilisé, alors la valeur de retour de YYFILL est ignorée et elle ne doit pas retourner en cas d'échec. La valeur maximale de len est YYMAXFILL.
YYFN
Une primitive qui définit le prototype de fonction dans le modèle de code --recursive-functions. Sa valeur doit être un tableau d'une ou plusieurs chaînes, où chaque chaîne contient deux ou trois composants séparés par la chaîne spécifiée dans la configuration re2c:fn:sep (généralement un point-virgule). Le premier élément du tableau définit le nom de la fonction et le type de retour (vide pour une fonction void). Les éléments suivants définissent les arguments de la fonction : d'abord, l'expression pour l'argument utilisé dans le corps de la fonction (généralement juste un nom) ; ensuite, le type de l'argument ; enfin, un paramètre formel optionnel (il est par défaut le premier composant - généralement, l'argument et le paramètre sont le même identifiant).
YYINPUT
Une r-value qui stocke la séquence d'entrée actuelle (chaîne, tampon, etc.).
YYMAXFILL
Une constante entière égale à la valeur maximale de l'argument de YYFILL. Elle peut être générée avec un bloc max.
YYLESSTHAN
Une primitive d'API générique avec une variable len. Elle doit être définie comme une r-value de type booléen qui est égale à true si et seulement si il y a moins de len caractères d'entrée.

Options

Certaines options ont des configurations correspondantes, d'autres sont globales et ne peuvent pas être modifiées après que re2c commence à lire le fichier d'entrée. Les options de débogage nécessitent généralement de compiler re2c dans une configuration de débogage. Les options internes sont utiles pour expérimenter les algorithmes utilisés dans re2c.

-? --help -h
Afficher le message d'aide.
--api <simple | record | generique>
Spécifie l'API utilisée par le code généré pour interagir avec le code défini par l'utilisateur. L'option simple doit être utilisée dans les cas simples où il n'y a pas besoin de rechargement de tampon et de stockage de l'état de l'analyseur lexical. L'option record doit être utilisée lorsque l'état de l'analyseur lexical doit être stocké dans un enregistrement (struct, classe, etc.). Option interne, obsolète. Elle activait auparavant l'algorithme TDFA(0). Contrairement à TDFA(1), l'algorithme TDFA(0) n'utilise pas de regard en arrière d'un symbole. Il applique des opérations de registre aux transitions entrantes plutôt qu'aux transitions sortantes. Les benchmarks ont montré que l'algorithme TDFA(0) est moins efficace que TDFA(1).

Option interne : supprime l'optimisation des variables de tag (utile pour le débogage).

Option interne : spécifie l'algorithme utilisé pour calculer la table de précedence POSIX. L'algorithme complex calcule la table de précedence en un seul parcours de l'arbre d'historique des tags et a une complexité quadratique par rapport au nombre d'états TNFA ; c'est le défaut. L'algorithme naive a une complexité cubique dans le pire cas par rapport au nombre d'états TNFA, mais il est beaucoup plus simple que complex et peut être légèrement plus rapide dans les cas non pathologiques.

Option interne, obsolète. Elle activait l'algorithme staDFA, qui diffère de TDFA en ce que les opérations de registre sont placées dans les états plutôt que sur les transitions. Les benchmarks ont montré que l'algorithme staDFA est moins efficace que TDFA.

Option interne : spécifie si l'optimisation des tags fixes doit être appliquée à tous les tags (all), aucun d'entre eux (none), ou seulement ceux dans la concaténation de niveau supérieur (toplevel). Le défaut est all. Les tags "fixes" sont ceux qui sont situés à une distance fixe d'un autre tag (appelé "base"). Dans de tels cas, seule la tag de base doit être suivie, et la valeur du tag fixe peut être calculée comme la valeur du tag de base plus un décalage statique. Pour les tags qui sont sous alternative ou répétition, il est également nécessaire de vérifier si le tag de base a une valeur de non-correspondance (dans ce cas, le tag fixe doit également être défini sur non-correspondance, ignorant le décalage). Pour les tags dans la concaténation de niveau supérieur, la vérification n'est pas nécessaire, car ils correspondent toujours.

Active tous les avertissements.
-Werror
Transforme les avertissements en erreurs. Notez que cette option seule n'active aucun avertissement ; elle n'affecte que les avertissements qui ont été activés jusqu'à présent ou qui seront activés plus tard.
-W<warning>

Désactive warning.

Active warning et le traite comme une erreur (cela implique -W<warning>).
-Wno-error-<warning>
Ne traite pas ce warning particulier comme une erreur. Cela ne désactive pas l'avertissement lui-même.

Avertit si le programme généré fait des suppositions implicites sur la numérotation des conditions. Il faudrait utiliser l'option --header ou le bloc conditions pour générer un mappage des noms de conditions aux numéros, puis utiliser les noms de conditions auto-générés.

Avertit si une expression régulière contient une classe de caractères vide. Essayer de faire correspondre une classe de caractères vide n'a aucun sens : cela devrait toujours échouer. Cependant, pour des raisons de compatibilité ascendante, re2d autorise les classes de caractères vides et les traite comme des chaînes vides. Utilisez l'option --empty-class pour modifier le comportement par défaut.

Avertit si une règle est nullable (correspond à une chaîne vide). Si le lexer s'exécute en boucle et que la correspondance vide est involontaire, le lexer peut se bloquer de manière inattendue dans une boucle infinie.
-Wswapped-range
Avertit si la borne inférieure d'une plage est supérieure à sa borne supérieure. Le comportement par défaut est d'échanger silencieusement les bornes de la plage.

Avertit si certaines chaînes d'entrée provoquent un flux de contrôle indéfini dans le lexer (les motifs fautifs sont signalés). C'est une erreur dangereuse et courante. -Wunreachable-rules
Avertit sur les règles qui sont masquées par d'autres règles et qui ne correspondent jamais.

Fichiers de syntaxe

Le support de différentes langues dans re2c repose sur l'idée de fichiers de syntaxe. Un fichier de syntaxe est un fichier de configuration qui définit la syntaxe de la langue cible -- pas toute la langue, mais une petite partie de celle-ci qui est utilisée par le code généré. Les fichiers de syntaxe rendent re2c très flexible, mais ils ne doivent pas être utilisés comme remplacement pour les configurations re2c: : leur objectif est de définir la syntaxe de la langue cible, et non de personnaliser un lexer particulier. Toutes les langues supportées ont des fichiers de syntaxe par défaut qui font partie de la distribution (voir le sous-répertoire include/syntax) ; ils sont également intégrés dans le binaire re2d. Les utilisateurs peuvent fournir un fichier de syntaxe personnalisé qui remplace quelques configurations pour l'une des langues supportées, ou ils peuvent choisir de redéfinir toutes les configurations (dans ce cas, l'option --lang none doit être utilisée). Les fichiers de syntaxe contiennent des configurations de quatre types différents : listes de fonctionnalités, configurations de langue, configurations inplace et modèles de code.

supported_features

Modèles de code

Les modèles de code définissent la syntaxe de la langue cible. Ils sont écrits dans un langage simple spécifique à un domaine avec la grammaire formelle suivante : 
code-template ::
      name '=' code-exprs ';'
    | CODE_TEMPLATE ';'
    | '<undefined>' ';'
code-exprs ::
      <EMPTY>
    | code-exprs code-expr
code-expr ::
      STRING
    | VARIABLE
    | optional
    | list
optional ::
      '(' CONDITIONAL '?' code-exprs ')'
    | '(' CONDITIONAL '?' code-exprs ':' code-exprs ')'
list ::
      '[' VARIABLE ':' code-exprs ']'
    | '[' VARIABLE '{' NUMBER '}' ':' code-exprs ']'
    | '[' VARIABLE '{' NUMBER ',' NUMBER '}' ':' code-exprs ']'

Un modèle de code est une séquence de littéraux de chaînes, de variables, d'éléments optionnels et de listes, ou une référence à un autre modèle de code, ou une valeur spéciale <undefined>. Les variables sont des espaces réservés qui sont substitués pendant la phase de génération de code. Les variables de liste sont spéciales : lors de l'expansion des modèles de liste, re2d répète les expressions du côté droit de la colonne plusieurs fois, remplaçant à chaque fois les occurrences de la variable de liste par une valeur spécifique à cette répétition. Les listes ont des limites optionnelles (les valeurs négatives sont comptées à partir de la fin, par exemple, -1 signifie le dernier élément). Les noms conditionnels commencent par un point. Les conditionnels et les variables peuvent être locaux (spécifiques au modèle de code donné) ou globaux (autorisés dans tous les modèles de code). Lorsque re2d lit le fichier de syntaxe, il vérifie que chaque modèle de code n'utilise que les variables et les conditionnels qui y sont autorisés.

Par exemple, le modèle de code suivant définit une construction if-then-else pour un langage de type C :

code:if_then_else =
    [branch{0}: topindent "if " cond " {" nl
        indent [stmt: stmt] dedent]
    [branch{1:-1}: topindent "} else" (.cond ? " if " cond) " {" nl
        indent [stmt: stmt] dedent]
    topindent "}" nl;

Ici, branch est une variable de liste : branch{0} s'étend à la première branche (qui est spéciale, car il n'y a pas de partie else), branch{1:-1} s'étend à toutes les branches restantes (s'il y en a). stmt est également une variable de liste : [stmt: stmt] est une liste imbriquée qui s'étend à une liste d'instructions dans le corps de la branche actuelle. topindent, indent, dedent et nl sont des variables globales, et .cond est un conditionnel local (leur signification est décrite ci-dessous).     // do something
} else if y {
    // do something else

GESTION DE LA FIN DE L'ENTRÉE

L'un des principaux problèmes pour l'analyseur lexical est de savoir quand s'arrêter. Il existe quelques conditions de terminaison :

  • l'analyseur lexical peut correspondre à une règle (y compris la règle par défaut *) et arriver à un état final
  • l'analyseur lexical peut ne pas correspondre à une règle et arriver à un état par défaut
  • l'analyseur lexical peut atteindre la fin de l'entrée

Les deux premières conditions terminent l'analyseur lexical de manière "naturelle" : il arrive à un état sans transitions sortantes, et la correspondance s'arrête automatiquement. La troisième condition, la fin de l'entrée, est différente : elle peut se produire dans n'importe quel état, et l'analyseur lexical doit être capable de la gérer. La vérification de la fin de l'entrée interrompt le flux de travail normal de l'analyseur lexical et ajoute des branches conditionnelles au programme généré, il est donc nécessaire de minimiser le nombre de ces vérifications. re2d prend en charge plusieurs méthodes pour gérer la fin de l'entrée. Laquelle utiliser dépend de la complexité des expressions régulières, du besoin de mise en mémoire tampon, des considérations de performance et d'autres facteurs. Voici une liste de méthodes :

  • Sentinele. Cette méthode élimine le besoin de vérifications de fin d'entrée. Elle est simple et efficace, mais limitée au cas où il existe un caractère de "sentinelle" naturel qui ne peut jamais apparaître dans une entrée valide. Ce caractère peut toujours apparaître dans une entrée invalide, mais il ne devrait pas être autorisé par les expressions régulières, sauf peut-être comme dernier caractère d'une règle. La sentinelle est ajoutée à la fin de l'entrée et sert de signal d'arrêt : lorsque l'analyseur lexical lit ce caractère, il s'agit soit d'une erreur de syntaxe, soit de la fin de l'entrée. Dans les deux cas, l'analyseur lexical doit s'arrêter. Cette méthode est utilisée si YYFILL est désactivé avec re2c:yyfill:enable = 0; et re2c:eof a la valeur par défaut -1.
  • Sentinelle avec vérifications de limites. Cette méthode est générique : elle permet de gérer n'importe quelle entrée sans restrictions sur les expressions régulières. L'idée est de réduire le nombre de vérifications de fin d'entrée en ne les effectuant que sur certains caractères. Similaire à la méthode "sentinelle", l'un des caractères est choisi comme "sentinelle" et ajouté à la fin de l'entrée. Cependant, il n'y a aucune restriction quant à l'endroit où la sentinelle peut apparaître (en fait, n'importe quel caractère peut être choisi pour une sentinelle). Lorsque l'analyseur lexical lit ce caractère, il effectue en plus une vérification de limites. Si la position actuelle est dans les limites, l'analyseur lexical reprend la correspondance et traite la sentinelle comme un caractère normal. Sinon, il invoque YYFILL (sauf si elle est désactivée). Si plus d'entrée est fournie, l'analyseur lexical réalignera le dernier caractère et continuera comme si la sentinelle n'était pas là. Sinon, ce doit être la vraie fin de l'entrée, et l'analyseur lexical s'arrête. Cette méthode est utilisée lorsque re2c:eof a une valeur non négative (elle doit être définie à la valeur numérique de la sentinelle). YYFILL est facultatif.
  • Vérifications de limites avec remplissage. Cette méthode est générique, et elle peut être plus rapide que la méthode "sentinelle avec vérifications de limites", mais elle est également plus complexe. L'idée est de partitionner les états du DFA en composantes fortement connexes (SCC) et de générer une seule vérification par SCC pour suffisamment de caractères pour couvrir le chemin non répétitif le plus long dans cette SCC. Ceci réduit le nombre de vérifications, mais il y a un problème avec les lexèmes courts en fin d'entrée, car la vérification nécessite suffisamment de caractères pour couvrir le lexème le plus long. Ceci peut être corrigé en remplissant l'entrée avec quelques caractères factices qui ne forment pas un suffixe de lexème valide (de sorte que l'analyseur lexical ne puisse pas les faire correspondre). La longueur du remplissage doit être YYMAXFILL, générée avec un bloc max. S'il n'y a pas assez d'entrée, l'analyseur lexical invoque YYFILL qui doit fournir au moins le nombre requis de caractères ou ne pas revenir. Cette méthode est utilisée si YYFILL est activé et re2c:eof est -1 (c'est la configuration par défaut).
  • Vérifications personnalisées. L'API générique permet de remplacer les opérations de base comme la lecture d'un caractère, ce qui permet d'inclure les vérifications de fin d'entrée dans celles-ci. Cette approche est sujette aux erreurs et doit être utilisée avec prudence. Pour utiliser une méthode personnalisée, activez l'API générique avec --api custom ou re2c:api = custom; et désactivez les vérifications de limites par défaut avec re2c:yyfill:enable = 0; ou re2c:yyfill:check = 0;.

Sentinelle

Cet exemple utilise un caractère sentinelle pour gérer la fin de l'entrée. Le programme compte les mots séparés par des espaces dans une chaîne terminée par null. La sentinelle est null : c'est le dernier caractère de chaque chaîne d'entrée, et elle n'est autorisée dans le milieu d'un lexème par aucune des règles (en particulier, elle n'est pas incluse dans les plages de caractères où elle est facile à ignorer). Si un null apparaît au milieu d'une chaîne, c'est une erreur de syntaxe et l'analyseur lexical fera correspondre la règle par défaut *, mais il ne lira pas au-delà de la fin de l'entrée et ne plantera pas (utilisez l'avertissement -Wsentinel-in-midrule et la configuration re2c:sentinel pour vérifier cela). La configuration re2c:yyfill:enable = 0; supprime la génération de vérifications de limites et d'invocations YYFILL.

// re2d $INPUT -o $OUTPUT
module main;
// Attend une chaîne terminée par null.
private int lex(const(char)* yycursor) {
    uint count = 0;
    for (;;) {
    /*!re2c
        re2c:YYCTYPE = char;
        re2c:yyfill:enable = 0;
        *      { return -1; }
        [\x00] { return count; }
        [a-z]+ { ++count; continue; }
        [ ]+   { continue; }
    */
    }
    assert(0); // inaccessible
}
void main() {
    assert(lex("") == 0);
    assert(lex("one two three") == 3);
    assert(lex("f0ur") == -1);
}

Sentinelle avec vérifications de limites

Cet exemple utilise une sentinelle avec vérifications de limites pour gérer la fin de l'entrée (cette méthode a été ajoutée dans la version 1.2). Le programme compte les chaînes d'un seul guillemet séparées par des espaces. Le caractère sentinelle est null, ce qui est spécifié avec la configuration re2c:eof = 0;. Comme dans la méthode sentinel, null est le dernier caractère de chaque chaîne d'entrée, mais il est autorisé au milieu d'une règle (par exemple, 'aaa\0aa'\0 est une entrée valide, mais 'aaa\0 est une erreur de syntaxe). Les vérifications de limites sont générées dans chaque état qui correspond à un caractère d'entrée, mais elles sont limitées à la branche qui gère le null. Les vérifications de limites sont de la forme YYLIMIT <= YYCURSOR ou YYLESSTHAN(1) avec l'API générique. Si la condition de vérification est vraie, l'analyseur lexical a atteint la fin de l'entrée et doit s'arrêter (YYFILL est désactivé avec re2c:yyfill:enable = 0; car l'entrée tient dans un seul tampon, voir la section YYFILL avec sentinelle pour un exemple utilisant YYFILL). Atteindre la fin de l'entrée ouvre trois possibilités : si l'analyseur lexical est dans l'état initial, il fera correspondre la règle de fin d'entrée $, sinon il peut se rabattre sur une règle précédemment correspondue (y compris la règle par défaut *) ou aller à un état par défaut, provoquant -Wundefined-control-flow.

// re2d $INPUT -o $OUTPUT
module main;
// Attend une chaîne terminée par null.
private int lex(immutable char[] s) {
    const(char)* yycursor = s.ptr, yylimit = s.ptr + s.length, yymarker;
    int count = 0;
    for (;;) {
    /*!re2c
        re2c:YYCTYPE = char;
        re2c:yyfill:enable = 0;
        re2c:eof = 0;
        str = ['] ([^'\\] | [\\][^])* ['];
        *    { return -1; }
        $    { return count; }
        str  { ++count; continue; }
        [ ]+ { continue; }
    */
    }
    assert(0); // inaccessible
}
void main() {
    assert(lex("") == 0);
    assert(lex("'qu\0tes' 'are' 'fine: \\'' ") == 3);
    assert(lex("'unterminated\\'") == -1);
}

Vérifications de limites avec remplissage

Cet exemple utilise des vérifications de limites avec remplissage pour gérer la fin de l'entrée (cette méthode est activée par défaut). Le programme compte les chaînes d'un seul guillemet séparées par des espaces. Il y a un remplissage de YYMAXFILL caractères null ajoutés à la fin de l'entrée, où la valeur YYMAXFILL est générée automatiquement avec un bloc max. Il n'est pas nécessaire d'utiliser null pour le remplissage --- n'importe quels caractères peuvent être utilisés tant qu'ils ne forment pas un suffixe de lexème valide (dans cet exemple, le remplissage ne doit pas contenir de guillemets simples, car ils pourraient être confondus avec un suffixe d'une chaîne d'un seul guillemet). Il y a une règle "stop" qui correspond au premier caractère de remplissage (null) et termine l'analyseur lexical (notez qu'elle vérifie si null est au début du remplissage, sinon c'est une erreur de syntaxe). Les vérifications de limites sont générées uniquement dans certains états qui sont déterminés par les composantes fortement connexes de l'automate sous-jacent. Les vérifications sont de la forme (YYLIMIT - YYCURSOR) < n ou YYLESSTHAN(n) avec

generic API, où n est le nombre minimum de caractères nécessaires au lexer pour continuer (cela signifie également que la prochaine vérification de limite se produira dans au plus n caractères). Si la condition de vérification est vraie, le lexer a atteint la fin de l'entrée et appellera YYFILL(n) qui devrait soit fournir au moins n caractères d'entrée, soit ne pas revenir. Dans cet exemple, YYFILL échoue toujours et termine le lexer avec une erreur (ce qui est acceptable car l'entrée tient dans un seul tampon). Voir la section YYFILL avec remplissage pour un exemple qui remplit le tampon d'entrée avec YYFILL.

// re2d $INPUT -o $OUTPUT
module main;
import core.stdc.stdlib;
import core.stdc.string;
/*!max:re2c*/
private int lex(immutable char[] s) {
    // Faire une copie de la chaîne avec YYMAXFILL zéros à la fin.
    char *buf = cast(char*) malloc(s.length + YYMaxFill);
    memcpy(buf, cast(const(void*)) s, s.length);
    memset(buf + s.length, 0, YYMaxFill);
    const(char)* yycursor = buf;
    const(char)* yylimit = buf + s.length + YYMaxFill;
    int count = 0;
loop:
    /*!re2c
        re2c:YYCTYPE = char;
        re2c:YYFILL = "goto fail;";
        str = ['] ([^'\\] | [\\][^])* ['];
        [\x00] {
            // Vérifier qu'il s'agit bien du sentinelle, pas d'un zéro inattendu.
            if (yycursor - 1 == buf + s.length) goto exit; else goto fail;
        }
        str  { ++count; goto loop; }
        [ ]+ { goto loop; }
        *    { goto fail; }
    */
fail:
    count = -1;
exit:
    free(buf);
    return count;
}
void main() {
    assert(lex("") == 0);
    assert(lex("'qu\0tes' 'are' 'fine: \\'' ") == 3);
    assert(lex("'unterminated\\'") == -1);
    assert(lex("'unexpected \0 null\\'") == -1);
}

Vérifications personnalisées

Cet exemple utilise une méthode personnalisée de gestion de la fin de l'entrée basée sur l'API générique. Le programme compte les chaînes entre guillemets simples séparées par des espaces. C'est le même que l'exemple sentinel, sauf que l'entrée n'est pas terminée par un zéro. Pour compenser l'absence d'un caractère sentinelle à la fin de l'entrée, YYPEEK est redéfini pour effectuer une vérification de limite avant de lire le prochain caractère d'entrée. C'est inefficace car les vérifications sont effectuées très souvent. Si la condition de vérification échoue, YYPEEK renvoie le caractère réel, sinon il renvoie un caractère sentinelle factice.

// re2d $INPUT -o $OUTPUT
module main;
import core.stdc.stdlib;
import core.stdc.string;
private int lex(immutable char[] s) {
    // Pour l'exemple, créer une chaîne sans zéro terminal.
    char *buf = cast(char*) malloc(s.length);
    memcpy(buf, cast(const(void*)) s, s.length);
    const(char) *cur = buf, lim = buf + s.length;
    int count = 0;
    for (;;) {
    /*!re2c
        re2c:api = generic;
        re2c:yyfill:enable = 0;
        re2c:YYCTYPE = char;
        re2c:YYPEEK = "cur < lim ? *cur : 0";  // faux zéro
        re2c:YYSKIP = "++cur;";
        *      { count = -1; break; }
        [\x00] { break;{} }
        [a-z]+ { ++count; continue;{} }
        [ ]+   { continue; }
    */
    }
    free(buf);
    return count;
}
void main() {
    assert(lex("") == 0);
    assert(lex("one two three ") == 3);
    assert(lex("f0ur") == -1);
}

REMPLISSAGE DU TAMPON

Le besoin de mise en tampon survient lorsque l'entrée ne peut pas être mappée en mémoire en une seule fois : soit elle est trop grande, soit elle arrive de manière séquentielle (comme la lecture depuis un socket). La technique habituelle dans de tels cas est d'allouer un tampon de mémoire de taille fixe et de traiter l'entrée par morceaux qui tiennent dans le tampon. Lorsque le morceau courant est traité, il est déplacé et de nouvelles données sont chargées. En pratique, c'est un peu plus complexe, car l'état du lexer ne consiste pas en une seule position d'entrée, mais en un ensemble de positions interdépendantes :

  • curseur : le prochain caractère d'entrée à lire (YYCURSOR dans l'API pointeur C ou YYSKIP/YYPEEK dans l'API générique)
  • limite : la position après le dernier caractère d'entrée disponible (YYLIMIT dans l'API pointeur C, implicitement géré par YYLESSTHAN dans l'API générique)
  • marqueur : la position de la correspondance la plus récente, le cas échéant (YYMARKER dans l'API par défaut ou YYBACKUP/YYRESTORE dans l'API générique)
  • token : le début du lexème courant (implicite dans l'API re2d, car il n'est pas nécessaire pour le fonctionnement normal du lexer et peut être défini et mis à jour par l'utilisateur)
  • marqueur de contexte : la position du contexte de fin (YYCTXMARKER dans l'API pointeur C ou YYBACKUPCTX/YYRESTORECTX dans l'API générique)
  • variables de balise : positions de sous-correspondance (définies avec les blocs stags et mtags et les primitives de l'API générique YYSTAGP/YYSTAGN/YYMTAGP/YYMTAGN)

Toutes ces positions ne sont pas utilisées dans tous les cas, mais si elles le sont, elles doivent être mises à jour par YYFILL. Toutes les positions actives se trouvent dans le segment entre le token et le curseur, par conséquent tout ce qui se trouve entre le début du tampon et le token peut être éliminé, le segment du token jusqu'à la limite doit être déplacé au début du tampon, et l'espace libre à la fin du tampon doit être rempli avec de nouvelles données. Afin d'éviter des appels fréquents à YYFILL, il est préférable de charger autant de caractères d'entrée que possible (même si moins de caractères pourraient suffire à reprendre le lexer). Les détails de l'implémentation de YYFILL varient légèrement en fonction de la méthode de gestion de la fin de fichier utilisée : le cas de la règle de fin de fichier est quelque peu plus simple que le cas de la vérification de limites avec remplissage. Notez également que si l'option -f --storable-state est utilisée, YYFILL a une sémantique légèrement différente (décrite dans la section sur l'état stockable).

YYFILL avec sentinelle

Si la règle de fin de fichier est utilisée, YYFILL est une primitive de type fonction qui n'accepte aucun argument et renvoie une valeur qui est comparée à zéro. L'invocation de YYFILL est déclenchée par la condition YYLIMIT <= YYCURSOR dans l'API pointeur C et YYLESSTHAN() dans l'API générique. Une valeur de retour non nulle signifie que YYFILL a échoué. Un appel réussi à YYFILL doit fournir au moins un caractère et ajuster les positions d'entrée en conséquence. La limite doit toujours être définie à une position après la dernière position d'entrée dans le tampon, et le caractère à cette position limite doit être le symbole sentinelle spécifié par la configuration re2c:eof. Les schémas ci-dessous montrent les emplacements relatifs des positions d'entrée dans le tampon avant et après l'appel YYFILL (le symbole sentinelle est marqué par #, et le second schéma montre le cas où il n'y a pas assez d'entrée pour remplir tout le tampon).

               <-- décalage -->
             >-A------------B---------C-------------D#-----------E->
             tampon       token    marqueur      limite,
                                                  curseur
>-A------------B---------C-------------D------------E#->
             tampon,  marqueur      curseur       limite
             token
               <-- décalage -->
             >-A------------B---------C-------------D#--E
             tampon       token    marqueur      limite,
                                                  curseur
>-A------------B---------C-------------D---E#........
             tampon,  marqueur      curseur limite
             token

Voici un exemple de programme qui lit le fichier d'entrée input.txt par morceaux de 4096 octets et utilise la règle de fin de fichier.

// re2d $INPUT -o $OUTPUT
module main;
import core.stdc.string;
import core.stdc.stdio;
enum BUFSIZE = 4095;
struct Input {
    FILE* file;
    char[BUFSIZE + 1] buffer;// +1 pour le sentinelle
    char* yylimit, yycursor, yymarker, token;
    bool eof;
};
private int fill(ref Input it) {
    if (it.eof) return 1;
    const size_t shift = it.token - it.buffer.ptr;
    const size_t used = it.yylimit - it.token;
    // Erreur : lexème trop long. Dans la vraie vie, on pourrait réallouer un tampon plus grand.
    if (shift < 1) return 2;
    // Décaler le contenu du tampon (éliminer tout jusqu'au token courant).
    memmove(cast(void*)it.buffer.ptr, it.token, used);
    it.yylimit -= shift;
    it.yycursor -= shift;
    it.yymarker -= shift;
    it.token -= shift;
    // Remplir l'espace libre à la fin du tampon avec de nouvelles données du fichier.
    it.yylimit += fread(it.yylimit, 1, BUFSIZE - used, it.file);
    it.yylimit[0] = 0;
    it.eof = it.yylimit < (it.buffer.ptr + BUFSIZE);
    return 0;
}
private int lex(ref Input yyrecord) {
    int count = 0;
    for (;;) {
        yyrecord.token = yyrecord.yycursor;
    /*!re2c
        re2c:api = record;
        re2c:YYCTYPE = "char";
        re2c:YYFILL = "fill(yyrecord) == 0";
        re2c:eof = 0;
        str = ['] ([^'\\] | [\\][^])* ['];
        *    { return -1; }
        $    { return count; }
        str  { ++count; continue; }
        [ ]+ { continue; }
    */
    }
    assert(0);
}
void main() {
    const char[] fname = "input";
    const char[] content = "'qu\0tes' 'are' 'fine: \\'' ";
    // Préparer le fichier d'entrée : plusieurs fois la taille du tampon, contenant
    // des chaînes avec des zéros et des guillemets échappés.
    FILE* f = fopen(fname.ptr, "w");
    for (int i = 0; i < BUFSIZE; ++i) {
        fwrite(cast(const(void*)) content.ptr, 1, content.length - 1, f);
    }
    fclose(f);
    int count = 3 * BUFSIZE; // nombre de chaînes entre guillemets écrites dans le fichier
    // Initialiser l'état du lexer : tous les pointeurs sont à la fin du tampon.
    Input it;
    it.file = fopen(fname.ptr, "r");
    it.yycursor = it.yymarker = it.token = it.yylimit = it.buffer.ptr + BUFSIZE;
    it.eof = 0;
    // Le sentinelle (au pointeur YYLIMIT) est mis à zéro, ce qui déclenche YYFILL.
    it.yylimit[0] = 0;
    // Exécuter le lexer.
    assert(lex(it) == count);
    // Nettoyage : supprimer le fichier d'entrée.
    fclose(it.file);
    remove(fname.ptr);
}

YYFILL avec remplissage

Dans le cas par défaut (lorsque la règle de fin de fichier n'est pas utilisée), YYFILL est une primitive de type fonction qui accepte un seul argument et ne renvoie aucune valeur. L'invocation de YYFILL est déclenchée par la condition (YYLIMIT - YYCURSOR) < n dans l'API pointeur C et YYLESSTHAN(n) dans l'API générique. L'argument passé à YYFILL est le nombre minimum de caractères qui doivent être fournis. S'il ne parvient pas à le faire, YYFILL ne doit pas revenir au lexer (c'est pourquoi il est mieux implémenté comme une macro qui revient de la fonction appelante en cas d'échec). En cas d'invocation réussie de YYFILL, la position limite doit être définie soit à une position après la dernière position d'entrée dans le tampon, soit à la fin du remplissage YYMAXFILL (dans le cas où YYFILL a lu avec succès au moins n caractères, mais pas assez pour remplir tout le tampon). Les schémas ci-dessous montrent les rela

tive positions des positions d'entrée dans le tampon avant et après l'invocation de YYFILL (le remplissage YYMAXFILL sur la seconde image est marqué avec des symboles #).

               <-- décalage -->                 <-- besoin -->
             >-A------------B---------C-----D-------E---F--------G->
             tampon       jeton    marqueur curseur  limite
>-A------------B---------C-----D-------E---F--------G->
             tampon,  marqueur curseur               limite
             jeton
               <-- décalage -->                 <-- besoin -->
             >-A------------B---------C-----D-------E-F        (EOF)
             tampon       jeton    marqueur curseur  limite
>-A------------B---------C-----D-------E-F###############
             tampon,  marqueur curseur                   limite
             jeton                        <- YYMAXFILL ->

Voici un exemple de programme qui lit le fichier d'entrée input.txt par blocs de 4096 octets et utilise la vérification des limites avec remplissage.

// re2d $INPUT -o $OUTPUT
module main;
import core.stdc.string;
import core.stdc.stdio;
/*!max:re2c*/
enum BufSize = (4096 - YYMaxFill);
struct Input {
    FILE* file;
    char[BufSize + YYMaxFill] buffer;
    char* yylimit, yycursor, token;
    bool eof;
};
private int fill(ref Input it, size_t need) {
    if (it.eof) return 1;
    const size_t shift = it.token - it.buffer.ptr;
    const size_t used = it.yylimit - it.token;
    // Erreur : lexème trop long. Dans la vie réelle, on pourrait réallouer un tampon plus grand.
    if (shift < need) return 2;
    // Décale le contenu du tampon (écarte tout jusqu'au jeton courant).
    memmove(it.buffer.ptr, it.token, used);
    it.yylimit -= shift;
    it.yycursor -= shift;
    it.token -= shift;
    // Remplit l'espace libre à la fin du tampon avec de nouvelles données du fichier.
    it.yylimit += fread(it.yylimit, 1, BufSize - used, it.file);
    // Si moins de données ont été lues que prévu, c'est la fin de l'entrée => ajoute un remplissage de zéro
    // afin que le lexer puisse accéder aux caractères à la fin du tampon.
    if (it.yylimit < it.buffer.ptr + BufSize) {
        it.eof = true;
        memset(it.yylimit, 0, YYMaxFill);
        it.yylimit += YYMaxFill;
    }
    return 0;
}
private int lex(ref Input yyrecord) {
    int count = 0;
    for (;;) {
        yyrecord.token = yyrecord.yycursor;
    /*!re2c
        re2c:api = record;
        re2c:YYCTYPE = "char";
        re2c:YYFILL = "if (fill(yyrecord, @@) != 0) return -1;";
        str = ['] ([^'\\] | [\\][^])* ['];
        [\x00] {
            // Vérifie qu'il s'agit du sentinelle, et non d'un zéro inattendu.
            return yyrecord.token == yyrecord.yylimit - YYMaxFill ? count : -1;
        }
        str  { ++count; continue; }
        [ ]+ { continue; }
        *    { return -1; }
    */
    }
    assert(0);
}
void main() {
    const char[] fname = "input";
    const char[] content = "'qu\0tes' 'are' 'fine: \\'' ";
    // Préparer le fichier d'entrée : quelques fois la taille du tampon, contenant
    // des chaînes avec des zéros et des guillemets échappés.
    FILE* f = fopen(fname.ptr, "w");
    for (int i = 0; i < BufSize; ++i) {
        fwrite(content.ptr, 1, content.length - 1, f);
    }
    fclose(f);
    int count = 3 * BufSize; // nombre de chaînes entre guillemets écrites dans le fichier
    // Initialise l'état du lexer : tous les pointeurs sont à la fin du tampon.
    // Cela déclenche immédiatement YYFILL, car la vérification `it.yycursor < it.yylimit` échoue.
    Input it;
    it.file = fopen(fname.ptr, "r");
    it.yycursor = it.token = it.yylimit = it.buffer.ptr + BufSize;
    it.eof = 0;
    // Exécute le lexer.
    assert(lex(it) == count);
    // Nettoyage : supprime le fichier d'entrée.
    fclose(it.file);
    remove(fname.ptr);
}

FONCTIONNALITÉS

Blocs multiples

Il est parfois nécessaire d'avoir plusieurs lexers interdépendantes (par exemple, s'il existe une machine à états de haut niveau qui transitionne entre les modes du lexer). Ceci peut être implémenté en utilisant plusieurs blocs re2d connectés. Une autre option consiste à utiliser des conditions de départ.

L'implémentation des connexions entre les blocs dépend de la langue cible. Dans les langages qui ont une instruction goto (comme C/C++ et Go), on peut avoir tous les blocs dans une seule fonction, chacun préfixé par une étiquette. La transition d'un bloc à un autre est un simple goto. Dans les langages qui n'ont pas de goto (comme Rust), il est nécessaire d'utiliser une boucle avec un switch sur une variable d'état, similaire à la boucle/switch yystate générée par re2d, ou d'encapsuler chaque bloc dans une fonction et d'utiliser des appels de fonction.

L'exemple ci-dessous utilise des blocs multiples pour analyser les nombres binaires, octaux, décimaux et hexadécimaux. Chaque base a son propre bloc. Le bloc initial détermine la base et distribue vers les autres blocs. Les configurations communes sont définies dans un bloc séparé au début du programme ; elles sont héritées par les autres blocs.

// re2d $INPUT -o $OUTPUT -i
module main;
enum ERROR = ulong.max;
private void add(ulong BASE)(ref ulong u, int d) {
    u = u * BASE + d;
    if (u > uint.max) { u = ERROR; }
}
private ulong parse_u32(const(char)* s) {
    const(char)* yycursor = s, yymarker;
    ulong u = 0;
    /*!re2c
        re2c:yyfill:enable = 0;
        re2c:YYCTYPE = char;
        end = "\x00";
        '0b' / [01]        { goto bin; }
        "0"                { goto oct; }
        "" / [1-9]         { goto dec; }
        '0x' / [0-9a-fA-F] { goto hex; }
        *                  { return ERROR; }
    */
bin:
    /*!re2c
        end   { return u; }
        [01]  { add!(2)(u, yycursor[-1] - '0'); goto bin; }
        *     { return ERROR; }
    */
oct:
    /*!re2c
        end   { return u; }
        [0-7] { add!(8)(u, yycursor[-1] - '0'); goto oct; }
        *     { return ERROR; }
    */
dec:
    /*!re2c
        end   { return u; }
        [0-9] { add!(10)(u, yycursor[-1] - '0'); goto dec; }
        *     { return ERROR; }
    */
hex:
    /*!re2c
        end   { return u; }
        [0-9] { add!(16)(u, yycursor[-1] - '0');      goto hex; }
        [a-f] { add!(16)(u, yycursor[-1] - 'a' + 10); goto hex; }
        [A-F] { add!(16)(u, yycursor[-1] - 'A' + 10); goto hex; }
        *     { return ERROR; }
    */
}
void main() {
    assert(parse_u32("") == ERROR);
    assert(parse_u32("1234567890") == 1234567890);
    assert(parse_u32("0b1101") == 13);
    assert(parse_u32("0x7Fe") == 2046);
    assert(parse_u32("0644") == 420);
    assert(parse_u32("9999999999") == ERROR);
}

Conditions de départ

Les conditions de départ sont activées avec l'option --start-conditions. Elles offrent un moyen d'encoder plusieurs automates interdépendants au sein du même bloc re2d.

Chaque condition correspond à un automate unique et possède un nom spécifié par l'utilisateur et un numéro interne unique défini par re2d. Les numéros sont utilisés pour basculer entre les conditions : le code généré utilise les primitives YYGETCOND et YYSETCOND pour obtenir la condition actuelle ou la définir sur le numéro donné. Utilisez le bloc conditions, l'option --header ou la configuration re2c:header pour générer des identificateurs de condition numériques. La configuration re2c:cond:enumprefix spécifie le préfixe de l'identificateur généré.

En mode condition, chaque règle doit être préfixée par une liste de noms de conditions séparés par des virgules entre chevrons, ou par un joker <*> pour désigner toutes les conditions. La syntaxe des règles est étendue comme suit :

< liste-conditions > expression-régulière code
Une règle qui est fusionnée à chaque condition de la liste-conditions. Elle correspond à l'expression-régulière et exécute le code associé.
< liste-conditions > expression-régulière => condition code
Une règle qui est fusionnée à chaque condition de la liste-conditions. Elle correspond à l'expression-régulière, définit la condition actuelle sur condition et exécute le code associé.
< liste-conditions > expression-régulière :=> condition
Une règle qui est fusionnée à chaque condition de la liste-conditions. Elle correspond à l'expression-régulière et transitionne immédiatement vers condition (il n'y a pas d'action sémantique).
< liste-conditions > !action code
Une règle qui lie le code à l'emplacement défini par l'action dans chaque condition de la liste-conditions (voir la section actions pour les différents types d'actions).
<! liste-conditions > code
Une règle qui ajoute le code aux actions sémantiques de toutes les règles pour chaque condition de la liste-conditions. Cette syntaxe est obsolète et l'action !pre_rule doit être utilisée à la place (elle fait exactement la même chose).
< > code
Une règle qui crée une condition d'entrée spéciale avec le numéro zéro et le nom "0" qui exécute le code avant de sauter vers d'autres conditions. Cette syntaxe est obsolète et l'action !entry doit être utilisée à la place (elle offre un contrôle plus granulaire, car le code peut être spécifié par condition, et on peut sauter directement au début de la condition sans passer par la distribution des conditions).
< > => condition code
Identique à la règle précédente, sauf qu'elle définit la condition suivante.
< > :=> condition
Identique à la règle précédente, sauf qu'elle n'a pas de code associé et saute immédiatement vers condition.

Le code que re2d génère pour les conditions dépend de l'utilisation par re2d de l'approche goto/label ou de l'approche boucle/switch pour encoder les automates.

Dans les langages qui ont une instruction goto (comme C/C++ et Go), les conditions sont naturellement implémentées comme des blocs de code préfixés par des étiquettes de la forme yyc_<cond>, où cond est un nom de condition (le préfixe de l'étiquette peut être modifié avec re2c:cond:prefix). Les transitions entre les conditions sont implémentées en utilisant goto et les étiquettes de condition. Avant toutes les conditions, re2d génère un switch initial sur YYGETSTATE qui saute vers l'état de départ de la condition courante. Les règles de raccourci :=> contournent le switch initial et sautent directement à la condition spécifiée (re2c:cond:goto peut être utilisé pour modifier le comportement par défaut). Les règles avec des actions sémantiques ne sautent pas automatiquement vers la condition suivante ; cela doit être fait par le code d'action défini par l'utilisateur.

Dans les langages qui n'ont pas de goto (comme Rust), re2d réutilise la variable yystate pour stocker les numéros de condition. Chaque condition reçoit un identifiant numérique égal au numéro de son état de départ, et un switch entre les conditions n'est pas différent d'un switch entre les états DFA d'un si

ngle condition. Il n'est pas nécessaire d'avoir un commutateur de condition initiale distinct. (Puisque la même approche est utilisée pour implémenter les états stockables, YYGETCOND/YYSETCOND sont redondants si les états stockables et les conditions sont tous deux utilisés).

Le programme ci-dessous utilise des conditions de départ pour analyser les nombres binaires, octaux, décimaux et hexadécimaux. Il existe un seul bloc où chaque base a sa propre condition, et la condition initiale est connectée à toutes. La variable définie par l'utilisateur cond stocke le numéro de la condition actuelle ; elle est initialisée au numéro de la condition initiale générée avec le bloc conditions.

// re2d $INPUT -o $OUTPUT -ci
module main;
enum ERROR = ulong.max;
/*!conditions:re2c*/
private void add(ulong BASE)(ref ulong u, int d) {
    u = u * BASE + d;
    if (u > uint.max) { u = ERROR; }
}
private ulong parse_u32(const(char)* s) {
    const(char)* yycursor = s, yymarker;
    YYCond yycond = YYCond.yycinit;
    ulong u = 0;
    /*!re2c
        re2c:yyfill:enable = 0;
        re2c:YYCTYPE = char;
        <*> * { return ERROR; }

}

    assert(parse_u32("1234567890") == 1234567890);

}

État stockable

Avec l'option --storable-state, re2c génère un analyseur lexical qui peut stocker son état actuel, retourner à l'appelant et reprendre plus tard les opérations exactement là où il s'est arrêté. Le mode de fonctionnement par défaut de re2c est un modèle "pull", dans lequel l'analyseur lexical "tire" plus d'entrée quand il en a besoin. Cela peut être inacceptable dans les cas où l'entrée devient disponible morceau par morceau (par exemple, si l'analyseur lexical est appelé par le parseur, ou si le programme d'analyseur lexical communique via un protocole socket avec un autre programme qui doit attendre une réponse de l'analyseur lexical avant de transmettre le prochain message). La fonctionnalité d'état stockable est conçue précisément pour de tels cas : elle permet de générer des analyseurs lexicaux qui fonctionnent selon un modèle "push". Lorsque l'analyseur lexical a besoin de plus d'entrée, il stocke son état et retourne à l'appelant. Plus tard, lorsque plus d'entrée est disponible, l'appelant reprend l'analyseur lexical exactement là où il s'est arrêté. Quelques changements sont nécessaires par rapport au modèle "pull" :

  • Définir les primitives YYSETSTATE() et YYGETSTATE(state).
  • Définir les variables yych, yyaccept (si utilisé) et state comme faisant partie de l'état persistant de l'analyseur lexical. La variable state doit être initialisée à -1.
  • YYFILL doit retourner au programme externe au lieu d'essayer de fournir plus d'entrée. Le code de retour doit indiquer que l'analyseur lexical a besoin de plus d'entrée.
  • Le programme externe doit reconnaître les situations où l'analyseur lexical a besoin de plus d'entrée et répondre de manière appropriée.
  • Utiliser optionnellement le bloc getstate pour générer le commutateur YYGETSTATE détaché de l'analyseur lexical principal. Cela ne fonctionne que pour les langages qui ont goto (pas en mode --loop-switch).
  • Utiliser re2c:eof et la méthode de *sentinelle avec vérifications de limites* pour gérer la fin de l'entrée. La méthode basée sur le remplissage peut ne pas fonctionner car il n'est pas clair quand ajouter le remplissage : la fin actuelle de l'entrée peut ne pas être la fin ultime de l'entrée, et ajouter du remplissage trop tôt peut couper un lexème avide lu partiellement. De plus, en raison de la logique du programme de haut niveau, obtenir plus d'entrée peut dépendre du traitement du lexème à la fin du tampon (qui est déjà bloqué en raison de la condition de fin d'entrée).

Voici un exemple d'analyseur lexical en modèle "push" qui simule la lecture de paquets depuis un socket. L'analyseur lexical boucle jusqu'à ce qu'il rencontre la fin de l'entrée et retourne à la fonction appelante. La fonction appelante fournit plus d'entrée en "envoyant" le paquet suivant et reprend l'analyse lexicale. Ce processus s'arrête lorsque tous les paquets ont été envoyés, ou en cas d'erreur.

// re2d $INPUT -o $OUTPUT -f
module main;
import core.stdc.stdio;
import core.stdc.string;
// Utiliser un petit tampon pour couvrir le cas où un lexème ne rentre pas.
// Dans la vraie vie, utiliser un tampon plus grand.
enum BUFSIZE = 10;
struct State {
    FILE* file;
    char[BUFSIZE + 1] buffer;
    char* yylimit, yycursor, yymarker, token;
    int yystate;
};
enum Status {END, READY, WAITING, BAD_PACKET, BIG_PACKET};
private Status fill(ref State st) {
    const size_t shift = st.token - cast(char*)st.buffer;
    const size_t used = st.yylimit - st.token;
    const size_t free = BUFSIZE - used;
    // Erreur : pas d'espace. Dans la vraie vie, on peut réallouer un tampon plus grand.
    if (free < 1) return Status.BIG_PACKET;
    // Décaler le contenu du tampon (ignorer les données déjà traitées).
    memmove(cast(void*)st.buffer, st.token, used);
    st.yylimit -= shift;
    st.yycursor -= shift;
    st.yymarker -= shift;
    st.token -= shift;
    // Remplir l'espace libre à la fin du tampon avec de nouvelles données.
    const size_t read = fread(st.yylimit, 1, free, st.file);
    st.yylimit += read;
    st.yylimit[0] = 0; // ajouter le symbole sentinelle
    return Status.READY;
}
private Status lex(ref State yyrecord, uint* recv) {
    char yych;
    /*!getstate:re2c*/
    for (;;) {
        yyrecord.token = yyrecord.yycursor;
    /*!re2c
        re2c:api = record;
        re2c:YYCTYPE = char;
        re2c:YYFILL = "return Status.WAITING;";
        re2c:eof = 0;
        packet = [a-z]+[;];
        *      { return Status.BAD_PACKET; }
        $      { return Status.END; }
        packet { *recv = *recv + 1; continue; }
    */
    }
    assert(0); // unreachable
}
private void test(string[] packets, Status expect) {
    // Créer un pipe (ouvrir le même fichier pour la lecture et l'écriture).
    const(char*) fname = "pipe";
    FILE* fw = fopen(fname, "w");
    FILE* fr = fopen(fname, "r");
    setvbuf(fw, null, _IONBF, 0);
    setvbuf(fr, null, _IONBF, 0);
    // Initialiser l'état de l'analyseur lexical : la valeur de `state` est -1, tous les pointeurs sont à la fin
    // du tampon.
    State st;
    st.file = fr;
    st.yycursor = st.yymarker = st.token = st.yylimit = cast(char*)st.buffer + BUFSIZE;
    // Le sentinelle (au pointeur YYLIMIT) est mis à zéro, ce qui déclenche YYFILL.
    st.yylimit[0] = 0;
    st.yystate = -1;
    // Boucle principale. Le tampon contient des données incomplètes qui apparaissent paquet par
    // paquet. Lorsque l'analyseur lexical a besoin de plus d'entrée, il sauvegarde son état interne et
    // retourne à l'appelant qui doit fournir plus d'entrée et reprendre l'analyse.
    Status status;
    uint send = 0, recv = 0;
    for (;;) {
        status = lex(st, &recv);
        if (status == Status.END) {
            debug{printf("done: got %u packets\n", recv);}
            break;
        } else if (status == Status.WAITING) {
            debug{printf("waiting...\n");}
            if (send < packets.length) {
                debug{printf("sent packet %u\n", send);}
                fprintf(fw, "%s", cast(char*)packets[send]);
                ++send;
            }
            status = fill(st);
            debug{printf("queue: '%s'\n", cast(char*)st.buffer);}
            if (status == Status.BIG_PACKET) {
                debug{printf("error: packet too big\n");}
                break;
            }
            assert(status == Status.READY);
        } else {
            assert(status == Status.BAD_PACKET);
            debug{printf("error: ill-formed packet\n");}
            break;
        }
    }
    // Vérifier les résultats.
    assert(status == expect);
    if (status == Status.END) assert(recv == send);
    // Nettoyage : supprimer le fichier d'entrée.
    fclose(fw);
    fclose(fr);
    remove(fname);
}
void main() {
    string[] packets1 = [];
    string[] packets2 = ["zero;", "one;", "two;", "three;", "four;"];
    string[] packets3 = ["zer0;"];
    string[] packets4 = ["looooooooooong;"];
    test(packets1, Status.END);
    test(packets2, Status.END);
    test(packets3, Status.BAD_PACKET);
    test(packets4, Status.BIG_PACKET);
}

Blocs réutilisables

Les blocs réutilisables de la forme /*!rules:re2c[:<nom>] ... */ ou %{règles[:<nom>] ... %} peuvent être réutilisés un nombre quelconque de fois et combinés avec d'autres blocs re2c. Le <nom> est facultatif. Un bloc de règles peut être utilisé dans un bloc use ou une directive. Le code d'un bloc de règles est généré à chaque point d'utilisation.

Les blocs d'utilisation sont définis avec /*!use:re2c[:<nom>] ... */ ou %{use[:<nom>] ... %}. Le <nom> est facultatif : s'il n'est pas spécifié, le bloc de règles associé est le plus récent (nommé ou non). Un bloc d'utilisation peut ajouter des définitions nommées, des configurations et des règles propres. Un cas d'utilisation important pour les blocs d'utilisation est un analyseur lexical qui prend en charge plusieurs encodages d'entrée : le même bloc de règles est réutilisé plusieurs fois avec des configurations spécifiques à l'encodage (voir l'exemple ci-dessous).

La directive d'utilisation dans le bloc !use:<nom>; peut être utilisée depuis l'intérieur d'un bloc re2c. Elle fusionne le bloc référencé <nom> dans le bloc actuel. Si certaines des règles et configurations fusionnées se chevauchent avec celles définies précédemment, les conflits sont résolus de la manière habituelle : la règle la plus ancienne a la priorité, et la configuration la plus récente remplace les précédentes. Une exception concerne les règles spéciales *, $ et (en mode condition) <!>, pour lesquelles une définition locale au bloc remplace toute définition héritée. La directive d'utilisation permet de combiner différents blocs re2c dans un seul bloc (voir l'exemple ci-dessous).

Les blocs nommés et la directive d'utilisation dans le bloc ont été ajoutés dans la version 2.2 de re2c. Depuis cette version, les blocs réutilisables sont autorisés par défaut (aucune option spéciale n'est nécessaire). Avant la version 2.2, le mode réutilisable était activé avec l'option -r --reusable. Avant la version 1.2, les blocs réutilisables ne pouvaient pas être mélangés avec des blocs normaux.

Extraction de sous-correspondances

re2d propose deux options pour l'extraction de sous-correspondances.

Balises
La première option consiste à utiliser des balises autonomes de la forme @stag ou #mtag, où stag et mtag sont des noms arbitraires définis par l'utilisateur. Les balises sont activées avec l'option -T --tags ou la configuration re2c:tags = 1. Sémantiquement, les balises sont des marqueurs de position : elles peuvent être insérées n'importe où dans une expression régulière et elles se lient à la ou aux positions correspondantes dans la chaîne d'entrée. Les balises s (simples) se lient à la dernière position correspondante, et les balises m (multiples) se lient à une liste de positions (elles peuvent être utilisées dans des sous-expressions de répétition, où une seule position dans une expression régulière correspond à plusieurs positions dans la chaîne d'entrée). Toutes les balises doivent être définies par l'utilisateur, soit manuellement, soit à l'aide des blocs svars et mvars. S'il existe plus d'une façon dont les balises peuvent correspondre à l'entrée, l'ambiguïté est résolue en utilisant la stratégie de désambiguïsation la plus à gauche et gourmande.
Captures
La seconde option consiste à utiliser des groupes de capture. Ils sont activés avec l'option --captures ou la configuration re2c:captures = 1. Il existe deux variantes pour différentes politiques de désambiguïsation : --leftmost-captures (par défaut) pour la politique gourmande la plus à gauche, et --posix-captures pour la politique de correspondance la plus longue de POSIX. Dans ce mode, toutes les sous-expressions entre parenthèses sont considérées comme des groupes de capture, et un point d'exclamation peut être utilisé pour marquer les groupes non capturants : (! ... ). Avec l'option --invert-captures ou la configuration re2c:invert-captures = 1, la signification du point d'exclamation est inversée. Le nombre de groupes pour la règle de correspondance est stocké dans une variable yynmatch (l'expression régulière entière est le groupe numéro zéro), et les résultats des sous-correspondances sont stockés dans le tableau yypmatch. yynmatch et yypmatch doivent être définis par l'utilisateur, et la taille de yypmatch doit être d'au moins [yynmatch * 2]. Utilisez le bloc maxnmatch pour définir YYMAXNMATCH, une constante égale à la valeur maximale de yynmatch parmi toutes les règles.
Captvars
Une autre façon d'utiliser les groupes de capture est l'option --captvars ou la configuration re2c:captvars = 1. La seule différence avec --captures réside dans la manière dont le code généré stocke les résultats des sous-correspondances : au lieu de yynmatch et yypmatch, re2d génère les variables yytl<k> et yytr<k> pour le k-ième groupe de capture (l'utilisateur doit les déclarer à l'aide d'un bloc svars). Les captures avec variables prennent en charge deux politiques de désambiguïsation : --leftmost-captvars ou re2c:leftmost-captvars = 1 pour la politique gourmande la plus à gauche (par défaut), et --posix-captvars ou re2c:posix-captvars pour la politique de correspondance la plus longue de POSIX.

En coulisses, toutes ces options se traduisent par des balises et des Automates Finis Déterministes Étiquetés avec Anticipation (TDFA). L'idée principale des TDFA est de minimiser la surcharge liée à l'extraction des sous-correspondances. Dans le cas extrême, s'il n'y a pas de balises ou de captures dans une expression régulière, un TDFA est simplement un DFA ordinaire. Si le nombre de balises est modéré, la surcharge est à peine perceptible. Le TDFA généré utilise un certain nombre de variables de balise qui ne correspondent pas directement aux balises : une seule variable peut être utilisée pour différentes balises, et une balise peut nécessiter plusieurs variables pour stocker toutes ses valeurs possibles. Finalement, l'ambiguïté est résolue et une seule variable finale par balise survit. Les variables de balise doivent être définies à l'aide des blocs stags ou mtags. Si l'état de l'analyseur est stocké, les variables de balise doivent en faire partie. Elles doivent également être mises à jour par YYFILL.

Les balises s prennent en charge les opérations suivantes :

  • sauvegarder la position d'entrée dans une balise s : t = YYCURSOR avec l'API de pointeur C ou une opération définie par l'utilisateur YYSTAGP(t) avec l'API générique
  • sauvegarder la valeur par défaut dans une balise s : t = NULL avec l'API de pointeur C ou une opération définie par l'utilisateur YYSTAGN(t) avec l'API générique
  • copier une balise s dans une autre : t1 = t2

Les balises m prennent en charge les opérations suivantes :

  • ajouter une position d'entrée à une balise m : une opération définie par l'utilisateur YYMTAGP(t) avec l'API par défaut et l'API générique
  • ajouter une valeur par défaut à une balise m : une opération définie par l'utilisateur YYMTAGN(t) avec l'API par défaut et l'API générique
  • copier une balise m dans une autre : t1 = t2

Les balises s peuvent être implémentées comme des valeurs scalaires (pointeurs ou décalages). Les balises m nécessitent une représentation plus complexe, car elles doivent stocker une séquence de valeurs de balise. La représentation la plus naïve et la moins efficace d'une balise m est une liste (tableau, vecteur) de valeurs de balise ; une représentation plus efficace consiste à stocker toutes les balises m dans un arbre préfixe représenté par un tableau de nœuds (v, p), où v est la valeur de la balise et p est un pointeur vers le nœud parent.

Voici un exemple simple d'utilisation de balises s pour analyser des versions sémantiques composées de trois composantes numériques : majeure, mineure, corrective (cette dernière étant facultative). Voir ci-dessous pour un exemple plus complexe utilisant YYFILL.

// re2d $INPUT -o $OUTPUT
module main;
struct SemVer {
    int major;
    int minor;
    int patch;
};
private int s2n(const(char)* s, const(char)* e) { // chaîne pré-analysée en nombre
    int n = 0;
    for (; s < e; ++s) n = n * 10 + (*s - '0');
    return n;
}
private bool lex(const(char)* str, ref SemVer ver) {
    const(char)* yycursor = str, yymarker;
    // Variables de balise finales disponibles dans l'action sémantique.
    /*!svars:re2c format = 'const(char)* @@;\n'; */
    // Variables de balise intermédiaires utilisées par l'analyseur (doivent être générées automatiquement).
    /*!stags:re2c format = 'const(char)* @@;\n'; */
    /*!re2c
        re2c:yyfill:enable = 0;
        re2c:tags = 1;
        re2c:YYCTYPE = "char";
        num = [0-9]+;
        @t1 num @t2 "." @t3 num @t4 ("." @t5 num)? [\x00] {
            ver.major = s2n(t1, t2);
            ver.minor = s2n(t3, t4);
            ver.patch = t5 != null ? s2n(t5, yycursor - 1) : 0;
            return true;
        }
        * { return false; }
    */
}
void main() {
    SemVer v;
    assert(lex("23.34", v) && v.major == 23 && v.minor == 34 && v.patch == 0);
    assert(lex("1.2.999", v) && v.major == 1 && v.minor == 2 && v.patch == 999);
    assert(!lex("1.a", v));
}

Voici un exemple plus complexe d'utilisation de balises s avec YYFILL pour analyser un fichier avec des versions sémantiques séparées par des nouvelles lignes. Les variables de balise font partie de l'état de l'analyseur et sont ajustées dans YYFILL comme les autres positions d'entrée. Notez que c'est nécessaire pour les balises s car leurs valeurs sont invalidées après le décalage du contenu du tampon. Cela peut ne pas être nécessaire dans une implémentation personnalisée où les variables de balise stockent des décalages relatifs au début de la chaîne d'entrée plutôt qu'au tampon, ce qui peut être le cas avec les balises m.

// re2d $INPUT -o $OUTPUT --tags
module main;
import core.stdc.string;
import core.stdc.stdio;
import std.stdio;
enum BUFSIZE = 4095;
struct Input {
    FILE* file;
    char[BUFSIZE + 1] buffer;// +1 pour le terminateur
    char* yylimit, yycursor, yymarker, token;
    // Les variables de balise intermédiaires doivent faire partie de l'état de l'analyseur passé à YYFILL.
    // Elles ne correspondent pas aux balises et doivent être générées automatiquement par re2c.
    /*!stags:re2c format = 'char* @@;'; */
    bool eof;
};
struct SemVer {
    int major;
    int minor;
    int patch;
};
private int s2n(const(char)* s, const(char)* e) { // chaîne pré-analysée en nombre
    int n = 0;
    for (; s < e; ++s) n = n * 10 + (*s - '0');
    return n;
}
private int fill(ref Input it) {
    if (it.eof) return 1;
    const size_t shift = it.token - it.buffer.ptr;
    const size_t used = it.yylimit - it.token;
    // Erreur : lexème trop long. Dans la réalité, on pourrait réallouer un tampon plus grand.
    if (shift < 1) return 2;
    // Décalage du contenu du tampon (supprimer tout jusqu'au jeton actuel).
    memmove(cast(void*)it.buffer.ptr, it.token, used);
    it.yylimit -= shift;
    it.yycursor -= shift;
    it.yymarker -= shift;
    it.token -= shift;
    // Les variables de balise doivent être décalées comme les autres positions d'entrée. La vérification
    // de la non-nullité n'est nécessaire que si certaines balises sont imbriquées dans des alternatives
    // ou des répétitions, afin qu'elles puissent avoir une valeur nulle.
    /*!stags:re2c format = "if (it.@@) it.@@ -= shift;\n"; */
    // Remplir l'espace libre à la fin du tampon avec de nouvelles données du fichier.
    it.yylimit += fread(it.yylimit, 1, BUFSIZE - used, it.file);
    it.yylimit[0] = 0;
    it.eof = it.yylimit < (it.buffer.ptr + BUFSIZE);
    return 0;
}
private bool lex(ref Input yyrecord, ref SemVer[] vers) {
    // Variables finales disponibles dans les actions sémantiques.
    /*!svars:re2c format = 'cha
r* @@;'; */
    for (;;) {
        yyrecord.token = yyrecord.yycursor;
    /*!re2c
        re2c:api = record;
        re2c:YYCTYPE = "char";
        re2c:YYFILL = "fill(yyrecord) == 0";
        re2c:eof = 0;
        num = [0-9]+;
        num @t1 "." @t2 num @t3 ("." @t4 num)? [\n] {
            int major = s2n(yyrecord.token, t1);
            int minor = s2n(t2, t3);
            int patch = t4 != null ? s2n(t4, yyrecord.yycursor - 1) : 0;
            SemVer ver = SemVer(major, minor, patch);
            vers ~= ver;
            continue;
        }
        $ { return true; }
        * { return false; }
    */
    }
    assert(0);
}
void main() {
    const char[] fname = "input";
    const char[] content = "1.22.333\n' ";
    SemVer[BUFSIZE] expect = SemVer(1, 22, 333);
    SemVer[] actual;
    // Préparer le fichier d'entrée : quelques fois la taille du tampon, contenant
    // des chaînes avec des zéros et des guillemets échappés.
    FILE* f = fopen(fname.ptr, "w");
    for (int i = 0; i < BUFSIZE; ++i) {
        fwrite(cast(const(void*)) content.ptr, 1, content.length - 2, f); // ignorer le terminateur nul
    }
    fclose(f);
    // Initialiser l'état du lexer : tous les pointeurs sont à la fin du tampon.
    Input it;
    it.file = fopen(fname.ptr, "r");
    it.yycursor = it.yymarker = it.token = it.yylimit = it.buffer.ptr + BUFSIZE;
    it.eof = 0;
    // Le sentinelle (au pointeur YYLIMIT) est défini à zéro, ce qui déclenche YYFILL.
    it.yylimit[0] = 0;
    // Exécuter le lexer.
    assert(lex(it, actual) && actual == expect);
    // Nettoyage : supprimer le fichier d'entrée.
    fclose(it.file);
    remove(fname.ptr);
}

Voici un exemple d'utilisation de m-tags pour analyser une version avec un nombre variable de composants. Les variables de balise sont stockées dans un trie.

// re2d $INPUT -o $OUTPUT
module main;
enum MtagRoot = -1;
// Un arbre m-tag est un moyen de stocker des historiques avec une opération de copie en O(1).
// Les historiques forment naturellement un arbre, car ils ont un début commun et se
// séparent à un certain point. L'arbre est stocké sous forme de tableau de paires (valeur de balise, lien vers le parent).
// Une m-tag est représentée par un seul lien dans l'arbre (index du tableau).
struct Mtag {
    const(char)* elem; // valeur de la balise
    int pred; // index du nœud prédécesseur ou de la racine
};
alias MtagTrie = Mtag[];
alias Ver = int[];
private int s2n(const(char)* s, const(char)* e) { // chaîne pré-analysée en nombre
    int n = 0;
    for (; s < e; ++s) n = n * 10 + (*s - '0');
    return n;
}
// Ajouter une seule valeur à un historique m-tag.
private void add_mtag(ref MtagTrie trie, ref int mtag, const(char)* value) {
    Mtag m = {value, mtag};
    mtag = cast(int)trie.length;
    trie ~= [m];
}
// Dérouler récursivement les historiques de balises et collecter les composants de version.
private void unfold(const ref MtagTrie trie, int x, int y, ref Ver ver) {
    // Atteint la racine de l'arbre m-tag, arrête la récursion.
    if (x == MtagRoot && y == MtagRoot) return;
    // Dérouler davantage l'historique.
    unfold(trie, trie[x].pred, trie[y].pred, ver);
    // Obtenir les valeurs des balises. Les historiques de balises doivent avoir la même longueur.
    assert(x != MtagRoot && y != MtagRoot);
    const(char)* ex = trie[x].elem, ey = trie[y].elem;
    if (ex != null && ey != null) {
        // Les deux balises sont des pointeurs valides, extraire le composant.
        ver ~= [s2n(ex, ey)];
    } else {
        // Les deux balises sont nulles (cela correspond à zéro répétitions).
        assert(ex == null && ey == null);
    }
}
private bool parse(const(char)* str, ref Ver ver) {
    const(char)* yycursor = str, yymarker;
    MtagTrie mt;
    // Variables de balise finales disponibles dans l'action sémantique.
    /*!svars:re2c format = "const(char)* @@;"; */
    /*!mvars:re2c format = "int @@;"; */
    // Variables de balise intermédiaires utilisées par le lexer (doivent être générées automatiquement).
    /*!stags:re2c format = "const(char)* @@ = null;"; */
    /*!mtags:re2c format = "int @@ = MtagRoot;"; */
    /*!re2c
        re2c:yyfill:enable = 0;
        re2c:tags = 1;
        re2c:YYCTYPE = "char";
        re2c:YYMTAGP = "add_mtag(mt, @@, yycursor);";
        re2c:YYMTAGN = "add_mtag(mt, @@, null);";
        num = [0-9]+;
        @t1 num @t2 ("." #t3 num #t4)* [\x00] {
            ver = [];
            ver ~= [s2n(t1, t2)];
            unfold(mt, t3, t4, ver);
            return true;
        }
        * { return false; }
    */
}
void main() {
    Ver v;
    assert(parse("1", v) && v == [1]);
    assert(parse("1.2.3.4.5.6.7", v) && v == [1, 2, 3, 4, 5, 6, 7]);
    assert(!parse("1.2.", v));
}

Support de l'encodage

Il est nécessaire de comprendre la différence entre les points de code et les unités de code. Un point de code est un identifiant numérique d'un symbole. Une unité de code est la plus petite unité de stockage dans le texte encodé. Un seul point de code peut être représenté par une ou plusieurs unités de code. Dans un encodage à longueur fixe, tous les points de code sont représentés par le même nombre d'unités de code. Dans un encodage à longueur variable, les points de code peuvent être représentés par un nombre différent d'unités de code. Notez que la règle "tout" [^] correspond à n'importe quel point de code, mais pas nécessairement à n'importe quelle unité de code (la seule façon de correspondre à n'importe quelle unité de code indépendamment de l'encodage est la règle par défaut *). Le lexer généré fonctionne avec un flux d'unités de code : yych contient une unité de code, et YYCTYPE est le type d'unité de code. Les expressions régulières, en revanche, sont spécifiées en termes de points de code. Lorsque re2d compile des expressions régulières en automates, il traduit les points de code en unités de code. Ce n'est généralement pas un mappage simple : dans les encodages à longueur variable, une seule plage de points de code peut être traduite en un graphe complexe d'unités de code. Les encodages suivants sont pris en charge :

  • ASCII (activé par défaut). C'est un encodage à longueur fixe avec un espace de code [0-255] et des points de code et des unités de code de 1 octet.
  • EBCDIC (activé avec --ebcdic ou re2c:encoding:ebcdic). C'est un encodage à longueur fixe avec un espace de code [0-255] et des points de code et des unités de code de 1 octet.
  • UCS2 (activé avec --ucs2 ou re2c:encoding:ucs2). C'est un encodage à longueur fixe avec un espace de code [0-0xFFFF] et des points de code et des unités de code de 2 octets.
  • UTF8 (activé avec --utf8 ou re2c:encoding:utf8). C'est un encodage Unicode à longueur variable. La taille de l'unité de code est de 1 octet. Les points de code sont représentés par 1 à 4 unités de code.
  • UTF16 (activé avec --utf16 ou re2c:encoding:utf16). C'est un encodage Unicode à longueur variable. La taille de l'unité de code est de 2 octets. Les points de code sont représentés par 1 à 2 unités de code.
  • UTF32 (activé avec --utf32 ou re2c:encoding:utf32). C'est un encodage Unicode à longueur fixe avec un espace de code [0-0x10FFFF] et des points de code et des unités de code de 4 octets.

Le fichier d'inclusion include/unicode_categories.re fournit des définitions re2d pour les catégories Unicode standard.

L'option --input-encoding spécifie l'encodage du fichier source, qui peut être utilisée pour activer les littéraux Unicode dans les expressions régulières. Par exemple, --input-encoding utf8 indique à re2d que le fichier source est en UTF8 (cela diffère de --utf8 qui définit l'encodage du texte d'entrée). L'option --encoding-policy spécifie la manière dont re2d gère les substituts Unicode (points de code dans la plage [0xD800-0xDFFF]).

Ci-dessous un exemple de lexer pour des identifiants Unicode encodés en UTF8.

// re2d $INPUT -o $OUTPUT -8 -i
module main;
/*!include:re2c "unicode_categories.re" */
private int lex(const(char)* s) {
    const(char)* yycursor = s, yymarker;
    /*!re2c
        re2c:YYCTYPE = "char";
        re2c:yyfill:enable = 0;
        // "Unicode Identifier and Pattern Syntax" simplifié
        // (voir https://unicode.org/reports/tr31)
        id_start    = L | Nl | [$_];
        id_continue = id_start | Mn | Mc | Nd | Pc | [\u200D\u05F3];
        identifier  = id_start id_continue*;
        identifier { return 0; }
        *          { return 1; }
    */
}
void main() {
    assert(lex("_Ыдентификатор") == 0);
    assert(lex("!!!")==1);
}

Fichiers inclus

re2d permet d'inclure d'autres fichiers en utilisant un bloc de la forme /*!include:re2c FICHIER */ ou %{include FICHIER %}, ou une directive dans un bloc !include FICHIER ;, où FICHIER est un chemin vers le fichier à inclure. re2d recherche les fichiers à inclure dans le répertoire du fichier incluant et dans les emplacements d'inclusion, qui peuvent être spécifiés avec l'option -I. Les blocs/directives d'inclusion dans re2d fonctionnent de la même manière que le #include de C/C++ : le contenu de FICHIER est copié tel quel à l'endroit du bloc/directive. Les fichiers inclus peuvent contenir d'autres inclusions. Utilisez l'option --depfile pour suivre les dépendances de compilation du fichier de sortie par rapport aux fichiers inclus. re2d fournit des fichiers d'inclusion prédéfinis qui peuvent être trouvés dans le sous-répertoire include/ du projet. Ces fichiers contiennent des définitions qui peuvent être utiles à d'autres projets (telles que les catégories Unicode) et forment une sorte de bibliothèque standard pour re2d. Voici un exemple d'utilisation des fichiers d'inclusion.

Fichier inclus 1 (definitions.d)

enum Result{ OK, FAIL };
/*!re2c
    number = [1-9][0-9]*;
*/

Inclure le fichier 2 (extra_rules.re.inc)

// nombres à virgule flottante
frac  = [0-9]* "." [0-9]+ | [0-9]+ ".";
exp   = 'e' [+-]? [0-9]+;
float = frac exp? | [0-9]+ exp;
float { return Result.OK; }

Fichier d'entrée

        re2c:YYCTYPE = "char";

    assert(lex("123.4567") == Result.OK);
}

Fichiers d'en-tête

re2d permet de générer un fichier d'en-tête à partir du fichier .re d'entrée à l'aide de l'option --header ou de la configuration re2c:header et de blocs de paires de la forme /*!header:re2c:on*/ et /*!header:re2c:off*/, ou de %{header:on%} et %{header:off%}. Le premier bloc marque le début du fichier d'en-tête, et le second bloc marque la fin. Tout ce qui se trouve entre ces blocs est traité par re2d, et le code généré est écrit dans le fichier spécifié avec l'option --header ou la configuration re2c:header (ou stdout si aucune option ni configuration n'est utilisée). Un fichier d'en-tête autogénéré peut être nécessaire dans les cas où re2d est utilisé pour générer des définitions qui doivent être visibles à partir d'autres unités de traduction.

Voici un exemple de génération d'un fichier d'en-tête contenant la définition de l'état du lexer avec des variables de balise (le nombre de variables dépend de la grammaire régulière et n'est pas connu du programmeur).

Fichier d'entrée

Programmes squelettes

Avec l'option -S, --skeleton, re2d ignore tout le code non-re2d et génère un programme C autonome qui peut être compilé et exécuté ultérieurement. Le programme se compose du code du lexer et des données d'entrée. Pour chaque AFD (bloc ou condition) construite, re2d génère un lexer autonome et deux fichiers : un fichier .input avec des chaînes dérivées de l'AFD, et un fichier .keys avec les résultats de correspondance attendus. Le programme exécute chaque lexer sur le fichier .input correspondant et compare les résultats avec les attentes. Les programmes squelettes sont très utiles pour plusieurs raisons :

  • Ils peuvent vérifier la correction de diverses optimisations de re2d (les données sont générées tôt dans le processus, avant toute transformation d'AFD).
  • La génération d'un ensemble de données d'entrée avec une bonne couverture peut être utile pour les tests et les benchmarks.
  • La génération de programmes exécutables autonomes permet d'obtenir des cas de test minimisés (le code original peut être volumineux ou avoir de nombreuses dépendances).

La difficulté de la génération de données d'entrée est que, pour tous les cas, sauf les plus triviaux, le nombre de chaînes d'entrée possibles est trop grand (même si la longueur de la chaîne est limitée). re2d résout cette difficulté en générant suffisamment de chaînes pour couvrir presque toutes les transitions d'AFD. Il utilise l'algorithme suivant. Tout d'abord, il construit un squelette de l'AFD. Pour les encodages avec une taille d'unité de code de 1 octet (comme ASCII, UTF-8 et EBCDIC), le squelette est simplement une copie exacte de l'AFD d'origine. Pour les encodages avec des unités de code multibyte, le squelette est une copie de l'AFD avec certaines transitions omises : à savoir, re2d prend au plus 256 unités de code pour chaque plage continue disjointes qui correspond à une transition d'AFD. Les valeurs choisies sont réparties uniformément et incluent les bornes de la plage. Au lieu d'essayer de couvrir tous les chemins possibles dans le squelette (ce qui est infaisable), re2d génère suffisamment de chemins pour couvrir toutes les transitions du squelette, et ainsi déclencher les sauts conditionnels correspondants dans le lexer. L'implémentation de l'algorithme est limitée à environ 1 Go de transitions et consomme une quantité constante de mémoire (re2d écrit les données dans un fichier dès qu'elles sont générées).

Visualisation et débogage

Avec l'option -D, --emit-dot, re2d ne génère pas de code. Au lieu de cela, il décharge l'AFD générée au format DOT. On peut convertir cette décharge en une image de l'AFD à l'aide de Graphviz ou d'une autre bibliothèque. Notez que cette option montre l'AFD finale après qu'elle a subi plusieurs optimisations et transformations. Les étapes précédentes peuvent être déchargées avec diverses options de débogage, telles que --dump-nfa, --dump-dfa-raw, etc. (voir la liste complète des options).
