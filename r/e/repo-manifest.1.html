NOM

repo - manifeste repo - page de manuel pour le manifeste repo

SYNTAXE

repo manifest [-o {-|NOM.xml}] [-m MANIFEST.xml] [-r]

DESCRIPTION

Résumé

Utilitaire d'inspection de manifeste

OPTIONS

-h, --help
afficher ce message d'aide et quitter
-r, --revision-as-HEAD
enregistrer les révisions comme HEAD actuel
-m NOM.xml, --manifest-name=NOM.xml
manifeste temporaire à utiliser pour cette synchronisation
--suppress-upstream-revision
si en mode -r, n'écrire pas le champ upstream (utile seulement si les noms de branche pour un manifeste sha1 sont sensibles)
--suppress-dest-branch
si en mode -r, n'écrire pas le champ dest-branch (utile seulement si les noms de branche pour un manifeste sha1 sont sensibles)
--format=FORMAT
format de sortie : xml, json (par défaut : xml)
--pretty
formater la sortie pour qu'elle soit lisible par des humains
--no-local-manifests
ignorer les manifestes locaux
-o -|NOM.xml, --output-file=-|NOM.xml
fichier dans lequel enregistrer le manifeste. (Préfixe de nom de fichier pour plusieurs arbres.)

Options de journalisation :

-v, --verbose
afficher toutes les sorties
-q, --quiet
afficher seulement les erreurs

Options multi-manifestes :

--outer-manifest
opérer en commençant par le manifeste le plus externe
--no-outer-manifest
ne pas opérer sur les manifestes externes
--this-manifest-only
opérer uniquement sur ce (sous-)manifeste
--no-this-manifest-only, --all-manifests
opérer sur ce manifeste et ses sous-manifestes

Exécutez `repo help manifest` pour voir le manuel détaillé.

DÉTAILS

Avec l'option -o, exporte le manifeste actuel pour inspection. Le manifeste et (s'il est présent) les `local_manifests/` sont combinés pour produire un fichier manifeste unique. Ce fichier peut être stocké dans un dépôt Git pour être utilisé lors des futures invocations de 'repo init'.

L'option -r peut être utilisée pour générer un fichier manifeste avec les révisions de projet définies sur le hachage de commit actuel. Ce sont les « manifestes à révisions verrouillées », car ils ne suivent pas une branche particulière. Dans ce cas, l'attribut 'upstream' est défini sur la référence sur laquelle nous étions lorsque le manifeste a été généré. L'attribut 'dest-branch' est défini pour indiquer la référence distante sur laquelle pousser les modifications via 'repo upload'.

Plusieurs formats de sortie sont pris en charge via --format. La sortie par défaut est XML, et les formats sont généralement « condensés ». Utilisez --pretty pour des variations plus lisibles par l'humain.

Format de manifeste repo

Un manifeste repo décrit la structure d'un client repo ; c'est-à-dire les répertoires qui sont visibles et d'où ils doivent être obtenus avec git.

La structure de base d'un manifeste est un dépôt Git vierge contenant un unique fichier `default.xml` dans le répertoire de niveau supérieur.

Les manifestes sont intrinsèquement versionnés, car ils sont conservés au sein d'un dépôt Git. Les mises à jour des manifestes sont automatiquement obtenues par les clients lors de `repo sync`.

Format de fichier XML

Un fichier XML de manifeste (par exemple, `default.xml`) est à peu près conforme au DTD suivant :

```xml <!DOCTYPE manifest [

<!ELEMENT manifest (notice?,
remote*, default?, manifest-server?, submanifest*?, remove-project*, project*, extend-project*, repo-hooks?, superproject?, contactinfo?, include*)>
<!ELEMENT notice (#PCDATA)>
<!ELEMENT remote (annotation*)> <!ATTLIST remote name ID #REQUIRED> <!ATTLIST remote alias CDATA #IMPLIED> <!ATTLIST remote fetch CDATA #REQUIRED> <!ATTLIST remote pushurl CDATA #IMPLIED> <!ATTLIST remote review CDATA #IMPLIED> <!ATTLIST remote revision CDATA #IMPLIED>
<!ELEMENT default EMPTY> <!ATTLIST default remote IDREF #IMPLIED> <!ATTLIST default revision CDATA #IMPLIED> <!ATTLIST default dest-branch CDATA #IMPLIED> <!ATTLIST default upstream CDATA #IMPLIED> <!ATTLIST default sync-j CDATA #IMPLIED> <!ATTLIST default sync-c CDATA #IMPLIED> <!ATTLIST default sync-s CDATA #IMPLIED> <!ATTLIST default sync-tags CDATA #IMPLIED>
<!ELEMENT manifest-server EMPTY> <!ATTLIST manifest-server url CDATA #REQUIRED>
<!ELEMENT submanifest EMPTY> <!ATTLIST submanifest name ID #REQUIRED> <!ATTLIST submanifest remote IDREF #IMPLIED> <!ATTLIST submanifest project CDATA #IMPLIED> <!ATTLIST submanifest manifest-name CDATA #IMPLIED> <!ATTLIST submanifest revision CDATA #IMPLIED> <!ATTLIST submanifest path CDATA #IMPLIED> <!ATTLIST submanifest groups CDATA #IMPLIED> <!ATTLIST submanifest default-groups CDATA #IMPLIED>
<!ELEMENT project (annotation*,
project*, copyfile*, linkfile*)>
<!ATTLIST project name
CDATA #REQUIRED>
<!ATTLIST project path
CDATA #IMPLIED>
<!ATTLIST project remote
IDREF #IMPLIED>
<!ATTLIST project revision
CDATA #IMPLIED>
<!ATTLIST project dest-branch CDATA #IMPLIED> <!ATTLIST project groups CDATA #IMPLIED> <!ATTLIST project sync-c CDATA #IMPLIED> <!ATTLIST project sync-s CDATA #IMPLIED> <!ATTLIST project sync-tags CDATA #IMPLIED> <!ATTLIST project upstream CDATA #IMPLIED> <!ATTLIST project clone-depth CDATA #IMPLIED> <!ATTLIST project force-path CDATA #IMPLIED>
<!ELEMENT annotation EMPTY> <!ATTLIST annotation name CDATA #REQUIRED> <!ATTLIST annotation value CDATA #REQUIRED> <!ATTLIST annotation keep CDATA "true">
<!ELEMENT copyfile EMPTY> <!ATTLIST copyfile src CDATA #REQUIRED> <!ATTLIST copyfile dest CDATA #REQUIRED>
<!ELEMENT linkfile EMPTY> <!ATTLIST linkfile src CDATA #REQUIRED> <!ATTLIST linkfile dest CDATA #REQUIRED>
<!ELEMENT extend-project EMPTY> <!ATTLIST extend-project name CDATA #REQUIRED> <!ATTLIST extend-project path CDATA #IMPLIED> <!ATTLIST extend-project dest-path CDATA #IMPLIED> <!ATTLIST extend-project groups CDATA #IMPLIED> <!ATTLIST extend-project revision CDATA #IMPLIED> <!ATTLIST extend-project remote CDATA #IMPLIED> <!ATTLIST extend-project dest-branch CDATA #IMPLIED> <!ATTLIST extend-project upstream CDATA #IMPLIED> <!ATTLIST extend-project base-rev CDATA #IMPLIED>
<!ELEMENT remove-project EMPTY> <!ATTLIST remove-project name CDATA #IMPLIED> <!ATTLIST remove-project path CDATA #IMPLIED> <!ATTLIST remove-project optional CDATA #IMPLIED> <!ATTLIST remove-project base-rev CDATA #IMPLIED>
<!ELEMENT repo-hooks EMPTY> <!ATTLIST repo-hooks in-project CDATA #REQUIRED> <!ATTLIST repo-hooks enabled-list CDATA #REQUIRED>
<!ELEMENT superproject EMPTY> <!ATTLIST superproject name CDATA #REQUIRED> <!ATTLIST superproject remote IDREF #IMPLIED> <!ATTLIST superproject revision CDATA #IMPLIED>
<!ELEMENT contactinfo EMPTY> <!ATTLIST contactinfo bugurl CDATA #REQUIRED>
<!ELEMENT include EMPTY> <!ATTLIST include name CDATA #REQUIRED> <!ATTLIST include groups CDATA #IMPLIED> <!ATTLIST include revision CDATA #IMPLIED>

]> ```

Pour des raisons de compatibilité entre les différentes versions du dépôt, tous les éléments inconnus sont silencieusement ignorés. Cependant, repo se réserve tous les noms possibles pour une utilisation future. Si vous souhaitez utiliser des éléments personnalisés, l'espace de noms `x-*` est réservé à cet effet, et repo garantit de ne jamais allouer de noms correspondants.

Une description des éléments et de leurs attributs suit.

Élément manifest

L'élément racine du fichier.

Élément notice

Texte arbitraire qui est affiché aux utilisateurs à chaque fois que `repo sync` se termine. Le contenu est simplement transmis tel quel dans le manifeste.

Élément remote

Un ou plusieurs éléments remote peuvent être spécifiés. Chaque élément remote spécifie une URL Git partagée par un ou plusieurs projets et (facultatif) le serveur de révision Gerrit via lequel ces projets soumettent des modifications.

Attribut `name`: Un nom court unique dans ce fichier manifeste. Le nom spécifié ici est utilisé comme nom distant dans le fichier `.git/config` de chaque projet, et est donc automatiquement disponible pour des commandes telles que `git fetch`, `git remote`, `git pull` et `git push`.

Attribut `alias`: L'alias, s'il est spécifié, est utilisé pour remplacer `name` et être défini comme nom distant dans le fichier `.git/config` de chaque projet. Sa valeur peut être dupliquée tandis que l'attribut `name` doit être unique dans le fichier manifeste. Cela aide chaque projet à pouvoir avoir le même nom distant qui pointe en réalité vers une URL distante différente.

Attribut `fetch`: Le préfixe d'URL Git pour tous les projets qui utilisent ce distant. Le nom de chaque projet est ajouté à ce préfixe pour former l'URL réelle utilisée pour cloner le projet.

Attribut `pushurl`: Le préfixe d'URL Git de « push » pour tous les projets qui utilisent ce distant. Le nom de chaque projet est ajouté à ce préfixe pour former l'URL réelle utilisée pour « git push » sur le projet. Cet attribut est facultatif; s'il n'est pas spécifié, « git push » utilisera la même URL que l'attribut `fetch`.

Attribut `review`: Le nom d'hôte du serveur Gerrit où les révisions sont téléchargées par `repo upload`. Cet attribut est facultatif; s'il n'est pas spécifié, `repo upload` ne fonctionnera pas.

Attribut `revision`: Nom d'une branche Git (par exemple, `main` ou `refs/heads/main`). Les remotes avec leur propre révision remplaceront la révision par défaut.

Élément default

Au plus un élément default peut être spécifié. Ses attributs remote et revision sont utilisés lorsqu'un élément project ne spécifie pas son propre attribut remote ou revision.

Attribut `remote`: Nom d'un élément remote précédemment défini. Les éléments project sans leur propre attribut remote utiliseront ce remote.

Attribut `revision`: Nom d'une branche Git (par exemple, `main` ou `refs/heads/main`). Les éléments project sans leur propre attribut revision utiliseront cette révision.

Attribut `dest-branch`: Nom d'une branche Git (par exemple, `main`). Les éléments project qui ne définissent pas leur propre `dest-branch` hériteront cette valeur. Si cette valeur n'est pas définie, les projets utiliseront `revision` par défaut à la place.

Attribut `upstream`: Nom de la référence Git dans laquelle un sha1 peut être trouvé. Utilisé lors de la synchronisation d'un manifeste avec une révision verrouillée en mode -c pour éviter de devoir synchroniser l'intégralité de l'espace de références. Les éléments project qui ne définissent pas leur propre `upstream` hériteront cette valeur.

Attribut `sync-j`: Nombre de jobs parallèles à utiliser lors de la synchronisation.

Attribut `sync-c`: Défini sur true pour synchroniser uniquement la branche Git donnée (spécifiée dans l'attribut `revision`) plutôt que tout l'espace de références. Les éléments project sans leur propre élément `sync-c` utiliseront cette valeur.

Attribut `sync-s`: Défini sur true pour synchroniser également les sous-projets.

Attribut `sync-tags`: Défini sur false pour synchroniser uniquement la branche Git donnée (spécifiée dans l'attribut `revision`) plutôt que les autres balises de référence.

Élément manifest-server

Au plus un manifest-server peut être spécifié. L'attribut url est utilisé pour spécifier l'URL d'un serveur de manifestes, qui est un service XML RPC.

Voir la [documentation smart sync](./smart-sync.md) pour plus de détails.

Élément submanifest

Un ou plusieurs éléments submanifest peuvent être spécifiés. Chaque élément décrit un seul manifeste à extraire comme enfant.

Attribut `name`: Un nom unique (au sein du manifeste (sous) actuel) pour ce submanifest. Il sert de défaut pour `revision` ci-dessous. Le même nom peut être utilisé pour des submanifests avec des (sous)manifestes parents différents.

Attribut `remote`: Nom d'un élément remote précédemment défini. S'il n'est pas fourni, le remote donné par l'élément default est utilisé.

Attribut `project`: Le nom du projet du manifeste. Le nom du projet est ajouté à l'URL de fetch de son remote pour générer l'URL réelle avec laquelle configurer le remote Git. L'URL est formée comme suit :

${remote_fetch}/${project_name}.git

où ${remote_fetch} est l'attribut fetch du remote et ${project_name} est l'attribut name du project. Le suffixe « .git » est toujours ajouté car repo suppose que l'upstream est une forêt de dépôts Git nus. Si le projet a un élément parent, son nom sera préfixé par celui du parent.

Le nom du projet doit correspondre au nom que Gerrit connaît, si Gerrit est utilisé pour les revues de code.

`project` ne doit pas être vide, et ne peut pas être un chemin absolu ou utiliser des composantes de chemin « . » ou « .. ». Il est toujours interprété par rapport aux paramètres de fetch du remote, donc si un chemin de base différent est nécessaire, déclarez un remote différent avec les nouveaux paramètres nécessaires.

S'il n'est pas fourni, le remote et le projet pour ce manifeste seront utilisés : `remote` ne peut pas être fourni.

Les projets d'un submanifest et de ses submanifests sont ajoutés au groupe `submanifest::path:<path_prefix>`.

Attribut `manifest-name`: Le nom du fichier manifeste dans le projet manifeste. S'il n'est pas fourni, `default.xml` est utilisé.

Attribut `revision`: Nom d'une branche Git (par exemple, « main » ou « refs/heads/main »), d'une balise (par exemple, « refs/tags/stable ») ou d'un hash de commit. S'il n'est pas fourni, `name` est utilisé.

Attribut `path`: Un chemin facultatif relatif au répertoire racine du client repo où le répertoire racine du client repo du submanifest doit être placé. S'il n'est pas fourni, `revision` est utilisé.

`path` ne peut pas être un chemin absolu ni utiliser des composantes de chemin « . » ou « .. ».

Attribut `groups`: Liste de groupes supplémentaires auxquels tous les projets du submanifest inclus appartiennent. Cela s'ajoute et se récursive, ce qui signifie que tous les projets dans les submanifests portent tous les groupes de submanifests parents. Même syntaxe que l'élément correspondant de `project`.

Attribut `default-groups`: La liste des groupes de manifestes à synchroniser si aucun paramètre `--groups=` n'a été spécifié à l'initialisation. Lorsque cette liste est vide, utilisez cette liste à la place de « default » comme liste des groupes à synchroniser.

Élément project

Un ou plusieurs éléments project peuvent être spécifiés. Chaque élément décrit un seul dépôt Git à cloner dans l'espace de travail du client repo. Vous pouvez spécifier des sous-modules Git en créant un projet imbriqué. Les sous-modules Git seront automatiquement reconnus et hériteront des attributs de leur parent, mais ceux-ci pourront être remplacés par un élément project explicitement spécifié.

Attribut `name`: Un nom unique pour ce projet. Le nom du projet est ajouté à l'URL de fetch de son remote pour générer l'URL réelle avec laquelle configurer le remote Git. L'URL est formée comme suit :

${remote_fetch}/${project_name}.git

où ${remote_fetch} est l'attribut fetch du remote et ${project_name} est l'attribut name du project. Le suffixe « .git » est toujours ajouté car repo suppose que l'upstream est une forêt de dépôts Git nus. Si le projet a un élément parent, son nom sera préfixé par celui du parent.

Le nom du projet doit correspondre au nom que Gerrit connaît, si Gerrit est utilisé pour les revues de code.

« name » ne doit pas être vide, et ne peut pas être un chemin absolu ou utiliser des composantes de chemin « . » ou « .. ». Il est toujours interprété par rapport aux paramètres de fetch du remote, donc si un chemin de base différent est nécessaire, déclarez un remote différent avec les nouveaux paramètres nécessaires. Ces restrictions ne sont pas appliquées pour les [Manifestes Locaux].

Attribut `path`: Un chemin facultatif relatif au répertoire racine du client repo où le répertoire de travail Git pour ce projet doit être placé. S'il n'est pas fourni, le « name » du projet est utilisé. Si le projet a un élément parent, son chemin sera préfixé par celui du parent.

« path » ne peut pas être un chemin absolu ni utiliser des composantes de chemin « . » ou « .. ». Ces restrictions ne sont pas appliquées pour les [Manifestes Locaux].

Si vous souhaitez placer des fichiers à la racine du checkout (par exemple, un README, un Makefile ou un autre script de build), utilisez les éléments [copyfile] ou [linkfile] à la place.

Attribut `remote`: Nom d'un élément remote précédemment défini. S'il n'est pas fourni, le remote donné par l'élément default est utilisé.

Attribut `revision`: Nom de la branche Git que le manifeste souhaite suivre pour ce projet. Les noms peuvent être relatifs à refs/heads (par exemple, juste « main ») ou absolus (par exemple, « refs/heads/main »). Les balises et/ou les SHA-1 explicites devraient fonctionner en théorie, mais n'ont pas été testés de manière exhaustive. S'il n'est pas fourni, la révision donnée par l'élément remote est utilisée si applicable, sinon l'élément default est utilisé.

Attribut `dest-branch`: Nom d'une branche Git (par exemple, `main`). Lors de l'utilisation de `repo upload`, les modifications seront soumises pour revue de code sur cette branche. Si non spécifié ici et dans l'élément default, `revision` est utilisé à la place.

Attribut `groups`: Liste des groupes auxquels ce projet appartient, séparés par des espaces ou des virgules. Tous les projets appartiennent au groupe « all », et chaque projet appartient automatiquement à un groupe de son nom:`name` et chemin:`path`. Par exemple, pour `<project name="monkeys" path="barrel-of"/>`, cette définition de projet est implicitement dans les groupes de manifestes suivants : default, name:monkeys, et path:barrel-of. Si vous placez un projet dans le groupe « notdefault », il ne sera pas automatiquement téléchargé par repo. Si le projet a un élément parent, le `name` et le `path` ici sont ceux qui sont préfixés.

Attribut `sync-c`: Défini sur true pour synchroniser uniquement la branche Git donnée (spécifiée dans l'attribut `revision`) plutôt que tout l'espace de références.

Attribut `sync-s`: Défini sur true pour synchroniser également les sous-projets.

Attribut `upstream`: Nom de la référence Git dans laquelle un sha1 peut être trouvé. Utilisé lors de la synchronisation d'un manifeste avec une révision verrouillée en mode -c pour éviter de devoir synchroniser l'intégralité de l'espace de références.

>

Attribut `clone-depth`: Définit la profondeur à utiliser lors de la récupération de ce projet. Si spécifiée, cette valeur remplacera toute valeur donnée à `repo init` avec l'option --depth sur la ligne de commande.

Attribut `force-path`: Défini sur vrai pour forcer ce projet à créer le dépôt miroir local selon son attribut `path` (s'il est fourni) plutôt que son attribut `name`. Cet attribut s'applique uniquement aux miroirs locaux en cours de synchronisation, il sera ignoré lors de la synchronisation des projets dans un répertoire de travail client.

Élément extend-project

Modifie les attributs du projet nommé.

Cet élément est principalement utile dans un fichier de manifeste local, pour modifier les attributs d'un projet existant sans remplacer complètement la définition du projet existant. Cela rend le manifeste local plus robuste aux changements apportés au manifeste d'origine.

Attribut `path`: Si spécifié, limite la modification aux projets extraits au chemin spécifié, plutôt qu'à tous les projets portant le même nom.

Attribut `dest-path`: Si spécifié, un chemin relatif au répertoire racine du client `repo` où le répertoire de travail Git pour ce projet doit être placé. Ceci est utilisé pour déplacer un projet dans le checkout en remplaçant le réglage `path` existant.

Attribut `groups`: Liste de groupes supplémentaires auxquels ce projet appartient. Même syntaxe que l'élément correspondant de `project`.

Attribut `revision`: Si spécifié, remplace la révision du projet d'origine. Même syntaxe que l'élément correspondant de `project`.

Attribut `remote`: Si spécifié, remplace le dépôt distant du projet d'origine. Même syntaxe que l'élément correspondant de `project`.

Attribut `dest-branch`: Si spécifié, remplace la branche de destination du projet d'origine. Même syntaxe que l'élément correspondant de `project`.

Attribut `upstream`: Si spécifié, remplace le dépôt amont du projet d'origine. Même syntaxe que l'élément correspondant de `project`.

Attribut `base-rev`: Si spécifié, ajoute une vérification de la révision à étendre. L'analyse du manifeste échouera et donnera une liste des extensions non concordantes si les révisions étendues ont changé depuis la définition de `base-rev`. Prévu pour être utilisé avec des manifestes superposés utilisant des révisions de hachage pour empêcher les branches de correctifs de masquer des révisions amont plus récentes. Compare également les références nommées comme les branches ou les tags, mais peut être trompeur si des branches sont utilisées comme `base-rev`. Même syntaxe que l'élément correspondant de `project`.

Élément annotation

Zéro ou plusieurs éléments `annotation` peuvent être spécifiés comme enfants d'un élément `project` ou `remote`. Chaque élément décrit une paire nom-valeur. Pour les projets, cette paire nom-valeur sera exportée dans l'environnement de chaque projet lors d'une commande `forall`, préfixée par `REPO__`. De plus, il existe un attribut optionnel "keep" qui accepte les valeurs insensibles à la casse "true" (par défaut) ou "false". Cet attribut détermine si l'annotation sera conservée ou non lorsqu'elle est exportée avec la sous-commande `manifest`.

Élément copyfile

Zéro ou plusieurs éléments `copyfile` peuvent être spécifiés comme enfants d'un élément `project`. Chaque élément décrit une paire source-destination de fichiers ; le fichier "src" sera copié à l'endroit "dest" lors de la commande `repo sync`.

"src" est relatif au projet, "dest" est relatif au sommet de l'arborescence. La copie à partir de chemins extérieurs au projet ou vers des chemins extérieurs au client `repo` n'est pas autorisée.

"src" et "dest" doivent être des fichiers. Les répertoires ou les liens symboliques ne sont pas autorisés. Les chemins intermédiaires ne doivent pas non plus être des liens symboliques.

Les répertoires parents de "dest" seront automatiquement créés s'ils sont manquants.

Élément linkfile

Il est identique à `copyfile` et s'exécute en même temps que `copyfile`, mais au lieu de copier, il crée un lien symbolique.

Le lien symbolique est créé à "dest" (relatif au sommet de l'arborescence) et pointe vers le chemin spécifié par "src", qui est un chemin dans le projet.

Les répertoires parents de "dest" seront automatiquement créés s'ils sont manquants.

La cible du lien symbolique peut être un fichier ou un répertoire, mais elle ne peut pas pointer à l'extérieur du client `repo`.

Élément remove-project

Supprime un projet de la table des manifestes interne, permettant éventuellement à un élément `project` ultérieur dans le même fichier de manifeste de remplacer le projet par une source différente.

Cet élément est principalement utile dans un fichier de manifeste local, où l'utilisateur peut supprimer un projet et éventuellement le remplacer par sa propre définition.

Le `name` ou le `path` du projet peut être utilisé pour spécifier la cible de suppression, ce qui signifie que l'un d'eux est requis. Si seul le nom est spécifié, tous les projets portant ce nom sont supprimés.

Si le nom et le chemin sont tous deux spécifiés, seuls les projets portant le même nom et le même chemin sont supprimés, ce qui signifie que les projets portant le même nom mais situés ailleurs sont conservés.

Si seul le chemin est spécifié, un projet correspondant est supprimé quel que soit son nom. La logique se comporte autrement comme si les deux étaient spécifiés.

Attribut `optional`: Défini sur vrai pour ignorer les éléments `remove-project` sans élément `project` correspondant.

Attribut `base-rev`: Si spécifié, ajoute une vérification de la révision à supprimer. L'analyse du manifeste échouera et donnera une liste des suppressions non concordantes si les révisions supprimées ont changé depuis la définition de `base-rev`. Prévu pour être utilisé avec des manifestes superposés utilisant des révisions de hachage pour empêcher les branches de correctifs de masquer des révisions amont plus récentes. Compare également les références nommées comme les branches ou les tags, mais peut être trompeur si des branches sont utilisées comme `base-rev`. Même syntaxe que l'élément correspondant de `project`.

Élément repo-hooks

NB : Voir la [documentation pratique](./repo-hooks.md) pour l'utilisation des hooks repo.

Un seul élément `repo-hooks` peut être spécifié à la fois. Tenter de le redéfinir échouera à l'analyse.

Attribut `in-project`: Le projet où les hooks sont définis. La valeur doit correspondre à l'attribut `name` (et **non** à l'attribut `path`) d'un élément `project` défini précédemment.

Attribut `enabled-list`: Liste des hooks à utiliser, séparés par des espaces ou des virgules.

Élément superproject

*** *Note* : Ceci est actuellement en cours de développement. ***

NB : Voir la [documentation des superprojets Git]( https://en.wikibooks.org/wiki/Git/Submodules_and_Superprojects) pour des informations générales.

Cet élément est utilisé pour spécifier l'URL du superprojet. Il a les attributs "name" et "remote". Seul "name" est requis, tandis que les autres ont des valeurs par défaut raisonnables. Au plus un superprojet peut être spécifié. Tenter de le redéfinir échouera à l'analyse.

Attribut `name`: Un nom unique pour le superprojet. Cet attribut a la même signification que l'attribut `name` du projet. Voir l'[élément project](#element-project) pour plus d'informations.

Attribut `remote`: Nom d'un élément `remote` défini précédemment. Si non fourni, le dépôt distant donné par l'élément `default` est utilisé.

Attribut `revision`: Nom de la branche Git que le manifeste souhaite suivre pour ce superprojet. Si non fourni, la révision donnée par l'élément `remote` est utilisée si applicable, sinon l'élément `default` est utilisé.

Élément contactinfo

*** *Note* : Ceci est actuellement en cours de développement. ***

Cet élément est utilisé pour permettre aux auteurs de manifestes de s'enregistrer eux-mêmes avec leurs informations de contact. Il a l'attribut "bugurl" comme attribut requis. Cet élément peut être répété, et toute entrée ultérieure écrasera les précédentes. Cela permettrait aux auteurs de manifestes qui étendent des manifestes de spécifier leurs propres informations de contact.

Attribut `bugurl`: L'URL pour déposer un rapport de bug contre le propriétaire du manifeste.

Élément include

Cet élément fournit la capacité d'inclure un autre fichier de manifeste dans le manifeste d'origine. Les règles normales s'appliquent pour que le manifeste cible puisse être inclus - il doit être un manifeste utilisable en soi.

Attribut `name`: le manifeste à inclure, spécifié par rapport à la racine du dépôt de manifestes.

"name" ne peut pas être un chemin absolu ni utiliser des composants de chemin "." ou "..". Ces restrictions ne sont pas appliquées pour les [Manifestes Locaux].

Attribut `groups`: Liste de groupes supplémentaires auxquels tous les projets du manifeste inclus appartiennent. Ceci ajoute et récursive, ce qui signifie que tous les projets des manifestes inclus portent tous les groupes d'inclusion parents. Même syntaxe que l'élément correspondant de `project`.

Attribut `revision`: Nom d'une branche Git (par exemple `main` ou `refs/heads/main`) par défaut à laquelle tous les projets du manifeste inclus appartiennent.

Manifestes Locaux

Des dépôts distants et des projets supplémentaires peuvent être ajoutés via des fichiers de manifestes locaux stockés dans `$TOP_DIR/.repo/local_manifests/*.xml`.

Par exemple:

$ ls .repo/local_manifests
local_manifest.xml another_local_manifest.xml
$ cat .repo/local_manifests/local_manifest.xml
<?xml version="1.0" encoding="UTF-8"?> <manifest>
<project path="manifest"
name="tools/manifest" />
<project path="platform-manifest"
name="platform/manifest" />
</manifest>

Les utilisateurs peuvent ajouter des projets au(x) manifeste(s) local(aux) avant une invocation de `repo sync`, ce qui demande à `repo` de télécharger et de gérer automatiquement ces projets supplémentaires.

Les fichiers de manifestes stockés dans `$TOP_DIR/.repo/local_manifests/*.xml` seront chargés par ordre alphabétique.

Les projets des fichiers de manifestes locaux sont ajoutés au groupe `local::<nom du fichier de manifeste local>`.

Le chemin hérité `$TOP_DIR/.repo/local_manifest.xml` n'est plus pris en charge.
