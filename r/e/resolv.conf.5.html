resolv.conf(5) Manuel des formats de fichiers resolv.conf(5)

NOM

resolv.conf - fichier de configuration du résolveur

SYNTAXE

/etc/resolv.conf

DESCRIPTION

Le résolveur est un ensemble de routines dans la bibliothèque C qui fournissent l'accès au système de noms de domaine (DNS) Internet. Le fichier de configuration du résolveur contient des informations qui sont lues par les routines du résolveur la première fois qu'elles sont appelées par un processus. Le fichier est conçu pour être lisible par l'homme et contient une liste de mots-clés avec des valeurs qui fournissent divers types d'informations du résolveur. Le fichier de configuration est considéré comme une source fiable d'informations DNS ; voir l'option trust-ad ci-dessous pour plus de détails.

Si ce fichier n'existe pas, seul le serveur de noms sur la machine locale sera interrogé, et la liste de recherche contiendra le nom de domaine local déterminé à partir du nom d'hôte.

Les différentes options de configuration sont :

nameserver Adresse IP du serveur de noms
Adresse Internet d'un serveur de noms que le résolveur doit interroger, soit une adresse IPv4 (en notation pointée), soit une adresse IPv6 en notation deux-points (et éventuellement pointée) selon la RFC 2373. Jusqu'à MAXNS (actuellement 3, voir <resolv.h>) serveurs de noms peuvent être listés, un par mot-clé. S'il y a plusieurs serveurs, la bibliothèque du résolveur les interroge dans l'ordre de la liste. Si aucune entrée nameserver n'est présente, le défaut est d'utiliser le serveur de noms de la machine locale. (L'algorithme utilisé est d'essayer un serveur de noms, et si la requête expire, d'essayer le suivant, jusqu'à épuisement des serveurs de noms, puis de recommencer à essayer tous les serveurs de noms jusqu'à ce qu'un nombre maximum de nouvelles tentatives soit effectué.)
search Liste de recherche pour la recherche de nom d'hôte.
Par défaut, la liste de recherche contient une entrée, le nom de domaine local. Il est déterminé à partir du nom d'hôte local renvoyé par gethostname(2) ; le nom de domaine local est tout ce qui suit le premier '.'. Enfin, si le nom d'hôte ne contient pas de '.', le domaine racine est supposé être le nom de domaine local.
Cela peut être modifié en listant le chemin de recherche des domaines souhaités après le mot-clé search, séparés par des espaces ou des tabulations. Les requêtes du résolveur comportant moins de ndots points (par défaut 1) seront tentées en utilisant chaque composant du chemin de recherche successivement jusqu'à ce qu'une correspondance soit trouvée. Pour les environnements avec plusieurs sous-domaines, veuillez lire l'option options ndots:n ci-dessous pour éviter les attaques de type "man-in-the-middle" et le trafic inutile vers les serveurs DNS racine. Notez que ce processus peut être lent et générer beaucoup de trafic réseau si les serveurs pour les domaines listés ne sont pas locaux, et que les requêtes expireront si aucun serveur n'est disponible pour l'un des domaines.
S'il y a plusieurs directives search, seule la liste de recherche de la dernière occurrence est utilisée.
Dans glibc 2.25 et antérieures, la liste de recherche est limitée à six domaines avec un total de 256 caractères. Depuis glibc 2.26, la liste de recherche est illimitée.
La directive domain est un nom obsolète pour la directive search qui ne gère qu'une seule entrée de liste de recherche.
sortlist
Cette option permet de trier les adresses renvoyées par gethostbyname(3). Une liste de tri est spécifiée par des paires adresse IP-masque réseau. Le masque est optionnel et par défaut, il s'agit du masque réseau naturel. L'adresse IP et les paires de réseaux optionnelles sont séparées par des barres obliques. Jusqu'à 10 paires peuvent être spécifiées. Voici un exemple :

sortlist 130.155.160.0/255.255.240.0 130.155.0.0
options
Les options permettent de modifier certaines variables internes du résolveur. La syntaxe est
options option ...

où option est l'une des suivantes :

debug
Définit RES_DEBUG dans _res.options (efficace uniquement si glibc a été compilé avec le support de débogage ; voir resolver(3)).
ndots:n
Définit un seuil pour le nombre de points qui doivent apparaître dans un nom donné à res_query(3) (voir resolver(3)) avant qu'une requête absolue initiale ne soit effectuée. La valeur par défaut de n est 1, ce qui signifie que s'il y a des points dans un nom, le nom sera d'abord essayé comme un nom absolu avant que tout élément de la liste de recherche ne lui soit ajouté. La valeur de cette option est silencieusement plafonnée à 15.
timeout:n
Définit le temps pendant lequel le résolveur attendra une réponse d'un serveur de noms distant avant de relancer la requête via un autre serveur de noms. Ceci peut ne pas être le temps total pris par un appel d'API du résolveur et il n'y a aucune garantie qu'un seul appel d'API du résolveur corresponde à un seul délai d'attente. Mesuré en secondes, la valeur par défaut est RES_TIMEOUT (actuellement 5, voir <resolv.h>). La valeur de cette option est silencieusement plafonnée à 30.
attempts:n
Définit le nombre de fois où le résolveur enverra une requête à ses serveurs de noms avant d'abandonner et de renvoyer une erreur à l'application appelante. La valeur par défaut est RES_DFLRETRY (actuellement 2, voir <resolv.h>). La valeur de cette option est silencieusement plafonnée à 5.
rotate
Définit RES_ROTATE dans _res.options, ce qui provoque une sélection en rotation (round-robin) des serveurs de noms parmi ceux listés. Cela a pour effet de répartir la charge des requêtes entre tous les serveurs listés, plutôt que d'avoir tous les clients qui essaient d'abord le premier serveur listé à chaque fois.
no-aaaa (depuis glibc 2.36)
Définit RES_NOAAAA dans _res.options, ce qui supprime les requêtes AAAA effectuées par le résolveur stub, y compris les recherches AAAA déclenchées par des interfaces basées sur NSS comme getaddrinfo(3). Seules les recherches DNS sont affectées : les données IPv6 dans hosts(5) sont toujours utilisées, getaddrinfo(3) avec AI_PASSIVE produira toujours des adresses IPv6, et les serveurs de noms IPv6 configurés sont toujours utilisés. Pour produire des résultats corrects d'erreur de nom (NXDOMAIN), les requêtes AAAA sont traduites en requêtes A. Cette option est destinée en premier lieu à des fins de diagnostic, pour exclure que les requêtes DNS AAAA aient un impact négatif. Elle est incompatible avec l'utilisation d'EDNS0 et la validation DNSSEC par les applications.
no-check-names
Définit RES_NOCHECKNAME dans _res.options, ce qui désactive la vérification moderne de BIND des noms d'hôtes et des noms de courrier entrants pour les caractères invalides tels que le tiret bas (_), les caractères non ASCII ou les caractères de contrôle.
inet6
Définit RES_USE_INET6 dans _res.options. Cela a pour effet d'essayer une requête AAAA avant une requête A dans la fonction gethostbyname(3), et de mapper les réponses IPv4 sous forme "tunnelisée" IPv6 si aucun enregistrement AAAA n'est trouvé mais qu'un ensemble d'enregistrements A existe. Depuis glibc 2.25, cette option est obsolète ; les applications doivent utiliser getaddrinfo(3), plutôt que gethostbyname(3).
ip6-bytestring (depuis glibc 2.3.4 jusqu'à glibc 2.24)
Définit RES_USEBSTRING dans _res.options. Cela provoque des recherches IPv6 inversées utilisant le format d'étiquette par octet décrit dans la RFC 2673 ; si cette option n'est pas définie (ce qui est le défaut), alors le format par nibble est utilisé. Cette option a été supprimée dans glibc 2.25, car elle reposait sur une extension DNS incompatible avec les versions antérieures qui n'a jamais été déployée sur Internet.
ip6-dotint/no-ip6-dotint

EXEMPLES

Voici un exemple typique de fichier /etc/resolv.conf :

     search example.com
     nameserver 192.0.2.1
     nameserver 2001:db8::1
     options ndots:2 timeout:5

Dans cet exemple, les requêtes sans points seront d'abord cherchées dans le domaine example.com. Si la recherche échoue, le résolveur essaiera de joindre 192.0.2.1, puis 2001:db8::1. Si une requête ne reçoit pas de réponse dans les 5 secondes, le résolveur essaiera le serveur suivant. Les requêtes contenant 2 points ou plus seront d'abord essayées comme des noms absolus avant que le domaine example.com ne soit ajouté.

FICHIERS

  • /etc/resolv.conf

VOIR AUSSI

getaddrinfo(3), gethostbyname(3), resolver(3), hosts(5), hostname(7), nsswitch(5)

TRADUCTION

La traduction est basée sur le fichier original en anglais. Si vous trouvez des erreurs ou des inexactitudes, veuillez les signaler sur le bug tracker d'Arch Linux.

/b> (glibc 2.3.4 à glibc 2.24)
Efface/définit RES_NOIP6DOTINT dans _res.options. Lorsque cette option est effacée (ip6-dotint), les recherches IPv6 inversées sont effectuées dans la zone (obsolète) ip6.int ; lorsque cette option est définie (no-ip6-dotint), les recherches IPv6 inversées sont effectuées dans la zone ip6.arpa par défaut. Ces options sont disponibles jusqu'à glibc 2.24, où no-ip6-dotint est la valeur par défaut. Étant donné que la prise en charge de ip6-dotint a cessé depuis longtemps d'être disponible sur Internet, ces options ont été supprimées dans glibc 2.25.
edns0 (depuis glibc 2.6)
Définit RES_USE_EDNS0 dans _res.options. Ceci active la prise en charge des extensions DNS décrites dans la RFC 2671.
single-request (depuis glibc 2.10)
Définit RES_SNGLKUP dans _res.options. Par défaut, glibc effectue les recherches IPv4 et IPv6 en parallèle depuis glibc 2.9. Certains serveurs DNS d'appareils ne peuvent pas gérer ces requêtes correctement et provoquent des délais d'attente. Cette option désactive ce comportement et amène glibc à effectuer les requêtes IPv6 et IPv4 séquentiellement (au détriment d'un certain ralentissement du processus de résolution).
single-request-reopen (depuis glibc 2.9)
Définit RES_SNGLKUPREOP dans _res.options. Le résolveur utilise le même socket pour les requêtes A et AAAA. Certains matériels renvoient à tort une seule réponse. Lorsque cela se produit, le système client attend la deuxième réponse. L'activation de cette option modifie ce comportement de manière à ce que, si deux requêtes provenant du même port ne sont pas gérées correctement, le socket soit fermé et un nouveau soit ouvert avant l'envoi de la deuxième requête.
no-tld-query (depuis glibc 2.14)
Définit RES_NOTLDQUERY dans _res.options. Cette option empêche res_nsearch() de tenter de résoudre un nom non qualifié comme s'il s'agissait d'un domaine de premier niveau (TLD). Cette option peut causer des problèmes si le site a « localhost » comme TLD plutôt que d'avoir localhost sur un ou plusieurs éléments de la liste de recherche. Cette option n'a aucun effet si ni RES_DEFNAMES ni RES_DNSRCH ne sont définis.
use-vc (depuis glibc 2.14)
Définit RES_USEVC dans _res.options. Cette option force l'utilisation de TCP pour les résolutions DNS.
no-reload (depuis glibc 2.26)
Définit RES_NORELOAD dans _res.options. Cette option désactive le rechargement automatique d'un fichier de configuration modifié.
trust-ad (depuis glibc 2.31)
Définit RES_TRUSTAD dans _res.options. Cette option contrôle le comportement du bit AD du résolveur stub. Si un résolveur validant définit le bit AD dans une réponse, cela indique que les données de la réponse ont été vérifiées conformément au protocole DNSSEC. Afin de pouvoir se fier au bit AD, le système local doit faire confiance à la fois au résolveur validant DNSSEC et au chemin réseau menant à celui-ci, d'où la nécessité d'un choix explicite. Si l'option trust-ad est active, le résolveur stub définit le bit AD dans les requêtes DNS sortantes (pour activer la prise en charge du bit AD) et conserve le bit AD dans les réponses. Sans cette option, le bit AD n'est pas défini dans les requêtes, et il est toujours supprimé des réponses avant qu'elles ne soient renvoyées à l'application. Cela signifie que les applications peuvent faire confiance au bit AD dans les réponses si l'option trust-ad a été correctement définie.
Dans glibc 2.30 et versions antérieures, l'AD n'est pas définie automatiquement dans les requêtes et est transmise inchangée aux applications dans les réponses.

Le mot-clé search d'un fichier resolv.conf d'un système peut être remplacé par processus en définissant la variable d'environnement LOCALDOMAIN avec une liste de domaines de recherche séparés par des espaces.

Le mot-clé options d'un fichier resolv.conf d'un système peut être complété par processus en définissant la variable d'environnement RES_OPTIONS avec une liste d'options du résolveur séparées par des espaces, comme expliqué ci-dessus sous options.

Le mot-clé et la valeur doivent apparaître sur une seule ligne, et le mot-clé (par exemple, nameserver) doit commencer la ligne. La valeur suit le mot-clé, séparée par des espaces blancs.

Les lignes contenant un point-virgule (;) ou un caractère dièse (#) dans la première colonne sont traitées comme des commentaires.
