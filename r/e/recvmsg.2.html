recv(2) Manuel des appels système recv(2)

NOM

recv, recvfrom, recvmsg - recevoir un message d'une socket

BIBLIOTHÈQUE

Bibliothèque C standard (libc, -lc)

SYNOPSIS

#include <sys/socket.h>
ssize_t recv(int sockfd, void buf[size], size_t size,
                 int flags);
ssize_t recvfrom(int sockfd, void buf[restrict size], size_t size,
                 int flags,
                 struct sockaddr *_Nullable restrict src_addr,
                 socklen_t *_Nullable restrict addrlen);
ssize_t recvmsg(int sockfd, struct msghdr *msg, int flags);

DESCRIPTION

Les appels recv(), recvfrom(), et recvmsg() sont utilisés pour recevoir des messages d'une socket. Ils peuvent être utilisés pour recevoir des données sur des sockets sans connexion et des sockets avec connexion. Cette page décrit d'abord les fonctionnalités communes des trois appels système, puis décrit les différences entre les appels.

La seule différence entre recv() et read(2) est la présence de flags. Avec un argument flags nul, recv() est généralement équivalent à read(2) (mais voir NOTES). De même, l'appel suivant


recv(sockfd, buf, size, flags);

est équivalent à


recvfrom(sockfd, buf, size, flags, NULL, NULL);

Les trois appels retournent la taille du message en cas de succès. Si un message est trop long pour tenir dans le tampon fourni, les octets excédentaires peuvent être rejetés en fonction du type de socket à partir de laquelle le message est reçu.

Si aucun message n'est disponible sur la socket, les appels de réception attendent l'arrivée d'un message, à moins que la socket ne soit non bloquante (voir fcntl(2)), auquel cas la valeur -1 est retournée et errno est défini à EAGAIN ou EWOULDBLOCK. Les appels de réception retournent normalement toutes les données disponibles, jusqu'à concurrence du montant demandé, plutôt que d'attendre la réception du montant total demandé.

Une application peut utiliser select(2), poll(2), ou epoll(7) pour déterminer quand plus de données arrivent sur une socket.

L'argument flags

L'argument flags est formé en combinant un ou plusieurs des valeurs suivantes :

MSG_CMSG_CLOEXEC (seulement recvmsg() ; depuis Linux 2.6.23)
Définit le drapeau close-on-exec pour le descripteur de fichier reçu via un descripteur de fichier UNIX en utilisant l'opération SCM_RIGHTS (décrite dans unix(7)). Ce drapeau est utile pour les mêmes raisons que le drapeau O_CLOEXEC de open(2).
MSG_DONTWAIT (depuis Linux 2.2)
Active le fonctionnement non bloquant ; si l'opération bloquerait, l'appel échoue avec EAGAIN ou EWOULDBLOCK. Cela fournit un comportement similaire à la définition du drapeau O_NONBLOCK (via l'opération F_SETFL de fcntl(2)), mais diffère en ce que MSG_DONTWAIT est une option par appel, tandis que O_NONBLOCK est un réglage sur la description de fichier ouverte (voir open(2)), qui affectera tous les threads du processus appelant ainsi que d'autres processus qui détiennent des descripteurs de fichiers se référant à la même description de fichier ouverte.
MSG_ERRQUEUE (depuis Linux 2.2)
Ce drapeau spécifie que les erreurs mises en file d'attente doivent être reçues depuis la file d'erreurs de la socket. L'erreur est transmise dans un message auxiliaire dont le type dépend du protocole (pour IPv4 IP_RECVERR). L'utilisateur doit fournir un tampon de taille suffisante. Voir cmsg(3) et ip(7) pour plus d'informations. La charge utile du paquet d'origine qui a causé l'erreur est transmise comme données normales via msg_iovec. L'adresse de destination d'origine du datagramme qui a causé l'erreur est fournie via msg_name.
L'erreur est fournie dans une structure sock_extended_err :

#define SO_EE_ORIGIN_NONE    0
#define SO_EE_ORIGIN_LOCAL   1
#define SO_EE_ORIGIN_ICMP    2
#define SO_EE_ORIGIN_ICMP6   3
struct sock_extended_err
{
    uint32_t ee_errno;   /* Numéro d'erreur */
    uint8_t  ee_origin;  /* Origine de l'erreur */
    uint8_t  ee_type;    /* Type */
    uint8_t  ee_code;    /* Code */
    uint8_t  ee_pad;     /* Rembourrage */
    uint32_t ee_info;    /* Informations supplémentaires */
    uint32_t ee_data;    /* Autres données */
    /* Plus de données peuvent suivre */
};
struct sockaddr *SO_EE_OFFENDER(struct sock_extended_err *);

ee_errno contient le numéro errno de l'erreur mise en file d'attente. ee_origin est le code d'origine de l'endroit où l'erreur est survenue. Les autres champs sont spécifiques au protocole. La macro SO_EE_OFFENDER retourne un pointeur vers l'adresse de l'objet réseau à l'origine de l'erreur, étant donné un pointeur vers le message auxiliaire. Si cette adresse n'est pas connue, le membre sa_family de sockaddr contient AF_UNSPEC et les autres champs de sockaddr ne sont pas définis. La charge utile du paquet qui a causé l'erreur est transmise comme données normales.
Pour les erreurs locales, aucune adresse n'est transmise (cela peut être vérifié avec le membre cmsg_len de cmsghdr). Pour les réceptions d'erreurs, le drapeau MSG_ERRQUEUE est défini dans msghdr. Après qu'une erreur a été transmise, l'erreur de socket en attente est régénérée en fonction de la prochaine erreur mise en file d'attente et sera transmise lors de la prochaine opération sur la socket.
MSG_OOB
Ce drapeau demande la réception de données hors bande qui ne seraient pas reçues dans le flux de données normal. Certains protocoles placent les données urgentes en tête de la file d'attente de données normale, et donc ce drapeau ne peut pas être utilisé avec de tels protocoles.
MSG_PEEK
Ce drapeau fait que l'opération de réception retourne les données depuis le début de la file d'attente de réception sans les en retirer. Ainsi, un appel de réception ultérieur retournera les mêmes données.
MSG_TRUNC (depuis Linux 2.2)
Pour les sockets brutes (AF_PACKET), datagramme Internet (depuis Linux 2.4.27/2.6.8), netlink (depuis Linux 2.6.22), et datagramme UNIX ainsi que séquencé-paquet (depuis Linux 3.4) : retourne la taille réelle du paquet ou du datagramme, même lorsqu'il était plus long que le tampon fourni.
Pour une utilisation avec les sockets de flux Internet, voir tcp(7).
MSG_WAITALL (depuis Linux 2.2)
Ce drapeau demande que l'opération bloque jusqu'à ce que la requête complète soit satisfaite. Cependant, l'appel peut toujours retourner moins de données que demandé si un signal est intercepté, qu'une erreur ou une déconnexion se produit, ou que les prochaines données à recevoir sont d'un type différent de celles retournées. Ce drapeau n'a aucun effet pour les sockets de datagramme.

recvfrom()

recvfrom() place le message reçu dans le tampon buf. L'appelant doit spécifier la taille du tampon dans size.

Si src_addr n'est pas NULL, et que le protocole sous-jacent fournit l'adresse source du message, cette adresse source est placée dans le tampon pointé par src_addr. Dans ce cas, addrlen est un argument valeur-résultat. Avant l'appel, il doit être initialisé à la taille du tampon associé à src_addr. Au retour, addrlen est mis à jour pour contenir la taille réelle de l'adresse source. L'adresse retournée est tronquée si le tampon fourni est trop petit ; dans ce cas, addrlen retournera une valeur supérieure à celle fournie lors de l'appel.

Si l'appelant ne s'intéresse pas à l'adresse source, src_addr et addrlen doivent être spécifiés comme NULL.

recv(), recvfrom(), recvmsg() - receive a message from a socket

LIBRARY

Socket API (libc, -lsocket)

SYNOPSIS

       #include <sys/types.h>
       #include <sys/socket.h>

       ssize_t recv(int sockfd, void *buf, size_t len, int flags);

       ssize_t recvfrom(int sockfd, void *buf, size_t len, int flags,
                        struct sockaddr *src_addr, socklen_t *addrlen);

       ssize_t recvmsg(int sockfd, struct msghdr *msg, int flags);

DESCRIPTION

The recv(), recvfrom(), and recvmsg() calls are used to receive messages from a socket. They are generally used with connected datagram sockets, or with sockets which are not connected.

The parameters are as follows:

sockfd
the file descriptor of the socket to receive from.
buf
the buffer into which the data will be placed.
len
the length of the buffer pointed to by buf.
flags
options to control the behavior of the function. The value of flags is the bitwise OR of zero or more of the following flags:
MSG_PEEK
do not consume data from the socket. If set, data read is not removed from the input queue. This is useful for things like checking the number of bytes available to read without discarding the data.
MSG_TRUNC
with IP datagram sockets, this returns the real length of the datagram when it is longer than len. If the datagram is larger than the buffer, the data is truncated. This flag is only defined for IP version 4.
MSG_DONTWAIT
enable non-blocking operation; with any other value, this flag is ignored. See the fcntl(2) man page for details on the non-blocking setting.
MSG_WAITALL
(since Linux) attempt to fill the buffer. In stream sockets, this option attempts to return all the requested data. The call will not return until either all the data is received, an error occurs, or the connection is abruptly closed. The recv() call counts the bytes received after the call returns. If the call is interrupted by a signal after some data has been received, E_INTR is returned.
MSG_ERRQUEUE
(since Linux) This flag allows a process to receive outbound messages generated by protocols at higher layers (e.g., ICMP messages). These messages are received from the socket error queue. See ip(7) for details.

The parameter src_addr is a pointer to a buffer that will receive the source address of the datagram. addrlen is a pointer to a socklen_t value that initially contains the size of the buffer pointed to by src_addr and, after the call returns, contains the actual size of the source address. If src_addr is NULL, no address information is retrieved.

recv()

The recv() call is normally used only on a connected socket (see connect(2)). It is equivalent to the call:


recvfrom(fd, buf, size, flags, NULL, NULL);

recvmsg()

The recvmsg() call uses a msghdr structure to minimize the number of directly supplied arguments. This structure is defined as follows in <sys/socket.h>:


struct msghdr {
    void         *msg_name;       /* Optional address */
    socklen_t     msg_namelen;    /* Size of address */
    struct iovec *msg_iov;        /* Scatter/gather array */
    size_t        msg_iovlen;     /* # elements in msg_iov */
    void         *msg_control;    /* Ancillary data, see below */
    size_t        msg_controllen; /* Ancillary data buffer size */
    int           msg_flags;      /* Flags on received message */
};

The msg_name field points to a caller-allocated buffer that is used to return the source address if the socket is unconnected. The caller should set msg_namelen to the size of this buffer before this call; upon return from a successful call, msg_namelen will contain the size of the returned address. If the application does not need to know the source address, msg_name can be specified as NULL.

The fields msg_iov and msg_iovlen describe scatter-gather locations, as discussed in readv(2).

The field msg_control, which has size msg_controllen, points to a buffer for other protocol control-related messages or miscellaneous ancillary data. When recvmsg() is called, msg_controllen should contain the size of the available buffer in msg_control; upon return from a successful call it will contain the size of the control message sequence.

The messages are of the form:


struct cmsghdr {
    size_t cmsg_len;    /* Data byte count, including header
                           (type is socklen_t in POSIX) */
    int    cmsg_level;  /* Originating protocol */
    int    cmsg_type;   /* Protocol-specific type */
/* followed by
    unsigned char cmsg_data[]; */
};

Ancillary data should be accessed only by the macros defined in cmsg(3).

As an example, Linux uses this ancillary data mechanism to pass extended errors, IP options, or file descriptors over UNIX domain sockets. For further information on the use of ancillary data in various socket domains, see unix(7) and ip(7).

The msg_flags field in the msghdr is set on return of recvmsg(). It can contain several flags:

MSG_EOR
indicates end-of-record; the data returned completed a record (generally, used with sockets of type SOCK_SEQPACKET).
MSG_TRUNC
indicates that the trailing portion of a datagram was discarded because the datagram was larger than the buffer supplied.
MSG_CTRUNC
indicates that some control data was discarded due to lack of space in the buffer for ancillary data.
MSG_OOB
is returned to indicate that expedited or out-of-band data was received.
MSG_ERRQUEUE
indicates that no data was received but an extended error from the socket error queue.
MSG_CMSG_CLOEXEC (since Linux 2.6.23)
indicates that MSG_CMSG_CLOEXEC was specified in the flags argument of recvmsg().

RETURN VALUE

These calls return the number of bytes received, or -1 if an error occurred. In the event of an error, errno is set to indicate the error.

When a stream socket peer has performed an orderly shutdown, the return value will be 0 (the traditional "end-of-file" return).

Datagram sockets in various domains (e.g., the UNIX and Internet domains) permit zero-size datagrams. When such a datagram is received, the return value is 0.

The value 0 may also be returned if the requested number of bytes to receive from a stream socket was 0.

ERRORS

These are some standard errors generated by the socket layer. Additional errors may be generated and returned from the underlying protocol modules; see their manual pages.

EAGAIN or EWOULDBLOCK
The socket is marked nonblocking and the receive operation would block, or a receive timeout had been set and the timeout expired before data was received. POSIX.1 allows either error to be returned for this case, and does not require these constants to have the same value, so a portable application should check for both possibilities.
EBADF
The argument sockfd is an invalid file descriptor.
ECONNREFUSED
A remote host refused to allow the network connection (typically because it is not running the requested service).
EFAULT
The receive buffer pointer(s) point outside the process's address space.
EINTR
The receive was interrupted by delivery of a signal before any data was available; see signal(7).
EINVAL
Invalid argument passed.
ENOMEM
Could not allocate memory for recvmsg().
ENOTCONN
The socket is associated with a connection-oriented protocol and has not been connected (see connect(2) and accept(2)).
ENOTSOCK
The file descriptor sockfd does not refer to a socket.

VERSIONS

According to POSIX.1, the msg_controllen field of the msghdr structure should be typed as socklen_t, and the msg_iovlen field should be typed as int, but glibc currently types both as size_t.

STANDARDS

POSIX.1-2024.

HISTORY

POSIX.1-2001, 4.2BSD.

POSIX.1 describes only the MSG_OOB, MSG_PEEK, and MSG_WAITALL flags.

NOTES

If a zero-size datagram is pending, read(2) and recv() with a flags argument of zero provide different behavior. In this circumstance, read(2) has no effect (the datagram remains pending), while recv() consumes the pending datagram.

See recvmmsg(2) for information about a Linux-specific system call that can be used to receive multiple datagrams in a single call.
