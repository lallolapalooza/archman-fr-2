recv(2) Manuel des appels système recv(2)

NOM

recv, recvfrom, recvmsg - recevoir un message d'une socket

BIBLIOTHEQUE

Bibliothèque C standard (libc, -lc)

SYNTAXE

#include <sys/socket.h>
ssize_t recv(size_t size;
                 int sockfd, void buf[size], size_t size,
                 int flags);
ssize_t recvfrom(size_t size;
                 int sockfd, void buf[restrict size], size_t size,
                 int flags,
                 struct sockaddr *_Nullable restrict src_addr,
                 socklen_t *_Nullable restrict addrlen);
ssize_t recvmsg(int sockfd, struct msghdr *msg, int flags);

DESCRIPTION

Les appels recv(), recvfrom(), et recvmsg() sont utilisés pour recevoir des messages d'une socket. Ils peuvent être utilisés pour recevoir des données sur des sockets sans connexion et des sockets orientées connexion. Cette page décrit d'abord les caractéristiques communes aux trois appels système, puis les différences entre les appels.

La seule différence entre recv() et read(2) est la présence de flags. Avec un argument flags à zéro, recv() est généralement équivalent à read(2) (mais voir NOTES). De plus, l'appel suivant


recv(sockfd, buf, size, flags);

est équivalent à


recvfrom(sockfd, buf, size, flags, NULL, NULL);

Les trois appels retournent la taille du message en cas de succès. Si un message est trop long pour tenir dans le tampon fourni, les octets excédentaires peuvent être rejetés en fonction du type de socket à partir de laquelle le message est reçu.

Si aucun message n'est disponible sur la socket, les appels de réception attendent qu'un message arrive, à moins que la socket ne soit non bloquante (voir fcntl(2)), auquel cas la valeur -1 est retournée et errno est défini à EAGAIN ou EWOULDBLOCK. Les appels de réception retournent normalement toutes les données disponibles, jusqu'à la quantité demandée, plutôt que d'attendre la réception du montant complet demandé.

Une application peut utiliser select(2), poll(2), ou epoll(7) pour déterminer quand plus de données arrivent sur une socket.

L'argument flags

L'argument flags est formé en ORant une ou plusieurs des valeurs suivantes :

MSG_CMSG_CLOEXEC (seulement pour recvmsg() ; depuis Linux 2.6.23)
Définit le drapeau de fermeture à l'exécution pour le descripteur de fichier reçu via un descripteur de fichier de domaine UNIX à l'aide de l'opération SCM_RIGHTS (décrite dans unix(7)). Ce drapeau est utile pour les mêmes raisons que le drapeau O_CLOEXEC de open(2).
MSG_DONTWAIT (depuis Linux 2.2)
Active le fonctionnement non bloquant ; si l'opération bloquerait, l'appel échoue avec EAGAIN ou EWOULDBLOCK. Cela fournit un comportement similaire à la définition du drapeau O_NONBLOCK (via l'opération fcntl(2) F_SETFL), mais diffère en ce que MSG_DONTWAIT est une option par appel, tandis que O_NONBLOCK est un paramètre de la description de fichier ouverte (voir open(2)), qui affectera tous les threads du processus appelant ainsi que d'autres processus qui détiennent des descripteurs de fichiers faisant référence à la même description de fichier ouverte.
MSG_ERRQUEUE (depuis Linux 2.2)
Ce drapeau spécifie que les erreurs en file d'attente doivent être reçues depuis la file d'attente d'erreurs de la socket. L'erreur est transmise dans un message auxiliaire dont le type dépend du protocole (pour IPv4 IP_RECVERR). L'utilisateur doit fournir un tampon de taille suffisante. Voir cmsg(3) et ip(7) pour plus d'informations. La charge utile du paquet original qui a causé l'erreur est transmise comme données normales via msg_iovec. L'adresse de destination originale du datagramme qui a causé l'erreur est fournie via msg_name.
L'erreur est fournie dans une structure sock_extended_err :

#define SO_EE_ORIGIN_NONE    0
#define SO_EE_ORIGIN_LOCAL   1
#define SO_EE_ORIGIN_ICMP    2
#define SO_EE_ORIGIN_ICMP6   3
struct sock_extended_err
{
    uint32_t ee_errno;   /* Numéro d'erreur */
    uint8_t  ee_origin;  /* D'où vient l'erreur */
    uint8_t  ee_type;    /* Type */
    uint8_t  ee_code;    /* Code */
    uint8_t  ee_pad;     /* Bourrage */
    uint32_t ee_info;    /* Informations supplémentaires */
    uint32_t ee_data;    /* Autres données */
    /* Plus de données peuvent suivre */
};
struct sockaddr *SO_EE_OFFENDER(struct sock_extended_err *);

ee_errno contient le numéro errno de l'erreur en file d'attente. ee_origin est le code d'origine d'où l'erreur est survenue. Les autres champs sont spécifiques au protocole. La macro SO_EE_OFFENDER renvoie un pointeur vers l'adresse de l'objet réseau où l'erreur est survenue, étant donné un pointeur vers le message auxiliaire. Si cette adresse n'est pas connue, le membre sa_family du sockaddr contient AF_UNSPEC et les autres champs du sockaddr ne sont pas définis. La charge utile du paquet qui a causé l'erreur est transmise comme données normales.
Pour les erreurs locales, aucune adresse n'est transmise (cela peut être vérifié avec le membre cmsg_len du cmsghdr). Pour les réceptions d'erreurs, le drapeau MSG_ERRQUEUE est défini dans msghdr. Après qu'une erreur a été transmise, l'erreur de socket en attente est régénérée en fonction de la prochaine erreur en file d'attente et sera transmise lors de la prochaine opération sur la socket.
MSG_OOB
Ce drapeau demande la réception de données hors bande qui ne seraient pas reçues dans le flux de données normal. Certains protocoles placent les données urgentes en tête de la file d'attente de données normales, et donc ce drapeau ne peut pas être utilisé avec de tels protocoles.
MSG_PEEK
Ce drapeau fait que l'opération de réception retourne les données depuis le début de la file d'attente de réception sans supprimer ces données de la file d'attente. Ainsi, un appel de réception ultérieur retournera les mêmes données.
MSG_TRUNC (depuis Linux 2.2)
Pour les sockets brutes (AF_PACKET), les datagrammes Internet (depuis Linux 2.4.27/2.6.8), netlink (depuis Linux 2.6.22) et les datagrammes UNIX ainsi que les séquences de paquets (depuis Linux 3.4) : retourner la taille réelle du paquet ou du datagramme, même lorsqu'il était plus long que le tampon fourni.
Pour une utilisation avec les sockets de flux Internet, voir tcp(7).
MSG_WAITALL (depuis Linux 2.2)
Ce drapeau demande que l'opération bloque jusqu'à ce que la demande complète soit satisfaite. Cependant, l'appel peut toujours retourner moins de données que demandé si un signal est intercepté, une erreur ou une déconnexion se produit, ou si les prochaines données à recevoir sont d'un type différent de celles retournées. Ce drapeau n'a aucun effet pour les sockets de datagrammes.

recvfrom()

recvfrom() place le message reçu dans le tampon buf. L'appelant doit spécifier la taille du tampon dans size.

Si src_addr n'est pas NULL, et que le protocole sous-jacent fournit l'adresse source du message, cette adresse source est placée dans le tampon pointé par src_addr. Dans ce cas, addrlen est un argument valeur-résultat. Avant l'appel, il doit être initialisé à la taille du tampon associé à src_addr. Au retour, addrlen est mis à jour pour contenir la taille réelle de l'adresse source. L'adresse retournée est tronquée si le tampon fourni est trop petit ; dans ce cas, addrlen retournera une valeur supérieure à celle fournie lors de l'appel.

NOM

recvfrom, recv, recvmsg - recevoir des données sur un socket

BIBLIOTHQUE

Bibliothèque de sockets C,
avec libc.so.6

SYNTAXE

#include <sys/types.h>
#include <sys/socket.h>

ssize_t recvfrom(int sockfd, void *buf, size_t len, int flags,
                 struct sockaddr *src_addr, socklen_t *addrlen);

ssize_t recv(int sockfd, void *buf, size_t len, int flags);

ssize_t recvmsg(int sockfd, struct msghdr *msg, int flags);

DESCRIPTION

Les appels système recvfrom(), recv() et recvmsg() sont utilisés pour recevoir des données d'un socket. Le descripteur de fichier spécifié par sockfd doit être connecté à un socket ou, pour recvfrom(), il peut être non connecté.

buf pointe vers un buffer où les données reçues seront stockées. len spécifie la taille maximale de ce buffer.

Les flags affectent le comportement de la lecture du socket. Les valeurs possibles pour flags sont la somme (OU binaire) des drapeaux suivants :

MSG_PEEK
Regarde les données entrantes sans les retirer de la file d'attente de réception. Une fois qu'une donnée a été lue avec MSG_PEEK, elle restera disponible pour une lecture ultérieure.
MSG_DONTWAIT
Ouvre le socket en mode non bloquant, même s'il est ouvert en mode bloquant. Ceci est équivalent à définir l'indicateur O_NONBLOCK sur le descripteur de fichier du socket.
MSG_WAITALL (depuis Linux 2.4)
Continue à lire jusqu'à ce que tous les len octets aient été reçus ou que la connexion soit terminée. Si cette option est spécifiée, recv() et recvfrom() bloqueront jusqu'à ce que la quantité de données demandée soit reçue. L'appel système peut retourner une valeur inférieure à len uniquement si un signal a interrompu la lecture (voir signal(7)) ou si une erreur se produit. Les autres drapeaux MSG_* ne sont pas autorisés avec MSG_WAITALL.

recvfrom()

L'appel recvfrom() lit des données d'un socket et stocke l'adresse de la source dans la structure src_addr. addrlen est un pointeur vers la taille du buffer d'adresse fourni par l'appelant. Au retour de l'appel, addrlen contiendra la taille réelle de l'adresse source. Si l'appelant n'a pas besoin de connaître l'adresse source, src_addr et addrlen doivent être spécifiés comme NULL.

Pour les sockets de type SOCK_DGRAM et SOCK_RAW, les données sont envoyées en datagrammes. Les datagrammes sont délivrés dans leur intégralité, et un appel recvfrom() ne recevra qu'un seul datagramme. Si le datagramme est plus grand que la taille du buffer len, il sera tronqué, et l'indicateur MSG_TRUNC sera défini dans le champ flags au retour de recvmsg() (voir ci-dessous). Si la taille du datagramme est de zéro octet, 0 sera retourné.

Si le socket est de type SOCK_STREAM, recvfrom() est équivalent à recv() avec les arguments src_addr et addrlen spécifiés comme NULL.

Pour les sockets de type SOCK_RAW, l'en-tête du protocole est également inclus dans le buffer de réception. Si le socket n'est pas lié à un protocole spécifique (c'est-à-dire sockfd est lié à un protocole générique tel que IP), le champ msg_name de la structure msghdr doit être utilisé pour spécifier le protocole de la réponse.

Pour les sockets AF_PACKET, le paquet complet reçu est placé dans buf. Si le socket n'est pas lié à un protocole spécifique (par exemple, sockfd est lié à ETH_P_ALL), alors l'en-tête de liaison de données (par exemple, l'en-tête Ethernet) est également inclus.

Le champ flags dans la structure msghdr, s'il est fourni et non NULL, peut être utilisé pour spécifier les mêmes drapeaux que ceux décrits pour recv() et recvfrom(). Le champ flags sera également mis à jour lors du retour, pour inclure les drapeaux décrits ci-dessous.

Si le socket n'est pas intéressé par l'adresse source, src_addr et addrlen doivent être spécifiés comme NULL.

recv()

L'appel recv() est normalement utilisé uniquement sur un socket connecté (voir connect(2)). Il est équivalent à l'appel :


recvfrom(fd, buf, size, flags, NULL, NULL);

recvmsg()

L'appel recvmsg() utilise une structure msghdr pour minimiser le nombre d'arguments directement fournis. Cette structure est définie comme suit dans <sys/socket.h> :


struct msghdr {
    void         *msg_name;       /* Adresse optionnelle */
    socklen_t     msg_namelen;    /* Taille de l'adresse */
    struct iovec *msg_iov;        /* Tableau scatter/gather */
    size_t        msg_iovlen;     /* Nombre d'éléments dans msg_iov */
    void         *msg_control;    /* Données auxiliaires, voir ci-dessous */
    size_t        msg_controllen; /* Taille du buffer de données auxiliaires */
    int           msg_flags;      /* Indicateurs sur le message reçu */
};

Le champ msg_name pointe vers un buffer alloué par l'appelant qui est utilisé pour retourner l'adresse source si le socket est non connecté. L'appelant doit définir msg_namelen à la taille de ce buffer avant cet appel ; au retour d'un appel réussi, msg_namelen contiendra la taille de l'adresse retournée. Si l'application n'a pas besoin de connaître l'adresse source, msg_name peut être spécifié comme NULL.

Les champs msg_iov et msg_iovlen décrivent des emplacements scatter-gather, comme discuté dans readv(2).

Le champ msg_control, dont la taille est msg_controllen, pointe vers un buffer pour d'autres messages liés au contrôle du protocole ou des données auxiliaires diverses. Lorsque recvmsg() est appelé, msg_controllen doit contenir la taille du buffer disponible dans msg_control ; au retour d'un appel réussi, il contiendra la taille de la séquence de messages de contrôle.

Les messages sont de la forme :


struct cmsghdr {
    size_t cmsg_len;    /* Nombre d'octets de données, incluant l'en-tête
                           (le type est socklen_t en POSIX) */
    int    cmsg_level;  /* Protocole d'origine */
    int    cmsg_type;   /* Type spécifique au protocole */
/* suivi par
    unsigned char cmsg_data[]; */
};

Les données auxiliaires ne doivent être accédées que par les macros définies dans cmsg(3).

Par exemple, Linux utilise ce mécanisme de données auxiliaires pour transmettre des erreurs étendues, des options IP ou des descripteurs de fichier sur des sockets de domaine UNIX. Pour plus d'informations sur l'utilisation des données auxiliaires dans divers domaines de sockets, voir unix(7) et ip(7).

Le champ msg_flags dans msghdr est défini au retour de recvmsg(). Il peut contenir plusieurs drapeaux :

MSG_EOR
indique la fin d'enregistrement ; les données reçues ont complété un enregistrement (généralement utilisé avec les sockets de type SOCK_SEQPACKET).
MSG_TRUNC
indique que la partie finale d'un datagramme a été écartée car le datagramme était plus grand que le buffer fourni.
MSG_CTRUNC
indique que certaines données de contrôle ont été écartées faute de place dans le buffer pour les données auxiliaires.
MSG_OOB
est retourné pour indiquer que des données urgentes ou hors bande ont été reçues.
MSG_ERRQUEUE
indique qu'aucune donnée n'a été reçue mais qu'une erreur étendue provient de la file d'attente d'erreurs du socket.
MSG_CMSG_CLOEXEC (depuis Linux 2.6.23)
indique que MSG_CMSG_CLOEXEC a été spécifié dans l'argument flags de recvmsg().

VALEUR DE RETOUR

Ces appels retournent le nombre d'octets reçus, ou -1 si une erreur s'est produite. En cas d'erreur, errno est défini pour indiquer l'erreur.

Lorsqu'un pair de socket de flux a effectué un arrêt ordonné, la valeur de retour sera 0 (le retour traditionnel de « fin de fichier »).

Les sockets de datagrammes dans divers domaines (par exemple, les domaines UNIX et Internet) autorisent les datagrammes de taille zéro. Lors de la réception d'un tel datagramme, la valeur de retour est 0.

La valeur 0 peut également être retournée si le nombre d'octets demandés à recevoir d'un socket de flux était de 0.

ERREURS

Voici quelques erreurs standard générées par la couche de socket. Des erreurs supplémentaires peuvent être générées et retournées par les modules de protocole sous-jacents ; voir leurs pages man.

EAGAIN ou EWOULDBLOCK
Le socket est marqué comme non bloquant et l'opération de réception bloquerait, ou un délai d'attente de réception a été défini et le délai a expiré avant que des données ne soient reçues. POSIX.1 autorise l'une ou l'autre de ces erreurs pour ce cas, et n'exige pas que ces constantes aient la même valeur, donc une application portable devrait vérifier les deux possibilités.
EBADF
L'argument sockfd est un descripteur de fichier invalide.
ECONNREFUSED
Un hôte distant a refusé l'autorisation de la connexion réseau (typiquement parce qu'il n'exécute pas le service demandé).
EFAULT
Les pointeurs du buffer de réception pointent en dehors de l'espace d'adressage du processus.
EINTR
La réception a été interrompue par la livraison d'un signal avant que des données ne soient disponibles ; voir signal(7).
EINVAL
Argument invalide passé.
ENOMEM
Impossible d'allouer de la mémoire pour recvmsg().
ENOTCONN
Le socket est associé à un protocole orienté connexion et n'a pas été connecté (voir connect(2) et accept(2)).
ENOTSOCK
Le descripteur de fichier sockfd ne fait pas référence à un socket.

VERSIONS

Selon POSIX.1, le champ msg_controllen de la structure msghdr doit être typé comme socklen_t, et le champ msg_iovlen doit être typé comme int, mais glibc le typé actuellement comme size_t.

NORMES

POSIX.1-2024.

HISTORIQUE

POSIX.1-2001, 4.2BSD.

POSIX.1 ne décrit que les drapeaux MSG_OOB, MSG_PEEK et MSG_WAITALL.

NOTES

Si un datagramme de taille zéro est en attente, read(2) et recv() avec un argument flags de zéro fournissent un comportement différent. Dans ce cas, read(2) n'a aucun effet (le datagramme reste en attente), tandis que recv() consomme le datagramme en attente.

Voir recvmmsg(2) pour des informations sur un appel système spécifique à Linux qui peut être utilisé pour recevoir plusieurs datagrammes en un seul appel.

EXEMPLES

Un exemple d'utilisation de recvfrom() est montré dans getaddrinfo(3).
