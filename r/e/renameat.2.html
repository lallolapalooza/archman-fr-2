rename(2) Manuel des appels système rename(2)

NOM

rename, renameat, renameat2 - changer le nom ou l'emplacement d'un fichier

BIBLIOTHEQUE

Bibliothèque C standard (libc, -lc)

SYNTAXE

#include <stdio.h>
int rename(const char *oldpath, const char *newpath);
#include <fcntl.h>           /* Définition des constantes AT_* */
#include <stdio.h>
int renameat(int olddirfd, const char *oldpath,
             int newdirfd, const char *newpath);
int renameat2(int olddirfd, const char *oldpath,
             int newdirfd, const char *newpath, unsigned int flags);
Exigences pour les macros de test de fonctionnalités sur glibc (voir feature_test_macros(7)):
renameat():
    Depuis glibc 2.10 :
        _POSIX_C_SOURCE >= 200809L
    Avant glibc 2.10 :
        _ATFILE_SOURCE
renameat2():
    _GNU_SOURCE

DESCRIPTION

rename() renomme un fichier, le déplaçant entre répertoires si nécessaire. Tous les autres liens physiques vers le fichier (tels que créés avec link(2)) ne sont pas affectés. Les descripteurs de fichiers ouverts pour oldpath ne sont pas non plus affectés.

Diverses restrictions déterminent si l'opération de renommage réussit ou non : voir ERREURS ci-dessous.

Si newpath existe déjà, il sera remplacé de manière atomique, de sorte qu'il n'y aura aucun point où un autre processus tentant d'accéder à newpath le trouvera manquant. Cependant, il y aura probablement une fenêtre pendant laquelle oldpath et newpath Pointeront vers le fichier en cours de renommage.

Si oldpath et newpath sont des liens physiques existants pointant vers le même fichier, alors rename() ne fait rien et retourne un statut de succès.

Si newpath existe mais que l'opération échoue pour une raison quelconque, rename() garantit de laisser une instance de newpath en place.

oldpath peut spécifier un répertoire. Dans ce cas, newpath doit soit ne pas exister, soit spécifier un répertoire vide.

Si oldpath pointe vers un lien symbolique, le lien est renommé ; si newpath pointe vers un lien symbolique, le lien sera écrasé.

renameat()

L'appel système renameat() fonctionne exactement de la même manière que rename(), à l'exception des différences décrites ici.

Si le chemin donné dans oldpath est relatif, il est interprété par rapport au répertoire référencé par le descripteur de fichier olddirfd (plutôt que par rapport au répertoire de travail courant du processus appelant, comme le fait rename() pour un chemin relatif).

Si oldpath est relatif et olddirfd est la valeur spéciale AT_FDCWD, alors oldpath est interprété par rapport au répertoire de travail courant du processus appelant (comme rename()).

Si oldpath est absolu, alors olddirfd est ignoré.

L'interprétation de newpath est la même que pour oldpath, sauf qu'un chemin relatif est interprété par rapport au répertoire référencé par le descripteur de fichier newdirfd.

Voir openat(2) pour une explication de la nécessité de renameat().

renameat2()

renameat2() a un argument supplémentaire flags. Un appel à renameat2() avec un argument flags égal à zéro est équivalent à renameat().

L'argument flags est un masque de bits composé de zéro ou plusieurs des indicateurs suivants :

RENAME_EXCHANGE
Échange oldpath et newpath de manière atomique. Les deux chemins doivent exister mais peuvent être de types différents (par exemple, l'un pourrait être un répertoire non vide et l'autre un lien symbolique).
RENAME_NOREPLACE
Ne pas écraser newpath lors du renommage. Retourner une erreur si newpath existe déjà.
RENAME_NOREPLACE ne peut pas être utilisé conjointement avec RENAME_EXCHANGE.
RENAME_NOREPLACE nécessite la prise en charge du système de fichiers sous-jacent. La prise en charge de divers systèmes de fichiers a été ajoutée comme suit :
•
ext4 (Linux 3.15) ;
•
btrfs, tmpfs et cifs (Linux 3.17) ;
•
xfs (Linux 4.0) ;
•
La prise en charge de nombreux autres systèmes de fichiers a été ajoutée dans Linux 4.9, y compris ext2, minix, reiserfs, jfs, vfat et bpf.
RENAME_WHITEOUT (depuis Linux 3.18)
Cette opération n'a de sens que pour les implémentations de systèmes de fichiers overlay/union.
Spécifier RENAME_WHITEOUT crée un objet "whiteout" à la source du renommage en même temps que l'exécution du renommage. Toute l'opération est atomique, de sorte que si le renommage réussit, le whiteout aura également été créé.
Un "whiteout" est un objet qui a une signification particulière dans les constructions de systèmes de fichiers union/overlay. Dans ces constructions, plusieurs couches existent et seule la supérieure est jamais modifiée. Un whiteout dans une couche supérieure masquera efficacement un fichier correspondant dans la couche inférieure, donnant l'impression que le fichier n'existe pas.
Lorsqu'un fichier qui existe dans la couche inférieure est renommé, le fichier est d'abord copié (s'il n'est pas déjà dans la couche supérieure), puis renommé dans la couche supérieure en lecture-écriture. En même temps, le fichier source doit être "whiteouté" (de sorte que la version du fichier source dans la couche inférieure soit rendue invisible).
Lorsqu'il ne fait pas partie d'une union/overlay, le whiteout apparaît comme un périphérique de caractères avec un numéro de périphérique {0,0}. (Notez que d'autres implémentations d'union/overlay peuvent utiliser des méthodes différentes pour stocker les entrées de whiteout ; en particulier, le montage union de BSD utilise un type d'inode distinct, DT_WHT, qui, bien que pris en charge par certains systèmes de fichiers disponibles sous Linux, tels que CODA et XFS, est ignoré par le code de prise en charge des whiteouts du noyau, depuis Linux 4.19, au moins.)
RENAME_WHITEOUT nécessite les mêmes privilèges que la création d'un nœud de périphérique (c'est-à-dire la capacité CAP_MKNOD).
RENAME_WHITEOUT ne peut pas être utilisé conjointement avec RENAME_EXCHANGE.
RENAME_WHITEOUT nécessite la prise en charge du système de fichiers sous-jacent. Parmi les systèmes de fichiers qui le prennent en charge figurent tmpfs (depuis Linux 3.18), ext4 (depuis Linux 3.18), XFS (depuis Linux 4.1), f2fs (depuis Linux 4.2), btrfs (depuis Linux 4.7) et ubifs (depuis Linux 4.9).

VALEUR DE RETOUR

En cas de succès, zéro est retourné. En cas d'erreur, -1 est retourné et errno est défini pour indiquer l'erreur.

ERREURS

EACCES
L'autorisation d'écriture est refusée pour le répertoire contenant oldpath ou newpath, ou l'autorisation de recherche est refusée pour l'un des répertoires du préfixe de chemin de oldpath ou newpath, ou oldpath est un répertoire qui n'autorise pas l'écriture (nécessaire pour mettre à jour l'entrée ..). (Voir aussi path_resolution(7).)
EBUSY
Le renommage échoue car oldpath ou newpath est un répertoire utilisé par un processus (peut-être comme répertoire courant, ou comme répertoire racine, ou parce qu'il était ouvert en lecture) ou est utilisé par le système (par exemple comme point de montage), alors que le système considère cela comme une erreur. (Notez qu'il n'y a aucune obligation de retourner EBUSY dans de tels cas — il n'y a rien de mal à effectuer le renommage de toute façon — mais il est autorisé à retourner EBUSY si le système ne peut pas gérer de telles situations autrement.)
EDQUOT
La quota de disque a été dépassé lors de la tentative de création de newpath.
EEXIST
newpath existe déjà et l'opération n'a pas été autorisée (par exemple, à cause de l'indicateur RENAME_NOREPLACE).
EFBIG
Le fichier résultant serait plus grand que la limite maximale autorisée par le système.
EINVAL
Les noms de chemin sont invalides, ou bien les indicateurs fournis à renameat2() ne sont pas valides.
EISDIR
Soit oldpath est un répertoire et newpath n'est pas vide (et n'est pas un répertoire vide aussi) ; soit newpath est un répertoire et oldpath n'est pas un répertoire vide (et n'est pas un répertoire aussi).
ELOOP
Un trop grand nombre de liens symboliques ont été rencontrés lors de la résolution de oldpath ou newpath.
EMLINK
Trop de liens physiques existent pour le fichier.
EMLINK
Trop de liens physiques existent pour le fichier.
ENAMETOOLONG
La longueur d'un composant de chemin, ou le chemin entier, dépasse la limite du système.
ENOENT
Un composant de chemin de oldpath ou newpath n'existe pas, ou oldpath est vide.
ENOSPC
Aucun espace n'est disponible sur le périphérique pour écrire le fichier. Cela peut se produire même si la taille du fichier est réduite, car il faut parfois faire une copie pour effectuer le renommage.
ENOTDIR
Un composant de chemin de oldpath ou newpath n'est pas un répertoire, ou oldpath est un répertoire et newpath est un lien symbolique vers un répertoire.
ENOTEMPTY
newpath est un répertoire qui n'est pas vide.
EROFS
Le fichier est sur un système de fichiers en lecture seule.
ETXTBUSY
Le fichier est un exécutable ouvert qui est utilisé par le système.
EXDEV
oldpath et newpath sont sur des systèmes de fichiers différents.

Pour renameat2() :

EINVAL
Les indicateurs fournis dans flags ne sont pas valides.
EINVAL
L'utilisation de RENAME_EXCHANGE et RENAME_NOREPLACE ensemble.
EINVAL
L'utilisation de RENAME_WHITEOUT et RENAME_EXCHANGE ensemble.
EPERM
L'utilisation de RENAME_WHITEOUT nécessite les privilèges de création de nœuds de périphérique (c'est-à-dire la capacité CAP_MKNOD).

CONFORMITÉ

rename() : POSIX.1-2008, SVr4, 4.3BSD.

renameat() : POSIX.1-2008.

renameat2() : GNU.

renameat(2) — Linux manual pages

NAME

rename, renameat, renameat2 — changer le nom ou l'emplacement d'un fichier

LIBRARY

Standard C library (libc)

SYNOPSIS

#include <sys/types.h>
#include <unistd.h>

int rename(const char *oldpath, const char *newpath);
int renameat(int olddirfd, const char *oldpath, int newdirfd, const char *newpath);

#if __GLIBC__ >= 2 && __GLIBC_MINOR__ >= 28
#define _GNU_SOURCE
#include <fcntl.h>

int renameat2(int olddirfd, const char *oldpath, int newdirfd, const char *newpath, unsigned int flags);
#endif

DESCRIPTION

The rename() system call renames a file or directory. If newpath exists and is a file, it will be replaced subject to conditions described below. If newpath exists and is a directory, the function fails with error EEXIST. The oldpath and newpath arguments can specify different directories. If the source and destination are on different filesystems, the operation fails with error EXDEV.

The renameat() system call is equivalent to rename() except that it can operate on relative paths with respect to directory file descriptors. The olddirfd and newdirfd arguments specify directories with respect to which a relative path in oldpath or newpath is interpreted. If oldpath (or newpath*) is an absolute path, then olddirfd (or newdirfd*) must refer to a valid directory; if it is a relative path, then olddirfd (or newdirfd*) specifies a directory relative to which the path is interpreted.

If oldpath is relative and olddirfd is "`AT_FDCWD`" (defined in fcntl.h), then oldpath is interpreted relative to the current working directory.

If newpath is relative and newdirfd is "`AT_FDCWD`", then newpath is interpreted relative to the current working directory.

The renameat2() system call is a further extension to renameat() that supports additional atomic operations via the flags argument.

The following flags can be specified in flags:

RENAME_NOREPLACE
Do not replace an existing file. If newpath exists, EEXIST is returned, even if it is a normal file. This flag is intended to be used for atomic renames of files where the source is a temporary file and the destination is the final name, ensuring that the destination is created atomically. This flag is a Linux-specific extension.
RENAME_EXCHANGE
Atomically exchange the existence of the two files, oldpath and newpath. Both oldpath and newpath must exist. If they exist, their names are swapped. This flag is useful for atomically replacing a file by another one, where the replaced file needs to be kept. This flag is a Linux-specific extension.
RENAME_WHITEOUT
Create a whiteout. This flag is intended for use with union filesystems. Creating a whiteout effectively deletes a file in a lower filesystem layer, making it invisible to the upper layer. This is achieved by creating a special file. Use of this flag requires the caller to have the CAP_MKNOD capability. This flag is a Linux-specific extension.

The olddirfd and newdirfd arguments are file descriptors. Each file descriptor refers to a directory. If the path is relative, it is interpreted relative to the directory referred to by the file descriptor. If the path is absolute, the file descriptor is ignored. If the file descriptor is the special value AT_FDCWD, the path is interpreted relative to the current working directory.

The following flags can be specified in flags for renameat2():

RENAME_NOREPLACE
Do not replace an existing file. If newpath exists, EEXIST is returned, even if it is a normal file. This flag is intended to be used for atomic renames of files where the source is a temporary file and the destination is the final name, ensuring that the destination is created atomically. This flag is a Linux-specific extension.
RENAME_EXCHANGE
Atomically exchange the existence of the two files, oldpath and newpath. Both oldpath and newpath must exist. If they exist, their names are swapped. This flag is useful for atomically replacing a file by another one, where the replaced file needs to be kept. This flag is a Linux-specific extension.
RENAME_WHITEOUT
Create a whiteout. This flag is intended for use with union filesystems. Creating a whiteout effectively deletes a file in a lower filesystem layer, making it invisible to the upper layer. This is achieved by creating a special file. Use of this flag requires the caller to have the CAP_MKNOD capability. This flag is a Linux-specific extension.

RETURN VALUE

On success, rename(), renameat(), and renameat2() return 0. On error, they return -1, and errno is set to indicate the error.

ERRORS

EACCES
Search permission denied for one of the directories in the path prefix of oldpath or newpath. Or, write access permission denied for the directory containing oldpath or newpath. Or, the directory containing oldpath or newpath has the sticky bit set, and the process is not the owner of the file being renamed or of the directory, and the process is not privileged (Linux: does not have the CAP_FOWNER capability).
EBUSY
One of the filesystems containing oldpath or newpath is busy (e.g. it is the target of a mounted filesystem).
EDQUOT
Le quota d'espace disque de l'utilisateur sur le système de fichiers est épuisé.
EEXIST
newpath existe déjà et ce n'est pas un fichier normal, ou le fichier nommé par newpath est un répertoire non vide.
EFAULT
oldpath ou newpath pointe en dehors de votre espace d'adressage accessible.
EINVAL
Le nouveau chemin contenait un préfixe de chemin de l'ancien, ou, plus généralement, une tentative a été faite de faire d'un répertoire un sous-répertoire de lui-même.
EISDIR
newpath est un répertoire existant, mais oldpath n'est pas un répertoire.
ELOOP
Trop de liens symboliques ont été rencontrés lors de la résolution de oldpath ou newpath.
EMLINK
oldpath a déjà le nombre maximum de liens vers lui, ou c'était un répertoire et le répertoire contenant newpath a le nombre maximum de liens.
ENAMETOOLONG
oldpath ou newpath était trop long.
ENOENT
Le lien nommé par oldpath n'existe pas ; ou, un composant de répertoire dans newpath n'existe pas ; ou, oldpath ou newpath est une chaîne vide.
ENOMEM
Mémoire noyau insuffisante était disponible.
ENOSPC
Le périphérique contenant le fichier n'a pas de place pour la nouvelle entrée de répertoire.
ENOTDIR
Un composant utilisé comme répertoire dans oldpath ou newpath n'est pas, en fait, un répertoire. Ou, oldpath est un répertoire, et newpath existe mais n'est pas un répertoire.
ENOTEMPTY ou EEXIST
newpath est un répertoire non vide, c'est-à-dire qu'il contient des entrées autres que "." et "..".
EPERM ou EACCES
Le répertoire contenant oldpath a le bit collant (S_ISVTX) défini et l'ID utilisateur effectif du processus n'est ni l'ID utilisateur du fichier à supprimer ni celui du répertoire qui le contient, et le processus n'est pas privilégié (Linux : n'a pas la capacité CAP_FOWNER) ; ou newpath est un fichier existant et le répertoire qui le contient a le bit collant défini et l'ID utilisateur effectif du processus n'est ni l'ID utilisateur du fichier à remplacer ni celui du répertoire qui le contient, et le processus n'est pas privilégié (Linux : n'a pas la capacité CAP_FOWNER) ; ou le système de fichiers contenant oldpath ne prend pas en charge le renommage du type demandé.
EROFS
Le fichier se trouve sur un système de fichiers en lecture seule.
EXDEV
oldpath et newpath ne sont pas sur le même système de fichiers monté. (Linux permet qu'un système de fichiers soit monté en plusieurs points, mais rename() ne fonctionne pas entre différents points de montage, même si le même système de fichiers est monté sur les deux.)

Les erreurs supplémentaires suivantes peuvent survenir pour renameat() et renameat2():

EBADF
oldpath (newpath) est relatif mais olddirfd (newdirfd) n'est pas un descripteur de fichier valide.
ENOTDIR
oldpath est relatif et olddirfd est un descripteur de fichier faisant référence à un fichier autre qu'un répertoire ; ou similaire pour newpath et newdirfd

Les erreurs supplémentaires suivantes peuvent survenir pour renameat2():

EEXIST
flags contient RENAME_NOREPLACE et newpath existe déjà.
EINVAL
Un indicateur invalide a été spécifié dans flags.
EINVAL
RENAME_NOREPLACE et RENAME_EXCHANGE ont été spécifiés dans flags.
EINVAL
RENAME_WHITEOUT et RENAME_EXCHANGE ont été spécifiés dans flags.
EINVAL
Le système de fichiers ne prend pas en charge l'un des indicateurs dans flags.
ENOENT
flags contient RENAME_EXCHANGE et newpath n'existe pas.
EPERM
RENAME_WHITEOUT a été spécifié dans flags, mais l'appelant n'a pas la capacité CAP_MKNOD.

glibc notes

Sur les anciens noyaux où renameat() n'est pas disponible, la fonction wrapper glibc se rabat sur l'utilisation de rename(). Lorsque oldpath et newpath sont des chemins relatifs, glibc construit des chemins basés sur les liens symboliques dans /proc/self/fd qui correspondent aux arguments olddirfd et newdirfd.

BUGS

Sur les systèmes de fichiers NFS, vous ne pouvez pas supposer que si l'opération a échoué, le fichier n'a pas été renommé. Si le serveur effectue l'opération de renommage puis plante, la RPC retransmise qui sera traitée lorsque le serveur sera de nouveau opérationnel provoquera un échec. L'application est censée gérer cela. Voir link(2) pour un problème similaire.
