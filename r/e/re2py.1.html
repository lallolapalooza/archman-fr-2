NOM

re2py - génère des analyseurs lexicaux rapides pour Python

SYNTAXE

re2py [ OPTIONS ] [ AVERTISSEMENTS ] ENTRÉE

L'entrée peut être soit un fichier, soit - pour l'entrée standard.

INTRODUCTION

re2py fonctionne comme un préprocesseur. Il lit le fichier d'entrée (qui est généralement un programme en Python, mais peut être n'importe quoi) et recherche des blocs de code entourés de marqueurs de début/fin de forme spéciale. Le texte en dehors de ces blocs est copié tel quel dans le fichier de sortie. Le contenu des blocs est traité par re2py. Il les traduit en code Python et génère le code résultant à la place du bloc.

Voici un exemple d'un petit programme qui vérifie si une chaîne donnée contient un nombre décimal :

# re2py $INPUT -o $OUTPUT
def lex(yyinput):
    yycursor = 0
%{
    re2c:yyfill:enable = 0;
    re2c:indent:top = 1;
    [1-9][0-9]* { return True }
    *           { return False }
%}
assert lex(b"1234\0")

Dans la sortie, re2py a remplacé le bloc du milieu par le code généré :

# Généré par re2py
# re2py $INPUT -o $OUTPUT
def lex(yyinput):
    yycursor = 0
    yystate = 0
    while True:
        match yystate:
            case 0:
                yych = yyinput[yycursor]
                yycursor += 1
                if yych <= 0x30:
                    yystate = 1
                    continue
                if yych <= 0x39:
                    yystate = 2
                    continue
                yystate = 1
                continue
            case 1:
                return False
            case 2:
                yych = yyinput[yycursor]
                if yych <= 0x2F:
                    yystate = 3
                    continue
                if yych <= 0x39:
                    yycursor += 1
                    yystate = 2
                    continue
                yystate = 3
                continue
            case 3:
                return True
            case _:
                raise "erreur interne de l'analyseur lexical"
assert lex(b"1234\0")

BASES

Un programme re2py est constitué d'une séquence de blocs entremêlés avec du code dans le langage cible. Un bloc peut contenir des définitions, des configurations, des règles, des actions et des directives dans n'importe quel ordre :

nom = expression-régulière ;
Une définition associe nom à expression-régulière. Les noms peuvent contenir des caractères alphanumériques et des traits de soulignement. La section expressions régulières donne un aperçu de la syntaxe de re2py pour les expressions régulières. Une fois défini, le nom peut être utilisé dans d'autres expressions régulières et dans les règles. La récursion dans les définitions nommées n'est pas autorisée, et chaque nom doit être défini avant d'être utilisé. Un bloc hérite des définitions nommées du scope global. Redéfinir un nom existant dans le scope courant est une erreur.
configuration = valeur ;
Une configuration permet de modifier le comportement de re2py et de personnaliser le code généré. Pour une liste complète des configurations supportées par re2py, consultez la section configurations. Selon la configuration, valeur peut être un mot-clé, un nombre entier non-négatif ou une chaîne de caractères sur une seule ligne, qui doit être entourée de guillemets doubles ou simples, sauf si elle est composée de caractères alphanumériques. Un bloc hérite des configurations du scope global et peut les redéfinir ou en ajouter de nouvelles. Les configurations définies à l'intérieur d'un bloc affectent l'ensemble du bloc, même si elles apparaissent à la fin de celui-ci.
expression-régulière code
Une règle associe une expression-régulière à son action sémantique (un bloc de code entre accolades, ou un bloc de code commençant par := et se terminant à la fin de la ligne suivie de tout caractère non-blanc). Si l'expression-régulière correspond, le code associé est exécuté. Si plusieurs règles correspondent, la plus longue correspondance a priorité. Si plusieurs règles correspondent à la même chaîne, la première d'entre elles a priorité. Il existe deux règles spéciales : la règle par défaut * et la règle de fin d'entrée $. La règle par défaut doit toujours être définie ; elle a la plus basse priorité quel que soit son emplacement dans le bloc, et elle correspond à toute unité de code (pas nécessairement un caractère valide, voir la section prise en charge des encodages). La règle de fin d'entrée doit être définie si la méthode correspondante pour la gestion de la fin d'entrée est utilisée. Avec les conditions de départ, les règles ont une syntaxe plus complexe.
!action code
Une action associe un bloc de code défini par l'utilisateur à un endroit particulier dans la machine à états finis générée (de la même manière que les actions sémantiques associent du code aux états finaux). Voir la section actions pour une liste complète des actions prédéfinies.
!directive ;
Une directive est l'une des instructions prédéfinies spéciales. Chaque directive a un but unique. Voir la section directives pour les détails.

Blocs

Les marqueurs de début et de fin de bloc sont soit /*!re2c et */, soit %{ et %} (les deux styles sont supportés). À partir de la version 2.2, les blocs peuvent avoir des noms optionnels qui permettent de les référencer dans d'autres blocs. Il existe différents types de blocs :

/*!re2c[:<nom>] ... */ ou %{[:<nom>] ... %}
Un bloc global contient des définitions, des configurations, des règles et des directives. re2py compile les expressions régulières associées à chaque règle en un automate fini déterministe, l'encode sous forme de sauts conditionnels dans le langage cible et remplace le bloc par le code généré. Les noms et configurations définis dans un bloc global sont ajoutés au scope global et deviennent visibles pour les blocs suivants. Au début du programme, le scope global est initialisé avec les options de la ligne de commande.
/*!local:re2c[:<nom>] ... */ ou %{local[:<nom>] ... %}
Un bloc local est similaire à un bloc global, mais les noms et les configurations qu'il contient ont une portée locale (ils n'affectent pas les autres blocs).
/*!rules:re2c[:<nom>] ... */ ou %{rules[:<nom>] ... %}
Un bloc de règles est similaire à un bloc local, mais il ne génère aucun code en lui-même, ni n'ajoute de définitions au scope global – il est destiné à être réutilisé dans d'autres blocs. C'est une façon de partager du code (plus de détails dans la section blocs réutilisables). Avant la version 2.2 de re2py, les blocs de règles nécessitaient l'option -r --reusable.
/*!use:re2c[:<nom>] ... */ ou %{use[:<nom>] ... %}
Un bloc d'utilisation qui référence un bloc de règles défini précédemment. Si le nom est spécifié, re2py recherche les blocs de règles portant ce nom. Sinon, le bloc de règles le plus récent est utilisé (qu'il soit nommé ou sans nom). Un bloc d'utilisation peut ajouter ses propres définitions, configurations et règles, qui sont ajoutées à celles du bloc de règles référencé. Avant la version 2.2 de re2py, les blocs d'utilisation nécessitaient l'option -r --reusable.
/*!max:re2c[:<nom1>[:<nom2>...]] ... */ ou %{max[:<nom1>[:<nom2>...]] ... %}
Un bloc qui génère la définition YYMAXFILL. Une liste optionnelle de noms de blocs spécifie quels blocs doivent être inclus lors du calcul de la valeur de YYMAXFILL (si la liste est vide, tous les blocs sont inclus). Par défaut, le code généré est une macro-définition pour C (#define YYMAXFILL <n>), ou une variable globale pour Go (var YYMAXFILL int = <n>). Il peut être personnalisé avec une configuration optionnelle format qui spécifie une chaîne de modèle où @@{max} (ou @@ pour faire court) est remplacé par la valeur numérique de YYMAXFILL.
/*!maxnmatch:re2c[:<nom1>[:<nom2>...]] ... */ ou %{maxnmatch[:<nom1>[:<nom2>...]] ... %}
Un bloc qui génère la définition YYMAXNMATCH (nécessite l'option -P --posix-captures). Une liste optionnelle de noms de blocs spécifie quels blocs doivent être inclus lors du calcul de la valeur de YYMAXNMATCH (si la liste est vide, tous les blocs sont inclus). Blocs qui spécifient un morceau de code modèle qui est étendu pour chaque variable s-tag/m-tag générée par re2py. Une liste optionnelle de noms de blocs spécifie quels blocs doivent être inclus lors du calcul de l'ensemble des variables de tags (si la liste est vide, tous les blocs sont inclus). Il existe deux configurations optionnelles : format et separator. La configuration format spécifie une chaîne modèle où @@{tag} (ou @@ en abrégé) est remplacé par le nom de chaque variable de tag. /*!svars:re2c[:<name1>[:<name2>...]] ... */, /*!mvars:re2c[:<name1>[:<name2>...]] ... */ ou %{svars[:<name1>[:<name2>...]] ... %}, %{mvars[:<name1>[:<name2>...]] ... %{
Blocs qui spécifient un morceau de code modèle qui est étendu pour chaque s-tag/m-tag qui est soit explicitement mentionné par les règles (avec l'option --tags) soit implicitement généré par re2py (avec les options --captvars ou --posix-captvars). Une liste optionnelle de noms de blocs spécifie quels blocs doivent être inclus lors du calcul de l'ensemble des tags (si la liste est vide, tous les blocs sont inclus). La configuration separator spécifie un morceau de code utilisé pour joindre les morceaux format générés pour différents tags.
/*!getstate:re2c[:<name1>[:<name2>...]] ... */ ou %{getstate[:<name1>[:<name2>...]] ... %}
Un bloc qui génère une répartition conditionnelle sur l'état de l'analyseur lexical (il nécessite l'option --storable-state). Une liste optionnelle de noms de blocs spécifie quels blocs doivent être inclus dans la répartition d'état. La transition par défaut va au label de début du premier bloc de la liste. Si la liste est vide, tous les blocs sont inclus, et la transition par défaut va au premier bloc du fichier qui a un label de début. Ce type de bloc est incompatible avec l'option --loop-switch, car il nécessite des transitions inter-blocs qui ne sont pas prises en charge sans goto ou appels de fonction.
/*!conditions:re2c[:<name1>[:<name2>...]] ... */, /*!types:re2c... */ ou %{conditions[:<name1>[:<name2>...]] ... %}, %{types... %}
Un bloc qui génère une énumération de conditions (il nécessite l'option --conditions). Une liste optionnelle de noms de blocs spécifie quels blocs doivent être inclus lors du calcul de l'ensemble des conditions (si la liste est vide, tous les blocs sont inclus). Par défaut, le code généré est une énumération YYCONDTYPE. Il peut être personnalisé avec les configurations optionnelles format et separator. La configuration format spécifie une chaîne modèle où @@{cond} (ou @@ en abrégé) est remplacé par le nom de chaque condition, et @@{num} est remplacé par un index numérique de cette condition. La configuration separator spécifie un morceau de code utilisé pour joindre les morceaux format générés pour différentes conditions.
/*!include:re2c <file> */ ou %{include <file> %}
Ce bloc permet d'inclure <file>, qui doit être un chemin de fichier entre guillemets doubles. Le contenu du fichier est substitué littéralement à la place du bloc, de la même manière que fonctionne #include en C/C++. Ce bloc peut être utilisé conjointement avec l'option --depfile pour générer des dépendances de système de construction sur les fichiers inclus.
/*!header:re2c:on*/ ou %{header:on %}
Ce bloc marque le début du fichier d'en-tête. Tout ce qui suit et jusqu'au bloc header:off suivant est traité par re2py et écrit dans le fichier d'en-tête spécifié avec l'option -t --type-header.
/*!header:re2c:off*/ ou %{header:off %}
Ce bloc marque la fin du fichier d'en-tête commencé avec le bloc header:on*/.
/*!ignore:re2c ... */ ou %{ignore ... %}
Un bloc dont le contenu est ignoré et supprimé du fichier de sortie.

Configurations

Voici une liste complète des configurations prises en charge par re2py :

re2c:api, re2c:input
Identique à l'option --api.
re2c:api:sigil
Spécifie le marqueur ("sigil") utilisé pour les espaces réservés d'arguments dans les primitives d'API. La valeur par défaut est @@. Un espace réservé commence par le sigil suivi du nom de l'argument entre accolades. Par exemple, si le sigil est défini sur $, alors les espaces réservés auront la forme ${nom}. Les API à argument unique peuvent utiliser une notation abrégée sans le nom entre accolades. Cette option peut être remplacée par des options pour des primitives d'API individuelles, par exemple re2c:YYFILL@len pour YYFILL.
re2c:api:style
Spécifie le style de l'API. Les valeurs possibles sont functions (par défaut pour C) et free-form (par défaut pour Go et Rust). Dans le style functions, les primitives d'API sont générées avec une liste d'arguments entre parenthèses suivant le nom de la primitive. Les arguments ne sont fournis que pour les paramètres auto-générés (tels que le nombre de caractères passés à YYFILL), mais pas pour le contexte général de l'analyseur lexical, de sorte que les primitives se comportent davantage comme des macros en C/C++ ou des fermetures en Go et Rust. Dans le style free-form, les primitives d'API n'ont pas de forme fixe : elles doivent être définies comme des chaînes contenant des morceaux de code libres avec des variables interpolées de la forme @@{var} ou @@ (elles correspondent aux arguments dans le style de fonction). Cette configuration peut être remplacée pour des primitives d'API individuelles, voir par exemple la configuration re2c:YYFILL:naked pour YYFILL.

re2c:cond:divider
Définit le séparateur pour les blocs de conditions. La valeur par défaut est /* *********************************** */. Les espaces réservés sont substitués par le nom de la condition (voir re2c:api;sigil et re2c:cond:divider@cond).

re2c:cond:prefix, re2c:condprefix
Spécifie le préfixe utilisé pour les labels de condition. La valeur par défaut est yyc_.

Spécifie le préfixe utilisé pour les identificateurs de condition. La valeur par défaut est yyc.

Expressions régulières

re2py utilise la syntaxe suivante pour les expressions régulières :

«foo»
Littéral de chaîne sensible à la casse.
'foo'
Littéral de chaîne insensible à la casse.
[a-xyz], [^a-xyz]
Classe de caractères (éventuellement niée).
.
N'importe quel caractère sauf un retour à la ligne.
R \ S
Différence des classes de caractères R et S.
R*
Zéro occurrence ou plus de R.
R+
Une occurrence ou plus de R.
R?
R optionnel.
R{n}
Répétition de R exactement n fois.
R{n,}
Répétition de R au moins n fois.
R{n,m}
Répétition de R de n à m fois.
(R)
Juste R ; les parenthèses sont utilisées pour remplacer la priorité. Si l'extraction de sous-correspondance est activée, (R) est un groupe de capture ou un groupe sans capture selon l'option --invert-captures.
(!R)
Si l'extraction de sous-correspondance est activée, (!R) est un groupe sans capture ou un groupe de capture selon l'option --invert-captures.
R S
Concaténation : R suivi de S.
R | S
Alternative : R ou S.
R / S
Lookahead : R suivi de S, mais S n'est pas consommé.
name
Expression régulière définie comme name (ou chaîne littérale «name» en mode de compatibilité Flex).
{name}
Expression régulière définie comme name en mode de compatibilité Flex.
@stag
Un s-tag : enregistre la dernière position d'entrée où @stag correspond dans une variable nommée stag.
#mtag
Un m-tag : enregistre toutes les positions d'entrée où #mtag correspond dans une variable nommée mtag.

Les classes de caractères et les littéraux de chaîne peuvent contenir les séquences d'échappement suivantes : \a, \b, \f, \n, \r, \t, \v, \\, échappements octaux \ooo et échappements hexadécimaux \xhh, \uhhhh et \Uhhhhhhhh.

Actions

Voici une liste des actions prédéfinies prises en charge par re2py :

!entry code
L'action d'entrée associe un bloc de code défini par l'utilisateur à l'état de départ de la machine à états finis actuelle. Si des conditions de départ sont utilisées, l'action d'entrée peut être définie individuellement pour chaque condition. Cette action peut être utilisée pour effectuer une initialisation, par exemple pour enregistrer la position de départ d'un lexème.
!pre_rule code
L'action pré-règle ajoute un bloc de code défini par l'utilisateur au début des actions sémantiques de toutes les règles du bloc actuel (ou de la condition, si des conditions de départ sont utilisées). Cette action peut être utilisée pour factoriser la partie commune de toutes les actions sémantiques (par exemple, enregistrer la position de fin d'un lexème).
!post_rule code
L'action post-règle ajoute un bloc de code défini par l'utilisateur à la fin des actions sémantiques de toutes les règles du bloc actuel (ou de la condition, si des conditions de départ sont utilisées). Cette action peut être utilisée pour émettre des instructions de piège qui protègent contre les flux de contrôle involontaires.

Directives

Voici une liste complète des directives prises en charge par re2py :

!use:name ;
Une directive d'utilisation intra-bloc qui fusionne un bloc de règles défini précédemment avec le nom spécifié dans le bloc actuel. Les définitions nommées, les configurations et les règles du bloc référencé sont ajoutées aux règles actuelles. Les conflits entre les règles et les configurations qui se chevauchent sont résolus de la manière habituelle : la première règle a la priorité, et la dernière configuration remplace les précédentes. Une exception concerne les règles spéciales *, $ et <!> pour lesquelles une définition locale au bloc a toujours la priorité. Une directive d'utilisation peut être placée n'importe où à l'intérieur d'un bloc, et plusieurs directives d'utilisation sont autorisées.
!include file ;
Cette directive est identique au bloc include : elle insère le contenu de file verbatim à la place de la directive.

Interface du programme

Le code généré interagit avec le programme externe à l'aide de primitives, collectivement appelées API. Les primitives qui doivent être définies pour un programme particulier dépendent de plusieurs facteurs, notamment la complexité des expressions régulières, la représentation des entrées, la mise en mémoire tampon et l'utilisation de diverses fonctionnalités. Toutes les primitives nécessaires doivent être définies par l'utilisateur sous forme de macros, de fonctions, de variables ou de toute autre forme appropriée qui rend le code généré syntaxiquement et sémantiquement correct. re2py ne vérifie pas (et ne peut pas vérifier) les définitions, donc si quelque chose manque ou est mal défini, le programme généré peut présenter des erreurs de compilation ou d'exécution. Ce manuel fournit des exemples de définitions d'API dans les cas les plus courants.

re2py propose trois saveurs d'API qui définissent l'ensemble de base des primitives utilisées par un programme :

API Simple
C'est l'API par défaut pour le backend Python. Elle se compose des primitives suivantes : YYINPUT (qui doit être défini comme une séquence d'unités de code, par exemple une chaîne de caractères) et YYCURSOR, YYMARKER, YYCTXMARKER, YYLIMIT (qui doivent être définis comme des indices dans YYINPUT).
API Record
L'API Record est utile dans les cas où l'état du lexer doit être stocké dans une classe. Elle est activée avec l'option --api record ou la configuration re2c:api = record. Cette API se compose d'une variable yyrecord (le nom peut être remplacé par re2c:yyrecord) qui doit être définie comme une classe avec les attributs yyinput, yycursor, yymarker, yyctxmarker, yylimit (seuls les champs utilisés par le code généré doivent être définis, et leurs noms peuvent être configurés).
API Générique
C'est l'API la plus flexible. Elle est activée avec l'option --api generic ou la configuration re2c:api = generic. Elle contient des primitives pour les opérations génériques : YYPEEK, YYSKIP, YYBACKUP, YYBACKUPCTX, YYSTAGP, YYSTAGN, YYMTAGP, YYMTAGN, YYRESTORE, YYRESTORECTX, YYRESTORETAG, YYSHIFT, YYSHIFTSTAG, YYSHIFTMTAG, YYLESSTHAN.

Voici une liste complète des primitives d'API qui peuvent être utilisées par le code généré pour interagir avec le programme externe.

YYCTYPE
Le type des caractères d'entrée (unités de code). Pour les encodages ASCII, EBCDIC et UTF-8 il doit s'agir d'un entier non signé de 1 octet. Pour UTF-16 ou UCS-2, il doit s'agir d'un entier non signé de 2 octets. Pour UTF-32, il doit s'agir d'un entier non signé de 4 octets.
YYCURSOR
Une l-value qui stocke la position d'entrée actuelle (un pointeur ou un décalage d'entier dans YYINPUT). Initialement, YYCURSOR doit pointer vers le premier caractère d'entrée, et plus tard, il est avancé par le code généré. Lorsqu'une règle correspond, la position de YYCURSOR est celle qui suit le dernier caractère correspondant.
YYLIMIT
Une r-value qui stocke la position de fin de l'entrée (un pointeur ou un décalage d'entier dans YYINPUT). Initialement, YYLIMIT doit pointer vers la position après le dernier caractère d'entrée disponible. Il n'est pas modifié par le code généré. Le lexer compare YYCURSOR à YYLIMIT pour déterminer s'il reste suffisamment de caractères d'entrée.
YYMARKER
Une l-value qui stocke la position de la dernière règle correspondante (un pointeur ou un décalage d'entier dans YYINPUT). Elle est utilisée pour restaurer la position de YYCURSOR si la correspondance la plus longue échoue et que le lexer doit faire un rollback. Aucune initialisation n'est nécessaire.
YYCTXMARKER
Une l-value qui stocke la position du contexte de suivi (un pointeur ou un décalage d'entier dans YYINPUT). Aucune initialisation n'est nécessaire. YYCTXMARKER n'est nécessaire que si l'opérateur de lookahead / est utilisé.
YYFILL
Une primitive d'API générique avec une variable len. YYFILL doit fournir au moins len caractères d'entrée supplémentaires ou échouer. Si re2c:eof est utilisé, alors len est toujours 1 et YYFILL doit toujours retourner à la fonction appelante ; une valeur de retour nulle indique un succès. Si re2c:eof n'est pas utilisé, alors la valeur de retour de YYFILL est ignorée et elle ne doit pas retourner en cas d'échec. La valeur maximale de len est YYMAXFILL.
YYFN
Une primitive qui définit le prototype de fonction dans le modèle de code --recursive-functions. Sa valeur doit être un tableau d'une ou plusieurs chaînes de caractères, où chaque chaîne contient deux ou trois composants séparés par la chaîne spécifiée dans la configuration re2c:fn:sep (typiquement un point-virgule). Le premier élément du tableau définit le nom de la fonction et le type de retour (vide pour une fonction void). Les éléments suivants définissent les arguments de la fonction : d'abord, l'expression de l'argument utilisée dans le corps de la fonction (généralement juste un nom) ; ensuite, le type de l'argument ; enfin, un paramètre formel optionnel (il est par défaut le premier composant - généralement, l'argument et le paramètre sont le même identifiant).
YYINPUT
Une valeur r qui stocke la séquence d'entrée actuelle (chaîne, tampon, etc.).
YYMAXFILL
Une constante entière égale à la valeur maximale de l'argument de YYFILL. Elle peut être générée avec un bloc max.
YYLESSTHAN
Une primitive API générique avec une variable len. Elle doit être définie comme une valeur r de type booléen qui est égale à true si et seulement si il reste moins de len caractères d'entrée.
YYPEEK
Une primitive API générique sans variables. Elle doit être définie comme une valeur r de type YYCTYPE qui est égale au caractère à la position d'entrée actuelle.
YYSKIP
Une primitive API générique qui doit faire avancer la position d'entrée actuelle d'une unité de code.
YYBACKUP
Une primitive API générique qui doit enregistrer la position d'entrée actuelle (pour être restaurée plus tard avec YYRESTORE).
YYRESTORE
Une primitive API générique qui doit restaurer la position d'entrée actuelle à la valeur enregistrée par YYBACKUP.
YYBACKUPCTX
Une primitive API générique qui doit enregistrer la position d'entrée actuelle comme la position du contexte de fin (pour être restaurée plus tard avec YYRESTORECTX).
YYRESTORECTX
Une primitive API générique qui doit restaurer la position du contexte de fin enregistrée avec YYBACKUPCTX.
YYRESTORETAG
Une primitive API générique avec une variable tag qui doit restaurer la position du contexte de fin à la valeur de tag.
YYSTAGP
Une primitive API générique avec une variable tag, où tag peut être un pointeur ou un décalage dans YYINPUT (voir la section extraction de sous-correspondance pour plus de détails). YYSTAGP doit définir tag à la position d'entrée actuelle.
YYSTAGN
Une primitive API générique avec une variable tag, où tag peut être un pointeur ou un décalage dans YYINPUT (voir la section extraction de sous-correspondance pour plus de détails). YYSTAGN doit définir tag à une valeur représentant une position d'entrée inexistante.
YYMTAGP
Une primitive API générique avec une variable tag. YYMTAGP doit ajouter la position actuelle à l'historique de sous-correspondance de tag (voir la section extraction de sous-correspondance pour plus de détails.)
YYMTAGN
Une primitive API générique avec une variable tag. YYMTAGN doit ajouter une valeur représentant une position d'entrée inexistante à l'historique de sous-correspondance de tag (voir la section extraction de sous-correspondance pour plus de détails.)
YYSHIFT
Une primitive API générique avec une variable shift qui doit décaler la position d'entrée actuelle de shift caractères (la valeur de décalage peut être négative).
YYCOPYSTAG
Une primitive API générique avec deux variables, lhs et rhs qui doit copier la variable s-tag de droite rhs dans la variable s-tag de gauche lhs. Pour la plupart des langages, cette primitive a une définition par défaut qui assigne lhs à rhs.
YYCOPYMTAG
Une primitive API générique avec deux variables, lhs et rhs qui doit copier la variable m-tag de droite rhs dans la variable m-tag de gauche lhs. Pour la plupart des langages, cette primitive a une définition par défaut qui assigne lhs à rhs.
YYSHIFTSTAG
Une primitive API générique avec deux variables, tag et shift qui doit décaler tag de shift unités de code (la valeur de décalage peut être négative).
YYSHIFTMTAG
Une primitive API générique avec deux variables, tag et shift qui doit décaler la dernière valeur de l'historique de tag de shift unités de code (la valeur de décalage peut être négative).
YYMAXNMATCH
Une constante entière égale au nombre maximal de groupes de capture POSIX dans une règle. Elle est générée avec un bloc maxnmatch.
YYCONDTYPE
Le type de l'énumération de condition. Il peut être généré soit avec le bloc conditions, soit avec l'option --header.
YYGETACCEPT
Une primitive avec une variable var qui stocke le sélecteur numérique de la règle acceptée. Pour la plupart des langages, cette primitive a une définition par défaut qui lit depuis var.
YYSETACCEPT
Une primitive avec deux variables : var (une valeur l de type entier non signé qui stocke le sélecteur numérique de la règle acceptée) et val (la valeur du sélecteur). Pour la plupart des langages, cette primitive a une définition par défaut qui assigne var à val.
YYGETCOND
Une valeur r de type YYCONDTYPE qui est égale à l'identifiant de condition actuel.
YYSETCOND
Une primitive avec une variable cond qui doit définir l'identifiant de condition actuel à cond.
YYGETSTATE
Une valeur r de type entier qui est égale à l'état actuel de l'analyseur lexical. Elle doit être initialisée à -1.
YYSETSTATE
Une primitive avec une variable state qui doit définir l'état actuel de l'analyseur lexical à state.
YYDEBUG
Cette primitive est générée uniquement avec l'option -d, --debug-output. Son but est d'ajouter de la journalisation au code généré (une définition typique de YYDEBUG est une instruction d'impression). Les instructions YYDEBUG sont générées dans chaque état et ont deux variables : state (soit un indice d'état DFA, soit -1) et symbol (le symbole d'entrée actuel).
yyaccept
Une valeur l de type entier non signé qui stocke le numéro de la dernière règle correspondante. Une définition utilisateur n'est nécessaire qu'avec l'option --storable-state.
yybm
Une table contenant des bitmaps compressées pour jusqu'à 8 transitions (utilisée avec l'option --bitmaps). La table contient 256 éléments et est indexée par des unités de code sur 1 octet. Chaque élément de 8 bits combine des valeurs booléennes pour jusqu'à 8 transitions. Le k-ième bit du n-ième élément est vrai si et seulement si la n-ième unité de code est dans la plage de la k-ième transition. L'idée de cette bitmap est de remplacer de nombreuses branches if ou cas switch par une seule vérification d'un seul bit dans la table.
yych
Une valeur l de type YYCTYPE qui stocke le caractère d'entrée actuel. Une définition utilisateur n'est nécessaire qu'avec les options -f --storable-state.
yyctable
Table de saut générée pour la dispersion initiale des conditions (activée avec la combinaison des options --conditions et --computed-gotos).
yyfill
Une valeur l qui stocke le résultat de l'appel YYFILL (cela peut être nécessaire pour les langages purement fonctionnels, où YYFILL est une fonction monadique avec une valeur de retour complexe).
yynmatch
Une valeur l de type entier non signé qui stocke le nombre de groupes de capture POSIX dans la règle correspondante. Utilisé uniquement avec l'option -P --posix-captures.
yypmatch
Un tableau de valeurs l utilisées pour contenir les valeurs de tag correspondant aux parenthèses de capture dans la règle correspondante. La longueur du tableau doit être d'au moins yynmatch * 2 (généralement YYMAXNMATCH * 2 est un bon choix). Utilisé uniquement avec l'option -P --posix-captures.
yystable
Obsolète.
yystate
Une valeur l utilisée avec l'option --loop-switch pour stocker l'état DFA actuel.
yytarget
Table de saut contenant les cibles de saut (adresses d'étiquettes) pour toutes les transitions d'un état. Cette table est locale à chaque état. La génération de tables yytarget est activée avec l'option --computed-gotos.

Options

Certaines options ont des configurations correspondantes, d'autres sont globales et ne peuvent pas être modifiées après que re2c commence à lire le fichier d'entrée. Les options de débogage nécessitent généralement de compiler re2c dans une configuration de débogage. Les options internes sont utiles pour expérimenter avec les algorithmes utilisés dans re2c.

-? --help -h
Afficher le message d'aide.
--api <simple | record | generic>
Spécifier l'API utilisée par le code généré pour interagir avec le code défini par l'utilisateur. L'option simple doit être utilisée dans des cas simples où il n'y a pas besoin de recharger le tampon et de stocker l'état de l'analyseur. L'option record doit être utilisée lorsque l'état de l'analyseur doit être stocké dans un enregistrement (structure, classe, etc.). L'option generic doit être utilisée dans des cas complexes lorsque les deux autres API ne sont pas suffisamment flexibles.
--bit-vectors -b
Optimiser les sauts conditionnels à l'aide de masques de bits. Cette op
tion implique --nested-ifs.
--captures, --leftmost-captures
Active l'extraction de sous-correspondances avec des groupes de capture gloutons de gauche à droite. Le résultat est collecté dans un tableau yybmatch de capacité 2 * YYMAXNMATCH, et yynmatch est défini sur le nombre de groupes pour la règle de correspondance.
--captvars, --leftmost-captvars
Active l'extraction de sous-correspondances avec des groupes de capture gloutons de gauche à droite. Le résultat est collecté dans les variables yytl<k>, yytr<k> pour le k-ième groupe de capture.
--case-insensitive
Traite les chaînes entre apostrophes simples et guillemets doubles comme insensibles à la casse.
--case-inverted
Inverse le sens des chaînes entre apostrophes simples et guillemets doubles : traite les chaînes entre apostrophes simples comme sensibles à la casse et les chaînes entre guillemets doubles comme insensibles à la casse.
--case-ranges
Regroupe les cas consécutifs dans les instructions switch en une plage de la forme low ... high. Cette syntaxe est une extension du langage C/C++ qui est prise en charge par des compilateurs comme GCC, Clang et Tcc. L'avantage principal par rapport à l'utilisation de cas individuels est un code généré plus petit et un temps de génération plus rapide, bien que pour certains compilateurs comme Tcc, cela entraîne également une taille de binaire plus petite.
--computed-gotos -g
Optimise les sauts conditionnels à l'aide de l'extension non standard "computed goto" (qui doit être prise en charge par le compilateur). re2py génère des tables de sauts uniquement dans les cas complexes avec de nombreuses branches conditionnelles. Le seuil de complexité peut être configuré avec la configuration cgoto:threshold. Les décalages relatifs peuvent être activés avec la configuration cgoto:relative. Cette option implique --bit-vectors.
--computed-gotos-relative
Similaire à --computed-gotos mais génère des décalages relatifs pour les tables de sauts au lieu de cela (ce qui doit être pris en charge par le compilateur). Cette option implique --computed-gotos.
--conditions --start-conditions -c
Active la prise en charge des "conditions" de type Flex : plusieurs analyseurs lexicaux interdépendants au sein d'un même bloc. C'est une alternative à la spécification manuelle de différents blocs re2py connectés par goto ou des appels de fonction.
--depfile FILE
Écrit les informations de dépendance dans FILE sous la forme d'une règle Makefile <output-file> : <input-file> [include-file ...]. Cela permet de suivre les dépendances de compilation en présence de blocs/directives include, de sorte que la mise à jour des fichiers inclus déclenche la régénération du fichier de sortie. Cette option dépend de l'option --output.
--ebcdic --ecb -e
Génère un analyseur lexical qui lit l'entrée en encodage EBCDIC. re2py suppose que la plage de caractères est de 0 à 0xFF et que la taille des caractères est de 1 octet.
--empty-class <match-empty | match-none | error>
Définit la manière dont re2py traite les classes de caractères vides. Avec match-empty (par défaut), une classe vide correspond à une entrée vide (ce qui est illogique, mais rétrocompatible). Avec match-none, une classe vide échoue toujours à correspondre. Avec error, une classe vide génère une erreur de compilation.
--encoding-policy <fail | substitute | ignore>
Définit la manière dont re2py traite les substituts Unicode. Avec fail, re2py s'arrête avec une erreur lorsqu'un substitut est rencontré. Avec substitute, re2py remplace silencieusement les substituts par le point de code d'erreur 0xFFFD. Avec ignore (par défaut), re2py traite les substituts comme des points de code normaux. La norme Unicode stipule que les substituts autonomes sont invalides, mais les bibliothèques et programmes du monde réel se comportent différemment.
--flex-syntax -F
Prise en charge partielle de la syntaxe Flex : dans ce mode, les définitions nommées n'ont pas besoin du signe égal ni du point-virgule de terminaison, et lorsqu'elles sont utilisées, elles doivent être entourées d'accolades. Les noms sans accolades sont traités comme des chaînes entre guillemets doubles.
--goto-label
Utilise le modèle de code "goto/label" : code le DFA sous forme de blocs de code étiquetés connectés par des transitions goto entre les blocs. Ceci n'est pris en charge que pour les langages qui ont une instruction goto.
--header --type-header -t HEADER
Génère un fichier HEADER. Le contenu du fichier peut être spécifié à l'aide de blocs spéciaux header:on et header:off. Si des conditions sont utilisées, l'en-tête généré aura un énumérateur de conditions ajouté automatiquement (sauf s'il y a un bloc conditions explicite).
-I PATH
Ajoute PATH à la liste des emplacements utilisés lors de la recherche de fichiers d'inclusion. Cette option est utile en combinaison avec le bloc ou la directive include. re2py recherche FILE dans le répertoire du fichier parent et dans les emplacements d'inclusion spécifiés avec l'option -I.
--input <default | custom>
Alias obsolète pour --api. L'option default correspond à simple (c'est effectivement le défaut pour la plupart des backends, mais pas pour tous). L'option custom correspond à generic.
--input-encoding <ascii | utf8>
Spécifie la manière dont re2py analyse les expressions régulières. Avec ascii (par défaut), re2py traite l'entrée comme étant encodée en ASCII : toute séquence d'unités de code est une séquence de caractères autonomes de 1 octet. Avec utf8, re2py traite l'entrée comme étant encodée en UTF8 et reconnaît les caractères multibytes.
--invert-captures
Inverse le sens des groupes de capture et des groupes non capturants. Par défaut, (...) est capturant et (! ...) est non capturant. Avec cette option, (! ...) est capturant et (...) est non capturant.
--lang <none | c | d | go | haskell | java | js | ocaml | python | rust | swift | v | zig>
Spécifie la langue cible. Les langues prises en charge sont C, D, Go, Haskell, Java, JS, OCaml, Python, Rust, Swift, V, Zig (d'autres langues peuvent être ajoutées via des fichiers de syntaxe définis par l'utilisateur, voir l'option --syntax). L'option none désactive les configurations de syntaxe par défaut, de sorte que la langue cible est indéfinie.
--location-format <gnu | msvc>
Spécifie le format d'emplacement dans les messages. Avec gnu, les emplacements sont imprimés comme 'filename:line:column: ...'. Avec msvc, les emplacements sont imprimés comme 'filename(line,column) ...'. Le défaut est gnu.
--loop-switch
Utilise le modèle de code "loop/switch" : code le DFA sous forme de boucle sur une instruction switch, où les états individuels sont des cas de switch. L'état est stocké dans une variable yystate. Les transitions entre les états mettent à jour yystate vers l'étiquette de cas de l'état de destination et continuent l'exécution vers le début de la boucle.
--nested-ifs -s
Utilise des instructions if imbriquées au lieu d'instructions switch dans les sauts conditionnels. Cela se traduit généralement par un code plus efficace avec des compilateurs non optimisants.
--no-debug-info -i
Ne produit pas d'informations de ligne. Cela peut être utile lorsque le code généré est stocké dans un système de contrôle de version (pour éviter d'énormes différences auto-générées lors de petits changements).
--no-generation-date
Supprime la sortie de la date dans le fichier généré.
--no-version
Supprime la sortie de la version dans le fichier généré.
--no-unsafe
Ne génère pas d'enveloppe unsafe autour de YYPEEK (cette option est spécifique à Rust). Pour des raisons de performance, YYPEEK devrait éviter la vérification des limites, car l'analyseur lexical effectue déjà des vérifications de fin d'entrée de manière plus efficace. L'utilisateur peut choisir de fournir une définition YYPEEK sûre, ou une définition qui n'est unsafe que dans les builds de production, auquel cas l'option --no-unsafe aide à éviter les avertissements concernant les blocs unsafe redondants.
--output -o OUTPUT
Spécifie le fichier OUTPUT.
--posix-captures, -P
Active l'extraction de sous-correspondances avec des groupes de capture de style POSIX. Le résultat est collecté dans un tableau yybmatch de capacité 2 * YYMAXNMATCH, et yynmatch est défini sur le nombre de groupes pour la règle de correspondance.
--posix-captvars
Active l'extraction de sous-correspondances avec des groupes de capture de style POSIX. Le résultat est collecté dans les variables yytl<k>, yytr<k> pour le k-ième groupe de capture.
--recursive-functions
Utilise un modèle de code basé sur des fonctions co-récursives, où chaque état du DFA est une fonction distincte qui peut appeler d'autres fonctions d'état ou elle-même.
--reusable -r
Obsolète depuis la version 2.2 (les blocs réutilisables sont autorisés par défaut maintenant).
--skeleton -S
Ignore le code d'interface défini par l'utilisateur et génère un programme "squelette" autonome. De plus, génère des fichiers d'entrée avec des chaînes dérivées de la grammaire régulière et des résultats de correspondance compressés qui sont utilisés pour vérifier le comportement du "squelette" sur toutes les entrées. Cette option est utile pour trouver des bugs dans les optimisations et la génération de code. Cette option n'est prise en charge que pour C.
--storable-state -f
Génère un analyseur lexical qui peut stocker son état interne. Ceci est utile dans les analyseurs lexicaux de type push qui sont stoppés
ped par un programme externe lorsqu'il n'y a pas assez d'entrée, puis repris lorsque plus d'entrée est disponible. Dans ce mode, les utilisateurs doivent en plus définir les primitives YYGETSTATE et YYSETSTATE, et les variables yych, yyaccept et state doivent faire partie de l'état du lexer sauvegardé.
--syntax FICHIER
Charge les configurations à partir du FICHIER spécifié et les applique par-dessus le fichier de syntaxe par défaut. Notez que FICHIER peut ne définir que quelques configurations (s'il est utilisé pour modifier le fichier de syntaxe par défaut), ou il peut définir un backend de langage entièrement nouveau (dans ce dernier cas, il est recommandé d'utiliser l'option --lang none).
--tags -T
Active l'extraction de sous-correspondances avec des balises.
--ucs2 --wide-chars -w
Génère un lexer qui lit une entrée encodée en UCS2. re2py suppose que la plage de caractères est de 0 -- 0xFFFF et que la taille des caractères est de 2 octets. Cette option implique --nested-ifs.
--utf8 --utf-8 -8
Génère un lexer qui lit une entrée encodée en UTF-8. re2py suppose que la plage de caractères est de 0 -- 0x10FFFF et que la taille des caractères est de 1 octet.
--utf16 --utf-16 -x
Génère un lexer qui lit une entrée encodée en UTF16. re2py suppose que la plage de caractères est de 0 -- 0x10FFFF et que la taille des caractères est de 2 octets. Cette option implique --nested-ifs.
--utf32 --unicode -u
Génère un lexer qui lit une entrée encodée en UTF32. re2py suppose que la plage de caractères est de 0 -- 0x10FFFF et que la taille des caractères est de 4 octets. Cette option implique --nested-ifs.
--verbose
Affiche un court message en cas de succès.
--vernum -V
Affiche les informations de version au format MMmmpp (majeur, mineur, correctif).
--version -v
Affiche les informations de version.
--single-pass -1
Obsolète. Ne fait rien (le passage unique est maintenant par défaut).
--debug-output -d
Émet des invocations de YYDEBUG dans le code généré. Ceci est utile pour suivre l'exécution du lexer.
--dump-adfa
Option de débogage : affiche le DFA après le tunneling (au format .dot).
--dump-cfg
Option de débogage : affiche le graphe de flot de contrôle des variables de balises (au format .dot).
--dump-closure-stats
Option de débogage : affiche les statistiques sur le nombre d'états dans la fermeture.
--dump-dfa-det
Option de débogage : affiche le DFA immédiatement après la déterminisation (au format .dot).
--dump-dfa-min
Option de débogage : affiche le DFA après la minimisation (au format .dot).
--dump-dfa-tagopt
Option de débogage : affiche le DFA après les optimisations de balises (au format .dot).
--dump-dfa-tree
Option de débogage : affiche le DFA en cours de construction avec les états représentés par des arbres d'historique de balises (au format .dot).
--dump-dfa-raw
Option de débogage : affiche le DFA en cours de construction avec des ensembles d'états étendus (au format .dot).
--dump-interf
Option de débogage : affiche la table d'interférence produite par l'analyse de vivacité des variables de balises.
--dump-nfa
Option de débogage : affiche le NFA (au format .dot).
--emit-dot -D
Au lieu de la sortie normale, génère le graphe du lexer au format .dot. La sortie peut être convertie en image à l'aide de Graphviz (par exemple, quelque chose comme dot -Tpng -odfa.png dfa.dot).
--dfa-minimization <moore | table>
Option interne : algorithme de minimisation de DFA utilisé par re2py. L' option moore est l'algorithme de Moore (c'est la valeur par défaut). L' option table est l'algorithme de "remplissage de table". Les deux algorithmes devraient produire le même DFA à un réétiquetage des états près ; le remplissage de table est plus simple et beaucoup plus lent et sert d'implémentation de référence.
--eager-skip
Option interne : fait avancer le lexer généré la position d'entrée précipitamment -- immédiatement après la lecture du symbole d'entrée. Ceci modifie le comportement par défaut lorsque la position d'entrée est avancée paresseusement -- après la transition vers le prochain état.
--no-lookahead
Option interne, obsolète. Elle activait l'algorithme TDFA(0). Contrairement à TDFA(1), l'algorithme TDFA(0) n'utilise pas de lookahead d'un symbole. Il applique des opérations de registre aux transitions entrantes plutôt qu'aux sortantes. Les benchmarks ont montré que l'algorithme TDFA(0) est moins efficace que TDFA(1).
--no-optimize-tags
Option interne : supprime l'optimisation des variables de balises (utile pour le débogage).
--posix-closure <gor1 | gtop>
Option interne : spécifie l'algorithme de chemin le plus court utilisé pour la construction de la fermeture epsilon avec sémantique de désambiguïsation POSIX : gor1 (la valeur par défaut) signifie algorithme de Goldberg-Radzik, et gtop signifie "ordre topologique global".
--posix-prectable <complex | naive>
Option interne : spécifie l'algorithme utilisé pour calculer la table de précédence POSIX. L'algorithme complex calcule la table de précédence en un seul parcours de l'arbre d'historique des balises et a une complexité quadratique par rapport au nombre d'états TNFA ; c'est la valeur par défaut. L'algorithme naive a une complexité cubique dans le pire des cas par rapport au nombre d'états TNFA, mais il est beaucoup plus simple que complex et peut être légèrement plus rapide dans les cas non pathologiques.
--stadfa
Option interne, obsolète. Elle activait l'algorithme staDFA, qui diffère de TDFA en ce que les opérations de registre sont placées dans les états plutôt que sur les transitions. Les benchmarks ont montré que l'algorithme staDFA est moins efficace que TDFA.
--fixed-tags <none | toplevel | all>
Option interne : spécifie si l'optimisation des balises fixes doit être appliquée à toutes les balises (all), à aucune d'entre elles (none), ou seulement à celles des concaténations de niveau supérieur (toplevel). La valeur par défaut est all. Les balises "fixes" sont celles qui sont situées à une distance fixe d'une autre balise (appelée "base"). Dans de tels cas, seule la balise de base doit être suivie, et la valeur de la balise fixe peut être calculée comme la valeur de la balise de base plus un décalage statique. Pour les balises qui se trouvent sous une alternative ou une répétition, il est également nécessaire de vérifier si la balise de base a une valeur de non-correspondance (dans ce cas, la balise fixe doit également être définie sur non-correspondance, ignorant le décalage). Pour les balises dans la concaténation de niveau supérieur, la vérification n'est pas nécessaire, car elles correspondent toujours.

Avertissements

Les avertissements peuvent être activés, désactivés et transformés en erreur individuellement.

-W
Active tous les avertissements.
-Werror
Transforme les avertissements en erreurs. Notez que cette option seule n'active aucun avertissement ; elle n'affecte que les avertissements qui ont été activés jusqu'à présent ou qui seront activés plus tard.
-W<avertissement>
Active avertissement.
-Wno-<avertissement>
Désactive avertissement.
-Werror-<avertissement>
Active avertissement et le traite comme une erreur (ceci implique -W<avertissement>).
-Wno-error-<avertissement>
Ne traite pas cet avertissement particulier comme une erreur. Ceci ne désactive pas l'avertissement lui-même.
-Wcondition-order
Avertit si le programme généré fait des suppositions implicites sur la numérotation des conditions. Il faut utiliser soit l'option --header, soit le bloc conditions pour générer une cartographie des noms de conditions vers des numéros et ensuite utiliser les noms de conditions autogénérés.
-Wempty-character-class
Avertit si une expression régulière contient une classe de caractères vide. Essayer de faire correspondre une classe de caractères vide n'a pas de sens : elle devrait toujours échouer. Cependant, pour des raisons de compatibilité ascendante, re2py autorise les classes de caractères vides et les traite comme des chaînes vides. Utilisez l'option --empty-class pour modifier le comportement par défaut.
-Wmatch-empty-string
Avertit si une règle est nullable (correspond à une chaîne vide). Si le lexer s'exécute en boucle et que la correspondance vide est involontaire, le lexer peut se bloquer de manière inattendue dans une boucle infinie.
-Wswapped-range
Avertit si la borne inférieure d'une plage est supérieure à sa borne supérieure. Le comportement par défaut est d'échanger silencieusement les bornes de la plage.
-Wundefined-control-flow
Avertit si certaines chaînes d'entrée provoquent un flux de contrôle indéfini dans le lexer (les motifs défectueux sont signalés). C'est une erreur dangereuse et courante. Elle peut être facilement corrigée en ajoutant la règle par défaut * qui a la priorité la plus basse, mat
ches toute unité de code, et consomme toujours une seule unité de code.
-Wunreachable-rules
Avertir des règles qui sont masquées par d'autres règles et qui ne correspondent jamais.
-Wdeprecated-eof_rule
Avertir des règles autonomes de fin d'entrée $ qui seront rompues par les changements futurs et nécessiteront une correction. Actuellement, ces règles ont la priorité lorsqu'elles entrent en conflit avec d'autres règles, mais après l'introduction du symbole généralisé de fin d'entrée $, l'ordre de priorité changera et ces règles seront masquées par d'autres règles.
-Wuseless-escape
Avertir si un symbole est échappé alors qu'il ne devrait pas l'être. Par défaut, re2py ignore silencieusement de tels échappements, mais cela peut aussi indiquer une faute de frappe ou une erreur dans la séquence d'échappement.
-Wnondeterministic-tags
Avertir si une balise a un degré de nondéterminisme n, où n est supérieur à 1.
-Wsentinel-in-midrule
Avertir si le symbole sentinelle se produit au milieu d'une règle --- cela peut provoquer des lectures au-delà de la fin du tampon, des plantages ou une corruption de mémoire dans l'analyseur lexical généré. Cet avertissement ne s'applique que si la méthode sentinelle de vérification de la fin de l'entrée est utilisée. Il est défini comme une erreur si la configuration re2c:sentinel est utilisée.
-Wundefined-syntax-config
Avertir si le fichier de syntaxe spécifié avec l'option --syntax manque de définitions pour certaines configurations. Cela aide à maintenir les fichiers de syntaxe définis par l'utilisateur : si une nouvelle version ajoute des configurations, l'ancien fichier de syntaxe générera un avertissement et l'utilisateur sera notifié. Si certaines configurations sont inutilisées et n'ont pas besoin de définition, elles doivent être explicitement définies sur <undefined>.

Fichiers de syntaxe

Le support des différents langages dans re2c repose sur l'idée de fichiers de syntaxe. Un fichier de syntaxe est un fichier de configuration qui définit la syntaxe du langage cible -- pas tout le langage, mais une petite partie de celui-ci qui est utilisée par le code généré. Les fichiers de syntaxe rendent re2c très flexible, mais ils ne doivent pas être utilisés comme remplacement pour les configurations re2c: : leur but est de définir la syntaxe du langage cible, et non de personnaliser un analyseur lexical particulier. Tous les langages supportés ont des fichiers de syntaxe par défaut qui font partie de la distribution (voir le sous-répertoire include/syntax) ; ils sont également intégrés dans le binaire re2py. Les utilisateurs peuvent fournir un fichier de syntaxe personnalisé qui remplace quelques configurations pour l'un des langages supportés, ou ils peuvent choisir de redéfinir toutes les configurations (dans ce cas, l'option --lang none devrait être utilisée). Les fichiers de syntaxe contiennent des configurations de quatre types différents : listes de fonctionnalités, configurations de langage, configurations "inplace" et modèles de code.

Listes de fonctionnalités

Quelques configurations de liste définissent diverses fonctionnalités supportées par un backend donné, de sorte que re2py puisse générer une erreur claire si l'utilisateur essaie d'activer une fonctionnalité non supportée :
supported_apis
Une liste des API supportées avec les éléments possibles simple, record, generic.
supported_api_styles
Une liste des styles d'API supportés avec les éléments possibles functions, free-form.
supported_code_models
Une liste des modèles de code supportés avec les éléments possibles goto-label, loop-switch, recursive-functions.
supported_targets
Une liste des cibles de génération de code supportées avec les éléments possibles code, dot, skeleton.
supported_features
Une liste des fonctionnalités supportées avec les éléments possibles nested-ifs, bitmaps, computed-gotos, case-ranges, monadic, unsafe, tags, captures, captvars.

Configurations de langage

Quelques configurations booléennes décrivent les caractéristiques du langage cible qui affectent l'analyseur et le générateur de code de re2py :
semicolons
Non-zéro si le langage utilise des points-virgules après les instructions.
backtick_quoted_strings
Non-zéro si le langage a des chaînes de caractères entre guillemets inversés.
single_quoted_strings
Non-zéro si le langage a des chaînes de caractères entre guillemets simples.
indentation_sensitive
Non-zéro si le langage est sensible à l'indentation.
wrap_blocks_in_braces
Non-zéro si les blocs d'instructions composés doivent être entourés d'accolades.

Configurations "Inplace"

Les fichiers de syntaxe définissent les valeurs initiales de toutes les configurations re2c:, car elles peuvent différer selon les langages. Voir la section des configurations pour une liste complète de toutes les configurations "inplace" et leur signification.

Modèles de code

Les modèles de code définissent la syntaxe du langage cible. Ils sont écrits dans un langage simple spécifique à un domaine avec la grammaire formelle suivante : 
code-template ::
      name '=' code-exprs ';'
    | CODE_TEMPLATE ';'
    | '<undefined>' ';'
code-exprs ::
      <EMPTY>
    | code-exprs code-expr
code-expr ::
      STRING
    | VARIABLE
    | optional
    | list
optional ::
      '(' CONDITIONAL '?' code-exprs ')'
    | '(' CONDITIONAL '?' code-exprs ':' code-exprs ')'
list ::
      '[' VARIABLE ':' code-exprs ']'
    | '[' VARIABLE '{' NUMBER '}' ':' code-exprs ']'
    | '[' VARIABLE '{' NUMBER ',' NUMBER '}' ':' code-exprs ']'

Un modèle de code est une séquence de littéraux de chaînes, de variables, d'éléments optionnels et de listes, ou une référence à un autre modèle de code, ou une valeur spéciale <undefined>. Les variables sont des espaces réservés qui sont substitués pendant la phase de génération de code. Les variables de liste sont spéciales : lors de l'expansion des modèles de liste, re2py répète les expressions du côté droit de la colonne plusieurs fois, en remplaçant à chaque fois les occurrences de la variable de liste par une valeur spécifique à cette répétition. Les listes ont des limites optionnelles (les valeurs négatives sont comptées à partir de la fin, par exemple -1 signifie le dernier élément). Les noms conditionnels commencent par un point. Les conditions et les variables peuvent être locales (spécifiques au modèle de code donné) ou globales (autorisées dans tous les modèles de code). Lorsque re2py lit le fichier de syntaxe, il vérifie que chaque modèle de code utilise uniquement les variables et les conditions qui y sont autorisées.

Par exemple, le modèle de code suivant définit la construction si-alors-sinon pour un langage de type C :

code:if_then_else =
    [branch{0}: topindent "if " cond " {" nl
        indent [stmt: stmt] dedent]
    [branch{1:-1}: topindent "} else" (.cond ? " if " cond) " {" nl
        indent [stmt: stmt] dedent]
    topindent "}" nl;

Ici, branch est une variable de liste : branch{0} s'étend à la première branche (qui est spéciale, car il n'y a pas de partie else), branch{1:-1} s'étend à toutes les branches restantes (le cas échéant). stmt est également une variable de liste : [stmt: stmt] est une liste imbriquée qui s'étend à une liste d'instructions dans le corps de la branche actuelle. topindent, indent, dedent et nl sont des variables globales, et .cond est une condition locale (leur signification est décrite ci-dessous). Ce modèle de code pourrait produire le code suivant :

if x {
    // faire quelque chose
} else if y {
    // faire quelque chose d'autre
} else {
    // ne rien faire
}

PRISE EN CHARGE DE LA FIN DE L'ENTRÉE

L'un des principaux problèmes pour l'analyseur lexical est de savoir quand s'arrêter. Il existe quelques conditions de terminaison :

  • l'analyseur lexical peut correspondre à une règle (y compris la règle par défaut *) et aboutir à un état final
  • l'analyseur lexical peut ne pas parvenir à correspondre à une règle et aboutir à un état par défaut
  • l'analyseur lexical peut atteindre la fin de l'entrée

Les deux premières conditions terminent l'analyseur lexical de manière "naturelle" : il atteint un état sans transitions sortantes, et la correspondance s'arrête automatiquement. La troisième condition, la fin de l'entrée, est différente : elle peut se produire dans n'importe quel état, et l'analyseur lexical doit être capable de la gérer. La vérification de la fin de l'entrée interrompt le flux normal de l'analyseur lexical et ajoute des branches conditionnelles au programme généré, il est donc nécessaire de minimiser le nombre de ces vérifications. re2py prend en charge quelques méthodes différentes pour gérer la fin de l'entrée. Celle à utiliser dépend de la complexité des expressions régulières, du besoin de mise en mémoire tampon, des considérations de performance et d'autres facteurs. Voici une liste de méthodes :

  • Sentinelle. Cette méthode élimine complètement le besoin de vérifications de fin d'entrée. Elle est simple et efficace, mais limitée au cas où il existe un caractère "sentinelle" naturel qui ne peut jamais apparaître dans une entrée valide. Ce caractère peut toujours apparaître dans une entrée invalide, mais il ne devrait pas être autorisé par les expressions régulières, sauf peut-être comme dernier caractère d'une règle. La sentinelle est ajoutée à la fin de l'entrée et sert de signal d'arrêt : lorsque l'analyseur lexical lit ce caractère, il s'agit soit d'une erreur de syntaxe, soit de la fin de l'entrée. Dans les deux cas, l'analyseur lexical doit s'arrêter. Cette méthode est utilisée si YYFILL est désactivé avec re2c:yyfill:enable = 0; et si re2c:eof a la valeur par défaut -1.
  • Sentinelle avec vérifications de limites. Cette méthode est générique : elle permet de gérer n'importe quelle entrée sans restrictions sur les expressions régulières. L'idée est de réduire le nombre de vérifications de fin d'entrée en ne les effectuant que sur certains caractères. Similaire à la méthode "sentinelle", l'un des caractères est choisi comme "sentinelle" et ajouté à la fin de l'entrée. Cependant, il n'y a aucune restriction quant à l'endroit où la sentinelle peut apparaître (en fait, n'importe quel caractère peut être choisi pour une sentinelle). Lorsque l'analyseur lexical lit ce caractère, il effectue en plus une vérification de limites. Si la position actuelle est dans les limites, l'analyseur lexical reprend la correspondance et traite la sentinelle comme un caractère normal. Sinon, il appelle YYFILL (sauf si elle est désactivée). Si plus d'entrée est fournie, l'analyseur lexical remettra en correspondance le dernier caractère et continuera comme si la sentinelle n'y était pas. Sinon, il doit s'agir de la véritable fin de l'entrée, et l'analyseur lexical s'arrête. Cette méthode est utilisée lorsque re2c:eof a une valeur non négative (elle doit être définie à la valeur numérique de la sentinelle). YYFILL est facultatif.
  • Vérifications de limites avec remplissage. Cette méthode est générique et peut être plus rapide que la méthode "sentinelle avec vérifications de limites", mais elle est aussi plus complexe. L'idée est de partitionner les états du DFA en composantes fortement connexes (SCC) et de générer une seule vérification par SCC pour suffisamment de caractères afin de couvrir le chemin non cyclique le plus long dans cette SCC. Cela réduit le nombre de vérifications, mais il y a un problème avec les lexèmes courts en fin d'entrée, car la vérification nécessite suffisamment de caractères pour couvrir le lexème le plus long. Cela peut être corrigé en remplissant l'entrée avec quelques caractères factices qui ne forment pas un suffixe de lexème valide (de sorte que l'analyseur lexical ne puisse pas les faire correspondre). La longueur du remplissage doit être YYMAXFILL, générée avec un bloc max. S'il n'y a pas assez d'entrée, l'analyseur lexical appelle YYFILL qui devrait fournir au moins le nombre requis de caractères ou ne pas retourner. Cette méthode est utilisée si YYFILL est activé et que re2c:eof est -1 (c'est la configuration par défaut).
  • Vérifications personnalisées. L'API générique permet de remplacer les opérations de base telles que la lecture d'un caractère, ce qui permet d'inclure les vérifications de fin d'entrée dans celles-ci. Cette approche est sujette aux erreurs et doit être utilisée avec prudence. Pour utiliser une méthode personnalisée, activez l'API générique avec --api custom ou re2c:api = custom; et désactivez les vérifications de limites par défaut avec re2c:yyfill:enable = 0; ou re2c:yyfill:check = 0;.

Sentinelle

Cet exemple utilise un caractère sentinelle pour gérer la fin de l'entrée. Le programme compte les mots séparés par des espaces dans une chaîne terminée par un nul. La sentinelle est le caractère nul : c'est le dernier caractère de chaque chaîne d'entrée, et il n'est autorisé dans le milieu d'un lexème par aucune des règles (en particulier, il n'est pas inclus dans les plages de caractères où il est facile de l'oublier). Si un caractère nul se produit au milieu d'une chaîne, c'est une erreur de syntaxe et l'analyseur lexical correspondra à la règle par défaut *, mais il ne lira pas au-delà de la fin de l'entrée et ne plantera pas (utilisez l'avertissement -Wsentinel-in-midrule et la configuration re2c:sentinel pour vérifier cela). La configuration re2c:yyfill:enable = 0; supprime la génération des vérifications de limites et des appels YYFILL.

# re2py $INPUT -o $OUTPUT
# attend une chaîne terminée par un nul
def lex(yyinput):
    yycursor = 0
    count = 0
    while True: %{
        re2c:yyfill:enable = 0;
        re2c:indent:top = 2;
        *      { return -1 }
        [\x00] { return count }
        [ ]+   { break }
        [a-z]+ {
            count += 1
            break
        }
    %}
assert lex(b"\0") == 0
assert lex(b"one two three\0") == 3
assert lex(b"f0ur\0") == -1

Sentinelle avec vérifications de limites

Cet exemple utilise une sentinelle avec des vérifications de limites pour gérer la fin de l'entrée (cette méthode a été ajoutée dans la version 1.2). Le programme compte les chaînes d'un seul guillemet séparées par des espaces. Le caractère sentinelle est le caractère nul, spécifié avec la configuration re2c:eof = 0;. Comme dans la méthode sentinel, le caractère nul est le dernier caractère de chaque chaîne d'entrée, mais il est autorisé au milieu d'une règle (par exemple, 'aaa\0aa'\0 est une entrée valide, mais 'aaa\0 est une erreur de syntaxe). Des vérifications de limites sont générées dans chaque état qui correspond à un caractère d'entrée, mais elles sont limitées à la branche qui gère le caractère nul. Les vérifications de limites sont de la forme YYLIMIT <= YYCURSOR ou YYLESSTHAN(1) avec l'API générique. Si la condition de vérification est vraie, l'analyseur lexical a atteint la fin de l'entrée et doit s'arrêter (YYFILL est désactivé avec re2c:yyfill:enable = 0; car l'entrée tient dans un seul tampon, voir la section YYFILL avec sentinelle pour un exemple qui utilise YYFILL). Atteindre la fin de l'entrée ouvre trois possibilités : si l'analyseur lexical est dans l'état initial, il correspondra à la règle de fin d'entrée $, sinon il pourra revenir en arrière vers une règle précédemment correspondue (y compris la règle par défaut *) ou aller à un état par défaut, provoquant -Wundefined-control-flow.

# re2py $INPUT -o $OUTPUT
# attend une chaîne terminée par un nul
def lex(yyinput):
    yycursor = 0
    yylimit = len(yyinput) - 1 # nul de terminaison non inclus
    count = 0
    while True: %{
        re2c:yyfill:enable = 0;
        re2c:eof = 0;
        re2c:indent:top = 2;
        str = ['] ([^'\\] | [\\][^])* ['];
        *    { return -1 }
        $    { return count }
        [ ]+ { break }
        str  {
            count += 1
            break
        }
    %}
def test(str, count):
    # nul de terminaison non inclus dans `lim`
    assert count == lex(str)
test(b"\0", 0);
test(b"'qu\0tes' 'are' 'fine: \\'' \0", 3);
test(b"'unterminated\\'\0", -1)

Vérifications de limites avec remplissage

Cet exemple utilise des vérifications de limites avec remplissage pour gérer la fin de l'entrée (cette méthode est activée par défaut). Le programme compte les chaînes d'un seul guillemet séparées par des espaces. Un remplissage de caractères nuls YYMAXFILL est ajouté à la fin de l'entrée, où la valeur YYMAXFILL est générée automatiquement avec un bloc max. Il n'est pas nécessaire d'utiliser le caractère nul pour le remplissage --- n'importe quels caractères peuvent être utilisés tant qu'ils ne forment pas

ormation d'un suffixe de lexème valide (dans cet exemple, le remplissage ne doit pas contenir de guillemets simples, car ils peuvent être confondus avec un suffixe de chaîne entre guillemets simples). Il existe une règle « stop » qui correspond au premier caractère de remplissage (null) et termine le lexer (notez qu'elle vérifie si null est au début du remplissage, sinon c'est une erreur de syntaxe). Les vérifications de limites ne sont générées que dans certains états déterminés par les composantes fortement connexes de l'automate sous-jacent. Les vérifications ont la forme (YYLIMIT - YYCURSOR) < n ou YYLESSTHAN(n) avec une API générique, où n est le nombre minimum de caractères nécessaires au lexer pour continuer (cela signifie également que la prochaine vérification de limite se produira dans au plus n caractères). Si la condition de vérification est vraie, le lexer a atteint la fin de l'entrée et appellera YYFILL(n) qui doit soit fournir au moins n caractères d'entrée, soit ne pas retourner. Dans cet exemple, YYFILL échoue toujours et termine le lexer avec une erreur (ce qui est acceptable car l'entrée tient dans un seul tampon). Voir la section YYFILL avec remplissage pour un exemple qui recharge le tampon d'entrée avec YYFILL.

# re2py $INPUT -o $OUTPUT
%{max %}
def lex(yyinput):
    yycursor = 0
    yylimit = len(yyinput)
    count = 0
    while True: %{
        re2c:YYFILL = "return -1";
        re2c:indent:top = 2;
        str = ['] ([^'\\] | [\\][^])* ['];
        [\x00] {
            # vérifier que c'est le sentinelle, pas un null inattendu
            return count if yycursor == yylimit - YYMAXFILL + 1 else -1
        }
        str {
            count += 1
            break
        }
        [ ]+ { break }
        *    { return -1 }
    %}
def test(str, count):
    padded_str = str + (b"\0" * YYMAXFILL)
    assert lex(padded_str) == count
test(b"", 0)
test(b"'unterminated\\'", -1)
test(b"'qu\x00tes' 'are' 'fine: \\'' ", 3)
test(b"'unexpected \x00 null", -1)

Vérifications personnalisées

Cet exemple utilise une méthode personnalisée de gestion de la fin de fichier basée sur l'API générique. Le programme compte les chaînes entre guillemets simples séparées par des espaces. C'est le même exemple que le sentinelle, sauf que l'entrée n'est pas terminée par null. Pour compenser l'absence d'un caractère sentinelle à la fin de l'entrée, YYPEEK est redéfini pour effectuer une vérification de limites avant de lire le prochain caractère d'entrée. Ceci est inefficace car les vérifications sont effectuées très souvent. Si la condition de vérification échoue, YYPEEK retourne le caractère réel, sinon il retourne un faux caractère sentinelle.

# re2py $INPUT -o $OUTPUT
# attend une chaîne sans null de terminaison
def lex(str):
    cur = 0
    lim = len(str)
    count = 0
    while True: %{
        re2c:api = generic;
        re2c:YYPEEK = "str[cur] if cur < lim else 0";
        re2c:YYSKIP = "cur += 1";
        re2c:yyfill:enable = 0;
        re2c:indent:top = 2;
        *      { return -1 }
        [\x00] { return count }
        [ ]+   { break }
        [a-z]+ {
            count += 1
            break
        }
    %}
assert lex(b"") == 0
assert lex(b"one two three") == 3
assert lex(b"f0ur") == -1

RECHARGEMENT DU TAMPON

Le besoin de mise en mémoire tampon apparaît lorsque l'entrée ne peut pas être mappée en mémoire en une seule fois : soit elle est trop grande, soit elle arrive sous forme de flux (comme lors de la lecture d'une socket). La technique habituelle dans de tels cas est d'allouer un tampon de mémoire de taille fixe et de traiter l'entrée par morceaux qui tiennent dans le tampon. Lorsque le morceau courant est traité, il est déplacé et de nouvelles données sont chargées. En pratique, c'est un peu plus complexe, car l'état du lexer ne consiste pas en une seule position d'entrée, mais en un ensemble de positions interdépendantes :

  • curseur : le prochain caractère d'entrée à lire (YYCURSOR dans l'API de pointeur C ou YYSKIP/YYPEEK dans l'API générique)
  • limite : la position après le dernier caractère d'entrée disponible (YYLIMIT dans l'API de pointeur C, gérée implicitement par YYLESSTHAN dans l'API générique)
  • marqueur : la position de la correspondance la plus récente, le cas échéant (YYMARKER dans l'API par défaut ou YYBACKUP/YYRESTORE dans l'API générique)
  • jeton : le début du lexème courant (implicite dans l'API re2py, car il n'est pas nécessaire pour le fonctionnement normal du lexer et peut être défini et mis à jour par l'utilisateur)
  • marqueur de contexte : la position du contexte arrière (YYCTXMARKER dans l'API de pointeur C ou YYBACKUPCTX/YYRESTORECTX dans l'API générique)
  • variables de balise : positions de sous-correspondance (définies avec les blocs stags et mtags et les primitives d'API générique YYSTAGP/YYSTAGN/YYMTAGP/YYMTAGN)

Tous ces éléments ne sont pas utilisés dans tous les cas, mais s'ils sont utilisés, ils doivent être mis à jour par YYFILL. Toutes les positions actives sont contenues dans le segment entre le jeton et le curseur, par conséquent tout ce qui se trouve entre le début du tampon et le jeton peut être jeté, le segment du jeton jusqu'à la limite doit être déplacé au début du tampon, et l'espace libre à la fin du tampon doit être rempli avec de nouvelles données. Afin d'éviter des appels fréquents à YYFILL, il est préférable de charger autant de caractères d'entrée que possible (même si moins de caractères pourraient suffire à reprendre le lexer). Les détails de l'implémentation de YYFILL diffèrent légèrement en fonction de la méthode de gestion de la fin de fichier utilisée : le cas de la règle EOF est quelque peu plus simple que le cas de la vérification de limites avec remplissage. Notez également que si l'option -f --storable-state est utilisée, YYFILL a une sémantique légèrement différente (décrite dans la section sur l'état stockable).

YYFILL avec sentinelle

Si la règle EOF est utilisée, YYFILL est une primitive de type fonction qui n'accepte aucun argument et retourne une valeur qui est vérifiée par rapport à zéro. L'invocation de YYFILL est déclenchée par la condition YYLIMIT <= YYCURSOR dans l'API de pointeur C et YYLESSTHAN() dans l'API générique. Une valeur de retour non nulle signifie que YYFILL a échoué. Un appel réussi à YYFILL doit fournir au moins un caractère et ajuster les positions d'entrée en conséquence. La limite doit toujours être définie à un après la dernière position d'entrée dans le tampon, et le caractère à la position limite doit être le symbole sentinelle spécifié par re2c:eof configuration. Les schémas ci-dessous montrent les emplacements relatifs des positions d'entrée dans le tampon avant et après l'appel YYFILL (le symbole sentinelle est marqué par #, et le deuxième schéma montre le cas où il n'y a pas assez d'entrée pour remplir tout le tampon).

             tampon       jeton    marqueur       limite,
                                                  curseur
>-A------------B---------C-------------D------------E#->

Voici un exemple de programme qui lit le fichier d'entrée input.txt par morceaux de 4096 octets et utilise la règle EOF.

# re2py $INPUT -o $OUTPUT
from enum import Enum
import os
BUFSIZE = 4096
class State:
    def __init__(self, fname):
        self.file = open(fname, "rb")
        self.yyinput = bytearray(BUFSIZE)
        self.yylimit = BUFSIZE - 1 # exclure le null de terminaison
        self.yycursor = self.yylimit
        self.yymarker = self.yylimit
        self.token = self.yylimit
        self.eof = False
    def __del__(self):
        self.file.close()
class Status(Enum):
    OK = 0
    EOF = 1
    LONG_LEXEME = 2
def fill(st):
    if st.eof:
        return Status.EOF
    # Erreur : lexème trop long. En réalité, on pourrait réallouer un tampon plus grand.
    if st.token < 1:
        return Status.LONG_LEXEME
    # Décalage du contenu du tampon (ignorer tout jusqu'au jeton courant).
    st.yyinput = st.yyinput[st.token:st.yylimit]
    st.yycursor -= st.token;
    st.yymarker -= st.token;
    st.yylimit -= st.token;
    st.token = 0;
    # Remplir l'espace libre à la fin du tampon avec de nouvelles données du fichier.
    bytes = st.file.read(BUFSIZE - st.yylimit - 1) # -1 pour le sentinelle
    if not bytes:
        st.eof = True # fin du fichier
    else:
        st.yylimit += len(bytes);
        st.yyinput += bytes
    st.yyinput += b'\0' # ajouter le sentinelle
    return Status.OK
def lex(yyrecord, count):
    while True:
        yyrecord.token = yyrecord.yycursor
    %{
        re2c:api = record;
        re2c:define:YYFILL = "fill(yyrecord) == Status.OK";
        re2c:eof = 0;
        re2c:indent:top = 2;
        str = ['] ([^'\\] | [\\][^])* ['];
        *    { return -1 }
        $    { return count }
        [ ]+ { break }
        str  {
            count += 1
            break
        }
    %}
def main():
    fname = "input"
    # Préparer le fichier d'entrée.
    f = open(fname, "w")
    for i in range(BUFSIZE):
        f.write("'qu\0tes' 'are' 'fine: \\'' ")
    f.close()
    # Exécuter le lexer sur le fichier préparé.
    st = State(fname)
    assert lex(st, 0) == 3 * BUFSIZE
    # Nettoyage.
    os.remove(fname)
if __name__ == '__main__':
    main()

YYFILL avec remplissage

Dans le cas par défaut (lorsque la règle EOF n'est pas utilisée), YYFILL est une primitive de type fonction qui accepte un seul argument et ne retourne aucune valeur. L'invocation de YYFILL est déclenchée par la condition (YYLIMIT - YYCURSOR) < n dans l'API de pointeur C et YYLESSTHAN(n) dans l'API générique. L'argument passé à YYFILL est le nombre minimum de caractères qui doivent être fournis. S'il ne parvient pas à le faire, YYFILL ne doit pas retourner au lexer (pour cette raison, il est préférable de l'implémenter comme une macro qui retourne de la fonction appelante en cas d'échec). En cas d'invocation réussie de YYFILL, la position limite doit être définie soit à un après la dernière position d'entrée dans le tampon, soit à la fin du remplissage YYMAXFILL (dans le cas où YYFILL a réussi à lire au moins n caractères, mais pas assez pour remplir tout le tampon). Les schémas ci-dessous montrent les positions relatives des positions d'entrée dans le tampon avant et après l'invocation de YYFILL (le remplissage YYMAXFILL dans le deuxième schéma est marqué par des symboles #).

             >-A------------B---------C-----D-------E---F--------G->
             tampon       jeton

FEATURES

  • Multiple blocks

Buffer padding and bounds checking

The re2py lexer uses a buffer to store input data. The buffer is accessed using three pointers: yycursor, yymarker, and yylimit.

  • yycursor: points to the current position in the input buffer.

  • yymarker: points to the beginning of the current token. The distance between yymarker and yycursor is the length of the current token.

  • yylimit: points to the end of the input buffer. Any access beyond yylimit is forbidden.

The lexer reads data from the input source in chunks. When the lexer reaches the end of the buffer (yycursor reaches yylimit), it needs to refill the buffer. The lexer must have at least one empty byte at the end of the buffer to check for the end of the input file. This requires padding the buffer with a sentinel value (e.g., null byte). The size of the padding is defined by the YYMAXFILL macro.

If the lexer needs to read more than YYMAXFILL bytes to complete a token, it indicates an error (e.g., a very long token). The program must handle this situation, for example, by reallocating a larger buffer or returning an error.

Buffer:      +------------------------------------------+
             |                                          |
             |               ^                          |
             +------------------------------------------+
                             cursor, marker, limit

             A------------B---------C-----D-------E---F--------G
Buffer:      +------------------------------------------+
             | A------------B---------C-----D-------E-F |
             |                          ^             ^ |

from enum import Enum
import os
BUFSIZE = 4096
%{max %}
class State:
    def __init__(self, fname):
        self.file = open(fname, "rb")
        self.yyinput = bytearray(BUFSIZE)
        self.yylimit = BUFSIZE - YYMAXFILL
        self.yycursor = self.yylimit
        self.yymarker = self.yylimit
        self.token = self.yylimit
        self.eof = False
    def __del__(self):
        self.file.close()
class Status(Enum):
    OK = 0
    EOF = 1
    LONG_LEXEME = 2
def fill(st, need):
    if st.eof:
        return Status.EOF
    # Erreur: lexème trop long. Dans la vie réelle, on pourrait réallouer un buffer plus grand.
    if st.token < need:
        return Status.LONG_LEXEME
    # Décalage du contenu du buffer (suppression de tout ce qui précède le jeton courant).
    st.yyinput = st.yyinput[st.token:st.yylimit]
    st.yycursor -= st.token;
    st.yymarker -= st.token;
    st.yylimit -= st.token;
    st.token = 0;
    # Remplissage de l'espace libre à la fin du buffer avec de nouvelles données du fichier.
    bytes = st.file.read(BUFSIZE - st.yylimit - 1) # -1 pour le sentinelle
    if not bytes:
        st.eof = True # fin du fichier
        st.yylimit += YYMAXFILL
        st.yyinput += b"\0" * YYMAXFILL
    else:
        st.yylimit += len(bytes);
        st.yyinput += bytes
    return Status.OK
def lex(yyrecord):
    count = 0
    while True:
        yyrecord.token = yyrecord.yycursor
    %{
        re2c:api = record;
        re2c:YYFILL = "if fill(yyrecord, @@) != Status.OK: return -1";
        re2c:indent:top = 2;
        str = ['] ([^'\\] | [\\][^])* ['];
        [\x00] {
            # Vérification qu'il s'agit du sentinelle, et non d'un nul inattendu.
            return count if yyrecord.token == yyrecord.yylimit - YYMAXFILL else -1
        }
        str {
            count += 1
            break
        }
        [ ]+ { break }
        *    { return -1 }
    %}
def main():
    fname = "input"
    # Préparation du fichier d'entrée.
    f = open(fname, "w")
    for i in range(BUFSIZE):
        f.write("'qu\0tes' 'are' 'fine: \\'' ")
    f.close()

Plusieurs blocs

Il est parfois nécessaire d'avoir plusieurs lexers interdépendants (par exemple, s'il existe une machine à états de haut niveau qui passe d'un mode de lexer à un autre). Cela peut être implémenté en utilisant plusieurs blocs re2py connectés. Une autre option est d'utiliser des conditions de démarrage.

L'implémentation des connexions entre les blocs dépend de la langue cible. Dans les langages qui ont l'instruction goto (comme C/C++ et Go), on peut avoir tous les blocs dans une seule fonction, chacun d'eux étant préfixé par une étiquette. La transition d'un bloc à un autre est un simple goto. Dans les langages qui n'ont pas de goto (comme Rust), il est nécessaire d'utiliser une boucle avec un switch sur une variable d'état, similaire à la boucle/switch yystate générée par re2py, ou d'encapsuler chaque bloc dans une fonction et d'utiliser des appels de fonction.

L'exemple ci-dessous utilise plusieurs blocs pour analyser des nombres binaires, octaux, décimaux et hexadécimaux. Chaque base a son propre bloc. Le bloc initial détermine la base et distribue vers les autres blocs. Les configurations communes sont définies dans un bloc séparé au début du programme ; elles sont héritées par les autres blocs.

# re2py $INPUT -o $OUTPUT
class State:
    def __init__(self, str):
        self.yyinput = str
        self.yycursor = 0
        self.yymarker = 0
# Définitions re2c communes partagées entre toutes les fonctions.
%{
    re2c:api = record;
    re2c:yyrecord = st;
    re2c:yyfill:enable = 0;
    re2c:indent:top = 2;
%}
def parse_u32(str):
    st = State(str)
%{local
    re2c:indent:top = 1;
    '0b' / [01]        { return parse_bin(st) }
    "0"                { return parse_oct(st) }
    "" / [1-9]         { return parse_dec(st) }
    '0x' / [0-9a-fA-F] { return parse_hex(st) }
    *                  { return None }
%}
def parse_bin(st):
    n = 0
    while True: %{
        [01] {
            n = n * 2 + (st.yyinput[st.yycursor - 1] - 48)
            break
        }
        * { return n }
    %}
def parse_oct(st):
    n = 0
    while True: %{
        [0-7] {
            n = n * 8 + (st.yyinput[st.yycursor - 1] - 48)
            break
        }
        * { return n }
    %}
def parse_dec(st):
    n = 0
    while True: %{
        [0-9] {
            n = n * 10 + (st.yyinput[st.yycursor - 1] - 48)
            break
        }
        * { return n }
    %}
def parse_hex(st):
    n = 0
    while True: %{
        [0-9] {
            n = n * 16 + (st.yyinput[st.yycursor - 1] - 48)
            break

        [a-f] {

            break
        }
        [A-F] {
            n = n * 16 + (st.yyinput[st.yycursor - 1] - 55)
            break
        }
        * { return n }
    %}

Conditions de démarrage

Les conditions de démarrage sont activées avec l'option --start-conditions. Elles offrent un moyen d'encoder plusieurs automates interdépendants au sein du même bloc re2py.

Chaque condition correspond à un automate unique et porte un nom spécifique défini par l'utilisateur ainsi qu'un numéro interne unique défini par re2py. Les numéros sont utilisés pour passer d'une condition à l'autre : le code généré utilise les primitives YYGETCOND et YYSETCOND pour obtenir la condition actuelle ou la définir à un nombre donné. Utilisez le bloc conditions, l'option --header ou la configuration re2c:header pour générer des identificateurs numériques de conditions. La configuration re2c:cond:enumprefix spécifie le préfixe identificateur généré.

En mode condition, chaque règle doit être préfixée par une liste de noms de conditions séparés par des virgules entre crochets angulaires, ou par un joker <*> pour désigner toutes les conditions. La syntaxe des règles est étendue comme suit :

< liste-conditions > expression-régulière code
Une règle qui est fusionnée à chaque condition de la liste-conditions. Elle correspond à une expression-régulière et exécute le code associé.
< liste-conditions > expression-régulière => condition code
Une règle qui est fusionnée à chaque condition de la liste-conditions. Elle correspond à une expression-régulière, définit la condition courante à condition et exécute le code associé.
< liste-conditions > expression-régulière :=> condition
Une règle qui est fusionnée à chaque condition de la liste-conditions. Elle correspond à une expression-régulière et transitionne immédiatement vers condition (il n'y a pas d'action sémantique).
< liste-conditions > !action code
Une règle qui lie le code à l'endroit défini par action dans chaque condition de la liste-conditions (voir la section actions pour les différents types d'actions).
<! liste-conditions > code
Une règle qui ajoute le code en préfixe des actions sémantiques de toutes les règles pour chaque condition de la liste-conditions. Cette syntaxe est dépréciée et l'action !pre_rule devrait être utilisée à la place (elle fait exactement la même chose).
< > code
Une règle qui crée une condition d'entrée spéciale avec le numéro zéro et le nom "0" qui exécute le code avant de sauter vers d'autres conditions. Cette syntaxe est dépréciée et l'action !entry devrait être utilisée à la place (elle offre un contrôle plus fin, car le code peut être spécifié par condition, et on peut sauter directement au début de la condition sans passer par la distribution des conditions).
< > => condition code
Identique à la règle précédente, sauf qu'elle définit la prochaine condition.
< > :=> condition
Identique à la règle précédente, sauf qu'elle n'a pas de code associé et saute immédiatement vers condition.

Le code généré par re2py pour les conditions dépend si re2py utilise l'approche goto/label ou l'approche boucle/switch pour encoder les automates.

Dans les langages qui ont l'instruction goto (comme C/C++ et Go), les conditions sont naturellement implémentées comme des blocs de code préfixés par des étiquettes de la forme yyc_<cond>, où cond est un nom de condition (le préfixe de l'étiquette peut être modifié avec re2c:cond:prefix). Les transitions entre les conditions sont implémentées à l'aide de goto et d'étiquettes de conditions. Avant toutes les conditions, re2py génère un switch initial sur YYGETSTATE qui saute à l'état de départ de la condition actuelle. Les règles de raccourci :=> contournent le switch initial et sautent directement à la condition spécifiée (re2c:cond:goto peut être utilisé pour modifier le comportement par défaut). Les règles avec des actions sémantiques ne sautent pas automatiquement à la condition suivante ; cela doit être fait par le code d'action défini par l'utilisateur.

Dans les langages qui n'ont pas de goto (comme Rust), re2py réutilise la variable yystate pour stocker les numéros de condition. Chaque condition reçoit un identifiant numérique égal au nombre de son état de départ, et un switch entre conditions n'est pas différent d'un switch entre états d'un DFA d'une seule condition. Il n'y a pas besoin de switch de condition initial séparé. (Étant donné que la même approche est utilisée pour implémenter des états stockables, YYGETCOND/YYSETCOND sont redondants si des états stockables et des conditions sont utilisés).

Le programme ci-dessous utilise des conditions de démarrage pour analyser des nombres binaires, octaux, décimaux et hexadécimaux. Il y a un seul bloc où chaque base a sa propre condition, et la condition initiale est connectée à toutes. La variable définie par l'utilisateur cond stocke le numéro de la condition actuelle ; elle est initialisée au numéro de la condition initiale générée avec conditions<

/b> bloc.

# re2py $INPUT -o $OUTPUT -c
%{conditions %}
def parse_u32(yyinput):
    yycursor = 0
    yycond = YYC_INIT
    num = 0
    while True: %{
        re2c:yyfill:enable = 0;
        re2c:indent:top = 2;
        <INIT> '0b' / [01]        :=> BIN
        <INIT> "0"                :=> OCT
        <INIT> "" / [1-9]         :=> DEC
        <INIT> '0x' / [0-9a-fA-F] :=> HEX
        <INIT> * { return None }
        <BIN> [01] {
            num = num * 2 + (yyinput[yycursor - 1] - 48)
            break
        }
        <OCT> [0-7] {
            num = num * 8 + (yyinput[yycursor - 1] - 48)
            break
        }
        <DEC> [0-9] {
            num = num * 10 + (yyinput[yycursor - 1] - 48)
            break
        }
        <HEX> [0-9] {
            num = num * 16 + (yyinput[yycursor - 1] - 48)
            break
        }
        <HEX> [a-f] {
            num = num * 16 + (yyinput[yycursor - 1] - 87)
            break
        }
        <HEX> [A-F] {
            num = num * 16 + (yyinput[yycursor - 1] - 55)
            break
        }
        <BIN, OCT, DEC, HEX> * { return num }
    %}

État stockable

Avec l'option --storable-state, re2py génère un analyseur lexical qui peut stocker son état actuel, retourner à l'appelant, puis reprendre les opérations exactement là où il s'est arrêté. Le mode de fonctionnement par défaut dans re2py est un modèle de type "pull", dans lequel l'analyseur lexical "tire" plus d'entrée quand il en a besoin. Ceci peut être inacceptable dans les cas où l'entrée est disponible pièce par pièce (par exemple, si l'analyseur lexical est invoqué par l'analyseur syntaxique, ou si le programme d'analyseur lexical communique via un protocole socket avec un autre programme qui doit attendre une réponse de l'analyseur lexical avant de transmettre le message suivant). La fonctionnalité d'état stockable est destinée précisément à de tels cas : elle permet de générer des analyseurs lexicaux qui fonctionnent selon un modèle de type "push". Lorsque l'analyseur lexical a besoin de plus d'entrée, il stocke son état et retourne à l'appelant. Plus tard, lorsque plus d'entrée est disponible, l'appelant reprend l'analyseur lexical exactement là où il s'est arrêté. Il y a quelques changements nécessaires par rapport au modèle "pull" :

  • Définir les primitives YYSETSTATE() et YYGETSTATE(state).
  • Définir les variables yych, yyaccept (si utilisé) et state comme faisant partie de l'état persistant de l'analyseur. La variable state doit être initialisée à -1.
  • YYFILL doit retourner au programme extérieur au lieu d'essayer de fournir plus d'entrée. Le code de retour doit indiquer que l'analyseur a besoin de plus d'entrée.
  • Le programme extérieur doit reconnaître les situations où l'analyseur a besoin de plus d'entrée et répondre de manière appropriée.
  • Utiliser éventuellement le bloc getstate pour générer un commutateur YYGETSTATE détaché de l'analyseur principal. Cela ne fonctionne que pour les langages qui ont goto (pas en mode --loop-switch).
  • Utiliser re2c:eof et la méthode du sentinelle avec vérifications de limites pour gérer la fin de l'entrée. La méthode basée sur le remplissage peut ne pas fonctionner car il est difficile de savoir quand ajouter le remplissage : la fin actuelle de l'entrée peut ne pas être la fin ultime de l'entrée, et ajouter le remplissage trop tôt peut couper un lexème gourmand partiellement lu. De plus, en raison de la logique du programme de haut niveau, obtenir plus d'entrée peut dépendre du traitement du lexème à la fin du tampon (qui est déjà bloqué en raison de la condition de fin d'entrée).

Voici un exemple d'analyseur lexical en mode "push" qui simule la lecture de paquets depuis une socket. L'analyseur lexical boucle jusqu'à ce qu'il rencontre la fin de l'entrée et retourne à la fonction appelante. La fonction appelante fournit plus d'entrée en "envoyant" le paquet suivant et reprend l'analyse lexicale. Ce processus s'arrête lorsque tous les paquets ont été envoyés, ou en cas d'erreur.

# re2py $INPUT -o $OUTPUT -f
from enum import Enum
import os
# Utiliser un petit tampon pour couvrir le cas où un lexème ne rentre pas.
# Dans la vie réelle, utiliser un tampon plus grand.
BUFSIZE = 10
DEBUG = False
class State:
    def __init__(self, file):
        self.file = file
        self.yyinput = bytearray(BUFSIZE)
        self.yylimit = BUFSIZE - 1 # exclure le null terminateur
        self.yycursor = self.yylimit
        self.yymarker = self.yylimit
        self.token = self.yylimit
        self.yystate = -1
class Status(Enum):
    END = 0
    READY = 1
    WAITING = 2
    BIG_PACKET = 3
    BAD_PACKET = 4
def fill(st):
    # Erreur : lexème trop long. Dans la vie réelle, on pourrait réallouer un tampon plus grand.
    if st.token < 1:
        return Status.BIG_PACKET
    # Décaler le contenu du tampon (ignorer tout jusqu'au jeton actuel).
    st.yyinput = st.yyinput[st.token:st.yylimit]
    st.yycursor -= st.token;
    st.yymarker -= st.token;
    st.yylimit -= st.token;
    st.token = 0;
    # Remplir l'espace libre à la fin du tampon avec de nouvelles données du fichier.
    bytes = st.file.read(BUFSIZE - st.yylimit - 1) # -1 pour le sentinelle
    if bytes:
        st.yylimit += len(bytes);
        st.yyinput += bytes
    st.yyinput += b'\0' # ajouter le sentinelle
    return Status.READY
def lex(yyrecord, recv):
    while True:
        yyrecord.token = yyrecord.yycursor
    %{
        re2c:api = record;
        re2c:YYFILL = "return Status.WAITING, recv";
        re2c:eof = 0;
        re2c:indent:top = 2;
        packet = [a-z]+[;];
        *      { return Status.BAD_PACKET, recv }
        $      { return Status.END, recv }
        packet {
            recv += 1
            break
        }
    %}
def test(packets, expect):
    # Créer un pipe (ouvrir le même fichier en lecture et écriture).
    fname = "pipe"
    fw = open(fname, "wb")
    fr = open(fname, "rb")
    # Initialiser l'état de l'analyseur lexical
    st = State(fr)
    # Boucle principale. Le tampon contient des données incomplètes qui apparaissent paquet par
    # paquet. Lorsque l'analyseur lexical a besoin de plus d'entrée, il sauvegarde son état interne et
    # retourne à l'appelant qui doit fournir plus d'entrée et reprendre l'analyse lexicale.
    send = 0
    recv = 0
    while True:
        status, recv = lex(st, recv)
        if status == Status.END:
            if DEBUG: print("terminé : {} paquets reçus".format(recv))
            break
        elif status == Status.WAITING:
            if DEBUG: print("attente...");
            if send < len(packets):
                if DEBUG: print("paquet envoyé {}: {}".format(send, packets[send]))
                fw.write(packets[send])
                fw.flush()
                send += 1
            status = fill(st)
            if DEBUG: print("file d'attente : '{}', état : {}".format(st.yyinput, status))
            if status == Status.BIG_PACKET:
                if DEBUG: print("erreur : paquet trop grand")
                break
            assert status == Status.READY
        else:
            assert status == Status.BAD_PACKET
            if DEBUG: print("erreur : paquet mal formé")
            break
    # Vérifier les résultats.
    assert status == expect
    if status == Status.END:
        assert recv == send
    # Nettoyage : supprimer le fichier d'entrée.
    fr.close()
    fw.close()
    os.remove(fname)
def main():
    test([], Status.END)
    test([b"zero;", b"one;", b"two;", b"three;", b"four;"], Status.END)
    test([b"zer0;"], Status.BAD_PACKET)
    test([b"goooooooooogle;"], Status.BIG_PACKET)
if __name__ == '__main__':
    main()

Blocs réutilisables

Les blocs réutilisables de la forme /*!rules:re2c[:<name>] ... */ ou %{rules[:<name>] ... %} peuvent être réutilisés un nombre quelconque de fois et combinés avec d'autres blocs re2py. Le <name> est facultatif. Un bloc de règles peut être utilisé dans un bloc ou une directive use. Le code d'un bloc de règles est généré à chaque point d'utilisation.

Les blocs d'utilisation sont définis avec /*!use:re2c[:<name>] ... */ ou %{use[:<name>] ... %}. Le <name> est facultatif : s'il n'est pas spécifié, le bloc de règles associé est le plus récent (qu'il soit nommé ou anonyme). Un bloc d'utilisation peut ajouter ses propres définitions nommées, configurations et règles. Un cas d'utilisation important des blocs d'utilisation est un analyseur lexical qui prend en charge plusieurs encodages d'entrée : le même bloc de règles est réutilisé plusieurs fois avec des configurations spécifiques à l'encodage (voir l'exemple ci-dessous).

La directive d'utilisation dans le bloc !use:<name>; peut être utilisée depuis l'intérieur d'un bloc re2py. Elle fusionne le bloc référencé <name> dans celui en cours. Si certaines des règles et configurations fusionnées entrent en conflit avec celles définies précédemment, les conflits sont résolus de la manière habituelle : la première règle appliquée a la priorité, et la dernière configuration appliquée remplace les précédentes. Une exception concerne les règles spéciales *, $ et (en mode condition) <!>, pour lesquelles une définition locale au bloc remplace toute définition héritée. La directive d'utilisation permet de combiner différents blocs re2py au sein d'un seul bloc (voir l'exemple ci-dessous).

Les blocs nommés et la directive d'utilisation dans le bloc ont été ajoutés dans la version 2.2 de re2py. Depuis cette version, les blocs réutilisables sont autorisés par défaut (aucune option spéciale n'est nécessaire). Avant la version 2.2, le mode réutilisable était activé avec l'option -r --reusable. Avant la version 1.2, les blocs réutilisables ne pouvaient pas être mélangés avec des blocs normaux.

Exemple d'une directive !use

# re2py $INPUT -o $OUTPUT
# Cet exemple montre comment combiner des blocs re2c réutilisables : deux blocs
# ('colors' et 'fish') sont fusionnés en un seul. La règle 'salmon' apparaît
# dans les deux blocs ; le bloc 'fish' a la priorité car il est utilisé
# plus tôt. La règle par défaut * apparaît dans les trois blocs ; la définition locale (non
# héritée) a la priorité.
from enum import Enum
class Ans(Enum):
    COLOR = 1
    FISH = 2
    DUNNO = 3
%{rules:colors
    *                            { raise "ah" }
    "red" | "salmon" | "magenta" { return Ans.COLOR }
%}
%{rules:fish
    *                            { raise "oh" }
    "haddock" | "salmon" | "eel" { return Ans.FISH }
%}
def lex(yyinput):
    yycursor = 0
    yycond = YYC_INIT
%{
    re2c:yyfill:enable = 0;
    re2c:indent:top = 1;
    !use:fish;
    !use:colors;
    * { return Ans.DUNNO } // remplace les règles '*' héritées
%}
assert lex(b"salmon") == Ans.FISH
assert lex(b"what?") == Ans.DUNNO

Extraction de sous-correspondances

re2py propose deux options pour l'extraction de sous-correspondances.

Balises
La première option consiste à utiliser des balises autonomes de la forme @stag ou #mtag, où stag et mtag sont des noms arbitraires définis par l'utilisateur. Les balises sont activées avec l'option -T --tags ou la configuration re2c:tags = 1. Sémantiquement, les balises sont des marqueurs de position : elles peuvent être insérées n'importe où dans une expression régulière, et elles se lient à la position correspondante (ou aux positions correspondantes) dans la chaîne d'entrée. Les S-tags se lient à la dernière position correspondante, et les m-tags se lient à une liste de positions (ils peuvent être utilisés dans des sous-expressions de répétition, où une seule position dans une expression régulière correspond à plusieurs positions dans la chaîne d'entrée). Toutes les balises doivent être définies par l'utilisateur, soit manuellement, soit à l'aide des blocs svars et mvars. S'il existe plus d'une façon de faire correspondre les balises à l'entrée, l'ambiguïté est résolue en utilisant la stratégie de désambiguïsation gloutonne la plus à gauche.
Captures
La seconde option consiste à utiliser des groupes de capture. Ils sont activés avec l'option --captures ou la configuration re2c:captures = 1. Il existe deux variantes pour différentes politiques de désambiguïsation, --leftmost-captures (par défaut) pour la politique gloutonne la plus à gauche, et --posix-captures pour la politique de correspondance la plus longue POSIX. Dans ce mode, toutes les sous-expressions entre parenthèses sont considérées comme des groupes de capture, et un point d'exclamation peut être utilisé pour marquer les groupes non capturants : (! ... ). Avec l'option --invert-captures ou la configuration re2c:invert-captures = 1, le sens du point d'exclamation est inversé. Le nombre de groupes pour la règle de correspondance est stocké dans la variable yynmatch (l'expression régulière entière est le groupe numéro zéro), et les résultats des sous-correspondances sont stockés dans le tableau yypmatch. yynmatch et yypmatch doivent être définis par l'utilisateur, et la taille de yypmatch doit être d'au moins [yynmatch * 2]. Utilisez le bloc maxnmatch pour définir YYMAXNMATCH, une constante égale à la valeur maximale de yynmatch parmi toutes les règles.
Captvars
Une autre façon d'utiliser les groupes de capture est l'option --captvars ou la configuration re2c:captvars = 1. La seule différence avec --captures réside dans la manière dont le code généré stocke les résultats des sous-correspondances : au lieu de yynmatch et yypmatch, re2py génère les variables yytl<k> et yytr<k> pour le k-ième groupe de capture (l'utilisateur doit les déclarer à l'aide d'un bloc svars). Les captures avec variables prennent en charge deux politiques de désambiguïsation : --leftmost-captvars ou re2c:leftmost-captvars = 1 pour la politique gloutonne la plus à gauche (celle par défaut), et --posix-captvars ou re2c:posix-captvars pour la politique de correspondance la plus longue POSIX.

En coulisses, toutes ces options se traduisent par des balises et des Automates Finis Déterministes Etiquetés avec Anticipation (TDFA). L'idée centrale des TDFA est de minimiser la surcharge liée à l'extraction des sous-correspondances. Dans le cas extrême, s'il n'y a pas de balises ou de captures dans une expression régulière, le TDFA est simplement un DFA ordinaire. Si le nombre de balises est modéré, la surcharge est à peine perceptible. Le TDFA généré utilise un certain nombre de variables de balises qui ne correspondent pas directement aux balises : une seule variable peut être utilisée pour différentes balises, et une balise peut nécessiter plusieurs variables pour contenir toutes ses valeurs possibles. Finalement, l'ambiguïté est résolue, et une seule variable finale par balise survit. Les variables de balises doivent être définies à l'aide des blocs stags ou mtags. Si l'état de l'analyseur est stocké, les variables de balises doivent en faire partie. Elles doivent également être mises à jour par YYFILL.

Les S-tags prennent en charge les opérations suivantes :

  • sauvegarder la position d'entrée dans un s-tag : t = YYCURSOR avec l'API de pointeur C ou une opération définie par l'utilisateur YYSTAGP(t) avec l'API générique
  • sauvegarder une valeur par défaut dans un s-tag : t = NULL avec l'API de pointeur C ou une opération définie par l'utilisateur YYSTAGN(t) avec l'API générique
  • copier un s-tag dans un autre : t1 = t2

Les m-tags prennent en charge les opérations suivantes :

  • ajouter une position d'entrée à un m-tag : une opération définie par l'utilisateur YYMTAGP(t) avec l'API par défaut et l'API générique
  • ajouter une valeur par défaut à un m-tag : une opération définie par l'utilisateur YYMTAGN(t) avec l'API par défaut et l'API générique
  • copier un m-tag dans un autre : t1 = t2

Les S-tags peuvent être implémentés comme des valeurs scalaires (pointeurs ou décalages). Les m-tags nécessitent une représentation plus complexe, car ils doivent stocker une séquence de valeurs de balises. La représentation la plus naïve et la moins efficace d'un m-tag est une liste (tableau, vecteur) de valeurs de balises ; une représentation plus efficace consiste à stocker tous les m-tags dans un arbre préfixe représenté comme un tableau de nœuds (v, p), où v est la valeur de la balise et p est un pointeur vers le nœud parent.

Voici un exemple simple d'utilisation de s-tags pour analyser des versions sémantiques composées de trois composants numériques : majeur, mineur, patch (ce dernier est facultatif). Voir ci-dessous pour un exemple plus complexe utilisant YYFILL.

# re2py $INPUT -o $OUTPUT
from collections import namedtuple
SemVer = namedtuple('SemVer', 'major minor patch')
NONE = -1
def parse(yyinput):
    yycursor = 0
    %{
    re2c:yyfill:enable = 0;
    re2c:tags = 1;
    re2c:indent:top = 1;
    num = [0-9]+;
    @t1 num @t2 "." @t3 num @t4 ("." @t5 num)? [\x00] {
        major = int(yyinput[t1:t2])
        minor = int(yyinput[t3:t4])
        patch = int(yyinput[t5:yycursor - 1]) if t5 != NONE else 0
        return SemVer(major, minor, patch)
    }
    * { return None }
%}
assert parse(b"23.34\0") == SemVer(23, 34, 0)
assert parse(b"1.2.99999\0") == SemVer(1, 2, 99999)
assert parse(b"1.a\0") == None

Voici un exemple plus complexe d'utilisation de s-tags avec YYFILL pour analyser un fichier contenant des versions sémantiques séparées par des sauts de ligne. Les variables de balises font partie de l'état de l'analyseur, et elles sont ajustées dans YYFILL comme les autres positions d'entrée. Il est nécessaire pour les s-tags car leurs valeurs sont invalidées après le déplacement du contenu du tampon. Cela peut ne pas être nécessaire dans une implémentation personnalisée où les variables de balises stockent des décalages par rapport au début de la chaîne d'entrée plutôt qu'au tampon, ce qui peut être le cas avec les m-tags.

# re2py $INPUT -o $OUTPUT
from collections import namedtuple
from enum import Enum
import os
BUFSIZE = 4096
SemVer = namedtuple('SemVer', 'major minor patch')
class State:
    def __init__(self, fname):
        self.file = open(fname, "rb")
        self.yyinput = bytearray(BUFSIZE)
        self.yylimit = BUFSIZE - 1 # exclude terminating null
        self.yycursor = self.yylimit
        self.yymarker = self.yylimit
        self.token = self.yylimit
        self.eof = False
        %{stags format = "\n        self.@@ = -1"; %}
    def __del__(self):
        self.file.close()
class Status(Enum):
    OK = 0
    EOF = 1
    LONG_LEXEME = 2
def fill(st):
    if st.eof:
        return Status.EOF
    # Error: lexeme too long. In real life could reallocate a larger buffer.
    if st.token < 1:
        return Status.LONG_LEXEME
    # Shift buffer contents (discard everything up to the current token).
    st.yyinput = st.yyinput[st.token:st.yylimit]
    st.yycursor -= st.token;
    st.yymarker -= st.token;
    st.yylimit -= st.token;
    %{stags format = "\n    if st.@@ != -1: st.@@ -= st.token"; %}
    st.token = 0;
    # Fill free space at the end of buffer with new data from file.
    bytes = st.file.read(BUFSIZE - st.yylimit - 1) # -1 for sentinel
    if not bytes:
        st.eof = True # end of file
    else:
        st.yylimit += len(bytes);
        st.yyinput += bytes
    st.yyinput += b'\0' # append sentinel
    return Status.OK
def lex(st, count):
    vers = []
    while True:
        st.token = st.yycursor
    %{
        re2c:api = record;
        re2c:yyrecord = st;
        re2c:YYFILL = "fill(st) == Status.OK";
        re2c:eof = 0;
        re2c:indent:top = 2;
        re2c:tags = 1;
        num = [0-9]+;
        num @t1 "." @t2 num @t3 ("." @t4 num)? [\n] {
            major = int(st.yyinput[st.token:t1])
            minor = int(st.yyinput[t2:t3])
            patch = int(st.yyinput[t4:st.yycursor - 1]) if t4 != -1 else 0
            vers.append(SemVer(major, minor, patch))
            break
        }
        $ { return vers }
        * { return None }
    %}
def main():
    fname = "input"
    verstr = b"1.22.333\n"
    expect = [SemVer(1, 22, 333)] * BUFSIZE
    # Prepare input file.
    f = open(fname, "wb")
    for i in range(BUFSIZE):
        f.write(verstr)
    f.close()
    # Run lexer on the prepared file.
    st = State(fname)
    assert lex(st, 0) == expect
    # Cleanup.
    os.remove(fname)
if __name__ == '__main__':
    main()

Prise en charge des encodages

Il est nécessaire de comprendre la différence entre points de code et unités de code. Un point de code est un identifiant numérique d'un symbole. Une unité de code est la plus petite unité de stockage dans le texte encodé. Un seul point de code peut être représenté par une ou plusieurs unités de code. Dans un encodage à longueur fixe, tous les points de code sont représentés avec le même nombre d'unités de code. Dans un encodage à longueur variable, les points de code peuvent être représentés avec un nombre différent d'unités de code. Notez que la règle « tout » [^] correspond à n'importe quel point de code, mais pas nécessairement à n'importe quelle unité de code (la seule façon de faire correspondre n'importe quelle unité de code, quel que soit l'encodage, est la règle par défaut *). Le lexer généré fonctionne avec un flux d'unités de code : yych stocke une unité de code et YYCTYPE est le type d'unité de code. Les expressions régulières, en revanche, sont spécifiées en termes de points de code. Lorsque re2py compile les expressions régulières en automates, il traduit les points de code en unités de code. Ce n'est généralement pas un mappage simple : dans les encodages à longueur variable, une seule plage de points de code peut être traduite en un graphe complexe d'unités de code. Les encodages suivants sont pris en charge :

  • ASCII (activé par défaut). C'est un encodage à longueur fixe avec un espace de code [0-255] et des points de code et des unités de code d'un octet.
  • EBCDIC (activé avec --ebcdic ou re2c:encoding:ebcdic). C'est un encodage à longueur fixe avec un espace de code [0-255] et des points de code et des unités de code d'un octet.
  • UCS2 (activé avec --ucs2 ou re2c:encoding:ucs2). C'est un encodage à longueur fixe avec un espace de code [0-0xFFFF] et des points de code et des unités de code de 2 octets.
  • UTF8 (activé avec --utf8 ou re2c:encoding:utf8). C'est un encodage Unicode à longueur variable. La taille de l'unité de code est d'un octet. Les points de code sont représentés par 1 à 4 unités de code.
  • UTF16 (activé avec --utf16 ou re2c:encoding:utf16). C'est un encodage Unicode à longueur variable. La taille de l'unité de code est de 2 octets. Les points de code sont représentés par 1 à 2 unités de code.
  • UTF32 (activé avec --utf32 ou re2c:encoding:utf32). C'est un encodage Unicode à longueur fixe avec un espace de code [0-0x10FFFF] et des points de code et des unités de code de 4 octets.

Le fichier d'inclusion include/unicode_categories.re fournit des définitions re2py pour les catégories Unicode standard.

L'option --input-encoding spécifie l'encodage du fichier source, qui peut être utilisé pour activer les littéraux Unicode dans les expressions régulières. Par exemple, --input-encoding utf8 indique à re2py que le fichier source est en UTF8 (cela diffère de --utf8 qui définit l'encodage du texte d'entrée). L'option --encoding-policy spécifie la manière dont re2py gère les substituts Unicode (points de code dans la plage [0xD800-0xDFFF]).

Voici un exemple de lexer pour des identifiants Unicode encodés en UTF8.

# re2py $INPUT -o $OUTPUT --utf8
%{include "unicode_categories.re" %}
def lex(yyinput):
    yycursor = 0
%{
    re2c:yyfill:enable = 0;
    re2c:indent:top = 1;
    // Simplified "Unicode Identifier and Pattern Syntax"
    // (see https://unicode.org/reports/tr31)
    id_start    = L | Nl | [$_];
    id_continue = id_start | Mn | Mc | Nd | Pc | [\u200D\u05F3];
    identifier  = id_start id_continue*;
    identifier { return True }
    *          { return False }
%}
assert lex(bytes("_Ыдентификатор\0", "utf-8"))

Fichiers d'inclusion

re2py permet d'inclure d'autres fichiers à l'aide d'un bloc de la forme /*!include:re2c FILE */ ou %{include FILE %}, ou d'une directive dans un bloc !include FILE ;, où FILE est un chemin vers le fichier à inclure. re2py recherche les fichiers d'inclusion dans le répertoire du fichier incluant et dans les emplacements d'inclusion, qui peuvent être spécifiés avec l'option -I. Les blocs/directives d'inclusion dans re2py fonctionnent de la même manière que le #include de C/C++ : le contenu de FILE est copié tel quel à la place du bloc/de la directive. Les fichiers d'inclusion peuvent contenir d'autres inclusions. Utilisez l'option --depfile pour suivre les dépendances de construction du fichier de sortie par rapport aux fichiers d'inclusion. re2py fournit certains fichiers d'inclusion prédéfinis qui se trouvent dans le sous-répertoire include/ du projet. Ces fichiers contiennent des définitions qui peuvent être utiles à d'autres projets (telles que les catégories Unicode) et forment une sorte de bibliothèque standard pour re2py. Ci-dessous un exemple d'utilisation de fichiers d'inclusion.

Fichier d'inclusion 1 (definitions.py)

from enum import Enum

Fichiers d'en-tête

re2py permet de générer un fichier d'en-tête à partir du fichier .re d'entrée à l'aide de l'option --header ou de la configuration re2c:header et des paires de blocs /*!header:re2c:on*/ et /*!header:re2c:off*/, ou %{header:on%} et %{header:off%}. Le premier bloc marque le début du fichier d'en-tête et le second bloc en marque la fin. Tout ce qui se trouve entre ces blocs est traité par re2py, et le code généré est écrit dans le fichier spécifié avec l'option --header ou la configuration re2c:header (ou stdout si aucune option ni configuration n'est utilisée). Un fichier d'en-tête auto-généré peut être nécessaire dans les cas où re2py est utilisé pour générer des définitions qui doivent être visibles à partir d'autres unités de traduction.

Programmes squelettes

Avec l'option -S, --skeleton, re2py ignore tout le code non-re2py et génère un programme C autonome qui peut être compilé et exécuté. Le programme se compose du code du lexer et des données d'entrée. Pour chaque automate fini déterministe (DFA) construit (bloc ou condition), re2py génère un lexer autonome et deux fichiers : un fichier .input avec des chaînes dérivées du DFA et un fichier .keys avec les résultats de correspondance attendus. Le programme exécute chaque lexer sur le fichier .input correspondant et compare les résultats aux attentes. Les programmes squelettes sont très utiles pour plusieurs raisons :

  • Ils peuvent vérifier la correction de diverses optimisations re2py (les données sont générées tôt dans le processus, avant toute transformation du DFA).
  • La génération d'un ensemble de données d'entrée avec une bonne couverture peut être utile à la fois pour les tests et les benchmarks.
  • La génération de programmes exécutables autonomes permet d'obtenir des cas de test minimisés (le code original peut être volumineux ou avoir de nombreuses dépendances).

La difficulté de générer des données d'entrée est que, pour tous les cas sauf les plus triviaux, le nombre de chaînes d'entrée possibles est trop grand (même si la longueur de la chaîne est limitée). re2py résout cette difficulté en générant suffisamment de chaînes pour couvrir presque toutes les transitions du DFA. Il utilise l'algorithme suivant. Premièrement, il construit un squelette du DFA. Pour les encodages avec une taille d'unité de code d'un octet (tels que ASCII, UTF-8 et EBCDIC), le squelette est juste une copie exacte du DFA original. Pour les encodages avec des unités de code multibits, le squelette est une copie du DFA avec certaines transitions omises : à savoir, re2py prend au maximum 256 unités de code pour chaque plage continue disjointes qui correspond à une transition de DFA. Les valeurs choisies sont uniformément réparties et incluent les bornes de la plage. Au lieu d'essayer de couvrir tous les chemins possibles dans le squelette (ce qui est infaisable), re2py génère suffisamment de chemins pour couvrir toutes les transitions du squelette, et donc déclencher les sauts conditionnels correspondants dans le lexer. L'implémentation de l'algorithme est limitée à environ 1 Go de transitions et consomme une quantité constante de mémoire (re2py écrit les données dans le fichier dès qu'elles sont générées).
