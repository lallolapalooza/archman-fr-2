NOM

re2zig - générer des analyseurs lexicaux rapides pour Zig

SYNTAXE

re2zig [ OPTIONS ] [ AVERTISSEMENTS ] ENTRÉE

L'entrée peut être soit un fichier soit - pour l'entrée standard.

INTRODUCTION

re2zig fonctionne comme un préprocesseur. Il lit le fichier d'entrée (qui est généralement un programme en Zig, mais peut être n'importe quoi) et recherche des blocs de code délimités par des marqueurs de début/fin de forme spéciale. Le texte en dehors de ces blocs est copié tel quel dans le fichier de sortie. Le contenu des blocs est traité par re2zig. Il le traduit en code Zig et génère le code résultant à la place du bloc.

Voici un exemple de petit programme qui vérifie si une chaîne donnée contient un nombre décimal :

// re2zig $INPUT -o $OUTPUT
const std = @import("std");
fn lex(yyinput: [:0]const u8) bool {
    var yycursor: u32 = 0;
    %{
        re2c:yyfill:enable = 0;
        [1-9][0-9]* { return true; }
        *           { return false; }
    %}
}
test {
    try std.testing.expect(lex("1234"));
}

Dans la sortie, re2zig a remplacé le bloc du milieu par le code généré :

// Généré par re2zig
// re2zig $INPUT -o $OUTPUT
const std = @import("std");
fn lex(yyinput: [:0]const u8) bool {
    var yycursor: u32 = 0;
    var yych: u8 = 0;
    var yystate: u32 = 0;
    yyl: while (true) {
        switch (yystate) {
            0 => {
                yych = yyinput[yycursor];
                yycursor += 1;
                switch (yych) {
                    0x31...0x39 => {
                        yystate = 2;
                        continue :yyl;
                    },
                    else => {
                        yystate = 1;
                        continue :yyl;
                    },
                }
            },
            1 => { return false; },
            2 => {
                yych = yyinput[yycursor];
                switch (yych) {
                    0x30...0x39 => {
                        yycursor += 1;
                        yystate = 2;
                        continue :yyl;
                    },
                    else => {
                        yystate = 3;
                        continue :yyl;
                    },
                }
            },
            3 => { return true; },
            else => { @panic("erreur interne de l'analyseur"); },
        }
    }
}
test {
    try std.testing.expect(lex("1234"));
}

BASES

Un programme re2zig consiste en une séquence de blocs entremêlés avec du code dans le langage cible. Un bloc peut contenir des définitions, des configurations, des règles, des actions et des directives dans n'importe quel ordre :

nom = expression-régulière ;
Une définition lie nom à expression-régulière. Les noms peuvent contenir des caractères alphanumériques et le trait de soulignement. La section expressions régulières donne un aperçu de la syntaxe de re2zig pour les expressions régulières. Une fois définie, le nom peut être utilisé dans d'autres expressions régulières et dans les règles. La récursivité dans les définitions nommées n'est pas autorisée, et chaque nom doit être défini avant d'être utilisé. Un bloc hérite des définitions nommées de la portée globale. Redéfinir un nom existant dans la portée actuelle est une erreur.
configuration = valeur ;
Une configuration permet de modifier le comportement de re2zig et de personnaliser le code généré. Pour une liste complète des configurations prises en charge par re2zig, consultez la section configurations. Selon la configuration, la valeur peut être un mot-clé, un nombre entier non négatif ou une chaîne d'une seule ligne qui doit être entourée de guillemets doubles ou simples, sauf si elle est composée de caractères alphanumériques. Un bloc hérite des configurations de la portée globale et peut les redéfinir ou en ajouter de nouvelles. Les configurations définies à l'intérieur d'un bloc affectent le bloc entier, même si elles apparaissent à la fin de celui-ci.
expression-régulière code
Une règle lie une expression-régulière à son action sémantique (un bloc de code entre accolades, ou un bloc de code qui commence par := et se termine sur un retour à la ligne suivi de tout caractère non blanc). Si l'expression-régulière correspond, le code associé est exécuté. Si plusieurs règles correspondent, la correspondance la plus longue a la priorité. Si plusieurs règles correspondent à la même chaîne, la première d'entre elles a la priorité. Il existe deux règles spéciales : la règle par défaut * et la règle de fin d'entrée $. La règle par défaut doit toujours être définie, elle a la priorité la plus basse quelle que soit sa place dans le bloc, et elle correspond à toute unité de code (pas nécessairement un caractère valide, voir la section support de l'encodage). La règle de fin d'entrée doit être définie si la méthode correspondante pour la gestion de la fin d'entrée est utilisée. Avec les conditions de départ, les règles ont une syntaxe plus complexe.
!action code
Une action lie un bloc de code défini par l'utilisateur à un emplacement particulier dans l'automate fini déterministe généré (de la même manière que les actions sémantiques lient le code aux états finaux). Voir la section actions pour une liste complète des actions prédéfinies.
!directive ;
Une directive est l'une des instructions spéciales prédéfinies. Chaque directive a un but unique. Voir la section directives pour les détails.

Blocs

Les marqueurs de début et de fin de bloc sont soit /*!re2c et */, soit %{ et %} (les deux styles sont pris en charge). Depuis la version 2.2, les blocs peuvent avoir des noms optionnels qui permettent de les référencer dans d'autres blocs. Il existe différents types de blocs :

/*!re2c[:<nom>] ... */ ou %{[:<nom>] ... %}
Un bloc global contient des définitions, des configurations, des règles et des directives. re2zig compile les expressions régulières associées à chaque règle en un automate fini déterministe, l'encode sous forme de sauts conditionnels dans le langage cible et remplace le bloc par le code généré. Les noms et les configurations définis dans un bloc global sont ajoutés à la portée globale et deviennent visibles pour les blocs suivants. Au début du programme, la portée globale est initialisée avec les options de la ligne de commande.
/*!local:re2c[:<nom>] ... */ ou %{local[:<nom>] ... %}
Un bloc local est similaire à un bloc global, mais les noms et les configurations qu'il contient ont une portée locale (ils n'affectent pas les autres blocs).
/*!rules:re2c[:<nom>] ... */ ou %{rules[:<nom>] ... %}
Un bloc de règles est similaire à un bloc local, mais il ne génère aucun code en soi, ni n'ajoute de définitions à la portée globale -- il est destiné à être réutilisé dans d'autres blocs. C'est une façon de partager du code (plus de détails dans la section blocs réutilisables). Avant la version 2.2 de re2zig, les blocs de règles nécessitaient l'option -r --reusable.
/*!use:re2c[:<nom>] ... */ ou %{use[:<nom>] ... %}
Un bloc d'utilisation qui référence un bloc de règles défini précédemment. Si le nom est spécifié, re2zig recherche des blocs de règles portant ce nom. Sinon, le bloc de règles le plus récent est utilisé (nommé ou non). Un bloc d'utilisation peut ajouter ses propres définitions, configurations et règles, qui sont ajoutées à celles du bloc de règles référencé. Avant la version 2.2 de re2zig, les blocs d'utilisation nécessitaient l'option -r --reusable.
/*!max:re2c[:<nom1>[:<nom2>...]] ... */ ou %{max[:<nom1>[:<nom2>...]] ... %}
Un bloc qui génère la définition YYMAXFILL. Une liste optionnelle de noms de blocs spécifie quels blocs doivent être inclus lors du calcul de la valeur YYMAXFILL (si la liste est vide, tous les blocs sont inclus). Par défaut, le code généré est une macro-définition pour C (#define YYMAXFILL <n>), ou une variable globale pour Go (var YYMAXFILL int = <n>). Il peut être personnalisé avec une configuration optionnelle format qui spécifie une chaîne de modèle où @@{max} (ou @@ pour faire court) est remplacé par la valeur numérique de YYMAXFILL.
/*!maxnmatch:re2c[:<nom1>[:<nom2>...]] ... */ ou %{maxnmatch[:<nom1>[:<nom2>...]] ... %}
Un bloc qui génère la définition de YYMAXNMATCH (il nécessite l'option -P --posix-captures). Une liste facultative de noms de blocs spécifie quels blocs doivent être inclus lors du calcul de la valeur de YYMAXNMATCH (si la liste est vide, tous les blocs sont inclus). Par défaut, le code généré est une macro-définition pour C (#define YYMAXNMATCH <n>), ou une variable globale pour Go (var YYMAXNMATCH int = <n>). Il peut être personnalisé avec une configuration facultative format qui spécifie une chaîne de modèle où @@{max} (ou @@ pour faire court) est remplacé par la valeur numérique de YYMAXNMATCH.
/*!stags:re2c[:<name1>[:<name2>...]] ... */, /*!mtags:re2c[:<name1>[:<name2>...]] ... */ ou %{stags[:<name1>[:<name2>...]] ... %}, %{mtags[:<name1>[:<name2>...]] ... %{
Blocs qui spécifient un fragment de code modèle qui est développé pour chaque variable s-tag/m-tag générée par re2zig. Une liste facultative de noms de blocs spécifie quels blocs doivent être inclus lors du calcul de l'ensemble des variables de balise (si la liste est vide, tous les blocs sont inclus). Il existe deux configurations facultatives : format et separator. La configuration format spécifie une chaîne de modèle où @@{tag} (ou @@ pour faire court) est remplacé par le nom de chaque variable de balise. La configuration separator spécifie un fragment de code utilisé pour joindre les fragments format générés pour différentes variables de balise.
/*!svars:re2c[:<name1>[:<name2>...]] ... */, /*!mvars:re2c[:<name1>[:<name2>...]] ... */ ou %{svars[:<name1>[:<name2>...]] ... %}, %{mvars[:<name1>[:<name2>...]] ... %{
Blocs qui spécifient un fragment de code modèle qui est développé pour chaque s-tag/m-tag qui est soit explicitement mentionné par les règles (avec l'option --tags), soit implicitement généré par re2zig (avec les options --captvars ou --posix-captvars). Une liste facultative de noms de blocs spécifie quels blocs doivent être inclus lors du calcul de l'ensemble des balises (si la liste est vide, tous les blocs sont inclus). Il existe deux configurations facultatives : format et separator. La configuration format spécifie une chaîne de modèle où @@{tag} (ou @@ pour faire court) est remplacé par le nom de chaque balise. La configuration separator spécifie un fragment de code utilisé pour joindre les fragments format générés pour différentes balises.
/*!getstate:re2c[:<name1>[:<name2>...]] ... */ ou %{getstate[:<name1>[:<name2>...]] ... %}
Un bloc qui génère une distribution conditionnelle sur l'état de l'analyseur lexical (il nécessite l'option --storable-state). Une liste facultative de noms de blocs spécifie quels blocs doivent être inclus dans la distribution d'état. La transition par défaut va à l'étiquette de début du premier bloc de la liste. Si la liste est vide, tous les blocs sont inclus, et la transition par défaut va au premier bloc du fichier qui a une étiquette de début. Ce type de bloc est incompatible avec l'option --loop-switch, car il nécessite des transitions inter-blocs qui ne sont pas prises en charge sans goto ou appels de fonction.
/*!conditions:re2c[:<name1>[:<name2>...]] ... */, /*!types:re2c... */ ou %{conditions[:<name1>[:<name2>...]] ... %}, %{types... %}
Un bloc qui génère une énumération de conditions (il nécessite l'option --conditions). Une liste facultative de noms de blocs spécifie quels blocs doivent être inclus lors du calcul de l'ensemble des conditions (si la liste est vide, tous les blocs sont inclus). Par défaut, le code généré est une énumération YYCONDTYPE. Il peut être personnalisé avec les configurations facultatives format et separator. La configuration format spécifie une chaîne de modèle où @@{cond} (ou @@ pour faire court) est remplacé par le nom de chaque condition, et @@{num} est remplacé par un indice numérique de cette condition. La configuration separator spécifie un fragment de code utilisé pour joindre les fragments format générés pour différentes conditions.
/*!include:re2c <file> */ ou %{include <file> %}
Ce bloc permet d'inclure <file>, qui doit être un chemin de fichier entre guillemets doubles. Le contenu du fichier est littéralement substitué à la place du bloc, de la même manière que fonctionne #include en C/C++. Ce bloc peut être utilisé conjointement avec l'option --depfile pour générer les dépendances du système de construction sur les fichiers inclus.
/*!header:re2c:on*/ ou %{header:on %}
Ce bloc marque le début du fichier d'en-tête. Tout ce qui suit et jusqu'au bloc header:off suivant est traité par re2zig et écrit dans le fichier d'en-tête spécifié avec l'option -t --type-header.
/*!header:re2c:off*/ ou %{header:off %}
Ce bloc marque la fin du fichier d'en-tête commencé avec le bloc header:on*/.
/*!ignore:re2c ... */ ou %{ignore ... %}
Un bloc dont le contenu est ignoré et supprimé du fichier de sortie.

Configurations

Voici une liste complète des configurations prises en charge par re2zig :

re2c:api, re2c:input
Identique à l'option --api.
re2c:api:sigil
Spécifie le marqueur ("sigil") utilisé pour les espaces réservés aux arguments dans les primitives API. La valeur par défaut est @@. Un espace réservé commence par le sigil suivi du nom de l'argument entre accolades. Par exemple, si le sigil est défini sur $, alors les espaces réservés auront la forme ${nom}. Les API à argument unique peuvent utiliser une notation abrégée sans le nom entre accolades. Cette option peut être remplacée par des options pour des primitives API individuelles, par exemple re2c:YYFILL@len pour YYFILL.
re2c:api:style
Spécifie le style de l'API. Les valeurs possibles sont functions (la valeur par défaut pour C) et free-form (la valeur par défaut pour Go et Rust). Dans le style functions, les primitives API sont générées avec une liste d'arguments entre parenthèses suivant le nom de la primitive. Les arguments ne sont fournis que pour les paramètres autogénérés (tels que le nombre de caractères passés à YYFILL), mais pas pour le contexte général de l'analyseur lexical, de sorte que les primitives se comportent davantage comme des macros en C/C++ ou des closures en Go et Rust. Dans le style free-form, les primitives API n'ont pas de forme fixe : elles doivent être définies comme des chaînes contenant des fragments de code libres avec des variables interpolées de la forme @@{var} ou @@ (elles correspondent aux arguments dans le style de type fonction). Cette configuration peut être remplacée pour des primitives API individuelles, voir par exemple la configuration re2c:YYFILL:naked pour YYFILL.
re2c:bit-vectors, re2c:flags:bit-vectors, re2c:flags:b
Identique à l'option --bit-vectors, mais peut être configuré par bloc.
re2c:captures, re2c:leftmost-captures
Identique à l'option --leftmost-captures, mais peut être configuré par bloc.
re2c:captvars, re2c:leftmost-captvars
Identique à l'option --leftmost-captvars, mais peut être configuré par bloc.
re2c:case-insensitive, re2c:flags:case-insensitive
Identique à l'option --case-insensitive, mais peut être configuré par bloc.
re2c:case-inverted, re2c:flags:case-inverted
Identique à l'option --case-inverted, mais peut être configuré par bloc.
re2c:case-ranges, re2c:flags:case-ranges
Identique à l'option --case-ranges, mais peut être configuré par bloc.
re2c:computed-gotos, re2c:flags:computed-gotos, re2c:flags:g
Identique à l'option --computed-gotos, mais peut être configuré par bloc.
re2c:computed-gotos:relative, re2c:cgoto:relative
Identique à l'option --computed-gotos-relative, mais peut être configuré par bloc.
re2c:computed-gotos:threshold, re2c:cgoto:threshold
Si goto calculé est utilisé, cette configuration spécifie le seuil de complexité qui déclenche la génération de tables de sauts au lieu d'une imbrication de if et de bitmaps. La valeur par défaut est 9.
re2c:cond:abort
Si défini à une valeur entière positive, le cas par défaut dans la distribution de conditions générée interrompt l'exécution du programme.
re2c:cond:goto
Spécifie un fragment de code utilisé pour les règles de raccourci auto-générées :=> dans les conditions. La valeur par défaut est goto @@;. L'espace réservé @@ est remplacé par le nom de la condition (voir les configurations re2c:api:sigil et re2c:cond:goto@cond).
re2c:cond:goto@cond
Spécifie le sigil utilisé pour la substitution d'arguments dans la définition de re2c:cond:goto. La valeur par défaut est @@. Remplace la configuration plus générique re2c:api:sigil.
re2c:cond:divider
Définit le diviseur pour les blocs de conditions. La valeur par défaut est /* *********************************** */. Les espaces réservés sont remplacés par le nom de la condition (voir re2c:api;sigil et re2c:cond:divider@cond).
re2c:cond:divider@cond
Spécifie le sigil utilisé pour la substitution d'arguments dans la définition de re2c:cond:divider. La valeur par défaut est @@. Remplace la configuration plus générique re2c:api:sigil.
re2c:cond:prefix, re2c:condprefix

Expressions régulières

re2zig utilise la syntaxe suivante pour les expressions régulières :

"foo"
Littéral de chaîne sensible à la casse.
'foo'
Littéral de chaîne insensible à la casse.
[a-xyz], [^a-xyz]
Classe de caractères (éventuellement niée).
.
Tout caractère sauf le saut de ligne.
R \ S
Différence des classes de caractères R et S.
R*
Zéro occurrence ou plus de R.
R+
Une occurrence ou plus de R.
R?
R optionnel.
R{n}
Répétition de R exactement n fois.
R{n,}
Répétition de R au moins n fois.
R{n,m}
Répétition de R de n à m fois.
(R)
Juste R ; les parenthèses sont utilisées pour modifier la priorité. Si l'extraction de sous-correspondance est activée, (R) est un groupe capturant ou non capturant selon l'option --invert-captures.
(!R)
Si l'extraction de sous-correspondance est activée, (!R) est un groupe non capturant ou capturant selon l'option --invert-captures.
R S
Concaténation : R suivi de S.
R | S
Alternative : R ou S.
R / S
Lookahead : R suivi de S, mais S n'est pas consommé.
name
Expression régulière définie comme name (ou littéral de chaîne "name" en mode de compatibilité Flex).
{name}
Expression régulière définie comme name en mode de compatibilité Flex.
@stag
Un s-tag : enregistre la dernière position d'entrée à laquelle @stag correspond dans une variable nommée stag.
#mtag
Un m-tag : enregistre toutes les positions d'entrée auxquelles #mtag correspond dans une variable nommée mtag.

Les classes de caractères et les littéraux de chaînes peuvent contenir les séquences d'échappement suivantes : \a, \b, \f, \n, \r, \t, \v, \\, échappements octaux \ooo et échappements hexadécimaux \xhh, \uhhhh et \Uhhhhhhhh.

Actions

Voici une liste des actions prédéfinies prises en charge par re2zig :

!entry code
L'action d'entrée lie un bloc de code défini par l'utilisateur à l'état de départ de la machine à états finis actuelle. Si des conditions de départ sont utilisées, l'action d'entrée peut être définie individuellement pour chaque condition. Cette action peut être utilisée pour effectuer l'initialisation, par exemple pour enregistrer la position de départ d'un lexème.
!pre_rule code
L'action pré-règle ajoute un bloc de code défini par l'utilisateur au début des actions sémantiques de toutes les règles du bloc actuel (ou de la condition, si des conditions de départ sont utilisées). Cette action peut être utilisée pour factoriser la partie commune de toutes les actions sémantiques (par exemple, enregistrer la position de fin d'un lexème).
!post_rule code
L'action post-règle ajoute un bloc de code défini par l'utilisateur à la fin des actions sémantiques de toutes les règles du bloc actuel (ou de la condition, si des conditions de départ sont utilisées). Cette action peut être utilisée pour émettre des instructions de piège qui protègent contre les flux de contrôle involontaires.

Directives

Voici une liste complète des directives prises en charge par re2zig :

!use:name ;
Une directive d'utilisation intra-bloc qui fusionne un bloc de règles précédemment défini avec le nom spécifié dans le bloc actuel. Les définitions nommées, les configurations et les règles du bloc référencé sont ajoutées aux éléments actuels. Les conflits entre les règles et les configurations qui se chevauchent sont résolus de la manière habituelle : la première règle a la priorité, et la dernière configuration remplace les précédentes. Une exception concerne les règles spéciales *, $ et <!> pour lesquelles une définition locale au bloc a toujours la priorité. Une directive d'utilisation peut être placée n'importe où à l'intérieur d'un bloc, et plusieurs directives d'utilisation sont autorisées.
!include file ;
Cette directive est identique au bloc include : elle insère le contenu de file verbatim à la place de la directive.

Interface du programme

Le code généré interagit avec le programme externe à l'aide de primitives, collectivement appelées API. Les primitives qui doivent être définies pour un programme particulier dépendent de plusieurs facteurs, notamment la complexité des expressions régulières, la représentation des entrées, la mise en mémoire tampon et l'utilisation de diverses fonctionnalités. Toutes les primitives nécessaires doivent être définies par l'utilisateur sous forme de macros, fonctions, variables ou toute autre forme appropriée qui rend le code généré syntaxiquement et sémantiquement correct. re2zig ne vérifie pas (et ne peut pas vérifier) les définitions, donc si quelque chose manque ou est mal défini, le programme généré peut avoir des erreurs de compilation ou d'exécution. Ce manuel fournit des exemples de définitions d'API dans les cas les plus courants.

re2zig a trois saveurs d'API qui définissent l'ensemble de base des primitives utilisées par un programme :

API Simple
C'est l'API par défaut pour le backend Zig. Elle se compose des primitives suivantes : YYINPUT (qui doit être définie comme une séquence d'unités de code, par exemple une chaîne de caractères) et YYCURSOR, YYMARKER, YYCTXMARKER, YYLIMIT (qui doivent être définies comme des index dans YYINPUT).
API d'enregistrement
L'API d'enregistrement est utile dans les cas où l'état de l'analyseur doit être stocké dans une structure. Elle est activée avec l'option --api record ou la configuration re2c:api = record. Cette API se compose d'une variable yyrecord (le nom peut être remplacé par re2c:yyrecord) qui doit être définie comme une structure avec les champs yyinput, yycursor, yymarker, yyctxmarker, yylimit (seuls les champs utilisés par le code généré doivent être définis, et leurs noms peuvent être configurés).
API Générique
C'est l'API la plus flexible. Elle est activée avec l'option --api generic ou la configuration re2c:api = generic. Elle contient des primitives pour les opérations génériques : YYPEEK, YYSKIP, YYBACKUP, YYBACKUPCTX, YYSTAGP, YYSTAGN, YYMTAGP, YYMTAGN, YYRESTORE, YYRESTORECTX, YYRESTORETAG, YYSHIFT, YYSHIFTSTAG, YYSHIFTMTAG, YYLESSTHAN.

Une primitive d'API générique sans variable. Elle doit être définie comme une valeur r de type YYCTYPE qui est égale au caractère à la position actuelle de l'entrée.
YYRESTORE
Une primitive d'API générique qui doit restaurer la position actuelle de l'entrée à la valeur sauvegardée par YYBACKUP.
YYRESTORECTX
Une primitive d'API générique qui doit restaurer la position du contexte final sauvegardée avec YYBACKUPCTX.
YYRESTORETAG
Une primitive d'API générique avec une variable tag qui doit restaurer la position du contexte final à la valeur de tag.
YYRUN
Une primitive avec une variable n. Elle est utilisée pour exécuter la règle n. Pour la plupart des langages, cette primitive a une définition par défaut qui exécute l'instruction goto étiquette yyRunn.
YYSETACCEPT
Une primitive avec deux variables : var (une valeur l qui stocke le sélecteur numérique de la règle acceptée) et val (la valeur du sélecteur). Pour la plupart des langages, cette primitive a une définition par défaut qui assigne var à val.
YYSETCOND
Une primitive avec une variable cond qui doit définir l'identifiant de la condition actuelle sur cond.
YYSETSTATE
Une primitive avec une variable state qui doit définir l'état actuel de l'analyseur lexical sur state.
YYSHIFT
Une primitive d'API générique avec une variable shift qui doit décaler la position actuelle de l'entrée de shift caractères (la valeur du décalage peut être négative).
YYSHIFTMTAG
Une primitive d'API générique avec deux variables, tag et shift, qui doit décaler la dernière valeur de l'historique de tag de shift unités de code (la valeur du décalage peut être négative).
YYSHIFTSTAG
Une primitive d'API générique avec deux variables, tag et shift, qui doit décaler tag de shift unités de code (la valeur du décalage peut être négative).
YYSTAGN
Une primitive d'API générique avec une variable tag, où tag peut être un pointeur ou un décalage dans YYINPUT (voir la section d'extraction de sous-correspondance pour plus de détails). YYSTAGN doit définir tag sur une valeur qui représente une position d'entrée inexistante.
YYSTAGP
Une primitive d'API générique avec une variable tag, où tag peut être un pointeur ou un décalage dans YYINPUT (voir la section d'extraction de sous-correspondance pour plus de détails). YYSTAGP doit définir tag sur la position actuelle de l'entrée.
YYSTAY
Une primitive avec une variable n. La primitive est utilisée pour déclencher le retour en arrière de l'entrée jusqu'au point de début de la règle n. Pour la plupart des langages, cette primitive a une définition par défaut qui exécute l'instruction goto étiquette yyStayn.
YYTEXT
Un r-value qui pointe vers le début de la chaîne de caractères correspondante.
YYTRANS
Une primitive d'API générique avec deux variables, from et to. Elle doit utiliser la table de transition pour trouver la prochaine étape.
YYTRANSITION
Une primitive d'API générique avec trois variables : state, symbol et n. Elle doit retourner la prochaine étape du DFA. La variable n est la longueur de la correspondance.
YYWARNF
Une primitive qui doit déclencher un avertissement indiquant qu'il y a eu un remplissage incomplet du tampon d'entrée.
YYWIDTH
Une valeur r qui contient la longueur de la chaîne de caractères correspondante.
yyaccept
Une valeur l d'un type entier non signé qui stocke le numéro de la dernière règle correspondante. La définition par l'utilisateur n'est nécessaire qu'avec l'option --storable-state.
yybm
Une table contenant des bitmaps compressées pour jusqu'à 8 transitions (utilisée avec l'option --bitmaps). La table contient 256 éléments et est indexée par des unités de code sur 1 octet. Chaque élément de 8 bits combine des valeurs booléennes pour jusqu'à 8 transitions. Le k-ième bit de l'n-ième élément est vrai si et seulement si l'unité de code n est dans la plage de la k-ième transition. L'idée de cette bitmap est de remplacer de nombreuses branches if ou cas switch par une seule vérification d'un seul bit dans la table.
yych
Une valeur l de type YYCTYPE qui stocke le caractère d'entrée actuel. La définition par l'utilisateur n'est nécessaire qu'avec l'option -f --storable-state.
yyctable
Table de saut générée pour la dispersion initiale des conditions (activée avec la combinaison des options --conditions et --computed-gotos).
yyfill
Une valeur l qui stocke le résultat de l'appel YYFILL (cela peut être nécessaire pour les langages purement fonctionnels, où YYFILL est une fonction monadique avec une valeur de retour complexe).
yynmatch
Une valeur l d'un type entier non signé qui stocke le nombre de groupes de captures POSIX dans la règle correspondante. Utilisé uniquement avec l'option -P --posix-captures.
yypmatch
Un tableau de valeurs l qui sont utilisées pour contenir les valeurs des balises correspondant aux parenthèses de capture dans la règle correspondante. La longueur du tableau doit être d'au moins yynmatch * 2 (généralement YYMAXNMATCH * 2 est un bon choix). Utilisé uniquement avec l'option -P --posix-captures.
yystable
Déprécié.
yystate
Une valeur l utilisée avec l'option --loop-switch pour stocker l'état actuel du DFA.
yytarget
Table de saut qui contient les cibles de saut (adresses d'étiquette) pour toutes les transitions d'un état. Cette table est locale à chaque état. La génération des tables yytarget est activée avec l'option --computed-gotos.

Options

Certaines des options ont des configurations correspondantes, d'autres sont globales et ne peuvent pas être modifiées après que re2c commence à lire le fichier d'entrée. Les options de débogage nécessitent généralement de construire re2c en configuration de débogage. Les options internes sont utiles pour expérimenter avec les algorithmes utilisés dans re2c.

-? --help -h
Afficher le message d'aide.
--api <simple | record | generic>
Spécifier l'API utilisée par le code généré pour l'interface avec le code défini par l'utilisateur. L'option simple doit être utilisée dans des cas simples lorsqu'il y a
no pas besoin de recharger le tampon ni de stocker l'état du lexer. L'option record doit être utilisée lorsque l'état du lexer doit être stocké dans un enregistrement (struct, classe, etc.). L'option generic doit être utilisée dans les cas complexes lorsque les deux autres API ne sont pas assez flexibles.
--bit-vectors -b
Optimise les sauts conditionnels à l'aide de masques de bits. Cette option implique --nested-ifs.
--captures, --leftmost-captures
Active l'extraction des sous-correspondances avec des groupes de capture gourmands les plus à gauche. Le résultat est collecté dans un tableau yybmatch de capacité 2 * YYMAXNMATCH, et yynmatch est défini au nombre de groupes pour la règle correspondante.
--captvars, --leftmost-captvars
Active l'extraction des sous-correspondances avec des groupes de capture gourmands les plus à gauche. Le résultat est collecté dans les variables yytl<k>, yytr<k> pour le k-ième groupe de capture.
--case-insensitive
Traite les chaînes entre apostrophes simples et guillemets doubles comme insensibles à la casse.
--case-inverted
Inverse la signification des chaînes entre apostrophes simples et guillemets doubles : traite les chaînes entre apostrophes simples comme sensibles à la casse et les chaînes entre guillemets doubles comme insensibles à la casse.
--case-ranges
Réduit les cas consécutifs dans les instructions switch en une plage de la forme low ... high. Cette syntaxe est une extension du langage C/C++ qui est prise en charge par des compilateurs tels que GCC, Clang et Tcc. L'avantage principal par rapport à l'utilisation de cas uniques est un code généré plus petit et un temps de génération plus rapide, bien que pour certains compilateurs comme Tcc, cela se traduise également par une taille binaire plus petite.
--computed-gotos -g
Optimise les sauts conditionnels à l'aide de l'extension non standard "computed goto" (qui doit être prise en charge par le compilateur). re2zig génère des tables de sauts uniquement dans les cas complexes avec de nombreuses branches conditionnelles. Le seuil de complexité peut être configuré avec la configuration cgoto:threshold. Les décalages relatifs peuvent être activés avec la configuration cgoto:relative. Cette option implique --bit-vectors.
--computed-gotos-relative
Similaire à --computed-gotos mais génère des décalages relatifs pour les tables de sauts au lieu de cela (ce qui doit être pris en charge par le compilateur). Cette option implique --computed-gotos.
--conditions --start-conditions -c
Active la prise en charge des "conditions" de type Flex : plusieurs lexers interdépendants au sein d'un même bloc. C'est une alternative à la spécification manuelle de différents blocs re2zig connectés par goto ou des appels de fonction.
--depfile FILE
Écrit les informations de dépendance dans FILE sous la forme d'une règle Makefile <fichier-sortie> : <fichier-entrée> [fichier-inclusion ...]. Cela permet de suivre les dépendances de construction en présence de blocs/directives include, de sorte que la mise à jour des fichiers d'inclusion déclenche la régénération du fichier de sortie. Cette option dépend de l'option --output.
--ebcdic --ecb -e
Génère un lexer qui lit l'entrée en encodage EBCDIC. re2zig suppose que la plage de caractères est 0 -- 0xFF et que la taille des caractères est de 1 octet.
--empty-class <match-empty | match-none | error>
Définit la manière dont re2zig traite les classes de caractères vides. Avec match-empty (par défaut), une classe vide correspond à une entrée vide (ce qui est illogique, mais rétrocompatible). Avec match-none, une classe vide échoue toujours à correspondre. Avec error, une classe vide déclenche une erreur de compilation.
--encoding-policy <fail | substitute | ignore>
Définit la manière dont re2zig traite les substituts Unicode. Avec fail, re2zig s'arrête avec une erreur lorsqu'un substitut est rencontré. Avec substitute, re2zig remplace silencieusement les substituts par le point de code d'erreur 0xFFFD. Avec ignore (par défaut), re2zig traite les substituts comme des points de code normaux. La norme Unicode stipule que les substituts autonomes sont invalides, mais les bibliothèques et les programmes du monde réel se comportent différemment.
--flex-syntax -F
Support partiel de la syntaxe Flex : dans ce mode, les définitions nommées n'ont pas besoin du signe égal et du point-virgule de terminaison, et lorsqu'elles sont utilisées, elles doivent être entourées d'accolades. Les noms sans accolades sont traités comme des chaînes entre guillemets doubles.
--goto-label
Utilise le modèle de code "goto/label" : encode le DFA sous forme de blocs de code étiquetés connectés par des transitions goto entre les blocs. Ceci n'est pris en charge que pour les langages qui ont une instruction goto.
--header --type-header -t HEADER
Génère un fichier HEADER. Le contenu du fichier peut être spécifié à l'aide des blocs spéciaux header:on et header:off. Si des conditions sont utilisées, l'en-tête généré aura un énum d'état automatiquement ajouté (sauf s'il existe un bloc conditions explicite).
-I PATH
Ajoute PATH à la liste des emplacements utilisés lors de la recherche de fichiers d'inclusion. Cette option est utile en combinaison avec le bloc ou la directive include. re2zig recherche FILE dans le répertoire du fichier parent et dans les emplacements d'inclusion spécifiés avec l'option -I.
--input <default | custom>
Alias obsolète pour --api. L'option default correspond à simple (c'est en effet le défaut pour la plupart des backends, mais pas pour tous). L'option custom correspond à generic.
--input-encoding <ascii | utf8>
Spécifie la manière dont re2zig analyse les expressions régulières. Avec ascii (par défaut), re2zig traite l'entrée comme encodée en ASCII : toute séquence d'unités de code est une séquence de caractères autonomes de 1 octet. Avec utf8, re2zig traite l'entrée comme encodée en UTF8 et reconnaît les caractères multibytes.
--invert-captures
Inverse la signification des groupes de capture et des groupes non capturants. Par défaut, (...) est capturant et (! ...) est non capturant. Avec cette option, (! ...) est capturant et (...) est non capturant.
--lang <none | c | d | go | haskell | java | js | ocaml | python | rust | swift | v | zig>
Spécifie la langue cible. Les langues prises en charge sont C, D, Go, Haskell, Java, JS, OCaml, Python, Rust, Swift, V, Zig (d'autres langues peuvent être ajoutées via des fichiers de syntaxe définis par l'utilisateur, voir l'option --syntax). L'option none désactive les configurations de syntaxe par défaut, de sorte que la langue cible est indéfinie.
--location-format <gnu | msvc>
Spécifie le format de localisation dans les messages. Avec gnu, les localisations sont imprimées comme 'nomfichier:ligne:colonne: ...'. Avec msvc, les localisations sont imprimées comme 'nomfichier(ligne,colonne) ...'. Le défaut est gnu.
--loop-switch
Utilise le modèle de code "loop/switch" : encode le DFA sous forme d'une boucle sur une instruction switch, où les états individuels sont des cas de switch. L'état est stocké dans une variable yystate. Les transitions entre les états mettent à jour yystate vers l'étiquette du cas de l'état de destination et continuent l'exécution jusqu'à la tête de la boucle.
--nested-ifs -s
Utilise des instructions if imbriquées au lieu d'instructions switch dans les sauts conditionnels. Cela conduit généralement à un code plus efficace avec des compilateurs non optimisants.
--no-debug-info -i
Ne produit pas de directives de ligne. Ceci peut être utile lorsque le code généré est stocké dans un système de contrôle de version (pour éviter d'énormes différences générées automatiquement sur de petits changements).
--no-generation-date
Supprime la sortie de la date dans le fichier généré.
--no-version
Supprime la sortie de la version dans le fichier généré.
--no-unsafe
Ne génère pas de wrapper unsafe autour de YYPEEK (cette option est spécifique à Rust). Pour des raisons de performance, YYPEEK devrait éviter les vérifications de limites, car le lexer effectue déjà des vérifications de fin d'entrée de manière plus efficace. L'utilisateur peut choisir de fournir une définition YYPEEK sûre, ou une définition qui n'est dangereuse que dans les builds de production, auquel cas l'option --no-unsafe permet d'éviter les avertissements concernant les blocs unsafe redondants.
--output -o OUTPUT
Spécifie le fichier OUTPUT.
--posix-captures, -P
Active l'extraction des sous-correspondances avec des groupes de capture de style POSIX. Le résultat est collecté dans un tableau yybmatch de capacité 2 * YYMAXNMATCH, et yynmatch est défini au nombre de groupes pour la règle correspondante.
--posix-captvars
Active l'extraction des sous-correspondances avec des groupes de capture de style POSIX. Le résultat est collecté dans les variables yytl<k>, yytr<k> pour le k-ième groupe de capture.
--recursive-functions
Utilise un modèle de code basé sur des fonctions co-récursives, où chaque état du DFA est une fonction distincte qui peut appeler d'autres fonctions d'état ou elle-même.
--reusable -r
Obsolète depuis la version 2.2 (les blocs réutilisables sont autorisés par défaut maintenant).
--skeleton -S
Ignore le code d'interface défini par l'utilisateur et génère un programme "squelette" autonome. De plus, génère des fichiers d'entrée avec des chaînes dérivées de la grammaire régulière
r et les résultats de correspondance compressés qui sont utilisés pour vérifier le comportement de "squelette" sur toutes les entrées. Cette option est utile pour trouver des bogues dans les optimisations et la génération de code. Cette option n'est prise en charge que pour C.
--storable-state -f
Génère un analyseur qui peut stocker son état interne. Ceci est utile dans les analyseurs de type "push" qui sont arrêtés par un programme externe lorsqu'il n'y a pas assez d'entrée, puis repris lorsqu'une entrée supplémentaire devient disponible. Dans ce mode, les utilisateurs doivent en plus définir les primitives YYGETSTATE et YYSETSTATE, et les variables yych, yyaccept et state doivent faire partie de l'état de l'analyseur stocké.
--syntax FICHIER
Charge les configurations du FICHIER spécifié et les applique par-dessus le fichier de syntaxe par défaut. Notez que FICHIER peut ne définir que quelques configurations (s'il est utilisé pour modifier le fichier de syntaxe par défaut), ou il peut définir un backend de langage entièrement nouveau (dans ce dernier cas, il est recommandé d'utiliser l'option --lang none).
--tags -T
Active l'extraction de sous-correspondances avec des balises.
--ucs2 --wide-chars -w
Génère un analyseur qui lit une entrée codée en UCS2. re2zig suppose que la plage de caractères est comprise entre 0 et 0xFFFF et que la taille des caractères est de 2 octets. Cette option implique --nested-ifs.
--utf8 --utf-8 -8
Génère un analyseur qui lit une entrée codée en UTF-8. re2zig suppose que la plage de caractères est comprise entre 0 et 0x10FFFF et que la taille des caractères est de 1 octet.
--utf16 --utf-16 -x
Génère un analyseur qui lit une entrée codée en UTF16. re2zig suppose que la plage de caractères est comprise entre 0 et 0x10FFFF et que la taille des caractères est de 2 octets. Cette option implique --nested-ifs.
--utf32 --unicode -u
Génère un analyseur qui lit une entrée codée en UTF32. re2zig suppose que la plage de caractères est comprise entre 0 et 0x10FFFF et que la taille des caractères est de 4 octets. Cette option implique --nested-ifs.
--verbose
Affiche un court message en cas de succès.
--vernum -V
Affiche les informations de version au format MMmmpp (majeur, mineur, correctif).
--version -v
Affiche les informations de version.
--single-pass -1
Obsolète. Ne fait rien (le passage unique est maintenant le comportement par défaut).
--debug-output -d
Émet des invocations de YYDEBUG dans le code généré. Ceci est utile pour suivre l'exécution de l'analyseur.
--dump-adfa
Option de débogage : affiche le DFA après le tunneling (au format .dot).
--dump-cfg
Option de débogage : affiche le graphe de flot de contrôle des variables de balise (au format .dot).
--dump-closure-stats
Option de débogage : affiche les statistiques sur le nombre d'états dans la fermeture.
--dump-dfa-det
Option de débogage : affiche le DFA immédiatement après la déterminisation (au format .dot).
--dump-dfa-min
Option de débogage : affiche le DFA après minimisation (au format .dot).
--dump-dfa-tagopt
Option de débogage : affiche le DFA après les optimisations de balise (au format .dot).
--dump-dfa-tree
Option de débogage : affiche le DFA en cours de construction avec des états représentés par des arbres d'historique de balises (au format .dot).
--dump-dfa-raw
Option de débogage : affiche le DFA en cours de construction avec des ensembles d'états développés (au format .dot).
--dump-interf
Option de débogage : affiche le tableau d'interférence produit par l'analyse de vivacité des variables de balise.
--dump-nfa
Option de débogage : affiche le NFA (au format .dot).
--emit-dot -D
Au lieu de la sortie normale, génère le graphe de l'analyseur au format .dot. La sortie peut être convertie en image à l'aide de Graphviz (par exemple, quelque chose comme dot -Tpng -odfa.png dfa.dot).
--dfa-minimization <moore | table>
Option interne : algorithme de minimisation de DFA utilisé par re2zig. L'option moore correspond à l'algorithme de Moore (qui est le défaut). L'option table correspond à l'algorithme de "remplissage de table". Les deux algorithmes devraient produire le même DFA à une permutation près des états ; le remplissage de table est plus simple et beaucoup plus lent, servant d'implémentation de référence.
--eager-skip
Option interne : fait avancer l'analyseur généré de manière anticipée sur la position d'entrée -- immédiatement après avoir lu le symbole d'entrée. Cela modifie le comportement par défaut où la position d'entrée est avancée de manière différée -- après la transition vers le nouvel état.
--no-lookahead
Option interne, obsolète. Elle permettait d'activer l'algorithme TDFA(0). Contrairement à TDFA(1), l'algorithme TDFA(0) n'utilise pas d'anticipation d'un symbole. Il applique des opérations sur les registres aux transitions entrantes plutôt qu'aux transitions sortantes. Les benchmarks ont montré que l'algorithme TDFA(0) est moins performant que TDFA(1).
--no-optimize-tags
Option interne : supprime l'optimisation des variables de balise (utile pour le débogage).
--posix-closure <gor1 | gtop>
Option interne : spécifie l'algorithme de plus court chemin utilisé pour la construction de la fermeture epsilon avec la sémantique de désambiguïsation POSIX : gor1 (par défaut) signifie l'algorithme de Goldberg-Radzik, et gtop signifie l'algorithme de "l'ordre topologique global".
--posix-prectable <complex | naive>
Option interne : spécifie l'algorithme utilisé pour calculer la table de précédence POSIX. L'algorithme complex calcule la table de précédence en un seul parcours de l'arbre d'historique des balises et a une complexité quadratique par rapport au nombre d'états TNFA ; c'est le défaut. L'algorithme naive a une complexité cubique dans le pire des cas par rapport au nombre d'états TNFA, mais il est beaucoup plus simple que complex et peut être légèrement plus rapide dans les cas non pathologiques.
--stadfa
Option interne, obsolète. Elle permettait d'activer l'algorithme staDFA, qui diffère de TDFA en ce que les opérations sur les registres sont placées dans les états plutôt que sur les transitions. Les benchmarks ont montré que l'algorithme staDFA est moins performant que TDFA.
--fixed-tags <none | toplevel | all>
Option interne : spécifie si l'optimisation des balises fixes doit être appliquée à toutes les balises (all), à aucune d'entre elles (none), ou uniquement à celles dans la concaténation de niveau supérieur (toplevel). Par défaut, c'est all. Les balises "fixes" sont celles qui sont situées à une distance fixe d'une autre balise (appelée "base"). Dans ce cas, seule la balise de base doit être suivie, et la valeur de la balise fixe peut être calculée comme la valeur de la balise de base plus un décalage statique. Pour les balises qui se trouvent sous une alternative ou une répétition, il est également nécessaire de vérifier si la balise de base a une valeur de non-correspondance (dans ce cas, la balise fixe doit également être définie sur non-correspondance, ignorant le décalage). Pour les balises dans la concaténation de niveau supérieur, la vérification n'est pas nécessaire, car elles correspondent toujours.

Avertissements

Les avertissements peuvent être activés, désactivés et transformés en erreur individuellement.

-W
Active tous les avertissements.
-Werror
Transforme les avertissements en erreurs. Notez que cette option seule n'active aucun avertissement ; elle affecte uniquement les avertissements qui ont été activés jusqu'à présent ou qui seront activés plus tard.
-W<avertissement>
Active l'avertissement.
-Wno-<avertissement>
Désactive l'avertissement.
-Werror-<avertissement>
Active l'avertissement et le traite comme une erreur (cela implique -W<avertissement>).
-Wno-error-<avertissement>
Ne traite pas cet avertissement particulier comme une erreur. Cela ne désactive pas l'avertissement lui-même.
-Wcondition-order
Avertit si le programme généré fait des suppositions implicites sur la numérotation des conditions. Il faut utiliser soit l'option --header, soit le bloc conditions pour générer une correspondance entre les noms de conditions et leurs numéros, puis utiliser les noms de conditions auto-générés.
-Wempty-character-class
Avertit si une expression régulière contient une classe de caractères vide. Essayer de faire correspondre une classe de caractères vide n'a aucun sens : elle devrait toujours échouer. Cependant, pour des raisons de compatibilité ascendante, re2zig autorise les classes de caractères vides et les traite comme des chaînes vides. Utilisez l'option --empty-class pour modifier le comportement par défaut.
-Wmatch-empty-string
Avertit si une règle est "nulle" (correspond à une chaîne vide). Si l'analyseur s'exécute en boucle et que la correspondance vide est involontaire, l'analyseur peut se bloquer de manière inattendue dans une boucle infinie.
-Wswapped-range
Avertit si la borne inférieure d'une plage est supérieure à
n sa limite supérieure. Le comportement par défaut est d'échanger silencieusement les bornes de la plage.
-Wundefined-control-flow
Avertir si certaines chaînes d'entrée provoquent un flux de contrôle indéfini dans le lexer (les modèles défectueux sont signalés). C'est une erreur courante et dangereuse. Elle peut être facilement corrigée en ajoutant la règle par défaut * qui a la priorité la plus basse, correspond à toute unité de code et consomme toujours une seule unité de code.
-Wunreachable-rules
Avertir sur les règles qui sont masquées par d'autres règles et qui ne correspondront jamais.
-Wdeprecated-eof_rule
Avertir sur les règles de fin d'entrée autonomes $ qui seront brisées par les changements futurs et nécessiteront une correction. Pour le moment, ces règles ont la priorité lorsqu'elles entrent en conflit avec d'autres règles, mais après l'introduction du symbole de fin d'entrée généralisé $, l'ordre de priorité changera et ces règles seront masquées par d'autres règles.
-Wuseless-escape
Avertir si un symbole est échappé alors qu'il ne devrait pas l'être. Par défaut, re2c ignore silencieusement de tels échappements, mais cela peut aussi indiquer une faute de frappe ou une erreur dans la séquence d'échappement.
-Wnondeterministic-tags
Avertir si une balise a un degré de nondéterminisme n, où n est supérieur à 1.
-Wsentinel-in-midrule
Avertir si le symbole sentinelle apparaît au milieu d'une règle --- cela peut provoquer des lectures au-delà de la fin du tampon, des plantages ou une corruption de mémoire dans le lexer généré. Cet avertissement ne s'applique que si la méthode sentinelle de vérification de la fin de l'entrée est utilisée. Il est défini comme une erreur si la configuration re2c:sentinel est utilisée.
-Wundefined-syntax-config
Avertir si le fichier de syntaxe spécifié avec l'option --syntax est manquant de définitions de certaines configurations. Cela aide à maintenir les fichiers de syntaxe définis par l'utilisateur : si une nouvelle version ajoute des configurations, un ancien fichier de syntaxe déclenchera un avertissement, et l'utilisateur sera informé. Si certaines configurations sont inutilisées et n'ont pas besoin de définition, elles doivent être explicitement définies sur <undefined>.

Fichiers de syntaxe

Le support des différents langages dans re2c est basé sur l'idée des fichiers de syntaxe. Un fichier de syntaxe est un fichier de configuration qui définit la syntaxe du langage cible -- pas tout le langage, mais une petite partie de celui-ci qui est utilisée par le code généré. Les fichiers de syntaxe rendent re2c très flexible, mais ils ne doivent pas être utilisés comme remplacement des configurations re2c:: leur but est de définir la syntaxe du langage cible, et non de personnaliser un lexer particulier. Tous les langages supportés ont des fichiers de syntaxe par défaut qui font partie de la distribution (voir le sous-répertoire include/syntax); ils sont également intégrés dans le binaire re2zig. Les utilisateurs peuvent fournir un fichier de syntaxe personnalisé qui remplace quelques configurations pour l'un des langages supportés, ou ils peuvent choisir de redéfinir toutes les configurations (auquel cas l'option --lang none doit être utilisée). Les fichiers de syntaxe contiennent des configurations de quatre types différents : listes de fonctionnalités, configurations de langage, configurations en place et modèles de code.

Listes de fonctionnalités

Quelques configurations de liste définissent diverses fonctionnalités supportées par un backend donné, de sorte que re2zig puisse donner une erreur claire si l'utilisateur essaie d'activer une fonctionnalité non supportée :
supported_apis
Une liste d'APIs supportées avec des éléments possibles simple, record, generic.
supported_api_styles
Une liste de styles d'API supportés avec des éléments possibles functions, free-form.
supported_code_models
Une liste de modèles de code supportés avec des éléments possibles goto-label, loop-switch, recursive-functions.
supported_targets
Une liste de cibles de génération de code supportées avec des éléments possibles code, dot, skeleton.
supported_features
Une liste de fonctionnalités supportées avec des éléments possibles nested-ifs, bitmaps, computed-gotos, case-ranges, monadic, unsafe, tags, captures, captvars.

Configurations de langage

Quelques configurations booléennes décrivent les fonctionnalités du langage cible qui affectent l'analyseur et le générateur de code de re2zig :
semicolons
Non nul si le langage utilise des points-virgules après les instructions.
backtick_quoted_strings
Non nul si le langage a des chaînes entre guillemets inversés.
single_quoted_strings
Non nul si le langage a des chaînes entre apostrophes.
indentation_sensitive
Non nul si le langage est sensible à l'indentation.
wrap_blocks_in_braces
Non nul si les instructions composées doivent être entourées d'accolades.

Configurations en place

Les fichiers de syntaxe définissent les valeurs initiales de toutes les configurations re2c:, car elles peuvent différer pour différents langages. Voir la section configurations pour une liste complète de toutes les configurations en place et leur signification.

Modèles de code

Les modèles de code définissent la syntaxe du langage cible. Ils sont écrits dans un langage simple spécifique à un domaine avec la grammaire formelle suivante : 
code-template ::
      name '=' code-exprs ';'
    | CODE_TEMPLATE ';'
    | '<undefined>' ';'
code-exprs ::
      <EMPTY>
    | code-exprs code-expr
code-expr ::
      STRING
    | VARIABLE
    | optional
    | list
optional ::
      '(' CONDITIONAL '?' code-exprs ')'
    | '(' CONDITIONAL '?' code-exprs ':' code-exprs ')'
list ::
      '[' VARIABLE ':' code-exprs ']'
    | '[' VARIABLE '{' NUMBER '}' ':' code-exprs ']'
    | '[' VARIABLE '{' NUMBER ',' NUMBER '}' ':' code-exprs ']'

Un modèle de code est une séquence de littéraux de chaînes, de variables, d'éléments optionnels et de listes, ou une référence à un autre modèle de code, ou une valeur spéciale <undefined>. Les variables sont des espaces réservés qui sont substitués pendant la phase de génération de code. Les variables de liste sont spéciales : lors de l'expansion des modèles de liste, re2zig répète les expressions du côté droit de la colonne plusieurs fois, remplaçant à chaque fois les occurrences de la variable de liste par une valeur spécifique à cette répétition. Les listes ont des limites optionnelles (les valeurs négatives sont comptées à partir de la fin, par exemple, -1 signifie le dernier élément). Les noms conditionnels commencent par un point. Les conditionnels et les variables peuvent être locaux (spécifiques au modèle de code donné) ou globaux (autorisés dans tous les modèles de code). Lorsque re2zig lit un fichier de syntaxe, il vérifie que chaque modèle de code n'utilise que les variables et les conditionnels qui y sont autorisés.

Par exemple, le modèle de code suivant définit une construction if-then-else pour un langage de type C :

code:if_then_else =
    [branch{0}: topindent "if " cond " {" nl
        indent [stmt: stmt] dedent]
    [branch{1:-1}: topindent "} else" (.cond ? " if " cond) " {" nl
        indent [stmt: stmt] dedent]
    topindent "}" nl;

Ici, branch est une variable de liste : branch{0} se développe pour la première branche (qui est spéciale, car il n'y a pas de partie else), branch{1:-1} se développe pour toutes les branches restantes (s'il y en a). stmt est aussi une variable de liste : [stmt: stmt] est une liste imbriquée qui se développe pour une liste d'instructions dans le corps de la branche actuelle. topindent, indent, dedent et nl sont des variables globales, et .cond est un conditionnel local (leur signification est décrite ci-dessous). Ce modèle de code pourrait produire le code suivant :

if x {
    // do something
} else if y {
    // do something else
} else {
    // don't do anything
}
