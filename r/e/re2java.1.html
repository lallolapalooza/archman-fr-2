NOM

re2java - générer des analyseurs lexicaux rapides pour Java

SYNTAXE

re2java [ OPTIONS ] [ AVERTISSEMENTS ] ENTRÉE

L'entrée peut être un fichier ou - pour l'entrée standard.

INTRODUCTION

re2java fonctionne comme un préprocesseur. Il lit le fichier d'entrée (qui est généralement un programme Java, mais peut être n'importe quoi) et recherche des blocs de code entourés de marqueurs de début/fin de forme spéciale. Le texte en dehors de ces blocs est copié tel quel dans le fichier de sortie. Le contenu des blocs est traité par re2java. Il les traduit en code Java et génère le code produit à la place du bloc.

Voici un exemple de petit programme qui vérifie si une chaîne donnée contient un nombre décimal :

// re2java $INPUT -o $OUTPUT
class Main {
    static boolean lex(String yyinput) {
        int yycursor = 0;
        /*!re2c
            re2c:YYCTYPE = "char";
            re2c:YYPEEK = "yyinput.charAt(yycursor)";
            re2c:yyfill:enable = 0;
            [1-9][0-9]* { return true; }
            *           { return false; }
        */
    }
    public static void main(String []args) {
        assert lex("1234\0");
    }
};

Dans la sortie, re2java a remplacé le bloc du milieu par le code généré :

// Généré par re2java
// re2java $INPUT -o $OUTPUT
class Main {
    static boolean lex(String yyinput) {
        int yycursor = 0;
{
    char yych = 0;
    int yystate = 0;
    yyl: while (true) {
        switch (yystate) {
            case 0:
                yych = yyinput.charAt(yycursor);
                yycursor += 1;
                switch (yych) {
                    case 0x31:
                    case 0x32:
                    case 0x33:
                    case 0x34:
                    case 0x35:
                    case 0x36:
                    case 0x37:
                    case 0x38:
                    case 0x39:
                        yystate = 2;
                        continue yyl;
                    default:
                        yystate = 1;
                        continue yyl;
                }
            case 1:
                { return false; }
            case 2:
                yych = yyinput.charAt(yycursor);
                switch (yych) {
                    case 0x30:
                    case 0x31:
                    case 0x32:
                    case 0x33:
                    case 0x34:
                    case 0x35:
                    case 0x36:
                    case 0x37:
                    case 0x38:
                    case 0x39:
                        yycursor += 1;
                        yystate = 2;
                        continue yyl;
                    default:
                        yystate = 3;
                        continue yyl;
                }
            case 3:
                { return true; }
            default:
                throw new IllegalStateException("erreur interne de l'analyseur");
        }
    }
}
    }
    public static void main(String []args) {
        assert lex("1234\0");
    }
};

BASES

Un programme re2java consiste en une séquence de blocs mélangée à du code dans le langage cible. Un bloc peut contenir des définitions, des configurations, des règles, des actions et des directives dans n'importe quel ordre :

nom = expression-régulière ;
Une définition lie nom à expression-régulière. Les noms peuvent contenir des caractères alphanumériques et le trait de soulignement. La section expressions régulières donne un aperçu de la syntaxe de re2java pour les expressions régulières. Une fois défini, le nom peut être utilisé dans d'autres expressions régulières et dans des règles. La récursivité dans les définitions nommées n'est pas autorisée, et chaque nom doit être défini avant d'être utilisé. Un bloc hérite des définitions nommées de la portée globale. Redéfinir un nom qui existe dans la portée actuelle est une erreur.
configuration = valeur ;
Une configuration permet de modifier le comportement de re2java et de personnaliser le code généré. Pour une liste complète des configurations supportées par re2java, voir la section configurations. En fonction d'une configuration particulière, la valeur peut être un mot-clé, un nombre entier non négatif ou une chaîne sur une seule ligne qui doit être entourée de guillemets doubles ou simples, sauf si elle est composée de caractères alphanumériques. Un bloc hérite des configurations de la portée globale et peut les redéfinir ou en ajouter de nouvelles. Les configurations définies à l'intérieur d'un bloc affectent tout le bloc, même si elles apparaissent à la fin de celui-ci.
expression-régulière code
Une règle lie une expression-régulière à son action sémantique (un bloc de code entre accolades, ou un bloc de code qui commence par := et se termine à la fin de la ligne suivie d'un caractère non blanc). Si l'expression-régulière correspond, le code associé est exécuté. Si plusieurs règles correspondent, la correspondance la plus longue a la priorité. Si plusieurs règles correspondent à la même chaîne, la plus ancienne a la priorité. Il existe deux règles spéciales : la règle par défaut * et la règle de fin d'entrée $. La règle par défaut doit toujours être définie, elle a la plus basse priorité quelle que soit sa place dans le bloc, et elle correspond à n'importe quelle unité de code (pas nécessairement un caractère valide, voir la section prise en charge de l'encodage). La règle de fin d'entrée doit être définie si la méthode correspondante pour la gestion de la fin d'entrée est utilisée. Avec les conditions de départ, les règles ont une syntaxe plus complexe.
!action code
Une action lie un bloc de code défini par l'utilisateur à un endroit particulier dans la machine à états finis générée (de la même manière que les actions sémantiques lient le code aux états finaux). Voir la section actions pour une liste complète des actions prédéfinies.
!directive ;
Une directive est une des instructions prédéfinies spéciales. Chaque directive a un but unique. Voir la section directives pour les détails.

Blocs

Les marqueurs de début et de fin de bloc sont soit /*!re2c et */, soit %{ et %} (les deux styles sont supportés). À partir de la version 2.2, les blocs peuvent avoir des noms optionnels qui permettent de les référencer dans d'autres blocs. Il existe différents types de blocs :

/*!re2c[:<nom>] ... */ ou %{[:<nom>] ... %}
Un bloc global contient des définitions, configurations, règles et directives. re2java compile les expressions régulières associées à chaque règle en un automate fini déterministe, l'encode sous forme de sauts conditionnels dans le langage cible et remplace le bloc par le code généré. Les noms et configurations définis dans un bloc global sont ajoutés à la portée globale et deviennent visibles pour les blocs suivants. Au début du programme, la portée globale est initialisée avec les options de la ligne de commande.
/*!local:re2c[:<nom>] ... */ ou %{local[:<nom>] ... %}
Un bloc local est comme un bloc global, mais les noms et les configurations y ont une portée locale (ils n'affectent pas les autres blocs).
/*!rules:re2c[:<nom>] ... */ ou %{rules[:<nom>] ... %}
Un bloc de règles est comme un bloc local, mais il ne génère aucun code par lui-même, ni n'ajoute de définitions à la portée globale - il est destiné à être réutilisé dans d'autres blocs. C'est une façon de partager du code (plus de détails dans la section blocs réutilisables). Avant la version 2.2 de re2java, les blocs de règles nécessitaient l'option -r --reusable.
/*!use:re2c[:<nom>] ... */ ou %{use[:<nom>] ... %}
Un bloc d'utilisation qui référence un bloc de règles défini précédemment. Si le nom est spécifié, re2java recherche des blocs de règles portant ce nom. Sinon, le bloc de règles le plus récent est utilisé (nommé ou non nommé). Un bloc d'utilisation peut ajouter ses propres définitions, configurations et règles, qui sont ajoutées à celles du bloc de règles référencé. Avant la version 2.2 de re2java, les blocs d'utilisation nécessitaient l'option -r --reusable.
/*!max:re2c[:<nom1>[:<nom2>...]] ... */ ou %{max[:<nom1>[:<nom2>...]] ... %}
Un bloc qui génère la définition YYMAXFILL. Une liste optionnelle de noms de blocs spécifie quels blocs doivent être inclus lors du calcul

Blocs

re2c re2c vous permet de spécifier de nombreux blocs de configuration qui peuvent être utilisés pour contrôler la génération de code. Ces blocs sont généralement écrits sous forme de commentaires C-style (/*! ... */) ou de blocs de code C-style (%{ ... %}).

/*!maxnmatch:re2c[:<nom1>[:<nom2>...]] ... */ ou %{maxnmatch[:<nom1>[:<nom2>...]] ... %}
Un bloc qui génère la définition YYMAXNMATCH (nécessite l'option -P --posix-captures). Une liste optionnelle de noms de blocs spécifie quels blocs doivent être inclus lors du calcul de la valeur de YYMAXNMATCH (si la liste est vide, tous les blocs sont inclus). Par défaut, le code généré est une macro-définition pour C (#define YYMAXNMATCH <n>), ou une variable globale pour Go (var YYMAXNMATCH int = <n>). Il peut être personnalisé avec une configuration optionnelle format qui spécifie une chaîne de modèle où @@{max} (ou @@ en abrégé) est remplacé par la valeur numérique de YYMAXNMATCH.
/*!stags:re2c[:<nom1>[:<nom2>...]] ... */, /*!mtags:re2c[:<nom1>[:<nom2>...]] ... */ ou %{stags[:<nom1>[:<nom2>...]] ... %}, %{mtags[:<nom1>[:<nom2>...]] ... %{
Blocs qui spécifient un modèle de morceau de code qui est développé pour chaque variable s-tag/m-tag générée par re2java. Une liste optionnelle de noms de blocs spécifie quels blocs doivent être inclus lors du calcul de l'ensemble des variables de tag (si la liste est vide, tous les blocs sont inclus). Il existe deux configurations optionnelles : format et separator. La configuration format spécifie une chaîne de modèle où @@{tag} (ou @@ en abrégé) est remplacé par le nom de chaque variable de tag. La configuration separator spécifie un morceau de code utilisé pour joindre les morceaux format générés pour différentes variables de tag.
/*!svars:re2c[:<nom1>[:<nom2>...]] ... */, /*!mvars:re2c[:<nom1>[:<nom2>...]] ... */ ou %{svars[:<nom1>[:<nom2>...]] ... %}, %{mvars[:<nom1>[:<nom2>...]] ... %{
Blocs qui spécifient un modèle de morceau de code qui est développé pour chaque s-tag/m-tag qui est soit explicitement mentionné par les règles (avec l'option --tags) soit implicitement généré par re2java (avec les options --captvars ou --posix-captvars). Une liste optionnelle de noms de blocs spécifie quels blocs doivent être inclus lors du calcul de l'ensemble des tags (si la liste est vide, tous les blocs sont inclus). Il existe deux configurations optionnelles : format et separator. La configuration format spécifie une chaîne de modèle où @@{tag} (ou @@ en abrégé) est remplacé par le nom de chaque tag. La configuration separator spécifie un morceau de code utilisé pour joindre les morceaux format générés pour différents tags.
/*!getstate:re2c[:<nom1>[:<nom2>...]] ... */ ou %{getstate[:<nom1>[:<nom2>...]] ... %}
Un bloc qui génère un dispatch conditionnel sur l'état du lexer (nécessite l'option --storable-state). Une liste optionnelle de noms de blocs spécifie quels blocs doivent être inclus dans le dispatch d'état. La transition par défaut mène à l'étiquette de début du premier bloc de la liste. Si la liste est vide, tous les blocs sont inclus, et la transition par défaut mène au premier bloc du fichier qui a une étiquette de début. Ce type de bloc est incompatible avec l'option --loop-switch, car il nécessite des transitions inter-blocs qui ne sont pas supportées sans goto ou appels de fonction.
/*!conditions:re2c[:<nom1>[:<nom2>...]] ... */, /*!types:re2c... */ ou %{conditions[:<nom1>[:<nom2>...]] ... %}, %{types... %}
Un bloc qui génère une énumération de conditions (nécessite l'option --conditions). Une liste optionnelle de noms de blocs spécifie quels blocs doivent être inclus lors du calcul de l'ensemble des conditions (si la liste est vide, tous les blocs sont inclus). Par défaut, le code généré est une énumération YYCONDTYPE. Il peut être personnalisé avec les configurations optionnelles format et separator. La configuration format spécifie une chaîne de modèle où @@{cond} (ou @@ en abrégé) est remplacé par le nom de chaque condition, et @@{num} est remplacé par un index numérique de cette condition. La configuration separator spécifie un morceau de code utilisé pour joindre les morceaux format générés pour différentes conditions.
/*!include:re2c <fichier> */ ou %{include <fichier> %}
Ce bloc permet d'inclure <fichier>, qui doit être un chemin de fichier entre guillemets doubles. Le contenu du fichier est littéralement substitué à la place du bloc, de la même manière que #include fonctionne en C/C++. Ce bloc peut être utilisé conjointement avec l'option --depfile pour générer des dépendances de système de construction sur les fichiers inclus.
/*!header:re2c:on*/ ou %{header:on %}
Ce bloc marque le début du fichier d'en-tête. Tout ce qui suit et jusqu'au bloc header:off suivant est traité par re2java et écrit dans le fichier d'en-tête spécifié avec l'option -t --type-header.
/*!header:re2c:off*/ ou %{header:off %}
Ce bloc marque la fin du fichier d'en-tête commencé avec le bloc header:on*/.
/*!ignore:re2c ... */ ou %{ignore ... %}
Un bloc dont le contenu est ignoré et supprimé du fichier de sortie.

Configurations

Voici une liste complète des configurations prises en charge par re2java :

re2c:api, re2c:input
Identique à l'option --api.
re2c:api:sigil
Spécifie le marqueur ("sigil") utilisé pour les espaces réservés aux arguments dans les primitives d'API. Par défaut, c'est @@. Un espace réservé commence par le sigil suivi du nom de l'argument entre accolades. Par exemple, si le sigil est défini sur $, les espaces réservés auront la forme ${nom}. Les API à argument unique peuvent utiliser une notation abrégée sans le nom entre accolades. Cette option peut être remplacée par des options pour des primitives d'API individuelles, par exemple re2c:YYFILL@len pour YYFILL.
re2c:api:style
Spécifie le style de l'API. Les valeurs possibles sont functions (par défaut pour C) et free-form (par défaut pour Go et Rust). En style functions, les primitives d'API sont générées avec une liste d'arguments entre parenthèses suivant le nom de la primitive. Les arguments ne sont fournis que pour les paramètres auto-générés (comme le nombre de caractères passés à YYFILL), mais pas pour le contexte général du lexer, de sorte que les primitives se comportent davantage comme des macros en C/C++ ou des fermetures (closures) en Go et Rust. En style free-form, les primitives d'API n'ont pas de forme fixe : elles doivent être définies comme des chaînes contenant des morceaux de code libres avec des variables interpolées de la forme @@{var} ou @@ (elles correspondent aux arguments dans le style fonctionnel). Cette configuration peut être remplacée pour des primitives d'API individuelles, voir par exemple la configuration re2c:YYFILL:naked pour YYFILL.
re2c:bit-vectors, re2c:flags:bit-vectors, re2c:flags:b

Contrôle la génération d'une étiquette de début de bloc. La valeur par défaut est zéro, ce qui signifie que l'étiquette de début n'est générée que si elle est utilisée. Une valeur de chaîne de caractères force également la génération de l'étiquette de début et définit le nom de l'étiquette sur la chaîne spécifiée. Spécifie le nom de l'étiquette optionnelle qui suit le switch YYGETSTATE en mode d'état stockable (activé avec re2c:state:nextlabel). La valeur par défaut est yyNext.

Obsolète (voir l'option obsolète --no-lookahead).
re2c:monadic
Si défini sur une valeur non nulle, le lexer généré utilisera la notation monadique (cette configuration est spécifique à Haskell).
re2c:nested-ifs, re2c:flags:nested-ifs, re2c:flags:s
Identique à l'option --nested-ifs, mais peut être configuré sur une base par bloc.
re2c:posix-captures, re2c:flags:posix-captures, re2c:flags:P

Identique à l'option --tags, mais peut être configuré sur une base par bloc.
re2c:tags:expression
Spécifie l'expression utilisée pour les variables de balise. Par défaut, re2java génère des expressions de la forme yyt<N>. Cela peut être incommode, par exemple si les variables de balise sont définies comme des champs dans une structure. Toutes les occurrences de @@{tag} ou @@ sont remplacées par le nom de balise réel. Par exemple, re2c:tags:expression = "s.@@"; aboutit à des expressions de la forme s.yyt<N> dans le code généré. Voir aussi la configuration re2c:api:sigil.
re2c:tags:negative
Spécifie l'expression constante utilisée pour la valeur de balise négative (typiquement ce serait -1 si les balises sont des décalages d'entiers dans la chaîne d'entrée, ou un pointeur nul si ce sont des pointeurs).
re2c:tags:prefix
Spécifie le préfixe des noms de variables de balise. La valeur par défaut est yyt.
re2c:sentinel
Spécifie le symbole sentinelle utilisé pour les vérifications de fin de fichier (lorsque les vérifications de limites sont désactivées avec re2c:yyfill:enable = 0; et que re2c:eof n'est pas défini). La valeur par défaut est -1` (dans ce cas, re2java suppose que le sentinelle est zéro, ce qui est le cas le plus courant). Seuls les nombres décimaux sont reconnus.

Identique à l'option --no-unsafe, mais peut être configuré sur une base par bloc. Si défini sur zéro, il supprime la génération de wrappers unsafe autour de YYPEEK. La valeur par défaut est non nulle (les wrappers sont générés). Cette configuration est spécifique à Rust.

Expressions régulières

re2java utilise la syntaxe suivante pour les expressions régulières :

"foo"
Littéral de chaîne sensible à la casse.
'foo'
Littéral de chaîne insensible à la casse.
[a-xyz], [^a-xyz]
Classe de caractères (éventuellement niée).
.
N'importe quel caractère sauf un saut de ligne.
R \ S
Différence des classes de caractères R et S.
R*
Zéro occurrence ou plus de R.
R+
Une occurrence ou plus de R.
R?
Occurrence optionnelle de R.
R{n}
Répétition de R exactement n fois.
R{n,}
Répétition de R au moins n fois.
R{n,m}
Répétition de R de n à m fois.
(R)
Simplement R ; les parenthèses sont utilisées pour remplacer la précédence. Si l'extraction de sous-correspondance est activée, (R) est un groupe capturant ou non capturant selon l'option --invert-captures.
(!R)
Si l'extraction de sous-correspondance est activée, (!R) est un groupe non capturant ou capturant selon l'option --invert-captures.
R S
Concaténation : R suivi de S.
R | S
Alternative : R ou S.
R / S
Lookahead : R suivi de S, mais S n'est pas consommé.
name
Expression régulière définie comme name (ou chaîne littérale "name" en mode compatibilité Flex).
{name}
Expression régulière définie comme name en mode compatibilité Flex.
@stag
Un s-tag : enregistre la dernière position d'entrée à laquelle @stag correspond dans une variable nommée stag.
#mtag
Un m-tag : enregistre toutes les positions d'entrée auxquelles #mtag correspond dans une variable nommée mtag.

Les classes de caractères et les littéraux de chaînes peuvent contenir les séquences d'échappement suivantes : \a, \b, \f, \n, \r, \t, \v, \\, les échappements octaux \ooo et les échappements hexadécimaux \xhh, \uhhhh et \Uhhhhhhhh.

Actions

Voici une liste des actions prédéfinies prises en charge par re2java :

!entry code
L'action d'entrée lie un bloc de code défini par l'utilisateur à l'état de départ de la machine à états finis actuelle. Si des conditions de départ sont utilisées, l'action d'entrée peut être définie individuellement pour chaque condition. Cette action peut être utilisée pour effectuer une initialisation, par exemple pour enregistrer la position de départ d'un lexème.
!pre_rule code
L'action pré-règle ajoute un bloc de code défini par l'utilisateur au début des actions sémantiques de toutes les règles du bloc actuel (ou de la condition, si des conditions de départ sont utilisées). Cette action peut être utilisée pour factoriser la partie commune de toutes les actions sémantiques (par exemple, enregistrer la position de fin d'un lexeme).
!post_rule code
L'action post-règle ajoute un bloc de code défini par l'utilisateur à la fin des actions sémantiques de toutes les règles du bloc actuel (ou de la condition, si des conditions de départ sont utilisées). Cette action peut être utilisée pour émettre des instructions de piégeage qui protègent contre les flux de contrôle involontaires.

Directives

Voici une liste complète des directives prises en charge par re2java :

!use:name ;
Une directive d'utilisation dans un bloc qui fusionne un bloc de règles défini précédemment avec le name spécifié dans le bloc actuel. Les définitions nommées, les configurations et les règles du bloc référencé sont ajoutées à ceux du bloc actuel. Les conflits entre règles et configurations qui se chevauchent sont résolus de la manière habituelle : la première règle a la priorité et la dernière configuration écrase les précédentes. Une exception concerne les règles spéciales *, $ et <!> pour lesquelles une définition locale au bloc a toujours la priorité. Une directive d'utilisation peut être placée n'importe où à l'intérieur d'un bloc, et plusieurs directives d'utilisation sont autorisées.
!include file ;
Cette directive est identique à la directive de bloc include : elle insère le contenu du fichier verbatim à la place de la directive.

Interface de programme

Le code généré interagit avec le programme externe à l'aide de primitives, collectivement appelées l'API. Les primitives qui doivent être définies pour un programme particulier dépendent de plusieurs facteurs, notamment la complexité des expressions régulières, la représentation de l'entrée, la mise en mémoire tampon et l'utilisation de diverses fonctionnalités. Toutes les primitives nécessaires doivent être définies par l'utilisateur sous forme de macros, de fonctions, de variables ou de toute autre forme appropriée qui rend le code généré syntaxiquement et sémantiquement correct. re2java ne vérifie pas (et ne peut pas vérifier) les définitions, donc si quelque chose manque ou est mal défini, le programme généré peut avoir des erreurs de compilation ou d'exécution. Ce manuel fournit des exemples de définitions d'API dans les cas les plus courants.

re2java propose trois styles d'API qui définissent l'ensemble de base des primitives utilisées par un programme :

API Simple
C'est l'API par défaut pour le backend Java. Elle se compose des primitives suivantes : YYINPUT (qui doit être défini comme une séquence d'unités de code, par exemple, une chaîne de caractères) et YYCURSOR, YYMARKER, YYCTXMARKER, YYLIMIT (qui doivent être définis comme des indices dans YYINPUT).
API Record
L'API Record est utile dans les cas où l'état du lexer doit être stocké dans une classe. Elle est activée avec l'option --api record ou la configuration re2c:api = record. Cette API se compose d'une variable yyrecord (dont le nom peut être surchargé avec re2c:yyrecord) qui doit être définie comme une classe avec les champs yyinput, yycursor, yymarker, yyctxmarker, yylimit (seuls les champs utilisés par le code généré doivent être définis, et leurs noms peuvent être configurés).
API Générique
C'est l'API la plus flexible. Elle est activée avec l'option --api generic ou la configuration re2c:api = generic. Elle contient des primitives pour les opérations génériques : YYPEEK, YYSKIP, YYBACKUP, YYBACKUPCTX, YYSTAGP, YYSTAGN, YYMTAGP, YYMTAGN, YYRESTORE, YYRESTORECTX, YYRESTORETAG, YYSHIFT, YYSHIFTSTAG, YYSHIFTMTAG, YYLESSTHAN.

Voici une liste complète des primitives d'API qui peuvent être utilisées par le code généré pour interagir avec le programme externe.

YYCTYPE
Le type des caractères d'entrée (unités de code). Pour les encodages ASCII, EBCDIC et UTF-8, il doit s'agir d'un entier non signé de 1 octet. Pour UTF-16 ou UCS-2, il doit s'agir d'un entier non signé de 2 octets. Pour UTF-32, il doit s'agir d'un entier non signé de 4 octets.
YYCURSOR
Une l-value qui stocke la position d'entrée actuelle (un pointeur ou un décalage d'entier dans YYINPUT). Initialement, YYCURSOR doit pointer vers le premier caractère d'entrée, et plus tard, il est avancé par le code généré. Lorsqu'une règle correspond, la position YYCURSOR est celle après le dernier caractère correspondant.
YYLIMIT
Une r-value qui stocke la fin de la position d'entrée (un pointeur ou un décalage d'entier dans YYINPUT). Initialement, YYLIMIT doit pointer vers la position après le dernier caractère d'entrée disponible. Il n'est pas modifié par le code généré. Le lexer compare YYCURSOR à YYLIMIT pour déterminer s'il reste suffisamment de caractères d'entrée.
YYMARKER
Une l-value qui stocke la position de la dernière règle correspondante (un pointeur ou un décalage d'entier dans YYINPUT). Elle est utilisée pour restaurer la position YYCURSOR si la correspondance la plus longue échoue et que le lexer doit revenir en arrière. Aucune initialisation n'est nécessaire.
YYCTXMARKER
Une l-value qui stocke la position du contexte final (un pointeur ou un décalage d'entier dans YYINPUT). Aucune initialisation n'est nécessaire. YYCTXMARKER n'est nécessaire que si l'opérateur de lookahead / est utilisé.
YYFILL
Une primitive d'API générique avec une variable len. YYFILL doit fournir au moins len caractères d'entrée supplémentaires ou échouer. Si re2c:eof est utilisé, alors len est toujours 1 et YYFILL doit toujours retourner à la fonction appelante ; une valeur de retour nulle indique une fin
success. Si re2c:eof n'est pas utilisé, alors la valeur de retour de YYFILL est ignorée et il ne doit pas retourner en cas d'échec. La valeur maximale de len est YYMAXFILL.
YYFN
Un primitif qui définit le prototype de fonction dans le modèle de code --recursive-functions. Sa valeur doit être un tableau d'une ou plusieurs chaînes, où chaque chaîne contient deux ou trois composants séparés par la chaîne spécifiée dans la configuration re2c:fn:sep (typiquement un point-virgule). Le premier élément du tableau définit le nom de la fonction et le type de retour (vide pour une fonction void). Les éléments suivants définissent les arguments de la fonction : premièrement, l'expression de l'argument utilisée dans le corps de la fonction (généralement juste un nom) ; deuxièmement, le type de l'argument ; troisièmement, un paramètre formel optionnel (il est par défaut le premier composant - généralement, l'argument et le paramètre sont le même identifiant).
YYINPUT
Une valeur r qui stocke la séquence de caractères d'entrée actuelle (chaîne, tampon, etc.).
YYMAXFILL
Une constante entière égale à la valeur maximale de l'argument de YYFILL. Elle peut être générée avec un bloc max.
YYLESSTHAN
Un primitif générique avec une variable len. Il doit être défini comme une valeur r de type booléen qui est égale à true si et seulement s'il reste moins de len caractères d'entrée.
YYPEEK
Un primitif générique sans variables. Il doit être défini comme une valeur r de type YYCTYPE qui est égale au caractère à la position d'entrée actuelle.
YYSKIP
Un primitif générique qui doit faire avancer la position d'entrée actuelle d'une unité de code.
YYBACKUP
Un primitif générique qui doit sauvegarder la position d'entrée actuelle (pour être restaurée plus tard avec YYRESTORE).
YYRESTORE
Un primitif générique qui doit restaurer la position d'entrée actuelle à la valeur sauvegardée par YYBACKUP.
YYBACKUPCTX
Un primitif générique qui doit sauvegarder la position d'entrée actuelle comme la position du contexte de fin (pour être restaurée plus tard avec YYRESTORECTX).
YYRESTORECTX
Un primitif générique qui doit restaurer la position du contexte de fin sauvegardée avec YYBACKUPCTX.
YYRESTORETAG
Un primitif générique avec une variable tag qui doit restaurer la position du contexte de fin à la valeur de tag.
YYSTAGP
Un primitif générique avec une variable tag, où tag peut être un pointeur ou un décalage dans YYINPUT (voir la section d'extraction des sous-correspondances pour plus de détails). YYSTAGP doit définir tag à la position d'entrée actuelle.
YYSTAGN
Un primitif générique avec une variable tag, où tag peut être un pointeur ou un décalage dans YYINPUT (voir la section d'extraction des sous-correspondances pour plus de détails). YYSTAGN doit définir tag à une valeur qui représente une position d'entrée inexistante.
YYMTAGP
Un primitif générique avec une variable tag. YYMTAGP doit ajouter la position actuelle à l'historique des sous-correspondances de tag (voir la section d'extraction des sous-correspondances pour plus de détails).
YYMTAGN
Un primitif générique avec une variable tag. YYMTAGN doit ajouter une valeur qui représente une position d'entrée inexistante à l'historique des sous-correspondances de tag (voir la section d'extraction des sous-correspondances pour plus de détails).
YYSHIFT
Un primitif générique avec une variable shift qui doit décaler la position d'entrée actuelle de shift caractères (la valeur de décalage peut être négative).
YYCOPYSTAG
Un primitif générique avec deux variables, lhs et rhs, qui doit copier la variable s-tag de droite rhs dans la variable s-tag de gauche lhs. Pour la plupart des langages, ce primitif a une définition par défaut qui assigne lhs à rhs.
YYCOPYMTAG
Un primitif générique avec deux variables, lhs et rhs, qui doit copier la variable m-tag de droite rhs dans la variable m-tag de gauche lhs. Pour la plupart des langages, ce primitif a une définition par défaut qui assigne lhs à rhs.
YYSHIFTSTAG
Un primitif générique avec deux variables, tag et shift, qui doit décaler tag de shift unités de code (la valeur de décalage peut être négative).
YYSHIFTMTAG
Un primitif générique avec deux variables, tag et shift, qui doit décaler la dernière valeur dans l'historique de tag de shift unités de code (la valeur de décalage peut être négative).
YYMAXNMATCH
Une constante entière égale au nombre maximal de groupes de capture POSIX dans une règle. Elle est générée avec un bloc maxnmatch.
YYCONDTYPE
Le type de l'énumération de condition. Il peut être généré soit avec un bloc conditions, soit avec l'option --header.
YYGETACCEPT
Un primitif avec une variable var qui stocke le sélecteur numérique de la règle acceptée. Pour la plupart des langages, ce primitif a une définition par défaut qui lit depuis var.
YYSETACCEPT
Un primitif avec deux variables : var (une valeur l (l-value) qui stocke le sélecteur numérique de la règle acceptée) et val (la valeur du sélecteur). Pour la plupart des langages, ce primitif a une définition par défaut qui assigne var à val.
YYGETCOND
Une valeur r de type YYCONDTYPE qui est égale à l'identifiant de condition actuel.
YYSETCOND
Un primitif avec une variable cond qui doit définir l'identifiant de condition actuel à cond.
YYGETSTATE
Une valeur r de type entier qui est égale à l'état actuel du lexer. Elle doit être initialisée à -1.
YYSETSTATE
Un primitif avec une variable state qui doit définir l'état actuel du lexer à state.
YYDEBUG
Ce primitif est généré uniquement avec l'option -d, --debug-output. Son but est d'ajouter de la journalisation au code généré (une définition YYDEBUG typique est une instruction d'impression). Les instructions YYDEBUG sont générées dans chaque état et ont deux variables : state (soit un index d'état DFA, soit -1) et symbol (le symbole d'entrée actuel).
yyaccept
Une valeur l de type entier non signé qui stocke le numéro de la dernière règle correspondante. La définition par l'utilisateur n'est nécessaire qu'avec l'option --storable-state.
yybm
Une table contenant des bitmaps compressées pour jusqu'à 8 transitions (utilisée avec l'option --bitmaps). La table contient 256 éléments et est indexée par des unités de code sur 1 octet. Chaque élément de 8 bits combine des valeurs booléennes pour jusqu'à 8 transitions. Le k-ième bit du n-ième élément est vrai si et seulement si la n-ième unité de code est dans la plage de la k-ième transition. L'idée de cette bitmap est de remplacer de nombreuses branches if ou cas switch par une seule vérification d'un seul bit dans la table.
yych
Une valeur l de type YYCTYPE qui stocke le caractère d'entrée actuel. La définition par l'utilisateur n'est nécessaire qu'avec l'option -f --storable-state.
yyctable
Table de sauts générée pour la distribution initiale des conditions (activée avec la combinaison des options --conditions et --computed-gotos).
yyfill
Une valeur l qui stocke le résultat de l'appel YYFILL (cela peut être nécessaire pour les langages purement fonctionnels, où YYFILL est une fonction monadique avec une valeur de retour complexe).
yynmatch
Une valeur l de type entier non signé qui stocke le nombre de groupes de capture POSIX dans la règle correspondante. Utilisée uniquement avec l'option -P --posix-captures.
yypmatch
Un tableau de valeurs l qui sont utilisées pour contenir les valeurs des balises correspondant aux parenthèses de capture dans la règle correspondante. La longueur du tableau doit être d'au moins yynmatch * 2 (généralement YYMAXNMATCH * 2 est un bon choix). Utilisée uniquement avec l'option -P --posix-captures.
yystable
Obsolète.
yystate
Une valeur l utilisée avec l'option --loop-switch pour stocker l'état actuel du DFA.
yytarget
Table de sauts qui contient les cibles de saut (adresses d'étiquettes) pour toutes les transitions d'un état. Cette table est locale à chaque état. La génération des tables yytarget est activée avec l'option --computed-gotos.

Option interne, obsolète. Elle permettait d'activer l'algorithme TDFA(0). Contrairement à TDFA(1), l'algorithme TDFA(0) n'utilise pas d'anticipation d'un symbole. Il applique des opérations de registre aux transitions entrantes plutôt qu'aux transitions sortantes. Les benchmarks ont montré que l'algorithme TDFA(0) est moins performant que TDFA(1).

Option interne : supprime l'optimisation des variables de balise (utile pour le débogage).

Option interne : spécifie l'algorithme de chemin le plus court utilisé pour la construction de la fermeture epsilon avec sémantique de désambiguïsation POSIX : gor1 (le défaut) signifie l'algorithme de Goldberg-Radzik, et gtop signifie l'algorithme de "l'ordre topologique global".
--posix-prectable <complex | naive>
Option interne : spécifie l'algorithme utilisé pour calculer la table de précédence POSIX. L'algorithme complex calcule la table de précédence en un seul parcours de l'arbre d'historique des balises et a une complexité quadratique par rapport au nombre d'états TNFA ; c'est le défaut. L'algorithme naive a une complexité cubique dans le pire des cas par rapport au nombre d'états TNFA, mais il est beaucoup plus simple que complex et peut être légèrement plus rapide dans des cas non pathologiques.
--stadfa
Option interne, obsolète. Elle permettait d'activer l'algorithme staDFA, qui diffère de TDFA en ce que les opérations de registre sont placées dans les états plutôt que sur les transitions. Les benchmarks ont montré que l'algorithme staDFA est moins performant que TDFA.
--fixed-tags <none | toplevel | all>
Option interne : spécifie si l'optimisation des balises fixes doit être appliquée à toutes les balises ( all ), à aucune d'entre elles ( none ), ou seulement à celles dans la concaténation de niveau supérieur ( toplevel ). Le défaut est all. Les balises "fixes" sont celles qui sont situées à une distance fixe d'une autre balise (appelée "base"). Dans de tels cas, seule la balise de base doit être suivie, et la valeur de la balise fixe peut être calculée comme la valeur de la balise de base plus un décalage statique. Pour les balises qui sont sous alternative ou répétition, il est également nécessaire de vérifier si la balise de base a une valeur de non-correspondance (dans ce cas, la balise fixe doit également être définie sur non-correspondance, ignorant le décalage). Pour les balises dans une concaténation de niveau supérieur, la vérification n'est pas nécessaire, car elles correspondent toujours.

Fichiers de syntaxe

Le support des différents langages dans re2c repose sur l'idée de fichiers de syntaxe. Un fichier de syntaxe est un fichier de configuration qui définit la syntaxe du langage cible -- pas tout le langage, mais une petite partie de celui-ci utilisée par le code généré. Les fichiers de syntaxe rendent re2c très flexible, mais ils ne doivent pas être utilisés comme substituts des configurations re2c:: leur but est de définir la syntaxe du langage cible, pas de personnaliser un lexer particulier. Tous les langages supportés ont des fichiers de syntaxe par défaut qui font partie de la distribution (voir le sous-répertoire include/syntax); ils sont également intégrés dans le binaire re2java. Les utilisateurs peuvent fournir un fichier de syntaxe personnalisé qui remplace quelques configurations pour l'un des langages supportés, ou ils peuvent choisir de redéfinir toutes les configurations (dans ce cas, l'option --lang none doit être utilisée). Les fichiers de syntaxe contiennent des configurations de quatre types différents : listes de fonctionnalités, configurations de langage, configurations "inplace" et modèles de code.

Une liste des API supportées avec les éléments possibles simple, record, generic.
supported_api_styles
Une liste des styles d'API supportés avec les éléments possibles functions, free-form.
supported_code_models
Une liste des modèles de code supportés avec les éléments possibles goto-label, loop-switch, recursive-functions.
supported_targets
Une liste des cibles de génération de code supportées avec les éléments possibles code, dot, skeleton.
supported_features
Une liste des fonctionnalités supportées avec les éléments possibles nested-ifs, bitmaps, computed-gotos, case-ranges, monadic, unsafe, tags, captures, captvars.

Modèles de code

Les modèles de code définissent la syntaxe du langage cible. Ils sont écrits dans un langage simple spécifique à un domaine avec la grammaire formelle suivante : 
code-template ::
      name '=' code-exprs ';'
    | CODE_TEMPLATE ';'
    | '<undefined>' ';'
code-exprs ::
      <EMPTY>
    | code-exprs code-expr
code-expr ::
      STRING
    | VARIABLE
    | optional
    | list
optional ::
      '(' CONDITIONAL '?' code-exprs ')'
    | '(' CONDITIONAL '?' code-exprs ':' code-exprs ')'
list ::
      '[' VARIABLE ':' code-exprs ']'
    | '[' VARIABLE '{' NUMBER '}' ':' code-exprs ']'
    | '[' VARIABLE '{' NUMBER ',' NUMBER '}' ':' code-exprs ']'

Un modèle de code est une séquence de littéraux de chaîne, de variables, d'éléments optionnels et de listes, ou une référence à un autre modèle de code, ou une valeur spéciale <undefined>. Les variables sont des espaces réservés qui sont substitués lors de la phase de génération de code. Les variables de liste sont spéciales : lors de l'expansion des modèles de liste, re2java répète les expressions de la partie droite de la colonne plusieurs fois, remplaçant à chaque fois les occurrences de la variable de liste par une valeur spécifique à cette répétition. Les listes ont des bornes optionnelles (les valeurs négatives sont comptées à partir de la fin, par exemple -1 signifie le dernier élément). Les noms conditionnels commencent par un point. Les conditionnels et les variables peuvent être locaux (spécifiques au modèle de code donné) ou globaux (autorisés dans tous les modèles de code). Lorsque re2java lit le fichier de syntaxe, il vérifie que chaque modèle de code n'utilise que les variables et les conditionnels qui y sont autorisés.

Par exemple, le modèle de code suivant définit la construction si-alors-sinon pour un langage de type C :

code:if_then_else =
    [branch{0}: topindent "if " cond " {" nl
        indent [stmt: stmt] dedent]
    [branch{1:-1}: topindent "} else" (.cond ? " if " cond) " {" nl
        indent [stmt: stmt] dedent]
    topindent "}" nl;

Ici, branch est une variable de liste : branch{0} s'étend à la première branche (qui est spéciale, car il n'y a pas de partie else), branch{1:-1} s'étend à toutes les branches restantes (s'il y en a). stmt est également une variable de liste : [stmt: stmt] est une liste imbriquée qui s'étend à une liste d'instructions dans le corps de la branche actuelle. topindent, indent, dedent et nl sont des variables globales, et .cond est un conditionnel local (leur signification est décrite ci-dessous). Ce modèle de code pourrait produire le code suivant :

if x {
    // faire quelque chose
} else if y {
    // faire autre chose
} else {
    // ne rien faire
}

GESTION DE LA FIN DU FLUX ENTRANT

L'un des principaux problèmes pour le lexer est de savoir quand s'arrêter. Il existe quelques conditions de terminaison :

  • le lexer peut correspondre à une règle (y compris la règle par défaut *) et arriver à un état final
  • le lexer peut ne pas correspondre à une règle et arriver à un état par défaut
  • le lexer peut atteindre la fin du flux entrant

Les deux premières conditions terminent le lexer de manière « naturelle » : il arrive à un état sans transition sortante, et la correspondance s'arrête automatiquement. La troisième condition, la fin du flux entrant, est différente : elle peut se produire dans n'importe quel état, et le lexer doit être capable de la gérer. La vérification de la fin du flux entrant interrompt le flux de travail normal du lexer et ajoute des branches conditionnelles au programme généré, il est donc nécessaire de minimiser le nombre de ces vérifications. re2java prend en charge plusieurs méthodes différentes pour gérer la fin du flux entrant. Celle à utiliser dépend de la complexité des expressions régulières, du besoin de mise en tampon, des considérations de performance et d'autres facteurs. Voici une liste de méthodes :

  • Sentinelle. Cette méthode élimine le besoin de vérifications de fin de flux entrant. Elle est simple et efficace, mais limitée au cas où il existe un caractère « sentinelle » naturel qui ne peut jamais apparaître dans une entrée valide. Ce caractère peut toujours apparaître dans une entrée invalide, mais il ne devrait pas être autorisé par les expressions régulières, sauf peut-être comme dernier caractère d'une règle. La sentinelle est ajoutée à la fin du flux entrant et sert de signal d'arrêt : lorsque le lexer lit ce caractère, il s'agit soit d'une erreur de syntaxe, soit de la fin du flux entrant. Dans les deux cas, le lexer doit s'arrêter. Cette méthode est utilisée si YYFILL est désactivé avec re2c:yyfill:enable = 0 ; et si re2c:eof a la valeur par défaut -1.
  • Sentinelle avec vérifications de limites. Cette méthode est générique : elle permet de gérer n'importe quelle entrée sans restriction sur les expressions régulières. L'idée est de réduire le nombre de vérifications de fin de flux entrant en ne les effectuant que sur certains caractères. Similaire à la méthode « sentinelle », l'un des caractères est choisi comme « sentinelle » et ajouté à la fin du flux entrant. Cependant, il n'y a aucune restriction sur l'endroit où la sentinelle peut apparaître (en fait, n'importe quel caractère peut être choisi comme sentinelle). Lorsque le lexer lit ce caractère, il effectue en plus une vérification de limites. Si la position actuelle est dans les limites, le lexer reprend la correspondance et gère la sentinelle comme un caractère normal. Sinon, il invoque YYFILL (sauf si elle est désactivée). Si plus de flux entrant est fourni, le lexer re-correspondra au dernier caractère et continuera comme si la sentinelle n'était pas là. Sinon, ce doit être la vraie fin du flux entrant, et le lexer s'arrête. Cette méthode est utilisée lorsque re2c:eof a une valeur non négative (elle doit être définie sur la valeur numérique de la sentinelle). YYFILL est facultatif.
  • Vérifications de limites avec remplissage. Cette méthode est générique, et elle peut être plus rapide que la méthode « sentinelle avec vérifications de limites », mais elle est aussi plus complexe. L'idée est de partitionner les états du DFA en composantes fortement connexes (SCC) et de générer une seule vérification par SCC pour suffisamment de caractères afin de couvrir le chemin non bouclé le plus long dans cette SCC. Cela réduit le nombre de vérifications, mais il y a un problème avec les lexèmes courts en fin de flux entrant, car la vérification nécessite suffisamment de caractères pour couvrir le lexème le plus long. Cela peut être corrigé en remplissant le flux entrant avec quelques caractères factices qui ne forment pas un suffixe de lexème valide (de sorte que le lexer ne puisse pas les faire correspondre). La longueur du remplissage doit être YYMAXFILL, générée avec un bloc max. S'il n'y a pas assez de flux entrant, le lexer invoque YYFILL qui doit fournir au moins le nombre requis de caractères ou ne pas retourner. Cette méthode est utilisée si YYFILL est activé et si re2c:eof est -1 (c'est la configuration par défaut).
  • Vérifications personnalisées. L'API générique permet de remplacer les opérations de base telles que la lecture d'un caractère, ce qui rend possible d'inclure les vérifications de fin de flux entrant dans celles-ci. Cette approche est sujette aux erreurs et doit être utilisée avec prudence. Pour utiliser une méthode personnalisée, activez l'API générique avec --api custom ou re2c:api = custom ; et désactivez les vérifications de limites par défaut avec re2c:yyfill:enable = 0 ; ou re2c:yyfill:check = 0 ;.

Les sous-sections suivantes contiennent un exemple de chaque méthode.

Sentinelle

Cet exemple utilise un caractère sentinelle pour gérer la fin du flux entrant. Le programme compte les mots séparés par des espaces dans une chaîne terminée par un caractère nul. La sentinelle est le caractère nul : c'est le dernier caractère de chaque chaîne d'entrée, et il n'est pas autorisé au milieu d'un lexème par aucune des règles (en particulier, il n'est pas inclus dans les plages de caractères où il est facile de l'oublier). Si un caractère nul apparaît au milieu d'une chaîne, c'est une erreur de syntaxe et le lexer correspondra à la règle par défaut *, mais il ne lira pas au-delà de la fin du flux entrant et ne plantera pas (utilisez l'avertissement -Wsentinel-in-midrule et la configuration re2c:sentinel pour le vérifier). La configuration re2c:yyfill:enable = 0 ; supprime la génération des vérifications de limites et des invocations de YYFILL.

// re2java $INPUT -o $OUTPUT
class Main {
    // Attend une chaîne terminée par un caractère nul.
    static int lex(String yyinput) {
        int yycursor = 0;
        int count = 0;
        loop: while (true) {
            /*!re2c
                re2c:YYCTYPE = "char";
                re2c:YYPEEK = "yyinput.charAt(yycursor)";
                re2c:yyfill:enable = 0;
                *      { return -1; }
                [\x00] { return count; }
                [a-z]+ { count += 1; continue loop; }
                [ ]+   { continue loop; }
            */
        }
    }
    public static void main(String []args) {
        assert lex("\0") == 0;
        assert lex("one two three\0") == 3;
        assert lex("f0ur\0") == -1;
    }
};

Sentinelle avec vérifications de limites

Cet exemple utilise une sentinelle avec des vérifications de limites pour gérer la fin du flux entrant (cette méthode a été ajoutée dans la version 1.2). Le programme compte les chaînes d'un seul guillemet séparées par des espaces. Le caractère sentinelle est le caractère nul, spécifié avec la configuration re2c:eof = 0 ;. Comme dans la méthode sentinel, le caractère nul est le dernier caractère de chaque chaîne d'entrée, mais il est autorisé au milieu d'une règle (par exemple, 'aaa\0aa'\0 est une entrée valide, mais 'aaa\0 est une erreur de syntaxe). Des vérifications de limites sont générées dans chaque état qui correspond à un caractère d'entrée, mais elles sont limitées à la branche qui gère le caractère nul. Les vérifications de limites sont de la forme YYLIMIT ou YYLESSTHAN(1) avec l'API générique. Si la condition de vérification est vraie, le lexer a atteint la fin du flux entrant et doit s'arrêter (YYFILL est désactivé avec re2c:yyfill:enable = 0 ; car le flux entrant tient dans un seul tampon, voir la section « YYFILL avec sentinelle » pour un exemple qui utilise YYFILL). Atteindre la fin du flux entrant ouvre trois possibilités : si le lexer est dans l'état initial, il correspondra à la règle de fin de flux entrant $, sinon il peut revenir à une règle précédemment correspondante (y compris la règle par défaut *) ou passer à un d

par défaut, provoquant -Wundefined-control-flow.

// re2java $INPUT -o $OUTPUT
class Main {
    // Attend une chaîne terminée par un caractère nul.
    static int lex(String yyinput) {
        int yycursor = 0;
        int yymarker = 0;
        int yylimit = yyinput.length() - 1; // yylimit pointe vers le caractère nul de terminaison
        int count = 0;
        loop: while (true) {
            /*!re2c
                re2c:YYCTYPE = "char";
                re2c:YYPEEK = "yyinput.charAt(yycursor)";
                re2c:yyfill:enable = 0;
                re2c:eof = 0;
                str = ['] ([^'\\] | [\\][^])* ['];
                *    { return -1; }
                $    { return count; }
                str  { count += 1; continue loop; }
                [ ]+ { continue loop; }
            */
        }
    }
    public static void main(String []args) {
        assert lex("\0") == 0;
        assert lex("'qu\0tes' 'are' 'fine: \\'' \0") == 3;
        assert lex("'unterminated\\'\0") == -1;
    }
};

Vérifications des limites avec remplissage

Cet exemple utilise des vérifications de limites avec remplissage pour gérer la fin de l'entrée (cette méthode est activée par défaut). Le programme compte les chaînes entre guillemets simples séparées par des espaces. Un remplissage de YYMAXFILL caractères nuls est ajouté à la fin de l'entrée, où la valeur de YYMAXFILL est générée automatiquement avec un bloc max. Il n'est pas nécessaire d'utiliser des zéros pour le remplissage --- n'importe quels caractères peuvent être utilisés tant qu'ils ne forment pas un suffixe de lexème valide (dans cet exemple, le remplissage ne doit pas contenir de guillemets simples, car ils pourraient être confondus avec un suffixe d'une chaîne entre guillemets simples). Il existe une règle d'arrêt qui correspond au premier caractère de remplissage (zéro) et termine le lexer (notez qu'il vérifie si le zéro est au début du remplissage, sinon c'est une erreur de syntaxe). Les vérifications de limites ne sont générées que dans certains états déterminés par les composantes fortement connexes de l'automate sous-jacent. Les vérifications prennent la forme (YYLIMIT - YYCURSOR) < n ou YYLESSTHAN(n) avec l'API générique, où n est le nombre minimum de caractères nécessaires au lexer pour continuer (cela signifie également que la prochaine vérification de limite se produira dans au plus n caractères). Si la condition de vérification est vraie, le lexer a atteint la fin de l'entrée et appellera YYFILL(n) qui doit soit fournir au moins n caractères d'entrée, soit ne pas retourner. Dans cet exemple, YYFILL échoue toujours et termine le lexer avec une erreur (ce qui est acceptable car l'entrée tient dans un seul tampon). Voir la section YYFILL avec remplissage pour un exemple qui recharge le tampon d'entrée avec YYFILL.

// re2java $INPUT -o $OUTPUT
class Main {
    /*!max:re2c*/
    // Attend une chaîne remplie avec yymaxfill zéros.
    static int lex(String str) {
        // Remplit la chaîne avec yymaxfill zéros à la fin.
        byte[] yyinput = new byte[str.length() + YYMAXFILL];
        System.arraycopy(str.getBytes(), 0, yyinput, 0, str.length());
        int yycursor = 0;
        int yylimit = yyinput.length;
        int count = 0;
        loop: while (true) {
            /*!re2c
                re2c:YYCTYPE = "byte";
                re2c:YYPEEK = "yyinput[yycursor]";
                re2c:YYFILL = "return -1;";
                str = ['] ([^'\\] | [\\][^])* ['];
                [\x00] {
                    // Vérifie qu'il s'agit du sentinelle, pas d'un zéro inattendu.
                    return (yycursor - 1 == str.length()) ? count : -1;
                }
                str  { count += 1; continue loop; }
                [ ]+ { continue loop; }
                *    { return -1; }
            */
        }
    }
    public static void main(String []args) {
        assert lex("") == 0;
        assert lex("'qu\0tes' 'are' 'fine: \\'' ") == 3;
        assert lex("'unterminated\\'") == -1;
        assert lex("'unexpected \00 null\\'") == -1;
    }
};

Vérifications personnalisées

Cet exemple utilise une méthode personnalisée de gestion de fin d'entrée basée sur l'API générique. Le programme compte les chaînes entre guillemets simples séparées par des espaces. C'est le même exemple que celui du sentinelle, à l'exception que l'entrée n'est pas terminée par un caractère nul. Pour compenser l'absence d'un caractère sentinelle à la fin de l'entrée, YYPEEK est redéfini pour effectuer une vérification de limites avant de lire le prochain caractère d'entrée. Ceci est inefficace car les vérifications sont effectuées très fréquemment. Si la condition de vérification échoue, YYPEEK renvoie le vrai caractère, sinon il renvoie un faux caractère sentinelle.

// re2java $INPUT -o $OUTPUT
class Main {
    // Attend une chaîne sans caractère nul de terminaison.
    static int lex(String str) {
        byte[] yyinput = str.getBytes();
        int yycursor = 0;
        int count = 0;
        loop: while (true) {
            /*!re2c
                re2c:api = generic;
                re2c:YYCTYPE = "byte";
                re2c:YYPEEK = "(yycursor < yyinput.length) ? yyinput[yycursor] : 0";
                re2c:YYSKIP = "yycursor += 1;";
                re2c:yyfill:enable = 0;
                *      { return -1; }
                [\x00] { return count; }
                [a-z]+ { count += 1; continue loop; }
                [ ]+   { continue loop; }
            */
        }
    }
    public static void main(String []args) {
        assert lex("") == 0;
        assert lex("one two three") == 3;
        assert lex("f0ur") == -1;
    }
};

RECHARGEMENT DU TAMPON

Le besoin de mise en tampon survient lorsque l'entrée ne peut pas être mappée en mémoire d'un seul coup : soit elle est trop grande, soit elle arrive de manière séquentielle (comme la lecture depuis un socket). La technique habituelle dans de tels cas est d'allouer un tampon de taille fixe et de traiter l'entrée par morceaux qui tiennent dans le tampon. Lorsque le morceau actuel est traité, il est déplacé et de nouvelles données sont chargées. En pratique, c'est un peu plus complexe, car l'état du lexer ne se compose pas d'une seule position d'entrée, mais d'un ensemble de positions interdépendantes :

  • curseur : le prochain caractère d'entrée à lire (YYCURSOR dans l'API de pointeur C ou YYSKIP/YYPEEK dans l'API générique)
  • limite : la position après le dernier caractère d'entrée disponible (YYLIMIT dans l'API de pointeur C, gérée implicitement par YYLESSTHAN dans l'API générique)
  • marqueur : la position de la correspondance la plus récente, le cas échéant (YYMARKER dans l'API par défaut ou YYBACKUP/YYRESTORE dans l'API générique)
  • token : le début du lexème courant (implicite dans l'API re2java, car il n'est pas nécessaire pour le fonctionnement normal du lexer et peut être défini et mis à jour par l'utilisateur)
  • marqueur de contexte : la position du contexte de suffixe (YYCTXMARKER dans l'API de pointeur C ou YYBACKUPCTX/YYRESTORECTX dans l'API générique)
  • variables de tag : positions de sous-correspondance (définies avec les blocs stags et mtags et les primitives de l'API générique YYSTAGP/YYSTAGN/YYMTAGP/YYMTAGN)

Tous ces éléments ne sont pas utilisés dans tous les cas, mais s'ils le sont, ils doivent être mis à jour par YYFILL. Toutes les positions actives se trouvent dans le segment entre le token et le curseur, donc tout ce qui se trouve entre le début du tampon et le token peut être écarté, le segment allant du token jusqu'à la limite doit être déplacé au début du tampon, et l'espace libre à la fin du tampon doit être rempli avec de nouvelles données. Afin d'éviter des appels fréquents à YYFILL, il est préférable de remplir autant de caractères d'entrée que possible (même si moins de caractères pourraient suffire pour reprendre le lexer). Les détails de l'implémentation de YYFILL diffèrent légèrement en fonction de la méthode de gestion de la fin de fichier utilisée : le cas de la règle EOF est un peu plus simple que le cas de la vérification de limites avec remplissage. Notez également que si l'option -f --storable-state est utilisée, YYFILL a une sémantique légèrement différente (décrite dans la section sur l'état stockable).

YYFILL avec sentinelle

Si la règle EOF est utilisée, YYFILL est une primitive de type fonction qui n'accepte aucun argument et renvoie une valeur qui est comparée à zéro. L'invocation de YYFILL est déclenchée par la condition YYLIMIT <= YYCURSOR dans l'API de pointeur C et YYLESSTHAN() dans l'API générique. Une valeur de retour non nulle signifie que YYFILL a échoué. Un appel réussi à YYFILL doit fournir au moins un caractère et ajuster les positions d'entrée en conséquence. La limite doit toujours être définie à un après la dernière position d'entrée dans le tampon, et le caractère à la position de limite doit être le symbole sentinelle spécifié par la configuration re2c:eof. Les schémas ci-dessous montrent les positions relatives des positions d'entrée dans le tampon avant et après l'appel à YYFILL (le symbole sentinelle est marqué par #, et la deuxième image montre le cas où il n'y a pas assez d'entrée pour remplir tout le tampon).

>-A------------B---------C-------------D------------E#->

Voici un exemple de programme qui lit le fichier d'entrée input.txt par blocs de 4096 octets et utilise la règle EOF.

// re2java $INPUT -o $OUTPUT
import java.io.*;
import java.nio.file.*;
class Lexer {
    public static final int BUFSIZE = 4096;
    private BufferedInputStream stream;
    private byte[] yyinput;
    private int yycursor;
    private int yymarker;
    private int yylimit;
    private int token;
    private boolean eof;
    public Lexer(File file) throws FileNotFoundException {
        stream = new BufferedInputStream(new FileInputStream(file));
        // Le sentinelle à l'offset `yylimit` est défini à zéro, ce qui déclenche YYFILL.
        yyinput = new byte[BUFSIZE + 1];
        yycursor = yymarker = yylimit = token = BUFSIZE;
        eof = false;
    }
    private int fill() throws IOException {
        if (eof) { return -1; } // EOF inattendu
        // Erreur : lexème trop long. Dans la vraie vie, on peut réallouer un tampon plus grand.
        if (token < 1) { return -2; }
        // Décale le contenu du tampon (écarte tout jusqu'au token courant).
        System.arraycopy(yyinput, token, yyinput, 0, yylimit - token);
        yycursor -
= token;
        yymarker -= token;
        yylimit -= token;
        token = 0;
        // Fill free space at the end of buffer with new data from file.
        yylimit += stream.read(yyinput, yylimit, BUFSIZE - yylimit);
        yyinput[yylimit] = 0; // append sentinel symbol
        // If read less than expected, this is the end of input.
        eof = yylimit < BUFSIZE;
        return 0;
    }
    // Expects a null-terminated string.
    public int lex() throws IOException {
        int count = 0;
        loop: while (true) {
            token = yycursor;
            /*!re2c
                re2c:YYCTYPE = "byte";
                re2c:YYPEEK = "yyinput[yycursor]";
                re2c:YYFILL = "fill() == 0";
                re2c:eof = 0;
                str = ['\\][^']*['\\] | [^'\\] ;
                *    { return -1; }
                $    { return count; }
                str  { count += 1; continue loop; }
                [ ]+ { continue loop; }
            */
        }
    }
    public static void main(String []args) throws FileNotFoundException, IOException {
        String fname = "input";
        String content = "'qu\0tes' 'are' 'fine: \\'' ".repeat(Lexer.BUFSIZE);
        // Prepare input file: a few times the size of the buffer, containing
        // strings with zeroes and escaped quotes.
        Files.writeString(Paths.get(fname), content);
        int count = 3 * Lexer.BUFSIZE; // number of quoted strings written to file
        // Prepare lexer state: all offsets are at the end of buffer.
        File file = new File(".", fname);
        Lexer lexer = new Lexer(file);
        // Run the lexer.
        int n = lexer.lex();
        assert n == count;
        // Cleanup: remove input file.
        file.delete();
    }
};

YYFILL avec remplissage

Dans le cas par défaut (lorsque la règle EOF n'est pas utilisée), YYFILL est une primitive de type fonction qui accepte un seul argument et ne retourne aucune valeur. L'invocation de YYFILL est déclenchée par la condition (YYLIMIT - YYCURSOR) < n dans l'API de pointeur C et YYLESSTHAN(n) dans l'API générique. L'argument passé à YYFILL est le nombre minimal de caractères qui doivent être fournis. S'il ne parvient pas à le faire, YYFILL ne doit pas retourner au lexer (pour cette raison, il est préférable de l'implémenter comme une macro qui retourne de la fonction appelante en cas d'échec). En cas d'invocation réussie de YYFILL, la position limite doit être définie soit après la dernière position d'entrée dans le tampon, soit à la fin du remplissage de YYMAXFILL (dans le cas où YYFILL a lu avec succès au moins n caractères, mais pas assez pour remplir tout le tampon). Les images ci-dessous montrent les positions relatives des entrées dans le tampon avant et après l'invocation de YYFILL (le remplissage de YYMAXFILL dans la deuxième image est marqué par des symboles #).

               <-- shift -->                 <-- need -->
             >-A------------B---------C-----D-------E---F--------G->
             buffer       token    marker cursor  limit
>-A------------B---------C-----D-------E---F--------G->
             buffer,  marker cursor               limit
             token
               <-- shift -->                 <-- need -->

>-A------------B---------C-----D-------E-F###############

Voici un exemple de programme qui lit le fichier d'entrée input.txt par blocs de 4096 octets et utilise la vérification des limites avec remplissage.

// re2java $INPUT -o $OUTPUT
import java.io.*;
import java.nio.file.*;
import java.util.Arrays;
class Lexer {
    /*!max:re2c*/
    public static final int BUFSIZE = 4096;
    private BufferedInputStream stream;
    private byte[] yyinput;
    private int yycursor;
    private int yylimit;
    private int token;
    private boolean eof;
    public Lexer(File file) throws FileNotFoundException {
        stream = new BufferedInputStream(new FileInputStream(file));
        // Prepare lexer state: all offsets are at the end of buffer.
        // This immediately triggers YYFILL, as the YYLESSTHAN condition is true.
        yyinput = new byte[BUFSIZE + YYMAXFILL];
        yycursor = yylimit = token = BUFSIZE;
        eof = false;
    }
    private int fill(int need) throws IOException {
        if (eof) { return -1; } // unexpected EOF
        // Error: lexeme too long. In real life can reallocate a larger buffer.
        if (token < need) { return -2; }
        // Shift buffer contents (discard everything up to the current token).
        System.arraycopy(yyinput, token, yyinput, 0, yylimit - token);
        yycursor -= token;
        yylimit -= token;
        token = 0;
        // Fill free space at the end of buffer with new data from file.
        yylimit += stream.read(yyinput, yylimit, BUFSIZE - yylimit);
        yyinput[yylimit] = 0; // append sentinel symbol
        // If read less than expected, this is the end of input.
        if (yylimit < BUFSIZE) {
            eof = true;
            Arrays.fill(yyinput, yylimit, yylimit + YYMAXFILL, (byte)0);
            yylimit += YYMAXFILL;
        }
        return 0;
    }
    // Expects a null-terminated string.
    public int lex() throws IOException {
        int count = 0;
        loop: while (true) {
            token = yycursor;
            /*!re2c
                re2c:YYCTYPE = "byte";
                re2c:YYPEEK = "yyinput[yycursor]";
                re2c:YYFILL = "if (fill(@@) != 0) { return -2; }";
                str = ['\\][^']*['\\] | [^'\\] ;
                [\x00] {
                    // Check that it is the sentinel, not some unexpected null.
                    return (token == yylimit - YYMAXFILL) ? count : -1;
                }
                str  { count += 1; continue loop; }
                [ ]+ { continue loop; }
                *    { return -1; }
            */
        }
    }
    public static void main(String []args) throws FileNotFoundException, IOException {
        String fname = "input";
        String content = "'qu\0tes' 'are' 'fine: \\'' ".repeat(Lexer.BUFSIZE);
        // Prepare input file: a few times the size of the buffer, containing
        // strings with zeroes and escaped quotes.
        Files.writeString(Paths.get(fname), content);
        int count = 3 * Lexer.BUFSIZE; // number of quoted strings written to file
        // Prepare lexer state: all offsets are at the end of buffer.
        File file = new File(".", fname);
        Lexer lexer = new Lexer(file);
        // Run the lexer.
        int n = lexer.lex();
        assert n == count;
        // Cleanup: remove input file.
        file.delete();
    }
};

FONCTIONNALITÉS

Blocs multiples

Il est parfois nécessaire d'avoir plusieurs lexers interconnectés (par exemple, s'il existe une machine à états de haut niveau qui passe d'un mode lexer à l'autre). Cela peut être implémenté en utilisant plusieurs blocs re2java connectés. Une autre option est d'utiliser des conditions de départ.

L'implémentation des connexions entre les blocs dépend de la langue cible. Dans les langages qui ont une instruction goto (comme C/C++ et Go), on peut avoir tous les blocs dans une seule fonction, chacun d'eux préfixé par une étiquette. La transition d'un bloc à un autre est un simple goto. Dans les langages qui n'ont pas de goto (comme Rust), il est nécessaire d'utiliser une boucle avec un switch sur une variable d'état, similaire à la boucle/switch yystate générée par re2java, ou alors d'encapsuler chaque bloc dans une fonction et d'utiliser des appels de fonction.

L'exemple ci-dessous utilise plusieurs blocs pour analyser les nombres binaires, octaux, décimaux et hexadécimaux. Chaque base a son propre bloc. Le bloc initial détermine la base et distribue le contrôle aux autres blocs. Les configurations communes sont définies dans un bloc séparé au début du programme ; elles sont héritées par les autres blocs.

// re2java $INPUT -o $OUTPUT
class Parser {
    private String yyinput;
    private int yycursor;
    private int yymarker;
    private int number;
    private void add_digit(int base, int offset) throws ArithmeticException {
        number = Math.addExact(
            Math.multiplyExact(number, base),
            yyinput.charAt(yycursor - 1) - offset);
    }
    public int parse(String str) throws ArithmeticException, IllegalArgumentException {
        yyinput = str;
        yycursor = 0;
        number = 0;
        try {
            /*!re2c
                re2c:YYCTYPE = "char";
                re2c:YYPEEK = "yyinput.charAt(yycursor)";
                re2c:yyfill:enable = 0;
                end = "\x00";
                '0b' / [01]        { return parse_bin(); }
                "0"                { return parse_oct(); }
                ""   / [1-9]       { return parse_dec(); }
                '0x' / [0-9a-fA-F] { return parse_hex(); }
                *                  { throw new IllegalArgumentException("not a number"); }
            */
        } catch (Exception e) {
            return -1;
        }
    }
    private int parse_bin() throws ArithmeticException, IllegalArgumentException {
        /*!re2c
            end   { return number; }
            [01]  { add_digit(2, 48); return parse_bin(); }
            *     { throw new IllegalArgumentException("ill-formed binary number"); }
        */
    }
    private int parse_oct() throws ArithmeticException, IllegalArgumentException {
        /*!re2c
            end   { return number; }
            [0-7] { add_digit(8, 48); return parse_oct(); }
            *     { throw new IllegalArgumentException("ill-formed octal number"); }
        */
    }
    private int parse_dec() throws ArithmeticException, IllegalArgumentException {
        /*!re2c
            end   { return number; }
            [0-9] { add_digit(10, 48); return parse_dec(); }
            *     { throw new IllegalArgumentException("ill-formed decimal number"); }
        */
    }
    private int parse_hex() throws ArithmeticException, IllegalArgumentException {
        /*!re2c
            end   { return number; }
            [0-9] { add_digit(16, 48); return parse_hex(); }
            [a-f] { add_digit(16, 87); return parse_hex(); }
            [A-F] { add_digit(16, 55); return parse_hex(); }
            *     { throw new IllegalArgumentException("ill-formed hexadecimal number"); }
        */
    }
    public static void main(String []args) {
        Parser parser = new Parser();

Conditions de départ

Start conditions

Les conditions de départ sont activées avec l'option --start-conditions. Elles fournissent un moyen d'encoder plusieurs automates interdépendant dans le même bloc re2java.

Chaque condition correspond à un automate unique et possède un nom unique spécifié par l'utilisateur et un numéro interne unique défini par re2java. Les numéros sont utilisés pour basculer entre les conditions : le code généré utilise les primitives YYGETCOND et YYSETCOND pour obtenir la condition actuelle ou la définir au numéro donné. Utilisez le bloc conditions, l'option --header ou la configuration re2c:header pour générer des identificateurs numériques de condition. La configuration re2c:cond:enumprefix spécifie le préfixe de l'identificateur généré.

En mode condition, chaque règle doit être préfixée par une liste de noms de conditions séparés par des virgules entre chevrons, ou par un joker <*> pour désigner toutes les conditions. La syntaxe de la règle est étendue comme suit :

< condition-list > regular-expression code
Une règle qui est fusionnée à chaque condition de la condition-list. Elle correspond à l'expression régulière regular-expression et exécute le code associé.
< condition-list > regular-expression => condition code
Une règle qui est fusionnée à chaque condition de la condition-list. Elle correspond à l'expression régulière regular-expression, définit la condition actuelle à condition et exécute le code associé.
< condition-list > regular-expression :=> condition
Une règle qui est fusionnée à chaque condition de la condition-list. Elle correspond à l'expression régulière regular-expression et bascule immédiatement vers condition (il n'y a pas d'action sémantique).
< condition-list > !action code
Une règle qui lie le code à l'endroit défini par action dans chaque condition de la condition-list (voir la section actions pour les différents types d'actions).
<! condition-list > code
Une règle qui ajoute code en préfixe aux actions sémantiques de toutes les règles pour chaque condition de la condition-list. Cette syntaxe est obsolète et l'action !pre_rule devrait être utilisée à la place (elle fait exactement la même chose).
< > code
Une règle qui crée une condition d'entrée spéciale avec le numéro zéro et le nom "0" qui exécute le code avant de basculer vers d'autres conditions. Cette syntaxe est obsolète et l'action !entry devrait être utilisée à la place (elle offre un contrôle plus fin, car le code peut être spécifié par condition, et on peut basculer directement vers le début de la condition sans passer par le dispatch des conditions).
< > => condition code
Identique à la règle précédente, sauf qu'elle définit la prochaine condition.
< > :=> condition
Identique à la règle précédente, sauf qu'elle n'a pas de code associé et bascule immédiatement vers condition.

Le code que re2java génère pour les conditions dépend de si re2java utilise une approche goto/label ou une approche loop/switch pour encoder les automates.

Dans les langages qui ont une instruction goto (comme C/C++ et Go), les conditions sont naturellement implémentées comme des blocs de code préfixés par des labels de la forme yyc_<cond>, où cond est un nom de condition (le préfixe du label peut être modifié avec re2c:cond:prefix). Les transitions entre les conditions sont implémentées en utilisant goto et des labels de condition. Avant toutes les conditions, re2java génère un switch initial sur YYGETSTATE qui bascule vers l'état de départ de la condition actuelle. Les règles de raccourci :=> contournent le switch initial et basculent directement vers la condition spécifiée (re2c:cond:goto peut être utilisé pour modifier le comportement par défaut). Les règles avec des actions sémantiques ne basculent pas automatiquement vers la condition suivante ; cela doit être fait par le code d'action défini par l'utilisateur.

Dans les langages qui n'ont pas goto (comme Rust), re2java réutilise la variable yystate pour stocker les numéros de condition. Chaque condition obtient un identifiant numérique égal au numéro de son état de départ, et un switch entre les conditions n'est pas différent d'un switch entre les états DFA d'une seule condition. Il n'y a pas besoin d'un switch de condition initial séparé. (Étant donné que la même approche est utilisée pour implémenter les états stockables, YYGETCOND/YYSETCOND sont redondants si les états stockables et les conditions sont utilisés).

Il y a un seul bloc où chaque base a sa propre condition, et la condition initiale est connectée à toutes. Storable state

Avec l'option --storable-state, re2java génère un lexer qui peut stocker son état actuel, retourner à l'appelant, et plus tard reprendre les opérations exactement là où il s'est arrêté. Le mode de fonctionnement par défaut dans re2java est un modèle "pull" (tirer), dans lequel le lexer "tire" plus d'entrée chaque fois qu'il en a besoin. Cela peut être inacceptable dans les cas où l'entrée devient disponible morceau par morceau (par exemple, si le lexer est appelé par l'analyseur, ou si le programme lexer communique via un protocole socket avec un autre programme qui doit attendre une réponse du lexer avant de transmettre le message suivant). La fonctionnalité d'état stockable est conçue exactement pour de tels cas : elle permet de générer des lexers qui fonctionnent selon un modèle "push" (pousser). Lorsque le lexer a besoin de plus d'entrée, il stocke son état et retourne à l'appelant. Plus tard, lorsque plus d'entrée est disponible, l'appelant reprend le lexer exactement là où il s'est arrêté. Il y a quelques changements nécessaires par rapport au modèle "pull" :

  • Définir les primitives YYSETSTATE() et YYGETSTATE(state).
  • Définir les variables yych, yyaccept (si utilisé) et state comme faisant partie de l'état persistant du lexer. La variable state doit être initialisée à -1.
  • YYFILL doit retourner au programme externe au lieu d'essayer de fournir plus d'entrée. Le code de retour doit indiquer que le lexer a besoin de plus d'entrée.
  • Le programme externe doit reconnaître les situations où le lexer a besoin de plus d'entrée et y répondre de manière appropriée.
  • Optionnellement, utiliser le bloc getstate pour générer un switch YYGETSTATE détaché du lexer principal. Cela ne fonctionne que pour les langages qui ont goto (pas en mode --loop-switch).
  • Utiliser re2c:eof et la méthode sentinelle avec vérifications de limites pour gérer la fin de l'entrée. La méthode basée sur le remplissage peut ne pas fonctionner car il est difficile de déterminer quand ajouter le remplissage : la fin actuelle de l'entrée peut ne pas être la fin ultime de l'entrée, et ajouter le remplissage trop tôt peut couper un lexème gourmand partiellement lu. De plus, en raison de la logique du programme de haut niveau, obtenir plus d'entrée peut dépendre du traitement du lexème à la fin du tampon (qui est déjà bloqué en raison de la condition de fin d'entrée).

Voici un exemple de lexer en modèle "push" qui simule la lecture de paquets depuis un socket. Le lexer boucle jusqu'à ce qu'il rencontre la fin de l'entrée et retourne à la fonction appelante. La fonction appelante fournit plus d'entrée en "envoyant" le paquet suivant et reprend l'analyse. Ce processus s'arrête lorsque tous les paquets ont été envoyés, ou en cas d'erreur.

package org.re2java.example;

import java.io.IOException;
import java.nio.ByteBuffer;
import java.nio.channels.Pipe;
import java.util.logging.Logger;

public class Lexer {
    private static final Logger log = Logger.getLogger(Lexer.class.getName());
    private static final int BUFSIZE = 4096;

    public enum Status {
        READY,
        WAITING,
        END,
        BAD_PACKET,
        BIG_PACKET
    }

    // State of the lexer.
    public static class State {
        public final Pipe.SourceChannel source;
        public byte[] yyinput;        // buffer for scanner
        public int yytchar;           // current char (used by scanner)
        public int yycursor;          // current position in buffer
        public int yylimit;           // end of buffer
        public int yymarker;          // used by scanner
        public int token;             // offset of the current token within yyinput
        public int received;          // number of received packets

        public State(Pipe pipe) throws IOException {
            this.source = pipe.source();
            this.yyinput = new byte[BUFSIZE];
            this.yylimit = BUFSIZE; // start with a full buffer
            this.yyinput[BUFSIZE - 1] = 0; // append sentinel symbol
        }
    }

    // Fill the lexer buffer if it is empty.
    private static Status fill(State st) throws IOException {
        if (st.token != 0) {
            // Buffer not empty. Discard processed input and shift the
            // remainder to the beginning of the buffer.
            if (st.token < 1) {
                return Status.BIG_PACKET;
            }
            // Shift buffer contents (discard everything up to the current token).
            System.arraycopy(st.yyinput, st.token, st.yyinput, 0, st.yylimit - st.token);
            st.yycursor -= st.token;
            st.yymarker -= st.token;
            st.yylimit -= st.token;
            st.token = 0;
        }
        // Fill free space at the end of buffer with new data from file.
        ByteBuffer buffer = ByteBuffer.wrap(st.yyinput, st.yylimit, BUFSIZE - st.yylimit);
        int have = st.source.read(buffer);
        if (have != -1) {
            st.yylimit += have; // -1 means that pipe is closed
        }
        st.yyinput[st.yylimit] = 0; // append sentinel symbol
        return Status.READY;
    }

    private static Status lex(State yyrecord) {
        byte yych;
        loop: while (true) {
            yyrecord.token = yyrecord.yycursor;
            /*!re2c
                re2c:api = record;
                re2c:YYCTYPE = "byte";
                re2c:YYPEEK = "yyrecord.yyinput[yyrecord.yycursor]";
                re2c:YYFILL = "return Status.WAITING;";
                re2c:eof = 0;
                packet = [a-z]+[;];
                *      { return Status.BAD_PACKET; }
                $      { return Status.END; }
                packet { yyrecord.received += 1; continue loop; }
            */
        }
    }

    public static void test(String[] packets, Status expect) throws IOException {
        // Create a pipe.
        Pipe pipe = Pipe.open();
        Pipe.SinkChannel sink = pipe.sink();
        // Initialize lexer state
        Lexer.State st = new Lexer.State(pipe);
        // Main loop. The buffer contains incomplete data which appears packet by
        // packet. When the lexer needs more input it saves its internal state and
        // returns to the caller which should provide more input and resume lexing.
        int send = 0;
        Status status;
        while (true) {
            status = lex(st);
            if (status == Status.END) {
                log.info("done: got " + st.received + " packets");
                break;
            } else if (status == Status.WAITING) {
                log.info("waiting...");
                if (send < packets.length) {
                    log.info("sent packet " + send + ": " + packets[send]);
                    ByteBuffer buffer = ByteBuffer.wrap(packets[send].getBytes());
                    sink.write(buffer);
                    send += 1;
                } else {
                    sink.close();
                }
                status = fill(st);
                if (status == Status.BIG_PACKET) {
                    log.info("error: packet too big");
                    break;
                }
                assert status == Status.READY;
            } else {
                assert status == Status.BAD_PACKET;
                log.info("error: ill-formed packet");
                break;
            }
        }
        // Check results.
        assert status == expect;
        if (status == Status.END) {
            assert send == st.received;
        }
    }

    public static void main(String []args) throws IOException {
        test(new String[]{}, Status.END);
        test(new String[]{"zero;", "one;", "two;", "three;", "four;"}, Status.END);
        test(new String[]{"zer0;"}, Status.BAD_PACKET);
        test(new String[]{"goooooooooogle;"}, Status.BIG_PACKET);
    }
};

Reusable   blocks

Reusable blocks of the form **/*!rules:re2c[:<name>] ...
    */** or **%{rules[:<name>] ... %}** can be reused any number of
    times and combined with other re2java blocks. The **<name>** is
    optional. A rules block can be used in a **use** block or directive. The
    code for a rules block is generated at every point of use.

Use blocks are defined with **/*!use:re2c[:<name>] ...
    */** or **%{use[:<name>] ... %}**. The **<name>** is
    optional: if it's not specified, the associated rules block is the most
    recent one (whether named or unnamed). A use block can add named
    definitions, configurations and rules of its own. An important use case for
    use blocks is a lexer that supports multiple input encodings: the same rules
    block is reused multiple times with encoding-specific configurations (see
    the example below).

In-block use directive **!use:<name>;** can be used from
    inside of a re2java block. It merges the referenced block
    **<name>** into the current one. If some of the merged rules and
    configurations overlap with the previously defined ones, conflicts are
    resolved in the usual way: the earliest rule takes priority, and latest
    configuration overrides preceding ones. One exception are the special rules
    **, **$** and (in condition mode) **<!>**, for which a
    block-local definition overrides any inherited ones. Use directive allows
    one to combine different re2java blocks together in one block (see the
    example below).

Named blocks and in-block use directive were added in re2java
    version 2.2. Since that version reusable blocks are allowed by default (no
    special option is needed). Before version 2.2 reuse mode was enabled with
    **-r --reusable** option. Before version 1.2 reusable blocks could not be
    mixed with normal blocks.

Example of a **!use** directive

        // re2java $INPUT -o $OUTPUT

        // ('colors' and 'fish') are merged into one. The 'salmon' rule occurs
        // in both blocks; the 'fish' block takes priority because it is used
        // earlier. Default rule * occurs in all three blocks; the local (not
        // inherited) definition takes priority.
        /*!rules:re2c:colors

        class Main {

                    re2c:yyfill:enable = 0;

Submatch   extraction

re2java has two options for submatch extraction.

    **Tags**
      The first option is to use standalone tags of the form **@stag**
      or **#mtag**, where **stag** and **mtag** are arbitrary
      used-defined names. Tags are enabled with **-T --tags** option or
      **re2c:tags = 1** configuration. Semantically tags are position
      markers: they can be inserted anywhere in a regular expression, and they
      bind to the corresponding position (or multiple positions) in the input
      string. S-tags bind to the last matching position, and
      m-tags bind to a list of positions (they may be used in repetition
      subexpressions, where a single position in a regular expression
      corresponds to multiple positions in the input string). All tags should be
      defined by the user, either manually or with the help of **svars** and
      **mvars** blocks. If there is more than one way tags can be matched
      against the input, ambiguity is resolved using leftmost greedy
      disambiguation strategy.
    **Captures**
      The second option is to use capturing groups. They are enabled with
      **--captures** option or **re2c:captures = 1** configuration. There
      are two flavours for different disambiguation policies,
      **--leftmost-captures** (the default) is for leftmost greedy policy,
      and, **--posix-captures** is for POSIX longest-match policy. In this
      mode all parenthesized subexpressions are considered capturing groups, and
      a bang can be used to mark non-capturing groups: **(! ... )**. With
      **--invert-captures** option or **re2c:invert-captures = 1**
      configuration the meaning of bang is inverted. The number of groups for
      the matching rule is stored in a variable **yynmatch** (the whole
      regular expression is group number zero), and submatch results are stored
      in **yypmatch** array. Both **yynmatch** and **yypmatch** should
      be defined by the user, and **yypmatch** size must be at least
      **[yynmatch * 2]**. Use **maxnmatch** block to define
      **YYMAXNMATCH**, a constant that equals to the maximum value of
      **yynmatch** among all rules.
    **Captvars**
      Another way to use capturing groups is the **--captvars** option or
      **re2c:captvars = 1** configuration. The only difference with
      **--captures** is in the way the generated code stores submatch
      results: instead of **yynmatch** and **yypmatch** re2java generates
      variables **yytl<k>** and **yytr<k>** for k-th
      capturing group (the user should declare these using an **svars**
      block). Captures with variables support two disambiguation policies:
      **--leftmost-captvars** or **re2c:leftmost-captvars = 1
 pour la politique gloutonne par défaut (celle par défaut) et --posix-captvars ou re2c:posix-captvars pour la politique de correspondance la plus longue de POSIX.

En interne, toutes ces options se traduisent par des balises et des automates finis déterministes étiquetés avec anticipation (TDFA). L'idée principale du TDFA est de minimiser la surcharge lors de l'extraction des sous-correspondances. Dans le cas extrême, s'il n'y a pas de balises ou de captures dans une expression régulière, le TDFA n'est qu'un DFA ordinaire. Si le nombre de balises est modéré, la surcharge est à peine perceptible. Le TDFA généré utilise un certain nombre de variables de balises qui ne correspondent pas directement aux balises : une seule variable peut être utilisée pour différentes balises, et une balise peut nécessiter plusieurs variables pour contenir toutes ses valeurs possibles. Finalement, l'ambiguïté est résolue, et seule une variable finale par balise subsiste. Les variables de balises doivent être définies à l'aide de blocs stags ou mtags. Si l'état de l'analyseur lexical est stocké, les variables de balises doivent en faire partie. Elles doivent également être mises à jour par YYFILL.

Les S-balises supportent les opérations suivantes :

  • sauvegarder la position d'entrée dans une s-balise : t = YYCURSOR avec l'API de pointeur C ou une opération définie par l'utilisateur YYSTAGP(t) avec l'API générique
  • sauvegarder la valeur par défaut dans une s-balise : t = NULL avec l'API de pointeur C ou une opération définie par l'utilisateur YYSTAGN(t) avec l'API générique
  • copier une s-balise dans une autre : t1 = t2

Les M-balises supportent les opérations suivantes :

  • ajouter une position d'entrée à une m-balise : une opération définie par l'utilisateur YYMTAGP(t) avec les API par défaut et générique
  • ajouter une valeur par défaut à une m-balise : une opération définie par l'utilisateur YYMTAGN(t) avec les API par défaut et générique
  • copier une m-balise dans une autre : t1 = t2

Les S-balises peuvent être implémentées comme des valeurs scalaires (pointeurs ou décalages). Les M-balises nécessitent une représentation plus complexe, car elles doivent stocker une séquence de valeurs de balises. La représentation la plus naïve et la moins efficace d'une m-balise est une liste (tableau, vecteur) de valeurs de balises ; une représentation plus efficace consiste à stocker toutes les m-balises dans un arbre préfixe représenté par un tableau de nœuds (v, p), où v est la valeur de la balise et p est un pointeur vers le nœud parent.

Voici un exemple plus complexe d'utilisation des s-balises avec YYFILL pour analyser un fichier contenant des versions sémantiques séparées par des sauts de ligne. Les variables de balises font partie de l'état de l'analyseur lexical, et elles sont ajustées dans YYFILL comme les autres positions d'entrée. Notez que c'est nécessaire pour les s-balises car leurs valeurs sont invalidées après le décalage du contenu du tampon. Cela peut ne pas être nécessaire dans une implémentation personnalisée où les variables de balises stockent des décalages par rapport au début de la chaîne d'entrée plutôt qu'au tampon, ce qui peut être le cas avec les m-balises.

// re2java $INPUT -o $OUTPUT
import java.io.*;
import java.nio.file.*;
import java.util.*;
class Lexer {
    static class SemVer {
        int major;
        int minor;
        int patch;
        public SemVer(int m, int n, int k) {
            major = m;
            minor = n;
            patch = k;
        }
        public boolean equals(SemVer v) {
            return major == v.major && minor == v.minor && patch == v.patch;
        }
    };
    public static final int BUFSIZE = 4096;
    private BufferedInputStream stream;
    private byte[] yyinput;
    private int yycursor;
    private int yymarker;
    private int yylimit;
    private int token;
    // Variables de balises intermédiaires utilisées par l'analyseur lexical (doivent être générées automatiquement).
    /*!stags:re2c format = "private int @@;\n"; */
    private boolean eof;
    public Lexer(File file) throws FileNotFoundException {
        stream = new BufferedInputStream(new FileInputStream(file));
        // Le sentinelle à l'offset `yylimit` est réglé sur zéro, ce qui déclenche YYFILL.
        yyinput = new byte[BUFSIZE + 1];
        yycursor = yymarker = yylimit = token = BUFSIZE;
        /*!stags:re2c format = "@@ = -1;\n"; */
        eof = false;
    }
    private int fill() throws IOException {
        if (eof) { return -1; } // EOF inattendu
        // Erreur : lexème trop long. Dans la réalité, on pourrait réallouer un tampon plus grand.
        if (token < 1) { return -2; }
        // Décale le contenu du tampon (rejette tout jusqu'au jeton actuel).
        System.arraycopy(yyinput, token, yyinput, 0, yylimit - token); 
        yycursor -= token;
        yymarker -= token;
        yylimit -= token;
        /*!stags:re2c format = "if (@@ != -1) {@@ -= token;}\n"; */
        token = 0;
        // Remplit l'espace libre à la fin du tampon avec de nouvelles données du fichier.
        yylimit += stream.read(yyinput, yylimit, BUFSIZE - yylimit);
        yyinput[yylimit] = 0; // ajoute un symbole sentinelle
        // Si moins de données que prévu ont été lues, c'est la fin de l'entrée.
        eof = yylimit < BUFSIZE;
        return 0;
    }
    private int readInt(int tag1, int tag2) {
        int n = 0;
        for (int i = tag1; i < tag2; ++i) { n = n * 10 + (yyinput[i] - 48); }
        return n;
    }
    public Optional<ArrayList<SemVer>> lex() throws IOException {
        ArrayList<SemVer> vers = new ArrayList<SemVer>();
        // Variables de balises finales disponibles dans l'action sémantique.
        /*!svars:re2c format = "int @@;"; */
        loop: while (true) {
            token = yycursor;
            /*!re2c
                re2c:YYCTYPE = "byte";
                re2c:YYPEEK = "yyinput[yycursor]";
                re2c:YYFILL = "fill() == 0";
                re2c:eof = 0;
                re2c:tags = 1;
                num = [0-9]+;
                @t1 num @t2 "." @t3 num @t4 ("." @t5 num)? [\n] {
                    int major = readInt(t1, t2);
                    int minor = readInt(t3, t4);
                    int patch = (t5 == -1) ? 0 : readInt(t5, yycursor - 1);
                    vers.add(new SemVer(major, minor, patch));
                    continue loop;
                }
                $ { return Optional.of(vers); }
                * { return Optional.empty(); }
            */
        }
    }
    public static void main(String []args) throws FileNotFoundException, IOException {
        String fname = "input";
        String content = "1.22.333\n".repeat(Lexer.BUFSIZE);
        // Préparer le fichier d'entrée : plusieurs fois la taille du tampon, contenant
        // des chaînes avec des zéros et des guillemets échappés.
        Files.writeString(Paths.get(fname), content);
        // Préparer l'état de l'analyseur lexical : tous les décalages sont à la fin du tampon.
        File file = new File(".", fname);
        Lexer lexer = new Lexer(file);
        // Exécuter l'analyseur lexical.
        Optional<ArrayList<SemVer>> vers = lexer.lex();
        // Vérifier les résultats.
        assert vers.isPresent() && vers.get().size() == BUFSIZE;
        SemVer v = new SemVer(1, 22, 333);
        for (int i = 0; i < BUFSIZE; ++i) {
            assert vers.get().get(i).equals(v);
        }
        // Nettoyage : supprimer le fichier d'entrée.
        file.delete();
    }
};

Prise en charge de l’encodage

Il est nécessaire de comprendre la différence entre les points de code et les unités de code. Un point de code est un identifiant numérique d'un symbole. Une unité de code est la plus petite unité de stockage dans le texte encodé. Un seul point de code peut être représenté par une ou plusieurs unités de code. Dans un encodage à longueur fixe, tous les points de code sont représentés avec le même nombre d'unités de code. Dans un encodage à longueur variable, les points de code peuvent être représentés avec un nombre différent d'unités de code. Notez que la règle « tout » [^] correspond à n'importe quel point de code, mais pas nécessairement à n'importe quelle unité de code (la seule façon de correspondre à n'importe quelle unité de code indépendamment de l'encodage est la règle par défaut *). Le lexer généré travaille avec un flux d'unités de code : yych stocke une unité de code, et YYCTYPE est le type de l'unité de code. Les expressions régulières, en revanche, sont spécifiées en termes de points de code. Lorsque re2java compile des expressions régulières en automates, il traduit les points de code en unités de code. Ce n'est généralement pas une simple correspondance : dans les encodages à longueur variable, une seule plage de points de code peut être traduite en un graphe complexe d'unités de code. Les encodages suivants sont pris en charge :

  • ASCII (activé par défaut). C'est un encodage à longueur fixe avec un espace de code [0-255] et des points de code et des unités de code de 1 octet.
  • EBCDIC (activé avec --ebcdic ou re2c:encoding:ebcdic). C'est un encodage à longueur fixe avec un espace de code [0-255] et des points de code et des unités de code de 1 octet.
  • UCS2 (activé avec --ucs2 ou re2c:encoding:ucs2). C'est un encodage à longueur fixe avec un espace de code [0-0xFFFF] et des points de code et des unités de code de 2 octets.
  • UTF8 (activé avec --utf8 ou re2c:encoding:utf8). C'est un encodage Unicode à longueur variable. La taille des unités de code est de 1 octet. Les points de code sont représentés avec 1 à 4 unités de code.
  • UTF16 (activé avec --utf16 ou re2c:encoding:utf16). C'est un encodage Unicode à longueur variable. La taille des unités de code est de 2 octets. Les points de code sont représentés avec 1 à 2 unités de code.
  • UTF32 (activé avec --utf32 ou re2c:encoding:utf32). C'est un encodage Unicode à longueur fixe avec un espace de code [0-0x10FFFF] et des points de code et des unités de code de 4 octets.

Le fichier d'inclusion include/unicode_categories.re fournit des définitions re2java pour les catégories Unicode standard.

L'option --input-encoding spécifie l'encodage du fichier source, qui peut être utilisé pour activer les littéraux Unicode dans les expressions régulières. Par exemple, --input-encoding utf8 indique à re2java que le fichier source est en UTF8 (cela diffère de --utf8 qui définit l'encodage du texte d'entrée). L'option --encoding-policy spécifie la manière dont re2java gère les substituts Unicode (points de code dans la plage [0xD800-0xDFFF]).

Ci-dessous se trouve un exemple de lexer pour des identifiants Unicode encodés en UTF8.

        int yycursor = 0;

            re2c:YYCTYPE = "char";

Fichiers d'inclusion

re2java permet d'inclure d'autres fichiers en utilisant un bloc de la forme /*!include:re2c FILE */ ou %{include FILE %}, ou une directive dans un bloc !include FILE ;, où FILE est le chemin d'accès au fichier à inclure. re2java recherche les fichiers d'inclusion dans le répertoire du fichier incluant et dans les emplacements d'inclusion, qui peuvent être spécifiés avec l'option -I. Les blocs/directives d'inclusion dans re2java fonctionnent de la même manière que les #include de C/C++ : le contenu de FILE est copié tel quel à la place du bloc/directive. Les fichiers d'inclusion peuvent contenir d'autres inclusions. Utilisez l'option --depfile pour suivre les dépendances de construction du fichier de sortie par rapport aux fichiers d'inclusion. re2java fournit des fichiers d'inclusion prédéfinis qui peuvent être trouvés dans le sous-répertoire include/ du projet. Ces fichiers contiennent des définitions qui peuvent être utiles à d'autres projets (telles que les catégories Unicode) et forment une sorte de bibliothèque standard pour re2java. Vous trouverez ci-dessous un exemple d'utilisation des fichiers d'inclusion.

Fichiers d'en-tête

re2java permet de générer un fichier d'en-tête à partir du fichier .re d'entrée à l'aide de l'option --header ou de la configuration re2c:header et des paires de blocs /*!header:re2c:on*/ et /*!header:re2c:off*/, ou %{header:on%} et %{header:off%}. Le premier bloc marque le début du fichier d'en-tête, et le second bloc en marque la fin. Tout ce qui se trouve entre ces blocs est traité par re2java, et le code généré est écrit dans le fichier spécifié avec l'option --header ou la configuration re2c:header (ou stdout si aucune option ni configuration n'est utilisée). Le fichier d'en-tête généré automatiquement peut être nécessaire dans les cas où re2java est utilisé pour générer des définitions qui doivent être visibles depuis d'autres unités de traduction.

Programmes squelettes

Avec l'option -S, --skeleton, re2java ignore tout le code non-re2java et génère un programme C autonome qui peut être compilé et exécuté. Le programme se compose du code du lexer et des données d'entrée. Pour chaque DFA construit (bloc ou condition), re2java génère un lexer autonome et deux fichiers : un fichier .input avec des chaînes dérivées du DFA et un fichier .keys avec les résultats attendus des correspondances. Le programme exécute chaque lexer sur le fichier .input correspondant et compare les résultats avec les attentes. Les programmes squelettes sont très utiles pour un certain nombre d'opérations.

re2java(1) — Manpages Arch Linux

RAISON D'ÊTRE

  • Ils peuvent vérifier l'exactitude de diverses optimisations re2java (les données sont générées tôt dans le processus, avant que des transformations DFA n'aient eu lieu).
  • La génération d'un ensemble de données d'entrée avec une bonne couverture peut être utile pour les tests et le benchmarking.
  • La génération de programmes exécutables autonomes permet d'obtenir des cas de test minimisés (le code original peut être volumineux ou avoir beaucoup de dépendances).

La difficulté de générer des données d'entrée est que, pour tous les cas sauf les plus triviaux, le nombre de chaînes d'entrée possibles est trop grand (même si la longueur de la chaîne est limitée). re2java résout cette difficulté en générant suffisamment de chaînes pour couvrir presque toutes les transitions DFA. Il utilise l'algorithme suivant. Premièrement, il construit un squelette du DFA. Pour les encodages avec une taille d'unité de code de 1 octet (tels que ASCII, UTF-8 et EBCDIC), le squelette est une copie exacte du DFA d'origine. Pour les encodages avec des unités de code multibytes, le squelette est une copie du DFA avec certaines transitions omises : à savoir, re2java prend au maximum 256 unités de code pour chaque plage continue et disjointe qui correspond à une transition DFA. Les valeurs choisies sont réparties uniformément et incluent les bornes de plage. Au lieu d'essayer de couvrir tous les chemins possibles dans le squelette (ce qui est irréalisable), re2java génère suffisamment de chemins pour couvrir toutes les transitions du squelette, et ainsi déclencher les sauts conditionnels correspondants dans le lexer. L'implémentation de l'algorithme est limitée à environ 1 Go de transitions et consomme une quantité constante de mémoire (re2java écrit les données dans un fichier dès qu'elles sont générées).

VISUALISATION ET DÉBOGAGE

Avec l'option -D, --emit-dot, re2java ne génère pas de code. Au lieu de cela, il exporte le DFA généré au format DOT. On peut convertir cette exportation en une image du DFA à l'aide de Graphviz ou d'une autre bibliothèque. Notez que cette option affiche le DFA final après qu'il a subi un certain nombre d'optimisations et de transformations. Les étapes précédentes peuvent être exportées avec diverses options de débogage, telles que --dump-nfa, --dump-dfa-raw, etc. (voir la liste complète des options).
