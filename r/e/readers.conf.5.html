NOM

readers.conf - Contrôle d'accès et configuration pour nnrpd

EN BREF

Le fichier readers.conf définit les paramètres qui autorisent les utilisateurs à se connecter en tant que lecteur de news et ce qu'ils sont autorisés à faire après la connexion. Gardez à l'esprit que dans readers.conf, l'authentification et l'autorisation sont configurées dans des blocs différents. Premièrement, un utilisateur est authentifié et se voit attribuer une identité (dans un bloc "auth"). Ensuite, cette identité est autorisée à accéder à certains groupes de news avec certains droits (dans un bloc "access").

Quant à l'authentification, votre bloc "auth" pour les utilisateurs à mot de passe pourrait ressembler à ceci :

auth "foreignokay" {
    auth: "ckpasswd -f <chemin vers db dans inn.conf>/newsusers"
    default: "<unauthenticated>"
}

Consultez la documentation du drapeau -f dans la page de manuel ckpasswd(8) pour savoir comment générer des mots de passe et utiliser ce fichier newsusers.

De cette façon, avec le bloc d'authentification "foreignokay", un utilisateur authentifié avec succès en tant qu'utilisateur "monnomutilisateur" se verra attribuer l'identité "monnomutilisateur". Si l'authentification échoue, il se verra attribuer l'identité par défaut "<unauthenticated>" qui sera vérifiée ultérieurement dans les blocs "access".

Les blocs d'authentification sont vérifiés de la fin du fichier readers.conf au début (du bas vers le haut). Dès qu'un bloc correspond, l'identité correspondante est attribuée à l'utilisateur.

Quant à l'autorisation, faisons quelque chose dans un bloc "access" pour les personnes authentifiées avec succès par mot de passe :

access "authenticatedpeople" {
    users: "*"
    newsgroups: "*,!junk,!control,!control.*"
}

Et ensuite, quelque chose comme l'un des deux blocs suivants, selon que les utilisateurs non authentifiés obtiennent ou non un accès :

access "restrictive" {
    users: "<unauthenticated>"
    newsgroups: "!*"
}
access "readonly" {
    users: "<unauthenticated>"
    read: "local.*"
    post: "!*"
}

Veuillez noter que le bloc "authenticatedpeople" doit apparaître dans readers.conf avant les blocs "restrictive" ou "readonly" car les blocs d'accès sont vérifiés de la fin du fichier readers.conf au début (du bas vers le haut). Dès qu'un bloc correspond à l'identité précédemment attribuée par un bloc d'authentification, il est choisi. Le bloc d'accès "authenticatedpeople" correspond à tous les utilisateurs qui n'ont pas reçu "<unauthenticated>" comme identité.

Plus d'exemples et de fonctionnalités sont détaillés plus bas dans cette page de manuel (notamment sans fichier de mot de passe, avec PAM, avec des hooks Perl ou Python).

Vous n'avez pas besoin de recharger quoi que ce soit après avoir modifié readers.conf ; chaque fois qu'un client de news se connecte au serveur, un nouveau processus nnrpd est lancé et lit sa configuration depuis le disque. Néanmoins, après toute modification, vous pouvez exécuter "inncheck" pour effectuer des vérifications syntaxiques de base sur le fichier readers.conf modifié.

DESCRIPTION

readers.conf dans pathetc spécifie le contrôle d'accès pour nnrpd(8). Il contrôle qui est autorisé à se connecter en tant que lecteur de news et ce qu'il est autorisé à faire après la connexion. nnrpd lit ce fichier chaque fois qu'un client de news se connecte au serveur, même lorsqu'il fonctionne en mode démon avec -D, ce qui signifie que toute modification de ce fichier prend effet immédiatement sur toutes les connexions ultérieures. (L'emplacement de readers.conf dans pathetc n'est que le défaut ; le même format s'applique à tout fichier spécifié avec "nnrpd -c".)

Il existe deux types d'entrées dans readers.conf : paires paramètre/valeur et groupes de configuration. Les lignes vides et tout ce qui suit un signe dièse ("#") sont ignorés, sauf si le caractère "#" est échappé avec "\". Le nombre maximum de caractères sur chaque ligne est de 8 191.

Les paires paramètre/valeur consistent en un mot-clé immédiatement suivi d'un deux-points, d'au moins un espace blanc, et d'une valeur. La casse du paramètre est significative (les paramètres doivent généralement être entièrement en minuscules), et un paramètre peut contenir n'importe quels caractères à l'exception des deux-points, "#" et des espaces blancs. Un exemple :

hosts: *.example.com

Les valeurs contenant des espaces blancs doivent être entourées de guillemets doubles, comme ceci :

hosts: "*.example.com, *.example.net"

Si le paramètre ne contient pas d'espaces blancs, comme :

hosts: *.example.com,*.example.net

il n'est pas nécessaire de le mettre entre guillemets, bien que vous puissiez souhaiter le faire pour plus de clarté.

Il n'y a aucun moyen de continuer une ligne sur la suivante, et par conséquent aucun moyen d'avoir un seul paramètre avec une valeur de plus de environ 8 180 caractères.

De nombreux paramètres acceptent une valeur booléenne. Pour tous ces paramètres, la valeur peut être spécifiée comme "true", "yes" ou "on" pour l'activer et peut être l'une des valeurs "false", "no" ou "off" pour la désactiver. La casse de ces valeurs n'est pas significative.

Il existe deux types fondamentaux de groupes de configuration : auth et access. Le groupe auth fournit des mécanismes pour établir l'identité de l'utilisateur, qui il est. Le groupe access détermine, étant donné l'identité de l'utilisateur, ce que cet utilisateur est autorisé à faire. Écrire un fichier readers.conf pour votre configuration est un processus en deux étapes : d'abord attribuer une identité à chaque connexion entrante en utilisant les groupes auth, puis donner à chaque identité les privilèges appropriés avec le groupe access. Nous recommandons de *ne pas* mélanger les groupes auth et les groupes access dans le fichier de configuration ; il est souvent plus sensé (en l'absence du paramètre key) de mettre tous les groupes auth en premier, et tous les groupes access en dessous.

Une identité d'utilisateur, telle qu'établie par un groupe auth, ressemble à une adresse e-mail si un domaine est spécifié (comme "<nomutilisateur>@<domaine>") ou sinon juste "<nomutilisateur>".

Si nnrpdauthsender est défini dans inn.conf, l'identité de l'utilisateur est également placée dans le champ d'en-tête Sender des messages postés par cet utilisateur. Voir la documentation de cette option dans inn.conf(5) pour plus de détails.

Une définition de groupe auth ressemble à ceci :

auth <nom> {
    hosts: <wildmat-hotes>
    auth: <programme-auth>
    res: <programme-res>
    default: <utilisateur-par-defaut>
    default-domain: <domaine-par-defaut>
    # ... potentiellement d'autres paramètres
}

Le <nom> est utilisé comme étiquette pour le groupe et sert uniquement à des fins de documentation. (Si votre configuration syslog enregistre la facilité "news.debug", le <nom> apparaîtra dans la sortie de débogage de nnrpd. L'examen de cette sortie peut être très utile pour comprendre pourquoi votre configuration ne fait pas ce que vous attendez.)

Un groupe auth donné ne s'applique qu'aux hôtes dont le nom ou l'adresse IP correspond à l'expression wildmat donnée avec le paramètre hosts (des expressions wildmat séparées par des virgules sont autorisées, mais "@" n'est pas supporté). Au lieu d'expressions wildmat, vous pouvez également utiliser la notation CIDR pour faire correspondre n'importe quelle adresse IP dans un bloc réseau ; par exemple, "10.10.10.0/24" correspondra à toute adresse IP comprise entre 10.10.10.0 et 10.10.10.255 inclus.

Si compilé avec les bibliothèques TLS/SSL ou SASL, un groupe auth avec le paramètre require_encryption défini sur true ne s'applique que si la connexion entrante utilise une couche de chiffrement, soit dès le début si le drapeau -S a été passé à nnrpd, soit après une utilisation réussie de STARTTLS, soit après une authentification réussie utilisant un mécanisme SASL qui négocie une couche de chiffrement.

Pour toute connexion provenant d'un hôte qui correspond à cette expression wildmat ou ce bloc réseau, chaque <programme-res> (plusieurs lignes res peuvent être présentes dans un bloc ; elles sont exécutées en séquence jusqu'à ce que l'une réussisse), le cas échéant, est exécuté pour déterminer l'identité de l'utilisateur à partir des seules informations de connexion.

Si <res-program> ne renvoie qu'un nom d'utilisateur, <defdomain> est utilisé comme domaine.

Si l'utilisateur s'authentifie ultérieurement via les commandes AUTHINFO USER/PASS, le nom d'utilisateur et le mot de passe fournis sont transmis à chaque <auth-program> (plusieurs lignes auth, perl_auth ou python_auth peuvent être présentes dans un bloc ; elles sont exécutées séquentiellement jusqu'à ce que l'une réussisse). Si l'une réussit et renvoie une identité différente de celle attribuée au moment de la connexion, elle est à nouveau comparée aux groupes d'accès disponibles et les actions que l'utilisateur est autorisé à effectuer peuvent changer. Le <auth-program> le plus couramment utilisé est ckpasswd, qui prend en charge plusieurs méthodes de vérification des mots de passe, y compris l'utilisation de PAM. Voir la page de manuel ckpasswd(8) pour plus de détails.

Lors de la comparaison des groupes d'authentification, le dernier groupe d'authentification du fichier qui correspond à une combinaison donnée de connexion et de nom d'utilisateur/mot de passe est utilisé.

Une définition de groupe d'accès ressemble généralement à ceci :

access <name> {
    users: <identity-wildmat>
    newsgroups: <group-wildmat>
    # ...potentiellement d'autres paramètres
}

Encore une fois, <name> est juste à des fins de documentation. Ceci indique que tous les utilisateurs dont l'identité correspond à <identity-wildmat> peuvent lire et poster sur tous les newsgroups correspondant à <group-wildmat> (comme précédemment, les expressions wildmat séparées par des virgules sont autorisées, mais "@" n'est pas supporté). Alternativement, vous pouvez utiliser la forme :

access <name> {
    users: <identity-wildmat>
    read: <read-wildmat>
    post: <post-wildmat>
}

et les utilisateurs correspondants pourront lire tout groupe correspondant à <read-wildmat> et poster sur tout groupe correspondant à <post-wildmat>. Vous pouvez également définir plusieurs autres choses dans le groupe d'accès ainsi que remplacer divers paramètres de inn.conf(5) pour un groupe d'utilisateurs particulier.

Tout comme pour les groupes d'authentification, lors de la comparaison des groupes d'accès, le dernier correspondant dans le fichier est utilisé pour déterminer les permissions de l'utilisateur. Il y a une exception à cette règle : si le groupe d'authentification qui correspondait au client contient un paramètre perl_access ou python_access, alors le script donné en argument est utilisé pour générer dynamiquement un groupe d'accès. Ce nouveau groupe d'accès est ensuite utilisé pour déterminer les droits d'accès du client ; les groupes d'accès dans le fichier sont ignorés.

Il existe un cas spécial supplémentaire à connaître. Lors de la formulation de règles d'authentification et d'autorisation particulièrement complexes, il est parfois utile que les identités fournies par un groupe d'authentification donné ne s'appliquent qu'à des groupes d'accès particuliers ; en d'autres termes, plutôt que de vérifier l'identité par rapport au paramètre users de chaque groupe d'accès, elle est vérifiée par rapport au paramètre users de seulement quelques groupes d'accès spécifiques. Ceci est fait avec le paramètre key. Par exemple :

auth example {
    key: special
    hosts: *.example.com
    default: <SPECIAL>
}
access example {
    key: special
    users: <SPECIAL>
    newsgroups: *
    addcanlockuser: none
}

Dans ce cas, les deux paramètres key lient ce groupe d'authentification à ce groupe d'accès. Pour toute connexion entrante correspondant à "*.example.com" (en supposant qu'il n'y ait pas de groupe d'authentification ultérieur qui corresponde également à de tels hôtes), aucun groupe d'accès qui ne contient pas "key: special" ne sera même pris en considération. De même, le groupe d'accès ci-dessus ne sera vérifié que si l'utilisateur a été authentifié avec un groupe d'authentification contenant "key: special". Ce mécanisme n'est normalement pas utile ; il existe presque toujours une meilleure façon d'obtenir le même résultat.

Notez également dans l'exemple qu'il n'y a pas de paramètre default-domain, ce qui signifie qu'aucun domaine n'est ajouté au nom d'utilisateur par défaut et que l'identité pour de telles connexions est simplement "<SPECIAL>". Notez que certains modules complémentaires à INN peuvent préférer que les identités authentifiées retournent toujours une adresse e-mail complète (y compris un domaine), vous voudrez donc peut-être configurer votre système de cette manière si vous utilisez des modules complémentaires. Comme plusieurs personnes différentes peuvent se voir attribuer la même identité "<SPECIAL>", aucun hachage Cancel-Lock spécifique à l'utilisateur ne devrait être généré.

Les fichiers de configuration peuvent être inclus dans d'autres fichiers de configuration via la syntaxe :

include <filename>

Le fichier nommé <filename> est alors inclus. Cette syntaxe n'est autorisée qu'au niveau supérieur.

Ci-dessous se trouve la liste complète des paramètres autorisés pour les groupes d'authentification et d'accès, et après cela, quelques exemples qui peuvent clarifier quelque peu la situation.

PARAMÈTRES DE GROUPE AUTH

Un groupe d'authentification sans au moins l'un des paramètres res, auth, perl_auth, python_auth ou default n'a aucun sens (et en pratique sera simplement ignoré).

auth
Une simple ligne de commande pour un authentificateur d'utilisateur (les métacaractères de shell ne sont pas pris en charge). Si un chemin complet n'est pas donné, le programme exécuté doit se trouver dans le répertoire pathbin/auth/passwd. Un authentificateur est un programme utilisé pour gérer un nom d'utilisateur et un mot de passe fournis par l'utilisateur, via un mécanisme tel que AUTHINFO USER/PASS. Comme avec res, un groupe d'authentification peut avoir plusieurs paramètres auth ; ils seront essayés dans l'ordre et les résultats du premier succès seront utilisés. Voir également perl_auth.

L'authentificateur le plus couramment utilisé est ckpasswd(8) ; voir sa page de manuel pour plus d'informations.

default
Le nom d'utilisateur par défaut pour les connexions correspondant à ce groupe d'authentification. Il s'agit du nom d'utilisateur attribué à l'utilisateur au moment de la connexion si tous les résolveurs échouent ou s'il n'y a pas de paramètres res. Notez qu'il peut s'agir soit d'un nom d'utilisateur brut, auquel cas default-domain (s'il est présent) est ajouté après un "@", soit d'une chaîne d'identité complète contenant un "@", auquel cas elle sera utilisée telle quelle.
default-domain
La chaîne de domaine par défaut pour ce groupe d'authentification. Si un résolveur d'utilisateur ou un authentificateur ne fournit pas de domaine, ou si le nom d'utilisateur par défaut est utilisé et qu'il ne contient pas de "@", ce domaine est utilisé pour former l'identité de l'utilisateur. (Notez que pour de nombreuses configurations, il n'est pas vraiment nécessaire que les identités des utilisateurs soient qualifiées par un nom de domaine, auquel cas il n'est pas nécessaire d'utiliser ce paramètre.)
hosts
Une liste séparée par des virgules d'hôtes distants, de motifs wildmat correspondant à des noms d'hôtes ou des adresses IP, ou de blocs réseau IP spécifiés en notation CIDR. Si un utilisateur se connecte depuis un hôte qui ne correspond pas à ce paramètre, ce groupe d'authentification ne correspondra pas à la connexion et sera ignoré.

Notez que si vous avez un grand nombre de motifs qui ne peuvent pas être fusionnés en motifs plus larges (comme un grand nombre de systèmes individuels répartis sur le réseau qui devraient avoir accès), le paramètre hosts peut dépasser la longueur maximale de ligne de 8 192 caractères. Dans ce cas, vous devrez diviser ce groupe d'authentification en plusieurs groupes d'authentification, chacun avec une partie des hôtes listés dans son paramètre hosts, et chacun attribuant la même identité utilisateur.

Tous les hôtes correspondent si ce paramètre n'est pas fourni.

key
Si ce paramètre est présent, toute connexion correspondant à ce groupe d'authentification aura ses privilèges déterminés uniquement par le sous-ensemble des groupes d'accès contenant un paramètre clé correspondant.
localaddress
Une liste séparée par des virgules d'hôtes locaux ou de motifs d'adresses avec la même syntaxe que le paramètre hosts. Si ce paramètre est spécifié, son groupe d'authentification ne correspondra qu'aux connexions effectuées à une interface locale correspondante. (Évidemment, cela n'est utile que pour les serveurs disposant de plusieurs interfaces.)

Toutes les adresses locales correspondent si ce paramètre n'est pas fourni.

perl_access
Un chemin vers un script Perl pour générer dynamiquement un groupe d'accès. Si un groupe d'authentification correspond avec succès et contient un paramètre perl_access, alors le script Perl argument sera utilisé pour créer un groupe d'accès. Ce groupe déterminera alors les droits d'accès du client, remplaçant tous les groupes d'accès dans readers.conf. Si et seulement si un groupe d'authentification réussi contient le paramètre perl_access, les groupes d'accès readers.conf sont ignorés et les droits du client sont déterminés dynamiquement. Ce paramètre n'est valide que si INN est compilé avec le support Perl (--with-perl passé à "configure"). Plus d'informations peuvent être trouvées dans le fichier doc/hook-perl.
perl_auth
Un chemin vers un script Perl pour l'authentification. Le paramètre perl_auth fonctionne exactement comme auth, sauf qu'il appelle le script nommé en utilisant le hook Perl plutôt qu'un programme externe. L'utilisation multiple/mixte des paramètres auth, perl_auth et python_auth est autorisée dans tout groupe d'authentification ; chaque ligne est essayée dans l'ordre où elle apparaît. perl_auth a plus de puissance que auth car il fournit au programme d'authentification des informations supplémentaires sur le client et la capacité de retourner une chaîne d'erreur et un nom d'utilisateur. Ce paramètre n'est valide que si INN est compilé avec le support Perl (--with-perl passé à "configure"). Plus d'informations peuvent être trouvées dans doc/hook-perl.
python_access
Un script Python pour générer dynamiquement un groupe d'accès. Si un groupe d'authentification correspond avec succès et contient un paramètre python_access, alors le script argument (sans son extension ".py") situé dans le répertoire pathfilter sera utilisé pour créer un groupe d'accès. Ce groupe déterminera alors les droits d'accès du client, remplaçant tous les groupes d'accès dans readers.conf.

Si et seulement si un groupe d'authentification réussi contient le paramètre python_access, les groupes d'accès readers.conf sont ignorés et les droits du client sont déterminés dynamiquement.

Ce paramètre n'est valide que si INN est compilé avec le support de Python (--with-python passé à "configure"). Plus d'informations peuvent être trouvées dans le fichier doc/hook-python.

python_auth
Un script Python pour l'authentification. Le paramètre python_auth fonctionne exactement comme auth, sauf qu'il appelle le script nommé (sans son extension ".py") situé dans le répertoire pathfilter en utilisant le hook Python plutôt qu'un programme externe. L'utilisation multiple/mixte des paramètres auth, perl_auth et python_auth est permise au sein de n'importe quel groupe d'authentification ; chaque ligne est essayée dans l'ordre où elle apparaît. python_auth a plus de puissance que auth car il fournit au programme d'authentification des informations supplémentaires sur le client et la capacité de retourner une chaîne d'erreur et un nom d'utilisateur.

Ce paramètre n'est valide que si INN est compilé avec le support de Python (--with-python passé à "configure"). Plus d'informations peuvent être trouvées dans doc/hook-python.

python_dynamic
Un script Python pour appliquer le contrôle d'accès dynamiquement sur une base de groupe de nouvelles. Si un groupe d'authentification correspond avec succès et contient un paramètre python_dynamic, alors le script argument (sans son extension ".py") situé dans le répertoire pathfilter sera utilisé pour déterminer les droits des clients chaque fois que l'utilisateur tente de visualiser un groupe de nouvelles, ou de lire ou poster un article. Les droits d'accès tels que déterminés par python_dynamic remplacent les valeurs des paramètres du groupe d'accès tels que newsgroups, read et post.

Ce paramètre n'est valide que si INN est compilé avec le support de Python (--with-python passé à "configure"). Plus d'informations peuvent être trouvées dans le fichier doc/hook-python.

require_encryption
Si défini à true, une connexion entrante ne correspond à ce groupe d'authentification que si elle est chiffrée, soit dès le début si le drapeau -S a été passé à nnrpd, soit après une utilisation réussie de STARTTLS, soit après une authentification réussie utilisant un mécanisme SASL qui négocie une couche chiffrée. Ce paramètre n'est valide que si INN est compilé avec le support TLS/SSL ou SASL (par défaut si les bibliothèques OpenSSL SSL et crypto ou la bibliothèque Cyrus SASL sont trouvées au moment de la configuration, sinon voir les flags --with-openssl et --with-sasl passés à "configure").
res
Une commande simple pour un résolveur d'utilisateurs (les métacaractères de shell ne sont pas pris en charge). Si un chemin complet n'est pas donné, le programme exécuté doit se trouver dans le répertoire pathbin/auth/resolv. Un résolveur est un programme d'authentification qui tente de déterminer l'identité de l'utilisateur connecté en utilisant uniquement les informations de connexion (en d'autres termes, l'utilisateur n'a pas fourni de nom d'utilisateur et de mot de passe). Un exemple de résolveur serait un programme qui attribue une identité à partir d'un rappel ident ou du nom d'hôte de l'utilisateur.

Un groupe d'authentification peut avoir plusieurs paramètres res, et ils seront essayés dans l'ordre où ils sont listés. Les résultats du premier succès seront utilisés.

Alternativement, un bloc res peut être utilisé à la place d'un paramètre res. Les paramètres reconnus dans de tels blocs res sont :

log
Une chaîne à journaliser dans pathlog/news.notice (avec "res also-log:" préfixé) avant que le résolveur ne soit essayé. Un groupe res peut avoir plusieurs paramètres log, et ils seront journalisés dans l'ordre où ils sont listés.
program
Ce paramètre est obligatoire dans un bloc res. Sa signification est la même que le paramètre res utilisé directement dans un bloc auth. 
auth <auth-name> {
    res: <res-program>
}

est donc équivalent à :

auth <auth-name> {
    res <res-name> {
        program: <res-program>
    }
}

PARAMÈTRES DU GROUPE D'ACCÈS

access
Un ensemble de lettres spécifiant les permissions accordées au client. Les lettres sont choisies parmi l'ensemble suivant :
A
Le client peut poster des articles avec des en-têtes Approved (en d'autres termes, peut approuver des articles pour les groupes de nouvelles modérés). Par défaut, cela n'est pas autorisé.
I
Le client peut injecter des articles avec IHAVE. Notez que pour injecter des articles avec la commande IHAVE, l'utilisateur doit également avoir la permission POST (l'option "P"). Les articles injectés avec IHAVE sont traités comme s'ils avaient été injectés avec POST, c'est-à-dire que ces articles ne doivent pas avoir été précédemment injectés (ils ne doivent pas contenir d'en-têtes comme Injection-Info).
L
Le client peut poster dans des groupes de nouvelles qui sont configurés pour interdire la publication locale (champs de statut "j", "n" et "x" dans le fichier active(5)).
N
Le client peut utiliser la commande NEWNEWS, en remplaçant le réglage global.
P
Le client peut poster des articles.
R
Le client peut lire des articles.

Notez que si ce paramètre est donné, allownewnews dans inn.conf est ignoré pour les connexions correspondant à ce groupe d'accès et la capacité du client à utiliser NEWNEWS est entièrement déterminée par la présence de "N" dans la chaîne d'accès. Si vous souhaitez prendre en charge NEWNEWS, assurez-vous d'inclure "N" dans la chaîne d'accès lorsque vous utilisez ce paramètre.

Notez que si ce paramètre est donné et "R" n'est pas présent dans la chaîne d'accès, le client ne peut pas lire, indépendamment des paramètres newsgroups ou read. De même, si ce paramètre est donné et "P" n'est pas présent, le client ne peut pas poster. Cette utilisation de access est dépréciée et confuse ; il est fortement recommandé que si le paramètre access est utilisé, "R" et "P" soient toujours inclus dans la chaîne d'accès et que newsgroups, read et post soient utilisés pour contrôler l'accès. (Pour accorder un accès en lecture mais aucun accès en publication, on peut avoir uniquement un paramètre read et aucun paramètre post.)

addcanlockuser
Si défini à "none", les publications faites par ces utilisateurs n'auront pas de hachage spécifique à l'utilisateur dans le champ d'en-tête Cancel-Lock (seul le hachage administrateur sera généré). Aucun champ d'en-tête Cancel-Key ne sera présent dans les demandes d'annulation ou de remplacement. Il s'agit d'une valeur de chaîne et la valeur par défaut est "username", c'est-à-dire qu'un hachage spécifique à l'utilisateur basé sur l'identité attribuée à la connexion est utilisé.

Une autre valeur possible pour ce paramètre est "ip", auquel cas un hachage spécifique à l'utilisateur basé sur l'adresse IP de la connexion est utilisé (qui devrait être une IP statique pour identifier réellement les utilisateurs).

Voir inn-secrets.conf(5) pour plus d'informations sur Cancel-Lock. La principale raison de ce paramètre est de désactiver ce mécanisme d'authentification lorsque la même identité ou IP peut être attribuée par un groupe d'accès à différentes personnes. Sinon, n'importe laquelle de ces personnes pourrait envoyer un retrait authentifié d'un article initialement envoyé par une autre personne avec la même identité ou IP.

domain
Lorsqu'il est défini, la valeur de ce paramètre est utilisée pour la partie domaine (le côté droit après "@") des ID de message auto-générés, ainsi que pour le nom du serveur indiqué dans les champs d'en-tête Injection-Info.

Par défaut, la valeur de ce paramètre est héritée du paramètre éponyme dans inn.conf. Cependant, si domain n'est pas explicitement défini dans readers.conf, le comportement spécifique décrit ci-dessus ne sera pas déclenché à moins que virtualhost ne soit défini à true.

Vous pourriez également vouloir définir le paramètre fromhost (hérité de inn.conf) pour l'adresse des plaintes dans le champ d'en-tête Injection-Info, si sa valeur par défaut doit être modifiée, et que le paramètre complaints n'est pas déjà défini ou que newsmaster ne contient pas déjà un "@".

groupexactcount
Ce paramètre contrôle le seuil en dessous duquel nnrpd doit donner le nombre exact d'articles encore existants présents dans les groupes de nouvelles au lieu d'une estimation. Le nombre exact est généralement mis à jour une fois par jour pendant le processus d'expiration par expirover (exécuté par news.daily), et est mis à jour lorsque de nouveaux articles arrivent mais pas nécessairement lorsque les articles sont annulés ou remplacés dans des méthodes de stockage à expiration automatique comme CNFS.

Lorsque le nombre estimé d'articles est strictement inférieur à groupexactcount, nnrpd recomptera le nombre d'articles encore existants, et rapportera la valeur exacte. Si groupexactcount est défini à 0, nnrpd recomptera toujours. S'il est défini à 1, il ne recomptera jamais.

Bien que les nombres exacts d'articles ne soient pas requis, ils peuvent être utiles pour distinguer les groupes de nouvelles vides en rapportant un nombre exact de 0 au lieu d'une estimation de 1 (lorsque cela se produit, le client de nouvelles peut indiquer que 1 article est présent dans le groupe de nouvelles, puis tente de récupérer l'article, et enfin ne montre rien à l'utilisateur).

Il n'est pas recommandé de définir une valeur élevée pour ce par

ameter car cela ralentira les réponses aux clients d'actualités (le recomptage des articles existants prend du temps, surtout dans les groupes de nouvelles contenant beaucoup d'articles).

C'est une valeur entière, et la valeur par défaut est 5.

key
Si ce paramètre est présent, ce groupe d'accès n'est pris en compte que lors de la recherche de privilèges pour les utilisateurs correspondant aux groupes d'authentification ayant le même paramètre key.
localtime
Si un champ d'en-tête Date ou Injection-Date n'est pas inclus dans un article publié, nnrpd ajoute normalement ces champs d'en-tête en UTC. Si ce paramètre est défini sur vrai, le champ d'en-tête Date sera formaté en heure locale à la place. (Le champ d'en-tête Injection-Date est ajouté conformément au comportement du paramètre addinjectiondate dans inn.conf, et restera en UTC, cependant.) C'est une valeur booléenne et la valeur par défaut est fausse.

Ce paramètre permet de gérer un cas limite relativement inhabituel. C'est principalement un outil pour les personnes qui veulent divulguer leur fuseau horaire local (cela peut être une information utile dans certains types de discussions), mais dont les clients ne le font pas pour une raison quelconque, et qui peuvent faire en sorte que le serveur soit dans le même fuseau horaire que le client.

max_rate
Si ce paramètre est présent (et non nul), il est utilisé pour le code de limitation de débit de nnrpd. Le client ne pourra télécharger qu'à cette vitesse (en octets/seconde). Notez que si une couche de chiffrement est utilisée, la limitation s'applique au flux de données pré-chiffrement.
newsgroups
Les utilisateurs qui correspondent à ce groupe d'accès sont autorisés à lire et à poster à tous les groupes de nouvelles correspondant à cette liste de motifs de type wildmat, séparés par des virgules. La chaîne vide équivaut à "newsgroups: *" ; si ce paramètre est absent, la connexion sera rejetée (sauf si read et/ou post sont utilisés à la place).
newsmaster
Utilisé comme adresse de contact dans le message d'aide renvoyé par nnrpd(8), si le paramètre virtualhost: est défini sur vrai.
perlfilter
Si défini sur faux, les articles publiés par ces utilisateurs ne passent pas par le filtre Perl, même s'il est autrement activé. C'est une valeur booléenne et la valeur par défaut est vraie.
post
Similaire au paramètre newsgroups, mais le client n'est autorisé qu'à poster aux groupes de nouvelles correspondants. Ce paramètre est souvent utilisé avec read pour définir les motifs de lecture et de publication séparément (généralement pour donner à l'utilisateur la permission de lire plus de groupes de nouvelles qu'il n'est autorisé à en publier). Il ne peut pas être utilisé dans le même groupe d'accès avec un paramètre newsgroups.
pythonfilter
Si défini sur faux, les articles publiés par ces utilisateurs ne passent pas par le filtre Python, même s'il est autrement activé. C'est une valeur booléenne et la valeur par défaut est vraie.

Ce paramètre n'a actuellement aucun effet car le filtrage Python n'est pas encore implémenté dans nnrpd. Si vous souhaitez effectuer un filtrage Python, vous devez utiliser celui implémenté dans innd.

read
Similaire au paramètre newsgroups, mais le client n'est autorisé qu'à lire les groupes de nouvelles correspondants. Ce paramètre est souvent utilisé avec post pour spécifier des groupes en lecture seule ; il ne peut pas être utilisé dans le même groupe d'accès avec un paramètre newsgroups. (Si read est utilisé et post est absent, le client n'aura qu'un accès en lecture seule.)
reject_with
Si ce paramètre est présent, un client correspondant à ce bloc sera déconnecté avec un message "Permission denied" contenant le contenu (une chaîne "raison") de ce paramètre. Certains lecteurs de news afficheront alors la raison à l'utilisateur.
strippath
Si défini sur vrai, tout champ d'en-tête Path fourni par un utilisateur dans un article sera supprimé plutôt qu'utilisé comme début du corps du champ d'en-tête Path de l'article. C'est une valeur booléenne et la valeur par défaut est fausse.
users
Les privilèges accordés par ce groupe d'accès s'appliquent à toute identité d'utilisateur correspondant à cette liste de motifs de type wildmat, séparés par des virgules. Si ce paramètre n'est pas fourni, le groupe d'accès s'applique à tous les utilisateurs (et est essentiellement équivalent à "users: *").
virtualhost
Définissez ce paramètre sur vrai pour que nnrpd se comporte comme s'il s'exécutait sur un serveur portant un nom différent de celui qu'il a réellement. Le paramètre domain doit alors être défini, soit dans inn.conf, soit dans le même groupe d'accès. Tous les articles et données d'aperçu affichés aux clients auront leur corps de champ d'en-tête Xref modifié pour apparaître comme provenant du serveur nommé dans domain, et les articles publiés utiliseront ce nom de serveur dans les corps des champs d'en-tête Message-ID et Injection-Info. (De plus, si le flag -I a été passé à nnrpd, les agents de publication se verront proposer d'utiliser des Message-IDs contenant la chaîne spécifiée avec -I.)

De même, les corps de champ d'en-tête Path affichés aux clients ou générés dans les articles publiés utiliseront la valeur de domain (si pathhost n'est pas défini dans le groupe d'accès, ou a la même valeur que dans inn.conf) ou pathhost (si pathhost est défini dans le groupe d'accès à une valeur autre que celle définie dans inn.conf).

En outre, la partie domaine (le côté droit après "@") de l'e-mail du newsmaster mentionné dans le message d'aide renvoyé par nnrpd utilisera la valeur de domain si le paramètre newsmaster n'a pas déjà de partie domaine.

Au moins un des paramètres domain ou pathhost doit être défini dans le groupe d'accès à quelque chose de différent de ce qui est dans inn.conf, sinon nnrpd échouera au démarrage.

Notez que la définition de ce paramètre oblige le serveur à modifier tous les articles avant de les présenter au client et peut donc légèrement diminuer les performances.

De plus, tous les paramètres suivants sont valides dans les groupes d'accès et remplacent le paramètre global dans inn.conf. Voir inn.conf(5) pour les descriptions de ces paramètres :

addinjectiondate, addinjectionpostingaccount,
addinjectionpostinghost, backoff_auth, backoff_db, backoff_k,
backoff_postfast, backoff_postslow, backoff_trigger,
checkincludedtext, clienttimeout, complaints, fromhost,
localmaxartsize, moderatormailer, nnrpdauthsender, nnrpdcheckart,
nnrpdoverstats, nnrpdposthost, nnrpdpostport, organization,
pathhost, readertrack, spoolfirst, strippostcc.

RÉSUMÉ

Voici un résumé de base de ce qui se passe lorsqu'un client se connecte :

  • Tous les groupes d'authentification sont analysés et ceux qui ne correspondent pas au client (en raison de hosts, localaddress, require_encryption, etc.) sont éliminés.
  • Les groupes d'authentification restants sont analysés de la fin au début, et une tentative est faite pour les appliquer à la connexion actuelle. Cela signifie l'exécution des programmes res, le cas échéant, et sinon l'application de default. Le premier groupe d'authentification (en partant du bas) qui renvoie un utilisateur valide est conservé comme groupe d'authentification actif.
  • Si aucun groupe d'authentification ne produit un utilisateur valide (aucun n'a de paramètres default ou de programmes res réussis), mais que certains des groupes d'authentification ont des lignes auth (indiquant la possibilité que l'utilisateur s'authentifie et obtienne ensuite des permissions), la connexion est considérée comme n'ayant aucun groupe d'authentification valide (ce qui signifie que les groupes d'accès sont complètement ignorés), mais la connexion n'est pas fermée. Au lieu de cela, un code de réponse 480 (signifiant que l'authentification est requise) est renvoyé pour tout jusqu'à ce que l'utilisateur s'authentifie.
  • Lorsque l'utilisateur s'authentifie, les groupes d'authentification sont réanalysés, et seuls les groupes correspondants contenant au moins une ligne auth, perl_auth ou python_auth sont pris en compte. Ces groupes d'authentification sont analysés de la fin au début, exécutant les programmes auth et les scripts perl_auth ou python_auth. Le premier groupe d'authentification (en partant du bas) qui renvoie un utilisateur valide est conservé comme groupe d'authentification actif.
  • Quelle que soit la manière dont un groupe d'authentification est établi, dès qu'il l'est, ce groupe d'authentification est utilisé pour attribuer une identité d'utilisateur en prenant le résultat de la ligne réussie res, auth, perl_auth ou python_auth (ou le default si nécessaire), et en ajoutant default-domain si nécessaire. (Si le paramètre perl_access ou python_access est présent.)
  • Enfin, un groupe d'accès est sélectionné en analysant les groupes d'accès de bas en haut et en trouvant la première correspondance. (Si le groupe d'authentification établi contenait une ligne perl_access ou python_access, le groupe d'accès généré dynamiquement renvoyé par le script est utilisé à la place.) Les permissions de l'utilisateur sont accordées en fonction du groupe d'accès établi.

EXEMPLES

Probablement l'exemple utile le plus simple d'un fichier readers.conf complet, celui-ci donne les permissions de lire et de publier à tous les groupes pour toutes les connexions du domaine "example.com", à l'exception de la machine de Bob, et aucun privilège pour quiconque se connectant ailleurs :

auth example.com {
    hosts: "*.example.com, example.com, !bob.example.com"
    default: "<EXAMPLE>"
}
access full {
    users: "<EXAMPLE>"
    newsgroups: *
    addcanlockuser: none
}

Notez que le domaine d'accès ci-dessus pourrait également être écrit sans la clé users, auquel cas il s'applique à toute identité d'utilisateur (bien que dans cet exemple, l'identité d'utilisateur qui sera attribuée à toutes les connexions correspondantes est "<EXAMPLE>"). Il est cependant recommandé de conserver une clé users explicite afin de mieux voir à qui le bloc d'accès s'applique.

Étant donné que le seul domaine d'authentification disponible ne correspond qu'aux hôtes du domaine "example.com", toutes les connexions provenant d'autres hôtes seront immédiatement rejetées.

Si vous avez des systèmes qui ne devraient avoir qu'un accès en lecture seule au serveur, vous pouvez modifier t

Voici un exemple qui ajoute une autorisation et un groupe d'accès supplémentaires : auth lab { hosts: « *.lab.example.com » default: } access lab { users: read: * } Si ces éléments sont placés dans le fichier après l'exemple ci-dessus, ils prendront le dessus (car ils sont plus loin dans le fichier) pour tout utilisateur provenant d'une machine du domaine lab.example.com, tout le monde n'aura qu'un accès en lecture, et non en publication. Voici un exemple similaire pour un serveur de news qui accepte les connexions de n'importe où mais exige que l'utilisateur spécifie un nom d'utilisateur et un mot de passe. Le nom d'utilisateur et le mot de passe sont d'abord vérifiés par rapport à une base de données externe de noms d'utilisateur et de mots de passe, puis utilisent PAM : auth all { auth: « ckpasswd -f /newsusers » auth: ckpasswd } access full { users: * newsgroups: * } Lorsque l'utilisateur se connecte pour la première fois, il n'y a pas de clés res et pas de défaut, donc il ne reçoit aucune identité valide et la connexion ne correspondra à aucun groupe d'accès (même ceux avec « users: * »). Ces utilisateurs ne reçoivent rien d'autre que des réponses exigeant une authentification de la part de nnrpd jusqu'à ce qu'ils s'authentifient. S'ils s'authentifient plus tard, le nom d'utilisateur et le mot de passe sont d'abord vérifiés en exécutant ckpasswd avec l'option -f pour un fichier externe de mots de passe cryptés, puis PAM est utilisé (si INN a été compilé avec le support de PAM) pour vérifier le mot de passe (et si cela échoue, il tente de vérifier le mot de passe par rapport au champ mot de passe renvoyé par getpwnam(3)). Si les deux échouent, l'utilisateur continuera à n'avoir aucune identité ; sinon, une identité sera attribuée (généralement le nom d'utilisateur fourni, éventuellement avec un domaine ajouté, bien qu'un authentificateur puisse techniquement fournir un nom d'utilisateur complètement différent pour l'identité), et le groupe d'accès correspondra, donnant un accès complet. Il peut être instructif d'examiner comment combiner les exemples ci-dessus ; les groupes généraux viennent toujours en premier. L'ordre des groupes d'authentification n'a en fait aucune importance, car le groupe « hosts: example.com » ne correspond qu'aux connexions avant que le nom d'utilisateur/mot de passe ne soit envoyé, et le groupe « auth: ckpasswd » ne correspond qu'après ; l'ordre serait important si l'un ou l'autre groupe s'appliquait aux deux cas. L'ordre des groupes d'accès dans ce cas est important, à condition que les lignes newsgroups diffèrent ; le groupe d'accès sans ligne users doit être le premier, avec le groupe « users:  » après. Voici un exemple d'un autre cas courant : un serveur qui n'autorise que les connexions d'un domaine local et possède une hiérarchie supplémentaire soumise à restriction par mot de passe. auth "example.com" { hosts: "*.example.com" auth: "ckpasswd -f /newsusers" default: "anonymous" } access regular { newsgroups: "*,!example.restricted.*" addcanlockuser: none } access full { users: "*,!anonymous" newsgroups: * } Dans cet exemple, les utilisateurs non authentifiés obtiennent l'identité « anonymous », qui ne correspond qu'au premier groupe d'accès et n'a donc pas accès à la hiérarchie « example.restricted.* ». Aucun élément Cancel-Lock spécifique à l'utilisateur ne doit être généré pour les utilisateurs anonymes. Toute personne s'authentifiant à l'aide d'un mot de passe dans le fichier newsusers obtient un accès complet à tous les groupes. Cependant, notez que le seul bloc d'authentification est limité aux noms d'hôtes du domaine example.com ; les connexions en dehors de ce domaine ne seront jamais autorisées ni n'auront la possibilité de s'authentifier. Voici un exemple très compliqué. Il s'agit d'une organisation qui possède une hiérarchie interne « example.* » uniquement accessible aux utilisateurs de shell locaux, qui se trouvent sur des machines où identd(8) peut être considéré comme fiable. Les utilisateurs dial-up doivent fournir un nom d'utilisateur et un mot de passe, qui sont ensuite vérifiés par rapport à RADIUS. Les utilisateurs distants doivent utiliser un nom d'utilisateur et un mot de passe qui sont vérifiés par rapport à une base de données sur le serveur de news. Enfin, le personnel administratif (utilisateurs « joe » et « jane ») peut poster n'importe où (y compris dans les groupes « example.admin.* » qui sont en lecture seule pour tous les autres), et est exempté du filtre Perl. Pour une touche supplémentaire, les publications des utilisateurs dial-up ont leur champ d'en-tête Sender remplacé par leur identité authentifiée. Comme cette organisation a des groupes de news modérés internes, le personnel administratif peut également publier des messages avec des champs d'en-tête Approved, mais les autres utilisateurs ne le peuvent pas. auth default { auth: "ckpasswd -f /newsusers" default: default-domain: example.com } auth shell { hosts: *.shell.example.com res: ident auth: ckpasswd default: default-domain: shell.example.com } auth dialup { hosts: *.dialup.example.com auth: radius default: default-domain: dialup.example.com } access shell { users: *@shell.example.com read: * post: "*, !example.admin.*" } access dialup { users: *@dialup.example.com newsgroups: *,!example.* nnrpdauthsender: true } access other { users: "*@example.com, !<FAIL>@example.com" newsgroups: *,!example.* } access fail { users: "@*" newsgroups: !* } access admin { users: "joe@*,jane@*" newsgroups: * access: "RPA" perlfilter: false } Notez l'utilisation de domaines différents pour séparer facilement les utilisateurs dial-up des utilisateurs shell. Une autre façon de faire serait d'utiliser des paramètres key, mais cette méthode fournit des chaînes d'identité légèrement plus intuitives. Notez également que le groupe d'accès fail intercepte non seulement les connexions échouées des utilisateurs externes, mais aussi les authentifications échouées des utilisateurs shell et dial-up avant qu'ils ne soient authentifiés. La chaîne d'identité donnée pour, disons, les utilisateurs dial-up avant que l'authentification RADIUS n'ait été tentée correspond aux groupes d'accès dial-up et fail, car elle est « @dialup.example.com », mais le groupe fail est le dernier, il a donc la priorité. Le groupe d'authentification shell a un paramètre auth afin que les utilisateurs « joe » et « jane » puissent, s'ils le souhaitent, utiliser l'authentification par nom d'utilisateur et mot de passe pour obtenir leurs privilèges spéciaux, même s'ils sont connectés en tant qu'autre utilisateur sur les machines shell (ou si ident ne fonctionne pas). Lorsqu'ils se connectent pour la première fois, ils auraient l'accès par défaut pour cet utilisateur, mais ils pourraient ensuite s'authentifier afin d'obtenir leur accès étendu. Notez également que si les utilisateurs « joe » et « jane » utilisent leurs propres comptes, ils obtiennent leurs privilèges spéciaux quel que soit leur mode de connexion, qu'il s'agisse des dial-ups, des machines shell, ou même de l'extérieur avec un nom d'utilisateur et un mot de passe. Enfin, voici un exemple très simple de configuration pour un serveur public pour une hiérarchie particulière. auth default { hosts: * default: } access default { users: newsgroups: example.* addcanlockuser: none } Notez que les clients ne sont pas autorisés à lire d'autres groupes ; cela les empêche d'accéder aux groupes administratifs ou de lire les messages de contrôle, par mesure de précaution. Lorsque vous exécutez un serveur public comme celui-ci, sachez que de nombreuses hiérarchies publiques seront ultérieurement téléchargées et réinjectées dans Usenet principal, il est donc fortement recommandé d'exécuter également un filtre Perl ou Python pour rejeter tout message crossposté en dehors de votre hiérarchie locale, et tout message contenant un en-tête Supersedes. Cela empêchera les messages publiés dans votre hiérarchie publique de nuire au reste de Usenet s'ils fuient. Pour des cas plus complexes, ou si vous préférez simplement utiliser une base de données pour stocker les informations d'authentification et/ou d'autorisation, vous pouvez utiliser des scripts Perl ou Python pour authentifier dynamiquement les utilisateurs et/ou générer leurs blocs d'accès. Vous pouvez alors stocker toutes les informations associées (utilisateur, mot de passe, groupes de news pour la lecture, groupes de news pour la publication, etc.) par exemple dans une base de données SQLite, et utiliser un script nnrpd_auth.pl ou nnrpd_auth.py pour authentifier les utilisateurs, et/ou un script nnrpd_access.pl ou nnrpd_access.py pour accorder l'accès. Alors readers.conf n'a besoin que de la définition suivante : auth checkcredentials { perl_auth: « /path/to/script/nnrpd_auth.pl » perl_access: « /path/to/script/nnrpd_access.pl » } ou : auth checkcredentials { python_auth: « nnrpd_auth » python_access: « nnrpd_access » } L'avantage de ces scripts externes est que vous pouvez coder toutes les règles que vous souhaitez, potentiellement basées sur une base de données partagée entre votre service de news et d'autres services que vous pourriez fournir à vos utilisateurs. Vous pouvez gérer plus facilement des centaines ou des milliers d'utilisateurs avec des scripts externes qu'avec la simple utilisation des blocs standard de readers.conf et d'un fichier plat pour les informations d'identification de chaque utilisateur listé.

CONSIDÉRATIONS DE SÉCURITÉ

En général, des mots de passe séparés doivent être utilisés pour NNTP chaque fois que possible ; le protocole NNTP lui-même ne protège pas les mots de passe contre l'interception fortuite, et de nombreuses implémentations (y compris celle-ci) ne « verrouillent » pas les comptes et ne découragent pas autrement les attaques par devinettes de mots de passe. Il est donc préférable de s'assurer qu'un mot de passe compromis a des effets minimaux.

L'authentification à l'aide des commandes AUTHINFO USER/PASS est transmise en clair sur le réseau. Une extrême prudence doit donc être exercée, en particulier avec les mots de passe système (par exemple, « auth: ckpasswd -s »). Les mots de passe peuvent être protégés en utilisant NNTP sur TLS/SSL ou via des tunnels ssh, et cette utilisation peut être imposée par une configuration de serveur bien réfléchie qui n'autorise que certains groupes d'authentification à être appliqués dans certains cas. On peut également s'authentifier à l'aide d'un mécanisme SASL robuste. Voici quelques idées :

  • Pour restreindre les connexions sur le port NNTP standard (119) à utiliser une couche de chiffrement pour certains (ou tous) les groupes d'authentification correspondants, utilisez le paramètre require_encryption. Notez qu'un client peut utiliser STARTTLS pour négocier une connexion TLS chiffrée. Une couche sécurisée peut également être négociée pendant l'authentification via AUTHINFO SASL.
  • Si vous considérez votre réseau local (mais pas Internet) comme sécurisé, ayez quelques groupes d'authentification avec un paramètre hosts restrictif ; ils iraient en haut, avec ceux ayant une applicabilité globale en bas.
  • Envisagez d'exécuter nnrpd avec le drapeau -S (soit également avec -D, soit à partir d'un « super-serveur » comme inetd) sur le port NNTPS (563) pour les clients qui prennent en charge TLS/SSL. Voir nnrpd(8) pour plus de détails sur la configuration. Vous pouvez utiliser le paramètre require_encryption ou le drapeau -c pour spécifier un fichier readers.conf alternatif si vous souhaitez une configuration substantiellement différente pour ce cas.

AUTH GROUP PARAMETERS

Les paramètres suivants sont disponibles pour le groupe auth.

localaddress

Si ce paramètre est défini sur yes, l'authentification réussira uniquement pour les connexions provenant de l'adresse locale (c'est-à-dire 127.0.0.1 ou ::1). Cela est utile pour restreindre l'accès aux utilisateurs exécutant des lecteurs de news sur localhost ou se connectant via un tunnel SSH.

ACCESS GROUP PARAMETERS

Les paramètres suivants sont disponibles pour le groupe access.

localaddress

Si ce paramètre est défini sur yes, l'accès sera autorisé uniquement pour les connexions provenant de l'adresse locale (c'est-à-dire 127.0.0.1 ou ::1). Comme pour le paramètre auth localaddress, cela est utile pour restreindre l'accès aux utilisateurs exécutant des lecteurs de news sur localhost ou se connectant via un tunnel SSH.

SUMMARY

Les groupes auth et access peuvent être configurés pour restreindre l'authentification et l'accès aux connexions locales en utilisant le paramètre localaddress.

EXAMPLES

Pour autoriser uniquement les connexions locales via SSH pour l'authentification et l'accès :

auth {
    localaddress: yes
}
access {
    localaddress: yes
}

Pour autoriser uniquement les connexions locales pour l'authentification, mais autoriser toutes les connexions pour l'accès :

auth {
    localaddress: yes
}
access {
    # Toutes les connexions sont autorisées
}

SECURITY CONSIDERATIONS

L'utilisation de localaddress: yes dans le groupe auth ou access est une mesure de sécurité importante pour empêcher l'accès non autorisé aux serveurs de news depuis Internet. Si vous avez besoin d'autoriser l'accès depuis des adresses IP externes, assurez-vous de configurer correctement les autres mécanismes d'authentification et d'autorisation.

Pour limiter un groupe d'authentification afin qu'il corresponde uniquement aux connexions en boucle locale (pour les utilisateurs exécutant des lecteurs de news sur localhost ou se connectant via un tunnel SSH), utilisez le paramètre localaddress.
