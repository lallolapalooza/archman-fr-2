NOM

re2swift - génère des analyseurs lexicaux rapides pour Swift

SYNTAXE

re2swift [ OPTIONS ] [ AVERTISSEMENTS ] ENTRÉE

L'entrée peut être un fichier ou - pour stdin.

INTRODUCTION

re2swift fonctionne comme un préprocesseur. Il lit le fichier d'entrée (qui est généralement un programme en Swift, mais peut être n'importe quoi) et recherche des blocs de code entourés de marqueurs spéciaux de début/fin. Le texte en dehors de ces blocs est copié tel quel dans le fichier de sortie. Le contenu des blocs est traité par re2swift. Il le traduit en code Swift et sort le code généré à la place du bloc.

Voici un exemple d'un petit programme qui vérifie si une chaîne donnée contient un nombre décimal :

// re2swift $INPUT -o $OUTPUT -i
func lex(_ yyinput: UnsafePointer<UInt8>) -> Bool {
  var yycursor = 0
  /*!re2c
    re2c:yyfill:enable = 0;
    [1-9][0-9]* { return true }
    *           { return false }
  */
}
assert(lex("1234"))

En sortie, re2swift a remplacé le bloc du milieu par le code généré :

/* Généré par re2swift */
// re2swift $INPUT -o $OUTPUT -i
func lex(_ yyinput: UnsafePointer<UInt8>) -> Bool {
  var yycursor = 0
  var yych: UInt8 = 0
  var yystate: UInt = 0
  yyl: while true {
    switch yystate {
      case 0:
        yych = yyinput[yycursor]
        yycursor += 1
        switch yych {
          case 0x31...0x39:
            yystate = 2
            continue yyl
          default:
            yystate = 1
            continue yyl
        }
      case 1: return false
      case 2:
        yych = yyinput[yycursor]
        switch yych {
          case 0x30...0x39:
            yycursor += 1
            yystate = 2
            continue yyl
          default:
            yystate = 3
            continue yyl
        }
      case 3: return true
      default: fatalError("Erreur interne de l'analyseur")
    }
  }
}
assert(lex("1234"))

BASES

Un programme re2swift se compose d'une séquence de blocs mélangés à du code dans le langage cible. Un bloc peut contenir des définitions, des configurations, des règles, des actions et des directives dans n'importe quel ordre :

nom = expression-régulière ;
Une définition lie nom à expression-régulière. Les noms peuvent contenir des caractères alphanumériques et des traits de soulignement. La section expressions régulières donne un aperçu de la syntaxe re2swift pour les expressions régulières. Une fois défini, le nom peut être utilisé dans d'autres expressions régulières et dans des règles. La récursion dans les définitions nommées n'est pas autorisée, et chaque nom doit être défini avant d'être utilisé. Un bloc hérite des définitions nommées du scope global. Redéfinir un nom existant dans le scope actuel est une erreur.
configuration = valeur ;
Une configuration permet de modifier le comportement de re2swift et de personnaliser le code généré. Pour une liste complète des configurations supportées par re2swift, voir la section configurations. En fonction d'une configuration particulière, la valeur peut être un mot-clé, un nombre entier non négatif ou une chaîne d'une seule ligne qui doit être entourée de guillemets doubles ou simples, sauf si elle est composée de caractères alphanumériques. Un bloc hérite des configurations du scope global et peut les redéfinir ou en ajouter de nouvelles. Les configurations définies à l'intérieur d'un bloc affectent tout le bloc, même si elles apparaissent à la fin de celui-ci.
expression-régulière code
Une règle lie une expression-régulière à son action sémantique (un bloc de code entre accolades, ou un bloc de code qui commence par := et se termine sur une nouvelle ligne suivie d'un caractère non blanc). Si l'expression-régulière correspond, le code associé est exécuté. Si plusieurs règles correspondent, la correspondance la plus longue a la priorité. Si plusieurs règles correspondent à la même chaîne, la première d'entre elles a la priorité. Il existe deux règles spéciales : la règle par défaut * et la règle de fin d'entrée $. La règle par défaut doit toujours être définie ; elle a la priorité la plus basse, quel que soit son emplacement dans le bloc, et elle correspond à n'importe quelle unité de code (pas nécessairement un caractère valide, voir la section support de l'encodage). La règle de fin d'entrée doit être définie si la méthode correspondante pour la gestion de la fin d'entrée est utilisée. Avec les conditions de départ, les règles ont une syntaxe plus complexe.
!action code
Une action lie un bloc de code défini par l'utilisateur à un endroit particulier dans la machine à états finis générée (de la même manière que les actions sémantiques lient le code aux états finaux). Voir la section actions pour une liste complète des actions prédéfinies.
!directive ;
Une directive est l'une des instructions spéciales prédéfinies. Chaque directive a un but unique. Voir la section directives pour les détails.

Blocs

Les marqueurs de début et de fin de bloc sont soit /*!re2c et */, soit %{ et %} (les deux styles sont supportés). À partir de la version 2.2, les blocs peuvent avoir des noms optionnels qui leur permettent d'être référencés dans d'autres blocs. Il existe différents types de blocs :

/*!re2c[:<nom>] ... */ ou %{[:<nom>] ... %}
Un bloc global contient des définitions, des configurations, des règles et des directives. re2swift compile les expressions régulières associées à chaque règle en un automate fini déterministe, l'encode sous forme de sauts conditionnels dans le langage cible et remplace le bloc par le code généré. Les noms et configurations définis dans un bloc global sont ajoutés au scope global et deviennent visibles pour les blocs suivants. Au début du programme, le scope global est initialisé avec les options de la ligne de commande.
/*!local:re2c[:<nom>] ... */ ou %{local[:<nom>] ... %}
Un bloc local est similaire à un bloc global, mais les noms et configurations qu'il contient ont une portée locale (ils n'affectent pas les autres blocs).
/*!rules:re2c[:<nom>] ... */ ou %{rules[:<nom>] ... %}
Un bloc de règles est similaire à un bloc local, mais il ne génère aucun code par lui-même, ni n'ajoute de définitions au scope global — il est destiné à être réutilisé dans d'autres blocs. C'est une façon de partager du code (plus de détails dans la section blocs réutilisables). Avant la version 2.2 de re2swift, les blocs de règles nécessitaient l'option -r --reusable.
/*!use:re2c[:<nom>] ... */ ou %{use[:<nom>] ... %}
Un bloc qui référence un bloc de règles défini précédemment. Si le nom est spécifié, re2swift recherche un bloc de règles portant ce nom. Sinon, le bloc de règles le plus récent est utilisé (nommé ou non nommé). Un bloc d'utilisation peut ajouter ses propres définitions, configurations et règles, qui sont ajoutées à celles du bloc de règles référencé. Avant la version 2.2 de re2swift, les blocs d'utilisation nécessitaient l'option -r --reusable.
/*!max:re2c[:<nom1>[:<nom2>...]] ... */ ou %{max[:<nom1>[:<nom2>...]] ... %}
Un bloc qui génère la définition YYMAXFILL. Une liste optionnelle de noms de blocs spécifie quels blocs doivent être inclus lors du calcul de la valeur YYMAXFILL (si la liste est vide, tous les blocs sont inclus). Par défaut, le code généré est une macro-définition pour C (#define YYMAXFILL <n>), ou une variable globale pour Go (var YYMAXFILL int = <n>). Il peut être personnalisé avec une configuration optionnelle format qui spécifie une chaîne de modèle où @@{max} (ou @@ pour faire court) est remplacé par la valeur numérique de YYMAXFILL.
/*!maxnmatch:re2c[:<nom1>[:<nom2>...]] ... */ ou %{maxnmatch[:<nom1>[:<nom2>...]] ... %}
Un bloc qui génère la définition YYMAXNMATCH (nécessite l'option -P --posix-captures). Une liste optionnelle de noms de blocs spécifie quels blocs doivent être inclus lors du calcul de la valeur YYMAXNMATCH (si la liste est vide, tous les blocs sont inclus). Par défaut, le code généré est une macro-définition pour C (#define YYMAXNMATCH <n>), ou une variable globale pour Go (var YYMAXNMATCH int = <n>). Il peut être personnalisé avec une configuration optionnelle format qui spécifie une chaîne de modèle où @@{nmatch} (ou @@ pour faire court) est remplacé par la valeur numérique de YYMAXNMATCH.

Blocs

Les blocs sont des commentaires spéciaux qui sont utilisés pour contrôler la génération de code à partir de re2swift. Ils sont reconnus par le préfixe /*! ou %{, suivi du nom du bloc et éventuellement d'options et de configurations. Les blocs peuvent également être nommés, ce qui permet de les inclure sélectivement dans la sortie. Les blocs nommés sont spécifiés après le nom du bloc, séparés par des deux-points. Par exemple, /*!name1:name2:block*/ définit un bloc nommé name1 et name2.

/*!max:re2c[:<name1>[:<name2>...]] ... */ ou %{max[:<name1>[:<name2>...]] ... %}
Un bloc qui spécifie une chaîne de modèle pour le nombre maximal de correspondances. Il accepte une configuration facultative format qui spécifie une chaîne de modèle où @@{max} (ou @@ pour faire court) est remplacé par la valeur numérique de YYMAXNMATCH.
/*!stags:re2c[:<name1>[:<name2>...]] ... */, /*!mtags:re2c[:<name1>[:<name2>...]] ... */ ou %{stags[:<name1>[:<name2>...]] ... %}, %{mtags[:<name1>[:<name2>...]] ... %{
Blocs qui spécifient un modèle de morceau de code qui est développé pour chaque variable de balise s/m générée par re2swift. Une liste facultative de noms de blocs spécifie quels blocs doivent être inclus lors du calcul de l'ensemble des variables de balise (si la liste est vide, tous les blocs sont inclus). Il existe deux configurations facultatives : format et separator. La configuration format spécifie une chaîne de modèle où @@{tag} (ou @@ pour faire court) est remplacé par le nom de chaque variable de balise. La configuration separator spécifie un morceau de code utilisé pour joindre les morceaux générés format pour différentes variables de balise.
/*!svars:re2c[:<name1>[:<name2>...]] ... */, /*!mvars:re2c[:<name1>[:<name2>...]] ... */ ou %{svars[:<name1>[:<name2>...]] ... %}, %{mvars[:<name1>[:<name2>...]] ... %{
Blocs qui spécifient un modèle de morceau de code qui est développé pour chaque balise s/m qui est soit explicitement mentionnée par les règles (avec l'option --tags) soit implicitement générée par re2swift (avec les options --captvars ou --posix-captvars). Une liste facultative de noms de blocs spécifie quels blocs doivent être inclus lors du calcul de l'ensemble des balises (si la liste est vide, tous les blocs sont inclus). Il existe deux configurations facultatives : format et separator. La configuration format spécifie une chaîne de modèle où @@{tag} (ou @@ pour faire court) est remplacé par le nom de chaque balise. La configuration separator spécifie un morceau de code utilisé pour joindre les morceaux générés format pour différentes balises.
/*!getstate:re2c[:<name1>[:<name2>...]] ... */ ou %{getstate[:<name1>[:<name2>...]] ... %}
Un bloc qui génère une dispersion conditionnelle sur l'état de l'analyseur lexical (il nécessite l'option --storable-state). Une liste facultative de noms de blocs spécifie quels blocs doivent être inclus dans la dispersion d'état. La transition par défaut va à l'étiquette de début du premier bloc de la liste. Si la liste est vide, tous les blocs sont inclus, et la transition par défaut va au premier bloc du fichier qui a une étiquette de début. Ce type de bloc est incompatible avec l'option --loop-switch, car il nécessite des transitions inter-blocs qui ne sont pas prises en charge sans goto ou appels de fonction.
/*!conditions:re2c[:<name1>[:<name2>...]] ... */, /*!types:re2c... */ ou %{conditions[:<name1>[:<name2>...]] ... %}, %{types... %}
Un bloc qui génère une énumération de conditions (il nécessite l'option --conditions). Une liste facultative de noms de blocs spécifie quels blocs doivent être inclus lors du calcul de l'ensemble des conditions (si la liste est vide, tous les blocs sont inclus). Par défaut, le code généré est une énumération YYCONDTYPE. Il peut être personnalisé avec les configurations facultatives format et separator. La configuration format spécifie une chaîne de modèle où @@{cond} (ou @@ pour faire court) est remplacé par le nom de chaque condition, et @@{num} est remplacé par un index numérique de cette condition. La configuration separator spécifie un morceau de code utilisé pour joindre les morceaux générés format pour différentes conditions.
/*!include:re2c <file> */ ou %{include <file> %}
Ce bloc permet d'inclure <file>, qui doit être un chemin de fichier entre guillemets doubles. Le contenu du fichier est littéralement substitué à la place du bloc, de la même manière que #include fonctionne en C/C++. Ce bloc peut être utilisé avec l'option --depfile pour générer des dépendances de système de build sur les fichiers inclus.
/*!header:re2c:on*/ ou %{header:on %}
Ce bloc marque le début du fichier d'en-tête. Tout ce qui suit et jusqu'à le bloc header:off suivant est traité par re2swift et écrit dans le fichier d'en-tête spécifié avec l'option -t --type-header.
/*!header:re2c:off*/ ou %{header:off %}
Ce bloc marque la fin du fichier d'en-tête commencé avec le bloc header:on*/.
/*!ignore:re2c ... */ ou %{ignore ... %}
Un bloc dont le contenu est ignoré et supprimé du fichier de sortie.

Configurations

Voici une liste complète des configurations prises en charge par re2swift :

re2c:api, re2c:input
Identique à l'option --api.
re2c:api:sigil
Spécifie le marqueur ("sigil") utilisé pour les espaces réservés d'arguments dans les primitives d'API. La valeur par défaut est @@. Un espace réservé commence par le sigil suivi du nom de l'argument entre accolades. Par exemple, si le sigil est défini sur $, les espaces réservés auront la forme ${name}. Les API à argument unique peuvent utiliser une notation abrégée sans le nom entre accolades. Cette option peut être remplacée par des options pour des primitives d'API individuelles, par exemple re2c:YYFILL@len pour YYFILL.
re2c:api:style
Spécifie le style de l'API. Les valeurs possibles sont functions (la valeur par défaut pour C) et free-form (la valeur par défaut pour Go et Rust). Dans le style functions, les primitives d'API sont générées avec une liste d'arguments entre parenthèses suivant le nom de la primitive. Les arguments ne sont fournis que pour les paramètres auto-générés (tels que le nombre de caractères passés à YYFILL), mais pas pour le contexte général de l'analyseur lexical, de sorte que les primitives se comportent davantage comme des macros en C/C++ ou des fermetures en Go et Rust. Dans le style free-form, les primitives d'API n'ont pas de forme fixe : elles doivent être définies comme des chaînes contenant des morceaux de code en forme libre avec des variables interpolées de la forme @@{var} ou @@ (elles correspondent aux arguments dans le style fonctionnel). Cette configuration peut être remplacée pour des primitives d'API individuelles, voir par exemple la configuration re2c:YYFILL:naked pour YYFILL.

re2c:case-insensitive, re2c:flags:case-insensitive

re2c:case-inverted, re2c:flags:case-inverted

re2c:case-ranges, re2c:flags:case-ranges
Identique à l'option --case-ranges, mais peut être configuré par bloc.
re2c:computed-gotos, re2c:flags:computed-gotos, re2c:flags:g

re2c:computed-gotos:relative, re2c:cgoto:relative

Si les goto calculés sont utilisés, cette configuration spécifie le seuil de complexité qui déclenche la génération de tables de sauts au lieu de conditions if imbriquées et de bitmaps. La valeur par défaut est 9.
re2c:cond:abort
Si elle est définie sur une valeur entière positive, le cas par défaut dans la dispersion de conditions générée arrête l'exécution du programme.
re2c:cond:goto
Spécifie un morceau de code utilisé pour les règles de raccourci auto-générées :=> dans les conditions. La valeur par défaut est goto @@;. L'espace réservé @@ est substitué par le nom de la condition (voir les configurations re2c:api:sigil et re2c:cond:goto@cond).
re2c:cond:goto@cond
Spécifie le sigil utilisé pour la substitution d'arguments dans la définition de re2c:cond:goto. La valeur par défaut est @@. Remplace la configuration plus générique re2c:api:sigil.
re2c:cond:divider
Définit le diviseur pour les blocs de conditions. La valeur par défaut est /* *********************************** */. Les espaces réservés sont substitués par le nom de la condition (voir re2c:api;sigil et re2c:cond:divider@cond).
re2c:cond:divider@cond
Spécifie le sigil utilisé pour la substitution d'arguments dans la définition de re2c:cond:divider. La valeur par défaut est @@. Remplace la configuration plus générique re2c:api:sigil.
re2c:cond:prefix, re2c:condprefix
Spécifie le préfixe utilisé pour les étiquettes de condition. La valeur par défaut est yyc_.

Spécifie le préfixe utilisé pour les identificateurs de condition. La valeur par défaut est yyc.

re2c:header, re2c:flags:type-header, re2c:flags:t
Spécifie le nom du fichier d'en-tête généré par rapport au répertoire du fichier de sortie. Identique à l'option --header, sauf que le chemin du fichier est relatif.
re2c:indent:string
Spécifie la chaîne utilisée pour l'indentation. La valeur par défaut est une tabulation unique "\t". La chaîne d'indentation ne doit contenir que des espaces blancs. Pour désactiver complètement l'indentation, définissez cette configuration sur une chaîne vide.
re2c:indent:top
Spécifie le montant minimum d'indentation à utiliser. La valeur par défaut est zéro. La valeur doit être un nombre entier non négatif.
re2c:invert-captures
Identique à l'option --invert-captures, mais peut être configuré par bloc.
re2c:label:prefix, re2c:labelprefix
Spécifie le préfixe utilisé pour les étiquettes d'état DFA. La valeur par défaut est yy.
re2c:label:start, re2c:startlabel
Contrôle la génération d'une étiquette de début de bloc. La valeur par défaut est zéro, ce qui signifie que l'étiquette de début est générée uniquement si elle est utilisée. Une valeur entière supérieure à zéro force la génération de l'étiquette de début, même si elle n'est pas utilisée par le lexer. Une valeur de chaîne force également la génération de l'étiquette de début et définit le nom de l'étiquette comme étant la chaîne spécifiée. Cette configuration s'applique uniquement au bloc actuel (elle est réinitialisée à la valeur par défaut pour le bloc suivant).
re2c:label:yyFillLabel
Spécifie le préfixe des étiquettes YYFILL utilisées avec re2c:eof et en mode état stockable.
re2c:label:yyloop
Spécifie le nom de l'étiquette marquant le début de la boucle du lexer avec l'option --loop-switch. La valeur par défaut est yyloop.
re2c:label:yyNext
Spécifie le nom de l'étiquette optionnelle qui suit le commutateur YYGETSTATE en mode état stockable (activé avec re2c:state:nextlabel). La valeur par défaut est yyNext.
re2c:lookahead, re2c:flags:lookahead
Obsolète (voir l'option obsolète --no-lookahead).
re2c:monadic
Si défini à une valeur non nulle, le lexer généré utilisera la notation monadique (cette configuration est spécifique à Haskell).
re2c:nested-ifs, re2c:flags:nested-ifs, re2c:flags:s
Identique à l'option --nested-ifs, mais peut être configuré par bloc.
re2c:posix-captures, re2c:flags:posix-captures, re2c:flags:P
Identique à l'option --posix-captures, mais peut être configuré par bloc.
re2c:posix-captvars
Identique à l'option --posix-captvars, mais peut être configuré par bloc.
re2c:tags, re2c:flags:tags, re2c:flags:T
Identique à l'option --tags, mais peut être configuré par bloc.
re2c:tags:expression
Spécifie l'expression utilisée pour les variables de balise. Par défaut, re2swift génère des expressions de la forme yyt<N>. Cela peut être gênant, par exemple si les variables de balise sont définies comme des champs dans une structure. Toutes les occurrences de @@{tag} ou @@ sont remplacées par le nom réel de la balise. Par exemple, re2c:tags:expression = "s.@@"; génère des expressions de la forme s.yyt<N> dans le code généré. Voir aussi la configuration re2c:api:sigil.
re2c:tags:negative
Spécifie l'expression constante utilisée pour une valeur de balise négative (typiquement ce serait -1 si les balises sont des décalages d'entiers dans la chaîne d'entrée, ou un pointeur nul si ce sont des pointeurs).
re2c:tags:prefix
Spécifie le préfixe des noms de variables de balise. La valeur par défaut est yyt.
re2c:sentinel
Spécifie le symbole sentinelle utilisé pour les vérifications de fin de fichier (lorsque les vérifications de limites sont désactivées avec re2c:yyfill:enable = 0; et que re2c:eof n'est pas défini). Cette configuration n'affecte pas la génération de code : son but est de vérifier que le sentinelle n'est pas autorisé au milieu d'une règle, et de s'assurer que le lexer ne lira pas au-delà de la fin du tampon. La valeur par défaut est -1` (dans ce cas, re2swift suppose que le sentinelle est zéro, ce qui est le cas le plus courant). Seuls les nombres décimaux sont reconnus.
re2c:state:abort
Si défini à une valeur entière positive, le cas par défaut dans la distribution d'état générée interrompt l'exécution du programme, et un cas explicite -1 contient la transition vers le début du bloc.
re2c:state:nextlabel
Contrôle si le commutateur YYGETSTATE est suivi d'une étiquette yyNext (la valeur par défaut est zéro, ce qui correspond à aucune étiquette). SYNOPSIS

The syntax for regular expressions used by re2swift is a simplified version of POSIX extended regular expressions, with a few extensions:

"foo"
Littéral de chaîne sensible à la casse.
'foo'
Littéral de chaîne insensible à la casse.
[a-xyz], [^a-xyz]
Classe de caractères (éventuellement niée).
.
N'importe quel caractère sauf une nouvelle ligne.
R \ S
Différence de classes de caractères R et S.
R*
Zéro ou plusieurs occurrences de R.
R+
Une ou plusieurs occurrences de R.
R?
R optionnel.
R{n}
Répétition de R exactement n fois.
R{n,}
Répétition de R au moins n fois.
R{n,m}
Répétition de R de n à m fois.
(R)
Juste R ; les parenthèses sont utilisées pour outrepasser la précédence. Si l'extraction de sous-correspondance est activée, (R) est un groupe capturant ou non capturant selon l'option --invert-captures.
(!R)
Si l'extraction de sous-correspondance est activée, (!R) est un groupe non capturant ou capturant selon l'option --invert-captures.
R S
Concaténation : R suivi de S.
R | S
Alternative : R ou S.
R / S
Lookahead : R suivi de S, mais S n'est pas consommé.
name
Expression régulière définie comme name (ou chaîne littérale "name" en mode compatibilité Flex).
{name}
Expression régulière définie comme name en mode compatibilité Flex.
@stag
Un s-tag : sauvegarde la dernière position d'entrée à laquelle @stag correspond dans une variable nommée stag.
#mtag
Un m-tag : sauvegarde toutes les positions d'entrée auxquelles #mtag correspond dans une variable nommée mtag.

Les classes de caractères et les littéraux de chaînes peuvent contenir les séquences d'échappement suivantes : \a, \b, \f, \n, \r, \t, \v, \\, les échappements octaux \ooo et les échappements hexadécimaux \xhh, \uhhhh et \Uhhhhhhhh.

Actions

Voici une liste des actions prédéfinies prises en charge par re2swift :

!entry code
L'action d'entrée lie un bloc de code défini par l'utilisateur à l'état de départ de la machine à états finis actuelle. Si des conditions de départ sont utilisées, l'action d'entrée peut être définie individuellement pour chaque condition. Cette action peut être utilisée pour effectuer une initialisation, par exemple pour sauvegarder l'emplacement de départ d'un lexeme.
!pre_rule code
L'action pré-règle préfixe un bloc de code défini par l'utilisateur aux actions sémantiques de toutes les règles du bloc actuel (ou condition, si des conditions de départ sont utilisées). Cette action peut être utilisée pour factoriser la partie commune de toutes les actions sémantiques (par exemple, sauvegarder l'emplacement de fin d'un lexeme).
!post_rule code
L'action post-règle ajoute un bloc de code défini par l'utilisateur aux actions sémantiques de toutes les règles du bloc actuel (ou condition, si des conditions de départ sont utilisées). Cette action peut être utilisée pour émettre des instructions de trap qui protègent contre les flux de contrôle involontaires.

Directives

Voici une liste complète des directives prises en charge par re2swift :

!use:name ;
Une directive d'utilisation intra-bloc qui fusionne un bloc de règles défini précédemment avec le nom spécifié dans le bloc actuel. Les définitions nommées, les configurations et les règles du bloc référencé sont ajoutées aux actuelles. Les conflits entre les règles et configurations chevauchantes sont résolus de la manière habituelle : la première règle a la priorité, et la dernière configuration remplace les précédentes. Une exception concerne les règles spéciales *, $ et <!> pour lesquelles une définition locale au bloc a toujours la priorité. Une directive d'utilisation peut être placée n'importe où à l'intérieur d'un bloc, et plusieurs directives d'utilisation sont autorisées.
!include file ;
Cette directive est identique au bloc include : elle insère le contenu de file verbatim à la place de la directive.

Interface du programme

Le code généré interagit avec le programme externe à l'aide de primitives, collectivement appelées API. Les primitives qui doivent être définies pour un programme particulier dépendent de plusieurs facteurs, notamment de la complexité des expressions régulières, de la représentation de l'entrée, de la mise en tampon et de l'utilisation de diverses fonctionnalités. Toutes les primitives nécessaires doivent être définies par l'utilisateur sous forme de macros, fonctions, variables ou toute autre forme appropriée qui rend le code généré syntaxiquement et sémantiquement correct. re2swift ne vérifie pas (et ne peut pas vérifier) les définitions, donc si quelque chose manque ou est mal défini, le programme généré peut présenter des erreurs de compilation ou d'exécution. Ce manuel fournit des exemples de définitions d'API dans les cas les plus courants.

re2swift a trois saveurs d'API qui définissent l'ensemble de base des primitives utilisées par un programme :

API Simple
C'est la valeur par défaut pour le backend Swift. Elle se compose des primitives suivantes : YYINPUT (qui doit être défini comme une séquence d'unités de code, par exemple une chaîne de caractères) et YYCURSOR, YYMARKER, YYCTXMARKER, YYLIMIT (qui doivent être définis comme des indices dans YYINPUT).
API Record
L'API Record est utile dans les cas où l'état du lexer doit être stocké dans un objet. Elle est activée avec l'option --api record ou la configuration re2c:api = record. Cette API se compose d'une variable yyrecord (le nom peut être remplacé par re2c:YYRECORD) qui doit être définie comme une structure ou une classe avec les champs yyinput, yycursor, yymarker, yyctxmarker, yylimit (seuls les champs utilisés par le code généré doivent être définis, et leurs noms peuvent être configurés).
API Générique
C'est l'API la plus flexible. Elle est activée avec l'option --api generic ou la configuration re2c:api = generic. Cette API contient les primitives suivantes pour les opérations génériques : YYPEEK, YYSKIP, YYBACKUP, YYBACKUPCTX, YYSTAGP, YYSTAGN, YYMTAGP, YYMTAGN, YYRESTORE, YYRESTORECTX, YYRESTORETAG, YYSHIFT, YYSHIFTSTAG, YYSHIFTMTAG, YYLESSTHAN. Par exemple, si l'entrée est un tableau d'octets terminé par zéro buffer: [UInt8], les variables cursor, limit, marker et ctxmarker de type Int représentent les positions d'entrée, et -1 représente les positions invalides, alors une API générique peut être définie comme suit :
/*!re2c
  re2c:YYPEEK       = "buffer[cursor]";
  re2c:YYSKIP       = "cursor++";
  re2c:YYBACKUP     = "marker = cursor";
  re2c:YYRESTORE    = "cursor = marker";
  re2c:YYBACKUPCTX  = "ctxmarker = cursor";
  re2c:YYRESTORECTX = "cursor = ctxmarker";
  re2c:YYRESTORETAG = "cursor = ${tag}";
  re2c:YYLESSTHAN   = "limit - cursor < @@{len}";
  re2c:YYSTAGP      = "@@{tag} = cursor";
  re2c:YYSTAGN      = "@@{tag} = -1";
  re2c:YYSHIFT      = "cursor += @@{shift}";
  re2c:YYSHIFTSTAG  = "@@{tag} += @@{shift}";
*/

Voici une liste complète des primitives d'API qui peuvent être utilisées par le code généré pour interagir avec le programme externe.

YYCTYPE
Le type des caractères d'entrée (unités de code). Pour les encodages ASCII, EBCDIC et UTF-8, il doit s'agir d'un entier non signé de 1 octet. Pour UTF-16 ou UCS-2, il doit s'agir d'un entier non signé de 2 octets. Pour UTF-32, il doit s'agir d'un entier non signé de 4 octets.
YYCURSOR
Une valeur l-value qui stocke la position d'entrée actuelle (un pointeur ou un décalage d'entier dans YYINPUT). Initialement, YYCURSOR doit pointer vers le premier caractère d'entrée, et plus tard, il est avancé par le code généré. Lorsqu'une règle correspond, la position YYCURSOR est celle qui suit le dernier caractère correspondant.
YYLIMIT
Une valeur r-value qui stocke la position de fin d'entrée (un pointeur ou un décalage d'entier dans YYINPUT). Initialement, YYLIMIT doit pointer vers la position suivant le dernier caractère d'entrée disponible. Il n'est pas modifié par le code généré. Le lexer compare YYCURSOR à YYLIMIT pour déterminer s'il reste suffisamment de caractères d'entrée.
YYMARKER
Une valeur l-value qui stocke la position de la dernière règle correspondante (un pointeur ou un décalage d'entier dans YYINPUT). Elle est utilisée pour restaurer la position YYCURSOR si la correspondance la plus longue échoue et que le lexer doit revenir en arrière. Aucune initialisation n'est nécessaire.
YYCTXMARKER
Une valeur l-value qui stocke la position du contexte de suivi (un pointeur ou un décalage d'entier dans YYINPUT). Aucune initialisation n'est nécessaire. YYCTXMARKER n'est nécessaire que si l'opérateur de lookahead / est utilisé.
YYFILL
Une primitive d'API générique avec une variable len. YYFILL doit fournir au moins len caractères d'entrée supplémentaires ou échouer. YYACCEPT
Une primitive qui stocke le nombre de règles correspondant à la dernière correspondance. Une primitive avec un argument cond. Elle vérifie si la condition donnée est la condition actuelle. Si oui, elle compare l'entrée à la fin de fichier et si c'est le cas, elle retourne 1 (vrai), sinon elle retourne 0 (faux). Sinon, elle retourne 0.

YYCOPYSTAG
Une primitive API générique avec deux variables, lhs et rhs, qui doit copier la variable de marque s de droite rhs vers la variable de marque s de gauche lhs. Pour la plupart des langages, cette primitive a une définition par défaut qui attribue lhs à rhs.
YYDEBUG
Cette primitive est générée uniquement avec l'option -d, --debug-output. Son but est d'ajouter de la journalisation au code généré (une définition YYDEBUG typique est une instruction d'impression). Les instructions YYDEBUG sont générées dans chaque état et ont deux variables : state (soit un index d'état DFA, soit -1) et symbol (le symbole d'entrée actuel).
YYFILL
Une primitive d'API générique avec une variable len. Elle doit être définie comme une instruction qui tente de lire au moins len caractères supplémentaires dans l'entrée. La valeur de retour de YYFILL est ignorée et elle ne doit pas retourner en cas d'échec. La valeur maximale de len est YYMAXFILL.
YYFN
Une primitive qui définit le prototype de fonction dans le modèle de code --recursive-functions. Sa valeur doit être un tableau d'une ou plusieurs chaînes de caractères, où chaque chaîne contient deux ou trois composants séparés par la chaîne spécifiée dans la configuration re2c:fn:sep (généralement un point-virgule). Le premier élément du tableau définit le nom de la fonction et le type de retour (vide pour une fonction void). Les éléments suivants définissent les arguments de la fonction : d'abord, l'expression de l'argument utilisée dans le corps de la fonction (généralement juste un nom) ; ensuite, le type de l'argument ; enfin, un paramètre formel optionnel (qui par défaut est le premier composant - généralement, l'argument et le paramètre sont le même identifiant).
YYGETACCEPT
Une primitive avec une variable var qui stocke le sélecteur numérique de la règle acceptée. Pour la plupart des langages, cette primitive a une définition par défaut qui lit à partir de var.
YYGETCOND
Une r-value de type YYCONDTYPE qui est égale à l'identifiant de la condition actuelle.
YYGETSTATE
Une r-value de type entier qui est égale à l'état actuel du lexer. Elle doit être initialisée à -1.
YYINPUT
Une r-value qui stocke la séquence d'entrée actuelle (chaîne, tampon, etc.).
YYLESSTHAN
Une primitive API générique avec une variable len. Elle doit être définie comme une r-value de type booléen qui est égale à true si et seulement s'il reste moins de len caractères d'entrée.
YYMAXFILL
Une constante entière égale à la valeur maximale de l'argument de YYFILL. Elle peut être générée avec un bloc max.
YYMAXNMATCH
Une constante entière égale au nombre maximal de groupes de capture POSIX dans une règle. Elle est générée avec un bloc maxnmatch.
YYMTAGN
Une primitive API générique avec une variable tag. YYMTAGN doit ajouter une valeur qui représente une position d'entrée inexistante à l'historique des sous-correspondances de tag (voir la section sur l'extraction des sous-correspondances).
YYMTAGP
Une primitive API générique avec une variable tag. YYMTAGP doit ajouter la position actuelle à l'historique des sous-correspondances de tag (voir la section sur l'extraction des sous-correspondances).
YYPEEK
Une primitive API générique sans variable. Elle doit être définie comme une r-value de type YYCTYPE qui est égale au caractère à la position actuelle de l'entrée.
YYRESTORE
Une primitive API générique qui doit restaurer la position actuelle de l'entrée à la valeur sauvegardée par YYBACKUP.
YYRESTORECTX
Une primitive API générique qui doit restaurer la position du contexte de fin sauvegardée avec YYBACKUPCTX.
YYRESTORETAG
Une primitive API générique avec une variable tag qui doit restaurer la position du contexte de fin à la valeur de tag.
YYSETACCEPT
Une primitive avec deux variables : var (une l-value qui stocke le sélecteur numérique de la règle acceptée) et val (la valeur du sélecteur). Pour la plupart des langages, cette primitive a une définition par défaut qui attribue var à val.
YYSETCOND
Une primitive avec une variable cond qui doit définir l'identifiant de la condition actuelle à cond.
YYSETSTATE
Une primitive avec une variable state qui doit définir l'état actuel du lexer à state.
YYSHIFT
Une primitive API générique avec une variable shift qui doit décaler la position actuelle de l'entrée de shift caractères (la valeur du décalage peut être négative).
YYSHIFTMTAG

YYSHIFTSTAG

YYSKIP

YYSTAGN

Options

Certaines des options ont des configurations correspondantes, d'autres sont gl

obligatoire et ne peut pas être modifié une fois que re2c commence à lire le fichier d'entrée. Les options de débogage nécessitent généralement de construire re2c dans une configuration de débogage. Les options internes sont utiles pour expérimenter avec les algorithmes utilisés dans re2c.

-? --help -h
Afficher le message d'aide.
--api <simple | record | générique>
Spécifier l'API utilisée par le code généré pour l'interface avec le code défini par l'utilisateur. L'option simple doit être utilisée dans des cas simples lorsqu'il n'y a pas besoin de recharger le tampon et de stocker l'état du lexer. L'option record doit être utilisée lorsque l'état du lexer doit être stocké dans un enregistrement (struct, classe, etc.). L'option générique doit être utilisée dans des cas complexes lorsque les deux autres API ne sont pas suffisamment flexibles.
--bit-vectors -b
Optimiser les sauts conditionnels à l'aide de masques de bits. Cette option implique --nested-ifs.
--captures, --leftmost-captures
Activer l'extraction de sous-correspondances avec des groupes de capture gloutons les plus à gauche. Le résultat est collecté dans un tableau yybmatch de capacité 2 * YYMAXNMATCH, et yynmatch est défini sur le nombre de groupes pour la règle de correspondance.
--captvars, --leftmost-captvars
Activer l'extraction de sous-correspondances avec des groupes de capture gloutons les plus à gauche. Le résultat est collecté dans les variables yytl<k>, yytr<k> pour le k-ième groupe de capture.
--case-insensitive
Traiter les chaînes entre apostrophes simples et guillemets doubles comme insensibles à la casse.
--case-inverted
Inverser la signification des chaînes entre apostrophes simples et guillemets doubles : traiter les chaînes entre apostrophes simples comme sensibles à la casse et les chaînes entre guillemets doubles comme insensibles à la casse.
--case-ranges
Réduire les cas consécutifs dans les instructions switch en une plage de la forme low ... high. Cette syntaxe est une extension du langage C/C++ prise en charge par des compilateurs comme GCC, Clang et Tcc. L'avantage principal par rapport à l'utilisation de cas uniques est un code généré plus petit et un temps de génération plus rapide, bien que pour certains compilateurs comme Tcc, cela se traduise également par une taille binaire plus petite.
--computed-gotos -g
Optimiser les sauts conditionnels à l'aide de l'extension non standard « computed goto » (qui doit être prise en charge par le compilateur). re2swift génère des tables de saut uniquement dans les cas complexes avec de nombreuses branches conditionnelles. Le seuil de complexité peut être configuré avec la configuration cgoto:threshold. Les décalages relatifs peuvent être activés avec la configuration cgoto:relative. Cette option implique --bit-vectors.
--computed-gotos-relative
Similaire à --computed-gotos mais génère des décalages relatifs pour les tables de saut à la place (qui doivent être prises en charge par le compilateur). Cette option implique --computed-gotos.
--conditions --start-conditions -c
Activer la prise en charge des « conditions » de type Flex : plusieurs lexers interdépendantes au sein d'un même bloc. C'est une alternative à la spécification manuelle de différents blocs re2swift connectés par goto ou des appels de fonction.
--depfile FILE
Écrire les informations de dépendance dans FILE sous la forme d'une règle Makefile <fichier-sortie> : <fichier-entrée> [fichier-inclusion ...]. Cela permet de suivre les dépendances de compilation en présence de blocs/directives include, de sorte que la mise à jour des fichiers inclus déclenche la régénération du fichier de sortie. Cette option dépend de l'option --output.
--ebcdic --ecb -e
Générer un lexer qui lit l'entrée en encodage EBCDIC. re2swift suppose que la plage de caractères est 0 -- 0xFF et que la taille des caractères est de 1 octet.
--empty-class <match-empty | match-none | error>
Définir la façon dont re2swift traite les classes de caractères vides. Avec match-empty (par défaut), la classe vide correspond à une entrée vide (ce qui est illogique, mais rétrocompatible). Avec match-none, la classe vide ne correspond jamais. Avec error, la classe vide déclenche une erreur de compilation.
--encoding-policy <fail | substitute | ignore>
Définir la façon dont re2swift traite les substituts Unicode. Avec fail, re2swift s'arrête avec une erreur lorsqu'un substitut est rencontré. Avec substitute, re2swift remplace silencieusement les substituts par le point de code d'erreur 0xFFFD. Avec ignore (par défaut), re2swift traite les substituts comme des points de code normaux. La norme Unicode stipule que les substituts autonomes sont invalides, mais les bibliothèques et les programmes du monde réel se comportent différemment.
--flex-syntax -F
Prise en charge partielle de la syntaxe Flex : dans ce mode, les définitions nommées n'ont pas besoin du signe égal et du point-virgule de terminaison, et lorsqu'elles sont utilisées, elles doivent être entourées d'accolades. Les noms sans accolades sont traités comme des chaînes entre guillemets doubles.
--goto-label
Utiliser le modèle de code « goto/label » : encoder le DFA sous forme de blocs de code étiquetés connectés par des transitions goto entre les blocs. Ceci n'est pris en charge que pour les langages qui ont une instruction goto.
--header --type-header -t HEADER
Générer un fichier HEADER. Le contenu du fichier peut être spécifié à l'aide des blocs spéciaux header:on et header:off. Si des conditions sont utilisées, l'en-tête généré aura automatiquement un énum de conditions ajouté (sauf s'il y a un bloc conditions explicite).
-I PATH
Ajouter PATH à la liste des emplacements utilisés lors de la recherche de fichiers d'inclusion. Cette option est utile en combinaison avec le bloc ou la directive include. re2swift recherche FILE dans le répertoire du fichier parent et dans les emplacements d'inclusion spécifiés avec l'option -I.
--input <default | custom>
Alias obsolète pour --api. L'option default correspond à simple (c'est en fait le défaut pour la plupart des backends, mais pas pour tous). L'option custom correspond à générique.
--input-encoding <ascii | utf8>
Spécifier la façon dont re2swift analyse les expressions régulières. Avec ascii (par défaut), re2swift traite l'entrée comme encodée en ASCII : toute séquence d'unités de code est une séquence de caractères autonomes de 1 octet. Avec utf8, re2swift traite l'entrée comme encodée en UTF8 et reconnaît les caractères multibytes.
--invert-captures
Inverser la signification des groupes de capture et des groupes non capturants. Par défaut, (...) est capturant et (! ...) est non capturant. Avec cette option, (! ...) est capturant et (...) est non capturant.
--lang <none | c | d | go | haskell | java | js | ocaml | python | rust | swift | v | zig>
Spécifier la langue cible. Les langues prises en charge sont C, D, Go, Haskell, Java, JS, OCaml, Python, Rust, Swift, V, Zig (d'autres langues peuvent être ajoutées via des fichiers de syntaxe définis par l'utilisateur, voir l'option --syntax). L'option none désactive les configurations de syntaxe par défaut, de sorte que la langue cible est indéfinie.
--location-format <gnu | msvc>
Spécifier le format d'emplacement dans les messages. Avec gnu, les emplacements sont imprimés sous forme de 'nom_fichier:ligne:colonne: ...'. Avec msvc, les emplacements sont imprimés sous forme de 'nom_fichier(ligne,colonne) ...'. Le défaut est gnu.

Utiliser le modèle de code « loop/switch » : encoder le DFA sous forme de boucle sur une instruction switch, où les états individuels sont des cas de switch. L'état est stocké dans une variable yystate. Les transitions entre les états mettent à jour yystate vers l'étiquette du cas de l'état de destination et continuent l'exécution vers la tête de la boucle.

Utiliser des instructions if imbriquées au lieu d'instructions switch dans les sauts conditionnels. Cela produit généralement un code plus efficace avec des compilateurs non optimisants.
--no-debug-info -i
Ne pas générer de directives de ligne. Cela peut être utile lorsque le code généré est stocké dans un système de contrôle de version (pour éviter d'énormes différences autogénérées sur de petits changements).
--no-generation-date
Supprimer la date de génération dans le fichier généré.
--no-version
Supprimer la version dans le fichier généré.
--no-unsafe
Ne pas générer d'enveloppement unsafe autour de YYPEEK (cette option est spécifique à Rust). L'utilisateur peut choisir de fournir une définition YYPEEK sûre, ou une définition qui n'est sûre que dans les builds de production, auquel cas l'option --no-unsafe aide à éviter les avertissements concernant les blocs unsafe redondants.
--output -o OUTPUT
Spécifier le fichier OUTPUT.

Ceci est un alias pour --empty-class match-none. Permet d'éviter l'utilisation de classes de caractères vides, qui ne correspondent à rien.
--sincode FILE

--skipping FILE

--stdfail
Ceci est un alias pour --empty-class error. Permet d'éviter l'utilisation de classes de caractères vides, qui ne correspondent à rien.
--string-mode

--syntax FILE

--tag STR

--tabs

--trace

Option interne : algorithme de minimisation du DFA utilisé par re2swift. L'option moore est l'algorithme de Moore (c'est le défaut). L'option table est l'algorithme de "remplissage de table". Les deux algorithmes devraient produire le même DFA jusqu'au renommage des états ; le remplissage de table est plus simple et beaucoup plus lent et sert d'implémentation de référence.

Option interne, obsolète. Elle permettait d'activer l'algorithme TDFA(0). Contrairement à TDFA(1), l'algorithme TDFA(0) n'utilise pas de lookahead d'un seul symbole. Il applique des opérations sur les registres aux transitions entrantes plutôt qu'aux transitions sortantes. Les benchmarks ont montré que l'algorithme TDFA(0) est moins efficace que TDFA(1).
--no-optimize-tags
Option interne : supprime l'optimisation des variables de balises (utile pour le débogage).

--posix-prectable <complex | naive>
Option interne : spécifie l'algorithme utilisé pour calculer la table de précedence POSIX. L'algorithme complex calcule la table de précedence en un seul parcours de l'arbre d'historique des balises et a une complexité quadratique par rapport au nombre d'états TNFA ; c'est le défaut. L'algorithme naive a une complexité cubique dans le pire des cas par rapport au nombre d'états TNFA, mais il est beaucoup plus simple que complex et peut être légèrement plus rapide dans les cas non pathologiques.
--stadfa
Option interne, obsolète. Elle permettait d'activer l'algorithme staDFA, qui diffère de TDFA en ce que les opérations sur les registres sont placées dans les états plutôt que sur les transitions. Les benchmarks ont montré que l'algorithme staDFA est moins efficace que TDFA.
--fixed-tags <none | toplevel | all>
Option interne : spécifie si l'optimisation des balises fixes doit être appliquée à toutes les balises (all), à aucune d'entre elles (none), ou seulement à celles dans la concaténation de niveau supérieur (toplevel). Le défaut est all. Les balises "fixes" sont celles qui sont situées à une distance fixe d'une autre balise (appelée "base"). Dans de tels cas, seule la balise de base doit être suivie, et la valeur de la balise fixe peut être calculée comme la valeur de la balise de base plus un décalage statique. Pour les balises sous alternative ou répétition, il est également nécessaire de vérifier si la balise de base a une valeur de non-correspondance (dans ce cas, la balise fixe doit également être définie sur non-correspondance, ignorant le décalage). Pour les balises dans une concaténation de niveau supérieur, la vérification n'est pas nécessaire, car elles correspondent toujours.

GESTION DE LA FIN DE LA DONNÉE

L'un des principaux problèmes pour le lexer est de savoir quand s'arrêter. Il existe plusieurs conditions de terminaison :

  • le lexer peut correspondre à une règle (y compris la règle par défaut *) et atteindre un état final
  • le lexer peut ne pas correspondre à aucune règle et atteindre un état par défaut
  • le lexer peut atteindre la fin de la donnée

Les deux premières conditions terminent le lexer de manière "naturelle" : il atteint un état sans transitions sortantes, et la correspondance s'arrête automatiquement. La troisième condition, la fin de la donnée, est différente : elle peut se produire dans n'importe quel état, et le lexer doit pouvoir la gérer. La vérification de la fin de la donnée interrompt le flux normal du lexer et ajoute des branches conditionnelles au programme généré, il est donc nécessaire de minimiser le nombre de telles vérifications. re2swift prend en charge plusieurs méthodes pour gérer la fin de la donnée. Laquelle utiliser dépend de la complexité des expressions régulières, du besoin de mise en tampon, des considérations de performance et d'autres facteurs. Voici une liste des méthodes :

  • Sentinelle. Cette méthode élimine le besoin de vérifications de fin de donnée. Elle est simple et efficace, mais limitée au cas où il existe un caractère "sentinelle" naturel qui ne peut jamais se produire dans une donnée valide. Ce caractère peut toujours se produire dans une donnée invalide, mais il ne devrait pas être autorisé par les expressions régulières, sauf peut-être comme dernier caractère d'une règle. La sentinelle est ajoutée à la fin de la donnée et sert de signal d'arrêt : lorsque le lexer lit ce caractère, il s'agit soit d'une erreur de syntaxe, soit de la fin de la donnée. Dans les deux cas, le lexer doit s'arrêter. Cette méthode est utilisée si YYFILL est désactivé avec re2c:yyfill:enable = 0; et que re2c:eof a la valeur par défaut -1.
  • Sentinelle avec vérifications de limites. Cette méthode est générique : elle permet de gérer n'importe quelle donnée sans restrictions sur les expressions régulières. L'idée est de réduire le nombre de vérifications de fin de donnée en les effectuant uniquement sur certains caractères. Similaire à la méthode "sentinelle", l'un des caractères est choisi comme "sentinelle" et ajouté à la fin de la donnée. Cependant, il n'y a aucune restriction quant à l'endroit où la sentinelle peut se produire (en fait, n'importe quel caractère peut être choisi comme sentinelle). Lorsque le lexer lit ce caractère, il effectue en plus une vérification de limites. Si la position actuelle est dans les limites, le lexer reprend la correspondance et traite la sentinelle comme un caractère normal. Sinon, il invoque YYFILL (sauf s'il est désactivé). Si plus de données sont fournies, le lexer réaffectera le dernier caractère et continuera comme si la sentinelle n'y était pas. Sinon, il doit s'agir de la véritable fin de la donnée, et le lexer s'arrête. Cette méthode est utilisée lorsque re2c:eof a une valeur non négative (elle doit être définie à la valeur numérique de la sentinelle). YYFILL est facultatif.
  • Vérifications de limites avec remplissage. Cette méthode est générique et peut être plus rapide que la méthode "sentinelle avec vérifications de limites", mais elle est aussi plus complexe. L'idée est de partitionner les états du DFA en composantes fortement connexes (SCC) et de générer une seule vérification par SCC pour suffisamment de caractères afin de couvrir le chemin non cyclique le plus long dans cette SCC. Cela réduit le nombre de vérifications, mais il y a un problème avec les lexèmes courts en fin de donnée, car la vérification nécessite suffisamment de caractères pour couvrir le lexème le plus long. Cela peut être corrigé en remplissant la donnée avec quelques caractères factices qui ne forment pas un suffixe de lexème valide (de sorte que le lexer ne puisse pas les faire correspondre). La longueur du remplissage doit être YYMAXFILL, générée avec un bloc max. S'il n'y a pas assez de données, le lexer invoque YYFILL qui doit fournir au moins le nombre requis de caractères ou ne pas revenir. Cette méthode est utilisée si YYFILL est activé et que re2c:eof est -1 (c'est la configuration par défaut).
  • Vérifications personnalisées. L'API générique permet de remplacer les opérations de base comme la lecture d'un caractère, ce qui rend possible d'inclure les vérifications de fin de donnée comme partie intégrante de celles-ci. Cette approche est sujette aux erreurs et doit être utilisée avec prudence. Pour utiliser une méthode personnalisée, activez l'API générique avec --api custom ou re2c:api = custom; et désactivez les vérifications de limites par défaut avec re2c:yyfill:enable = 0; ou re2c:yyfill:check = 0;.

BUFFER REFILLING

The need for buffering arises when the input cannot be mapped in memory all at once: either it is too large, or it comes in a streaming fashion (like reading from a socket). The usual technique in such cases is to allocate a fixed-sized memory buffer and process input in chunks that fit into the buffer. When the current chunk is processed, it is moved out and new data is moved in. In practice it is somewhat more complex, because lexer state consists not of a single input position, but a set of interrelated positions:

  • cursor: the next input character to be read (YYCURSOR in C pointer API or YYSKIP/YYPEEK in generic API)
  • limit: the position after the last available input character (YYLIMIT in C pointer API, implicitly handled by YYLESSTHAN in generic API)
  • marker: the position of the most recent match, if any (YYMARKER in default API or YYBACKUP/YYRESTORE in generic API)
  • token: the start of the current lexeme (implicit in re2swift API, as it is not needed for the normal lexer operation and can be defined and updated by the user)
  • context marker: the position of the trailing context (YYCTXMARKER in C pointer API or YYBACKUPCTX/YYRESTORECTX in generic API)
  • tag variables: submatch positions (defined with stags and mtags blocks and generic API primitives YYSTAGP/YYSTAGN/YYMTAGP/YYMTAGN)

Not all these are used in every case, but if used, they must be updated by YYFILL. All active positions are contained in the segment between token and cursor, therefore everything between buffer start and token can be discarded, the segment from token and up to limit should be moved to the beginning of buffer, and the free space at the end of buffer should be filled with new data. In order to avoid frequent YYFILL calls it is best to fill in as many input characters as possible (even though fewer characters might suffice to resume the lexer). The details of YYFILL implementation are slightly different depending on which EOF handling method is used: the case of EOF rule is somewhat simpler than the case of bounds-checking with padding. Also note that if -f --storable-state option is used, YYFILL has slightly different semantics (described in the section about storable state).

Blocs multiples

Il est parfois nécessaire d'avoir plusieurs analyseurs lexicaux interconnectés (par exemple, s'il existe une machine à états de haut niveau qui passe d'un mode d'analyseur à l'autre). Cela peut être implémenté en utilisant plusieurs blocs re2swift connectés. Une autre option consiste à utiliser des conditions de départ.

L'implémentation des connexions entre les blocs dépend du langage cible. Dans les langages qui ont une instruction goto (comme C/C++ et Go), on peut avoir tous les blocs dans une seule fonction, chacun d'eux étant préfixé par une étiquette. La transition d'un bloc à un autre est un simple goto. Dans les langages qui n'ont pas de goto (comme Rust), il est nécessaire d'utiliser une boucle avec un commutateur sur une variable d'état, similaire à la boucle/commutateur yystate générée par re2swift, ou sinon d'encapsuler chaque bloc dans une fonction et d'utiliser des appels de fonction.

  var yycursor = 0, yymarker = 0

    re2c:yyfill:enable = 0;

    "0"                { return parseOct() }

    *                  { return nil }

    let digit = yyinput[yycursor - 1] - UInt8(ascii: charOrigin)
    accum = min(accum * base + UInt64(digit) + offset, UInt64(UInt32.max) + 1)
  }

    var accum: UInt64 = 0
    parse: while true {
      /*!re2c
        [01] { add(&accum, "0", 2); continue parse }
        *    { return UInt32(exactly: accum) }
      */
    }
  }
  func parseOct() -> UInt32? {
    var accum: UInt64 = 0
    parse: while true {
      /*!re2c
        [0-7] { add(&accum, "0", 8); continue parse }
        *     { return UInt32(exactly: accum) }
      */
    }
  }
  func parseDec() -> UInt32? {
    var accum: UInt64 = 0
    parse: while true {
      /*!re2c
        [0-9] { add(&accum, "0", 10); continue parse }
        *     { return UInt32(exactly: accum) }
      */
    }

Les conditions de départ sont activées avec l'option --start-conditions. Elles fournissent un moyen d'encoder plusieurs automates interconnectés au sein du même bloc re2swift.

Chaque condition correspond à un automate unique et possède un nom unique spécifié par l'utilisateur et un numéro interne unique défini par re2swift. Start conditions

Start conditions are used to define different scanning contexts. re2c assigns a number to each start condition and generates a lexer that is capable of switching between them. By default, these numbers are assigned in the order of appearance in the source code. Names for conditions are optional; if a name is not given, re2c uses the condition number as its name. The number of the initial condition is zero.

The condition definitions are given in a block starting with the /*!conditions:re2c directive.

The following rules can be used inside the conditions block:

conditions:re2c
Defines the start condition block. The name after the colon is optional and specifies the name of the condition block if it is not the default one.
<condition> code
Assigns the given code to the specified condition. This code is executed when the scanner enters the condition.
<condition> regular-expression / code
Defines a rule that matches regular-expression and executes the associated code. When the rule is matched, the scanner transitions to the current condition.
<condition> regular-expression :=> condition code
A rule that matches regular-expression, sets the current condition to condition and executes the associated code.
< condition-list > regular-expression :=> condition
A rule that is merged to every condition on the condition-list. It matches regular-expression and immediately transitions to condition (there is no semantic action).
< condition-list > !action code
A rule that binds code to the place defined by action in every condition on the condition-list (see the actions section for various types of actions).
<! condition-list > code
A rule that prepends code to semantic actions of all rules for every condition on the condition-list. This syntax is deprecated and the !pre_rule action should be used instead (it does exactly the same).
< > code
A rule that creates a special entry condition with number zero and name "0" that executes code before jumping to other conditions. This syntax is deprecated, and the !entry action should be used instead (it provides a more fine-grained control, as the code can be specified on a per-condition basis, and one can jump directly to condition start without going through condition dispatch).
< > => condition code
Same as the previous rule, except that it sets the next condition.
< > :=> condition
Same as the previous rule, except that it has no associated code and immediately jumps to condition.

The code re2swift generates for conditions depends on whether re2swift uses goto/label approach or loop/switch approach to encode the automata.

In languages that have goto statement (such as C/C++ and Go) conditions are naturally implemented as blocks of code prefixed with labels of the form yyc_<cond>, where cond is a condition name (label prefix can be changed with re2c:cond:prefix). Transitions between conditions are implemented using goto and condition labels. Before all conditions re2swift generates an initial switch on YYGETSTATE that jumps to the start state of the current condition. The shortcut rules :=> bypass the initial switch and jump directly to the specified condition (re2c:cond:goto can be used to change the default behavior). The rules with semantic actions do not automatically jump to the next condition; this should be done by the user-defined action code.

In languages that do not have goto (such as Rust) re2swift reuses the yystate variable to store condition numbers. Each condition gets a numeric identifier equal to the number of its start state, and a switch between conditions is no different than a switch between DFA states of a single condition. There is no need for a separate initial condition switch. (Since the same approach is used to implement storable states, YYGETCOND/YYSETCOND are redundant if both storable states and conditions are used).

The program below uses start conditions to parse binary, octal, decimal and hexadecimal numbers. There is a single block where each base has its own condition, and the initial condition is connected to all of them. User-defined variable cond stores the current condition number; it is initialized to the number of the initial condition generated with conditions block.

func parseUInt32(_ yyinput: UnsafePointer<UInt8>) -> UInt32? {
  var yycursor = 0, yymarker = 0, yycond = yycinit
  var accum: UInt64 = 0
  loop: while true {
    /*!re2c
      re2c:yyfill:enable = 0;
      <init> '0b' / [01]        :=> bin
      <init> "0"                :=> oct
      <init> "" / [1-9]         :=> dec
      <init> '0x' / [0-9a-fA-F] :=> hex
      <bin> [01]  { add("0", 2);      continue loop }
      <oct> [0-7] { add("0", 8);      continue loop }
      <dec> [0-9] { add("0", 10);     continue loop }
      <hex> [0-9] { add("0", 16);     continue loop }
      <hex> [a-f] { add("a", 16, 10); continue loop }
      <hex> [A-F] { add("A", 16, 10); continue loop }
      <bin, oct, dec, hex> "\x00" { return UInt32(exactly: accum) }
      <*> * { return nil }
    */
  }
  func add(_ charOrigin: UnicodeScalar, _ base: UInt64, _ offset: UInt64 = 0) {
    let digit = yyinput[yycursor - 1] - UInt8(ascii: charOrigin)
    accum = min(accum * base + UInt64(digit) + offset, UInt64(UInt32.max) + 1)
  }

État stockable

Avec l'option --storable-state, re2swift génère un lexer capable de stocker son état courant, de retourner à l'appelant, et plus tard de reprendre les opérations exactement là où il s'est arrêté. Le mode de fonctionnement par défaut dans re2swift est un modèle "pull", dans lequel le lexer "tire" plus d'entrée chaque fois qu'il en a besoin. Cela peut être inacceptable dans les cas où l'entrée devient disponible morceau par morceau (par exemple, si le lexer est invoqué par l'analyseur syntaxique, ou si le programme lexer communique via un protocole de socket avec un autre programme qui doit attendre une réponse du lexer avant de transmettre le message suivant). La fonctionnalité d'état stockable est destinée précisément à ces cas : elle permet de générer des lexers qui fonctionnent selon un modèle "push". Lorsque le lexer a besoin de plus d'entrée, il stocke son état et retourne à l'appelant. Plus tard, lorsque plus d'entrée est disponible, l'appelant reprend le lexer exactement là où il s'est arrêté. Il y a quelques modifications nécessaires par rapport au modèle "pull" :

  • Définir les primitives YYSETSTATE() et YYGETSTATE(state).
  • Définir les variables yych, yyaccept (si utilisé) et state comme faisant partie de l'état persistant du lexer. La variable state doit être initialisée à -1.
  • YYFILL doit retourner au programme externe au lieu d'essayer de fournir plus d'entrée. Le code de retour doit indiquer que le lexer a besoin de plus d'entrée.
  • Le programme externe doit reconnaître les situations où le lexer a besoin de plus d'entrée et y répondre de manière appropriée.
  • Utiliser éventuellement le bloc getstate pour générer le switch YYGETSTATE détaché du lexer principal. Cela ne fonctionne que pour les langages qui ont goto (pas en mode --loop-switch).
  • Utiliser re2c:eof et la méthode du sentinelle avec vérifications de limites pour gérer la fin de l'entrée. La méthode basée sur le remplissage peut ne pas fonctionner car il n'est pas clair quand ajouter le remplissage : la fin actuelle de l'entrée peut ne pas être la fin ultime de l'entrée, et ajouter du remplissage trop tôt peut couper un lexème glouton partiellement lu. De plus, en raison de la logique du programme de haut niveau, obtenir plus d'entrée peut dépendre du traitement du lexème à la fin du tampon (qui est déjà bloqué en raison de la condition de fin d'entrée).

// Nombre illimité de composants de version.
struct Ver: Equatable { let components: [Int] }
func parse(_ yyinput: UnsafePointer<UInt8>) -> Ver? {
  let tagNone = -1
  var yycursor = 0, yymarker = 0
  var mTagPool = [MTag]()
  // Variables de balise finales disponibles dans l'action sémantique.
  /*!svars:re2c format = "  let @@: Int\n"; */
  /*!mvars:re2c format = "  let @@: MTag?\n"; */
  // Variables de balise intermédiaires utilisées par l'analyseur lexical (doivent être générées automatiquement).
  /*!stags:re2c format = "  var @@ = tagNone\n"; */
  /*!mtags:re2c format = "  var @@: MTag? = nil\n"; */
  /*!re2c
    re2c:tags = 1;
    re2c:yyfill:enable = 0;
    re2c:YYSTAGP = "@@ = yycursor";
    re2c:YYSTAGN = "@@ = tagNone";
    re2c:YYMTAGP = "@@ = add(tag: @@, value: yycursor)";
    re2c:YYMTAGN = "@@ = add(tag: @@, value: tagNone)";
    num = [0-9]+;
    @t1 num @t2 ("." #t3 num #t4)* [\x00] {
      var components = [s2n(t1..<t2)]
      unfold(&components, t3, t4)
      return Ver(components: components)
    }
    * { return nil }
  */
  // Déroule récursivement les historiques des balises et collecte les composants de version.
  func unfold(_ ver: inout [Int], _ x: MTag?, _ y: MTag?) {
    if x == nil && y == nil {
      // Atteint la racine de l'arbre de balises m, arrête la récursion.
      return
    }
    // Déroule l'historique davantage.
    unfold(&ver, x?.prev, y?.prev)
    // Récupère les valeurs des balises, les historiques des balises doivent avoir la même longueur.
    guard let ex = x?.elem, let ey = y?.elem else {
      fatalError("longueur d'historique incohérente")
    }
    guard ex != tagNone && ey != tagNone else {
      // Les deux balises sont vides, cela correspond à zéro répétition.
      assert(ex == ey)
      return
    }
    // Les deux balises sont des indices valides, extrait le composant.
    ver.append(s2n(ex..<ey))
  }
  // Chaîne pré-analysée en nombre.
  func s2n(_ range: Range<Int>) -> Int {
    range.reduce(0) { accum, idx in
      accum * 10 + Int(yyinput[idx] - UInt8(ascii: "0"))
    }
  }
  // Ajoute une seule valeur à un historique de balise m.
  func add(tag prevTag: MTag?, value: Int) -> MTag {
    let tag = MTag(prev: prevTag, element: value)
    mTagPool.append(tag)
    return tag
  }
}
// Un arbre de balises m est une façon de stocker des historiques avec une opération de copie O(1).
// Les historiques forment naturellement un arbre, car ils ont un début commun et se divisent à un certain
// point. L'arbre est stocké sous forme de tableau de paires (valeur de balise, lien vers le parent).
// Une balise m est représentée par un seul lien dans l'arbre (index de tableau).
class MTag {
  weak var prev: MTag?  // Lien du nœud précédent ou racine (nil)
  var elem: Int  // Valeur de la balise
  init(prev: MTag?, element: Int) {
    self.prev = prev
    self.elem = element
  }
}
assert(parse("1") == Ver(components: [1]))
assert(parse("1.2.3.4.5.6.7") == Ver(components: [1, 2, 3, 4, 5, 6, 7]))
assert(parse("1.2.") == nil)

Support de l'encodage

Il est nécessaire de comprendre la différence entre les points de code et les unités de code. Un point de code est un identifiant numérique d'un symbole. Une unité de code est la plus petite unité de stockage dans le texte encodé. Un seul point de code peut être représenté par une ou plusieurs unités de code. Dans un encodage à longueur fixe, tous les points de code sont représentés par le même nombre d'unités de code. Dans un encodage à longueur variable, les points de code peuvent être représentés par un nombre différent d'unités de code. Notez que la règle « tout » [^] correspond à n'importe quel point de code, mais pas nécessairement à n'importe quelle unité de code (la seule façon de correspondre à n'importe quelle unité de code, quel que soit l'encodage, est la règle par défaut *). L'analyseur lexical généré fonctionne avec un flux d'unités de code : yych stocke une unité de code, et YYCTYPE est le type de l'unité de code. Les expressions régulières, en revanche, sont spécifiées en termes de points de code. Lorsque re2swift compile des expressions régulières en automates, il traduit les points de code en unités de code. Ce n'est généralement pas une opération simple : dans les encodages à longueur variable, une seule plage de points de code peut être traduite en une expression complexe de code.

graph d'unité. Les encodages suivants sont pris en charge :

  • ASCII (activé par défaut). Il s'agit d'un encodage de longueur fixe avec un espace de code [0-255] et des points de code et unités de code de 1 octet.
  • EBCDIC (activé avec --ebcdic ou re2c:encoding:ebcdic). Il s'agit d'un encodage de longueur fixe avec un espace de code [0-255] et des points de code et unités de code de 1 octet.
  • UCS2 (activé avec --ucs2 ou re2c:encoding:ucs2). Il s'agit d'un encodage de longueur fixe avec un espace de code [0-0xFFFF] et des points de code et unités de code de 2 octets.
  • UTF8 (activé avec --utf8 ou re2c:encoding:utf8). Il s'agit d'un encodage Unicode à longueur variable. La taille de l'unité de code est de 1 octet. Les points de code sont représentés par 1 à 4 unités de code.
  • UTF16 (activé avec --utf16 ou re2c:encoding:utf16). Il s'agit d'un encodage Unicode à longueur variable. La taille de l'unité de code est de 2 octets. Les points de code sont représentés par 1 à 2 unités de code.
  • UTF32 (activé avec --utf32 ou re2c:encoding:utf32). Il s'agit d'un encodage Unicode de longueur fixe avec un espace de code [0-0x10FFFF] et des points de code et unités de code de 4 octets.

Le fichier d'inclusion include/unicode_categories.re fournit les définitions re2swift pour les catégories Unicode standard.

L'option --input-encoding spécifie l'encodage du fichier source, qui peut être utilisé pour activer les littéraux Unicode dans les expressions régulières. Par exemple, --input-encoding utf8 indique à re2swift que le fichier source est en UTF8 (cela diffère de --utf8 qui définit l'encodage du texte d'entrée). L'option --encoding-policy spécifie la manière dont re2swift gère les substituts Unicode (points de code dans la plage [0xD800-0xDFFF]).

Ci-dessous un exemple de lexer pour les identifiants Unicode encodés en UTF8.

// re2swift $INPUT -o $OUTPUT -8 -i
/*!include:re2c "unicode_categories.re" */
func lex(_ yyinput: UnsafePointer<UInt8>) -> Bool {
  var yycursor = 0, yymarker = 0
  /*!re2c
    re2c:yyfill:enable = 0;
    // "Syntaxe simplifiée des identifiants et modèles Unicode"
    // (voir https://unicode.org/reports/tr31)
    id_start    = L | Nl | [$_];
    id_continue = id_start | Mn | Mc | Nd | Pc | [\u200D\u05F3];
    identifier  = id_start id_continue*;
    identifier { return true }
    *          { return false }
  */
}
assert(lex("_Ыдентификатор"))
assert(lex("識別子"))
assert(!lex("+"))

Fichiers d'inclusion

re2swift permet d'inclure d'autres fichiers à l'aide d'un bloc de la forme /*!include:re2c FICHIER */ ou %{include FICHIER %}, ou d'une directive dans le bloc !include FICHIER ;, où FICHIER est un chemin vers le fichier à inclure. re2swift recherche les fichiers d'inclusion dans le répertoire du fichier incluant et dans les emplacements d'inclusion, qui peuvent être spécifiés avec l'option -I. Les blocs/directives d'inclusion dans re2swift fonctionnent de la même manière que #include en C/C++ : le contenu de FICHIER est copié-collé tel quel à la place du bloc/directive. Les fichiers d'inclusion peuvent contenir d'autres inclusions. Utilisez l'option --depfile pour suivre les dépendances de build du fichier de sortie par rapport aux fichiers inclus. re2swift fournit des fichiers d'inclusion prédéfinis que l'on trouve dans le sous-répertoire include/ du projet. Ces fichiers contiennent des définitions qui peuvent être utiles à d'autres projets (telles que les catégories Unicode) et forment une sorte de bibliothèque standard pour re2swift. Ci-dessous un exemple d'utilisation de fichiers d'inclusion.

Fichier d'inclusion 1 (definitions.swift)

enum Result { case ok, fail }
/*!re2c
  number = [1-9][0-9]*;
*/

Fichier d'inclusion 2 (extra_rules.re.inc)

// nombres à virgule flottante
frac  = [0-9]* "." [0-9]+ | [0-9]+ ".";
exp   = 'e' [+-]? [0-9]+;
float = frac exp? | [0-9]+ exp;
float { return .ok }

Fichier d'entrée

// re2swift $INPUT -o $OUTPUT -i
/*!include:re2c "definitions.swift" */
func lex(_ yyinput: UnsafePointer<UInt8>) -> Result {
  var yycursor = 0, yymarker = 0
  /*!re2c
    re2c:yyfill:enable = 0;
    *      { return .fail }
    number { return .ok }
    !include "extra_rules.re.inc";
  */
}
assert(lex("123") == .ok)
assert(lex("123.4567") == .ok)

Fichiers d'en-tête

re2swift permet de générer un fichier d'en-tête à partir du fichier .re d'entrée en utilisant l'option --header ou la configuration re2c:header et des paires de blocs de la forme /*!header:re2c:on*/ et /*!header:re2c:off*/, ou %{header:on%} et %{header:off%}. Le premier bloc marque le début du fichier d'en-tête, et le second bloc marque la fin. Tout ce qui se trouve entre ces blocs est traité par re2swift, et le code généré est écrit dans le fichier spécifié avec l'option --header ou la configuration re2c:header (ou stdout si aucune option ni configuration n'est utilisée). Le fichier d'en-tête auto-généré peut être nécessaire dans les cas où re2swift est utilisé pour générer des définitions qui doivent être visibles depuis d'autres unités de traduction.

Voici un exemple de génération d'un fichier d'en-tête qui contient la définition de l'état du lexer avec des variables de balise (le nombre de variables dépend de la grammaire régulière et est inconnu du programmeur).

Fichier d'entrée

// re2swift $INPUT -o $OUTPUT -i --header lexer/state.swift
/*!header:re2c:on*/

  var yyinput: UnsafePointer<UInt8>
  var yycursor: Int
  /*!stags:re2c format = "var @@ = -1"; */
  init(str: UnsafePointer<UInt8>, cur: Int = 0) {
    self.yyinput = str
    self.yycursor = cur
  }
}
/*!header:re2c:off*/
extension LexerState {
  mutating func lex() -> Int {
  let t: Int
  /*!re2c
    re2c:header        = "lexer/state.swift";
    re2c:api           = record;
    re2c:tags          = 1;
    re2c:yyfill:enable = 0;
    re2c:yyrecord      = "self";
    [a]* @t [b]* { return t }
  */
  }
}
@main struct Program {
  static func main() {
    let str: StaticString = "ab"
    var state = LexerState(str: str.utf8Start)
    assert(state.lex() == 1)
  }
}

Programmes squelettes

Avec l'option -S, --skeleton, re2swift ignore tout code non-re2swift et génère un programme C autonome qui peut être compilé et exécuté. Le programme se compose du code du lexer et des données d'entrée. Pour chaque DFA construit (bloc ou condition), re2swift génère un lexer autonome et deux fichiers : un fichier .input contenant des chaînes dérivées du DFA et un fichier .keys contenant les résultats de correspondance attendus. Le programme exécute chaque lexer sur le fichier .input correspondant et compare les résultats avec les attentes. Les programmes squelettes sont très utiles pour plusieurs raisons :

  • Ils peuvent vérifier l'exactitude de diverses optimisations re2swift (les données sont générées tôt dans le processus, avant toute transformation du DFA).
  • La génération d'un ensemble de données d'entrée avec une bonne couverture peut être utile pour les tests et le benchmarking.
  • La génération de programmes exécutables autonomes permet d'obtenir des cas de test minimisés (le code d'origine peut être volumineux ou avoir beaucoup de dépendances).

La difficulté de générer des données d'entrée est que, sauf dans les cas les plus triviaux, le nombre de chaînes d'entrée possibles est trop grand (même si la longueur de la chaîne est limitée). re2swift résout cette difficulté en générant suffisamment de chaînes pour couvrir presque toutes les transitions du DFA. Il utilise l'algorithme suivant. Premièrement, il construit un squelette du DFA. Pour les encodages avec une taille d'unité de code de 1 octet (tels que ASCII, UTF-8 et EBCDIC), le squelette est simplement une copie exacte du DFA d'origine. Pour les encodages avec des unités de code multiblocs, le squelette est une copie du DFA avec certaines transitions omises : à savoir, re2swift prend au maximum 256 unités de code pour chaque plage continue disjointes qui correspond à une transition de DFA. Les valeurs choisies sont réparties uniformément et incluent les limites de plage. Au lieu d'essayer de couvrir tous les chemins possibles dans le squelette (ce qui est infaisable), re2swift génère suffisamment de chemins pour couvrir toutes les transitions du squelette, et donc déclencher les sauts conditionnels correspondants dans le lexer. L'implémentation de l'algorithme est limitée à environ 1 Go de transitions et consomme une quantité constante de mémoire (re2swift écrit les données dans le fichier dès qu'elles sont générées).

Visualisation et débogage

Avec l'option -D, --emit-dot, re2swift ne génère pas de code. Au lieu de cela, il vide le DFA généré au format DOT. On peut convertir ce vidage en une image du DFA à l'aide de Graphviz ou d'une autre bibliothèque. Notez que cette option affiche le DFA final après qu'il ait subi un certain nombre d'optimisations et de transformations. Les étapes antérieures peuvent être vidées à l'aide de diverses options de débogage, telles que --dump-nfa, --dump-dfa-raw, etc. (voir la liste complète des options).
