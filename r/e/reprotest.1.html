Paquet: reprotest

REPROTEST(1) Commandes utilisateur REPROTEST(1)

NOM

reprotest - Construire des paquets et vérifier leur reproductibilité.

SYNTAXE

reprotest --help [<nom_serveur_virtuel>]
reprotest [options] [-c <commande_construction>] <racine_source> [<motif_artefact>] [-- <args_serveur_virtuel> [<args_serveur_virtuel> ...]]
reprotest [options] [-s <racine_source>] <commande_construction> [<motif_artefact>] [-- <args_serveur_virtuel> [<args_serveur_virtuel> ...]]

""

DESCRIPTION

reprotest construit le même code source deux fois dans des environnements différents, puis vérifie les binaires produits par chaque construction pour des différences. Si des différences sont trouvées, alors diffoscope(1) (ou si indisponible alors diff(1)) est utilisé pour les afficher en détail pour une analyse ultérieure.

Voir la section EXEMPLES DE LIGNE DE COMMANDE plus bas pour commencer, ainsi que des explications plus détaillées de toutes les options de ligne de commande. Les mêmes informations sont également disponibles dans /usr/share/doc/reprotest/README.rst ou similaire.

racine_source|commande_construction
Le premier argument est traité soit comme une racine_source (voir l'option -s) soit comme une commande_construction (voir l'option -c) selon son apparence. La plupart du temps, cela devrait fonctionner ; mais spécifiquement : si ni -c ni -s ne sont donnés, alors : si ceci existe comme fichier ou répertoire et n'est pas "auto", alors ceci est traité comme une racine_source, sinon comme une commande_construction. Sinon, si l'une des options -c ou -s est donnée, alors ceci est traité comme l'autre. Si les deux sont données, alors c'est une erreur de syntaxe et nous sortons avec le code 2.
motif_artefact
Artefact de construction à tester pour la reproductibilité. Peut être un motif shell tel que "*.deb *.changes".
args_serveur_virtuel
Arguments à passer au serveur_virtuel, le premier argument étant le nom du serveur. Si celui-ci contient lui-même des options (de la forme -xxx ou --xxx), ou si l'un des arguments précédents est omis, vous devriez mettre un "--" entre ces arguments et les propres options de reprotest. Défaut : "null", pour exécuter directement dans /tmp. Choix : chroot, lxc, lxd, null, qemu, schroot, ssh

options :

--help [NOM_SERVEUR_VIRTUEL]
Affiche ce message d'aide et quitte. Lorsqu'un argument est donné, affiche à la place le message d'aide pour ce serveur virtuel et quitte.
-f, --fichier-config FICHIER_CONFIG
Fichier à partir duquel charger la configuration. (Défaut : Aucun)

options de base :

--verbeux VERBEUX
Un entier. Contrôle quels messages sont affichés (0 : silencieux (avertissement/erreur seulement), 1 : informations, 2 : débogage).
-v, --verbose
Comme --verbeux, mais donné plusieurs fois sans arguments.
--hote-distro DISTRO_HOTE
La distribution qui exécutera les tests (Défaut : Aucun)
-s, --racine-source CHEMIN
Racine de l'arborescence source, qui est copiée vers le serveur virtuel et rendue disponible pendant la construction. Si un fichier est donné ici, son répertoire parent est utilisé à la place. Défaut : "." (répertoire de travail courant).
--motif-source MOTIFS
Motif de glob shell pour restreindre les fichiers dans <racine_source> qui sont rendus disponibles pendant la construction. Défaut : vide, c.-à-d. copier tout le répertoire <racine_source> sans restrictions.
-c, --commande-construction COMMANDES
Commande de construction à exécuter. Si c'est "auto", alors reprotest essaiera de deviner comment construire la racine_source donnée, auquel cas diverses autres options peuvent être automatiquement définies si elles ne le sont pas. Défaut : auto
--dir-sauvegarde RÉPERTOIRE
Sauvegarder les artefacts dans ce répertoire, qui doit être vide ou inexistant. Sinon, les artefacts seront supprimés et vous ne verrez que leurs hachages (s'ils sont reproductibles) ou la sortie de diff (s'ils ne le sont pas). Voir aussi --pas-nettoyer-en-cas-d-erreur.
--variations VARIATIONS
Variations de construction à tester sous forme de liste de noms de variations séparés par des virgules. Le défaut est "+tout", équivalent à "+environnement, +chemin_construction, +noyau, +aslr, +nb_cpus, +temps, +utilisateur_groupe, +ordonnancement_fichiers, +hote_domaine, +home, +locales, +chemin_exec, +fuseau_horaire, +umask", testant toutes les variations disponibles. Voir la page de manuel sur VARIATIONS pour des options de syntaxe plus avancées, y compris le réglage du fonctionnement de certaines variations.
--varier VARIATIONS
Comme --variations, mais ajoute aux valeurs --varier précédentes au lieu de les écraser. La dernière valeur définie pour --variations est traitée implicitement comme la première valeur --varier.
--construction-extra VARIATIONS
Effectuer une autre construction avec les VARIATIONS données (qui peuvent être vides) à appliquer en plus de ce qui a été donné pour --variations et --varier. Chaque occurrence de ce drapeau spécifie une autre construction, donc par exemple donné deux fois cela fera effectuer 4 constructions par reprotest au total.
--auto-construction
Effectuer automatiquement des constructions pour essayer de déterminer quelles variations spécifiques provoquent l'irréproductibilité, potentiellement jusqu'à celles spécifiées par --variations et --varier. Conflits avec --construction-extra.
--construction-env
Effectuer automatiquement des constructions pour essayer de déterminer quelles variables d'environnement spécifiques provoquent l'irréproductibilité, basé sur une liste blanche et une liste noire codées en dur. Vous voudrez probablement définir également --varier=-tout lorsque vous définissez ce drapeau ; voir la page de manuel pour les détails. Conflits avec --construction-extra et --autobuild.
--min-cpus NB
Nombre minimum de CPU à utiliser lors de la fixation de num_cpus. Défaut : 1.

options de diff :

--diffoscope-arg ARG
Donner des arguments supplémentaires à diffoscope lors de son exécution. Défaut : ['--exclure-metadonnees-repertoire=oui']. Les arguments sont formatés en {}- avec {0} le nom de chaque expérience exécutée, et {1} le chemin de la sortie de l'expérience.
--diffoscope CHEMIN
Chemin vers diffoscope(1). Défaut : diffoscope
--pas-diffoscope
Ne pas exécuter diffoscope ; exécuter diff(1) à la place. Utile si vous ne voulez pas installer diffoscope et/ou si vous voulez juste une réponse rapide sur la réussite ou l'échec de la reproduction, sans passer de temps à calculer toutes les différences détaillées.

options avancées :

--testbed-pre COMMANDES
Commandes shell à exécuter avant de démarrer le banc d'essai, dans le contexte de l'environnement système actuel. Ceci peut être utilisé pour, par exemple, calculer des informations nécessaires à la construction, où le calcul nécessite des paquets que vous ne voulez pas installer dans le banc d'essai lui-même.
--testbed-init COMMANDES
Commandes shell à exécuter après le démarrage du banc d'essai, avant d'exécuter quoi que ce soit d'autre. Utilisé pour, par exemple, installer disorderfs dans un chroot.
--testbed-construction-pre COMMANDES
Commandes shell à exécuter avant chaque construction, même avant d'appliquer les variations pour cette construction. Utilisé pour, par exemple, installer les dépendances de construction.

EXEMPLES DE LIGNE DE COMMANDE

La manière la plus simple d'exécuter reprotest est via nos préréglages :

# Construire le répertoire courant dans un serveur nul (/tmp)
$ reprotest .
$ reprotest . -vv -- null -d # pour une sortie très verbeuse
# Construire un programme basé sur make
$ reprotest "make clean && make" monexecutable
# Construire un paquet Debian
$ apt-get source hello && cd hello-2.10
$ reprotest  auto -- null
# Construire un paquet Debian et désactiver certaines variations
$ reprotest --vary=-user_group,-domain_host,-fileordering auto -- null
# Construire le paquet source Debian donné dans un schroot
# Voir https://wiki.debian.org/sbuild pour les instructions de configuration.
$ reprotest reprotest_0.3.3.dsc -- schroot unstable-amd64-sbuild
# Construire le paquet source RPM donné
# Seul le serveur nul (/tmp) est actuellement supporté.
$ reprotest reprotest-0.7.16.src.rpm
# Construire le paquet source RPM donné et installer automatiquement les dépendances
$ reprotest --testbed-build-pre 'dnf -y builddep ./*.src.rpm' reprotest-0.7.16.src.rpm

Actuellement, nous ne prenons en charge que les paquets basés sur Debian et RPM, mais nous sommes désireux d'en ajouter d'autres. Si nous n'avons pas les connaissances nécessaires pour construire votre fichier ou répertoire, vous pouvez nous envoyer un patch ajoutant cette intelligence - consultez le module python reprotest.presets et adaptez la logique existante.

En attendant, vous pouvez utiliser d'autres parties de l'interface en ligne de commande pour construire des éléments arbitraires. Vous devrez fournir deux arguments obligatoires, la commande de build à exécuter et le fichier/motif de l'artefact de build à tester après l'exécution de la commande. Par exemple :

$ reprotest 'python3 setup.py bdist' 'dist/*.tar.gz'

Cela exécute la commande sur ., le répertoire de travail courant. Pour l'exécuter sur un projet situé ailleurs :

$ reprotest -s ../chemin/vers/autre/projet 'python3 setup.py bdist' 'dist/*.tar.gz'
$ reprotest -c 'python3 setup.py bdist' ../chemin/vers/autre/projet 'dist/*.tar.gz'

Ces deux invocations sont équivalentes ; vous pouvez choisir celle qui convient le mieux à votre cas d'utilisation. Lorsque vous les utilisez depuis un shell :

  • Si la commande de build contient des espaces, vous devrez les mettre entre guillemets, par exemple reprotest "dpkg-buildpackage -b --no-sign" [..].
  • Si vous souhaitez utiliser plusieurs motifs d'artefacts de build, ou si vous souhaitez utiliser des jokers de shell comme motif, vous devrez également les mettre entre guillemets, par exemple reprotest [..] "*.tar.gz *.tar.xz".
  • Si vos artefacts de build ont des espaces dans leurs noms, vous devrez les mettre entre guillemets deux fois, par exemple '"un fichier avec des espaces.gz"' pour un seul artefact ou '"dir 1"/* "dir 2"/*' pour plusieurs motifs.

Pour obtenir plus d'aide sur l'interface en ligne de commande, y compris la documentation sur les arguments optionnels et leur fonction, exécutez :

$ reprotest --help

EXÉCUTION DANS UN SERVEUR VIRTUEL

Vous pouvez également exécuter le build à l'intérieur de ce que l'on appelle un "serveur virtuel". Il peut s'agir d'un conteneur, d'un chroot, etc. Vous les exécutez comme suit :

$ reprotest 'python3 setup.py bdist_wheel'   'dist/*.whl' -- qemu    /chemin/vers/qemu.img
$ reprotest 'dpkg-buildpackage -b --no-sign' '../*.deb'   -- schroot unstable-amd64

Il existe différents types de serveurs disponibles. Consultez --help pour en obtenir la liste, qui apparaît en haut, dans la partie "virtual_server_args" de la section "positional arguments".

Pour chaque serveur virtuel (par exemple, "schroot"), vous verrez les arguments supplémentaires qu'il prend en charge :

$ reprotest --help schroot

Lors de l'exécution de builds dans un serveur virtuel, vous devrez probablement fournir des commandes supplémentaires pour configurer vos dépendances de build à l'intérieur du serveur virtuel. Par exemple, pour vous montrer à quoi ressemblerait le préréglage "Répertoire Debian" si nous l'exécutions en utilisant l'interface en ligne de commande complète :

# Préréglage "Répertoire Debian"
$ reprotest . -- schroot unstable-amd64-sbuild
# Ceci est exactement équivalent à ceci :
$ reprotest -c auto . -- schroot unstable-amd64-sbuild
# Dans l'interface en ligne de commande complète sans préréglage, ceci est à peu près similaire à :
$ reprotest \
    --testbed-init 'apt-get -y --no-install-recommends install \
                    disorderfs faketime locales-all sudo util-linux; \
                    test -c /dev/fuse || mknod -m 666 /dev/fuse c 10 229; \
                    test -f /etc/mtab || ln -s ../proc/self/mounts /etc/mtab' \
    --testbed-build-pre 'apt-get -y --no-install-recommends build-dep ./' \
    --build-command 'dpkg-buildpackage --no-sign -b' \
    . \
    '../*.deb' \
    -- \
    schroot unstable-amd64-sbuild

L'argument --testbed-init est nécessaire pour configurer les outils de base dont reprotest a besoin pour créer les variations en premier lieu. Cela devrait être le même indépendamment du paquet en cours de construction, mais pourrait différer en fonction du virtual_server utilisé.

Ensuite, nous avons --testbed-build-pre, puis --build-command (ou -c). Pour notre répertoire Debian, nous installons les dépendances de build en utilisant apt-get, puis nous exécutons la commande de build réelle elle-même en utilisant dpkg-buildpackage(1).

Ensuite, nous avons le source_root et le artifact_pattern. Pour la reproductibilité, nous ne nous intéressons qu'aux paquets binaires.

Enfin, nous spécifions que cela doit avoir lieu dans le serveur virtuel "schroot" avec les arguments "unstable-amd64-sbuild".

Bien sûr, tout cela est fastidieux à retenir si vous devez exécuter la même chose plusieurs fois. C'est pourquoi l'ajout de nouveaux préréglages pour de nouveaux types de paquets serait une bonne chose.

Voici un exemple plus complexe. Il indique à reprotest de stocker les produits de build dans ./artifacts pour une analyse ultérieure ; et ajuste également le préréglage "Dsc Debian" afin qu'il utilise notre outillage expérimental https://wiki.debian.org/ReproducibleBuilds/ExperimentalToolchain :

$ reprotest --store-dir=artifacts \
    --auto-preset-expr '_.prepend.testbed_init("apt-get install -y wget; \
        echo deb http://reproducible.alioth.debian.org/debian/ ./ >> /etc/apt/sources.list; \
        wget -q -O- https://reproducible.alioth.debian.org/reproducible.asc | apt-key add -; \
        apt-get update; apt-get upgrade -y; ")' \
    ./bash_4.4-4.0~reproducible1.dsc \
    -- \
    schroot unstable-amd64-sbuild

Alternativement, vous pouvez cloner votre chroot unstable-amd64-sbuild, ajouter notre dépôt au chroot cloné, puis utiliser ce chroot à la place de "unstable-amd64-sbuild". Cela vous permettrait d'omettre le long flag --auto-preset-expr ci-dessus.

FICHIER DE CONFIGURATION

Vous pouvez également passer des options à reprotest via un fichier de configuration. C'est une mesure d'économie de temps similaire aux préréglages auto ; la différence est qu'ils sont plus adaptés aux builds locaux qui conviennent à vos objectifs personnels. (Vous pouvez utiliser à la fois les préréglages et les fichiers de configuration dans le même build.)

Le fichier de configuration prend exactement les mêmes options que l'interface en ligne de commande, mais avec la restriction supplémentaire que le nom de la section doit correspondre à ceux donnés dans l'aide. Les espaces sont autorisés si et seulement si la même option de ligne de commande autorise les espaces. Enfin, il n'est pas possible de passer d'arguments positionnels via ce mécanisme.

Reprotest, par défaut, ne charge aucun fichier de configuration. Vous pouvez lui dire d'en charger un avec les options de ligne de commande --config-file ou -f. Si vous lui donnez un répertoire tel que ., il chargera .reprotestrc dans ce répertoire.

Un exemple de fichier de configuration est ci-dessous :

[basics]
verbosity = 1
variations =
  environment
  build_path
  user_group.available+=builduser:builduser
  fileordering
  home
  kernel
  locales
  exec_path
  time
  timezone
  umask
store_dir =
  /home/foo/build/reprotest-artifacts
[diff]
diffoscope_arg =
  --debug

ANALYSE DE LA SORTIE DE DIFF

Normalement, lorsque diffoscope compare des répertoires, il compare également les métadonnées des fichiers dans ces répertoires - permissions, propriétaires, etc.

Cependant, selon les circonstances, ces métadonnées au niveau du système de fichiers peuvent ou non être destinées à être distribuées à d'autres systèmes. Par exemple : (1) pour la plupart des constructeurs de paquets des distributions, nous ne nous soucions pas des métadonnées des fichiers de sortie du paquet ; seuls les contenus des fichiers seront distribués à d'autres systèmes. D'un autre côté, (2) lors de l'exécution de quelque chose comme make install, nous nous soucions des métadonnées, car c'est ce qui sera recréé sur un autre système.

Dans le développement de reprotest, notre expérience a été que le cas (1) est plus courant et nous passons donc --exclude-directory-metadata=yes par défaut à diffoscope. Si vous utilisez reprotest pour le cas (2), vous devriez passer --diffoscope-args=--exclu de-directory-metadata=no pour reprotest, pour indiquer à diffoscope de ne pas ignorer les métadonnées puisqu'elles seront distribuées et devraient donc être reproductibles. Sinon, vous pourriez obtenir un résultat faux positif.

VARIATIONS

Les options --vary et --variations, dans leurs formes simples, sont une liste d'ordres de variation séparés par des virgules qui indiquent quelles variations appliquer. La liste complète des noms est donnée dans le texte --help pour --variations.

En détail, les options sont une liste d'actions séparées par des virgules, comme suit :
+$variation (ou $variation sans opérateur explicite)
-$variation
Activer ou désactiver une variation
@$variation
Activer une variation, en réinitialisant ses paramètres (voir ci-dessous) aux valeurs par défaut.
$variation.$param=$valeur
$variation.$param+=$valeur
$variation.$param-=$valeur
Définir/ajouter/supprimer $valeur comme/à/depuis la valeur actuelle du paramètre $param
de la $variation.
$variation.$param++
$variation.$param--
Incrémenter/décrémenter la valeur du paramètre $param de la $variation.

La plupart des variations n'ont pas de paramètres, et pour celles-ci, seuls les opérateurs + et - sont pertinents. Les variations qui acceptent des paramètres sont :

build_path.path
Le chemin à utiliser pour les compilations d'expérimentation lorsque les variations de chemin de compilation sont activées. Il doit se trouver dans un emplacement accessible en écriture par l'utilisateur utilisé pour exécuter la compilation. Ceci est (ironiquement) utile pour normaliser le chemin de compilation lorsqu'il est utilisé conjointement avec --control-build pour comparer avec une compilation existante non effectuée avec reprotest.
domain_host.use_sudo
Un entier, pour indiquer s'il faut utiliser sudo(1) avec unshare(1) pour modifier le nom d'hôte et le nom de domaine du système. 0 signifie ne pas utiliser sudo ; toute valeur non nulle signifie utiliser sudo. La valeur par défaut est 0, cependant ce n'est pas recommandé et peut faire échouer votre compilation, voir "Variation des noms de domaine et d'hôte" pour plus de détails.
environment.variables
Un ensemble ordonné, séparé par des points-virgules, spécifiant les variables d'environnement que reprotest doit essayer de faire varier. La valeur par défaut est "REPROTEST_CAPTURE_ENVIRONMENT". Prend en charge la syntaxe basée sur les expressions régulières, par exemple.
  • PID=\d{1,6}
  • HOME=(/\w{3,12}){1,4}
  • (GO|PYTHON|)PATH=(/\w{3,12}){1,4}(:(/\w{3,12}){1,4}){0,4}

Cas spéciaux :

  • $VARNAME= (RHS vide) pour indiquer à reprotest de supprimer la variable
  • $VARNAME=.{0} pour indiquer à reprotest de définir réellement une valeur vide
  • \x2c et \x3b pour correspondre ou générer , et ; respectivement.
user_group.available
Un ensemble ordonné, séparé par des points-virgules, spécifiant les combinaisons utilisateur+groupe disponibles que reprotest peut utiliser avec sudo(1). La valeur par défaut est vide, auquel cas la variation est une opération nulle et vous verrez un avertissement à ce sujet. Chaque utilisateur+groupe doit être donné sous la forme $utilisateur:$groupe où l'un des composants peut être omis, ou sinon s'il n'y a pas de deux-points, il est interprété comme seulement un $utilisateur, sans variation de $groupe.
time.faketimes
Un ensemble ordonné, séparé par des points-virgules, spécifiant les descripteurs de temps possibles de faketime(1) à utiliser. La valeur par défaut est vide, auquel cas nous choisissons une heure : soit maintenant (si la dernière heure de modification de fichier dans source_root est plus ancienne que 398 jours) soit plus de 398 jours dans le futur.

Notez que l'horloge continue de fonctionner pendant la compilation. Il est possible que faketime(1) la freeze, mais nous ne le supportons pas encore ; cela augmente la probabilité que votre compilation échoue ou se comporte mal.

locales.locale
Une liste séparée par des points-virgules d'une ou plusieurs locales à tester lors de l'exécution des variations de locales. Si plusieurs locales sont spécifiées, une sera choisie au hasard. Les locales avec des propriétés différentes de en_US.UTF-8 sont fr_CH.UTF-8, ru_RU.CP1251, kk_KZ.RK1048 ou zh_CN. La valeur par défaut est et_EE.UTF-8 si non spécifiée.
num_cpus.cpus
Une liste séparée par des points-virgules d'une ou plusieurs valeurs numériques pour sélectionner le nombre de cpus utilisés lors de l'exécution des variations de num_cpus.

La différence entre --vary et --variations est que le premier ajoute aux valeurs précédentes tandis que le second les réinitialise. De plus, la dernière valeur définie pour --variations est traitée comme le n-ième argument --vary. Par exemple :

reprotest --vary=-user_group

signifie varier +all (la valeur par défaut pour --variations) et -user_group (la valeur donnée pour --vary), tandis que :

reprotest --variations=-all,locales --variations=home,time --vary=timezone --vary=-time

signifie varier home, time (la dernière valeur donnée pour --variations), timezone, et -time (les multiples valeurs données pour --vary), c'est-à-dire home et timezone.

NOTES SUR LES VARIATIONS

reprotest s'efforce d'effectuer des variations sans supposer qu'il a un accès root complet au système. Il suppose également que d'autres logiciels peuvent s'exécuter sur le même système, il n'effectue donc pas de modifications au niveau du système qui affecteraient d'autres processus. En raison de ces hypothèses, certaines variations sont implémentées à l'aide de hacks de différents niveaux de saleté, qui sont documentés ci-dessous.

Nous espérons lever ces hypothèses pour certains contextes virtual_server à l'avenir. Cela permettrait probablement un fonctionnement plus fluide dans ces contextes. Les hypothèses resteront pour le contexte "null" (par défaut) virtual_server cependant.

Nombre de CPUs

La compilation de contrôle n'utilise qu'un seul CPU afin d'essayer de réduire l'indéterminisme qui pourrait exister en raison du multithreading ou du multiprocessing. Si vous êtes sûr que votre compilation n'est pas affectée par cela (et les bonnes compilations ne devraient pas l'être), vous pouvez spécifier --min-cpus=99999 pour utiliser tous les cœurs disponibles pour les deux compilations.

Domaine ou hôte

Faire cela sans sudo *peut* entraîner l'échec de votre compilation.

L'échec est probable si votre compilation doit effectuer des opérations liées au système - par opposition au simple traitement de bits et d'octets. C'est parce qu'elle s'exécute dans un espace de noms séparé où votre utilisateur non privilégié ressemble à "root", mais cela empêche le système de fichiers de reconnaître les fichiers appartenant au véritable utilisateur "root", entre autres choses. C'est une limitation de unshare(1) et il n'est pas possible de contourner cela dans reprotest sans efforts importants.

Par conséquent, il est recommandé d'exécuter cette variation avec use_sudo=1. Pour éviter les invites de mot de passe, voir la section "Éviter les invites de mot de passe sudo(1)" ci-dessous.

Lors de l'exécution dans un serveur virtuel :

La méthode sans sudo échoue avec "Operation not permitted", même si vous avez modifié /proc/sys/kernel/unprivileged_userns_clone. La cause est actuellement inconnue.

La méthode sudo ne fonctionne que si vous prenez des mesures pour éviter les invites de mot de passe sudo, car les conteneurs n'ont pas de méthode pour les saisir.

Utilisateur ou groupe

Si vous faites également varier l'ordre des fichiers en même temps (ce qui est le cas par défaut), chaque utilisateur que vous utilisez doit appartenir au groupe "fuse". Faites-le en exécutant usermod -aG fuse $AUTREUTILISATEUR en tant que root.

Pour éviter les invites de mot de passe sudo(1), voir la section "Éviter les invites de mot de passe sudo(1)" ci-dessous.

Temps

La variation "time" utilise faketime(1) qui cause *parfois* des problèmes étranges et difficiles à diagnostiquer. Par le passé, cela incluait :

  • des compilations prenant un temps infini ; bien que cela devrait être corrigé dans les versions récentes de reprotest.
  • des compilations avec des différences invraisemblablement énormes causées par des scripts ./configure produisant des résultats différents avec et sans faketime. Cela affecte toujours bash et probablement certains autres packages utilisant autotools.
  • des compilations accédant au réseau échouant en raison d'erreurs d'expiration de certificat et/ou d'autres erreurs de sécurité liées au temps. (Les compilations transparentes de FOSS ne devraient pas accéder au réseau en premier lieu, mais il est hors de portée de reprotest de vérifier ou d'empêcher cela.)

Si vous constatez une différence qui, selon vous, ne devrait pas exister, essayez de passer --variations=-time à reprotest, et/ou vérifiez nos résultats sur https://tests.reproducible-builds.org/ qui utilisent un mécanisme différent (plus fiable) pour faire varier l'heure du système.

Noyau

La variation "kernel" ne fonctionne actuellement pas pour les packages basés sur RPM et d'autres processus de compilation nécessitant ldconfig. Lors de la compilation avec cette variation activée, ldconfig se plaint de FATAL: kernel too old et abandonne la compilation.

ÉVITER LES INVITES DE MOT DE PASSE SUDO(1)

Il n'y a actuellement aucun bon moyen de le faire. Ce qui suit est une solution EXPÉRIMENTALE, instable et peu propre. Vous devrez décider vous-même si cela en vaut la peine pour votre cas d'utilisation :

$ reprotest --print-sudoers \
    --variations=user_group.available+=guest-builder,domain_host.use_sudo=1 \
    | sudo EDITOR=tee visudo -f /etc/sudoers.d/local-reprotest

Assurez-vous de définir les variations que vous souhaitez réellement utiliser. Évidemment, ne choisissez pas d'utilisateurs privilégiés à cette fin, comme root.

(Simplifier la sortie à l'aide de caractères génériques ouvrirait l'accès sans mot de passe pour chown n'importe quoi sur votre système, car les caractères génériques correspondent ici aux espaces blancs. Je ne sais pas ce que les auteurs de sudo pensaient.)

Non, ce n'est pas du tout agréable - suggestions et correctifs bienvenus.

Si vous souhaitez utiliser cela dans un serveur virtuel tel qu'un chroot, vous devrez copier (ou monter ou mapper autrement) le résultat

reprotest(1) — Arch manual pages

AVOID SUDO(1) PASSWORD PROMPTS

In order to run reprotest with root privileges within a chroot (e.g. schroot(1)), you will need to configure sudo(8) to allow this.

It is possible to make reprotest run without password prompts from sudo by configuring the sudoers file. The recommended method is to use the /etc/sudoers.d directory.

The simplest way to achieve this is to add a file /etc/sudoers.d/local-reprotest into your chroot.

For example, for an schroot, you should (1) login to the source schroot and create an empty file /etc/sudoers.d/local-reprotest (this is important) and then (2) add the line:

/etc/sudoers.d/local-reprotest /etc/sudoers.d/local-reprotest none bind 0 0

to your schroot's fstab.
