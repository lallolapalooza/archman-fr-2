rename(2) Manuel des appels système rename(2)

NOM

rename, renameat, renameat2 - changer le nom ou l'emplacement d'un fichier

BIBLIOTHÈQUE

Bibliothèque C standard (libc, -lc)

SYNTAXE

#include <stdio.h>
int rename(const char *oldpath, const char *newpath);
#include <fcntl.h>           /* Définition des constantes AT_* */
#include <stdio.h>
int renameat(int olddirfd, const char *oldpath,
             int newdirfd, const char *newpath);
int renameat2(int olddirfd, const char *oldpath,
             int newdirfd, const char *newpath, unsigned int flags);
Besoins en macros de test de fonctionnalités pour glibc (voir feature_test_macros(7)):
renameat():
    Depuis glibc 2.10 :
        _POSIX_C_SOURCE >= 200809L
    Avant glibc 2.10 :
        _ATFILE_SOURCE
renameat2():

DESCRIPTION

rename() renomme un fichier, le déplaçant entre répertoires si nécessaire. Tous les autres liens physiques vers le fichier (créés avec link(2)) ne sont pas affectés. Les descripteurs de fichiers ouverts pour oldpath ne sont pas non plus affectés.

Diverses restrictions déterminent si l'opération de renommage réussit ou non : voir ERREURS ci-dessous.

Si newpath existe déjà, il sera atomiquement remplacé, de sorte qu'aucun autre processus tentant d'accéder à newpath ne le trouvera manquant. Cependant, il y aura probablement une fenêtre pendant laquelle oldpath et newpath feront référence au fichier en cours de renommage.

Si oldpath et newpath sont des liens physiques existants faisant référence au même fichier, alors rename() ne fait rien et renvoie un statut de succès.

Si newpath existe mais que l'opération échoue pour une raison quelconque, rename() garantit de laisser une instance de newpath en place.

oldpath peut spécifier un répertoire. Dans ce cas, newpath doit soit n'exister pas, soit spécifier un répertoire vide.

Si oldpath fait référence à un lien symbolique, le lien est renommé ; si newpath fait référence à un lien symbolique, le lien sera écrasé.

renameat()

L'appel système renameat() fonctionne exactement de la même manière que rename(), sauf pour les différences décrites ici.

Si le chemin spécifié dans oldpath est relatif, il est interprété par rapport au répertoire référencé par le descripteur de fichier olddirfd (plutôt que par rapport au répertoire de travail actuel du processus appelant, comme le fait rename() pour un chemin relatif).

Si oldpath est relatif et olddirfd est la valeur spéciale AT_FDCWD, alors oldpath est interprété par rapport au répertoire de travail actuel du processus appelant (comme rename()).

Si oldpath est absolu, alors olddirfd est ignoré.

L'interprétation de newpath est la même que pour oldpath, sauf qu'un chemin relatif est interprété par rapport au répertoire référencé par le descripteur de fichier newdirfd.

Voir openat(2) pour une explication de la nécessité de renameat().

renameat2()

renameat2() a un argument flags supplémentaire. Un appel à renameat2() avec un argument flags à zéro est équivalent à renameat().

L'argument flags est un masque de bits constitué de zéro ou plusieurs des indicateurs suivants :

RENAME_EXCHANGE
Échange atomiquement oldpath et newpath. Les deux chemins doivent exister mais peuvent être de types différents (par exemple, l'un peut être un répertoire non vide et l'autre un lien symbolique).
RENAME_NOREPLACE
N'écrase pas newpath lors du renommage. Renvoie une erreur si newpath existe déjà.
RENAME_NOREPLACE ne peut pas être utilisé conjointement avec RENAME_EXCHANGE.
RENAME_NOREPLACE nécessite le support du système de fichiers sous-jacent. Le support pour divers systèmes de fichiers a été ajouté comme suit :
•
ext4 (Linux 3.15) ;
•
btrfs, tmpfs et cifs (Linux 3.17) ;
•
xfs (Linux 4.0) ;
•
Le support pour de nombreux autres systèmes de fichiers a été ajouté dans Linux 4.9, y compris ext2, minix, reiserfs, jfs, vfat et bpf.
RENAME_WHITEOUT (depuis Linux 3.18)
Cette opération n'a de sens que pour les implémentations de systèmes de fichiers overlay/union.
Spécifier RENAME_WHITEOUT crée un objet "whiteout" à la source du renommage en même temps qu'il effectue le renommage. Toute l'opération est atomique, de sorte que si le renommage réussit, le whiteout aura également été créé.
Un "whiteout" est un objet qui a une signification spéciale dans les constructions de systèmes de fichiers union/overlay. Dans ces constructions, plusieurs couches existent et seule la supérieure est jamais modifiée. Un whiteout sur une couche supérieure masquera efficacement un fichier correspondant dans la couche inférieure, donnant l'impression que le fichier n'existe pas.
Lorsqu'un fichier qui existe dans la couche inférieure est renommé, le fichier est d'abord copié (s'il n'est pas déjà dans la couche supérieure), puis renommé dans la couche supérieure en lecture-écriture. Simultanément, le fichier source doit être "whiteouté" (de sorte que la version du fichier source dans la couche inférieure devienne invisible). Toute l'opération doit être effectuée de manière atomique.
Lorsqu'il ne fait pas partie d'une union/overlay, le whiteout apparaît comme un périphérique caractère avec un numéro de périphérique {0,0}. (Notez que d'autres implémentations d'union/overlay peuvent utiliser des méthodes différentes pour stocker les entrées whiteout ; en particulier, le montage union de BSD utilise un type d'inode séparé, DT_WHT, qui, bien que supporté par certains systèmes de fichiers disponibles sous Linux, tels que CODA et XFS, est ignoré par le code de prise en charge des whiteouts du noyau, à partir de Linux 4.19, au moins.)
RENAME_WHITEOUT nécessite les mêmes privilèges que la création d'un nœud de périphérique (c'est-à-dire la capacité CAP_MKNOD).
RENAME_WHITEOUT ne peut pas être utilisé conjointement avec RENAME_EXCHANGE.
RENAME_WHITEOUT nécessite le support du système de fichiers sous-jacent. Parmi les systèmes de fichiers qui le supportent, citons tmpfs (depuis Linux 3.18), ext4 (depuis Linux 3.18), XFS (depuis Linux 4.1), f2fs (depuis Linux 4.2), btrfs (depuis Linux 4.7) et ubifs (depuis Linux 4.9).

VALEUR DE RETOUR

En cas de succès, zéro est renvoyé. En cas d'erreur, -1 est renvoyé, et errno est défini pour indiquer l'erreur.

ERREURS

EACCES
L'autorisation d'écrire est refusée pour le répertoire contenant oldpath ou newpath, ou l'autorisation de recherche est refusée pour l'un des répertoires dans le préfixe du chemin de oldpath ou newpath, ou oldpath est un répertoire et n'autorise pas l'écriture (nécessaire pour mettre à jour l'entrée ..). (Voir aussi path_resolution(7).)
EBUSY
Le renommage échoue car oldpath ou newpath est un répertoire utilisé par un processus (peut-être comme répertoire courant, ou comme répertoire racine, ou parce qu'il était ouvert en lecture) ou est utilisé par le système (par exemple comme point de montage), tandis que le système considère cela comme une erreur. (Notez qu'il n'y a aucune obligation de renvoyer EBUSY dans de tels cas — il n'y a rien de mal à effectuer le renommage quand même — mais il est permis de renvoyer EBUSY si le système ne peut pas gérer de telles situations autrement.)
EDQUOT

DESCRIPTION

The rename() function renames a file or directory. The name change occurs atomically (as far as the kernel is concerned) if oldpath and newpath are in the same directory.

The renameat() function is equivalent to calling rename(), except in the case where either oldpath or newpath is a relative path. In this case, it is interpreted relative to the directory referred to by the file descriptor olddirfd respectively newdirfd. If oldpath (or newpath) is relative and olddirfd (or newdirfd) is the special value AT_FDCWD, then oldpath (or newpath) is interpreted relative to the current working directory.

The renameat2() function is a variation of renameat() that allows atomic renaming with additional control flags specified in the flags argument. The supported flags are:

RENAME_NOREPLACE
Do not replace an existing file. If newpath exists, renameat2() fails with an error.
RENAME_EXCHANGE
Atomically exchange the contents of oldpath and newpath. Both paths must exist, and must be files (not directories). This operation is atomic.
RENAME_WHITEOUT
Create a whiteout on the destination. This flag is intended for use with copy-on-write filesystems. It causes newpath to be marked as a whiteout entry, which is a special type of directory entry that causes its parent directory to appear empty to the VFS layer. This is primarily useful for implementing efficient file removal in copy-on-write environments. This flag requires the caller to have the CAP_MKNOD capability.

If flags is zero, renameat2() behaves like renameat().

The interaction of RENAME_EXCHANGE with other flags is restricted. Neither RENAME_NOREPLACE nor RENAME_WHITEOUT can be specified with RENAME_EXCHANGE.

If oldpath and newpath specify the same file, rename() does nothing.

If newpath exists, it is removed. If it is a directory, it must be empty (see rmdir(2)).

If the link named by oldpath is a symbolic link, then the link itself is renamed, not the file or directory it points to.

If oldpath refers to a file that is being executed, the behavior is undefined. (On Linux, the rename will fail with EBUSY.)

If oldpath is a directory, then newpath must not exist. If oldpath is a directory, it must be empty before it can be renamed. Renaming a directory is not supported by all filesystems.

If oldpath and newpath are not on the same filesystem, the operation fails with EXDEV.

If newpath is a directory, it must be empty.

RETURN VALUE

On success, zero is returned. On failure, -1 is returned, and errno is set to indicate the error.

ERRORS

EACCES
Search permission denied for one of the directories in the path prefix of oldpath or newpath. Or, write permission denied for the directory in which the entry for oldpath is to be created, or for the directory in which the entry for newpath is to be created, or the directory containing newpath has the sticky bit (S_ISVTX) set and the process's effective user ID is neither the user ID of the file to be replaced nor that of the directory containing it, and the process is not privileged (Linux: does not have the CAP_FOWNER capability).
EBUSY
The file referred to by oldpath is in use (e.g. it is being executed). Or, the directory containing newpath has the sticky bit (S_ISVTX) set and the process's effective user ID is neither the user ID of the file to be replaced nor that of the directory containing it, and the process is not privileged (Linux: does not have the CAP_FOWNER capability).
EEXIST
newpath exists and RENAME_NOREPLACE was specified in flags. Or, newpath is a nonempty directory.
EINVAL
The new pathname contained a path prefix of the old, or, more generally, an attempt was made to make a directory a subdirectory of itself.
EISDIR
newpath is an existing directory, but oldpath is not a directory.
ELOOP
Too many symbolic links were encountered in resolving oldpath or newpath.
EMLINK
oldpath already has the maximum number of links to it, or it was a directory and the directory containing newpath has the maximum number of links.
ENAMETOOLONG
oldpath or newpath was too long.
ENOENT
The link named by oldpath does not exist; or, a directory component in newpath does not exist; or, oldpath or newpath is an empty string.
ENOMEM
Insufficient kernel memory was available.
ENOSPC
The device containing the file has no room for the new directory entry.
ENOTDIR
A component used as a directory in oldpath or newpath is not, in fact, a directory. Or, oldpath is a directory, and newpath exists but is not a directory.
ENOTEMPTY or EEXIST
newpath is a nonempty directory, that is, contains entries other than "." and "..".
EPERM or EACCES
The directory containing oldpath has the sticky bit (S_ISVTX) set and the process's effective user ID is neither the user ID of the file to be deleted nor that of the directory containing it, and the process is not privileged (Linux: does not have the CAP_FOWNER capability); or newpath is an existing file and the directory containing it has the sticky bit set and the process's effective user ID is neither the user ID of the file to be replaced nor that of the directory containing it, and the process is not privileged (Linux: does not have the CAP_FOWNER capability); or the filesystem containing oldpath does not support renaming of the type requested.
EROFS
The file is on a read-only filesystem.
EXDEV
oldpath and newpath are not on the same mounted filesystem. (Linux permits a filesystem to be mounted at multiple points, but rename() does not work across different mount points, even if the same filesystem is mounted on both.)

The following additional errors can occur for renameat() and renameat2():

EBADF
oldpath (newpath) is relative but olddirfd (newdirfd) is not a valid file descriptor.
ENOTDIR
oldpath is relative and olddirfd is a file descriptor referring to a file other than a directory; or similar for newpath and newdirfd

The following additional errors can occur for renameat2():

EEXIST
flags contains RENAME_NOREPLACE and newpath already exists.
EINVAL
An invalid flag was specified in flags.
EINVAL
Both RENAME_NOREPLACE and RENAME_EXCHANGE were specified in flags.
EINVAL
Both RENAME_WHITEOUT and RENAME_EXCHANGE were specified in flags.
EINVAL
The filesystem does not support one of the flags in flags.
ENOENT
flags contains RENAME_EXCHANGE and newpath does not exist.
EPERM
RENAME_WHITEOUT was specified in flags, but the caller does not have the CAP_MKNOD capability.

glibc notes

On older kernels where renameat() is unavailable, the glibc wrapper function falls back to the use of rename(). When oldpath and newpath are relative pathnames, glibc constructs pathnames based on the symbolic links in /proc/self/fd that correspond to the olddirfd and newdirfd arguments.

BUGS

On NFS filesystems, you can not assume that if the operation failed, the file was not renamed. If the server does the rename operation and then crashes, the retransmitted RPC which will be processed when the server is up again causes a failure. The application is expected to deal with this. See link(2) for a similar problem.
