recv(2) Manuel des appels système recv(2)

NOM

recv, recvfrom, recvmsg - recevoir un message d'une socket

BIBLIOTHÈQUE

Bibliothèque C standard (libc, -lc)

SYNTAXE

#include <sys/socket.h>
ssize_t recv(int sockfd, void buf[restrict size], size_t size,
                 int flags);
ssize_t recvfrom(int sockfd, void buf[restrict size], size_t size,
                 int flags,
                 struct sockaddr *_Nullable restrict src_addr,
                 socklen_t *_Nullable restrict addrlen);
ssize_t recvmsg(int sockfd, struct msghdr *msg, int flags);

DESCRIPTION

Les appels recv(), recvfrom() et recvmsg() sont utilisés pour recevoir des messages d'une socket. Ils peuvent être utilisés pour recevoir des données sur des sockets sans connexion et orientées connexion. Cette page décrit d'abord les caractéristiques communes aux trois appels système, puis les différences entre les appels.

La seule différence entre recv() et read(2) est la présence de flags. Avec un argument flags nul, recv() est généralement équivalent à read(2) (mais voir NOTES). De plus, l'appel suivant


recv(sockfd, buf, size, flags);

est équivalent à


recvfrom(sockfd, buf, size, flags, NULL, NULL);

Les trois appels retournent la taille du message en cas de succès. Si un message est trop long pour tenir dans le tampon fourni, les octets excédentaires peuvent être ignorés selon le type de socket à partir duquel le message est reçu.

Si aucun message n'est disponible sur la socket, les appels de réception attendent qu'un message arrive, à moins que la socket ne soit non bloquante (voir fcntl(2)), auquel cas la valeur -1 est retournée et errno est défini à EAGAIN ou EWOULDBLOCK. Les appels de réception retournent normalement les données disponibles, jusqu'au montant demandé, plutôt que d'attendre la réception du montant total demandé.

Une application peut utiliser select(2), poll(2), ou epoll(7) pour déterminer quand plus de données arrivent sur une socket.

L'argument flags

L'argument flags est formé en combinant un ou plusieurs des valeurs suivantes par un OU binaire :

MSG_CMSG_CLOEXEC (uniquement recvmsg() ; depuis Linux 2.6.23)
Définit le drapeau close-on-exec pour le descripteur de fichier reçu via un descripteur de fichier de domaine UNIX en utilisant l'opération SCM_RIGHTS (décrite dans unix(7)). Ce drapeau est utile pour les mêmes raisons que le drapeau O_CLOEXEC de open(2).
MSG_DONTWAIT (depuis Linux 2.2)
Active le fonctionnement non bloquant ; si l'opération bloquerait, l'appel échoue avec EAGAIN ou EWOULDBLOCK. Ceci fournit un comportement similaire à la définition du drapeau O_NONBLOCK (via l'opération F_SETFL de fcntl(2)), mais diffère en ce que MSG_DONTWAIT est une option par appel, tandis que O_NONBLOCK est un réglage sur la description de fichier ouverte (voir open(2)), ce qui affectera tous les threads du processus appelant ainsi que d'autres processus qui détiennent des descripteurs de fichiers se référant à la même description de fichier ouverte.
MSG_ERRQUEUE (depuis Linux 2.2)
Ce drapeau spécifie que les erreurs mises en file d'attente doivent être reçues depuis la file d'erreurs de la socket. L'erreur est passée dans un message auxiliaire dont le type dépend du protocole (pour IPv4 IP_RECVERR). L'utilisateur doit fournir un tampon de taille suffisante. Voir cmsg(3) et ip(7) pour plus d'informations. La charge utile du paquet original qui a causé l'erreur est passée comme donnée normale via msg_iovec. L'adresse de destination originale du datagramme qui a causé l'erreur est fournie via msg_name.
L'erreur est fournie dans une structure sock_extended_err :

#define SO_EE_ORIGIN_NONE    0
#define SO_EE_ORIGIN_LOCAL   1
#define SO_EE_ORIGIN_ICMP    2
#define SO_EE_ORIGIN_ICMP6   3
struct sock_extended_err
{
    uint32_t ee_errno;   /* Numéro d'erreur */
    uint8_t  ee_origin;  /* Origine de l'erreur */
    uint8_t  ee_type;    /* Type */
    uint8_t  ee_code;    /* Code */
    uint8_t  ee_pad;     /* Bourrage */
    uint32_t ee_info;    /* Informations supplémentaires */
    uint32_t ee_data;    /* Autres données */
    /* D'autres données peuvent suivre */
};
struct sockaddr *SO_EE_OFFENDER(struct sock_extended_err *);

ee_errno contient le numéro errno de l'erreur mise en file d'attente. ee_origin est le code d'origine de l'endroit où l'erreur est survenue. Les autres champs sont spécifiques au protocole. La macro SO_EE_OFFENDER retourne un pointeur vers l'adresse de l'objet réseau où l'erreur est survenue, étant donné un pointeur vers le message auxiliaire. Si cette adresse n'est pas connue, le membre sa_family de sockaddr contient AF_UNSPEC et les autres champs de sockaddr ne sont pas définis. La charge utile du paquet qui a causé l'erreur est passée comme donnée normale.
Pour les erreurs locales, aucune adresse n'est passée (cela peut être vérifié avec le membre cmsg_len de cmsghdr). Pour les réceptions d'erreurs, le drapeau MSG_ERRQUEUE est défini dans msghdr. Après qu'une erreur a été transmise, l'erreur de socket en attente est régénérée sur la base de la prochaine erreur en file d'attente et sera transmise lors de la prochaine opération sur la socket.
MSG_OOB
Ce drapeau demande la réception de données hors bande qui ne seraient pas reçues dans le flux de données normal. Certains protocoles placent les données urgentes en tête de la file d'attente de données normales, et donc ce drapeau ne peut pas être utilisé avec de tels protocoles.
MSG_PEEK
Ce drapeau fait en sorte que l'opération de réception retourne les données depuis le début de la file de réception sans supprimer ces données de la file. Ainsi, un appel de réception ultérieur retournera les mêmes données.
MSG_TRUNC (depuis Linux 2.2)
Pour les sockets brutes (AF_PACKET), datagrammes Internet (depuis Linux 2.4.27/2.6.8), netlink (depuis Linux 2.6.22), et datagrammes UNIX ainsi que séquencées par paquets (depuis Linux 3.4) : retourner la taille réelle du paquet ou du datagramme, même lorsqu'il était plus long que le tampon fourni.
À utiliser avec les sockets de flux Internet, voir tcp(7).
MSG_WAITALL (depuis Linux 2.2)
Ce drapeau demande que l'opération bloque jusqu'à ce que la requête complète soit satisfaite. Cependant, l'appel peut toujours retourner moins de données que demandé si un signal est intercepté, une erreur ou une déconnexion se produit, ou si les prochaines données à recevoir sont d'un type différent de celles retournées. Ce drapeau n'a aucun effet pour les sockets de datagrammes.

recvfrom()

recvfrom() place le message reçu dans le tampon buf. L'appelant doit spécifier la taille du tampon dans size.

Si src_addr n'est pas NULL, et que le protocole sous-jacent fournit l'adresse source du message, cette adresse source est placée dans le tampon pointé par src_addr. Dans ce cas, addrlen est un argument valeur-résultat. Avant l'appel, il doit être initialisé à la taille du tampon associé à src_addr. Au retour, addrlen est mis à jour pour contenir la taille réelle de l'adresse source. L'adresse retournée est tronquée si le tampon fourni est trop petit ; dans ce cas, addrlen retournera une valeur supérieure à celle fournie à l'appel.

Si l'appelant ne s'intéresse pas à l'adresse source, src_addr et addrlen doivent être spécifiés comme NULL.

recvmsg()

recvmsg() est une interface plus générale pour recevoir des données et des informations auxiliaires. Elle est utilisée pour recevoir des données sur des sockets de type datagramme ou stream, et elle est particulièrement utile pour recevoir des informations auxiliaires, telles que des options de socket ou des descripteurs de fichiers sur des sockets UNIX (utilisant SCM_RIGHTS).

Le paramètre msg est un pointeur vers une structure msghdr, qui est définie comme suit :


struct msghdr {
    void         *msg_name;       /* Pointeur vers l'adresse du socket */
    socklen_t     msg_namelen;    /* Taille de l'adresse du socket */
    struct iovec *msg_iov;        /* Tableau de tampons de données */
    size_t        msg_iovlen;     /* Nombre de tampons dans msg_iov */
    void         *msg_control;    /* Pointeur vers le buffer des données auxiliaires */
    size_t        msg_controllen; /* Taille du buffer des données auxiliaires */
    int           msg_flags;      /* Flags de réception/envoi */
};

L'appel recvmsg() remplit les champs de la structure msghdr comme suit :

  • msg_name et msg_namelen spécifient la taille et le tampon où stocker l'adresse de l'expéditeur (si le protocole le fournit).
  • msg_iov et msg_iovlen spécifient un tableau de structures iovec décrivant où stocker les données reçues. L'appel lit les données dans ces tampons jusqu'à ce que tous les tampons soient remplis ou que le message soit entièrement lu.
  • msg_control et msg_controllen spécifient la taille et le tampon où stocker les données auxiliaires (par exemple, options de socket, contrôles).
  • msg_flags est un champ de retour qui contient les flags de réception pour le message reçu.

Les données auxiliaires sont représentées par des structures cmsghdr. L'utilisation de recvmsg() pour les données auxiliaires est détaillée dans cmsg(3).

VALEUR_RETOURNEE

En cas de succès, ces appels retournent le nombre d'octets reçus. Si un message est trop long pour le tampon fourni, le comportement dépend du type de socket ; voir la description de MSG_TRUNC.

En cas d'échec, -1 est retourné et errno est défini pour indiquer l'erreur.

ERREURS

Les erreurs courantes, mais non limitatives, sont :

EAGAIN
La socket est non bloquante et aucune donnée n'est disponible pour la réception.
EBADF
Le paramètre sockfd n'est pas un descripteur de fichier valide.
ECONNRESET
Une connexion a été rompue par votre pair. Ceci est un problème du niveau de protocole, tel que le pair a fermé la connexion de manière abrupte.
EFAULT
L'adresse buf, src_addr, ou msg est hors de l'espace d'adressage accessible.
EINTR
L'appel a été interrompu par un signal avant que des données ne soient disponibles.
EINVAL
L'argument flags est invalide, ou msg_iovlen est invalide.
ENOTCONN
La socket n'est pas connectée (par exemple, un appel à recv() sur une socket sans connexion).
ENOTSOCK
Le paramètre sockfd est une socket.
EWOULDBLOCK
Identique à EAGAIN.

D'autres erreurs sont possibles.

CONFORMITÉS

Les appels recv(), recvfrom() et recvmsg() sont conformes à POSIX.1-2001 et aux versions ultérieures.

NOTES

Différences entre read et recv

Bien que recv() avec flags = 0 soit généralement équivalent à read(2), il existe quelques différences dans des cas limites. Par exemple, sur certaines architectures, read(2) peut retourner moins que la valeur de size même si des données sont disponibles et que la socket n'est pas en mode non bloquant, alors que recv() avec flags = 0 devrait normalement retourner tout ce qui est disponible jusqu'à size.

Les appels recv() et read(2) peuvent tous deux retourner moins de données que demandé, même si plus de données sont disponibles. L'appelant doit donc vérifier la valeur de retour et continuer à lire jusqu'à ce que toutes les données requises soient reçues.

Les appels recv(), recvfrom() et recvmsg() ne doivent pas être utilisés sur une socket qui a déjà été fermée ou qui est en train d'être fermée. Le comportement est indéfini.

MSG_PEEK et MSG_TRUNC

Si MSG_PEEK est utilisé avec MSG_TRUNC, la taille complète du paquet sera retournée, même si le tampon est trop petit. Les données restantes dans le paquet seront disponibles pour les appels de réception ultérieurs.

MSG_ERRQUEUE et recvfrom()

Lorsque MSG_ERRQUEUE est utilisé avec recvfrom(), l'adresse source src_addr contiendra l'adresse de l'expéditeur du paquet qui a causé l'erreur, si elle est disponible.

MSG_WAITALL

Le drapeau MSG_WAITALL n'est pas garanti de fonctionner correctement sur tous les protocoles. Pour une utilisation fiable, il est préférable d'utiliser des mécanismes de multiplexage comme select(2) ou poll(2).

recv()

L'appel recv() est normalement utilisé uniquement sur une socket connectée (voir connect(2)). Il est équivalent à l'appel :


recvfrom(fd, buf, size, flags, NULL, NULL);

recvmsg()

L'appel recvmsg() utilise une structure msghdr pour minimiser le nombre d'arguments fournis directement. Cette structure est définie comme suit dans <sys/socket.h> :


struct msghdr {
    void         *msg_name;       /* Adresse optionnelle */
    socklen_t     msg_namelen;    /* Taille de l'adresse */
    struct iovec *msg_iov;        /* Tableau scatter/gather */
    size_t        msg_iovlen;     /* Nombre d'éléments dans msg_iov */
    void         *msg_control;    /* Données auxiliaires, voir ci-dessous */
    size_t        msg_controllen; /* Taille du tampon de données auxiliaires */
    int           msg_flags;      /* Indicateurs sur le message reçu */
};

Le champ msg_name pointe vers un tampon alloué par l'appelant qui est utilisé pour retourner l'adresse source si la socket n'est pas connectée. L'appelant doit définir msg_namelen à la taille de ce tampon avant cet appel ; après le retour d'un appel réussi, msg_namelen contiendra la taille de l'adresse retournée. Si l'application n'a pas besoin de connaître l'adresse source, msg_name peut être spécifié comme NULL.

Les champs msg_iov et msg_iovlen décrivent les emplacements de diffusion/collecte, comme discuté dans readv(2).

Le champ msg_control, dont la taille est msg_controllen, pointe vers un tampon pour d'autres messages liés au contrôle du protocole ou des données auxiliaires diverses. Lorsque recvmsg() est appelé, msg_controllen doit contenir la taille du tampon disponible dans msg_control ; après le retour d'un appel réussi, il contiendra la taille de la séquence de messages de contrôle.

Les messages sont de la forme :


struct cmsghdr {
    size_t cmsg_len;    /* Nombre d'octets de données, y compris l'en-tête
                           (le type est socklen_t dans POSIX) */
    int    cmsg_level;  /* Protocole d'origine */
    int    cmsg_type;   /* Type spécifique au protocole */
/* suivi par
    unsigned char cmsg_data[]; */
};

Les données auxiliaires ne doivent être accessibles que par les macros définies dans cmsg(3).

À titre d'exemple, Linux utilise ce mécanisme de données auxiliaires pour passer des erreurs étendues, des options IP ou des descripteurs de fichiers sur les sockets de domaine UNIX. Pour plus d'informations sur l'utilisation des données auxiliaires dans divers domaines de sockets, voir unix(7) et ip(7).

Le champ msg_flags dans le msghdr est défini au retour de recvmsg(). Il peut contenir plusieurs indicateurs :

MSG_EOR
indique la fin d'un enregistrement ; les données retournées ont complété un enregistrement (généralement utilisé avec des sockets de type SOCK_SEQPACKET).
MSG_TRUNC
indique que la partie finale d'un datagramme a été écartée parce que le datagramme était plus grand que le tampon fourni.
MSG_CTRUNC
indique que certaines données de contrôle ont été écartées en raison d'un manque d'espace dans le tampon pour les données auxiliaires.
MSG_OOB
est retourné pour indiquer que des données urgentes ou hors bande ont été reçues.
MSG_ERRQUEUE
indique qu'aucune donnée n'a été reçue mais qu'une erreur étendue provient de la file d'attente des erreurs de la socket.
MSG_CMSG_CLOEXEC (depuis Linux 2.6.23)
indique que MSG_CMSG_CLOEXEC a été spécifié dans l'argument flags de recvmsg().

VALEUR DE RETOUR

Ces appels retournent le nombre d'octets reçus, ou -1 si une erreur s'est produite. En cas d'erreur, errno est défini pour indiquer l'erreur.

Lorsqu'un pair de socket de flux a effectué une fermeture ordonnée, la valeur de retour sera 0 (le retour traditionnel de « fin de fichier »).

Les sockets de datagrammes dans divers domaines (par exemple, les domaines UNIX et Internet) autorisent les datagrammes de taille zéro. Lorsqu'un tel datagramme est reçu, la valeur de retour est 0.

La valeur 0 peut également être retournée si le nombre d'octets demandé à recevoir d'une socket de flux était de 0.

ERREURS

Ce sont quelques erreurs standard générées par la couche de sockets. Des erreurs supplémentaires peuvent être générées et retournées par les modules de protocole sous-jacents ; voir leurs pages de manuel.

EAGAIN ou EWOULDBLOCK
La socket est marquée comme non bloquante et l'opération de réception bloquerait, ou un délai d'attente de réception avait été défini et le délai a expiré avant que des données ne soient reçues. POSIX.1 autorise l'une ou l'autre erreur pour ce cas, et n'exige pas que ces constantes aient la même valeur, donc une application portable devrait vérifier les deux possibilités.
EBADF
L'argument sockfd est un descripteur de fichier invalide.
ECONNREFUSED
Un hôte distant a refusé d'autoriser la connexion réseau (typiquement parce qu'il n'exécute pas le service demandé).
EFAULT
Les pointeurs du tampon de réception pointent à l'extérieur de l'espace d'adressage du processus.
EINTR
La réception a été interrompue par la livraison d'un signal avant que des données ne soient disponibles ; voir signal(7).
EINVAL
Argument invalide passé.
ENOMEM
Impossible d'allouer de la mémoire pour recvmsg().
ENOTCONN
La socket est associée à un protocole orienté connexion et n'a pas été connectée (voir connect(2) et accept(2)).
ENOTSOCK
Le descripteur de fichier sockfd ne fait pas référence à une socket.

VERSIONS

Selon POSIX.1, le champ msg_controllen de la structure msghdr doit être typé comme socklen_t, et le champ msg_iovlen doit être typé comme int, mais glibc les tape actuellement tous les deux comme size_t.

NORMES

POSIX.1-2024.

HISTORIQUE

POSIX.1-2001, 4.2BSD.

POSIX.1 ne décrit que les indicateurs MSG_OOB, MSG_PEEK et MSG_WAITALL.

NOTES

Si un datagramme de taille zéro est en attente, read(2) et recv() avec un argument flags de zéro ont un comportement différent. Dans cette circonstance, read(2) n'a aucun effet (le datagramme reste en attente), tandis que recv() consomme le datagramme en attente.

Voir recvmmsg(2) pour des informations sur un appel système spécifique à Linux qui peut être utilisé pour recevoir plusieurs datagrammes en un seul appel.

EXEMPLES

Un exemple d'utilisation de recvfrom() est montré dans getaddrinfo(3).
