readv(2) Manuel des appels système readv(2)

NOM

readv, writev, preadv, pwritev, preadv2, pwritev2 - lire ou écrire des données dans plusieurs tampons

BIBLIOTHÈQUE

Bibliothèque C standard (libc, -lc)

SYNTAXE

#include <sys/uio.h>
ssize_t readv(int fd, const struct iovec *iov, int iovcnt);
ssize_t writev(int fd, const struct iovec *iov, int iovcnt);
ssize_t preadv(int fd, const struct iovec *iov, int iovcnt,
                off_t offset);
ssize_t pwritev(int fd, const struct iovec *iov, int iovcnt,
                off_t offset);
ssize_t preadv2(int fd, const struct iovec *iov, int iovcnt,
                off_t offset, int flags);
ssize_t pwritev2(int fd, const struct iovec *iov, int iovcnt,
                off_t offset, int flags);
Exigences de macros de test de fonctionnalités pour glibc (voir feature_test_macros(7)) :

preadv(), pwritev() :

    Depuis glibc 2.19 :
        _DEFAULT_SOURCE
    glibc 2.19 et antérieur :
        _BSD_SOURCE

DESCRIPTION

L'appel système readv() lit iovcnt tampons depuis le fichier associé au descripteur de fichier fd dans les tampons décrits par iov (« entrée dispersée »).

L'appel système writev() écrit iovcnt tampons de données décrits par iov dans le fichier associé au descripteur de fichier fd (« sortie groupée »).

Le pointeur iov pointe vers un tableau de structures iovec, décrit dans iovec(3type).

L'appel système readv() fonctionne comme read(2) sauf que plusieurs tampons sont remplis.

L'appel système writev() fonctionne comme write(2) sauf que plusieurs tampons sont écrits.

Les tampons sont traités dans l'ordre du tableau. Cela signifie que readv() remplit complètement iov[0] avant de passer à iov[1], et ainsi de suite. (S'il y a une quantité de données insuffisante, tous les tampons pointés par iov ne seront peut-être pas remplis.) De même, writev() écrit l'intégralité du contenu de iov[0] avant de passer à iov[1], et ainsi de suite.

Les transferts de données effectués par readv() et writev() sont atomiques : les données écrites par writev() sont écrites en un seul bloc qui n'est pas mélangé avec les écritures d'autres processus ; de manière analogue, readv() est garanti de lire un bloc contigu de données depuis le fichier, indépendamment des opérations de lecture effectuées dans d'autres threads ou processus qui ont des descripteurs de fichier faisant référence à la même description de fichier ouverte (voir open(2)).

preadv() et pwritev()

L'appel système preadv() combine les fonctionnalités de readv() et de pread(2). Il effectue la même tâche que readv(), mais ajoute un quatrième argument, offset, qui spécifie le décalage dans le fichier auquel l'opération de lecture doit être effectuée.

L'appel système pwritev() combine les fonctionnalités de writev() et de pwrite(2). Il effectue la même tâche que writev(), mais ajoute un quatrième argument, offset, qui spécifie le décalage dans le fichier auquel l'opération d'écriture doit être effectuée.

Le décalage dans le fichier n'est pas modifié par ces appels système. Le fichier référencé par fd doit être capable de se déplacer.

preadv2() et pwritev2()

Ces appels système sont similaires aux appels preadv() et pwritev(), mais ajoutent un cinquième argument, flags, qui modifie le comportement de manière individuelle.

Contrairement à preadv() et pwritev(), si l'argument offset est -1, alors le décalage de fichier actuel est utilisé et mis à jour.

L'argument flags contient un OU binaire de zéro ou plusieurs des indicateurs suivants :

RWF_DSYNC (depuis Linux 4.7)
Fournit un équivalent par écriture de l'indicateur open(2) O_DSYNC. Cet indicateur n'est significatif que pour pwritev2(), et son effet s'applique uniquement à la plage de données écrite par l'appel système.
RWF_HIPRI (depuis Linux 4.6)
Lecture/écriture à priorité élevée. Permet aux systèmes de fichiers basés sur des blocs d'utiliser le polling du périphérique, ce qui offre une latence plus faible, mais peut utiliser des ressources supplémentaires. (Actuellement, cette fonctionnalité n'est utilisable que sur un descripteur de fichier ouvert en utilisant l'indicateur O_DIRECT.)
RWF_SYNC (depuis Linux 4.7)
Fournit un équivalent par écriture de l'indicateur open(2) O_SYNC. Cet indicateur n'est significatif que pour pwritev2(), et son effet s'applique uniquement à la plage de données écrite par l'appel système.
RWF_NOWAIT (depuis Linux 4.14)
Ne pas attendre les données qui ne sont pas immédiatement disponibles. Si cet indicateur est spécifié, l'appel système preadv2() retournera instantanément s'il devait lire des données depuis le stockage sous-jacent ou attendre un verrou. Si des données ont été lues avec succès, il retournera le nombre d'octets lus. S'il n'y a eu aucun octet lu, il retournera -1 et mettra errno à EAGAIN (mais voir BUGS). Actuellement, cet indicateur n'est significatif que pour preadv2().
RWF_APPEND (depuis Linux 4.16)
Fournit un équivalent par écriture de l'indicateur open(2) O_APPEND. Cet indicateur n'est significatif que pour pwritev2(), et son effet s'applique uniquement à la plage de données écrite par l'appel système. L'argument offset n'affecte pas l'opération d'écriture ; les données sont toujours ajoutées à la fin du fichier. Cependant, si l'argument offset est -1, le décalage de fichier actuel est mis à jour.
RWF_NOAPPEND (depuis Linux 6.9)
Ne pas tenir compte de l'indicateur open(2) O_APPEND. Cet indicateur n'est significatif que pour pwritev2(). Historiquement, Linux tenait compte de l'indicateur O_APPEND s'il était défini et ignorait l'argument offset, ce qui est un bogue. Pour pwritev2(), l'argument offset est pris en compte comme prévu si l'indicateur RWF_NOAPPEND est défini, de la même manière que si l'indicateur O_APPEND n'était pas défini.
RWF_ATOMIC (depuis Linux 6.11)
Exige que les écritures sur les fichiers réguliers dans les systèmes de fichiers basés sur des blocs soient effectuées avec une protection contre les écritures déformées. La protection contre les écritures déformées signifie que pour une panne de courant ou toute autre défaillance matérielle, tout ou partie des données de l'écriture seront stockées, mais jamais un mélange d'anciennes et de nouvelles données. Cet indicateur n'est significatif que pour pwritev2(), et son effet s'applique uniquement à la plage de données écrite par l'appel système. La longueur totale de l'écriture doit être une puissance de 2 et être dimensionnée dans la plage [stx_atomic_write_unit_min, stx_atomic_write_unit_max]. L'écriture doit se faire à un décalage naturellement aligné dans le fichier par rapport à la longueur totale de l'écriture. Par exemple, une écriture de 32 KiB à un décalage de fichier de 32 KiB est autorisée, cependant une écriture de 32 KiB à un décalage de fichier de 48 KiB n'est pas autorisée. La limite supérieure de iovcnt pour pwritev2() est donnée par la valeur dans stx_atomic_write_segments_max. La protection contre les écritures déformées ne fonctionne qu'avec l'indicateur O_DIRECT, c'est-à-dire que les écritures mises en mémoire tampon ne sont pas prises en charge. Pour garantir la cohérence entre l'état en mémoire du fichier et le périphérique de stockage, O_SYNC ou O_DSYNC doit être spécifié pour open(2). RWF_DONTCACHE (depuis Linux 6.14)
Les lectures ou écritures sur un fichier régulier supprimeront le contenu instancié du cache de pages à la fin de l'opération. Ceci est différent des opérations d'E/S tamponnées normales, où les données restent généralement en cache jusqu'à ce qu'elles soient récupérées en raison de contraintes mémoire. Si des plages de l'E/S lue ou écrite étaient déjà en cache avant cette lecture ou écriture, alors ces plages ne seront pas supprimées au moment de la fin de l'E/S.
De plus, toute plage marquée comme sale par une opération d'écriture avec RWF_DONTCACHE défini sera mise en attente d'écriture (writeback). Ceci est similaire à l'appel de sync_file_range(2) avec SYNC_FILE_RANGE_WRITE pour démarrer l'écriture sur la plage donnée. RWF_DONTCACHE est un indice, ou un effort maximal, où aucune garantie rigide n'est donnée sur l'état du cache de pages une fois l'opération terminée.
Si utilisé sur un système de fichiers ou un périphérique bloc qui ne le supporte pas, cela retournera -1, et errno sera défini à EOPNOTSUPP.

VALEUR DE RETOUR

En cas de succès, readv(), preadv() et preadv2() retournent le nombre d'octets lus ; writev(), pwritev() et pwritev2() retournent le nombre d'octets écrits.

Notez qu'il n'est pas une erreur pour un appel réussi de transférer moins d'octets que demandé (voir read(2) et write(2)).

En cas d'erreur, -1 est retourné, et errno est défini pour indiquer l'erreur.

ERREURS

Les erreurs sont celles indiquées pour read(2) et write(2). De plus, preadv(), preadv2(), pwritev() et pwritev2() peuvent également échouer pour les mêmes raisons que lseek(2). De plus, les erreurs suivantes sont définies :

EINVAL
La somme des valeurs iov_len dépasse une valeur ssize_t.
EINVAL
Si RWF_ATOMIC est spécifié, la combinaison de la somme des valeurs iov_len et de la valeur offset ne respecte pas les règles de protection contre les écritures déchirées (torn-write).
EINVAL
Le nombre de vecteurs, iovcnt, est inférieur à zéro ou supérieur au maximum autorisé. Si RWF_ATOMIC est spécifié, ce maximum est donné par la valeur stx_atomic_write_segments_max de statx.
EOPNOTSUPP
RWF_DONTCACHE a été défini dans flags et le fichier ne le supporte pas.
EOPNOTSUPP
Un indicateur inconnu est spécifié dans flags.

VERSIONS

Différences bibliothèque C/noyau

Les appels système bruts preadv() et pwritev() ont des signatures d'appel légèrement différentes de celles des fonctions wrapper correspondantes de la bibliothèque C GNU présentées dans le SYNOPSIS. Le dernier argument, offset, est décomposé par les fonctions wrapper en deux arguments dans les appels système :

unsigned long pos_l, unsigned long pos

Ces arguments contiennent respectivement les 32 bits de poids faible et de poids fort de offset.

Différences historiques bibliothèque C/noyau

Pour gérer le fait que IOV_MAX était si bas sur les premières versions de Linux, les fonctions wrapper de glibc pour readv() et writev() effectuaient un travail supplémentaire si elles détectaient que l'appel système sous-jacent échouait parce que cette limite était dépassée. Dans le cas de readv(), la fonction wrapper allouait un tampon temporaire suffisamment grand pour tous les éléments spécifiés par iov, passait ce tampon dans un appel à read(2), copiait les données du tampon vers les emplacements spécifiés par les champs iov_base des éléments de iov, puis libérait le tampon. La fonction wrapper pour writev() effectuait la tâche analogue en utilisant un tampon temporaire et un appel à write(2).

La nécessité de cet effort supplémentaire dans les fonctions wrapper de glibc a disparu avec Linux 2.2 et les versions ultérieures. Cependant, glibc a continué à fournir ce comportement jusqu'à glibc 2.10. À partir de glibc 2.9, les fonctions wrapper fournissent ce comportement uniquement si la bibliothèque détecte que le système exécute un noyau Linux antérieur à Linux 2.6.18 (une version de noyau sélectionnée arbitrairement). Et depuis glibc 2.20 (qui nécessite un minimum de Linux 2.6.32), les fonctions wrapper de glibc invoquent simplement directement les appels système.

NOTES

POSIX.1 permet à une implémentation de placer une limite sur le nombre d'éléments qui peuvent être passés dans iov. Une implémentation peut annoncer sa limite en définissant IOV_MAX dans <limits.h> ou au moment de l'exécution via la valeur de retour de sysconf(_SC_IOV_MAX). Sur les systèmes Linux modernes, la limite est de 1024. Dans les jours de Linux 2.0, cette limite était de 16.

BOGUES

Linux 5.9 et Linux 5.10 ont un bug où preadv2() avec l'indicateur RWF_NOWAIT peut retourner 0 même lorsque ce n'est pas la fin du fichier.

EXEMPLES

L'exemple de code suivant démontre l'utilisation de writev() :


char          *str0 = "hello ";
char          *str1 = "world\n";
ssize_t       nwritten;
struct iovec  iov[2];
iov[0].iov_base = str0;
iov[0].iov_len = strlen(str0);
iov[1].iov_base = str1;
iov[1].iov_len = strlen(str1);
nwritten = writev(STDOUT_FILENO, iov, 2);
