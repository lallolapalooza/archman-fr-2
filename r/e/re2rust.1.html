NOM

re2rust - générer des analyseurs lexicaux rapides pour Rust

SYNTAXE

re2rust [ OPTIONS ] [ AVERTISSEMENTS ] ENTRÉE

L'entrée peut être soit un fichier, soit - pour l'entrée standard.

INTRODUCTION

re2rust fonctionne comme un préprocesseur. Il lit le fichier d'entrée (qui est généralement un programme en Rust, mais peut être n'importe quoi) et recherche des blocs de code délimités par des marqueurs de début/fin de forme spéciale. Le texte en dehors de ces blocs est copié tel quel dans le fichier de sortie. Le contenu des blocs est traité par re2rust. Il le traduit en code Rust et génère le code résultant à la place du bloc.

Voici un exemple de petit programme qui vérifie si une chaîne donnée contient un nombre décimal :

// re2rust $INPUT -o $OUTPUT --no-unsafe --api simple
fn lex(yyinput: &[u8]) -> bool {
    let mut yycursor = 0;
    /*!re2c
        re2c:YYCTYPE = u8;
        re2c:yyfill:enable = 0;
        [1-9][0-9]* { return true; }
        *           { return false; }
    */
}
fn main() {
    assert!(lex(b"1234\0"));
}

Dans la sortie, re2rust a remplacé le bloc du milieu par le code généré :

/* Généré par re2rust */
// re2rust $INPUT -o $OUTPUT --no-unsafe --api simple
fn lex(yyinput: &[u8]) -> bool {
    let mut yycursor = 0;
{
    #[allow(unused_assignments)]
    let mut yych : u8 = 0;
    let mut yystate : usize = 0;
    'yyl: loop {
        match yystate {
            0 => {
                yych = yyinput[yycursor];
                yycursor += 1;
                match yych {
                    0x31 ..= 0x39 => {
                        yystate = 2;
                        continue 'yyl;
                    }
                    _ => {
                        yystate = 1;
                        continue 'yyl;
                    }
                }
            }
            1 => { return false; },
            2 => {
                yych = yyinput[yycursor];
                match yych {
                    0x30 ..= 0x39 => {
                        yycursor += 1;
                        yystate = 2;
                        continue 'yyl;
                    }
                    _ => {
                        yystate = 3;
                        continue 'yyl;
                    }
                }
            }
            3 => { return true; },
            _ => panic!("erreur interne de l'analyseur"),
        }
    }
}
}
fn main() {
    assert!(lex(b"1234\0"));
}

BASES

Un programme re2rust est composé d'une séquence de blocs entremêlés de code dans le langage cible. Un bloc peut contenir des définitions, des configurations, des règles, des actions et des directives dans n'importe quel ordre :

nom = expression-régulière ;
Une définition associe nom à expression-régulière. Les noms peuvent contenir des caractères alphanumériques et le trait de soulignement. La section expressions régulières donne un aperçu de la syntaxe de re2rust pour les expressions régulières. Une fois définie, le nom peut être utilisé dans d'autres expressions régulières et dans les règles. La récursion dans les définitions nommées n'est pas autorisée, et chaque nom doit être défini avant d'être utilisé. Un bloc hérite des définitions nommées de la portée globale. Redéfinir un nom qui existe dans la portée actuelle est une erreur.
configuration = valeur ;
Une configuration permet de modifier le comportement de re2rust et de personnaliser le code généré. Pour une liste complète des configurations prises en charge par re2rust, voir la section configurations. Selon la configuration, la valeur peut être un mot-clé, un nombre entier non négatif ou une chaîne sur une seule ligne qui doit être entourée de guillemets doubles ou simples, sauf si elle est composée de caractères alphanumériques. Un bloc hérite des configurations de la portée globale et peut les redéfinir ou en ajouter de nouvelles. Les configurations définies à l'intérieur d'un bloc affectent tout le bloc, même si elles apparaissent à la fin de celui-ci.
expression-régulière code
Une règle associe une expression-régulière à son action sémantique (un bloc de code entre accolades, ou un bloc de code qui commence par := et se termine sur un saut de ligne suivi d'un caractère non blanc). Si l'expression-régulière correspond, le code associé est exécuté. Si plusieurs règles correspondent, la correspondance la plus longue a priorité. Si plusieurs règles correspondent à la même chaîne, la première apparaît a priorité. Il existe deux règles spéciales : la règle par défaut * et la règle de fin d'entrée $. La règle par défaut doit toujours être définie, elle a la priorité la plus basse quelle que soit sa place dans le bloc, et elle correspond à n'importe quelle unité de code (pas nécessairement un caractère valide, voir la section prise en charge de l'encodage). La règle de fin d'entrée doit être définie si la méthode correspondante pour la gestion de la fin d'entrée est utilisée. Avec les conditions de départ, les règles ont une syntaxe plus complexe.
!action code
Une action associe un bloc de code défini par l'utilisateur à un endroit particulier dans la machine à états finis générée (de la même manière que les actions sémantiques associent du code aux états finaux). Voir la section actions pour une liste complète des actions prédéfinies.
!directive ;
Une directive est l'une des instructions prédéfinies spéciales. Chaque directive a un objectif unique. Voir la section directives pour plus de détails.

Blocs

Les marqueurs de début et de fin de bloc sont soit /*!re2c et */, soit %{ et %} (les deux styles sont pris en charge). Depuis la version 2.2, les blocs peuvent avoir des noms optionnels qui permettent de les référencer dans d'autres blocs. Il existe différents types de blocs :

/*!re2c[:<nom>] ... */ ou %{[:<nom>] ... %}
Un bloc global contient des définitions, des configurations, des règles et des directives. re2rust compile les expressions régulières associées à chaque règle en un automate fini déterministe, l'encode sous forme de sauts conditionnels dans le langage cible et remplace le bloc par le code généré. Les noms et configurations définis dans un bloc global sont ajoutés à la portée globale et deviennent visibles pour les blocs suivants. Au début du programme, la portée globale est initialisée avec les options de la ligne de commande.
/*!local:re2c[:<nom>] ... */ ou %{local[:<nom>] ... %}
Un bloc local est similaire à un bloc global, mais les noms et configurations qu'il contient ont une portée locale (ils n'affectent pas les autres blocs).
/*!rules:re2c[:<nom>] ... */ ou %{rules[:<nom>] ... %}
Un bloc de règles est similaire à un bloc local, mais il ne génère aucun code en soi, ni n'ajoute de définitions à la portée globale — il est destiné à être réutilisé dans d'autres blocs. C'est une façon de partager du code (plus de détails dans la section blocs réutilisables). Avant la version 2.2 de re2rust, les blocs de règles nécessitaient l'option -r --reusable.
/*!use:re2c[:<nom>] ... */ ou %{use[:<nom>] ... %}
Un bloc d'utilisation qui référence un bloc de règles défini précédemment. Si le nom est spécifié, re2rust recherche les blocs de règles portant ce nom. Sinon, le bloc de règles le plus récent est utilisé (nommé ou non nommé). Un bloc d'utilisation peut ajouter ses propres définitions, configurations et règles, qui sont ajoutées à celles du bloc de règles référencé. Avant la version 2.2 de re2rust, les blocs d'utilisation nécessitaient l'option -r --reusable.
/*!max:re2c[:<nom1>[:<nom2>...]] ... */ ou %{max[:<nom1>[:<nom2>...]] ... %}
Un bloc qui génère la définition YYMAXFILL. Une liste optionnelle de noms de blocs spécifie quels blocs doivent être inclus lors du calcul de la valeur de YYMAXFILL (si la liste est vide, tous les blocs sont inclus). Par défaut, le code généré est une macro-définition pour C (#define YYMAXFILL <n>), ou une variable globale pour Go (var YYMAXFILL int = <n>). Il peut être personnalisé avec une configuration optionnelle format qui spécifie une chaîne modèle où @@{max} (ou @@ pour faire court) est remplacé par la valeur numérique de YYMAXFILL.
/*!maxnmatch:re2c[:<nom1>[:<nom2>...]] ... */ ou %{maxnmatch[:<nom1>[:<

Blocks

/*!rule:re2c[:<name1>[:<name2>...]] ... */, %{rule[:<name1>[:<name2>...]] ... %}
A block that specifies a grammar rule. An optional list of block names specifies which rules should be included when computing the result of rule analysis (if the list is empty, all rules are included). By default the generated code is a macro-definition for C (#define YYMAXNMATCH <n>), or a global variable for Go (var YYMAXNMATCH int = <n>). It can be customized with an optional configuration format that specifies a template string where @@{max} (or @@ for short) is replaced with the numeric value of YYMAXNMATCH.
/*!maxnmatch:re2c[:<name1>[:<name2>...]] ... */, %{maxnmatch[:<name1>[:<name2>...]] ... %}
A block that generates YYMAXNMATCH definition (it requires -P --posix-captures option). An optional list of block names specifies which blocks should be included when computing YYMAXNMATCH value (if the list is empty, all blocks are included). By default the generated code is a macro-definition for C (#define YYMAXNMATCH <n>), or a global variable for Go (var YYMAXNMATCH int = <n>). It can be customized with an optional configuration format that specifies a template string where @@{max} (or @@ for short) is replaced with the numeric value of YYMAXNMATCH.
/*!stags:re2c[:<name1>[:<name2>...]] ... */, /*!mtags:re2c[:<name1>[:<name2>...]] ... */ or %{stags[:<name1>[:<name2>...]] ... %}, %{mtags[:<name1>[:<name2>...]] ... %{
Blocks that specify a template piece of code that is expanded for each s-tag/m-tag variable generated by re2rust. An optional list of block names specifies which blocks should be included when computing the set of tag variables (if the list is empty, all blocks are included). There are two optional configurations: format and separator. Configuration format specifies a template string where @@{tag} (or @@ for short) is replaced with the name of each tag variable. Configuration separator specifies a piece of code used to join the generated format pieces for different tag variables.
/*!svars:re2c[:<name1>[:<name2>...]] ... */, /*!mvars:re2c[:<name1>[:<name2>...]] ... */ or %{svars[:<name1>[:<name2>...]] ... %}, %{mvars[:<name1>[:<name2>...]] ... %{
Blocks that specify a template piece of code that is expanded for each s-tag/m-tag that is either explicitly mentioned by the rules (with --tags option) or implicitly generated by re2rust (with --captvars or --posix-captvars options). An optional list of block names specifies which blocks should be included when computing the set of tags (if the list is empty, all blocks are included). There are two optional configurations: format and separator. Configuration format specifies a template string where @@{tag} (or @@ for short) is replaced with the name of each tag. Configuration separator specifies a piece of code used to join the generated format pieces for different tags.
/*!getstate:re2c[:<name1>[:<name2>...]] ... */ or %{getstate[:<name1>[:<name2>...]] ... %}
A block that generates conditional dispatch on the lexer state (it requires --storable-state option). An optional list of block names specifies which blocks should be included in the state dispatch. The default transition goes to the start label of the first block on the list. If the list is empty, all blocks are included, and the default transition goes to the first block in the file that has a start label. This block type is incompatible with the --loop-switch option, as it requires cross-block transitions that are unsupported without goto or function calls.
/*!conditions:re2c[:<name1>[:<name2>...]] ... */, /*!types:re2c... */ or %{conditions[:<name1>[:<name2>...]] ... %}, %{types... %}
A block that generates condition enumeration (it requires --conditions option). An optional list of block names specifies which blocks should be included when computing the set of conditions (if the list is empty, all blocks are included). By default the generated code is an enumeration YYCONDTYPE. It can be customized with optional configurations format and separator. Configuration format specifies a template string where @@{cond} (or @@ for short) is replaced with the name of each condition, and @@{num} is replaced with a numeric index of that condition. Configuration separator specifies a piece of code used to join the generated format pieces for different conditions.
/*!include:re2c <file> */ or %{include <file> %}
This block allows one to include <file>, which must be a double-quoted file path. The contents of the file are literally substituted in place of the block, in the same way as #include works in C/C++. This block can be used together with the --depfile option to generate build system dependencies on the included files.
/*!header:re2c:on*/ or %{header:on %}
This block marks the start of header file. Everything after it and up to the following header:off block is processed by re2rust and written to the header file specified with -t --type-header option.
/*!header:re2c:off*/ or %{header:off %}
This block marks the end of header file started with header:on*/ block.
/*!ignore:re2c ... */ or %{ignore ... %}
A block which contents are ignored and removed from the output file.

Configurations

Here is a full list of configurations supported by re2rust:

re2c:api, re2c:input
Same as the --api option.
re2c:api:sigil
Specify the marker ("sigil") that is used for argument placeholders in the API primitives. The default is @@. A placeholder starts with sigil followed by the argument name in curly braces. For example, if sigil is set to $, then placeholders will have the form ${name}. Single-argument APIs may use shorthand notation without the name in braces. This option can be overridden by options for individual API primitives, e.g. re2c:YYFILL@len for YYFILL.
re2c:api:style
Specify API style. Possible values are functions (the default for C) and free-form (the default for Go and Rust). In functions style API primitives are generated with an argument list in parentheses following the name of the primitive. The arguments are provided only for autogenerated parameters (such as the number of characters passed to YYFILL), but not for the general lexer context, so the primitives behave more like macros in C/C++ or closures in Go and Rust. In free-form style API primitives do not have a fixed form: they should be defined as strings containing free-form pieces of code with interpolated variables of the form @@{var} or @@ (they correspond to arguments in function-like style). This configuration may be overridden for individual API primitives, see for example re2c:YYFILL:naked configuration for YYFILL.
re2c:bit-vectors, re2c:flags:bit-vectors, re2c:flags:b
Same as the --bit-vectors option, but can be configured on per-block basis.
re2c:captures, re2c:leftmost-captures
Same as the --leftmost-captures option, but can be configured on per-block basis.
re2c:captvars, re2c:leftmost-captvars
Same as the --leftmost-captvars option, but can be configured on per-block basis.
re2c:case-insensitive, re2c:flags:case-insensitive
Same as the --case-insensitive option, but can be configured on per-block basis.
re2c:case-inverted, re2c:flags:case-inverted
Same as the --case-inverted option, but can be configured on per-block basis.
re2c:case-ranges, re2c:flags:case-ranges
Same as the --case-ranges option, but can be configured on per-block basis.
re2c:computed-gotos, re2c:flags:computed-gotos, re2c:flags:g
Same as the --computed-gotos option, but can be configured on per-block basis.
re2c:computed-gotos:relative, re2c:cgoto:relative
Same as the --computed-gotos-relative option, but can be configured on per-block basis.
re2c:computed-gotos:threshold, re2c:cgoto:threshold
If computed goto is used, this configuration specifies the complexity threshold that triggers the generation of jump tables instead of nested if statements and bitmaps. The default value is 9.
re2c:cond:abort
If set to a positive integer value, the default case in the generated condition dispatch aborts program execution.
re2c:cond:goto
Specifies a piece of code used for the autogenerated shortcut rules :=> in conditions. The default is goto @@;. The @@ placeholder is substituted with condition name (see configurations re2c:api:sigil and re2c:cond:goto@cond).
re2c:cond:goto@cond
Specifies the sigil used for argument substitution in re2c:cond:goto definition. The default value is @@. Overrides the more generic re2c:api:sigil configuration.
re2c:cond:divider
Defines the divider for condition blocks. The default value is /* *********************************** */. Placeholders are substituted with condition name (see re2c:api;sigil and re2c:cond:divider@cond).
re2c:cond:divider@cond
Specifies the sigil used for argument substitution in re2c:cond:divider definition. The default is @@. Overrides the more generic re2c:api:sigil configuration.
re2c:cond:prefix,
re2c:condprefix
Spécifie le préfixe utilisé pour les étiquettes de condition. Par défaut, c'est yyc_.
re2c:cond:enumprefix, re2c:condenumprefix
Spécifie le préfixe utilisé pour les identificateurs de condition. Par défaut, c'est yyc.
re2c:debug-output, re2c:flags:debug-output, re2c:flags:d
Identique à l'option --debug-output, mais peut être configuré par bloc.
re2c:empty-class, re2c:flags:empty-class
Identique à l'option --empty-class, mais peut être configuré par bloc.
re2c:encoding:ebcdic, re2c:flags:ecb, re2c:flags:e
Identique à l'option --ebcdic, mais peut être configuré par bloc.
re2c:encoding:ucs2, re2c:flags:wide-chars, re2c:flags:w
Identique à l'option --ucs2, mais peut être configuré par bloc.
re2c:encoding:utf8, re2c:flags:utf-8, re2c:flags:8
Identique à l'option --utf8, mais peut être configuré par bloc.
re2c:encoding:utf16, re2c:flags:utf-16, re2c:flags:x
Identique à l'option --utf16, mais peut être configuré par bloc.
re2c:encoding:utf32, re2c:flags:unicode, re2c:flags:u
Identique à l'option --utf32, mais peut être configuré par bloc.
re2c:encoding-policy, re2c:flags:encoding-policy
Identique à l'option --encoding-policy, mais peut être configuré par bloc.
re2c:eof
Spécifie le symbole sentinelle utilisé avec la règle de fin de fichier $. La valeur par défaut est -1 (la règle $ n'est pas utilisée). D'autres valeurs possibles incluent toutes les unités de code valides. Seuls les nombres décimaux sont reconnus.
re2c:header, re2c:flags:type-header, re2c:flags:t
Spécifie le nom du fichier d'en-tête généré par rapport au répertoire du fichier de sortie. Identique à l'option --header, à l'exception que le chemin du fichier est relatif.
re2c:indent:string
Spécifie la chaîne utilisée pour l'indentation. La valeur par défaut est un seul caractère tabulation "\t". La chaîne d'indentation ne doit contenir que des caractères d'espacement. Pour désactiver complètement l'indentation, définissez cette configuration sur une chaîne vide.
re2c:indent:top
Spécifie le montant minimum d'indentation à utiliser. La valeur par défaut est zéro. La valeur doit être un nombre entier non négatif.
re2c:invert-captures
Identique à l'option --invert-captures, mais peut être configuré par bloc.
re2c:label:prefix, re2c:labelprefix
Spécifie le préfixe utilisé pour les étiquettes d'état du DFA. Par défaut, c'est yy.
re2c:label:start, re2c:startlabel
Contrôle la génération d'une étiquette de début de bloc. La valeur par défaut est zéro, ce qui signifie que l'étiquette de début n'est générée que si elle est utilisée. Une valeur entière supérieure à zéro force la génération de l'étiquette de début même si elle n'est pas utilisée par le lexer. Une valeur de chaîne force également la génération de l'étiquette de début et définit son nom comme la chaîne spécifiée. Cette configuration s'applique uniquement au bloc actuel (elle est réinitialisée à la valeur par défaut pour le bloc suivant).
re2c:label:yyFillLabel
Spécifie le préfixe des étiquettes YYFILL utilisées avec re2c:eof et en mode d'état stockable.
re2c:label:yyloop
Spécifie le nom de l'étiquette marquant le début de la boucle du lexer avec l'option --loop-switch. Par défaut, c'est yyloop.
re2c:label:yyNext
Spécifie le nom de l'étiquette optionnelle qui suit le commutateur YYGETSTATE en mode d'état stockable (activé avec re2c:state:nextlabel). Par défaut, c'est yyNext.
re2c:lookahead, re2c:flags:lookahead
Obsolète (voir l'option obsolète --no-lookahead).
re2c:monadic
Si défini à une valeur non nulle, le lexer généré utilisera la notation monadique (cette configuration est spécifique à Haskell).
re2c:nested-ifs, re2c:flags:nested-ifs, re2c:flags:s
Identique à l'option --nested-ifs, mais peut être configuré par bloc.
re2c:posix-captures, re2c:flags:posix-captures, re2c:flags:P
Identique à l'option --posix-captures, mais peut être configuré par bloc.
re2c:posix-captvars
Identique à l'option --posix-captvars, mais peut être configuré par bloc.
re2c:tags, re2c:flags:tags, re2c:flags:T
Identique à l'option --tags, mais peut être configuré par bloc.
re2c:tags:expression
Spécifie l'expression utilisée pour les variables de tag. Par défaut, re2rust génère des expressions de la forme yyt<N>. Cela peut être peu pratique, par exemple si les variables de tag sont définies comme des champs dans une structure. Toutes les occurrences de @@{tag} ou @@ sont remplacées par le nom réel du tag. Par exemple, re2c:tags:expression = "s.@@"; génère des expressions de la forme s.yyt<N> dans le code généré. Voir également la configuration re2c:api:sigil.
re2c:tags:negative
Spécifie l'expression constante utilisée pour la valeur de tag négative (généralement ce serait -1 si les tags sont des décalages d'entiers dans la chaîne d'entrée, ou un pointeur nul s'il s'agit de pointeurs).
re2c:tags:prefix
Spécifie le préfixe des noms de variables de tag. Par défaut, c'est yyt.
re2c:sentinel
Spécifie le symbole sentinelle utilisé pour les vérifications de fin de fichier (lorsque les vérifications de limites sont désactivées avec re2c:yyfill:enable = 0; et que re2c:eof n'est pas défini). Cette configuration n'affecte pas la génération de code : son objectif est de vérifier que le sentinelle n'est pas autorisé au milieu d'une règle, et de s'assurer que le lexer ne lira pas au-delà de la fin du tampon. La valeur par défaut est -1` (dans ce cas, re2rust suppose que le sentinelle est zéro, ce qui est le cas le plus courant). Seuls les nombres décimaux sont reconnus.
re2c:state:abort
Si défini à une valeur entière positive, le cas par défaut dans la répartition d'état générée arrête l'exécution du programme, et un cas -1 explicite contient une transition vers le début du bloc.
re2c:state:nextlabel
Contrôle si le commutateur YYGETSTATE est suivi d'une étiquette yyNext (la valeur par défaut est zéro, ce qui correspond à aucune étiquette). Alternativement, on peut utiliser re2c:label:start pour générer une étiquette de début spécifique, ou un bloc getstate explicite pour générer le commutateur YYGETSTATE séparément du bloc lexer.
re2c:unsafe, re2c:flags:unsafe
Identique à l'option --no-unsafe, mais peut être configuré par bloc. Si défini à zéro, il supprime la génération de wrappers unsafe autour de YYPEEK. Par défaut, la valeur est non nulle (les wrappers sont générés). Cette configuration est spécifique à Rust.

Expressions rationnelles

re2rust utilise la syntaxe suivante pour les expressions régulières :

"foo"
Littéral de chaîne de caractères sensible à la casse.
'foo'
Littéral de chaîne de caractères insensible à la casse.
[a-xyz], [^a-xyz]
Classe de caractères (potentiellement niée).
.
N'importe quel caractère sauf un saut de ligne.
R \ S
Différence entre les classes de caractères R et S.
R*
Zéro occurrence ou plus de R.
R+
Une occurrence ou plus de R.
R?
R optionnel.
R{n}
Répétition de R exactement n fois.
R{n,}
Répétition de R au moins n fois.
R{n,m}
Répétition de R de n à m fois.
(R)
Juste R ; les parenthèses sont utilisées pour modifier la précédence. Si l'extraction de sous-correspondance est activée, (R) est un groupe capturant ou non capturant en fonction de l'option --invert-captures.
(!R)
Si l'extraction de sous-correspondance est activée, (!R) est un groupe non capturant ou capturant en fonction de l'option --invert-captures.
R S
Concaténation : R suivi de S.
R | S
Alternative : R ou S.
R / S
Lookahead : R suivi de S, mais S n'est pas consommé.
name
Expression régulière définie comme name (ou littéral de chaîne "name" en mode de compatibilité Flex).
{name}
Expression régulière définie comme name en mode de compatibilité Flex.
@stag
Un *s-tag* : sauvegarde la dernière position d'entrée où @stag correspond dans une variable nommée stag.
#mtag
Un *m-tag* : sauvegarde toutes les positions d'entrée où #mtag correspond dans une variable nommée mtag.

Les classes de caractères et les littéraux de chaînes peuvent contenir les séquences d'échappement suivantes : \a, \b, \f, \n, \r, \t, \v, \\, échappements octaux \ooo et échappements hexadécimaux \xhh, \uhhhh et \Uhhhhhhhh.

Actions

Voici une liste des actions prédéfinies prises en charge par re2rust :

!entry code
Une action d'entrée lie un bloc de code défini par l'utilisateur au début de l'état de la machine à états finis actuelle. Si des *conditions de départ* sont utilisées, l'action d'entrée peut être définie individuellement pour chaque condition. Cette action peut être utilisée pour effectuer une initialisation, par exemple pour sauvegarder le début d'un lexème.
!pre_rule code
Une action pré-règle ajoute un bloc de code défini par l'utilisateur au début des actions sémantiques de toutes les règles du bloc actuel (ou condition, si des *conditions de départ* sont utilisées). Cette action peut être utilisée pour factoriser la partie commune de toutes les actions sémantiques (par exemple, sauvegarder la fin d'un lexème).
!post_rule code
Une action post-règle ajoute un bloc de code défini par l'utilisateur à la fin des actions sémantiques de toutes les règles du bloc actuel (ou condition, si des *conditions de départ* sont utilisées). Cette action peut être utilisée pour émettre des instructions de piège qui protègent contre un flux de contrôle involontaire.

Directives

Voici une liste complète des directives prises en charge par re2rust :

!use:name ;
Une directive `use` intra-bloc qui fusionne un bloc de règles précédemment défini avec le nom spécifié dans le bloc actuel. Les définitions nommées, les configurations et les règles du bloc référencé sont ajoutées aux règles actuelles. Les conflits entre des règles et des configurations qui se chevauchent sont résolus de la manière habituelle : la première règle a la priorité, et la dernière configuration remplace les précédentes. Une exception concerne les règles spéciales *, $ et <!> pour lesquelles une définition locale au bloc a toujours la priorité. Une directive `use` peut être placée n'importe où à l'intérieur d'un bloc, et plusieurs directives `use` sont autorisées.
!include file ;
Cette directive est identique au bloc include : elle insère le contenu du fichier verbatim à la place de la directive.

Interface du programme

Le code généré interagit avec le programme externe à l'aide de *primitives*, collectivement appelées *API*. Les primitives qui doivent être définies pour un programme particulier dépendent de plusieurs facteurs, notamment la complexité des expressions régulières, la représentation de l'entrée, la mise en mémoire tampon et l'utilisation de diverses fonctionnalités. Toutes les primitives nécessaires doivent être définies par l'utilisateur sous forme de macros, de fonctions, de variables ou de toute autre forme appropriée qui rend le code généré syntaxiquement et sémantiquement correct. re2rust ne vérifie pas (et ne peut pas vérifier) les définitions, donc si quelque chose manque ou est mal défini, le programme généré peut avoir des erreurs de compilation ou d'exécution. Ce manuel fournit des exemples de définitions d'API dans les cas les plus courants.

re2rust dispose de trois types d'API qui définissent l'ensemble de base des primitives utilisées par un programme :

API Simple
(ajoutée dans la version 4.0) Il s'agit d'une API de base qui peut être activée avec l'option --api simple ou la configuration re2c:api = simple. Elle se compose des primitives suivantes : YYINPUT (qui doit être définie comme une séquence d'unités de code, par exemple une chaîne) et YYCURSOR, YYMARKER, YYCTXMARKER, YYLIMIT (qui doivent être définis comme des indices dans YYINPUT).
API Enregistrement
(ajoutée dans la version 4.0) L'API d'enregistrement est utile dans les cas où l'état de l'analyseur lexical doit être stocké dans une structure. Elle est activée avec l'option --api record ou la configuration re2c:api = record. Cette API se compose d'une variable yyrecord (le nom peut être remplacé par re2c:yyrecord) qui doit être définie comme une structure avec les champs yyinput, yycursor, yymarker, yyctxmarker, yylimit (seuls les champs utilisés par le code généré doivent être définis, et leurs noms peuvent être configurés).
API Générique
C'est l'API la plus flexible et l'API par défaut pour le backend Rust. Cette API contient des primitives pour les opérations génériques : YYPEEK, YYSKIP, YYBACKUP, YYBACKUPCTX, YYSTAGP, YYSTAGN, YYMTAGP, YYMTAGN, YYRESTORE, YYRESTORECTX, YYRESTORETAG, YYSHIFT, YYSHIFTSTAG, YYSHIFTMTAG, YYLESSTHAN. Par exemple, si l'entrée est une tranche d'octets buffer: &[u8], les variables cursor, limit, marker et ctxmarker de type usize représentent les positions d'entrée, et une constante NONE représente une position invalide, alors l'API générique peut être définie comme suit :
/*!re2c
  re2c:YYPEEK       = "*buffer.get_unchecked(cursor)";
  re2c:YYSKIP       = "cursor += 1;";
  re2c:YYBACKUP     = "marker = cursor;";
  re2c:YYRESTORE    = "cursor = marker;";
  re2c:YYBACKUPCTX  = "ctxmarker = cursor;";
  re2c:YYRESTORECTX = "cursor = ctxmarker;";
  re2c:YYRESTORETAG = "cursor = @@{tag};";
  re2c:YYLESSTHAN   = "limit - cursor < @@{len}";
  re2c:YYSTAGP      = "@@{tag} = cursor;";
  re2c:YYSTAGN      = "@@{tag} = NONE;";
  re2c:YYSHIFT      = "cursor = (cursor as isize + @@{shift}) as usize;";
  re2c:YYSHIFTSTAG  = "@@{tag} = (@@{tag} as isize + @@{shift}) as usize;";
*/

Voici une liste complète des primitives d'API qui peuvent être utilisées par le code généré pour interagir avec le programme externe.

YYCTYPE
Le type des caractères d'entrée (unités de code). Pour les codages ASCII, EBCDIC et UTF-8, il doit s'agir d'un entier non signé de 1 octet. Pour UTF-16 ou UCS-2, il doit s'agir d'un entier non signé de 2 octets. Pour UTF-32, il doit s'agir d'un entier non signé de 4 octets.
YYCURSOR
Une l-value qui stocke la position d'entrée actuelle (un pointeur ou un décalage entier dans YYINPUT). Initialement, YYCURSOR doit pointer vers le premier caractère d'entrée, et plus tard, il est avancé par le code généré. Lorsqu'une règle correspond, la position YYCURSOR est celle après le dernier caractère correspondant.
YYLIMIT
Une r-value qui stocke la position de fin d'entrée (un pointeur ou un décalage entier dans YYINPUT). Initialement, YYLIMIT doit pointer vers la position après le dernier caractère d'entrée disponible. Elle n'est pas modifiée par le code généré. L'analyseur lexical compare YYCURSOR à YYLIMIT pour déterminer s'il reste suffisamment de caractères d'entrée.
YYMARKER
Une l-value qui stocke la position de la dernière règle correspondante (un pointeur ou un décalage entier dans YYINPUT). Elle est utilisée pour restaurer la position YYCURSOR si la correspondance la plus longue échoue et que l'analyseur lexical doit revenir en arrière. Aucune initialisation n'est nécessaire.
YYCTXMARKER
Une l-value qui stocke la position
ion du contexte de fin (un pointeur ou un décalage entier dans YYINPUT). Aucune initialisation n'est nécessaire. YYCTXMARKER n'est requis que si l'opérateur de recherche anticipée / est utilisé.
YYFILL
Une primitive d'API générique avec une variable len. YYFILL doit fournir au moins len caractères d'entrée supplémentaires ou échouer. Si re2c:eof est utilisé, alors len est toujours 1 et YYFILL doit toujours retourner à la fonction appelante ; une valeur de retour nulle indique un succès. Si re2c:eof n'est pas utilisé, alors la valeur de retour de YYFILL est ignorée et elle ne doit pas retourner en cas d'échec. La valeur maximale de len est YYMAXFILL.
YYFN
Une primitive qui définit le prototype de fonction dans le modèle de code --recursive-functions. Sa valeur doit être un tableau d'une ou plusieurs chaînes, où chaque chaîne contient deux ou trois composants séparés par la chaîne spécifiée dans la configuration re2c:fn:sep (typiquement un point-virgule). Le premier élément du tableau définit le nom de la fonction et le type de retour (vide pour une fonction void). Les éléments suivants définissent les arguments de la fonction : d'abord, l'expression pour l'argument utilisé dans le corps de la fonction (généralement juste un nom) ; ensuite, le type de l'argument ; enfin, un paramètre formel optionnel (il prend par défaut le premier composant - généralement, l'argument et le paramètre sont le même identifiant).
YYINPUT
Une r-value qui stocke la séquence de caractères d'entrée actuelle (chaîne, tampon, etc.).
YYMAXFILL
Une constante entière égale à la valeur maximale de l'argument de YYFILL. Elle peut être générée avec un bloc max.
YYLESSTHAN
Une primitive d'API générique avec une variable len. Elle doit être définie comme une r-value de type booléen qui est égale à true si et seulement s'il reste moins de len caractères d'entrée.
YYPEEK
Une primitive d'API générique sans variables. Elle doit être définie comme une r-value de type YYCTYPE qui est égale au caractère à la position d'entrée actuelle.
YYSKIP
Une primitive d'API générique qui doit avancer la position d'entrée actuelle d'une unité de code.
YYBACKUP
Une primitive d'API générique qui doit sauvegarder la position d'entrée actuelle (pour être restaurée plus tard avec YYRESTORE).
YYRESTORE
Une primitive d'API générique qui doit restaurer la position d'entrée actuelle à la valeur sauvegardée par YYBACKUP.
YYBACKUPCTX
Une primitive d'API générique qui doit sauvegarder la position d'entrée actuelle comme position du contexte de fin (pour être restaurée plus tard avec YYRESTORECTX).
YYRESTORECTX
Une primitive d'API générique qui doit restaurer la position du contexte de fin sauvegardée avec YYBACKUPCTX.
YYRESTORETAG
Une primitive d'API générique avec une variable tag qui doit restaurer la position du contexte de fin à la valeur de tag.
YYSTAGP
Une primitive d'API générique avec une variable tag, où tag peut être un pointeur ou un décalage dans YYINPUT (voir la section sur l'extraction des sous-correspondances pour plus de détails). YYSTAGP doit définir tag à la position d'entrée actuelle.
YYSTAGN
Une primitive d'API générique avec une variable tag, où tag peut être un pointeur ou un décalage dans YYINPUT (voir la section sur l'extraction des sous-correspondances pour plus de détails). YYSTAGN doit définir tag à une valeur représentant une position d'entrée inexistante.
YYMTAGP
Une primitive d'API générique avec une variable tag. YYMTAGP doit ajouter la position actuelle à l'historique des sous-correspondances de tag (voir la section sur l'extraction des sous-correspondances pour plus de détails.)
YYMTAGN
Une primitive d'API générique avec une variable tag. YYMTAGN doit ajouter une valeur représentant une position d'entrée inexistante à l'historique des sous-correspondances de tag (voir la section sur l'extraction des sous-correspondances pour plus de détails.)
YYSHIFT
Une primitive d'API générique avec une variable shift qui doit décaler la position d'entrée actuelle de shift caractères (la valeur du décalage peut être négative).
YYCOPYSTAG
Une primitive d'API générique avec deux variables, lhs et rhs, qui doit copier la variable s-tag du côté droit rhs dans la variable s-tag du côté gauche lhs. Pour la plupart des langages, cette primitive a une définition par défaut qui assigne lhs à rhs.
YYCOPYMTAG
Une primitive d'API générique avec deux variables, lhs et rhs, qui doit copier la variable m-tag du côté droit rhs dans la variable m-tag du côté gauche lhs. Pour la plupart des langages, cette primitive a une définition par défaut qui assigne lhs à rhs.
YYSHIFTSTAG
Une primitive d'API générique avec deux variables, tag et shift, qui doit décaler tag de shift unités de code (la valeur du décalage peut être négative).
YYSHIFTMTAG
Une primitive d'API générique avec deux variables, tag et shift, qui doit décaler la dernière valeur de l'historique de tag de shift unités de code (la valeur du décalage peut être négative).
YYMAXNMATCH
Une constante entière égale au nombre maximal de groupes de capture POSIX dans une règle. Elle est générée avec un bloc maxnmatch.
YYCONDTYPE
Le type de l'énumération de condition. Il peut être généré soit avec un bloc conditions, soit avec l'option --header.
YYGETACCEPT
Une primitive avec une variable var qui stocke le sélecteur numérique de la règle acceptée. Pour la plupart des langages, cette primitive a une définition par défaut qui lit à partir de var.
YYSETACCEPT
Une primitive avec deux variables : var (une l-value qui stocke le sélecteur numérique de la règle acceptée) et val (la valeur du sélecteur). Pour la plupart des langages, cette primitive a une définition par défaut qui assigne var à val.
YYGETCOND
Une r-value de type YYCONDTYPE qui est égale à l'identifiant de condition actuel.
YYSETCOND
Une primitive avec une variable cond qui doit définir l'identifiant de condition actuel à cond.
YYGETSTATE
Une r-value de type entier qui est égale à l'état actuel du lexer. Elle doit être initialisée à -1.
YYSETSTATE
Une primitive avec une variable state qui doit définir l'état actuel du lexer à state.
YYDEBUG
Cette primitive n'est générée qu'avec l'option -d, --debug-output. Son but est d'ajouter de la journalisation au code généré (une définition YYDEBUG typique est une instruction d'impression). Les instructions YYDEBUG sont générées dans chaque état et ont deux variables : state (soit un index d'état DFA, soit -1) et symbol (le symbole d'entrée actuel).
yyaccept
Une l-value de type entier non signé qui stocke le numéro de la dernière règle correspondante. La définition par l'utilisateur n'est nécessaire qu'avec l'option --storable-state.
yybm
Une table contenant des bitmaps compressées pour jusqu'à 8 transitions (utilisée avec l'option --bitmaps). La table contient 256 éléments et est indexée par des unités de code d'1 octet. Chaque élément de 8 bits combine des valeurs booléennes pour jusqu'à 8 transitions. Le k-ième bit du n-ième élément est vrai si et seulement si la n-ième unité de code est dans la plage de la k-ième transition. L'idée de cette bitmap est de remplacer de nombreuses branches if ou cas switch par une seule vérification d'un seul bit dans la table.
yych
Une l-value de type YYCTYPE qui stocke le caractère d'entrée actuel. La définition par l'utilisateur n'est nécessaire qu'avec l'option -f --storable-state.
yyctable
Table de saut générée pour la répartition initiale des conditions (activée avec la combinaison des options --conditions et --computed-gotos).
yyfill
Une l-value qui stocke le résultat de l'appel YYFILL (cela peut être nécessaire pour les langages purement fonctionnels, où YYFILL est une fonction monadique avec une valeur de retour complexe).
yynmatch
Une l-value de type entier non signé qui stocke le nombre de groupes de capture POSIX dans la règle correspondante. Utilisée uniquement avec l'option -P --posix-captures.
yypmatch
Un tableau de l-values qui sont utilisées pour contenir les valeurs des tags correspondant aux parenthèses de capture dans la règle correspondante. La longueur du tableau doit être au moins yynmatch * 2 (généralement YYMAXNMATCH * 2 est un bon choix). Utilisé uniquement avec l'option -P --posix-captures.
yystable
Obsolète.
yystate
Une l-value utilisée avec l'option --loop-switch pour stocker l'état DFA actuel.
yytarget
Table de sauts qui contient les cibles de sauts (adresses d'étiquettes) pour toutes les transitions d'un état. Cette table est locale à chaque état. La génération des tables yytarget est activée avec l'option --computed-gotos.

Options

Certaines options ont des configurations correspondantes, d'autres sont globales et ne peuvent pas être modifiées après que re2c commence à lire le fichier d'entrée. Les options de débogage nécessitent généralement la compilation de re2c dans une configuration de débogage. Les options internes sont utiles pour expérimenter avec les algorithmes utilisés dans re2c.

-? --help -h
Afficher le message d'aide.
--api <simple | record | generic>
Spécifier l'API utilisée par le code généré pour l'interface avec le code défini par l'utilisateur. L'option simple doit être utilisée dans les cas simples où il n'y a pas besoin de rechargement de tampon et de stockage de l'état du lexer. L'option record doit être utilisée lorsque l'état du lexer doit être stocké dans un enregistrement (struct, classe, etc.). L'option generic doit être utilisée dans les cas complexes où les deux autres API ne sont pas suffisamment flexibles.
--bit-vectors -b
Optimiser les sauts conditionnels à l'aide de masques de bits. Cette option implique --nested-ifs.
--captures, --leftmost-captures
Activer l'extraction des sous-correspondances avec les groupes de capture gourmands de gauche. Le résultat est collecté dans un tableau yybmatch d'une capacité de 2 * YYMAXNMATCH, et yynmatch est défini au nombre de groupes pour la règle de correspondance.
--captvars, --leftmost-captvars
Activer l'extraction des sous-correspondances avec les groupes de capture gourmands de gauche. Le résultat est collecté dans les variables yytl<k>, yytr<k> pour le groupe de capture k.
--case-insensitive
Traiter les chaînes entre apostrophes et guillemets comme insensibles à la casse.
--case-inverted
Inverser la signification des chaînes entre apostrophes et guillemets : traiter les chaînes entre apostrophes comme sensibles à la casse et les chaînes entre guillemets comme insensibles à la casse.
--case-ranges
Réduire les cas consécutifs dans les instructions switch en une plage de la forme low ... high. Cette syntaxe est une extension du langage C/C++ qui est prise en charge par des compilateurs comme GCC, Clang et Tcc. L'avantage principal par rapport à l'utilisation de cas individuels est un code généré plus petit et un temps de génération plus rapide, bien que pour certains compilateurs comme Tcc, cela se traduise également par une taille binaire plus petite.
--computed-gotos -g
Optimiser les sauts conditionnels à l'aide de l'extension non standard "computed goto" (qui doit être prise en charge par le compilateur). re2rust génère des tables de sauts uniquement dans les cas complexes avec de nombreuses branches conditionnelles. Le seuil de complexité peut être configuré avec la configuration cgoto:threshold. Les décalages relatifs peuvent être activés avec la configuration cgoto:relative. Cette option implique --bit-vectors.
--computed-gotos-relative
Similaire à --computed-gotos mais génère des décalages relatifs pour les tables de sauts à la place (ce qui doit être pris en charge par le compilateur). Cette option implique --computed-gotos.
--conditions --start-conditions -c
Activer la prise en charge des "conditions" de type Flex : plusieurs lexers interdépendants au sein d'un même bloc. Il s'agit d'une alternative à la spécification manuelle de différents blocs re2rust connectés par goto ou par des appels de fonction.
--depfile FILE
Écrire les informations de dépendance dans FILE sous la forme d'une règle Makefile <output-file> : <input-file> [include-file ...]. Cela permet de suivre les dépendances de compilation en présence de blocs/directives include, de sorte que la mise à jour des fichiers inclus déclenche la régénération du fichier de sortie. Cette option dépend de l'option --output.
--ebcdic --ecb -e
Générer un lexer qui lit l'entrée en encodage EBCDIC. re2rust suppose que la plage de caractères est 0 -- 0xFF et que la taille des caractères est de 1 octet.
--empty-class <match-empty | match-none | error>
Définir la manière dont re2rust traite les classes de caractères vides. Avec match-empty (par défaut), une classe vide correspond à une entrée vide (ce qui est illogique, mais rétrocompatible). Avec match-none, une classe vide ne correspond jamais. Avec error, une classe vide génère une erreur de compilation.
--encoding-policy <fail | substitute | ignore>
Définir la manière dont re2rust traite les surrogates Unicode. Avec fail, re2rust s'arrête avec une erreur lorsqu'un surrogate est rencontré. Avec substitute, re2rust remplace silencieusement les surrogates par le point de code d'erreur 0xFFFD. Avec ignore (par défaut), re2rust traite les surrogates comme des points de code normaux. La norme Unicode indique que les surrogates autonomes sont invalides, mais les bibliothèques et les programmes du monde réel se comportent différemment.
--flex-syntax -F
Prise en charge partielle de la syntaxe Flex : dans ce mode, les définitions nommées n'ont pas besoin du signe égal et du point-virgule de terminaison, et lorsqu'elles sont utilisées, elles doivent être entourées d'accolades. Les noms sans accolades sont traités comme des chaînes entre guillemets doubles.
--goto-label
Utiliser le modèle de code "goto/label" : encoder le DFA sous forme de blocs de code étiquetés connectés par des transitions goto entre les blocs. Ceci n'est pris en charge que pour les langages qui ont une instruction goto.
--header --type-header -t HEADER
Générer un fichier HEADER. Le contenu du fichier peut être spécifié à l'aide des blocs spéciaux header:on et header:off. Si des conditions sont utilisées, l'en-tête généré aura un énuméré de conditions ajouté automatiquement (sauf s'il y a un bloc conditions explicite).
-I PATH
Ajouter PATH à la liste des emplacements utilisés lors de la recherche de fichiers d'inclusion. Cette option est utile en combinaison avec le bloc ou la directive include. re2rust recherche FILE dans le répertoire du fichier parent et dans les emplacements d'inclusion spécifiés avec l'option -I.
--input <default | custom>
Alias obsolète pour --api. L'option default correspond à simple (c'est en effet le défaut pour la plupart des backends, mais pas pour tous). L'option custom correspond à generic.
--input-encoding <ascii | utf8>
Spécifier la manière dont re2rust analyse les expressions régulières. Avec ascii (par défaut), re2rust traite l'entrée comme encodée en ASCII : toute séquence d'unités de code est une séquence de caractères autonomes d'un octet. Avec utf8, re2rust traite l'entrée comme encodée en UTF8 et reconnaît les caractères multibytes.
--invert-captures
Inverser la signification des groupes de capture et des groupes non capturants. Par défaut, (...) est capturant et (! ...) est non capturant. Avec cette option, (! ...) est capturant et (...) est non capturant.
--lang <none | c | d | go | haskell | java | js | ocaml | python | rust | swift | v | zig>
Spécifier la langue cible. Les langues prises en charge sont C, D, Go, Haskell, Java, JS, OCaml, Python, Rust, Swift, V, Zig (d'autres langues peuvent être ajoutées via des fichiers de syntaxe définis par l'utilisateur, voir l'option --syntax). L'option none désactive les configurations de syntaxe par défaut, de sorte que la langue cible est indéfinie.
--location-format <gnu | msvc>
Spécifier le format de localisation dans les messages. Avec gnu, les localisations sont affichées comme 'filename:line:column: ...'. Avec msvc, les localisations sont affichées comme 'filename(line,column) ...'. Le défaut est gnu.
--loop-switch
Utiliser le modèle de code "loop/switch" : encoder le DFA sous forme d'une boucle sur une instruction switch, où les états individuels sont des cas de switch. L'état est stocké dans une variable yystate. Les transitions entre les états mettent à jour yystate vers l'étiquette du cas de l'état de destination et continuent l'exécution jusqu'à la tête de la boucle.
--nested-ifs -s
Utiliser des instructions if imbriquées au lieu d'instructions switch dans les sauts conditionnels. Cela se traduit généralement par un code plus efficace avec les compilateurs non optimisants.
--no-debug-info -i
Ne pas générer de directives de ligne. Cela peut être utile lorsque le code généré est stocké dans un système de contrôle de version (pour éviter des diffs autogénérés énormes lors de petits changements).
--no-generation-date
Supprimer l'affichage de la date dans le fichier généré.
--no-version
Supprimer l'affichage de la version dans le fichier généré.
--no-unsafe
Ne pas générer d'enveloppe unsafe autour de YYPEEK (cette option est spécifique à Rust). Pour des raisons de performance, YYPEEK doit éviter la vérification des limites, car le lexer effectue déjà des vérifications de fin d'entrée de manière plus efficace. L'utilisateur peut choisir de fournir une définition YYPEEK sûre, ou une définition qui n'est dangereuse que dans les builds de production, auquel cas l'option --no-unsafe aide à éviter les avertissements concernant des blocs unsafe redondants.
--output -o OUTPUT
Spécifier le fichier OUTPUT.
--posix-captures, -P
Activer l'extraction de sous-correspondances avec des groupes de capture de style POSIX. Le résultat est collecté dans un tableau yybmatch de capacité 2 * YYMAXNMATCH, et yynmatch est défini sur le nombre de groupes pour la règle correspondante.
--posix-captvars
Activer l'extraction de sous-correspondances avec des groupes de capture de style POSIX. Le résultat est collecté dans les variables yytl<k>, yytr<k> pour le k-ième groupe de capture.
--recursive-functions
Utiliser un modèle de code basé sur des fonctions co-récursives, où chaque état de DFA est une fonction distincte qui peut appeler d'autres fonctions d'état ou elle-même.
--reusable -r
Obsolète depuis la version 2.2 (les blocs réutilisables sont autorisés par défaut maintenant).
--skeleton -S
Ignorer le code d'interface défini par l'utilisateur et générer un programme "squelette" autonome. De plus, générer des fichiers d'entrée avec des chaînes dérivées de la grammaire régulière et des résultats de correspondance compressés qui sont utilisés pour vérifier le comportement du "squelette" sur toutes les entrées. Cette option est utile pour trouver des bugs dans les optimisations et la génération de code. Cette option n'est prise en charge que pour C.
--storable-state -f
Générer un lexer capable de stocker son état interne. Ceci est utile pour les lexers de type push-model qui sont arrêtés par un programme externe lorsqu'il n'y a pas assez d'entrée, et sont ensuite repris lorsqu'une entrée supplémentaire devient disponible. Dans ce mode, les utilisateurs doivent en plus définir les primitives YYGETSTATE et YYSETSTATE, et les variables yych, yyaccept et state doivent faire partie de l'état stocké du lexer.
--syntax FILE
Charger les configurations du FILE spécifié et les appliquer par-dessus le fichier de syntaxe par défaut. Notez que FILE peut définir seulement quelques configurations (s'il est utilisé pour modifier le fichier de syntaxe par défaut), ou il peut définir un backend de langage entièrement nouveau (dans ce dernier cas, il est recommandé d'utiliser l'option --lang none).
--tags -T
Activer l'extraction de sous-correspondances avec des balises.
--ucs2 --wide-chars -w
Générer un lexer qui lit des entrées encodées en UCS2. re2rust suppose que la plage de caractères est 0 -- 0xFFFF et que la taille des caractères est de 2 octets. Cette option implique --nested-ifs.
--utf8 --utf-8 -8
Générer un lexer qui lit des entrées en encodage UTF-8. re2rust suppose que la plage de caractères est 0 -- 0x10FFFF et que la taille des caractères est de 1 octet.
--utf16 --utf-16 -x
Générer un lexer qui lit des entrées encodées en UTF16. re2rust suppose que la plage de caractères est 0 -- 0x10FFFF et que la taille des caractères est de 2 octets. Cette option implique --nested-ifs.
--utf32 --unicode -u
Générer un lexer qui lit des entrées encodées en UTF32. re2rust suppose que la plage de caractères est 0 -- 0x10FFFF et que la taille des caractères est de 4 octets. Cette option implique --nested-ifs.
--verbose
Afficher un court message en cas de succès.
--vernum -V
Afficher les informations de version au format MMmmpp (majeur, mineur, correctif).
--version -v
Afficher les informations de version.
--single-pass -1
Obsolète. Ne fait rien (le passage unique est le comportement par défaut maintenant).
--debug-output -d
Émettre des invocations YYDEBUG dans le code généré. Ceci est utile pour tracer l'exécution du lexer.
--dump-adfa
Option de débogage : afficher le DFA après le tunneling (au format .dot).
--dump-cfg
Option de débogage : afficher le graphe de flot de contrôle des variables de balises (au format .dot).
--dump-closure-stats
Option de débogage : afficher les statistiques sur le nombre d'états dans la fermeture.
--dump-dfa-det
Option de débogage : afficher le DFA immédiatement après la détermisation (au format .dot).
--dump-dfa-min
Option de débogage : afficher le DFA après minimisation (au format .dot).
--dump-dfa-tagopt
Option de débogage : afficher le DFA après optimisation des balises (au format .dot).
--dump-dfa-tree
Option de débogage : afficher le DFA en cours de construction avec les états représentés par des arbres d'historique de balises (au format .dot).
--dump-dfa-raw
Option de débogage : afficher le DFA en cours de construction avec des ensembles d'états développés (au format .dot).
--dump-interf
Option de débogage : afficher le tableau d'interférence produit par l'analyse de vivacité des variables de balises.
--dump-nfa
Option de débogage : afficher le NFA (au format .dot).
--emit-dot -D
Au lieu de la sortie normale, générer le graphe du lexer au format .dot. La sortie peut être convertie en image à l'aide de Graphviz (par exemple, quelque chose comme dot -Tpng -odfa.png dfa.dot).
--dfa-minimization <moore | table>
Option interne : algorithme de minimisation de DFA utilisé par re2rust. L'option moore est l'algorithme de Moore (c'est le comportement par défaut). L'option table est l'algorithme de "remplissage de table". Les deux algorithmes devraient produire le même DFA à des étiquetages d'états près ; le remplissage de table est plus simple et beaucoup plus lent, et sert d'implémentation de référence.
--eager-skip
Option interne : faire avancer le lexer généré dans la position d'entrée avec empressement -- immédiatement après la lecture du symbole d'entrée. Cela modifie le comportement par défaut où la position d'entrée est avancée avec réticence -- après la transition vers le nouvel état.
--no-lookahead
Option interne, obsolète. Elle activait auparavant l'algorithme TDFA(0). Contrairement à TDFA(1), l'algorithme TDFA(0) n'utilise pas d'anticipation d'un symbole. Il applique des opérations de registre aux transitions entrantes plutôt qu'aux sortantes. Les benchmarks ont montré que l'algorithme TDFA(0) est moins efficace que TDFA(1).
--no-optimize-tags
Option interne : supprimer l'optimisation des variables de balises (utile pour le débogage).
--posix-closure <gor1 | gtop>
Option interne : spécifier l'algorithme de plus court chemin utilisé pour la construction de la fermeture epsilon avec des sémantiques de désambiguïsation POSIX : gor1 (le défaut) représente l'algorithme de Goldberg-Radzik, et gtop représente l'algorithme de "l'ordre topologique global".
--posix-prectable <complex | naive>
Option interne : spécifier l'algorithme utilisé pour calculer la table de précédence POSIX. L'algorithme complex calcule la table de précédence en un seul parcours de l'arbre d'historique des balises et a une complexité quadratique par rapport au nombre d'états TNFA ; c'est le comportement par défaut. L'algorithme naive a une complexité cubique dans le pire des cas par rapport au nombre d'états TNFA, mais il est beaucoup plus simple que complex et peut être légèrement plus rapide dans des cas non pathologiques.
--stadfa
Option interne, obsolète. Elle activait auparavant l'algorithme staDFA, qui diffère de TDFA par le placement des opérations de registre dans les états plutôt que sur les transitions. Les benchmarks ont montré que l'algorithme staDFA est moins efficace que TDFA.
--fixed-tags <none | toplevel | all>
Option interne : spécifier si l'optimisation des balises fixes doit être appliquée à toutes les balises (all), à aucune d'entre elles (none), ou seulement à celles dans la concaténation de niveau supérieur (toplevel). Le comportement par défaut est all. Les balises "fixes" sont celles qui sont situées à une distance fixe d'une autre balise (appelée "base"). Dans de tels cas, seule la balise de base doit être suivie, et la valeur de la balise fixe peut être calculée comme la valeur de la balise de base plus un décalage statique. Pour les balises qui se trouvent sous une alternative ou une répétition, il est également nécessaire de vérifier si la balise de base a une valeur de non-correspondance (dans ce cas, la balise fixe devrait également être définie sur non-correspondance, ignorant le décalage). Pour les balises dans la concaténation de niveau supérieur, la vérification n'est pas nécessaire, car elles correspondent toujours.

Avertissements

Les avertissements peuvent être activés, désactivés et transformés en erreurs individuellement.

-W
Activer tous les avertissements.
-Werror
Transformer les avertissements en erreurs. Notez que cette option seule n'active aucun avertissement ; elle affecte seulement les avertissements qui ont été activés jusqu'à présent ou qui seront activés plus tard.
-W<warning>
Activer l'avertissement warning.
-Wno-<warning>
Désactiver l'avertissement warning.
-Werror-<warning>
Activer l'avertissement warning et le traiter comme une erreur (ceci implique -W<warning>).
-Wno-error-<warning>
Ne pas traiter cet avertissement particulier comme une erreur. Ceci ne désactive pas l'avertissement lui-même.
-Wcondition-order
Avertissement si le programme généré fait des suppositions implicites sur le numérotage des conditions. Il faut utiliser soit l'option --header, soit le bloc conditions pour générer une correspondance entre les noms de conditions et leurs numéros, puis utiliser les noms de conditions auto-générés.
-Wempty-character-class
Avertissement si une expression régulière contient une classe de caractères vide. Essayer de faire correspondre une classe de caractères vide n'a aucun sens : cela devrait toujours échouer. Cependant, pour des raisons de compatibilité descendante, re2rust autorise les classes de caractères vides et les traite comme des chaînes vides. Utilisez l'option --empty-class pour modifier le comportement par défaut.
-Wmatch-empty-string
Avertissement si une règle est nulle (correspond à une chaîne vide). Si le lexer s'exécute en boucle et que la correspondance vide est involontaire, le lexer peut rester bloqué de manière inattendue dans une boucle infinie.
-Wswapped-range
Avertissement si la borne inférieure d'une plage est supérieure à sa borne supérieure. Le comportement par défaut consiste à échanger silencieusement les bornes de la plage.
-Wundefined-control-flow
Avertissement si certaines chaînes d'entrée provoquent un flux de contrôle indéfini dans le lexer (les motifs défectueux sont signalés). C'est une erreur dangereuse et courante. Elle peut être facilement corrigée en ajoutant la règle par défaut * qui a la priorité la plus basse, correspond à n'importe quelle unité de code, et consomme toujours une seule unité de code.
-Wunreachable-rules
Avertissement concernant les règles qui sont masquées par d'autres règles et qui ne correspondront jamais.
-Wdeprecated-eof_rule
Avertissement concernant les règles de fin de fichier autonomes $ qui seront rompues par les changements futurs et nécessiteront une correction. À l'heure actuelle, ces règles ont la priorité lorsqu'elles entrent en conflit avec d'autres règles, mais après l'introduction du symbole de fin de fichier généralisé $, l'ordre de priorité changera et ces règles seront masquées par d'autres règles.
-Wuseless-escape
Avertissement si un symbole est échappé alors qu'il ne devrait pas l'être. Par défaut, re2rust ignore silencieusement de tels échappements, mais cela peut aussi indiquer une faute de frappe ou une erreur dans la séquence d'échappement.
-Wnondeterministic-tags
Avertissement si une balise a un degré de non-déterminisme de n, où n est supérieur à 1.
-Wsentinel-in-midrule
Avertissement si le symbole sentinelle se produit au milieu d'une règle --- cela peut entraîner des lectures au-delà de la fin du tampon, des plantages ou une corruption de mémoire dans le lexer généré. Cet avertissement n'est applicable que si la méthode sentinelle de vérification de la fin de l'entrée est utilisée. Il est défini comme une erreur si la configuration re2c:sentinel est utilisée.
-Wundefined-syntax-config
Avertissement si le fichier de syntaxe spécifié avec l'option --syntax manque de définitions de certaines configurations. Cela permet de maintenir les fichiers de syntaxe définis par l'utilisateur : si une nouvelle version ajoute des configurations, un ancien fichier de syntaxe déclenchera un avertissement, et l'utilisateur sera notifié. Si certaines configurations ne sont pas utilisées et n'ont pas besoin de définition, elles doivent être explicitement définies sur <undefined>.

Fichiers de syntaxe

Le support des différents langages dans re2c repose sur l'idée de fichiers de syntaxe. Un fichier de syntaxe est un fichier de configuration qui définit la syntaxe du langage cible -- pas tout le langage, mais une petite partie de celui-ci qui est utilisée par le code généré. Les fichiers de syntaxe rendent re2c très flexible, mais ils ne doivent pas être utilisés comme un remplacement pour les configurations re2c: : leur but est de définir la syntaxe du langage cible, et non de personnaliser un lexer particulier. Tous les langages supportés ont des fichiers de syntaxe par défaut qui font partie de la distribution (voir le sous-répertoire include/syntax); ils sont également intégrés dans le binaire re2rust. Les utilisateurs peuvent fournir un fichier de syntaxe personnalisé qui remplace quelques configurations pour l'un des langages supportés, ou ils peuvent choisir de redéfinir toutes les configurations (dans ce cas, l'option --lang none devrait être utilisée). Les fichiers de syntaxe contiennent des configurations de quatre types différents : listes de fonctionnalités, configurations de langage, configurations in-place et modèles de code.

Listes de fonctionnalités

Quelques configurations de liste définissent diverses fonctionnalités supportées par un backend donné, afin que re2rust puisse générer une erreur claire si l'utilisateur essaie d'activer une fonctionnalité non supportée :
supported_apis
Une liste des API supportées avec des éléments possibles simple, record, generic.
supported_api_styles
Une liste des styles d'API supportés avec des éléments possibles functions, free-form.
supported_code_models
Une liste des modèles de code supportés avec des éléments possibles goto-label, loop-switch, recursive-functions.
supported_targets
Une liste des cibles de génération de code supportées avec des éléments possibles code, dot, skeleton.
supported_features
Une liste des fonctionnalités supportées avec des éléments possibles nested-ifs, bitmaps, computed-gotos, case-ranges, monadic, unsafe, tags, captures, captvars.

Configurations de langage

Quelques configurations booléennes décrivent les fonctionnalités du langage cible qui affectent le parseur et le générateur de code de re2rust :
semicolons
Non nul si le langage utilise des points-virgules après les instructions.
backtick_quoted_strings
Non nul si le langage a des chaînes entre guillemets inversés.
single_quoted_strings
Non nul si le langage a des chaînes entre guillemets simples.
indentation_sensitive
Non nul si le langage est sensible à l'indentation.
wrap_blocks_in_braces
Non nul si les instructions composées doivent être entourées d'accolades.

Configurations in-place

Les fichiers de syntaxe définissent les valeurs initiales de toutes les configurations re2c:, car elles peuvent différer pour différents langages. Voir la section configurations pour une liste complète de toutes les configurations in-place et leur signification.

Modèles de code

Les modèles de code définissent la syntaxe du langage cible. Ils sont écrits dans un langage simple spécifique au domaine avec la grammaire formelle suivante : 
code-template ::
      name '=' code-exprs ';'
    | CODE_TEMPLATE ';'
    | '<undefined>' ';'
code-exprs ::
      <EMPTY>
    | code-exprs code-expr
code-expr ::
      STRING
    | VARIABLE
    | optional
    | list
optional ::
      '(' CONDITIONAL '?' code-exprs ')'
    | '(' CONDITIONAL '?' code-exprs ':' code-exprs ')'
list ::
      '[' VARIABLE ':' code-exprs ']'
    | '[' VARIABLE '{' NUMBER '}' ':' code-exprs ']'
    | '[' VARIABLE '{' NUMBER ',' NUMBER '}' ':' code-exprs ']'

Un modèle de code est une séquence de littéraux de chaîne, de variables, d'éléments optionnels et de listes, ou une référence à un autre modèle de code, ou une valeur spéciale <undefined>. Les variables sont des espaces réservés qui sont substitués pendant la phase de génération de code. Les variables de liste sont spéciales : lors de l'expansion des modèles de liste, re2rust répète les expressions du côté droit de la colonne plusieurs fois, remplaçant à chaque fois les occurrences de la variable de liste par une valeur spécifique à cette répétition. Les listes ont des limites optionnelles (les valeurs négatives sont comptées à partir de la fin, par exemple -1 signifie le dernier élément). Les noms conditionnels commencent par un point. Les conditionnels et les variables peuvent être locaux (spécifiques au modèle de code donné) ou globaux (autorisés dans tous les modèles de code). Lorsque re2rust lit le fichier de syntaxe, il vérifie que chaque modèle de code n'utilise que les variables et les conditionnels qui y sont autorisés.

Par exemple, le modèle de code suivant définit la construction if-then-else pour un langage de type C :

code:if_then_else =
    [branch{0}: topindent "if " cond " {" nl
        indent [stmt: stmt] dedent]
    [branch{1:-1}: topindent "} else" (.cond ? " if " cond) " {" nl
        indent [stmt: stmt] dedent]
    topindent "}" nl;

Ici, branch est une variable de liste : branch{0} s'étend à la première branche (qui est spéciale, car il n'y a pas de partie else), branch{1:-1} s'étend à toutes les branches restantes (s'il y en a). stmt est également une variable de liste : [stmt: stmt] est une liste imbriquée qui s'étend à une liste d'instructions dans le corps de la branche actuelle. topindent, indent, dedent et nl sont des variables globales, et .cond est un conditionnel local (leur signification est décrite ci-dessous). Ce modèle de code pourrait produire le code suivant :

if x {
    // do something
} else if y {
    // do something else
} else {
    // don't do anything
}

GESTION DE LA FIN DE LA SAISIE

L'un des principaux problèmes pour le lexer est de savoir quand s'arrêter. Il existe quelques conditions de terminaison :

  • le lexer peut correspondre à une règle (y compris la règle par défaut *) et arriver à un état final
  • le lexer peut ne pas correspondre à aucune règle et arriver à un état par défaut
  • le lexer peut atteindre la fin de la saisie

Les deux premières conditions terminent le lexer de manière "naturelle" : il arrive à un état sans transitions sortantes, et la correspondance s'arrête automatiquement. La troisième condition, la fin de la saisie, est différente : elle peut survenir dans n'importe quel état, et le lexer doit pouvoir la gérer. La vérification de la fin de la saisie interrompt le flux de travail normal du lexer et ajoute des branches conditionnelles au programme généré, il est donc nécessaire de minimiser le nombre de ces vérifications. re2rust prend en charge plusieurs méthodes pour gérer la fin de la saisie. Laquelle utiliser dépend de la complexité des expressions régulières, du besoin de mise en tampon, des considérations de performance et d'autres facteurs. Voici une liste des méthodes :

  • Sentinelle. Cette méthode élimine complètement la nécessité de vérifier la fin de la saisie. Elle est simple et efficace, mais limitée au cas où il existe un caractère "sentinelle" naturel qui ne peut jamais apparaître dans une saisie valide. Ce caractère peut toujours apparaître dans une saisie invalide, mais il ne devrait pas être autorisé par les expressions régulières, sauf peut-être comme dernier caractère d'une règle. La sentinelle est ajoutée à la fin de la saisie et sert de signal d'arrêt : lorsque le lexer lit ce caractère, il s'agit soit d'une erreur de syntaxe, soit de la fin de la saisie. Dans les deux cas, le lexer doit s'arrêter. Cette méthode est utilisée si YYFILL est désactivé avec re2c:yyfill:enable = 0; et si re2c:eof a la valeur par défaut -1.
  • Sentinelle avec vérifications de limites. Cette méthode est générique : elle permet de gérer n'importe quelle saisie sans restriction sur les expressions régulières. L'idée est de réduire le nombre de vérifications de fin de saisie en ne les effectuant que sur certains caractères. Similaire à la méthode "sentinelle", l'un des caractères est choisi comme "sentinelle" et ajouté à la fin de la saisie. Cependant, il n'y a aucune restriction sur l'endroit où la sentinelle peut apparaître (en fait, n'importe quel caractère peut être choisi pour une sentinelle). Lorsque le lexer lit ce caractère, il effectue en plus une vérification de limites. Si la position actuelle est dans les limites, le lexer reprend la correspondance et traite la sentinelle comme un caractère normal. Sinon, il appelle YYFILL (sauf si elle est désactivée). Si plus de saisie est fournie, le lexer rematchera le dernier caractère et continuera comme si la sentinelle n'était pas là. Sinon, ce doit être la vraie fin de la saisie, et le lexer s'arrête. Cette méthode est utilisée lorsque re2c:eof a une valeur non négative (elle doit être définie sur la valeur numérique de la sentinelle). YYFILL est facultatif.
  • Vérifications de limites avec remplissage. Cette méthode est générique et peut être plus rapide que la méthode "sentinelle avec vérifications de limites", mais elle est aussi plus complexe. L'idée est de partitionner les états du DFA en composants fortement connectés (SCC) et de générer une seule vérification par SCC pour suffisamment de caractères afin de couvrir le chemin non cyclique le plus long dans ce SCC. Cela réduit le nombre de vérifications, mais il y a un problème avec les lexèmes courts en fin de saisie, car la vérification nécessite suffisamment de caractères pour couvrir le lexème le plus long. Cela peut être corrigé en remplissant la saisie avec quelques caractères fictifs qui ne forment pas un suffixe de lexème valide (de sorte que le lexer ne puisse pas les faire correspondre). La longueur du remplissage doit être YYMAXFILL, générée avec un bloc max. S'il n'y a pas assez de saisie, le lexer appelle YYFILL qui devrait fournir au moins le nombre de caractères requis ou ne pas revenir. Cette méthode est utilisée si YYFILL est activé et que re2c:eof est -1 (c'est la configuration par défaut).
  • Vérifications personnalisées. L'API générique permet de remplacer les opérations de base comme la lecture d'un caractère, ce qui rend possible d'inclure les vérifications de fin de saisie dans celles-ci. Cette approche est sujette aux erreurs et doit être utilisée avec prudence. Pour utiliser une méthode personnalisée, activez l'API générique avec --api custom ou re2c:api = custom; et désactivez les vérifications de limites par défaut avec re2c:yyfill:enable = 0; ou re2c:yyfill:check = 0;.

Sentinelle

Cet exemple utilise un caractère sentinelle pour gérer la fin de la saisie. Le programme compte les mots séparés par des espaces dans une chaîne terminée par un caractère nul. La sentinelle est le caractère nul : c'est le dernier caractère de chaque chaîne d'entrée, et il n'est autorisé dans le milieu d'un lexème par aucune des règles (en particulier, il n'est pas inclus dans les plages de caractères où il est facile de l'oublier). Si un caractère nul apparaît au milieu d'une chaîne, il s'agit d'une erreur de syntaxe et le lexer fera correspondre la règle par défaut *, mais il ne lira pas au-delà de la fin de la saisie et ne planterait pas (utilisez l'avertissement -Wsentinel-in-midrule et la configuration re2c:sentinel pour vérifier cela). La configuration re2c:yyfill:enable = 0; supprime la génération des vérifications de limites et des appels à YYFILL.

// re2rust $INPUT -o $OUTPUT --api simple
fn lex(yyinput: &[u8]) -> isize {
    // L'entrée doit être terminée par un caractère nul, sinon la fonction a un comportement indéfini.
    assert_eq!(yyinput.last(), Some(&0));
    let mut yycursor = 0;
    let mut count = 0;

Sentinelle avec vérifications de limites

Cet exemple utilise la sentinelle avec vérifications de limites pour gérer la fin de la saisie (cette méthode a été ajoutée dans la version 1.2). Le programme compte les chaînes d'un seul guillemet séparées par des espaces. Le caractère sentinelle est le caractère nul, spécifié avec la configuration re2c:eof = 0;. Comme dans la méthode sentinel, le caractère nul est le dernier caractère de chaque chaîne d'entrée, mais il est autorisé au milieu d'une règle (par exemple, 'aaa\0aa'\0 est une saisie valide, mais 'aaa\0 est une erreur de syntaxe). Des vérifications de limites sont générées dans chaque état qui correspond à un caractère d'entrée, mais elles sont limitées à la branche qui gère le caractère nul. Les vérifications de limites sont de la forme YYLIMIT <= YYCURSOR ou YYLESSTHAN(1) avec l'API générique. Si la condition de vérification est vraie, le lexer a

atteint la fin de l'entrée et doit s'arrêter (YYFILL est désactivé avec re2c:yyfill:enable = 0; car l'entrée tient dans un seul tampon, voir la section YYFILL avec sentinelle pour un exemple qui utilise YYFILL). Atteindre la fin de l'entrée ouvre trois possibilités : si le lexer est dans l'état initial, il correspondra à la règle de fin d'entrée $, sinon il peut se rabattre sur une règle précédemment correspondante (y compris la règle par défaut *) ou aller à un état par défaut, provoquant -Wundefined-control-flow.

// re2rust $INPUT -o $OUTPUT --api simple
fn lex(yyinput: &[u8]) -> isize {
    // L'entrée doit être terminée par un caractère nul, sinon la fonction a un comportement indéfini.
    assert_eq!(yyinput.last(), Some(&0));
    let (mut yycursor, mut yymarker) = (0, 0);
    let yylimit = yyinput.len() - 1; // terminateur nul non inclus
    let mut count = 0;
    'lex: loop { /*!re2c
        re2c:YYCTYPE = u8;
        re2c:yyfill:enable = 0;
        re2c:eof = 0;
        str = ['] ([^'\\] | [\\][^])* ['];
        *    { return -1; }
        $    { return count; }
        str  { count += 1; continue 'lex; }
        [ ]+ { continue 'lex; }
    */}
}
fn main() {
    assert_eq!(lex(b"\0"), 0);
    assert_eq!(lex(b"'qu\0tes' 'are' 'fine: \\'' \0"), 3);
    assert_eq!(lex(b"'unterminated\\'\0"), -1);
}

Vérifications des limites avec remplissage

Cet exemple utilise des vérifications de limites avec remplissage pour gérer la fin de l'entrée (cette méthode est activée par défaut). Le programme compte les chaînes de caractères entre apostrophes séparées par des espaces. Il y a un remplissage de YYMAXFILL caractères nuls ajoutés à la fin de l'entrée, où la valeur de YYMAXFILL est auto-générée avec un bloc max. Il n'est pas nécessaire d'utiliser des zéros pour le remplissage --- n'importe quels caractères peuvent être utilisés tant qu'ils ne forment pas un suffixe de lexème valide (dans cet exemple, le remplissage ne doit pas contenir d'apostrophes, car elles pourraient être confondues avec un suffixe d'une chaîne entre apostrophes). Il y a une règle "stop" qui correspond au premier caractère de remplissage (zéro) et termine le lexer (notez qu'il vérifie si le zéro est au début du remplissage, sinon c'est une erreur de syntaxe). Les vérifications de limites sont générées uniquement dans certains états déterminés par les composantes fortement connexes de l'automate sous-jacent. Les vérifications ont la forme (YYLIMIT - YYCURSOR) < n ou YYLESSTHAN(n) avec l'API générique, où n est le nombre minimum de caractères nécessaires au lexer pour continuer (cela signifie également que la prochaine vérification de limite se produira dans au plus n caractères). Si la condition de vérification est vraie, le lexer a atteint la fin de l'entrée et appellera YYFILL(n) qui devrait soit fournir au moins n caractères d'entrée, soit ne pas retourner. Dans cet exemple, YYFILL échoue toujours et termine le lexer avec une erreur (ce qui est acceptable car l'entrée tient dans un seul tampon). Voir la section YYFILL avec remplissage pour un exemple qui recharge le tampon d'entrée avec YYFILL.

// re2rust $INPUT -o $OUTPUT --api simple
/*!max:re2c*/
fn lex(s: &[u8]) -> isize {
    let mut count = 0;
    let mut yycursor = 0;
    let yylimit = s.len() + YYMAXFILL;
    // Copie la chaîne dans un tampon et ajoute un remplissage de zéros YYMAXFILL.
    let mut yyinput = Vec::with_capacity(yylimit);
    yyinput.extend_from_slice(s);
    yyinput.extend([0 as u8; YYMAXFILL]);
    'lex: loop { /*!re2c
        re2c:YYCTYPE = u8;
        re2c:YYFILL = "return -1;";
        str = ['] ([^'\\] | [\\][^])* ['];
        [\x00] {
            // Vérifie qu'il s'agit du sentinelle, pas d'un zéro inattendu.
            return if yycursor == s.len() + 1 { count } else { -1 }
        }
        str  { count += 1; continue 'lex; }
        [ ]+ { continue 'lex; }
        *    { return -1; }
    */}
}
fn main() {
    assert_eq!(lex(b""), 0);
    assert_eq!(lex(b"'qu\0tes' 'are' 'fine: \\'' "), 3);
    assert_eq!(lex(b"'unterminated\\'"), -1);
    assert_eq!(lex(b"'unexpected \0 null"), -1);
}

RECHARGE DU TAMPON

Le besoin de mise en mémoire tampon survient lorsque l'entrée ne peut pas être mappée entièrement en mémoire : soit elle est trop grande, soit elle provient d'un flux (comme la lecture depuis un socket). La technique habituelle dans de tels cas consiste à allouer un tampon de mémoire de taille fixe et à traiter l'entrée par morceaux qui tiennent dans le tampon. Lorsque le morceau courant est traité, il est déplacé et de nouvelles données sont chargées. En pratique, c'est un peu plus complexe, car l'état du lexer ne consiste pas en une seule position d'entrée, mais en un ensemble de positions interdépendantes :

  • curseur : le prochain caractère d'entrée à lire (YYCURSOR dans l'API pointeur C ou YYSKIP/YYPEEK dans l'API générique)
  • limite : la position après le dernier caractère d'entrée disponible (YYLIMIT dans l'API pointeur C, géré implicitement par YYLESSTHAN dans l'API générique)
  • marqueur : la position de la correspondance la plus récente, le cas échéant (YYMARKER dans l'API par défaut ou YYBACKUP/YYRESTORE dans l'API générique)
  • token : le début du lexème courant (implicite dans l'API re2rust, car il n'est pas nécessaire pour le fonctionnement normal du lexer et peut être défini et mis à jour par l'utilisateur)
  • marqueur de contexte : la position du contexte de traînée (YYCTXMARKER dans l'API pointeur C ou YYBACKUPCTX/YYRESTORECTX dans l'API générique)
  • variables de balise : positions de sous-correspondance (définies avec les blocs stags et mtags et les primitives de l'API générique YYSTAGP/YYSTAGN/YYMTAGP/YYMTAGN)

Toutes ces positions ne sont pas utilisées dans tous les cas, mais si elles le sont, elles doivent être mises à jour par YYFILL. Toutes les positions actives sont contenues dans le segment entre le token et le curseur, donc tout ce qui se trouve entre le début du tampon et le token peut être rejeté, le segment du token jusqu'à la limite doit être déplacé au début du tampon, et l'espace libre à la fin du tampon doit être rempli avec de nouvelles données. Afin d'éviter des appels fréquents à YYFILL, il est préférable de charger autant de caractères d'entrée que possible (même si moins de caractères pourraient suffire à reprendre le lexer). Les détails de l'implémentation de YYFILL varient légèrement en fonction de la méthode de gestion de la fin de fichier utilisée : le cas de la règle EOF est quelque peu plus simple que le cas de la vérification des limites avec remplissage. Notez également que si l'option -f --storable-state est utilisée, YYFILL a une sémantique légèrement différente (décrite dans la section sur l'état stockable).

YYFILL avec sentinelle

Si la règle EOF est utilisée, YYFILL est une primitive de type fonction qui n'accepte aucun argument et retourne une valeur qui est vérifiée par rapport à zéro. L'invocation de YYFILL est déclenchée par la condition YYLIMIT <= YYCURSOR dans l'API pointeur C et YYLESSTHAN() dans l'API générique. Une valeur de retour non nulle signifie que YYFILL a échoué. Un appel réussi à YYFILL doit fournir au moins un caractère et ajuster les positions d'entrée en conséquence. La limite doit toujours être définie à un après la dernière position d'entrée dans le tampon, et le caractère à la position limite doit être le symbole sentinelle spécifié par la configuration re2c:eof. use std::fs::File;
use std::io::{Read, Write};
use std::path::Path;

const BUFSIZE: usize = 4096;
// Add padding for YYFILL. If we need N characters, we can have at most
// BUFSIZE - N available. YYMAXFILL is the maximum number of characters
// YYFILL can be asked for.
const YYMAXFILL: usize = 16;

// lexer state
struct State {
    file: File,
    // buffer holding the input data
    yyinput: [u8; BUFSIZE],
    // end of input data in buffer
    yylimit: usize,
    // current position in buffer
    yycursor: usize,
    // position of the last match
    yymarker: usize,
    // start of the current token
    token: usize,
    // end of file flag
    eof: bool,
}

// Fill buffer with new input data.
// `need` is the minimum number of characters that must be read.
#[derive(PartialEq)]
enum Fill {
    Ok,
    Eof,
    LongLexeme, // the input 'lexeme' is too long for the buffer
}

fn fill(st: &mut State, need: usize) -> Fill {
    if st.eof {
        return Fill::Eof;
    }
    // Error: lexeme too long. In real life can reallocate a larger buffer.
    // The current token starts at `st.token`. If the cursor `st.yycursor` is
    // less than `need` characters away from the token start, it means that
    // the lexeme is too long to fit in the buffer even after shifting.
    if st.token < need {
        return Fill::LongLexeme;
    }

    // Shift buffer contents (discard everything up to the current token).
    // The contents from `st.token` to `st.yylimit` are moved to the beginning
    // of the buffer.
    st.yyinput.copy_within(st.token..st.yylimit, 0);
    // Adjust `yylimit`, `yycursor`, and `yymarker` to reflect the shift.
    st.yylimit -= st.token;
    st.yycursor -= st.token;
    // `yymarker` is also shifted. `.overflowing_sub` is used to handle the
    // case where `yymarker` is `st.token` (i.e., the marker was not used).
    st.yymarker = st.yymarker.overflowing_sub(st.token).0;
    // Reset `token` to the beginning of the buffer.
    st.token = 0;

    // Fill free space at the end of buffer with new data from file.
    // We leave `YYMAXFILL` bytes at the end of the buffer for padding.
    let n = match st.file.read(&mut st.yyinput[st.yylimit..BUFSIZE - YYMAXFILL]) {
        Ok(n) => n,
        Err(why) => panic!("cannot read from file: {}", why),
    };

    // Update `yylimit` with the number of bytes read.
    st.yylimit += n;

    // If we read zero characters, this means we've reached the end of the input.
    // We set the `eof` flag and add zero padding to the end of the buffer.
    // This padding ensures that the lexer can always read up to `YYMAXFILL`
    // characters past the actual end of the input, allowing lexemes that
    // end exactly at the end of the file to be processed correctly.
    if n == 0 {
        st.eof = true;
        for i in 0..YYMAXFILL {
            st.yyinput[st.yylimit + i] = 0;
        }
        st.yylimit += YYMAXFILL;
    }

    Fill::Ok
}

fn lex(yyrecord: &mut State) -> isize {
    let mut count: isize = 0;
    'lex: loop {
        // `token` is set to the current `yycursor` position. This marks the
        // beginning of the potential lexeme that will be matched in this iteration.
        yyrecord.token = yyrecord.yycursor;
        /*!re2c
            re2c:api = record;
            re2c:YYCTYPE = u8;
            // YYFILL is enabled. It's called when the condition `YYLESSTHAN(n)`
            // becomes true, meaning there are fewer than `n` characters available
            // in the buffer. The `fill` function is called with `@@` representing
            // the number of characters needed. If `fill` returns anything other
            // than `Fill::Ok`, the lexer returns -1 (error).
            re2c:YYFILL = "if fill(yyrecord, @@) != Fill::Ok { return -1; }";
            // `str` rule matches a single-quoted string, allowing escaped quotes.
            str = ['“] ( [^'“\\] | [\\] [^])* ['”];
            // Null character rule: This rule is specifically for the sentinel
            // zero-byte padding added by `fill` at the end of the file.
            // It checks if the current position (`yyrecord.token`) is exactly
            // at the end of the buffer where the padding starts (`yylimit - YYMAXFILL`).
            // If it is, we've successfully processed all input, and return the `count`.
            // Otherwise, it indicates an unexpected null byte, and we return -1.
            [\x00] {
                // Check that it is the sentinel, not some unexpected null.
                return if yyrecord.token == yyrecord.yylimit - YYMAXFILL { count } else { -1 }
            }
            // `str` rule matches a single-quoted string, allowing escaped quotes.
            str  { count += 1; continue 'lex; }
            // Whitespace rule: matches one or more space characters.
            // It simply skips over whitespace without incrementing the count.
            [ ]+ { continue 'lex; }
            // Default rule: matches any character not matched by previous rules.
            // If this rule is encountered, it means an unexpected character was found,
            // so we return -1 to indicate an error.
            *    { return -1; }
        */}
    }
}

    let content = b"'qu\0tes' 'are' 'fine: \\'' ";

    // to ensure the buffer needs to be filled multiple times.

Les conditions de départ sont activées avec l'option --start-conditions. Elles offrent un moyen d'encoder plusieurs automates interconnectés au sein du même bloc re2rust.


Chaque condition correspond à un automate unique et possède un nom unique spécifié par l'utilisateur et un numéro interne unique défini par re2rust. Les numéros sont utilisés pour passer d'une condition à l'autre : le code généré utilise les primitives YYGETCOND et YYSETCOND pour obtenir la condition actuelle ou la définir au numéro donné. Utilisez le bloc conditions, l'option --header ou la configuration re2c:header pour générer des identificateurs de conditions numériques. La configuration re2c:cond:enumprefix spécifie le préfixe de l'identificateur généré.


En mode condition, chaque règle doit être précédée d'une liste de noms de conditions séparés par des virgules entre chevrons, ou d'un joker <*> pour indiquer toutes les conditions. La syntaxe des règles est étendue comme suit :









  
< liste-conditions > expression-régulière code

  
Une règle qui est fusionnée à chaque condition de la liste-conditions. Elle correspond à l'expression-régulière et exécute le code associé.

  
< liste-conditions > expression-régulière => condition code

  
Une règle qui est fusionnée à chaque condition de la liste-conditions. Elle correspond à l'expression-régulière, définit la condition actuelle à condition et exécute le code associé.

  
< liste-conditions > expression-régulière :=> condition

  
Une règle qui est fusionnée à chaque condition de la liste-conditions. Elle correspond à l'expression-régulière et bascule immédiatement vers la condition (il n'y a pas d'action sémantique).

  
< liste-conditions > !action code

  
Une règle qui lie le code à l'endroit défini par l'action dans chaque condition de la liste-conditions (voir la section actions pour les différents types d'actions).

  
<! liste-conditions > code

  
Une règle qui ajoute le code en préfixe aux actions sémantiques de toutes les règles pour chaque condition de la liste-conditions. Cette syntaxe est obsolète et l'action !pre_rule doit être utilisée à la place (elle fait exactement la même chose).

  
< > code

  
Une règle qui crée une condition d'entrée spéciale avec le numéro zéro et le nom "0" qui exécute le code avant de sauter vers d'autres conditions. Cette syntaxe est obsolète et l'action !entry doit être utilisée à la place (elle offre un contrôle plus granulaire, car le code peut être spécifié par condition, et on peut sauter directement au début de la condition sans passer par la gestion des conditions).

  
< > => condition code

  
Identique à la règle précédente, sauf qu'elle définit la prochaine condition.

  
< > :=> condition

  
Identique à la règle précédente, sauf qu'elle n'a pas de code associé et saute immédiatement vers la condition.










Le code que re2rust génère pour les conditions dépend de l'utilisation par re2rust de l'approche goto/label ou de l'approche boucle/commutateur pour encoder les automates.


Dans les langages qui ont une instruction goto (comme C/C++ et Go), les conditions sont naturellement implémentées comme des blocs de code précédés d'étiquettes de la forme yyc_<cond>, où cond est un nom de condition (le préfixe des étiquettes peut être modifié avec re2c:cond:prefix). Les transitions entre conditions sont implémentées à l'aide de goto et d'étiquettes de condition. Avant toutes les conditions, re2rust génère un commutateur initial sur YYGETSTATE qui saute à l'état de départ de la condition actuelle. Les règles de raccourci :=> contournent le commutateur initial et sautent directement à la condition spécifiée (re2c:cond:goto peut être utilisé pour modifier le comportement par défaut). Les règles avec des actions sémantiques ne sautent pas automatiquement à la condition suivante ; cela doit être fait par le code d'action défini par l'utilisateur.


Dans les langages qui n'ont pas de goto (comme Rust), re2rust réutilise la variable yystate pour stocker les numéros de condition. Chaque condition reçoit un identifiant numérique égal au numéro de son état de départ, et un commutateur entre conditions n'est pas différent d'un commutateur entre états de DFA d'une seule condition. État stockable

Avec l'option --storable-state, re2rust génère un analyseur lexical qui peut stocker son état actuel, retourner à l'appelant, et reprendre plus tard les opérations exactement là où il s'est arrêté. Le mode de fonctionnement par défaut dans re2rust est un modèle "pull", dans lequel l'analyseur lexical "tire" plus d'entrée chaque fois qu'il en a besoin. Ceci peut être inacceptable dans les cas où l'entrée devient disponible par morceaux (par exemple, si l'analyseur lexical est appelé par l'analyseur syntaxique, ou si le programme d'analyseur lexical communique via un protocole de socket avec un autre programme qui doit attendre une réponse de l'analyseur lexical avant de transmettre le message suivant). La fonctionnalité d'état stockable est conçue exactement pour de tels cas : elle permet de générer des analyseurs lexicaux qui fonctionnent selon un modèle "push". Lorsque l'analyseur lexical a besoin de plus d'entrée, il stocke son état et retourne à l'appelant. Plus tard, lorsque plus d'entrée devient disponible, l'appelant reprend l'analyseur lexical exactement là où il s'est arrêté. Il y a quelques changements nécessaires par rapport au modèle "pull" :

  • Définir les primitives YYSETSTATE() et YYGETSTATE(state).
  • Définir les variables yych, yyaccept (si utilisées) et state comme faisant partie de l'état persistant de l'analyseur lexical. La variable state doit être initialisée à -1.
  • YYFILL doit retourner au programme externe au lieu d'essayer de fournir plus d'entrée. Le code de retour doit indiquer que l'analyseur lexical a besoin de plus d'entrée.
  • Le programme externe doit reconnaître les situations où l'analyseur lexical a besoin de plus d'entrée et répondre de manière appropriée.
  • Utiliser optionnellement le bloc getstate pour générer un commutateur YYGETSTATE détaché de l'analyseur lexical principal. Cela ne fonctionne que pour les langages qui ont goto (pas en mode --loop-switch).
  • Utiliser re2c:eof et la méthode sentinelle avec vérifications de limites pour gérer la fin de l'entrée. La méthode basée sur le remplissage peut ne pas fonctionner car il est incertain quand ajouter le remplissage : la fin actuelle de l'entrée peut ne pas être la fin ultime de l'entrée, et ajouter le remplissage trop tôt peut couper un lexème gourmand partiellement lu. De plus, en raison de la logique du programme de haut niveau, l'obtention de plus d'entrée peut dépendre du traitement du lexème à la fin du tampon (qui est déjà bloqué en raison de la condition de fin d'entrée).

// Fill buffer. Returns `Status::BigPacket` if packet is too big,
// `Status::Ready` otherwise.
fn fill(yyrecord: &mut State) -> Status {
    let mut yych;
    'fill: loop {
        yyrecord.yycursor = yyrecord.yymarker;
        // Set `yymarker` to the end of the buffer.
        yyrecord.yymarker = yyrecord.yylimit;
        // Read into the buffer starting after the last consumed input.
        // The input is read into the buffer starting from `yycursor`.
        // `yycursor` points to the first character of the input.
        // `yylimit` points to the end of the input.
        // The sentinel character (null) is at `yylimit`.
        match yyrecord.file.read(&mut yyrecord.yyinput[yyrecord.yycursor..yyrecord.yylimit]) {
            Err(why) => panic!("cannot read file: {}", why),
            Ok(0) => {
                // EOF reached. Null termination triggers YYFILL.
                // Set `yylimit` to the end of the buffer, so null termination
                // will be the sentinel.
                yyrecord.yylimit = BUFSIZE - 1;
                yyrecord.yyinput[yyrecord.yylimit] = 0;
                yyrecord.yycursor = yyrecord.yylimit;
                // No more input, exit loop.
                break 'fill;
            }
            Ok(n) => {
                // Update `yylimit` to reflect the new end of input.
                yyrecord.yylimit = yyrecord.yycursor + n;
                yyrecord.yyinput[yyrecord.yylimit] = 0;
                // Update `yycursor` to the beginning of the buffer.
                yyrecord.yycursor = 0;
                // Resume lexing.
                break 'fill;
            }
        }
    }
    // Check if the packet is too big.
    // If `yymarker` is still at the end of the buffer, it means that
    // the sentinel has not yet been reached.
    if yyrecord.yymarker == yyrecord.yylimit {
        return Status::BigPacket;
    }
    // Set `yystate` to 0 for the next lexing pass.
    yyrecord.yystate = 0;
    return Status::Ready;
}

Dans une expression régulière, TDFA n'est qu'un DFA ordinaire.
Si le nombre de balises est modéré, la surcharge est à peine perceptible. Le TDFA généré utilise un certain nombre de variables de balises qui ne correspondent pas directement aux balises : une seule variable peut être utilisée pour différentes balises, et une balise peut nécessiter plusieurs variables pour contenir toutes ses valeurs possibles. Finalement, l'ambiguïté est résolue, et une seule variable finale par balise survit. Les variables de balises doivent être définies en utilisant des blocs stags ou mtags. Si l'état du lexer est stocké, les variables de balises doivent en faire partie. Elles doivent également être mises à jour par YYFILL.


Les S-tags prennent en charge les opérations suivantes :




    

  • sauvegarder la position d'entrée dans une s-tag : t = YYCURSOR avec l'API pointeur C ou une opération définie par l'utilisateur YYSTAGP(t) avec l'API générique
    • 

  • sauvegarder la valeur par défaut dans une s-tag : t = NULL avec l'API pointeur C ou une opération définie par l'utilisateur YYSTAGN(t) avec l'API générique
    • 

  • copier une s-tag dans une autre : t1 = t2
    • 





Les M-tags prennent en charge les opérations suivantes :




    

  • ajouter la position d'entrée à une m-tag : une opération définie par l'utilisateur YYMTAGP(t) avec les API par défaut et générique
    • 

  • ajouter la valeur par défaut à une m-tag : une opération définie par l'utilisateur YYMTAGN(t) avec les API par défaut et générique
    • 

  • copier une m-tag dans une autre : t1 = t2
    • 





Les S-tags peuvent être implémentées comme des valeurs scalaires (pointeurs ou décalages). Les M-tags nécessitent une représentation plus complexe, car elles doivent stocker une séquence de valeurs de balises. La représentation la plus naïve et inefficace d'une m-tag est une liste (tableau, vecteur) de valeurs de balises ; une représentation plus efficace consiste à stocker toutes les m-tags dans un arbre préfixe représenté comme un tableau de nœuds (v, p), où v est la valeur de la balise et p est un pointeur vers le nœud parent.

use std::fs::File;

const BUFSIZE: usize = 4096;
const NONE: usize = usize::MAX;
struct State {
    file: File,
    yyinput: [u8; BUFSIZE],
    yylimit: usize,
    yycursor: usize,
    yymarker: usize,
    token: usize,
    // Les variables de balises intermédiaires doivent faire partie de l'état du lexer passé à YYFILL.
    // Elles ne correspondent pas aux balises et doivent être générées automatiquement par re2c.
    /*!stags:re2c format = "@@: usize,\n"; */
    eof: bool,
}
#[derive(PartialEq)]
enum Fill { Ok, Eof, LongLexeme }
#[derive(Debug, PartialEq)]
struct SemVer(u32, u32, u32); // version: (majeur, mineur, patch)
fn s2n(str: &[u8]) -> u32 { // convertir une chaîne pré-analysée en nombre
    let mut n = 0;
    for i in str { n = n * 10 + *i as u32 - 48; }
    return n;
}
macro_rules! shift { // ignorer le dépassement, le marqueur et les balises peuvent ne pas être encore définis
    ($x:expr, $y:expr) => { $x = $x.overflowing_sub($y).0 }
}
fn fill(st: &mut State) -> Fill {
    if st.eof { return Fill::Eof; }
    // Erreur : lexème trop long. Dans la vraie vie, on pourrait réallouer un tampon plus grand.
    if st.token < 1 { return Fill::LongLexeme; }
    // Déplacer le contenu du tampon (ignorer tout jusqu au jeton courant).
    st.yyinput.copy_within(st.token..st.yylimit, 0);
    st.yylimit -= st.token;
    st.yycursor -= st.token;
    shift!(st.yymarker, st.token);
    // Les variables de balises doivent être déplacées comme d'autres positions d'entrée. La vérification
    // de NONE n'est nécessaire que si certaines balises sont imbriquées dans une alternative ou
    // une répétition, afin qu'elles puissent avoir la valeur NONE.
    /*!stags:re2c format = "if st.@@ != NONE { shift!(st.@@, st.token); }\n"; */
    st.token = 0;
    // Remplir l'espace libre à la fin du tampon avec de nouvelles données du fichier.
    match st.file.read(&mut st.yyinput[st.yylimit..BUFSIZE - 1]) {
        Ok(n) => {
            st.yylimit += n;
            st.eof = n == 0;
            st.yyinput[st.yylimit] = 0;
        }
        Err(why) => panic!("impossible de lire depuis le fichier : {}", why)
    }
    return Fill::Ok;
}
fn parse(st: &mut State) -> Option<Vec::<SemVer>> {
    let mut vers = Vec::new();
    // Variables de balise finales disponibles dans l'action sémantique.
    /*!svars:re2c format = 'let mut @@;\n'; */
    'parse: loop {
        st.token = st.yycursor;
    /*!re2c
        re2c:api = record;
        re2c:eof = 0;
        re2c:tags = 1;
        re2c:yyrecord = st;
        re2c:YYCTYPE = u8;
        re2c:YYFILL = "fill(st) == Fill::Ok";
        num = [0-9]+;
        num @t1 "." @t2 num @t3 ("." @t4 num)? [\n] {
            let major = s2n(&st.yyinput[st.token..t1]);
            let minor = s2n(&st.yyinput[t2..t3]);
            let patch = if t4 != NONE {s2n(&st.yyinput[t4..st.yycursor - 1])} else {0};
            vers.push(SemVer(major, minor, patch));
            continue 'parse;
        }
        $ { return Some(vers); }
        * { return None; }
    */
    }
}

// re2rust $INPUT -o $OUTPUT --api simple
const NONE: usize = std::usize::MAX;
const MTAG_ROOT: usize = NONE - 1;
// Un arbre de m-tags est un moyen de stocker des historiques avec une opération de copie O(1).
// Les historiques forment naturellement un arbre, car ils ont un début commun et se ramifient à un certain
// point. L'arbre est stocké comme un tableau de paires (valeur de la balise, lien vers le parent).
// Une m-tag est représentée par un seul lien dans l'arbre (indice du tableau).
type MtagTrie = Vec::<MtagElem>;
struct MtagElem {
    elem: usize, // valeur de la balise
    pred: usize, // index du nœud prédécesseur ou de la racine
}
// Ajouter une seule valeur à un historique de m-tag.
fn add_mtag(trie: &mut MtagTrie, mtag: usize, value: usize) -> usize {
    trie.push(MtagElem{elem: value, pred: mtag});
    return trie.len() - 1;
}
// Dérouler récursivement les historiques de balises et collecter les composants de version.
fn unwind(trie: &MtagTrie, x: usize, y: usize, str: &[u8], ver: &mut Ver) {
    // Atteint la racine de l'arbre de m-tags, arrêter la récursion.
    if x == MTAG_ROOT && y == MTAG_ROOT { return; }
    // Dérouler l'historique davantage.
    unwind(trie, trie[x].pred, trie[y].pred, str, ver);
    // Obtenir les valeurs des balises. Les historiques de balises doivent avoir la même longueur.
    assert!(x != MTAG_ROOT && y != MTAG_ROOT);
    let (ex, ey) = (trie[x].elem, trie[y].elem);
    // Les valeurs des balises sont les positions de début des composants de version.
    // Si l'une des balises a une longueur nulle, cela signifie qu'elle n'a pas été
    // trouvée, et que le composant de version correspondant n'a donc pas été trouvé.
    if ex == NONE || ey == NONE { return; }
    // Ajouter le composant de version analysé au vecteur de version.
    let elem = &str[ex..ey];
    ver.push(s2n(elem));
}
// Convertir une chaîne pré-analysée en nombre
fn s2n(str: &[u8]) -> u32 {
    let mut n = 0;
    for i in str { n = n * 10 + *i as u32 - 48; }
    return n;
}
fn parse(yyinput: &[u8]) -> Option<Vec<u32>> {
    assert_eq!(yyinput.last(), Some(&0)); // attendre une entrée terminée par null
    let (mut yycursor, mut yymarker) = (0, 0);
    // Variables de balises finales disponibles dans l'action sémantique.
    /*!svars:re2c format = 'let mut @@;\n'; */
    // Variables de balises intermédiaires utilisées par le lexer (doivent être générées automatiquement).
    /*!stags:re2c format = 'let mut @@ = NONE;'; */
    // M-tags sont stockés dans un trie.
    let mut trie: MtagTrie = Vec::new();
    let mut ver: Vec = Vec::new();
    /*!re2c
        re2c:YYCTYPE = u8;
        re2c:yyfill:enable = 0;
        re2c:tags = 1;
        // M-tags sont stockés dans un trie.
        re2c:mtags:trie = trie;
        num = [0-9]+;
        @t1 num @t2 ("." @t3 num)+ [\x00] {
            // Dérouler l'historique de m-tags pour obtenir les composants de version.
            unwind(&trie, t1, t2, yyinput, &mut ver);
            return Some(ver);
        }

    */

Prise en charge de l\'encodage

Il est nécessaire de comprendre la différence entre les points de code et les unités de code. Un point de code est un identifiant numérique d'un symbole. Une unité de code est la plus petite unité de stockage dans le texte encodé. Un seul point de code peut être représenté avec une ou plusieurs unités de code. Dans un encodage à longueur fixe, tous les points de code sont représentés avec le même nombre d'unités de code. Dans un encodage à longueur variable, les points de code peuvent être représentés avec un nombre différent d'unités de code. Notez que la règle « quelconque » [^] correspond à n'importe quel point de code, mais pas nécessairement à n'importe quelle unité de code (la seule façon de faire correspondre n'importe quelle unité de code, quel que soit l'encodage, est la règle par défaut *). Le lexer généré travaille avec un flux d'unités de code : yych stocke une unité de code, et YYCTYPE est le type d'unité de code. Les expressions régulières, en revanche, sont spécifiées en termes de points de code. Lorsque re2rust compile les expressions régulières en automates, il traduit les points de code en unités de code. Ce n'est généralement pas une simple correspondance : dans les encodages à longueur variable, une plage de points de code unique peut être traduite en un graphe complexe d'unités de code. Les encodages suivants sont pris en charge :

  • ASCII (activé par défaut). C'est un encodage à longueur fixe avec un espace de code [0-255] et des points de code et des unités de code de 1 octet.
  • EBCDIC (activé avec --ebcdic ou re2c:encoding:ebcdic). C'est un encodage à longueur fixe avec un espace de code [0-255] et des points de code et des unités de code de 1 octet.
  • UCS2 (activé avec --ucs2 ou re2c:encoding:ucs2). C'est un encodage à longueur fixe avec un espace de code [0-0xFFFF] et des points de code et des unités de code de 2 octets.
  • UTF8 (activé avec --utf8 ou re2c:encoding:utf8). C'est un encodage Unicode à longueur variable. La taille de l'unité de code est de 1 octet. Les points de code sont représentés avec 1 à 4 unités de code.
  • UTF16 (activé avec --utf16 ou re2c:encoding:utf16). C'est un encodage Unicode à longueur variable. La taille de l'unité de code est de 2 octets. Les points de code sont représentés avec 1 à 2 unités de code.
  • UTF32 (activé avec --utf32 ou re2c:encoding:utf32). C'est un encodage Unicode à longueur fixe avec un espace de code [0-0x10FFFF] et des points de code et des unités de code de 4 octets.

Le fichier d'inclusion include/unicode_categories.re fournit les définitions re2rust pour les catégories Unicode standard.

L'option --input-encoding spécifie l'encodage du fichier source, qui peut être utilisé pour activer les littéraux Unicode dans les expressions régulières. Par exemple, --input-encoding utf8 indique à re2rust que le fichier source est en UTF8 (cela diffère de --utf8 qui définit l'encodage du texte d'entrée). L'option --encoding-policy spécifie la manière dont re2rust gère les substituts Unicode (points de code dans la plage [0xD800-0xDFFF]).

Ci-dessous un exemple de lexer pour les identifiants Unicode encodés en UTF8.

// re2rust $INPUT -o $OUTPUT --utf8 --api simple
/*!include:re2c "unicode_categories.re" */
fn lex(yyinput: &[u8]) -> bool {
    assert_eq!(yyinput.last(), Some(&0)); // s'attend à une entrée terminée par null
    let (mut yycursor, mut yymarker) = (0, 0);
    /*!re2c
        re2c:YYCTYPE = u8;
        re2c:yyfill:enable = 0;
        // "Unicode Identifier and Pattern Syntax" simplifié
        // (voir https://unicode.org/reports/tr31)
        id_start    = L | Nl | [$_];
        id_continue = id_start | Mn | Mc | Nd | Pc | [\u200D\u05F3];
        identifier  = id_start id_continue*;
        identifier { return true; }
        *          { return false; }
    */
}
fn main() {
    assert!(lex("_Ыдентификатор\0".as_bytes()));
}

Fichiers d'inclusion

re2rust permet d'inclure d'autres fichiers en utilisant un bloc de la forme /*!include:re2c FILE */ ou %{include FILE %}, ou une directive dans le bloc !include FILE ;, où FILE est un chemin vers le fichier à inclure. re2rust recherche les fichiers d'inclusion dans le répertoire du fichier incluant et dans les emplacements d'inclusion, qui peuvent être spécifiés avec l'option -I. Les blocs/directives d'inclusion dans re2rust fonctionnent de la même manière que le #include de C/C++ : le contenu de FILE est copié verbatim à la place du bloc/de la directive. Les fichiers d'inclusion peuvent contenir d'autres inclusions. Utilisez l'option --depfile pour suivre les dépendances de build du fichier de sortie sur les fichiers d'inclusion. re2rust fournit des fichiers d'inclusion prédéfinis qui peuvent être trouvés dans le sous-répertoire include/ du projet. Ces fichiers contiennent des définitions qui peuvent être utiles à d'autres projets (telles que les catégories Unicode) et forment une sorte de bibliothèque standard pour re2rust. Voici un exemple d'utilisation des fichiers d'inclusion.

Fichier d'inclusion 1 (definitions.rs)

#[derive(Debug, PartialEq)]
enum Num { Int, Float, NaN }
/*!re2c
    number = [1-9][0-9]*;
*/
Fichier d'inclusion 2 (extra_rules.re.inc) 
// nombres à virgule flottante
frac  = [0-9]* "." [0-9]+ | [0-9]+ ".";
exp   = 'e' [+-]? [0-9]+;
float = frac exp? | [0-9]+ exp;
float { return Num::Float; }

Fichier d'entrée

// re2rust $INPUT -o $OUTPUT --api simple
/*!include:re2c "definitions.rs" */
fn lex(yyinput: &[u8]) -> Num {
    assert_eq!(yyinput.last(), Some(&0)); // s'attend à une entrée terminée par null
    let mut yycursor = 0;
    let mut yymarker = 0;
    /*!re2c
        re2c:yyfill:enable = 0;
        re2c:YYCTYPE = u8;
        *      { return Num::NaN; }
        number { return Num::Int; }
        !include "extra_rules.re.inc";
    */
}
fn main() {
    assert_eq!(lex(b"123\0"), Num::Int);
    assert_eq!(lex(b"123.4567\0"), Num::Float);
}

Fichiers d'en-tête

re2rust permet de générer un fichier d'en-tête à partir du fichier .re d'entrée en utilisant l'option --header ou la configuration re2c:header et des paires de blocs de la forme /*!header:re2c:on*/ et /*!header:re2c:off*/, ou %{header:on%} et %{header:off%}. Le premier bloc marque le début du fichier d'en-tête, et le second bloc marque la fin. Tout ce qui se trouve entre ces blocs est traité par re2rust, et le code généré est écrit dans le fichier spécifié avec l'option --header ou la configuration re2c:header (ou stdout si aucune option ni configuration n'est utilisée). Le fichier d'en-tête généré automatiquement peut être nécessaire dans les cas où re2rust est utilisé pour générer des définitions qui doivent être visibles depuis d'autres unités de traduction.

Voici un exemple de génération d'un fichier d'en-tête contenant la définition de l'état du lexer avec des variables de balise (les variables numériques dépendent de la grammaire régulière et ne sont pas connues du programmeur).

Fichier d'entrée

// re2rust $INPUT -o $OUTPUT --header lexer/state.rs
mod lexer;
use lexer::state::State; // le module est généré par re2c
/*!header:re2c:on*/
pub struct State<'a> {
    pub yyinput: &'a [u8],
    pub yycursor: usize,
    /*!stags:re2c format = "pub @@: usize,"; */
}
/*!header:re2c:off*/

    assert_eq!(yyrecord.yyinput.last(), Some(&0)); // s'attend à une entrée terminée par null
    let t: usize;
    /*!re2c
        re2c:header = "lexer/state.rs";
        re2c:yyfill:enable = 0;
        re2c:api = record;
        re2c:YYCTYPE = "u8";
        re2c:tags = 1;
        [a]* @t [b]* { return t; }
    */
}
fn main() {
    let mut st = State {
        yyinput: b"ab\0",
        yycursor: 0,
        /*!stags:re2c format = "@@: 0,"; */
    };
    assert_eq!(lex(&mut st), 1);
}

Programmes squelettes

Avec l'option -S, --skeleton, re2rust ignore tout le code non-re2rust et génère un programme C autonome qui peut être compilé et exécuté ultérieurement. Le programme se compose du code du lexer et des données d'entrée. Pour chaque automate fini déterministe (DFA) construit (bloc ou condition), re2rust génère un lexer autonome et deux fichiers : un fichier .input avec des chaînes dérivées du DFA et un fichier .keys avec les résultats de correspondance attendus. Le programme exécute chaque lexer sur le fichier correspondant.

re2rust(1) — Arch Linux man pages

NAME

re2rust — A regular expression compiler for Rust.

SYNOPSIS

re2rust [-h | --help] [--version] [-i | --input file] [-o | --output file] [-D | --emit-dot] [options]

INTRODUCTION

re2rust is a tool that takes a description of a regular language and generates a Rust program that recognizes strings belonging to that language. It is based on the re2c compiler.

BASICS

The input to re2rust is a file containing a set of regular expressions and associated actions. The output is a Rust program that, when run, reads input and performs the specified actions when a regular expression is matched. For example:

    %{
    // User code
    %}
    
    char:
      "a"  { println!("Saw an 'a'"); }
    | "b"  { println!("Saw a 'b'"); }
    ;
    
    input:
      char+  { println!("Saw one or more characters."); }
    ;
    
    "a" { println!("Saw an 'a' (top level)"); }

This simple grammar defines two rules. The first rule, char, matches either a single character 'a' or a single character 'b'. The second rule, input, matches one or more char characters. Finally, a top-level rule matches a single 'a'. When the generated program is run, it will read input and execute the corresponding action when a pattern is matched. Note that re2rust uses a greedy matching strategy, so if multiple rules match, the longest match is preferred. If there are multiple rules of the same longest length, the first one specified in the input file is chosen.

HANDLING THE END OF INPUT

re2rust provides special support for handling the end of input. The EOF condition can be matched using the special symbol '$'. For example:

    "$"{
      println!("End of input reached.");
    }

This rule will match only when the end of the input stream is encountered.

BUFFER REFILLING

For large inputs or when dealing with complex regular expressions, re2rust supports automatic buffer refilling. This allows the generated scanner to read input in chunks, rather than all at once. This is enabled by default. The user can provide a custom refilling function by including it in the user code section.

Example of default refilling:

    <<%option buffer-fill-function="rust_fill_buf" %>>
    char:
      "a" { /* ... */ }
    ;

Here, rust_fill_buf would be a Rust function responsible for reading more data into the scanner's buffer.

FEATURES

re2rust includes several features to aid in testing and debugging:

  • Skeleton programs: re2rust can generate programs that produce random strings which are then fed into the generated Rust code. This is done using the --skeleton-file=<file> option. The skeleton program reads input from the specified .input file and compares results with the expectations. Skeleton programs are very useful for a number of reasons:
    • They can check correctness of various re2rust optimizations (the data is generated early in the process, before any DFA transformations have taken place).
    • Generating a set of input data with good coverage may be useful for both testing and benchmarking.
    • Generating self-contained executable programs allows one to get minimized test cases (the original code may be large or have a lot of dependencies).

The difficulty with generating input data is that for all but the most trivial cases the number of possible input strings is too large (even if the string length is limited). re2rust solves this difficulty by generating sufficiently many strings to cover almost all DFA transitions. It uses the following algorithm. First, it constructs a skeleton of the DFA. For encodings with 1-byte code unit size (such as ASCII, UTF-8 and EBCDIC) skeleton is just an exact copy of the original DFA. For encodings with multibyte code units skeleton is a copy of DFA with certain transitions omitted: namely, re2rust takes at most 256 code units for each disjoint continuous range that corresponds to a DFA transition. The chosen values are evenly distributed and include range bounds. Instead of trying to cover all possible paths in the skeleton (which is infeasible) re2rust generates sufficiently many paths to cover all skeleton transitions, and thus trigger the corresponding conditional jumps in the lexer. The algorithm implementation is limited by ~1Gb of transitions and consumes constant amount of memory (re2rust writes data to file as soon as it is generated).

Visualization and debug

With the -D, --emit-dot option, re2rust does not generate code. Instead, it dumps the generated DFA in DOT format. One can convert this dump to an image of the DFA using Graphviz or another library. Note that this option shows the final DFA after it has gone through a number of optimizations and transformations. Earlier stages can be dumped with various debug options, such as --dump-nfa, --dump-dfa-raw etc. (see the full list of options).
