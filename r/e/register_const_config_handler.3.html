DESCRIPTION

Les fonctions constituent un système assez extensible pour l'analyse de divers fichiers de configuration au moment de l'exécution d'une application. Le flux de configuration est divisé dans les phases suivantes :

1.
Enregistrement des gestionnaires.
2.
Lecture des fichiers de configuration pour les besoins d'analyse pré-MIB.
3.
Lecture et analyse des fichiers MIB textuels.
4.
Lecture des fichiers de configuration pour les directives de configuration.
5.
Optionnellement, relecture des fichiers de configuration à une date ultérieure.

L'idée est que l'application appelante soit capable d'enregistrer des gestionnaires pour certains tokens spécifiés dans certains fichiers de configuration nommés. La fonction read_configs() peut alors être appelée pour rechercher tous les fichiers de configuration pertinents, faire correspondre le premier mot de chaque ligne avec la liste des tokens enregistrés et passer le reste de la ligne au gestionnaire enregistré approprié.

ENREGISTREMENT D'UN GESTIONNAIRE

register_config_handler()
Enregistre une routine de gestion de configuration, qui doit être appelée pour traiter les directives de configuration commençant par le token spécifié. Par exemple :
register_config_handler("snmp", "exampleToken", example_handler, NULL, "ARG1 [ARG2]");
enregistrerait la fonction example_handler() de manière à ce qu'elle soit appelée chaque fois que le premier mot d'une ligne dans le fichier(s) de configuration snmp.conf correspond à "exampleToken".
L'appel des gestionnaires appropriés pour traiter les directives de fichier de configuration est la responsabilité de read_configs() (voir ci-dessous).
register_const_config_handler()
Similaire à la fonction register_config_handler(), mais la routine d'analyse est explicitement limitée à ne pas modifier la chaîne analysée.
register_prenetsnmp_mib_handler()
Similaire à la fonction register_config_handler(), mais la routine de gestionnaire enregistrée sera appelée *avant* la lecture des MIBs textuels. Ceci est généralement utilisé pour les tokens qui affecteront la configuration du parseur MIB, et sera normalement utilisé uniquement au sein de la bibliothèque SNMP elle-même.
register_mib_handlers()
Routine d'initialisation pour enregistrer les gestionnaires de configuration internes de la bibliothèque SNMP.
unregister_config_handler()
Supprime le gestionnaire de configuration enregistré pour le filePrefix et le token spécifiés.
unregister_all_config_handlers()
Supprime tous les gestionnaires de configuration enregistrés.

Gestionnaires de tokens

Les fonctions de gestionnaire doivent avoir la signature suivante :

void handler(const char *token, char *line);
ou
void handler(const char *token, const char *line); (si enregistré via register_const_config_handler)

La fonction sera appelée avec deux arguments, le premier étant le token qui a déclenché l'appel à cette fonction (c'est-à-dire le token utilisé lors de l'enregistrement du gestionnaire), et le second étant le reste de la ligne du fichier de configuration (c'est-à-dire tout ce qui suit l'espace blanc après le token correspondant).

Libération des gestionnaires

Si la fonction de gestionnaire de token alloue dynamiquement des ressources lors du traitement d'une entrée de configuration, celles-ci pourraient devoir être libérées avant de relire les fichiers de configuration. Si le quatrième paramètre (releaser) passé à register_config_handler n'est pas NULL, il spécifie une fonction à appeler avant de relire les fichiers de configuration. Cette fonction doit libérer toutes les ressources allouées par la fonction de gestionnaire de token et réinitialiser sa notion de configuration à ses valeurs par défaut. La fonction de gestionnaire de token peut alors être appelée à nouveau en toute sécurité. Aucun argument n'est passé au gestionnaire de libération de ressources.
Notez que cette fonction n'est pas appelée lorsque le gestionnaire est dés-enregistré individuellement (mais elle *est* appelée dans le cadre de unregister_all_config_handlers() ).

NAME

register_const_config_handler, register_app_config_handler, unregister_const_config_handler, unregister_app_config_handler - MIB module configuration handler registration

SYNOPSIS

#include <net-snmp/library/configure.h>

void
    register_const_config_handler(
        const char *token,
        snmp_config_handler *handler,
        void *data);

void
    register_app_config_handler(
        const char *token,
        snmp_config_handler *handler,
        void *data);

void
    unregister_const_config_handler(
        const char *token,
        snmp_config_handler *handler,
        void *data);

void
    unregister_app_config_handler(
        const char *token,
        snmp_config_handler *handler,
        void *data);

DESCRIPTION

These functions are used to register callbacks (handlers) for specific configuration tokens found in the configuration files used by the net-snmp agent. When the configuration files are read, these handlers are called when their associated token is encountered.

register_const_config_handler()

This function registers a configuration handler for a given token. The token is the string that will be looked for in the configuration file. The handler is a function pointer to the callback function that will be invoked when the token is found. The data argument is a pointer to application-specific data that will be passed to the handler function.

The handler function should have the following signature:

    int handler(int argc, char **argv, void *data);

The handler function is called with the token as the first argument (argv[0]), and subsequent arguments from the configuration line as argv[1] through argv[argc-1]. It should return 1 if the configuration line was processed successfully, and 0 otherwise.

The token string must not contain spaces or other whitespace characters. The handler is registered globally.

register_app_config_handler()

This function is similar to register_const_config_handler(), but the handler is registered on a per-application basis. This means that multiple applications can register handlers for the same token without conflict. The application name is determined by the filePrefix argument passed to init_snmp().

unregister_const_config_handler()

This function unregisters a previously registered configuration handler. The arguments must match those used when registering the handler.

unregister_app_config_handler()

These functions are analagous to register_config_handler(), register_prenetsnmp_mib_handler() and unregister_config_handler() but do not require the file type argument (which is filled in by the application). It is intended that MIB modules written for the agent use these functions to allow the agent to have more control over which configuration files are read (typically the snmpd.conf files).

READING CONFIGURATION FILES

read_premib_configs()
read_configs()
These routines process the configuration files found in the configuration search path (see below). For each entry, the handler registered for that configuration token is called.

read_premib_configs() is run before the MIB files are read in, and processes those configuration tokens registered using register_prenetsnmp_mib_handler() (or register_app_prenetsnmp_mib_handler() ). All other entries are ignored.

read_configs() is run after the MIB files have been read in, and processes those configuration tokens registered using register_config_handler() (or register_app_config_handler() ). If it encounters a configuration token for which no handler has been registered (either pre- or post-mib), then it will display a warning message, and continue processing with the next line of the configuration file.

Configuration Search Path

The configuration files to be read are found by searching a list of configuration directories for appropriately named files. In each such directory, the library will look for files named snmp.conf, snmp.local.conf, app.conf, app.local.conf,
(where app is the appication-specific filePrefix used to register configuration handlers). It is not necessary for any or all of these files to be present in each directory. Missing files will be silently skipped.
The idea behind the two different suffixes is that the first file can be shared (via rdist or an NFS mount) across a large number of machines and the second file can be used to configure local settings for one particular machine.

The default list of directories to search is /etc/snmp, followed by /usr/share/snmp, followed by /usr/lib/snmp, followed by $HOME/.snmp. This list can be changed by setting the environmental variable SNMPCONFPATH to be a (colon separated) list of directories to search.

init_snmp()

The normal mode of operation would be to register the application-specific configuration handlers, and then invoke init_snmp(). This would call the routines listed above to register the internal library configuration handlers, process any configuration tokens registered with register_prenetsnmp_mib_handler(), read in the textual MIB files using init_mib(), and finally parse the configuration file tokens registered with register_config_handler().

If the init_snmp() function is used, none of these functions need to be explicitly called by the application.

HELP STRINGS AND ERRORS

The usageLine parameter passed to register_config_handler() and similar calls, is used to display help information when the read_config_print_usage() function is called. This function is used by all of the applications when the -H flag is passed on the command line. It prints a summary of all of the configuration file lines, and the associated files, that the configuration system understands. The usageLine parameter should be a list of arguments expected after the token, and not a lengthy description (which should go into a manual page instead). The lead prefix will be prepended to each line that the function prints to stderr, where it displays its output.

The init_snmp() function should be called before the read_config_print_usage() function is called, so that the library can register its configuration file directives as well for the read_config_print_usage() function to display.

Error Handling Functions

The two functions config_pwarn() and config_perror() both take an error string as an argument and print it to stderr along with the file and line number that caused the error. A call to the second function will also force read_configs() to eventually return with an error code indicating to it's calling function that it should abort the operation of the application.

ENVIRONMENT VARIABLES

SNMPCONFPATH
A colon separated list of directories to search for configuration files in. Default:
/etc/snmp:/usr/share/snmp:/usr/lib/snmp:$HOME/.snmp

NOM

register_const_config_handler, register_app_config_handler, unregister_const_config_handler, unregister_app_config_handler - Enregistrement des gestionnaires de configuration de modules MIB

SYNTAXE

#include <net-snmp/library/configure.h>

void
    register_const_config_handler(
        const char *token,
        snmp_config_handler *handler,
        void *data);

void
    register_app_config_handler(
        const char *token,
        snmp_config_handler *handler,
        void *data);

void
    unregister_const_config_handler(
        const char *token,
        snmp_config_handler *handler,
        void *data);

void
    unregister_app_config_handler(
        const char *token,
        snmp_config_handler *handler,
        void *data);

DESCRIPTION

Ces fonctions sont utilisées pour enregistrer des fonctions de rappel (gestionnaires) pour des jetons de configuration spécifiques utilisés par l'agent net-snmp. Lorsque les fichiers de configuration sont lus, ces gestionnaires sont appelés lorsqu'un jeton associé est rencontré.

register_const_config_handler()

Cette fonction enregistre un gestionnaire de configuration pour un jeton donné. Le jeton est la chaîne de caractères qui sera recherchée dans le fichier de configuration. Le gestionnaire est un pointeur de fonction vers la fonction de rappel qui sera appelée lorsque le jeton est trouvé. L'argument data est un pointeur vers des données spécifiques à l'application qui seront passées à la fonction de gestionnaire.

La fonction de gestionnaire doit avoir la signature suivante :

    int handler(int argc, char **argv, void *data);

La fonction de gestionnaire est appelée avec le jeton comme premier argument (argv[0]), et les arguments suivants de la ligne de configuration comme argv[1] à argv[argc-1]. Elle doit retourner 1 si la ligne de configuration a été traitée avec succès, et 0 sinon.

La chaîne de caractères jeton ne doit pas contenir d'espaces ou d'autres caractères d'espacement. Le gestionnaire est enregistré globalement.

register_app_config_handler()

Cette fonction est similaire à register_const_config_handler(), mais le gestionnaire est enregistré par application. Cela signifie que plusieurs applications peuvent enregistrer des gestionnaires pour le même jeton sans conflit. Le nom de l'application est déterminé par l'argument filePrefix passé à init_snmp().

unregister_const_config_handler()

Cette fonction désenregistre un gestionnaire de configuration précédemment enregistré. Les arguments doivent correspondre à ceux utilisés lors de l'enregistrement du gestionnaire.

unregister_app_config_handler()

Ces fonctions sont analogues à register_config_handler(), register_prenetsnmp_mib_handler() et unregister_config_handler() mais ne nécessitent pas l'argument du type de fichier (qui est rempli par l'application). Il est prévu que les modules MIB écrits pour l'agent utilisent ces fonctions pour permettre à l'agent d'avoir plus de contrôle sur les fichiers de configuration qui sont lus (typiquement les fichiers snmpd.conf).

LECTURE DES FICHIERS DE CONFIGURATION

read_premib_configs()
read_configs()
Ces routines traitent les fichiers de configuration trouvés dans le chemin de recherche de configuration (voir ci-dessous). Pour chaque entrée, le gestionnaire enregistré pour ce jeton de configuration est appelé.

read_premib_configs() est exécuté avant la lecture des fichiers MIB, et traite les jetons de configuration enregistrés à l'aide de register_prenetsnmp_mib_handler() (ou register_app_prenetsnmp_mib_handler() ). Toutes les autres entrées sont ignorées.

read_configs() est exécuté après la lecture des fichiers MIB, et traite les jetons de configuration enregistrés à l'aide de register_config_handler() (ou register_app_config_handler() ). S'il rencontre un jeton de configuration pour lequel aucun gestionnaire n'a été enregistré (avant ou après les MIB), il affichera un message d'avertissement et continuera le traitement avec la ligne suivante du fichier de configuration.

Chemin de Recherche de Configuration

Les fichiers de configuration à lire sont trouvés en recherchant dans une liste de répertoires de configuration des fichiers nommés de manière appropriée. Dans chaque répertoire, la bibliothèque recherchera les fichiers nommés snmp.conf, snmp.local.conf, app.conf, app.local.conf,
(où app est le préfixe de fichier spécifique à l'application utilisé pour enregistrer les gestionnaires de configuration). Il n'est pas nécessaire que tous ces fichiers soient présents dans chaque répertoire. Les fichiers manquants seront ignorés silencieusement.
L'idée derrière les deux suffixes différents est que le premier fichier peut être partagé (via rdist ou un montage NFS) sur un grand nombre de machines et le second fichier peut être utilisé pour configurer les paramètres locaux d'une machine particulière.

La liste par défaut des répertoires à rechercher est /etc/snmp, suivi de /usr/share/snmp, suivi de /usr/lib/snmp, suivi de $HOME/.snmp. Cette liste peut être modifiée en définissant la variable d'environnement SNMPCONFPATH sur une liste (séparée par des deux-points) de répertoires à rechercher.

init_snmp()

Le mode de fonctionnement normal consisterait à enregistrer les gestionnaires de configuration spécifiques à l'application, puis à appeler init_snmp(). Cela appellerait les routines listées ci-dessus pour enregistrer les gestionnaires de configuration internes de la bibliothèque, traiter les jetons de configuration enregistrés avec register_prenetsnmp_mib_handler(), lire les fichiers MIB textuels à l'aide de init_mib(), et enfin analyser les jetons de fichier de configuration enregistrés avec register_config_handler().

Si la fonction init_snmp() est utilisée, aucune de ces fonctions n'a besoin d'être explicitement appelée par l'application.

CHAÎNES D'AIDE ET ERREURS

Le paramètre usageLine passé à register_config_handler() et aux appels similaires, est utilisé pour afficher des informations d'aide lorsque la fonction read_config_print_usage() est appelée. Cette fonction est utilisée par toutes les applications lorsque le drapeau -H est passé sur la ligne de commande. Elle imprime un résumé de toutes les lignes de fichiers de configuration, et des fichiers associés, que le système de configuration comprend. Le paramètre usageLine doit être une liste d'arguments attendus après le jeton, et non une longue description (qui devrait plutôt aller dans une page de manuel). Le préfixe lead sera ajouté à chaque ligne que la fonction imprime sur stderr, où elle affiche sa sortie.

La fonction init_snmp() doit être appelée avant la fonction read_config_print_usage(), afin que la bibliothèque puisse enregistrer ses directives de fichier de configuration également pour que la fonction read_config_print_usage() les affiche.

Fonctions de Gestion des Erreurs

Les deux fonctions config_pwarn() et config_perror() prennent toutes deux une chaîne d'erreur comme argument et l'impriment sur stderr avec le fichier et le numéro de ligne qui ont causé l'erreur. Un appel à la seconde fonction forcera également read_configs() à retourner éventuellement avec un code d'erreur indiquant à sa fonction appelante qu'elle doit abandonner l'opération de l'application.

VARIABLES D'ENVIRONNEMENT

SNMPCONFPATH
Une liste séparée par des deux-points de répertoires dans lesquels rechercher les fichiers de configuration. Défaut :
/etc/snmp:/usr/share/snmp:/usr/lib/snmp:$HOME/.snmp
