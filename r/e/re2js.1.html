NOM

re2js - génère des analyseurs lexicaux rapides pour JavaScript

SYNTAXE

re2js [ OPTIONS ] [ AVERTISSEMENTS ] ENTRÉE

L'entrée peut être soit un fichier, soit - pour l'entrée standard.

INTRODUCTION

re2js fonctionne comme un préprocesseur. Il lit le fichier d'entrée (qui est généralement un programme en JavaScript, mais peut être n'importe quoi) et recherche des blocs de code délimités par des marqueurs de début/fin de forme spéciale. Le texte en dehors de ces blocs est copié tel quel dans le fichier de sortie. Le contenu des blocs est traité par re2js. Il les traduit en code JavaScript et génère le code en place du bloc.

Voici un exemple de petit programme qui vérifie si une chaîne donnée contient un nombre décimal :

// re2js $INPUT -o $OUTPUT
function lex(yyinput) {
    let yycursor = 0;
    /*!re2c
        re2c:yyfill:enable = 0;
        [1-9][0-9]* { return true; }
        *           { return false; }
    */
}
if (!lex("1234\0")) {
    throw "error!"
}

Dans la sortie, re2js a remplacé le bloc du milieu par le code généré :

// Généré par re2js
// re2js $INPUT -o $OUTPUT
function lex(yyinput) {
    let yycursor = 0;
{
    let yych = 0
    let yystate = 0
    yyl: while (true) {
        switch (yystate) {
            case 0:
                yych = yyinput.charCodeAt(yycursor)
                yycursor += 1;
                switch (yych) {
                    case 0x31:
                    case 0x32:
                    case 0x33:
                    case 0x34:
                    case 0x35:
                    case 0x36:
                    case 0x37:
                    case 0x38:
                    case 0x39:
                        yystate = 2
                        continue yyl
                    default:
                        yystate = 1
                        continue yyl
                }
            case 1:
                { return false; }
            case 2:
                yych = yyinput.charCodeAt(yycursor)
                switch (yych) {
                    case 0x30:
                    case 0x31:
                    case 0x32:
                    case 0x33:
                    case 0x34:
                    case 0x35:
                    case 0x36:
                    case 0x37:
                    case 0x38:
                    case 0x39:
                        yycursor += 1;
                        yystate = 2
                        continue yyl
                    default:
                        yystate = 3
                        continue yyl
                }
            case 3:
                { return true; }
            default:
                throw "internal lexer error"
        }
    }
}
}
if (!lex("1234\0")) {
    throw "error!"
}

BASES

Un programme re2js se compose d'une séquence de blocs entremêlés de code dans le langage cible. Un bloc peut contenir des définitions, des configurations, des règles, des actions et des directives dans n'importe quel ordre :

nom = expression-régulière ;
Une définition lie nom à expression-régulière. Les noms peuvent contenir des caractères alphanumériques et un tiret bas. La section expressions régulières donne un aperçu de la syntaxe re2js pour les expressions régulières. Une fois défini, le nom peut être utilisé dans d'autres expressions régulières et dans les règles. La récursion dans les définitions nommées n'est pas autorisée, et chaque nom doit être défini avant d'être utilisé. Un bloc hérite des définitions nommées de la portée globale. Redéfinir un nom qui existe dans la portée actuelle est une erreur.
configuration = valeur ;
Une configuration permet de modifier le comportement de re2js et de personnaliser le code généré. Pour une liste complète des configurations supportées par re2js, voir la section configurations. Selon la configuration, la valeur peut être un mot-clé, un nombre entier non négatif ou une chaîne sur une seule ligne qui doit être entourée de guillemets doubles ou simples, sauf si elle est composée de caractères alphanumériques. Un bloc hérite des configurations de la portée globale et peut les redéfinir ou en ajouter de nouvelles. Les configurations définies à l'intérieur d'un bloc affectent l'ensemble du bloc, même si elles y apparaissent à la fin.
expression-régulière code
Une règle lie une expression-régulière à son action sémantique (un bloc de code entre accolades, ou un bloc de code qui commence par := et se termine sur une nouvelle ligne suivie d'un caractère non blanc). Si l'expression-régulière correspond, le code associé est exécuté. Si plusieurs règles correspondent, la correspondance la plus longue a la priorité. Si plusieurs règles correspondent à la même chaîne, la première apparaît a la priorité. Il existe deux règles spéciales : la règle par défaut * et la règle de fin d'entrée $. La règle par défaut doit toujours être définie, elle a la plus basse priorité quelle que soit sa place dans le bloc, et elle correspond à n'importe quelle unité de code (pas nécessairement un caractère valide, voir la section support de l'encodage). La règle de fin d'entrée doit être définie si la méthode correspondante pour la gestion de la fin de l'entrée est utilisée. Avec les conditions de départ, les règles ont une syntaxe plus complexe.
!action code
Une action lie un bloc de code défini par l'utilisateur à un endroit particulier dans la machine à états finis générée (de la même manière que les actions sémantiques lient du code aux états finaux). Voir la section actions pour une liste complète des actions prédéfinies.
!directive ;
Une directive est l'une des instructions prédéfinies spéciales. Chaque directive a un but unique. Voir la section directives pour les détails.

Blocs

Les marqueurs de début et de fin de bloc sont soit /*!re2c et */, soit %{ et %} (les deux styles sont supportés). Depuis la version 2.2, les blocs peuvent avoir des noms optionnels qui permettent de les référencer dans d'autres blocs. Il existe différents types de blocs :

/*!re2c[:<nom>] ... */ ou %{[:<nom>] ... %}
Un bloc global contient des définitions, des configurations, des règles et des directives. re2js compile les expressions régulières associées à chaque règle en un automate fini déterministe, l'encode sous forme de sauts conditionnels dans le langage cible et remplace le bloc par le code généré. Les noms et configurations définis dans un bloc global sont ajoutés à la portée globale et deviennent visibles pour les blocs suivants. Au début du programme, la portée globale est initialisée avec les options de la ligne de commande.
/*!local:re2c[:<nom>] ... */ ou %{local[:<nom>] ... %}
Un bloc local est similaire à un bloc global, mais les noms et les configurations qu'il contient ont une portée locale (ils n'affectent pas les autres blocs).
/*!rules:re2c[:<nom>] ... */ ou %{rules[:<nom>] ... %}
Un bloc de règles est similaire à un bloc local, mais il ne génère pas de code en lui-même, ni n'ajoute de définitions à la portée globale -- il est destiné à être réutilisé dans d'autres blocs. C'est une façon de partager du code (plus de détails dans la section blocs réutilisables). Avant la version 2.2 de re2js, les blocs de règles nécessitaient l'option -r --reusable.
/*!use:re2c[:<nom>] ... */ ou %{use[:<nom>] ... %}
Un bloc d'utilisation qui référence un bloc de règles défini précédemment. Si le nom est spécifié, re2js recherche les blocs de règles portant ce nom. Sinon, le bloc de règles le plus récent est utilisé (qu'il soit nommé ou sans nom). Un bloc d'utilisation peut ajouter ses propres définitions, configurations et règles, qui sont ajoutées à celles du bloc de règles référencé. Avant la version 2.2 de re2js, les blocs d'utilisation nécessitaient l'option -r --reusable.
/*!max:re2c[:<nom1>[:<nom2>...]] ... */ ou %{max[:<nom1>[:<nom2>...]] ... %}
Un bloc qui génère la définition YYMAXFILL. Une liste optionnelle de noms de blocs spécifie quels blocs doivent être inclus lors du calcul de la valeur YYMAXFILL (si la liste est vide, tous les blocs sont inclus). Par défaut, le code généré est une macro-définition pour C (#define YYMAXFILL <n>), ou une variable globale pour Go (var YYMAXFILL int = <n>). Cela peut être personnalisé avec une configuration optionnelle.
format qui spécifie une chaîne de modèle où @@{max} (ou @@ en abrégé) est remplacé par la valeur numérique de YYMAXFILL.
/*!maxnmatch:re2c[:<nom1>[:<nom2>...]] ... */ ou %{maxnmatch[:<nom1>[:<nom2>...]] ... %}
Un bloc qui génère la définition YYMAXNMATCH (il nécessite l'option -P --posix-captures). Une liste optionnelle de noms de blocs spécifie quels blocs doivent être inclus lors du calcul de la valeur de YYMAXNMATCH (si la liste est vide, tous les blocs sont inclus). Par défaut, le code généré est une macro-définition pour C (#define YYMAXNMATCH <n>), ou une variable globale pour Go (var YYMAXNMATCH int = <n>). Il peut être personnalisé avec une configuration optionnelle format qui spécifie une chaîne de modèle où @@{max} (ou @@ en abrégé) est remplacé par la valeur numérique de YYMAXNMATCH.
/*!stags:re2c[:<nom1>[:<nom2>...]] ... */, /*!mtags:re2c[:<nom1>[:<nom2>...]] ... */ ou %{stags[:<nom1>[:<nom2>...]] ... %}, %{mtags[:<nom1>[:<nom2>...]] ... %{
Blocs qui spécifient un morceau de code modèle qui est développé pour chaque variable de s-tag/m-tag générée par re2js. Une liste optionnelle de noms de blocs spécifie quels blocs doivent être inclus lors du calcul de l'ensemble des variables de tag (si la liste est vide, tous les blocs sont inclus). Il existe deux configurations optionnelles : format et separator. La configuration format spécifie une chaîne de modèle où @@{tag} (ou @@ en abrégé) est remplacé par le nom de chaque variable de tag. La configuration separator spécifie un morceau de code utilisé pour joindre les morceaux de format générés pour différentes variables de tag.
/*!svars:re2c[:<nom1>[:<nom2>...]] ... */, /*!mvars:re2c[:<nom1>[:<nom2>...]] ... */ ou %{svars[:<nom1>[:<nom2>...]] ... %}, %{mvars[:<nom1>[:<nom2>...]] ... %{
Blocs qui spécifient un morceau de code modèle qui est développé pour chaque s-tag/m-tag qui est soit explicitement mentionné par les règles (avec l'option --tags) soit implicitement généré par re2js (avec les options --captvars ou --posix-captvars). Une liste optionnelle de noms de blocs spécifie quels blocs doivent être inclus lors du calcul de l'ensemble des tags (si la liste est vide, tous les blocs sont inclus). Il existe deux configurations optionnelles : format et separator. La configuration format spécifie une chaîne de modèle où @@{tag} (ou @@ en abrégé) est remplacé par le nom de chaque tag. La configuration separator spécifie un morceau de code utilisé pour joindre les morceaux de format générés pour différents tags.
/*!getstate:re2c[:<nom1>[:<nom2>...]] ... */ ou %{getstate[:<nom1>[:<nom2>...]] ... %}
Un bloc qui génère une distribution conditionnelle sur l'état du lexer (il nécessite l'option --storable-state). Une liste optionnelle de noms de blocs spécifie quels blocs doivent être inclus dans la distribution d'état. La transition par défaut va à l'étiquette de début du premier bloc de la liste. Si la liste est vide, tous les blocs sont inclus, et la transition par défaut va au premier bloc du fichier qui a une étiquette de début. Ce type de bloc est incompatible avec l'option --loop-switch, car il nécessite des transitions inter-blocs qui ne sont pas supportées sans goto ou appels de fonction.
/*!conditions:re2c[:<nom1>[:<nom2>...]] ... */, /*!types:re2c... */ ou %{conditions[:<nom1>[:<nom2>...]] ... %}, %{types... %}
Un bloc qui génère une énumération de conditions (il nécessite l'option --conditions). Une liste optionnelle de noms de blocs spécifie quels blocs doivent être inclus lors du calcul de l'ensemble des conditions (si la liste est vide, tous les blocs sont inclus). Par défaut, le code généré est une énumération YYCONDTYPE. Il peut être personnalisé avec des configurations optionnelles format et separator. La configuration format spécifie une chaîne de modèle où @@{cond} (ou @@ en abrégé) est remplacé par le nom de chaque condition, et @@{num} est remplacé par un index numérique de cette condition. La configuration separator spécifie un morceau de code utilisé pour joindre les morceaux de format générés pour différentes conditions.
/*!include:re2c <fichier> */ ou %{include <fichier> %}
Ce bloc permet d'inclure <fichier>, qui doit être un chemin de fichier entre guillemets doubles. Le contenu du fichier est littéralement substitué à la place du bloc, de la même manière que #include fonctionne en C/C++. Ce bloc peut être utilisé en conjonction avec l'option --depfile pour générer des dépendances du système de build sur les fichiers inclus.
/*!header:re2c:on*/ ou %{header:on %}
Ce bloc marque le début du fichier d'en-tête. Tout ce qui suit et jusqu'au bloc header:off suivant est traité par re2js et écrit dans le fichier d'en-tête spécifié avec l'option -t --type-header.
/*!header:re2c:off*/ ou %{header:off %}
Ce bloc marque la fin du fichier d'en-tête commencé avec le bloc header:on*/.
/*!ignore:re2c ... */ ou %{ignore ... %}
Un bloc dont le contenu est ignoré et supprimé du fichier de sortie.

Configurations

Voici une liste complète des configurations prises en charge par re2js :

re2c:api, re2c:input
Identique à l'option --api.
re2c:api:sigil
Spécifie le marqueur ("sigil") utilisé pour les espaces réservés d'arguments dans les primitives d'API. La valeur par défaut est @@. Un espace réservé commence par le sigil suivi du nom de l'argument entre accolades. Par exemple, si le sigil est défini sur $, les espaces réservés auront la forme ${nom}. Les API à argument unique peuvent utiliser une notation abrégée sans le nom entre accolades. Cette option peut être remplacée par des options pour des primitives d'API individuelles, par exemple re2c:YYFILL@len pour YYFILL.
re2c:api:style
Spécifie le style de l'API. Les valeurs possibles sont functions (la valeur par défaut pour C) et free-form (la valeur par défaut pour Go et Rust). Dans le style functions, les primitives d'API sont générées avec une liste d'arguments entre parenthèses suivant le nom de la primitive. Les arguments ne sont fournis que pour les paramètres autogénérés (tels que le nombre de caractères passés à YYFILL), mais pas pour le contexte général du lexer, de sorte que les primitives se comportent davantage comme des macros en C/C++ ou des fermetures en Go et Rust. Dans le style free-form, les primitives d'API n'ont pas de forme fixe : elles doivent être définies comme des chaînes contenant des morceaux de code libre avec des variables interpolées de la forme @@{var} ou @@ (elles correspondent aux arguments dans le style fonctionnel). Cette configuration peut être remplacée pour des primitives d'API individuelles, voir par exemple la configuration re2c:YYFILL:naked pour YYFILL.
re2c:bit-vectors, re2c:flags:bit-vectors, re2c:flags:b
Identique à l'option --bit-vectors, mais peut être configuré bloc par bloc.
re2c:captures, re2c:leftmost-captures
Identique à l'option --leftmost-captures, mais peut être configuré bloc par bloc.
re2c:captvars, re2c:leftmost-captvars
Identique à l'option --leftmost-captvars, mais peut être configuré bloc par bloc.
re2c:case-insensitive, re2c:flags:case-insensitive
Identique à l'option --case-insensitive, mais peut être configuré bloc par bloc.
re2c:case-inverted, re2c:flags:case-inverted
Identique à l'option --case-inverted, mais peut être configuré bloc par bloc.
re2c:case-ranges, re2c:flags:case-ranges
Identique à l'option --case-ranges, mais peut être configuré bloc par bloc.
re2c:computed-gotos, re2c:flags:computed-gotos, re2c:flags:g

re2c:computed-gotos:relative, re2c:cgoto:relative
Identique à l'option --computed-gotos-relative, mais peut être configuré bloc par bloc.
re2c:computed-gotos:threshold, re2c:cgoto:threshold
Si le goto calculé est utilisé, cette configuration spécifie le seuil de complexité qui déclenche la génération de tables de sauts au lieu d'instructions if imbriquées et de bitmaps. La valeur par défaut est 9.
re2c:cond:abort
Si définie à une valeur entière positive, le cas par défaut dans la distribution de conditions générée interrompt l'exécution du programme.
re2c:cond:goto
Spécifie un morceau de code utilisé pour les règles de raccourci autogénérées :=> dans les conditions. La valeur par défaut est goto @@;. L'espace réservé @@ est substitué par le nom de la condition (voir les configurations re2c:api:sigil et re2c:cond:goto@cond).
re2c:cond:goto@cond
Spécifie le sigil utilisé pour la substitution d'arguments dans la définition de re2c:cond:goto. La valeur par défaut est @@. Remplace la configuration plus générique re2c:api:sigil.
re2c:cond:divider
Définit le séparateur pour les blocs de conditions. La valeur par défaut est /* *********************************** */. Les espaces réservés sont substitués par le nom de la condition (voir re2c:api;sigil et re2c:cond:divider@cond).
re2c:cond:divider@cond
Spécifie le sigil utilisé pour l'arg
ument substitution dans la définition re2c:cond:divider. La valeur par défaut est @@. Remplace la configuration plus générique re2c:api:sigil.
re2c:cond:prefix, re2c:condprefix
Spécifie le préfixe utilisé pour les étiquettes de condition. La valeur par défaut est yyc_.
re2c:cond:enumprefix, re2c:condenumprefix
Spécifie le préfixe utilisé pour les identifiants de condition. La valeur par défaut est yyc.
re2c:debug-output, re2c:flags:debug-output, re2c:flags:d

re2c:header, re2c:flags:type-header, re2c:flags:t
Spécifie le nom du fichier d'en-tête généré par rapport au répertoire du fichier de sortie. Identique à l'option --header, sauf que le chemin du fichier est relatif.
re2c:indent:string
Spécifie la chaîne utilisée pour l'indentation. La valeur par défaut est un unique caractère de tabulation "\t". La chaîne d'indentation doit contenir uniquement des caractères d'espacement. Pour désactiver complètement l'indentation, définissez cette configuration sur une chaîne vide.
re2c:indent:top
Spécifie le montant minimum d'indentation à utiliser. La valeur par défaut est zéro. La valeur doit être un nombre entier non négatif.
re2c:invert-captures
Identique à l'option --invert-captures, mais peut être configuré par bloc.
re2c:label:prefix, re2c:labelprefix
Spécifie le préfixe utilisé pour les étiquettes d'état de l'AFN. La valeur par défaut est yy.
re2c:label:start, re2c:startlabel
Contrôle la génération d'une étiquette de début de bloc. La valeur par défaut est zéro, ce qui signifie que l'étiquette de début est générée uniquement si elle est utilisée. Une valeur entière supérieure à zéro force la génération de l'étiquette de début, même si elle n'est pas utilisée par le lexer. Une valeur de chaîne force également la génération de l'étiquette de début et définit le nom de l'étiquette à la chaîne spécifiée. Cette configuration ne s'applique qu'au bloc courant (elle est réinitialisée à la valeur par défaut pour le bloc suivant).
re2c:label:yyFillLabel
Spécifie le préfixe des étiquettes YYFILL utilisées avec re2c:eof et en mode d'état stockable.
re2c:label:yyloop
Spécifie le nom de l'étiquette marquant le début de la boucle du lexer avec l'option --loop-switch. La valeur par défaut est yyloop.
re2c:label:yyNext
Spécifie le nom de l'étiquette optionnelle qui suit le commutateur YYGETSTATE en mode d'état stockable (activé avec re2c:state:nextlabel). La valeur par défaut est yyNext.
re2c:lookahead, re2c:flags:lookahead
Obsolète (voir l'option obsolète --no-lookahead).
re2c:monadic
Si défini sur une valeur non nulle, le lexer généré utilisera la notation monadique (cette configuration est spécifique à Haskell).
re2c:nested-ifs, re2c:flags:nested-ifs, re2c:flags:s
Identique à l'option --nested-ifs, mais peut être configuré par bloc.
re2c:posix-captures, re2c:flags:posix-captures, re2c:flags:P
Identique à l'option --posix-captures, mais peut être configuré par bloc.
re2c:posix-captvars
Identique à l'option --posix-captvars, mais peut être configuré par bloc.
re2c:tags, re2c:flags:tags, re2c:flags:T
Identique à l'option --tags, mais peut être configuré par bloc.
re2c:tags:expression
Spécifie l'expression utilisée pour les variables de balise. Par défaut, re2js génère des expressions de la forme yyt<N>. Cela peut être gênant, par exemple si les variables de balise sont définies comme des champs dans une structure. Toutes les occurrences de @@{tag} ou @@ sont remplacées par le nom de balise réel. Par exemple, re2c:tags:expression = "s.@@"; génère des expressions de la forme s.yyt<N> dans le code généré. Voir aussi la configuration re2c:api:sigil.
re2c:tags:negative
Spécifie l'expression constante utilisée pour la valeur de balise négative (généralement -1 si les balises sont des décalages d'entiers dans la chaîne d'entrée, ou un pointeur nul s'il s'agit de pointeurs).
re2c:tags:prefix
Spécifie le préfixe pour les noms de variables de balise. La valeur par défaut est yyt.
re2c:sentinel
Spécifie le symbole sentinelle utilisé pour les vérifications de fin d'entrée (lorsque les vérifications de limites sont désactivées avec re2c:yyfill:enable = 0; et que re2c:eof n'est pas défini). Cette configuration n'affecte pas la génération de code : son but est de vérifier que la sentinelle n'est pas autorisée au milieu d'une règle et de s'assurer que le lexer ne lira pas au-delà de la fin du tampon. La valeur par défaut est -1` (dans ce cas, re2js suppose que la sentinelle est zéro, ce qui est le cas le plus courant). Seuls les nombres décimaux sont reconnus.
re2c:state:abort
Si défini sur une valeur entière positive, le cas par défaut dans la répartition d'état générée interrompt l'exécution du programme, et un cas -1 explicite contient une transition vers le début du bloc.
re2c:state:nextlabel
Contrôle si le commutateur YYGETSTATE est suivi d'une étiquette yyNext (la valeur par défaut est zéro, ce qui correspond à aucune étiquette). Alternativement, on peut utiliser re2c:label:start pour générer une étiquette de début spécifique, ou un bloc getstate explicite pour générer le commutateur YYGETSTATE séparément du bloc lexer.
re2c:unsafe, re2c:flags:unsafe
Identique à l'option --no-unsafe, mais peut être configuré par bloc. S'il est défini sur zéro, il supprime la génération d'enveloppes unsafe autour de YYPEEK. La valeur par défaut est non nulle (les enveloppes sont générées). Cette configuration est spécifique à Rust.
re2c:YYBACKUP, re2c:define:YYBACKUP
Définit la primitive d'API générique YYBACKUP.
re2c:YYBACKUPCTX, re2c:define:YYBACKUPCTX
Définit la primitive d'API générique YYBACKUPCTX.
re2c:YYCONDTYPE, re2c:define:YYCONDTYPE
Définit la primitive d'API YYCONDTYPE.
re2c:YYCTYPE, re2c:define:YYCTYPE
Définit la primitive d'API YYCTYPE.
re2c:YYCTXMARKER, re2c:define:YYCTXMARKER

Expressions régulières

re2js utilise la syntaxe suivante pour les expressions régulières :

"foo"
Littéral de chaîne sensible à la casse.
'foo'
Littéral de chaîne insensible à la casse.
[a-xyz], [^a-xyz]
Classe de caractères (éventuellement niée).
.
N'importe quel caractère sauf le saut de ligne.
R \ S
Différence des classes de caractères R et S.
R*
Zéro ou plusieurs occurrences de R.
R+
Une ou plusieurs occurrences de R.
R?
Occurrence optionnelle de R.
R{n}
Répétition de R exactement n fois.
R{n,}
Répétition de R au moins n fois.
R{n,m}
Répétition de R de n à m fois.
(R)
Simplement R ; les parenthèses sont utilisées pour modifier la priorité. Si l'extraction de sous-correspondances est activée, (R) est un groupe de capture ou un groupe sans capture en fonction de l'option --invert-captures.
(!R)
Si l'extraction de sous-correspondances est activée, (!R) est un groupe sans capture ou un groupe de capture en fonction de l'option --invert-captures.
R S
Concaténation : R suivi de S.
R | S
Alternative : R ou S.
R / S
Lookahead : R suivi de S, mais S n'est pas consommé.
name
Expression régulière définie comme name (ou chaîne littérale "name" en mode compatibilité Flex).
{name}
Expression régulière définie comme name en mode compatibilité Flex.
@stag
Un s-tag : sauvegarde la dernière position d'entrée à laquelle @stag correspond dans une variable nommée stag.
#mtag
Un m-tag : sauvegarde toutes les positions d'entrée auxquelles #mtag correspond dans une variable nommée mtag.

Les classes de caractères et les littéraux de chaînes peuvent contenir les séquences d'échappement suivantes : \a, \b, \f, \n, \r, \t, \v, \\, échappements octaux \ooo et échappements hexadécimaux \xhh, \uhhhh et \Uhhhhhhhh.

Actions

Voici une liste des actions prédéfinies prises en charge par re2js :

!entry code
L'action d'entrée associe un bloc de code défini par l'utilisateur à l'état de départ de la machine à états finis actuelle. Si des *conditions de départ* sont utilisées, l'action d'entrée peut être définie individuellement pour chaque condition. Cette action peut être utilisée pour effectuer des initialisations, par exemple pour sauvegarder la position de départ d'un lexème.
!pre_rule code
L'action pré-règle ajoute un bloc de code défini par l'utilisateur au début des actions sémantiques de toutes les règles du bloc actuel (ou de la condition, si des *conditions de départ* sont utilisées). Cette action peut être utilisée pour factoriser la partie commune de toutes les actions sémantiques (par exemple, sauvegarder la position de fin d'un lexème).
!post_rule code
L'action post-règle ajoute un bloc de code défini par l'utilisateur à la fin des actions sémantiques de toutes les règles du bloc actuel (ou de la condition, si des *conditions de départ* sont utilisées). Cette action peut être utilisée pour émettre des instructions de "trap" qui protègent contre les flux de contrôle involontaires.

Directives

Voici une liste complète des directives prises en charge par re2js :

!use:name ;
Une directive `use` intra-bloc qui fusionne un bloc de règles précédemment défini avec le nom spécifié dans le bloc actuel. Les définitions nommées, les configurations et les règles du bloc référencé sont ajoutées aux règles actuelles. Les conflits entre les règles et les configurations qui se chevauchent sont résolus de la manière habituelle : la première règle a la priorité, et la dernière configuration remplace les précédentes. Une exception concerne les règles spéciales *, $ et <!> pour lesquelles une définition locale au bloc a toujours la priorité. Une directive `use` peut être placée n'importe où à l'intérieur d'un bloc, et plusieurs directives `use` sont autorisées.
!include file ;
Cette directive est identique à la directive de bloc include : elle insère le contenu de file verbatim à la place de la directive.

Interface du programme

Le code généré interagit avec le programme externe à l'aide de primitives, collectivement appelées API. Les primitives qui doivent être définies pour un programme particulier dépendent de plusieurs facteurs, notamment la complexité des expressions régulières, la représentation de l'entrée, la mise en mémoire tampon et l'utilisation de diverses fonctionnalités. Toutes les primitives nécessaires doivent être définies par l'utilisateur sous forme de macros, fonctions, variables ou toute autre forme appropriée qui rend le code généré syntaxiquement et sémantiquement correct. re2js ne vérifie pas (et ne peut pas vérifier) les définitions, donc si quelque chose manque ou est mal défini, le programme généré peut avoir des erreurs de compilation ou d'exécution. Ce manuel fournit des exemples de définitions d'API dans les cas les plus courants.

re2js possède trois styles d'API qui définissent l'ensemble de base des primitives utilisées par un programme :

API Simple
C'est l'API par défaut pour le backend JavaScript. Elle se compose des primitives suivantes : YYINPUT (qui doit être définie comme une séquence d'unités de code, par exemple une chaîne de caractères) et YYCURSOR, YYMARKER, YYCTXMARKER, YYLIMIT (qui doivent être définis comme des indices dans YYINPUT).
API Enregistrement
L'API Enregistrement est utile dans les cas où l'état du lexer doit être stocké dans un objet. Elle est activée avec l'option --api record ou la configuration re2c:api = record. Cette API se compose d'une variable yyrecord (le nom peut être remplacé par re2c:yyrecord) qui doit être définie comme un objet avec les propriétés yyinput, yycursor, yymarker, yyctxmarker, yylimit (seuls les champs utilisés par le code généré doivent être définis, et leurs noms peuvent être configurés).
API Générique
C'est l'API la plus flexible. Elle est activée avec l'option --api generic ou la configuration re2c:api = generic. Elle contient des primitives pour les opérations génériques : YYPEEK, YYSKIP, YYBACKUP, YYBACKUPCTX, YYSTAGP, YYSTAGN, YYMTAGP, YYMTAGN, YYRESTORE, YYRESTORECTX, YYRESTORETAG, YYSHIFT, YYSHIFTSTAG, YYSHIFTMTAG, YYLESSTHAN.

Voici une liste complète des primitives d'API qui peuvent être utilisées par le code généré pour interagir avec le programme externe.

YYCTYPE
Le type des caractères d'entrée (unités de code). Pour les encodages ASCII, EBCDIC et UTF-8, il doit s'agir d'un entier non signé de 1 octet. Pour UTF-16 ou UCS-2, il doit s'agir d'un entier non signé de 2 octets. Pour UTF-32, il doit s'agir d'un entier non signé de 4 octets.
YYCURSOR
Une valeur l-value qui stocke la position d'entrée actuelle (un pointeur ou un décalage d'entier dans YYINPUT). Initialement, YYCURSOR doit pointer vers le premier caractère d'entrée, et plus tard, il est avancé par le code généré. Lorsqu'une règle correspond, la position YYCURSOR est celle après le dernier caractère correspondant.
YYLIMIT
Une valeur r-value qui stocke la fin de la position d'entrée (un pointeur ou un décalage d'entier dans YYINPUT). Initialement, YYLIMIT doit pointer vers la position après le dernier caractère d'entrée disponible. Il n'est pas modifié par le code généré. Le lexer compare YYCURSOR à YYLIMIT pour déterminer s'il reste suffisamment de caractères d'entrée.
YYMARKER
Une valeur l-value qui stocke la position de la dernière règle correspondante (un pointeur ou un décalage d'entier dans YYINPUT). Elle est utilisée pour restaurer la position YYCURSOR si la correspondance la plus longue échoue et que le lexer doit revenir en arrière. Aucune initialisation n'est nécessaire.
YYCTXMARKER
Une valeur l-value qui stocke la position du contexte de suivi (un pointeur ou un décalage d'entier dans YYINPUT). Aucune initialisation n'est nécessaire. YYCTXMARKER n'est nécessaire que si l'opérateur de lookahead / est utilisé.
YYFILL
Une primitive d'API générique avec une variable len. YYFILL doit fournir au moins len caractères d'entrée supplémentaires ou échouer. Si re2c:eof est utilisé, alors len est toujours 1 et YYFILL doit toujours retourner à la fonction appelante ; une valeur de retour nulle indique le succès. Si re2c:eof n'est pas utilisé, alors la valeur de retour de YYFILL est ignorée et elle ne doit pas retourner en cas d'échec. La valeur maximale de len est YYMAXFILL.
YYFN
Une primitive qui définit le prototype de fonction dans
--recursive-functions code model. Sa valeur doit être un tableau d'une ou plusieurs chaînes de caractères, où chaque chaîne contient deux ou trois composantes séparées par la chaîne spécifiée dans la configuration re2c:fn:sep (typiquement un point-virgule). Le premier élément du tableau définit le nom de la fonction et le type de retour (vide pour une fonction void). Les éléments suivants définissent les arguments de la fonction : premièrement, l'expression de l'argument utilisée dans le corps de la fonction (généralement juste un nom) ; deuxièmement, le type de l'argument ; troisièmement, un paramètre formel optionnel (il est par défaut la première composante - généralement, l'argument et le paramètre sont le même identifiant).
YYINPUT
Une r-value qui stocke la séquence de caractères d'entrée actuelle (chaîne, tampon, etc.).
YYMAXFILL
Une constante entière égale à la valeur maximale de l'argument de YYFILL. Elle peut être générée avec un bloc max.
YYLESSTHAN
Une primitive d'API générique avec une variable len. Elle doit être définie comme une r-value de type booléen qui est égale à true si et seulement s'il reste moins de len caractères d'entrée.
YYPEEK
Une primitive d'API générique sans variable. Elle doit être définie comme une r-value de type YYCTYPE qui est égale au caractère à la position d'entrée actuelle.
YYSKIP
Une primitive d'API générique qui doit faire avancer la position d'entrée actuelle d'une unité de code.
YYBACKUP
Une primitive d'API générique qui doit sauvegarder la position d'entrée actuelle (pour être restaurée plus tard avec YYRESTORE).
YYRESTORE
Une primitive d'API générique qui doit restaurer la position d'entrée actuelle à la valeur sauvegardée par YYBACKUP.
YYBACKUPCTX
Une primitive d'API générique qui doit sauvegarder la position d'entrée actuelle comme position du contexte final (pour être restaurée plus tard avec YYRESTORECTX).
YYRESTORECTX
Une primitive d'API générique qui doit restaurer la position du contexte final sauvegardée avec YYBACKUPCTX.
YYRESTORETAG
Une primitive d'API générique avec une variable tag qui doit restaurer la position du contexte final à la valeur de tag.
YYSTAGP
Une primitive d'API générique avec une variable tag, où tag peut être un pointeur ou un décalage dans YYINPUT (voir la section sur l'extraction des sous-correspondances pour plus de détails). YYSTAGP doit définir tag à la position d'entrée actuelle.
YYSTAGN
Une primitive d'API générique avec une variable tag, où tag peut être un pointeur ou un décalage dans YYINPUT (voir la section sur l'extraction des sous-correspondances pour plus de détails). YYSTAGN doit définir tag à une valeur qui représente une position d'entrée inexistante.
YYMTAGP
Une primitive d'API générique avec une variable tag. YYMTAGP doit ajouter la position actuelle à l'historique des sous-correspondances de tag (voir la section sur l'extraction des sous-correspondances pour plus de détails).
YYMTAGN
Une primitive d'API générique avec une variable tag. YYMTAGN doit ajouter une valeur qui représente une position d'entrée inexistante à l'historique des sous-correspondances de tag (voir la section sur l'extraction des sous-correspondances pour plus de détails).
YYSHIFT
Une primitive d'API générique avec une variable shift qui doit décaler la position d'entrée actuelle de shift caractères (la valeur du décalage peut être négative).
YYCOPYSTAG
Une primitive d'API générique avec deux variables, lhs et rhs, qui doit copier la variable s-tag du membre de droite rhs vers la variable s-tag du membre de gauche lhs. Pour la plupart des langages, cette primitive a une définition par défaut qui assigne lhs à rhs.
YYCOPYMTAG
Une primitive d'API générique avec deux variables, lhs et rhs, qui doit copier la variable m-tag du membre de droite rhs vers la variable m-tag du membre de gauche lhs. Pour la plupart des langages, cette primitive a une définition par défaut qui assigne lhs à rhs.
YYSHIFTSTAG
Une primitive d'API générique avec deux variables, tag et shift, qui doit décaler tag de shift unités de code (la valeur du décalage peut être négative).
YYSHIFTMTAG
Une primitive d'API générique avec deux variables, tag et shift, qui doit décaler la dernière valeur de l'historique de tag de shift unités de code (la valeur du décalage peut être négative).
YYMAXNMATCH
Une constante entière égale au nombre maximal de groupes de capture POSIX dans une règle. Elle est générée avec un bloc maxnmatch.
YYCONDTYPE
Le type de l'énumération de conditions. Il peut être généré soit avec le bloc conditions, soit avec l'option --header.
YYGETACCEPT
Une primitive avec une variable var qui stocke le sélecteur numérique de la règle acceptée. Pour la plupart des langages, cette primitive a une définition par défaut qui lit à partir de var.
YYSETACCEPT
Une primitive avec deux variables : var (une l-value qui stocke le sélecteur numérique de la règle acceptée) et val (la valeur du sélecteur). Pour la plupart des langages, cette primitive a une définition par défaut qui assigne var à val.
YYGETCOND
Une r-value de type YYCONDTYPE qui est égale à l'identifiant de condition actuel.
YYSETCOND
Une primitive avec une variable cond qui doit définir l'identifiant de condition actuel à cond.
YYGETSTATE
Une r-value de type entier qui est égale à l'état actuel du lexer. Elle doit être initialisée à -1.
YYSETSTATE
Une primitive avec une variable state qui doit définir l'état actuel du lexer à state.
YYDEBUG
Cette primitive n'est générée qu'avec l'option -d, --debug-output. Son but est d'ajouter des journaux au code généré (la définition typique de YYDEBUG est une instruction d'impression). Les instructions YYDEBUG sont générées dans chaque état et ont deux variables : state (soit un index d'état DFA, soit -1) et symbol (le symbole d'entrée actuel).
yyaccept
Une l-value de type entier non signé qui stocke le numéro de la dernière règle correspondante. La définition par l'utilisateur n'est nécessaire qu'avec l'option --storable-state.
yybm
Une table contenant des bitmaps compressées pour jusqu'à 8 transitions (utilisée avec l'option --bitmaps). La table contient 256 éléments et est indexée par des unités de code de 1 octet. Chaque élément de 8 bits combine des valeurs booléennes pour jusqu'à 8 transitions. Le k-ième bit du n-ième élément est vrai si et seulement si la n-ième unité de code est dans la plage de la k-ième transition. L'idée de cette bitmap est de remplacer de nombreuses branches if ou cas switch par une seule vérification d'un seul bit dans la table.
yych
Une l-value de type YYCTYPE qui stocke le caractère d'entrée actuel. La définition par l'utilisateur n'est nécessaire qu'avec l'option -f --storable-state.
yyctable
Table de saut générée pour la répartition initiale des conditions (activée avec la combinaison des options --conditions et --computed-gotos).
yyfill
Une l-value qui stocke le résultat de l'appel YYFILL (cela peut être nécessaire pour les langages purement fonctionnels, où YYFILL est une fonction monadique avec une valeur de retour complexe).
yynmatch
Une l-value de type entier non signé qui stocke le nombre de groupes de capture POSIX dans la règle correspondante. Utilisé uniquement avec l'option -P --posix-captures.
yypmatch
Un tableau de l-values qui sont utilisées pour contenir les valeurs de tags correspondant aux parenthèses de capture dans la règle correspondante. La longueur du tableau doit être d'au moins yynmatch * 2 (généralement YYMAXNMATCH * 2 est un bon choix). Utilisé uniquement avec l'option -P --posix-captures.
yystable
Obsolète.
yystate
Une l-value utilisée avec l'option --loop-switch pour stocker l'état actuel du DFA.
yytarget
Table de saut qui contient les cibles de saut (adresses d'étiquettes) pour toutes les transitions d'un état. Cette table est locale à chaque état. La génération des tables yytarget est activée avec l'option --computed-gotos.

Options

Certaines options ont des configurations correspondantes, d'autres sont globales et ne peuvent pas être modifiées après que re2c commence à lire le fichier d'entrée. Les options de débogage nécessitent généralement de construire re2c dans une configuration de débogage. Les options internes sont utiles pour expérimenter les algorithmes utilisés dans re2c.

-? --help -h
Afficher le message d'aide.
--api <simple | record | generic>
Spécifie l'API utilisée par le code généré pour interagir avec le code défini par l'utilisateur. L'option simple doit être utilisée dans les cas simples où il n'y a pas besoin de rechargement de tampon et de stockage de l'état du lexer. L'option record doit être utilisée lorsque l'état du lexer doit être stocké dans un enregistrement (struct, class, etc.). L'option generic doit être utilisée dans les cas complexes où les deux autres API ne sont pas assez flexibles.
--bit-vectors -b
Optimise les sauts conditionnels à l'aide de masques de bits. Cette option implique --nested-ifs.
--captures, --leftmost-captures
Active l'extraction de sous-correspondances avec des groupes de capture gourmands les plus à gauche. Le résultat est collecté dans un tableau yybmatch de capacité 2 * YYMAXNMATCH, et yynmatch est défini sur le nombre de groupes pour la règle de correspondance.
--captvars, --leftmost-captvars
Active l'extraction de sous-correspondances avec des groupes de capture gourmands les plus à gauche. Le résultat est collecté dans les variables yytl<k>, yytr<k> pour le k-ième groupe de capture.
--case-insensitive
Traite les chaînes entre guillemets simples et doubles comme insensibles à la casse.
--case-inverted
Inverse la signification des chaînes entre guillemets simples et doubles : traite les chaînes entre guillemets simples comme sensibles à la casse et les chaînes entre guillemets doubles comme insensibles à la casse.
--case-ranges
Réduit les cas consécutifs dans les instructions switch en une plage de la forme low ... high. Cette syntaxe est une extension du langage C/C++ prise en charge par des compilateurs comme GCC, Clang et Tcc. Le principal avantage par rapport à l'utilisation de cas uniques est la réduction du code généré et du temps de génération, bien que pour certains compilateurs comme Tcc, elle entraîne également une taille binaire plus petite.
--computed-gotos -g
Optimise les sauts conditionnels à l'aide de l'extension non standard "computed goto" (qui doit être prise en charge par le compilateur). re2js génère des tables de saut uniquement dans les cas complexes avec de nombreuses branches conditionnelles. Le seuil de complexité peut être configuré avec la configuration cgoto:threshold. Les décalages relatifs peuvent être activés avec la configuration cgoto:relative. Cette option implique --bit-vectors.
--computed-gotos-relative
Similaire à --computed-gotos mais génère des décalages relatifs pour les tables de saut à la place (qui doivent être prises en charge par le compilateur). Cette option implique --computed-gotos.
--conditions --start-conditions -c
Active la prise en charge des "conditions" de type Flex : plusieurs lexers interdépendants au sein d'un même bloc. Ceci est une alternative à la spécification manuelle de différents blocs re2js connectés par goto ou des appels de fonction.
--depfile FILE
Écrit les informations de dépendance dans FILE sous la forme d'une règle Makefile <output-file> : <input-file> [include-file ...]. Cela permet de suivre les dépendances de construction en présence de blocs/directives include, de sorte que la mise à jour des fichiers inclus déclenche la régénération du fichier de sortie. Cette option dépend de l'option --output.
--ebcdic --ecb -e
Génère un lexer qui lit l'entrée en encodage EBCDIC. re2js suppose que la plage de caractères est 0 -- 0xFF et que la taille des caractères est de 1 octet.
--empty-class <match-empty | match-none | error>
Définit la manière dont re2js traite les classes de caractères vides. Avec match-empty (par défaut), la classe vide correspond à une entrée vide (ce qui est illogique, mais rétrocompatible). Avec match-none, la classe vide ne parvient jamais à correspondre. Avec error, la classe vide déclenche une erreur de compilation.
--encoding-policy <fail | substitute | ignore>
Définit la manière dont re2js traite les surrogates Unicode. Avec fail, re2js s'arrête avec une erreur lorsqu'un surrogate est rencontré. Avec substitute, re2js remplace silencieusement les surrogates par le point de code d'erreur 0xFFFD. Avec ignore (par défaut), re2js traite les surrogates comme des points de code normaux. La norme Unicode stipule que les surrogates autonomes sont invalides, mais les bibliothèques et les programmes réels se comportent différemment.
--flex-syntax -F
Prise en charge partielle de la syntaxe Flex : dans ce mode, les définitions nommées n'ont pas besoin du signe égal ni du point-virgule de fin, et lorsqu'elles sont utilisées, elles doivent être entourées d'accolades. Les noms sans accolades sont traités comme des chaînes entre guillemets doubles.
--goto-label
Utilise le modèle de code "goto/label" : encode le DFA sous forme de blocs de code étiquetés connectés par des transitions goto entre les blocs. Ceci n'est pris en charge que pour les langages qui ont une instruction goto.
--header --type-header -t HEADER
Génère un fichier HEADER. Le contenu du fichier peut être spécifié à l'aide des blocs spéciaux header:on et header:off. Si des conditions sont utilisées, l'en-tête généré aura automatiquement un enum de condition ajouté (sauf s'il existe un bloc conditions explicite).
-I PATH
Ajoute PATH à la liste des emplacements utilisés lors de la recherche de fichiers d'inclusion. Cette option est utile en combinaison avec le bloc ou la directive include. re2js recherche FILE dans le répertoire du fichier parent et dans les emplacements d'inclusion spécifiés avec l'option -I.
--input <default | custom>
Alias obsolète pour --api. L'option default correspond à simple (c'est effectivement le défaut pour la plupart des backends, mais pas pour tous). L'option custom correspond à generic.
--input-encoding <ascii | utf8>
Spécifie la manière dont re2js analyse les expressions régulières. Avec ascii (par défaut), re2js traite l'entrée comme étant encodée en ASCII : toute séquence d'unités de code est une séquence de caractères autonomes de 1 octet. Avec utf8, re2js traite l'entrée comme étant encodée en UTF8 et reconnaît les caractères multi-octets.
--invert-captures
Inverse la signification des groupes de capture et des groupes non capturants. Par défaut, (...) est capturant et (! ...) est non capturant. Avec cette option, (! ...) est capturant et (...) est non capturant.
--lang <none | c | d | go | haskell | java | js | ocaml | python | rust | swift | v | zig>
Spécifie le langage cible. Les langages pris en charge sont C, D, Go, Haskell, Java, JS, OCaml, Python, Rust, Swift, V, Zig (d'autres langages peuvent être ajoutés via des fichiers de syntaxe définis par l'utilisateur, voir l'option --syntax). L'option none désactive les configurations de syntaxe par défaut, de sorte que le langage cible soit indéfini.
--location-format <gnu | msvc>
Spécifie le format de localisation dans les messages. Avec gnu, les emplacements sont imprimés sous la forme 'filename:line:column: ...'. Avec msvc, les emplacements sont imprimés sous la forme 'filename(line,column) ...'. Le défaut est gnu.
--loop-switch
Utilise le modèle de code "loop/switch" : encode le DFA sous forme d'une boucle sur une instruction switch, où les états individuels sont des cas de switch. L'état est stocké dans une variable yystate. Les transitions entre les états mettent à jour yystate avec l'étiquette du cas de l'état de destination et continuent l'exécution vers la tête de la boucle.
--nested-ifs -s
Utilise des instructions if imbriquées au lieu d'instructions switch pour les sauts conditionnels. Cela conduit généralement à un code plus efficace avec les compilateurs non optimisants.
--no-debug-info -i
Ne pas générer de directives de ligne. Cela peut être utile lorsque le code généré est stocké dans un système de contrôle de version (pour éviter d'énormes différences générées automatiquement lors de petites modifications).
--no-generation-date

--no-version
Supprime la version de sortie dans le fichier généré.
--no-unsafe
Ne pas générer d'enveloppe unsafe autour de YYPEEK (cette option est spécifique à Rust). L'utilisateur peut choisir de fournir une définition YYPEEK sûre, ou une définition qui n'est sûre que dans les builds de production, auquel cas l'option --no-unsafe aide à éviter les avertissements concernant les blocs unsafe redondants.
--output -o OUTPUT
Spécifie le fichier OUTPUT.
--posix-captures, -P
Active l'extraction de sous-correspondances avec des groupes de capture de style POSIX. Le résultat est collecté dans un tableau yybmatch de capacité 2 * YYMAXNMATCH, et yynmatch est défini sur le nombre de groupes pour la règle de correspondance.
--posix-captvars

--recursive-functions
Utilise un modèle de code basé sur des fonctions co-récursives, où chaque état du DFA est une fonction distincte qui peut appeler d'autres fonctions d'état ou elle-même.
--reusable -r

De plus, génère des fichiers d'entrée avec des chaînes dérivées de la grammaire régulière et des résultats de correspondance compressés qui sont utilisés pour vérifier le comportement du "squelette" sur toutes les entrées. Cette option est utile pour trouver des bugs dans les optimisations et la génération de code. Cette option n'est prise en charge que pour C.
--storable-state -f
Génère un analyseur lexical capable de stocker son état interne. Ceci est utile dans les analyseurs lexicaux de type "push" qui sont arrêtés par un programme externe lorsqu'il n'y a pas assez d'entrée, puis repris lorsque davantage d'entrée devient disponible. --dfa-minimization <moore | table>
Option interne : algorithme de minimisation de DFA utilisé par re2js. L'option moore est l'algorithme de Moore (c'est le comportement par défaut). L'option table est l'algorithme de "remplissage de table". Les deux algorithmes devraient produire le même DFA jusqu'au re-étiquetage des états ; le remplissage de table est plus simple et beaucoup plus lent, et sert d'implémentation de référence.
--eager-skip
Option interne : fait avancer l'analyseur lexical généré de manière anticipée dans l'entrée -- immédiatement après la lecture du symbole d'entrée. Cela modifie le comportement par défaut où la position d'entrée est avancée paresseusement -- après la transition vers l'état suivant.
--no-lookahead
Option interne, obsolète. Elle permettait d'activer l'algorithme TDFA(0). Contrairement à TDFA(1), l'algorithme TDFA(0) n'utilise pas de lookahead d'un symbole. Il applique des opérations de registre aux transitions entrantes plutôt qu'aux sortantes. Des benchmarks ont montré que l'algorithme TDFA(0) est moins efficace que TDFA(1).
--no-optimize-tags
Option interne : supprime l'optimisation des variables de balises (utile pour le débogage).
--posix-closure <gor1 | gtop>
Option interne : spécifie l'algorithme de plus court chemin utilisé pour la construction de la clôture epsilon avec sémantique de désambiguïsation POSIX : gor1 (par défaut) signifie l'algorithme de Goldberg-Radzik, et gtop signifie l'algorithme "ordre topologique global".
--posix-prectable <complex | naive>
Option interne : spécifie l'algorithme utilisé pour calculer la table de précedence POSIX. L'algorithme complex calcule la table de précedence en un seul parcours de l'arbre d'historique des balises et a une complexité quadratique par rapport au nombre d'états TNFA ; c'est le comportement par défaut. L'algorithme naive a une complexité cubique dans le pire des cas par rapport au nombre d'états TNFA, mais il est beaucoup plus simple que complex et peut être légèrement plus rapide dans les cas non pathologiques.
--stadfa
Option interne, obsolète. Elle permettait d'activer l'algorithme staDFA, qui diffère de TDFA en ce que les opérations de registre sont placées dans les états plutôt que sur les transitions. Des benchmarks ont montré que l'algorithme staDFA est moins efficace que TDFA.
--fixed-tags <none | toplevel | all>
Option interne : spécifie si l'optimisation des balises fixes doit être appliquée à toutes les balises (all), à aucune d'entre elles (none), ou seulement à celles dans la concaténation de niveau supérieur (toplevel). Le comportement par défaut est all. Les balises "fixes" sont celles qui sont situées à une distance fixe d'une autre balise (appelée "base"). Dans de tels cas, seule la balise de base doit être suivie, et la valeur de la balise fixe peut être calculée comme la valeur de la balise de base plus un décalage statique. Pour les balises sous une alternative ou une répétition, il est également nécessaire de vérifier si la balise de base a une valeur de non-correspondance (dans ce cas, la balise fixe doit également être définie sur non-correspondance, ignorant le décalage). Pour les balises dans une concaténation de niveau supérieur, la vérification n'est pas nécessaire, car elles correspondent toujours.

Avertissements

Les avertissements peuvent être activés, désactivés et transformés en erreur individuellement.

-W
Active tous les avertissements.
-Werror
Transforme les avertissements en erreurs. Notez que cette option seule n'active aucun avertissement ; elle n'affecte que les avertissements qui ont été activés jusqu'à présent ou qui seront activés plus tard.
-W<avertissement>
Active l'avertissement.
-Wno-<avertissement>
Désactive l'avertissement.
-Werror-<avertissement>
Active l'avertissement et le traite comme une erreur (cela implique -W<avertissement>).
-Wno-error-<avertissement>
Ne traite pas cet avertissement particulier comme une erreur. Cela ne désactive pas l'avertissement lui-même.
-Wcondition-order
Avertit si le programme généré fait des hypothèses implicites sur le classement des conditions. Il faut utiliser soit l'option --header, soit le bloc conditions pour générer un mappage des noms de conditions aux numéros, puis utiliser les noms de conditions auto-générés.
-Wempty-character-class
Avertit si une expression régulière contient une classe de caractères vide. Essayer de faire correspondre une classe de caractères vide n'a pas de sens : elle devrait toujours échouer. Cependant, pour des raisons de compatibilité ascendante, re2js autorise les classes de caractères vides et les traite comme des chaînes vides. Utilisez l'option --empty-class pour modifier le comportement par défaut.
-Wmatch-empty-string
Avertit si une règle est nullable (m
(correspond à une chaîne vide). Si le lexer fonctionne en boucle et que la correspondance vide est involontaire, le lexer peut se bloquer de manière inattendue dans une boucle infinie.
-Wswapped-range
Avertit si la borne inférieure d'une plage est supérieure à sa borne supérieure. Le comportement par défaut est d'échanger silencieusement les bornes de la plage.
-Wundefined-control-flow
Avertit si certaines chaînes d'entrée provoquent un flux de contrôle indéfini dans le lexer (les motifs défectueux sont signalés). C'est une erreur courante et dangereuse. Avertit si une balise a un degré de nondéterminisme n, où n est supérieur à 1.

Fichiers de syntaxe

Le support des différents langages dans re2c repose sur l'idée des fichiers de syntaxe. Un fichier de syntaxe est un fichier de configuration qui définit la syntaxe du langage cible -- pas la totalité du langage, mais une petite partie de celui-ci qui est utilisée par le code généré. Les fichiers de syntaxe rendent re2c très flexible, mais ils ne doivent pas être utilisés comme substituts des configurations re2c:: leur but est de définir la syntaxe du langage cible, pas de personnaliser un lexer particulier. Tous les langages supportés ont des fichiers de syntaxe par défaut qui font partie de la distribution (voir le sous-répertoire include/syntax); ils sont également intégrés dans le binaire re2js. Les utilisateurs peuvent fournir un fichier de syntaxe personnalisé qui remplace quelques configurations pour l'un des langages supportés, ou ils peuvent choisir de redéfinir toutes les configurations (dans ce cas, l'option --lang none devrait être utilisée). Les fichiers de syntaxe contiennent des configurations de quatre types différents : listes de fonctionnalités, configurations de langage, configurations en place et modèles de code.

Une liste des API supportées avec des éléments possibles simple, record, generic.
supported_api_styles
Une liste des styles d'API supportés avec des éléments possibles functions, free-form.
supported_code_models
Une liste des modèles de code supportés avec des éléments possibles goto-label, loop-switch, recursive-functions.
supported_targets
Une liste des cibles de génération de code supportées avec des éléments possibles code, dot, skeleton.
supported_features
Une liste des fonctionnalités supportées avec des éléments possibles nested-ifs, bitmaps, computed-gotos, case-ranges, monadic, unsafe, tags, captures, captvars.

semicolons
Non nul si le langage utilise des points-virgules après les instructions.
backtick_quoted_strings
Non nul si le langage possède des chaînes entre guillemets inversés.
single_quoted_strings
Non nul si le langage possède des chaînes entre apostrophes.
indentation_sensitive
Non nul si le langage est sensible à l'indentation.

Non nul si les blocs d'instructions composites doivent être entourés d'accolades.

Configurations en place

Modèles de code

Les modèles de code définissent la syntaxe du langage cible. Ils sont écrits dans un langage simple spécifique à un domaine avec la grammaire formelle suivante : 
code-template ::
      name '=' code-exprs ';'
    | CODE_TEMPLATE ';'
    | '<undefined>' ';'
code-exprs ::
      <EMPTY>
    | code-exprs code-expr
code-expr ::
      STRING
    | VARIABLE
    | optional
    | list
optional ::
      '(' CONDITIONAL '?' code-exprs ')'
    | '(' CONDITIONAL '?' code-exprs ':' code-exprs ')'
list ::
      '[' VARIABLE ':' code-exprs ']'
    | '[' VARIABLE '{' NUMBER '}' ':' code-exprs ']'
    | '[' VARIABLE '{' NUMBER ',' NUMBER '}' ':' code-exprs ']'

Un modèle de code est une séquence de littéraux de chaîne, de variables, d'éléments optionnels et de listes, ou une référence à un autre modèle de code, ou une valeur spéciale <undefined>. Les variables sont des espaces réservés qui sont substitués pendant la phase de génération de code. Les variables de liste sont spéciales : lors de l'expansion des modèles de liste, re2js répète les expressions du côté droit de la colonne plusieurs fois, remplaçant à chaque fois les occurrences de la variable de liste par une valeur spécifique à cette répétition. Les listes ont des bornes optionnelles (les valeurs négatives sont comptées à partir de la fin, par exemple -1 signifie le dernier élément). Les noms conditionnels commencent par un point. Les conditions et les variables peuvent être locales (spécifiques au modèle de code donné) ou globales (autorisées dans tous les modèles de code). Lorsque re2js lit un fichier de syntaxe, il vérifie que chaque modèle de code n'utilise que les variables et les conditions qui lui sont autorisées.

Par exemple, le modèle de code suivant définit une construction si-alors-sinon pour un langage de type C :

code:if_then_else =
    [branch{0}: topindent "if " cond " {" nl
        indent [stmt: stmt] dedent]
    [branch{1:-1}: topindent "} else" (.cond ? " if " cond) " {" nl
        indent [stmt: stmt] dedent]
    topindent "}" nl;

Ici, branch est une variable de liste : branch{0} s'étend à la première branche (qui est spéciale, car il n'y a pas de partie else), branch{1:-1} s'étend à toutes les branches restantes (s'il y en a). stmt est également une variable de liste : [stmt: stmt] est une liste imbriquée qui s'étend à une liste d'instructions dans le corps de la branche actuelle. topindent, indent, dedent et nl sont des variables globales, et .cond est une condition locale (leur signification est décrite ci-dessous). Ce modèle de code pourrait produire le code suivant :

if x {
    // do something
} else if y {
    // do something else
} else {
    // don't do anything
}

GESTION DE LA FIN DE L'ENTRÉE

L'un des principaux problèmes pour le lexer est de savoir quand s'arrêter. Il existe plusieurs conditions de terminaison :

  • le lexer peut correspondre à une règle (y compris la règle par défaut *) et arriver à un état final
  • le lexer peut ne pas correspondre à une règle et arriver à un état par défaut
  • le lexer peut atteindre la fin de l'entrée

Les deux premières conditions terminent le lexer d'une manière "naturelle" : il arrive à un état sans transitions sortantes, et la correspondance s'arrête automatiquement. La troisième condition, la fin de l'entrée, est différente : elle peut survenir dans n'importe quel état, et le lexer doit pouvoir la gérer. La vérification de la fin de l'entrée interrompt le flux normal du lexer et ajoute des branches conditionnelles au programme généré, il est donc nécessaire de minimiser le nombre de ces vérifications. re2js prend en charge plusieurs méthodes pour gérer la fin de l'entrée. Laquelle utiliser dépend de la complexité des expressions régulières, du besoin de mise en tampon, des considérations de performance et d'autres facteurs. Voici une liste de méthodes :

  • Sentinelle. Cette méthode élimine complètement le besoin de vérifier la fin de l'entrée. Elle est simple et efficace, mais limitée au cas où il existe un caractère de "sentinelle" naturel qui ne peut jamais se produire dans une entrée valide. Ce caractère peut toujours se produire dans une entrée invalide, mais il ne devrait pas être autorisé par les expressions régulières, sauf peut-être comme dernier caractère d'une règle. La sentinelle est ajoutée à la fin de l'entrée et sert de signal d'arrêt : lorsque le lexer lit ce caractère, il s'agit soit d'une erreur de syntaxe, soit de la fin de l'entrée. Dans les deux cas, le lexer doit s'arrêter. Cette méthode est utilisée si YYFILL est désactivé avec re2c:yyfill:enable = 0; et re2c:eof a la valeur par défaut -1.
  • Sentinelle avec vérifications de limites. Cette méthode est générique : elle permet de gérer n'importe quelle entrée sans restrictions sur les expressions régulières. L'idée est de réduire le nombre de vérifications de fin d'entrée en ne les effectuant que sur certains caractères. Similaire à la méthode "sentinelle", l'un des caractères est choisi comme "sentinelle" et ajouté à la fin de l'entrée. Cependant, il n'y a aucune restriction quant à l'endroit où la sentinelle peut se produire (en fait, n'importe quel caractère peut être choisi pour une sentinelle). Lorsque le lexer lit ce caractère, il effectue en plus une vérification de limites. Si la position courante est dans les limites, le lexer reprend la correspondance et gère la sentinelle comme un caractère normal. Sinon, il invoque YYFILL (sauf si elle est désactivée). Si davantage d'entrée est fournie, le lexer remontera le dernier caractère et continuera comme si la sentinelle n'était pas là. Sinon, il doit s'agir de la fin réelle de l'entrée, et le lexer s'arrête. Cette méthode est utilisée lorsque re2c:eof a une valeur non négative (elle doit être définie à la valeur numérique de la sentinelle). YYFILL est facultatif.
  • Vérifications de limites avec remplissage. Cette méthode est générique et peut être plus rapide que la méthode "sentinelle avec vérifications de limites", mais elle est aussi plus complexe. L'idée est de partitionner les états du DFA en composantes fortement connexes (SCC) et de générer une seule vérification par SCC pour suffisamment de caractères afin de couvrir le chemin non cyclique le plus long dans cette SCC. Cela réduit le nombre de vérifications, mais il y a un problème avec les lexèmes courts à la fin de l'entrée, car la vérification nécessite suffisamment de caractères pour couvrir le lexème le plus long. Cela peut être corrigé en remplissant l'entrée avec quelques caractères factices qui ne forment pas un suffixe de lexème valide (de sorte que le lexer ne puisse pas les faire correspondre). La longueur du remplissage doit être YYMAXFILL, généré avec un bloc max. S'il n'y a pas assez d'entrée, le lexer invoque YYFILL qui doit fournir au moins le nombre requis de caractères ou ne pas retourner. Cette méthode est utilisée si YYFILL est activé et re2c:eof est -1 (c'est la configuration par défaut).
  • Vérifications personnalisées. L'API générique permet de remplacer les opérations de base comme la lecture d'un caractère, ce qui rend possible l'inclusion des vérifications de fin d'entrée dans celles-ci. Cette approche est sujette aux erreurs et doit être utilisée avec prudence. Pour utiliser une méthode personnalisée, activez l'API générique avec --api custom ou re2c:api = custom; et désactivez les vérifications de limites par défaut avec re2c:yyfill:enable = 0; ou re2c:yyfill:check = 0;.

Sentinelle

Cet exemple utilise un caractère de sentinelle pour gérer la fin de l'entrée. Le programme compte les mots séparés par des espaces dans une chaîne terminée par null. La sentinelle est le caractère null : c'est le dernier caractère de chaque chaîne d'entrée, et il n'est pas autorisé au milieu d'un lexème par aucune des règles (en particulier, il n'est pas inclus dans les plages de caractères où il est facile de le négliger). Si un null se produit au milieu d'une chaîne, c'est une erreur de syntaxe et le lexer fera correspondre la règle par défaut *, mais il ne lira pas au-delà de la fin de l'entrée et ne plantera pas (utilisez l'avertissement -Wsentinel-in-midrule et la configuration re2c:sentinel pour vérifier cela). La configuration re2c:yyfill:enable = 0; supprime la génération des vérifications de limites et des invocations YYFILL.

// attend une chaîne terminée par null
function lex(yyinput) {
    let yycursor = 0;
    let count = 0
    loop: while (true) {
    /*!re2c
        re2c:yyfill:enable = 0;
        *      { return -1 }
        [\x00] { return count }
        [ ]+   { continue loop }
        [a-z]+ { count += 1; continue loop }
    */
    }

Sentinelle avec vérifications de limites

Cet exemple utilise une sentinelle avec vérifications de limites pour gérer la fin de l'entrée (cette méthode a été ajoutée dans la version 1.2). Le programme compte les chaînes d'un seul guillemet séparées par des espaces. Le caractère sentinelle est null, ce qui est spécifié avec la configuration re2c:eof = 0;. Comme dans la méthode sentinel, null est le dernier caractère de chaque chaîne d'entrée, mais il est autorisé au milieu d'une règle (par exemple, 'aaa\0aa'\0 est une entrée valide, mais 'aaa\0 est une erreur de syntaxe). Les vérifications de limites sont générées dans chaque état qui correspond à un caractère d'entrée, mais elles sont limitées à la branche qui gère le null. Les vérifications de limites sont de la forme YYLIMIT <= YYCURSOR ou YYLESSTHAN(1) avec l'API générique. Si la condition de vérification est vraie, le lexer a atteint la fin de l'entrée et doit s'arrêter (YYFILL est désactivé avec re2c:yyfill:enable = 0; car l'entrée tient dans un seul tampon, voir la section YYFILL avec sentinelle pour un exemple qui utilise YYFILL). Atteindre la fin de l'entrée ouvre trois possibilités : si le lexer est dans l'état initial, il fera correspondre la règle de fin d'entrée $, sinon il peut se rabattre sur une règle précédemment correspondue (y compris la règle par défaut *) ou aller à un état par défaut, provoquant -Wundefined-control-flow.

        re2c:eof = 0;

        *    { return -1 }
        $    { return count }
        [ ]+ { continue loop }
        str  { count += 1; continue loop }
    */
    }
}

Vérifications des limites avec remplissage

Cet exemple utilise des vérifications des limites avec remplissage pour gérer la fin de l'entrée (cette méthode est activée par défaut). Le programme compte les chaînes de caractères entre apostrophes simples séparées par des espaces. Il y a un remplissage de YYMAXFILL caractères nuls ajoutés à la fin de l'entrée, où la valeur de YYMAXFILL est auto-générée avec un bloc max. Il n'est pas nécessaire d'utiliser des nuls pour le remplissage --- n'importe quels caractères peuvent être utilisés tant qu'ils ne forment pas un suffixe de lexème valide (dans cet exemple, le remplissage ne doit pas contenir d'apostrophes, car elles pourraient être confondues avec un suffixe d'une chaîne entre apostrophes simples). Il y a une règle "stop" qui correspond au premier caractère de remplissage (nul) et termine le lexer (notez qu'elle vérifie si le nul est au début du remplissage, sinon c'est une erreur de syntaxe). Les vérifications des limites ne sont générées que dans certains états déterminés par les composantes fortement connexes de l'automate sous-jacent. Les vérifications prennent la forme (YYLIMIT - YYCURSOR) < n ou YYLESSTHAN(n) avec l'API générique, où n est le nombre minimum de caractères nécessaires au lexer pour continuer (cela signifie également que la prochaine vérification des limites se produira dans au plus n caractères). Si la condition de vérification est vraie, le lexer a atteint la fin de l'entrée et appellera YYFILL(n) qui devrait soit fournir au moins n caractères d'entrée, soit ne pas retourner. Dans cet exemple, YYFILL échoue toujours et termine le lexer avec une erreur (ce qui est acceptable car l'entrée tient dans un seul tampon). Voir la section YYFILL avec remplissage pour un exemple qui remplit le tampon d'entrée avec YYFILL.

// re2js $INPUT -o $OUTPUT
/*!max:re2c*/
function lex(yyinput) {
    let yycursor = 0;
    let yylimit = yyinput.length
    let count = 0
    loop: while (true) {
    /*!re2c
        re2c:YYFILL = "return -1";
        str = ['] ([^'\\] | [\\][^])* ['];
        [\x00] {
            // check that it is the sentinel, not some unexpected null
            return (yycursor == yylimit - YYMAXFILL + 1) ? count : -1
        }
        str  { count += 1; continue loop }
        [ ]+ { continue loop }
        *    { return -1 }
    */
    }
}
function test(s, n) {
    let padded_s = s + "\0".repeat(YYMAXFILL)
    if (lex(padded_s) != n) throw "error!"
}

Cet exemple utilise une méthode personnalisée de gestion de la fin d'entrée basée sur l'API générique. Le programme compte les chaînes de caractères entre apostrophes simples séparées par des espaces. C'est identique à l'exemple du sentinelle, sauf que l'entrée n'est pas terminée par un nul. Pour compenser l'absence d'un caractère sentinelle à la fin de l'entrée, YYPEEK est redéfini pour effectuer une vérification des limites avant de lire le prochain caractère d'entrée. Ceci est inefficace car les vérifications sont effectuées très fréquemment. Si la condition de vérification échoue, YYPEEK retourne le vrai caractère, sinon il retourne un caractère sentinelle factice.

// re2js $INPUT -o $OUTPUT
// expects a string without terminating null
function lex(str) {

        re2c:yyfill:enable = 0;
        *      { return -1 }
        [\x00] { return count }
        [ ]+   { continue loop }
        [a-z]+ { count += 1; continue loop }
    */
    }

REMPLISSAGE DU TAMPON

Le besoin de mise en tampon survient lorsque l'entrée ne peut pas être mappée en mémoire en une seule fois: soit elle est trop volumineuse, soit elle provient d'un flux (comme la lecture d'une socket). La technique habituelle dans de tels cas consiste à allouer un tampon mémoire de taille fixe et à traiter l'entrée par morceaux qui tiennent dans le tampon. Lorsque le morceau courant est traité, il est déplacé et de nouvelles données sont chargées. En pratique, c'est un peu plus complexe, car l'état du lexer ne consiste pas en une seule position d'entrée, mais en un ensemble de positions interdépendantes:

  • curseur : le prochain caractère d'entrée à lire (YYCURSOR dans l'API de pointeur C ou YYSKIP/YYPEEK dans l'API générique)
  • limite : la position après le dernier caractère d'entrée disponible (YYLIMIT dans l'API de pointeur C, géré implicitement par YYLESSTHAN dans l'API générique)
  • marqueur : la position de la correspondance la plus récente, le cas échéant (YYMARKER dans l'API par défaut ou YYBACKUP/YYRESTORE dans l'API générique)
  • jeton : le début du lexème courant (implicite dans l'API re2js, car il n'est pas nécessaire pour le fonctionnement normal du lexer et peut être défini et mis à jour par l'utilisateur)
  • marqueur de contexte : la position du contexte de fin (YYCTXMARKER dans l'API de pointeur C ou YYBACKUPCTX/YYRESTORECTX dans l'API générique)
  • variables de balises : positions de sous-correspondance (définies avec les blocs stags et mtags et les primitives de l'API générique YYSTAGP/YYSTAGN/YYMTAGP/YYMTAGN)

Tous ces éléments ne sont pas utilisés dans tous les cas, mais s'ils le sont, ils doivent être mis à jour par YYFILL. Toutes les positions actives sont contenues dans le segment entre le jeton et le curseur, par conséquent tout ce qui se trouve entre le début du tampon et le jeton peut être écarté, le segment du jeton jusqu'à la limite doit être déplacé au début du tampon, et l'espace libre à la fin du tampon doit être rempli avec de nouvelles données. Afin d'éviter des appels fréquents à YYFILL, il est préférable de charger autant de caractères d'entrée que possible (même si moins de caractères pourraient suffire à reprendre le lexer). Les détails de l'implémentation de YYFILL diffèrent légèrement selon la méthode de gestion de la fin de fichier utilisée: le cas de la règle EOF est quelque peu plus simple que le cas des vérifications de limites avec remplissage. Notez également que si l'option -f --storable-state est utilisée, YYFILL a une sémantique légèrement différente (décrite dans la section sur l'état stockable).

YYFILL avec sentinelle

Si la règle EOF est utilisée, YYFILL est une primitive de type fonction qui n'accepte aucun argument et retourne une valeur qui est vérifiée par rapport à zéro. L'invocation de YYFILL est déclenchée par la condition YYLIMIT <= YYCURSOR dans l'API de pointeur C et YYLESSTHAN() dans l'API générique. Une valeur de retour non nulle signifie que YYFILL a échoué. Un appel réussi à YYFILL doit fournir au moins un caractère et ajuster les positions d'entrée en conséquence. La limite doit toujours être définie à un après la dernière position d'entrée dans le tampon, et le caractère à la position limite doit être le symbole sentinelle spécifié par la configuration re2c:eof. Les schémas ci-dessous montrent les positions relatives des entrées dans le tampon avant et après l'appel à YYFILL (le symbole sentinelle est marqué par #, et le second schéma montre le cas où il n'y a pas assez d'entrée pour remplir tout le tampon).

>-A------------B---------C-------------D------------E#->

// re2js $INPUT -o $OUTPUT
const fs = require('fs')
const BUFSIZE = 4096
const OK = 0
const EOF = 1
const LONG_LEXEME = 2
function fill(st) {
    if (st.eof) return EOF
    // Error: lexeme too long. In real life could reallocate a larger buffer.
    if (st.token < 1) return LONG_LEXEME
    // Shift buffer contents (discard everything up to the current token).
    st.yyinput.copy(st.yyinput, 0, st.token, st.yylimit)
    st.yycursor -= st.token;
    st.yymarker -= st.token;
    st.yylimit -= st.token;
    st.token = 0;
    // Read a new chunk of data from file and append it to `yyinput`.
    let want = BUFSIZE - st.yylimit - 1 // -1 for sentinel
    let nread = fs.readSync(st.file, st.yyinput, st.yylimit, want)
    st.eof = nread < want // end of file?
    st.yylimit += nread
    st.yyinput.writeUInt8(0, st.yylimit) // sentinel
    return OK
}
function lex(yyrecord, count) {
    loop: while (true) {
        yyrecord.token = yyrecord.yycursor
        /*!re2c
            re2c:api = record;
            re2c:YYPEEK = "readUInt8";
            re2c:YYFILL = "fill(yyrecord) == OK";
            re2c:eof = 0;
            str = ['] ([^'\\] | [\\][^])* ['];
            *    { return -1 }
            $    { return count }
            [ ]+ { continue loop }
            str  { count += 1; continue loop }
        */
    }
}
function main() {
    let fname = "input"
    // Create input file.
    let content = "'qu\0tes' 'are' 'fine: \\'' ".repeat(BUFSIZE)
    fs.writeFileSync(fname, content, function(err) { if (err) throw err; })
    // Init lexer state.
    let limit = BUFSIZE - 1 // exclude terminating null
    let st = {
        file: fs.openSync(fname, 'r'),
        yyinput: Buffer.alloc(BUFSIZE),
        yylimit: limit,
        yycursor: limit,
        yymarker: limit,
        token: limit,
        eof: false
    }
    // Run lexer on the prepared file.
    if (lex(st, 0) != 3 * BUFSIZE) { throw "error :[" }
    // Cleanup.
    fs.unlink(fname, function(err){ if (err) throw err; })
}

YYFILL avec remplissage

Dans le cas par défaut (lorsque la règle EOF n'est pas utilisée), YYFILL est une primitive de type fonction qui accepte un seul argument et ne retourne aucune valeur. L'invocation de YYFILL est déclenchée par la condition (YYLIMIT - YYCURSOR) < n dans l'API de pointeur C et YYLESSTHAN(n) dans l'API générique. L'argument passé à YYFILL est le nombre minimum de caractères qui doivent être fournis. S'il ne parvient pas à le faire, YYFILL ne doit pas retourner au lexer (pour cela r

raison pour laquelle il est mieux implémenté en tant que macro qui revient de la fonction appelante en cas d'échec). En cas de succès de l'invocation de YYFILL, la position limite doit être définie soit à une position après la dernière position d'entrée dans le tampon, soit à la fin du rembourrage YYMAXFILL (si YYFILL a lu avec succès au moins n caractères, mais pas assez pour remplir entièrement le tampon). Les figures ci-dessous montrent les emplacements relatifs des positions d'entrée dans le tampon avant et après l'invocation de YYFILL (le rembourrage YYMAXFILL dans la deuxième figure est marqué par des symboles #).

const fs = require('fs')
const BUFSIZE = 4096
const OK = 0
const EOF = 1
const LONG_LEXEME = 2
/*!max:re2c*/
function fill(st, need) {
    if (st.eof) return EOF
    // Erreur : lexème trop long. Dans la vie réelle, on pourrait réallouer un tampon plus grand.
    if (st.token < need) return LONG_LEXEME
    // Décale le contenu du tampon (rejette tout jusqu'au jeton courant).
    st.yyinput.copy(st.yyinput, 0, st.token, st.yylimit)
    st.yycursor -= st.token;
    st.yylimit -= st.token;
    st.token = 0;
    // Lit un nouveau bloc de données du fichier et l'ajoute à `yyinput`.
    let want = BUFSIZE - st.yylimit - 1 // -1 pour le sentinelle
    let nread = fs.readSync(st.file, st.yyinput, st.yylimit, want)
    st.yylimit += nread
    if (nread < want) {
        st.eof = true // fin du fichier
        st.yyinput.write("\0".repeat(YYMAXFILL), st.yylimit)
        st.yylimit += YYMAXFILL
    }
    return OK
}

    loop: while (true) {
        yyrecord.token = yyrecord.yycursor
        /*!re2c
            re2c:api = record;

                return yyrecord.token == yyrecord.yylimit - YYMAXFILL ? count : -1
            }
            str  { count += 1; continue loop }
            [ ]+ { continue loop }
            *    { return -1 }
        */

Blocs multiples

Il est parfois nécessaire d'avoir plusieurs lexers interconnectés (par exemple, s'il existe une machine à états de haut niveau qui passe d'un mode de lexer à un autre). Cela peut être implémenté à l'aide de plusieurs blocs re2js connectés. Une autre option est d'utiliser des conditions de départ.

L'implémentation des connexions entre les blocs dépend du langage cible. Dans les langages qui ont une instruction goto (comme C/C++ et Go), on peut avoir tous les blocs dans une seule fonction, chacun d'eux étant précédé d'une étiquette. La transition d'un bloc à un autre est un simple goto. Dans les langages qui n'ont pas de goto (comme Rust), il est nécessaire d'utiliser une boucle avec un commutateur sur une variable d'état, similaire à la boucle/commutateur yystate générée par re2js, ou d'encapsuler chaque bloc dans une fonction et d'utiliser des appels de fonction.

Conditions de départ

Les conditions de départ sont activées avec l'option --start-conditions. Elles offrent un moyen d'encoder plusieurs automates interconnectés au sein du même bloc re2js.

Chaque condition correspond à un automate unique et porte un nom défini par l'utilisateur ainsi qu'un numéro interne unique défini par re2js. Les numéros sont utilisés pour basculer entre les conditions : le code généré utilise les primitives YYGETCOND et YYSETCOND pour obtenir la condition actuelle ou la définir à un numéro donné. Utilisez le bloc conditions, l'option --header ou la configuration re2c:header pour générer des identifiants de condition numériques. La configuration re2c:cond:enumprefix spécifie le préfixe de l'identifiant généré.

En mode condition, chaque règle doit être précédée d'une liste de noms de conditions séparés par des virgules entre chevrons, ou d'un joker <*> pour désigner toutes les conditions. La syntaxe de la règle est étendue comme suit :

< liste-conditions > expression-régulière code
Une règle qui est fusionnée à chaque condition de la liste-conditions. Elle correspond à l'expression-régulière et exécute le code associé.
< liste-conditions > expression-régulière => condition code
Une règle qui est fusionnée à chaque condition de la liste-conditions. Elle correspond à l'expression-régulière, définit la condition actuelle à condition et exécute le code associé.
< liste-conditions > expression-régulière :=> condition
Une règle qui est fusionnée à chaque condition de la liste-conditions. Elle correspond à l'expression-régulière et passe immédiatement à la condition (il n'y a pas d'action sémantique).
< liste-conditions > !action code
Une règle qui lie le code à l'endroit défini par l'action dans chaque condition de la liste-conditions (voir la section actions pour les différents types d'actions).
<! liste-conditions > code
Une règle qui ajoute le code au début des actions sémantiques de toutes les règles pour chaque condition de la liste-conditions. Cette syntaxe est dépréciée et l'action !pre_rule doit être utilisée à la place (elle fait exactement la même chose).
< > code
Une règle qui crée une condition d'entrée spéciale avec le numéro zéro et le nom "0" qui exécute le code avant de sauter vers d'autres conditions. Le code que re2js génère pour les conditions dépend de l'utilisation par re2js de l'approche goto/label ou de l'approche boucle/commutateur pour encoder les automates.

Dans les langages qui ont une instruction goto (comme C/C++ et Go), les conditions sont naturellement implémentées comme des blocs de code précédés d'étiquettes de la forme yyc_<cond>, où cond est un nom de condition (le préfixe d'étiquette peut être modifié avec re2c:cond:prefix). Les transitions entre conditions sont implémentées à l'aide de goto et d'étiquettes de condition. Avant toutes les conditions, re2js génère un commutateur initial sur YYGETSTATE qui saute à l'état de départ de la condition actuelle. Les règles de raccourci :=> contournent le commutateur initial et sautent directement à la condition spécifiée (re2c:cond:goto peut être utilisé pour modifier le comportement par défaut). Les règles avec des actions sémantiques ne sautent pas automatiquement à la condition suivante ; cela doit être fait par le code d'action défini par l'utilisateur.

Dans les langages qui n'ont pas de goto (comme Rust), re2js réutilise la variable yystate pour stocker le numéro de la condition

umbers. Chaque condition reçoit un identifiant numérique égal au numéro de son état de départ, et un changement de condition n'est pas différent d'un changement d'état de DFA d'une seule condition. Il n'est pas nécessaire de changer d'état initial séparé. (Comme la même approche est utilisée pour implémenter les états stockables, YYGETCOND/YYSETCOND sont redondants si les états stockables et les conditions sont utilisés).

État stockable

Avec l'option --storable-state, re2js génère un lexer capable de stocker son état actuel, de retourner à l'appelant, et de reprendre plus tard les opérations exactement là où il s'est arrêté. Le mode de fonctionnement par défaut dans re2js est un modèle "pull", dans lequel le lexer "tire" davantage d'entrée quand il en a besoin. Cela peut être inacceptable dans les cas où l'entrée devient disponible morceau par morceau (par exemple, si le lexer est appelé par l'analyseur syntaxique, ou si le programme lexer communique via un protocole socket avec un autre programme qui doit attendre une réponse du lexer avant de transmettre le prochain message). La fonctionnalité d'état stockable est conçue précisément pour de tels cas : elle permet de générer des lexers qui fonctionnent selon un modèle "push". Lorsque le lexer a besoin de plus d'entrée, il stocke son état et retourne à l'appelant. Plus tard, lorsque davantage d'entrée est disponible, l'appelant reprend le lexer exactement là où il s'est arrêté. Il y a quelques changements nécessaires par rapport au modèle "pull" :

  • Définir les primitives YYSETSTATE() et YYGETSTATE(state).
  • Définir les variables yych, yyaccept (si utilisé) et state dans le cadre de l'état persistant du lexer. La variable state doit être initialisée à -1.
  • YYFILL doit retourner au programme extérieur au lieu d'essayer de fournir plus d'entrée. Le code de retour doit indiquer que le lexer a besoin de plus d'entrée.
  • Le programme extérieur doit reconnaître les situations où le lexer a besoin de plus d'entrée et y répondre de manière appropriée.
  • Utiliser éventuellement le bloc getstate pour générer un switch YYGETSTATE détaché du lexer principal. Cela ne fonctionne que pour les langages qui ont goto (pas en mode --loop-switch).
  • Utiliser re2c:eof et la méthode du sentinelle avec vérifications de limites pour gérer la fin de l'entrée. La méthode basée sur le padding peut ne pas fonctionner car il n'est pas clair quand ajouter le padding : la fin actuelle de l'entrée peut ne pas être la fin ultime de l'entrée, et ajouter du padding trop tôt peut couper un lexème gourmand lu partiellement. De plus, en raison de la logique du programme de haut niveau, l'obtention de plus d'entrée peut dépendre du traitement du lexème à la fin du tampon (qui est déjà bloqué en raison de la condition de fin d'entrée).

Voici un exemple de lexer en mode "push" qui simule la lecture de paquets depuis un socket. Le lexer boucle jusqu'à ce qu'il rencontre la fin de l'entrée et retourne à la fonction appelante. La fonction appelante fournit plus d'entrée en "envoyant" le prochain paquet et reprend l'analyse lexicale. Ce processus s'arrête lorsque tous les paquets ont été envoyés, ou lorsqu'il y a une erreur.

// re2js $INPUT -o $OUTPUT -f
const fs = require('fs')
// Utiliser un petit tampon pour couvrir le cas où un lexème ne convient pas.
// Dans la vraie vie, utiliser un tampon plus grand.
const BUFSIZE = 10
const DEBUG = false
const END = 0
const READY = 1
const WAITING = 2
const BIG_PACKET = 3
const BAD_PACKET = 4
function log() {
    if (DEBUG) console.log.apply(console, arguments)
}
function fill(st) {
    // Erreur : lexème trop long. Dans la vraie vie, on pourrait réallouer un tampon plus grand.
    if (st.token < 1) return BIG_PACKET
    // Décaler le contenu du tampon (ignorer tout ce qui précède le jeton actuel).
    st.yyinput.copy(st.yyinput, 0, st.token, st.yylimit)
    st.yycursor -= st.token;
    st.yymarker -= st.token;
    st.yylimit -= st.token;
    st.token = 0;
    // Lire un nouveau bloc de données du fichier et l'ajouter à `yyinput`.
    let want = BUFSIZE - st.yylimit - 1 // -1 pour le sentinelle
    let nread = fs.readSync(st.file, st.yyinput, st.yylimit, want)
    st.yylimit += nread
    st.yyinput.writeUInt8(0, st.yylimit) // sentinelle
    return READY
}
function lex(yyrecord) {
    loop: while (true) {
        yyrecord.token = yyrecord.yycursor
        /*!re2c
            re2c:api = record;
            re2c:YYPEEK = "readUInt8";
            re2c:YYFILL = "return WAITING";
            re2c:eof = 0;
            packet = [a-z]+[;];
            *      { return BAD_PACKET }
            $      { return END }
            packet { yyrecord.received += 1; continue loop }
        */
    }
}
function test(packets, expect) {
    // Émuler un "tube" en ouvrant le même fichier en lecture et en écriture.
    let fname = "input"
    let fw = fs.openSync(fname, 'w');
    let fr = fs.openSync(fname, 'r');
    // Initialiser l'état du lexer.
    let limit = BUFSIZE - 1 // exclure le nul terminateur
    let st = {
        file: fr,
        yyinput: Buffer.alloc(BUFSIZE),
        yylimit: limit,
        yycursor: limit,
        yymarker: limit,
        token: limit,
        yystate: -1,
        received: 0
    }
    // Boucle principale. Le tampon contient des données incomplètes qui apparaissent paquet par
    // paquet. Lorsque le lexer a besoin de plus d'entrée, il sauvegarde son état interne et
    // retourne à l'appelant qui doit fournir plus d'entrée et reprendre l'analyse lexicale.
    let send = 0
    let status
    loop: while (true) {
        status = lex(st)
        if (status == END) {
            log("terminé : reçu", st.received, "paquets")
            break loop
        } else if (status == WAITING) {
            log("attente...");
            if (send < packets.length) {
                log("paquet envoyé", send, packets[send])
                fs.writeFileSync(fw, packets[send])
                send += 1
            }
            status = fill(st)
            log("file:", st.yyinput.toString())
            if (status == BIG_PACKET) {
                log("erreur : paquet trop gros")
                break loop
            }
            if (status != READY) throw "attendu READY"
        } else {
            if (status != BAD_PACKET) throw "attendu BAD_PACKET"
            log("erreur : paquet mal formé")
            break loop
        }
    }
    // Vérifier les résultats.
    if (status != expect) throw "statut inattendu"
    if (status == END && st.received != send) "nombre de paquets inattendu"
    // Nettoyage.
    fs.unlinkSync(fname, function(err){ if (err) throw err; })
}
function main() {
    test([], END)
    test(["zero;", "one;", "two;", "three;", "four;"], END)
    test(["zer0;"], BAD_PACKET)
    test(["goooooooooogle;"], BIG_PACKET)
}

Blocs réutilisables

Les blocs réutilisables de la forme /*!rules:re2c[:<name>] ... */ ou %{rules[:<name>] ... %} peuvent être réutilisés plusieurs fois et combinés avec d'autres blocs re2js. Le <name> est facultatif. Un bloc de règles peut être utilisé dans un bloc ou une directive use. Le code d'un bloc de règles est généré à chaque point d'utilisation.

Les blocs d'utilisation sont définis avec /*!use:re2c[:<name>] ... */ ou %{use[:<name>] ... %}. Le <name> est facultatif : s'il n'est pas spécifié, le bloc de règles associé est le plus récent (nommé ou non). Un bloc d'utilisation peut ajouter ses propres définitions nommées, configurations et règles. Un cas d'utilisation important des blocs d'utilisation est un lexer qui prend en charge plusieurs encodages d'entrée : le même bloc de règles est réutilisé plusieurs fois avec des configurations spécifiques à l'encodage (voir l'exemple ci-dessous).

La directive d'utilisation intra-bloc !use:<name>; peut être utilisée à l'intérieur d'un bloc re2js. Elle fusionne le bloc référencé <name> dans le bloc actuel. Si certaines des règles et configurations fusionnées chevauchent celles précédemment définies, les conflits sont résolus de la manière habituelle : la règle la plus ancienne a la priorité, et la configuration la plus récente remplace les précédentes. Une exception concerne les règles spéciales *, $ et (en mode condition) <!>, pour lesquelles une définition locale au bloc remplace toutes les définitions héritées. La directive d'utilisation permet de combiner différents blocs re2js au sein d'un même bloc (voir l'exemple ci-dessous).

Les blocs nommés et la directive d'utilisation intra-bloc ont été ajoutés dans la version 2.2 de re2js. Depuis cette version, les blocs réutilisables sont autorisés par défaut (aucune option spéciale n'est nécessaire). Avant la version 2.2, le mode réutilisable était activé avec l'option -r --reusable. Avant la version 1.2, les blocs réutilisables ne pouvaient pas être mélangés avec des blocs normaux.

Extraction de sous-correspondances

re2js propose deux options pour l'extraction de sous-correspondances.

Tags
La première option consiste à utiliser des tags autonomes de la forme @stag ou #mtag, où stag et mtag sont des noms arbitraires définis par l'utilisateur. Les tags sont activés avec l'option -T --tags ou la configuration re2c:tags = 1. Sémantiquement, les tags sont des marqueurs de position : ils peuvent être insérés n'importe où dans une expression régulière, et ils s'attachent à la position correspondante (ou aux positions multiples) dans la chaîne d'entrée. Les s-tags s'attachent à la dernière position correspondante, et les m-tags s'attachent à une liste de positions (ils peuvent être utilisés dans des sous-expressions de répétition, où une seule position dans une expression régulière correspond à plusieurs positions dans la chaîne d'entrée). Tous les tags doivent être définis par l'utilisateur, manuellement ou à l'aide des blocs svars et mvars. S'il existe plus d'une façon pour les tags de correspondre à l'entrée, l'ambiguïté est résolue en utilisant une stratégie de désambiguïsation gourmande de gauche à droite.
Captures
La deuxième option consiste à utiliser des groupes de capture. Ils sont activés avec l'option --captures ou la configuration re2c:captures = 1. Il existe deux variantes pour différentes politiques de désambiguïsation, --leftmost-captures (par défaut) pour la politique gourmande de gauche à droite, et --posix-captures pour la politique de correspondance la plus longue de POSIX. Dans ce mode, toutes les sous-expressions entre parenthèses sont considérées comme des groupes de capture, et un point d'exclamation peut être utilisé pour marquer les groupes non capturants : (! ... ). Avec l'option --invert-captures ou la configuration re2c:invert-captures = 1 la signification du point d'exclamation est inversée. Le nombre de groupes pour la règle de correspondance est stocké dans une variable yynmatch (l'expression régulière entière est le groupe numéro zéro), et les résultats des sous-correspondances sont stockés dans le tableau yypmatch. yynmatch et yypmatch doivent être définis par l'utilisateur, et la taille de yypmatch doit être au moins [yynmatch * 2]. Utilisez le bloc maxnmatch pour définir YYMAXNMATCH, une constante égale à la valeur maximale de yynmatch parmi toutes les règles.
Captvars
Une autre façon d'utiliser les groupes de capture est l'option --captvars ou la configuration re2c:captvars = 1. La seule différence avec --captures réside dans la manière dont re2js stocke les résultats des sous-correspondances : au lieu de yynmatch et yypmatch, re2js génère les variables yytl<k> et yytr<k> pour le k-ième groupe de capture (l'utilisateur doit les déclarer à l'aide d'un bloc svars). Les captures avec variables supportent deux politiques de désambiguïsation : --leftmost-captvars ou re2c:leftmost-captvars = 1 pour la politique gourmande de gauche à droite (par défaut) et --posix-captvars ou re2c:posix-captvars pour la politique de correspondance la plus longue de POSIX.

En interne, toutes ces options se traduisent par des tags et des Automates Finis Déterministes Etiquetés avec Anticipation (TDFA). L'idée principale du TDFA est de minimiser la surcharge liée à l'extraction des sous-correspondances. À l'extrême, s'il n'y a pas de tags ou de captures dans une expression régulière, le TDFA n'est qu'un DFA ordinaire. Si le nombre de tags est modéré, la surcharge est à peine perceptible. Le TDFA généré utilise un certain nombre de variables de tag qui ne correspondent pas directement aux tags : une seule variable peut être utilisée pour différents tags, et un tag peut nécessiter plusieurs variables pour contenir toutes ses valeurs possibles. Finalement, l'ambiguïté est résolue, et une seule variable finale par tag survit. Les variables de tag doivent être définies à l'aide des blocs stags ou mtags. Si l'état de l'analyseur est stocké, les variables de tag doivent en faire partie. Elles doivent également être mises à jour par YYFILL.

Les s-tags supportent les opérations suivantes :

  • sauvegarder la position d'entrée dans un s-tag : t = YYCURSOR avec l'API de pointeur C ou une opération définie par l'utilisateur YYSTAGP(t) avec l'API générique
  • sauvegarder une valeur par défaut dans un s-tag : t = NULL avec l'API de pointeur C ou une opération définie par l'utilisateur YYSTAGN(t) avec l'API générique
  • copier un s-tag dans un autre : t1 = t2

Les m-tags supportent les opérations suivantes :

  • ajouter une position d'entrée à un m-tag : une opération définie par l'utilisateur YYMTAGP(t) avec l'API par défaut et générique
  • ajouter une valeur par défaut à un m-tag : une opération définie par l'utilisateur YYMTAGN(t) avec l'API par défaut et générique
  • copier un m-tag dans un autre : t1 = t2

Les s-tags peuvent être implémentés comme des valeurs scalaires (pointeurs ou décalages). Les m-tags nécessitent une représentation plus complexe, car ils doivent stocker une séquence de valeurs de tag. La représentation la plus naïve et la moins efficace d'un m-tag est une liste (tableau, vecteur) de valeurs de tag ; une représentation plus efficace consiste à stocker tous les m-tags dans un arbre préfixe représenté sous forme de tableau de nœuds (v, p), où v est la valeur du tag et p est un pointeur vers le nœud parent.

Voici un exemple simple d'utilisation de s-tags pour analyser des versions sémantiques composées de trois composants numériques : majeur, mineur, correctif (ce dernier est facultatif). Voir ci-dessous pour un exemple plus complexe qui utilise YYFILL.

// re2js $INPUT -o $OUTPUT
const assert = require('assert');
function parse(yyinput) {
    let yycursor = 0
    // Variables de tag finales disponibles dans l'action sémantique.
    /*!svars:re2c format = "let @@\n"; */
    // Variables de tag intermédiaires utilisées par l'analyseur (doivent être générées automatiquement).
    /*!stags:re2c format = "let @@\n"; */
    /*!re2c
        re2c:yyfill:enable = 0;
        re2c:tags = 1;
        num = [0-9]+;
        @t1 num @t2 "." @t3 num @t4 ("." @t5 num)? [\x00] {
            return {
                major: Number(yyinput.substring(t1, t2)),
                minor: Number(yyinput.substring(t3, t4)),
                patch: t5 == -1 ? 0 : Number(yyinput.substring(t5, yycursor - 1))
            }
        }
        * { return null }
    */
}

assert.deepEqual(parse("1.2.99999\0"), {major: 1, minor: 2, patch: 99999})
assert.deepEqual(parse("1.a\0"), null)

Voici un exemple plus complexe d'utilisation de s-tags avec YYFILL pour analyser un fichier avec des versions sémantiques séparées par des sauts de ligne. Les variables de tag font partie de l'état de l'analyseur, et elles sont ajustées dans YYFILL comme les autres positions d'entrée. Il est nécessaire pour les s-tags car leurs valeurs sont invalidées après le déplacement du contenu du tampon. Ce n'est peut-être pas nécessaire dans une implémentation personnalisée où les variables de tag stockent des décalages par rapport au début de la chaîne d'entrée plutôt qu'au tampon, ce qui peut être le cas avec les m-tags.

// re2js $INPUT -o $OUTPUT
const assert = require('assert');
const fs = require('fs')
const BUFSIZE = 4096
const OK = 0
const EOF = 1
const LONG_LEXEME = 2
function fill(st) {
    if (st.eof) return EOF
    // Erreur : lexème trop long. Dans la réalité, on pourrait réallouer un tampon plus grand.
    if (st.token < 1) return LONG_LEXEME
    // Déplacer le contenu du tampon (ignorer tout jusqu'au jeton courant).
    st.yyinput.copy(st.yyinput, 0, st.token, st.yylimit)
    st.yycursor -= st.token;
    st.yymarker -= st.token;
    st.yylimit -= st.token;
    /*!stags:re2c format = "if (st.@@ != -1) st.@@ -= st.token\n"; */
    st.token = 0;
    // Lire un nouveau bloc de données du fichier et l'ajouter à `yyinput`.
    let want = BUFSIZE - st.yylimit - 1 // -1 pour le sentinelle
    let nread = fs.readSync(st.file, st.yyinput, st.yylimit, want)
    st.eof = nread < want // fin du fichier ?
    st.yylimit += nread
    st.yyinput.writeUInt8(0, st.yylimit) // sentinelle
    return OK
}
function lex(st) {
    let vers = []
    loop: while (true) {
        st.token = st.yycursor
        // Variables de tag finales disponibles dans l'action sémantique.
        /*!svars:re2c format = "let @@\n"; */
        /*!re2c
            re2c:api = record;
            re2c:yyrecord = st;
            re2c:YYPEEK = "readUInt8";
            re2c:YYFILL = "fill(st) == OK";
            re2c:eof = 0;
            re2c:tags = 1;
            num = [0-9]+;
            num @t1 "." @t2 num @t3 ("." @t4 num)? [\n] {
                vers.push({
                    major: Number(st.yyinput.subarray(st.token, t1)),
                    minor: Number(st.yyinput.subarray(t2, t3)),
                    patch: t4 == -1 ? 0 : Number(st.yyinput.subarray(t4, st.yycursor - 1))
                })
                continue loop
            }

            * { return null }
        */

function main() {
    let fname = "input"
    // Créer le fichier d'entrée.
    let content = "1.22.333\n".repeat(BUFSIZE)

Support des encodages

Il est nécessaire de comprendre la différence entre les points de code et les unités de code. Un point de code est un identifiant numérique d'un symbole. Une unité de code est la plus petite unité de stockage dans le texte encodé. Un seul point de code peut être représenté par une ou plusieurs unités de code. Dans un encodage à longueur fixe, tous les points de code sont représentés par le même nombre d'unités de code. Dans un encodage à longueur variable, les points de code peuvent être représentés par un nombre différent d'unités de code. Notez que la règle "tout" [^] correspond à n'importe quel point de code, mais pas nécessairement à n'importe quelle unité de code (la seule façon de correspondre à n'importe quelle unité de code, quel que soit l'encodage, est la règle par défaut *). Le lexer généré fonctionne avec un flux d'unités de code : yych stocke une unité de code, et YYCTYPE est le type d'unité de code. Les expressions régulières, quant à elles, sont spécifiées en termes de points de code. Lorsque re2js compile les expressions régulières en automates, il traduit les points de code en unités de code. Ce n'est généralement pas un mappage simple : dans les encodages à longueur variable, une plage de points de code unique peut être traduite en un graphe complexe d'unités de code. Les encodages suivants sont pris en charge :

  • ASCII (activé par défaut). C'est un encodage à longueur fixe avec un espace de code [0-255] et des points de code et des unités de code de 1 octet.
  • EBCDIC (activé avec --ebcdic ou re2c:encoding:ebcdic). C'est un encodage à longueur fixe avec un espace de code [0-255] et des points de code et des unités de code de 1 octet.
  • UCS2 (activé avec --ucs2 ou re2c:encoding:ucs2). C'est un encodage à longueur fixe avec un espace de code [0-0xFFFF] et des points de code et des unités de code de 2 octets.
  • UTF8 (activé avec --utf8 ou re2c:encoding:utf8). C'est un encodage Unicode à longueur variable. La taille des unités de code est de 1 octet. Les points de code sont représentés par 1 à 4 unités de code.
  • UTF16 (activé avec --utf16 ou re2c:encoding:utf16). C'est un encodage Unicode à longueur variable. La taille des unités de code est de 2 octets. Les points de code sont représentés par 1 à 2 unités de code.
  • UTF32 (activé avec --utf32 ou re2c:encoding:utf32). C'est un encodage Unicode à longueur fixe avec un espace de code [0-0x10FFFF] et des points de code et des unités de code de 4 octets.

Le fichier d'inclusion include/unicode_categories.re fournit les définitions re2js pour les catégories Unicode standard.

L'option --input-encoding spécifie l'encodage du fichier source, qui peut être utilisé pour activer les littéraux Unicode dans les expressions régulières. Par exemple, --input-encoding utf8 indique à re2js que le fichier source est en UTF8 (cela diffère de --utf8 qui définit l'encodage du texte d'entrée). L'option --encoding-policy spécifie la manière dont re2js gère les substituts Unicode (points de code dans la plage [0xD800-0xDFFF]).

Fichiers d'inclusion

re2js permet d'inclure d'autres fichiers à l'aide d'un bloc de la forme /*!include:re2c FILE */ ou %{include FILE %}, ou d'une directive in-bloc !include FILE ;, où FILE est un chemin vers le fichier à inclure. re2js recherche les fichiers d'inclusion dans le répertoire du fichier incluant et dans les emplacements d'inclusion, qui peuvent être spécifiés avec l'option -I. Les blocs/directives d'inclusion dans re2js fonctionnent de la même manière que #include en C/C++ : le contenu de FILE est copié-collé tel quel à la place du bloc/directive. Les fichiers d'inclusion peuvent contenir d'autres inclusions. Utilisez l'option --depfile pour suivre les dépendances de compilation du fichier de sortie par rapport aux fichiers d'inclusion. re2js fournit quelques fichiers d'inclusion prédéfinis qui se trouvent dans le sous-répertoire include/ du projet. Ces fichiers contiennent des définitions qui peuvent être utiles à d'autres projets (telles que les catégories Unicode) et forment une sorte de bibliothèque standard pour re2js. Voici un exemple d'utilisation des fichiers d'inclusion.

Fichier d'inclusion 1 (definitions.js)

const INT = 1
const FLOAT = 2
const NAN = 3
/*!re2c
    number = [1-9][0-9]*;
*/

Fichier d'inclusion 2 (extra_rules.re.inc)

Fichier d'entrée

Fichiers d'en-tête

re2js permet de générer un fichier d'en-tête à partir du fichier .re d'entrée à l'aide de l'option --header ou de la configuration re2c:header et des paires de blocs /*!header:re2c:on*/ et /*!header:re2c:off*/, ou %{header:on%} et %{header:off%}. Le premier bloc marque le début du fichier d'en-tête, et le second bloc marque sa fin. Tout ce qui se trouve entre ces blocs est traité par re2js, et le code généré est écrit dans le fichier spécifié avec l'option --header ou la configuration re2c:header (ou stdout si aucune option ni configuration n'est utilisée). Le fichier d'en-tête généré automatiquement peut être nécessaire dans les cas où re2js est utilisé pour générer des définitions qui doivent être visibles depuis d'autres unités de traduction.

        re2c:header = "lexer/state.js";

}

    throw "error!"

Programmes squelettes
