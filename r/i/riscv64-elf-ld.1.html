LD(1) Outils de développement GNU LD(1)

NOM

ld - L'éditeur de liens GNU

SYNTAXE

ld [options] fichier objet ...

DESCRIPTION

ld combine un certain nombre de fichiers objets et d'archives, relocalise leurs données et résout les références de symboles. Généralement, la dernière étape de la compilation d'un programme consiste à exécuter ld.

ld accepte des fichiers de langage de commande de l'éditeur de liens écrits dans un sur-ensemble de la syntaxe du langage de commande de l'éditeur de liens d'AT&T, afin de fournir un contrôle explicite et total sur le processus d'édition de liens.

Cette page de manuel ne décrit pas le langage de commande ; voir l'entrée ld dans "info" pour des détails complets sur le langage de commande et sur d'autres aspects de l'éditeur de liens GNU.

Cette version de ld utilise les bibliothèques BFD à usage général pour opérer sur les fichiers objets. Cela permet à ld de lire, combiner et écrire des fichiers objets dans de nombreux formats différents, par exemple, COFF ou "a.out". Différents formats peuvent être liés ensemble pour produire n'importe quel type de fichier objet disponible.

Outre sa flexibilité, l'éditeur de liens GNU est plus utile que d'autres éditeurs de liens pour fournir des informations diagnostiques. De nombreux éditeurs de liens abandonnent l'exécution immédiatement en cas d'erreur ; dans la mesure du possible, ld continue l'exécution, vous permettant d'identifier d'autres erreurs (ou, dans certains cas, d'obtenir un fichier de sortie malgré l'erreur).

L'éditeur de liens GNU ld est conçu pour couvrir un large éventail de situations et pour être aussi compatible que possible avec d'autres éditeurs de liens. Par conséquent, vous avez de nombreux choix pour contrôler son comportement.

OPTIONS

L'éditeur de liens prend en charge une pléthore d'options en ligne de commande, mais en pratique peu d'entre elles sont utilisées dans un contexte particulier. Par exemple, une utilisation fréquente de ld est de lier des fichiers objets Unix standard sur un système Unix standard et pris en charge. Sur un tel système, pour lier un fichier "hello.o" :

ld -o <sortie> /lib/crt0.o hello.o -lc

Cela indique à ld de produire un fichier nommé sortie comme résultat de la liaison du fichier "/lib/crt0.o" avec "hello.o" et la bibliothèque "libc.a", qui proviendra des répertoires de recherche standard. (Voir la discussion de l'option -l ci-dessous.)

Certaines des options en ligne de commande de ld peuvent être spécifiées à n'importe quel endroit de la ligne de commande. Cependant, les options qui font référence à des fichiers, telles que -l ou -T, entraînent la lecture du fichier à l'endroit où l'option apparaît dans la ligne de commande, par rapport aux fichiers objets et aux autres options de fichier. Répéter des options non liées à des fichiers avec un argument différent n'aura aucun effet supplémentaire, ou annulera les occurrences précédentes (celles plus à gauche sur la ligne de commande) de cette option. Les options qui peuvent être spécifiées de manière significative plusieurs fois sont notées dans les descriptions ci-dessous.

Les arguments qui ne sont pas des options sont des fichiers objets ou des archives qui doivent être liés ensemble. Ils peuvent suivre, précéder ou être mélangés avec les options en ligne de commande, à l'exception qu'un argument de fichier objet ne peut pas être placé entre une option et son argument.

Généralement, l'éditeur de liens est invoqué avec au moins un fichier objet, mais vous pouvez spécifier d'autres formes de fichiers d'entrée binaires en utilisant -l, -R, et le langage de commande de script. Si *aucun* fichier d'entrée binaire n'est spécifié du tout, l'éditeur de liens ne produit aucune sortie et émet le message No input files.

Si l'éditeur de liens ne peut pas reconnaître le format d'un fichier objet, il supposera qu'il s'agit d'un script d'éditeur de liens. Un script spécifié de cette manière augmente le script principal de l'éditeur de liens utilisé pour la liaison (soit le script par défaut, soit celui spécifié avec -T). Cette fonctionnalité permet à l'éditeur de liens de se lier à un fichier qui semble être un objet ou une archive, mais qui ne fait en réalité que définir certaines valeurs de symboles, ou utilise "INPUT" ou "GROUP" pour charger d'autres objets. Spécifier un script de cette manière ne fait qu'augmenter le script principal de l'éditeur de liens, les commandes supplémentaires étant placées après le script principal ; utilisez l'option -T pour remplacer entièrement le script principal de l'éditeur de liens, mais notez l'effet de la commande "INSERT".

Pour les options dont le nom est une seule lettre, les arguments des options doivent soit suivre la lettre de l'option sans espace intermédiaire, soit être donnés comme arguments séparés immédiatement après l'option qui les requiert.

Pour les options dont le nom est composé de plusieurs lettres, un seul trait d'union ou deux peuvent précéder le nom de l'option ; par exemple, -trace-symbol et --trace-symbol sont équivalents. Notez qu'il y a une exception à cette règle. Les options composées de plusieurs lettres commençant par un 'o' minuscule ne peuvent être précédées que de deux traits d'union. Ceci est fait pour réduire la confusion avec l'option -o. Ainsi, par exemple, -omagic définit le nom du fichier de sortie à magic tandis que --omagic définit le drapeau NMAGIC sur la sortie.

Les arguments des options composées de plusieurs lettres doivent être séparés du nom de l'option par un signe égal, ou être donnés comme arguments séparés immédiatement après l'option qui les requiert. Par exemple, --trace-symbol foo et --trace-symbol=foo sont équivalents. Des abréviations uniques des noms des options composées de plusieurs lettres sont acceptées.

Notez que si l'éditeur de liens est invoqué indirectement, via un compilateur pilote (par exemple, gcc), alors toutes les options de la ligne de commande de l'éditeur de liens doivent être préfixées par -Wl, (ou ce qui est approprié pour le pilote de compilation particulier) comme ceci :

gcc -Wl,--start-group foo.o bar.o -Wl,--end-group

Ceci est important, car sinon le programme pilote de compilation peut silencieusement ignorer les options de l'éditeur de liens, résultant en une liaison incorrecte. Une confusion peut également survenir lors du passage d'options nécessitant des valeurs via un pilote, car l'utilisation d'un espace entre l'option et l'argument agit comme un séparateur, et amène le pilote à passer uniquement l'option à l'éditeur de liens et l'argument au compilateur. Dans ce cas, il est plus simple d'utiliser les formes jointes des options à lettre unique et à plusieurs lettres, telles que :

gcc foo.o bar.o -Wl,-eENTRY -Wl,-Map=a.map

Voici une table des commutateurs génériques de ligne de commande acceptés par l'éditeur de liens GNU :

@fichier
Lit les options de la ligne de commande depuis fichier. Les options lues sont insérées à la place de l'option @fichier d'origine. Si fichier n'existe pas, ou ne peut être lu, alors l'option sera traitée littéralement, et ne sera pas supprimée.

Les options dans fichier sont séparées par des espaces blancs. Un caractère d'espace blanc peut être inclus dans une option en entourant l'option entière de guillemets simples ou doubles. N'importe quel caractère (y compris un antislash) peut être inclus en préfixant le caractère à inclure par un antislash. Le fichier peut lui-même contenir d'autres options @fichier ; ces options seront traitées récursivement.

-a mot-clé
Cette option est prise en charge pour la compatibilité HP/UX. L'argument mot-clé doit être l'une des chaînes archive, shared, ou default. -aarchive est fonctionnellement équivalent à -Bstatic, et les deux autres mots-clés sont fonctionnellement équivalents à -Bdynamic. Cette option peut être utilisée un nombre illimité de fois.
--audit BIBLIOTHEQUE_AUDIT
Ajoute BIBLIOTHEQUE_AUDIT à l'entrée "DT_AUDIT" de la section dynamique. BIBLIOTHEQUE_AUDIT n'est pas vérifiée quant à son existence, et n'utilisera pas non plus le DT_SONAME spécifié dans la bibliothèque. Si spécifié plusieurs fois, "DT_AUDIT" contiendra une liste séparée par des deux-points des interfaces d'audit à utiliser. Si l'éditeur de liens trouve un objet avec une entrée d'audit lors de la recherche de bibliothèques partagées, il ajoutera une entrée "DT_DEPAUDIT" correspondante dans le fichier de sortie. Cette option n'est significative que sur les plateformes ELF prenant en charge l'interface rtld-audit.
-b format-entrée
--format=format-entrée
ld peut être configuré pour prendre en charge plus d'un type de fichier objet. Si votre ld est configuré de cette manière, vous pouvez utiliser l'option -b pour spécifier le format binaire des fichiers objets qui suivent cette option sur la ligne de commande. Même lorsque ld est configuré pour prendre en charge des formats d'objets alternatifs, vous n'avez généralement pas besoin de le spécifier, car ld devrait être configuré pour attendre comme
un format d'entrée par défaut, le format le plus courant sur chaque machine. input-format est une chaîne de caractères, le nom d'un format particulier pris en charge par les bibliothèques BFD. (Vous pouvez lister les formats binaires disponibles avec objdump -i.)

Vous voudrez peut-être utiliser cette option si vous liez des fichiers avec un format binaire inhabituel. Vous pouvez également utiliser -b pour changer explicitement de format (lors de la liaison de fichiers objets de formats différents), en incluant -b input-format avant chaque groupe de fichiers objets d'un format particulier.

Le format par défaut est pris de la variable d'environnement "GNUTARGET".

Vous pouvez également définir le format d'entrée à partir d'un script, en utilisant la commande "TARGET" ;

-c MRI-commandfile
--mri-script=MRI-commandfile
Pour la compatibilité avec les linkers produits par MRI, ld accepte des fichiers scripts écrits dans un langage de commande alternatif et restreint, décrit dans la section Fichiers Scripts Compatibles MRI de la documentation de GNU ld. Introduisez les fichiers scripts MRI avec l'option -c ; utilisez l'option -T pour exécuter les scripts de linker écrits dans le langage de script généraliste ld. Si MRI-cmdfile n'existe pas, ld le recherche dans les répertoires spécifiés par les options -L.
-d
-dc
-dp
Ces trois options sont équivalentes ; plusieurs formes sont prises en charge pour la compatibilité avec d'autres linkers. Elles assignent de l'espace aux symboles communs même si un fichier de sortie relocable est spécifié (avec -r). La commande script "FORCE_COMMON_ALLOCATION" a le même effet.
--depaudit AUDITLIB
-P AUDITLIB
Ajoute AUDITLIB à l'entrée "DT_DEPAUDIT" de la section dynamique. AUDITLIB n'est pas vérifié quant à son existence, ni n'utilisera le DT_SONAME spécifié dans la bibliothèque. Si spécifié plusieurs fois, "DT_DEPAUDIT" contiendra une liste d'interfaces d'audit séparées par des deux-points à utiliser. Cette option n'a de sens que sur les plateformes ELF prenant en charge l'interface rtld-audit. L'option -P est fournie pour la compatibilité Solaris.
--enable-linker-version
Active la directive de script de linker "LINKER_VERSION", décrite dans **Données de Section de Sortie**. Si cette directive est utilisée dans un script de linker et que cette option a été activée, une chaîne contenant la version du linker sera insérée au point actuel.

Note - la position de cette option sur la ligne de commande du linker est importante. Elle n'affectera que les scripts de linker qui la suivent sur la ligne de commande, ou qui sont intégrés au linker.

--disable-linker-version
Désactive la directive de script de linker "LINKER_VERSION", de sorte qu'elle n'insère pas de chaîne de version. C'est le comportement par défaut.
--enable-non-contiguous-regions
Cette option évite de générer une erreur si une section d'entrée ne rentre pas dans une section de sortie correspondante. Le linker essaie d'allouer la section d'entrée aux sections de sortie correspondantes suivantes, et ne génère une erreur que si aucune section de sortie n'est suffisamment grande. Ceci est utile lorsque plusieurs régions de mémoire non contiguës sont disponibles et que la section d'entrée ne nécessite pas une région particulière. L'ordre dans lequel les sections d'entrée sont évaluées ne change pas, par exemple : 
MEMORY {
  MEM1 (rwx) : ORIGIN = 0x1000, LENGTH = 0x14
  MEM2 (rwx) : ORIGIN = 0x1000, LENGTH = 0x40
  MEM3 (rwx) : ORIGIN = 0x2000, LENGTH = 0x40
}
SECTIONS {
  mem1 : { *(.data.*); } > MEM1
  mem2 : { *(.data.*); } > MEM2
  mem3 : { *(.data.*); } > MEM3
}

avec des sections d'entrée :
.data.1: taille 8
.data.2: taille 0x10
.data.3: taille 4

résulte en .data.1 affecté à mem1, et .data.2 et .data.3
affectés à mem2, même si .data.3 rentre dans mem3.

Cette option est incompatible avec les instructions INSERT car elle modifie la manière dont les sections d'entrée sont mappées aux sections de sortie.

--enable-non-contiguous-regions-warnings
Cette option active les avertissements lorsque "--enable-non-contiguous-regions" permet des correspondances potentiellement inattendues dans le mappage des sections, ce qui peut conduire à ignorer silencieusement une section au lieu d'échouer car elle ne rentre dans aucune région de sortie.
-e entry
--entry=entry
Utilise entry comme symbole explicite pour commencer l'exécution de votre programme, plutôt que le point d'entrée par défaut. S'il n'y a pas de symbole nommé entry, le linker essaiera d'analyser entry comme un nombre, et l'utilisera comme adresse d'entrée (le nombre sera interprété en base 10 ; vous pouvez utiliser un 0x préfixé pour la base 16, ou un 0 préfixé pour la base 8).
--exclude-libs lib,lib,...
Spécifie une liste de bibliothèques d'archives à partir desquelles les symboles ne doivent pas être automatiquement exportés. Les noms de bibliothèques peuvent être délimités par des virgules ou des deux-points. Spécifier "--exclude-libs ALL" exclut les symboles de toutes les bibliothèques d'archives de l'exportation automatique. Cette option n'est disponible que pour le port cible i386 PE du linker et pour les ports cibles ELF. Pour i386 PE, les symboles explicitement listés dans un fichier .def sont toujours exportés, quelle que soit cette option. Pour les ports cibles ELF, les symboles affectés par cette option seront traités comme cachés.
--exclude-modules-for-implib module,module,...
Spécifie une liste de fichiers objets ou de membres d'archives, à partir desquels les symboles ne doivent pas être automatiquement exportés, mais qui doivent être copiés intégralement dans la bibliothèque d'importation générée pendant la liaison. Les noms de modules peuvent être délimités par des virgules ou des deux-points, et doivent correspondre exactement aux noms de fichiers utilisés par ld pour ouvrir les fichiers ; pour les membres d'archives, il s'agit simplement du nom du membre, mais pour les fichiers objets, le nom listé doit inclure et correspondre précisément à tout chemin utilisé pour spécifier le fichier d'entrée sur la ligne de commande du linker. Cette option n'est disponible que pour le port cible i386 PE du linker. Les symboles explicitement listés dans un fichier .def sont toujours exportés, quelle que soit cette option.
-E
--export-dynamic
--no-export-dynamic
Lors de la création d'un exécutable lié dynamiquement, l'utilisation de l'option -E ou de l'option --export-dynamic demande au linker d'ajouter tous les symboles à la table des symboles dynamiques. La table des symboles dynamiques est l'ensemble des symboles qui sont visibles depuis les objets dynamiques au moment de l'exécution.

Si vous n'utilisez aucune de ces options (ou si vous utilisez l'option --no-export-dynamic pour rétablir le comportement par défaut), la table des symboles dynamiques contiendra normalement uniquement les symboles qui sont référencés par un objet dynamique mentionné dans la liaison.

Si vous utilisez "dlopen" pour charger un objet dynamique qui doit renvoyer vers les symboles définis par le programme, plutôt que vers un autre objet dynamique, vous devrez probablement utiliser cette option lors de la liaison du programme lui-même.

Vous pouvez également utiliser la liste dynamique pour contrôler quels symboles doivent être ajoutés à la table des symboles dynamiques si le format de sortie le prend en charge. Voir la description de --dynamic-list.

Notez que cette option est spécifique aux ports cibles ELF. Les cibles PE prennent en charge une fonction similaire pour exporter tous les symboles depuis une DLL ou un EXE ; voir la description de --export-all-symbols ci-dessous.

--export-dynamic-symbol=glob
Lors de la création d'un exécutable lié dynamiquement, les symboles correspondant à glob seront ajoutés à la table des symboles dynamiques. Lors de la création d'une bibliothèque partagée, les références aux symboles correspondant à glob ne seront pas liées aux définitions à l'intérieur de la bibliothèque partagée. Cette option est une opération nulle lors de la création d'une bibliothèque partagée et lorsque -Bsymbolic ou --dynamic-list ne sont pas spécifiés. Cette option n'a de sens que sur les plateformes ELF qui prennent en charge les bibliothèques partagées.
--export-dynamic-symbol-list=file
Spécifie un --export-dynamic-symbol pour chaque modèle dans le fichier. Le format du fichier est identique au nœud de version sans portée ni nom de nœud. Voir **VERSION** pour plus d'informations.
-EB
Lie des objets big-endian. Cela affecte le format de sortie par défaut.
-EL
Lie des objets little-endian. Cela affecte le format de sortie par défaut.
-f name
--auxiliary=name
Lors de la création d'un objet partagé ELF, définit le champ interne DT_AUXILIARY sur le nom spécifié. Cela indique au linker dynamique que la table des symboles de l'objet partagé doit être utilisée comme un filtre auxiliaire sur la table des symboles de l'objet partagé name.

Si vous liez plus tard un programme contre cet objet filtre, alors, lorsque vous exécuterez le programme, le linker dynamique verra le champ DT_AUXILIARY. Si le linker dynamique résout des symboles à partir de l'objet filtre, il vérifiera d'abord s'il existe une définition dans l'objet partagé name. S'il y en a une, elle sera utilisée à la place de la définition dans l'objet filtre. L'objet partagé name n'a pas besoin d'exister. Ainsi, l'objet partagé name peut être utilisé pour fournir une implémentation alternative de certaines fonctions, peut-être pour le débogage ou pour des performances spécifiques à la machine.

Cette option peut être spécifiée plusieurs fois. Les entrées DT_AUXILIARY seront créées dans l'ordre où elles apparaissent sur la ligne de commande.

-F name
--filter=nom
Lors de la création d'un objet partagé ELF, définit le champ interne DT_FILTER sur le nom spécifié. Cela indique à l'éditeur de liens dynamique que la table des symboles de l'objet partagé qui est en cours de création doit être utilisée comme filtre pour la table des symboles de l'objet partagé nom.

Si vous liez ultérieurement un programme à cet objet filtre, lorsque vous exécutez le programme, l'éditeur de liens dynamique verra le champ DT_FILTER. L'éditeur de liens dynamique résoudra les symboles conformément à la table des symboles de l'objet filtre comme d'habitude, mais il se liera en réalité aux définitions trouvées dans l'objet partagé nom. Ainsi, l'objet filtre peut être utilisé pour sélectionner un sous-ensemble des symboles fournis par l'objet nom.

Certains éditeurs de liens plus anciens utilisaient l'option -F tout au long d'une chaîne d'outils de compilation pour spécifier le format des fichiers objets pour les fichiers objets d'entrée et de sortie. L'éditeur de liens GNU utilise d'autres mécanismes à cet effet : les options -b, --format, --oformat, la commande "TARGET" dans les scripts de l'éditeur de liens, et la variable d'environnement "GNUTARGET". L'éditeur de liens GNU ignorera l'option -F lorsqu'il ne créera pas d'objet partagé ELF.

-fini=nom
Lors de la création d'un exécutable ou d'un objet partagé ELF, appelle NOM lorsque l'exécutable ou l'objet partagé est déchargé, en définissant DT_FINI sur l'adresse de la fonction. Par défaut, l'éditeur de liens utilise "_fini" comme fonction à appeler.
-g
Ignoré. Fourni pour la compatibilité avec d'autres outils.
-G valeur
--gpsize=valeur
Définit la taille maximale des objets à optimiser à l'aide du registre GP sur taille. Ceci n'est significatif que pour les formats de fichiers objets tels que MIPS ELF qui prennent en charge le placement d'objets volumineux et petits dans des sections différentes. Ceci est ignoré pour les autres formats de fichiers objets.
-h nom
-soname=nom
Lors de la création d'un objet partagé ELF, définit le champ interne DT_SONAME sur le nom spécifié. Lorsqu'un exécutable est lié à un objet partagé qui possède un champ DT_SONAME, lorsque l'exécutable est exécuté, l'éditeur de liens dynamique tentera de charger l'objet partagé spécifié par le champ DT_SONAME plutôt que d'utiliser le nom de fichier donné à l'éditeur de liens.
-i
Effectue une liaison incrémentielle (identique à l'option -r).
-init=nom
Lors de la création d'un exécutable ou d'un objet partagé ELF, appelle NOM lorsque l'exécutable ou l'objet partagé est chargé, en définissant DT_INIT sur l'adresse de la fonction. Par défaut, l'éditeur de liens utilise "_init" comme fonction à appeler.
-l spécification-nom
--library=spécification-nom
Ajoute l'archive ou le fichier objet spécifié par spécification-nom à la liste des fichiers à lier. Cette option peut être utilisée un nombre quelconque de fois. Si spécification-nom est de la forme :nomfichier, ld recherchera dans le chemin de bibliothèques un fichier nommé nomfichier, sinon il recherchera dans le chemin de bibliothèques un fichier nommé libspécification-nom.a.

Sur les systèmes qui prennent en charge les bibliothèques partagées, ld peut également rechercher des fichiers autres que libspécification-nom.a. Spécifiquement, sur les systèmes ELF et SunOS, ld recherchera dans un répertoire une bibliothèque nommée libspécification-nom.so avant de rechercher celle nommée libspécification-nom.a. (Par convention, une extension ".so" indique une bibliothèque partagée.) Notez que ce comportement ne s'applique pas à :nomfichier, qui spécifie toujours un fichier nommé nomfichier.

L'éditeur de liens ne recherchera dans une archive qu'une seule fois, à l'emplacement où elle est spécifiée sur la ligne de commande. Si l'archive définit un symbole qui était indéfini dans un objet apparu avant l'archive sur la ligne de commande, l'éditeur de liens inclura les fichiers appropriés de l'archive. Cependant, un symbole indéfini dans un objet apparaissant plus tard sur la ligne de commande ne provoquera pas une nouvelle recherche dans l'archive par l'éditeur de liens.

Voir l'option -( pour une façon de forcer l'éditeur de liens à rechercher les archives plusieurs fois.

Vous pouvez lister la même archive plusieurs fois sur la ligne de commande.

Ce type de recherche d'archives est standard pour les éditeurs de liens Unix. Cependant, si vous utilisez ld sur AIX, notez qu'il est différent du comportement de l'éditeur de liens AIX.

-L répertoire-recherche
--library-path=répertoire-recherche
Ajoute le chemin répertoire-recherche à la liste des chemins que ld recherchera pour les bibliothèques d'archives et les scripts de contrôle de ld. Vous pouvez utiliser cette option un nombre quelconque de fois. Les répertoires sont recherchés dans l'ordre où ils sont spécifiés sur la ligne de commande. Les répertoires spécifiés sur la ligne de commande sont recherchés avant les répertoires par défaut. Toutes les options -L s'appliquent à toutes les options -l, indépendamment de l'ordre dans lequel les options apparaissent. Les options -L n'affectent pas la façon dont ld recherche un script d'éditeur de liens, sauf si l'option -T est spécifiée.

Si répertoire-recherche commence par "=" ou $SYSROOT, alors ce préfixe sera remplacé par le préfixe sysroot, contrôlé par l'option --sysroot, ou spécifié lors de la configuration de l'éditeur de liens.

L'ensemble par défaut des chemins recherchés (sans être spécifiés avec -L) dépend du mode d'émulation que ld utilise, et dans certains cas également de la façon dont il a été configuré.

Les chemins peuvent également être spécifiés dans un script de liaison avec la commande "SEARCH_DIR". Les répertoires spécifiés de cette manière sont recherchés au point où le script de liaison apparaît sur la ligne de commande.

-m émulation
Émule l'éditeur de liens émulation. Vous pouvez lister les émulations disponibles avec les options --verbose ou -V.

Si l'option -m n'est pas utilisée, l'émulation est prise de la variable d'environnement "LDEMULATION", si elle est définie.

Sinon, l'émulation par défaut dépend de la façon dont l'éditeur de liens a été configuré.

--remap-inputs=motif=nomfichier
--remap-inputs-file=fichier
Ces options permettent de modifier les noms des fichiers d'entrée avant que l'éditeur de liens ne tente de les ouvrir. L'option --remap-inputs=foo.o=bar.o provoquera la tentative de chargement d'un fichier nommé bar.o à la place de toute tentative de chargement d'un fichier nommé foo.o. Des motifs génériques sont autorisés dans le premier nom de fichier, donc --remap-inputs=foo*.o=bar.o renommera tout fichier d'entrée correspondant à foo*.o en bar.o.

Une forme alternative de l'option --remap-inputs-file=nomfichier permet de lire les remappings à partir d'un fichier. Chaque ligne du fichier peut contenir un seul remapping. Les lignes vides sont ignorées. Tout à partir d'un caractère dièse (#) jusqu'à la fin d'une ligne est considéré comme un commentaire et est également ignoré. Le motif de mappage peut être séparé du nom de fichier par un espace blanc ou un caractère égal (=).

Les options peuvent être spécifiées plusieurs fois. Leurs contenus s'accumulent. Les remappings seront traités dans l'ordre où ils apparaissent sur la ligne de commande, et s'ils proviennent d'un fichier, dans l'ordre où ils apparaissent dans le fichier. Si une correspondance est trouvée, aucune vérification supplémentaire pour ce nom de fichier ne sera effectuée.

Si le nom de fichier de remplacement est /dev/null ou simplement NUL, le remapping provoquera effectivement l'ignorance du fichier d'entrée. Cela peut être un moyen pratique d'expérimenter en supprimant des fichiers d'entrée d'un environnement de build complexe.

Notez que cette option dépend de la position et n'affecte que les noms de fichiers qui la suivent sur la ligne de commande. Ainsi :

ld foo.o --remap-inputs=foo.o=bar.o

N'aura aucun effet, alors que :

ld --remap-inputs=foo.o=bar.o foo.o

Renommera le fichier d'entrée foo.o en bar.o.

Remarque : ces options affectent également les fichiers référencés par les instructions INPUT dans les scripts de l'éditeur de liens. Mais comme les scripts de l'éditeur de liens sont traités après la lecture de toute la ligne de commande, la position des options de remapping sur la ligne de commande n'est pas significative.

Si l'option verbose est activée, tous les mappages correspondants seront signalés, bien que là encore, l'option verbose doive être activée sur la ligne de commande avant que les noms de fichiers remappés n'apparaissent.

Si les options -Map ou --print-map sont activées, la liste de remapping sera incluse dans la sortie de la carte.

-M
--print-map
Imprime une carte de liaison sur la sortie standard. Une carte de liaison fournit des informations sur la liaison, notamment :
  • Où les fichiers objets sont mappés en mémoire.
  • Comment les symboles communs sont alloués.
  • Tous les membres d'archive inclus dans la liaison, avec une mention du symbole qui a provoqué l'inclusion du membre d'archive.
  • Les valeurs attribuées aux symboles.

    Remarque : les symboles dont les valeurs sont calculées par une expression qui implique une référence à une valeur précédente du même symbole peuvent ne pas afficher le résultat correct dans la carte de liaison. En effet, l'éditeur de liens élimine les résultats intermédiaires et ne conserve que la valeur finale d'une expression. Dans de telles circonstances, l'éditeur de liens affichera la valeur finale entourée de crochets. Ainsi, par exemple, un script d'éditeur de liens contenant :

    foo = 1
foo = foo * 4
foo = foo + 8

    produira la sortie suivante dans la carte de liaison si l'option -M est utilisée :

    0x00000001                foo = 0x1
[0x0000000c]                foo = (foo * 0x4)
[0x0000000c]                foo = (foo + 0x8)

    Voir Expressions pour

plus d'informations sur les expressions dans les scripts de liaison.

  • Comment les propriétés GNU sont fusionnées.

    Lorsque le lieur fusionne les sections .note.gnu.property d'entrée en une section .note.gnu.property de sortie, certaines propriétés sont supprimées ou mises à jour. Ces actions sont rapportées dans la carte de liaison. Par exemple :

    Propriété 0xc0000002 supprimée pour fusionner foo.o (0x1) et bar.o (non trouvé)

    Cela indique que la propriété 0xc0000002 est supprimée de la sortie lors de la fusion des propriétés dans foo.o, dont la valeur de la propriété 0xc0000002 est 0x1, et bar.o, qui n'a pas la propriété 0xc0000002.

    Propriété 0xc0010001 (0x1) mise à jour pour fusionner foo.o (0x1) et bar.o (0x1)

    Cela indique que la valeur de la propriété 0xc0010001 est mise à jour à 0x1 en sortie lors de la fusion des propriétés dans foo.o, dont la valeur de la propriété 0xc0010001 est 0x1, et bar.o, dont la valeur de la propriété 0xc0010001 est 0x1.

  • Sur certaines cibles ELF, une liste de corrections insérées par --relax 
    foo.o : Ajustement de la branche à 0x00000008 vers « far » dans la section .text

    Cela indique que la branche à 0x00000008 dans foo.o, ciblant le symbole « far » dans la section .text, a été remplacée par un trampoline.

    -( archives -)
    --start-group archives --end-group
    Les archives doivent être une liste de fichiers d'archives. Elles peuvent être des noms de fichiers explicites ou des options -l.

    Les archives spécifiées sont recherchées de manière répétée jusqu'à ce qu'aucune nouvelle référence non résolue ne soit créée. Normalement, une archive n'est recherchée qu'une seule fois dans l'ordre où elle est spécifiée sur la ligne de commande. Si un symbole dans cette archive est nécessaire pour résoudre un symbole non résolu auquel fait référence un objet dans une archive qui apparaît plus tard sur la ligne de commande, l'éditeur de liens ne serait pas en mesure de résoudre cette référence. En regroupant les archives, elles seront toutes recherchées de manière répétée jusqu'à ce que toutes les références possibles soient résolues.

    L'utilisation de cette option a un coût de performance significatif. Il est préférable de l'utiliser uniquement lorsqu'il existe des références circulaires inévitables entre deux archives ou plus.

    --as-needed
    --no-as-needed
    Cette option affecte les balises DT_NEEDED ELF pour les bibliothèques dynamiques mentionnées sur la ligne de commande après l'option --as-needed. Normalement, l'éditeur de liens ajoutera une balise DT_NEEDED pour chaque bibliothèque dynamique mentionnée sur la ligne de commande, que la bibliothèque soit effectivement nécessaire ou non. --as-needed fait qu'une balise DT_NEEDED n'est émise que pour une bibliothèque qui, à ce stade du lien, satisfait une référence de symbole non faible non résolue d'un fichier objet ou, si la bibliothèque n'est pas trouvée dans les listes DT_NEEDED d'autres bibliothèques nécessaires, une référence de symbole non faible non résolue d'une autre bibliothèque dynamique nécessaire. Cela élimine l'espace en double inutilisé dans la bibliothèque partagée, et empêche également toute confusion possible sur la résolution vers le mauvais doublon lorsqu'il y a de nombreux modules dynamiques avec des chemins de recherche spécialisés pour la résolution des symboles à l'exécution.

    L'éditeur de liens traite les arguments --defsym et les arguments -T dans l'ordre. Placer --defsym avant -T définira le symbole avant le traitement du script de l'éditeur de liens de -T, tandis que placer --defsym après -T définira le symbole après le traitement du script de l'éditeur de liens. Cette différence a des conséquences sur les expressions dans le script de l'éditeur de liens qui utilisent les symboles --defsym ; l'ordre correct dépendra de ce que vous essayez d'accomplir.

Les alignements de symboles considérés sont de seize octets ou plus, de huit octets, de quatre octets, de deux octets et d'un octet. Ceci afin d'éviter les écarts entre les symboles dus aux contraintes d'alignement. Si aucun ordre de tri n'est spécifié, alors l'ordre décroissant est supposé.
    --sort-section=name
    Cette option appliquera "SORT_BY_NAME" à tous les motifs de section jokers dans le script d'éditeur de liens.
    --sort-section=alignment
    Cette option appliquera "SORT_BY_ALIGNMENT" à tous les motifs de section jokers dans le script d'éditeur de liens.
    --spare-dynamic-tags=nombre
    Cette option spécifie le nombre d'emplacements vides à laisser dans la section .dynamic des objets partagés ELF. Des emplacements vides peuvent être nécessaires pour les outils de post-traitement, tels que le pré-éditeur de liens. La valeur par défaut est 5.
    --split-by-file[=taille]
    Similaire à --split-by-reloc mais crée une nouvelle section de sortie pour chaque fichier d'entrée lorsque taille est atteinte. taille vaut par défaut 1 si elle n'est pas donnée.
    --split-by-reloc[=nombre]
    Essaie de créer des sections supplémentaires dans le fichier de sortie de sorte qu'aucune section de sortie unique dans le fichier ne contienne plus de nombre relocations. Ceci est utile lors de la génération de fichiers relocalisables énormes pour le téléchargement dans certains noyaux en temps réel avec le format de fichier objet COFF ; car COFF ne peut pas représenter plus de 65535 relocations dans une seule section. Notez que cela ne fonctionnera pas avec les formats de fichiers objets qui ne supportent pas les sections arbitraires. L'éditeur de liens ne fractionnera pas les sections d'entrée individuelles pour redistribution, donc si une section d'entrée contient plus de nombre relocations, une section de sortie en conterra ce nombre. nombre vaut par défaut 32768.
    --stats
    Calcule et affiche des statistiques sur le fonctionnement de l'éditeur de liens, telles que le temps d'exécution et l'utilisation de la mémoire.
    --sysroot=répertoire
    Utilise répertoire comme emplacement du sysroot, remplaçant la valeur par défaut configurée lors de la compilation. Cette option n'est prise en charge que par les éditeurs de liens qui ont été configurés à l'aide de --with-sysroot.
    --task-link
    Ceci est utilisé par les cibles basées sur COFF/PE pour créer un fichier objet liant les tâches où tous les symboles globaux ont été convertis en statiques.
    --traditional-format
    Pour certaines cibles, la sortie de ld diffère à certains égards de la sortie de certains éditeurs de liens existants. Ce commutateur demande à ld d'utiliser le format traditionnel à la place.

    Par exemple, sur SunOS, ld combine les entrées dupliquées dans la table des chaînes de symboles. Cela peut réduire la taille d'un fichier de sortie avec des informations de débogage complètes de plus de 30 pour cent. Malheureusement, le programme "dbx" de SunOS ne peut pas lire le programme résultant ("gdb" n'a aucun problème). Le commutateur --traditional-format indique à ld de ne pas combiner les entrées dupliquées.

    --section-start=nomsection=org
    Localise une section dans le fichier de sortie à l'adresse absolue donnée par org. Vous pouvez utiliser cette option autant de fois que nécessaire pour localiser plusieurs sections dans la ligne de commande. org doit être un entier hexadécimal unique ; pour la compatibilité avec d'autres éditeurs de liens, vous pouvez omettre le préfixe 0x généralement associé aux valeurs hexadécimales. Note : il ne doit pas y avoir d'espace blanc entre nomsection, le signe égal ("="), et org.
    -Tbss=org
    -Tdata=org
    -Ttext=org
    Identique à --section-start, avec ".bss", ".data" ou ".text" comme nomsection.
    -Ttext-segment=org
    Lors de la création d'un exécutable ELF, il définit l'adresse du premier octet du segment de texte.
    -Trodata-segment=org
    Lors de la création d'un exécutable ELF ou d'un objet partagé pour une cible où les données en lecture seule se trouvent dans leur propre segment séparé du texte exécutable, il définit l'adresse du premier octet du segment de données en lecture seule.
    -Tldata-segment=org
    Lors de la création d'un exécutable ELF ou d'un objet partagé pour le modèle de mémoire moyenne x86-64, il définit l'adresse du premier octet du segment ldata.
    --unresolved-symbols=méthode
    Détermine comment gérer les symboles non résolus. Il existe quatre valeurs possibles pour méthode :
    ignore-all
    Ne signaler aucun symbole non résolu.
    report-all
    Signaler tous les symboles non résolus. C'est la valeur par défaut.
    ignore-in-object-files
    Signaler les symboles non résolus contenus dans les bibliothèques partagées, mais les ignorer s'ils proviennent de fichiers objets réguliers.
    ignore-in-shared-libs
    Signaler les symboles non résolus provenant de fichiers objets réguliers, mais les ignorer s'ils proviennent de bibliothèques partagées. Cela peut être utile lors de la création d'un binaire dynamique et lorsque l'on sait que toutes les bibliothèques partagées auxquelles il devrait faire référence sont incluses dans la ligne de commande de l'éditeur de liens.

    Le comportement pour les bibliothèques partagées seules peut également être contrôlé par l'option --[no-]allow-shlib-undefined.

    Normalement, l'éditeur de liens générera un message d'erreur pour chaque symbole non résolu signalé, mais l'option --warn-unresolved-symbols peut changer cela en un avertissement.

    --dll-verbose
    --verbose[=NOMBRE]
    Affiche le numéro de version de ld et liste les émulations d'éditeur de liens supportées. Affiche quels fichiers d'entrée peuvent être ouverts et lesquels ne le peuvent pas. Affiche le script d'éditeur de liens utilisé par l'éditeur de liens. Si l'argument facultatif NOMBRE est > 1, le statut des symboles du plugin sera également affiché.
    --version-script=fichier-script-version
    Spécifie le nom d'un script de version à l'éditeur de liens. Ceci est typiquement utilisé lors de la création de bibliothèques partagées pour spécifier des informations supplémentaires sur la hiérarchie des versions de la bibliothèque en cours de création. Cette option n'est entièrement prise en charge que sur les plates-formes ELF qui supportent les bibliothèques partagées ; voir VERSION. Elle est partiellement prise en charge sur les plates-formes PE, qui peuvent utiliser des scripts de version pour filtrer la visibilité des symboles en mode d'exportation automatique : tous les symboles marqués comme local dans le script de version ne seront pas exportés.
    --warn-common
    Avertit lorsqu'un symbole commun est combiné avec un autre symbole commun ou avec une définition de symbole. Les éditeurs de liens Unix autorisent cette pratique quelque peu laxiste, mais les éditeurs de liens sur certains autres systèmes d'exploitation ne le font pas. Cette option vous permet de trouver des problèmes potentiels liés à la combinaison de symboles globaux. Malheureusement, certaines bibliothèques C utilisent cette pratique, vous pourriez donc recevoir des avertissements concernant des symboles dans les bibliothèques ainsi que dans vos programmes.

    Il existe trois types de symboles globaux, illustrés ici par des exemples C :

    int i = 1;
    Une définition, qui va dans la section de données initialisées du fichier de sortie.
    extern int i;
    Une référence indéfinie, qui
    h n'alloue pas d'espace. Il doit y avoir soit une définition, soit un symbole commun pour la variable quelque part.
    int i;
    Un symbole commun. S'il n'y a qu'un ou plusieurs symboles communs pour une variable, celle-ci est placée dans la zone de données non initialisées du fichier de sortie. L'éditeur de liens fusionne plusieurs symboles communs pour la même variable en un seul symbole. S'ils sont de tailles différentes, il choisit la taille la plus grande. L'éditeur de liens transforme un symbole commun en déclaration s'il existe une définition de la même variable.

    L'option --warn-common peut produire cinq types d'avertissements. Chaque avertissement se compose d'une paire de lignes : la première décrit le symbole vient d'être rencontré, et la seconde décrit le symbole précédent rencontré avec le même nom. Un ou deux des deux symboles seront un symbole commun.

    1.
    Transformation d'un symbole commun en référence, car il existe déjà une définition du symbole. 
    <file>(<section>): warning: common of `<symbol>'
   overridden by definition
<file>(<section>): warning: defined here
    2.
    Transformation d'un symbole commun en référence, car une définition ultérieure du symbole est rencontrée. C'est la même chose que le cas précédent, sauf que les symboles sont rencontrés dans un ordre différent. 
    <file>(<section>): warning: definition of `<symbol>'
   overriding common
<file>(<section>): warning: common is here
    3.
    Fusion d'un symbole commun avec un symbole commun précédent de même taille. 
    <file>(<section>): warning: multiple common
   of `<symbol>'
<file>(<section>): warning: previous common is here
    4.
    Fusion d'un symbole commun avec un symbole commun précédent plus grand. 
    <file>(<section>): warning: common of `<symbol>'
   overridden by larger common
<file>(<section>): warning: larger common is here
    5.
    Fusion d'un symbole commun avec un symbole commun précédent plus petit. C'est la même chose que le cas précédent, sauf que les symboles sont rencontrés dans un ordre différent. 
    <file>(<section>): warning: common of `<symbol>'
   overriding smaller common
<file>(<section>): warning: smaller common is here
    --warn-constructors
    Avertir si des constructeurs globaux sont utilisés. Ceci n'est utile que pour quelques formats de fichiers objets. Pour des formats comme COFF ou ELF, l'éditeur de liens ne peut pas détecter l'utilisation de constructeurs globaux.
    --warn-execstack
    --warn-execstack-objects
    --no-warn-execstack
    Sur les plateformes ELF, l'éditeur de liens peut générer des messages d'avertissement s'il est invité à créer un fichier de sortie contenant une pile exécutable. Il y a trois états possibles :
    1.
    Ne générer aucun avertissement.
    2.
    Générer toujours des avertissements, même si la pile exécutable est demandée via l'option de ligne de commande -z execstack.
    3.
    Générer un avertissement uniquement si un fichier objet demande une pile exécutable, mais pas si l'option -z execstack est utilisée.

    L'état par défaut dépend de la manière dont l'éditeur de liens a été configuré lors de sa construction. L'option --no-warn-execstack met toujours l'éditeur de liens en mode sans avertissement. L'option --warn-execstack met l'éditeur de liens en mode avertissement permanent. L'option --warn-execstack-objects met l'éditeur de liens en mode avertissement uniquement pour les fichiers objets.

    Remarque : les fichiers d'entrée au format ELF peuvent spécifier qu'ils nécessitent une pile exécutable en ayant une section .note.GNU-stack avec le bit exécutable défini dans ses indicateurs de section. Ils peuvent spécifier qu'ils n'ont pas besoin d'une pile exécutable en ayant la même section, mais sans le bit exécutable défini. Si un fichier d'entrée n'a pas de section .note.GNU-stack, alors le comportement par défaut est spécifique à la cible. Pour certaines cibles, l'absence d'une telle section implique qu'une pile exécutable *est* requise. C'est souvent un problème pour les fichiers assembleur créés à la main.

    --error-execstack
    --no-error-execstack
    Si l'éditeur de liens doit générer un message d'avertissement concernant une pile exécutable, l'option --error-execstack transformera cet avertissement en erreur. Remarque : cette option ne modifie pas l'état de génération d'avertissements execstack de l'éditeur de liens. Utilisez --warn-execstack ou --warn-execstack-objects pour définir un état d'avertissement spécifique.

    L'option --no-error-execstack rétablira le comportement par défaut de génération de messages d'avertissement.

    --warn-multiple-gp
    Avertir si plusieurs valeurs de pointeur global sont nécessaires dans le fichier de sortie. Ceci n'est pertinent que pour certains processeurs, comme l'Alpha. Spécifiquement, certains processeurs placent les constantes de grande valeur dans une section spéciale. Un registre spécial (le pointeur global) pointe vers le milieu de cette section, de sorte que les constantes peuvent être chargées efficacement via un mode d'adressage relatif à un registre de base. Comme le décalage en mode relatif au registre de base est fixe et relativement petit (par exemple, 16 bits), cela limite la taille maximale du pool de constantes. Ainsi, dans les grands programmes, il est souvent nécessaire d'utiliser plusieurs valeurs de pointeur global afin de pouvoir adresser toutes les constantes possibles. Cette option provoque un avertissement chaque fois que ce cas se produit.
    --warn-once
    N'émettre un avertissement qu'une seule fois pour chaque symbole non défini, au lieu d'une fois par module qui y fait référence.
    --warn-rwx-segments
    --no-warn-rwx-segments
    Avertir si l'éditeur de liens crée un segment chargeable, de taille non nulle, qui a les trois indicateurs d'autorisation lecture, écriture et exécution définis. Un tel segment représente une vulnérabilité de sécurité potentielle. De plus, des avertissements seront générés si un segment de stockage local à thread est créé avec l'indicateur d'autorisation d'exécution défini, indépendamment du fait qu'il ait ou non les indicateurs de lecture et/ou d'écriture définis.

    Ces avertissements sont activés par défaut. Ils peuvent être désactivés via l'option --no-warn-rwx-segments et réactivés via l'option --warn-rwx-segments.

    --error-rwx-segments
    --no-error-rwx-segments
    Si l'éditeur de liens doit générer un message d'avertissement concernant un segment exécutable et inscriptible, ou un segment TLS exécutable, alors l'option --error-rwx-segments transformera cet avertissement en erreur à la place. L'option --no-error-rwx-segments rétablira le comportement par défaut de génération de messages d'avertissement.

    Remarque : l'option --error-rwx-segments n'active pas à elle seule les avertissements concernant ces segments. Ces avertissements sont soit activés par défaut, si l'éditeur de liens a été configuré ainsi, soit via l'option de ligne de commande --warn-rwx-segments.

    --warn-section-align
    Avertir si l'adresse d'une section de sortie est modifiée en raison de l'alignement. Typiquement, l'alignement sera défini par une section d'entrée. L'adresse ne sera modifiée que si elle n'est pas explicitement spécifiée ; c'est-à-dire, si la commande "SECTIONS" ne spécifie pas d'adresse de départ pour la section.
    --warn-textrel
    Avertir si l'éditeur de liens ajoute DT_TEXTREL à un exécutable indépendant de la position ou à un objet partagé.
    --warn-alternate-em
    Avertir si un objet possède un code machine ELF alternatif.
    --warn-unresolved-symbols
    Si l'éditeur de liens doit signaler un symbole non résolu (voir l'option --unresolved-symbols), il générera normalement une erreur. Cette option le fait générer un avertissement à la place.
    --error-unresolved-symbols
    Ceci rétablit le comportement par défaut de l'éditeur de liens consistant à générer des erreurs lorsqu'il signale des symboles non résolus.
    --whole-archive
    Pour chaque archive mentionnée sur la ligne de commande après l'option --whole-archive, inclure chaque fichier objet de l'archive dans la liaison, plutôt que de rechercher dans l'archive les fichiers objets requis. Ceci est normalement utilisé pour transformer un fichier archive en une bibliothèque partagée, forçant l'inclusion de chaque objet dans la bibliothèque partagée résultante. Cette option peut être utilisée plus d'une fois.

    Deux notes lors de l'utilisation de cette option avec gcc : Premièrement, gcc ne connaît pas cette option, vous devez donc utiliser -Wl,-whole-archive. Deuxièmement, n'oubliez pas d'utiliser -Wl,-no-whole-archive après votre liste d'archives, car gcc ajoutera sa propre liste d'archives à votre liaison et vous ne voudrez peut-être pas que cet indicateur affecte celles-ci également.

    --wrap=symbole
    Utiliser une fonction d'encapsulation (wrapper) pour symbole. Toute référence non définie à symbole sera résolue en "__wrap_symbole". Toute référence non définie à "__real_symbole" sera résolue en symbole.

    Ceci peut être utilisé pour fournir un wrapper pour une fonction système. La fonction wrapper doit être appelée "__wrap_symbole". Si elle souhaite appeler la fonction système, elle doit appeler "__real_symbole".

    Voici un exemple trivial :

    void *
__wrap_malloc (size_t c)
{
  printf ("malloc called with %zu\n", c);
  return __real_malloc (c);
}

    Si vous liez d'autres codes avec ce fichier en utilisant --wrap malloc, alors tous les appels à "malloc" appelleront la fonction "__wrap_malloc" à la place. L'appel à "__real_malloc" dans "__wrap_malloc" appellera la fonction "malloc" réelle.

    Vous pourriez également souhaiter fournir une fonction "__real_malloc", afin que les liaisons sans l'option --wrap réussissent. Si vous le faites, vous ne devez pas placer la définition de "__real_malloc" dans le même fichier que "__wrap_malloc" ; si vous le faites, l'assembleur peut résoudre l'appel avant que l'éditeur de liens n'ait la possibilité de le lier à "malloc".

    Seules les références indéfinies sont remplacées par l'éditeur de liens. Ainsi, les références internes à l'unité de traduction à symbol ne sont pas résolues en "__wrap_symbol". Dans l'exemple suivant, l'appel à "f" dans "g" n'est pas résolu en "__wrap_f".

    int
f (void)
{
  return 123;
}

int
g (void)
{
  return f();
}
    --eh-frame-hdr
    --no-eh-frame-hdr
    Demande (--eh-frame-hdr) ou supprime (--no-eh-frame-hdr) la création de la section ".eh_frame_hdr" et de l'en-tête de segment ELF "PT_GNU_EH_FRAME".
    --no-ld-generated-unwind-info
    Demande la création d'informations de déroulement (unwind info) dans ".eh_frame" pour les sections de code générées par l'éditeur de liens, comme le PLT. Cette option est activée par défaut si les informations de déroulement générées par l'éditeur de liens sont prises en charge. Cette option contrôle également la génération d'informations de trace de pile ".sframe" pour les sections de code générées par l'éditeur de liens, comme le PLT.
    --enable-new-dtags
    --disable-new-dtags
    Cet éditeur de liens peut créer les nouvelles balises dynamiques en ELF. Mais les anciens systèmes ELF pourraient ne pas les comprendre. Si vous spécifiez --enable-new-dtags, les nouvelles balises dynamiques seront créées au besoin et les anciennes balises dynamiques seront omises. Si vous spécifiez --disable-new-dtags, aucune nouvelle balise dynamique ne sera créée. Par défaut, les nouvelles balises dynamiques ne sont pas créées. Notez que ces options ne sont disponibles que pour les systèmes ELF.
    --hash-size=nombre
    Définit la taille par défaut des tables de hachage de l'éditeur de liens à un nombre premier proche de nombre. Augmenter cette valeur peut réduire le temps nécessaire à l'éditeur de liens pour effectuer ses tâches, au détriment d'une augmentation de la mémoire requise par l'éditeur de liens. Inversement, réduire cette valeur peut réduire les besoins en mémoire au détriment de la vitesse.
    --hash-style=style
    Définit le type des tables de hachage de l'éditeur de liens. style peut être "sysv" pour la section ELF classique ".hash", "gnu" pour la nouvelle section GNU ".gnu.hash" ou "both" pour les tables de hachage ELF classique ".hash" et nouvelle GNU ".gnu.hash". Le défaut dépend de la manière dont l'éditeur de liens a été configuré, mais pour la plupart des systèmes basés sur Linux, ce sera "both".
    --compress-debug-sections=none
    --compress-debug-sections=zlib
    --compress-debug-sections=zlib-gnu
    --compress-debug-sections=zlib-gabi
    --compress-debug-sections=zstd
    Sur les plates-formes ELF, ces options contrôlent la compression des sections de débogage DWARF à l'aide de zlib.

    --compress-debug-sections=none ne compresse pas les sections de débogage DWARF. --compress-debug-sections=zlib-gnu compresse les sections de débogage DWARF et les renomme pour commencer par .zdebug au lieu de .debug. --compress-debug-sections=zlib-gabi compresse également les sections de débogage DWARF, mais au lieu de les renommer, il définit l'indicateur SHF_COMPRESSED dans les en-têtes des sections.

    L'option --compress-debug-sections=zlib est un alias pour --compress-debug-sections=zlib-gabi.

    --compress-debug-sections=zstd compresse les sections de débogage DWARF à l'aide de zstd.

    Notez que cette option remplace toute compression dans les sections de débogage d'entrée, donc si un binaire est lié avec --compress-debug-sections=none par exemple, alors toutes les sections de débogage compressées dans les fichiers d'entrée seront décompressées avant d'être copiées dans le binaire de sortie.

    Le comportement de compression par défaut varie en fonction de la cible concernée et des options de configuration utilisées pour construire la chaîne d'outils. Le comportement par défaut peut être déterminé en examinant la sortie de l'option --help de l'éditeur de liens.

    --reduce-memory-overheads
    Cette option réduit les besoins en mémoire à l'exécution de ld, au détriment de la vitesse de liaison. Elle a été introduite pour sélectionner l'ancien algorithme O(n^2) pour la génération du fichier de carte de liaison, plutôt que le nouvel algorithme O(n) qui utilise environ 40% de mémoire en plus pour le stockage des symboles.

    Un autre effet de ce commutateur est de définir la taille par défaut de la table de hachage à 1021, ce qui économise de la mémoire au prix d'un temps d'exécution plus long pour l'éditeur de liens. Cela n'est toutefois pas fait si le commutateur --hash-size a été utilisé.

    Le commutateur --reduce-memory-overheads peut également être utilisé pour activer d'autres compromis dans les futures versions de l'éditeur de liens.

    --max-cache-size=taille
    ld met normalement en cache les informations de relocalisation et les tables de symboles des fichiers d'entrée en mémoire avec une taille illimitée. Cette option définit la taille maximale du cache à taille.
    --build-id
    --build-id=style
    Demande la création d'une section de note ELF ".note.gnu.build-id" ou d'une section COFF ".buildid". Le contenu de la note est un identifiant unique de ce fichier lié. style peut être "uuid" pour utiliser 128 bits aléatoires, "sha1" pour utiliser un hachage SHA1 de 160 bits sur les parties normatives du contenu de sortie, "md5" pour utiliser un hachage MD5 de 128 bits sur les parties normatives du contenu de sortie, ou "0xchaînehex" pour utiliser une chaîne de bits choisie spécifiée sous forme d'un nombre pair de chiffres hexadécimaux (les caractères "-" et ":" entre les paires de chiffres sont ignorés). Si style est omis, "sha1" est utilisé.

    Les styles "md5" et "sha1" produisent un identifiant qui est toujours identique dans un fichier de sortie identique, mais qui sera unique parmi tous les fichiers de sortie non identiques. Il n'est pas destiné à être comparé comme une somme de contrôle du contenu du fichier. Un fichier lié peut être modifié ultérieurement par d'autres outils, mais la chaîne de bits de l'ID de construction identifiant le fichier lié d'origine ne change pas.

    Passer "none" pour style désactive le réglage des options "--build-id" antérieures sur la ligne de commande.

    --package-metadata=JSON
    Demande la création d'une section de note ELF ".note.package". Le contenu de la note est au format JSON, conformément à la spécification des métadonnées de paquet. Pour plus d'informations, voir : https://systemd.io/ELF_PACKAGE_METADATA/ Si l'argument JSON est absent/vide, cela désactivera la création de la note de métadonnées, si une avait été activée par une occurrence antérieure de l'option --package-metadata. Si l'éditeur de liens a été construit avec libjansson, la chaîne JSON sera validée.

    L'éditeur de liens PE i386 prend en charge l'option -shared, qui fait que la sortie est une bibliothèque liée dynamiquement (DLL) au lieu d'un exécutable normal. Vous devez nommer la sortie "*.dll" lorsque vous utilisez cette option. De plus, l'éditeur de liens prend entièrement en charge les fichiers "*.def" standard, qui peuvent être spécifiés sur la ligne de commande de l'éditeur de liens comme un fichier objet (en fait, ils doivent précéder les archives dont ils exportent des symboles, afin de s'assurer qu'ils sont liés, tout comme un fichier objet normal).

    En plus des options communes à toutes les cibles, l'éditeur de liens PE i386 prend en charge des options de ligne de commande supplémentaires qui sont spécifiques à la cible PE i386. Les options qui prennent des valeurs peuvent être séparées de leurs valeurs par un espace ou un signe égal.

    --add-stdcall-alias

    --disable-long-section-names
    Les variantes PE du format d'objet COFF ajoutent une extension qui permet d'utiliser des noms de section plus longs que huit caractères, la limite normale pour COFF. Par défaut, ces noms sont activés
    autorisé uniquement dans les fichiers objets, car les images exécutables entièrement liées ne transportent pas la table de chaînes COFF requise pour prendre en charge les noms plus longs. En tant qu'extension GNU, il est possible de permettre leur utilisation dans les images exécutables également, ou de les interdire (probablement inutilement !) dans les fichiers objets, en utilisant ces deux options. Les images exécutables générées avec ces noms de section longs sont légèrement non standard, transportant une table de chaînes, et peuvent générer une sortie confuse lors de l'examen avec des outils non-GNU compatibles PE, tels que les visualiseurs et les dumpers de fichiers. Cependant, GDB s'appuie sur l'utilisation des noms de section longs PE pour trouver des sections d'informations de débogage Dwarf-2 dans une image exécutable à l'exécution, et donc si aucune des options n'est spécifiée sur la ligne de commande, ld activera les noms de section longs, remplaçant le comportement par défaut et techniquement correct lorsqu'il détecte la présence d'informations de débogage lors de la liaison d'une image exécutable et que les symboles ne sont pas supprimés. [Cette option est valide pour tous les ports PE ciblés du lieur]

    --disable-stdcall-fixup
    Si la liaison trouve un symbole qu'elle ne peut pas résoudre, elle tentera de faire une « liaison floue » en recherchant un autre symbole défini qui diffère uniquement par le format du nom du symbole (cdecl vs stdcall) et résoudra ce symbole en le liant à la correspondance. Par exemple, le symbole non défini "_foo" pourrait être lié à la fonction "_foo@12", ou le symbole non défini "_bar@16" pourrait être lié à la fonction "_bar". Lorsque le lieur fait cela, il affiche un avertissement, car il aurait normalement dû échouer à la liaison, mais parfois les bibliothèques d'importation générées à partir de dll tierces peuvent nécessiter cette fonctionnalité pour être utilisables. Si vous spécifiez --enable-stdcall-fixup, cette fonctionnalité est entièrement activée et les avertissements ne sont pas imprimés. Si vous spécifiez --disable-stdcall-fixup, cette fonctionnalité est désactivée et de telles divergences sont considérées comme des erreurs. [Cette option est spécifique au port PE i386 ciblé du lieur]

    Note : L'utilisation de l'extension 'auto-import' rendra la section de texte du fichier image inscriptible. Ceci n'est pas conforme à la spécification du format PE-COFF publiée par Microsoft.

    Note - l'utilisation de l'extension 'auto-import' placera également les données en lecture seule qui seraient normalement placées dans la section .rdata dans la section .data à la place. Ceci est afin de contourner un problème avec les consts qui est décrit ici : http://www.cygwin.com/ml/cygwin/2004-09/msg01101.html

    L'utilisation de 'auto-import' fonctionnera généralement 'sans problème' -- mais parfois vous verrez ce message :

    "variable '<var>' ne peut pas être auto-importée. Veuillez lire la documentation de "--enable-auto-import" de ld pour plus de détails."

    Ce message survient lorsque certaines (sous-)expressions accèdent à une adresse finalement donnée par la somme de deux constantes (les tables d'importation Win32 n'en autorisent qu'une). Les instances où cela peut se produire incluent les accès aux champs membres de variables struct importées d'une DLL, ainsi que l'utilisation d'un index constant dans une variable tableau importée d'une DLL. Toute variable multi-mots (tableaux, structures, long long, etc.) peut déclencher cette condition d'erreur. Cependant, quel que soit le type de données exact de la variable exportée fautive, ld la détectera toujours, émettra un avertissement et s'arrêtera.

    Il existe plusieurs façons de résoudre cette difficulté, quel que soit le type de données de la variable exportée :

    Une façon est d'utiliser l'interrupteur --enable-runtime-pseudo-reloc. Cela laisse la tâche d'ajuster les références dans votre code client à l'environnement d'exécution, donc cette méthode ne fonctionne que lorsque l'environnement d'exécution prend en charge cette fonctionnalité.

    Une deuxième solution consiste à forcer l'une des 'constantes' à être une variable -- c'est-à-dire, inconnue et non optimisable au moment de la compilation. Pour les tableaux, il y a deux possibilités : a) faire de l'indexé (l'adresse du tableau) une variable, ou b) faire de l'index 'constant' une variable. Ainsi :

    extern type extern_array[];
extern_array[1] -->
   { volatile type *t=extern_array; t[1] }

    ou

    extern type extern_array[];
extern_array[1] -->
   { volatile int t=1; extern_array[t] }

    Pour les structures (et la plupart des autres types de données multi-mots), la seule option est de faire de la structure elle-même (ou du long long, ou du ...) une variable :

    extern struct s extern_struct;
extern_struct.field -->
   { volatile struct s *t=&extern_struct; t->field }

    ou

    extern long long extern_ll;
extern_ll -->
  { volatile long long * local_ll=&extern_ll; *local_ll }

    Une troisième méthode pour traiter cette difficulté est d'abandonner 'auto-import' pour le symbole fautif et de le marquer avec "__declspec(dllimport)". Cependant, en pratique, cela nécessite d'utiliser des #define au moment de la compilation pour indiquer si vous construisez une DLL, si vous construisez du code client qui se liera à la DLL, ou simplement si vous construisez/liez une bibliothèque statique. En choisissant parmi les différentes méthodes de résolution du problème 'adresse directe avec décalage constant', vous devriez considérer l'usage typique en monde réel :

    Original :

    --foo.h
extern int arr[];
--foo.c
#include "foo.h"
void main(int argc, char **argv){
  printf("%d\n",arr[1]);
}

    Solution 1 :

    --foo.h
extern int arr[];
--foo.c
#include "foo.h"
void main(int argc, char **argv){
  /* Ce contournement est pour win32 et cygwin ; ne pas "optimiser" */
  volatile int *parr = arr;
  printf("%d\n",parr[1]);
}

    Solution 2 :

    --foo.h
/* Note : auto-export est supposé (pas de __declspec(dllexport)) */
#if (defined(_WIN32) || defined(__CYGWIN__)) && \
  !(defined(FOO_BUILD_DLL) || defined(FOO_STATIC))
#define FOO_IMPORT __declspec(dllimport)
#else
#define FOO_IMPORT
#endif
extern FOO_IMPORT int arr[];
--foo.c
#include "foo.h"
void main(int argc, char **argv){
  printf("%d\n",arr[1]);
}

    Une quatrième façon d'éviter ce problème est de recoder votre bibliothèque pour utiliser une interface fonctionnelle plutôt qu'une interface de données pour les variables fautives (par exemple, des fonctions d'accès set_foo() et get_foo()).

    Pour la cible pdp11-aout, trois variantes du format de sortie peuvent être produites, sélectionnées par les options suivantes. La variante par défaut pour pdp11-aout est l'option --omagic, tandis que pour d'autres cibles, --nmagic est la valeur par défaut. L'option --imagic est définie uniquement pour la cible pdp11-aout, tandis que les autres sont décrites ici telles qu'elles s'appliquent à la cible pdp11-aout.

    -N
    --omagic
    Marque la sortie comme "OMAGIC" (0407) dans l'en-tête a.out pour indiquer que le segment texte ne doit pas être protégé en écriture et partagé. Puisque les segments texte et données sont à la fois lisibles et inscriptibles, le segment données est alloué immédiatement après le segment texte. C'est le plus ancien format pour les programmes exécutables PDP11 et c'est la valeur par défaut pour ld sur les systèmes Unix PDP11 depuis le début jusqu'à 2.11BSD.
    -n
    --nmagic
    Marque la sortie comme "NMAGIC" (0410) dans l'en-tête a.out pour indiquer que lorsque le fichier de sortie est exécuté, la partie texte sera en lecture seule et partageable entre tous les processus exécutant le même fichier. Cela implique de déplacer les zones de données jusqu'à la première frontière de page de 8 Ko possible suivant la fin du texte. Cette option crée un format d'exécutable pur.
    -z
    --imagic
    Marque la sortie comme "IMAGIC" (0411) dans l'en-tête a.out pour indiquer que lors de l'exécution du fichier, les zones de texte et de données du programme seront chargées dans des espaces d'adressage séparés en utilisant la fonctionnalité de séparation des instructions et des données de l'unité de gestion de mémoire dans les modèles plus grands du PDP11. Cela double l'espace d'adressage disponible pour le programme. Le segment texte est à nouveau pur, protégé en écriture et partageable. La seule différence dans le format de sortie entre cette option et les autres, outre le nombre magique, est que les segments texte et données commencent tous deux à l'emplacement 0. L'option -z sélectionnait ce format dans 2.11BSD. Cette option crée un format d'exécutable séparé.
    --no-omagic
    Équivalent à --nmagic pour pdp11-aout.

    ENVIRONNEMENT

    Vous pouvez modifier le comportement de ld avec les variables d'environnement "GNUTARGET", "LDEMULATION" et "COLLECT_NO_DEMANGLE".

    "GNUTARGET" détermine le format objet du fichier d'entrée si vous n'utilisez pas -b (ou son synonyme --format). Sa valeur doit être l'un des noms BFD pour un format d'entrée. S'il n'y a pas de "GNUTARGET" dans l'environnement, ld utilise le format naturel de la cible. Si "GNUTARGET" est défini sur "default", alors BFD tente de découvrir le format d'entrée en examinant les fichiers binaires d'entrée ; cette méthode réussit souvent, mais il existe des ambiguïtés potentielles, car il n'existe aucun moyen de garantir que le nombre magique utilisé pour spécifier les formats de fichiers objet soit unique. Cependant, la procédure de configuration de BFD sur chaque système place le format conventionnel pour ce système en premier dans la liste de recherche, de sorte que les ambiguïtés sont résolues en faveur de la convention.

    "LDEMULATION" détermine l'émulation par défaut si vous n'utilisez pas l'option -m. L'émulation peut affecter divers aspects du comportement du lieur, en particulier le script de lieur par défaut. Vous pouvez lister les émulations disponibles avec les options --verbose ou -V. Si l'option -m n'est pas utilisée et que la variable d'environnement "LDEMULATION" n'est pas définie, l'émulation par défaut dépend de la manière dont le lieur a été configuré.

    Normalement, le lieur annulera le "mangling" des symboles par défaut. Cependant, si "COLLECT_NO_DEMANGLE" est défini dans l'environnement, alors il sera par défaut de ne pas démangler les symboles. Cette variable d'environnement est utilisée de manière similaire par le programme "gcc", l'enveloppe de l'éditeur de liens. Le comportement par défaut peut être remplacé par les options --demangle et --no-demangle.
