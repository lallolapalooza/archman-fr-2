GDBSERVER(1) Outils de développement GNU GDBSERVER(1)

NOM

gdbserver - Serveur distant pour le débogueur GNU

SYNTAXE

gdbserver comm prog [args...]

gdbserver --attach comm pid

gdbserver --multi comm

DESCRIPTION

gdbserver est un programme qui permet d'exécuter GDB sur une machine différente de celle qui exécute le programme en cours de débogage.

Utilisation (côté serveur (cible)) :

Tout d'abord, vous devez avoir une copie du programme que vous souhaitez déboguer sur le système cible. Le programme peut être dépouillé pour économiser de l'espace si nécessaire, car gdbserver ne se soucie pas des symboles. Toute la gestion des symboles est prise en charge par GDB exécuté sur le système hôte.

Pour utiliser le serveur, connectez-vous au système cible et exécutez le programme gdbserver. Vous devez lui indiquer (a) comment communiquer avec GDB, (b) le nom de votre programme et (c) ses arguments. La syntaxe générale est :

cible> gdbserver <comm> <programme> [<args> ...]

Par exemple, en utilisant un port série, vous pourriez dire :

cible> gdbserver /dev/com1 emacs foo.txt

Cela indique à gdbserver de déboguer emacs avec l'argument foo.txt, et de communiquer avec GDB via /dev/com1. gdbserver attend maintenant patiemment que GDB hôte communique avec lui.

Pour utiliser une connexion TCP, vous pourriez dire :

cible> gdbserver hôte:2345 emacs foo.txt

Cela dit à peu près la même chose que le dernier exemple, sauf que nous allons communiquer avec le GDB "hôte" via TCP. L'argument "hôte:2345" signifie que nous attendons une connexion TCP de "hôte" vers le port TCP local 2345. (Actuellement, la partie "hôte" est ignorée.) Vous pouvez choisir n'importe quel numéro de port qui ne conflit pas avec d'autres ports TCP existants sur le système cible. Ce même numéro de port doit être utilisé dans la commande "target remote" de GDB hôte, qui sera décrite prochainement. Notez que si vous choisissez un numéro de port qui entre en conflit avec un autre service, gdbserver affichera un message d'erreur et se terminera.

gdbserver peut également s'attacher à des programmes en cours d'exécution. Ceci est réalisé via l'argument --attach. La syntaxe est :

cible> gdbserver --attach <comm> <pid>

pid est l'identifiant de processus d'un processus en cours d'exécution. Il n'est pas nécessaire de pointer gdbserver vers un binaire pour le processus en cours d'exécution.

Pour démarrer "gdbserver" sans fournir de commande initiale à exécuter ni d'identifiant de processus à attacher, utilisez l'option de ligne de commande --multi. Dans ce cas, vous devrez vous connecter en utilisant "target extended-remote" pour démarrer le programme que vous souhaitez déboguer.

cible> gdbserver --multi <comm>

Utilisation (côté hôte) :

Vous avez besoin d'une copie non dépouillée du programme cible sur votre système hôte, car GDB doit examiner ses tables de symboles, etc. Démarrez GDB comme vous le feriez normalement, avec le programme cible comme premier argument. (Vous devrez peut-être utiliser l'option --baud si la ligne série fonctionne à un autre débit que 9600 bauds.) C'est "gdb PROGRAMME_CIBLE", ou "gdb --baud DÉBIT PROGRAMME_CIBLE". Ensuite, la seule nouvelle commande que vous devez connaître est "target remote" (ou "target extended-remote"). Son argument est soit un nom de périphérique (généralement un périphérique série, comme /dev/ttyb), soit un descripteur "HÔTE:PORT". Par exemple :

(gdb) target remote /dev/ttyb

communique avec le serveur via la ligne série /dev/ttyb, et :

(gdb) target remote cible:2345

communique via une connexion TCP au port 2345 sur l'hôte `cible', où vous avez précédemment lancé gdbserver avec le même numéro de port. Notez que pour les connexions TCP, vous devez lancer gdbserver avant d'utiliser la commande `target remote', sinon vous pourriez obtenir une erreur du type `Connection refused'.

gdbserver peut également déboguer plusieurs inférieurs simultanément, décrits dans le manuel GDB dans le nœud "Connexions et programmes des inférieurs" -- commande shell "info -f gdb -n 'Connexions et programmes des inférieurs'". Dans ce cas, utilisez la variante de commande GDB "extended-remote" :

(gdb) target extended-remote cible:2345

L'option --multi de gdbserver peut ou peut ne pas être utilisée dans ce cas.

OPTIONS

Il existe trois modes différents pour invoquer gdbserver :

  • Déboguer un programme spécifique spécifié par son nom de programme : 
    gdbserver <comm> <prog> [<args>...]

    Le paramètre comm spécifie comment le serveur doit communiquer avec GDB ; il s'agit soit d'un nom de périphérique (pour utiliser une ligne série), d'un numéro de port TCP (":1234"), soit de "-" ou "stdio" pour utiliser l'entrée/sortie standard de "gdbserver". Spécifiez le nom du programme à déboguer dans prog. Les arguments restants seront passés tels quels au programme. Lorsque le programme se termine, GDB fermera la connexion et "gdbserver" se terminera.

  • Déboguer un programme spécifique en spécifiant l'identifiant de processus d'un programme en cours d'exécution : 
    gdbserver --attach <comm> <pid>

    Le paramètre comm est tel que décrit ci-dessus. Fournissez l'identifiant de processus d'un programme en cours d'exécution dans pid ; GDB fera le reste. Comme pour le mode précédent, lorsque le processus pid se termine, GDB fermera la connexion et "gdbserver" se terminera.

  • Mode multi-processus -- déboguer plus d'un programme/processus : 
    gdbserver --multi <comm>

    Dans ce mode, GDB peut indiquer à gdbserver quelle(s) commande(s) exécuter. Contrairement aux 2 autres modes, GDB ne fermera pas la connexion lorsqu'un processus débogué se termine, vous pouvez donc déboguer plusieurs processus dans la même session.

Dans chacun des modes, vous pouvez spécifier ces options :

--help
Liste toutes les options avec de brèves explications.
--version
Cette option fait en sorte que gdbserver affiche son numéro de version et se quitte.
--attach
gdbserver s'attachera à un programme en cours d'exécution. La syntaxe est : 
cible> gdbserver --attach <comm> <pid>

pid est l'identifiant de processus d'un processus en cours d'exécution. Il n'est pas nécessaire de pointer gdbserver vers un binaire pour le processus en cours d'exécution.

--multi
Pour démarrer "gdbserver" sans fournir de commande initiale à exécuter ni d'identifiant de processus à attacher, utilisez cette option de ligne de commande. Vous pouvez ensuite vous connecter en utilisant "target extended-remote" et démarrer le programme que vous souhaitez déboguer. La syntaxe est : 
cible> gdbserver --multi <comm>
--debug[=option1,option2,...]
Demande à "gdbserver" d'afficher des informations de statut supplémentaires sur le processus de débogage. Cette option est destinée au développement de "gdbserver" et aux rapports de bugs aux développeurs.

Chaque option est le nom d'un composant pour lequel le débogage doit être activé. La liste des options possibles est all, threads, event-loop, remote. L'option spéciale all active tous les composants. La liste des options est traitée de gauche à droite, et une option peut être préfixée du caractère "-" pour désactiver la sortie pour ce composant, vous pourriez donc écrire :

cible> gdbserver --debug=all,-event-loop

pour activer la sortie de débogage pour tous les composants sauf event-loop. Si aucune option n'est passée à --debug, cela est traité comme équivalent à --debug=thre

gdbserver(1) — Arch Linux

NOM

gdbserver — Débogage à distance avec le débogueur GNU

SYNTAXE

gdbserver [options] [listen-address] program [program-args ...]

gdbserver --attach listen-address pid

DESCRIPTION

gdbserver est un programme qui permet le débogage à distance d'un programme cible. Il fonctionne sur la machine cible et communique avec un client GDB sur une autre machine via un socket TCP. Il peut soit lancer un programme, soit s'attacher à un processus existant.

L'adresse d'écoute spécifie l'interface réseau et le port sur lesquels gdbserver écoutera les connexions entrantes de GDB. Elle peut être au format port, hostname:port, ou ip-address:port. Si seul le port est spécifié, gdbserver écoutera sur toutes les interfaces réseau.

OPTIONS

--multi-thread
Indique à gdbserver de gérer les threads de manière à ce que chaque nouvelle connexion GDB puisse déboguer indépendamment. Cela permet à plusieurs sessions GDB de se connecter simultanément et de contrôler différents threads du programme cible. Ce comportement peut changer dans les futures versions de "gdbserver".
--debug-file=nom-fichier
Demande à "gdbserver" d'envoyer toutes les sorties de débogage dans le nom-fichier donné. Cette option est destinée au développement de "gdbserver" et aux rapports de bugs aux développeurs.
--debug-format=option1[,option2,...]
Demande à "gdbserver" d'inclure des informations supplémentaires dans chaque ligne de sortie de débogage.
--wrapper
Spécifie un wrapper pour lancer les programmes à déboguer. L'option doit être suivie du nom du wrapper, puis de tous les arguments de ligne de commande à passer au wrapper, puis de "--" indiquant la fin des arguments du wrapper.
--once
Par défaut, gdbserver maintient le port TCP d'écoute ouvert, de sorte que des connexions supplémentaires soient possibles. Cependant, si vous lancez "gdbserver" avec l'option --once, il cessera d'écouter toute tentative de connexion supplémentaire après s'être connecté à la première session GDB.

VOIR AUSSI

La documentation complète de GDB est maintenue sous forme de manuel Texinfo. Si les programmes "info" et "gdb" ainsi que la documentation Texinfo de GDB sont correctement installés sur votre site, la commande

info gdb

devrait vous donner accès au manuel complet.
