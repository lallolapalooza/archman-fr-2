LD(1) Outils de développement GNU LD(1)

NOM

ld - L'éditeur de liens GNU

SYNTAXE

ld [options] fichier-objet ...

DESCRIPTION

ld combine un certain nombre de fichiers objets et d'archives, relocalise leurs données et résout les références de symboles. C'est généralement la dernière étape de la compilation d'un programme que d'appeler ld.

ld accepte des fichiers de commande d'éditeur de liens écrits dans un sur-ensemble de la syntaxe du langage de commande de l'éditeur de liens d'AT&T, afin de fournir un contrôle explicite et total sur le processus de liaison.

Cette page de manuel ne décrit pas le langage de commande ; consultez l'entrée ld dans "info" pour des détails complets sur le langage de commande et sur d'autres aspects de l'éditeur de liens GNU.

Cette version de ld utilise les bibliothèques BFD à usage général pour opérer sur les fichiers objets. Cela permet à ld de lire, combiner et écrire des fichiers objets dans de nombreux formats différents, par exemple COFF ou "a.out". Différents formats peuvent être liés ensemble pour produire n'importe quel type de fichier objet disponible.

Outre sa flexibilité, l'éditeur de liens GNU est plus utile que les autres éditeurs de liens en fournissant des informations de diagnostic. De nombreux éditeurs de liens abandonnent l'exécution immédiatement en cas d'erreur ; lorsque cela est possible, ld continue son exécution, vous permettant d'identifier d'autres erreurs (ou, dans certains cas, d'obtenir un fichier de sortie malgré l'erreur).

L'éditeur de liens GNU ld est conçu pour couvrir une large gamme de situations, et pour être aussi compatible que possible avec les autres éditeurs de liens. En conséquence, vous avez de nombreux choix pour contrôler son comportement.

OPTIONS

L'éditeur de liens prend en charge une pléthore d'options en ligne de commande, mais en pratique, peu d'entre elles sont utilisées dans un contexte particulier. Par exemple, une utilisation fréquente de ld est de lier des fichiers objets Unix standard sur un système Unix standard et supporté. Sur un tel système, pour lier un fichier "hello.o" :

ld -o <sortie> /lib/crt0.o hello.o -lc

Cela indique à ld de produire un fichier nommé sortie comme résultat de la liaison du fichier "/lib/crt0.o" avec "hello.o" et la bibliothèque "libc.a", qui proviendra des répertoires de recherche standard. (Voir la discussion de l'option -l ci-dessous.)

Certaines options de la ligne de commande de ld peuvent être spécifiées à tout moment. Cependant, les options qui font référence à des fichiers, comme -l ou -T, entraînent la lecture du fichier au moment où l'option apparaît dans la ligne de commande, par rapport aux fichiers objets et aux autres options de fichier. Répéter des options qui ne se rapportent pas à des fichiers avec un argument différent n'aura soit aucun effet supplémentaire, soit remplacera les occurrences précédentes (celles plus à gauche dans la ligne de commande) de cette option. Les options qui peuvent être spécifiées plusieurs fois de manière significative sont notées dans les descriptions ci-dessous.

Les arguments qui ne sont pas des options sont des fichiers objets ou des archives qui doivent être liés ensemble. Ils peuvent suivre, précéder ou être mélangés avec les options de la ligne de commande, à l'exception qu'un argument de fichier objet ne peut pas être placé entre une option et son argument.

Habituellement, l'éditeur de liens est appelé avec au moins un fichier objet, mais vous pouvez spécifier d'autres formes de fichiers d'entrée binaires en utilisant -l, -R, et le langage de script de commande. Si *aucun* fichier d'entrée binaire n'est spécifié, l'éditeur de liens ne produit aucune sortie et affiche le message No input files (Aucun fichier d'entrée).

Si l'éditeur de liens ne peut pas reconnaître le format d'un fichier objet, il supposera qu'il s'agit d'un script d'éditeur de liens. Un script spécifié de cette manière complète le script d'éditeur de liens principal utilisé pour la liaison (soit le script d'éditeur de liens par défaut, soit celui spécifié à l'aide de -T). Cette fonctionnalité permet à l'éditeur de liens de se lier à un fichier qui semble être un objet ou une archive, mais qui définit en fait simplement certaines valeurs de symboles, ou utilise "INPUT" ou "GROUP" pour charger d'autres objets. La spécification d'un script de cette manière complète simplement le script d'éditeur de liens, avec les commandes supplémentaires placées après le script principal ; utilisez l'option -T pour remplacer complètement le script d'éditeur de liens par défaut, mais notez l'effet de la commande "INSERT".

Pour les options dont les noms sont une seule lettre, les arguments des options doivent soit suivre la lettre d'option sans espace blanc, soit être donnés comme arguments séparés immédiatement après l'option qui les requiert.

Pour les options dont les noms sont composés de plusieurs lettres, un seul tiret ou deux peuvent précéder le nom de l'option ; par exemple, -trace-symbol et --trace-symbol sont équivalents. Notez qu'il y a une exception à cette règle. Les options à plusieurs lettres commençant par un 'o' minuscule ne peuvent être précédées que de deux tirets. Ceci afin de réduire la confusion avec l'option -o. Ainsi, par exemple, -omagic définit le nom du fichier de sortie à magic, tandis que --omagic définit le drapeau NMAGIC sur la sortie.

Les arguments des options à plusieurs lettres doivent soit être séparés du nom de l'option par un signe égal, soit être donnés comme arguments séparés immédiatement après l'option qui les requiert. Par exemple, --trace-symbol foo et --trace-symbol=foo sont équivalents. Les abréviations uniques des noms des options à plusieurs lettres sont acceptées.

Notez que si l'éditeur de liens est appelé indirectement, via un pilote de compilateur (par exemple, gcc), alors toutes les options de ligne de commande de l'éditeur de liens doivent être préfixées par -Wl, (ou ce qui est approprié pour le pilote de compilateur particulier) comme ceci :

gcc -Wl,--start-group foo.o bar.o -Wl,--end-group

Ceci est important, car sinon le programme pilote de compilateur peut ignorer silencieusement les options de l'éditeur de liens, entraînant une liaison incorrecte. De la confusion peut également survenir lors du passage d'options nécessitant des valeurs via un pilote, car l'utilisation d'un espace entre l'option et l'argument agit comme un séparateur, et amène le pilote à transmettre uniquement l'option à l'éditeur de liens et l'argument au compilateur. Dans ce cas, il est plus simple d'utiliser les formes jointes des options à une seule lettre et à plusieurs lettres, comme :

gcc foo.o bar.o -Wl,-eENTRY -Wl,-Map=a.map

Voici une table des commutateurs génériques de ligne de commande acceptés par l'éditeur de liens GNU :

@fichier
Lit les options de la ligne de commande depuis fichier. Les options lues sont insérées à la place de l'option @fichier originale. Si fichier n'existe pas, ou ne peut pas être lu, alors l'option sera traitée littéralement, et ne sera pas supprimée.

Les options dans fichier sont séparées par des espaces blancs. Un caractère d'espace blanc peut être inclus dans une option en entourant l'option entière de guillemets simples ou doubles. N'importe quel caractère (y compris une barre oblique inverse) peut être inclus en précédant le caractère à inclure avec une barre oblique inverse. Le fichier peut lui-même contenir des options @fichier supplémentaires ; toutes ces options seront traitées récursivement.

-a mot-clé
Cette option est supportée pour la compatibilité HP/UX. L'argument mot-clé doit être l'une des chaînes archive, shared, ou default. -aarchive est fonctionnellement équivalent à -Bstatic, et les deux autres mots-clés sont fonctionnellement équivalents à -Bdynamic. Cette option peut être utilisée un nombre quelconque de fois.
--audit BIB_AUDIT
Ajoute BIB_AUDIT à l'entrée "DT_AUDIT" de la section dynamique. BIB_AUDIT n'est pas vérifié pour l'existence, ni n'utilisera le DT_SONAME spécifié dans la bibliothèque. S'il est spécifié plusieurs fois, "DT_AUDIT" contiendra une liste d'interfaces d'audit séparées par des deux-points à utiliser. Si l'éditeur de liens trouve un objet avec une entrée d'audit lors de la recherche de bibliothèques partagées, il ajoutera une entrée correspondante "DT_DEPAUDIT" dans le fichier de sortie. Cette option n'est significative que sur les plates-formes ELF supportant l'interface rtld-audit.
-b format-entrée
--format=format-entrée
ld peut être configuré pour supporter plus d'un type de fichier objet. Si votre ld est configuré de cette manière, vous pouvez utiliser l'option -b pour spécifier le format binaire des fichiers objets qui suivent cette option dans la ligne de commande. Vous pourriez vouloir utiliser cette option si vous liez des fichiers avec un format binaire inhabituel. Vous pouvez également utiliser -b pour changer de format explicitement (lors de la liaison de fichiers objets de formats différents), en incluant -b format-entrée avant chaque groupe de fichiers objets d'un format particulier.

Le format par défaut est pris de la variable d'environnement "GNUTARGET".

-c fichier-commande-MRI
--mri-script=fichier-commande-MRI
Pour la compatibilité avec les éditeurs de liens produits par MRI, ld accepte des fichiers scripts écrits dans un langage de commande alternatif et restreint, décrit dans la section Fichiers de scripts compatibles MRI de la documentation GNU ld. Introduisez les fichiers de scripts MRI avec l'option -c ; utilisez l'option -T pour exécuter des scripts d'éditeur de liens écrits dans le langage de script ld à usage général. Si fichier-commande-MRI n'existe pas, ld le recherche dans les répertoires spécifiés par les options -L.
-d
-dc
-dp
Ces trois options sont équivalentes ; plusieurs formes sont supportées pour la compatibilité avec d'autres éditeurs de liens. Elles allouent de l'espace aux symboles communs même si un fichier de sortie déplaçable est spécifié (avec -r). La commande script "FORCE_COMMON_ALLOCATION" a le même effet.
--depaudit BIBLIOAUDIT
-P BIBLIOAUDIT
Ajoute BIBLIOAUDIT à l'entrée "DT_DEPAUDIT" de la section dynamique. BIBLIOAUDIT n'est pas vérifié pour son existence, et n'utilisera pas le DT_SONAME spécifié dans la bibliothèque. Si spécifié plusieurs fois, "DT_DEPAUDIT" contiendra une liste d'interfaces d'audit séparées par des deux-points à utiliser. Cette option n'est pertinente que sur les plateformes ELF supportant l'interface rtld-audit. L'option -P est fournie pour la compatibilité Solaris.
--enable-linker-version
Active la directive de script d'éditeur de liens "LINKER_VERSION", décrite dans Données de section de sortie. Si cette directive est utilisée dans un script d'éditeur de liens et que cette option a été activée, une chaîne contenant la version de l'éditeur de liens sera insérée au point courant.

Notez que l'emplacement de cette option sur la ligne de commande de l'éditeur de liens est significatif. Elle n'affectera que les scripts d'éditeur de liens qui la suivent sur la ligne de commande, ou ceux qui sont intégrés à l'éditeur de liens.

--disable-linker-version
Désactive la directive de script d'éditeur de liens "LINKER_VERSION", de sorte qu'elle n'insère pas de chaîne de version. C'est le comportement par défaut.
--enable-non-contiguous-regions
Cette option évite de générer une erreur si une section d'entrée ne rentre pas dans une section de sortie correspondante. L'éditeur de liens essaie d'allouer la section d'entrée aux sections de sortie correspondantes subséquentes, et ne génère une erreur que si aucune section de sortie n'est assez grande. Ceci est utile lorsque plusieurs régions de mémoire non contiguës sont disponibles et que la section d'entrée ne requiert pas une région particulière. L'ordre dans lequel les sections d'entrée sont évaluées ne change pas, par exemple : 
MEMORY {
  MEM1 (rwx) : ORIGIN = 0x1000, LENGTH = 0x14
  MEM2 (rwx) : ORIGIN = 0x1000, LENGTH = 0x40
  MEM3 (rwx) : ORIGIN = 0x2000, LENGTH = 0x40
}
SECTIONS {
  mem1 : { *(.data.*); } > MEM1
  mem2 : { *(.data.*); } > MEM2
  mem3 : { *(.data.*); } > MEM3
}

avec les sections d'entrée :
.data.1: taille 8
.data.2: taille 0x10
.data.3: taille 4

résulte en .data.1 affecté à mem1, et .data.2 et .data.3
affectés à mem2, même si .data.3 rentrerait dans mem3.

Cette option est incompatible avec les instructions INSERT car elle modifie la manière dont les sections d'entrée sont mappées aux sections de sortie.

--enable-non-contiguous-regions-warnings
Cette option active les avertissements lorsque "--enable-non-contiguous-regions" permet des correspondances potentiellement inattendues dans le mappage des sections, ce qui pourrait conduire à rejeter silencieusement une section au lieu d'échouer parce qu'elle ne rentre dans aucune région de sortie.
-e point-entrée
--entry=point-entrée
Utilise point-entrée comme symbole explicite pour commencer l'exécution de votre programme, plutôt que le point d'entrée par défaut. S'il n'y a pas de symbole nommé point-entrée, l'éditeur de liens essaiera d'interpréter point-entrée comme un nombre, et l'utilisera comme adresse d'entrée (le nombre sera interprété en base 10 ; vous pouvez utiliser un préfixe 0x pour la base 16, ou un préfixe 0 pour la base 8).
--exclude-libs lib,lib,...
Spécifie une liste de bibliothèques archives dont les symboles ne doivent pas être exportés automatiquement. Les noms de bibliothèques peuvent être séparés par des virgules ou des deux-points. Spécifier "--exclude-libs ALL" exclut les symboles de toutes les bibliothèques archives de l'exportation automatique. Cette option n'est disponible que pour le port ciblé i386 PE de l'éditeur de liens et pour les ports ciblés ELF. Pour i386 PE, les symboles explicitement listés dans un fichier .def sont toujours exportés, quelle que soit cette option. Pour les ports ciblés ELF, les symboles affectés par cette option seront traités comme cachés.
--exclude-modules-for-implib module,module,...
Spécifie une liste de fichiers objets ou de membres d'archives, à partir desquels les symboles ne doivent pas être exportés automatiquement, mais qui doivent être copiés intégralement dans la bibliothèque d'importation générée pendant la liaison. Les noms de modules peuvent être séparés par des virgules ou des deux-points, et doivent correspondre exactement aux noms de fichiers utilisés par ld pour ouvrir les fichiers ; pour les membres d'archives, c'est simplement le nom du membre, mais pour les fichiers objets, le nom listé doit inclure et correspondre précisément à tout chemin utilisé pour spécifier le fichier d'entrée sur la ligne de commande de l'éditeur de liens. Cette option n'est disponible que pour le port ciblé i386 PE de l'éditeur de liens. Les symboles explicitement listés dans un fichier .def sont toujours exportés, quelle que soit cette option.
-E
--export-dynamic
--no-export-dynamic
Lors de la création d'un exécutable lié dynamiquement, l'utilisation de l'option -E ou de l'option --export-dynamic fait que l'éditeur de liens ajoute tous les symboles à la table des symboles dynamiques. La table des symboles dynamiques est l'ensemble des symboles qui sont visibles depuis les objets dynamiques à l'exécution.

Si vous n'utilisez aucune de ces options (ou utilisez l'option --no-export-dynamic pour restaurer le comportement par défaut), la table des symboles dynamiques contiendra normalement uniquement les symboles qui sont référencés par un objet dynamique mentionné dans la liaison.

Si vous utilisez "dlopen" pour charger un objet dynamique qui doit faire référence aux symboles définis par le programme, plutôt qu'à un autre objet dynamique, vous devrez probablement utiliser cette option lors de la liaison du programme lui-même.

Vous pouvez également utiliser la liste dynamique pour contrôler quels symboles doivent être ajoutés à la table des symboles dynamiques si le format de sortie le supporte. Voir la description de --dynamic-list.

Notez que cette option est spécifique aux ports ciblés ELF. Les cibles PE supportent une fonction similaire pour exporter tous les symboles depuis une DLL ou un EXE ; voir la description de --export-all-symbols ci-dessous.

--export-dynamic-symbol=glob
Lors de la création d'un exécutable lié dynamiquement, les symboles correspondant à glob seront ajoutés à la table des symboles dynamiques. Lors de la création d'une bibliothèque partagée, les références aux symboles correspondant à glob ne seront pas liées aux définitions au sein de la bibliothèque partagée. Cette option est sans effet lors de la création d'une bibliothèque partagée et si -Bsymbolic ou --dynamic-list ne sont pas spécifiés. Cette option n'est pertinente que sur les plateformes ELF supportant les bibliothèques partagées.
--export-dynamic-symbol-list=fichier
Spécifie un --export-dynamic-symbol pour chaque modèle dans le fichier. Le format du fichier est le même que celui du nœud de version sans portée et nom de nœud. Voir VERSION pour plus d'informations.
-EB
Lie des objets big-endian. Ceci affecte le format de sortie par défaut.
-EL
Lie des objets little-endian. Ceci affecte le format de sortie par défaut.
-f nom
--auxiliary=nom
Lors de la création d'un objet partagé ELF, définit le champ interne DT_AUXILIARY sur le nom spécifié. Ceci indique à l'éditeur de liens dynamique que la table des symboles de l'objet partagé doit être utilisée comme un filtre auxiliaire sur la table des symboles de l'objet partagé nom.

Si vous liez plus tard un programme contre cet objet filtre, alors, lors de l'exécution du programme, l'éditeur de liens dynamique verra le champ DT_AUXILIARY. Si l'éditeur de liens dynamique résout des symboles à partir de l'objet filtre, il vérifiera d'abord s'il existe une définition dans l'objet partagé nom. S'il y en a une, elle sera utilisée à la place de la définition dans l'objet filtre. L'objet partagé nom n'a pas besoin d'exister. Ainsi, l'objet partagé nom peut être utilisé pour fournir une implémentation alternative de certaines fonctions, peut-être pour le débogage ou pour des performances spécifiques à la machine.

Cette option peut être spécifiée plusieurs fois. Les entrées DT_AUXILIARY seront créées dans l'ordre où elles apparaissent sur la ligne de commande.

-F nom
--filter=nom
Lors de la création d'un objet partagé ELF, définit le champ interne DT_FILTER au nom spécifié. Cela indique à l'éditeur de liens dynamique que la table des symboles de l'objet partagé en cours de création doit être utilisée comme filtre sur la table des symboles de l'objet partagé nom.

Si vous liez ultérieurement un programme à cet objet filtre, alors, lorsque vous exécutez le programme, l'éditeur de liens dynamique verra le champ DT_FILTER. L'éditeur de liens dynamique résoudra les symboles selon la table des symboles de l'objet filtre comme d'habitude, mais il se liera en réalité aux définitions trouvées dans l'objet partagé nom. Ainsi, l'objet filtre peut être utilisé pour sélectionner un sous-ensemble des symboles fournis par l'objet nom.

Certains éditeurs de liens plus anciens utilisaient l'option -F tout au long d'une chaîne d'outils de compilation pour spécifier le format du fichier objet pour les fichiers objets d'entrée et de sortie. L'éditeur de liens GNU utilise d'autres mécanismes à cette fin : les options -b, --format, --oformat, la commande "TARGET" dans les scripts d'éditeur de liens, et la variable d'environnement "GNUTARGET". L'éditeur de liens GNU ignorera l'option -F lorsqu'il ne créera pas d'objet partagé ELF.

-fini=nom
Lors de la création d'un exécutable ELF ou d'un objet partagé ELF, appelle NOM lors du déchargement de l'exécutable ou de l'objet partagé, en définissant DT_FINI à l'adresse de la fonction. Par défaut, l'éditeur de liens utilise "_fini" comme fonction à appeler.
-g
Ignoré. Fourni pour la compatibilité avec d'autres outils.
-G valeur
--gpsize=valeur
Définit la taille maximale des objets à optimiser en utilisant le registre GP à taille. Ceci n'est significatif que pour les formats de fichiers objets tels que MIPS ELF qui prennent en charge le placement d'objets grands et petits dans différentes sections. Ceci est ignoré pour les autres formats de fichiers objets.
-h nom
-soname=nom
Lors de la création d'un objet partagé ELF, définit le champ interne DT_SONAME au nom spécifié. Lorsqu'un exécutable est lié à un objet partagé qui possède un champ DT_SONAME, alors lors de l'exécution de l'exécutable, l'éditeur de liens dynamique tentera de charger l'objet partagé spécifié par le champ DT_SONAME plutôt que d'utiliser le nom de fichier donné à l'éditeur de liens.
-i
Effectue une liaison incrémentielle (identique à l'option -r).
-init=nom
Lors de la création d'un exécutable ELF ou d'un objet partagé ELF, appelle NOM lors du chargement de l'exécutable ou de l'objet partagé, en définissant DT_INIT à l'adresse de la fonction. Par défaut, l'éditeur de liens utilise "_init" comme fonction à appeler.
-l spécification_nom
--library=spécification_nom
Ajoute l'archive ou le fichier objet spécifié par spécification_nom à la liste des fichiers à lier. Cette option peut être utilisée un nombre quelconque de fois. Si spécification_nom est de la forme :nom_fichier, ld recherchera dans le chemin de la bibliothèque un fichier nommé nom_fichier, sinon il recherchera dans le chemin de la bibliothèque un fichier nommé libspécification_nom.a.

Sur les systèmes qui prennent en charge les bibliothèques partagées, ld peut également rechercher des fichiers autres que libspécification_nom.a. Plus précisément, sur les systèmes ELF et SunOS, ld recherchera dans un répertoire une bibliothèque nommée libspécification_nom.so avant de rechercher celle nommée libspécification_nom.a. (Par convention, une extension ".so" indique une bibliothèque partagée.) Notez que ce comportement ne s'applique pas à :nom_fichier, qui spécifie toujours un fichier nommé nom_fichier.

L'éditeur de liens ne recherchera dans une archive qu'une seule fois, à l'emplacement où elle est spécifiée dans la ligne de commande. Si l'archive définit un symbole qui était indéfini dans un objet apparu avant l'archive sur la ligne de commande, l'éditeur de liens inclura les fichiers appropriés de l'archive. Cependant, un symbole indéfini dans un objet apparaissant plus tard sur la ligne de commande ne fera pas que l'éditeur de liens recherchera à nouveau l'archive.

Voir l'option -( pour un moyen de forcer l'éditeur de liens à rechercher les archives plusieurs fois.

Vous pouvez lister la même archive plusieurs fois sur la ligne de commande.

Ce type de recherche d'archives est standard pour les éditeurs de liens Unix. Cependant, si vous utilisez ld sur AIX, notez qu'il est différent du comportement de l'éditeur de liens AIX.

-L répertoire_recherche
--library-path=répertoire_recherche
Ajoute le chemin répertoire_recherche à la liste des chemins que ld recherchera pour les bibliothèques d'archives et les scripts de contrôle de ld. Vous pouvez utiliser cette option un nombre quelconque de fois. Les répertoires sont recherchés dans l'ordre où ils sont spécifiés dans la ligne de commande. Les répertoires spécifiés dans la ligne de commande sont recherchés avant les répertoires par défaut. Toutes les options -L s'appliquent à toutes les options -l, quel que soit l'ordre dans lequel les options apparaissent. Les options -L n'affectent pas la façon dont ld recherche un script d'éditeur de liens, sauf si l'option -T est spécifiée.

Si répertoire_recherche commence par "=" ou $SYSROOT, alors ce préfixe sera remplacé par le préfixe sysroot, contrôlé par l'option --sysroot, ou spécifié lors de la configuration de l'éditeur de liens.

L'ensemble par défaut des chemins recherchés (sans être spécifié avec -L) dépend du mode d'émulation utilisé par ld, et dans certains cas également de la façon dont il a été configuré.

Les chemins peuvent également être spécifiés dans un script de liaison avec la commande "SEARCH_DIR". Les répertoires spécifiés de cette manière sont recherchés au moment où le script de liaison apparaît dans la ligne de commande.

-m émulation
Émule l'éditeur de liens émulation. Vous pouvez lister les émulations disponibles avec les options --verbose ou -V.

Si l'option -m n'est pas utilisée, l'émulation est prise de la variable d'environnement "LDEMULATION", si elle est définie.

Sinon, l'émulation par défaut dépend de la façon dont l'éditeur de liens a été configuré.

--remap-inputs=modèle=nom_fichier
--remap-inputs-file=fichier
Ces options permettent de modifier les noms des fichiers d'entrée avant que l'éditeur de liens ne tente de les ouvrir. L'option --remap-inputs=foo.o=bar.o fera en sorte que toute tentative de chargement d'un fichier nommé foo.o essaie plutôt de charger un fichier nommé bar.o. Les modèles génériques sont autorisés dans le premier nom de fichier, donc --remap-inputs=foo*.o=bar.o renommera tout fichier d'entrée correspondant à foo*.o en bar.o.

Une forme alternative de l'option --remap-inputs-file=nom_fichier permet de lire les remappages à partir d'un fichier. Chaque ligne du fichier peut contenir un seul remappage. Les lignes vides sont ignorées. Tout ce qui va d'un caractère dièse (#) à la fin d'une ligne est considéré comme un commentaire et est également ignoré. Le modèle de mappage peut être séparé du nom de fichier par des espaces blancs ou un caractère égal (=).

Les options peuvent être spécifiées plusieurs fois. Leurs contenus s'accumulent. Les remappages seront traités dans l'ordre où ils apparaissent dans la ligne de commande, et s'ils proviennent d'un fichier, dans l'ordre où ils apparaissent dans le fichier. Si une correspondance est trouvée, aucune vérification supplémentaire pour ce nom de fichier ne sera effectuée.

Si le nom de fichier de remplacement est /dev/null ou simplement NUL, alors le remappage provoquera l'ignorance du fichier d'entrée. Cela peut être un moyen pratique d'expérimenter en supprimant des fichiers d'entrée d'un environnement de build complexe.

Notez que cette option dépend de la position et n'affecte que les noms de fichiers qui la suivent dans la ligne de commande. Ainsi :

ld foo.o --remap-inputs=foo.o=bar.o

N'aura aucun effet, tandis que :

ld --remap-inputs=foo.o=bar.o foo.o

Renommera le fichier d'entrée foo.o en bar.o.

Notez que ces options affectent également les fichiers référencés par les instructions INPUT dans les scripts d'éditeur de liens. Mais comme les scripts d'éditeur de liens sont traités après que toute la ligne de commande a été lue, la position des options de remappage dans la ligne de commande n'est pas significative.

Si l'option verbose est activée, tous les mappages correspondants seront signalés, bien que là encore l'option verbose doive être activée dans la ligne de commande avant que les noms de fichiers remappés n'apparaissent.

Si les options -Map ou --print-map sont activées, la liste de remappage sera incluse dans la sortie de la carte.

-M
--print-map
Imprime une carte de liaison sur la sortie standard. Une carte de liaison fournit des informations sur la liaison, notamment :
  • Où les fichiers objets sont mappés en mémoire.
  • Comment les symboles communs sont alloués.
  • Tous les membres d'archive inclus dans la liaison, avec une mention du symbole qui a causé l'inclusion du membre d'archive.
  • Les valeurs attribuées aux symboles.

    Notez que les symboles dont les valeurs sont calculées par une expression qui implique une référence à une valeur précédente du même symbole peuvent ne pas avoir le résultat correct affiché dans la carte de liaison. Ceci est dû au fait que l'éditeur de liens ignore les résultats intermédiaires et ne conserve que la valeur finale d'une expression. Dans de telles circonstances, l'éditeur de liens affichera la valeur finale entourée de crochets. Ainsi, par exemple, un script d'éditeur de liens contenant :

    foo = 1
foo = foo * 4
foo = foo + 8

    Produira la sortie suivante dans la carte de liaison si l'option -M est utilisée :

    0x00000001                foo = 0x1
[0x0000000c]                foo = (foo * 0x4)
[0x0000000c]                foo = (foo + 0x8)

Pour d'autres binaires cependant, l'option -Ur est similaire à -r mais résout également les références aux constructeurs et destructeurs.

    Pour les systèmes où -r et -Ur se comportent différemment, il ne fonctionne pas d'utiliser -Ur sur des fichiers qui ont eux-mêmes été liés avec -Ur ; une fois que la table des constructeurs a été construite, elle ne peut plus être complétée. Utilisez -Ur uniquement pour le dernier lien partiel, et -r pour les autres.

    MODE peut avoir l'une des valeurs suivantes :

    "place"
    Les sections orphelines sont placées dans une section de sortie appropriée suivant la stratégie décrite dans Sections orphelines. L'option --unique affecte également la manière dont les sections sont placées.
    "discard"
    Toutes les sections orphelines sont rejetées, en les plaçant dans la section /DISCARD/.
    "warn"
    Le lieur placera la section orpheline comme pour "place" et émettra également un avertissement.
    "error"
    Le lieur se terminera avec une erreur si une section orpheline est trouvée.

    La valeur par défaut si --orphan-handling n'est pas spécifié est "place".

Une section orpheline est une section qui n'est pas spécifiquement mentionnée dans un script de lien. Vous pouvez utiliser cette option plusieurs fois sur la ligne de commande ; elle empêche la fusion normale des sections d'entrée portant le même nom, outrepassant les affectations de sections de sortie dans un script de lien.

    -( archives -)
    --start-group archives --end-group
    Les archives doivent être une liste de fichiers archive. Ils peuvent être des noms de fichiers explicites ou des options -l.

    Les archives spécifiées sont recherchées de manière répétée jusqu'à ce qu'aucun nouveau symbole non résolu ne soit créé. Normalement, une archive n'est recherchée qu'une seule fois dans l'ordre où elle est spécifiée sur la ligne de commande. Si un symbole dans cette archive est nécessaire pour résoudre un symbole non résolu référencé par un objet dans une archive qui apparaît plus tard sur la ligne de commande, l'éditeur de liens ne serait pas en mesure de résoudre cette référence. En regroupant les archives, elles seront toutes recherchées de manière répétée jusqu'à ce que toutes les références possibles soient résolues.

    L'utilisation de cette option a un coût de performance significatif. Il est préférable de l'utiliser uniquement lorsqu'il existe des références circulaires inévitables entre deux archives ou plus.

    --accept-unknown-input-arch
    --no-accept-unknown-input-arch
    Indique à l'éditeur de liens d'accepter les fichiers d'entrée dont l'architecture ne peut pas être reconnue. L'hypothèse est que l'utilisateur sait ce qu'il fait et souhaite délibérément lier ces fichiers d'entrée inconnus. C'était le comportement par défaut de l'éditeur de liens, avant la version 2.14. Le comportement par défaut à partir de la version 2.14 est de rejeter de tels fichiers d'entrée, et donc l'option --accept-unknown-input-arch a été ajoutée pour restaurer l'ancien comportement.
    --as-needed
    --no-as-needed
    Cette option affecte les balises DT_NEEDED ELF pour les bibliothèques dynamiques mentionnées sur la ligne de commande après l'option --as-needed. Normalement, l'éditeur de liens ajoutera une balise DT_NEEDED pour chaque bibliothèque dynamique mentionnée sur la ligne de commande, que la bibliothèque soit réellement nécessaire ou non. --as-needed fait qu'une balise DT_NEEDED n'est émise que pour une bibliothèque qui, à ce stade de l'édition des liens, satisfait une référence de symbole non faible non résolu d'un fichier objet régulier ou, si la bibliothèque n'est pas trouvée dans les listes DT_NEEDED d'autres bibliothèques nécessaires, une référence de symbole non faible non résolu d'une autre bibliothèque dynamique nécessaire. Les fichiers objets ou les bibliothèques apparaissant sur la ligne de commande après la bibliothèque en question n'affectent pas si la bibliothèque est considérée comme nécessaire. Ceci est similaire aux règles d'extraction des fichiers objets des archives. --no-as-needed restaure le comportement par défaut.

    Remarque : sur les systèmes basés sur Linux, l'option --as-needed affecte également le comportement des options --rpath et --rpath-link. Voir la description de --rpath-link pour plus de détails.

    Spécifie le nom d'un fichier de liste dynamique à l'éditeur de liens. Ceci est typiquement utilisé lors de la création de bibliothèques partagées pour spécifier une liste de symboles globaux dont les références ne doivent pas être liées à la définition au sein de la bibliothèque partagée, ou lors de la création d'exécutables liés dynamiquement pour spécifier une liste de symboles qui doivent être ajoutés à la table des symboles dans l'exécutable. Cette option n'est significative que sur les plateformes ELF qui prennent en charge les bibliothèques partagées.

    Le format de la liste dynamique est le même que celui du nœud de version sans le scope et le nom du nœud. Voir VERSION pour plus d'informations.

    --dynamic-list-data
    Inclure tous les symboles de données globaux dans la liste dynamique.
    --dynamic-list-cpp-new
    Fournit la liste dynamique intégrée pour les opérateurs new et delete de C++. Il est principalement utile pour construire la bibliothèque partagée libstdc++.
    --dynamic-list-cpp-typeinfo
    Fournit la liste dynamique intégrée pour l'identification des types d'exécution de C++.
    --check-sections
    --no-check-sections
    Demande à l'éditeur de liens de *ne pas* vérifier les adresses des sections après qu'elles aient été attribuées pour voir s'il y a des chevauchements. Normalement, l'éditeur de liens effectuera cette vérification, et s'il trouve des chevauchements, il produira des messages d'erreur appropriés. L'éditeur de liens connaît les sections dans les superpositions et en tient compte. Le comportement par défaut peut être restauré en utilisant le commutateur de ligne de commande --check-sections. Le chevauchement de sections n'est généralement pas vérifié pour les liens re கொள்ளுங்கள்ables. Vous pouvez forcer la vérification dans ce cas en utilisant l'option --check-sections.
    --copy-dt-needed-entries
    --no-copy-dt-needed-entries
    Cette option affecte le traitement des bibliothèques dynamiques référencées par les tags DT_NEEDED *à l'intérieur* des bibliothèques dynamiques ELF mentionnées sur la ligne de commande. Normalement, l'éditeur de liens n'ajoutera pas de tag DT_NEEDED au binaire de sortie pour chaque bibliothèque mentionnée dans un tag DT_NEEDED d'une bibliothèque dynamique d'entrée. Cependant, avec --copy-dt-needed-entries spécifié sur la ligne de commande, les entrées DT_NEEDED des bibliothèques dynamiques qui le suivent seront ajoutées. Le comportement par défaut peut être restauré avec --no-copy-dt-needed-entries.

    Cette option a également un effet sur la résolution des symboles dans les bibliothèques dynamiques. Avec --copy-dt-needed-entries, les bibliothèques dynamiques mentionnées sur la ligne de commande seront recherchées récursivement, en suivant leurs tags DT_NEEDED vers d'autres bibliothèques, afin de résoudre les symboles requis par le binaire de sortie. Avec le réglage par défaut, cependant, la recherche des bibliothèques dynamiques qui le suivent s'arrêtera à la bibliothèque dynamique elle-même. Aucun lien DT_NEEDED ne sera traversé pour résoudre les symboles.

    --cref
    Produire une table de références croisées. Si un fichier de carte de l'éditeur de liens est généré, la table de références croisées est imprimée dans le fichier de carte. Sinon, elle est imprimée sur la sortie standard.

    Le format de la table est intentionnellement simple, de sorte qu'il puisse être facilement traité par un script si nécessaire. Les symboles sont imprimés, triés par nom. Pour chaque symbole, une liste de noms de fichiers est donnée. Si le symbole est défini, le premier fichier listé est l'emplacement de la définition. Si le symbole est défini comme une valeur commune, alors les fichiers où cela se produit apparaissent ensuite. Enfin, les fichiers qui référencent le symbole sont listés.

    --ctf-variables
    --no-ctf-variables
    Le format d'informations de débogage CTF prend en charge une section qui encode les noms et les types des variables trouvées dans le programme qui n'apparaissent dans aucune table de symboles. Ces variables ne peuvent clairement pas être recherchées par adresse par les débogueurs conventionnels, donc l'espace utilisé pour leurs types et noms est généralement gaspillé : les types sont généralement petits mais les noms ne le sont souvent pas. --ctf-variables provoque la génération d'une telle section. Le comportement par défaut peut être restauré avec --no-ctf-variables.
    --ctf-share-types=méthode
    Ajuste la méthode utilisée pour partager les types entre les unités de traduction en CTF.
    share-unconflicted
    Place tous les types qui n'ont pas de définitions ambiguës dans le dictionnaire partagé, où les débogueurs peuvent y accéder facilement, même s'ils n'apparaissent que dans une seule unité de traduction. C'est le comportement par défaut.
    share-duplicated
    Place uniquement les types qui apparaissent dans plusieurs unités de traduction dans le dictionnaire partagé : les types avec une seule définition vont dans des dictionnaires par unité de traduction. Les types avec des définitions ambiguës dans plusieurs unités de traduction vont toujours dans des dictionnaires par unité de traduction. Cela tend à rendre le CTF plus volumineux, mais peut réduire la quantité de CTF dans le dictionnaire partagé. Pour de très grands projets, cela peut accélérer l'ouverture du CTF et économiser de la mémoire dans le consommateur de CTF à l'exécution.
    --no-define-common
    Cette option inhibe l'attribution d'adresses aux symboles communs. La commande de script "INHIBIT_COMMON_ALLOCATION" a le même effet.

    L'option --no-define-common permet de découpler la décision d'attribuer des adresses aux symboles communs du choix du type de fichier de sortie ; sinon, un type de sortie non re கொள்ளுங்கள்able force l'attribution d'adresses aux symboles communs. L'utilisation de --no-define-common permet aux symboles communs référencés depuis une bibliothèque partagée d'être attribués à des adresses uniquement dans le programme principal. Cela élimine l'espace dupliqué inutilisé dans la bibliothèque partagée, et évite également toute confusion possible sur la résolution vers le mauvais doublon lorsqu'il existe de nombreux modules dynamiques avec des chemins de recherche spécialisés pour la résolution des symboles à l'exécution.

    --force-group-allocation
    Cette option fait en sorte que l'éditeur de liens place les membres de groupes de sections comme des sections d'entrée normales, et supprime les groupes de sections. C'est le comportement par défaut pour un lien final, mais cette option peut être utilisée pour changer le comportement d'un lien re கொள்ளுங்கள்able (-r). La commande de script "FORCE_GROUP_ALLOCATION" a le même effet.
    --defsym=symbole=expression
    Crée un symbole global dans le fichier de sortie, contenant l'adresse absolue donnée par expression. Vous pouvez utiliser cette option autant de fois que nécessaire pour définir plusieurs symboles sur la ligne de commande. Une forme limitée d'arithmétique est prise en charge pour l'expression dans ce contexte : vous pouvez donner une constante hexadécimale ou le nom d'un symbole existant, ou utiliser "+" et "-" pour additionner ou soustraire des constantes hexadécimales ou des symboles. Si vous avez besoin d'expressions plus élaborées, envisagez d'utiliser le langage de commande de l'éditeur de liens à partir d'un script. Remarque : il ne doit pas y avoir d'espace blanc entre symbole, le signe égal ("="), et expression.

    L'éditeur de liens traite les arguments --defsym et -T dans l'ordre. Placer --defsym avant -T définira le symbole avant que le script de l'éditeur de liens de -T ne soit traité, tandis que placer --defsym après -T définira le symbole après que le script de l'éditeur de liens ait été traité. Cette différence a des conséquences pour les expressions dans le script de l'éditeur de liens qui utilisent les symboles --defsym ; l'ordre correct dépendra de ce que vous essayez d'accomplir.

    --demangle[=style]
    --no-demangle
    Ces options contrôlent si les noms de symboles doivent être désérialisés dans les messages d'erreur et autres sorties. Lorsque l'éditeur de liens est invité à désérialiser, il essaie de présenter les noms de symboles de manière lisible : il supprime les traits de soulignement initiaux s'ils sont utilisés par le format de fichier objet, et convertit les noms de symboles C++ "manglés" en noms lisibles par l'utilisateur. Différents compilateurs ont différents styles de "mangling". L'argument optionnel de style de désérialisation peut être utilisé pour choisir un style de désérialisation approprié pour votre compilateur. L'éditeur de liens désérialise par défaut, sauf si la variable d'environnement COLLECT_NO_DEMANGLE est définie. Ces options peuvent être utilisées pour remplacer le comportement par défaut.
    -Ifichier
    --dynamic-linker=fichier
    Définit le nom de l'éditeur de liens dynamique. Ceci n'est significatif que lors de la génération d'exécutables ELF liés dynamiquement. L'éditeur de liens dynamique par défaut est normalement correct ; n'utilisez pas ceci sauf si vous savez ce que vous faites.
    --no-dynamic-linker
    Lors de la production d'un fichier exécutable, omet la demande d'utilisation d'un éditeur de liens dynamique au moment du chargement. Ceci n'est significatif que pour les exécutables ELF qui contiennent des re கொள்ளுங்கள்s dynamiques, et nécessite généralement un code d'entrée capable de traiter ces re கொள்ளுங்கள்s.
    --embedded-relocs
    Cette option est similaire à l'option --emit-relocs, sauf que les re கொள்ளுங்கள்s sont stockées dans une section spécifique à la cible. Cette option n'est prise en charge que par les cibles BFIN, CR16 et M68K.
    --disable-multiple-abs-defs
    Ne pas autoriser plusieurs définitions avec des symboles inclus dans le nom de fichier invoqué par -R ou --just-symbols
    --
    --fatal-warnings
    --no-fatal-warnings
    Traiter tous les avertissements comme des erreurs. Le comportement par défaut peut être rétabli avec l'option --no-fatal-warnings.
    -w
    --no-warnings
    Ne pas afficher de messages d'avertissement ou d'erreur. Ceci remplace --fatal-warnings s'il a été activé. Cette option peut être utilisée lorsqu'il est connu que le binaire de sortie ne fonctionnera pas, mais qu'il est toujours nécessaire de le créer.
    --force-exe-suffix
    S'assurer qu'un fichier de sortie possède le suffixe .exe.

    Si un fichier de sortie entièrement lié et construit avec succès ne possède pas le suffixe ".exe" ou ".dll", cette option force l'éditeur de liens à copier le fichier de sortie vers un autre portant le même nom avec un suffixe ".exe". Cette option est utile lors de l'utilisation de makefiles Unix non modifiés sur un hôte Microsoft Windows, car certaines versions de Windows n'exécutent pas une image à moins qu'elle ne se termine par un suffixe ".exe".

    --gc-sections
    --no-gc-sections
    Activer la collecte des sections d'entrée inutilisées. Elle est ignorée sur les cibles qui ne prennent pas en charge cette option. Le comportement par défaut (ne pas effectuer cette collecte) peut être rétabli en spécifiant --no-gc-sections sur la ligne de commande. Notez que la collecte pour les cibles aux formats COFF et PE est prise en charge, mais l'implémentation est actuellement considérée comme expérimentale.

    --gc-sections décide quelles sections d'entrée sont utilisées en examinant les symboles et les relocations. La section contenant le symbole d'entrée et toutes les sections contenant des symboles indéfinis sur la ligne de commande seront conservées, ainsi que les sections contenant des symboles référencés par des objets dynamiques. Notez que lors de la construction de bibliothèques partagées, l'éditeur de liens doit supposer que tout symbole visible est référencé. Une fois cet ensemble initial de sections déterminé, l'éditeur de liens marque récursivement comme utilisées toutes les sections référencées par leurs relocations. Voir --entry, --undefined, et --gc-keep-exported.

    Cette option peut être définie lors d'un lien partiel (activé avec l'option -r). Dans ce cas, la racine des symboles conservés doit être explicitement spécifiée soit par l'une des options --entry, --undefined, ou --gc-keep-exported, soit par une commande "ENTRY" dans le script de l'éditeur de liens.

    En tant qu'extension GNU, les sections d'entrée ELF marquées avec le drapeau "SHF_GNU_RETAIN" ne seront pas collectées.

    --print-gc-sections
    --no-print-gc-sections
    Lister toutes les sections supprimées par la collecte. La liste est imprimée sur stderr. Cette option n'est efficace que si la collecte a été activée via l'option --gc-sections. Le comportement par défaut (ne pas lister les sections supprimées) peut être rétabli en spécifiant --no-print-gc-sections sur la ligne de commande.
    --gc-keep-exported
    Lorsque --gc-sections est activé, cette option empêche la collecte des sections d'entrée inutilisées qui contiennent des symboles globaux ayant une visibilité par défaut ou protégée. Cette option est destinée à être utilisée pour les exécutables où les sections non référencées seraient autrement collectées indépendamment de la visibilité externe des symboles contenus. Notez que cette option n'a aucun effet lors de l'édition de liens d'objets partagés, car c'est déjà le comportement par défaut. Cette option n'est prise en charge que pour les cibles au format ELF.
    --print-output-format
    Imprimer le nom du format de sortie par défaut (potentiellement influencé par d'autres options de ligne de commande). C'est la chaîne qui apparaîtrait dans une commande de script d'éditeur de liens "OUTPUT_FORMAT".
    --print-memory-usage
    Imprimer la taille utilisée, la taille totale et la taille utilisée des régions de mémoire créées avec la commande MEMORY. Ceci est utile sur les cibles embarquées pour avoir une vue rapide de la quantité de mémoire libre. Le format de sortie a un en-tête et une ligne par région. Il est à la fois lisible par l'homme et facilement analysable par des outils. Voici un exemple de sortie : 
    Région mémoire     Taille Utilisée  Taille Région  % Utilisé
             ROM:        256 Ko         1 Mo     25.00%
             RAM:          32 octets         2 Go      0.00%
    --help
    Imprimer un résumé des options de ligne de commande sur la sortie standard et quitter.
    --target-help
    Imprimer un résumé de toutes les options spécifiques à la cible sur la sortie standard et quitter.
    -Map=mapfile
    Imprimer une carte de lien dans le fichier mapfile. Voir la description de l'option -M, ci-dessus. Si mapfile est juste le caractère "-", la carte sera écrite sur stdout.

    La spécification d'un répertoire comme mapfile entraîne l'écriture de la carte de l'éditeur de liens dans un fichier à l'intérieur du répertoire. Normalement, le nom du fichier dans le répertoire est calculé à partir du nom de base du fichier de sortie avec ".map" ajouté. Si cependant le caractère spécial "%" est utilisé, il sera remplacé par le chemin complet du fichier de sortie. De plus, s'il y a des caractères après le symbole %, alors ".map" ne sera plus ajouté.

    -o foo.exe -Map=bar                  [Crée ./bar]
-o ../dir/foo.exe -Map=bar           [Crée ./bar]
-o foo.exe -Map=../dir               [Crée ../dir/foo.exe.map]
-o ../dir2/foo.exe -Map=../dir       [Crée ../dir/foo.exe.map]
-o foo.exe -Map=%                    [Crée ./foo.exe.map]
-o ../dir/foo.exe -Map=%             [Crée ../dir/foo.exe.map]
-o foo.exe -Map=%.bar                [Crée ./foo.exe.bar]
-o ../dir/foo.exe -Map=%.bar         [Crée ../dir/foo.exe.bar]
-o ../dir2/foo.exe -Map=../dir/%     [Crée ../dir/../dir2/foo.exe.map]
-o ../dir2/foo.exe -Map=../dir/%.bar [Crée ../dir/../dir2/foo.exe.bar]

    Il est interdit de spécifier plus d'un caractère "%".

    Si le fichier de carte existe déjà, il sera écrasé par cette opération.

    --no-keep-memory
    ld optimise normalement la vitesse par rapport à l'utilisation de la mémoire en mettant en cache les tables de symboles des fichiers d'entrée en mémoire. Cette option indique à ld d'optimiser plutôt l'utilisation de la mémoire, en relisant les tables de symboles si nécessaire. Cela peut être requis si ld manque d'espace mémoire lors de l'édition de liens d'un grand exécutable.
    --no-undefined
    -z defs
    Signaler les références de symboles non résolues provenant des fichiers objets réguliers. Ceci est fait même si l'éditeur de liens crée une bibliothèque partagée non symbolique. Le commutateur --[no-]allow-shlib-undefined contrôle le comportement de signalement des références non résolues trouvées dans les bibliothèques partagées en cours de liaison.

    Les effets de cette option peuvent être annulés en utilisant "-z undefs".

    --allow-multiple-definition
    -z muldefs
    Normalement, lorsqu'un symbole est défini plusieurs fois, l'éditeur de liens signale une erreur fatale. Ces options autorisent les définitions multiples et la première définition sera utilisée.
    --allow-shlib-undefined
    --no-allow-shlib-undefined
    Autorise ou refuse les symboles indéfinis dans les bibliothèques partagées. Ce commutateur est similaire à --no-undefined, sauf qu'il détermine le comportement lorsque les symboles indéfinis se trouvent dans une bibliothèque partagée plutôt que dans un fichier objet régulier. Il n'affecte pas la façon dont les symboles indéfinis dans les fichiers objets réguliers sont traités.

    Le comportement par défaut est de signaler des erreurs pour tout symbole indéfini référencé dans les bibliothèques partagées si l'éditeur de liens est utilisé pour créer un exécutable, mais de les autoriser si l'éditeur de liens est utilisé pour créer une bibliothèque partagée.

    Les raisons pour lesquelles les références de symboles indéfinis dans les bibliothèques partagées spécifiées au moment de la liaison sont autorisées sont les suivantes :

    • Une bibliothèque partagée spécifiée au moment de la liaison peut ne pas être la même que celle qui est disponible au moment du chargement, de sorte que le symbole peut en fait être résoluble au moment du chargement.
    • Il existe certains systèmes d'exploitation, par exemple BeOS et HPPA, où les symboles indéfinis dans les bibliothèques partagées sont normaux.

      Le noyau BeOS, par exemple, patch les bibliothèques partagées au moment du chargement pour sélectionner la fonction la plus appropriée pour l'architecture actuelle. Ceci est utilisé, par exemple, pour sélectionner dynamiquement une fonction memset appropriée.

    --error-handling-script=nom_script
    Si cette option est fournie, l'éditeur de liens invoquera nom_script chaque fois qu'une erreur sera rencontrée. Actuellement, seuls deux types d'erreurs sont pris en charge : symboles manquants et bibliothèques manquantes. Deux arguments seront passés au script : le mot-clé "undefined-symbol" ou `missing-lib" et le nom du symbole indéfini ou de la bibliothèque manquante. L'intention est que le script fournisse des suggestions à l'utilisateur quant à l'endroit où le symbole ou la bibliothèque pourrait être trouvé. Une fois le script terminé, le message d'erreur normal de l'éditeur de liens sera affiché.

    La disponibilité de cette option est contrôlée par un commutateur de configuration, elle peut donc ne pas être présente dans des implémentations spécifiques.

    --no-undefined-version
    Normalement, lorsqu'un symbole a une version indéfinie, l'éditeur de liens l'ignore. Cette option interdit les symboles avec une version indéfinie et une erreur fatale sera émise à la place.
    --default-symver
    Créer et utiliser une version de symbole par défaut (le nom de la bibliothèque partagée) pour les symboles exportés non versionnés.
    --unresolved-symbols=mode
    --default-imported-symver
    Crée et utilise une version de symbole par défaut (le soname) pour les symboles importés non versionnés.
    --no-warn-mismatch
    Normalement, ld générera une erreur si vous tentez de lier des fichiers d'entrée qui sont incompatibles pour une raison quelconque, peut-être parce qu'ils ont été compilés pour des processeurs différents ou pour des endiannesses différentes. Cette option indique à ld de permettre silencieusement de telles erreurs potentielles. Cette option ne doit être utilisée qu'avec prudence, dans les cas où vous avez pris des mesures spéciales qui garantissent que les erreurs du lieur sont inappropriées.
    --no-warn-search-mismatch
    Normalement, ld émettra un avertissement s'il trouve une bibliothèque incompatible lors d'une recherche de bibliothèque. Cette option supprime l'avertissement.
    --no-whole-archive
    Désactive l'effet de l'option --whole-archive pour les archives suivantes.
    --noinhibit-exec
    Conserve le fichier de sortie exécutable tant qu'il est utilisable. Normalement, le lieur ne produira pas de fichier de sortie s'il rencontre des erreurs pendant le processus de liaison ; il se terminera sans écrire de fichier de sortie lorsqu'il émettra une erreur quelconque.
    -nostdlib
    Ne recherche les répertoires de bibliothèques explicitement spécifiés sur la ligne de commande. Les répertoires de bibliothèques spécifiés dans les scripts de lieur (y compris les scripts de lieur spécifiés sur la ligne de commande) sont ignorés.
    --oformat=format-sortie
    ld peut être configuré pour prendre en charge plusieurs types de fichiers objets. Si votre ld est configuré de cette manière, vous pouvez utiliser l'option --oformat pour spécifier le format binaire du fichier objet de sortie. Même lorsque ld est configuré pour prendre en charge des formats d'objets alternatifs, vous n'avez généralement pas besoin de le spécifier, car ld devrait être configuré pour produire en tant que format de sortie par défaut le format le plus courant sur chaque machine. format-sortie est une chaîne de texte, le nom d'un format particulier pris en charge par les bibliothèques BFD. (Vous pouvez lister les formats binaires disponibles avec objdump -i.) La commande de script "OUTPUT_FORMAT" peut également spécifier le format de sortie, mais cette option la remplace.
    --out-implib fichier
    Crée une bibliothèque d'importation dans fichier correspondant à l'exécutable que le lieur génère (par exemple, une DLL ou un programme ELF). Cette bibliothèque d'importation (qui devrait s'appeler "*.dll.a" ou "*.a" pour les DLL) peut être utilisée pour lier des clients à l'exécutable généré ; ce comportement permet de sauter une étape séparée de création de bibliothèque d'importation (par exemple, "dlltool" pour les DLL). Cette option n'est disponible que pour les ports i386 PE et ELF du lieur.
    -pie
    --pic-executable
    Crée un exécutable indépendant de la position. Ceci n'est actuellement pris en charge que sur les plateformes ELF. Les exécutables indépendants de la position sont similaires aux bibliothèques partagées en ce sens qu'ils sont relocalisés par le lieur dynamique à l'adresse virtuelle que le système d'exploitation leur attribue (qui peut varier entre les invocations). Comme les exécutables liés dynamiquement normaux, ils peuvent être exécutés et les symboles définis dans l'exécutable ne peuvent pas être remplacés par des bibliothèques partagées.
    -no-pie
    Crée un exécutable dépendant de la position. C'est le comportement par défaut.
    -qmagic
    Cette option est ignorée pour la compatibilité Linux.
    -Qy
    Cette option est ignorée pour la compatibilité SVR4.
    --relax
    --no-relax
    Une option avec des effets dépendants de la machine. Cette option n'est prise en charge que sur quelques cibles.

    Sur certaines plateformes, l'option --relax effectue des optimisations globales spécifiques à la cible qui deviennent possibles lorsque le lieur résout l'adressage dans le programme, telles que la relaxation des modes d'adressage, la synthèse de nouvelles instructions, la sélection de versions plus courtes des instructions actuelles et la combinaison de valeurs constantes.

    Sur certaines plateformes, ces optimisations globales au moment de la liaison peuvent rendre le débogage symbolique de l'exécutable résultant impossible. C'est le cas connu pour la famille de processeurs Matsushita MN10200 et MN10300.

    Sur les plateformes où la fonctionnalité est prise en charge, l'option --no-relax la désactive.

    Sur les plateformes où la fonctionnalité n'est pas prise en charge, --relax et --no-relax sont acceptées, mais ignorées.

    --retain-symbols-file=nomfichier
    Conserve *uniquement* les symboles listés dans le fichier nomfichier, en rejetant tous les autres. nomfichier est simplement un fichier plat, avec un nom de symbole par ligne. Cette option est particulièrement utile dans les environnements (comme VxWorks) où une grande table de symboles globale est accumulée progressivement, afin de conserver la mémoire d'exécution.

    --retain-symbols-file ne rejette *pas* les symboles indéfinis, ni les symboles nécessaires aux relocalisations.

    Vous ne pouvez spécifier --retain-symbols-file qu'une seule fois sur la ligne de commande. Elle remplace -s et -S.

    -rpath=rep
    Ajoute un répertoire au chemin de recherche des bibliothèques d'exécution. Ceci est utilisé lors de la liaison d'un exécutable ELF avec des objets partagés. Tous les arguments -rpath sont concaténés et transmis au lieur d'exécution, qui les utilise pour localiser les objets partagés à l'exécution.

    L'option -rpath est également utilisée lors de la localisation des objets partagés requis par les objets partagés explicitement inclus dans la liaison ; voir la description de l'option -rpath-link. La recherche de -rpath de cette manière n'est prise en charge que par les lieurs natifs et les lieurs croisés qui ont été configurés avec l'option --with-sysroot.

    Si -rpath n'est pas utilisé lors de la liaison d'un exécutable ELF, le contenu de la variable d'environnement "LD_RUN_PATH" sera utilisé s'il est défini.

    L'option -rpath peut également être utilisée sur SunOS. Par défaut, sur SunOS, le lieur forme un chemin de recherche d'exécution à partir de toutes les options -L qui lui sont fournies. Si une option -rpath est utilisée, le chemin de recherche d'exécution sera formé exclusivement à l'aide des options -rpath, ignorant les options -L. Cela peut être utile lors de l'utilisation de gcc, qui ajoute de nombreuses options -L qui peuvent se trouver sur des systèmes de fichiers montés NFS.

    Pour la compatibilité avec d'autres lieurs ELF, si l'option -R est suivie d'un nom de répertoire, plutôt que d'un nom de fichier, elle est traitée comme l'option -rpath.

    -rpath-link=rep
    Lors de l'utilisation d'ELF ou de SunOS, une bibliothèque partagée peut en nécessiter une autre. Cela se produit lorsqu'une liaison "ld -shared" inclut une bibliothèque partagée comme l'un des fichiers d'entrée.

    Lorsque le lieur rencontre une telle dépendance lors d'une liaison non partagée et non déplaçable, il essaie automatiquement de localiser la bibliothèque partagée requise et de l'inclure dans la liaison, si elle n'est pas incluse explicitement. Dans un tel cas, l'option -rpath-link spécifie le premier ensemble de répertoires à rechercher. L'option -rpath-link peut spécifier une séquence de noms de répertoires soit en spécifiant une liste de noms séparés par des deux-points, soit en apparaissant plusieurs fois.

    Les jetons $ORIGIN et $LIB peuvent apparaître dans ces répertoires de recherche. Ils seront remplacés par le chemin complet du répertoire contenant le programme ou l'objet partagé dans le cas de $ORIGIN et soit lib - pour les binaires 32 bits - soit lib64 - pour les binaires 64 bits - dans le cas de $LIB.

    La forme alternative de ces jetons - ${ORIGIN} et ${LIB} - peut également être utilisée. Le jeton $PLATFORM n'est pas pris en charge.

    Cette option doit être utilisée avec prudence car elle remplace le chemin de recherche qui a pu être codé en dur dans une bibliothèque partagée. Dans un tel cas, il est possible d'utiliser involontairement un chemin de recherche différent de celui que le lieur d'exécution utiliserait.

    Le lieur utilise les chemins de recherche suivants pour localiser les bibliothèques partagées requises :

    1.
    Tous les répertoires spécifiés par les options -rpath-link.
    2.
    Tous les répertoires spécifiés par les options -rpath. La différence entre -rpath et -rpath-link est que les répertoires spécifiés par les options -rpath sont inclus dans l'exécutable et utilisés à l'exécution, tandis que l'option -rpath-link n'est effective qu'au moment de la liaison. La recherche de -rpath de cette manière n'est prise en charge que par les lieurs natifs et les lieurs croisés qui ont été configurés avec l'option --with-sysroot.
    3.
    Sur un système ELF, pour les lieurs natifs, si les options -rpath et -rpath-link n'ont pas été utilisées, recherchez dans le contenu de la variable d'environnement "LD_RUN_PATH".
    4.
    Sur SunOS, si l'option -rpath n'a pas été utilisée, recherchez dans tous les répertoires spécifiés à l'aide des options -L.
    5.
    Pour un lieur natif, recherchez dans le contenu de la variable d'environnement "LD_LIBRARY_PATH".
    6.
    Pour un lieur ELF natif, les répertoires dans "DT_RUNPATH" ou "DT_RPATH" d'une bibliothèque partagée sont recherchés pour les bibliothèques partagées dont elle a besoin. Les entrées "DT_RPATH" sont ignorées si des entrées "DT_RUNPATH" existent.

    Pour un lieur natif sur un système FreeBSD, tous les répertoires spécifiés par la macro "_PATH_ELF_HINTS" définie dans le fichier d'en-tête elf-hints.h.
    9.
    Tous les répertoires spécifiés par une commande "SEARCH_DIR" dans un script de lieur fourni sur la ligne de commande, y compris les scripts spécifiés par -T (mais pas -dT).
    10.
    Les répertoires par défaut, normalement /lib et /usr/lib.

    -Bshareable

    --sort-common
    --sort-common=ascending
    --sort-common=descending
    Cette option indique à ld de trier les symboles communs par alignement dans l'ordre croissant ou décroissant lors de leur placement dans les sections de sortie appropriées. Les alignements de symboles considérés sont de seize octets ou plus, de huit octets, de quatre octets, de deux octets et d'un octet. Ceci afin d'éviter des espaces entre les symboles dus aux contraintes d'alignement. Si aucun ordre de tri n'est spécifié, alors l'ordre décroissant est supposé.

    Cette option appliquera "SORT_BY_NAME" à tous les motifs de section génériques dans le script de lieur.
    --sort-section=alignment

    Cette option spécifie le nombre d'emplacements vides à laisser dans la section .dynamic des objets partagés ELF. Des emplacements vides peuvent être nécessaires pour les outils de post-traitement, tels que le pré-lieur. La valeur par défaut est 5.
    --split-by-file[=taille]
    Similaire à --split-by-reloc mais crée une nouvelle section de sortie pour chaque fichier d'entrée lorsque taille est atteinte. taille vaut par défaut 1 si elle n'est pas donnée.
    --split-by-reloc[=nombre]
    Tente de créer des sections supplémentaires dans le fichier de sortie de sorte qu'aucune section de sortie unique dans le fichier ne contienne plus de nombre relocations. Ceci est utile lors de la génération de fichiers relogeables volumineux pour les télécharger dans certains noyaux temps réel avec le format de fichier objet COFF ; car COFF ne peut pas représenter plus de 65535 relocations dans une seule section. Notez que cela échouera avec les formats de fichiers objets qui ne prennent pas en charge les sections arbitraires. Le lieur ne divisera pas les sections d'entrée individuelles pour la redistribution, donc si une seule section d'entrée contient plus de nombre relocations, une section de sortie contiendra ce nombre de relocations. nombre vaut par défaut 32768.

    Calcule et affiche des statistiques sur le fonctionnement du lieur, telles que le temps d'exécution et l'utilisation de la mémoire.
    --sysroot=répertoire
    Utilise répertoire comme emplacement du sysroot, remplaçant la valeur par défaut configurée lors de la compilation. Cette option n'est prise en charge que par les lieurs configurés avec --with-sysroot.
    --task-link
    Ceci est utilisé par les cibles basées sur COFF/PE pour créer un fichier objet lié à une tâche où tous les symboles globaux ont été convertis en statiques.
    --traditional-format
    Pour certaines cibles, la sortie de ld diffère à certains égards de la sortie de certains lieurs existants. Ce commutateur demande à ld d'utiliser le format traditionnel à la place.

    Par exemple, sur SunOS, ld combine les entrées dupliquées dans la table des chaînes de symboles. Cela peut réduire la taille d'un fichier de sortie avec des informations de débogage complètes de plus de 30 %. Malheureusement, le programme "dbx" de SunOS ne peut pas lire le programme résultant ("gdb" n'a aucun problème). Le commutateur --traditional-format indique à ld de ne pas combiner les entrées dupliquées.

    --section-start=nomsection=org
    Localise une section dans le fichier de sortie à l'adresse absolue donnée par org. Vous pouvez utiliser cette option autant de fois que nécessaire pour localiser plusieurs sections dans la ligne de commande. org doit être un entier hexadécimal unique ; pour la compatibilité avec d'autres lieurs, vous pouvez omettre le préfixe 0x généralement associé aux valeurs hexadécimales. Note : il ne doit y avoir aucun espace blanc entre nomsection, le signe égal ("=") et org.

    -Tdata=org
    -Ttext=org

    Lors de la création d'un exécutable ELF, il définit l'adresse du premier octet du segment de texte.
    -Trodata-segment=org
    Lors de la création d'un exécutable ELF ou d'un objet partagé pour une cible où les données en lecture seule se trouvent dans leur propre segment, séparé du texte exécutable, il définit l'adresse du premier octet du segment de données en lecture seule.
    -Tldata-segment=org
    Lors de la création d'un exécutable ELF ou d'un objet partagé pour le modèle de mémoire moyenne x86-64, il définit l'adresse du premier octet du segment ldata.

    Détermine comment gérer les symboles non résolus. Il existe quatre valeurs possibles pour méthode :

    Ne pas signaler de symboles non résolus.
    report-all
    Signaler tous les symboles non résolus. C'est la valeur par défaut.
    ignore-in-object-files
    Signaler les symboles non résolus contenus dans les bibliothèques partagées, mais les ignorer s'ils proviennent de fichiers objets réguliers.

    Signaler les symboles non résolus provenant de fichiers objets réguliers, mais les ignorer s'ils proviennent de bibliothèques partagées. Ceci peut être utile lors de la création d'une binaire dynamique et lorsqu'il est connu que toutes les bibliothèques partagées auxquelles il devrait faire référence sont incluses dans la ligne de commande du lieur.

    --verbose[=NOMBRE]
    Affiche le numéro de version de ld et liste les émulations de lieur prises en charge. Affiche quels fichiers d'entrée peuvent être ouverts et lesquels ne le peuvent pas. Affiche le script de lieur utilisé par le lieur. Si l'argument optionnel NOMBRE est supérieur à 1, l'état des symboles des plugins sera également affiché.

    Spécifie le nom d'un script de version au lieur. Ceci est généralement utilisé lors de la création de bibliothèques partagées pour spécifier des informations supplémentaires sur la hiérarchie des versions de la bibliothèque créée. Cette option n'est entièrement prise en charge que sur les plateformes ELF qui prennent en charge les bibliothèques partagées ; voir VERSION. Elle est partiellement prise en charge sur les plateformes PE, qui peuvent utiliser des scripts de version pour filtrer la visibilité des symboles en mode d'exportation automatique : tous les symboles marqués local dans le script de version ne seront pas exportés.
    --warn-common
    Avertit lorsqu'un symbole commun est combiné avec un autre symbole commun ou avec une définition de symbole. Les lieurs Unix autorisent cette pratique quelque peu laxiste, mais les lieurs sur certains autres systèmes d'exploitation ne le font pas. Cette option vous permet de détecter des problèmes potentiels dus à la combinaison de symboles globaux. Malheureusement, certaines bibliothèques C utilisent cette pratique, vous pourriez donc recevoir des avertissements concernant les symboles dans les bibliothèques ainsi que dans vos programmes.

    Il existe trois types de symboles globaux, illustrés ici par des exemples en C :

    int i = 1;
    Une définition, qui va dans la section des données initialisées du fichier de sortie.
    extern int i;
    Une référence indéfinie, quih n'alloue pas d'espace. Il doit y avoir soit une définition, soit un symbole commun pour la variable quelque part.
    int i;
    Un symbole commun. S'il n'y a que (un ou plusieurs) symboles communs pour une variable, celle-ci est placée dans la zone de données non initialisées du fichier de sortie. L'éditeur de liens fusionne plusieurs symboles communs pour la même variable en un seul symbole. S'ils sont de tailles différentes, il choisit la taille la plus grande. L'éditeur de liens transforme un symbole commun en une déclaration si une définition de la même variable existe.

    L'option --warn-common peut produire cinq types d'avertissements. Chaque avertissement consiste en une paire de lignes : la première décrit le symbole qui vient d'être rencontré, et la seconde décrit le symbole précédent rencontré portant le même nom. Un ou les deux symboles seront des symboles communs.

    1.
    Transformation d'un symbole commun en référence, car une définition existe déjà pour le symbole. 
    <fichier>(<section>): avertissement : commun de `<symbole>'
   écrasé par la définition
<fichier>(<section>): avertissement : défini ici
    2.
    Transformation d'un symbole commun en référence, car une définition ultérieure du symbole est rencontrée. C'est la même chose que le cas précédent, sauf que les symboles sont rencontrés dans un ordre différent. 
    <fichier>(<section>): avertissement : définition de `<symbole>'
   écrasant le commun
<fichier>(<section>): avertissement : commun ici
    3.
    Fusion d'un symbole commun avec un symbole commun précédent de même taille. 
    <fichier>(<section>): avertissement : multiples communs
   de `<symbole>'
<fichier>(<section>): avertissement : commun précédent ici
    4.
    Fusion d'un symbole commun avec un symbole commun précédent plus grand. 
    <fichier>(<section>): avertissement : commun de `<symbole>'
   écrasé par un commun plus grand
<fichier>(<section>): avertissement : commun plus grand ici
    5.
    Fusion d'un symbole commun avec un symbole commun précédent plus petit. C'est la même chose que le cas précédent, sauf que les symboles sont rencontrés dans un ordre différent. 
    <fichier>(<section>): avertissement : commun de `<symbole>'
   écrasant un commun plus petit
<fichier>(<section>): avertissement : commun plus petit ici
    --warn-constructors
    Avertir si des constructeurs globaux sont utilisés. Ceci n'est utile que pour quelques formats de fichiers objets. Pour des formats comme COFF ou ELF, l'éditeur de liens ne peut pas détecter l'utilisation de constructeurs globaux.
    --warn-execstack
    --warn-execstack-objects
    --no-warn-execstack
    Sur les plateformes ELF, l'éditeur de liens peut générer des messages d'avertissement s'il est invité à créer un fichier de sortie contenant une pile exécutable. Il existe trois états possibles :
    1.
    Ne générer aucun avertissement.
    2.
    Générer toujours des avertissements, même si la pile exécutable est demandée via l'option de ligne de commande -z execstack.
    3.
    Générer un avertissement uniquement si un fichier objet demande une pile exécutable, mais pas si l'option -z execstack est utilisée.

    L'état par défaut dépend de la manière dont l'éditeur de liens a été configuré lors de sa construction. L'option --no-warn-execstack met toujours l'éditeur de liens en état de non-avertissement. L'option --warn-execstack place l'éditeur de liens dans l'état d'avertissement systématique. L'option --warn-execstack-objects place l'éditeur de liens dans l'état d'avertissement uniquement pour les fichiers objets.

    Note : Les fichiers d'entrée au format ELF peuvent spécifier qu'ils nécessitent une pile exécutable en ayant une section .note.GNU-stack avec le bit exécutable activé dans ses drapeaux de section. Ils peuvent spécifier qu'ils n'ont pas besoin d'une pile exécutable en ayant la même section, mais sans le bit exécutable activé. Si un fichier d'entrée n'a pas de section .note.GNU-stack, le comportement par défaut est spécifique à la cible. Pour certaines cibles, l'absence d'une telle section implique qu'une pile exécutable est requise. C'est souvent un problème pour les fichiers assembleur créés manuellement.

    --error-execstack
    --no-error-execstack
    Si l'éditeur de liens est sur le point de générer un message d'avertissement concernant une pile exécutable, l'option --error-execstack transformera cet avertissement en erreur. Notez que cette option ne modifie pas l'état de génération des avertissements execstack de l'éditeur de liens. Utilisez --warn-execstack ou --warn-execstack-objects pour définir un état d'avertissement spécifique.

    L'option --no-error-execstack restaurera le comportement par défaut de génération de messages d'avertissement.

    --warn-multiple-gp
    Avertir si plusieurs valeurs de pointeur global sont nécessaires dans le fichier de sortie. Ceci n'est significatif que pour certains processeurs, comme l'Alpha. Spécifiquement, certains processeurs placent les constantes de grande valeur dans une section spéciale. Un registre spécial (le pointeur global) pointe vers le milieu de cette section, de sorte que les constantes puissent être chargées efficacement via un mode d'adressage relatif au registre de base. Comme le décalage en mode relatif au registre de base est fixe et relativement petit (par exemple, 16 bits), cela limite la taille maximale du pool de constantes. Ainsi, dans les grands programmes, il est souvent nécessaire d'utiliser plusieurs valeurs de pointeur global afin de pouvoir adresser toutes les constantes possibles. Cette option génère un avertissement lorsque ce cas se produit.
    --warn-once
    Avertir une seule fois pour chaque symbole non résolu, au lieu d'une fois par module qui y fait référence.
    --warn-rwx-segments
    --no-warn-rwx-segments
    Avertir si l'éditeur de liens crée un segment chargeable de taille non nulle qui possède les trois drapeaux de permission lecture, écriture et exécution. Un tel segment représente une vulnérabilité de sécurité potentielle. De plus, des avertissements seront générés si un segment de stockage local de thread est créé avec le drapeau de permission d'exécution activé, que les drapeaux de lecture et/ou d'écriture soient définis ou non.

    Ces avertissements sont activés par défaut. Ils peuvent être désactivés via l'option --no-warn-rwx-segments et réactivés via l'option --warn-rwx-segments.

    --error-rwx-segments
    --no-error-rwx-segments
    Si l'éditeur de liens génère un message d'avertissement concernant un segment exécutable et inscriptible, ou un segment TLS exécutable, l'option --error-rwx-segments transformera cet avertissement en erreur. L'option --no-error-rwx-segments restaurera le comportement par défaut de génération d'un simple message d'avertissement.

    Notez que l'option --error-rwx-segments n'active pas par elle-même les avertissements concernant ces segments. Ces avertissements sont soit activés par défaut, si l'éditeur de liens a été configuré ainsi, soit via l'option de ligne de commande --warn-rwx-segments.

    --warn-section-align
    Avertir si l'adresse d'une section de sortie est modifiée en raison de l'alignement. Généralement, l'alignement sera défini par une section d'entrée. L'adresse ne sera modifiée que si elle n'est pas explicitement spécifiée ; c'est-à-dire si la commande "SECTIONS" ne spécifie pas d'adresse de départ pour la section.
    --warn-textrel
    Avertir si l'éditeur de liens ajoute DT_TEXTREL à un exécutable indépendant de la position ou à un objet partagé.
    --warn-alternate-em
    Avertir si un objet possède un code machine ELF alternatif.
    --warn-unresolved-symbols
    Si l'éditeur de liens doit signaler un symbole non résolu (voir l'option --unresolved-symbols), il générera normalement une erreur. Cette option lui fait générer un avertissement à la place.
    --error-unresolved-symbols
    Ceci restaure le comportement par défaut de l'éditeur de liens consistant à générer des erreurs lorsqu'il signale des symboles non résolus.
    --whole-archive
    Pour chaque archive mentionnée sur la ligne de commande après l'option --whole-archive, inclure chaque fichier objet de l'archive dans la liaison, plutôt que de rechercher dans l'archive les fichiers objets requis. Ceci est normalement utilisé pour transformer un fichier archive en une bibliothèque partagée, forçant l'inclusion de chaque objet dans la bibliothèque partagée résultante. Cette option peut être utilisée plusieurs fois.

Deuxièmement, n'oubliez pas d'utiliser -Wl,-no-whole-archive après votre liste d'archives, car gcc ajoutera sa propre liste d'archives à votre liaison et vous pourriez ne pas vouloir que cet indicateur affecte celles-ci également.

    --wrap=symbole
    Utiliser une fonction de remplacement pour symbole. Toute référence non résolue à symbole sera résolue en "__wrap_symbole". Toute référence non résolue à "__real_symbole" sera résolue en symbole.

    Ceci peut être utilisé pour fournir une fonction de remplacement pour une fonction système. La fonction de remplacement doit être appelée "__wrap_symbole". Si elle souhaite appeler la fonction système, elle doit appeler "__real_symbole".

    void *

{
  printf ("malloc appelé avec %zu\n", c);
  return __real_malloc (c);
}

    /span> appellera la fonction "malloc" réelle.

    Vous pouvez également souhaiter fournir une fonction "__real_malloc", de sorte que les liens sans l'option --wrap réussissent. Si vous le faites, vous ne devez pas placer la définition de "__real_malloc" dans le même fichier que "__wrap_malloc" ; si vous le faites, l'assembleur peut résoudre l'appel avant que l'éditeur de liens n'ait la possibilité de le lier à "malloc".

    Seules les références indéfinies sont remplacées par l'éditeur de liens. Ainsi, les références internes à l'unité de traduction à symbole ne sont pas résolues en "__wrap_symbole". Dans l'exemple suivant, l'appel à "f" dans "g" n'est pas résolu en "__wrap_f".

{
  return 123;
}

int

{
  return f();

Si vous spécifiez --enable-new-dtags, les nouvelles balises dynamiques seront créées au besoin et les anciennes balises dynamiques seront omises. Si vous spécifiez --disable-new-dtags, aucune nouvelle balise dynamique ne sera créée. Par défaut, les nouvelles balises dynamiques ne sont pas créées.     --hash-size=nombre
    Définit la taille par défaut des tables de hachage de l'éditeur de liens sur un nombre premier proche de nombre. Augmenter cette valeur peut réduire le temps nécessaire à l'éditeur de liens pour effectuer ses tâches, au détriment d'une augmentation des besoins en mémoire de l'éditeur de liens. De même, réduire cette valeur peut réduire les besoins en mémoire au détriment de la vitesse.

    --compress-debug-sections=none
    --compress-debug-sections=zlib
    --compress-debug-sections=zlib-gnu
    --compress-debug-sections=zlib-gabi
    --compress-debug-sections=zstd
    Sur les plateformes ELF, ces options contrôlent la compression des sections de débogage DWARF à l'aide de zlib.

    --compress-debug-sections=none ne compresse pas les sections de débogage DWARF. --compress-debug-sections=zlib-gnu compresse les sections de débogage DWARF et les renomme pour commencer par .zdebug au lieu de .debug. --compress-debug-sections=zlib-gabi compresse également les sections de débogage DWARF, mais au lieu de les renommer, elle définit le drapeau SHF_COMPRESSED dans les en-têtes des sections.

    L'option --compress-debug-sections=zlib est un alias pour --compress-debug-sections=zlib-gabi.

    --compress-debug-sections=zstd compresse les sections de débogage DWARF à l'aide de zstd.

    Notez que cette option remplace toute compression dans les sections de débogage d'entrée, donc si un binaire est lié avec --compress-debug-sections=none par exemple, alors toutes les sections de débogage compressées dans les fichiers d'entrée seront décompressées avant d'être copiées dans le binaire de sortie.

    Le comportement de compression par défaut varie en fonction de la cible impliquée et des options de configuration utilisées pour construire la chaîne d'outils. Le comportement par défaut peut être déterminé en examinant la sortie de l'option --help de l'éditeur de liens.

    --reduce-memory-overheads
    Cette option réduit les besoins en mémoire à l'exécution de ld, au détriment de la vitesse de liaison. Elle a été introduite pour sélectionner l'ancien algorithme O(n^2) pour la génération du fichier de mappage de liens, plutôt que le nouvel algorithme O(n) qui utilise environ 40 % de mémoire en plus pour le stockage des symboles.

    Un autre effet de cette option est de définir la taille par défaut de la table de hachage sur 1021, ce qui économise de la mémoire au détriment de l'allongement du temps d'exécution de l'éditeur de liens. Ceci n'est cependant pas fait si l'option --hash-size a été utilisée.

    L'option --reduce-memory-overheads peut également être utilisée pour activer d'autres compromis dans les futures versions de l'éditeur de liens.

    --max-cache-size=taille
    ld met normalement en cache les informations de relocalisation et les tables de symboles des fichiers d'entrée en mémoire avec une taille illimitée. Cette option définit la taille maximale du cache à taille.
    --build-id
    --build-id=style
    Demande la création d'une section de note ELF ".note.gnu.build-id" ou d'une section COFF ".buildid". Le contenu de la note identifie de manière unique ce fichier lié. style peut être "uuid" pour utiliser 128 bits aléatoires, "sha1" pour utiliser un hachage SHA1 de 160 bits sur les parties normatives du contenu de sortie, "md5" pour utiliser un hachage MD5 de 128 bits sur les parties normatives du contenu de sortie, ou "0xchaînehex" pour utiliser une chaîne de bits choisie spécifiée comme un nombre pair de chiffres hexadécimaux (les caractères "-" et ":" entre les paires de chiffres sont ignorés). Si style est omis, "sha1" est utilisé.

    Les styles "md5" et "sha1" produisent un identifiant qui est toujours le même dans un fichier de sortie identique, mais qui sera unique parmi tous les fichiers de sortie non identiques. Il n'est pas destiné à être comparé comme une somme de contrôle du contenu du fichier. Un fichier lié peut être modifié ultérieurement par d'autres outils, mais la chaîne de bits d'ID de construction identifiant le fichier lié d'origine ne change pas.

    Passer "none" pour style désactive le paramètre de toute option "--build-id" précédente sur la ligne de commande.

    Note : L'utilisation de l'extension 'auto-import' rendra la section de texte du fichier image inscriptible. Ceci n'est pas conforme à la spécification du format PE-COFF publiée par Microsoft.

    Note - l'utilisation de l'extension 'auto-import' entraînera également le placement des données en lecture seule, qui seraient normalement placées dans la section .rdata, dans la section .data à la place. Ceci afin de contourner un problème avec les constantes qui est décrit ici : http://www.cygwin.com/ml/cygwin/2004-09/msg01101.html

    L'utilisation de 'auto-import' fonctionnera généralement 'sans problème' -- mais parfois vous verrez ce message :

    "variable '<var>' ne peut pas être auto-importée. Veuillez lire la documentation de ld pour "--enable-auto-import" pour plus de détails."

    Ce message se produit lorsqu'une (sous-)expression accède à une adresse finalement donnée par la somme de deux constantes (les tables d'importation Win32 n'en autorisent qu'une). Les cas où cela peut se produire incluent les accès aux champs membres de variables de structure importées d'une DLL, ainsi que l'utilisation d'un index constant dans une variable tableau importée d'une DLL. Toute variable multi-mots (tableaux, structures, long long, etc.) peut déclencher cette condition d'erreur. Cependant, quel que soit le type de données exact de la variable exportée incriminée, ld la détectera toujours, émettra un avertissement et quittera.

    Il existe plusieurs façons de résoudre cette difficulté, quel que soit le type de données de la variable exportée :

    Une façon est d'utiliser l'option --enable-runtime-pseudo-reloc. Ceci laisse la tâche d'ajuster les références dans votre code client pour l'environnement d'exécution, donc cette méthode ne fonctionne que lorsque l'environnement d'exécution supporte cette fonctionnalité.

    Une deuxième solution consiste à forcer l'une des 'constantes' à être une variable -- c'est-à-dire, inconnue et non optimisable au moment de la compilation. Pour les tableaux, il y a deux possibilités : a) faire de l'indexé (l'adresse du tableau) une variable, ou b) faire de l'index 'constant' une variable. Ainsi :

    extern type extern_array[];
extern_array[1] -->
   { volatile type *t=extern_array; t[1] }

    ou

    extern type extern_array[];
extern_array[1] -->
   { volatile int t=1; extern_array[t] }

    Pour les structures (et la plupart des autres types de données multi-mots) la seule option est de rendre la structure elle-même (ou le long long, ou le ...) variable :

    extern struct s extern_struct;
extern_struct.field -->
   { volatile struct s *t=&extern_struct; t->field }

    ou

    extern long long extern_ll;
extern_ll -->
  { volatile long long * local_ll=&extern_ll; *local_ll }

    Une troisième méthode pour traiter cette difficulté est d'abandonner 'auto-import' pour le symbole incriminé et de le marquer avec "__declspec(dllimport)". Cependant, en pratique, cela nécessite d'utiliser des #defines au moment de la compilation pour indiquer si vous construisez une DLL, construisez du code client qui se liera à la DLL, ou simplement construisez/liez à une bibliothèque statique. En faisant le choix entre les différentes méthodes de résolution du problème 'adresse directe avec décalage constant', vous devriez considérer l'usage typique dans le monde réel :

    Original :

    --foo.h
extern int arr[];
--foo.c
#include "foo.h"
void main(int argc, char **argv){
  printf("%d\n",arr[1]);
}

    Solution 1 :

    --foo.h
extern int arr[];
--foo.c
#include "foo.h"
void main(int argc, char **argv){
  /* Ce contournement est pour win32 et cygwin; ne pas "optimiser" */
  volatile int *parr = arr;
  printf("%d\n",parr[1]);
}

    Solution 2 :

    --foo.h
/* Note : auto-export est supposé (pas de __declspec(dllexport)) */
#if (defined(_WIN32) || defined(__CYGWIN__)) && \
  !(defined(FOO_BUILD_DLL) || defined(FOO_STATIC))
#define FOO_IMPORT __declspec(dllimport)
#else
#define FOO_IMPORT
#endif
extern FOO_IMPORT int arr[];
--foo.c
#include "foo.h"
void main(int argc, char **argv){
  printf("%d\n",arr[1]);
}

    Une quatrième façon d'éviter ce problème est de recoder votre bibliothèque pour utiliser une interface fonctionnelle plutôt qu'une interface de données pour les variables incriminées (par exemple, des fonctions d'accès set_foo() et get_foo()).

    --disable-no-isolation
    Bien que l'image comprenne l'isolation, n'isole pas l'image. Cette option est désactivée par défaut.
    --no-seh
    --disable-no-seh
    L'image n'utilise pas SEH (Structured Exception Handling). Aucun gestionnaire SE ne peut être appelé depuis cette image. Cette option est désactivée par défaut.
    --no-bind
    --disable-no-bind
    Ne lie pas cette image. Cette option est désactivée par défaut.
    --wdmdriver
    --disable-wdmdriver
    Le pilote utilise le MS Windows Driver Model. Cette option
    est désactivé par défaut.
    --tsaware
    --disable-tsaware
    L'image est consciente du serveur de terminal. Cette option est désactivée par défaut.
    --insert-timestamp
    --no-insert-timestamp
    Insérer une vraie estampille temporelle dans l'image. C'est le comportement par défaut car il correspond au code hérité et signifie que l'image fonctionnera avec d'autres outils propriétaires. Le problème avec cette valeur par défaut est qu'elle produira des images légèrement différentes à chaque fois que les mêmes sources seront liées. L'option --no-insert-timestamp peut être utilisée pour insérer une valeur nulle pour l'estampille temporelle, garantissant ainsi que les binaires produits à partir de sources identiques se compareront de manière identique.

    Si --insert-timestamp est actif, l'heure insérée est soit l'heure à laquelle la liaison a lieu, soit, si la variable d'environnement "SOURCE_DATE_EPOCH" est définie, le nombre de secondes depuis l'époque Unix tel que spécifié par cette variable.

    --enable-reloc-section
    --disable-reloc-section
    Créer la table de relocation de base, nécessaire si l'image est chargée à une base d'image différente de celle spécifiée dans l'en-tête PE. Cette option est activée par défaut.

    La cible C6X uClinux utilise un format binaire appelé DSBT pour prendre en charge les bibliothèques partagées. Chaque bibliothèque partagée dans le système doit avoir un index unique ; tous les exécutables utilisent un index de 0.

    --dsbt-size taille
    Cette option définit le nombre d'entrées dans le DSBT de l'exécutable ou de la bibliothèque partagée actuelle à taille. La valeur par défaut est de créer une table avec 64 entrées.
    --dsbt-index index
    Cette option définit l'index DSBT de l'exécutable ou de la bibliothèque partagée actuelle à index. La valeur par défaut est 0, ce qui convient à la génération d'exécutables. Si une bibliothèque partagée est générée avec un index DSBT de 0, les relocations "R_C6000_DSBT_INDEX" sont copiées dans le fichier de sortie.

    Le commutateur --no-merge-exidx-entries désactive la fusion des entrées exidx adjacentes dans les informations de déroulement de trame.

    --branch-stub
    Cette option active la relaxation des branchements par le lieur en insérant des sections de "stubs" de branchement lorsque cela est nécessaire pour étendre la portée des branchements. Cette option n'est généralement pas requise car C-SKY prend en charge les instructions de branchement et d'appel qui peuvent accéder à toute la plage de mémoire et la relaxation des branchements est normalement gérée par le compilateur ou l'assembleur.
    --stub-group-size=N
    Cette option permet un contrôle plus fin de la création des "stubs" de branchement par le lieur. Elle définit la taille maximale d'un groupe de sections d'entrée qui peuvent être gérées par une section de "stub". Une valeur négative de N place les sections de "stub" après leurs branchements, tandis qu'une valeur positive permet aux sections de "stub" d'apparaître avant ou après les branchements. Les valeurs 1 ou -1 indiquent que le lieur doit choisir des valeurs par défaut appropriées.

    Les lieurs 68HC11 et 68HC12 prennent en charge des options spécifiques pour contrôler la cartographie de commutation de banque mémoire et la génération de code "trampoline".

    --no-trampoline
    Cette option désactive la génération de "trampoline". Par défaut, une "trampoline" est générée pour chaque fonction distante appelée à l'aide d'une instruction "jsr" (cela se produit lorsqu'un pointeur vers une fonction distante est pris).
    --bank-window nom
    Cette option indique au lieur le nom de la région mémoire dans la spécification MEMORY qui décrit la fenêtre de banque mémoire. La définition d'une telle région est ensuite utilisée par le lieur pour calculer la pagination et les adresses dans la fenêtre mémoire.

    Les options suivantes sont prises en charge pour contrôler la gestion de la génération du GOT lors de la liaison pour les cibles 68K.

    --got=type
    Cette option indique au lieur quel schéma de génération GOT utiliser. type doit être l'un des éléments suivants : single, negative, multigot ou target. Pour plus d'informations, consultez l'entrée Info pour ld.

    Les options suivantes sont prises en charge pour contrôler la génération d'instructions microMIPS et les vérifications de relocation de branchement pour les transitions de mode ISA lors de la liaison pour les cibles MIPS.

    --insn32
    --no-insn32
    Ces options contrôlent le choix des instructions microMIPS utilisées dans le code généré par le lieur, comme dans le PLT ou les "stubs" de liaison paresseuse, ou dans la relaxation. Si --insn32 est utilisé, le lieur n'utilise que des codages d'instructions de 32 bits. Par défaut ou si --no-insn32 est utilisé, tous les codages d'instructions sont utilisés, y compris ceux de 16 bits lorsque cela est possible.
    --ignore-branch-isa
    --no-ignore-branch-isa
    Ces options contrôlent les vérifications de relocation de branchement pour les transitions de mode ISA invalides. Si --ignore-branch-isa est utilisé, le lieur accepte toutes les relocations de branchement et toute transition de mode ISA requise est perdue dans le calcul de la relocation, à l'exception de certains cas d'instructions "BAL" qui satisfont aux conditions de relaxation et sont converties en instructions "JALX" équivalentes lors du calcul de la relocation associée. Par défaut ou si --no-ignore-branch-isa est utilisé, une vérification est effectuée, entraînant la perte d'une transition de mode ISA, produisant une erreur.
    --compact-branches
    --no-compact-branches
    Ces options contrôlent la génération d'instructions compactes par le lieur dans les entrées PLT pour MIPS R6.

    Pour la cible pdp11-aout, trois variantes du format de sortie peuvent être produites, sélectionnées par les options suivantes. La variante par défaut pour pdp11-aout est l'option --omagic, tandis que pour les autres cibles, --nmagic est la valeur par défaut. L'option --imagic est définie uniquement pour la cible pdp11-aout, tandis que les autres sont décrites ici telles qu'elles s'appliquent à la cible pdp11-aout.

    -N
    --omagic
    Marquer la sortie comme "OMAGIC" (0407) dans l'en-tête a.out pour indiquer que le segment de texte ne doit pas être protégé en écriture et partagé. Étant donné que les segments de texte et de données sont tous deux lisibles et inscriptibles, le segment de données est alloué immédiatement après le segment de texte. C'est le format le plus ancien pour les programmes exécutables PDP11 et c'est la valeur par défaut pour ld sur les systèmes Unix PDP11 depuis le début jusqu'à 2.11BSD.
    -n
    --nmagic
    Marquer la sortie comme "NMAGIC" (0410) dans l'en-tête a.out pour indiquer que lorsque le fichier de sortie est exécuté, la partie texte sera en lecture seule et partageable entre tous les processus exécutant le même fichier. Cela implique de déplacer les zones de données jusqu'à la première limite de page de 8 Ko possible après la fin du texte. Cette option crée un format d'exécutable pur.
    -z
    --imagic
    Marquer la sortie comme "IMAGIC" (0411) dans l'en-tête a.out pour indiquer que lorsque le fichier de sortie est exécuté, les zones de texte et de données du programme seront chargées dans des espaces d'adressage séparés en utilisant la fonctionnalité d'espace d'instructions et de données séparés de l'unité de gestion de mémoire dans les modèles plus grands du PDP11. Cela double l'espace d'adressage disponible pour le programme. Le segment de texte est à nouveau pur, protégé en écriture et partageable. La seule différence dans le format de sortie entre cette option et les autres, outre le nombre magique, est que les segments de texte et de données commencent tous deux à l'emplacement 0. L'option -z sélectionnait ce format dans 2.11BSD. Cette option crée un format d'exécutable séparé.

    --no-omagic

    --no-omagic
    Équivalent à --nmagic pour pdp11-aout.

    ENVIRONNEMENT

    Vous pouvez modifier le comportement de ld avec les variables d'environnement "GNUTARGET", "LDEMULATION" et "COLLECT_NO_DEMANGLE".

    "GNUTARGET" détermine le format d'objet des fichiers d'entrée si vous n'utilisez pas -b (ou son synonyme --format). Sa valeur doit être l'un des noms BFD pour un format d'entrée. S'il n'y a pas de "GNUTARGET" dans l'environnement, ld utilise le format naturel de la cible. Si "GNUTARGET" est défini sur "default", alors BFD tente de découvrir le format d'entrée en examinant les fichiers binaires d'entrée ; cette méthode réussit souvent, mais il existe des ambiguïtés potentielles, car il n'existe aucun moyen de garantir que le nombre magique utilisé pour spécifier les formats de fichiers objet est unique. Cependant, la procédure de configuration de BFD sur chaque système place le format conventionnel pour ce système en premier dans la liste de recherche, de sorte que les ambiguïtés sont résolues en faveur de la convention.

    "LDEMULATION" détermine l'émulation par défaut si vous n'utilisez pas l'option -m. L'émulation peut affecter divers aspects du comportement du lieur, en particulier le script de lieur par défaut. Vous pouvez lister les émulations disponibles avec les options --verbose ou -V. Si l'option -m n'est pas utilisée et que la variable d'environnement "LDEMULATION" n'est pas définie, l'émulation par défaut dépend de la manière dont le lieur a été configuré.

    Normalement, le lieur effectue un "démêlage" des symboles par défaut. Cependant, si "COLLECT_NO_DEMANGLE" se trouve dans l'environnement, alors il sera par défaut de ne pas démangler les symboles. Cette variable d'environnement est utilisée de manière similaire par le programme wrapper de l'éditeur de liens "gcc". Le défaut peut être annulé par les options --demangle et --no-demangle.
