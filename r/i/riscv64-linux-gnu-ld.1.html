LD(1) Outils de développement GNU LD(1)

NOM

ld - L'éditeur de liens GNU

SYNOPSIS

ld [options] fichier objet ...

DESCRIPTION

ld combine un certain nombre de fichiers objets et d'archives, relocalise leurs données et résout les références de symboles. Normalement, la dernière étape de la compilation d'un programme est l'exécution de ld.

ld accepte des fichiers de langage de commande de l'éditeur de liens écrits dans un sur-ensemble de la syntaxe du langage de commande de l'éditeur de liens d'AT&T, afin de fournir un contrôle explicite et total sur le processus de liaison.

Cette page de manuel ne décrit pas le langage de commande; voir l'entrée ld dans "info" pour des détails complets sur le langage de commande et sur d'autres aspects de l'éditeur de liens GNU.

Cette version de ld utilise les bibliothèques BFD à usage général pour opérer sur les fichiers objets. Cela permet à ld de lire, combiner et écrire des fichiers objets dans de nombreux formats différents - par exemple, COFF ou "a.out". Différents formats peuvent être liés ensemble pour produire n'importe quel type de fichier objet disponible.

Outre sa flexibilité, l'éditeur de liens GNU est plus utile que d'autres éditeurs de liens pour fournir des informations diagnostiques. De nombreux éditeurs de liens abandonnent l'exécution immédiatement en rencontrant une erreur; lorsque c'est possible, ld continue l'exécution, vous permettant d'identifier d'autres erreurs (ou, dans certains cas, d'obtenir un fichier de sortie malgré l'erreur).

L'éditeur de liens GNU ld est conçu pour couvrir un large éventail de situations et être aussi compatible que possible avec d'autres éditeurs de liens. Par conséquent, vous avez de nombreux choix pour contrôler son comportement.

OPTIONS

L'éditeur de liens prend en charge une pléthore d'options en ligne de commande, mais en pratique, peu d'entre elles sont utilisées dans un contexte particulier. Par exemple, une utilisation fréquente de ld est de lier des fichiers objets Unix standards sur un système Unix standard et supporté. Sur un tel système, pour lier un fichier "hello.o":

ld -o <sortie> /lib/crt0.o hello.o -lc

Ceci indique à ld de produire un fichier nommé sortie comme résultat de la liaison du fichier "/lib/crt0.o" avec "hello.o" et la bibliothèque "libc.a", qui proviendra des répertoires de recherche standards. (Voir la discussion de l'option -l ci-dessous.)

Certaines des options en ligne de commande de ld peuvent être spécifiées à n'importe quel endroit de la ligne de commande. Cependant, les options qui font référence à des fichiers, telles que -l ou -T, font que le fichier est lu à l'endroit où l'option apparaît dans la ligne de commande, par rapport aux fichiers objets et autres options de fichier. Répéter des options non liées à des fichiers avec un argument différent n'aura soit aucun effet supplémentaire, soit remplacera les occurrences précédentes (celles plus à gauche dans la ligne de commande) de cette option. Les options qui peuvent être significativement spécifiées plus d'une fois sont notées dans les descriptions ci-dessous.

Les arguments non-option sont des fichiers objets ou des archives qui doivent être liés ensemble. Ils peuvent suivre, précéder ou être mélangés avec les options de ligne de commande, à l'exception du fait qu'un argument de fichier objet ne peut pas être placé entre une option et son argument.

Habituellement, l'éditeur de liens est invoqué avec au moins un fichier objet, mais vous pouvez spécifier d'autres formes de fichiers d'entrée binaires en utilisant -l, -R, et le langage de commande de scripts. Si *aucun* fichier d'entrée binaire n'est spécifié du tout, l'éditeur de liens ne produit aucune sortie et émet le message Aucun fichier d'entrée.

Si l'éditeur de liens ne peut pas reconnaître le format d'un fichier objet, il supposera qu'il s'agit d'un script d'éditeur de liens. Un script spécifié de cette manière augmente le script principal de l'éditeur de liens utilisé pour la liaison (soit le script par défaut, soit celui spécifié en utilisant -T). Cette fonctionnalité permet à l'éditeur de liens de lier avec un fichier qui ressemble à un objet ou à une archive, mais qui ne fait que définir certaines valeurs de symboles, ou utilise "INPUT" ou "GROUP" pour charger d'autres objets. Spécifier un script de cette manière ne fait qu'augmenter le script principal de l'éditeur de liens, les commandes supplémentaires étant placées après le script principal; utilisez l'option -T pour remplacer entièrement le script de l'éditeur de liens par défaut, mais notez l'effet de la commande "INSERT".

Pour les options dont les noms sont une seule lettre, les arguments d'option doivent soit suivre la lettre de l'option sans espace blanc intercalaire, soit être donnés comme arguments séparés immédiatement après l'option qui les exige.

Pour les options dont les noms sont des lettres multiples, un tiret ou deux peuvent précéder le nom de l'option; par exemple, -trace-symbol et --trace-symbol sont équivalents. Notez - il y a une exception à cette règle. Les options à lettres multiples qui commencent par une lettre 'o' minuscule ne peuvent être précédées que de deux tirets. Ceci est pour réduire la confusion avec l'option -o. Ainsi, par exemple, -omagic définit le nom du fichier de sortie à magic tandis que --omagic définit l'indicateur NMAGIC sur la sortie.

Les arguments des options à lettres multiples doivent être séparés du nom de l'option par un signe égal, ou être donnés comme arguments séparés immédiatement après l'option qui les exige. Par exemple, --trace-symbol foo et --trace-symbol=foo sont équivalents. Des abréviations uniques des noms des options à lettres multiples sont acceptées.

Notez - si l'éditeur de liens est invoqué indirectement, via un pilote de compilateur (par exemple, gcc) alors toutes les options de ligne de commande de l'éditeur de liens doivent être préfixées par -Wl, (ou ce qui est approprié pour le pilote de compilateur particulier) comme ceci:

gcc -Wl,--start-group foo.o bar.o -Wl,--end-group

C'est important, car sinon le programme pilote de compilation peut ignorer silencieusement les options de l'éditeur de liens, résultant en une liaison incorrecte. La confusion peut également survenir lors du passage d'options qui nécessitent des valeurs par un pilote, car l'utilisation d'un espace entre l'option et l'argument agit comme un séparateur, et fait que le pilote passe uniquement l'option à l'éditeur de liens et l'argument au compilateur. Dans ce cas, il est plus simple d'utiliser les formes jointes des options à lettre unique et à lettres multiples, telles que:

gcc foo.o bar.o -Wl,-eENTRY -Wl,-Map=a.map

Voici une table des commutateurs génériques acceptés par l'éditeur de liens GNU:

@fichier
Lit les options de la ligne de commande depuis fichier. Les options lues sont insérées à la place de l'option @fichier d'origine. Si fichier n'existe pas, ou ne peut pas être lu, alors l'option sera traitée littéralement, et non supprimée.

Les options dans fichier sont séparées par des espaces blancs. Un caractère d'espace blanc peut être inclus dans une option en entourant l'option entière de guillemets simples ou doubles. N'importe quel caractère (y compris une barre oblique inverse) peut être inclus en précédant le caractère à inclure avec une barre oblique inverse. Le fichier peut lui-même contenir des options @fichier supplémentaires; toutes ces options seront traitées récursivement.

-a mot-clé
Cette option est supportée pour la compatibilité HP/UX. L'argument mot-clé doit être l'une des chaînes archive, shared, ou default. -aarchive est fonctionnellement équivalent à -Bstatic, et les deux autres mots-clés sont fonctionnellement équivalents à -Bdynamic. Cette option peut être utilisée un nombre quelconque de fois.
--audit BIBLIO_AUDIT
Ajoute BIBLIO_AUDIT à l'entrée "DT_AUDIT" de la section dynamique. BIBLIO_AUDIT n'est pas vérifiée pour son existence, ni n'utilisera le DT_SONAME spécifié dans la bibliothèque. Si spécifiée plusieurs fois, "DT_AUDIT" contiendra une liste d'interfaces d'audit séparées par des deux-points à utiliser. Si l'éditeur de liens trouve un objet avec une entrée d'audit lors de la recherche de bibliothèques partagées, il ajoutera une entrée correspondante "DT_DEPAUDIT" dans le fichier de sortie. Cette option n'est significative que sur les plateformes ELF supportant l'interface rtld-audit.
-b format-entrée
--format=format-entrée
ld peut être configuré pour supporter plus d'un type de fichier objet. Si votre ld est configuré de cette manière, vous pouvez utiliser l'option -b pour spécifier le format binaire des fichiers objets qui suivent cette option sur la ligne de commande. Même lorsque ld est configuré pour supporter des formats d'objets alternatifs, vous n'avez pas généralement besoin de le spécifier, car ld devrait être configuré pour détecter automatiquement le format. ... (Le reste de la description de l'option -b est omis ici pour la concision)

-b format
Specify the input binary file format. If not specified, ld will try to guess the format of each input file, selecting the most usual format on each machine. input-format is a text string, the name of a particular format supported by the BFD libraries. (You can list the available binary formats with objdump -i.)

You may want to use this option if you are linking files with an unusual binary format. You can also use -b to switch formats explicitly (when linking object files of different formats), by including -b input-format before each group of object files in a particular format.

The default format is taken from the environment variable "GNUTARGET".

You can also define the input format from a script, using the command "TARGET";

-c MRI-commandfile
--mri-script=MRI-commandfile
For compatibility with linkers produced by MRI, ld accepts script files written in an alternate, restricted command language, described in the MRI Compatible Script Files section of GNU ld documentation. Introduce MRI script files with the option -c; use the -T option to run linker scripts written in the general-purpose ld scripting language. If MRI-cmdfile does not exist, ld looks for it in the directories specified by any -L options.
-d
-dc
-dp
These three options are equivalent; multiple forms are supported for compatibility with other linkers. They assign space to common symbols even if a relocatable output file is specified (with -r). The script command "FORCE_COMMON_ALLOCATION" has the same effect.
--depaudit AUDITLIB
-P AUDITLIB
Adds AUDITLIB to the "DT_DEPAUDIT" entry of the dynamic section. AUDITLIB is not checked for existence, nor will it use the DT_SONAME specified in the library. If specified multiple times "DT_DEPAUDIT" will contain a colon separated list of audit interfaces to use. This option is only meaningful on ELF platforms supporting the rtld-audit interface. The -P option is provided for Solaris compatibility.
--enable-linker-version
Enables the "LINKER_VERSION" linker script directive, described in Output Section Data. If this directive is used in a linker script and this option has been enabled then a string containing the linker version will be inserted at the current point.

Note - this location of this option on the linker command line is significant. It will only affect linker scripts that come after it on the command line, or which are built into the linker.

--disable-linker-version
Disables the "LINKER_VERSION" linker script directive, so that it does not insert a version string. This is the default.
--enable-non-contiguous-regions
This option avoids generating an error if an input section does not fit a matching output section. The linker tries to allocate the input section to subseque nt matching output sections, and generates an error only if no output section is large enough. This is useful when several non-contiguous memory regions are available and the input section does not require a particular one. The order in which input sections are evaluated does not change, for instance: 
MEMORY {
  MEM1 (rwx) : ORIGIN = 0x1000, LENGTH = 0x14
  MEM2 (rwx) : ORIGIN = 0x1000, LENGTH = 0x40
  MEM3 (rwx) : ORIGIN = 0x2000, LENGTH = 0x40
}
SECTIONS {
  mem1 : { *(.data.*); } > MEM1
  mem2 : { *(.data.*); } > MEM2
  mem3 : { *(.data.*); } > MEM3
}

with input sections:
.data.1: size 8
.data.2: size 0x10
.data.3: size 4

results in .data.1 affected to mem1, and .data.2 and .data.3
affected to mem2, even though .data.3 would fit in mem3.

This option is incompatible with INSERT statements because it changes the way input sections are mapped to output sections.

--enable-non-contiguous-regions-warnings
This option enables warnings when "--enable-non-contiguous-regions" allows possibly unexpected matches in sections mapping, potentially leading to silently discarding a section instead of failing because it does not fit any output region.
-e entry
--entry=entry
Use entry as the explicit symbol for beginning execution of your program, rather than the default entry point. If there is no symbol named entry, the linker will try to parse entry as a number, and use that as the entry address (the number will be interpreted in base 10; you may use a leading 0x for base 16, or a leading 0 for base 8).
--exclude-libs lib,lib,...
Specifies a list of archive libraries from which symbols should not be automatically exported. The library names may be delimited by commas or colons. Specifying "--exclude-libs ALL" excludes symbols in all archive libraries from automatic export. This option is available only for the i386 PE targeted port of the linker and for ELF targeted ports. For i386 PE, symbols explicitly listed in a .def file are still exported, regardless of this option. For ELF targeted ports, symbols affected by this option will be treated as hidden.
--exclude-modules-for-implib module,module,...
Specifies a list of object files or archive members, from which symbols should not be automatically exported, but which should be copied wholesale into the import library being generated during the link. The module names may be delimited by commas or colons, and must match exactly the filenames used by ld to open the files; for archive members, this is simply the member name, but for object files the name listed must include and match precisely any path used to specify the input file on the linker's command-line. This option is available only for the i386 PE targeted port of the linker. Symbols explicitly listed in a .def file are still exported, regardless of this option.
-E
--export-dynamic
--no-export-dynamic
When creating a dynamically linked executable, using the -E option or the --export-dynamic option causes the linker to add all symbols to the dynamic symbol table. The dynamic symbol table is the set of symbols which are visible from dynamic objects at run time.

If you do not use either of these options (or use the --no-export-dynamic option to restore the default behavior), the dynamic symbol table will normally contain only those symbols which are referenced by some dynamic object mentioned in the link.

If you use "dlopen" to load a dynamic object which needs to refer back to the symbols defined by the program, rather than some other dynamic object, then you will probably need to use this option when linking the program itself.

You can also use the dynamic list to control what symbols should be added to the dynamic symbol table if the output format supports it. See the description of --dynamic-list.

Note that this option is specific to ELF targeted ports. PE targets support a similar function to export all symbols from a DLL or EXE; see the description of --export-all-symbols below.

--export-dynamic-symbol=glob
When creating a dynamically linked executable, symbols matching glob will be added to the dynamic symbol table. When creating a shared library, references to symbols matching glob will not be bound to the definitions within the shared library. This option is a no-op when creating a shared library and -Bsymbolic or --dynamic-list are not specified. This option is only meaningful on ELF platforms which support shared libraries.
--export-dynamic-symbol-list=file
Specify a --export-dynamic-symbol for each pattern in the file. The format of the file is the same as the version node without scope and node name. See VERSION for more information.
-EB
Link big-endian objects. This affects the default output format.
-EL
Link little-endian objects. This affects the default output format.
-f name
--auxiliary=name
When creating an ELF shared object, set the internal DT_AUXILIARY field to the specified name. This tells the dynamic linker that the symbol table of the shared object should be used as an auxiliary filter on the symbol table of the shared object name.

If you later link a program against this filter object, then, when you run the program, the dynamic linker will see the DT_AUXILIARY field. If the dynamic linker resolves any symbols from the filter object, it will first check whether there is a definition in the shared object name. If there is one, it will be used instead of the definition in the filter object. The shared object name need not exist. Thus the shared object name may be used to provide an alternative implementation of certain functions, perhaps for debugging or for machine-specific performance.

This option may be specified more than once. The DT_AUXILIARY entries will be created in the order in which they appear on the command line.

-F name
--filter=name
When creating an ELF shared object, set the internal DT_FILTER field to the specified name. This tells the dynamic linker that the symbol table of the shared object should be used as a filter on the symbol table of the shared object name.

If you later link a program against this filter object, then, when you run the program, the dynamic linker will see the DT_FILTER field. It will use the symbol table of the shared object name to resolve symbols required by the program. Symbols defined in the filter object itself will not be available to the program, unless they are also exported by the shared object name. The shared object name need not exist.

This option may be specified more than once. The DT_FILTER entries will be created in the order in which they appear on the command line.

-G num
Set the largest common symbol that will be placed in the data section. Any common symbols larger than num will be placed in the bss section. This option is only supported for MIPS targets.
-h name
--shared-script=name
When creating an ELF shared object, use name as the linker script file. This is primarily used to set the internal DT_NEEDED field of the shared object. This option may be specified more than once. The DT_NEEDED entries will be created in the order in which they appear on the command line.
-H ident
Add an identifier string to the output file. This is intended for use with make, where the identifier can be a pattern string, used to prevent relinking if the inputs have not changed.
-i
Perform a partial link. This is equivalent to the -r option.
-j section
Keep only a section named section in the output file. This is only supported for COFF output formats.
-Kname

This option is used to control the dynamic linking of shared libraries. The specific behavior depends on the target platform.

-Khash
On systems with a /usr/lib/libhash.so library, this option is equivalent to linking with "-lhash".
-Kpic
Generate position-independent code. This is equivalent to "-fPIC" for C, but it can also affect other languages.
-Kcommon
Do not merge common symbols. This is equivalent to "-non-shared" when linking shared libraries.
-Knocommon
Do not allocate space for common symbols. This is equivalent to "-Bsymbolic" when linking shared libraries.

These options are provided for compatibility with other linkers.

-l names
Add a library to the list of libraries to link. The linker searches for files named "lib%s.a", where %s is the library name specified. Libraries specified with this option are searched for after all libraries specified by other options. This option is also available for dynamic objects.
-L path
Add directory to the list of directories where the linker searches for libraries. Only affects libraries specified with the -l option.
-m emulation
Set the linker emulation. For example, on a SPARC, you can use "-m le" to link little-endian objects. This option affects the default output format, and can be used to select between different target configurations.
-M
Produce a map file. The map file lists the sections of the output file, and their addresses. This option is only supported for PE targets.
-n
Copy initialized data and code into the text section. This is only for binary formats that do not distinguish between code and data.
-N
This option is equivalent to the script command "FORCE_COMMON_ALLOCATION". It is used to assign space to common symbols even if a relocatable output file is specified (with -r). This option is deprecated.
-O format
Specify the output binary file format. The default is to infer the format from the target system. You can list the available formats with objdump -i.
-o outfile
Use outfile as the name for the output file. The default name is "a.out" or "core".
-p
Perform a partial link. This is equivalent to the -r option.
-r
Produce a relocatable output file. This is used to link multiple object files together, without producing a final executable. This option is equivalent to the -i and -p options.
-s
Remove all symbol table information from the output file. This is useful for reducing the size of the executable.
-S
Remove all debugging information from the output file. This is useful for reducing the size of the executable.
-t
--trace-symbol=symbol
Trace the symbol symbol. This will cause the linker to print a message every time the symbol is referenced. This is useful for debugging dynamic linking problems.
-T text
Use text as the linker script. The linker script is written in the general-purpose ld scripting language. This option can be specified multiple times. Linker scripts are used to control the memory layout of the output file, and the placement of sections.
-u symbol
Enter symbol in the output file's symbol table, even if it is not otherwise referenced. This is useful for linking with libraries that expect certain symbols to be defined. This option can be specified multiple times.
-v

href="#filter=">--filter=nom
Lors de la création d'un objet partagé ELF, définit le champ interne DT_FILTER sur le nom spécifié. Cela indique à l'éditeur de liens dynamique que la table des symboles de l'objet partagé qui est créé doit être utilisée comme filtre pour la table des symboles de l'objet partagé nom.

Si vous liez ultérieurement un programme à cet objet filtre, alors, lors de l'exécution du programme, l'éditeur de liens dynamique verra le champ DT_FILTER. L'éditeur de liens dynamique résoudra les symboles selon la table des symboles de l'objet filtre comme d'habitude, mais il se liera en fait aux définitions trouvées dans l'objet partagé nom. Ainsi, l'objet filtre peut être utilisé pour sélectionner un sous-ensemble des symboles fournis par l'objet nom.

Certains éditeurs de liens plus anciens utilisaient l'option -F tout au long d'une chaîne d'outils de compilation pour spécifier le format de fichier objet pour les fichiers objets d'entrée et de sortie. L'éditeur de liens GNU utilise d'autres mécanismes à cette fin : les options -b, --format, --oformat, la commande "TARGET" dans les scripts de l'éditeur de liens, et la variable d'environnement "GNUTARGET". L'éditeur de liens GNU ignorera l'option -F lorsqu'il ne crée pas d'objet partagé ELF.

-fini=nom
Lors de la création d'un exécutable ou d'un objet partagé ELF, appelle NOM lorsque l'exécutable ou l'objet partagé est déchargé, en définissant DT_FINI à l'adresse de la fonction. Par défaut, l'éditeur de liens utilise "_fini" comme fonction à appeler.
-g
Ignoré. Fourni pour la compatibilité avec d'autres outils.
-G valeur
--gpsize=valeur
Définit la taille maximale des objets à optimiser en utilisant le registre GP à taille. Ceci n'est significatif que pour les formats de fichiers objets tels que MIPS ELF qui prennent en charge la mise de grands et petits objets dans différentes sections. Ceci est ignoré pour les autres formats de fichiers objets.
-h nom
-soname=nom
Lors de la création d'un objet partagé ELF, définit le champ interne DT_SONAME sur le nom spécifié. Lorsqu'un exécutable est lié à un objet partagé qui a un champ DT_SONAME, alors lors de l'exécution de l'exécutable, l'éditeur de liens dynamique tentera de charger l'objet partagé spécifié par le champ DT_SONAME plutôt que d'utiliser le nom de fichier donné à l'éditeur de liens.
-i
Effectue une liaison incrémentielle (identique à l'option -r).
-init=nom
Lors de la création d'un exécutable ou d'un objet partagé ELF, appelle NOM lorsque l'exécutable ou l'objet partagé est chargé, en définissant DT_INIT à l'adresse de la fonction. Par défaut, l'éditeur de liens utilise "_init" comme fonction à appeler.
-l spécification_nom
--library=spécification_nom
Ajoute l'archive ou le fichier objet spécifié par spécification_nom à la liste des fichiers à lier. Cette option peut être utilisée un nombre illimité de fois. Si spécification_nom est de la forme :nom_fichier, ld recherchera dans le chemin de bibliothèques un fichier nommé nom_fichier, sinon il recherchera dans le chemin de bibliothèques un fichier nommé libspécification_nom.a.

Sur les systèmes qui prennent en charge les bibliothèques partagées, ld peut également rechercher des fichiers autres que libspécification_nom.a. Spécifiquement, sur les systèmes ELF et SunOS, ld recherchera dans un répertoire une bibliothèque nommée libspécification_nom.so avant de rechercher celle nommée libspécification_nom.a. (Par convention, une extension ".so" indique une bibliothèque partagée.) Notez que ce comportement ne s'applique pas à :nom_fichier, qui spécifie toujours un fichier nommé nom_fichier.

L'éditeur de liens recherchera une archive une seule fois, à l'emplacement où elle est spécifiée sur la ligne de commande. Si l'archive définit un symbole qui était indéfini dans certains objets qui apparaissaient avant l'archive sur la ligne de commande, l'éditeur de liens inclura les fichiers appropriés de l'archive. Cependant, un symbole indéfini dans un objet apparaissant plus tard sur la ligne de commande ne forcera pas l'éditeur de liens à rechercher à nouveau l'archive.

Voir l'option -( pour une façon de forcer l'éditeur de liens à rechercher les archives plusieurs fois.

Vous pouvez spécifier la même archive plusieurs fois sur la ligne de commande.

Ce type de recherche d'archives est standard pour les éditeurs de liens Unix. Cependant, si vous utilisez ld sur AIX, notez qu'il est différent du comportement de l'éditeur de liens AIX.

-L répertoire_recherche
--library-path=répertoire_recherche
Ajoute le chemin répertoire_recherche à la liste des chemins que ld utilisera pour rechercher les bibliothèques d'archives et les scripts de contrôle de ld. Vous pouvez utiliser cette option un nombre illimité de fois. Les répertoires sont recherchés dans l'ordre où ils sont spécifiés sur la ligne de commande. Les répertoires spécifiés sur la ligne de commande sont recherchés avant les répertoires par défaut. Toutes les options -L s'appliquent à toutes les options -l, quelle que soit l'ordre d'apparition des options. Les options -L n'affectent pas la manière dont ld recherche un script d'éditeur de liens à moins que l'option -T ne soit spécifiée.

Si répertoire_recherche commence par "=" ou $SYSROOT, alors ce préfixe sera remplacé par le préfixe sysroot, contrôlé par l'option --sysroot, ou spécifié lors de la configuration de l'éditeur de liens.

L'ensemble par défaut des chemins recherchés (sans être spécifiés avec -L) dépend du mode d'émulation que ld utilise, et dans certains cas également de la manière dont il a été configuré.

Les chemins peuvent également être spécifiés dans un script de liaison avec la commande "SEARCH_DIR". Les répertoires spécifiés de cette manière sont recherchés au point où le script de liaison apparaît sur la ligne de commande.

-m émulation
Émule l'éditeur de liens émulation. Vous pouvez lister les émulations disponibles avec les options --verbose ou -V.

Si l'option -m n'est pas utilisée, l'émulation est tirée de la variable d'environnement "LDEMULATION", si celle-ci est définie.

Sinon, l'émulation par défaut dépend de la manière dont l'éditeur de liens a été configuré.

--remap-inputs=motif=nom_fichier
--remap-inputs-file=fichier
Ces options permettent de modifier les noms des fichiers d'entrée avant que l'éditeur de liens ne tente de les ouvrir. L'option --remap-inputs=foo.o=bar.o fera en sorte que toute tentative de chargement d'un fichier nommé foo.o essaie plutôt de charger un fichier nommé bar.o. Les motifs génériques sont autorisés dans le premier nom de fichier, donc --remap-inputs=foo*.o=bar.o renommera tout fichier d'entrée qui correspond à foo*.o en bar.o.

Une forme alternative de l'option --remap-inputs-file=nom_fichier permet de lire les remappages à partir d'un fichier. Chaque ligne du fichier peut contenir un seul remappage. Les lignes vides sont ignorées. Tout ce qui suit un caractère dièse (#) jusqu'à la fin de la ligne est considéré comme un commentaire et est également ignoré. Le motif de mappage peut être séparé du nom de fichier par un espace blanc ou un caractère égal (=).

Les options peuvent être spécifiées plusieurs fois. Leur contenu s'accumule. Les remappages seront traités dans l'ordre où ils apparaissent sur la ligne de commande, et s'ils proviennent d'un fichier, dans l'ordre où ils apparaissent dans le fichier. Si une correspondance est trouvée, aucune vérification supplémentaire pour ce nom de fichier ne sera effectuée.

Si le nom de fichier de remplacement est /dev/null ou simplement NUL, le remappage provoquera en fait l'ignorance du fichier d'entrée. Cela peut être un moyen pratique d'expérimenter en supprimant des fichiers d'entrée d'un environnement de build compliqué.

Notez que cette option dépend de la position et n'affecte que les noms de fichiers qui la suivent sur la ligne de commande. Ainsi :

ld foo.o --remap-inputs=foo.o=bar.o

N'aura aucun effet, tandis que :

ld --remap-inputs=foo.o=bar.o foo.o

Renommera le fichier d'entrée foo.o en bar.o.

Remarque : ces options affectent également les fichiers référencés par les instructions INPUT dans les scripts de l'éditeur de liens. Mais comme les scripts de l'éditeur de liens sont traités après que toute la ligne de commande a été lue, la position des options de remappage sur la ligne de commande n'est pas significative.

Si l'option verbose est activée, alors tout remappage correspondant sera signalé, bien que là encore, l'option verbose doive être activée sur la ligne de commande avant que les noms de fichiers remappés n'apparaissent.

Si les options -Map ou --print-map sont activées, alors la liste de remappage sera incluse dans la sortie de la carte.

-M
--print-map
Imprime une carte de liaison sur la sortie standard. Une carte de liaison fournit des informations sur la liaison, notamment les éléments suivants :
  • Où les fichiers objets sont mappés en mémoire.
  • Comment les symboles communs sont alloués.
  • Tous les membres d'archive inclus dans la liaison, avec une mention du symbole qui a causé l'inclusion du membre d'archive.
  • Les valeurs attribuées aux symboles.

    Remarque : les symboles dont les valeurs sont calculées par une expression qui implique une référence à une valeur précédente du même symbole peuvent ne pas avoir le résultat correct affiché dans la carte de liaison. Ceci est dû au fait que l'éditeur de liens rejette les résultats intermédiaires et ne conserve que la valeur finale de une expression. Dans de telles circonstances, l'éditeur de liens affichera la valeur finale entourée de crochets. Ainsi, par exemple, un script d'éditeur de liens contenant :

    foo = 1
foo = foo * 4
foo = foo + 8

    produira la sortie suivante dans la carte de liaison si l'option -M est utilisée :

    0x00000001                foo = 0x1
[0x0000000c]                foo = (foo * 0x4)
[0x0000000c]                foo = (foo + 0x8)

    Voir Expressions

b> pour plus d'informations sur les expressions dans les scripts de liaison.

  • Comment les propriétés GNU sont fusionnées.

    Lorsque la liaison fusionne les sections .note.gnu.property d'entrée en une seule section .note.gnu.property de sortie, certaines propriétés sont supprimées ou mises à jour. Ces actions sont rapportées dans la carte de liaison. Par exemple :

    Propriété supprimée 0xc0000002 pour fusionner foo.o (0x1) et bar.o (introuvable)

    Cela indique que la propriété 0xc0000002 est supprimée de la sortie lors de la fusion des propriétés dans foo.o, dont la valeur de la propriété 0xc0000002 est 0x1, et bar.o, qui n'a pas la propriété 0xc0000002.

    Propriété mise à jour 0xc0010001 (0x1) pour fusionner foo.o (0x1) et bar.o (0x1)

    Cela indique que la valeur de la propriété 0xc0010001 est mise à jour à 0x1 en sortie lors de la fusion des propriétés dans foo.o, dont la valeur de la propriété 0xc0010001 est 0x1, et bar.o, dont la valeur de la propriété 0xc0010001 est 0x1.

  • Sur certaines cibles ELF, une liste de corrections insérées par --relax 
    foo.o : Ajustement de la branche à 0x00000008 vers "far" dans la section .text

    Cela indique que la branche à 0x00000008 dans foo.o, ciblant le symbole "far" dans la section .text, a été remplacée par un trampoline.

    --output=sortie
    Utiliser sortie comme nom du programme produit par ld ; si cette option n'est pas spécifiée, le nom a.out est utilisé par défaut. La commande de script "OUTPUT" peut également spécifier le nom du fichier de sortie.

    --dependency-file=depfile
    Écrire un fichier de dépendances dans depfile. Ce fichier contient une règle adaptée à "make" décrivant le fichier de sortie et tous les fichiers d'entrée qui ont été lus pour le produire. La sortie est similaire à la sortie du compilateur avec -M -MP. Notez qu'il n'y a pas d'option comme le -MM du compilateur, pour exclure les "fichiers système" (ce qui n'est pas un concept bien défini dans le programme de liaison, contrairement aux "en-têtes système" dans le compilateur). Ainsi, la sortie de --dependency-file est toujours spécifique à l'état exact de l'installation où elle a été produite, et ne doit pas être copiée dans les makefiles distribués sans modification attentive.
    -O niveau
    Si niveau est une valeur numérique supérieure à zéro, ld optimise la sortie. Cela peut prendre beaucoup plus de temps et ne devrait donc probablement être activé que pour le binaire final. Pour le moment, cette option n'affecte que la génération de bibliothèques partagées ELF. Les futures versions du programme de liaison pourraient utiliser davantage cette option. De plus, il n'y a actuellement aucune différence dans le comportement du programme de liaison pour différentes valeurs non nulles de cette option. Encore une fois, cela pourrait changer dans les futures versions.
    -plugin nom
    Impliquer un plugin dans le processus de liaison. Le paramètre nom est le nom de fichier absolu du plugin. Généralement, ce paramètre est automatiquement ajouté par le compilateur lors de l'utilisation de l'optimisation au moment de la liaison, mais les utilisateurs peuvent également ajouter leurs propres plugins s'ils le souhaitent.

    Notez que l'emplacement des plugins originaires du compilateur est différent de l'endroit où les programmes ar, nm et ranlib recherchent leurs plugins. Pour que ces commandes utilisent un plugin basé sur le compilateur, il doit d'abord être copié dans le répertoire ${libdir}/bfd-plugins. Tous les plugins de liaison basés sur gcc sont rétrocompatibles, il suffit donc de copier le plus récent.

    -r
    --relocatable
    Générer une sortie déplaçable (relocatable) --- c'est-à-dire, générer un fichier de sortie qui peut à son tour servir d'entrée à ld. Ceci est souvent appelé liaison partielle. Comme effet secondaire, dans les environnements qui prennent en charge les nombres magiques standard de Unix, cette option définit également le nombre magique du fichier de sortie à "OMAGIC". Si cette option n'est pas spécifiée, un fichier absolu est produit. Lors de la liaison de programmes C++, cette option ne résoudra pas les références aux constructeurs ; pour ce faire, utilisez -Ur.

Lors du traitement d'une entrée déplaçable avec une section .gnu_object_only, le programme de liaison extraira la section .gnu_object_only comme une entrée distincte.

    -( archives -)
    --start-group archives --end-group
    Les archives doivent être une liste de fichiers d'archives. Ils peuvent être soit des noms de fichiers explicites, soit des options -l.

    Les archives spécifiées sont recherchées de manière répétée jusqu'à ce qu'aucun nouveau symbole non résolu ne soit créé. Normalement, une archive n'est recherchée qu'une seule fois dans l'ordre où elle est spécifiée sur la ligne de commande. Si un symbole dans cette archive est nécessaire pour résoudre un symbole non résolu référencé par un objet dans une archive qui apparaît plus tard sur la ligne de commande, l'éditeur de liens ne pourrait pas résoudre cette référence. En regroupant les archives, elles seront toutes recherchées de manière répétée jusqu'à ce que toutes les références possibles soient résolues.

    L'utilisation de cette option a un coût de performance significatif. Il est préférable de l'utiliser uniquement lorsqu'il existe des références circulaires inévitables entre deux archives ou plus.

    --accept-unknown-input-arch
    --no-accept-unknown-input-arch
    Indique à l'éditeur de liens d'accepter les fichiers d'entrée dont l'architecture ne peut pas être reconnue. L'hypothèse est que l'utilisateur sait ce qu'il fait et souhaite délibérément lier ces fichiers d'entrée inconnus. C'était le comportement par défaut de l'éditeur de liens, avant la version 2.14. Le comportement par défaut à partir de la version 2.14 est de rejeter de tels fichiers d'entrée, et donc l'option --accept-unknown-input-arch a été ajoutée pour rétablir l'ancien comportement.
    --as-needed
    dd>
    --no-as-needed
    Cette option affecte les étiquettes DT_NEEDED ELF pour les bibliothèques dynamiques mentionnées sur la ligne de commande après l'option --as-needed. Normalement, l'éditeur de liens ajoute une étiquette DT_NEEDED pour chaque bibliothèque dynamique mentionnée sur la ligne de commande, qu'elle soit réellement nécessaire ou non. --as-needed fait qu'une étiquette DT_NEEDED n'est émise que pour une bibliothèque qui, *à ce point du lien*, satisfait une référence à un symbole indéfini non faible provenant d'un fichier objet régulier ou, si la bibliothèque n'est pas trouvée dans les listes DT_NEEDED d'autres bibliothèques nécessaires, une référence à un symbole indéfini non faible provenant d'une autre bibliothèque dynamique nécessaire. Les fichiers objets ou les bibliothèques apparaissant sur la ligne de commande *après* la bibliothèque en question n'affectent pas si la bibliothèque est considérée comme nécessaire. Ceci est similaire aux règles d'extraction des fichiers objets des archives. --no-as-needed restaure le comportement par défaut.

    --cref
    Produire une table de références croisées. Si un fichier de carte de l'éditeur de liens est généré, la table de références croisées est imprimée dans le fichier de carte. Sinon, elle est imprimée sur la sortie standard.

    Le format de la table est intentionnellement simple, de sorte qu'il puisse être facilement traité par un script si nécessaire. Les symboles sont imprimés, triés par nom. Pour chaque symbole, une liste de noms de fichiers est donnée. Si le symbole est défini, le premier fichier listé est l'emplacement de la définition. Si le symbole est défini comme une valeur commune, alors les fichiers où cela se produit apparaissent ensuite. Enfin, les fichiers qui référencent le symbole sont listés.

    --ctf-variables
    --no-ctf-variables
    Le format d'informations de débogage CTF prend en charge une section qui encode les noms et les types des variables trouvées dans le programme qui n'apparaissent dans aucune table de symboles. Ces variables ne peuvent clairement pas être recherchées par adresse par les débogueurs conventionnels, de sorte que l'espace utilisé pour leurs types et leurs noms est généralement perdu : les types sont généralement petits mais les noms ne le sont souvent pas. --ctf-variables provoque la génération d'une telle section.     Pour un éditeur de liens ELF natif, les répertoires dans "DT_RUNPATH" ou "DT_RPATH" d'une bibliothèque partagée sont recherchés pour les bibliothèques partagées dont elle a besoin. Les entrées "DT_RPATH" sont ignorées si des entrées "DT_RUNPATH" existent.
    7.
    Pour un éditeur de liens pour un système Linux, si le fichier /etc/ld.so.conf existe, la liste des répertoires trouvés dans ce fichier. Remarque : le chemin de ce fichier est préfixé par la valeur "sysroot", si elle est définie, puis par toute chaîne "prefix" si l'éditeur de liens a été configuré avec l'option --prefix=<path>.
    8.
    Pour un éditeur de liens natif sur un système FreeBSD, tous les répertoires spécifiés par la macro "_PATH_ELF_HINTS" définie dans le fichier d'en-tête elf-hints.h.
    9.
    Tous les répertoires spécifiés par une commande "SEARCH_DIR" dans un script d'édition de liens fourni sur la ligne de commande, y compris les scripts spécifiés par -T (mais pas par -dT).
    10.
    Les répertoires par défaut, normalement /lib et /usr/lib.
    11.
    Tous les répertoires spécifiés par un plugin LDPT_SET_EXTRA_LIBRARY_PATH.
    12.
    Tous les répertoires spécifiés par une commande "SEARCH_DIR" dans un script d'édition de liens par défaut.

    Notez cependant que sur les systèmes basés sur Linux, il y a une mise en garde supplémentaire : Si l'option --as-needed est active *et* qu'une bibliothèque partagée est trouvée qui satisferait normalement la recherche *et* que cette bibliothèque n'a pas de tag DT_NEEDED pour libc.so *et* qu'il y a une bibliothèque partagée plus loin dans l'ensemble des répertoires de recherche qui satisfait également la recherche *et* que cette seconde bibliothèque a un tag DT_NEEDED pour libc.so *alors* la seconde bibliothèque sera sélectionnée à la place de la première.

    Si la bibliothèque partagée requise n'est pas trouvée, l'éditeur de liens émettra un avertissement et poursuivra l'édition de liens.

    --section-ordering-file=script
    Cette option est utilisée pour augmenter le script d'édition de liens actuel avec un mappage supplémentaire des sections d'entrée aux sections de sortie. Ce fichier doit utiliser la même syntaxe pour "SECTIONS" que celle utilisée dans les scripts d'édition de liens normaux, mais il ne doit rien faire d'autre que de placer les sections d'entrée dans les sections de sortie. @pxref{SECTIONS}

    Une deuxième contrainte sur le script d'ordonnancement des sections est qu'il ne peut référencer que des sections de sortie déjà définies par le script d'édition de liens actuellement utilisé. (C'est-à-dire le script d'édition de liens par défaut ou un script spécifié sur la ligne de commande). L'avantage du script d'ordonnancement des sections est cependant qu'il peut être utilisé pour mapper les sections d'entrée au début des sections de sortie, de sorte qu'il puisse assurer l'ordonnancement des sections dans la section de sortie. Par exemple, imaginez que le script d'édition de liens par défaut ressemble à ceci :

    SECTIONS {
  .text : { *(.text.hot) ; *(.text .text.*) }
  .data : { *(.data.big) ; *(.data .data.*) }
  }

    Ensuite, si un fichier d'ordonnancement de sections comme celui-ci est utilisé :

    .text : { *(.text.first) ; *(.text.z*) }
.data : { foo.o(.data.first) ; *(.data.small) }

    Cela équivaudrait à un script d'édition de liens comme celui-ci :

    SECTIONS {
  .text : { *(.text.first) ; *(.text.z*) ; *(.text.hot) ; *(.text .text.*) }
  .data : { foo.o(.data.first) ; *(.data.small) ; *(.data.big) ; *(.data .data.*) }
  }

    L'avantage du fichier d'ordonnancement des sections est qu'il peut être utilisé pour ordonnancer les sections qui importent à l'utilisateur sans avoir à se soucier des autres sections, ou des régions mémoire, ou de quoi que ce soit d'autre.

    -shared
    -Bshareable
    Créer une bibliothèque partagée. Ceci n'est actuellement pris en charge que sur les plates-formes ELF, XCOFF et SunOS. Sur SunOS, l'éditeur de liens créera automatiquement une bibliothèque partagée si l'option -e n'est pas utilisée et qu'il y a des symboles indéfinis dans le lien.
    --sort-common
    --sort-common=ascending
    --sort-common=descending
    Cette option indique à ld de trier les symboles communs par alignement dans l'ordre croissant ou décroissant lors de leur placement dans les sections de sortie appropriées. Les alignements de symboles considérés sont de seize octets ou plus, de huit octets, de quatre octets, de deux octets et d'un octet. Ceci afin d'éviter les écarts entre les symboles dus aux contraintes d'alignement. Si aucun ordre de tri n'est spécifié, l'ordre décroissant est supposé.
    --sort-section=name
    Cette option appliquera "SORT_BY_NAME" à tous les modèles de sections génériques dans le script d'édition de liens.
    --sort-section=alignment
    Cette option appliquera "SORT_BY_ALIGNMENT" à tous les modèles de sections génériques dans le script d'édition de liens.
    --spare-dynamic-tags=count
    Cette option spécifie le nombre d'emplacements vides à laisser dans la section .dynamic des objets partagés ELF. Des emplacements vides peuvent être nécessaires pour les outils de post-traitement, tels que le pré-éditeur de liens. La valeur par défaut est 5.
    --split-by-file[=size]
    Similaire à --split-by-reloc mais crée une nouvelle section de sortie pour chaque fichier d'entrée lorsque size est atteint. size vaut par défaut 1 s'il n'est pas donné.
    --split-by-reloc[=count]
    Tente de créer des sections supplémentaires dans le fichier de sortie de sorte qu'aucune section de sortie unique dans le fichier ne contienne plus de count relocations. Ceci est utile lors de la génération de fichiers déplaçables énormes pour le téléchargement dans certains noyaux temps réel avec le format de fichier objet COFF ; car COFF ne peut pas représenter plus de 65535 relocations dans une seule section. Notez que cela ne fonctionnera pas avec les formats de fichiers objets qui ne prennent pas en charge les sections arbitraires. L'éditeur de liens ne divisera pas les sections d'entrée individuelles pour la redistribution, donc si une section d'entrée contient plus de count relocations, une section de sortie en contiendra ce nombre. count vaut par défaut 32768.
    --stats
    Calcule et affiche des statistiques sur le fonctionnement de l'éditeur de liens, telles que le temps d'exécution et l'utilisation de la mémoire.
    --sysroot=directory
    Utilise directory comme emplacement du sysroot, remplaçant la valeur par défaut au moment de la configuration. Cette option n'est prise en charge que
    par des éditeurs qui ont été configurés avec --with-sysroot.
    --task-link
    Ceci est utilisé par les cibles basées sur COFF/PE pour créer un fichier objet lié à une tâche où tous les symboles globaux ont été convertis en statiques.
    --traditional-format
    Pour certaines cibles, la sortie de ld diffère à certains égards de la sortie de certains éditeurs existants. Ce commutateur demande à ld d'utiliser le format traditionnel à la place.

    Par exemple, sur SunOS, ld combine les entrées dupliquées dans la table des chaînes de symboles. Cela peut réduire la taille d'un fichier de sortie avec des informations de débogage complètes de plus de 30 pour cent. Malheureusement, le programme SunOS "dbx" ne peut pas lire le programme résultant ("gdb" n'a aucun problème). Le commutateur --traditional-format indique à ld de ne pas combiner les entrées dupliquées.

    --section-start=nomsection=org
    Place une section dans le fichier de sortie à l'adresse absolue donnée par org. Vous pouvez utiliser cette option autant de fois que nécessaire pour placer plusieurs sections dans la ligne de commande. org doit être un entier hexadécimal unique ; pour la compatibilité avec d'autres éditeurs, vous pouvez omettre le préfixe 0x généralement associé aux valeurs hexadécimales. Note : il ne doit y avoir aucun espace entre nomsection, le signe égal ("=") et org.
    --image-base=org
    Lors de l'utilisation d'ELF, identique à -Ttext-segment, les deux options définissant effectivement l'adresse de base de l'exécutable ELF.

    Lors de l'utilisation de PE, utilisez valeur comme adresse de base de votre programme ou DLL. C'est le plus petit emplacement mémoire qui sera utilisé lors du chargement de votre programme ou DLL. Pour réduire le besoin de relocalisation et améliorer les performances de vos DLL, chacune doit avoir une adresse de base unique et ne pas chevaucher d'autres DLL. La valeur par défaut est 0x400000 pour les exécutables, et 0x10000000 pour les DLL.

    -Tbss=org
    -Tdata=org
    -Ttext=org
    Identique à --section-start, avec ".bss", ".data" ou ".text" comme nomsection.
    -Ttext-segment=org
    Lors de la création d'un exécutable ELF, définit l'adresse du premier octet du premier segment. Notez que lorsque -pie est utilisé avec -Ttext-segment=org, l'exécutable de sortie est marqué ET_EXEC de sorte que l'adresse du premier octet du segment de texte sera garantie d'être org à l'exécution.
    -Trodata-segment=org
    Lors de la création d'un exécutable ELF ou d'un objet partagé pour une cible où les données en lecture seule se trouvent dans son propre segment, séparé du texte exécutable, il définit l'adresse du premier octet du segment de données en lecture seule.
    -Tldata-segment=org
    Lors de la création d'un exécutable ELF ou d'un objet partagé pour un modèle de mémoire moyenne x86-64, il définit l'adresse du premier octet du segment de données ldata.
    --unresolved-symbols=méthode
    Détermine comment gérer les symboles non résolus. Il existe quatre valeurs possibles pour méthode :
    ignore-all
    Ne signale aucun symbole non résolu.
    report-all
    Signale tous les symboles non résolus. C'est la valeur par défaut.
    ignore-in-object-files
    Signale les symboles non résolus contenus dans les fichiers objets partagés, mais les ignore s'ils proviennent de fichiers objets réguliers.
    ignore-in-shared-libs
    Signale les symboles non résolus provenant de fichiers objets réguliers, mais les ignore s'ils proviennent de bibliothèques partagées. Cela peut être utile lors de la création d'une binaire dynamique où l'on sait que toutes les bibliothèques partagées auxquelles elle devrait faire référence sont incluses dans la ligne de commande de l'éditeur.

    Le comportement pour les bibliothèques partagées seules peut également être contrôlé par l'option --[no-]allow-shlib-undefined.

    Normalement, l'éditeur générera un message d'erreur pour chaque symbole non résolu signalé, mais l'option --warn-unresolved-symbols peut changer cela en un avertissement.

    --dll-verbose
    --verbose[=NOMBRE]
    Affiche le numéro de version de ld et liste les émulations d'éditeur prises en charge. Affiche quels fichiers d'entrée peuvent être ouverts et lesquels ne le peuvent pas. Affiche le script de l'éditeur utilisé par l'éditeur. Si l'argument optionnel NOMBRE est > 1, l'état des symboles des plugins sera également affiché.
    --version-script=fichier-script-version
    Spécifie le nom d'un script de version à l'éditeur. Ceci est généralement utilisé lors de la création de bibliothèques partagées pour spécifier des informations supplémentaires sur la hiérarchie des versions de la bibliothèque créée. Cette option n'est entièrement prise en charge que sur les plateformes ELF qui prennent en charge les bibliothèques partagées ; voir VERSION. Elle est partiellement prise en charge sur les plateformes PE, qui peuvent utiliser des scripts de version pour filtrer la visibilité des symboles en mode d'exportation automatique : tous les symboles marqués local dans le script de version ne seront pas exportés.
    --warn-common
    Avertit lorsqu'un symbole commun est combiné avec un autre symbole commun ou avec une définition de symbole. Les éditeurs Unix autorisent cette pratique quelque peu négligente, mais les éditeurs sur certains autres systèmes d'exploitation ne le font pas. Cette option vous permet de détecter les problèmes potentiels liés à la combinaison de symboles globaux. Malheureusement, certaines bibliothèques C utilisent cette pratique, vous pouvez donc recevoir des avertissements concernant des symboles dans les bibliothèques ainsi que dans vos programmes.

    Il existe trois types de symboles globaux, illustrés ici par des exemples en C :

    int i = 1;
    Une définition, qui va dans la section des données initialisées du fichier de sortie.
    extern int i;
    Une référence indéfinie, qui n'alloue pas d'espace. Il doit y avoir soit une définition, soit un symbole commun pour la variable quelque part.
    int i;
    Un symbole commun. S'il n'y a que (un ou plusieurs) symboles communs pour une variable, elle va dans la zone de données non initialisées du fichier de sortie. L'éditeur fusionne plusieurs symboles communs pour la même variable en un seul symbole. S'ils sont de tailles différentes, il choisit la taille la plus grande. L'éditeur transforme un symbole commun en une déclaration, s'il existe une définition de la même variable.

    L'option --warn-common peut produire cinq types d'avertissements. Chaque avertissement consiste en une paire de lignes : la première décrit le symbole qui vient d'être rencontré, et la seconde décrit le symbole précédent rencontré avec le même nom. Un ou les deux symboles seront un symbole commun.

    1.
    Transformation d'un symbole commun en référence, car il existe déjà une définition pour le symbole. 
    <fichier>(<section>): avertissement : commun de `<symbole>'
   remplacé par une définition
<fichier>(<section>): avertissement : défini ici
    2.
    Transformation d'un symbole commun en référence, car une définition ultérieure du symbole est rencontrée. C'est le même cas que le précédent, sauf que les symboles sont rencontrés dans un ordre différent. 
    <fichier>(<section>): avertissement : définition de `<symbole>'
   remplaçant un commun
<fichier>(<section>): avertissement : le commun est ici
    3.
    Fusion d'un symbole commun avec un symbole commun précédent de même taille. 
    <fichier>(<section>): avertissement : multiples communs
   de `<symbole>'
<fichier>(<section>): avertissement : le commun précédent est ici
    4.
    Fusion d'un symbole commun avec un symbole commun précédent plus grand. 
    <fichier>(<section>): avertissement : commun de `<symbole>'
   remplacé par un commun plus grand
<fichier>(<section>): avertissement : le commun plus grand est ici
    5.
    Fusion d'un symbole commun avec un symbole commun précédent plus petit. C'est le même cas que le précédent, sauf que les symboles sont rencontrés dans un ordre différent. 
    <fichier>(<section>): avertissement : commun de `<symbole>'
   remplaçant un commun plus petit
<fichier>(<section>): avertissement : le commun plus petit est ici
    --warn-constructors
    Avertit si des constructeurs globaux sont utilisés. Ceci n'est utile que pour quelques formats de fichiers objets. Pour les formats comme COFF ou ELF, l'éditeur ne peut pas détecter l'utilisation de constructeurs globaux.
    --warn-execstack
    --warn-execstack-objects
    --no-warn-execstack
    Sur les plateformes ELF, l'éditeur peut générer des messages d'avertissement s'il est demandé de créer un fichier de sortie contenant une pile exécutable. Il existe trois états possibles :
    1.
    Ne générer aucun avertissement.
    2.
    Générer toujours des avertissements, même si la pile exécutable est demandée via l'option de ligne de commande -z execstack.
    3.
    Générer un avertissement uniquement si un fichier objet demande une pile exécutable, mais pas si l'option -z execstack est utilisée.

    L'état par défaut dépend de la manière dont l'éditeur a été configuré lors de sa construction. L'option --no-warn-execstack place toujours l'éditeur dans l'état sans avertissement. L'option --warn-execstack place l'éditeur dans l'état d'avertissement systématique. L'option --warn-execstack-objects place l'éditeur dans l'état d'avertissement uniquement pour les fichiers objets.

    Note : Les fichiers d'entrée au format ELF peuvent spécifier que la

    y ont besoin d'une pile exécutable en ayant une section .note.GNU-stack avec le bit exécutable défini dans ses drapeaux de section. Ils peuvent spécifier qu'ils n'ont pas besoin d'une pile exécutable en ayant la même section, mais sans le bit de drapeau exécutable défini. Si un fichier d'entrée n'a pas de section .note.GNU-stack, alors le comportement par défaut est spécifique à la cible. Pour certaines cibles, l'absence d'une telle section implique qu'une pile exécutable *est* requise. Ceci est souvent un problème pour les fichiers assembleur créés manuellement.

    --error-execstack
    --no-error-execstack
    Si l'éditeur de liens doit générer un message d'avertissement concernant une pile exécutable, l'option --error-execstack transformera cet avertissement en une erreur. Remarque : cette option ne modifie pas l'état de génération des avertissements de l'éditeur de liens concernant la pile exécutable. Utilisez --warn-execstack ou --warn-execstack-objects pour définir un état d'avertissement spécifique.

    L'option --no-error-execstack rétablira le comportement par défaut consistant à générer des messages d'avertissement.

    --warn-multiple-gp
    Avertir si plusieurs valeurs de pointeur global sont nécessaires dans le fichier de sortie. Ceci n'est pertinent que pour certains processeurs, comme l'Alpha. Spécifiquement, certains processeurs placent des constantes de grande valeur dans une section spéciale. Un registre spécial (le pointeur global) pointe vers le milieu de cette section, de sorte que les constantes peuvent être chargées efficacement via un mode d'adressage relatif au registre de base. Comme le décalage en mode relatif au registre de base est fixe et relativement petit (par exemple, 16 bits), cela limite la taille maximale du pool de constantes. Ainsi, dans les grands programmes, il est souvent nécessaire d'utiliser plusieurs valeurs de pointeur global afin de pouvoir adresser toutes les constantes possibles. Cette option provoque un avertissement chaque fois que ce cas se produit.
    --warn-once
    Avertir une seule fois pour chaque symbole non défini, plutôt qu'une fois par module qui y fait référence.
    --warn-rwx-segments
    --no-warn-rwx-segments
    Avertir si l'éditeur de liens crée un segment chargeable de taille non nulle qui possède les trois indicateurs de permission lecture, écriture et exécution. Un tel segment représente une vulnérabilité de sécurité potentielle. De plus, des avertissements seront générés si un segment de stockage local de thread est créé avec l'indicateur de permission d'exécution défini, indépendamment de s'il possède ou non les indicateurs de lecture et/ou d'écriture définis.

    Ces avertissements sont activés par défaut. Ils peuvent être désactivés via l'option --no-warn-rwx-segments et réactivés via l'option --warn-rwx-segments.

    --error-rwx-segments
    --no-error-rwx-segments
    Si l'éditeur de liens doit générer un message d'avertissement concernant un segment exécutable et inscriptible, ou un segment TLS exécutable, alors l'option --error-rwx-segments transformera cet avertissement en erreur. L'option --no-error-rwx-segments rétablira le comportement par défaut consistant à ne générer qu'un message d'avertissement.

    Remarque : l'option --error-rwx-segments n'active pas en elle-même les avertissements concernant ces segments. Ces avertissements sont soit activés par défaut, si l'éditeur de liens a été configuré ainsi, soit via l'option de ligne de commande --warn-rwx-segments.

    --warn-section-align
    Avertir si l'adresse d'une section de sortie est modifiée en raison de l'alignement. Typiquement, l'alignement sera défini par une section d'entrée. L'adresse ne sera modifiée que si elle n'est pas explicitement spécifiée ; c'est-à-dire, si la commande "SECTIONS" ne spécifie pas d'adresse de départ pour la section.
    --warn-textrel
    Avertir si l'éditeur de liens ajoute DT_TEXTREL à un exécutable indépendant de la position ou à un objet partagé.
    --warn-alternate-em
    Avertir si un objet a un code machine ELF alternatif.
    --warn-unresolved-symbols
    Si l'éditeur de liens doit signaler un symbole non résolu (voir l'option --unresolved-symbols), il générera normalement une erreur. Cette option fait qu'il génère un avertissement à la place.
    --error-unresolved-symbols
    Ceci rétablit le comportement par défaut de l'éditeur de liens, qui consiste à générer des erreurs lorsqu'il signale des symboles non résolus.
    --whole-archive
    Pour chaque archive mentionnée sur la ligne de commande après l'option --whole-archive, inclure tous les fichiers objets de l'archive dans la liaison, plutôt que de rechercher dans l'archive les fichiers objets requis. Ceci est normalement utilisé pour transformer un fichier archive en une bibliothèque partagée, forçant chaque objet à être inclus dans la bibliothèque partagée résultante. Cette option peut être utilisée plusieurs fois.

    Deux remarques lors de l'utilisation de cette option avec gcc : Premièrement, gcc ne connaît pas cette option, vous devez donc utiliser -Wl,-whole-archive. Deuxièmement, n'oubliez pas d'utiliser -Wl,-no-whole-archive après votre liste d'archives, car gcc ajoutera sa propre liste d'archives à votre liaison et vous ne voudrez peut-être pas que ce drapeau affecte également celles-ci.

    --wrap=symbole
    Utiliser une fonction de wrapper pour symbole. Toute référence non définie à symbole sera résolue en "__wrap_symbole". Toute référence non définie à "__real_symbole" sera résolue en symbole.

    Ceci peut être utilisé pour fournir un wrapper pour une fonction système. La fonction de wrapper doit être appelée "__wrap_symbole". Si elle souhaite appeler la fonction système, elle doit appeler "__real_symbole".

    Voici un exemple trivial :

    void *
__wrap_malloc (size_t c)
{
  printf ("malloc appelé avec %zu\n", c);
  return __real_malloc (c);
}

    Si vous liez d'autre code avec ce fichier en utilisant --wrap malloc, tous les appels à "malloc" appelleront la fonction "__wrap_malloc" à la place. L'appel à "__real_malloc" dans "__wrap_malloc" appellera la vraie fonction "malloc".

    Vous pourriez vouloir fournir également une fonction "__real_malloc", afin que les liaisons sans l'option --wrap réussissent. Si vous le faites, vous ne devez pas placer la définition de "__real_malloc" dans le même fichier que "__wrap_malloc" ; si vous le faites, l'assembleur peut résoudre l'appel avant que l'éditeur de liens n'ait la chance de le wrapper vers "malloc".

    Seules les références non définies sont remplacées par l'éditeur de liens. Donc, les références internes à l'unité de traduction à symbole ne sont pas résolues en "__wrap_symbole". Dans l'exemple suivant, l'appel à "f" dans "g" n'est pas résolu en "__wrap_f".

    int
f (void)
{
  return 123;
}

int
g (void)
{
  return f();
}
    --eh-frame-hdr
    --no-eh-frame-hdr
    Demander (--eh-frame-hdr) ou supprimer (--no-eh-frame-hdr) la création de la section ".eh_frame_hdr" et de l'en-tête de segment ELF "PT_GNU_EH_FRAME".
    --no-ld-generated-unwind-info
    Demander la création d'informations de déroulement (unwind info) ".eh_frame" pour les sections de code générées par l'éditeur de liens comme PLT. Cette option contrôle également la génération d'informations de trace de pile ".sframe" pour les sections de code générées par l'éditeur de liens comme PLT.
    --enable-new-dtags
    --disable-new-dtags
    Cet éditeur de liens peut créer les nouvelles balises dynamiques en ELF. Mais les anciens systèmes ELF peuvent ne pas les comprendre. Si vous spécifiez --enable-new-dtags, les nouvelles balises dynamiques seront créées au besoin et les anciennes balises dynamiques seront omises. Si vous spécifiez --disable-new-dtags, aucune nouvelle balise dynamique ne sera créée. Par défaut, les nouvelles balises dynamiques ne sont pas créées. Notez que ces options ne sont disponibles que pour les systèmes ELF.
    --hash-size=nombre
    Définir la taille par défaut des tables de hachage de l'éditeur de liens à un nombre premier proche de nombre. Augmenter cette valeur peut réduire le temps nécessaire à l'éditeur de liens pour effectuer ses tâches, au détriment de l'augmentation des besoins en mémoire de l'éditeur de liens. Inversement, réduire cette valeur peut réduire les besoins en mémoire au détriment de la vitesse.
    --hash-style=style
    Définir le type des tables de hachage de l'éditeur de liens. style peut être soit "sysv" pour la section ELF classique ".hash", "gnu" pour la nouvelle section GNU ".gnu.hash", soit "both" pour les deux tables de hachage, la section ELF classique ".hash" et la nouvelle section GNU ".gnu.hash". Le défaut dépend de la configuration de l'éditeur de liens, mais pour la plupart des systèmes basés sur Linux, ce sera "both".
    --compress-debug-sections=none
    --compress-debug-sections=zlib
    --compress-debug-sections=zlib-gnu
    --compress-debug-sections=zlib-gabi
    --compress-debug-sections=zstd
    Sur les plateformes ELF, ces options contrôlent la compression des sections de débogage DWARF à l'aide de zlib.

    --compress-debug-sections=none ne compresse pas les sections de débogage DWARF. --compress-debug-sections=zlib-gnu compresse les sections de débogage DWARF et les renomme pour qu'elles commencent par .zdebug au lieu de .debug. --compress-debug-sections=zlib-gabi compresse également les sections de débogage DWARF, mais au lieu de les renommer, il définit l'indicateur SHF_COMPRESSED dans les en-têtes des sections.

    L'option --compress-debug-sections=zlib est un alias pour --compress-debug-sections=zlib-gabi.

    --compress-debug-sections=zstd compresse les sections de débogage DWARF à l'aide de zstd.

    Notez que cette option remplace toute compression dans les sections de débogage d'entrée. Ainsi, si un binaire est lié avec --compress-debug-sections=none, par exemple, toute section de débogage compressée dans les fichiers d'entrée sera décompressée avant d'être copiée dans le binaire de sortie.

    Le comportement de compression par défaut varie en fonction de la cible impliquée et des options de configuration utilisées pour créer la chaîne d'outils. Le défaut peut être déterminé en examinant la sortie de l'option --help de l'éditeur de liens.

    --reduce-memory-overheads
    Cette option réduit les besoins en mémoire au moment de l'exécution de ld, au détriment de la vitesse de liaison. Elle a été introduite pour sélectionner l'ancien algorithme O(n^2) pour la génération du fichier de carte de liaison, plutôt que le nouvel algorithme O(n) qui utilise environ 40 % de mémoire supplémentaire pour le stockage des symboles.

    Un autre effet de ce commutateur est de définir la taille par défaut de la table de hachage à 1021, ce qui économise de la mémoire au détriment de l'allongement du temps d'exécution de l'éditeur de liens. Cependant, cela n'est pas fait si le commutateur --hash-size a été utilisé.

    Le commutateur --reduce-memory-overheads peut également être utilisé pour activer d'autres compromis dans les futures versions de l'éditeur de liens.

    --max-cache-size=taille
    ld met normalement en cache les informations de relocalisation et les tables de symboles des fichiers d'entrée en mémoire avec une taille illimitée. Cette option définit la taille maximale du cache à taille.
    --build-id
    --build-id=style
    Demande la création d'une section de note ELF ".note.gnu.build-id" ou d'une section COFF ".buildid". Le contenu de la note sont des bits uniques identifiant ce fichier lié. style peut être "uuid" pour utiliser 128 bits aléatoires ; "sha1" pour utiliser un hachage SHA1 de 160 bits, "md5" pour utiliser un hachage MD5 de 128 bits, ou "xx" pour utiliser un XXHASH de 128 bits sur les parties normatives du contenu de sortie ; ou "0xchaînehex" pour utiliser une chaîne de bits choisie spécifiée comme un nombre pair de chiffres hexadécimaux (les caractères "-" et ":" entre les paires de chiffres sont ignorés). Si style est omis, "sha1" est utilisé.

    Les styles "md5", "sha1" et "xx" produisent un identifiant qui est toujours le même dans un fichier de sortie identique, mais qui est presque certainement unique parmi tous les fichiers de sortie non identiques. Il n'est pas destiné à être comparé comme une somme de contrôle du contenu du fichier. Un fichier lié peut être modifié ultérieurement par d'autres outils, mais la chaîne d'identifiant de construction identifiant le fichier lié d'origine ne change pas.

    Fournir "none" comme style désactive le réglage de toute option "--build-id" précédente sur la ligne de commande.

    --package-metadata=JSON
    Demande la création d'une section de note ELF ".note.package". Le contenu de la note est au format JSON, conformément à la spécification des métadonnées de paquet. Pour plus d'informations, voir : https://systemd.io/ELF_PACKAGE_METADATA/ L'argument JSON supporte l'encodage percent et l'encodage suivant %[chaîne] (où chaîne fait référence au nom dans les Références de Caractères Nommés HTML) : %[comma] pour ,, %[lbrace] pour {, %[quot] pour ", %[rbrace] pour }, et %[space] pour le caractère espace. Si l'argument JSON est manquant/vide, cela désactivera la création de la note de métadonnées, si elle avait été activée par une occurrence précédente de l'option --package-metadata. Si l'éditeur de liens a été construit avec libjansson, la chaîne JSON sera validée.

    --enable-long-section-names
    --disable-long-section-names
    Les variantes PE du format objet COFF ajoutent une extension qui permet l'utilisation de noms de section plus longs que huit caractères, la limite normale pour COFF. Par défaut, ces noms ne sont autorisés que dans les fichiers objets, car les images exécutables entièrement liées ne transportent pas la table de chaînes COFF requise pour supporter les noms plus longs. En tant qu'extension GNU, il est possible de permettre leur utilisation dans les images exécutables également, ou de les interdire (probablement inutilement !) dans les fichiers objets, en utilisant ces deux options. Les images exécutables générées avec ces noms de section longs sont légèrement non standard, car elles transportent une table de chaînes, et peuvent générer une sortie confuse lorsqu'elles sont examinées avec des outils non GNU compatibles PE, tels que des visualiseurs de fichiers et des dumpers. Cependant, GDB s'appuie sur l'utilisation des noms de section longs PE pour trouver les sections d'informations de débogage Dwarf-2 dans une image exécutable au moment de l'exécution, et donc si aucune des options n'est spécifiée sur la ligne de commande, ld activera les noms de section longs, outrepassant le comportement par défaut et techniquement correct, lorsqu'il trouve la présence d'informations de débogage lors de la liaison d'une image exécutable et sans suppression de symboles. [Cette option est valide pour tous les ports ciblés PE de l'éditeur de liens]
    --enable-stdcall-fixup
    --disable-stdcall-fixup
    Si la liaison trouve un symbole qu'elle ne peut pas résoudre, elle tentera une "liaison floue" en recherchant un autre symbole défini qui diffère seulement dans le format du nom du symbole (cdecl vs stdcall) et résoudra ce symbole en le liant à la correspondance. Par exemple, le symbole indéfini "_foo" pourrait être lié à la fonction "_foo@12", ou le symbole indéfini "_bar@16" pourrait être lié à la fonction "_bar". Lorsque l'éditeur de liens fait cela, il affiche un avertissement, car il aurait normalement dû échouer à lier, mais parfois les bibliothèques d'importation générées à partir de DLL tierces peuvent avoir besoin que cette fonctionnalité soit utilisable. Si vous spécifiez --enable-stdcall-fixup, cette fonctionnalité est complètement activée et les avertissements ne sont pas affichés. Si vous spécifiez --disable-stdcall-fixup, cette fonctionnalité est désactivée et de telles divergences sont considérées comme des erreurs.     Remarque : L'utilisation de l'extension « auto-import » rendra la section texte du fichier image inscriptible. Cela n'est pas conforme à la spécification du format PE-COFF publiée par Microsoft.

    Remarque - l'utilisation de l'extension « auto-import » placera également les données en lecture seule qui seraient normalement placées dans la section .rdata dans la section .data à la place. Ceci afin de contourner un problème avec les constantes décrit ici : http://www.cygwin.com/ml/cygwin/2004-09/msg01101.html

    L'utilisation de « auto-import » fonctionnera généralement « juste bien » — mais parfois vous verrez ce message :

    "la variable '<var>' ne peut pas être auto-importée. Veuillez lire la documentation de ld concernant "--enable-auto-import" pour plus de détails."

    Ce message survient lorsque certaines (sous)expressions accèdent à une adresse finalement donnée par la somme de deux constantes (les tables d'importation Win32 n'en autorisent qu'une). Les cas où cela peut se produire incluent les accès aux champs de membres de variables structurées importées d'une DLL, ainsi que l'utilisation d'un index constant dans un tableau importé d'une DLL. Tout tableau (ou structure, ou entier long long, etc.) composé de plusieurs mots peut déclencher cette condition d'erreur. Cependant, quel que soit le type de données exact de la variable exportée fautive, ld la détectera toujours, émettra l'avertissement et s'arrêtera.

    Il existe plusieurs façons de résoudre cette difficulté, quel que soit le type de données de la variable exportée :

    Une façon est d'utiliser le commutateur --enable-runtime-pseudo-reloc. Cela laisse la tâche d'ajustement des références dans votre code client à l'environnement d'exécution, donc cette méthode ne fonctionne que lorsque l'environnement d'exécution prend en charge cette fonctionnalité.

    Une deuxième solution consiste à forcer l'une des 'constantes' à être une variable — c'est-à-dire inconnue et non optimisable au moment de la compilation. Pour les tableaux, il existe deux possibilités : a) rendre l'indexé (l'adresse du tableau) une variable, ou b) rendre l'index 'constant' une variable. Ainsi :

    extern type extern_array[];
extern_array[1] -->
   { volatile type *t=extern_array; t[1] }

    ou

    extern type extern_array[];
extern_array[1] -->
   { volatile int t=1; extern_array[t] }

    Pour les structures (et la plupart des autres types de données multi-mots), la seule option est de rendre la structure elle-même (ou le long long, ou le ...) variable :

    extern struct s extern_struct;
extern_struct.field -->
   { volatile struct s *t=&extern_struct; t->field }

    ou

    extern long long extern_ll;
extern_ll -->
  { volatile long long * local_ll=&extern_ll; *local_ll }

    Une troisième méthode pour traiter cette difficulté est d'abandonner 'auto-import' pour le symbole fautif et de le marquer avec "__declspec(dllimport)". Cependant, en pratique, cela nécessite d'utiliser des #defines au moment de la compilation pour indiquer si vous construisez une DLL, si vous construisez du code client qui se liera à la DLL, ou si vous construisez/liez simplement à une bibliothèque statique. En créantle choix parmi les différentes méthodes de résolution du problème de "l'adresse directe avec décalage constant", vous devriez considérer l'utilisation typique dans le monde réel :

    Original :

    --foo.h
extern int arr[];
--foo.c
#include "foo.h"
void main(int argc, char **argv){
  printf("%d\n",arr[1]);
}

    Solution 1 :

    --foo.h
extern int arr[];
--foo.c
#include "foo.h"
void main(int argc, char **argv){
  /* Ce contournement est pour win32 et cygwin ; ne pas "optimiser" */
  volatile int *parr = arr;
  printf("%d\n",parr[1]);
}

    Solution 2 :

    --foo.h
/* Note : l'exportation automatique est supposée (pas de __declspec(dllexport)) */
#if (defined(_WIN32) || defined(__CYGWIN__)) && \
  !(defined(FOO_BUILD_DLL) || defined(FOO_STATIC))
#define FOO_IMPORT __declspec(dllimport)
#else
#define FOO_IMPORT
#endif
extern FOO_IMPORT int arr[];
--foo.c
#include "foo.h"
void main(int argc, char **argv){
  printf("%d\n",arr[1]);
}

    Une quatrième façon d'éviter ce problème est de recoder votre bibliothèque pour utiliser une interface fonctionnelle plutôt qu'une interface de données pour les variables incriminées (par exemple, les fonctions d'accès set_foo() et get_foo()).

L'option --no-insert-timestamp peut être utilisée pour insérer une valeur de zéro pour l'horodatage, garantissant ainsi que les binaires produits à partir de sources identiques se compareront de manière identique.

    Si --insert-timestamp est actif, l'heure insérée est soit l'heure à laquelle la liaison a lieu, soit, si la variable d'environnement "SOURCE_DATE_EPOCH" est définie, le nombre de secondes depuis l'époque Unix tel que spécifié par cette variable.

    --enable-reloc-section
    --disable-reloc-section
    Crée la table de relocation de base, nécessaire si l'image est chargée à une base d'image différente de celle spécifiée dans l'en-tête PE. Cette option est activée par défaut.

    La cible C6X uClinux utilise un format binaire appelé DSBT pour prendre en charge les bibliothèques partagées. Chaque bibliothèque partagée dans le système doit avoir un index unique ; tous les exécutables utilisent un index de 0.

    --dsbt-size taille
    Cette option définit le nombre d'entrées dans le DSBT de l'exécutable ou de la bibliothèque partagée actuelle à taille. La valeur par défaut est de créer une table avec 64 entrées.
    --dsbt-index index
    Cette option définit l'index DSBT de l'exécutable ou de la bibliothèque partagée actuelle à index. La valeur par défaut est 0, ce qui convient pour générer des exécutables. Si une bibliothèque partagée est générée avec un index DSBT de 0, les relocations "R_C6000_DSBT_INDEX" sont copiées dans le fichier de sortie.

    Le commutateur --no-merge-exidx-entries désactive la fusion des entrées exidx adjacentes dans les informations de déroulement de pile.

    --branch-stub
    Cette option active la relaxation de branche de l'éditeur de liens en insérant des sections de stubs de branche si nécessaire pour étendre la portée des branches. Cette option n'est généralement pas requise car C-SKY prend en charge les instructions de branche et d'appel qui peuvent accéder à toute la plage mémoire et la relaxation de branche est normalement gérée par le compilateur ou l'assembleur.
    --stub-group-size=N
    Cette option permet un contrôle plus fin de la création de stubs de branche par l'éditeur de liens. Elle définit la taille maximale d'un groupe de sections d'entrée qui peuvent être gérées par une section de stub. Une valeur négative de N place les sections de stub après leurs branches, tandis qu'une valeur positive permet aux sections de stub d'apparaître avant ou après les branches. Les valeurs de 1 ou -1 indiquent que l'éditeur de liens doit choisir des valeurs par défaut appropriées.

    Les éditeurs de liens 68HC11 et 68HC12 prennent en charge des options spécifiques pour contrôler le mappage de la commutation de banque mémoire et la génération de code trampoline.

    --no-trampoline
    Cette option désactive la génération de trampoline. Par défaut, un trampoline est généré pour chaque fonction lointaine qui est appelée à l'aide d'une instruction "jsr" (cela se produit lorsqu'un pointeur vers une fonction lointaine est pris).

    NAME

    ld - GNU linker

    SYNOPSIS

    ld [-] [-a] [-A name] [-b format] [-c libpath] [-d] [-e entry] [-E] [-f] [-g] [-G maxpagesize] [-H output-format] [-i] [-l names] [-L dirpath] [-m emulation] [-M] [-n] [-N] [-o outfile] [-O optimization-level] [-p] [-P] [-r] [-R path] [-s] [-S] [-t] [-T script] [-u symbol] [-U symbol] [-v] [-V] [-x] [-X] [-y] [-Z] [--help] [--info] [--verbose] [--version] [--copy-dt-entries] [--dynamic-linker file] [--enable-new-dtags] [--fatal-warnings] [--filter-library] [--gc-sections] [--help-options] [--ignore-dep-groups] [--incremental-archive] [--just-symbols=file] [--no-copy-dt-entries] [--no-gc-sections] [--no-keep-memory] [--no-warn-search-mismatch] [--no-whole-archive] [--omagic] [--output-im-directly-usable] [--pie] [--relax] [--shared] [--sort-section=name] [--sort-sections] [--split-by-relococount] [--split-by-size] [--static] [--traditional-format] [--unresolved-symbols=mode] [--whole-archive] [objfiles...] [-({archive|library}) objfile...] [-({<|>}) objfile...]

    DESCRIPTION

    The GNU linker ld is used to combine a number of object files and libraries that have been produced by the compiler/assembler into a single executable file, another object file or to produce nothing at all. The linker sorts out the symbol table and performs relocation.

    This manual page is not intended to be a full tutorial. The detailed documentation is in the binutils package Info manual. You can access it by running `info ld’.

    The options are grouped according to the function they perform.

    OPTIONS

    Options that relate to the output file format:

    -N
    --nmagic
    Mark the output as "NMAGIC" (0410) in the a.out header to indicate that when the output file is executed, the text portion will be read-only and shareable among all processes executing the same file. This involves moving the data areas up to the first possible 8K byte page boundary following the end of the text. This option creates a pure executable format.
    -N
    This is the default for most targets.
    --omagic
    Mark the output as "OMAGIC" (0407) in the a.out header to indicate that the text segment is not to be write-protected and shared. Since the text and data sections are both readable and writable, the data section is allocated immediately contiguous after the text segment. This is the oldest format for PDP11 executable programs and is the default for ld on PDP11 Unix systems from the beginning through 2.11BSD.
    -z
    --imagic
    Mark the output as "IMAGIC" (0411) in the a.out header to indicate that when the output file is executed, the program text and data areas will be loaded into separate address spaces using the split instruction and data space feature of the memory management unit in larger models of the PDP11. This doubles the address space available to the program. The text segment is again pure, write-protected, and shareable. The only difference in the output format between this option and the others, besides the magic number, is that both the text and data sections start at location 0. The -z option selected this format in 2.11BSD. This option creates a separate executable format.

    Options relating to the memory map:

    --wrap=symbol
    This option can be used to wrap a symbol, causing the linker to look for it first in the archive or object file that defines it, and if not found there, look for it in the object files that follow. This can be used to provide a version of a library routine that calls the standard library version. For example, if you link with a file containing "my_malloc.c" which includes a call to "malloc", and you link using "-Wl,--wrap=malloc" you will be linked with the standard library version of malloc. For more information refer to the Info entry for ld.
    -M
    This option informs the linker that the specified region is part of a memory bank window. The definition of such region is then used by the linker to compute paging and addresses within the memory window.
    name
    This option indicates to the linker the name of the memory region in the MEMORY specification that describes the memory bank window. The definition of such region is then used by the linker to compute paging and addresses within the memory window.

    The following options are supported to control handling of GOT generation when linking for 68K targets.

    --got=type
    This option tells the linker which GOT generation scheme to use. type should be one of single, negative, multigot or target. For more information refer to the Info entry for ld.

    The following options are supported to control microMIPS instruction generation and branch relocation checks for ISA mode transitions when linking for MIPS targets.

    --insn32
    --no-insn32
    These options control the choice of microMIPS instructions used in code generated by the linker, such as that in the PLT or lazy binding stubs, or in relaxation. If --insn32 is used, then the linker only uses 32-bit instruction encodings. By default or if --no-insn32 is used, all instruction encodings are used, including 16-bit ones where possible.
    --ignore-branch-isa
    --no-ignore-branch-isa
    These options control branch relocation checks for invalid ISA mode transitions. If --ignore-branch-isa is used, then the linker accepts any branch relocations and any ISA mode transition required is lost in relocation calculation, except for some cases of "BAL" instructions which meet relaxation conditions and are converted to equivalent "JALX" instructions as the associated relocation is calculated. By default or if --no-ignore-branch-isa is used a check is made causing the loss of an ISA mode transition to produce an error.
    --compact-branches
    --no-compact-branches
    These options control the generation of compact instructions by the linker in the PLT entries for MIPS R6.

    For the pdp11-aout target, three variants of the output format can be produced as selected by the following options. The default variant for pdp11-aout is the --omagic option, whereas for other targets --nmagic is the default. The --imagic option is defined only for the pdp11-aout target, while the others are described here as they apply to the pdp11-aout target.

    Mark the output as "OMAGIC" (0407) in the a.out header to indicate that the text segment is not to be write-protected and shared. Since the text and data sections are both readable and writable, the data section is allocated immediately contiguous after the text segment. This is the oldest format for PDP11 executable programs and is the default for ld on PDP11 Unix systems from the beginning through 2.11BSD.

    Equivalent to --nmagic for pdp11-aout.

    ENVIRONMENT

    You can change the behaviour of ld with the environment variables "GNUTARGET", "LDEMULATION" and "COLLECT_NO_DEMANGLE".

    "GNUTARGET" determines the input-file object format if you don't use -b (or its synonym --format). Its value should be one of the BFD names for an input format. If there is no "GNUTARGET" in the environment, ld uses the natural format of the target. If "GNUTARGET" is set to "default" then BFD attempts to discover the input format by examining binary input files; this method often succeeds, but there are potential ambiguities, since there is no method of ensuring that the magic number used to specify object-file formats is unique. However, the configuration procedure for BFD on each system places the conventional format for that system first in the search-list, so ambiguities are resolved in favor of convention.

    "LDEMULATION" determines the default emulation if you don't use the -m option. The emulation can affect various aspects of linker behaviour, particularly the default linker script. You can list the available emulations with the --verbose or -V options. If the -m option is not used, and the "LDEMULATION" environment variable is not defined, the default emulation depends upon how the linker was configured.

    Normally, the linker will default to demangling symbols. However, if "COLLECT_NO_DEMANGLE" is set in the environment, then it will default to not demangling symbols. This environment variable is used in a similar fashion by the "gcc" linker wrapper program. The default may be overridden by the --demangle and --no-demangle options.

    If the PE/COFF specific --insert-timestamp is active and the SOURCE_DATE_EPOCH environment variable is defined, then the timestamp value in this variable will be inserted into the COFF header instead of the current time.
