NOM

gcov - outil de test de couverture

SYNTAXE

gcov [-v|--version] [-h|--help]
[-a|--all-blocks]
[-b|--branch-probabilities]
[-c|--branch-counts]
[-g|--conditions]
[-e|--prime-paths]
[--prime-paths-lines[=type]]
[--prime-paths-source[=type]]
[-d|--display-progress]
[-f|--function-summaries]
[--include regex]
[--exclude regex]
[-j|--json-format]
[-H|--human-readable]
[-k|--use-colors]
[-l|--long-file-names]
[-m|--demangled-names]
[-M|--filter-on-demangled]
[-n|--no-output]
[-o|--object-directory répertoire|fichier]
[-p|--preserve-paths]
[-q|--use-hotness-colors]
[-r|--relative-only]
[-s|--source-prefix répertoire]
[-t|--stdout]
[-u|--unconditional-branches]
[-x|--hash-filenames] fichiers

DESCRIPTION

gcov est un programme de couverture de test. Utilisez-le en conjonction avec GCC pour analyser vos programmes afin de créer du code plus efficace et plus rapide, et pour découvrir les parties non testées de votre programme. Vous pouvez utiliser gcov comme outil de profilage pour découvrir où vos efforts d'optimisation auront le plus d'impact sur votre code. Vous pouvez également utiliser gcov avec l'autre outil de profilage, gprof, pour évaluer quelles parties de votre code utilisent le plus de temps de calcul.

Les outils de profilage vous aident à analyser les performances de votre code. En utilisant un profileur comme gcov ou gprof, vous pouvez obtenir des statistiques de performance de base, telles que :

  • la fréquence d'exécution de chaque ligne de code
  • quelles lignes de code sont effectivement exécutées
  • combien de temps de calcul chaque section de code utilise

Une fois que vous connaissez ces informations sur le fonctionnement de votre code une fois compilé, vous pouvez examiner chaque module pour voir lesquels doivent être optimisés. gcov vous aide à déterminer où concentrer vos efforts d'optimisation.

Les développeurs de logiciels utilisent également les tests de couverture en concertation avec des suites de tests pour s'assurer que le logiciel est suffisamment bon pour une publication. Les suites de tests peuvent vérifier qu'un programme fonctionne comme prévu ; un programme de couverture vérifie quelle partie du programme est exercée par la suite de tests. Les développeurs peuvent alors déterminer quels types de cas de test doivent être ajoutés aux suites de tests pour créer à la fois de meilleurs tests et un meilleur produit final.

Vous devriez compiler votre code sans optimisation si vous envisagez d'utiliser gcov, car l'optimisation, en combinant certaines lignes de code en une seule fonction, peut ne pas vous donner autant d'informations que nécessaire pour rechercher les `points chauds' où le code utilise une grande quantité de temps de calcul. De même, comme gcov accumule les statistiques par ligne (à la résolution la plus basse), il fonctionne mieux avec un style de programmation qui place une seule instruction par ligne. Si vous utilisez des macros compliquées qui se développent en boucles ou en autres structures de contrôle, les statistiques sont moins utiles --- elles ne signalent que la ligne où l'appel de macro apparaît. Si vos macros complexes se comportent comme des fonctions, vous pouvez les remplacer par des fonctions inline pour résoudre ce problème.

gcov crée un fichier journal appelé sourcefile.gcov qui indique combien de fois chaque ligne d'un fichier source sourcefile.c a été exécutée. Vous pouvez utiliser ces fichiers journaux avec gprof pour aider à affiner les performances de vos programmes. gprof fournit des informations de temps que vous pouvez utiliser avec les informations que vous obtenez de gcov.

gcov ne fonctionne que sur le code compilé avec GCC. Il n'est pas compatible avec aucun autre mécanisme de profilage ou de couverture de test.

OPTIONS

-a
--all-blocks
Écrit des comptes d'exécution individuels pour chaque bloc de base. Normalement, gcov ne sort les comptes d'exécution que pour les blocs principaux d'une ligne. Avec cette option, vous pouvez déterminer si des blocs au sein d'une même ligne ne sont pas exécutés.
-b
--branch-probabilities
Écrit les fréquences de branchement dans le fichier de sortie et les informations récapitulatives des branchements dans la sortie standard. Cette option vous permet de voir combien de fois chaque branchement de votre programme a été pris. Les branchements inconditionnels ne seront pas affichés, sauf si l'option -u est donnée.
-c
--branch-counts
Écrit les fréquences de branchement sous forme de nombre de branchements pris, plutôt que sous forme de pourcentage de branchements pris.
-g
--conditions
Écrit la couverture des conditions dans le fichier de sortie et les informations récapitulatives des conditions dans la sortie standard. Cette option vous permet de voir si les conditions de votre programme ont au moins une fois eu un effet indépendant sur le résultat de l'expression booléenne (couverture modifiée des conditions/décisions). Cela nécessite de compiler la source avec -fcondition-coverage.
-e
--prime-paths
Écrit la couverture des chemins dans le fichier de sortie et les informations récapitulatives des chemins dans la sortie standard. Cette option vous permet de voir combien de chemins principaux ont été pris au moins une fois. Un chemin est une séquence de blocs de base. Un chemin est simple s'il n'a pas de blocs répétés (pas de boucles) sauf éventuellement le premier et le dernier bloc, et principal s'il s'agit d'un chemin simple de longueur maximale. Pour la sortie régulière, cette option inclut seulement le nombre de chemins couverts. Pour des informations plus détaillées sur les chemins, vous pouvez utiliser --prime-paths-lines ou --prime-paths-source. Avec --json-format, tous les détails des chemins sont inclus dans la sortie. Cela nécessite de compiler la source avec -fpath-coverage.
--prime-paths-lines [=type]
Écrit la couverture des chemins dans le fichier de sortie et les informations récapitulatives des chemins dans la sortie standard. Cette option vous permet de voir combien de chemins principaux ont été pris au moins une fois, et un rapport dense sur les chemins couverts ou non couverts et comment les couvrir. Ce mode est utile pour le reporting automatisé et le suivi des progrès. type peut être omis, ou l'un des suivants :
  • uncovered - Inclure les chemins non couverts (non pris). C'est la valeur par défaut.
  • covered - Inclure les chemins couverts (pris).
  • both - Inclure tous les chemins. Ceci est équivalent à utiliser à la fois covered et uncovered.

Voici un exemple de sortie de --prime-paths-lines :

chemins couverts 12 sur 15
chemin 2 non couvert : lignes 8 8(faux) 11(vrai) 11 13(vrai) 13(vrai) 14 17
chemin 3 non couvert : lignes 8 8(faux) 11(vrai) 11 13(vrai) 13(faux) 16 17
chemin 4 non couvert : lignes 8 8(faux) 11(vrai) 11 13(faux) 16 17

Cela signifie que pour couvrir le chemin 2, vous devez exécuter les lignes 8, 11, 13, 14 et 17, en évaluant la décision à 8 comme faux et les décisions à 11 et 13 comme faux.

--prime-paths-source [=type]
Écrit la couverture des chemins dans le fichier de sortie et les informations récapitulatives des chemins dans la sortie standard. Cette option vous permet de voir combien de chemins principaux ont été pris au moins une fois, et un rapport détaillé sur les chemins non couverts et comment les couvrir. Ce mode est utile pour comprendre les chemins et les interactions entre les sections de votre programme. type peut être omis, ou l'un des suivants :
  • uncovered - Inclure les chemins non couverts (non pris). C'est la valeur par défaut.
  • covered - Inclure les chemins couverts (pris).
  • both - Inclure tous les chemins. Ceci est équivalent à utiliser à la fois covered et uncovered.

Voici un exemple de sortie de --prime-paths- source sortie :

chemin 10 non couvert :
BB  3 :           8 :  for (i = 0 ; i < 10 ; i++)
BB  3 :           9 :    total += i ;
BB  4 : (faux)   8 :  for (i = 0 ; i < 10 ; i++)
BB  5 : (vrai)   11 :  int v = total > 100 ? 1 : 2 ;
BB  6 :          11 :  int v = total > 100 ? 1 : 2 ;
BB  8 : (faux)   13 :  if (total != 45 && v == 1)
BB 11 :          16 :    printf ("Succès\n") ;
BB 12 :          17 :  return 0 ;

La première colonne (BB) est la séquence des blocs de base (voir -w). La colonne du milieu (vrai/faux) est la décision pour cette ligne. La troisième colonne est le numéro de ligne. La quatrième colonne est la ligne elle-même. Ces lignes doivent être exécutées dans cet ordre pour couvrir le chemin 10.

-d
--display-progress
Affiche la progression sur la sortie standard.
-f
--function-summaries
Produit des résumés pour chaque fonction en plus du résumé au niveau du fichier.
--include regex
Inclut les fonctions correspondant à regex. Cette option fait que gcov ne signale que les fonctions qui correspondent à l'expression régulière étendue regex. Ce drapeau peut être combiné avec --exclude. Si une fonction correspond à la fois aux inclusions et aux exclusions, la dernière inclusion/exclusion s'applique. Par défaut, gcov signale toutes les fonctions, mais si un --include est utilisé, seules les fonctions correspondant à l'inclusion seront signalées.
--exclude regex
Exclut les fonctions correspondant à regex. Cette option fait que gcov n'a pas de rapport sur les fonctions qui correspondent à l'expression régulière étendue regex. Ce drapeau peut être combiné avec --include. Si une fonction correspond à la fois aux inclusions et aux exclusions, la dernière inclusion/exclusion s'applique. Par défaut, gcov signale toutes les fonctions, et si --exclude est utilisé, les fonctions correspondantes seront omises.
-h
--help
Affiche l'aide sur l'utilisation de gcov (sur la sortie standard) et quitte sans effectuer d'autre traitement.
-j
--json-format
Produit le fichier gcov dans un format intermédiaire JSON facile à analyser, qui ne nécessite pas de code source pour sa génération. Le fichier JSON est compressé avec l'algorithme de compression gzip et les fichiers ont l'extension .gcov.json.gz.

La structure du JSON est la suivante :

{
  "current_working_directory": "foo/bar",
  "data_file": "a.out",
  "format_version": "2",
  "gcc_version": "11.1.1 20210510"
  "files": ["$file"]
}

Les champs de l'élément racine ont les sémantiques suivantes :

  • current_working_directory : répertoire de travail où une unité de compilation a été compilée
  • data_file : nom du fichier de données (GCDA)
  • format_version : version sémantique du format

    Changements dans la version 2 :

*
calls : des informations sur les appels de fonction sont ajoutées
*
gcc_version : version du compilateur GCC

Chaque file a la forme suivante :

{
  "file": "a.c",
  "functions": ["$function"],
  "lines": ["$line"]
}

Les champs de l'élément file ont les sémantiques suivantes :

*
file_name : nom du fichier source

Chaque function a la forme suivante :

{
  "blocks": 2,
  "blocks_executed": 2,
  "demangled_name": "foo",
  "end_column": 1,
  "end_line": 4,
  "execution_count": 1,
  "name": "foo",
  "start_column": 5,
  "start_line": 1
}

Les champs de l'élément function ont les sémantiques suivantes :

  • blocks : nombre de blocs dans la fonction
  • blocks_executed : nombre de blocs exécutés de la fonction
  • demangled_name : nom démêlé de la fonction
  • end_column : colonne dans le fichier source où la fonction se termine
  • end_line : ligne dans le fichier source où la fonction se termine
  • execution_count : nombre d'exécutions de la fonction
  • name : nom de la fonction
  • start_column : colonne dans le fichier source où la fonction commence
  • start_line : ligne dans le fichier source où la fonction commence

Notez que les numéros de ligne et de colonne commencent à 1. Dans l'implémentation actuelle, start_line et start_column n'incluent aucun paramètre de modèle ni le type de retour initial, mais cela est susceptible d'être corrigé à l'avenir.

Chaque line a la forme suivante :

{
  "block_ids": ["$block_id"],
  "branches": ["$branch"],
  "calls": ["$call"],
  "count": 2,
  "conditions": ["$condition"],
  "line_number": 15,
  "unexecuted_block": false,
  "function_name": "foo",
}

Les branches et les appels ne sont présents qu'avec l'option -b. Les champs de l'élément line ont les sémantiques suivantes :

  • block_ids : identifiants des blocs de base qui appartiennent à la ligne
  • count : nombre d'exécutions de la ligne
  • line_number : numéro de ligne
  • unexecuted_block : drapeau indiquant si la ligne contient un bloc non exécuté (toutes les instructions de la ligne ne sont pas exécutées)
  • function_name : nom d'une fonction à laquelle cette line appartient (peut ne pas être défini pour une ligne avec des instructions inline)

Chaque branch a la forme suivante :

{
  "count": 11,
  "destination_block_id": 17,
  "fallthrough": true,
  "source_block_id": 13,
  "throw": false
}

Les champs de l'élément branch ont les sémantiques suivantes :

  • count : nombre d'exécutions de la branche
  • fallthrough : vrai lorsque la branche est une branche de chute
  • throw : vrai lorsque la branche est une branche exceptionnelle
  • isource_block_id : ID du bloc de base où cette branche se produit
  • destination_block_id : ID du bloc de base vers lequel cette branche saute

Chaque call a la forme suivante :

{
  "destination_block_id": 1,
  "returned": 11,
  "source_block_id": 13
}

Les champs de l'élément call ont les sémantiques suivantes :

  • returned : nombre de fois qu'un appel de fonction est retourné (le nombre d'appels est égal à line::count)
  • isource_block_id : ID du bloc de base où cet appel se produit
  • destination_block_id : ID du bloc de base où l'appel se poursuit après le retour

Chaque condition a la forme suivante :

{
  "count": 4,
  "covered": 2,
  "not_covered_false": [],
  "not_covered_true": [0, 1],
}

Les champs de l'élément condition ont les sémantiques suivantes :

  • count : nombre de résultats de condition dans cette expression
  • covered : nombre de résultats de condition couverts dans cette expression
  • not_covered_true : termes, par index, non vus comme vrais dans cette expression
  • not_covered_false : termes, par index, non vus comme faux dans cette expression
-H
--human-readable
Écrit les comptes dans un format lisible par l'homme (comme 24.6k).
-k
--use-colors
Utilise les couleurs pour les lignes de code qui ont une couverture nulle. Nous utilisons la couleur rouge pour les lignes non exceptionnelles et le cyan pour les exceptionnelles. Les mêmes couleurs sont utilisées pour les blocs de base avec l'option -a.
-l
--long-file-names
Crée de longs noms de fichiers pour les fichiers source inclus. Par exemple, si le fichier d'en-tête x.h contient du code et a été inclus dans le fichier a.c, l'exécution de gcov sur le fichier a.c produira un fichier de sortie appelé a.c##x.h.gcov au lieu de x.h.gcov. Cela peut être utile si x.h est inclus dans plusieurs fichiers source et que vous souhaitez voir les contributions individuelles. Si vous utilisez l'option -p, les noms des fichiers incluant et inclus seront des chemins d'accès complets.
-m
--demangled-names
Affiche les noms de fonctions démêlés dans la sortie. Par défaut, les noms de fonctions sont affichés tels quels (mangled).
-M
--filter-on-demangled
Fait correspondre --include et --exclude aux noms démêlés. Cela n'affecte que la correspondance et n'implique pas --demangled-names, mais peut être combiné en toute sécurité avec.
-n
--no-output
Ne crée pas le fichier de sortie gcov.
-o répertoire|fichier
--object-directory répertoire
--object-file fichier
Spécifie soit le répertoire contenant les fichiers de données gcov, soit le nom du chemin de l'objet. Les fichiers de données .gcno et .gcda sont recherchés à l'aide de cette option. Si un répertoire est spécifié, les fichiers de données se trouvent dans ce répertoire et sont nommés d'après le nom du fichier d'entrée, sans son extension. Si un fichier est spécifié ici, les fichiers de données sont nommés d'après ce fichier, sans son extension.
-p
--preserve-paths
Préserve les informations de chemin complètes dans les noms des fichiers .gcov générés. Sans cette option, seul le composant du nom de fichier est utilisé. Avec cette option, tous les répertoires sont utilisés, les caractères / étant traduits en caractères #, les composants de répertoire . étant supprimés et les composants .. non supprimables étant renommés en ^. Ceci est utile si les fichiers source se trouvent dans plusieurs répertoires différents.
-q
--use-hot-colors
Émet une sortie colorée de type perf pour les lignes chaudes. La légende de l'échelle de couleurs est imprimée au tout début du fichier de sortie.
-r
--relative-only
N'affiche que les informations sur les fichiers source ayant un nom de chemin relatif (après élision du préfixe source). Les chemins absolus sont généralement des fichiers d'en-tête système et la couverture des fonctions inline qui s'y trouvent n'est normalement pas intéressante.
-s directory
--source-prefix directory
Un préfixe pour les noms de fichiers source à supprimer lors de la génération des fichiers de sortie de couverture. Cette option est utile lorsque la compilation est effectuée dans un répertoire séparé, et que le chemin d'accès au répertoire source n'est pas souhaité lors de la détermination des noms de fichiers de sortie. Notez que cette détection de préfixe est appliquée avant de déterminer si le fichier source est absolu.
-t
--stdout
Sortie vers la sortie standard au lieu des fichiers de sortie.
-u
--unconditional-branches
Lorsque les probabilités de branchement sont fournies, inclure celles des branchements inconditionnels. Les branchements inconditionnels ne sont normalement pas intéressants.
-v
--version
Affiche le numéro de version de gcov (sur la sortie standard) et quitte sans traitement supplémentaire.
-w
--verbose
Imprime des informations détaillées relatives aux blocs de base et aux arcs.
-x
--hash-filenames
Lors de l'utilisation de --preserve-paths, gcov utilise le chemin complet des fichiers source pour créer un nom de fichier de sortie. Cela peut entraîner des noms de fichiers longs qui peuvent dépasser les limites du système de fichiers. Cette option crée des noms de la forme source-file##md5.gcov, où le composant source-file est la partie finale du nom de fichier et le composant md5 est calculé à partir du nom complété qui aurait été utilisé autrement. L'option est une alternative à --preserve-paths sur les systèmes qui ont une limite de système de fichiers.

gcov doit être exécuté avec le répertoire courant identique à celui dans lequel vous avez appelé le compilateur. Sinon, il ne pourra pas localiser les fichiers source. gcov produit des fichiers appelés mangledname.gcov dans le répertoire courant. Ceux-ci contiennent les informations de couverture du fichier source auquel ils correspondent. Un fichier .gcov est produit pour chaque fichier source (ou d'en-tête) contenant du code, qui a été compilé pour produire les fichiers de données. La partie mangledname du nom du fichier de sortie est généralement simplement le nom du fichier source, mais peut être quelque chose de plus compliqué si les options -l ou -p sont données. Reportez-vous à ces options pour plus de détails.

Si vous invoquez gcov avec plusieurs fichiers d'entrée, les contributions de chaque fichier d'entrée sont additionnées. Typiquement, vous l'invoqueriez avec la même liste de fichiers que celle de la liaison finale de votre exécutable.

Les fichiers .gcov contiennent des champs séparés par des : avec le code source du programme. Le format est

<execution_count>:<line_number>:<source line text>

Des informations de bloc supplémentaires peuvent suivre chaque ligne, lorsqu'elles sont demandées par une option de ligne de commande. L'execution_count est - pour les lignes ne contenant aucun code. Les lignes non exécutées sont marquées ##### ou =====, selon qu'elles sont accessibles par des chemins non exceptionnels ou uniquement par des chemins exceptionnels tels que les gestionnaires d'exceptions C++, respectivement. Avec l'option -a, les blocs non exécutés sont marqués $$$$$ ou %%%%%, selon qu'un bloc de base est accessible via des chemins non exceptionnels ou exceptionnels. Les blocs de base exécutés ayant une instruction avec un execution_count nul se terminent par un caractère * et sont colorés en magenta avec l'option -k. Cette fonctionnalité n'est pas supportée en Ada.

Notez que GCC peut supprimer complètement les corps des fonctions qui ne sont pas nécessaires -- par exemple, si elles sont inline partout. Ces fonctions sont marquées avec -, ce qui peut être déroutant. Utilisez les options -fkeep-inline-functions et -fkeep-static-functions pour conserver ces fonctions et permettre à gcov de montrer correctement leur execution_count.

Certaines lignes d'informations au début ont un line_number de zéro. Ces lignes de préambule sont de la forme

-:0:<tag>:<value>

L'ordre et le nombre de ces lignes de préambule seront augmentés au fur et à mesure que le développement de gcov progresse --- ne comptez pas sur leur maintien inchangé. Utilisez tag pour localiser une ligne de préambule particulière.

Les informations de bloc supplémentaires sont de la forme

<tag> <information>

L'information est lisible par l'homme, mais conçue pour être suffisamment simple pour être analysée par machine également.

Lors de l'impression des pourcentages, 0% et 100% ne sont imprimés que lorsque les valeurs sont exactement 0% et 100% respectivement. Les autres valeurs qui seraient conventionnellement arrondies à 0% ou 100% sont au lieu de cela imprimées comme la valeur non limite la plus proche.

Lorsque vous utilisez gcov, vous devez d'abord compiler votre programme avec une option spéciale de GCC --coverage. Cela indique au compilateur de générer des informations supplémentaires nécessaires à gcov (principalement un graphe de flux du programme) et inclut également du code supplémentaire dans les fichiers objet pour générer les informations de profilage supplémentaires nécessaires à gcov. Ces fichiers supplémentaires sont placés dans le répertoire où se trouve le fichier objet.

L'exécution du programme générera une sortie de profilage. Pour chaque fichier source compilé avec -fprofile-arcs, un fichier .gcda accompagnant sera placé dans le répertoire du fichier objet.

L'exécution de gcov avec les noms de fichiers source de votre programme comme arguments produira maintenant un listing du code avec la fréquence d'exécution pour chaque ligne. Par exemple, si votre programme s'appelle tmp.cpp, voici ce que vous voyez lorsque vous utilisez la fonctionnalité de base de gcov :

$ g++ --coverage tmp.cpp -c
$ g++ --coverage tmp.o
$ a.out
$ gcov tmp.cpp -m
File 'tmp.cpp'
Lines executed:92.86% of 14
Creating 'tmp.cpp.gcov'

Pour chaque fonction, une ligne est imprimée montrant combien de fois la fonction est appelée, combien de fois elle retourne et quel pourcentage des blocs de la fonction ont été exécutés.

Pour chaque bloc de base, une ligne est imprimée après la dernière ligne du bloc de base décrivant le branchement ou l'appel qui termine le bloc de base. Il peut y avoir plusieurs branchements et appels listés pour une seule ligne source s'il y a plusieurs blocs de base qui se terminent sur cette ligne. Dans ce cas, les branchements et les appels reçoivent chacun un numéro. Il n'y a pas de moyen simple de relier ces branchements et appels aux constructions sources. En général, cependant, le branchement ou l'appel numéroté le plus bas correspondra à la construction la plus à gauche sur la ligne source.

Pour un branchement, s'il a été exécuté au moins une fois, un pourcentage indiquant le nombre de fois où le branchement a été pris divisé par le nombre de fois où le branchement a été exécuté sera imprimé. Sinon, le message "never executed" est imprimé.

Pour un appel, s'il a été exécuté au moins une fois, un pourcentage indiquant le nombre de fois où l'appel a retourné divisé par le nombre de fois où l'appel a été exécuté sera imprimé. Cela sera généralement de 100%, mais peut être inférieur pour les fonctions qui appellent "exit" ou "longjmp", et donc peuvent ne pas retourner à chaque fois qu'elles sont appelées.

Les nombres d'exécutions sont cumulatifs. Si le programme exemple était exécuté à nouveau sans supprimer le fichier .gcda, le nombre de fois où chaque ligne du code source

Utilisation de gcov avec l'optimisation GCC

Si vous prévoyez d'utiliser gcov pour optimiser votre code, vous devez d'abord compiler votre programme avec une option GCC spéciale --coverage. En dehors de cela, vous pouvez utiliser toutes les autres options GCC ; mais si vous voulez prouver que chaque ligne de votre programme a été exécutée, vous ne devriez pas compiler avec l'optimisation en même temps. Sur certaines machines, l'optimiseur peut éliminer certaines lignes de code simples en les combinant avec d'autres lignes. Par exemple, un code comme celui-ci :

if (a != b)
  c = 1;
else
  c = 0;

peut être compilé en une seule instruction sur certaines machines. Dans ce cas, il n'y a aucun moyen pour gcov de calculer des comptes d'exécution séparés pour chaque ligne car il n'y a pas de code séparé pour chaque ligne. Par conséquent, la sortie de gcov ressemble à ceci si vous avez compilé le programme avec l'optimisation :

100:   12:if (a != b)
100:   13:  c = 1;
100:   14:else
100:   15:  c = 0;

La sortie montre que ce bloc de code, combiné par l'optimisation, a été exécuté 100 fois. En un sens, ce résultat est correct, car il n'y avait qu'une seule instruction représentant ces quatre lignes. Cependant, la sortie n'indique pas combien de fois le résultat était 0 et combien de fois le résultat était 1.

Les fonctions inline peuvent créer des comptes de lignes inattendus. Les comptes de lignes sont affichés pour le code source de la fonction inlineable, mais ce qui est affiché dépend de l'endroit où la fonction est inline, ou si elle n'est pas inline du tout.

Si la fonction n'est pas inline, le compilateur doit émettre une copie hors ligne de la fonction, dans tout fichier objet qui en a besoin. Si fileA.o et fileB.o contiennent tous deux des corps hors ligne d'une fonction inlineable particulière, ils contiendront également tous deux des compteurs de couverture pour cette fonction. Lorsque fileA.o et fileB.o sont liés ensemble, l'éditeur de liens sélectionnera, sur de nombreux systèmes, l'un de ces corps hors ligne pour tous les appels à cette fonction, et supprimera ou ignorera l'autre. Malheureusement, il ne supprimera pas les compteurs de couverture pour le corps de fonction inutilisé. Par conséquent, lors de l'instrumentation, toutes les utilisations de cette fonction sauf une afficheront des comptes nuls.

Si la fonction est inline à plusieurs endroits, la structure de blocs à chaque emplacement peut ne pas être la même. Par exemple, une condition peut maintenant être calculable au moment de la compilation dans certains cas. Parce que la couverture de toutes les utilisations de la fonction inline sera affichée pour les mêmes lignes sources, les comptes de lignes eux-mêmes pourraient sembler incohérents.

Les applications de longue durée peuvent utiliser les installations "__gcov_reset" et "__gcov_dump" pour limiter la collecte de profil à la région du programme d'intérêt. Appeler "__gcov_reset(void)" effacera tous les compteurs de profil d'exécution à zéro, et appeler "__gcov_dump(void)" provoquera le vidage des informations de profil collectées à ce moment-là dans les fichiers de sortie .gcda. Les applications instrumentées utilisent un destructeur statique de priorité 99 pour invoquer la fonction "__gcov_dump". Ainsi, "__gcov_dump" est exécuté après tous les destructeurs statiques définis par l'utilisateur, ainsi que les gestionnaires enregistrés avec "atexit".

Si un exécutable charge un objet partagé dynamique via la fonctionnalité dlopen, -Wl,--dynamic-list-data est nécessaire pour vider toutes les données de profil.

La bibliothèque d'exécution de profilage signale diverses erreurs liées à la manipulation et à la sauvegarde de profils. Les erreurs sont imprimées dans la sortie d'erreur standard ou dans le fichier GCOV_ERROR_FILE, si la variable d'environnement est utilisée. Pour terminer immédiatement après une erreur, définissez la variable d'environnement GCOV_EXIT_AT_ERROR. Cela peut aider les utilisateurs à trouver les conflits de profil qui conduisent à un profil trompeur.
