DESCRIPTION

gcov est un programme de couverture de test. Utilisez-le en conjonction avec GCC pour analyser vos programmes afin de créer du code plus efficace et plus rapide, et pour découvrir les parties non testées de votre programme. Vous pouvez utiliser gcov comme outil de profilage pour déterminer où vos efforts d'optimisation auront le meilleur impact sur votre code. Vous pouvez également utiliser gcov avec l'autre outil de profilage, gprof, pour évaluer quelles parties de votre code utilisent le plus de temps de calcul.

Les outils de profilage vous aident à analyser les performances de votre code. En utilisant un profileur tel que gcov ou gprof, vous pouvez obtenir des statistiques de performance de base, telles que :

  • la fréquence d'exécution de chaque ligne de code
  • quelles lignes de code sont effectivement exécutées
  • combien de temps de calcul chaque section de code utilise

Une fois que vous connaissez ces informations sur le fonctionnement de votre code une fois compilé, vous pouvez examiner chaque module pour voir les modules qui devraient être optimisés. gcov vous aide à déterminer sur quoi travailler pour l'optimisation.

Les développeurs de logiciels utilisent également les tests de couverture en conjonction avec des suites de tests pour s'assurer que le logiciel est réellement suffisamment bon pour une publication. Les suites de tests peuvent vérifier qu'un programme fonctionne comme prévu ; un programme de couverture vérifie quelle partie du programme est exercée par la suite de tests. Les développeurs peuvent alors déterminer quels types de cas de test doivent être ajoutés aux suites de tests pour créer à la fois des tests meilleurs et un meilleur produit final.

Vous devriez compiler votre code sans optimisation si vous prévoyez d'utiliser gcov, car l'optimisation, en combinant certaines lignes de code en une seule fonction, peut ne pas vous donner autant d'informations que vous le souhaitez pour rechercher les "points chauds" où le code consomme beaucoup de temps de calcul. De même, comme gcov accumule les statistiques par ligne (à la résolution la plus fine), il fonctionne mieux avec un style de programmation qui place une seule instruction par ligne. Si vous utilisez des macros complexes qui se développent en boucles ou en autres structures de contrôle, les statistiques sont moins utiles --- elles ne rapportent que la ligne où l'appel de macro apparaît. Si vos macros complexes se comportent comme des fonctions, vous pouvez les remplacer par des fonctions inline pour résoudre ce problème.

gcov crée un fichier journal appelé fichier_source.gcov qui indique combien de fois chaque ligne d'un fichier source fichier_source.c a été exécutée. Vous pouvez utiliser ces fichiers journaux en conjonction avec gprof pour aider à affiner les performances de vos programmes. gprof fournit des informations de temps que vous pouvez utiliser avec les informations obtenues de gcov.

gcov ne fonctionne que sur le code compilé avec GCC. Il n'est pas compatible avec aucun autre mécanisme de profilage ou de couverture de test.

OPTIONS

-a
--all-blocks
Écrit les comptes d'exécution individuels pour chaque bloc de base. Normalement, gcov ne génère des comptes d'exécution que pour les blocs principaux d'une ligne. Avec cette option, vous pouvez déterminer si des blocs au sein d'une même ligne ne sont pas exécutés.
-b
--branch-probabilities
Écrit les fréquences de branchement dans le fichier de sortie, et écrit le résumé des branches sur la sortie standard. Cette option vous permet de voir la fréquence à laquelle chaque branche de votre programme a été prise. Les branches inconditionnelles ne seront pas affichées, sauf si l'option -u est donnée.
-c
--branch-counts
Écrit les fréquences de branchement sous forme du nombre de branches prises, plutôt que du pourcentage de branches prises.
-g
--conditions
Écrit la couverture des conditions dans le fichier de sortie, et écrit le résumé des conditions sur la sortie standard. Cette option vous permet de voir si les conditions de votre programme ont au moins une fois eu un effet indépendant sur le résultat de l'expression booléenne (couverture de décision/conditions modifiée). Cela nécessite de compiler la source avec -fcondition-coverage.
-d
--display-progress
Affiche la progression sur la sortie standard.
-f
--function-summaries
Génère des résumés pour chaque fonction en plus du résumé au niveau du fichier.
-h
--help
Affiche l'aide sur l'utilisation de gcov (sur la sortie standard) et quitte sans effectuer d'autres traitements.
-j
--json-format
Génère le fichier gcov dans un format JSON intermédiaire facile à analyser, qui ne nécessite pas de code source pour sa génération. Le fichier JSON est compressé avec l'algorithme de compression gzip et les fichiers ont l'extension .gcov.json.gz.

La structure du JSON est la suivante :

{
  "current_working_directory": "foo/bar",
  "data_file": "a.out",
  "format_version": "2",
  "gcc_version": "11.1.1 20210510"
  "files": ["$file"]
}

Les champs de l'élément racine ont la sémantique suivante :

  • current_working_directory : répertoire de travail où une unité de compilation a été compilée
  • data_file : nom du fichier de données (GCDA)
  • format_version : version sémantique du format

    Changements dans la version 2 :

*
calls : informations sur les appels de fonction ajoutées
*
gcc_version : version du compilateur GCC

Chaque file a la forme suivante :

{
  "file": "a.c",
  "functions": ["$function"],
  "lines": ["$line"]
}

Les champs de l'élément file ont la sémantique suivante :

*
file_name : nom du fichier source

Chaque function a la forme suivante :

{
  "blocks": 2,
  "blocks_executed": 2,
  "demangled_name": "foo",
  "end_column": 1,
  "end_line": 4,
  "execution_count": 1,
  "name": "foo",
  "start_column": 5,
  "start_line": 1
}

Les champs de l'élément function ont la sémantique suivante :

  • blocks : nombre de blocs dans la fonction
  • blocks_executed : nombre de blocs exécutés de la fonction
  • demangled_name : nom démêlé de la fonction
  • end_column : colonne dans le fichier source où la fonction se termine
  • end_line : ligne dans le fichier source où la fonction se termine
  • execution_count : nombre d'exécutions de la fonction
  • name : nom de la fonction
  • start_column : colonne dans le fichier source où la fonction commence
  • start_line : ligne dans le fichier source où la fonction commence
-H
--human-readable
Écrit le nom de fichier complet dans le fichier de sortie, au lieu de seulement le nom de fichier de base. Ceci est utile pour les fichiers sources situés dans différents répertoires.
-k
--use-colors
Utilise des couleurs pour le texte de sortie. L'utilisation des couleurs est activée par défaut si la sortie est un terminal.
-l
--long-file-names
Écrit le nom de fichier complet dans le fichier de sortie, au lieu de seulement le nom de fichier de base. Ceci est utile pour les fichiers sources situés dans différents répertoires.
-m
--demangled-names
Écrit les noms démêlés des fonctions dans le fichier de sortie. Ceci est utile pour les fonctions C++ qui ont été renommées par le compilateur.
-n
--no-output
Ne génère aucun fichier de sortie. Ceci est utile pour vérifier les options de gcov sans générer de fichiers.
-o
--object-directory répertoire|fichier
Spécifie le répertoire où se trouvent les fichiers objet (par exemple, les fichiers .gcno). Peut être utilisé pour spécifier un fichier unique. Par défaut, gcov recherche dans le répertoire courant.
-p
--preserve-paths
Ne supprime pas les chemins des noms de fichiers dans la sortie. Par défaut, gcov supprime le chemin du répertoire de travail courant des noms de fichiers.
-q
--use-hotness-colors
Utilise des couleurs pour mettre en évidence les lignes de code les plus exécutées. Les couleurs sont utilisées pour indiquer les zones du code qui sont exécutées le plus souvent.
-r
--relative-only
N'écrit que les noms de fichiers relatifs dans la sortie. Utile pour éviter les chemins absolus.
-s
--source-prefix répertoire
Supprime le préfixe spécifié des noms de fichiers sources. Utile si les fichiers sources sont dans un sous-répertoire spécifique.
-t
--stdout
Écrit la sortie sur la sortie standard au lieu de créer des fichiers .gcov. Utile pour le traitement par d'autres outils.
-u
--unconditional-branches
Inclut les branches inconditionnelles dans le résumé des branches. Par défaut, seules les branches conditionnelles sont incluses.
-x
--hash-filenames
Utilise des noms de fichiers hachés dans la sortie. Utile pour éviter les problèmes avec les noms de fichiers contenant des caractères spéciaux ou des chemins longs.

EXEMPLES

Compilation avec la couverture activée :

gcc -fprofile-arcs -ftest-coverage hello.c -o hello

Exécution du programme :

./hello

Génération du fichier de couverture :

gcov hello.c

Génération du fichier de couverture avec des informations sur les branches :

gcov -b hello.c

Génération du fichier de couverture au format JSON :

gcov -j hello.c

Certaines lignes d'informations au début ont un line_number de zéro. Ces lignes d'en-tête sont de la forme

-:0:<tag>:<value>

L'ordre et le nombre de ces lignes d'en-tête seront augmentés au fur et à mesure du développement de gcov --- ne vous fiez pas à leur immuabilité. Utilisez tag pour localiser une ligne d'en-tête particulière.

Les informations supplémentaires sur les blocs sont de la forme

<tag> <information>

L'information est lisible par l'homme, mais conçue pour être suffisamment simple pour un traitement automatique.

Lors de l'affichage des pourcentages, 0% et 100% ne sont affichés que lorsque les valeurs sont exactement 0% et 100% respectivement. Les autres valeurs qui seraient conventionnellement arrondies à 0% ou 100% sont affichées comme la valeur non limite la plus proche.

Lorsque vous utilisez gcov, vous devez d'abord compiler votre programme avec une option spéciale de GCC --coverage. Cela indique au compilateur de générer les informations supplémentaires nécessaires à gcov (essentiellement un graphe de flux du programme) et inclut également du code supplémentaire dans les fichiers objets pour générer les informations de profilage supplémentaires requises par gcov. Ces fichiers supplémentaires sont placés dans le répertoire où se trouve le fichier objet.

L'exécution du programme générera une sortie de profil. Pour chaque fichier source compilé avec -fprofile-arcs, un fichier .gcda correspondant sera placé dans le répertoire du fichier objet.

L'exécution de gcov avec les noms de fichiers source de votre programme en arguments produira maintenant une liste du code accompagnée de la fréquence d'exécution pour chaque ligne. Par exemple, si votre programme s'appelle tmp.cpp, voici ce que vous voyez lorsque vous utilisez la fonctionnalité de base de gcov:

$ g++ --coverage tmp.cpp -c
$ g++ --coverage tmp.o
$ a.out
$ gcov tmp.cpp -m
Fichier 'tmp.cpp'

Pour chaque fonction, une ligne est imprimée indiquant combien de fois la fonction est appelée, combien de fois elle retourne et quel pourcentage des blocs de la fonction a été exécuté.

Pour chaque bloc de base, une ligne est imprimée après la dernière ligne du bloc de base décrivant le branchement ou l'appel qui termine le bloc de base. Il peut y avoir plusieurs branchements et appels listés pour une seule ligne source s'il y a plusieurs blocs de base qui se terminent sur cette ligne. Dans ce cas, les branchements et les appels reçoivent chacun un numéro. Il n'y a pas de moyen simple de mapper ces branchements et appels aux constructions source. En général, cependant, le branchement ou l'appel numéroté le plus bas correspondra à la construction la plus à gauche sur la ligne source.

Pour un branchement, s'il a été exécuté au moins une fois, un pourcentage indiquant le nombre de fois où le branchement a été pris divisé par le nombre de fois où le branchement a été exécuté sera affiché. Sinon, le message "jamais exécuté" sera affiché.

Pour un appel, s'il a été exécuté au moins une fois, un pourcentage indiquant le nombre de fois où l'appel est retourné divisé par le nombre de fois où l'appel a été exécuté sera affiché. Ce sera généralement 100%, mais peut être inférieur pour les fonctions qui appellent "exit" ou "longjmp", et donc peuvent ne pas retourner chaque fois qu'elles sont appelées.

Les décomptes d'exécution sont cumulatifs. Si le programme exemple était exécuté à nouveau sans supprimer le fichier .gcda, le compte du nombre de fois où chaque ligne de la source a été exécutée serait ajouté aux résultats de l'exécution précédente. Ceci est potentiellement utile de plusieurs manières. Par exemple, il pourrait être utilisé pour accumuler des données sur un certain nombre d'exécutions de programme dans le cadre d'une suite de vérification de tests, ou pour fournir des informations plus précises à long terme sur un grand nombre d'exécutions de programme.

NAME

gcov - coverage analysis tool

SYNOPSIS

Synopsis

gcov [-b] [-c] [-d] [-f] [-o objdir] [-n] [-l] [-p] [-r] [-u] [-v] [-w] [-x] [--] [sourcefile...

DESCRIPTION

gcov is a tool that helps you to understand how much of your code is being exercised. It can be used to help you to optimize your code. It works by annotating the source code with execution counts. When used with the GCC compiler, you can compile your program with special options to instrument your code. Then, when you run your program, it will generate a counter file containing information about execution counts.

This counter file is then processed by gcov to produce an annotated source file, showing the number of times each line of your program was executed. This annotated file can help you to find parts of your code that are not being exercised, and thus may be worth optimizing.

The gcov tool works in conjunction with the GCC compiler. You must compile your program with the -fprofile-arcs option to generate the necessary instrumentation. Then, when you run your executable, it will generate a .gcda file for each source file. These files contain the execution counts for each branch of your code.

When you run gcov on a source file, it reads the .gcda file and produces an annotated source file, typically with a .gcov extension. This annotated file shows the execution counts for each line.

The profiling data stored in the .gcda files is not written when the program exits. Instead, it's written whenever the profiling code detects that it needs to write it. In a program compiled with -fprofile-arcs, the profiling code first attempts to read in an existing .gcda file; if the file doesn't match the executable (differing number of basic block counts) it will ignore the contents of the file. It then adds in the new execution counts and finally writes the data to the file.

Using gcov with GCC Optimization

If you plan to use gcov to help optimize your code, you must first compile your program with a special GCC option --coverage. Aside from that, you can use any other GCC options; but if you want to prove that every single line in your program was executed, you should not compile with optimization at the same time. On some machines the optimizer can eliminate some simple code lines by combining them with other lines. For example, code like this:

if (a != b)
  c = 1;
else
  c = 0;

can be compiled into one instruction on some machines. In this case, there is no way for gcov to calculate separate execution counts for each line because there isn't separate code for each line. Hence the gcov output looks like this if you compiled the program with optimization:

100:   12:if (a != b)
100:   13:  c = 1;
100:   14:else
100:   15:  c = 0;

The output shows that this block of code, combined by optimization, executed 100 times. In one sense this result is correct, because there was only one instruction representing all four of these lines. However, the output does not indicate how many times the result was 0 and how many times the result was 1.

Inlineable functions can create unexpected line counts. Line counts are shown for the source code of the inlineable function, but what is shown depends on where the function is inlined, or if it is not inlined at all.

If the function is not inlined, the compiler must emit an out of line copy of the function, in any object file that needs it. If fileA.o and fileB.o both contain out of line bodies of a particular inlineable function, they will also both contain coverage counts for that function. When fileA.o and fileB.o are linked together, the linker will, on many systems, select one of those out of line bodies for all calls to that function, and remove or ignore the other. Unfortunately, it will not remove the coverage counters for the unused function body. Hence when instrumented, all but one use of that function will show zero counts.

If the function is inlined in several places, the block structure in each location might not be the same. For instance, a condition might now be calculable at compile time in some instances. Because the coverage of all the uses of the inline function will be shown for the same source lines, the line counts themselves might seem inconsistent.

Long-running applications can use the "__gcov_reset" and "__gcov_dump" facilities to restrict profile collection to the program region of interest. Calling "__gcov_reset(void)" will clear all run-time profile counters to zero, and calling "__gcov_dump(void)" will cause the profile information collected at that point to be dumped to .gcda output files. Instrumented applications use a static destructor with priority 99 to invoke the "__gcov_dump" function. Thus "__gcov_dump" is executed after all user defined static destructors, as well as handlers registered with "atexit".

If an executable loads a dynamic shared object via dlopen functionality, -Wl,--dynamic-list-data is needed to dump all profile data.

Profiling run-time library reports various errors related to profile manipulation and profile saving. Errors are printed into standard error output or GCOV_ERROR_FILE file, if environment variable is used. In order to terminate immediately after an errors occurs set GCOV_EXIT_AT_ERROR environment variable. That can help users to find profile clashing which leads to a misleading profile.
