NOM

rigctld - démon de contrôle de radio par TCP

SYNTAXE

rigctld [-hlLouV] [-m id] [-r périphérique] [-p périphérique] [-d périphérique] [-P type] [-D type] [-s débit] [-c id] [-S caractère] [-T ADRESSEIP] [-t nombre] [-C parm=val] [-X secondes] [-v[-Z]]

DESCRIPTION

Le programme rigctld est un démon de contrôle de radio qui gère les requêtes des clients via des sockets TCP. Cela permet à plusieurs programmes utilisateurs de partager une seule radio (cela nécessite plus de développement). Plusieurs radios peuvent être contrôlées sur différents ports TCP en utilisant plusieurs processus rigctld. Notez que plusieurs processus/ports sont également nécessaires si certains clients utilisent des réponses étendues et/ou le mode VFO. Ainsi, jusqu'à 4 processus/ports peuvent être nécessaires pour chaque combinaison de réponses étendues/mode VFO. La syntaxe des commandes est la même que celle de rigctl(1). On espère que rigctld sera particulièrement utile pour les auteurs de clients utilisant des langages tels que Perl, Python, PHP et d'autres.

rigctld communique avec un client via un socket TCP en utilisant des commandes textuelles partagées avec rigctl. Le protocole est simple, les commandes sont envoyées à rigctld sur une ligne et rigctld répond aux commandes get avec les valeurs demandées, une par ligne, en cas de succès, sinon, il répond avec une ligne “RPRT x”, où ‘x’ est un nombre négatif indiquant le code d'erreur. Les commandes qui ne retournent pas de valeurs répondent avec la ligne “RPRT x”, où ‘x’ est ‘0’ en cas de succès, sinon c'est un nombre négatif indiquant le code d'erreur. Chaque ligne est terminée par un caractère de nouvelle ligne ‘\n’. Ce protocole est principalement destiné à être utilisé par le backend NET rigctl (modèle de radio 2).

Un Protocole de réponse étendu distinct étend le comportement ci-dessus en écho la chaîne de commande reçue comme en-tête, toute valeur retournée comme paire clé:valeur, et la chaîne “RPRT x” comme marqueur de fin de réponse qui inclut la valeur de succès ou d'échec de Hamlib. Voir la section PROTOCOLE pour plus de détails. Envisagez d'utiliser ce protocole pour les clients qui interagiront directement avec rigctld via un socket TCP.

Gardez à l'esprit que Hamlib est un logiciel de niveau BÊTA. Bien que de nombreuses bibliothèques backend manquent de support complet des radios, les fonctions de base sont généralement bien prises en charge.

Veuillez signaler les bugs et fournir vos commentaires à l'adresse e-mail indiquée dans la section BUGS ci-dessous. Les correctifs et les améliorations de code envoyés à la même adresse sont les bienvenus.

OPTIONS

Ce programme suit la syntaxe habituelle des lignes de commande GNU. Les options courtes qui prennent un argument peuvent avoir la valeur immédiatement après ou être séparées par un espace. Les options longues commençant par deux tirets (‘-’) nécessitent un ‘=’ entre l'option et tout argument.

Voici un résumé des options prises en charge :

-m, --model=id
Sélectionne le numéro du modèle de radio. Par défaut : radio factice.
Voir la liste des modèles (utiliser “rigctld -l”).
Note : rigctl (ou un logiciel tiers utilisant l'API C) utilisera le modèle de radio 2 pour NET rigctl (ce numéro de modèle n'est pas utilisé pour rigctld même s'il apparaît dans la liste des modèles).
-r, --rig-file=périphérique
Utilise périphérique comme nom de fichier du port connecté à la radio.
Généralement /dev/ttyS0, /dev/ttyS1, /dev/ttyUSB0, etc. sous Linux, COM1, COM2, etc. sous MS Windows. Les variantes BSD et Mac OS/X ont leurs propres désignations. Voir la documentation de votre système.
Peut être une adresse réseau:port, par exemple 127.0.0.1:12345
La chaîne spéciale “uh-rig” peut être fournie pour activer la prise en charge des périphériques micro-ham.
-p, --ptt-file=périphérique
Utilise périphérique comme nom de fichier du périphérique Push-To-Talk en utilisant un fichier de périphérique tel que décrit ci-dessus.
-d, --dcd-file=périphérique
Utilise périphérique comme nom de fichier du périphérique Data Carrier Detect en utilisant un fichier de périphérique tel que décrit ci-dessus.
-P, --ptt-type=type
Utilise le type de périphérique Push-To-Talk.
Les types pris en charge sont ‘RIG’ (commande CAT), ‘DTR’, ‘RTS’, ‘PARALLEL’, ‘CM108’, ‘GPIO’, ‘GPION’, ‘NONE’, remplaçant le type PTT défini dans le backend de la radio.
Certains effets secondaires de cette commande sont que lorsque le type est défini sur DTR, l'état PTT lu provient du frontend Hamlib, et non de la radio. Lorsqu'il est défini sur NONE, l'état PTT ne peut être ni lu ni défini, même si le backend de la radio prend en charge la lecture/définition de l'état PTT à partir de la radio.
-D, --dcd-type=type
Utilise le type de périphérique Data Carrier Detect.
Les types pris en charge sont ‘RIG’ (commande CAT), ‘DSR’, ‘CTS’, ‘CD’, ‘PARALLEL’, ‘CM108’, ‘GPIO’, ‘GPION’, ‘NONE’.
-s, --serial-speed=débit
Définit la vitesse série sur un débit de débit.
Utilise la vitesse série maximale des capacités du backend de la radio (définie par -m ci-dessus) par défaut.
-c, --civaddr=id
Utilise id comme adresse CI-V pour communiquer avec la radio.
Utile uniquement pour les radios Icom et certains radios Ten-Tec.
Note : L'id est en notation décimale, sauf s'il est précédé de 0x, auquel cas il est en hexadécimal.
-S, --separator=caractère
Utilise caractère comme séparateur au lieu de nouvelle ligne.
Par défaut, c'est ‘\n’. Il est recommandé d'utiliser $ ou @ car ils fonctionnent à la fois sous Unix et Windows.
-T, --listen-addr=ADRESSEIP
Utilise ADRESSEIP comme adresse IP d'écoute.
Par défaut : ANY (0.0.0.0).
rigctld peut être lancé et connecté comme ceci :
rigctld
rigctl -m 2
rigctl -m 2 -r 127.0.0.1
rigctl -m 2 -r localhost
rigctl -m 2 -r 192.168.1.1 (adresse IP locale)
rigctl -m 2 -r ::1 (sous Linux, rigctld n'écoute pas sur IPV6 par défaut)

rigctld -T 127.0.0.1
rigctl -m 2 (se lie à toutes les interfaces)
rigctl -m 2 -r 127.0.0.1 (se lie uniquement à 127.0.0.1)
Exceptions : 
rigctl -m 2 -r localhost (ne fonctionne que si localhost est une adresse IPV4)


rigctld -T localhost (se configurera sur IPV4 ou IPV6 basé sur localhost)
rigctl -m 2
rigctl -m 2 -r localhost
rigctl -m 2 ip6-localhost
Exceptions : 
rigctl -m 2 -r 127.0.0.1 (ne fonctionne que si localhost est une adresse IPV4)
rigctl -m 2 -r ::1 (ne fonctionne que si localhost est une adresse IPV6)

Sous Linux uniquement où ip6-localhost est fe00::0 : 
rigctld -T ip6-localhost
rigctl -m 2 -r ip6-localhost
-t, --port=nombre
Utilise nombre comme port d'écoute TCP. L'utilitaire rigctld écoute sur le port 4532 par défaut. Ce numéro de port est celui défini dans le Manuel de l'utilisateur de rigctld.
-C, --set-conf=parm=val
Permet de définir des paramètres spécifiques au modèle de radio.
Utilisez une commande comme “rigctld -l” pour voir la liste des modèles et des paramètres disponibles.
-X, --timeout=secondes
Définit le délai d'attente client TCP avant de fermer la connexion.
Défaut est 60 secondes.
-v, --version
Affiche les informations de version et quitte.
-v, --verbose
Active la sortie de débogage de Hamlib.
La deuxième invocation (-vv) activera encore plus de débogage.
-h, --help
Affiche un message d'aide et quitte.

PROTOCOLE

Le protocole de base et le protocole de réponse étendu sont décrits dans le manuel de rigctl(1).

EXEMPLES

Pour se connecter à une radio Kenwood TS-2000 à l'aide d'un port série Linux et d'une vitesse de 9600 bauds :

    rigctld -m 13 -r /dev/ttyS0 -s 9600

Pour se connecter à une radio Icom IC-746 sur le port COM3 avec l'adresse CI-V 0x72 :

    rigctld -m 23 -r COM3 -c 0x72

Pour utiliser le protocole de réponse étendu avec une radio connectée sur le port TCP 5000 :

    rigctld -m 2 -p 5000

Pour utiliser le protocole de réponse étendue et pour écouter sur le port 4532 (défaut) sur l'adresse IP 127.0.0.1 :

    rigctld -m 2 -T 127.0.0.1

Pour utiliser le protocole de réponse étendue et pour écouter sur le port 4532 (défaut) sur toutes les interfaces réseaux :

    rigctld -m 2

COMMANDES

Les commandes peuvent être envoyées via le socket TCP soit sous forme d'un seul caractère, soit sous forme d'un nom de commande long plus la ou les valeurs séparées par des espaces sur une ligne terminée par ‘\n’. Voir PROTOCOL.

Étant donné que la plupart des opérations Hamlib ont une méthode set et une méthode get, une seule lettre majuscule sera utilisée pour les méthodes set tandis que la lettre minuscule correspondante fera référence à la méthode get. Chaque opération a également un nom long ; préfixez une barre oblique inverse, ‘\’, pour envoyer un nom de commande long entièrement en minuscules.

Exemple (Perl) : « print $socket »\\dump_caps\n » » ; » pour voir ce que le backend de la radio peut faire (Note : En Perl et dans de nombreux autres langages, une ‘\’ devra être échappée avec une ‘\’ précédente afin que, même si deux caractères backslash apparaissent dans le code, un seul soit transmis à rigctld. C'est un bug potentiel, attention !).

Note : Le backend pour la radio à contrôler, ou la radio elle-même, peut ne pas prendre en charge certaines commandes. Dans ce cas, l'opération échouera avec un message d'erreur Hamlib.

Voici un résumé des commandes prises en charge (Dans le cas des commandes set, la chaîne italique entre guillemets est remplacée par la valeur dans la description. Dans le cas des commandes get, la chaîne italique entre guillemets est le nom clé de la valeur retournée) :

F, set_freq 'Fréquence'
Définit la 'Fréquence', en Hz.
La fréquence peut être une valeur flottante ou entière.
f, get_freq
Obtient la 'Fréquence', en Hz.
Retourne une valeur entière et le VFO que Hamlib considère comme actif. Notez que certaines radios (par exemple, toutes les Icom) ne peuvent pas suivre le VFO actuel, de sorte que Hamlib peut se désynchroniser de la radio si l'utilisateur appuie sur des boutons de la radio comme le VFO. Les clients rigctld doivent s'assurer qu'ils définissent le VFO souhaité ou qu'ils utilisent le mode vfo.
M, set_mode 'Mode' 'Bande passante'
Définit le 'Mode' et la 'Bande passante'.
Mode est un jeton : « USB », « LSB », « CW », « CWR », « RTTY », « RTTYR », « AM », « FM », « WFM », « AMS », « PKTLSB », « PKTUSB », « PKTFM », « ECSSUSB », « ECSSLSB », « FA », « SAM », « SAL », « SAH », « DSB ».
La bande passante est en Hz sous forme d'entier, -1 pour aucun changement, ou '0' pour la valeur par défaut du backend de la radio. IC7300 peut utiliser 1,2,3 pour sélectionner le filtre à utiliser
Note : Passer un '?' (requête) comme premier argument au lieu d'un jeton de Mode retournera une liste séparée par des espaces des Modes pris en charge par le backend de la radio. Utilisez ceci pour déterminer les Modes pris en charge d'un backend de radio donné.

Retourne le Mode sous forme de jeton et la Bande passante en Hz comme dans set_mode ci-dessus.

PROTOCOL

There are two protocols in use by rigctld, the Default Protocol and the Extended Response Protocol.

The Default Protocol is intended primarily for the communication between Hamlib library functions and rigctld (“NET rigctl”, available using radio model ‘2’).

The Extended Response Protocol is intended to be used with scripts or other programs interacting directly with rigctld as consistent feedback is provided.

Default Protocol

The Default Protocol is intentionally simple. Commands are entered on a single line with any needed values. In practice, reliable results are obtained by terminating each command string with a newline character, ‘\n’.

Example set frequency and mode commands (Perl code (typed text shown in bold)):


print $socket "F 14250000\n";
print $socket "\set_mode LSB 2400\n";   # escape leading '\'

A one line response will be sent as a reply to set commands, “RPRT x\n” where x is the Hamlib error code with ‘0’ indicating success of the command.

Responses from rigctld get commands are text values and match the same tokens used in the set commands. Each value is returned on its own line. On error the string “RPRT x\n” is returned where x is the Hamlib error code.

Example get frequency (Perl code):


print $socket "f\n";
"14250000\n"

Most get functions return one to three values. A notable exception is the dump_caps command which returns many lines of key:value pairs.

This protocol is primarily used by the “NET rigctl” (rigctl model 2) backend which allows applications already written for Hamlib's C API to take advantage of rigctld without the need of rewriting application code. An application's user can select rotator model 2 (“NET rigctl”) and then set rig_pathname to “localhost:4532” or other network host:port (set by the -T/-t options, respectively, above).

Extended Response Protocol

The Extended Response protocol adds several rules to the strings returned by rigctld and adds a rule for the command syntax.

1. The command received by rigctld is echoed with its long command name followed by the value(s) (if any) received from the client terminated by the specified response separator as the first record of the response.

2. The last record of each block is the string “RPRT x\n” where x is the numeric return value of the Hamlib backend function that was called by the command.

3. Any records consisting of data values returned by the radio backend are prepended by a string immediately followed by a colon then a space and then the value terminated by the response separator. e.g. “Frequency: 14250000\n” when the command was prepended by ‘+’.

4. All commands received will be acknowledged by rigctld with records from rules 1 and 2. Records from rule 3 are only returned when data values must be returned to the client.

An example response to a set_mode command sent from the shell prompt (note the prepended ‘+’):


$ echo "+M USB 2400" | nc -w 1 localhost 4532
set_mode: USB 2400
RPRT 0

In this case the long command name and values are returned on the first line and the second line contains the end of block marker and the numeric radio backend return value indicating success.

An example response to a get_mode query:


$ echo "+\get_mode" | nc -w 1 localhost 4532
get_mode:
Mode: USB
Passband: 2400
RPRT 0
Note: The ‘\’ is still required for the long command name even with the ERP character.

In this case, as no value is passed to rigctld, the first line consists only of the long command name. The final line shows that the command was processed successfully by the radio backend.

Invoking the Extended Response Protocol requires prepending a command with a punctuation character. As shown in the examples above, prepending a ‘+’ character to the command results in the responses being separated by a newline character (‘\n’). Any other punctuation character recognized by the C ispunct() function except ‘\’, ‘?’, or ‘_’ will cause that character to become the response separator and the entire response will be on one line.

Separator character summary:

‘+’
Each record of the response is appended with a newline (‘\n’).
‘;’, ‘|’, or, ‘,’
Each record of the response is appended by the given character resulting in entire response on one line.
These are common record separators for text representations of spreadsheet data, etc.
‘?’
Reserved for help in rigctl.
‘_’
Reserved for get_info short command
‘#’
Reserved for comments when reading a command file script.
Note: Other punctuation characters have not been tested! Use at your own risk.

PROTOCOL

Un requête get_mode avec un ‘;’ de tête renvoie:


get_mode:;Mode: USB;Passband: 2400;RPRT 0

Ou, en utilisant le caractère pipe ‘|’ renvoie:


get_mode:|Mode: USB|Passband: 2400|RPRT 0

Et une commande set_mode préfixée par un ‘|’ renvoie:


set_mode: USB 2400|RPRT 0

Un tel format permettra de lire une réponse comme un seul événement en utilisant un séparateur de réponse préféré. D'autres caractères de ponctuation n'ont pas été testés !

DIAGNOSTICS

L'option -v, --verbose permet différents niveaux de diagnostics à afficher sur stderr et correspondent à -v pour BUG, -vv pour ERR, -vvv pour WARN, -vvvv pour VERBOSE, ou -vvvvv pour TRACE.

Un niveau verbeux donné est utile pour fournir les informations de débogage nécessaires à l'adresse e-mail ci-dessous. Par exemple, la sortie TRACE montre toutes les valeurs envoyées et reçues de la radio, ce qui est très utile pour le développement de bibliothèques backend radio et peut être demandé par les développeurs.

EXAMPLES

Démarrer rigctld pour un Yaesu FT-920 utilisant un adaptateur USB vers série et en arrière-plan :


$ rigctld -m 1014 -r /dev/ttyUSB1 &

Démarrer rigctld pour un Yaesu FT-920 utilisant un adaptateur USB vers série tout en définissant le débit en bauds et les bits d'arrêt, et en arrière-plan :


$ rigctld -m 1014 -r /dev/ttyUSB1 -s 4800 -C stop_bits=2 &

Démarrer rigctld pour un Elecraft K3 sur COM2 sous MS Windows :


$ rigctld -m 2029 -r COM2

Se connecter au rigctld déjà en cours d'exécution et régler la fréquence sur 14,266 MHz avec un délai de lecture de 1 seconde en utilisant le protocole par défaut depuis l'invite de commande :


$ echo "\set_freq 14266000" | nc -w 1 localhost 4532

Se connecter à un rigctld en cours d'exécution avec rigctl sur l'hôte local :


$ rigctl -m2

SECURITY

Aucune authentification ; NE LAISSEZ PAS ce port TCP ouvert sur Internet. Veuillez demander si une sécurité plus forte est nécessaire ou envisagez d'utiliser un tunnel Secure Shell (ssh(1)).

Comme rigctld n'a pas besoin de plus de permissions que rigctl, il est conseillé de ne pas démarrer rigctld en tant que “root” ou un autre compte utilisateur système afin de limiter toute vulnérabilité.

BUGS

Le démon ne se détache pas et ne s'exécute pas en arrière-plan.

Aucune méthode pour quitter le démon, donc la commande kill(1) doit être utilisée pour le terminer.

Plusieurs clients utilisant le démon peuvent rencontrer des conflits avec la radio connectée.
