rsync(1) Commandes utilisateur rsync(1)

NOM

rsync - un outil de copie de fichiers rapide, polyvalent, distant (et local)

SYNTAXE

Local :
    rsync [OPTION...] SRC... [DEST]
Accès via shell distant :
    Récupérer :
        rsync [OPTION...] [USER@]HOST:SRC... [DEST]
    Envoyer :
        rsync [OPTION...] SRC... [USER@]HOST:DEST
Accès via démon rsync :
    Récupérer :
        rsync [OPTION...] [USER@]HOST::SRC... [DEST]
        rsync [OPTION...] rsync://[USER@]HOST[:PORT]/SRC... [DEST]
    Envoyer :
        rsync [OPTION...] SRC... [USER@]HOST::DEST
        rsync [OPTION...] SRC... rsync://[USER@]HOST[:PORT]/DEST)

Les utilisations avec un seul argument SRC et aucun argument DEST listeront les fichiers source au lieu de les copier.

La version en ligne de cette page de manuel (qui inclut des liens croisés entre les rubriques) est disponible sur https://download.samba.org/pub/rsync/rsync.1.

DESCRIPTION

Rsync est un outil de copie de fichiers rapide et extraordinairement polyvalent. Il peut copier localement, vers/depuis une autre machine sur n'importe quel shell distant, ou vers/depuis un démon rsync distant. Il offre un grand nombre d'options qui contrôlent chaque aspect de son comportement et permettent une spécification très flexible de l'ensemble des fichiers à copier. Il est célèbre pour son algorithme de transfert différentiel (delta-transfer algorithm), qui réduit la quantité de données envoyées sur le réseau en n'envoyant que les différences entre les fichiers source et les fichiers existants dans la destination. Rsync est largement utilisé pour les sauvegardes et la mise en miroir, ainsi que comme commande de copie améliorée pour un usage quotidien.

Rsync trouve les fichiers qui doivent être transférés en utilisant un algorithme de "vérification rapide" (par défaut) qui recherche les fichiers dont la taille ou l'heure de dernière modification a changé. Toute modification des autres attributs préservés (tels que demandés par les options) est effectuée directement sur le fichier de destination lorsque la vérification rapide indique que les données du fichier n'ont pas besoin d'être mises à jour.

Quelques fonctionnalités supplémentaires de rsync sont :

o
prise en charge de la copie des liens, des périphériques, des propriétaires, des groupes et des permissions
o
options d'exclusion et d'exclusion-de-fichier similaires à GNU tar
o
un mode d'exclusion CVS pour ignorer les mêmes fichiers que CVS ignorerait
o
peut utiliser n'importe quel shell distant transparent, y compris ssh ou rsh
o
ne nécessite pas de privilèges de super-utilisateur
o
pipelining des transferts de fichiers pour minimiser les coûts de latence
o
prise en charge des démons rsync anonymes ou authentifiés (idéal pour la mise en miroir)

GÉNÉRAL

Rsync copie les fichiers soit vers ou depuis une machine distante, soit localement sur la machine actuelle (il ne prend pas en charge la copie de fichiers entre deux machines distantes).

Il existe deux manières différentes pour rsync de contacter un système distant : en utilisant un programme de shell distant comme transport (tel que ssh ou rsh) ou en contactant directement un démon rsync via TCP. Le transport par shell distant est utilisé chaque fois que le chemin source ou destination contient un seul deux-points (:) comme séparateur après une spécification d'hôte. Contacter directement un démon rsync se produit lorsque le chemin source ou destination contient une double paire de deux-points (::) comme séparateur après une spécification d'hôte, OU lorsqu'une URL rsync:// est spécifiée (voir également la section UTILISER LES FONCTIONNALITÉS DU DÉMON RSYNC VIA UNE CONNEXION SHELL DISTANTE pour une exception à cette dernière règle).

Comme cas spécial, si un seul argument source est spécifié sans destination, les fichiers sont listés dans un format de sortie similaire à "ls -l".

Comme attendu, si ni la source ni la destination ne spécifient une machine distante, la copie se fait localement (voir également l'option --list-only).

Rsync appelle le côté local le client et le côté distant le serveur. Ne confondez pas serveur avec un démon rsync. Un démon est toujours un serveur, mais un serveur peut être soit un démon, soit un processus lancé par un shell distant.

CONFIGURATION

Consultez le fichier README.md pour les instructions d'installation.

Une fois installé, vous pouvez utiliser rsync sur n'importe quelle machine à laquelle vous pouvez accéder via un shell distant (ainsi que certaines auquelles vous pouvez accéder en utilisant le protocole du mode démon rsync). Pour les transferts distants, un rsync moderne utilise ssh pour ses communications, mais il peut avoir été configuré pour utiliser un autre shell distant par défaut, tel que rsh ou remsh.

Vous pouvez également spécifier n'importe quel shell distant de votre choix, soit en utilisant l'option de ligne de commande -e, soit en définissant la variable d'environnement RSYNC_RSH.

Notez que rsync doit être installé sur la machine source et la machine de destination.

UTILISATION

Vous utilisez rsync de la même manière que vous utilisez rcp. Vous devez spécifier une source et une destination, dont l'une peut être distante.

La meilleure façon d'expliquer la syntaxe est peut-être avec quelques exemples :

rsync -t *.c foo:src/

Ceci transférerait tous les fichiers correspondant au motif *.c du répertoire courant vers le répertoire src sur la machine foo. Si certains des fichiers existent déjà sur le système distant, alors le protocole de mise à jour distante de rsync est utilisé pour mettre à jour le fichier en n'envoyant que les différences dans les données. Notez que l'expansion des caractères génériques (wildcards) sur la ligne de commande (*.c) en une liste de fichiers est gérée par le shell avant qu'il n'exécute rsync et non par rsync lui-même (exactement comme tous les autres programmes de style Posix).

rsync -avz foo:src/bar /data/tmp

Ceci transférerait récursivement tous les fichiers du répertoire src/bar sur la machine foo vers le répertoire /data/tmp/bar sur la machine locale. Les fichiers sont transférés en mode archive, ce qui garantit que les liens symboliques, les périphériques, les attributs, les permissions, les propriétaires, etc., sont préservés lors du transfert. De plus, la compression sera utilisée pour réduire la taille des parties de données du transfert.

rsync -avz foo:src/bar/ /data/tmp

Une barre oblique finale sur la source change ce comportement pour éviter de créer un niveau de répertoire supplémentaire à la destination. Vous pouvez considérer une barre oblique finale sur une source comme signifiant "copier le contenu de ce répertoire" par opposition à "copier le répertoire par son nom", mais dans les deux cas, les attributs du répertoire parent sont transférés au répertoire parent sur la destination. En d'autres termes, chacune des commandes suivantes copie les fichiers de la même manière, y compris la définition des attributs de /dest/foo :

rsync -av /src/foo /dest
rsync -av /src/foo/ /dest/foo

Notez également que les références d'hôte et de module ne nécessitent pas une barre oblique finale pour copier le contenu du répertoire par défaut. Par exemple, les deux commandes suivantes copient le contenu du répertoire distant dans "/dest" :

rsync -av host: /dest
rsync -av host::module /dest

Vous pouvez également utiliser rsync en mode local uniquement, où la source et la destination n'ont pas de ':' dans leur nom. Dans ce cas, il se comporte comme une commande de copie améliorée.

Enfin, vous pouvez lister tous les modules (listerables) disponibles à partir d'un démon rsync particulier en omettant le nom du module :

rsync somehost.mydomain.com::

COPIER SOUS UN NOM DIFFÉRENT

Lorsque vous souhaitez copier un répertoire sous un nom différent, utilisez une barre oblique finale sur le répertoire source pour placer le contenu du répertoire dans n'importe quel répertoire de destination de votre choix :

rsync -ai foo/ bar/

Rsync a également la capacité de personnaliser le nom d'un fichier de destination lors de la copie d'un seul élément. Les règles pour cela sont :

o
La liste de transfert doit être composée d'un seul élément (un fichier ou un répertoire vide)
o
Le dernier élément du chemin de destination n'existe pas en tant que répertoire
o
Le chemin de destination n'a pas été spécifié avec une barre oblique finale

Dans ces circonstances, rsync définira le nom de l'unique élément de la destination sur le dernier élément du chemin de destination. Gardez à l'esprit qu'il sera

st pour utiliser cet idiome uniquement lors de la copie d'un fichier et utilisez l'idiome du slash final ci-dessus lors de la copie d'un répertoire.

L'exemple suivant copie le fichier foo.c en tant que bar.c dans le répertoire save (en supposant que bar.c n'est pas un répertoire) :

rsync -ai src/foo.c save/bar.c

La règle de copie d'élément unique pourrait accidentellement vous jouer un tour si vous copiez involontairement un élément unique et spécifiez un répertoire de destination qui n'existe pas (sans utiliser de slash final). Par exemple, si src/*.c correspond à un seul fichier et que save/dir n'existe pas, cela vous confondra en nommant le fichier de destination save/dir :

rsync -ai src/*.c save/dir

Pour éviter un tel accident, assurez-vous que le répertoire de destination existe ou spécifiez le chemin de destination avec un slash final :

rsync -ai src/*.c save/dir/

ORDRE DE TRANSFERT TRIÉ

Rsync trie toujours les noms de fichiers spécifiés dans sa liste de transfert interne. Cela permet de fusionner le contenu de répertoires de noms identiques, et facilite la suppression des noms de fichiers dupliqués. Cela peut, cependant, dérouter quelqu'un lorsque les fichiers sont transférés dans un ordre différent de celui donné en ligne de commande.

Si vous avez besoin qu'un fichier particulier soit transféré avant un autre, séparez les fichiers en appels rsync distincts, ou envisagez d'utiliser --delay-updates (qui n'affecte pas l'ordre de transfert trié, mais rend la phase finale de mise à jour des fichiers beaucoup plus rapide).

SÉCURITÉ MULTI-HÔTE

Rsync prend des mesures pour garantir que les requêtes de fichiers partagées dans un transfert sont protégées contre divers problèmes de sécurité. La plupart des problèmes potentiels surviennent côté réception, où rsync prend des mesures pour garantir que la liste des fichiers transférés reste dans les limites de ce qui a été demandé.

À cette fin, rsync 3.1.2 et versions ultérieures ont été interrompus lorsqu'une liste de fichiers contient un chemin absolu ou relatif qui tente de s'échapper du haut du transfert. De plus, à partir de la version 3.2.5, rsync effectue deux vérifications de sécurité supplémentaires de la liste de fichiers pour (1) s'assurer qu'aucun argument source supplémentaire n'a été ajouté au transfert autre que ceux demandés par le client et (2) s'assurer que la liste de fichiers respecte les règles d'exclusion envoyées à l'expéditeur.

Pour ceux qui n'ont pas encore de client rsync 3.2.5 (ou ceux qui veulent être particulièrement prudents), il est plus sûr de faire une copie dans un répertoire de destination dédié pour les fichiers distants lorsque vous ne faites pas confiance à l'hôte distant. Par exemple, au lieu de faire une copie rsync dans votre répertoire personnel :

rsync -aiv host1:dir1 ~

Dédiez un répertoire "host1-files" au contenu distant :

rsync -aiv host1:dir1 ~/host1-files

Voir l'option --trust-sender pour plus de détails.

ATTENTION : il n'est pas particulièrement sûr d'utiliser rsync pour copier des fichiers d'un système de fichiers respectant la casse vers un système de fichiers ignorant la casse. Si vous devez effectuer une telle copie, vous devriez soit désactiver les liens symboliques via --no-links, soit activer la modification des liens symboliques via --munge-links (et vous assurer d'utiliser l'option locale ou distante appropriée). Cela empêchera rsync de faire des choses potentiellement dangereuses si le nom d'un lien symbolique chevauche un fichier ou un répertoire. Cela ne garantit cependant pas que vous obteniez une copie complète de tous les fichiers (car cela peut ne pas être possible lorsque les noms se chevauchent). Une solution potentiellement meilleure consiste à lister tous les fichiers sources et à créer une liste de noms de fichiers sûre que vous passez à l'option --files-from. Tout fichier dont le nom entre en conflit devra être copié dans des répertoires de destination différents en utilisant plusieurs copies.

Bien qu'une copie d'un système de fichiers ignorant la casse vers un système de fichiers ignorant la casse puisse bien se passer, si aucune option --delete-during ou --delete-before n'est active, rsync peut potentiellement mettre à jour un fichier existant côté réception sans remarquer que la casse du nom de fichier devrait être modifiée pour correspondre à l'expéditeur.

USAGE AVANCÉ

La syntaxe pour demander plusieurs fichiers à un hôte distant se fait en spécifiant des arguments hôte-distant supplémentaires dans le même style que le premier, ou en omettant le nom d'hôte. Par exemple, tout cela fonctionne :

rsync -aiv host:file1 :file2 host:file{3,4} /dest/
rsync -aiv host::modname/file{1,2} host::modname/extra /dest/
rsync -aiv host::modname/first ::extra-file{1,2} /dest/

Notez qu'une connexion de démon ne prend en charge l'accès qu'à un seul module par commande de copie. Par conséquent, si le début d'un chemin suivant ne commence pas par le nom du module du premier chemin, il est supposé être un chemin dans le module (comme les extra-file1 et extra-file2 qui sont récupérés ci-dessus).

Les versions très anciennes de rsync (2.6.9 et antérieures) ne permettaient de spécifier qu'un seul argument source distant. Certains utilisateurs se sont donc appuyés sur le shell distant pour scinder un argument en plusieurs chemins. Un tel comportement non intuitif n'est plus pris en charge par défaut (bien que vous puissiez le demander, comme décrit ci-dessous).

À partir de 3.2.4, les noms de fichiers sont passés à un shell distant de manière à préserver les caractères que vous leur donnez. Ainsi, si vous demandez un fichier avec des espaces dans son nom, c'est ce que le rsync distant recherche :

rsync -aiv host:'a simple file.pdf' /dest/

Si vous utilisez des scripts écrits pour appliquer manuellement un quotage supplémentaire aux arguments rsync distants (ou pour nécessiter une division des arguments distants), vous pouvez demander à rsync de laisser votre script gérer l'échappement supplémentaire. Cela se fait soit en ajoutant l'option --old-args aux exécutions rsync dans le script (ce qui nécessite un nouveau rsync), soit en exportant RSYNC_OLD_ARGS=1 et RSYNC_PROTECT_ARGS=0 (ce qui fonctionne avec les anciennes ou les nouvelles versions de rsync).

CONNEXION À UN DÉMON RSYNC

Il est également possible d'utiliser rsync sans shell distant comme transport. Dans ce cas, vous vous connecterez directement à un démon rsync distant, généralement en utilisant le port TCP 873. (Cela nécessite évidemment que le démon soit en cours d'exécution sur le système distant, référez-vous donc à la section DÉMARRER UN DÉMON RSYNC POUR ACCEPTER LES CONNEXIONS ci-dessous pour plus d'informations à ce sujet.)

Utiliser rsync de cette manière est identique à l'utiliser avec un shell distant, sauf que :

o
Utilisez la syntaxe double-point (::) ou la syntaxe d'URL rsync:// au lieu de la syntaxe simple-point (shell distant).
o
Le premier élément du "chemin" est en fait un nom de module.
o
Les arguments sources distants supplémentaires peuvent utiliser une syntaxe abrégée qui omet le nom d'hôte et/ou le nom du module, comme discuté dans USAGE AVANCÉ.
o
Le démon distant peut afficher un "message du jour" lorsque vous vous connectez.
o
Si vous spécifiez uniquement l'hôte (sans module ni chemin), une liste des modules accessibles sur le démon est affichée.
o
Si vous spécifiez un chemin source distant mais aucune destination, une liste des fichiers correspondants sur le démon distant est affichée.
o
L'option --rsh (-e) doit être omise pour éviter de changer le style de connexion de l'utilisation d'une connexion socket à L'UTILISATION DES FONCTIONNALITÉS DU DÉMON RSYNC VIA UNE CONNEXION SHELL DISTANT.

Un exemple qui copie tous les fichiers d'un module distant nommé "src" :

rsync -av host::src /dest

Certains modules sur le démon distant peuvent nécessiter une authentification. Si c'est le cas, vous recevrez une invite de mot de passe lors de la connexion. Vous pouvez éviter l'invite de mot de passe en définissant la variable d'environnement RSYNC_PASSWORD avec le mot de passe que vous souhaitez utiliser ou en utilisant l'option --password-file. Cela peut être utile lors du scripting de rsync.

AVERTISSEMENT : Sur certains systèmes, les variables d'environnement sont visibles par tous les utilisateurs. Sur ces systèmes, l'utilisation de --password-file est recommandée.

Vous pouvez établir la connexion via un proxy web en définissant la variable d'environnement RSYNC_PROXY avec une paire nom d'hôte:port pointant vers votre proxy web. Notez que la configuration de votre proxy web doit supporter les connexions proxy vers le port 873.

Vous pouvez également établir une connexion de démon en utilisant un programme comme proxy en définissant la variable d'environnement RSYNC_CONNECT_PROG avec les commandes que vous souhaitez exécuter au lieu de faire une connexion socket directe. La chaîne peut contenir l'échappement "%H" pour représenter le nom d'hôte spécifié dans la commande rsync (utilisez donc "%%" si vous avez besoin d'un seul "%" dans votre chaîne). Par exemple :

export RSYNC_CONNECT_PROG='ssh proxyhost nc %H 873'
rsync -av targethost1::module/src/ /dest/
rsync -av rsync://targethost2/module/src/ /dest/

La commande ci-dessus utilise ssh pour exécuter nc (netcat) sur un proxyhost, qui transmet toutes les données au port 873 (le démon rsync) sur le targethost (%H).

Notez également que si la variable d'environnement RSYNC_SHELL est définie, ce programme sera utilisé pour exécuter la commande RSYNC_CONNECT_PROG au lieu d'utiliser le shell par défaut de l'appel system().

UTILISATION DES FONCTIONNALITÉS DU DÉMON RSYNC VIA UNE CONNEXION SHELL DISTANT

Il est parfois utile d'utiliser diverses fonctionnalités d'un démon rsync (comme les modules nommés) sans autoriser de nouvelles connexions socket vers un système (autre que ce qui est déjà nécessaire pour autoriser l'accès via shell distant). Rsync prend en charge la connexion à un hôte en utilisant un shell distant, puis le lancement d'un serveur "démon" à usage unique qui s'attend à lire son fichier de configuration dans le répertoire personnel de l'utilisateur distant. Cela peut être utile si vous souhaitez chiffrer les données d'un transfert de type démon, mais comme le démon est démarré à neuf par l'utilisateur distant, vous ne pourrez peut-être pas utiliser des fonctionnalités comme chroot ou changer l'uid utilisé par le démon. (Pour une autre façon de chiffrer un transfert de démon, envisagez d'utiliser ssh pour tunneliser un port local vers une machine distante et configurez un démon rsync normal sur cet hôte distant pour autoriser uniquement les connexions depuis "localhost".)

Du point de vue de l'utilisateur, un transfert de démon via une connexion shell distant utilise presque la même

syntaxe en ligne de commande comme un démon rsync normal transfert, à la seule exception près que vous devez explicitement définir le programme de shell distant sur la ligne de commande avec l'option --rsh=COMMAND . (Définir RSYNC_RSH dans l'environnement n'activera pas cette fonctionnalité.) Par exemple :

rsync -av --rsh=ssh hôte::module /dest

Si vous devez spécifier un utilisateur de shell distant différent, gardez à l'esprit que le préfixe utilisateur@ devant l'hôte spécifie la valeur rsync-user (pour un module qui nécessite une authentification basée sur l'utilisateur). Cela signifie que vous devez donner l'option '-l utilisateur' à ssh lors de la spécification du shell distant, comme dans cet exemple qui utilise la version courte de l'option --rsh :

rsync -av -e "ssh -l ssh-user" rsync-user@hôte::module /dest

Le "ssh-user" sera utilisé au niveau ssh ; le "rsync-user" sera utilisé pour se connecter au "module".

Dans cette configuration, le démon est démarré par la commande ssh qui accède au système (ce qui peut être forcé via le fichier ~/.ssh/authorized_keys, si désiré). Cependant, lors de l'accès direct à un démon, celui-ci doit être démarré au préalable.

DÉMARRER UN DÉMON RSYNC POUR ACCEPTER LES CONNEXIONS

Afin de se connecter à un démon rsync, le système distant doit avoir un démon déjà en cours d'exécution (ou avoir configuré quelque chose comme inetd pour lancer un démon rsync pour les connexions entrantes sur un port particulier). Pour des informations complètes sur la façon de démarrer un démon qui gérera les connexions socket entrantes, consultez la page de manuel rsyncd.conf(5) -- c'est le fichier de configuration du démon, et il contient tous les détails sur la façon de faire fonctionner le démon (y compris les configurations autonome et inetd).

Si vous utilisez l'un des transports de shell distant pour le transfert, il n'est pas nécessaire de démarrer manuellement un démon rsync.

EXEMPLES

Voici quelques exemples d'utilisation de rsync.

Pour sauvegarder un répertoire personnel, qui se compose de gros fichiers MS Word et de dossiers de courrier, un travail cron par utilisateur peut être utilisé pour exécuter ceci chaque jour :

rsync -aiz . bkhost:backup/joe/

Pour déplacer des fichiers d'un hôte distant vers l'hôte local, vous pouvez exécuter :

rsync -aiv --remove-source-files rhost:/tmp/{file1,file2}.c ~/src/

OPTIONS

Rsync accepte les options longues (double-tirets + mot) et courtes (un seul tiret + lettre). La liste complète des options disponibles est décrite ci-dessous. Si une option peut être spécifiée de plusieurs façons, les choix sont séparés par des virgules. Certaines options n'ont qu'une variante longue, pas courte.

Si l'option prend un paramètre, le paramètre n'est listé qu'après la variante longue, même s'il doit également être spécifié pour la courte. Lors de la spécification d'un paramètre, vous pouvez utiliser la forme --option=param, --option param, -o=param, -o param, ou -oparam (ces derniers choix supposent que votre option a une variante courte).

Le paramètre peut devoir être cité d'une manière ou d'une autre pour survivre à l'analyse de la ligne de commande du shell. Gardez également à l'esprit qu'un tilde (~) en préfixe dans un nom de chemin est substitué par votre shell, alors assurez-vous de séparer le nom de l'option du nom de chemin à l'aide d'un espace si vous voulez que le shell local l'étende.

--help
Imprime une courte page d'aide décrivant les options disponibles dans rsync et quitte. Vous pouvez également utiliser -h pour --help lorsqu'il est utilisé sans aucune autre option (car il signifie normalement --human-readable).
--version, -V
Imprime la version de rsync plus d'autres informations et quitte. Lorsqu'elle est répétée, les informations sont sorties au format JSON qui est encore assez lisible (côté client uniquement).
La sortie comprend une liste des capacités compilées, une liste d'optimisations, la liste par défaut des algorithmes de somme de contrôle, la liste par défaut des algorithmes de compression, la liste par défaut des digests d'authentification de démon, un lien vers le site web de rsync et quelques autres éléments.
--verbose, -v
Cette option augmente la quantité d'informations que vous recevez pendant le transfert. Par défaut, rsync fonctionne en silence. Un seul -v vous donnera des informations sur les fichiers transférés et un bref résumé à la fin. Deux options -v vous donneront des informations sur les fichiers ignorés et un peu plus d'informations à la fin. Plus de deux options -v ne devraient être utilisées que si vous déboguez rsync.
Le résumé de fin indique le nombre d'octets envoyés au démon rsync distant (qui est le côté récepteur lors d'une copie locale), le nombre d'octets reçus de l'hôte distant et la moyenne d'octets par seconde des données transférées, calculée sur toute la durée de l'exécution de rsync. La deuxième ligne affiche la taille totale (en octets), qui est la somme de toutes les tailles de fichiers que rsync a pris en compte pour le transfert. Elle affiche également une valeur de "speedup", qui est le rapport entre la taille totale du fichier divisée par la somme des octets envoyés et reçus (ce qui est vraiment juste un chiffre pour se sentir bien, plus c'est grand, mieux c'est). Notez que ces valeurs d'octets peuvent être rendues plus (ou moins) lisibles par l'homme en utilisant les options --human-readable (ou --no-human-readable).
Dans un rsync moderne, l'option -v est équivalente à l'ensemble des options --info et --debug. Vous pouvez choisir d'utiliser ces options plus récentes en plus de, ou à la place de, --verbose, car tous les réglages fins remplacent les réglages implicites de -v. --info et --debug ont tous deux un moyen de demander de l'aide qui vous indique exactement quels drapeaux sont définis pour chaque augmentation de la verbosité.
Cependant, n'oubliez pas que le réglage "max verbosity" d'un démon limitera le niveau auquel les divers drapeaux individuels peuvent être définis côté démon. Par exemple, si le maximum est de 2, alors tout drapeau d'information et/ou de débogage qui est défini à une valeur supérieure à ce qui serait défini par -vv sera rétrogradé au niveau -vv dans la journalisation du démon.
--info=DRAPEAUX
Cette option vous permet de contrôler finement les informations de sortie que vous souhaitez voir. Un nom de drapeau individuel peut être suivi d'un numéro de niveau, 0 signifiant de supprimer cette sortie, 1 étant le niveau de sortie par défaut, et des numéros plus élevés augmentant la sortie de ce drapeau (pour ceux qui supportent des niveaux plus élevés). Utilisez --info=help pour voir tous les noms de drapeaux disponibles, ce qu'ils affichent et quels noms de drapeaux sont ajoutés pour chaque augmentation du niveau de verbosité. Quelques exemples :
rsync -a --info=progress2 src/ dest/
rsync -avv --info=stats2,misc1,flist0 src/ dest/
Notez que la sortie de --info=name est affectée par les options --out-format et --itemize-changes (-i). Voir ces options pour plus d'informations sur ce qui est affiché et quand.
Cette option a été ajoutée en 3.1.0, donc un rsync plus ancien côté serveur pourrait rejeter vos tentatives de contrôle fin (si un ou plusieurs drapeaux devraient être envoyés au serveur et que le serveur était trop ancien pour les comprendre). Voir également la mise en garde concernant "max verbosity" ci-dessus lorsque vous traitez avec un démon.
--debug=DRAPEAUX
Cette option vous permet de contrôler finement la sortie de débogage que vous souhaitez voir. Un nom de drapeau individuel peut être suivi d'un numéro de niveau, 0 signifiant de supprimer cette sortie, 1 étant le niveau de sortie par défaut, et des numéros plus élevés augmentant la sortie de ce drapeau (pour ceux qui supportent des niveaux plus élevés). Utilisez --debug=help pour voir tous les noms de drapeaux disponibles, ce qu'ils affichent et quels noms de drapeaux sont ajoutés pour chaque augmentation du niveau de verbosité. Quelques exemples :
rsync -avvv --debug=none src/ dest/
rsync -avA --del --debug=del2,acl src/ dest/
Notez que certains messages de débogage ne seront affichés que lorsque l'option --stderr=all est spécifiée, en particulier ceux concernant le débogage des E/S et des tampons.
À partir de la version 3.2.0, cette option n'est plus automatiquement transmise au côté serveur afin de vous permettre de spécifier différentes valeurs de débogage pour chaque côté du transfert, ainsi que de spécifier une nouvelle option de débogage qui n'est présente que dans l'une des versions de rsync. Si vous souhaitez dupliquer la même option des deux côtés, utiliser l'expansion des accolades est un moyen facile de vous épargner de la saisie. Cela fonctionne dans zsh et bash :
rsync -aiv {-M,}--debug=del2 src/ dest/
--stderr=erreurs|tous|client
Cette option contrôle quels processus sortent vers stderr et si les messages d'information sont également redirigés vers stderr. Les chaînes de mode peuvent être abrégées, alors n'hésitez pas à utiliser une valeur d'une seule lettre. Les 3 choix possibles sont :
o
erreurs - (par défaut) fait en sorte que tous les processus rsync envoient une erreur directement à stderr, même si le processus est du côté distant du transfert. Les messages d'information sont envoyés au côté client via le flux de protocole. Si stderr n'est pas disponible (c'est-à-dire lorsqu'on se connecte directement à un démon via un socket), les erreurs reviennent à être envoyées via le flux de protocole.
o
tous - fait en sorte que tous les messages rsync (informations et erreurs) soient écrits directement sur stderr par tous les processus (possibles). Cela rend stderr tamponné par ligne (au lieu d'être brut) et élimine la possibilité de diviser les messages d'information et d'erreur par descripteur de fichier. Pour ceux qui font du débogage ou qui utilisent plusieurs niveaux de verbosité, cette option peut aider à éviter de surcharger le flux de transfert (ce qui devrait empêcher toute chance qu'un bug de blocage ne bloque les choses). Elle permet également à --debug d'activer des messages supplémentaires liés aux E/S.
o
client - fait en sorte que tous les messages rsync soient envoyés au côté client via le flux de protocole. Un processus client affiche tous les messages, avec les erreurs sur stderr et les messages d'information sur stdout. C'était le défaut dans les anciennes versions de rsync, mais cela peut entraîner des retards d'erreurs lorsqu'une grande quantité de données de transfert précède les messages. Si vous envoyez des fichiers à un rsync plus ancien, vous voudrez peut-être utiliser --stderr=all car cet idiome existe depuis plusieurs versions.
Cette option a été ajoutée dans rsync 3.2.3. Cette version a également commencé la transmission d'un paramètre non par défaut au côté distant, bien que rsync utilise les options rétrocompatibles --msgs2stderr et --no-msgs2stderr pour représenter les paramètres all et client, respectivement. Un rsync plus récent continuera d'accepter ces anciens noms d'options pour maintenir la compatibilité.
--quiet, -q
Cette option diminue la quantité d'informations que vous recevez pendant le transfert, supprimant notamment les messages d'information du serveur distant. Cette option est utile lors de l'invocation de rsync depuis cron.
--no-motd
Cette option affecte les informations qui sont affichées par le client au début d'un transfert de démon. Elle supprime le message du jour (MOTD), mais elle affecte également la liste des modules que le démon envoie en réponse à la requête "rsync host::" (en raison d'une limitation du protocole rsync), alors omettez cette option si vous souhaitez demander la liste des modules au démon.
--ignore-times, -I
Normalement, rsync ignorera tous les fichiers qui ont déjà la même taille et ont
la même horodatage de modification. Cette option désactive ce comportement de "vérification rapide", obligeant tous les fichiers à être mis à jour.
Cette option peut être déroutante par rapport à --ignore-existing et --ignore-non-existing car elles font que rsync transfère moins de fichiers, tandis que cette option fait que rsync transfère plus de fichiers.
--size-only
Cela modifie l'algorithme de "vérification rapide" de rsync pour trouver les fichiers qui doivent être transférés, le passant du défaut de transfert des fichiers ayant une taille modifiée ou une dernière modification modifiée à uniquement la recherche des fichiers dont la taille a changé. Ceci est utile lors du démarrage de rsync après avoir utilisé un autre système de miroir qui pourrait ne pas préserver les horodatages avec précision.
--modify-window=NUM, -@
Lors de la comparaison de deux horodatages, rsync considère les horodatages comme étant égaux s'ils diffèrent de plus du montant du modify-window. La valeur par défaut est 0, qui correspond uniquement aux secondes entières. Si vous spécifiez une valeur négative (et que le récepteur est au moins de version 3.1.3), les nanosecondes seront également prises en compte. Spécifier 1 est utile pour les copies vers/depuis les systèmes de fichiers FAT de MS Windows, car FAT représente les temps avec une résolution de 2 secondes (permettant aux temps de différer de l'original jusqu'à 1 seconde).
Si vous voulez que tous vos transferts comparent par défaut les nanosecondes, vous pouvez créer un fichier ~/.popt et y mettre les lignes suivantes :
rsync alias -a -a@-1
rsync alias -t -t@-1
Avec cela comme défaut, vous devriez spécifier --modify-window=0 (alias -@0) pour le remplacer et ignorer les nanosecondes, par exemple si vous copiez entre ext3 et ext4, ou si le rsync récepteur est plus ancien que 3.1.3.
--checksum, -c
Cela change la façon dont rsync vérifie si les fichiers ont été modifiés et nécessitent un transfert. Sans cette option, rsync utilise une "vérification rapide" qui (par défaut) vérifie si la taille et la dernière date de modification de chaque fichier correspondent entre l'expéditeur et le récepteur. Cette option change cela pour comparer une somme de contrôle (checksum) de 128 bits pour chaque fichier ayant une taille correspondante. La génération des sommes de contrôle signifie que les deux côtés dépenseront beaucoup d'E/S disque en lisant toutes les données des fichiers dans le transfert, donc cela peut ralentir considérablement les choses (et cela, avant toute lecture qui sera effectuée pour transférer les fichiers modifiés).
Le côté expéditeur génère ses sommes de contrôle pendant qu'il effectue l'analyse du système de fichiers qui construit la liste des fichiers disponibles. Le récepteur génère ses sommes de contrôle lorsqu'il analyse les fichiers modifiés, et calculera la somme de contrôle de tout fichier ayant la même taille que le fichier correspondant de l'expéditeur : les fichiers ayant une taille modifiée ou une somme de contrôle modifiée sont sélectionnés pour le transfert.
Notez que rsync vérifie toujours que chaque fichier transféré a été correctement reconstruit du côté récepteur en vérifiant une somme de contrôle de fichier complet générée lors du transfert du fichier, mais cette vérification automatique après transfert n'a rien à voir avec la vérification "Ce fichier doit-il être mis à jour ?" avant le transfert de cette option.
La somme de contrôle utilisée est automatiquement négociée entre le client et le serveur, mais peut être remplacée en utilisant soit l'option --checksum-choice (--cc), soit une variable d'environnement qui est discutée dans la section de cette option.
--archive, -a
Ceci est équivalent à -rlptgoD. C'est un moyen rapide de dire que vous voulez la récursion et que vous voulez préserver presque tout. Sachez que cela n'inclut pas la préservation des ACL (-A), des xattrs (-X), des atimes (-U), des crtimes (-N), ni la recherche et la préservation des liens physiques (-H).
La seule exception à l'équivalence ci-dessus est lorsque --files-from est spécifié, auquel cas -r n'est pas implicite.
--no-OPTION
Vous pouvez désactiver une ou plusieurs options implicites en préfixant le nom de l'option par "no-". Toutes les options positives n'ont pas d'opposé négatif, mais beaucoup en ont, y compris celles qui peuvent être utilisées pour désactiver une option implicite (par exemple, --no-D, --no-perms) ou ont des défauts différents dans diverses circonstances (par exemple, --no-whole-file, --no-blocking-io, --no-dirs). Chaque option négative valide accepte à la fois le nom court et le nom long de l'option après le préfixe "no-" (par exemple, --no-R est identique à --no-relative).
Par exemple, si vous souhaitez utiliser --archive (-a) mais que vous ne souhaitez pas utiliser --owner (-o), au lieu de convertir -a en -rlptgD, vous pouvez spécifier -a --no-o (alias --archive --no-owner).
L'ordre des options est important : si vous spécifiez --no-r -a, l'option -r serait finalement activée, le contraire de -a --no-r. Notez également que les effets secondaires de l'option --files-from ne sont PAS positionnels, car elle affecte l'état par défaut de plusieurs options et change légèrement la signification de -a (voir l'option --files-from pour plus de détails).
--recursive, -r
Ceci indique à rsync de copier les répertoires récursivement. Voir aussi --dirs (-d) pour une option qui permet l'analyse d'un seul répertoire.
Voir l'option --inc-recursive pour une discussion sur la récursion incrémentielle pour créer la liste des fichiers à transférer.
--inc-recursive, --i-r
Cette option active explicitement la récursion incrémentielle lors de la recherche de fichiers, qui est activée par défaut lorsque l'option --recursive est utilisée et que les deux côtés du transfert exécutent rsync 3.0.0 ou plus récent.
La récursion incrémentielle utilise beaucoup moins de mémoire que la récursion non incrémentielle, tout en commençant le transfert plus rapidement (car elle n'a pas besoin d'analyser toute la hiérarchie de transfert avant de commencer à transférer les fichiers). Si aucune récursion n'est activée dans les fichiers source, cette option n'a aucun effet.
Certaines options nécessitent que rsync connaisse la liste complète des fichiers, donc ces options désactivent le mode de récursion incrémentielle. Celles-ci incluent :
o
--delete-before (l'ancien défaut de --delete)
o
--delete-after
o
--prune-empty-dirs
o
--delay-updates
Afin de rendre --delete compatible avec la récursion incrémentielle, rsync 3.0.0 a fait de --delete-during le mode de suppression par défaut (qui a été ajouté pour la première fois dans la version 2.6.4).
Un effet secondaire de la récursion incrémentielle est que tous les sous-répertoires manquants à l'intérieur d'un répertoire scanné récursivement sont (par défaut) créés avant de récurer dans les sous-répertoires. Ce point de création précoce (par rapport à une récursion non incrémentielle) permet à rsync de définir ensuite l'heure de modification du répertoire terminé immédiatement (sans avoir à attendre que de nombreuses copies récursives soient terminées). Cependant, ces répertoires créés tôt n'ont pas encore leur mode, leur mtime ou leur propriété complets ; ils ont des droits plus restrictifs jusqu'à ce que la copie du sous-répertoire commence réellement. Cet idiome de création précoce peut être évité en utilisant l'option --omit-dir-times.
La récursion incrémentielle peut être désactivée en utilisant l'option --no-inc-recursive (--no-i-r).
--no-inc-recursive, --no-i-r
Désactive le nouvel algorithme de récursion incrémentielle de l'option --recursive. Cela oblige rsync à analyser la liste complète des fichiers avant de commencer à transférer les fichiers. Voir --inc-recursive pour plus d'informations.
--relative, -R
Utilise des chemins relatifs. Cela signifie que les noms de chemin complet spécifiés sur la ligne de commande sont envoyés au serveur plutôt que seulement les dernières parties des noms de fichiers. Ceci est particulièrement utile lorsque vous souhaitez envoyer plusieurs répertoires différents en même temps. Par exemple, si vous avez utilisé cette commande :
rsync -av /foo/bar/baz.c remote:/tmp/
créerait un fichier nommé baz.c dans /tmp/ sur la machine distante. Si, au lieu de cela, vous avez utilisé
rsync -avR /foo/bar/baz.c remote:/tmp/
alors un fichier nommé /tmp/foo/bar/baz.c serait créé sur la machine distante, préservant son chemin complet. Ces éléments de chemin supplémentaires sont appelés "répertoires implicites" (c'est-à-dire les répertoires "foo" et "foo/bar" dans l'exemple ci-dessus).
À partir de rsync 3.0.0, rsync envoie toujours ces répertoires implicites comme de vrais répertoires dans la liste des fichiers, même si un élément de chemin est réellement un lien symbolique du côté de l'expéditeur. Cela évite certains comportements vraiment inattendus lors de la copie du chemin complet d'un fichier dont vous ne saviez pas qu'il contenait un lien symbolique. Si vous souhaitez dupliquer un lien symbolique côté serveur, incluez à la fois le lien symbolique via son chemin et le répertoire référent via son chemin réel. Si vous avez affaire à une ancienne version de rsync côté expéditeur, vous devrez peut-être utiliser l'option --no-implied-dirs.
Il est également possible de limiter la quantité d'informations de chemin envoyées comme répertoires implicites pour chaque chemin que vous spécifiez. Avec une version moderne de rsync côté expéditeur (à partir de la version 2.6.7), vous pouvez insérer un point et une barre oblique dans le chemin source, comme ceci :
rsync -avR /foo/./bar/baz.c remote:/tmp/
Cela créerait /tmp/bar/baz.c sur la machine distante. (Notez que le point doit être suivi d'une barre oblique, donc "/foo/." ne serait pas abrégé.) Pour les versions plus anciennes de rsync, vous devriez utiliser un changement de répertoire (chdir) pour limiter le chemin source. Par exemple, lors de l'envoi de fichiers :
(cd /foo; rsync -avR bar/baz.c remote:/tmp/)
(Notez que les parenthèses placent les deux commandes dans un sous-shell, de sorte que la commande "cd" n'ait pas d'effet pour les commandes futures.) Si vous récupérez des fichiers d'un ancien rsync, utilisez cet idiome (mais seulement pour un transfert non-démon) :
rsync -avR --rsync-path="cd /foo; rsync" \
     remote:bar/baz.c /tmp/
--no-implied-dirs
Cette option affecte le comportement par défaut de l'option --relative. Lorsqu'elle est spécifiée, les attributs des répertoires implicites des noms source ne sont pas inclus dans le transfert. Cela signifie que les éléments de chemin correspondants sur le système de destination restent inchangés s'ils existent, et tous les répertoires implicites manquants sont créés avec des attributs par défaut. Cela permet même à ces éléments de chemin implicites d'avoir de grandes différences, comme être un lien symbolique vers un répertoire du côté récepteur.
Par exemple, si un argument de ligne de commande ou une entrée de fichiers-from indiquait à rsync de transférer le fichier "path/foo/file", les répertoires "path" et "path/foo" sont implicites lorsque --relative est utilisé. Si "path/foo" est un lien symbolique vers "bar" sur le système de destination, le rsync récepteur supprimerait normalement "path/foo", le recréerait en tant que répertoire et recevrait le fichier dans le nouveau répertoire. Avec --no-implied-dirs, le rsync récepteur met à jour "path/foo/file" en utilisant les éléments de chemin existants, ce qui signifie que le fichier finit par être créé dans "path/bar". Une autre façon d'accomplir cette préservation des liens est d'utiliser l'option --keep-dirlinks (qui affectera également les liens symboliques vers les répertoires dans le reste du transfert).
Lors de la récupération de fichiers à partir d'un rsync antérieur à 3.0.0, vous devrez peut-être utiliser cette option si le côté expéditeur a un lien symbolique dans le chemin que vous demandez et que vous souhaitez que les répertoires implicites soient transférés en tant que répertoires normaux.
--backup, -b
Avec cette option, les fichiers de destination préexistants sont renommés lors du transfert ou de la suppression de chaque fichier. Vous pouvez contrôler où le fichier de sauvegarde va et quel suffixe (le cas échéant) est ajouté en utilisant les options --backup-dir et --suffix.
Si vous ne spécifiez pas --backup-dir :
1.
l'option --omit-dir-times sera forcée
2.
l'utilisation de --delete (sans --delete-excluded) amène rsync à ajouter une règle de filtre "protect" pour le suffixe de sauvegarde à la fin de tous vos filtres existants, qui ressemble à ceci : -f "P *~". Cette règle empêche la suppression des fichiers sauvegardés précédemment.
Notez que si vous fournissez vos propres règles de filtre, vous devrez peut-être insérer manuellement votre propre règle d'exclusion/protection quelque part plus haut dans la liste afin qu'elle ait une priorité suffisamment élevée pour être efficace (par exemple, si vos règles spécifient une inclusion/exclusion finale de *, la règle ajoutée automatiquement ne serait jamais atteinte).
--backup-dir=DIR
Ceci implique l'option --backup, et indique à rsync de stocker toutes les sauvegardes dans le répertoire spécifié du côté récepteur. Ceci peut être utilisé pour des sauvegardes incrémentielles. Vous pouvez spécifier un suffixe de sauvegarde supplémentaire en utilisant l'option --suffix (sinon les fichiers sauvegardés dans le répertoire spécifié conserveront leurs noms de fichiers d'origine).
Notez que si vous spécifiez un chemin relatif, le répertoire de sauvegarde sera relatif au répertoire de destination, vous voudrez donc probablement spécifier un chemin absolu ou un chemin qui commence par "../". Si un démon rsync est le récepteur, le répertoire de sauvegarde ne peut pas sortir de la hiérarchie des chemins du module, alors prenez des précautions supplémentaires pour ne pas le supprimer ou y copier des fichiers.
--suffix=SUFFIX
Cette option vous permet de remplacer le suffixe de sauvegarde par défaut utilisé avec l'option --backup (-b). Le suffixe par défaut est un ~ si aucun --backup-dir n'a été spécifié, sinon c'est une chaîne vide.
--update, -u
Ceci oblige rsync à ignorer tous les fichiers qui existent sur la destination et dont l'heure de modification est plus récente que celle du fichier source. (Si un fichier de destination existant a une heure de modification égale à celle du fichier source, il sera mis à jour si les tailles sont différentes.)
Notez que cela n'affecte pas la copie des répertoires, des liens symboliques ou d'autres fichiers spéciaux. De plus, une différence de format de fichier entre l'expéditeur et le récepteur est toujours considérée comme suffisamment importante pour une mise à jour, quelle que soit la date des objets. En d'autres termes, si la source a un répertoire là où la destination a un fichier, le transfert se produirait indépendamment des horodatages.
Cette option est une RÈGLE DE TRANSFERT, n'attendez donc aucun effet secondaire d'exclusion.
Une mise en garde pour ceux qui choisissent de combiner --inplace avec --update : un transfert interrompu laissera derrière lui un fichier partiel du côté récepteur avec une heure de modification très récente, donc relancer le transfert ne continuera probablement pas le fichier interrompu. Par conséquent, il est généralement préférable d'éviter de combiner cela avec --inplace, sauf si vous avez mis en œuvre des étapes manuelles pour gérer les fichiers en cours d'interruption.
--inplace
Cette option modifie la façon dont rsync transfère un fichier lorsque ses données doivent être mises à jour : au lieu de la méthode par défaut qui consiste à créer une nouvelle copie du fichier et à la déplacer en place une fois terminée, rsync écrit directement les données mises à jour dans le fichier de destination.
Cela a plusieurs effets :
o
Les liens matériels ne sont pas brisés. Cela signifie que les nouvelles données seront visibles via d'autres liens matériels vers le fichier de destination. De plus, les tentatives de copie de fichiers sources différents sur un fichier de destination multi-liens entraîneront une "lutte à deux" avec les données de destination qui changent de manière répétée.
o
Les binaires en cours d'utilisation ne peuvent pas être mis à jour (soit le système d'exploitation l'empêchera, soit les binaires qui tentent d'échanger leurs données se comporteront mal ou planteront).
o
Les données du fichier seront dans un état incohérent pendant le transfert et resteront ainsi si le transfert est interrompu ou si une mise à jour échoue.
o
Un fichier auquel rsync ne peut pas écrire ne peut pas être mis à jour. Bien qu'un super utilisateur puisse mettre à jour n'importe quel fichier, un utilisateur normal doit se voir accorder la permission d'écriture pour que l'ouverture du fichier en écriture réussisse.
o
L'efficacité de l'algorithme de transfert delta de rsync peut être réduite si certaines données du fichier de destination sont écrasées avant de pouvoir être copiées vers une position ultérieure dans le fichier. Cela ne s'applique pas si vous utilisez --backup, car rsync est suffisamment intelligent pour utiliser le fichier de sauvegarde comme fichier de base pour le transfert.
ATTENTION : vous ne devez pas utiliser cette option pour mettre à jour des fichiers consultés par d'autres, soyez donc prudent lorsque vous choisissez de l'utiliser pour une copie.
Cette option est utile pour transférer de gros fichiers avec des modifications basées sur des blocs ou des données ajoutées, ainsi que sur des systèmes liés au disque, pas au réseau. Elle peut également aider à empêcher un instantané de système de fichiers en copie sur écriture de diverger du contenu entier d'un fichier qui n'a que des modifications mineures.
L'option implique --partial (puisqu'un transfert interrompu ne supprime pas le fichier), mais entre en conflit avec --partial-dir et --delay-updates. Avant rsync 2.6.4, --inplace était également incompatible avec --compare-dest et --link-dest.
--append
Ce mode de copie spécial fonctionne uniquement pour mettre à jour efficacement les fichiers dont on sait qu'ils grossissent et dont le contenu existant côté récepteur est également connu pour être identique au contenu côté expéditeur. L'utilisation de --append peut être dangereuse si vous n'êtes pas sûr à 100% que tous les fichiers du transfert sont partagés et en croissance. Vous devriez donc utiliser des règles de filtre pour vous assurer d'éliminer tous les fichiers qui ne correspondent pas à ces critères.
Rsync met à jour ces fichiers en croissance en place sans vérifier le contenu existant du fichier (il ne vérifie que le contenu qu'il ajoute). Rsync ignore tous les fichiers qui existent côté récepteur et qui ne sont pas plus courts que le fichier associé côté expéditeur (ce qui signifie que les nouveaux fichiers sont transférés). Il ignore également tous les fichiers dont la taille côté expéditeur diminue pendant les négociations d'envoi (rsync avertit d'un fichier "réduit" lorsque cela se produit).
Cela n'interfère pas avec la mise à jour des attributs non-contenu d'un fichier (par exemple, permissions, propriétaire, etc.) lorsque le fichier n'a pas besoin d'être transféré, ni n'affecte la mise à jour des répertoires ou des fichiers non-réguliers.
--append-verify
Ce mode de copie spécial fonctionne comme --append, sauf que toutes les données du fichier sont incluses dans la vérification de somme de contrôle (ce qui le rend moins efficace mais potentiellement plus sûr). Cette option peut être dangereuse si vous n'êtes pas sûr à 100% que tous les fichiers du transfert sont partagés et en croissance. Voir l'option --append pour plus de détails.
Note : avant rsync 3.0.0, l'option --append fonctionnait comme --append-verify, donc si vous interagissez avec un ancien rsync (ou si le transfert utilise un protocole antérieur à 30), spécifier l'une ou l'autre option d'ajout déclenchera un transfert --append-verify.
--dirs, -d
Indique au côté expéditeur d'inclure tous les répertoires rencontrés. Contrairement à --recursive, le contenu d'un répertoire n'est pas copié à moins que le nom du répertoire spécifié ne soit "." ou ne se termine par une barre oblique (par exemple, ".", "dir/.", "dir/", etc.). Sans cette option ou l'option --recursive, rsync ignorera tous les répertoires qu'il rencontre (et affichera un message à ce sujet pour chacun). Si vous spécifiez à la fois --dirs et --recursive, --recursive a la priorité.
L'option --dirs est implicite dans l'option --fil
--dirs, -d
Ajoute les répertoires à la liste des fichiers, ce qui est le comportement par défaut de rsync lorsqu'il est utilisé avec l'option --mkpath ou l'option --list-only (y compris une utilisation implicite de --list-only) si --recursive n'a pas été spécifié (afin que les répertoires soient visibles dans la liste). Spécifiez --no-dirs (ou --no-d) si vous souhaitez désactiver cela.
Il existe également une option d'aide pour la compatibilité ascendante, --old-dirs (--old-d) qui indique à rsync d'utiliser un subterfuge de -r --exclude='/*/*' pour qu'une ancienne version de rsync liste un seul répertoire sans récursion.
--mkpath
Crée tous les composants de chemin manquants du chemin de destination.
Par défaut, rsync autorise uniquement le dernier composant du chemin de destination à ne pas exister, ce qui est une tentative de vous aider à valider votre chemin de destination. Avec cette option, rsync crée tous les composants du chemin de destination manquants, comme si mkdir -p $DEST_PATH avait été exécuté du côté récepteur.
Lors de la spécification d'un chemin de destination, l'inclusion d'une barre oblique finale garantit que tout le chemin est traité comme des noms de répertoires à créer, même lorsque la liste de fichiers contient un seul élément. Voir la section COPIER VERS UN AUTRE NOM pour plus de détails sur la façon dont rsync décide si un composant final du chemin de destination doit être créé en tant que répertoire ou non.
Si vous souhaitez que les répertoires de destination nouvellement créés correspondent aux répertoires du côté de l'expéditeur, vous devez utiliser --relative (-R) au lieu de --mkpath. Par exemple, les deux commandes suivantes aboutissent à l'arborescence de destination identique, mais seule la deuxième commande garantit que les composants "some/extra/path" correspondent aux répertoires du côté de l'expéditeur :
rsync -ai --mkpath host:some/extra/path/*.c some/extra/path/
rsync -aiR host:some/extra/path/*.c ./
--links, -l
Ajoute des liens symboliques aux fichiers transférés au lieu de les ignorer bruyamment avec un avertissement "fichier non régulier" pour chaque lien symbolique rencontré. Vous pouvez alternativement faire taire l'avertissement en spécifiant --info=nonreg0.
Le traitement par défaut des liens symboliques est de recréer la valeur inchangée de chaque lien symbolique du côté récepteur.
Voir la section LIENS SYMBOLIQUES pour des informations multi-options.
--copy-links, -L
L'expéditeur transforme chaque lien symbolique rencontré lors du transfert en l'élément référencé, en suivant la chaîne de liens symboliques jusqu'au fichier ou répertoire qu'il référence. Si une chaîne de liens symboliques est rompue, une erreur est générée et le fichier est retiré du transfert.
Cette option remplace toutes les autres options qui affectent les liens symboliques dans le transfert, car il ne reste plus de liens symboliques dans le transfert.
Cette option ne modifie pas le traitement des liens symboliques existants du côté récepteur, contrairement aux versions de rsync antérieures à 2.6.3 qui avaient pour effet secondaire d'indiquer au récepteur de suivre également les liens symboliques. Une version moderne de rsync ne transmettra pas cette option à un récepteur distant (car seul l'expéditeur doit en être informé), donc cette mise en garde ne devrait affecter que ceux qui utilisent un client rsync plus ancien que 2.6.7 (date à laquelle -L a cessé d'être transmis au récepteur).
Voir --keep-dirlinks (-K) si vous avez besoin qu'un lien symbolique vers un répertoire soit traité comme un vrai répertoire du côté récepteur.
Voir la section LIENS SYMBOLIQUES pour des informations multi-options.
--copy-unsafe-links
Cela indique à rsync de copier le référent des liens symboliques qui pointent à l'extérieur de l'arborescence copiée. Les liens symboliques absolus sont également traités comme des fichiers ordinaires, tout comme les liens symboliques dans le chemin source lui-même lorsque --relative est utilisé.
Notez que le point de coupure est le sommet du transfert, qui est la partie du chemin que rsync ne mentionne pas dans la sortie détaillée. Si vous copiez "/src/subdir" vers "/dest/", alors le répertoire "subdir" est un nom à l'intérieur de l'arbre de transfert, pas le sommet du transfert (qui est /src), il est donc légal que les liens symboliques relatifs créés fassent référence à d'autres noms à l'intérieur des répertoires /src et /dest. Si vous copiez plutôt "/src/subdir/" (avec une barre oblique finale) vers "/dest/subdir", cela n'autoriserait pas les liens symboliques vers des fichiers en dehors de "subdir".
Notez que les liens symboliques sûrs ne sont copiés que si --links a également été spécifié ou implicite. L'option --copy-unsafe-links n'a aucun effet supplémentaire lorsqu'elle est combinée avec --copy-links.
Voir la section LIENS SYMBOLIQUES pour des informations multi-options.
--safe-links
Cela indique au rsync récepteur d'ignorer tous les liens symboliques dans le transfert qui pointent à l'extérieur de l'arborescence copiée. Tous les liens symboliques absolus sont également ignorés.
Étant donné que cette ignoration se produit du côté récepteur, elle sera toujours effective même lorsque le côté expéditeur a des liens symboliques modifiés (lorsqu'il utilise --munge-links). Elle affecte également les suppressions, car la présence du fichier dans le transfert empêche la suppression de tout fichier correspondant sur le récepteur lorsque le lien symbolique est jugé non sûr et est ignoré.
Cette option doit être combinée avec --links (ou --archive) pour que les liens symboliques dans le transfert soient conditionnellement ignorés. Son effet est supplanté par --copy-unsafe-links.
L'utilisation de cette option en conjonction avec --relative peut donner des résultats inattendus.
Voir la section LIENS SYMBOLIQUES pour des informations multi-options.
--munge-links
Cette option affecte un seul côté du transfert et indique à rsync de modifier les valeurs des liens symboliques lorsqu'il reçoit des fichiers ou de démodifier les valeurs des liens symboliques lorsqu'il envoie des fichiers. Les valeurs modifiées rendent les liens symboliques inutilisables sur le disque, mais permettent de récupérer le contenu d'origine des liens symboliques.
Le rsync côté serveur active souvent cette option à l'insu du client, par exemple dans un fichier de configuration de démon rsync ou par une option donnée au script rrsync (rsync restreint). Lorsqu'elle est spécifiée côté client, spécifiez l'option normalement si c'est le côté client qui a/a besoin des liens symboliques modifiés, ou utilisez -M--munge-links pour donner l'option au serveur lorsqu'il a/a besoin des liens symboliques modifiés. Notez que dans un transfert local, le client est l'expéditeur, donc spécifier l'option démodifie directement les liens symboliques tandis que la spécifier comme option distante les modifie.
Cette option n'a aucun effet lorsqu'elle est envoyée à un démon via --remote-option car le démon configure s'il souhaite des liens symboliques modifiés via son paramètre "munge symlinks".
La valeur du lien symbolique est modifiée/démodifiée une fois qu'elle est dans le transfert, donc toute option qui transforme les liens symboliques en non-liens symboliques se produit avant la modification/démodification, sauf pour --safe-links, qui est un choix fait par le récepteur, donc il base sa décision sur la valeur modifiée/démodifiée. Cela signifie que si un récepteur a la modification activée, l'utilisation de --safe-links entraînera l'ignorance de tous les liens symboliques (car ils sont tous absolus).
La méthode que rsync utilise pour modifier les liens symboliques est de préfixer leur valeur avec la chaîne "/rsyncd-munged/". Cela empêche les liens d'être utilisés tant que le répertoire n'existe pas. Lorsque cette option est activée, rsync refusera de s'exécuter si ce chemin est un répertoire ou un lien symbolique vers un répertoire (bien qu'il ne vérifie qu'au démarrage). Voir également le script python "munge-symlinks" dans le répertoire support du code source pour une façon de modifier/démodifier un ou plusieurs liens symboliques en place.
--copy-dirlinks, -k
Cette option amène le côté expéditeur à traiter un lien symbolique vers un répertoire comme s'il s'agissait d'un vrai répertoire. Ceci est utile si vous ne souhaitez pas que les liens symboliques vers des non-répertoires soient affectés, comme ce serait le cas avec --copy-links.
Sans cette option, si le côté expéditeur a remplacé un répertoire par un lien symbolique vers un répertoire, le côté récepteur supprimera tout ce qui gêne le nouveau lien symbolique, y compris une hiérarchie de répertoires (tant que --force ou --delete est en vigueur).
Voir également --keep-dirlinks pour une option analogue pour le côté récepteur.
--copy-dirlinks s'applique à tous les liens symboliques vers des répertoires dans la source. Si vous souhaitez suivre uniquement quelques liens symboliques spécifiés, une astuce que vous pouvez utiliser est de les passer comme arguments source supplémentaires avec une barre oblique finale, en utilisant --relative pour que les chemins correspondent correctement. Par exemple :
rsync -r --relative src/./ src/./follow-me/ dest/
Cela fonctionne car rsync appelle lstat(2) sur l'argument source tel qu'il est donné, et la barre oblique finale amène lstat(2) à suivre le lien symbolique, donnant lieu à un répertoire dans la liste de fichiers qui remplace le lien symbolique trouvé lors du parcours de "src/./".
Voir la section LIENS SYMBOLIQUES pour des informations multi-options.
--keep-dirlinks, -K
Cette option amène le côté récepteur à traiter un lien symbolique vers un répertoire comme s'il s'agissait d'un vrai répertoire, mais seulement s'il correspond à un vrai répertoire de l'expéditeur. Sans cette option, le lien symbolique du récepteur serait supprimé et remplacé par un vrai répertoire.
Par exemple, supposons que vous transférez un répertoire "foo" qui contient un fichier "file", mais que "foo" est un lien symbolique vers le répertoire "bar" sur le récepteur. Sans --keep-dirlinks, le récepteur supprime le lien symbolique "foo", le recrée en tant que répertoire et reçoit le fichier dans le nouveau répertoire. Avec --keep-dirlinks, le récepteur conserve le lien symbolique et "file" se retrouve dans "bar".
Une mise en garde : si vous utilisez --keep-dirlinks, vous devez faire confiance à tous les liens symboliques dans la copie ou activer l'option --munge-links du côté récepteur ! S'il est possible qu'un utilisateur non fiable crée son propre lien symbolique vers n'importe quel vrai répertoire, l'utilisateur pourrait alors (lors d'une copie ultérieure) remplacer le lien symbolique par un vrai répertoire et affecter le contenu de n'importe quel répertoire auquel le lien symbolique fait référence. Pour les copies de sauvegarde, il est préférable d'utiliser quelque chose comme un montage bind au lieu d'un lien symbolique pour modifier votre hiérarchie de réception.
Voir également --copy-dirlinks pour une option analogue pour l'expéditeur
côté.
Voir la section LIENS SYMBOLIQUES pour des informations sur plusieurs options.
--hard-links, -H
Ceci indique à rsync de rechercher les fichiers liés en dur dans la source et de lier ensemble les fichiers correspondants dans la destination. Sans cette option, les fichiers liés en dur dans la source sont traités comme s'ils étaient des fichiers séparés.
Cette option ne garantit PAS nécessairement que le modèle de liens en dur dans la destination corresponde exactement à celui de la source. Les cas où la destination peut se retrouver avec des liens en dur supplémentaires incluent les suivants :
o
Si la destination contient des liens en dur superflus (plus de liens que ce qui est présent dans la liste des fichiers source), l'algorithme de copie ne les cassera pas explicitement. Cependant, si un ou plusieurs des chemins présentent des différences de contenu, le processus normal de mise à jour des fichiers cassera ces liens supplémentaires (sauf si vous utilisez l'option --inplace).
o
Si vous spécifiez un répertoire --link-dest qui contient des liens en dur, la liaison des fichiers de destination par rapport aux fichiers --link-dest peut entraîner la liaison de certains chemins dans la destination en raison des associations --link-dest.
Notez que rsync ne peut détecter les liens en dur qu'entre les fichiers qui se trouvent dans l'ensemble du transfert. Si rsync met à jour un fichier qui a des connexions supplémentaires en liens en dur vers des fichiers en dehors du transfert, cette liaison sera rompue. Si vous êtes tenté d'utiliser l'option --inplace pour éviter cette rupture, soyez très attentif à la manière dont vos fichiers sont mis à jour afin d'être certain qu'aucun changement non intentionnel ne se produise en raison de liens en dur persistants (et consultez l'option --inplace pour plus de caveats).
Si la récursion incrémentale est active (voir --inc-recursive), rsync peut transférer un fichier lié en dur manquant avant de découvrir qu'un autre lien pour ce contenu existe ailleurs dans la hiérarchie. Cela n'affecte pas l'exactitude du transfert (c'est-à-dire quels fichiers sont liés en dur ensemble), seulement son efficacité (c'est-à-dire la copie des données pour une copie nouvelle et précoce d'un fichier lié en dur qui aurait pu être trouvé plus tard dans le transfert dans un autre membre de l'ensemble de fichiers liés en dur). Une façon d'éviter cette inefficacité est de désactiver la récursion incrémentale en utilisant l'option --no-inc-recursive.
--perms, -p
Cette option indique à rsync de définir les permissions de destination pour qu'elles soient les mêmes que les permissions source. (Voir aussi l'option --chmod pour modifier ce que rsync considère comme les permissions source.)
Lorsque cette option est désactivée, les permissions sont définies comme suit :
o
Les fichiers existants (y compris les fichiers mis à jour) conservent leurs permissions existantes, bien que l'option --executability puisse modifier uniquement la permission d'exécution pour le fichier.
o
Les nouveaux fichiers obtiennent leurs bits de permission « normaux » définis sur les permissions du fichier source masquées par les permissions par défaut du répertoire de destination (soit l'umask du processus de réception, soit les permissions spécifiées via la liste de contrôle d'accès par défaut du répertoire de destination), et leurs bits de permission spéciaux désactivés, sauf dans le cas où un nouveau répertoire hérite d'un bit setgid de son répertoire parent.
Ainsi, lorsque --perms et --executability sont tous deux désactivés, le comportement de rsync est identique à celui d'autres utilitaires de copie de fichiers, tels que cp(1) et tar(1).
En résumé : pour donner aux fichiers de destination (anciens et nouveaux) les permissions source, utilisez --perms. Pour donner aux nouveaux fichiers les permissions par défaut de la destination (tout en laissant les fichiers existants inchangés), assurez-vous que l'option --perms est désactivée et utilisez --chmod=ugo=rwX (ce qui garantit que tous les bits non masqués sont activés). Si vous souhaitez rendre ce dernier comportement plus facile à taper, vous pouvez définir un alias popt pour cela, par exemple en plaçant cette ligne dans le fichier ~/.popt (ce qui suit définit l'option -Z et inclut --no-g pour utiliser le groupe par défaut du répertoire de destination) :
rsync alias -Z --no-p --no-g --chmod=ugo=rwX
Vous pourriez alors utiliser cette nouvelle option dans une commande comme celle-ci :
rsync -avZ src/ dest/
(Caveat : assurez-vous que -a ne suit pas -Z, sinon il réactivera les deux options --no-* mentionnées ci-dessus.)
La préservation du bit setgid de destination sur les répertoires nouvellement créés lorsque --perms est désactivé a été ajoutée dans rsync 2.6.7. Les anciennes versions de rsync préservaient par erreur les trois bits de permission spéciaux pour les nouveaux fichiers lorsque --perms était désactivé, tout en remplaçant le réglage du bit setgid de destination sur un répertoire nouvellement créé. L'observation des ACL par défaut a été ajoutée au patch ACL pour rsync 2.6.7, donc les versions plus anciennes (ou sans ACL activées) de rsync utilisent l'umask même si des ACL par défaut sont présentes. (Gardez à l'esprit que c'est la version du rsync récepteur qui affecte ces comportements.)
--executability, -E
Cette option indique à rsync de préserver l'exécutabilité (ou la non-exécutabilité) des fichiers réguliers lorsque --perms n'est pas activé. Un fichier régulier est considéré comme exécutable si au moins un 'x' est activé dans ses permissions. Lorsqu'un fichier de destination existant a une exécutabilité différente de celle du fichier source correspondant, rsync modifie les permissions du fichier de destination comme suit :
o
Pour rendre un fichier non exécutable, rsync désactive toutes ses permissions 'x'.
o
Pour rendre un fichier exécutable, rsync active chaque permission 'x' qui a une permission 'r' correspondante activée.
Si --perms est activé, cette option est ignorée.
--acls, -A
Cette option indique à rsync de mettre à jour les ACL de destination pour qu'elles soient identiques aux ACL source. L'option implique également --perms.
Les systèmes source et destination doivent avoir des entrées ACL compatibles pour que cette option fonctionne correctement. Voir l'option --fake-super pour une méthode de sauvegarde et de restauration des ACL incompatibles.
--xattrs, -X
Cette option indique à rsync de mettre à jour les attributs étendus de destination pour qu'ils soient identiques à ceux de la source.
Pour les systèmes qui prennent en charge les espaces de noms d'attributs étendus, une copie effectuée par un super-utilisateur copie tous les espaces de noms sauf system.*. Un utilisateur normal ne copie que l'espace de noms user.*. Pour pouvoir sauvegarder et restaurer des espaces de noms non utilisateur en tant qu'utilisateur normal, voir l'option --fake-super.
Le filtrage de noms ci-dessus peut être contourné en utilisant une ou plusieurs options de filtre avec le modificateur x. Lorsque vous spécifiez une règle de filtrage affectant les xattr, rsync exige que vous effectuiez votre propre filtrage système/utilisateur, ainsi que tout filtrage supplémentaire pour les noms de xattr à copier et ceux autorisés à être supprimés. Par exemple, pour ignorer l'espace de noms système, vous pourriez spécifier :
--filter='-x system.*'
Pour ignorer tous les espaces de noms sauf l'espace de noms utilisateur, vous pourriez spécifier une correspondance utilisateur négative :
--filter='-x! user.*'
Pour empêcher la suppression d'attributs, vous pourriez spécifier une règle uniquement récepteur qui exclut tous les noms :
--filter='-xr *'
Notez que l'option -X ne copie pas les valeurs spéciales de xattr de rsync (par exemple, celles utilisées par --fake-super) à moins que vous ne répétiez l'option (par exemple, -XX). Ce mode « copier tous les xattrs » ne peut pas être utilisé avec --fake-super.
--chmod=CHMOD
Cette option indique à rsync d'appliquer un ou plusieurs modes « chmod » séparés par des virgules aux permissions des fichiers dans le transfert. La valeur résultante est traitée comme si c'était les permissions que le côté source a fournies pour le fichier, ce qui signifie que cette option peut sembler n'avoir aucun effet sur les fichiers existants si --perms n'est pas activé.
En plus des règles d'analyse normales spécifiées dans la page de manuel chmod(1), vous pouvez spécifier un élément qui ne doit s'appliquer qu'à un répertoire en le préfixant avec un 'D', ou spécifier un élément qui ne doit s'appliquer qu'à un fichier en le préfixant avec un 'F'. Par exemple, ce qui suit garantira que tous les répertoires obtiennent le bit set-gid, qu'aucun fichier ne soit inscriptible par les autres, que tous deux soient inscriptibles par l'utilisateur et le groupe, et que tous deux aient une exécutabilité cohérente sur tous les bits :
--chmod=Dg+s,ug+w,Fo-w,+X
L'utilisation de nombres de mode octaux est également autorisée :
--chmod=D2775,F664
Il est également légal de spécifier plusieurs options --chmod, car chaque option supplémentaire est simplement ajoutée à la liste des modifications à apporter.
Voir les options --perms et --executability pour savoir comment la valeur de permission résultante peut être appliquée aux fichiers du transfert.
--owner, -o
Cette option indique à rsync de définir le propriétaire du fichier de destination comme étant le même que celui du fichier source, mais uniquement si le rsync récepteur est exécuté en tant que super-utilisateur (voir aussi les options --super et --fake-super). Sans cette option, le propriétaire des nouveaux fichiers et/ou des fichiers transférés est défini sur l'utilisateur appelant du côté réception.
La préservation de la propriété associera les noms correspondants par défaut, mais peut se rabattre sur l'utilisation de l'identifiant numérique.
mber dans certaines circonstances (voir aussi l'option --numeric-ids pour une discussion complète).
--group, -g
Cette option fait que rsync attribue au fichier de destination le même groupe que le fichier source. Si le programme récepteur ne s'exécute pas en tant que super-utilisateur (ou si --no-super a été spécifié), seuls les groupes dont l'utilisateur appelant du côté récepteur est membre seront préservés. Sans cette option, le groupe est défini sur le groupe par défaut de l'utilisateur appelant du côté récepteur.
La préservation des informations de groupe associe les noms correspondants par défaut, mais peut se rabattre sur l'utilisation du numéro d'identifiant dans certaines circonstances (voir aussi l'option --numeric-ids pour une discussion complète).
--devices
Cette option fait que rsync transfère les fichiers de périphériques caractère et bloc vers le système distant pour recréer ces périphériques. Si le rsync récepteur ne s'exécute pas en tant que super-utilisateur, rsync ignore silencieusement la création des fichiers de périphériques (voir aussi les options --super et --fake-super).
Par défaut, rsync génère un avertissement « fichier non régulier » pour chaque fichier de périphérique rencontré lorsque cette option n'est pas définie. Vous pouvez supprimer l'avertissement en spécifiant --info=nonreg0.
--specials
Cette option fait que rsync transfère les fichiers spéciaux, tels que les sockets nommés et les FIFOs. Si le rsync récepteur ne s'exécute pas en tant que super-utilisateur, rsync ignore silencieusement la création des fichiers spéciaux (voir aussi les options --super et --fake-super).
Par défaut, rsync génère un avertissement « fichier non régulier » pour chaque fichier spécial rencontré lorsque cette option n'est pas définie. Vous pouvez supprimer l'avertissement en spécifiant --info=nonreg0.
-D
L'option -D est équivalente à « --devices --specials ».
--copy-devices
Cela indique à rsync de traiter un périphérique du côté émetteur comme un fichier régulier, lui permettant d'être copié vers un fichier de destination normal (ou un autre périphérique si --write-devices a également été spécifié).
Cette option est refusée par défaut par un démon rsync.
--write-devices
Cela indique à rsync de traiter un périphérique du côté récepteur comme un fichier régulier, permettant d'écrire des données de fichier dans un périphérique.
Cette option implique l'option --inplace.
Soyez prudent lors de l'utilisation de cette option, car vous devez savoir quels périphériques sont présents du côté récepteur du transfert, en particulier lors de l'exécution de rsync en tant que root.
Cette option est refusée par défaut par un démon rsync.
--times, -t
Cela indique à rsync de transférer les heures de modification avec les fichiers et de les mettre à jour sur le système distant. Notez que si cette option n'est pas utilisée, l'optimisation qui exclut les fichiers qui n'ont pas été modifiés ne peut pas être efficace ; en d'autres termes, une absence de -t (ou -a) entraînera le comportement du transfert suivant comme s'il utilisait --ignore-times (-I), provoquant la mise à jour de tous les fichiers (bien que l'algorithme de transfert delta de rsync rende la mise à jour assez efficace si les fichiers n'ont pas réellement changé, il est beaucoup plus judicieux d'utiliser -t).
Un rsync moderne qui utilise le protocole de transfert 30 ou 31 transmet une heure de modification sur 8 octets. Si rsync est obligé de parler un ancien protocole (peut-être en raison d'un rsync distant plus ancien que 3.0.0), une heure de modification est transmise sur 4 octets. Avant la version 3.2.7, ces valeurs de 4 octets pouvaient transmettre une plage de dates allant du 13 décembre 1901 au 19 janvier 2038. À partir de la version 3.2.7, ces valeurs de 4 octets transmettent maintenant une plage de dates allant du 1er janvier 1970 au 7 février 2106. Si vous avez des fichiers datant d'avant 1970, assurez-vous que vos exécutables rsync sont mis à jour afin que la plage complète des dates puisse être transmise.
--atimes, -U
Cela indique à rsync d'attribuer aux fichiers de destination les mêmes temps d'accès (utilisation) que les fichiers sources.
Si répété, il active également l'option --open-noatime, ce qui peut vous aider à faire en sorte que les systèmes d'envoi et de réception aient les mêmes temps d'accès sur les fichiers transférés sans avoir besoin d'exécuter rsync une fois supplémentaire après le transfert d'un fichier.
Notez que certaines anciennes versions de rsync (avant la 3.2.0) peuvent avoir été compilées avec un correctif bêta de --atimes qui n'implique pas --open-noatime lorsque cette option est répétée.
--open-noatime
Cela indique à rsync d'ouvrir les fichiers avec le drapeau O_NOATIME (sur les systèmes qui le prennent en charge) pour éviter de modifier le temps d'accès des fichiers qui sont en cours de transfert. Si votre système d'exploitation ne prend pas en charge le drapeau O_NOATIME, rsync ignorera silencieusement cette option. Notez également que certains systèmes de fichiers sont montés de manière à éviter la mise à jour du temps d'accès lors de la lecture, même sans le drapeau O_NOATIME.
--crtimes, -N,
Cela indique à rsync d'attribuer aux fichiers de destination les mêmes temps de création (nouveauté) que les fichiers sources. Votre système d'exploitation et votre système de fichiers doivent prendre en charge la définition de temps de création arbitraires pour que cette option soit prise en charge.
--omit-dir-times, -O
Cela indique à rsync d'omettre les répertoires lors de la préservation des temps de modification, d'accès et de création. Si NFS partage les répertoires du côté récepteur, il est conseillé d'utiliser -O. Cette option est déduite si vous utilisez --backup sans --backup-dir.
Cette option a également pour effet secondaire d'éviter la création précoce de sous-répertoires manquants lorsque la récursion incrémentielle est activée, comme expliqué dans la section --inc-recursive.
--omit-link-times, -J
Cela indique à rsync d'omettre les liens symboliques lors de la préservation des temps de modification, d'accès et de création.
--super
Cela indique au côté récepteur de tenter des activités de super-utilisateur même si le rsync récepteur n'a pas été exécuté par le super-utilisateur. Ces activités comprennent : la préservation des utilisateurs via l'option --owner, la préservation de tous les groupes (pas seulement les groupes de l'utilisateur courant) via l'option --group, et la copie de périphériques via l'option --devices. Ceci est utile pour les systèmes qui autorisent de telles activités sans être le super-utilisateur, et aussi pour s'assurer que vous obtiendrez des erreurs si le côté récepteur n'est pas exécuté en tant que super-utilisateur. Pour désactiver les activités de super-utilisateur, le super-utilisateur peut utiliser --no-super.
--fake-super
Lorsque cette option est activée, rsync simule les activités de super-utilisateur en sauvegardant/restaurant les attributs privilégiés via des attributs étendus spéciaux qui sont attachés à chaque fichier (au besoin). Cela inclut le propriétaire et le groupe du fichier (s'il ne s'agit pas de ceux par défaut), les informations sur le périphérique du fichier (les périphériques et fichiers spéciaux sont créés en tant que fichiers texte vides), et tous les bits de permission que nous n'autorisons pas à définir sur le vrai fichier (par exemple, le vrai fichier obtient u-s,g-s,o-t par sécurité) ou qui limiteraient l'accès du propriétaire (puisque le vrai super-utilisateur peut toujours accéder/modifier un fichier, les fichiers que nous créons peuvent toujours être accédés/modifiés par l'utilisateur créateur). Cette option gère également les ACLs (si --acls a été spécifié) et les attributs étendus non utilisateur (si --xattrs a été spécifié).
C'est une bonne façon de sauvegarder des données sans utiliser de super-utilisateur, et de stocker des ACLs provenant de systèmes incompatibles.
L'option --fake-super n'affecte que le côté où l'option est utilisée. Pour affecter le côté distant d'une connexion par shell distant, utilisez l'option --remote-option (-M) :
rsync -av -M--fake-super /src/ host:/dest/
Pour une copie locale, cette option affecte à la fois la source et la destination. Si vous souhaitez qu'une copie locale active cette option uniquement pour les fichiers de destination, spécifiez -M--fake-super. Si vous souhaitez qu'une copie locale active cette option uniquement pour les fichiers sources, combinez --fake-super avec -M--super.
Cette option est remplacée par --super et --no-super.
Voir aussi le réglage fake super dans le fichier rsyncd.conf du démon.
--sparse, -S
Essayer de gérer les fichiers épars efficacement afin qu'ils prennent moins de place sur la destination. S'il est combiné avec --inplace, le fichier créé pourrait ne pas avoir de blocs épars avec certaines combinaisons de version de noyau et/ou de type de système de fichiers. Si --whole-file est actif (par exemple, pour une copie locale), cela fonctionnera toujours car rsync tronque le fichier avant d'écrire la version mise à jour.
Notez que les versions de rsync antérieures à 3.1.3 refuseront la combinaison de --sparse et --inplace.
--preallocate
Cela indique au récepteur d'allouer chaque fichier de destination à sa taille définitive avant d'écrire des données dans le fichier. Rsync utilisera uniquement le support réel d'allocation préalable au niveau du système de fichiers fourni par l'appel système fallocate(2) de Linux ou posix_fallocate(3) de Cygwin, pas l'implémentation lente de glibc qui écrit un octet nul dans chaque bloc.
Sans cette option, les fichiers plus volumineux peuvent ne pas être entièrement contigus sur le système de fichiers, mais avec cette option, rsync copiera probablement plus lentement. Si la destination n'est pas un système de fichiers prenant en charge les étendues (comme ext4, xfs, NTFS, etc.), cette option peut n'avoir aucun effet positif.
Si combiné avec --sparse, le fichier n'aura que des blocs épars (par opposition à des séquences d'octets nuls alloués) si la version du noyau et le type de système de fichiers prennent en charge la création de trous dans les données allouées.
--dry-run, -n
Cela fait que rsync effectue une simulation qui n'apporte aucune modification (et produit à peu près le même résultat qu'une exécution réelle). Elle est le plus souvent utilisée en combinaison avec les options --verbose (-v) et/ou --itemize-changes (-i) pour voir ce qu'une commande rsync va faire avant de l'exécuter réellement.
La sortie de --itemize-ch
Un --dry-run (ou -n) doit se comporter exactement de la même manière qu'une exécution réelle (sauf erreurs de système intentionnelles ou appels système échoués) ; si ce n'est pas le cas, c'est un bug. Les autres sorties devraient être globalement inchangées, mais peuvent différer sur certains points. Notamment, un --dry-run n'envoie pas les données réelles pour les transferts de fichiers, donc --progress n'a aucun effet, les statistiques « octets envoyés », « octets reçus », « données littérales » et « données correspondantes » sont trop petites, et la valeur « accélération » est équivalente à une exécution où aucun transfert de fichier n'a été nécessaire.
--whole-file, -W
Cette option désactive l'algorithme de transfert par delta de rsync, ce qui oblige tous les fichiers transférés à être envoyés en entier. Le transfert peut être plus rapide si cette option est utilisée lorsque la bande passante entre les machines source et destination est supérieure à la bande passante vers le disque (en particulier lorsque le « disque » est en fait un système de fichiers réseau). C'est le comportement par défaut lorsque la source et la destination sont spécifiées comme des chemins locaux, mais seulement si aucune option d'écriture par lots n'est effective.
--no-whole-file, --no-W
Désactive la mise à jour de fichiers entiers lorsqu'elle est activée par défaut pour un transfert local. Cela ralentit généralement rsync, mais peut être utile si vous essayez de minimiser les écritures sur le fichier de destination (si combiné avec --inplace) ou pour tester l'algorithme de mise à jour basé sur la somme de contrôle.
Voir aussi l'option --whole-file.
--checksum-choice=STR, --cc=STR
Cette option remplace les algorithmes de somme de contrôle. Si un nom d'algorithme est spécifié, il est utilisé à la fois pour les sommes de contrôle de transfert et (en supposant que --checksum est spécifié) pour les sommes de contrôle avant transfert. Si deux noms séparés par une virgule sont fournis, le premier nom affecte les sommes de contrôle de transfert, et le second nom affecte les sommes de contrôle avant transfert (-c).
Les options de somme de contrôle que vous pouvez être en mesure d'utiliser sont :
o
auto (le choix automatique par défaut)
o
xxh128
o
xxh3
o
xxh64 (alias xxhash)
o
md5
o
md4
o
sha1
o
none
Exécutez rsync --version pour voir la liste par défaut des sommes de contrôle compilée dans votre version (qui peut différer de la liste ci-dessus).
Si « none » est spécifié pour le premier (ou unique) nom, l'option --whole-file est forcée et aucune vérification de somme de contrôle n'est effectuée sur les données transférées. Si « none » est spécifié pour le second (ou unique) nom, l'option --checksum ne peut pas être utilisée.
L'option « auto » est par défaut, où rsync base son choix d'algorithme sur une négociation entre le client et le serveur comme suit :
Lorsque les deux côtés du transfert sont au moins en version 3.2.0, rsync choisit le premier algorithme de la liste des choix du client qui est également dans la liste des choix du serveur. Si aucun choix commun de somme de contrôle n'est trouvé, rsync se termine avec une erreur. Si le rsync distant est trop ancien pour prendre en charge la négociation de somme de contrôle, une valeur est choisie en fonction de la version du protocole (qui choisit entre MD5 et diverses variantes de MD4 en fonction de l'âge du protocole).
L'ordre par défaut peut être personnalisé en définissant la variable d'environnement RSYNC_CHECKSUM_LIST avec une liste d'algorithmes de somme de contrôle acceptables séparés par des espaces. Si la chaîne contient un caractère « & », elle est séparée en « chaîne client & chaîne serveur », sinon la même chaîne s'applique aux deux. Si la chaîne (ou une partie de chaîne) ne contient aucun caractère non blanc, la liste par défaut des sommes de contrôle est utilisée. Cette méthode ne vous permet pas de spécifier la somme de contrôle de transfert séparément de la somme de contrôle avant transfert, et elle ignore « auto » et tous les noms de somme de contrôle inconnus. Une liste contenant uniquement des noms invalides entraîne un échec de négociation.
L'utilisation de l'option --checksum-choice remplace cette liste d'environnement.
--one-file-system, -x
Ceci indique à rsync d'éviter de traverser une frontière de système de fichiers lors de la récursion. Cela ne limite pas la capacité de l'utilisateur à spécifier des éléments à copier à partir de plusieurs systèmes de fichiers, mais seulement la récursion de rsync à travers la hiérarchie de chaque répertoire que l'utilisateur a spécifié, ainsi que la récursion analogue du côté réception lors de la suppression. Gardez également à l'esprit que rsync traite un montage « bind » vers le même périphérique comme étant sur le même système de fichiers.
Si cette option est répétée, rsync omet tous les répertoires de point de montage de la copie. Sinon, il inclut un répertoire vide à chaque point de montage qu'il rencontre (en utilisant les attributs du répertoire monté car ceux du répertoire de point de montage sous-jacent sont inaccessibles).
Si rsync a été invité à effondrer les liens symboliques (via --copy-links ou --copy-unsafe-links), un lien symbolique vers un répertoire sur un autre périphérique est traité comme un point de montage. Les liens symboliques vers des non-répertoires ne sont pas affectés par cette option.
--ignore-non-existing, --existing
Ceci indique à rsync d'ignorer la création de fichiers (y compris les répertoires) qui n'existent pas encore sur la destination. Si cette option est combinée avec l'option --ignore-existing, aucun fichier ne sera mis à jour (ce qui peut être utile si tout ce que vous voulez faire est de supprimer les fichiers superflus).
Cette option est une RÈGLE DE TRANSFERT, donc ne vous attendez pas à des effets secondaires d'exclusion.
--ignore-existing
Ceci indique à rsync d'ignorer la mise à jour des fichiers qui existent déjà sur la destination (cela n'ignore *pas* les répertoires existants, sinon rien ne serait fait). Voir aussi --ignore-non-existing.
Cette option est une RÈGLE DE TRANSFERT, donc ne vous attendez pas à des effets secondaires d'exclusion.
Cette option peut être utile pour ceux qui effectuent des sauvegardes en utilisant l'option --link-dest lorsqu'ils ont besoin de continuer une sauvegarde interrompue. Comme une exécution avec --link-dest est copiée dans une nouvelle hiérarchie de répertoires (lorsqu'elle est utilisée correctement), l'utilisation de [--ignore-existing garantira que les fichiers déjà traités ne seront pas modifiés (ce qui évite un changement de permissions sur les fichiers liés en dur). Cela signifie que cette option ne regarde que les fichiers existants dans la hiérarchie de destination elle-même.
Lorsque --info=skip2 est utilisé, rsync affichera des messages « FILENAME existe (INFO) » où INFO indique l'un des éléments suivants : « changement de type », « changement de somme » (nécessite -c), « changement de fichier » (basé sur la vérification rapide), « changement d'attribut », ou « à jour ». L'utilisation de --info=skip1 (qui est également implicite avec 2 options -v) affiche le message d'existence sans le suffixe INFO.
--remove-source-files
Ceci indique à rsync de supprimer du côté expéditeur les fichiers (c'est-à-dire les non-répertoires) qui font partie du transfert et qui ont été dupliqués avec succès sur le côté récepteur.
Notez que vous ne devriez utiliser cette option que sur des fichiers source qui sont quiescents. Si vous l'utilisez pour déplacer des fichiers qui apparaissent dans un répertoire particulier vers un autre hôte, assurez-vous que les fichiers terminés sont renommés dans le répertoire source, et non écrits directement dedans, afin que rsync ne puisse pas transférer un fichier qui n'est pas encore entièrement écrit. Si vous ne pouvez pas d'abord écrire les fichiers dans un répertoire différent, vous devriez utiliser un idiome de nommage qui permet à rsync d'éviter de transférer les fichiers qui ne sont pas encore terminés (par exemple, nommez le fichier « foo.new » lorsqu'il est écrit, renommez-le « foo » lorsqu'il est terminé, puis utilisez l'option --exclude='*.new' pour le transfert rsync).
À partir de la version 3.1.0, rsync sautera la suppression côté expéditeur (et affichera une erreur) si la taille ou l'heure de modification du fichier n'est pas restée inchangée.
À partir de la version 3.2.6, une copie rsync locale s'assurera que l'expéditeur ne supprime pas un fichier que le récepteur vient de vérifier, par exemple lorsque l'utilisateur rend accidentellement le répertoire source et le répertoire de destination identiques.
--delete
Ceci indique à rsync de supprimer les fichiers superflus du côté récepteur (ceux qui ne sont pas du côté expéditeur), mais uniquement pour les répertoires qui sont synchronisés. Vous devez avoir demandé à rsync d'envoyer tout le répertoire (par exemple, « dir » ou « dir/ ») sans utiliser de wildcard pour le contenu du répertoire (par exemple, « dir/* ») car la wildcard est développée par le shell et rsync reçoit ainsi une requête pour transférer des fichiers individuels, et non le répertoire parent des fichiers. Les fichiers qui sont exclus du transfert sont également exclus de la suppression, sauf si vous utilisez l'option --delete-excluded ou si vous marquez les règles comme ne correspondant que du côté expéditeur (voir les modificateurs d'inclusion/exclusion dans la section des RÈGLES DE FILTRAGE).
Avant rsync 2.6.7, cette option n'avait aucun effet à moins que --recursive ne soit activé. Depuis 2.6.7, les suppressions se produiront également lorsque --dirs (-d) est activé, mais uniquement pour les répertoires dont le contenu est copié.
Cette option peut être dangereuse si elle est utilisée incorrectement ! Il est fortement recommandé d'essayer d'abord une exécution en utilisant l'option --dry-run (-n) pour voir quels fichiers vont être supprimés.
Si le côté expéditeur détecte des erreurs d'E/S, alors la suppression de tous les fichiers sur la destination sera automatiquement désactivée. Ceci afin d'empêcher les échecs temporaires de système de fichiers (tels que les erreurs NFS) du côté expéditeur de provoquer une suppression massive de fichiers sur la destination. Vous pouvez outrepasser cela avec l'option --ignore-errors.
L'option --delete peut être combinée avec l'une des options --delete-WHEN sans conflit, ainsi qu'avec --delete-excluded. Cependant, si aucune des options --delete-WHEN n'est spécifiée, rsync choisira l'algorithme --delete-during lorsqu'il communique avec rsync 3.0.0 ou plus récent, ou l'algorithme --delete-before lorsqu'il
talking to an older rsync. See also --delete-delay and --delete-after.
--delete-before
Demande que les suppressions de fichiers côté réception soient effectuées avant le début du transfert. Voir --delete (qui est implicite) pour plus de détails sur la suppression de fichiers.
La suppression avant le transfert est utile si le système de fichiers manque d'espace et que la suppression de fichiers superflus pourrait aider à rendre le transfert possible. Cependant, cela introduit un délai avant le début du transfert, et ce délai pourrait entraîner un timeout du transfert (si --timeout a été spécifié). Cela force également rsync à utiliser l'ancien algorithme de récursion non incrémentiel qui oblige rsync à charger tous les fichiers du transfert en mémoire en une seule fois (voir --recursive).
--delete-during, --del
Demande que les suppressions de fichiers côté réception soient effectuées de manière incrémentielle au fur et à mesure du transfert. L'analyse des suppressions par répertoire est effectuée juste avant la vérification des mises à jour de chaque répertoire, de sorte qu'elle se comporte comme un --delete-before plus efficace, y compris en effectuant les suppressions avant la mise à jour de tout fichier de filtre par répertoire. Cette option a été ajoutée pour la première fois dans la version 2.6.4 de rsync. Voir --delete (qui est implicite) pour plus de détails sur la suppression de fichiers.
--delete-delay
Demande que les suppressions de fichiers côté réception soient calculées pendant le transfert (comme --delete-during), puis supprimées après la fin du transfert. C'est utile lorsqu'il est combiné avec --delay-updates et/ou --fuzzy, et est plus efficace que d'utiliser --delete-after (mais peut se comporter différemment, car --delete-after calcule les suppressions dans un passage séparé après que toutes les mises à jour soient terminées). Si le nombre de fichiers supprimés dépasse un tampon interne, un fichier temporaire sera créé côté réception pour y stocker les noms (il est supprimé pendant qu'il est ouvert, vous ne devriez donc pas le voir pendant le transfert). Si la création du fichier temporaire échoue, rsync essaiera de revenir à l'utilisation de --delete-after (ce qu'il ne peut pas faire si --recursive effectue une analyse incrémentielle). Voir --delete (qui est implicite) pour plus de détails sur la suppression de fichiers.
--delete-after
Demande que les suppressions de fichiers côté réception soient effectuées après la fin du transfert. C'est utile si vous envoyez de nouveaux fichiers de fusion par répertoire dans le cadre du transfert et que vous souhaitez que leurs exclusions prennent effet pour la phase de suppression du transfert en cours. Cela force également rsync à utiliser l'ancien algorithme de récursion non incrémentiel qui oblige rsync à charger tous les fichiers du transfert en mémoire en une seule fois (voir --recursive). Voir --delete (qui est implicite) pour plus de détails sur la suppression de fichiers.
Voir également l'option --delete-delay qui pourrait être un choix plus rapide pour ceux qui veulent simplement que les suppressions se produisent à la fin du transfert.
--delete-excluded
Cette option transforme toutes les règles d'exclusion/inclusion non qualifiées en règles côté serveur qui n'affectent pas les suppressions du récepteur.
Par défaut, une exclusion ou une inclusion a un effet côté serveur (pour "masquer" et "afficher" les fichiers lors de la construction de la liste de fichiers du serveur) et un effet côté récepteur (pour "protéger" et "risquer" les fichiers lors des suppressions). Toute règle qui n'a pas de modificateur pour spécifier les côtés sur lesquels elle est exécutée sera plutôt traitée comme une règle côté serveur uniquement, évitant ainsi tout effet de "protection" des règles.
Une règle peut toujours s'appliquer aux deux côtés même avec cette option spécifiée si la règle reçoit les lettres modificateurs sender & receiver (par exemple, -f'-sr foo'). Les règles de protection/risque côté récepteur peuvent également être spécifiées explicitement pour limiter les suppressions. Cela vous évite d'avoir à modifier un tas de règles -f'- foo' en règles -f'-s foo' (alias -f'H foo') (sans parler des inclusions correspondantes).
Voir la section FILTER RULES pour plus d'informations. Voir --delete (qui est implicite) pour plus de détails sur la suppression.
--ignore-missing-args
Lorsque rsync traite d'abord les fichiers source explicitement demandés (par exemple, arguments de ligne de commande ou entrées --files-from), c'est normalement une erreur si le fichier ne peut pas être trouvé. Cette option supprime cette erreur et n'essaie pas de transférer le fichier. Cela n'affecte pas les erreurs ultérieures de fichier disparu si un fichier a été initialement trouvé présent et qu'il n'est plus là par la suite.
--delete-missing-args
Cette option pousse le comportement de l'option (implicite) --ignore-missing-args un peu plus loin : chaque argument manquant deviendra une demande de suppression du fichier de destination correspondant côté réception (s'il existe). Si le fichier de destination est un répertoire non vide, il ne sera supprimé avec succès que si --force ou --delete sont en vigueur. Autrement, cette option est indépendante de tout autre type de traitement de suppression.
Les fichiers source manquants sont représentés par des entrées spéciales dans la liste de fichiers qui s'affichent comme une entrée "*missing" dans la sortie --list-only.
--ignore-errors
Indique à --delete de continuer à supprimer des fichiers même en cas d'erreurs d'E/S.
--force
Cette option indique à rsync de supprimer un répertoire non vide lorsqu'il doit être remplacé par un non-répertoire. Ceci n'est pertinent que si les suppressions ne sont pas actives (voir --delete pour les détails).
Note pour les anciennes versions de rsync : --force était autrefois encore nécessaire lors de l'utilisation de --delete-after, et il était autrefois inopérant à moins que l'option --recursive ne soit également activée.
--max-delete=NUM
Ceci indique à rsync de ne pas supprimer plus de NUM fichiers ou répertoires. Si cette limite est dépassée, toutes les suppressions ultérieures sont ignorées jusqu'à la fin du transfert. À la fin, rsync affiche un avertissement (y compris un compte des suppressions ignorées) et se termine avec un code d'erreur de 25 (sauf si une condition d'erreur plus importante s'est également produite).
À partir de la version 3.0.0, vous pouvez spécifier --max-delete=0 pour être averti de tout fichier supplémentaire dans la destination sans en supprimer aucun. Les clients plus anciens interprétaient cela comme "illimité", donc si vous ne connaissez pas la version du client, vous pouvez utiliser le moins évident --max-delete=-1 comme moyen rétrocompatible de spécifier qu'aucune suppression ne doit être autorisée (bien que les versions très anciennes n'aient pas averti lorsque la limite était dépassée).
--max-size=SIZE
Ceci indique à rsync d'éviter de transférer tout fichier dont la taille est supérieure à la taille spécifiée. Une valeur numérique peut être suffixée par une chaîne pour indiquer les unités numériques ou laissée sans qualification pour spécifier des octets. N'hésitez pas à utiliser une valeur fractionnaire avec les unités, telle que --max-size=1.5m.
Cette option est une RÈGLE DE TRANSFERT, n'attendez donc aucun effet secondaire d'exclusion.
La première lettre d'une chaîne d'unités peut être B (octets), K (kilo), M (méga), G (giga), T (téra), ou P (péta). Si la chaîne est un seul caractère ou si "ib" lui est ajouté (par exemple, "G" ou "GiB"), alors les unités sont des multiples de 1024. Si vous utilisez un suffixe à deux lettres se terminant par "B" (par exemple, "kb"), vous obtenez des unités qui sont des multiples de 1000. Les lettres de la chaîne peuvent être un mélange de majuscules et de minuscules selon votre préférence.
Enfin, si la chaîne se termine par "+1" ou "-1", elle est décalée d'un octet dans la direction indiquée. La valeur la plus grande possible est généralement 8192P-1.
Exemples : --max-size=1.5mb-1 est égal à 1499999 octets, et --max-size=2g+1 est égal à 2147483649 octets.
Notez que les versions de rsync antérieures à 3.1.0 ne permettaient pas --max-size=0.
--min-size=SIZE
Ceci indique à rsync d'éviter de transférer tout fichier plus petit que la taille spécifiée, ce qui peut aider à ne pas transférer de petits fichiers inutiles. Voir l'option --max-size pour une description de SIZE et d'autres informations.
Notez que les versions de rsync antérieures à 3.1.0 ne permettaient pas --min-size=0.
--max-alloc=SIZE
Par défaut, rsync limite chaque malloc/realloc individuel à environ 1 Go. Pour la plupart des utilisateurs, cette limite fonctionne parfaitement et empêche une erreur de protocole de faire en sorte que rsync demande une quantité massive de mémoire. Cependant, si vous avez plusieurs millions de fichiers dans un transfert, une grande quantité de mémoire côté serveur, et que vous ne souhaitez pas diviser votre transfert en plusieurs parties, vous pouvez augmenter la limite par allocation à quelque chose de plus grand et rsync consommera plus de mémoire.
Gardez à l'esprit qu'il ne s'agit pas d'une limite sur la taille totale de la mémoire allouée. C'est une valeur de vérification de sanity pour chaque allocation individuelle.
Voir l'option --max-size pour une description de la façon dont SIZE peut être spécifié. Le suffixe par défaut s'il n'y en a pas est "octets".
À partir de la version 3.2.7, une valeur de 0 est un moyen simple de spécifier SIZE_MAX (la limite la plus grande possible).
Vous pouvez définir une valeur par défaut en utilisant la variable d'environnement RSYNC_MAX_ALLOC en utilisant les mêmes valeurs de SIZE que celles prises en charge par cette option. Si le rsync distant ne comprend pas l'option --max-alloc, vous pouvez remplacer une valeur environnementale en spécifiant --max-alloc=1g, ce qui fera en sorte que rsync évite d'envoyer l'option au côté distant (car "1G" est la valeur par défaut).
--block-size=SIZE, -B
Ceci force la taille des blocs utilisée dans l'algorithme de transfert delta de rsync à une valeur fixe. Elle est normalement sélectionnée en fonction de la taille de chaque fichier mis à jour. Voir le rapport technique pour les détails.
À partir de la version 3.2.3, la taille peut être spécifiée avec un suffixe comme détaillé dans l'option --max-size. Les versions plus anciennes n'acceptaient qu'un nombre d'octets.
--rsh=COMMAND, -e
Cette option vous permet de choisir un
Un programme de shell distant alternatif à utiliser pour la communication entre les copies locales et distantes de rsync. Typiquement, rsync est configuré pour utiliser ssh par défaut, mais vous pourriez préférer utiliser rsh sur un réseau local.
Si cette option est utilisée avec [user@]host::module/path, alors le shell distant COMMAND sera utilisé pour lancer un démon rsync sur l'hôte distant, et toutes les données seront transmises via cette connexion shell distante, plutôt que via une connexion socket directe à un démon rsync en cours d'exécution sur l'hôte distant. Voir la section UTILISATION DES FONCTIONNALITÉS DE RSYNC-DAEMON VIA UNE CONNEXION REMOTE-SHELL ci-dessus.
À partir de rsync 3.2.0, la variable d'environnement RSYNC_PORT sera définie lorsqu'une connexion démon est établie via une connexion remote-shell. Elle est définie sur 0 si le port démon par défaut est supposé, ou elle est définie sur la valeur du port rsync spécifié via l'option --port ou une valeur de port non vide dans une URL rsync://. Cela permet au script de déterminer si un port non standard est demandé, permettant par exemple à un script d'assistance SSL ou stunnel de se connecter à un port par défaut ou alternatif.
Les arguments en ligne de commande sont autorisés dans COMMAND à condition que COMMAND soit présenté à rsync comme un seul argument. Vous devez utiliser des espaces (pas des tabulations ou d'autres espaces blancs) pour séparer la commande et les arguments les uns des autres, et vous pouvez utiliser des guillemets simples et/ou doubles pour préserver les espaces dans un argument (mais pas les barres obliques inverses). Notez que doubler un guillemet simple à l'intérieur d'une chaîne entre guillemets simples donne un guillemet simple ; de même pour les guillemets doubles (bien que vous deviez faire attention aux guillemets que votre shell analyse et à ceux que rsync analyse). Quelques exemples :
-e 'ssh -p 2234'
-e 'ssh -o "ProxyCommand nohup ssh firewall nc -w1 %h %p"'
(Notez que les utilisateurs de ssh peuvent alternativement personnaliser les options de connexion spécifiques au site dans leur fichier .ssh/config.)
Vous pouvez également choisir le programme de shell distant en utilisant la variable d'environnement RSYNC_RSH, qui accepte la même gamme de valeurs que -e.
Voir aussi l'option --blocking-io qui est affectée par cette option.
--rsync-path=PROGRAM
Utilisez ceci pour spécifier quel programme doit être exécuté sur la machine distante pour démarrer rsync. Souvent utilisé lorsque rsync n'est pas dans le chemin du shell distant par défaut (par exemple, --rsync-path=/usr/local/bin/rsync). Notez que PROGRAM est exécuté à l'aide d'un shell, il peut donc s'agir de n'importe quel programme, script ou séquence de commandes que vous souhaitez exécuter, tant qu'il ne corrompt pas les entrées standard et sorties standard que rsync utilise pour communiquer.
Un exemple délicat est de définir un répertoire par défaut différent sur la machine distante pour l'option --relative. Par exemple :
rsync -avR --rsync-path="cd /a/b && rsync" host:c/d /e/
--remote-option=OPTION, -M
Cette option est utilisée pour des situations plus avancées où vous voulez que certains effets soient limités à un seul côté du transfert. Par exemple, si vous voulez passer --log-file=FILE et --fake-super au système distant, spécifiez-le comme suit :
rsync -av -M --log-file=foo -M--fake-super src/ dest/
Si vous voulez qu'une option affecte uniquement le côté local d'un transfert alors qu'elle affecte normalement les deux côtés, envoyez sa négation à l'autre côté. Comme ceci :
rsync -av -x -M--no-x src/ dest/
Soyez prudent en utilisant cela, car il est possible de basculer une option qui fera que rsync aura une idée différente de quelles données attendre ensuite sur le socket, et cela provoquera une erreur de manière cryptique.
Notez que vous devez utiliser une option -M distincte pour chaque option distante que vous souhaitez passer. Sur les anciennes versions de rsync, la présence de n'importe quel espace dans l'argument remote-option pouvait entraîner sa division en arguments distants séparés, mais cela nécessite l'utilisation de --old-args dans un rsync moderne.
Lors d'un transfert local, le côté « local » est l'expéditeur et le côté « distant » est le récepteur.
Notez que certaines versions de la bibliothèque d'analyse d'options popt ont un bug qui vous empêche d'utiliser un argument adjacent avec un égal à l'intérieur à côté d'une lettre d'option courte (par exemple, -M--log-file=/tmp/foo). Si ce bug affecte votre version de popt, vous pouvez utiliser la version de popt incluse avec rsync.
--cvs-exclude, -C
Ceci est un raccourci utile pour exclure un large éventail de fichiers que vous ne souhaitez souvent pas transférer entre systèmes. Il utilise un algorithme similaire à celui de CVS pour déterminer si un fichier doit être ignoré.
La liste d'exclusion est initialisée pour exclure les éléments suivants (ces éléments initiaux sont marqués comme périssables -- voir la section RÈGLES DE FILTRAGE) :
RCS SCCS CVS CVS.adm RCSLOG cvslog.* tags TAGS .make.state .nse_depinfo *~ #* .#* ,* _$* *$ *.old *.bak *.BAK *.orig *.rej .del-* *.a *.olb *.o *.obj *.so *.exe *.Z *.elc *.ln core .svn/ .git/ .hg/ .bzr/
ensuite, les fichiers listés dans un $HOME/.cvsignore sont ajoutés à la liste et tous les fichiers listés dans la variable d'environnement CVSIGNORE (tous les noms cvsignore sont délimités par des espaces).
Enfin, tout fichier est ignoré s'il se trouve dans le même répertoire qu'un fichier .cvsignore et correspond à l'un des motifs listés dans celui-ci. Contrairement aux fichiers de filtre/exclusion de rsync, ces motifs sont séparés par des espaces. Voir le manuel cvs(1) pour plus d'informations.
Si vous combinez -C avec vos propres règles --filter, vous devriez noter que ces exclusions CVS sont ajoutées à la fin de vos propres règles, quelle que soit la position de -C sur la ligne de commande. Cela leur donne une priorité inférieure à celle de toutes les règles que vous avez spécifiées explicitement. Si vous souhaitez contrôler où ces exclusions CVS sont insérées dans vos règles de filtre, vous devriez omettre -C comme option de ligne de commande et utiliser une combinaison de --filter=:C et --filter=-C (soit sur votre ligne de commande, soit en plaçant les règles « :C » et « -C » dans un fichier de filtre avec vos autres règles). La première option active la recherche par répertoire pour le fichier .cvsignore. La deuxième option effectue une importation unique des exclusions CVS mentionnées ci-dessus.
--filter=RULE, -f
Cette option vous permet d'ajouter des règles pour exclure sélectivement certains fichiers de la liste des fichiers à transférer. C'est plus utile en combinaison avec un transfert récursif.
Vous pouvez utiliser autant d'options --filter sur la ligne de commande que vous le souhaitez pour construire la liste des fichiers à exclure. Si le filtre contient des espaces, assurez-vous de le mettre entre guillemets afin que le shell donne la règle à rsync comme un seul argument. Le texte ci-dessous mentionne également que vous pouvez utiliser un underscore pour remplacer l'espace qui sépare une règle de son argument.
Voir la section RÈGLES DE FILTRAGE pour des informations détaillées sur cette option.
-F
L'option -F est un raccourci pour ajouter deux règles --filter à votre commande. La première fois qu'elle est utilisée, elle est un raccourci pour cette règle :
--filter='dir-merge /.rsync-filter'
Cela indique à rsync de rechercher des fichiers .rsync-filter par répertoire qui ont été parsemés dans la hiérarchie et d'utiliser leurs règles pour filtrer les fichiers du transfert. Si -F est répété, c'est un raccourci pour cette règle :
--filter='exclude .rsync-filter'
Cela filtre les fichiers .rsync-filter eux-mêmes du transfert.
Voir la section RÈGLES DE FILTRAGE pour des informations détaillées sur le fonctionnement de ces options.
--exclude=PATTERN
Cette option est une forme simplifiée de l'option --filter qui spécifie une règle d'exclusion et n'autorise pas la syntaxe complète d'analyse de règles des règles de filtre normales. Ceci est équivalent à spécifier -f'- PATTERN'.
Voir la section RÈGLES DE FILTRAGE pour des informations détaillées sur cette option.
--exclude-from=FILE

Les lignes vides dans le fichier sont ignorées, tout comme les commentaires sur ligne entière qui commencent par ';' ou '#' (les règles de nom de fichier qui contiennent ces caractères ne sont pas affectées).

Si FILE est '-', la liste sera lue depuis l'entrée standard.

Voir la section RÈGLES DE FILTRAGE pour des informations détaillées sur cette option.

Si une ligne commence par "-&nbsp;" (tiret, espace) ou "+&nbsp;" (plus, espace), alors le type de règle est explicitement spécifié comme une exclusion ou une inclusion (respectivement). Toutes les règles sans ce préfixe sont considérées comme une inclusion.
Si une ligne ne contient que "!", les règles de filtre actuelles sont effacées avant d'ajouter toute autre règle.
Si FICHIER est '-', la liste sera lue depuis l'entrée standard.
--files-from=FICHIER
L'utilisation de cette option vous permet de spécifier la liste exacte des fichiers à transférer (lue depuis le FICHIER spécifié ou '-' pour l'entrée standard). Elle modifie également le comportement par défaut de rsync pour faciliter le transfert des fichiers et répertoires spécifiés :
o
L'option --relative (-R) est implicite, ce qui préserve les informations de chemin spécifiées pour chaque élément dans le fichier (utilisez --no-relative ou --no-R si vous voulez désactiver cela).
o
L'option --dirs (-d) est implicite, ce qui créera les répertoires spécifiés dans la liste sur la destination plutôt que de les ignorer bruyamment (utilisez --no-dirs ou --no-d si vous voulez désactiver cela).
o
Le comportement de l'option --archive (-a) n'implique pas --recursive (-r), spécifiez-la donc explicitement si vous le souhaitez.
o
Ces effets secondaires modifient l'état par défaut de rsync, donc la position de l'option --files-from dans la ligne de commande n'a aucune incidence sur la façon dont les autres options sont analysées (par exemple, -a fonctionne de la même manière avant ou après --files-from, tout comme --no-R et toutes les autres options).
Les noms de fichiers lus depuis le FICHIER sont tous relatifs au répertoire source&nbsp;-- toute barre oblique initiale est supprimée et aucune référence ".." n'est autorisée à remonter plus haut que le répertoire source. Par exemple, prenons cette commande :
rsync -a --files-from=/tmp/foo /usr remote:/backup
Si /tmp/foo contient la chaîne "bin" (ou même "/bin"), le répertoire /usr/bin sera créé sous /backup/bin sur l'hôte distant. S'il contient "bin/" (notez la barre oblique finale), le contenu immédiat du répertoire serait également envoyé (sans avoir besoin d'être explicitement mentionné dans le fichier&nbsp;-- ceci a commencé dans la version 2.6.4). Dans les deux cas, si l'option -r était activée, toute la hiérarchie de ce répertoire serait également transférée (gardez à l'esprit que -r doit être spécifié explicitement avec --files-from, car il n'est pas implicite avec -a. Notez également que l'effet de l'option (activée par défaut) -r est de dupliquer uniquement les informations de chemin lues à partir du fichier&nbsp;-- elle ne force pas la duplication du chemin de spécification source (dans ce cas, /usr).
De plus, le fichier --files-from peut être lu depuis l'hôte distant plutôt que depuis l'hôte local si vous spécifiez un "hôte:" avant le fichier (l'hôte doit correspondre à l'une des extrémités du transfert). En raccourci, vous pouvez spécifier juste un préfixe de ":" pour signifier "utiliser l'extrémité distante du transfert". Par exemple :
rsync -a --files-from=:/path/file-list src:/ /tmp/copy
Ceci copierait tous les fichiers spécifiés dans le fichier /path/file-list qui se trouve sur l'hôte distant "src".
Si les options --iconv et --secluded-args sont spécifiées et que les noms de fichiers --files-from sont envoyés d'un hôte à un autre, les noms de fichiers seront traduits du jeu de caractères de l'hôte d'envoi vers celui de l'hôte de réception.
REMARQUE : trier la liste des fichiers dans l'entrée --files-from aide rsync à être plus efficace, car il évitera de revisiter les éléments de chemin qui sont partagés entre les entrées adjacentes. Si l'entrée n'est pas triée, certains éléments de chemin (répertoires implicites) peuvent finir par être analysés plusieurs fois, et rsync les dédupliquera éventuellement après qu'ils soient transformés en éléments de liste de fichiers.
--from0, -0
Ceci indique à rsync que les règles/noms de fichiers qu'il lit d'un fichier sont terminés par un caractère null ('\0') et non par un NL, CR ou CR+LF. Ceci affecte --exclude-from, --include-from, --files-from, et tous les fichiers fusionnés spécifiés dans une règle --filter. Cela n'affecte pas --cvs-exclude (car tous les noms lus à partir d'un fichier .cvsignore sont séparés par des espaces).
--old-args
Cette option indique à rsync d'arrêter d'essayer de protéger les valeurs des arguments du côté distant contre la division de mots non intentionnelle ou d'autres mauvaises interprétations. Elle permet également au client de traiter un argument vide comme un "." au lieu de générer une erreur.
Par défaut dans un rsync moderne, les caractères "actifs pour le shell" (y compris les espaces) sont échappés avec une barre oblique inverse dans les arguments envoyés au shell distant. Les caractères génériques *, ?, [, et ] ne sont pas échappés dans les arguments de nom de fichier (leur permettant de se développer en plusieurs noms de fichiers) tout en étant protégés dans les arguments d'option, tels que --usermap.
Si vous avez un script qui souhaite utiliser la division d'arguments à l'ancienne dans ses noms de fichiers, spécifiez cette option une fois. Si le shell distant a un problème avec des échappements par barre oblique inverse, spécifiez cette option deux fois.
Vous pouvez également contrôler ce paramètre via la variable d'environnement RSYNC_OLD_ARGS. Si elle a la valeur "1", rsync utilisera par défaut un paramètre d'option unique. Si elle a la valeur "2" (ou plus), rsync utilisera par défaut un paramètre d'option répété. Si elle est "0", vous obtiendrez le comportement d'échappement par défaut. L'environnement est toujours outrepassé par les options spécifiées manuellement, positives ou négatives (la négative est --no-old-args).
Notez que cette option désactive également la vérification de sécurité supplémentaire ajoutée en 3.2.5 qui garantit qu'un expéditeur distant n'inclut pas d'éléments de niveau supérieur supplémentaires dans la liste de fichiers que vous n'avez pas demandés. Cet effet secondaire est nécessaire car nous ne pouvons pas savoir avec certitude quels noms attendre lorsque le shell distant interprète les arguments.
Cette option entre en conflit avec l'option --secluded-args.
--secluded-args, -s
Cette option envoie tous les noms de fichiers et la plupart des options au rsync distant via le protocole (pas la ligne de commande du shell distant), ce qui évite de laisser le shell distant les modifier. Les caractères génériques sont développés sur l'hôte distant par rsync au lieu d'un shell.
Ceci est similaire à l'échappement par défaut des arguments avec barre oblique inverse ajouté en 3.2.4 (voir --old-args) car il empêche des problèmes comme la division par espaces et des effets secondaires de caractères indésirables. Cependant, il présente les inconvénients d'être incompatible avec les anciennes versions de rsync (antérieures à 3.0.0) et d'être refusé par les shells restreints qui souhaitent pouvoir inspecter toutes les valeurs d'options pour des raisons de sécurité.
Cette option est utile pour les cas où vous avez besoin que le jeu de caractères de l'argument soit converti pour l'hôte distant, si le shell distant est incompatible avec la méthode d'échappement par barre oblique inverse par défaut, ou s'il y a une autre raison pour laquelle vous souhaitez que la majorité des options et arguments contournent la ligne de commande du shell distant.
Si vous combinez cette option avec --iconv, les arguments liés au côté distant seront traduits du jeu de caractères local vers le jeu de caractères distant. La traduction se produit avant le développement des caractères génériques. Voir également l'option --files-from.
Vous pouvez également contrôler ce paramètre via la variable d'environnement RSYNC_PROTECT_ARGS. Si elle a une valeur non nulle, ce paramètre sera activé par défaut, sinon il sera désactivé par défaut. L'un ou l'autre état est outrepassé par une version manuellement spécifiée, positive ou négative, de cette option (notez que --no-s et --no-secluded-args sont les versions négatives). Cette variable d'environnement est également supplantée par une valeur non nulle de RSYNC_OLD_ARGS exportée.
Cette option entre en conflit avec l'option --old-args.
Cette option était auparavant appelée --protect-args (avant 3.2.6) et ce nom plus ancien peut toujours être utilisé (bien que la spécification en tant que -s soit toujours le choix le plus simple et le plus compatible).
--trust-sender
Cette option désactive deux contrôles de validation supplémentaires qu'un client local effectue sur la liste de fichiers générée par un expéditeur distant. Cette option ne doit être utilisée que si vous faites confiance à l'expéditeur pour ne pas insérer d'éléments malveillants dans la liste de fichiers (quelque chose qui pourrait éventuellement être fait via un rsync modifié, un shell modifié, ou une autre manipulation similaire).
Normalement, le client rsync (à partir de la version 3.2.5) exécute deux contrôles de validation supplémentaires lors du téléchargement de fichiers à partir d'un rsync distant :
o
Il vérifie que des éléments d'argument supplémentaires n'ont pas été ajoutés en haut du transfert.
o
Il vérifie qu'aucun des éléments de la liste de fichiers ne sont des noms qui auraient dû être exclus (si des règles de filtre étaient spécifiées).
Notez que diverses options peuvent désactiver un ou les deux de ces contrôles si l'option interfère avec la validation. Par exemple :
o
L'utilisation d'un fichier de filtre par répertoire lit les règles de filtre que seul le serveur connaît, de sorte que la vérification du filtre est désactivée.
o
L'utilisation de l'option --old-args permet à l'expéditeur de manipuler les arguments demandés, de sorte que la vérification des arguments est désactivée.
o
La lecture de la liste files-from du côté serveur signifie que le client ne connaît pas la liste des arguments, de sorte que la vérification des arguments est désactivée.
o
L'utilisation de --read-batch désactive les deux contrôles car le fichier batch's les contenus auront été vérifiés lors de leur création.
Cette option peut aider un client serveur sous-alimenté si la correspondance de motifs supplémentaire ralentit les choses lors d'un transfert énorme. Elle peut également être utilisée pour contourner un bogue actuellement inconnu dans la logique de vérification d'un transfert provenant d'un expéditeur de confiance.
Lorsque vous utilisez cette option, il est conseillé de spécifier un répertoire de destination dédié, comme mentionné dans la section SÉCURITÉ MULTI-HÔTES.
--copy-as=USER[:GROUP]
Cette option indique à rsync d'utiliser l'USER et (si spécifié après deux points) le GROUP pour les opérations de copie. Cela ne fonctionne que si l'utilisateur qui exécute rsync a la capacité de changer d'utilisateur. Si le groupe n'est pas spécifié, les groupes par défaut de l'utilisateur sont utilisés.
Cette option peut aider à réduire le risque qu'un rsync exécuté en tant que root accède à un répertoire qui pourrait avoir des modifications en cours et vous voulez vous assurer que les actions de lecture ou d'écriture au niveau root de fichiers système ne sont pas possibles. Bien que vous puissiezAlternatively, exécuter tout rsync en tant qu'utilisateur spécifié, il est parfois nécessaire d'utiliser les identifiants d'accès hôte au niveau root, de sorte que cela permet à rsync de renoncer aux privilèges root pour la partie copie de l'opération après l'établissement de la connexion rsh ou démon.
L'option n'affecte qu'un côté du transfert, sauf si le transfert est local, auquel cas elle affecte les deux côtés. Utilisez --remote-option pour affecter le côté distant, tel que -M--copy-as=joe. Pour un transfert local, le fichier d'assistance lsh (ou lsh.sh) fournit un script d'aide de shell local qui peut être utilisé pour permettre de spécifier une spécification d'hôte "localhost:" ou "lh:" sans avoir besoin de configurer de shells distants, vous permettant de spécifier des options distantes qui affectent le côté du transfert qui utilise la spécification d'hôte (et l'utilisation du nom d'hôte "lh" évite le remplacement du répertoire distant par le répertoire personnel de l'utilisateur).
Par exemple, le rsync suivant écrit les fichiers locaux en tant qu'utilisateur "joe" :
sudo rsync -aiv --copy-as=joe host1:backups/joe/ /home/joe/
Cela rend tous les fichiers appartenant à l'utilisateur "joe", limite les groupes à ceux disponibles pour cet utilisateur, et empêche l'utilisateur joe de réaliser une exploitation temporelle du chemin pour modifier un fichier que l'utilisateur joe n'a pas les permissions de modifier.
La commande suivante effectue une copie locale dans le répertoire "dest/" en tant qu'utilisateur "joe" (en supposant que vous ayez installé support/lsh dans un répertoire de votre $PATH) :
sudo rsync -aive lsh -M--copy-as=joe src/ lh:dest/
--temp-dir=DIR, -T
Cette option indique à rsync d'utiliser DIR comme répertoire temporaire lors de la création de copies temporaires des fichiers transférés côté réception. Le comportement par défaut est de créer chaque fichier temporaire dans le même répertoire que le fichier de destination associé. À partir de rsync 3.1.1, les noms des fichiers temporaires dans le DIR spécifié ne seront pas préfixés par un point supplémentaire (bien qu'ils aient toujours un suffixe aléatoire ajouté).
Cette option est le plus souvent utilisée lorsque la partition disque de réception ne dispose pas de suffisamment d'espace libre pour contenir une copie du plus grand fichier du transfert. Dans ce cas (c'est-à-dire lorsque le répertoire temporaire se trouve sur une partition disque différente), rsync ne pourra pas renommer chaque fichier temporaire reçu par-dessus le fichier de destination associé, mais devra plutôt le copier sur place. Rsync le fait en copiant le fichier par-dessus le fichier de destination, ce qui signifie que le fichier de destination contiendra des données tronquées pendant cette copie. Si cela n'était pas fait de cette manière (même si le fichier de destination était d'abord supprimé, les données copiées localement vers un fichier temporaire dans le répertoire de destination, puis renommées sur place), il serait possible que l'ancien fichier continue d'occuper de l'espace disque (si quelqu'un l'avait ouvert), et donc il pourrait ne pas y avoir assez de place pour faire tenir la nouvelle version sur le disque en même temps.
Si vous utilisez cette option pour des raisons autres qu'une pénurie d'espace disque, vous souhaiterez peut-être la combiner avec l'option --delay-updates, qui garantira que tous les fichiers copiés seront placés dans des sous-répertoires de la hiérarchie de destination, en attendant la fin du transfert. Si vous n'avez pas assez de place pour dupliquer tous les fichiers arrivants sur la partition de destination, une autre façon de dire à rsync que vous n'êtes pas excessivement préoccupé par l'espace disque est d'utiliser l'option --partial-dir avec un chemin relatif ; car cela dit à rsync qu'il est acceptable de stocker une copie d'un seul fichier dans un sous-répertoire de la hiérarchie de destination, rsync utilisera le partial-dir comme zone de transit pour transférer le fichier copié, puis le renommera sur place à partir de là. (Spécifier un --partial-dir avec un chemin absolu n'a pas cet effet secondaire.)
--fuzzy, -y
Cette option indique à rsync qu'il doit rechercher un fichier de base pour tout fichier de destination manquant. L'algorithme actuel recherche dans le même répertoire que le fichier de destination soit un fichier de taille et de date de modification identiques, soit un fichier de nom similaire. S'il est trouvé, rsync utilise le fichier de base "flou" pour tenter d'accélérer le transfert.
Si l'option est répétée, l'analyse "floue" sera également effectuée dans tous les répertoires de destination correspondants spécifiés via --compare-dest, --copy-dest, ou --link-dest.
Notez que l'utilisation de l'option --delete pourrait supprimer les fichiers correspondants "flous", donc utilisez soit --delete-after, soit spécifiez des exclusions de noms de fichiers pour éviter cela.
--compare-dest=DIR
Cette option indique à rsync d'utiliser DIR sur la machine de destination comme une hiérarchie supplémentaire pour comparer les fichiers de destination lors des transferts (si les fichiers sont manquants dans le répertoire de destination). Si un fichier est trouvé dans DIR et qu'il est identique au fichier de l'expéditeur, le fichier NE sera PAS transféré dans le répertoire de destination. Ceci est utile pour créer une sauvegarde sparse des seuls fichiers qui ont changé par rapport à une sauvegarde antérieure. Cette option est généralement utilisée pour copier dans un répertoire vide (ou nouvellement créé).
Depuis la version 2.6.4, plusieurs répertoires --compare-dest peuvent être fournis, ce qui amènera rsync à rechercher dans la liste dans l'ordre spécifié une correspondance exacte. Si une correspondance est trouvée qui ne diffère que par les attributs, une copie locale est effectuée et les attributs sont mis à jour. Si aucune correspondance n'est trouvée, un fichier de base de l'un des DIRs sera sélectionné pour tenter d'accélérer le transfert.
Si DIR est un chemin relatif, il est relatif au répertoire de destination. Voir aussi --copy-dest et --link-dest.
NOTE : depuis la version 3.1.0, rsync supprimera un fichier d'une hiérarchie de destination non vide si une correspondance exacte est trouvée dans l'une des hiérarchies compare-dest (rendant le résultat final plus proche d'une copie fraîche).
--copy-dest=DIR
Cette option se comporte comme --compare-dest, mais rsync copiera également les fichiers inchangés trouvés dans DIR vers le répertoire de destination en utilisant une copie locale. Ceci est utile pour effectuer des transferts vers une nouvelle destination tout en laissant les fichiers existants intacts, puis pour effectuer un basculement rapide une fois que tous les fichiers ont été transférés avec succès.
Plusieurs répertoires --copy-dest peuvent être fournis, ce qui amènera rsync à rechercher dans la liste dans l'ordre spécifié un fichier inchangé. Si aucune correspondance n'est trouvée, un fichier de base de l'un des DIRs sera sélectionné pour tenter d'accélérer le transfert.
Si DIR est un chemin relatif, il est relatif au répertoire de destination. Voir aussi --compare-dest et --link-dest.
--link-dest=DIR
Cette option se comporte comme --copy-dest, mais les fichiers inchangés sont liés en dur (hard-linked) depuis DIR vers le répertoire de destination. Les fichiers doivent être identiques dans tous les attributs préservés (par exemple, permissions, éventuellement propriété) pour que les fichiers soient liés entre eux. Un exemple :
rsync -av --link-dest=$PWD/prior_dir host:src_dir/ new_dir/
Si les fichiers ne sont pas liés, vérifiez leurs attributs. Vérifiez également si certains attributs sont forcés en dehors du contrôle de rsync, comme une option de montage qui écrase root en un seul utilisateur, ou monte un disque amovible avec une propriété générique (comme l'option "Ignorer la propriété sur ce volume" d'OS X).
Depuis la version 2.6.4, plusieurs répertoires --link-dest peuvent être fournis, ce qui amènera rsync à rechercher dans la liste dans l'ordre spécifié une correspondance exacte (il y a une limite de 20 tels répertoires). Si une correspondance est trouvée qui ne diffère que par les attributs, une copie locale est effectuée et les attributs sont mis à jour. Si aucune correspondance n'est trouvée, un fichier de base de l'un des DIRs sera sélectionné pour tenter d'accélérer le transfert.
Cette option fonctionne mieux lors de la copie dans une hiérarchie de destination vide, car les fichiers existants peuvent voir leurs attributs modifiés, et cela peut affecter les fichiers de destination alternatifs via des liens physiques. De plus, l'énumération des changements peut devenir un peu confuse. Notez qu'avant la version 3.1.0, une correspondance exacte dans un répertoire alternatif ne serait jamais trouvée (ni liée dans la destination) lorsqu'un fichier de destination existe déjà.
Notez que si vous combinez cette option avec --ignore-times, rsync ne liera aucun fichier ensemble car il ne lie que les fichiers identiques ensemble en remplacement du transfert du fichier, jamais comme une vérification supplémentaire après la mise à jour du fichier.
Si DIR est un chemin relatif, il est relatif au répertoire de destination. Voir aussi --compare-dest et --copy-dest.
Notez que les versions de rsync antérieures à 2.6.1 présentaient un bogue qui pouvait empêcher --link-dest de fonctionner correctement pour un non-superutilisateur lorsque --owner (-o) était spécifié (ou implicite). Vous pouvez contourner ce bogue en évitant l'option -o (ou en utilisant --no-o) lors de l'envoi à un ancien rsync.
--compress, -z
Avec cette option, rsync compresse les données du fichier lors de leur envoi vers la machine de destination
e, ce qui réduit la quantité de données transmises — quelque chose d'utile sur une connexion lente. Rsync prend en charge plusieurs méthodes de compression et en choisira une pour vous, sauf si vous forcez le choix à l'aide de l'option --compress-choice (--zc). Exécutez rsync --version pour voir la liste de compression par défaut intégrée à votre version. Lorsque les deux côtés du transfert sont au moins à la version 3.2.0, rsync choisit le premier algorithme de la liste de choix du client qui se trouve également dans la liste de choix du serveur. Si aucun choix de compression commun n'est trouvé, rsync se termine avec une erreur. Si le rsync distant est trop ancien pour prendre en charge la négociation de sommes de contrôle, sa liste est supposée être "zlib". L'ordre par défaut peut être personnalisé en définissant la variable d'environnement RSYNC_COMPRESS_LIST sur une liste d'algorithmes de compression acceptables séparés par des espaces. Si la chaîne contient un caractère "&", elle est séparée en "chaîne client & chaîne serveur", sinon la même chaîne s'applique aux deux. Si la chaîne (ou une partie de la chaîne) ne contient aucun caractère non-espace blanc, la liste de compression par défaut est utilisée. Tous les noms de compression inconnus sont supprimés de la liste, mais une liste avec uniquement des noms invalides entraîne un échec de négociation. Il existe certaines versions plus anciennes de rsync qui étaient configurées pour rejeter une option -z et exiger l'utilisation de -zz car leur bibliothèque de compression n'était pas compatible avec la méthode de compression zlib par défaut. Vous pouvez généralement ignorer cette bizarrerie à moins que le serveur rsync ne se plaigne et ne vous dise de spécifier -zz.
--compress-choice=STR, --zc=STR
Cette option peut être utilisée pour remplacer la négociation automatique de l'algorithme de compression qui se produit lorsque --compress est utilisé. L'option implique --compress à moins que "none" n'ait été spécifié, ce qui implique plutôt --no-compress. Les options de compression que vous pourriez être en mesure d'utiliser sont :
o
zstd
o
lz4
o
zlibx
o
zlib
o
none
Exécutez rsync --version pour voir la liste de compression par défaut intégrée à votre version (qui peut différer de la liste ci-dessus). Notez que si vous voyez une erreur concernant une option nommée --old-compress ou --new-compress, il s'agit de rsync essayant d'envoyer l'option --compress-choice=zlib ou --compress-choice=zlibx d'une manière rétrocompatible que plus de versions de rsync comprennent. Cette erreur indique que la version plus ancienne de rsync sur le serveur ne vous permettra pas de forcer le type de compression. Notez que l'algorithme de compression "zlibx" est simplement l'algorithme "zlib" avec les données correspondantes exclues du flux de compression (pour essayer de le rendre plus compatible avec une implémentation zlib externe).
--compress-level=NUM, --zl=NUM
Définissez explicitement le niveau de compression à utiliser (voir --compress, -z) au lieu de laisser le niveau par défaut. L'option --compress est implicite tant que le niveau choisi n'est pas un niveau "ne pas compresser" pour l'algorithme de compression en vigueur (par exemple, la compression zlib traite le niveau 0 comme "désactivé"). Les valeurs de niveau varient en fonction de la somme de contrôle en vigueur. Parce que rsync négociera un choix de somme de contrôle par défaut (lorsque le rsync distant est suffisamment récent), il peut être utile de combiner cette option avec une option --compress-choice (--zc) à moins que vous ne soyez sûr du choix en vigueur. Par exemple : 
rsync -aiv --zc=zstd --zl=22 host:src/ dest/
Pour la compression zlib & zlibx, les valeurs valides vont de 1 à 9, 6 étant la valeur par défaut. Spécifier --zl=0 désactive la compression, et spécifier --zl=-1 choisit le niveau par défaut de 6. Pour la compression zstd, les valeurs valides vont de -131072 à 22, 3 étant la valeur par défaut. Spécifier 0 choisit la valeur par défaut de 3. Pour la compression lz4, il n'y a pas de niveaux, donc la valeur est toujours 0. Si vous spécifiez une valeur trop grande ou trop petite, le nombre est silencieusement limité à une valeur valide. Cela vous permet de spécifier quelque chose comme --zl=999999999 et d'être assuré que vous obtiendrez le niveau de compression maximum, quel que soit l'algorithme choisi. Si vous voulez connaître le niveau de compression en vigueur, spécifiez --debug=nstr pour voir les résultats de la "chaîne négociée". Cela affichera quelque chose comme "Client compress: zstd (level 3)" (avec le choix de somme de contrôle en vigueur).
--skip-compress=LIST
NOTE : aucune méthode de compression ne prend actuellement en charge les modifications de compression par fichier, cette option n'a donc aucun effet. Remplacez la liste des suffixes de fichiers qui seront compressés le moins possible. Rsync définit le niveau de compression sur une base par fichier en fonction du suffixe du fichier. Si l'algorithme de compression a un niveau "désactivé", alors aucune compression ne se produit pour ces fichiers. D'autres algorithmes qui prennent en charge la modification du niveau de flux à la volée auront le niveau minimisé pour réduire l'utilisation du CPU autant que possible pour un fichier correspondant. La LISTE doit être un ou plusieurs suffixes de fichiers (sans le point) séparés par des barres obliques (/). Vous pouvez spécifier une chaîne vide pour indiquer qu'aucun fichier ne doit être ignoré. Une correspondance simple de classe de caractères est prise en charge : chaque élément doit consister en une liste de lettres entre crochets (par exemple, aucune classe spéciale, telle que "[:alpha:]", n'est prise en charge, et '-' n'a aucune signification spéciale). Les caractères astérisque (*) et point d'interrogation (?) n'ont aucune signification spéciale. Voici un exemple qui spécifie 6 suffixes à ignorer (puisque 1 des 5 règles correspond à 2 suffixes) : 
--skip-compress=gz/jpg/mp[34]/7z/bz2

Cette liste sera remplacée par votre liste --skip-compress dans toutes les situations sauf une : une copie à partir d'un daemon rsync ajoutera vos suffixes ignorés à sa liste de fichiers non compressés (et sa liste peut être configurée sur une valeur par défaut différente).
--numeric-ids
Avec cette option, rsync transférera les identifiants numériques de groupe et d'utilisateur plutôt que d'utiliser les noms d'utilisateur et de groupe et de les mapper des deux côtés. Par défaut, rsync utilisera les noms d'utilisateur et de groupe pour déterminer la propriété des fichiers. L'identifiant spécial 0 et le groupe spécial 0 ne sont jamais mappés via des noms d'utilisateur/groupe, même si l'option --numeric-ids n'est pas spécifiée. Si un utilisateur ou un groupe n'a pas de nom sur le système source ou s'il n'a pas de correspondance sur le système de destination, alors l'identifiant numérique du système source est utilisé à la place. Voir également le paramètre use chroot dans la page de manuel rsyncd.conf pour quelques commentaires sur la façon dont le paramètre chroot affecte la capacité de rsync à rechercher les noms d'utilisateurs et de groupes et ce que vous pouvez faire à ce sujet.
--usermap=STRING, --groupmap=STRING
Ces options vous permettent de spécifier des utilisateurs et des groupes qui doivent être mappés à d'autres valeurs par le côté récepteur. La CHAÎNE est une ou plusieurs paires DE:VERS séparées par des virgules. Toute valeur DE correspondante de l'expéditeur est remplacée par une valeur VERS du récepteur. Vous pouvez spécifier des noms d'utilisateur ou des identifiants d'utilisateur pour les valeurs DE et VERS, et la valeur DE peut également être une chaîne générique, qui sera mise en correspondance avec les noms de l'expéditeur (les caractères génériques ne correspondent PAS aux numéros d'identifiant, bien que voir ci-dessous pour expliquer pourquoi un '*' correspond à tout). Vous pouvez plutôt spécifier une plage d'identifiants via une plage inclusive : BAS-HAUT. Par exemple : 
--usermap=0-99:nobody,wayne:admin,*:normal --groupmap=usr:1,1:usr
La première correspondance dans la liste est celle qui est utilisée. Vous devez spécifier toutes vos correspondances d'utilisateurs à l'aide d'une seule option --usermap, et/ou toutes vos correspondances de groupes à l'aide d'une seule option --groupmap. Notez que les noms de l'expéditeur pour les utilisateurs et groupes 0 ne sont pas transmis au récepteur, vous devez donc soit faire correspondre ces valeurs en utilisant 0, soit utiliser les noms en vigueur sur le côté récepteur (typiquement "root"). Tous les autres noms DE correspondent à ceux en vigueur côté expéditeur. Tous les noms VERS correspondent à ceux en vigueur côté récepteur. Tous les identifiants qui n'ont pas de nom côté expéditeur sont traités comme ayant un nom vide pour la mise en correspondance. Cela leur permet d'être mis en correspondance via un "*" ou en utilisant un nom vide. Par exemple : 
--usermap=:nobody --groupmap=*:nobody
Lorsque l'option --numeric-ids est utilisée, l'expéditeur n'envoie aucun nom, donc tous les identifiants sont traités comme ayant un nom vide. Cela signifie que vous devrez spécifier des valeurs DE numériques si vous souhaitez mapper ces identifiants sans nom à des valeurs différentes. Pour que l'option --usermap fonctionne, le récepteur devra être exécuté en tant que super-utilisateur (voir également les options --super et --fake-super). Pour que l'option --groupmap fonctionne, le récepteur devra avoir la permissions pour définir ce groupe.
À partir de rsync 3.2.4, l'option --usermap implique l'option --owner (-o) tandis que l'option --groupmap implique l'option --group (-g) (car rsync doit avoir ces options activées pour que les options de mappage fonctionnent).
Un ancien client rsync peut avoir besoin d'utiliser -s pour éviter une plainte concernant les caractères génériques, mais un rsync moderne gère cela automatiquement.
--chown=USER:GROUP
Cette option force tous les fichiers à appartenir à USER avec le groupe GROUP. C'est une interface plus simple que d'utiliser --usermap et --groupmap directement, mais elle est implémentée en utilisant ces options en interne, donc elles ne peuvent pas être mélangées. Si USER ou GROUP est vide, aucun mappage pour l'utilisateur/groupe omis n'aura lieu. Si GROUP est vide, le deux-points final peut être omis, mais si USER est vide, un deux-points initial doit être fourni.
Si vous spécifiez "--chown=foo:bar", c'est exactement la même chose que de spécifier "--usermap=*:foo --groupmap=*:bar", mais plus facile (et avec les mêmes options --owner et/ou --group implicites).
Un ancien client rsync peut avoir besoin d'utiliser -s pour éviter une plainte concernant les caractères génériques, mais un rsync moderne gère cela automatiquement.
--timeout=SECONDS
Cette option vous permet de définir un délai d'attente maximal pour les entrées/sorties en secondes. Si aucune donnée n'est transférée pendant le temps spécifié, rsync se terminera. La valeur par défaut est 0, ce qui signifie aucun délai d'attente.
--contimeout=SECONDS
Cette option vous permet de définir le temps pendant lequel rsync attendra que sa connexion à un démon rsync réussisse. Si le délai d'attente est atteint, rsync se termine avec une erreur.
--address=ADDRESS
Par défaut, rsync se liera à l'adresse wildcard lors de la connexion à un démon rsync. L'option --address vous permet de spécifier une adresse IP spécifique (ou un nom d'hôte) à laquelle se lier.
Voir aussi la version démon de l'option --address.
--port=PORT
Ceci spécifie un numéro de port TCP alternatif à utiliser plutôt que le défaut de 873. Ceci n'est nécessaire que si vous utilisez la syntaxe à double deux-points (::) pour vous connecter à un démon rsync (car la syntaxe URL a un moyen de spécifier le port dans le cadre de l'URL).
Voir aussi la version démon de l'option --port.
--sockopts=OPTIONS
Cette option peut procurer un plaisir sans fin aux personnes qui aiment optimiser leurs systèmes à l'extrême. Vous pouvez définir toutes sortes d'options de socket qui peuvent rendre les transferts plus rapides (ou plus lents !). Lisez la page de manuel de l'appel système setsockopt() pour plus de détails sur certaines des options que vous pouvez définir. Par défaut, aucune option de socket spéciale n'est définie. Ceci n'affecte que les connexions directes par socket à un démon rsync distant.
Voir aussi la version démon de l'option --sockopts.
--blocking-io
Ceci indique à rsync d'utiliser les E/S bloquantes lors du lancement d'un transport de shell distant. Si le shell distant est rsh ou remsh, rsync utilise par défaut des E/S bloquantes, sinon il utilise par défaut des E/S non bloquantes. (Notez que ssh préfère les E/S non bloquantes.)
--outbuf=MODE
Ceci définit le mode de mise en mémoire tampon de sortie. Le mode peut être None (alias Unbuffered), Line, ou Block (alias Full). Vous pouvez spécifier aussi peu qu'une seule lettre pour le mode, et utiliser la casse majuscule ou minuscule.
L'utilisation principale de cette option est de changer la mise en mémoire tampon complète en mise en mémoire tampon par ligne lorsque la sortie de rsync va vers un fichier ou un tube.
--itemize-changes, -i
Demande une liste simple et itemisée des changements apportés à chaque fichier, y compris les changements d'attributs. Ceci est exactement la même chose que de spécifier --out-format='%i %n%L'. Si vous répétez l'option, les fichiers inchangés seront également affichés, mais seulement si le rsync récepteur est au moins la version 2.6.7 (vous pouvez utiliser -vv avec d'anciennes versions de rsync, mais cela active aussi l'affichage d'autres messages détaillés).
Le caractère d'échappement "%i" a une sortie cryptique longue de 11 lettres. Le format général est similaire à la chaîne YXcstpoguax, où Y est remplacé par le type de mise à jour effectuée, X est remplacé par le type de fichier, et les autres lettres représentent des attributs qui peuvent être affichés s'ils sont modifiés.
Les types de mise à jour qui remplacent Y sont les suivants :
o
Un < signifie qu'un fichier est transféré vers l'hôte distant (envoyé).
o
Un > signifie qu'un fichier est transféré vers l'hôte local (reçu).
o
Un c signifie qu'un changement/création locale se produit pour l'élément (tel que la création d'un répertoire ou la modification d'un lien symbolique, etc.).
o
Un h signifie que l'élément est un lien physique vers un autre élément (nécessite --hard-links).
o
Un . signifie que l'élément n'est pas mis à jour (bien qu'il puisse avoir des attributs modifiés).
o
Un * signifie que le reste de la zone d'affichage itemisée contient un message (par exemple, "suppression").
Les types de fichiers qui remplacent X sont : f pour un fichier, un d pour un répertoire, un L pour un lien symbolique, un D pour un périphérique, et un S pour un fichier spécial (par exemple, sockets nommés et FIFOs).
Les autres lettres de la chaîne indiquent si certains attributs du fichier ont changé, comme suit :
o
"." - l'attribut n'est pas modifié.
o
"+" - le fichier est nouvellement créé.
o
" " - tous les attributs ne sont pas modifiés (tous les points deviennent des espaces).
o
"?" - le changement est inconnu (lorsque le rsync distant est ancien).
o
Une lettre indique qu'un attribut est mis à jour.
L'attribut associé à chaque lettre est le suivant :
o
Un c signifie soit qu'un fichier régulier a une somme de contrôle différente (nécessite --checksum), soit qu'un lien symbolique, un périphérique ou un fichier spécial a une valeur modifiée. Notez que si vous envoyez des fichiers à un rsync antérieur à 3.0.1, ce drapeau de changement ne sera présent que pour les fichiers réguliers dont la somme de contrôle diffère.
o
Un s signifie que la taille d'un fichier régulier est différente et sera mise à jour par le transfert de fichier.
o
Un t signifie que l'heure de modification est différente et est mise à jour avec la valeur de l'expéditeur (nécessite --times). Une valeur alternative de T signifie que l'heure de modification sera définie sur l'heure du transfert, ce qui se produit lorsqu'un fichier/lien symbolique/périphérique est mis à jour sans --times et lorsqu'un lien symbolique est modifié et que le récepteur ne peut pas définir son heure. (Note : lors de l'utilisation d'un client rsync 3.0.0, vous pourriez voir le drapeau s combiné avec t au lieu du drapeau T correct pour cet échec de définition de l'heure.)
o
Un p signifie que les permissions sont différentes et sont mises à jour avec la valeur de l'expéditeur (nécessite --perms).
o
Un o signifie que le propriétaire est différent et est mis à jour avec la valeur de l'expéditeur (nécessite --owner et des privilèges de super-utilisateur).
o
Un g signifie que le groupe est différent et est mis à jour avec la valeur de l'expéditeur (nécessite --group et l'autorité pour définir le groupe).
o
o
Un u|n|b indique les informations suivantes :

u signifie que l'heure d'accès (utilisation) est différente et est mise à jour avec la valeur de l'expéditeur (nécessite --atimes)

o
n signifie que l'heure de création (nouveauté) est différente et est mise à jour avec la valeur de l'expéditeur (nécessite --crtimes)
o
b signifie que les heures d'accès et de création sont toutes deux mises à jour
o
Le a signifie que les informations ACL sont modifiées.
o
Le x signifie que les informations d'attributs étendus sont modifiées.
Une autre sortie est possible : lors de la suppression de fichiers, le "%i" affichera la chaîne "*deleting" pour chaque élément qui est supprimé (en supposant que vous parlez à un rsync suffisamment récent pour qu'il enregistre les suppressions au lieu de les afficher comme un message détaillé).
--out-format=FORMAT
Ceci vous permet de spécifier exactement ce que le client rsync affiche à l'utilisateur par mise à jour. Le format est une chaîne de texte contenant des séquences d'échappement à un seul caractère intégrées, préfixées par un caractère pourcentage (%). Un format par défaut de "%n%L" est supposé si --info=name ou -v est spécifié (ceci vous indique seulement le nom du fichier et, si l'élément est un lien, où il pointe). Pour une liste complète des caractères d'échappement possibles, voir le paramètre log format dans la page de manuel de rsyncd.conf.
La spécification de l'option --out-format implique l'option --info=name
/b> option, qui mentionnera chaque fichier, répertoire, etc. qui est mis à jour de manière significative (un fichier transféré, un lien symbolique/périphérique recréé, ou un répertoire touché). De plus, si l'échappement itemize-changes (%i) est inclus dans la chaîne (par exemple, si l'option --itemize-changes a été utilisée), la journalisation des noms augmente pour mentionner tout élément qui est modifié de quelque manière que ce soit (tant que le côté récepteur est au moins en version 2.6.4). Voir l'option --itemize-changes pour une description de la sortie de "%i".
Rsync affichera la chaîne de format de sortie avant le transfert d'un fichier, sauf si l'une des échappements de statistiques de transfert est demandée, auquel cas la journalisation se fait à la fin du transfert du fichier. Lorsque cette journalisation tardive est activée et que --progress est également spécifié, rsync affichera également le nom du fichier en cours de transfert avant ses informations de progression (suivi, bien sûr, de la sortie du format de sortie).
--log-file=FILE
Cette option fait en sorte que rsync enregistre ce qu'il fait dans un fichier. Ceci est similaire à la journalisation qu'un démon effectue, mais peut être demandé pour le côté client et/ou le côté serveur d'un transfert non-démon. Si spécifié comme une option client, la journalisation des transferts sera activée avec un format par défaut de "%i %n%L". Voir l'option --log-file-format si vous souhaitez modifier ce comportement.
Voici un exemple de commande qui demande au côté distant de journaliser ce qui se passe :
rsync -av --remote-option=--log-file=/tmp/rlog src/ dest/
Ceci est très utile si vous avez besoin de déboguer pourquoi une connexion se ferme de manière inattendue.
Voir aussi la version démon de l'option --log-file.
--log-file-format=FORMAT
Ceci vous permet de spécifier exactement ce que la journalisation par mise à jour est introduite dans le fichier spécifié par l'option --log-file (qui doit également être spécifiée pour que cette option ait un effet). Si vous spécifiez une chaîne vide, les fichiers mis à jour ne seront pas mentionnés dans le fichier journal. Pour une liste des caractères d'échappement possibles, voir le réglage log format dans la page de manuel rsyncd.conf.
Le FORMAT par défaut utilisé si --log-file est spécifié et que cette option ne l'est pas est '%i %n%L'.
Voir aussi la version démon de l'option --log-file-format.
--stats
Ceci indique à rsync d'afficher un ensemble détaillé de statistiques sur le transfert de fichiers, vous permettant de savoir à quel point l'algorithme de transfert delta de rsync est efficace pour vos données. Cette option est équivalente à --info=stats2 si combinée avec 0 ou 1 option -v, ou --info=stats3 si combinée avec 2 options -v ou plus.
Les statistiques actuelles sont les suivantes :
o
Nombre de fichiers est le décompte de tous les "fichiers" (au sens générique), qui inclut les répertoires, les liens symboliques, etc. Le décompte total sera suivi d'une liste de décomptes par type de fichier (si le total n'est pas nul). Par exemple : "(reg : 5, dir : 3, link : 2, dev : 1, special : 1)" liste les totaux pour les fichiers réguliers, les répertoires, les liens symboliques, les périphériques et les fichiers spéciaux. Si une valeur est de 0, elle est complètement omise de la liste.
o
Nombre de fichiers créés est le décompte du nombre de "fichiers" (sens générique) qui ont été créés (par opposition à mis à jour). Le décompte total sera suivi d'une liste de décomptes par type de fichier (si le total n'est pas nul).
o
Nombre de fichiers supprimés est le décompte du nombre de "fichiers" (sens générique) qui ont été supprimés. Le décompte total sera suivi d'une liste de décomptes par type de fichier (si le total n'est pas nul). Notez que cette ligne n'est affichée que si les suppressions sont activées, et seulement si le protocole 31 est utilisé (par défaut pour rsync 3.1.x).
o
Nombre de fichiers réguliers transférés est le décompte des fichiers normaux qui ont été mis à jour via l'algorithme de transfert delta de rsync, qui n'inclut pas les répertoires, les liens symboliques, etc. Notez que rsync 3.1.0 a ajouté le mot "réguliers" à ce titre.
o
Taille totale des fichiers est la somme totale de toutes les tailles de fichiers dans le transfert. Ceci ne compte aucune taille pour les répertoires ou les fichiers spéciaux, mais inclut la taille des liens symboliques.
o
Taille totale des fichiers transférés est la somme totale de toutes les tailles de fichiers pour uniquement les fichiers transférés.
o
Données littérales est la quantité de données de mise à jour de fichier non correspondantes que nous avons dû envoyer au récepteur pour qu'il recrée les fichiers mis à jour.
o
Données correspondantes est la quantité de données que le récepteur a obtenues localement lors de la recréation des fichiers mis à jour.
o
Taille de la liste des fichiers est la taille des données de la liste de fichiers lorsque l'expéditeur l'a envoyée au récepteur. Ceci est plus petit que la taille en mémoire pour la liste des fichiers en raison d'une certaine compression des données dupliquées lorsque rsync envoie la liste.
o
Temps de génération de la liste des fichiers est le nombre de secondes que l'expéditeur a passé à créer la liste des fichiers. Ceci nécessite une version moderne de rsync du côté de l'expéditeur pour être présent.
o
Temps de transfert de la liste des fichiers est le nombre de secondes que l'expéditeur a passé à envoyer la liste des fichiers au récepteur.
o
Total d'octets envoyés est le décompte de tous les octets que rsync a envoyés du côté client vers le côté serveur.
o
Total d'octets reçus est le décompte de tous les octets non-messages que rsync a reçus du côté client du côté serveur. "Octets non-messages" signifie que nous ne comptons pas les octets pour un message verbeux que le serveur nous a envoyé, ce qui rend les statistiques plus cohérentes.
--8-bit-output, -8
Ceci indique à rsync de laisser tous les caractères à bit élevé sans échappement dans la sortie au lieu d'essayer de les tester pour voir s'ils sont valides dans la locale actuelle et d'échapper ceux qui ne le sont pas. Tous les caractères de contrôle (mais jamais les tabulations) sont toujours échappés, quelle que soit la configuration de cette option.
L'idiome d'échappement qui a commencé en 2.6.7 consiste à afficher une barre oblique inverse littérale (\) et un dièse (#), suivis de exactement 3 chiffres octaux. Par exemple, un saut de ligne serait affiché sous la forme ""\#012"". Une barre oblique inverse littérale qui se trouve dans un nom de fichier n'est pas échappée, sauf si elle est suivie d'un dièse et de 3 chiffres (0-9).
--human-readable, -h
Affiche les nombres dans un format plus lisible par l'homme. Il y a 3 niveaux possibles :
1.
affiche les nombres avec un séparateur entre chaque groupe de 3 chiffres (soit une virgule, soit un point, selon que le point décimal est représenté par un point ou une virgule).
2.
affiche les nombres dans des unités de 1000 (avec un suffixe de caractère pour les unités plus grandes -- voir ci-dessous).
3.
affiche les nombres dans des unités de 1024.
La valeur par défaut est le niveau lisible par l'homme 1. Chaque option -h augmente le niveau de un. Vous pouvez réduire le niveau à 0 (pour afficher les nombres sous forme de chiffres purs) en spécifiant l'option --no-human-readable (--no-h).
Les lettres d'unité qui sont ajoutées aux niveaux 2 et 3 sont : K (kilo), M (méga), G (giga), T (téra), ou P (péta). Par exemple, un fichier de 1234567 octets serait affiché comme 1.23M au niveau 2 (en supposant qu'un point est votre séparateur décimal local).
Note de compatibilité ascendante : les versions de rsync antérieures à 3.1.0 ne prennent pas en charge le niveau 1 lisible par l'homme, et elles utilisent par défaut le niveau 0. Ainsi, spécifier une ou deux options -h se comportera de manière comparable dans les versions anciennes et nouvelles tant que vous n'avez pas spécifié d'option --no-h avant une ou plusieurs options -h. Voir l'option --list-only pour une différence.
--partial
Par défaut, rsync supprimera tout fichier partiellement transféré si le transfert est interrompu. Dans certaines circonstances, il est plus souhaitable de conserver les fichiers partiellement transférés. L'utilisation de l'option --partial indique à rsync de conserver le fichier partiel, ce qui devrait rendre un transfert ultérieur du reste du fichier beaucoup plus rapide.
--partial-dir=DIR
Cette option modifie le comportement de l'option --partial tout en impliquant qu'elle est activée. Cette méthode de fichier partiel améliorée place tous les fichiers partiellement transférés dans le DIR spécifié au lieu d'écrire le fichier partiel dans le fichier de destination. Lors du prochain transfert, rsync utilisera un fichier trouvé dans ce répertoire comme données pour accélérer la reprise du transfert et le supprimera ensuite après qu'il ait servi son objectif.
Notez que si --whole-file est spécifié (ou implicite), tous les fichiers partiels trouvés pour un fichier en cours de mise à jour seront simplement supprimés (car rsync envoie les fichiers sans utiliser l'algorithme de transfert delta de rsync).
Rsync créera le DIR s'il manque, mais seulement le dernier répertoire -- pas tout le chemin. Cela facilite l'utilisation d'un chemin relatif (tel que "--partial-dir=.rsync-partial") pour que rsync crée le répertoire partiel dans le répertoire du fichier de destination lorsqu'il est nécessaire, puis le supprime à nouveau lorsque le fichier partiel est supprimé. Notez que cette suppression de répertoire n'est effectuée que pour un chemin relatif, car on s'attend à ce qu'un chemin absolu pointe vers un répertoire réservé au travail de partial-dir.
Si la valeur de partial-dir n'est pas un chemin absolu, rsync ajoutera une règle d'exclusion à la fin de toutes vos exclusions existantes. Cela empêchera l'envoi de tout fichier partial-dir qui pourrait exister du côté de l'expéditeur, et empêchera également la suppression prématurée des éléments partial-dir du côté du récepteur. Exemple : le --partial ci-dessus
rsync rsync -a -v -P --delete --exclude '.cache/' --exclude 'node_modules/' --exclude 'dist/' . user@host:/path/to/destination DESCRIPTION rsync is a versatile file copying tool. It can efficiently transfer and synchronize files between two locations, either locally or remotely. --bwlimit=TAUX
Cette option vous permet de spécifier le taux de transfert maximum pour les données envoyées sur la socket, spécifié en unités par seconde. La valeur TAUX peut être suffixée d'une chaîne pour indiquer un multiplicateur de taille, et peut être une valeur fractionnaire (par exemple, --bwlimit=1.5m). Si aucun suffixe n'est spécifié, la valeur sera supposée être en unités de 1024 octets (comme si "K" ou "KiB" avait été ajouté). Voir l'option --max-size pour une description de tous les suffixes disponibles. Une valeur de 0 ne spécifie aucune limite.
Pour des raisons de compatibilité ascendante, la limite de débit sera arrondie à l'unité KiB la plus proche, donc aucun débit inférieur à 1024 octets par seconde n'est possible.
Rsync écrit les données sur la socket par blocs, et cette option limite à la fois la taille des blocs que rsync écrit, et essaie de maintenir le taux de transfert moyen à la limite demandée. Une certaine "rafale" peut être observée lorsque rsync écrit un bloc de données puis dort pour que le taux moyen soit conforme.
En raison de la mise en tampon interne des données, l'option --progress peut ne pas refléter fidèlement la vitesse d'envoi des données. En effet, certains fichiers peuvent apparaître comme envoyés rapidement lorsque les données sont rapidement mises en tampon, tandis que d'autres peuvent apparaître comme très lents lors de la vidange du tampon de sortie. Ceci pourra être corrigé dans une future version.
Voir également la version démon de l'option --bwlimit.

Cela permet l'utilisation de l'option même lorsque seul un côté de la connexion la prend en charge. Cette option indique à rsync d'arrêter la copie lorsque le point dans le temps spécifié a été atteint. La date et l'heure peuvent être entièrement spécifiées dans un format numérique année-mois-jourThour:minute (par exemple, 2000-12-31T23:59) dans le fuseau horaire local. --only-write-batch=FICHIER
Fonctionne comme --write-batch, sauf qu'aucune mise à jour n'est effectuée sur le système de destination lors de la création du batch. Cela vous permet de transporter les modifications vers le système de destination par un autre moyen, puis d'appliquer les modifications via --read-batch.
Notez que vous pouvez librement écrire le batch directement sur un support portable : si ce support se remplit avant la fin du transfert, vous pouvez appliquer ce transfert partiel à la destination et répéter tout le processus pour obtenir le reste des modifications (tant que vous ne vous souciez pas d'un système de destination partiellement mis à jour pendant que le cycle de plusieurs mises à jour est en cours).
Notez également que vous ne économisez de la bande passante que lorsque vous envoyez des modifications à un système distant, car cela permet de détourner les données batch de l'expéditeur vers le fichier batch sans avoir à passer par le fil vers le récepteur (lors de la réception, l'expéditeur est distant et ne peut donc pas écrire le batch).
--read-batch=FICHIER
Applique toutes les modifications stockées dans FICHIER, un fichier précédemment généré par --write-batch. Si *FICHIER* est -, les données du batch seront lues depuis l'entrée standard. Voir la section "MODE BATCH" pour les détails.
--protocol=NUM
Force l'utilisation d'une ancienne version du protocole. Ceci est utile pour créer un fichier batch compatible avec une ancienne version de rsync. Par exemple, si rsync 2.6.4 est utilisé avec l'option --write-batch, mais que rsync 2.6.3 sera utilisé pour exécuter l'option --read-batch, vous devriez utiliser "--protocol=28" lors de la création du fichier batch pour forcer l'ancienne version du protocole à être utilisée dans le fichier batch (en supposant que vous ne pouvez pas mettre à jour le rsync sur le système de lecture).
--iconv=CONVERT_SPEC
Rsync peut convertir les noms de fichiers entre jeux de caractères à l'aide de cette option. L'utilisation de CONVERT_SPEC égal à "." indique à rsync de rechercher le jeu de caractères par défaut via le paramètre de locale. Alternativement, vous pouvez spécifier entièrement quelle conversion faire en donnant un jeu de caractères local et distant séparés par une virgule dans l'ordre --iconv=LOCAL,REMOTE, par exemple --iconv=utf8,iso88591. Cet ordre garantit que l'option restera la même, que vous poussiez ou tiriez des fichiers. Enfin, vous pouvez spécifier --no-iconv ou une CONVERT_SPEC de "-" pour désactiver toute conversion. Le réglage par défaut de cette option est spécifique au site, et peut également être affecté par la variable d'environnement RSYNC_ICONV.
Pour une liste des noms de jeux de caractères que votre bibliothèque iconv locale prend en charge, vous pouvez exécuter "iconv --list".
Si vous spécifiez l'option --secluded-args (-s), rsync va traduire les noms de fichiers que vous spécifiez sur la ligne de commande et qui sont envoyés à l'hôte distant. Voir aussi l'option --files-from.
Notez que rsync n'effectue aucune conversion de noms dans les fichiers de filtre (y compris les fichiers include/exclude). Il vous appartient de vous assurer que vous spécifiez des règles de correspondance qui peuvent correspondre des deux côtés du transfert. Par exemple, vous pouvez spécifier des règles include/exclude supplémentaires s'il existe des différences de noms de fichiers entre les deux côtés qui doivent être prises en compte.
Lorsque vous passez une option --iconv à un démon rsync qui l'autorise, le démon utilise le jeu de caractères spécifié dans son paramètre de configuration "charset" quel que soit le jeu de caractères distant que vous passez réellement. Ainsi, vous pouvez vous sentir libre de spécifier uniquement le jeu de caractères local pour un transfert de démon (par exemple, --iconv=utf8).
--ipv4, -4 ou --ipv6, -6
Indique à rsync de préférer IPv4/IPv6 lors de la création de sockets ou de l'exécution de ssh. Ceci affecte les sockets sur lesquels rsync a un contrôle direct, tels que le socket sortant lors du contact direct avec un démon rsync, ainsi que la transmission de l'option -4 ou -6 à ssh lorsque rsync peut déduire que ssh est utilisé comme shell distant. Pour les autres shells distants, vous devrez spécifier directement l'option "--rsh SHELL -4" (ou toute autre option d'indication IPv4/IPv6 qu'il utilise).
Voir aussi la version daemon de ces options.
Si rsync a été compilé sans prise en charge d'IPv6, l'option --ipv6 n'aura aucun effet. La sortie de rsync --version contiendra "no IPv6" si c'est le cas.
--checksum-seed=NUM
Définit la graine de somme de contrôle sur l'entier NUM. Cette graine de somme de contrôle de 4 octets est incluse dans le calcul de chaque bloc et de la somme de contrôle de fichier MD4 (les sommes de contrôle de fichier MD5 plus modernes n'utilisent pas de graine). Par défaut, la graine de somme de contrôle est générée par le serveur et utilise par défaut l'heure actuelle (time()). Cette option est utilisée pour définir une graine de somme de contrôle spécifique, utile pour les applications qui souhaitent des sommes de contrôle de bloc répétables, ou dans le cas où l'utilisateur souhaite une graine de somme de contrôle plus aléatoire. Définir NUM sur 0 fait que rsync utilise la valeur par défaut de time() pour la graine de somme de contrôle.

OPTIONS DAEMON

Les options autorisées lors du lancement d'un démon rsync sont les suivantes :

--daemon
Ceci indique à rsync de s'exécuter en tant que démon. Le démon que vous lancez peut être accédé à l'aide d'un client rsync utilisant la syntaxe host::module ou rsync://host/module/.
Si l'entrée standard est un socket, rsync supposera qu'il est exécuté via inetd, sinon il se détachera du terminal actuel et deviendra un démon en arrière-plan. Le démon lira le fichier de configuration (rsyncd.conf) à chaque connexion d'un client et répondra aux requêtes en conséquence.
Voir la page de manuel de rsyncd.conf(5) pour plus de détails.
--address=ADDRESS
Par défaut, rsync se liera à l'adresse wildcard lorsqu'il est exécuté en tant que démon avec l'option --daemon. L'option --address vous permet de spécifier une adresse IP spécifique (ou un nom d'hôte) à laquelle se lier. Cela rend l'hébergement virtuel possible en conjonction avec l'option --config.
Voir aussi l'option globale d'adresse dans la page de manuel de rsyncd.conf et la version client de l'option --address.
--bwlimit=RATE
Cette option vous permet de spécifier le débit de transfert maximum pour les données que le démon envoie sur le socket. Le client peut toujours spécifier une valeur --bwlimit plus petite, mais aucune valeur plus grande ne sera autorisée.
Voir la version client de l'option --bwlimit pour quelques détails supplémentaires.
--config=FILE
Ceci spécifie un fichier de configuration alternatif au fichier par défaut. Ceci n'est pertinent que lorsque --daemon est spécifié. Le fichier par défaut est /etc/rsyncd.conf, sauf si le démon s'exécute via un programme de shell distant et que l'utilisateur distant n'est pas le super-utilisateur ; dans ce cas, le fichier par défaut est rsyncd.conf dans le répertoire courant (typiquement $HOME).
--dparam=OVERRIDE, -M
Cette option peut être utilisée pour définir un paramètre de configuration du démon lors du démarrage de rsync en mode démon. Elle équivaut à ajouter le paramètre à la fin des paramètres globaux avant la définition du premier module. Les noms de paramètres peuvent être spécifiés sans espaces, si vous le souhaitez. Par exemple :
rsync --daemon -M pidfile=/path/rsync.pid
--no-detach
Lorsqu'il est exécuté en tant que démon, cette option demande à rsync de ne pas se détacher et de ne pas devenir un processus d'arrière-plan. Cette option est requise lors de l'exécution en tant que service sur Cygwin, et peut également être utile lorsque rsync est supervisé par un programme tel que daemontools ou le System Resource Controller d'AIX. Il est également recommandé d'utiliser --no-detach lorsque rsync est exécuté sous un débogueur. Cette option n'a aucun effet si rsync est exécuté à partir d'inetd ou de sshd.
--port=PORT
Ceci spécifie un numéro de port TCP alternatif pour que le démon écoute, au lieu du port par défaut 873.
Voir aussi la version client de l'option --port et le paramètre global de port dans la page de manuel de rsyncd.conf.
--log-file=FILE
Cette option indique au démon rsync d'utiliser le nom de fichier journal donné au lieu d'utiliser le paramètre "log file" dans le fichier de configuration.
Voir aussi la version client de l'option --log-file.
--log-file-format=FORMAT
Cette option indique au démon rsync d'utiliser la chaîne FORMAT donnée au lieu d'utiliser le paramètre "log format" dans le fichier de configuration. Elle active également la "journalisation des transferts" sauf si la chaîne est vide, auquel cas la journalisation des transferts est désactivée.
Voir aussi la version client de l'option --log-file-format.
--sockopts
Ceci remplace le paramètre socket options dans le fichier rsyncd.conf et a la même syntaxe.
Voir aussi la version client de l'option --sockopts.
--verbose, -v
Cette option augmente la quantité d'informations que le démon journalise pendant sa phase de démarrage. Après la connexion du client, le niveau de verbosité du démon sera contrôlé par les options utilisées par le client et le paramètre "max verbosity" dans la section du module de configuration.
Voir aussi la version client de l'option --verbose.
--ipv4, -4 ou --ipv6, -6
Indique à rsync de préférer IPv4/IPv6 lors de la création des sockets entrants que le démon rsync utilisera pour écouter les connexions. L'une de ces options peut être requise dans les anciennes versions de Linux pour contourner un bug IPv6 du noyau (si vous voyez une erreur "adresse déjà utilisée" alors que rien d'autre n'utilise le port, essayez de spécifier --ipv6 ou --ipv4 lors du démarrage du démon).
Voir aussi la version client de ces options.
Si rsync a été compilé sans prise en charge d'IPv6, l'option --ipv6 n'aura aucun effet. La sortie de rsync --version contiendra "no IPv6" si c'est le cas.

RÈGLES DE FILTRE

Les règles de filtre permettent un contrôle personnalisé de plusieurs aspects de la manière dont les fichiers sont traités :

o
Contrôle quels fichiers le côté expéditeur inclut dans la liste de fichiers qui décrit la hiérarchie du transfert
o
Contrôle quels fichiers le côté récepteur protège de la suppression lorsque le fichier n'est pas dans la liste de fichiers de l'expéditeur
o
Contrôle quels noms d'attributs étendus sont ignorés lors de la copie des xattrs

Les règles sont soit spécifiées directement via des arguments d'option, soit elles peuvent être lues à partir d'un ou plusieurs fichiers. Les fichiers de règles de filtre peuvent même faire partie de la hiérarchie des fichiers copiés, affectant différentes parties de l'arborescence de différentes manières.

RÈGLES SIMPLES INCLUDE/EXCLUDE

Nous allons d'abord couvrir les bases de la manière dont les règles include & exclude affectent les fichiers transférés, en ignorant les effets secondaires de suppression. Les règles de filtre affectent principalement le contenu des répertoires dans lesquels rsync "récursive", mais elles peuvent également affecter un élément de niveau supérieur dans le transfert qui a été spécifié comme argument.

Par défaut, tout fichier/répertoire non correspondant est inclus dans le transfert, ce qui place le fichier/répertoire dans la liste de fichiers de l'expéditeur. L'utilisation d'une règle d'exclusion entraîne l'exclusion d'un ou plusieurs fichiers/répertoires correspondants de la liste de fichiers de l'expéditeur. Une règle d'inclusion peut être utilisée pour limiter l'effet d'une règle d'exclusion qui correspond à trop de fichiers.

L'ordre des règles est important car la première règle qui correspond est celle qui prend effet. Ainsi, si une règle précoce exclut un fichier, aucune règle d'inclusion qui la suit ne peut avoir d'effet. Cela signifie que vous devez placer toute substitution d'inclusion avant l'exclusion qu'elle est censée limiter.

Lorsqu'un répertoire est exclu, tout son contenu et sous-contenu sont également exclus. L'expéditeur ne le scanne pas du tout, ce qui peut économiser beaucoup de temps lors de l'ignorance de sous-arborescences volumineuses non nécessaires.

Il est également important de comprendre que les règles include/exclude sont appliquées à chaque fichier et répertoire dans lesquels l'expéditeur fait une récursion.

FILTER RULES

Rsync's filter rules allow you to specify which files and directories should be included or excluded from a transfer. This is a powerful feature that can be used to fine-tune your transfers, but it can also be complex to understand.

The basic idea is that rsync maintains a list of include and exclude rules. As rsync traverses the directory tree, it applies these rules to each file and directory it encounters. The first rule that matches a file or directory determines whether it is included or excluded from the transfer.

It is important to understand how rsync applies these rules when you are recursing into directories. If you specify a directory to be transferred, rsync must be able to traverse all the directories on the way down to that file. If any of those directories are excluded, the file will never be found and thus will not be included in the transfer. For example, if you are transferring the directory "a/path" and you want to ensure that the file "a/path/down/deep/wanted.txt" is included, then the directories "a/path", "a/path/down", and "a/path/down/deep" must not be excluded by any filter rules.

When you are working on the rules, it can be helpful to ask rsync to tell you what is being excluded/included and why. Specifying --debug=FILTER or (when pulling files) -M--debug=FILTER turns on level 1 of the FILTER debug information that will output a message any time that a file or directory is included or excluded and which rule it matched. Beginning in 3.2.4 it will also warn if a filter rule has trailing whitespace, since an exclude of "foo " (with a trailing space) will not exclude a file named "foo".

Exclude and include rules can specify wildcard PATTERN MATCHING RULES (similar to shell wildcards) that allow you to match things like a file suffix or a portion of a filename.

A rule can be limited to only affecting a directory by putting a trailing slash onto the filename.

SIMPLE INCLUDE/EXCLUDE EXAMPLE

With the following file tree created on the sending side:

mkdir x/
touch x/file.txt
mkdir x/y/
touch x/y/file.txt
touch x/y/zzz.txt
mkdir x/z/
touch x/z/file.txt

Then the following rsync command will transfer the file "x/y/file.txt" and the directories needed to hold it, resulting in the path "/tmp/x/y/file.txt" existing on the remote host:

rsync -ai -f'+ x/' -f'+ x/y/' -f'+ x/y/file.txt' -f'- *' x host:/tmp/

Aside: this copy could also have been accomplished using the -R option (though the 2 commands behave differently if deletions are enabled):

rsync -aiR x/y/file.txt host:/tmp/

The following command does not need an include of the "x" directory because it is not a part of the transfer (note the trailing slash). Running this command would copy just "/tmp/x/file.txt" because the "y" and "z" dirs get excluded:

rsync -ai -f'+ file.txt' -f'- *' x/ host:/tmp/x/

This command would omit the zzz.txt file while copying "x" and everything else it contains:

rsync -ai -f'- zzz.txt' x host:/tmp/

FILTER RULES WHEN DELETING

By default the include & exclude filter rules affect both the sender (as it creates its file list) and the receiver (as it creates its file lists for calculating deletions). If no delete option is in effect, the receiver skips creating the delete-related file lists. This two-sided default can be manually overridden so that you are only specifying sender rules or receiver rules, as described in the FILTER RULES IN DEPTH section.

When deleting, an exclude protects a file from being removed on the receiving side while an include overrides that protection (putting the file at risk of deletion). The default is for a file to be at risk -- its safety depends on it matching a corresponding file from the sender.

An example of the two-sided exclude effect can be illustrated by the copying of a C development directory between 2 systems. When doing a touch-up copy, you might want to skip copying the built executable and the .o files (sender hide) so that the receiving side can build their own and not lose any object files that are already correct (receiver protect). For instance:

rsync -ai --del -f'- *.o' -f'- cmd' src host:/dest/

Note that using -f'-p *.o' is even better than -f'- *.o' if there is a chance that the directory structure may have changed. The "p" modifier is discussed in FILTER RULE MODIFIERS.

One final note, if your shell doesn't mind unexpanded wildcards, you could simplify the typing of the filter options by using an underscore in place of the space and leaving off the quotes. For instance, -f -_*.o -f -_cmd (and similar) could be used instead of the filter options above.

FILTER RULES IN DEPTH

Rsync supports old-style include/exclude rules and new-style filter rules. The older rules are specified using --include and --exclude as well as the --include-from and --exclude-from. These are limited in behavior but they don't require a "-" or "+" prefix. An old-style exclude rule is turned into a "- name" filter rule (with no modifiers) and an old-style include rule is turned into a "+ name" filter rule (with no modifiers).

Rsync builds an ordered list of filter rules as specified on the command-line and/or read-in from files. New style filter rules have the following syntax:

RULE [PATTERN_OR_FILENAME]
RULE,MODIFIERS [PATTERN_OR_FILENAME]

You have your choice of using either short or long RULE names, as described below. If you use a short-named rule, the ',' separating the RULE from the MODIFIERS is optional. The PATTERN or FILENAME that follows (when present) must come after either a single space or an underscore (_). Any additional spaces and/or underscores are considered to be a part of the pattern name. Here are the available rule prefixes:

exclude, '-'
spécifie un modèle d'exclusion qui (par défaut) est à la fois une action de cacher et de protéger.
include, '+'
spécifie un modèle d'inclusion qui (par défaut) est à la fois une action de montrer et de risquer.
merge, '.'
spécifie un fichier de fusion côté client pour lire d'autres règles.
dir-merge, ':'
spécifie un fichier de fusion par répertoire. Utiliser ce type de règle de filtre nécessite de faire confiance à la vérification des filtres du côté de l'expéditeur, donc cela a l'effet secondaire mentionné sous l'option --trust-sender.
hide, 'H'
spécifie un modèle pour cacher des fichiers du transfert. Équivalent à une exclusion côté expéditeur uniquement, donc -f'H foo' peut également être spécifié comme -f'-s foo'.
show, 'S'
les fichiers qui correspondent au modèle ne sont pas cachés. Équivalent à une inclusion côté expéditeur uniquement, donc -f'S foo' peut également être spécifié comme -f'+s foo'.
protect, 'P'
spécifie un modèle pour protéger des fichiers contre la suppression. Équivalent à une exclusion côté récepteur uniquement, donc -f'P foo' peut également être spécifié comme -f'-r foo'.
risk, 'R'
les fichiers qui correspondent au modèle ne sont pas protégés. Équivalent à une inclusion côté récepteur uniquement, donc -f'R foo' peut également être spécifié comme -f'+r foo'.
clear, '!'
efface la liste d'inclusion/exclusion actuelle (ne prend pas d'argument)

Lorsque les règles sont lues à partir d'un fichier (en utilisant merge ou dir-merge), les lignes vides sont ignorées, tout comme les commentaires sur ligne entière commençant par un '#' (les règles de nom de fichier qui contiennent un caractère dièse ne sont pas affectées).

Notez également que les options --filter, --include et --exclude prennent une règle/un modèle chacune. Pour en ajouter plusieurs, vous pouvez répéter les options sur la ligne de commande, utiliser la syntaxe de fichier de fusion de l'option --filter, ou les options --include-from / --exclude-from.

PATTERN MATCHING RULES

La plupart des règles mentionnées ci-dessus prennent un argument qui spécifie ce que la règle doit faire correspondre. Si rsync parcourt une hiérarchie de répertoires, gardez à l'esprit que chaque modèle est comparé au nom de chaque répertoire dans le chemin de descente lors de la recherche des noms de fichiers à envoyer par rsync.

Les règles de correspondance pour l'argument du modèle prennent plusieurs formes :

o
Si un modèle contient un / (sans compter une barre oblique finale) ou un "**" (qui peut correspondre à une barre oblique), alors le modèle est comparé au chemin complet, y compris les répertoires préfixant dans le transfert. Si le modèle ne contient pas de / (non final) ou de "**", alors il est comparé uniquement au dernier composant du nom de fichier ou du chemin. Par exemple, foo signifie que le dernier composant du chemin doit être "foo" tandis que foo/bar correspondra aux 2 derniers éléments du chemin (tant que les deux éléments sont dans le transfert).
o
Un modèle qui se termine par une / ne correspond qu'à un répertoire, pas à un fichier régulier, un lien symbolique ou un périphérique.
o
Un modèle qui commence par une / est ancré au début du chemin de transfert au lieu de la fin. Par exemple, /foo/** ou /foo/bar/** ne correspondent qu'aux éléments initiaux du chemin. Si la règle est lue à partir d'un fichier de filtre par répertoire, le chemin de transfert correspondant commencera au niveau du fichier de filtre au lieu du sommet du transfert. Voir la section sur L'ANCRAGE DES MOTIFS D'INCLUSION/EXCLUSION pour une discussion complète sur la manière de spécifier un modèle qui correspond à la racine du transfert.

Rsync choisit entre effectuer une correspondance de chaîne simple et une correspondance de caractères génériques en vérifiant si le modèle contient l'un de ces trois caractères génériques : '*', '?', et '[' :

o
un '?' correspond à n'importe quel caractère unique sauf une barre oblique (/).
o
d>a '*' correspond à zéro ou plusieurs caractères ne faisant pas partie des barres obliques.
o
un '**' correspond à zéro ou plusieurs caractères, y compris les barres obliques.
o
un '[' introduit une classe de caractères, telle que [a-z] ou [[:alpha:]], qui doit correspondre à un seul caractère.
o
un '***' à la fin du modèle est un raccourci qui permet de faire correspondre un répertoire et tout son contenu à l'aide d'une seule règle. Par exemple, spécifier "dir_name/***" correspondra à la fois au répertoire "dir_name" (comme si "dir_name/" avait été spécifié) et à tout ce qui se trouve dans le répertoire (comme si "dir_name/**" avait été spécifié).
o
une barre oblique inverse peut être utilisée pour échapper un caractère joker, mais elle n'est interprétée comme un caractère d'échappement que si au moins un caractère joker est présent dans le modèle de correspondance. Par exemple, le modèle "foo\bar" correspond à cette barre oblique inverse littéralement, tandis que le modèle "foo\bar*" devrait être modifié en "foo\\bar*" pour éviter que "\b" ne devienne simplement "b".

Voici quelques exemples de correspondance d'exclusion/inclusion :

o
L'option -f'- *.o' exclurait tous les noms de fichiers se terminant par .o
o
L'option -f'- /foo' exclurait un fichier (ou un répertoire) nommé foo dans le répertoire racine du transfert
o
L'option -f'- foo/' exclurait tout répertoire nommé foo
o
L'option -f'- foo/*/bar' exclurait tout fichier/répertoire nommé bar qui se trouve à deux niveaux en dessous d'un répertoire nommé foo (si foo se trouve dans le transfert)
o
Les options -f'- /foo/**/bar' excluraient tout fichier/répertoire nommé bar qui se trouve à deux niveaux ou plus en dessous d'un répertoire de niveau supérieur nommé foo (notez que /foo/bar n'est pas exclu par ceci)
o
Les options -f'+ */' -f'+ *.c' -f'- *' incluraient tous les répertoires et les fichiers source .c mais rien d'autre
o
Les options -f'+ foo/' -f'+ foo/bar.c' -f'- *' incluraient uniquement le répertoire foo et foo/bar.c (le répertoire foo doit être explicitement inclus ou il serait exclu par "- *")

MODIFICATEURS DE REGLES DE FILTRE

Les modificateurs suivants sont acceptés après une règle d'inclusion (+) ou d'exclusion (-):

o
Un / spécifie que la règle d'inclusion/exclusion doit être comparée au chemin d'accès absolu de l'élément courant. Par exemple, -f'-/ /etc/passwd' exclurait le fichier passwd à chaque fois que le transfert envoie des fichiers du répertoire "/etc", et "-/ subdir/foo" exclurait toujours "foo" lorsqu'il se trouve dans un répertoire nommé "subdir", même si "foo" se trouve à la racine du transfert actuel.
o
Un ! spécifie que l'inclusion/exclusion prendra effet si le modèle échoue à correspondre. Par exemple, -f'-! */' exclurait tous les éléments qui ne sont pas des répertoires.
o
Un C est utilisé pour indiquer que toutes les règles d'exclusion globales de CVS doivent être insérées comme exclusions à la place de "-C". Aucun argument ne doit suivre.
o
Un s est utilisé pour indiquer que la règle s'applique au côté de l'envoi. Lorsqu'une règle affecte le côté de l'envoi, elle affecte les fichiers qui sont mis dans la liste des fichiers de l'expéditeur. Par défaut, une règle affecte les deux côtés sauf si l'option --delete-excluded a été spécifiée, auquel cas les règles par défaut ne s'appliquent qu'au côté de l'expéditeur. Voir également les règles de masquage (H) et d'affichage (S), qui sont un moyen alternatif de spécifier les inclusions/exclusions côté envoi.
o
Un r est utilisé pour indiquer que la règle s'applique au côté de la réception. Lorsqu'une règle affecte le côté de la réception, elle empêche la suppression des fichiers. Voir le modificateur s pour plus d'informations. Voir également les règles de protection (P) et de risque (R), qui sont un moyen alternatif de spécifier les inclusions/exclusions côté récepteur.
o
Un p indique qu'une règle est périssable, ce qui signifie qu'elle est ignorée dans les répertoires qui sont supprimés. Par exemple, les règles de l'option --cvs-exclude (-C) qui excluent des éléments tels que "CVS" et "*.o" sont marquées comme périssables, et n'empêcheront pas la suppression d'un répertoire qui a été supprimé sur la source sur la destination.
o
Un x indique qu'une règle affecte les noms de xattr dans les opérations de copie/suppression de xattr (et est donc ignorée lors de la comparaison des noms de fichiers/répertoires). Si aucune règle de comparaison de xattr n'est spécifiée, une règle de filtrage de xattr par défaut est utilisée (voir l'option --xattrs).

REGLES DE FILTRE DE FICHIER DE FUSION

Vous pouvez fusionner des fichiers entiers dans vos règles de filtre en spécifiant une règle de filtre de fusion (.) ou de fusion de répertoire (:), comme introduit dans la section REGLES DE FILTRE ci-dessus.

Il existe deux types de fichiers fusionnés : les fichiers de fusion à instance unique ('.') et les fichiers de fusion par répertoire (':'). Un fichier de fusion à instance unique est lu une fois, et ses règles sont incorporées dans la liste de filtres à la place de la règle ".". Pour les fichiers de fusion par répertoire, rsync scannera chaque répertoire qu'il traverse à la recherche du fichier nommé, fusionnant son contenu lorsque le fichier existe dans la liste actuelle des règles héritées. Ces fichiers de règles par répertoire doivent être créés côté expéditeur car c'est le côté expéditeur qui est scanné pour les fichiers disponibles à transférer. Ces fichiers de règles peuvent également devoir être transférés côté récepteur si vous voulez qu'ils affectent les fichiers qui ne sont pas supprimés (voir REGLES PAR REPERTOIRE ET SUPPRESSION ci-dessous).

Quelques exemples :

merge /etc/rsync/default.rules
. /etc/rsync/default.rules
dir-merge .per-dir-filter
dir-merge,n- .non-inherited-per-dir-excludes
:n- .non-inherited-per-dir-excludes

Les modificateurs suivants sont acceptés après une règle de fusion ou de fusion de répertoire :

o
Un - spécifie que le fichier doit contenir uniquement des modèles d'exclusion, sans autre analyse de règles, sauf pour les commentaires dans le fichier.
o
Un + spécifie que le fichier doit contenir uniquement des modèles d'inclusion, sans autre analyse de règles, sauf pour les commentaires dans le fichier.
o
Un C est un moyen de spécifier que le fichier doit être lu d'une manière compatible CVS. Cela active 'n', 'w' et '-', mais permet également de spécifier le jeton de suppression de liste (!). Si aucun nom de fichier n'est fourni, ".cvsignore" est supposé.
o
Un e exclura le nom du fichier de fusion du transfert ; par exemple, "dir-merge,e .rules" est comme "dir-merge .rules" et "- .rules".
o
Un n spécifie que les règles ne sont pas héritées par les sous-répertoires.
o
Un w spécifie que les règles sont divisées en mots par les espaces blancs au lieu de la division normale par lignes. Cela désactive également les commentaires. Note : l'espace qui sépare le préfixe de la règle est traité spécialement, donc "- foo + bar" est analysé comme deux règles (en supposant que l'analyse des préfixes n'ait pas été désactivée également).
o
Vous pouvez également spécifier n'importe lequel des modificateurs pour les règles "+" ou "-" (ci-dessus) afin que les règles lues à partir du fichier par défaut aient ce modificateur défini (à l'exception du modificateur !, qui ne serait pas utile). Par exemple, "merge,-/ .excl" traiterait le contenu de .excl comme des exclusions de chemin absolu, tandis que "dir-merge,s .filt" et ":sC" appliqueraient tous leurs règles par répertoire uniquement côté expéditeur. Si la règle de fusion spécifie les côtés à affecter (via le modificateur s ou r ou les deux), alors les règles dans le fichier ne doivent pas spécifier de côtés (via un modificateur ou un préfixe de règle tel que hide).

Les règles par répertoire sont héritées dans tous les sous-répertoires du répertoire où le fichier de fusion a été trouvé, sauf si le modificateur 'n' a été utilisé. Les règles de chaque sous-répertoire sont ajoutées avant les règles par répertoire héritées de leurs parents, ce qui donne aux nouvelles règles une priorité plus élevée que les règles héritées. L'ensemble des règles de fusion de répertoire sont regroupées à l'endroit où le fichier de fusion a été spécifié, il est donc possible de remplacer les règles de fusion de répertoire via une règle spécifiée plus tôt dans la liste des règles globales. Lorsque la règle de suppression de liste ("!") est lue à partir d'un fichier par répertoire, elle ne supprime que les règles héritées pour le fichier de fusion actuel.

Une autre façon d'empêcher une règle unique d'un fichier de fusion par répertoire d'être héritée est de l'ancrer avec une barre oblique initiale. Les règles ancrées dans un fichier de fusion par répertoire sont relatives au répertoire du fichier de fusion, donc un modèle "/foo" ne correspondra qu'au fichier "foo" dans le répertoire où le fichier de fusion par répertoire a été trouvé.

Voici un exemple de fichier de filtre que vous spécifieriez via --filter=". file":

merge /home/user/.global-filter
- *.gz
dir-merge .rules
+ *.[ch]
- *.o
- foo*

Cela fusionnera le contenu du fichier /home/user/.global-filter au début de la liste et transformera également le nom de fichier ".rules" en un fichier de filtre par répertoire. Toutes les règles lues avant le début du balayage du répertoire suivent les règles d'ancrage globales (c'est-à-dire qu'une barre oblique initiale correspond à la racine du transfert).

Si un fichier de fusion par répertoire est spécifié avec un chemin qui est un répertoire parent du premier répertoire de transfert, rsync scannera tous les répertoires parents à partir de ce point de départ jusqu'au répertoire de transfert pour le fichier par répertoire indiqué

RÈGLES DE FILTRE

Ces règles affectent la façon dont rsync analyse la liste des fichiers qui génèrent le transfert. Elles peuvent affecter les fichiers et les répertoires. Les règles de filtre sont appliquées dans l'ordre où elles apparaissent dans la ligne de commande, avec une priorité plus élevée pour les règles données plus tard. Ceci est un exemple de filtre courant (voir -F) :

--filter=': /.rsync-filter'

Cette règle indique à rsync de rechercher le fichier .rsync-filter dans tous les répertoires, de la racine jusqu'au répertoire parent du transfert, avant de commencer l'analyse normale des fichiers dans les répertoires envoyés dans le cadre du transfert. (Note : pour un démon rsync, la racine est toujours la même que le « chemin » du module.)

Quelques exemples de cette pré-analyse pour les fichiers par répertoire :

rsync -avF /src/path/ /dest/dir
rsync -av --filter=': ../../.rsync-filter' /src/path/ /dest/dir
rsync -av --filter=': .rsync-filter' /src/path/ /dest/dir

Les deux premières commandes ci-dessus rechercheront « .rsync-filter » dans « / » et « /src » avant que l'analyse normale ne commence à rechercher le fichier dans « /src/path » et ses sous-répertoires. La dernière commande évite l'analyse du répertoire parent et ne recherche les fichiers « .rsync-filter » que dans chaque répertoire qui fait partie du transfert.

Si vous souhaitez inclure le contenu d'un « .cvsignore » dans vos modèles, vous devriez utiliser la règle « :C », qui crée une fusion de répertoire du fichier .cvsignore, mais analysée d'une manière compatible avec CVS. Vous pouvez l'utiliser pour affecter l'emplacement où l'inclusion par défaut du fichier .cvsignore par répertoire de l'option --cvs-exclude (-C) est placée dans vos règles en plaçant « :C » où vous le souhaitez dans vos règles de filtre. Sans cela, rsync ajouterait la règle de fusion de répertoire pour le fichier .cvsignore à la fin de toutes vos autres règles (lui donnant une priorité inférieure à vos règles de ligne de commande). Par exemple :

cat <<EOT | rsync -avC --filter='. -' a/ b
+ foo.o
:C
- *.old
EOT
rsync -avC --include=foo.o -f :C --exclude='*.old' a/ b

Les deux commandes rsync ci-dessus sont identiques. Chacune fusionnera toutes les règles .cvsignore par répertoire au milieu de la liste plutôt qu'à la fin. Cela permet à leurs règles spécifiques au répertoire de supplanter les règles qui suivent le :C au lieu d'être asservies à toutes vos règles. Pour affecter les autres règles d'exclusion CVS (c'est-à-dire la liste par défaut des exclusions, le contenu de $HOME/.cvsignore et la valeur de $CVSIGNORE), vous devriez omettre l'option de ligne de commande -C et insérer à la place une règle « -C » dans vos règles de filtre ; par exemple, « --filter=-C ».

RÈGLE DE FILTRE DE VIDAGE DE LISTE

Vous pouvez vider la liste inclure/exclure actuelle en utilisant la règle de filtre « ! » (comme introduit dans la section RÈGLES DE FILTRE ci-dessus). La liste « actuelle » est soit la liste globale des règles (si la règle est rencontrée lors de l'analyse des options de filtre), soit un ensemble de règles par répertoire (qui sont héritées dans leur propre sous-liste, de sorte qu'un sous-répertoire peut utiliser ceci pour vider les règles du parent).

MODÈLES D'INCLUSION/EXCLUSION ANCRÉS

Comme mentionné précédemment, les modèles globaux d'inclusion/exclusion sont ancrés à la « racine du transfert » (par opposition aux modèles par répertoire, qui sont ancrés au répertoire du fichier de fusion). Si vous considérez le transfert comme un sous-arbre de noms envoyés de l'expéditeur au destinataire, la racine du transfert est l'endroit où l'arbre commence à être dupliqué dans le répertoire de destination. Cette racine régit les endroits où correspondent les modèles commençant par un /.

Parce que la correspondance est relative à la racine du transfert, modifier la barre oblique finale sur un chemin source ou modifier votre utilisation de l'option --relative affecte le chemin que vous devez utiliser dans votre correspondance (en plus de changer la quantité de l'arborescence de fichiers dupliquée sur l'hôte de destination). Les exemples suivants le démontrent.

Disons que nous voulons faire correspondre deux fichiers source, l'un avec un chemin absolu de « /home/me/foo/bar », et l'un avec un chemin de « /home/you/bar/baz ». Voici comment les différents choix de commande diffèrent pour un transfert à 2 sources :

Commande d'exemple : rsync -a /home/me /home/you /dest
Modèle +/- : /me/foo/bar
Modèle +/- : /you/bar/baz
Fichier cible : /dest/me/foo/bar
Fichier cible : /dest/you/bar/baz
Commande d'exemple : rsync -a /home/me/ /home/you/ /dest
Modèle +/- : /foo/bar               (notez l'absence de « me »)
Modèle +/- : /bar/baz               (notez l'absence de « you »)
Fichier cible : /dest/foo/bar
Fichier cible : /dest/bar/baz
Commande d'exemple : rsync -a --relative /home/me/ /home/you /dest
Modèle +/- : /home/me/foo/bar       (notez le chemin complet)
Modèle +/- : /home/you/bar/baz      (idem)
Fichier cible : /dest/home/me/foo/bar
Fichier cible : /dest/home/you/bar/baz
Commande d'exemple : cd /home; rsync -a --relative me/foo you/ /dest

Modèle +/- : /you/bar/baz     (idem)

Le moyen le plus simple de voir quel nom vous devriez filtrer est de regarder la sortie lorsque vous utilisez --verbose et de mettre un / devant le nom (utilisez l'option --dry-run si vous n'êtes pas encore prêt à copier des fichiers).

RÈGLES PAR RÉPERTOIRE ET SUPPRESSION

Sans option de suppression, les règles par répertoire ne sont pertinentes que du côté de l'expéditeur, vous pouvez donc exclure les fichiers de fusion sans affecter le transfert. Pour faciliter cela, le modificateur 'e' ajoute cette exclusion pour vous, comme vu dans ces deux commandes équivalentes :

rsync -av --filter=': .excl' --exclude=.excl host:src/dir /dest
rsync -av --filter=':e .excl' host:src/dir /dest

Cependant, si vous souhaitez effectuer une suppression du côté du destinataire ET que vous voulez que certains fichiers soient exclus de la suppression, vous devrez vous assurer que le côté destinataire connaît les fichiers à exclure. Le moyen le plus simple est d'inclure les fichiers de fusion par répertoire dans le transfert et d'utiliser --delete-after, car cela garantit que le côté destinataire obtient toutes les mêmes règles d'exclusion avant d'essayer de supprimer quoi que ce soit :

rsync -avF --delete-after host:src/dir /dest

Cependant, si les fichiers de fusion ne font pas partie du transfert, vous devrez soit spécifier des règles d'exclusion globales (c'est-à-dire spécifiées sur la ligne de commande), soit vous devrez maintenir vos propres fichiers de fusion par répertoire du côté du destinataire. Un exemple du premier est ceci (supposons que les fichiers .rules distants s'excluent eux-mêmes) :

rsync -av --filter=': .rules' --filter='. /my/extra.rules'
   --delete host:src/dir /dest

Dans l'exemple ci-dessus, le fichier extra.rules peut affecter les deux côtés du transfert, mais (du côté de l'expéditeur) les règles sont asservies aux règles fusionnées depuis les fichiers .rules car elles ont été spécifiées après la règle de fusion par répertoire.

Dans un dernier exemple, le côté distant exclut les fichiers .rsync-filter du transfert, mais nous voulons utiliser nos propres fichiers .rsync-filter pour contrôler ce qui est supprimé du côté du destinataire. Pour ce faire, nous devons exclure spécifiquement les fichiers de fusion par répertoire (afin qu'ils ne soient pas supprimés) puis placer des règles dans les fichiers locaux pour contrôler ce qui ne doit pas être supprimé. Comme avec l'une de ces commandes :

rsync -av --filter=':e /.rsync-filter' --delete \
    host:src/dir /dest
rsync -avFF --delete host:src/dir /dest

RÈGLES DE TRANSFERT

En plus des RÈGLES DE FILTRE qui affectent les analyses récursives de fichiers qui génèrent la liste des fichiers côté expéditeur et (en cas de suppression) côté destinataire, il existe des règles de transfert. Ces règles affectent les fichiers que le générateur décide de transférer sans les effets secondaires d'une règle de filtre d'exclusion. Les règles de transfert affectent uniquement les fichiers et jamais les répertoires.

Étant donné qu'une règle de transfert n'affecte pas ce qui entre dans la liste de fichiers de l'expéditeur (et du destinataire), elle ne peut avoir aucun effet sur les fichiers qui sont supprimés du côté du destinataire. Par exemple, si le fichier « foo » est présent dans la liste de l'expéditeur mais que sa taille est telle qu'il est omis en raison d'une règle de transfert, le côté destinataire ne demande pas le fichier. Cependant, sa présence dans la liste des fichiers signifie qu'un passage de suppression ne supprimera pas un fichier correspondant nommé « foo » du côté du destinataire. D'autre part, une exclusion côté serveur (masquage) du fichier « foo » laisse le fichier hors de la liste des fichiers du serveur, et en l'absence d'une exclusion côté destinataire (protection), le destinataire supprimera un fichier correspondant nommé « foo » si des suppressions sont demandées.

Étant donné que les fichiers sont toujours dans la liste des fichiers de l'expéditeur, l'option --prune-empty-dirs ne jugera pas un répertoire comme étant vide même s'il ne contient que des fichiers omis par les règles de transfert.

De même, une règle de transfert n'a aucun effet supplémentaire sur les fichiers qui sont supprimés du côté du destinataire, donc la définition d'une taille de fichier maximale pour le transfert n'empêche pas la suppression de gros fichiers.

Les exemples de règles de transfert incluent l'algorithme par défaut de « vérification rapide » (qui compare la taille et l'heure de modification), l'option --update, l'option --max-size, l'option --ignore-non-existing, et quelques autres.

MODE BATCH

Le mode batch peut être utilisé pour appliquer le même ensemble de mises à jour à de nombreux systèmes identiques. Supposons que l'on ait une arborescence répliquée sur plusieurs hôtes. Supposons maintenant que des modifications aient été apportées à cet arbre source et que ces modifications doivent être propagées aux autres hôtes. Pour ce faire en utilisant le mode batch, rsync est exécuté avec l'option write-batch pour appliquer les modifications apportées à l'arbre source à l'un des arbres de destination. L'option write-batch fait en sorte que le client rsync stocke dans un « fichier batch » toutes les informations nécessaires pour répéter cette opération sur d'autres arbres de destination identiques.

La génération du fichier batch une seule fois permet d'éviter d'avoir à effectuer la génération du statut du fichier, de la somme de contrôle et des blocs de données plus d'une fois lors de la mise à jour de plusieurs arbres de destination. Les protocoles de transport multicast peuvent être utilisés pour transférer les fichiers de mise à jour batch en parallèle vers de nombreux hôtes à la fois, au lieu d'envoyer les mêmes données à chaque hôte individuellement.

Pour appliquer les modifications enregistrées à un autre arbre de destination, exécutez rsync avec l'option read-batch, en spécifiant le nom du même fichier batch et l'arbre de destination. Rsync met à jour l'arbre de destination en utilisant les informations stockées dans le fichier batch.

Pour votre commodité, un fichier script est également créé lorsque l'option write-batch est utilisée : il sera nommé de la même manière que le fichier batch avec

".sh" ajouté. Ce fichier script contient une commande appropriée pour mettre à jour un arbre de destination à l'aide du fichier batch associé. Il peut être exécuté en utilisant un shell Bourne (ou similaire), en passant éventuellement un chemin d'arbre de destination alternatif qui est alors utilisé à la place du chemin de destination d'origine. Ceci est utile lorsque le chemin de l'arbre de destination sur l'hôte actuel diffère de celui utilisé pour créer le fichier batch.

Exemples:

$ rsync --write-batch=foo -a host:/source/dir/ /adest/dir/
$ scp foo* remote:
$ ssh remote ./foo.sh /bdest/dir/
$ rsync --write-batch=foo -a /source/dir/ /adest/dir/
$ ssh remote rsync --read-batch=- -a /bdest/dir/ <foo

Dans ces exemples, rsync est utilisé pour mettre à jour /adest/dir/ à partir de /source/dir/ et les informations pour répéter cette opération sont stockées dans "foo" et "foo.sh". L'hôte "remote" est ensuite mis à jour avec les données batchées allant dans le répertoire /bdest/dir. Les différences entre les deux exemples révèlent une partie de la flexibilité dont vous disposez quant à la manière de traiter les lots :

o
Le premier exemple montre que la copie initiale n'a pas besoin d'être locale -- vous pouvez pousser ou tirer des données vers/depuis un hôte distant en utilisant soit la syntaxe du shell distant, soit la syntaxe du démon rsync, selon votre préférence.
o
Le premier exemple utilise le fichier "foo.sh" créé pour obtenir les bonnes options rsync lors de l'exécution de la commande read-batch sur l'hôte distant.
o
Le second exemple lit les données batchées via l'entrée standard, de sorte que le fichier batch n'a pas besoin d'être copié sur la machine distante au préalable. Cet exemple évite le script foo.sh car il fallait utiliser une option --read-batch modifiée, mais vous pourriez éditer le fichier script si vous souhaitiez l'utiliser (assurez-vous simplement qu'aucune autre option n'essaie d'utiliser l'entrée standard, comme l'option --exclude-from=-).

Mises en garde:

L'option read-batch s'attend à ce que l'arbre de destination qu'elle met à jour soit identique à l'arbre de destination utilisé pour créer le jeu de fichiers de mise à jour batchée. Lorsqu'une différence entre les arbres de destination est rencontrée, la mise à jour peut être rejetée avec un avertissement (si le fichier apparaît comme déjà à jour) ou la mise à jour du fichier peut être tentée et, si le fichier ne parvient pas à être vérifié, la mise à jour sera rejetée avec une erreur. Cela signifie qu'il devrait être sûr de relancer une opération read-batch si la commande a été interrompue. Si vous souhaitez forcer la tentative de mise à jour batchée systématique, indépendamment de la taille et de la date du fichier, utilisez l'option -I (lors de la lecture du batch). En cas d'erreur, l'arbre de destination sera probablement dans un état partiellement mis à jour. Dans ce cas, rsync peut être utilisé dans son mode de fonctionnement habituel (non batch) pour corriger l'arbre de destination.

La version de rsync utilisée sur toutes les destinations doit être au moins aussi récente que celle utilisée pour générer le fichier batch. Rsync se terminera avec une erreur si la version du protocole dans le fichier batch est trop récente pour que le rsync qui lit le batch puisse la gérer. Voir également l'option --protocol pour une manière de faire générer par le rsync créant un fichier batch qu'un rsync plus ancien peut comprendre. (Notez que les fichiers batch ont changé de format dans la version 2.6.3, donc mélanger des versions plus anciennes que celle-ci avec des versions plus récentes ne fonctionnera pas.)

Lors de la lecture d'un fichier batch, rsync forcera la valeur de certaines options pour qu'elles correspondent aux données du fichier batch si vous ne les avez pas définies de la même manière que la commande d'écriture batch. D'autres options peuvent (et devraient) être modifiées. Par exemple, --write-batch devient --read-batch, --files-from est supprimé, et les options --filter / --include / --exclude ne sont pas nécessaires à moins que l'une des options --delete ne soit spécifiée.

Le code qui crée le fichier BATCH.sh transforme toutes les options de filtre/inclusion/exclusion en une seule liste qui est ajoutée en tant que document "here" (ici) au fichier script shell. Un utilisateur avancé peut l'utiliser pour modifier la liste d'exclusion si un changement dans ce qui est supprimé par --delete est souhaité. Un utilisateur normal peut ignorer ce détail et simplement utiliser le script shell comme un moyen facile d'exécuter la commande --read-batch appropriée pour les données batchées.

Le mode batch d'origine dans rsync était basé sur "rsync+", mais la dernière version utilise une nouvelle implémentation.

LIENS SYMBOLIQUES

Trois comportements de base sont possibles lorsqu'rsync rencontre un lien symbolique dans le répertoire source.

Par défaut, les liens symboliques ne sont pas transférés du tout. Un message "skipping non-regular" (ignorant le fichier non régulier) est émis pour tous les liens symboliques existants.

Si --links est spécifié, alors les liens symboliques sont ajoutés au transfert (au lieu d'être ignorés bruyamment), et le comportement par défaut est de les recréer avec la même cible sur la destination. Notez que --archive implique --links.

Si --copy-links est spécifié, alors les liens symboliques sont "effondrés" en copiant leur référence, plutôt que le lien.

Rsync peut également distinguer les liens symboliques "sûrs" et "dangereux". Un exemple où cela pourrait être utilisé est un miroir de site web qui souhaite s'assurer que le module rsync copié n'inclut pas de liens symboliques vers /etc/passwd dans la section publique du site. L'utilisation de --copy-unsafe-links entraînera la copie de tous les liens comme le fichier vers lequel ils pointent sur la destination. L'utilisation de --safe-links entraînera l'omission des liens dangereux par le récepteur. (Notez que vous devez spécifier ou impliquer --links pour que --safe-links ait un effet.)

Les liens symboliques sont considérés comme dangereux s'ils sont des liens absolus (commencent par /), vides, ou s'ils contiennent suffisamment de composants ".." pour remonter au-dessus du transfert.

Voici un résumé de l'interprétation des options de lien symbolique. La liste est par ordre de priorité, donc si votre combinaison d'options n'est pas mentionnée, utilisez la première ligne qui est un sous-ensemble complet de vos options :

--copy-links
Transforme tous les liens symboliques en fichiers et répertoires normaux (ne laissant aucun lien symbolique dans le transfert pour que d'autres options agissent).
--copy-dirlinks
Transforme uniquement les liens symboliques vers des répertoires en vrais répertoires, laissant tous les autres liens symboliques être traités comme décrit ci-dessous.
--links --copy-unsafe-links
Transforme tous les liens symboliques dangereux en fichiers et crée tous les liens symboliques sûrs.
--copy-unsafe-links
Transforme tous les liens symboliques dangereux en fichiers, ignore bruyamment tous les liens symboliques sûrs.
--links --safe-links
Le récepteur omet la création des liens symboliques dangereux trouvés dans le transfert et crée ceux qui sont sûrs.
--links
Crée tous les liens symboliques.

Pour l'effet de --munge-links, voir la discussion dans la section de cette option.

Notez que l'option --keep-dirlinks n'affecte pas les liens symboliques dans le transfert, mais affecte plutôt la manière dont rsync traite un lien symbolique vers un répertoire qui existe déjà côté réception. Voir la section de cette option pour un avertissement.

DIAGNOSTICS

Rsync produit occasionnellement des messages d'erreur qui peuvent sembler un peu cryptiques. Celui qui semble causer le plus de confusion est "protocol version mismatch -- is your shell clean?" (incompatibilité de version de protocole -- votre shell est-il propre ?).

Ce message est généralement causé par vos scripts de démarrage ou votre installation de shell distant produisant des caractères indésirables sur le flux que rsync utilise pour son transport. La manière de diagnostiquer ce problème est d'exécuter votre shell distant comme suit :

ssh remotehost /bin/true > out.dat

puis regardez out.dat. Si tout fonctionne correctement, out.dat devrait être un fichier de taille nulle. Si vous obtenez l'erreur ci-dessus de la part de rsync, vous constaterez probablement que out.dat contient du texte ou des données. Examinez le contenu et essayez de déterminer ce qui le produit. La cause la plus fréquente est la mauvaise configuration des scripts de démarrage du shell (tels que .cshrc ou .profile) qui contiennent des instructions de sortie pour les connexions non interactives.

Si vous avez des difficultés à déboguer les motifs de filtrage, essayez de spécifier l'option -vv. À ce niveau de verbosité, rsync montrera pourquoi chaque fichier individuel est inclus ou exclu.
