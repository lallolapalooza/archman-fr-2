rsyncd.conf(5) Commandes utilisateur rsyncd.conf(5)

NOM

rsyncd.conf - fichier de configuration pour rsync en mode démon

SYNOPSIS

rsyncd.conf

La version en ligne de cette page de manuel (qui inclut des liens croisés vers les sujets) est disponible sur https://download.samba.org/pub/rsync/rsyncd.conf.5.

DESCRIPTION

Le fichier rsyncd.conf est le fichier de configuration d'exécution pour rsync lorsqu'il est exécuté en tant que démon rsync.

Le fichier rsyncd.conf contrôle l'authentification, l'accès, la journalisation et les modules disponibles.

FORMAT DU FICHIER

Le fichier se compose de modules et de paramètres. Un module commence par le nom du module entre crochets et se poursuit jusqu'à ce qu'un autre module commence. Les modules contiennent des paramètres de la forme nom = valeur.

Le fichier est basé sur des lignes -- c'est-à-dire que chaque ligne terminée par un retour à la ligne représente soit un commentaire, un nom de module, soit un paramètre.

Seul le premier signe égal dans un paramètre est significatif. Les espaces avant ou après le premier signe égal sont ignorés. Les espaces au début, à la fin et à l'intérieur des noms de modules et de paramètres sont sans importance. Les espaces au début et à la fin d'une valeur de paramètre sont ignorés. Les espaces à l'intérieur d'une valeur de paramètre sont conservés littéralement.

Toute ligne **commençant** par un dièse (#) est ignorée, de même que les lignes ne contenant que des espaces. (Si un dièse apparaît après autre chose que des espaces en début de ligne, il est considéré comme faisant partie du contenu de la ligne.)

Toute ligne se terminant par un \ est « continuée » sur la ligne suivante, à la manière habituelle d'UNIX.

Les valeurs qui suivent le signe égal dans les paramètres sont soit une chaîne (pas besoin de guillemets), soit une valeur booléenne, qui peut être donnée sous forme de oui/non, 0/1 ou vrai/faux. La casse n'est pas sensible dans les valeurs booléennes, mais elle est préservée dans les valeurs de chaîne.

LANCEMENT DU DÉMON RSYNC

Le démon rsync est lancé en spécifiant l'option --daemon à rsync.

Le démon doit s'exécuter avec les privilèges root si vous souhaitez utiliser le chroot, vous connecter à un port numéroté inférieur à 1024 (comme c'est le cas par défaut pour 873), ou définir la propriété des fichiers. Sinon, il doit simplement avoir l'autorisation de lire et écrire les fichiers de données, de journalisation et de verrouillage appropriés.

Vous pouvez le lancer soit via inetd, soit en tant que démon autonome, soit depuis un client rsync via un shell distant. S'il est exécuté en tant que démon autonome, lancez simplement la commande « rsync --daemon » depuis un script de démarrage approprié.

Lorsque vous l'exécutez via inetd, vous devriez ajouter une ligne comme celle-ci à /etc/services :

rsync           873/tcp

et une seule ligne ressemblant à ceci dans /etc/inetd.conf :

rsync   stream  tcp     nowait  root   /usr/bin/rsync rsyncd --daemon

Remplacez « /usr/bin/rsync » par le chemin d'accès à l'endroit où vous avez installé rsync sur votre système. Vous devrez ensuite envoyer un signal HUP à inetd pour qu'il relise son fichier de configuration.

Notez que vous ne devez **pas** envoyer de signal HUP au démon rsync pour le forcer à relire le fichier rsyncd.conf. Le fichier est re-lu à chaque connexion client.

PARAMÈTRES GLOBAUX

Les premiers paramètres du fichier (avant un en-tête [module]) sont les paramètres globaux :

motd file
Ce paramètre vous permet de spécifier un « message du jour » (MOTD) à afficher aux clients à chaque connexion. Il contient généralement des informations sur le site et des avis légaux. La valeur par défaut est aucun fichier MOTD. Ceci peut être remplacé par l'option de ligne de commande --dparam=motdfile=FICHIER lors du démarrage du démon.
pid file
Ce paramètre indique au démon rsync d'écrire son identifiant de processus dans ce fichier. rsync garde le fichier verrouillé afin de savoir quand il est sûr de remplacer un fichier existant.
Le nom du fichier peut être remplacé par l'option de ligne de commande --dparam=pidfile=FICHIER lors du démarrage du démon.
port
Vous pouvez remplacer le port par défaut sur lequel le démon écoutera en spécifiant cette valeur (par défaut 873). Ceci est ignoré si le démon est exécuté par inetd, et est remplacé par l'option de ligne de commande --port.
address
Vous pouvez remplacer l'adresse IP par défaut sur laquelle le démon écoutera en spécifiant cette valeur. Ceci est ignoré si le démon est exécuté par inetd, et est remplacé par l'option de ligne de commande --address.
socket options
Ce paramètre peut procurer un plaisir infini aux personnes qui aiment optimiser leurs systèmes à l'extrême. Vous pouvez définir toutes sortes d'options de socket qui peuvent rendre les transferts plus rapides (ou plus lents !). Lisez la page man de l'appel système setsockopt() pour des détails sur certaines des options que vous pouvez être en mesure de définir. Par défaut, aucune option spéciale de socket n'est définie. Ces paramètres peuvent également être spécifiés via l'option de ligne de commande --sockopts.
listen backlog
Vous pouvez remplacer la valeur par défaut de la file d'attente (backlog) lorsque le démon écoute les connexions. Par défaut, elle est de 5.

Vous pouvez également inclure des PARAMÈTRES DE MODULE dans la partie globale du fichier de configuration, auquel cas la valeur fournie remplacera la valeur par défaut pour ce paramètre.

Vous pouvez utiliser des références aux variables d'environnement dans les valeurs des paramètres. Les paramètres de type chaîne verront leurs références %VAR% développées aussi tard que possible (lorsque la chaîne est utilisée pour la première fois dans le programme), permettant l'utilisation de variables que rsync définit au moment de la connexion, comme RSYNC_USER_NAME. Les paramètres non-chaînes (comme les paramètres vrai/faux) sont développés lors de leur lecture depuis le fichier de configuration. Si une variable n'existe pas dans l'environnement, ou si une séquence de caractères n'est pas une référence valide (comme un signe pourcentage non apparié), les caractères bruts sont transmis tels quels. Cela aide à la compatibilité descendante et à la sécurité (par exemple, développer un %VAR% inexistant en une chaîne vide dans un chemin pourrait aboutir à un chemin très dangereux). La manière la plus sûre d'insérer un % littéral dans une valeur est d'utiliser %%.

PARAMÈTRES DE MODULE

Après les paramètres globaux, vous devez définir un certain nombre de modules, chaque module exportant un arbre de répertoires sous un nom symbolique. Les modules sont exportés en spécifiant un nom de module entre crochets [module] suivi des paramètres pour ce module. Le nom du module ne peut pas contenir de barre oblique ni de crochet fermant. Si le nom contient des espaces, chaque séquence d'espaces internes sera remplacée par un seul espace, tandis que les espaces au début ou à la fin seront ignorés.

Il existe également un nom de module spécial « [global] » qui ne définit pas un module mais bascule plutôt vers le contexte des paramètres globaux où des paramètres par défaut peuvent être spécifiés. Étant donné que chaque module défini reçoit son ensemble complet de paramètres en combinant les valeurs par défaut définies à cette position dans le fichier de configuration et sa propre liste de paramètres, l'utilisation d'une section « [global] » peut aider à maintenir des valeurs de configuration partagées pour plusieurs modules.

Comme pour les PARAMÈTRES GLOBAUX, vous pouvez utiliser des références aux variables d'environnement dans les valeurs des paramètres. Voir cette section pour les détails.

comment
Ce paramètre spécifie une chaîne de description qui est affichée à côté du nom du module lorsque les clients obtiennent la liste des modules disponibles. La valeur par défaut est aucun commentaire.
path
Ce paramètre spécifie le répertoire dans le système de fichiers du démon à rendre disponible dans ce module. Vous devez spécifier ce paramètre pour chaque module dans rsyncd.conf.
Si la valeur contient un élément « /./ », le chemin sera divisé à cet endroit en un répertoire chroot et un sous-répertoire inner-chroot. Si use chroot est défini sur false, cependant, le répertoire pointant inutilement sera simplement retiré du chemin. Un exemple de cette idiome est :
path =

Ce site n'est en aucun cas associé à Arch Linux ni affilié à ce projet. Le contenu est uniquement une traduction des pages de manuel d'Arch publiées sur man.archlinux.org.

/var/rsync/./module1
Cela va (lors de l'utilisation de chroot) faire un chroot vers "/var/rsync" et définir le chemin interne au chroot sur "/module1".
Vous pouvez baser la valeur du chemin sur une variable d'environnement en entourant le nom de la variable de signes de pourcentage. Vous pouvez même référencer une variable qui est définie par rsync lorsque l'utilisateur se connecte. Par exemple, ceci utiliserait le nom de l'utilisateur autorisant dans le chemin :
path = /home/%RSYNC_USER_NAME%
Il est acceptable que le chemin contienne des espaces internes ; ils seront conservés tels quels (ce qui signifie que vous ne devriez pas essayer de les échapper). Si votre répertoire final a un espace à la fin (et que ce n'est pas quelque chose que vous souhaitez corriger), ajoutez une barre oblique à la fin du chemin pour éviter de perdre l'espace blanc final.
use chroot
Si "use chroot" est vrai, le démon rsync effectuera un chroot vers le "path" avant de commencer le transfert de fichiers avec le client. Cela présente l'avantage d'une protection supplémentaire contre d'éventuels trous de sécurité dans l'implémentation, mais il présente les inconvénients de nécessiter des privilèges de super-utilisateur, de ne pas pouvoir suivre les liens symboliques qui sont absolus ou situés en dehors de la nouvelle racine du chemin, et de compliquer la préservation des utilisateurs et des groupes par nom (voir ci-dessous).
Si use chroot n'est pas défini, il tente par défaut d'activer un chroot mais permet au démon de continuer (après avoir enregistré un avertissement) s'il échoue. La seule exception à cela est lorsqu'un path de module contient un diviseur de chroot "/./" ; cela amène une valeur non définie à être traitée comme vraie pour ce module.
Avant rsync 3.2.7, la valeur par défaut était "true". Le nouveau défaut "non défini" facilite la configuration d'un démon rsync en tant qu'utilisateur non root ou l'exécution d'un démon sur un système où chroot échoue. Définir explicitement la valeur sur "true" dans rsyncd.conf nécessitera toujours que le chroot réussisse.
Il est également possible de spécifier un répertoire de points (dot-dir) dans le "path" du module pour indiquer que vous souhaitez changer de répertoire (chdir) vers la partie précédente du chemin, puis servir des fichiers depuis l'intérieur de la partie suivante du chemin (avec assainissement et suppression par défaut des liens symboliques). Cela peut être utile si vous avez besoin de certains répertoires de bibliothèques à l'intérieur du chroot (typiquement pour les recherches uid et gid) mais que vous ne souhaitez pas placer le répertoire de bibliothèques en haut du chemin servi (même s'ils peuvent être masqués avec une directive exclude). Cependant, un meilleur choix pour une configuration rsync moderne est d'utiliser un name converter et d'essayer d'éviter complètement les répertoires de bibliothèques internes. Voir également le paramètre daemon chroot, qui amène rsync à faire un chroot dans sa propre zone de chroot avant d'effectuer tout chroot lié au chemin.
Si le démon sert le répertoire "/" (soit directement, soit en raison d'un chroot vers le chemin du module), rsync n'effectue aucun assainissement de chemin ni aucune modification (par défaut) des liens.
Lorsqu'il doit limiter l'accès à un sous-répertoire particulier (soit parce que le chroot est désactivé, soit parce qu'un chemin interne au chroot est défini), rsync modifie les liens symboliques (par défaut) et assainit les chemins. Ceux qui n'aiment pas les liens symboliques modifiés (et qui font vraiment, vraiment confiance à leurs utilisateurs pour ne pas s'échapper du sous-répertoire) peuvent désactiver la modification des liens symboliques via le paramètre "munge symlinks".
Lorsque rsync assainit les chemins, il supprime les éléments de chemin ".." des arguments qui, selon lui, échapperaient à la hiérarchie du module. Il substitue également les barres obliques initiales dans les chemins absolus par le chemin du module (de sorte que les options telles que --backup-dir et --compare-dest interprètent un chemin absolu comme étant ancré dans le répertoire "path" du module).
Lorsqu'un chroot est en vigueur et que le paramètre "name converter" n'est pas défini, le paramètre "numeric ids" sera activé par défaut (désactivant les recherches de noms). Cela signifie que si vous configurez manuellement des bibliothèques de recherche de noms dans votre chroot (au lieu d'utiliser un convertisseur de noms), vous devez explicitement définir numeric ids = false pour que rsync effectue des recherches de noms.
Si vous copiez des ressources de bibliothèque dans la zone de chroot du module, vous devriez les protéger via les paramètres normaux d'utilisateur/groupe ou ACL de votre système d'exploitation (pour empêcher l'utilisateur du module rsync de les modifier), puis les masquer à la vue de l'utilisateur via "exclude" (voir comment dans la discussion de ce paramètre). Cependant, il est plus facile et plus sûr de configurer un convertisseur de noms.
daemon chroot
Ce paramètre spécifie un chemin vers lequel le démon effectuera un chroot avant de commencer la communication avec les clients. Les chemins des modules (et tous les paramètres "use chroot") seront alors relatifs à celui-ci. Cela vous permet de choisir si vous voulez que l'ensemble du démon soit en chroot (avec ce paramètre), seulement les transferts soient en chroot (avec "use chroot"), ou les deux. Gardez à l'esprit que la zone "daemon chroot" peut nécessiter divers fichiers OS/lib/etc installés pour permettre au démon de fonctionner. Par défaut, le démon s'exécute sans aucun chroot.
proxy protocol
Lorsque ce paramètre est activé, toutes les connexions entrantes doivent commencer par un en-tête de protocole proxy V1 ou V2. Si l'en-tête est introuvable, la connexion est fermée.
Définir ceci sur true nécessite un serveur proxy pour transmettre les informations IP sources à rsync, vous permettant de journaliser des informations IP/hôte correctes et d'utiliser des restrictions IP orientées client. La valeur par défaut false signifie que les informations IP proviennent directement des métadonnées du socket. Si rsync n'est pas derrière un proxy, cela doit être désactivé.
ATTENTION : l'utilisation de cette option peut être dangereuse si vous ne vous assurez pas que seul le proxy est autorisé à se connecter au port rsync. Si des connexions non proxysées sont autorisées, le client pourra utiliser un rsync modifié pour usurper n'importe quelle adresse IP distante de son choix. Vous pouvez sécuriser cela en utilisant des règles iptables comme -uid-owner root (pour un accès strict en localhost), diverses règles de pare-feu, ou vous pouvez exiger une authentification par mot de passe afin que toute usurpation par les utilisateurs ne leur accorde pas d'accès supplémentaire.
Ce paramètre est global. Si vous avez besoin que certains modules l'exigent et d'autres non, vous devrez configurer plusieurs processus de démon rsync sur différents ports.
name converter
Ce paramètre vous permet de spécifier un programme qui sera exécuté par le démon rsync pour effectuer des conversions d'utilisateurs et de groupes entre noms et identifiants. Ce script est démarré avant toute configuration de chroot, et s'exécute en tant qu'utilisateur du démon (pas l'utilisateur du transfert). Vous pouvez spécifier un chemin absolu complet ou un nom de programme présent dans le $PATH.
Le programme peut être utilisé pour effectuer des recherches normales d'utilisateurs et de groupes sans avoir à placer de fichiers supplémentaires dans la zone de chroot du module ou vous pouvez effectuer des conversions personnalisées.
Le programme nameconvert a accès à toutes les variables d'environnement décrites dans la section sur pre-xfer exec. Ceci est utile si vous souhaitez personnaliser la conversion en utilisant des informations sur le module et/ou la requête de copie.
Il existe un script python d'exemple dans le répertoire de support nommé "nameconvert" qui implémente les recherches normales d'utilisateurs et de groupes. N'hésitez pas à le personnaliser ou à l'utiliser simplement comme documentation pour implémenter le vôtre.
numeric ids
L'activation de ce paramètre désactive le mappage des utilisateurs et des groupes par nom pour le module de démon actuel. Cela empêche le démon d'essayer de charger des fichiers ou des bibliothèques liés aux utilisateurs/groupes. Cette activation fait que le transfert se comporte comme si le client avait passé l'option de ligne de commande --numeric-ids. Par défaut, ce paramètre est activé pour les modules chroot et désactivé pour les modules non chroot. Gardez également à l'esprit que la préservation des uid/gid nécessite que le module s'exécute en tant que root (voir "uid") ou que "fake super" soit configuré.
Un module activé pour le chroot ne doit pas avoir ce paramètre défini sur false, sauf si vous utilisez un programme "name converter" ou si vous avez pris des mesures pour garantir que le module dispose des ressources nécessaires pour traduire les noms et qu'il n'est pas possible pour un utilisateur de modifier ces ressources.
munge symlinks
Ce paramètre indique à rsync de modifier tous les liens symboliques de la même manière que l'option de ligne de commande --munge-links (qui n'affecte pas le démon) (en utilisant une méthode décrite ci-dessous). Cela devrait aider à protéger vos fichiers contre les manipulations de l'utilisateur lorsque votre module de démon est inscriptible. La valeur par défaut est désactivée lorsque "use chroot" est activé avec un chemin interne au chroot de "/", OU si "daemon chroot" est activé, sinon il est activé.
Si vous désactivez ce paramètre sur un démon qui n'est pas en lecture seule, il existe des astuces qu'un utilisateur peut utiliser avec des liens symboliques téléchargés pour accéder à des éléments exclus du démon (si votre module en a), et, si "use chroot" est désactivé, rsync peut même être piégé pour montrer ou modifier des données situées en dehors du chemin du module (selon les permissions d'accès).
La façon dont rsync désactive l'utilisation des liens symboliques est de préfixer chacun d'eux avec la chaîne "/rsyncd-munged/". Cela empêche l'utilisation des liens tant que ce répertoire n'existe pas. Lorsque ce paramètre est activé, rsync refusera de s'exécuter si ce chemin est un répertoire ou un lien symbolique vers un répertoire. Lors de l'utilisation du paramètre "munge symlinks" dans une zone chroot avec un chemin interne au chroot de "/", vous devriez ajouter "/rsyncd-munged/" au paramètre exclude du module afin qu'un utilisateur ne puisse pas essayer de le créer.
Note : rsync ne fait aucune tentative pour vérifier si les liens symboliques préexistants dans la hiérarchie du module sont aussi sûrs que vous le souhaitez (sauf, bien sûr, s'il vient de copier toute la hiérarchie). Si vous configurez un démon rsync sur une nouvelle zone ou ajoutez des liens symboliques localement, vous pouvez protéger manuellement vos liens symboliques contre les abus en préfixant "/rsyncd-munged/" au début de la valeur de chaque lien symbolique. Il existe un script perl dans le répertoire de support du code source nommé "munge-symlinks" qui peut être utilisé pour ajouter ou supprimer ce préfixe de vos liens symboliques.
Lorsque ce paramètre est désactivé sur un module inscriptible et que "use chroot" est désactivé (ou que le chemin interne au chroot n'est pas "/"), les liens symboliques entrants seront modifiés pour supprimer une barre oblique initiale et supprimer les éléments de chemin ".." que rsync pense permettre à un lien symbolique de s'échapper.
Les façons astucieuses de contourner cela existent, cependant, vous devriez faire confiance à vos utilisateurs si vous choisissez cette combinaison de paramètres.
charset
Ceci spécifie le nom du jeu de caractères dans lequel les noms de fichiers du module sont stockés. Si le client utilise une option --iconv, le démon utilisera la valeur du paramètre "charset" indépendamment du jeu de caractères que le client a réellement passé. Cela permet au démon de supporter la conversion des jeux de caractères dans un module chroot sans fichiers supplémentaires dans la zone chroot, et assure également que la traduction des noms est effectuée de manière cohérente. Si le paramètre "charset" n'est pas défini, l'option --iconv est refusée, tout comme si "iconv" avait été spécifié via "refuse options".
Si vous souhaitez forcer les utilisateurs à utiliser toujours --iconv pour un module particulier, ajoutez "no-iconv" au paramètre "refuse options". Gardez à l'esprit que cela restreindra l'accès à votre module aux clients rsync très récents.
max connections
Ce paramètre vous permet de spécifier le nombre maximum de connexions simultanées que vous autoriserez. Tous les clients se connectant lorsque le maximum est atteint recevront un message leur demandant de réessayer plus tard. La valeur par défaut est 0, ce qui signifie aucune limite. Une valeur négative désactive le module. Voir aussi le paramètre "lock file".
log file
Lorsque le paramètre "log file" est défini sur une chaîne non vide, le démon rsync enregistrera les messages dans le fichier indiqué plutôt que d'utiliser syslog. Ceci est particulièrement utile sur les systèmes (tels que AIX) où syslog() ne fonctionne pas pour les programmes chrootés. Le fichier est ouvert avant l'appel à chroot(), ce qui permet de le placer en dehors du transfert. Si cette valeur est définie au niveau du module plutôt qu'au niveau global, le journal global contiendra toujours les échecs d'autorisation ou les messages d'erreur du fichier de configuration.
Si le démon ne parvient pas à ouvrir le fichier spécifié, il se rabattra sur l'utilisation de syslog et affichera une erreur concernant l'échec. (Notez que l'échec d'ouverture du fichier journal spécifié était auparavant une erreur fatale.)
Ce réglage peut être outrepassé en utilisant les options de ligne de commande --log-file=FILE ou --dparam=logfile=FILE. La première outrepasse tous les paramètres du fichier journal du démon et tous les réglages du module. La seconde définit le fichier journal du démon et la valeur par défaut pour tous les modules, ce qui permet toujours aux modules d'outrepasser le réglage par défaut.
syslog facility
Ce paramètre vous permet de spécifier le nom de la facilité syslog à utiliser lors de l'enregistrement des messages du démon rsync. Vous pouvez utiliser n'importe quel nom de facilité syslog standard défini sur votre système. Les noms courants sont auth, authpriv, cron, daemon, ftp, kern, lpr, mail, news, security, syslog, user, uucp, local0, local1, local2, local3, local4, local5, local6 et local7. La valeur par défaut est daemon. Ce réglage n'a aucun effet si le réglage "log file" est une chaîne non vide (définie dans les réglages par module ou héritée des réglages globaux).
syslog tag
Ce paramètre vous permet de spécifier le tag syslog à utiliser lors de l'enregistrement des messages du démon rsync. La valeur par défaut est "rsyncd". Ce réglage n'a aucun effet si le réglage "log file" est une chaîne non vide (définie dans les réglages par module ou héritée des réglages globaux).
Par exemple, si vous souhaitiez que le nom de chaque utilisateur authentifié soit inclus dans le tag syslog, vous pourriez faire quelque chose comme ceci :
syslog tag = rsyncd.%RSYNC_USER_NAME%
max verbosity
Ce paramètre vous permet de contrôler la quantité maximale d'informations verbeuses que vous autoriserez le démon à générer (car les informations vont dans le fichier journal). La valeur par défaut est 1, ce qui permet au client de demander un niveau de verbosité.
Cela affecte également la capacité de l'utilisateur à demander des niveaux plus élevés de journalisation --info et --debug. Si la valeur maximale est 2, alors aucune valeur d'info et/ou de débogage supérieure à ce qui serait défini par -vv ne sera honorée par le démon dans sa journalisation. Pour voir jusqu'à quel niveau de verbosité vous devez accepter pour un niveau d'info/débogage particulier, référez-vous à rsync --info=help et rsync --debug=help. Par exemple, il faut un max-verbosity de 4 pour pouvoir afficher les débug TIME2 et FLIST3.
lock file
Ce paramètre spécifie le fichier à utiliser pour supporter le paramètre "max connections". Le démon rsync utilise le verrouillage d'enregistrement sur ce fichier pour garantir que la limite maximale de connexions n'est pas dépassée pour les modules partageant le fichier de verrouillage. La valeur par défaut est /var/run/rsyncd.lock.
read only
Ce paramètre détermine si les clients pourront télécharger des fichiers ou non. Si "read only" est vrai, toutes les tentatives de téléchargement échoueront. Si "read only" est faux, les téléchargements seront possibles si les permissions de fichiers côté démon les autorisent. La valeur par défaut est que tous les modules sont en lecture seule.
Notez que "auth users" peut outrepasser ce réglage par utilisateur.
write only
Ce paramètre détermine si les clients pourront télécharger des fichiers ou non. Si "write only" est vrai, toutes les tentatives de téléchargement échoueront. Si "write only" est faux, les téléchargements seront possibles si les permissions de fichiers côté démon les autorisent. La valeur par défaut est que ce paramètre est désactivé.
Astuce utile : vous voudrez probablement spécifier "refuse options = delete" pour un module en écriture seule.
open noatime
Lorsqu'il est défini sur True, ce paramètre indique au démon rsync d'ouvrir les fichiers avec le drapeau O_NOATIME (sur les systèmes qui le supportent) pour éviter de modifier le temps d'accès des fichiers transférés. Si votre OS ne supporte pas le drapeau O_NOATIME, rsync ignorera silencieusement cette option. Notez également que certains systèmes de fichiers sont montés pour éviter de mettre à jour l'atime lors de l'accès en lecture même sans que le drapeau O_NOATIME soit défini.
Lorsqu'il est défini sur False, ce paramètre garantit que les fichiers sur le serveur ne sont pas ouverts avec O_NOATIME.
Lorsqu'il est défini sur Non défini (par défaut), l'utilisateur contrôle le réglage via --open-noatime.
list
Ce paramètre détermine si ce module est listé lorsque le client demande une liste des modules disponibles. De plus, si c'est faux, le démon fera semblant que le module n'existe pas lorsqu'un client refusé par "hosts allow" ou "hosts deny" tente d'y accéder. Réalisez que si "reverse lookup" est désactivé globalement mais activé pour le module, la recherche inversée résultante vers un serveur DNS potentiellement contrôlé par le client peut toujours révéler au client qu'il a atteint un module existant. La valeur par défaut est que les modules sont listables.
uid
Ce paramètre spécifie le nom d'utilisateur ou l'ID utilisateur sous lequel les transferts de fichiers vers et depuis ce module doivent avoir lieu lorsque le démon est exécuté en tant que root. En combinaison avec le paramètre "gid", cela détermine quelles permissions de fichiers sont disponibles. La valeur par défaut lorsque exécuté par un super-utilisateur est de passer à l'utilisateur "nobody" du système. La valeur par défaut pour un non-super-utilisateur est de ne pas essayer de changer d'utilisateur. Voir aussi le paramètre "gid".
La variable d'environnement RSYNC_USER_NAME peut être utilisée pour demander que rsync s'exécute en tant qu'utilisateur autorisant. Par exemple, si vous voulez qu'un rsync s'exécute en tant que le même utilisateur reçu pour l'authentification rsync, cette configuration est utile :
uid = %RSYNC_USER_NAME%
gid = *
gid
Ce paramètre spécifie un ou plusieurs noms/ID de groupes qui seront utilisés lors de l'accès au module. Le premier sera le groupe par défaut, et les groupes supplémentaires seront définis comme groupes supplémentaires. Vous pouvez également spécifier un "*" comme premier gid dans la liste, qui sera remplacé par tous les groupes normaux pour l'utilisateur du transfert (voir "uid"). La valeur par défaut lorsque exécuté par un super-utilisateur est de passer au groupe "nobody" (ou peut-être "nogroup") de votre OS sans autres groupes supplémentaires. La valeur par défaut pour un non-super-utilisateur est de ne pas changer d'attributs de groupe (et en fait, votre OS peut ne pas permettre à un non-super-utilisateur d'essayer de changer ses paramètres de groupe).
La liste spécifiée est normalement divisée en jetons basés sur les espaces et les virgules. Cependant, si la liste commence par une virgule, alors la liste n'est divisée que par les virgules, ce qui permet à un nom de groupe de contenir un espace. Dans les deux cas, les espaces blancs de début et/ou de fin sont supprimés des jetons et les jetons vides sont ignorés.
daemon uid
Ce paramètre spécifie un uid sous lequel le démon s'exécutera. Le démon s'exécute généralement sous l'utilisateur root, et lorsque cela n'est pas défini, l'utilisateur n'est pas modifié. Voir aussi le paramètre "uid".
daemon gid
Ce paramètre spécifie un gid sous lequel le démon s'exécutera. Le démon s'exécute généralement sous le groupe root, et lorsque cela n'est pas défini, le groupe n'est pas modifié. Voir aussi le paramètre "gid".
fake super
Définir "fake super = yes" pour un module fait que le côté démon se comporte comme si l'option de ligne de commande --fake-super avait été spécifiée. Cela permet de stocker les attributs complets d'un fichier sans avoir le démon en cours d'exécution en tant que root.
filter
Le démon a sa propre chaîne de filtres qui détermine quels fichiers il autorise le client à accéder. Cette chaîne n'est pas envoyée au client et est indépendante de tout filtre que le client aurait pu spécifier. Les fichiers exclus par la chaîne de filtres du démon (fichiers daemon-excluded) sont traités comme inexistants si le client tente de les récupérer, sont ignorés avec un message d'erreur si le client tente de les envoyer (provoquant le code de sortie 23), et ne sont jamais supprimés du module. Vous pouvez
Utilisez les filtres de démon pour empêcher les clients de télécharger ou de falsifier des fichiers administratifs privés, tels que les fichiers que vous pourriez ajouter pour prendre en charge les traductions de noms uid/gid.
La chaîne de filtres de démon est construite à partir des paramètres "filter", "include from", "include", "exclude from", et "exclude", dans cet ordre de priorité. Les motifs ancrés sont ancrés à la racine du module. Pour empêcher l'accès à un sous-arbre entier, par exemple, "/secret", vous devez exclure tout dans le sous-arbre ; le moyen le plus simple de le faire est d'utiliser un motif étoile triple comme "/secret/***".
Le paramètre "filter" prend une liste de règles de filtre de démon séparées par des espaces, bien qu'il soit suffisamment intelligent pour savoir de ne pas diviser un jeton à un espace interne dans une règle (par exemple, "- /foo - /bar" est analysé comme deux règles). Vous pouvez spécifier une ou plusieurs règles de fichier de fusion en utilisant la syntaxe normale. Un seul paramètre "filter" peut s'appliquer à un module donné dans le fichier de configuration, alors mettez toutes les règles que vous souhaitez dans un seul paramètre. Notez que les règles de fichier de fusion par répertoire n'offrent pas autant de protection que les règles globales, mais elles peuvent être utilisées pour que --delete fonctionne mieux lors d'une opération de téléchargement client si les fichiers de fusion par répertoire sont inclus dans le transfert et que le client demande leur utilisation.
exclude
Ce paramètre prend une liste de motifs d'exclusion de démon séparés par des espaces. Comme avec l'option client --exclude, les motifs peuvent être qualifiés avec "- " ou "+ " pour indiquer explicitement l'exclusion/l'inclusion. Un seul paramètre "exclude" peut s'appliquer à un module donné. Voir le paramètre "filter" pour une description de la manière dont les fichiers exclus affectent le démon.
include
Utilisez un "include" pour remplacer les effets du paramètre "exclude". Un seul paramètre "include" peut s'appliquer à un module donné. Voir le paramètre "filter" pour une description de la manière dont les fichiers exclus affectent le démon.
exclude from
Ce paramètre spécifie le nom d'un fichier sur le démon qui contient des motifs d'exclusion de démon, un par ligne. Un seul paramètre "exclude from" peut s'appliquer à un module donné ; si vous avez plusieurs fichiers d'exclusion, vous pouvez les spécifier comme un fichier de fusion dans le paramètre "filter". Voir le paramètre "filter" pour une description de la manière dont les fichiers exclus affectent le démon.
include from
Analogue de "exclude from" pour un fichier de motifs d'inclusion de démon. Un seul paramètre "include from" peut s'appliquer à un module donné. Voir le paramètre "filter" pour une description de la manière dont les fichiers exclus affectent le démon.
incoming chmod
Ce paramètre vous permet de spécifier un ensemble de chaînes chmod séparées par des virgules qui affecteront les permissions de tous les fichiers entrants (fichiers reçus par le démon). Ces modifications interviennent après tous les autres calculs de permissions, et cela remplacera même les permissions par défaut de destination et/ou existantes lorsque le client ne spécifie pas --perms. Voir la description de l'option rsync --chmod et la page de manuel chmod(1) pour des informations sur le format de cette chaîne.
outgoing chmod
Ce paramètre vous permet de spécifier un ensemble de chaînes chmod séparées par des virgules qui affecteront les permissions de tous les fichiers sortants (fichiers envoyés depuis le démon). Ces modifications interviennent en premier, donnant l'impression que les permissions envoyées sont différentes de celles stockées dans le système de fichiers lui-même. Par exemple, vous pourriez désactiver les permissions d'écriture du groupe sur le serveur tout en donnant l'impression qu'elles sont activées pour les clients. Voir la description de l'option rsync --chmod et la page de manuel chmod(1) pour des informations sur le format de cette chaîne.
auth users
Ce paramètre spécifie une liste de règles d'autorisation séparées par des virgules et/ou des espaces. Dans sa forme la plus simple, vous listez les noms d'utilisateur qui seront autorisés à se connecter à ce module. Les noms d'utilisateur n'ont pas besoin d'exister sur le système local. Les règles peuvent contenir des caractères génériques de shell qui seront mis en correspondance avec le nom d'utilisateur fourni par le client pour l'authentification. Si "auth users" est défini, le client sera invité à fournir un nom d'utilisateur et un mot de passe pour se connecter au module. Un protocole d'authentification par réponse au défi est utilisé pour cet échange. Les noms d'utilisateur et mots de passe en texte clair sont stockés dans le fichier spécifié par le paramètre "secrets file". Par défaut, tous les utilisateurs peuvent se connecter sans mot de passe (ceci est appelé "rsync anonyme").
En plus de la correspondance des noms d'utilisateur, vous pouvez spécifier la correspondance des noms de groupe via un préfixe '@'. Lors de l'utilisation de la correspondance des noms de groupe, le nom d'utilisateur authentifiant doit être un utilisateur réel sur le système, sinon il sera supposé appartenir à aucun groupe. Par exemple, spécifier "@rsync" correspondra à l'utilisateur authentifiant si l'utilisateur nommé est membre du groupe rsync.
Enfin, des options peuvent être spécifiées après un deux-points (:). Les options vous permettent de "refuser" un utilisateur ou un groupe, de définir l'accès sur "ro" (lecture seule), ou de définir l'accès sur "rw" (lecture/écriture). La définition d'un paramètre ro/rw spécifique à une règle d'autorisation remplace le paramètre "read only" du module.
Assurez-vous de placer les règles dans l'ordre dans lequel vous souhaitez qu'elles soient mises en correspondance, car la vérification s'arrête au premier utilisateur ou groupe correspondant, et c'est la seule authentification qui est vérifiée. Par exemple :
auth users = joe:deny @guest:deny admin:rw @rsync:ro susan joe sam
Dans la règle ci-dessus, l'utilisateur joe sera refusé, quel que soit le cas. Tout utilisateur membre du groupe "guest" sera également refusé. L'utilisateur "admin" obtient l'accès en mode lecture/écriture, mais seulement si l'utilisateur admin ne fait pas partie du groupe "guest" (car la règle de correspondance de l'utilisateur admin ne serait jamais atteinte si l'utilisateur fait partie du groupe "guest"). Tout autre utilisateur membre du groupe "rsync" obtiendra un accès en lecture seule. Enfin, les utilisateurs susan, joe et sam obtiennent le réglage ro/rw du module, mais seulement si l'utilisateur n'a pas correspondu à une règle de groupe antérieure.
Si vous devez spécifier un nom d'utilisateur ou de groupe contenant un espace, commencez votre liste par une virgule pour indiquer que la liste ne doit être divisée que par des virgules (bien que les espaces en début et fin de chaîne soient également supprimés, et que les entrées vides soient simplement ignorées). Par exemple :
auth users = , joe:deny, @Some Group:deny, admin:rw, @RO Group:ro
Voir la description du fichier secrets pour savoir comment avoir des mots de passe par utilisateur ainsi que des mots de passe par groupe. Il explique également comment un utilisateur peut s'authentifier en utilisant son mot de passe utilisateur ou (lorsque applicable) un mot de passe de groupe, en fonction de la règle qui est authentifiée.
Voir aussi la section intitulée "USING RSYNC-DAEMON FEATURES VIA A REMOTE SHELL CONNECTION" dans rsync(1) pour des informations sur la manière de gérer un nom d'utilisateur au niveau rsyncd.conf différent du nom d'utilisateur au niveau shell distant lors de l'utilisation d'un shell distant pour se connecter à un démon rsync.
secrets file
Ce paramètre spécifie le nom d'un fichier contenant les paires username:password et/ou @groupname:password utilisées pour authentifier ce module. Ce fichier n'est consulté que si le paramètre "auth users" est spécifié. Le fichier est basé sur des lignes et contient une paire name:password par ligne. Toute ligne commençant par un dièse (#) comme premier caractère est considérée comme un commentaire et est ignorée. Les mots de passe peuvent contenir n'importe quels caractères, mais attention, de nombreux systèmes d'exploitation limitent la longueur des mots de passe qui peuvent être saisis côté client, vous pourriez donc constater que les mots de passe de plus de 8 caractères ne fonctionnent pas.
L'utilisation de lignes spécifiques aux groupes n'est pertinente que lorsque le module est autorisé à l'aide d'une règle correspondante "@groupname". Lorsque cela se produit, l'utilisateur peut être autorisé via sa ligne "username:password" ou la ligne "@groupname:password" pour le groupe qui a déclenché l'authentification.
Il vous appartient de décider quels types d'entrées de mot de passe inclure, soit des utilisateurs, des groupes, soit les deux. L'utilisation de règles de groupe dans "auth users" ne nécessite pas que vous spécifiiez un mot de passe de groupe si vous ne souhaitez pas utiliser de mots de passe partagés.
Il n'y a pas de valeur par défaut pour le paramètre "secrets file", vous devez choisir un nom (tel que /etc/rsyncd.secrets). Le fichier ne doit normalement pas être lisible par "autres" ; voir "strict modes". Si le fichier n'est pas trouvé ou est rejeté, aucune connexion pour un module "auth users" ne sera possible.
strict modes
Ce paramètre détermine si les permissions du fichier secrets sont vérifiées ou non. Si "strict modes" est vrai, alors le fichier secrets ne doit être lisible par aucun ID utilisateur autre que celui sous lequel le démon rsync s'exécute. Si "strict modes" est faux, la vérification n'est pas effectuée. La valeur par défaut est vraie. Ce paramètre a été ajouté pour prendre en charge rsync s'exécutant sous le système d'exploitation Windows.
hosts allow
Ce paramètre vous permet de spécifier une liste de motifs séparés par des virgules et/ou des espaces qui sont mis en correspondance avec le nom d'hôte et l'adresse IP d'un client connecté. Si aucun des motifs ne correspond, la connexion est rejetée.
Chaque motif peut prendre l'une des six formes suivantes :
o
une adresse IPv4 décimale pointée de la forme a.b.c.d, ou une adresse IPv6 de la forme a:b:c::d:e:f. Dans ce cas, l'adresse IP de la machine entrante doit correspondre exactement.
o
une adresse/masque de la forme ipaddr/n où ipaddr est l'adresse IP et n est le nombre de bits à 1 dans le masque réseau. Toutes les adresses IP qui correspondent à l'adresse IP masquée seront autorisées.
o
une adresse/masque de la forme
le format ipaddr/maskaddr où ipaddr est l'adresse IP et maskaddr est le masque de réseau en notation décimale pointée pour IPv4, ou similaire pour IPv6, par exemple ffff:ffff:ffff:ffff:: au lieu de /64. Toutes les adresses IP qui correspondent à l'adresse IP masquée seront autorisées.
o
un modèle de nom d'hôte utilisant des caractères génériques. Si le nom d'hôte de l'IP de connexion (tel que déterminé par une recherche inversée) correspond au nom avec caractères génériques (en utilisant les mêmes règles que la correspondance de nom de fichier Unix normale), le client est autorisé. Cela ne fonctionne que si la "recherche inversée" est activée (par défaut).
o
un nom d'hôte. Un nom d'hôte simple est mis en correspondance avec le DNS inversé de l'IP de connexion (si la "recherche inversée" est activée), et/ou l'IP du nom d'hôte donné est mis en correspondance avec l'IP de connexion (si la "recherche directe" est activée, comme c'est le cas par défaut). Toute correspondance sera autorisée.
o
un '@' suivi d'un nom de groupe de réseau (netgroup), qui correspondra si le DNS inversé de l'IP de connexion se trouve dans le groupe de réseau spécifié.
Notez que les adresses link-local IPv6 peuvent avoir une portée dans la spécification de l'adresse :
fe80::1%link1
fe80::%link1/64
fe80::%link1/ffff:ffff:ffff:ffff::
Vous pouvez également combiner "hosts allow" avec "hosts deny" comme moyen d'ajouter des exceptions à votre liste de refus. Lorsque les deux paramètres sont spécifiés, le paramètre "hosts allow" est vérifié en premier et une correspondance permet au client de se connecter. Un hôte non autorisé est ensuite mis en correspondance avec la liste "hosts deny" pour voir s'il doit être rejeté. Un hôte qui ne correspond à aucune des deux listes est autorisé à se connecter.
Par défaut, aucun paramètre "hosts allow" n'est spécifié, ce qui signifie que tous les hôtes peuvent se connecter.
hosts deny
Ce paramètre vous permet de spécifier une liste de modèles séparés par des virgules et/ou des espaces qui sont mis en correspondance avec le nom d'hôte et l'adresse IP d'un client connectant. Si le modèle correspond, la connexion est rejetée. Voir le paramètre "hosts allow" pour plus d'informations.
Par défaut, aucun paramètre "hosts deny" n'est spécifié, ce qui signifie que tous les hôtes peuvent se connecter.
reverse lookup
Contrôle si le démon effectue une recherche inversée sur l'adresse IP du client pour déterminer son nom d'hôte, qui est utilisé pour les vérifications "hosts allow" et "hosts deny" ainsi que pour le code de journalisation "%h". Ceci est activé par défaut, mais vous pourriez vouloir le désactiver pour gagner du temps si vous savez que la recherche ne retournera pas de résultat utile, auquel cas le démon utilisera le nom "UNDETERMINED" à la place.
Si ce paramètre est activé globalement (même par défaut), rsync effectue la recherche dès qu'un client se connecte, donc le désactiver pour un module n'évitera pas la recherche. Par conséquent, vous voudrez probablement le désactiver globalement, puis l'activer pour les modules qui ont besoin de l'information.
forward lookup
Contrôle si le démon effectue une recherche directe sur tout nom d'hôte spécifié dans un réglage hosts allow/deny. Par défaut, cela est activé, permettant l'utilisation d'un nom d'hôte explicite qui ne serait pas retourné par le DNS inversé de l'IP de connexion.
ignore errors
Ce paramètre indique à rsyncd d'ignorer les erreurs d'E/S sur le démon lors de la décision d'exécuter la phase de suppression du transfert. Normalement, rsync saute l'étape --delete si des erreurs d'E/S se sont produites afin d'éviter des suppressions désastreuses dues à une pénurie temporaire de ressources ou à une autre erreur d'E/S. Dans certains cas, ce test est contre-productif, vous pouvez donc utiliser ce paramètre pour désactiver ce comportement.
ignore nonreadable
Ceci indique au démon rsync d'ignorer complètement les fichiers qui ne sont pas lisibles par l'utilisateur. Ceci est utile pour les archives publiques qui peuvent avoir des fichiers non lisibles parmi les répertoires, et l'administrateur système ne veut pas que ces fichiers soient vus du tout.
transfer logging
Ce paramètre active la journalisation par fichier des téléchargements et des téléversements dans un format quelque peu similaire à celui utilisé par les démons ftp. Le démon journalise toujours le transfert à la fin, donc si un transfert est interrompu, aucune mention ne sera faite dans le fichier journal.
Si vous souhaitez personnaliser les lignes de journalisation, consultez le paramètre "log format".
log format
Ce paramètre vous permet de spécifier le format utilisé pour la journalisation des transferts de fichiers lorsque la journalisation des transferts est activée. Le format est une chaîne de texte contenant des séquences d'échappement à un seul caractère intégrées, précédées d'un signe pourcentage (%). Une largeur de champ numérique facultative peut également être spécifiée entre le signe pourcentage et la lettre d'échappement (par exemple, "%-50n %8l %07p"). En outre, un ou plusieurs apostrophes peuvent être spécifiés avant une séquence d'échappement numérique pour indiquer que la valeur numérique doit être rendue plus lisible par l'homme. Les 3 niveaux pris en charge sont les mêmes que pour l'option de ligne de commande --human-readable, bien que par défaut la lisibilité par l'homme soit désactivée. Chaque apostrophe ajoutée augmente le niveau (par exemple, "%''l %'b %f").
Le format de journalisation par défaut est "%o %h [%a] %m (%u) %f %l", et un "%t [%p] " est toujours préfixé lors de l'utilisation du paramètre "log file". (Un script Perl qui résume ce format de journal par défaut est inclus dans la distribution source de rsync dans le sous-répertoire "support" : rsyncstats.)
Les séquences d'échappement à un seul caractère comprises sont les suivantes :
o
%a l'adresse IP distante (uniquement disponible pour un démon)
o
%b le nombre d'octets réellement transférés
o
%B les bits d'autorisation du fichier (par exemple, rwxrwxrwt)
o
%c la taille totale des sommes de contrôle de blocs reçues pour le fichier de base (uniquement lors de l'envoi)
o
%C la somme de contrôle du fichier complet si elle est connue pour le fichier. Pour les anciens protocoles/versions rsync, la somme de contrôle était salée, et n'est donc pas une valeur utile (et n'est pas affichée lorsque c'est le cas). Pour que la somme de contrôle soit affichée pour un fichier, soit l'option --checksum doit être activée, soit le fichier doit avoir été transféré sans utilisation d'une somme de contrôle salée. Voir l'option --checksum-choice pour choisir l'algorithme.
o
%f le nom du fichier (forme longue pour l'expéditeur ; pas de "/" à la fin)
o
%G le gid du fichier (décimal) ou "DEFAULT"
o
%h le nom d'hôte distant (uniquement disponible pour un démon)
o
%i une liste itemisée de ce qui est mis à jour
o
%l la longueur du fichier en octets
o
%L la chaîne " => SYMLINK", " = HARDLINK", ou "" (où SYMLINK ou HARDLINK est un nom de fichier)
o
%m le nom du module
o
%M l'heure de dernière modification du fichier
o
%n le nom du fichier (forme courte ; "/" à la fin pour les répertoires)
o
%o l'opération, qui est "send", "recv", ou "del." (cette dernière inclut le point final)
o
%p l'identifiant du processus de cette session rsync
o
%P le chemin du module
o
%t la date et l'heure actuelles
o
%u le nom d'utilisateur authentifié ou une chaîne vide
o
%U le uid du fichier (décimal)
Pour une liste de ce que signifient les caractères produits par "%i", consultez l'option --itemize-changes dans le manuel rsync.
Notez que certaines des sorties de journalisation changent lors de la communication avec d'anciennes versions de rsync. Par exemple, les fichiers supprimés n'étaient signalés que par des messages verbaux avant rsync 2.6.4.
timeout
Ce paramètre vous permet de remplacer le choix du client pour le délai d'attente d'E/S pour ce module. En utilisant ce paramètre, vous pouvez vous assurer que rsync n'attendra pas indéfiniment un client mort. Le délai d'attente est spécifié en secondes. Une valeur de zéro signifie pas de délai d'attente et est la valeur par défaut. Une bonne valeur pour les démons rsync anonymes pourrait être 600 (ce qui donne un délai de 10 minutes).
refuse options
Ce paramètre vous permet de spécifier une liste d'options de ligne de commande rsync séparées par des espaces qui seront refusées par votre démon rsync. Vous pouvez spécifier le nom complet de l'option, son abréviation à une lettre, ou une chaîne de caractères génériques qui correspond à plusieurs options. À partir de la version 3.2.0, vous pouvez également nier un terme correspondant en commençant par un "!".
Lorsqu'une option est refusée, le démon affiche un message d'erreur et se termine.
Par exemple, ceci refuserait --checksum (-c) et toutes les options de suppression diverses :
refuse options = c delete
La raison pour laquelle ce qui précède refuse toutes les options de suppression est que les options impliquent --delete, et les options implicites sont refusées tout comme les options explicites.
L'utilisation d'une correspondance niée permet d'affiner vos refus après une chaîne de caractères génériques, comme ceci :
refuse options = delete-* !delete-during
La correspondance négative peut également transformer votre liste d'options refusées en une liste d'options acceptées. Pour ce faire, commencez la liste par un « * » (pour refuser toutes les options) puis spécifiez une ou plusieurs correspondances négatives pour accepter. Par exemple :
refuser options = * !a !v !compress*
Ne vous inquiétez pas que le « * » refuse certaines options vitales telles que --dry-run, --server, --no-iconv, --seclude-args, etc. Ces options importantes ne sont pas mises en correspondance par un caractère générique, elles doivent donc être remplacées par leur nom exact. Par exemple, si vous forcez les transferts iconv, vous pourriez utiliser quelque chose comme ceci :
refuser options = * no-iconv !a !v
Comme aide supplémentaire (à partir de la version 3.2.0), refuser (ou « !refuser ») l'option « a » ou « archive » affecte également toutes les options que l'option --archive implique (-rdlptgoD), mais uniquement si l'option est explicitement mise en correspondance (pas en utilisant un caractère générique). Si vous voulez faire quelque chose de subtil, vous pouvez utiliser « archive* » pour éviter cet effet secondaire, mais gardez à l'esprit qu'aucun client rsync normal n'envoie jamais l'option archive réelle au serveur.
Comme mesure de sécurité supplémentaire, le refus de « delete » refuse également remove-source-files lorsque le démon est l'expéditeur ; si vous souhaitez ce dernier sans le premier, refusez plutôt « delete-* » car cela refuse tous les modes de suppression sans affecter --remove-source-files. (Gardez à l'esprit que l'option --delete du client aboutit généralement à --delete-during.)
Lors de la ré-acceptation des options de suppression, vous devriez soit spécifier « !delete* » (pour accepter toutes les options de suppression), soit spécifier un ensemble limité qui inclut « delete », comme suit :
refuser options = * !a !delete !delete-during
... alors que ceci accepte toute option de suppression sauf --delete-after :
refuser options = * !a !delete* delete-after
Une note sur le refus de « compress » : il peut être préférable de définir le paramètre du démon « dont compress » sur « * » et de s'assurer que RSYNC_COMPRESS_LIST=zlib est défini dans l'environnement du démon afin de désactiver la compression silencieusement au lieu de renvoyer une erreur qui oblige le client à supprimer l'option -z.
Si vous ré-acceptez l'option compress, vous voudrez peut-être faire correspondre « !compress* » si vous souhaitez également autoriser l'option --compress-level.
Notez que les options « copy-devices » et « write-devices » sont refusées par défaut, mais elles peuvent être explicitement acceptées avec « !copy-devices » et/ou « !write-devices ». Les options « log-file » et « log-file-format » sont refusées de force et ne peuvent pas être acceptées.
Voici toutes les options qui ne sont pas mises en correspondance par des caractères génériques :
o
--server : Requis pour que rsync fonctionne.
o
--rsh, -e : Requis pour transmettre les indicateurs de compatibilité au serveur.
o
--out-format : Nécessaire pour transmettre le comportement de sortie à un récepteur distant. Bien que rsync transmette l'ancien alias --log-format pour des raisons de compatibilité, ces options ne doivent pas être confondues avec --log-file-format.
o
--sender : Utilisez le paramètre « écriture seule » au lieu de refuser celui-ci.
o
--dry-run, -n : Qui voudrait désactiver cela ?
o
--seclude-args, -s : C'est la plus ancienne méthode de protection des arguments.
o
--from0, -0 : Facilite l'acceptation/le refus de --files-from sans affecter ce modificateur utile.
o
--iconv : Ceci est automatiquement désactivé sur la base du paramètre « charset ».
o
--no-iconv : La plupart des transferts utilisent cette option.
o
--checksum-seed : C'est une option assez rare et sûre.
o
--write-devices : N'est pas un caractère générique mais est également désactivé automatiquement.
ne compresse pas
NOTE : Ce paramètre n'a actuellement aucun effet sauf dans un cas : s'il est défini sur « * », il minimise ou désactive la compression pour tous les fichiers (pour ceux qui ne veulent pas refuser complètement l'option --compress).
Ce paramètre vous permet de sélectionner des noms de fichiers basés sur des modèles de caractères génériques qui ne doivent pas être compressés lors de la récupération de fichiers depuis le démon (aucun paramètre analogue n'existe pour régir la poussée de fichiers vers un démon). La compression peut être coûteuse en termes d'utilisation du processeur, il est donc généralement bon de ne pas essayer de compresser des fichiers qui ne se compressent pas bien, comme des fichiers déjà compressés.
Le paramètre « ne compresse pas » prend une liste de modèles de caractères génériques séparés par des espaces et insensibles à la casse. Tout nom de fichier source correspondant à l'un des modèles sera compressé le moins possible pendant le transfert. Si l'algorithme de compression a un niveau « désactivé », aucune compression ne se produit pour ces fichiers. Si un algorithme a la capacité de changer le niveau en cours de flux, il sera minimisé pour réduire l'utilisation du processeur autant que possible.
Consultez le paramètre --skip-compress dans la page de manuel de rsync(1) pour la liste des suffixes de fichiers qui sont ignorés par défaut si ce paramètre n'est pas défini.
exéc tôt, exéc pre-xfer, exéc post-xfer
Vous pouvez spécifier une commande à exécuter dans les premières étapes de la connexion, ou juste avant et/ou après le transfert. Si la commande early exec ou pre-xfer exec renvoie un code d'erreur, le transfert est annulé avant de commencer. Toute sortie de la commande pre-xfer exec sur la sortie standard (jusqu'à plusieurs Ko) sera affichée à l'utilisateur lors de l'annulation, mais n'est pas affichée si le script renvoie un succès. Les autres programmes ne peuvent pas envoyer de texte à l'utilisateur. Toute sortie, à l'exception de la sortie standard de pre-xfer exec, va à la sortie standard/erreur du démon correspondant, qui est généralement ignorée. Consultez l'option --no-detach pour voir la sortie du démon, ce qui peut aider au débogage.
Notez que la commande early exec s'exécute avant que toute partie de la requête de transfert ne soit connue, à l'exception du nom du module. Ce script d'assistance peut être utilisé pour configurer un montage de disque ou décrypter des données dans un répertoire de module, mais vous pourriez avoir besoin d'utiliser lock file et max connections pour éviter les problèmes de concurrence. Si le client rsync a spécifié l'option --early-input=FICHIER, il peut envoyer jusqu'à environ 5 Ko de données à l'entrée standard du script précoce. L'entrée standard sera sinon vide.
Notez que la commande post-xfer exec est toujours exécutée même si l'un des autres scripts renvoie un code d'erreur. La commande pre-xfer exec ne sera cependant pas exécutée si la commande early exec échoue.
Les variables d'environnement suivantes seront définies, bien que certaines soient spécifiques à l'environnement pré-xfer ou post-xfer :
o
RSYNC_MODULE_NAME : Le nom du module accédé.
o
RSYNC_MODULE_PATH : Le chemin configuré pour le module.
o
RSYNC_HOST_ADDR : L'adresse IP de l'hôte accédant.
o
RSYNC_HOST_NAME : Le nom de l'hôte accédant.
o
RSYNC_USER_NAME : Le nom de l'utilisateur accédant (vide s'il n'y a pas d'utilisateur).
o
RSYNC_PID : Un numéro unique pour ce transfert.
o
RSYNC_REQUEST : (pré-xfer seulement) Les informations du module/chemin spécifiées par l'utilisateur. Notez que l'utilisateur peut spécifier plusieurs fichiers source, la requête peut donc être quelque chose comme « mod/chemin1 mod/chemin2 », etc.
o
RSYNC_ARG# : (pré-xfer seulement) Les arguments pré-requête sont définis dans ces valeurs numérotées. RSYNC_ARG0 est toujours « rsync », suivi des options utilisées dans RSYNC_ARG1, et ainsi de suite. Il y aura une valeur de « . » indiquant que les options sont terminées et que les arguments de chemin commencent -- ceux-ci contiennent des informations similaires à RSYNC_REQUEST, mais avec des valeurs séparées et le nom du module retiré.
o
RSYNC_EXIT_STATUS : (post-xfer seulement) La valeur de sortie du côté serveur. Ce sera 0 pour une exécution réussie, une valeur positive pour une erreur générée par le serveur, ou -1 si rsync n'a pas réussi à se terminer correctement. Notez qu'une erreur survenant côté client n'est actuellement pas envoyée côté serveur, ce n'est donc pas le statut de sortie final pour l'ensemble du transfert.
o
RSYNC_RAW_STATUS : (post-xfer seulement) La valeur de sortie brute de waitpid().
Même si les commandes peuvent être associées à un module particulier, elles sont exécutées en utilisant les permissions de l'utilisateur qui a démarré le démon (et non le paramètre uid/gid du module) sans aucune restriction de chroot.
Ces paramètres respectent 2 variables d'environnement : utilisez RSYNC_SHELL pour définir un shell à utiliser lors de l'exécution de la commande (qui utilise sinon le shell par défaut de votre appel system()), et utilisez RSYNC_NO_XFER_EXEC pour désactiver complètement les deux options.

DIRECTIVES DE CONFIGURATION

Il existe actuellement deux directives de configuration qui permettent à un fichier de configuration d'incorporer le contenu d'autres fichiers : &include et &merge. Les deux permettent une référence à un fichier ou à un répertoire. Ils diffèrent dans la manière dont le contenu du fichier est considéré comme étant séparé.

La directive &include traite chaque fichier comme plus distinct, chacun héritant des valeurs par défaut du fichier parent, en commençant l'analyse des paramètres comme globaux/par défaut, et en laissant les valeurs par défaut inchangées pour l'analyse du reste du fichier parent.

La directive &merge, en revanche, traite le contenu du fichier comme s'il était simplement inséré à la place de la directive, et peut donc définir des paramètres dans un module démarré dans un autre fichier, affecter les valeurs par défaut pour d'autres fichiers, etc.

Lorsqu'une directive &include ou &merge fait référence à un répertoire, elle lira tous les fichiers *.conf ou *.inc (respectivement) contenus dans ce répertoire (sans analyse récursive), les fichiers étant triés par ordre alphabétique. Ainsi, si vous avez un répertoire nommé "rsyncd.d" avec les fichiers "foo.conf", "bar.conf", et "baz.conf" à l'intérieur, cette directive :

&include /chemin/rsyncd.d

serait équivalente à cet ensemble de directives :

&include /chemin/rsyncd.d/bar.conf
&include /chemin/rsyncd.d/baz.conf
&include /chemin/rsyncd.d/foo.conf

sauf qu'elle s'ajuste à mesure que des fichiers sont ajoutés et supprimés du répertoire.

L'avantage de la directive &include est que vous pouvez définir un ou plusieurs modules dans un fichier séparé sans vous soucier des effets secondaires involontaires entre les fichiers de module autonomes.

L'avantage de la directive &merge est que vous pouvez charger des extraits de configuration qui peuvent être inclus dans plusieurs définitions de module, et vous pouvez également définir des valeurs globales qui affecteront les connexions (telles que motd file), ou des globales qui affecteront d'autres fichiers d'inclusion.

Par exemple, voici un fichier /etc/rsyncd.conf utile :

port = 873
log file = /var/log/rsync.log
pid file = /var/lock/rsync.lock
&merge /etc/rsyncd.d
&include /etc/rsyncd.d

Cela fusionnerait tous les fichiers /etc/rsyncd.d/*.inc (pour les valeurs globales qui doivent rester en vigueur), puis inclurait tous les fichiers /etc/rsyncd.d/*.conf (définissant des modules sans aucune interférence de valeurs globales).

FORCE DE L'AUTHENTIFICATION

Le protocole d'authentification utilisé dans rsync est un système de défi-réponse basé sur MD4 sur 128 bits. C'est une protection assez faible, cependant (avec au moins un algorithme de recherche de hachage par force brute publiquement disponible), donc si vous voulez une sécurité de très haute qualité, je vous recommande d'exécuter rsync sur ssh. (Oui, une future version de rsync passera à une méthode de hachage plus forte.)

Notez également que le protocole du démon rsync ne fournit actuellement aucun chiffrement des données transférées sur la connexion. Seule l'authentification est fournie. Utilisez ssh comme transport si vous voulez du chiffrement.

Vous pouvez également utiliser le chiffrement SSL/TLS si vous placez rsync derrière un proxy SSL.

CONFIGURATION DU DÉMON SSL/TLS

Lors de la configuration d'un démon rsync pour un accès via SSL/TLS, vous devrez configurer un proxy TCP (tel que haproxy ou nginx) comme façade qui gère le chiffrement.

o
Vous devriez limiter l'accès au port rsync backend pour ne permettre que au proxy de se connecter. S'il est sur le même hôte que le proxy, le configurer pour qu'il n'écoute que sur localhost est une bonne idée.
o
Vous devriez envisager d'activer le paramètre du démon rsync proxy protocol si votre proxy prend en charge l'envoi de ces informations. Les exemples ci-dessous supposent que cela est activé.

Un exemple de configuration haproxy est le suivant :

frontend fe_rsync-ssl
   bind :::874 ssl crt /etc/letsencrypt/example.com/combined.pem
   mode tcp
   use_backend be_rsync
backend be_rsync
   mode tcp
   server local-rsync 127.0.0.1:873 check send-proxy

Un exemple de configuration de proxy nginx est le suivant :

stream {
   server {
       listen 874 ssl;
       listen [::]:874 ssl;
       ssl_certificate /etc/letsencrypt/example.com/fullchain.pem;
       ssl_certificate_key /etc/letsencrypt/example.com/privkey.pem;
       proxy_pass localhost:873;
       proxy_protocol on; # Nécessite dans rsyncd.conf "proxy protocol = true"
       proxy_timeout 1m;
       proxy_connect_timeout 5s;
   }
}

Si rsyncd doit être accessible chiffré et non chiffré en même temps, faites écouter le proxy sur le port 873 également et laissez-le gérer les deux flux.

EXEMPLES DE CONFIGURATION DU DÉMON

Un fichier rsyncd.conf simple qui autorise le rsync anonyme vers une zone ftp à /home/ftp serait :

[ftp]
        path = /home/ftp
        comment = zone d'exportation ftp

Un exemple plus sophistiqué serait :

uid = nobody
gid = nobody
use chroot = yes
max connections = 4
syslog facility = local5
pid file = /var/run/rsyncd.pid
[ftp]
        path = /var/ftp/./pub
        comment = zone ftp entière (environ 6,1 Go)
[sambaftp]
        path = /var/ftp/./pub/samba
        comment = zone ftp Samba (environ 300 Mo)
[rsyncftp]
        path = /var/ftp/./pub/rsync
        comment = zone ftp rsync (environ 6 Mo)
[sambawww]
        path = /public_html/samba
        comment = pages web Samba (environ 240 Mo)
[cvs]
        path = /data/cvs
        comment = dépôt CVS (nécessite une authentification)
        auth users = tridge, susan
        secrets file = /etc/rsyncd.secrets

Le fichier /etc/rsyncd.secrets ressemblerait à ceci :

tridge:mypass
susan:herpass
