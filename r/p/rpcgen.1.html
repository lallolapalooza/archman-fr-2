rpcgen(1) Manuel des commandes générales rpcgen(1)

NOM

rpcgen - compilateur de protocoles RPC

SYNOPIS

rpcgen infile
rpcgen [-Dname[=value]] [-T] [-K secs] infile
rpcgen -c|-h|-l|-m|-M|-t [-o outfile ] infile
rpcgen -s nettype [-o outfile] infile
rpcgen -n netid [-o outfile] infile

DESCRIPTION

rpcgen est un outil qui génère du code C pour implémenter un protocole RPC. L'entrée de rpcgen est un langage similaire au C, connu sous le nom de Langage RPC (Langage d'Appel de Procédure Distante).

rpcgen est normalement utilisé comme dans la première synopsie, où il prend un fichier d'entrée et génère jusqu'à quatre fichiers de sortie. Si le fichier d'entrée s'appelle proto.x, alors rpcgen générera un fichier d'en-tête dans proto.h, les routines XDR dans proto_xdr.c, les "stubs" côté serveur dans proto_svc.c, et les "stubs" côté client dans proto_clnt.c. Avec l'option -T, il générera également la table de dispatch RPC dans proto_tbl.i. Avec l'option -Sc, il générera également un code d'exemple qui illustrera comment utiliser les procédures distantes côté client. Ce code serait créé dans proto_client.c. Avec l'option -Ss, il générera également un exemple de code serveur qui illustrera comment écrire les procédures distantes. Ce code serait créé dans proto_server.c.

Le serveur créé peut être démarré à la fois par les moniteurs de ports (par exemple, inetd ou listen) ou par lui-même. Lorsqu'il est démarré par un moniteur de ports, il crée des serveurs uniquement pour le transport pour lequel le descripteur de fichier 0 a été passé. Le nom du transport doit être spécifié en configurant la variable d'environnement PM_TRANSPORT. Lorsque le serveur généré par rpcgen est exécuté, il crée des "handles" de serveur pour tous les transports spécifiés dans la variable d'environnement NETPATH, ou s'il est non défini, il crée des "handles" de serveur pour tous les transports visibles du fichier /etc/netconfig. Note: les transports sont choisis à l'exécution et non à la compilation.

Lorsqu'il est compilé pour un moniteur de ports (rpcgen -I), et que le serveur est auto-démarré, il se met en arrière-plan par défaut. Un symbole de définition spécial RPC_SVC_FG peut être utilisé pour exécuter le processus serveur au premier plan.

La deuxième synopsie fournit des fonctionnalités spéciales qui permettent la création de serveurs RPC plus sophistiqués. Ces fonctionnalités incluent le support des #defines fournis par l'utilisateur et des tables de dispatch RPC. Les entrées de la table de dispatch RPC contiennent :

•
des pointeurs vers la routine de service correspondant à cette procédure,
•
un pointeur vers les arguments d'entrée et de sortie
•
la taille de ces routines
Un serveur peut utiliser la table de dispatch pour vérifier l'autorisation puis exécuter la routine de service ; une bibliothèque cliente peut l'utiliser pour gérer les détails de gestion de la mémoire et la conversion des données XDR.

Les trois autres synopsies présentées ci-dessus sont utilisées lorsqu'on ne souhaite pas générer tous les fichiers de sortie, mais seulement un fichier particulier. Quelques exemples de leur utilisation sont décrits dans la section EXEMPLE ci-dessous. Lorsque rpcgen est exécuté avec l'option -s, il crée des serveurs pour cette classe particulière de transports. Lorsqu'il est exécuté avec l'option -n, il crée un serveur pour le transport spécifié par netid. Si infile n'est pas spécifié, rpcgen accepte l'entrée standard.

Le préprocesseur C, cc -E [voir cc(1)], est exécuté sur le fichier d'entrée avant qu'il ne soit réellement interprété par rpcgen. Pour chaque type de fichier de sortie, rpcgen définit un symbole de préprocesseur spécial à utiliser par le programmeur rpcgen :

RPC_HDR
défini lors de la compilation en fichiers d'en-tête
RPC_XDR
défini lors de la compilation en routines XDR
RPC_SVC
défini lors de la compilation en "stubs" côté serveur
RPC_CLNT
défini lors de la compilation en "stubs" côté client
RPC_TBL
défini lors de la compilation en tables de dispatch RPC

Toute ligne commençant par `%' est transmise directement dans le fichier de sortie, non interprétée par rpcgen.

Pour chaque type de données référencé dans infile, rpcgen suppose qu'il existe une routine avec la chaîne xdr_ préfixée au nom du type de données. Si cette routine n'existe pas dans la bibliothèque RPC/XDR, elle doit être fournie. La fourniture d'un type de données non défini permet la personnalisation des routines XDR.

Les options suivantes sont disponibles :

-a
Génère tous les fichiers, y compris le code d'exemple pour le client et le serveur.
-b
Génère du code pour le style rpc de SunOS4.1. C'est pour la compatibilité ascendante. C'est la valeur par défaut.
-5
Génère du code pour le style rpc de SysVr4. Il est utilisé par le RPC indépendant du transport qui se trouve dans les systèmes Svr4. Par défaut, rpcgen génère du code pour le style rpc de SunOS4.1.
-c
Compile en routines XDR.
-C
Génère du code en ANSI C. Cette option génère également du code qui pourrait être compilé avec le compilateur C++. C'est la valeur par défaut.
-k
Génère du code en K&R C. La valeur par défaut est ANSI C.
-Dname[=value]
Définit un symbole name. Équivalent à la directive #define dans la source. Si aucune value n'est donnée, value est définie comme 1. Cette option peut être spécifiée plus d'une fois.
-h
Compile en définitions de données C (un fichier d'en-tête). L'option -T peut être utilisée conjointement pour produire un fichier d'en-tête qui supporte les tables de dispatch RPC.
-I
Génère un service qui peut être démarré depuis inetd. La valeur par défaut est de générer un service statique qui gère les transports sélectionnés avec -s. L'utilisation de -I permet de démarrer un service par l'une ou l'autre méthode.
-K secs
Par défaut, les services créés à l'aide de rpcgen attendent 120 secondes après avoir traité une requête avant de se terminer. Cet intervalle peut être modifié à l'aide de l'indicateur -K. Pour créer un serveur qui se termine immédiatement après avoir traité une requête, -K 0 peut être utilisé. Pour créer un serveur qui ne se termine jamais, l'argument approprié est -K -1.
Lors de la surveillance d'un serveur, certains moniteurs de ports, comme listen(1M), lancent *toujours* un nouveau processus en réponse à une requête de service. S'il est connu qu'un serveur sera utilisé avec un tel moniteur, le serveur doit se terminer immédiatement après l'achèvement. Pour de tels serveurs, rpcgen doit être utilisé avec -K -1.
-l
Compile en "stubs" côté client.
-m
Compile en "stubs" côté serveur, mais ne génère pas de routine “main”. Cette option est utile pour les routines de rappel et pour les utilisateurs qui ont besoin d'écrire leur propre routine “main” pour effectuer l'initialisation.
-M
Génère des "stubs" compatibles multi-threads pour le passage d'arguments et de résultats entre le code généré par rpcgen et le code écrit par l'utilisateur. Cette option est utile pour les utilisateurs qui souhaitent utiliser des threads dans leur code.

NOM

rpcgen ― compilateur de protocole RPC

SYNTAXIS

rpcgen [ -a | -A ] [ -b ] [ -C ] [ -Dname[=value] ] [ -f ] [ -g ] [ -h ] [ -Idir ] [ -j ] [ -k ] [ -K ] [ -l ] [ -N ] [ -ooutfile ] [ -snettype ] [ -Sc ] [ -Sm ] [ -Ss ] [ -t ] [ -T ] [ -v ] [ -x ] [ -X ] file

DESCRIPTION

Le programme rpcgen est un utilitaire qui génère du code C à partir d'une spécification de protocole RPC. Il peut générer quatre types de fichiers : le fichier d'en-tête, le code client, le code serveur et le code de liaison XDR. Par défaut, rpcgen génère le fichier d'en-tête, le code client, le code serveur et le code de liaison XDR.

Le programme rpcgen peut également générer les fichiers suivants :

-a
Génère un ensemble complet de fichiers client, serveur et de liaison XDR. Les fichiers sont nommés en remplaçant l'extension du fichier d'entrée par les extensions .h, _clnt.c, _svc.c et _xdr.c.
-A
Génère un ensemble complet de fichiers client, serveur et de liaison XDR. Les fichiers sont nommés en remplaçant l'extension du fichier d'entrée par les extensions .h, _clnt.c, _svc.c et _xdr.c. Le code généré est compatible avec la version 2 de RPC.
-b
Génère un code stub client qui peut être utilisé sur des systèmes incompatibles avec les stubs RPC standards. Ce code stub client est généralement utilisé pour accéder à un serveur RPC sur un système différent.
-c
Génère uniquement le code client.
-C
Génère du code client et serveur C++. Le code généré est écrit en C++ et peut être compilé à l'aide d'un compilateur C++.
-Dname[=value]
Définit le symbole name pour le préprocesseur C. L'option -D peut être utilisée plusieurs fois pour définir plusieurs symboles.
-f
Génère uniquement le code client. Cette option est identique à l'option -c.
-g
Génère uniquement le code serveur.
-h
Génère uniquement le fichier d'en-tête.
-Idir
Ajoute le répertoire dir à la liste des chemins de recherche pour les fichiers d'inclusion.
-j
Génère un code serveur qui peut être compilé sur des systèmes compatibles avec les stubs RPC standards. Ce code serveur est généralement utilisé pour servir des requêtes RPC à partir d'un client RPC sur un système différent.
-k
Génère du code serveur pour le système distant. Cette option est généralement utilisée pour générer du code serveur qui sera exécuté sur un système différent de celui où le code est généré.
-K
Génère du code serveur pour le système distant. Cette option est identique à l'option -k.
-l
Génère uniquement le code client.
-m
Génère du code serveur générique. Ce code serveur peut être utilisé pour servir des requêtes RPC à partir de clients sur différents systèmes.
-n netid
Compile en stubs côté serveur pour le transport spécifié par netid. Il doit y avoir une entrée pour netid dans la base de données netconfig. Cette option peut être spécifiée plusieurs fois, afin de compiler un serveur qui dessert plusieurs transports.
-N
Utilise le nouveau style de rpcgen. Cela permet aux procédures d'avoir plusieurs arguments. Il utilise également le style de passage de paramètres qui ressemble étroitement à C. Ainsi, lorsque vous passez un argument à une procédure distante, vous n'avez pas besoin de passer un pointeur vers l'argument, mais l'argument lui-même. Ce comportement est différent du style ancien du code généré par rpcgen. Le nouveau style n'est pas le cas par défaut en raison de la compatibilité ascendante.
-o outfile
Spécifie le nom du fichier de sortie. Si aucun n'est spécifié, la sortie standard est utilisée (modes -c, -h, -l, -m, -n, -s, -Sc, -Sm, -Ss, et -t seulement).
-s nettype
Compile en stubs côté serveur pour tous les transports appartenant à la classe nettype. Les classes prises en charge sont netpath, visible, circuit_n, circuit_v, datagram_n, datagram_v, tcp, et udp [voir rpc(3N) pour les significations associées à ces classes]. Cette option peut être spécifiée plusieurs fois. Remarque : les transports sont choisis au moment de l'exécution et non au moment de la compilation.
-Sc
Génère un exemple de code pour montrer l'utilisation de la procédure distante et comment se lier au serveur avant d'appeler les stubs côté client générés par rpcgen.
-Sm
Génère un exemple de Makefile qui peut être utilisé pour compiler l'application.
-Ss
Génère un code squelette pour les procédures distantes côté serveur. Vous devrez remplir le code réel pour les procédures distantes.
-t
Compile en table de dispatch RPC.
-T
Génère le code pour prendre en charge les tables de dispatch RPC.

Les options -c, -h, -l, -m, -s et -t sont utilisées exclusivement pour générer un type particulier de fichier, tandis que les options -D et -T sont globales et peuvent être utilisées avec les autres options.

NOTES

Le langage RPC ne prend pas en charge l'imbrication des structures. Comme solution de contournement, les structures peuvent être déclarées au niveau supérieur et leur nom utilisé à l'intérieur d'autres structures afin d'obtenir le même effet.

Des conflits de noms peuvent survenir lors de l'utilisation de définitions de programmes, car la portée apparente ne s'applique pas réellement. La plupart d'entre eux peuvent être évités en donnant des noms uniques aux programmes, versions, procédures et types.

Le code serveur généré avec l'option -n fait référence au transport indiqué par netid et est donc très spécifique au site.

EXEMPLE

L'exemple suivant :

$ rpcgen -T prot.x

génère les cinq fichiers : prot.h, prot_clnt.c, prot_svc.c, prot_xdr.c et prot_tbl.i.

L'exemple suivant envoie les définitions de données C (fichier d'en-tête) vers la sortie standard.

$ rpcgen -h prot.x

Pour envoyer la version de test de -DTEST, les stubs côté serveur pour tous les transports appartenant à la classe datagram_n vers la sortie standard, utilisez :

$ rpcgen -s datagram_n -DTEST prot.x

Pour créer les stubs côté serveur pour le transport indiqué par netid tcp, utilisez :

$ rpcgen -n tcp -o prot_svc.c prot.x
