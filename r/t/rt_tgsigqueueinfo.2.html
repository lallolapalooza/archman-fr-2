rt_sigqueueinfo(2) Manuel des appels système rt_sigqueueinfo(2)

NOM

rt_sigqueueinfo, rt_tgsigqueueinfo - mettre en file d'attente un signal et des données

BIBLIOTHÈQUE

Bibliothèque C standard (libc, -lc)

SYNTAXE

#include <linux/signal.h>     /* Définition des constantes SI_* */
#include <sys/syscall.h>      /* Définition des constantes SYS_* */
#include <unistd.h>
int syscall(SYS_rt_sigqueueinfo, pid_t tgid,
            int sig, siginfo_t *info);
int syscall(SYS_rt_tgsigqueueinfo, pid_t tgid, pid_t tid,
            int sig, siginfo_t *info);

Note : Il n'y a pas de wrappers glibc pour ces appels système ; voir NOTES.

DESCRIPTION

Les appels système rt_sigqueueinfo() et rt_tgsigqueueinfo() sont les interfaces de bas niveau utilisées pour envoyer un signal plus des données à un processus ou un thread. Le récepteur du signal peut obtenir les données associées en établissant un gestionnaire de signal avec le drapeau SA_SIGINFO de sigaction(2).

Ces appels système ne sont pas destinés à une utilisation directe par les applications ; ils sont fournis pour permettre l'implémentation de sigqueue(3) et pthread_sigqueue(3).

L'appel système rt_sigqueueinfo() envoie le signal sig au groupe de threads avec l'ID tgid. (Le terme "groupe de threads" est synonyme de "processus", et tgid correspond à l'ID de processus UNIX traditionnel.) Le signal sera délivré à un membre arbitraire du groupe de threads (c'est-à-dire, l'un des threads qui ne bloque pas actuellement le signal).

L'argument info spécifie les données accompagnant le signal. Cet argument est un pointeur vers une structure de type siginfo_t, décrite dans sigaction(2) (et définie en incluant <sigaction.h>). L'appelant doit définir les champs suivants dans cette structure :

si_code
Ceci doit être l'un des codes SI_* du fichier source du noyau Linux include/asm-generic/siginfo.h. Si le signal est envoyé à un processus autre que celui de l'appelant lui-même, les restrictions suivantes s'appliquent :
•
Le code ne peut pas être une valeur supérieure ou égale à zéro. En particulier, il ne peut pas être SI_USER, utilisé par le noyau pour indiquer un signal envoyé par kill(2), ni SI_KERNEL, utilisé pour indiquer un signal généré par le noyau.
•
Le code ne peut pas (depuis Linux 2.6.39) être SI_TKILL, utilisé par le noyau pour indiquer un signal envoyé à l'aide de tgkill(2).
si_pid
Ceci doit être défini à un ID de processus, typiquement l'ID du processus expéditeur.
si_uid
Ceci doit être défini à un ID utilisateur, typiquement l'ID utilisateur réel de l'expéditeur.
si_value
Ce champ contient les données utilisateur accompagnant le signal. Pour plus d'informations, voir la description du dernier argument (union sigval) de sigqueue(3).

En interne, le noyau définit le champ si_signo à la valeur spécifiée dans sig, de sorte que le récepteur du signal puisse également obtenir le numéro du signal via ce champ.

L'appel système rt_tgsigqueueinfo() est similaire à rt_sigqueueinfo(), mais envoie le signal et les données au thread unique spécifié par la combinaison de tgid, un ID de groupe de threads, et tid, un thread dans ce groupe de threads.

VALEUR DE RETOUR

En cas de succès, ces appels système retournent 0. En cas d'erreur, ils retournent -1 et errno est défini pour indiquer l'erreur.

ERREURS

EAGAIN
La limite des signaux pouvant être mis en file d'attente a été atteinte. (Voir signal(7) pour plus d'informations.)
EINVAL
sig, tgid, ou tid était invalide.
EPERM
L'appelant n'a pas la permission d'envoyer le signal à la cible. Pour les permissions requises, voir kill(2).
EPERM
tgid spécifie un processus autre que celui de l'appelant et info->si_code est invalide.
ESRCH
rt_sigqueueinfo() : Aucun groupe de threads correspondant à tgid n'a été trouvé.

rt_tgsigqueinfo() : Aucun thread correspondant à tgid et tid n'a été trouvé.

NORMES

Linux.

HISTORIQUE

rt_sigqueueinfo()
Linux 2.2.
rt_tgsigqueueinfo()
Linux 2.6.31.

NOTES

Comme ces appels système ne sont pas destinés à l'utilisation par les applications, il n'y a pas de fonctions wrappers glibc ; utilisez syscall(2) dans le cas peu probable où vous voudriez les appeler directement.

Comme avec kill(2), le signal nul (0) peut être utilisé pour vérifier si le processus ou le thread spécifié existe.

VOIR AUSSI

kill(2), pidfd_send_signal(2), sigaction(2), sigprocmask(2), tgkill(2), pthread_sigqueue(3), sigqueue(3), signal(7)
