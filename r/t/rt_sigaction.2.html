sigaction(2) Manuel des appels système sigaction(2)

NOM

sigaction, rt_sigaction - examiner et modifier une action de signal

BIBLIOTHÈQUE

Bibliothèque C standard (libc, -lc)

SYNTAXE

#include <signal.h>
int sigaction(int signum,
              const struct sigaction *_Nullable restrict act,
              struct sigaction *_Nullable restrict oldact);
Exigences de macros de test de fonctionnalités pour glibc (voir feature_test_macros(7)) :

sigaction() :

    _POSIX_C_SOURCE

siginfo_t :

    _POSIX_C_SOURCE >= 199309L

DESCRIPTION

L'appel système sigaction() est utilisé pour modifier l'action entreprise par un processus lors de la réception d'un signal spécifique. (Voir signal(7) pour un aperçu des signaux.)

signum spécifie le signal et peut être n'importe quel signal valide sauf SIGKILL et SIGSTOP.

Si act n'est pas NULL, la nouvelle action pour le signal signum est installée à partir de act. Si oldact n'est pas NULL, l'action précédente est sauvegardée dans oldact.

La structure sigaction est définie comme suit :


struct sigaction {
    void     (*sa_handler)(int);
    void     (*sa_sigaction)(int, siginfo_t *, void *);
    sigset_t   sa_mask;
    int        sa_flags;
    void     (*sa_restorer)(void);
};

Sur certaines architectures, une union est impliquée : n'assignez pas à la fois sa_handler et sa_sigaction.

Le champ sa_restorer n'est pas destiné à être utilisé par l'application. (POSIX ne spécifie pas de champ sa_restorer.) Certains détails supplémentaires sur le but de ce champ se trouvent dans sigreturn(2).

sa_handler spécifie l'action à associer à signum et peut être l'une des suivantes :

•
SIG_DFL pour l'action par défaut.
•
SIG_IGN pour ignorer ce signal.
•
Un pointeur vers une fonction de gestion de signal. Cette fonction reçoit le numéro de signal comme seul argument.

Si SA_SIGINFO est spécifié dans sa_flags, alors sa_sigaction (au lieu de sa_handler) spécifie la fonction de gestion de signal pour signum. Cette fonction reçoit trois arguments, comme décrit ci-dessous.

sa_mask spécifie un masque de signaux qui doivent être bloqués (c'est-à-dire ajoutés au masque de signaux du thread dans lequel le gestionnaire de signal est invoqué) pendant l'exécution du gestionnaire de signal. De plus, le signal qui a déclenché le gestionnaire sera bloqué, sauf si le drapeau SA_NODEFER est utilisé.

sa_flags spécifie un ensemble de drapeaux qui modifient le comportement du signal. Il est formé par l'opération OU bit à bit de zéro ou plusieurs des drapeaux suivants :

SA_NOCLDSTOP
Si signum est SIGCHLD, ne pas recevoir de notification lorsque les processus enfants s'arrêtent (c'est-à-dire lorsqu'ils reçoivent l'un de SIGSTOP, SIGTSTP, SIGTTIN ou SIGTTOU) ou reprennent (c'est-à-dire qu'ils reçoivent SIGCONT) (voir wait(2)). Ce drapeau n'est pertinent que lors de l'établissement d'un gestionnaire pour SIGCHLD.
SA_NOCLDWAIT (depuis Linux 2.6)
Si signum est SIGCHLD, ne pas transformer les enfants en zombies lorsqu'ils se terminent. Voir aussi waitpid(2). Ce drapeau n'est pertinent que lors de l'établissement d'un gestionnaire pour SIGCHLD, ou lors de la définition de la disposition de ce signal à SIG_DFL.
Si le drapeau SA_NOCLDWAIT est défini lors de l'établissement d'un gestionnaire pour SIGCHLD, POSIX.1 laisse non spécifié si un signal SIGCHLD est généré lorsqu'un processus enfant se termine. Sous Linux, un signal SIGCHLD est généré dans ce cas ; sur certaines autres implémentations, ce n'est pas le cas.
SA_NODEFER
Ne pas ajouter le signal au masque de signaux du thread pendant que le gestionnaire s'exécute, sauf si le signal est spécifié dans act.sa_mask. Par conséquent, une autre instance du signal peut être délivrée au thread pendant qu'il exécute le gestionnaire. Ce drapeau n'est pertinent que lors de l'établissement d'un gestionnaire de signal.
SA_NOMASK est un synonyme obsolète et non standard pour ce drapeau.
SA_ONSTACK
Appeler le gestionnaire de signal sur une pile de signaux alternative fournie par sigaltstack(2). Si aucune pile alternative n'est disponible, la pile par défaut sera utilisée. Ce drapeau n'est pertinent que lors de l'établissement d'un gestionnaire de signal.
SA_RESETHAND
Restaurer l'action du signal à la valeur par défaut lors de l'entrée dans le gestionnaire de signal. Ce drapeau n'est pertinent que lors de l'établissement d'un gestionnaire de signal.
SA_ONESHOT est un synonyme obsolète et non standard pour ce drapeau.
SA_RESTART
Fournir un comportement compatible avec les sémantiques de signaux BSD en rendant certains appels système redémarrables après des signaux. Ce drapeau n'est pertinent que lors de l'établissement d'un gestionnaire de signal. Voir signal(7) pour une discussion sur le redémarrage des appels système.
SA_RESTORER
Non destiné à être utilisé par l'application. Ce drapeau est utilisé par les bibliothèques C pour indiquer que le champ sa_restorer contient l'adresse d'un "tremplin de signal". Voir sigreturn(2) pour plus de détails.
SA_SIGINFO (depuis Linux 2.2)
Le gestionnaire de signal prend trois arguments, pas un. Dans ce cas, sa_sigaction doit être défini au lieu de sa_handler. Ce drapeau n'est pertinent que lors de l'établissement d'un gestionnaire de signal.
SA_UNSUPPORTED (depuis Linux 5.11)
Utilisé pour sonder dynamiquement la prise en charge des bits de drapeau.
Si une tentative d'enregistrement d'un gestionnaire réussit avec ce drapeau défini dans act->sa_flags aux côtés d'autres drapeaux qui ne sont pas potentiellement pris en charge par le noyau, et si un appel sigaction() immédiatement ultérieur spécifiant le même numéro de signal et avec un argument oldact non NULL renvoie SA_UNSUPPORTED effacé dans oldact->sa_flags, alors oldact->sa_flags peut être utilisé comme un masque de bits décrivant quels des drapeaux potentiellement non pris en charge sont en fait pris en charge. Voir la section "Sondage dynamique pour la prise en charge des bits de drapeau" ci-dessous pour plus de détails.
SA_EXPOSE_TAGBITS (depuis Linux 5.11)
Normalement, lors de la délivrance d'un signal, un ensemble de bits de balisage spécifique à l'architecture sont effacés du champ si_addr de siginfo_t. Si ce drapeau est défini, un sous-ensemble spécifique à l'architecture des bits de balisage sera conservé dans si_addr.
Les programmes qui doivent être compatibles avec les versions de Linux antérieures à 5.11 doivent utiliser SA_UNSUPPORTED pour sonder la prise en charge.

L'argument siginfo_t d'un gestionnaire SA_SIGINFO

Lorsque le drapeau SA_SIGINFO est spécifié dans act.sa_flags, l'adresse du gestionnaire de signal est passée via le champ act.sa_sigaction. Ce gestionnaire prend trois arguments, comme suit :


void
handler(int sig, siginfo_t *info, void *ucontext)
{
    ...
}

Ces trois arguments sont les suivants :

sig
Le numéro du signal qui a provoqué l'invocation du gestionnaire.
info
Un pointeur vers un siginfo_t, qui est une structure contenant des informations supplémentaires sur le signal, comme décrit ci-dessous.

Ceci est un pointeur vers une structure ucontext_t, casté en void *. La structure pointée par ce champ contient des informations de contexte de signal qui ont été sauvegardées sur la pile de l'espace utilisateur par le noyau ; pour plus de détails, voir sigreturn(2). Des informations supplémentaires sur la structure ucontext_t se trouvent dans getcontext(3) et signal(7). Couramment, la fonction gestionnaire n'utilise pas le troisième argument.

Le type de données siginfo_t est une structure avec les champs suivants :


siginfo_t {
    int      si_signo;     /* Numéro de signal */
    int      si_errno;     /* Une valeur errno */
    int      si_code;      /* Code de signal */
    int      si_trapno;    /* Numéro de piège qui a provoqué
                              le signal généré par le matériel
                              (inutilisé sur la plupart des architectures) */
    pid_t    si_pid;       /* ID du processus d'envoi */
    uid_t    si_uid;       /* ID utilisateur réel du processus d'envoi */
    int      si_status;    /* Valeur de sortie ou signal */
    clock_t  si_utime;     /* Temps utilisateur consommé */
    clock_t  si_stime;     /* Temps système consommé */
    union sigval si_value; /* Valeur du signal */
    int      si_int;       /* Signal POSIX.1b */
    void    *si_ptr;       /* Signal POSIX.1b */
    int      si_overrun;   /* Compteur de dépassement de délai ;
                              timers POSIX.1b */
    int      si_timerid;   /* ID du timer ; timers POSIX.1b */
    void    *si_addr;      /* Emplacement mémoire qui a provoqué l'échec */
    long     si_band;      /* Événement de bande (était int dans
                              glibc 2.3.2 et antérieur) */
    int      si_fd;        /* Descripteur de fichier */
    short    si_addr_lsb;  /* Bit le moins significatif de l'adresse
                              (depuis Linux 2.6.32) */
    void    *si_lower;     /* Limite inférieure lors de la violation d'adresse
                              survenue (depuis Linux 3.19) */
    void    *si_upper;     /* Limite supérieure lors de la violation d'adresse
                              survenue (depuis Linux 3.19) */
    int      si_pkey;      /* Clé de protection sur le PTE qui a provoqué
                              l'échec (depuis Linux 4.6) */
    void    *si_call_addr; /* Adresse de l'instruction d'appel système
                              (depuis Linux 3.5) */
    int      si_syscall;   /* Numéro de l'appel système tenté
                              (depuis Linux 3.5) */
    unsigned int si_arch;  /* Architecture de l'appel système tenté
                              (depuis Linux 3.5) */
}

si_signo, si_errno et si_code sont définis pour tous les signaux. (si_errno est généralement inutilisé sous Linux.) Le reste de la structure peut être une union, de sorte qu'il ne faut lire que les champs qui ont un sens pour le signal donné :

•
Les signaux envoyés avec kill(2) et sigqueue(3) remplissent si_pid et si_uid. De plus, les signaux envoyés avec sigqueue(3) remplissent si_int et si_ptr avec les valeurs spécifiées par l'expéditeur du signal ; voir sigqueue(3) pour plus de détails.
•
Les signaux envoyés par les timers POSIX.1b (depuis Linux 2.6) remplissent si_overrun et si_timerid. Le champ si_timerid est un ID interne utilisé par le noyau pour identifier le timer ; il n'est pas le même que l'ID du timer renvoyé par timer_create(2). Le champ si_overrun est le compteur de dépassement de délai du timer ; il s'agit des mêmes informations que celles obtenues par un appel à timer_getoverrun(2). Ces champs sont des extensions non standard de Linux.
•
Les signaux envoyés pour la notification de file d'attente de messages (voir la description de SIGEV_SIGNAL dans mq_notify(3)) remplissent si_int/si_ptr, avec la valeur sigev_value fournie à mq_notify(3) ; si_pid, avec l'ID du processus de l'expéditeur du message ; et si_uid, avec l'ID utilisateur réel de l'expéditeur du message.
•
SIGCHLD remplit si_pid, si_uid, si_status, si_utime et si_stime, fournissant des informations sur l'enfant. Le champ si_pid est l'ID du processus de l'enfant ; si_uid est l'ID utilisateur réel de l'enfant. Le champ si_status contient le statut de sortie de l'enfant (si si_code est CLD_EXITED), ou le numéro du signal qui a provoqué le changement d'état du processus. Les champs si_utime et si_stime contiennent le temps CPU utilisateur et système utilisé par le processus enfant ; ces champs n'incluent pas les temps utilisés par les enfants attendus (contrairement à getrusage(2) et times(2)). Jusqu'à Linux 2.6, et depuis Linux 2.6.27, ces champs rapportent le temps CPU dans des unités de sysconf(_SC_CLK_TCK). Dans les noyaux Linux 2.6 avant Linux 2.6.27, un bug a fait que ces champs rapportaient le temps dans des unités du jiffy système (configurable) (voir time(7)).
•
SIGILL, SIGFPE, SIGSEGV, SIGBUS et SIGTRAP remplissent si_addr avec l'adresse de l'échec. Sur certaines architectures, ces signaux remplissent également le champ si_trapno.
Certaines sous-erreurs de SIGBUS, en particulier BUS_MCEERR_AO et BUS_MCEERR_AR, remplissent également si_addr_lsb. Ce champ indique le bit le moins significatif de l'adresse rapportée et donc l'étendue de la corruption. Par exemple, si une page entière a été corrompue, si_addr_lsb contient log2(sysconf(_SC_PAGESIZE)). Lorsque SIGTRAP est délivré en réponse à un événement ptrace(2) (PTRACE_EVENT_foo), si_addr n'est pas renseigné, mais si_pid et si_uid sont renseignés avec les ID de processus et utilisateur respectifs responsables de la livraison du piège. Dans le cas de seccomp(2), le tracee sera montré comme livrant l'événement. BUS_MCEERR_* et si_addr_lsb sont des extensions spécifiques à Linux.
La sous-erreur SEGV_BNDERR de SIGSEGV remplit si_lower et si_upper.
La sous-erreur SEGV_PKUERR de SIGSEGV remplit si_pkey.
•
SIGIO/SIGPOLL (les deux noms sont des synonymes sous Linux) remplissent si_band et si_fd. L'événement si_band est un masque de bits contenant les mêmes valeurs que celles remplies dans le champ revents par poll(2). Le champ si_fd indique le descripteur de fichier pour lequel l'événement d'E/S s'est produit ; pour plus de détails, voir la description de F_SETSIG dans fcntl(2).
•
SIGSYS, généré (depuis Linux 3.5) lorsqu'un filtre seccomp renvoie SECCOMP_RET_TRAP, remplit si_call_addr, si_syscall, si_arch, si_errno et d'autres champs comme décrit dans seccomp(2).

Le champ si_code

Le champ si_code dans l'argument siginfo_t qui est passé à un gestionnaire de signal SA_SIGINFO est une valeur (pas un masque de bits) indiquant pourquoi ce signal a été envoyé. Pour un événement ptrace(2), si_code contiendra SIGTRAP et aura l'événement ptrace dans l'octet de poids fort :


(SIGTRAP | PTRACE_EVENT_foo << 8).

Pour un événement non-ptrace(2), les valeurs qui peuvent apparaître dans si_code sont décrites dans le reste de cette section. Depuis glibc 2.20, les définitions de la plupart de ces symboles sont obtenues à partir de <signal.h> en définissant des macros de test de fonctionnalités (avant d'inclure n'importe quel fichier d'en-tête) comme suit :

•
_XOPEN_SOURCE avec la valeur 500 ou plus ;
•
_XOPEN_SOURCE et _XOPEN_SOURCE_EXTENDED ; ou
•
_POSIX_C_SOURCE avec la valeur 200809L ou plus.

Pour les constantes TRAP_*, les définitions de symboles ne sont fournies que dans les deux premiers cas. Avant glibc 2.20, aucune macro de test de fonctionnalité n'était requise pour obtenir ces symboles.

DESCRIPTION

The sigaction() system call examines and changes the action taken by a process for a specific signal. The argument signum is the signal number for which to change the action; this is a signal identifier like SIGINT or SIGTERM.

The argument act is a pointer to a structure that specifies the new action to be taken when the signal signum is delivered. If act is NULL, then the current action for the signal is not changed.

The argument oldact is a pointer to a structure in which the previous action for the signal is saved. If oldact is NULL, the previous action is not saved.

The structure sigaction has the following members:

        void     (*sa_handler)(int);
        void     (*sa_sigaction)(int, siginfo_t *, void *);
        sigset_t   sa_mask;
        int        sa_flags;
        void     (*sa_restorer)(void);

If SA_SIGINFO is specified in sa_flags, then sa_sigaction is used for the signal handler; otherwise, sa_handler is used. The sa_mask argument specifies additional signals to be blocked during the execution of the handler. While a signal handler is executing, the signal that caused its invocation is always blocked.

The sa_flags field specifies optional actions. The supported values for sa_flags are:

SA_NOCLDSTOP
If the signal is SIGCHLD, this flag prevents the signal from being sent when a child process stops (i.e., when it receives SIGSTOP, SIGTSTP, SIGTTIN, or SIGTTOU).
SA_NOCLDWAIT
If the signal is SIGCHLD, this flag causes the system to ignore the child death notification. If the last child of a process terminates, and if the process has set up a handler for SIGCHLD, then no signal is generated. If all children of a process terminate, the process receives no signal. This flag has no effect if the process is ignoring SIGCHLD.
SA_SIGINFO
The signal handler takes three arguments as opposed to the traditional one. The third argument is a pointer to a siginfo_t structure that provides more detailed information about the signal. The handler is specified by sa_sigaction.
SA_ONSTACK
Execute the handler on an alternate signal stack. See sigaltstack(2).
SA_RESTART
Some system calls automatically restart after being interrupted by a signal if this flag is set. This behavior depends on the system and the specific system call. The default behavior for signals is to not restart system calls. This flag is ignored for SIGCHLD.
SA_RESETHAND
Restore the default disposition of the signal when the handler is invoked. The signal handler will be reset to SIG_DFL.
SA_NODEFER
Do not block the signal when the handler is executing. By default, the signal that caused the handler to be invoked is blocked.
SA_RESTORER
This flag can only be used when establishing a signal handler using a non-NULL act->sa_restorer. If set, the sa_restorer field points to a function that is called after the signal handler returns. This function is responsible for restoring the stack frame and returning from the signal handler. This is typically used by shared libraries to implement signal handling mechanisms. On most architectures, the C library provides a default restorer function that can be pointed to by sa_restorer. See sigreturn(2).
SA_UNSUPPORTED (since Linux 5.11)
This flag is used to detect support for new flags. When setting flags in act->sa_flags, if any unsupported flags are set, the kernel will clear them in the oldact->sa_flags returned by a subsequent sigaction() call. This means that if oldact->sa_flags & SA_UNSUPPORTED is non-zero after the call, then some flags in act->sa_flags were not supported by the kernel.

The siginfo_t structure

When the SA_SIGINFO flag is set, the signal handler is invoked with a pointer to a siginfo_t structure. This structure contains the following members:

        int     si_signo;       /* Signal number */
        int     si_errno;       /* If non-zero, indicates an error number */
        int     si_code;        /* Signal code */
        pid_t   si_pid;         /* Sending process ID */
        uid_t   si_uid;         /* Sending process UID */
        void   *si_addr;        /* Address (causes signal) */
        int     si_status;      /* Exit value or signal */
        int     si_int;         /* Integer value */
        int     si_ptr;         /* Pointer value */
        /* ... further members depend on the signal */

The si_signo, si_errno, si_pid, si_uid, and si_addr members are always meaningful for signals where SA_SIGINFO is supported.

The si_code member provides further information about the cause of the signal. Its interpretation depends on the signal number.

The si_status member is the exit value of the child process (if si_code is CLD_EXITED), or the signal number that caused the child process to terminate (if si_code is CLD_KILLED or CLD_DUMPED).

The si_int member is an integer value available for some signals.

The si_ptr member is a pointer value available for some signals.

Délai d'exécution utilisateur syscall déclenché.

La valeur suivante peut être placée dans si_code pour un signal SIGEMT :

EMT_TAGOVF (SPARC uniquement)
Dépassement d'étiquette.

Sondage dynamique du support des bits d'indicateur

L'appel sigaction() sous Linux accepte les bits inconnus définis dans act->sa_flags sans erreur. Le comportement du noyau à partir de Linux 5.11 est qu'un second appel sigaction() effacera les bits inconnus de oldact->sa_flags. Cependant, historiquement, un second appel sigaction() laissait généralement ces bits définis dans oldact->sa_flags.

Cela signifie que le support de nouveaux indicateurs ne peut pas être détecté simplement en testant un indicateur dans sa_flags, et un programme doit tester que SA_UNSUPPORTED a été effacé avant de se fier au contenu de sa_flags.

Étant donné que le comportement du gestionnaire de signaux ne peut pas être garanti sauf si la vérification réussit, il est conseillé soit de bloquer le signal affecté lors de l'enregistrement du gestionnaire et d'effectuer la vérification dans ce cas, soit, lorsque cela n'est pas possible, par exemple si le signal est synchrone, d'émettre le deuxième appel sigaction() dans le gestionnaire de signaux lui-même.

Dans les noyaux qui ne supportent pas un indicateur spécifique, le comportement du noyau est comme si l'indicateur n'était pas défini, même si l'indicateur était défini dans act->sa_flags.

Les indicateurs SA_NOCLDSTOP, SA_NOCLDWAIT, SA_SIGINFO, SA_ONSTACK, SA_RESTART, SA_NODEFER, SA_RESETHAND, et, s'il est défini par l'architecture, SA_RESTORER peuvent ne pas être sondés de manière fiable à l'aide de ce mécanisme, car ils ont été introduits avant Linux 5.11. Cependant, en général, les programmes peuvent supposer que ces indicateurs sont pris en charge, car ils sont tous pris en charge depuis Linux 2.6, qui est sorti en 2003.

Voir EXEMPLES ci-dessous pour une démonstration de l'utilisation de SA_UNSUPPORTED.

VALEUR DE RETOUR

sigaction() renvoie 0 en cas de succès ; en cas d'erreur, -1 est renvoyé, et errno est défini pour indiquer l'erreur.

ERREURS

EFAULT
act ou oldact pointe vers une mémoire qui ne fait pas partie de l'espace d'adressage valide du processus.
EINVAL
Un signal invalide a été spécifié. Ceci sera également généré si une tentative est faite pour modifier la disposition du signal SIGKILL ou SIGSTOP, qui ne peuvent pas être interceptés ou ignorés.

VERSIONS

Différences bibliothèque C/noyau

La fonction wrapper glibc pour sigaction() renvoie une erreur (EINVAL) lors des tentatives de modification de la disposition des deux signaux temps réel utilisés en interne par l'implémentation du threading NPTL. Voir nptl(7) pour les détails.

Sur les architectures où le trampoline de signal réside dans la bibliothèque C, la fonction wrapper glibc pour sigaction() place l'adresse du code du trampoline dans le champ act.sa_restorer et définit l'indicateur SA_RESTORER dans le champ act.sa_flags. Voir sigreturn(2).

L'appel système Linux d'origine s'appelait sigaction().

rt_sigaction(2) — man pages

NOM

rt_sigaction, sigaction - examiner et modifier l'action d'un signal

BIBLIOTHÈQUE

Bibliothèque C standard (libc, -lc)

SYNTAXE

       #include <signal.h>

       int sigaction(int sig, const struct sigaction *act,
                     struct sigaction *oldact);
       int rt_sigaction(int sig, const struct sigaction *act,
                        struct sigaction *oldact, size_t sigsetsize);

DESCRIPTION

La fonction de bibliothèque C sigaction() est un wrapper autour de l'appel système du même nom. L'appel système rt_sigaction() permet d'examiner et de modifier la disposition d'un signal pour un processus spécifié. Il peut être utilisé pour changer l'action associée à un signal spécifié, pour vérifier l'action actuelle associée à un signal, ou pour les deux. Le signal est spécifié par l'argument sig.

Les informations sur l'action à effectuer pour le signal sont stockées dans la structure pointée par act. Si act est NULL, alors ces paramètres ne sont pas modifiés.

Les anciennes informations sur l'action du signal sont retournées à l'emplacement pointé par oldact. Si oldact est NULL, alors l'ancienne information n'est pas retournée.

La structure sigaction est définie comme suit :

       struct sigaction {
           void     (*sa_handler)(int);
           void     (*sa_sigaction)(int, siginfo_t *, void *);
           sigset_t   sa_mask;
           int        sa_flags;
           void     (*sa_restorer)(void);
       };

Le champ sa_handler spécifie la routine de traitement du signal à associer à l'argument sig. Si sa_handler est SIG_DFL, l'action par défaut est effectuée pour le signal. Si sa_handler est SIG_IGN, le signal est ignoré.

Si le champ sa_sigaction est utilisé au lieu de sa_handler, alors la fonction spécifiée par sa_sigaction est appelée lorsque le signal est livré. Cette fonction reçoit trois arguments : le numéro du signal, un pointeur vers une structure siginfo_t contenant des informations détaillées sur le signal, et un pointeur vers une structure ucontext_t (casté en void *) qui contient le contexte du thread au moment de la livraison du signal.

Le champ sa_mask spécifie un masque de signaux qui seront bloqués pendant l'exécution du gestionnaire de signaux. En plus des signaux spécifiés dans sa_mask, le signal en cours de traitement est également bloqué.

Le champ sa_flags spécifie une option ou un ensemble d'options qui modifient le comportement de la manipulation des signaux. Les drapeaux suivants sont reconnus :

SA_NOCLDWAIT
Si le signal est SIGCHLD, cela empêche la création de zombies. Lorsque le processus enfant se termine, ses ressources sont libérées immédiatement. L'appelant ne recevra pas de notification de la terminaison de l'enfant (par le biais de SIGCHLD), et il n'y aura pas de zombie à récolter. Cet indicateur n'a d'effet que si le processus parent ignore le signal SIGCHLD.
SA_NOCLDSTOP
Si le signal est SIGCHLD, cela fait en sorte que le signal ne soit pas livré lorsque l'enfant s'arrête (reçoit SIGSTOP ou un signal équivalent), mais seulement lorsqu'il se termine. Si cet indicateur n'est pas spécifié, le signal SIGCHLD est livré lorsque l'enfant s'arrête et lorsqu'il se termine.
SA_NODEFER
Empêche le signal spécifié dans sig d'être bloqué pendant l'exécution du gestionnaire. Normalement, le signal est masqué pendant l'exécution du gestionnaire.
SA_ONSTACK
Appelle le gestionnaire de signal sur une pile alternative. La pile alternative est spécifiée par sigaltstack(2).
SA_RESETHAND
Réinitialise la disposition du signal à sa valeur par défaut après être entré dans le gestionnaire de signal. Cela signifie que, lors des livraisons ultérieures du même signal, l'action par défaut sera effectuée (sauf si le signal est à nouveau intercepté ou ignoré).
SA_RESTART
Si un appel système interrompu est redémarré à la suite de la réception de ce signal, l'appel système sera redémarré au lieu de retourner une erreur avec errno défini sur EINTR. La nature exacte du redémarrage dépend de l'appel système et du noyau. Voir également signal(7).
SA_SIGINFO
Permet de fournir des informations supplémentaires sur le signal via le champ sa_sigaction. Sans cet indicateur, seul le champ sa_handler est utilisé.

Le champ sa_restorer est généralement ignoré et doit être défini sur NULL. Il était utilisé dans les anciennes versions de systèmes pour restaurer le contexte avant le gestionnaire, mais cela est désormais géré par le noyau.

Le système d'appels rt_sigaction() est la version moderne de l'appel système sigaction(). Dans les noyaux Linux plus anciens, la taille du type sigset_t était fixée à 32 bits. Cependant, avec l'ajout de signaux en temps réel dans le noyau Linux 2.2, le type sigset_t de taille fixe et 32 bits pris en charge par cet appel système n'était plus adapté. Par conséquent, un nouvel appel système, rt_sigaction(), a été ajouté pour prendre en charge un type sigset_t agrandi. Le nouvel appel système prend un quatrième argument, size_t sigsetsize, qui spécifie la taille en octets des ensembles de signaux dans act.sa_mask et oldact.sa_mask. Cet argument doit actuellement avoir la valeur sizeof(sigset_t) (sinon l'erreur EINVAL résulte). La fonction wrapper sigaction() de glibc nous cache ces détails, appelant de manière transparente rt_sigaction() lorsque le noyau le fournit.

VALEUR RENDUE

En cas de succès, 0 est retourné. En cas d'échec, -1 est retourné, et errno est défini pour indiquer l'erreur.

ERREURS

EINVAL
L'argument sig n'est pas un signal valide, ou sigsetsize n'est pas égal à sizeof(sigset_t) lors de l'appel à rt_sigaction().
EFAULT
act ou oldact pointe vers une adresse mémoire invalide.

VERSIONS

L'appel système rt_sigaction() est présent depuis le noyau Linux 2.2. La fonction wrapper sigaction() est fournie par la glibc.

STANDARDS

POSIX.1-2024.

HISTORIQUE

POSIX.1-2001, SVr4.

POSIX.1-1990 interdisait la définition de l'action pour SIGCHLD à SIG_IGN. POSIX.1-2001 et versions ultérieures permettent cette possibilité, de sorte que l'ignorance de SIGCHLD peut être utilisée pour empêcher la création de zombies (voir wait(2)). Néanmoins, les comportements historiques BSD et System V pour ignorer SIGCHLD diffèrent, de sorte que la seule méthode complètement portable pour s'assurer que les enfants terminés ne deviennent pas des zombies est de capturer le signal SIGCHLD et d'effectuer un wait(2) ou similaire.

POSIX.1-1990 ne spécifiait que SA_NOCLDSTOP. POSIX.1-2001 a ajouté SA_NOCLDWAIT, SA_NODEFER, SA_ONSTACK, SA_RESETHAND, SA_RESTART et SA_SIGINFO en tant qu'extensions XSI. POSIX.1-2008 a déplacé SA_NODEFER, SA_RESETHAND, SA_RESTART et SA_SIGINFO vers les spécifications de base. L'utilisation de ces dernières valeurs dans sa_flags peut être moins portable dans les applications destinées aux anciennes implémentations UNIX.

L'indicateur SA_RESETHAND est compatible avec l'indicateur SVr4 du même nom.

L'indicateur SA_NODEFER est compatible avec l'indicateur SVr4 du même nom sous les noyaux 1.3.9 et plus récents. Sur les noyaux plus anciens, l'implémentation Linux permettait la réception de n'importe quel signal, pas seulement celui que nous installons (remplaçant effectivement tout réglage de sa_mask).

NOTES

Un enfant créé via fork(2) hérite d'une copie des dispositions de signaux de son parent. Lors d'un execve(2), les dispositions des signaux gérés sont réinitialisées à la valeur par défaut ; les dispositions des signaux ignorés restent inchangées.

Selon POSIX, le comportement d'un processus est indéfini après avoir ignoré un signal SIGFPE, SIGILL ou SIGSEGV qui n'a pas été généré par kill(2) ou raise(3). La division entière par zéro a un résultat indéfini. Sur certaines architectures, elle générera un signal SIGFPE. (Diviser également l'entier le plus négatif par -1 peut générer SIGFPE.) Ignorer ce signal pourrait conduire à une boucle infinie.

sigaction() peut être appelé avec un argument second NULL pour interroger le gestionnaire de signal actuel. Il peut également être utilisé pour vérifier si un signal donné est valide pour la machine actuelle en l'appelant avec des arguments seconds et tiers NULL.

Il n'est pas possible de bloquer SIGKILL ou SIGSTOP (en les spécifiant dans sa_mask). Les tentatives de le faire sont silencieusement ignorées.

Voir sigsetops(3) pour les détails sur la manipulation des ensembles de signaux.

Voir signal-safety(7) pour une liste des fonctions sûres pour les signaux asynchrones qui peuvent être appelées en toute sécurité à l'intérieur d'un gestionnaire de signaux.

POSIX ne garantit que SI_TIMER pour les signaux créés par timer_create(2). Les implémentations sont libres de les fournir également pour d'autres types de timers. Le comportement de Linux correspond à NetBSD.

Non documenté

Avant l'introduction de SA_SIGINFO, il était également possible d'obtenir des informations supplémentaires sur le signal. Ceci était fait en fournissant un gestionnaire de signal sa_handler avec un deuxième argument de type struct sigcontext, qui est la même structure que celle qui est passée dans le champ uc_mcontext de la structure ucontext qui est passée (via un pointeur) dans le troisième argument du gestionnaire sa_sigaction. Voir les sources pertinentes du noyau Linux pour les détails. Cette utilisation est obsolète maintenant.

BOGUES

Lors de la livraison d'un signal résultant d'une exception matérielle avec un gestionnaire SA_SIGINFO, le noyau ne fournit pas toujours des valeurs significatives pour tous les champs de siginfo_t qui sont pertinents pour ce signal. Par exemple, lorsque l'instruction int x86 est appelée avec un argument interdit (n'importe quel nombre autre que 3 ou 128), un signal SIGSEGV est livré, mais le siginfo_t passé au gestionnaire de signal a tous ses champs, à l'exception de si_signo et si_code, mis à zéro, même si d'autres champs devraient être définis (par exemple, si_addr devrait être non nul pour tous les signaux SIGSEGV).

Jusqu'à et y compris Linux 2.6.13, la spécification de SA_NODEFER dans sa_flags empêchait non seulement le signal livré d'être bloqué pendant l'exécution du gestionnaire, mais aussi les signaux spécifiés dans sa_mask. Ce bogue a été corrigé dans Linux 2.6.14.

Voir mprotect(2).

Sondage pour la prise en charge des indicateurs

L'exemple de programme suivant se termine avec le statut EXIT_SUCCESS si SA_EXPOSE_TAGBITS est déterminé comme étant pris en charge, et EXIT_FAILURE sinon.

#include <signal.h>
#include <stdio.h>
#include <stdlib.h>
#include <unistd.h>
static void
handler(int signo, siginfo_t *info, void *context)
{
    struct sigaction oldact;
    if (sigaction(SIGSEGV, NULL, &oldact) == -1
        || (oldact.sa_flags & SA_UNSUPPORTED)
        || !(oldact.sa_flags & SA_EXPOSE_TAGBITS))
    {
        _exit(EXIT_FAILURE);
    }
    _exit(EXIT_SUCCESS);
}
int
main(void)
{
    struct sigaction act = { 0 };
    act.sa_flags = SA_SIGINFO | SA_UNSUPPORTED | SA_EXPOSE_TAGBITS;
    act.sa_sigaction = &handler;
    if (sigaction(SIGSEGV, &act, NULL) == -1) {
        perror("sigaction");
        exit(EXIT_FAILURE);
    }
    raise(SIGSEGV);
}
