rtc(4) Manuel des pilotes de périphériques rtc(4)

NOM

rtc - horloge temps réel

SYNTAXE

#include <linux/rtc.h>
int ioctl(fd, RTC_request, param);

DESCRIPTION

Ceci est l'interface des pilotes pour les horloges temps réel (RTC).

La plupart des ordinateurs disposent d'une ou plusieurs horloges matérielles qui enregistrent l'heure actuelle. Celles-ci sont appelées « horloges temps réel » (RTC). L'une d'entre elles dispose généralement d'une alimentation de secours par batterie afin qu'elle continue à suivre l'heure même lorsque l'ordinateur est éteint. Les RTC fournissent souvent des alarmes et d'autres interruptions.

Tous les PC i386 et les systèmes basés sur ACPI disposent d'une RTC compatible avec la puce Motorola MC146818 du PC/AT d'origine. Aujourd'hui, une telle RTC est généralement intégrée dans le chipset de la carte mère (pont sud) et utilise une pile bouton remplaçable.

Les systèmes non-PC, tels que les systèmes embarqués basés sur des processeurs système sur puce (SoC), utilisent d'autres implémentations. Ils n'offriront généralement pas les mêmes fonctionnalités que la RTC d'un PC/AT.

RTC vs horloge système

Il ne faut pas confondre les RTC avec l'horloge système, qui est une horloge logicielle maintenue par le noyau et utilisée pour implémenter gettimeofday(2) et time(2), ainsi que pour définir les horodatages des fichiers, etc. L'horloge système indique les secondes et les microsecondes depuis un point de départ, défini comme l'époque POSIX : 1970-01-01 00:00:00 +0000 (UTC). (Une implémentation courante compte les interruptions du minuteur, une par « jiffy », à une fréquence de 100, 250 ou 1000 Hz.) C'est-à-dire qu'elle est censée indiquer l'heure universelle, ce que font également les RTC.

Une différence clé entre une RTC et l'horloge système est que les RTC fonctionnent même lorsque le système est dans un état de faible consommation (y compris « éteint »), ce que l'horloge système ne peut pas faire. Tant qu'elle n'est pas initialisée, l'horloge système ne peut indiquer que le temps écoulé depuis le démarrage du système, et non depuis l'époque POSIX. Ainsi, au démarrage, et après la reprise d'un état de faible consommation, l'horloge système sera souvent réglée sur l'heure universelle actuelle à l'aide d'une RTC. Les systèmes sans RTC doivent régler l'horloge système à l'aide d'une autre horloge, peut-être via le réseau ou en saisissant manuellement ces données.

Fonctionnalité RTC

Les RTC peuvent être lues et écrites avec hwclock(8), ou directement avec les requêtes ioctl(2) listées ci-dessous.

En plus de suivre la date et l'heure, de nombreuses RTC peuvent également générer des interruptions

•
à chaque mise à jour de l'horloge (c'est-à-dire une fois par seconde) ;
•
à des intervalles périodiques avec une fréquence pouvant être réglée sur n'importe quel multiple de puissance de 2 dans la plage de 2 Hz à 8192 Hz ;
•
à l'atteinte d'une heure d'alarme précédemment spécifiée.

Chacune de ces sources d'interruption peut être activée ou désactivée séparément. Sur de nombreux systèmes, l'interruption d'alarme peut être configurée comme un événement de réveil du système, qui peut sortir le système d'un état de faible consommation tel que Suspend-to-RAM (STR, appelé S3 dans les systèmes ACPI), Hibernation (appelé S4 dans les systèmes ACPI), ou même « éteint » (appelé S5 dans les systèmes ACPI). Sur certains systèmes, la RTC alimentée par batterie ne peut pas générer d'interruptions, mais une autre horloge le peut.

Le périphérique /dev/rtc (ou /dev/rtc0, /dev/rtc1, etc.) ne peut être ouvert qu'une seule fois (jusqu'à sa fermeture) et est en lecture seule. Lors d'un read(2) et d'un select(2), le processus appelant est bloqué jusqu'à réception de la prochaine interruption de cette RTC. Suite à l'interruption, le processus peut lire un entier long, dont le byte de poids faible contient un masque de bits codant les types d'interruptions qui se sont produites, tandis que les 3 bytes restants contiennent le nombre d'interruptions depuis le dernier read(2).

Interface ioctl(2)

Les requêtes ioctl(2) suivantes sont définies sur les descripteurs de fichiers connectés aux périphériques RTC :

RTC_RD_TIME
Retourne l'heure de cette RTC dans la structure suivante :

struct rtc_time {
    int tm_sec;
    int tm_min;
    int tm_hour;
    int tm_mday;
    int tm_mon;
    int tm_year;
    int tm_wday;     /* inutilisé */
    int tm_yday;     /* inutilisé */
    int tm_isdst;    /* inutilisé */
};

Les champs de cette structure ont la même signification et les mêmes plages que pour la structure tm décrite dans gmtime(3). Un pointeur vers cette structure doit être passé comme troisième argument de ioctl(2).
RTC_SET_TIME
Définit l'heure de cette RTC à l'heure spécifiée par la structure rtc_time pointée par le troisième argument ioctl(2). Pour définir l'heure de la RTC, le processus doit être privilégié (c'est-à-dire avoir la capacité CAP_SYS_TIME).
RTC_ALM_READ
RTC_ALM_SET
Lit et définit l'heure de l'alarme, pour les RTC qui supportent les alarmes. L'interruption d'alarme doit être activée ou désactivée séparément à l'aide des requêtes RTC_AIE_ON, RTC_AIE_OFF. Le troisième argument ioctl(2) est un pointeur vers une structure rtc_time. Seuls les champs tm_sec, tm_min et tm_hour de cette structure sont utilisés.
RTC_IRQP_READ
RTC_IRQP_SET
Lit et définit la fréquence des interruptions périodiques, pour les RTC qui supportent les interruptions périodiques. L'interruption périodique doit être activée ou désactivée séparément à l'aide des requêtes RTC_PIE_ON, RTC_PIE_OFF. Le troisième argument ioctl(2) est un unsigned long * ou un unsigned long, respectivement. La valeur est la fréquence en interruptions par seconde. L'ensemble des fréquences autorisées sont les multiples de deux dans la plage de 2 à 8192. Seul un processus privilégié (c'est-à-dire ayant la capacité CAP_SYS_RESOURCE) peut définir des fréquences supérieures à la valeur spécifiée dans /proc/sys/dev/rtc/max-user-freq. (Ce fichier contient la valeur 64 par défaut.)
RTC_AIE_ON
RTC_AIE_OFF
Active ou désactive l'interruption d'alarme, pour les RTC qui supportent les alarmes. Le troisième argument ioctl(2) est ignoré.
RTC_UIE_ON
RTC_UIE_OFF
Active ou désactive l'interruption à chaque mise à jour de l'horloge, pour les RTC qui supportent cette interruption une fois par seconde. Le troisième argument ioctl(2) est ignoré.
RTC_PIE_ON
RTC_PIE_OFF
Active ou désactive l'interruption périodique, pour les RTC qui supportent ces interruptions périodiques. Le troisième argument ioctl(2) est ignoré. Seul un processus privilégié (c'est-à-dire ayant la capacité CAP_SYS_RESOURCE) peut activer l'interruption périodique si la fréquence est actuellement réglée au-dessus de la valeur spécifiée dans /proc/sys/dev/rtc/max-user-freq.
RTC_EPOCH_READ
RTC_EPOCH_SET
De nombreuses RTC codent l'année dans un registre 8 bits qui est soit interprété comme un nombre binaire 8 bits, soit comme un nombre BCD. Dans les deux cas, le nombre est interprété par rapport à l'Epoch de cette RTC. rtc(4) — Linux manual pages

NAME

rtc - Real Time Clock device

SYNOPSIS

#include <sys/ioctl.h>

#include <linux/rtc.h>

int fd;
struct tm tbuf;
unsigned long epoch;
struct rtc_wkalrm wkalrm;

ioctl(fd, RTC_RD_TIME, &tbuf);
ioctl(fd, RTC_SET_TIME, &tbuf);
ioctl(fd, RTC_ALM_READ, &tbuf);
ioctl(fd, RTC_ALM_SET, &tbuf);
ioctl(fd, RTC_IRQP_READ, &irqdata);
ioctl(fd, RTC_IRQP_SET, &irqdata);
ioctl(fd, RTC_EPOCH_READ, &epoch);
ioctl(fd, RTC_EPOCH_SET, &epoch);
ioctl(fd, RTC_WKALM_RD, &wkalrm);
ioctl(fd, RTC_WKALM_SET, &wkalrm);

DESCRIPTION

The device node /dev/rtc (or /dev/rtc0, /dev/rtc1, etc.) provides an interface to a hardware Real Time Clock (RTC). The primary use is to set or read the system time from the hardware clock. Most of the functionality is accessed via the ioctl(2) system call.

The structure struct tm is defined in gmtime(3). The fields used are:

  • tm_sec: seconds (0-60)
  • tm_min: minutes (0-59)
  • tm_hour: hours (0-23)
  • tm_mday: day of month (1-31)
  • tm_mon: month (0-11; January=0!)
  • tm_year: years since 1900
  • tm_isdst: ignored

The following ioctl(2) commands are supported:

RTC_RD_TIME
Read the current time from the RTC device. The second ioctl(2) argument is a pointer to a struct tm, which is filled with the current RTC time.
RTC_SET_TIME
Set the RTC device to the time specified in the struct tm pointed to by the second ioctl(2) argument. This operation requires root privileges (CAP_SYS_TIME).
RTC_ALM_READ
Read the current alarm time from the RTC device. The second ioctl(2) argument is a pointer to a struct tm, which is filled with the current alarm time.
RTC_ALM_SET
Set the alarm time of the RTC device to the time specified in the struct tm pointed to by the second ioctl(2) argument. This operation requires root privileges (CAP_SYS_TIME).
RTC_AIE_ON
Enable the alarm interrupt (Periodic Interrupt Enable). When the RTC alarm time is reached, the kernel sends a SIGALRM signal to the calling process.
RTC_AIE_OFF
Disable the alarm interrupt.
RTC_IRQP_READ
Read the periodic interrupt frequency. The second ioctl(2) argument is a pointer to an unsigned long which is filled with the frequency in Hz. This is only supported by some RTCs.
RTC_IRQP_SET
Set the periodic interrupt frequency. The second ioctl(2) argument is a pointer to an unsigned long which specifies the frequency in Hz. Supported frequencies are typically powers of 2, from 2 Hz up to 8192 Hz. This operation requires root privileges (CAP_SYS_TIME). This is only supported by some RTCs.
RTC_EPOCH_READ
Read the RTC's epoch value. The Epoch is a year that determines how the two-digit year value in the RTC is interpreted. For example, if the Epoch is 1996, then a year value of 90 means 1990, and a year value of 5 means 2005. The second ioctl(2) argument is a pointer to an unsigned long which is filled with the Epoch year.
RTC_EPOCH_SET
Set the RTC's epoch value. The second ioctl(2) argument is a pointer to an unsigned long, and the value written is the Epoch year. This operation requires root privileges (CAP_SYS_TIME). This is only supported by some RTCs.
RTC_WKALM_RD
RTC_WKALM_SET
Some RTCs support a more powerful alarm interface, using these ioctls to read or write the RTC's alarm time (respectively) with this structure:

struct rtc_wkalrm {
    unsigned char enabled;
    unsigned char pending;
    struct rtc_time time;
};
The enabled flag is used to enable or disable the alarm interrupt, or to read its current status; when using these calls, RTC_AIE_ON and RTC_AIE_OFF are not used. The pending flag is used by RTC_WKALM_RD to report a pending interrupt (so it's mostly useless on Linux, except when talking to the RTC managed by EFI firmware). The time field is as used with RTC_ALM_READ and RTC_ALM_SET except that the tm_mday, tm_mon, and tm_year fields are also valid. A pointer to this structure should be passed as the third ioctl(2) argument.

FILES

/dev/rtc
/dev/rtc0
/dev/rtc1
...
RTC special character device files.
/proc/driver/rtc
status of the (first) RTC.

NOTES

When the kernel's system time is synchronized with an external reference using adjtimex(2) it will update a designated RTC periodically every 11 minutes. To do so, the kernel has to briefly turn off periodic interrupts; this might affect programs using that RTC.

An RTC's Epoch has nothing to do with the POSIX Epoch which is used only for the system clock.

If the year according to the RTC's Epoch and the year register is less than 1970 it is assumed to be 100 years later, that is, between 2000 and 2069.

Some RTCs support "wildcard" values in alarm fields, to support scenarios like periodic alarms at fifteen minutes after every hour, or on the first day of each month. Such usage is nonportable; portable user-space code expects only a single alarm interrupt, and will either disable or reinitialize the alarm after receiving it.

Some RTCs support periodic interrupts with periods that are multiples of a second rather than fractions of a second; multiple alarms; programmable output clock signals; nonvolatile memory; and other hardware capabilities that are not currently exposed by this API.
