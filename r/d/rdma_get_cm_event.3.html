RDMA_GET_CM_EVENT(3) Manuel du programmeur Librdmacm RDMA_GET_CM_EVENT(3)

NOM

rdma_get_cm_event - Récupère le prochain événement de communication en attente.

SYNTAXE

#include <rdma/rdma_cma.h>

int rdma_get_cm_event (struct rdma_event_channel *canal, struct rdma_cm_event **événement);

ARGUMENTS

canal
Canal d'événements à vérifier pour les événements.
événement
Informations allouées sur le prochain événement de communication.

DESCRIPTION

Récupère un événement de communication. Si aucun événement n'est en attente, par défaut, l'appel bloquera jusqu'à ce qu'un événement soit reçu.

VALEUR DE RETOUR

Retourne 0 en cas de succès, ou -1 en cas d'erreur. Si une erreur survient, errno sera défini pour indiquer la raison de l'échec.

NOTES

Le comportement synchrone par défaut de cette routine peut être modifié en modifiant le descripteur de fichier associé au canal donné. Tous les événements signalés doivent être acquittés en appelant rdma_ack_cm_event. La destruction d'un rdma_cm_id bloquera jusqu'à ce que les événements associés aient été acquittés.

DONNÉES ÉVÉNEMENT

Les détails de l'événement de communication sont retournés dans la structure rdma_cm_event. Cette structure est allouée par le rdma_cm et libérée par la routine rdma_ack_cm_event. Les détails de la structure rdma_cm_event sont donnés ci-dessous.

id
L'identifiant rdma_cm associé à l'événement. Si le type d'événement est RDMA_CM_EVENT_CONNECT_REQUEST, cela fait référence à un nouvel id pour cette communication.
listen_id
Pour les types d'événements RDMA_CM_EVENT_CONNECT_REQUEST, cela fait référence à l'identifiant de la requête d'écoute correspondante.
événement
Spécifie le type d'événement de communication qui s'est produit. Voir TYPES D'ÉVÉNEMENTS ci-dessous.
status
Retourne toute information d'erreur asynchrone associée à un événement. Le statut est zéro si l'opération a réussi, sinon la valeur du statut est non nulle et est soit définie sur un errno négatif, soit sur une valeur spécifique au transport. Pour plus de détails sur les valeurs de statut spécifiques au transport, voir les informations sur le type d'événement ci-dessous.
param
Fournit des détails supplémentaires en fonction du type d'événement. Les utilisateurs doivent sélectionner les sous-champs conn ou ud en fonction de l'espace de ports rdma (rdma_port_space) du rdma_cm_id associé à l'événement. Voir DONNÉES D'ÉVÉNEMENT UD et DONNÉES D'ÉVÉNEMENT DE CONNEXION ci-dessous.

DONNÉES ÉVÉNEMENT UD

Paramètres d'événement liés aux services de datagrammes non fiables (UD) : RDMA_PS_UDP et RDMA_PS_IPOIB. Les données d'événement UD sont valides pour les événements RDMA_CM_EVENT_ESTABLISHED et RDMA_CM_EVENT_MULTICAST_JOIN, sauf indication contraire.

private_data
Fait référence à toute donnée spécifiée par l'utilisateur associée aux événements RDMA_CM_EVENT_CONNECT_REQUEST ou RDMA_CM_EVENT_ESTABLISHED. Les données référencées par ce champ correspondent à celles spécifiées par le côté distant lors de l'appel de rdma_connect ou rdma_accept. Ce champ est NULL si l'événement n'inclut pas de données privées. Le tampon référencé par ce pointeur est désalloué lors de l'appel de rdma_ack_cm_event.
private_data_len
La taille du tampon de données privées. Les utilisateurs doivent noter que la taille du tampon de données privées peut être supérieure à la quantité de données privées envoyées par le côté distant. Tout espace supplémentaire dans le tampon sera mis à zéro.
ah_attr
Informations d'adresse nécessaires pour envoyer des données aux points d'extrémité distants. Les utilisateurs doivent utiliser cette structure lors de l'allocation de leur handle d'adresse.
qp_num
Numéro QP du point d'extrémité distant ou du groupe de multidiffusion.
qkey
QKey nécessaire pour envoyer des données aux points d'extrémité distants.

DONNÉES ÉVÉNEMENT CONNEXION

Paramètres d'événement liés aux services de QP connectés : RDMA_PS_TCP. Les données d'événement de connexion sont valides pour les événements RDMA_CM_EVENT_CONNECT_REQUEST et RDMA_CM_EVENT_ESTABLISHED, sauf indication contraire.

private_data
Fait référence à toute donnée spécifiée par l'utilisateur associée à l'événement. Les données référencées par ce champ correspondent à celles spécifiées par le côté distant lors de l'appel de rdma_connect ou rdma_accept. Ce champ est NULL si l'événement n'inclut pas de données privées. Le tampon référencé par ce pointeur est désalloué lors de l'appel de rdma_ack_cm_event.
private_data_len
La taille du tampon de données privées. Les utilisateurs doivent noter que la taille du tampon de données privées peut être supérieure à la quantité de données privées envoyées par le côté distant. Tout espace supplémentaire dans le tampon sera mis à zéro.
responder_resources
Le nombre de ressources répondeur demandées au destinataire. Ce champ correspond à la profondeur de l'initiateur spécifiée par le nœud distant lors de l'appel de rdma_connect et rdma_accept.
initiator_depth
Le nombre maximum d'opérations RDMA read/atomic en attente que le destinataire peut avoir. Ce champ correspond aux ressources répondeur spécifiées par le nœud distant lors de l'appel de rdma_connect et rdma_accept.
flow_control
Indique si le contrôle de flux au niveau matériel est fourni par l'expéditeur.
retry_count
Pour les événements RDMA_CM_EVENT_CONNECT_REQUEST uniquement, indique le nombre de fois où le destinataire doit retenter les opérations d'envoi.
rnr_retry_count
Le nombre de fois où le destinataire doit retenter les erreurs de NACK "récepteur non prêt" (RNR).
srq
Indique si l'expéditeur utilise une file de réception partagée (shared-receive queue).
qp_num
Indique le numéro QP distant pour la connexion.

TYPES ÉVÉNEMENT

Les types suivants d'événements de communication peuvent être signalés.

RDMA_CM_EVENT_ADDR_RESOLVED
La résolution d'adresse (rdma_resolve_addr) s'est terminée avec succès.
RDMA_CM_EVENT_ADDR_ERROR
La résolution d'adresse (rdma_resolve_addr) a échoué.
RDMA_CM_EVENT_ROUTE_RESOLVED
La résolution de route (rdma_resolve_route) s'est terminée avec succès.
RDMA_CM_EVENT_ROUTE_ERROR
La résolution de route (rdma_resolve_route) a échoué.
RDMA_CM_EVENT_CONNECT_REQUEST
Généré du côté passif pour notifier l'utilisateur d'une nouvelle requête de connexion.
RDMA_CM_EVENT_CONNECT_RESPONSE
Généré du côté actif pour notifier l'utilisateur d'une réponse réussie à une requête de connexion. Il n'est généré que sur les rdma_cm_id qui n'ont pas de QP associé.
RDMA_CM_EVENT_CONNECT_ERROR
Indique qu'une erreur s'est produite

rdma_get_cm_event(3) — rdma-core — Arch Linux

NAME

rdma_get_cm_event — retrieve an RDMA Connection Manager (CM) event

SYNOPSIS

#include <rdma/rdma_cma.h>

int rdma_get_cm_event(struct rdma_event_channel *event_channel, struct rdma_cm_event **event);

ARGUMENTS

event_channel
The RDMA CM event channel to retrieve an event from.
event
A pointer to a pointer that will be set to the retrieved event. The caller is responsible for freeing the event using rdma_ack_cm_event(3).

DESCRIPTION

The rdma_get_cm_event function retrieves an event from the specified RDMA CM event channel. This function will block until an event is available or an error occurs.

Upon successful retrieval of an event, the event parameter will be populated with a pointer to a struct rdma_cm_event structure. The caller is responsible for freeing the memory associated with the event structure using rdma_ack_cm_event(3).

If the event channel is destroyed while a thread is blocked in rdma_get_cm_event, the function will return -1 and set errno to ECANCELED.

RETURN VALUE

On success, rdma_get_cm_event returns 0. On failure, it returns -1 and sets errno.

NOTES

An RDMA CM event channel should be created using rdma_create_event_channel(3).

The struct rdma_cm_event structure contains information about the event, including the event type and status.

EVENT DATA

The struct rdma_cm_event contains the following fields:

struct rdma_cm_id *id
The RDMA CM identifier associated with the event.
enum rdma_cm_event_type event
The type of the event. See EVENT TYPES below.
int status
The status of the event. For connection-related events, this will typically be 0 on success, or an errno value on failure. For other events, its meaning is transport-specific.

UD EVENT DATA

For Unreliable Datagram (UD) queue pairs (QPs), the event structure may contain additional data in the udata field, which is a pointer to a union. The relevant member of the union is determined by the event type.

CONN EVENT DATA

For connection-oriented services, the event structure may contain additional connection information in the conn_data field.

EVENT TYPES

RDMA_CM_EVENT_CONNECT_REQUEST
Generated on the passive side to notify the user of a connection request from a remote client. The user should call rdma_accept(3) or rdma_reject(3) in response.
RDMA_CM_EVENT_CONNECT_RESPONSE
Generated on the active side to notify the user of a response to a connection request. The event status indicates whether the connection was accepted or rejected.
RDMA_CM_EVENT_USER_BINDING
Generated on the passive side to notify the user that a connection request has been received and that the user is now bound to the rdma_cm_id, and the QP is ready to be created. The user may now call rdma_accept(3) or rdma_reject(3).
RDMA_CM_EVENT_UNREACHABLE
Generated on the active side to notify the user that the remote server is not reachable or unable to respond to a connection request. If this event is generated in response to a UD QP resolution request over InfiniBand, the event status field will contain an errno, if negative, or the status result carried in the IB CM SIDR REP message.
RDMA_CM_EVENT_REJECTED
Indicates that a connection request or response was rejected by the remote end point. The event status field will contain the transport specific reject reason if available. Under InfiniBand, this is the reject reason carried in the IB CM REJ message.
RDMA_CM_EVENT_ESTABLISHED
Indicates that a connection has been established with the remote end point.
RDMA_CM_EVENT_DISCONNECTED
The connection has been disconnected.
RDMA_CM_EVENT_DEVICE_REMOVAL
The local RDMA device associated with the rdma_cm_id has been removed. Upon receiving this event, the user must destroy the related rdma_cm_id.
RDMA_CM_EVENT_MULTICAST_JOIN
The multicast join operation (rdma_join_multicast) completed successfully.
RDMA_CM_EVENT_MULTICAST_ERROR
An error either occurred joining a multicast group, or, if the group had already been joined, on an existing group. The specified multicast group is no longer accessible and should be rejoined, if desired.
RDMA_CM_EVENT_ADDR_CHANGE
The network device associated with this ID through address resolution changed its HW address, eg following of bonding failover. This event can serve as a hint for applications who want the links used for their RDMA sessions to align with the network stack.
RDMA_CM_EVENT_TIMEWAIT_EXIT
The QP associated with a connection has exited its timewait state and is now ready to be re-used. After a QP has been disconnected, it is maintained in a timewait state to allow any in flight packets to exit the network. After the timewait state has completed, the rdma_cm will report this event.
RDMA_CM_EVENT_ADDRINFO_RESOLVED
Address information resolution (rdma_resolve_addrinfo) completed successfully.
RDMA_CM_EVENT_ADDRINFO_ERROR
Address information resolution (rdma_resolve_addrinfo) failed.
RDMA_CM_EVENT_USER
This allows a user-defined event to be written to the RDMA CM event channel. Event details are specified by the user and not interpreted by the librdmacm. This event is useful for a multi-threaded application to signal a thread which may be waiting on the RDMA CM event channel.
