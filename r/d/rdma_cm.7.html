RDMA_CM(7) Manuel du programmeur Librdmacm RDMA_CM(7)

NOM

rdma_cm - Gestionnaire de communication RDMA.

SYNTAXE

#include <rdma/rdma_cma.h>

DESCRIPTION

Utilisé pour établir la communication sur les transports RDMA.

NOTES

Le RDMA CM est un gestionnaire de communication utilisé pour configurer des transferts de données fiables, connectés et de datagrammes non fiables. Il fournit une interface neutre pour le transport RDMA pour établir des connexions. Les concepts de l'API sont basés sur les sockets, mais adaptés aux sémantiques basées sur les paires de files d'attente (QP) : la communication doit se faire via un périphérique RDMA spécifique, et les transferts de données sont basés sur des messages.

Le RDMA CM peut contrôler à la fois le QP et la gestion de la communication (établissement/clôture de connexion) de l'API RDMA, ou seulement la partie gestion de la communication. Il fonctionne en conjonction avec l'API des verbes définie par la bibliothèque libibverbs. La bibliothèque libibverbs fournit les interfaces sous-jacentes nécessaires pour envoyer et recevoir des données.

Le RDMA CM peut fonctionner de manière asynchrone ou synchrone. Le mode de fonctionnement est contrôlé par l'utilisateur via l'utilisation du paramètre de canal d'événements rdma_cm dans des appels spécifiques. Si un canal d'événements est fourni, un identifiant rdma_cm rapportera ses données d'événements (résultats de connexion, par exemple) sur ce canal. Si aucun canal n'est fourni, toutes les opérations rdma_cm pour l'identifiant rdma_cm sélectionné bloqueront jusqu'à leur achèvement.

Le RDMA CM offre une option aux différents fournisseurs libibverbs pour annoncer et utiliser diverses options de configuration de QP spécifiques à ce fournisseur. Cette fonctionnalité est appelée ECE (établissement de connexion amélioré).

VERBES RDMA

Le rdma_cm prend en charge toute la gamme des verbes disponibles via la bibliothèque libibverbs et ses interfaces. Cependant, il fournit également des fonctions d'encapsulation pour certaines des fonctionnalités des verbes les plus couramment utilisées. L'ensemble complet des appels de verbes abstraits est le suivant :

rdma_reg_msgs - enregistre un tableau de tampons pour l'envoi et la réception

rdma_reg_read - enregistre un tampon pour les opérations de lecture RDMA

rdma_reg_write - enregistre un tampon pour les opérations d'écriture RDMA

rdma_dereg_mr - désenregistre une région mémoire

rdma_post_recv - poste un tampon pour recevoir un message

rdma_post_send - poste un tampon pour envoyer un message

rdma_post_read - poste une opération de lecture RDMA pour lire des données dans un tampon

rdma_post_write - poste une opération d'écriture RDMA pour envoyer des données à partir d'un tampon

rdma_post_recvv - poste un vecteur de tampons pour recevoir un message

rdma_post_sendv - poste un vecteur de tampons pour envoyer un message

rdma_post_readv - poste un vecteur de tampons pour recevoir une lecture RDMA

rdma_post_writev - poste un vecteur de tampons pour envoyer une écriture RDMA

rdma_post_ud_send - poste un tampon pour envoyer un message sur un QP UD

rdma_get_send_comp - obtient l'état de complétion pour une opération d'envoi ou RDMA

rdma_get_recv_comp - obtient des informations sur une réception terminée

OPÉRATION CLIENT

Cette section fournit un aperçu général du fonctionnement de base pour le côté actif, ou client, de la communication. Ce flux suppose un fonctionnement asynchrone avec les détails des appels de bas niveau montrés. Pour un fonctionnement synchrone, les appels à rdma_create_event_channel, rdma_get_cm_event, rdma_ack_cm_event et rdma_destroy_event_channel seraient éliminés. Les appels abstraits, tels que rdma_create_ep, encapsulent plusieurs de ces appels sous une seule API. Les utilisateurs peuvent également se référer aux exemples d'applications pour des échantillons de code. Un flux de connexion général serait :

rdma_create_event_channel

rdma_create_id

rdma_resolve_addr
obtenir un périphérique RDMA local pour atteindre l'adresse distante

rdma_ack_cm_event
accuser réception de l'événement
rdma_create_qp
allouer un QP pour la communication
rdma_resolve_route
déterminer la route vers l'adresse distante
rdma_get_cm_event
attendre l'événement RDMA_CM_EVENT_ROUTE_RESOLVED
rdma_ack_cm_event
accuser réception de l'événement
rdma_connect
se connecter au serveur distant
rdma_get_cm_event
attendre l'événement RDMA_CM_EVENT_ESTABLISHED
rdma_ack_cm_event
accuser réception de l'événement

Effectuer des transferts de données sur la connexion

rdma_ack_cm_event
accuser réception de l'événement

rdma_set_local_ece

Un processus presque identique est utilisé pour configurer la communication de datagrammes non fiables (UD) entre les nœuds. Cependant, aucune connexion réelle n'est formée entre les QP, donc la déconnexion n'est pas nécessaire.

Bien que cet exemple montre le client initiant la déconnexion, les deux côtés d'une connexion peuvent initier la déconnexion.

The following functions are related to establishing and tearing down RDMA connections:

CODES DE RETOUR

= 0
succès
= -1
erreur - voir errno pour plus de détails

La plupart des fonctions librdmacm renvoient 0 pour indiquer le succès, et une valeur de retour -1 pour indiquer un échec. Si une fonction fonctionne de manière asynchrone, une valeur de retour de 0 signifie que l'opération a été démarrée avec succès. L'opération peut toujours échouer ; les utilisateurs doivent vérifier l'état de l'événement associé. Si la valeur de retour est -1, alors errno contiendra des informations supplémentaires concernant la raison de l'échec.

Les versions antérieures de la bibliothèque renvoyaient -errno et ne définissaient pas errno pour certains cas liés aux codes ENOMEM, ENODEV, ENODATA, EINVAL et EADDRNOTAVAIL. Les applications qui souhaitent vérifier ces codes et avoir une compatibilité avec les versions antérieures de la bibliothèque doivent définir manuellement errno à l'opposé négatif du code de retour s'il est < -1.
