RGBASM(5) Manuel des formats de fichiers RGBASM(5)

NOM

rgbasm — documentation du langage d'assemblage

DESCRIPTION

Ceci est la description complète du langage d'assemblage utilisé par rgbasm(1). Pour la description complète des instructions du langage machine supporté par le CPU du Game Boy, voir gbz80(7).

Il est conseillé d'avoir une certaine familiarité avec le matériel du Game Boy avant de lire ce document. RGBDS est spécifiquement conçu pour le Game Boy, et par conséquent, bon nombre de ses fonctionnalités sont directement liées à ses concepts. Ce document n'est pas destiné à servir de référence matérielle pour le Game Boy.

En général, « l'éditeur de liens » fait référence à rgblink(1), mais tout programme qui traite les fichiers objet RGBDS (décrits dans rgbds(5)) peut être utilisé à sa place.

SYNTAXE

La syntaxe est basée sur les lignes, comme dans tout autre assembleur. Chaque ligne peut comporter des composants dans cet ordre :

[directive] [; commentaire]
[étiquette:] [instruction [:: instruction ...]] [; commentaire]

Les directives sont des commandes destinées à l'assembleur lui-même, telles que PRINTLN, SECTION, ou OPT.

Les étiquettes lient un nom à un emplacement spécifique dans une section (voir Étiquettes ci-dessous).

Les instructions sont assemblées en codes opératoires du Game Boy. Plusieurs instructions sur une même ligne peuvent être séparées par des doubles points « :: ».

Les instructions disponibles sont documentées dans gbz80(7).

Notez que là où une instruction nécessite un registre 8 bits r8, rgbasm peut interpréter HIGH(r16) comme le registre supérieur de 8 bits du r16 donné, par exemple, HIGH(HL) pour H ; et LOW(r16) comme la partie inférieure, par exemple, LOW(HL) pour L (sauf pour LOW(AF), car F n'est pas un registre valide).

Notez également que là où une instruction nécessite un code de condition cc, rgbasm peut interpréter !cc comme le code de condition opposé ; par exemple, !nz pour z.

Tous les mots-clés réservés (directives, noms de registres, etc.) sont insensibles à la casse ; tous les identifiants (étiquettes et autres noms de symboles) sont sensibles à la casse.

Les commentaires servent à fournir des informations sur le code aux humains, telles que des explications. L'assembleur ignore toujours les commentaires et leur contenu.

Il existe deux types de commentaires : en ligne et de bloc. Les commentaires en ligne sont tout ce qui suit un point-virgule « ; » qui n'est pas à l'intérieur d'une chaîne, jusqu'à la fin de la ligne. Les commentaires de bloc, commençant par « /* » et se terminant par « */ », peuvent s'étendre sur plusieurs lignes, ou apparaître au milieu d'une expression.

Un exemple illustrant ces caractéristiques de syntaxe :

SECTION "Mon Code", ROM0  ; une directive
MaFonction:              ; une étiquette
    push hl              ; une instruction
    /* ...et plusieurs instructions,
       avec casse mixte */
    ld a, [hli] :: LD H, [HL] :: Ld l, a
    pop /*attendez ça*/ hl
    ret

Parfois, les lignes peuvent être trop longues et il peut être nécessaire de les scinder. Pour ce faire, placez une barre oblique inverse à la fin de la ligne :

    DB 1, 2, 3, \
       4, 5, 6, \ ; Mettez-le avant tout commentaire
       7, 8, 9
    DB "Bonjour, \  ; L'espace avant le \ est inclus
monde!"           ; Tout espace de début est inclus

Interpolation de symboles

Une fonctionnalité amusante consiste à écrire un symbole entre accolades « {accolades} », appelée « interpolation de symbole ». Cela collera le contenu du symbole comme s'il faisait partie du fichier source. S'il s'agit d'un symbole de chaîne, ses caractères sont simplement insérés tels quels. S'il s'agit d'un symbole numérique, sa valeur est convertie en notation hexadécimale avec un signe dollar « $ » préfixé.

Les interpolations de symboles peuvent également être imbriquées !

DEF sujet EQUS "la vie, l'univers et "tout""
DEF sens EQUS "réponse"
; Définit réponse = 42
DEF {sens} = 42
; Affiche "La réponse à la vie, l'univers et "tout" est $2A"
PRINTLN "La {sens} à {sujet} est {{sens}}"
PURGE sujet, sens, {sens}

Les symboles peuvent être interpolés même dans des contextes qui désactivent l'expansion automatique expansion des constantes de chaîne : « nom » sera développé dans tous les contextes de « DEF({nom}) », « DEF {nom} EQU/=/EQUS/etc ... », « PURGE {nom} », et « MACRO {nom} », mais, par exemple, ne sera pas dans « DEF(nom) ».

Il est possible de modifier la façon dont les symboles sont imprimés en spécifiant un format d'impression comme suit : « {fmt:symbole} ». Le spécificateur « fmt » est composé des parties suivantes : « <signe><exact><alignement><remplissage><largeur><frac><préc><type> ». Ces parties sont :

Partie Signification
« <signe> » Peut être « + » ou «   ». Si spécifié, imprime ce caractère devant les nombres non négatifs.
« <exact> » Peut être « # ». Si spécifié, imprime la valeur dans un format « exact » : avec un préfixe de base pour les types entiers non décimaux (« $ », « & », ou « % ») ; avec un suffixe de précision « q » pour les nombres à virgule fixe ; ou avec des caractères d'échappement « \ » pour les chaînes.
« <alignement> » Peut être « - ». Si spécifié, aligne à gauche au lieu de droite.
« <remplissage> » Peut être « 0 ». Si spécifié, remplit les nombres alignés à droite avec des zéros au lieu d'espaces.
« <largeur> » Peut être un ou plusieurs chiffres « 0 » à « 9 ». Si spécifié, remplit la valeur jusqu'à cette largeur, alignée à droite avec des espaces par défaut.
« <frac> » Peut être « . » suivi d'un ou plusieurs chiffres « 0 » à « 9 ». Si spécifié, imprime ce nombre de chiffres fractionnaires d'un nombre à virgule fixe. Par défaut 5 chiffres, maximum 255 chiffres.
« <préc> » Peut être « q » suivi d'un ou plusieurs chiffres « 0 » à « 9 ». Si spécifié, le nombre sera imprimé avec cette précision. La précision est utilisée pour les nombres entiers, les nombres à virgule fixe et les nombres flottants. La valeur entière sera divisée par 10 élevé à la puissance de la précision, avant d'être imprimée.
« <type> » Ce peut être un des caractères suivants : « b » (binaire), « o » (octal), « d » (décimal), « x » (hexadécimal, minuscules), « X » (hexadécimal, majuscules), « p » (pointeur, comme « x »), « s » (chaîne).

Par exemple, pour imprimer une valeur de 16 bits avec un préfixe hexadécimal, une largeur de 4 chiffres, remplie avec des zéros et en utilisant des lettres minuscules pour les chiffres de a à f, utilisez le format « {04x:valeur} ».

Pour imprimer un nombre signé de 32 bits en décimal, avec un signe `+` pour les positifs, une largeur de 10 chiffres et rempli avec des espaces, utilisez le format « {+10d:nombre} ».

Pour imprimer une chaîne avec une précision de 10 caractères, alignée à gauche et remplie d'espaces, utilisez le format « {10.10s:chaine} ».

Il est possible de combiner plusieurs formats :

DEF num EQ 123
DEF val EQ 456.789
DEF str EQ "longue chaine de caracteres"
PRINTLN "{#08x:{num}} ; Imprime 123 en hexadécimal, avec préfixe, largeur 8, rempli de zéros : $0000007B
PRINTLN "{+10.5f:{val}} ; Imprime 456.78900 en format flottant, avec signe +, largeur 10, 5 chiffres après la virgule :   +456.78900
PRINTLN "{10.10s:{str}} ; Imprime les 10 premiers caractères de la chaîne, alignés à gauche, largeur 10 : longue chaî
PRINTLN "{#04q:{val}} ; Imprime 456.78900 avec suffixe de précision q : 456.78900q

Étiquettes

Une étiquette est un identifiant qui pointe vers une adresse mémoire. Les étiquettes peuvent être définies en plaçant un identifiant suivi d'un deux-points « : » en début de ligne.

Une étiquette peut également être placée à la fin d'une instruction, précédée d'un deux-points.

Les étiquettes peuvent être globales ou locales. Les étiquettes locales sont des identifiants commençant par un point « . ». Elles ne sont visibles que dans le périmètre de la section où elles sont définies.

Les étiquettes peuvent également être relatives, c'est-à-dire qu'elles peuvent être définies comme relatives à une autre étiquette. Cela est fait en utilisant le symbole « @ ».

start:
    nop
    jp start

.loop:
    ld a, 1
    add a, 1
    jp .loop

; L'étiquette "end" est relative à l'étiquette "start"
start:
    jp end
end:
    ret

; Équivalent à l'exemple précédent
start@:
    jp end@
end@:
    ret

Les étiquettes peuvent être utilisées dans les expressions pour faire référence à une adresse mémoire. Par exemple :

    ld hl, start
    ld de, .loop
    ld bc, end - start

Il est également possible de définir des étiquettes pour des champs spécifiques dans les données. Cela est fait en utilisant la syntaxe « étiquette:champ », où « champ » est un nombre entier.

data:
    db $11
data:0: equ $11 ; Équivaut à l'étiquette "data"
data:1: equ $12 ; Pointe vers le octet suivant

Directives

Les directives sont des commandes pour l'assembleur. Elles ne sont pas assemblées en code machine, mais affectent la façon dont le code est généré ou traité.

Voici quelques directives courantes :

SECTION
Démarre une nouvelle section de code ou de données. Une section est une partie logique du programme qui sera placée à un endroit spécifique dans la ROM ou la RAM. Les sections sont typiquement nommées et ont un type (par exemple, ROM0, VRAM, WRAM).
ORG
Définit l'adresse de départ pour la section courante. Cela est généralement fait implicitement par la directive SECTION.
DB
Définit un octet (ou une séquence d'octets) de données.
DW
Définit un mot (2 octets) de données.
DS
Réserve un espace de données (en octets).
EQU
Assigne une valeur numérique à un symbole.
EQUS
Assigne une chaîne de caractères à un symbole.
IF
Contrôle le flux d'assemblage basé sur une condition. Le bloc de code suivant est assemblé uniquement si la condition est vraie.
ELSE
Utilisé avec IF pour définir un bloc de code à assembler si la condition IF est fausse.
ENDIF
Termine un bloc IF.
INCLUDE
Inclut le contenu d'un autre fichier source dans le fichier courant.
MACRO
Définit une macro, qui est un bloc de code réutilisable.
ENDM
Termine la définition d'une macro.
PRINT
Imprime un message pendant l'assemblage.
PRINTLN
Imprime un message suivi d'un saut de ligne pendant l'assemblage.
WARN
Émet un avertissement pendant l'assemblage.
ERROR
Émet une erreur pendant l'assemblage et arrête le processus.
OPT
Définit des options pour l'assembleur (par exemple, la casse des symboles, le format de sortie).

Types de données

Les données peuvent être définies en utilisant les directives DB (octets) et DW (mots). Les chaînes de caractères peuvent être définies en utilisant des guillemets doubles ou simples.

Les nombres peuvent être spécifiés dans différents formats :

  • Décimal : 123
  • Hexadécimal : $123 ou 0x123
  • Binaire : %101010
  • Octal : &123

Les chaînes de caractères peuvent contenir des séquences d'échappement, telles que \n pour une nouvelle ligne, \t pour une tabulation, \" pour un guillemet double, \' pour un guillemet simple, et \\ pour une barre oblique inverse.

Assemblage conditionnel

L'assembleur rgbasm prend en charge l'assemblage conditionnel à l'aide des directives IF, ELSE et ENDIF. Cela permet d'inclure ou d'exclure du code en fonction de certaines conditions définies lors de l'assemblage.

DEF DEBUG EQ 1

IF DEBUG
    PRINTLN "Mode débogage activé."
ENDIF

IF !DEBUG
    PRINTLN "Mode débogage désactivé."
ENDIF

EXPRESSIONS

Une expression peut être composée de nombreuses choses. Les expressions numériques sont toujours évaluées en utilisant des calculs signés sur 32 bits. Zéro est considéré comme le seul nombre « faux », tous les nombres non nuls (y compris les négatifs) sont « vrais ».

Une expression est dite « constante » si rgbasm connaît sa valeur. C'est généralement toujours le cas, sauf lorsqu'une étiquette est impliquée, comme expliqué dans la section SYMBOLS. Cependant, certains opérateurs peuvent être constants même avec des opérandes non constants, comme expliqué dans la section Opérateurs ci-dessous.

Les instructions du langage macro nécessitent généralement des expressions constantes.

Formats numériques

Il existe un certain nombre de formats numériques.

Les underscores sont également acceptés dans les nombres, sauf au début. Cela peut être utile pour grouper les chiffres, comme ‘123_456’ ou ‘%1100_1001’.

La forme « constante caractère » donne la valeur à laquelle le caractère correspond dans la charmap actuelle. Par exemple, par défaut (voir ascii(7)), ‘'A'’ donne 65. Une constante caractère doit représenter une seule valeur, elle ne peut donc pas contenir plusieurs caractères, ni des caractères qui correspondent à plusieurs valeurs. Vous pouvez également utiliser des symboles, qui sont implicitement remplacés par leur valeur.

‘**’ élève un nombre à une puissance non négative. C'est le seul opérateur associatif à droite, ce qui signifie que ‘p ** q ** r’ est égal à ‘p ** (q ** r)’, et non à ‘(p ** q) ** r’. Tous les autres opérateurs binaires sont associatifs à gauche.

‘~’ complète une valeur en inversant ses 32 bits.

‘%’ est utilisé pour obtenir le reste de la division correspondante, de sorte que ‘x / y * y + x % y == x’ soit toujours vrai. Le résultat a le même signe que le diviseur. Cela rend ‘x % y’ égal à ‘(x + y) % y’ ou ‘(x - y) % y’.

Le décalage fonctionne en décalant tous les bits de l'opérande gauche soit vers la gauche (‘<<’) soit vers la droite (‘>>’) du nombre de décalage de l'opérande droit. Lors d'un décalage à gauche, tous les bits nouvellement insérés sont remis à zéro ; lors d'un décalage à droite, ce sont des copies du bit le plus significatif original. Cela rend ‘a << b’ et ‘a >> b’ équivalents à multiplier et diviser par 2 à la puissance de b, respectivement.

Les opérateurs de comparaison retournent 0 si la comparaison est fausse, et 1 sinon.

Contrairement à de nombreux autres langages, et pour des raisons techniques, rgbasm évalue toujours les deux opérandes de ‘&&’ et ‘||’.

Les opérateurs ‘&&’ et ‘&’ avec une constante zéro comme l'un des opérandes vaudront 0, et ‘||’ avec une constante non nulle comme l'un des opérandes vaudra 1, même si l'autre opérande est non constant.

‘!’ retourne 1 si l'opérande était 0, et 0 sinon. Même un opérande non constant avec des bits non nuls retournera 0.

Fonctions entières

En plus des opérateurs, il existe également des fonctions qui ont des usages plus spécialisés.

Expressions en virgule fixe

Les nombres en virgule fixe sont techniquement des entiers, mais conceptuellement ils ont un point décimal à un emplacement fixe (d'où leur nom). Cela leur confère une précision accrue, au détriment d'une plage plus petite, tout en restant beaucoup moins coûteux à manipuler que les nombres à virgule flottante (que rgbasm ne prend pas en charge).

La précision par défaut de tous les nombres en virgule fixe est de 16 bits, ce qui signifie que les 16 bits inférieurs sont utilisés pour la partie fractionnaire ; ils comptent donc par 65536èmes de 1.0. Cette précision peut être modifiée avec l'option de ligne de commande -Q, et/ou avec OPT Q (voir Changement des options pendant l'assemblage). Une littéral de virgule fixe individuelle peut spécifier sa propre précision, remplaçant la valeur par défaut actuelle, en ajoutant un « q » suivi du nombre de bits fractionnaires : par exemple, ‘1234.5q8’ est égal à $0004d2_80 ( =1234.5*28 ).

Comme les valeurs en virgule fixe ne sont toujours que des entiers, vous pouvez les utiliser dans des expressions entières normales. Vous pouvez facilement tronquer un nombre en virgule fixe en un entier en le décalant vers la droite du nombre de bits fractionnaires. Il s'ensuit que vous pouvez convertir un entier en un nombre en virgule fixe en le décalant vers la gauche du même montant.

Notez que le nombre actuel de bits fractionnaires peut être calculé comme TZCOUNT(1.0).

Les fonctions suivantes sont conçues pour fonctionner avec des nombres en virgule fixe :

Nom Opération
DIV(x, y) Division en virgule fixe
MUL(x, y) Multiplication en virgule fixe
FMOD(x, y) Modulo en virgule fixe
POW(x, y) xy
LOG(x, y) Logarithme de x en base y
ROUND(x) Arrondir x à l'entier le plus proche
CEIL(x) Arrondir x vers le haut à l'entier le plus proche
FLOOR(x) Arrondir x vers le bas à l'entier le plus proche
SIN(x) Sinus de x
COS(x) Cosinus de x
TAN(x) Tangente de x
ASIN(x) Sinus inverse de x
ACOS(x) Cosinus inverse de x
ATAN(x) Tangente inverse de x
ATAN2(y, x) Angle entre (x,y) et (1,0)

Il n'y a pas de fonctions pour l'addition et la soustraction en virgule fixe, car les opérateurs « + » et « - » peuvent ajouter et soustraire des paires d'opérandes en virgule fixe.

Notez que certains opérateurs ou fonctions sont significatifs lors de la combinaison d'entiers et de valeurs en virgule fixe. Par exemple, ‘2.0 * 3’ est équivalent à ‘MUL(2.0, 3.0)’, et ‘6.0 / 2’ est équivalent à ‘DIV(6.0, 2.0)’. Soyez prudent et réfléchissez à la signification des opérations lorsque vous faites ce genre de choses.

Toutes ces fonctions en virgule fixe peuvent prendre un argument final optionnel, qui est la précision à utiliser pour cette seule opération. Par exemple, ‘MUL(6.0q8, 7.0q8, 8)’ sera évalué à ‘42.0q8’>, quelle que soit la valeur définie comme option Q actuelle. rgbasm ne vérifie pas la cohérence des précisions, donc une entrée absurde comme ‘MUL(4.2q8, 6.9q12, 16)’ produira un résultat absurde (mais techniquement correct) : « garbage in, garbage out ».

La fonction FMOD est utilisée pour obtenir le reste de la division en virgule fixe correspondante, de sorte que ‘MUL(DIV(x, y), y) + FMOD(x, y) == x’ soit toujours vrai. Le résultat a le même signe que le dividende ; c'est l'inverse de la façon dont fonctionne l'opérateur modulo entier « % » !

Les fonctions trigonométriques (SIN, COS, TAN, etc) sont définies en termes d'un cercle divisé en 1.0 « tours » (égal à 2π radians, ou 360 degrés).

Ces fonctions sont utiles pour la génération automatique de diverses tables. Par exemple :

; Générer une table de 128 valeurs de sinus
; de sin(0.0) à sin(0.5) exclus,
; avec une amplitude mise à l'échelle de [-1.0, 1.0] à [0.0, 128.0].
FOR angle, 0.0, 0.5, 0.5 / 128
    db MUL(SIN(angle) + 1.0, 128.0 / 2) >> 16
ENDR

Expressions de chaîne

L'expression de chaîne la plus basique est n'importe quelle séquence de caractères contenue entre guillemets doubles (‘"par exemple"’). Le caractère antislash ‘\’ est spécial car il fait que le caractère qui le suit est « échappé », ce qui signifie qu'il est traité différemment de la normale. Il existe un certain nombre de séquences d'échappement que vous pouvez utiliser dans une chaîne :

Séquence Signification
‘\\’ Antislash (échappe le caractère d'échappement lui-même)
‘\"’ Guillemet double (ne termine pas une chaîne)
‘\'’ Guillemet simple (ne termine pas un littéral de caractère)
‘\{’ Accolade ouvrante (ne commence pas l'interpolation)
‘\}’ Accolade fermante (ne termine pas l'interpolation)
‘\n’ Nouvelle ligne (ASCII $0A)
‘\r’ Retour chariot (ASCII $0D)
‘\t’ Tabulation (ASCII $09)
‘\0’ Nul (ASCII $00)

Les chaînes multilignes sont contenues entre triple guillemets (‘"""par exemple"""’). Les séquences d'échappement fonctionnent de la même manière dans les chaînes multilignes ; cependant, les caractères de nouvelle ligne littéraux seront inclus tels quels, sans avoir besoinpour s'en échapper avec ‘\r’ ou ‘\n’.

Les chaînes brutes sont préfixées par un hash ‘#’. À l'intérieur, les antislahs et les accolades sont traités comme des caractères ordinaires, ils ne seront donc pas développés en arguments de macro, interpolés en symboles ou interprétés comme des séquences d'échappement. Par exemple, la chaîne brute ‘#"\t\1{s}\"’ est équivalente à la chaîne ordinaire ‘"\\t\\1\{s}\\"’. (Notez que cela empêche les chaînes brutes d'inclure le caractère guillemet double.) Les chaînes brutes peuvent également être délimitées par des triples guillemets pour être multilignes, elles peuvent donc inclure des caractères de nouvelle ligne ou de guillemet littéraux (bien que toujours pas trois guillemets de suite).

Vous pouvez utiliser l'opérateur ‘++’ pour concaténer deux chaînes. ‘"str" ++ "ing"’ est équivalent à ‘"string"’, ou à ‘STRCAT("str", "ing")’.

Tables de caractères

Lors de l'écriture de chaînes de caractères destinées à être affichées sur la Game Boy, le codage des caractères dans la ROM peut devoir être différent du codage du fichier source. Par exemple, les tuiles utilisées pour les lettres majuscules peuvent être placées à partir de l'indice de tuile 128, ce qui diffère de l'ASCII qui commence à 65.

Les tables de caractères permettent de mapper des chaînes à des séquences arbitraires de nombres :

CHARMAP "A", 42
CHARMAP ":)", 39
CHARMAP "<br>", 13, 10
CHARMAP "&euro;", $20ac

Cela aurait pour effet que ‘db "Amen :)<br>"’ soit équivalent à ‘db 42, 109, 101, 110, 32, 39, 13, 10’, et que ‘dw "25&euro;"’ soit équivalent à ‘dw 50, 53, $20ac’.

Tous les caractères d'une chaîne sans mappages définis seront copiés directement, en utilisant le codage des caractères en octets du fichier source.

Il est possible de créer plusieurs tables de caractères, puis de passer de l'une à l'autre selon les besoins. Cela peut être utilisé, par exemple, pour coder des informations de débogage en ASCII et utiliser un codage différent pour d'autres finalités. Initialement, il existe une table de caractères appelée ‘main’ et elle est automatiquement sélectionnée comme table de caractères actuelle dès le début. Il existe également une pile de tables de caractères qui peut être utilisée pour sauvegarder et restaurer la table de caractères actuellement active.

Commande Signification

NEWCHARMAP nom, nom_base Crée une nouvelle table de caractères appelée nom, copiée de la table de caractères nom_base, et bascule dessus.
SETCHARMAP nom Bascule sur la table de caractères nom.
PUSHC Pousse la table de caractères actuelle sur la pile.
PUSHC nom Pousse la table de caractères actuelle sur la pile et bascule sur la table de caractères nom.
POPC Dépile une table de caractères et bascule dessus.

Note : Les modifications apportées à une table de caractères prennent effet immédiatement à partir de ce moment-là.

SECTIONS

Avant de pouvoir commencer à écrire du code, vous devez définir une section. Cela indique à l'assembleur le type d'informations qui suit et, s'il s'agit de code, où le placer.

SECTION nom, type
SECTION nom, type, options
SECTION nom, type[addr]
SECTION nom, type[addr], options

nom est une chaîne entourée de guillemets doubles, et peut être un nouveau nom ou le nom d'une section existante. Si le type ne correspond pas, une erreur se produit. Toutes les autres sections doivent avoir un nom unique, même dans des fichiers source différents, sinon le lieur considérera cela comme une erreur.

Les types de section possibles sont les suivants :

ROM0
Une section ROM. addr peut aller de $0000 à $3FFF, ou de $0000 à $7FFF si le mode ROM minuscule est activé dans le lieur.
ROMX
Une section ROM bancée. addr peut aller de $4000 à $7FFF. bank peut aller de 1 à 511. Devient un alias pour ROM0 si le mode ROM minuscule est activé dans le lieur.
VRAM
Une section bancée de VRAM. addr peut aller de $8000 à $9FFF. bank peut être 0 ou 1, mais la banque 1 n'est pas disponible si le mode DMG est activé dans le lieur.
SRAM
Une section bancée de RAM externe (de sauvegarde). addr peut aller de $A000 à $BFFF. bank peut aller de 0 à 15.
WRAM0
Une section RAM à usage général. addr peut aller de $C000 à $CFFF, ou de $C000 à $DFFF si le mode WRAM0 est activé dans le lieur.
WRAMX
Une section bancée de RAM à usage général. addr peut aller de $D000 à $DFFF. bank peut aller de 1 à 7. Devient un alias pour WRAM0 si le mode WRAM0 est activé dans le lieur.
OAM
Une section OAM (Object Attribute Memory). addr peut aller de $FE00 à $FE9F.
HRAM
Une section de RAM haute. addr peut aller de $FF80 à $FFFE.

Étant donné que RGBDS produit des ROMs, le code et les données ne peuvent être placés que dans des sections ROM0 et ROMX. Pour en mettre dans la RAM, il faut qu'ils soient stockés dans la ROM, puis copiés dans la RAM.

options sont séparées par des virgules et peuvent inclure :

BANK[bank]
Spécifie dans quelle bank le lieur doit placer la section. Voir ci-dessus pour les valeurs possibles de bank, en fonction du type.
ALIGN[alignement, décalage]
Place la section à une adresse dont les alignement bits les moins significatifs sont égaux
au décalage. Notez que ALIGN[alignement] est un raccourci pour ALIGN[alignement, 0]. Cette option peut être utilisée avec [adresse], tant qu'ils ne se contredisent pas. Il est également possible de demander un alignement au milieu d'une section ; voir Demande d'alignement ci-dessous.

Si [adresse] n'est pas spécifié, la section est considérée comme « flottante » ; l'éditeur de liens calculera automatiquement une adresse appropriée pour la section. De même, si BANK[banque] n'est pas spécifié, l'éditeur de liens trouvera automatiquement une banque avec suffisamment d'espace.

Les sections peuvent également être placées en utilisant un fichier de script d'éditeur de liens. Le format est décrit dans rgblink(5). Ils permettent à l'utilisateur de placer des sections flottantes dans la banque souhaitée dans l'ordre spécifié dans le script. Ceci est utile si les sections ne peuvent pas être placées à une adresse manuellement car leur taille peut changer, mais qu'elles doivent être ensemble.

Exemples de sections :

  • SECTION "Cool Stuff", ROMX

    Cela passe à la section nommée « CoolStuff », la créant si elle n'existe pas déjà. Elle peut se retrouver dans n'importe quelle banque ROM. Le code et les données peuvent suivre.

  • Si nécessaire, l'adresse de base de la section peut être spécifiée : 
    SECTION "Cool Stuff", ROMX[$4567]
  • Un exemple avec une banque fixe : 
    SECTION "Cool Stuff", ROMX[$4567], BANK[3]
  • Et si vous voulez forcer uniquement la banque de la section, et non sa position dans la banque, c'est également possible : 
    SECTION "Cool Stuff", ROMX, BANK[7]
  • Exemples d'alignement : Le premier pourrait être utile pour définir un tampon OAM à transférer par DMA, car il doit être aligné sur 256 octets. Le second pourrait également convenir au HDMA GBC, ou à un code de copie optimisé qui nécessite un alignement. 
    SECTION "OAM Data", WRAM0, ALIGN[8] ; alignement sur 256 octets
SECTION "VRAM Data", ROMX, BANK[2], ALIGN[4] ; alignement sur 16 octets

La section courante peut être terminée sans en démarrer une nouvelle en utilisant ENDSECTION. Cette directive effacera le contexte de la section, vous ne pourrez donc plus écrire de code avant d'en démarrer une autre. Elle peut être utile pour éviter de définir accidentellement du code ou des données dans la mauvaise section.

Pile de sections

POPS et PUSHS fournissent l'interface de la pile de sections. Le nombre d'entrées dans la pile est limité uniquement par la quantité de mémoire de votre machine.

PUSHS empilera le contexte de section actuel sur la pile de sections. POPS pourra ensuite être utilisé plus tard pour le restaurer. Utile pour définir des sections dans des fichiers inclus lorsque vous ne souhaitez pas remplacer le contexte de section au point où le fichier a été inclus.

PUSHS peut également prendre les mêmes arguments que SECTION, afin d'empiler le contexte de section actuel et de définir une nouvelle section en même temps :

SECTION "Code", ROM0
Function:
    ld a, 42
    PUSHS "Variables", WRAM0
        wAnswer: db
    POPS
    ld [wAnswer], a

Code en RAM

Parfois, vous souhaitez avoir du code en RAM. Mais vous ne pouvez pas simplement le placer dans une section RAM, vous devez le stocker en ROM et le copier en RAM à un moment donné.

Cela signifie que le code (ou les données) ne sera pas stocké à l'endroit où il sera exécuté. Heureusement, les blocs LOAD sont la solution parfaite pour cela. Voici un exemple d'utilisation :

SECTION "LOAD example", ROMX
CopyCode:
    ld de, RAMCode
    ld hl, RAMLocation
    ld c, RAMCode.end - RAMCode
.loop
    ld a, [de]
    inc de
    ld [hli], a
    dec c
    jr nz, .loop
    ret

RAMCode:
  LOAD "RAM code", WRAM0
RAMLocation:
    ld hl, .string
    ld de, $9864
.copy
    ld a, [hli]
    ld [de], a
    inc de
    and a
    jr nz, .copy
    ret

.string
    db "Hello World!\0"
  ENDL
.end

Un bloc LOAD ressemble à une déclaration SECTION car il en crée une nouvelle. Toutes les données et le code générés dans un tel bloc sont placés dans la section actuelle comme d'habitude, mais toutes les étiquettes sont créées comme si elles étaient placées dans cette nouvelle section.

Dans l'exemple ci-dessus, tout le code et les données se retrouveront dans la section « LOAD example ». Vous remarquerez les étiquettes « RAMCode » et « RAMLocation ». La première est située en ROM, où le code est stocké, la seconde en RAM, où le code sera chargé.

Vous ne pouvez pas imbriquer de blocs LOAD, ni modifier ou arrêter la section actuelle à l'intérieur de ceux-ci.

Le bloc LOAD actuel peut être terminé en utilisant ENDL. Cette directive n'est nécessaire que si vous souhaitez reprendre l'écriture de code dans sa section ROM parente. N'importe laquelle des directives LOAD, SECTION, ENDSECTION, ou POPS terminera le bloc LOAD actuel avant d'exécuter sa propre fonction.

Les blocs LOAD peuvent utiliser les modificateurs UNION ou FRAGMENT comme décrit dans Sections unionisées ci-dessous.

Sections unionisées

Lorsque vous manquez de RAM, vous voudrez peut-être définir des allocations de mémoire statiques qui se chevauchent, comme expliqué dans la section Allocation d'espaces qui se chevauchent en RAM. Cependant, une UNION ne fonctionne qu'au sein d'un seul fichier, elle ne peut donc pas être utilisée, par exemple, pour définir des variables temporaires dans plusieurs fichiers, qui utilisent tous la même mémoire allouée statiquement. Les sections unionisées résolvent ce problème. Pour déclarer une section unionisée, ajoutez le mot-clé UNION après celui de SECTION ; la déclaration n'est sinon pas différente. Les sections unionisées suivent quelques règles différentes des sections normales :

  • La même section unionisée (c'est-à-dire portant le même nom) peut être déclarée plusieurs fois par invocation de rgbasm, et au cours de plusieurs invocations. Les différentes déclarations sont traitées et fusionnées de manière identique, que ce soit au sein de la même invocation ou d'invocations différentes.
  • Si une section a été déclarée comme unionisée, toutes les sections portant le même nom doivent également être déclarées comme unionisées.
  • Toutes les déclarations doivent avoir le même type. Par exemple, même si le drapeau -w de rgblink(1) est utilisé, les types WRAM0 et WRAMX sont toujours considérés comme différents.
  • Des contraintes différentes (alignement, banque, etc.) peuvent être spécifiées pour chaque déclaration de section unionisée, mais elles doivent toutes être compatibles. Par exemple, l'alignement doit être compatible avec toute adresse fixe, toutes les banques spécifiées doivent être identiques, etc.
  • Les sections unionisées ne peuvent pas avoir le type ROM0 ou ROMX.

Les différentes déclarations de la même section unionisée ne sont pas ajoutées, mais se superposent, tout comme dans Allocation d'espaces qui se chevauchent en RAM. De même, la taille d'une section unionisée est la plus grande de toutes ses déclarations.

Fragments de section

Les fragments de section sont des sections avec une petite particularité : lorsque plusieurs sections portant le même nom sont rencontrées, elles sont concaténées au lieu de produire une erreur. Cela fonctionne au sein du même fichier (parallèlement au comportement des sections « simples » dans les versions précédentes), mais aussi entre les fichiers objet. Pour déclarer un fragment de section, ajoutez le mot-clé FRAGMENT après celui de SECTION ; la déclaration n'est sinon pas différente. Cependant, de manière similaire aux Sections unionisées, certaines règles doivent être respectées :

  • Si une section a été déclarée comme fragment, toutes les sections portant le même nom doivent également être déclarées comme fragments.
  • Toutes les déclarations doivent avoir le même type. Par exemple, même si le drapeau -w de rgblink(1) est utilisé, les types WRAM0 et WRAMX sont toujours considérés comme différents.
  • Des contraintes différentes (alignement, banque, etc.) peuvent être spécifiées pour chaque déclaration de fragment de section, mais elles doivent toutes être compatibles. Par exemple, l'alignement doit être compatible avec toute adresse fixe, toutes les banques spécifiées doivent être identiques, etc.
  • Un fragment de section ne peut pas être unionisé ; après tout, cela n'aurait pas beaucoup de sens.

Lorsque RGBASM fusionne deux fragments, celui rencontré plus tard est ajouté à celui rencontré précédemment.

Lorsque RGBLINK fusionne deux fragments, celui dont le fichier a été spécifié en dernier est ajouté à celui dont le fichier a été spécifié en premier. Par exemple, en supposant que « bar.o », « baz.o » et « foo.o » contiennent tous un fragment portant le même nom, la commande

rgblink -o rom.gb baz.o foo.o bar.o
produirait d'abord le fragment de « baz.o », suivi de celui de « foo.o », et enfin celui de « bar.o ».

Littéraux de fragment

Les littéraux de fragment sont utiles pour de courts blocs de code ou de données qui ne sont référencés qu'une seule fois. Ce sont des fragments de section créés en entourant des instructions ou des directives de crochets doubles « [[ » et « ]] », sans SECTION FRAGMENT distinct

/code> déclaration.

Le contenu d'une littéral de fragment devient une SECTION FRAGMENT, partageant le même nom et la même banque que sa section ROM parente, mais sans aucune autre contrainte. La section parente devient également un FRAGMENT si elle n'en était pas déjà un, de sorte qu'elle puisse être fusionnée avec ses littéraux de fragment. RGBLINK fusionne les fragments dans un ordre quelconque.

Un littéral de fragment peut remplacer n'importe quelle constante entière de 16 bits ‘n16’ de la documentation gbz80(7), ainsi qu'un élément DW. Le littéral de fragment évalue ensuite à son adresse de départ. Par exemple, vous pouvez CALL ou JP vers un littéral de fragment.

Ce code utilisant des étiquettes nommées :

DataTable:
    dw First
    dw Second
    dw Third
First:  db 1
Second: db 4
Third:  db 9
Routine:
    push hl
    ld hl, Left
    jr z, .got_it
    ld hl, Right
.got_it
    call .print
    pop hl
    ret
.print:
    ld de, $1003
    ld bc, STARTOF(VRAM)
    jp Print
Left:  db "left\0"
Right: db "right\0"

est équivalent à ce code utilisant des littéraux de fragment :

DataTable:
    dw [[ db 1 ]]
    dw [[ db 4 ]]
    dw [[ db 9 ]]
Routine:
    push hl
    ld hl, [[ db "left\0" ]]
    jr z, .got_it
    ld hl, [[ db "right\0" ]]
.got_it
    call [[
        ld de, $1003
        ld bc, STARTOF(VRAM)
        jp Print
    ]]
    pop hl
    ret

La différence est que l'exemple utilisant des littéraux de fragment ne déclare pas d'ordre particulier pour ses morceaux.

Les littéraux de fragment peuvent être imbriqués arbitrairement, de sorte que des cas d'utilisation extrêmes sont techniquement possibles. Ce code utilisant des étiquettes nommées :

dw FortyTwo
FortyTwo:
    call Sub1
    jr Sub2
Sub1:
    ld a, [Twenty]
    ret
Twenty: db 20
Sub2:
    jp Sub3
Sub3:
    call Sub1
    inc a
    add a
    ret

est équivalent à ce code utilisant des littéraux de fragment :

dw [[
    call [[
        Sub1: ld a, [ [[db 20]] ] :: ret
    ]]
    jr [[
        jp [[ call Sub1 :: inc a :: add a :: ret ]]
    ]]
]]

SYMBOLS

RGBDS prend en charge plusieurs types de symboles :

Étiquette
Symbole numérique désignant un emplacement mémoire. Peut ou non avoir une valeur connue au moment de l'assemblage.
Constante
Symbole numérique dont la valeur doit être connue au moment de l'assemblage.
Macro
Un bloc de code rgbasm qui peut être appelé ultérieurement.
Chaîne
Une chaîne de texte qui peut être développée ultérieurement, de manière similaire à une macro.

Les noms de symboles peuvent contenir des lettres ASCII, des chiffres, des underscores ‘_’, des dièses ‘#’, des signes dollar ‘$’, et des arrobes ‘@’. Cependant, ils doivent commencer par une lettre ou un underscore. De plus, les noms d'étiquettes peuvent contenir jusqu'à un seul point ‘.’, qui ne peut pas être le premier caractère.

Un symbole ne peut pas avoir le même nom qu'un mot-clé réservé, sauf si son nom est un « identifiant brut » préfixé par un dièse ‘#’. Par exemple, ‘#load’ désigne un symbole nommé ‘load’, et ‘#LOAD’ désigne un symbole différent nommé ‘LOAD’ ; dans les deux cas, le ‘#’ les empêche d'être traités comme le mot-clé LOAD.

Étiquettes

Une des tâches principales de l'assembleur est de suivre les adresses pour vous, afin que vous puissiez travailler avec des noms significatifs au lieu de nombres « magiques ». Les étiquettes permettent cela : une étiquette associe un nom à un emplacement spécifique dans une section. Une étiquette se résout en une banque et une adresse, déterminées en même temps que celles de sa section parente (voir plus loin dans cette section).

Une étiquette est définie en écrivant son nom au début d'une ligne, suivi d'un ou deux points-virgules, sans espace entre le nom de l'étiquette et le(s) point(s)-virgule. Déclarer une étiquette (globale ou locale) avec deux points-virgules ‘::’ la définira et l'EXPORTera en même temps. (Voir Exportation et importation de symboles ci-dessous). Lors de la définition d'une étiquette locale, le point-virgule peut être omis, et rgbasm agira comme s'il n'y en avait qu'un seul.

Une étiquette est dite locale si son nom contient un point ‘.’ ; sinon, elle est dite globale (à ne pas confondre avec « exportée », expliqué dans Exportation et importation de symboles ci-dessous). Plus d'un point dans les noms d'étiquettes n'est pas autorisé.

Par commodité, les étiquettes locales peuvent utiliser une syntaxe abrégée : lorsqu'un nom de symbole commençant par un point est trouvé (par exemple, à l'intérieur d'une expression, ou lors de la définition d'une étiquette), alors la « portée d'étiquette » actuelle est implicitement préfixée.

Définir une étiquette globale la définit comme la « portée d'étiquette » actuelle, jusqu'à la prochaine définition d'étiquette globale, ou la fin de la section actuelle.

Voici quelques exemples de définitions d'étiquettes :

GlobalLabel:
AnotherGlobal:
.locallabel ; Ceci définit "AnotherGlobal.locallabel"
.another_local:
AnotherGlobal.with_another_local:
ThisWillBeExported:: ; Notez les deux points-virgules
ThisWillBeExported.too::

Dans une expression numérique, une étiquette évalue à son adresse en mémoire. (Pour obtenir sa banque, utilisez la fonction ‘BANK()’ décrite dans Autres fonctions). Par exemple, étant donné ce qui suit, ‘ld de, vPlayerTiles’ serait équivalent à ‘ld de, $80C0’ en supposant que la section se retrouve à $80C0 :

SECTION "Player tiles", VRAM
vPlayerTiles:
    ds 6 * 16
.end

L'emplacement (et donc la valeur) d'une étiquette n'est généralement pas déterminé avant l'étape de liaison, de sorte que les étiquettes ne peuvent généralement pas être utilisées comme constantes. Cependant, si la section dans laquelle l'étiquette est définie a une adresse de base fixe, sa valeur est connue au moment de l'assemblage.

De plus, bien que rgbasm puisse évidemment calculer la différence entre deux étiquettes si les deux sont constantes, il est également capable de calculer la différence entre deux étiquettes non constantes si elles appartiennent toutes deux à la même section, comme ‘PlayerTiles’ et ‘PlayerTiles.end’ ci-dessus.

Étiquettes anonymes

Les étiquettes anonymes sont utiles pour de courts blocs de code. Elles sont définies comme des étiquettes normales, mais sans nom avant le point-virgule. Les étiquettes anonymes sont indépendantes des portées d'étiquettes, de sorte que définir une étiquette anonyme ne change pas l'étiquette portée, et référencer une étiquette anonyme n'est pas affecté par l'étiquette portée actuelle.

Les étiquettes anonymes sont référencées en utilisant un point-virgule ‘:’ suivi de plus ‘+’ ou de moins ‘-’. Ainsi :+ référence la prochaine après l'expression, :++ celle d'après ; :- référence celle avant l'expression ; et ainsi de suite.

    ld hl, :++
:   ld a, [hli] ; référencé par "jr nz"
    ldh [c], a
    dec c
    jr nz, :-
    ret

:   ; référencé par "ld hl"
    dw $7FFF, $1061, $03E0, $58A5

Variables

Un signe égal ‘=’ est utilisé pour définir des symboles numériques mutables. Contrairement aux autres symboles décrits ci-dessous, les variables peuvent être redéfinies. Ceci est utile pour les symboles internes dans les macros, pour les compteurs, etc.

DEF ARRAY_SIZE EQU 4
DEF COUNT = 2
DEF COUNT = 3
DEF COUNT = ARRAY_SIZE + COUNT
DEF COUNT *= 2
; COUNT a maintenant la valeur 14

Notez que les points-virgules ‘:’ suivant le nom ne sont pas autorisés.

Les variables peuvent être redéfinies de manière pratique par des opérateurs d'affectation composée comme en C :

Opérateur Signification
+= -= Plus/moins composé
*= /= %= Multiplication/division/modulo composé
<<= >>= Décalage gauche/droit composé
&= |= ^= Et/ou/xor composé

Exemples :

DEF x = 10
DEF x += 1    ; x == 11
DEF y = x - 1 ; y == 10
DEF y *= 2    ; y == 20
DEF y >>= 1   ; y == 10
DEF x ^= y    ; x == 1

Déclarer une variable avec EXPORT DEF ou EXPORT REDEF la définira et l'EXPORTera en même temps. (Voir Exportation et importation de symboles ci-dessous).

Constantes numériques

EQU est utilisé pour définir des symboles constants numériques. Contrairement à ‘=’ ci-dessus, les constantes définies de cette manière ne peuvent pas être redéfinies. Ces constantes peuvent être utilisées pour des valeurs immuables telles que les propriétés du matériel.

def SCREEN_WIDTH  equ 160 ; En pixels
def SCREEN_HEIGHT equ 144

Notez que les deux-points ‘:’ suivant le nom ne sont pas autorisés.

Si vous en avez vraiment besoin, le mot-clé REDEF définira ou redéfinira une constante numérique symbolique. (Il peut aussi être utilisé pour les variables, bien que ce ne soit pas nécessaire car elles sont mutables.) Ceci peut être utilisé, par exemple, pour mettre à jour une constante à l'aide d'une macro, sans la rendre mutable en général.

    def NUM_ITEMS equ 0
MACRO add_item
    redef NUM_ITEMS equ NUM_ITEMS + 1
    def ITEM_{02x:NUM_ITEMS} equ \1
ENDM
    add_item 1
    add_item 4
    add_item 9
    add_item 16
    assert NUM_ITEMS == 4
    assert ITEM_04 == 16

Déclarer une constante numérique avec EXPORT DEF ou EXPORT REDEF la définira et l'EXPORTera en même temps. (Voir Exportation et importation de symboles ci-dessous).

Constantes d'offset

Le groupe de commandes RS est un moyen pratique de définir des offsets de structures :

               RSRESET
DEF str_pStuff RW   1
DEF str_tData  RB   256
DEF str_bCount RB   1
DEF str_SIZEOF RB   0

L'exemple définit quatre constantes comme si elles étaient définies par :

DEF str_pStuff EQU 0
DEF str_tData  EQU 2
DEF str_bCount EQU 258
DEF str_SIZEOF EQU 259

Il y a cinq commandes dans le groupe de commandes RS :

Commande Signification
RSRESET Équivalent à ‘RSSET 0’.
RSSET constexpr Définit le compteur _RS à constexpr.
DEF nom RB constexpr Définit nom à _RS puis ajoute constexpr à _RS.
DEF nom RW constexpr Définit nom à _RS puis ajoute constexpr * 2 à _RS.
DEF nom RL constexpr Définit nom à _RS puis ajoute constexpr * 4 à _RS.

Si l'argument constexpr à RB, RW ou RL est omis, il est supposé être 1.

Notez que les deux-points ‘:’ suivant le nom ne sont pas autorisés.

Déclarer une constante d'offset avec EXPORT DEF la définira et l'EXPORTera en même temps. (Voir Exportation et importation de symboles ci-dessous).

Constantes de chaînes

EQUS est utilisé pour définir des symboles de constantes de chaînes. Partout où l'assembleur lit une constante de chaîne, elle est développée : le nom du symbole est remplacé par son contenu, de manière similaire à #define dans le langage de programmation C. Ce développement est désactivé dans quelques contextes : ‘DEF(name)’, ‘DEF name EQU/=/EQUS/etc ...’, ‘PURGE name’, et ‘MACRO name’ ne développeront pas les constantes de chaînes dans leurs noms. Le développement est également désactivé si le nom de la constante de chaîne est un identifiant brut précédé d'un dièse ‘#’.

DEF COUNTREG EQUS "[hl+]"
    ld a, COUNTREG

DEF PLAYER_NAME EQUS "\"John\""
    db PLAYER_NAME

Ceci sera interprété comme :

ld a, [hl+]
db "John"

Les constantes de chaînes peuvent également être utilisées pour définir de petites macros sur une seule ligne :

DEF pusha EQUS "push af\npush bc\npush de\npush hl\n"

Notez que les deux-points ‘:’ suivant le nom ne sont pas autorisés.

Les constantes de chaînes, comme les constantes numériques, ne peuvent pas être redéfinies. Cependant, le mot-clé REDEF définira ou redéfinira une constante de chaîne symbolique. Par exemple :

DEF s EQUS "Hello, "
REDEF s EQUS "{s}world!"
; imprime "Hello, world!"
PRINTLN "{s}\n"

Les constantes de chaînes ne peuvent pas être exportées ou importées.

Note importante : Lorsqu'une constante de chaîne est développée, son développement peut contenir une autre constante de chaîne, qui sera elle-même développée, et cela peut être récursif. Si cela crée une boucle infinie, rgbasm générera une erreur une fois qu'un certain niveau de profondeur est atteint (voir l'option de ligne de commande -r dans rgbasm(1)). Le même problème peut survenir si le développement d'une constante de chaîne invoque une macro, qui se développe elle-même.

Macros

L'une des meilleures caractéristiques d'un assembleur est la possibilité d'écrire des macros pour lui. Les macros peuvent être appelées avec des arguments et peuvent réagir en fonction des entrées à l'aide de constructions IF.

MACRO my_macro
    ld a, 80
    call MyFunc
ENDM

L'exemple ci-dessus définit ‘my_macro’ comme une nouvelle macro. Les constantes de chaînes ne sont pas développées dans le nom de la macro.

Les macros ne peuvent pas être exportées ou importées.

La définition imbriquée de macros n'est pas possible, donc ceci ne fonctionnera pas :

MACRO outer
    MACRO inner
        PRINTLN "Hello!"
    ENDM ; ceci termine en fait la macro 'outer'...
ENDM     ; ...et ensuite ceci est une erreur de syntaxe !

Mais vous pouvez contourner cette limitation en utilisant EQUS, donc ceci fonctionnera :

MACRO outer
    DEF definition EQUS "MACRO inner\nPRINTLN \"Hello!\"\nENDM"
    definition
    PURGE definition
ENDM

Plus d'informations sur la façon de définir et d'appeler des macros sont décrites dans LE LANGAGE DES MACROS ci-dessous.

Exportation et importation de symboles

L'importation et l'exportation de symboles sont des fonctionnalités très utiles lorsque votre projet s'étend sur plusieurs fichiers source et, par exemple, vous avez besoin de sauter vers une routine définie dans un autre fichier.

L'exportation de symboles doit être effectuée manuellement, l'importation est effectuée automatiquement si rgbasm trouve un symbole qu'il ne connaît pas.

Ce qui suit fera en sorte que symbol1, symbol2 et ainsi de suite soient accessibles à d'autres fichiers pendant le processus de liaison :

EXPORT symbol1 [, symbol2, ...]

Par exemple, si vous avez les trois fichiers suivants :

‘a.asm’ :

SECTION "a", WRAM0
LabelA:

‘b.asm’ :

SECTION "b", WRAM0
ExportedLabelB1::
ExportedLabelB2:
    EXPORT ExportedLabelB2

‘c.asm’ :

SECTION "C", ROM0[0]
    dw LabelA
    dw ExportedLabelB1
    dw ExportedLabelB2

Alors ‘c.asm’ peut utiliser ‘ExportedLabelB1’ et ‘ExportedLabelB2’, mais pas ‘LabelA’, donc les lier ensemble échouera :

$ rgbasm -o a.o a.asm
$ rgbasm -o b.o b.asm
$ rgbasm -o c.o c.asm
$ rgblink a.o b.o c.o
error: c.asm(2): Unknown symbol "LabelA"
Linking failed with 1 error

Notez également que seuls les symboles exportés apparaîtront dans les fichiers de symboles et les fichiers de mappage produits par rgblink(1).

Suppression des symboles

PURGE vous permet de supprimer complètement un symbole de la table des symboles, comme s'il n'avait jamais été défini. Soyez très prudent lors de la suppression de symboles, en particulier les étiquettes, car cela pourrait entraîner des erreurs imprévisibles si quelque chose dépend du symbole manquant (par exemple, des expressions que l'éditeur de liens doit calculer).

DEF Kamikaze EQUS "I don't want to live anymore"
AOLer: DB "Me too lol"
PURGE Kamikaze, AOLer
ASSERT !DEF(Kamikaze) && !DEF(AOLer)

Les constantes de chaînes ne sont pas développées dans les noms de symboles.

Symboles prédéfinis

Les symboles suivants sont définis par l'assembleur :

DÉFINITION DES DONNÉES

Définition de données constantes en ROM

DB définit une liste d'octets qui seront stockés dans l'image finale. Idéal pour les tables et le texte.

DB 1,2,3,4,"Ceci est une chaîne"

Alternativement, vous pouvez utiliser DW pour stocker une liste de mots (16 bits) ou DL pour stocker une liste de doubles mots (32 bits). Les deux écrivent leurs données en ordre d'octets little-endian ; par exemple, ‘dw $CAFE’ est équivalent à ‘db $FE, $CA’ et non ‘db $CA, $FE’.

Les chaînes sont traitées un peu spécialement : elles subissent d'abord une conversion de charmap (voir Charmaps), puis chaque caractère résultant est généré individuellement. Par exemple, sous la charmap par défaut, les deux lignes suivantes sont identiques :

DW "Bonjour!"
DW "B", "o", "n", "j", "o", "u", "r", "!"

Si vous ne souhaitez pas ce traitement spécial, entourez la chaîne de parenthèses.

DS peut également être utilisé pour remplir une région de mémoire avec certaines valeurs répétées. Par exemple :

; génère 3 octets : $AA, $AA, $AA
DS 3, $AA
; génère 7 octets : $BB, $CC, $BB, $CC, $BB, $CC, $BB
DS 7, $BB, $CC

Vous pouvez également utiliser DB, DW et DL sans arguments. Cela fonctionne exactement comme DS 1, DS 2 et DS 4 respectivement. Par conséquent, DB, DW et DL sans argument peuvent être utilisés dans une section WRAM0 / WRAMX / HRAM / VRAM / SRAM.

Inclusion de fichiers de données binaires

Vous avez probablement des graphiques, des données de niveau, etc. que vous aimeriez inclure. Utilisez INCBIN pour inclure un fichier binaire brut tel quel. Si le fichier n'est pas trouvé dans le répertoire courant, la liste des chemins d'inclusion passée à l'option -I de rgbasm(1) sur la ligne de commande sera recherchée.

INCBIN "titlepic.bin"
INCBIN "sprites/hero.bin"

Vous pouvez également inclure seulement une partie d'un fichier avec INCBIN. L'exemple ci-dessous inclut 256 octets du fichier data.bin, à partir de l'octet 78.

INCBIN "data.bin", 78, 256

L'argument de longueur est optionnel. Si seule la position de départ est spécifiée, les octets depuis la position de départ jusqu'à la fin du fichier seront inclus.

Allocation statique d'espace en RAM

DS alloue statiquement un nombre d'octets vides. C'est la méthode préférée pour allouer de l'espace dans une section RAM. Vous pouvez également utiliser DB, DW et DL sans arguments (voir Définition de données constantes en ROM ci-dessous).

DS 42 ; Alloue 42 octets

L'espace vide dans les sections RAM ne sera pas initialisé. Dans les sections ROM, il sera rempli avec la valeur passée à l'option de ligne de commande -p, sauf lors de l'utilisation d'overlays avec -O.

Au lieu d'un nombre exact d'octets, vous pouvez spécifier ALIGN[align, offset] pour allouer le nombre d'octets requis pour aligner les données suivantes. Ainsi, ‘DS ALIGN[align, offset], ...’ est équivalent à ‘DS n, ...’ suivi de ‘ALIGN[align, offset]’, où n est la valeur minimale nécessaire pour satisfaire la contrainte ALIGN (voir Demande d'alignement ci-dessous). Notez que ALIGN[align] est un raccourci pour ALIGN[align, 0].

Allocation d'espaces RAM qui se chevauchent

Les unions permettent à plusieurs allocations mémoire statiques de se chevaucher, comme les unions en C. Cela n'augmente pas la quantité de mémoire disponible, mais permet de réutiliser la même région mémoire à des fins différentes.

Une union commence par le mot-clé UNION et se termine par le mot-clé ENDU correspondant. NEXTU sépare chaque bloc d'allocations, et vous pouvez l'utiliser autant de fois que nécessaire à l'intérieur d'une union.

; Supposons que PC == $C0DE ici
UNION
    ; Ici, PC == $C0DE
    wName:: ds 10
    ; Non
w, PC == $C0E8 wNickname:: ds 10 ; PC == $C0F2 NEXTU ; PC is back to $C0DE wHealth:: dw ; PC == $C0E0 wLives:: db ; PC == $C0E1 ds 7 ; PC == $C0E8 wBonus:: db ; PC == $C0E9 NEXTU ; PC is back to $C0DE again wVideoBuffer: ds 16 ; PC == $C0EE ENDU ; Afterward, PC == $C0F2

Dans l'exemple ci-dessus, ‘wName, wHealth’, et ‘wVideoBuffer’ ont tous la même valeur ; de même que ‘wNickname’ et ‘wBonus’. Ainsi, gardez à l'esprit que ‘ld [wHealth], a’ s'assemble exactement de la même manière que ‘ld [wName], a’.

La taille totale de cet ensemble d'unions est de 20 octets, la taille du plus grand bloc (le premier, contenant ‘wName’ et ‘wNickname’).

Les unions peuvent être imbriquées, chaque union interne ayant sa taille déterminée comme ci-dessus, et affectant son union externe comme toute autre allocation.

Les unions peuvent être utilisées dans n'importe quelle section, mais elles ne peuvent contenir que des directives d'allocation d'espace comme DS (voir Allocation d'espace statique en RAM).

Demande d'alignement

Bien que ALIGN tel que présenté dans SECTIONS soit souvent utile tel quel, parfois vous voulez plutôt qu'un morceau de données (ou de code) au milieu de la section soit aligné. Ceci est facilité par l'utilisation de ALIGN en milieu de section align, offset. Cela modifiera rétroactivement les attributs de la section pour garantir que l'emplacement où se trouve la directive ALIGN, ait ses bits de poids faible align égaux à offset.

Si la contrainte ne peut être satisfaite (par exemple, parce que la section est fixée à une adresse incompatible), une erreur est produite. Notez que ALIGN align est un raccourci pour ALIGN align, 0.

Il peut arriver que vous ne vouliez pas seulement spécifier une contrainte d'alignement à l'emplacement actuel, mais aussi avancer jusqu'à ce que la contrainte puisse être satisfaite. Dans ce cas, vous pouvez utiliser DS ALIGN[align, offset] pour allouer autant d'octets que nécessaire pour aligner les données suivantes.

Si la contrainte ne peut être satisfaite en sautant un quelconque espace, une erreur est produite. Notez que ALIGN[align] est un raccourci pour ALIGN[align, 0].

LE LANGAGE DES MACROS

Invocation des macros

Une macro est invoquée en utilisant son nom en début de ligne, comme une directive, suivi des arguments séparés par des virgules.

add a, b
ld sp, hl
my_macro      ; Ceci sera développé
sub a, 87
my_macro 42   ; Ceci aussi
ret c
my_macro 1, 2 ; Et ceci aussi

Après que rgbasm ait lu la ligne d'invocation de la macro, il développera le corps de la macro (les lignes entre MACRO et ENDM) à sa place.

Note importante : Lorsqu'un corps de macro est développé, son expansion peut contenir une autre invocation de macro, qui sera également développée, et peut être récursive. Si cela crée une boucle infinie, rgbasm générera une erreur une fois qu'une certaine profondeur est atteinte (voir l'option de ligne de commande -r dans rgbasm(1)). Le même problème peut survenir si l'expansion d'une macro développe ensuite une constante de chaîne, qui s'étend elle-même.

Il est possible de passer également des arguments aux macros !

MACRO lb
    ld \1, (\2) << 8 | (\3)
ENDM
    lb hl, 20, 18        ; Se développe en "ld hl, ((20) << 8) | (18)"
    lb de, 3 + 1, NUM**2 ; Se développe en "ld de, ((3 + 1) << 8) | (NUM**2)"

Vous développez les arguments à l'intérieur du corps de la macro en utilisant les séquences d'échappement \1 à \9, \1 étant le premier argument, \2 le second, et ainsi de suite. Comme il n'y a que neuf chiffres, vous ne pouvez utiliser que les neuf premiers arguments de macro de cette manière. Pour utiliser les suivants, vous mettez le numéro de l'argument entre chevrons, comme \<10>.

Cette syntaxe entre chevrons prend en charge les nombres décimaux et les symboles numériques, où les valeurs négatives comptent à partir du dernier argument. Par exemple, ‘\<_NARG>’ ou ‘\<-1>’ obtiendra le dernier argument.

D'autres arguments de macro et interpolations de symboles seront également développés à l'intérieur des chevrons. Par exemple, si ‘\1’ est ‘13’, alors ‘\<\1>’ à l'intérieur du corps de la macro se développera en ‘\<13>’. Ou si ‘DEF v10 = 42’ et ‘DEF x = 10’, alors ‘\<v{d:x}>’ se développera en ‘\<42>’.

Les arguments de macro sont passés sous forme de constantes de chaîne, bien qu'il n'y ait pas besoin de les entourer de guillemets. Ainsi, les arguments ne sont pas évalués en tant qu'expressions, mais sont plutôt développés directement à l'intérieur du corps de la macro. Cela signifie qu'ils prennent en charge toutes les séquences d'échappement des chaînes (voir Expressions de chaînes ci-dessus), ainsi que certaines de leurs propres séquences :

Séquence Signification
‘\,’ Virgule (ne termine pas l'argument)
‘\(’ Parenthèse ouvrante (ne commence pas l'enfermement du contenu de l'argument)
‘\)’ Parenthèse fermante (ne termine pas l'enfermement du contenu de l'argument)

Les continuations de ligne fonctionnent comme d'habitude à l'intérieur des macros ou des listes d'arguments de macro. Cependant, certains caractères doivent être échappés, comme dans l'exemple suivant :

MACRO PrintMacro1
    PRINTLN STRCAT(\1)
ENDM
    PrintMacro1 "Hello "\, \
                "world"
MACRO PrintMacro2
    PRINT \1
ENDM
    PrintMacro2 STRCAT("Hello ", \
                       "world\n")

La virgule dans ‘PrintMacro1’ doit être échappée pour l'empêcher de commencer un autre argument de macro. La virgule dans ‘PrintMacro2’ n'a pas besoin d'être échappée car elle est entre parenthèses, similaire aux arguments de macro dans le langage de programmation C. La barre oblique inverse dans ‘\n’ n'a pas non plus besoin d'être échappée car les littéraux de chaîne entre guillemets fonctionnent comme d'habitude à l'intérieur des arguments de macro.

Étant donné que les arguments de macro sont développés directement, il est souvent judicieux de les entourer de parenthèses s'ils sont destinés à faire partie d'une expression numérique. Par exemple, considérez ce qui suit :

MACRO print_double
    PRINTLN \1 * 3
ENDM
    print_double 1 + 2

Le corps se développera en ‘PRINTLN 1 + 2 * 3’, ce qui affichera 7 et non 9 comme vous l'auriez peut-être attendu.

La directive SHIFT n'est disponible qu'à l'intérieur des corps de macro. Elle décale les numéros d'arguments vers la gauche, donc ce qui était \2 est maintenant \1, ce qui était \3 est maintenant \2, et ainsi de suite. (Ce qui était \1 n'est plus accessible, donc _NARG est décrémenté de 1.)

SHIFT peut également prendre un paramètre entier pour décaler autant de fois au lieu d'une seule. Un paramètre négatif décale les arguments vers la droite, ce qui permet de retrouver l'accès à ceux précédemment décalés.

SHIFT est particulièrement utile dans les boucles REPT pour itérer sur différents arguments, en évaluant le même corps de boucle à chaque fois.

Il existe quelques séquences d'échappement qui ne sont valides qu'à l'intérieur du corps d'une macro :

Séquence Signification
‘\1’ – ‘\9’ Le 1er au 9ème argument de macro
‘\<...>’ Arguments de macro supplémentaires
‘\#’ Tous les arguments de macro _NARG, séparés par des virgules
‘\@’ Affixe de nom de symbole unique (voir ci-dessous)

La séquence d'échappement \@ est souvent utile dans les macros qui définissent des symboles. Supposons que votre macro se développe en une boucle de code assembleur :

MACRO loop_c_times
    xor a, a
.loop
    ld [hl+], a
    dec c
    jr nz, .loop
ENDM

Si vous utilisez cette macro plus d'une fois dans le même portée d'étiquette, cela définira ‘.loop’ deux fois, ce qui est une erreur. Pour contourner ce problème, vous pouvez utiliser \@ comme suffixe d'étiquette :

MACRO loop_c_times_fixed
    xor a, a
.loop\@
    ld [hl+], a
    dec c
    jr nz, .loop\@
ENDM

Cela se développera en une valeur différente à chaque invocation, similaire à gensym dans le langage de programmation Lisp.

\@ fonctionne également dans les blocs REPT, se développant en une valeur différente à chaque itération.

Blocs de code à répétition automatique

Supposons que vous souhaitiez dérouler une boucle longue sans la copier-coller. REPT est là à cet effet. Tout ce qui se trouve entre REPT et le ENDR correspondant sera répété un certain nombre de fois, comme si vous aviez effectué une opération de copier-coller vous-même. L'exemple suivant assemblera ‘add a, c’ quatre fois :

REPT 4
    add a, c
ENDR

Vous pouvez également utiliser REPT pour générer des tables à la volée :

; Génère une table des valeurs au carré de 0**2 = 0 à 100**2 = 10000
DEF x = 0
REPT 101
    dw x * x
    DEF x += 1
ENDR

Comme dans les macros, vous pouvez également utiliser la séquence d'échappement \@. Les blocs REPT peuvent être imbriqués.

Un modèle courant consiste à répéter un bloc pour chaque valeur d'une certaine plage. FOR est plus simple que REPT à cette fin. Tout ce qui se trouve entre FOR et le ENDR correspondant sera répété pour chaque valeur d'un symbole donné. Les constantes de chaîne ne sont pas développées dans le nom du symbole. Par exemple, ce code produira une table de valeurs au carré de 0 à 255 :

FOR N, 256
    dw N * N
ENDR

Cela agit comme si vous aviez fait :

DEF N = 0
    dw N * N
DEF N = 1
    dw N * N
DEF N = 2
    dw N * N
; ...
DEF N = 255
    dw N * N
DEF N = 256

Vous pouvez personnaliser la plage des valeurs FOR, similaire à la fonction « range » du langage de programmation Python :

Code Plage
FOR V, stop V s'incrémente de 0 à stop
FOR V, start, stop V s'incrémente de start à stop
FOR V, start, stop, step V va de start à stop par pas de step

La valeur FOR sera mise à jour par step jusqu'à ce qu'elle atteigne ou dépasse stop, c'est-à-dire qu'elle couvre la plage semi-ouverte de start (inclus) à stop (exclus). La variable V se verra attribuer cette valeur au début de chaque nouvelle itération ; toute modification apportée à celle-ci dans le corps de la boucle FOR sera écrasée. Ainsi, le symbole V n'a pas besoin d'être déjà défini avant une quelconque itération de la boucle FOR, mais il doit s'agir d'une variable (Variables) si c'est le cas. Par exemple :

FOR V, 4, 25, 5
    PRINT "{d:V} "
    DEF V *= 2
ENDR
    PRINTLN "done {d:V}"

Cela affichera :

4 9 14 19 24 done 29

Comme avec les blocs REPT, vous pouvez utiliser la séquence d'échappement \@ à l'intérieur des blocs FOR, et ceux-ci peuvent être imbriqués.

Vous pouvez arrêter un bloc de répétition avec la commande BREAK. Un BREAK à l'intérieur d'un bloc REPT ou FOR interrompra l'itération en cours et ne répétera plus. Il continuera l'exécution du code après le ENDR du bloc. Par exemple :

FOR V, 1, 100
    PRINT "{d:V}"
    IF V == 5
        PRINT " stop! "
        BREAK
    ENDC
    PRINT ", "
ENDR
    PRINTLN "done {d:V}"

Cela affichera :

1, 2, 3, 4, 5 stop! done 5

Assemblage conditionnel de blocs de code

Les quatre commandes IF, ELIF, ELSE et ENDC permettent à rgbasm de sauter certaines parties de votre code en fonction d'une condition. Il s'agit d'une fonctionnalité puissante couramment utilisée dans les macros.

IF NUM < 0
  PRINTLN "NUM < 0"
ELIF NUM == 0
  PRINTLN "NUM == 0"
ELSE
  PRINTLN "NUM > 0"
ENDC

Les blocs ELIF (pour « else if ») et ELSE sont facultatifs. Les blocs IF / ELIF / ELSE / ENDC peuvent être imbriqués.

Notez que si un bloc ELSE est trouvé avant un bloc ELIF, le bloc ELIF sera ignoré. Tous les blocs ELIF doivent précéder le bloc ELSE. De plus, s'il y a plus d'un bloc ELSE, tous sauf le premier seront ignorés.

Inclusion d'autres fichiers source

Utilisez INCLUDE pour traiter un autre fichier assembleur, puis revenir au fichier actuel une fois terminé. Si le fichier n'est pas trouvé dans le répertoire courant, la liste des chemins d'inclusion passée à l'option -I de rgbasm(1) en ligne de commande sera explorée. Vous pouvez imbriquer les appels INCLUDE à l'infini (ou jusqu'à épuisement de la mémoire, selon ce qui arrive en premier).

INCLUDE "irq.inc"

Vous pouvez également inclure implicitement un fichier avant le fichier source avec l'option -P de rgbasm(1).

Impression de choses pendant l'assemblage

Les commandes PRINT et PRINTLN impriment du texte et des valeurs sur la sortie standard. Utile pour déboguer des macros, ou partout où vous pourriez ressentir le besoin de vous communiquer des informations importantes.

PRINT "Hello world!\n"
PRINTLN "Hello world!"
PRINT _NARG, " arguments\n"
PRINTLN "somme: ", 2+3, " produit: ", 2*3
PRINTLN STRFMT("E = %f", 2.718)
PRINT
imprime chacun de ses arguments séparés par des virgules. Les nombres sont imprimés en hexadécimal sans signe et en majuscules, précédés d'un « $ ». Pour des formats différents, utilisez STRFMT.
PRINTLN
imprime chacun de ses arguments séparés par des virgules, le cas échéant, suivi d'un saut de ligne (« \n »).

Arrêt du processus d'assemblage

FAIL et WARN peuvent être utilisés pour imprimer respectivement des erreurs et des avertissements pendant le processus d'assemblage. C'est particulièrement utile pour les macros qui reçoivent un argument invalide. FAIL et WARN prennent une chaîne de caractères comme seul argument et imprimeront cette chaîne comme une erreur normale avec un numéro de ligne.

FAIL arrête immédiatement l'assemblage, tandis que WARN affiche le message mais continue ensuite.

Si vous avez besoin de vous assurer qu'une hypothèse est correcte lors de la compilation, vous pouvez utiliser ASSERT et STATIC_ASSERT. Des exemples de syntaxe sont donnés ci-dessous :

Function:
    xor a
ASSERT LOW(MyByte) == 0
    ld h, HIGH(MyByte)
    ld l, a
    ld a, [hli]
; Vous pouvez aussi indenter cela !
    ASSERT BANK(OtherFunction) == BANK(Function)
    call OtherFunction
; Les minuscules fonctionnent aussi
    ld hl, FirstByte
    ld a, [hli]
assert FirstByte + 1 == SecondByte
    ld b, [hl]
    ret
.end
    ; Si vous en spécifiez un, un message sera imprimé
    STATIC_ASSERT .end - Function < 256, "La fonction est trop grande !"

Premièrement, la différence entre ASSERT et STATIC_ASSERT est que la première est évaluée par RGBASM si possible, sinon par RGBLINK ; mais la seconde n'est jamais évaluée que par RGBASM. Si RGBASM ne peut pas calculer la valeur de l'argument de STATIC_ASSERT, il produira une erreur.

Deuxièmement, comme montré ci-dessus, une chaîne de caractères peut être facultativement ajoutée à la fin, pour donner un aperçu de ce que l'assertion vérifie.

Enfin, vous pouvez ajouter l'un des mots-clés WARN, FAIL ou FATAL comme premier argument facultatif à ASSERT ou STATIC_ASSERT. Si l'assertion échoue, WARN provoquera un simple avertissement (contrôlé par l'indicateur -Wassert de rgbasm(1)) ; FAIL (par défaut) provoquera une erreur non fatale ; et FATAL arrêtera immédiatement.

Changement d'options pendant l'assemblage

OPT peut être utilisé pour changer certaines des options pendant l'assemblage depuis le code source, au lieu de les définir en ligne de commande. (Voir rgbasm(1)).

OPT prend une liste d'options séparées par des virgules comme argument :

PUSHO
    OPT g.oOX, Wdiv       ; agit comme les commandes -g.oOX -Wdiv
    DW `..ooOOXX          ; utilise les caractères graphiques constants de OPT g
    PRINTLN $80000000/-1  ; imprime un avertissement sur la division
POPO
    DW `00112233          ; utilise les caractères graphiques constants par défaut
    PRINTLN $80000000/-1  ; pas d'avertissement par défaut

OPT peut modifier les options b, g, p, Q, r, et W.

POPO et PUSHO fournissent l'interface à la pile d'options. PUSHO empilera l'ensemble actuel des options sur la pile d'options. POPO pourra ensuite être utilisé pour les restaurer. Utile si vous souhaitez modifier certaines options dans un fichier inclus et que vous ne voulez pas détruire les options définies par le programme qui a inclus votre fichier. Le nombre d'entrées de la pile est limité uniquement par la quantité de mémoire de votre machine.

PUSHO peut également prendre une liste d'options séparées par des virgules, pour empiler l'ensemble actuel et appliquer l'ensemble d'arguments en même temps :

PUSHO b.X, g.oOX
    DB %..XXXX..
    DW `..ooOOXX
POPO
