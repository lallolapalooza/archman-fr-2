YAZ-ZTEST(8) Commandes de gestion du système YAZ-ZTEST(8)

NOM

yaz-ztest - Serveur de test Z39.50/SRU

SYNTAXE

application [-install] [-installa] [-remove] [-a fichier] [-v niveau] [-l fichier] [-u uid] [-c config] [-f vconfig] [-C fname] [-t minutes] [-k kilooctets] [-K] [-d daemon] [-w rép] [-p pidfile] [-r kilooctets] [-ziDSTV1] [spécificateur-écouteur...]

DESCRIPTION

yaz-ztest est un serveur de test Z39.50/SRU qui utilise l'API générique YAZ de serveur frontal (GFS). Le serveur agit comme un véritable serveur Z39.50/SRU mais n'utilise pas de base de données. Il retourne un nombre aléatoire de résultats et renvoie un sous-ensemble de quelques enregistrements intégrés.

Le spécificateur-écouteur se compose d'un mode de transport suivi d'un deux-points, puis d'une adresse d'écoute. Le mode de transport est soit tcp, unix, soit ssl.

Pour TCP et SSL, une adresse a la forme :

    nom-hôte | numéro-IP [ : numéro-port ]

Pour les sockets locaux UNIX, l'adresse est le nom de fichier du socket local.

OPTIONS

-a fichier

Spécifie un fichier pour le vidage des PDU (à des fins de diagnostic). Le nom spécial - (tiret) envoie la sortie vers stderr.

-S

Ne pas créer de processus fils (fork) ni de threads lors des demandes de connexion. Ceci est utile pour le débogage, mais non recommandé pour une utilisation réelle : bien que le serveur soit asynchrone et non bloquant, il peut être utile d'éviter qu'un dysfonctionnement logiciel (d'accord, un crash) n'affecte tous les utilisateurs actuels.

-1

Comme -S mais après une session, le serveur se termine. Ce mode est réservé au débogage uniquement.

-T

Fait fonctionner le serveur en mode thread. Le serveur crée un thread pour chaque connexion au lieu de créer un processus fils. Uniquement disponible sur les systèmes UNIX qui offrent des threads POSIX.

-s

Utilise le protocole SR (obsolète).

-z

Utilise le protocole Z39.50 (par défaut). Cette option et -s se complètent. Vous pouvez utiliser les deux plusieurs fois sur la même ligne de commande, entre les spécificateurs d'écouteur (voir ci-dessous). Ainsi, vous pouvez configurer le serveur pour écouter les connexions dans les deux protocoles simultanément, sur différents ports locaux.

-l fichier

Le fichier journal.

-c config

Une option utilisateur qui sert de spécificateur pour une sorte de configuration, généralement un nom de fichier. L'argument de cette option est transféré au membre configname du bloc statserv_options_block.

-f vconfig

Ceci spécifie un fichier XML qui décrit un ou plusieurs serveurs virtuels frontaux YAZ.

-C fname

Définit le nom du fichier de certificat SSL pour le serveur (PEM).

-v niveau

Le niveau de journalisation. Utilisez une liste séparée par des virgules des membres de l'ensemble {fatal,debug,warn,log,malloc,all,none}.

-u uid

Définit l'ID utilisateur. Définit l'UID réel du processus serveur sur celui de l'utilisateur donné. C'est utile si vous n'êtes pas à l'aise avec le fait que le serveur s'exécute en tant que root, mais que vous devez le démarrer en tant que tel pour lier un port privilégié.

-w rép

Le serveur se déplace dans ce répertoire avant d'écouter les connexions entrantes. Cette option est utile lorsque le serveur fonctionne à partir du démon inetd (voir -i).

-p pidfile

Spécifie que le serveur doit écrire son ID de processus dans le fichier donné par pidfile. Un emplacement typique serait /var/run/yaz-ztest.pid.

-i

Utilisez ceci pour que le serveur s'exécute à partir du serveur inetd (UNIX uniquement).

-D

Utilisez ceci pour que le serveur se mette en arrière-plan et s'exécute en tant que démon. Si ni -i ni -D n'est donné, le serveur démarre au premier plan.

-install

Utilisez ceci pour installer le serveur en tant que service NT (Windows NT/2000/XP uniquement). Contrôlez le serveur en allant dans Services dans le Panneau de configuration.

-installa

Utilisez ceci pour installer le serveur en tant que service NT et le marquer comme "démarrage automatique". Contrôlez le serveur en allant dans Services dans le Panneau de configuration.

-remove

Utilisez ceci pour supprimer le serveur des services NT (Windows NT/2000/XP uniquement).

-t minutes

Délai d'attente de session inactive, en minutes.

-k taille

Taille maximale d'enregistrement/message, en kilooctets.

-K

Force le mode sans keepalive pour les sessions HTTP. Par défaut, GFS maintient les sessions actives pour les sessions HTTP 1.1 (telles que définies par la norme). L'utilisation de cette option forcera GFS à fermer la connexion pour chaque opération.

-r taille

Taille maximale du fichier journal avant rotation, en kilooctets. La taille par défaut est de 1048576 k (=1 Go).

-d daemon

Définit le nom du démon à utiliser dans le fichier d'accès aux hôtes. Voir hosts_access(5) et tcpd(8).

-m format-temps

Définit le format des horodatages dans le fichier journal. Spécifiez une chaîne dans le format d'entrée pour strftime().

-V

Affiche la version YAZ et quitte.

TEST

yaz-ztest retourne normalement un nombre aléatoire de résultats entre 0 et 24. Cependant, si un terme de recherche inclut des chiffres initiaux, la valeur entière de ce terme est utilisée comme nombre de résultats. Cela permet aux testeurs de renvoyer n'importe quel nombre de résultats. yaz-ztest inclut 24 enregistrements MARC pour les tests. Les nombres de résultats dépassant 24 feront que yaz-ztest renverra le même lot d'enregistrements encore et encore. Ainsi, les enregistrements à la position 1, 25, 49, etc. sont équivalents.

Pour XML, si aucun jeu d'éléments n'est donné ou si l'élément a la valeur "marcxml", MARCXML est renvoyé (chacun des 24 enregistrements factices convertis de ISO2709 en XML). Pour le jeu d'éléments OP, alors OPAC XML est renvoyé.

yaz-ztest peut également renvoyer des enregistrements XML prédéfinis (pour les tests). Ceci est activé si la variable d'environnement YAZ_ZTEST_XML_FETCH est définie. Un enregistrement est récupéré d'un fichier (un enregistrement par fichier). Le chemin du nom de fichier est FE.d.xml où F est la valeur de YAZ_ZTEST_XML_FETCH (éventuellement vide), E est le jeu d'éléments, d est la position de l'enregistrement (à partir de 1).

Les bases de données suivantes sont honorées par yaz-ztest : Default, slow et db.* (toutes les bases de données avec le préfixe "db"). Toute autre base de données fera renvoyer à yaz-ztest le diagnostic 109 : "Base de données indisponible".

Les options de recherche peuvent être incluses dans le formulaire ou les arguments GET de l'URL inclus dans le nom de la base de données Z39.50. Les options de base de données suivantes sont présentes : search-delay, present-delay, fetch-delay et seed.

Les premières, options de délai, spécifient un délai fictif (sleep) que yaz-ztest effectuera lors de la recherche, de la présentation, de la récupération des enregistrements respectivement. La valeur du délai peut être soit une valeur flottante fixe qui spécifie le délai en secondes. Alternativement, la valeur peut être donnée sous la forme de deux nombres flottants séparés par un deux-points, ce qui fera que yaz-ztest effectuera une pause aléatoire entre le premier et le deuxième nombre.

Le paramètre de base de données seed prend un entier comme valeur. Cela appellera srand avec cet entier pour garantir que le comportement aléatoire puisse être rejoué.

Supposons que nous voulions que les recherches prennent entre 0,1 et 0,5 seconde et une récupération prenne 0,2 seconde. Pour accéder à la base de données de test Default, nous utiliserions : Default?search-delay=0.1:0.5&fetch-delay=0.2.

Pour le protocole HTTP, l'hôte virtuel est spécifié dans l'en-tête Host. Pour le protocole Z39.50, l'hôte virtuel est spécifié comme dans la requête Initialize dans OtherInfo, OID 1.2.840.10003.10.1000.81.1.


Note

Tous les clients Z39.50 ne permettent pas de définir les informations VHOST. Pour ceux-ci, la sélection du back-end doit reposer uniquement sur les informations TCP/IP (port et adresse).

Le serveur frontal YAZ utilise XML pour décrire les configurations des back-ends. L'option de ligne de commande -f spécifie le nom du fichier de configuration XML.

La configuration utilise l'élément racine yazgfs. Cet élément comprend une liste d'éléments listen, suivis d'un ou plusieurs éléments server.

L'élément listen décrit un point d'écoute (point d'extrémité de transport), tel que TCP/IP, un socket de fichier Unix ou un serveur SSL. Contenu d'un élément listen :

CDATA (requis)

Le CDATA de l'élément listen contient la chaîne du point d'écoute, telle que tcp:@:210, tcp:server1:2100, etc.

attribut id (facultatif)

Identifiant de ce point d'écoute. Il peut être référencé à partir des sections server.

Note

Nous nous attendons à ce que plus d'informations soient ajoutées à la section listen dans une future version, telles que le fichier CERT pour les serveurs SSL.

L'élément server décrit un serveur et les paramètres pour ce type de serveur. Contenu d'un élément server :

attribut id (facultatif)

Identifiant de ce serveur. Actuellement, il n'est utilisé à aucune fin, mais il pourrait l'être à des fins de journalisation.

attribut listenref (facultatif)

Spécifie un ou plusieurs points d'écoute pour ce serveur. Chaque ID de serveur est séparé par une virgule. Si cet attribut n'est pas donné, le serveur est accessible depuis tous les points d'écoute. Pour que le serveur soit réellement utilisé, cependant, l'hôte virtuel doit correspondre s'il est spécifié dans la configuration.

élément config (facultatif)

Spécifie la configuration du serveur. Ceci est équivalent à la configuration spécifiée à l'aide de l'option de ligne de commande -c.

élément directory (facultatif)

Spécifie un répertoire de travail pour ce serveur backend. S'il est spécifié, le frontend YAZ change le répertoire de travail courant vers ce répertoire chaque fois qu'un backend de ce type est démarré (gestionnaire de backend bend_start), arrêté (gestionnaire de backend hand_stop) et initialisé (bend_init).

élément host (facultatif)

Spécifie l'hôte virtuel pour ce serveur. S'il est spécifié, un client *doit* spécifier cette chaîne d'hôte pour utiliser ce backend.

élément cql2rpn (facultatif)

Spécifie un nom de fichier qui inclut la conversion CQL vers RPN pour ce serveur backend. Voir ???. S'il est donné, le serveur backend ne verra qu'une requête de type 1/RPN.

élément ccl2rpn (facultatif)

Spécifie un nom de fichier qui inclut la conversion CCL vers RPN pour ce serveur backend. Voir ???. S'il est donné, le serveur backend ne verra qu'une requête de type 1/RPN.

élément stylesheet (facultatif)

Spécifie la référence de feuille de style à inclure dans les réponses HTTP SRU lorsque le client n'en spécifie pas. Si aucune n'est donnée, et si le client n'en spécifie pas non plus, aucune référence de feuille de style ne fait partie de la réponse HTTP SRU.

élément client_query_charset (facultatif)

S'il est spécifié, une conversion du jeu de caractères donné vers UTF-8 est effectuée par le serveur frontal générique. Elle n'est exécutée que pour les requêtes de recherche Z39.50 (SRU/Solr sont supposés être encodés en UTF-8 déjà).

élément docpath (facultatif)

Spécifie un chemin pour l'accès aux fichiers locaux via HTTP. Toutes les URL avec un préfixe (/ exclus) correspondant à la valeur de docpath sont utilisées pour l'accès aux fichiers. Par exemple, si le serveur doit proposer un accès dans le répertoire xsl, le docpath sera xsl et toutes les URL de la forme http://host/xsl entraîneront un accès à un fichier local.

élément explain (facultatif)

Spécifie le contenu ZeeRex SRW/SRU pour ce serveur. Copié littéralement au client. Dans l'état actuel, une partie du contenu Explain semble redondante car les informations d'hôte, etc. sont également stockées ailleurs.

élément maximumrecordsize (facultatif)

Spécifie la taille maximale d'enregistrement/message, en octets. Cette valeur sert également de taille maximale des paquets *entrants* (pour les mises à jour d'enregistrement, etc.). C'est la même valeur que celle donnée par l'option -k.

élément retrievalinfo (facultatif)

Active la facilité de récupération pour supporter les conversions et les spécifications des formats/types d'enregistrement. Voir ??? pour plus d'informations.

Le XML ci-dessous configure un serveur qui accepte les connexions de deux ports, le port TCP/IP 9900 et un socket de fichier UNIX local. Nous nommons le serveur TCP/IP public et l'autre serveur interne.

 <yazgfs>
  <listen id="public">tcp:@:9900</listen>
  <listen id="internal">unix:/var/tmp/socket</listen>
  <server id="server1">
    <host>server1.mydomain</host>
    <directory>/var/www/s1</directory>
    <config>config.cfg</config>
  </server>
  <server id="server2" listenref="public,internal">
    <host>server2.mydomain</host>
    <directory>/var/www/s2</directory>
    <config>config.cfg</config>
    <cql2rpn>../etc/pqf.properties</cql2rpn>
    <explain xmlns="http://explain.z3950.org/dtd/2.0/">
      <serverInfo>
        <host>server2.mydomain</host>
        <port>9900</port>
        <database>a</database>
      </serverInfo>
    </explain>
  </server>
  <server id="server3" listenref="internal">
    <directory>/var/www/s3</directory>
    <config>config.cfg</config>
  </server>
 </yazgfs>

Il y a trois serveurs backend configurés. Les deux premiers serveurs, « server1 » et « server2 », sont accessibles depuis les deux adresses d'écoute. « server1 » est accessible depuis tous (les deux) car aucun attribut listenref n'est spécifié. « server2 » est accessible depuis les deux points d'écoute spécifiés. Pour les distinguer, un hôte virtuel a été spécifié pour chaque serveur dans les éléments host.

Pour « server2 », les éléments de conversion CQL vers RPN sont pris en charge et des informations d'explication ont été ajoutées (une courte ici pour garder l'exemple petit).

Le troisième serveur, « server3 », n'est accessible que via le point d'écoute « internal ».
