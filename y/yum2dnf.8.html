NOM

yum2dnf - Changements dans DNF par rapport à YUM

--SKIP-BROKEN

Pour la commande d'installation :

L'option --skip-broken est un alias pour --setopt=strict=0. Les deux options peuvent être utilisées avec DNF pour ignorer tous les paquets indisponibles ou les paquets avec des dépendances cassées donnés à DNF sans générer d'erreur provoquant l'échec de toute l'opération. Ce comportement peut être défini par défaut dans le fichier dnf.conf. Voir l'option de configuration strict <#strict-label>.

Pour la commande de mise à niveau :

La sémantique qui était censée se déclencher dans YUM avec --skip-broken est maintenant définie par défaut pour un simple dnf update. Il n'est pas nécessaire d'utiliser --skip-broken avec la commande dnf upgrade. Pour utiliser uniquement les dernières versions des paquets dans les transactions, il y a le commutateur de ligne de commande --best.

LES COMMANDES UPDATE ET UPGRADE SONT IDENTIQUES

L'invocation de dnf update ou dnf upgrade, sous toutes leurs formes, a le même effet dans DNF, le dernier étant préféré. Dans YUM, yum upgrade était exactement comme yum --obsoletes update.

NETTOYAGE DES EXIGENCES À LA SUPPRESSION ACTIVÉ PAR DÉFAUT

Le commutateur clean_requirements_on_remove <#clean-requirements-on-remove-label> est activé par défaut dans DNF. Il peut donc être déroutant de comparer les résultats de l'opération "remove" entre DNF et YUM, car par défaut DNF supprimera souvent plus de paquets.

PAS DE COMMANDE RESOLVEDEP

La version YUM de cette commande est maintenue uniquement pour des raisons d'héritage. L'utilisateur peut simplement utiliser dnf provides pour savoir quel paquet fournit un fichier particulier.

PAS DE COMMANDE DEPLIST

Une alternative à la commande YUM deplist pour connaître les dépendances d'un paquet est dnf repoquery --deplist en utilisant la commande repoquery <#repoquery-command-label>.

Note :

Alternativement, il existe un support de compatibilité YUM où yum deplist est un alias pour la commande dnf repoquery --deplist

EXCLUSIONS ET EXCLUSIONS DE RÉPERTOIRE S'APPLIQUENT À TOUTES LES OPÉRATIONS

YUM ne respecte les exclusions que lors des installations et mises à niveau. DNF étend cela à toutes les opérations, notamment la suppression et la liste. Si, par exemple, vous souhaitez voir une liste de tous les paquets installés python-f* mais aucun des paquets Flask, ce qui suit fonctionnera :

dnf -x '*flask*' list installed 'python-f*'

L'OPTION INCLUDE A ÉTÉ SUPPRIMÉE

L'inclusion d'autres fichiers de configuration dans le fichier de configuration principal n'est plus prise en charge.

DNF PROVIDES /BIN/<FICHIER> N'EST PAS TOTALEMENT PRIS EN CHARGE

Après UsrMove https://fedoraproject.org/wiki/Features/UsrMove, il n'y a pas de répertoire /bin sur les systèmes Fedora et aucun fichier n'y est installé, /bin n'est qu'un lien symbolique créé par le paquet filesystem pour pointer vers /usr/bin. Résoudre les liens symboliques vers leur chemin réel ne donnerait à l'utilisateur qu'une fausse impression que cela fonctionne, alors qu'en fait les requêtes d'appartenance utilisant des jokers comme :

dnf provides /b*/<fichier>

échoueront toujours (comme ils le font maintenant dans YUM). Pour savoir ce qui fournit un binaire particulier, utilisez le chemin réel pour les binaires sur Fedora :

dnf provides /usr/bin/<fichier>

Voir également les bugzillas Fedora associées 982947 https://bugzilla.redhat.com/show_bug.cgi?id=982947 et 982664 https://bugzilla.redhat.com/show_bug.cgi?id=982664.

SKIP_IF_UNAVAILABLE POURRAIT ÊTRE ACTIVÉ PAR DÉFAUT

Dans certaines distributions, DNF est livré avec skip_if_unavailable=True dans le fichier de configuration DNF <#conf-ref-label>. La raison de ce changement est que les dépôts tiers peuvent souvent être indisponibles. Sans ce paramètre dans le fichier de configuration du dépôt concerné, YUM s'arrête immédiatement en cas d'erreur de synchronisation du dépôt, ce qui désoriente et dérange l'utilisateur.

Voir le bug Fedora associé 984483 https://bugzilla.redhat.com/show_bug.cgi?id=984483.

OVERWRITE_GROUPS SUPPRIMÉ, FONCTIONS COMPS AGISSANT COMME SI TOUJOURS DÉSACTIVÉES

Cette option de configuration a été supprimée. Lorsque DNF voit plusieurs groupes avec le même ID de groupe, il fusionne le contenu des groupes.

MIRRORLIST_EXPIRE SUPPRIMÉ

Pour simplifier les choses pour l'utilisateur, DNF utilise metadata_expire pour l'expiration des métadonnées et du fichier mirrorlist (qui est une sorte de métadonnées lui-même).

METALINK NON RECONNU DANS L'OPTION DE RÉPERTOIRE MIRRORLIST

La partie suivante de yum.conf(5) ne s'applique plus à l'option mirrorlist :

Par convention spéciale, si l'URL de mirrorlist contient le mot "metalink", alors la valeur de mirrorlist est copiée dans metalink (si metalink n'est pas défini).

Les fichiers de configuration de dépôt pertinents ont été corrigés pour respecter cela, voir le bug Fedora associé 948788 https://bugzilla.redhat.com/show_bug.cgi?id=948788.

ALWAYSPROMPT SUPPRIMÉ

Non pris en charge pour simplifier la configuration.

UPGRADE_REQUIREMENTS_ON_INSTALL SUPPRIMÉ

La suppression de cette option de configuration aux sémantiques floues simplifie la configuration. DNF se comporte comme si elle était désactivée. Si l'utilisateur souhaitait mettre à niveau tout vers la dernière version, elle utiliserait simplement dnf upgrade.

VÉRIFICATION ROLLBACK HISTORIQUE DNF SUPPRIMÉE

Étant donné que DNF tolère l'utilisation d'autres gestionnaires de paquets, il est possible que toutes les modifications apportées à la RPMDB ne soient pas stockées dans l'historique des transactions. Par conséquent, DNF n'échoue pas si une telle situation est rencontrée et donc l'option force n'est plus nécessaire.

REMPLACEMENT DE PAQUETS SANS SWAP YUM

De temps en temps, il faut supprimer un paquet installé et le remplacer par un autre, offrant les mêmes capacités tandis que d'autres paquets dépendant de ces capacités restent installés. Sans casser (de manière transitoire) la cohérence de la base de données des paquets, cela peut être fait en effectuant la suppression et l'installation dans une seule transaction. La manière courante de configurer une telle transaction dans DNF est d'utiliser dnf shell ou le commutateur --allowerasing.

Par exemple, supposons que vous souhaitiez remplacer A (fournissant P) par B (fournissant également P, en conflit avec A) sans

dnf --allowerasing install B

DNF fournit la commande swap, mais seule la syntaxe dnf swap A B est prise en charge.

LES DÉTAILS DU TRAITEMENT DES DÉPENDANCES NE SONT PAS AFFICHÉS DANS LA CLI

Pendant sa phase de résolution des dépendances, YUM affiche des lignes similaires à :

---> Package rubygem-rhc.noarch 0:1.16.9-1.fc19 will be an update
--> Processing Dependency: rubygem-net-ssh-multi >= 1.2.0 for package: rubygem-rhc-1.16.9-1.fc19.noarch

DNF n'affiche pas d'informations de ce type. La raison technique est que le résolveur de dépendances sous DNF considère toujours toutes les dépendances pour les candidats à la mise à jour et que la sortie serait très longue. Deuxièmement, même dans YUM, cette sortie devient rapidement confuse, en particulier pour les transactions importantes, et fait donc plus de mal que de bien.

Voir le bug Fedora 1044999 associé https://bugzilla.redhat.com/show_bug.cgi?id=1044999.

DNF PROVIDES EST CONFORME À LA DOCUMENTATION DE COMMANDE DE YUM

Lorsque l'on exécute :

yum provides sandbox

YUM applique des heuristiques supplémentaires pour déterminer ce que l'utilisateur voulait dire par sandbox, par exemple, il préfixe séquentiellement les entrées de la variable d'environnement PATH pour voir si cela correspond à un fichier fourni par un paquet. C'est un comportement non documenté que DNF n'émule pas. Utilisez simplement de manière typique :

dnf provides /usr/bin/sandbox

ou même :

dnf provides '*/sandbox'

pour obtenir des résultats similaires.

LIMITATION DE LA BANDE PASSANTE

DNF prend en charge les options throttle et bandwidth familières de YUM. Contrairement à YUM, lorsque plusieurs téléchargements s'exécutent simultanément, la vitesse de téléchargement totale est limitée. Ce n'était pas possible dans YUM car les téléchargeurs s'exécutaient dans des processus différents.

OPTION DE CONFIGURATION INSTALLONLYPKGS

Par rapport à YUM, DNF ajoute les valeurs de liste des options de configuration installonlypkgs aux valeurs par défaut de DNF, tandis que YUM écrase les valeurs par défaut par les valeurs de l'option.

UTILISATION DES FICHIERS DELTA RPM

L'option booléenne deltarpm contrôle si les fichiers delta RPM sont utilisés. Par rapport à YUM, DNF ne prend pas en charge deltarpm_percentage et choisit à la place une valeur optimale du rapport DRPM/RPM pour décider si l'utilisation de deltarpm est judicieuse dans le cas donné.

GESTION DES FICHIERS .SRPM ET DES PAQUETS INEXISTANTS

DNF se terminera tôt avec une erreur si une commande est exécutée demandant une opération d'installation sur un fichier .srpm local :

$ dnf install fdn-0.4.17-1.fc20.src.rpm tour-4-6.noarch.rpm
Error: Will not install a source rpm package (fdn-0.4.17-1.fc20.src).

Il en va de même pour les spécifications de paquets qui ne correspondent à aucun paquet disponible.

YUM n'émettra qu'un avertissement dans ce cas et continuera l'installation du paquet "tour". La logique derrière le résultat dans DNF est qu'un programme doit se terminer avec une erreur s'il ne peut pas exécuter entièrement la commande CLI.

PROMOTION D'UN PAQUET À INSTALLER VERS UN PAQUET QUI L'OBSOLÈTE

DNF ne remplacera pas magiquement une demande d'installation du paquet X par l'installation du paquet Y si Y obsolète X. YUM le fait si son option de configuration obsoletes est activée, mais le comportement n'est pas correctement documenté et peut être nuisible.

Voir le bug Fedora 1096506 associé https://bugzilla.redhat.com/show_bug.cgi?id=1096506 et les directives pour le renommage et l'obsolescence des paquets dans Fedora http://fedoraproject.org/wiki/Upgrade_paths_%E2%80%94_renaming_or_splitting_packages.

COMPORTEMENT DE L'OPTION --INSTALLROOT

DNF offre un comportement plus prévisible d'installroot. DNF traite le chemin différemment de l'option de ligne de commande --config, où ce chemin est toujours lié au système hôte (YUM combine ce chemin avec installroot). Reposdir est également géré légèrement différemment, si un chemin des répertoires de dépôts existe à l'intérieur d'installroot, alors les dépôts sont strictement pris d'installroot (YUM teste chaque chemin de repos séparément et utilise le chemin d'installroot s'il existe). Voir la description détaillée de l'option --installroot <#installroot-label>.

PROMPT DIFFÉRENT APRÈS LE TABLEAU DE TRANSACTION

DNF ne fournit pas de fonctionnalité de téléchargement après l'affichage du tableau de transaction. Il demande seulement à l'utilisateur s'il faut continuer la transaction ou non. Si l'on souhaite télécharger des paquets, on peut utiliser la commande 'download'.

LA COMMANDE LIST AFFICHE TOUTES LES ALTERNATIVES DE DÉPÔT

DNF liste tous les paquets de tous les dépôts, ce qui signifie qu'il peut y avoir des noms de paquets dupliqués (avec des noms de dépôts différents). Cela est dû à la possibilité offerte aux utilisateurs de choisir leur dépôt préféré.

LES SOUS-COMMANDES YUM-LANGPACKS ONT ÉTÉ SUPPRIMÉES

Les traductions font partie du cœur de DNF et il n'est plus nécessaire de gérer les packs de langues individuels.

Les sous-commandes suivantes ont été supprimées :

  • langavailable
  • langinstall
  • langremove
  • langlist
  • langinfo

LES SOUS-COMMANDES DNF HISTORY LIST ET INFO RENVOIENT 0 QUAND AUCUNE TRANSACTION N'EST TROUVÉE

DNF dnf history list et dnf history info renvoient un statut de sortie zéro lorsqu'ils ne trouvent pas de transactions pour un paquet spécifié.

Ceci est différent des correspondants YUM yum history package-list et yum history list, qui renvoient tous deux un statut de sortie non nul lorsqu'ils ne trouvent pas

YUM-UPDATEONBOOT ET YUM-CRON

DNF n'a pas de remplacement direct des commandes yum-updateonboot et yum-cron. Cependant, un résultat similaire peut être obtenu avec la commande dnf automatic (voir DNF Automatic <>).

Vous pouvez soit utiliser le raccourci :

$ systemctl enable --now dnf-automatic-install.timer

Ou définir l'option apply_updates de /etc/dnf/automatic.conf sur True et utiliser l'unité timer générique :

$ systemctl enable --now dnf-automatic.timer

Le timer dans les deux cas est activé 1 heure après le démarrage du système, puis répétitivement toutes les 24 heures. Il y a également un délai aléatoire sur ces timers défini à 5 minutes. Ces valeurs peuvent être ajustées via les fichiers de configuration dnf-automatic*.timer situés dans le répertoire /usr/lib/systemd/system/.

NAME

yum2dnf - convert yum configuration to dnf configuration

--SKIP-BROKEN

This option is not present in dnf and it has been removed.

UPDATE AND UPGRADE COMMANDS ARE THE SAME

Commands update and upgrade are the same in dnf and yum.

CLEAN REQUIREMENTS ON REMOVE ON BY DEFAULT

The option clean_requirements_on_remove is on by default in dnf.

NO RESOLVEDEP COMMAND

The command resolvedep has been removed in dnf.

NO DEPLIST COMMAND

The command deplist has been removed in dnf.

EXCLUDES AND REPO EXCLUDES APPLY TO ALL OPERATIONS

The excludes and repo excludes options apply to all operations in dnf.

THE INCLUDE OPTION HAS BEEN REMOVED

The include option has been removed in dnf.

DNF PROVIDES /BIN/<FILE> IS NOT FULLY SUPPORTED

Provides file name like /bin/<file> is not fully supported in dnf.

SKIP_IF_UNAVAILABLE COULD BE ENABLED BY DEFAULT

The option skip_if_unavailable could be enabled by default in dnf.

OVERWRITE_GROUPS DROPPED, COMPS FUNCTIONS ACTING AS IF ALWAYS DISABLED

The option overwrite_groups has been dropped in dnf. Comps functions act as if always disabled.

MIRRORLIST_EXPIRE DROPPED

The option mirrorlist_expire has been dropped in dnf.

METALINK NOT RECOGNIZED IN THE MIRRORLIST REPO OPTION

Metalink is not recognized in the mirrorlist repo option in dnf.

ALWAYSPROMPT DROPPED

The option alwaysprompt has been dropped in dnf.

UPGRADE_REQUIREMENTS_ON_INSTALL DROPPED

The option upgrade_requirements_on_install has been dropped in dnf.

DNF HISTORY ROLLBACK CHECK DROPPED

The rollback check in dnf history has been dropped.

PACKAGES REPLACEMENT WITHOUT YUM SWAP

The replacement of packages without yum swap works in dnf.

DEPENDENCY PROCESSING DETAILS ARE NOT SHOWN IN THE CLI

Dependency processing details are not shown in the cli in dnf.

DNF PROVIDES COMPLIES WITH THE YUM DOCUMENTATION OF THE COMMAND

The provides command in dnf complies with the yum documentation of the command.

BANDWIDTH LIMITING

Bandwidth limiting is supported in dnf.

INSTALLONLYPKGS CONFIG OPTION

The installonlypkgs config option is supported in dnf.

THE USAGE OF DELTA RPM FILES

Delta rpm files are used in dnf.

HANDLING .SRPM FILES AND NON-EXISTENT PACKAGES

.srpm files and non-existent packages are handled in dnf.

PROMOTING PACKAGE TO INSTALL TO A PACKAGE THAT OBSOLETES IT

Promoting package to install to a package that obsoletes it works in dnf.

BEHAVIOR OF --INSTALLROOT OPTION

The behavior of --installroot option is the same in dnf and yum.

DIFFERENT PROMPT AFTER TRANSACTION TABLE

The prompt after transaction table is different in dnf.

LIST COMMAND SHOWS ALL REPO ALTERNATIVES

The list command shows all repo alternatives in dnf.

YUM-LANGPACKS SUBCOMMANDS HAVE BEEN REMOVED

The yum-langpacks subcommands have been removed in dnf.

DNF HISTORY SUBCOMMANDS LIST AND INFO RETURN 0 WHEN TRANSACTIONS NOT FOUND

The dnf history subcommands list and info return 0 when transactions not found.

YUM-UPDATEONBOOT AND YUM-CRON

yum-updateonboot and yum-cron are not present in dnf.
