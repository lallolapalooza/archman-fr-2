YACC(1P) Manuel du programmeur POSIX YACC(1P)

PROLOGUE

Cette page de manuel fait partie du Manuel du programmeur POSIX. L'implémentation Linux de cette interface peut différer (consulter la page de manuel Linux correspondante pour les détails du comportement sous Linux), ou l'interface peut ne pas être implémentée sous Linux.

NOM

yacc — encore un autre compilateur de compilateur (DÉVELOPPEMENT)

SYNOPIS

yacc [-dltv] [-b préfixe_fichier] [-p préfixe_symbole] grammaire

DESCRIPTION

L'utilitaire yacc lit une description d'une grammaire sans contexte dans grammaire et écrit du code source C, conforme à la norme ISO C, dans un fichier de code, et éventuellement des informations d'en-tête dans un fichier d'en-tête, dans le répertoire courant. Le code source généré ne doit dépendre d'aucun comportement non défini, non spécifié ou défini par l'implémentation, sauf dans les cas où il est copié directement depuis la grammaire fournie, ou dans les cas qui sont documentés par l'implémentation. Le code C définit une fonction et des routines et macros connexes pour un automate qui exécute un algorithme d'analyse syntaxique répondant aux exigences de la section Algorithmes.

La forme et le sens de la grammaire sont décrits dans la section DESCRIPTION ÉTENDUE.

Le code source C et le fichier d'en-tête sont produits dans un format adapté à l'entrée du compilateur C (voir c99).

OPTIONS

L'utilitaire yacc est conforme aux Définitions de base du volume POSIX.1‐2017, Section 12.2, Directives de syntaxe utilitaire, à l'exception de la directive 9.

Les options suivantes sont prises en charge :

-b préfixe_fichier
Utilise préfixe_fichier au lieu de y comme préfixe pour tous les noms de fichiers de sortie. Le fichier de code y.tab.c, le fichier d'en-tête y.tab.h (créé lorsque -d est spécifié), et le fichier de description y.output (créé lorsque -v est spécifié), sont modifiés en préfixe_fichier.tab.c, préfixe_fichier.tab.h, et préfixe_fichier.output, respectivement.
-d
Écrit le fichier d'en-tête ; par défaut, seul le fichier de code est écrit. Voir la section FICHIERS DE SORTIE.
-l
Produit un fichier de code qui ne contient aucune directive #line. Si cette option n'est pas présente, il n'est pas spécifié si le fichier de code ou le fichier d'en-tête contient des directives #line. Ceci ne doit être utilisé qu'après que la grammaire et les actions associées soient entièrement déboguées.
-p préfixe_symbole

Utilise préfixe_symbole au lieu de yy comme préfixe pour tous les noms externes produits par yacc. Les noms affectés incluent les fonctions yyparse(), yylex(), et yyerror(), ainsi que les variables yylval, yychar, et yydebug. (Dans le reste de cette section, les six symboles cités sont référencés en utilisant leurs noms par défaut uniquement comme commodité de notation.) Les noms locaux peuvent également être affectés par l'option -p ; cependant, l'option -p n'affectera pas les symboles #define générés par yacc.
-t
Modifie les directives de compilation conditionnelle pour permettre la compilation de code de débogage dans le fichier de code. Les instructions de débogage d'exécution seront toujours contenues dans le fichier de code, mais par défaut, les directives de compilation conditionnelle empêchent leur compilation.
-v
Écrit un fichier contenant une description de l'analyseur syntaxique et un rapport des conflits générés par des ambiguïtés dans la grammaire.

OPÉRANDES

L'opérande suivant est requis :

grammaire
Un nom de chemin d'un fichier contenant les instructions, ci-après grammaire, pour lesquelles un analyseur syntaxique doit être créé. Le format de la grammaire est décrit dans la section DESCRIPTION ÉTENDUE.

STDIN

Non utilisé.

FICHIERS D'ENTRÉE

Le fichier grammaire doit être un fichier texte formaté comme spécifié dans la section DESCRIPTION ÉTENDUE.

VARIABLES D'ENVIRONNEMENT

Les variables d'environnement suivantes affectent l'exécution de yacc :

LANG
Fournit une valeur par défaut pour les variables d'internationalisation qui sont non définies ou nulles. (Voir le volume Définitions de base de POSIX.1‐2017, Section 8.2, Variables d'internationalisation pour la priorité des variables d'internationalisation utilisées pour déterminer les valeurs des catégories de locale.)
LC_ALL
Si défini à une chaîne de caractères non vide, remplace les valeurs de toutes les autres variables d'internationalisation.
LC_CTYPE
Détermine la locale pour l'interprétation des séquences d'octets de données textuelles en tant que caractères (par exemple, caractères mono-octet par opposition aux caractères multi-octets dans les arguments et les fichiers d'entrée).
LC_MESSAGES

Détermine la locale qui doit être utilisée pour affecter le format et le contenu des messages de diagnostic écrits sur la sortie d'erreur standard.
NLSPATH
Détermine l'emplacement des catalogues de messages pour le traitement de LC_MESSAGES.

Les variables LANG et LC_* affectent l'exécution de l'utilitaire yacc comme indiqué. La fonction main() définie dans la Bibliothèque Yacc appelle :

setlocale(LC_ALL, "")

et donc le programme généré par yacc sera également affecté par le contenu de ces variables au moment de l'exécution.

ÉVÉNEMENTS SYNCHRONES

Défaut.

STDOUT

Non utilisé.

STDERR

Si des conflits décalage/réduction ou réduction/réduction sont détectés dans grammaire, yacc écrit un rapport de ces conflits sur la sortie d'erreur standard dans un format non spécifié.

La sortie d'erreur standard est également utilisée pour les messages diagnostiques.

FICHIERS DE SORTIE

Le fichier de code, le fichier d'en-tête et le fichier de description sont des fichiers texte. Tous sont décrits dans les sections suivantes.

Fichier de Code

Ce fichier contient le code source C de la fonction yyparse(). Il contient le code pour les diverses actions sémantiques avec substitution de macros effectuée sur celles-ci comme décrit dans la section DESCRIPTION ÉTENDUE. Il contient également une copie des directives #define du fichier d'en-tête. Si une déclaration %union est utilisée, la déclaration de YYSTYPE est également incluse dans ce fichier.

Fichier d'En-tête

Le fichier d'en-tête contient des directives #define qui associent les numéros de jeton aux noms de jeton. Cela permet aux fichiers source autres que le fichier de code d'accéder aux codes de jeton. Si une déclaration %union est utilisée, la déclaration de YYSTYPE et une déclaration extern YYSTYPE yylval sont également incluses dans ce fichier.

Fichier de Description

Le fichier de description est un fichier texte contenant une description de la machine à états correspondant à l'analyseur syntaxique, en utilisant un format non spécifié.

LIMITES

Les limites pour les tables internes (voir Limites) doivent également être signalées, d'une manière définie par l'implémentation. (Certaines implémentations peuvent utiliser des techniques d'allocation dynamique et n'avoir pas de valeurs limites spécifiques à signaler.)

DESCRIPTION ÉTENDUE

La commande yacc accepte un langage qui est utilisé pour définir une grammaire pour un langage cible à analyser par les tables et le code générés par yacc. Le langage accepté par yacc comme grammaire pour le langage cible est décrit ci-dessous en utilisant le langage d'entrée yacc lui-même.

La grammaire d'entrée comprend des règles décrivant la structure d'entrée du langage cible et le code à invoquer lorsque ces règles sont reconnues pour fournir l'action sémantique associée. Le code à exécuter doit apparaître sous forme de corps de texte qui sont destinés à être du code en langage C. Ces corps de texte ne doivent pas contenir de trigraphes en langage C. Les inclusions en langage C sont présumées former une fonction correcte lorsqu'elles sont traitées par yacc dans ses fichiers de sortie. Le code inclus de cette manière sera exécuté pendant la reconnaissance du langage cible.

Étant donné une grammaire, l'utilitaire yacc génère les fichiers décrits dans la section FICHIERS DE SORTIE. Le fichier de code peut être compilé et lié à l'aide de c99. Si les sections de déclaration et de programmes du fichier de grammaire n'incluent pas les définitions de main(), yylex(), et yyerror(), la sortie compilée nécessite une liaison avec des versions fournies extérieurement de ces fonctions. Des versions par défaut de main() et yyerror() sont fournies dans la bibliothèque yacc et peuvent être liées en utilisant l'opérande -l y à c99. Les interfaces de la bibliothèque yacc n'ont pas besoin de prendre en charge des interfaces avec des préfixes de symboles autres que le préfixe par défaut yy. L'application fournit la fonction d'analyse lexicale, yylex(); l'utilitaire lex est spécifiquement conçu pour générer une telle routine.

Langage d'entrée

L'application doit s'assurer que chaque fichier de spécification se compose de trois sections dans l'ordre : déclarations, règles de grammaire, et programmes, séparées par des caractères double <signe-pourcentage> ("%%"). Les sections de déclarations et de programmes peuvent être vides. Si cette dernière est vide, la marque "%%" précédente la séparant de la section des règles peut être omise.

L'entrée est un texte libre suivant la structure de la grammaire définie ci-dessous.

Structure lexicale de la grammaire

Les caractères <espace>, <nouvelle ligne>, et <saute de page> doivent être ignorés, sauf que l'application doit s'assurer qu'ils n'apparaissent pas dans les noms ou les symboles réservés de plusieurs caractères. Les commentaires doivent être délimités par "/* ... */", et peuvent apparaître partout où un nom est valide.

Les noms sont de longueur arbitraire, composés de lettres, de points ('.'), de traits de soulignement ('_'), et de chiffres non initiaux. Les lettres majuscules et minuscules sont distinctes. Les applications conformes ne doivent pas utiliser de noms commençant par yy ou YY car l'analyseur yacc utilise de tels noms. Beaucoup de ces noms apparaissent dans la sortie finale de yacc, et ils doivent donc être choisis pour être conformes à toute règle supplémentaire créée par le compilateur C à utiliser. En particulier, ils apparaissent dans les instructions #define.

Un littéral doit consister en un seul caractère entouré de guillemets simples. Toutes les séquences d'échappement prises en charge pour les constantes de caractères par la norme ISO C doivent être prises en charge par yacc.

La relation avec l'analyseur lexical est discutée en détail ci-dessous.

L'application doit s'assurer que le caractère NUL n'est pas utilisé dans les règles de grammaire ou les littéraux.

Section des déclarations

La section des déclarations est utilisée pour définir les symboles utilisés pour définir le langage cible et leur relation les uns avec les autres. En particulier, une grande partie des informations supplémentaires requises pour résoudre les ambiguïtés dans la grammaire non contextuelle du langage cible est fournie ici.

Habituellement, yacc attribue la relation entre les noms symboliques qu'il génère et leur valeur numérique sous-jacente. La section des déclarations permet de contrôler l'attribution de ces valeurs.

Il est également possible de conserver des informations sémantiques associées aux jetons actuellement sur la pile d'analyse dans une union définie par l'utilisateur en langage C, si les membres de l'union sont associés aux divers noms de la grammaire. La section des déclarations le permet également.

Le premier groupe de déclarateurs ci-dessous prend tous une liste de noms comme arguments. Cette liste peut éventuellement être précédée du nom d'un membre d'union C (appelé une étiquette ci-dessous) apparaissant entre '<' et '>'. (Par exception aux conventions typographiques du reste de ce volume de POSIX.1‐2017, dans ce cas <étiquette> ne représente pas une méta-variable, mais les caractères littéraux de parenthèses angulaires entourant un symbole.) L'utilisation de tag spécifie que les jetons nommés sur cette ligne doivent être du même type C que le membre d'union référencé par tag. Ceci est discuté plus en détail ci-dessous.

Pour les listes utilisées pour définir des jetons, la première apparition d'un jeton donné peut être suivie d'un entier positif (sous forme de chaîne de chiffres décimaux). Si cela est fait, la valeur sous-jacente qui lui est attribuée à des fins lexicales sera considérée comme ce nombre.

La déclaration suivante déclare name comme un jeton :

%token [<tag>] name [number] [name [number]]...

Si tag est présent, le type C pour tous les jetons de cette ligne doit être déclaré comme le type référencé par tag. Si un entier positif, number, suit un name, cette valeur doit être attribuée au jeton.

La déclaration suivante déclare name comme un jeton et lui attribue une précédence :

%left [<tag>] name [number] [name [number]]...
%right [<tag>] name [number] [name [number]]...

Une ou plusieurs lignes, chacune commençant par l'un de ces symboles, peuvent apparaître dans cette section. Tous les jetons sur la même ligne ont le même niveau de précédence et la même associativité ; les lignes sont dans l'ordre de précédence croissante ou de force de liaison. %left indique que les opérateurs sur cette ligne sont associatifs à gauche, et %right indique de même des opérateurs associatifs à droite. Si tag est présent, il doit déclarer un type C pour les names tel que décrit pour %token.

La déclaration suivante déclare name comme un jeton et indique qu'il ne peut pas être utilisé de manière associative :

%nonassoc [<tag>] name [number] [name [number]]...

Si l'analyseur rencontre une utilisation associative de ce jeton, il signale une erreur. Si tag est présent, il doit déclarer un type C pour les names tel que décrit pour %token.

La déclaration suivante déclare que les membres d'union names sont des non-terminaux, et qu'il est donc requis d'avoir un champ tag à leur début :

%type <tag> name...

Parce qu'elle ne concerne que les non-terminaux, l'attribution d'un numéro de jeton ou l'utilisation d'un littéral est également interdite. Si cette construction est présente, yacc effectuera une vérification des types ; si cette construction n'est pas présente, la pile d'analyse ne contiendra que le type int.

Chaque nom utilisé dans grammar non défini par une déclaration %token, %left, %right, ou %nonassoc est présumé représenter un symbole non-terminal. L'utilitaire yacc signalera une erreur pour tout symbole non-terminal qui n'apparaît pas du côté gauche d'au moins une règle de grammaire.

Une fois que le type, la précédence, ou le numéro de jeton d'un nom est spécifié, il ne doit pas être modifié. Si la première déclaration d'un jeton n'attribue pas de numéro de jeton, yacc attribuera un numéro de jeton. Une fois cette attribution effectuée, le numéro de jeton ne doit pas être modifié par une attribution explicite.

Les déclarateurs suivants ne suivent pas le modèle précédent.

La déclaration suivante déclare le non-terminal name comme symbole de démarrage, qui représente la structure la plus large et la plus générale décrite par les règles de grammaire :

%start name

Par défaut, c'est le côté gauche de la première règle de grammaire ; cette valeur par défaut peut être remplacée par cette déclaration.

La déclaration suivante déclare que la pile de valeurs de yacc est une union des différents types de valeurs souhaitées.

%union { corps de l'union (en C) }

Le corps de l'union ne doit pas contenir de jetons de prétraitement avec des accolades déséquilibrées.

Par défaut, les valeurs retournées par les actions (voir ci-dessous) et l'analyseur lexical seront de type int. L'utilitaire yacc suit les types, et il insérera les noms de membres d'union correspondants afin d'effectuer une vérification stricte des types de l'analyseur résultant.

Alternativement, étant donné qu'au moins une construction <tag> est utilisée, l'union peut être déclarée dans un fichier d'en-tête (qui doit être inclus dans la section des déclarations en utilisant une construction #include dans %{ et %}), et un typedef utilisé pour définir le symbole YYSTYPE afin de représenter cette union. L'effet de %union est de fournir la déclaration de YYSTYPE directement à partir de l'entrée yacc.

Des déclarations et définitions en langage C peuvent apparaître dans la section des déclarations, délimitées par les marques suivantes :

%{ ... %}

Ces instructions doivent être copiées dans le fichier de code, et ont une portée globale à l'intérieur afin qu'elles puissent être utilisées dans les sections de règles et de programmes. Les instructions ne doivent pas contenir "%}" en dehors d'un commentaire, d'une chaîne littérale, ou d'une constante multi-caractères.

L'application doit s'assurer que la section des déclarations est terminée par le jeton %%.

Règles de grammaire dans yacc

La section des règles définit la grammaire non contextuelle à accepter par la fonction que yacc génère, et associe à ces règles des actions en langage C et des informations supplémentaires.

yacc - manual page

YACC(1)

2017-07-13

NAME

yacc - language directed compiler writing system

SYNOPSIS

yacc [-bdltv?] [-p name] [file ...]

DESCRIPTION

The yacc utility takes a grammar description and generates a parser for it. The parser is a communication program which should be used with output generated by the lexical analyzer generator lex.

The input grammar file consists of three sections, separated by the %% line. The sections are:

	declarations
	%%
	grammar rules
	%%
	user subroutines

The declarations and grammar rules sections are required. The user subroutines section is optional.

Declarations Section

The declarations section is used to define the set of token and non-terminal symbols used in the grammar rules. It also contains declarations for C code and control information for the yacc utility.

The declarations section has the following structure:

%{
    /* C declarations */
%}
/* yacc declarations */

The C declarations between %{ and %} are placed directly into the output file, and are available to the C code generated by yacc, including the lexical analyzer and the actions. They should include declarations for global variables and any types used for semantic values that are not specified via the %union declaration.

The yacc declarations consist of declarations that inform yacc about the grammar symbols, associativity, precedence, and type information. These declarations are used to control the generation of the parser.

%token, %left, %right, %nonassoc
These declarations inform yacc that the named symbols are token symbols. The declarations %left, %right, and %nonassoc inform yacc of the associativity and precedence of the token symbols. All tokens must be declared.
%type
This declaration specifies the C type associated with a non-terminal symbol. If the non-terminal symbol is to be used in actions, it must be declared with a %type declaration.
%union
This declaration specifies the C type of the value associated with each symbol. The type definition consists of a C union definition. The default type is int. When a %type declaration is used, the type specified must be one of the members of the union.
%start
This declaration specifies the starting symbol of the grammar. The default starting symbol is the left-hand side of the first grammar rule.
pure-identifier
This is a grammar symbol that has not had its precedence or type declared. It is assumed to be a token.
pure-literal
This is a literal token that has not had its precedence or type declared. It is assumed to be a token.

Grammar Rules Section

The grammar rules section defines the grammatical structure of the language being described. It consists of one or more grammar rules, which specify the tokens and non-terminal symbols that comprise the language. The grammar rules section is terminated by the second %% line.

A grammar rule has the form:

A : BODY ;

The symbol A represents a non-terminal name, and BODY represents a sequence of zero or more names, literals, and semantic actions that can then be followed by optional precedence rules. Only the names and literals participate in the formation of the grammar; the semantic actions and precedence rules are used in other ways. The : and the ; are yacc punctuation. If there are several successive grammar rules with the same left-hand side, the | can be used to avoid rewriting the left-hand side; in this case the ; appears only after the last rule. The BODY part can be empty (or empty of names and literals) to indicate that the non-terminal symbol matches the empty string.

The yacc utility assigns a unique number to each rule. Rules using the vertical bar notation are distinct rules. The number assigned to the rule appears in the description file.

The elements comprising a BODY are:

name, literal
These form the rules of the grammar: name is either a token or a non-terminal; literal stands for itself (less the lexically required quotation marks).
semantic action

With each grammar rule, the user can associate actions to be performed each time the rule is recognized in the input process. (Note that the word ``action'' can also refer to the actions of the parser—shift, reduce, and so on.)

These actions can return values and can obtain the values returned by previous actions. These values are kept in objects of type YYSTYPE (see %union). The result value of the action shall be kept on the parse stack with the left-hand side of the rule, to be accessed by other reductions as part of their right-hand side. By using the <tag> information provided in the declarations section, the code generated by yacc can be strictly type checked and contain arbitrary information. In addition, the lexical analyzer can provide the same kinds of values for tokens, if desired.

An action is an arbitrary C statement and as such can do input or output, call subprograms, and alter external variables. An action is one or more C statements enclosed in curly braces { and }. The statements shall not contain unbalanced curly brace preprocessing tokens.

Certain pseudo-variables can be used in the action. These are macros for access to data structures known internally to yacc.

$$
The value of the action can be set by assigning it to $$. If type checking is enabled and the type of the value to be assigned cannot be determined, a diagnostic message may be generated.
$number
This refers to the value returned by the component specified by the token number in the right side of a rule, reading from left to right; number can be zero or negative. If number is zero or negative, it refers to the data associated with the name on the parser's stack preceding the leftmost symbol of the current rule. (That is, "$0" refers to the name immediately preceding the leftmost name in the current rule to be found on the parser's stack and "$-1" refers to the symbol to its left.) If number refers to an element past the current point in the rule, or beyond the bottom of the stack, the result is undefined. If type checking is enabled and the type of the value to be assigned cannot be determined, a diagnostic message may be generated.
$<tag>number

These correspond exactly to the corresponding symbols without the tag inclusion, but allow for strict type checking (and preclude unwanted type conversions). The effect is that the macro is expanded to use tag to select an element from the YYSTYPE union (using dataname.tag). This is particularly useful if number is not positive.
$<tag>$
This imposes on the reference the type of the union member referenced by tag. This construction is applicable when a reference to a left context value occurs in the grammar, and provides yacc with a means for selecting a type.

Actions can occur anywhere in a rule (not just at the end); an action can access values returned by actions to its left, and in turn the value it returns can be accessed by actions to its right. An action appearing in the middle of a rule shall be equivalent to replacing the action with a new non-terminal symbol and adding an empty rule with that non-terminal symbol on the left-hand side. The semantic action associated with the new rule shall be equivalent to the original action. The use of actions within rules might introduce conflicts that would not otherwise exist.

By default, the value of a rule shall be the value of the first element in it. If the first element does not have a type (particularly in the case of a literal) and type checking is turned on by %type, an error message shall result.

precedence
The keyword %prec can be used to change the precedence level associated with a particular grammar rule. Examples of this are in cases where a unary and binary operator have the same symbolic representation, but need to be given different precedences, or where the handling of an ambiguous if-else construction is necessary. The reserved symbol %prec can appear immediately after the body of the grammar rule and can be followed by a token name or a literal. It shall cause the precedence of the grammar rule to become that of the following token name or literal. The action for the rule as a whole can follow %prec.

If a program section follows, the application shall ensure that the grammar rules are terminated by %%.

Programs Section

The programs section can include the definition of the lexical analyzer yylex(), and any other functions; for example, those used in the actions specified in the grammar rules. It is unspecified whether the programs section precedes or follows the semantic actions in the output file; therefore, if the application contains any macro definitions and declarations intended to apply to the code in the semantic actions, it shall place them within "%{ ... %}" in the declarations section.

Input Grammar

The following input to yacc yields a parser for the input to yacc. This formal syntax takes precedence over the preceding text syntax description.

The lexical structure is defined less precisely; Lexical Structure of the Grammar defines most terms. The correspondence between the previous terms and the tokens below is as follows.

IDENTIFIER
This corresponds to the concept of name, given previously. It also includes literals as defined previously.
C_IDENTIFIER
This is a name, and additionally it is known to be followed by a <colon>. A literal cannot yield this token.
NUMBER
A string of digits (a non-negative decimal integer).
TYPE, LEFT, MARK, LCURL, RCURL

These correspond directly to %type, %left, %%, %{, and %}.
{ ... }
This indicates C-language source code, with the possible inclusion of '$' macros as discussed previously. 
/* Grammar for the input to yacc. */
/* Basic entries. */
/* The following are recognized by the lexical analyzer. */
%token    IDENTIFIER      /* Includes identifiers and literals */
%token    C_IDENTIFIER    /* identifier (but not literal)
                             followed by a :. */
%token    NUMBER          /* [0-9][0-9]* */
/* Reserved words : %type=>TYPE %left=>LEFT, and so on */
%token    LEFT RIGHT NONASSOC TOKEN PREC TYPE START UNION
%token    MARK            /* The %% mark. */
%token    LCURL           /* The %{ mark. */
%token    RCURL           /* The %} mark. */
/* 8-bit character literals stand for themselves; */
/* tokens have to be defined for multi-byte characters. */
%start    spec
%%
spec  : defs MARK rules tail
      ;
tail  : MARK
      {
        /* In this action, set up the rest of the file. */
      }
      | /* Empty; the second MARK is optional. */
      ;
defs  : /* Empty. */
      |    defs def
      ;
def   : START IDENTIFIER
      |    UNION
      {
        /* Copy union definition to output. */
      }
      |    LCURL
      {
        /* Copy C code to output file. */
      }
        RCURL
      |    rword tag nlist
      ;
rword : TOKEN
      | LEFT
      | RIGHT
      | NONASSOC
      | TYPE
      ;
tag   : /* Empty: union tag ID optional. */
      | '<' IDENTIFIER '>'
      ;
nlist : nmno
      | nlist nmno
      ;
nmno  : IDENTIFIER         /* Note: literal invalid with % type. */
      | IDENTIFIER NUMBER  /* Note: invalid with % type. */
      ;
/* Rule section */
rules : C_IDENTIFIER rbody prec
      | rules  rule
      ;
rule  : C_IDENTIFIER rbody prec
      | '|' rbody prec
      ;
rbody : /* empty */
      | rbody IDENTIFIER
      | rbody act
      ;

        {
          /* Copy action, translate $$, and so on. */
        }
        '}'
      ;

      | PREC IDENTIFIER act
      | prec ';'
      ;

Conflicts

The parser produced for an input grammar may contain states in which conflicts occur. The conflicts occur because the grammar is not LALR(1). An ambiguous grammar always contains at least one LALR(1) conflict. The yacc utility shall resolve all conflicts, using either default rules or user-specified precedence rules.

Conflicts are either shift/reduce conflicts or reduce/reduce conflicts. A shift/reduce conflict is where,

pour un état et un symbole de recherche donnés un symbole, une action de décalage et une action de réduction sont possibles. Un conflit de réduction/réduction est là où, pour un état et un symbole de recherche donnés, les réductions par deux règles différentes sont possibles.

Les règles ci-dessous décrivent comment spécifier les actions à entreprendre lorsqu' un conflit survient. Tous les conflits de décalage/réduction ne peuvent pas être résolus avec succès de cette manière car le conflit peut être dû à quelque chose d'autre que l'ambiguïté, ainsi une utilisation imprudente de ces facilités peut causer le langage accepté par l'analyseur à être très différent de celui qui était prévu. Le fichier de description doit contenir suffisamment d'informations pour comprendre la cause du conflit. Lorsque l'ambiguïté est la raison, les règles par défaut ou explicites devraient suffire à produire un analyseur fonctionnel.

Les précédences et associativités déclarées (voir Section des déclarations) sont utilisées pour résoudre les conflits d'analyse comme suit :

1.
Une précédence et une associativité sont associées à chaque règle de grammaire ; il s'agit de la précédence et de l'associativité du dernier jeton ou littéral dans le corps de la règle. Si le mot-clé %prec est utilisé, il remplace cette valeur par défaut. Certaines règles de grammaire peuvent ne pas avoir à la fois de précédence et d'associativité.
2.
S'il y a un conflit de décalage/réduction, et que la règle de grammaire et le symbole d'entrée ont tous deux une précédence et une associativité associées, alors le conflit est résolu en faveur de l'action (décalage ou réduction) associée à la précédence la plus élevée. Si les précédences sont identiques, alors l'associativité est utilisée ; associative à gauche implique la réduction, associative à droite implique le décalage, et non-associative implique une erreur dans la chaîne en cours d'analyse.
3.
Lorsqu'il y a un conflit de décalage/réduction qui ne peut pas être résolu par la règle 2, le décalage est effectué. Les conflits résolus de cette manière sont comptés dans le diagnostic de sortie décrit dans Gestion des erreurs.
4.
Lorsqu'il y a un conflit de réduction/réduction, une réduction est effectuée par la règle de grammaire qui apparaît plus tôt dans la séquence d'entrée. Les conflits résolus de cette manière sont comptés dans le diagnostic de sortie décrit dans Gestion des erreurs.

Les conflits résolus par précédence ou associativité ne doivent pas être comptés dans les conflits de décalage/réduction et de réduction/réduction signalés par yacc soit sur la sortie standard, soit dans le fichier de description.

Gestion des erreurs

Le jeton error doit être réservé pour la gestion des erreurs. Le nom error peut être utilisé dans les règles de grammaire. Il indique les endroits où l'analyseur peut récupérer d'une erreur de syntaxe. La valeur par défaut de error doit être 256. Sa valeur peut être modifiée à l'aide d'une déclaration %token. L'analyseur lexical ne doit pas retourner la valeur de error.

L'analyseur détectera une erreur de syntaxe lorsqu'il sera dans un état où l'action associée au symbole de recherche est error. Une action sémantique peut amener l'analyseur à initier la gestion des erreurs en exécutant la macro YYERROR. Lorsque YYERROR est exécutée, l'action sémantique transmet le contrôle à l'analyseur. YYERROR ne peut pas être utilisé en dehors des actions sémantiques.

Lorsque l'analyseur détecte une erreur de syntaxe, il appelle normalement yyerror() avec la chaîne de caractères "syntax error" comme argument. L'appel ne doit pas être fait si l'analyseur est encore en train de récupérer d'une erreur précédente lorsque l'erreur est détectée. L'analyseur est considéré comme en train de récupérer d'une erreur précédente jusqu'à ce que l'analyseur ait décalé au moins trois symboles d'entrée normaux depuis la détection de la dernière erreur ou qu'une action sémantique ait exécuté la macro yyerrok. L'analyseur ne doit pas appeler yyerror() lorsque YYERROR est exécutée.

La macro fonction YYRECOVERING doit retourner 1 si une erreur de syntaxe a été détectée et que l'analyseur ne s'en est pas encore complètement remis. Sinon, zéro doit être retourné.

Lorsqu'une erreur de syntaxe est détectée par l'analyseur, l'analyseur doit vérifier si une erreur de syntaxe précédente a été détectée. Si une erreur précédente a été détectée, et si aucun symbole d'entrée normal n'a été décalé depuis la détection de l'erreur précédente, l'analyseur vérifie si le symbole de recherche est un marqueur de fin (voir Interface avec l'analyseur lexical). S'il l'est, l'analyseur doit retourner avec une valeur non nulle. Sinon, le symbole de recherche sera ignoré et l'analyse normale reprendra.

Lorsque YYERROR est exécutée ou lorsque l'analyseur détecte une erreur de syntaxe et qu'aucune erreur précédente n'a été détectée, ou qu'au moins un symbole d'entrée normal a été décalé depuis la détection de l'erreur précédente, l'analyseur doit dépiler un état à la fois jusqu'à ce que la pile d'analyse soit vide ou que l'état actuel permette un décalage sur error. Si l'analyseur vide la pile d'analyse, il doit retourner avec une valeur non nulle. Sinon, il décalera sur error puis reprendra l'analyse normale. Si l'analyseur lit un symbole de recherche avant que l'erreur ne soit détectée, ce symbole doit toujours être le symbole de recherche lorsque l'analyse reprend.

La macro yyerrok dans une action sémantique doit amener l'analyseur à agir comme s'il s'était complètement remis de toute erreur précédente. La macro yyclearin doit amener l'analyseur à ignorer le jeton de recherche actuel. Si le jeton de recherche actuel n'a pas encore été lu, yyclearin n'aura aucun effet.

La macro YYACCEPT doit amener l'analyseur à retourner avec la valeur zéro. La macro YYABORT doit amener l'analyseur à retourner avec une valeur non nulle.

Interface avec l'analyseur lexical

La fonction yylex() est une fonction entière qui retourne un numéro de jeton représentant le type de jeton lu. S'il existe une valeur associée au jeton retourné par yylex() (voir la discussion sur le tag ci-dessus), elle doit être assignée à la variable externe yylval.

Si l'analyseur et yylex() ne sont pas d'accord sur ces numéros de jeton, une communication fiable entre eux ne peut pas se produire. Pour les littéraux (à caractère unique), le jeton est simplement la valeur numérique du caractère dans le jeu de caractères actuel. Les numéros pour les autres jetons peuvent être choisis par yacc, ou choisis par l'utilisateur. Dans les deux cas, la construction #define de C est utilisée pour permettre à yylex() de retourner ces numéros symboliquement. Les instructions #define sont placées dans le fichier de code, et le fichier d'en-tête si ce fichier est demandé. L'ensemble des caractères autorisés par yacc dans un identifiant est plus grand que celui autorisé par C. Les noms de jetons contenant de tels caractères ne doivent pas être inclus dans les déclarations #define.

Si les numéros de jeton sont choisis par yacc, les jetons autres que les littéraux se verront attribuer des numéros supérieurs à 256, bien qu'aucun ordre ne soit implicite. Un jeton peut se voir attribuer explicitement un numéro en suivant sa première apparition dans la section des déclarations avec un numéro. Les noms et les littéraux non définis de cette manière conservent leur définition par défaut. Tous les numéros de jeton assignés par yacc doivent être uniques et distincts des numéros de jeton utilisés pour les littéraux et les jetons assignés par l'utilisateur. Si des numéros de jeton dupliqués causent des conflits dans la génération de l'analyseur, yacc signalera une erreur ; sinon, il n'est pas spécifié si l'affectation de jeton est acceptée ou si une erreur est signalée.

La fin de l'entrée est marquée par un jeton spécial appelé le marqueur de fin, qui a un numéro de jeton nul ou négatif. (Ces valeurs sont invalides pour tout autre jeton.) Tous les analyseurs lexicaux doivent retourner un numéro de jeton nul ou négatif lorsqu'ils atteignent la fin de leur entrée. Si les jetons jusqu'au marqueur de fin, inclus, forment une structure qui correspond au symbole de départ, l'analyseur acceptera l'entrée. Si le marqueur de fin est vu dans un autre contexte, il sera considéré comme une erreur.

Complétion du programme

En plus de yyparse() et yylex(), les fonctions yyerror() et main() sont nécessaires pour former un programme complet. L'application peut fournir main() et yyerror(), ou ces routines peuvent être obtenues de la bibliothèque yacc.

Bibliothèque Yacc

Les fonctions suivantes doivent apparaître uniquement dans la bibliothèque yacc accessible via l'opérande -l y de c99 ; elles peuvent donc être redéfinies par une application conforme :

int main(void)

Cette fonction doit appeler yyparse() et quitter avec une valeur non spécifiée. D'autres actions dans cette fonction ne sont pas spécifiées.
int yyerror(const char *s)

Cette fonction doit écrire l'argument NUL-terminé sur la sortie standard, suivi d'un saut de ligne.

L'ordre des opérandes -l y et -l l donnés à c99 est important ; l'application doit soit fournir sa propre fonction main() soit s'assurer que -l y précède -l l.

Débogage de l'analyseur

L'analyseur généré par yacc doit contenir des installations de diagnostic qui peuvent être activées facultativement soit au moment de la compilation, soit à l'exécution (si activées à la compilation). La compilation du code de débogage d'exécution est sous le contrôle de YYDEBUG, un symbole de préprocesseur. Si YYDEBUG a une valeur non nulle, le code de débogage doit être inclus. Si sa valeur est nulle, le code ne doit pas être inclus.

Dans les analyseurs où le code de débogage a été inclus, la variable externe int yydebug peut être utilisée pour activer le débogage (avec une valeur non nulle) et le désactiver (valeur nulle) à l'exécution. La valeur initiale de yydebug doit être zéro.

Lorsque -t est spécifié, le fichier de code doit être construit de telle sorte que, si YYDEBUG n'est pas déjà défini au moment de la compilation (en utilisant l'option c99 -D YYDEBUG, par exemple), YYDEBUG soit explicitement défini à 1. Lorsque -t n'est pas spécifié, le fichier de code doit être construit de telle sorte que, si YYDEBUG n'est pas déjà défini, il soit explicitement défini à zéro.

Le format de la sortie de débogage n'est pas spécifié, mais il comprend au moins suffisamment d'informations pour déterminer les actions de décalage et de réduction, ainsi que les symboles d'entrée. Il fournit également des informations sur la récupération d'erreur.

yacc

The yacc utility yacc January 2007

DESCRIPTION

The yacc utility reads a grammar description written in an implementation-dependent variant of the Augmented BNF described in Grammar Rules in yacc, and generates a C program that recognizes the source language described by the grammar. The generated C program contains a number of tables and a generic parsing procedure. This procedure, when compiled and linked with the C code generated by a separate lexical analyzer (such as lex), forms a functional parser for the source language.

The parser generator implements a bottom-up parsing technique. It may be table-driven or direct-coded.

A parser generated by yacc shall never request an input symbol from yylex() while in a state where the only actions other than the error action are reductions by a single rule.

The literature of parsing theory defines these concepts.

The implementation shall define the relationship between these values and between them and any error messages that the implementation may generate should it run out of space for any internal structure. An implementation may combine groups of these resources into a single pool as long as the total available to the user does not fall below the sum of the sizes specified by this section.

If any errors are encountered, the run is aborted and yacc exits with a non-zero status. Partial code files and header files may be produced. The summary information in the description file shall always be produced if the -v flag is present.

APPLICATION USAGE

Historical implementations experience name conflicts on the names yacc.tmp, yacc.acts, yacc.debug, y.tab.c, y.tab.h, and y.output if more than one copy of yacc is running in a single directory at one time. The -b option was added to overcome this problem. The related problem of allowing multiple yacc parsers to be placed in the same file was addressed by adding a -p option to override the previously hard-coded yy variable prefix.

The description of the -p option specifies the minimal set of function and variable names that cause conflict when multiple parsers are linked together. YYSTYPE does not need to be changed. Instead, the programmer can use -b to give the header files for different parsers different names, and then the file with the yylex() for a given parser can include the header for that parser. Names such as yyclearerr do not need to be changed because they are used only in the actions; they do not have linkage. It is possible that an implementation has other names, either internal ones for implementing things such as yyclearerr, or providing non-standard features that it wants to change with -p.

Unary operators that are the same token as a binary operator in general need their precedence adjusted. This is handled by the %prec advisory symbol associated with the particular grammar rule defining that unary operator. (See Grammar Rules in yacc.) Applications are not required to use this operator for unary operators, but the grammars that do not require it are rare.

EXAMPLES

Access to the yacc library is obtained with library search operands to c99. To use the yacc library main():

c99 y.tab.c -l y

Both the lex library and the yacc library contain main(). To access the yacc main():

c99 y.tab.c lex.yy.c -l y -l l

This ensures that the yacc library is searched first, so that its main() is used.

The historical yacc libraries have contained two simple functions that are normally coded by the application programmer. These functions are similar to the following code:

#include <locale.h>
int main(void)
{
    extern int yyparse();
    setlocale(LC_ALL, "");
    /* If the following parser is one created by lex, the
       application must be careful to ensure that LC_CTYPE
       and LC_COLLATE are set to the POSIX locale. */
    (void) yyparse();
    return (0);
}
#include <stdio.h>
int yyerror(const char *msg)
{
    (void) fprintf(stderr, "%s\n", msg);
    return (0);
}

RATIONALE

The references in Referenced Documents may be helpful in constructing the parser generator. The referenced DeRemer and Pennello article (along with the works it references) describes a technique to generate parsers that conform to this volume of POSIX.1‐2017. Work in this area continues to be done, so implementors should consult current literature before doing any new implementations. The original Knuth article is the theoretical basis for this kind of parser, but the tables it generates are impractically large for reasonable grammars and should not be used. The ``equivalent to'' wording is intentional to assure that the best tables that are LALR(1) can be generated.

There has been confusion between the class of grammars, the algorithms needed to generate parsers, and the algorithms needed to parse the languages. They are all reasonably orthogonal. In particular, a parser generator that accepts the full range of LR(1) grammars need not generate a table any more complex than one that accepts SLR(1) (a relatively weak class of LR grammars) for a grammar that happens to be SLR(1). Such an implementation need not recognize the case, either; table compression can yield the SLR(1) table (or one even smaller than that) without recognizing that the grammar is SLR(1). The speed of an LR(1) parser for any class is dependent more upon the table representation and compression (or the code generation if a direct parser is generated) than upon the class of grammar that the table generator handles.

The speed of the parser generator is somewhat dependent upon the class of grammar it handles. However, the original Knuth article algorithms for constructing LR parsers were judged by its author to be impractically slow at that time. Although full LR is more complex than LALR(1), as computer speeds and algorithms improve, the difference (in terms of acceptable wall-clock execution time) is becoming less significant.

Potential authors are cautioned that the referenced DeRemer and Pennello article previously cited identifies a bug (an over-simplification of the computation of LALR(1) lookahead sets) in some of the LALR(1) algorithm statements that preceded it to publication. They should take the time to seek out that paper, as well as current relevant work, particularly Aho's.

The -b option was added to provide a portable method for permitting yacc to work on multiple separate parsers in the same directory. If a directory contains more than one yacc grammar, and both grammars are constructed at the same time (by, for example, a parallel make program), conflict results. While the solution is not historical practice, it corrects a known deficiency in historical implementations. Corresponding changes were made to all sections that referenced the filenames y.tab.c (now ``the code file''), y.tab.h (now ``the header file''), and y.output (now ``the description file'').

The grammar for yacc input is based on System V documentation. The textual description shows there that the ';' is required at the end of the rule. The grammar and the implementation do not require this. (The use of C_IDENTIFIER causes a reduce to occur in the right place.)

Also, in that implementation, the constructs such as %token can be terminated by a <semicolon>, but this is not permitted by the grammar. The keywords such as %token can also appear in uppercase, which is again not discussed. In most places where '%' is used, <backslash> can be substituted, and there are alternate spellings for some of the symbols (for example, %LEFT can be "%<" or even "\<").

Historically, <tag> can contain any characters except '>', including white space, in the implementation. However, since the tag must reference an ISO C standard union member, in practice conforming implementations need to support only the set of characters for ISO C standard identifiers in this context.

Décider quand utiliser %prec illustre la difficulté de spécifier le comportement de yacc. Il peut y avoir des situations où la grammaire n'est pas, à proprement parler, erronée, et pourtant yacc ne peut pas l'interpréter sans ambiguïté. Il est souvent plus facile et cela produit généralement un analyseur plus petit de prendre cette alternative lorsqu'elle est appropriée.

La taille et le temps d'exécution d'un programme produit sans le code de débogage d'exécution sont généralement plus petits et légèrement plus rapides dans les implémentations historiques.

Le rapport des tables internes dans le fichier de description est laissé défini par l'implémentation car tous les aspects de ces limites sont également définis par l'implémentation. Certaines implémentations peuvent utiliser des techniques d'allocation dynamique et n'avoir aucune valeur limite spécifique à signaler.

Le format du fichier y.output n'est pas donné car la spécification du format n'a pas été considérée comme améliorant la portabilité des applications. La liste est principalement destinée à aider les utilisateurs humains à comprendre et à déboguer l'analyseur ; l'utilisation de y.output par un script d'application conforme serait inhabituelle. De plus, les implémentations n'ont pas produit de sortie cohérente et aucun format populaire n'était apparent. Le format sélectionné par l'implémentation doit être lisible par l'homme, en plus de l'exigence qu'il s'agisse d'un fichier texte.

Les rapports d'erreurs standard ne sont pas spécifiquement décrits car ils sont rarement utiles aux applications conformes et il n'y avait aucune raison de restreindre les implémentations.

Certaines implémentations reconnaissent "={" comme étant équivalent à '{' car il apparaît dans la documentation historique. Cette construction a été reconnue et documentée comme obsolète dès 1978, dans le Yacc: Yet Another Compiler-Compiler référencé. Ce volume de POSIX.1‐2017 a choisi de la laisser obsolète et de l'omettre.

Les caractères multi-octets doivent être reconnus par l'analyseur lexical et retournés sous forme de jetons. Ils ne doivent pas être retournés sous forme de littéraux de caractères multi-octets. Le jeton error utilisé pour la récupération des erreurs est normalement assigné à la valeur 256 dans l'implémentation historique. Ainsi, la valeur du jeton 256, qui est utilisée dans de nombreux jeux de caractères multi-octets, n'est pas disponible pour être utilisée comme valeur d'un jeton défini par l'utilisateur.
