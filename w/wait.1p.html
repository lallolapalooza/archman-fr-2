WAIT(1P) Manuel du programmeur POSIX WAIT(1P)

PROLOGUE

Cette page de manuel fait partie du Manuel du programmeur POSIX. L'implémentation Linux de cette interface peut différer (consultez la page de manuel Linux correspondante pour les détails du comportement Linux), ou l'interface peut ne pas être implémentée sous Linux.

NOM

wait — attendre l'achèvement d'un processus

SYNTAXE

wait [pid...]

DESCRIPTION

Lorsqu'une liste asynchrone (voir Section 2.9.3.1, Exemples) est lancée par le shell, l'ID de processus de la dernière commande de chaque élément de la liste asynchrone devient connu dans l'environnement d'exécution du shell courant ; voir Section 2.12, Environnement d'exécution du shell.

Si l'utilitaire wait est appelé sans opérande, il attendra que tous les IDs de processus connus du shell appelant se terminent et se terminera avec un statut de sortie de zéro.

Si un ou plusieurs opérandes pid sont spécifiés qui représentent des IDs de processus connus, l'utilitaire wait attendra que tous se terminent. Si un ou plusieurs opérandes pid sont spécifiés qui représentent des IDs de processus inconnus, wait les traitera comme s'ils étaient des IDs de processus connus qui se sont terminés avec un statut de sortie de 127. Le statut de sortie retourné par l'utilitaire wait sera le statut de sortie du processus demandé par le dernier opérande pid.

Les IDs de processus connus ne sont applicables que pour les invocations de wait dans l'environnement d'exécution du shell courant.

OPTIONS

Aucune.

OPÉRANDES

L'opérande suivant sera pris en charge :

pid
L'un des éléments suivants :
1.
L'entier décimal non signé représentant l'ID de processus d'une commande, pour laquelle l'utilitaire doit attendre la terminaison.
2.
Un ID de job de contrôle de job (voir le volume Base Definitions de POSIX.1‐2017, Section 3.204, Job Control Job ID) qui identifie un groupe de processus en arrière-plan à attendre. La notation d'ID de job de contrôle de job n'est applicable que pour les invocations de wait dans l'environnement d'exécution du shell courant ; voir Section 2.12, Environnement d'exécution du shell. Le statut de sortie de wait sera déterminé par la dernière commande du pipeline.
Note :
Le type d'ID de job de contrôle de job de pid n'est disponible que sur les systèmes prenant en charge l'option User Portability Utilities.

ENTRÉE STANDARD

Non utilisé.

FICHIERS D'ENTRÉE

Aucun.

VARIABLES D'ENVIRONNEMENT

Les variables d'environnement suivantes affecteront l'exécution de wait :

LANG
Fournit une valeur par défaut pour les variables d'internationalisation qui sont non définies ou vides. (Voir le volume Base Definitions de POSIX.1‐2017, Section 8.2, Variables d'internationalisation pour la précédence des variables d'internationalisation utilisées pour déterminer les valeurs des catégories de locale.)
LC_ALL
Si défini à une chaîne de caractères non vide, remplace les valeurs de toutes les autres variables d'internationalisation.
LC_CTYPE
Détermine la locale pour l'interprétation des séquences d'octets de données textuelles en caractères (par exemple, caractères mono-octet par opposition aux caractères multi-octets dans les arguments).
LC_MESSAGES

Détermine la locale qui doit être utilisée pour affecter le format et le contenu des messages diagnostiques écrits sur la sortie d'erreur standard.
NLSPATH
Détermine l'emplacement des catalogues de messages pour le traitement de LC_MESSAGES.

ÉVÉNEMENTS ASYNCHRONES

Par défaut.

SORTIE STANDARD

Non utilisée.

SORTIE D'ERREUR STANDARD

La sortie d'erreur standard ne sera utilisée que pour les messages diagnostiques.

FICHIERS DE SORTIE

Aucun.

DESCRIPTION ÉTENDUE

Aucune.

STATUT DE SORTIE

Si un ou plusieurs opérandes ont été spécifiés, qu'ils se sont tous terminés ou n'étaient pas connus du shell appelant, et que le statut du dernier opérande spécifié est connu, le statut de sortie de wait sera les informations de statut de sortie de la commande indiquée par le dernier opérande spécifié. Si le processus s'est terminé anormalement suite à la réception d'un signal, le statut de sortie sera supérieur à 128 et sera distinct du statut de sortie généré par d'autres signaux, mais la valeur exacte n'est pas spécifiée. (Voir l'option kill -l.) Sinon, l'utilitaire wait se terminera avec l'une des valeurs suivantes :

    0
L'utilitaire wait a été appelé sans opérande et tous les IDs de processus connus du shell appelant se sont terminés.
1‐126
L'utilitaire wait a détecté une erreur.
  127
La commande identifiée par le dernier opérande pid spécifié est inconnue.

CONSÉQUENCES DES ERREURS

Par défaut.

Les sections suivantes sont informatives.

UTILISATION PAR L'APPLICATION

Sur la plupart des implémentations, wait est une fonction intégrée au shell. S'il est appelé dans un sous-shell ou un environnement d'exécution utilitaire distinct, tel que l'un des suivants :

(wait)
nohup wait ...
find . -exec wait ... \;

il retourne immédiatement car il n'y a pas d'IDs de processus connus à attendre dans ces environnements.

Les implémentations historiques des shells interactifs ont supprimé le statut de sortie des processus en arrière-plan terminés avant chaque invite du shell. Par conséquent, le statut des processus en arrière-plan était généralement perdu à moins qu'il ne se termine pendant que wait l'attendait. Cela pouvait être un problème sérieux lorsqu'un job censé s'exécuter longtemps se terminait en fait rapidement avec une erreur de syntaxe ou d'initialisation, car le statut de sortie retourné était généralement zéro si l'ID de processus demandé n'était pas trouvé. Ce volume de POSIX.1‐2017 exige que l'implémentation conserve le statut des jobs terminés disponible jusqu'à ce que le statut soit demandé, de sorte que les scripts comme :

j1&
p1=$!
j2&
wait $p1
echo Le job 1 s'est terminé avec le statut $?
wait $!
echo Le job 2 s'est terminé avec le statut $?

fonctionnent sans perdre de statut sur aucun des jobs. Le shell est autorisé à supprimer le statut de tout processus s'il détermine que l'application ne peut pas obtenir l'ID de processus de ce processus à partir du shell. Il est également tenu de ne conserver que {CHILD_MAX} nombre de processus de cette manière. Étant donné que la seule façon d'obtenir l'ID de processus du shell est d'utiliser le paramètre shell '!', le shell est autorisé à supprimer le statut d'une liste asynchrone si "$!" n'a pas été référencé avant qu'une autre liste asynchrone ne soit démarrée. (Cela signifie que le shell n'a qu'à conserver le statut de la dernière liste asynchrone démarrée si l'application n'a pas référencé "$!". wait(1p) - POSIX utilities

PROLOG

This page is a manual page for wait (1p). Part of the IEEE Std 1003.1-2017 (“POSIX.1‗) specification.

The man and mandoc utilities were used to format this page.

NAME

wait - wait for a process to complete

SYNOPSIS

wait [pid...]

DESCRIPTION

The wait utility shall suspend the calling shell until all child processes of that shell have terminated, or until the specified process IDs (PIDs) have terminated. The exit status of wait shall be the exit status of the last process specified by a pid argument to terminate.

If no operands are specified, wait shall suspend the calling shell until all child processes have terminated. If any child process terminates with a non-zero exit status, wait shall return that exit status. Otherwise, wait shall return a zero exit status.

If one or more operands are specified, wait shall suspend the calling shell until each of the specified child processes has terminated. The exit status of wait shall be the exit status of the last specified process to terminate. If a specified process has already terminated, wait shall return immediately with the exit status of that process.

If the shell has not created any child processes, or if all child processes have already terminated, wait shall return immediately with a zero exit status.

The exit status of wait shall be interpreted as described in the EXIT STATUS section.

OPTIONS

None.

OPERANDS

The following operand shall be supported:

“pid”
A decimal integer representing a process ID. If this process ID does not correspond to a child process of the current shell, the behavior is undefined.

STDIN

None.

INPUT FILES

None.

ENVIRONMENT VARIABLES

None.

ASYNCHRONOUS EVENTS

If the shell is waiting for asynchronous events and a specified process terminates, wait shall return the exit status of that process. If no explicit pid arguments are given, and an asynchronous job terminates, the exit status of the shell is affected by the exit status of the terminated job.

STDOUT

None.

STDERR

The standard error shall be used only for diagnostic messages.

OUTPUT FILES

None.

EXTENDED DESCRIPTION

None.

EXIT STATUS

The exit status of wait depends on the exit status of the child processes.

no operands
The exit status is that of the last child process to terminate. If all child processes terminate successfully (exit status 0), wait shall return 0. If any child process terminates with a non-zero exit status, wait shall return the exit status of the last child process to terminate. (Note: the exit status of a process that is terminated by a signal is implementation-defined, but shall be greater than 128.)
operands
The exit status is that of the last child process specified by a pid argument to terminate. If a specified process has already terminated, wait returns immediately with the exit status of that process.

If the exit status is greater than 128, it is the signal number plus 128. (For example, if a process was terminated by signal 9 (SIGKILL), the exit status is 137.)

If wait is unable to determine the exit status of a process (e.g., if the process ID is invalid), it shall return an exit status of 1.

CONSEQUENCES OF ERRORS

None.

APPLICATION USAGE

The shell variable “$!” is set to the PID of the most recently executed asynchronous command. If the shell application is not saving this information, it can use the wait command without operands to discard the exit status of all asynchronous lists. This can be used to trim the list of saved information.

A successful call to wait with no operands discards the exit status of all asynchronous lists.

If the exit status of wait is greater than 128, there is no way for the application to know if the waited-for process exited with that value or was killed by a signal. Since most utilities exit with small values, there is seldom any ambiguity. Even in the ambiguous cases, most applications just need to know that the asynchronous job failed; it does not matter whether it detected an error and failed or was killed and did not complete its job normally.

EXAMPLES

Although the exact value used when a process is terminated by a signal is unspecified, if it is known that a signal terminated a process, a script can still reliably determine which signal by using kill as shown by the following script:

sleep 1000&
pid=$!
kill -KILL $pid
wait $pid
echo $pid was terminated by a SIG$(kill -l $?) signal.

If the following sequence of commands is run in less than 31 seconds:

sleep 257 | sleep 31 &
jobs -l %%

either of the following commands returns the exit status of the second sleep in the pipeline:

wait <pid of sleep 31>
wait %%

RATIONALE

The description of wait does not refer to the waitpid() function from the System Interfaces volume of POSIX.1‐2017 because that would needlessly overspecify this interface. However, the wording means that wait is required to wait for an explicit process when it is given an argument so that the status information of other processes is not consumed. Historical implementations use the wait() function defined in the System Interfaces volume of POSIX.1‐2017 until wait() returns the requested process ID or finds that the requested process does not exist. Because this means that a shell script could not reliably get the status of all background children if a second background job was ever started before the first job finished, it is recommended that the wait utility use a method such as the functionality provided by the waitpid() function.

The ability to wait for multiple pid operands was adopted from the KornShell.

This new functionality was added because it is needed to determine the exit status of any asynchronous list accurately. The only compatibility problem that this change creates is for a script like

while sleep 60 do
    job& echo Job started $(date) as $!  done

which causes the shell to monitor all of the jobs started until the script terminates or runs out of memory. This would not be a problem if the loop did not reference “$!” or if the script would occasionally wait for jobs it started.
