wimapply(1)

Paquet: wimlib

Licences: custom

WIMAPPLY(1) Commandes utilisateur WIMAPPLY(1)

NOM

wimapply - Appliquer une image WIM

SYNTAXE

wimapply FICHIER_WIM [IMAGE] CIBLE [OPTION...]

DESCRIPTION

wimapply, ou de manière équivalente wimlib-imagex apply, extrait ("applique") une image, ou toutes les images, de l'archive Windows Imaging (WIM) FICHIER_WIM.

IMAGE spécifie l'image dans FICHIER_WIM à extraire. Il peut s'agir de l'index 1-basé d'une image, du nom d'une image, ou du mot-clé "all" pour spécifier toutes les images. Il peut être omis si FICHIER_WIM ne contient qu'une seule image. Vous pouvez utiliser wiminfo(1) pour lister les images contenues dans FICHIER_WIM.

CIBLE spécifie où extraire l'image (ou les images). Si CIBLE est un répertoire, alors l'image (ou les images) sera (seront) extraite(s) dans ce répertoire conformément à EXTRACTION DE RÉPERTOIRE (UNIX) ou EXTRACTION DE RÉPERTOIRE (WINDOWS). Si CIBLE n'existe pas, un répertoire y sera d'abord créé. Alternativement, si CIBLE spécifie un périphérique bloc UNIX, alors l'image y sera extraite comme décrit dans EXTRACTION DE VOLUME NTFS (UNIX).

Notez que wimapply est conçu pour extraire, ou "appliquer", des images WIM complètes. Si vous souhaitez plutôt extraire uniquement certains fichiers ou répertoires d'une image WIM, utilisez plutôt wimextract(1).

Si IMAGE est "all", alors toutes les images de FICHIER_WIM seront extraites dans des sous-répertoires de CIBLE nommés d'après les images, en utilisant l'index de l'image comme solution de repli lorsqu'une image n'a pas de nom ou a un nom inhabituel. Ceci n'est pas encore supporté en mode EXTRACTION DE VOLUME NTFS (UNIX).

Si FICHIER_WIM est "-", alors le WIM est lu depuis l'entrée standard plutôt que depuis le disque. Voir WIMS PIPABLES pour plus d'informations.

EXTRACTION DE RÉPERTOIRE (UNIX)

Sur les systèmes de type UNIX, une image WIM peut être extraite dans un répertoire. Ce mode a la limitation que les métadonnées NTFS ou spécifiques à Windows ne seront pas extraites. Bien que certains concepts tels que les liens physiques, les liens symboliques, les horodatages de dernier accès et les horodatages de dernière modification seront traduits en leurs équivalents UNIX, d'autres métadonnées seront perdues (avec des avertissements). Notamment, les types de métadonnées suivants ne seront *pas* extraits dans ce mode :

•
Attributs de fichiers Windows
•
Descripteurs de sécurité Windows (par exemple, propriétaires de fichiers et DACL)
•
Horodatages de création de fichiers
•
Points de reparse autres que les liens symboliques et les points de jonction
•
Flux de données nommés
•
Noms de fichiers courts (également appelés noms 8.3 ou noms DOS).
•
IDs d'objets

Ces mêmes limitations s'appliquent à wimextract. Par conséquent, ce mode est surtout utile dans les situations où les métadonnées spécifiques à NTFS ou à Windows sont sans importance, par exemple lorsque l'on souhaite extraire des fichiers spécifiques, ou lorsque l'on effectue une archivage de fichiers uniquement sur des systèmes de type UNIX, éventuellement en combinaison avec --unix-data. Lorsque les métadonnées spécifiques à Windows sont importantes, soit le mode EXTRACTION DE VOLUME NTFS (UNIX) doit être utilisé, soit la version Windows de wimlib doit être utilisée (voir EXTRACTION DE RÉPERTOIRE (WINDOWS)).

EXTRACTION DE VOLUME NTFS (UNIX)

Sur les systèmes de type UNIX, CIBLE peut également être spécifié comme un périphérique bloc (par exemple, /dev/sda3) contenant un volume NTFS non monté. Dans ce mode, wimapply utilise libntfs-3g pour appliquer l'image WIM spécifiée à la racine du volume NTFS. Le volume cible doit être vide, par exemple nouvellement créé par mkntfs(8). Dans ce mode, les données et métadonnées NTFS et spécifiques à Windows seront extraites, y compris les éléments suivants :

•
Tous les flux de données de tous les fichiers, à l'exception des fichiers chiffrés, y compris le flux de données anonyme ainsi que tous les flux de données nommés.
•
Points de reparse, y compris les liens symboliques, les points de jonction et autres points de reparse.
•
Horodatages de création, d'accès et de modification de fichiers et de répertoires, avec la résolution native NTFS de 100 nanosecondes.
•
Descripteurs de sécurité Windows, y compris tous les composants (propriétaire, groupe, DACL et SACL).
•
Attributs de fichiers Windows
•
Tous les noms de tous les fichiers, y compris les noms dans l'espace de noms Win32, l'espace de noms DOS, l'espace de noms Win32+DOS et l'espace de noms POSIX. Cela inclut les liens physiques.
•
IDs d'objets.

Cependant, les fichiers chiffrés ne seront pas extraits.

La restauration des attributs étendus (EA) n'est pas non plus encore supportée dans ce mode.

Néanmoins, comme presque toutes les informations de l'image WIM sont restaurées dans ce mode, il est possible (et entièrement supporté) de restaurer une image d'une installation Windows réelle en utilisant wimapply sur un système de type UNIX comme alternative à l'utilisation de wimapply ou DISM sous Windows. Dans la section EXEMPLES ci-dessous, il y a un exemple d'application d'une image d'un fichier "install.wim" tel que trouvé sur le média d'installation Windows.

Notez que pour démarrer réellement Windows (Vista ou ultérieur) à partir d'une image "install.wim" appliquée, vous devez également marquer la partition comme "amorçable" et configurer divers fichiers de démarrage, tels que \BOOTMGR et \BOOT\BCD. Cette dernière tâche est plus facilement accomplie en exécutant bcdboot.exe à partir d'un système Windows live tel que Windows PE, mais il existe d'autres options.

Enfin, notez que ce mode utilise libntfs-3g directement, sans passer par le pilote ntfs-3g(8). Par conséquent, il n'y a pas de support spécifique pour appliquer une image WIM à un répertoire sur lequel un système de fichiers NTFS a été monté à l'aide de ntfs-3g(8) ; vous devez le démonter d'abord. Il n'y a pas non plus de support pour appliquer une image WIM à un sous-répertoire du volume NTFS ; vous ne pouvez appliquer qu'à la racine du répertoire.

EXTRACTION DE RÉPERTOIRE (WINDOWS)

Sous Windows, wimapply (et wimextract) supportent nativement les métadonnées NTFS et spécifiques à Windows. Pour de meilleurs résultats, le répertoire cible doit être situé sur un volume NTFS et le programme doit être exécuté avec les privilèges d'Administrateur ; cependant, les systèmes de fichiers non-NTFS et l'exécution sans privilèges d'Administrateur sont également supportés, sous réserve de limitations.

Sous Windows, wimapply essaie d'extraire autant de données et de métadonnées que possible, y compris :

•
Tous les flux de données de tous les fichiers. Cela inclut le contenu de fichier par défaut, ainsi que les flux de données nommés si le volume cible les supporte.
•
Points de reparse, y compris les liens symboliques, les points de jonction et autres points de reparse, si le volume cible les supporte. La restauration des liens symboliques nécessite des privilèges d'Administrateur. Voir également --rpfix et --norpfix pour plus de détails sur la manière dont les liens symboliques et les jonctions absolus sont extraits.
•
Horodatages de création, d'accès et de modification de fichiers et de répertoires, à la plus haute résolution supportée par le volume cible.
•
Descripteurs de sécurité, si le système de fichiers le supporte et si --no-acls n'est pas spécifié. Notez que cela nécessite généralement des privilèges d'Administrateur, et peut n'être que partiellement réussi si le programme est exécuté sans ces privilèges (voir --strict-acls).
•
Attributs de fichiers, y compris cachés, compressés, chiffrés, épars, etc., lorsque le système de fichiers le supporte.
•
Noms courts (également appelés noms 8.3 ou noms DOS).
•
Liens physiques, si le système de fichiers cible les supporte.
•
IDs d'objets, si le système de fichiers cible les supporte.
•
Attributs étendus (EA), si le système de fichiers cible les supporte.

Notes supplémentaires sur l'extraction de fichiers sous Windows :

•
wimapply affichera des avertissements s'il ne parvient pas à extraire les métadonnées et données exactes de l'image WIM en raison des limitations du système de fichiers cible.
•
Étant donné que les fichiers chiffrés (avec FILE_ATTRIBUTE_ENCRYPTED) ne sont pas stockés en clair dans l'image WIM, wimapply ne peut pas restaurer les fichiers chiffrés
aux systèmes de fichiers ne prenant pas en charge le chiffrement. Par conséquent, sur de tels systèmes de fichiers, les fichiers chiffrés ne seront pas extraits. De plus, même si des fichiers chiffrés sont restaurés sur un système de fichiers qui prend en charge le chiffrement, ils ne seront déchiffrables que si la clé de déchiffrement est disponible.
•
Les fichiers dont les noms ne peuvent pas être représentés sous Windows ne seront pas extraits par défaut ; voir --include-invalid-names.
•
Les fichiers dont les chemins complets dépassent 260 caractères (le soi-disant MAX_PATH) seront extraits, mais attention, ces fichiers seront inaccessibles à la plupart des logiciels Windows et pourront ne pas être supprimables facilement.
•
Sous Windows, sauf si l'option --no-acls est spécifiée, wimlib tentera de restaurer les descripteurs de sécurité des fichiers tels qu'ils sont fournis dans l'image WIM. Attention, les installations Windows typiques contiennent des fichiers dont les descripteurs de sécurité ne permettent pas à l'administrateur de les supprimer. Par conséquent, ces fichiers ne pourront pas être supprimés, ou dans certains cas même lus, après extraction, à moins d'être traités avec un programme spécialisé qui sait acquérir les privilèges SE_RESTORE_NAME et/ou SE_BACKUP_NAME qui permettent de remplacer les listes de contrôle d'accès. Ce n'est pas un bug de wimlib, qui fonctionne comme prévu pour restaurer correctement les données qui ont été archivées, mais plutôt un problème avec les droits d'accès que Windows utilise sur certains fichiers. Mais si vous voulez juste les données des fichiers et que les descripteurs de sécurité ne vous intéressent pas, utilisez --no-acls pour ignorer la restauration de tous les descripteurs de sécurité.
•
Une mise en garde similaire s'applique aux attributs de fichiers tels que Lecture seule, Caché et Système. Par conception, sous Windows, wimlib restaurera ces attributs de fichier ; par conséquent, les fichiers extraits peuvent avoir ces attributs. Si ce n'est pas ce que vous souhaitez, utilisez l'option --no-attributes.

WIMS DIVISÉS

Vous pouvez utiliser wimapply pour appliquer des images à partir d'un WIM divisé, ou wimextract pour extraire des fichiers d'un WIM divisé. L'argument WIMFILE doit spécifier la première partie du WIM divisé, tandis que les parties supplémentaires du WIM divisé doivent être spécifiées dans une ou plusieurs options --ref="GLOB". Comme le globbing est intégré à l'option --ref, généralement une seule option --ref est nécessaire. Par exemple, les noms des parties de WIM divisé se présentent habituellement comme suit :

mywim.swm
mywim2.swm
mywim3.swm
mywim4.swm
mywim5.swm

Pour appliquer la première image de ce WIM divisé au répertoire "dir", exécutez :

wimapply mywim.swm 1 dir --ref="mywim*.swm"

WIMS DIFFUSABLES

wimapply prend également en charge l'application d'un WIM à partir d'un fichier non cherchable, tel qu'un tube (pipe), à condition que le WIM ait été capturé dans le format diffusable spécifique à wimlib à l'aide de --pipable (voir wimcapture(1)). Pour utiliser l'entrée standard comme WIM, spécifiez "-" comme WIMFILE. Une utilisation possible de cette fonctionnalité est d'appliquer une image WIM diffusée depuis le réseau. Par exemple, pour appliquer la première image d'un fichier WIM disponible sur un serveur HTTP à un volume NTFS sur /dev/sda1, exécutez quelque chose comme :

wget -O - https://myserver/mywim.wim | wimapply - 1 /dev/sda1

Les WIM diffusables peuvent également être divisés en plusieurs parties, tout comme les WIM normaux. Pour appliquer un WIM diffusable divisé à partir d'un tube, les parties doivent être concaténées et toutes envoyées dans le tube. La première partie doit être envoyée en premier, mais les parties restantes peuvent être envoyées dans n'importe quel ordre.

OPTIONS

--check
Avant d'appliquer l'image, vérifiez l'intégrité de WIMFILE s'il contient des informations d'intégrité supplémentaires.
--ref="GLOB"
Glob de fichiers de WIM supplémentaires ou de parties de WIM divisées pour référencer des ressources. Voir WIMS_DIVISÉS. Cette option peut être spécifiée plusieurs fois. Note : GLOB est entre guillemets car il est interprété par wimapply et peut nécessiter d'être mis entre guillemets pour le protéger de l'expansion du shell.
--rpfix, --norpfix
Définir s'il faut corriger les cibles des liens symboliques absolus (points de reparse dans la terminologie Windows) ou non. Lorsque l'option est activée (--rpfix), les liens symboliques absolus extraits qui sont marqués dans l'image WIM comme étant corrigés sont supposés avoir des cibles absolues relatives à la racine de l'image, et par conséquent wimapply ajoute le chemin absolu du répertoire d'extraction à leurs cibles. L'intention est que vous puissiez appliquer une image contenant des liens symboliques absolus et qu'ils restent valides après leur application à n'importe quel emplacement.
Le comportement par défaut est --rpfix si des images dans WIMFILE ont été capturées avec des corrections de points de reparse effectuées. Sinon, c'est --norpfix.
Les corrections de points de reparse ne sont jamais effectuées en mode d'extraction de volume NTFS sur les systèmes de type UNIX.
--unix-data
(Systèmes de type UNIX uniquement) Restaurer les métadonnées spécifiques à UNIX et les fichiers spéciaux qui ont été capturés par wimcapture avec l'option --unix-data. Cela inclut : les permissions de fichiers UNIX standard (propriétaire, groupe et mode) ; les nœuds de périphériques, les tubes nommés et les sockets ; et les attributs étendus (Linux uniquement).
--no-acls
Ne pas restaurer les descripteurs de sécurité sur les fichiers et répertoires extraits.
--strict-acls
Échouer immédiatement si le descripteur de sécurité complet d'un fichier ou d'un répertoire ne peut pas être défini exactement comme spécifié dans le fichier WIM. Si cette option n'est pas spécifiée, lorsque wimapply sous Windows n'a pas la permission de définir un descripteur de sécurité sur un fichier extrait, il se rabat sur la définition partielle (par exemple, avec SACL omise), et dans le pire des cas l'omet entièrement. Cependant, cela ne devrait être un problème que lorsque wimapply est exécuté sans droits d'administrateur. De plus, sur les systèmes de type UNIX, ce drapeau peut également être combiné avec --unix-data pour faire en sorte que wimapply émette une erreur si les permissions UNIX ne peuvent pas être appliquées à un fichier extrait.
--no-attributes
Ne pas restaurer les attributs de fichiers Windows tels que lecture seule, caché, etc.
--include-invalid-names
Extraire les fichiers et répertoires avec des noms invalides en remplaçant les caractères et en ajoutant un suffixe au lieu de les ignorer. Ce qui est exactement considéré comme un nom "invalide" dépend de la plateforme.
Sur les systèmes compatibles POSIX, les noms de fichiers sont sensibles à la casse et peuvent contenir n'importe quel octet sauf '\0' et '/', donc sur un système compatible POSIX, cette option n'aura d'effet que dans le cas peu probable où l'image WIM contiendrait pour une raison quelconque un nom de fichier contenant l'un de ces caractères.
Sous Windows, les noms de fichiers sont insensibles à la casse(*), ne peuvent pas inclure de caractères de contrôle et ne peuvent pas inclure les caractères '/', '\0', '\', ':', '*', '?', '"', '<', '>' ou '|'. Normalement, les fichiers dans les images WIM devraient également satisfaire ces conditions. Cependant, ce n'est pas garanti, et en particulier une image WIM capturée avec wimcapture sur un système compatible POSIX pourrait contenir de tels fichiers. Par défaut, les noms invalides seront ignorés, et s'il y a plusieurs noms ne différant que par la casse, l'un sera choisi arbitrairement pour l'extraction ; cependant, avec --include-invalid-names, tous les noms seront sanitaires et extraits sous une forme ou une autre.
(*) À moins que le paramètre ObCaseInsensitive n'ait été défini sur 0 dans le registre Windows, auquel cas certains logiciels, y compris la version Windows de wimapply, respecteront les noms de fichiers sensibles à la casse sur NTFS et d'autres systèmes de fichiers compatibles.
--wimboot
Uniquement pour Windows : au lieu d'extraire les fichiers eux-mêmes, extraire des "fichiers pointeurs" vers l'archive WIM. Cela peut entraîner des économies d'espace considérables. Cependant, cela a plusieurs coûts potentiels, comme l'impossibilité de supprimer les archives WIM et un accès potentiellement plus lent aux fichiers. Voir la documentation de Microsoft sur "WIMBoot" pour plus d'informations.
S'il existe, la section [PrepopulateList] du fichier \Windows\System32\WimBootCompress.ini dans l'image WIM sera lue. Les fichiers correspondant à l'un de ces modèles seront extraits normalement, et non en tant que "fichiers pointeurs" WIMBoot. Ceci est utile pour certains fichiers que Windows doit lire tôt dans le processus de démarrage.
Cette option ne fonctionne que lorsque le programme est exécuté en tant qu'administrateur et que le volume cible est NTFS ou un autre système de fichiers prenant en charge les points de reparse.
De plus, cette option fonctionne mieux lorsqu'elle est exécutée sur Windows 8.1 Update 1 ou une version ultérieure, car c'est la première version de Windows qui contient le pilote de filtre de système de fichiers Overlay Windows ("WOF"). Si le pilote WOF est détecté, wimlib créera les "fichiers pointeurs" WIMBoot en utilisant les ioctls documentés fournis par WOF.
Sinon, si le pilote WOF n'est pas détecté, wimlib créera les points de reparse et modifiera manuellement le fichier "\System Volume Information\WimOverlay.dat" sur le volume cible. Ceci est potentiellement sujet à des problèmes, car bien que le code fonctionne dans certains cas testés, aucun de ces formats de données n'est réellement documenté par Microsoft. Avant d'écraser ce fichier, wimlib enregistrera la version précédente dans "\System Volume Information\WimOverlay.wimlib_backup", que vous pourrez potentiellement restaurer si nécessaire.
Vous pouvez toujours effectuer une extraction --wimboot même si l'image WIM n'est pas marquée comme "compatible WIMBoot". Cette option fait que les fichiers extraits sont définis comme "sauvegardés extérieurement" par le fichier WIM. Le pilote de Microsoft qui implémente cette fonctionnalité de "sauvegarde externe" ne semble pas se soucier que les images du WIM soient réellement marquées comme compatibles WIMBoot. Par conséquent, la balise "compatible WIMBoot" (<WIMBOOT> dans les données XML) semble être un simple marqueur d'intention. De plus, le pilote Microsoft peut sauvegarder externement des fichiers à partir de WIM utilisant des blocs XPRESS de taille 8192.
, 16384, et 32768, ou des blocs LZX de taille 32768, en plus des blocs XPRESS par défaut de taille 4096 qui sont créés lorsque wimcapture est exécuté avec l'option --wimboot.
--compact=FORMAT
Windows uniquement : compresse les fichiers extraits à l'aide de la compression système, lorsque cela est possible. Cela ne fonctionne que sur Windows 10 ou une version ultérieure, ou sur une ancienne version de Windows à laquelle le pilote wofadk.sys de Microsoft a été ajouté. Plusieurs formats de compression différents peuvent être utilisés avec la compression système, et un doit être spécifié comme FORMAT. Les choix sont : xpress4k, xpress8k, xpress16k et lzx.
Les exclusions sont gérées de la même manière qu'avec l'option --wimboot. C'est-à-dire : si elle existe, la section [PrepopulateList] du fichier \Windows\System32\WimBootCompress.ini dans l'image WIM sera lue, et les fichiers correspondant à l'un des modèles de cette section ne seront pas compressés. De plus, wimlib dispose d'une liste codée en dur de fichiers pour lesquels il sait, pour assurer la compatibilité avec le chargeur de démarrage Windows, qu'il doit remplacer le format de compression demandé.
--recover-data
Si un fichier est corrompu (son hachage stocké ne correspond pas à son hachage réel, ou certaines parties ne peuvent pas être décompressées), extrait le fichier corrompu de toute façon avec un avertissement, plutôt que d'interrompre avec une erreur. Cela peut être utile pour récupérer des données si une archive WIM a été corrompue. Notez que la récupération de données n'est pas garantie de réussir, car elle dépend du type de corruption survenu.

NOTES

Intégrité des données : les fichiers WIM incluent des sommes de contrôle des données des fichiers. Pour détecter une corruption accidentelle (non malveillante) des données, wimlib calcule la somme de contrôle de chaque fichier qu'il extrait et émet une erreur si elle n'a pas la valeur attendue, sauf si l'option --recover-data est donnée. (Ce comportement par défaut semble équivalent à l'option /verify d'ImageX.) De plus, un fichier WIM peut inclure une table d'intégrité (sommes de contrôle supplémentaires) sur les données brutes de l'ensemble du fichier WIM. Pour des raisons de performance, wimlib ne vérifie pas la table d'intégrité par défaut, mais l'option --check peut être passée pour le faire.

Fichiers ESD : wimlib peut extraire des fichiers de WIM compressés en mode continu, ou des fichiers "ESD" (.esd), tout comme des fichiers WIM (.wim) normaux. Cependant, Microsoft distribue parfois des fichiers ESD avec des segments cryptés ; wimlib ne peut pas extraire de tels fichiers tant qu'ils n'ont pas été préalablement décryptés.

Sécurité : wimlib a été soigneusement écrit pour valider toutes les entrées et est censé être sécurisé contre certains types d'attaques qui affectent souvent d'autres programmes d'archivage de fichiers, par exemple les attaques par traversée de répertoire (auxquelles, incidemment, le logiciel WIM de Microsoft est vulnérable). Les parties importantes de wimlib, par exemple les décompresseurs, ont également été testées par fuzzing. Cependant, wimlib n'est actuellement pas conçu pour se protéger contre certains types d'attaques par déni de service (DOS), par exemple l'épuisement de la mémoire ou les "zip bombs".

EXEMPLES

Extraire la première image du WIM de Windows PE sur le support d'installation de Windows vers le répertoire "boot" :

wimapply /mnt/windows/sources/boot.wim 1 boot

Sous Windows, appliquer une image d'un volume entier, par exemple à partir de "install.wim" qui se trouve sur le support d'installation de Windows :

wimapply install.wim 1 E:\

Identique à ci-dessus, mais exécuté sur un système de type UNIX où la partition correspondante est /dev/sda2 :

wimapply install.wim 1 /dev/sda2

Notez qu'avant d'exécuter l'une des commandes ci-dessus, un système de fichiers NTFS peut devoir être créé sur la partition, par exemple avec format.exe sous Windows ou mkntfs(8) sur les systèmes de type UNIX. Par exemple, sous UNIX, vous pourriez exécuter :

mkntfs /dev/sda2 && wimapply install.wim 1 /dev/sda2

(Bien sûr, ne faites pas cela si vous ne voulez pas détruire toutes les données existantes sur la partition !)

Voir WIMS PARTITIONNÉS et WIMS EN FLUX pour des exemples d'application de WIM partitionnés et en flux, respectivement.
