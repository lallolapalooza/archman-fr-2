WIMCAPTURE(1) Commandes utilisateur WIMCAPTURE(1)

NOM

wimcapture, wimappend - Capturer ou ajouter une image WIM

SYNOPIS

wimcapture SOURCE WIMFILE [NOM_IMAGE  [DESC_IMAGE]] [OPTION...]
wimappend SOURCE WIMFILE [NOM_IMAGE  [DESC_IMAGE]] [OPTION...]

DESCRIPTION

Les commandes wimcapture (équivalent : wimlib-imagex capture) et wimappend (équivalent : wimlib-imagex append) créent (« capturent ») une nouvelle image Windows Imaging (WIM). wimcapture crée une nouvelle archive WIM WIMFILE pour contenir la nouvelle image, tandis que wimappend ajoute l'image à l'archive WIM existante WIMFILE (ou, avec --create, la crée si nécessaire).

SOURCE spécifie l'emplacement des fichiers à partir desquels créer l'image WIM. Si SOURCE est un répertoire ou un lien symbolique pointant vers un répertoire, alors l'image est capturée depuis ce répertoire conformément à la description de CAPTURE DE RÉPERTOIRE (UNIX) ou CAPTURE DE RÉPERTOIRE (WINDOWS). Alternativement, si --source-list est spécifié, alors SOURCE est interprété comme un fichier contenant une liste de fichiers et de répertoires à inclure dans l'image. Toujours alternativement, si SOURCE est un périphérique bloc UNIX, alors une image est capturée depuis le volume NTFS qu'il contient, conformément à la description de CAPTURE DE VOLUME NTFS (UNIX).

NOM_IMAGE et DESC_IMAGE spécifient le nom et la description à donner à la nouvelle image. Si NOM_IMAGE n'est pas spécifié, il prend par défaut le nom de fichier de SOURCE, en ajoutant un suffixe unique si nécessaire. Sinon, NOM_IMAGE doit être soit un nom non déjà utilisé par une image dans WIMFILE, soit la chaîne vide pour créer une image sans nom. Si DESC_IMAGE n'est pas spécifié, la nouvelle image n'aura pas de description.

Si WIMFILE est spécifié comme « - », alors l'option --pipable est supposée et une WIM transmissible par canalisation est écrite sur la sortie standard (c'est une extension de wimlib).

CAPTURE DE RÉPERTOIRE (UNIX)

Sur les systèmes de type UNIX, si SOURCE spécifie un répertoire ou un lien symbolique vers un répertoire, alors l'image WIM sera capturée depuis ce répertoire. Le répertoire peut être sur n'importe quel type de système de fichiers, et les points de montage sont suivis. Dans ce mode, les types d'informations suivants sont capturés :

•
Répertoires et fichiers réguliers, ainsi que le contenu des fichiers réguliers.
•
Liens physiques.
•
Liens symboliques (traduits sans perte en points d'analyse Windows).
•
Horodatages de dernière modification (mtime) et de dernier accès (atime) avec une granularité de 100 nanosecondes.
•
Les fichiers qui semblent être creux (sparse) seront marqués comme tels, mais leurs données complètes seront quand même stockées, soumises à la compression habituelle.
•
Avec --unix-data : permissions de fichiers UNIX standard (propriétaire, groupe et mode).
•
Avec --unix-data : nœuds de périphériques, tubes nommés et sockets.
•
Avec --unix-data : attributs étendus (Linux uniquement).

Il n'y a pas de support pour stocker les horodatages de derniers changements d'état (ctime), ni les informations de liens physiques pour les liens symboliques (chaque lien symbolique sera stocké comme un fichier distinct). De plus, les noms de fichiers et les cibles de liens symboliques qui ne sont pas des noms UTF-8 valides avec l'ajout de points de code de substitution ne sont pas pris en charge. Notez que si vous avez un système de fichiers contenant des noms de fichiers dans un autre encodage multibyte, tel que l'ISO-8859-1, et que vous souhaitez l'archiver avec wimlib, vous pourriez être en mesure de le monter avec une option qui fait que ses noms de fichiers soient présentés en UTF-8.

CAPTURE DE VOLUME NTFS (UNIX)

Sur les systèmes de type UNIX, SOURCE peut également être spécifié comme un périphérique bloc (par exemple, /dev/sda3) contenant un volume NTFS non monté. Dans ce mode, wimcapture utilise libntfs-3g pour capturer une image WIM depuis le répertoire racine du volume NTFS. Dans ce mode, autant de données et de métadonnées que possible sont capturées, y compris les métadonnées spécifiques NTFS et Windows :

•
Tous les flux de données de tous les fichiers non chiffrés, y compris le flux de données sans nom ainsi que tous les flux de données nommés.
•
Points d'analyse. Voir POINTS D'ANALYSE ET LIENS SYMBOLIQUES pour plus de détails.
•
Horodatages de création, d'accès et de modification de fichiers et répertoires, en utilisant la résolution native NTFS de 100 nanosecondes.
•
Descripteurs de sécurité Windows, y compris tous les composants (propriétaire, groupe, DACL et SACL).
•
Indicateurs d'attributs de fichiers DOS/Windows.
•
Tous les noms de tous les fichiers, y compris les noms dans l'espace de noms Win32, l'espace de noms DOS, l'espace de noms Win32+DOS et l'espace de noms POSIX. Cela inclut les liens physiques.
•
Identifiants d'objet.

Cependant, les principales limitations de ce mode sont :

•
Les fichiers chiffrés sont exclus.
•
Les attributs étendus (EA) ne sont pas encore stockés.
•
Les fichiers creux seront marqués comme tels, mais leurs données complètes seront quand même stockées, soumises à la compression habituelle.
•
Certains types de points d'analyse sont transparentement déréférencés par Windows mais pas par NTFS-3G. Voir POINTS D'ANALYSE ET LIENS SYMBOLIQUES.

Notez que ce mode utilise libntfs-3g directement, sans passer par le pilote ntfs-3g(8). Par conséquent, il n'y a pas de support spécial pour capturer une image WIM à partir d'un répertoire sur lequel un système de fichiers NTFS a été monté en utilisant ntfs-3g(8) ; vous devez d'abord le démonter. Il n'y a pas non plus de support pour capturer un sous-répertoire du volume NTFS ; vous ne pouvez capturer que le volume entier.

CAPTURE DE RÉPERTOIRE (WINDOWS)

Sous Windows, wimcapture et wimappend prennent en charge nativement les données spécifiques à Windows et NTFS. Ils agissent donc de manière similaire aux commandes correspondantes d'ImageX ou de DISM de Microsoft. Pour de meilleurs résultats, le répertoire capturé doit se trouver sur un volume NTFS et le programme doit être exécuté avec des privilèges d'administrateur ; cependant, les systèmes de fichiers non NTFS et l'exécution sans privilèges d'administrateur sont également pris en charge, sous réserve de limitations.

Sous Windows, wimcapture et wimappend tentent de capturer autant de données et de métadonnées que possible, y compris :

•
Tous les flux de données de tous les fichiers.
•
Points d'analyse, si pris en charge par le système de fichiers source. Voir POINTS D'ANALYSE ET LIENS SYMBOLIQUES pour plus de détails.
•
Horodatages de création, d'accès et de modification de fichiers et répertoires. Ceux-ci sont stockés avec la résolution native de Windows de 100 nanosecondes.
•
Descripteurs de sécurité, si pris en charge par le système de fichiers source et si --no-acls n'est pas spécifié. Remarque : lorsque vous n'êtes pas exécuté en tant qu'administrateur, les descripteurs de sécurité peuvent être capturés partiellement (voir --strict-acls).
•
Attributs de fichiers, y compris cachés, creux, compressés, chiffrés, etc. Les fichiers chiffrés seront stockés sous forme chiffrée plutôt qu'en texte brut. Les fichiers compressés de manière transparente seront lus comme non compressés et stockés en fonction de la propre compression du WIM. Il n'y a pas de traitement spécial pour le stockage de fichiers creux, mais ils sont susceptibles d'être compressés en une petite taille.
•
Noms DOS (8.3) des fichiers ; cependant, l'échec de leur lecture n'est pas considéré comme une condition d'erreur.
•
Liens physiques, si pris en charge par le système de fichiers source.
•
Identifiants d'objet, si pris en charge par le système de fichiers source.
•
Attributs étendus (EA), si pris en charge par le système de fichiers source.

POINTS D'ANALYSE ET LIENS SYMBOLIQUES

Un « lien symbolique » (ou « symlink ») est un fichier spécial qui « pointe vers » un autre fichier ou répertoire. Sous Windows, un « point d'analyse » est une généralisation d'un lien symbolique qui permet de rediriger l'accès à un fichier ou un répertoire de manière plus complexe. Windows utilise les points d'analyse pour implémenter les liens symboliques et les utilise parfois pour diverses autres fonctionnalités. Normalement, les applications peuvent choisir si elles souhaitent « déréférencer » les points d'analyse et les liens symbo

mlinks ou pas.

Le comportement par défaut de wimcapture est que les points de réanalyse et les liens symboliques ne sont *pas* déréférencés, ce qui signifie que les points de réanalyse ou les liens symboliques eux-mêmes sont stockés dans l'archive plutôt que les fichiers ou les données auxquels ils pointent. Il existe une option --dereference, mais elle n'est actuellement prise en charge que par la version UNIX de wimcapture sur les systèmes de fichiers UNIX (elle n'est pas encore implémentée pour les systèmes de fichiers Windows).

Windows traite également certains types de points de réanalyse spécialement. Par exemple, les applications Windows lisant des fichiers dédupliqués, basés sur WIM ou compressés par le système voient toujours les données déréférencées, même si elles demandent le contraire. Par conséquent, wimcapture sous Windows stockera ces fichiers déréférencés, et non comme des points de réanalyse. Mais wimcapture sous UNIX en mode NTFS-3G ne peut pas déréférencer ces fichiers et les stockera comme des points de réanalyse à la place. Cette différence peut être significative dans certaines situations, par exemple lors de la capture de fichiers dédupliqués qui, pour être lisibles après extraction, nécessitent que le stockage des blocs soit également présent.

OPTIONS

--boot
Marque la nouvelle image comme étant l'image "amorçable" du WIM. L'image "amorçable" est l'image que le chargeur de démarrage Windows utilisera lors du chargement de Windows PE à partir du WIM.
--check
Inclut des informations d'intégrité supplémentaires dans le fichier WIM résultant. Avec wimappend, vérifie également l'intégrité du WIM avant d'y ajouter. Vérifie également l'intégrité des WIM spécifiés par --update-of et/ou --delta-from.
--include-integrity
Inclut des informations d'intégrité supplémentaires dans le fichier WIM résultant, c'est-à-dire comme --check mais sans aucune vérification préalable.
--compress=TYPE[:LEVEL]
Avec wimcapture, utilise le format de compression spécifié dans le nouveau fichier WIM. TYPE peut être "none", "XPRESS" (alias : "fast"), "LZX" (alias : "maximum") ou "LZMS" (alias : "recovery"). TYPE est insensible à la casse. La valeur par défaut est "LZX".
Vous pouvez éventuellement spécifier également un niveau de compression entier LEVEL. Le niveau de compression spécifie la rigueur avec laquelle l'algorithme de compression pour le TYPE de compression spécifié travaillera pour compresser les données. Les valeurs sont mises à l'échelle de telle sorte que 20 soit une compression rapide, 50 une compression moyenne et 100 une compression élevée. Cependant, vous pouvez choisir n'importe quelle valeur et pas seulement ces valeurs particulières. La valeur par défaut est 50.
Cette option n'affecte que le type de compression utilisé dans les ressources WIM non solides. Si vous créez un WIM solide (en utilisant l'option --solid), vous voudrez probablement --solid-compress à la place.
Soyez prudent si vous choisissez la compression LZMS. Elle n'est pas compatible avec wimlib avant la v1.6.0, WIMGAPI avant Windows 8, DISM avant Windows 8.1 et 7-Zip avant la v15.12. Notez également que le choix de la compression LZMS n'implique pas automatiquement la compression en mode solide, comme c'est le cas avec DISM. Utilisez --solid si vous voulez créer un WIM solide, ou un "fichier ESD".
--chunk-size=TAILLE
Avec wimcapture, utilise une taille de bloc de compression de TAILLE octets. Une taille de bloc de compression plus grande donne un meilleur taux de compression. wimlib prend en charge différentes tailles de blocs en fonction du type de compression :
•
XPRESS : 4K, 8K, 16K, 32K, 64K
•
LZX : 32K, 64K, 128K, 256K, 512K, 1M, 2M
•
LZMS : 32K, 64K, 128K, 256K, 512K, 1M, 2M, 4M, 8M, 16M, 32M, 64M, 128M, 256M, 512M, 1G
Vous pouvez fournir le nombre complet (par exemple, 32768), ou vous pouvez utiliser l'un des suffixes K, M ou G. KiB, MiB et GiB sont également acceptés.
Cette option n'affecte que la taille des blocs utilisée dans les ressources WIM non solides. Si vous créez un WIM solide (en utilisant l'option --solid), vous voudrez probablement --solid-chunk-size à la place.
Utilisez cette option avec prudence si la compatibilité avec les logiciels WIM de Microsoft est souhaitée, car leur logiciel a un support limité pour les tailles de blocs non par défaut.
--solid
Avec wimcapture, crée un fichier WIM "solide" qui compresse les fichiers ensemble plutôt qu'indépendamment. Cela entraîne un taux de compression nettement meilleur, mais cela se fait au prix d'une compression lente avec une utilisation très élevée de la mémoire, une compatibilité réduite et un accès aléatoire lent au fichier WIM résultant.
Par défaut, cela active la compression LZMS solide, créant ainsi un fichier équivalent à celui créé avec l'option /compress:recovery de DISM. Ces fichiers sont également appelés "fichiers ESD" et ont été supportés pour la première fois par WIMGAPI sous Windows 8, par DISM sous Windows 8.1 et par 7-Zip 15.12.
--solid-compress=TYPE[:LEVEL]
Comme --compress, mais définit le type de compression utilisé dans les ressources solides. La valeur par défaut est la compression LZMS. Cette option n'a d'effet que lorsque --solid est également spécifié.
--solid-chunk-size=TAILLE
Comme --chunk-size, mais définit la taille des blocs utilisée dans les ressources solides. La valeur par défaut, en supposant la compression LZMS, est 64MiB (67108864) ; cela nécessite environ 640MiB de mémoire par thread. Cette option n'a d'effet que lorsque --solid est également spécifié. Remarque : le logiciel WIM de Microsoft n'est pas compatible avec les tailles de blocs LZMS supérieures à 64MiB.
--threads=NB_THREADS
Nombre de threads à utiliser pour compresser les données. Défaut : autodétection (nombre de CPU disponibles).
--rebuild
Avec wimappend, reconstruit l'intégralité du WIM plutôt que d'y ajouter les nouvelles données à la fin. La reconstruction du WIM est plus lente, mais permet d'économiser de l'espace qui serait autrement laissé comme un trou dans le WIM. Voir aussi wimoptimize(1).
--flags=EDITIONID
Spécifie une chaîne à utiliser dans l'élément <FLAGS> des données XML pour la nouvelle image.
--image-property NOM=VALEUR
Attribue une propriété arbitraire à la nouvelle image dans le document XML du WIM. VALEUR est la chaîne à définir comme valeur de la propriété. NOM est le nom de la propriété de l'image, par exemple "NAME", "DESCRIPTION" ou "TOTALBYTES". Le nom peut contenir des barres obliques pour indiquer un élément XML imbriqué ; par exemple, "WINDOWS/VERSION/BUILD" indique l'élément BUILD imbriqué dans l'élément VERSION imbriqué dans l'élément WINDOWS. Un nombre entre crochets peut être utilisé pour indiquer l'un des plusieurs éléments de même nom ; par exemple, "WINDOWS/LANGUAGES/LANGUAGE[2]" indique le deuxième élément "LANGUAGE" imbriqué dans l'élément "WINDOWS/LANGUAGES". Lors de l'ajout d'une liste d'éléments de cette manière, ils doivent être spécifiés dans l'ordre séquentiel. Notez que les noms d'éléments sont sensibles à la casse. Cette option peut être spécifiée plusieurs fois.
--dereference
(Systèmes de type UNIX uniquement) Suit les liens symboliques et archive les fichiers auxquels ils pointent, plutôt que d'archiver les liens eux-mêmes.
--config=FICHIER
Spécifie un fichier de configuration (encodé en UTF-8 ou UTF-16LE ; ASCII brut fonctionne aussi) pour la capture de la nouvelle image. Le fichier de configuration spécifie les fichiers qui doivent être traités spécialement pendant la capture de l'image.
Le format du fichier de configuration est de style INI ; c'est-à-dire qu'il est organisé en sections entre crochets. Actuellement, les sections suivantes sont reconnues :
•
[ExclusionList] --- contient une liste de globs de chemins à exclure de la capture. Si un répertoire est trouvé, le répertoire et son contenu sont exclus.
•
[ExclusionException] --- contient une liste de globs de chemins à inclure, même si le fichier ou le répertoire correspond également à un glob dans [ExclusionList]. Si un répertoire est trouvé, tout son contenu est également inclus. Les fichiers ou répertoires *dans* un répertoire exclu par [ExclusionList] peuvent même être inclus en utilisant ceci, bien qu'actuellement cela ne fonctionne que pour les globs absolus (ceux qui commencent par "/" ou "\") ; par exemple, "/dir/file" peut être inclus alors que "/dir" peut être exclu, mais inclure simplement "file" ne fonctionnera pas dans ce cas.
•
[PrepopulateList] --- cela n'affecte pas la capture, mais si l'image est appliquée plus tard avec --wimboot, il s'agit de globs de fichiers qui seront extraits normalement, et non comme des "fichiers pointeurs" de WIMBoot. Si un répertoire est trouvé, tous les fichiers et sous-répertoires sont également trouvés récursivement.
Les globs de chemins peuvent contenir les métacaractères '*' et '?'. Les globs relatifs (par exemple, *.mp3) correspondent à un nom de fichier dans n'importe quel répertoire. Les globs absolus (par exemple, /dir/file) sont traités comme des chemins commençant au répertoire principal en cours de capture, ou à la racine du volume NTFS en mode de capture de volume NTFS. N'utilisez pas de lettres de lecteur dans les chemins ; elles seront ignorées. Les séparateurs de chemin peuvent être des barres obliques ou des barres inversées.
Les lignes commençant par les caractères '#' ou ';' sont traitées comme des commentaires et ignorées. Les globs contenant des espaces blancs n'ont pas besoin d'être mis entre guillemets ; cependant, s'ils le sont, les guillemets doubles et simples sont acceptés.
Si cette option n'est pas spécifiée, le fichier de configuration par défaut suivant est utilisé :
[ExclusionList]
\$ntfs.log
\hiberfil.sys
\pagefile.sys
\swapfile.sys
\System Volume Information
\RECYCLER
\$RECYCLE.BIN
\$Recycle.Bin
\Windows\CSC
Cependant, un comportement spécial s'applique si --wimboot est également spécifié. Par défaut, avec --wimboot spécifié, le fichier Windows/System32/WimBootDans le répertoire capturé, Compress.ini sera utilisé comme fichier de configuration. Cependant, cela peut être remplacé en utilisant --config ; et cela provoque également l'enregistrement du fichier de configuration spécifié dans l'image WIM sous le nom Windows/System32/WimBootCompress.ini, remplaçant celui qui pourrait être présent sur le système de fichiers.
--unix-data
(Systèmes de type UNIX uniquement) Stocker les métadonnées et fichiers spéciaux spécifiques à UNIX. Cela comprend : les permissions de fichiers UNIX standard (propriétaire, groupe et mode) ; les nœuds de périphériques, les tubes nommés et les sockets ; et les attributs étendus (Linux uniquement). Ces informations peuvent être ultérieurement restaurées par wimapply avec l'option --unix-data.
Les informations spécifiques à UNIX sont ignorées par le logiciel WIM de Microsoft et par la version Windows de wimlib.
--no-acls
Ne pas capturer les descripteurs de sécurité des fichiers.
--strict-acls
Échouer immédiatement si le descripteur de sécurité complet d'un fichier ne peut pas être lu. Sous Windows, le comportement par défaut sans cette option est d'essayer d'abord d'omettre le SACL du descripteur de sécurité, puis d'essayer d'omettre complètement le descripteur de sécurité. Le but est de capturer autant de données que possible sans toujours requérir les privilèges d'administrateur. Cependant, si vous souhaitez que tous les descripteurs de sécurité soient capturés exactement, vous pourriez souhaiter fournir cette option, bien que l'administrateur doive avoir la permission de tout lire de toute façon.
--rpfix, --norpfix
Définir s'il faut corriger les cibles des liens symboliques absolus (points de réanalyse dans la terminologie Windows) ou non. Lorsqu'il est activé (--rpfix), les liens symboliques absolus qui pointent à l'intérieur de l'arborescence de répertoires capturée seront ajustés pour être absolus par rapport à la racine de l'arborescence de répertoires capturée. Lorsqu'il est désactivé (--norpfix), les liens symboliques absolus seront capturés tels quels.
Le comportement par défaut de wimcapture est équivalent à --rpfix. Le comportement par défaut de wimappend est équivalent à --rpfix si des corrections de points de réanalyse ont été effectuées précédemment sur WIMFILE, sinon --norpfix.
Dans le cas d'une capture multi-sources (--source-list spécifié), il est recommandé de passer --norpfix. Sinon, les corrections de points de réanalyse seront désactivées sur toutes les sources de capture destinées à des emplacements non racine dans l'image WIM, tandis que les sources de capture destinées à la racine WIM recevront le comportement par défaut du paragraphe précédent.
--source-list
wimcapture et wimappend prennent en charge la création d'une image WIM à partir de plusieurs fichiers ou répertoires distincts. Lorsque --source-list est spécifié, l'argument SOURCE spécifie le nom d'un fichier texte, dont chaque ligne est soit 1, soit 2 chemins de fichiers séparés par des espaces. Le premier chemin de fichier, la source, spécifie le chemin d'un fichier ou d'un répertoire à capturer dans l'image WIM. Il peut être absolu ou relatif au répertoire de travail actuel. Le second chemin de fichier, s'il est fourni, est la cible et spécifie le chemin dans l'image WIM où ce fichier ou répertoire sera enregistré. Les barres obliques de début et de fin dans la cible sont ignorées, sauf si elle est entièrement constituée de barres obliques (par exemple, "/"), ce qui indique que le répertoire doit devenir la racine de l'image WIM. Si elle est omise, la chaîne cible est par défaut la même que la chaîne source.
Un exemple de fichier source list est le suivant :
# Créer l'image WIM à partir du répertoire 'winpe'
winpe	/
# Envoyer le répertoire 'overlay' vers '/overlay' dans l'image WIM
overlay	/overlay
# Superposer un répertoire séparé directement sur la racine de l'image WIM.
/data/stuff	/
Les sous-répertoires dans le WIM sont créés si nécessaire. Plusieurs répertoires sources peuvent partager la même cible, ce qui implique une superposition. Dans le cas où cela résulterait à ce qu'un fichier non-répertoire soit ajouté à l'image WIM plusieurs fois, la dernière version (telle qu'énumérée dans le fichier source list) remplace toute version antérieure.
Les chemins de fichiers contenant des espaces peuvent être entourés d'apostrophes ou de guillemets. Les guillemets ne peuvent pas être échappés.
Les lignes ne contenant que des espaces et les lignes commençant par '#' précédées d'espaces optionnels sont ignorées.
À titre spécial, si SOURCE est "-", la liste source est lue depuis l'entrée standard plutôt que depuis un fichier externe.
Le mode de capture de volume NTFS sur les systèmes de type UNIX ne peut pas être utilisé avec --source-list, car seule la capture d'un volume NTFS complet est prise en charge.
--pipable
Avec wimcapture, créez un WIM "pipable" spécifique à wimlib qui peut être capturé et appliqué entièrement séquentiellement. Si WIMFILE est spécifié comme "-", alors le WIM pipable est écrit directement sur la sortie standard ; sinon, il est écrit sur disque comme d'habitude. L'image dans le WIM pipable peut être appliquée plus tard avec wimapply, soit depuis le disque, soit depuis l'entrée standard. Une utilisation typique des WIM pipables pourrait impliquer de diffuser l'image WIM vers un serveur distant lors de sa capture et/ou de diffuser l'image WIM depuis un serveur distant lors de son application.
Généralement, toutes les commandes wimlib-imagex fonctionnent sur les WIM pipables et non pipables. wimoptimize et wimexport peuvent également être utilisés pour convertir entre WIM pipables et WIM non pipables. Cependant, il existe quelques limitations pour les WIM pipables :
•
Les WIM pipables sont une extension de wimlib qui ne sont *pas* compatibles avec le logiciel WIM de Microsoft ou avec d'autres programmes comme 7-Zip.
•
En utilisant wimappend, plusieurs images peuvent être ajoutées à un WIM pipable. Ceci est pris en charge, bien que moins efficace que de le faire avec des WIM non pipables car un WIM pipable est entièrement reconstruit à chaque fois qu'il est ajouté ; et lors du piping d'un tel WIM vers wimapply pour extraire une image, certaines données inutiles seront envoyées sur le pipe.
•
Bien qu'une image WIM pipable puisse être mise à jour à l'aide de wimupdate, cela nécessite une reconstruction complète du fichier WIM, ce qui la rend moins efficace que la mise à jour d'un WIM non pipable.
•
Les WIM pipables solides ne sont pas encore pris en charge.
--not-pipable
Avec wimappend, reconstruire le fichier WIM au format non-pipable (régulier). Cette option est seulement utile si vous ajoutez une image à un WIM pipable (voir --pipable) que vous souhaitez plutôt au format non-pipable. Notez que wimoptimize(1) peut également être utilisé pour convertir entre WIM non-pipables et pipables.
--update-of=[WIMFILE:]IMAGE
Indiquer que l'image capturée ou ajoutée à partir de SOURCE est globalement la même que l'image existante IMAGE dans WIMFILE, mais capturée à un moment ultérieur, éventuellement avec quelques modifications entre-temps. Ceci est conçu pour être utilisé dans des sauvegardes incrémentielles du même système de fichiers ou de la même arborescence de répertoires. IMAGE peut être un index basé sur 1 ou le nom d'une image existante dans WIMFILE. Il peut également s'agir d'un entier négatif pour indexer à rebours dans les images (par exemple, -1 signifie la dernière image existante dans WIMFILE).
Lorsque cette option est fournie, la capture ou l'ajout de la nouvelle image sera optimisé en ne lisant pas les fichiers qui, d'après les métadonnées telles que les horodatages, semblent ne pas avoir été modifiés depuis leur archivage dans l'image existante IMAGE. Sans manipulation des horodatages, cette option affecte seulement les performances et ne modifie pas l'image WIM résultante (mais voir la note ci-dessous).
Comme montré, la syntaxe complète de l'argument de cette option est de spécifier le fichier WIM, deux points, et l'image ; par exemple, "--update-of mywim.wim:1". Cependant, le fichier WIM et les deux points peuvent être omis si --delta-from est spécifié exactement une fois, auquel cas le WIM par défaut est celui spécifié dans --delta-from, ou si l'opération est wimappend plutôt que wimcapture, auquel cas le WIM par défaut est celui auquel on ajoute.
Note : dans la version Windows de wimlib, il a été observé que le mode --update-of n'est pas complètement fiable pour détecter les modifications dans le contenu des fichiers, provoquant parfois l'archivage du contenu ancien de quelques fichiers plutôt que du contenu actuel. La cause de ce problème est que Windows ne met pas à jour immédiatement l'horodatage de dernière modification d'un fichier après chaque écriture dans ce fichier. Malheureusement, il n'existe aucun moyen connu pour les applications comme wimlib de contourner automatiquement ce bug. Des solutions manuelles sont possibles ; théoriquement, toute action qui provoque la fermeture des fichiers problématiques, comme le redémarrage des applications ou de l'ordinateur lui-même, devrait entraîner la mise à jour des horodatages des fichiers. Notez également que wimlib compare les tailles de fichiers ainsi que les horodatages pour déterminer si un fichier a changé, ce qui contribue à rendre le problème moins probable ; et le problème ne se produit pas sur d'autres systèmes d'exploitation comme Linux qui maintiennent correctement les horodatages de dernière modification des fichiers.
--delta-from=WIMFILE
Capturer ou ajouter la nouvelle image comme un "delta" à partir de WIMFILE. Toute donnée de fichier qui devrait normalement être archivée dans le WIM nouveau ou mis à jour est omise si elle est déjà présente dans le WIMFILE sur lequel le delta est basé. Le WIM résultant contiendra toujours une copie complète des métadonnées de l'image, mais il s'agit généralement d'une fraction seulement de la taille totale d'un WIM.
Cette option peut être spécifiée plusieurs fois, auquel cas le WIM delta résultant ne contiendra que les données de fichiers non présentes dans l'un des WIM de base spécifiés.
Pour opérer sur le WIM delta résultant avec d'autres commandes comme wimapply, vous devez spécifier le WIM delta comme fichier WIM sur lequel opérer, mais également référencer le(s) WIM de base en utilisant l'option --ref. Attention : pour conserver le bon fonctionnement du WIM delta, vous ne pouvez ajouter, pas supprimer, des fichiers et des images aux WIM de base après la capture.
of a delta from it.
--delta-from peut être combiné avec --update-of pour augmenter la vitesse de capture d'un delta WIM.
À titre d'exemple, considérez la séquence de sauvegarde et de restauration suivante :
(sauvegarde initiale)
$ wimcapture /some/directory bkup-base.wim
(quelques jours plus tard, création d'une deuxième sauvegarde comme delta de la première)
$ wimcapture /some/directory bkup-2013-08-20.dwm \
	--update-of bkup-base.wim:-1 --delta-from bkup-base.wim
(restauration de la deuxième sauvegarde)
$ wimapply bkup-2013-08-20.dwm --ref=bkup-base.wim 1 \
	/some/directory
Cependant, notez qu'en alternative à la séquence ci-dessus qui utilisait un delta WIM, la deuxième sauvegarde aurait pu simplement être ajoutée au WIM en tant que nouvelle image à l'aide de wimappend. Les delta WIM ne devraient être utilisés que si l'on souhaite baser les sauvegardes ou les images sur un fichier séparé et volumineux, rarement modifié.
--delta-from est pris en charge par wimcapture et wimappend.
Les delta WIM sont compatibles avec le logiciel WIM de Microsoft. Par exemple, vous pouvez utiliser l'option /ref d'ImageX pour référencer les WIM de base, comme ci-dessus.
Note supplémentaire : wimlib est suffisamment généralisé pour que vous puissiez en fait combiner --pipable et --delta-from pour créer des delta WIM pipables. Dans de tels cas, les WIM de base doivent être capturés comme pipables, tout comme le delta WIM, et lors de l'application d'une image, les WIM de base doivent être envoyés sur le tuyau après le delta WIM.
--wimboot
Marque l'image comme compatible WIMBoot. Voir la documentation de Microsoft pour plus d'informations sur WIMBoot. Avec wimcapture, cette option définira le type de compression sur XPRESS et la taille des blocs sur 4096 octets ; ceux-ci peuvent cependant toujours être remplacés par les paramètres --compress et --chunk-size, respectivement. De plus, cette option définira le fichier de configuration sur SOURCE\Windows\System32\WimBootCompress.ini s'il est présent et accessible ; cependant, cela peut toujours être remplacé par le paramètre --config.
--unsafe-compact
Avec wimappend, compacte l'archive WIM en place et ajoute toutes les nouvelles données, éliminant les "trous". C'est efficace, mais en général, cette option ne devrait *pas* être utilisée car une compaction échouée ou interrompue corrompra l'archive WIM. Pour plus d'informations, consultez la documentation de cette option pour wimoptimize(1).
--snapshot
Crée un instantané temporaire du système de fichiers du répertoire source et capture les fichiers à partir de celui-ci. Actuellement, cette option n'est prise en charge que sous Windows, où elle utilise le Volume Shadow Copy Service (VSS). En utilisant cette option, vous pouvez créer une sauvegarde cohérente du volume système d'un système Windows en cours d'exécution sans rencontrer de problèmes avec les fichiers verrouillés. Pour que l'instantané VSS soit créé avec succès, wimlib-imagex doit être exécuté en tant qu'administrateur et ne peut pas être exécuté en mode WoW64 (c'est-à-dire si Windows est 64 bits, alors wimlib-imagex doit également être 64 bits).
--create
Avec wimappend, si le fichier WIM n'existe pas encore, alors créez-le (comme wimcapture).

NOTES

wimappend ne prend pas en charge l'ajout d'une image à un WIM divisé.

Sauf lors de l'utilisation de --unsafe-compact, il est sûr d'interrompre une commande wimappend à mi-chemin ; cependant, après cela, il est recommandé d'exécuter wimoptimize pour supprimer toutes les données qui ont été ajoutées au fichier WIM physique mais pas encore incorporées dans la structure du WIM, sauf si le WIM était entièrement reconstruit (par exemple avec --rebuild), auquel cas vous devriez supprimer le fichier temporaire laissé.

wimlib-imagex crée des WIM compatibles avec les logiciels de Microsoft (WIMGAPI, ImageX, DISM), avec quelques mises en garde :

•
Avec wimlib-imagex sur les systèmes de type UNIX, il est possible de créer une image WIM contenant des fichiers dont les noms diffèrent uniquement par la casse, ou des fichiers dont les noms contiennent les caractères ':', '*', '?', '"', '<', '>', '|', ou '\', qui sont valides sur les systèmes de fichiers conformes POSIX mais pas sous Windows. Attention, ces fichiers ne seront pas extraits par défaut par la version Windows de wimlib-imagex, et (pire encore) ImageX de Microsoft peut être dérouté par ces noms et arrêter d'extraire l'image à mi-chemin.
•
Les WIM pipables sont incompatibles avec les logiciels de Microsoft. Les WIM pipables ne sont créés que si WIMFILE a été spécifié comme "-" (sortie standard) ou si le drapeau --pipable a été spécifié.
•
Les WIM capturés avec une taille de bloc non par défaut (avec l'option --chunk-size) ou comme archives solides (avec l'option --solid) ou avec la compression LZMS (avec --compress=LZMS ou --compress=recovery) ont des niveaux de compatibilité variables avec les logiciels de Microsoft. En général, les versions plus récentes des logiciels de Microsoft sont plus compatibles.

EXEMPLES

Premier exemple : Créer un nouveau WIM 'mywim.wim' avec compression LZX ("maximum") qui contiendra une image capturée de l'arborescence de répertoires 'somedir'. Notez que le nom de l'image n'a pas besoin d'être spécifié et sera par défaut 'somedir' :

wimcapture somedir mywim.wim

Ensuite, ajouter l'image d'un autre répertoire au WIM créé ci-dessus :

wimappend anotherdir mywim.wim

Assez simple, et les exemples ci-dessus d'imagerie d'arborescences de répertoires fonctionnent aussi bien sur les systèmes de type UNIX que sous Windows. Ensuite, capturez un WIM avec plusieurs options non par défaut, y compris la compression XPRESS ("rapide"), des informations d'intégrité supplémentaires, aucune manipulation des liens symboliques absolus, et un nom et une description d'image :

wimcapture somedir mywim.wim --compress=fast \

--check --norpfix "Some Name" "Some Description"

Sur un système de type UNIX, capturez un volume NTFS complet dans un nouveau WIM en utilisant le mode NTFS VOLUME CAPTURE (UNIX), et nommez l'image "Windows 7" :

wimcapture /dev/sda2 windows7.wim "Windows 7"

ou, sous Windows, pour capturer un volume NTFS complet, vous devez plutôt spécifier le répertoire racine du volume monté, par exemple :

wimcapture E:\ windows7.wim "Windows 7"

Identique à l'exemple UNIX ci-dessus, mais capturez le WIM dans le format "pipable" spécifique à wimlib qui peut être redirigé vers wimapply :

wimcapture /dev/sda2 windows7.wim "Windows 7" --pipable

Identique à ci-dessus, mais au lieu d'écrire le WIM pipable dans le fichier "windows7.wim", écrivez-le directement sur la sortie standard via un tuyau vers un autre programme "someprog", qui pourrait, par exemple, être un programme ou un script qui diffuse les données vers un serveur :

wimcapture /dev/sda2 - "Windows 7" | someprog
