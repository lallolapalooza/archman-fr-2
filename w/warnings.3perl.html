warnings(3perl) Guide de référence du programmeur Perl warnings(3perl)

NOM

warnings - Pragma Perl pour contrôler les avertissements optionnels

SYNOPIS

use warnings;
no warnings;
# Les avertissements standards sont activés par use v5.35 ou supérieur
use v5.35;
use warnings "all";
no warnings "uninitialized";
# ou équivalent aux deux derniers...
use warnings qw(all -uninitialized);
use warnings::register;
if (warnings::enabled()) {
    warnings::warn("un avertissement");
}
if (warnings::enabled("void")) {
    warnings::warn("void", "un avertissement");
}
if (warnings::enabled($object)) {
    warnings::warn($object, "un avertissement");
}
warnings::warnif("un avertissement");
warnings::warnif("void", "un avertissement");
warnings::warnif($object, "un avertissement");

DESCRIPTION

Le pragma "warnings" permet de contrôler quels avertissements sont activés dans quelles parties d'un programme Perl. C'est une alternative plus flexible au drapeau de ligne de commande -w et à la variable Perl équivalente, $^W.

Ce pragma fonctionne comme le pragma "strict". Cela signifie que la portée du pragma d'avertissement est limitée au bloc englobant. Cela signifie également que le réglage du pragma ne fuira pas à travers les fichiers (via "use", "require" ou "do"). Cela permet aux auteurs de définir indépendamment le degré de vérification des avertissements qui sera appliqué à leur module.

Par défaut, les avertissements optionnels sont désactivés, donc tout code hérité qui ne tente pas de contrôler les avertissements fonctionnera inchangé.

Tous les avertissements sont activés dans un bloc par l'une de ces commandes :

use warnings;
use warnings 'all';

De même, tous les avertissements sont désactivés dans un bloc par l'une de ces commandes :

no warnings;
no warnings 'all';

Par exemple, considérez le code ci-dessous :

use warnings;
my @x;
{
    no warnings;
    my $y = @x[0];
}
my $z = @x[0];

Le code dans le bloc englobant a les avertissements activés, mais le bloc intérieur les a désactivés. Dans ce cas, cela signifie que l'affectation au scalaire $z déclenchera l'avertissement "Scalar value @x[0] better written as $x[0]", mais l'affectation au scalaire $y ne le fera pas.

Tous les avertissements sont automatiquement activés dans la portée d'une déclaration "use v5.35" (ou supérieure).

Avertissements par défaut et Avertissements optionnels

Avant l'introduction des avertissements lexicaux, Perl avait deux classes d'avertissements : obligatoires et optionnels.

Comme son nom l'indique, si votre code déclenchait un avertissement obligatoire, vous recevriez un avertissement que vous le vouliez ou non. Par exemple, le code ci-dessous produirait toujours un avertissement "isn't numeric" concernant le "2:".

my $x = "2:" + 3;

Avec l'introduction des avertissements lexicaux, les avertissements obligatoires deviennent des avertissements par *défaut*. La différence est que, bien que les avertissements précédemment obligatoires soient toujours activés par défaut, ils peuvent ensuite être activés ou désactivés avec le pragma d'avertissement lexical. Par exemple, dans le code ci-dessous, un avertissement "isn't numeric" ne sera signalé que pour la variable $x.

my $x = "2:" + 3;
no warnings;
my $y = "2:" + 3;

Notez que ni le drapeau -w ni $^W ne peuvent être utilisés pour désactiver/activer les avertissements par défaut. Ils sont toujours obligatoires dans ce cas.

Avertissements négatifs

Par souci de commodité, vous pouvez (depuis Perl 5.34) passer des arguments à la méthode import() de manière positive et négative. Les avertissements négatifs sont ceux qui ont un signe "-" préfixé à leur nom ; les avertissements positifs sont tout le reste. Cela vous permet d'activer certains avertissements et d'en désactiver d'autres en une seule commande. Ainsi, en supposant que vous ayez déjà activé un tas d'avertissements mais que vous souhaitiez les ajuster un peu dans un bloc, vous pouvez faire ceci :

{
    use warnings qw(uninitialized -redefine);
    ...
}

ce qui est équivalent à :

{
    use warnings qw(uninitialized);
    no warnings qw(redefine);
    ...
}

La liste d'arguments est traitée dans l'ordre où vous la spécifiez. Ainsi, par exemple, si vous ne souhaitez pas être averti de l'utilisation de fonctionnalités expérimentales, à l'exception de "somefeature" que vous détestez vraiment, vous pouvez dire ceci :

use warnings qw(all -experimental experimental::somefeature);

ce qui est équivalent à :

use warnings 'all';
no warnings  'experimental';
use warnings 'experimental::somefeature';

À mesure que les fonctionnalités expérimentales deviennent des fonctionnalités régulières de Perl, les avertissements correspondants ne sont plus imprimés. Ils ne sont plus non plus répertoriés dans la section "Hiérarchie des catégories" ci-dessous.

Il est toujours possible de demander l'activation ou la désactivation de ces avertissements, mais le faire n'a aucun effet.

Qu'est-ce qui ne va pas avec -w et $^W

Bien qu'étant très utiles, le gros problème avec l'utilisation de -w sur la ligne de commande pour activer les avertissements est que c'est tout ou rien. Prenez le scénario typique lorsque vous écrivez un programme Perl. Vous écrirez vous-même certaines parties du code, mais il est très probable que vous utiliserez des modules Perl pré-écrits. Si vous utilisez le drapeau -w dans ce cas, vous finirez par activer les avertissements dans des morceaux de code que vous n'avez pas écrits.

De même, l'utilisation de $^W pour désactiver ou activer des blocs de code est fondamentalement défectueuse. Pour commencer, dites que vous voulez désactiver les avertissements dans un bloc de code. Vous pourriez vous attendre à ce que cela suffise pour faire l'affaire :

{
    local ($^W) = 0;
    my $x =+ 2;
    my $y; chop $y;
}

Lorsque ce code est exécuté avec le drapeau -w, un avertissement sera produit pour la ligne $x : "Reversed += operator".

Le problème est que Perl a des avertissements à la fois au moment de la compilation et au moment de l'exécution. Pour désactiver les avertissements au moment de la compilation, vous devez réécrire le code comme suit :

{
    BEGIN { $^W = 0 }
    my $x =+ 2;
    my $y; chop $y;
}

Et notez que contrairement au premier exemple, cela définira définitivement $^W puisqu'il ne peut pas à la fois s'exécuter au moment de la compilation et être localisé à un bloc au moment de l'exécution.

L'autre gros problème avec $^W est la façon dont vous pouvez involontairement changer le réglage des avertissements dans des endroits inattendus de votre code. Par exemple, lorsque le code ci-dessous est exécuté (sans le drapeau -w), le deuxième appel à "doit" déclenchera un avertissement "Use of uninitialized value", alors que le premier ne le fera pas.

sub doit
{
    my $y; chop $y;
}
doit();
{
    local ($^W) = 1;
    doit()
}

C'est un effet secondaire de la portée dynamique de $^W.

Les avertissements lexicaux contournent ces limitations en permettant un contrôle plus fin sur les endroits où les avertissements peuvent ou ne peuvent pas être déclenchés.

Contrôle des avertissements depuis la ligne de commande

Il existe trois indicateurs de ligne de commande qui peuvent être utilisés pour contrôler quand les avertissements sont (ou ne sont pas) produits :

-w
C'est l'indicateur existant. Si le pragma des avertissements lexicaux n'est pas utilisé dans votre code, ou dans l'un des modules que vous utilisez, cet indicateur activera les avertissements partout. Voir "Compatibilité descendante" pour les détails sur la façon dont cet indicateur interagit avec les avertissements lexicaux.
-W
Si l'indicateur -W est utilisé sur la ligne de commande, il activera tous les avertissements dans tout le programme, que les avertissements aient été désactivés localement à l'aide de "no warnings" ou de "$^W =0". Cela inclut tous les fichiers qui sont inclus via "use", "require" ou "do". Th

Compatibilité ascendante

Si vous avez l'habitude de travailler avec une version de Perl antérieure à l'introduction des avertissements à portée lexicale, ou si vous avez du code qui utilise à la fois les avertissements lexicaux et $^W, cette section décrira comment ils interagissent.

Comment les avertissements lexicaux interagissent avec -w/$^W :

1.
Si aucun des trois drapeaux de ligne de commande (-w, -W ou -X) qui contrôlent les avertissements n'est utilisé et que ni $^W ni le pragma "warnings" ne sont utilisés, alors les avertissements par défaut seront activés et les avertissements optionnels désactivés. Cela signifie que le code hérité qui ne tente pas de contrôler les avertissements fonctionnera sans modification.
2.
Le drapeau -w définit simplement la variable globale $^W comme dans 5.005. Cela signifie que tout code hérité qui repose actuellement sur la manipulation de $^W pour contrôler le comportement des avertissements fonctionnera toujours tel quel.
3.
Outre le fait d'être maintenant booléenne, la variable $^W fonctionne exactement de la même manière horrible et incontrôlée globalement, sauf qu'elle ne peut pas désactiver/activer les avertissements par défaut.
4.
Si un morceau de code est sous le contrôle du pragma "warnings", la variable $^W et le drapeau -w seront ignorés pour la portée de l'avertissement lexical.
5.
La seule façon de remplacer un paramètre d'avertissement lexical est d'utiliser les drapeaux de ligne de commande -W ou -X.

L'effet combiné de 3 et 4 est qu'il permettra au code utilisant le pragma "warnings" de contrôler le comportement des avertissements du code de type $^W (en utilisant un "local $^W=0") s'il le souhaite vraiment, mais pas l'inverse.

Tout comme le pragma « strict », toutes ces catégories peuvent être combinées

use warnings qw(void redefine);
no warnings qw(io syntax untie);

De même que pour le pragma « strict », s'il y a plus d'une instance du pragma "warnings" dans une portée donnée, l'effet cumulatif est additif.

use warnings qw(void); # seuls les avertissements "void" sont activés
...
use warnings qw(io);   # seuls les avertissements "void" et "io" sont activés
...
no warnings qw(void);  # seuls les avertissements "io" sont activés

Pour déterminer à quelle catégorie un avertissement spécifique a été attribué, consultez perldiag.

Note : Avant 5.21.0, la catégorie d'avertissements lexicaux « missing » était définie en interne comme étant identique à la catégorie « uninitialized ». Elle est désormais une catégorie de premier niveau à part entière.

Avertissements fatals

La présence du mot « FATAL » dans la liste des catégories transformera les avertissements de ces catégories en erreurs fatales dans cette portée lexicale.

NOTE : Les avertissements FATAL doivent être utilisés avec précaution, en particulier "FATAL => 'all'".

Les bibliothèques utilisant warnings::warn pour des catégories d'avertissements personnalisées ne s'attendent généralement pas à ce que warnings::warn soit fatal et peuvent se retrouver dans un état inattendu en conséquence. Pour les modules XS émettant des avertissements catégorisés, de telles exceptions imprévues pourraient également révéler des bugs de fuite de mémoire.

De plus, l'interpréteur Perl lui-même a eu de graves bugs impliquant des avertissements fatalisés. Pour un résumé des problèmes résolus et non résolus en janvier 2015, veuillez consulter cette publication de perl5-porters http://www.nntp.perl.org/group/perl.perl5.porters/2015/01/msg225235.html.

Bien que certains développeurs trouvent que la fatalisation de certains avertissements est une technique de programmation défensive utile, l'utilisation de "FATAL => 'all'" pour fataliser toutes les catégories d'avertissements possibles – y compris les personnalisées – est particulièrement risquée. Par conséquent, l'utilisation de "FATAL => 'all'" est déconseillée.

Le module strictures sur CPAN offre un exemple de sous-ensemble d'avertissements que les auteurs du module estiment relativement sûr à fataliser.

NOTE : Les utilisateurs d'avertissements FATAL, en particulier ceux utilisant "FATAL => 'all'", doivent être pleinement conscients qu'ils risquent la portabilité future de leurs programmes en le faisant. Perl ne prend aucun engagement de ne pas introduire de nouveaux avertissements ou catégories d'avertissements à l'avenir ; en effet, nous nous réservons explicitement le droit de le faire. Le code qui peut ne pas avertir maintenant peut avertir dans une future version de Perl si l'équipe de développement Perl5 le juge dans le meilleur intérêt de la communauté. Si un code utilisant des avertissements FATAL se casse en raison de l'introduction d'un nouvel avertissement, nous ne le considérerons PAS comme un changement incompatible. Les utilisateurs d'avertissements FATAL doivent prendre des précautions particulières lors des mises à niveau pour vérifier si leur code déclenche des avertissements nouveaux et doivent accorder une attention particulière aux petits caractères de la documentation des fonctionnalités qu'ils utilisent pour s'assurer qu'ils n'exploitent pas de fonctionnalités documentées comme risquées, obsolètes ou non spécifiées, ou lorsque la documentation indique « donc ne faites pas ça », ou quoi que ce soit de sens et d'esprit similaire. L'utilisation de telles fonctionnalités en combinaison avec des avertissements FATAL est ENTIÈREMENT AUX RISQUES DE L'UTILISATEUR.

La documentation suivante décrit comment utiliser les avertissements FATAL, mais les développeurs Perl5 recommandent fortement de comprendre les risques avant de le faire, en particulier pour le code de bibliothèque destiné à être utilisé par d'autres, car il n'y a aucun moyen pour les utilisateurs en aval de modifier le choix des catégories fatales.

Dans le code ci-dessous, l'utilisation de "time", "length" et "join" peut tous produire un avertissement "Useless use of xxx in void context".

use warnings;
time;
{
    use warnings FATAL => qw(void);
    length "abc";
}
join "", 1,2,3;
print "done\n";

Comme "warnings::warnif", mais $level spécifie la trame d'appel exacte, 0 étant l'appelant immédiat.
warnings::register_categories(@names)
Ceci enregistre des catégories d'avertissements pour les noms donnés et est principalement destiné à être utilisé par le pragma warnings::register.

Voir aussi "Pragmatic Modules" dans perlmodlib et perldiag.
