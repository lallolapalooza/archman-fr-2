write(2) Manuel des appels système write(2)

NOM

write - écrire dans un descripteur de fichier

BIBLIOTHQUE

Bibliothèque C standard (libc, -lc)

SYNTAXE

#include <unistd.h>
ssize_t write(size_t count;
              int fd, const void buf[count], size_t count);

DESCRIPTION

write() écrit jusqu'à count octets depuis le tampon commençant à buf vers le fichier désigné par le descripteur de fichier fd.

Le nombre d'octets écrits peut être inférieur à count si, par exemple, il n'y a pas assez d'espace sur le support physique sous-jacent, ou si la limite de ressources RLIMIT_FSIZE est atteinte (voir setrlimit(2)), ou si l'appel a été interrompu par un gestionnaire de signaux après avoir écrit moins de count octets. (Voir aussi pipe(7).)

Pour un fichier accessible en recherche (c'est-à-dire un fichier sur lequel lseek(2) peut être appliqué, par exemple un fichier ordinaire), l'écriture a lieu à la position du fichier, et le décalage du fichier est incrémenté par le nombre d'octets réellement écrits. Si le fichier a été ouvert avec O_APPEND (open(2)), le décalage du fichier est d'abord positionné à la fin du fichier avant l'écriture. L'ajustement du décalage du fichier et l'opération d'écriture sont effectués comme une étape atomique.

POSIX exige qu'une lecture (read(2)) qui peut être prouvée avoir lieu après le retour d'un write() retourne les nouvelles données. Notez que tous les systèmes de fichiers ne sont pas conformes à POSIX.

Conformément à POSIX.1, si count est supérieur à SSIZE_MAX, le résultat est défini par l'implémentation ; voir NOTES pour la limite supérieure sous Linux.

VALEUR DE RETOUR

En cas de succès, le nombre d'octets écrits est retourné. En cas d'erreur, -1 est retourné et errno est défini pour indiquer l'erreur.

Notez qu'un write() réussi peut transférer moins de count octets. De telles écritures partielles peuvent survenir pour diverses raisons ; par exemple, parce qu'il n'y avait pas assez d'espace sur le périphérique disque pour écrire tous les octets demandés, ou parce qu'un write() bloquant vers une socket, un pipe ou similaire a été interrompu par un gestionnaire de signaux après avoir transféré certains, mais pas tous, les octets demandés. En cas d'écriture partielle, l'appelant peut effectuer un autre appel write() pour transférer les octets restants. L'appel ultérieur transférera d'autres octets ou peut entraîner une erreur (par exemple, si le disque est maintenant plein).

Si count est zéro et fd fait référence à un fichier régulier, alors write() peut retourner un statut d'échec si l'une des erreurs ci-dessous est détectée. Si aucune erreur n'est détectée, ou si la détection d'erreurs n'est pas effectuée, 0 est retourné sans aucun autre effet. Si count est zéro et fd fait référence à un fichier autre qu'un fichier régulier, les résultats ne sont pas spécifiés.

ERREURS

EAGAIN
Le descripteur de fichier fd fait référence à un fichier autre qu'une socket et a été marqué comme non bloquant (O_NONBLOCK), et l'écriture bloquerait. Voir open(2) pour plus de détails sur le drapeau O_NONBLOCK.
EAGAIN ou EWOULDBLOCK
Le descripteur de fichier fd fait référence à une socket et a été marqué comme non bloquant (O_NONBLOCK), et l'écriture bloquerait. POSIX.1-2001 autorise l'une ou l'autre erreur pour ce cas, et n'exige pas que ces constantes aient la même valeur, donc une application portable doit vérifier les deux possibilités.
EBADF
fd n'est pas un descripteur de fichier valide ou n'est pas ouvert en écriture.
EDESTADDRREQ
fd fait référence à une socket de datagramme pour laquelle une adresse de pair n'a pas été définie à l'aide de connect(2).
EDQUOT
Le quota de blocs disque de l'utilisateur sur le système de fichiers contenant le fichier référencé par fd a été épuisé.
EFAULT
buf est en dehors de votre espace d'adressage accessible.
EFBIG
Une tentative a été faite pour écrire dans un fichier qui dépasse la taille maximale définie par l'implémentation ou la limite de taille de fichier du processus, ou pour écrire à une position au-delà du décalage maximum autorisé.
EINTR
L'appel a été interrompu par un signal avant que des données ne soient écrites ; voir signal(7).
EINVAL
fd est attaché à un objet inapproprié pour l'écriture ; ou le fichier a été ouvert avec le drapeau O_DIRECT, et soit l'adresse spécifiée dans buf, la valeur spécifiée dans count, soit le décalage du fichier ne sont pas correctement alignés.
EIO
Une erreur d'E/S de bas niveau s'est produite lors de la modification de l'inode. Cette erreur peut être liée à l'écriture différée des données écrites par un write() précédent, qui peut avoir été émis sur un descripteur de fichier différent sur le même fichier. Depuis Linux 4.13, les erreurs d'écriture différée promettent qu'elles *peuvent* être signalées par des requêtes write() ultérieures, et *seront* signalées par un fsync(2) ultérieur (qu'elles aient été signalées ou non par write()). Une autre cause possible de EIO sur les systèmes de fichiers réseau est lorsqu'un verrou consultatif a été pris sur le descripteur de fichier et que ce verrou a été perdu. Voir la section Verrous perdus de fcntl(2) pour plus de détails.
ENOSPC
Le périphérique contenant le fichier référencé par fd n'a plus de place pour les données.
EPERM
L'opération a été empêchée par un sceau de fichier ; voir fcntl(2).
EPIPE
fd est connecté à un pipe ou à une socket dont l'extrémité de lecture est fermée. Lorsque cela se produit, le processus d'écriture reçoit également un signal SIGPIPE. (Ainsi, la valeur de retour de write n'est vue que si le programme intercepte, bloque ou ignore ce signal.)

D'autres erreurs peuvent survenir, en fonction de l'objet connecté à fd.

NORMES

POSIX.1-2024.

HISTORIQUE

SVr4, 4.3BSD, POSIX.1-2001.

Sous SVr4, une écriture peut être interrompue et retourner EINTR à tout moment, pas seulement avant que des données ne soient écrites.

NOTES

Un retour réussi de write() ne garantit pas que les données ont été validées sur le disque. Sur certains systèmes de fichiers, y compris NFS, il ne garantit même pas que l'espace a été réservé avec succès pour les données. Dans ce cas, certaines erreurs pourraient être retardées jusqu'à un avenir write(), fsync(2), ou même close(2). La seule façon d'être sûr est d'appeler fsync(2) après avoir terminé d'écrire toutes vos données.

Si un write() est interrompu par un gestionnaire de signaux avant que des octets n'aient été écrits, alors l'appel échoue avec l'erreur EINTR ; s'il est interrompu après qu'au moins un octet ait été écrit, l'appel réussit,

et renvoie le nombre d'octets écrits.

Sous Linux, write() (et les appels système similaires) transférera au maximum 0x7ffff000 (2 147 479 552) octets, en renvoyant le nombre d'octets effectivement transférés. (Ceci est vrai sur les systèmes 32 bits et 64 bits.)

Une valeur de retour d'erreur lors de l'exécution de write() en utilisant l'E/S directe ne signifie pas que l'ensemble de l'écriture a échoué. Des données partielles peuvent avoir été écrites et les données à l'offset du fichier sur lequel write() a été tenté doivent être considérées comme incohérentes.

BOGUES

Selon POSIX.1-2008/SUSv4 Section XSI 2.9.7 (« Thread Interactions with Regular File Operations ») :

Toutes les fonctions suivantes doivent être atomiques les unes par rapport aux autres dans les effets spécifiés dans POSIX.1-2008 lorsqu'elles opèrent sur des fichiers réguliers ou des liens symboliques : ...

Parmi les API listées ensuite figurent write() et writev(2). Et parmi les effets qui devraient être atomiques entre les threads (et processus) figurent les mises à jour de l'offset du fichier. Cependant, avant Linux 3.14, ce n'était pas le cas : si deux processus qui partagent une description de fichier ouverte (voir open(2)) effectuent un write() (ou writev(2)) en même temps, alors les opérations d'E/S n'étaient pas atomiques par rapport à la mise à jour de l'offset du fichier, avec pour résultat que les blocs de données produits par les deux processus pouvaient (incorrectement) se chevaucher. Ce problème a été corrigé dans Linux 3.14.
