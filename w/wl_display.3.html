Description détaillée

Représente une connexion au compositeur et agit comme un proxy pour l'objet singleton wl_display.

Un objet wl_display représente une connexion client à un compositeur Wayland. Il est créé soit avec wl_display_connect(), soit avec wl_display_connect_to_fd(). Une connexion est terminée en utilisant wl_display_disconnect().

Un wl_display est également utilisé comme le wl_proxy pour l'objet singleton wl_display côté compositeur.

Un wl_display gère toutes les données envoyées depuis et vers le compositeur. Lorsqu'un wl_proxy prépare une requête, il écrira sa représentation filaire dans le tampon d'écriture du display. Les données sont envoyées au compositeur lorsque le client appelle wl_display_flush().

Les données entrantes sont traitées en deux étapes : mise en file d'attente et distribution. Dans l'étape de mise en file d'attente, les données provenant du descripteur de fichier du display sont interprétées et ajoutées à une file d'attente. Dans l'étape de distribution, le gestionnaire de l'événement entrant défini par le client sur le wl_proxy correspondant est appelé.

Un wl_display possède au moins une file d'attente d'événements, appelée la file d'attente par défaut. Les clients peuvent créer des files d'attente d'événements supplémentaires avec wl_display_create_queue() et y assigner des wl_proxy. Les événements survenant sur un proxy particulier sont toujours mis en file d'attente dans sa file d'attente assignée. Un client peut s'assurer qu'une certaine hypothèse, comme détenir un verrou ou s'exécuter depuis un thread donné, est vraie lorsqu'un gestionnaire d'événements de proxy est appelé, en assignant ce proxy à une file d'attente d'événements et en s'assurant que cette file d'attente n'est distribuée que lorsque l'hypothèse est vérifiée.

La file d'attente par défaut est distribuée en appelant wl_display_dispatch(). Cela distribuera tous les événements mis en file d'attente dans la file par défaut et tentera de lire à partir du descripteur de fichier du display s'il est vide. Les événements lus sont ensuite mis en file d'attente dans les files appropriées selon l'assignation du proxy.

Une file d'attente créée par l'utilisateur est distribuée avec wl_display_dispatch_queue(). Cette fonction se comporte exactement comme wl_display_dispatch() mais elle distribue la file donnée au lieu de la file par défaut.

Un exemple concret d'utilisation des files d'attente d'événements est l'implémentation par Mesa de eglSwapBuffers() pour la plateforme Wayland. Cette fonction pourrait avoir besoin de bloquer jusqu'à ce qu'un rappel de frame soit reçu, mais la distribution de la file par défaut pourrait provoquer le début d'un nouveau dessin par un gestionnaire d'événements côté client. Ce problème est résolu en utilisant une autre file d'attente d'événements, de sorte que seuls les événements gérés par le code EGL soient distribués pendant le blocage.

Cela crée un problème où un thread distribue une file d'attente non défaut, lisant toutes les données du descripteur de fichier du display. Si l'application appelait poll(2) après cela, elle bloquerait, même s'il pourrait y avoir des événements en file d'attente dans la file par défaut. Ces événements devraient être distribués avec wl_display_dispatch_pending() ou wl_display_dispatch_queue_pending() avant de vider et de bloquer.

struct wl_client * wl_client_create (struct wl_display * display, int fd)

Crée un client pour le descripteur de fichier donné

Paramètres

display L'objet display
fd Le descripteur de fichier pour le socket vers le client

Retourne

Le nouvel objet client ou NULL en cas d'échec.

Étant donné un descripteur de fichier correspondant à une extrémité d'un socket, cette fonction créera une structure wl_client et ajoutera le nouveau client à la liste des clients du compositeur. À ce stade, le client est initialisé et prêt à fonctionner, comme si le client s'était connecté au socket d'écoute du serveur. Lorsque le client envoie finalement des requêtes au compositeur, l'argument wl_client du gestionnaire de requête sera le wl_client retourné par cette fonction.

L'autre extrémité du socket peut être passée à wl_display_connect_to_fd() côté client ou utilisée avec la variable d'environnement WAYLAND_SOCKET.

struct wl_client * wl_client_create (struct wl_display * display, int fd)

Create a new Wayland client object on the given file descriptor.

Parameters

display The display object
fd The file descriptor for the client connection

Returns

A pointer to the new client object on success, or NULL on failure.

This function is used by the Wayland server to accept new incoming connections. It creates a wl_client object representing the client and sets up the necessary internal structures to handle communication with the client side.

Listeners added with wl_display_add_client_created_listener() will be notified by this function after the client is fully constructed.

On failure this function sets errno accordingly and returns NULL.

On success, the new client object takes the ownership of the file descriptor. On failure, the ownership of the socket endpoint file descriptor is unchanged, it is the responsibility of the caller to perform cleanup, e.g. call close().

struct wl_protocol_logger * wl_display_add_protocol_logger (struct wl_display * display, wl_protocol_logger_func_t func, void * user_data)

Ajoute un nouveau journal de protocole.

Lorsqu'un nouveau message de protocole arrive ou est envoyé depuis le serveur, toutes les fonctions de journalisation de protocole seront appelées, en transmettant le pointeur user_data, le type du message (requête ou événement) et le message réel. La durée de vie des messages passés à la fonction de journalisation se termine lorsqu'ils reviennent, de sorte que les messages ne peuvent pas être stockés et accessibles ultérieurement.

errno est défini en cas d'erreur.

Paramètres

func La fonction à appeler pour enregistrer un nouveau message de protocole
user_data Le pointeur de données utilisateur à passer à func

Retourne

L'objet de journalisation de protocole en cas de succès, NULL en cas d'échec.

uint32_t * wl_display_add_shm_format (struct wl_display * display, uint32_t format)

Ajoute la prise en charge d'un format de pixel wl_shm

Paramètres

display L'objet d'affichage
format Le format de pixel wl_shm à annoncer

Retourne

Un pointeur vers le format wl_shm qui a été ajouté à la liste ou NULL si l'ajout à la liste a échoué.

Ajoute le format wl_shm spécifié à la liste des formats que l'objet wl_shm annonce lorsqu'un client s'y connecte. L'ajout d'un format à la liste signifie que les clients sauront que le compositeur prend en charge ce format et peuvent l'utiliser pour créer des tampons wl_shm. Le compositeur doit être capable de gérer le format de pixel lorsqu'un client le demande.

Le compositeur prend en charge par défaut WL_SHM_FORMAT_ARGB8888 et WL_SHM_FORMAT_XRGB8888.

int wl_display_add_socket (struct wl_display * display, const char * name)

Ajoute un socket à l'affichage Wayland pour que les clients s'y connectent.

Paramètres

display Affichage Wayland auquel le socket doit être ajouté.
name Nom du socket Unix.

Retourne

0 en cas de succès. -1 en cas d'échec.

Ceci ajoute un socket Unix à l'affichage Wayland qui peut être utilisé par les clients pour se connecter à l'affichage Wayland.

Si NULL est passé comme nom, il recherchera la variable d'environnement WAYLAND_DISPLAY pour le nom du socket. Si WAYLAND_DISPLAY n'est pas défini, le nom par défaut wayland-0 est utilisé.

Si le nom du socket est un chemin relatif, le socket Unix sera créé dans le répertoire pointé par la variable d'environnement XDG_RUNTIME_DIR. Si XDG_RUNTIME_DIR est invalide ou non défini, cette fonction échoue et renvoie -1.

Si le nom du socket est un chemin absolu, il est utilisé tel quel pour le socket Unix.

La longueur du chemin de socket calculé ne doit pas dépasser la longueur maximale d'un chemin de socket Unix. La fonction échoue également si l'utilisateur n'a pas la permission d'écrire dans le répertoire ou si le chemin est déjà utilisé.

int wl_display_add_socket_fd (struct wl_display * display, int sock_fd)

sock_fd Le descripteur de fichier de socket existant à utiliser

struct wl_display * wl_display_connect (const char * name)

Se connecte à un affichage Wayland

Paramètres

name Nom de l'affichage Wayland auquel se connecter

Retourne

Un objet wl_display ou NULL en cas d'échec

Se connecte à l'affichage Wayland nommé name. Si name est NULL, sa valeur sera remplacée par la variable d'environnement WAYLAND_DISPLAY si elle est définie, sinon l'affichage "wayland-0" sera utilisé.

Si WAYLAND_SOCKET est défini, il est interprété comme un numéro de descripteur de fichier faisant référence à un socket déjà ouvert. Dans ce cas, le socket est utilisé tel quel et name est ignoré.

Si name est un chemin relatif, alors le socket est ouvert relativement au répertoire XDG_RUNTIME_DIR.

Si name est un chemin absolu, alors ce chemin est utilisé tel quel pour l'emplacement du socket sur lequel le serveur Wayland écoute ; aucune qualification à l'intérieur de XDG_RUNTIME_DIR n'est tentée.

Si name est NULL et que la variable d'environnement WAYLAND_DISPLAY est définie sur un nom de chemin absolu, alors ce nom de chemin est utilisé tel quel pour le socket de la même manière que si name contenait un chemin absolu. La prise en charge des chemins absolus dans name et WAYLAND_DISPLAY est présente depuis la version 1.15 de Wayland.

int wl_display_dispatch (struct wl_display * display)

Traiter les événements entrants

Paramètres

display L'objet de contexte d'affichage

Retourne

Le nombre d'événements traités en cas de succès ou -1 en cas d'échec

Traite les événements sur la file d'attente d'événements par défaut.

Si la file d'attente d'événements par défaut est vide, cette fonction se bloque jusqu'à ce qu'il y ait des événements à lire depuis le descripteur de fichier de l'affichage. Les événements sont lus et mis en file d'attente sur les files d'attente d'événements appropriées. Enfin, les événements sur la file d'attente d'événements par défaut sont traités. En cas d'échec, -1 est retourné et errno est défini de manière appropriée.

Dans un environnement multi-threadé, n'attendez pas manuellement en utilisant poll() (ou équivalent) avant d'appeler cette fonction, car cela pourrait entraîner un interblocage. Si une dépendance externe sur poll() (ou équivalent) est requise, voir wl_display_prepare_read_queue() pour savoir comment procéder.

Cette fonction est thread-safe tant qu'elle traite la bonne file d'attente sur le bon thread. Elle est également compatible avec l'API de préparation de lecture d'événements multi-thread (voir wl_display_prepare_read_queue()) et utilise la fonctionnalité équivalente en interne. Il n'est pas autorisé d'appeler cette fonction pendant que le thread est préparé pour lire les événements, et le faire provoquera un interblocage.

Note

Il n'est pas possible de vérifier s'il y a des événements sur la file d'attente ou non. Pour traiter les événements de la file d'attente par défaut sans blocage, voir wl_display_dispatch_pending().

Retourne

Si la file d'attente d'événements donnée est vide, cette fonction se bloque jusqu'à ce qu'il y ait des événements à lire depuis le descripteur de fichier de l'affichage. Les événements sont lus et mis en file d'attente sur les files d'attente d'événements appropriées. Enfin, les événements sur la file d'attente d'événements donnée sont traités. En cas d'échec, -1 est retourné et errno est défini de manière appropriée.

Dans un environnement multi-threadé, n'attendez pas manuellement en utilisant poll() (ou équivalent) avant d'appeler cette fonction, car cela pourrait entraîner un interblocage. Si une dépendance externe sur poll() (ou équivalent) est requise, voir wl_display_prepare_read_queue() pour savoir comment procéder.

Cette fonction est thread-safe tant qu'elle traite la bonne file d'attente sur le bon thread. Elle est également compatible avec l'API de préparation de lecture d'événements multi-thread (voir wl_display_prepare_read_queue()) et utilise la fonctionnalité équivalente en interne. Il n'est pas autorisé d'appeler cette fonction pendant que le thread est préparé pour lire les événements, et le faire provoquera un interblocage.

Elle peut être utilisée comme fonction d'aide pour faciliter la procédure de lecture et de traitement des événements.

Note

Depuis Wayland 1.5, l'affichage dispose d'une file d'attente supplémentaire pour ses propres événements (c'est-à-dire delete_id). Cette file d'attente est toujours traitée, quelle que soit la file d'attente passée en argument à cette fonction. Cela signifie que cette fonction peut retourner même si aucun événement n'a été traité pour la file d'attente donnée.

int wl_display_flush (struct wl_display * display)

Envoie toutes les requêtes mises en mémoire tampon sur l'affichage au serveur

Paramètres

display L'objet de contexte d'affichage

Retourne

Le nombre d'octets envoyés en cas de succès ou -1 en cas d'échec

Envoie toutes les données mises en mémoire tampon du côté client au serveur. Les clients doivent toujours appeler cette fonction avant de se bloquer sur l'entrée du descripteur de fichier de l'affichage. En cas de succès, le nombre d'octets envoyés au serveur est retourné. En cas d'échec, cette fonction retourne -1 et errno est défini de manière appropriée.

wl_display_flush() ne se bloque jamais. Elle écrira autant de données que possible, mais si toutes les données n'ont pas pu être écrites, errno sera défini à EAGAIN et -1 sera retourné. Dans ce cas, utilisez poll sur le descripteur de fichier de l'affichage pour attendre qu'il redevienne écrivable.

int wl_display_prepare_read_queue(struct wl_display *display, struct wl_event_queue *queue)

Préparer la lecture des événements à partir du descripteur de fichier de l'affichage vers une file d'attente

Paramètres

display L'objet de contexte d'affichage
queue La file d'attente à utiliser

Retour

0 en cas de succès ou -1 si la file d'attente d'événements n'était pas vide

Cette fonction (ou wl_display_prepare_read()) doit être appelée avant de lire à partir du descripteur de fichier à l'aide de wl_display_read_events(). L'appel de wl_display_prepare_read_queue() annonce l'intention du thread appelant de lire et garantit que jusqu'à ce que le thread soit prêt à lire et appelle wl_display_read_events(), aucun autre thread ne lira à partir du descripteur de fichier. Cela ne réussit que si la file d'attente d'événements est vide, et sinon -1 est retourné et errno est défini sur EAGAIN.

Si un thread appelle avec succès wl_display_prepare_read_queue(), il doit soit appeler wl_display_read_events() lorsqu'il est prêt, soit annuler l'intention de lecture en appelant wl_display_cancel_read().

Utilisez cette fonction avant de sonder le fd de l'affichage ou d'intégrer le fd dans une boucle d'événements de toolkit d'une manière sans course. Une utilisation correcte serait (la plupart des vérifications d'erreurs laissées de côté) :

while (wl_display_prepare_read_queue(display, queue) != 0)
        wl_display_dispatch_queue_pending(display, queue);
wl_display_flush(display);
ret = poll(fds, nfds, -1);
if (has_error(ret))
        wl_display_cancel_read(display);
else
        wl_display_read_events(display);
wl_display_dispatch_queue_pending(display, queue);

Ici, nous appelons wl_display_prepare_read_queue(), ce qui garantit qu'entre le retour de cet appel et l'appel final de wl_display_read_events(), aucun autre thread ne lira à partir du fd et ne mettra en file d'attente les événements dans notre file d'attente. Si l'appel à wl_display_prepare_read_queue() échoue, nous traitons les événements en attente et essayons à nouveau jusqu'à ce que nous réussissions.

La fonction wl_display_prepare_read_queue() n'acquiert pas l'accès exclusif au fd de l'affichage. Elle enregistre seulement que le thread appelant cette fonction a l'intention de lire à partir du fd. Lorsque tous les lecteurs enregistrés appellent wl_display_read_events(), un seul (au hasard) lit et met en file d'attente les événements, et les autres dorment pendant ce temps. De cette façon, nous évitons les courses et pouvons toujours lire à partir de plusieurs threads.

Voir aussi

wl_display_cancel_read(), wl_display_read_events(), wl_display_prepare_read()

int wl_display_read_events(struct wl_display *display)

Lire les événements à partir du descripteur de fichier de l'affichage

Paramètres

display L'objet de contexte d'affichage

Retour

0 en cas de succès ou -1 en cas d'erreur. En cas d'erreur, errno sera défini en conséquence

L'appel de cette fonction entraînera la lecture des données disponibles sur le descripteur de fichier de l'affichage et les événements lus seront mis en file d'attente sur leurs files d'attente d'événements correspondantes.

Avant d'appeler cette fonction, selon le thread à partir duquel elle doit être appelée, wl_display_prepare_read_queue() ou wl_display_prepare_read() doit être appelée. Voir wl_display_prepare_read_queue() pour plus de détails.

Lorsqu'elle est appelée à un moment où d'autres threads ont été préparés pour la lecture (en utilisant wl_display_prepare_read_queue() ou wl_display_prepare_read()), cette fonction dormira jusqu'à ce que tous les autres threads préparés aient soit été annulés (en utilisant wl_display_cancel_read()), soit soient entrés eux-mêmes dans cette fonction. Le dernier thread qui appelle cette fonction lira et mettra en file d'attente les événements sur leurs files d'attente d'événements correspondantes, et enfin réveillera tous les autres appels à wl_display_read_events() les faisant retourner.

Si un thread annule une préparation de lecture lorsque tous les autres threads qui ont préparé la lecture ont soit appelé wl_display_cancel_read(), soit wl_display_read_events(), tous les threads lecteurs retourneront sans avoir lu de données.

Pour traiter les événements qui ont pu être mis en file d'attente, appelez wl_display_dispatch_pending() ou wl_display_dispatch_queue_pending().

void wl_display_set_default_buffer_size (struct wl_display * display, uint32_t max_buffer_size)

Sets the default size of the internal connection buffers for new clients. It doesn't change the buffer size for existing wl_client.

The connection buffer size of an existing wl_client can be adjusted using wl_client_set_max_buffer_size().

The actual size of the connection buffers is a power of two, the requested max_buffer_size is therefore rounded up to the nearest power of two value.

The minimum buffer size is 4096.

void wl_display_set_global_filter (struct wl_display * display, wl_display_global_filter_func_t filter, void * data)

Set a filter function for global objects

Parameters

display The Wayland display object.
filter The global filter function.
data User data to be associated with the global filter.

Set a filter for the wl_display to advertise or hide global objects to clients. The set filter will be used during wl_global advertisement to determine whether a global object should be advertised to a given client, and during wl_global binding to determine whether a given client should be allowed to bind to a global.

Clients that try to bind to a global that was filtered out will have an error raised.

Setting the filter NULL will result in all globals being advertised to all clients. The default is no filter.

The filter should be installed before any client connects and should always take the same decision given a client and a global. Not doing so will result in inconsistent filtering and broken wl_registry event sequences.

void wl_display_set_max_buffer_size (struct wl_display * display, size_t max_buffer_size)

Adjust the maximum size of the client connection buffers

Parameters

display The display context object
max_buffer_size The maximum size of the connection buffers

Client buffers are unbounded by default. This function sets a limit to the size of the connection buffers.

A value of 0 for max_buffer_size requests the buffers to be unbounded.

The actual size of the connection buffers is a power of two, the requested max_buffer_size is therefore rounded up to the nearest power of two value.

Lowering the maximum size may not take effect immediately if the current content of the buffer does not fit within the new size limit.
